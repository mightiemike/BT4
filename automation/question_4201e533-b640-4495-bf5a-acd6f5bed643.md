Target: `system_events::create_system_transactions`/`signed_system_transaction` (crates/evm/src/evm/system_events.rs:88-112) sign every `SystemEvent` with the fixed `SYSTEM_SIGNATURE = PrimitiveSignature::new(U256::ZERO, U256::ZERO, false)` and `Recovered::new_unchecked(signed_no_hash, SYSTEM_SIGNER)`, i.e. the signature is never actually checked against the caller. Attacker action: send an ordinary CallMessage RLP tx (via `eth_sendRawTransaction`) whose `r=0, s=0, v=false` fields match `SYSTEM_SIGNATURE` exactly, targeting `BridgeWrapper::address()` with `depositCall` selector + attacker-controlled bytes. Preconditions: node accepts arbitrary RLP tx bytes into `CallMessage.txs`; `Recovered::try_from` for a plain tx (crates/evm/src/call.rs:44-48) does not itself force ecrecover to equal caller field unless it fully validates signature. Call sequence: `Evm::execute_call` -> tx decode -> `is_system_caller` check in handler passes if decode yields signer==SYSTEM_SIGNER. Binding: cBTC credited on L2 == a Bitcoin-side deposit that actually happened. Impact: Critical - if signature verification of ordinary CallMessage transactions can be bypassed for a zero-signature tx, an attacker could call `BridgeWrapper::deposit`'s Solidity entrypoint as apparent SYSTEM_CALLER without any actual Bitcoin deposit or short-header-proof check (verify_system_tx in executor.rs only checks `setBlockInfoCall` selector, not deposit calls). Proof: cargo test in crates/evm/src/tests/sys_tx_tests.rs submitting a `CallMessage` with a manually RLP-encoded transaction using r=0,s=0,v=false and to=BridgeWrapper::address(), input=depositCall(attacker_bytes), asserting the call is rejected (recovery must fail) rather than executed, and that `BridgeWrapper::deposit` state (`processedTxIds`, recipient balance) is unchanged.
