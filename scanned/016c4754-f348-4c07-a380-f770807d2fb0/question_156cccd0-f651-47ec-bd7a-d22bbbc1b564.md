In postmicroblock.rs, `try_handle_request` calls `Relayer::static_check_problematic_relayed_microblock(chainstate.mainnet, epoch_id, &microblock)` using `epoch_id` derived from `parent_block_snapshot.block_height`, not from the microblock's own eventual confirming anchored block's epoch. Can an attacker submit a microblock at an epoch boundary where the parent snapshot's epoch differs from the epoch the confirming Nakamoto/epoch2x anchored block will actually be validated under, such that `static_check_problematic_relayed_microblock` verdict on node A (computed at push-time) diverges from the verdict node B recomputes at block-confirmation time, i.e. epoch_id(at push)!=epoch_id(at confirm)? Impact: Critical if this admits a problematic microblock's transactions into a later-accepted block on one node while another node discards them, producing state_root(node A)!=state_root(node B). Proof idea: booted two-epoch chainstate; craft a microblock just before an epoch transition, POST it to both nodes at different heights straddling the epoch boundary, then confirm with an anchored block and diff MARF roots.
