`preprocess_streamed_microblock` in blocks.rs performs `if self.has_descendant_microblock_indexed(&parent_index_hash, &microblock.block_hash())?` then no-ops re-storing, but does NOT re-verify the transactions inside a microblock whose `block_hash()` happens to collide with an already-stored one under a different serialization (e.g., differing but hashing to the same digest is infeasible, but the `microblock.block_hash()` is computed only over the header, not the tx body) — can an attacker submit a `StacksMicroblock` with the same header (hence same `block_hash()`) as an already-staged microblock but a mutated `txs` vector whose `tx_merkle_root` was NOT re-verified against `header.tx_merkle_root` at storage time, so `store_staging_microblock` persists the new tx body while `has_descendant_microblock_indexed` treats it as a duplicate, causing committed_root(node A, using first-seen txs) != committed_root(node B, using second-seen txs) for the eventually confirming block? Impact: Critical, state root not reproducible across nodes. Proof idea: two-node harness; push microblock M1 to node A, then push a header-identical M2 with different `txs` (invalid merkle root) to node B before confirmation, confirm with an anchored block on both, and diff the resulting MARF root / account balances.
