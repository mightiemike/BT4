In `stacks-signer/src/chainstate/v1.rs`, `SortitionState::is_timed_out` returns `false` early if `db.has_signed_block_in_tenure(sortition)?` is true, treating ANY previously signed block (even one whose VRF-seed binding a signer later learns was invalid) as proof the tenure's miner is not timed out. Can an attacker who won ONE valid sortition get a single block signed (satisfying `has_signed_block_in_tenure`), then submit all SUBSEQUENT blocks in that tenure with a VRF proof that no longer needs re-validation by this timeout gate (since VRF-seed is only tenure-start-bound), extending an effectively-stalled tenure indefinitely by drip-feeding minimally-valid blocks purely to keep `has_signed_block_in_tenure` true and suppress `is_timed_out`, at the expense of the true next miner's sortition never getting a chance? Equality: signer's `is_timed_out` verdict must equal the true liveness state of the tenure's miner relative to `block_proposal_timeout`, not merely 'has ever produced one block'. Impact: High — bounded to temporary tip/liveness disagreement (a censorship/stalling issue among signers, not a state-root or reward-equality break), since it only delays fallback to the next miner. Proof idea: signerdb-based unit test where `has_signed_block_in_tenure` is true from block 1 but no further blocks arrive for far longer than `block_proposal_timeout`, assert whether `is_timed_out` ever returns true and whether the protocol has an alternate liveness check (e.g. `get_last_activity_time`) that the miner can also stall via minimal touches.
