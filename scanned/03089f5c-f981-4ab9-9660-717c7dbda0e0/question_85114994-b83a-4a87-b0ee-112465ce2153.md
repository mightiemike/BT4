In `VRFSeed::is_from_proof` (stacks-common/src/types/chainstate.rs), the check is `self.as_bytes().to_vec() == VRFSeed::from_proof(proof).as_bytes().to_vec()`, a plain SHA512/256 digest equality with no domain separation from other VRFSeed-shaped hashes used elsewhere (e.g. sortition hash mixing). Can an attacker find a VRF proof P' (over inputs they control, e.g. a self-chosen `sortition_hash` from a low-value tenure they mined) whose `Sha512Trunc256Sum::from_data(&P'.to_bytes())` collides with a `new_seed` the attacker precommitted in an EARLIER unrelated block-commit, allowing a single `new_seed` value to be validated as `is_from_proof` against two different real proofs from two different tenures? Preconditions: attacker mines two low-cost sortitions and searches proof space (bounded by VRF's own hardness, but the search space over WHICH tenure's proof is checked against a reused seed is attacker-controlled). Equality: `new_seed == VRFSeed::from_proof(the one true parent proof)` must hold uniquely, not admit a reused seed validated against a second unrelated proof. Impact: Critical if achievable, since it lets a tenure's declared randomness be replayed, biasing the attacker's own future sortition odds relative to other miners (SORTITION winner determinism broken). Proof idea: property test attempting to construct two distinct VRFProof byte-strings whose SHA512Trunc256Sum outputs collide within tractable search bounds; expected to fail (safe) demonstrating hash-collision resistance is load-bearing but not a repo-level bug — reframe as regression test asserting `validate_vrf_seed` rejects any non-matching proof/seed pair across two real tenures.
