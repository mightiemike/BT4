In `check_normal_coinbase_tx` (stackslib/src/chainstate/nakamoto/mod.rs), `VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes())` verifies the coinbase VRF proof against `leader_vrf_key` supplied by the caller. Can an attacker cause the caller to pass a DIFFERENT leader key than the one bound to the winning block-commit's `key_block_ptr`/`key_vtxindex` (e.g. by registering a second `LeaderKeyRegisterOp` at the same block height with the same `memo`/miner_pkh but different `public_key`, then crafting a block-commit whose `key_block_ptr` ambiguously resolves), so that `VRF::verify` returns true for a proof that was never generated under the burnchain-committed key? Preconditions: attacker submits two `LeaderKeyRegisterOp`s in the same burn block, one consumed by their own commit. Equality: `leader_vrf_key` passed into `check_normal_coinbase_tx` == the `public_key` field of the `LeaderKeyRegisterOp` at `(block_commit.key_block_ptr, block_commit.key_vtxindex)` that the winning commit references. Impact: Critical — a coinbase VRF proof accepted under an unbound key breaks the SORTITION/VRF identity that a block's randomness traces to the burnchain-committed leader key, letting the attacker forge future-seed influence. Proof idea: integration test registering two keys in one burn block, crafting a commit pointing at key index 1 while proof is generated with key index 2's private key, assert `check_normal_coinbase_tx` correctly errors rather than accepting.
