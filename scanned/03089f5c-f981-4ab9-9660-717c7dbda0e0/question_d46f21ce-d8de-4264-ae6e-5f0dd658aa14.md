Can an unprivileged attacker submit TWO block-commits in the same sortition window that both reference the identical `(key_block_ptr, key_vtxindex)` of a single `LeaderKeyRegisterOp`, such that both are accepted as valid competitors (double-spend of one VRF leader key across two distinct block hashes)? Preconditions: attacker registers one leader key, then crafts two commits with distinct `block_header_hash`/`new_seed` but identical key pointer, submitted before the leader-key-consumption check indexes by winning txid only. Equality: leader_key.consumed_by == exactly one winning `block_commit.txid` per sortition; two commits must never both validate against the same key. Impact: Critical — if both are accepted as sortition candidates, the deterministic VRF-winner computation on node A could differ from node B depending on relay order (SORTITION winner divergence == chain split).
