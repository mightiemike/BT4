`Bridge.sol::deposit`'s `onlySystemOrOperator` modifier (crates/evm/src/evm/system_contracts/src/Bridge.sol line 190, referenced in docs/system-contracts.md) allows this exact function to be called EITHER by the SYSTEM_SIGNER (via the deposit mempool RPC flow) OR directly by the `operator` address as a normal EVM transaction. An unprivileged attacker cannot become `operator`, but can an attacker who is NOT the operator still reach `deposit()` execution logic through the public sequencer/full-node RPC by crafting an ordinary EVM transaction (not going through `citrea_sendRawDepositTransaction`) that calls `Bridge.deposit(moveTx, proof, shaScriptPubkeys)` directly, relying on `onlySystemOrOperator` to revert, and does the REVERT PATH itself leak or otherwise allow a side effect (e.g. `processedTxIds[txId] = true` being set before the modifier check in some inlined ordering, or gas-metering telling the attacker which check failed) that could be chained with a legitimate operator/system deposit to cause `txId already spent` to reject a genuine later deposit of the same underlying Bitcoin transaction submitted correctly? Binding: processedTxIds[txId] transitions to true only as a result of a deposit() call that ALSO successfully completed signature verification and inclusion checks for that exact txId, never as a side effect of a reverted unauthorized call. Impact: High, an unauthenticated EVM transaction attempting to mutate Bridge state should have zero effect; if any partial state mutation survives a revert due to reentrancy or check-ordering, it is a bug freezing a genuine future deposit. Proof idea: cargo test / forge test sending `bridge.deposit(...)` directly from a non-operator, non-system address with a valid moveTx/proof, asserting revert AND that `processedTxIds[txId]` remains false afterward so a subsequent correct system-or-operator call still succeeds.
