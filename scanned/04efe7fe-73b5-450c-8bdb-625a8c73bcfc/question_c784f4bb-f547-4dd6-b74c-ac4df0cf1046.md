[shadow.rs -> NakamotoStagingBlocksConnRef::get_shadow_tenure_start_block] Uses 'ORDER BY height DESC LIMIT 1' to pick the tenure-start block among all shadow-obtained rows for a consensus_hash, which silently prefers the highest-height row rather than the true height-0-of-tenure row if multiple shadow rows with obtain_method=Shadow exist for that hash. Attacker action: cause insertion of two shadow-flagged blocks under the same consensus_hash at different chain_length values (feasible if add_shadow_block's per-height uniqueness check is bypassed as in the chain_length-collision scenario above), so this query returns the wrong 'start' block on nodes that received the rows in different orders (SQLite ORDER BY is stable given identical stored data, but the row set stored per node may differ if one node dropped a row via a race). Preconditions: two shadow rows for one consensus_hash exist on at least one node. Call sequence: get_shadow_tenure_start_block returns block X on node A (which has both rows) but returns block Y on node B (which only received one row due to a dropped/late message), used downstream to seed VRF proof lookup and tenure-start MARF root. Equality broken: tenure-start-block-on-node-A == tenure-start-block-on-node-B for the same consensus_hash. Impact: Critical - divergent tenure-start header leads to divergent recomputed state root. Proof idea: integration test storing two shadow blocks under one consensus_hash on node A only, calling get_shadow_tenure_start_block on both A and a fresh node B seeded with just one of the rows, and asserting the returned NakamotoBlock differs.
