[shadow.rs -> NakamotoChainState::get_shadow_vrf_proof] Retrieves the VRF proof strictly keyed by tip_block_id's tenure_consensus_hash via get_block_header_nakamoto_tenure_id, with no check binding it back to the block-commit that anchors that tenure to a burnchain sortition. Attacker action: submit two sibling shadow-eligible blocks (both with version|=0x80) for the same consensus_hash but different block_hash, each carrying a differently-encoded coinbase VRF proof, and race their delivery to two nodes. Preconditions: consensus_hash T's sortition has already committed (any winner). Call sequence: get_shadow_vrf_proof(tip_block_id=A) and get_shadow_vrf_proof(tip_block_id=B) each returns whichever sibling was stored/queried on that node, since ORDER BY height DESC LIMIT 1 in get_shadow_tenure_start_block picks per-node whichever row exists. Equality broken: sortition-winner's VRF-proof-on-node-A == VRF-proof-on-node-B for the same tenure_consensus_hash T. Impact: Critical - divergent VRF proof binding leads to a state root that cannot be reconciled across nodes. Proof idea: integration test inserting two sibling shadow blocks with distinct VRF proofs under one consensus_hash into separate node databases, then calling get_shadow_vrf_proof on each and asserting the returned Some(proof) values differ.
