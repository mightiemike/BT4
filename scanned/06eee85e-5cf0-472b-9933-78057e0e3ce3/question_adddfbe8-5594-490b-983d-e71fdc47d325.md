`crates/bitcoin-da/src/helpers/parsers.rs::VerifyParsed::get_sig_verified_hash` recovers `key` via `k256::ecdsa::VerifyingKey::from_sec1_bytes(self.public_key())` — i.e. it verifies the signature against the pubkey embedded in the inscription itself, not an externally-trusted pubkey. For `ParsedTransaction::Complete`/`Aggregate`/`SequencerCommitment`, the *caller* (`run_l1_block`, `bitcoin-da/src/service.rs`) then separately checks `blob.sender() == batch_prover_da_public_key` / `sequencer_da_public_key`. Given the attacker fully controls the inscription and can put any `public_key` bytes in the body, can they submit a blob where `public_key` equals the honest `batch_prover_da_public_key`, but the *signature* was produced with an attacker-controlled private key, such that `get_sig_verified_hash` (checking sig against that embedded pubkey) fails and the blob is correctly dropped -- confirm this holds for `DataOnDa::Complete` (which requires signature verification) but does NOT hold for `DataOnDa::Chunk`, which has zero sender/signature check at all, as the asymmetry that breaks AUTHORITY only for Chunk. Impact: Critical, since Chunk data with no authentication can be injected by anyone and consumed by Aggregate. Proof idea: cargo test showing `parse_relevant_transaction` accepts an attacker-crafted Chunk with arbitrary body/no valid signature field required, contrasted with a Complete blob with mismatched pubkey/signature being rejected by `get_sig_verified_hash().is_none()`.
