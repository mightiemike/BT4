Target: NakamotoChainState::check_normal_coinbase_tx combined with StacksChainState::get_coinbase_reward (blocks.rs) height parameter `chain_tip_burn_header_height`. Attacker action: attacker submits a Nakamoto tenure-change block whose header declares a burn_header_height inconsistent with the sortition it claims to descend from (e.g. an off-by-one height feeding into epoch.coinbase_reward's halving schedule), attempting to claim a higher pre-halving coinbase amount for a tenure that actually occurred post-halving. Preconditions: attacker's block is submitted right around a coinbase-halving burn height boundary. Call sequence: calculate_scheduled_tenure_reward reads `chain_tip_burn_header_height` from the SNAPSHOT tied to `block.header.consensus_hash` (via get_block_snapshot_consensus), not from attacker-supplied header fields directly, so the height used for get_coinbase_reward is bound to the sortition DB's recorded burn height for that consensus_hash. Equality that must break: coinbase_at_block computed via StacksChainState::get_coinbase_reward(evaluated_epoch, mainnet, chain_tip_burn_header_height, first_block_height) == the coinbase amount that epoch.coinbase_reward() deterministically assigns to the ACTUAL burn height of the winning sortition, with no attacker-controllable height substitution. Impact: Critical if any header field bypasses the snapshot-derived height, allowing a pre-halving coinbase amount to be claimed post-halving (STX over-mint). Proof idea: Rust test mining a tenure exactly at a coinbase halving/threshold boundary height and asserting the scheduled coinbase strictly matches epoch.coinbase_reward() for the sortition's true recorded burn height, regardless of any block-header-level height field an attacker might manipulate.
