Target: `LeaderBlockCommitOp::is_parent_genesis` returns `self.parent_block_ptr == 0 && self.parent_vtxindex == 0`, used by consumers to treat a commit as chaining to genesis. `parse_from_tx`'s sanity check only rejects `parent_block_ptr == 0 && parent_vtxindex != 0` (asymmetric guard) — it does NOT reject `parent_block_ptr != 0 && parent_vtxindex == 0`, meaning an attacker can craft a commit with a nonzero `parent_block_ptr` but `parent_vtxindex = 0`, which `is_parent_genesis()` classifies as NOT genesis (since `parent_block_ptr != 0`), yet if vtxindex 0 within that referenced block corresponds to a coinbase/non-commit transaction, the referenced 'parent' commit doesn't actually exist, and downstream linking logic (`expected_chained_utxo`/`spent_output()` matching in `make_min_median_distribution`) may silently fail to link (treating it as an unlinked/fresh chain, `burns=1` fallback) inconsistently versus a node that has a stricter interpretation. Preconditions: attacker submits a commit with `parent_block_ptr>0, parent_vtxindex=0` pointing at a real prior block but invalid vtxindex 0 slot. Call sequence: `parse_from_tx` accepts (no rejection for this combination) -> `check` (no explicit parent-existence check beyond `check_intended_sortition` on the missed-commit path) -> `make_min_median_distribution` -> ambiguous linking (fallback `burns=1` vs real chain value) depending on node interpretation. Equality broken: parent-commit resolution for `(parent_block_ptr, parent_vtxindex)` on node A == node B. Impact: Critical if the ambiguity yields divergent `burns` values feeding `sample_burn_distribution`'s ranges, causing a chain split.
