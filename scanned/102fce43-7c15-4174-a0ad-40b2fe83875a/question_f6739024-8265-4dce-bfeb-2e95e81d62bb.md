Target: `SortitionDB::pick_recipients`'s `reward_set_vrf_seed.choose_two(reward_set_size as u32)` (called from `get_next_block_recipients`) selects PoX reward-set indices deterministically from `parent_snapshot.sortition_hash.mix_burn_header(...)`. This has no attacker-controlled input directly, but `LeaderBlockCommitOp::check`'s `self.check_pox(epoch.epoch_id, burnchain, tx, reward_set_info)` validates the miner's `commit_outs` against `reward_set_info`'s recipients; an attacker submits a commit whose `commit_outs` list matches the recipients returned by a stale/cached `RewardSetInfo` computed under a different `next_pox_info` branch than the one the validating node currently holds (race across a reward-cycle boundary block). Preconditions: burn block that is the first block of a new reward cycle, attacker submits the commit right at the boundary. Call sequence: `evaluate_sortition` -> `get_next_block_recipients` -> `pick_recipients`/`pick_recipients_from_next_cycle` branch selection -> `check_pox` validates `commit_outs` against possibly-mismatched recipients on two nodes with different anchor-block visibility. Equality broken: `RewardSetInfo` used by `check_pox` on node A == on node B for the same sortition. Impact: Critical, a commit with `commit_outs` valid on one node's reward-set view but invalid on another's is accepted/rejected inconsistently, producing a chain split at reward-cycle boundaries. Proof idea: two-node harness where one node has processed the anchor block and the other hasn't, both receiving the same boundary block-commit, asserting `check()`'s Ok/Err result is identical.
