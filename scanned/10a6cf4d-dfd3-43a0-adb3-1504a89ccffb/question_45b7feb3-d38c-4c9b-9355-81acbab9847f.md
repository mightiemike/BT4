[File: stackslib/src/net/relay.rs, fn `Relayer::static_check_problematic_relayed_block` / `static_check_problematic_relayed_nakamoto_block`] These functions are only used for relay-gating (should we forward/store the block) but are *not* the same function as `NakamotoBlock::validate_problematic_txs`/`validate_transactions_static`, meaning a block can fail relay-level `static_check_problematic_relayed_nakamoto_block` on node A (so A drops it and never gossips further) while still being validly accepted by `NakamotoChainState::validate_nakamoto_block_static` on node B who received it via a different path (e.g. HTTP upload rather than P2P relay), since the actual consensus-level static check never calls `static_check_problematic_relayed_tx` on the whole block. Preconditions: attacker submits a block containing a `tx_exceeds`-style deep-AST contract-publish directly via HTTP upload to node B while relaying nothing to node A over P2P. Call sequence: node B: `posttransaction`/block-upload path bypasses `Relayer::do_static_problematic_checks` gating that P2P relay applies via `filter_problematic_transactions`, so node B's mempool/staging accepts and later builds on the tx -> node A never receives it via relay because `static_check_problematic_relayed_nakamoto_block` would have dropped it, but eventually receives the resulting *block* via block-relay (different code path, `preprocess_downloaded_blocks`/`preprocess_pushed_blocks`) which does NOT re-run `static_check_problematic_relayed_nakamoto_block` before calling `NakamotoChainState::validate_nakamoto_block_static`. Equality: block-acceptance verdict for the same block bytes via the HTTP-upload path == verdict via the P2P block-relay path == verdict at `validate_nakamoto_block_static`. Impact: Critical — if the block is accepted into node B's canonical chain despite containing a tx that `static_check_problematic_relayed_tx` would flag, and other honest nodes' local mempool policies would have refused to ever build such a block, this exposes a path to a block that only some nodes will build on top of, risking a fork. Proof idea: two-node harness; submit an oversized-AST contract-publish via `posttransaction` directly to node B (bypassing P2P relay's `filter_problematic_transactions`), mine it into a block, relay that *block* (not the raw tx) to node A, and assert whether `validate_nakamoto_block_static` on node A accepts or rejects it, and whether the two nodes end up with different canonical tips.
