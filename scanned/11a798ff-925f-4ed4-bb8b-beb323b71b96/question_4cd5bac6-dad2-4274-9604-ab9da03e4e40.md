Target: `NakamotoChainState::validate_shadow_against_burnchain` and `check_shadow_coinbase_tx` (stackslib/src/chainstate/nakamoto/shadow.rs). Attacker action: an unprivileged participant who runs tooling attempts to submit a would-be shadow block (`header.version` with the shadow bit `0x80` set) over the normal P2P block-relay path, crafted with a VRF proof and coinbase recipient set to their own address rather than the burn address. Preconditions: attacker controls their own tenure sortition win and crafts a block whose header sets the shadow-block bit. Call sequence: block enters `store_block` in staging_blocks.rs, which classifies `obtain_method` as `NakamotoBlockObtainMethod::Shadow` purely from `block.is_shadow_block()`; validation later calls `check_shadow_coinbase_tx`, which requires `recipient == StacksAddress::burn_address(mainnet)`. Equality that breaks: shadow-tenure coinbase recipient enforced == burn address, but the check only fires for the shadow path, not the normal one — an attacker-set shadow bit could relay through `add_shadow_block`'s `is_shadow_tenure` gate if a normal tenure is empty. Impact: Critical if it lets an attacker mint an un-burned coinbase into a shadow tenure that becomes canonical. Proof idea: integration test constructing a `NakamotoBlock` with the shadow header bit and a non-burn-address coinbase recipient, call `add_shadow_block`/`process_shadow_block`, and assert it is rejected with `InvalidStacksBlock`.
