Target: `StacksChainState::find_next_staging_block`'s `can_attach` re-derivation against `block_headers` (stackslib/src/chainstate/stacks/db/blocks.rs). Attacker action: submit a block whose parent was already `delete_orphaned_epoch_data`-marked (`orphaned=1, processed=1`) on one node due to an earlier-processed sibling, but not yet propagated as orphaned on a peer node that has a slower coordinator. Preconditions: burnchain fork causes one sortition-winning block-commit to be orphaned on node A but the corresponding staging block is still `attachable=1, processed=0` on node B. Call sequence: `find_next_staging_block`'s SQL only filters `processed = 0 AND attachable = 1 AND orphaned = 0`; if a race lets `can_attach` return true on B while A has already invalidated the parent, B calls `process_next_staging_block` and accepts a block whose parent is invalid. Equality that breaks: a block accepted as a valid chain extension on node B == rejected (orphaned) on node A for the identical parent-child pair. Impact: Critical — one node permanently commits state on top of an invalid/unavailable parent, producing a state root divergent from the network. Proof idea: two-node harness: on node A, call `delete_orphaned_epoch_data` for the parent before node B processes the pending child; run `process_blocks` on B and assert it must NOT produce a receipt (i.e., that the orphan-propagation happens before staging-block processing on every node).
