Target: `NakamotoStagingBlocksTx::add_shadow_block` (stackslib/src/chainstate/nakamoto/shadow.rs) and its `is_shadow_tenure` gate. Attacker action: submit a normal (non-shadow) Nakamoto block into a tenure consensus hash that a SIP-authorized shadow-repair tool has already populated with a shadow block, or vice versa, via crafted P2P relay timing. Preconditions: a tenure's consensus hash exists in `nakamoto_staging_blocks` with `obtain_method = Shadow`; attacker races a normal block with the identical `consensus_hash`. Call sequence: `store_block` checks `self.conn().is_shadow_tenure(&block.header.consensus_hash)? && !block.is_shadow_block()` and rejects; but the check is asymmetric — verify whether a shadow block can be inserted into a non-empty non-shadow tenure is enforced only in `add_shadow_block`, not in the generic block-acceptance path reachable from P2P. Equality that breaks: the set of blocks accepted into a given tenure on node A (which enforces the mutual-exclusion gate) == the set accepted on node B (if the gate is bypassable via a different insertion entrypoint). Impact: Critical — a shadow block promoted into a tenure that already has honestly-mined normal blocks would fork the canonical chain. Proof idea: integration test that first stages a normal block for consensus hash CH via the ordinary download path, then calls `add_shadow_block` for the same CH, and asserts the second call returns `Err(InvalidStacksBlock(\"Shadow block cannot be inserted into non-empty non-shadow tenure\"))` on every entrypoint, not just this one.
