Target: `NakamotoChainState::get_expected_burns` (stackslib/src/chainstate/nakamoto/mod.rs). Attacker action: submit a non-tenure-change Nakamoto block whose `parent_block_id` points to a block not yet processed by the target node but already processed (with different `total_burns`) by another node due to arrival-order differences. Preconditions: parent block staged but unprocessed on node A, processed on node B; both received the same child block over P2P. Call sequence: on node A `get_expected_burns` returns `Ok(None)` since `get_block_header` on the unprocessed parent misses, deferring the burn check; on node B it returns `Some(parent.anchored_header.total_burns())` and enforces it in `common_validate_against_burnchain`. Equality that breaks: `expected_burn` computed on node A == `expected_burn` computed on node B for the same child block. Impact: High, a minority-triggerable ordering-dependent validation divergence that can allow a block accepted on one node while blocked on another (bounded to staging delay, escalates to Critical only if it persists into finalized state). Proof idea: two-node harness where node B processes the parent first and node A does not; submit the same child block to both and diff their `get_expected_burns` results and subsequent accept/reject outcome.
