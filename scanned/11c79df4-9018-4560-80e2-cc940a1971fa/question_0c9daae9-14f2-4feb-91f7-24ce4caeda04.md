In crates/sequencer/src/db_provider/mod.rs, DbProvider::new constructs Evm::<DefaultContext>::default() bound to whatever storage: <DefaultContext as Spec>::Storage is passed in, and every subsequent trait method (basic_account, storage, last_block, chain_spec, finalized_block_number) reads through this single storage handle with no field asserting which L1/L2 height this storage snapshot corresponds to versus the ledger_db's recorded head. Preconditions: sequencer processing a block that applies a BridgeDeposit system event concurrently with RPC reads on the same DbProvider clone (DbProvider derives Clone, so storage is shared, cloned handle). Call sequence: DbProvider::new used by CitreaMempool and RPC handlers share the same underlying storage snapshot lineage -> AccountReader::basic_account or StateProvider::storage read mid-block-application. Impact (Critical, CUSTODY): an RPC consumer (e.g., an exchange or bridge watcher) can observe a transient, unfinalized cBTC balance that does not correspond one-to-one with a completed Bitcoin deposit, and nothing in DbProvider re-derives or flags this as provisional.
