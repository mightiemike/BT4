In crates/sequencer/src/db_provider/mod.rs, ChainSpecProvider::chain_spec for DbProvider builds an Arc<ChainSpec> fresh on every call, re-deriving genesis/config from self.cfg() and self.genesis_block() each time rather than caching a single canonical value, meaning two calls separated by a storage mutation (e.g., an applied SystemEvent::BridgeInitialize re-run or a corrupted genesis re-write) could yield two different ChainSpec objects from the same DbProvider instance. Attacker action: none directly triggers genesis mutation (only privileged code writes genesis), but an unprivileged attacker can exploit any downstream code that calls chain_spec() twice across a block boundary and assumes referential/value stability for validating a transaction's replay-protection (chain_id) fields consistently. Preconditions: sequencer running with CitreaMempool's validator holding a chain_spec snapshot captured once at CitreaMempool::new time, while other code paths call DbProvider::chain_spec() fresh per-call. Call sequence: mempool holds stale chain_spec-derived validator config; a later fresh DbProvider::chain_spec() call by another RPC path could disagree if cfg() or genesis_block() ever returns different values for the same node lifetime. Binding: the ChainSpec DbProvider::chain_spec() returns at mempool-construction time == the ChainSpec it would return during actual block execution for the same node lifetime. Impact (High): a transaction validated against one snapshot of chain configuration could execute under another, risking honest nodes with different call timings diverging on transaction acceptance criteria. Proof idea: cargo test calling DbProvider::chain_spec() twice across a simulated genesis-adjacent state mutation and asserting both invocations are byte-for-byte equal.
