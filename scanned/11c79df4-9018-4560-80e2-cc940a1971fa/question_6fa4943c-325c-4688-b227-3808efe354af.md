In crates/sequencer/src/db_provider/mod.rs, DbProvider::cfg reads EvmChainConfig purely from self.storage via self.evm.get_chain_config, and this exact chain_id feeds DbProvider::chain_spec (impl ChainSpecProvider) which is consumed by CitreaMempool's TransactionValidationTaskExecutor to validate EIP-155 chain_id on incoming transactions. Attacker action: submit an EVM transaction via eth_sendRawTransaction signed with a chain_id equal to whatever cfg.chain_id currently reports (attacker can read it via eth_chainId first). Preconditions: sequencer running on any network (mainnet/testnet/devnet) with genesis-configured chain_id. Call sequence: DbProvider::cfg -> ChainSpecBuilder::chain(Chain::from_id(cfg.chain_id)) -> mempool validator accepts tx -> runner.rs includes tx in L2 block whose journal a batch prover later signs. Binding: chain_id DbProvider::cfg exposes to the mempool == chain_id the light-client/batch-proof circuit enforces via citrea_network_to_chain_id(network) when validating BatchProofMethodIdBody.chain_id (crates/sovereign-sdk/rollup-interface/src/state_machine/da.rs). Impact (Critical, AUTHORITY): if these two chain_id sources are independently configured and ever diverge, a transaction admitted by the sequencer's mempool could be included in a chain whose batch proof targets a different chain_id, letting a state transition be accepted for the wrong network context. Proof idea: cargo test asserting DbProvider::cfg().chain_id equals citrea_network_to_chain_id(Network) used by the circuit for the same running network.
