In crates/sequencer/src/db_provider/mod.rs, DbProvider::bytecode_by_hash (impl StateProvider) returns code via self.evm.offchain_code.get(code_hash, ...) without verifying that code_hash corresponds to a contract deployed through a transaction actually included in a proven L2 block. Attacker action: deploy a contract via a normal EVM transaction to the public sequencer RPC, then immediately call eth_getCode / any RPC path that triggers DbProvider::bytecode_by_hash before the block containing the deployment has been committed in any DA-inscribed sequencer commitment. Preconditions: sequencer node with pending (not yet DA-committed) blocks. Call sequence: eth_sendRawTransaction (deploy) -> block sealed by runner.rs -> DbProvider::bytecode_by_hash serves code -> no cross-check against SequencerCommitment merkle_root posted to DA. Binding: bytecode DbProvider::bytecode_by_hash serves for code_hash == bytecode present in the L2 block whose hash is included in the merkle_root of the SequencerCommitment eventually posted to Bitcoin DA. Impact (High): an honest full node or light client relying on this RPC response before DA commitment can diverge from state the proved chain ultimately contains if the sequencer reorgs its uncommitted blocks. Proof idea: cargo test comparing bytecode returned pre-commitment vs bytecode present in the state root once a SequencerCommitment covering that block is DA-inscribed and processed.
