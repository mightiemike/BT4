`TxInfo` in crates/evm/src/evm/handler.rs has field `l1_diff_size: u64` computed via `calc_diff_size(evm.ctx())`, which iterates `JournalEntry` variants collected during `revm` execution and calls `context.db().is_first_time_committing_address(&addr)` on `EvmDb` (crates/evm/src/evm/db.rs) to decide whether to add `ACCOUNT_IDX_KEY_SIZE + ACCOUNT_IDX_SIZE`. Since this predicate reads mutable DB-only bookkeeping state (not the `ReadWriteLog`/`Witness` itself), can a transaction touching an address whose 'first-time' status differs between the sequencer's native `ProverStorage`-backed `EvmDb` and the guest's `ZkStorage`-backed `EvmDb` (e.g. because the account index was populated by side effects of a prior transaction whose write was pruned or reordered) produce a different `l1_diff_size`/`l1_fee` natively than in the circuit? Binding: `l1_diff_size` computed by `calc_diff_size` in `CitreaEvm::output` on `ProverStorage` == `l1_diff_size` computed by `calc_diff_size` on `ZkStorage` for the same tx sequence. Impact: Critical — a diverging L1 fee changes the post-tx account balances and hence the final state root, so a batch proof commits a root the honest full node's native execution does not produce. Proof idea: cargo test in crates/evm driving two fresh `EvmDb` instances (one via `ProverStorage`, one via `ZkStorage` fed the recorded witness) with an address-creating tx and assert identical `TxInfo::l1_diff_size`.
