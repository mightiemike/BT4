In `LightClientProofCircuit::run_l1_block`, `DataOnDa::Chunk(chunk)` branch calls `ChunkAccessor::<S>::insert(blob.wtxid(), chunk, &mut working_set)` with no sender check. Can an unprivileged attacker inscribe a Bitcoin reveal transaction whose payload borsh-deserializes as `DataOnDa::Chunk(attacker_bytes)` and whose wtxid collides with (or is mined before) the wtxid the honest batch prover intends to use for its own chunk, such that `ChunkAccessor::get(wtxid, ..)` inside the `DataOnDa::Aggregate` branch returns `attacker_bytes` instead of the batch prover's chunk? Preconditions: regtest bitcoind with `REVEAL_TX_PREFIX`-matching reveal script, light-client-prover harness with a batch prover key configured, empty JMT chunk slot for that wtxid. Call sequence: attacker inscribes chunk tx -> `run_l1_block` iterates `da_txs`, hits `DataOnDa::Chunk` -> `ChunkAccessor::insert` stores attacker bytes keyed by wtxid -> later a legitimate `DataOnDa::Aggregate(_, wtxids)` from the real batch prover looks up that same wtxid via `ChunkAccessor::get` -> concatenation is fed to `DS::decompress_chunks` -> `process_complete_proof`. Binding: bytes(`ChunkAccessor::get(wtxid)`) == bytes the batch prover chunked and signed for that wtxid. Impact: Critical - a `BatchProofCircuitOutput` accepted by `process_complete_proof` for a state transition the batch prover never produced (PROOF SOUNDNESS violated), affecting all cBTC custody and state-root consumers of the light client proof. Proof idea: cargo test in `crates/light-client-prover/src/tests` that submits an attacker `DataOnDa::Chunk` blob with a chosen wtxid before the batch prover's chunk lands, then submits an `Aggregate` referencing that wtxid, and asserts the resulting `LightClientCircuitOutput.l2_state_root` differs from the state root a run without attacker interference would produce.
