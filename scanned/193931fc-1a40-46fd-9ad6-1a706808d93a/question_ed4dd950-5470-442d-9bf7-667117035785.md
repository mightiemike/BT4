target: `system_events::signed_system_transaction`/`create_system_transactions`, which always encode `nonce` from the caller-supplied `evm_nonce`/`sys_signer_nonce` argument. Attacker action: none directly (attacker cannot call these), but attacker can race the mempool by submitting a normal tx from `SYSTEM_SIGNER`-colliding signature (per conversions.rs bug above) with a nonce equal to the current system-signer on-chain nonce, before the sequencer's own `process_sys_txs` runs in the same L2 block. Preconditions: sequencer builds txs in order sys-txs-first; attacker tx admitted to pool under SYSTEM_SIGNER identity via the forged-signature path. Call sequence: mempool orders txs -> `process_sys_txs` calls `evm.account_info(&SYSTEM_SIGNER,...)` to fetch nonce -> attacker's forged tx already consumed that nonce -> legitimate `BridgeDeposit`/`BitcoinLightClientSetBlockInfo` system tx now has wrong nonce and is rejected or shifted. Binding: nonce consumed by the block's system transactions == nonce sequence `create_system_transactions` expects strictly increasing from `system_signer.nonce`. Scoped impact: Critical/High boundary — if a legitimate `BridgeDeposit` system event is starved out this block (nonce collision), that deposit's cBTC mint never happens this block though it may retry next block (impact: temporary but real desync between event log and expected mint, use to test PROOF SOUNDNESS around system tx nonce assumptions). Proof idea: cargo test in crates/sequencer that submits a forged SYSTEM_SIGNER-signature tx into the mempool right before `produce_and_run_system_transactions`/`process_sys_txs`, and assert whether a legitimate `SystemEvent::BridgeDeposit` for the same block fails due to nonce mismatch (`L2BlockModuleCallError::EvmTransactionExecutionError` nonce-too-high/low).
