Attacker action: query `eth_getLogs` with a filter spanning a block range and compare returned logs against logs independently reconstructed from the JMT-proven transaction execution results (i.e., verify that accessory-state-served logs cannot diverge from what the JMT state root implies happened). Preconditions: none, public RPC. Call sequence: `eth_get_logs` -> `logs_for_filter` -> reads `self.receipts`/`self.transactions` StateMaps via `working_set.accessory_state()`, which per `sov-modules-core/src/storage/mod.rs` docs is explicitly *not* part of consensus/JMT state and thus not checked by any proof. Binding: the set of logs served via `eth_getLogs` for L2 block N == the set of logs that would be derived by re-executing L2 block N's transactions against the JMT-proven state for block N (i.e., accessory-state logs must be a faithful, non-divergent projection of the JMT-committed execution). Impact: Critical if an attacker could get a node's accessory `receipts`/`transactions` store to diverge from the JMT-proven execution (e.g., via a code path that writes logs without a corresponding successful JMT-committed transaction), it would let a false claim (e.g., a fabricated event that downstream bridge/oracle logic trusts) become effectively 'provable' to off-chain consumers despite never having happened on the proven chain. Proof idea: cargo test comparing `eth_getLogs` output for a block against logs recomputed by replaying that block's transactions through the batch-proof circuit's `StfBlueprint::apply_l2_block`, asserting identical log sets and ordering.
