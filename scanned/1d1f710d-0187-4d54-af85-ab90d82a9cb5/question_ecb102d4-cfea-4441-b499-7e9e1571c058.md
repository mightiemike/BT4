`update_proof.verify_update(jmt::RootHash(prev_state_root), jmt::RootHash(new_root), batch)` (zk_storage.rs:101-109) uses `witness.get_hint()` for both `update_proof` and `new_root`, meaning the circuit *trusts* the host-supplied `new_root` and merely checks the proof is internally consistent with it — it does not independently recompute `new_root` from the batch. Can an attacker who controls only transaction content cause a scenario where native `ProverStorage::compute_state_update` (which *does* independently compute the new root via the JMT crate) legitimately produces root R1 for a given block, but a malicious or buggy host (not this attacker's role, but exercised via this attacker's crafted state diff triggering an edge case in the JMT update, e.g. an empty-value delete of a nonexistent key) causes the *witness-embedded* `new_root` fed to the guest to be R2 != R1 while `verify_update` still passes because it only checks proof-validity for whatever `new_root` hint is given? Binding: `new_root` witnessed into the circuit (zk_storage.rs:102) == the root `ProverStorage::compute_state_update` independently derives for the identical `state_log`/`batch`. Impact: Critical, a batch proof could commit to a root that the honest full node's independent JMT computation never produced, for state diffs involving deletes of already-absent keys or other edge-case JMT updates.
