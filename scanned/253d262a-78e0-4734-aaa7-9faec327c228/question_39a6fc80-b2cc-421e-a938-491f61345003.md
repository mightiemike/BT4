Target: `NakamotoChainState::get_expected_burns` in nakamoto/mod.rs, used to enforce `block.header.burn_spent == expected_burn` in `append_block`. Attacker action: attacker miner produces a tenure-change block whose `TenureChangePayload.burn_view_consensus_hash` points to a burn view snapshot with a `total_burn` value that is correct for the attacker's own Bitcoin observation but inconsistent with a signer/node that saw a different set of block-commits at the same height due to network partition of Bitcoin peers. Preconditions: burn view sortitions available differ by node due to Bitcoin P2P propagation lag (not a Bitcoin-consensus bug, just timing). Call sequence: `append_block` -> `get_expected_burns` -> `SortitionDB::get_block_snapshot_consensus(burn_view_ch)` -> compare `total_burn`. Equality: `block.header.burn_spent` accepted on node A == `expected_burn` computed on node B for the same `burn_view_consensus_hash`. Impact: Critical — a block valid on one node (matches its locally observed total_burn) but invalid on another, causing a fork. Proof idea: integration test with two chainstate DBs seeded with divergent (but each internally consistent) sortition histories for the same consensus_hash's ancestry, submit the identical block, and assert differing `append_block` outcomes.
