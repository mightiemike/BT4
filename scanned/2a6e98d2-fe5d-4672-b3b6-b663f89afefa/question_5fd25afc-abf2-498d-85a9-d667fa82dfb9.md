`NakamotoBlockHeader::check_normal_coinbase_tx` (stackslib/src/chainstate/nakamoto/mod.rs lines 1808-1856) verifies `VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes())` using `tenure_burn_chain_tip.sortition_hash`, but never cross-checks that `leader_vrf_key` itself belongs to the same leader-key registration transaction that the winning block-commit referenced. Can an attacker submit a block-commit that wins sortition (their own BTC, correct burn amount) but references a *stale* leader-key VRF public key from an earlier registration (still technically 'the miner's' key but for a since-superseded VRF keypair), producing a coinbase whose VRF proof validates against `sortition_hash` yet whose `MinerPaymentSchedule.recipient` (derived independently from `coinbase_tx.get_origin()` in `make_scheduled_miner_reward`) still resolves correctly to that same attacker — i.e., does the reward path enforce recipient==coinbase-tx-signer exactly once, with no double-crediting if the same attacker resubmits the same tenure's coinbase under two different but validly-registered leader keys across a fork choice? Preconditions: attacker owns two valid, distinct leader-key registrations both eligible at the winning sortition height. Call sequence: fork A uses leader-key 1's VRF proof, fork B (same attacker, same sortition win) uses leader-key 2's VRF proof for a differently-hashed block at the same tenure-start; both pass `check_normal_coinbase_tx` independently since each checks only its own `leader_vrf_key`. Equality broken: each tenure's authorising sortition == exactly one accepted block/coinbase; two structurally-valid coinbases for the same sortition must not both mature and pay. Impact: Critical if chain-selection doesn't strictly pick one tenure-start block per sortition before scheduling rewards (would be a chain split, not just a double pay). Proof idea: integration test where the same sortition winner produces two candidate tenure-start blocks with different VRF proofs (both technically owned by attacker), assert only the chain-selected one's `MinerPaymentSchedule` is ever inserted via `insert_miner_payment_schedule`, and the other is rejected at the block-selection layer before reaching reward scheduling.
