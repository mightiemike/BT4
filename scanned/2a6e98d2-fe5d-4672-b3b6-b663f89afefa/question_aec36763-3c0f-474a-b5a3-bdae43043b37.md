In `find_mature_miner_rewards` (accounts.rs), `poison_recipient_opt` is fetched via `StacksChainState::get_poison_microblock_report(clarity_tx, reward_height)` (line 1030) and, if present, is passed into `calculate_miner_reward` to redirect the *miner's own* coinbase+fees to the reporter. Can an attacker file a poison-microblock report (`filed via P2P poison report, unprivileged`) against a tenure height where the actual malicious microblock fork was never mined by that tenure's miner (a false/stale report referencing a height the reporter doesn't actually have valid conflicting microblock headers for), such that `get_poison_microblock_report` returns a stored report keyed only by `height` without validating it corresponds to *that specific* miner's microblock fork at maturation time, causing an honest miner's full coinbase+fees to be redirected to an unrelated reporter address? Preconditions: attacker has broadcast two conflicting microblocks under some other miner's stream and filed a poison report accepted at block height = reward_height. Call sequence: `get_poison_microblock_report` -> `calculate_miner_reward(mainnet, epoch, &miner, &miner, &users, &parent_miner, poison_recipient_opt.as_ref())` -> honest miner's `MinerReward.recipient` is overwritten to the attacker's `poison_recipient_opt` address. Equality broken: reward paid to sortition winner's specified recipient == recipient only if the poison report genuinely implicates *that* winning miner's microblocks; a report for a different miner or fork should not redirect this tenure's reward. Impact: Critical, block-reward theft from an honest miner to an attacker-controlled poison-reporter address. Proof idea: integration test where a valid PoisonMicroblock report exists for consensus data not actually produced by the miner being matured at `reward_height`, assert `find_mature_miner_rewards` does NOT redirect that miner's `MinerReward.recipient` unless the report is proven to correspond to that exact tenure/miner's conflicting microblocks.
