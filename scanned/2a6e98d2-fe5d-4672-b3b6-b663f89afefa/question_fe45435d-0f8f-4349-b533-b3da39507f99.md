For a Nakamoto tenure using `MinerPaymentTxFees::Nakamoto`, both functions return `0` unconditionally (line 207, 217) regardless of `parent_fees` — is `parent_fees` (used in `calculate_scheduled_tenure_reward`) reconciled anywhere else so total credited equals total fees collected, or can an attacker construct an epoch-2 streamed-fee total not divisible by 5 (e.g. streamed=7) so that `streamed_tx_fees_confirmed()+streamed_tx_fees_produced()=(21/5)+(14/5)=4+2=6 != 7`, permanently orphaning 1 uSTX per block, and does this rounding loss compound to a state-root mismatch if two nodes compute the split differently due to future code drift? Preconditions: mine an epoch-2 block whose streamed microblock fee total is not a multiple of 5. Call sequence: `calculate_miner_reward` -> `streamed_tx_fees_confirmed`/`streamed_tx_fees_produced` -> summed into two separate `MinerReward` structs -> `process_matured_miner_rewards`. Equality broken: reward paid (sum of confirmed+produced shares) == coinbase+fees earned (streamed fee total), off by up to 4 uSTX per block. Impact: High, bounded permanent fee loss (rounding dust), not a double-payment, but is deterministic and identical on every node so it does not cause a state-root mismatch by itself — flag as a fee-loss bug bounded to a few uSTX.
