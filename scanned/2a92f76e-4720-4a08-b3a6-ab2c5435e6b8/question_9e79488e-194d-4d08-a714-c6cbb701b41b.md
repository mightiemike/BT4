BitcoinBlockParser::parse_data extracts opcode = data[MAGIC_BYTES_LENGTH] and payload = data[MAGIC_BYTES_LENGTH+1..] from an OP_RETURN script only after checking data.starts_with(magic_bytes) and data.len() > MAGIC_BYTES_LENGTH. Can an attacker craft an OP_RETURN payload exactly MAGIC_BYTES_LENGTH+1 bytes long (data.len() == MAGIC_BYTES_LENGTH+1, one over the '<=' cutoff) so LeaderBlockCommitOp::parse_data (which requires data.len() >= 77) rejects on all nodes but a shorter downstream opcode handler (e.g., leader-key-register with fewer required bytes) accepts it, producing an operation with a truncated/garbage seed or key field that still validates? Equality broken: SORTITION — the winner computed from VRFSeed/new_seed must be identical bit-for-bit across nodes. Impact: Critical, since a garbage new_seed silently accepted feeds a different next-sortition VRF seed on some nodes than others. Proof: integration test feeding a boundary-length OP_RETURN tx and diffing SortitionDB::get_block_snapshot's sortition_hash across two independently-fed nodes.
