BitcoinBlockParser::parse_tx computes txid via Txid::from_vec_be(tx.txid().as_bytes()).unwrap() and this txid becomes the LeaderBlockCommitOp.txid used later as an idempotency/uniqueness key when the sortition handler records candidate commits per burn block. Can an attacker broadcast two distinct Bitcoin transactions (different witness/scriptSig, e.g. differing only in a low-S vs. high-S signature malleated variant under BitcoinTxInputRaw parsing) that Bitcoin Core treats as distinct txids but that encode byte-identical OP_RETURN commit data (same block_header_hash, new_seed, parent/key pointers), so both are separately counted as valid, distinct LeaderBlockCommitOp candidates competing in the same sortition, when the intent was one commit per miner-slot? Equality broken: SORTITION — the burn-weight sum used for the deterministic VRF-weighted draw must count each real economic commitment once. Impact: High, sortition-weight duplication bounded to the attacker's own burn amount (no majority needed to demonstrate the mechanism), escalating to Critical if it lets a minority miner double-count its own burn to bias winner selection. Proof: submit both malleated txs into a regtest burnchain, and assert SortitionDB's computed burn-weight total is NOT simply the sum of two op-derived burn_fee entries when only one economic burn occurred.
