Target: `LeaderBlockCommitOp::check` -> `check_pox` (PoX-address validation against `reward_set_info: Option<&RewardSetInfo>`). Attacker action: submit a block-commit whose `commit_outs` PoX addresses partially match the expected reward set but include one address that would only be valid recipients under a *different* reward cycle's `RewardSetInfo` (e.g., during a reward-cycle boundary burn block), exploiting a possible off-by-one in which `reward_set_info` a node has cached vs. computed fresh via `pick_recipients`. Preconditions: burn block at the exact reward-cycle transition height. Call sequence: `sortdb.rs::evaluate_sortition` computing `reward_set_info` via `pick_recipients` -> `check` -> `check_pox`. Equality: `reward_set_info` (and hence `check_pox`'s accept/reject) computed on node A == on node B for the same burn height. Impact: Critical — divergent PoX-recipient validation at a reward-cycle boundary is a documented consensus-fragile point; a commit accepted on one node and rejected on another splits the chain. Proof idea: two-node harness both syncing to the exact reward-cycle-boundary height and asserting identical `reward_set_info` and identical `check_pox` result for the boundary commit.
