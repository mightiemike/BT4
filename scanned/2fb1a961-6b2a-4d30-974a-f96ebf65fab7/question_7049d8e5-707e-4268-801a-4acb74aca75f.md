The macro-generated StacksMessageCodec::consensus_deserialize for byte-array types (impl_byte_array_message_codec in stacks-common/src/codec/macros.rs) is used for ConsensusHash, which feeds check_valid_consensus_hash's db_handle.has_consensus_hash lookups in tenure.rs. Because $thing::from_bytes(&buf).expect(...) panics rather than returning a codec Error if from_bytes ever has an internal validity constraint (currently none for ConsensusHash, but the macro provides no compile-time guarantee that future byte-array wrapper types stay panic-free), can an attacker submit a Nakamoto block or a P2P message containing a byte-array field for a TYPE THAT DOES enforce a validity constraint in its from_bytes (audit which impl_byte_array_message_codec! invocations wrap a from_bytes with fallible internal checks) with a payload chosen to trigger that panic during consensus_deserialize inside block-relay parsing on a node, crashing that node's block-processing thread and thereby permanently rejecting all subsequent valid blocks on that node while other nodes using a from_bytes without the same constraint (or that never received the malformed bytes) continue advancing? Equality broken: liveness/verdict parity across nodes on all following blocks. Impact: Critical if such a from_bytes exists in the codebase (chain split via selective node crash) -- flag as High until a concrete from_bytes with an internal panic-capable check is identified. Proof idea: grep every impl_byte_array_message_codec! invocation, inspect each wrapped type's ::from_bytes for panics on out-of-range input, and for any found, craft the triggering byte sequence and drive it through consensus_deserialize inside a full block-parsing integration test on two nodes.
