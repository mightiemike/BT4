StacksChainState::calculate_scheduled_tenure_reward (stackslib/src/chainstate/nakamoto/tenure.rs) reads accumulated_coinbase_ustx from the BlockSnapshot returned by SortitionDB::get_block_snapshot_consensus keyed only by block.header.consensus_hash, without checking that this snapshot is the one on the CURRENT canonical sortition fork at reward-computation time. Can an attacker who causes a burnchain micro-fork around the block's sortition make one node compute total_coinbase from a snapshot that briefly existed on a since-abandoned fork (same consensus_hash reused is impossible, but a re-orged snapshot row can carry different accumulated_coinbase_ustx before vs after fork resolution due to missed-sortition accumulation) end up scheduling a coinbase reward amount that differs between the two nodes for the identical tenure-start block? Preconditions: two-node harness racing a Bitcoin fork around a missed-sortition burn block. Equality broken: total_coinbase(nodeA) == total_coinbase(nodeB) for the same StacksBlockId. Impact: Critical, reward paid != coinbase+fees earned by the canonical tenure -> unreversible mispayment once matured. Proof idea: integration test forcing divergent accumulated_coinbase_ustx across two SortitionDB replicas processing the same burn ops in different fork orders, then asserting equal make_scheduled_miner_reward outputs after both converge to the same canonical fork.
