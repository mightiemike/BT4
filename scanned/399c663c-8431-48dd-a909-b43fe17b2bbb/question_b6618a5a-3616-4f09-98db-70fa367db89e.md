`get_signers_weights` (stackslib/src/chainstate/nakamoto/signer_set.rs) reads the signer list via a read-only Clarity call `(get-signers u{reward_cycle})` against `SIGNERS_NAME` at a given `block_id`, independent of the `reward_set` object used by `verify_signer_signatures` (which is loaded via `load_nakamoto_reward_set_for_tenure`/`OnChainRewardSetProvider`). Can an unprivileged attacker exploit a fork where the `.signers` contract state at `block_id` (used by `get_signers_weights`) has diverged from the `RewardSet` structure loaded from the sortition-DB-cached reward-set path (used by `verify_signer_signatures`), for example by mining a fork that skips the `update_signers` Clarity write for a cycle, so that two different consumers of 'the reward set for cycle N' (one via Clarity read, one via cached `RewardSet`) disagree on signer weights for the SAME `block_id`/cycle? Equality broken: `get_signers_weights(chainstate, sortdb, block_id, cycle)` == `reward_set.signers()` weights used by `verify_signer_signatures` for the same `(block_id, cycle)`. Impact: Critical — divergent weight bookkeeping between the two authoritative sources for the same cycle can let a block be validated as sufficiently signed by one code path's weights while being insufficient per the other, producing consensus disagreement (STATE ROOT / DETERMINISM violation) between components/nodes that rely on different lookup paths. Proof idea: integration test that forks a chain such that one branch skips `NakamotoSigners::check_and_handle_prepare_phase_start` (no `.signers` update) while the other performs it, then compare `get_signers_weights` output against the `RewardSet` loaded by `load_nakamoto_reward_set_for_tenure` at the same block_id/cycle, asserting they diverge.
