`create_inscription_type_1`'s `DataOnDa::Aggregate(reveal_tx_ids, reveal_wtx_ids)` is signed via `sign_blob_with_private_key(&reveal_body, da_private_key)`, but each individual `DataOnDa::Chunk(chunk)` referenced inside is NOT signed (per the code comment 'No need to check sender for chunk' in circuit/mod.rs). Can an unprivileged attacker inscribe their own unsigned `RawTxData::Chunks` chunk transaction with an arbitrary wtxid, then reference that chunk's txid inside a otherwise-valid Aggregate body (if they could ever get one signed) — or, more directly, can an attacker race-insert a `DataOnDa::Chunk` at the exact wtxid the real batch prover's Aggregate will reference, before the real chunk lands, so `ChunkAccessor::<S>::insert(blob.wtxid(), chunk, ...)` in `run_l1_block` stores the attacker's bytes under that wtxid? Preconditions: regtest, light client circuit processing DA txs; the aggregate references chunks purely by (txid, wtxid), not by content hash. Call sequence: attacker inscribes chunk with colliding wtxid before/after legitimate prover posts real chunk in the same or different order within the block; `run_l1_block`'s blob_loop inserts by wtxid unconditionally for every `DataOnDa::Chunk`. Binding: the chunk bytes assembled into `complete_proof` for a given wtxid == the chunk bytes the real batch prover posted for that same wtxid. Impact: Critical, DA_INTEGRITY / PROOF_SOUNDNESS — an attacker-substituted chunk corrupts the reassembled proof body, silently causing decompression/verification failure or, in a crafted case, a different accepted proof than the honest one, for all light client provers. Impact affected: any dependent (Clementine bridge, all full nodes reading light client proof). Proof idea: cargo test posting two `DataOnDa::Chunk` blobs with the same wtxid (attacker's first) before the aggregate, and assert `ChunkAccessor::get` returns the attacker's bytes, not the honest prover's, demonstrating no signature/content re-derivation reconciles which chunk was 'the real one'.
