Target: check_block_commit_vrf_seed (nakamoto/mod.rs) verifying a Nakamoto block's VRF proof against the seed committed by the winning block-commit. Attacker action: submit a Nakamoto block whose VRF proof verifies correctly under the miner's OWN VRFPublicKey and OWN chosen seed value, rather than the seed value actually recorded in the winning block-commit's committed seed field (attacker mines a valid VRF proof for a seed of their choosing rather than the one they were bound to). Preconditions: attacker won a minority-stake sortition with a valid leader key; commits a block-commit with seed S_committed but later produces a block with proof P verifying to S_own != S_committed under the SAME public key (both are internally-consistent w.r.t. that key, but only one matches the burnchain-committed seed). Call sequence: nakamoto block processing -> check_block_commit_vrf_seed pulls the committed seed from the sortition's winning block-commit -> compares against VRF.verify(pubkey, S_own, P) instead of re-deriving S_committed and checking VRF.verify(pubkey, S_committed, P). Equality that breaks: VRF seed committed by the winning block-commit on the burnchain == the seed against which the block's VRF proof is actually validated. Impact: Critical, accepted block whose VRF proof does not correspond to committed randomness, letting the miner grind/choose their own leader-election seed for the NEXT tenure (breaks unpredictability, a consensus-relevant equality). Proof idea: integration test where a block-commit commits seed S1 on-chain, the block author submits a valid proof for S2 (self-chosen) under the same pubkey, assert current code either rejects (safe) or accepts (bug) by checking whether check_block_commit_vrf_seed re-derives the expected seed from the committed value before calling VRF.verify.
