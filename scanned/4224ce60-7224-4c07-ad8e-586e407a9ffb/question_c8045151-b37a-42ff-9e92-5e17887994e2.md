Target: `NakamotoChainState::accept_block` signer weight check via `verify_signer_signatures` (scope: SIGNING equality). Attacker action: submit a block signed by a set of signers whose combined weight from the *current* cycle's reward set is below threshold, but whose weight computed against a *stale* previous-cycle reward set (due to a reward-set reload race) would exceed threshold. Preconditions: cycle boundary just crossed; some nodes haven't refreshed `OnChainRewardSetProvider` reward set for the new cycle. Call sequence: `accept_block` -> `verify_signer_signatures(reward_set, epoch_id)`. Equality: signing_weight computed with cycle-N reward_set on node A == signing_weight computed with cycle-N reward_set on node B (both must use the *same* cycle's reward set, not a stale one). Impact: Critical — if any node incorrectly uses cycle N-1's reward set to validate a cycle-N block, threshold(N) can be satisfied on that node using stale weights while failing on up-to-date nodes, causing one node to accept an under-signed block others reject. Proof idea: two-node test where one node's reward-set cache is deliberately stale at the cycle boundary; submit a block signed just below the true cycle-N threshold and assert both nodes reject it identically.
