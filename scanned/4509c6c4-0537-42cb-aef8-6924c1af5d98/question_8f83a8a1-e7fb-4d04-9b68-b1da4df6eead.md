Target `verify_method_id_security_council` signature-malleability check. Attacker action: take a valid `(signature, index)` triplet observed from a broadcasted council body and flip the `s` component to `n - s` (ECDSA malleability) before re-inscribing the same body with the malleated bytes. Preconditions: none beyond observing a genuine council-signed blob on L1. Call sequence: `Signature::from_bytes(&signature.into())` -> `verify_prehash`. Binding: `Signature::from_bytes` accepting malleated bytes == the same logical signature the council key produced, and the outcome of `verify_method_id_security_council` must be identical to the pre-malleation call. Impact: Critical only if malleation lets a different `method_id` body pass; if the check simply re-validates the same body it is not a bypass, this question isolates whether malleated bytes can be paired with a different `body.serialize()` and still verify. Proof idea: cargo test constructing a low-S and non-canonical high-S encoding of the same signature and asserting the verification result is unchanged and cannot be combined with a different msg.
