Target `run_l1_block` interaction between `DataOnDa::BatchProofMethodId` insertion and `process_complete_proof`'s `Z::verify` call within the *same* L1 block. Attacker action: in one Bitcoin block, first position a genuinely council-signed `BatchProofMethodId` body activating at `activation_l2_height = X`, then in a later transaction position of the same block, submit a `DataOnDa::Complete` blob (requires actual `batch_prover_da_public_key` sender, so this step needs the real batch prover to be honest and unaware) whose proof's `last_l2_height` is exactly `X`, to test whether the newly-inserted method id is visible to `process_complete_proof` within the same block via the shared `working_set`. Preconditions: single `run_l1_block` call, both blobs same block. Call sequence: `BatchProofMethodIdAccessor::insert` mutates `working_set` -> subsequent `process_complete_proof` call in the same iteration reads `BatchProofMethodIdAccessor::get(working_set)` fresh, seeing the new entry. Binding: the `method_id` used to `Z::verify` a given `last_l2_height` == the entry whose `activation_l2_height` is the greatest one `<= last_l2_height` among *all* entries present in the accessor at the time of that specific proof's processing within the block, matching the order transactions appear in `da_txs`. Impact: Critical, if blob ordering within a block lets method-id updates and proof verification race in an attacker-influenced way (attacker controls tx position via fees) to make a proof verify under a method id different from what was active when it was actually generated. Proof idea: cargo test constructing a single block with both blob types in attacker-chosen order and asserting `Z::verify` is called with the method id matching the height, not an order-dependent one.
