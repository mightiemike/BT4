Target: `NakamotoChainState::check_normal_coinbase_tx` (stackslib/src/chainstate/nakamoto/mod.rs, `VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes())`). Attacker action: submit a Nakamoto tenure-start block whose coinbase VRF proof was generated with the attacker's own VRF private key but is checked against a stale `leader_vrf_key` fetched from a leader-key registration belonging to a different, already-superseded sortition height (key rotation race). Preconditions: attacker has registered two `LeaderKeyRegisterOp`s across two burn blocks and only the older one is passed to verification due to a caching bug in the caller. Call sequence: sortition winner lookup -> `get_leader_key_at(key_block_ptr,key_vtxindex)` -> `check_normal_coinbase_tx`. Equality: `leader_vrf_key == the VRFPublicKey actually referenced by the winning block-commit's key_block_ptr/key_vtxindex`. Impact: Critical — a proof verified under the wrong key can pass `VRF::verify` for values it wasn't produced for only if the verification target key is wrong, letting an invalid block be accepted network-wide. Proof idea: integration test constructing two `LeaderKeyRegisterOp`s, feeding the wrong one into `check_normal_coinbase_tx`, and asserting the call returns `Err(InvalidStacksBlock)` — a regression test that fails if the wrong-key path silently returns `Ok`.
