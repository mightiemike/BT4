In NakamotoTenureDownloader::try_accept_tenure_end_block, the state machine trusts tc_payload.prev_tenure_consensus_hash == tenure_start_block.header.consensus_hash as proof that the tenure-change descends from exactly one parent tenure. In try_advance_from_chainstate's shadow-tenure branch, however, the parent tenure_start_block_id is instead derived by reading `StacksBlockId(coinbase_payload.0)` straight out of the shadow block's Coinbase transaction payload, with no cross-check against tc_payload.prev_tenure_consensus_hash or the SortitionDB's recorded winner for that shadow tenure. Can a minority miner who is granted (or forges) a shadow-tenure-adjacent slot embed an arbitrary StacksBlockId inside its coinbase payload so that the downloader on one node resolves tenure_start_block_id to block X while a node that instead receives the same tenure via the non-shadow path (real block-commit) resolves it to the true parent block Y? Equality broken: TENURE/REWARD — tenure descends from exactly one parent == the sortition-authorised parent, but the shadow path substitutes an unvalidated coinbase-embedded pointer. Impact: Critical — two nodes converge on different tenure-start blocks for the same consensus hash, producing different MARF state roots for the same tenure and splitting the canonical chain. Proof idea: booted two-node chainstate where one node processes a shadow tenure with a coinbase pointing to a block never actually committed by the winning sortition, and assert StacksBlockId parent resolution and post-tenure state root diverge from a node using the ordinary get_nakamoto_block path.
