The `completed_tenures: HashSet<CompletedTenure>` in NakamotoTenureDownloaderSet dedupes purely on the tuple (tenure_id, start_block, end_block) derived from `impl From<&TenureStartEnd> for CompletedTenure` and `impl From<&mut NakamotoTenureDownloader> for CompletedTenure`. In make_tenure_downloaders, a tenure already present in completed_tenures is skipped via `schedule.pop_front()` without ever re-verifying that its recorded start_block/end_block still match the node's current sortition-derived view of that tenure_id_consensus_hash after a fork switch. Can an attacker force a local reorg (extend a competing fork past the previously-canonical one) such that the same tenure_id_consensus_hash is now associated with a different start_block_id/end_block_id, while the stale CompletedTenure entry (from the abandoned fork) causes the downloader to treat the tenure as already-fetched and skip re-downloading the now-canonical version? Equality broken: STATE ROOT — committed root == root every node recomputes; a stale, off-fork tenure's blocks must not be treated as satisfying the canonical tenure's data requirement. Impact: Critical — a node can retain and build on the abandoned fork's tenure data believing it satisfies the new canonical schedule, producing a state root divergent from nodes that redownloaded the correct blocks. Proof idea: two-fork harness where fork A's tenure X is downloaded and marked completed, then fork B (extended by the attacker with more work) reuses the same consensus hash for a different tenure body; assert the node's completed_tenures short-circuits re-fetch and its resulting state root differs from a node built entirely from fork B.
