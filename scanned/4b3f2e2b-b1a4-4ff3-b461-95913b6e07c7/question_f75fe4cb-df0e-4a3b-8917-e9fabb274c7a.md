In TenureStartEnd::from_inventory's second loop (handling tenures spanning into `next_wanted_tenures`), the end_reward_cycle is computed via `pox_constants.block_height_to_reward_cycle(first_burn_height, wt_start.burn_height)`, which can legitimately differ from the first loop's `rc, rc` assignment. Given that the resulting `TenureStartEnd.end_reward_cycle` directly selects which RewardSet (`end_signer_keys`) is used in NakamotoTenureDownloader::try_accept_tenure_end_block's `verify_signer_signatures`, can an attacker who controls exactly which sortitions have inventory bits set (by, e.g., mining a block-commit that wins a sortition and then never producing a corresponding Nakamoto block, shifting which wanted_tenure index is 'next available') cause wt_start to be resolved to a wanted_tenure whose burn_height falls in a different reward cycle than the one the honest majority's SortitionDB would assign for that same logical tenure boundary? Equality broken: SIGNING — the end_signer_keys reward set used to verify the tenure-end block's signatures must equal the reward set that cycle's honest majority actually derived. Impact: Critical if it lets a block signed by an old/foreign reward set pass verify_signer_signatures because the wrong (attacker-shifted) cycle's RewardSet was fetched. Proof idea: integration test with a deliberately-missing Nakamoto block for a won sortition near a reward-cycle boundary, driving from_inventory on two nodes with different views of which bit is 'next', and asserting the resulting end_reward_cycle/end_signer_keys differ and that this changes the Ok/Err verdict of try_accept_tenure_end_block for an identical block.
