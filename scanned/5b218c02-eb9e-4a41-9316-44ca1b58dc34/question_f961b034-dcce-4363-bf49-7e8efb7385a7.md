BlockSnapshot::null_miner_wins (stackslib/src/chainstate/burn/sortition.rs) builds a null_winner by flipping every bit of commit_winner.block_header_hash and constructs a 2-point burn_dist [null_sample_winner, burn_sample_winner] whose boundary is atc.into_sortition_probability(). Since AtcRational::into_sortition_probability (stackslib/src/chainstate/burn/atc.rs) clamps to Self::one_sup().into_inner() << 192 whenever self.inner() >= Self::one().inner(), can a miner manipulate their own burn_fee history (their own BTC, no other party) across the MINING_COMMITMENT_WINDOW to produce an AtcRational value that lands exactly at this clamp boundary on one node's floating computation path (e.g. via get_miner_commit_carryover's AtcRational::frac(block_burn_total, windowed_median_burns)) versus a value just under it on a node with a differently-ordered burn_dist (from equally valid but differently-ordered windowed_block_commits), producing a different null_prob_u256 and hence a different sample_burn_distribution winner (miner wins on one node, null wins -- no sortition -- on the other)? Precondition: block_burn_total/windowed_median_burns ratio deliberately near an AtcRational boundary. Equality: get_miner_commit_carryover(total_burns, windowed_median_burns) and null_miner_wins() verdict must be identical for every node computing over the same accepted burn ops. Impact: Critical — one network partition treats a sortition as having a winner while another treats it as make_snapshot_no_sortition, i.e., a chain split on whether a Stacks tip advances. Proof idea: integration test constructing burn ops whose derived ATC lands within one Uint256 unit of the clamp boundary and asserting null_miner_wins() is invariant to windowed_block_commits ordering.
