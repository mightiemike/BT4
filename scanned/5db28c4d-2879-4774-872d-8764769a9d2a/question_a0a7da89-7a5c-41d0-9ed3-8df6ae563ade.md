Can a miner replay the exact same `new_seed`/VRF proof pair across two different tenures by pointing two distinct block-commits' `parent_block_id` at the same ancestor, exploiting `get_parent_vrf_proof`'s reliance on `block_commit_txid`-derived `parent_sortition_id` lookup (`SortitionDB::get_block_commit_parent_sortition_id`) rather than a strict monotonic tenure-chain check? Attacker action: craft two sibling tenures whose block-commits both declare the same `parent_block_ptr/parent_vtxindex`, producing seeds `VRFSeed::from_proof(same_proof)` for both. Preconditions: attacker mines two competing tenures off the same parent (a legitimate fork). Call sequence: `get_parent_vrf_proof` -> `get_block_commit_parent_sortition_id` -> `get_block_vrf_proof` -> `validate_vrf_seed`. Equality: each accepted tenure's VRF seed must be unique per parent-tenure-VRF-proof pairing consumed exactly once; sortition/burn distribution (`select_winning_block`) must still pick only one winner per height. Impact: Critical -- if both tenures validate independently (which is expected for a legitimate fork) but the *sortition winner selection* uses a VRF seed that can be predicted/replayed, this could bias `sample_burn_distribution`'s winner choice deterministically in the attacker's favor, causing a minority-triggerable divergence in sortition. Proof idea: two-fork harness, both tenures anchored to the same parent VRF proof, assert `BlockSnapshot::sample_burn_distribution` output is identical across both forks given identical seed and check whether this predictability lets the attacker bias which of *their own* multiple commits wins.
