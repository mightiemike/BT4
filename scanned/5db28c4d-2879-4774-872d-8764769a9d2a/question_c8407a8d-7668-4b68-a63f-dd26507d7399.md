Can an attacker exploit `LeaderKeyRegisterOp::check` (leader_key_register.rs), which only enforces `has_VRF_public_key` uniqueness and never binds the key to the `apparent_sender` of the eventual block-commit, to consume a VRF key registered by a distinct, unrelated Bitcoin sender in a later block-commit? Attacker action: observe an honest miner's `LeaderKeyRegisterOp` broadcast (public_key P, height H, vtxindex V) before it's mined N blocks deep, and submit their own `LeaderBlockCommitOp` referencing `key_block_ptr=H, key_vtxindex=V` before the honest miner does. Preconditions: attacker monitors mempool/burnchain, has their own BTC for a commit. Call sequence: block-commit `check()` -> key op lookup by (block_ptr, vtxindex) -> no sender-identity binding assertion. Equality: the miner who is credited with tenure/coinbase reward for consuming key (H,V) must equal the entity that registered (H,V); this equality is never checked. Impact: Critical -- reward theft: attacker's tenure is credited using a leader key they never registered, and the honest registrant's key becomes unusable (`LeaderKeyAlreadyRegistered`-style consumption), causing unclaimed/misdirected reward. Proof idea: two-miner integration test where miner B's commit races miner A's registered key index; assert whether the chainstate allows B's tenure to proceed on A's key.
