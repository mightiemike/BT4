Target: `ChunkAccessor::<S>::insert` and the aggregate reassembly's size guard `if chunk.len() + complete_proof.len() > MAX_COMPRESSED_BLOB_SIZE`. Attacker action: inscribe a `DataOnDa::Chunk` reveal with a chunk body sized so that, when concatenated in the batch prover's exact wtxid order, the running total exceeds `MAX_COMPRESSED_BLOB_SIZE` at an attacker-chosen wtxid inside the batch prover's own `wtxids` list, forcing `continue 'blob_loop` before the last chunk is appended. Preconditions: attacker knows (from public mempool observation) the batch prover's wtxid list and remaining chunk sizes before the aggregate confirms. Call sequence: `run_l1_block` -> `DataOnDa::Aggregate` arm -> loop over `wtxids` -> `ChunkAccessor::get` returns the *attacker's* oversized chunk (if attacker's chunk landed at that wtxid slot first) -> size check trips -> `continue 'blob_loop`, silently dropping the whole aggregate without calling `process_complete_proof`. Binding: whether the aggregate is processed == whether the batch prover's real chunk set totals <= `MAX_COMPRESSED_BLOB_SIZE`; attacker must not be able to flip this outcome by substituting a chunk of different size at a wtxid the prover controls. Scoped impact: Critical only if this makes a true state transition permanently unprovable (the batch proof can never be resubmitted under a wtxid the prover doesn't control) — otherwise High/DoS (out of scope). Proof idea: cargo test asserting that for a fixed honest wtxid-to-chunk mapping, no attacker-controlled `ChunkAccessor::insert` at a wtxid outside the prover's set can alter the size-check outcome for the prover's own `wtxids` list, i.e. isolation between attacker chunks and prover chunk keys.
