LruCache::flush (stacks-common/src/util/lru_cache.rs) iterates self.order via a plain for loop over Vec<Node<K,V>> filtered by dirty, calling f(&node.key, node.value) in Vec-index order rather than LRU order. If NonceCache::get relies on flush ordering to persist nonces before a dirty entry with the same key is evicted and re-inserted by evict_lru reusing the same Vec slot (stacks-common/src/util/lru_cache.rs insert_with_dirty capacity branch), a race between insert_with_dirty's std::mem::replace of tail_node.key and a concurrent flush could persist a stale (key,value) pair. Equality: (key,value) persisted by flush == the last insert_with_dirty call's (key,value) for that key at the time of eviction. Impact: Critical — if this cache is reused to memoize any sortition/reward-set-derived value (any future caller keying by (cycle, address) burn-weight or signer-weight lookups), a stale flushed value could make node A's SIGNING or SORTITION verdict diverge from node B's freshly-computed value, splitting the network. Proof idea: two-node harness: instantiate two LruCache<K,V> with capacity 1, apply identical insert/evict sequences with a forced reordering (simulate via separate threads or interleaved evict_lru + flush calls), assert flushed output multiset from node A == node B.
