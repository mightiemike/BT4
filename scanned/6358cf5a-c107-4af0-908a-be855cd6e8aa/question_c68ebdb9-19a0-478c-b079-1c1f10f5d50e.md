NonceCache::reset_cache (stackslib/src/core/nonce_cache.rs) replaces self.cache with a fresh LruCache::new(self.max_size) and issues 'DELETE FROM nonces' on LruCacheCorrupted detection, but only best-effort logs (warn!) if the DELETE fails, without aborting the tenure-processing call that triggered it. Preconditions: an attacker crafts input driving LruCache into a corrupted state (via any of the invariant violations above reachable from address-keyed nonce lookups during Nakamoto block validation), and the subsequent DELETE FROM nonces fails (e.g., due to a concurrent read lock held by another connection legitimately open during block processing). Equality: nonce state used by node A after a failed reset (stale nonces table + empty in-memory cache) == nonce state on node B (either not corrupted, or successfully reset). Impact: Critical — a transaction with a nonce that should be rejected as already-used passes NonceCache::get returning a lower stale nonce on node A only, letting a transaction execute twice with 'valid' nonce on one node while node B rejects it, producing a state root divergence (STATE ROOT: committed root == root every node recomputes) between honest nodes over the same Nakamoto block. Proof idea: Rust integration test forcing LruCacheCorrupted (e.g., by directly constructing a malformed LruCache order/head/tail via test-only accessors or by exhausting op sequences known from the property tests to produce a cycle) concurrently with a locked mempool DB connection, then compare block-processing state root on two node instances fed the identical block.
