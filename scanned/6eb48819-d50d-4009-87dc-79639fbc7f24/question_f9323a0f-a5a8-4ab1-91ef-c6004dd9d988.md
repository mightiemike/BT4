Target: `run_l1_block`'s aggregate reconstruction loop reading `ChunkAccessor::<S>::get(*wtxid, ...)` for `wtxid in &wtxids` where `wtxids: Vec<[u8;32]>` comes from the attacker-unverified `DataOnDa::Aggregate(_, wtxids)` blob body itself (only `blob.sender()` of the *Aggregate* blob is checked, not that the referenced `wtxids` are wtxids of *chunk* transactions the same prover actually sent). Attacker action: the batch prover's own signed `DataOnDa::Aggregate` blob lists `wtxids`; an attacker cannot forge this list since the whole blob (including the list) must be signed by `batch_prover_da_public_key`. However, an attacker CAN pre-populate `ChunkAccessor` entries at wtxids that the prover has not yet used but might reuse later (wtxid namespace has no prover-only reservation), so if the prover's future aggregate ever references a wtxid the attacker got to first with a `DataOnDa::Chunk`, the entry is attacker-controlled forever (no overwrite protection in `ChunkAccessor::insert`, unlike `SequencerCommitmentAccessor`). Preconditions: attacker predicts a wtxid the prover will use (e.g., via address reuse or public knowledge of prover-controlled UTXOs feeding future reveal transactions) and mines/broadcasts a `DataOnDa::Chunk` reveal with a *different* transaction but colliding wtxid is cryptographically infeasible (SHA256), so the realistic path is: prover reuses a wtxid is impossible since wtxid is transaction-specific — reduces this question to whether `ChunkAccessor::insert` should have `if get(wtxid).is_none()` guard like `SequencerCommitmentAccessor` does. Call sequence: `DataOnDa::Chunk` -> unconditional `ChunkAccessor::insert` overwrite, unlike `SequencerCommitmentAccessor::insert`'s `is_none()` guard. Binding: chunk value read by the aggregate reconstruction for wtxid `w` == chunk value inserted by the transaction whose actual wtxid is `w` (should be automatically true since wtxid uniquely identifies one transaction, but the store has no idempotency/first-writer-wins protection against a later blob at the identical wtxid, which cannot happen without reorg). Scoped impact: Critical if a Bitcoin reorg replaces the chunk transaction at wtxid `w` with a different transaction sharing the same wtxid (impossible without breaking SHA256) — so this specific vector is not exploitable; documented as a confirmed non-finding for completeness. Proof idea: cargo test inserting two different chunk payloads under the identical wtxid key in sequence and asserting the second overwrites the first, confirming the JMT store itself has no first-writer-wins protection, then reasoning about reachability given wtxid uniqueness.
