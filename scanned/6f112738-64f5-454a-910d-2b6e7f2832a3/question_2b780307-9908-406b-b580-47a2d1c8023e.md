Target: NakamotoChainState::make_scheduled_miner_reward (stackslib/src/chainstate/nakamoto/tenure.rs), which sets `tx_fees: MinerPaymentTxFees::Nakamoto { parent_fees }` where `parent_fees` is the *parent tenure's* total fees, fetched via `get_total_tenure_tx_fees_at(chainstate_tx, &block.header.parent_block_id)`. Can a miner submit a tenure-change block whose `parent_block_id` points to a non-canonical (orphaned) prior tenure with an inflated total tx-fee accumulation (e.g. by mining a private, high-fee-but-never-broadcast parent tenure that later gets orphaned but was locally the 'parent' at authoring time), so that `parent_tenure_fees` used in make_scheduled_miner_reward reflects fees from a tenure that other honest nodes recompute differently, producing a MinerPaymentSchedule.coinbase+tx_fees mismatch across nodes for the same block? Preconditions: attacker controls the parent tenure's block-authoring and privately maximizes fees, then reveals a divergent version to the network relative to what it privately built on. Call sequence: check_sortition_exists -> calculate_scheduled_tenure_reward -> get_total_tenure_tx_fees_at(parent_block_id) -> make_scheduled_miner_reward -> insert_miner_payment_schedule. Equality broken: parent_tenure_fees computed by every node from `block.header.parent_block_id`'s locally-stored tenure total == the same value on every node (deterministic replay), since get_total_tenure_tx_fees_at reads from local chainstate keyed by parent_block_id, which is a committed, agreed-upon value from block validation, not attacker-supplied. Impact: Critical only if get_total_tenure_tx_fees_at can diverge across honest nodes for the same parent_block_id; otherwise not exploitable. Proof idea: run the same tenure sequence on two independently-booted nodes and assert get_total_tenure_tx_fees_at returns identical values for identical parent_block_id on both.
