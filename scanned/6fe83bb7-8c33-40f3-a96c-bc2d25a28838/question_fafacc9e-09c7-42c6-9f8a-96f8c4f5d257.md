Can an attacker cause a legitimate deposit to be dropped by submitting, ahead of it, a blob that passes `Evm::get_call` simulation and is inserted via `add_deposit_tx`, but is never included in any block because `fetch_deposits(limit_per_block)` is bounded and the attacker continuously refills `accepted_deposit_txs` with fresh, always-passing-simulation, never-conflicting deposit blobs (distinct `calc_tx_id`s) faster than `limit_per_block` per block, so the legitimate depositor's entry sits at the back of the `VecDeque` behind an unbounded, ever-growing set of attacker entries that never get `remove_deposits`'d because they're never fetched? Preconditions: `limit_per_block` is small relative to attacker's submission rate; `accepted_deposit_txs`/`pending_deposits` have no eviction/expiry. Binding: every honestly presigned Bitcoin move-to-vault output must eventually be counted once by a SYSTEM_SIGNER deposit; unbounded queue-jumping breaks 'eventually'. Impact: Critical (permanent freeze) if there is no FIFO guarantee bounding the wait, since `fetch_deposits` always takes from the front but the front is attacker-controlled if attacker's earlier submissions occupy earlier queue slots. Proof idea: cargo test enqueuing legitimate deposit first, then N synthetic distinct-txid deposits, and asserting the legitimate deposit is fetched within a bounded number of `fetch_deposits` calls (FIFO order should guarantee this since VecDeque preserves insertion order) — if the legitimate deposit was inserted first it should be fetched first, so this specifically tests whether an attacker can front-run the *insertion order* itself via faster RPC calls, not just volume.
