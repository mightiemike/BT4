Target: `make_scheduled_miner_reward` (tenure.rs:283-333). Attacker action: an unprivileged miner who wins a single sortition submits a coinbase tx (`TransactionPayload::Coinbase`) whose `recipient_opt` field names an arbitrary principal the miner does not control the keys for, e.g. a large exchange deposit address. Preconditions: Epoch >= Epoch21, valid sortition win, valid VRF proof. Call sequence: `check_normal_coinbase_tx` only validates the VRF proof, never the recipient field -> `calculate_scheduled_tenure_reward` -> `make_scheduled_miner_reward` reads `recipient_opt` unauthenticated and stores it as `MinerPaymentSchedule.recipient`. Equality that should hold: reward paid == coinbase+fees earned, paid to the SORTITION WINNER's specified recipient, but nothing authenticates that recipient is a party the miner intended/controls versus a griefing target. Does the block-acceptance path ever reject a coinbase recipient that differs from a keyed principal, or is any principal string accepted as-is? Impact: Critical if this allows a miner to durably send another party's matured STX with no recourse (not a griefing-only issue since it is a scheduled DB write). Proof idea: integration test mining a tenure with a coinbase recipient set to a fixed principal with no key, confirm `insert_matured_child_miner_reward` credits that principal exactly coinbase+fees once.
