In `run_l1_block`, chunks are never removed from `ChunkAccessor` state after being consumed by a successful aggregate. Can an unprivileged attacker who observes a batch prover's `DataOnDa::Chunk` wtxid list from one L1 block re-use those same wtxids (by controlling the pointer wtxids field of a *new* `DataOnDa::Aggregate` they cannot send, since aggregates need `batch_prover_da_public_key` — but can they get the *batch prover's own future* aggregate in a subsequent block to accidentally reference a wtxid the attacker has since overwritten via a second attacker `DataOnDa::Chunk` insert at that same key before the batch prover's aggregate transaction is processed) mutate the chunk body retroactively between the block where the chunk was first accepted and the block where an aggregate resolves it? Binding: `ChunkAccessor::get(wtxid, ...)` at aggregate-resolution time == the chunk body as it existed when the batch prover chunked and referenced that wtxid. Impact: Critical, a time-of-check/time-of-use style overwrite of unauthenticated chunk storage lets an attacker retroactively swap proof bytes the batch prover already committed to. Proof idea: cargo test performing an attacker `ChunkAccessor::insert` at wtxid W in block N, then an honest insert at the same W is impossible only if wtxid is unique per tx, so instead assert whether `run_l1_block` ever re-reads a chunk across multiple blocks without pinning it to the block it was found in, breaking DETERMINISM across two honest provers if state is JMT-persisted differently.
