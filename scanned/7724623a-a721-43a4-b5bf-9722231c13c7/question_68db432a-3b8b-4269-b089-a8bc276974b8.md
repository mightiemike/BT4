DoS/soundness probe against `process_complete_proof`. Since `blob.sender()` is checked immediately after variant matching (crates/light-client-prover/src/circuit/mod.rs:443 for Complete, :469 for Aggregate, and equivalent for `DataOnDa::SequencerCommitment`), any attacker-authored `Complete`/`Aggregate`/`SequencerCommitment` blob is filtered by `continue` before `process_complete_proof` ever runs, so this variant of the attack is NOT viable for those three variants. Preconditions: only the `DataOnDa::Chunk` variant (see other questions) skips the sender check. Binding: the set of `DataOnDa::Complete`/`Aggregate`/`SequencerCommitment` blobs that reach `process_complete_proof`/`SequencerCommitmentAccessor::insert` == the set whose `blob.sender()` equals `batch_prover_da_public_key`/`sequencer_da_public_key` exactly. Impact: Critical impact would occur ONLY if sender check could be bypassed, which per code review it cannot for these three variants - flagging this as a NEGATIVE finding (control works as intended) to be verified by test, not exploited. Proof idea: cargo test submitting an attacker-signed (non-batch-prover-key) `DataOnDa::Complete`/`Aggregate`/`SequencerCommitment` blob and asserting `run_l1_block`'s resulting `RunL1BlockResult` is IDENTICAL (state root, last_l2_height, last_sequencer_commitment_index unchanged) to running without that blob at all, confirming the sender check is a hard filter with no bypass via crafted borsh discriminant collision.
