The `MAX_COMPRESSED_BLOB_SIZE` bound in the `DataOnDa::Aggregate` loop is checked as `chunk.len() + complete_proof.len() > MAX_COMPRESSED_BLOB_SIZE`. Can an unprivileged attacker insert a `DataOnDa::Chunk` whose `chunk.len()` is exactly crafted such that, combined with legitimate chunks already accumulated for a given aggregate, the running sum wraps or sits exactly at the boundary, letting `DS::decompress_chunks` receive a byte string longer or structured differently than what `MAX_COMPRESSED_BLOB_SIZE` was meant to bound, and be misinterpreted as a smaller valid compressed blob whose decompression diverges from the honest one? Binding: `complete_proof.len()` accumulated == the exact byte length the batch prover compressed and chunked for that aggregate. Impact: Critical, boundary manipulation of attacker-supplied chunk bytes changes the decompressed `BatchProofCircuitOutput` bytes fed to `process_complete_proof`. Proof idea: cargo test with attacker chunk sized to the `MAX_COMPRESSED_BLOB_SIZE` boundary inserted at a wtxid within a batch-prover aggregate's wtxid list, asserting the decompressed output differs from the honest batch prover's output.
