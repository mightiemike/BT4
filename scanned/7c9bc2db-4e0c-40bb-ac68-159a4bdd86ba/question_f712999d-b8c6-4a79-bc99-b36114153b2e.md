target: BitcoinVerifier::verify_transactions coinbase commitment search `coinbase_tx.output.iter().rposition(...)`. Attacker action: mine a block whose coinbase transaction has two outputs matching `WITNESS_COMMITMENT_PREFIX` and length >= `MINIMUM_WITNESS_COMMITMENT_SIZE`, where the earlier (lower-index) output encodes the real segwit commitment and the later (higher-index) output is an attacker-crafted output that also matches the pattern but with garbage commitment bytes. Preconditions: attacker just needs enough hashpower or luck (or acts as the block's transaction submitter feeding candidate outputs to a miner willing to include arbitrary outputs) to get a coinbase with such structure mined; only unprivileged submission of a witness/commitment-shaped OP_RETURN output via a transaction is required, not mining itself under this ruleset's threat model exclusions — however this specifically concerns coinbase tx outputs, controllable by whoever assembles the coinbase (pool), so treat as a block-content observation the attacker can produce via any assisting relay/inscription of a fake commitment output if they run the mining software; still testable via crafted regtest block. Call sequence: `rposition` picks the highest-index matching output as `commitment_idx`; verifier checks `script_pubkey[6..38] != commitment` against merkle_root+witness_reserved_value hash; if native software (e.g., bitcoind or another independent verifier) instead picks the first matching output (lowest index) for its own commitment interpretation. Binding: commitment_output_selected_by_circuit(B) == commitment_output_selected_by_native_verifier(B). Impact: Critical — the circuit accepts a witness commitment computed from the wrong (attacker-added) output while the real one lower-index output is ignored, potentially making `IncorrectWitnessCommitment` diverge between two honest verifiers reading the same block, splitting the light client proof. Proof idea: cargo test with a synthetic coinbase tx containing two prefix-matching outputs at different indices with different commitment bytes, run `verify_transactions` and assert which index is chosen and whether an alternate but equally 'honest' selection rule (lowest index) would accept/reject differently.
