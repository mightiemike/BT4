`DepositDataMempool::fetch_deposits(&mut self, limit_per_block: usize)` returns a `Vec<Deposit>` by cloning the front of `accepted_deposit_txs` without removing them, and can be called repeatedly by `runner` before `remove_deposits` is invoked for a given block. Can an attacker who also controls timing of RPC calls (submitting many `citrea_sendRawDepositTransaction` blobs in quick succession) cause `runner` to call `fetch_deposits` twice for two different block-production attempts (e.g. due to a retry after a `process_sys_txs` failure elsewhere in the block) before `remove_deposits` runs for the first attempt, resulting in the SAME deposit blob being included as a `SystemEvent::BridgeDeposit` in two different blocks' `system_events` and both being applied by `process_sys_txs` since `remove_deposits` for block 1 hadn't executed before block 2's `fetch_deposits` ran? Binding: number of L2 blocks in which a given deposit's `SystemEvent::BridgeDeposit(Vec<u8>)` is applied == 1. Impact: Critical, double-crediting the same Bitcoin move-to-vault output's cBTC amount to the recipient across two blocks. Proof idea: cargo test that calls `fetch_deposits` twice without an intervening `remove_deposits`, simulates both results being fed into `process_sys_txs` for consecutive blocks, and asserts the Bridge's `processedTxIds` (or equivalent L2-side idempotency) prevents the second application — if it doesn't, the double-credit is demonstrated by comparing recipient balance delta to the single Bitcoin output value.
