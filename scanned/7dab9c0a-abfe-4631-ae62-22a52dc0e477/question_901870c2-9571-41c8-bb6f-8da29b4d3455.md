`NakamotoChainState::check_normal_coinbase_tx` only asserts `VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes())`; it never checks that `coinbase_tx.get_origin()` equals the tenure's leader key hash (`miner_pubkey_hash160`) used by `check_miner_signature`. Can an attacker submit a Nakamoto block for their own won tenure where the coinbase tx's *origin* signing key differs from the block header's miner key, producing a mismatch between `MinerPaymentSchedule.address` (derived from `coinbase_tx.get_origin().get_address()`) and the actual sortition-winning leader, while `validate_normal_against_burnchain` still returns `Ok(())`? Preconditions: attacker-controlled tenure, valid VRF proof, valid block-header miner signature. Call sequence: block build -> `validate_normal_against_burnchain` -> `check_miner_signature` (checks header only) + `check_normal_coinbase_tx` (checks VRF only) -> accepted -> `make_scheduled_miner_reward` derives `address`/`recipient` from `coinbase_tx.get_origin()`. Equality broken: coinbase-tx-origin-address == block-header-signing-miner-address is never enforced. Impact: Critical (reward could be scheduled to a principal not tied to the sortition winner's leader key, undermining 'paid once, to the miner who won'). Proof idea: integration test constructing a NakamotoBlock whose coinbase tx is signed by a different keypair than the one that signs the block header, run through `NakamotoChainState::append_block`, and assert whether acceptance succeeds and to whom the `MinerPaymentSchedule` is attributed.
