Attacker action: an attacker running a proof-serving service (SIP-defined light-client gateway) crafts a proof byte stream where a `Shunt` variant's `hashes` array is truncated to fewer than the type's fixed count (e.g., padded with `TrieHash::ZERO` via `deserialize_id_hash_node!`), passing `consensus_deserialize` but causing `verify_segment_proof`/`verify_shunt_proof_head` to compute a hash using zeroed sibling hashes that happens to match a `root_hash` the attacker precomputed offline for an unrelated (key, value). Preconditions: attacker can precompute (query-only) node hashes from public chainstate for any real block. Call sequence: RPC client deserializes proof -> `verify_proof` -> `is_proof_well_formed` -> `verify_segment_proof` -> `verify_shunt_proof_head`. Equality that must break: `*root_hash == trie_hash` returns true for a `path`/`value` combination not present in the trie identified by `root_hash`. Impact: Critical - forged inclusion proof accepted by any light client (wallets, bridges) trusting `verify_proof`, i.e., proof-verified (key,value) != actually committed (key,value). Proof idea: unit/integration test constructing a proof with a `Shunt` entry using zero-padded hashes for a crafted (key,value) pair and confirming whether `verify_proof` incorrectly returns true against a real chain's `root_hash`/`root_to_block` table produced by `read_root_to_block_table`.
