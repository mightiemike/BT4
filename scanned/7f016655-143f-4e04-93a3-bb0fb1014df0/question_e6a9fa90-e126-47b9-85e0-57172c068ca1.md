Target: `MARF::insert_leaf` / `inner_insert_batch` (marf.rs:1470-1523) key ordering dependency for skiplist root hashing (`last insert updates the root with the skiplist hash`). Attacker action: submit two Nakamoto blocks with the same set of Clarity state writes but where the miner orders the underlying `keys`/`values` batch differently (both are valid orderings per Clarity's nondeterministic-but-equivalent map iteration in some analysis pass), causing `inner_insert_batch`'s last-key-special-case to compute a different final root hash depending on which key is last. Preconditions: any block whose Clarity execution touches more than one MARF key such that batch insert order is not fully pinned by the block's transaction order (e.g., events from a single contract-call touching multiple map keys). Call sequence: Clarity `ClarityDatabase` writes -> `MARF::insert_leaf_in_batch` (all but last) -> final `MARF::insert_leaf` for `last_key` -> `calculate_node_hashes`. Equality that must break: `state_index_root` for block content C computed with key order O1 != `state_index_root` for the same content C computed with key order O2 on another honest node whose Clarity execution enumerates the same logical writes in a different order. Impact: Critical - nondeterministic root from write-order sensitivity is a direct consensus failure. Proof idea: integration test calling `inner_insert_batch` twice with the same key/value set but reversed order, asserting the two resulting `state_index_root`s are equal (or, if this test fails, that constitutes the vulnerability) — this directly targets whether MARF root computation is a commutative function of the write-set, which the identity requires.
