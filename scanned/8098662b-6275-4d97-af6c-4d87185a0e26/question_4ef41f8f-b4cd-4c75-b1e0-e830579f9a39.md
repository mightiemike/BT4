In `crates/light-client-prover/src/circuit/mod.rs::run_l1_block` (docs/light-client-circuit.md:69-79), when processing `DataOnDa::Complete`, the LCP verifies the 'sequencer commitment relation': `previous_commitment_index`/`previous_commitment_hash` on the batch proof must match the commitment stored in the LCP's own JMT state (`SequencerCommitmentAccessor`), which was populated earlier from `DataOnDa::SequencerCommitment` blobs whose sender must equal `sequencer_da_public_key`. An unprivileged attacker cannot forge a `SequencerCommitment` (its sender is checked), but can inscribe a duplicate or conflicting `DataOnDa::SequencerCommitment` reveal transaction with the *correct* sequencer signature copied byte-for-byte from a previously observed legitimate commitment onto a different Bitcoin block/wtxid, replaying it before the genuine one is mined at a different `index`. Precondition: sequencer has already broadcast one legitimate commitment observed by the attacker; attacker rebroadcasts the identical signed body as their own inscription in an earlier block. Binding: the commitment stored at a given `index` in `SequencerCommitmentAccessor` == the single canonical commitment the sequencer's key authorised for that index, counted exactly once. Does `run_l1_block`'s handling of `DataOnDa::SequencerCommitment` (mod.rs, 'if submitted by the sequencer and no existing commitment is stored for that index, it is added') correctly no-op on the replay, or could replay-then-original ordering across blocks cause the LCP JMT to store the replayed copy under a different DA context, breaking downstream index continuity used in `apply_l2_blocks_from_sequencer_commitments`'s sequential-index assertion (`last_commitment_end_height + 1 == sequencer_commitment_l2_start_height`)? Impact: Critical - if replay causes duplicate-index bookkeeping to diverge between two honest LCP instances that saw the replay in different relative block positions, this is a DETERMINISM split. Proof idea: cargo test feeding the same signed `SequencerCommitment` bytes into `run_l1_block` twice across two separate L1 blocks and asserting the second is a no-op and the JMT state matches a single honest run.
