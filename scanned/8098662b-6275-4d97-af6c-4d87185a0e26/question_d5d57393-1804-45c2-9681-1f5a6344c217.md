In `crates/sequencer/src/rpc.rs::send_raw_deposit_transaction`, deposit validity is checked via `evm.get_call` — a stateless `eth_call`-style simulation against `BlockId::pending()` — before adding to `DepositDataMempool`. An unprivileged attacker submits deposit blob D1 that passes simulation (e.g. because the Bridge's `processedTxIds[txId]` is not yet set for D1's txId), then rapidly submits a byte-identical or near-identical deposit blob D2 differing only in bytes that don't affect the `Deposit` struct's `txId` derivation but do affect an unrelated field, before D1 is included in a block. Precondition: sequencer running, mempool `pending_deposits: HashSet<Vec<u8>>` (deposit_data_mempool.rs:24) dedups on the raw byte vector, not on the derived Bitcoin `txId`. Binding: cBTC credited via `deposit()` for a given Bitcoin `txId` == exactly one deposit executed for that `txId`, counted exactly once. Since `pending_deposits` hashes the full raw blob rather than the parsed `txId`, can two distinct raw blobs (e.g. differing by an appended no-op byte inside a VarInt field, or a semantically-irrelevant witness field) both parse to the SAME `txId` in `Bridge.sol::deposit`, both pass `evm.get_call` simulation (since `processedTxIds` isn't set yet in the pending, uncommitted view), and both get queued as separate deposit system transactions, relying solely on the Solidity `require(!processedTxIds[txId])` at actual execution time to reject the second? Impact: Critical if that Solidity-side check is bypassable (excluded, Solidity bug) but High/Critical for this repo: wasted system tx slot / potential double-processing race if simulation view isn't consistent with commit-time view across the two queued sys txs in the same block. Proof idea: cargo test queuing two distinct-byte, same-txId deposit blobs into `DepositDataMempool`, running both through `process_sys_txs` in one L2 block, and asserting only one increases `recipient` balance while confirming the mempool's dedup key is actually the parsed txId, not the raw bytes.
