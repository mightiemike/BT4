Target: `NakamotoChainState::accept_block`'s ordering of `is_wellformed_tenure_start_block` / `is_wellformed_tenure_extend_block` checks vs `get_expected_burns` (stackslib/src/chainstate/nakamoto/mod.rs). Attacker action: attacker submits a block that is simultaneously well-formed as neither a tenure-start nor continuation from the *staging* DB's point of view on node A (parent absent, so both checks are best-effort skipped) but is later found, once the parent arrives, to violate `is_tenure_extend && is_new_tenure` mutual exclusion enforced only in `append_block`. Preconditions: parent block not yet downloaded when the child is submitted (routine in P2P propagation, exploitable by an attacker deliberately delaying parent relay to specific peers). Call sequence: accept_block (stores block optimistically since parent-dependent checks are deferred) -> later append_block re-derives `is_new_tenure`/`is_tenure_extend` and enforces exclusivity. Equality that breaks: static-validation verdict at accept time == static-validation verdict at append time; if a node processes the block before the parent needed for full validation is available and some code path short-circuits acceptance, two nodes with different parent-arrival timing could diverge on whether the block is ever staged as attachable. Scoped impact: High (bounded to staging-attachability divergence, escalating to Critical only if one node fully appends it without the exclusivity re-check). Proof idea: integration test submitting a block with both tenure-start and tenure-extend markers before its parent is known, then supply the parent and assert `append_block` uniformly rejects it with 'Both started and extended tenure' on all nodes regardless of arrival order.
