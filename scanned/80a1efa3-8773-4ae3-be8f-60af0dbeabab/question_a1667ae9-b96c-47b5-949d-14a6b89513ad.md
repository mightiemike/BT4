Target: `shadow_chainstate_repair` iterative loop building one shadow tenure per skipped burn height (stackslib/src/chainstate/nakamoto/shadow.rs). Attacker action: although shadow-block creation itself is operator-only, an unprivileged attacker can trigger the *precondition* for shadow-repair to become necessary by intentionally submitting zero block-commits during a prepare phase they could have committed to (withholding their own BTC spend), causing an empty prepare phase; when the network later disagrees on whether/how many shadow tenures were needed (e.g., partial rollout), some nodes compute `header_sn.block_height+1 .. sort_tip.block_height` differently based on their own already-processed tip. Preconditions: empty prepare phase caused by withheld attacker commits; asynchronous operator rollout of the shadow-repair tool across the network. Call sequence: shadow_chainstate_repair -> `get_canonical_block_header`/`get_canonical_burn_chain_tip` -> loop `make_shadow_tenure` + `process_shadow_block` per missing height. Equality that breaks: the sequence/number of shadow tenures synthesized on node A == the sequence on node B, since the loop bounds depend on each node's *current* canonical tip at repair time, and nodes repairing at different points in the rollout could synthesize a different count of shadow blocks for the same gap. Scoped impact: Critical, permanent chain split between differently-shadow-patched nodes for the same underlying gap. Proof idea: simulate two nodes at different canonical heights when shadow-repair tooling runs, assert the resulting shadow tenure sequences (`NakamotoBlock::block_id()` list) differ, then verify subsequent normal blocks fail to reconcile via `validate_shadow_parent_burnchain` cross-checks.
