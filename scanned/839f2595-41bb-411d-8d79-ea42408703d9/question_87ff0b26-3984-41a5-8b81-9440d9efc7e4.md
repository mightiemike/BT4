Target: NakamotoChainState::verify_signer_signatures and NakamotoBlockHeader::compute_voting_weight_threshold (stackslib/src/chainstate/nakamoto/mod.rs). Attacker action: an unprivileged miner proposes a Nakamoto block whose signer_signature vector is built from valid signatures collected from a stale RewardSet snapshot (e.g. right at a reward-cycle boundary) rather than the reward set the sortdb currently associates with that block's burn view. Preconditions: reward cycle boundary where SortitionDB's canonical RewardSet for the block's cycle differs from a just-superseded RewardSet the attacker cached. Call sequence: verify_signer_signatures recomputes total_weight = reward_set.total_signing_weight() and threshold = compute_voting_weight_threshold(total_weight) from whatever RewardSet is passed in by the caller; if two honest nodes pass different RewardSet snapshots (stale vs. current) for the same block, they compute different thresholds. Equality that breaks: threshold_node_A(total_weight_A) == threshold_node_B(total_weight_B) for the same block and same reward cycle. Impact: Critical - two honest nodes render different accept/reject verdicts on the same block, producing a chain split. Proof idea: two-node integration test that advances the burnchain across a reward-cycle boundary with a deliberately delayed RewardSet propagation on one node, submits a single Nakamoto block signed against the old set, and asserts canonical tip equality between both nodes.
