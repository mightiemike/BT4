In stackslib/src/chainstate/stacks/index/storage.rs, BlockHashCache::store_block_hash() (cache.rs) asserts !self.block_hash_cache.contains_key(&block_id) but TrieFileStorage::get_block_id_caching() and TrieStorageConnection::get_block_id_caching() populate this cache keyed only by the u32 rowid from trie_sql::get_block_identifier(). Precondition: attacker extends two sibling forks from the same tip so that two distinct Nakamoto blocks are processed by the same open TrieFileStorage session without a flush between them, each producing a MARF trie whose block_identifier rowid is reused after a fork-drop/rollback in unconfirmed mode. Call sequence: open_block(bhh_A) -> get_block_id_caching(bhh_A) caches id=N; fork drop; open_block(bhh_B) on the reorg'd path where sqlite reissues rowid N to bhh_B -> get_block_id_caching(bhh_B) hits the stale cache entry for id=N still mapped to bhh_A's hash in block_id_cache. Equality that must hold: get_block_hash_caching(N) on node A == the actual header of the block stored at rowid N == what node B independently recomputes; if this breaks, TrieHash(chr) child hashes computed via get_block_hash_caching(ptr.back_block()) diverge and the committed root != the root every node recomputes. Impact: Critical, state-root divergence across a reorg with no reconciliation. Proof idea: Rust integration test on a booted MARF that opens a block, drops/reorgs it via an unconfirmed-trie rollback, opens a second block that would receive the same sqlite rowid, and asserts get_block_hash_caching(rowid) is identical to the hash trie_sql::get_block_hash(&db, rowid) reads directly from disk.
