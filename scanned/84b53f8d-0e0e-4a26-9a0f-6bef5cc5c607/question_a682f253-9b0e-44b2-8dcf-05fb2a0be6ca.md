Target: DepositDataMempool::fetch_deposits(limit_per_block) which returns a cloned slice from accepted_deposit_txs without removing them, and DepositDataMempool::remove_deposits which is only called by the sequencer runner after successful block production. Attacker action: submit SYSTEM_TX_GAS_LIMIT-sized deposit blobs that pass the eth_call simulation gate (e.g. simple valid deposits to attacker-controlled addresses) in a volume that always fills limit_per_block ahead of a legitimate, larger, already-pending Clementine deposit that was submitted earlier (FIFO by accepted_deposit_txs VecDeque push_back order, so this specifically targets ordering not volume alone). Preconditions: attacker's own deposits are cheaper/faster to construct and submitted after the legitimate one but the runner is mid-cycle so timing allows front-loading. Call sequence: fetch_deposits(limit_per_block) always returns the front of the VecDeque, so as long as attacker deposits are queued before the legitimate one, they'll be fetched first; this does not indefinitely block the legit one purely by FIFO order (it is a queue position issue), but check whether SM.deposit_tx_size / repeated submissions of already-pending duplicates can requeue and effectively reset the legitimate deposit's position. Binding: the deposit set fetch_deposits returns for inclusion == the deposit set that was queued first (FIFO fairness), and whether a legitimate deposit already at position 0 can ever be displaced from that position. Impact: Critical only if position 0 changes; otherwise excluded (queue-depth DoS is out of scope) — this question targets whether remove_deposits' retain-based filtering by recomputed calc_tx_id can accidentally remove the wrong entry when two blobs share the collision from calc_tx_id described above. Proof idea: cargo test queuing deposit A first, then a colliding-hash deposit B (per the calc_tx_id concatenation ambiguity), calling remove_deposits with only B's bytes, and asserting A is not also removed from accepted_deposit_txs/pending_deposits.
