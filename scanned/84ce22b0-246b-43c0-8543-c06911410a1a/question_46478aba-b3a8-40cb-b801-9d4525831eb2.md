DepositDataMempool::remove_deposits (crates/sequencer/src/deposit_data_mempool.rs) recomputes calc_tx_id for every entry in accepted_deposit_txs and pending_deposits.remove(txid) whenever the id matches. Because calc_tx_id can panic-free-error only via calc_tx_id(deposit).expect("calc_tx_id should never be called on non-deposit"), what happens if an attacker's earlier add_deposit_tx call inserted a blob that decodes successfully via BridgeContract::depositCall::abi_decode_raw (satisfying calc_tx_id's own decode) but produces a moveTx whose vin/vout are non-canonical (e.g., zero-length) such that a LATER legitimate deposit's calc_tx_id happens to collide bytewise on the sha256d output purely due to the reduced entropy of a crafted degenerate vin/vout? Binding: calc_tx_id(attacker_deposit) == calc_tx_id(legitimate_deposit) implies they must correspond to the same Bitcoin txid Clementine presigned, but if attacker crafts a colliding preimage, remove_deposits would delete the legitimate deposit from accepted_deposit_txs when only the attacker's was meant to be removed. Impact: Critical -- legitimate deposit removed from mempool without having been included, permanently dropping the user's pending mint. Proof idea: cargo test attempting a preimage search over small-length crafted vin/vout showing at minimum that calc_tx_id has no domain separation from real Bitcoin txids, and asserting remove_deposits' retain-closure removes by id equality only, not by full byte equality of the Deposit itself.
