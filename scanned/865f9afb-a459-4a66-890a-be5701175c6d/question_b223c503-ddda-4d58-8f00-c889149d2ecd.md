Target `DepositDataMempool::calc_tx_id` (crates/sequencer/src/deposit_data_mempool.rs) which computes the *dedup* key from `tx.version, tx.vin, tx.vout, tx.locktime` only, deliberately excluding `tx.witness`. Attacker action: submit two `citrea_sendRawDepositTransaction` blobs with identical `version/vin/vout/locktime` fields but different `witness` (hence different recipient address extracted from the witness script by `Bridge.sol::deposit`). Preconditions: both blobs pass the `eth_call` simulation independently before either is added; sequencer running with an empty mempool for the first call. Call sequence: RPC -> `make_deposit_tx_from_data` -> `get_call` simulation success for blob A -> `add_deposit_tx(A)` succeeds, `pending_deposits` keyed by `calc_tx_id(A)` -> RPC call with blob B where `calc_tx_id(B) == calc_tx_id(A)` -> `add_deposit_tx` returns `Ok(false)`, rejecting B. Binding: `calc_tx_id(deposit_blob)` must equal a value that uniquely determines the *entire* accepted deposit including witness/recipient, i.e., `calc_tx_id(A) == calc_tx_id(B)` implies `A == B`; the test shows this equality can hold while `A != B` (different witness), meaning the dedup key is not the same as the CUSTODY-relevant blob. Scoped impact (Critical, borderline High): a legitimate second deposit to a different recipient can be silently dropped by the FIFO mempool despite differing witness data, potentially freezing that depositor's cBTC mint. Proof idea: cargo test constructing two ABI-encoded depositCall blobs sharing vin/vout/version/locktime but differing witness scripts, asserting `calc_tx_id` collides and the second `add_deposit_tx` is rejected even though it targets a different recipient.
