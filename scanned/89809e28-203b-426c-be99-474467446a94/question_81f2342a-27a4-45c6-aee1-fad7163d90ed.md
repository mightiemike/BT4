Target: `NakamotoStagingBlocksTx::add_shadow_block` (stackslib/src/chainstate/nakamoto/shadow.rs). Attacker action: none required from an unprivileged attacker directly (shadow blocks require tooling), but attacker can race a normal block submission against shadow-block insertion into the same tenure by submitting a normal Nakamoto block for a consensus hash right as `is_shadow_tenure` check is evaluated. Preconditions: `nakamoto_staging_blocks` table is empty for the consensus hash at the exact moment attacker's normal block's `store_block` call runs its `is_shadow_tenure` check (mod.rs `store_block` line 688) versus the moment a shadow block is added. Call sequence: `store_block` reads `is_shadow_tenure(&block.header.consensus_hash)` -> `false` -> inserts a non-shadow block; concurrently, `add_shadow_block` reads `SELECT 1 FROM nakamoto_staging_blocks WHERE consensus_hash=?1` -> finds the just-inserted non-shadow row -> since `is_shadow_tenure` is now `false` too -> returns `Err(InvalidStacksBlock)`, or vice versa if ordering reversed, both racing to define the tenure's obtain_method. Equality that must hold: the set of blocks admitted for a given `consensus_hash` on node A == on node B (a tenure is either all-shadow or all-normal, never mixed). Scoped impact: Critical if a race lets one node accept a normal block for a consensus hash that another node has already sealed as shadow-only, producing divergent staging DBs and different canonical tips. Proof idea: concurrent-insert integration test racing `store_block` and `add_shadow_block` for the same consensus_hash inside one SQLite transaction boundary, assert final state (`is_shadow_tenure` result) is identical and deterministic across repeated runs and across two independently-ordered nodes.
