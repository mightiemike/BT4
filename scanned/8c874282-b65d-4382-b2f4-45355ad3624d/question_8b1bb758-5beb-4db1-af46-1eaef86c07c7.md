In `NakamotoChainState::get_expected_burns` (stackslib/src/chainstate/nakamoto/mod.rs), for a block *without* a tenure-change tx, the expected burn is taken from the parent's `anchored_header.total_burns()` rather than the current burnchain tip's total burn. Can a miner submit a non-tenure-change Nakamoto block whose `header.burn_spent` matches its immediate parent's `total_burns()` but is stale relative to the canonical burnchain tip's true accumulated burn (because the parent itself was mined atop an older burn view before further burnchain blocks with no sortition arrived), such that `common_validate_against_burnchain`'s equality check `self.header.burn_spent != expected_burn` passes even though the block does not reflect the current `tenure_burn_chain_tip.total_burn`, letting a signer set that hasn't refreshed its burnchain view sign a block that the majority-synced signers/miners would reject? Preconditions: a period with burn blocks that have no winning sortition, so `total_burn` accumulates but no tenure-change is needed. Equality that should hold but doesn't: `block.header.burn_spent` == the burnchain tip's actual accumulated `total_burn` (STATE_ROOT/TENURE precondition). Impact: High, minority-triggerable static-validation divergence bounded by burn-accounting rather than direct fund loss, escalate to Critical only if it lets an invalid block be accepted network-wide. Proof idea: integration test producing several burn blocks with no sortition between two Nakamoto blocks, then submit a non-tenure block whose `burn_spent` reflects only the parent's stale total, and check whether `validate_normal_against_burnchain` on a fully-synced node's `db_handle` still accepts it.
