Target: `LeaderBlockCommitOp::check`'s parent back-pointer validation together with `select_winning_block`'s parent linkage assumed by tenure. Attacker action: an unprivileged miner submits a commit with `parent_block_ptr`/`parent_vtxindex` pointing to a sortition that had `sortition: false` (no winner) rather than to a real prior winning commit. Preconditions: a burn block earlier in the chain where sortition failed (e.g., all commits rejected or null-miner won). Call sequence: `parse_from_tx` (checks only `parent_block_ptr < block_height`, no live-winner check) -> `check` -> `check_common`/`check_pox` -> distribution -> `select_winning_block`. Equality: only commits whose parent linkage traces to the actual prior *winning* block-commit chain should be eligible to win; the winner selected by node A's traversal of parent pointers == winner selected by node B's traversal. Impact: Critical — accepting a commit whose parent pointer references a non-winning (or nonexistent) prior commit as a legitimate chain-continuation could let an attacker fork the miner UTXO-chaining logic in `make_min_median_distribution`, producing a `burns`/`frequency` computation that differs between nodes replaying the same ops, causing a chain split. Proof idea: Rust integration test with a commit chained to a sortition where `tip.sortition == false`, asserting the commit is excluded from `Vec<BurnSamplePoint>` (frequency counted at 1, not chained) identically on two independent chainstate replays.
