LeaderBlockCommitOp::check (stackslib/src/chainstate/burn/operations/leader_block_commit.rs) routes to check_after_pox_sunset() or check_pox(epoch_id, burnchain, tx, reward_set_info) depending on burnchain.pox_constants.is_after_pox_sunset_end(self.block_height, epoch.epoch_id). Can an unprivileged committer submit a LeaderBlockCommitOp exactly at the sunset_end block height boundary with commit_outs matching the PoX-branch format but relying on integer block_height comparisons that could be evaluated against a locally cached burnchain.pox_constants on one node versus a freshly-loaded one on another (e.g. after a config reload or epoch transition mid-sync), such that is_after_pox_sunset_end returns true on one node and false on another for the identical block_height, causing one node's check() to call check_after_pox_sunset (rejecting non-burn commit_outs) while the other calls check_pox (accepting PoX commit_outs) for the same commit? Precondition: a block-commit transaction submitted at the exact sunset_end block height. Equality: is_after_pox_sunset_end(self.block_height, epoch.epoch_id) and hence check()'s Ok/Err verdict must be identical on every node for the same block_height/epoch pair. Impact: Critical, a commit accepted as eligible on one node and rejected on another for the sortition burn_dist causes divergent winners. Proof idea: integration test mining a block-commit exactly at pox_constants.sunset_end and asserting check() returns identically across two independently-initialized SortitionDB instances built from the same burnchain config.
