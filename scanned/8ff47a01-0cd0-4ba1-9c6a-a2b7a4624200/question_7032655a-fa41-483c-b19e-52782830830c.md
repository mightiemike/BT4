BurnSamplePoint::get_total_burns (stackslib/src/chainstate/burn/distribution.rs) folds sample_point.burns (u128, from checked min(median,most_recent) computed per-candidate) into a u64 accumulator via checked_add, returning None on overflow; make_sortition_ranges calls .unwrap() on this Option. Given burn_fee is bounded by Bitcoin's transaction output amount (attacker-controlled up to their own UTXO value), can a set of unprivileged miners collectively submit block-commits at a single burn height whose summed burns (each within u64 range individually) overflow u64::MAX in aggregate, causing get_total_burns() to return None and the subsequent .unwrap() in make_sortition_ranges to panic deterministically on every node processing that burn block -- and is this panic actually reached identically on all nodes (safe), or could an implementation difference (e.g. a node using a checked u128 total elsewhere for get_total_burns_u128()) cause one node to panic while another silently proceeds using windowed_median_burns() which sums differently? Precondition: multiple committers each spending near-u64::MAX burn_fee at the same height (theoretically possible on a regtest/testnet fork with unrealistic UTXO values used for the test harness, not requiring real BTC value). Equality: get_total_burns's Option result must be identical (Some(x) with the same x, or None) across every node evaluating the same block_commits set. Impact: Critical, a deterministic halt on one node and continued operation on another during BlockSnapshot::make_snapshot processing is a state-root non-reproducibility bug (one node's chain tip advances, the other's does not).
