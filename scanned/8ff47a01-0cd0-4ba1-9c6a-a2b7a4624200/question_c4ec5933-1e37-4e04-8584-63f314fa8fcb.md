BurnSamplePoint::zero (stackslib/src/chainstate/burn/distribution.rs) is used by BlockSnapshot::null_miner_wins to construct a synthetic BurnSamplePoint whose candidate field is a full clone of commit_winner with only the block_header_hash bit-flipped -- all other fields (txid, apparent_sender, burn_fee, key_block_ptr/key_vtxindex) are IDENTICAL to the real winner. If null_miner_wins() ever returns true and the caller in BlockSnapshot::make_snapshot sets reject_winner_reason (correctly producing a no-sortition snapshot), verify: does any other code path (e.g. get_consumed_leader_keys, or the accepted_ops bookkeeping in Burnchain::sync_with_indexer) accidentally treat this synthetic null_winner clone as a real, distinct LeaderBlockCommitOp with its own txid, causing the SAME key_block_ptr/key_vtxindex leader key to be marked consumed twice (once for the real commit_winner and once for the phantom null_winner) in a way that differs between two nodes depending on whether the no-sortition path was taken via null_miner_wins vs. check_miner_is_active? Precondition: a burn block where null_miner_wins() returns true. Equality: the set of leader keys marked 'consumed' after processing a burn block whose winner was rejected via the null miner must be identical to the set consumed when rejected via check_miner_is_active, and identical across all nodes. Impact: Critical, an inconsistently-consumed leader key could let a future commit re-reference (or fail to reference) the same key on some nodes vs others, corrupting LeaderBlockCommitOp::check_common's leader-key existence check divergently.
