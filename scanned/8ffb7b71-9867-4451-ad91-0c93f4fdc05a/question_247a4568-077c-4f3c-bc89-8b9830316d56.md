In `run_l1_block`, `DataOnDa::Complete(proof)` requires `blob.sender().as_ref() != batch_prover_da_public_key` to match, but the `DataOnDa::Chunk` variant used to construct an `Aggregate`-derived `complete_proof` performs no sender check on individual chunks - only the wrapping `Aggregate` blob is checked. Can an attacker inscribe a `DataOnDa::Chunk` reveal whose wtxid is NOT referenced by any real prover aggregate, and separately (without ever forging the batch-prover signature) can they cause `ChunkAccessor::<S>::insert` state bloat or wtxid collisions that make an honest full node and an honest light-client-prover disagree on `ChunkAccessor::<S>::get(wtxid, ...)` for the same wtxid, if one node processed the attacker's chunk-bearing L1 block before the real chunk (e.g. differing tie-break on same-block same-wtxid duplicate transactions, which cannot exist since wtxid is unique per tx, but different: attacker inscribes chunk1 in block N at wtxid W, prover organically reuses same content producing same wtxid W in block N+5, causing a JMT no-op reinsertion) - is there any scenario where two honest full nodes / light-client-prover instances following identical `da_txs` iteration order from `verify_transactions` diverge on the final `ChunkAccessor` value for a shared wtxid due to non-deterministic HashMap/Vec ordering in `da_service.extract_relevant_blobs_with_proof` or `verify_transactions`? Binding: the JMT state (and thus `lcp_state_root`) one honest light-client-prover computes for L1 block N == the JMT state every other honest light-client-prover computes for the same L1 block N, i.e. `ChunkAccessor` insert order is deterministic across nodes. Impact: Critical, a split in the light client proof (two honest provers committing different `lcp_state_root` / `LightClientCircuitOutput` for the same L1 block). Proof idea: cargo test running `run_l1_block` twice with the same `da_txs` Vec but permuted order (if `extract_relevant_blobs_with_proof` return order is not canonically sorted, e.g. by transaction position in block) and asserting `lcp_state_root` equality; if it fails, that permutation is the vulnerability class, though it requires the DA layer itself to return non-deterministic ordering, which should be checked in `crates/bitcoin-da/src/service.rs`.
