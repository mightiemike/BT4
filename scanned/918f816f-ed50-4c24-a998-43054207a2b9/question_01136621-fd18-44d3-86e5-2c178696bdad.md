The mark_failed_and_deprioritize_peer / attempt_failed_tenures bookkeeping in NakamotoTenureDownloaderSet only deprioritizes the reporting peer for PEER_DEPRIORITIZATION_TIME_SECS and never invalidates or re-derives the RewardSet snapshot (`start_reward_set`/`end_reward_set`) that was captured into the *retried* NakamotoTenureDownloader::new call on the next attempt from `current_reward_cycles`. If an attacker forces repeated failures (e.g. serving a truncated tenure to trigger try_accept_tenure_blocks's Err path) timed around a burnchain reorg that changes the reward-cycle anchor block, can the retried downloader be instantiated with `attempt_count` incremented but a RewardSet that is stale relative to what `current_reward_cycles` now holds for that same start_reward_cycle key, because `current_reward_cycles` is a reference passed in per-call rather than re-derived from a single canonical source at accept time? Equality broken: SIGNING — the signer weight threshold check for the retried download must use the identical RewardSet every other node derives for that reward cycle. Impact: High/Critical boundary — if the stale RewardSet still passes threshold checks for a block signed under the old set, a block could be accepted on this node that a node with the fresh RewardSet would reject. Proof idea: integration test forcing a download failure immediately before a reward-cycle anchor-block reorg, then asserting the RewardSet used on retry equals the RewardSet computed fresh from the post-reorg SortitionDB.
