Attacker action: submit a tenure-start block whose coinbase VRF proof was generated with the attacker's OWN VRF private key over the CORRECT `sortition_hash`, but the block's `header.consensus_hash`/tenure links to a leader key belonging to a DIFFERENT registered public key. Preconditions: attacker controls two registered leader keys across two tenures. Can the lookup be desynchronized (e.g. wrong index arguments) so a proof validates against a public key that is not the one the burnchain sortition committed to? Scoped impact: Critical, accepted block whose VRF proof doesn't correspond to the committed leader key.
