Target: storage.rs's `calculate_marf_root_hash` and `with_reinstated_data`, which temporarily reinstates a moved TrieRAM's data into `storage_tx` to walk ancestor tries during the seal step. Attacker action: submit a block at a height where an ancestor MARF path lookup during `with_reinstated_data` must resolve a back-pointer into a block that is concurrently being squashed (squash.rs), so that the reinstated read sees a half-migrated blob (some bytes already moved to the squashed shared-blob format, others still in the archival marf_data table) rather than a fully consistent snapshot. Preconditions: a MARF undergoing squash concurrently with a new block's seal() call touching ancestor hashes near the squash_height boundary. Call sequence: inner_seal_marf -> with_reinstated_data -> calculate_marf_root_hash -> Trie::get_trie_root_hash -> Trie::get_trie_ancestor_hashes_bytes (reads ancestor block hashes, potentially from a half-migrated blob). Equality that breaks: the MARF root hash computed while squash is in-flight == the MARF root hash computed once the squash fully completes (or on a node that never squashes at all), for the identical block. Scoped impact: Critical, state root not reproducible between an archival-only node and one that squashes concurrently with new block processing. Proof idea: Rust integration test that runs squash and new-block sealing concurrently (or in a deliberately interleaved sequence within the test) and asserts the final committed root hash matches an equivalent non-concurrent (squash-then-seal, or seal-then-squash) control run.
