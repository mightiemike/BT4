Target: `NakamotoChainState::check_normal_coinbase_tx` (stackslib/src/chainstate/nakamoto/mod.rs). Attacker action: attacker miner who won a sortition submits a Nakamoto block whose coinbase VRF proof correctly verifies (so `check_normal_coinbase_tx` returns Ok) but whose coinbase transaction's `recipient_opt` field is set to a completely unrelated principal never involved in the block-commit or leader-key registration. Preconditions: attacker's own block-commit and VRF keypair are valid and won the sortition; epoch >= Epoch21 so alt-recipient coinbases are legal. Call sequence: `validate_normal_against_burnchain` -> `check_miner_signature` (checks only that the header was signed by the tenure's pubkey_hash, unrelated to coinbase recipient) -> `check_tenure_tx` -> `check_normal_coinbase_tx` (checks only VRF proof, not recipient) -> block accepted; `make_scheduled_miner_reward` later reads `recipient_opt` verbatim. Equality that breaks: recipient credited by `insert_miner_payment_schedule`/`get_matured_miner_payment` should equal 'the sortition winner's specified recipient' where 'sortition winner' is cryptographically tied to the winning block-commit/leader-key -- but no validation function ties `recipient_opt` to anything derived from the winning sortition; it is an attacker-controlled unauthenticated field accepted network-wide as valid. Impact: Critical -- every honest node accepts the block and credits the reward to an arbitrary attacker-chosen address, a network-wide-accepted block-reward misdirection (not theft between miners, but a structural gap letting the winning miner redirect payment to any principal, which is fine by design -- the bug is if this can be exploited to redirect an *already-scheduled prior tenure's* payout via the wrong tenure's recipient field, see next test). Proof idea: Rust integration test asserting `check_normal_coinbase_tx` returns Ok for a coinbase with `recipient_opt = Some(principal_unrelated_to_leader_key_or_block_commit)`, then asserting the block is fully accepted by `validate_normal_against_burnchain`, demonstrating recipient is entirely unauthenticated relative to sortition identity.
