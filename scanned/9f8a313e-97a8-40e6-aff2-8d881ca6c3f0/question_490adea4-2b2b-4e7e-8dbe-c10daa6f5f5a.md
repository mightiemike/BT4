DepositDataMempool (crates/sequencer/src/deposit_data_mempool.rs) is constructed fresh via DepositDataMempool::new() and is only ever populated in-memory (accepted_deposit_txs: VecDeque<Deposit>, pending_deposits: HashSet<Vec<u8>>), with no persistence to LedgerDB. If the sequencer process restarts between add_deposit_tx succeeding and the corresponding process_sys_txs/remove_deposits cycle completing on-chain, the in-memory queue is lost. Can an attacker exploit this restart-induced amnesia by submitting a deposit blob for a move-tx immediately before a sequencer restart (attacker cannot trigger the restart themselves, but can time submission around a known upgrade/restart window), such that the deposit is silently forgotten by the new DepositDataMempool::new() instance forever, since only the attacker (or the real depositor whose move-tx this represents) has a copy of the raw bytes and there is no other component that re-derives pending deposits from Bitcoin history? Precondition: sequencer restarts (a normal, non-adversarial operational event) with a deposit blob still in accepted_deposit_txs and not yet in a finalized L2 block. Call sequence: send_raw_deposit_transaction -> add_deposit_tx (in-memory only) -> sequencer process restart -> DepositDataMempool::new() -> the previously-accepted deposit bytes are unrecoverable except by the original submitter resubmitting. Binding broken: cBTC credited by a SYSTEM_SIGNER Bridge deposit == exactly one Bitcoin move-to-vault output Clementine actually presigned, counted once -- fails transiently in the sense that a real deposit is delayed/dropped from the queue with no protocol-level (as opposed to operational) recovery signal to the depositor. Impact: High, since recovery only requires the legitimate depositor to resubmit (not a fund-loss by itself, and this is a known operational gap rather than adversarial exploit) but worth confirming there is no double-mint risk on resubmission after restart. Proof idea: cargo test that adds a deposit, drops and recreates DepositDataMempool, resubmits the same bytes, and asserts add_deposit_tx succeeds again with no double application on-chain (relying on Bridge.sol's processedTxIds as the actual safety net).
