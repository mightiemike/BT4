Target `NakamotoSigners::valid_vote_transaction` / `parse_vote_for_aggregate_public_key` and `update_filtered_transactions` (signer_set.rs lines ~1147-1228), used to admit a signer's aggregate-key vote transaction into a block. Attacker action: as a signer holding minority weight, broadcast two vote transactions for the same `(origin_address, nonce)` with different `txid`s; `update_filtered_transactions` picks the one with lower `txid` deterministically via `entry.txid() > transaction.txid()`. But an attacker can also broadcast the *same* nonce vote transaction to two different miners assembling competing blocks in the same tenure, each of which independently runs `update_filtered_transactions` over its own mempool ordering. Preconditions: minority signer weight, active PoX-4/5 voting window, two competing miners racing for the same tenure. Call sequence: mempool selection -> `update_filtered_transactions` -> included vote tx -> Clarity `vote-for-aggregate-public-key` in signers-voting.clar -> `aggregate-public-keys` map write -> next cycle's sBTC recipient key (`pox_5_compute_and_update_signers`'s `get-current-aggregate-pubkey`). Equality: the selected vote transaction (and hence the resulting aggregate public key committed to the reward set) on the canonical-tip block must equal what every node recomputes when replaying that exact same block — `update_filtered_transactions`'s deterministic tie-break on `txid` guarantees this *if* the block only ever contains the miner's chosen subset, so the real question is whether both candidate blocks (from the two racing miners) could each independently pass `valid_vote_transaction` and get included, i.e., whether the SORTITION winner determines which vote is canonical. Impact: Critical if the losing block's vote transaction contents diverge from the winner's and this affects the derived aggregate pubkey / sBTC waterfall address used for reward routing (`sbtc_pox5_deposit_taproot_output_key`), causing reward funds to be computed to a different address on two forks. Proof idea: two-fork Rust integration test where each fork's miner independently assembles a block including a different but individually-valid vote transaction for the same signer, assert `pox_5_compute_and_update_signers`'s derived `sbtc_address` differs, and force a reorg to show the losing fork's committed sBTC address becomes permanently unreachable/lost.
