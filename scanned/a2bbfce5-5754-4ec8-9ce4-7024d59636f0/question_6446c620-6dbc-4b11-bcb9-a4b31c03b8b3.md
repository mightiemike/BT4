Target: `NakamotoChainState::check_normal_coinbase_tx` (nakamoto/mod.rs), which calls `VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes())`. Can an attacker miner submit a coinbase VRF proof generated under a *different* leader key than the one registered via their `LeaderKeyRegisterOp.public_key` and referenced by the winning `LeaderBlockCommitOp.key_block_ptr`/`key_vtxindex`, such that `check_normal_coinbase_tx` is invoked with a mismatched `leader_vrf_key` due to a stale or wrong key lookup, given preconditions of two outstanding `LeaderKeyRegisterOp`s from the same miner at different block heights? Call sequence: sortition tallies winning commit -> `SortitionDB` resolves `key_block_ptr`/`key_vtxindex` to a `LeaderKeyRegisterOp.public_key` -> block acceptance calls `check_normal_coinbase_tx(leader_vrf_key, sortition_hash)` -> `VRF::verify`. Equality that must hold: `leader_vrf_key` resolved from the winning commit's `(key_block_ptr, key_vtxindex)` == the VRF public key under which the block's coinbase `vrf_proof` was actually generated. Scoped impact: Critical - a block accepted that should be invalid, since a wrong-key verification path that happens to still return `Ok(true)` for maliciously-chosen proof/key pairs would let a proof-less-bound block into the canonical chain. Exposed: all nodes since `VRF::verify` is deterministic and any divergence here is a static-validation bug, not a fork, but landing here would let an unbound proof pass everywhere, corrupting the seed used by the next tenure.
