`ForkManager::register_block` (crates/sovereign-sdk/rollup-interface/src/fork/manager.rs) advances `active_fork_idx` based on the sequencer's own tracked `height`, independently of `fork_from_block_number`'s lookup into the global `FORKS` static used inside `citrea_evm`/`query.rs`/`tx_validator.rs`. Since these are two separate fork-resolution mechanisms reading the same `get_forks()` table but invoked at different call sites (`CitreaSequencer::new`/block production hooks vs per-RPC-call `fork_from_block_number`), can an attacker time a transaction to land in the single L2 block where `ForkManager`'s `active_fork_idx` and a stateless `fork_from_block_number(height)` call for that same height disagree (e.g. due to `ForkManager` being constructed with a stale `current_l2_height` versus the height actually being produced), causing the sequencer to apply a stale spec's L1-fee/opcode rules to a block while `fork_from_block_number` elsewhere (used by the batch/light-client circuit) resolves the new spec for the same height? Binding: `SpecId` returned by `ForkManager::active_fork()` for L2 height N == `SpecId` returned by `fork_from_block_number(N)` for the same height N. Impact: Critical — a one-block spec mismatch changes opcode gas rules or fee formulas between block production and proof verification, making the produced block's state root unprovable under the circuit's resolved spec. Proof idea: cargo test in bin/citrea/tests/bitcoin/fork.rs constructing a `ForkManager` initialized one block behind the true activation height and asserting `active_fork().spec_id == fork_from_block_number(height).spec_id` fails, then checking whether this can occur in `CitreaSequencer::new`'s real initialization path.
