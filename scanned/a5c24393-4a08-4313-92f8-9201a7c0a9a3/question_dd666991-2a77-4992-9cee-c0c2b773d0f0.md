Target: `apply_l2_blocks_from_sequencer_commitments` sequencer public key parsing: `K256PublicKey::try_from_slice(sequencer_public_key).expect("Sequencer public key must be valid")` and subsequent per-block `verify_signature(l2_header, &sequencer_public_key)`. Attacker action: an unprivileged operator running a modified prover host supplies L2 blocks whose `SignedL2Header.signature` was produced by an attacker-controlled key, hoping `verify_signature` is only checked on a subset of blocks (e.g. only the first block of a commitment) rather than every block. Preconditions: attacker controls a full node/host that constructs `BatchProofCircuitInputV3Part1` fed to their own prover instance. Call sequence: `apply_l2_block` -> `verify_l2_block` -> `verify_signature(l2_header, sequencer_public_key)` invoked once per L2 block inside the `for _ in 0..state_change_count` loop. Binding: every `L2Block` counted in `state_roots`/`final_l2_block_hash` == a block whose header signature verifies under `sequencer_public_key`, with none skipped. Impact: Critical, an unsigned or wrongly-signed block folded into the state transition would let cBTC-affecting EVM execution (e.g. Bridge contract calls) the sequencer never authorized be proven as part of the canonical chain. Proof idea: cargo test inserting one block signed by a random key among otherwise correctly-signed blocks in the same commitment and asserting `apply_l2_block` returns an error causing the outer `.expect("L2 block must succeed")` to panic.
