Target: `citrea_evm::system_events::SystemEvent::BitcoinLightClientSetBlockInfo(hash, txs_commitments, coinbase_depth)` vs `BridgeDeposit` ordering within a single `produce_and_run_system_transactions` call. Attacker action: none on-chain; the question targets whether the sequencer itself could ever place a `BridgeDeposit` system tx for a deposit that references a Bitcoin block whose `set_block_info` event has not yet been applied within the same block's system-tx list, which an attacker could try to trigger by flooding `citrea_sendRawDepositTransaction` with a deposit blob claiming to be included in the very latest, not-yet-committed light-client block. Preconditions: attacker submits a deposit blob whose embedded block height/merkle proof references the newest DA block just about to be processed this cycle. Call sequence: `populate_deposit_system_events`/`populate_set_block_info_event` (citrea_evm) build the ordered `Vec<SystemEvent>` -> `create_system_transactions` assigns sequential nonces -> `apply_l2_block_txs` executes them strictly in list order. Binding: for every block, the index of the `BitcoinLightClientSetBlockInfo` system tx that establishes block X's info is strictly less than the index of any `BridgeDeposit` system tx whose merkle proof is verified against block X's `BitcoinLightClient` state. Impact: Critical - if a deposit tx executes before the corresponding `set_block_info`, the Bridge contract's proof verification would run against stale/absent light-client state, either wrongly rejecting a genuine deposit (frozen funds) or, if it fails open, minting from an unverified claim. Proof idea: cargo test with a deposit blob referencing the block committed in the same cycle and asserting the produced system-tx order always places `set_block_info` first, and that the deposit's merkle proof verifies against exactly that block's committed hash/commitment.
