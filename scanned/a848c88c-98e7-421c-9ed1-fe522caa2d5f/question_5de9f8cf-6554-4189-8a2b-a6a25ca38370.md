Target: `LightClientInputBuilder::build_from_l1_block`'s reliance on `ledger_db.get_light_client_proof_data_by_l1_height(previous_l1_height)` to source `previous_lcp_output` rather than re-deriving it from `previous_lcp_proof` verification inside the circuit. Attacker action: none direct (native-DB trust boundary), but attacker can trigger by causing consecutive L1 blocks to be processed where the *only* linkage between them is this ledger lookup; craft Bitcoin transactions so that `l1_height` sequence has an L1 reorg-adjacent block where an honest full node's `ledger_db` entry for `previous_l1_height` reflects a now-orphaned proof. Preconditions: a shallow Bitcoin reorg (still in scope since attacker can mine low-work regtest blocks) changes which L1 block is 'previous'. Call sequence: `build_from_l1_block` fetches `previous_lcp_output` keyed purely by `previous_l1_height` (a u64), not by the L1 block hash; if the reorg changes the block at that height, the fetched `previous_lcp_output.last_l2_height` may not correspond to the new chain's ancestor. Binding: `previous_lcp_output` fetched by `previous_l1_height` == the light client proof output for the L1 block that is the actual parent of `l1_block` in the (possibly reorged) chain, not merely same-height. Scoped impact: Critical - light client circuit could chain onto a `last_l2_height`/`lcp_state_root` from an orphaned branch, producing a `LightClientCircuitOutput` two honest full nodes (pre- and post-reorg) would compute differently for the same eventual canonical L1 block. Proof idea: cargo test in `crates/light-client-prover/src/tests` simulating a reorg at `previous_l1_height` and asserting `build_from_l1_block` errors or re-derives rather than reusing a stale `ledger_db` row keyed only by height.
