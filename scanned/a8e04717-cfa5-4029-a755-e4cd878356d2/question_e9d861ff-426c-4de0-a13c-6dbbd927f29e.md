[Target: pox.clar `check-caller-allowed` / `allowance-contract-callers` map, and its interaction with reward-set derivation in NakamotoSigners::pox_5_compute_and_update_signers] Attacker action: an unprivileged contract-caller registers itself via allow-contract-caller with an until-burn-ht exactly one block before a reward-cycle's prepare-phase-start block, then issues a stack-aggregation-commit through that caller in the final permitted block, racing the prepare-phase computation. Preconditions: until-burn-ht == prepare-phase-start height - 1. Call sequence: check-caller-allowed -> get_check_delegation/stack-aggregation-commit -> pox_5_stake_entries iterator consumed by pox_5_make_signer_set at prepare-phase-start. Equality that breaks: the set of stake entries observed by pox_5_make_signer_set on the node that processes the caller-allowance-expiry block first == the set observed by a node processing it in a different relative order within the same burn block (transaction ordering within a block should be deterministic, but the boundary condition of 'until-burn-ht' equality vs strict-inequality is the actual equality under test). Impact: Critical - a stake entry included on one node's reward-set computation and excluded on another's, from the identical block, is a divergent RewardSet, which is a direct consensus failure once signatures are checked against it. Proof idea: Rust integration test constructing the exact until-burn-ht boundary block and asserting get-check-delegation/check-caller-allowed's `<` vs `<=` semantics produce identical (not off-by-one) results on two independent re-executions of the same block.
