Target: BridgeWrapper::deposit wrapper call construction in system_events.rs versus the Solidity Bridge.deposit's onlySystemOrOperator modifier (per docs/system-contracts.md). Attacker action: call the Bridge contract's deposit(Transaction calldata moveTx, MerkleProof calldata proof, bytes32 shaScriptPubkeys) function directly as an ordinary EVM transaction (not via the citrea_sendRawDepositTransaction/system-tx path) using an EOA that has been set as `operator` is impossible for an unprivileged attacker, but this question targets whether the onlySystemOrOperator check can be bypassed by an attacker calling with caller==SYSTEM_SIGNER's address literal (0xdead...dead) directly as a regular signed transaction without going through signed_system_transaction — testing whether evm/call.rs's admission of ordinary transactions treats an attacker-forged 'from' equal to the literal SYSTEM_SIGNER bytes (requires attacker to actually sign with that private key, which they don't have) versus whether ANY other check besides ECDSA-recovered caller identity gates onlySystemOrOperator. Preconditions: attacker has no SYSTEM_SIGNER key and is not the registered operator. Call sequence: attacker sends signed tx from own EOA to BridgeWrapper::address() with deposit() calldata -> Solidity onlySystemOrOperator checks msg.sender against SYSTEM_CALLER and configured operator -> reverts for attacker's real address. Binding: BridgeWrapper.processedTxIds[txId]_after == BridgeWrapper.processedTxIds[txId]_before for any deposit() call where msg.sender is neither SYSTEM_CALLER nor the configured operator. Impact: Critical if bypassable, direct unauthorized cBTC minting. Proof idea: cargo test sending a direct EVM call to BridgeWrapper::address() with deposit() selector and arbitrary (even validly-formatted) moveTx/proof data from a freshly generated non-operator EOA, asserting revert and zero balance change to the deposit recipient and Bridge contract.
