In verify_signer_signatures (stackslib/src/chainstate/nakamoto/mod.rs), the public-key recovery via Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s intentionally allows high-S signatures ('always been allowed... okay for signer signatures' per test_high_s_single_signature). Can an attacker signer produce two syntactically distinct MessageSignature byte encodings (low-S and its negated high-S form) for the SAME (message, private key), and get a downstream duplicate-detection mechanism elsewhere in the codebase (e.g., a StackerDB anti-duplicate-message dedup keyed on raw signature bytes rather than recovered pubkey) to treat them as two independent approvals, feeding both into a miner's locally-tallied total_weight_approved (StackerDBListener) even though verify_signer_signatures itself would collapse them to one signer via signers_by_pk removal? Preconditions: attacker is a single signer able to submit both signature encodings for the same block sighash through StackerDB slots. Call sequence: StackerDBListener processes each chunk independently; block.gathered_signatures.contains_key(&slot_id) guards duplicate slot_id but not duplicate recovered-pubkey across two different slot_ids if the same signer is (mis)configured with two slots. Equality: number of DISTINCT recovered public keys contributing weight in the miner's local tally == number of distinct public keys verify_signer_signatures will ultimately count; a mismatch means the miner may believe it has reached weight_threshold and broadcast prematurely, though the canonical check in verify_signer_signatures will not be fooled. Impact: High (bounded to a temporary tip/broadcast-readiness disagreement rather than an accepted invalid block, since verify_signer_signatures still dedups by pubkey) - premature broadcast, delayed convergence. Proof idea: integration test simulating two StackerDB chunks with high-S and low-S variants of the same signer's signature under two slot_ids mapped to the same underlying signing_key, asserting the miner-side tally reaches threshold while verify_signer_signatures on the assembled header returns a lower true weight, then checking whether the block is still correctly rejected downstream.
