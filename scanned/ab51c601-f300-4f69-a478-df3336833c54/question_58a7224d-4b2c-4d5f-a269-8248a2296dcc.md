Target: `BlockHashCache::get_block_hash_caching`/`store_block_hash` (cache.rs) used by `write_consensus_bytes`'s `block_map.get_block_hash_caching(self.back_block())` during hashing. Attacker action: none required beyond ordinary block submission causing a backptr's local block id to be reused across a fork boundary (block-id numbering is monotonic per MARF file, but the cache's `block_hash_cache`/`block_id_cache` are never evicted per the doc comment "Contents are never evicted"). Preconditions: a long-running node processes many forks/rounds where block ids get assigned; a node restarts or reopens a connection mid-fork-switch. Call sequence: `TrieStorageConnection::get_block_hash_caching(id)` -> cache lookup keyed purely by numeric `id`, trusting the first-ever resolution `trie_sql::get_block_hash(&self.db, id)` forever. Equality broken: `hash used in write_consensus_bytes for backptr id == the actual on-disk block hash for that id at the time the block was mined`, which fails if `id` is ever reassigned or if a stale connection's cache disagrees with a freshly reopened connection's authoritative DB read — producing a different consensus hash for the same node between two connections (i.e., node A talking to itself pre/post-restart, or nodeA vs nodeB with cold vs warm caches) if any code path ever calls `store_block_hash` twice for a given id (the `assert!` guards against overwrite but not against having cached a transiently-wrong value before the row was committed). Impact: Critical — a state-root divergence between a freshly-synced node and one with a long-lived cache. Proof idea: integration test that opens a `TrieFileStorage`, warms the `BlockHashCache` for an ID before its corresponding SQL row is finalized/committed (simulate via manual cache poisoning), then commits, and asserts subsequent `write_consensus_bytes` output for a backptr referencing that id matches a fresh `reopen_readonly()` connection's output bit-for-bit.
