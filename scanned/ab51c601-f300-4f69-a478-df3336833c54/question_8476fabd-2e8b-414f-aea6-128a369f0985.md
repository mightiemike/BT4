Target: `TrieMerkleProof::verify_proof`'s root_to_block lookup step (proofs.rs ~1178-1190, ~1281-1293): `root_to_block.get(&trie_hash)` treats the map as authoritative for mapping an intermediate skiplist hash to a block header hash, which is then reinterpreted as 32 raw bytes and fed back into the *next* segment's hash chain as if it were a `TrieHash`. Attacker action: a light client relies on a `root_to_block` map supplied by a possibly-adversarial peer (e.g. over a state-proof relay protocol) rather than deriving it from its own trusted chain history; the peer supplies a `root_to_block` map with an extra/incorrect entry mapping some `trie_hash` to an attacker-chosen block hash `bhh`. Preconditions: verifier trusts an externally-supplied `root_to_block` map (explicitly flagged as an external dependency in the function's own doc comment: "the verifier needs to know which Trie roots correspond to which block headers... calculated and verified independently"). Call sequence: `verify_proof` substitutes `TrieHash(bhh.clone().to_bytes())` for `node_hash` and continues the chain, ultimately comparing to caller-supplied `root_hash`. Equality broken: `root_to_block used by the verifier == the true, chain-derived mapping`, and if the verifier fails to independently validate this map (as the doc comment warns is the caller's responsibility), a forged mapping lets an attacker splice a fabricated shunt chain that terminates at the legitimate `root_hash` while proving a value never committed. Impact: Critical for any consumer that doesn't independently validate `root_to_block` — but scoped here strictly to `verify_proof`'s contract, so the finding is that the function provides no internal defense against a malicious map. Proof idea: unit test constructing a deliberately wrong `root_to_block` entry and confirming `verify_proof` returns true for a proof/value pair that is not actually committed, documenting that callers MUST independently derive `root_to_block` and never accept it from an untrusted peer.
