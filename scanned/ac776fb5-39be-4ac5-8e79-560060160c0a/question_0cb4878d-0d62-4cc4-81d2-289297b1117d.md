Target: `NakamotoChainState::make_scheduled_miner_reward` (tenure.rs) missing `coinbase_tx` origin/authentication link to `MinerPaymentSchedule.address`. An attacker submits a coinbase transaction signed by key A (origin) but sets `recipient = Some(principal_B)` where B is unrelated, then separately forges a *second* block claiming to be 'produced by' B via a different nonce/auth path for the *same* tenure height using a sybil identity. Preconditions: epoch_id >= Epoch21; attacker controls both keys A and B (still counts as a single attacker, single BTC spend on the winning block-commit only tied to A). Call sequence: `miner_addr = miner_auth.get_address(mainnet)` is derived only from `coinbase_tx.get_origin()`; the `address` field (used for burn-share proportionality) is A but `recipient` (who gets paid) is B, and nothing ties B back to the winning sortition's block-commit committer. Equality: reward paid == coinbase+fees earned by the sortition winner's committed identity (the block-commit's committer), which should equal A; paying to B is fine only as an authorized redirection, but if B can independently also be scheduled as 'address' for a forged competing schedule row for the same tenure height, two schedule rows for one sortition slot could both mature. Impact: Critical if a second schedule row for the same tenure height can be inserted and matured. Proof idea: integration test attempting to insert two `MinerPaymentSchedule` rows for the same stacks_block_height/tenure from two different coinbase txs and confirm only one matures per `find_mature_miner_rewards`'s `latest_matured_miners_head` selection.
