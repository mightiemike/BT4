Target: `VRFSeed::is_from_proof` / `VRFSeed::from_proof` (stacks-common/src/types/chainstate.rs), used by both `validate_vrf_seed` and `StacksBlockHeader::validate_burnchain`. Attacker action: submit a block-commit whose `new_seed` is deliberately set to `VRFSeed::from_proof(some_other_valid_proof)` where `some_other_valid_proof` is a genuinely valid VRF proof, but one generated over a *different* message (not `sortition_hash.as_bytes()` of the intended tenure) — i.e. a proof 'recycled' from an unrelated VRF computation whose hash happens to match by construction (attacker picks the message). Preconditions: attacker controls their own VRF key and can freely compute proofs over any message before committing. Call sequence: `is_from_proof` only hashes the proof bytes, it does not bind the proof's message; `check_normal_coinbase_tx` separately verifies `VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes())` — the message-binding check. Equality: `VRFSeed::from_proof(proof) == new_seed` AND `VRF::verify(leader_vrf_key, proof, sortition_hash) == true` must jointly force `proof` to be over the correct `sortition_hash`; verify no code path checks only the first equality (e.g. during pre-append staging/relay) and defers the second, letting an attacker's block sit accepted in the staging DB before the VRF-message check runs. Impact: High (temporary staging-DB acceptance of unauthenticated seed) escalating to Critical if the staged block is used by downstream consensus-relevant logic (e.g. next tenure's parent VRF proof lookup) before `check_normal_coinbase_tx` runs. Proof idea: integration test inserting a block into `NakamotoStagingBlocks` with a seed-matching-but-message-mismatched proof and checking whether `get_parent_vrf_proof` for a child tenure can read this proof before full validation completes.
