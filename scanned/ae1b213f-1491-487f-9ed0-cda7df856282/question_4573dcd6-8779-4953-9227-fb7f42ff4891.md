c32_check_decode (stacks-common/src/address/c32.rs) computes `computed_sum` via double_sha256_checksum(check_data) and compares it byte-for-byte against `expected_sum` extracted from the tail of the decoded payload; the function returns Ok whenever these 4-byte arrays are bytewise equal. Because double_sha256_checksum only returns `tmp[0..4]` of SHA256(SHA256(x)), can an attacker enumerate c32 payload strings whose decoded (version, data) differs from the intended value but whose first 4 checksum bytes still collide (32-bit birthday space, ~2^16 work), and submit such a colliding address as a reward-set entry's pox-addr, so that node A's c32_address_decode accepts it as address X while an out-of-band recomputation (e.g. re-deriving the address from the raw hashbytes/version pox-addr tuple, bypassing the c32 string entirely, as done in PoxAddress::try_from_pox_tuple) yields address Y != X, breaking the equality: reward paid to c32_address_decode(x).1 == reward earned by PoxAddress-tuple-derived stacker identity? Scoped impact: High (bounded to a single stacker's own reward slot, not a majority attack, and requires a real 32-bit collision search which is currently out of feasible attacker budget but the invariant is unenforced code-side). Proof idea: Rust test using a precomputed 4-byte checksum collision pair, asserting c32_address_decode returns Ok for the colliding string, then asserting the byte-decoded value diverges from the tuple-derived PoxAddress for the same logical stacker.
