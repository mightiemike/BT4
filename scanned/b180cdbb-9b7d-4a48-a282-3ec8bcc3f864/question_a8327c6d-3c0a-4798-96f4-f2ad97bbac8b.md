In `BlockSnapshot::select_winning_block`, `Self::get_last_vrf_seed(sort_tx, block_header)` supplies `VRF_seed` used to mix into `sortition_hash`. If an attacker can influence which prior sortition's `new_seed` is treated as canonical by extending a short-lived fork right before the burn block in question (a reorg the attacker can trigger by withholding/broadcasting their own commit tx at a chosen time, i.e., without any majority Bitcoin hash-power, simply by timing broadcast), can two nodes that resolve the immediately-preceding burn-chain tip differently (temporarily, before reorg convergence) compute different `VRF_seed` inputs and thus different `sortition_hash.mix_VRF_seed(VRF_seed).to_uint256()` for the *same* nominal burn block, selecting different `winning_block_txid`s, breaking sortition-winner(nodeA) == sortition-winner(nodeB) during the reorg window? Impact: Critical, temporary chain split that can become permanent if blocks are built on the divergent winners before reconciliation. Proof: two-fork harness that delivers burn blocks to node A and node B in different tip order for one block, then reconverges; assert both nodes ultimately pick the *same* winner post-reorg, and flag if `handle_new_burnchain_block` on either node had already advanced Stacks chainstate on the wrong winner before reconciliation.
