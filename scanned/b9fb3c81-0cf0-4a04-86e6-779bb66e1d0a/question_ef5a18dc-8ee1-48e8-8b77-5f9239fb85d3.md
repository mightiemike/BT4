get_signers_weights (stackslib/src/chainstate/nakamoto/signer_set.rs) reads signer weight via `chainstate.eval_boot_code_read_only(sortdb, block_id, SIGNERS_NAME, "(get-signers uCYCLE)")` at a caller-supplied `block_id`, meaning the weights returned are whatever the .signers Clarity map holds *at that specific block_id's MARF state*, not necessarily the state at the block being validated. Can an unprivileged attacker exploit a caller passing a stale or attacker-influenced block_id (e.g. an ancestor before a .signers update transaction was processed) to get_signers_weights so that the weight map used to compute a threshold for block N reflects a *pre-update* signer set, letting a signer whose weight was later reduced (or a signer removed from the set) still count toward SIGNING at full old weight? Preconditions: a reward-cycle transition where .signers is updated mid-prepare-phase and a caller queries get_signers_weights against a block_id predating that update. Equality broken: SIGNING - weight must be drawn from exactly the reward set for that block's cycle, not a stale MARF snapshot. Impact: Critical - if all nodes share the caller's stale block_id bug, an invalid weight distribution is accepted network-wide (state root divergence when other logic assumes the updated set); if only some do, it is a chain split. Proof idea: integration test invoking get_signers_weights with a block_id before and after a known .signers update transaction and asserting the returned weight map differs, then verifying the caller in the actual validation path (verify_signer_signatures / signing coordinator) always uses the post-update block_id.
