Target: `Trie::walk_from` end-of-node-path vs `Trie::walk_from_nohash` used respectively by `MARF::walk` and `MARF::walk_cow` (trie.rs / marf.rs). Attacker action: exploit the fact that hash-carrying (`walk_from`) and hash-omitting (`walk_from_nohash`) traversal share cursor-mutation logic but diverge on whether an intermediate node's hash is fetched — engineer a corrupted-but-plausible on-disk node whose declared hash byte differs from its true content hash (bit rot / partial write during a prior crash) so that `walk_from` silently accepts a wrong hash while `walk_from_nohash` (used during writes) proceeds down the same path without ever checking it, then hashing fresh — leaving mined and read-path nodes with divergent cached vs. computed hash values feeding `read_root_hash`. Preconditions: a node has experienced a non-atomic crash mid trie-write leaving one node's on-disk hash byte stale (not attacker-controlled directly, but the read paths' asymmetric hash validation is the bug being probed). Call sequence: recovery -> next block applies `walk_cow`/`walk_from_nohash` (no verification) -> commits new root computed from the corrupted node's *fresh* hash, versus a peer whose disk was never corrupted computing from the *original* hash. Equality broken: state root committed == root every node recomputes. Impact: Critical — since neither code path cross-checks a stored node hash against a freshly computed one during normal operation, storage corruption on one node is silently baked into a divergent, still-valid-looking root. Proof idea: integration test that manually flips a node-hash byte on disk for one of two identical chainstates, replays an identical subsequent block on both, and confirms the corrupted node produces a different final root without any validation error being raised.
