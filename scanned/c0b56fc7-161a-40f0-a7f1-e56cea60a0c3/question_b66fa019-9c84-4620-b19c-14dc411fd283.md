Target: `NakamotoChainState::make_scheduled_miner_reward` (stackslib/src/chainstate/nakamoto/tenure.rs). Attacker action: an unprivileged miner wins a single Nakamoto sortition and submits a coinbase tx whose `TransactionPayload::Coinbase(..., recipient_opt, ...)` sets `recipient_opt` to an address the attacker controls that differs from `coinbase_tx.get_origin()`'s address. Preconditions: epoch_id >= Epoch21, attacker holds the winning VRF/leader key for one tenure only. Call sequence: block passes `check_normal_coinbase_tx`, `make_scheduled_miner_reward` computes `recipient = recipient_opt.cloned().unwrap_or(miner_addr...)`, schedule is inserted via `insert_miner_payment_schedule`, later matured via `find_mature_miner_rewards`/`calculate_miner_reward`. Equality that must hold: paid recipient in `MinerPaymentSchedule.recipient` == the coinbase-tx-designated recipient of the sortition winner's own signed transaction, not an unauthenticated origin substitution. Impact: Critical if the recipient can be forged to a value not authorized by the winning miner's signature, causing reward theft. Proof idea: integration test booting one Nakamoto tenure with a coinbase tx whose auth signer differs from the sortition-winning leader key, and assert `check_normal_coinbase_tx` combined with tenure-linkage checks reject or correctly bind recipient.
