Target: BitcoinVerifier::verify_transactions HeaderInclusionTxCountMismatch guard `block_header.tx_count as usize != inclusion_proof.wtxids.len()`. Attacker action: none needed beyond mining an ordinary block; the risk is a discrepancy between how block_header.tx_count is populated by the full node's block-fetch code and how many wtxids the same node places into inclusion_proof.wtxids when constructing InclusionMultiProof, for a block containing a maximal number of coinbase-only transactions or unusual reorg-truncated tx lists. Preconditions: regtest, block near reorg boundary or with a non-standard tx count (e.g. exactly 1, or very large tx count near integer boundaries). Call sequence: HeaderWrapper::tx_count is set at header-construction time from the raw block; InclusionMultiProof.wtxids is built in BitcoinService::extract_relevant_blobs_with_proof by iterating block.txdata directly. Binding: block_header.tx_count (as stored/propagated by the full node) == inclusion_proof.wtxids.len() (as derived independently from the same block's raw txdata) for every block, with no path where a reorg or resync updates one without the other. Scoped impact: Critical DA INTEGRITY — a false HeaderInclusionTxCountMismatch causing a light client prover to halt (permanently unprovable transition) even though the full node processed the block successfully. Proof idea: cargo test simulating a reorg (see bin/citrea/tests/bitcoin/rollback.rs patterns) then re-deriving both tx_count and wtxids.len() for the post-reorg canonical block, asserting equality survives the resync.
