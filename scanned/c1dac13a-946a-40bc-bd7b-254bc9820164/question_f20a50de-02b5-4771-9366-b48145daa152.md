Target: `BitcoinVerifier::verify_transactions`, coinbase witness-commitment lookup via `coinbase_tx.output.iter().rposition(...)` guarded by `MINIMUM_WITNESS_COMMITMENT_SIZE` and `WITNESS_COMMITMENT_PREFIX`. Attacker action: mine a coinbase transaction with two outputs matching `WITNESS_COMMITMENT_PREFIX`: an earlier valid 38+-byte commitment and a later truncated (`prefix`-only, size < `MINIMUM_WITNESS_COMMITMENT_SIZE`) output. Preconditions: regtest network, attacker controls block template (self-mined regtest block; applies equally on any Bitcoin fork Citrea DA tracks). Call sequence: `rposition` scans from the end and would pick the truncated commitment first, but the length check `>= MINIMUM_WITNESS_COMMITMENT_SIZE` causes it to skip to the earlier valid one, so `commitment_idx` differs between what BIP-141-compliant Bitcoin Core node software treats as the canonical commitment (Core only considers commitments meeting its own iteration semantics) and what `verify_transactions` selects. Binding: commitment_idx_native_bitcoind(B) == commitment_idx_circuit(B). Impact: Critical, DA_INTEGRITY - a coinbase whose commitment structure is accepted by the circuit but interpreted differently by real Bitcoin Core consensus rules, letting relevant blobs be included or excluded inconsistently with what an honest full node relying on Core's view would expect. Proof idea: cargo test replicating `test_malicious_multiple_witness_commitments` but placing the truncated (invalid-size) commitment after the valid one and asserting `commitment_idx` selected still equals the last output index per BIP-141 semantics, not merely the last matching-prefix output.
