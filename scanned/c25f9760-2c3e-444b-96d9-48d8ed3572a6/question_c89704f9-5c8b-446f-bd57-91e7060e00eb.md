[Target: account_credit called from matured reward payout path, MinerReward.recipient vs MinerReward.address] Attacker as sortition winner sets a coinbase recipient (PrincipalData::Contract or a different StacksAddress) distinct from their own mining address, then during a later reorg the OLD stored MinerPaymentSchedule row (with the old recipient) coexists with a newly inserted row for a competing fork bearing a different recipient for the same miner address. Preconditions: attacker resubmits a modified block for the same tenure slot with a changed coinbase recipient field before/after a fork choice reorg (two block-commits/timings referencing the same sortition winner). Call sequence: insert_miner_payment_schedule (per index_block_hash, so two distinct rows can coexist for two forked blocks with the same address but different recipient) -> only the canonical fork's row is matured via get_scheduled_block_rewards_at_block -> account_credit(recipient, amount). Equality: exactly one MinerPaymentSchedule row (the canonical fork's) is ever matured and its recipient is the one credited; the orphaned fork's row, even though persisted in the payments table, must never independently trigger account_credit. Scoped impact: Critical if a stale/orphaned schedule row can still be matured (e.g., via get_scheduled_block_rewards_in_fork_at_height using stale tip ancestor lookups after a reorg) and credit a second, now-unauthorized recipient. Proof idea: two-fork integration test where a miner submits two competing blocks at the same height with different coinbase recipients, force a reorg to pick one, and assert account balances show exactly one recipient credited, never both.
