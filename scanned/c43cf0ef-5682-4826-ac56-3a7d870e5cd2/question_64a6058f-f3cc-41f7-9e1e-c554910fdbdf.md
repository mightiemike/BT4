Target `make_scheduled_miner_reward` (stackslib/src/chainstate/nakamoto/tenure.rs): the `recipient` field is set to `coinbase_tx.try_as_coinbase()`'s `recipient_opt` when present, defaulting to `miner_addr` only when absent. Attacker action: craft a `TransactionPayload::Coinbase` (or `NakamotoCoinbase`) whose `recipient_opt` names a third-party principal that never authorized this tenure's mining, while the tx is still signed by the winning miner's own key. Preconditions: attacker won the sortition and mines the block themselves; sortition winner's committed reward recipient (per protocol) should be the winner's own address unless a legitimate alt-recipient was configured beforehand. Call sequence: `check_normal_coinbase_tx` (VRF only) -> `calculate_scheduled_tenure_reward` -> `make_scheduled_miner_reward` -> `insert_miner_payment_schedule`. Equality that breaks: reward recipient credited == sortition winner's authenticated recipient. Impact: Critical, since no check ties `recipient_opt` to any commitment made at block-commit time, a miner can arbitrarily redirect their own coinbase, but more critically nothing verifies `recipient_opt` isn't controlled to grief the miner's own payout is not the vulnerability window -- the real gap is that any block with a valid VRF/tenure but an unchecked recipient field pays whoever is named with no cross-reference to the block-commit. Proof idea: integration test with a nakamoto block whose coinbase recipient is an arbitrary standard principal never seen in the block-commit; assert the scheduled `MinerPaymentSchedule.recipient` differs from the block-commit's declared reward address and that block acceptance still succeeds.
