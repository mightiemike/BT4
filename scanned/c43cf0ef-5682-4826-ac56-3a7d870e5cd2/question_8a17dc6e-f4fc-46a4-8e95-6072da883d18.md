In `check_normal_coinbase_tx` (stackslib/src/chainstate/nakamoto/mod.rs, called from the internals hook path for coinbase validation), an attacker who wins a sortition submits a Nakamoto block whose coinbase's `vrf_proof_opt` was generated with a VRF keypair different from the winning leader key, but reuses a `sortition_hash` from a stale/ancestor snapshot that happens to validate under `VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes())`. Preconditions: attacker holds a single winning block-commit for tenure T; two nodes have processed different burn forks up to T so their `sortition_hash` differs. Call sequence: block ingestion -> `NakamotoBlockHeader::check_normal_coinbase_tx` -> VRF::verify -> `make_scheduled_miner_reward` schedules coinbase to the block's miner. Equality that must break: `leader_vrf_key`/`sortition_hash` pair validated on node A == pair validated on node B (DETERMINISM), which if it diverges lets one node accept a coinbase tx that pays a reward the other rejects. Impact: Critical, chain split on reward-bearing blocks. Proof idea: two-node harness feeding node A and node B distinct burn forks up to the same consensus_hash tenure and asserting `check_normal_coinbase_tx` returns different Ok/Err.
