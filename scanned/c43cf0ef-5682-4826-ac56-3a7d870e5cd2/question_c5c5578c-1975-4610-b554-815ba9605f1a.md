Target `check_normal_coinbase_tx`'s VRF check versus `make_scheduled_miner_reward`'s recipient/address derivation: the VRF check authenticates that `coinbase_tx`'s embedded `vrf_proof` was produced by `leader_vrf_key` (the sortition winner's registered VRF key), but `make_scheduled_miner_reward` derives `miner_addr` from `coinbase_tx.get_origin()` -- the transaction's *spending authorization* key -- which is never cross-checked against the sortition winner's `pubkey_hash` from the tenure-change (`tc_payload.pubkey_hash`, checked only in `check_tenure_tx`, a separate function). Attacker action: as the legitimate sortition winner, sign the block header/tenure-change with the correct leader key (passing `check_tenure_tx`) and correct VRF proof (passing `check_normal_coinbase_tx`), but author the *coinbase transaction itself* with a different origin keypair the attacker also controls, so `miner_addr` (the fallback recipient) is an address never registered at block-commit time. Preconditions: attacker is the sole sortition winner for tenure T (minority resource, own BTC). Call sequence: block validation checks tenure-tx and coinbase VRF independently; neither ties `coinbase_tx.get_origin()`'s hash160 to `tc_payload.pubkey_hash`; `calculate_scheduled_tenure_reward` -> `make_scheduled_miner_reward` uses the unverified origin address as fallback recipient. Equality that breaks: reward recipient (fallback path) == the address whose key was proven via VRF/tenure-change to have won the sortition; since no code ties them together, an attacker (or, more importantly, anyone who can forge/replay a differently-signed coinbase inside an otherwise-valid block body) can redirect the payout without re-winning the sortition. Impact: Critical, this is the exact mechanism the coinbase-recipient design should prevent, but the absence of a cross-check between `check_tenure_tx`'s `pubkey_hash` and `coinbase_tx.get_origin()` widens the attack surface to any code path that can splice a differently-authored coinbase tx into a validly tenure-signed block. Proof idea: integration test building a Nakamoto block that passes `check_tenure_tx` and `check_normal_coinbase_tx` but whose coinbase tx origin key differs from `tc_payload.pubkey_hash`'s corresponding key, and asserting whether `NakamotoBlockHeader` validation as a whole rejects it (it should, if some caller enforces this elsewhere) or whether `make_scheduled_miner_reward` silently schedules payment to the mismatched origin address.
