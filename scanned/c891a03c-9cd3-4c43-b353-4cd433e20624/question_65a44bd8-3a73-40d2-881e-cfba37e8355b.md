Target: `NakamotoChainState::make_scheduled_miner_reward` (tenure.rs L283-333). The `recipient` field is read from `coinbase_tx.try_as_coinbase()` unconditionally in epoch >= 2.1, with no check that this `PrincipalData` was authorized by the sortition-winning miner beyond the coinbase tx's own origin signature. Attacker action: an unprivileged miner who wins a single sortition submits a Nakamoto block whose coinbase tx sets `recipient` to an arbitrary contract or address unrelated to the miner's leader-key identity. Preconditions: attacker controls one winning block-commit/leader-key pair, tip is post-Epoch21. Call sequence: block passes `check_normal_coinbase_tx` (only verifies VRF proof, not recipient) -> `calculate_scheduled_tenure_reward` -> `make_scheduled_miner_reward` -> `insert_miner_payment_schedule`. Equality tested: recipient credited by `find_mature_miner_rewards`/`process_matured_miner_rewards` == the sortition winner's own address (per the target Identity clause), not an arbitrary third party. Impact: Critical if this diverts the coinbase away from the winning miner's declared identity in a way two honest nodes disagree on; otherwise this is intended behavior - test whether any validation path treats a pay-to-contract coinbase as invalid on one node and valid on another. Proof: Rust integration test with two peers processing the same block, asserting identical parsed recipient and identical `get_matured_miner_payment` result.
