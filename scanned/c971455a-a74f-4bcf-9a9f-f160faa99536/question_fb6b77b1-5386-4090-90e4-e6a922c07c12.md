`DataOnDa::Chunk(chunk)` bypasses `blob.sender()` validation entirely in `run_l1_block` (crates/light-client-prover/src/circuit/mod.rs, comment: "No need to check sender for chunk"). Can an unprivileged attacker inscribe a `DataOnDa::Chunk` reveal transaction whose `wtxid` is engineered (by grinding nonces/witness data in their own reveal transaction, which they fully control since they sign it) to exactly equal the wtxid the honest batch prover's actual chunk transaction will later have, so that when the honest transaction is later broadcast and mined, the attacker's earlier `ChunkAccessor::insert(blob.wtxid(), chunk, ...)` has already written poisoned bytes at that same JMT key, and (depending on Bitcoin's rule that duplicate wtxids across the chain are extremely unlikely to both confirm, but the honest tx would simply fail to confirm as a duplicate, OR if only the attacker's version confirms because they won the wtxid race) any later `DataOnDa::Aggregate` referencing that wtxid resolves attacker bytes as if they were the batch prover's? Preconditions: attacker has enough lead time/fee-bidding power (in scope, since fee payment by attacker is allowed) to grind and broadcast first. Call sequence: attacker grinds wtxid collision (computationally infeasible for true SHA256 collision, but if the batch prover's chunk-splitting scheme has any low-entropy predictable component, e.g., deterministic per-chunk transaction structure with attacker-known content, the attacker could construct a transaction with byte-identical or near-identical witness leading to a genuinely equal wtxid) -> attacker's tx confirms first at the shared wtxid -> honest batch prover's tx (same wtxid, mempool policy dependent) either double-spends/conflicts or is rejected as duplicate -> `run_l1_block` inserts attacker's chunk under that wtxid -> aggregate resolution returns attacker bytes. Binding: the chunk bytes `ChunkAccessor::get(wtxid)` returns == the chunk bytes the entity holding `batch_prover_da_public_key` actually broadcast under that same wtxid. Impact: Critical — proof body substitution without any sender check at all on the chunk primitive, the root cause of the entire threat class described in this file's scope. Proof idea: cargo test directly calling `ChunkAccessor::insert` with attacker-chosen bytes at a wtxid, then separately simulating the batch prover's real chunk arriving at the same wtxid key (last-write-wins collision), and asserting whichever chunk is present when `DataOnDa::Aggregate` resolution runs is unconditionally trusted with no sender provenance recorded.
