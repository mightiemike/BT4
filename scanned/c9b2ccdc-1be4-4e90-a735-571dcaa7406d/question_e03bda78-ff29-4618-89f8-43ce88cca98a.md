`process_complete_proof` computes `batch_proof_method_id` via `binary_search_by_key(&batch_proof_output_last_l2_height, |(height, _)| *height)`, using `Err(idx) => idx.saturating_sub(1)` on a miss, i.e. picks the highest activation height <= the proof's last L2 height. Attacker action: as an unprivileged party you cannot insert method ids, but you CAN craft/replay a `DataOnDa::Complete` proof (assuming a genuinely batch-prover-signed complete proof is publicly visible on DA, e.g. leaked/observed by anyone since DA is public) whose bytes are re-inscribed by you under your own transaction (sender check is on the wrapping DA transaction's signer, not on proof content) at a LATER L1 block where the `BatchProofMethodIdAccessor` vector has since gained a new entry, shifting which `batch_proof_method_id` the binary search selects for the SAME `batch_proof_output_last_l2_height`. Preconditions: `blob.sender().as_ref() != batch_prover_da_public_key` check — re-inscribing someone else's proof bytes under your own key fails this check immediately, `continue`. Binding: a `DataOnDa::Complete` blob is processed by `process_complete_proof` only if `blob.sender()` (the DA transaction signer) == `batch_prover_da_public_key`, for every honest prover reading the same block. Impact: Critical — AUTHORITY; confirms an attacker cannot replay another party's proof body under their own signing key to hijack method-id selection.
