Target: `NakamotoBlock::check_shadow_coinbase_tx` in shadow.rs, which requires a shadow coinbase's recipient to be the burn address but explicitly states 'can't check the VRF proof because the creator of the shadow block ... isn't a miner, so it could be anything.' Attacker action: an attacker who can only submit normal (non-shadow) blocks cannot set the shadow version bit themselves (consensus-restricted), but can attempt to submit a normal-looking block whose VRF proof is copy-pasted from a known shadow block's arbitrary/garbage VRF bytes, hoping `check_normal_coinbase_tx` (used for normal blocks, which does verify VRF against `vrf_public_key`) is bypassed if a node mistakenly routes it through `check_shadow_coinbase_tx` due to the version-bit check being evaluated on a mutable/attacker-influenced field before signature verification. Preconditions: `NakamotoBlockHeader::is_shadow_block()` is checked before `check_miner_signature`, i.e., version byte alone decides the validation path in `accept_block`. Call sequence: `accept_block` -> `if block.is_shadow_block() { validate_shadow_nakamoto_block_burnchain } else { validate_normal_nakamoto_block_burnchain }`. Equality: VRF-proof-verified coinbase winner (per `vrf_public_key` of the sortition's leader key) == the coinbase recipient/VRF actually recorded in the accepted block for every non-shadow tenure. Impact: Critical — a block accepted via the shadow path (which skips VRF/signature checks) despite representing a normal miner-claimed tenure, letting an attacker skip `check_miner_signature`/`check_normal_coinbase_tx`. Proof idea: integration test setting the header version high bit on an otherwise-normal attacker block with an invalid VRF proof and confirming `accept_block` routes it to `validate_shadow_nakamoto_block_burnchain`, which never calls `check_miner_signature`, then assert whether `store_block_if_better` is (wrongly) reachable — if the node treats it as an accepted block, DETERMINISM/SIGNING fails.
