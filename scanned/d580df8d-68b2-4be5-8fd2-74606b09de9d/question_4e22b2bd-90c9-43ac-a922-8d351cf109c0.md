`DepositDataMempool::remove_deposits` recomputes `calc_tx_id` for every entry in `accepted_deposit_txs` and only removes entries whose id is in the removal set derived from `deposits_to_remove`. Since `calc_tx_id` commits to only `moveTx.{version,vin,vout,locktime}`, can an attacker submit blob B_evil with the SAME four fields as a legitimate, already-included deposit's moveTx but different scriptPubKey/proof bytes, timed so B_evil sits in `accepted_deposit_txs` when `runner` later calls `remove_deposits(&fetched)` for an unrelated batch that happens to include the legitimate deposit's id, causing B_evil to be silently evicted from the mempool without ever having been executed by `runner`? Binding: an entry removed from `pending_deposits`/`accepted_deposit_txs` == a blob that was actually executed by `runner` in that L2 block, counted once. Impact: Critical - a deposit whose funds were never credited is erroneously dropped, potentially permanently losing the ability to re-submit if the attacker's own subsequent identical resubmission is now accepted as 'new' but the original depositor's Bitcoin funds go uncredited. Proof idea: cargo test crafting an id-colliding pair, feeding one through the runner's inclusion path and asserting the other is spuriously removed via `remove_deposits`.
