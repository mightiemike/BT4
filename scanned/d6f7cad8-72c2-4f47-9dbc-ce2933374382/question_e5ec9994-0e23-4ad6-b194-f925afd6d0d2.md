Target: `check_normal_coinbase_tx` and `check_shadow_coinbase_tx` divergence (stackslib/src/chainstate/nakamoto/mod.rs:1808-1856 and stackslib/src/chainstate/nakamoto/shadow.rs:119-161). Attacker action: attacker crafts a block with `header.version` bit 0x80 unset (looks normal) but whose coinbase recipient is the burn address exactly as a shadow block would require, attempting to make a normal block masquerade as underpaying nothing while still going through `validate_normal_against_burnchain`'s `check_normal_coinbase_tx`, which does NOT check the recipient at all (only the VRF proof). Preconditions: attacker wins a sortition normally. Call sequence: `is_shadow_block()` returns false (version bit unset) -> `check_normal_coinbase_tx` only validates VRF, not recipient -> `make_scheduled_miner_reward` pays whatever `recipient` the attacker set, including the burn address itself if attacker wants (self-burning is allowed and harmless), but also confirm the *reverse* is impossible: a shadow-flagged block (version bit set) cannot bypass `check_shadow_coinbase_tx`'s mandatory burn-address check to redirect real STX to an attacker address. Equality broken: for shadow blocks, recipient == burn address always; verify this holds under `validate_shadow_against_burnchain` for every code path that could set the shadow bit post-validation (e.g., mutation between check and storage). Impact: Critical, reward theft if a block's shadow bit can be flipped or ignored between `check_shadow_coinbase_tx` validation and the point where `make_scheduled_miner_reward`/payment scheduling reads `header.version` again. Proof idea: Integration test that validates a shadow block, then mutates `header.version` before calling the payment-scheduling path, asserting the mismatch is caught, not silently paid.
