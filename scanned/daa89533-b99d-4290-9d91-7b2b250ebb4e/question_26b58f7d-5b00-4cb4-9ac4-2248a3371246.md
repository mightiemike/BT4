Target `NakamotoChainState::make_scheduled_miner_reward` (tenure.rs): the `recipient` field is taken directly from `coinbase_tx.try_as_coinbase()`'s `recipient_opt` with no check that the coinbase transaction's origin is the sortition winner recorded in the block-commit. Can an attacker submit a valid Nakamoto block whose coinbase tx sets an arbitrary `recipient_opt` principal unrelated to the winning miner's block-commit `apparent_sender`, so `insert_miner_payment_schedule` schedules the reward to attacker-chosen principal X while `address` still shows the miner? Precondition: attacker wins a sortition (their own BTC, minority stake) then crafts the coinbase tx recipient field freely (recipient field is only checked against tx signature auth, not against block-commit-declared miner). Equality: reward recipient == sortition winner's *declared* recipient per the block-commit/consensus rules (TENURE_REWARD). Impact: Critical if this lets a miner redirect funds to bypass some restriction (e.g. PoX lockup) - name as reward paid to wrong recipient. Proof idea: integration test mining a Nakamoto tenure with coinbase recipient != miner address, confirming through maturity, and asserting `get_matured_miner_payment().recipient` equals the expected (block-commit) principal, not an arbitrary one.
