Target: `NakamotoChainState::get_ongoing_tenure` (tenure.rs:524-532) vs `check_tenure_continuity` (tenure.rs:887-923). Attacker action: submit a non-tenure-change block (no `TenureChangeCause`) whose `header.consensus_hash` matches the parent's consensus hash but whose `parent_block_id` points to a block that is NOT the tip of `get_ongoing_tenure` for that consensus hash (i.e., a sibling block within the same nominal tenure, created by equivocating on which block is 'the' tenure's chain). Preconditions: attacker's single miner slot produced two competing blocks inside its own tenure (miner equivocation) and gets a third node to build on the non-canonical one. Call sequence: `append_block` -> no tenure_tx -> `check_tenure_continuity(parent_ch, header)` -> `get_ongoing_tenure(parent_block_id)` -> compare `highest_tenure.tenure_id_consensus_hash != parent_ch`. Equality: for every non-tenure-change block, `get_ongoing_tenure(parent_block_id).tenure_id_consensus_hash == header.consensus_hash == parent_ch`. Impact: Critical — if this check is skipped on any ingestion path (e.g. block relay fast-path), a node could extend the non-canonical sibling, producing two accepted chains from one tenure that both mature separate coinbases at the same coinbase height. Proof idea: integration test where a miner equivocates within one tenure, feed both sibling blocks to two nodes, assert only the canonical one is accepted on both (STATE_ROOT/TENURE_REWARD).
