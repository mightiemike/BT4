Because `DataOnDa::Chunk` has no size-checked-at-insertion-time cap tied per-chunk (the `MAX_COMPRESSED_BLOB_SIZE` bound in `run_l1_block`'s aggregate arm is only checked cumulatively as `chunk.len() + complete_proof.len() > MAX_COMPRESSED_BLOB_SIZE`), can an unprivileged attacker insert a single oversized or specially-crafted `DataOnDa::Chunk` at a wtxid the batch prover is known to reuse across multiple pending aggregates (e.g., a shared prefix chunk reused in retried aggregate submissions after an initial `process_complete_proof` failure), such that the cumulative-size early-exit (`continue 'blob_loop`) is triggered deterministically for the honest aggregate on every attempt, permanently starving that aggregate's assembly for that wtxid and thus permanently preventing `process_complete_proof` from ever being called for the batch prover's intended complete proof at that sequencer-commitment range? Preconditions: batch prover reuses wtxids across retried aggregate attempts (or attacker predicts a future wtxid before broadcast, which is infeasible for wtxid grinding on the batch prover's own signed tx, so this specifically targets scenarios where the same chunk wtxid is deliberately reused by tooling). Call sequence: attacker chunk insert overwrites/occupies the wtxid slot with oversized content -> honest `DataOnDa::Aggregate` loop hits `chunk.len() + complete_proof.len() > MAX_COMPRESSED_BLOB_SIZE` -> `continue 'blob_loop` skips the entire aggregate, discarding all already-accumulated legitimate chunks read in that same pass -> `process_complete_proof` never runs -> `last_sequencer_commitment_index`/`last_l2_height` never advance for that range. Binding: whether `process_complete_proof` is invoked for a given complete proof == whether the batch prover's actual (non-attacker) chunk bytes for every referenced wtxid are what get concatenated. Impact: Critical — a true state transition made permanently unprovable if the wtxid is never reused with different content (griefing the specific proof range indefinitely until the batch prover picks new wtxids, which itself is not guaranteed by any protocol invariant).
