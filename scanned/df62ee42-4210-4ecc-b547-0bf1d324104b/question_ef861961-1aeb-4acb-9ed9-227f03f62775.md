In `LightClientProofCircuit::run_l1_block`, the `DataOnDa::Chunk(chunk)` arm calls `ChunkAccessor::<S>::insert(blob.wtxid(), chunk, &mut working_set)` with no `blob.sender()` check (unlike `DataOnDa::Complete`/`DataOnDa::Aggregate`/`DataOnDa::SequencerCommitment`). Can an unprivileged attacker inscribe a Bitcoin reveal transaction whose data is `borsh::to_vec(&DataOnDa::Chunk(attacker_bytes))` and whose wtxid is chosen (via grinding the witness/tx structure while keeping the reveal prefix) to collide with a wtxid the honest batch prover intends to reference in a later `DataOnDa::Aggregate(_, wtxids)`, so that `ChunkAccessor::get(*wtxid, &mut working_set)` in the aggregate-processing loop resolves to `attacker_bytes` instead of the batch prover's chunk? Preconditions: mainnet/testnet Bitcoin regtest DA, light client prover has scanned the L1 block containing both the attacker's chunk inscription and the batch prover's later aggregate inscription, JMT has no prior entry for that wtxid. Call sequence: attacker's chunk tx mined before batch prover's chunk tx for the same wtxid -> `run_l1_block` chunk loop inserts attacker bytes keyed by wtxid -> batch prover's own chunk tx (different content, if wtxid differs) is ignored since key exists already is not checked (insert overwrites) -> aggregate arm concatenates chunks assuming they are the prover's -> `DS::decompress_chunks` -> `process_complete_proof`. Binding: `complete_proof` bytes reconstructed by `process_complete_proof` == the byte string the batch prover actually signed and chunked. Impact: Critical — a light client proof accepts a state transition or batch proof output the batch prover never produced, causing `LightClientCircuitOutput::l2_state_root`/`last_l2_height` to diverge from truth, consumed later by Clementine's bridge proof.
