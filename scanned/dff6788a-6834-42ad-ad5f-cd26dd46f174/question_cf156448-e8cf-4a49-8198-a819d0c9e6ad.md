Target: NakamotoChainState::calculate_scheduled_tenure_reward (tenure.rs), specifically the accumulated_rewards read from SortitionDB::get_block_snapshot_consensus(...).accumulated_coinbase_ustx. Attacker action: attacker deliberately misses/skips sortitions (does not submit a block-commit) across N burn blocks to inflate accumulated_coinbase_ustx, then wins the following sortition with a minimal-burn commit and claims the full accumulated coinbase. Preconditions: attacker controls a single mining slot with minority BTC, sortition winner chosen normally, no signer collusion needed. Call sequence: calculate_scheduled_tenure_reward reads accumulated_rewards from the snapshot -> total_coinbase = coinbase_at_block.saturating_add(accumulated_rewards) -> make_scheduled_miner_reward sets coinbase: total_coinbase. Equality that must hold: coinbase credited for the winning tenure == StacksEpochId::coinbase_reward(...) for that burn height PLUS the accumulated_coinbase_ustx strictly attributable to sortitions with zero winners since the last paid coinbase (per consensus-defined accumulation rule), not an attacker-inflatable multiple. Scoped impact: High (bounded to the deterministic coinbase-accumulation formula which is itself consensus-critical, not exploitable beyond spec) unless the accumulation formula double-counts across a fork -- if two different forks both read the same snapshot's accumulated_coinbase_ustx and both mature it, impact escalates to Critical double-payment. Proof idea: integration test with several deliberately-missed sortitions followed by a win, asserting matured coinbase equals the documented sum, and that a second competing fork sharing the same accumulated snapshot cannot also credit that accumulation once one fork matures it.
