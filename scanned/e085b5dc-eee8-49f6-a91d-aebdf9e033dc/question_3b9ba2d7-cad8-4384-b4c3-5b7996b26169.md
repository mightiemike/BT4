`StacksChainState::process_matured_miner_rewards` computes `let mut coinbase_reward = miner_share.coinbase; ... for reward in users_share.iter() { coinbase_reward += reward.coinbase; ...}` and returns this sum to be passed to `clarity_tx.increment_ustx_liquid_supply(matured_ustx)`. Since `calculate_miner_reward`'s `users` branch (`else { (0, 0, 0) }` for tx fees) can still, in principle, be handed a non-zero `coinbase_reward` for a `participant` schedule row that is not the actual `miner` row (if a `MinerPaymentSchedule.miner` flag were ever `false` yet `vtxindex==0` due to a data-path bug reachable via a crafted PoisonMicroblock or Stacks-on-Bitcoin user-burn-support op an attacker submits), can `coinbase_reward` end up double-counting the tenure's coinbase across `miner_share` and a user row, so `increment_ustx_liquid_supply` mints more STX than the single coinbase issued for that tenure? Equality: `coinbase_reward` passed to `increment_ustx_liquid_supply` must equal exactly the tenure's single `coinbase_at_block`/`total_coinbase` value, counted once. Impact: Critical, STX over-mint (liquid-supply inflation) exceeding coinbase+fees. Proof idea: craft a `MinerPaymentSchedule` set (via lowest-level DB insert helpers in a test) where a non-miner row also carries nonzero `coinbase`, run `find_mature_miner_rewards` -> `process_matured_miner_rewards`, and assert the returned `coinbase_reward` against the single canonical `total_coinbase` for that tenure.
