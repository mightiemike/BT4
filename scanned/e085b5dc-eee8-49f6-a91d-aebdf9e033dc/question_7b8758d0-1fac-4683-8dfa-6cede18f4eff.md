`NakamotoBlock::check_shadow_coinbase_tx` requires shadow-block coinbases to pay the burn address (`StacksAddress::burn_address(mainnet).to_account_principal()`), while `check_normal_coinbase_tx` imposes no recipient restriction at all for ordinary Nakamoto blocks. Can an attacker exploit `NakamotoBlockHeader::is_shadow_block()` misclassification — e.g., a header that satisfies whatever bit-pattern `is_shadow_block()` checks for shadow-block status but is routed through `validate_normal_against_burnchain` instead of `validate_shadow_against_burnchain` (or vice versa) due to a caller-side branch mismatch — to get a shadow-style block's coinbase credited to a non-burn recipient, i.e., to mint a real (non-burned) miner reward for a block that should have paid to the burn address only? Equality: every block for which `is_shadow_block()==true` must have its reward recipient forced to the burn address; every block for which it is false is a normal reward-bearing coinbase — the classification used at validation time must equal the classification used at reward-scheduling time. Impact: Critical, unclaimed/burned reward instead becomes claimed reward (or the reverse: a real block reward gets shadow-classified and its STX permanently burned/frozen). Proof idea: integration test constructing a NakamotoBlock at the shadow/normal classification boundary and tracing which of `check_normal_coinbase_tx` vs `check_shadow_coinbase_tx` actually executes versus which is used later in `make_scheduled_miner_reward`'s call path, asserting classification consistency end-to-end through `append_block`.
