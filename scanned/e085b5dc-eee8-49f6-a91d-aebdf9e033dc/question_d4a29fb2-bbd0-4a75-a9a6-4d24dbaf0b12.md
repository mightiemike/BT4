`NakamotoChainState::calculate_scheduled_tenure_reward` reads `accumulated_rewards` from `SortitionDB::get_block_snapshot_consensus(...).accumulated_coinbase_ustx` for the *current* block's consensus hash and adds it via `coinbase_at_block.saturating_add(accumulated_rewards)` into `total_coinbase`. Since `accumulated_coinbase_ustx` accrues from missed sortitions, can an attacker who intentionally causes a sortition to be missed (by not submitting a block-commit in a burn block they could have committed in, or by submitting a late/invalid one) on one fork, then wins the *next* sortition on that same fork, receive `total_coinbase` counted once in that fork — while a competing observer computing the same accumulated value from a *different* snapshot (due to snapshot forking during the missed-sortition window) computes a different `accumulated_coinbase_ustx`, breaking node-to-node agreement on `total_coinbase` for the winning tenure? Equality: `accumulated_coinbase_ustx` for a given `consensus_hash` must be identical on every node that has processed that sortition. Impact: Critical, state-root divergence via disagreement on scheduled coinbase amount. Proof idea: harness with a deliberately-missed sortition round on one node's view vs the same burnchain replayed independently on a second node; assert `SortitionDB::get_block_snapshot_consensus(..).accumulated_coinbase_ustx` and the resulting `MinerPaymentSchedule.coinbase` are byte-identical on both nodes.
