SpvClient::drop_headers (spv.rs) and the subsequent insert_block_headers_after(new_tip - 1, new_headers) in inner_find_bitcoin_reorg's merge step (indexer.rs) execute as two separate transactions with no atomic wrapper. Attacker action: as a Bitcoin miner extending a competing fork with more total work, trigger a reorg merge, and cause the process to crash or be killed (simulable in a Rust integration test as an early return/panic injected between the two calls) after drop_headers(new_tip) commits but before insert_block_headers_after commits. Precondition: orig_total_work < reorg_total_work has just been established, triggering the merge branch. Call sequence: orig_spv_client.drop_headers(new_tip) commits, deleting all headers above new_tip; process restarts before insert_block_headers_after runs; on restart get_headers_height() reports new_tip+1, a lower tip than any peer that completed the merge. Equality broken: get_headers_height(node A after crash-restart) == get_headers_height(node B that completed the merge) fails, and since neither node has re-run the reorg logic yet, node A's SortitionDB burn view is stuck at new_tip while node B has already advanced past it, so SORTITION winner(node A, height new_tip+1..) is undefined/absent while SORTITION winner(node B, same heights) is populated -- a temporary but externally-observable tip disagreement. Impact: Critical if any Stacks block gets accepted against node B's advanced view before node A catches up and a tenure-change references a sortition node A does not yet have, causing node A to reject a block node B accepts. Proof: two-node harness, kill/restart one node between drop_headers and insert_block_headers_after (mockable via a custom load_reorg_headers closure that panics after the drop), assert get_headers_height() mismatch and that block acceptance verdicts differ across the two nodes for the same submitted Nakamoto block.
