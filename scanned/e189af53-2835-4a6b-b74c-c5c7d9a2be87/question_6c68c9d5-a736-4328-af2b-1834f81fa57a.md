SpvClient::insert_block_headers_before (spv.rs) explicitly skips continuity validation against the existing chain when read_block_header(end_height) returns None ('will not validate continuity'), only checking the block immediately below start_height via prev_blockhash. Attacker action: feed a descending getheaders reply (reverse_order=true) whose middle segment is internally contiguous but whose lower end connects to a forged ancestor not actually on the canonical chain, at a height where the true child header has not yet been fetched. Precondition: reverse_order sync in progress, no header stored yet at end_height. Call sequence: insert_block_headers_before -> validate_header_integrity (passes, only checks internal contiguity) -> child-check skipped -> write_block_headers commits the forged segment. Equality broken: burn_header_hash stored by this node at that height == burn_header_hash independently computed by an ascending-synced peer fails once the true child header later arrives and no longer matches prev_blockhash. Impact: Critical, this node's SortitionDB burn view is unrecoverably wrong for that height unless it detects and reorgs, and if a Stacks block-commit already got scanned against it, its sortition winner is derived from a hash no other honest node accepts. Proof: build a descending SpvClient sync test that inserts a forged low segment before the true child exists, then insert the true child and assert insert_block_headers_after (or a subsequent handle_headers) fails to re-validate the already-committed forged rows, i.e. no in-place check catches the mismatch that was written.
