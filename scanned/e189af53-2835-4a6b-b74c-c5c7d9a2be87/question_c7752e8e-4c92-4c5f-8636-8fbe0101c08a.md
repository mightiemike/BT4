SpvClient::get_target_between_headers (spv.rs) computes actual_timespan as (last_header.header.time - first_header.header.time) as u64 on raw u32 timestamps with no check that last_header.time >= first_header.time. Attacker action: as a Bitcoin miner extending their own low-hashpower fork, craft the last header of a 2016-block interval with a timestamp earlier than the interval's first header (Bitcoin consensus itself does not forbid a modest local timestamp irregularity within its own median-time-past rule at each single step, but the difficulty-interval endpoints checked here are far apart and not directly covered by SpvClient::validate_header_work's local median-of-11 check at those two exact heights). Precondition: interval boundary retarget computation reached via get_target's fallback to get_target_between_headers when not on Regtest and not within the Testnet special-case branch. Call sequence: get_target_between_headers -> u32 subtraction underflows before the 'as u64' cast -> actual_timespan wraps to a huge value -> clamped to target_timespan*4 -> new_target computed from a timespan the header's real chronology never had. Equality broken: bits(recomputed by node A) == bits(recomputed by node B) can differ across build profiles (checked-sub panics in debug builds, wraps in release), but even within one profile the wrapped target no longer equals the Bitcoin-consensus-correct target, so validate_header_work's bits comparison accepts a header that a spec-correct client would reject. Impact: Critical if it lets sub-difficulty headers into the canonical view feeding sortition; scoped to nodes on the same build profile as the attacker's crafted timestamps target. Proof: unit-construct first/last LoneBlockHeader with last.time < first.time, call get_target_between_headers directly, assert the returned bits differ from the Bitcoin-consensus target for the same real elapsed time.
