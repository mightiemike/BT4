SpvClient::get_target (spv.rs) selects its parent header from headers_in_range[0] when non-empty, else falls back to read_block_header(current_header_height - 1); which branch a node takes depends purely on local sync order (ascending vs reverse_order). Attacker action: submit headers in an order that forces one honest node down the headers_in_range branch and another down the read_block_header branch for the same current_header_height, e.g. by fragmenting a getheaders reply so that node A already cached a differing ancestor set. Precondition: both nodes at the same start height, Testnet network_id so the special-min-difficulty path is live. Call sequence: get_target -> Testnet branch checks current_header.time > parent_header.time + 1200 using two different parent_header values -> different (bits, target) accepted. Equality broken: bits(node A) == bits(node B) fails for the identical current_header, so validate_header_work accepts the header on one node and rejects it on the other. Impact: Critical, one node's canonical tip diverges (a valid-on-A block permanently rejected on B, or vice versa), splitting the burnchain view feeding sortition. Proof: two SpvClient DBs pre-loaded with different partial header caches, call get_target with the same current_header, assert returned (bits, target) tuples differ.
