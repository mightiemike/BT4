Target: `verify_system_tx` (crates/evm/src/evm/executor.rs) reading L1 block info via `SHORT_HEADER_PROOF_PROVIDER.get_and_verify_short_header_proof_by_l1_hash`. Attacker action: none directly (system txs are sequencer-authored), but an attacker who can delay/withhold a Bitcoin transaction so a `ShortHeaderProofProviderError::ShortHeaderProofNotFound` occurs for the sequencer at inclusion time can cause the *sequencer's* short header proof provider (backed by its own DA view) to succeed while a full node's provider (syncing from a different DA source/timing) fails, or vice versa, for the identical `l2_height`. Preconditions: sequencer and full node have different DA sync states when processing the same `setBlockInfoCall` system tx at L2 height H. Call sequence: sequencer includes the system tx (proof available to it) -> full node re-executes the same L2 block via `execute_l2_block`/`apply_l2_block` -> full node's `verify_system_tx` fails to find/verify the SHP for the same `l1_block_hash`. Binding: state root computed by sequencer at height H (using SHP available to it) == state root a full node computes re-executing the identical L2 block (needing the same SHP availability). Impact: Critical/High — a full node that cannot verify the SHP either panics/errors and stalls (denial to that node, excluded) or, if it silently treats verification differently, could diverge in state root, splitting honest full nodes' state root views. Proof idea: cargo test in `crates/fullnode` simulating a full node whose `SHORT_HEADER_PROOF_PROVIDER` is missing the relevant SHP while re-executing a stored L2 block via the state-diff RPC path (`crates/fullnode/src/rpc.rs` computed_root vs stored_state_root assertion) and confirm it surfaces as an error rather than silently accepting a different root.
