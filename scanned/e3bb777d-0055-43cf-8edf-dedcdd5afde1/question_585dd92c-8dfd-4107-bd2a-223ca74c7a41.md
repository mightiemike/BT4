Target: `BitcoinLightClientContract::setBlockInfoCall` field `_coinbaseDepth` cast in `verify_system_tx`. Attacker action: send a `setBlockInfo`-selector transaction with `_coinbaseDepth` set to a value that overflows the target integer type or is inconsistent with the queued short header proof's actual `coinbase_txid_merkle_proof_height`, exploiting the `.try_into().map_err(...)` boundary. Preconditions: attacker can choose arbitrary calldata bytes for any transaction whose first 4 bytes equal the selector, since `verify_system_tx` inspects only the selector, not caller privilege in this file's scope. Call sequence: `verify_system_tx` decodes `call._coinbaseDepth` -> `try_into()` -> if it fails returns `EvmSystemTxParseError`; if it succeeds but is wrong, `get_and_verify_short_header_proof_by_l1_hash`'s `coinbase_depth == l1_update_info.coinbase_txid_merkle_proof_height` check should reject. Binding: `coinbase_depth` accepted by the STF == `l1_update_info.coinbase_txid_merkle_proof_height` derived independently from the verified short header proof's own Merkle path. Impact: Critical if any code path allows the equality check to be bypassed (e.g., via type coercion truncation), letting a forged coinbase-depth claim through into the committed L1 hash chain. Proof idea: cargo test in `sys_tx_tests.rs` submitting a coinbase depth value near integer boundaries and asserting rejection.
