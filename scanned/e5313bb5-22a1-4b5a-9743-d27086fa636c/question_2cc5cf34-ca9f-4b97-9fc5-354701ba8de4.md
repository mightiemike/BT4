Target: `StateCheckpoint::freeze` and `StateDelta::freeze` in scratchpad.rs, which extract `(ReadWriteLog, Witness)` used later to call `Storage::validate_and_commit`. Attacker action: a normal EVM transaction sequence executed by the sequencer whose `ReadWriteLog.cache_log` is later replayed by a light client / batch prover circuit. Preconditions: sequencer produces an L2 block, full node/prover re-executes to build its own witness. Call sequence: `WorkingSet` mutated by tx execution -> `checkpoint()` -> `StateCheckpoint::freeze()` -> `(ReadWriteLog, Witness)` fed into `validate_and_commit`. Binding: the `Witness` extracted by `StateDelta::freeze` on the prover's native run == the `Witness` the guest circuit consumes to reconstruct the same JMT reads during proof generation. If a `StorageKey`/`CacheKey` version mismatch occurs (via `to_cache_key_version(self.version)`), the witness recorded natively will not match what the guest expects for the same logical key, since `version: Option<Version>` distinguishes archival lookups. Impact: Critical - a proof could be generated over a witness that does not correspond to the actual state read during real execution, making a true transition unprovable or a wrong root provable. Proof idea: cargo test creating a `WorkingSet` with `set_archival_version` mid-execution, freezing twice, and asserting the two `CacheKey`s recorded for the same `StorageKey` differ if `version` differs, demonstrating the witness/state binding can desync.
