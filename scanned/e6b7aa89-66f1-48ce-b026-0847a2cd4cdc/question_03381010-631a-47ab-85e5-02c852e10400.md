In stackslib/src/chainstate/nakamoto/mod.rs, check_normal_coinbase_tx() verifies VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes()) but leader_vrf_key and sortition_hash are supplied by the caller rather than derived strictly from the winning LeaderBlockCommitOp's key_block_ptr/key_vtxindex and its own sortition. Can an attacker who controls a LeaderKeyRegisterOp construct a coinbase VRF proof valid under a *different* registered VRF public key than the one bound to the winning block-commit's key_block_ptr/key_vtxindex, such that check_normal_coinbase_tx accepts a proof that does not correspond to the committed leader key? Preconditions: attacker registers two LeaderKeyRegisterOp entries (key_1, key_2) in the same reward cycle; wins a sortition with a block-commit pointing key_block_ptr/key_vtxindex at key_1, but crafts a coinbase VRF proof using key_2's private key. Call sequence: append_block -> check_normal_coinbase_tx -> VRF::verify(leader_vrf_key, ...). Equality: leader_vrf_key passed to VRF::verify == the VRFPublicKey resolved by SortitionDB::get_leader_key_at(block_commit.key_block_ptr, block_commit.key_vtxindex) for the *winning* commit, and the proof must verify only under that key. Scope: Critical — if the wrong-key lookup path is reachable, a block is accepted whose coinbase VRF proof is not bound to the committed randomness, letting an attacker bias/reuse VRF outputs and corrupting deterministic sortition_hash derivation for the next tenure, causing state-root divergence across nodes. Proof idea: integration test constructing a NakamotoBlock with a coinbase VRF proof signed by a non-committed VRF key and asserting append_block rejects it; then assert the equality get_leader_key_at(key_block_ptr,key_vtxindex).public_key == proof's actual signer key must be enforced end-to-end, not just structurally.
