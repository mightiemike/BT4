leader_key_register.rs's LeaderKeyRegisterOp::check() only enforces `!tx.has_VRF_public_key(&self.public_key)` (no reuse of the same VRF pubkey) but performs no binding between the registering transaction's apparent sender and the memo's Hash160 (interpret_nakamoto_signing_key). Can an unprivileged attacker submit a LeaderKeyRegisterOp with a memo encoding a Hash160 belonging to a different miner's Nakamoto signing key, then win a sortition and produce a NakamotoBlock signed by that other miner's key, exploiting the fact that check() never verifies memo ownership against apparent_sender? Preconditions: victim miner V has published blocks signed by pkh160_V; attacker registers a fresh unused VRF key K with memo = pkh160_V. Call sequence: LeaderKeyRegisterOp::check -> accepted into burnchain state -> attacker wins a block-commit referencing key K -> NakamotoBlock::check_miner_signature recovers pkh160 from block signature and compares to leader-key memo. Equality: the Hash160 bound in the winning leader-key's memo (interpret_nakamoto_signing_key) == the pubkey-hash160 of the actual entity that controls the corresponding VRF private key and mines under it. Scope: High — no chain split by itself (check_miner_signature still requires attacker to actually sign with pkh160_V's key, which attacker doesn't have), but the missing binding is a latent validation gap; ask whether any downstream code path assumes memo hash160 == registrant identity without further signature verification, which would let an attacker impersonate another miner's leader-key attribution in tooling/relayer bookkeeping and cause reward misattribution. Proof idea: integration test registering a LeaderKeyRegisterOp with memo = an arbitrary Hash160 not derived from the sender's own key and asserting op_error::LeaderKeyAlreadyRegistered is the only check performed (no ownership check), then checking whether check_miner_signature is the sole guard preventing exploitation.
