In the `DataOnDa::Aggregate` arm, `wtxids` in `DataOnDa::Aggregate(Vec<[u8;32]>, Vec<[u8;32]>)` is fully attacker-visible plaintext embedded in a blob the batch prover signs, but `blob.sender()` is checked only for the top-level Aggregate blob, not for each individual referenced chunk. Can an unprivileged attacker who front-runs the batch prover's own planned chunk-reveal UTXO spend (regtest: attacker observes the commit transaction in mempool and broadcasts a conflicting reveal with attacker-chosen `DataOnDa::Chunk` bytes before the honest reveal confirms) cause the wtxid the batch prover later cites in its `Aggregate` list to resolve, via `ChunkAccessor::get`, to attacker bytes instead of the batch prover's intended chunk? Preconditions: regtest bitcoind, batch prover has broadcast (but not yet confirmed) its commit transaction. Binding: `DS::decompress_chunks(&complete_proof)` bytes `process_complete_proof` verifies == the exact proof bytes the batch prover intended to chunk. Impact: Critical, PROOF SOUNDNESS - `process_complete_proof` may accept a state transition assembled partly from attacker-controlled bytes if decompression/deserialization still succeeds. Proof idea: cargo test simulating a mempool race in bin/citrea/tests/bitcoin/light_client_test.rs where two reveal transactions target the same taproot commit output, asserting which chunk body `ChunkAccessor::get` returns after both are (attempted to be) mined.
