[Target: BitcoinVerifier::verify_transactions, coinbase commitment_idx = coinbase_tx.output.iter().rposition(...)] Attacker (as a miner on their own regtest node, or by crafting a template) constructs a coinbase transaction with two outputs matching WITNESS_COMMITMENT_PREFIX and >=MINIMUM_WITNESS_COMMITMENT_SIZE: the first (lower index) is the true segwit commitment matching txs_commitment/merkle_root of the actual wtxid set, and the second (higher index, thus chosen by rposition) is a forged 38-byte output whose commitment bytes are arbitrary. Preconditions: attacker mines this block themselves (regtest, or any unprivileged party able to construct/mine a block with this coinbase shape). Call sequence: BitcoinVerifier::verify_transactions picks commitment_idx via rposition (highest index wins per BIP-141), computes merkle_root from inclusion_proof.wtxids, checks script_pubkey[6..38] of coinbase_tx.output[commitment_idx] against calculate_double_sha256(merkle_root||input_witness_value); since the attacker's forged commitment at the higher index does not match, this returns Err(IncorrectWitnessCommitment) and the ENTIRE block's relevant txs are rejected. Binding: verify that Bitcoin Core (and thus what an honest full node's da_block_handler treats as the 'real' block content) ALSO uses highest-output-index as canonical commitment (BIP-141 compliant) so that block B's real committed wtxid set == the wtxid set BitcoinVerifier::verify_transactions computes from inclusion_proof.wtxids in this two-commitment scenario. If Bitcoin Core's actual validation differs from `rposition` semantics for this edge case, one honest full node's da_block_handler view of block B's blobs diverges from what the circuit will ever prove for B. Impact: Critical DA_INTEGRITY split between what an honest full node consumed live vs. what any prover can ever prove for that block, permanently orphaning true blobs.
