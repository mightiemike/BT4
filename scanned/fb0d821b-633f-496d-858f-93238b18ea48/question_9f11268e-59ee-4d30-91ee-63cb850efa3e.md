Target: DepositDataMempool::calc_tx_id's double-SHA256 computation (Sha256::hash(&data) then Sha256::hash(&hasher)). Attacker action: submit a deposit blob whose moveTx.version.0, vin.0, vout.0, or locktime.0 byte slices are empty or zero-length (e.g., an empty vin.0), producing a data buffer that collapses to bytes indistinguishable from a different, non-empty-but-equal-length-adjusted legitimate moveTx's concatenation. Preconditions: BridgeContract::depositCall::abi_decode_raw accepts empty dynamic-bytes fields without rejecting the call. Call sequence: calc_tx_id concatenates possibly-empty fields with no separators or length prefixes, so an attacker can always find a byte split degenerate case where two distinct decoded MoveTx structs serialize to the same flat byte string. Binding: calc_tx_id is intended to uniquely identify one Bitcoin move-to-vault transaction, but the hashing scheme's lack of field-length binding means the equality calc_tx_id(tx1) == calc_tx_id(tx2) does not imply tx1 == tx2, breaking the 'counted once' identity the pending_deposits/accepted_deposit_txs de-duplication relies on. Impact: Critical, cBTC credit accounting can be based on an identity function that is not injective over the space of valid moveTx values, letting an attacker either block or displace a legitimate deposit. Proof idea: cargo test enumerating crafted (vin,vout) byte splits with identical concatenation and asserting calc_tx_id collision while confirming BridgeContract::depositCall::abi_decode_raw parses both to distinct Rust struct values.
