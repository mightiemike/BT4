`LightClientProofCircuit::process_complete_proof` computes `batch_proof_method_id` via `binary_search_by_key(&batch_proof_output_last_l2_height, |(height, _)| *height)` against `BatchProofMethodIdAccessor::<S>::get`. If an attacker (who cannot hold the method-id upgrade authority key but *can* choose which already-valid batch proof bytes to (re-)inscribe and in what order relative to a legitimate method-id upgrade blob) submits an old-format valid batch proof whose `last_l2_height` straddles a just-activated method-id boundary, can `idx.saturating_sub(1)` select the *wrong* (superseded) method id, causing `Z::verify` to validate a proof against a decommissioned circuit version whose soundness properties for post-upgrade opcodes were never guaranteed? Binding: the `batch_proof_method_id` selected for a given `last_l2_height` must equal the method id that was authoritative for that specific L2 height range, one-to-one. Impact: Critical, a batch proof accepted under a stale method id for L2 blocks that should require the new one — a proof for a transition that circuit was never designed to check. Proof idea: cargo test seeding `BatchProofMethodIdAccessor` with two method ids at different activation heights and submitting a batch proof whose `last_l2_height` is exactly at the boundary, asserting the selected `idx` matches the height-appropriate entry.
