### Title
Multisig weight bypass via signature malleability in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract sums the weights of recovered signer addresses to check whether a permission's threshold is satisfied. The de-duplication logic in its signature-processing loop only skips an entry when the *exact same signature bytes* were already processed for a recovered address; if the same address is recovered from a second, distinct-but-valid signature over the same hash (e.g., an ECDSA malleated variant `(r, n-s)` of an original `(r, s)`), the loop does not skip weight accumulation for it. This is structurally the same defect described in the reference report: a duplicate/limit check is performed against a value that is not properly re-validated on every iteration of a loop, letting a single actor's contribution be counted more than once and bypass the intended cap (here, the signer weight cap represented by the permission threshold).

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute()`: [1](#0-0) 

```java
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);

  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) {
    return Pair.of(true, DATA_FALSE);
  }
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
if (totalWeight >= permission.getThreshold()) {
  return Pair.of(true, dataOne());
}
```

The intent of the `matrixContains(executedSignList, recoveredAddr)` check is clearly to detect that a given address has already contributed its weight (mirroring the `currentIdleDeposits`-style cap check in the reference report). However, the code only actually skips accumulation (`continue`) when the *entire merged signature* (`address || raw signature bytes`) has been seen before — i.e., only exact duplicate submissions are rejected. When the address was seen before but the raw signature bytes differ, the code merely calls `MUtil.checkCPUTime()` (a CPU-time throttling guard) and falls straight through to `totalWeight += weight`, adding the same signer's weight again.

Because ECDSA signatures are malleable (a valid `(r, s)` signature has an equally valid `(r, n-s)` counterpart, with an adjusted recovery id), an attacker holding a single private key can trivially produce two (or more, bounded by `MAX_SIZE = 5`) distinct byte-level signatures that all recover to the same address for the same message hash. Submitting these as separate entries in the `signatures[]` array to the `validatemultisign(address,uint256,bytes32,bytes[])` precompile call causes the same key's weight to be counted multiple times, inflating `totalWeight` past `permission.getThreshold()`.

### Impact Explanation
Any smart contract on TVM that relies on this precompiled contract (address alias for `ValidateMultiSign`) to authorize multi-signature actions (a common pattern for on-chain multisig wallets/governance contracts checking TRON account permissions) can have its authorization threshold satisfied by a single signer producing multiple malleated signatures, instead of requiring the intended number of independent key holders. This is an unauthorized-operation / authorization-bypass condition reachable purely from contract execution triggered by an ordinary broadcast transaction (no privileged actor required). The severity depends on what the calling contract gates behind the multisig check (fund transfers, governance actions, etc.), but the underlying primitive is a full authorization bypass of the threshold logic exposed by this precompile.

### Likelihood Explanation
High. The prerequisite is only possession of a single valid ECDSA private key/signature over the target hash — signature malleability (`s → n - s`) is a standard, well-known, cheaply-computable transformation requiring no cryptographic breakthrough. No special node or peer privileges are needed; the attacker simply deploys/calls a contract that invokes `validatemultisign` with the crafted `bytes[]` signature array, i.e., a normal, anonymous, unprivileged transaction.

### Recommendation
Change the loop to unconditionally skip weight accumulation whenever `recoveredAddr` has already contributed, regardless of whether the specific signature bytes differ:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  continue; // always skip duplicate addresses, malleated or not
}
```
Keep `MUtil.checkCPUTime()` (or equivalent) only for genuine CPU-cost accounting of the extra `ecrecover`, but never allow a second `totalWeight += weight` for an address that has already been credited. The same audit should be applied to the analogous logic in `BatchValidateSign`/other signature-aggregation code paths in this file to confirm they do not share the pattern.

### Proof of Concept
1. Owner account has an `Active` permission with `threshold = T` and a single key `K` with `weight = T` (i.e., normally one signature from `K` alone should already satisfy the threshold — but consider a permission with `threshold = 2*T` where `K`'s weight is only `T`, so a single signature from `K` should NOT satisfy it).
2. Attacker (holder of `K`) computes `sig1 = sign(hash, K)` and derives a malleated variant `sig2 = malleate(sig1)` such that `ecrecover(hash, sig2) == address(K)` but `sig2 != sig1` byte-for-byte.
3. Attacker calls the `validatemultisign(address, permissionId, hash, bytes[])` precompile (either directly via a contract, or through a wallet contract that gates an operation on its return value) with `signatures = [sig1, sig2]`.
4. In the loop: iteration 1 adds `weight(K)` to `totalWeight` and records `K` and `merge(K, sig1)`. Iteration 2 recovers `K` again; `matrixContains(executedSignList, K)` is true, but `matrixContains(executedSignList, merge(K, sig2))` is false (different signature bytes), so it does not `continue` — it adds `weight(K)` a second time.
5. `totalWeight` now equals `2 * weight(K)`, which can meet or exceed `permission.getThreshold()` even though only one distinct key ever signed, causing the precompile to return "authorized" (`dataOne()`), incorrectly satisfying a multisig threshold check that should have required at least two independent signers.
