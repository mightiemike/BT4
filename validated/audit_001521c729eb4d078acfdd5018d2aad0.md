This confirms a strong analog: a known, self-documented, and only partially-mitigated bug (tracked as [near/nearcore#12606](https://github.com/near/nearcore/issues/12606)) where receipts can be created above `max_receipt_size` because the size check runs at receipt-creation time, before `output_data_receivers` are appended, letting an oversized receipt slip past validation and persist into state/cross-shard flow.

### Title
Receipt size validation runs before `output_data_receivers` are appended, allowing oversized receipts into consensus state - (File: `runtime/runtime/src/lib.rs`)

### Summary
`validate_receipt` enforces `max_receipt_size` on newly created receipts, but this check happens in `apply_action` before the runtime later mutates the same receipt by appending `output_data_receivers` in `runtime/runtime/src/lib.rs` (around lines 1146-1191). A `FunctionCall` that returns a receipt index (`ReturnData::ReceiptIndex`) causes the parent's `output_data_receivers` to be extended onto the already-validated child receipt, which can push it past `max_receipt_size` after the size gate has already passed.

### Finding Description
`validate_receipt` in [1](#0-0)  computes `borsh::object_length(receipt)` and rejects anything over `limit_config.max_receipt_size` only when `mode == ValidateReceiptMode::NewReceipt`. This is invoked from `runtime/runtime/src/lib.rs` right after `apply_action` produces `new_result.new_receipts`, as seen in [2](#0-1) .

However, later in the same apply loop, when a function call finishes with `ReturnData::ReceiptIndex(receipt_index)`, the runtime mutates the already-validated receipt in place by appending the *parent's* `output_data_receivers` onto it: [3](#0-2) . This mutation happens after the size check already ran, so the final persisted/forwarded receipt can exceed `max_receipt_size` with no re-validation.

The codebase itself documents this as a known, tracked bug (`near/nearcore#12606`) and only applies a symptom-level workaround, not a root-cause fix:
- `ValidateReceiptMode::ExistingReceipt` is explicitly documented to "tolerate" oversized receipts because of this exact bug: [4](#0-3) .
- `try_forward` in congestion control clamps `size` to `max_receipt_size` for admission-limit bookkeeping specifically to work around oversized receipts getting stuck, citing the same issue number: [5](#0-4) .
- A dedicated regression test titled `test_max_receipt_size_promise_return` reproduces exactly this construction and states in its own comment that "the receipt should be rejected, but currently isn't because of a bug": [6](#0-5)  and [7](#0-6) .
- A second variant, `test_max_receipt_size_value_return`, produces an oversized `Data` receipt via a returned value the same way: [8](#0-7) .

This is directly analogous to the pallet-ethereum CVE-2021-39193 bug class: a validation-order gap allows a transaction/receipt whose actual on-chain size violates a stated invariant to still be accepted into canonical state, because the size check does not cover the object's *final* serialized form.

### Impact Explanation
Any unprivileged account can trigger this from a single deployed contract by calling a method that creates a promise, has that promise's callback create another promise near the size boundary, and calls `promise_return` on it while the outer receipt also has `output_data_receivers` — exactly what the existing regression test does via `near_test_contracts::rs_contract()` methods. The result is a receipt whose actual serialized size exceeds the protocol-mandated `max_receipt_size`, breaking a hard invariant relied upon elsewhere (e.g. `docs/misc/state_witness_size_limits.md`'s guarantee that `ChunkStateWitness` stays bounded, and cross-shard receipt/bandwidth accounting that assumes `size <= max_receipt_size`). Because chunk producers and validators only "tolerate" this via `ValidateReceiptMode::ExistingReceipt` and a size-clamp workaround rather than actually preventing or re-validating it, an oversized receipt can propagate into consensus-relevant state (witnesses, outgoing buffers, congestion accounting) with real byte sizes larger than the limit was designed to bound.

### Likelihood Explanation
High reachability: no special privileges, only a deployed WASM contract and one function call are required. The exact reproduction is already codified as a passing regression test in the repository, confirming determinism and current-day reproducibility.

### Recommendation
Move the `max_receipt_size` validation to after all in-place mutations of a newly created receipt are complete (i.e., re-validate size after the `output_data_receivers` extension block in `runtime/runtime/src/lib.rs`), or refuse to append additional `output_data_receivers` once the receipt is already at/near the size limit, and reject the action with `ReceiptSizeExceeded` at that later point rather than only clamping/tolerating downstream.

### Proof of Concept
Use the existing repository test as the reproduction, which is a real (not hypothetical) proof of concept: [9](#0-8) 
It deploys a contract, computes `args_size` so a generated receipt is exactly `max_receipt_size` bytes, then calls a method that creates promise `A -then-> B`, where `A`'s execution creates promise `C` and calls `promise_return` on it, causing `C`'s already-validated receipt to have `output_data_receivers` appended and grow past `max_receipt_size`. `assert_oversized_receipt_occurred` at [10](#0-9)  confirms such an oversized receipt is found in the chain's incoming receipt proofs.

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
