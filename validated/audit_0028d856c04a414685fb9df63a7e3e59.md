Analysis supporting this conclusion:

The premise requires that `cur_commits` can contain two distinct `LeaderBlockCommitOp` entries sharing the same `txid` and that their relative order can differ across nodes due to "indexer/DB ordering". Both parts of this premise fail on inspection:

1. **Txid duplication cannot occur legitimately.** Each `LeaderBlockCommitOp.txid` is set directly from `tx.txid()` in `LeaderBlockCommitOp::parse_from_tx` [1](#0-0) , i.e., the Bitcoin transaction hash of the underlying, distinct on-chain transaction. Two *distinct* block-commits sharing a txid would require either the same Bitcoin transaction being counted twice (impossible — a tx appears once per block) or a SHA-256d hash collision, which is a Bitcoin-consensus-level cryptographic infeasibility, explicitly out of scope per the rules ("Bitcoin-consensus defects with no path through this repo").

2. **Retrieval order is deterministic, not indexer/insertion-order-dependent.** `cur_commits` (i.e., `block_commits[rel_block_height]`) is populated via `SortitionDB::get_block_commits_by_block`, which executes `SELECT * FROM block_commits WHERE sortition_id = ?1 ORDER BY vtxindex ASC` [2](#0-1) . This canonical `ORDER BY vtxindex` clause is applied on every read, regardless of insertion order, so the vector fed into `make_min_median_distribution` is deterministically ordered by `vtxindex` for any node holding the same set of `block_commits` rows for that `sortition_id`. The callers that assemble the windowed `block_commits` (`stackslib/src/burnchains/burnchain.rs:273` and `stackslib/src/config/chain_data.rs:101`) both use this same query [3](#0-2) [4](#0-3) . Since the underlying `block_commits` rows for a given `sortition_id` are themselves derived deterministically from the shared Bitcoin burnchain (the same set of ops is extracted by every node from the same Bitcoin block), two honest nodes will always have identical rows and identical `vtxindex`-sorted order — there is no "indexer returns ops in different insertion order" degree of freedom reaching this function.

Because duplicate txids cannot arise from distinct commits, and because the vector order feeding `cur_commits_map`'s construction is canonicalized by `ORDER BY vtxindex` rather than by insertion/indexer order, the `HashMap::collect`-last-write-wins behavior at `stackslib/src/chainstate/burn/distribution.rs:220-223` [5](#0-4)  cannot produce divergent results between two honest nodes for the same burn block set. The claimed equality break does not materialize.
