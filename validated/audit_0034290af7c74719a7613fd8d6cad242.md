## Finding

### Title
Unbounded `ActiveBallotIDs` scan in `ExpireBallotsBeforeHeight` can be inflated by cheap external-chain events to permanently block inbound/outbound ballot creation - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
`CreateBallot` unconditionally calls `ExpireBallotsBeforeHeight`, which performs a full linear scan of the `ActiveBallotIDs` set plus a `Ballots.Get` read per entry, on every single new ballot creation. A new ballot is created on the very first Universal Validator vote for any not-yet-seen inbound/outbound observation key. Since inbound observation keys are derived from attacker-controllable external-chain data (`source_chain:tx_hash:log_index`), and the protocol explicitly supports zero-amount inbound events, an unprivileged external actor can cheaply generate an unbounded number of distinct inbound events on a source chain, forcing `ActiveBallotIDs` to grow without any protocol-level cap. Once the set is large enough, the O(N) scan executed inline inside every `MsgVoteInbound`/`MsgVoteOutbound` transaction that creates a new ballot can exceed the per-tx/per-block gas budget, causing those transactions to fail atomically (no partial commit in Cosmos SDK) and permanently blocking the creation of any *new* ballot going forward — effectively freezing the inbound/outbound observation pipeline, exactly analogous to the `DepositQueue` permanent-lock bug class.

### Finding Description
`CreateBallot` is the single choke point through which every first-time ballot (per unique inbound/outbound key) is created: [1](#0-0) 

It always invokes `ExpireBallotsBeforeHeight`, which does a full iteration of `ActiveBallotIDs`, reading each corresponding `Ballots` entry to check its expiry height: [2](#0-1) 

`GetOrCreateBallot` — invoked from `VoteOnBallot`, which is invoked from `VoteOnInboundBallot`/`VoteOnOutboundBallot` for every validator vote — calls `CreateBallot` precisely when the ballot ID does not yet exist, i.e., on the first vote for a brand-new inbound/outbound observation: [3](#0-2) [4](#0-3) 

Ballot IDs for inbounds are derived from `source_chain:tx_hash:log_index` (attacker-controlled fields on the source chain), and the codebase explicitly supports zero-amount inbound events (`GAS`, `GAS_AND_PAYLOAD` with `Amount: "0"`), meaning an attacker can generate an unbounded stream of distinct, real, honestly-observed inbound events at negligible cost (just gas on the external chain to hit the Gateway contract), each of which honest UVs will independently vote on: [5](#0-4) 

Every one of those distinct events triggers a fresh `CreateBallot`/`ExpireBallotsBeforeHeight` full scan of `ActiveBallotIDs`. If the attacker sustains a high enough rate of distinct dust/zero-amount events (faster than validators can converge to quorum and remove entries via `MarkBallotFinalized`/`MarkBallotExpired`), `ActiveBallotIDs` grows unbounded. Removal from the active set only happens when a ballot reaches quorum or its own expiry is reached during a *subsequent* scan — there is no independent BeginBlocker sweep and no cap on the set's size, so growth outruns cleanup under sustained flooding.

Because Cosmos SDK transactions are atomic — an out-of-gas panic during execution reverts all state changes for that transaction — once the scan cost exceeds the effective gas budget, the vote transaction that would have created the *next* new ballot fails entirely and no ballot is created. This blocks quorum formation (and hence `UniversalTx` creation, fund minting, and outbound resolution) for that inbound/outbound and for every subsequent new inbound/outbound, since each of those also requires a first-vote `CreateBallot` call that must pay for the now-oversized scan. This is architecturally identical to the `DepositQueue.remove` bug: a gas-intensive, unbounded-size operation sits on the hot path of ordinary user-triggered activity, and once the backing collection is inflated past a threshold, the entire pipeline (deposits/inbounds) can no longer make progress.

### Impact Explanation
This falls squarely within the "Honest-validator finalization path" and "State safety path" allowed impacts: user-created source events alone (zero-amount or dust inbound events, no privileged actor, no malicious validator required) can prevent honest Universal Validators from converging on new ballots, halting material execution of the universal inbound/outbound pipeline. Concretely:
- New inbound observations cannot form ballots → no `UniversalTx` created → user deposits are not minted/processed (funds effectively frozen).
- New outbound observations cannot form ballots → outbound resolution (refunds on failure, completion confirmation) stalls, risking funds stuck mid-flight.
- Because the failure occurs inside message execution (not `BeginBlocker`), it does not halt the chain outright, but it durably blocks the specific state transitions (ballot creation) needed for correctness of the universal execution flow, matching "permanent freezing" of user/protocol funds and "consensus/state-machine divergence reachable from ordinary user deposits."

### Likelihood Explanation
Likelihood is moderate-to-high given normal operation: the trigger requires only that an unprivileged actor generate many distinct external-chain events (even zero-value ones) faster than the validator set can reach quorum and prune `ActiveBallotIDs`. Zero-amount inbound support and cheap L1/L2 external-chain gas make this economically feasible without needing to move real value into the vault. The exact size at which the scan becomes gas-prohibitive depends on chain gas parameters and validator-set size (each iteration involves a KV prefix-iterate step plus a full `Ballots.Get`), but there is no protocol-level cap preventing `ActiveBallotIDs` from growing arbitrarily large, so the condition is reachable purely through sustained flooding.

### Recommendation
- Decouple ballot expiry cleanup from the ballot-creation hot path: run expiry sweeps in `BeginBlocker`/`EndBlocker` with a bounded batch size per block instead of inline, full-scan cleanup inside every `CreateBallot` call.
- Cap the number of concurrently active ballots (or active ballots per observation type/source chain), rejecting or rate-limiting new ballot creation once the cap is reached, forcing backpressure instead of unbounded growth.
- Consider a minimum economic cost or rate limit on new distinct inbound/outbound observation keys accepted from a given source chain, mirroring the "minimum investment requirement" recommendation from the original report.
- Ensure the `ExpireBallotsBeforeHeight` scan cost is bounded (e.g., processing a fixed maximum number of stale entries per invocation, continuing the sweep across multiple blocks) so no single transaction's gas cost scales with total active-ballot count.

### Proof of Concept
1. Deploy/target the Gateway contract on a supported external chain (testnet gas is negligible).
2. Repeatedly submit distinct zero-amount (or dust) transactions to the Gateway from many source addresses/log indices, each producing a unique `Inbound{SourceChain, TxHash, LogIndex}` and therefore a unique `utx_key`/ballot ID (see `types.GetInboundBallotKey`).
3. Sustain the event rate high enough that Universal Validators cannot vote to quorum and prune (`MarkBallotFinalized`/`MarkBallotExpired`) faster than new ballots are created via `CreateBallot` (each first vote on a new key calls `ExpireBallotsBeforeHeight`, scanning the growing `ActiveBallotIDs` set — [2](#0-1) ).
4. As `ActiveBallotIDs` grows, observe the gas cost of subsequent `MsgVoteInbound`/`MsgVoteOutbound` transactions that must call `CreateBallot` rising linearly; once it exceeds the achievable per-tx/per-block gas, those transactions fail out-of-gas and revert entirely (no ballot created), blocking all further first-votes on new inbound/outbound events and halting universal execution progress for new deposits.

// GetOrCreateBallot returns the ballot if it exists, otherwise creates it.
func (k Keeper) GetOrCreateBallot(
	ctx context.Context,
	id string,
	ballotType types.BallotObservationType,
	voters []string,
	votesNeeded int64,
	expiryAfterBlocks int64,
) (types.Ballot, bool, error) {

	if ballot, err := k.Ballots.Get(ctx, id); err == nil {
		k.Logger().Debug("ballot found (existing)", "ballot_id", id)
		return ballot, false, nil
	}

	k.Logger().Debug("ballot not found, creating new", "ballot_id", id, "ballot_type", ballotType.String())
	newBallot, err := k.CreateBallot(ctx, id, ballotType, voters, votesNeeded, expiryAfterBlocks)

	return newBallot, true, err
}

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
