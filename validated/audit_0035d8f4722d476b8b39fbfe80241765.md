### Title
Stale `AccountInfo` in clean's `store_counts` computation can panic the validator via unguarded `.unwrap() - 1` - (File: accounts-db/src/accounts_db.rs)

### Summary
`AccountsDb::clean_accounts` computes a `store_counts` map to decide which storages are fully purgeable. For the first `(slot, pubkey)` occurrence in each candidate bin, it looks up the storage entry by `(slot, account_info.store_id())` and computes `count = store.count() - 1` using a bare `.unwrap()` and unchecked subtraction, exactly mirroring the CDPVault pattern where a value computed from one point in time (`virtualDebt`) is later subtracted against a second, independently-updated value (`debt`) without validating that the subtraction is still safe.

### Finding Description
In the clean pass, candidate `slot_list`/`ref_count` snapshots are captured by `do_clean_scan` from a live read of `self.accounts_index` [1](#0-0) . Sometime later, and without holding any lock that prevents concurrent modification of the same slot's storage, the `store_counts` loop re-reads storage state fresh from `self.storage`: [2](#0-1) 

If a concurrent shrink operation (which explicitly runs independently of clean — see the comment "shrinking could be running in the background, independently" [3](#0-2) ) rewrites and replaces the storage entry for that same slot between the scan and this lookup, the `account_info.store_id()` captured in the candidate's stale `slot_list` may no longer resolve via `get_account_storage_entry`, since the old storage entry is fully removed from both `map` and `shrink_in_progress_map` once `ShrinkInProgress` is dropped [4](#0-3) . In that case `.map(|store| store.count()).unwrap()` panics on `None`. Even if the store is still found, `store.count()` reflects the *current* live account count, which a concurrent shrink/clean could have already reduced to `0`, causing the trailing `- 1` to underflow.

This is structurally identical to the CDPVault bug class: a value (`debt` / `store.count()`) is fetched at one point, and a separately-fetched or previously-cached value (`liquidatorRepayAmount` / candidate `slot_list`) is subtracted from it without re-validating consistency, so an intervening state change (front-run repayment / concurrent shrink) invalidates the subtraction's safety invariant.

### Impact Explanation
An unguarded `.unwrap()` panic or unchecked-subtraction underflow in the accounts-cleaning background thread is a concrete node-panic vector: `clean_accounts` runs continuously in `AccountsBackgroundService` on every validator, and this code path executes on ordinary, unprivileged account/storage churn (shrink races with clean), not on any privileged/validator-only action. A panic here crashes the validator process.

### Likelihood Explanation
The race requires a slot that is simultaneously a clean candidate and a shrink target to be shrunk to completion in the narrow window between `do_clean_scan` capturing the candidate's `slot_list` and the `store_counts` loop resolving `account_info.store_id()` against live storage. Both clean and shrink are triggered continuously by ordinary account write/update activity (no attacker privilege required), and the code comments explicitly acknowledge shrink and clean operate "independently," but there is no lock/barrier in this specific segment preventing the race, so the likelihood is timing-dependent but not merely theoretical.

### Recommendation
Replace the bare `.unwrap() - 1` with an explicit `checked_sub`/graceful fallback path (skip/retry the pubkey, or re-validate the slot's live storage before subtracting) whenever `get_account_storage_entry` returns `None` or `store.count()` is already `0`, mirroring the safe pattern already used in `AccountStorageEntry::remove_accounts`, which asserts invariants with a descriptive message rather than allowing an unchecked panic-prone `.unwrap()`.

### Proof of Concept
1. Store account `A` in slot `S`, root it, so it lands in a storage entry with `store_id = X`.
2. Trigger clean's `do_clean_scan`, which snapshots the candidate's `slot_list` referencing `(S, X)`.
3. Before the `store_counts` loop executes, trigger a shrink of slot `S` (e.g., via other zero-lamport/dead accounts in the same slot) that completes fully — `ShrinkInProgress` drops, removing storage id `X` from both `map` and `shrink_in_progress_map` [4](#0-3) .
4. The `store_counts` loop calls `self.storage.get_account_storage_entry(S, X)`, which returns `None` because `X` no longer exists, and `.unwrap()` panics, crashing the validator process.
