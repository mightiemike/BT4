Based on my investigation, I found a genuine local integrity gap, not merely a restatement of the external report, but structurally analogous: a single verification path that is documented as skipping/bypassing part of its own integrity check, silently disabling detection of state divergence.

### Title
`ensure_match_transaction_info` skips checkpoint-hash verification during replay, allowing state-root divergence to go undetected - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by chunk replay/verification paths (state-sync chunk executor, `db-tool replay-on-archive`, backup transaction restore's verify mode) to confirm that a locally re-executed transaction output matches the transaction info already authenticated by the ledger's accumulator proof. The function validates status, gas used, write-set hash, and event root hash, but explicitly and admittedly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The comparator checks `status`, `gas_used`, `write_set_hash` vs `txn_info.state_change_hash()`, and `event_root_hash` vs `txn_info.event_root_hash()`, but the function's own TODO admits the gap: [2](#0-1) 

This comparator is used as the single verification gate in the chunk executor's `verify_execution`, which drives verify-mode replay (state sync and replay-verify tooling): [3](#0-2) 

The chunk is executed via `DoGetExecutionOutput::by_transaction_execution`, whose builder path for state checkpoints computes and (if a `known_state_checkpoints` set is supplied) validates the checkpoint hash separately in `DoStateCheckpoint::get_state_checkpoint_hashes` [4](#0-3) . However, the replay/verify call path in `verify_execution` does not pass the trusted `transaction_infos` state-checkpoint fields as `known_state_checkpoints` into this builder — it relies solely on `ensure_match_transaction_info` after the fact, which is documented to ignore exactly this field.

The write-set hash (`state_change_hash`) is checked, so a divergence directly caused by wrong write ops is caught. But the *state_checkpoint_hash* — the actual Sparse-Merkle-Tree root of the world state (and the position/hot-state SMT roots introduced by the "trading-native" feature) — is a distinct, separately-computed commitment that is not cross-checked in this path. A bug in the local JMT/position-state accumulation logic, storage schema handling, or a divergent code path enabled by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state feature flags could produce a `state_checkpoint_hash`/`position_state_checkpoint_hash` that differs from the one embedded in the accumulator-proof-authenticated `TransactionInfo`, while replay-verify still reports success.

### Impact Explanation
This satisfies the "hard-fork-only divergence during commit, replay, restore, or proof verification" impact class: a node relying on replay-verify tooling (`db-tool replay-on-archive`, state-sync's chunk-executor verify mode, or backup restore verify mode) to confirm that its locally derived durable ledger state matches the authenticated chain state will not detect a state-root discrepancy in the checkpoint/hot-state/position-state fields. That undermines the core guarantee of these tools — that they can validate committed state against consensus-authenticated transaction infos — and could let a genuine storage-layer state divergence (e.g., introduced by a JMT bug, an inconsistent feature-flag rollout, or a native "trading" state root bug) go unnoticed until it manifests as an actual consensus/state-proof mismatch elsewhere.

### Likelihood Explanation
The gap is exercised on every replay/verify invocation of these tools, since `ensure_match_transaction_info` is unconditionally the checkpoint-hash-skipping comparator. It requires a pre-existing divergence-inducing bug elsewhere (e.g., in the hot-state/position-state root computation, gated behind the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` config called out in the TODO) to actually manifest, so likelihood of exploitation depends on that separate bug existing; but the detection gap itself is unconditional and directly acknowledged in code.

### Recommendation
Extend `ensure_match_transaction_info` (or the call sites in `chunk_executor::verify_execution` / `db-tool replay_on_archive`) to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the locally computed values before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any related feature) is enabled, so replay-verify cannot silently succeed while a state-root divergence exists.

### Proof of Concept
Not independently exploitable by an external attacker without a separate root-cause bug producing a divergent checkpoint hash (e.g., in hot-state/position-state root computation); the PoC is the code path itself: `ChunkExecutorInner::verify_execution` → `TransactionOutput::ensure_match_transaction_info` (checkpoint-hash checks skipped per the function's own TODO) [5](#0-4) [2](#0-1) . I was unable to fully trace all downstream commit-time consumers (e.g., whether the backup-restore commit path independently re-validates checkpoint hashes against the accumulator-proof-backed `TransactionInfo` before persisting), so this should be treated as a detection/verification-tooling gap requiring confirmation of a concrete divergence-inducing bug for a full end-to-end PoC.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
