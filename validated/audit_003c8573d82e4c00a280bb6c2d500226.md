### Title
Wallet Contract's `has_in_flight_tx` Lock May Never Reset on Callback Out-of-Gas, Permanently Freezing Funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (an eth-implicit-account global contract used to relay Ethereum-style signed transactions as NEAR actions) uses a boolean flag `has_in_flight_tx` as its only "stopped/in-progress" guard. `rlp_execute` — the sole public entry point through which the wallet's funds can be moved — immediately rejects any call while `has_in_flight_tx` is `true`. The flag is only cleared inside callback methods (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`) that are scheduled with a small, fixed static gas allowance. If any of these callbacks fails to complete (e.g. runs out of the statically allocated gas) after `has_in_flight_tx` was set to `true` by the prior call, NEAR rolls back all state changes for that failed receipt, so the flag is never actually reset to `false`. This is structurally the same bug class as the Trader Joe `allowEmergencyWithdraw()` finding: an administrative/normal state-transition sets a "stopped" style flag which then permanently disables the only path (`rlp_execute`) that could ever clear it or move funds, locking the account's balance forever.

### Finding Description
`WalletContract` stores `has_in_flight_tx` with the documented invariant that it must be `true` while a promise is outstanding and `false` otherwise [1](#0-0) .

`rlp_execute` is the single entry point through which any owner or relayer action (transfers, function calls, key management) on the wallet account is initiated, and it unconditionally rejects calls while `has_in_flight_tx` is `true`: [2](#0-1) 

The flag is set to `true` right before returning a `Promise`, and is only cleared as the very first statement of the eventual callback: [3](#0-2) 

Each callback is scheduled with a fixed, small static gas budget rather than one scaled to worst-case execution cost: [4](#0-3) 

If the callback execution (which performs additional logic such as promise-batch refund creation on `PromiseResult::Failed`, JSON/base64 handling, or nested callback dispatch in `address_check_callback` / `nep_141_storage_balance_callback`) exceeds the statically attached gas, the callback receipt fails with an out-of-gas `FunctionCallError`. NEAR's runtime discards all state changes made by a failed function-call receipt, meaning the `self.has_in_flight_tx = false` write at the top of the callback is rolled back along with everything else. The contract is left permanently in the `has_in_flight_tx = true` state.

Because `rlp_execute` is the only production entry point capable of ever clearing the flag again (all clearing sites are callbacks reachable only from a fresh `rlp_execute` call), and `rlp_execute` itself refuses to run while the flag is `true`, the contract deadlocks: no further Ethereum-emulated transaction, transfer, or key action can ever be executed by/for that account again. Any $NEAR or NEP-141 balance owned by the eth-implicit account becomes permanently inaccessible through the wallet contract, exactly mirroring the Trader Joe pattern where a state-flag set during normal operation locks out the only withdrawal path.

### Impact Explanation
This causes permanent loss of access to funds held by the affected eth-implicit account: any NEAR balance or token balance reachable only via `rlp_execute` becomes frozen with no code path to recover it, since the wallet contract exposes no non-callback method to reset `has_in_flight_tx`. This is a concrete "permanently frozen funds" outcome reachable from a single transaction/relayer call, matching the required impact bar (unauthorized value movement is not applicable here, but permanent freezing of user funds is explicitly an accepted impact class).

### Likelihood Explanation
The wallet contract is explicitly documented as a "temporary (placeholder) implementation ... Must not use in production!" [5](#0-4) , which lowers current real-world exposure. However, the underlying trigger — a relayer or user constructing (intentionally or not) a transaction path whose callback gas requirement exceeds the hardcoded `*_CALLBACK_GAS` constants (e.g., the `PromiseResult::Failed` refund-batch branch, or the extra nested dispatch in `address_check_callback`/`nep_141_storage_balance_callback`) — requires only a single signed transaction from an unprivileged relayer/signer, with no special privileges needed, making it straightforward to reach once the contract is deployed for real accounts.

### Recommendation
Do not rely on a single boolean cleared only inside gas-constrained callbacks as the sole guard for a stateful "in-flight" invariant. Either: (1) increase and validate the static gas attached to every callback to provably cover its worst-case execution path (including nested callback dispatch and refund-batch creation), with a safety margin; (2) add an explicit recovery/reset method (analogous to Trader Joe's fix of allowing withdrawal in `emergencyWithdraw()`) that can be safely invoked to clear a stuck `has_in_flight_tx` after a bounded timeout, gated by appropriate access control (e.g., only the account's own key) so funds can never become unconditionally unrecoverable; and (3) add integration tests that deliberately underfund a callback's gas to confirm the flag is not left permanently stuck.

### Proof of Concept
1. Deploy the wallet contract for an eth-implicit account and fund it, as in `test_wallet_contract_interaction` [6](#0-5) .
2. Submit an RLP-encoded Ethereum transaction via `rlp_execute` whose resulting NEAR action routes through `nep_141_storage_balance_callback` or triggers the `PromiseResult::Failed` refund branch of `rlp_execute_callback`, while attaching only the minimum gas required for the happy path so the callback's fixed `RLP_EXECUTE_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget is insufficient for the actual (failure-path) execution cost.
3. Observe the callback receipt fails with an out-of-gas error; per NEAR runtime semantics all state writes from that failed receipt — including the `self.has_in_flight_tx = false` reset — are rolled back, leaving `has_in_flight_tx == true` in contract state.
4. Submit any subsequent `rlp_execute` call (even from a legitimate signer/relayer): it is immediately rejected with `"Error: transaction already in progress, please try again later."` [7](#0-6) , and this rejection persists forever since no other method can clear the flag, permanently freezing the account's funds.
