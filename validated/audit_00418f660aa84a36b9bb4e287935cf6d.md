## Title
`LiquidityCap` in `TokenConfig` is stored but never enforced before `depositPRC20Token` mints unbounded PRC20 supply - (File: `x/uexecutor/keeper/handler.go`)

### Summary
`uregistry.TokenConfig` carries a `LiquidityCap` field documented as the "max supply cap" for each bridged token's PRC20 representation [1](#0-0) , and `ValidateBasic` requires it to be non-empty at registration time [2](#0-1) . However, in the actual inbound-funds execution path that mints PRC20 tokens into a recipient, `depositPRC20` reads the token config only to fetch the `NativeRepresentation.ContractAddress` and parses the inbound amount, then calls `CallPRC20Deposit` unconditionally, with no comparison of `LiquidityCap` against the token's current or resulting total supply [3](#0-2) .

### Finding Description
`CallPRC20Deposit` performs a `DerivedEVMCall` to `depositPRC20Token` on `UniversalCore` unconditionally, minting the full inbound amount to the recipient with no cap check performed by `x/uexecutor` before issuing the call [4](#0-3) . This deposit path is invoked from every inbound execution flow that mints funds — plain `FUNDS`, `FUNDS_AND_PAYLOAD` (both UEA and non-UEA/CEA branches), Solana inbound, and synthetic-bridge inbound — all of which call `depositPRC20` directly with the raw inbound amount [5](#0-4) [6](#0-5) .

The `LiquidityCap` value is validated as non-empty on registration and update messages [7](#0-6) , giving the impression that it is an enforced accounting invariant, but grep across the entire repository (`x/uexecutor`, `x/uregistry` keeper code, and the `UNIVERSAL_CORE_ABI`/PRC20 Solidity ABI definitions used by the module) finds `LiquidityCap`/`liquidity_cap`/`liquidityCap` used only in protobuf marshal/unmarshal code and test fixtures — never read by any keeper function that performs or authorizes a mint. The `depositPRC20Token` ABI exposed to the module has no cap parameter and no revert-on-cap-exceeded semantics visible from the Go-side integration [8](#0-7) .

This is the direct native analog of the C4 finding: in the audited report, a `maxCap` check existed but was computed against the wrong (pre-fee) amount, letting `totalSupply` exceed `maxCap` once fees were applied. Here the situation is more severe — the analogous quantity (`LiquidityCap`) is defined per-token in the registry but is not read at all by the minting code path, so there is no enforcement whatsoever, not even a flawed one.

### Impact Explanation
Any attacker who can get an inbound observed and voted to quorum by honest Universal Validators (i.e. any real deposit event on a supported source chain, or via CEA-controlled payload configurations reachable by ordinary users) can cause PRC20 tokens to be minted without regard to the configured `LiquidityCap`. Because the field is explicitly named "max supply cap" and required to be set for every registered token, its absence of enforcement breaks the accounting invariant that PRC20 supply on Push Chain should be bounded relative to backing liquidity/collateral on the source chain. Depending on how downstream systems (AMM pools, swap quoting via `GetDefaultFeeTierForToken`/`getSwapQuoteForRefund`, collateral-backed redemption assumptions) rely on this cap, uncapped minting could allow disproportionate draining of pooled liquidity or PRC20/native asset accounting corruption once redeemed against a fixed pool of backing collateral.

### Likelihood Explanation
High reachability: every FUNDS-bearing inbound flow (`FUNDS`, `FUNDS_AND_PAYLOAD`, Solana, synthetic bridge, CEA variants) goes through `depositPRC20`/`CallPRC20Deposit` unconditionally once quorum is reached by honest validators observing genuine external-chain deposits — no privileged action or malicious validator/relayer is required. The trigger is simply repeated ordinary deposits (or repeated votes on distinct, legitimately-observed inbound events) whose cumulative minted amount exceeds `LiquidityCap`, exactly mirroring how the original bug is triggered by ordinary pool joins.

### Recommendation
Before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`, look up the token's current on-chain PRC20 `totalSupply()` (or track cumulative minted PRC20 amount per token in `x/uregistry`/`x/uexecutor` state) and compare `currentSupply + amount` against `tokenConfig.LiquidityCap` before minting. If the cap would be exceeded, fail the deposit (recording a `FAILED` `PCTx` and triggering the existing revert/rescue path) rather than minting past the configured cap. This check should be performed inside `depositPRC20` in `x/uexecutor/keeper/handler.go` prior to invoking `CallPRC20Deposit`, using the already-fetched `tokenConfig.LiquidityCap`.

### Proof of Concept
1. Register a `TokenConfig` for chain `eip155:11155111` / asset `USDC` with `LiquidityCap = "1000000"` (as in the test fixtures) [9](#0-8) .
2. Submit and vote to quorum (3-of-4 honest validators) two or more legitimate `FUNDS` inbounds each with `Amount` close to `LiquidityCap`, e.g. as done in `TestSolanaInboundFunds`'s "multiple ... inbounds accumulate balance" case, which explicitly demonstrates unrestricted balance accumulation across separate inbound votes with no cap check anywhere in the flow [10](#0-9) .
3. Observe that `balanceOf(recipient)` (and hence total minted PRC20 supply) grows without any rejection once the sum exceeds the registered `LiquidityCap`, confirming no cap enforcement exists in the mint path.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
