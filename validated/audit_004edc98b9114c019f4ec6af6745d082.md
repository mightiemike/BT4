### Title
Attacker-controlled CEA recipient contract executes with no enforced gas-limit bound, letting an unprivileged attacker force uncompensated computation cost onto the protocol - ([File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go])

### Summary
The UniswapX report describes fillers being forced to fund arbitrary, gas-intensive callback execution triggered by an attacker (the swapper) with no prior chance to bound or refuse the cost, and only a weak, after-the-fact recovery mechanism. The Push Chain analog is the `isCEA` "smart contract recipient" path of inbound execution: `x/uexecutor` calls `executeUniversalTx` on an attacker-deployed, fully arbitrary EVM contract via `CallExecuteUniversalTx`, with `gasLimit=nil` and no attacker-independent bound, while the only cost-recovery mechanism (`DeductGasFeesFromReceipt`) is a post-hoc balance check on the recipient itself that fails openly and cheaply if the recipient simply holds no `upc`.

### Finding Description
For `FUNDS_AND_PAYLOAD` / `GAS_AND_PAYLOAD` inbounds where `IsCEA` is true and the recipient is a deployed, non-UEA smart contract (attacker's own bytecode, detected purely by `GetCodeHash`), the keeper calls into it directly: [1](#0-0) 

Execution goes through `CallExecuteUniversalTx`, which issues a `DerivedEVMCall` with `gasLimit=nil`: [2](#0-1) 

Per the module's own documentation, `gasLimit=nil` means "use a sensible default" rather than a value tied to attacker-provided funds or an owner-signed bound: [3](#0-2) 

This is materially different from the UEA payload path, where the gas limit is explicit and taken from the owner's signed `UniversalPayload.GasLimit`, and `DeductGasFeesFromReceipt` cross-checks `gasUsed` against that same signed bound before charging: [4](#0-3) [5](#0-4) 

For the CEA smart-contract path, `DeductGasFeesFromReceipt` is called with `universalPayload = utx.InboundTx.UniversalPayload`, which the attacker fully controls as part of the inbound they trigger (this is not a signature-authenticated, pre-committed bound the way a UEA owner's payload is) — the "gasLimit exceeded" check at `fees.go:130-132` only protects against exceeding whatever the attacker themselves declared, not a network-enforced ceiling independent of the attacker: [6](#0-5) 

The EVM call and fee deduction are wrapped in a `CacheContext`, so a failed fee deduction (e.g., because the malicious contract holds zero `upc`) discards state effects of the contract call, but this rollback happens only after the module has already dispatched the real, `commit=true` derived EVM transaction and paid the corresponding EVM execution cost: [7](#0-6) 

This mirrors the UniswapX bug class exactly: the party that must fund arbitrary attacker-chosen computation (the module/protocol, standing in for the "filler") has no meaningful opportunity to bound or refuse the cost *before* it is incurred, and the only recourse (`DeductGasFeesFromReceipt`) is a downstream balance check that the attacker trivially defeats by keeping the recipient contract's `upc` balance at zero — exactly like a malicious ERC-20/swapper defeating a filler's post-hoc recovery via a hostile `transferFrom` callback.

### Impact Explanation
An unprivileged attacker can deploy a contract whose `executeUniversalTx` entry point performs maximal, gas-intensive computation (loops, storage writes, nested calls) up to whatever the fork's undocumented default `gasLimit` allows, then trigger a minimal-value cross-chain inbound (`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD`, `isCEA=true`) that honest Universal Validators will legitimately vote through, since nothing here requires a malicious validator. Once quorum is reached, `x/uexecutor` unconditionally dispatches the attacker's arbitrary bytecode on-chain and only afterwards attempts to recover the incurred gas cost from the same attacker-controlled contract, which the attacker can guarantee has no funds. This forces the protocol/validators to repeatedly absorb EVM execution cost for attacker-chosen, worst-case computation with no assurance of reimbursement, for the cost of only a minimal token deposit (or none, since `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` explicitly allow zero-amount inbounds to still execute the payload).

### Likelihood Explanation
The trigger requires only: (1) deploying an ordinary EVM contract, and (2) submitting a cheap/zero-value cross-chain deposit that is routed through the standard, unprivileged inbound-voting flow — no validator collusion, admin action, or key compromise is needed. This is directly reachable from default user transaction submission paths, matching the "ordinary user deposits/payloads/contracts" trigger class called out in the scope.

### Recommendation
- Enforce a protocol-defined, attacker-independent maximum `gasLimit` for `CallExecuteUniversalTx` (not `nil`/default-from-fork), scaled to what can reasonably be recovered, rather than trusting attacker-supplied `UniversalPayload.GasLimit` for the CEA smart-contract-recipient path.
- Require and verify a minimum `upc` balance (or bonded escrow) on the recipient contract before dispatching `executeUniversalTx`, so cost recovery is not a discretionary post-hoc check the attacker can trivially defeat.
- Consider metering/pricing the CEA smart-contract-recipient call against the bridged deposit amount itself, so the attacker cannot decouple the cost of computation from the value they are willing to put at risk.

### Proof of Concept
1. Attacker deploys `MaliciousRecipient` on Push Chain EVM with `executeUniversalTx(...)` implementing a gas-heavy loop/storage-write pattern, and ensures the contract's `upc` balance is zero.
2. Attacker triggers a source-chain gateway event that Universal Validators observe and vote as an `Inbound` with `TxType=GAS_AND_PAYLOAD` or `FUNDS_AND_PAYLOAD`, `IsCEA=true`, `Recipient=MaliciousRecipient`, and `Amount` at or near zero (permitted by `ValidateForExecution`, see [8](#0-7) ).
3. Once quorum is reached, `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` detects the non-UEA recipient has code (`isSmartContract=true`) and calls `CallExecuteUniversalTx` with `gasLimit=nil`, executing the attacker's expensive bytecode as a real, committed derived EVM transaction.
4. `DeductGasFeesFromReceipt` attempts to bill the recipient's zero balance and fails; the `CacheContext` discards the contract's storage effects, but the underlying EVM computation for that block has already been performed by every validator, with no compensating value received by the protocol.
5. Repeating this with new minimal-cost inbounds lets the attacker impose recurring, uncompensated computation cost, bounded only by the fork's undocumented default `gasLimit` (whose exact magnitude could not be verified in this repository, since `DerivedEVMCall`'s nil-gasLimit default lives in the external `github.com/pushchain/evm` fork).

```go
// CallExecuteUniversalTx calls executeUniversalTx on a smart-contract recipient.
// This is used for isCEA inbounds whose recipient is a deployed contract (not a UEA).
func (k Keeper) CallExecuteUniversalTx(
	ctx sdk.Context,
	recipientAddr common.Address,
	sourceChain string,
	ceaAddress []byte,
	payload []byte,
	amount *big.Int,
	prc20AssetAddr common.Address,
	txId [32]byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	recipientABI, err := types.ParseRecipientContractABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse recipient contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		recipientABI,
		ueModuleAccAddress,
		recipientAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"executeUniversalTx",
		sourceChain,
		ceaAddress,
		payload,
		amount,
		prc20AssetAddr,
		txId,
	)
}
```
