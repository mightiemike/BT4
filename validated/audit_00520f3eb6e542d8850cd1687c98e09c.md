### Title
`ProposalStore.get` throws uncaught NullPointerException on nonexistent proposal IDs, reachable via public `GetProposalById` RPC - (File: `chainbase/src/main/java/org/tron/core/store/ProposalStore.java`)

### Summary
`ProposalStore.get(byte[] key)` never checks whether `revokingDB.get(key)` returned `null` before passing the value into `new ProposalCapsule(value)`, and `ProposalCapsule`'s byte-array constructor calls `Proposal.parseFrom(data)` which throws a raw `NullPointerException` (not `InvalidProtocolBufferException`) when `data` is `null`. This is directly reachable by any unprivileged client calling the public `GetProposalById` gRPC method with an ID that does not exist in the store.

### Finding Description
`ProposalStore.get` is declared to throw `ItemNotFoundException` but its implementation skips that check entirely: [1](#0-0) 

`ProposalCapsule`'s byte-array constructor only catches `InvalidProtocolBufferException`: [2](#0-1) 

Because `Proposal.parseFrom(null)` (via `CodedInputStream.newInstance(byte[])`) dereferences `data.length` before any protobuf parsing logic runs, it throws a plain `NullPointerException`, which is *not* an `InvalidProtocolBufferException` and therefore propagates out of the constructor unhandled.

The public entrypoint `Wallet.getProposalById` only catches `StoreException`, which `NullPointerException` does not extend: [3](#0-2) 

This is invoked directly from the gRPC-exposed `GetProposalById` handler in `RpcApiService`, with no additional exception handling: [4](#0-3) 

An unprivileged attacker simply queries any proposal ID that was never created (or has been pruned/rolled back) — e.g. ID `0`, or any ID greater than `getLatestProposalNum` — causing `revokingDB.get(key)` to return `null` and triggering the NPE inside the RPC handler thread. Note that the sibling method `Wallet.getPaginatedProposalList` wraps the same `ProposalStore.get` call in a generic `catch (Exception ex)`, showing the codebase is aware `get` can throw unexpected runtime exceptions on missing keys, but `getProposalById` (and the `GetProposalById` RPC) was not given the same protection: [5](#0-4) 

### Impact Explanation
Every call to the public `GetProposalById` RPC with a nonexistent proposal ID throws an unhandled `NullPointerException` inside the request-handling code path instead of the intended `ItemNotFoundException`/graceful "not found" response. gRPC's server-side call dispatch will typically catch this at the framework level and return an `INTERNAL`/`UNKNOWN` error status to the caller rather than crashing the whole node process, so the primary confirmed impact is: incorrect API behavior (violates the "not found" contract), log noise, and unnecessary exception overhead on every miss. Repeated concurrent invocation with invalid/out-of-range IDs could add load/latency to the RPC service, but there is no evidence in the reachable code that this crashes the entire server process or corrupts state.

### Likelihood Explanation
Trivially reproducible: any client can call `GetProposalById` with an ID it knows or guesses does not exist (e.g. `0`, or a value beyond `getLatestProposalNum`) without needing to race a concurrent rollback. No authentication or special privileges are required, since this is a plain read-only public gRPC API.

### Recommendation
Add a null check in `ProposalStore.get` and throw `ItemNotFoundException` explicitly when `revokingDB.get(key)` returns `null`, consistent with other stores' `get` overrides (e.g. mirroring the pattern used in `TransactionStore`/base `TronStoreWithRevoking.get`), for example:
```java
@Override
public ProposalCapsule get(byte[] key) throws ItemNotFoundException {
  byte[] value = revokingDB.get(key);
  if (value == null) {
    throw new ItemNotFoundException("proposal not found");
  }
  return new ProposalCapsule(value);
}
```
This restores the documented contract (`throws ItemNotFoundException`) and lets `Wallet.getProposalById`'s existing `catch (StoreException e)` correctly convert it into a `null`/not-found response.

Expected today: the first test fails because `NullPointerException` is thrown instead of `ItemNotFoundException`, and (depending on gRPC's internal exception wrapping) the RPC call returns an error status rather than the documented empty/not-found `Proposal` response.
