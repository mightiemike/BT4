## Title
Gas-key `FunctionCall`-restricted transactions bypass receiver/method/deposit permission checks - (File: `runtime/runtime/src/verifier.rs`)

### Summary
A `FunctionCall`-restricted access key is meant to lock a key holder to one receiver account, an allow-list of method names, and zero deposit <cite repo="patrichyt/nearcore--011" path="runtime/runtime/src/verifier.rs" start="204="211" end="251" />. For **regular** transactions this restriction is enforced by `verify_and_charge_tx_ephemeral`, which explicitly calls `verify_function_call_permission` before accepting the transaction [1](#0-0) . The same `FunctionCallPermission` struct is also legal on a **gas key** (`GasKeyFunctionCall(GasKeyInfo, FunctionCallPermission)`) — the only extra rule `validate_add_key_action` enforces for a gas key is that its `allowance` must be `None`; the `receiver_id`/`method_names` restriction fields are otherwise unrestricted and are expected to still apply [2](#0-1) . However, the gas-key transaction verifier, `verify_and_charge_gas_key_tx_ephemeral`, only validates that the key is a gas key, that the `nonce_index` is in range, and that the gas/deposit cost split against the gas-key balance and account balance succeeds — it never calls `verify_function_call_permission` [3](#0-2) . This mirrors the documented behavior in the accounts-keys protocol-model spec, which itemizes exactly which checks the gas-key path performs (nonce-index, gas-key balance split, deposit split, `DepositFailed`) with no `FunctionCall permission` step, in contrast to the regular path where that step is called out explicitly [4](#0-3) .

### Finding Description
This is directly analogous to the reported `AccessTokenContract.sol` bug: two entry points exist for the same conceptual action (spending through a `FunctionCallPermission`-restricted key), one path (`paidMint`/regular tx) enforces the restriction, the other (`referralMint`/gas-key tx) does not, letting the caller obtain a more favorable outcome than the restriction was designed to allow.

Concretely, an app or user can create a gas key intending it to be restricted (e.g. `receiver_id = "my-dapp.near"`, `method_names = ["safe_method"]`, zero allowance as required for gas keys) via `AddKey`/`action_add_gas_key`, believing the restriction will be enforced the same way it is for regular `FunctionCall` access keys [5](#0-4) . Because gas-key transactions must go through `verify_and_charge_gas_key_tx_ephemeral` instead of `verify_and_charge_tx_ephemeral` [6](#0-5) , and that function never validates `receiver_id`, `method_names`, or the zero-deposit rule, the holder of the gas key can sign a transaction to **any** receiver, calling **any** method, and even attach a deposit (drawn from the account's own balance via the `deposit_cost` split) [7](#0-6) . The restriction that the key issuer relied on to scope the key's blast radius is silently bypassed simply by using the gas-key nonce path instead of the regular path.

### Impact Explanation
Any account that issues a restricted `GasKeyFunctionCall` key to a less-trusted party (a common pattern for session keys / delegated dApp access, analogous to `referralMint` bypassing `paidMint`'s `winChance` restriction) loses all the intended containment: the key holder can invoke arbitrary contracts/methods and move funds via deposit-bearing calls charged against the account's own balance, well beyond what the `receiver_id`/`method_names` allow-list was meant to permit. This is an invalid-state-transition/permission-bypass class issue enabling unauthorized value movement out of the owning account.

### Likelihood Explanation
High likelihood of exploitability: the bug requires no privileged access — any account holder who creates (or a relying party who receives) a `GasKeyFunctionCall` key can immediately construct a `TransactionV1` with a `GasKeyNonce` (`nonce_index`) instead of a plain `Nonce` to route around the restriction check. No race condition, timing, or validator collusion is needed; it is a straightforward missing-check in a public, transaction-admission code path reachable by any signer.

### Recommendation
Call `verify_function_call_permission` (or an equivalent check enforcing `receiver_id`, `method_names`, and zero-deposit) from `verify_and_charge_gas_key_tx_ephemeral` whenever `access_key.permission.function_call_permission()` is `Some`, mirroring the check already performed in `verify_and_charge_tx_ephemeral`. Add regression tests (in `test-loop-tests/src/tests/gas_keys.rs`) covering: gas key with restricted `receiver_id` used against a different receiver, restricted `method_names` used with a disallowed method, and a nonzero deposit attached to a `FunctionCall` gas-key transaction, all of which should be rejected.

### Proof of Concept
1. Account `alice.near` adds a gas key with `AccessKey::gas_key_function_call(num_nonces, FunctionCallPermission { allowance: None, receiver_id: "dapp.near", method_names: ["safe_method"] })` via `action_add_key`/`action_add_gas_key` [5](#0-4) .
2. `alice.near` funds the gas key via `TransferToGasKey` so it has a spendable `balance` [8](#0-7) .
3. The key holder signs a `TransactionV1` using `TransactionNonce::GasKeyNonce { nonce, nonce_index }` targeting `evil.near::drain()` with a non-zero deposit, instead of `dapp.near::safe_method`.
4. This transaction is verified through `verify_and_charge_gas_key_tx_ephemeral`, which checks only gas-key-ness, nonce-index range, nonce validity, and the gas/deposit balance split [9](#0-8)  — never checking `receiver_id`, `method_names`, or the zero-deposit rule — so the transaction succeeds despite violating the key's stated `FunctionCallPermission` restriction, unlike the equivalent regular-key transaction which would be rejected by `verify_function_call_permission` at `verifier.rs:388-393`.
