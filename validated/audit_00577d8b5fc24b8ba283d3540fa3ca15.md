### Title
`BuildOutboundsFromReceipt` aborts *all* outbounds in a multi-outbound payload execution when any single destination chain has outbound disabled - ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
`BuildOutboundsFromReceipt` iterates over every `UniversalTxOutbound` gateway log in a single EVM receipt and, for each one, checks `IsChainOutboundEnabled` for that log's destination chain. The moment it hits one log whose destination chain has outbound disabled, it returns a hard error and discards the entire in-progress `outbounds` slice — including any outbounds to other, fully-enabled destination chains that were already built earlier in the same loop.

### Finding Description
`BuildOutboundsFromReceipt` builds outbounds by walking `receipt.Logs` for `UniversalTxOutboundEventSig` events emitted by the gateway contract: [1](#0-0) 

For each decoded event it calls `k.uregistryKeeper.IsChainOutboundEnabled(ctx, event.ChainId)` and, if disabled, returns `nil, error` immediately — discarding the local `outbounds` slice that may already contain entries appended from earlier iterations of the same loop: [2](#0-1) 

This is the same bug class as the reported `LiqFacet::removeLiq` issue: a loop over multiple independent per-destination resources (vaults in the original report; destination chains here) where one item being "paused"/disabled aborts the whole batch instead of skipping just that item.

The function is invoked from both `AttachOutboundsToExistingUniversalTx` (used after inbound `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` execution) and `CreateUniversalTxFromReceiptIfOutbound` (used from `MsgExecutePayload`/EVM hooks), both of which propagate the error straight up without partial handling: [3](#0-2) 

In `ExecuteInboundFundsAndPayload`, a failure from `AttachOutboundsToExistingUniversalTx` is only recorded as `RevertError` on the UTX record — it does not create any outbound at all (not even for the enabled destination chains) and does not trigger a fund-revert path for the already-minted/committed synthetic tokens: [4](#0-3) 

Confirmed test coverage for the single-outbound disabled case shows the UTX is still created but with `OutboundTx` left empty — the pattern the multi-outbound case inherits, except in the multi-outbound case *legitimate* outbounds to enabled chains are also silently dropped: [5](#0-4) 

### Impact Explanation
A single user-triggered UEA payload that fans out into multiple destination-chain outbounds (e.g., a multi-hop swap or batched transfer as described in the module docs: "one inbound's payload can spawn multiple outbounds") can have its execution silently record zero outbounds if just one of the N destination chains has outbound disabled by an admin (a normal, expected registry operation independent of the user's action). The bridged/synthetic funds that were already minted on Push Chain during the inbound execution are not reverted (no revert outbound is generated by this failure path — only `RevertError` string metadata is set), and the outbounds destined for chains that *were* enabled are never created or indexed into `PendingOutbounds`. This causes a form of fund immobilization/loss-of-liveness for the unprivileged user: their crosschain-payload funds are stuck on Push Chain with no outbound path and no automatic revert, requiring manual/admin intervention. This matches the "Medium" impact class of the seed report (temporary loss of user funds/liquidity due to a batch operation being blocked by one disabled/paused sub-resource).

### Likelihood Explanation
Likelihood is Medium: it requires a chain to have `IsOutboundEnabled=false` (an admin-controlled, but externally-observable and legitimate registry state — chains can be disabled for maintenance, incident response, etc.) at the moment an unprivileged user's multi-destination payload executes. Any UEA payload that produces more than one `UniversalTxOutbound` event where at least one target chain is outbound-disabled will trigger this — an ordinary, non-privileged user action (submitting a normal cross-chain payload) is sufficient to hit the bug; no malicious validator or admin collusion is required.

### Recommendation
In `BuildOutboundsFromReceipt`, do not abort the whole loop when one destination chain is outbound-disabled. Instead, skip that individual log (optionally recording it for a later refund/revert path) and continue building outbounds for the remaining, enabled destination chains, e.g.:
```go
if !outboundEnabled {
    k.Logger().Warn("outbound disabled for chain, skipping this outbound", "chain_id", event.ChainId, "utx_id", utxId)
    continue // instead of return nil, err
}
```
Additionally, consider surfacing the skipped/disabled outbound events so that the corresponding bridged funds are routed through a revert/refund path rather than being silently stuck with only a `RevertError` string attached to the UTX.

### Proof of Concept
1. Admin registers two enabled destination chains, A and B, via `uregistry`.
2. A user submits `MsgExecutePayload` (or triggers `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` inbound execution) whose UEA logic emits two `UniversalTxOutbound` gateway events in the same receipt: one targeting chain A, one targeting chain B.
3. Admin (independently, for unrelated maintenance reasons) sets chain B's `Enabled.IsOutboundEnabled = false` via `MsgUpdateChainConfig` before this transaction executes (or the payload happens to target a chain that is currently disabled).
4. `BuildOutboundsFromReceipt` processes chain A's log first, appends an outbound to the local `outbounds` slice, then processes chain B's log, finds `IsChainOutboundEnabled` is `false`, and returns `nil, error` — discarding chain A's already-built outbound.
5. `AttachOutboundsToExistingUniversalTx` propagates the error; `ExecuteInboundFundsAndPayload` records only `utx.RevertError` and creates zero outbounds. The user's synthetic funds intended for chain A (whose outbound was perfectly valid) are never released, with no automatic revert triggered by this failure path.

func (k Keeper) BuildOutboundsFromReceipt(
	ctx context.Context,
	utxId string,
	receipt *evmtypes.MsgEthereumTxResponse,
) ([]*types.OutboundTx, error) {

	outbounds := []*types.OutboundTx{}
	universalGatewayPC := strings.ToLower(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_GATEWAY_PC"].Address)

	k.Logger().Debug("building outbounds from receipt", "utx_id", utxId, "tx_hash", receipt.Hash, "log_count", len(receipt.Logs))

	for _, lg := range receipt.Logs {
		if lg.Removed {
			continue
		}

		if strings.ToLower(lg.Address) != universalGatewayPC {
			continue
		}

		if len(lg.Topics) == 0 {
			continue
		}

		if strings.ToLower(lg.Topics[0]) != strings.ToLower(types.UniversalTxOutboundEventSig) {
			continue
		}

		event, err := types.DecodeUniversalTxOutboundFromLog(lg)
		if err != nil {
			return nil, fmt.Errorf("failed to decode UniversalTxWithdraw: %w", err)
		}

		// Check if outbound is enabled for the destination chain
		outboundEnabled, err := k.uregistryKeeper.IsChainOutboundEnabled(ctx, event.ChainId)
		if err != nil {
			return nil, fmt.Errorf("failed to check outbound enabled for chain %s: %w", event.ChainId, err)
		}
		if !outboundEnabled {
			k.Logger().Warn("outbound disabled for chain", "chain_id", event.ChainId, "utx_id", utxId)
			return nil, fmt.Errorf("outbound is disabled for chain %s", event.ChainId)
		}

// AttachOutboundsToExistingUniversalTx
// Used when UniversalTx already exists (e.g. inbound execution)
// It attaches outbounds extracted from receipt to the existing utx.
func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}

// CreateUniversalTxFromReceiptIfOutbound
// Creates a UniversalTx ONLY if outbound events exist in the receipt.
// Safe to call from ExecutePayload, EVM hooks
func (k Keeper) CreateUniversalTxFromReceiptIfOutbound(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalTxKey, err := k.BuildPcUniversalTxKey(ctx, pcTx)
	if err != nil {
		return errors.Wrap(err, "failed to create UniversalTx key")
	}

	outbounds, err := k.BuildOutboundsFromReceipt(ctx, universalTxKey, receipt)
	if err != nil {
		return err
	}

	if len(outbounds) == 0 {
		return nil
	}

	utx, err := k.CreateUniversalTxFromPCTx(ctx, pcTx)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
