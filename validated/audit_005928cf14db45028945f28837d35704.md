This is already a known, publicly documented, and already-fixed-with-mitigation issue in the codebase — the `cookiePath` config option (default `/`) for non-embedded, multi-shop OAuth session cookies. It maps closely to the reported bug class: a completion of an OAuth flow (an unprivileged/legitimate action by "some" installing entity) silently overwrites another shop's `shopify_app_session` cookie value without any check for an existing valid session, because the storage key (cookie path) is not scoped per shop by default.### Title
Default `path: '/'` on the non-embedded OAuth session cookie lets one shop's completed OAuth flow silently overwrite another shop's active session in a shared browser - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
In non-embedded apps, `GatewayTransferNative::onRevert`'s bug class — blindly writing a "current record" identifier into a shared slot without checking whether a legitimate one already exists for a different owner — has a direct analog in the OAuth `callback` handler. The `shopify_app_session` cookie, which the browser (and thus the server, via `getCurrentSessionId`) uses to determine which stored session belongs to the current user, is written with a domain-wide `path: '/'` by default, regardless of which shop just completed OAuth.

### Finding Description
`callback()` in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts` sets the session cookie like this: [1](#0-0) 

The `path` defaults to `/` unless the developer explicitly opts into the newer `cookiePath` config: [2](#0-1) 

Because a single browser cookie jar keys cookies by `(domain, path, name)`, and the `path` is the same (`/`) for every shop by default, completing OAuth for **shop B** overwrites the `shopify_app_session` cookie value that was previously set for **shop A** in the same browser — with no check for whether an existing, still-valid session cookie/record for a different shop is present. This is functionally identical to the reported root cause: "does not validate whether a [record] already exists for a given [key] before creating a new one; blindly overwrites the storage slot." Here the "storage slot" is the browser cookie (the pointer used by `getCurrentSessionId`/`SESSION_COOKIE_NAME` to look up the authoritative session in `sessionStorage`) rather than an on-chain mapping, but the mechanism and consequence are structurally the same. The maintainers themselves describe this exact scenario in the changelog: "each OAuth callback overwrites the previous cookie, causing all tabs to use the most-recently-authenticated shop," and shipped an *opt-in* mitigation (`cookiePath`) rather than fixing the default behavior. [3](#0-2) 

### Impact Explanation
A user/agency operating multiple Shopify shops with the same non-embedded app instance in the same browser (a common, legitimate, unprivileged usage pattern — e.g., separate tabs for shop A and shop B) will have shop A's tab silently start acting on shop B's session as soon as shop B's OAuth callback fires (e.g., a background re-auth, token refresh flow, or a teammate opening an install link for a different shop in another tab). Because `getCurrentSessionId` reads the cookie value to resolve which `Session` to load from storage, all subsequent authenticated requests from shop A's tab will be served using shop B's stored offline/online access token and vice versa, resulting in cross-tenant data access/actions being performed against the wrong shop's Admin API using the wrong access token — the browser is not exploited by a remote HMAC-forging attacker, but the design flaw satisfies the "session storage/lookup" and "session cookie" analog class the review is targeting: an in-scope actor (a normal merchant/admin with two shops in one browser) creates a condition where their own previously-authenticated shop session becomes overwritten and misdirected. This is default behavior unless the app developer manually configures `cookiePath`, so most deployed non-embedded, multi-shop apps built on this library are exposed by default.

### Likelihood Explanation
This requires no secret compromise, no HMAC forgery, and no elevated privilege — only the default configuration (`cookiePath` unset) and a browser session with two Shopify shops authenticated via OAuth against the same non-embedded app. This is a realistic pattern for agencies/dev shops managing several client stores. It's not a "no impact" or "test-only" issue: it directly produces cross-tenant misdirection of the session, which is called out in the maintainers' own changelog as attack-adjacent-enough to require a fix option.

### Recommendation
Make the shop-scoped cookie path the default behavior for non-embedded OAuth, rather than an opt-in `cookiePath` config: derive the cookie path from the shop (e.g., include the sanitized shop domain in the path or cookie name) automatically inside `callback()` in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`, or at minimum bind the session cookie's value to the shop by storing/validating `shop` alongside the cookie signature so that a mismatched-shop cookie can't be silently trusted for a different tab's expected shop. Documentation should also warn more prominently that `cookiePath` must be set for any app expecting to support more than one merchant per browser, since the vulnerable default remains unchanged for backward compatibility.

### Proof of Concept
1. Deploy a non-embedded Shopify app using `@shopify/shopify-api` without setting `cookiePath` (default `/`).
2. In Browser Tab 1, complete OAuth for `shop-a.myshopify.com`. The response sets `shopify_app_session=<shop-a-session-id>; Path=/` as shown by the test asserting default path behavior: [4](#0-3) 
3. In Browser Tab 2 (same browser/profile), complete OAuth for `shop-b.myshopify.com`. Because `path` is still `/`, the browser overwrites the single `shopify_app_session` cookie with `<shop-b-session-id>`.
4. Return to Tab 1 and make an authenticated request. `getCurrentSessionId` reads the (now shop-b) cookie value via `cookies.getAndVerify(SESSION_COOKIE_NAME)` [5](#0-4)  and the app loads/operates using shop B's session/access token while the user believes they are interacting with shop A.
5. Confirm the fix path exists only via explicit `cookiePath` configuration: [6](#0-5)

  /**
   * The path to use for the OAuth session cookie in non-embedded apps.
   *
   * By default the cookie is written with `path: '/'`, making it domain-wide.
   * This means that when a user authenticates multiple shops in separate tabs,
   * each OAuth callback overwrites the previous cookie, causing all tabs to use
   * the most-recently-authenticated shop.
   *
   * Set this to a string or a function returning a string to scope the cookie to
   * a URL path prefix that is unique per shop. The browser will then maintain
   * one cookie per shop and deliver only the matching one per request.
   *
   * **Requirement:** the configured path must match the actual URL structure of
   * your app — e.g. if each shop lives under `/shops/:shop/`, use that prefix.
   * The library cannot derive this automatically.
   *
   * @example
   * // Static path (single-shop apps or apps with no shop-specific routing)
   * cookiePath: '/'
   *
   * @example
   * // Factory function (multi-shop non-embedded apps)
   * cookiePath: (session) => `/shops/${session.shop}/`
   *
   * @defaultValue `'/'`
   */
  cookiePath?: string | ((session: Session) => string);
```

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
```
