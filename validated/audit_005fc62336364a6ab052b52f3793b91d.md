## Analysis Result

### Title
Liquidity-index rounding loss is permanently discarded because `last-update` advances on any index change, not per-index - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
`accrue()` recomputes both the borrow index (`index`) and the supply/liquidity index (`lindex`) from a single shared `time-delta` derived from `last-update`, then resets `last-update` to `stacks-block-time` if **either** index changed. Because the liquidity-side multiplier rounds down while the debt-side multiplier rounds up, it is common for the debt index to advance while the liquidity index truncates to no change in the same call. The clock still advances, so the tiny time window that should have kept accruing towards the liquidity index is discarded rather than carried forward — the exact "truncated residual not preserved" bug class described in the external MultiRewards report, mapped onto Zest's shared-clock interest accrual.

### Finding Description
In every vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` counterparts), `accrue()` computes: [1](#0-0) 

```
(next (next-index))
(nliq (next-liquidity-index))
...
(if (not (is-eq idx next)) (var-set index next) false)
(if (not (is-eq lidx nliq)) (var-set lindex nliq) false)
...
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
```

Both `next-index` and `next-liquidity-index` derive their multiplier from the **same** `time-delta`: [2](#0-1) 

The borrow-index multiplier rounds *up* (`mul-div-up`, `round-up true`), while the liquidity-index multiplier rounds *down* (`mul-div-down`, `round-up false`), and the liquidity rate itself is derived from two additional down-rounding `mul-bps-down` steps (utilization applied, then reserve-factor applied): [3](#0-2) 

Because the liquidity-side value is smaller and passes through more down-rounding stages than the debt-side value, it is straightforward for `next-index` to differ from `idx` (interest accrued to debt) while `next-liquidity-index` truncates to exactly `lidx` (no supply-side growth) in the same call. When that happens, the `or` condition is still true (because the debt index changed), so `last-update` is reset to `stacks-block-time`. The elapsed `time-delta` that "almost" produced a liquidity-index increment is lost forever — the next `accrue()` call starts its `time-delta` calculation from the new `last-update`, with no record that a fractional/truncated liquidity-interest window was skipped. This is a per-call, single-transaction precision loss with no residual/carry-over mechanism, mirroring the report's core defect: truncation from a division (`leftover / rewardsDuration` in the analog; `mul-div-down` on the liquidity multiplier here) is not accounted for anywhere before the "clock" moves on.

### Impact Explanation
Every time this asymmetric rounding occurs, suppliers permanently lose the small amount of yield that should have accrued to `lindex` for that time window — this is unclaimed-yield loss, since the interest is silently dropped rather than merely delayed (the clock that measures it has already moved). Any individual occurrence is small, matching the "Low" impact rated in the external analog, but it recurs on essentially every `accrue()` invocation where the borrow side ticks but the liquidity side is truncated to zero.

### Likelihood Explanation
High. `accrue()` is invoked on nearly every vault interaction (`deposit`, `redeem`, `system-borrow`, `system-repay`, `market.clar`'s `accrue-and-cache`), and low-utilization or low-reserve-factor conditions combined with short inter-transaction time deltas make it easy for the down-rounded liquidity multiplier to resolve to `INDEX-PRECISION` (no change) while the up-rounded debt multiplier still increments. This can happen on essentially every call under normal, permissionless usage — no privileged action or DAO compromise is required.

### Recommendation
Decouple `last-update` from the combined `or` condition, or track a separate accrual checkpoint per index (`index` vs `lindex`), so that a period during which the liquidity index rounds down to no change is not discarded. Alternatively, maintain a residual/carry-over accumulator for the liquidity-rate calculation (analogous to `rewardResidual` in the referenced fix) so that truncated fractional liquidity interest compounds into future accruals instead of being lost when `last-update` advances.

### Proof of Concept
1. Vault starts with `index = lindex = INDEX-PRECISION`, `last-update = T0`, a positive `fee-reserve`, and low `utilization`/`rate` such that the liquidity-rate is very small.
2. A user calls any vault entry point that triggers `accrue()` (e.g., `deposit`) shortly after `T0`, so `time-delta` is small.
3. In `next-index`, `mul-div-up` rounds the small `rate * time-delta` product up, producing `next-index != idx` (debt index ticks up by at least 1).
4. In `next-liquidity-index`, the smaller `liquidity-rate` combined with `mul-div-down` (three down-rounding stages: two `mul-bps-down` plus the final `mul-div-down` in `calc-index-next`) resolves to exactly `INDEX-PRECISION`, so `nliq == lidx` (no change).
5. In `accrue()`, since `idx != next`, `(var-set index next)` executes and, critically, `(var-set last-update stacks-block-time)` also executes because of the `or` — even though `lidx` did not change.
6. The time window `[T0, stacks-block-time]` that almost produced supply-side interest is now unrecoverable: the next `accrue()` call computes `time-delta` from the new `last-update`, with no memory of the truncated liquidity-interest fraction from step 4.
7. Repeating steps 2-6 on every subsequent transaction accumulates a systematic, permanent shortfall in supplier yield relative to what the protocol's own interest-rate model implies should have accrued. [4](#0-3) [5](#0-4)
