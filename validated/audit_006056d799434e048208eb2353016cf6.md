### Title
Relayer fee refund is sent unconditionally, without confirming the underlying user action succeeded - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
In `inner_rlp_execute`, when an emulated Ethereum base-token or ERC-20 transfer specifies a non-zero relayer `fee`, the Wallet Contract creates a standalone transfer promise to pay that fee to `predecessor_account_id` (the relayer). This promise is created independently of, and is not chained (`.then`) to, the promise that actually performs the user's requested action (the base-token transfer or `ft_transfer`). The code never checks/awaits the success of the user's action before dispatching the fee payment. [1](#0-0) 

### Finding Description
The fee-refund logic reads:
```rust
if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { fee, .. })
| TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) = &transaction_kind
{
    if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
        let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
        env::promise_batch_action_transfer(refund_promise, *fee);
    }
}
``` [1](#0-0) 

This `refund_promise` is a brand-new root promise, scheduled as an independent outgoing receipt from the function call, completely separate from the `promise` variable computed later in the same function that performs the actual transfer/`ft_transfer` and is chained with `.then(ext.rlp_execute_callback(caller_deposit))`: [2](#0-1) 

Because the two receipts are independent, the fee payment is not conditioned on the success of the accompanying user action. If the ERC-20 `ft_transfer` (or the base-token transfer) subsequently fails — for example the token contract panics due to insufficient balance, the token contract itself is malicious/misbehaving, or the base-token transfer runs out of gas/attached balance — the relayer nonetheless receives the fee, because the transfer of the fee was never gated on (nor does it check) the return/execution status of the paired action. This is directly analogous to the referenced Sherlock finding: a value-moving external call/action's outcome (`deposit` returning `bool` in the Olympus report; the paired transfer/`ft_transfer` action succeeding in nearcore) is never checked before the code proceeds to treat the operation as successful and irreversibly move value (paying the fee).

### Impact Explanation
This allows relayers to collect fees for transactions that never actually executed on behalf of the user. Because the user's tokens for the fee are deducted up-front (via `CallerDeposit`/attached deposit accounting) while the corresponding action may fail independently, this results in unauthorized value transfer to the relayer without delivering the service (the transaction execution) the fee was meant to pay for. This meets the "concrete unauthorized value movement" bar since NEAR-token or fee funds move to the relayer even when the paired action the fee was for did not succeed.

### Likelihood Explanation
This path is reachable by any relayer (a normal, unprivileged party) submitting `rlp_execute` with an `EOABaseTokenTransfer` or `ERC20Transfer` transaction kind that specifies a non-zero `fee`, targeting a token contract or account that can be made to fail after the fee-transfer receipt is already dispatched (e.g., a token contract that reverts on `ft_transfer` for insufficient balance, paused state, or blacklist). No special privileges beyond being able to call `rlp_execute` (which is meant to be permissionless for any relayer per the code's own comments) are required, making the likelihood high given it's part of the normal emulated-transfer flow.

### Recommendation
Do not fire the fee-refund transfer as an independent promise. Instead, chain it after the action promise resolves successfully (e.g., attach it in the `rlp_execute_callback`/`nep_141_storage_balance_callback` success branch, or make the fee-payment promise depend on `promise_result`/be part of the `.then()` chain), and only pay the relayer if `PromiseResult::Successful` is observed for the underlying action.

### Proof of Concept
1. A relayer submits an RLP-encoded `ERC20Transfer` transaction via `rlp_execute` with a non-zero `fee` for a token contract that will reject the transfer (e.g., the sender's token balance is insufficient, or the token contract is paused).
2. `inner_rlp_execute` unconditionally creates `refund_promise` and calls `env::promise_batch_action_transfer(refund_promise, *fee)` to pay the relayer, per [3](#0-2) .
3. Separately, the actual `ft_transfer` promise chain (via `nep_141_storage_balance_callback` → `rlp_execute_callback`) fails because the token contract panics/reverts.
4. Result: the relayer's fee-payment receipt still executes and succeeds independently, so the relayer is paid even though the user's requested ERC-20 transfer never completed.
