### Title
Missing zero-output check in `deposit` allows share-price rounding to mint 0 shares for a real deposit - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
All Zest v2 tokenized vaults (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`) compute the shares to mint (`inkind`) via `convert-to-shares-preview` and only enforce a slippage floor against `min-out`, without ever asserting that the computed output is non-zero. `redeem` on the same contracts explicitly guards against a zero output (`ERR-OUTPUT-ZERO`), but `deposit` does not, letting a depositor's principal be pulled into the vault while zero shares are minted back.

### Finding Description
`deposit` computes `inkind` before any guard runs and only checks it against `min-out`: [1](#0-0) 

```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (...
      (inkind (convert-to-shares-preview amount)))
    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)
    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    ...
```

Contrast this with `redeem` on the same contract, which explicitly guards the computed output before it is used: [2](#0-1) 

`redeem` asserts `(> inkind u0) ERR-OUTPUT-ZERO` in addition to the slippage check, but `deposit` has no equivalent assertion. The zero-error constant even exists in the same contract but is unused by `deposit`: [3](#0-2) 

`inkind` is derived from `convert-to-shares-preview`, which rounds down and returns `u0` whenever `amount * total-supply / total-assets` truncates to zero (e.g. once the vault's share price rises above 1:1 via accrued interest, and the deposit amount is small relative to that price): [4](#0-3) 

Because a caller who is unaware of the exact share price will typically pass `min-out = 0` (the same failure mode the external report describes for `_minOut`), the assertion `(>= inkind min-out)` becomes `(>= u0 u0)`, which is always true. The deposit therefore proceeds: `receive-underlying` pulls the user's real tokens into the vault, `ft-mint?` mints `0` shares to `recipient`, and `assets` is increased by the full deposited `amount` — with no shares issued to reclaim it.

### Impact Explanation
The depositor's underlying tokens are absorbed into vault `assets` while they receive zero `zft` shares, i.e., no claim to redeem those assets back. This is a permanent loss of the deposited principal for that user (it becomes distributed pro-rata to existing shareholders instead), matching the in-scope "permanent freezing/theft of funds" impact class. Every vault variant in `mainnet/contracts/vault/` shares this identical `deposit` implementation and is affected.

### Likelihood Explanation
This triggers in a single transaction whenever `convert-to-shares-preview(amount)` rounds to zero for the caller's chosen `amount`, which becomes more likely as the vault's share price appreciates (higher `total-assets/total-supply` ratio) and for depositors using small amounts or integrating naively with `min-out = 0`. No coordination with another user or DAO action is required.

### Recommendation
Add `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` to `deposit` in every vault contract, mirroring the existing check already present in `redeem`, so a deposit that would mint zero shares reverts before `receive-underlying`/`ft-mint?` are executed.

### Proof of Concept
1. Vault accrues interest so that `total-assets-preview() / total-supply-preview() > 1` (share price > 1 underlying-unit per share).
2. Attacker/victim calls `deposit(amount, min-out: u0, recipient)` with a small `amount` such that `convert-to-shares-preview(amount)` rounds down to `u0` — see `mainnet/contracts/vault/v0-vault-usdc.clar` lines 761-779 and the rounding logic in `convert-to-shares-preview` (`local-testing/contracts/vault/vault-usdh.clar` lines 310-317).
3. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` evaluates `(>= u0 u0)` → passes.
4. `(try! (receive-underlying amount account))` transfers the depositor's real underlying tokens into the vault.
5. `(try! (ft-mint? zft inkind recipient))` mints `u0` shares to `recipient`.
6. `assets` is increased by `amount`; the depositor has no `zft` balance and cannot redeem the value they deposited.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
