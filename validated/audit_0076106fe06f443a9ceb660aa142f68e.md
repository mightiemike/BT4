### Title
Non-deterministic Mint-Token event indexing due to `latest_state_checkpoint_view` lookups in `EventV2Translator` - (File: storage/indexer/src/event_v2_translator.rs)

### Summary
`MintTokenTranslator` (and its sibling V1 token/collection translators) resolve the on-chain `Collections`/`FixedSupply`/`UnlimitedSupply`/`TokenStore`/object-group resources needed to reconstruct a legacy `EventKey`/sequence number by querying `main_db_reader.latest_state_checkpoint_view()` — the *current* state of the account, evaluated at whatever version the indexer instance happens to be caught up to when it processes the batch — instead of the state as of the version the mint event was emitted at.

### Finding Description
The internal indexer's secondary event indices (`EventByKeySchema`, `EventByVersionSchema`) are built asynchronously per-node from the main DB by `DBIndexer::process_a_batch`. For `ContractEvent::V2` module events, the engine must synthesize a V1 `EventKey`/sequence number by reading the emitting resource's `EventHandle` from chain state. All such lookups go through `get_state_value_bytes_for_resource`/`get_state_value_bytes_for_object_group_resource`, both of which call `latest_state_checkpoint_view()` unconditionally rather than a state view pinned to the transaction version being translated.

Because different fullnode/indexer instances catch up to the tip at different times (restart, replay, backpressure, or simply processing batches at different wall-clock moments), the "latest" view seen while translating the *same* historical mint-v2 event for version `V` can differ between nodes: if the account's `Collections` resource is later modified/removed by any subsequent, unprivileged transaction from that account (e.g. it burns/moves its whole token-v1 collection, or otherwise triggers removal/replacement of the `Collections` resource) before some indexer instances reach version `V`, those instances will see the resource missing and get `Err("Collections resource not found")` from `MintTokenTranslator`, which `DBIndexer::translate_event_v2_to_v1` swallows into `Ok(None)`. Instances that processed version `V` earlier (before the resource was removed) will have succeeded and permanently recorded the `EventByKeySchema`/`EventByVersionSchema`/`TranslatedV1EventSchema` entries for that mint. The write is asynchronous and irreversible once committed — there is no re-translation pass — so this produces a durable, permanent divergence in the local secondary indices of otherwise identical nodes for an identical, VM-committed write set and event stream.

This does not require any malicious peer behavior: it is triggered purely by (a) ordinary indexing lag/restart timing across nodes and (b) any unprivileged account performing subsequent state-mutating transactions on its own `Collections` resource. It is a determinism bug in a state-derived, though non-consensus, on-disk index that is served directly by the JSON REST events API (`get_events_by_event_key`), so it manifests as node-visible, API-visible inconsistency of "ground truth" event history for the same account/version across nodes, even though core consensus state (accumulator/JMT roots, VM write set, transaction info) is untouched.

### Impact Explanation
- This does **not** affect the consensus-critical state (ledger root hashes, JMT, accumulator, transaction infos, write sets) — those remain byte-identical across nodes, so it is not a hard fork or a proof-corruption issue in the strict sense demanded by the review's "Proof And Storage Pivots" section.
- It does corrupt an **authenticated-adjacent, API-served secondary index** (`EventByKeySchema`/`EventByVersionSchema`/`TranslatedV1EventSchema`) that different nodes serve for the exact same historical version, producing divergent answers to `get_events`/`get_events_by_event_key` queries for legacy Token V1 mint events converted from V2 module events. Clients (indexers, exchanges, marketplaces) relying on the REST events API for token mint history can observe missing mint events on some fullnodes and present on others for the identical on-chain event, depending purely on which node/replica timing they hit.
- Given the review's Decision Standard requires impact on "committed state, proof material, authenticated response binding, or hard-fork divergence," this finding is best framed as a **response-integrity/availability defect** in a non-consensus indexing subsystem rather than a state-commitment or proof-binding break: the underlying `write_set`/accumulator/JMT proofs for the events themselves are unaffected — this is a bug in how nodes locally reconstruct legacy `EventKey` metadata for serving, not a corruption of the committed ledger or its proofs.

### Likelihood Explanation
Requires: (1) an account whose `Collections` resource can be removed/replaced by a subsequent unprivileged transaction after having minted Token V1 tokens, and (2) at least two indexer instances observing different "latest" states while translating the same historical event, which is the normal operating condition of any two nodes with different sync/restart timing (this is common, not adversarial). The reviewer note in the code itself ("If the collections resource is not found, we skip the event translation to avoid panic because the creation number cannot be decided") confirms this is a known, accepted-as-best-effort code path, but its dependence on a moving "latest" view rather than the event's own version was likely unintentional.

### Recommendation
Pin the state view used inside `EventV2Translator::translate_event_v2_to_v1` to the version of the transaction/event being translated (a versioned state view at `version - 1`/`version`, not `latest_state_checkpoint_view()`), so that the resource lookup is deterministic and depends only on the ledger version being indexed, not on how far the indexer has otherwise progressed. This makes translation success/failure purely a function of on-chain history and thus identical across all correctly-functioning indexer instances regardless of lag.

### Proof of Concept
1. Create account `A`, call `token::mint_token` (legacy V1-mapped, V2 `MintToken` event) at version `V1`, requiring `0x3::token::Collections` to exist at `A`.
2. In a later transaction (any unprivileged tx from `A` or via a helper that removes/rewrites the `Collections` resource, e.g. through subsequent v1->v2 token migration flows if available) remove/replace `A`'s `Collections` resource at version `V2 > V1`.
3. Spin up `DbIndexer` instance `X` and call `process_a_batch` covering `[V1, V1+1)` immediately after `V1` commits (before `V2`). Observe `EventByKeySchema`/`EventByVersionSchema` gets the mint event recorded.
4. Spin up a second `DbIndexer` instance `Y` (simulating indexing lag/restart) and call `process_a_batch` over `[V1, V1+1)` only after `V2` has already committed to the main DB. Because `get_state_value_bytes_for_resource` calls `latest_state_checkpoint_view()`, `Y` observes the post-`V2` state, finds `Collections` missing, and `MintTokenTranslator` returns `Err`, causing `DBIndexer::translate_event_v2_to_v1` to return `Ok(None)` and skip the index write.
5. Assert: `X.indexer_db` contains an `EventByKeySchema`/`EventByVersionSchema` entry for the mint event at `V1`; `Y.indexer_db` does not — despite both processing the identical VM-committed transaction/event/write-set at `V1`. This demonstrates the divergence described in the exploit question is real and reproducible via the described `process_a_batch`-on-two-instances test methodology.

    fn translate_event_v2_to_v1(
        &self,
        v2: &ContractEventV2,
        engine: &EventV2TranslationEngine,
    ) -> Result<ContractEventV1> {
        let mint = MintToken::try_from_bytes(v2.event_data())?;
        let struct_tag = StructTag::from_str("0x3::token::Collections")?;
        let (key, sequence_number) = if let Some(state_value_bytes) =
            engine.get_state_value_bytes_for_resource(mint.creator(), &struct_tag)?
        {
            let token_store_resource: CollectionsResource = bcs::from_bytes(&state_value_bytes)?;
            let key = *token_store_resource.mint_token_events().key();
            let sequence_number = engine
                .get_next_sequence_number(&key, token_store_resource.mint_token_events().count())?;
            (key, sequence_number)
        } else {
            // If the collections store resource is not found, we skip the event translation to
            // avoid panic because the creation number cannot be decided.
            return Err(AptosDbError::from(anyhow::format_err!(
                "Collections resource not found"
            )));
        };
        let mint_event = MintTokenEvent::new(mint.id().clone(), mint.amount());

        Ok(ContractEventV1::new(
            key,
            sequence_number,
            MINT_TOKEN_EVENT_TYPE.clone(),
            bcs::to_bytes(&mint_event)?,
        )?)
    }
}
