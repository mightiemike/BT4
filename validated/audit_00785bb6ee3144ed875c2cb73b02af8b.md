### Title
Permanent Loss of Funds via `DeleteAccount` with Self as `beneficiary_id` — (`runtime/runtime/src/actions.rs`)

---

### Summary

`action_delete_account` in `runtime/runtime/src/actions.rs` emits a `Receipt::new_balance_refund` targeting `delete_account.beneficiary_id`, then immediately removes the account from state. No validation prevents `beneficiary_id == account_id` (the account being deleted). When the refund receipt later arrives at the now-deleted account, the transfer fails with `AccountDoesNotExist`, and per the documented refund-failure rule the entire balance is permanently burned.

---

### Finding Description

In `action_delete_account` (`runtime/runtime/src/actions.rs`, lines 349–356):

```rust
// We use current amount as a pay out to beneficiary.
let account_balance = account_ref.amount();
if account_balance > Balance::ZERO {
    result
        .new_receipts
        .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
}
let remove_result = remove_account(state_update, account_id)?;
``` [1](#0-0) 

The balance refund receipt is created **before** `remove_account` is called, but it is only **delivered** in a later block. If `beneficiary_id == account_id`, the receipt targets an account that no longer exists by the time it is executed.

`Receipt::new_balance_refund` stamps `predecessor_id = "system"`, making the receipt a refund receipt: [2](#0-1) 

When this receipt is processed, `is_refund = true`. The `check_transfer_to_nonexisting_account` helper is called with `implicit_account_creation_eligible = false` for all refund receipts (the comment in the code explicitly states: *"Account deletion with beneficiary creates a refund, so it'll not create a new account"*): [3](#0-2) 

Because the account no longer exists and implicit creation is ineligible, the transfer action inside the refund receipt returns `AccountDoesNotExist`. Per the documented refund-failure rule:

> *"If the execution of a refund fails, the refund amount is burnt."* [4](#0-3) 

The entire account balance is permanently burned.

The action-validation layer (`runtime/runtime/src/action_validation.rs`) only checks that `beneficiary_id` is a syntactically valid account ID; it does **not** check that `beneficiary_id != receiver_id` (the account being deleted): [5](#0-4) 

The same absence of a guard exists in the VM host function `promise_batch_action_delete_account`, which reads and parses the beneficiary ID from contract memory but performs no semantic check: [6](#0-5) 

---

### Impact Explanation

Any user who submits a `DeleteAccount` transaction (or any contract that calls `promise_batch_action_delete_account`) with `beneficiary_id == account_id` will have their entire liquid balance permanently burned. The balance is deducted from the deleted account, a refund receipt is emitted, the account is removed, and the refund receipt fails silently — the tokens are added to `tokens_burnt` and are irrecoverable. This is a direct, unprivileged loss-of-funds path with no recovery mechanism.

---

### Likelihood Explanation

The trigger requires a user (or a contract on behalf of a user) to set `beneficiary_id` equal to the account being deleted. This can occur:

1. **Accidentally** — a developer or wallet sets `beneficiary_id = signer_id` when `signer_id == receiver_id` (the exact pattern used in the `delete_account` test helper in `integration-tests/src/user/mod.rs` line 267).
2. **Via a buggy contract** — a contract calling `promise_batch_action_delete_account` with a wrong beneficiary argument burns the contract account's balance. [7](#0-6) 

---

### Recommendation

Add a validation check in `validate_action_with_mode` (or a dedicated `validate_delete_account_action` helper) that rejects `DeleteAccountAction` when `beneficiary_id == receiver` (the receipt's receiver account ID). This mirrors the existing `InvalidDeterministicStateInitReceiver` pattern already used for other actions:

```rust
// In validate_action_with_mode, for Action::DeleteAccount:
if delete_account.beneficiary_id == *receiver {
    return Err(ActionsValidationError::InvalidAccountId {
        account_id: delete_account.beneficiary_id.to_string(),
    });
}
```

Optionally, also warn (or reject) when `beneficiary_id` is a named account that does not exist at validation time, though that check is harder to enforce at the transaction-validation layer.

---

### Proof of Concept

1. Alice has account `alice.near` with balance 10 NEAR.
2. Alice submits:
   ```json
   {
     "signer_id": "alice.near",
     "receiver_id": "alice.near",
     "actions": [{ "DeleteAccount": { "beneficiary_id": "alice.near" } }]
   }
   ```
3. `action_delete_account` runs:
   - Creates `Receipt::new_balance_refund("alice.near", 10 NEAR)`.
   - Calls `remove_account(state_update, "alice.near")` — account is gone.
4. The balance-refund receipt is routed to `alice.near`.
5. Runtime processes the receipt: `alice.near` does not exist → `AccountDoesNotExist` error.
6. Refund receipt failed → 10 NEAR added to `tokens_burnt`.
7. Alice's 10 NEAR is permanently destroyed.

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}
