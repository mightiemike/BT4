### Title
Missing negative-value check in `extractDestGasAmountFromMap` allows integer-wraparound to a huge `DestGasAmount` - ([File: core/capabilities/ccip/ccipsolana/executecodec.go])

### Summary
`extractDestGasAmountFromMap` in `core/capabilities/ccip/ccipsolana/executecodec.go` only rejects `int64` values that exceed `math.MaxUint32`, but never checks for negative values before converting with `uint32(v)`. A negative `int64` (e.g. `-1`) silently wraps around to a large `uint32` (e.g. `4294967295`) and is accepted as a valid `DestGasAmount`.

### Finding Description
The claimed case-permutation bypass is **not valid**: field names are normalized with `strings.ToLower(fieldName)` before comparison at [1](#0-0) , so any casing of `destGasAmount` (`DESTGASAMOUNT`, `DestGasAmount`, etc.) maps to the same `"destgasamount"` branch — casing cannot be used to dodge the type switch.

However, the type switch itself has a real range-validation gap. For the `int64` case, only an upper bound is enforced: [2](#0-1) 
There is no check that `v >= 0`. A negative `int64`, e.g. `-1`, passes `v > math.MaxUint32` (false, since `-1 < math.MaxUint32`) and is then converted via `uint32(v)`, which for `-1` yields `0xFFFFFFFF` (4294967295) due to Go's two's-complement truncation — silently turning a negative value into the maximum possible `uint32`.

This decoded map originates from `e.extraDataCodec.DecodeTokenAmountDestExecData(tokenAmount.DestExecData, ...)` at [3](#0-2) , which decodes `DestExecData` bytes that are part of the CCIP message's token-transfer extra data — data that originates from the source-chain sender of the CCIP message (an ordinary, unprivileged account calling the on-chain router/onramp to initiate a cross-chain token transfer can choose arbitrary extra-data bytes for destExecData, subject to the source-chain codec's own encoding format). The resulting (wrapped) `destGasAmount` is then embedded directly into the on-chain execution report: [4](#0-3) 

### Impact Explanation
An attacker-influenced negative gas value can be silently converted into `DestGasAmount = 4294967295` (max uint32) in the `ccip_offramp.Any2SVMTokenTransfer` struct that is Borsh-encoded and submitted as part of the execution report on Solana. This is a data-tampering/misreporting bug: the invariant "destGasAmount is a validated non-negative uint32 bound to the token transfer" is violated for negative inputs, producing an inflated, attacker-influenced gas budget rather than a rejected/error result. Depending on how `DestGasAmount` is consumed on the Solana program side (e.g. as an added compute/gas allowance for the token-receiver callback), this could allow disproportionate resource consumption or execution behavior not intended by the actual sender-specified value.

### Likelihood Explanation
The bug is trivially reachable: any party able to construct/influence the source-chain-side `DestExecData` (i.e. any user sending a CCIP token transfer with custom extra-data bytes that decode to a negative `destGasAmount` field) exercises this path without any additional privilege, signature bypass, or node compromise. The only precondition is that the source-chain extra-data codec (e.g. an EVM ABI decoder for the relevant chain family) can decode a negative signed integer into this field as an `int64` in the resulting Go map — this depends on the specific codec's decoding behavior but is not gated by any authorization check in this function.

### Recommendation
Add an explicit non-negative check before the upper-bound check, e.g.:
```go
case int64:
    if v < 0 || v > math.MaxUint32 {
        return 0, fmt.Errorf("destGasAmount out of uint32 range, got %d", v)
    }
    return uint32(v), nil
```

### Proof of Concept
Add a table-driven/fuzz test for `extractDestGasAmountFromMap` in `core/capabilities/ccip/ccipsolana/executecodec_test.go`:
- Input `map[string]any{"destGasAmount": int64(-1)}` → currently returns `(4294967295, nil)`; expected: an error.
- Input `map[string]any{"destGasAmount": int64(math.MinInt64)}` → currently wraps to some large uint32 value without error; expected: an error.
- Input `map[string]any{"destGasAmount": int64(math.MaxInt64)}` → correctly errors today (exceeds MaxUint32) — confirms upper bound works, contrasted with the missing lower bound.
- Fuzz `extractDestGasAmountFromMap` over random `int64` values and assert: result is only non-error for `0 <= v <= math.MaxUint32`; all negative values must return an error.
