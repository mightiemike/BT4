### Title
Panic (DoS) on Empty L1 Handler Calldata in `l1_handler_message_hash` - (File: crates/starknet_api/src/hash.rs)

### Summary
`l1_handler_message_hash` unconditionally calls `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")` on the transaction's `Calldata`. `Calldata` has no non-empty invariant enforced by its type or by `Deserialize`, so an `L1HandlerTransaction` with empty calldata is constructible. When `calc_msg_hash()` (which wraps this function) is invoked on such a transaction, the `.expect()` panics.

### Finding Description
`Calldata` is a thin wrapper `Arc<Vec<Felt>>` with no validation preventing an empty vector [1](#0-0) . The codebase already acknowledges this gap in a sibling function, `payload_size()`, which explicitly guards against empty calldata using `saturating_sub` with a comment stating `Calldata has no non-empty invariant` [2](#0-1) . However, `l1_handler_message_hash` was not given the same treatment and still uses an unguarded `.expect()`: [3](#0-2) 

This is called from `L1HandlerTransaction::calc_msg_hash()` [4](#0-3) , which is invoked during proposal building in the L1 events provider's `get_txs()` for every transaction pulled into a block proposal (for debug logging of L1↔L2 message hashes) [5](#0-4) .

This is functionally analogous to the vim `grab_file_name` bug class: a data-parsing routine assumes a minimum structural invariant (non-empty buffer / non-empty calldata) without validating it, and indexing/slicing operations that rely on that assumption crash when the assumption is violated by attacker-supplied data.

### Impact Explanation
If an `L1HandlerTransaction` with empty `calldata` reaches this code path (e.g., via a malformed/adversarial L1 message, a bug in event decoding, or a directly-constructed transaction reaching `get_txs`/other reachable call sites), the `.expect()` panics and crashes the process handling the L1 events provider / batcher path. A crash of this component during block proposal directly maps to "a network unable to confirm new transactions" for the affected sequencer instance.

### Likelihood Explanation
Likelihood is constrained by whether the L1 message sender can actually produce an `L1HandlerTransaction` with zero-length calldata (normally, the L1 messaging contract prepends the `from_address` field, making calldata non-empty by construction at the L1 contract level). The test file demonstrates the sequencer's own code explicitly anticipates and defends against this exact empty-calldata condition in `payload_size()`, indicating the invariant is not trusted end-to-end within this codebase [6](#0-5) , yet `calc_msg_hash` was missed. I could not confirm from available context whether the L1 scraper enforces non-empty calldata before constructing the `L1HandlerTransaction`, so likelihood should be treated as uncertain/moderate pending verification of the L1 event decoding path (`apollo_l1_events`/`papyrus_base_layer` event parsing).

### Recommendation
Apply the same defensive pattern used in `payload_size()` to `l1_handler_message_hash`: validate that `calldata.0` is non-empty before calling `split_first()`, and return a proper `Result`/error (or treat empty payload as `from_address = 0`) instead of panicking, consistent with how `payload_size` was hardened.

### Proof of Concept
1. Construct `crate::transaction::L1HandlerTransaction` with `calldata: Calldata(Arc::new(vec![]))` (as already done in the existing regression test for `payload_size`) [7](#0-6) .
2. Call `.calc_msg_hash()` on the resulting transaction's `tx` field.
3. Observe the `.expect("Invalid calldata, expected at least from_address")` panic in `l1_handler_message_hash` [8](#0-7) .

**Caveat:** I was unable to fully verify, given index limitations, whether the actual L1 event scraping/decoding pipeline (`papyrus_base_layer`/`apollo_l1_events`) enforces non-empty calldata before this point, which would determine whether this is genuinely reachable from an L1 message sender or only from internal/test-constructed transactions. A Devin session with full repo access would be needed to trace the L1 log-to-`L1HandlerTransaction` decoding logic to confirm end-to-end reachability.
