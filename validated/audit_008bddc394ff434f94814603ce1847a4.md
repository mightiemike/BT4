### Title
Full-table RocksDB scan in `Wallet.getAssetIssueByName` enables attacker-inflated O(n) RPC-API DoS - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
When `getAllowSameTokenName()` is 1 (the default post-fork state), `Wallet.getAssetIssueByName(ByteString)` calls `chainBaseManager.getAssetIssueV2Store().getAllAssetIssues()`, which streams and deserializes **every** entry in the `AssetIssueV2Store` RocksDB column family before filtering by name in memory. Because every unprivileged account can issue one asset for a fee, an attacker can inflate this store and then repeatedly invoke `GetAssetIssueByName` over gRPC/HTTP to force full linear scans per request, with no caching or keyed lookup.

### Finding Description
`Wallet.getAssetIssueByName` branches on `getAllowSameTokenName()`: [1](#0-0) 

In the `==0` branch it performs a direct keyed `get()` on `AssetIssueStore`, but in the `!=0` branch (default state post name-duplication fork) it calls `getAllAssetIssues()` on `AssetIssueV2Store`, which is implemented as: [2](#0-1) 

This iterates the entire underlying RocksDB store (`iterator()`), deserializing every `AssetIssueCapsule`, and only then filters in-memory by name equality. The same pattern also backs `getAssetIssueList`, `getAssetIssueByAccount`, and `getAssetIssueListByName` in `Wallet.java` (lines 1530-1544, 1568-1589, 1774-1795), so the issue is systemic to the V2 asset store access pattern, not unique to this one method.

This method is reachable from unauthenticated/unprivileged clients via:
- gRPC `getAssetIssueByName` (`RpcApiService.java`)
- HTTP `/wallet/getassetissuebyname` (`GetAssetIssueByNameServlet.java`), which extends `RateLimiterServlet` — so the HTTP path has *some* rate limiting, but the gRPC path does not appear to have an equivalent per-call cost/rate limiter based on the code reviewed. [3](#0-2) 

**Attacker cost to inflate the store:** issuing an asset requires `AssetIssueActuator`, which charges `calcFee()` (the `AssetIssueFee` dynamic parameter) burned from the caller's balance, and each account may issue **only one** asset ("An account can only issue one asset"): [4](#0-3) 

This means asset issuance is *not* free — inflating the store to N entries costs N × `AssetIssueFee` plus N distinct funded accounts (each needing enough balance to also pay bandwidth/energy for the issuing transaction), which is a real, non-trivial economic cost, contrary to the "cheap asset issuance" premise in the question.

**Query-side cost:** once the store is inflated, each `GetAssetIssueByName` call (a read-only, feeless RPC query, not a state-changing transaction) triggers the full linear scan and deserialization of all N entries, with no caching between requests. No existing check (signature validation, actuator validate(), fork gates, energy/bandwidth accounting) applies to this read path since it is a query API, not a transaction.

### Impact Explanation
This is a DoS-via-RPC-API concern: an attacker who has paid to inflate `AssetIssueV2Store` can subsequently cause disproportionate CPU/I/O load on any full node per query, scaled to the size of the store the attacker built. Impact is bounded to node responsiveness/latency for the query RPC surface, not to consensus, funds, or private keys.

### Likelihood Explanation
- Preconditions: `allowSameTokenName == 1` (this is the default state in mainnet post-hard-fork, so this precondition is trivially satisfied).
- Attacker must pay `AssetIssueFee` × N and control N distinct funded accounts to build up N entries in the store — this is a real chain cost, not free, unlike the "cheap issuance" premise assumed in the question. This meaningfully limits attacker economics: to force e.g. 10,000 entries the attacker must burn 10,000 × `AssetIssueFee` in TRX plus fund 10,000 accounts.
- Once the store is built (which is a one-time, amortized cost across all future queries by any client, not just the attacker), any subsequent `GetAssetIssueByName` query — feeless and repeatable at high frequency, especially over gRPC where no evident per-call rate limiter was found in the reviewed code — degrades with the size of the store.
- The HTTP path is mitigated somewhat by `RateLimiterServlet`, reducing achievable request rate there.

### Recommendation
- Replace the full-table scan with a keyed lookup by name (e.g., maintain a name→id index in `AssetIssueV2Store` or use `assetName` as part of the DB key) so `getAssetIssueByName` performs O(1)/O(log n) lookups instead of O(n) scans.
- Apply the same fix to `getAssetIssueList`, `getAssetIssueByAccount`, and `getAssetIssueListByName`, which share the same full-scan pattern.
- Add pagination/limits and consistent rate limiting to the gRPC query surface analogous to `RateLimiterServlet` on HTTP.

@Test
public void testGetAssetIssueByNameScalesWithStoreSize() {
  chainBaseManager.getDynamicPropertiesStore().saveAllowSameTokenName(1);

  // Baseline latency with empty-ish store
  long t0 = System.nanoTime();
  wallet.getAssetIssueByName(ByteString.copyFromUtf8("nonexistent"));
  long baseline = System.nanoTime() - t0;

  // Simulate attacker-inflated store: insert 10_000 AssetIssueCapsule entries directly
  for (int i = 0; i < 10_000; i++) {
    AssetIssueCapsule cap = new AssetIssueCapsule(
        ByteArray.fromHexString(OWNER_ADDRESS), String.valueOf(i),
        "asset" + i, "abbr", 1_000_000L, 6);
    chainBaseManager.getAssetIssueV2Store().put(cap.createDbV2Key(), cap);
  }

  long t1 = System.nanoTime();
  wallet.getAssetIssueByName(ByteString.copyFromUtf8("nonexistent"));
  long afterInflate = System.nanoTime() - t1;

  // Assert latency scales roughly linearly with N (afterInflate >> baseline)
  Assert.assertTrue(afterInflate > baseline * 100);
}
