### Title
Missing null check on `contractStore.get()` result in `TransactionTrace.pay()` allows NPE / billing bypass for calls to just-suicided contracts within the same block - ([File: chainbase/src/main/java/org/tron/core/db/TransactionTrace.java])

### Summary
In `TransactionTrace.pay()`, when `trxType == TRX_CONTRACT_CALL_TYPE`, the code fetches `ContractCapsule contractCapsule = contractStore.get(callContract.getContractAddress().toByteArray())` and immediately dereferences it (`contractCapsule.getOriginAddress()`, `contractCapsule.getConsumeUserResourcePercent(...)`) with no null check. [1](#0-0)  If a contract self-destructs in one transaction and a subsequent transaction in the same block targets the same address before/without re-deployment, the `ContractCapsule` will already be removed from `contractStore`, causing `contractStore.get(...)` to return `null` and the subsequent field access to throw an NPE.

### Finding Description
`TransactionTrace.finalization()` calls `pay()` and then, for every address returned by `transactionContext.getProgramResult().getDeleteAccounts()`, calls `deleteContract(address)`, which deletes the entries from `abiStore`, `codeStore`, `accountStore`, and `contractStore` for that address. [2](#0-1) [3](#0-2) 

Because transactions inside a block are processed and finalized sequentially, once transaction N (which contains a `SUICIDE`/self-destruct of contract `X`) finishes its `finalization()`, `contractStore`, `accountStore`, `codeStore`, and `abiStore` no longer have entries for `X` for the remainder of block processing. Any subsequent transaction N+1 in the same block that is a `TriggerSmartContract` targeting `X` will go through `exec()` (VM execution) and then `pay()`. In `pay()`'s `TRX_CONTRACT_CALL_TYPE` branch, `contractStore.get(X)` returns `null`, and the immediately following line `originAccount = contractCapsule.getOriginAddress();` dereferences a null reference, throwing an NPE. [4](#0-3) 

The `default: return;` branch is not taken because `trxType` is still resolved as `TRX_CONTRACT_CALL_TYPE` at `TransactionTrace` construction time (based purely on the `ContractType` of the transaction, not on whether the target contract currently exists). [5](#0-4) 

### Impact Explanation
An unhandled `NullPointerException` inside `pay()`, which is invoked from `finalization()` during block processing, is not caught by the existing `catch (BalanceInsufficientException e)` handler in `finalization()`, so it would propagate up uncaught. [6](#0-5)  Depending on how the caller of `finalization()` (block-processing manager) handles unchecked exceptions, this could stall or crash block application for the node processing the block — a potential DoS via the TRON protocol implementation. Alternatively, if the code path were changed to avoid the NPE without added logic (e.g., an early return added carelessly), it could allow energy consumption to occur without any billing to an origin account, breaking value-conservation guarantees for VM execution.

### Likelihood Explanation
This is a critical caveat I could not fully verify: I was not able to confirm, within the available tool budget, whether `TriggerSmartContractActuator.validate()` (which runs before `exec()`/`pay()` for every transaction, including transaction N+1) independently rejects a `TriggerSmartContract` transaction whose target address is missing from `contractStore`/`accountStore` before the VM/`pay()` stage is ever reached. If `validate()` already throws a `ContractValidateException` for a non-existent contract address, the transaction would be rejected earlier and `pay()`'s null-dereference would never be hit in practice, closing off this exploit path. I was unable to locate and inspect `TriggerSmartContractActuator.validate()` in this session to confirm or rule this out.

If such a pre-check does NOT exist (or can be bypassed, e.g. because the VM handles calls to non-existent/empty accounts as no-ops rather than rejecting them outright, which is standard EVM-like behavior), then the attack requires only:
- Deploying/using a contract `X` that can self-destruct (`SUICIDE`), a normal unprivileged smart-contract operation.
- Broadcasting two ordered transactions in the same block: tx1 (trigger `X`'s suicide) and tx2 (`TriggerSmartContract` to `X`), both attacker-controlled and paid for by attacker fees/energy — no privileged role needed.
- Relying on block-producer/witness transaction ordering to place both in the same block, which is plausible but not fully attacker-controlled (attacker can only submit and hope for favorable ordering, or attempt to get both transactions accepted from their own account in sequence).

Given the uncertainty about the `validate()` gate, I present this with reduced confidence: the null-check bug in `pay()` is real and directly readable from the code, but full end-to-end reachability from an unprivileged attacker's broadcast transaction was not conclusively confirmed.

### Recommendation
Add an explicit null check on `contractCapsule` in `TransactionTrace.pay()` immediately after `contractStore.get(...)` for the `TRX_CONTRACT_CALL_TYPE` case. If null (contract deleted/self-destructed), treat this deterministically — e.g., skip origin-energy billing and charge only the caller's own bandwidth/energy per protocol rules, or fail the transaction with a defined `ContractExeException` rather than allowing an NPE to propagate. Also verify that `TriggerSmartContractActuator.validate()` (or an equivalent pre-VM check) is guaranteed to run against the current, up-to-date `contractStore`/`accountStore` state before `pay()` is reached, so that calls to non-existent contracts are consistently rejected at the earliest possible stage.
