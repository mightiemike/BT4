## Analog Found

### Title
`DeleteAccountAction.beneficiary_id` is never checked for existence before the account is irreversibly deleted, permanently burning the account's balance - ([File: runtime/runtime/src/actions.rs])

### Summary
The Sherlock report flags `OwnableImpl.transferOwnership` for performing an irreversible state change (owner transfer) to an address that is validated only for format, not for whether it is a usable/existing destination — so a mistaken target permanently loses the asset. The same defect class exists in nearcore's `DeleteAccount` action: the `beneficiary_id` supplied by an unprivileged transaction signer is validated only for account-id *syntax*, never for *existence*, before the signer's account and its balance are irreversibly destroyed.

### Finding Description
`DeleteAccountAction` validation only checks that `beneficiary_id` is a syntactically valid account id: [1](#0-0) 

There is no existence check performed at validation time or at execution time before the action commits. During execution, `action_delete_account` unconditionally removes the account (`*account = None`) and enqueues the entire remaining balance as a `Transfer` receipt to whatever `beneficiary_id` was given: [2](#0-1) 

That refund is built via `Receipt::new_balance_refund`, a `predecessor_id: "system"` receipt: [3](#0-2) 

If `beneficiary_id` does not exist as an account, the runtime's own tests confirm the refund receipt is rejected with `AccountDoesNotExist` rather than creating the account: [4](#0-3) 

And per the documented refund semantics, a refund receipt that fails to execute has its deposit **burnt**, not returned to anyone: [5](#0-4) 

The official action spec for `DeleteAccountAction` documents only a format-level `InvalidAccountId` validation error for `beneficiary_id` — no existence check is ever performed, and the delete itself is final (enforced only positionally by `DeleteActionMustBeFinal`, which does not imply reversibility): [6](#0-5) 

### Impact Explanation
Any unprivileged transaction signer who submits `Action::DeleteAccount` with a `beneficiary_id` that is syntactically valid but does not exist on-chain (e.g. a typo, or an account that was never created / was itself deleted between signing and execution) will have their entire account balance permanently burnt with no way to recover it — this is a real, protocol-level "irreversible transfer to an unvalidated destination" analogous to the reported `OwnableImpl.transferOwnership` bug class: a one-step, unchecked, irreversible action whose failure mode is permanent loss of value rather than a safe revert of the whole transaction.

### Likelihood Explanation
Reachable directly by any single signed transaction or contract-issued `promise_batch_action_delete_account` call from any account — no special privilege, validator role, or multi-party coordination required. The only precondition is supplying a `beneficiary_id` that passes format validation but does not exist at execution time.

### Recommendation
Before committing the delete, verify that `beneficiary_id` resolves to an existing account (or otherwise fail the whole action/receipt instead of allowing the account removal to proceed while its refund silently burns). Alternatively, make the beneficiary-existence check part of `validate_delete_action`/`check_account_existence` so the entire `DeleteAccount` receipt is rejected up front rather than only failing at the refund-receipt stage after the account has already been deleted.

### Proof of Concept
1. Sign and submit a transaction containing a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "does-not-exist.near" })` as the final (and only, per `DeleteActionMustBeFinal`) action on the signer's own account, where `"does-not-exist.near"` is a syntactically valid but non-existent account id.
2. `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) removes the account and enqueues `Receipt::new_balance_refund(&beneficiary_id, account_balance)`.
3. That refund receipt executes against a receiver that does not exist and fails with `AccountDoesNotExist`; per `runtime/runtime/src/tests/apply.rs:6883-6926` and the documented refund-burn rule in `docs/RuntimeSpec/Refunds.md:10-13`, the deposit is burnt instead of returned.
4. Net effect: the deleting account's entire remaining balance is permanently and irrecoverably destroyed, with no two-step confirmation or existence check having been offered before the irreversible deletion.

**File:** docs/RuntimeSpec/Refunds.md (L10-13)
```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```

## DeleteAccountAction

```rust
pub struct DeleteAccountAction {
    /// The remaining account balance will be transferred to the AccountId below
    pub beneficiary_id: AccountId,
}

**Outcomes**:

- The account, as well as all the data stored under the account, is deleted and the tokens are transferred to `beneficiary_id`.

### Errors

**Validation Error**:

- If `beneficiary_id` is not a valid account id, the following error will be returned

```rust
/// Invalid account ID.
InvalidAccountId { account_id: AccountId },
```

- If this action is not the last action in the action list of a receipt, the following error will be returned

```rust
/// The delete action must be a final action in transaction
DeleteActionMustBeFinal
