### Title
Unbounded full asset-store scan via `getAssetIssueByAccount`/`getAssetIssueListByName` enables CPU-amplified DoS - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getAssetIssueByAccount(ByteString)` and `Wallet.getAssetIssueListByName(ByteString)` both call `getAllAssetIssues()` which iterates the entire `AssetIssueStore`/`AssetIssueV2Store` and then apply an in-memory `Stream.filter`, with no pagination or per-request cost limit. Any unprivileged HTTP client can call `/wallet/getassetissuebyaccount` or `/wallet/getassetissuelistbyname` with arbitrary/non-matching addresses or names to force a full-store scan on every call while receiving a near-empty response.

### Finding Description
Both endpoints are backed by `GetAssetIssueByAccountServlet` and `GetAssetIssueListByNameServlet`, which simply forward the raw address/name query parameter into `Wallet.getAssetIssueByAccount` [1](#0-0)  and `Wallet.getAssetIssueListByName` [2](#0-1) .

Inside `Wallet.java`, both methods fetch the full asset list via `getAssetIssueStoreFinal(...).getAllAssetIssues()` and then filter in a stream, discarding the vast majority of results when the filter value doesn't match: [3](#0-2) [4](#0-3) 

`getAllAssetIssues()` in `AssetIssueStore` iterates the entire underlying RocksDB column family with no bound: [5](#0-4) 

By contrast, the paginated variant `getAssetIssuesPaginated` caps `limit` at `ASSET_ISSUE_COUNT_LIMIT_MAX` [6](#0-5) , but `getAssetIssueByAccount` and `getAssetIssueListByName` have no such bound — they always scan the whole store regardless of input.

The only mitigation in place is `RateLimiterServlet`, which applies a generic per-endpoint QPS/global rate limiter before dispatching to the servlet [7](#0-6) . This limits request *rate*, not per-request *cost*: each admitted request still performs an O(N) scan over all stored assets, so an attacker who stays within the QPS budget (or uses multiple source IPs, since `IPQPSRateLimiterAdapter` is keyed per IP) can sustain a steady stream of maximal-cost, minimal-response-size requests indefinitely.

### Impact Explanation
This matches the "DoS via RPC-API" bounty class. Because each request costs O(number of assets in store) CPU/IO regardless of whether a match is found, and the JSON response is tiny (empty `AssetIssueList`) when no match occurs, an attacker gets a very high CPU-cost-to-response-size ratio. Repeated concurrent calls to these two endpoints (or their gRPC/Solidity/PBFT equivalents, which all delegate to the same `Wallet` methods per `RpcApiService.java`) can consume disproportionate node CPU relative to bandwidth used, degrading service for legitimate API consumers on that node.

### Likelihood Explanation
No special privileges are required — any anonymous HTTP/gRPC client can call these endpoints with arbitrary addresses/asset names, there is no fee, no transaction broadcast, and no signature required (these are read-only query endpoints). Feasibility is bounded only by the existing generic QPS rate limiter (`DefaultBaseQqsAdapter`/`IPQPSRateLimiterAdapter`), which limits request frequency but not per-request work, so an attacker can still achieve sustained scan cost proportional to QPS × store size, and can trivially scale further via multiple IPs if `IPQPSRateLimiterAdapter` is used. The impact scales with the size of `AssetIssueStore`, which grows monotonically over time as more assets are issued on-chain, making this more severe on long-lived mainnet-like databases.

### Recommendation
Add pagination or a hard result/scan cap to `getAssetIssueByAccount` and `getAssetIssueListByName` similar to `getAssetIssuesPaginated`, or maintain a secondary index (owner-address → asset IDs, name → asset IDs) so lookups aren't O(N) full-store scans. At minimum, apply a stricter, cost-aware rate limit (e.g., `GlobalPreemptibleAdapter`) to these two servlets specifically.

  public AssetIssueList getAssetIssueByAccount(ByteString accountAddress) {
    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
