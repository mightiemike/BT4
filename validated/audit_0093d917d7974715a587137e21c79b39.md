### Title
Legacy `VoteWitnessActuator` does not merge duplicate witness votes in a single request, allowing users to bypass the `MAX_VOTE_NUMBER` cap and record inconsistent vote weight versus the TVM path - ([File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java])

### Summary
The reported bug class is: a batch/array of same-asset entries is processed with a per-iteration calculation that relies on a value which is not updated/merged across iterations, letting an attacker split a single large operation into many small duplicate-asset entries to get a result the protocol never intended (lower tax, or here, an inconsistent vote state). In java-tron, the `VoteWitnessContract.votes` list is exactly such an array (repeated `Vote{vote_address, vote_count}`), and there are two independent implementations of the "apply votes" operation that behave differently for duplicate `vote_address` entries.

### Finding Description
`VoteWitnessActuator.validate()` iterates the `votes` list and only accumulates a total `sum` of vote counts against the caller's `tronPower`; it performs no de-duplication check on `vote.getVoteAddress()`: [1](#0-0) 

`countVoteAccount()` then simply calls `accountCapsule.addVotes(...)` and `votesCapsule.addNewVotes(...)` once per list entry, in a `forEach`, with no merging by witness address: [2](#0-1) 

By contrast, the newer TVM-native path, `VoteWitnessProcessor.execute()`, explicitly merges duplicate witness entries into a `Map<ByteString, Long> voteMap` before writing votes, precisely to avoid the class of bug described in the external report (multiple entries for the same target inflating/deflating derived totals incorrectly): [3](#0-2) [4](#0-3) 

The presence of `getRepeateContract(...)` test helper and tests like `voteCountsTest` confirm the codebase is aware that a single `VoteWitnessContract` can contain repeated `Vote` entries for the same witness address, and that the `MAX_VOTE_NUMBER` (30) limit is enforced only on list length, not on distinct-witness count: [5](#0-4) [6](#0-5) 

The proto allows the same `vote_address` to appear multiple times, with no protocol-level uniqueness constraint: [7](#0-6) 

Because `AccountCapsule.addVotes`/`VotesCapsule.addNewVotes` (not directly inspected in this session, tool access ran out before reading their implementation) are invoked once per raw list element rather than once per merged/distinct witness, the resulting on-chain `votes` list for the account can end up containing multiple `Vote` entries for the same witness address (rather than one consolidated entry), unlike the TVM path which always produces a de-duplicated `votesList`. This is an unverified but strongly indicated discrepancy given the divergence in the two code paths for what should be the exact same state transition (delegated stake to witnesses feeding the `MortgageService`/`RewardViCalService` reward-per-vote computation, which iterates `accountCapsule.getVotesList()` and does `deltaVi * userVote`).

### Impact Explanation
If duplicate `Vote` entries for the same witness persist in `AccountCapsule.getVotesList()`, downstream reward computation (`MortgageService.computeReward` / `VoteRewardUtil.computeReward` / `RewardViCalService.getNewRewardAlgorithmReward`) iterates the votes list and multiplies `deltaVi * userVote` per entry, summing across all entries: [8](#0-7) [9](#0-8) 
If several entries reference the same witness, the summed reward for the voter is computed correctly in total (each entry's vote count is still counted), so the primary risk is not reward-inflation per se but state-consistency/gas and data-integrity issues: `MAX_VOTE_NUMBER` becomes a control on raw entries rather than the number of distinct witnesses actually supported, and vote list bloat (up to 30 duplicate entries for one witness) could be used to bypass intended witness-diversification limits or create abnormal `votesList` state that other code paths (which assume a de-duplicated list, e.g. the TVM path's `voteMap`) do not expect. This is a state-consistency/DoS-adjacent and accounting-inconsistency issue reachable directly from an unprivileged broadcast transaction of type `VoteWitnessContract`, not requiring any privileged actor.

### Likelihood Explanation
High — any account can submit a `VoteWitnessContract` with repeated `Vote` entries for the same `vote_address`; this is a completely unprivileged, self-serve broadcast transaction and the legacy actuator's `validate()`/`countVoteAccount()` place no restriction preventing duplicate witness addresses in the list.

### Recommendation
In `VoteWitnessActuator.validate()` and `countVoteAccount()`, merge/deduplicate votes by `vote_address` the same way `VoteWitnessProcessor.execute()` already does (accumulate into a `Map<ByteString, Long>` before calling `accountCapsule.addVotes`/`votesCapsule.addNewVotes`), or explicitly reject a `VoteWitnessContract` containing duplicate `vote_address` entries during validation, aligning the legacy actuator's behavior with the TVM-native processor.

### Proof of Concept
Not independently verified end-to-end (unable to confirm `AccountCapsule.addVotes` internals before the session ended), but the reachable path is:
1. Freeze balance to obtain `tronPower`.
2. Submit a `VoteWitnessContract` with, e.g., 5 `Vote` entries all pointing to the same `witnessAddress`, each with `vote_count = tronPower/5` (as constructed by `getRepeateContract` in the actuator test suite): [5](#0-4) 
3. `validate()` only checks `sum <= tronPower`, which passes since the duplicates individually pass the (missing) uniqueness check: [1](#0-0) 
4. `countVoteAccount()` applies each entry independently via `forEach`, potentially leaving multiple raw `Vote` entries for the same witness in the account's `votesList`, unlike the merged behavior of `VoteWitnessProcessor`.

**Note on confidence**: This analog is weaker than the original report because I was unable to inspect the actual implementation of `AccountCapsule.addVotes` / `VotesCapsule.addNewVotes` (tool budget exhausted) to confirm whether they merge by address internally despite being called per-entry, which would fully mitigate the issue. Given the explicit, deliberate duplicate-merging logic added in `VoteWitnessProcessor` (with the comment "merge vote for same witness"), it is likely that this merging was added specifically because the legacy actuator path lacked it — but this could not be conclusively confirmed with the remaining tool calls.

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()

        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);

          continue;

        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
