Based on my investigation, I found a genuine analog to the "unprotected initializer" bug class in the Push Chain scoped code.

### Title
Unprotected `initialize(address)` on the genesis-deployed FactoryV1 proxy allows front-running takeover of UEA deployment authority - (File: `x/uexecutor/keeper/genesis.go`)

### Summary
Push Chain's `x/uexecutor` module deploys the `FactoryV1` proxy/implementation/proxy-admin triple directly into EVM state at genesis via `deployFactoryEA` [1](#0-0) , but this genesis path never invokes the contract's `initialize(address initialOwner)` function that sets `Ownable.owner`. The only place in the codebase that calls `initialize` on the Factory is test-only setup code [2](#0-1) , executed as a manual, separate EVM call. This mirrors the FiatToken `initializeV2()` pattern: an implementation contract exposes an initializer that is not called atomically as part of the (proxy) deployment step, and is not otherwise access-restricted to a privileged caller before the first legitimate call lands.

### Finding Description
`FactoryV1ABI` exposes an `initialize(address initialOwner)` entry point [3](#0-2) , which sets the `Ownable` owner used to gate `setUEAProxyImplementation` (and other admin-only factory functions such as chain/UEA registration). The genesis deployment routine `deployFactoryEA` only sets up the proxy, proxy-admin, and implementation bytecode/storage slots — it does not call `initialize` [1](#0-0) . In the test harness, initialization is a distinct, later `CallEVM(... "initialize", owner)` step performed by whoever runs the setup script [4](#0-3) . If production genesis/deployment tooling follows the same two-step pattern (deploy bytecode, then separately call `initialize`) rather than baking ownership into the genesis state atomically, there is a window in which the Factory proxy exists on-chain with an implementation whose `initialize` has not yet been consumed — any unprivileged account able to submit a transaction to the freshly-live JSON-RPC endpoint could call `initialize(attacker)` first and become the permanent Factory owner.

### Impact Explanation
Owning the `FactoryV1` contract grants control over `setUEAProxyImplementation`, which determines the UEA proxy implementation used for **all** UEAs computed/deployed through `CallFactoryToDeployUEA` [5](#0-4) . An attacker-controlled Factory owner could point every subsequently deployed UEA at a malicious implementation, letting them intercept or redirect universal-execution-layer funds and payload execution chain-wide — a direct violation of the "unauthorized UEA execution" and "unauthorized module-originated EVM execution" invariants called out in the allowed-impact scope.

### Likelihood Explanation
This depends entirely on whether the real (non-test) deployment/genesis flow calls `initialize` atomically within the same genesis block/transaction as the bytecode deployment, or as a separate follow-up transaction/script (as the test helper does). I could not locate a non-test production code path in this repository that performs the `initialize` call — `deployFactoryEA` in `x/uexecutor/keeper/genesis.go` never calls it, and grepping the module for other call sites only surfaced the test helper. This is the same "unproven atomicity" gap flagged in the original report as High severity. Because I cannot confirm from this repository alone whether an external deployment script guarantees atomic initialization (analogous to StablR's mitigation of "running deployment and initialization before announcement"), likelihood is uncertain and should be verified against the actual mainnet/testnet genesis/deploy tooling.

### Recommendation
- Fold the `initialize(owner)` call into the same genesis routine that deploys the Factory bytecode (`deployFactoryEA`/`deploySystemContracts`), so ownership is set atomically at the same height as code deployment, leaving no callable window for a third party.
- Alternatively, harden the implementation contract itself with OpenZeppelin's `_disableInitializers()` in the implementation's constructor and/or restrict the first `initialize` call to a hardcoded, chain-controlled address, consistent with the pattern already used for `ProxyAdmin.owner` (set directly via `SetState` at genesis rather than via a callable initializer) [6](#0-5) .
- Audit the actual deployment/upgrade scripts (outside this repo, e.g. `push-chain-core-contracts` deploy scripts) to confirm `initialize` is called in the same atomic step as proxy deployment, not as a separately-broadcastable transaction.

### Proof of Concept
1. At genesis, `deploySystemContracts`/`deployFactoryEA` installs the `FactoryV1` proxy, admin, and implementation bytecode and storage slots, but the `Ownable.owner` storage slot in the implementation is left unset (no `initialize` call in this code path) [1](#0-0) .
2. If node/network operators initialize the Factory via a separate transaction after the chain is live (mirroring the test flow) [4](#0-3) , an attacker who submits `initialize(attackerAddress)` to the Factory proxy address before the legitimate operator's transaction is included becomes the recorded owner.
3. The attacker then calls `setUEAProxyImplementation(maliciousImpl)`, redirecting all future UEA deployments to attacker-controlled logic.

**Uncertainty note**: I was unable to find code in this repository that performs the atomic `initialize` call outside of test helpers, so I cannot confirm whether this is exploitable in the actual production deployment flow or whether an external, unindexed deploy script mitigates it (as StablR did for the original finding). This should be verified against the real genesis/deployment tooling before treating it as confirmed-exploitable.

func deployProxyAdminContract(ctx context.Context, evmKeeper types.EVMKeeper) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	proxyAdminAddress := common.HexToAddress(types.PROXY_ADMIN_ADDRESS_HEX)
	owner := common.HexToAddress(types.PROXY_ADMIN_OWNER_ADDRESS_HEX)

	// Compute the code hash from the runtime bytecode
	codeHash := crypto.Keccak256(types.ProxyAdminRuntimeBytecode)

	// Create the EVM account object
	evmAccount := statedb.Account{
		Nonce:    1,             // to prevent tx nonce=0 conflicts
		Balance:  new(uint256.Int), // zero balance by default
		CodeHash: codeHash,      // link to deployed code
	}

	// Set the EVM account with the proxy admin contract
	err := evmKeeper.SetAccount(sdkCtx, proxyAdminAddress, evmAccount)
	if err != nil {
		panic("failed to set proxy admin contract account: " + err.Error())
	}

	// Store the runtime bytecode linked to the code hash
	evmKeeper.SetCode(sdkCtx, codeHash, types.ProxyAdminRuntimeBytecode)

	// Initialize storage slot 0 (Ownable.owner) with the owner address (left padded to 32 bytes)
	evmKeeper.SetState(sdkCtx, proxyAdminAddress, common.Hash{}, common.LeftPadBytes(owner.Bytes(), 32))
}

// CallFactoryToDeployUEA deploys a new UEA using factory contract
// Returns deployment response or error if deployment fails
func (k Keeper) CallFactoryToDeployUEA(
	ctx sdk.Context,
	from, factoryAddr common.Address,
	universalAccount *types.UniversalAccountId,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: deployUEA",
		"factory", factoryAddr.Hex(),
		"chain_namespace", universalAccount.ChainNamespace,
		"chain_id", universalAccount.ChainId,
		"owner", universalAccount.Owner,
	)

	abi, err := types.ParseFactoryABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse factory ABI")
	}

	abiUniversalAccount, err := types.NewAbiUniversalAccountId(universalAccount)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal account")
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,        // who is sending the transaction
		factoryAddr, // destination: FactoryV1 contract
		big.NewInt(0),
		nil,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"deployUEA",
		abiUniversalAccount,
	)
}
