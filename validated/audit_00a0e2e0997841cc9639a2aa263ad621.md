### Title
Unbounded recursion in bytecode segment hashing/structuring allows stack-overflow DoS via a crafted `declare` transaction - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
Similar to CVE-2019-20198, where `ezxml_ent_ok()` recurses without a depth bound over attacker-supplied XML, several functions in the sequencer recurse over the `bytecode_segment_lengths` (`NestedIntList`) structure of a Sierra→CASM compiled class without any depth limit. This structure's nesting is derived from the *nesting of control flow/branches* in the Sierra program submitted in a `declare` transaction, and a class declarer fully controls it. Because there is no cap on segmentation depth in these code paths, a crafted class can drive native-stack recursion deep enough to overflow the thread stack.

### Finding Description
When a class is declared, the sequencer compiles the submitted Sierra to CASM and computes its compiled-class hash to validate it against the value in the transaction: [1](#0-0) 
This calls `hash()`, which dispatches to `bytecode_hash`/`bytecode_hash_node`: [2](#0-1) 
`bytecode_hash_node` recurses once per nesting level of the segment tree with **no depth check whatsoever** — unlike the sibling function `NestedFeltCounts::new_inner` in the blockifier, which explicitly asserts `segmentation_depth <= 1`: [3](#0-2) 
The same unbounded-recursion pattern also exists in the Starknet OS hint helper used when re-executing/proving a block, which builds the analogous segment tree for every declared/executed class: [4](#0-3) 
This is invoked from `load_classes_and_create_bytecode_segment_structures`, which runs for every compiled class touched by a block during OS re-execution: [5](#0-4) 
And again the class-hash check performed on the declare transaction itself: [6](#0-5) 

The nesting of `bytecode_segment_lengths` is produced by the Cairo compiler based on the structure of the submitted Sierra program (functions/branches). Because compilation is deterministic and there is no explicit rejection of deeply-nested/adversarial control-flow shapes before this hash computation, a class declarer can shape a Sierra program whose compiled segment tree is nested to a depth sufficient to exhaust the native call stack in `bytecode_hash_node`, `create_bytecode_segment_structure_inner`, and related helpers, none of which are tail-recursive or iterative.

### Impact Explanation
A stack overflow in these recursive routines crashes the process performing the computation:
- In the Sierra compiler / class manager component during `declare` handling (`SierraCompiler::compile`), this can crash the compiler service that every sequencer relies on for admitting new declares.
- In `starknet_os` re-execution/proving, this can crash the re-execution/proving pipeline for a block containing the malicious class, potentially stalling block confirmation for that height (network unable to confirm new transactions / prove blocks), since the OS-hint code path runs deterministically for every honest node re-executing or proving the block.

This matches "network unable to confirm new transactions" and process-crash-based availability impact, which is within the accepted Medium/High impact categories.

### Likelihood Explanation
Any account able to submit a `declare` transaction (an unprivileged, permissionless action) can attempt this by submitting a Sierra program engineered to compile into a deeply nested `bytecode_segment_lengths` tree. Exploitability depends on how deep an adversarial-but-valid Sierra program's segmentation can go before the compilation step itself becomes prohibitively expensive/rejected (e.g. via `max_contract_bytecode_size`/`max_contract_class_object_size` limits in the gateway config), so an attacker must trade off contract size against nesting depth. Given typical native stack sizes (single-digit MB) and multi-hundred-byte-per-frame recursion, a few thousand to tens of thousands of nesting levels — plausibly achievable from a bytecode of at most `max_contract_bytecode_size` (81920) instructions with deeply nested branch structure — would suffice, making this feasible without requiring collusion or privileged access.

### Recommendation
- Add an explicit maximum recursion/segmentation depth check (mirroring the existing `assert!(segmentation_depth <= 1, ...)` guard already present in `NestedFeltCounts::new_inner`) to `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs`), `create_bytecode_segment_structure_inner` (`crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`), and `get_visited_segments` (`crates/blockifier/src/execution/contract_class.rs`), rejecting classes whose segment tree exceeds the bound during declare validation.
- Alternatively, convert these functions to iterative (stack-based) traversal instead of native recursion so an adversarial nesting depth cannot exhaust the thread stack.
- Ensure the same bound is enforced consistently by the Sierra→CASM compiler itself so nonconforming classes are rejected at compile time, before hash computation or OS re-execution ever sees them.

### Proof of Concept
1. Craft a Sierra program whose control-flow structure (e.g., deeply nested `match`/branch chains or deeply nested function calls near the `max_contract_bytecode_size` limit) compiles to a `CasmContractClass` with a `bytecode_segment_lengths: NestedIntList::Node(...)` nested to a depth on the order of the native stack's frame capacity (empirically a few thousand to tens of thousands of levels, depending on frame size).
2. Submit this class via a `declare` transaction (v2/v3) to the gateway.
3. During compilation (`SierraCompiler::compile` → `executable_class.hash(&HashVersion::V2)`), `bytecode_hash_node` recurses once per nesting level with no depth guard, exhausting the stack and crashing the compiling process; alternatively, if compilation succeeds and the class is later declared/used, the same unbounded recursion is triggered again during OS re-execution/proving via `create_bytecode_segment_structure_inner`.

```rust
fn bytecode_hash<H, NL>(bytecode: &[Felt], bytecode_segment_lengths: &NL) -> Felt
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    let mut bytecode_iter = bytecode.iter().copied();
    let (len, bytecode_hash) =
        bytecode_hash_node::<H, NL>(&mut bytecode_iter, bytecode_segment_lengths);
    assert_eq!(len, bytecode.len());
    bytecode_hash
}

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
```

```rust
pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
```
