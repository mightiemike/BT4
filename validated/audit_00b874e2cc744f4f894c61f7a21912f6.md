### Title
Legacy `ExchangeProcessor` bancor math can silently corrupt/overflow instead of reverting when an exchange pool's token balance is driven near zero - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Asymmetry report describes a zero-supply edge case: a sole LP-share holder can shrink `totalSupply` to `1`, after which `underlyingValue` can be forced to `0`, causing `preDepositPrice = 0` and a divide-by-zero DoS in `stake()`. The analogous asset in java-tron's Exchange (TRC10 AMM) module is a pool's `firstTokenBalance`/`secondTokenBalance`, and the analogous price-ratio computation is `ExchangeProcessor.exchange()`, which is reachable from any account via the unprivileged, broadcastable `ExchangeTransactionContract`.

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  selects between a legacy `ExchangeProcessor` (double/float bancor math) and a `SafeExchangeProcessor` (BigDecimal, hardened) depending on `hardenedCalc` (`allowHarden()`), which is controlled by a dynamic-property/proposal flag: [2](#0-1) . On any deployment/network of this codebase where that hardening proposal has not been activated, every `ExchangeTransactionContract` still executes through the legacy, un-hardened `ExchangeProcessor`.

The legacy processor does the bancor computation with raw doubles: `exchangeToSupply` divides `quant` by `newBalance` and computes `Math.pow`, and `exchangeFromSupply` mutates a *local* `supply` variable (`supply -= supplyQuant`) and then divides `supplyQuant / supply` before another `pow` call [3](#0-2) . The result is cast directly with `(long) issuedSupply` / `(long) exchangeBalance` — a plain narrowing cast, not `longValueExact()` — so `Infinity`, `-Infinity`, or `NaN` silently become `Long.MAX_VALUE`, `Long.MIN_VALUE`, or `0` respectively instead of throwing. This bypasses the `catch (ArithmeticException e)` safety net that both `ExchangeTransactionActuator.execute()`/`validate()` and `ExchangeWithdrawActuator`/`ExchangeInjectActuator` rely on [4](#0-3) . By contrast, the hardened `SafeExchangeProcessor` uses `BigDecimal` division and `longValueExact()`, which does throw on overflow/undefined results [5](#0-4) , confirming that the un-hardened path is the historically-fixed-but-still-reachable variant of this exact bug class.

The trigger condition mirrors the safETH report's "sole holder drains supply to 1": any account can call `ExchangeCreateActuator` to become the (self-assigned, non-privileged) `creatorAddress` of its own pool [6](#0-5) , then repeatedly call `ExchangeWithdrawActuator`, whose `doValidate()`/`execute()` only guard against a balance of exactly `0` (`"Token balance in exchange is equal with 0, the exchange has been closed"`), never against a near-zero balance such as `1` [7](#0-6) . The same shallow `==0` guard exists in `ExchangeInjectActuator` [8](#0-7)  and `ExchangeTransactionActuator` [9](#0-8) , exactly matching the "check only for the absolute zero case, not the near-zero degenerate case" flaw called out in the original report. With the pool's `firstTokenBalance` driven to `1`, any unprivileged account (not just the creator) can then submit an `ExchangeTransactionContract` with a large `tokenQuant`, causing `exchangeToSupply`'s `quant/newBalance` ratio to become huge, `Math.pow` to overflow toward `Infinity`, and the local relay `supply` in `exchangeFromSupply` to be driven to zero/negative — producing a silently corrupted `anotherTokenQuant` instead of a reverted transaction.

### Impact Explanation
The impact is localized to the specific exchange pool (not global consensus), matching the Medium-severity classification of the original finding: the pool's balances/accounting can either become permanently unusable (perpetual `ContractExeException` failures resembling a DoS, since every subsequent `ExchangeTransactionActuator` call recomputes the same broken ratio) or, worse, silently mint/allocate a corrupted `anotherTokenQuant` (e.g. `Long.MAX_VALUE`) that is then added to a real account's TRC10/TRX balance via `addAssetAmountV2`/`setBalance` in `execute()` [10](#0-9) , which is an asset-accounting-corruption outcome, not merely a revert.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the vulnerable legacy path is only exercised when the chain's `allowHarden()` dynamic property/proposal has not been enabled (this is the pre-hardening default and remains the code path for any private/consortium chain built from this codebase that has not activated that specific proposal); (2) getting the relay/supply math to actually reach an overflow region requires driving a pool balance down to a very small value through many creator-only `ExchangeWithdraw` calls and then submitting a transaction with a disproportionately large `tokenQuant`, which is gated by balance/asset-sufficiency checks but not by any minimum-pool-balance floor. This is a real, reachable, but non-trivial-to-execute condition — comparable to the Medium severity assigned to the original safETH finding.

### Recommendation
1. In `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator`, replace the `firstTokenBalance == 0 || secondTokenBalance == 0` checks with a check against a configurable minimum pool balance (analogous to the report's suggestion of enforcing `minimumSupply`), rejecting withdrawals/injections that would leave either balance below that floor.
2. Deprecate/remove the legacy `ExchangeProcessor` double-based path entirely (always use `SafeExchangeProcessor`), or at minimum replace the raw `(long)` casts in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` with an explicit finiteness/range check that throws `ArithmeticException` on `Infinity`/`NaN`/out-of-range results, so it is caught by the existing `catch (ArithmeticException e)` handlers.
3. Add an explicit sanity check on `anotherTokenQuant` (must be `> 0` and not exceed the pool's opposing balance) before it is applied to account balances in all three Exchange actuators.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create pool P with `firstTokenBalance = X`, `secondTokenBalance = Y` (self-assigned creator, unprivileged action) — `ExchangeCreateActuator.execute()` [11](#0-10) .
2. Attacker repeatedly calls `ExchangeWithdrawContract` as the pool creator, each time withdrawing amounts that only avoid the `==0` guard, until `firstTokenBalance` (or `secondTokenBalance`) equals `1` — guard only rejects exact zero [12](#0-11) .
3. Any account (not necessarily the creator) submits `ExchangeTransactionContract` selling a large `tokenQuant` of the opposite token against pool P.
4. `ExchangeCapsule.transaction()` invokes legacy `ExchangeProcessor.exchange()` (since `allowHarden()` is false on the target network) [13](#0-12) ; with the tiny `sellTokenBalance`/`buyTokenBalance`, the internal `pow` computations approach `Infinity`/`NaN`, and the `(long)` cast silently yields a corrupted, non-`ArithmeticException`-triggering `anotherTokenQuant`, which is then credited to the attacker's account via `addAssetAmountV2`/`setBalance`, or alternatively causes the pool to become permanently unusable for legitimate trades (repeated failures on every subsequent call).

    Processor processor = hardenedCalc

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
