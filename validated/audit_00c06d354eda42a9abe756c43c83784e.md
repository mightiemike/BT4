## Analysis

The external report's core pattern — a resource identifier (`_cardId`) accepted without verifying it belongs to the caller's own scope, allowing action on another owner's asset — maps to Push Chain's CEA (Cross-account Execution Address) inbound-execution path in `x/uexecutor`.

### Title
Unauthorized UEA payload execution via attacker-controlled CEA `Recipient` in `ExecuteInboundFundsAndPayload` - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
For a `TxType` inbound with `IsCEA=true`, the recipient UEA address is taken directly from attacker-supplied inbound event data rather than being deterministically derived from the source-chain sender. When that recipient happens to be an already-deployed UEA belonging to a different owner, the function still falls through to the generic "execute payload via UEA" step, invoking `ExecutePayloadV2`/`CallUEAExecutePayload` with the `uexecutor` module account as `from`. Per the module's documented design, calls originating from the module account (`UNIVERSAL_EXECUTOR_MODULE`) bypass the UEA contract's owner-signature check — that bypass is safe only when the target UEA is provably derived from the same sender who signed the source-chain transaction (the non-CEA path). In the CEA branch there is no such binding check between `utx.InboundTx.Sender` and the arbitrary `Recipient`/`ueaAddr`.

### Finding Description [1](#0-0) 
sets `ueaAddr = common.HexToAddress(utx.InboundTx.Recipient)` — an attacker-controlled field decoded from the raw source-chain gateway event — and only checks `isUEA` (whether the factory recognizes it as *some* deployed UEA), not whether it is the UEA belonging to `utx.InboundTx.Sender`.

Execution then proceeds past the CEA-specific branches (deposit-only accounting) into the shared payload-execution step: [2](#0-1) 
which calls `ExecutePayloadV2(ctx, ueModuleAddr, ueaAddr, utx.InboundTx.UniversalPayload, utx.InboundTx.VerificationData)` — `ueaAddr` here is the attacker-chosen `Recipient`, and the sender is the module account, not the attacker's own derived EVM address. [3](#0-2)  shows `ExecutePayloadV2` unconditionally calls `CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, ...)`. [4](#0-3)  documents that the on-chain signature check is only guaranteed to fire "since `evmFrom != UNIVERSAL_EXECUTOR_MODULE`" — implying the module-account sender path is a deliberate bypass of the UEA's owner-signature check, safe only because in the non-CEA flow `ueaAddr` is deterministically computed from the observed sender (`CallFactoryToGetUEAAddressForOrigin` with `universalAccountId` built from `utx.InboundTx.Sender`, see lines 30–39 and 106). In the CEA flow, that binding is absent — `ueaAddr` comes straight from attacker-controlled `Recipient`.

Because inbound observations reach finalization once honest Universal Validators reach quorum on the *observed event bytes* (which the attacker fully controls when crafting the source-chain gateway call, including the `recipient`/CEA target and the `UniversalPayload`/`VerificationData` fields), an attacker can submit a genuine, honestly-observed source-chain gateway transaction that sets `isCEA=true`, `Recipient` = a victim's already-deployed UEA address, and a `UniversalPayload` whose `data` calls something like `transfer`/`approve` on a PRC20 the victim's UEA holds. Once observed and voted PASSED by honest UVs (no validator misbehavior required — they are just relaying what actually happened on the source chain), the module executes that payload against the victim's UEA using the module's signature-check-bypass privilege.

### Impact Explanation
This is unauthorized UEA execution (in-scope: "unauthorized UEA or CEA execution ... unauthorized state transitions in universal execution flows") reachable by an ordinary unprivileged attacker who only needs to submit a transaction on any supported source chain — no validator, relayer, or admin compromise required. The impact is direct: arbitrary EVM calldata execution against a third party's UEA using the module's bypass of the UEA's own signature check, which can be used to drain PRC20/native balances held by that UEA (theft of user-controlled funds).

### Likelihood Explanation
Likelihood is high for any unprivileged attacker: they only need to (a) know or discover a victim's deployed UEA address (these are deterministic/computable and often public), and (b) submit a normal gateway call on a source chain with `isCEA=true` and `recipient` set to that UEA plus a malicious payload. No collusion with validators, relayers, or TSS signers is needed — UVs are only asked to honestly observe and vote on an event that genuinely occurred, which the attacker fully controls the content of.

### Recommendation
In the CEA branch, when `isUEA == true`, verify that `ueaAddr` corresponds to the UEA deterministically derived from `utx.InboundTx.Sender` (via `CallFactoryToGetUEAAddressForOrigin`) before allowing the module-bypass payload-execution step to proceed. If `ueaAddr` does not match the sender's own UEA, either reject the payload-execution step (deposit-only, as already done for the EOA/non-UEA sub-case) or require standard signature verification (module should not use its bypass privilege against a UEA it did not derive from the observed sender).

### Proof of Concept
1. Attacker deploys/derives their own UEA `A` on Push Chain via the factory (normal onboarding), and separately knows victim's UEA address `V` (holding PRC20 balance).
2. Attacker submits a gateway transaction on a supported external chain (e.g., Sepolia) that emits an inbound event with: `tx_type = FUNDS_AND_PAYLOAD` (or similar), `isCEA = true`, `recipient = V` (victim's UEA, not attacker's), `universal_payload.data` = ABI-encoded call transferring `V`'s PRC20 balance to attacker's address, and `verification_data` set to arbitrary/empty bytes (irrelevant, since the module-bypass path does not enforce it against `V`'s owner key).
3. Honest UVs observe this genuine on-chain event and vote it via `MsgVoteInbound`; ballot reaches PASSED because the observation is accurate.
4. `ExecuteInboundFundsAndPayload` runs: since `Recipient` (`V`) is a real UEA, `isUEA=true`; deposit step (if any) runs against `V`; execution falls through to the shared "Step 3" which calls `ExecutePayloadV2(ctx, ueModuleAddr, V, ...)`, bypassing `V`'s owner signature check because the caller is the module account, and executes attacker's malicious payload — draining `V`'s PRC20 balance to the attacker.

func (k Keeper) ExecutePayloadV2(ctx context.Context, evmFrom common.Address, ueaAddr common.Address, universalPayload *types.UniversalPayload, verificationData string) (*vmtypes.MsgEthereumTxResponse, error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Debug("execute payload v2",
		"uea", ueaAddr.Hex(),
		"from", evmFrom.Hex(),
	)

	// Step 1: Validate payload and verificationData early (fast-fail before EVM work)
	if _, err := types.NewAbiUniversalPayload(universalPayload); err != nil {
		return nil, errors.Wrapf(err, "invalid universal payload")
	}

	verificationDataVal, err := utils.HexToBytes(verificationData)
	if err != nil {
		return nil, errors.Wrapf(err, "invalid verificationData format")
	}

	// Step 2: Wrap EVM execution + fee deduction in a CacheContext so they
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
	}

#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
