## Title
Native-position `Extension` writes are silently dropped from the persisted `WriteSet` when serialized as `WriteSetV0`, causing replay/restore to reconstruct a different ledger state - (File: `types/src/write_set.rs`)

### Summary
`WriteSetV0` marks its `hotness` and `extensions` fields `#[serde(skip)]`, so `bcs::to_bytes(&WriteSet::V0(..))` (used verbatim by `WriteSetSchema::encode_value` in storage) never serializes `Extension::NativePosition` data, even when it is populated via `WriteSet::add_native_positions`. [1](#0-0) [2](#0-1) 

### Finding Description
`WriteSet::add_native_positions` can install a `Extension::NativePosition(BTreeMap<StateKey, NativePositionOp>)` bucket onto *either* `WriteSetV0` or `WriteSetV1` — the method operates generically through `extensions_mut()`, which dereferences into whichever variant the `WriteSet` currently holds, with no compile-time or runtime check that the write set is V1 before installing extensions. [3](#0-2) [4](#0-3) 

Whether a `TransactionOutput`'s write set is upgraded to V1 is decided purely by the `HOTNESS_IN_EPILOGUE` feature flag, via `convert_write_sets_to_v1` / `TransactionOutput::convert_write_set_to_v1`, gated in `BlockExecutorConfigFromOnchain::with_features`: [5](#0-4) [6](#0-5) 

However, native-position writes themselves are gated by the separate `TRADING_NATIVE`/`NATIVE_POSITION` feature flags, not by `HOTNESS_IN_EPILOGUE`: [7](#0-6) 

The `compute_trading_native_state_roots` config comment explicitly acknowledges the danger — the on-chain-config layer only "degrades to off" the *state-root computation* if `HOTNESS_IN_EPILOGUE` is off, but this is a coarse-grained runtime knob and does not stop native-position VM writes from being emitted while the write set remains `WriteSetV0`: [8](#0-7) 

`WriteSetSchema::encode_value` calls `bcs::to_bytes(self)` directly on the `WriteSet` enum, and because `WriteSetV0::hotness`/`extensions` are `#[serde(skip)]`, any `Extension::NativePosition` payload attached to a V0-tagged write set is silently discarded on persistence — no error, no panic, and the persisted bytes decode back into a `WriteSet::V0` with an *empty* extensions vector: [9](#0-8) 

Any code path that reconstructs post-commit state purely from the persisted `WriteSetSchema` — the transaction backup/restore path (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`), replay-verify tooling, chunk-executor re-apply, or state-sync serving stored write sets to peers — would silently reconstruct a ledger missing the native-position (`TradingNative`/position) state updates that were actually applied by the original executing node, because the position writes never round-trip through this schema in the first place. This is precisely the same bug class as the referenced report: a value that is semantically present in the domain model gets silently dropped/rejected by a lower-level serialization/encoding boundary that the higher-level code assumed would faithfully carry it through.

### Impact Explanation
This falls under "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and "Hard-fork-only divergence during commit, replay, restore." If a validator (or a chunk executor / backup-restore consumer) ever emits or reads a `WriteSetV0` that carried native-position writes, replaying that write set from durable storage yields a ledger state that omits the position writes entirely, silently diverging from the state the original execution produced (and from the state other, still-in-memory-consistent nodes hold). Because position writes feed into `position_state_checkpoint_hash` (a proof-integrity, consensus-committed field once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is on), any downstream consumer relying on the persisted `WriteSet` (rather than the transient `TransactionOutput`) to recompute or verify that root would derive a mismatching value.

### Likelihood Explanation
I could **not fully verify** in this pass whether current production code paths ever call `add_native_positions` while the containing `WriteSet` is still tagged `V0` at persistence time — the `BlockExecutorConfigFromOnchain::with_features` logic tries to prevent the *state-root feature* from being enabled without `HOTNESS_IN_EPILOGUE`, and `add_native_positions` may only be invoked downstream of `convert_write_sets_to_v1`. Confirming the exact call order (whether native-position extension attachment always happens strictly after the V0→V1 upgrade, for every code path including chunk-executor replay and any transaction-generation/test harnesses) requires tracing `add_native_positions`' callers, which I was unable to complete before running out of iterations. Given this uncertainty about whether the ordering invariant is actually enforced everywhere, and because the type system does nothing to prevent attaching extensions to a `WriteSetV0`, I flag this as a real structural landmine rather than a confirmed, exploitable-today divergence.

### Recommendation
- Make `add_native_positions` (and `add_hotness`) fail/panic (or be type-unavailable) when called on `WriteSet::V0`, instead of silently succeeding and later losing data at serialization time.
- Alternatively, have `WriteSetSchema::encode_value` reject (`bail!`) attempting to persist a `WriteSetV0` that has a non-empty `extensions`/`hotness` bucket, rather than silently dropping it via `#[serde(skip)]`.
- Add a targeted unit/round-trip test asserting that a `WriteSet` with populated `Extension::NativePosition` always survives a `WriteSetSchema` encode/decode cycle bit-for-bit, mirroring the pattern used for `LegacyWriteSetV1Payload` compatibility.

### Proof of Concept
Local code-level trace (not run in this environment; based on static analysis of the cited files):
1. Construct `let mut ws = WriteSetMut::new(vec![]).freeze().unwrap();` → yields `WriteSet::V0(WriteSetV0::default())`.
2. Call `ws.add_native_positions(btreemap!{ some_key => NativePositionOp::from_write_op(write_op) });` — succeeds silently because `extensions_mut()` matches on `Self::V0` and returns `&mut ws.extensions` with no assertion that the variant is V1 [10](#0-9) .
3. `WriteSetSchema::encode_value(&ws)` → `bcs::to_bytes(&ws)`; because `WriteSetV0::extensions` is `#[serde(skip)]`, the serialized bytes contain no trace of the native-position entry [1](#0-0) .
4. `WriteSetSchema::decode_value` on those bytes returns a `WriteSet::V0` whose `native_position_iter()` yields nothing, even though the originally-committed transaction wrote a position update.

Because I could not confirm within the remaining iterations that every caller enforces "upgrade to V1 before calling `add_native_positions`," I present this as the strongest local candidate matched against the report's bug class, but recommend a Devin/engineering follow-up to trace all callers of `add_native_positions` and `convert_write_set_to_v1` before treating this as a confirmed, high-severity finding.

    fn encode_value(&self) -> Result<Vec<u8>> {
        bcs::to_bytes(self).map_err(Into::into)
    }

    fn decode_value(data: &[u8]) -> Result<Self> {
        // TODO(HotState): we could simply use `bcs::from_bytes` for everything once the latest
        // release branch does not write LegacyWriteSetV1Payload and forge-compat test would not
        // fail in CI.
        match data.first() {
            Some(&1) => match bcs::from_bytes::<WriteSet>(data) {
                Ok(ws) => Ok(ws),
                // Legacy V1 payload lacks the trailing `extensions` field, so the new decoder
                // runs out of bytes while reading it. Any other error indicates real corruption
                // and should propagate.
                Err(bcs::Error::Eof) => {
                    let legacy: LegacyWriteSetV1Payload = bcs::from_bytes(&data[1..])?;
                    let mut ws = WriteSet::V0(legacy.value);
                    ws.add_hotness(legacy.hotness);
                    Ok(ws)
                },
                Err(e) => Err(e.into()),
            },
            _ => bcs::from_bytes::<WriteSet>(data).map_err(Into::into),
        }
    }
}
