Based on my investigation, the relevant code path is `get_txs` in `L1EventsProvider`, which calls `tx.tx.calc_msg_hash()` on every `L1HandlerTransaction` pulled from the provider when the sequencer is building a proposal [1](#0-0) . That in turn calls `l1_handler_message_hash`, which does an unchecked `calldata.0.split_first().expect(...)` on the transaction's `Calldata` [2](#0-1) .

### Title
Panic (DoS) on `.expect()` in `l1_handler_message_hash` when L1 handler calldata is empty - ([File: crates/starknet_api/src/hash.rs])

### Summary
`l1_handler_message_hash` unconditionally calls `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")` [3](#0-2) . If `calldata.0` is empty, this panics instead of returning an error, analogous to the DNS OOB-read/crash in the reported CVE where a malformed message without payload causes a crash.

### Finding Description
The codebase itself acknowledges that `L1HandlerTransaction.calldata` can legitimately be empty at the type level: `payload_size()` explicitly guards against it with `saturating_sub(1)`, noting "`L1HandlerTransaction` derives `Deserialize` and `Calldata` has no non-empty invariant" and would otherwise underflow in release builds [4](#0-3) . This shows the type does not statically guarantee `calldata.0` is non-empty; the invariant is only maintained by convention at construction sites (e.g., `EventData::from` and RPC `MessageFromL1::from` always prepend `from_address`) [5](#0-4) [6](#0-5) .

Unlike `payload_size()`, `l1_handler_message_hash` has no such guard and will panic via `.expect()` if that invariant is ever violated for a transaction that reaches it [2](#0-1) . This function is reached from the sequencer's L1 events provider on every proposal-building call, `get_txs`, which logs `tx.tx.calc_msg_hash()` for every transaction it returns for sequencing [7](#0-6) , and is also exposed via the RPC API (`api_impl.rs`, matched in my search but not fully inspected).

### Impact Explanation
If reached with empty calldata, this causes a hard Rust panic. Since `get_txs` is invoked by the proposer during block building for every L1 handler transaction slated for sequencing, a panic here would crash the batcher/sequencer process handling proposals — a denial-of-service on the block-building path, potentially preventing the network from confirming new transactions if this path is hit deterministically by all validators (honest-node divergence / halt), similar in effect to the original CVE's DoS impact.

### Likelihood Explanation
**Uncertain / likely low in practice.** All discovered construction paths (`EventData::from`, RPC `MessageFromL1::from`, `L1EventsScraper`) always prepend the L1 sender address before constructing calldata, so calldata should never actually be empty when built through the normal L1-event ingestion pipeline. I could not find a concrete, unprivileged-reachable path (e.g., a gateway/RPC endpoint accepting an arbitrary `L1HandlerTransaction` with attacker-controlled empty calldata) that flows into `calc_msg_hash()`/`get_txs()`. The defensive `saturating_sub` fix in `payload_size()` suggests the underlying type's lack of invariant was a known concern, but I did not find evidence of the same gap being exploited for `calc_msg_hash`. Given the ask-only scope and inability to trace a concrete external trigger, I flag this as a **likely non-exploitable / unconfirmed** analog rather than a confirmed high-severity finding.

### Recommendation
Replace the `.expect()` panic in `l1_handler_message_hash` with a proper `Result`-returning check (mirroring the `saturating_sub` guard already used in `payload_size()`), so that empty calldata produces a typed error instead of crashing the process, and audit all callers (`get_txs`, RPC `api_impl.rs`) to propagate that error instead of relying on construction-site invariants that the type system does not enforce.

### Proof of Concept
Not confirmed as concretely reachable by an unprivileged actor. A conceptual PoC would require constructing/injecting an `L1HandlerTransaction` with `calldata.0 == vec![]` into a path that eventually calls `.calc_msg_hash()` (e.g., `L1EventsProvider::get_txs` or the RPC `api_impl.rs` handlers that call `l1_handler_message_hash` /`calc_msg_hash`). I was not able to verify, within the scope of this investigation, an entry point where an untrusted L1 sender or RPC caller can supply such empty calldata that survives to reach this call — this would need further tracing of `api_impl.rs` and the gateway/mempool ingestion of L1 handler transactions to confirm real-world exploitability.
