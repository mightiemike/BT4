### Title
Outbound events with amounts exceeding Solana's u64 range get stuck permanently in CONFIRMED with unbounded retries and no terminal failure/revert - (File: universalClient/tss/coordinator/coordinator.go, universalClient/chains/svm/tx_builder.go)

### Summary
An unprivileged user bridging any ordinary token with 18 decimals (a very common ERC20 configuration) to a Solana (SVM) destination in an amount as small as ~18.45 whole tokens produces a raw `Amount` value greater than `u64::MAX` (2^64-1 ≈ 1.8446744e19). This amount passes all on-chain validation (`Inbound.ValidateForExecution` and `OutboundTx.ValidateBasic` only check "valid uint256, non-negative/positive"), gets attached verbatim to `OutboundCreatedEvent.Amount`, and is picked up by the coordinator's TSS signing pipeline. The Solana `TxBuilder.GetOutboundSigningRequest` correctly rejects it with `"amount exceeds u64 max"`, but the coordinator never converts this deterministic, permanent failure into a terminal event state — the event stays `CONFIRMED` forever and is retried every poll tick indefinitely.

### Finding Description
The call path is:
`Coordinator.pollLoop` → `processConfirmedEvents` (universalClient/tss/coordinator/coordinator.go:337) → `processEventAsCoordinator` (coordinator.go:468-473) → `createSignSetup` → `buildSignTransaction` (coordinator.go:740-785) → `client.GetTxBuilder().GetOutboundSigningRequest` (svm/tx_builder.go:188-214). [1](#0-0) 

When `GetOutboundSigningRequest` returns an error (e.g., amount overflow), `buildSignTransaction` propagates it, `createSignSetup` propagates it, and `processEventAsCoordinator` propagates it up to `processConfirmedEvents`, which does nothing but log: [2](#0-1) 

The event's DB row (`store.Event`) is never updated to a terminal `FAILED`/`REVERTED` state, and sign events carry `ExpiryBlockHeight: 0` (no client-side expiry) — confirmed by the event-parser test comment: [3](#0-2) 

So `GetNonExpiredConfirmedEvents` (coordinator.go:383) will keep returning this event on every poll tick forever, and the amount-overflow error will recur identically every time since the underlying event data never changes. There is no path in the coordinator, session manager, or tx broadcaster that observes "outbound build permanently fails" and converts the outbound to a failed/reverted terminal state — that machinery (txresolver, expirysweeper) only operates on events that reach `SIGNED`/`BROADCASTED` state, which this event never does.

The root cause is that neither `x/uexecutor/types/inbound.go:ValidateForExecution` (bounds-checks only as "valid non-negative uint256") nor `x/uexecutor/types/outbound_tx.go:ValidateBasic` (bounds-checks only as "valid positive uint256") is aware of destination-chain VM-specific numeric limits (u64 for SVM) at the time the `OutboundTx`/`OutboundCreatedEvent` is created on-chain — the check only happens client-side inside the SVM `TxBuilder`, too late to prevent a stuck record.

### Impact Explanation
The affected outbound's funds are effectively permanently stuck: value was already accounted for on the Push Chain side (burned/locked in anticipation of the outbound) and the event enters a state from which it can never be signed, broadcast, or reverted — it just gets retried forever with the exact same deterministic failure. This is unreachable-liveness for that specific transfer, matching the allowed "permanent freezing... of user or protocol-controlled funds" impact. The trigger condition is realistic and cheap: any 18-decimal token withdrawal above ~18.45 tokens (or any token/decimals combination whose raw amount exceeds 2^64-1) targeting a Solana destination chain reaches this state via ordinary, unprivileged withdrawal flow — no malicious validator, TSS participant, or admin involvement required.

The "expensive parse/hash amplification" framing in the original question is not accurate — the actual parse (`big.Int.SetString`, `IsUint64()`) is cheap, not a compute-DoS vector. The real, in-scope defect is the missing terminal-failure/revert transition for a class of outbounds the SVM builder will always reject, not amplification cost.

### Likelihood Explanation
High likelihood of being hit unintentionally (any user bridging normal amounts of common 18-decimal tokens to Solana), and trivially and intentionally triggerable by an attacker who wants to grief their own or another party's outbound into a permanently stuck state. No privileged actor is needed — this is reachable purely through the ordinary inbound-deposit → outbound-creation → TSS-coordinator pipeline.

### Recommendation
- Add a destination-chain-VM-aware amount bound check (e.g., u64 limit for SVM chains) at `OutboundTx.ValidateBasic()` in `x/uexecutor/types/outbound_tx.go` or in `BuildOutboundsFromReceipt` in `x/uexecutor/keeper/create_outbound.go`, before the outbound is ever attached to a UniversalTx and before `OutboundCreatedEvent` is emitted, so amounts that cannot be represented on the destination chain are converted into a failed PCTx / revert-outbound immediately (the same pattern already used for missing token config / invalid recipient failures).
- Alternatively/additionally, in `universalClient/tss/coordinator/coordinator.go`, when `buildSignTransaction`/`createSignSetup` returns a permanent (non-transient) error such as amount-overflow, transition the event to a terminal `FAILED`/`REVERTED` status in the event store instead of silently logging and retrying forever, and surface this so an on-chain revert/refund path can be triggered.

### Proof of Concept
1. Configure a token with 18 decimals normally used for cross-chain transfer, and a Solana destination chain enabled for outbound.
2. Submit (or vote as honest UVs on) an `Inbound`/withdrawal that results in `OutboundTx.Amount` = `"20000000000000000000"` (20 tokens × 10^18, i.e., > `2^64-1` = 18446744073709551615) with `DestinationChain` pointing at an SVM chain.
3. Observe `BuildOutboundsFromReceipt` (x/uexecutor/keeper/create_outbound.go:69-91) and `OutboundTx.ValidateBasic()` (x/uexecutor/types/outbound_tx.go:56-63) accept this amount without error, and `OutboundCreatedEvent` is emitted and picked up by the universalClient event listener as a `SIGN_OUTBOUND` event with `Status = CONFIRMED`.
4. Run the coordinator's `pollLoop` for several ticks and confirm via logs / DB inspection that `processConfirmedEvents` repeatedly calls `buildSignTransaction` → `GetOutboundSigningRequest`, which returns `"amount exceeds u64 max"` every single time, and that the event's `Status` in the event store remains `CONFIRMED` indefinitely (never transitions to `FAILED`/`REVERTED`, never expires since `ExpiryBlockHeight == 0` for sign events).
