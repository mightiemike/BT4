### Title
Attached deposit to `WalletContract::rlp_execute` is permanently stranded (never refunded) when transaction parsing fails before any promise is created - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`WalletContract::rlp_execute` is a `#[payable]` method, so any caller (the ETH-implicit account owner, a relayer, or an arbitrary third party) can attach a NEAR deposit when invoking it. That deposit is intended to be tracked via `CallerDeposit` and refunded if the resulting cross-contract call later fails [1](#0-0) . However, the refund logic only ever runs inside `rlp_execute_callback`, which is reached solely through the `Promise` path [2](#0-1) . If `inner_rlp_execute` returns an `Err` before ever constructing a `Promise` (e.g. malformed RLP, invalid ABI data, invalid account id, exhausted nonce, invalid key encoding, oversized value, etc.), `rlp_execute` short-circuits straight to `PromiseOrValue::Value(e.into())` without creating any promise and without ever refunding the attached deposit [3](#0-2) .

### Finding Description
`rlp_execute` computes `result = inner_rlp_execute(...)` and only handles two outcomes that produce a `Promise` (`Ok`, and `Err(Error::Relayer(_))` when the caller is itself the signer/owner, which routes to `create_ban_relayer_promise`) [4](#0-3) . Every other `Err(e)` variant — which includes all `Error::User(_)` variants (`InvalidAbiEncodedData`, `UnknownFunctionSelector`, `ExcessYoctoNear`, `ValueTooLarge`, `UnknownPublicKeyKind`, `InvalidEd25519Key`, `InvalidSecp256k1Key`, `InvalidAccessKeyAccountId`, `UnsupportedAction`, `EvmDeployDisallowed`), `Error::AccountId(_)`, `Error::AccountNonceExhausted`, and even `Error::Relayer(_)` when the caller is a non-owner external caller — falls into `Err(e) => PromiseOrValue::Value(e.into())` [5](#0-4) .

Inside `inner_rlp_execute`, `CallerDeposit::new(&context)` is computed from `env::attached_deposit()` for any non-self caller, precisely to guarantee a refund path exists [6](#0-5) . But `caller_deposit` is only consumed by the callback functions (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) that are chained onto a `Promise` [7](#0-6) . Every early return of `Err(err)` inside `inner_rlp_execute` (parsing errors at lines 389–393 and 394–409) bypasses `caller_deposit` entirely — the value is simply dropped and never referenced again, and no promise/refund transfer is ever scheduled.

Since NEAR requires `#[payable]` methods to explicitly transfer back any attached deposit they don't want to keep (there is no implicit auto-refund of `attached_deposit` for a successfully-returning method call, unlike a failed receipt which triggers the protocol-level deposit refund described in `docs/RuntimeSpec/Refunds.md`), the deposit is unconditionally absorbed into the wallet's own account balance whenever this early-error path is taken [8](#0-7) . Unlike a genuine account-owner deposit, funds attached by an external caller/relayer who intended to fund or pay a fee for a specific action are absorbed into an account they do not control the private key of — an ETH-implicit account can only ever be spent by signing an RLP transaction with the owner's Secp256K1 key [9](#0-8) . The external caller therefore has no mechanism whatsoever to reclaim that NEAR — directly analogous to the reported `SwapRouter.sol receive()` issue, where ETH sent to the contract is accepted but there is no code path to return or use it as intended.

### Impact Explanation
Any relayer or third-party caller that attaches NEAR to a `rlp_execute` call (for example, to cover a fee, a storage deposit, or a value transfer on behalf of the wallet owner) risks having that NEAR permanently and irrecoverably absorbed by the target ETH-implicit account whenever the RLP-encoded payload fails any of the numerous validation checks performed in `internal::parse_rlp_tx_to_action` prior to promise creation. Because the funds land in an account exclusively controlled by a Secp256K1 key the caller does not hold, this constitutes permanently frozen/stranded funds for the depositor — a concrete, unauthorized, and irreversible value loss.

### Likelihood Explanation
Likelihood is non-trivial: the wallet contract is explicitly designed to be invoked by third-party relayers relaying user-signed Ethereum-style transactions, and it is `#[payable]`, so nothing prevents any caller from attaching a deposit on any call, including malformed ones. Any of the many `UserError`/`AccountIdError`/`AccountNonceExhausted` conditions (e.g. a relayer bug, malformed base64, unsupported ABI selector, nonce exhaustion) triggers this path without requiring any privileged access. The project's own README notes the current implementation "must not use in production" and the contract build is currently disabled [10](#0-9) , which somewhat limits current exposure, but the code exists in-repo and is exercised by integration/unit tests as a live feature path (NEP-518), so the flaw is real in the shipped logic and would activate as soon as the contract is deployed for ETH-implicit accounts.

### Recommendation
In `rlp_execute`, ensure that any `Err(e)` branch that does not create a promise still issues a transfer to refund `env::attached_deposit()` (or the tracked `CallerDeposit`) back to the predecessor account before returning `PromiseOrValue::Value(e.into())`. Alternatively, compute and validate the transaction before accepting any deposit, or reject the call outright (panic) when `attached_deposit() > 0` and the call cannot yet guarantee refund-safe handling.

### Proof of Concept
1. A relayer calls `rlp_execute(target, tx_bytes_b64)` on an ETH-implicit account's `WalletContract`, attaching `N` yoctoNEAR as `attached_deposit` (e.g., intending to pre-fund a NEP-141 `storage_deposit` fee it expects to be refunded if unused).
2. The relayer supplies a `tx_bytes_b64` that fails validation in `internal::parse_rlp_tx_to_action` — for instance, ABI data shorter than 4 bytes (`UserError::InvalidAbiEncodedData`) or an out-of-range `yocto_near` (`UserError::ExcessYoctoNear`).
3. `inner_rlp_execute` reaches `Err(err @ Error::User(_)) => { *nonce = nonce.saturating_add(1); return Err(err); }` [11](#0-10) , and no `Promise` is ever created — `caller_deposit` computed earlier is discarded.
4. `rlp_execute` receives `Err(e)` and returns `PromiseOrValue::Value(e.into())` directly [12](#0-11) , with no refund transfer scheduled.
5. The `N` yoctoNEAR attached by the relayer is now part of the ETH-implicit account's balance, spendable only by the holder of the corresponding Secp256K1 private key — the relayer has no way to recover it.

**Uncertainty/limitations:** I was unable to fully trace `action_to_promise` (the function that turns a parsed `near_action::Action` into a `Promise`) because it was not returned by search/grep within the available iterations, so I cannot fully confirm whether `caller_deposit` is otherwise consumed somewhere in that function for the success path (this does not affect the finding above, since the issue is specifically about the early-`Err` paths that never reach `action_to_promise` at all). Also, per the crate's own README, this wallet-contract implementation is currently marked as a non-production placeholder with contract builds disabled, which may affect current real-world exploitability until/unless it is enabled for production ETH-implicit accounts.

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }

        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }

/// is available on Near. These errors relate to parsing a 20-byte address

pub enum AccountIdError {
    AccountIdTooShort,
    Missing0xPrefix,
    InvalidHex,
}

/// Errors which should never happen if the relayer is honest.
/// If these errors happen then we should ban the relayer (revoke their access key).
/// An external caller (as opposed to a relayer with a Function Call access key) may
/// also trigger these errors by passing bad arguments, but this is not an issue
/// (there is no ban list for external callers) because they are paying the gas fees
/// for their own mistakes.
#[derive(Debug, PartialEq, Eq, Clone)]
pub enum RelayerError {
    /// Relayers should always check the nonce before sending
    InvalidNonce,
    /// Relayers should always encode the transaction correctly
    InvalidBase64,
    /// Relayers should always send valid transactions
    TxParsing(aurora_engine_transactions::Error),
    /// Relayers should always send correctly signed transactions
    InvalidSender,
    /// Relayers should always give the correct target account
    InvalidTarget,
    /// Relayers should always check the transaction is signed with the correct chain id.
    InvalidChainId,
    /// Relayers should always attach at least as much gas as the user requested.
    InsufficientGas,
}
