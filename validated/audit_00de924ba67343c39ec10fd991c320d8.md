This confirms the technical premise of the question is false: the accounts write cache is keyed per-slot per-pubkey (`SlotCache::insert` in [1](#0-0) ), so repeated create/close/recreate cycles on the same key within one slot simply overwrite the same `DashMap` entry rather than accumulating N entries. `AccountsCache::store` only touches the cross-slot index when `is_new_key` is true, i.e. the first time that pubkey appears in that slot [2](#0-1) . Zero-lamport writes are further filtered at `write_accounts_to_cache`, which skips storing a zero-lamport account entirely when the ancestor state is already zero-lamport or doesn't exist (`is_ancestor_zero_lamport`), so a rapid zero->non-zero->zero toggle inside the same slot does not multiply the number of stored cache items [3](#0-2) . fn test_clean_multiple_zero_lamport_decrements_index_ref_count() {

    // immediately. Set latest full snapshot slot to zero to avoid cleaning zero lamport accounts
    accounts.set_latest_full_snapshot_slot(0);

    // Store non-zero versions of both accounts in slot 0, then kill pubkey1 twice (slots 1

    // the older version is in the index at flush, and reclaims the version it supersedes
    accounts.store_for_tests((

        [
            (&pubkey1, &one_lamport_account),
            (&pubkey2, &one_lamport_account),
        ]

    ));
    accounts.add_root_and_flush_write_cache(0);
    accounts.store_for_tests((1, [(&pubkey1, &zero_lamport_account)].as_slice()));
    accounts.add_root_and_flush_write_cache(1);
    accounts.store_for_tests((
        2,
        [
            (&pubkey1, &zero_lamport_account),
            (&pubkey2, &zero_lamport_account),
        ]
        .as_slice(),
    ));

    // reclaimed and marked obsolete during flush

    // zero-lamport flushes
    assert!(accounts.storage.get_slot_storage_entry(0).is_none());
    assert!(accounts.storage.get_slot_storage_entry(1).is_none());
