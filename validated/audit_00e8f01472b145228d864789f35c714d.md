### Title
Unbounded per-key re-traversal in `calc_delete_dependencies` causes quadratic clean-accounts cost for pinned/co-located accounts - (File: `accounts-db/src/accounts_db.rs`)

### Summary
`AccountsDb::calc_delete_dependencies` propagates "cannot delete" status through a BFS over slots, but for every processed slot it re-walks the *entire* `slot_list` of every pubkey referenced by that slot, with no per-pubkey visited-guard (only a per-slot guard via `already_counted`). An unprivileged attacker who repeatedly co-locates disposable ("throwaway") accounts with a long-lived ("anchor") account in the same slot's storage can force this same disposable pubkey's slot list to be re-scanned once per blocking slot, turning per-write cleanup cost into O(ref_count²) instead of O(ref_count), while paying only linear transaction fees.

### Finding Description
In `calc_delete_dependencies` [1](#0-0) , when a pubkey's stores are not all removable (either because `store_counts` shows a non-zero count for one of its slots, or `slot_list.len() != ref_count`), the code seeds a `pending_stores` BFS over the account's own slots [2](#0-1) . As the BFS pops a slot, it removes that slot's entry from `store_counts` exactly once (`already_counted` guards re-processing the *slot*), but for each `key` in that slot's `affected_pubkeys` set, it calls `update_pending_stores`, which unconditionally iterates that key's **entire** `slot_list` again [3](#0-2) . There is no `already_counted`-style guard at the pubkey level.

Consequently, if a pubkey `K` appears in the `affected_pubkeys` set of `R` different blocked slots (which happens naturally when `K` has `ref_count == R`, since `store_counts` construction inserts `K` into the key-set of every slot in `K`'s slot list [4](#0-3) ), then each of those `R` slots, when it is popped from `pending_stores` and found to be non-zero, triggers a full O(R) re-walk of `K`'s slot list. Total cost for `K` alone becomes O(R²).

An unprivileged attacker can force this: in every slot, submit transactions that write both (a) several "throwaway" accounts that will be superseded again next slot, and (b) one "anchor" account left untouched for a long time. Because the anchor keeps its slot's on-disk store count above zero, the throwaway accounts' stale versions in that slot can never satisfy the `all_stores_being_deletable`/`delete=true` fast path [5](#0-4) , so their old slot-list entries are never reclaimed by `purge_keys_exact`. Each subsequent write to the same throwaway pubkey re-enters `clean_accounts` with an ever-growing `slot_list` for that key, and each cycle re-triggers the O(R) traversal once per still-blocked historical slot, yielding cumulative O(1+2+...+R) = O(R²) work in the background clean thread for R linear fee-paying writes. This is not gated by any ancestor/zero-lamport/obsolete-account/ref-count check — those guards only decide store-count arithmetic correctness, not visitation complexity.

### Impact Explanation
This causes disproportionate CPU time in `AccountsDb::clean_accounts` (invoked from the background accounts-background-service thread via `calc_delete_dependencies`), which can starve other maintenance work and let `dirty_stores`/uncleaned index entries backlog grow, consistent with the "Scope: High" impact described (background cleanup work exhausted by cheap attacker input relative to fees paid). The vulnerability is confined to accounts-db bookkeeping cost/latency; it does not directly corrupt state, cause stale reads, or change balances (LIFECYCLE_NEUTRALITY holds — state is unchanged, only cost is affected).

### Likelihood Explanation
Preconditions are achievable by any unprivileged account owner: repeatedly writing a batch of disposable accounts alongside one long-lived "anchor" account in the same slot, then rewriting the disposable accounts every subsequent slot while leaving the anchor untouched. No leader/validator control, no crafted snapshots, and no more than ordinary transaction submission rates are required. The magnitude of amplification scales with how many slots the attacker sustains this pattern (R), which is bounded only by attacker patience/fee budget, and the quadratic-vs-linear cost mismatch grows with R regardless of shrink's eventual (rate-limited, best-effort) mitigation.

### Recommendation
Add a per-pubkey "already expanded" guard (e.g., an `IntSet<Pubkey>` alongside `already_counted`) in `calc_delete_dependencies` so that `update_pending_stores` walks a given key's `slot_list` at most once per call, regardless of how many blocked slots reference that key.

### Proof of Concept
Extend the existing `test_delete_dependencies` unit test pattern [6](#0-5)  into a scaling/fuzz test:

```rust
// pseudo-outline, place near test_delete_dependencies in accounts_db/tests/impl.rs
fn build_pinned_scenario(r: usize) -> (AccountsDb, Vec<HashMap<Pubkey, CleaningInfo>>, HashMap<Slot, (usize, HashSet<Pubkey>)>) {
    // For slots 0..r:
    //   - write `throwaway_i` (superseded again next slot) and `anchor_i`
    //     (never rewritten) into the SAME slot's storage.
    // Build `candidates` bins and `store_counts` exactly as clean_accounts does,
    // but leave every slot's store_count > 0 (anchor still alive there).
}

#[test]
fn test_calc_delete_dependencies_quadratic_blowup() {
    let mut timings = vec![];
    for &r in &[200usize, 400, 800, 1600] {
        let (accounts, candidates, mut store_counts) = build_pinned_scenario(r);
        let start = std::time::Instant::now();
        accounts.calc_delete_dependencies(&candidates, &mut store_counts, None);
        timings.push((r, start.elapsed()));
    }
    // Assert that doubling r roughly quadruples wall time (superlinear),
    // rather than the ~2x expected for O(r) cost proportional to fees paid.
    for w in timings.windows(2) {
        let ratio = w[1].1.as_secs_f64() / w[0].1.as_secs_f64();
        assert!(ratio > 3.0, "expected superlinear growth, got ratio {ratio}");
    }
}
```

Expected result: wall time grows faster than linearly in `r` (approaching quadratic), demonstrating that `calc_delete_dependencies` cost is not proportional to the number of writes (fees) the attacker paid to create the scenario.
