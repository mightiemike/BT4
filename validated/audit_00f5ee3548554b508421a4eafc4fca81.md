### Title
Unmetered per-request cost amplification in `GetPaginatedExchangeListServlet` / `Wallet.getPaginatedExchangeList` - (File: `framework/src/main/java/org/tron/core/services/http/GetPaginatedExchangeListServlet.java`)

### Summary
`GetPaginatedExchangeListServlet.doGet`/`doPost` pass an attacker-controlled `limit` (clamped only to `EXCHANGE_COUNT_LIMIT_MAX`) straight into `Wallet.getPaginatedExchangeList`, which performs up to `EXCHANGE_COUNT_LIMIT_MAX` individual `ExchangeStore`/`ExchangeV2Store.get(key)` calls per single HTTP request. The rate limiting applied (`RateLimiterServlet`) throttles by request count, not by the amount of underlying DB work a request triggers, so the cost-per-request is highly asymmetric between attacker and node.

### Finding Description
`GetPaginatedExchangeListServlet.doGet` reads `offset`/`limit` directly from the query string with no fee, auth, or per-item cost check, and calls `wallet.getPaginatedExchangeList(offset, limit)`: [1](#0-0) 

`Wallet.getPaginatedExchangeList` clamps `limit` to `EXCHANGE_COUNT_LIMIT_MAX` (not to the actual number of existing exchanges) and then builds a `ContiguousSet` range from `offset` to `end`, doing one `getExchangeStoreFinal(...).get(key)` store lookup per id in the range, even when no exchange exists for that id: [2](#0-1) 

Request throttling happens in `RateLimiterServlet.service`, which acquires a per-endpoint permit (`IPQPSRateLimiterAdapter` or `DefaultBaseQqsAdapter` if unconfigured) and then a `GlobalRateLimiter` permit: [3](#0-2) 

The per-endpoint adapter (`IPQPSRateLimiterAdapter`) keys solely on `RuntimeData.getRemoteAddr()`: [4](#0-3) 

so an attacker rotating source IPs (or default configs that don't apply `IPQPSRateLimiterAdapter` to this endpoint at all — only `GetAccountServlet` is shown configured with it in `docs/configuration.md`) can defeat this per-IP throttle. `GlobalRateLimiter`, however, does also apply a node-wide QPS cap (`rateLimiter`, a single static `RateLimiter` shared across all IPs and all endpoints) in addition to a per-IP limiter: [5](#0-4) 

This global limiter is not bypassed by IP rotation, so the DoS is bounded by the global QPS setting (default example in docs is `global.qps = 50000`). None of these limiters, however, account for the *cost* of a single admitted request — whether it triggers 1 store `get()` or up to `EXCHANGE_COUNT_LIMIT_MAX` store `get()` calls (each requiring a serialized/deserialized capsule read from LevelDB/RocksDB). This is the core issue: request-count-based throttling does not bound work-per-request, so each admitted request can still be made maximally expensive by simply setting `limit=EXCHANGE_COUNT_LIMIT_MAX`, at zero fee/auth cost to the caller. The HTTP-layer request has no relation to on-chain fee/energy/bandwidth accounting (this is a read-only query API, not a transaction), so `FAITHFUL_METERING` (cost proportional to work performed) is not enforced at this layer.

### Impact Explanation
This falls under DoS via RPC-API: an attacker can force the node to perform up to `EXCHANGE_COUNT_LIMIT_MAX` store lookups per admitted HTTP request for free, amplifying request-count-based rate limits into disproportionate CPU/DB read load. At sufficient concurrency (bounded by the global QPS limiter, not by per-IP limits if those are unconfigured or bypassed via IP rotation), this can degrade HTTP thread pool availability and increase request latency for legitimate API users. The `/wallet/getpaginatedproposallist` and `/wallet/getpaginatedassetissuelist` endpoints share the identical pattern (`getPaginatedProposalList`, presumably a similarly-structured asset issue variant) and are equally affected.

### Likelihood Explanation
No authentication or fee is required to call this HTTP endpoint; preconditions are only network access to the HTTP API port (default enabled on full nodes). The per-IP rate limiter can be bypassed by rotating source addresses, and even without rotation, the node-wide `GlobalRateLimiter` QPS cap does not scale down with request cost, so an attacker operating within the global QPS budget can still generate maximum per-request DB read amplification cheaply and repeatably. This is a real, low-cost, repeatable amplification vector, though its severity is bounded (not unbounded) by the configured global QPS ceiling, which is a pre-existing partial mitigation not called out in the question.

### Recommendation
Add cost-aware limiting for pagination-style read endpoints: e.g., weight rate-limiter token consumption by the requested `limit` (or by `end - offset` after clamping), lower `EXCHANGE_COUNT_LIMIT_MAX`/`PROPOSAL_COUNT_LIMIT_MAX` to a smaller default, or iterate an index/range scan instead of doing `limit` individual point lookups when few real entries exist. Additionally, ensure `IPQPSRateLimiterAdapter` (or similar) is applied by default to all pagination endpoints rather than relying on `DefaultBaseQqsAdapter`, and consider making the global QPS budget configurable per-endpoint-cost rather than per-request-count.

  public ExchangeList getPaginatedExchangeList(long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
    }
    limit =
        limit > EXCHANGE_COUNT_LIMIT_MAX ? EXCHANGE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestExchangeNum ? latestExchangeNum : end;

    ExchangeList.Builder builder = ExchangeList.newBuilder();
    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ExchangeCapsule::calculateDbKey).map(key -> {
      try {
        return getExchangeStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getExchangeStore(),
            chainBaseManager.getExchangeV2Store()).get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(exchangeCapsule -> builder
            .addExchanges(exchangeCapsule.getInstance()));
    return builder.build();

  }

  public static boolean tryAcquire(RuntimeData runtimeData) {
    String ip = runtimeData.getRemoteAddr();
    if (!Strings.isNullOrEmpty(ip)) {
      RateLimiter r = loadIpLimiter(ip);
      if (r == null || !r.tryAcquire()) {
        return false;
      }
    }
    return rateLimiter.tryAcquire();
  }

  public static boolean acquire(RuntimeData runtimeData) {
    String ip = runtimeData.getRemoteAddr();
    if (!Strings.isNullOrEmpty(ip)) {
      RateLimiter r = loadIpLimiter(ip);
      if (r == null) {
        return false;
      }
      r.acquire();
    }
    rateLimiter.acquire();
    return true;
  }

  public static boolean acquirePermit(RuntimeData runtimeData) {
    return Args.getInstance().isRateLimiterApiNonBlocking()
        ? tryAcquire(runtimeData)
