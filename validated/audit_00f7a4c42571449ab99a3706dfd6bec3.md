### Title
Owner-Controlled `DeleteAccount` Permanently Burns Account Balance When `beneficiary_id` Does Not Exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` validation only checks that `beneficiary_id` is a *syntactically* valid `AccountId`, never that the account actually exists. The delete-account execution path unconditionally emits a balance-refund receipt to that `beneficiary_id`. If the account does not exist (and is not implicit-account-eligible), the resulting system-refund receipt's `Transfer` fails with `AccountDoesNotExist`, and because refund receipts that fail are burnt rather than bounced back, the entire remaining account balance is destroyed forever. This mirrors the reported bug class exactly: a value-transferring action controlled by the account owner (or anyone who has stolen the account's full-access key, analogous to "an attacker who gains access to the owner address") lacks a check on the destination, permanently destroying funds.

### Finding Description
`validate_delete_action` only calls `validate_action_account_id`, a purely syntactic check: [1](#0-0) 

`action_delete_account` then unconditionally builds a balance-refund receipt to `delete_account.beneficiary_id` using the account's current balance, with no existence check performed before queuing this receipt: [2](#0-1) 

When that refund receipt is later processed as an `ActionReceipt::Transfer` to `beneficiary_id`, `check_account_existence` rejects it with `AccountErrorKind::AccountDoesNotExist` unless the target is eligible for implicit-account creation: [3](#0-2) [4](#0-3) 

Per the protocol's own refund spec, refund receipts are identified by `predecessor_id == "system"`, and if such a receipt's execution fails, the funds are not returned to anyone — they are simply burnt: [5](#0-4) 

This is implemented in the runtime's receipt-application loop: for system-predecessor receipts whose result is an error, the deposit is added to `other_burnt_amount` instead of being refunded anywhere: [6](#0-5) 

### Impact Explanation
Any full-access-key holder of an account (the account "owner", or an attacker who has stolen/compromised that key — directly analogous to the report's "owner or attacker who gains access to owner address") can submit a single `DeleteAccountAction` with a `beneficiary_id` that is a syntactically valid but non-existent named account. The entire remaining NEAR balance of the deleted account is irrecoverably burnt, with no path to recovery for the account holder or any counterparty. This is a concrete, unauthorized, permanent value-destruction bug reachable directly from a single submitted transaction, matching the "permanently frozen/destroyed funds" impact class.

### Likelihood Explanation
The trigger is trivial and requires no special conditions: it can happen accidentally (typo in the beneficiary account, or racing with the beneficiary account being deleted between transaction construction and execution) or be exploited deliberately by an attacker who has obtained a full-access key and wants to grief/destroy the victim's remaining funds instead of stealing them, or as a way to reduce total supply. Because validation happens only at the syntax level and never checks existence, there is no way for the protocol or wallets to reject this at submission time with certainty (existence could change between validation and execution).

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or is otherwise guaranteed to be creatable, e.g. via implicit-account rules) at execution time, and reject the `DeleteAccount` action with an explicit error (e.g. a new `ActionErrorKind::BeneficiaryDoesNotExist`) instead of silently emitting a doomed refund receipt whose failure results in burning. Alternatively, treat failed delete-account balance refunds specially — e.g., by falling back to the deleting account's owner/predecessor instead of the system-burn path used for generic refund failures — since this refund did not originate from an unpredictable receipt failure but from a fully attacker/owner-controlled action argument.

### Proof of Concept
1. Account `alice.near` has a full-access key and non-zero balance.
2. `alice.near` signs a `DeleteAccountAction { beneficiary_id: "does-not-exist.near" }` (a syntactically valid, but never-created, named account).
3. `validate_delete_action` accepts the action since `"does-not-exist.near"` passes `validate_action_account_id`.
4. `action_delete_account` removes `alice.near` from state and queues `Receipt::new_balance_refund("does-not-exist.near", account_balance)`.
5. When this system refund receipt is processed, `check_account_existence` for the `Transfer` action returns `AccountDoesNotExist` because `"does-not-exist.near"` is a `NamedAccount` (not implicit-creation-eligible) and does not exist.
6. Per `runtime/runtime/src/lib.rs:926-934`, because `receipt.predecessor_id().is_system()` and `result.result.is_err()`, the entire `account_balance` is added to `other_burnt_amount` — permanently destroyed, with no receiver crediting and no possibility of recovery for `alice.near` or anyone else.

fn check_transfer_to_nonexisting_account(
    config: &RuntimeConfig,
    account_id: &AccountId,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    if implicit_account_creation_eligible
        && account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts)
    {
        // OK. It's implicit account creation.
        // Notes:
        // - Transfer action has to be the only action in the transaction to avoid
        // abuse by hijacking this account with other public keys or contracts.
        // - Refunds don't automatically create accounts, because refunds are free and
        // we don't want some type of abuse.
        // - Account deletion with beneficiary creates a refund, so it'll not create a
        // new account.
        Ok(())
    } else {
        Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
    }
}
