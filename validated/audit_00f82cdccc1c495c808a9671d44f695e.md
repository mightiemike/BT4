## Analysis Summary

The external Fei report is fundamentally about **a safeguard function silently omitting the specific check that would have caught a divergence** (Burner-role enforcement) when invoked through an indirect path (`withdraw` → `_burnFeiHeld`). The Aptos-native analog I identified reduces to the same invariant class: *a "must-match" integrity comparator silently skips a critical field, so downstream tooling reports success even though the protected value has diverged.*

### Title
`TransactionOutput::ensure_match_transaction_info` never validates state-checkpoint / hot-state / position-state roots, letting replay-verify and chunk-replay tooling certify a divergent ledger state as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the canonical "does my re-executed output match the authenticated on-chain `TransactionInfo`" comparator. It is relied on by `db-tool`'s `replay-verify`/`replay-on-archive`, the CLI transaction replayer, and the chunk executor's `verify_execution` path used during backup restore and state-sync replay verification. The function checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the locally recomputed values, even though those fields exist on every `TransactionInfo` and are exactly the fields carrying the Sparse-Merkle/JMT state roots that these tools exist to validate.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  performs four checks (status, gas, write-set hash, event root hash) and then returns `Ok(())`. The trailing comment explicitly documents the gap: [2](#0-1) 

This function is the sole "match" check used by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, invoked during backup replay/restore verification [3](#0-2) 
- `aptos-move/cli/src/commands.rs` replay command [4](#0-3) 
- `storage/db-tool/src/replay_on_archive.rs` and the `db-tool replay-verify` / backup `replay-verify` coordinator, which is the operational tool used to certify that a full backup archive, when replayed, reproduces the authenticated chain history [5](#0-4) 

Meanwhile `TransactionInfoV0`/`V1` carry `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class, hashed fields committed into the transaction accumulator [6](#0-5) , and these are exactly the roots produced by `DoStateCheckpoint`/`DoLedgerUpdate` during normal execution [7](#0-6) . None of that root material is ever cross-checked by `ensure_match_transaction_info`.

Note this gap is not scoped to the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature only — `state_checkpoint_hash` (the primary JMT state root, present unconditionally on every `TransactionInfoV0`/`V1`) and `hot_state_checkpoint_hash` are also silently unchecked, regardless of any feature flag.

### Impact Explanation
This breaks the "replay paths… must not reinterpret committed data into a different ledger state" invariant. `replay-verify`/`replay-on-archive` is the operational safety net operators and the Aptos Foundation rely on to detect: (a) archive-storage corruption or tampering of state data served by an untrusted backup provider, and (b) hard-fork-only nondeterminism bugs where a subset of the network computes a different state root than the rest but otherwise produces an identical write set / event list / gas / status for a given transaction (a state root can diverge from the write set without the write set itself differing, e.g. due to a JMT/hashing bug, incorrect base state, or backward-incompatible replay of a state-dependent computation). Because the comparator never checks `state_checkpoint_hash`, such a divergence would be reported as "ReplayVerify coordinator succeeded" [8](#0-7)  even though the restored/replayed database silently carries a wrong, unauthenticated state root at that checkpoint. Any node bootstrapped from that "verified" backup would serve authenticated-looking API responses and proofs derived from the wrong state tree.

### Likelihood Explanation
No privileged access is required to trigger the missed check — it fires deterministically whenever locally recomputed state roots diverge from the recorded `TransactionInfo`, which is the exact scenario this tooling is designed to catch (untrusted archive data, non-determinism, or backward-incompatibility bugs during replay). The bug is a straightforward code omission (self-documented via the TODO comment), not a hard-to-trigger race, but its blast radius is limited to the offline/asynchronous replay-verify and restore-verify workflows rather than to live consensus, since consensus-path proof verification (`TransactionInfoListWithProof::verify`, `TransactionAccumulatorProof`) independently binds `TransactionInfo` bytes (including all checkpoint hash fields) to the signed `LedgerInfo`, so a signed root cannot be silently substituted at the protocol level.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the values on `txn_info`, mirroring the pattern already used for `state_change_hash` and `event_root_hash`. Since this function only receives a `TransactionOutput` and not the resulting state root today, the state root would need to be threaded in by callers (e.g., from `DoStateCheckpoint`'s output) so replay-verify tooling can perform a full, non-partial match instead of silently accepting an unauthenticated divergence.

### Proof of Concept
1. Take any historical transaction range and produce a corrupted/backdated `TransactionInfo` and/or backup archive whose state key-values hash to a different `state_checkpoint_hash` root than the one embedded in the `TransactionInfo`, while leaving write-set bytes, gas, status, and events untouched (e.g., simulate archive bit-rot or a JMT computation bug in one code path).
2. Run `db-tool replay-verify` (or `aptos-move/cli` transaction replay) against this data via `TransactionRestoreBatchController`/`ChunkExecutor::verify_execution` [9](#0-8) .
3. Observe `ensure_match_transaction_info` returns `Ok(())` and the tool logs "ReplayVerify coordinator succeeded" [10](#0-9)  despite the state root being wrong, confirming the comparator's blind spot.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
