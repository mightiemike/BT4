### Title
Token-level `Enabled` flag in `TokenConfig` is never checked during inbound execution, allowing minting/bridging of admin-disabled tokens - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
`uregistry.TokenConfig` has an `Enabled` field explicitly documented as "Whether this token is enabled for minting/bridging" [1](#0-0) . Unlike the chain-level `ChainEnabled.IsInboundEnabled`/`IsOutboundEnabled` flags, which are consistently checked before creating a UTX or executing an inbound [2](#0-1) [3](#0-2) [4](#0-3) , the token-level `Enabled` flag is never read anywhere in `x/uexecutor`. This mirrors the M-34 pattern: a per-entity pausable/enabled flag exists in configuration, but the code path that mutates value-bearing state (mint/deposit) iterates/uses the entity without honoring that flag.

### Finding Description
The token minting helper `depositPRC20` fetches `TokenConfig` purely to resolve the PRC20 contract address and never inspects `tokenConfig.Enabled` before calling `CallPRC20Deposit`: [5](#0-4) .

The same pattern repeats in every inbound execution route that mints PRC20 against a `TokenConfig`:
- `ExecuteInboundGas` retrieves `tokenConfig` and proceeds straight to swap/deposit logic without an enabled check [6](#0-5) .
- `ExecuteInboundFundsAndPayload` calls `k.depositPRC20(...)` on the non-CEA path with no enabled gate [7](#0-6) .
- `ExecuteInboundGasAndPayload` resolves `tokenConfig` and calls `gasAndPayloadDepositAutoSwap` for both the CEA and non-CEA branches without checking `Enabled` [8](#0-7) .

Searching the entire `x/uexecutor` module for `Enabled` usage confirms only the chain-level flags (`IsChainInboundEnabled`, `IsChainOutboundEnabled` on `ChainConfig.Enabled`) are consulted, in `msg_vote_inbound.go`, `create_outbound.go`, and `msg_execute_payload.go`; the token-level `TokenConfig.Enabled` bit is set/read by admin messages (`AddTokenConfig`/`UpdateTokenConfig`/`RemoveTokenConfig` in `x/uregistry`) but has zero read-sites in the execution keeper. `RemoveTokenConfig` fully deletes the config (causing `GetTokenConfig` lookup failures downstream), but there is no code path that merely disables a token via `Enabled=false` while still honoring that flag during mint.

Because `VoteInbound`'s validation (`ValidateForExecution`, chain-enabled check) never queries token-level enablement, an attacker submitting (and honest validators voting on) an inbound event that references a token an admin has disabled (`Enabled=false`, e.g., depegged/compromised/being sunset) will still have PRC20 minted to the recipient UEA once the inbound ballot finalizes — exactly the "excluded/paused entity still updated" defect described in M-34, just applied to token minting instead of reward-exclusion accounting.

### Impact Explanation
If `TokenConfig.Enabled=false` is meant as a bridging kill-switch (per its own proto doc comment), its lack of enforcement means:
- Tokens explicitly disabled by governance/admin (e.g., due to a compromised bridge asset, depeg, or liquidity-cap breach mitigation) can still be minted as PRC20 on Push Chain from ordinary user-submitted inbound events, since honest validators vote based only on chain-level and structural inbound validation, not token enablement.
- This is an unauthorized-mint class issue: value (PRC20 supply) is created against the intent of the token registry's explicit `Enabled` gate, with no corresponding realistic backing-fund reconciliation control at that layer.

### Likelihood Explanation
Reaching this path requires no privileged access: any external user can trigger an `Inbound` event on the source chain gateway using a token whose `TokenConfig.Enabled` was previously set to `false` (but not removed) by governance; honest universal validators will vote per normal flow (`VoteInbound` → `ExecuteInbound*`), and the enabled flag is silently ignored throughout. The `Enabled` field must be set false but the token config must still exist (a realistic operational state — disabling first, deciding on removal later).

### Recommendation
Add a check on `tokenConfig.Enabled` in every inbound execution path that resolves a `TokenConfig` before minting/depositing PRC20 — mirroring the existing `IsChainInboundEnabled` gate:
- In `depositPRC20` (`x/uexecutor/keeper/handler.go`), return an error if `!tokenConfig.Enabled` before calling `CallPRC20Deposit`.
- In `ExecuteInboundGas`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGasAndPayload`, check `tokenConfig.Enabled` immediately after `GetTokenConfig` and route to the existing revert/failure handling (`shouldRevert = true; revertReason = ...`) consistent with other validation failures in these functions.
- Optionally, also validate token enablement earlier in `VoteInbound`/`ValidateForExecution` so a disabled token is rejected before a UTX is even finalized, analogous to the `IsChainInboundEnabled` check.

### Proof of Concept
1. Admin calls `MsgUpdateTokenConfig` on `x/uregistry` to set `TokenConfig.Enabled = false` for token `T` on chain `C` (config remains present, only `Enabled` flips).
2. An external, unprivileged user (or attacker) deposits token `T` into the gateway contract on chain `C`, emitting a standard inbound event.
3. Honest universal validators observe the event and call `MsgVoteInbound` as usual; `VoteInbound` only checks `IsChainInboundEnabled` [2](#0-1)  — which is unrelated to token `T`'s `Enabled` flag — so the ballot finalizes normally.
4. `ExecuteInboundFundsAndPayload` (or `ExecuteInboundGas`/`ExecuteInboundGasAndPayload` depending on `TxType`) calls `k.depositPRC20` / `gasAndPayloadDepositAutoSwap`, which fetches `TokenConfig` for `T`, never checks `Enabled`, and successfully mints PRC20 `T` to the recipient's UEA [7](#0-6) .
5. Result: PRC20 for a token explicitly marked disabled by governance is minted on Push Chain despite the registry's kill-switch intent.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
