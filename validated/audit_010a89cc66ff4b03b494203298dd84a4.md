## Nonce-Griefing Front-Run Blocks Third-Party `MsgExecutePayload` Execution Against a UEA - (`x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
Push Chain's `MsgExecutePayload` reproduces the exact race-condition shape described in the Symmetrical H-7 report: any account may submit a pre-authorized, owner-signed payload on behalf of a Universal Executor Account (UEA), and the UEA contract accepts it only if a **monotonic, strictly-matching nonce** embedded in the signed payload matches on-chain state. Because the UEA owner can always submit a trivial, self-signed payload for free (no Cosmos fee — the message type is gasless) that consumes the current nonce, the owner can front-run and permanently invalidate any specific pre-authorized payload that a third-party relayer/keeper is trying to land on their behalf.

### Finding Description
`MsgExecutePayload` is documented as intentionally allowing **any account** to deliver an owner's pre-authorized payload — this is the whole point of the "contract-only binding" model: [1](#0-0) 

Authorization/replay protection is enforced entirely inside the UEA contract via a nonce that is "monotonic per UEA": [2](#0-1) 

The Push Chain node's role is simply to route the call: `ExecutePayload` in `x/uexecutor/keeper/msg_execute_payload.go` resolves the UEA and forwards to `CallUEAExecutePayload`, which issues a `DerivedEVMCall` to `executeUniversalTx(payload, signature)` on the UEA: [3](#0-2) [4](#0-3) 

Because `MsgExecutePayload` is in the gasless whitelist, submitting it costs the sender nothing at the Cosmos-tx-fee layer: [5](#0-4) 

The UEA's ABI confirms `nonce` is a plain field inside the signed `UniversalPayload` tuple, checked by the contract on every `executeUniversalTx` call: [6](#0-5) 

This is structurally identical to Symmetrical's `verifyPartyAUpnl`/`verifyPartyBUpnl` pattern: an off-chain-authorized action (there, a liquidation upnl signature; here, a relayer-delivered payload) is validated against an on-chain account nonce that the account owner fully controls. In Symmetrical, PartyA could front-run a pending liquidation by bumping their own nonce via any self-initiated action (allocate/deallocate dust, lock/unlock dummy position, etc.). In Push Chain, the UEA owner can achieve the same effect for free by submitting any trivially cheap, self-authored `MsgExecutePayload` (e.g., a payload with `to = self`, `value = 0`, empty `data`) that consumes the current nonce before the targeted third-party payload lands. Any pending `MsgExecutePayload` carrying the old nonce — submitted by a relayer/keeper/dApp on the owner's behalf — will then revert at the UEA's nonce check, and the entire Cosmos tx (including any partial state) rolls back per the documented atomicity guarantee.

### Impact Explanation
Any protocol or dApp built on Push Chain's UEA model that relies on third-party delivery of owner-pre-authorized payloads — scheduled/recurring executions, automated stop-loss/liquidation-style triggers, subscription payments, DCA orders, or any "keeper" pattern — can be indefinitely griefed by the UEA owner themselves. The owner can watch the mempool (or simply always keep a queued no-op payload ready) and burn the current nonce the instant an unfavorable authorized payload is about to be delivered, at zero Cosmos fee cost. This lets a user dodge automated/adverse actions authorized against their own account, exactly mirroring the "block liquidation" impact in H-7: unfairness to the counterparty relying on the pre-authorized action executing, denial of service on a core execution path (`x/uexecutor` payload execution), and potential fund-safety implications for any dApp assuming reliable execution of owner-signed payloads.

### Likelihood Explanation
High. No privileged role, validator collusion, or TSS/relayer compromise is required — only the UEA owner's own key, which they always possess. The griefing transaction is gasless at the Cosmos fee layer (only UEA-balance EVM gas is spent, which can be made near-zero with an empty payload), so the cost of continuously invalidating unwanted payloads is negligible. This is reachable through the default `MsgExecutePayload` submission path with no additional preconditions beyond having a deployed, funded UEA.

### Recommendation
- Consider decoupling "freshness/replay" nonce semantics from "adversarial cancellation" semantics for flows where third parties are expected to deliver payloads the owner did not just author (e.g., allow a `deadline`-only fast path, per-payload unique identifiers not tied to a single strictly-monotonic counter, or a nonce namespace reserved for keeper-delivered payloads that the owner cannot silently invalidate with unrelated self-submitted actions).
- If strict monotonic nonces must be retained for security reasons, document and rate-limit or timelock the owner's ability to submit competing zero-effect payloads, or require an explicit cancellation message (with clear semantics) rather than allowing implicit invalidation via unrelated payload execution.
- At minimum, flag this as an accepted architectural risk for any dApp built on top of `MsgExecutePayload`/UEA payload delivery, since the guarantee "any account may submit the message" is fundamentally undermined by the owner's unilateral ability to invalidate pending deliveries.

### Proof of Concept
1. Relayer/keeper obtains payload `P1` (nonce = N) signed by UEA owner authorizing some action unfavorable to the owner (e.g., automated collateral seizure in a lending dApp built on Push, or a scheduled payment).
2. Relayer broadcasts `MsgExecutePayload{ UniversalAccountId: owner, UniversalPayload: P1, VerificationData: sig(P1) }`.
3. Owner observes this (mempool, or simply anticipates it) and immediately submits their own `MsgExecutePayload{ UniversalAccountId: owner, UniversalPayload: P2 (nonce = N, to=self, value=0, data=0x), VerificationData: sig(P2) }` — trivially cheap and gasless at the Cosmos layer per `app/txpolicy/gasless.go`.
4. If `P2` lands first, the UEA's on-chain nonce advances from N to N+1.
5. Relayer's `P1` (still carrying nonce N) reaches `executeUniversalTx`, fails the contract's nonce check, and `CallUEAExecutePayload`/`ExecutePayload` returns `execErr`, rolling back the entire Cosmos transaction per the documented atomicity guarantee [7](#0-6) .
6. Owner repeats step 3 indefinitely (or whenever they detect a new unfavorable payload), permanently blocking the intended action at negligible cost.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.

// CallUEAExecutePayload executes a universal payload through UEA
func (k Keeper) CallUEAExecutePayload(
	ctx sdk.Context,
	from, ueaAddr common.Address,
	universal_payload *types.UniversalPayload,
	verificationData []byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	abi, err := types.ParseUeaABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UEA ABI")
	}

	abiUniversalPayload, err := types.NewAbiUniversalPayload(universal_payload)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal payload")
	}

	gasLimit := new(big.Int)
	gasLimit, ok := gasLimit.SetString(universal_payload.GasLimit, 10)
	if !ok {
		return nil, fmt.Errorf("invalid gas limit: %s", universal_payload.GasLimit)
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,
		ueaAddr,
		big.NewInt(0),
		gasLimit,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"executeUniversalTx",
		abiUniversalPayload,
		verificationData,
	)
}
