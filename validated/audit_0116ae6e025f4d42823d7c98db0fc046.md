## Analysis

The reported bug class — a pause/lock mechanism that can permanently prevent a user from moving funds via the only reachable code path — has a direct analog in the NEAR Wallet Contract's `has_in_flight_tx` in-flight-transaction lock.

### Title
Permanent lock-up of ETH-implicit wallet funds via stuck `has_in_flight_tx` flag on callback gas exhaustion - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (used by ETH-implicit accounts to execute NEAR actions via RLP-encoded Ethereum transactions) guards against concurrent execution using a boolean `has_in_flight_tx` flag [1](#0-0) . `rlp_execute` immediately rejects any call while this flag is `true` [2](#0-1) , and the flag is only ever reset back to `false` inside `#[private]` promise callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) [3](#0-2) . If any of these callback receipts fails (e.g. runs out of gas mid-execution) after the flag was set to `true` by the initiating call, the state write resetting the flag is never committed, and there is no other entry point to clear it.

### Finding Description
Each cross-contract call scheduled by the wallet contract is attached fixed, hard-coded static gas via `.with_static_gas(...)` (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, all only 5–10 Tgas) with no dynamic/unused-gas-weight allocation [4](#0-3) . These fixed budgets are used for the callback receipts that reset `has_in_flight_tx` [5](#0-4) [6](#0-5) .

Because a NEAR receipt's state changes are only committed atomically on successful completion, if a callback (e.g. `rlp_execute_callback`, `address_check_callback`, or `nep_141_storage_balance_callback`) fails part-way through execution — for example by exhausting its small fixed gas allotment while deserializing a large `promise_result`, formatting error strings, or handling an unexpectedly large payload from a called contract/token — the entire receipt, including the `self.has_in_flight_tx = false` write made at the top of the function, is discarded. The flag remains permanently `true` because it was already durably set to `true` by the prior successfully-committed `rlp_execute` (or `address_check_callback`/`nep_141_storage_balance_callback`) call [7](#0-6) .

Once stuck, every subsequent call to `rlp_execute` — the sole entry point for the account owner (via a relayer holding a `FunctionCall`-restricted access key scoped only to `rlp_execute`) to move funds or otherwise use the account — is rejected with "transaction already in progress" [2](#0-1) . There is no admin/reset method, and the relevant reset methods are `#[private]`, callable only as promise callbacks of the wallet contract itself, so there is no external way to unstick the flag [8](#0-7) [9](#0-8) . Since ETH-implicit accounts derive their identity from a secp256k1 key and typically hold no native NEAR access key other than the relayer's `rlp_execute`-restricted one, this makes the account and its balance permanently unusable/frozen.

This is reachable by any ordinary transaction signer or relayer: any account (honest user, careless relayer, or malicious actor with a `FunctionCall` key scoped to `rlp_execute`) can trigger `rlp_execute` with attached gas high enough to pass promise-creation static-gas checks but insufficient for the eventual callback's actual dynamic execution needs (particularly for larger cross-contract responses in the NEP-141/registrar flows), causing a permanent denial-of-service on the wallet.

### Impact Explanation
This produces a concrete, permanently frozen-funds condition for an ETH-implicit account: once `has_in_flight_tx` is stuck `true`, the account's NEAR balance (and any NEP-141 tokens routed through it) can never again be moved via the only functional entry point, `rlp_execute`. This matches the "permanently frozen funds" acceptance criterion, triggered purely by an ordinary/malicious transaction sender or relayer without any privileged or network-level access.

### Likelihood Explanation
Likelihood is Medium: it requires a relayer (which can be the account owner acting as its own relayer, or an untrusted third-party relayer) to submit a `rlp_execute` call whose attached gas is enough to reach and dispatch a callback but insufficient for the callback's actual execution, or for the wallet's cross-contract targets (address registrar / NEP-141 tokens) to return unusually large payloads or error strings that exceed the hard-coded static gas budgets. This can happen accidentally with a poorly chosen gas value, or be triggered deliberately by a malicious relayer as a griefing attack against a specific victim wallet, since no funds beyond gas are needed to attempt it repeatedly.

### Recommendation
- Increase static gas budgets for callbacks with safety margin and/or use `with_unused_gas_weight` so callbacks receive a proportional share of any leftover gas rather than a small fixed amount.
- Add a fail-safe/timeout mechanism (e.g., allow the flag to be cleared if a configurable number of blocks have passed since it was set, or track a receipt/promise id and validate on the next `rlp_execute` call) so a single failed callback cannot permanently brick the wallet.
- Consider structuring the flag-clearing logic so it is set in a step that cannot itself run out of gas before completing (e.g., minimal work before persisting the flag reset, with heavier logic split into a follow-up, gas-safe step).

### Proof of Concept
1. Deploy a `WalletContract` for an ETH-implicit account as in `integration-tests/src/tests/features/wallet_contract.rs` `test_wallet_contract_interaction`, and register a relayer access key restricted to `rlp_execute` [10](#0-9) .
2. Craft (or have the relayer submit) a signed Ethereum ERC-20 transfer routed through `rlp_execute`, targeting a NEP-141 token contract that returns from `storage_balance_of`/`ft_transfer` with an unusually large successful response payload, while attaching only the minimum NEAR gas needed to pass the promise-scheduling static-gas checks for `nep_141_storage_balance_callback`/`rlp_execute_callback` (i.e., near `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`RLP_EXECUTE_CALLBACK_GAS`).
3. The callback receipt begins execution (so `self.has_in_flight_tx = false` is set in-memory) but exhausts its fixed gas budget while deserializing the large `promise_result`/formatting the response, causing the whole receipt to fail and all its state changes (including the flag reset) to be discarded, per [11](#0-10) .
4. Any subsequent call to `rlp_execute` — even a well-formed, correctly-signed, adequately-gassed one from the legitimate owner — is immediately rejected because `self.has_in_flight_tx` remains `true` forever [2](#0-1) , permanently freezing the account's funds.
