### Title
Non-embedded apps default to a domain-wide `shopify_app_session` cookie path, silently overwriting sessions across shops - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
For non-embedded apps, `oauth.ts`'s `callback` function writes the post-OAuth session identifier into a single cookie, `shopify_app_session`, whose `path` defaults to `'/'` unless the app developer explicitly opts into the new `cookiePath` config option. [1](#0-0)  Because the cookie is not scoped per shop by default, this is the same bug class as the Y2K Finance oracle report: a value that legitimately varies "per pair" (here, per shop) is tracked/stored under a single shared key (the domain-wide cookie path), so a later write silently clobbers the earlier one instead of being kept distinct.

### Finding Description
`STATE_COOKIE_NAME` (`shopify_app_state`) is scoped to `callbackPath` during `begin`, which is fine because it's a short-lived, single-use nonce. [2](#0-1)  But `SESSION_COOKIE_NAME` (`shopify_app_session`), which is the browser's pointer to which `Session` should be treated as "current" for subsequent requests, is written with `path: cookiePath` where `cookiePath` defaults to `'/'`:

```
const cookiePath =
  typeof config.cookiePath === 'function'
    ? config.cookiePath(session)
    : (config.cookiePath ?? '/');
await cookies.setAndSign(SESSION_COOKIE_NAME, session.id, {
  expires: session.expires,
  sameSite: 'lax',
  secure: true,
  path: cookiePath,
});
``` [1](#0-0) 

With a single domain-wide path, the cookie is not disambiguated by shop. The changelog explicitly documents this as the root cause and confirms the default is still `'/'`: "all shops shared a single `shopify_app_session` cookie at `path=/`, so authenticating a new shop would silently overwrite the previous shop's session," and the mitigation is an *opt-in* `cookiePath` function that "must match the actual URL structure of your app — e.g. if each shop lives under `/shops/:shop/`" — something "the library cannot derive automatically." [3](#0-2)  The same caveat is repeated verbatim in the config type docs. [4](#0-3) 

This mirrors the oracle report precisely:
- Oracle bug: `tokenToOracle[token]` is keyed by a single asset when the real relationship is a *pair* (token A vs token B); a second, differing pair silently reuses the old oracle instead of erroring or storing distinctly.
- This bug: `shopify_app_session` is keyed by a single cookie/path when the real relationship is *per-shop*; a second shop's session silently overwrites the first's cookie instead of being kept distinct, because the mapping key (cookie name + path) doesn't include the shop.

### Impact Explanation
For non-embedded, multi-shop-capable apps that have not configured `cookiePath` (the default), if a user (merchant/staff) authenticates two different shops in separate browser tabs against the same app domain, the second OAuth callback's `Set-Cookie` for `shopify_app_session` overwrites the first tab's cookie at the shared `path: '/'`. Any subsequent request made from the first tab (which still shows shop A's UI) will present the browser's session cookie now pointing at shop B's session ID. This is a session/tenant-mixing condition: requests believed by the user/browser to belong to shop A are authenticated and processed using shop B's session context, i.e., cross-tenant confusion caused purely by the cookie-key design, not by any attacker action. It only affects non-embedded apps (`!config.isEmbeddedApp`) using cookie-based "current session" resolution.

### Likelihood Explanation
This triggers under an ordinary, non-adversarial workflow — no forged requests or credential compromise needed — whenever the same browser is used to install/authenticate more than one shop for a non-embedded app without the app developer setting a custom `cookiePath`. Given that `cookiePath` is optional and the safe value requires the app's own routing knowledge ("the library cannot derive this automatically"), it is easy for developers to leave the default and unknowingly ship the collision.

### Recommendation
Make the session cookie shop-aware by default rather than relying on an opt-in, app-specific `cookiePath` function: e.g., derive a shop-scoped path automatically (such as encoding a hash of the shop domain into the cookie name or path) instead of defaulting to `'/'`, or require `cookiePath` to be supplied when `isEmbeddedApp` is false and multiple shops may be used. At minimum, log or fail fast when `cookiePath` is left at its default and multiple distinct shops are authenticated from the same origin, similar to how the y2k-finance recommendation was to key `tokenToOracle` by the full pair rather than a single token.

### Proof of Concept
1. Configure a non-embedded app without setting `cookiePath` (default `'/'`).
2. In browser Tab 1, complete OAuth for `shop-a.myshopify.com`; observe `Set-Cookie: shopify_app_session=offline_shop-a...; path=/`.
3. In browser Tab 2 (same browser/profile), complete OAuth for `shop-b.myshopify.com`; observe `Set-Cookie: shopify_app_session=offline_shop-b...; path=/`, which overwrites the cookie from step 2 for the entire origin.
4. Return to Tab 1 and issue a request; the app reads `shopify_app_session` and resolves it to shop B's session id (per `session.id` construction in `createSession`) even though the UI still shows shop A, demonstrating cross-tenant session confusion without any request forgery. [5](#0-4)

### Minor Changes

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
```

   * The path to use for the OAuth session cookie in non-embedded apps.
   *
   * By default the cookie is written with `path: '/'`, making it domain-wide.
   * This means that when a user authenticates multiple shops in separate tabs,
   * each OAuth callback overwrites the previous cookie, causing all tabs to use

   *
   * Set this to a string or a function returning a string to scope the cookie to
   * a URL path prefix that is unique per shop. The browser will then maintain
   * one cookie per shop and deliver only the matching one per request.
   *
   * **Requirement:** the configured path must match the actual URL structure of
   * your app — e.g. if each shop lives under `/shops/:shop/`, use that prefix.
   * The library cannot derive this automatically.
   *
   * @example
   * // Static path (single-shop apps or apps with no shop-specific routing)
   * cookiePath: '/'
   *
   * @example
   * // Factory function (multi-shop non-embedded apps)
   * cookiePath: (session) => `/shops/${session.shop}/`
   *
   * @defaultValue `'/'`
   */
  cookiePath?: string | ((session: Session) => string);
