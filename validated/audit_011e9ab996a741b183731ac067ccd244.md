### Title
Unvalidated felt-sized L2→L1 message address on L3 chains causes a guaranteed panic in `get_sorted_l2_to_l1_messages` - ([File: crates/blockifier/src/execution/call_info.rs])

### Summary
On chains configured with `chain_info.is_l3 = true`, the `send_message_to_l1` syscall deliberately skips the 20-byte `EthAddress` range check for the message's `to_address`, storing the full 252-bit felt as `L1Address`. However, `OrderedL2ToL1Message::to_ordered_tuple`, which is unconditionally invoked whenever `CallInfo::get_sorted_l2_to_l1_messages` is called (used for building `TransactionExecutionInfo`/receipts and OS-consumed message summaries), performs `self.message.to_address.try_into().expect("Failed to convert L1Address to EthAddress")` with no `is_l3` awareness. Any address that does not fit the 20-byte Ethereum format causes this `.expect()` to panic.

### Finding Description
`send_message_to_l1` in both the deprecated and current syscall paths validates the address only for non-L3 chains: [1](#0-0) [2](#0-1) 

This means on an L3 chain, a contract can freely pass any felt value up to `Felt::MAX` (252 bits) as `to_address`, which is stored unchecked as `L1Address(Felt)`: [3](#0-2) 

Later, regardless of `is_l3`, converting the collected messages to the externally-consumed `StarknetAPIMessageToL1` type always forces the address back into a strict 20-byte `EthAddress` via `.try_into().expect(...)`: [4](#0-3) 

The `TryFrom<Felt> for EthAddress` implementation explicitly errors (does not clamp/truncate) if the top 12 bytes are nonzero: [5](#0-4) 

`get_sorted_l2_to_l1_messages` — which calls `to_ordered_tuple` — is a normal, non-fallible path invoked from execution/receipt-building code: [6](#0-5) 

Since the syscall path for L3 chains explicitly allows out-of-range addresses to pass validation (this is confirmed working as intended by the existing test `test_send_message_to_l1_invalid_address`, which asserts `result.is_ok()` when `is_l3` is true): [7](#0-6) 

there is a direct contradiction between the intake validation (skipped for L3) and the downstream consumption logic (`to_ordered_tuple`, unconditionally enforcing the 20-byte bound). No `is_l3` check exists in `call_info.rs` to reconcile this.

### Impact Explanation
Any unprivileged L3-chain transaction sender can deploy or call a contract that invokes `send_message_to_l1` with a `to_address` felt greater than `2^160 - 1`. Execution succeeds at the syscall layer (per the `is_l3` bypass), but as soon as the sequencer/node attempts to summarize or serialize that call's messages via `get_sorted_l2_to_l1_messages` (used when building `TransactionExecutionInfo`, receipts, and any consumer relying on `StarknetAPIMessageToL1`), the process panics on `.expect("Failed to convert L1Address to EthAddress")`. This is a process-halting panic reachable from a single ordinary transaction, causing denial of service for block production/re-execution on any L3 deployment of this sequencer — i.e., the network becomes unable to confirm new transactions once such a message is included/re-executed.

### Likelihood Explanation
High. This does not require any privileged role — any contract deployer/caller on an L3 chain can trigger it with a single `send_message_to_l1` syscall call using an out-of-EthAddress-range felt. The existing unit test even demonstrates that such calls are accepted (`is_ok()`) when `is_l3` is true, confirming the code path is reachable and intentionally permissive at the syscall boundary, while the downstream conversion was not updated to match.

### Recommendation
Make `OrderedL2ToL1Message::to_ordered_tuple` (and any other unconditional `L1Address -> EthAddress` `.expect()` conversions, e.g. in `crates/apollo_rpc_execution/src/objects.rs`) `is_l3`-aware: either keep `to_address` as a wide type (`L1Address`/felt) throughout the receipt/message pipeline for L3 chains instead of coercing to `EthAddress`, or reject/revert the transaction gracefully (instead of panicking) when the conversion fails, consistent with how `StarknetApiError::OutOfRange` is already surfaced as an execution error at the syscall boundary for non-L3 chains.

### Proof of Concept
1. Configure `ChainInfo` with `is_l3 = true`.
2. Deploy/call a Cairo1 contract that invokes `send_message_to_l1` (e.g., the `test_send_message_to_l1` test contract) with `to_address = felt!("0x10000000000000000000000000000000000000000")` (exceeds 20 bytes), as done in `test_send_message_to_l1_invalid_address`.
3. Per that test, `entry_point_call.execute_directly_given_block_context` returns `Ok(...)` for `is_l3 = true` (validation bypassed).
4. Subsequently call `CallInfo::get_sorted_l2_to_l1_messages()` on the resulting `CallInfo` (as done internally whenever building `TransactionExecutionInfo`/receipts) — this invokes `OrderedL2ToL1Message::to_ordered_tuple`, which panics at:
`self.message.to_address.try_into().expect("Failed to convert L1Address to EthAddress")`
(`crates/blockifier/src/execution/call_info.rs:108-112`), crashing the executing node/process.

    pub fn send_message_to_l1(&mut self, message: MessageToL1) -> SyscallResult<()> {

impl TryFrom<Felt> for EthAddress {
    type Error = StarknetApiError;
    fn try_from(felt: Felt) -> Result<Self, Self::Error> {
        const COMPLIMENT_OF_H160: usize = std::mem::size_of::<Felt>() - H160::len_bytes();

        let bytes = felt.to_bytes_be();
        let (rest, h160_bytes) = bytes.split_at(COMPLIMENT_OF_H160);
        if rest != [0u8; COMPLIMENT_OF_H160] {
            return Err(StarknetApiError::OutOfRange { string: felt.to_string() });
        }

        Ok(EthAddress(H160::from_slice(h160_bytes)))
    }
}

#[cfg_attr(feature = "cairo_native", case::native(RunnableCairo1::Native))]

fn test_send_message_to_l1_invalid_address(
    #[case] runnable_version: RunnableCairo1,
    #[values(true, false)] is_l3: bool,
) {
    let test_contract = FeatureContract::TestContract(CairoVersion::Cairo1(runnable_version));
    let mut chain_info = ChainInfo::create_for_testing();
    chain_info.is_l3 = is_l3;
    let mut state = test_state(&chain_info, BALANCE, &[(test_contract, 1)]);

    let invalid_to_address = felt!("0x10000000000000000000000000000000000000000");
    let payload = vec![felt!(2019_u16), felt!(2020_u16)];
    let calldata = Calldata(
        concat(vec![
            vec![
                invalid_to_address,
                felt!(u64::try_from(payload.len()).expect("Failed to convert usize to u64.")),
            ],
            payload.clone(),
        ])
        .into(),
    );
    let entry_point_call = CallEntryPoint {
        entry_point_selector: selector_from_name("test_send_message_to_l1"),
        calldata,
        ..trivial_external_entry_point_new(test_contract)
    };
    let block_context = BlockContext::create_for_testing().with_chain_info(chain_info.clone());
    let result = entry_point_call.execute_directly_given_block_context(&mut state, block_context);

    if is_l3 {
        assert!(result.is_ok(), "Expected execution to succeed on L3 chain");
    } else {
        assert!(result.is_err(), "Expected execution to fail with invalid address");
        let error = result.unwrap_err();
        let error_string = error.to_string();
        assert!(
            error_string.contains("Out of range"),
            "Expected error containing 'Out of range', got: {error_string}"
        );
    }
}
