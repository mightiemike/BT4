## Finding: `TransactionOutput::ensure_match_transaction_info` Skips Checkpoint-Hash Comparison, Letting Replay/Chunk Verification Accept a Diverged State Root

### Title
Replay-verification (`ensure_match_transaction_info`) omits state/hot-state/position checkpoint hash checks, allowing a corrupted or malicious `TransactionInfo` state root to pass verification - (`File: types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to prove that a freshly (re-)executed `TransactionOutput` matches a trusted, already-authenticated `TransactionInfo` during chunk replay and archive replay-verification. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but it never compares the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields, which are the fields that actually commit to the resulting state tree/version root.

### Finding Description
`ensure_match_transaction_info` [1](#0-0)  validates status, gas, and the write-set hash against the corresponding `TransactionInfo` fields, and validates the event root hash [2](#0-1) . It stops there — the function's own comment admits the gap: [3](#0-2) 

This is the checkpoint hash that binds the *state* produced by a batch of transactions to a Merkle/JMT root (`state_checkpoint_hash`, and — for the newer V1 format — `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` used when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) [4](#0-3) .

This check is invoked from `ChunkExecutorInner::verify_execution`, which re-executes a batch of transactions locally and compares the freshly produced `TransactionOutput`s against `transaction_infos` that were taken from an external/archived source (e.g. an untrusted or corrupted backup, or a peer-provided list during `TransactionReplayer::replay`): [5](#0-4) 

The same function is also called from `storage/db-tool/src/replay_on_archive.rs`, the tool operators use to audit archived ledger data for state-root divergence after a hard fork or upgrade.

Because `state_checkpoint_hash` is never compared, if a stored/archived `TransactionInfo` carries a **wrong** `state_checkpoint_hash` (e.g. due to storage corruption, a bug in an older node version, or a malicious archive source) while write set, events, gas, and status happen to match, `verify_execution`/`ensure_match_transaction_info` will report success even though the resulting state tree root actually diverges from what local execution computed.

### Impact Explanation
This breaks the "proof-integrity" invariant that a `TransactionInfo`'s checkpoint hash is validated end-to-end during replay: an authenticated response (replay-verify report / db-tool output) can be bound to the wrong state root without detection. On mainnet this specifically affects trust in replay-verification tooling that is used to detect state divergence around upgrades and hard forks — the exact "hard-fork-only divergence during commit, replay ... or proof verification" category. It does not directly corrupt data already committed by consensus (the accumulator/commit path in `DoLedgerUpdate`/`DoStateCheckpoint` still independently recomputes checkpoint hashes for freshly executed blocks), so the practical blast radius is limited to detection/verification tooling silently passing over a real divergence rather than corrupting live consensus-committed state.

### Likelihood Explanation
Low-to-medium. Exploitation requires an attacker (or corruption event) to control or influence the `TransactionInfo` list being verified against (e.g. a malicious/compromised backup/archive source consumed by `replay_on_archive`), while keeping write set/events/gas/status identical. This is a narrow, tool-specific condition rather than a path reachable by ordinary unprivileged transaction submission.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, when present, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) between the recomputed checkpoint output and the `txn_info` being verified against, as the existing TODO in the code already flags: "Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [3](#0-2) .

### Proof of Concept
1. Construct a `TransactionInfo` with a correct `state_change_hash`/`event_root_hash`/`gas_used`/`status` but an incorrect `state_checkpoint_hash` (simulating storage bit-rot or a malicious archive).
2. Feed it into `ChunkExecutorInner::verify_execution` (or `db-tool replay-on-archive`) alongside the corresponding real transaction/output.
3. Observe `ensure_match_transaction_info` returns `Ok(())` [6](#0-5)  despite the state-tree root committed by that `TransactionInfo` differing from the one computed by local execution, i.e. replay-verify falsely reports success.

**Note on confidence**: This is a self-acknowledged gap (the code comment itself names the exact risk), not a hidden logic bug I derived independently — I want to be explicit that this reduces novelty, but the underlying broken invariant and its exact reachable path (`verify_execution` → `ensure_match_transaction_info` → `replay_on_archive`/`TransactionReplayer`) is verified directly in the local code.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
