### Title
Witness/SR ranking ties are broken deterministically by address, letting a grinded address "game" active-witness/standby-witness selection and reward eligibility - (File: `chainbase/src/main/java/org/tron/core/store/WitnessStore.java`)

### Summary
`WitnessStore.sortWitnesses()`/`sortWitness()` rank witnesses by vote count, but when two witnesses have equal votes the tie is broken deterministically by the witness's address (via `hashCode()` or hex string), not by any random or vote-independent mechanism. This ranking directly decides which witnesses fall inside the top-27 active Super Representative (SR) set and the top-127 standby set, both of which receive block/standby rewards. This is the same root-cause pattern as the SEDA bug: a deterministic, grindable sort key (public key/address) used to allocate scarce reward slots among otherwise-equal participants.

### Finding Description
`sortWitnesses()` orders witnesses primarily by `getVoteCount()` descending, and for ties uses either the address `hashCode()` or the hex-encoded address string, both reversed: [1](#0-0) 

The identical tie-break logic exists in `sortWitness(List<ByteString>, boolean)`: [2](#0-1) 

This ranking is used in two reward-critical paths:

1. **Active witness (SR) selection** — during maintenance, `MaintenanceManager.doMaintenance()` builds the candidate address list and calls `dposService.updateWitness(newWitnessAddressList)`, which sorts the list via `consensusDelegate.sortWitness(list)` (delegating to `WitnessStore.sortWitness`) and then truncates to `MAX_ACTIVE_WITNESS_NUM`: [3](#0-2) [4](#0-3) [5](#0-4) 

Active witnesses are the ones that actually produce blocks and receive `getWitnessPayPerBlock()` rewards via `Manager.payReward()`: [6](#0-5) 

2. **Standby witness reward selection** — `WitnessStore.getWitnessStandby()` sorts all witnesses with the same tie-break logic and takes the top `WITNESS_STANDBY_LENGTH` (127), which are then paid via `MortgageService.payStandbyWitness()`: [7](#0-6) [8](#0-7) 

In both cases, when two or more witnesses (either genuinely or via Sybil/vote-splitting among cooperating accounts) end up with the exact same vote count at the cutoff boundary, whichever address sorts "higher" under the tie-break comparator is included in the reward-earning set while an equally-voted competitor is excluded. Because TRON account addresses are derived from key pairs that anyone can freely generate (grind) before registering as a witness candidate, an attacker can pre-compute an address whose `hashCode()` (legacy path, `allowWitnessSortOptimization()==false`) or hex string (optimized path, `==true`) will consistently win ties against expected competitors, guaranteeing preferential inclusion in the paid witness set whenever a tie occurs at the boundary.

### Impact Explanation
This directly parallels the SEDA finding: a deterministic, attacker-controllable sort key (address/pubkey) decides which equally-deserving participants receive rewards and which are excluded. In java-tron's case:
- Exclusion/inclusion in the top-27 active SR set determines who gets to produce blocks and earn `WitnessPayPerBlock` rewards.
- Exclusion/inclusion in the top-127 standby set determines who gets `Witness127PayPerBlock` rewards.

At the tie boundary this allows an attacker with a grinded address to unfairly and consistently displace a legitimately equally-voted competitor, resulting in underpriced/unfair allocation of protocol-paid rewards — a concrete accounting/fairness impact, not merely theoretical.

### Likelihood Explanation
Exploitability requires the vote-count tie to actually occur at the relevant cutoff boundary (rank 27 or rank 127), which depends on real-world voting distribution; exact ties are less common at scale but plausible for standby ranks (127th position) or during periods of low/concentrated voting, and can also be engineered by an attacker who controls multiple candidate witnesses and coordinates voters to equalize vote counts at the boundary. Address grinding itself is cheap and unprivileged (anyone can create arbitrary numbers of key pairs before registering as a witness candidate via `WitnessCreateContract`), so the attacker-controlled portion of the attack (choosing a favorably-sorting address) is trivial and free.

### Recommendation
Do not use the witness address (or any attacker-controllable value) as a tie-breaker for reward-relevant ranking. Options:
- Break ties using a value not controllable by the participant before registration, e.g., witness registration order/timestamp, or a hash combining block-level randomness (e.g., recent block hash) with the address, recomputed each maintenance cycle so it cannot be pre-ground.
- Alternatively, split rewards proportionally among all tied witnesses at the cutoff boundary instead of granting an all-or-nothing inclusion based on sort order.

### Proof of Concept
1. An attacker generates many key pairs offline and computes `hashCode()` (or hex string) ordering, selecting one address `A` known to sort ahead of a target competitor address `B` under `WitnessStore.sortWitnesses`/`sortWitness` comparator ( [9](#0-8) ).
2. Attacker registers `A` as a witness candidate and arranges (via own votes or Sybil accounts) for `A`'s vote count to equal `B`'s vote count at the 27th or 127th ranking boundary.
3. During `MaintenanceManager.doMaintenance()`, `sortWitness`/`sortWitnesses` places `A` ahead of `B` due to the tie-break, so `A` is included in `newWitnessAddressList.subList(0, MAX_ACTIVE_WITNESS_NUM)` (or `getWitnessStandby()`'s top 127) while `B` is excluded, despite identical vote support ( [3](#0-2) , [7](#0-6) ).
4. `A` subsequently earns block/standby rewards (`Manager.payReward`, `MortgageService.payStandbyWitness`) that `B` should have had an equal chance at.

    List<WitnessCapsule> ret;
    List<WitnessCapsule> all = getAllWitnesses();
    sortWitnesses(all, isSortOpt);
    if (all.size() > Parameter.ChainConstant.WITNESS_STANDBY_LENGTH) {
      ret = new ArrayList<>(all.subList(0, Parameter.ChainConstant.WITNESS_STANDBY_LENGTH));
    } else {
      ret = new ArrayList<>(all);
    }
    // trim voteCount = 0
    ret.removeIf(w -> w.getVoteCount() < 1);
    return ret;
  }

  public static void sortWitnesses(List<WitnessCapsule> witnesses, boolean isSortOpt) {
    witnesses.sort(Comparator.comparingLong(WitnessCapsule::getVoteCount).reversed()
        .thenComparing(isSortOpt
            ? Comparator.comparing(WitnessCapsule::createReadableString).reversed()
            : Comparator.comparingInt((WitnessCapsule w) -> w.getAddress().hashCode()).reversed()));
  }

  public void sortWitness(List<ByteString> list, boolean isSortOpt) {
    list.sort(Comparator.comparingLong((ByteString b) -> get(b.toByteArray()).getVoteCount())
        .reversed().thenComparing(isSortOpt
            ? Comparator.comparing(
                (ByteString b) -> ByteArray.toHexString(b.toByteArray())).reversed()
            : Comparator.comparingInt(ByteString::hashCode).reversed()));
  }

  public void payStandbyWitness() {
    List<WitnessCapsule> witnessStandbys = witnessStore.getWitnessStandby(
        dynamicPropertiesStore.allowWitnessSortOptimization());
    long voteSum = witnessStandbys.stream().mapToLong(WitnessCapsule::getVoteCount).sum();
    if (voteSum < 1) {
      return;
    }
    long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
    double eachVotePay = (double) totalPay / voteSum;
    for (WitnessCapsule w : witnessStandbys) {
      long pay = (long) (w.getVoteCount() * eachVotePay);
      payReward(w.getAddress().toByteArray(), pay);
      logger.debug("Pay {} stand reward {}.", Hex.toHexString(w.getAddress().toByteArray()), pay);
    }
  }
