### Title
Witness rewards accrued while a witness has zero votes are silently discarded instead of credited to anyone - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
`DelegationStore.accumulateWitnessVi()` is the java-tron analog of the `_updateRewardState()` reward-per-token accumulator described in the report. When a "liquidity" measure (vote count) is zero for a reward period, the accrued reward for that period is dropped entirely instead of being credited to any account (owner/treasury or otherwise), permanently stranding the funds.

### Finding Description
Block rewards and transaction-fee rewards are accumulated per-witness per-cycle via `MortgageService.payReward()`, which calls `delegationStore.addReward(cycle, witnessAddress, value)` unconditionally whenever a witness produces a block, independent of that witness's current vote count: [1](#0-0) 

At maintenance time, these accumulated rewards are converted into the per-vote reward index ("Vi", analogous to `rewardPerTokenStored`) via `DelegationStore.accumulateWitnessVi()`: [2](#0-1) 

If `voteCount == 0` for that cycle, the branch `if (reward == 0 || voteCount == 0)` is taken: the previous Vi is simply carried forward and the `reward` value fetched from `getReward(cycle, address)` is discarded — never divided into `deltaVi`, never credited to any user's allowance, and never redirected to a treasury/owner balance. This is the exact analog of the reported issue: the reward corresponding to an interval with zero pool liquidity (here, zero effective vote weight) is computed and funded, but the mechanism that would make it withdrawable (the Vi/rewardPerToken update) skips it, and there is no "accumulatedFees"-equivalent bucket to recapture it. The call site `MaintenanceManager.doMaintenance()` invokes this accumulation using the live vote count of an already-active witness: [3](#0-2) 

Since a witness's active/standby status and block-production schedule for cycle N are derived from vote counts computed at the end of cycle N-1, and delegators can freely withdraw votes at any time during cycle N (any unprivileged account calling the vote/withdraw actuator), it is possible for an already-scheduled witness to have `voteCount == 0` by the time `accumulateWitnessVi` runs for cycle N, while it has already earned `reward` from `payBlockReward`/`payTransactionFeeReward` during that same cycle.

### Impact Explanation
Reward tokens (TRX) that were already deducted from transaction senders as fees, or issued as block rewards, and recorded in `delegationStore`'s reward key for a given witness/cycle become permanently unclaimable: no voter's Vi delta reflects them (since the divisor, vote count, is zero and the branch is skipped), and there is no owner/treasury sweep of this value. This is an accounting/resource-reward corruption: funds are effectively burned/stuck in on-chain state rather than being distributed or reclaimed, matching the report's "loss of funds" impact class.

### Likelihood Explanation
This requires a witness to be actively producing blocks (and thus earning rewards) in a cycle during which its snapshot vote count is zero — reachable by any set of unprivileged accounts withdrawing/moving all votes away from a witness right after the vote-count snapshot for the next cycle is taken, while the witness remains scheduled/active for that cycle. This is the same "highly improbable but reachable" characterization as in the original report (zero liquidity during active reward accrual), so likelihood is low but the trigger path relies purely on unprivileged voting/withdrawal actions, not privileged actors.

### Recommendation
Mirror the recommended fix from the report: when `voteCount == 0` in `DelegationStore.accumulateWitnessVi()`, do not simply discard `reward`. Instead, either (a) return/refund it to a treasury-like accumulator that the owner or a designated fund can later claim, or (b) roll it forward into the next cycle's reward pool for that witness so it is eventually distributed once votes exist again, instead of silently vanishing from any claimable state.

### Proof of Concept
1. Witness `W` is elected active with vote count > 0 at the end of cycle `N-1`; `delegationStore.setWitnessVote(N, W, voteCount)` stores this. [4](#0-3) 
2. During cycle `N`, all delegators withdraw/move their votes away from `W` (unprivileged vote actuator calls), but `W`'s on-chain `WitnessCapsule.voteCount` used by `accumulateWitnessVi` at the *next* maintenance drops to 0 for cycle `N`.
3. `W` still produces blocks during cycle `N`, so `MortgageService.payBlockReward`/`payTransactionFeeReward` call `delegationStore.addReward(N, W, value)` repeatedly, accumulating a nonzero `reward` for cycle `N`.
4. At the maintenance boundary for cycle `N`, `accumulateWitnessVi(N, W, 0)` is invoked; since `voteCount == 0`, the `reward` fetched is discarded and Vi is simply carried forward.
5. No account's `queryReward`/`withdrawReward` computation (`MortgageService.computeReward`) can ever recover this amount, since it depends solely on Vi deltas, and this delta was never applied.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
