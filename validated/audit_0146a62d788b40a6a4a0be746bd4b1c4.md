Reviewing `verify()` in `precompiles/src/secp256r1.rs`, the point-decompression step is not vulnerable to the described attack.

`EcPoint::from_bytes(&group, pubkey, &mut ctx)` calls OpenSSL's `EC_POINT_oct2point`, which for a compressed encoding computes the y-coordinate deterministically from the x-coordinate byte string and the leading sign byte (`0x02`/`0x03`) by solving `y² = x³ + ax + b mod p`. This only succeeds if `x³+ax+b` is a quadratic residue mod p — i.e., if the given x-coordinate actually corresponds to a genuine point on the P-256 curve. There is no way to supply a "malformed" 33-byte compressed encoding that parses successfully into a point that is *not* actually on the curve; OpenSSL's decompression routine is a well-defined deterministic curve-point derivation, not a naive/unchecked deserializer. So the premise that `from_bytes`/`from_public_key` could "happen to parse without error" into an attacker-forged, off-curve point is false for this OpenSSL API. [1](#0-0) 

Given that, the only way `verifier.verify(&ecdsa_sig)` at [2](#0-1)  returns `true` for an attacker-chosen `(r,s)` is if that signature is a valid ECDSA signature for the message under the private key corresponding to whatever pubkey point was decoded. If the attacker supplies their own pubkey bytes (a real point on the curve they control the private key for) and signs with their own key, they only forge "authorization" keyed by *their own* pubkey — not the victim's. Substituting a different, real pubkey that isn't the victim's would simply cause any downstream Pubkey-equality check (done by the calling program, not this precompile) to fail, since the precompile never claims the verified key equals a specific expected identity — that binding is the responsibility of the invoking program logic, not `secp256r1::verify`.

Forging a valid `(r,s)` for the victim's actual pubkey without their private key would require breaking ECDSA over P-256, which is outside any code-level bug in this repository. Range checks on `r`/`s` (`within_range`, low-S enforcement) are already present and correctly bound signature components before verification. [3](#0-2)
