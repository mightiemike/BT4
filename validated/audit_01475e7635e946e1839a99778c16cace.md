### Title
Insufficient L1-handler fee enforcement lets any L1 message consume sequencer resources without paying the computed fee - ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs])

### Summary
`L1HandlerTransaction::execute_raw` computes the actual fee owed for processing the message (`receipt.fee`, derived from the transaction's real gas usage) but never compares it against `paid_fee_on_l1` — the fee the L1 sender actually paid. It only checks that `paid_fee_on_l1 != Fee(0)`.

### Finding Description
This is the same class of bug as the reported Cooler issue: two values that are supposed to represent "the same" cost — `paid_fee_on_l1` (what was paid, analogous to `Cooler.loans[loanId].amount`) and `receipt.fee` (what was actually computed to be owed, analogous to `Clearinghouse.receivables`) — diverge, and the code that should compare them instead performs a degenerate/incorrect check.

In `execute_raw`: [1](#0-0) 

the code computes `receipt.fee` from `TransactionReceipt::from_l1_handler`, which is based on the real gas vector of the executed L1 handler call, but the only guard before committing execution is:
```rust
let paid_fee = self.paid_fee_on_l1;
// For now, assert only that any amount of fee was paid.
// The error message still indicates the required fee.
if paid_fee == Fee(0) {
    return Err(...)
}
```
This never validates `paid_fee_on_l1 >= receipt.fee`. The comment itself ("For now, assert only that any amount of fee was paid") documents that the intended check (comparing paid vs. actual) was weakened to a trivial nonzero check. The `TransactionFeeError::InsufficientFee` error type still carries both `paid_fee` and `actual_fee` fields, showing the comparison was meant to be enforced: [2](#0-1) 

Additionally, `paid_fee_on_l1` is attacker/message-controlled: it comes directly from the L1 message value forwarded by the `StarknetCoreContract`'s `sendMessageToL2`, and the sequencer's transaction-converter path currently even hardcodes it to `Fee(1)`: [3](#0-2) 

Meanwhile, execution is permitted to consume gas up to `l1_handler_max_amount_bounds` (a substantial resource budget) before the (still-incomplete) fee check runs: [4](#0-3) 

Crucially, `l1_handler_tx_execution_info` unconditionally zeroes the reported fee (`receipt.fee = Fee(0)`) and sets `fee_transfer_call_info: None`, meaning no on-chain fee-transfer/debit ever occurs for L1 handler transactions — the L1-side `paid_fee_on_l1` is the *only* accounting mechanism for compensating the network for the resources consumed, and it is not actually enforced to cover the real cost: [5](#0-4) 

### Impact Explanation
An unprivileged L1 message sender can trigger arbitrarily expensive L1-handler execution (bounded only by `l1_handler_max_amount_bounds`, which allows a large gas/step budget) while paying a nominal fee (as low as 1 wei, and in the current wiring, always exactly `Fee(1)`). Since the actual computed fee is never charged against the paid amount, and no ERC20 transfer of the real fee ever happens for L1 handlers, this results in concrete unrecovered/unbounded resource consumption cost to the network for every L1-handler message — a fee-evasion/loss-of-funds class issue on the sequencer side, directly analogous to the Cooler/Clearinghouse under-accounting bug where the checked value (`receivables`) and the tracked truth (`loan.amount`) diverge and the defensive comparison is effectively bypassed.

### Likelihood Explanation
High reachability: any L1 contract that can call `sendMessageToL2` (i.e., any L1 account) can mint an L1HandlerTransaction with an attacker-chosen `paid_fee_on_l1`, and the sequencer path (`apollo_transaction_converter`) is presently wired to disregard the real L1-paid value entirely (`Fee(1)` hardcoded, per its own TODO). Both the "only assert nonzero" check and the hardcoded `Fee(1)` conversion are explicitly marked with TODOs acknowledging the gap, indicating this is a known-incomplete safeguard rather than a hardened one.

### Recommendation
- Enforce `paid_fee_on_l1 >= receipt.fee` (not just `paid_fee_on_l1 != 0`) before committing an L1 handler transaction's execution, reverting/rejecting when the L1-side payment does not cover the actual computed cost.
- Wire the real `paid_fee_on_l1` value (as scraped from the L1 `LogMessageToL2` event) through `apollo_transaction_converter::convert_consensus_l1_handler_to_internal_l1_handler` instead of the hardcoded `Fee(1)` placeholder.
- Reconsider whether the TODO ("Consider removing this check. It is covered by the starknet core contract.") is safe — the check is the only defense in blockifier itself; if it is to be relied upon as backstop, it must actually compare against the receipt's computed fee.

### Proof of Concept
1. An L1 account calls `StarknetCoreContract.sendMessageToL2` with `msg.value` (paid fee) set to `1 wei` and calldata that triggers an expensive contract entrypoint (e.g., heavy storage writes/loops) up to the `l1_handler_max_amount_bounds` gas ceiling.
2. The sequencer converts this into an `L1HandlerTransaction` with `paid_fee_on_l1 = Fee(1)` (or, in the current wiring, unconditionally `Fee(1)` regardless of the L1 value, per `convert_consensus_l1_handler_to_internal_l1_handler`).
3. `execute_raw` runs the handler to (near) the full `l1_handler_max_amount_bounds` gas budget, computes a large `receipt.fee` reflecting real resource cost, then only checks `paid_fee == Fee(0)` — which passes since `paid_fee = Fee(1) != 0`.
4. The transaction commits; `fee_transfer_call_info` is `None` and `receipt.fee` is reported as `Fee(0)` in the execution info, so no compensating value ever flows to the network for the consumed resources — the sender has purchased a maximal-cost execution for a nominal/fixed fee, repeatable across arbitrarily many L1 messages.
