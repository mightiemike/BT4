## Finding [1](#0-0) 

The relayer-fee refund inside `inner_rlp_execute` is dispatched as a completely independent receipt (`env::promise_batch_create` + `env::promise_batch_action_transfer`) that is created and sent **before** the promise for the actual user-requested action (base-token transfer / ERC-20 `ft_transfer`, or even before the address-registrar validation for `EOABaseTokenTransfer{address_check: Some(_)}`) is known to succeed. This is the same root cause as the DODO report: two token/value movements that are supposed to be atomically coupled are instead executed via separate, unchecked operations, so one side can complete while the other fails.

### Title
Relayer fee is paid out unconditionally, independent of whether the underlying emulated action succeeds or is later found fraudulent - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`inner_rlp_execute` fires a NEAR `Transfer` receipt paying the relayer's `fee` to `predecessor_account_id` for `EOABaseTokenTransfer` and `ERC20Transfer` transaction kinds as soon as parsing succeeds, via its own top-level `env::promise_batch_create`/`env::promise_batch_action_transfer` call. This fee-refund receipt is not chained (`.then`) to, or otherwise made contingent on, the promise that actually performs the requested transfer/function call. [2](#0-1) 

### Finding Description
For `EOABaseTokenTransfer` and `ERC20Transfer` kinds, as soon as the fee is non-zero and the caller isn't the wallet itself, the fee-transfer promise is created and dispatched immediately, unconditionally: [3](#0-2) 

Only afterward does the code build the actual action promise (the ERC-20 `ft_transfer`/`storage_deposit` chain or, for `address_check: Some(address)`, the address-registrar lookup that determines whether the relayer supplied a fraudulent `target`): [4](#0-3) 

Two independent problems follow from this decoupling:
1. **ERC-20 case**: if the token's `storage_balance_of`/`storage_deposit`/`ft_transfer` cross-contract calls later fail (e.g., insufficient balance, paused token, malicious/broken token contract, or gas exhaustion), the `rlp_execute_callback` only refunds the caller's own attached deposit (`caller_deposit`), never the relayer fee that was already sent in a separate, already-completed receipt: [5](#0-4) 
2. **`EOABaseTokenTransfer{address_check: Some(_)}` case**: this branch exists specifically to punish a dishonest relayer who lies about `target` being an unregistered eth-implicit account when it is really an existing named account — in that case the wallet is supposed to ban the relayer's key via `create_ban_relayer_promise`: [6](#0-5)  However, the fee-refund transfer to that very relayer has already been sent unconditionally back in `inner_rlp_execute` before the registrar check even runs, so banning the relayer's key afterward does not recover the fee that was paid out based on the (subsequently proven) fraudulent request.

This is functionally the same bug class as the report: a value transfer (`env::promise_batch_action_transfer` paying the relayer) is executed without verifying that the paired action (the token/asset movement it is compensating for) actually completed successfully or was legitimate, letting an untrusted actor (a relayer, i.e. an unprivileged meta-transaction sender) collect payment without delivering the corresponding service.

### Impact Explanation
A malicious or careless relayer can repeatedly submit transactions that are guaranteed (or likely) to fail on the token/registrar side while always collecting the `fee` NEAR transfer, draining value from the wallet-contract owner's balance with no corresponding action performed. This is a concrete unauthorized value movement out of the deterministic wallet-contract account, reachable purely by any account that can call `rlp_execute` with a validly signed Ethereum-emulation transaction — i.e., a normal RPC/transaction submitter acting as a relayer, no privileged or network-level position required.

### Likelihood Explanation
Likelihood is high: any relayer (which by design is meant to be an untrusted, permissionless party — that is the entire point of `rlp_execute` supporting arbitrary relayers) can trivially observe token state (e.g., low/zero balance, paused contract) before submitting, guaranteeing the downstream `ft_transfer` fails while still collecting the fee, or can lie about `target` in the `EOABaseTokenTransfer` address-check path to extract a fee before being "banned."

### Recommendation
Chain the fee-refund transfer to the relayer via `.then()` after the main action promise resolves successfully (e.g., issue it from inside `rlp_execute_callback`/`address_check_callback` conditioned on `PromiseResult::Successful`), instead of dispatching it eagerly and unconditionally in `inner_rlp_execute`. For the `address_check: Some(_)` path specifically, the fee must not be sent until after the registrar lookup confirms the relayer was honest.

### Proof of Concept
1. Wallet owner signs an `ERC20Transfer` (or `EOABaseTokenTransfer`) meta-transaction with a non-zero relayer `fee`.
2. A relayer observes (via view call) that the underlying NEP-141 token transfer will fail (e.g., insufficient token balance, paused contract).
3. Relayer submits the transaction to `rlp_execute` anyway.
4. `inner_rlp_execute` immediately creates and sends the fee `Transfer` promise to the relayer [3](#0-2) .
5. The subsequent `ft_transfer`/`storage_deposit` chain fails; `rlp_execute_callback` reports `success: false` but only refunds `caller_deposit`, not the already-paid relayer fee [5](#0-4) .
6. Net effect: relayer keeps the fee; wallet owner's intended action never executed, yet NEAR was paid out.
