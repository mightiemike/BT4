### Title
Authorization bypass via the `BOOTSTRAP` declare special-case allows unauthenticated, fee-free, repeatable class declaration - (File: crates/blockifier/src/transaction/account_transaction.rs)

### Summary
`AccountTransaction::execute_raw` special-cases declare transactions whose `sender_address` equals the constant "bootstrap address" (`'BOOTSTRAP'`), skipping `__validate_declare__`, nonce handling, and fee charging entirely as long as `nonce == 0` and `charge_fee == false`. `enforce_fee` (and therefore `charge_fee`) is derived purely from attacker-supplied resource bounds (`resource_bounds.max_possible_fee(tip) == 0`), and the bootstrap address's nonce is *never incremented* on this path, so the same bypass is replayable indefinitely. This mirrors the reported IDOR pattern: a state-changing operation is gated only by an object identifier (here, `sender_address == bootstrap_address()`) rather than by verifying the caller's right to act — no signature/ownership check is ever performed for this "account".

### Finding Description
The bootstrap-declare short-circuit in `execute_raw` runs before any account authentication: [1](#0-0) 

`is_bootstrap_declare` checks only three attacker/gateway-controlled fields: `sender_address == bootstrap_address()`, `nonce == 0`, and `!charge_fee`: [2](#0-1) 

`charge_fee` for a submitted transaction is computed from `enforce_fee`, which is a pure function of the transaction's own resource bounds/tip — fully attacker-controlled fields on any submitted `Declare` transaction: [3](#0-2) [4](#0-3) 

Because the bootstrap branch returns before `perform_pre_validation_stage` (which normally calls `handle_nonce` to increment nonce) is ever reached, the sender's nonce at `bootstrap_address()` is never incremented by this path: [5](#0-4) [6](#0-5) 

The corresponding Starknet OS Cairo code implements the identical bypass, gating solely on the literal `sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, with a zero max possible fee — again with no signature/validate call and no nonce increment for that path: [7](#0-6) 

There is no gateway- or mempool-level restriction preventing an arbitrary, unprivileged sender from constructing a `Declare` transaction with `sender_address = bootstrap_address()`; `check_declare_permissions` only enforces the *separate*, optional `authorized_declarer_accounts` allow-list, which defaults to `None` (i.e., unrestricted) in the default/observed deployment configs: [8](#0-7) [9](#0-8) [10](#0-9) 

This is architecturally analogous to the reported IDOR: the "LockReport" mutation trusted a caller-supplied `reportId` without checking the caller's relationship to that ID; here, the transaction pipeline trusts a caller-supplied `sender_address` value (`bootstrap_address()`) as sufficient "proof" that the sender is entitled to skip authentication/fee/nonce enforcement, without any actual signature verification or restriction to a genesis/bootstrap execution context.

### Impact Explanation
Any unprivileged party able to submit a transaction to the gateway can submit `Declare` transactions with `sender_address = bootstrap_address()`, `nonce = 0`, and resource bounds crafted so `max_possible_fee == 0` (e.g., zero `max_amount`/`max_price_per_unit`). Such a transaction:
- Skips `__validate_declare__` entirely (no signature check of any kind is performed against this pseudo-account).
- Skips nonce increment, so the exploit is replayable across every block indefinitely (each new declare of a *not-yet-declared* class hash succeeds for free).
- Skips fee charging, letting an attacker flood the network with free `Declare` transactions and force sierra→CASM compilation load on gateway compilers.
- Since the class-declaration state change ("declare the class hash only if `prev_value == 0`") is still committed to state, this results in unauthorized declaration of arbitrary contract classes without payment and without any owning-account validation — a resource-exhaustion and fee-bypass vector reachable by a single submitted transaction, matching "concrete loss... unauthorized account action" criteria (fee is a fund-loss avoidance for the attacker at the network's expense, and it's an unauthorized action performed under the guise of the reserved bootstrap identity).

### Likelihood Explanation
High: this path is reachable by any external, unauthenticated transaction sender through the normal gateway `add_tx` flow. It requires only constructing a V3 `Declare` transaction with a specific, publicly known `sender_address` constant (`'BOOTSTRAP'` felt, hard-coded and documented in `bootstrap_address()`) and zero-valued resource bounds — both of which are ordinary, unprivileged fields of a submitted transaction. No special network position, staking, or privileged role is required.

### Recommendation
Restrict the bootstrap-declare bypass so it cannot be triggered by ordinary transaction submission after genesis:
- Gate the bypass behind an explicit sequencer/genesis-only execution mode flag (not solely on `sender_address`/`nonce`/`charge_fee`, all of which are attacker-controlled inputs), or
- Enforce that the bootstrap address can only ever be used once network-wide (e.g., track a persistent "bootstrap consumed" flag in state rather than relying on nonce, since nonce is intentionally never incremented on this path), and
- Ensure this special case is disabled entirely once the chain has left the bootstrap/genesis phase, both in the Rust blockifier (`account_transaction.rs`) and in the corresponding Starknet OS Cairo logic (`transaction_impls.cairo`) to keep native/OS execution consistent.

### Proof of Concept
1. Submit an RPC `Declare` (V3) transaction to the gateway with:
   - `sender_address = 0x424f4f545354524150` (the felt encoding of `'BOOTSTRAP'`, per `DeclareTransaction::bootstrap_address()`).
   - `nonce = 0`.
   - `resource_bounds` such that `l1_gas.max_amount = l2_gas.max_amount = l1_data_gas.max_amount = 0` (or otherwise `max_possible_fee(tip) == 0`), causing `enforce_fee()`/`charge_fee` to evaluate to `false`.
   - A valid, previously-undeclared `class_hash`/`compiled_class_hash` and empty/default signature.
2. The gateway's `check_declare_permissions` passes when `authorized_declarer_accounts` is unset (default `None`).
3. `AccountTransaction::execute_raw` detects `tx.is_bootstrap_declare(charge_fee=false) == true` and runs only `try_declare`, never invoking `__validate_declare__`, `handle_nonce`, or fee transfer.
4. The class hash becomes declared in state at zero cost and with no signature check; the bootstrap address's nonce remains `0`, so the same request pattern (with a new class hash) can be repeated indefinitely.

    fn handle_nonce(
        state: &mut dyn State,
        tx_info: &TransactionInfo,
        strict: bool,
    ) -> TransactionPreValidationResult<()> {
        if tx_info.is_v0() {
            return Ok(());
        }

        let address = tx_info.sender_address();
        let account_nonce = state.get_nonce_at(address)?;
        let incoming_tx_nonce = tx_info.nonce();
        let valid_nonce = if strict {
            account_nonce == incoming_tx_nonce
        } else {
            account_nonce <= incoming_tx_nonce
        };
        if valid_nonce {
            return Ok(state.increment_nonce(address)?);
        }
        Err(TransactionPreValidationError::InvalidNonce {
            address,
            account_nonce,
            incoming_tx_nonce,
        })
    }

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }
