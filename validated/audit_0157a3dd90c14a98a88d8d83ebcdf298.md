## Finding

### Title
Dual, inconsistent Sierra-version parsing of attacker-controlled `sierra_program` bytes lets unsupported classes bypass gateway validation - (File: `crates/apollo_gateway_config/src/compiler_version.rs`, `crates/starknet_api/src/contract_class/structs.rs`)

### Summary
The webrick CVE is a classic "two parsers disagree on the same input" bug: WEBrick and a downstream proxy each decide independently — and differently — where a request ends (`Content-Length` vs `Transfer-Encoding`), letting an attacker smuggle a second request past validation. The sequencer has a structurally analogous situation for declared-class version parsing: **two independent functions parse the Sierra-version prefix of the same, fully attacker-controlled `sierra_program: Vec<Felt>` array using different algorithms and different minimum-length requirements**, and the result of one is used to *gate* the transaction at the gateway while the result of the other is what actually governs execution/fee semantics downstream.

### Finding Description
- The gateway uses `VersionId::from_sierra_program` to enforce `min_sierra_version`/`max_sierra_version` before admitting a Declare transaction: it requires at least 6 felts, converts them to `BigUintAsHex` via `sierra_program_as_felts_to_big_uint_as_hex`, and hands them to the external `cairo_lang_starknet_classes::contract_class::version_id_from_serialized_sierra_program` routine. [1](#0-0) 

- Everywhere else in the stack — fee/DA accounting, resource-type selection (e.g. `min_sierra_version_for_sierra_gas`), compiled-class construction, and `ClassInfo`/execution — the Sierra version is derived via `SierraVersion::extract_from_program`, which only requires 3 felts and directly casts each of the first three felts to `u64` as `(major, minor, patch)`. [2](#0-1) [3](#0-2) 

- These two decoders consume a different number of felts (6 vs 3) from the same untrusted byte prefix and use fundamentally different decoding logic (an external cairo-lang BigUint-based deserialization routine vs a direct felt→u64 cast). Because the stateless gateway validator calls `VersionId::from_sierra_program` purely to gate admission (`UnsupportedSierraVersion`), while the class hash, `ClassInfo.sierra_version`, and OS/blockifier resource semantics are all derived from `SierraVersion::extract_from_program`, a crafted `sierra_program` can be engineered so the two functions disagree: the gateway-computed `VersionId` falls inside `[min_sierra_version, max_sierra_version]` (so the transaction is admitted), while the actual `SierraVersion` used everywhere downstream is a version the sequencer's execution/fee logic was never meant to support (e.g. below `min_sierra_version_for_sierra_gas`, or below/above the range the compiler/blockifier assumes). [4](#0-3) 

- This is directly comparable to the request-smuggling primitive: the "front-end" validator (gateway) and the "back-end" consumer (execution/fee/OS) each independently parse the same ambiguous, attacker-supplied length-prefixed field and can reach different conclusions about it.

### Impact Explanation
If the gateway's admission check can be bypassed while the actual, execution-relevant `SierraVersion` is out of the supported range, a class the sequencer was never designed to safely execute or fee-account for can be declared and reach block building/blockifier execution and Starknet OS re-execution. Because `SierraVersion` also selects fee/resource-accounting behavior (`min_sierra_version_for_sierra_gas`) and gates compiler assumptions, this can produce incorrect fee charging, execution behavior the OS does not expect, or an execution/compilation panic during block building or OS re-execution — a path toward halted block production or incorrect committed state for that class, both of which are in-scope impacts (wrong committed root, network unable to confirm new transactions).

### Likelihood Explanation
Reachability is straightforward: any account can submit a Declare transaction with an arbitrary `sierra_program` felt array through the public gateway RPC — no privileged role is needed. What is **not fully verified** is whether a concrete felt sequence exists that makes `version_id_from_serialized_sierra_program` (external `cairo_lang_starknet_classes` crate) disagree with the simple 3-felt cast in `SierraVersion::extract_from_program`; I could not inspect that external crate's decoding internals with the tools available. The structural precondition for the bug class (two independent parsers, different felt counts, different decode algorithms, over the same untrusted input, used for different security-relevant decisions) is clearly present in this repo, but exploitability depends on cairo-lang's internal encoding, which is outside indexed repo content.

### Recommendation
Have the gateway derive the enforced version from the *same* function/representation that execution and fee accounting use (`SierraVersion::extract_from_program`), or conversely make `SierraVersion::extract_from_program` delegate to `VersionId::from_sierra_program` so there is a single canonical parser for the Sierra-version prefix. At minimum, add a cross-check that the two derived values are equal and reject the declare transaction otherwise, closing the "two parsers, one input" ambiguity.

### Proof of Concept
Not able to construct a concrete disagreeing felt sequence without access to `cairo_lang_starknet_classes::contract_class::version_id_from_serialized_sierra_program`'s source, which is not present in the indexed repo content (external dependency). The concrete test fixtures shown at [5](#0-4)  confirm that `VersionId::from_sierra_program` requires 6 felts and can fail/succeed independently of `SierraVersion::extract_from_program`'s 3-felt requirement, but a full byte-level PoC would require exercising the external crate directly (e.g., a background Devin session with repo/dependency access) to find felt values where `version_id_from_serialized_sierra_program`'s BigUint-based decode yields a different `(major, minor, patch)` than the direct felt cast.

```rust
    pub fn from_sierra_program(sierra_program: &[Felt]) -> Result<Self, VersionIdError> {
        let sierra_program_for_compiler = sierra_program_as_felts_to_big_uint_as_hex(
            sierra_program.get(..6).ok_or(VersionIdError::InvalidVersion {
                message: format!(
                    "Failed to retrieve version from the program: insufficient length. Expected \
                     at least 6 felts (got {}).",
                    sierra_program.len()
                ),
            })?,
        );

        let (version_id, _compiler_version_id) = version_id_from_serialized_sierra_program(
            &sierra_program_for_compiler,
        )
        .map_err(|err| VersionIdError::InvalidVersion {
            message: format!("Error extracting version ID from Sierra program: {err}"),
        })?;

        Ok(VersionId(version_id))
    }
```

```rust
    pub fn extract_from_program<F>(sierra_program: &[F]) -> Result<Self, StarknetApiError>
    // TODO(Aviv): Refactor the implementation to remove generic handling once we standardize to a
    // single type of Felt.
    where
        F: TryInto<u64> + Display + Clone,
        <F as TryInto<u64>>::Error: std::fmt::Display,
    {
        if sierra_program.len() < 3 {
            return Err(StarknetApiError::ParseSierraVersionError(
                "Sierra program length must be at least 3 Felts.".to_string(),
            ));
        }

        let version_components: Vec<u64> = sierra_program
            .iter()
            .take(3)
            .enumerate()
            .map(|(index, felt)| {
                felt.clone().try_into().map_err(|err| {
                    StarknetApiError::ParseSierraVersionError(format!(
                        "Failed to parse Sierra program to Sierra version. Index: {index}, Felt: \
                         {felt}, Error: {err}"
                    ))
                })
            })
            .collect::<Result<_, _>>()?;

        Ok(Self::new(version_components[0], version_components[1], version_components[2]))
    }
```
