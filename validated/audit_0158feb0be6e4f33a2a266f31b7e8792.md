### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` lists causes linear-scan cost blow-up on the legacy (non-optimized) resource-delegation index path - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
The reported `csprUSD` bug is a classic "growing list stored as a single value, linearly scanned on every hot-path check" issue. The closest reachable analog in java-tron is the legacy `DelegatedResourceAccountIndexStore` mechanism, which (when `AllowDelegateOptimization` is not enabled) stores each account's list of delegation counterparties as a single protobuf-encoded `DelegatedResourceAccountIndex` value containing `to_accounts`/`from_accounts` repeated fields, and performs an `O(n)` `contains()` scan plus full read/rewrite of the entire list on every `FreezeBalanceContract` delegation to a new receiver.

### Finding Description
In `FreezeBalanceActuator.delegateResource`, whenever `dynamicPropertiesStore.supportAllowDelegateOptimization()` is false, the actuator reads the entire `DelegatedResourceAccountIndexCapsule` for both the owner and receiver, performs a linear `List<ByteString>.contains()` check, and if the address is new, appends it and rewrites the whole capsule back to the store: [1](#0-0) 

The underlying capsule exposes only whole-list getters/setters — there is no dictionary/indexed structure, mirroring exactly the `Vec<PublicKey>` pattern flagged in the `csprUSD` report: [2](#0-1) 

Every additional distinct delegation counterparty a user has ever interacted with makes this list larger; each subsequent `FreezeBalanceContract` (delegated) call against the same owner/receiver pair re-reads, re-scans, and re-serializes the ever-growing list. `UnfreezeBalanceActuator` exhibits the same pattern when removing entries (copy list, `remove()`, rewrite): [3](#0-2) 

Notably, the codebase already contains a "fixed" replacement mechanism — the same pattern remediation described in the bug report (dictionary-keyed indices instead of a monolithic vector): `DelegatedResourceAccountIndexStore.delegate/unDelegate` store one entry per `(from,to)` key-prefixed pair rather than a growing list, activated only when `supportAllowDelegateOptimization()` is true: [4](#0-3) 

This confirms the team is aware the list-based approach does not scale — the new dictionary-style store exists specifically as a fix for it, exactly as in the `csprUSD` remediation. However, the legacy code path (`supportAllowDelegateOptimization() == false`) remains present and reachable for any network/state where this proposal has not been activated, and there is no length cap enforced on `toAccounts`/`fromAccounts` in `FreezeBalanceActuator.validate()` or `execute()`.

### Impact Explanation
Unlike the `csprUSD` case, this list is scoped per-account (not a single global list read on every token transfer), so the blast radius is narrower: only the specific account's own delegation operations (`FreezeBalanceContract`/`UnfreezeBalanceContract` with a receiver) become progressively more expensive to process as that account accumulates more distinct delegation counterparties. It does not affect unrelated users' transfers, unlike the `csprUSD` `is_blacklisted_util` check that gated every `transfer`/`mint`/`burn`. This materially reduces severity relative to the original report — it is a self-inflicted, account-scoped resource-exhaustion/gas-griefing risk rather than a protocol-wide DoS of core token functionality.

### Likelihood Explanation
Reachability depends entirely on whether the `AllowDelegateOptimization` proposal has been activated on the target chain; once active, the vulnerable code path is bypassed entirely in favor of the dictionary-based store. On any deployment where this optimization proposal has not been passed (e.g., older private/side chains still running this codebase, or a period before mainnet activation), an unprivileged user could deliberately delegate resources to many distinct addresses to grow their own index list, which would then make their own subsequent freeze/unfreeze operations disproportionately costly (and, in extreme cases, could push a single transaction's resource consumption toward node/protocol limits). Because impact is confined to the attacker's own account and the fix already exists and is likely enabled on live TRON mainnet, real-world exploitability is limited to legacy/non-upgraded deployments.

### Recommendation
Ensure `AllowDelegateOptimization` (or an equivalent enforced migration) is unconditionally active for all deployments running this codebase, and remove/deprecate the legacy list-based `DelegatedResourceAccountIndexCapsule` code path in `FreezeBalanceActuator`/`UnfreezeBalanceActuator` so the vulnerable pattern cannot be reached even before the proposal soft-fork is voted in. If backward compatibility must be retained, enforce a maximum size on `toAccounts`/`fromAccounts` and reject further delegations beyond that cap.

### Proof of Concept
1. Deploy/operate a chain instance where `supportAllowDelegateOptimization()` returns false (i.e., the corresponding maintenance proposal has not been activated) — this matches the pre-optimization behavior exercised in `FreezeBalanceActuatorTest.testFreezeDelegatedBalanceForBandwidth`.
2. As an unprivileged account, repeatedly submit `FreezeBalanceContract` transactions with distinct `receiver_address` values (e.g., 10,000 freshly generated addresses), each delegating a small bandwidth/energy amount.
3. Each call triggers `FreezeBalanceActuator.delegateResource` to load the account's `DelegatedResourceAccountIndexCapsule`, perform `toAccountsList.contains(...)` (O(n)) over the ever-growing list, append the new entry, and persist the entire capsule again — as demonstrated at scale in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, which already exercises a 100+ entry list without any bound: [5](#0-4) 
4. Observe that transaction processing cost (serialization + linear scan) for this account's freeze/unfreeze operations grows with the number of prior distinct delegation counterparties, with no cap enforced in the validate/execute logic.

  public void delegate(byte[] from, byte[] to, long time) {
    byte[] fromKey = Bytes.concat(FROM_PREFIX, from, to);
    DelegatedResourceAccountIndexCapsule toIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));
    toIndexCapsule.setTimestamp(time);
    this.put(fromKey, toIndexCapsule);

    byte[] toKey = Bytes.concat(TO_PREFIX, to, from);
    DelegatedResourceAccountIndexCapsule fromIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(from));
    fromIndexCapsule.setTimestamp(time);
    this.put(toKey, fromIndexCapsule);
  }
