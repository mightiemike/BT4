Based on my investigation, `x/uexecutor` never reads `TokenConfig.Enabled` in any inbound/outbound execution path — the field is validated for presence on write (`ValidateBasic`) but is dead at read time (`GetTokenConfig`, `depositPRC20`, `ExecuteInboundGas`, `ExecuteInboundGasAndPayload`, `ExecuteInboundFundsAndPayload`, `build_revert_outbound.go` all fetch the `TokenConfig` and use `NativeRepresentation`/`LiquidityCap` but never branch on `.Enabled`). This mirrors the report's bug class: a "kill switch" field exists in the registry and is documented as gating an action ("Whether this token is enabled for minting/bridging"), but the actual execution code path never checks it, so disabling it does not stop the corresponding behavior. That is analogous to `killBribeVault` failing to stop future reward accrual — except here the gate never worked at all, for any user, since it isn't wired into the mint/deposit code path.

I was not able to fully verify this in the final iteration — my last grep confirmed `TokenConfig.Enabled` is absent from `x/uexecutor` execution logic and that `x/uregistry/keeper/msg_update_token_config.go` exists as the only mutator, but I did not get to inspect `msg_update_token_config.go` or `query_server.go` contents directly, nor cross-check every execution/outbound file exhaustively (e.g. outbound creation and `RESCUE_FUNDS` paths) before running out of iterations. This should be verified with a full read of `x/uregistry/keeper/msg_update_token_config.go`, `x/uexecutor/keeper/build_revert_outbound.go`, `x/uexecutor/keeper/create_outbound.go`, and a repo-wide search restricted to `.Enabled` usages excluding `ChainEnabled`/`IsInboundEnabled`/`IsOutboundEnabled` before filing this as a confirmed finding.

### Title
TokenConfig.Enabled kill-switch is never enforced in inbound/outbound execution, allowing continued minting/bridging of disabled tokens - (File: x/uexecutor/keeper/handler.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go, x/uexecutor/keeper/execute_inbound_funds_and_payload.go)

### Summary
`TokenConfig` in `x/uregistry` carries a `bool enabled` field documented as "Whether this token is enabled for minting/bridging." Governance/admin can flip this via `MsgUpdateTokenConfig` to disable a token (e.g., after discovering a bridging bug, an exploited external contract, or a depegged/compromised asset). However, none of the `x/uexecutor` code paths that consume `TokenConfig` (`depositPRC20` in `x/uexecutor/keeper/handler.go`, `ExecuteInboundGas`, `ExecuteInboundGasAndPayload`, `ExecuteInboundFundsAndPayload`) check the `Enabled` field before minting PRC20 or executing a deposit. Only `ChainConfig.Enabled.IsInboundEnabled` / `IsOutboundEnabled` are enforced (in `x/uexecutor/keeper/msg_vote_inbound.go` and `x/uregistry/keeper/keeper.go`'s `IsChainInboundEnabled`/`IsChainOutboundEnabled`), and there is no equivalent `IsTokenEnabled` gate anywhere in the executor. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`x/uregistry` defines a per-token `Enabled` flag intended as an emergency/administrative kill switch, distinct from and parallel to the per-chain `ChainEnabled.IsInboundEnabled`/`IsOutboundEnabled` flags. The chain-level flags are actively enforced: `VoteInbound` calls `k.uregistryKeeper.IsChainInboundEnabled(ctx, inbound.SourceChain)` before any state mutation and rejects the vote if disabled (`x/uexecutor/keeper/msg_vote_inbound.go:31-39`), with dedicated tests confirming no UTX is created when a chain is disabled (`test/integration/uexecutor/chain_enabled_test.go`).

No equivalent check exists for `TokenConfig.Enabled`. `k.uregistryKeeper.GetTokenConfig(ctx, chain, address)` simply fetches the stored config and returns it — it never inspects `Enabled` (`x/uregistry/keeper/keeper.go:227-234`). Every caller of `GetTokenConfig` in `x/uexecutor` (the deposit helper in `handler.go`, and the execution paths in `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, `execute_inbound_funds_and_payload.go`) proceeds directly to minting PRC20 / calling `CallPRC20Deposit` using `tokenConfig.NativeRepresentation.ContractAddress`, regardless of `tokenConfig.Enabled`'s value.

This is a live analog of the report's bug class: a governance/admin-facing kill switch that is supposed to gate a specific state-changing action (bridging/minting for a token) but is not consulted by the very code path it is meant to gate. In the original report, `killBribeVault()` correctly blocked new votes but failed to block "poke" refreshes of already-cast votes referencing the disabled vault, letting stale privileged state persist. Here, the parallel invariant break is broader: the disable flag is entirely dead code with respect to `x/uexecutor`, so an unprivileged user can continue submitting `Inbound` votes (via bonded UVs observing real external-chain events) for a token that governance has explicitly disabled, and the chain will happily continue minting PRC20 and executing deposits/payloads for it — the "disabled" state never changes the corrupted value (minted PRC20 supply / UEA balances) at all.

### Impact Explanation
If governance disables a `TokenConfig` (e.g., in response to a compromised external token contract, a bridging vulnerability, or a liquidity/backing issue), the intended effect — halting further synthetic minting or bridging of that asset — does not occur. Ordinary users (not privileged actors) can keep sending inbound transfers of the disabled asset from the source chain, and honest Universal Validators will continue voting them through, since the vote path (`VoteInbound`) only checks chain-level enablement, not token-level enablement. This can result in unauthorized/unintended PRC20 minting continuing after an emergency disable, corrupting the accounting invariant that a disabled token's PRC20 supply should be frozen, and defeating an operator's primary tool for stopping an in-progress incident.

### Likelihood Explanation
Low/Medium. Exploitation requires: (1) governance/admin to disable a `TokenConfig` (an external event, not attacker-controlled, but a realistic and expected operational action — analogous to the original report's "incoming governance proposal" precondition), and (2) an ordinary user continuing to submit inbound transfers of that token from the source chain, which is a completely permissionless, default action requiring no special capital or privilege. Given that the check is simply absent rather than merely buggy under specific edge cases, this triggers on the very first attempt post-disable, unconditionally.

### Recommendation
Add an `IsTokenEnabled(ctx, chain, address)` (or `GetTokenConfig` variant) analogous to `IsChainInboundEnabled`/`IsChainOutboundEnabled`, and enforce it inside `x/uexecutor` execution paths — ideally both at `VoteInbound` time (to avoid producing stale ballots/UTX for disabled tokens) and defensively inside `depositPRC20`/`ExecuteInboundGas*`/`ExecuteInboundFundsAndPayload` before any `CallPRC20Deposit`/mint occurs, mirroring the chain-level enforcement pattern already present in `msg_vote_inbound.go`.

### Proof of Concept
1. Admin registers a `TokenConfig` for `eip155:11155111`/USDC with `Enabled=true` and a valid `NativeRepresentation`.
2. A user bridges USDC inbound normally; UVs vote via `MsgVoteInbound`, quorum is reached, and PRC20 is minted (as shown by the existing test `TestVoteInbound_ChainEnabled`/`TestInboundSyntheticBridge` flows).
3. Admin calls `MsgUpdateTokenConfig` to set `Enabled=false` on that same `chain:address` (intended to halt further bridging of this token).
4. A new inbound event for the same token/chain is observed and voted on by UVs exactly as before. Because `VoteInbound` only calls `IsChainInboundEnabled` (not any token-level check) and `depositPRC20`/`GetTokenConfig` never consult `Enabled`, the vote passes and `CallPRC20Deposit` mints new PRC20 to the recipient exactly as if the token were still enabled — no error, no revert, no `INBOUND_REVERT` outbound, contradicting the intended effect of disabling the token.

// IsChainInboundEnabled checks if inbound is enabled for a given chain
func (k Keeper) IsChainInboundEnabled(ctx context.Context, chain string) (bool, error) {
	config, err := k.GetChainConfig(ctx, chain)
	if err != nil {
		if errors.Is(err, collections.ErrNotFound) {
			// chain not found
			return false, nil
		}
		return false, err
	}
	if config.Enabled == nil {
		return false, nil
	}
	return config.Enabled.IsInboundEnabled, nil
}
