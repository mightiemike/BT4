### Title
Unbounded subtraction in `UnDelegateResource` can push receiver's `NetUsage`/`EnergyUsage` negative, artificially inflating available bandwidth/energy — ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
This is the same bug class as the Aave `LTV = 0` finding: a "limit − usage" style calculation performs a raw, unguarded subtraction that can underflow when the subtrahend is derived from an approximate (floating-point) ratio rather than being provably bounded by the minuend. In java-tron, `UnDelegateResourceActuator.execute()` (and its TVM-native counterpart `UnDelegateResourceProcessor.execute()`) computes a `transferUsage` value via floating-point division/multiplication and then subtracts it directly from the receiver account's `NetUsage`/`EnergyUsage` without any floor/clamp, exactly mirroring the unguarded `netBorrowLimit.sub(borrowValue)` pattern that caused the original underflow.

### Finding Description
In `UnDelegateResourceActuator.execute()`: [1](#0-0) 
the code computes:
```
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
...
long newNetUsage = receiverCapsule.getNetUsage() - transferUsage;
receiverCapsule.setNetUsage(newNetUsage);
```
The identical pattern exists for `ENERGY`: [2](#0-1) 
and in the TVM-reachable native processor: [3](#0-2) 

`transferUsage` is intended to always be `<= receiverCapsule.getNetUsage()`, since it is `netUsage * (unDelegateBalance / allFrozenBalanceForBandwidth)` and the ratio should be `<= 1`. However:
- The ratio is computed with `double` arithmetic, not exact integer/BigInteger math (unlike the hardened exchange and resource-limit code elsewhere in the codebase, e.g. `RepositoryImpl.calculateGlobalEnergyLimit` and `ResourceProcessor.calculateGlobalLimitV1/V2`, which explicitly use `BigInteger` for exactness under `hardenCalculation()`).
- `min(unDelegateMaxUsage, transferUsage)` only bounds `transferUsage` against a *separately computed* floating-point quantity (`unDelegateMaxUsage`), not against the true `receiverCapsule.getNetUsage()` value being subtracted from. It does not guarantee `transferUsage <= getNetUsage()`.
- The final line `receiverCapsule.getNetUsage() - transferUsage` is a raw `long` subtraction with no `max(..., 0)` clamp and no use of `subtractExact`/hardened math, unlike other resource-accounting code in the same codebase that explicitly guards against negative results, e.g.: [4](#0-3) 
and [5](#0-4) 
both of which wrap the analogous subtraction in `max(0, ...)`.

If `transferUsage` ends up numerically larger than `receiverCapsule.getNetUsage()` (due to floating-point rounding when `unDelegateBalance` is close to `allFrozenBalanceForBandwidth`, or due to prior state where `getNetUsage()` was already reduced by a previous partial `UnDelegateResource` call using imprecise double math), `newNetUsage` becomes negative and is persisted directly via `setNetUsage()`/`setEnergyUsage()` with no validation.

A negative stored `NetUsage`/`EnergyUsage` then corrupts every downstream "limit − usage" computation performed by `BandwidthProcessor`/`EnergyProcessor` (e.g. `useAccountNet`, `useEnergy`, `getAccountLeftEnergyFromFreeze`), where `bytes > (netLimit - newNetUsage)` or `energy > (energyLimit - newEnergyUsage)` is evaluated. A negative usage inflates the effective available bandwidth/energy for the account far beyond its true entitlement — the same "perceived limit becomes incredibly large" effect described in the Aave report, since `limit − (negative usage)` is larger than `limit`.

### Impact Explanation
This directly affects on-chain resource accounting reachable from an ordinary, unprivileged, broadcast `UnDelegateResourceContract` transaction (both via the actuator path and the TVM-native `unDelegateResource` precompiled/native path). A corrupted negative usage value would let the affected receiver account consume bandwidth/energy beyond its legitimate frozen-balance-derived limit, effectively bypassing the network's resource-throttling/anti-spam mechanism — a DoS-adjacent resource-accounting corruption bug, analogous in severity/class to the referenced Aave finding (perceived limit becomes unintentionally large due to unguarded underflow-prone subtraction).

### Likelihood Explanation
Likelihood is uncertain without deeper numeric analysis or a live reproduction: the ratio `unDelegateBalance / allFrozenBalanceForBandwidth` should mathematically be `<= 1` in well-formed states, and `validate()` (see `unDelegateResourceContract` validation logic) enforces `unDelegateBalance <= delegateBalance`, which constrains but does not exactly equal `allFrozenBalanceForBandwidth`. Triggering the underflow would likely require chained/partial undelegate operations and specific balance ratios that expose double-precision rounding at the boundary (e.g., `unDelegateBalance` very close to `allFrozenBalanceForBandwidth`). This is a real code-path weakness (no explicit invariant enforced) but I could not fully confirm from static reading alone whether floating-point rounding in practice can push the ratio above 1.0 for realistic values, since I was unable to execute the arithmetic or find an existing test exercising this specific underflow (the existing test suite around `UnDelegateResourceActuator`/`FreezeV2Test` was not reviewed for this exact scenario).

### Recommendation
- Replace the floating-point ratio computation with exact integer/`BigInteger` arithmetic (as already done elsewhere in the codebase under `hardenCalculation()`/`hardenResourceCalculation()`), or explicitly clamp `transferUsage` to `Math.min(transferUsage, receiverCapsule.getNetUsage())` / `Math.min(transferUsage, receiverCapsule.getEnergyUsage())` before subtracting.
- Wrap the final `newNetUsage`/`newEnergyUsage` computation in `Math.max(0, ...)` (mirroring the pattern already used in `EnergyProcessor.getAccountLeftEnergyFromFreeze` and `Wallet.calcCanDelegatedBandWidthMaxSize`), or use `subtractExact` combined with an explicit floor at zero, so a negative usage value can never be persisted.
- Add regression tests for `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` that exercise boundary ratios (`unDelegateBalance` at/near `allFrozenBalanceForBandwidth`/`allFrozenBalanceForEnergy`) to ensure `NetUsage`/`EnergyUsage` never goes negative after undelegation.

### Proof of Concept
Not independently reproduced/executed. The described PoC path is: an account delegates bandwidth/energy to a receiver, the receiver consumes some of it (raising `NetUsage`/`EnergyUsage`), and the delegator issues one or more `UnDelegateResourceContract` transactions whose `balance` values, combined with floating-point rounding in `(double) unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth()`, cause the computed `transferUsage` to exceed the receiver's actual `getNetUsage()`/`getEnergyUsage()` at subtraction time, producing a negative stored usage value. Confirming an exact triggering input set would require running the arithmetic (unit test) against the live code, which was not available in this analysis.
