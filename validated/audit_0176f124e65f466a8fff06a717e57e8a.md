### Title
Missing Slippage Protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's Bancor-style TRX/TRC10 `Exchange` module has two categories of user actions: trading (`ExchangeTransactionContract`) and liquidity management (`ExchangeInjectContract`/`ExchangeWithdrawContract`). The trading path lets the caller specify a minimum-received `expected` value that is checked against the freshly-computed swap output at execution time, exactly like the ZAP path in the external report. The liquidity-injection and liquidity-withdrawal paths, however, provide **no equivalent bound**: the counter-asset amount (`anotherTokenQuant`) is computed purely from the exchange pool's live balances at execution time, with no user-supplied minimum/maximum to protect against balance changes between transaction submission and execution — the same missing-slippage-check bug class described in the external report (where `_postLiquidate` burns USG using a live-computed amount with no bound, unlike the ZAP path which checks `minUSGOut`).

### Finding Description
For `ExchangeTransactionContract`, `ExchangeTransactionActuator.doValidate()` computes `anotherTokenQuant` via `exchangeCapsule.transaction(...)` and explicitly enforces the caller-supplied floor: [1](#0-0) 

In contrast, `ExchangeInjectActuator.execute()` recomputes `anotherTokenQuant` from the exchange's *current* `firstTokenBalance`/`secondTokenBalance` at execution time and immediately debits/credits the account for it — there is no field in `ExchangeInjectContract` (only `owner_address`, `exchange_id`, `token_id`, `quant`) that lets the caller bound the counter-asset amount they will receive/pay: [2](#0-1) [3](#0-2) 

Likewise, `ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` at validate time from the live pool ratio and only checks a fixed 0.01% precision-rounding tolerance (`"Not precise enough"`), not a user-chosen slippage bound; `ExchangeWithdrawContract` also has no min/max field: [4](#0-3) [5](#0-4) 

Because the pool balances (`firstTokenBalance`/`secondTokenBalance`) are shared, mutable on-chain state that can be moved by any other pending `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` broadcast around the same time (block-producer transaction ordering is not controlled by the submitter), a caller of Inject/Withdraw has no way to cap the amount of the counter-asset they will actually pay or receive once the transaction executes — mirroring the report's root cause: a value-moving action computed from live state with no caller-enforced bound, while a sibling action (`ExchangeTransactionContract`) in the same module already has this protection.

### Impact Explanation
An unprivileged liquidity provider using `ExchangeInjectContract`/`ExchangeWithdrawContract` can lose value relative to their intent if the pool ratio shifts between the moment they decide the trade and the moment it executes (e.g., due to other transactions being included first in the same or an earlier block). For injection, they could end up contributing a different (worse) amount of the counter-asset than expected; for withdrawal, they could receive less of the counter-asset than expected. This is a concrete accounting/value-transfer impact on unprivileged user funds, not merely theoretical, since `execute()` unconditionally moves both asset balances based on the live ratio.

### Likelihood Explanation
Any account holding TRX/TRC10 balances can call `injectexchangetoken`/`withdrawexchangetoken` (constrained only to being the exchange creator, which is any regular account that created that specific exchange pair — not a privileged system role). Exchange pool ratios naturally move whenever other participants trade, inject, or withdraw, which is a normal, frequent occurrence for any active exchange, making the exposure window realistic rather than contrived.

### Recommendation
Add slippage-protection fields (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeInjectContract` and `ExchangeWithdrawContract` — e.g., a caller-specified minimum/maximum `anotherTokenQuant` — and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s `doValidate()`/`execute()`, rejecting the transaction if the live-computed counter-asset amount falls outside the caller's bound, consistent with the check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Account A creates an exchange with pool balances `firstTokenBalance=1000`, `secondTokenBalance=1000`.
2. Account A broadcasts `ExchangeInjectContract` intending to inject `100` of the first token, expecting `anotherTokenQuant≈100`.
3. Before A's transaction is included, another account performs an `ExchangeTransactionContract` swap that shifts the pool ratio significantly (e.g., to `firstTokenBalance=1000`, `secondTokenBalance=200`).
4. A's injection then executes in `ExchangeInjectActuator.execute()` using the shifted ratio, computing `anotherTokenQuant = floorDiv(200*100, 1000) = 20` instead of the originally expected `~100`, and A's second-token balance is debited by only `20` — locking A into a materially different (and now creator-privileged, imbalanced) liquidity position than intended, with no on-chain mechanism (`Tron protobuf protocol document.md:1384-1401`) to have rejected the transaction for this deviation.
