Based on my investigation, I found a genuine, self-documented state-integrity gap in the replay/verification path, distinct from the original EIP-712 nonce report but analogous in kind (a security-relevant field silently excluded from an authentication/verification check).

### Title
Replay-verification `ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, allowing state-root divergence to pass silently - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by node-operator/auditor tooling (`db-tool replay_on_archive`, `aptos-debugger`, `aptos move cli`) to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` stored in the ledger/accumulator. It checks status, gas, write-set hash, and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the actual state root (Sparse Merkle Tree / hot-state / position-state root) committed to the ledger.

### Finding Description
`ensure_match_transaction_info` [1](#0-0)  validates:
- execution status vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- write-set hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

but explicitly and knowingly skips the checkpoint-hash fields, as stated in the trailing comment: [2](#0-1) 

`TransactionInfoV0`/`V1` carry `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` precisely because they authenticate the world-state root at that version [3](#0-2) , yet none of these are cross-checked against locally computed values in this function.

This function is the sole correctness gate used by:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` to decide pass/fail for the whole replay-verify tool [4](#0-3) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` (same call, used for auditing/replay verification of production chain data).

Because the state-root fields are never compared, a scenario where the locally recomputed state root (e.g. due to a storage schema bug, a JMT/restore bug, or a hard-fork-only VM divergence affecting only state application, not the write set encoding) diverges from the archived, authenticated `TransactionInfo` will still report "verified" success, since write-set hash and event hash equality do not imply state-root equality in the presence of checkpoint-hash-affecting bugs (e.g. hot-state or position-state bugs, or any bug in the checkpoint construction/proof-binding layer downstream of `do_state_checkpoint.rs` [5](#0-4) ).

### Impact Explanation
This is a proof/verification-integrity gap: a tool whose entire purpose is to authenticate that re-executed state matches the historically committed, accumulator-proven ledger state can return a false "verified" result when the state root has silently diverged. This directly undermines the "Committed state that differs from the correct VM result... accepted as valid" and "Hard-fork-only divergence during... replay" criteria — operators, auditors, and disaster-recovery/restore validation relying on `replay_on_archive` or `aptos-debugger` for state-root assurance get a false sense of correctness.

### Likelihood Explanation
Likelihood is Medium: this doesn't require an attacker in the classic sense — it manifests whenever a state-root-affecting bug or fork exists elsewhere in the stack (storage, checkpoint hashing, hot-state, or position-state code), and it means such a bug would go undetected by the project's own replay-verification safety net. The gap is already self-acknowledged in-code via the TODO comment, confirming it is a real, currently-unaddressed omission rather than an intentional design choice.

### Recommendation
Extend `ensure_match_transaction_info` to accept and compare the locally computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when available) against the corresponding fields of `txn_info`, and thread the actually-computed checkpoint hashes from the execution pipeline (`do_state_checkpoint.rs`) into the verification call sites in `replay_on_archive.rs`, `aptos_debugger.rs`, and `commands.rs`, per the TODO's own recommendation, before any reliance on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
1. Archive/backup a chain segment whose `TransactionInfo` (V0/V1) contains correct `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
2. Run `replay_on_archive` (`Verifier::execute_and_verify`) against a local execution environment with a hypothetical state-application divergence that keeps write-set bytes and events identical but changes the resulting state root (e.g., a JMT construction or hot-state bug).
3. Observe `ensure_match_transaction_info` returns `Ok(())` because it never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so `execute_and_verify` reports the chunk as verified despite the state root being wrong.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
