### Title
Unbounded, non-deduplicated growth of the per-shop session-id index in `KVSessionStorage` leads to Denial-of-Service ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage` maintains a `shop:<shop>` key holding a JSON array of every session id ever stored for that shop, used by `findSessionsByShop`/token-exchange re-authentication flows. Unlike the sibling `RedisSessionStorage` adapter, the KV adapter's `addShopIds` helper appends ids without checking for duplicates, so the array can grow without bound whenever `storeSession` is invoked repeatedly for the same session id (e.g., recurring offline-token re-exchange after expiry/invalidation). This mirrors the "unbounded array growth causing out-of-gas/DoS" bug class from the referenced report, here manifesting as unbounded KV value growth and unbounded iteration cost.

### Finding Description
`addShopIds` simply concatenates new ids into the existing list with no de-duplication: [1](#0-0) 

Compare this to the Redis adapter, which explicitly guards against duplicate insertion: [2](#0-1) 

`storeSession` calls `addShopIds(session.shop, [session.id])` on every store, and session ids for offline/online tokens are deterministic per shop/user (`getOfflineId(shop)` / `getJwtSessionId(shop, sub)`), so re-storing the same session (e.g., after token invalidation or expiry) repeatedly appends the identical id string to the `shop:<shop>` array: [3](#0-2) 

This code path is reachable from the token-exchange authentication handlers used by embedded apps, which re-run `storeSession` whenever the currently stored session is missing or inactive/invalidated: [4](#0-3) [5](#0-4) 

`invalidateAccessToken` clears the access token on a 401 response and this handler is wired into `handleClientError`, so a client that can force repeated 401s against the admin API (or simply repeated expiry cycles for online sessions) will cause `storeSession` → `addShopIds` to run repeatedly for the same shop/session id, each time growing the KV array by one duplicate entry with no cap.

`findSessionsByShop` then iterates the full (duplicate-laden) id list and issues one KV `get` per entry: [6](#0-5) 

### Impact Explanation
As the `shop:<shop>` array grows unbounded:
- The JSON payload stored under `shop:<shop>` grows without limit, eventually exceeding Cloudflare KV's 25 MiB value-size limit, causing `put` calls in `addShopIds`/`storeSession` to fail and permanently breaking session persistence for that shop.
- `findSessionsByShop` cost grows linearly with the (duplicate-inflated) array size, causing increasing latency/CPU usage on every call, which can exceed platform CPU-time limits for the Worker handling the request, denying service to legitimate app-install/auth checks for that shop (e.g., `AppInstallations.includes`/`delete` in `shopify-app-express`, which depend on `findSessionsByShop`).
- Because this affects the authentication/session-lookup path itself, once triggered it degrades or blocks all subsequent authenticated requests for the affected shop — a persistent, self-inflicted DoS analogous to the "permanently locked" state in the reference report.

### Likelihood Explanation
Reachable by a single merchant/user session without any special privileges: any repeated cycle of "session missing/expired → offline or online token re-exchange" (natural expiry of online tokens, or forced 401 via `invalidateAccessToken`) drives `storeSession` for the same session id repeatedly. No admin/privileged access is required — only the ability to repeatedly trigger the token-exchange re-authentication branch of `perform-token-exchange.ts` / `token-exchange.ts`.

### Recommendation
In `addShopIds` (and the analogous `removeShopIds`), de-duplicate before writing, mirroring the Redis adapter's guard:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```
Additionally consider capping the number of tracked session ids per shop and pruning expired/stale entries during `findSessionsByShop`/`storeSession`.

### Proof of Concept
1. Configure an embedded app using `KVSessionStorage` with the token-exchange authentication strategy (`shopify-app-react-router` or `shopify-app-express`).
2. As a normal merchant/session-token holder, repeatedly cause the "no valid session" branch to execute for the same shop — e.g., let the online access token expire (or force a 401 so `invalidateAccessToken` clears the offline token) and re-issue an authenticated request N times.
3. Each cycle calls `storeSession(offlineSession)` (and `storeSession(onlineSession)` if online tokens are enabled) with the same deterministic session id, and `addShopIds` appends a duplicate id each time with no check.
4. Inspect the `shop:<shop>` KV entry: its array length grows by one per cycle indefinitely; after enough cycles, `findSessionsByShop` becomes measurably slower (linear in array size with many stale/duplicate `loadSession` calls) and, at scale, `put` calls will fail once the JSON payload exceeds the KV value size limit, breaking session storage for that shop.
