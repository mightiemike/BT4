### Title
Unguarded division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` relies on a disabled Java `assert`, permitting divide-by-zero / silent corruption - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
The Y2K-Finance `Carousel.mintRollovers` bug stems from an aggregate value (`finalTVL`) that can legitimately become `0`, being divided into without a guard, causing a revert that permanently freezes an account's rollover slot. The java-tron analog is `RepositoryImpl.calculateGlobalEnergyLimit`, which divides by the global aggregate `totalEnergyWeight` and only protects against the zero case with a Java `assert` statement — a construct that is compiled out / disabled at runtime unless the JVM is started with `-ea`, which production nodes are not. This differs from the sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit`, which has an explicit runtime check (`if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) { return 0; }`) before doing the same division.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` computes a resource limit by dividing by the chain-wide aggregate `totalEnergyWeight`: [1](#0-0) 

The only defense against `totalEnergyWeight == 0` is `assert totalEnergyWeight > 0;` at line 976. In standard JVM deployments assertions are disabled by default, so this line is a no-op in production. If `totalEnergyWeight` is ever `0` when this method executes:
- With `hardenResourceCalculation()` enabled, `BigInteger.divide(BigInteger.ZERO)` throws an uncaught `ArithmeticException`.
- Without hardening, the legacy double-arithmetic branch `(long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight))` silently produces `Infinity`/`NaN`, which truncates to an undefined `long` value, corrupting the returned energy limit.

By contrast, the equivalent function in `EnergyProcessor` explicitly guards this exact aggregate against zero before dividing: [2](#0-1) 

and the bandwidth counterpart in `BandwidthProcessor` does the same for `totalNetWeight`: [3](#0-2) 

This shows the project is aware `totalEnergyWeight`/`totalNetWeight` can be `0` (it is only recalculated once per maintenance cycle, decoupled from real-time freeze/unfreeze activity) and normally treats that as a defensive short-circuit — except in the `RepositoryImpl` path used by the TVM native-contract/`Repository` layer, which is invoked from `ContractState` and `Wallet`.

### Impact Explanation
This mirrors the Y2K root cause exactly: an aggregate (`finalTVL` there, `totalEnergyWeight` here) that the code assumes is always positive can legitimately be `0`, and the divide is unguarded outside of a debug-only assertion. Reaching this state (e.g., before the aggregate has been (re)computed by a maintenance cycle, or after all energy-frozen balances have unfrozen) causes:
- An uncaught `ArithmeticException` during deterministic TVM/native-contract execution paths, which is a state-transition/consensus-relevant computation — an uncaught runtime exception here risks inconsistent handling across implementations/versions (divergence) rather than a clean, intentional revert.
- Or, in the non-hardened path, silent corruption of the computed energy limit (`NaN`/`Infinity` → undefined `long`), which is an accounting/invalid-state bug feeding into resource-limit logic.

### Likelihood Explanation
`totalEnergyWeight` is a chain-wide, periodically-recalculated aggregate (only updated at maintenance cycles), not synchronously maintained with every freeze/unfreeze, so a window where it is `0` while an individual account already has `frozeBalance >= TRX_PRECISION` is plausible (e.g., early network life before the first maintenance cycle, or a private/test chain). This does not require privileged access — any account freezing energy exercises this code path. That said, I was not able to fully verify from the index alone whether production genesis/maintenance-cycle sequencing makes `totalEnergyWeight == 0` unreachable on mainnet specifically (this would need runtime/genesis-block verification beyond what the index provides).

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime guard mirroring `EnergyProcessor.calculateGlobalEnergyLimit`'s `allowNewReward()`/`totalEnergyWeight <= 0` check that returns `0` (or another safe sentinel) instead of dividing, ensuring behavior is consistent and safe across both processor implementations regardless of JVM assertion settings.

### Proof of Concept
1. Deploy/initialize a chain state (or unit test harness) where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., fresh genesis prior to the first maintenance cycle, as exercised by tests such as [4](#0-3) , which explicitly set `totalEnergyWeight` independent of any account state).
2. Have an account freeze `>= TRX_PRECISION` for energy so `frozeBalance >= TRX_PRECISION`, passing the early-return guard at line 969.
3. Call `RepositoryImpl.calculateGlobalEnergyLimit(accountCapsule)` (reachable via `ContractState`/`Wallet` TVM-facing paths) with `hardenResourceCalculation()` enabled: `BigInteger.valueOf(totalEnergyWeight)` is `0`, and `.divide(BigInteger.ZERO)` throws `ArithmeticException`, uncaught by this method — mirroring the Sherlock report's `previewWithdraw` revert-on-zero-TVL pattern, but here manifesting as an uncaught runtime exception instead of an intentional, catchable revert.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {

    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();

    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }
