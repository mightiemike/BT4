### Title
Poison-microblock double-sign check accepts identical, duplicated microblock headers with no evidence of equivocation - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`check_microblock_header_signer` only verifies that the recovered public-key hashes of the two supplied `StacksMicroblockHeader`s are equal; it never checks that the two headers are actually distinct (different signature/content). Because a header trivially recovers to the same pubkey hash as itself, an attacker can submit `PoisonMicroblock(M.header, M.header.clone())` for any single, legitimately-published microblock `M` and have it accepted as proof of equivocation, causing the originating miner to be slashed and the attacker to be paid a commission with no second, conflicting microblock ever having existed.

### Finding Description
The equality the protocol is supposed to enforce is: *poison report accepted ⇔ two DISTINCT microblock headers exist, signed by the same key, that conflict (equivocation)*. The code instead only checks pkh1 == pkh2: [1](#0-0) 

`handle_poison_microblock` calls this check and then, if it passes, looks up whether the pubkey hash was ever seen in this fork (`get_microblock_pubkey_hash_height`) and whether it's still within the maturity window, then unconditionally records a poison report via `insert_microblock_poison`: [2](#0-1) [3](#0-2) 

Neither `check_microblock_header_signer`, `handle_poison_microblock`, nor `get_microblock_pubkey_hash_height` verifies that `mblock_header_1` and `mblock_header_2` differ in any field (signature, sequence, prev_block, tx_merkle_root). `get_microblock_pubkey_hash_height` only confirms that the pubkey hash was used to sign *some* microblock at *some* height in this fork — it does not prove two conflicting microblocks exist. The mempool-side static check in `blocks.rs` (`TransactionPayload::PoisonMicroblock` arm) only requires `sequence`, `prev_block`, `version` to match and pkh1 == pkh2 — all of which are trivially true when the two headers are bit-for-bit identical: [4](#0-3) 

The existing unit tests for this path always construct two genuinely distinct microblocks (`assert!(mblock_1 != mblock_2)`) and never exercise or assert rejection of the identical-header case: [5](#0-4) 

**Attacker's exact input**: any previously-broadcast, legitimate `StacksMicroblockHeader` `M` (publicly observable), duplicated as `PoisonMicroblock(M.header, M.header)`.

**Exploit flow**: `process_transaction` → `run_poison_microblock` → `handle_poison_microblock` → `check_microblock_header_signer(M, M)` returns `Ok(pkh)` trivially → `get_microblock_pubkey_hash_height(pkh)` succeeds because the miner did in fact sign at that height with that key → `insert_microblock_poison` records a poison/commission entry against the miner, though no second, conflicting header was ever produced.

**Why existing guards fail**: All guards (`check_microblock_header_signer`, the mempool static-validation arm, `get_microblock_pubkey_hash_height`, the maturity-window check) validate signature validity, pubkey-hash equality, and recency — none validate header distinctness/non-identity, which is the actual defining property of equivocation.

### Impact Explanation
This is a reward mis-payment / miner-slashing bug bounded to the coinbase commission mechanism (poison reports redirect a miner's matured coinbase reward to the reporter). It does not cause a chain split, an invalid block being accepted, or a non-reproducible MARF root — all nodes process the transaction identically and agree on the (incorrect) outcome. Per the severity rubric, this falls under **High**: "a poison or reward mis-payment bounded to fees" — the miner is wrongfully slashed and the attacker wrongfully collects a commission, but consensus itself remains consistent across nodes.

### Likelihood Explanation
- Precondition: any miner has published at least one microblock ever (near-universal, since virtually every miner tenure that runs microblocks produces this).
- The attacker needs no stake, no signing key, no privileged role — only the ability to observe a public microblock header and submit a standard Stacks transaction (pays only the normal tx fee).
- Fully repeatable against any miner's microblock stream at any time within the maturity window (`MINER_REWARD_MATURITY`), by any unprivileged party.
- Feasibility is high: constructing `PoisonMicroblock(M.header, M.header.clone())` requires no cryptography beyond copying already-public data.

### Recommendation
Add an explicit distinctness check in `check_microblock_header_signer` (or `handle_poison_microblock`) requiring that the two headers are not identical — e.g., reject if `mblock_hdr_1.block_hash() == mblock_hdr_2.block_hash()` (or compare full serialized headers) before accepting the poison report as evidence of equivocation. Apply the same guard in the mempool static-check path in `stackslib/src/chainstate/stacks/db/blocks.rs` for `TransactionPayload::PoisonMicroblock`.

        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {

                format!("Failed to recover public key: {:?}", &e),
                false,
            )

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {

                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
