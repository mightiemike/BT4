## Analog Found: Precision loss via divide-before-multiply in legacy vote reward computation

### Title
Loss of precision in `MortgageService.computeReward` (legacy per-cycle reward path) due to division performed before multiplication - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The reported Solidity issue divides `x` by `t_r` before later multiplying it by `y`, discarding remainder bits that should have survived until after the multiplication. The same class of bug — dividing a ratio first and only then multiplying it against a large value — exists in `MortgageService`'s legacy ("old algorithm") reward computation, which converts a voter's share of a witness's total vote into a TRX reward using floating-point division ahead of multiplication.

### Finding Description
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes, for each cycle before `NewRewardAlgorithmEffectiveCycle`, a voter's share of total reward like this: [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
```

Here `voteRate = userVote / totalVote` is computed and truncated to a `double` **before** being multiplied by `totalReward`. This is structurally identical to the reported `scalarPrice` bug: `x = (t + t_mod) * b_18 / t_r` computed (and rounded) before being multiplied by `y`. In both cases, doing the division first discards precision that a "multiply-then-divide" ordering would have preserved, and — because `double` only has 53 bits of mantissa — for large `totalReward`/`totalVote` values (TRX reward amounts are in `sun`, i.e., can be large 64-bit longs) this can silently truncate reward amounts.

This is invoked from the actively used reward-withdrawal path: `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)` calls `getOldReward(beginCycle, oldEndCycle, srAddresses)` for the portion of the cycle range prior to `newAlgorithmCycle`, which in turn calls this per-cycle `computeReward`: [2](#0-1) 

By contrast, the *new* reward algorithm in the same file (and in `VoteRewardUtil`/`RewardViCalService`) explicitly avoids this exact bug class by using `BigInteger` and multiplying before dividing: [3](#0-2) 

The codebase in general shows the team is aware of and has systematically hardened this bug class elsewhere (`RepositoryImpl.calculateGlobalEnergyLimit`, `ResourceProcessor.calculateGlobalLimitV1/V2`, `BandwidthProcessor.calculateGlobalNetLimit`, `SafeExchangeProcessor`), each behind an `allowHarden*` feature flag with dedicated regression tests comparing "buggy" doubles vs. `BigInteger`-exact results, e.g.: [4](#0-3) 

However, `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` (the legacy per-cycle vote-reward split) has **no** such BigInteger-hardened path — it remains on raw `double` arithmetic with division ordered before multiplication.

### Impact Explanation
Medium: any unprivileged user withdrawing SR voting rewards accrued in cycles prior to the new reward algorithm's activation cycle receives a reward amount computed via a lossy `double` division-then-multiplication instead of an exact `BigInteger` multiply-then-divide. The discrepancy is generally small per voter/per cycle, but it directly affects real TRX payouts (`WithdrawBalanceActuator` → `MortgageService.withdrawReward` → `computeReward`), i.e., an underpriced/misallocated economic settlement, matching the "price will not be very far from expected, but a loss of precision occurs" characterization of the original report.

### Likelihood Explanation
Medium: this path is exercised whenever any voter withdraws rewards for cycles that occurred before `getNewRewardAlgorithmEffectiveCycle()`. Since that cycle boundary is fixed historically, the amount of exposure is bounded to historical cycles, but the code path remains live and reachable by any account with legacy voting rewards to withdraw. Reproducing exact numeric divergence would require replaying real historical `totalVote`/`totalReward`/`userVote` values through both a `double`-based and a `BigInteger`-based computation (as the project's own hardened tests do for other calculators), which I could not execute here.

### Recommendation
Change `computeReward(long cycle, List<Pair<byte[], Long>> votes)` to compute `reward += userVote * totalReward / totalVote` using `BigInteger` (multiply before divide, mirroring the pattern already used in the "new algorithm" path and in `RewardViCalService`/`ResourceProcessor`), eliminating the floating-point divide-before-multiply ordering.

### Proof of Concept
Not independently executed in this session (no terminal access). Conceptually: for `userVote = 3`, `totalVote = 7`, `totalReward = 10_000_000_000_000L` (10,000 TRX in sun), `voteRate = 3.0/7.0` rounds to a `double` with limited precision; `voteRate * totalReward` will differ from the exact integer result of `(3 * 10_000_000_000_000L) / 7` by a rounding error that grows with the magnitude of `totalReward`. The project's own `CalculateGlobalLimitHardenTest` demonstrates this exact class of divergence for the analogous energy/bandwidth calculations (`testGlobalEnergyLimitV2CorrectVsDoublePrecisionLoss`), confirming the bug class is real and previously observed in this codebase, just not yet remediated in `MortgageService.computeReward`.
