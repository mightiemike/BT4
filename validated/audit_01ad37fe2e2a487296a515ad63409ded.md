### Title
Unbounded `DelegatedResourceAccountIndexStore.getV2Index` prefix scan enables cheap resource-exhaustion DoS on `GetDelegatedResourceAccountIndexV2` - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
The Sherlock finding shows that `BondAggregator.liveMarketsBy` becomes unusable because it loops over an unbounded, attacker/user-growable list and does per-item work without any pagination, so the cost of a single query call grows without bound. java-tron has the same structural bug class in `DelegatedResourceAccountIndexStore.getV2Index`, which backs the `GetDelegatedResourceAccountIndexV2` / `getDelegatedResourceAccountIndexV2` wallet API. Any account can cheaply and unboundedly grow the number of distinct delegate relationships attached to its address (1 TRX minimum per distinct receiver, no cap on distinct receivers), and every subsequent call to this API for that address does a full, unbounded `prefixQuery` DB scan, deserialization, and sort over that ever-growing list.

### Finding Description
`DelegateResourceActuator.validate()` only requires `delegateBalance >= TRX_PRECISION` (1 TRX) and that receiver != owner and receiver is not a contract; it enforces no limit on the number of *distinct* receiver addresses an owner may delegate to over time [1](#0-0) . Each successful `DelegateResourceContract` execution calls `delegatedResourceAccountIndexStore.delegateV2(owner, receiver, ts)`, which writes new `V2_FROM_PREFIX`/`V2_TO_PREFIX` keyed entries per distinct (owner, receiver) pair with no upper bound on how many such entries can accumulate [2](#0-1) [3](#0-2) .

The read path, `getV2Index(address)`, calls `getWithPrefix`, which runs `prefixQuery` twice (once for the "to" list, once for the "from" list) over the full key range for that address, deserializes every matching `DelegatedResourceAccountIndexCapsule`, and sorts the entire result set by timestamp before returning it — with no offset/limit parameters at all [4](#0-3) . `prefixQuery` itself streams and deserializes every matching key/value pair in the store with no cap [5](#0-4) .

This is exposed directly to any unprivileged caller via the `getDelegatedResourceAccountIndexV2` wallet method and the corresponding RPC/HTTP endpoints [6](#0-5) , unlike the sibling `getPaginatedNowWitnessList`/`getPaginatedProposalList` APIs that were explicitly given offset/limit pagination to bound per-call cost [7](#0-6) [8](#0-7) .

This mirrors the Sherlock report exactly: an attacker-controllable, ever-growing on-chain list is scanned in full by a "read" API with no pagination, so the per-call cost of that API scales linearly with the number of entries the attacker has created, eventually degrading or effectively denying that endpoint.

### Impact Explanation
An attacker can, using ordinary `DelegateResourceContract` transactions (1 TRX minimum, no cap on distinct receivers), grow a single account's delegate-index entry set to an arbitrarily large size at will. Every subsequent call to `GetDelegatedResourceAccountIndexV2`/`getDelegatedResourceAccountIndexV2` for that account then triggers an unbounded double `prefixQuery`, full deserialization, and a full sort of the result set on the full node, unlike deprecated-but-still-supported cousins that received explicit pagination. This is a resource-exhaustion path reachable by any unprivileged user against a public wallet/API surface, causing degraded or unusable service (elevated CPU/latency, and worst case node stalls under repeated/concurrent abuse) for that endpoint — consistent with the "underpriced-public-work"/"resource exhaustion" impact class.

### Likelihood Explanation
High. No privileged role or special contract state is required — a normal account can issue many cheap `DelegateResourceContract` transactions to distinct freshly generated receiver addresses (only 1 TRX and enough frozen balance to cover the minimum delegate amount are required per receiver), continuously growing its own index entry. The victim API (`GetDelegatedResourceAccountIndexV2`) is a standard public wallet/RPC/HTTP endpoint queried by explorers, wallets, and dApps, so the degraded query is easily and repeatedly triggerable by anyone.

### Recommendation
Add offset/limit-based pagination to `DelegatedResourceAccountIndexStore.getV2Index`/`getWithPrefix` (mirroring the pattern already used for `getPaginatedNowWitnessList`/`getPaginatedProposalList`), and/or introduce a maximum-count guard on `prefixQuery` results consumed per call. Consider also enforcing a maximum number of distinct delegate relationships per account in `DelegateResourceActuator.validate()` to bound state growth at the write path.

### Proof of Concept
1. Attacker account A freezes enough TRX/energy resource balance.
2. A repeatedly submits `DelegateResourceContract` transactions from A to N distinct freshly-generated receiver addresses, each delegating the minimum 1 TRX — each transaction is accepted because `validate()` places no cap on the number of distinct receivers [1](#0-0) .
3. Each execution adds a new entry via `delegatedResourceAccountIndexStore.delegateV2(A, receiver_i, now)` [9](#0-8) .
4. Any client calls `GetDelegatedResourceAccountIndexV2` for address A; this triggers `getV2Index(A)` → `getWithPrefix`, performing two full unbounded `prefixQuery` scans, N deserializations, and a full sort with no pagination [4](#0-3) .
5. As N grows (attacker-controlled, cheaply and unboundedly), the cost of every subsequent call for A grows proportionally, degrading that node's ability to service the query — the same root cause described in the referenced Sherlock report.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  public WitnessList getPaginatedNowWitnessList(long offset, long limit) throws
      MaintenanceUnavailableException {
    if (limit <= 0 || offset < 0) {
      return null;
    }
    if (limit > WITNESS_COUNT_LIMIT_MAX) {
      limit = WITNESS_COUNT_LIMIT_MAX;
    }

    /*
      In the maintenance period, the VoteStores will be cleared.
      To avoid the race condition of VoteStores deleted but Witness vote counts not updated,
      return retry error.
      Only apply to requests that rely on the latest block,
      which means the normal fullnode requests with HEAD cursor.
    */
    boolean isMaintenance = chainBaseManager.getDynamicPropertiesStore().getStateFlag() == 1;
    if (isMaintenance && !Args.getInstance().isSolidityNode() && getCursor() == Cursor.HEAD) {
      String message =
          "Service temporarily unavailable during maintenance period. Please try again later.";
      throw new MaintenanceUnavailableException(message);
    }
    // It contains the final vote count at the end of the last epoch.
    List<WitnessCapsule> witnessCapsuleList = chainBaseManager.getWitnessStore().getAllWitnesses();
    if (offset >= witnessCapsuleList.size()) {
      return null;
    }

    VotesStore votesStore = chainBaseManager.getVotesStore();
    // Count the vote changes for each witness in the current epoch, it is maybe negative.
    Map<ByteString, Long> countWitness = countVote(votesStore);

    // Iterate through the witness list to apply vote changes and calculate the real-time vote count
    witnessCapsuleList.forEach(witnessCapsule -> {
      long voteCount = countWitness.getOrDefault(witnessCapsule.getAddress(), 0L);
      witnessCapsule.setVoteCount(witnessCapsule.getVoteCount() + voteCount);
    });

    // Use the same sorting logic as in the Maintenance period
    WitnessStore.sortWitnesses(witnessCapsuleList,
        chainBaseManager.getDynamicPropertiesStore().allowWitnessSortOptimization());

    List<WitnessCapsule> sortedWitnessList = witnessCapsuleList.stream()
        .skip(offset)
        .limit(limit)
        .collect(Collectors.toList());

    WitnessList.Builder builder = WitnessList.newBuilder();
    sortedWitnessList.forEach(witnessCapsule ->
        builder.addWitnesses(witnessCapsule.getInstance()));

    return builder.build();
  }

  public ProposalList getPaginatedProposalList(long offset, long limit) {

    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestProposalNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestProposalNum();
    if (latestProposalNum <= offset) {
      return null;
    }
    limit =
        limit > PROPOSAL_COUNT_LIMIT_MAX ? PROPOSAL_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestProposalNum ? latestProposalNum : end;
    ProposalList.Builder builder = ProposalList.newBuilder();

    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ProposalCapsule::calculateDbKey).map(key -> {
      try {
        return chainBaseManager.getProposalStore().get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(proposalCapsule -> builder
            .addProposals(proposalCapsule.getInstance()));
    return builder.build();
  }
