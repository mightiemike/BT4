### Title
Unstake-triggered vote rescaling truncates minority SR votes to zero via floating-point division - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java])

### Summary
`UnfreezeBalanceV2Processor.updateVote()` recomputes an account's vote allocations across multiple Super Representatives (SRs) whenever the account's `tronPower` (from staked TRX) drops below the sum of previously cast votes (e.g. after an `unfreezeBalanceV2`/unstake transaction). This is structurally the same bug class as the Migration `newFractionSupply` issue: an arbitrary reduction of a "total" denominator (here, `ownedTronPower`) is used to rescale minority allocations (here, per-witness vote counts), and integer/double truncation can zero out a minority allocation entirely, silently and irreversibly dropping it — with no opt-out or revert.

### Finding Description
`updateVote()` is invoked from `execute()` of `UnfreezeBalanceV2Processor`, which is the resource-v2 native-contract handler backing the `UnfreezeBalanceV2` transaction type (also reachable through the TVM `unfreezeBalanceV2` native contract call, per `Program.java`), i.e. it is reachable by any unprivileged account broadcasting an unstake transaction. [1](#0-0) 

When the account's total votes exceed the reduced `ownedTronPower`, the code proportionally rescales every witness's vote count using floating-point arithmetic and truncates the result to a `long`: [2](#0-1) 

Specifically:
```java
long newVoteCount =
    (long) ((double) vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION);
if (newVoteCount > 0) {
  votesToAdd.add(...);
}
```
For a witness that received only a small minority of the account's votes relative to `totalVote`, this division can round down to `0`, and the `if (newVoteCount > 0)` guard silently drops that vote entry from `votesToAdd` — the entire vote for that SR disappears rather than being scaled to at least `1` or otherwise preserved. This mirrors the reported bug class: an arbitrary reduction to a "supply"/denominator value (here `ownedTronPower`, controlled indirectly by the user's own unstake amount) is used in a proportional-share recomputation, and minority allocations are zeroed by truncation without any explicit safeguard (e.g. no `require` that the new allocation preserve nonzero minority shares, no minimum-guarantee, no user consent per witness).

The threshold check only tests whether `ownedTronPower >= totalVote * TRX_PRECISION` as a whole: [3](#0-2) 
but does not check per-witness truncation risk before committing the rescaled vote list.

### Impact Explanation
Loss of votes to a minority SR removes the account's earned voting influence for that SR without the user's explicit intent, which:
- Silently alters on-chain governance/voting weight (consensus/reward-distribution side effect via `MortgageService`/`VoteRewardUtil`, since future rewards from that SR-vote pair are computed off `accountCapsule.getVotesList()`).
- Cannot be recovered — the dropped vote entry is gone from `votesCapsule`/`accountCapsule`, and the user must manually re-vote for that SR if they notice.
- Is entirely implementation-dependent (double-precision truncation), matching the original finding's "implementation based, can go unnoticed" characterization, and it happens automatically as a side effect of an ordinary unstake action rather than through any explicit confirmation step.

This is a lower-severity accounting/consensus-integrity issue rather than a fund-drain, since no TRX itself is lost (only voting weight/allocation to a specific SR), but it corrupts the intended vote/reward-accounting state.

### Likelihood Explanation
This code path triggers whenever `supportAllowNewResourceModel` is not yet in effect (or the account's old TronPower has not been invalidated) and the account partially unstakes TRON via `UnfreezeBalanceV2`/TVM `unfreezeBalanceV2`, while holding votes spread across multiple SRs where one SR received a small vote count relative to the total. This is easily reachable by any account through a normal, unprivileged unstake transaction and does not require any special network condition, making the likelihood moderate-to-high for accounts that vote for multiple SRs with skewed weights.

### Recommendation
In `updateVote()`, avoid silently dropping vote entries that truncate to zero. Options:
- Guarantee a minimum of `1` vote for any witness with `vote.getVoteCount() > 0` before rescaling if the proportional share would otherwise round to `0` (subject to not exceeding `ownedTronPower / TRX_PRECISION` in aggregate), or
- Use integer math with remainder distribution (e.g. largest-remainder method) instead of `double` division, so total redistributed votes always sum consistently with `ownedTronPower / TRX_PRECISION` without arbitrarily zeroing minority allocations, or
- At minimum, log/emit an event when a vote entry is dropped due to truncation so this side effect is observable rather than fully silent.

### Proof of Concept
1. Account A freezes/stakes TRX and casts votes: 999 to SR1 (majority) and 1 vote to SR2 (minority), for `totalVote = 1000`.
2. Account A later calls `UnfreezeBalanceV2` (or the TVM `unfreezeBalanceV2` native contract) to unstake most of its TRX, reducing `ownedTronPower` to, say, `500 * TRX_PRECISION`.
3. `updateVote()` executes:
   - For SR1: `newVoteCount = (long)(999.0/1000 * 500) = 499` (kept).
   - For SR2: `newVoteCount = (long)(1.0/1000 * 500) = 0` (dropped — `if (newVoteCount > 0)` filters it out).
4. Account A's vote for SR2 disappears entirely from `votesCapsule`/`accountCapsule`, even though A never asked to withdraw that specific vote, and A silently loses any future SR2 reward eligibility until re-voting.

  public long execute(UnfreezeBalanceV2Param param, Repository repo) {
    byte[] ownerAddress = param.getOwnerAddress();
    long unfreezeBalance = param.getUnfreezeBalance();
    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();

    long unfreezeExpireBalance = this.unfreezeExpire(accountCapsule, now);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    long expireTime = this.calcUnfreezeExpireTime(now, repo);
    accountCapsule.addUnfrozenV2List(param.getResourceType(), unfreezeBalance, expireTime);

    this.updateTotalResourceWeight(accountCapsule, param.getResourceType(), unfreezeBalance, repo);
    this.updateVote(accountCapsule, param.getResourceType(), ownerAddress, repo);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && !accountCapsule.oldTronPowerIsInvalid()) {
      accountCapsule.invalidateOldTronPower();
    }

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return unfreezeExpireBalance;
  }
