### Title
Snapshot minimizer discards `purge_keys_exact` reclaims, leaking stale storage entries and account-count/byte accounting - ([File: accounts-db/src/accounts_db.rs] / [File: runtime/src/snapshot_minimizer.rs])

### Summary
`AccountsDb::purge_keys_exact` is annotated `#[must_use]` because its `ReclaimsSlotList<AccountInfo>` return value must be fed into `handle_reclaims` to actually remove the reclaimed entries from storage (decrementing per-storage account counts/bytes and dropping storages that become empty). `SnapshotMinimizer::filter_storage` in `runtime/src/snapshot_minimizer.rs` calls `purge_keys_exact` and explicitly discards the result with `let _ = ...`, never calling `handle_reclaims` on the returned reclaims. This mirrors the reported ERC20 bug class: a return value that signals whether an operation fully "succeeded" (i.e., whether storage-side bookkeeping still needs to be applied) is silently ignored, leaving the system in an inconsistent, partially-updated state.

### Finding Description
`purge_keys_exact` removes the purged `(pubkey, slot)` pairs from the in-memory accounts index slot lists and returns a `ReclaimsSlotList<AccountInfo>` describing exactly which `(slot, AccountInfo)` entries were removed from the index. [1](#0-0) 

Every other production call site treats this return value as load-bearing: it is checked for emptiness and, if non-empty, passed to `handle_reclaims`, which is the function responsible for updating the corresponding `AccountStorageEntry`'s live account count/bytes and for detecting and removing storages that no longer hold any live accounts: [2](#0-1) [3](#0-2) 

In contrast, `SnapshotMinimizer::filter_storage` calls `purge_keys_exact` on the pubkeys it decided to drop from a storage (because they weren't in `minimized_account_set`) and discards the result: [4](#0-3) 

Because the returned reclaims are never routed to `handle_reclaims`, the storage-level accounting (per-`AccountStorageEntry` alive-account count/bytes) for the purged accounts is never decremented, and the old storage entry that held those purged accounts is never checked for/reclaimed as dead. The index-side removal happens (the pubkeys leave the index's slot list), but the storage-side state that mirrors it does not — an analog of the ERC20 `claim` bug where the "transfer" (index purge) proceeds while the corresponding acknowledgement/accounting step (storage reclaim) is silently skipped.

### Impact Explanation
Skipping `handle_reclaims` after `purge_keys_exact` leaves the old storage entry's bookkeeping stale: it still reports the purged accounts as "alive" bytes/count even though they are no longer reachable from the index. This can cause:
- Storage entries that are logically fully dead (all their accounts purged from the index) to never be identified as dead and reclaimed, since `handle_reclaims` is what detects "this storage now has zero alive accounts" and drops it.
- Incorrect/stale `alive_bytes`/count accounting used by shrink and clean heuristics (e.g. `is_shrinking_productive`), potentially causing disproportionate storage retention or skipped shrink/clean for storages that should have been reclaimed — a resource-accounting divergence between the accounts index and AccountsDb storage bookkeeping, consistent with the "disproportionate storage cost" class of impact.
- This runs during snapshot minimization (used to produce a minimal snapshot subset for local cluster/testing use), so the affected storages persist in the running `AccountsDb` instance after minimization until some other unrelated cleanup path eventually catches up, if at all, since these entries never get properly marked/counted as reclaimed.

### Likelihood Explanation
This path is reached whenever `SnapshotMinimizer` runs and a storage has purge candidates (pubkeys not in `minimized_account_set` but still contained in `self.accounts_db()`), which is a normal, expected condition for any minimization run that actually filters out data. No adversarial input is required — it's a deterministic consequence of the `let _ =` discard in `filter_storage`, `#[must_use]` on `purge_keys_exact` was specifically added to catch exactly this class of mistake, and this call site directly violates it.

### Recommendation
In `SnapshotMinimizer::filter_storage`, capture the `ReclaimsSlotList` returned by `purge_keys_exact` and, mirroring the pattern used elsewhere (`accounts_db.rs:2120-2131`, `4074-4089`), check `!reclaims.is_empty()` and pass it to `self.accounts_db().handle_reclaims(...)` with an appropriate `MarkAccountsObsolete` value, so that storage-side alive counts/bytes are correctly decremented and any storage left with no alive accounts is properly reclaimed.

### Proof of Concept
1. Run `SnapshotMinimizer::minimize` (or directly call `filter_storage`) against a storage where every stored account's pubkey is *not* in `minimized_account_set` (i.e., the whole storage should be purged).
2. Observe that `purge_pubkeys_collect` will contain every pubkey in the storage, and `purge_keys_exact` will remove them from the accounts index, returning a non-empty `ReclaimsSlotList`.
3. Because `filter_storage` discards this with `let _ = ...` (`runtime/src/snapshot_minimizer.rs:305`) rather than calling `handle_reclaims`, the storage entry's `count()`/`alive_bytes()` are never updated to reflect the removal, and the storage is not routed through the dead-storage detection that `handle_reclaims` performs.
4. Compare against the sibling call site in `purge_slot_storage` (`accounts_db.rs:4074-4089`), which performs the identical `purge_keys_exact` → `handle_reclaims` sequence and asserts the expected slot ends up marked dead — demonstrating that omitting the second step (as `filter_storage` does) leaves the storage bookkeeping in the stale, unreconciled state described above.
