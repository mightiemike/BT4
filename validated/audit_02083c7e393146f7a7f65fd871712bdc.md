The n8n advisory describes a confidentiality leak: an authenticated but restricted user reads a **secret** credential value (an HTTP header) through an expression-evaluation side channel and exfiltrates it via unrelated item data, bypassing the credential's own access restriction. This bug class fundamentally depends on a **secrecy boundary between a shared credential and other workflow users** — something with no analog in nearcore's threat model.

nearcore's runtime and state are public by design: account balances, access-key permissions/allowances, receipts, and contract state are all globally readable via JSON-RPC view calls and are not access-controlled "secrets" the way credentials are in n8n. Access keys, gas keys, and allowances (`core/primitives-core/src/account.rs`, `runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/verifier.rs`) restrict *what actions* a key can authorize, not *confidential data* that could be leaked to another party via an expression-like read path. [1](#0-0) [2](#0-1) 

I searched the areas most analogous to "restricted actor reads privileged data through an expression/host-function path" — promise results (`runtime/near-vm-runner/src/wasmtime_runner/logic.rs` `promise_result`), receipt/data-receiver routing (`runtime/runtime/src/receipt_manager.rs`, `runtime/runtime/src/lib.rs` output-data-receiver handling), and meta-transaction/access-key allowance accounting (`docs/architecture/how/meta-tx.md`, `integration-tests/src/tests/features/delegate_action.rs`) — and found no mechanism where a value intended to stay confidential to a privileged party is exposed to a lower-privileged party and can then be moved into a separate exfiltration channel with concrete unauthorized value movement, supply inflation, fee/gas bypass, state-root divergence, invalid state-transition acceptance, receipt loss/duplication, frozen funds, or a halt. Since nearcore has no analogous "shared secret exposed via expression evaluation" primitive and the required impact categories (unauthorized value movement, supply inflation, fee/gas bypass, state divergence, receipt loss/duplication, frozen funds, or halt) don't map onto a pure confidentiality leak (CWE-200) in a fully public ledger, there is no valid analog.

pub fn promise_result(
    ctx: &mut Ctx,
    _memory: &mut [u8],

    register_id: u64,

    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(
            HostError::ProhibitedInView { method_name: "promise_result".to_string() }.into()
        );
    }
    match ctx
        .context
        .promise_results
        .get(result_idx as usize)
        .ok_or(HostError::InvalidPromiseResultIndex { result_idx })?
    {
        PromiseResult::NotReady => Ok(0),
        PromiseResult::Successful(data) => {
            ctx.registers.set_rc_data(
                &mut ctx.result_state.gas_counter,
                &ctx.config.limit_config,
                register_id,
                Rc::clone(data),
            )?;
            Ok(1)
        }
        PromiseResult::Failed => Ok(2),
    }
