### Title
Unbounded gzip decompression of user-supplied declare-v1 `program` in RPC `decompress_program` allows decompression-bomb DoS - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
The Starknet gateway path (`apollo_http_server`, `apollo_gateway`) enforces decompressed-size limits on gzip-compressed payloads via `starknet_api::compression_utils::decompress_with_size_limit`, which bounds the reader with `.take(max_size + 1)` before reading to completion. [1](#0-0)  However, the JSON-RPC execution path's `decompress_program` function, used to decode the base64+gzip-compressed Cairo `program` field of a `BroadcastedDeclareV1Transaction` supplied to `starknet_simulateTransactions`/`starknet_estimateFee`/`starknet_traceTransaction`-style flows, performs unbounded decompression with `decoder.read_to_end(&mut decompressed)` and carries an explicit `// TODO(dan): add time and size limits.` marker acknowledging the gap. [2](#0-1) 

### Finding Description
`decompress_program` base64-decodes and gzip-decompresses attacker-controlled data with no cap on the output size:
```
pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    ...
    let mut decoder = GzDecoder::new(compressed_data.as_slice());
    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    ...
}
``` [2](#0-1) 

This is functionally identical to the reported cpp-httplib bug class: a request-body size limit is enforced at the transport/wire layer (via jsonrpsee's body-size middleware, analogous to `RequestBodyLimitLayer`), but the *decompressed* payload derived from that small, size-limited wire body is allowed to expand without bound before any check is applied, defeating the purpose of the outer limit. This mirrors the exact contrast visible elsewhere in the codebase: the gateway's own `decode_and_decompress_with_size_limit` explicitly caps decompression output [3](#0-2) , and the HTTP server layer additionally wraps decompression with a hard streaming limit specifically to prevent "zip bombs from expanding in memory" [4](#0-3) , but the RPC execution/simulation code path for declare-v1 class programs has no equivalent protection.

An attacker can submit a `starknet_simulateTransactions` (or `starknet_estimateFee`) JSON-RPC call containing a `BroadcastedDeclareV1Transaction` whose `contract_class.program` field is a small base64-encoded gzip blob (e.g., a few KB) that decompresses to gigabytes of data, causing large memory allocation and CPU consumption on the RPC-serving node.

### Impact Explanation
This is reachable by any unprivileged RPC caller submitting a simulate/trace/estimate-fee request with a crafted declare-v1 program, without needing to pay gas or have the transaction accepted into the mempool (simulation happens before/independent of mempool admission). A successful exploit causes memory/CPU exhaustion on the node serving JSON-RPC requests, a denial-of-service condition consistent with the "no size/time limits" TODO explicitly left in the code.

### Likelihood Explanation
High likelihood: the vulnerable function is directly reachable via a standard, unauthenticated public JSON-RPC endpoint, requires no prior state (no funded account, no accepted transaction), and the code path has zero size enforcement — unlike every other decompression path in the repository (gateway's `decode_and_decompress_with_size_limit`, HTTP server's `RequestBodyLimitLayer` wrapping `RequestDecompressionLayer`) which were hardened against exactly this bug class.

### Recommendation
Apply the same bounded-decompression pattern used elsewhere in the codebase: wrap the `GzDecoder` reader with a `.take(max_size + 1)` limit (as done in `decompress_with_size_limit`) and reject the request if the decompressed size exceeds a configured maximum (e.g., reuse `max_contract_bytecode_size`/`max_contract_class_object_size` config values), returning an RPC error instead of proceeding with unbounded allocation. Ideally, replace the ad hoc `decompress_program` implementation with a call into `starknet_api::compression_utils::decode_and_decompress_with_size_limit`.

### Proof of Concept
1. Craft a small program payload of repeated bytes (e.g., 10 MB of `'a'`), gzip-compress it (compresses to a few hundred bytes), and base64-encode it.
2. Submit a JSON-RPC `starknet_simulateTransactions` (or equivalent trace/estimate) request with a `BroadcastedDeclareV1Transaction` whose `contract_class.program` field is set to this compressed string.
3. Observe that `decompress_program` fully decompresses the payload via `read_to_end` with no size check, consuming memory proportional to the decompression ratio (analogous to the existing unit test `get_decompressed_program` which calls `decompress_program` directly on a compressed fixture, confirming the code path and lack of any limit). [5](#0-4) 
4. Repeating the request concurrently amplifies memory/CPU pressure on the RPC node, causing degraded service or crash.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
```
