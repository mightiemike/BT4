Findings on why: `VoteStateView` binds `data: Arc<Vec<u8>>` and `frame: VoteStateFrame` together at construction time in `VoteStateView::try_new`, and the frame is always computed fresh from whatever `bytes` are passed in at that call [1](#0-0) . There is no mechanism that reuses a previously-computed `VoteStateFrameV1_14_11` against a different, later `Arc<Vec<u8>>` buffer — offsets are stored inside the same struct as the data they were derived from, and accessors like `node_pubkey()` index into `self.data`, the exact buffer the frame was parsed from [2](#0-1) .

Every entry point that produces a `VoteStateView`/`VoteAccount` for a vote account rebuilds it from scratch on the current account bytes rather than reusing a cached frame across writes: `VoteAccount::try_from` always calls `VoteStateView::try_new(account.data_clone())` on the `AccountSharedData` being converted [3](#0-2) , and `StakesCache::check_and_store`, which runs on every account write observed by the cache, calls `VoteAccount::try_from(create_account_shared_data(account))` again on the newest data before upserting into the map [4](#0-3) . A resize/realloc that shrinks the account's data produces a new `AccountSharedData`/`Arc<Vec<u8>>`, which goes through this same `try_from` path and gets an entirely new `VoteStateFrameV1_14_11` computed via `VoteStateFrameV1_14_11::try_new` against the new (shorter) buffer [5](#0-4) , which also validates that the cursor position after reading nested list frames does not exceed `bytes.len()`, rejecting undersized buffers as `AccountDataTooSmall` [6](#0-5) .

No cross-write frame cache (e.g., keyed only by pubkey and reused independent of data length/content) exists in `VoteAccount`, `VoteAccounts`, or `StakesCache`; the only cache in `VoteAccounts` is `staked_nodes: OnceLock<...>`, which is unrelated to per-account frame offsets and is explicitly reset (`OnceLock::new()`) whenever the map is cloned or mutated [7](#0-6) . Therefore the premised attack — a stale `VoteStateFrameV1_14_11` computed from a larger buffer being reused against a shrunk buffer for the same pubkey — has no code path in this repository to occur; the frame is always recomputed on the byte slice it is immediately parsed from.

impl VoteStateFrameV1_14_11 {
    pub(super) fn try_new(bytes: &[u8]) -> Result<Self> {
        let votes_offset = Self::votes_offset();
        let mut cursor = std::io::Cursor::new(bytes);
        cursor.set_position(votes_offset as u64);

        let votes_frame = LockoutListFrame::read(&mut cursor)?;
        let root_slot_frame = RootSlotFrame::read(&mut cursor)?;
        let authorized_voters_frame = AuthorizedVotersListFrame::read(&mut cursor)?;
        PriorVotersFrame::read(&mut cursor);
        let epoch_credits_frame = EpochCreditsListFrame::read(&mut cursor)?;
        cursor.consume(core::mem::size_of::<BlockTimestamp>());
        // trailing bytes are allowed. consistent with default behavior of
        // function bincode::deserialize
        if cursor.position() as usize <= bytes.len() {
            Ok(Self {
                votes_frame,
                root_slot_frame,
                authorized_voters_frame,
                epoch_credits_frame,
            })
        } else {
            Err(VoteStateViewError::AccountDataTooSmall)
        }
    }
