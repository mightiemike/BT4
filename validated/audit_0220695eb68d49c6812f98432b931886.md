### Title
ECDSA signature malleability in `check_recover_pubkey` allows forging a spurious "second" microblock header that falsely implicates an innocent miner in `handle_poison_microblock` - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`StacksMicroblockHeader::check_recover_pubkey` recovers a public key from a recoverable ECDSA signature without enforcing low-S canonicalization, using `recover_to_pubkey_without_validating_low_s`. Given any single, honestly-broadcast microblock header signed by a real miner, an unprivileged attacker can compute the malleated (`s -> n-s`, flipped recovery bit) variant of that same signature — a pure public computation requiring no private key — and submit it alongside the original as a `PoisonMicroblock` transaction. Both "headers" have identical content (same `sequence`, `prev_block`, `version`, `tx_merkle_root`) and both recover to the same `pkh`, so `check_microblock_header_signer` and the mempool admission checks accept the pair as a valid double-signing proof, even though the miner never signed two conflicting microblocks.

### Finding Description
The claimed equality is: **"pkh1 == pkh2 via `check_recover_pubkey`" implies "the miner genuinely produced two distinct, conflicting microblock signatures."** This equality does not hold.

- `check_recover_pubkey` recovers the signer key using `recover_to_pubkey_without_validating_low_s`, deliberately skipping low-S/canonical-signature enforcement: [1](#0-0) 
- The underlying recovery routine explicitly supports skipping the low-S check via a boolean flag: [2](#0-1) 
- The codebase itself documents and exercises the malleated-signature construction (`with_negated_s`), which negates `s` mod n and flips the recovery-id parity bit — producing a **different byte-level signature that is still a valid recoverable ECDSA signature for the exact same message digest and recovers to the exact same public key**: [3](#0-2) 

Given a genuine microblock header `H` (fields: `version`, `sequence`, `prev_block`, `tx_merkle_root`, `signature=sig`) honestly signed and broadcast by a real miner with private key `d`, an attacker (holding no private key) can construct `H' = H` with `signature = malleate(sig)`. `H` and `H'` have:
- identical `sequence`, `prev_block`, `version`, `tx_merkle_root` (i.e., they are the *same logical microblock*, not a fork),
- different raw `signature` bytes (so `H != H'` as structs and `block_hash(H) != block_hash(H')`),
- identical recovered `pkh` via `check_recover_pubkey`.

The attacker submits `PoisonMicroblock(H, H')`. The dispatch/admission path only checks `sequence`, `prev_block`, `version` equality and pkh equality — it never checks that the headers actually differ in content (e.g., `tx_merkle_root`), which is the only field that would indicate genuine equivocation: [4](#0-3) 

`check_microblock_header_signer` performs the same insufficient check — it only compares recovered pkh1 vs pkh2, with no verification that the headers' non-signature content actually diverges: [5](#0-4) 

`handle_poison_microblock` then trusts this result unconditionally: it looks up `pkh` via `get_microblock_pubkey_hash_height` (populated for the real miner by `insert_microblock_pubkey_hash`), verifies the maturity window, and calls `insert_microblock_poison` recording a slashing report against that miner's block height — entitling the attacker/reporter to a commission of the punished miner's coinbase: [6](#0-5) 

None of `check_tenure_tx`, `verify_signer_signatures`, or MARF/reward-schedule logic intervene here, because the vulnerability is entirely inside the poison-microblock signature-equivalence check itself, which is the sole gate for whether a "fork" is genuine.

### Impact Explanation
This causes **block-reward theft/loss to an innocent miner**: a real miner who only ever produced one honest microblock stream can be falsely flagged as having equivocated, and their coinbase reward diverted (in part or fully, per the poison-microblock reward-commission mechanism) to an attacker who never held any signing key and never observed a genuine fork. This is repeatable against any miner whose real signed microblock the attacker can observe on the wire, and requires no stake, no majority position, and no privileged role — only the ability to see one broadcast microblock and submit a transaction, both of which are available to an ordinary unprivileged participant. This matches the "Critical - block-reward theft/double-payment/loss" category.

### Likelihood Explanation
Preconditions are minimal and cheap: the attacker needs (1) visibility into a single genuinely-signed microblock header from a target miner (trivially available since microblocks are broadcast/relayed), (2) the miner's pubkey hash to already be registered via `insert_microblock_pubkey_hash` (true for any active miner producing microblocks), and (3) the report to be submitted within the `MINER_REWARD_MATURITY` window, which is a normal window during which such transactions are naturally processed. No BTC spend, no stake, and no compromise of any key is required — the malleation is a pure, deterministic scalar/point arithmetic operation on public data. This is fully repeatable against every miner that produces microblocks.

### Recommendation
Enforce canonical (low-S) signature validation in `StacksMicroblockHeader::check_recover_pubkey` (i.e., use the low-S-validating recovery path instead of `recover_to_pubkey_without_validating_low_s`) so that only one canonical signature encoding is ever considered valid for a given message/key pair, eliminating the malleated variant as an independently-valid "second" signature. Additionally, harden the `PoisonMicroblock` validation path (`check_microblock_header_signer` / the mempool admission check in `blocks.rs`) to require that the two headers differ in content beyond the signature — e.g., require `tx_merkle_root` (or the full pre-signature payload) to differ — so a poison report can never be based on two encodings of the same underlying microblock.

### Proof of Concept
Rust integration test plan (in `stackslib/src/chainstate/stacks/db/transactions.rs` test module, alongside existing `process_poison_microblock_*` tests):
1. Generate `block_privk`/`block_pubkh`, register `insert_microblock_pubkey_hash(&mut conn, height, &block_pubkh)`.
2. Construct one genuine `StacksMicroblockHeader` `h1` with `sequence = N`, `prev_block = P`, `tx_merkle_root = M`, signed with `block_privk` via `.sign(&block_privk)`.
3. Construct `h2 = h1.clone()` and replace `h2.signature` with `h1.signature.with_negated_s()` (no access to `block_privk` used for this step).
4. Assert (equality check before exploit): `h1.check_recover_pubkey().unwrap() == block_pubkh` and `h2.check_recover_pubkey().unwrap() == block_pubkh` — i.e., both recover to the miner's real key despite `h2`'s signature never being produced by a genuine signing operation over distinct content.
5. Assert `h1.tx_merkle_root == h2.tx_merkle_root` and `h1.sequence == h2.sequence` and `h1.prev_block == h2.prev_block` (proving these are the *same* microblock content, not a real fork), while `h1.signature != h2.signature`.
6. Build `TransactionPayload::PoisonMicroblock(h1.clone(), h2.clone())`, sign with an unrelated `reporter_privk` (simulating the unprivileged attacker), and call `StacksChainState::process_transaction`.
7. Assert the call succeeds (no `InvalidStacksTransaction`/`PoisonMicroblocksDoNotConflict` error) and that `get_poison_microblock_report(&mut conn, height)` returns `Some((reporter_addr, N))` — proving `insert_microblock_poison` was invoked and the innocent miner at `height` was slashed/reported, despite never having double-signed anything.

        let mut bytes = vec![];
        self.serialize(&mut bytes, true)

            )
        })?;

        pubk.set_compressed(true);
        Ok(Hash160::from_node_public_key(&pubk))
    }

    pub fn with_negated_s(&self) -> Self {
        let mut bytes = [0u8; 65];
        bytes.copy_from_slice(self.as_bytes());

        // A `PrivateKey` is just a number, and it conveniently has a .negate()
