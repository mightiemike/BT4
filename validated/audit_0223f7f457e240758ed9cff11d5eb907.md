The premise doesn't hold: both `CharResponseWrapper` and `BufferedResponseWrapper` are instantiated as fresh, request-scoped local objects inside `doFilter`, not shared or pooled across requests/threads.

- `HttpApiAccessFilter.doFilter` creates `new CharResponseWrapper(resp)` per invocation and passes it down the chain; it is a local variable with no static or shared state. [1](#0-0) 
- `HttpInterceptor.doFilter` likewise creates a new `CharResponseWrapper` per request. [2](#0-1) 
- `CharResponseWrapper` itself has no static fields; its `outputStream`/`writer`/`streamCopy` are instance fields lazily initialized once per wrapper instance (i.e., per request), and `ServletOutputStreamCopy` is likewise a fresh object tied to that wrapper. [3](#0-2) 
- `BufferedResponseWrapper` similarly holds a private, non-static `ByteArrayOutputStream buffer` created in the constructor for each request, with no pooling/reuse mechanism. [4](#0-3) 

The servlet itself, `GetAssetIssueListByNameServlet`, is a Spring singleton bean (shared across threads as normal for servlets), but `doGet`/`doPost`/`fillResponse` use only local variables (`value`, `reply`) and write directly to the `response` parameter passed in for that specific request — there is no instance-level mutable state that could leak between concurrent requests. [5](#0-4) 

Since each HTTP request gets its own wrapper object instance (allocated fresh on the calling thread within `doFilter`), thread-pool reuse only means a different wrapper instance runs on a recycled thread — it does not cause byte buffers to be shared between concurrently-handled requests. There is no code path (no static/ThreadLocal cache, no object pool) that would make one request's buffered bytes bleed into another's response. The question's premise of a "wrapper reuse bug" is not supported by the actual implementation.
