# Division by Zero in `update_stake_pool` Transaction-Fee Distribution Can Abort Epoch Reconfiguration — ([File: aptos-move/framework/aptos-framework/sources/stake.move])

### Summary
`update_stake_pool` in the `stake` module distributes pending transaction fees to a validator's active/pending-inactive stake by computing `fee_octa * stake_pending_inactive / (stake_active + stake_pending_inactive)`. If a validator's stake pool has both `active` and `pending_inactive` balances equal to zero while a nonzero fee is still queued for that validator index in `PendingTransactionFee`, this division aborts with a Move arithmetic error, even though the function's own doc comment states "This function shouldn't abort." Because `update_stake_pool` is invoked for every current-epoch validator during `on_new_epoch` reconfiguration, a single validator triggering this state can cause the reconfiguration transaction to fail deterministically for all validators, i.e., a permanent, un-recoverable chain halt.

### Finding Description [1](#0-0) 

The function explicitly documents the invariant it is supposed to uphold:

> "This function shouldn't abort." — [2](#0-1) 

Yet the fee distribution block does:

```
let stake_active = (coin::value(&stake_pool.active) as u128);
let stake_pending_inactive = (coin::value(&stake_pool.pending_inactive) as u128);
fee_pending_inactive =
    (((fee_octa as u128) * stake_pending_inactive
        / (stake_active + stake_pending_inactive)) as u64);
``` [3](#0-2) 

This division is only guarded by `pending_fee_by_validator.contains(&validator_index)` — it does **not** check that `stake_active + stake_pending_inactive > 0`. In Move, integer division by zero triggers a runtime arithmetic abort.

A validator remains part of the *current* epoch's `active_validators` set (and therefore keeps participating in consensus and proposing blocks, since consensus voting power for the epoch is fixed at the last reconfiguration) even after voluntarily draining their stake pool to zero mid-epoch via `unlock`/`withdraw` (their `get_voting_power` check and removal from the *next* validator set only happens at the *next* reconfiguration in `next_validator_consensus_infos_v2`, not immediately). If such a validator proposes a block while their `active` and `pending_inactive` balances are both already zero, and a transaction fee gets recorded for their `validator_index` in `PendingTransactionFee` (populated during block execution/fee distribution, independent from this check), then at the next `on_new_epoch` reconfiguration, `update_stake_pool` for that validator computes `0/0`, aborting the whole reconfiguration transaction.

### Impact Explanation
`on_new_epoch` is part of the mandatory system/reconfiguration transaction executed at every epoch boundary. If it aborts deterministically due to this division, the epoch-ending block cannot be committed successfully — the same abort recurs identically on every validator's execution and on every retry, since it's a pure function of on-chain state, resulting in a chain halt with no automatic recovery path (analogous to the reported "funds locked / DoS with no recovery" pattern, but here manifesting as a liveness-breaking commit failure at the state-transition layer rather than a caller-facing revert). This is a high/critical state-integrity impact: mainnet reconfiguration would stop, and unlike the original report's isolated vault, this affects the entire chain's ability to commit new epochs.

### Likelihood Explanation
The precondition (an active validator with `active == 0` and `pending_inactive == 0`, plus a pending fee credited to that validator's index) requires: (a) the validator owner permissionlessly unlocking and withdrawing all stake mid-epoch — an ordinary, unprivileged staking operation — and (b) that same validator having proposed at least one block in the current epoch after fully draining its stake, so a fee entry is created for its `validator_index`. Whether normal fee-distribution logic can attribute a fee to a validator after they have zero-out their stake needs runtime confirmation against the exact call site that inserts into `pending_fee_by_validator` (not fully traced here due to search-depth limits), but nothing in `update_stake_pool` itself prevents this ordering, and no other part of the reviewed code path checks for `stake_active + stake_pending_inactive == 0` before the division.

### Recommendation
Add an explicit zero-denominator guard before the division in `update_stake_pool`, e.g.:
```
if (stake_active + stake_pending_inactive == 0) {
    fee_pending_inactive = 0;
} else {
    fee_pending_inactive = (((fee_octa as u128) * stake_pending_inactive
        / (stake_active + stake_pending_inactive)) as u64);
};
```
and route any residual `fee_octa` that cannot be attributed (validator has drained its pool) to a safe fallback (e.g., burn, treasury, or re-queue) rather than silently dropping it, restoring the documented "this function shouldn't abort" invariant.

### Proof of Concept
Conceptual reproduction (concrete Move test not fully constructed due to tool/time limits):
1. Validator `V` joins with minimum stake and becomes active.
2. `V` proposes at least one block in epoch `N`; a fee gets queued via the fee-distribution path into `PendingTransactionFee.pending_fee_by_validator[V.validator_index]`.
3. `V`'s owner calls `unlock` for the full active balance, then (assuming lockup already expired or via repeated epoch waiting in a controlled/test setup) withdraws all `pending_inactive`/`inactive` funds, bringing `stake_pool.active == 0` and `stake_pool.pending_inactive == 0`, while `V` remains in `active_validators` until the next reconfiguration.
4. At the next `on_new_epoch` call, `update_stake_pool(V)` executes `fee_octa * 0 / (0 + 0)`, aborting with a Move arithmetic error.
5. Because this occurs inside the reconfiguration system logic, the epoch-changing transaction fails identically for every validator replaying the block, halting progress.

Given the scope constraints of this review (no execution harness available), this should be validated with a concrete Move unit/integration test exercising `unlock` → `withdraw` → fee accrual → `on_new_epoch` before treating it as confirmed exploitable in production ordering.

    /// Calculate the stake amount of a stake pool for the next epoch.
    /// Update individual validator's stake pool if `commit == true`.
    ///
    /// 1. distribute transaction fees to active/pending_inactive delegations
    /// 2. distribute rewards to active/pending_inactive delegations
    /// 3. process pending_active, pending_inactive correspondingly
    /// This function shouldn't abort.
    fun update_stake_pool(
        validator_perf: &ValidatorPerformance,
        pool_address: address,
        staking_config: &StakingConfig
    ) acquires AptosCoinCapabilities, PendingTransactionFee, StakePool, TransactionFeeConfig, ValidatorConfig {
        let stake_pool = borrow_global_mut<StakePool>(pool_address);
        let validator_config = borrow_global<ValidatorConfig>(pool_address);
        let validator_index = validator_config.validator_index;
        let cur_validator_perf = validator_perf.validators.borrow(validator_index);
        let num_successful_proposals = cur_validator_perf.successful_proposals;

        let fee_pending_inactive = 0;
        let fee_active = 0;
        let fee_limit =
            if (exists<TransactionFeeConfig>(@aptos_framework)) {
                let TransactionFeeConfig::V0 { max_fee_octa_allowed_per_epoch_per_pool } =
                    borrow_global<TransactionFeeConfig>(@aptos_framework);
                *max_fee_octa_allowed_per_epoch_per_pool
            } else {
                MAX_U64 as u64
            };

        if (exists<PendingTransactionFee>(@aptos_framework)) {
            let pending_fee_by_validator =
                &mut borrow_global_mut<PendingTransactionFee>(@aptos_framework).pending_fee_by_validator;
            if (pending_fee_by_validator.contains(&validator_index)) {
                let fee_octa = pending_fee_by_validator.remove(&validator_index).read();
                if (fee_octa > fee_limit) {
                    fee_octa = fee_limit;
                };
                let stake_active = (coin::value(&stake_pool.active) as u128);
                let stake_pending_inactive =
                    (coin::value(&stake_pool.pending_inactive) as u128);
                fee_pending_inactive =
                    (
                        ((fee_octa as u128) * stake_pending_inactive
                            / (stake_active + stake_pending_inactive)) as u64
                    );
                fee_active = fee_octa - fee_pending_inactive;
            }
        };
