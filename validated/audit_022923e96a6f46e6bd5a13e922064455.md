### Title
Missing slippage protection in `ExchangeWithdrawActuator` allows front-running of exchange liquidity withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's built-in Bancor-style exchange market exposes an `ExchangeWithdrawContract` that lets the pool creator burn part of their `first_token`/`second_token` liquidity for a proportional amount of the other side. Unlike `ExchangeTransactionContract` (the swap operation), which carries an `expected` field enforced as a minimum-received check, `ExchangeWithdrawContract` has no equivalent minimum-amount parameter, so the amount of the counter-token returned is entirely determined by the pool ratio at the moment the transaction executes on-chain.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` [1](#0-0) . In `ExchangeWithdrawActuator.doValidate()`/`execute()`, `anotherTokenQuant` is computed purely from the current `firstTokenBalance`/`secondTokenBalance` ratio in the `ExchangeCapsule` read at execution time [2](#0-1) , and validation only checks that `anotherTokenQuant > 0` and within “precise enough” bounds — there is no caller-supplied minimum threshold that must be met [3](#0-2) .

This is the exact bug class described in the report: the Uniswap V3 `claim`/`decreaseLiquidity` equivalent (`pool.burn`) returns amounts based on pool state at execution time, and without a slippage floor a transaction that gets sandwiched (front-run by a pool-ratio-shifting trade, followed by the withdraw, followed by a reversing trade) can return far less of one token than the withdrawer expects.

In java-tron, the ratio-shifting counterpart operation is `ExchangeTransactionContract`, processed by `ExchangeTransactionActuator`, which is a fully public/anonymous-reachable broadcast transaction that changes `firstTokenBalance`/`secondTokenBalance` via `exchangeCapsule.transaction(...)` [4](#0-3) . Notably, this actuator itself implements the exact defense the report recommends: it takes a caller-supplied `tokenExpected` and validates `token required must greater than expected` [5](#0-4) . The absence of an analogous field/check in `ExchangeWithdrawContract`/`ExchangeWithdrawActuator` is the gap.

### Impact Explanation
Any address holding assets can submit `ExchangeTransactionContract` transactions against a given `exchange_id` to shift the `firstTokenBalance:secondTokenBalance` ratio immediately before a pending `ExchangeWithdrawContract` transaction from the pool creator is included in a block, and can reverse the trade immediately after. Because `anotherTokenQuant` in the withdraw is computed strictly from the ratio at execution time with no floor, the pool creator's withdrawal can yield a materially smaller amount of the counter-token than intended, realizing an impermanent-loss-like value transfer to the manipulator. This matches the medium-severity judged rating in the referenced report — asset/accounting corruption for the withdrawing party without any privileged access required.

### Likelihood Explanation
Both `ExchangeTransactionContract` and `ExchangeWithdrawContract` are ordinary broadcastable transactions reachable by any account; a withdraw transaction sitting in the mempool (or predictable due to being periodic/scheduled) is straightforward to target with a sandwich of swap transactions in adjacent blocks, especially for pools with realistic liquidity depth for the manipulator's capital. The `ExchangeTransactionActuator`'s own existing `expected`/slippage check demonstrates the codebase already recognizes and defends against this exact class of manipulation for swaps, but the equivalent protection was omitted for withdrawals.

### Recommendation
Add a minimum-amount field (e.g., `expected_another_token_quant`) to `ExchangeWithdrawContract`, and in `ExchangeWithdrawActuator.doValidate()`/`execute()` require `anotherTokenQuant >= expected` before mutating the `ExchangeCapsule` and account balances, mirroring the check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Pool creator constructs `ExchangeWithdrawContract(exchange_id, token_id=firstTokenID, quant=Q)` expecting to receive `anotherTokenQuant ≈ secondTokenBalance*Q/firstTokenBalance` based on current pool state, and broadcasts it.
2. An attacker observes the pending transaction and, in the block immediately preceding it, broadcasts `ExchangeTransactionContract` swaps against the same `exchange_id` that shift `firstTokenBalance`/`secondTokenBalance` sharply (still bounded by `getExchangeBalanceLimit()` [6](#0-5) ).
3. The withdraw executes against the manipulated ratio in `ExchangeWithdrawActuator.execute()` [7](#0-6) , giving the creator a much smaller `anotherTokenQuant` than intended, with no validation rejecting the transaction since only positivity/precision is checked [8](#0-7) .
4. The attacker reverses their swap in a subsequent block, restoring the ratio and capturing the value difference.
