## Analysis

The report describes a pattern where a contract optimistically marks an operation as "done" (`executed? = true`) right after dispatching a value-carrying, bounceable outbound message, without any mechanism to correct that state if the message is rejected by the receiver. The `near-wallet-contract` implementation in this repo contains a structurally identical pattern in its `has_in_flight_tx` guard. [1](#0-0) 

### Title
Wallet Contract `has_in_flight_tx` guard can be permanently stuck `true` when the relayer-ban batch receipt fails, freezing the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` uses `has_in_flight_tx` as a single-transaction-in-flight lock, set to `true` before a promise is dispatched and reset to `false` only inside dedicated private callback methods (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`). For the relayer-ban path, the "clear the flag" logic (`ban_relayer`) is not a separate callback receipt — it is bundled as the *second action* in the very same batched receipt as `delete_key`, with no `.then()` continuation and no failure handling. If that batched receipt fails (e.g. because the `delete_key` action fails), `ban_relayer` never executes, `has_in_flight_tx` is never reset, and the wallet becomes permanently locked. This mirrors the audit finding: state is optimistically marked "in-flight"/"done" based on message dispatch rather than confirmed successful execution, and the "bounce" (receipt failure) case is never handled.

### Finding Description
In `rlp_execute`, when a relayer's transaction is malformed (`Err(Error::Relayer(_))`), the contract builds a single promise via `create_ban_relayer_promise` combining `delete_key(pk)` and `function_call_weight("ban_relayer", ...)` on the same account, in the same batched action receipt, and immediately sets `has_in_flight_tx = true`: [2](#0-1) [3](#0-2) 

Unlike every other promise-dispatch path in this contract, this one has no `.then()` callback to reset `has_in_flight_tx` on failure — `ban_relayer` (which resets the flag) is only reached if `delete_key` succeeds as part of the *same* action receipt, since NEAR executes all actions in a batched receipt atomically: if any action fails, the whole receipt fails and subsequent actions in that receipt are never applied. [4](#0-3) 

Contrast this with `rlp_execute_callback`, which correctly branches on `PromiseResult::Failed` vs `Successful` and always resets the flag regardless of outcome: [5](#0-4) 

If the target `delete_key(pk)` action fails — for example, because that access key public key was already removed from the account (e.g. by an earlier, independently-processed `DeleteKey` action the owner legitimately submitted through `action_to_promise`, which also allows `near_action::Action::DeleteKey` against the wallet's own account) — the entire ban receipt fails, `ban_relayer` never runs, and `has_in_flight_tx` remains `true` forever. There is no other code path in the contract that can clear it afterward.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, every subsequent call to `rlp_execute` (the sole entry point for the account owner/relayer to perform actions through this wallet) is rejected up front: [6](#0-5) 

This permanently freezes the wallet account: the owner can no longer move funds, call contracts, or manage access keys through it, since there is no external mechanism to reset the flag. This satisfies "permanently frozen funds" from the accepted impact categories.

### Likelihood Explanation
Triggering this requires a specific but realistic ordering: an in-flight, previously-signed relayer transaction that will fail parsing/validation and route through `create_ban_relayer_promise`, combined with a separate, earlier-executing receipt that removes the same access key from the account before the ban receipt executes (e.g. the owner proactively rotating/removing a relayer's access key while an old relayer transaction is still pending in the network/mempool). Since relayer access keys are explicitly designed to be revocable via normal `DeleteKey` actions routed through this same contract, and the "ban on bad relayer data" path is a documented, reachable behavior for any relayer sending malformed input, this ordering is plausible without requiring any privileged or out-of-protocol actor — a single account owner performing routine key hygiene alongside normal relayer traffic can trigger it.

### Recommendation
Do not combine `delete_key` and the state-resetting `ban_relayer` call into a single atomic batched receipt. Instead, dispatch `delete_key` as its own promise and chain a `.then()` callback (mirroring `rlp_execute_callback`) that resets `has_in_flight_tx` regardless of whether the `delete_key` action succeeded or failed. More generally, ensure every code path that sets `has_in_flight_tx = true` has a guaranteed corresponding callback that resets it on both success and failure, rather than relying on an action embedded inside the same receipt whose success is not guaranteed.

### Proof of Concept
1. Grant a relayer a `FunctionCallPermission` access key (public key `pk_R`) on the wallet account, restricted to `rlp_execute`.
2. Relayer submits `rlp_execute` with a malformed/garbage `tx_bytes_b64` (transaction T2, using `pk_R`); this transaction is converted to a receipt and queued (e.g. delayed by congestion, or simply pending processing).
3. Before T2's receipt is applied, the wallet owner submits a valid `rlp_execute` transaction T1 (using a still-valid access key) whose decoded action is `near_action::Action::DeleteKey` targeting the wallet's own account with `public_key = pk_R`; T1 executes fully and successfully removes `pk_R`, and `has_in_flight_tx` correctly returns to `false` afterward via `rlp_execute_callback`.
4. T2's receipt is now applied: `inner_rlp_execute` fails to parse the garbage data → `Error::Relayer(_)` → `create_ban_relayer_promise(current_account_id)` is dispatched and `has_in_flight_tx` is set to `true`.
5. The dispatched batched receipt attempts `delete_key(pk_R)`, which now fails because `pk_R` no longer exists on the account → the whole receipt fails → `ban_relayer` is never invoked.
6. `has_in_flight_tx` remains `true` permanently; every future call to `rlp_execute` on this wallet account returns `"Error: transaction already in progress, please try again later."` indefinitely, freezing the account.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

fn create_ban_relayer_promise(current_account_id: AccountId) -> Promise {
