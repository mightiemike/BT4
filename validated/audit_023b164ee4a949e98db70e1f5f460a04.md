## Analysis Result

Confirmed root cause: `grep_search` for `state_change_hash` across `storage/**` returns **no hits** in the backup/restore code path (`storage/backup/backup-cli/**`, `storage/aptosdb/src/backup/**`). The only occurrences anywhere in storage are in test files. This confirms that nowhere in the transaction-backup restore pipeline is a loaded `WriteSet` ever hashed and compared against `TransactionInfo::state_change_hash()`.

### Title
Unauthenticated write-sets accepted during transaction-backup restore - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
`LoadedChunk::load` reads `(Transaction, PersistedAuxiliaryInfo, TransactionInfo, Events, WriteSet)` tuples from a backup chunk file and verifies them by constructing a `TransactionListWithProofV2` (txns + events + txn_infos) and calling `.verify(...)`. The `WriteSet` is never included in that verification object, and no code path re-derives `CryptoHash::hash(&write_set)` and compares it to `txn_info.state_change_hash()` before the write set is persisted via `restore_utils::save_transactions`.

### Finding Description [1](#0-0) 
`LoadedChunk::load` deserializes `write_sets` directly from the raw record bytes read off backup storage, separately from the fields that get wrapped into `TransactionListWithProofV2`. Only `txns`, `event_vecs`, and `txn_infos` are placed into the verifiable structure; `write_sets` is carried alongside, untouched by `.verify()`.

The verification method that *is* called, `TransactionListWithProof::verify` (via `TransactionListWithProofV2`), checks transaction hash vs. `txn_info.transaction_hash()` and event root hash vs. `txn_info.event_root_hash()` (and finally checks the accumulator proof against the ledger info): [2](#0-1) 
There is no analogous check for `state_change_hash` here, unlike `TransactionOutputListWithProof::verify`, which is used elsewhere (e.g., state-sync output-list verification) and *does* check `txn_info.state_change_hash() == CryptoHash::hash(&write_set)`: [3](#0-2) 

The unverified `write_sets` then flow straight into the DB commit path: [4](#0-3) 
and ultimately into `restore_utils::save_transactions` / `save_transactions_impl`, which writes them to `WriteSetDb` and (in `kv_replay` mode) feeds them into `state_store.calculate_state_and_put_updates` to derive the new JMT state root — again with no hash check against `txn_info.state_change_hash()`: [5](#0-4) 

Although `TransactionInfo::hash()` (which is authenticated by the accumulator proof against a trusted `LedgerInfoWithSignatures`/waypoint) cryptographically commits to the correct `state_change_hash`, the restore code never uses that committed value to authenticate the write set it is about to persist. A tampered or corrupted backup archive (the write-set bytes are stored in a plain, non-Merkle-proved record stream, separate from the proof file) can therefore substitute arbitrary write sets for the correct ones while keeping the (correctly signed) `TransactionInfo`/proof/`Transaction` intact, and `LoadedChunk::load`'s verification will still pass.

### Impact Explanation
This is a state-commitment integrity break in the restore path (in scope per the "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" pivot). When `replay_from_version` is not requested for a version range (the common "save without replay" fast path used by full-node/backup restore and by `verify`'s restore-to-mock-store path), the target database ends up storing write sets that do not correspond to the VM execution that produced the authenticated `TransactionInfo`. In `kv_replay` mode this corrupted write set is also used to compute new state values and (via `calculate_state_and_put_updates`) a derived state root, silently diverging the restored node's ledger state from the canonical chain state while the node still believes it restored a verified, waypoint-anchored history. This can produce durable, silently-corrupted ledger data and diverging state across restored nodes — a hard-fork-class/critical impact if such a restored node is later used to serve state, sync peers, or participate in consensus/state-sync.

### Likelihood Explanation
Exploitation requires control over (or corruption of) the backup storage bytes (e.g., a compromised/malicious backup S3 bucket, MITM on backup download, or corrupted archive) — not a privileged on-chain actor, and not "malicious peer/node" behavior in the excluded network-DoS sense; it is a data-integrity gap in how the *local* restore code validates input before committing it to durable storage. Because backup files are widely distributed and often fetched from third-party or self-hosted storage without additional out-of-band write-set attestation, this is a realistic supply-chain-style vector, though it does require an attacker with write access to the backup artifact.

### Recommendation
In `LoadedChunk::load` (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`), before returning `write_sets`, compute `CryptoHash::hash(&write_set)` for each entry and assert equality with the corresponding `txn_infos[i].state_change_hash()`, mirroring the check already implemented in `TransactionOutputListWithProof::verify`. Fail the chunk load (propagate an error) on mismatch, exactly as done for transaction-hash and event-root mismatches.

### Proof of Concept
1. Produce (or intercept) a transaction backup chunk whose `.transactions` record stream is well-formed BCS for `(Transaction, PersistedAuxiliaryInfo, TransactionInfo, Vec<ContractEvent>, WriteSet)`, but replace one `WriteSet` with an attacker-chosen one (e.g., writing to an unrelated `StateKey`), while keeping `Transaction`, `TransactionInfo` (thus `transaction_hash`, `event_root_hash`, `state_change_hash` fields), and the accompanying `.proof` file (accumulator proof + signed `LedgerInfoWithSignatures`) unchanged.
2. Run `TransactionRestoreController::run()`/`aptos-db-tool restore` (or the backup `verify` coordinator) pointing at this tampered chunk.
3. Observe that `LoadedChunk::load`'s call to `txn_list_with_proof.verify(...)` succeeds (transaction hash, event root, and accumulator-proof checks all pass because those fields were left untouched), and the tampered `WriteSet` is committed via `restore_utils::save_transactions` into the target `AptosDB`, producing a state value that differs from the correct VM output for that transaction with no verification error raised.

    async fn load(
        manifest: TransactionChunk,
        storage: &Arc<dyn BackupStorage>,
        epoch_history: Option<&Arc<EpochHistory>>,
    ) -> Result<Self> {
        let mut file = BufReader::new(storage.open_for_read(&manifest.transactions).await?);
        let mut txns = Vec::new();
        let mut persisted_aux_info = Vec::new();
        let mut txn_infos = Vec::new();
        let mut event_vecs = Vec::new();
        let mut write_sets = Vec::new();

        while let Some(record_bytes) = file.read_record_bytes().await? {
            let (txn, aux_info, txn_info, events, write_set): (
                _,
                PersistedAuxiliaryInfo,
                _,
                _,
                WriteSet,
            ) = match manifest.format {
                TransactionChunkFormat::V0 => {
                    let (txn, txn_info, events, write_set) = bcs::from_bytes(&record_bytes)?;
                    (
                        txn,
                        PersistedAuxiliaryInfo::None,
                        txn_info,
                        events,
                        write_set,
                    )
                },
                TransactionChunkFormat::V1 => bcs::from_bytes(&record_bytes)?,
            };
            txns.push(txn);
            persisted_aux_info.push(aux_info);
            txn_infos.push(txn_info);
            event_vecs.push(events);
            write_sets.push(write_set);
        }

        ensure!(
            manifest.first_version + (txns.len() as Version) == manifest.last_version + 1,
            "Number of items in chunks doesn't match that in manifest. first_version: {}, last_version: {}, items in chunk: {}",
            manifest.first_version,
            manifest.last_version,
            txns.len(),
        );

        let (range_proof, ledger_info) = storage
            .load_bcs_file::<(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)>(
                &manifest.proof,
            )
            .await?;
        if let Some(epoch_history) = epoch_history {
            epoch_history.verify_ledger_info(&ledger_info)?;
        }

        // make a `TransactionListWithProof` to reuse its verification code.
        let txn_list_with_proof =
            TransactionListWithProofV2::new(TransactionListWithAuxiliaryInfos::new(
                TransactionListWithProof::new(
                    txns,
                    Some(event_vecs),
                    Some(manifest.first_version),
                    TransactionInfoListWithProof::new(range_proof, txn_infos),
                ),
                persisted_aux_info,
            ));
        txn_list_with_proof.verify(ledger_info.ledger_info(), Some(manifest.first_version))?;
        // and disassemble it to get things back.
        let (txn_list_with_proof, persisted_aux_info) = txn_list_with_proof.into_parts();
        let txns = txn_list_with_proof.transactions;
        let range_proof = txn_list_with_proof
            .proof
            .ledger_info_to_transaction_infos_proof;
        let txn_infos = txn_list_with_proof.proof.transaction_infos;
        let event_vecs = txn_list_with_proof.events.expect("unknown to be Some.");

        Ok(Self {
            manifest,
            txns,
            persisted_aux_info,
            txn_infos,
            event_vecs,
            range_proof,
            write_sets,
        })
