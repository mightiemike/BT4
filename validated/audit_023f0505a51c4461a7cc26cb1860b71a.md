### Title
`ExchangeTransactionActuator` checks the `expected` slippage bound in `validate()` against a stale/discarded pool snapshot but never re-applies or re-verifies it during `execute()` - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`ExchangeTransactionActuator.doValidate()` computes the amount of tokens the trader will receive (`anotherTokenQuant`) by calling `exchangeCapsule.transaction(...)` on a freshly-loaded, throwaway `ExchangeCapsule`, and checks it against the caller-supplied minimum `tokenExpected` [1](#0-0) . That capsule instance and its computed result are discarded once `validate()` returns — nothing from this check is carried into `execute()`. In `execute()`, a brand-new `ExchangeCapsule` is loaded from the store again and `transaction(...)` is invoked a second, independent time to compute the actual payout that gets credited to the user and persisted [2](#0-1) . The `tokenExpected` slippage bound is never referenced or enforced in `execute()`.

### Finding Description
`ExchangeCapsule.transaction()` mutates the pool's `firstTokenBalance`/`secondTokenBalance` in place and returns the amount bought based on the pool state at the moment it is called [3](#0-2) . Because `validate()` and `execute()` each load a separate `ExchangeCapsule` instance from the store and independently call `transaction()`, the slippage check performed in `validate()` (`anotherTokenQuant < tokenExpected`) is computed against whatever pool state existed at validation time, but the value actually used to credit the account in `execute()` is recomputed from whatever pool state exists at execution time [4](#0-3) [5](#0-4) .

If any other transaction against the same exchange pool (another user's `ExchangeTransactionContract`, or an `ExchangeInjectContract`/`ExchangeWithdrawContract`) is processed between this transaction's `validate()` and its `execute()` — which routinely happens for transactions ordered later within the same block, since TRON validates/executes transactions in sequence and pool state is shared and mutable — the pool balances used at `execute()` time can differ from those used at `validate()` time. The `tokenExpected` minimum-output guarantee the user supplied is therefore not actually enforced against the value that is ultimately paid out; it is only enforced against a value that is thrown away. This mirrors the reported bug class exactly: a slippage bound is checked but the checked value/effect is never the one actually applied.

### Impact Explanation
A trader submitting an `ExchangeTransactionContract` with an `expected` minimum output can receive fewer tokens than that minimum if the pool composition shifts between validation and execution (e.g., due to other trades on the same exchange landing earlier in the same block), because the actual payout in `execute()` is derived from an independent, unchecked recomputation. This defeats the purpose of the `expected` slippage-protection field entirely for this actuator, exposing users to unbounded price-impact/sandwiching within block processing with no on-chain protection, even though the protocol advertises this field as protecting against exactly that [6](#0-5) .

### Likelihood Explanation
This requires no privileged access — any account can submit a competing `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` against the same `exchange_id` and have it ordered ahead of the victim's transaction within the same block (transaction ordering within a block is attacker-influenceable via broadcast timing/fee strategy in TRON's transaction pool). Given exchanges are a public, permissionless feature, and pools with lower liquidity are more sensitive to this shift, likelihood of exploitation is realistic whenever an exchange pool sees concurrent trading activity.

### Recommendation
Perform the `tokenExpected` check against the actual `anotherTokenQuant` computed inside `execute()` (using the same `ExchangeCapsule` instance that will be persisted), rather than relying solely on the disconnected check inside `validate()`. Concretely, move the `anotherTokenQuant < tokenExpected` comparison into `execute()` right after computing `anotherTokenQuant` at line 68, and throw/abort (or revert the balance changes) if it is not satisfied, in addition to keeping the early `validate()` check as a fast-fail pre-check.

### Proof of Concept
1. Exchange pool E has balances such that selling `Q` of token A currently yields `R` of token B, with `R >= expected` for user U's pending `ExchangeTransactionContract` (`quant=Q`, `expected=X`, where `X <= R`).
2. `validate()` is called for U's transaction: it loads its own `ExchangeCapsule`, computes `anotherTokenQuant = R`, checks `R >= X` — passes [4](#0-3) .
3. Before U's transaction is executed (e.g., it is later in the same block), another user's `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` on the same `exchange_id` is executed, shifting the pool balances such that selling the same `Q` of token A would now yield `R' < X`.
4. `execute()` runs for U's transaction: it loads a fresh `ExchangeCapsule` reflecting the new pool state and calls `transaction()` again, computing `anotherTokenQuant = R' < X`, and unconditionally credits U with `R'` tokens and persists the new pool state [5](#0-4) .
5. U's transaction succeeds (`code.SUCESS`) despite receiving less than their specified `expected` minimum, confirming the slippage bound was checked but never actually applied to the executed trade.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
