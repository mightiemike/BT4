## Title
`ensure_match_transaction_info` silently skips checkpoint-hash verification, letting replay/backup-verify tooling accept a diverged position/hot-state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated comparator used by replay and debug tooling (e.g. `aptos-move/cli/src/commands.rs`) to confirm a locally re-executed transaction matches the `TransactionInfo` that was actually committed to the ledger accumulator. The function checks status, gas used, write-set hash, and event-root hash, but a code comment in the function itself documents that it deliberately omits comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The function computes and asserts equality for `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`, but returns `Ok(())` without ever reading or comparing `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The comment explicitly states:

"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This is the sole match-verification entry point used by `aptos-move/cli/src/commands.rs` when replaying a transaction from the debugger and validating it against the persisted `TransactionInfo` [2](#0-1) . The state/hot-state/position checkpoint hashes are exactly the fields that bind a `TransactionInfo` (and hence the accumulator leaf that gets Merkle-proved) to the Sparse-Merkle/Jellyfish state root computed at checkpoint boundaries [3](#0-2) . Because these fields are excluded from the equality check, a locally re-executed transaction whose resulting state root differs from what was actually committed (e.g. due to a divergent state-computation bug, a Jellyfish/position-tree materialization defect, or replay against subtly different state) will still pass `ensure_match_transaction_info` as long as write-set bytes, events, gas, and status happen to match.

### Impact Explanation
This directly weakens the state-integrity guarantee that proof/verification tooling is supposed to provide: it can cause `db-tool` replay-verify and CLI-based transaction-replay checks to falsely report success even when the position/state/hot-state checkpoint root actually diverges from the authenticated, committed root. This matches the "Proof and Storage Pivots" invariant that "authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object" — here the verification path silently drops the strongest state-root binding check, so an underlying state-commitment bug (e.g. in the Jellyfish Merkle/position-state root computation path) could go undetected by the very tool meant to catch it during archive-node replay-verify or db restore validation.

### Likelihood Explanation
The code comment itself flags this as a known gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating the omission is real and currently reachable any time `ensure_match_transaction_info` is invoked (CLI replay tool today; more broadly if reused when the trading-native state-root feature is enabled). It requires no privileged access — a verifier operator running the standard replay/verify tooling is silently under-protected.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (using the caller-supplied expected values or a freshly recomputed checkpoint hash where available), and fail loudly on mismatch, before any code path that relies on this comparator for authenticated-state verification (particularly before `compute_trading_native_state_roots`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled).

### Proof of Concept
Not independently reproducible as an on-chain state-corruption exploit from local code alone: the gap is a verification-omission in an offline CLI/replay tool, not a divergence in the consensus commit path itself. The concrete, code-confirmed defect is:
1. `ensure_match_transaction_info` in `types/src/transaction/mod.rs:2139-2204` never reads `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` from `txn_info`.
2. `aptos-move/cli/src/commands.rs:2809-2813` uses this function as the sole correctness gate after replaying a transaction via the debugger.
3. Therefore, a transaction whose replayed write-set/events/gas/status match but whose resulting checkpoint/position state root differs from the one actually committed would pass this check without any signal, as explicitly documented in the source comment.

I was unable to fully verify whether this comparator is also reachable from any consensus-critical or mainnet-committing code path (versus being confined to the `aptos-move/cli` debugger tool and potentially future trading-native-state-root tooling); the search tools indicate its only current caller is the CLI replay command. This limits confidence that the impact rises to "committed state differs from correct VM result" on mainnet today, rather than being a latent gap in verification tooling awaiting the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
