This is very important - I found the key confirmation: `DelegateAction`'s NEP-461 signature does **not** include any chain/network identifier (`genesis_hash`, `chain_id`) in its signed payload, unlike a regular `Transaction` which binds to a specific `block_hash` for replay protection. Combined with the mirror tool's own comment confirming exactly this class of issue, this is the closest concrete analog to the Solidity DOMAIN_SEPARATOR bug: a signature scheme whose signed message omits the network-distinguishing value, so a signature is valid identically on every network that shares the same account/key state (e.g., a forked NEAR network, or "mirror" replica chain).### Title
`SignedDelegateAction`/`SignedTransaction` signing payloads omit any chain/network identifier, enabling meta-transaction and transaction signature replay across forked NEAR networks - ([File: core/primitives/src/signable_message.rs])

### Summary
NEP-366 meta transactions are authorized via `SignedDelegateAction::verify`, which hashes a `SignableMessage{ discriminant, msg: &DelegateAction }` and checks an ed25519/secp256k1 signature over that hash. Unlike a regular `Transaction`, which is anchored to a specific `block_hash` for freshness/replay protection [1](#0-0) , the `DelegateAction`/`DelegateActionV2` struct that gets signed contains no `genesis_id`, `chain_id`, or any other network-distinguishing value at all - only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` [2](#0-1) . The signature is produced purely as `hash(borsh(SignableMessage{discriminant, msg: delegate_action}))` [3](#0-2)  and verified the same way in `SignedDelegateAction::verify`/`VersionedSignedDelegateAction::verify` [4](#0-3) [5](#0-4) . This is structurally the same class of bug as the reported Uniswap `DOMAIN_SEPARATOR` issue: a signed authorization payload that is supposed to be scoped to one execution context is missing the field that would make it unique to that context (there, `chainId`; here, any network/genesis identifier), so the exact same signed bytes verify successfully on every network that shares the signer's account/access-key state.

### Finding Description
`Runtime::apply_delegate_action` accepts a `SignedDelegateAction` as long as `signed_delegate_action.verify()` succeeds, the access key's nonce is fresh, and `max_block_height` has not passed [6](#0-5) . None of the nonce/access-key/height checks reference anything about which network the runtime is executing on - they are all local, network-agnostic state (`access_key.nonce`, `apply_state.block_height`). The signed hash itself, computed by `get_nep461_hash`, is `hash(borsh(SignableMessage{discriminant, msg: &delegate_action}))` [7](#0-6) , entirely determined by content that is independent of which NEAR network (mainnet, testnet, a hard fork, or a "mirrored"/forked replica chain built from a state dump, as documented in `tools/mirror`) the message is submitted to.

The `tools/mirror` documentation itself independently confirms this exact bug class exists in the codebase for plain `SignedTransaction`s: it states that when mirroring transactions from a source chain onto a forked target chain that shares the same account/key state, "the first approach we might try is to just send the source chain transactions byte-for-byte unaltered to the target chain... [but] the `block_hash` field in the transactions will be rejected," forcing them to remap public keys just to get past the `block_hash`/validity-period check [8](#0-7) . That check only works because ordinary transactions bind to a specific recent `block_hash` on the source chain that (usually) won't exist on the fork. `DelegateAction`, however, has no equivalent binding at all - not to a `block_hash`, and not to any longer-lived, per-network identifier like `genesis_hash`/`chain_id`. So even the (admittedly narrow) protection that ordinary transactions get "by accident" from `block_hash` mismatch is absent for the meta-transaction signature itself. If an access key with the same nonce state exists on two networks derived from a common genesis (e.g., a chain fork, a state-dumped mirror/testnet clone, or a future protocol split), a `SignedDelegateAction` valid on one is trivially replayable, unmodified, on the other, because the relayer only needs a fresh outer `Transaction` (with a valid `block_hash` on the target network) to carry the identical, already-signed `DelegateAction` bytes.

### Impact Explanation
A user's meta-transaction authorization (e.g., "transfer these tokens," "add this access key," "call this contract with this deposit") signed for use on one NEAR network can be relayed and executed unmodified on any other network that shares the same account state and access-key nonce counter (post-fork networks, testnet/mainnet forks derived from the same records, or mirrored/forked test networks built via `neard view-state dump-state` as `tools/mirror` explicitly supports). This is unauthorized execution of a user-signed authorization outside its intended execution context, resulting in unauthorized value movement or unauthorized key/account modification on the unintended network. This matches the "concrete unauthorized value movement" / "invalid state transition acceptance" criteria: the runtime accepts a `DelegateAction` signature as valid proof of user intent for a network the user never intended to interact with.

### Likelihood Explanation
The precondition (two networks sharing account/access-key state with the same nonce for a given public key) is exactly the scenario nearcore's own `tools/mirror` is built to create and that a live chain fork event produces natively (all state, including access keys and nonces, is identical at the fork point). Any relayer or malicious party holding a previously-observed `SignedDelegateAction` (relayers necessarily see these in plaintext to submit them) can replay it on the sibling network without any additional signing step, only needing to wrap it in a fresh outer transaction (which requires no special privilege - any account can be the outer signer/relayer since the DelegateAction's inner sender pays/authorizes the actions). This is a realistic and directly reachable path for any meta-transaction user on the day of a fork, or on networks intentionally rehydrated from mainnet/testnet snapshots.

### Recommendation
Include a network-distinguishing value (e.g., `genesis_hash` or a protocol-defined `chain_id`, analogous to EIP-155's `chainId` in the `DOMAIN_SEPARATOR`) inside the `DelegateAction`/`DelegateActionV2` payload that gets hashed and signed in `SignableMessage`/`get_nep461_hash`, and require `apply_delegate_action` to check it against the current network's genesis/chain identifier before honoring the signature. This closes the replay gap without waiting for a fork event to "just work out" via unrelated fields like `block_hash` (which ordinary transactions rely on only incidentally).

### Proof of Concept
1. Network A and Network B share identical genesis/state (e.g., B is a `view-state dump-state` fork of A, or B is a post-fork chain continuing from A's history), including account `alice.near`'s access key and its current nonce.
2. Alice signs a `DelegateAction{ sender_id: alice.near, receiver_id: bob.near, actions: [Transfer{...}], nonce: N, max_block_height: H, public_key: alice_pk }` intending it to run only on Network A, producing `signature = sign(hash(borsh(SignableMessage{discriminant, &delegate_action})))` per `DelegateAction::get_nep461_hash`/`SignableMessage::sign` [7](#0-6) [9](#0-8) .
3. A relayer (or anyone who observed the `SignedDelegateAction`) wraps the identical, unmodified `SignedDelegateAction` bytes in a new outer `SignedTransaction` addressed to Network B (using a fresh, valid `block_hash` from Network B's own chain and any relayer account/nonce on B), and submits it there.
4. On Network B, `apply_delegate_action` calls `signed_delegate_action.verify()`, which succeeds because the hash/signature check has no dependency on which network is executing it [10](#0-9) ; it then checks only `max_block_height` against B's local block height and Alice's access-key nonce on B (which, since B shares A's genesis state, is in the same range), both of which pass, and the transfer/action executes on Network B even though Alice never intended or authorized action on Network B.

        Self { discriminant, msg }

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }
