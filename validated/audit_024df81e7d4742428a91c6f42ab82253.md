### Title
Signature Malleability Allows a Single Signer's Authorization to be Double-Counted, Bypassing Multi-Signature Threshold in `ValidateMultiSign` Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract (used by smart contracts to verify on-chain multi-signature authorization) deduplicates submitted signatures by comparing the raw `(address, signature-bytes)` pair rather than by signer address alone. Because ECDSA signatures over secp256k1 are malleable (a valid `(r, s)` signature can be transformed into another valid `(r, n-s)` signature for the same message/address without knowledge of the private key), an attacker can take a single legitimate signature from one signer and derive additional distinct-byte signatures that recover to the *same* address. Each such variant is accepted and its weight is added again, letting one real signer's authorization satisfy a threshold meant to require multiple distinct signers — precisely the bug class described in the external report (`bigclaim()`/lack-of-distinct-signer check), reproduced here in java-tron's on-chain multisig verification path.

### Finding Description
`ValidateMultiSign.execute` recovers an address for every supplied signature and tracks previously seen entries in `executedSignList`, which stores both the recovered address and a `merge(recoveredAddr, sign)` compound value: [1](#0-0) 

The de-duplication logic only skips counting weight again when the *exact same signature bytes* for an address have already been seen (`matrixContains(executedSignList, sign)`). If the recovered address is already present but the raw signature bytes differ, it does **not** skip — it merely calls `MUtil.checkCPUTime()` (an anti-DoS guard, not a security check) and then falls through to add the address's weight to `totalWeight` again: [2](#0-1) 

Because secp256k1 ECDSA signatures are malleable — given a valid `(r, s, v)` triple, `(r, n-s, 1-v)` is also a valid signature recoverable to the same address, computable by anyone who possesses the original signature, without the private key — an attacker holding one authorized signer's signature can trivially derive a second, third, etc. distinct-byte signature for the same address. Each of these is treated by the loop as if it came from an independent co-signer, and its weight is added to `totalWeight` on every iteration until `permission.getThreshold()` is reached, returning `dataOne()` (success) at line 1109.

This is the same root cause identified in the external report: the check enforces "no exact duplicate submission" instead of enforcing "signatures must come from distinct signers." The contrast with the correct pattern in `TransactionCapsule.checkWeight`, used for ordinary transaction/permission signature verification, is instructive — that function deduplicates by `encode58Check(address)` (post fork `VERSION_4_7_1`), i.e., by signer identity, not by raw signature bytes: [3](#0-2) 

`ValidateMultiSign` never adopted this address-keyed dedup; it only guards against literal byte-for-byte resubmission of the same signature, which malleability trivially defeats.

### Impact Explanation
This precompile is reachable by any smart contract via a standard TVM call (address for `ValidateMultiSign`) invoked from an ordinary `TriggerSmartContract` broadcast transaction — no privileged role or special network position is required. Any DApp/contract that relies on `ValidateMultiSign(address, permissionId, data, signatures[])` to enforce an on-chain multi-signer authorization policy (e.g., custodial wallets, escrow, governance contracts, bridges) can be tricked into accepting an operation as multi-sig-approved when only a single real signer actually authorized it. This directly corrupts the security guarantee of on-chain multi-signature/permission validation and can lead to unauthorized asset transfers or unauthorized privileged operations gated behind that check, matching the report's core concern ("a single signer can provide all required signatures").

### Likelihood Explanation
High. Exploitation requires only: (1) obtaining one valid signature from a legitimate signer (which the attacker may already possess if they are that signer, or which is exposed in any prior authorized call), and (2) performing a standard, well-known secp256k1 signature malleability transform (`s' = n - s`, flip recovery id) — a purely local, private-key-free computation. No race condition, no special timing, no node/consensus access is needed; it is a pure calldata-crafting attack against a public TVM precompile.

### Recommendation
In `ValidateMultiSign.execute` (and any similarly structured precompile, e.g. review `BatchValidateSign` for the same pattern), deduplicate by recovered **address only**, not by `(address, signature-bytes)`. Concretely, track only `recoveredAddr` in a set; if the address has already contributed weight, skip counting it again regardless of whether the signature bytes differ (mirroring the `encode58Check(address)`-keyed logic already used in `TransactionCapsule.checkWeight`). Additionally, consider normalizing/canonicalizing signatures (reject non-canonical high-`s` values) at the point of signature format validation to remove the cheap malleability vector entirely.

### Proof of Concept
1. Deploy/target an account with an `Active` permission requiring `threshold = 2`, with keys for signer `A` (weight 1) and signer `B` (weight 1).
2. Attacker controls only signer `A`'s key. `A` produces one valid signature `sig1 = (r, s, v)` over the precompile's hash (`address || permissionId || data`).
3. Attacker computes the malleated signature `sig2 = (r, n-s, 1-v)` — no private key needed, purely arithmetic on the existing `sig1`.
4. Attacker submits `signatures[] = [sig1, sig2]` to `ValidateMultiSign(address, permissionId, data, signatures)` via a `TriggerSmartContract` call.
5. In the loop: iteration 1 recovers `A`, adds weight 1, records `merge(A, sig1)`. Iteration 2 recovers `A` again (same address) but `merge(A, sig2)` is not in `executedSignList` (different bytes), so the `continue` is skipped, and weight 1 is added again — `totalWeight = 2 >= threshold(2)`, and the call returns `dataOne()` (success), even though only signer `A` ever authorized the request.
