## Title
`ensure_match_transaction_info` skips native-position/checkpoint hash validation, letting replay-verify tooling accept a divergent authenticated ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the core invariant check used by replay/verification tooling (`db-tool replay-on-archive`, `aptos-debugger`, `aptos move` CLI commands) to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` stored/committed on-chain. The function validates status, gas, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as documented in its own inline comment.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  checks:
- transaction status vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `write_set_hash` vs. `txn_info.state_change_hash()`
- `event_root_hash` vs. `txn_info.event_root_hash()`

but the function's own trailing comment states: [2](#0-1) 
which acknowledges that the checkpoint hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, and the newly repurposed `position_state_checkpoint_hash`) are never compared. `TransactionInfoV1` carries these fields as first-class, hash-committed data [3](#0-2) , and they are meant to bind the periodic Sparse-Merkle-Tree / hot-state / native-position roots into the transaction-accumulator-covered `TransactionInfo` hash. The commit-path assembly of these hashes (`assemble_transaction_infos` in `execution/executor/src/workflow/do_ledger_update.rs:58-127`) treats them as authoritative parts of the committed ledger state, and `DoStateCheckpoint::get_state_checkpoint_hashes` explicitly `ensure!`s that freshly computed checkpoint roots match "known" hashes taken from `TransactionInfo` during chunk execution and normal block execution (`execution/executor/src/workflow/do_state_checkpoint.rs:192-234`). This shows the checkpoint hashes are treated elsewhere in the codebase as integrity-critical, proof-bound fields — but `ensure_match_transaction_info` (used specifically by replay/verification tooling that reads transactions *from backup/archive* and re-executes them) does not perform the same check.

This is the direct analog of the C4 "yield" bug: a returned/committed value (`sellBasePreview`'s `returned` amount there; here, the checkpoint/position-state root hashes embedded in a fetched `TransactionInfo`) is accepted and used to gate a downstream trust decision without validating it against the independently-derivable ground truth, silently downgrading the check to a no-op for that specific field.

### Impact Explanation
Replay-verification is one of Aptos's core defense-in-depth mechanisms for detecting silent state divergence (non-determinism bugs, storage corruption, malicious archive data, or governance-triggered execution regressions) after the fact. Because `ensure_match_transaction_info` never compares `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, a corrupted or maliciously altered snapshot/backup archive (or a node with divergent Merkle/position state due to a hard-fork bug) can pass `replay_on_archive` and CLI/debugger replay checks even when the actual world-state root, hot-state root, or native order-book position-state root committed on-chain diverges from what local re-execution computes. This directly matches the "Proof And Storage Pivots" requirement that "Authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object," and the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category. It undermines confidence that replay tooling would actually catch a state-root corruption bug before/after it reaches mainnet.

### Likelihood Explanation
The gap is not theoretical — it is called out by an explicit TODO comment in the function itself, gating enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. The state-checkpoint-hash gap (state/hot-state) already exists unconditionally for every call of `ensure_match_transaction_info`, independent of that feature flag: any replay tool run today would not catch a state-checkpoint-hash mismatch. I was not able to fully verify in this session whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (native-position state root) is currently enabled on mainnet — the flag exists in `types/src/on_chain_config/aptos_features.rs` and is threaded through `execution/executor-types/src/execution_output.rs` and `execution/executor/src/workflow/do_get_execution_output.rs`, but confirming its current mainnet activation state and the real-world reachability/severity of the `position_state_checkpoint_hash` portion of this gap requires access I don't have in this index (feature-flag on-chain state is not a static code fact). The `state_checkpoint_hash`/`hot_state_checkpoint_hash` omission, however, is unconditional and always active in `ensure_match_transaction_info`.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` and `hot_state_checkpoint_hash` against independently recomputed roots wherever they are available to the caller (mirroring the pattern already used in `DoStateCheckpoint::get_state_checkpoint_hashes`), and finish wiring in the `position_state_checkpoint_hash` comparison before (or gated behind) enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the existing comment already recommends.

### Proof of Concept
Not independently constructed with a concrete runnable exploit in this session — the finding is grounded in the explicit self-documented gap in `ensure_match_transaction_info` [4](#0-3)  together with confirmation from the commit path that checkpoint hashes are treated as authoritative/proof-bearing values elsewhere (`execution/executor/src/workflow/do_state_checkpoint.rs:206-221`, `execution/executor/src/workflow/do_ledger_update.rs:95-121`). Full exploitation would require constructing a corrupted backup/archive chunk whose write-set/event hashes match but whose checkpoint state root is altered, and running it through `storage/db-tool/src/replay_on_archive.rs`, which I could not execute in this read-only session.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
