### Title
Systematic underpayment in `MarketSellAssetActuator` order matching due to floor-rounding of TRX/token amounts owed - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The external report describes a rounding-direction bug in `CollateralAuctionHouse`: an amount that represents a payment *into* the system is truncated (rounded down) instead of rounded up, letting the payer settle for less than the fair value. The java-tron TRC10 order-book market (`MarketSellAssetContract` → `MarketSellAssetActuator`) contains the same class of bug: the quantity a taker must pay to fully consume a maker's remaining order is computed with floor division (`MarketUtils.multiplyAndDivide`, which uses `floorDiv`), while the quantity the taker *receives* is set to the maker's full remaining balance (not rounded). This systematically lets the taker underpay the maker by up to 1 unit of the sell token per fill.

### Finding Description
`MarketUtils.multiplyAndDivide` performs `a*b` and then `floorDiv(tmp, c)` (rounding toward negative infinity, i.e. truncation for positive operands), falling back to `BigInteger` division (also truncating) on overflow: [1](#0-0) 

In `MarketSellAssetActuator.matchSingleOrder`, when the taker's demand exceeds the maker's remaining sell quantity ("taker > maker" branch), the taker receives the *entire* remaining sell quantity of the maker's order (an exact, non-rounded amount), but the amount debited from the taker (i.e., paid to the maker) — `makerBuyTokenQuantityReceive` — is computed via `MarketUtils.multiplyAndDivide`, which floors the result: [2](#0-1) 

The same asymmetric pattern (exact amount given to taker vs. floor-rounded amount taken from taker/given to maker) also occurs in the "taker == maker" branch: [3](#0-2) 

In both cases the taker's "sell quantity remain" (the amount debited to satisfy the trade) is reduced by the floor-rounded `makerBuyTokenQuantityReceive`, not by a ceiling-rounded value: [4](#0-3) 

This mirrors exactly the root cause in the reference report: an amount owed/paid into a settlement is truncated down instead of rounded up, so the payer (here, the taker) pays strictly less than the maker's stated exchange ratio requires, while the counterparty (maker) receives less value than it is owed for the tokens it gave up. There is no reconciling check anywhere in `MarketSellAssetActuator` (unlike `ExchangeWithdrawActuator`, which has an explicit `"Not precise enough"` 0.01% deviation check) that bounds or corrects this rounding loss.

### Impact Explanation
Every partial/complete maker-order consumption where the maker's remaining-quantity ratio does not divide evenly causes the maker to be shortchanged by up to 1 unit of its receive-token per fill, while the taker fully receives the maker's advertised sell amount. This is an accounting/settlement divergence directly caused by an incorrect rounding direction on a value representing payment owed into the trade, i.e., "underpriced-public-work" in the market settlement path. An attacker acting as taker can deliberately construct or target maker orders whose ratios do not divide evenly (or repeatedly trade against many small maker orders) to systematically extract fractional-unit value from makers across the permissionless, unprivileged `MarketSellAssetContract` flow, at no cost beyond the standard market fee.

### Likelihood Explanation
The `MarketSellAssetContract`/`MarketSellAssetActuator` flow is fully public and unprivileged — any account can place sell orders and trigger matching, and matching happens automatically whenever quantities/ratios don't divide evenly, which is the common case for arbitrary integer order sizes. No additional preconditions (approvals, admin roles, timing) are required, so the rounding-favorable-to-taker condition is trivially and repeatedly reachable.

### Recommendation
In `MarketSellAssetActuator.matchSingleOrder`, when the taker consumes the maker's full remaining order (the "taker == maker" and "taker > maker" branches), the amount debited from the taker (`makerBuyTokenQuantityReceive`) should be rounded up (ceiling division) rather than floored via `MarketUtils.multiplyAndDivide`'s `floorDiv`, so the taker cannot pay less than the fair proportional amount for the tokens they receive. Alternatively, add a compensating precision check similar to the one already present in `ExchangeWithdrawActuator` (`doValidate`) that bounds the acceptable rounding deviation.

### Proof of Concept
1. Create a maker order via `MarketSellAssetContract`: sell 3 units of token A for 2 units of TRX (ratio 3:2), leaving `sellTokenQuantityRemain = 3`.
2. Submit a taker `MarketSellAssetContract` selling ≥2 TRX for token A, entering `matchSingleOrder` with `takerBuyTokenQuantityRemain >= makerOrderCapsule.getSellTokenQuantityRemain()` ("taker > maker" branch).
3. `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain() = 3` (taker gets all 3 units of A).
4. `makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(3, 2, 3, ...) ` — exact value; use a ratio that doesn't divide evenly, e.g. maker sells 5 A for 3 TRX (`sellTokenQuantityRemain=5`), taker consumes all 5: `multiplyAndDivide(5, 3, 5)` = 3 exactly is a bad example; pick maker sell=7 A for buy=3 TRX: `multiplyAndDivide(7,3,7)=3` also exact only because remain==sellQuantity. To see the loss, set the maker's remaining quantity to be less than its original sellTokenQuantity (a partially-filled order), e.g. original order 7 A for 3 TRX, already partially filled down to `sellTokenQuantityRemain = 5`; then `makerBuyTokenQuantityReceive = floorDiv(5*3, 7) = floorDiv(15,7) = 2` instead of the fair `15/7 ≈ 2.14` (should round up to 3 to fully compensate the maker for its remaining 5 A). The taker receives all 5 remaining A tokens for only 2 TRX debited from its order remainder, instead of the fair ~2.15–3 TRX, at line: [5](#0-4) 
5. The maker's stored order is closed at `sellTokenQuantityRemain = 0` having received only the floor-rounded TRX amount for its full remaining token quantity, confirming the underpayment.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
