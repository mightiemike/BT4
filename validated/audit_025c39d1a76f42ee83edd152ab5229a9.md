### Title
Rosetta RPC NEP-141 Event Collector Processes Logs from Failed Receipts and Emits Them as `SUCCESS` Operations — (`File: chain/rosetta-rpc/src/adapters/nep141.rs`, `chain/rosetta-rpc/src/adapters/transactions.rs`)

---

### Summary

`collect_nep141_events` iterates over every execution outcome in a block — including those with `ExecutionStatusView::Failure` — without checking the receipt's execution status. The downstream function `convert_fungible_token_balance_change_to_operations` then unconditionally marks every resulting Rosetta `Operation` as `OperationStatusKind::Success`. An unprivileged user who deploys a contract that emits `EVENT_JSON:` NEP-141 `ft_transfer` logs and then panics will cause the Rosetta API to report phantom token transfers as successful operations, misleading any exchange or service that uses the Rosetta API for balance reconciliation.

---

**Step 3 — The resulting Rosetta `Operation` is unconditionally marked `SUCCESS`.**

`convert_fungible_token_balance_change_to_operations` hardcodes `OperationStatusKind::Success` for every FT operation it creates, regardless of the `FungibleTokenEvent.status` string field:

```rust

    fungible_token_event: &FungibleTokenEvent,
    operations: &mut Vec<crate::models::Operation>,
) {
    operations.push(crate::models::Operation {
        ...
        type_: crate::models::OperationType::Transfer,
        status: Some(crate::models::OperationStatusKind::Success),  // ← always SUCCESS
        ...
    });
}
``` [5](#0-4) 

The `OperationStatusKind` enum has no `Failure` variant — only `Success` and `Empty`:

```rust
pub(crate) enum OperationStatusKind {
    Success,
    #[serde(rename = "")]
    Empty,
}
``` [6](#0-5) 

Although `get_status` in `nep141.rs` does produce a `"FAILURE"` string for failed outcomes, this string is stored only in `FungibleTokenEvent.status` and is never consulted when the Rosetta `Operation` is built. [7](#0-6) 

---

### Impact Explanation

In NEAR, when a receipt fails, state changes are rolled back via `state_update.rollback()`, but **logs are preserved** in the `ExecutionOutcome`. A contract can therefore emit `EVENT_JSON:` NEP-141 `ft_transfer` logs and then panic. The on-chain token balances are unchanged, but the Rosetta API will include the phantom transfer as a `SUCCESS` operation in the block response. Any exchange, custodian, or indexer that uses the Rosetta `/block` endpoint for balance reconciliation will credit the attacker with tokens they never actually received. This is a balance-manipulation impact reachable from an ordinary unprivileged user action (deploying and calling a contract).

---

### Likelihood Explanation

The attack requires only a deployed contract — no privileged access, no validator control. Any NEAR account can deploy a contract that emits arbitrary `EVENT_JSON:` logs before panicking. The Rosetta RPC is a production endpoint used by exchanges for balance tracking. The likelihood is moderate-to-high for any operator relying on the Rosetta API for NEP-141 accounting.

---

### Recommendation

In `collect_nep141_events` (or in `extract_events`), skip any outcome whose status is not `ExecutionStatusView::SuccessValue` or `ExecutionStatusView::SuccessReceiptId`:

```rust
pub(crate) fn collect_nep141_events(
    receipt_execution_outcomes: &Vec<ExecutionOutcomeWithIdView>,
    ...
) -> crate::errors::Result<Vec<FungibleTokenEvent>> {
    let mut res = Vec::new();
    for outcome in receipt_execution_outcomes {
        // Only process logs from successful receipts
        match outcome.outcome.status {
            ExecutionStatusView::SuccessValue(_)
            | ExecutionStatusView::SuccessReceiptId(_) => {}
            _ => continue,
        }
        let events = extract_events(outcome);
        ...
    }
    Ok(res)
}
```

Alternatively, add the same guard inside `extract_events`. Either way, the fix must be applied before `convert_fungible_token_balance_change_to_operations` is called, since that function has no access to the outcome status.

---

### Proof of Concept

1. Deploy a contract on NEAR mainnet/testnet with the following logic in a callable method:
   ```rust
   env::log_str(r#"EVENT_JSON:{"standard":"nep141","version":"1.0.0","event":"ft_transfer","data":[{"old_owner_id":"victim.near","new_owner_id":"attacker.near","amount":"1000000000000000000000000"}]}"#);
   panic!("intentional failure");
   ```
2. Call the method from any account. The receipt will fail; on-chain token balances are unchanged.
3. Query the Rosetta `/block` endpoint for the block containing that receipt.
4. Observe that the response contains a `Transfer` operation with `status: "SUCCESS"` crediting `attacker.near` with `1000000000000000000000000` yoctoNEAR-equivalent tokens of the spoofed NEP-141 contract.
5. Any exchange reconciling balances from the Rosetta API will incorrectly credit `attacker.near`.

pub(crate) fn extract_events(
    execution_outcome: &ExecutionOutcomeWithIdView,
) -> Vec<crate::models::Nep141Event> {
    let prefix = "EVENT_JSON:";
    execution_outcome
        .outcome
        .logs
        .iter()
        .filter_map(|untrimmed_log| {
            let log = untrimmed_log.trim();
            if !log.starts_with(prefix) {
                return None;
            }

            match serde_json::from_str::<'_, crate::models::Nep141Event>(log[prefix.len()..].trim())
            {
                Ok(result) => Some(result),
                Err(_err) => None,
            }
        })
        .collect()
}
```
