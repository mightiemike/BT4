### Title
Short PoX-treatment bitvec silently masks reward/punish mismatches for multi-slot addresses — ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoChainState::check_pox_bitvector` is supposed to enforce an equality between a block-commit's PoX `Treatment` (reward vs. punish, computed independently from burnchain outputs) and the miner-signed `pox_treatment` bitvector in the block header. When the header's bitvector is shorter than the active reward set, out-of-range bits are defaulted to `true` rather than causing rejection. For addresses that occupy more than one slot in the reward set, this default can produce a *mixed* result (some real bits `false`, some defaulted `true`) that satisfies neither the `all_1` nor `all_0` branch, silently skipping the consistency check instead of rejecting the block.

### Finding Description
`check_pox_bitvector` builds a map from PoX address to all slot indices it occupies in `active_reward_set.rewarded_addresses()`: [1](#0-0) 

For each treated address in the block-commit, it reads the bit at every occupied index, but when the header's `block_bitvec` is shorter than that index, it substitutes a hard-coded default of `true` ("rewarded") instead of erroring out: [2](#0-1) 

The verdict is then only enforced at the extremes: [3](#0-2) 

- If **all** collected bit values are `1` → reject a `Punish` treatment.
- If **all** collected bit values are `0` → reject a `Reward` treatment.
- **Any mixed combination is accepted unconditionally**, regardless of what the block-commit actually did.

A stacker/PoX address can legitimately occupy multiple slots in the V0 reward set (this is explicitly exercised in `pox_treatment` test where each stacker gets 3 slots — see `stackslib/src/chainstate/nakamoto/coordinator/tests.rs:1756-1760`). The expected invariant is: `pox_treatment.len() == active_reward_set.pox_treatment_bitvec_len()` (i.e., one bit per slot) — see `RewardSet::pox_treatment_bitvec_len` [4](#0-3)  and how miners always construct headers at full length [5](#0-4) . However, `check_pox_bitvector` itself never validates that the header's `pox_treatment.len()` actually equals `active_reward_set.pox_treatment_bitvec_len()` before indexing into it — the length equality is only asserted in test helper code and miner-construction code, not as a hard consensus check inside the validator itself. A miner is free to sign a header with a truncated bitvector (as long as it deserializes, since the codec only forbids zero-length), and this function will silently paper over the truncation for any multi-slot address whose occupied indices straddle the "real" vs. "defaulted" boundary.

### Impact Explanation
This breaks the equality that `check_pox_bitvector` is meant to enforce: *the signer-attested treatment bitvector must match the block-commit's actual reward/punish behavior*. If a malicious/buggy miner crafts a short `pox_treatment` header combined with a block-commit that punishes (burns instead of pays) a multi-slot PoX address, the validator can be fooled into accepting the block as valid (mixed 0/1 result → no error), when honest nodes reconstructing state from the same reward set and full-length bitvector semantics would compute a different, deterministic verdict. Because `check_pox_bitvector` runs during `setup_block`/`setup_ephemeral_block` on the path that all full nodes execute independently when processing/replaying a block [6](#0-5) , this is not a signer-only or wallet-only concern — every node applies this exact deterministic function to decide block validity, so a divergence here is consensus-relevant. This lines up with the High-severity impact bucket ("a minority-triggerable ... static-validation divergence") since the attacker only needs to be the block's own miner (no majority/collusion needed) to construct the malformed header/commit pair, potentially causing a payout treatment to be accepted that should have been rejected as invalid.

### Likelihood Explanation
Likelihood is moderate-to-low but non-zero: it requires (a) a reward set where a stacker holds ≥2 slots (routine, since PoX-4 always allocates `stacked_amt / threshold` slots per signer/stacker, frequently >1), (b) a miner willing to sign a header with a `pox_treatment` shorter than `pox_treatment_bitvec_len()`, and (c) a block-commit whose `treatment` vector actually diverges (Punish where honest nodes expect Reward, or vice versa) for that same address. The BitVec codec's only length restriction is "non-zero" [7](#0-6) , so a shorter, still-valid bitvector is deserializable and not rejected purely on length by this function. No majority of signers or nodes is needed to trigger it — the malicious miner alone crafts the block. Whether a signer or another portion of validation elsewhere (outside `check_pox_bitvector`) independently rejects the too-short bitvector is not something I could fully confirm from the retrieved code; I found the miner-side code paths always constructing full-length bitvectors, and test helpers that assert full length, but no explicit consensus-level length-equality assertion inside `check_pox_bitvector` itself or nearby callers guarding against a short header.

### Recommendation
In `check_pox_bitvector`, before iterating `tenure_block_commit.treatment`, assert that `block_bitvec.len() == active_reward_set.pox_treatment_bitvec_len()` (for V0 reward sets) and return `ChainstateError::InvalidStacksBlock` immediately if they differ, rather than silently defaulting out-of-range reads to `true`. This removes the ambiguous "mixed" case entirely and restores the intended equality check between the signer-attested bitvector and the block-commit's actual PoX treatment.

### Proof of Concept
Conceptual PoC (cannot be executed here, but derivable from the code paths and existing test scaffolding at `stackslib/src/chainstate/nakamoto/coordinator/tests.rs:1693-1926`, which already manipulates `pox_treatment` and `commit_outs` in this exact function):
1. Set up a PoX-4 reward cycle where a single stacker occupies 2+ slots (e.g., 3 slots, as in `pox_treatment()` test).
2. As the miner, construct a `LeaderBlockCommitOp` whose `commit_outs` sends that stacker's slots to a burn address instead of paying them (yielding `Treatment::Punish(addr)` for that address, real intent = "punish/all bits should be 0").
3. As the miner, sign a Nakamoto block header whose `pox_treatment` bitvector is *shorter* than `active_reward_set.pox_treatment_bitvec_len()`, such that only some of the stacker's 3 slot-indices fall within the vector (set to `false`) and the rest fall outside it (defaulted to `true` by `check_pox_bitvector`).
4. Submit the block for processing via `setup_block`/`check_pox_bitvector`.
5. Expected (correct) behavior: reject, since real block-commit behavior was "punish" but header data is inconsistent/incomplete. Observed (buggy) behavior: `bitvec_values` is a mix of `false`/`true`, so neither `all_1` nor `all_0` holds, and the function returns `Ok(())`, accepting the block despite the truncated, non-length-matching bitvector.
