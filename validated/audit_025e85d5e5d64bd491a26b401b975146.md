Based on the investigation, I found a concrete, code-documented integrity gap rather than a fabricated one. The bug-class analog (Velar Artha's "amounts paid vs. received diverge without detection due to a comparator that doesn't check the full invariant") maps to Aptos's own transaction-output-vs-`TransactionInfo` comparator, which explicitly and admittedly skips verifying the state-commitment fields.

### Title
Replay-verify comparator omits state/hot-state/position checkpoint hash checks, allowing state-root divergence to pass as valid replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by replay/verification tooling to confirm that a freshly re-executed transaction output matches the authenticated `TransactionInfo` stored on-chain/in backups, checks status, gas, write-set hash, and event-root hash — but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is called out in-code as a known, currently-live gap.

### Finding Description
`ensure_match_transaction_info` validates four fields against `txn_info` and then stops, with an explicit TODO acknowledging the state-checkpoint fields are skipped: [1](#0-0) 

This function is the sole "does this txn output match the authenticated `TransactionInfo`" gate used by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which is invoked by the replay-verify chunk executor used in `ReplayVerifyCoordinator` / `storage/db-tool/src/replay_verify.rs`. [2](#0-1) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`, other callers relying on it to authenticate re-executed output.

The `state_checkpoint_hash` (and its V1 siblings `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) is precisely the field that binds a `TransactionInfo` to the actual Sparse-Merkle/Jellyfish state root produced by execution, per its own doc comment: [3](#0-2) 

Because the comparator never re-derives or compares this hash against the locally-recomputed state root, `verify_execution`/replay-verify can walk an entire backup/archive range, recompute every transaction, and report success even if the locally computed state-checkpoint root differs from the one embedded in the archived, "authenticated" `TransactionInfo`. The gap is explicitly staged for the upcoming native-position/trading feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`), which introduces the new `position_state_checkpoint_hash` field into the exact same unchecked path: [4](#0-3) 

### Impact Explanation
This falls under "Wrong accumulator root, Merkle proof, transaction proof, event proof, or state proof accepted as valid" and "Authenticated API or state-view output bound to the wrong version, object, or proof context." Replay-verify is the mechanism operators and auditors use to confirm that an archived/backed-up ledger's authenticated `TransactionInfo`s (and therefore the accumulator/state roots they feed into) genuinely correspond to the VM's deterministic output. With this comparator silently ignoring the checkpoint-hash fields, a state-root divergence — whether from a backup/restore corruption, a non-determinism bug, or a malicious archive/full-node serving corrupted `TransactionInfo`s — is not caught by `replay_on_archive`/`replay_verify`, i.e. corrupted durable state can be certified as correct.

### Likelihood Explanation
The gap is unconditional today (state_checkpoint_hash comparison is simply absent for all replay-verify runs), and the TODO comment shows the team is aware of it but has deferred fixing it until `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled — meaning the unprotected window persists and will widen (new `position_state_checkpoint_hash` field) rather than shrink. No privileged access is required to trigger the missed detection; it's a passive gap in the verifier itself, only requiring that some already-corrupted or maliciously-served archive data be run through replay-verify.

### Recommendation
In `ensure_match_transaction_info`, recompute the local state-checkpoint root and, when `txn_info.state_checkpoint_hash()` (and V1's `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`) is `Some`, assert equality before returning `Ok(())`, exactly as already done for `state_change_hash` and `event_root_hash`.

### Proof of Concept
1. Take any archived/backup transaction range and mutate the state-checkpoint root recorded in one `TransactionInfo` entry's `state_checkpoint_hash` while leaving `write_set`/`events`/`status`/`gas_used` correct (i.e., corrupt exactly the field this comparator skips).
2. Run `storage/db-tool/src/replay_verify.rs` (`ReplayVerifyCoordinator`) or `replay_on_archive.rs` against this data.
3. Observe `verify_execution` in `execution/executor/src/chunk_executor/mod.rs` (line 692) calling `ensure_match_transaction_info`, which returns `Ok(())` despite the state-checkpoint hash mismatch, because no comparison of that field exists in the function body — the tool reports a clean replay.
