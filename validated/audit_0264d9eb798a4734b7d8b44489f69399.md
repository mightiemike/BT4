### Title
Panic in `NativeSyscallHandler` callbacks can unwind unsafely across the Cairo-Native JIT/FFI boundary without a `catch_unwind` guard - (File: crates/blockifier/src/execution/native/entry_point_execution.rs)

### Summary
The Cairo-Native execution path invokes JIT-compiled (LLVM/MLIR-generated) contract code via `AotContractExecutor::run`, passing a mutable `NativeSyscallHandler` that is called back into from that compiled native code for every syscall [1](#0-0) . This callback interface is functionally an FFI boundary: Rust code (`NativeSyscallHandler`) is invoked from natively compiled machine code that was never compiled by `rustc` with matching unwind tables. Several of the handler's internal invariants are enforced with `assert!`/`panic!`-style constructs, e.g. the guard against setting `unrecoverable_error` twice [2](#0-1) . Unlike the sibling concurrency path, which explicitly wraps thread execution in `panic::catch_unwind` plus an `AbortIfPanic` guard specifically because of this exact class of risk [3](#0-2) , the direct call into `compiled_class.executor.run(...)` in `native_entry_point_execution::execute_entry_point_call` has no local unwind boundary or abort guard around the JIT call itself.

### Finding Description
`execute_entry_point_call` in `crates/blockifier/src/execution/native/entry_point_execution.rs` calls into a `cairo_native::executor::AotContractExecutor`, which runs machine code compiled ahead-of-time from attacker-declared Sierra bytecode [4](#0-3) . During execution, the JIT code calls back into `NativeSyscallHandler`'s `StarknetSyscallHandler` trait implementation for every syscall (`call_contract`, `library_call`, etc.) [5](#0-4) .

If a Rust panic occurs inside one of these callbacks — for instance the `assert!(self.unrecoverable_error.is_none(), ...)` invariant in `handle_error` [2](#0-1) , or any other `unwrap()`/`expect()`/`assert!` reachable from syscall-handling code (`native/syscall_handler.rs` and `native/utils.rs` both contain such calls) — the panic must unwind back through the JIT-compiled Cairo-Native stack frames before any Rust `catch_unwind` can observe it. This is analogous to the reported bug class (GHSA-xvcg-2q82-r87j / CVE-2019-25055): a panic crossing an FFI-like boundary (here, the Rust↔JIT boundary introduced by Cairo-Native) is undefined behavior unless that boundary is explicitly compiled/configured to support Rust unwinding, or the panic is caught before crossing it.

The codebase's own design elsewhere shows the authors are aware of exactly this danger: `WorkerThread::_run_executor` explicitly notes "if a panic is not handled ... we abort the program" and wraps `worker_executor.run()` (which transitively includes native contract execution) in `catch_unwind` + `AbortIfPanic`, converting an otherwise-unsound unwind into a controlled `std::process::abort()` [6](#0-5) . However, this protection lives at the top-level block-execution/thread boundary, not immediately around the JIT call in `entry_point_execution.rs`. Any panic originating deep in a nested Cairo-Native call chain (nested `call_contract`/`library_call` syscalls, each spawning its own `NativeSyscallHandler` and re-entering `AotContractExecutor::run`) must unwind through multiple layers of natively-JIT-compiled stack frames before it ever reaches the single top-level `catch_unwind`. Additionally, the sequential (non-concurrent) execution path (`execute_txs_sequentially`) also relies only on the outer thread's `join()` (with `.expect(...)`, not `catch_unwind`) to propagate a panic [7](#0-6) , meaning there is no guaranteed intermediate catch point at all in that mode before the panic reaches native code boundaries.

### Impact Explanation
If unwinding through JIT-generated frames corrupts the stack or otherwise misbehaves (rather than being safely caught), the sequencer process can crash or exhibit undefined behavior while executing a single, attacker-submitted transaction. Because Cairo-Native is only used by nodes running with the `cairo_native` feature enabled, this creates a client-implementation-dependent execution divergence: VM-only nodes process the transaction (or safely revert on panic) while Cairo-Native nodes crash or behave unpredictably, which can partition the network's ability to reach consensus on the same block, or halt affected sequencer nodes entirely, preventing them from confirming new transactions.

### Likelihood Explanation
Reaching a panic requires finding a concrete calldata/entry-point sequence within blockifier's `NativeSyscallHandler` (or its trait implementation in the external `cairo-native` crate) that violates one of the internal `assert!`/`unwrap()`/`expect()` invariants gated behind attacker-reachable code paths (e.g., triggering `handle_error` twice on the same handler instance, or an unexpected native execution result). I could not fully verify from the indexed code whether such a double-invocation is currently reachable through Sierra-level Result/error propagation from a submitted transaction, since it depends on control flow inside the vendored `cairo-native` crate (not included in this index) as well as the exact set of internal invariants across `native/syscall_handler.rs` and `native/utils.rs`. This uncertainty affects confidence in a fully concrete PoC, but the structural weakness (JIT/FFI boundary with no local unwind containment) is independently confirmed by the source.

### Recommendation
- Wrap `compiled_class.executor.run(...)` in `native_entry_point_execution::execute_entry_point_call` with `std::panic::catch_unwind` (mirroring the `AbortIfPanic` + `catch_unwind` pattern already used in `worker_pool.rs`), and deliberately `std::process::abort()` (not attempt to recover) if a panic is caught, since safely resuming after unwinding through JIT frames cannot be guaranteed.
- Audit and remove/replace all `assert!`, `unwrap()`, and `expect()` calls in `crates/blockifier/src/execution/native/syscall_handler.rs` and `native/utils.rs` that are reachable via attacker-controlled Sierra/calldata paths, converting them into recoverable `Result`-based error handling instead of panics.
- Verify with the `cairo-native` upstream project whether `AotContractExecutor::run` and its generated code are compiled/configured to support unwinding (`-C panic=unwind` and proper landing pads) across the JIT boundary; if not, any panic originating in a syscall callback must never be allowed to propagate through JIT frames at all.

### Proof of Concept
A complete, concrete proof-of-concept transaction sequence could not be fully constructed from the indexed code alone, because it requires triggering a specific internal-invariant panic through `NativeSyscallHandler` (e.g., causing `handle_error` to be invoked twice on one handler instance) and confirming the exact unwind behavior of the vendored `cairo-native` JIT code, which is outside this repository's index. The structural absence of a `catch_unwind`/`AbortIfPanic` guard immediately around `compiled_class.executor.run(...)` in `crates/blockifier/src/execution/native/entry_point_execution.rs` (contrasted with the guarded pattern in `crates/blockifier/src/concurrency/worker_pool.rs`) is directly verifiable in the source, but a live crash reproduction requires access to a running Cairo-Native-enabled sequencer and the compiled `cairo-native` executor, which are beyond the scope of static code review here.

pub fn execute_entry_point_call(
    call: ExecutableCallEntryPoint,
    compiled_class: NativeCompiledClassV1,
    state: &mut dyn State,
    context: &mut EntryPointExecutionContext,
) -> Result<CallInfo, EntryPointExecutionError> {
    let entry_point = compiled_class
        .get_entry_point(&call.type_and_selector())
        .map_err(EntryPointExecutionError::from)?;

    let mut syscall_handler: NativeSyscallHandler<'_> =
        NativeSyscallHandler::new(call, state, context);

    let gas_costs = &syscall_handler.base.context.gas_costs();
    let builtin_costs = BuiltinCosts {
        // todo(rodrigo): Unsure of what value `const` means, but 1 is the right value.
        r#const: 1,
        pedersen: gas_costs.builtins.pedersen,
        bitwise: gas_costs.builtins.bitwise,
        ecop: gas_costs.builtins.ecop,
        poseidon: gas_costs.builtins.poseidon,
        add_mod: gas_costs.builtins.add_mod,
        mul_mod: gas_costs.builtins.mul_mod,
        blake: gas_costs.builtins.blake,
    };

    // Pre-charge entry point's initial budget to ensure sufficient gas for executing a minimal
    // entry point code. When redepositing is used, the entry point is aware of this pre-charge
    // and adjusts the gas counter accordingly if a smaller amount of gas is required.
    let initial_budget = syscall_handler.base.context.gas_costs().base.entry_point_initial_budget;
    let call_initial_gas = syscall_handler
        .base
        .call
        .initial_gas
        .checked_sub(initial_budget)
        .ok_or(PreExecutionError::InsufficientEntryPointGas)?;

    let execution_result = compiled_class.executor.run(
        entry_point.selector.0,
        &syscall_handler.base.call.calldata.0.clone(),
        call_initial_gas,
        Some(builtin_costs),
        &mut syscall_handler,
    );

    fn call_contract(
        &mut self,
        address: Felt,
        entry_point_selector: Felt,
        calldata: &[Felt],
        remaining_gas: &mut u64,
    ) -> SyscallResult<Vec<Felt>> {
        self.pre_execute_syscall(
            remaining_gas,
            self.gas_costs().syscalls.call_contract.base_syscall_cost(),
            SyscallSelector::CallContract,
        )?;

        let contract_address = ContractAddress::try_from(address)
            .map_err(|error| self.handle_error(remaining_gas, error.into()))?;

        let class_hash = self
            .base
            .state
            .get_class_hash_at(contract_address)
            .map_err(|e| self.handle_error(remaining_gas, e.into()))?;
        if self.base.context.execution_mode == ExecutionMode::Validate
            && self.base.call.storage_address != contract_address
        {
            let err = SyscallExecutorBaseError::InvalidSyscallInExecutionMode {
                syscall_name: "call_contract".to_string(),
                execution_mode: self.base.context.execution_mode,
            };
            return Err(self.handle_error(remaining_gas, err.into()));
        }
        let selector = EntryPointSelector(entry_point_selector);
        self.base
            .maybe_block_direct_execute_call(selector)
            .map_err(|e| self.handle_error(remaining_gas, e))?;

        let wrapper_calldata = Calldata(Arc::new(calldata.to_vec()));

        let entry_point = CallEntryPoint {
            class_hash: None,
            code_address: Some(contract_address),
            entry_point_type: EntryPointType::External,
            entry_point_selector: selector,
            calldata: wrapper_calldata,
            storage_address: contract_address,
            caller_address: self.base.call.storage_address,
            call_type: CallType::Call,
            initial_gas: *remaining_gas,
        };

    /// Runs a single worker executor.
    fn _run_executor(&self, worker_executor: &WorkerExecutor<S>) {
        if self.a_thread_panicked.load(Ordering::Acquire) {
            panic!("Another thread panicked. Aborting.");
        }

        // Making sure that the program will abort if a panic occurred while halting
        // the scheduler.
        let abort_guard = AbortIfPanic;
        // If a panic is not handled or the handling logic itself panics, then we
        // abort the program.
        let res = panic::catch_unwind(panic::AssertUnwindSafe(|| {
            worker_executor.run();
        }));
        if let Err(err) = res {
            // First, set the panic flag. This must be done before halting the scheduler.
            self.a_thread_panicked.store(true, Ordering::Release);

            // If the program panics here, the abort guard will exit the program.
            // In this case, no panic message will be logged. Add the cargo flag
            // --nocapture to log the panic message.

            worker_executor.scheduler.halt();
            abort_guard.release();
            panic::resume_unwind(err);
        }

        abort_guard.release();
    }

    pub fn execute_txs_sequentially(
        &mut self,
        txs: &[Transaction],
        execution_deadline: Option<Instant>,
    ) -> Vec<TransactionExecutorResult<TransactionExecutionOutput>> {
        #[cfg(not(feature = "cairo_native"))]
        return self.execute_txs_sequentially_inner(txs, execution_deadline);
        #[cfg(feature = "cairo_native")]
        {
            // TODO(meshi): find a way to access the contract class manager config from transaction
            // executor.
            let txs = txs.to_vec();
            std::thread::scope(|s| {
                std::thread::Builder::new()
                    // when running Cairo natively, the real stack is used and could get overflowed
                    // (unlike the VM where the stack is simulated in the heap as a memory segment).
                    //
                    // We pre-allocate the stack here, and not during Native execution (not trivial), so it
                    // needs to be big enough ahead.
                    // However, making it very big is wasteful (especially with multi-threading).
                    // So, the stack size should support calls with a reasonable gas limit, for extremely deep
                    // recursions to reach out-of-gas before hitting the bottom of the recursion.
                    //
                    // The gas upper bound is MAX_POSSIBLE_SIERRA_GAS, and sequencers must not raise it without
                    // adjusting the stack size.
                    .stack_size(self.config.stack_size)
                    .spawn_scoped(s, || self.execute_txs_sequentially_inner(&txs, execution_deadline))
                    .expect("Failed to spawn thread")
                    .join()
                    .expect("Failed to join thread.")
            })
        }
    }
