### Title
Undelegating resource balance in tiny (1-sun) increments truncates `transferUsage` to zero, letting an owner reclaim delegated TRX weight while stripping bandwidth/energy usage accounting from the receiver - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Summary
`UnDelegateResourceProcessor::execute` (and its non-VM twin `UnDelegateResourceActuator::execute`) computes the amount of consumed bandwidth/energy ("usage") that must be transferred back from the receiver to the owner when TRX delegation is revoked, using a proportional floor-division style formula. Because the minimum `unDelegateBalance` allowed is a single sun (no `TRX_PRECISION` floor, unlike `DelegateResourceProcessor`), an attacker can split an undelegate operation into many 1-sun transactions, each of which independently truncates `transferUsage` to `0`, while the exact TRX/frozen-balance amount is still moved in full. This is the same rounding-truncation bug class as the reported Sablier `wstETH`/share issue: a proportional "backing" value is computed via integer division and, for small enough increments relative to the balance, always rounds to zero, decoupling the accounting of consumed resource from the balance that was supposed to carry it.

### Finding Description
In `UnDelegateResourceProcessor.execute` (`actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java:100-156`), for BANDWIDTH:

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * dynamicStore.getTotalNetLimit() / repo.getTotalNetWeight());
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage, VMConfig.disableJavaLangMath());
``` [1](#0-0) 

and the analogous logic in the classic actuator: [2](#0-1) 

`transferUsage` is used only when `> 0`:
```java
if (Objects.nonNull(receiverCapsule) && transferUsage > 0) {
  processor.unDelegateIncrease(ownerCapsule, receiverCapsule, transferUsage, BANDWIDTH, now);
}
``` [3](#0-2) 

Whenever `unDelegateBalance` is small relative to `receiverCapsule.getAllFrozenBalanceForBandwidth()` (or `...ForEnergy`), `transferUsage` truncates to `0`. Critically, `UnDelegateResourceProcessor.validate` (the TVM native-contract entrypoint invoked by any smart contract) only enforces `unDelegateBalance > 0`, with no minimum of `TRX_PRECISION` (1 TRX):
```java
long unDelegateBalance = param.getUnDelegateBalance();
if (unDelegateBalance <= 0) {
  throw new ContractValidateException("unDelegateBalance must be more than 0 TRX");
}
``` [4](#0-3) 

This is the mirror image of `DelegateResourceProcessor.validate`, which explicitly requires `delegateBalance >= TRX_PRECISION`: [5](#0-4) 

So while delegating a minimum of 1 TRX at a time is enforced, undelegating in 1-sun increments is not, which is exactly the asymmetry that enables the exploit: an owner (or a coordinated owner/receiver pair, since delegation is opt-in and the receiver-side effects benefit the owner) can call `UnDelegateResourceContract` (or its TVM equivalent through a contract) repeatedly with `unDelegateBalance = 1` sun, up to the full delegated amount. Each call:
- Fully restores the sun of TRX/frozen-balance weight to the owner (`ownerCapsule.addFrozenBalanceForBandwidthV2(unDelegateBalance)`), exactly like normal.
- Computes `transferUsage = 0` due to floor-division truncation, so `unDelegateIncrease` is skipped — the receiver's already-consumed `netUsage`/`energyUsage` is never decremented and never transferred back to the owner.

Net effect after N such calls: the owner recovers 100% of the previously delegated TRX weight (and the associated bandwidth/energy capacity) while the receiver's `netUsage`/`energyUsage` remains exactly what it was before any undelegation — none of the usage debt that should have been proportionally clawed back from the receiver (per the intended accounting invariant enforced when done in one bulk call) is ever moved. This corrupts the resource-usage accounting invariant between owner and receiver: a bulk undelegate of the full balance yields a materially different (correct) `transferUsage` than the same total amount split into 1-sun increments (always `0`), so the observable protocol state depends on how a legitimate value is partitioned across transactions — exactly the rounding-truncation bug class described in the report.

### Impact Explanation
This breaks the intended proportional resource-accounting invariant of `DelegateResource`/`UnDelegateResource`, similar in kind to the reported issue (value backing silently detached from the balance meant to carry it). The receiver ends up retaining usage debt with no corresponding delegated balance backing it (their effective bandwidth/energy headroom can go negative/degraded relative to what the protocol intends), while the owner is able to strip back the full frozen weight without ever paying the usage-transfer cost that a single bulk call would have imposed. This is an accounting-corruption / resource-metering integrity issue reachable purely through normal broadcast transactions or smart-contract calls (`UnDelegateResourceContract` / TVM `unDelegateResource` native contract), requiring no privileged role, leaked key, or malicious peer — satisfying the "unprivileged, RPC/transaction reachable" requirement. However, unlike the original wstETH report, the value affected here is transient, self-decaying resource-usage state (which naturally resets over the bandwidth/energy window) rather than a durable fungible asset such as TRX or TRC10 tokens; TRX/frozen-balance movement itself is tracked exactly (no floor division), so no direct loss of TRX/tokens occurs. The impact is therefore limited to temporary resource-metering skew/DoS-adjacent effects rather than direct fund loss.

### Likelihood Explanation
Likelihood is moderate: the missing lower bound on `unDelegateBalance` (compared to the explicit `>= TRX_PRECISION` check on `DelegateResource`) makes the 1-sun-increment path trivially reachable by any account that has delegated resource to another account (including one it controls itself, or a cooperating receiver), at the cost of transaction fees/bandwidth for issuing many small transactions. No special permissions or race conditions are needed.

### Recommendation
- Enforce a minimum `unDelegateBalance` of `TRX_PRECISION` (mirroring `DelegateResourceProcessor`'s `delegateBalance >= TRX_PRECISION` check) in both `UnDelegateResourceProcessor.validate` and `UnDelegateResourceActuator.validate`.
- Alternatively/additionally, compute `transferUsage` (and `unDelegateMaxUsage`) using integer/BigInteger arithmetic with explicit rounding semantics that are invariant to how a bulk amount is split into multiple partial undelegations (e.g., accumulate remainder, or require `transferUsage` rounding to be ceiling-based so partial undelegations can never collectively transfer less usage than one bulk call would).
- Add a regression test performing a full undelegate as many 1-sun calls versus one bulk call and assert the receiver's final `netUsage`/`energyUsage` and owner's final usage/frozen-balance are identical in both paths.

### Proof of Concept
Conceptual reproduction using the existing actuator test harness (`framework/src/test/java/org/tron/core/actuator/UnDelegateResourceActuatorTest.java`), analogous to `testPartialUnDelegateForBandwidth` [6](#0-5) :
1. Delegate a large bandwidth balance from Owner to Receiver, and set `Receiver.netUsage` to a large nonzero value (as in `testUnDelegateForBandwidth`) [7](#0-6) .
2. Path A (bulk): call `UnDelegateResourceActuator.execute` once with the entire `delegateBalance`; observe `transferUsage > 0`, and both owner's and receiver's `netUsage` change accordingly.
3. Path B (increments): reset state, then call `UnDelegateResourceActuator.execute` repeatedly with `unDelegateBalance = 1` sun until the full `delegateBalance` has been undelegated.
4. Compare final state: in Path B, `ownerCapsule.getFrozenBalanceForBandwidthV2()`/`getNetUsage()` and `receiverCapsule.getNetUsage()` will differ from Path A — specifically, `receiverCapsule.getNetUsage()` remains unchanged (never decremented) in Path B because every call's `transferUsage` floor-divided to `0`, whereas Path A properly transfers a proportional share of usage back to the owner. This demonstrates that splitting the operation into small increments changes the resulting on-chain accounting versus doing it as a single call, confirming the rounding-truncation defect.
