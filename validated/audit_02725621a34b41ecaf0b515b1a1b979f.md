### Title
Failed `INBOUND_REVERT` outbounds permanently strand user funds instead of re-crediting PRC20 on Push Chain - (File: x/uexecutor/keeper/outbound.go)

### Summary
When an inbound (`GAS`, `GAS_AND_PAYLOAD`, `FUNDS`, or `FUNDS_AND_PAYLOAD`) fails to execute on Push Chain, `buildRevertOutbound` creates a compensating outbound tagged `TxType_INBOUND_REVERT` whose job is to return the user's original funds back to the source chain. If Universal Validators later vote that *this* outbound itself failed on the destination (source) chain, `handleFailedOutbound` does not re-credit the user anywhere — it only marks the outbound `REVERTED` and attempts a gas refund. The user's funds are neither delivered on the source chain nor re-minted on Push Chain, resulting in a silent, permanent loss with no automated recovery path.

### Finding Description
`buildRevertOutbound` always constructs the compensating outbound with `TxType: types.TxType_INBOUND_REVERT`, regardless of the failing inbound's original type: [1](#0-0) 

That outbound is attached and voted on through the normal `MsgVoteOutbound` → `FinalizeOutbound` path: [2](#0-1) 

`handleFailedOutbound` only re-mints PRC20 back to the recipient when `outbound.TxType` is `FUNDS`, `GAS_AND_PAYLOAD`, or `FUNDS_AND_PAYLOAD`: [3](#0-2) 

`TxType_INBOUND_REVERT` is not in that list, so for a revert outbound the compensating branch is skipped entirely; the code falls straight through to marking `Status_REVERTED` and only runs `applyGasRefund` (which only refunds the *excess gas fee*, not the principal/bridged amount): [4](#0-3) 

Per the module's own `TxType` documentation, `INBOUND_REVERT` has no defined outbound semantics ("—"), confirming this path was never given fund-recovery handling: [5](#0-4) 

Once `outbound_status` becomes `REVERTED`, there is no further automated or admin-triggered code path that re-attempts delivery or re-mints the PRC20 — `Status_REVERTED` is treated as terminal (unlike `Status_ABORTED`, which the README explicitly documents as requiring manual/governance intervention). `RESCUE_FUNDS` is a separate, admin-initiated flow and does not automatically trigger for a failed `INBOUND_REVERT`.

### Impact Explanation
This is a permanent, unauthorized loss of user funds reachable purely by ordinary, unprivileged flows: any inbound that fails on Push Chain (e.g., swap slippage exceeded, UEA deploy failure, EVM revert, insufficient liquidity) triggers an `INBOUND_REVERT` outbound meant to return the user's original bridged asset. If that specific outbound then fails to land on the source chain — which can happen for entirely benign, non-adversarial reasons (destination gas spike, temporarily paused gateway, nonce/relaying issue, contract-level revert) — honest, correctly-functioning validators will vote `success=false` and the protocol will mark the outbound `REVERTED` without ever crediting the user on Push Chain. The user's funds vanish from both chains with no recovery mechanism, satisfying the "permanent loss/freezing of user funds" allowed-impact criterion, and is a direct native analog of the WatchPug finding (unrefunded leftover balance left stranded in the contract/module with no return path).

### Likelihood Explanation
The trigger is not adversarial — it requires only that an already-rare-but-realistic revert-outbound execution fails on the destination chain, which can happen from ordinary conditions (temporary chain congestion, gas estimation drift, external gateway pause) with no attacker action needed. Given that `handleFailedOutbound` is the sole finalize-time fund-recovery mechanism and it structurally excludes `INBOUND_REVERT`, every failed revert-outbound is affected, making this a systematic gap rather than an edge case.

### Recommendation
Include `types.TxType_INBOUND_REVERT` (and, if applicable, `TxType_RESCUE_FUNDS`) in the re-mint condition inside `handleFailedOutbound` so that a failed revert-outbound re-credits the user's PRC20 balance on Push Chain via `CallPRC20Deposit`, mirroring the existing `FUNDS`/`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` handling. Alternatively, if `INBOUND_REVERT` intentionally represents "outbound of the original locked asset" rather than a PRC20-backed balance, add an explicit compensating action (e.g., mark for `RESCUE_FUNDS` outbound generation automatically, not just via manual admin trigger) so no code path leaves `Status_REVERTED` as a fund-losing terminal state.

### Proof of Concept
1. A user submits a `GAS` inbound; `ExecuteInboundGas` calls `CallPRC20DepositAutoSwap`, which fails (e.g., `minPCOut` slippage check fails at the AMM). [6](#0-5) 
2. `shouldRevert=true` triggers `buildRevertOutbound`, creating an `OutboundTx` with `TxType_INBOUND_REVERT`, `Status_PENDING`, instructing UVs to return the original bridged amount to the sender on the source chain. [7](#0-6) 
3. UVs sign/broadcast the revert outbound via TSS; it fails on the source chain (e.g., reverts due to gas or contract state) and honest UVs vote `success=false` via `MsgVoteOutbound`.
4. `FinalizeOutbound` → `handleFailedOutbound` runs; since `outbound.TxType == TxType_INBOUND_REVERT` is not in `{FUNDS, GAS_AND_PAYLOAD, FUNDS_AND_PAYLOAD}`, the fund re-mint branch is skipped, and the outbound is marked `Status_REVERTED` with only a gas-fee refund attempted.
5. The user's original funds are never returned on the source chain (execution failed) and never re-minted on Push Chain — permanently lost, with no further automated recovery.

Note: I was unable to fully trace whether `universalClient/` or an off-chain relayer/monitoring component independently detects `Status_REVERTED` `INBOUND_REVERT` outbounds and files a manual `RESCUE_FUNDS` request; if such a manual/governance-driven safety net exists, this would reduce (but likely not eliminate, given "manual intervention" is out of scope per the report's threat model of unprivileged reachability) the severity of this finding.

func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}

### `TxType` — what flavour of crosschain action

The same enum is used on both `Inbound` and `OutboundTx` to describe what the message is for.

| `TxType` | Inbound semantics | Outbound semantics |
|---|---|---|
| `GAS` | User pre-paid gas on the source chain. Mints PC to the recipient as a gas top-up. | Refund of unused gas back to a source chain. |
| `GAS_AND_PAYLOAD` | Gas top-up + executes a payload through the recipient's UEA in the same Push Chain tx. | Same combo on the destination side. |
| `FUNDS` | Pure synthetic transfer — mints PRC20 representation of an external token. | Pure transfer of a PRC20 back out of Push Chain. |
| `FUNDS_AND_PAYLOAD` | Mints funds + runs a payload (e.g. deposit + DEX swap atomically). | Funds delivery with a destination-side call. |
| `PAYLOAD` | Pure payload execution, no value movement. | Pure call on the destination chain. |
| `INBOUND_REVERT` | Reverts a previously-executed inbound (returns funds to the source-chain sender). | — |
| `RESCUE_FUNDS` | Admin-driven rescue path for stuck funds. | Outbound that delivers the rescue. |
