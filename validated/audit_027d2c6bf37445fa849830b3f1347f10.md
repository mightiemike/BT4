## Title
Fixed-gas cross-contract callback in the NEAR Wallet Contract can permanently lock `has_in_flight_tx`, freezing the account's funds and access — ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR wallet contract (an eth-implicit "meta-transaction" account contract that lets an Ethereum-style key control a NEAR account) serializes all user activity through a single in-flight lock, `has_in_flight_tx`. The lock is cleared at the *start* of each async callback and only re-armed if the callback fully finishes without panicking. Several of these callbacks attach a small, hardcoded static gas budget to schedule a chained cross-contract call and process an untrusted-size response from an attacker-selectable NEP-141 token contract. If that fixed budget is insufficient — analogous to the immutable, too-small VRF callback gas limit in the reported Solidity issue — the callback panics with `GasExceeded`/`GasLimitExceeded`, all of that receipt's state writes are discarded by NEAR's atomic per-receipt rollback, and the *previous* persisted value of `has_in_flight_tx` (`true`) survives. From that point on `rlp_execute` unconditionally rejects every future call, permanently freezing the account.

### Finding Description
`WalletContract` guards re-entrancy with a boolean invariant documented at [1](#0-0) : `has_in_flight_tx` must be `true` while a promise chain is pending and `false` otherwise. `rlp_execute` refuses to start a new transaction whenever this flag is `true`: [2](#0-1) .

Every private callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) clears the flag as its very first statement, then does further work (deserializing an untrusted promise result, building and scheduling a follow-up promise) before setting the flag back to `true` right before returning `PromiseOrValue::Promise`, e.g.: [3](#0-2) [4](#0-3) 

The promise chain for an emulated ERC‑20 transfer attaches only a small, compile-time-fixed static gas budget for this callback (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, effectively `5 + 5 + 5` Tgas plus the user's inner action gas) that the *caller cannot increase*, because it is computed by the contract itself, not supplied per-transaction: [5](#0-4)  and [6](#0-5) . The `token_id` (`target`) of this ERC‑20 emulation is attacker-selectable — it is whatever NEAR account the RLP-encoded, user-signed transaction names as the ERC‑20 contract — so an attacker can point it at their own contract and have `storage_balance_of` return an arbitrarily large/expensive-to-parse payload, inflating the gas cost of `serde_json::from_slice` inside `nep_141_storage_balance_callback` past the fixed budget.

This is architecturally identical to the reported bug class: a callback that must complete bookkeeping/state-transition logic runs under a **hardcoded gas ceiling that is not sized for its worst-case input**, and if it is exceeded the callback aborts.

The critical divergence from a "just fails harmlessly" case is nearcore's per-receipt atomicity: `runtime/runtime/AGENTS.md` states that "when a receipt fails, its state changes are rolled back using TrieUpdate" [7](#0-6) , and the architecture doc confirms "the state update is only finalized at the end of `apply`. During all intermediate steps state changes can be reverted." . Consequently, when the callback panics with `GasExceeded` after having already executed `self.has_in_flight_tx = false`, that write (and every subsequent write in the same execution) is discarded, and the persisted value reverts to whatever it was before this receipt started — which is `true`, because the previous successful call (`rlp_execute`/prior callback) is what set it and scheduled this callback: [8](#0-7) .

Unlike a normal failed cross-contract call in NEAR (where the caller simply learns of the failure and can retry with different parameters), here the retry surface does not exist: a *single* attacker-triggered out-of-gas failure in this specific callback leaves `has_in_flight_tx == true` permanently, and there is no admin/owner method anywhere in the contract to reset it (the only writers of the flag are `rlp_execute` and the callbacks themselves, all gated behind the very flag that is now stuck).

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true`, `rlp_execute` — the sole entry point for every action on this account (transfers, function calls, key management) — unconditionally returns an error for all future calls: [9](#0-8) . This permanently freezes any NEAR balance and any assets/authority controlled by this wallet-contract account, with no on-chain recovery path (matches the "permanently frozen funds" and "transaction-triggered halt" impact categories: a single crafted transaction irreversibly disables the account). This is a High-severity, single-transaction-triggerable denial of service of the entire contract instance, mirroring the reported Infiltration.sol issue where a fixed VRF callback gas cap could deadlock the whole game.

### Likelihood Explanation
The trigger requires only a single unprivileged, user-signed RLP transaction naming an ERC‑20 `target` contract that the attacker controls and that returns an oversized/expensive `storage_balance_of` response — no validator, relayer, or node compromise is needed, and no repeated retries are required (a single failure is sufficient, unlike the original report which needed accumulation over many rounds). The static callback gas budget is a compile-time constant unrelated to the size of the token contract's response, so the condition for triggering the bug is entirely attacker-controlled and deterministic.

### Recommendation
- Do not hard-code a fixed static gas amount for callbacks that must parse externally-controlled, unbounded-size promise results; size the budget based on a strict upper bound on expected/allowed response size, or bound/validate the size of `promise_result` data before deserializing it.
- Re-order the state mutation so `has_in_flight_tx` is only cleared after the follow-up promise (or terminal response) has been successfully constructed, or use a `try`/guard pattern (e.g., a panic hook or `#[private]` wrapper that guarantees `has_in_flight_tx` is reset even on early return paths) so a mid-callback abort cannot leave the flag in the "locked" state.
- Provide a supervised recovery/reset mechanism (e.g., timeout-based unlock, or an owner-authorized reset callable only by the signer that controls the wallet) so a stuck flag does not permanently brick the account.

### Proof of Concept
1. Attacker deploys a NEP‑141-like contract `evil.token.near` whose `storage_balance_of` method returns an extremely large/complex JSON payload (e.g., many nested/duplicated fields) sized to make `serde_json::from_slice` deserialization cost exceed the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget once combined with the follow-up promise/action-base gas costs charged in `nep_141_storage_balance_callback`.
2. Attacker (who is also the eth-key holder of a NEAR wallet-contract account `victim.near`, or convinces/relays for a victim who signs with that eth key) submits an RLP-encoded "ERC‑20 transfer" transaction to `rlp_execute` on `victim.near` with `target = evil.token.near`.
3. `inner_rlp_execute` builds the promise chain in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-458`, calling `evil.token.near::storage_balance_of` then `.then(ext.nep_141_storage_balance_callback(...))` with the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`. `has_in_flight_tx` is set to `true` and persisted.
4. `evil.token.near::storage_balance_of` returns the oversized payload; `nep_141_storage_balance_callback` starts, sets `self.has_in_flight_tx = false`, then attempts `serde_json::from_slice(&value)` on the huge payload and exceeds its attached gas, causing a `GasExceeded`/`GasLimitExceeded` panic.
5. Per NEAR's per-receipt atomicity (`runtime/runtime/AGENTS.md:64`), all state writes from this callback receipt — including `self.has_in_flight_tx = false` — are rolled back; the persisted value remains `true` from step 3.
6. All subsequent calls to `rlp_execute` on `victim.near` now immediately fail with "transaction already in progress", permanently, with no recovery function available in the contract.
