### Title
`sanitizeHost` crashes with uncaught `TypeError` instead of `InvalidHostError` when base64 `host` decodes to a string containing forbidden URL host code points - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`sanitizeHost` validates the `host` parameter by base64-decoding it via `decodeHost` (`atob`) and passing the result directly into `new URL('https://' + decoded)` with no `try/catch`. Because `atob` produces an arbitrary binary string, an attacker can craft a base64 payload that decodes to bytes forbidden in a URL host (e.g. `NUL`, space, `<`, `>`, backslash), causing the WHATWG URL parser to throw a raw `TypeError` that propagates out of `sanitizeHost` uncaught, instead of being converted to the library's graceful `InvalidHostError`.

### Finding Description
`sanitizeHost` (`packages/apps/shopify-api/lib/utils/shop-validator.ts:52-91`) does:
```
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
  ...
}
``` [1](#0-0) 

`decodeHost` is a thin wrapper around `atob`: [2](#0-1) 

The `base64regex` (`/^[0-9a-zA-Z+/]+={0,2}$/`) only checks that the input is valid base64 *charset*; it places no constraint on what the *decoded bytes* are. `atob` will happily decode base64 into a "binary string" containing any byte value 0–255, including `NUL` (`\u0000`), space, `<`, `>`, `\`, `^`, `|`, `#`, `?`, `@`, `[`, `]` — all of which are WHATWG "forbidden host code points". When such a byte lands in the host portion of `https://${decoded}`, `new URL()` throws a `TypeError: Invalid URL` synchronously. This throw is not wrapped in a `try/catch` anywhere in `sanitizeHost`, so it propagates straight out of the function — bypassing the intended `InvalidHostError` handling that exists for the `!sanitizedHost && throwOnInvalid` branch further down (line 85-87).

This function is reachable with fully attacker-controlled input (the `host` query parameter) from multiple unauthenticated entry points that precede any session/OAuth validation:
- `buildEmbeddedAppUrl` calls `sanitizeHost(config)(host, true)` with no surrounding try/catch: [3](#0-2) 
- `shopify-app-express`'s `redirectToAuth` → `clientSideRedirect` calls `api.utils.sanitizeHost(req.query.host as string)` directly against the attacker-supplied query string, with no try/catch around it: [4](#0-3) 
- `shopify-app-remix`/`shopify-app-react-router`'s `validateShopAndHostParams`, invoked at the start of `authenticate.admin()` before any session-token or OAuth verification, calls `api.utils.sanitizeHost(url.searchParams.get('host')!)` unguarded: [5](#0-4) 

None of these call sites, nor `sanitizeHost` itself, catch the `TypeError` that `new URL()` can throw. The existing unit tests (`shop-validator.test.ts`) only exercise base64-syntax-invalid or domain-mismatch cases, never a payload that decodes to forbidden host characters, so this gap is untested. [6](#0-5) 

### Impact Explanation
An unauthenticated request to any app route that validates the `host` param before authentication (admin embed bootstrap, `redirectToAuth`'s client-side-redirect branch, or `authenticate.admin()`'s pre-auth `validateShopAndHostParams`) with a crafted `host=` value causes an uncaught exception in that request path. Depending on the host framework's error handling, this manifests as an unhandled 500 error per request (denial of service against that specific request/route) rather than crashing the whole process, since Express/Remix/React Router typically catch synchronous throws in route handlers into a 500 response. This matches the audit's target impact class of "DoS in the auth bootstrap flow that precedes token exchange," but the severity is bounded to per-request failure (unhandled error response) rather than a full-process crash or resource-exhaustion DoS — there is no evidence in the codebase of unbounded memory/CPU consumption, and the "10MB of null bytes" framing in the question does not by itself amplify impact beyond triggering the parse exception faster than would a single forbidden byte.

### Likelihood Explanation
No preconditions or privileges are required: the attacker only needs to send a single HTTP request with a crafted `host` query parameter to a public app route, e.g. the admin auth-begin path or the embedded-app bootstrap path. The base64 charset check does not filter the resulting host content, so a one-line payload triggers it deterministically and repeatably.

### Recommendation
Wrap the `new URL(...)` call in `sanitizeHost` in a `try/catch`, treating any parse failure the same as an invalid host (set `sanitizedHost = null` and fall through to the existing `throwOnInvalid` → `InvalidHostError` logic), e.g.:
```ts
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  try {
    const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
    ...
  } catch {
    sanitizedHost = null;
  }
}
```
Also add a regression test decoding to a string containing `\u0000` or other forbidden host code points and assert `sanitizeHost(...)` returns `null` / throws `InvalidHostError` (not a raw `TypeError`).

### Proof of Concept
```ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';
import {InvalidHostError} from '../../error';

test('sanitizeHost should not throw a raw TypeError on malformed decoded host', () => {
  const shopify = shopifyApi(testConfig());

  // decodes to "myshopify.com/admin\u0000" -> NUL is a forbidden host code point
  const malformedHost = Buffer.from(
    'myshopify.com/admin\u0000',
    'binary',
  ).toString('base64');

  // Current behavior: throws a raw TypeError ("Invalid URL") from `new URL()`,
  // NOT the expected InvalidHostError -> test fails against current code.
  expect(() => shopify.utils.sanitizeHost(malformedHost, true)).toThrow(
    InvalidHostError,
  );
});
```
Running this against the current implementation throws `TypeError: Invalid URL` instead of `InvalidHostError`, demonstrating the uncaught-exception path.
