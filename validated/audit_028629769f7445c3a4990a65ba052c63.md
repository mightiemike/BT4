### Title
Miner-signature (ECDSA) malleability makes `NakamotoBlockHeader::signer_signature_hash()` / `block_id()` non-canonical for an otherwise-identical block - (File: `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
`NakamotoBlockHeader::signer_signature_hash_inner()` commits, byte-for-byte, to the raw `miner_signature` field rather than to a canonical representation of "the miner authorized this content." Because miner signatures are explicitly allowed to use the non-canonical (high-S) ECDSA encoding, the same logically-identical block can be re-serialized by its own miner into two different byte strings that both recover to the correct miner public key, yet hash to two different `signer_signature_hash`/`block_id()` values. This breaks the intended equality "one block, one identity" for signer thresholding, mirroring the SAML/XML wrapping bug class where data can be mutated without invalidating the signature that is supposed to bind it.

### Finding Description
`signer_signature_hash_inner()` explicitly folds the raw `self.miner_signature` bytes into the digest that signers sign and that becomes `block_hash()`/`block_id()`: [1](#0-0) 

`block_hash()`/`block_id()` are derived directly from this same digest: [2](#0-1) 

Miner-signature validation deliberately does not enforce canonical (low-S) signatures — it only checks that the signature recovers to the expected miner pubkey hash, and the signer chainstate test suite explicitly documents and asserts that high-S miner signatures are accepted: [3](#0-2) 

This is corroborated at the header level: `verify_signer_signatures` recovers signer pubkeys with `recover_to_pubkey_without_validating_low_s`, and a dedicated unit test proves a *signer* signature with negated-S is accepted: [4](#0-3) [5](#0-4) 

Because ECDSA signatures are malleable under `(r, s) ↔ (r, n-s)` (with a corresponding flip in the implicit recovery id), the *miner* — who already possesses the tenure's own signing key and needs no other party's key or any majority — can take a single legitimately-produced `miner_signature` and derive a second, distinct byte encoding of it (`MessageSignature::with_negated_s()`, used identically in the test above) that:
- still recovers to the same miner public key / address (`check_proposal`'s `PubkeyHashMismatch`/`recover_miner_pk` checks pass identically for both), and
- still satisfies `miner_signature_hash()` unchanged (that hash excludes the signature itself), but
- produces a **different** `signer_signature_hash()` / `block_hash()` / `block_id()` because those digests include the raw `miner_signature` bytes.

The signer/proposal-evaluation path (`GlobalStateView::check_proposal`) validates content equality (`consensus_hash`, `pox_treatment`, miner pubkey hash) but has no notion that two proposals with different `signer_signature_hash` values are the *same* underlying block: [6](#0-5) 

Downstream, both the stackerdb-listener aggregation and the v0 signer's `store_and_process_block_signature` key all signature bookkeeping (`gathered_signatures`, `total_weight_approved`, `block_lookup_by_reward_cycle`) strictly by this same `signer_signature_hash`: [7](#0-6) [8](#0-7) 

So two byte-distinct proposals that are semantically the exact same block (same txs, same `tx_merkle_root`, `state_index_root`, `parent_block_id`, `consensus_hash`, `chain_length`) are tracked, validated, and tallied as two completely unrelated blocks.

### Impact Explanation
A single miner (the current tenure winner — no majority or third-party key required) can broadcast two variants of "the same" block that differ only in the malleated encoding of their own `miner_signature`. Each variant gets its own independent `signer_signature_hash`/`block_id`, its own independent 70%-of-weight signature tally, and — because `check_proposal` treats each as fully valid — signers evaluating either variant in isolation have no way to detect that it duplicates another already-seen proposal for the same tenure slot. This can produce two distinct, independently-thresholded, fully-signed `NakamotoBlock`s for the same logical tenure position, each with a different `block_id`. Whichever variant a given node observes crossing threshold first becomes that node's chain tip, so different honest nodes can adopt different `block_id`s for the same tenure — at minimum a temporary tip disagreement, and under favorable signer-set partitioning, an actual chain split (both variants independently reaching quorum). This matches the "temporary tip disagreement" / "committed state root two nodes disagree on" class of High/Critical impact described in scope.

### Likelihood Explanation
Triggering this requires only the block-producing miner's own key (which they already hold) and standard ECDSA signature malleability (negating `s`), which is explicitly permitted and unit-tested as accepted behavior for miner signatures. No signer collusion, no majority, and no other party's key is needed — only routing/timing control over which signers see which byte-variant of the proposal, which a miner already has via `.miners`/StackerDB message delivery.

### Recommendation
Canonicalize `miner_signature` (and any other signature fields folded into `signer_signature_hash_inner`) before hashing — e.g., normalize to low-S form prior to computing `signer_signature_hash()`/`block_hash()`, or exclude the raw signature bytes from the hash and instead bind to the recovered miner public key/address. Additionally, have signer-side proposal deduplication key on content-equality (e.g., `(consensus_hash, chain_length, tx_merkle_root, state_index_root, parent_block_id)`) rather than solely on `signer_signature_hash`, so that two byte-variants of the same block cannot both be tallied independently.

### Proof of Concept
1. Miner produces a normal Nakamoto block and signs it: `header.sign_miner(&miner_sk)`, giving `miner_signature = sig`.
2. Miner computes `sig2 = sig.with_negated_s()` (as exercised in `check_proposal_accepts_high_s_miner_sign`, `stacks-signer/src/chainstate/tests/v2.rs:238-255`) and creates a second header identical in every field except `miner_signature = sig2`.
3. Both headers pass `GlobalStateView::check_proposal`'s miner-pubkey-hash check (`recover_miner_pk` recovers the same address for both).
4. `header.signer_signature_hash()` (`stackslib/src/chainstate/nakamoto/mod.rs:1028-1045`) differs between the two headers because it hashes the raw `miner_signature` bytes, yielding two distinct `block_id()`s for the same logical block.
5. The miner sends variant 1 to one subset of signers and variant 2 to another subset via `.miners` StackerDB; each subset independently tallies weight against its own `signer_signature_hash` (`stacks-signer/src/v0/signer.rs:2442-2461`, `stacks-node/src/nakamoto_node/stackerdb_listener.rs:400-410`), with no cross-check that the two hashes represent the same content.

    fn signer_signature_hash_inner(&self) -> Result<Sha512Trunc256Sum, CodecError> {
        let mut hasher = Sha512_256::new();
        let fd = &mut hasher;
        write_next(fd, &self.version)?;
        write_next(fd, &self.chain_length)?;
        write_next(fd, &self.burn_spent)?;
        write_next(fd, &self.consensus_hash)?;
