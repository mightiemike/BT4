## Analysis

The Lens Protocol bug class — referencing mutable on-chain state purely by a **sequentially-assigned integer ID** rather than by content — has a direct structural analog in java-tron's TRC10 Exchange (Bancor-style AMM) module.

### Title
Exchange transactions identify pools solely by sequential `exchange_id`, making them vulnerable to fork-switch/reorg pool reassignment - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeCreateActuator` assigns each newly created TRC10 exchange pool an ID by incrementing a global counter (`dynamicStore.getLatestExchangeNum() + 1`), independent of the pool's actual contents (token pair). `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all look up the target pool exclusively by this numeric `exchange_id`, with no binding to the token pair the caller expects. Because java-tron's `Manager` supports fork switching (`switchFork`), a short reorg that drops an `ExchangeCreateContract` transaction and replaces it with a different one (e.g., from a different, concurrently-eligible sender) can cause the same `exchange_id` to become bound to a completely different token pair on the new fork. A pending `ExchangeTransactionContract`/`ExchangeInjectContract` that only references `exchange_id` will then be re-applied against the wrong pool once the fork resolves.

### Finding Description
In `ExchangeCreateActuator.execute`, the pool ID is derived purely from a monotonically increasing counter: [1](#0-0) 

This ID has no cryptographic or content-based relationship to the `firstTokenID`/`secondTokenID` pair being created — it is purely a function of transaction ordering, exactly like the Lens `publicationId` in the original report.

Every subsequent operation on that pool — trading (`ExchangeTransactionActuator`), adding liquidity (`ExchangeInjectActuator`), and removing liquidity (`ExchangeWithdrawActuator`) — resolves the pool solely via this numeric ID: [2](#0-1) [3](#0-2) 

No part of validation or execution checks that `firstTokenID`/`secondTokenID` (or any content hash of the pool) matches what the caller expected when constructing the transaction — the caller is expected to trust that `exchange_id` N still refers to the same token pair it referred to when they broadcast their transaction.

java-tron supports chain reorganizations via fork switching, confirming that block-ordering changes after a transaction is broadcast are a real, handled scenario in this codebase: [4](#0-3) 
(`switchFork` is implemented and exercised in `ManagerTest`/`ManagerMockTest`).

Scenario (directly mirroring the Lens report):
1. Block N: Alice's `ExchangeCreateContract` confirms, creating pool `exchange_id = 5` for TRX/TokenA.
2. Block N+1: Bob broadcasts `ExchangeTransactionContract` with `exchange_id = 5`, buying TokenA with TRX, expecting Alice's pool.
3. Block N+2: Carol's `ExchangeCreateContract` (for TRX/TokenB) is also broadcast around the same height.
4. A short fork switch occurs: the block containing Alice's create-exchange transaction is replaced by one where Carol's create-exchange transaction is included first at the same sequence position, so `exchange_id = 5` is now bound to TRX/TokenB instead of TRX/TokenA.
5. Bob's already-signed `ExchangeTransactionContract` (still referencing `exchange_id = 5`, `tokenId = TokenA`) either fails validation (if `tokenId` no longer matches the pool's pair) or — for withdraw/inject flows without a token-id check on the same object — settles against a totally different liquidity pool than Bob intended, causing him to receive/pay against unrelated token reserves.

### Impact Explanation
If the exchange ID a user's pending trade/inject/withdraw transaction references becomes rebound to a different token pair due to a fork switch, users can have TRX or TRC10 tokens moved into/out of the wrong pool, or have transactions unexpectedly fail/succeed against unintended reserves — a direct settlement/accounting-divergence impact consistent with loss of funds, similar to the "loss of funds due to paying fees to the wrong recipient" impact described in the original Lens finding.

### Likelihood Explanation
java-tron's DPoS consensus is subject to short-range fork switches (`switchFork` in `Manager.java`), and multiple actors can broadcast `ExchangeCreateContract` transactions competing for adjacent block slots, satisfying the same "multiple addresses can create the referenced object" condition that the Lens judge accepted as valid (delegated executors/owners analog = any account capable of broadcasting a create-exchange transaction). This makes the reordering scenario plausible under real-world fork-switch conditions, though it requires a fork switch to coincide precisely with contention over exchange creation ordering, which narrows the practical window.

### Recommendation
Bind exchange-referencing operations (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) to the pool's content, not just its numeric ID — e.g., require the caller to also supply/verify the expected `first_token_id`/`second_token_id` (already partially enforced for `tokenId` in `ExchangeTransactionActuator.doValidate`, but not for the *pair* as a whole) and reject execution if the pool's current token pair does not match what the transaction was constructed against.

### Proof of Concept
Not executable without live multi-node fork-switch orchestration; the vulnerable code path is demonstrated by the actuator logic cited above: `ExchangeCreateActuator` assigns IDs via `dynamicStore.getLatestExchangeNum() + 1` [5](#0-4) , and `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` resolve pools purely via `contract.getExchangeId()` with no pool-content binding beyond a single-token check [6](#0-5) .
