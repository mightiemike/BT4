Confirmed: `is-in-voting-window` (and `is-in-prepare-phase`) are defined in `signers-voting.clar` but never referenced inside `vote-for-aggregate-public-key`. This is a direct structural analog to the reported bug class: a temporal-validity predicate exists in the codebase but is not enforced at the point of the privileged/state-changing action, exactly like `devise_invitable`'s `invite_for` expiry being defined but not checked by the password-reset acceptance path.

### Title
Signer aggregate-key voting never enforces the prepare-phase voting window, allowing votes and key finalization outside the intended window - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
The `signers-voting.clar` contract defines `is-in-voting-window` / `is-in-prepare-phase` to restrict aggregate-public-key voting to the reward cycle's prepare phase, but `vote-for-aggregate-public-key` never calls either predicate.

### Finding Description
`is-in-prepare-phase` [1](#0-0)  and `is-in-voting-window` [2](#0-1)  are defined specifically to gate when aggregate-key voting is legitimate: the doc comment on `vote-for-aggregate-public-key` states the vote "must happen after the list of signers has been set by the node, which occurs in the first block of the prepare phase" [3](#0-2) . However, the actual `asserts!` checks inside `vote-for-aggregate-public-key` only validate: the key not already set for the cycle, key length, key novelty, no duplicate vote, and round monotonicity [4](#0-3) . Neither `is-in-voting-window` nor `is-in-prepare-phase` is invoked anywhere in the vote function or in `get-and-cache-total-weight`/`get-signer-weight`. `ERR_OUT_OF_VOTING_WINDOW` is defined and referenced as an error code [5](#0-4) , but it is only ever returned by the "key already set" check, not by an actual window/timing check — the error name suggests intended enforcement that was never wired in, matching the bug-class pattern from the external report (a defined expiry/validity check that is bypassed because the calling code doesn't invoke it).

Because `get-signer-weight` only checks that `tx-sender` matches the signer registered for that `reward-cycle`/index (`is-eq (get signer details) tx-sender)`) [6](#0-5) , and doesn't check burn height/current reward cycle at all, a signer that was valid for `reward-cycle` can call `vote-for-aggregate-public-key` for that same `reward-cycle` at any later burn height — long after the reward cycle's prepare phase, and even after the cycle it applied to has become active or ended — as long as `(map-get? aggregate-public-keys reward-cycle)` is still `none` (i.e., consensus was never reached in time).

### Impact Explanation
If consensus on the aggregate key legitimately fails to close during the prepare phase (e.g., due to network partition, minority of signers offline, or being right at the edge of the window), a signer can still submit `vote-for-aggregate-public-key` calls after the reward cycle has begun/ended, potentially causing `aggregate-public-keys` for a given `reward-cycle` to be set well after that cycle should have started using it, or allowing a set of signers who control >70% weight to coordinate an aggregate-key approval at a time the node/network did not expect it (outside the window all other honest software assumes voting is closed). This can cause node/signer-set-level disagreement about which aggregate key is "the" approved key for a cycle and when it became final — a minority-triggerable divergence in consensus-relevant state (`get-approved-aggregate-key`) between nodes/signers that believe voting closed at the end of prepare phase versus the contract's actual (unenforced) behavior. This maps to the "signer weight/validation verdict disagreement" class in scope — a boot-contract equality (`is-in-voting-window` should gate `vote-for-aggregate-public-key`) that is silently not enforced.

### Likelihood Explanation
No majority is required to trigger the divergence — any single signer (or subset controlling enough weight to eventually cross 70%) can submit valid votes at any burn height as long as the aggregate key for that reward cycle hasn't yet been finalized, since none of the assertions in the function check burn-height against the reward cycle's prepare-phase window. This is directly reachable by any registered signer using the existing public entry point, with no privileged access needed.

### Recommendation
Add an explicit `asserts!` in `vote-for-aggregate-public-key` calling `is-in-voting-window burn-block-height reward-cycle` (or equivalent), returning `ERR_OUT_OF_VOTING_WINDOW` when outside the intended window, so that the contract enforces the same temporal boundary its own helper functions and documentation describe.

### Proof of Concept
1. Reward cycle `N`'s prepare phase begins; `.signers` sets the signer list for cycle `N` (`last-set-cycle = N`).
2. Voting stalls (e.g., some signers offline) and no candidate key reaches the 70% threshold before the prepare phase ends and cycle `N` becomes active — `get-approved-aggregate-key(N)` is still `none`.
3. After the prepare phase for cycle `N` has passed (`burn-block-height` now well past `is-in-prepare-phase` window, potentially into cycle `N` itself or beyond), a signer that was part of cycle `N`'s signer set calls `vote-for-aggregate-public-key` for `reward-cycle = N`.
4. Because `vote-for-aggregate-public-key` never calls `is-in-voting-window`/`is-in-prepare-phase`, the vote is accepted; if enough weight accumulates, `aggregate-public-keys` for cycle `N` gets set outside the intended window, contradicting the window enforced by the contract's own helper functions and its documented protocol [7](#0-6) .

(define-public (vote-for-aggregate-public-key (signer-index uint) (key (buff 33)) (round uint) (reward-cycle uint))
    (let ((tally-key {reward-cycle: reward-cycle, round: round, aggregate-public-key: key})
            ;; vote by signer weight
            (signer-weight (try! (get-signer-weight signer-index reward-cycle)))
            (new-total (+ signer-weight (default-to u0 (map-get? tally tally-key))))
            (cached-weight (try! (get-and-cache-total-weight reward-cycle)))
            (threshold-weight (get-threshold-weight reward-cycle))
            (current-round (default-to {
                votes-count: u0, 
                votes-weight: u0} (map-get? round-data {reward-cycle: reward-cycle, round: round})))
                )
        ;; Check that the key has not yet been set for this reward cycle
        (asserts! (is-none (map-get? aggregate-public-keys reward-cycle)) (err ERR_OUT_OF_VOTING_WINDOW))
        ;; Check that the aggregate public key is the correct length
        (asserts! (is-eq (len key) u33) (err ERR_ILL_FORMED_AGGREGATE_PUBLIC_KEY))

        ;; Check that signer hasn't voted in this reward-cycle & round

        ;; Check that the round is incremented by at most 1
        (try! (update-last-round reward-cycle round))
