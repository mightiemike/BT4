Confirmed: `LiquidityCap` on `TokenConfig` is never read anywhere in `x/uexecutor` — it is only validated for non-emptiness at config-creation time (`x/uregistry/types/token_config.go` `ValidateBasic`) and is otherwise inert. The actual mint path (`x/uexecutor/keeper/handler.go` `depositPRC20` → `x/uexecutor/keeper/evm.go` `CallPRC20Deposit`) never fetches or checks it against any running total.

### Title
Declared per-token `liquidity_cap` is never enforced against cumulative PRC20 minting, allowing unbounded unauthorized minting via repeated legitimate inbounds - (File: x/uexecutor/keeper/handler.go)

### Summary
`TokenConfig.LiquidityCap` is documented as the "max supply cap for this token" [1](#0-0)  and is required to be non-empty when a token is registered [2](#0-1) . However, no code path in `x/uexecutor` — the module that actually mints PRC20 tokens on inbound execution — ever reads `LiquidityCap` or tracks cumulative minted amount per token to compare against it.

### Finding Description
Every inbound deposit flows through `depositPRC20`, which fetches the `TokenConfig` purely to resolve the PRC20 contract address, with no reference to `LiquidityCap`: [3](#0-2) 

The deposit is then executed unconditionally via `CallPRC20Deposit`, which simply mints the requested amount to the recipient with no supply-cap check: [4](#0-3) 

This is structurally the same class of bug as the Goldfinch/Carapace issue: a protective invariant (a cap meant to bound how much value can be created/locked against a single resource) is declared in configuration but the code path that creates new value never accumulates usage against that cap. In Carapace, `canBuyProtection` checked a single protection's size against `remainingPrincipal` but never tracked the sum of all protections already bought for the same loan, so a buyer could keep buying protections until the pool's `leverageRatioFloor` was exhausted. Here, `liquidity_cap` is intended to bound the total PRC20 supply mintable for a given external token, but since it is never read during minting, any number of ordinary, unprivileged users can submit legitimate bridge deposits (each individually valid, each producing a new, distinct `Inbound` with its own `tx_hash:log_index`, so the per-event dedup in `VoteInbound`/`GetInboundUniversalTxKey` does not block this) and the aggregate minted PRC20 supply for that token can grow without bound, exceeding the declared cap.

### Impact Explanation
This is an unauthorized-mint condition: PRC20 tokens are backed 1:1 by the notion that locked funds on the source chain match the cap operators intended to allow for that asset class/route. Silently exceeding `liquidity_cap` breaks accounting invariants the registry is meant to enforce and can be used to over-mint synthetic representation of a token beyond what the protocol operators judged safe (e.g., for exposure/risk-limit purposes per source chain or asset), which maps to "corruption of PRC20 ... accounting" and "unauthorized mint ... of user or protocol-controlled funds" in the allowed impact set.

### Likelihood Explanation
High reachability: any unprivileged user can trigger deposits repeatedly from a source chain (each a distinct, honestly-observed inbound event), and honest Universal Validators will vote and finalize each one normally — no malicious validator, relayer, or admin action is required. The only actor needed is an ordinary user submitting many legitimate bridge transactions.

### Recommendation
Track cumulative minted PRC20 supply per token config (e.g., in a new keeper-managed collection keyed by chain+asset address) and enforce it in `depositPRC20`/`CallPRC20Deposit` before minting: fetch `TokenConfig.LiquidityCap`, compare against the running total plus the new amount, and reject or otherwise handle the inbound instead of minting when the cap would be exceeded — mirroring how `ExecuteInboundFundsAndPayload` already reverts/records failures for other validation failures.

### Proof of Concept
1. Register a token config with `liquidity_cap = "1000000000000000000000000"` (config files uniformly set this, e.g. [5](#0-4) ).
2. As an unprivileged user, repeatedly send small deposits from the source chain gateway, each producing a distinct `tx_hash`/`log_index` inbound.
3. Universal Validators honestly observe and vote each inbound; each passes `VoteInbound` → `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload` → `depositPRC20` → `CallPRC20Deposit`, minting PRC20 to the recipient every time.
4. Because no code anywhere sums prior mints against `LiquidityCap`, the total minted PRC20 supply for that token surpasses the configured `1000000000000000000000000` cap with no error or rejection at any point.

Note: I could not find any enforcement of `LiquidityCap` anywhere in the repository outside proto/config validation — this is based on exhaustive grep across the codebase; if enforcement exists in code not covered by the index, that would invalidate this finding, but no such code was found in `x/uexecutor`, `x/uregistry`, or related keepers.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
