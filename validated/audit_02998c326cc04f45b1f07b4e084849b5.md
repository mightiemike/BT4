### Title
Cross-tenant session hijacking in fulfillment service authentication due to HMAC not binding the shop domain — ([File: packages/apps/shopify-api/lib/fulfillment-service/validate.ts])

### Summary
`shopify.fulfillmentService.validate` computes and checks the HMAC over the raw request body only, never binding the `X-Shopify-Shop-Domain` header to the signature. `authenticateFulfillmentServiceFactory` then trusts that unauthenticated, unsigned header to select *which shop's offline session* (and therefore which shop's Admin API access token) to hand to the app's fulfillment handler. Because the app's `apiSecretKey` used for HMAC signing is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), any tenant that legitimately receives one valid `(rawBody, hmac)` pair for their own shop can replay it against the endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop, and the request will still pass validation — causing the app to act using the victim shop's Admin session on attacker-supplied payload data.

### Finding Description
The fulfillment-service HMAC check only signs `rawBody`: [1](#0-0) 

which delegates to the generic HMAC validator that hashes only the body against the app's shared `config.apiSecretKey`: [2](#0-1) 

The framework adapters then read the shop domain straight from the (unsigned) request header **after** this body-only HMAC check succeeds, and use it to resolve and expose a live offline session/admin client for that shop: [3](#0-2) [4](#0-3) 

`ensureValidOfflineSession(params, shop)` loads (and, per the associated helpers, can refresh) the stored offline access token for whatever `shop` string was supplied in the header, then constructs an authenticated `admin` GraphQL client bound to that shop's real access token, which is handed to the app's own handler along with the attacker-controlled `payload`.

Because the app secret is identical for every shop the app is installed on, the HMAC over a given `rawBody` is also identical regardless of which shop originated it. A merchant/tenant who has legitimately installed the app and operates a fulfillment service therefore:
1. Receives a real, correctly-signed fulfillment order notification for their own store (`rawBody`, `X-Shopify-Hmac-Sha256`).
2. Replays the exact same `rawBody`/HMAC pair to the app's fulfillment endpoint, but substitutes `X-Shopify-Shop-Domain` with a victim shop's domain that also has the app installed.
3. `validate()` succeeds (it never looked at the domain header), and `authenticate.fulfillmentService` loads and refreshes the victim's offline session and admin client, then invokes the app's handler with that victim-scoped `admin` client plus the attacker's chosen `payload`.

This is directly analogous to the referenced Ajna finding: an unprivileged (or minimally privileged, single-tenant) actor can cause the system to attach/act on a resource belonging to a different owner without any signature binding the resource identifier (shop) to the authorization proof (HMAC), because the "attachment key" (shop domain) sits outside the cryptographically verified data.

### Impact Explanation
An attacker who is any single legitimate/installed merchant of a multi-tenant app (or anyone who can obtain one valid body/HMAC pair, e.g. by triggering a fulfillment event on their own store) can cause the app server to execute fulfillment-handler logic using a **different, victim shop's** live Admin API access token. Depending on what the app's `authenticate.fulfillmentService` handler does with `admin` and `payload` (see the documented usage pattern querying/mutating `assignedFulfillmentOrders`), this can lead to cross-tenant data disclosure or cross-tenant mutation of fulfillment orders — a clear cross-tenant access violation, not merely a DoS.

### Likelihood Explanation
Likelihood is meaningfully high in any deployment that uses `authenticate.fulfillmentService` for a multi-shop app: the attacker does not need the app's secret, does not need to break any signature, and does not need special privileges beyond being one of the app's installed shops (a "single merchant"). They only need to capture or generate one legitimately-signed request body from their own shop and resend it with a modified header — no cryptographic material needs to be forged.

### Recommendation
Bind the shop identity to the signed payload before trusting it:
- Incorporate the shop domain (and ideally a nonce/timestamp) into the HMAC-signed material for fulfillment service requests, or
- Cross-check that the `X-Shopify-Shop-Domain` header value is consistent with an independently verified value (e.g., derived from the payload itself or from a per-shop webhook secret instead of the shared app secret), and
- Reject/rate-limit replay of previously-seen `(rawBody, hmac)` pairs (nonce/timestamp binding) to prevent the header-swap replay described above.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com` (both real tenants), both handled by the same deployed app instance sharing one `apiSecretKey`.
2. Shopify sends a legitimate fulfillment order notification to the app for `shop-a`:
   ```
   POST /fulfillment_order_notification
   X-Shopify-Hmac-Sha256: <valid HMAC over rawBody using app secret>
   X-Shopify-Shop-Domain: shop-a.myshopify.com
   Body: {"kind":"FULFILLMENT_REQUEST", ...}
   ```
3. The operator of `shop-a` (a legitimate, low-privileged app installer) captures this exact `rawBody` and `X-Shopify-Hmac-Sha256` value from their own server logs/network capture.
4. They resend the identical body and HMAC header to the same endpoint, but change only:
   ```
   X-Shopify-Shop-Domain: shop-b.myshopify.com
   ```
5. `shopify.fulfillmentService.validate` (`packages/apps/shopify-api/lib/fulfillment-service/validate.ts`) validates successfully because it only checks the HMAC against `rawBody`, which is unchanged.
6. `authenticateFulfillmentServiceFactory` (`packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts` / the react-router equivalent) reads `shop = "shop-b.myshopify.com"` from the header and calls `ensureValidOfflineSession(params, "shop-b.myshopify.com")`, returning `shop-b`'s real offline session/access token bound to an `admin` client, which is then passed to the app's handler together with the attacker-controlled payload — granting the `shop-a` operator effective access to act via `shop-b`'s Admin API session.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }
