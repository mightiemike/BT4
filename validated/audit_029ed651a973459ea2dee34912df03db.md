### Title
Missing validation that access-key / implicit-account public keys are non-degenerate (low-order) points allows universal Ed25519 signature forgery and theft of funds - (File: `core/crypto/src/signature.rs`, `runtime/runtime/src/actions.rs`)

### Summary
NEAR's Ed25519 signature verification path (`Signature::verify`) never rejects a public key that decodes to a low-order (torsion) point on the curve. NEAR is aware of this exact hazard elsewhere in the codebase — `core/crypto/src/key_conversion.rs::is_valid_staking_key` explicitly requires the key be `is_torsion_free()` — but that check is applied **only** to staking keys, not to the general transaction/access-key/delegate-action verification path. Combined with the fact that a NEAR-implicit account's full-access key is derived verbatim from the (attacker-choosable) 64-hex-character account id with no validity check, an attacker can create/fund an account whose installed public key is the all-zero byte string (a small-order point), then forge a single, universally-valid signature for that key without ever possessing a private key, and drain any funds sent to it.

### Finding Description
`Signature::verify` in `core/crypto/src/signature.rs` handles the ED25519 case like this: [1](#0-0) 

It calls `ed25519_dalek::VerifyingKey::from_bytes` and then the default (non-strict, "cofactored") `verify()`. Ed25519-dalek's default `verify()` implements the RFC 8032 cofactored check `[8]sB == [8]R + [8]hA`. If the public key `A` has order dividing 8 (a small-order/torsion point), the term `[8]hA` collapses to the identity for *every* value of `h`, so the equation degenerates to `[8]sB == [8]R`, which is trivially satisfiable by choosing `s = 0` and `R` = the identity element — independent of the message and independent of any secret key. This is precisely the "weak/degenerate key" class the repository itself is aware of: `is_valid_staking_key`/`convert_public_key` in `core/crypto/src/key_conversion.rs` explicitly reject keys that are not `is_torsion_free()`, but only for the staking code path: [2](#0-1) 

No equivalent check exists for `Signature::verify`, meaning any access key, `DelegateAction` public key, or gas key installed with a torsion-order value is universally forgeable.

The all-zero byte string is exactly such a point: on Curve25519's field, `y = 0` requires `x² = -1`, which is solvable (a valid point of order 4). Nothing in the codebase rejects it as a `PublicKey` — it is even used pervasively as `PublicKey::empty(KeyType::ED25519)` in test helpers (`EmptySigner`, `EmptyValidatorSigner`): [3](#0-2) [4](#0-3) 

The reachable path to install such a key on a real account is NEAR-implicit account creation: a transfer to a 64-lowercase-hex account id derives the account's full-access key **directly from the account id string, with no key-validity check**: [5](#0-4) 

`"0"*64` (64 hex zero characters) is a syntactically valid NEAR-implicit account id (64 lowercase hex chars, no separators), so anyone can send a `Transfer` to it. That single action both creates the account and installs `PublicKey::ED25519([0u8;32])` — the low-order point — as its `FullAccess` key.

Transaction signature validation, which every submitted transaction must pass, is: [6](#0-5) 

This calls the vulnerable `Signature::verify`. Because no one holds a secret key for the zero public key (it is a degenerate point, not a keypair anyone generated), this account has *no legitimate owner* — yet, because of the cofactor-forgery, literally any party can construct a signature (`R` = encoding of the identity point, `s` = 0) that verifies successfully for *any* message against this key.

### Impact Explanation
Any NEAR account funded at the `"0"repeated-64` (or any other implicit account id that hex-decodes to a low-order Ed25519 point) implicit address becomes permanently and universally drainable by anyone, with no private key needed. This is direct unauthorized value movement: an attacker can submit `Transfer`/`DeleteAccount` transactions signed with the forged, always-valid signature and steal the entire balance, with the NEAR runtime treating this as a fully authorized, correctly-signed transaction. Because address generation tools/derivations are automated (`derive_near_implicit_account_id`), other low-order/torsion 32-byte values (there are 8 small-order points, several of which are dense in low-entropy byte patterns) similarly produce unowned, universally forgeable accounts, widening the class of exploitable addresses beyond just the trivial all-zero case. This is a genuine protocol-level authentication bypass, not merely a resource or availability issue.

### Likelihood Explanation
Exploitation requires only: (1) funding a syntactically valid but degenerate-key implicit account (any user can do this with an ordinary `Transfer`, including accidentally, since such addresses look like normal 64-hex implicit accounts), and (2) constructing one deterministic, publicly-known forged signature — no cryptanalysis, brute force, or privileged access is required once the low-order points are known (they are a small, enumerable, public set defined by the curve). Both steps are executable by any unprivileged transaction sender via ordinary RPC submission.

### Recommendation
Reject public keys that are not proper full-order group elements before they are used for transaction, delegate-action, or access-key signature verification — mirror the existing `is_torsion_free()` check from `core/crypto/src/key_conversion.rs` inside `Signature::verify` (or at minimum in `ValidatedTransaction::new`/`SignedDelegateAction::verify`) for the `ED25519` case, and/or switch to `ed25519_dalek`'s `verify_strict` (which additionally rejects small-order `R`/`A` components) instead of the default cofactored `verify`. Separately, validate that a NEAR-implicit account id's decoded bytes form a valid, torsion-free Ed25519 point before allowing `action_implicit_account_creation_transfer` to install it as a `FullAccess` key, so degenerate "unowned" accounts cannot be created at all.

### Proof of Concept
1. Compute the account id `victim = "0".repeat(64)` — a syntactically valid NEAR-implicit account id.
2. Any user sends `SignedTransaction::send_money(nonce, sender, victim, ..., deposit, block_hash)`. This creates `victim` and installs `PublicKey::ED25519([0u8; 32])` as its `FullAccess` key (`runtime/runtime/src/actions.rs:234-251`).
3. Attacker builds a `Transaction` with `signer_id = victim`, `public_key = PublicKey::ED25519([0u8;32])`, `receiver_id = attacker`, `actions = [Transfer(deposit_all)]`.
4. Attacker sets `signature = Signature::ED25519(sig)` where `sig` bytes are `R = 32-byte encoding of the Edwards identity (0x01 followed by 31 zero bytes)` and `s = [0u8; 32]`.
5. Submit via RPC. `ValidatedTransaction::new` (`core/primitives/src/transaction.rs:337-342`) calls `Signature::verify`, which reduces (due to cofactor clearing on the order-4 public key) to checking `[8]·0·B == [8]·R_identity`, which holds trivially — the signature verifies for this or any other message, and the transfer executes, draining `victim`'s balance to the attacker with no private key ever having existed for the account.

pub fn is_valid_staking_key(public_key: &PublicKey) -> bool {
    // The valid staking key is ED25519, and can be converted to ristretto.
    match public_key {
        PublicKey::ED25519(key) => convert_public_key(key).is_some(),
        PublicKey::SECP256K1(_) | PublicKey::MLDSA65(_) => false,
    }
}

pub fn convert_public_key(key: &signature::ED25519PublicKey) -> Option<vrf::PublicKey> {
    let ep: EdwardsPoint = CompressedEdwardsY::from_slice(&key.0).ok()?.decompress()?;
    // All properly generated public keys are torsion-free. RistrettoPoint type can handle some values that are not torsion-free, but not all.
    if !ep.is_torsion_free() {
        return None;
    }
    // Unfortunately, dalek library doesn't provide a better way to do this.
    let rp: RistrettoPoint = unsafe { transmute(ep) };
    Some(vrf::PublicKey(rp.compress().to_bytes(), rp))
}
