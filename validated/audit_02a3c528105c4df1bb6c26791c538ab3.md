Confirmed: `remove_account` (`core/store/src/utils/mod.rs:505-575`) removes the `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` entries, but it does **not** remove `PromiseYieldReceipt` or `PromiseYieldStatus`/yield-id-mapping trie keys that were created for that account by `enqueue_promise_yield_timeout`/`set_promise_yield_receipt`. `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) only checks storage-usage size and gas-key balance thresholds before calling `remove_account`; it never checks whether the account has an outstanding `PromiseYield` awaiting resumption.

### Title
Deleting an account with a pending PromiseYield leaves an orphaned yield receipt reachable via a self-triggered `DeleteAccount` action - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` clears an account's balance, access keys, gas keys, and contract data, but has no check for outstanding `PromiseYield` state (a `PromiseYieldReceipt` entry plus its corresponding `PromiseYieldTimeout` queue entry) associated with the account. This mirrors the "clearTokenConfig" pattern: state describing an in-progress/active operation (a parked yielded promise awaiting `yield_resume`) can be wiped out from under an account that a contract itself chooses to delete mid-flight, without checks that the associated operation isn't still pending.

### Finding Description
A contract can call `promise_yield_create` to park an action receipt keyed by `(receiver_id, data_id)`, storing:
- a `PromiseYieldReceipt` entry via `set_promise_yield_receipt` (`core/store/src/utils/mod.rs:200-212`)
- a `PromiseYieldTimeout` queue entry via `enqueue_promise_yield_timeout` (`core/store/src/utils/mod.rs:182-198`), keyed only by an incrementing index and containing `{account_id, data_id, expires_at}` [1](#0-0) 

In the same or a later receipt, the same account (`receiver_id == predecessor_id`, self-delete) can submit a `DeleteAccount` action. `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) only validates (a) account storage-usage size (`DeleteAccountWithLargeState`) and (b) gas-key balance sum (`GasKeyBalanceTooHigh`) — see [2](#0-1)  — before calling `remove_account`, which never touches `TrieKey::PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId` entries [3](#0-2) . There is also no check equivalent to `DeleteAccountStaking` for "has an outstanding PromiseYield."

Later, when the corresponding `PromiseYieldTimeout` matures, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3113-3220`) checks `state_update.contains_key(&promise_yield_key, ...)` (still true, since the receipt entry was never removed) and unconditionally builds/forwards a `PromiseResume` receipt addressed to `queue_entry.account_id` — the now-deleted account — [4](#0-3) . When that `PromiseResume` receipt is processed, `apply_action_receipt` calls `apply_action_receipt` on the retrieved `yield_receipt` (whose `receiver_id` is the deleted account) [5](#0-4) . This directs an action-receipt execution at an account that no longer exists in the trie.

### Impact Explanation
Receipts destined for a nonexistent account normally resolve to `AccountDoesNotExist` and generate a refund, which is the "safe" catch-all near-core relies on for missing accounts. However, the orphaned `PromiseYieldReceipt`/`PromiseYieldTimeout`/`YieldIdToDataId` entries permanently remain in the trie for an account that will never resolve them (state bloat that is never cleaned up by ordinary account deletion, unlike the deliberate cleanup path exercised in the resume/timeout-success case at `runtime/runtime/src/lib.rs:1572-1591`). Because deletion is entirely under the account owner's control (a self-submitted `DeleteAccount` action requires no special privilege), any contract using yield/resume can trigger this by deleting itself while a yield is outstanding, leaving dangling protocol state and skipping the state cleanup normally performed when a `PromiseResume` is properly matched and consumed. This is a state-hygiene/permanent-storage-leak issue rather than a fund-theft or consensus-divergence primitive, since the described `PromiseResume` execution path is guarded by `AccountDoesNotExist` handling in `apply_action`/`check_account_existence`.

### Likelihood Explanation
High reachability: any account can trigger this in one straightforward sequence — call `yield_create`, then self-delete via `DeleteAccountAction` — using only actions available to an ordinary transaction signer. No validator or node privilege is required.

### Recommendation
Before allowing `action_delete_account` to proceed, check whether the account has any outstanding `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId` entries (analogous to the existing `DeleteAccountStaking` check for locked balance), and either reject the deletion with a new `ActionErrorKind` until the yield resolves/times out, or have `remove_account` proactively purge these entries (and their corresponding `PromiseYieldTimeout` queue slot) so no dangling references to the deleted account remain in state.

### Proof of Concept
1. Deploy a contract account `child.alice.near` implementing `promise_yield_create`.
2. Submit a receipt to `child.alice.near` calling `promise_yield_create`, creating a `PromiseYieldReceipt` and a `PromiseYieldTimeout` entry keyed to `child.alice.near`.
3. In the same or a subsequent receipt with `predecessor_id == receiver_id == child.alice.near`, submit `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: ... })`.
4. Observe `action_delete_account` succeeds (storage usage and gas-key checks pass trivially for a small/no-gas-key account) and removes the `Account` record, while `PromiseYieldReceipt`/`PromiseYieldTimeout` entries for `child.alice.near` remain in the trie.
5. Advance blocks until `queue_entry.expires_at` is reached; `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3113`) still finds the `PromiseYieldReceipt` key present and issues a `PromiseResume` receipt targeting the deleted `child.alice.near`, which resolves via the standard `AccountDoesNotExist`/refund path rather than being cleaned up as in the normal resume flow, confirming the orphaned bookkeeping was never invalidated at deletion time.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
