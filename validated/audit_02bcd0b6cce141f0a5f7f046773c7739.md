## Title
Replay-verify tool fails to check state-checkpoint root hashes, masking silent state-root divergence — (`File: types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the comparator used by `db-tool`'s `replay_on_archive` (and by `aptos-debugger`/`cli` commands) to verify a locally re-executed transaction against the archived, authenticated `TransactionInfo`, checks transaction status, gas, write-set hash, and event root hash — but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This mirrors the reported bug class: a validation that exists in one entry point (normal, trusted-comparison paths) is silently missing in a sibling entry point that is supposed to enforce the same invariant.

### Finding Description
`ensure_match_transaction_info` is the authoritative comparator that decides whether a locally re-executed `TransactionOutput` "matches" a `TransactionInfo` pulled from archived/backup storage: [1](#0-0) 

It validates `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`, but the function ends with an explicit acknowledgement that it skips the state-checkpoint-related hashes: [2](#0-1) 

This function is the sole correctness gate in `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and only fails/reports an error via `ensure_match_transaction_info`: [3](#0-2) 

Because `state_checkpoint_hash` (and the hot-state / position-state variants) is never compared, a state-checkpoint root recorded in the archived `TransactionInfo` that diverges from the root actually produced by local re-execution will not be flagged. In the normal execution pipeline `assemble_transaction_infos` computes and embeds these same fields into the `TransactionInfo` it builds and hashes into the accumulator: [4](#0-3) 

so the state-checkpoint hash is a first-class, security-relevant field of the committed ledger — it is exactly the kind of field that `check_txn_info_hashes.rs`-style tooling and replay-verify are meant to validate against a trusted, independently re-computed value. Skipping it in the one comparator used for offline replay verification breaks the "replay paths must not reinterpret committed data into a different ledger state" invariant: a corrupted, tampered, or buggy-VM-produced state root in archived data is accepted as verified.

### Impact Explanation
Replay-verify (`db-tool replay-on-archive`) exists specifically to detect state divergence/hard-fork bugs by independently re-executing historical transactions and comparing the resulting state to what was archived/authenticated. Because the checkpoint-hash fields are not compared, this tool will report a "successful" replay-verify run even when the locally computed Jellyfish Merkle / hot-state / position-state root differs from the one embedded in the (supposedly trusted) `TransactionInfo`. This falls squarely in the accepted category of "Hard-fork-only divergence during commit, replay, restore, or proof verification" — a real state-root divergence (e.g., caused by a VM execution bug, an on-disk corruption, or a malicious archive) would go completely undetected by the primary tool designed to catch exactly that class of bug.

### Likelihood Explanation
The gap is unconditional: it applies to every call of `ensure_match_transaction_info`, regardless of feature flags, since the comparison logic is a straight `Ok(())` fallthrough with no checks for the checkpoint hashes — the TODO comment even documents the omission and only ties `position_state_checkpoint_hash` to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, but says nothing about the pre-existing `state_checkpoint_hash`/`hot_state_checkpoint_hash`, which are already live fields checked and populated elsewhere in the executor.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute the state checkpoint hash(es) from the post-execution state view for checkpoint boundaries and assert equality against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` (and `position_state_checkpoint_hash()` once relevant), consistent with how `write_set_hash` and `event_root_hash` are already validated.

### Proof of Concept
1. Run `db-tool replay-on-archive` against an archived range that includes a state-checkpoint transaction whose `TransactionInfo.state_checkpoint_hash` was tampered with (or produced by a divergent/buggy VM run).
2. `execute_and_verify` re-executes the block and calls `ensure_match_transaction_info` per output.
3. Because status/gas/write-set-hash/event-root-hash for that transaction are unaffected by the tampering, the function returns `Ok(())`, and the tool reports the range as verified even though the state root diverges — demonstrated by the omitted checks at [5](#0-4) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
