### Title
Unbounded O(N) TRC10 asset-map iteration in `MUtil.transferAllToken` combined with fixed-cost `SUICIDE` energy pricing enables underpriced VM work - ([File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java])

### Summary
`MUtil.transferAllToken`, invoked when a contract self-destructs, unconditionally iterates every entry of `fromAccountCap.getAssetMapV2()` and rewrites both the source and destination account protobufs for each `tokenId`, with no cap on map size and no skip for negligible/zero balances (unlike `MUtil.transfer` and `MUtil.transferToken`, which both early-return on `amount == 0`). Because the `SUICIDE` opcode is charged a fixed energy cost, an attacker who accumulates many distinct TRC10 `tokenId` entries in a contract's balance can force that fixed-cost opcode to perform work proportional to the number of distinct assets held.

### Finding Description
`MUtil.transfer` and `MUtil.transferToken` both guard against no-op work: [1](#0-0) [2](#0-1) 

`transferAllToken`, however, has no such guard and unconditionally walks the full `AssetMapV2` of the self-destructing account, mutating both account builders per entry: [3](#0-2) 

This function is referenced from `Program.java`, which is the VM's `SUICIDE`/self-destruct handling path (confirmed via 3 references to `transferAllToken` in `Program.java`), meaning every `SUICIDE` execution that transfers a contract's TRC10 asset balances to a target address does O(N) protobuf `putAssetV2` operations, where N is the number of distinct `tokenId` entries the contract currently holds — regardless of whether those balances are dust or zero.

Meanwhile the `SUICIDE` opcode's energy cost is computed via a fixed-cost function (`EnergyCost.getSuicideCost`, referenced in `EnergyCost.java` and `OperationRegistry.java`); I was not able to fully inspect its body before running out of tool calls, but the search results show no code path in `EnergyCost.java` that ties the suicide cost to the size of the sender's `AssetMapV2`. Assuming (based on the fixed-opcode-cost architecture visible in `OperationRegistry.java`/`EnergyCost.java`) that this cost does not scale with asset count, this is a genuine mismatch: the priced energy for `SUICIDE` does not reflect the O(N) map-iteration and protobuf-rebuild work actually performed.

### Impact Explanation
A contract holding a large number of distinct TRC10 `tokenId` balances can trigger disproportionately expensive processing in a single `SUICIDE` call while paying only the fixed energy price. This is a form of underpriced public work: the node performing block validation must do work proportional to attacker-chosen N while the fee/energy charged is constant, which can degrade block processing throughput if repeated across many contracts/blocks.

### Likelihood Explanation
Building the precondition state (a contract holding N distinct TRC10 tokenIds) requires N separate transfer transactions into the contract, each individually fee/energy-priced at the normal (roughly constant) per-transfer cost — so the attacker pays cost roughly proportional to N in aggregate, spread across many cheap transactions/blocks. The single `SUICIDE` transaction that finally triggers the O(N) iteration, however, is priced independently of N. This makes the attack a classic "pay linear cost across many cheap transactions, trigger fixed-cost op that does the accumulated O(N) work in one transaction" pattern — feasible for an attacker willing to spend on many small transfers of already-existing TRC10 tokens (no need to issue new tokens, which would carry a large TRX issuance fee), and repeatable across multiple contracts.

I was unable to fully confirm (due to tool-call exhaustion) the exact formula inside `EnergyCost.getSuicideCost` and whether any existing cap/mitigation on distinct asset count per account exists elsewhere in the codebase. This should be verified directly in `EnergyCost.java` before treating the fixed-cost assumption as certain.

### Recommendation
- Add an early-return guard in `MUtil.transferAllToken` skipping entries with zero balance, matching the pattern in `transfer`/`transferToken`.
- Bound the number of distinct TRC10 asset entries a single account/contract may hold, or make `SUICIDE` energy cost scale with the size of `AssetMapV2` being transferred (similar to how per-storage-slot costs scale with touched slots elsewhere in the VM).
- Alternatively, charge energy proportional to `fromAccountCap.getAssetMapV2().size()` at the point `transferAllToken` is invoked from the `SUICIDE` handler in `Program.java`.

### Proof of Concept
Java integration test plan (framework module, similar to existing `CreateContractSuicideTest.java` / `OperationsTest.java` patterns):
1. Deploy a contract account.
2. Issue or acquire N (e.g., 2,000) distinct existing TRC10 tokenIds, each transferring a dust amount (1 sun) into the contract account via `TransferAssetContract`/`transferToken`.
3. Call `SUICIDE` from the contract, transferring remaining balance/assets to a target address.
4. Measure wall-clock execution time and DB write volume for the `SUICIDE` execution as a function of N, and compare to the fixed energy consumed (`EnergyCost.getSuicideCost` value) converted to expected processing time bound.
5. Assert that execution time/work grows linearly with N while charged energy remains constant, exceeding an expected energy-proportional bound (e.g., assert wall time / energy-cost ratio increases with N beyond a defined tolerance), or assert failure of an added cap if the fix caps asset-map size.

```java
  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
```
