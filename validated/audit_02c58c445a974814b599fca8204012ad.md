### Title
TRX Sent as Call Value to Fixed Precompiled-Contract Addresses Is Permanently Locked - (`File: actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress` accepts a nonzero `msg.getEndowment()` (callValue) when a smart contract executes a `CALL`/`STATICCALL`-style opcode against one of the fixed precompiled-contract addresses (e.g. `voteContractAddr`, `proposalCreateAddr`, `getChainParameterAddr`, etc.) and unconditionally credits that TRX to the precompile's address via `MUtil.transfer`, exactly as the Ion-Protocol report describes contracts/constructors that accept ETH with no corresponding withdrawal path.

### Finding Description
When the TVM executes a message call whose target resolves to a `PrecompiledContract` (`PrecompiledContracts.getContractForAddress`), the call-value handling logic in `Program.callToPrecompiledAddress` runs before the precompiled logic itself: [1](#0-0) 

If `endowment > 0`, `MUtil.transfer` moves the balance directly onto the `contextAddress` (the precompile's fixed system address, e.g. `0x0000...010001` for the vote precompile, `0x0000...010006` for proposal-create, etc., enumerated in `PrecompiledContracts.getContractForAddress`): [2](#0-1) 

`MUtil.transfer` performs no destination-specific validation beyond `VMUtils.validateForSmartContract` (basic sanity checks) and simply does `deposit.addBalance(toAddress, amount)`: [3](#0-2) 

The precompiled contracts implementing vote/proposal/freeze-v2/resource-query logic operate purely on repository state (accounts, proposals, resource stores) and never consume, forward, or refund the `endowment` balance that was credited to their address. These addresses are fixed, protocol-defined constants (not derived from any private key, and not a normal `TriggerSmartContract`-invoked contract with its own logic) — there is no actuator, precompiled handler, or governance mechanism anywhere in the codebase that reads a balance from these addresses and moves it back out. Unlike normal user/contract accounts, which can always be drained via `TransferContract`, `TriggerSmartContract` calls, or `selfdestruct`, TRX credited to a precompile pseudo-address has no owner key and no code path that spends it. This mirrors the reported bug class exactly: a payable entry point accepts value with no corresponding withdraw function, so any value sent is permanently stranded.

Note: the normal contract-call path (`Program.callToAddress`, `Program.createContractImpl`) similarly moves callValue to `contextAddress` before executing bytecode, but that is legitimate because ordinary contract accounts execute their own bytecode/fallback and may implement withdraw logic (or intentionally reject it, as EVM/TVM does for non-payable functions). The precompiled-address path has no equivalent because precompiles are not driven by bytecode that could implement a withdrawal.

### Impact Explanation
Any TRX sent as `callValue` in a `CALL` to one of the precompiled contract addresses (vote, proposal create/approve/delete, freeze-v2 query precompiles, chain-parameter query precompiles, etc.) becomes permanently inaccessible — it increases the on-chain balance of a fixed system address that no actor, including SRs or the account owner, can subsequently withdraw or spend, since the address is not a real keyed account and no contract logic exists to move funds out of it. This is a permanent-loss-of-user-funds bug (asset corruption via unrecoverable value), matching the "Locked ETH in Contract" bug class. It requires no privileged access — it can be triggered by any account issuing a `TriggerSmartContract` whose deployed bytecode performs a `CALL` with nonzero value against a precompile address.

### Likelihood Explanation
Exploitability requires only that a smart contract (which can be deployed by anyone) performs a low-level `call{value: X}` to one of the known precompiled-contract addresses; this is straightforward to construct with a single Solidity `call` instruction and does not require special privileges, malicious peers, or race conditions. The likelihood of accidental fund loss (rather than intentional demonstration) is lower since developers must specifically target these unusual fixed addresses, but the flaw is trivially reachable via a normal `TriggerSmartContract` transaction from any external account.

### Recommendation
In `Program.callToPrecompiledAddress`, reject calls that carry nonzero `endowment`/`callValue` when the target is a precompiled contract address (return failure / push zero and refund energy, analogous to how EVM implementations forbid value transfers to typical precompiles), unless a given precompile is explicitly designed to consume that value (in which case its `execute` method should account for and use/refund it). This closes off the accumulation of unrecoverable balance on fixed system addresses.

### Proof of Concept
1. Deploy a contract with a function such as:
```solidity
function drainToVotePrecompile() external payable {
    address(0x0000000000000000000000000000000000010001).call{value: msg.value}("");
}
```
2. Call `TriggerSmartContract` with `call_value > 0` invoking `drainToVotePrecompile`.
3. Observe via `Program.callToPrecompiledAddress` → `MUtil.transfer` that the TRX balance is credited to the fixed vote-precompile address `0x...10001`.
4. Confirm (by inspecting `AccountStore`) that this balance can never be moved by any subsequent transaction type (`TransferContract`, `TriggerSmartContract` from that "address", etc.), since no private key or contract code exists at that address to authorize a spend.
