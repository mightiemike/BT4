Based on my investigation, I found a concrete, unprivileged, minority-triggerable analog in the `.signers-voting` boot contract: the `vote-for-aggregate-public-key` public function never enforces its own voting-window/eligibility check.

### Title
`vote-for-aggregate-public-key` never calls `is-in-voting-window`, allowing votes/threshold computation outside the valid signer set - ([File: stackslib/src/chainstate/stacks/boot/signers-voting.clar])

### Summary
`signers-voting.clar` defines a private helper `is-in-voting-window` whose stated purpose is to gate voting to the correct reward cycle and prepare phase. However, `vote-for-aggregate-public-key`, the only public entry point that consumes signer weight and the cached `cycle-total-weight`, never invokes this helper. This mirrors the reported bug class: a value/condition intended to be checked (fee stored/threshold gating) is computed but never wired into the code path that performs the consequential state transition, producing a discrepancy between intended and actual enforcement.

### Finding Description
`is-in-voting-window` is defined at [1](#0-0)  to check that the target `reward-cycle` matches `.signers get-last-set-cycle` and that the current burn height is within the prepare phase. This is precisely the guarantee the doc-comment on `vote-for-aggregate-public-key` promises: "This vote must happen after the list of signers has been set by the node, which occurs in the first block of the prepare phase" [2](#0-1) .

But the actual public function body never calls `is-in-voting-window`. Its only gating checks are: the aggregate key not already set for the cycle, key length, key novelty, and duplicate-vote protection via `map-insert votes` [3](#0-2) . `ERR_OUT_OF_VOTING_WINDOW` is defined and even referenced as the error code for the "already-set key" check [4](#0-3) , but the constant name shows the author's intent was to reject votes outside the valid voting window — that specific temporal/cycle-correctness check via `is-in-voting-window` is dead code, never reached.

The weight and threshold computations that follow are directly affected by this missing gate:
- `get-signer-weight` returns the caller's weight for `reward-cycle` from `.signers`, keyed only by signer-index/cycle match [5](#0-4) .
- `get-and-cache-total-weight` computes and permanently caches `cycle-total-weight` for a `reward-cycle` the *first* time it's invoked for that cycle [6](#0-5) .
- `get-threshold-weight` derives the 70% supermajority threshold purely from that cached total [7](#0-6) .

Because nothing prevents calling `vote-for-aggregate-public-key` for a `reward-cycle` before `.signers` has finished being populated for that cycle (i.e., before the node's first-prepare-phase-block `set-signers` call, or for a cycle whose signer list is not yet the `last-set-cycle`), a signer can trigger `get-and-cache-total-weight` while `.signers get-signers reward-cycle` still returns an empty/stale/zero-weight list (`signers.clar`'s `cycle-signer-set` map defaults to `none` and `get-signers` returns `(map-get? cycle-signer-set cycle)` [8](#0-7) ). If the map is empty for that cycle, `unwrap!` on `contract-call? .signers get-signers reward-cycle` in `get-and-cache-total-weight` fails softly only if the call itself errors; but if the cycle key legitimately exists with zero/partial entries (e.g., queried for a future cycle not yet finalized, or after a stale/partial set), the `fold sum-weights` total can be permanently cached as `0` or as a partial total that never matches the eventual "real" signer set weight used elsewhere by `get-signer-weight`.

This breaks the equality the contract is supposed to guarantee: `total-weight` used in `get-threshold-weight` (cached once, forever, for that cycle) **must equal** the sum of weights actually assigned in `.signers cycle-signer-set` for that cycle at the time it is authoritative. Once cached at zero (or some other value) via a premature call outside the intended voting window, `get-threshold-weight` returns `0` (or an artificially low value) permanently for that reward cycle, since `cycle-total-weight` is never recomputed (`match` short-circuits on any cached value, even `u0`, per `get-and-cache-total-weight`'s `match` semantics) [6](#0-5) .

### Impact Explanation
With `threshold-weight` cached as `0` (or artificially low), the very next legitimate vote from a single minority signer (`new-total >= threshold-weight`) at line 181 will satisfy the "reached consensus" branch, causing `map-insert aggregate-public-keys reward-cycle key` to succeed and emit `approved-aggregate-public-key` for a key with far less than 70% actual signing weight backing it [9](#0-8) . This is a minority-triggerable divergence between the intended 70%-weight DKG consensus and the actual accepted aggregate public key for the cycle — a High-severity static-validation/threshold divergence bounded to the signer-DKG-voting subsystem, since it lets a minority of signer weight dictate the reward cycle's aggregate key, which downstream is relied upon for PoX signing/verification.

### Likelihood Explanation
Likelihood is Medium: it requires a signer (an entity already holding a valid signer-index/weight assignment for some cycle — not an arbitrary unprivileged party, but not requiring majority or admin keys either) to race a `vote-for-aggregate-public-key` call before the node's `set-signers`/`stackerdb-set-signer-slots` sequence establishes the full signer list for `reward-cycle`, or to call it for the "next" cycle before that cycle's list is finalized. Whether this race is practically reachable given the surrounding node scheduling of `pox_4_compute_and_update_signers` is not fully verifiable from static code alone — a background agent/Devin session with sequence-diagram tracing across `nakamoto/signer_set.rs`, `signers.clar`, and the timing of `current-reward-cycle` vs `last-set-cycle` would be needed to confirm the exact reachable window, but the missing call to `is-in-voting-window` is a clear, provable code defect independent of exact timing feasibility.

### Recommendation
Add the missing gate to `vote-for-aggregate-public-key`: `(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))` before any weight/threshold computation, ensuring `cycle-total-weight` is only ever cached once `.signers` has authoritatively finished being set for that `reward-cycle` (i.e., `last-set-cycle == reward-cycle`) and while still in the prepare phase.

### Proof of Concept
1. Reward cycle `N`'s prepare phase begins; the node has not yet called `set-signers` for cycle `N` (or has only partially populated it), so `.signers get-signers N` currently returns a stale/empty list from a prior state.
2. A signer who already has *some* valid `signer-index` entry for cycle `N` (from a previous partial write, or by calling with a cycle whose list is not yet current) calls `vote-for-aggregate-public-key` for `reward-cycle: N`.
3. `get-and-cache-total-weight` executes, sees no `cycle-total-weight` entry yet, computes `fold sum-weights` over the current (empty/stale/small) `.signers get-signers N` list, and permanently caches an artificially small `total-weight` via `map-set cycle-total-weight N total`.
4. `get-threshold-weight N` now always returns `(total * 70 + 99) / 100` based on that permanently-cached, too-small total — never recomputed even after `.signers` is later correctly populated with the full signer set and full weights.
5. Any subsequent minority-weight vote for cycle `N` satisfies `new-total >= threshold-weight`, causing `aggregate-public-keys` to be set for cycle `N` with a key that did not receive 70% of the *actual* signer weight — breaking the DKG-consensus equality the contract is designed to enforce.
