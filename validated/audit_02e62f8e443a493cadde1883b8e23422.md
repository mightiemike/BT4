### Title
L1 handler `paid_fee_on_l1` is hardcoded during proposal validation, causing the fee-sufficiency check to always pass and creating execution divergence between proposer and validators - (File: `crates/apollo_transaction_converter/src/transaction_converter.rs`)

### Summary
When a validator reconstructs an `L1Handler` transaction received via the consensus proposal (rather than fetching it directly from L1 itself), it discards the real fee that was paid on L1 and substitutes a hardcoded placeholder `Fee(1)`. This is the same bug class as the reported `receiveFlashLoan` issue: an externally supplied fee-related value from a trusted third party (here, the L1 core contract via the L1 scraper) is ignored and replaced by an assumption that "the value doesn't matter," which silently defeats a downstream sufficiency check.

### Finding Description
`convert_consensus_l1_handler_to_internal_l1_handler` builds the internal `executable_transaction::L1HandlerTransaction` with a hardcoded fee, explicitly flagged as a stopgap: [1](#0-0) 

This function is invoked from `convert_consensus_tx_to_internal_consensus_tx` whenever a `ConsensusTransaction::L1Handler` is converted to `InternalConsensusTransaction::L1Handler`: [2](#0-1) 

Note that when the proposer originally serializes its own consensus transaction, it strips the real `paid_fee_on_l1` and `tx_hash` entirely, sending only the raw `tx` (`ConsensusTransaction::L1Handler(tx.tx)`): [3](#0-2) 

Validators receiving that proposal (in `validate_proposal.rs`, via `convert_consensus_tx_to_internal_consensus_tx`) therefore have no way to recover the real fee that was paid on L1 for this message, and always fabricate `Fee(1)`.

The only place `paid_fee_on_l1` is used is `execute_raw` in the L1-handler execution path, which merely checks it is nonzero: [4](#0-3) 

Because the transaction hash for L1-handler transactions deliberately excludes the fee field (`"// No fee in l1 handler transaction."`), this substitution is invisible to hash-based integrity checks: [5](#0-4) 

The consequence: the proposer computes the L1-handler transaction directly from the L1 event scraper, which carries the *real* fee paid on L1: [6](#0-5) 
but the validators who re-execute the very same proposed transaction (to validate the block) always see `paid_fee_on_l1 = Fee(1)`, i.e., "always considered paid," regardless of what was actually paid on L1.

### Impact Explanation
`InsufficientFee` is the only fee-based outcome distinguishing "reverted" vs. "executed" for an L1-handler transaction (see the reverted-vs-executed branching in `execute_raw`). If an L1 message is sent with `fee == 0` on L1 (nothing in the code path prevents this from being scraped and forwarded as a proposal — the L1 core contract's own fee enforcement is out of scope for the sequencer):
- The **proposer** (which has the real fee value) will correctly evaluate `paid_fee == Fee(0)` and revert the transaction execution, producing an empty/no-op state diff for that transaction.
- Every **validator** re-executing the identical proposal will instead see `Fee(1)` and treat the check as passed, executing the L1 handler's side effects (state writes) normally.

This produces divergent state diffs / committed roots between the block proposer and the honest validators re-executing the same proposal — an honest-node divergence that can cause validators to reject an otherwise-valid block (denial of block confirmation) or, in the worst case, accept a state root that the proposer itself did not intend to commit to, undermining the guarantee that all honest nodes converge on the same state after executing the same transaction set. This satisfies the "wrong committed root" / "honest-node divergence" impact bar.

### Likelihood Explanation
Reachable by any L1 message sender (a permissionless message from any L1 account/contract to the Starknet core contract) — no privileged role is required. The divergence is triggered purely by the *fee amount actually paid on L1* for the message, which is fully controlled by the unprivileged sender of the L1→L2 message. The bug is deterministic (not probabilistic) whenever such a message is included in a proposal and reaches the fee-check boundary condition.

### Recommendation
- **Short term:** Propagate the real `paid_fee_on_l1` through the consensus transaction payload (instead of stripping it in `convert_internal_consensus_tx_to_consensus_tx` and fabricating it in `convert_consensus_l1_handler_to_internal_l1_handler`), so that proposer and validators evaluate the exact same fee value for the `InsufficientFee` check.
- **Long term:** Remove reliance on hardcoded/placeholder values for any externally-sourced field that feeds into consensus-relevant execution decisions; add a lint/test asserting that no `TODO`-guarded placeholder value can affect transaction execution outcome (revert vs. success) differently across proposer and validator.

### Proof of Concept
1. An unprivileged L1 account sends a `sendMessageToL2` call to the Starknet core contract with `msg.value = 0` (or whatever the minimum-fee boundary condition is), targeting an L2 contract's L1-handler entry point.
2. The L1 scraper picks this up with `fee = Fee(0)` and the proposer creates the `L1HandlerTransaction` with `paid_fee_on_l1 = Fee(0)` from `apollo_l1_events_types` (`crates/apollo_l1_events_types/src/lib.rs:317-320`).
3. During proposal building, the proposer executes it via `execute_raw` (`crates/blockifier/src/transaction/l1_handler_transaction.rs:97-116`); since `paid_fee == Fee(0)`, the transaction reverts and no state changes are applied — the proposer includes it in the block as a reverted L1-handler transaction with empty state diff.
4. The proposer strips the fee from the outgoing consensus payload (`crates/apollo_transaction_converter/src/transaction_converter.rs:178-181`), sending only the bare `L1HandlerTransaction` (`tx.tx`) to validators.
5. Validators reconstruct the transaction via `convert_consensus_l1_handler_to_internal_l1_handler`, hardcoding `paid_fee_on_l1 = Fee(1)` (`crates/apollo_transaction_converter/src/transaction_converter.rs:473-483`).
6. Validators re-execute the same transaction; since `paid_fee == Fee(1) != Fee(0)`, the `InsufficientFee` branch is not taken, so the transaction executes normally and applies its state-modifying side effects — producing a state diff/root that differs from what the proposer computed and intended to commit.
