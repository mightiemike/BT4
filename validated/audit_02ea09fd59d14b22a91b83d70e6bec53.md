### Title
Unbounded per-call O(n) `max()` scan (net O(n²) per transaction) in `AccountStore.recordBalance` when `historyBalanceLookup` is enabled - ([File: chainbase/src/main/java/org/tron/core/store/AccountStore.java])

### Summary
When a node runs with `storage.balance.history.lookup=true`, every `AccountStore.put`/`delete` call inside a single transaction invokes `recordBalance`, which recomputes `operationIdentifier` by scanning the entire accumulated `TransactionBalanceTrace.operation` list with a stream `.max()`, and then rebuilds the whole protobuf operation list via `toBuilder().addOperation().build()`. Since the list only grows within one transaction and is rescanned/rebuilt on every account touch, the accounting cost of a transaction that touches N accounts is O(N²) rather than O(N).

### Finding Description
`AccountStore.put`/`AccountStore.delete` call `recordBalance` for every account balance change once `CommonParameter.getInstance().isHistoryBalanceLookup()` is true: [1](#0-0) 

`recordBalance` fetches the current `TransactionBalanceTrace`, scans its full `operation` list to find the max `operationIdentifier`, then appends a new operation by rebuilding the (immutable protobuf) list from scratch: [2](#0-1) 

Because `currentTransactionBalanceTrace` persists and grows across all account touches within the same transaction (reset only at transaction boundaries in `BalanceTraceStore.resetCurrentTransactionTrace`/`initCurrentTransactionBalanceTrace`), each additional account touched in that transaction pays for scanning and copying all previously recorded operations, making the cumulative cost of N touches O(N²): [3](#0-2) 

An attacker can increase N (number of accounts touched in a single transaction) with a TVM contract executing value-transferring `CALL`s to many distinct addresses in a loop; each such call costs `CALL_ENERGY` + `VT_CALL` (and `NEW_ACCT_CALL` for new addresses) as fixed per-call energy fees defined in `EnergyCost.java`, unrelated to the size of the growing `TransactionBalanceTrace`: [4](#0-3) 

No guard exists that scales the required energy/fee with the current size of `currentTransactionBalanceTrace.getOperationList()`, so the fee model does not price the growing quadratic bookkeeping cost.

### Impact Explanation
This is a real algorithmic-complexity issue in a feature-gated code path, but the practical, scoped security impact is limited:
- The vulnerable path is entirely gated behind `CommonParameter.isHistoryBalanceLookup()`, which defaults to `false` and must be explicitly enabled by node operators via `storage.balance.history.lookup=true` in `config.conf`: [5](#0-4)  This is a deployment/opt-in choice by the node operator (typically archive/exchange nodes), not something an unprivileged attacker can toggle on a victim node.
- Where the flag is enabled, an unprivileged attacker can still submit a normal, fully-paid transaction (e.g., a contract looping value-transferring `CALL`s to N distinct addresses) to inflate N within one transaction, causing the operator's node to do O(N²) work in `recordBalance` rather than O(N), which is disproportionate to the (per-call, fixed) energy fee charged for each `CALL`.
- The magnitude of N is nonetheless energy-bounded (each value-transfer `CALL` costs a fixed minimum of `CALL_ENERGY`(40) + `VT_CALL`(9000), or +`NEW_ACCT_CALL`(25000) for new accounts, per `EnergyCost.java`), so the attacker still pays proportionally increasing (though not increasing per-unit) fees for larger N; this is not "free" unbounded work, only a quadratic multiplier on otherwise-paid execution.

### Likelihood Explanation
Exploitability strictly requires the operator-controlled `historyBalanceLookup` feature to be enabled, which is off by default and used only by a subset of specialized nodes (e.g., archive/exchange nodes serving `GetAccountBalance`/`GetBlockBalance`). On such nodes, triggering the O(N²) accounting is straightforward and repeatable via a standard, fee-paid contract transaction with many internal value transfers; no privileged access or protocol bypass is required. The impact is a moderate, resource-scaling inefficiency rather than an unbounded/free amplification, since energy fees already scale (linearly) with N.

### Recommendation
Track `operationIdentifier` as a running counter (e.g., an `AtomicLong`/mutable counter or the current list size) alongside `currentTransactionBalanceTrace` instead of recomputing `max()` over the growing list on every call, and consider building the transaction's operation list with a mutable/growable structure (e.g., `List<Operation>` accumulated locally and only converted to the protobuf `TransactionBalanceTrace` once at transaction finalization) to avoid the repeated `toBuilder().addOperation().build()` full-list copy.

  private void recordBalance(AccountCapsule accountCapsule, long diff) {
    TransactionBalanceTrace transactionBalanceTrace = balanceTraceStore.getCurrentTransactionBalanceTrace();

    if (transactionBalanceTrace == null) {
      return;
    }

    long operationIdentifier;
    OptionalLong max = transactionBalanceTrace.getOperationList().stream()
        .mapToLong(Operation::getOperationIdentifier)
        .max();
    if (max.isPresent()) {
      operationIdentifier = max.getAsLong() + 1;
    } else {
      operationIdentifier = 0;
    }

    ByteString address = accountCapsule.getAddress();
    Operation operation = Operation.newBuilder()
        .setAddress(address)
        .setAmount(diff)
        .setOperationIdentifier(operationIdentifier)
        .build();
    transactionBalanceTrace = transactionBalanceTrace.toBuilder()
        .addOperation(operation)
        .build();
    balanceTraceStore.setCurrentTransactionBalanceTrace(transactionBalanceTrace);
  }

  public void resetCurrentTransactionTrace() {
    if (!CommonParameter.getInstance().isHistoryBalanceLookup()) {
      return;
    }

    if (currentBlockId == null) {
      return;
    }

    if (!CollectionUtils.isEmpty(currentTransactionBalanceTrace.getOperationList())) {
      currentBlockBalanceTraceCapsule.addTransactionBalanceTrace(currentTransactionBalanceTrace);
    }

    currentTransactionId = null;
    currentTransactionBalanceTrace = null;
  }

  public void resetCurrentBlockTrace() {
    if (CommonParameter.getInstance().isHistoryBalanceLookup()) {
      putBlockBalanceTrace(currentBlockBalanceTraceCapsule);
      currentBlockId = null;
      currentBlockBalanceTraceCapsule = null;
    }
  }

  public void initCurrentBlockBalanceTrace(BlockCapsule blockCapsule) {
    if (CommonParameter.getInstance().isHistoryBalanceLookup()) {
      setCurrentBlockId(blockCapsule);
      currentBlockBalanceTraceCapsule = new BlockBalanceTraceCapsule(blockCapsule);
    }
  }

  public void initCurrentTransactionBalanceTrace(TransactionCapsule transactionCapsule) {
    if (!CommonParameter.getInstance().isHistoryBalanceLookup()) {
      return;
    }

    if (currentBlockId == null) {
      return;
    }

    setCurrentTransactionId(transactionCapsule);
    currentTransactionBalanceTrace = TransactionBalanceTrace.newBuilder()
        .setTransactionIdentifier(transactionCapsule.getTransactionId().getByteString())
        .setType(transactionCapsule.getInstance().getRawData().getContract(0).getType().name())
        .build();
  }
