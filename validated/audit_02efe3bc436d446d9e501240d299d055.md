## Analysis Result

### Title
Missing upper-bound check on `max_price_per_unit` allows resource-bounds packing overflow into adjacent fields during transaction hash computation - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/transaction_hash/transaction_hash.cairo`)

### Summary
The Starknet OS's `pack_resource_bounds` function packs three logically-separate fields (`resource`, `max_amount`, `max_price_per_unit`) into a single felt using fixed bit-offsets (64 bits for `resource`/`max_amount` boundary, 128 bits reserved for `max_price_per_unit`), but only range-checks `max_amount` against its intended width. `max_price_per_unit` is only checked to be non-negative, never checked to be `< 2**128`. This is the same bug class as the Balancer report: a value intended to occupy a fixed-width slot of a packed word is not bounded to that width before being combined arithmetically with neighboring fields, letting it "spill" into bits that are supposed to represent different, unrelated fields.

### Finding Description
`pack_resource_bounds` is defined as: [1](#0-0) 

```
func pack_resource_bounds{range_check_ptr}(resource_bounds: ResourceBounds) -> felt {
    assert_nn_le(resource_bounds.max_amount, 2 ** 64 - 1);
    assert_nn(resource_bounds.max_price_per_unit);
    return (resource_bounds.resource * 2 ** 64 + resource_bounds.max_amount) * 2 ** 128 +
        resource_bounds.max_price_per_unit;
}
```

The intended layout (per the documented comment format elsewhere in the codebase, e.g. `get_concat_resource` in `crates/starknet_api/src/transaction_hash.rs`) is `[resource_name (56 bit) | max_amount (64 bit) | max_price_per_unit (128 bit)]`. `assert_nn_le` bounds `max_amount` to `2**64 - 1`, matching its slot width. But `max_price_per_unit` — which occupies the low 128 bits of the packed felt — is only checked with `assert_nn` (non-negativity), never bounded to `2**128 - 1`. Since `resource_bounds` is a `felt` (up to ~2^251, loaded directly from the untrusted `tx` hint variable via the `LoadCommonTxFields` hint in `get_account_tx_common_fields`), an attacker fully controls this value as part of their own submitted transaction: [2](#0-1) 

Because the packing is `(resource * 2**64 + max_amount) * 2**128 + max_price_per_unit` computed as arithmetic over the felt field (not bit-masked truncation), an out-of-range `max_price_per_unit = P0 + k * 2**128` (for arbitrary `k`) produces the exact same packed felt as a transaction whose real `max_amount` differs by `k` and whose real `max_price_per_unit` is `P0`. This packed felt directly feeds `poseidon_hash_many` in `hash_fee_fields`, which is consumed by `hash_tx_common_fields` and ultimately `compute_invoke_transaction_hash` / `compute_declare_transaction_hash` / `compute_deploy_account_transaction_hash`: [3](#0-2) 

Meanwhile, the *actual* (unpacked, out-of-range) `max_price_per_unit` felt is what's used directly (not via the packed word) for real fee accounting, e.g. in `compute_max_possible_fee`: [4](#0-3) 

This creates a divergence between the value bound into the transaction-hash pre-image (which can collide with a different, "legitimate" `(resource, max_amount, max_price_per_unit)` triple) and the raw field values actually used for gas/fee accounting.

### Impact Explanation
This affects the transaction hashing path inside Starknet OS re-execution, reachable by any unprivileged transaction sender simply by crafting a v3 transaction with an out-of-range `max_price_per_unit` resource bound (a field fully attacker-controlled and part of a submitted transaction). Because the fee-fields hash is a component of the final transaction hash — which the OS asserts must equal the externally-computed/committed transaction hash (`AssertTransactionHash` hint) — a crafted, out-of-range `max_price_per_unit` can make the packed representation used for hashing collide with that of a different, "canonical" in-range triple. This breaks the intended one-to-one binding between a transaction's committed hash and its resource-bounds fields, undermining a core hashing invariant used for transaction identity/commitment during OS re-execution, and could enable honest-node divergence if different execution/verification paths decode or validate `max_price_per_unit` bounds inconsistently (e.g., some paths assume `< 2**128` per the documented layout while others do not enforce it explicitly here).

### Likelihood Explanation
Likelihood is moderate: exploitation requires only submitting a single, self-crafted V3 transaction (invoke/declare/deploy-account) with a `max_price_per_unit` field set above `2**128 - 1`. Whether this is actually reachable end-to-end depends on whether upstream layers (gateway validation, RPC/protobuf deserialization into a `u128`-typed `GasPrice`) already reject or truncate such out-of-range values before the transaction reaches OS re-execution — I was not able to fully confirm within these tool-call constraints whether a gateway-level bound check enforces `< 2**128` on `max_price_per_unit` prior to Starknet OS processing the raw hint-loaded felt. The OS-level function itself, however, does not perform this check independently, which is inconsistent with its treatment of `max_amount` and is the exact root-cause pattern called out in the source report.

### Recommendation
Add an explicit range check in `pack_resource_bounds` mirroring the one already present for `max_amount`:
```
assert_nn_le(resource_bounds.max_price_per_unit, 2 ** 128 - 1);
```
in place of (or in addition to) the current `assert_nn(resource_bounds.max_price_per_unit)` call, so that `max_price_per_unit` cannot exceed the 128-bit slot it is packed into, preventing overflow/collision with the `max_amount`/`resource` fields of the packed felt.

### Proof of Concept
Conceptual PoC (not executed, derived from code inspection):
1. Submit a V3 invoke transaction with `resource_bounds.l1_data_gas.max_price_per_unit = P0 + 2**128` (i.e., one "unit" beyond the 128-bit slot), while keeping `max_amount = A`.
2. Inside `pack_resource_bounds`, the packed felt becomes `(resource * 2**64 + A) * 2**128 + (P0 + 2**128) = (resource * 2**64 + A + 1) * 2**128 + P0`, which is numerically identical to the packed felt for a transaction with `max_amount = A + 1` and `max_price_per_unit = P0`.
3. This identical packed felt is hashed via `poseidon_hash_many` into `fee_fields_hash`, meaning the resulting transaction hash pre-image component cannot distinguish `(A, P0 + 2**128)` from `(A+1, P0)`, while `compute_max_possible_fee` (used for actual fee enforcement) uses the raw, unbounded `max_price_per_unit` value directly. func hash_fee_fields{range_check_ptr, poseidon_ptr: PoseidonBuiltin*}(
```text
    tip: felt, resource_bounds: ResourceBounds*, n_resource_bounds: felt
) -> felt {
    alloc_locals;

    let (local data_to_hash: felt*) = alloc();
    assert data_to_hash[0] = tip;
    assert_nn_le(tip, 2 ** 64 - 1);

    static_assert L1_GAS_INDEX == 0;
    static_assert L2_GAS_INDEX == 1;
    static_assert L1_DATA_GAS_INDEX == 2;

    with_attr error_message("Invalid number of resource bounds: {n_resource_bounds}.") {
        assert n_resource_bounds = 3;
    }

    // L1 gas.
    let l1_gas_bounds = resource_bounds[L1_GAS_INDEX];
    assert l1_gas_bounds.resource = L1_GAS;
    assert data_to_hash[1] = pack_resource_bounds(l1_gas_bounds);

    // L2 gas.
    let l2_gas_bounds = resource_bounds[L2_GAS_INDEX];
    assert l2_gas_bounds.resource = L2_GAS;
    assert data_to_hash[2] = pack_resource_bounds(l2_gas_bounds);

    // L1 data gas.
    let l1_data_gas_bounds = resource_bounds[L1_DATA_GAS_INDEX];
    assert l1_data_gas_bounds.resource = L1_DATA_GAS;
    assert data_to_hash[3] = pack_resource_bounds(l1_data_gas_bounds);

    let (hash) = poseidon_hash_many(n=n_resource_bounds + 1, elements=data_to_hash);
    return hash;
}
```

```text
// Returns the maximum possible fee that can be charged for the transaction.
func compute_max_possible_fee(tx_info: TxInfo*) -> felt {
    tempvar resource_bounds: ResourceBounds* = tx_info.resource_bounds_start;
    let n_resource_bounds = (tx_info.resource_bounds_end - resource_bounds) / ResourceBounds.SIZE;

    // Only V3 transactions with all resource bounds are supported.
    assert tx_info.version = 3;
    assert n_resource_bounds = 3;

    tempvar l1_gas_bounds: ResourceBounds = resource_bounds[L1_GAS_INDEX];
    tempvar l2_gas_bounds: ResourceBounds = resource_bounds[L2_GAS_INDEX];
    tempvar l1_data_gas_bounds = resource_bounds[L1_DATA_GAS_INDEX];

    return l1_gas_bounds.max_amount * l1_gas_bounds.max_price_per_unit + l2_gas_bounds.max_amount *
        (l2_gas_bounds.max_price_per_unit + tx_info.tip) + l1_data_gas_bounds.max_amount *
        l1_data_gas_bounds.max_price_per_unit;
```
