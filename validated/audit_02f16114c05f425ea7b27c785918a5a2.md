### Title
Premature/unconditional deletion of the OAuth state cookie allows an attacker to DoS a merchant's pending install/auth flow - (File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts)

### Summary
The GEB report describes an attacker front-running a state-mutating call (`popDebtFromQueue`) to invalidate a precondition (`unqueuedUnauctionedDebt == 0`) checked by another function (`auctionSurplus`), causing it to revert and denying service. The analogous pattern in `shopify-app-js` is in the OAuth `callback` handler: the single-use `state` cookie that anchors the CSRF check is deleted unconditionally *before* the callback query is validated, so any request that merely carries the still-valid signed cookie — even one with bogus/garbage query parameters — consumes (invalidates) that state token and prevents the legitimate OAuth completion from succeeding.

### Finding Description
`begin()` sets a signed, short-lived (`60000`ms) `state` cookie (`STATE_COOKIE_NAME`) scoped to the `callbackPath`, with `sameSite: 'lax'`: [1](#0-0) 

In `callback()`, the code reads and verifies the cookie, and then **unconditionally deletes it** before the query (HMAC + state match) is validated: [2](#0-1) 

Only afterward does the code check `validQuery()` (HMAC + `safeCompare` of `state`): [3](#0-2) [4](#0-3) 

Because the cookie is `sameSite: 'lax'`, it is automatically attached by the browser on top-level GET navigations that cross origins (e.g., a link/redirect an attacker controls). This means the single "slot" represented by that state cookie can be consumed by an attacker-crafted request that reaches the callback path with any (invalid) query string, deleting the cookie regardless of whether validation later succeeds — exactly mirroring the GEB pattern where an unprivileged actor pops a queue slot to invalidate the precondition another legitimate operation depends on.

### Impact Explanation
If an attacker can get a merchant's browser to navigate (top-level GET) to `<app>/auth/callback?shop=<shop>` with any garbage query string while the merchant's real OAuth flow (initiated via `begin()`) is still in flight (within the 60-second cookie lifetime), the cookie is deleted on this bogus request. When Shopify's genuine OAuth redirect subsequently reaches the callback with valid `code`/`state`/`hmac`, `cookies.getAndVerify(STATE_COOKIE_NAME)` returns nothing, causing `ShopifyErrors.CookieNotFound` to be thrown and the legitimate install/auth attempt to fail, forcing the merchant to restart the OAuth flow. This is a denial-of-service of the auth handler, triggerable by an unprivileged, anonymous actor targeting a single merchant during their OAuth flow, requiring no secret knowledge, no privileged access, and no MITM.

### Likelihood Explanation
Exploitation requires the attacker to time a forged GET request to the app's `/auth/callback` path during a merchant's ~60-second install/auth window and get it to execute with the merchant's cookies attached (e.g., via a crafted link, redirect chain, or malicious page the merchant is lured to visit mid-flow). The `sameSite: 'lax'` setting permits this for top-level navigations. This is a narrow but realistic window, and the low complexity of the payload (just a shop param) makes it easy to attempt repeatedly.

### Recommendation
Perform the HMAC/state validation (`validQuery`) before deleting the state cookie, and only delete it once the callback is confirmed to be a legitimate, successfully-validated completion (or when the request is definitively going to fail for a reason unrelated to cookie reuse). This prevents an attacker from being able to burn/invalidate a merchant's pending state token via an unauthenticated forged request, closing the front-running/DoS vector analogous to the GEB fix (validate/settle state before consuming the shared resource).

### Proof of Concept
1. Merchant clicks "Install app"; `begin()` sets a signed `state` cookie (`shopify_app_state`), 60s expiry, `sameSite=lax`, scoped to `callbackPath`.
2. Before the merchant's browser receives Shopify's OAuth redirect back to the app, an attacker gets the merchant's browser to perform a top-level GET navigation to `https://<app-domain>/auth/callback?shop=<shop>` (e.g. via a malicious link, or an ad/redirect the merchant clicks) — the cookie is sent automatically due to `sameSite=lax`.
3. Server executes `cookies.getAndVerify(STATE_COOKIE_NAME)` → cookie found and verified → `cookies.deleteCookie(STATE_COOKIE_NAME)` executes immediately (before any further validation of the query since this request has no valid `code`/`hmac`, `validQuery` will fail afterward, but the cookie is already gone).
4. Shopify's genuine callback redirect (with correct `code`, `state`, `hmac`) now arrives; `cookies.getAndVerify(STATE_COOKIE_NAME)` returns `undefined` since the cookie was already deleted, and `ShopifyErrors.CookieNotFound` is thrown, blocking the legitimate OAuth completion: [5](#0-4)

async function validQuery({
  config,
  query,
  stateFromCookie,
}: {
  config: ConfigInterface;
  query: AuthQuery;
  stateFromCookie: string;
}): Promise<boolean> {
  return (
    (await validateHmac(config)(query)) &&
    safeCompare(query.state!, stateFromCookie)
  );
}
