## Title
Order-dependent, permanent loss of an authorized `BatchProofMethodId` activation due to un-sorted `da_txs` processing in `run_l1_block` - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
`LightClientProofCircuit::run_l1_block` applies `DataOnDa::BatchProofMethodId` blobs strictly in `da_txs` iteration order, using `batch_proof_method_ids.last().expect("Should be at least one").0` as the monotonicity gate. If two independently valid, correctly-signed method-id blobs for heights `H1 < H2` are processed with `H2` before `H1` in the same block, the `H1` update is silently and permanently discarded, because the `<=` check compares against the tail of the vector rather than any authority-defined sequence number.

### Finding Description
The binding claimed by the accessor's design is:

`final_state(BatchProofMethodIdAccessor) after processing block with blob set {blob(H1), blob(H2)}` should be identical regardless of the relative position of `blob(H1)` and `blob(H2)` in `da_txs`, i.e. it should be a function of the *authority-signed* `(activation_l2_height, method_id)` pairs alone, not of Bitcoin transaction ordering.

In `run_l1_block`, the `DataOnDa::BatchProofMethodId` branch computes: [1](#0-0) 

`last_activation_height` is read from `batch_proof_method_ids.last()` — the tail of the vector *as it currently stands in the working set*, which is mutated in-place by `BatchProofMethodIdAccessor::insert` for each processed blob: [2](#0-1) 

Trace for `da_txs = [blob(H1), blob(H2)]` (canonical order): iteration 1 sees `last_activation_height = 0` (or genesis), inserts `(H1, id1)`; iteration 2 sees `last_activation_height = H1`, `H2 > H1` passes, inserts `(H2, id2)`. Final vector: `[..., (H1,id1), (H2,id2)]`.

Trace for `da_txs = [blob(H2), blob(H1)]` (attacker-reordered replay of the same two validly-signed blobs): iteration 1 sees `last_activation_height = 0`, inserts `(H2, id2)`. Iteration 2 processes `blob(H1)`: `last_activation_height` is now `H2` (the accessor's tail), and `H1 <= H2` is true, so the branch hits `continue` at line 541 — the id1 activation is **skipped, never inserted**, and can never be inserted later either, since any future re-submission of the same signed `H1` blob will forever fail the same `<=` check against the now-permanent tail `H2`.

The two orderings therefore produce *different final states* for the identical set of authority-signed inputs: `[..., (H1,id1), (H2,id2)]` vs `[..., (H2,id2)]`. The security-council-authorized activation of `id1` for the L2 height range `[H1, H2)` is irrecoverably lost. Existing guards (`verify_method_id_security_council`, chain-id check) only validate signature/authenticity of each blob in isolation; none of them enforce that the *set* of activations applied is independent of relative blob position, and there is no sort-by-`activation_l2_height` step before or during the `'blob_loop'`.

### Impact Explanation
The dropped activation is permanent for that light-client-proof chain (the accessor is append-only across all subsequent blocks, and the `<=` check makes re-insertion of `H1` impossible once `H2` has become the tail). Any batch proof that was generated by the batch prover using method id `id1` for L2 blocks in `[H1, H2)` will fail verification against the LCP's JMT state (which still reflects the pre-`H1` method id for that range), i.e. a true, authorized state transition becomes permanently unprovable through the light client circuit — this is the "a true one made unprovable" Critical category. It also means the security council's chosen upgrade schedule is overridden purely by Bitcoin-transaction positioning, violating the "activation height ordering must be authority-determined" property. The blast radius covers every honest light-client prover processing that same block (since they all see the same fixed transaction order in the finalized block, they'd all reach the same corrupted result — this is a determinism-preserving but authority-violating bug, not a split between honest provers on the same block).

### Likelihood Explanation
Requires: (1) two real, validly-signed `BatchProofMethodId` blobs for distinct heights existing on the public network (attacker-observable, since Bitcoin data is public), and (2) the attacker being able to get copies of both re-inscribed reveal transactions mined within the same L1 block with `H2`'s copy positioned ahead of `H1`'s copy. Copying and re-broadcasting the exact witness/script payload is within the granted attacker capabilities ("pay Bitcoin fees to inscribe or mine any Bitcoin transaction"); influencing relative ordering within a single block via fee-rate bidding is a normal, low-cost Bitcoin operation (no hashrate majority needed). The scenario is more likely if the council issues sequential upgrades close together in time such that both are still unconfirmed/replayable when the attacker acts.

### Recommendation
Do not derive `last_activation_height` from vector-tail order coupled to blob processing order. Instead, either (a) collect all `BatchProofMethodId` blobs seen in the block, validate each independently, then sort by `activation_l2_height` before inserting, rejecting/ignoring only truly stale ones against the pre-block state; or (b) compare each candidate's `activation_l2_height` against the maximum activation height across *all* entries already committed prior to this block (not the just-mutated in-loop tail), and require insertion to always keep the vector sorted, inserting at the correct position rather than only appending.

// crates/light-client-prover/src/circuit/mod.rs test target: run_l1_block
// Setup: initial method id at height 0. Two council-signed BatchProofMethodId blobs:
//   blob_h1 = create_new_method_id_tx(H1=100, id1, method_id_sender, Network::Nightly)
//   blob_h2 = create_new_method_id_tx(H2=200, id2, method_id_sender, Network::Nightly)
// (Use the same helper `create_new_method_id_tx` + valid council signatures as in
//  crates/light-client-prover/src/tests/mod.rs)

#[test]
fn test_method_id_activation_order_dependence() {
    // Run A: da_txs = [blob_h1.clone(), blob_h2.clone()]
    let result_a = /* run_l1_block with da_txs = vec![blob_h1.clone(), blob_h2.clone()] */;
    let ids_a = BatchProofMethodIdAccessor::<ProverStorage>::get(&mut working_set_a).unwrap();

    // Run B: da_txs = [blob_h2, blob_h1]  (attacker-reordered replay)
    let result_b = /* run_l1_block with da_txs = vec![blob_h2, blob_h1] */;
    let ids_b = BatchProofMethodIdAccessor::<ProverStorage>::get(&mut working_set_b).unwrap();

    // Binding under test: final accessor state must be identical regardless of blob order.
    assert_eq!(ids_a, vec![(0u64, INITIAL_ID), (100u64, id1), (200u64, id2)]);
    assert_eq!(ids_b, ids_a); // FAILS: ids_b == vec![(0, INITIAL_ID), (200, id2)] — H1/id1 silently dropped
}
