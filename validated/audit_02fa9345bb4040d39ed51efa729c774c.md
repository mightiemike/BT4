### Title
sBTC depositor's BTC is permanently unrecoverable because PoX-5 disables the reclaim path while the watched deposit address rotates every reward cycle - ([File: stackslib/src/chainstate/nakamoto/signer_set.rs])

### Summary
The tbtc bug is: a funder pays for keep creation, the signing group can decline/fail to establish the keep in time, and there is no protocol-level refund of the funder's payment. In this repo, PoX-5's sBTC integration reproduces the same asymmetry for BTC depositors: the P2TR deposit address that a depositor sends BTC to is derived from the *current* aggregate pubkey at reward-cycle boundaries, and the reclaim leaf is deliberately built with `lock_time = u16::MAX`, i.e. effectively disabled. If the signer set/aggregate key that a deposit was locked to is rotated or fails to process the deposit before the cycle turns over, the depositor has no push refund (no one credits them) and no pull refund (the CSV reclaim path is unusable for ~65535 blocks). Funds sent to a per-cycle sBTC address can become permanently stuck with no recovery path in-protocol, mirroring exactly the "funder loses payment to keep if signing group is not established in time" bug class, but for BTC principal rather than a keep-creation fee.

### Finding Description
`pox_5_compute_and_update_signers` computes, once per reward cycle, a fresh sBTC deposit-watch address (`WaterfallCycleSet.sbtc_address`) from whatever `get-current-aggregate-pubkey` currently returns: [1](#0-0) 

The address derivation itself is a P2TR taproot output committing to a `deposit` leaf (spendable by the signer aggregate key) and a `reclaim` leaf (spendable by the depositor after a CSV timelock): [2](#0-1) 

Critically, the PoX-5 wrapper bakes in `lock_time = u16::MAX` and a `[OP_RETURN]` user-script, which the module's own doc comment says "disable[s] the reclaim path": [3](#0-2) [4](#0-3) 

Because the watched address is recomputed every reward cycle from `get-current-aggregate-pubkey` (which itself is set by the pox-5 signer set via `vote-for-aggregate-public-key`, a threshold vote requiring 70% signer weight to conclude, and can be re-voted/rotated across cycles): [5](#0-4) 

a depositor who broadcasts BTC to the cycle-N address is only safe if the cycle-N signer set (and its aggregate key) actually processes/credits the deposit before the key material or willingness to cooperate under the old aggregate key is retired at the next cycle boundary. Since:
1. There is no pull-refund mechanism (reclaim CSV effectively disabled at `u16::MAX`), and
2. There is no push-refund mechanism visible in this codebase's PoX-5/sbtc-registry integration for deposits that never get processed,

the depositor's BTC is stuck exactly like the tbtc funder's fee: paid to a party (the aggregate-key holders of a given cycle) whose cooperation is not guaranteed, with no way for the depositor to reclaim it if that cooperation never materializes.

### Impact Explanation
If a signer set (a legitimate minority relative to future cycles, or one that simply loses enough weight/rotates keys) never signs/relays the BTC transaction crediting a deposit before the aggregate key rotates, the underlying BTC is permanently locked in a taproot output whose only two spending paths are (a) the old, now-uncooperative aggregate key, and (b) a reclaim path timelocked to `u16::MAX` (~65535 blocks, well over a year, explicitly called out as "disabling the reclaim path" in-repo). This is a permanent, irreversible loss of depositor funds — the BTC-side analog of the tbtc funder losing their fee — with no mechanism in the Stacks-side contracts examined (`pox-5.clar`, `signers-voting.clar`, `signer_set.rs`, `sbtc.rs`) to detect the stranded deposit and make the depositor whole.

### Likelihood Explanation
This is triggerable by ordinary protocol operation, not just adversarial minority action: any deposit that is broadcast near a reward-cycle boundary, or any cycle whose signer set changes composition/aggregate key (which is an expected, routine PoX-5 event via `vote-for-aggregate-public-key`), can strand a deposit. No majority collusion is required — simply a lack of timely processing by the current signer set, or a scheduled key rotation, is sufficient. This is compounded by the fact that the reclaim path is explicitly and permanently disabled in the current scaffolding rather than being a rare edge case.

### Recommendation
Adopt the same fix pattern that upstream tbtc applied for this class of bug (pull-refund, not push): give the sBTC deposit reclaim leaf a real, bounded `lock_time` (not `u16::MAX`) so depositors can reclaim BTC that a signer set fails to process before it rotates its aggregate key, and/or maintain a mapping from an aggregate pubkey to the reward cycle(s) during which its signer set is contractually obligated to keep honoring deposits made against addresses derived from it, so a stranded deposit can still be credited or refunded after key rotation.

### Proof of Concept
1. At reward-cycle boundary for cycle N, `pox_5_compute_and_update_signers` reads `get-current-aggregate-pubkey` = `pubkey_N` and derives `sbtc_address_N` via `sbtc_pox5_deposit_taproot_output_key(pubkey_N, ...)` with `lock_time = u16::MAX` baked in (`stackslib/src/chainstate/nakamoto/signer_set.rs:778-807`, `stackslib/src/chainstate/stacks/sbtc.rs:88-110`).
2. A user broadcasts a BTC deposit to `sbtc_address_N` late in cycle N.
3. Before the deposit is observed/processed by the cycle-N signer set (e.g., due to normal latency, signer downtime, or a scheduled key rotation), a new aggregate key `pubkey_N+1` is approved via `vote-for-aggregate-public-key` (`stackslib/src/chainstate/stacks/boot/signers-voting.clar:143-171`), and `sbtc_address_N+1 != sbtc_address_N` becomes the new watched address.
4. The cycle-N signers, no longer the "current" set, have no protocol obligation or path to sign a transaction moving the depositor's UTXO; the reclaim leaf's CSV lock time of `u16::MAX` blocks makes the depositor's own reclaim path practically unusable.
5. The BTC is now permanently unrecoverable, with no push-refund or pull-refund mechanism present in the reviewed contracts/code — the funder (depositor) loses their payment exactly as in the tbtc report, without needing majority collusion, just ordinary key rotation/latency.

//! sBTC P2TR (taproot) deposit-script derivation.
//!
//! The per-cycle sBTC recipient is a witness-v1 P2TR output committing to a
//! 2-leaf script tree:
//!
//! - deposit: `<deposit-data> OP_DROP OP_PUSHBYTES_32 <x-only-pubkey> OP_CHECKSIG`
//!   where `<deposit-data> = <max-fee:u64-be> || <consensus-encoded recipient principal>`.
//! - reclaim: `<lock_time push> OP_CSV <user-supplied-bytes>`. PoX-5 scaffolding
//!   uses `lock_time = u16::MAX` and `[OP_RETURN]` for user bytes, disabling
//!   the reclaim path.
//!
//! The taproot internal key is the BIP-0341 NUMS x-coordinate (no known
//! discrete log), so neither leaf is reachable via key-path; only script-path
//! through the two leaves.
//!

/// PoX-5 wrapper around `sbtc_deposit_taproot_output_key`.
///
/// Bakes in the values PoX-5 uses:
/// (`lock_time = u16::MAX`, user-script `[OP_RETURN]`)
///  and accepts the
/// pubkey in 33-byte compressed form (which is what
/// `get-current-aggregate-pubkey` returns).
pub fn sbtc_pox5_deposit_taproot_output_key(
    aggregate_pubkey_compressed: &[u8; 33],
    recipient: &PrincipalData,
    max_fee_sats: u64,
) -> Result<[u8; 32], ChainstateError> {
    let xonly: &[u8; 32] = aggregate_pubkey_compressed[1..]
        .try_into()
        .expect("constant slice length");
    sbtc_deposit_taproot_output_key(
        xonly,
        recipient,
        max_fee_sats,
        u16::MAX,
        &[Opcode::OP_RETURN as u8],
    )
}
