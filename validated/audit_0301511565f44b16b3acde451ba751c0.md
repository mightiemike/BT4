## Analog Found

### Title
Missing validation on `DeleteAccountAction.beneficiary_id` allows permanent burn of the deleted account's balance - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
The reported Lido bug is a missing zero-address check on a security-sensitive address field (`addGuardian`), which lets an unusable/unspendable value be accepted where only a valid, reachable address should be allowed. The analogous defect in nearcore is in `validate_delete_action`, the sole validation applied to `DeleteAccountAction::beneficiary_id`. It only checks that the value is a syntactically well-formed `AccountId`, never that it is a real, reachable, spendable destination (i.e. not the reserved `"system"` sentinel account, not an account that can never be registered, and not the very account being deleted). Just like `guardian != address(0)` was missing in Lido, `beneficiary_id` is missing an equivalent "not a sentinel / not unusable" check here.

### Finding Description
`validate_delete_action` is the only validation performed on the beneficiary field of a `DeleteAccount` action: [1](#0-0) 

It merely forwards to `validate_action_account_id`, which checks string format only: [2](#0-1) 

At execution time, `action_delete_account` unconditionally builds a balance-refund receipt addressed to whatever `beneficiary_id` was supplied, with no check that the id refers to an account that exists or can ever exist: [3](#0-2) 

That refund receipt is a system/refund receipt (`predecessor_id == "system"`). The runtime's own refund-processing rule states plainly that refund receipts can never create the destination account, and if the refund's execution fails, the deposit amount is burnt rather than returned to anyone: [4](#0-3) 

This is confirmed by the runtime's own handling: refund receipts to `"system"`-typed or nonexistent targets are rejected with `AccountDoesNotExist`, and the burn path is explicit at the receipt-processing level: [5](#0-4) [6](#0-5) 

Because `validate_delete_action` never rejects `beneficiary_id == "system"` (a syntactically valid, always-nonexistent account id) or `beneficiary_id == account_id` (the very account about to be removed), a `DeleteAccount` action can be constructed whose refund receipt is guaranteed to fail and therefore have its full balance burnt — exactly the "unusable target address" failure mode the zero-address check pattern exists to prevent.

### Impact Explanation
A single `DeleteAccountAction` submitted with a sentinel/self beneficiary permanently and irreversibly destroys the entire remaining NEAR balance of the account being deleted (burnt, not refunded to anyone), because the runtime treats a failed system refund as a burn by design. This is a concrete, unrecoverable loss of funds triggered purely by a value the protocol should have rejected at validation time, analogous to accepting `address(0)` as a guardian and then having privileged operations silently fail against it.

### Likelihood Explanation
Any account owner (or any relayer/meta-transaction sender constructing a `DeleteAccount` action on a user's behalf, e.g. via `Delegate`/`DelegateV2`) can trigger this with an ordinary transaction — no special privileges, validator status, or network position are required. The only requirement is supplying `beneficiary_id = "system"` (or the account's own id) in the `DeleteAccountAction`, both of which pass the existing `AccountId::validate` format check unmodified.

### Recommendation
Extend `validate_delete_action` to reject beneficiary ids that can never be a valid refund target, mirroring the recommended `require(addr != address(0), ...)` pattern:
```rust
fn validate_delete_action(
    action: &DeleteAccountAction,
    account_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_action_account_id(&action.beneficiary_id)?;
    if action.beneficiary_id.is_system() {
        return Err(ActionsValidationError::InvalidAccountId {
            account_id: action.beneficiary_id.to_string(),
        });
    }
    if action.beneficiary_id == *account_id {
        return Err(ActionsValidationError::InvalidAccountId {
            account_id: action.beneficiary_id.to_string(),
        });
    }
    Ok(())
}
```

### Proof of Concept
1. Create/own an account `alice.near` with a positive balance.
2. Sign a transaction with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "system".parse().unwrap() })`, receiver `alice.near`.
3. `validate_delete_action` accepts it (format-only check) as shown at [1](#0-0) .
4. `action_delete_account` executes, deletes `alice.near`, and emits `Receipt::new_balance_refund(&"system", account_balance)` per [3](#0-2) .
5. The refund receipt (predecessor `"system"`) cannot create/target the nonexistent `"system"` account and fails with `AccountDoesNotExist`; per the burn-on-failed-refund rule at [5](#0-4)  the entire `account_balance` is permanently burnt with no recipient.
