### Title
Unsigned underflow in `PathToBottom::is_left_descendant` on a zero-length edge path leading to panic/incorrect descent classification during commitment tree updates - ([File: crates/starknet_patricia/src/patricia_merkle_tree/node_data/inner_node.rs])

### Summary
`PathToBottom::is_left_descendant` computes `self.path.0 >> (self.length.0 - 1)`, where `self.length.0` is a `u8`. If `length` is `0` (a legitimate, explicitly constructed value via `PathToBottom::new_zero()` / `EdgePathLength(0)`), the subtraction `0u8 - 1` underflows: in debug builds this panics (arithmetic overflow check), and in release builds it wraps to `255`, silently producing a semantically wrong (but not out-of-range for `U256`) shift amount. This mirrors the DML2.1 bug: an explicitly-zeroed unsigned field feeds a `width/length - 1` expression that is then used to drive a shift, without a guard for the zero case. [1](#0-0) 

### Finding Description
`EdgePathLength(0)` is a valid, constructible value (`PathToBottom::new_zero()`), and `PathToBottom` values with length 0 are used as identity/no-op path markers (see `DescentStart` construction with `Path(PathToBottom::new_zero())` throughout `patricia/utils.rs` and `create_tree_helper_test.rs`). [2](#0-1) 

`is_left_descendant()` is called from `update_edge_node` in the updated-skeleton tree builder, which is the core routine that turns a set of leaf modifications (i.e., storage writes triggered by *any* transaction) into skeleton updates for the state commitment tree: [3](#0-2) 

The `path_to_bottom` passed into `update_edge_node` originates from `OriginalSkeletonNode::Edge(path_to_bottom)` — data that is either read from the previous committer state (attacker cannot directly forge this) or synthesized internally by `remove_first_edges`/`concat_paths` during recursive updates. `remove_first_edges` explicitly allows the result length to become `0` (`self.length - n_edges` where `n_edges == self.length` is valid, only guarded against `n_edges > length`): [4](#0-3) 

So an edge node whose original path length equals the number of edges removed produces a `length == 0` `PathToBottom`. If such a zero-length edge node is later passed into `update_edge_node` (e.g., during recursive processing of nested edge/leaf structures created by an adversarial pattern of storage writes across a transaction's calldata), `is_left_descendant()` underflows.

### Impact Explanation
- In debug/test builds (and any build with overflow checks enabled, which `cargo build --release` does not disable by default only if explicitly configured), this is a panic reachable from processing a single block's state diff, which is a **crash / inability to build or re-execute a block** (a node divergence risk if only some nodes run with overflow checks and others don't, or a full derailment if all sequencer/committer nodes use the same build profile).
- In release builds without overflow checks, `length.0 - 1` wraps to `255`, and `self.path.0 >> 255` is evaluated on the `U256` path value. Since `path.0` is bounded to at most 251 bits, shifting a 251-bit-max value right by `255` yields `0` in all cases, so `is_left_descendant` always returns `true` regardless of the actual path — this **misclassifies the descent direction**, causing `update_edge_node` to route leaf modifications to the wrong child subtree. This directly risks producing a **wrong committed root hash**, i.e., honest-node divergence in the committed state root for the block, since different runtime configurations (or the same node under different builds) could produce different root hashes for the same state diff.

### Likelihood Explanation
Reaching this precise state requires the committer/skeleton-builder to encounter a zero-length `PathToBottom` on an `Edge` node that is passed through `update_edge_node`'s `is_left_descendant()` call, which requires a specific but constructible pattern of storage-key modifications relative to existing tree structure (edge collapsing via `remove_first_edges` down to length 0). This is a state-shape corner case rather than something a single crafted transaction directly injects a raw value into — it's data-dependent on the Merkle tree structure at commit time, similar to how the DML2.1 bug depended on the phantom-pipe cursor path deliberately zeroing a field. Given the complexity of engineering the required tree shape, likelihood is assessed as **medium**, but the reachability is from ordinary state writes performed by any transaction sender (invoke/declare/deploy causing storage writes), not from any operator/prover-only path.

### Recommendation
Guard `is_left_descendant` (and the related `remove_first_edges`/shift call sites) for the `length == 0` case explicitly, e.g.:
```rust
pub fn is_left_descendant(&self) -> bool {
    match self.length.0.checked_sub(1) {
        Some(shift) => self.path.0 >> shift == 0,
        None => true, // zero-length path: no path bits to inspect, i.e. trivially "left" (or handle as an explicit invariant violation).
    }
}
```
Add an explicit invariant check/test to confirm the intended semantics for `length == 0` in `update_edge_node`, ensuring both debug and release builds compute the identical committed root for such inputs.

### Proof of Concept
A concrete PoC requires constructing a `PathToBottom`/skeleton tree state where an original `Edge` node's `path_to_bottom.length` is reduced to `0` via `remove_first_edges` and then passed to `update_edge_node`, at which point:
```rust
let path = PathToBottom::new_zero(); // length = 0
path.is_left_descendant(); // debug: panics on `0u8 - 1`; release: shifts by 255 (wrapped), always returns true
```
I was not able to fully trace an end-to-end minimal transaction/calldata sequence that forces this exact tree shape within the scope of static code search (this requires either running the committer against a crafted state diff or deeper analysis of `update_node_in_nonempty_tree`/`split_leaves` recursion, which is not confirmed from indexed code alone). This should be validated with a live/dynamic Devin session against `starknet_patricia`'s test harness (`create_tree_helper_test.rs`) to construct the exact leaf/skeleton input triggering `length == 0` at the `is_left_descendant()` call site.
