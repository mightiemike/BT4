### Title
Divide-before-multiply reward computation causes avoidable rounding-error leakage in `MortgageService.computeReward` (legacy vote-reward path) - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The legacy (pre-Vi-algorithm) SR voting-reward calculation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` performs a division (`userVote / totalVote`) before multiplying by `totalReward`, exactly the "multiple divisions instead of one" pattern flagged in the River.sol report. This introduces avoidable rounding error into a value that is paid out to real TRX holders via the public `WithdrawBalanceContract` actuator.

This mirrors the reported bug class precisely: instead of computing the single, most-precise expression `userVote * totalReward / totalVote` (ideally in `BigInteger`/fixed-point form to avoid overflow, as is done everywhere else in this same class, e.g. the Vi-based `computeReward(beginCycle, endCycle, ...)` at lines 215-227 which correctly uses `BigInteger` multiply-then-divide), the code first divides `userVote` by `totalVote` into a lossy `double`, then multiplies by `totalReward`. This is the same "divide, then multiply" ordering that the report identifies as introducing unnecessary rounding error compared to reducing to a single division.

The same anti-pattern also appears in the still-active DPoS standby-witness incentive code: [2](#0-1) [3](#0-2) 

Both divide `totalPay`/`voteSum` first (as `double`) and only then multiply by each witness's `voteCount`, rather than doing `voteCount * totalPay / voteSum` (or better, integer/BigInteger arithmetic) in one division step.

This `computeReward(cycle, votes)` path is reachable by any unprivileged user: `WithdrawBalanceActuator.execute` (an actuator for the public `WithdrawBalanceContract`) unconditionally calls `MortgageService.withdrawReward`: [4](#0-3) 

which, for any account whose unwithdrawn reward cycles fall before `getNewRewardAlgorithmEffectiveCycle()`, routes through `getOldReward` → the legacy `computeReward(cycle, votes)`: [5](#0-4) [6](#0-5) 

### Impact Explanation
Because the division happens before the multiplication, and `double` cannot exactly represent most fractional vote ratios, the computed `reward` systematically loses precision relative to the mathematically exact `userVote * totalReward / totalVote`. Since `double` arithmetic is deterministic (IEEE-754) it will not cause a chain fork/consensus divergence between nodes, but it causes a real accounting divergence: the sum of per-voter rewards paid out will generally not equal the `totalReward` recorded in `delegationStore` for that cycle/witness, silently leaking or under/over-paying value at each withdrawal versus the intended exact split. This is the same class of impact called out in the original report — rounding errors that do not benefit the party they're computed for (here, the voter/staker), analogous to underpriced/mispriced settlement of a reward distribution.

### Likelihood Explanation
High likelihood of being exercised: any account with unclaimed vote rewards accrued in cycles prior to `newRewardAlgorithmEffectiveCycle` will trigger this exact code path the next time it submits a `WithdrawBalanceContract`, or even just calls the read-only `queryReward`/vote related RPCs. No special privileges are required — this is a standard user action (freeze/vote/withdraw flow available on every java-tron network).

### Recommendation
Refactor `computeReward(long cycle, List<Pair<byte[], Long>> votes)` (and similarly `MortgageService.payStandbyWitness` / `IncentiveManager.reward`) to avoid dividing before multiplying. Compute the reward as a single division using widened integer arithmetic, e.g. `BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote))`, consistent with how the newer Vi-based `computeReward(beginCycle, endCycle, ...)` already does it in the same class.

### Proof of Concept
1. Set up a cycle where `totalVote = 3`, `userVote = 1` (i.e. voter owns exactly 1/3 of votes), and `totalReward = 10` (in SUN).
2. Exact value: `1 * 10 / 3 = 3.333...` → correctly rounded integer result should be `3`.
3. Current code: `voteRate = (double) 1 / 3 = 0.3333333333333333`; `reward += voteRate * 10 = 3.333333333333333` → cast to `long` inside `reward +=` still truncates similarly here, but with larger `totalReward`/`userVote` magnitudes (e.g. `userVote = 1_000_000_000_007L`, `totalVote = 3_000_000_000_023L`, `totalReward = 987_654_321L`) the double-precision division loses bits that the exact integer `multiply-then-divide` would retain, producing a different (and non-reconcilable against `delegationStore` per-witness totals) result across many voters in the same cycle. Running both formulas side by side (as already unit-tested elsewhere in this repo, e.g. `RepositoryImplHardenTest.testUsageToBalanceCorrectAcrossDoublePrecision`, which specifically demonstrates `BigInteger` vs. naive arithmetic divergence for similar magnitude values) confirms the discrepancy.

    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
