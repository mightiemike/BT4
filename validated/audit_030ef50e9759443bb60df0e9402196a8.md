### Title
WorkflowSpec.Validate accepts and silently sets an empty `WorkflowOwner` when the YAML `owner` field is blank but `name` is set - ([File: core/services/job/models.go])

### Summary
`WorkflowSpec.Validate` uses the check `if s.Owner+s.Name != ""` to decide whether to take the owner/name values from the parsed YAML SDK spec. Because this is a string-concatenation check rather than validating each field individually, an attacker-supplied workflow YAML with `owner: ""` and a non-empty `name` still satisfies the condition, causing `w.WorkflowOwner` to be set to the empty string (`strings.TrimPrefix("", "0x")` == `""`) while `w.WorkflowName` is populated from attacker input.

### Finding Description
In `core/services/job/models.go`, `WorkflowSpec.Validate` does: [1](#0-0) 

The intent (per the comment) is: "for yaml-based workflow specs, use the owner & name fields defined there [if both are present]; otherwise fall back to the owner/name already on the job spec." The implementation instead checks `s.Owner+s.Name != ""`, which is true whenever *either* field is non-empty. If an attacker crafts a YAML workflow where `owner` is `""` and `name` is any non-empty string, the branch is taken, `w.WorkflowOwner` is overwritten with `TrimPrefix("", "0x")` → `""`, and `w.WorkflowName` is set to the attacker-controlled `name`. The only subsequent check in `Validate` is on `len(w.WorkflowID)` (derived from the content-addressed CID, independent of owner/name), so an empty `WorkflowOwner` combined with an arbitrary `WorkflowName` passes validation cleanly: [2](#0-1) 

This means a YAML workflow spec's `owner` field is not required to be a well-formed identifier; supplying an empty owner does not cause rejection as long as `name` is non-empty (or vice versa), producing an internally-inconsistent record: a named workflow with no attributable owner. Because `WorkflowOwner` is a `db`-indexed column used to key/attribute workflow specs, this creates the potential for owner-attribution confusion in code paths that rely on `WorkflowOwner` (e.g., DB queries, uniqueness constraints, or any consumer of the stored spec that assumes owner is always populated for a named workflow).

### Impact Explanation
This is best classified as a data-integrity / input-validation bug rather than a confirmed authentication or authorization bypass. I was not able to trace, within the available context, a downstream authorization/ACL check in this repository snapshot that gates privileged actions purely on `WorkflowSpec.WorkflowOwner` being non-empty (e.g., an on-chain workflow registry ownership check reachable from this exact validation path). Without that downstream trace, I cannot confirm this rises to "auth bypass" or "unauthorized transaction/workflow execution" as required by the bounty criteria — it is a real logic defect in the validation condition, but its exploitable security impact (beyond storing a spec with an empty owner field) is unproven from the code inspected.

### Likelihood Explanation
Trivially reachable: any unprivileged caller able to submit a workflow spec (YAML `owner: ""`, `name: "<value>"`) through the job/workflow creation path exercises this exact branch. The precondition (crafting owner="" name=non-empty) is fully attacker-controlled and requires no special privilege.

### Recommendation
Change the condition to require both fields to be authoritatively present (and consistent) rather than concatenation-based truthiness, e.g. `if s.Owner != "" && s.Name != ""`, and explicitly reject/report an error when exactly one of `owner`/`name` is set (partial specification), rather than silently defaulting the missing field to empty.

### Proof of Concept
Unit test in `core/services/job/models_test.go`:
1. Construct a `WorkflowSpec` with `SpecType: YamlSpec` and a `Workflow` YAML body containing `owner: ""` and `name: "my-workflow"` (and a valid `WorkflowID` of length 64 to isolate the owner/name behavior).
2. Call `w.Validate(ctx)`.
3. Assert that the current code returns `nil` error and `w.WorkflowOwner == ""` while `w.WorkflowName == "my-workflow"` — demonstrating the spec is accepted with an empty owner attributed to a named workflow, i.e., the "both present" invariant intended by the comment is not enforced.
4. Expected/fixed behavior: `Validate` should return an error (e.g., "owner and name must both be provided or both omitted") instead of accepting the partially-specified pair.

Given the inability to confirm a concrete downstream compromise path (auth bypass, unauthorized execution, secret disclosure) from the code available, this should be treated as a validation-logic defect requiring further tracing of `WorkflowOwner` consumers (e.g., workflow registry sync, RBAC checks) before escalating severity.
