### Title
Inconsistent price snapshots between `current-notional` and `added-collateral-value` in `collateral-add` allow the capacity (health) check to be bypassed - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
In `collateral-add`, the "future capacity must not decrease" check compares `current-capacity` (derived from `current-notional`, computed from oracle prices resolved *before* `write-feeds` is invoked) against `future-capacity` (derived partly from `added-collateral-value`, computed *after* `write-feeds` updates the price cache). The two USD-value components of the same inequality are evaluated against two different price snapshots, so the check can pass even when the position would actually be unhealthy under one consistent price view.

### Finding Description
`collateral-add` computes the values in this order for a user with existing debt who is adding a *new* collateral asset:

1. `current-notional` (and thus `current-coll-usd`/`current-debt-usd`) is computed from `get-notional-evaluation` using whatever prices are currently cached/resolved at that point in execution. [1](#0-0) 
2. `write-feeds` is then called, which resolves/writes the (possibly caller-supplied) fresh price feeds into the oracle cache for this transaction. [2](#0-1) 
3. `current-capacity` is derived from the pre-`write-feeds` `current-coll-usd`. [3](#0-2) 
4. `added-collateral-value` (via `get-asset-value`) and thus `future-coll-usd`/`future-capacity` are computed *after* `write-feeds`, i.e., using the fresh, caller-controlled price feed for the newly-added asset. [4](#0-3) 

The safety assertion `(asserts! (>= future-capacity current-capacity) ERR-UNHEALTHY)` therefore combines a "before-price-update" baseline with an "after-price-update" addition. This is the same class of bug as the report's total-vs-individual mismatch: two related quantities that are supposed to be computed from the same underlying state end up computed from different states within a single transaction, because one value is bound early and used after its source (the oracle price cache) is mutated by `write-feeds`. If the caller supplies a `price-feeds` payload that inflates the price of the asset being added relative to the price implicitly used for the pre-existing collateral snapshot, `future-capacity` can be made to appear non-decreasing (satisfying the check) while the true, fully-refreshed capacity would actually have decreased.

### Impact Explanation
This mismatch weakens the capacity/health invariant meant to prevent users from adding new collateral in a way that would let them subsequently under-collateralize or manipulate LTV boundaries against a borrow position. Since egroup capacity checks gate borrowing power and liquidation thresholds, a bypass here can permit debt positions to be pushed into unsafe states relative to actual collateral value, i.e., a path toward under-collateralized debt / impaired liquidation health — a form of temporary freezing/impairment of protocol solvency guarantees for the affected position, without directly involving DAO compromise, oracle-third-party depeg, or flashloan mechanics.

### Likelihood Explanation
Likelihood depends on the attacker's ability to supply a `price-feeds` payload for the *new* collateral asset that is valid (passes oracle freshness/signature checks) yet more favorable than the price snapshot already reflected in `current-notional`. Because `price-feeds` is caller-supplied per the function signature `(price-feeds (optional (list 3 (buff 8192))))`, and `write-feeds` is only invoked after `current-notional` is captured, the ordering itself is deterministic and reachable in a single transaction — no cross-block timing or reorg is required, matching the single-transaction/single-block analog class.

### Recommendation
Call `write-feeds` (or otherwise resolve/refresh all relevant price feeds) before computing `current-notional`, so both `current-coll-usd`/`current-debt-usd` and `added-collateral-value` are derived from the same, fully up-to-date price snapshot within the transaction. Alternatively, recompute `current-notional` again after `write-feeds` and use that refreshed value for `current-capacity`.

### Proof of Concept
1. User with existing debt and one collateral asset calls `collateral-add` for a *new* second collateral asset, supplying a `price-feeds` payload.
2. `current-notional`/`current-coll-usd` is computed using the oracle price cache state *before* the feeds are written (e.g., a stale/lower price for context, or simply whatever was cached from a prior read). [1](#0-0) 
3. `write-feeds` executes, updating the oracle cache with the caller's supplied feed data for the new asset. [2](#0-1) 
4. `added-collateral-value` is computed via `get-asset-value` using this freshly-written, attacker-influenced price for the new collateral. [5](#0-4) 
5. `future-capacity = (current-coll-usd + added-collateral-value) * future-ltv` is compared against `current-capacity = current-coll-usd * current-ltv`, where the two `current-coll-usd` terms share the same stale figure but `added-collateral-value` reflects the newer, more favorable price — allowing the `>=` check to pass in cases it should not. [6](#0-5) 
6. The collateral add proceeds, and the account's true capacity (computed with fully consistent, current prices) may actually be lower than before, undermining the intended invariant.

Note: I was unable to fully trace `write-feeds`, `get-asset-value`, and `get-notional-evaluation` implementations in this pass to confirm exactly how stale the pre-`write-feeds` price cache can be (e.g., whether it defaults to a previous block's value or reverts if unresolved). This should be verified against the full definitions of `write-feeds` and `get-asset-value` in `mainnet/contracts/market/v0-4-market.clar` before treating this as fully confirmed.
