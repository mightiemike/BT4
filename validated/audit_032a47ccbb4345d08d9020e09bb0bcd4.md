Based on the docs, `withdraw()`'s dust UTXO is a real Bitcoin UTXO that the user first acquires themselves and controls (they later sign a PSBT spending it). This confirms the front-running griefing scenario is real: `withdraw(txId, outputId)` doesn't bind the registration to `msg.sender` or verify any Bitcoin-side ownership/signature at the point of calling — it only checks `usedWithdrawalUTXO[sha256(txId, outputId)]`. An attacker can observe a pending `withdraw`/`batchWithdraw` transaction in the mempool and front-run it with the identical `(txId, outputId)` pair (paying the same `depositAmount` from their own funds), which marks the UTXO key as used and causes the legitimate user's transaction to revert with `"UTXO already used"`.

### Title
Front-runnable `Bridge.withdraw()`/`batchWithdraw()` allow squatting another user's dust-UTXO identifier, permanently blocking their withdrawal registration - (File: crates/evm/src/evm/system_contracts/src/Bridge.sol)

### Summary
`withdraw(bytes32 txId, bytes4 outputId)` and `batchWithdraw` key the `usedWithdrawalUTXO` mapping solely on `sha256(txId, outputId)`, with no binding to `msg.sender`, no signature check, and no proof that the caller controls the referenced Bitcoin UTXO at call time [1](#0-0) . Per the withdrawal flow documented in `docs/bridge-contract.md`, a user first acquires a dust UTXO on Bitcoin, then calls `withdraw()`/`batchWithdraw()` referencing that UTXO's `(txId, outputId)` before later signing the actual payout PSBT off-chain [2](#0-1) . Because the mempool transaction (including the plaintext `txId`/`outputId`) is publicly visible before confirmation, an unprivileged adversary can front-run it with the exact same `(txId, outputId)` pair, paying the same `depositAmount`, and get their call mined first.

### Finding Description
This mirrors the ExtraordinaryFunding-class bug: an identifier used to gate a state transition is derived from attacker-observable, non-binding data, letting a griefer race a legitimate actor's transaction and permanently occupy the identifier. Here, the `usedWithdrawalUTXO` mapping key `sha256(abi.encodePacked(txId, outputId))` is exactly the tuple a legitimate user broadcasts in their `withdraw`/`batchWithdraw` call [3](#0-2) . Nothing in `withdraw()` ties the UTXO reference to the caller's identity or requires proof-of-control (e.g., a signature over the dust UTXO) — only `safeWithdraw()` performs such verification via `isSchnorrSigValid` [4](#0-3) . Once the attacker's front-run transaction is mined, `usedWithdrawalUTXO[utxoKey] = true` is permanently set, and the legitimate user's follow-up call reverts with `"UTXO already used"` (this exact revert path is already unit-tested for the honest double-call case, showing the mapping is a hard, irreversible gate) [5](#0-4) .

### Impact Explanation
The victim's specific dust UTXO becomes permanently unusable for registering a withdrawal on the bridge contract, since `usedWithdrawalUTXO` can never be reset. The attacker's registration entry in `withdrawalUTXOs` references a UTXO the attacker does not control (they cannot produce the BIP-341 signature needed to actually spend it in the follow-up PSBT flow used by `safeWithdraw`/off-chain settlement), so the attacker's own `depositAmount` cBTC is effectively wasted while the victim is denied use of that specific withdrawal slot. This is a griefing/DoS effect targeting a chosen victim's withdrawal attempt, not an unconditional, protocol-wide freeze of funds: the victim can mitigate by acquiring a fresh dust UTXO and retrying `withdraw()`. Given the explicit scope exclusion of "denial of service, rate limiting, retry behaviour" and given that no cBTC is stolen, no false state transition is proven, and no custody/proof/DA/authority boundary is crossed (the attacker cannot redirect funds to themselves — they only waste their own `depositAmount` and delay the victim), this does not meet the bar for a Critical/High "concrete bridge value loss" finding under the stated impact taxonomy.

### Likelihood Explanation
Trivial to execute: the attack requires only mempool visibility of a pending `withdraw`/`batchWithdraw` transaction (calldata is plaintext) and the ability to submit a competing transaction with a higher gas price, standard front-running conditions. No privileged role, key compromise, or majority hashrate is needed.

### Recommendation
Bind the withdrawal registration to a value the caller cannot forge, e.g., require the caller to submit a Schnorr signature over `(txId, outputId, msg.sender)` proving control of the dust UTXO (as `safeWithdraw` already does for the full flow), or otherwise ensure `withdraw()`/`batchWithdraw()` cannot be front-run with someone else's chosen UTXO reference.

### Proof of Concept
Not applicable as an in-repo Solidity/Foundry PoC was not executed here, but the exploit path is directly demonstrated by the existing `testCannotDoubleWithdrawWithSameUTXO` test, which shows that a second call to `withdraw()` with the same `(txId, outputId)` unconditionally reverts with `"UTXO already used"` regardless of which address made the first call [5](#0-4) ; an attacker simply needs to be the one to submit that first call using a victim's observed `(txId, outputId)` values from the mempool.

**Note:** This finding is best characterized as griefing/DoS against a specific withdrawal attempt rather than a Critical bridge-value-loss bug per the stated rubric, since the attacker cannot redirect or steal the victim's BTC/cBTC and the victim can recover by using a different dust UTXO. I flag this explicitly given the rules' exclusion of pure DoS findings — treat the severity classification above as the most defensible conclusion reachable from the in-scope code, not a confirmed Critical/High per the strict rubric.

```markdown
1.  **Initiate Withdrawal**: A user wanting to withdraw from Citrea, first acquires a dust output (financially irrelevant, or even 0 sat) on Bitcoin. Then they call the `withdraw()` or `batchWithdraw()` function on the bridge contract with `depositAmount` (essentially burning/locking their balance) and with this dust UTXO. 
2.  **Request Queue**: The contract records this request in a public `withdrawalUTXOs` array. This array serves as a queue of pending withdrawals for the operators to process.
3.  **Completion of the Withdrawal**: After calling the `withdraw()` function, the user signs a `SIGHASH_ALL | ANYONECAN_PAY` PSBT that spends this dust UTXO and outputs `depositAmount` to an address they control. The user then starts an off-chain dutch auction in which they decrease the amount they receive on the Bitcoin side via publishing new signatures when no bridge operator accepts the signed PSBT. When an operator accepts the PSBT, they add the necessary outputs to the PSBT and broadcast the transaction.
```
