### Title
Unbounded duplicate growth of the per-shop session ID list in `KVSessionStorage` causes denial-of-service of `storeSession`/`findSessionsByShop` - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.addShopIds` appends new session ids to the per-shop id list stored in Cloudflare Workers KV without checking whether the id is already present, unlike the equivalent `RedisSessionStorage.addKeyToShopList`, which explicitly de-duplicates. Because offline (and embedded online) session ids are deterministic, a single merchant repeatedly completing the OAuth flow for the same shop causes the same id to be pushed into the array over and over, growing it without bound.

### Finding Description
`KVSessionStorage.storeSession` unconditionally calls `addShopIds(session.shop, [session.id])` on every store: [1](#0-0) 

`addShopIds` reads the current array and appends the new id without checking for an existing entry: [2](#0-1) 

This mirrors the root cause of the reported bug class: a value that should gate/dedupe a list push (there, `amount == 0`; here, "id already present") is not checked, so the same list entry can be pushed indefinitely.

Crucially, session ids for offline sessions (and for embedded online sessions) are **deterministic**, derived only from the shop domain (and user id for online), not randomized: [3](#0-2) [4](#0-3) 

Every time the OAuth callback completes (a normal, unprivileged action any merchant/install can trigger repeatedly by re-authorizing/re-installing the app), the framework calls `sessionStorage.storeSession(callbackResponse.session)`: [5](#0-4) 

Since the resulting session `id` is the same value (`offline_<shop>` or `<shop>_<userId>`) each time, a merchant re-running OAuth N times causes N duplicate entries of the same id to accumulate in the shop's KV id-list, unlike the Redis implementation which explicitly guards against this: [6](#0-5) 

### Impact Explanation
The bloated, ever-growing id list is consumed by `findSessionsByShop`, which maps over every (duplicate) id and performs a `namespace.get` fetch per entry: [7](#0-6) 

As the list grows, `findSessionsByShop` becomes increasingly slow/expensive (redundant KV reads for the same session), degrading or effectively breaking any app functionality that depends on it. Because Cloudflare Workers KV values have a hard size ceiling, sufficiently repeated re-authorization can eventually make the stored id-list value too large to write, causing subsequent `put()` calls in `addShopIds`/`storeSession` to fail — which breaks the OAuth callback path (`storeSession` throwing surfaces as a failed callback, per `auth-callback.ts`'s error handling) and can persistently prevent that shop from completing installation/token refresh again. This is a session-storage/OAuth-handler DoS confined to the affected shop's own session records.

### Likelihood Explanation
Triggering this requires no special privileges beyond being able to (re-)authorize the app for a shop — an action any merchant/install owner can perform repeatedly and cheaply through the normal OAuth/install flow. No secrets, forged signatures, or cross-tenant access are needed; the flaw is purely in `addShopIds` never checking for existing entries before pushing.

### Recommendation
Mirror the Redis implementation's de-duplication check in `KVSessionStorage.addShopIds` before appending, e.g.:

```diff
 private async addShopIds(shop: string, ids: string[]) {
   const key = this.getShopSessionIdsKey(shop);
   const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
-  await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
+  const merged = new Set([...shopIds, ...ids]);
+  await this.namespace.put(key, JSON.stringify([...merged]));
 }
```

### Proof of Concept
1. Configure an embedded app to use `KVSessionStorage`.
2. Install the app on `test-shop.myshopify.com`, completing OAuth (offline). `storeSession` is invoked, and `shop:test-shop.myshopify.com` KV key becomes `["offline_test-shop.myshopify.com"]`.
3. Uninstall and reinstall (or trigger re-auth) the app on the same shop repeatedly, e.g. N times, without ever calling `deleteSession` in between.
4. Inspect the KV key `shop:test-shop.myshopify.com` — it now contains N duplicate copies of `offline_test-shop.myshopify.com`.
5. Call `findSessionsByShop('test-shop.myshopify.com')` — it performs N redundant `loadSession` calls, and as N grows large, both the array size (approaching the per-value KV limit) and unnecessary read amplification degrade or eventually break session storage for that shop.

      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }

      await this.client.set(shopKey, JSON.stringify([idKey]));
