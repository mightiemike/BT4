### Title
Divergent validation of shadow-parent block-commit constraints causes accept/reject split - (`stackslib/src/chainstate/nakamoto/shadow.rs`)

### Summary
`NakamotoChainState::validate_shadow_parent_burnchain` decides whether to enforce the `block_commit.parent_vtxindex == 0` / `block_commit.parent_block_ptr == shadow_parent_sortition.block_height` invariant based on whether the parent header can be found in the *local* `nakamoto_staging_blocks` table at the moment the check runs. If the shadow parent header is not yet present locally, the function silently returns `Ok(())`, exactly as if the parent were not a shadow block at all, skipping the check entirely. Because this validation runs exactly once — during `accept_block` — and is never re-checked later during `append_block`/`process_next_nakamoto_block`, two honest nodes that load the shadow tenure at different real times relative to receiving the child block will reach different Ok/Err verdicts for the identical child block.

### Finding Description
The claimed equality is: for a normal block whose parent is a shadow block, `block_commit.parent_vtxindex == 0` and `block_commit.parent_block_ptr == parent_sn.block_height` must hold identically on every validating node [1](#0-0) .

The bug is not in the arithmetic of that equality (which is deterministic given canonical burnchain state) but in whether the check is even *performed*. `validate_shadow_parent_burnchain` first looks up the parent header via `staging_db.get_nakamoto_block_header(&block.header.parent_block_id)`. If that lookup returns `None` — because the local node hasn't yet stored the shadow parent header in its `nakamoto_staging_blocks` table — the function returns `Ok(())` unconditionally, treating "parent not found" the same as "parent is not a shadow block": [2](#0-1) 

This function is invoked only from `validate_normal_nakamoto_block_burnchain`, which in turn is called from `NakamotoChainState::accept_block` — i.e. at the moment a block is first offered for staging insertion: [3](#0-2) [4](#0-3) 

There is no second invocation of `validate_shadow_parent_burnchain` anywhere else in the codebase (confirmed: only the definition, its single call site in `validate_normal_nakamoto_block_burnchain`, and test call sites exist). Crucially, `append_block`'s parent-lookup only checks that a parent *header* exists at all (`Self::get_block_header`) and that `parent_block_id` matches; it does not re-verify the shadow-specific block-commit fields: [5](#0-4) 

Attacker's exact input: a normal `NakamotoBlock` whose `parent_block_id` points to a shadow block, submitted alongside (or as the tenure-start of) a block-commit with `parent_vtxindex != 0` (invalid per the shadow-parent contract). Exploit flow:
1. A prior shadow tenure exists in the network (inserted out-of-band via tooling, e.g. `add_shadow_block`) [6](#0-5) .
2. Node A has already stored/received the shadow parent header in its local `nakamoto_staging_blocks` before the attacker's child block arrives. Its `accept_block` call runs `validate_shadow_parent_burnchain`, which finds the parent header, sees `is_shadow_block()==true`, checks `parent_vtxindex != 0` and rejects the block, so it is never stored in staging.
3. Node B has not yet stored/loaded the shadow parent header locally (e.g., it applied the shadow-block emergency patch later, or simply hasn't relayed/ingested it yet) when the same child block arrives. `get_nakamoto_block_header` returns `None`, the function returns `Ok(())`, the shadow-parent check is skipped, and the malformed block passes `accept_block` and is stored in staging.
4. Once Node B later loads the shadow parent header (into the headers table), `process_next_nakamoto_block`/`append_block` only checks that *some* parent header with a matching `parent_block_id` exists — it never re-validates the block-commit's `parent_vtxindex`/`parent_block_ptr` fields — so the invalid block is processed and appended to Node B's canonical chain.
5. Node A and Node B now have permanently divergent canonical chains built from the identical block and identical burnchain state.

Existing guards do not prevent this: `common_validate_against_burnchain` only checks consensus hash and burn totals [7](#0-6) ; `check_tenure_tx`/`verify_signer_signatures`/static validators do not inspect the parent's shadow-ness or the block-commit's parent pointer fields; and the block-commit-level check in `leader_block_commit.rs` only requires `parent_vtxindex == 0` for a *maybe*-shadow-parent commit's PoX descendant computation, not full equality enforcement at Stacks-block acceptance time [8](#0-7) .

### Impact Explanation
This is a Critical-category divergence: an invalid block (one whose block-commit does not correctly point at its shadow-tenure parent) is permanently rejected by one honest node and permanently accepted into the canonical chain by another, purely as a function of local, non-canonical staging-DB state (arrival/load ordering of the shadow tenure). This produces a genuine chain split/fork between honest nodes with no way to reconcile short of manual intervention, satisfying "an invalid block accepted or a valid block rejected network-wide" / "chain split or deep fork."

### Likelihood Explanation
Preconditions: a shadow tenure must already exist (requires tooling/emergency-upgrade process, as stated) and the attacker must control (or coordinate with) a miner slot able to submit a Stacks block plus a block-commit with a bad `parent_vtxindex`/`parent_block_ptr` — well within an unprivileged single-miner-slot capability. The trigger condition (nodes disagreeing on whether they've locally ingested the shadow parent header before the child block arrives) is realistic during/after an emergency shadow-block deployment, when nodes upgrade and ingest the shadow tenure asynchronously while the network continues relaying new blocks. This is deterministic and fully repeatable with a two-node harness controlling ingestion order.

### Recommendation
Make the shadow-parent block-commit check independent of ephemeral local staging state, or defer/re-run it deterministically:
- Instead of returning `Ok(())` when the parent header cannot be found, return a retryable/pending error (mirroring how `append_block` treats missing parents as "cannot process yet") so the block cannot bypass the check by being accepted before the parent is known locally.
- Re-verify `validate_shadow_parent_burnchain` at `append_block`/processing time, using the canonical headers table (not the staging table), so the check runs against a state that is guaranteed to be present for every node before the block is finalized into the canonical chain.

### Proof of Concept
Rust integration test plan (two-node/staging harness):
1. Construct a chainstate through Epoch 3.0 with a shadow tenure inserted via `NakamotoChainState::make_shadow_tenure`/`add_shadow_block`, mirroring `stackslib/src/chainstate/nakamoto/tests/node.rs:2338-2409`.
2. Craft a normal child `NakamotoBlock` whose `header.parent_block_id` is the shadow block's id, and a `LeaderBlockCommitOp` with `parent_vtxindex = 1` (invalid) and `parent_block_ptr` matching the shadow tenure's sortition height.
3. **Node A** (has the shadow header already stored in its `nakamoto_staging_blocks`): call `NakamotoChainState::validate_shadow_parent_burnchain(staging_db_with_shadow_header, ..., &block, &bad_commit)` — assert `Err(ChainstateError::InvalidStacksBlock(_))`, and via `accept_block` assert the block is never stored (`Ok(false)`/error, `has_nakamoto_block_with_index_hash == false`).
4. **Node B** (shadow header NOT yet stored in its `nakamoto_staging_blocks`, e.g. a fresh `NakamotoStagingBlocksTx` without the shadow block inserted): call the same `validate_shadow_parent_burnchain` — assert it returns `Ok(())` even though the same equality (`parent_vtxindex==0`) is violated, then call `accept_block` and assert `Ok(true)` (block stored).
5. On Node B, subsequently insert the shadow header into staging/headers, then call `process_next_nakamoto_block`/`append_block` — assert the malformed child is processed and becomes part of the canonical tip, while Node A's canonical tip never includes it — demonstrating divergent Ok/Err verdicts and a resulting chain-tip mismatch between the two nodes for the identical input block.

impl NakamotoStagingBlocksTx<'_> {
    /// Add a shadow block.
    /// Fails if there are any non-shadow blocks present in the tenure.
    pub fn add_shadow_block(&self, shadow_block: &NakamotoBlock) -> Result<(), ChainstateError> {
        if !shadow_block.is_shadow_block() {
            return Err(ChainstateError::InvalidStacksBlock(
                "Not a shadow block".into(),
            ));
        }
        let block_id = shadow_block.block_id();

        // is this block stored already?
        let qry = "SELECT 1 FROM nakamoto_staging_blocks WHERE index_block_hash = ?1";
        let args = params![block_id];
        let present: Option<i64> = query_row(self, qry, args)?;
        if present.is_some() {
            return Ok(());
        }

        // this tenure must be empty, or it must be a shadow tenure
        let qry = "SELECT 1 FROM nakamoto_staging_blocks WHERE consensus_hash = ?1";
        let args = rusqlite::params![&shadow_block.header.consensus_hash];
        let present: Option<u32> = query_row(self, qry, args)?;
        if present.is_some()
            && !self
                .conn()
                .is_shadow_tenure(&shadow_block.header.consensus_hash)?
        {
            return Err(ChainstateError::InvalidStacksBlock(
                "Shadow block cannot be inserted into non-empty non-shadow tenure".into(),
            ));
        }

        // there must not be a block at this height in this tenure
        let qry = "SELECT 1 FROM nakamoto_staging_blocks WHERE consensus_hash = ?1 AND height = ?2";
        let args = rusqlite::params![
            &shadow_block.header.consensus_hash,
            u64_to_sql(shadow_block.header.chain_length)?
        ];
        let present: Option<u32> = query_row(self, qry, args)?;
        if present.is_some() {
            return Err(ChainstateError::InvalidStacksBlock(format!(
                "Conflicting block at height {} in tenure {}",
                shadow_block.header.chain_length, &shadow_block.header.consensus_hash
            )));
        }

        // the shadow block is crafted post-hoc, so we know the consensus hash exists.
        // thus, it's always burn-attachable
        let burn_attachable = true;

        // shadow blocks cannot be replaced
        let signing_weight = u32::MAX;

        self.store_block_if_better(
            shadow_block,
            burn_attachable,
            signing_weight,
            NakamotoBlockObtainMethod::Shadow,
        )?;
        Ok(())
    }
