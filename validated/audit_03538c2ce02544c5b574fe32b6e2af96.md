## Analog Vulnerability Found

### Title
Bouncer's per-builtin proving-gas cost is derived via floor division, causing systematic under-accounting of block proving-gas usage across many transactions - (File: crates/blockifier/src/bouncer.rs)

### Summary
The Cooler bug arises because a proportional value (`decollateralized`) is derived via integer division from a fresh numerator each call (`collateral * repaid / loan.amount`), so repeated small operations each round the derived value down to zero, while the true proportional value accumulated over those operations is non-zero — producing a lasting accounting deficit. The sequencer contains a structurally analogous pattern in `BuiltinInstanceLimits::induced_gas_costs`, which derives a fixed **per-instance proving-gas price** for each Cairo builtin/opcode via floor division of the block-wide proving-gas budget by a configured per-block instance limit, and then applies that already-rounded-down unit price uniformly to every instance of that builtin used by every transaction admitted to the block.

### Finding Description
`BuiltinInstanceLimits::induced_gas_costs` computes, for each builtin, `cost = floor(proving_gas / limit)`: [1](#0-0) 

This per-unit price (`BuiltinGasCosts`) is obtained once from `BouncerConfig::builtin_gas_costs`: [2](#0-1) 

and then used as the "proving" pricing table for every transaction's builtin/opcode usage counts, via `get_tx_weights` → `compute_proving_gas` → `proving_gas_from_cairo_primitives_and_sierra_gas`, whose resulting `total_proving_gas` is accumulated across all transactions in the block by `Bouncer::try_update`: [3](#0-2) 

Because the per-instance price is the *floor* of `proving_gas / limit` rather than an exact rational price, every single instance of a builtin is undercharged by up to `(remainder / limit)` of a gas unit relative to the "true" proportional cost implied by the configured budget/limit ratio. As in the Cooler `repay` bug — where `decollateralized = collateral * repaid / loan.amount` truncates to 0 for small `repaid` even though the cumulative effect over many partial repayments should be non-zero — here each builtin instance's rounded-down unit cost is summed, unmodified, over potentially millions of instances across many transactions in the same block. The aggregate shortfall between the sum of floored per-instance charges and the "true" proportional proving-gas cost grows linearly with the total instance count. In the worst case, if the configured per-primitive `limit` exceeds the block's `proving_gas` capacity, the derived cost floors to exactly `0`, meaning that builtin's usage is *never* counted toward the block's proving-gas capacity at all, regardless of how many instances a sequence of transactions produces.

### Impact Explanation
The Bouncer's proving-gas weight is the mechanism by which the block builder ensures a block's total prover workload stays within `block_max_capacity.proving_gas` — the true, provable resource budget (`Bouncer::try_update` / `within_max_capacity_or_err` at [4](#0-3)  and [5](#0-4) ). Because the per-instance price used for this accounting is systematically rounded down and then applied unmodified across an unbounded number of transactions/instances, the bouncer can under-report a block's true proving-gas usage relative to the real cost model, letting the block builder admit strictly more Cairo-primitive instances than the block's actual provable capacity permits. Any unprivileged transaction sender can generate large volumes of a specific builtin's usage in ordinary contract calls, so this is reachable purely through normal transaction submission. In the degenerate case where the floored unit cost for a builtin is 0, that resource is effectively exempted from bouncer accounting altogether, letting the block accumulate an unbounded amount of that builtin's real proving workload — risking production of blocks whose true prover-resource requirements exceed what the network intended to allow, jeopardizing the network's ability to prove/finalize such a block.

### Likelihood Explanation
Any sequence of ordinary, unprivileged transactions that exercise a given Cairo builtin/opcode heavily (well within existing bouncer resource limits like `sierra_gas` or `n_txs`) will trigger this under-accounting; no special privileges or malicious infrastructure roles are required — only that the accumulated true proving-gas cost of a builtin's usage across a block diverges from the block's floor-derived per-instance price. The magnitude of the discrepancy depends on the configured `builtin_instance_limits` vs. `block_max_capacity.proving_gas` ratio and the total instance count admitted per block, so its severity is configuration-dependent but structurally always present due to the use of plain integer (floor) division in `induced_gas_costs`.

### Recommendation
Avoid deriving a single truncated per-instance integer price and applying it uniformly; instead accumulate proving-gas cost using exact rational arithmetic (e.g., `Ratio<u64>`/`Ratio<u128>`, as is already done elsewhere in the fee code, e.g. `ResourceCost`/`Ratio` usage in `crates/blockifier/src/fee/fee_utils.rs`) and round only once, at the point where the final aggregated proving-gas total is compared against `block_max_capacity.proving_gas`, ensuring the cumulative rounding error cannot exceed a single unit regardless of transaction count.

### Proof of Concept
1. Configure (or use a chain configuration where) a builtin's `BuiltinInstanceLimits` entry is close to or exceeds `block_max_capacity.proving_gas`, so `induced_gas_costs` (`crates/blockifier/src/bouncer.rs:456-457`) floors that builtin's per-instance price to a very small value or `0`.
2. Submit a large volume of ordinary transactions (fully within reach of any unprivileged sender) that heavily exercise that specific builtin (e.g., many `range_check`/`poseidon`/`ecdsa` operations), while staying within all other bouncer weight limits (`sierra_gas`, `n_txs`, etc.).
3. Because each instance is charged the same floored (possibly zero) unit price, `Bouncer::try_update`'s `accumulated_weights.proving_gas` (`crates/blockifier/src/bouncer.rs:669-670`) grows far more slowly than the true proportional proving-gas cost implied by `builtin_instance_limits`.
4. The bouncer keeps reporting `has_room` (`crates/blockifier/src/bouncer.rs:117-119`) and admits many more transactions/instances than the block's real proving capacity allows, producing a block whose true prover workload for that builtin exceeds the intended `block_max_capacity.proving_gas` budget.

impl BuiltinInstanceLimits {
    /// Induces the per-instance proving-gas cost of each Cairo primitive from its per-block
    /// instance limit: `cost = floor(proving_gas / limit)`.
    pub fn induced_gas_costs(&self, proving_gas: GasAmount) -> BuiltinGasCosts {
        let derive = |limit: NonZeroU64| -> u64 { proving_gas.0 / limit.get() };
        BuiltinGasCosts {
            pedersen: derive(self.pedersen),
            range_check: derive(self.range_check),
            range_check96: derive(self.range_check96),
            poseidon: derive(self.poseidon),
            ecdsa: derive(self.ecdsa),
            ecop: derive(self.ecop),
            bitwise: derive(self.bitwise),
            keccak: derive(self.keccak),
            add_mod: derive(self.add_mod),
            mul_mod: derive(self.mul_mod),
            blake: derive(self.blake),
        }
    }
