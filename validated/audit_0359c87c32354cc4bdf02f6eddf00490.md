### Title
Incomplete Receipt Size Validation: `output_data_receivers` Appended After `max_receipt_size` Check Allows Oversized Receipts to Bypass Hard Limit — (`runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`)

---

### Summary

`validate_receipt` checks a newly created receipt's borsh size against `max_receipt_size` at the moment the receipt is constructed inside `apply_action_receipt`. However, the runtime subsequently appends `output_data_receivers` entries to that same receipt object — after validation has already passed — when a contract uses `promise_return`. The final, enlarged receipt is forwarded and processed without re-validation, violating the hard size limit. This is the direct nearcore analog of the UMA M03 bug: validation at construction time does not account for fields that are appended later.

---

### Finding Description

**Validation point** — `validate_receipt(..., NewReceipt)` is called inside `apply_action_receipt` immediately after each new receipt is created by a contract action: [1](#0-0) 

The check measures the borsh-serialized size of the receipt at that instant and rejects it if it exceeds `max_receipt_size` (4 MiB).

**Post-validation mutation** — After all actions in the receipt have been executed and their new receipts validated, the runtime handles `promise_return` semantics. When the executing receipt has `output_data_receivers` and the contract returned a `ReceiptIndex` (i.e., called `promise_return`), the runtime appends the parent receipt's `output_data_receivers` directly onto the child receipt that was already validated: [2](#0-1) 

This mutation happens **after** `validate_receipt` has already approved the receipt. The receipt's borsh size is now larger than `max_receipt_size`, but no re-validation occurs.

**Confirmed by the codebase itself** — The `ValidateReceiptMode::ExistingReceipt` variant was introduced specifically to tolerate these oversized receipts when they arrive as incoming receipts on subsequent chunks: [3](#0-2) 

The congestion-control layer also has an explicit workaround that clamps the size of oversized receipts to `max_receipt_size` to prevent them from getting permanently stuck: [4](#0-3) 

The test suite explicitly documents and reproduces the bug: [5](#0-4) 

---

### Impact Explanation

The `max_receipt_size` limit is a **hard limit** whose purpose is to keep `ChunkStateWitness` under 17 MiB. An oversized receipt that bypasses this limit:

1. **Contract execution flow breakage**: the receipt that should be rejected with `ReceiptSizeExceeded` is instead forwarded and executed normally. The hard invariant "all receipts in state are ≤ max_receipt_size" is violated.
2. **Witness inflation**: the oversized receipt is included in `ChunkStateWitness`, pushing it beyond the intended 17 MiB ceiling. Chunk validators must still process and endorse the chunk.
3. **Non-network-level DoS**: a single unprivileged user can craft a contract that repeatedly produces near-limit receipts with `promise_return`, inflating witness sizes across shards. This is fixable without a hardfork (by re-validating after the `output_data_receivers` append).

---

### Likelihood Explanation

Any unprivileged user can deploy a contract that:
- Creates a near-`max_receipt_size` action receipt via `promise_create`
- Calls `promise_return` on it from within a callback that itself has `output_data_receivers`

The trigger is reachable through ordinary `FunctionCall` transactions. The test contract `max_receipt_size_promise_return_method1` in the test suite demonstrates the exact exploit path. [6](#0-5) 

---

### Recommendation

Re-validate the receipt's size **after** appending `output_data_receivers` in `apply_action_receipt` (`runtime/runtime/src/lib.rs` lines 1040–1049). Specifically, after the `extend_from_slice` call, re-run the borsh size check against `max_receipt_size` and return a `NewReceiptValidationError::ReceiptSizeExceeded` action error if the limit is exceeded. This mirrors the fix pattern from UMA PR #3524: account for all fields that are appended after the initial validation.

---

### Proof of Concept

1. Deploy a contract with two methods: `method1` creates promise chain `[A -then-> B]`; when `A` executes it creates a near-`max_receipt_size` receipt `C` and calls `promise_return(C)`, causing the runtime to append `B`'s `output_data_receivers` onto `C`.

2. The receipt `C` passes `validate_receipt(..., NewReceipt)` at creation (size = `max_receipt_size`).

3. After `output_data_receivers` are appended, `C`'s borsh size exceeds `max_receipt_size`.

4. `C` is forwarded via `ReceiptSink::forward_or_buffer_receipt` with its size clamped to `max_receipt_size` (workaround), then processed on the receiving shard under `ValidateReceiptMode::ExistingReceipt` (which skips the size check).

5. The test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` confirms the oversized receipt is observed in the chain: [7](#0-6)
