Cross-tenant webhook impersonation via unauthenticated `X-Shopify-Shop-Domain` header - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
Shopify webhook validation in this library authenticates a webhook request solely by HMAC-signing the raw request body with the app's single shared `apiSecretKey`. The `X-Shopify-Shop-Domain` (and topic/apiVersion) headers are never included in the signed material, yet that unauthenticated `domain` value is trusted downstream to select which shop's offline session/access token to load and expose to the webhook handler. Because the signing secret (`apiSecretKey`) is shared across every shop that installs the app (it is the app's client secret, not a per-shop secret), any merchant who has installed the app can obtain a genuine `rawBody + HMAC` pair for their own shop (e.g. via a real webhook delivery or Shopify's manual "send test notification" feature) and replay that exact body/HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. The HMAC check still passes (it only validates the body), so the request is accepted as if it came from the victim shop.

### Finding Description
`validateHmacFromRequestFactory` in [1](#0-0)  computes/verifies the HMAC exclusively over `rawBody`: [2](#0-1) 

`validateFactory` in [3](#0-2)  runs this body-only HMAC check and then, independently and without any cryptographic binding to the verified body, extracts `topic`, `domain`, `apiVersion`, `webhookId` straight from request headers via `checkWebhooksHeaders`: [4](#0-3) 

None of these header values are covered by the signature. Downstream, `authenticateWebhookFactory` (identical in both the remix and react-router packages) takes the unauthenticated `check.domain` value and uses it directly to look up/refresh the shop's offline session and to build an authenticated admin API client that is handed to the app's webhook handler: [5](#0-4) 

Since `apiSecretKey` is the app's single client secret (shared by every shop that has the app installed — see the token-exchange/OAuth flow which reuses the same `config.apiSecretKey` for all shops, e.g. [6](#0-5) ), an attacker who has installed the app on their own store possesses (or can obtain, e.g. through the store's genuine webhook deliveries or Shopify's "send test notification" feature, which the code's own comment acknowledges exists — [7](#0-6) ) a valid `rawBody`+HMAC pair signed with that same secret. Replaying that pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a different, victim shop passes HMAC validation unchanged, because the domain is never part of what is signed.

This mirrors the root cause identified in the reference report: the check validates a component (`rawBody`) that is disconnected from the security-critical field actually trusted afterwards (`domain`), exactly as ParaSwap's operator validated balances of a declared token rather than the token that was actually swapped.

### Impact Explanation
A successful forgery causes the app to process a webhook "as" a shop the attacker does not own: `ensureValidOfflineSession` loads that victim's real offline session/access token, and the resulting `admin` client in the webhook context lets the app's own registered handler logic run authenticated Admin API calls scoped to the victim's shop (e.g. `APP_UNINSTALLED` handlers that delete data, custom handlers that write/read merchant data) — a cross-tenant compromise entirely under attacker control by choosing which topic/payload to replay and which victim domain header to set.

### Likelihood Explanation
Requires only that the attacker (a) can install the target app on any shop of their own (unprivileged, self-service) and (b) can capture one authentic `rawBody`/HMAC pair for any topic they want to forge (trivially available from their own store's genuine webhook deliveries or Shopify's manual webhook-resend tooling), then (c) POST that pair to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` value. No secrets, MITM, or privileged access are needed beyond ordinary app installation.

### Recommendation
Bind the shop domain (and topic/webhook id) into the value that is cryptographically verified, e.g. by validating the domain against the shop recorded when the corresponding session/webhook subscription was created, or by requiring that the resolved `check.domain` match a shop that has an active session in storage created via a completed OAuth/token-exchange for that specific webhook subscription, rather than trusting the raw header. At minimum, cross-check `check.domain` against an independent source of truth (e.g., the registered webhook's `address`/subscription metadata) before using it to load a session or construct an authenticated Admin client.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, completing OAuth so the app has an offline session/access token for that shop.
2. Attacker triggers (or captures) a genuine webhook delivery for a topic the app handles (e.g. `PRODUCTS_CREATE`), obtaining the exact `rawBody` and its `X-Shopify-Hmac-Sha256` value as sent by Shopify — both are valid because they're signed with the app's shared `apiSecretKey`.
3. Attacker POSTs that identical `rawBody` (with its unmodified HMAC header) to the app's `/webhooks` endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `validateHmacFromRequestFactory` verifies the HMAC over `rawBody` successfully (it never inspects the domain header) — [8](#0-7) .
5. `checkWebhooksHeaders` returns `domain: 'victim-shop.myshopify.com'` as part of the "valid" result — [9](#0-8) .
6. `authenticateWebhookFactory` loads `victim-shop.myshopify.com`'s offline session and builds an authenticated admin client for it, then invokes the app's webhook handler as if the event genuinely originated from the victim shop — [10](#0-9) .

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,

      return validHmacResult;
