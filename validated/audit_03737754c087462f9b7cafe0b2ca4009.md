### Title
Starknet OS `execute_replace_class` Omits Declared-Class Check Present in Blockifier, Enabling Honest-Node State Divergence - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The Starknet OS Cairo implementation of the `replace_class` syscall does not verify that the target `class_hash` corresponds to a declared class before writing it into `contract_state_changes`, whereas the Rust blockifier's implementation of the same syscall performs this check. This is directly analogous to the reported bug class: a state-mutating operation ("replace_class"/hook-like callback) is executed without validating a precondition that the *other* code path (the wallet's hook-initialization check / here, the blockifier's declared-class check) enforces, letting privileged state end up in an inconsistent, unauthorized configuration.

### Finding Description
In the blockifier (the execution engine that builds blocks), `replace_class` explicitly requires the class to be declared before mutating storage: [1](#0-0) 

```
fn replace_class(...) {
    // Ensure the class is declared (by reading it).
    syscall_handler.state.get_compiled_class(request.class_hash)?;
    syscall_handler.state.set_class_hash_at(syscall_handler.storage_address, request.class_hash)?;
    ...
}
```

This is confirmed by dedicated tests (`undeclared_class_hash` expects rejection with "is not declared"): [2](#0-1) 

However, the Cairo Starknet OS implementation of the identical syscall — used for re-execution / proving the block that the blockifier already produced — explicitly skips this check, as marked by its own TODO comment: [3](#0-2) 

```
func execute_replace_class{...}(contract_address: felt) {
    ...
    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address, prev_value=cast(state_entry, felt), new_value=cast(new_state_entry, felt)
    );
    ...
}
```

The deprecated syscall version of `replace_class` in `deprecated_execute_syscalls.cairo` has the identical gap: [4](#0-3) 

The Starknet OS is the ground-truth re-execution engine that proves that a sequencer-produced block (built by the blockifier) is valid; its Cairo hints trust the values supplied by the prover/hint layer (`%{ GetContractAddressStateEntry %}`) and, unlike the blockifier, apply the class-hash mutation unconditionally. Any transaction — reachable by any unprivileged account that includes a `replace_class` syscall in an `__execute__` call (a single INVOKE transaction) — thus exercises code paths with differing validation semantics between the two independent implementations of the same protocol rule.

### Impact Explanation
Because the blockifier and the Starknet OS are supposed to be semantically equivalent (the OS is the canonical, provable specification of Starknet execution, and the sequencer's blockifier execution must match it exactly for block hash/state root to be provable), a validation gap of this kind is a state-transition-function mismatch:
- If any hint-processor/prover-supplied data path can cause the OS to accept a `replace_class` call for an undeclared class hash (which the blockifier would reject/revert), the OS-computed state diff and resulting global state root can diverge from what the blockifier (and hence normal full nodes replaying with the Rust implementation) computed for the same block, i.e. "wrong committed root" / "honest-node divergence" between the OS-based proving pipeline and the RPC/blockifier-based execution pipeline.
- Because `execute_replace_class` blindly trusts `GetContractAddressStateEntry` (populated via a Python/Rust hint, not an OS-internal read validated against declared classes), an out-of-consensus difference in "is class X declared" between the OS's view and the blockifier's view is not detected, breaking the guarantee that the proof attests to the same computation that produced the block.

This maps to the categories accepted by the rules: "wrong committed root or block hash" / "honest-node divergence," reached purely by a normal contract's `__execute__` invoking the `replace_class` syscall from a single unprivileged transaction sender.

### Likelihood Explanation
The gap is explicitly acknowledged in-code with a dated TODO ("TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash"), confirming this is a known, currently-unfixed omission rather than a design choice. The syscall is reachable directly by any account contract via `replace_class_syscall`, requiring no special privileges — only a normal transaction from any unprivileged sender whose contract invokes `replace_class`. The precise conditions under which the OS's `GetContractAddressStateEntry` hint could supply state inconsistent with blockifier's declared-class bookkeeping (e.g., during OS-only replay/proving paths, or divergent hint implementations) were not verifiable from the indexed code alone; this reduces certainty of full end-to-end exploitability but the missing invariant enforcement itself is concretely confirmed in the source.

### Recommendation
Add the same declared-class existence check in the Starknet OS Cairo `execute_replace_class` (both the current and deprecated syscall implementations) that the blockifier already performs, i.e., verify a corresponding entry exists in `contract_class_changes` (or the OS's declared-classes structure) for `class_hash` before updating `contract_state_changes`, so that the OS's state-transition function stays byte-for-byte consistent with the blockifier's for this syscall.

### Proof of Concept
Not independently reproducible from static analysis alone (would require running the OS with a `replace_class` call to an undeclared class hash and observing whether it fails to reject it the way blockifier does, and diffing the resulting state commitments); however, the code discrepancy itself is directly demonstrated by:
- Blockifier's positive check and negative test: [2](#0-1) 
- OS's unchecked mutation with explicit TODO: [5](#0-4)

        // Not enough gas to execute the syscall.
