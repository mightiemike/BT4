### Title
Cookie signatures are not bound to cookie purpose, allowing OAuth-state/session cookie signature reuse across cookie types - (File: packages/apps/shopify-api/runtime/http/cookies.ts)

### Summary
The `Cookies` helper signs cookie values with `createCookieSignature(key, value)`, an HMAC over the cookie *value* only, derived from a single fixed domain-separation string shared by every cookie name. `isSignedCookieValid` verifies a signature the same way. Neither the signing nor verification step incorporates the cookie's name/purpose (e.g. `shopify_app_state` vs `shopify_app_session`), so a valid `(value, signature)` pair minted for one cookie purpose is accepted as valid for a different cookie purpose, as long as the raw value happens to match.

### Finding Description
`createCookieSignature` derives a single key via `deriveSHA256HMACKey(key, COOKIE_SIGNING_INFO)` where `COOKIE_SIGNING_INFO = 'shopify-app-js/cookie-signing/v1'` is a constant shared by *all* cookies signed through `setAndSign`/verified through `isSignedCookieValid`/`getAndVerify`: [1](#0-0) [2](#0-1) [3](#0-2) 

This library uses `setAndSign`/`getAndVerify` for at least two distinct cookies with different security semantics: the OAuth `STATE_COOKIE_NAME` (`shopify_app_state`, holding a random nonce used for CSRF protection during OAuth) and the `SESSION_COOKIE_NAME` (`shopify_app_session`, holding a session identifier used to look up an authenticated session): [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Because the HMAC is computed purely as `HMAC(derivedKey, value)` with no cookie-name/purpose binding, this is structurally the same bug class as the report: a "commitment" (here, a cookie signature) is not cryptographically tied to the context it is meant to authenticate (which cookie/purpose it belongs to), only to the raw payload. This is analogous to the vote-commit issue where the commitment hash was not bound to the voter's address/context, enabling reuse of a valid commitment in an unintended context.

The project's own changelog documents that they previously found and partially addressed a related issue — an OAuth-state cookie signature being replayable as a webhook HMAC — by deriving a cookie-specific key separate from the webhook-HMAC key: [8](#0-7) 

However, that fix only separated "cookie signing" as a domain from "webhook HMAC," using one single derived key for *all* cookies rather than a per-cookie-name derivation. Consequently, cross-cookie-purpose reuse within the cookie-signing domain (state cookie vs. session cookie, or any other cookie added later using `setAndSign`) remains structurally possible: any observer of a valid `(value, value.sig)` pair set by the library for one cookie name can present that same pair under a different cookie name and have it validated by `isSignedCookieValid`.

### Impact Explanation
The practical exploitability depends on whether an attacker can either (a) predict/control a cookie value that collides between purposes, or (b) get a target's browser to send a forged `Set-Cookie` (which normally requires header injection or another cookie-setting vector, not just possession of the value/signature pair, since cookies aren't directly settable across origins by attackers without another vulnerability). Given the deterministic construction of offline session IDs (`offline_${shop}`) and the fact that the OAuth flow itself exposes the (nonce, signature) pair to the client browser via `Set-Cookie`, the *design* violates standard domain-separation practice for signed tokens (each signed artifact should authenticate both its value and its intended use). This is a genuine defense-in-depth weakness, but I could not fully verify a concrete, remotely-triggerable exploit chain (e.g., a way for an unauthenticated attacker to inject a cookie header cross-origin) within the scope of this repo, since ordinary same-origin cookie scoping and `sameSite`/`path` restrictions on these cookies would need to be bypassed for a real cross-purpose replay to matter.

### Likelihood Explanation
Low-to-Medium. Exploiting this requires an attacker to also control or inject the `Cookie` header sent to the target endpoint (e.g., via a cookie-injection or subdomain-takeover vector, or a client-side vulnerability), since the library does not expose an HTTP endpoint that itself lets a remote caller set arbitrary cookies signed by the app secret. Absent such a vector, this is a latent design weakness rather than a directly exploitable end-to-end vulnerability from a bare unauthenticated HTTP request.

### Recommendation
Bind the cookie name/purpose into the signed material, e.g. `createSHA256HMAC(cookieSigningKey, `${cookieName}:${value}`)`, or derive a distinct HMAC key per cookie name (similar to how `deriveSHA256HMACKey` is already used to separate cookie-signing from webhook-HMAC signing) so that a signature computed for one cookie name can never validate for another.

### Proof of Concept
Not fully demonstrable as a complete remote exploit from the available code alone — the underlying HMAC scheme conflates all cookie names, but weaponizing it into a genuine cross-tenant/session forgery additionally requires a way to make a victim's browser (or the authenticate handler under test) present a cookie of the *wrong* type with a value/signature pair captured from another cookie context. Conceptually:
1. Complete OAuth `begin()` for shop-a, capturing the `Set-Cookie` for `shopify_app_state=NONCE; shopify_app_state.sig=SIG` (`packages/apps/shopify-api/lib/auth/oauth/oauth.ts:88-100`).
2. Present a request carrying `shopify_app_session=NONCE; shopify_app_session.sig=SIG` instead.
3. `isSignedCookieValid('shopify_app_session')` (`packages/apps/shopify-api/runtime/http/cookies.ts:205-236`) recomputes `HMAC(derivedKey, NONCE)` and finds it matches `SIG`, incorrectly validating the forged session cookie as authentic, even though it was never signed for that purpose. [9](#0-8)

const COOKIE_SIGNING_INFO = 'shopify-app-js/cookie-signing/v1';

async function createCookieSignature(
  key: string,
  value: string,
): Promise<string> {
  const cookieSigningKey = await deriveSHA256HMACKey(key, COOKIE_SIGNING_INFO);
  return createSHA256HMAC(cookieSigningKey, value);
}

const signatureEncoder = new TextEncoder();

function safelyCompareSignatures(signatureA: string, signatureB: string) {
  const buffA = signatureEncoder.encode(signatureA);
  const buffB = signatureEncoder.encode(signatureB);

  if (buffA.length !== buffB.length) return false;

  let out = 0;
  for (let i = 0; i < buffA.length; i++) {
    out |= buffA[i] ^ buffB[i];
  }

  return out === 0;
}

  async isSignedCookieValid(cookieName: string): Promise<boolean> {
    const signedCookieName = `${cookieName}.sig`;
    if (
      !this.cookieExists(cookieName) ||
      !this.cookieExists(signedCookieName)
    ) {
      this.deleteInvalidCookies(cookieName, signedCookieName);
      return false;
    }
    const cookieValue = this.get(cookieName);
    const signature = this.get(signedCookieName);

    if (!cookieValue || !signature) {
      this.deleteInvalidCookies(cookieName, signedCookieName);
      return false;
    }

    const allCheckSignatures = await Promise.all(
      this.keys.map((key) => createCookieSignature(key, cookieValue)),
    );

    const validSignature = allCheckSignatures.some((checkSignature) =>
      safelyCompareSignatures(checkSignature, signature),
    );

    if (!validSignature) {
      this.deleteInvalidCookies(cookieName, signedCookieName);
      return false;
    }

    return true;
  }
