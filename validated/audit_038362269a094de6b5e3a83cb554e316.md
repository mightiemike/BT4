### Title
Metering `Settle` skips `RPC_EVM` spend units from balance accounting, causing full refund of earmarked credits despite real resource consumption - (File: `core/services/workflows/metering/metering.go`)

### Summary
In `Report.Settle`, per-unit spend aggregation is computed in a loop over `resourceSpends`, but any spend reported with unit `"RPC_EVM"` is explicitly skipped via a `continue` before it is added to `spentCredits` or converted to `AggregatedSpends`. [1](#0-0)  Because the refund logic afterwards computes `step.Deduction.Sub(spentCredits)` and credits that difference back to the local balance, any real "RPC_EVM" spend that was actually consumed is never subtracted, so the entire earmarked deduction is refunded as if $0 was spent. [2](#0-1)  This mirrors the reported `_decrementWeightUntilFree` bug class: a special-cased subset of entries (deprecated gauges / here, the `RPC_EVM` unit) is excluded from the aggregate total used for accounting, producing incorrect accounting of the "free"/refundable amount.

### Finding Description
`Settle` groups per-node metering responses by `SpendUnit`, then for each unit computes a median spend value and converts it to universal credits via `r.balance.ConvertToBalance(unit, value)`, adding the result to `spentCredits`. [3](#0-2)  Immediately after aggregating raw values for a unit, the code special-cases `unit == "RPC_EVM"` and `continue`s to the next unit — skipping the median computation, conversion to credits, and the addition to `spentCredits` for that unit entirely, while still building the response `Spends` field, so the on-chain/DB metering report *does* record the raw spend values. [4](#0-3)  The earmarked `step.Deduction` (set during `Deduct`) is never reduced by this excluded amount because `spentCredits` under-counts. At the end of `Settle`, the code refunds `step.Deduction - spentCredits` back to the local balance and only calls `AddSpent(spentCredits)`. [5](#0-4)  Consequently, whatever credits were earmarked for an `RPC_EVM`-spending capability call get fully refunded to the workflow's local balance regardless of the actual consumption, and the true "spent" credits total tracked via `balance.AddSpent` (and ultimately reported via `SubmitWorkflowReceipt`'s `CreditsConsumed`) is understated. [6](#0-5) 

### Impact Explanation
Any workflow (owned by an unprivileged workflow author) that composes a capability which reports spend under the `"RPC_EVM"` unit will not be charged in local balance accounting for that spend, yet the local reserved balance is fully replenished as if no spend occurred. This is a billing/metering accounting bug: it allows workflow executions to consume "RPC_EVM"-metered resources for free relative to the local credit balance and understates `CreditsConsumed` sent to the billing service, directly matching the "misreporting/data tampering" impact category (incorrect financial accounting analogous to the incorrect free-weight accounting in the referenced report).

### Likelihood Explanation
This code path executes on every `Settle` call whenever a capability response includes a metering entry with `SpendUnit == "RPC_EVM"`, which is fully within the reach of a normal (unprivileged) workflow author simply by using any capability that reports that unit — no malicious node or operator collusion is required, since the `continue` unconditionally skips accounting regardless of which node reported the value. The code comment itself acknowledges this is a known, deliberate stop-gap ("explicitly ignore RPC_EVM spend types for now"), confirming the accounting gap is real and currently live in the codebase. [1](#0-0) 

### Recommendation
Do not special-case `RPC_EVM` (or any) spend unit when computing `spentCredits`/refund logic. If `RPC_EVM` truly has no supported conversion rate yet, still count the raw value in the metering report and either (a) exclude the corresponding portion of `step.Deduction` from the refund calculation explicitly and symmetrically, or (b) route it into `switchToMeteringMode` (fail-safe, no local accounting) instead of silently skipping only the accounting side while still allowing normal refund math to run with an inconsistent (incomplete) `spentCredits`.

### Proof of Concept
1. Workflow author's workflow invokes a capability that returns `ResponseMetadata.Metering` entries with `SpendUnit: "RPC_EVM"` and a non-zero `SpendValue`, alongside `Deduct` having earmarked `step.Deduction > 0` for that call.
2. `Settle` groups the entries, then hits `if unit == "RPC_EVM" { continue }`, skipping conversion/aggregation for that unit. [7](#0-6) 
3. `spentCredits` remains `0` (or excludes the RPC_EVM contribution) for this step.
4. `r.balance.Add(step.Deduction.Sub(spentCredits))` refunds the full earmarked amount back into the local balance, and `r.balance.AddSpent(spentCredits)` records less spend than actually occurred. [5](#0-4) 
5. The workflow's local credit balance is effectively unaffected by the RPC_EVM spend, and the billing receipt's `CreditsConsumed` undercounts actual usage. [6](#0-5)
