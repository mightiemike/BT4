## Analysis

The Napier bug's root invariant is: **a value derived from an on-chain, attacker-influenceable exchange rate is used directly (with only a tiny/no time-weighting or bounding) to gate value transferred to users, so an attacker who can move that rate at the moment of use can permanently skew accounting.**

The closest reachable analog in this Push Chain scope is not "max scale" itself (there is no PT/YT/Tranche-style accrual here), but the **spot-price Uniswap V3 quote used to gate the `GAS_AND_PAYLOAD` / `GAS` inbound auto-swap**, in `x/uexecutor/keeper/execute_inbound_gas.go` and `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, backed by `k.GetSwapQuote` / `k.CallPRC20DepositAutoSwap` in `x/uexecutor/keeper/evm.go`.

### Title
Sandwichable spot-price Uniswap V3 quote used as slippage floor for inbound gas auto-swap - (File: x/uexecutor/keeper/execute_inbound_gas.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go, x/uexecutor/keeper/evm.go)

### Summary
When an inbound `GAS` or `GAS_AND_PAYLOAD` transaction is finalized, the module fetches a live spot price from the on-chain Uniswap V3 `QuoterV2.quoteExactInputSingle` (no TWAP, `SqrtPriceLimitX96 = 0`) and uses it, minus a flat 5% slippage buffer, as the `minPCOut` floor passed into `UniversalCore.depositPRC20WithAutoSwap`. Because the quote and the actual swap execute inside the same finalizing transaction and both read the pool's current spot price, an unprivileged attacker can manipulate that spot price around this window (classic sandwich) to push the executed swap output down to the 95%-of-manipulated-price floor, siphoning value out of the WPC/PRC20 pool and off the resulting UEA deposit.

### Finding Description
`GetSwapQuote` in `x/uexecutor/keeper/evm.go` calls `QuoterV2.quoteExactInputSingle` with `SqrtPriceLimitX96: big.NewInt(0)`, i.e. it reads the pool's current spot price with no time-weighting: [1](#0-0) 

`ExecuteInboundGas` (for `GAS`) and `gasAndPayloadDepositAutoSwap` (for `GAS_AND_PAYLOAD`) both call this quote and then derive `minPCOut` as a fixed 95% of that same-block quote: [2](#0-1) [3](#0-2) 

The quote-then-swap sequence executes as ordinary EVM calls issued from the module account via `DerivedEVMCall` inside the same state-transition that finalizes the inbound ballot (triggered by a normal `MsgVoteInbound` transaction from a Universal Validator once quorum is reached — see `x/uexecutor/keeper/msg_vote_inbound.go` / `ballot_hooks.go`). Nothing pins the quote to a historical block, checks pool liquidity depth, or requires the caller (the depositing user) to supply their own `minOut`; the protocol computes the floor itself from the manipulable current price and hard-codes a flat 5% tolerance regardless of the actual size of `amount` relative to pool depth.

An unprivileged attacker who holds WPC/PRC20 liquidity can, in the same block window as the finalizing vote transaction, execute a large swap against the same Uniswap V3 pool used by `quoterAddr`/`wpcAddr` (both discoverable via `GetUniversalCoreQuoterAddress`/`GetUniversalCoreWPCAddress`, which are public view calls) to push the spot price down immediately before `depositPRC20WithAutoSwap` executes, then reverse the swap afterward. Since `minPCOut` is derived from the same manipulated spot price (just 5% below it), the auto-swap will still pass the `minPCOut` check while delivering far less real value to the recipient UEA than the pre-manipulation market price would have, with the difference captured by the attacker as arbitrage/sandwich profit. This mirrors the Napier root cause: a self-referential, attacker-movable exchange-rate observation gates the invariant that should protect the victim, instead of protecting it.

### Impact Explanation
This directly corrupts PRC20/native asset accounting on the accepted inbound flow: users whose cross-chain deposits require gas auto-swap into WPC receive materially less value than the honest market price, and the module-driven swap silently accepts it because both the quote and the floor come from the same manipulated observation. This falls within "corruption of PRC20 or native asset accounting ... revert destination ... token mapping" and "unauthorized module-originated EVM execution" impact categories, since honest-user funds are routed through a swap whose price-protection guarantee is illusory when contested by an unprivileged attacker.

### Likelihood Explanation
Likelihood is bounded by: (1) the attacker needing enough capital/liquidity in the specific WPC/PRC20 pool to move the spot price meaningfully within the tolerance window, and (2) transaction ordering — the attacker's swap and reversal must land around the finalizing `MsgVoteInbound` tx in the same or adjacent blocks. Neither requires any privileged role (validator, admin, TSS, relayer); pool addresses and fee tiers are all discoverable via public view calls (`GetUniversalCoreQuoterAddress`, `GetUniversalCoreWPCAddress`, `GetDefaultFeeTierForToken`), making this a realistic MEV/sandwich scenario for any inbound gas-swap of non-trivial size, particularly against thinner pools.

### Recommendation
Do not derive the slippage floor from a same-transaction spot-price quote. Use a TWAP-based quote (or a governance/registry-configured maximum-deviation oracle) for `minPCOut`, require a minimum liquidity-depth check relative to `amount`, and/or widen protection with a per-amount dynamic slippage bound instead of a flat 5%, so that an attacker cannot self-referentially set both the observed price and the guarantee derived from it within the same execution window.

### Proof of Concept
1. Identify the WPC/PRC20 Uniswap V3 pool address via `GetUniversalCoreQuoterAddress`/`GetUniversalCoreWPCAddress` (public view calls) and the fee tier via `defaultFeeTier` on `UniversalCore`.
2. Monitor the mempool/relayer network for an inbound `GAS`/`GAS_AND_PAYLOAD` transaction about to reach quorum (`MsgVoteInbound` from the last needed Universal Validator).
3. Submit a large swap into the same pool to depress the WPC-per-PRC20 spot price just before the finalizing vote tx executes in the same block (or an adjacent block if ordering allows).
4. When `ExecuteInboundGas`/`gasAndPayloadDepositAutoSwap` runs, `GetSwapQuote` returns the manipulated low price; `minPCOut = quote * 95/100` is computed from that same depressed price, so `depositPRC20WithAutoSwap` executes and still satisfies its own floor while delivering less WPC than fair value to the victim's UEA.
5. Attacker reverses the initial swap afterward, pocketing the price difference; this can be repeated against every sizeable `GAS`/`GAS_AND_PAYLOAD` inbound.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
