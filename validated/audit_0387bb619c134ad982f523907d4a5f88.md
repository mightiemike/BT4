Based on my research, I found a strong analog for this bug class in java-tron's vote-reward accounting, where two parallel implementations of the same reward formula diverge for historical data — analogous to the original report's inconsistent unit/decimal handling across parallel conversion paths.

### Title
Vote reward computed via the TVM `withdrawreward`/`queryReward` native precompile silently drops rewards accrued before the new reward algorithm's effective cycle - (File: `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
`VoteRewardUtil.computeReward` (used by the TVM native-contract path for `withdrawreward`) and `MortgageService.computeReward` (used by the classic `WithdrawBalanceContract` path) are two independent re-implementations of the same "vote reward" accounting formula. `MortgageService` correctly splits the cycle range at `newRewardAlgorithmEffectiveCycle` and delegates the pre-upgrade portion to `getOldReward`, while `VoteRewardUtil` unconditionally applies the VI-based (`deltaVi * userVote / DECIMAL_OF_VI_REWARD`) formula to the *entire* `[beginCycle, endCycle)` range, including cycles before the algorithm was ever active for that data source. Because the VI values for those old cycles were only ever backfilled into a separate `RewardViStore` (via `RewardViCalService`), not into `DelegationStore` (which `VoteRewardUtil` reads from), the old-cycle deltas resolve to zero and are silently skipped.

### Finding Description
`MortgageService.computeReward` explicitly branches: [1](#0-0) 

For cycles before `newRewardAlgorithmEffectiveCycle`, it calls `getOldReward`, which either uses the legacy per-cycle double-based formula or, if `allowOldRewardOpt()` is enabled, delegates to `RewardViCalService.getNewRewardAlgorithmReward`, which reads VI values from the dedicated `rewardViStore`: [2](#0-1) [3](#0-2) 

In contrast, `VoteRewardUtil.computeReward` (the TVM native-contract path used by `WithdrawRewardProcessor` for the `withdrawreward` opcode/precompile) has no such split. It unconditionally reads `deltaVi` for the whole `[beginCycle, endCycle)` range directly from `repository.getDelegationStore().getWitnessVi(...)`: [4](#0-3) 

`DelegationStore.getWitnessVi` only returns non-zero values for cycles where `DelegationStore.accumulateWitnessVi`/`setWitnessVi` were actually invoked — i.e., cycles occurring at/after the new reward algorithm went live: [5](#0-4) 

The one-time backfill of VI for pre-upgrade cycles is written to a *different* store (`RewardViStore`, populated by `RewardViCalService.accumulateWitnessVi`/`startRewardCal`), which `VoteRewardUtil` never queries: [6](#0-5) 

Consequently, for any pre-upgrade cycle, `beginVi`/`endVi` obtained by `VoteRewardUtil` are both `BigInteger.ZERO`, so `deltaVi.signum() <= 0` and that portion of the reward is skipped entirely (`continue`), rather than being computed via the legacy or backfilled path as `MortgageService` does. This is directly analogous to the original bug class: two code paths that are supposed to produce the same accounted value under a shared formula diverge because one path assumes a data representation (backfilled/legacy) that the other never applies, resulting in an inconsistent/lossy value being produced for the same logical state.

### Impact Explanation
Any unprivileged account (in particular a smart-contract account that voted for witnesses prior to the new reward algorithm's activation cycle and later withdraws rewards through the TVM `withdrawreward` precompile, e.g. via `WithdrawRewardProcessor`) will lose the portion of its accrued vote reward corresponding to cycles predating the algorithm switch. This is a concrete accounting/settlement bug causing under-payment of legitimately earned rewards — value loss for the user — while the same account withdrawing via the classic `WithdrawBalanceContract`/`MortgageService.withdrawReward` path would receive the full, correct amount. This produces state divergence between the two withdrawal paths for the same underlying reward entitlement.

### Likelihood Explanation
Reachable by any unprivileged contract account that: (1) voted for witnesses before `newRewardAlgorithmEffectiveCycle`, (2) has an outstanding `beginCycle`/`endCycle` window spanning the old algorithm's cycles, and (3) withdraws rewards using the TVM-based `withdrawreward` native contract instead of the classic transaction type. Given `allowTvmVote`-gated TVM voting/reward features were introduced after the original reward-algorithm upgrade, there is a realistic window where accounts accumulated reward-eligible votes under the old algorithm and only later adopt the TVM-based withdrawal flow, making this consistently reachable rather than purely theoretical.

### Recommendation
Align `VoteRewardUtil.computeReward` with `MortgageService.computeReward`: split the `[beginCycle, endCycle)` range at `newRewardAlgorithmEffectiveCycle`, and for the pre-upgrade portion, delegate to the same `getOldReward`/`RewardViCalService.getNewRewardAlgorithmReward` (or equivalent legacy per-cycle) logic that `MortgageService` uses, ensuring both code paths compute identical reward amounts for identical account/cycle state. Add unit/integration tests that withdraw the same account's rewards through both paths and assert equality, particularly across the algorithm-switch boundary.

### Proof of Concept
1. Configure `newRewardAlgorithmEffectiveCycle` at some cycle `N` (as done in existing tests), with `allowOldRewardOpt()` enabled or a legacy double-based reward for cycles `< N`.
2. Have witness A accrue votes/rewards for cycles `1..N-1` for account `X` (a contract account) without withdrawing, so `beginCycle=1`.
3. Advance to cycle `M > N`.
4. Call `MortgageService.withdrawReward(X)` (or `queryReward`) and record the reward amount `R1`; it will include the pre-upgrade cycles via `getOldReward`.
5. Reset state equivalently, then instead invoke the TVM path (`WithdrawRewardProcessor.execute` / `VoteRewardUtil.withdrawReward`) for the same account/vote history and record `R2`.
6. Observe `R2 < R1` because `VoteRewardUtil.computeReward` reads `DelegationStore.getWitnessVi` for cycles `1..N-1`, gets `BigInteger.ZERO`, and skips that reward entirely, while `MortgageService` correctly accounts for it.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private void accumulateWitnessVi(long cycle, byte[] address) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long voteCount = getWitnessVote(cycle, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
