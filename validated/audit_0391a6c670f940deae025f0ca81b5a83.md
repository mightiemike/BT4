### Title
Meta-Transaction Deposit Refund Misdirection Allows Sender to Drain Relayer Funds — (File: `runtime/runtime/src/actions.rs`)

---

### Summary

When a `DelegateAction` (meta-transaction) inner receipt fails execution on the receiver's shard, the attached deposit is refunded to the `sender_id` (the DelegateAction signer, Alice) rather than the relayer who actually paid for it. An unprivileged user can exploit this by crafting a `DelegateAction` with a large deposit attached to an action designed to fail, causing the relayer to permanently lose the deposit while the attacker gains it. This is the nearcore analog to clickjacking: the attacker tricks a third party into performing an action that transfers funds to the attacker without the third party's informed consent.

---

### Finding Description

In `apply_delegate_action` (`runtime/runtime/src/actions.rs`), when a `DelegateAction` is processed on Alice's shard, a new inner receipt is created. The critical assignment is:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // ← Alice, NOT the relayer
    receiver_id: delegate_action.receiver_id().clone(),
    ...
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(),  // ← Relayer
        ...
        actions: delegate_action.get_actions(),  // includes FunctionCall with deposit
    }),
});
``` [1](#0-0) 

The relayer's account is only recorded as `signer_id` in the inner `ActionReceipt`. The `predecessor_id` of the inner receipt is Alice.

When the inner receipt fails execution on the receiver's shard, the runtime's refund logic calls `receipt.balance_refund_receiver()`: [2](#0-1) 

This returns `refund_to.as_ref().unwrap_or_else(|| self.predecessor_id())` — which is Alice, not the relayer. The deposit refund receipt is then pushed to Alice: [3](#0-2) 

The code comment at lines 471–475 of `actions.rs` explicitly acknowledges this design:

> "Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas. If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction... Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit." [4](#0-3) 

The protocol documentation also confirms this:

> "there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [5](#0-4) 

The nearcore code has no guard preventing Alice from crafting such a `DelegateAction`. The only mitigation is a relayer-side check, which is not enforced by the protocol.

---

### Impact Explanation

**Broken invariant:** The party that pays for a deposit (the relayer) must receive the refund if the action fails. Instead, the deposit refund goes to the `DelegateAction` sender (Alice), who did not pay for it.

**Exact corrupted value:** Relayer's balance decreases by `deposit`; Alice's balance increases by `deposit`.

This matches the allowed impact gate: **stealing or loss of funds** and **balance manipulation**. The attack is repeatable across multiple relayers or against the same relayer, enabling systematic fund extraction.

---

### Likelihood Explanation

Medium. The attack requires Alice to convince a relayer to submit her `DelegateAction`. This is feasible because:
1. Relayers are designed to accept and submit `DelegateAction`s from users — that is their purpose.
2. The relayer may not verify whether the inner action is designed to fail (e.g., calling a non-existent method on a contract).
3. The attack can be disguised as a legitimate meta-transaction (e.g., a token transfer that "accidentally" fails).
4. No special privileges are required — Alice is a fully unprivileged user.

The `FunctionCallPermission` allowance bypass documented at `docs/architecture/how/meta-tx.md` lines 258–260 further widens the attack surface: even a function-call access key with a near-zero allowance can be used to sign a `DelegateAction` with a large deposit, since the allowance is not checked during delegate action key validation. [6](#0-5) [7](#0-6) 

---

### Recommendation

The protocol should redirect deposit refunds for failed inner receipts of `DelegateAction`s to the relayer (the `signer_id` of the outer receipt), not to the `sender_id` (Alice). Concretely, the inner receipt created in `apply_delegate_action` should use `ActionReceiptV2` with `refund_to: Some(relayer_account_id)` so that `balance_refund_receiver()` returns the relayer rather than Alice. This would close the misdirection at the protocol level without requiring relayer-side workarounds. [8](#0-7) 

---

### Proof of Concept

1. Alice creates a `DelegateAction`:
   - `sender_id = Alice`
   - `receiver_id = some_contract`
   - `actions = [FunctionCall { method_name: "non_existent_method", deposit: 100 NEAR }]`
   - Signs it with her key (full-access or function-call key — allowance is not checked for delegates).

2. Alice sends the signed `DelegateAction` to a relayer service.

3. The relayer wraps it in a transaction and submits it, paying the 100 NEAR deposit from its own balance.

4. On Alice's shard, `apply_delegate_action` creates an inner receipt with `predecessor_id = Alice`, `signer_id = Relayer`, and the 100 NEAR deposit.

5. On `some_contract`'s shard, the inner receipt fails (`MethodNotFound`).

6. The runtime calls `receipt.balance_refund_receiver()` → returns `predecessor_id` = Alice.

7. A `Receipt::new_balance_refund(&Alice, 100 NEAR)` is pushed.

8. Alice's balance increases by 100 NEAR; the relayer's balance is permanently reduced by 100 NEAR.

The attack can be repeated indefinitely with different deposit amounts and different failing contracts, draining the relayer's funds. [9](#0-8) [10](#0-9) [11](#0-10)
