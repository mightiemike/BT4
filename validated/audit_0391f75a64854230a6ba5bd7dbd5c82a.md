### Title
Unbounded legacy `getOldReward` loop lets a dormant voter force an O(cycles × votes) synchronous scan during `WithdrawBalanceContract` execution - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Finding Description
`MortgageService.withdrawReward` is invoked unconditionally from `WithdrawBalanceActuator.execute()` for every `WithdrawBalanceContract` transaction [1](#0-0) . Inside it, `computeReward(beginCycle, endCycle, accountCapsule)` is called with `beginCycle` taken directly from `delegationStore.getBeginCycle(address)` (last time the account settled) and `endCycle = currentCycle` (the live chain cycle) [2](#0-1) . When `beginCycle < newAlgorithmCycle`, `computeReward` calls `getOldReward(beginCycle, oldEndCycle, srAddresses)` [3](#0-2) . If `allowOldRewardOpt()` is false, `getOldReward` runs a straight `for (long cycle = begin; cycle < end; cycle++) reward += computeReward(cycle, votes)` loop, where the inner `computeReward(cycle, votes)` iterates the full vote list per cycle [4](#0-3) [5](#0-4) .

There is no bound on the gap `endCycle - beginCycle` before it reaches `getOldReward`: any account can vote once (populating a vote list) and then simply avoid sending any `WithdrawBalanceContract` for an arbitrary number of cycles. Cycles advance automatically once per maintenance interval regardless of user action [6](#0-5) , so `beginCycle` staying fixed while `currentCycle` grows is a normal, permissionless outcome of doing nothing. `WithdrawBalanceActuator.validate()` only checks a 24h cooldown since the *account's own* `latestWithdrawTime` and that pending reward is positive — it does not check or cap the size of `endCycle - beginCycle`, nor the size of the vote list [7](#0-6) . `calcFee()` for this actuator returns `0`, i.e., the transaction is essentially fee-exempt/flat-fee regardless of the amount of work it triggers [8](#0-7) .

Additionally, this same code path is reachable from the TVM via `VoteRewardUtil.withdrawReward` / `Program.withdrawReward`, meaning an attacker could also trigger it via a `WithdrawRewardContract`-invoking smart-contract call, though this specific finding focuses on the `WithdrawBalanceActuator` entry point named in the question [9](#0-8) .

### Impact Explanation
An account that votes once and then stays dormant while `allowOldRewardOpt()` remains false accumulates an ever-growing `[beginCycle, newAlgorithmCycle)` window. When the account (or anyone triggering `mortgageService.withdrawReward` for it, e.g. via `payReward`/other flows that also call it) finally submits a `WithdrawBalanceContract`, block/tx execution synchronously executes `cycles × votes` iterations of `computeReward`, each doing store reads (`delegationStore.getReward`, `getWitnessVote`) and floating point math. This is CPU/I-O work proportional to attacker-chosen dormancy duration and vote-list size, executed inside consensus-critical block processing, for a transaction that costs a flat/zero fee — a case of underpriced public work that can degrade node performance for all validators processing that block.

### Likelihood Explanation
Preconditions are attacker-reachable and require no privilege: `allowChangeDelegation()` must be true (this is the normal steady-state for delegation-enabled chains) and `allowOldRewardOpt()` false (this is the legacy/default state before the reward-Vi optimization is turned on, which per `ComputeRewardTest` is a governance-controlled flag `saveAllowOldRewardOpt`) [10](#0-9) . An attacker only needs to submit a `VoteWitnessContract` once and then do nothing for many cycles — this is standard permissionless account behavior, fully repeatable, and scales with however many cycles/votes the attacker is willing to accumulate before finally broadcasting `WithdrawBalanceContract`.

### Recommendation
Bound the per-transaction cost of the legacy reward loop, e.g.:
- Cap `endCycle - beginCycle` processed in a single `withdrawReward`/`queryReward` call (e.g., process in fixed-size chunks and require multiple withdrawal transactions to fully catch up, persisting partial progress to `beginCycle`), or
- Charge a fee proportional to `(endCycle - beginCycle) * votes.size()` for `WithdrawBalanceContract`/TVM `withdrawReward`, or
- Force migration to `allowOldRewardOpt()`/the O(1) Vi-based algorithm before allowing accounts to accumulate large gaps, or retroactively backfill stale accounts via a background/maintenance job (amortized cost) instead of doing it synchronously inside `execute()`.

```java
// framework/src/test/java/org/tron/core/services/OldRewardGapTest.java
// Extends BaseTest, mirrors setup in DelegationServiceTest / ComputeRewardTest.

@Test
public void unboundedOldRewardLoopCost() {
  dbManager.getDynamicPropertiesStore().saveChangeDelegation(1);
  dbManager.getDynamicPropertiesStore().saveAllowOldRewardOpt(0); // legacy path forced
  dbManager.getDynamicPropertiesStore().saveNewRewardAlgorithmEffectiveCycle(); // sets far-future cutover

  byte[] sr = decodeFromBase58Check("TLTDZBcPoJ8tZ6TTEeEqEvwYFk2wgotSfD");
  byte[] user = decodeFromBase58Check("THKJYuUmMKKARNf7s2VT51g5uPY6KEqnat");

  AccountCapsule account = dbManager.getAccountStore().get(user);
  account.addVotes(ByteString.copyFrom(sr), 1_000_000);
  dbManager.getAccountStore().put(user, account); // vote once

  dbManager.getDynamicPropertiesStore().saveCurrentCycleNumber(0);
  dbManager.getDelegationStore().setBeginCycle(user, 0);
  dbManager.getDelegationStore().setEndCycle(user, 1);

  int GAP = 50_000; // attacker-chosen dormancy period
  for (int c = 0; c < GAP; c++) {
    dbManager.getDelegationStore().setWitnessVote(c, sr, 100_000_000);
    dbManager.getDelegationStore().addReward(c, sr, 1_000); // nonzero reward each cycle
  }
  dbManager.getDynamicPropertiesStore().saveCurrentCycleNumber(GAP);

  long start = System.nanoTime();
  dbManager.getMortgageService().withdrawReward(user); // simulates WithdrawBalanceActuator.execute()
  long elapsedMs = (System.nanoTime() - start) / 1_000_000;

  // Assert this scales roughly linearly with GAP and exceeds a "flat fee" budget,
  // e.g. compare against a run with GAP=100 and show >100x wall time for >100x GAP,
  // while WithdrawBalanceActuator.calcFee() remains 0 regardless of GAP.
  Assert.assertTrue("legacy loop cost should scale with attacker-chosen gap",
      elapsedMs > /* threshold proving linear-in-GAP cost */ 50);
}
```
Run with increasing `GAP` values (e.g., 1k, 10k, 100k) to demonstrate wall-clock time scaling linearly with attacker-controlled dormancy while the transaction fee (`calcFee()` returns `0`) stays constant, confirming underpriced, unbounded work executed synchronously in `execute()`.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
