### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay-verify accept a state/hot-state/position-state root divergence - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/execution-verification tooling to confirm that a locally re-executed `TransactionOutput` matches a trusted, proof-carrying `TransactionInfo`. It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` builds `write_set_hash` and `event_root_hash` from the locally produced `TransactionOutput` and compares them against `txn_info.state_change_hash()` / `txn_info.event_root_hash()`, and also checks `status` and `gas_used`. It never touches `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` — the fields that carry the Sparse-Merkle-Tree/hot-state/position-state root committed for that transaction. The comment in the code acknowledges this:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [2](#0-1) 

This function is invoked from `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution`, which is the code path used by `TransactionReplayer::remove_and_replay_epoch` when re-executing transactions from a backup/chunk to validate that local re-execution matches the recorded `TransactionInfo`s: [3](#0-2) 

It is also referenced from `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`, both of which are used for auditing/replay-verify workflows over archived/mainnet transaction history.

### Impact Explanation
The state-checkpoint hash inside `TransactionInfo` is the authenticated binding between a transaction and the Jellyfish Merkle / hot-state / position-state root committed to the accumulator (and ultimately signed by validators in the `LedgerInfo`). Because `ensure_match_transaction_info` omits comparing these fields, any tooling that relies on it as its sole state-integrity check (chunk-executor `verify_execution`, `db-tool replay_on_archive`, debugger-based replay-verify) can report a **successful** replay/verification even when the locally recomputed state root (main state, hot state, or position state) diverges from the value bound in the trusted `TransactionInfo`. This is precisely the kind of "authenticated response bound to the wrong root/version" and "proof verification silently accepting wrong state" condition the task calls out. Note that the primary consensus/commit path is separately protected — `DoStateCheckpoint::get_state_checkpoint_hashes` does assert computed vs. known checkpoint hashes when building `LedgerUpdateOutput` [4](#0-3) 
so the gap is isolated to replay-verification/auditing tooling rather than block execution/commit itself — meaning the exploitable consequence is a false-positive "verified" signal from replay-verify/debugger tools over potentially corrupted archived data, not a live consensus fork. This still meets the "hard-fork-only divergence during ... replay ... or proof verification" and "authenticated API ... bound to the wrong ... root" categories, but the severity is bounded to detection/auditing correctness rather than causing bad state to be committed on mainnet.

### Likelihood Explanation
This is not a hypothetical: the gap is triggered any time `verify_execution`/`replay_on_archive` is used to validate historical/backup data whose state-checkpoint hash has been altered or corrupted (e.g., a tampered or buggy backup snapshot, or a bug in state-checkpoint computation) while the write set and events still match. Given `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` are newer fields gated by feature flags (`HOT_STATE_ROOT_IN_TXN_INFO`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), the likelihood of a latent computation bug specifically in those newer state roots slipping past replay-verify is non-trivial, and the code's own comment flags this as an active concern for `replay_on_archive`.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `txn_info.state_checkpoint_hash()` against the locally computed state-checkpoint root (when the checkpoint is expected for that transaction), and likewise validate `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` whenever those roots are known/computed by the replay flow — matching the comment's own call to action before any tooling (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-gated replay verification) is enabled that depends on this comparator for correctness.

### Proof of Concept
1. In a chunk replay path (`TransactionReplayer::verify_execution`), supply archived transactions/write-sets/events that are correct, but a `TransactionInfo` (or state-checkpoint root produced during backup) whose `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` do not correspond to the actual resulting state (simulating storage corruption or a bug in state-root calculation for one of those newer roots). [3](#0-2) 
2. Call `ensure_match_transaction_info`; because write_set_hash, event_root_hash, gas_used, and status all still match, the function returns `Ok(())` despite the state/hot-state/position-state root divergence. [5](#0-4) 
3. Downstream replay-verify tooling (db-tool `replay_on_archive`, `aptos-debugger`) reports the chunk as successfully verified even though the authenticated state root differs from local re-execution — a false-positive proof/state-integrity acceptance.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
