## Title
OAuth callback and token-exchange auth handlers never check the `SessionStorage.storeSession()` success return value — ([File: packages/apps/shopify-app-express/src/auth/auth-callback.ts])

### Summary
The `SessionStorage` interface explicitly returns a `Promise<boolean>` from `storeSession()` to signal whether the session was actually persisted [1](#0-0) . Every first-party auth entry point in `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router` calls `storeSession()` after OAuth/token-exchange completes but discards this boolean and continues execution as if persistence always succeeds — this is the same bug class as the reported MerkleVesting issue where an unchecked external call's success/failure is assumed rather than verified.

### Finding Description
After a merchant completes OAuth or the app performs token exchange, the returned `Session` (containing the freshly-issued access token) is written to storage with an un-checked, fire-and-forget `await`:

- `authCallback()` in shopify-app-express: `await config.sessionStorage.storeSession(callbackResponse.session);` immediately followed by webhook registration, setting `res.locals.shopify.session`, and firing `afterAuth` — none of which check the boolean result [2](#0-1) .
- `performTokenExchange()` in shopify-app-express: both the offline and online `storeSession` calls are unchecked before `next()` is invoked and the session is trusted for the rest of the request pipeline [3](#0-2) .
- `handleAuthCallbackRequest()` in shopify-app-remix's auth-code-flow strategy: `await config.sessionStorage!.storeSession(session);` is unchecked before redirecting the merchant back into the embedded app [4](#0-3) .
- The token-exchange strategy's `authenticate()` performs the same unchecked pattern for both offline and online sessions [5](#0-4) .
- `invalidateAccessToken()` likewise blindly trusts that clearing the access token via `storeSession` succeeded [6](#0-5) .

Notably, the library's own documentation for the same operation demonstrates checking the return value and logging a warning on failure — showing the correct pattern was known but not implemented in the production code paths: `if ((await sqliteSessionStorage.storeSession(callbackResponse.session)) == false) { console.log('Failed to store session...') }` [7](#0-6) . The `implementing-session-storage.md` guide also models implementations that legitimately `return false` on a caught write error rather than throwing [8](#0-7) , confirming `false` is a supported, non-exceptional outcome that calling code is expected to handle.

### Impact Explanation
If a merchant's configured `SessionStorage` implementation returns `false` (a documented, supported outcome — e.g., a transient DB write failure, as in the original ERC20 analog), the auth handlers proceed as though the session was durably saved: webhooks get registered with an access token that was never persisted, `afterAuth` hooks fire, and the merchant is redirected into the app UI using an in-memory session. On the merchant's very next request, `ensureInstalledOnShop`/session-lookup middleware will find no stored session and force the merchant back into OAuth — trapping them in a redirect loop until the underlying storage issue resolves. This is a DoS of the auth handler for that shop, with no way for the app or merchant to detect why installation appears successful yet immediately breaks.

### Likelihood Explanation
Any transient storage failure (DB connection blip, unique-constraint retry exhaustion, etc.) during the single, unprivileged OAuth/token-exchange flow that every merchant goes through triggers this path — no attacker action beyond normal install/re-auth is required. Because `storeSession` returning `false` is explicitly part of the interface contract and documented pattern, this is a realistic failure mode, not a purely theoretical one.

### Recommendation
In `auth-callback.ts`, `perform-token-exchange.ts`, `auth-code-flow.ts`, `token-exchange.ts` (both remix and react-router variants), and `invalidate-access-token.ts`, check the boolean returned by `storeSession()`; on `false`, abort the flow, log/alert, and return an error response (e.g., 500) instead of proceeding to register webhooks, invoke `afterAuth`, or redirect the merchant into the app as if authenticated.

### Proof of Concept
1. Configure a custom `SessionStorage` whose `storeSession` catches a write error and returns `false` (per the documented pattern in `implementing-session-storage.md`).
2. Simulate a transient failure during OAuth callback or token exchange.
3. Observe that `authCallback`/`performTokenExchange`/`handleAuthCallbackRequest`/`token-exchange.authenticate` all proceed to register webhooks, run `afterAuth`, and redirect/`next()` the request as authenticated, despite `storeSession` returning `false`.
4. On the following request, the session cannot be loaded (it was never stored), forcing the merchant back into OAuth — an unrecoverable loop while the storage failure persists.
