### Title
Native-token transfers sent directly to the gateway/vault contract (bypassing `sendFunds`) are never observed and are permanently lost — ([File: universalClient/chains/evm/event_listener.go])

### Summary
Push Chain's inbound-observation pipeline mirrors the Rio `RewardDistributor` pattern: it relies solely on a specific "trigger" (matching known event-log topics emitted by explicit gateway/vault method calls) to become aware that funds arrived from a source chain. A native-token transfer sent directly to the gateway or vault contract address — without invoking the `sendFunds`/`executeUniversalTx` methods that emit the tracked events — produces no event, is never picked up by Universal Validators, never becomes a `UniversalTx`, is never minted as PRC20, and has no rescue path, because the rescue mechanism itself requires a pre-existing `UniversalTx` to attach to.

### Finding Description
`EventListener` is built from a fixed, narrow set of event topics derived from `GatewayMethods`/`VaultMethods` (`sendFunds`, `executeUniversalTx`, `revertUniversalTx`, `finalizeUniversalTx`, `fundsRescued`): [1](#0-0) 

Block scanning is then strictly filtered by contract address (gateway + vault) and by this fixed topic list — nothing else is ever considered an inbound signal: [2](#0-1) 

`ParseEvent` only understands these same enumerated event types and silently drops anything else: [3](#0-2) 

This is architecturally identical to the Rio bug: the protocol's only "receive" mechanism for incoming value is an explicit, narrow trigger (there, `receive()`; here, a specific event-log topic from a specific method call). Any value that reaches the gateway/vault contract through a path that doesn't emit one of these five topics — e.g., a plain native-currency transfer to the gateway address, or any other value-transfer mechanism the contract may support outside of `sendFunds` — is invisible to the entire inbound pipeline (`VoteInbound` → `UniversalTx` → `depositPRC20`).

Critically, unlike a normal failed/observed inbound, there is **no recovery path** for funds that were never observed at all. The only fund-recovery mechanism, `AttachRescueOutboundFromReceipt`, requires decoding a `RescueFundsOnSourceChain` event whose `universalTxId` must reference an **already-existing** `UniversalTx`: [4](#0-3) 

Since no `UniversalTx` was ever created (no observation ever fired), rescue is structurally unreachable for these funds — precisely mirroring the Rio finding that "there is currently no way to distribute [unobserved] rewards."

### Impact Explanation
Funds sent to the gateway/vault contract through any path other than the enumerated method calls are permanently and irrecoverably lost to the sender: never minted as PRC20 on Push Chain, and ineligible for the rescue-funds flow because no `UniversalTx` exists to attach a rescue outbound to. This is a direct, unprivileged, permanent loss of user funds triggered purely by ordinary interaction with the documented bridge entry point (the gateway contract address), matching the "permanent loss ... of user ... funds" allowed-impact category.

### Likelihood Explanation
Reachable by any unprivileged external user simply by sending native currency to the gateway/vault address instead of calling `sendFunds` (a mistake that is common with bridge contracts, and is exactly the scenario that made the original Rio EL-rewards bug a valid Medium finding — value can reach a contract through a channel other than its designated entry point). No relayer, validator, or admin action is required to trigger the loss; only honest-validator behavior (they correctly refuse to vote on something they cannot observe) is assumed.

### Recommendation
- Ensure the on-chain gateway/vault contracts reject any incoming native-value transfer that does not go through an explicit tracked entry point (i.e., no unguarded `receive()`/`fallback()` capable of accepting value), so that "invisible" deposits cannot occur in the first place.
- If accepting bare transfers is a requirement, add an event (and a corresponding `EventListener` topic + `ParseEvent` case) for that path so Universal Validators can observe and process it like any other inbound.
- Add a validator-side reconciliation check (periodic balance-vs-accounted-total comparison per gateway/vault contract) that can flag/alert on unaccounted incoming value, and extend the rescue-funds flow to support recovery of funds with no corresponding `UniversalTx` (e.g., an admin/governance-gated sweep informed by such reconciliation).

### Proof of Concept
1. A user calls the gateway contract's plain-transfer path (or any function that increases the contract's native balance without emitting `sendFunds`), sending native tokens intended to bridge to Push Chain.
2. `EventListener.processBlockChunk` filters logs by the fixed `eventTopics` list built in `NewEventListener`; since no matching topic was emitted, no log is returned for this transaction. [5](#0-4) 
3. No `store.Event` is created, so `VoteInbound` is never called by any Universal Validator, and no `PendingInbounds`/`UniversalTx` entry is ever created for this transaction.
4. The user's funds remain locked in the gateway/vault contract on the source chain indefinitely. Since `AttachRescueOutboundFromReceipt` requires an existing `UniversalTx` keyed by `universalTxId`, and none exists, the rescue-funds flow cannot recover them. [6](#0-5)

// ParseEvent parses a log into a store.Event based on the event type.
// eventType should be one of: sendFunds, executeUniversalTx, revertUniversalTx.
func ParseEvent(log *types.Log, eventType string, chainID string, logger zerolog.Logger) *store.Event {
	if len(log.Topics) == 0 {
		return nil
	}

	switch eventType {
	case EventTypeSendFunds:
		return parseSendFundsEvent(log, chainID, logger)
	case EventTypeExecuteUniversalTx, EventTypeRevertUniversalTx, EventTypeFinalizeUniversalTx, EventTypeFundsRescued:
		// All share the same topic layout: Topics[1]=txID, Topics[2]=universalTxID.
		return parseOutboundObservationEvent(log, chainID, logger)
	default:
		logger.Debug().
			Str("event_type", eventType).
			Str("tx_hash", log.TxHash.Hex()).
			Msg("unknown event type, skipping")
		return nil
	}
}
