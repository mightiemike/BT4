## Title
Panic on empty L1 handler calldata in message-hash computation - ([File: crates/starknet_api/src/hash.rs])

## Summary
`l1_handler_message_hash` computes the L1→L2 message hash for an `L1HandlerTransaction` by unconditionally calling `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")`. `Calldata` carries no non-empty invariant and `L1HandlerTransaction` derives `Deserialize`, so a transaction with zero-length calldata is constructible and will make this call panic instead of returning an error, matching the TBTC report's root cause: a user/external-controlled field ("one of the relatively few pieces of data in the system that is completely user-controlled") that was not validated at the point of use, missed by unit tests covering the redemption/message-processing entry point.

## Finding Description
`crates/starknet_api/src/hash.rs` defines: [1](#0-0) 
The function panics via `.expect()` if `calldata.0` is empty. The codebase already acknowledges this exact hazard in a sibling function `payload_size` (in `crates/starknet_api/src/executable_transaction.rs`), which was hardened with `saturating_sub` specifically because "`Calldata` has no non-empty invariant and `L1HandlerTransaction` derives `Deserialize`, so an empty calldata is constructible," as documented and tested: [2](#0-1) [3](#0-2) 
However, `calc_msg_hash`/`l1_handler_message_hash` was not given the same treatment and still uses `.expect()`, i.e., the fix was applied to one call site but missed at another — the same class of oversight the TBTC incident describes (incomplete validation coverage of a user-controlled field across all code paths that consume it).

This function is reachable from `L1EventsProvider::get_txs`, which logs the message hash for every proposed L1 handler transaction: [4](#0-3) 
and from RPC API handlers in `crates/apollo_rpc/src/v0_8/api/api_impl.rs` (message-status lookups) that call `calc_msg_hash` on `L1HandlerTransaction` objects, including ones sourced from the storage/feeder-gateway representation `apollo_starknet_client::reader::objects::transaction::L1HandlerTransaction`, which is `#[derive(Deserialize)]` with no length validation on `calldata`: [5](#0-4) 

## Impact Explanation
If an `L1HandlerTransaction` with empty calldata can enter any of these code paths (e.g. via a malformed/legacy synced block, a crafted feeder-gateway/L2 sync payload, or a stored transaction with empty calldata), `l1_handler_message_hash` panics. In the proposer path (`L1EventsProvider::get_txs`), a panic during block proposal would crash the proposing sequencer node's process/thread that builds blocks, which can prevent that node from confirming new transactions and, if this affects consensus-critical block-building logic broadly, constitutes a liveness/availability risk (network unable to confirm new transactions from that node) rather than silent data corruption.

## Likelihood Explanation
Likelihood is constrained by the fact that legitimate L1 message flows (`MessageFromL1 -> L1HandlerTransaction`, the L1 events scraper, and OS-level `consume_l1_to_l2_message`) always prepend the L1 sender address, guaranteeing non-empty calldata in the normal path: [6](#0-5) 
The realistic trigger requires an `L1HandlerTransaction` object with empty calldata to be deserialized/constructed outside that guaranteed-prepend path (sync from feeder gateway, stored/replayed transaction, or a future direct submission surface) and then passed to `calc_msg_hash`. I could not fully confirm within the available context whether any of the identified call sites (`api_impl.rs`, `l1_scraper.rs`) can receive such a transaction from an unprivileged, externally-controlled source without prior validation — this needs further tracing of the exact call chain and any upstream validation before `calc_msg_hash` is invoked.

## Recommendation
Harden `l1_handler_message_hash` the same way `payload_size` was hardened: return a `Result`/explicit error (or treat empty payload gracefully) instead of `.expect()`-panicking, and add unit tests exercising empty-calldata `L1HandlerTransaction` values through every call site (`calc_msg_hash`, RPC handlers, provider logging) to close the gap between the two currently-inconsistent handling strategies for the same invariant violation.

## Proof of Concept
```rust
// Construct an L1HandlerTransaction with empty calldata (allowed, since Calldata
// has no non-empty invariant and the type derives Deserialize).
let tx = starknet_api::transaction::L1HandlerTransaction {
    version: TransactionVersion::ZERO,
    nonce: Nonce::default(),
    contract_address: ContractAddress::default(),
    entry_point_selector: EntryPointSelector::default(),
    calldata: Calldata(std::sync::Arc::new(vec![])),
};

// This panics: split_first() on an empty slice returns None, and .expect() aborts.
let _ = tx.calc_msg_hash();
```
