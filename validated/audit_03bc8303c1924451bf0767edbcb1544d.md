### Title
Webhook authentication only signs the request body, not the shop-identifying headers, enabling cross-tenant webhook forgery - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-201`) computes and checks the webhook HMAC over `rawBody` only, using the app's single, shared `apiSecretKey`. The `X-Shopify-Shop-Domain` header (and topic/webhookId/apiVersion) is read out-of-band by `checkWebhooksHeaders`/`checkEventsHeaders` in `packages/apps/shopify-api/lib/webhooks/validate.ts:99-146` without being bound to the signed payload in any way. Since `apiSecretKey` is identical for every shop that installs the app, a body+HMAC pair that is valid for shop A's webhook is also a valid HMAC for the exact same body claimed to originate from shop B — the "channel" (shop domain) is never authenticated, mirroring the Allora `OnRecvPacket` bug where the channel ID/sender was never checked against the packet.

### Finding Description
The webhook signature scheme in `validateHmacString`/`validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:153-201`) validates:
```
localHmac = HMAC-SHA256(apiSecretKey, rawBody)
```
It never incorporates the shop domain, webhook topic, or webhook ID into the signed material. `checkWebhooksHeaders` (`packages/apps/shopify-api/lib/webhooks/validate.ts:99-146`) then simply reads these fields from plain, unsigned HTTP headers and returns them as trusted (`valid: true`) output. Consumers such as `authenticateWebhookFactory` in `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:35-52` and the identical react-router variant pass `check.domain` straight into `ensureValidOfflineSession(params, check.domain)` to fetch that shop's stored offline access token and construct an authenticated `admin` API client for it. Because `apiSecretKey` is shared across all shops that install a given app, any merchant who has installed the app on their own store can capture one legitimately-signed webhook body+HMAC pair (or generate one, since they control their store's events) and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different, victim shop that has also installed the app. The HMAC check still passes (it never looked at the domain header), and the webhook handler runs the app's business logic against the victim shop's offline session/access token and data.

### Impact Explanation
This is a cross-tenant access vulnerability: a low-privilege actor (any merchant who has installed the app) can forge/replay webhook deliveries attributed to a different tenant, triggering the app's webhook-driven business logic (order/product/customer mutations, `APP_UNINSTALLED` cleanup, GDPR/mandatory compliance topics, etc.) using the victim shop's offline access token and stored session, without any interaction from the victim. Depending on what the specific app's webhook handlers do, this can corrupt victim shop data, leak information back to the attacker via handler side effects, or trigger destructive actions (e.g. forged `APP_UNINSTALLED` wiping the victim's stored session/data).

### Likelihood Explanation
Reachable by any anonymous/self-registered merchant with no special privileges: they only need (a) their own valid installation of the target app to obtain one genuine `(rawBody, X-Shopify-Hmac-Sha256)` pair, and (b) knowledge/guess of a target shop's `myshopify.com` domain that also has the app installed (shop domains are not secret and are often discoverable). No signature secret theft, MITM, or dependency issue is required — the flaw is structural in how the library scopes its HMAC check.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the authenticated material, or otherwise cryptographically verify the claimed domain matches the webhook delivery, for example by:
- Looking up the stored offline session for `check.domain` and, before trusting it, confirming that the shop actually has a webhook currently registered/expected for this topic (defense in depth), and/or
- Including the `X-Shopify-Shop-Domain`/topic/webhook-id headers in the HMAC computation server-side comparison logic where feasible, and/or
- At minimum, rate-limiting/monitoring for repeated webhook deliveries with mismatched domains and the same body/HMAC combination, since a legitimate Shopify-origin webhook for shop A will never carry shop B's domain header.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`; app's shared `apiSecretKey` is `S`.
2. Attacker triggers/collects a real webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: HMAC-SHA256(S, B)` (topic e.g. `APP_UNINSTALLED` or any handled topic), captured from their own store.
3. Attacker POSTs the same `B` and the same HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop known to have the app installed).
4. `validateHmacFromRequestFactory` only checks `HMAC-SHA256(S, B)` against the header — this still matches because `S` and `B` are unchanged, so `check.valid === true` and `check.domain === 'victim.myshopify.com'`.
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim.myshopify.com')`, loading the victim's real offline access token, and executes the app's webhook business logic (e.g., data deletion for `APP_UNINSTALLED`, or handler side effects) against the victim's shop, entirely under attacker control of the payload/topic content.     missingHeaders,

      reason: WebhookValidationErrorReason.MissingHeaders,

    domain: domain!,
