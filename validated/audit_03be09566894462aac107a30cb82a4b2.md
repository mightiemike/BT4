### Title
Function-call access-key allowance is never checked or decremented when the key is used to sign a meta-transaction, letting a restricted key spend beyond its allowance - ([File: runtime/runtime/src/actions.rs])

### Summary
`validate_delegate_action_key` in `runtime/runtime/src/actions.rs` validates a `FunctionCallPermission` key used to sign a `DelegateAction` against `receiver_id`, `method_names`, action count, and deposit, but it never checks or decrements `FunctionCallPermission.allowance`. This mirrors the Metrom bug class: a resource limit that is supposed to be tied to a specific signer/key ("resolved fee"/allowance) can be sidestepped by routing the action through an alternate execution path (a relayer/meta-transaction) that never re-applies the restriction, instead of the restriction being enforced uniformly regardless of the path taken.

### Finding Description
`FunctionCallPermission.allowance` (`core/primitives-core/src/account.rs`) is meant to cap how much of an account's balance a restricted access key can authorize for gas/deposit spend, exactly analogous to Metrom's per-address "resolved fee" that is supposed to bind to the entity that created/owns the campaign.

For ordinary (non-meta) transactions, `verify_and_charge_tx_ephemeral` in `runtime/runtime/src/verifier.rs` checks and decrements the allowance before letting a `FunctionCall` action through.

For meta-transactions (NEP-366 `DelegateAction`), the equivalent check happens in `validate_delegate_action_key` (`runtime/runtime/src/actions.rs:579-728`). This function checks:
- action count / `RequiresFullAccess` (`:672-679`)
- deposit-with-function-call (`:680-694`)
- `receiver_id` match (`:695-704`)
- `method_names` match (`:705-718`)

but at no point reads or mutates `access_key.permission...allowance`. The `access_key` returned from `get_access_key` at `:588` is later only used for its nonce, not its allowance. [1](#0-0) 

This gap is explicitly acknowledged in project documentation: [2](#0-1) 
> "For allowance, however, there is no check. All costs have been covered by the relayer. Hence, even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work... if someone were to limit a function access key to one trivial action by setting a very small allowance, that is circumventable by going through a relayer."

The delegate-action path deliberately bills all costs to the relayer, not the restricted key's allowance (`apply_delegate_action`, `runtime/runtime/src/actions.rs:453-534`), and the relayer itself pays with its own full balance rather than being constrained by the sender's allowance: [3](#0-2) 

### Impact Explanation
An account owner (or anyone who compromises/receives a restricted `FunctionCallPermission` key with a deliberately small allowance) can use *any* relayer to invoke the exact contract/method the key is scoped to, at unlimited gas/repeat frequency, completely bypassing the allowance cap that the key owner (or whoever issued the key, e.g. as a limited-trust delegation to a third party or dApp) relied on as a hard financial boundary. This is a concrete "fee/limit bypass" — the very security property the allowance field exists to provide (bounding how much value a specific restricted key can authorize) is defeated whenever the action is wrapped in a `DelegateAction`, without any special privilege beyond being able to submit a signed meta-transaction (something any RPC caller can construct and any relayer will happily forward). Any application relying on `FunctionCallPermission.allowance` as an enforced spending limit for a semi-trusted key is silently unprotected against a holder who also has access to (or colludes with) a relayer.

### Likelihood Explanation
High. No validator, network, or state privilege is required — only a signed `DelegateAction` submitted through a relayer, i.e., something reachable by an ordinary transaction signer/RPC caller. The bypass is deterministic and works on every call; the project's own documentation already flags it as a known consequence of the meta-transaction design, so it triggers reliably rather than depending on edge-case timing or race conditions.

### Recommendation
- Track and enforce the `FunctionCallPermission.allowance` for the *delegate-action path* the same way it is enforced for ordinary transactions: charge the decremented amount against the sender's access-key allowance (not just against the relayer's balance) inside `validate_delegate_action_key` / `apply_delegate_action`, and fail the delegate action with an appropriate error (e.g. `NotEnoughAllowance`) if the allowance would be exceeded.
- If allowance enforcement for delegated calls is considered out of scope by design, this limitation must be made an explicit, hard security warning surfaced at the `AccessKeyPermission::FunctionCall` API/RPC level (not just buried in architecture docs), since dApps and wallets currently have no on-chain guarantee that an allowance-limited key cannot be drained via a relayer.

### Proof of Concept
1. Account `alice.near` adds a `FunctionCall` access key with `allowance = 0.01 NEAR`, `receiver_id = "token.near"`, `method_names = ["transfer"]`, intending this key to only ever authorize ~0.01 NEAR worth of gas for `transfer` calls (e.g., handed to a semi-trusted bot).
2. Using that same restricted key, sign a `DelegateAction` with `sender_id = alice.near`, `receiver_id = "token.near"`, `actions = [FunctionCall("transfer", ...)]`.
3. Any relayer (including `alice.near` herself using a second, unrelated full-access account, or any public relayer service) wraps this in a `SignedTransaction` and submits it.
4. `validate_delegate_action_key` (`runtime/runtime/src/actions.rs:579-728`) validates receiver/method/deposit/nonce and succeeds — it never inspects `allowance`. `apply_delegate_action` bills all gas/deposit to the relayer.
5. Repeat step 2-4 arbitrarily many times (each with a fresh nonce) — the restricted key authorizes unlimited `transfer` calls on `token.near`, far exceeding the `0.01 NEAR` allowance that was supposed to bound its usage, as long as a relayer is willing to pay gas each time.

## Function access keys in meta transactions

Assume alice sends a meta transaction and signs with a function access key.
How exactly are permissions applied in this case?

Function access keys can limit the allowance, the receiving contract, and the
contract methods. The allowance limitation acts slightly strange with meta
transactions.

But first, both the methods and the receiver will be checked as expected. That
is, when the delegate action is unwrapped on Alice's shard, the access key is
loaded from the DB and compared to the function call. If the receiver or method
is not allowed, the function call action fails.

For allowance, however, there is no check. All costs have been covered by the
relayer. Hence, even if the allowance of the key is insufficient to make the call
directly, indirectly through meta transaction it will still work.

This behavior is in the spirit of allowance limiting how much financial
resources the user can use from a given account. But if someone were to limit a
function access key to one trivial action by setting a very small allowance,
that is circumventable by going through a relayer. An interesting twist that
comes with the addition of meta transactions.
