### Title
Program-cache cold-load metering gap allows CU-cost-mismatched block-processing latency amplification - (File: svm/src/transaction_processor.rs)

### Summary
`CostTracker::try_add`'s `programs_execution_cost` is derived solely from the transaction's declared `compute_unit_limit`, while `TransactionBatchProcessor::replenish_program_cache` performs synchronous ELF loading, `RequisiteVerifier` bytecode verification, and JIT compilation for every not-yet-cached program with zero contribution to that metered cost. An attacker can therefore submit many transactions, each invoking a distinct freshly-deployed near-max-size BPF program with a minimal `set_compute_unit_limit`, causing the leader/replay validator to perform many full ELF load/verify/JIT cycles whose real wall-clock cost is decoupled from the `MAX_BLOCK_UNITS`-bounded accounting.

### Finding Description
`CostModel::get_estimated_execution_cost` (`cost-model/src/cost_model.rs:159-178`) sets `programs_execution_cost = compute_unit_limit` taken directly from the transaction's `ComputeBudgetInstruction::set_compute_unit_limit`, with no term reflecting program bytecode size or whether the program is already resident in the global `ProgramCache`. `CostTracker::try_add` (`cost-model/src/cost_tracker.rs:204-271`) then only checks this declared sum against `MAX_BLOCK_UNITS` (60,000,000) and per-account limits — it has no visibility into, or accounting for, program-loading work.

On the execution side, `TransactionBatchProcessor::replenish_program_cache` (`svm/src/transaction_processor.rs:925-1002`) is invoked once per transaction for any `missing_programs` not already present in `program_cache_for_tx_batch`/`global_program_cache`. For each miss it calls `load_program_with_pubkey`, which ultimately calls `ProgramCacheEntry::load` (`program-runtime/src/program_cache_entry.rs:195-241`): this does `Executable::load(elf_bytes, ...)`, `executable.verify::<RequisiteVerifier>()`, and `executable.jit_compile()` — all CPU-bound operations whose cost scales with program size, entirely inside the hot execution path and entirely untracked by the cost model.

Because each transaction in the attack targets a *distinct* program pubkey, the global program cache provides no cross-transaction amortization: every transaction is a genuine cache miss requiring a fresh load/verify/JIT cycle. `limit_to_load_programs`/`hit_max_limit` only guards against cache *insertion races* (an entry being evicted mid-batch), not against the sheer volume of loading work, so it does not bound this attack. Consequently, an attacker paying only ~200 CU per instruction (well under `MAX_BLOCK_UNITS`) can force the validator to spend disproportionate wall-clock time in `replenish_program_cache`, decoupling actual leader/replay processing time from the cost-tracker's block-cost accounting — a violation of the metering invariant that `block_cost` should be a reasonable proxy for processing time.

### Impact Explanation
This is a liveness-degradation vector rather than a fund-theft or consensus-divergence bug: leader block production and replay of the resulting block both pay the same synchronous load/verify/JIT cost, so it does not by itself cause safety divergence between validators (the entries are deterministic). The primary Solana bounty-relevant category is validator/cluster liveness degradation — leader slot processing latency and replay latency can be inflated far beyond what `block_cost` (bounded by `MAX_BLOCK_UNITS`) implies, potentially causing skipped slots or replay lag under sustained attack.

### Likelihood Explanation
Preconditions are attacker-affordable but non-trivial: the attacker must first deploy many distinct, large (near max ~10MB) BPF programs on-chain, which itself costs substantial rent-exemption lamports and many prior write transactions (each subject to normal cost-tracker/data-size limits), making the attack costly but not infeasible for a well-funded attacker, and fully repeatable every block/epoch since program cache eviction (`evict_using_random_selection`) does not retain a "trusted" cross-block warm set for adversarial pubkeys. This is a known, general characteristic of Solana's compute-unit-based cost model (compute cost is estimated from declared CU limit, not from loader/verifier/JIT work), rather than a newly introduced regression in this specific commit history, but it remains reachable via ordinary transaction submission with no special privileges.

### Recommendation
Incorporate a metered cost component for program cache misses (e.g., proportional to ELF/account size) into `CostModel`/`CostTracker`, or impose an explicit per-block/per-batch cap on the number of distinct newly-loaded (previously uncached) programs independent of declared CU limits, so that the wall-clock cost of `replenish_program_cache` is bounded by the same block-level guarantees as `MAX_BLOCK_UNITS`.

### Proof of Concept
Integration test plan (in `svm/tests` or a `runtime/src/bank` test):
1. Deploy `N` (e.g., 200) distinct BPF programs near the max program size via LoaderV3, each with unique bytecode padding to avoid dedup/caching effects.
2. Build a block/batch of `N` transactions, each invoking one distinct program with `ComputeBudgetInstruction::set_compute_unit_limit(200)` and minimal other instructions.
3. Run `load_and_execute_sanitized_transactions` (or `Bank::load_execute_and_commit_transactions`) with a fresh `global_program_cache` (simulating cold start / no reuse across blocks) and measure:
   - `cost_tracker.block_cost()` after processing (assert it is small, e.g., `< 200 * ~1500` CU, far under `MAX_BLOCK_UNITS`).
   - Wall-clock time spent inside `replenish_program_cache` (via `ExecuteTimingType::ProgramCacheUs` in `execute_timings`), asserting it dominates total processing time and scales roughly linearly with `N * program_size`, disproportionate to the reported `block_cost`.

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn replenish_program_cache<CB: TransactionProcessingCallback>(
        &self,
        account_loader: &AccountLoader<CB>,
        mut missing_programs: Vec<ProgramToLoad>,
        program_runtime_environment_for_execution: &ProgramRuntimeEnvironment,
        program_cache_for_tx_batch: &mut ProgramCacheForTxBatch,
        execute_timings: &mut ExecuteTimings,
        limit_to_load_programs: bool,
        increment_usage_counter: bool,
    ) {
        if missing_programs.is_empty() {
            // Nothing to load, so skip the global cache and fork graph locks.
            // Program-cache hit/miss counters are unchanged for empty work.
            return;
        }
        let mut count_hits_and_misses = true;
        loop {
            // Lock the global cache.
            let global_program_cache = self.global_program_cache.read().unwrap();
            // Figure out which program needs to be loaded next.
            let program_to_load = global_program_cache.extract(
                &mut missing_programs,
                program_cache_for_tx_batch,
                program_runtime_environment_for_execution,
                increment_usage_counter,
                count_hits_and_misses,
            );
            count_hits_and_misses = false;
            let task_waiter = Arc::clone(&global_program_cache.loading_task_waiter);
            let task_cookie = task_waiter.cookie();
            // Unlock the global cache again.
            drop(global_program_cache);

            let program_to_store = program_to_load.map(|key| {
                // Load, verify and compile one program.
                let (program, last_modification_slot) = load_program_with_pubkey(
                    account_loader,
                    program_runtime_environment_for_execution,
                    &key,
                    self.slot,
                    execute_timings,
                )
                .expect("called load_program_with_pubkey() with nonexistent account");
                (key, program, last_modification_slot)
            });

            if let Some((key, program, last_modification_slot)) = program_to_store {
                program_cache_for_tx_batch.loaded_missing = true;
                let mut global_program_cache = self.global_program_cache.write().unwrap();
                // Submit our last completed loading task.
                if global_program_cache.finish_cooperative_loading_task(
                    program_runtime_environment_for_execution,
                    self.slot,
                    key,
                    last_modification_slot,
                    program,
                ) && limit_to_load_programs
                {
                    // This branch is taken when there is an error in assigning a program to a
                    // cache slot. It is not possible to mock this error for SVM unit
                    // tests purposes.
                    *program_cache_for_tx_batch = ProgramCacheForTxBatch::new(self.slot);
                    program_cache_for_tx_batch.hit_max_limit = true;
                    return;
                }
            } else if missing_programs.is_empty() {
                break;
            } else {
                // Remember: there are multiple transaction processor threads running concurrently
                // and those other threads may be loading this or other programs.
                //
                // So, sleep until some other thread submits a program with their
                // `finish_cooperative_loading_task` call. We'll then wake up and try to load the
                // missing programs inside the tx batch again.
                let _new_cookie = task_waiter.wait(task_cookie);
            }
        }
