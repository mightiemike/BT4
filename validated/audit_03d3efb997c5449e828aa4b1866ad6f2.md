### Title
Denial-of-Service via unbounded, linearly-scanned `toAccounts`/`fromAccounts` list in `DelegatedResourceAccountIndexCapsule` (legacy resource-delegation path) - (File: `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
The Predy finding describes an unbounded array that is linearly scanned to find/remove an element, allowing an attacker to grow the array so large that removal (needed for liquidation) becomes prohibitively expensive or reverts. The java-tron analog is the legacy (pre-"delegate optimization") resource-delegation bookkeeping structure `DelegatedResourceAccountIndexCapsule`, whose `toAccounts`/`fromAccounts` lists are grown with `contains()`/`add` checks and shrunk with `List.remove(Object)` — both O(n) operations — driven entirely by attacker-chosen, unprivileged `FreezeBalanceContract`/`DelegateResourceContract`/`UnfreezeBalanceContract` transactions.

### Finding Description
When an account delegates bandwidth/energy to a new receiver via the legacy path (`dynamicStore.supportAllowDelegateOptimization()==false`), `FreezeBalanceActuator.delegateResource` and `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor` maintain per-account index lists: [1](#0-0) 

Adding an entry checks membership with `List.contains()` before calling `addToAccount`/`addFromAccount`: [2](#0-1) 

Removal (triggered from `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor` when a delegation's balance is fully unfrozen) copies the whole list, does `List.remove(Object)`, and rewrites the entire list into the capsule: [3](#0-2) 

Because an unprivileged account can freely delegate small amounts of bandwidth/energy to any number of distinct receiver addresses (each delegation to a not-yet-seen receiver appends one more unique entry to `toAccounts`), the `toAccounts`/`fromAccounts` lists can be grown arbitrarily large by the account owner. Every subsequent freeze/delegate operation from that account performs an O(n) `contains()` scan, and every unfreeze/undelegate operation performs an O(n) `contains()`+`remove()`+full list rebuild, mirroring the `ArrayLib.getItemIndex`/`removeItem` pattern in the referenced report.

### Impact Explanation
Unlike EVM gas metering, TVM/native-contract fees for `FreezeBalanceContract`/`DelegateResourceContract`/`UnfreezeBalanceContract` are charged based on transaction bandwidth size, not on the actual CPU work performed by the actuator during block processing. This creates an asymmetry: the cost paid by the attacker is fixed and small, while the CPU cost imposed on every full node validating/re-executing the block (and later re-processing further ops from that account) grows linearly with the size of the attacker-controlled list. Because this logic runs synchronously during block application, a sufficiently bloated per-account index can slow block processing for all nodes handling transactions from (or referencing) that account, degrading throughput — a resource-accounting/consensus-processing DoS vector rather than a simple wasted-gas issue as in the original Solidity report.

### Likelihood Explanation
This path only applies while the `AllowDelegateOptimization` chain parameter is disabled (`!dynamicStore.supportAllowDelegateOptimization()`); once enabled, delegation bookkeeping switches to prefix-keyed DB entries (`delegatedResourceAccountIndexStore.delegate/unDelegate`) which are O(1) and immune to this issue, as seen in the optimized branch of the same actuator. Likelihood is therefore tied to whether/how long this legacy code path remained reachable on production chains before the optimization proposal was activated, and any chain instance (e.g., a private/sidechain deployment or a network that hasn't yet enabled the proposal) still running with the flag off remains exposed. The attack requires only ordinary account permissions and a modest amount of TRX to freeze/delegate in small increments to many distinct addresses.

### Recommendation
- Ensure the `AllowDelegateOptimization` (prefix-keyed, O(1)) code path is the only path shipped/enabled for new deployments, and remove or gate the legacy list-based `DelegatedResourceAccountIndexCapsule.addToAccount/addFromAccount/removeToAccount/removeFromAccount` logic behind mandatory migration.
- If the legacy path must remain for backward compatibility, cap the number of unique `toAccounts`/`fromAccounts` entries a single account can accumulate, or replace the `List<ByteString>` scan/remove with a set-like or key-prefixed structure (similar to the optimized path) to avoid O(n) operations entirely.
- Add fee/energy accounting proportional to the size of these per-account index lists so the cost of growing/searching them is borne by the transaction sender.

### Proof of Concept
1. On a chain with `AllowDelegateOptimization` disabled, an attacker account repeatedly submits `FreezeBalanceContract` (delegated form) transactions, each freezing a minimal amount of TRX and delegating to a fresh, never-before-used receiver address.
2. Each transaction appends one entry to the attacker's `DelegatedResourceAccountIndexCapsule.toAccounts` list via `FreezeBalanceActuator.delegateResource` → `addToAccount`, since the receiver is not yet in `toAccountsList`.
3. After accumulating a very large `toAccounts`/`fromAccounts` list (bounded only by the attacker's willingness to pay ordinary bandwidth fees per tx, not by any list-size limit), subsequent freeze/delegate calls from or to this account incur `contains()` scans over the full list, and any unfreeze/undelegate operation incurs `contains()+remove()+rebuild` over the full list in `DelegatedResourceAccountIndexCapsule.removeToAccount/removeFromAccount`, called from `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor`.
4. Nodes re-executing these transactions during block validation pay disproportionate CPU cost relative to the bandwidth fee charged, demonstrating the DoS/resource-accounting imbalance.

  public void addFromAccount(ByteString fromAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addFromAccounts(fromAccount)
        .build();
  }

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }

  public void addToAccount(ByteString toAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addToAccounts(toAccount)
        .build();
  }

  public void removeToAccount(ByteString toAccount) {
    if (getToAccountsList().contains(toAccount)) {
      List<ByteString> toList = new ArrayList<>(getToAccountsList());
      toList.remove(toAccount);
      setAllToAccounts(toList);
    }
  }
