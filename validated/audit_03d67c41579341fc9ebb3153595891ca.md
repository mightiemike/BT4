### Title
Unbounded recursive depth in native Rust CASM bytecode-hash computation allows stack-exhaustion DoS on class declaration - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
The CVE-2018-18484 bug class (unbounded, attacker-influenced recursion in a native, non-tail-recursive function leading to stack exhaustion) has a plausible structural analog in the compiled-class-hash computation used by the sequencer's Sierra→CASM class declaration flow. `bytecode_hash_node` in [1](#0-0)  recurses once per nesting level of the `NestedIntList`/`HashableNestedIntList` bytecode-segment tree, with no explicit recursion-depth bound in this function itself, and is invoked from the class-declaration/compilation path reachable by any contract declarer.

### Finding Description
When a class is declared, `SierraCompiler::compile` compiles the Sierra program to CASM and then computes the executable class hash via `executable_class.hash(&HashVersion::V2)` in [2](#0-1) . That hash routine descends into `bytecode_hash` → `bytecode_hash_node`, a function that recurses into every child of a `NestedIntList` node: [1](#0-0) 

The `NestedIntList` bytecode-segmentation tree (`node.iter_children()`) is derived from the *compiled* CASM's function/branch segment structure, which is itself a function of the shape of the declared Sierra program's control flow (nested branches/functions produce nested segments), as also seen in the parallel Rust structure-builder `NestedFeltCounts::new_inner` in [3](#0-2)  (note this sibling function does assert `segmentation_depth <= 1`, but that assertion is local to that struct and does not bound `bytecode_hash_node` in `starknet_api`, which has no such guard).

Only the overall CASM bytecode size is capped, via `max_bytecode_size` (default `80 * 1024` felts, see [4](#0-3) ). The bound is on total felt count, not on segment-tree nesting depth. If the underlying Sierra-to-CASM compiler's segmentation algorithm can produce a deeply and irregularly nested segment tree for a program crafted with heavily nested branch/function structure (many levels of nested control flow, each contributing a small number of felts), the resulting `NestedIntList` could have a nesting depth on the order of thousands, well beyond the ~2-level (function → branch) depth the code elsewhere assumes.

Because `bytecode_hash_node` is genuine native Rust recursion (not Cairo VM execution, which uses a heap-backed memory segment rather than the host call stack — as explicitly called out in the Cairo-native stack-overflow test comment, [5](#0-4) ), sufficiently deep nesting can exhaust the sequencer process's host thread stack and crash the process (SIGSEGV / abort), unlike Cairo-level recursion which is bounded by gas/step accounting.

### Impact Explanation
If reachable, a crafted DECLARE transaction (or an L1-sourced deployment path that includes class declaration) could crash the class-manager / gateway / sequencer process computing the compiled class hash, since this hash is computed synchronously as part of normal class declaration handling in [6](#0-5) . A crash of this component during declare processing could disrupt block building / transaction admission — a network-availability impact (temporary inability to confirm new transactions if this recurs across nodes deterministically).

### Likelihood Explanation
Low-to-uncertain. I could not confirm from the code in this repository whether the actual Sierra→CASM compiler segmentation algorithm (external, in `cairo-lang-starknet-classes`, invoked via a subprocess in [7](#0-6) ) can actually produce segment trees with depth much greater than the two levels (function, branch) implicitly assumed elsewhere in this codebase (e.g., the `segmentation_depth <= 1` assertion in blockifier's `NestedFeltCounts::new_inner`). If the compiler bounds segmentation to ~2 levels in practice, `bytecode_hash_node`'s recursion depth is trivial and this analog does not hold. Additionally, `compile_with_args` runs the Sierra compiler itself under CPU/memory resource limits (`ResourceLimits`), but the *hash computation* (`executable_class.hash(...)`) happens in-process, after that subprocess returns, and is not resource-limited the same way.

### Recommendation
- Verify the maximum possible nesting depth the external Sierra-to-CASM compiler can emit for `bytecode_segment_lengths` given `max_bytecode_size`, for both audited and non-audited libfunc sets.
- If depth is not tightly bounded, convert `bytecode_hash_node` (and its Cairo `bytecode_hash_internal_node` counterpart used during OS re-execution/proving, which is fine since it's step-metered) to an iterative, explicit-stack algorithm, or impose an explicit maximum segment-tree depth check before hashing, rejecting classes that exceed it.
- Add a fuzz/regression test compiling a Sierra program with deeply nested control flow to confirm actual recursion depth and stack safety margins.

### Proof of Concept
Not constructed — I was unable to verify, from the code available in this repository, the maximum nesting depth actually produced by the external Sierra-to-CASM compiler for pathological deeply-nested-branch Sierra programs, which is required to determine whether a stack-exhaustion depth is reachable within the `max_bytecode_size` limit. This is the key unresolved uncertainty; without confirming that the compiler's segmentation tree depth is unbounded (or bounded to something large enough to exhaust a typical thread stack), this finding should be treated as a plausible-but-unconfirmed analog rather than a proven vulnerability.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

impl NestedFeltCounts {
    /// Builds a nested structure matching `layout`, consuming values from `bytecode`.
    #[allow(unused)]
    pub fn new(bytecode_segment_lengths: &NestedIntList, bytecode: &[BigUintAsHex]) -> Self {
        let (base_node, consumed_felts) = Self::new_inner(bytecode_segment_lengths, bytecode, 0);
        assert_eq!(consumed_felts, bytecode.len());
        base_node
    }

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }
}
