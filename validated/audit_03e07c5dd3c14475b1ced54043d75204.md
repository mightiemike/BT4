### Title
Transaction-fee reward funds are permanently unclaimable when `voteCount` is 0 at cycle-boundary Vi accumulation - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
java-tron's new-reward-algorithm distributes per-cycle witness rewards to voters through a `Vi` (value-per-vote) accumulator, computed incrementally each maintenance cycle. `DelegationStore.accumulateWitnessVi` (and the equivalent `RewardViCalService.accumulateWitnessVi`) explicitly skips the `Vi` update whenever `voteCount == 0` for that witness/cycle, only forwarding the previous `Vi` unchanged. This is analogous to the reported `EscrowedToken` bug, where `ratePerToken` is not incremented when `totalVesting == 0`: in both cases the guard against a division/no-recipient scenario causes the "leftover" reward amount to be silently dropped from the distribution accounting, with no mechanism to recover or redistribute it.

### Finding Description
The reward is deducted from the real `transactionFeePool` in `Manager.payReward`: [1](#0-0) 
and credited into `delegationStore` per witness/cycle via `MortgageService.payReward` → `delegationStore.addReward(cycle, witnessAddress, value)`: [2](#0-1) 

At the end of each maintenance cycle, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount())` for every witness, using the witness's vote count *at that moment* (before the cycle's vote-count deltas from `countVote()` are applied to the witness objects): [3](#0-2) 

Inside `accumulateWitnessVi`, if the witness's reward for that cycle is non-zero but its `voteCount` is `0`, the delta-Vi computation (`reward * DECIMAL / voteCount`, which would otherwise divide by zero) is skipped entirely and only the previous `Vi` is forwarded: [4](#0-3) 

The identical guard/skip pattern exists in `RewardViCalService.accumulateWitnessVi`: [5](#0-4) 

Because `Vi` is the sole mechanism by which `MortgageService.computeReward` (and `VoteRewardUtil.computeReward`) compute `deltaVi` to pay out staker rewards: [6](#0-5) 
any reward recorded for a witness in a cycle where its `voteCount` is `0` never gets reflected in `Vi`, and therefore is never paid to any voter through `withdrawReward`/`queryReward`. There is no `unclaimableFunds`-style tracking variable and no recovery function — the TRX that was already subtracted from `transactionFeePool` (a real, shared accounting pool, not merely inflationary emission) is permanently lost from the distributable reward accounting, exactly mirroring the `removedAmount` being stranded in `EscrowedToken` when `totalVesting == 0`.

A witness can have `voteCount == 0` at the point `accumulateWitnessVi` runs for a given cycle while still having accrued block/transaction-fee reward in that same cycle — e.g., a witness produces blocks (and thus earns transaction-fee reward via `payTransactionFeeReward`) earlier in the cycle, but is fully unvoted by the time `doMaintenance()` executes at cycle end (the vote-count update in the same maintenance pass happens after the Vi accumulation, at lines 111-127 vs 96-101).

### Impact Explanation
Real TRX removed from the shared `transactionFeePool` (funded by transaction fees from *all* users, i.e., protocol-wide funds, not a witness-specific balance) is credited into per-witness/per-cycle reward records but becomes permanently unreachable by any staker once `Vi` fails to account for it. This is a concrete, non-recoverable state/accounting divergence: total value removed from the transaction fee pool no longer equals the total value claimable through `withdrawReward`, and no admin/recovery function exists to reclaim or redistribute it. This matches the "stuck forever" accounting-loss impact class from the source report, occurring in a widely-used chain accounting mechanism (delegated-vote reward distribution) rather than a peripheral flow.

### Likelihood Explanation
This requires a witness to lose all votes within the span of a single maintenance cycle after having earned block/tx-fee reward in that cycle — a naturally occurring scenario under normal user behavior (unvoting), not a privileged or contrived edge case, and it can recur every cycle for any witness whose voters withdraw support. No special permissions or attacker collusion are needed; it is triggered by ordinary voter actions plus normal witness reward accrual, making it moderately likely to occur over time on a live network.

### Recommendation
Track reward amounts that are skipped due to `voteCount == 0` (or `reward` present with no eligible voters) in a dedicated accumulator (e.g., an "orphaned reward" pool per cycle/witness or a global unclaimable-rewards counter), and either roll them forward into the next cycle's distributable reward for that witness's future voters, or provide an explicit, auditable mechanism to return them to the `transactionFeePool` / total reward pool rather than silently dropping the accounting record in `DelegationStore.accumulateWitnessVi` and `RewardViCalService.accumulateWitnessVi`.

### Proof of Concept
Conceptual sequence (cannot be executed here, but derivable directly from the cited code):
1. Witness `W` has `voteCount > 0` and produces a block in cycle `C`, causing `MortgageService.payTransactionFeeReward` to call `payReward`, which subtracts `transactionFeeReward` from `dynamicPropertiesStore`'s `transactionFeePool` and calls `delegationStore.addReward(C, W, value)`.
2. Before `MaintenanceManager.doMaintenance()` runs for cycle `C`'s boundary, all voters of `W` withdraw their votes (via `VoteWitnessProcessor`/`UnfreezeBalanceV2Processor` clearing votes), so `witness.getVoteCount()` becomes `0` by the time `accumulateWitnessVi` is invoked (line 99 in `MaintenanceManager.java`, before `countVote()`'s reassignment at lines 111-127).
3. `DelegationStore.accumulateWitnessVi(C, W, 0)` sees `voteCount == 0`, skips the `deltaVi` computation, and simply forwards `preVi` unchanged.
4. The reward recorded via `addReward(C, W, value)` in step 1 is now permanently orphaned: no future `computeReward` call over any voter's vote history will ever include this cycle's contribution, since `Vi` was never incremented for it — yet the equivalent TRX was already deducted from the real `transactionFeePool`.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
