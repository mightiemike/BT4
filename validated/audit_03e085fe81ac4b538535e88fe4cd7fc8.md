Based on my investigation, I found a genuine analog of the "domain separator not scoped to instance" bug class in the StackerDB signing scheme, confirmed by explicit code evidence: the chunk-authentication digest `SlotMetadata::auth_digest()` at `libstackerdb/src/libstackerdb.rs:159-166` binds only to `(slot_id, slot_version, data_hash)` — it never includes the `smart_contract_id` (the `QualifiedContractIdentifier`) that names *which* StackerDB replica the chunk belongs to. This is architecturally the same defect as the MechMarketplace bug: a signature is computed without a domain separator that distinguishes between multiple independent "instances" (there, multiple proxies of one implementation; here, multiple StackerDB replicas — e.g., `.signers-N-M` contracts across reward cycles, or `.miners`/`.signers` sibling contracts) that share the same signer key.

### Title
StackerDB chunk signatures omit the contract identifier, enabling cross-StackerDB chunk replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest` (and thus `StackerDBChunkData::sign`/`verify`) commits only to `slot_id`, `slot_version`, and `data_hash`. It does not incorporate the target StackerDB's `smart_contract_id`. Because the same signer private key is reused for slot assignments across multiple distinct StackerDB replicas (e.g., successive reward-cycle `.signers-N-M` contracts, whose slot layouts can coincidentally reuse the same `slot_id`), a chunk validly signed for replica A can be replayed as a validly-signed chunk for replica B, since `try_replace_chunk`/`validate_received_chunk` verify the signature against the signer address for the *target* contract without the contract identity ever being part of what was signed.

### Finding Description
`SlotMetadata::auth_digest()`:
```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
``` [1](#0-0) 

This digest is used both to sign (`StackerDBChunkData::sign`) and to verify (`SlotMetadata::verify`) a chunk. [2](#0-1) 

When a chunk is written, `StackerDBTx::try_replace_chunk` looks up the expected signer for the given `smart_contract` + `slot_id` pair and calls `slot_desc.verify(&slot_validation.signer)`, but the `smart_contract` identifier itself is never mixed into the signed bytes — it's only used as a lookup key to fetch which address *should* have signed:
```
let slot_validation = self.get_slot_validation(smart_contract, slot_desc.slot_id)?...
if !slot_desc.verify(&slot_validation.signer)? { ... }
``` [3](#0-2) 

Because signer keys are the same Stacks signing key across reward cycles (and StackerDB slot assignment is deterministic by address ordering), the same signer can be assigned the identical `slot_id` in two different StackerDB replicas that are simultaneously live (e.g. the miner/`.signers` StackerDB for the current and upcoming reward cycle, both configured while transitioning). This is exactly the "same code, different deployment/instance, same domain-less signature" bug class described in the external report: the missing per-instance separator (there, `domainSeparator`; here, `smart_contract_id`) is what should make the signed payload unique per StackerDB instance, but isn't.

### Impact Explanation
This does not directly forge a block or steal a reward, but it is a minority-triggerable signature-verification divergence in the peer-to-peer StackerDB replication layer, which underlies signer block-proposal/response gossip. A signer (or anyone who has captured one signed chunk from replica A) can push a byte-identical `(slot_id, slot_version, data_hash)` payload with a different data blob under a different `smart_contract_id`, and `validate_received_chunk`/`try_replace_chunk` will accept it as authentically signed by that address for the *new* target DB, since the verification only checks the signature against the digest, not against which contract the chunk was written to. This can cause different nodes to accept/reject a StackerDB chunk (and thus a block-proposal/response artifact used by signers) inconsistently depending on which StackerDB instances they have configured, producing a temporary signer-view/tip disagreement — matching the "temporary tip disagreement" / signature-divergence class called out as High in the impact criteria.

### Likelihood Explanation
Requires: (1) a signer whose key is (re)used with the same `slot_id` across at least two live StackerDB contract instances (a normal, expected condition around reward-cycle rollover when the current-cycle and next-cycle `.signers-*` StackerDB configs coexist), and (2) an unprivileged party relaying a previously-observed chunk to the "wrong" contract endpoint. No majority collusion or admin access is needed — this is triggerable by any single node/relay with knowledge of one valid chunk, which satisfies "minority-triggerable."

### Recommendation
Include the target `smart_contract_id` (or at least a stable per-StackerDB domain tag, e.g., its `QualifiedContractIdentifier` bytes) inside `SlotMetadata::auth_digest()` so that signatures are cryptographically bound to the specific StackerDB instance they were produced for, mirroring the fix recommended for MechMarketplace (bind the separator to the specific deployed instance, not just to fields common across all instances).

### Proof of Concept
1. Configure two StackerDB replicas, `contract_A` and `contract_B`, both assigning `slot_id = 0` to the same signer address/key (this occurs naturally across successive reward-cycle `.signers-N-M` contracts).
2. Signer produces `chunk_A = StackerDBChunkData { slot_id: 0, slot_version: 1, data: X }` and signs it (`chunk_A.sign(&signer_sk)`), submitting it to `contract_A`.
3. An observer copies `chunk_A`'s `(slot_id, slot_version, sig, data)` verbatim and submits it as a push/put to `contract_B` for slot 0.
4. `validate_received_chunk`/`try_replace_chunk` for `contract_B` calls `slot_metadata.verify(&addr_for_contract_B)`, which recomputes `auth_digest()` from `(slot_id, slot_version, data_hash)` only — identical to what was signed for `contract_A` — so verification succeeds even though the signer never authorized this chunk for `contract_B`.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
