## Analysis

The report describes a TOCTOU/ownership race in file creation for sensitive data: writing secret data to a path before permissions/ownership are secured allows a local unprivileged attacker to either read the secret in the write window, or (more importantly) pre-plant a file they own at that path so the victim process writes secrets *into a file the attacker still owns*.

The chainlink node has an exact analog in its session-secret persistence path.

### Root cause

`core/services/chainlink/secret_generator.go` generates the node's session-signing secret and persists it to `<rootDir>/secret` using `utils.WriteFileWithMaxPerms`: [1](#0-0) 

`WriteFileWithMaxPerms` opens the path with `O_CREATE` but **without `O_EXCL`**, so if the path already exists (e.g., pre-created by an attacker on a shared host) it is opened rather than rejected. It then narrows permissions by ANDing the *existing* mode with the desired mask, and only afterward writes the secret bytes: [2](#0-1) 

Critically, `os.Chmod`/`file.Chmod` never changes file **ownership**. If an attacker pre-creates `rootDir/secret` (owned by the attacker, with permissions permissive enough for the chainlink process to write, e.g. group/world-writable) before the node starts, chainlink will:
1. Open the attacker-owned file,
2. Chmod it down to `0600`,
3. Write the session-signing secret into it — while the attacker remains the file **owner**.

As file owner, the attacker retains the POSIX privilege to `chmod`/`chown` the file again at any later time regardless of its current mode bits, and can trivially read the secret back out, defeating the permission restriction entirely — this is precisely "Exploit Scenario 2" from the report.

The node does have an ownership check, `utils.IsFileOwnedByChainlink`, but it is invoked far too late and is non-blocking: [3](#0-2) [4](#0-3) 

`checkFilePermissions` explicitly lists `"secret"` (the session-signing key file) among `protectedFiles`, checks perms/ownership, and if not owned by chainlink **only logs a warning** — the comment even states "This will be made mandatory in the future," acknowledging the gap. This check also runs only after the application (and its secret generation) has already started, i.e., after the secret has already been written into whatever file existed at that path: [5](#0-4) 

### Impact
The session secret signs/encrypts the node's admin API session cookies (`securecookie`). If an attacker on the same host can win this race (pre-create `rootDir/secret` before first node start, or predict/target it in shared/multi-tenant deployment setups), they can recover the secret and forge valid session cookies, achieving authentication bypass against the node's admin HTTP API — a direct node-compromise / secret-disclosure impact, not merely theoretical.

### Likelihood
This requires local filesystem access to the node's `rootDir` prior to first startup (or ability to race file creation) — an unprivileged-local-user threat model, same precondition class as the original EthStaker report. It is a real, code-supported bug (missing `O_EXCL`, no ownership verification before writing secrets, non-blocking ownership warning after the fact) rather than a hypothetical.

### Title
Session secret file is created/written without ownership verification, allowing owner-retained secret disclosure - (File: core/services/chainlink/secret_generator.go)

### Summary
The node's session-signing secret is persisted via `WriteFileWithMaxPerms`, which opens the target path with `O_CREATE` (no `O_EXCL`) and only chmods — never chowns — the file before writing sensitive data. The only ownership check (`IsFileOwnedByChainlink`, used in `checkFilePermissions`) runs later, during `runNode`, and is non-fatal (log warning only).

### Finding Description
`FilePersistedSecretGenerator.Generate` [1](#0-0)  writes the node's cookie-signing secret to `<rootDir>/secret` via `utils.WriteFileWithMaxPerms` [6](#0-5) . Because `os.OpenFile` is called without `O_EXCL`, a pre-existing (attacker-owned) file at that path is opened and written to instead of causing an error. Ownership is never re-asserted; the code path only ANDs the current mode bits, and `os.Chmod`/`file.Chmod` cannot change the file's owner. The one ownership check that exists, `utils.IsFileOwnedByChainlink` [3](#0-2) , is invoked from `checkFilePermissions` in `core/cmd/shell_local.go` [4](#0-3) , well after application/secret initialization, and only logs a warning rather than refusing to start or re-securing the file.

### Impact Explanation
An attacker who can win this ownership race retains the ability to reclaim read access to the node's session-signing secret after chainlink writes it, enabling forgery of admin session cookies and unauthorized access to the node's privileged HTTP API — a direct secret-disclosure / authentication-bypass outcome.

### Likelihood Explanation
Requires local unprivileged filesystem access to the node's data/root directory prior to secret creation (shared host, containers with shared volumes, or predictable first-run timing) — a plausible unprivileged-local-user trust boundary, matching the original report's threat model.

### Recommendation
Use `os.OpenFile` with `O_CREATE|O_EXCL` (fail if the file already exists) when creating the `secret` file and other files listed in `protectedFiles`, and make the ownership check in `checkFilePermissions` fail-fast (return an error / abort startup) instead of only warning, per the comment already present in the code acknowledging this should be mandatory.

### Proof of Concept
1. On a shared multi-tenant host, as an unprivileged attacker user, create `rootDir/secret` with mode `0666` (world read/write) before the chainlink node's first startup: `touch rootDir/secret && chmod 666 rootDir/secret`.
2. Start the chainlink node as the victim user with `--rootDir` pointed at that directory. `FilePersistedSecretGenerator.Generate` opens the existing file (no `O_EXCL`), chmods it to `0600`, and writes the new session secret into it.
3. Because the attacker remains the file's owner, they run `chmod 644 rootDir/secret` (permitted for the owner regardless of current mode) and read the secret.
4. Use the recovered secret with `gorilla/securecookie` to forge a valid admin session cookie and access the node's protected API endpoints.

// WriteFileWithMaxPerms writes `data` to `path` and ensures that
// the file has permissions that are no more permissive than the given ones.
func WriteFileWithMaxPerms(path string, data []byte, perms os.FileMode) (err error) {
	f, err := os.OpenFile(path, os.O_RDWR|os.O_CREATE|os.O_TRUNC, perms)
	if err != nil {
		return err
	}
	defer func() { err = stderrors.Join(err, f.Close()) }()
	err = EnsureFileMaxPerms(f, perms)
	if err != nil {
		return
	}
	_, err = f.Write(data)
	return
}

// EnsureFileMaxPerms ensures that the given file has permissions
// that are no more permissive than the given ones.
func EnsureFileMaxPerms(file *os.File, perms os.FileMode) error {
	stat, err := file.Stat()
	if err != nil {
		return err
	}
	if stat.Mode() == perms {
		return nil
	}
	return file.Chmod(stat.Mode() & perms)
}
