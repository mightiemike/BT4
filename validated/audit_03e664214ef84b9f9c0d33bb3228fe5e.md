### Title
TRC10 Exchange (Bancor-style DEX) ignores per-token `precision`, causing decimal-mismatch mispricing analogous to the ULTI WETH-decimals assumption - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java])

### Summary
The reported ULTI issue is a class of bug where a contract treats an arbitrary ERC20 input token as if it always has a fixed, assumed number of decimals (18, like WETH), using hardcoded constants/ratios instead of the token's actual `decimals()`. The java-tron TRC10 exchange module exhibits the same root cause: TRC10 tokens can be issued with an arbitrary `precision` field (0–6) [1](#0-0) , validated up to 6 in `AssetIssueActuator` [2](#0-1) , but the Bancor-style exchange actuators (`ExchangeCreateActuator`, `ExchangeTransactionActuator`, `ExchangeWithdrawActuator`) and `ExchangeCapsule`/`ExchangeProcessor` never read or apply this `precision` value when computing balances, ratios, or trade output.

### Finding Description
`ExchangeCreateActuator.doValidate()` accepts `firstTokenBalance`/`secondTokenBalance` as raw integer quantities and only checks them against a global `balanceLimit` and the account's raw asset balance — with no adjustment for the token's declared precision [3](#0-2) . The pool balances are stored as-is in `ExchangeCapsule.setBalance(firstTokenBalance, secondTokenBalance)` [4](#0-3) .

Trading logic in `ExchangeCapsule.transaction()` and `ExchangeWithdrawActuator.doValidate()` performs Bancor-formula math (`processor.exchange(...)`, BigDecimal ratio calculations) purely on these raw integer balances, using a hardcoded virtual `supply = 1_000_000_000_000_000_000L` constant regardless of the paired tokens' actual precision [5](#0-4) , and similarly `ExchangeWithdrawActuator` computes cross-token ratios directly from raw balances with no precision normalization [6](#0-5) .

A grep across the exchange module confirms `getPrecision()`/`precision` is never referenced by any Exchange* actuator or `ExchangeCapsule` in production code (only referenced in `AssetIssueActuator` and `AssetIssueCapsule`, and in test files). This mirrors the ULTI bug exactly: `inputTokenDecimals` is captured but never used in constant/ratio math because the code implicitly assumes a fixed decimal scale (there, WETH's 18; here, TRX's fixed 6-decimal `drops`/`TRX_PRECISION`). Just as pairing USDC (6 decimals) with the ULTI constants breaks the launch math, pairing a TRC10 token issued with `precision = 0` (a "whole unit" token) against TRX (fixed 6-decimal drops) or against another TRC10 token with `precision = 6` produces an exchange pool whose price ratio does not reflect real economic value, because the raw integer balances are treated as if they were on the same decimal scale.

### Impact Explanation
Because the exchange constant-product/Bancor math operates on raw balances without decimal normalization, a pool created between two TRC10 assets (or TRC10 vs TRX) with different `precision` settings will have a systematically distorted price from the moment of creation. Traders using `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` can exploit the resulting mispricing to extract value disproportionate to the tokens deposited, and pool creators (or the first depositor) can also be economically disadvantaged unknowingly. This is a concrete public-facing accounting/pricing correctness issue reachable by any unprivileged user who creates or trades against such a pool — no privileged role is required, matching the "underpriced-public-work / mispricing" impact class.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires (a) a TRC10 asset issuer choosing a non-default `precision` (which is explicitly supported and validated up to 6, so this is a normal, expected user path, not a theoretical edge case) [2](#0-1) , and (b) an exchange pool being created pairing that asset with TRX or another asset of different precision via `ExchangeCreateActuator`. Both actions are permissionless and require no special privileges, so the precondition is easily satisfiable by any user, though the resulting mispricing severity depends on how much the precisions diverge.

### Recommendation
Incorporate each token's `AssetIssueContract.precision` (fetched via `AssetIssueCapsule.getPrecision()`) into the exchange pricing/validation logic:
- Normalize `firstTokenBalance`/`secondTokenBalance` (and later trade quantities) to a common decimal scale before applying Bancor/ratio math in `ExchangeCreateActuator`, `ExchangeCapsule.transaction()`, and `ExchangeWithdrawActuator`.
- Alternatively, reject exchange pool creation when paired tokens have mismatched `precision` unless explicit scaling factors are supplied and validated.
- Replace the hardcoded virtual `supply` constant in `ExchangeCapsule.transaction()` with one derived from actual token precisions where relevant.

### Proof of Concept
1. Issue TRC10 token `A` with `precision = 0` via `AssetIssueActuator` (valid per `SameTokenNameCloseInvalidPrecision`-style tests confirming precision 0–6 accepted) [7](#0-6) .
2. Issue TRC10 token `B` with `precision = 6`.
3. Call `ExchangeCreateActuator` to create a pool pairing `A` and `B` with balances chosen to look economically "1:1" nominally (e.g., `firstTokenBalance = 1_000_000`, `secondTokenBalance = 1_000_000`) — `doValidate()` accepts this with no precision check [8](#0-7) .
4. Because `A` (`precision=0`) units represent 10^6 times the "real world" value per unit compared to `B` (`precision=6`) units, the pool's actual price ratio is off by a factor of 10^6 relative to the tokens' intended value, and any trade executed via `ExchangeTransactionActuator`/withdrawal via `ExchangeWithdrawActuator` settles at this distorted rate — precisely the "unexpected behavior from wrong decimal assumption" pattern described in the ULTI report.

Note: I was unable to execute this scenario in a live environment; the analysis is based on static code review of the cited actuator/capsule logic, which is confirmed to never invoke `getPrecision()` in the exchange path.
