### Title
On-disk `BucketMap` index capacity only grows and never shrinks, allowing cheap create/close account churn to permanently bloat validator storage - ([File: bucket_map/src/bucket.rs])

### Summary
Analogous to the Perennial bug where a minimal-cost `deposit`+`withdraw` cycle repeatedly triggered an expensive, unpaid-for oracle request, an unprivileged Solana user can repeatedly create a rent-exempt system account and immediately close it (getting the rent lamports back, paying only the fixed, tiny transaction fee) using a fresh `Pubkey` each time. On validators running the disk-backed accounts index (`BucketMap`), each unique pubkey ever inserted forces the on-disk index bucket (`Bucket::grow_index`) to grow to accommodate the high-water mark of entries seen, but there is no corresponding shrink path when those entries are later deleted (`Bucket::delete_key`). The cost of maintaining/growing this index is paid entirely by the validator (CPU for the O(capacity) rehash-copy, and permanent disk space) while the attacker pays only a fixed per-transaction fee unrelated to the number of distinct accounts churned.

### Finding Description
`Bucket::delete_key` in `bucket_map/src/bucket.rs` (around lines 663-679) only marks the index slot free (`self.index.free(elem_ix)`); it never reduces `self.index.contents.capacity()` nor triggers a compaction of the underlying `BucketStorage`/mmap file.

`Bucket::grow_index` (lines 685-747) is the only path that changes index capacity, and it is one-directional: it is invoked from `Bucket::insert`/`Bucket::batch_insert_non_duplicates` whenever `try_write` returns `BucketMapError::IndexNoSpace`, and it always allocates a *larger* file (`new_capacity = (current_capacity * 110 / 100).max(anticipated_size)`), never a smaller one. There is no `shrink_index`, `compact`, or equivalent counterpart anywhere in `bucket_map/src/bucket.rs`, `bucket_api.rs`, or `bucket_map.rs` (confirmed by search: only `grow_index`/`IndexNoSpace` references exist; no `shrink`/`compact` routine touches the disk index capacity).

In contrast, the in-memory index (`in_mem_accounts_index.rs`) *does* have logic to reallocate/shrink its `HashMap` when tombstones accumulate (`reallocate_to_clear_tombstones`), showing that the disk-backed `BucketMap` structure deliberately/accidentally lacks the equivalent capacity-recovery mechanism.

This means: a user can pay a fixed transaction fee to create a new rent-exempt account (`system_instruction::create_account`) and then close it (transfer all lamports out, which is treated as a delete per `test_drained_created_account` / `test_accounts_clean_after_snapshot_restore_then_old_revives` semantics for zero-lamport accounts), reclaiming their rent lamports. Repeating this with a fresh pubkey each time permanently ratchets up the on-disk bucket's capacity (and thus the mmap file size on disk) because:
1. Each new pubkey is a cache miss/insert into the bucket map index.
2. Growth is monotonic and keyed off historical peak occupancy, not current live count.
3. Deletion never triggers compaction/shrink.

The validator therefore accumulates disk usage and repeatedly pays for `grow_index`'s O(capacity) copy-and-rehash (visible in the loop at lines 693-733, which scans and re-inserts every occupied entry from the old index into the new one) each time growth is required, in proportion to the *total number of distinct accounts ever created*, not the number of *live* accounts - a cost never compensated by any per-account fee.

### Impact Explanation
This is a disproportionate storage and CPU cost issue: an attacker pays a fixed, minimal fee per create/close cycle but forces the validator's disk-backed accounts index to grow without bound and without ever reclaiming space, and forces repeated expensive full-bucket rehash/copy operations. Over a sustained period, this could materially increase disk consumption and background CPU/IO cost on any validator running the disk index (`--accounts-index-path`), which is common in production for memory-constrained nodes. This does not corrupt state or cause node panics, but it is a genuine resource-exhaustion/cost-asymmetry issue analogous in class to the Perennial oracle-fee-drain bug: cheap, repeatable user action causing metered/unbounded protocol-side resource cost.

### Likelihood Explanation
The action requires only standard, unprivileged instructions available to any user (`CreateAccount` + a transfer/close that zeroes the account), each protected only by the ordinary, small transaction fee - there is no additional cost tied to the number of distinct new pubkeys used. It is trivially scriptable and requires no special permissions, matching the "viable, even if unlikely to be maximally exploited, low-cost attack path" bar. Likelihood of *some* impact is high for any validator using the disk index; the *magnitude* depends on sustained attacker spend (transaction fees) versus disk growth, so it is a slow/creeping DoS rather than an instant one.

### Recommendation
- Add a shrink/compaction path to `BucketMap`'s on-disk index (mirroring `in_mem_accounts_index.rs`'s `reallocate_to_clear_tombstones`) that reduces `BucketStorage` capacity (and reclaims/truncates the mmap file) when the live/occupied fraction drops well below a low-water mark, rather than only ever growing.
- Track the number of free (deleted) slots and periodically trigger a "grow-to-current-size" repack even when strictly no larger capacity is required, to bound disk usage by live occupancy rather than historical peak.
- Consider bounding per-slot/per-epoch number of distinct new pubkeys serviceable without proportional fee increase, or explicitly documenting/monitoring bucket-map file growth as an operational metric so operators can detect and mitigate this pattern.

### Proof of Concept
Conceptual (cannot be fully driven without a running validator + disk-index config, but the mechanism is directly inspectable in code):
1. Configure a validator with the disk-backed accounts index enabled.
2. Repeatedly submit, in a loop, `system_instruction::create_account(payer, new_keypair, rent_exempt_minimum, small_space, owner)` followed immediately (same or next slot) by fully draining `new_keypair`'s lamports back to `payer` (a "create-then-drain" pattern, exactly as exercised functionally, minus the loop, by `runtime/src/bank/tests.rs::test_drained_created_account` and `test_accounts_data_size_delta_on_chain_with_deleted_account_transaction`'s `PreExecState::Uninitialized` case).
3. Use a fresh `Keypair` each iteration so each is a distinct pubkey inserted into (and later deleted from) the `BucketMap` index.
4. Observe (via `BucketStats`/`bucket.stats.index` fields such as `resizes`, `max_size`, `total_file_size`, exposed in `bucket_map/src/bucket_stats.rs`) that `index.max_size`/`total_file_size` monotonically increases with the number of distinct accounts ever created, and never decreases despite `delete_key` being called on each drained account - confirming the absence of any shrink path in `Bucket::grow_index`/`Bucket::delete_key` (`bucket_map/src/bucket.rs:663-747`).     pub fn grow_index(&self, mut current_capacity: u64) {
        if self.index.contents.capacity() == current_capacity {
            // make sure to grow to at least % more than the anticipated size
            // The indexing algorithm expects to require some over-allocation.
            let anticipated_size = self.anticipated_size * 140 / 100;
            let mut m = Measure::start("grow_index");
            //debug!("GROW_INDEX: {}", current_capacity_pow2);
            let mut count = 0;
            loop {
                count += 1;
                // grow relative to the current capacity
                let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
                let (mut index, file_name) = BucketStorage::new_with_capacity(
                    Arc::clone(&self.drives),
                    1,
                    std::mem::size_of::<IndexEntry<T>>() as u64,
                    Capacity::Actual(new_capacity),
                    self.index.max_search,
                    Arc::clone(&self.stats.index),
                    Arc::clone(&self.index.count),
                );
                // index may have allocated something larger than we asked for,
                // so, in case we fail to reindex into this larger size, grow from this size next iteration.
                current_capacity = index.capacity();
                let mut valid = true;
                for ix in 0..self.index.capacity() {
                    if !self.index.is_free(ix) {
                        let elem: &IndexEntry<T> = self.index.get(ix);
                        let new_ix =
                            Self::bucket_create_key(&mut index, &elem.key, self.random, true);
                        if new_ix.is_err() {
                            valid = false;
                            break;
                        }
                        let new_ix = new_ix.unwrap();
                        let new_elem: &mut IndexEntry<T> = index.get_mut(new_ix);
                        *new_elem = *elem;
                        index.copying_entry(new_ix, &self.index, ix);
                    }
                }
                if valid {
                    self.stats.index.update_max_size(index.capacity());
                    let mut items = self.reallocated.items.lock().unwrap();
                    items.index = Some(index);
                    self.reallocated.add_reallocation();
                    self.restartable_bucket.set_file(file_name, self.random);
                    break;
                }
            }
            m.stop();
            if count > 1 {
                self.stats
                    .index
                    .failed_resizes
                    .fetch_add(count - 1, Ordering::Relaxed);
            }
            self.stats.index.resizes.fetch_add(1, Ordering::Relaxed);
            self.stats
                .index
                .resize_us
                .fetch_add(m.as_us(), Ordering::Relaxed);
        }
    }

impl BucketStats {
    pub fn update_max_size(&self, size: u64) {
        self.max_size.fetch_max(size, Ordering::Relaxed);
    }

    pub fn resize_grow(&self, old_size: u64, new_size: u64) {
        let size_change = new_size.saturating_sub(old_size);
        self.total_file_size
            .fetch_add(size_change, Ordering::Relaxed);
    }
}

    /// reallocate_to_clear_tombstones must rebuild the bin's hashmap so that all
    /// remaining entries survive and `capacity()` recovers from the drop caused by
    /// tombstones consuming `growth_left`.
    #[test]
    fn test_reallocate_to_clear_tombstones_preserves_entries() {
        // Reallocate only runs in Threshold mode. For this test HWM must be less
        // than the number of inserts to ensure the calculated bucket size is
        // the same for hwm and num_inserts
        let hwm = 199;
        let lwm = 140;
        let index = new_should_write_through_for_test(Some((hwm, lwm)));

        // Fill the bin's hashmap exactly to hashbrown's max_load (7/8 of 256 buckets).
        // At this size at least one remove is all but guaranteed (odds ~1e-10) to create a tombstone
        let num_inserts = 224;
        // Then remove enough entries to drop down to the low water mark
        let num_removes = 84;
        let pubkeys: Vec<_> = (0..num_inserts)
            .map(|_| solana_pubkey::new_rand())
            .collect();
        {
            let mut map = index.map_internal.write().unwrap();
            for pubkey in &pubkeys {
                let entry = Box::new(AccountMapEntry::new(
                    SlotList::from([(0, 42)]),
                    1,
                    AccountMapEntryMeta::new_dirty(&index.storage, true),
                ));
                map.insert(*pubkey, entry);
            }
        }
        let capacity_after_inserts = index.map_internal.read().unwrap().capacity();

        // Remove a portion of the entries to create tombstones. Hashbrown reduces capacity
        // for each tombstone created, so we should see a capacity drop here.
        let mut map = index.map_internal.write().unwrap();
        for pubkey in &pubkeys[..num_removes] {
            map.remove(pubkey);
        }
        drop(map);

        let capacity_after_removes = index.map_internal.read().unwrap().capacity();

        // Verify that capacity dropped due to added tombstones
        assert!(capacity_after_removes < capacity_after_inserts);

        index.reallocate_to_clear_tombstones();

        let map = index.map_internal.read().unwrap();

        // All remaining entries should survive the realloc.
        assert_eq!(map.len(), num_inserts - num_removes);
        for pubkey in &pubkeys[num_removes..] {
            assert!(map.contains_key(pubkey));
        }

        // Tombstones cleared: the new map sized for `len()` lands on the same raw
        // bucket count as before the removes, so capacity is back to its post-insert
        // value.
        assert_eq!(map.capacity(), capacity_after_inserts);
        drop(map);

        assert_eq!(
            index
                .stats()
                .num_hashmap_reallocates
                .load(Ordering::Relaxed),
            1
        );
    }
