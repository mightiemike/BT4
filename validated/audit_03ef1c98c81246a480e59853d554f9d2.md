### Title
State-value chunks committed to durable storage without Merkle proof verification in `KvOnly` restore mode - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
`StateSnapshotRestore::add_chunk` in `storage/aptosdb/src/state_restore/mod.rs` branches on `restore_mode`. In `StateSnapshotRestoreMode::TreeOnly` and `::Default`, the `SparseMerkleRangeProof` supplied with each chunk is verified against the tree's `expected_root_hash` before/while data is written. In `StateSnapshotRestoreMode::KvOnly`, the proof argument is silently dropped and the raw key/value chunk is written straight to `kv_restore` with no cryptographic check at all [2](#0-1) .

### Finding Description
`add_chunk`'s `KvOnly` arm calls `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?` and never touches `proof` or `self.tree_restore` [3](#0-2) . Contrast this with the `Default` arm, which explicitly documents the intended invariant: "verify proof -> write state_kv_db -> write state_merkle_db" [4](#0-3) , and the `TreeOnly` arm, which calls `add_chunk_impl`, which itself calls `verify_chunk` before writing [5](#0-4) .

`restore_mode` is not an internal-only enum — it is a `clap`-derived CLI field on `StateSnapshotRestoreOpt`, directly settable via `--restore-mode` on the `state-snapshot restore`/verify commands exposed by `db-tool`/`backup-cli` [1](#0-0) . This means an operator or an automated pipeline calling the restore tool with `KvOnly` will commit arbitrary key/value pairs from a backup source into `state_kv_db` with zero verification that they are consistent with the target `expected_root_hash`/`TransactionInfo.state_checkpoint_hash` that the manifest and ledger-info proof otherwise establish (`StateSnapshotRestoreController::run_impl` verifies the *manifest's* root hash against the `TransactionInfoWithProof` [6](#0-5) , but that only proves the manifest's claimed root, not that the individual K/V chunks actually correspond to that root when `KvOnly` skips the JMT proof check).

If the backup source (untrusted storage backend, tampered file, MITM'd download, or malicious `BackupStorage` implementation) supplies corrupted or substituted `(key, value)` pairs, `KvOnly` mode will persist them into `state_kv_db` unconditionally, silently diverging the restored node's key-value state from the value that the accumulator/JMT root actually commits to.

### Impact Explanation
This breaks the "restore helpers must not reinterpret committed data into a different ledger state" and "Storage schemas ... must preserve deterministic proof binding" invariants: a restored node's `state_kv_db` can end up holding values that do not match the JMT root it claims to be at. Any subsequent reads served from that KV store (e.g., via the fast-path find-KV-only lookups or before the tree side is populated) would be wrong/corrupted durable data, and if such a divergent KV store is later used as the basis of execution or replay, the node can silently diverge from other correctly-restored/full nodes (hard-fork/replay divergence), or serve state to light clients/backup-verify tooling that superficially looks proof-backed (a manifest-level proof exists) but the individual leaf data was never actually checked against the JMT proof.

### Likelihood Explanation
Likelihood is moderate: it requires selecting `KvOnly` mode, which is a real, reachable, user-facing CLI option rather than pure dead code, and requires an untrusted or compromised backup/storage source (which the restore/verify tooling is explicitly designed to defend against via Merkle range proofs in `Default`/`TreeOnly` modes). Because `KvOnly` is presumably intended as an internal optimization used together with a separate/parallel `TreeOnly` verification pass (as hinted by the coordinator's phase-based restore, where `TreeOnly` is used to (re)verify the tree independently) [7](#0-6) , if an operator (or automation) runs `KvOnly` in isolation, or if the corresponding tree-verification pass is skipped/misconfigured, the missing proof check is not otherwise compensated for.

### Recommendation
Either remove the `KvOnly` no-verification fast path entirely, or require that it can only run in combination with a mandatory, already-completed/enforced `TreeOnly` (or `Default`) verification of the same chunk boundaries for the same version before allowing `kv_restore.add_chunk` to be called — e.g., pass in and check a `previous_leaf`/`range_proof` verification result from the `tree_restore` side, or refuse to expose `restore_mode` on the public CLI without an explicit safety flag and a preceding successful tree-only verification of the identical byte range/version.

### Proof of Concept
1. Run `db-tool state-snapshot restore --state-manifest <M> --state-into-version <V> --restore-mode kv-only` against a backup source under attacker control (or a corrupted local file).
2. Craft `M`'s referenced state-value chunk file(s) so that at least one `(key, value)` pair does not match the leaf hash implied by the manifest's `SparseMerkleRangeProof`, while leaving the manifest's top-level `root_hash`/`TransactionInfoWithProof` untouched.
3. `StateSnapshotRestoreController::run_impl` verifies only the manifest-level proof/root hash [6](#0-5) ; it then calls `receiver.add_chunk(...)` per chunk.
4. Because `restore_mode == KvOnly`, `add_chunk` reaches only the `self.kv_restore....add_chunk(chunk)?` branch and never calls `verify_chunk`/`tree_restore` [3](#0-2) , so the corrupted K/V pair is committed to `state_kv_db` at version `V` despite not matching the JMT leaf hash that the (unused) proof would have rejected.

Note: I could not fully trace every downstream consumer of a `KvOnly`-restored `state_kv_db` (e.g., whether/how the corresponding `TreeOnly` verification pass is guaranteed to always run before this KV data is trusted in the actual production restore-coordinator flow), so the exact end-to-end exploitability in the default `db-tool bootstrap` flow (which currently only invokes `TreeOnly`/`Default`, not `KvOnly`, per `coordinators/restore.rs`) is not fully confirmed — the concrete risk is clearest for direct/manual `KvOnly` CLI invocations rather than the automated `RestoreCoordinator` path.

            },
