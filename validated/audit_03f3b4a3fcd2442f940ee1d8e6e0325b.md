### Title
Failed outbound re-mint permanently locks bridged funds via unrecoverable `ABORTED` state - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`handleFailedOutbound` in `x/uexecutor/keeper/outbound.go` attempts to re-mint PRC20 tokens back to the user when a destination-chain outbound fails. If that re-mint call itself fails, the code calls `AbortOutbound`, which unconditionally sets the outbound to the terminal `Status_ABORTED` state [1](#0-0) . This is the exact bug-class described in the Booster `shutdownPool()` report: a terminal/finalized state is committed even though the underlying fund-recovery operation did not succeed, and there is no mechanism to reopen or retry it — permanently freezing the user's bridged principal.

### Finding Description
`FinalizeOutbound` routes failed destination-chain observations to `handleFailedOutbound`: [2](#0-1) 

`handleFailedOutbound` tries to mint the bridged PRC20 back to the revert recipient via `CallPRC20Deposit` (a `DerivedEVMCall`). If that call errors, the outbound is immediately marked `ABORTED` and the function returns — no retry, no re-queue: [3](#0-2) 

`AbortOutbound` writes this terminal status and removes the entry from `PendingOutbounds`, so nothing in the normal outbound lifecycle will ever revisit it: [4](#0-3) 

The only on-chain fund-recovery path for "stuck" cross-chain funds is `AttachRescueOutboundFromReceipt`, but its eligibility check explicitly only covers two cases: (a) `IsCEA` inbounds whose first deposit `PcTx` is `FAILED`, or (b) non-CEA inbounds that have an `INBOUND_REVERT` outbound with status `REVERTED`. `Status_ABORTED` outbounds produced by a failed re-mint are not recognized by this check at all: [5](#0-4) 

There is also no `MsgRetryOutbound`/admin re-mint message anywhere in the module — the only comparable admin recovery tools are `RecomputeBallotQuorum` (ballot-level) and `RevertStuckInbound` (only for inbounds whose ballot never finalized), neither of which applies to an already-finalized, already-`ABORTED` outbound.

The re-mint recipient (`recipient := outbound.Sender`, overridden by `outbound.RevertInstructions.FundRecipient`) is attacker-controlled data carried from the original inbound submission: [6](#0-5) 

An unprivileged user submitting an ordinary crosschain transaction can set `RevertInstructions.FundRecipient` to a value that makes `CallPRC20Deposit`'s underlying EVM call revert deterministically (e.g., a receiving contract without proper token acceptance, or any address for which the PRC20/registry-side logic reverts on deposit). When the destination-chain leg subsequently fails (attacker can also influence this, e.g. by supplying a payload/gas configuration that fails on the destination chain), the combination guarantees the re-mint path fails and the outbound is permanently `ABORTED` with the underlying value neither delivered on the destination chain nor recovered on Push Chain.

### Impact Explanation
This produces a permanent freeze of user principal funds analogous to the C4 finding: the PRC20 representation is burned/spent as part of outbound creation, the destination-chain delivery failed, and the fallback re-mint also failed — with the protocol marking the case as terminally resolved (`ABORTED`) rather than retriable. No governance or rescue flow currently recognizes or resolves `ABORTED` outbounds, so funds are permanently lost from the user's perspective. This matches the in-scope impact "permanent freezing ... of user or protocol-controlled funds" and "corruption of ... canonical UniversalTx state" (an outbound is marked ABORTED/terminal despite the recovery leg never succeeding).

### Likelihood Explanation
Medium. It requires: (1) an outbound observation to be voted as failed by honest UVs (a legitimate, non-adversarial occurrence — e.g., destination-chain revert, insufficient gas, or a target contract rejecting the call), and (2) the PC-side re-mint call to independently fail (e.g., due to a revert-recipient address/contract that cannot receive the PRC20, transient EVM issues, or fee-tier/quote failures in a swap-adjacent path). Because `RevertInstructions.FundRecipient` is attacker-supplied, a user can deliberately construct this scenario against their own funds, and it can also occur non-adversarially whenever a destination failure coincides with any re-mint issue — consistent with how the original C4 judge treated the pattern as valid even without a fully deterministic real-world trigger.

### Recommendation
Do not treat a failed re-mint as terminal. Options:
- Keep the outbound in a retriable state (e.g., a new `Status_REMINT_PENDING`) and re-queue it (e.g., back into `PendingOutbounds` or a dedicated retry index) so future blocks/admin actions can retry `CallPRC20Deposit`.
- Extend `AttachRescueOutboundFromReceipt`'s eligibility check to also recognize `Status_ABORTED` outbounds (in addition to `INBOUND_REVERT`+`REVERTED` and CEA-deposit-`FAILED`), so the existing rescue mechanism can resolve them.
- At minimum, add an explicit admin/governance message to manually retry or redirect a `PcRevertExecution` re-mint for `ABORTED` outbounds, mirroring `RevertStuckInbound`'s design for the inbound side.

### Proof of Concept
1. Submit a normal cross-chain `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` inbound with `RevertInstructions.FundRecipient` set to an address/contract engineered to make the PRC20 deposit revert (e.g., a contract lacking the required receive hook, or any address the PRC20/registry deposit path rejects).
2. Let the resulting outbound reach the destination chain and have honest UVs vote it as failed (`MsgVoteOutbound` with `success=false`), which routes into `FinalizeOutbound` → `handleFailedOutbound`. [2](#0-1) 
3. `CallPRC20Deposit(ctx, prc20, recipient, amount)` reverts because of the crafted recipient. [3](#0-2) 
4. `AbortOutbound` sets `OutboundStatus = Status_ABORTED` and removes the entry from `PendingOutbounds`. [7](#0-6) 
5. Query the UTX: `outbound.OutboundStatus == ABORTED`, `PcRevertExecution.Status == "FAILED"`, funds delivered nowhere (not on destination chain, not re-minted on Push Chain).
6. Attempt rescue via `AttachRescueOutboundFromReceipt` — it rejects the UTX because the eligibility check does not match `Status_ABORTED` (only checks CEA-deposit-`FAILED` or `INBOUND_REVERT`+`REVERTED`). [8](#0-7)

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}
