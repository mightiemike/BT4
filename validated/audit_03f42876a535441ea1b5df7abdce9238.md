### Title
Blocking global rate limiter on bounded gRPC executor causes node-wide RPC-API DoS - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/RateLimiterInterceptor.java])

### Summary
`RateLimiterInterceptor.interceptCall` runs on the gRPC server's fixed-size executor and calls `GlobalRateLimiter.acquirePermit`, which by default (`rate.limiter.apiNonBlocking = false`) dispatches to the blocking `GlobalRateLimiter.acquire()`, invoking Guava's `RateLimiter.acquire()` synchronously on the calling worker thread. Because `RpcService.initServerBuilder` binds the gRPC server to a fixed-size `ExecutorService` sized by `rpcThreadNum`, sustained request volume from a single unprivileged client can put every worker thread to sleep inside `acquire()`, stalling all RPC methods for all clients — including unrelated cheap calls.

### Finding Description
`RpcService.initServerBuilder` creates a bounded thread pool via `ExecutorServiceManager.newFixedThreadPool(this.executorName, parameter.getRpcThreadNum())` and binds it as the gRPC server executor (`serverBuilder.executor(this.executorService)`), so every incoming gRPC call — across `Wallet`, `WalletSolidity`, `Database`, `Monitor`, etc. — is dispatched onto this one shared, size-limited pool. [1](#0-0) 

`RateLimiterInterceptor.interceptCall` runs inline on that executor thread and calls `GlobalRateLimiter.acquirePermit(runtimeData)` as part of the call's dispatch path, before `next.startCall` even runs. [2](#0-1) 

`GlobalRateLimiter.acquirePermit` dispatches to `acquire()` (blocking) when `rate.limiter.apiNonBlocking` is `false`, and `acquire()` calls Guava `RateLimiter.acquire()` on the per-IP limiter and then the shared global limiter — both of which block the calling thread until a token becomes available: [3](#0-2) 

Critically, `rate.limiter.apiNonBlocking = false` is the shipped **default** in both `reference.conf` and `config.conf`, and `CommonParameter.rateLimiterApiNonBlocking` defaults to `false` as well — no non-default configuration is required to reach this state: [4](#0-3) [5](#0-4) [6](#0-5) 

`rpcThreadNum` defaults to `(availableProcessors + 1) / 2` when unset (a small, single-digit number on most deployments), and `ExecutorServiceManager.newFixedThreadPool` uses `Executors.newFixedThreadPool`, i.e., a fixed-size pool backed by an unbounded queue: [7](#0-6) [8](#0-7) 

Exploit flow: an unauthenticated client opens more concurrent gRPC calls than `rpcThreadNum` and sustains a call rate that exceeds either the per-IP QPS budget (`global.ip.qps`, default 10000) or the global QPS budget (`global.qps`, default 50000). Once the token bucket is exhausted, every task that reaches `GlobalRateLimiter.acquire()` blocks the executor thread it is running on. Because all `rpcThreadNum` threads can simultaneously be blocked inside `RateLimiter.acquire()`, and the queue in front of the fixed pool is unbounded, additional/queued calls — from the attacker or from any other legitimate client, on any RPC method — cannot be dispatched to a worker thread until a token frees up, causing a node-wide stall of the gRPC API. No existing check intercepts this: the per-endpoint `IRateLimiter` check happens first but does not prevent this at all since `GlobalRateLimiter.acquirePermit` is unconditionally invoked afterward whenever the per-endpoint check passes (or when no per-endpoint limiter is configured at all, which is the shipped default — `rpc = []` in `config.conf`). [9](#0-8) 

### Impact Explanation
This is a total gRPC-API unavailability / thread-pool exhaustion DoS reachable by any unauthenticated network client — no signed transaction, funded account, or privileged role is required. It matches the "DoS via RPC-API" bounty impact class: worker-thread starvation on the shared, bounded gRPC executor stalls delivery of all RPC methods node-wide, including unrelated read-only/health-check-style calls, for the duration the attacker sustains excess request volume.

### Likelihood Explanation
- Preconditions: default configuration (`apiNonBlocking=false` is the shipped default; no per-endpoint rate limiter is configured by default), and a fixed-size gRPC executor (default when `rpcThreadNum` resolves to a positive value from `postProcess`, which it always does).
- Attacker cost: none beyond network access and enough concurrent connections/bandwidth to exceed the per-IP (10000 QPS) or global (50000 QPS) token budget; no fees, signatures, or account balance are required since gRPC calls are not on-chain transactions.
- Feasibility: sustaining tens of thousands of QPS from one or few sources is a moderate but realistic bar for a dedicated DoS attacker (achievable with a handful of high-throughput clients or reflected/distributed IPs), and is trivially repeatable.

### Recommendation
Do not perform blocking `RateLimiter.acquire()` calls on the same bounded executor threads used to service gRPC calls. Options: (1) make the blocking wait happen off the gRPC executor (e.g., via a `ScheduledExecutorService`/`CompletableFuture` that defers call dispatch without occupying a worker thread), (2) always use the non-blocking `tryAcquire` path for the shared/global limiter regardless of `apiNonBlocking`, rejecting overloaded requests immediately with `RESOURCE_EXHAUSTED` instead of parking worker threads, or (3) bound the wait time with `RateLimiter.tryAcquire(timeout)` and fail fast if the token is not available within a small deadline, freeing the worker thread for other calls.

### Proof of Concept
```java
// Integration-style PoC (JUnit), mirroring RateLimiterInterceptorTest but using
// a small fixed thread pool and a mocked blocking RateLimiter.acquire().
@Test
public void testBlockingRateLimiterStarvesFixedExecutor() throws Exception {
  int poolSize = 4;
  ExecutorService pool = Executors.newFixedThreadPool(poolSize);
  CountDownLatch releaseGate = new CountDownLatch(1); // never released within test timeout
  AtomicInteger servicedBeyondPool = new AtomicInteger(0);

  Runnable rpcTask = () -> {
    try {
      // Simulates GlobalRateLimiter.acquire() blocking forever because the
      // configured QPS budget is exhausted.
      releaseGate.await();
      servicedBeyondPool.incrementAndGet();
    } catch (InterruptedException ignored) { }
  };

  // Saturate the pool: poolSize + 1 concurrent "calls"
  List<Future<?>> futures = new ArrayList<>();
  for (int i = 0; i < poolSize + 1; i++) {
    futures.add(pool.submit(rpcTask));
  }

  // Even an unrelated "cheap" call submitted after saturation never runs.
  AtomicBoolean healthCheckServiced = new AtomicBoolean(false);
  pool.submit(() -> healthCheckServiced.set(true));

  Thread.sleep(2000); // simulate the test timeout window

  // All poolSize worker threads are stuck in "acquire()"; nothing beyond
  // the pool size gets serviced, including the health-check task.
  assertEquals(0, servicedBeyondPool.get());
  assertFalse(healthCheckServiced.get());
}
```
This demonstrates the invariant break: once `poolSize` worker threads are blocked inside the equivalent of `GlobalRateLimiter.acquire()`, no further gRPC method — regardless of which service or endpoint it belongs to — can be serviced by the bounded executor bound in `RpcService.initServerBuilder`, confirming the node-wide liveness failure described in the finding.
