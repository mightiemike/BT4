### Title
Malicious declared class can permanently disable native compilation and crash transaction-processing threads via a poisoned compilation channel - (File: `crates/blockifier/src/state/native_class_manager.rs`)

### Summary
The `NativeClassManager` compiles declared Sierra classes to Cairo-Native asynchronously through a single background worker thread that reads compilation requests from a shared `sync_channel`. If a declared class's native compilation fails and `panic_on_compilation_failure` is enabled, the worker thread panics and terminates, dropping the receiver. Any subsequent transaction (submitted by any unprivileged account) that triggers `send_compilation_request` on the now-disconnected channel unconditionally panics in the caller's thread. This is structurally the same bug class as the reported Y2K Carousel issue: an attacker permissionlessly inserts an item into a shared queue/worker (a Declare transaction triggering native compilation), and once that item is "processed" it can make the shared processing pipeline permanently unusable for everyone else, not just for the attacker's own item.

### Finding Description
`NativeClassManager::start` spawns exactly one compilation worker thread that owns the receiving end of the `CompilationRequest` channel: [1](#0-0) 

That worker calls `process_compilation_request` for every request, and does so with `panic_on_compilation_failure` from config: [2](#0-1) 

Inside `process_compilation_request`, if the native compiler fails on the given Sierra program and `panic_on_compilation_failure` is set, the function unconditionally panics: [3](#0-2) 

Because this runs on a dedicated `std::thread::spawn`, a panic here kills the compilation worker thread and drops the channel's receiver, disconnecting the channel. Any legitimate, unrelated Declare transaction submitted afterward (from any account) that reaches `set_and_compile` -> `send_compilation_request` will hit `TrySendError::Disconnected` and unconditionally panic on the *caller's* thread: [4](#0-3) 

`set_and_compile` (and therefore `send_compilation_request`) is invoked as part of normal class caching during block building/execution for any Declare transaction whose class needs Native compilation, i.e. it runs inline within the batcher's or gateway's transaction-processing call stack, not in an isolated sandbox: [5](#0-4) 

The class hash of the attacker's malicious class is entirely attacker-controlled (they choose the Sierra program to declare), and one Declare transaction that fails native compilation is enough to poison the shared, process-global compilation channel for every future Declare transaction handled by that node process.

### Impact Explanation
If `panic_on_compilation_failure` is enabled in a deployment (the flag appears in the production `batcher_config.json` and `gateway_config.json` app configs found in the repo, though I could not confirm the concrete boolean value used at runtime with the tools available), a single unprivileged Declare transaction whose class fails native compilation:
1. Kills the sole compilation worker thread and disconnects its channel.
2. Causes every subsequent Declare transaction (from any account) that needs `LazyCompilation` to panic the calling thread inside `send_compilation_request`, since it unconditionally panics on `Disconnected`.

Depending on how that thread is scheduled (batcher's block-building worker pool / gateway validation thread pool), this can crash the block-building/validation task and prevent the node from confirming new blocks/transactions containing Declare transactions — matching the "network unable to confirm new transactions" impact bucket. This is a direct sequencer-level analog of the reported bug: one permissionless, attacker-controlled item entering a shared, non-isolated processing pipeline (compilation queue) can permanently break processing for all other legitimate participants sharing that pipeline.

### Likelihood Explanation
Reaching this requires: (a) `cairo_native_mode` set to `LazyCompilation` (or `WaitOnCompilation`, which panics inline immediately) and (b) `panic_on_compilation_failure` set to `true` for the deployment. Both are configuration-dependent, and I was not able to confirm within the available tool budget whether production deployments actually set `panic_on_compilation_failure: true` (the config key exists in `batcher_config.json`/`gateway_config.json`, but its concrete value is unverified). If it is `false`, the failure is caught and cached as `CachedCairoNative::CompilationFailed`, and this analog does not apply. Crafting a Sierra program that passes the CASM-oriented gateway compile checks but fails the separate Cairo-Native compiler is plausible given the two compilers are distinct toolchains with different libfunc/resource support, but I could not verify a concrete PoC input in this pass.

### Recommendation
- Avoid `panic!` in any code path reachable from processing untrusted, attacker-controlled input (i.e. never panic from a native-compilation failure of an attacker-declared class); always downgrade to graceful fallback (as already done in the non-panic branch).
- Remove the `panic!("Compilation request channel is closed.")` in `send_compilation_request` and instead return a recoverable error/log-and-drop, so a disconnected worker thread cannot cascade into panics on unrelated future transactions.
- If the worker thread can panic, restart it (or use `catch_unwind`) rather than let the channel become permanently disconnected.
- Audit/confirm the runtime value of `panic_on_compilation_failure` in all production deployment configs and default it to `false`.

### Proof of Concept
Not independently verified end-to-end (would require confirming `panic_on_compilation_failure=true` in a live config and crafting a Sierra program that passes `SierraToCasmCompiler::compile` but fails `SierraToNativeCompiler::compile`). The structural flaw is demonstrated by the code paths cited above: `process_compilation_request` panics on native-compile failure when the flag is set, and `send_compilation_request` panics unconditionally once the channel is disconnected, with no isolation between the attacker's Declare transaction and subsequent unrelated Declare transactions sharing the same process-global compilation worker/channel.

```rust
    pub fn set_and_compile(&self, class_hash: ClassHash, compiled_class: CompiledClasses) {
        match compiled_class {
            CompiledClasses::V0(_) => self.class_cache.set(class_hash, compiled_class),
            CompiledClasses::V1(compiled_class_v1, sierra_contract_class) => {
                if self.cairo_native_mode() == CairoNativeMode::WaitOnCompilation {
                    let compiler = self.compiler.as_ref().expect("Compiler not available.");
                    // After this point, the Native class should be cached and available through
                    // `get_runnable` access.
                    // Ignore compilation errors for now.
                    process_compilation_request(
                        self.class_cache.clone(),
                        compiler.clone(),
                        (class_hash, sierra_contract_class, compiled_class_v1),
                        self.cairo_native_run_config.panic_on_compilation_failure,
                    )
                    .unwrap_or(());
                    return;
                }

                // Cache the V1 class.
                self.class_cache.set(
                    class_hash,
                    CompiledClasses::V1(compiled_class_v1.clone(), sierra_contract_class.clone()),
                );

                if self.cairo_native_mode() == CairoNativeMode::LazyCompilation {
                    // Send a non-blocking compilation request.
                    // Ignore compilation errors for now.
                    self.send_compilation_request((
                        class_hash,
                        sierra_contract_class,
                        compiled_class_v1,
                    ))
                    .unwrap_or(());
                }
            }
            // TODO(Yoni): consider panic since this flow should not be reachable.
            CompiledClasses::V1Native(_) => self.class_cache.set(class_hash, compiled_class),
        }
    }
```

```rust
    /// Sends a compilation request to the compilation worker. Does not block the sender. Logs an
    /// error if the channel is full.
    fn send_compilation_request(
        &self,
        request: CompilationRequest,
    ) -> Result<(), ContractClassManagerError> {
        let sender = self.sender.as_ref().expect("Compilation channel not available.");
        // TODO(Avi, 15/12/2024): Check for duplicated requests.
        sender.try_send(request).map_err(|err| match err {
            TrySendError::Full((class_hash, _, _)) => {
                log::debug!(
                    "Compilation request channel is full (size: {}). Compilation request for \
                     class hash {:#066x} was not sent.",
                    self.cairo_native_run_config.channel_size,
                    class_hash.0
                );
                ContractClassManagerError::TrySendError(TrySendError::Full(class_hash))
            }
            TrySendError::Disconnected(_) => {
                panic!("Compilation request channel is closed.")
            }
        })
    }
```

```rust
fn run_compilation_worker(
    class_cache: RawClassCache,
    receiver: Receiver<CompilationRequest>,
    compiler: Arc<SierraToNativeCompiler>,
    panic_on_compilation_failure: bool,
) {
    log::info!("Compilation worker started.");
    for compilation_request in receiver.iter() {
        process_compilation_request(
            class_cache.clone(),
            compiler.clone(),
            compilation_request,
            panic_on_compilation_failure,
        )
        .unwrap_or(());
    }
    log::info!("Compilation worker terminated.");
}
```
