### Title
Age-based eviction in `pruneCallbacks` lets an unprivileged attacker force early eviction of legitimate pending callbacks - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`pruneCallbacks` trims `h.savedCallbacks` strictly by `createdAt`, always deleting the *oldest* half when the map exceeds `MaxSavedCallbacks`, with no per-user quota or attribution. Because `HandleLegacyUserMessage` accepts unauthenticated/unprivileged user messages and inserts a `savedCallback` for every request with no rate limiting (explicitly marked as a TODO), an attacker can cheaply flood the map with fresh entries to push it over `MaxSavedCallbacks`, guaranteeing that older, legitimate, still-pending callbacks are the ones evicted on the next prune tick.

### Finding Description
`HandleLegacyUserMessage` unconditionally stores every incoming user request as a `savedCallback` keyed by the attacker-controlled `msg.Body.MessageId`, and explicitly has no allowlist/rate-limiting applied yet: [1](#0-0) [2](#0-1) 

`pruneCallbacks` runs periodically (`CallbackPruneIntervalSec`, default 30s) under a single `h.mu` lock, first removing entries older than `maxAge`, then, if the map still exceeds `MaxSavedCallbacks`, sorting all remaining entries ascending by `createdAt` and deleting `entries[:len(entries)-maxSize/2]` — i.e., it always deletes the **oldest** entries first, regardless of whether they belong to a legitimate, still in-flight request or an attacker-manufactured one: [3](#0-2) 

Because eviction ordering is purely a function of `createdAt`, an attacker who can call `HandleLegacyUserMessage` repeatedly (no auth beyond the generic message validity checks, no per-sender rate limit on this path) can inject a burst of many new callbacks. If this burst plus existing legitimate callbacks pushes `len(h.savedCallbacks)` above `MaxSavedCallbacks` (default 20000) before the next prune tick, the *oldest* entries — which are exactly the legitimate, already-pending requests that arrived earlier and are still awaiting a DON node's response — get deleted first, while the attacker's newer flood entries survive. The subsequent legitimate node response for the evicted `MessageId` will find nothing in `h.savedCallbacks` in `handleWebAPITriggerMessage` and silently drop the response (`found` is false, no callback invoked): [4](#0-3) 

No existing authz, rate-limit, or ordering safeguard prevents this: `nodeRateLimiter` throttles gateway→node traffic by node address, not user-message ingestion, and the user-message path itself has no rate limiting (per the TODO comment).

### Impact Explanation
This allows an unprivileged, unauthenticated attacker to cause denial of service against specific in-flight legitimate user requests handled by the gateway's capabilities handler by simply out-flooding the callback table with cheap requests, causing the victim's pending callback to be silently dropped before the DON's response ever reaches them. This matches "unauthorized denial of legitimate workflow/request execution results" — a scoped node/service DoS impact against gateway request delivery.

### Likelihood Explanation
Feasible and repeatable: the attacker needs only the ability to send `HandleLegacyUserMessage`-routed messages (reachable via the gateway's ordinary user-facing endpoint) with distinct `MessageId`s and a timestamp within `MaxAllowedMessageAgeSec`. Generating tens of thousands of such messages within a 30-second prune interval is cheap (no signature/authorization barrier beyond generic message validation, and no rate limiter on this ingestion path). The condition is more likely under load (map "near MaxSavedCallbacks"), but an attacker can also unilaterally create that condition by flooding.

### Recommendation
Do not evict purely by age/order-of-arrival when trimming for size. Consider: (1) applying per-sender/per-IP rate limiting on `HandleLegacyUserMessage` before inserting into `savedCallbacks` (the TODO already flags this), (2) bounding the number of pending callbacks per originating identity so no single actor can dominate the map, and/or (3) when trimming for `MaxSavedCallbacks`, avoid evicting callbacks that are still within a "grace" window from legitimate low-volume senders, or reject new insertions once near capacity instead of evicting existing ones.

### Proof of Concept
Unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Set `MaxSavedCallbacks` to a small value (e.g., 10) and `CallbackMaxAgeSec` large enough that nothing expires by age.
2. Seed one legitimate `savedCallback` with `createdAt = now - 1s` (simulating an earlier, still-pending request).
3. Seed 10+ attacker-style `savedCallback` entries with `createdAt = now` (simulating a flood via repeated `HandleLegacyUserMessage` calls).
4. Call `h.pruneCallbacks()`.
5. Assert that the legitimate callback's `MessageId` is no longer present in `h.savedCallbacks` (evicted) while attacker entries remain — demonstrating that a targeted legitimate pending callback is dropped purely because it is older than attacker-injected flood entries.

	savedCb, found := h.savedCallbacks[msg.Body.MessageId]

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
