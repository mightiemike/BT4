### Title
Witness brokerage fee can be truncated to zero via double-to-long precision loss, allowing repeated small transaction-fee reward distributions to bypass brokerage cuts - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.payReward()` computes the witness "brokerage" (a protocol-analogous interest/service fee taken from block/transaction-fee rewards before crediting the remainder to the shared reward pool) using floating-point `double` arithmetic and then truncates to `long`. When the reward `value` passed in is small relative to the brokerage percentage, `(long) (brokerageRate * value)` rounds down to `0`, exactly mirroring the Sherlock finding where `interestAccrued.mulDiv(pool.interestFee, 1e18)` rounds to zero for low-decimal/low-value amounts, silently losing the protocol's/witness's fee cut for that call while the timestamp/state is still advanced (`delegationStore.addReward` still updates), so the lost fee can never be recovered.

### Finding Description
`payReward` in `MortgageService.java` (lines 79-87):
```java
private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
}
``` [1](#0-0) 

This function is invoked by `payBlockReward` and `payTransactionFeeReward`, which are the two public entry points into fee/reward accrual to a witness: [2](#0-1) 

The witness-controlled `brokerage` percentage is set via `UpdateBrokerageActuator`, which allows any registered witness to set their own brokerage rate between 0 and 100 (`ActuatorConstant.ONE_HUNDRED`), broadcastable by anyone who controls that witness account: [3](#0-2) 

Root cause parity with the referenced report: just as `feeAssets = interestAccrued.mulDiv(pool.interestFee, 1e18)` can be truncated to `0` for small `interestAccrued` amounts (e.g., low-decimal assets, short accrual windows), `brokerageAmount = (long)(brokerageRate * value)` truncates to `0` whenever `value < 100/brokerage` (in the smallest TRX unit, sun). For a low but valid brokerage (e.g. 1%), any reward `value` below 100 sun (0.0001 TRX) yields a truncated brokerage of `0`, and the full `value` is credited to `delegationStore.addReward` with no fee withheld — exactly the "checkpoint advances, loss is permanent" pattern described in the report (there `pool.lastUpdated` advances; here the reward is fully credited to the pool's `addReward` bucket for that cycle, so the missed brokerage cannot be recovered later).

Transaction-fee rewards (`payTransactionFeeReward`) are paid per-block from the sum of transaction fees for that block, and the value passed can be arbitrarily small under low-fee conditions or bandwidth/energy-only transactions where the TRX-denominated fee component is minimal. Because witness brokerage is fully witness-controlled and can be repeatedly, indefinitely triggered by network activity (every block), this is a systemic precision-loss bug, not a one-off rounding artifact.

### Impact Explanation
This causes the same class of loss as the referenced Sherlock M-18: the protocol's/witness's fee-share (`brokerageAmount`, credited via `adjustAllowance`) is silently lost to `0` whenever the reward payment is small enough relative to the brokerage percentage, while the entire un-fee'd `value` is credited into the shared `delegationStore.addReward` bucket that gets distributed to voters. This under-collects the intended cut owed to the witness's declared brokerage split, corrupting the accounting balance between the witness's allowance and the shared voter-reward pool over many blocks/cycles. Given block reward and transaction fee rewards are paid every block indefinitely, cumulative losses over time are structurally analogous to the referenced medium-severity finding (compounding truncation loss in a reward-accounting path, not a single bounded event).

### Likelihood Explanation
This does not require any privileged action beyond a witness setting a legitimate, in-range brokerage value (an unprivileged, permitted witness self-service operation) and does not require exploiting timing tricks — any low-value block/transaction-fee reward triggers the truncation naturally as part of normal `payBlockReward`/`payTransactionFeeReward` calls during ordinary block production. It's a "constant volume of low-value transactions" scenario directly analogous to the report's discussion of unintentional precision loss from normal usage.

### Recommendation
Avoid floating-point truncation for brokerage fee computation. Compute `brokerageAmount` using integer/`BigInteger` math with correct scaling (e.g., `value * brokerage / 100` using `long`/`BigInteger` multiply-then-divide, matching the pattern already used elsewhere in the codebase such as `DelegationStore`'s `BigInteger`-based Vi reward accumulation), and consider tracking any remainder/dust so that it isn't perpetually rounded away over repeated calls.

### Proof of Concept
Given `brokerage = 1` (1%, a valid witness-set value per `UpdateBrokerageActuator` validation), and a `payTransactionFeeReward`/`payBlockReward` call with `value = 50` (50 sun, i.e., 0.00005 TRX, plausible for a very low fee/bandwidth-heavy transaction or a witness receiving a fractional share of a distributed fee pool):
```
brokerageRate = 1.0 / 100 = 0.01
brokerageAmount = (long) (0.01 * 50) = (long) 0.5 = 0
value -= 0            // unchanged
delegationStore.addReward(cycle, witnessAddress, 50)   // full amount credited, no fee withheld
adjustAllowance(witnessAddress, 0)                       // witness gets zero brokerage
```
The witness's intended 1% brokerage cut is permanently lost for that call, and because this executes on every block reward / fee distribution, it can be repeated indefinitely at zero cost to any party, mirroring the "0.01% loss replayed indefinitely = 100% loss" reasoning accepted in the referenced Sherlock judgment.
