Based on my investigation, I found a strong structural analog in NEAR's `DeterministicStateInitAction` (NEP-616), where the account's contract `code` is a `GlobalContractIdentifier` chosen entirely by whoever crafts the `state_init`, and the receiving account id is *derived deterministically* from that same `state_init`. This exactly mirrors the Allo pattern: a "pool" (here, a deterministic account) whose controlling logic ("strategy") is an attacker-chosen, unvalidated reference, and a victim who is lured into sending funds to that derived account id without realizing the "strategy" (global contract) is attacker-controlled and may not behave as expected, or may reference a contract that is later swapped by its owner (`GlobalContractDeployMode::AccountId`) to a malicious version.

### Title
Depositors can be lured into funding a deterministic account backed by an attacker-controlled, mutable global contract - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
`DeterministicStateInitAction` lets any unprivileged transaction sender create/fund an account whose contract code is set purely by reference to a `GlobalContractIdentifier` supplied in the `state_init` [1](#0-0) . The account id itself is deterministically derived from that `state_init`, so an adversary can construct a `state_init` referencing a global contract they own (in `AccountId` deploy mode) and publicize the resulting deterministic account id as a "pool"/"vault" to receive deposits, exactly as the Allo report's malicious custom strategy lures depositors into `fundPool(pool_id)`.

### Finding Description
`action_deterministic_state_init` creates the account (if not already created) and calls `deploy_deterministic_account`, which sets the account's contract purely from `state_init.code()` via `use_global_contract` [2](#0-1) . There is no protocol-level vetting of whether the referenced global contract is "safe" — any account can `DeployGlobalContract` with `GlobalContractDeployMode::AccountId`, and that identifier can subsequently be referenced by anyone's `DeterministicStateInitAction`/`UseGlobalContract` [3](#0-2) . Critically, `AccountId` mode explicitly documents that "This allows the owner to update the contract for all its users" [4](#0-3) , meaning the code backing an already-funded deterministic account can be swapped out later by the original deployer at will. Since the account id is deterministically derived from `state_init` (so a victim can be shown/verify a "legitimate-looking" derivation) but the actual WASM logic is opaque and mutable, a victim who sends a deposit (via the action's `deposit` field or via `Transfer`/`FunctionCall` to that account) has no on-chain guarantee that the code executing on that account will behave honestly, matching the Allo bug class where the pool creator's chosen "strategy" contract siphons funds instead of implementing the expected behavior.

### Impact Explanation
Depositors funding such a deterministic/global-contract-backed account can have their NEAR balance captured by attacker-authored WASM logic (e.g. a contract method that transfers the balance out on call, analogous to `MockStrategy`/`StratergyCustom` in the report), resulting in concrete unauthorized value movement from an unprivileged signer's deposit to the adversary. Because the vulnerable code path is reachable purely through normal actions (`DeployGlobalContract`, `DeterministicStateInitAction`, `Transfer`/`FunctionCall`) available to any signer, this qualifies as depositor-fund loss without any privileged/validator/node compromise, satisfying the High-severity impact bar.

### Likelihood Explanation
Likelihood is High: constructing a malicious global contract and a state-init referencing it is trivial and requires no special permission, and social-engineering victims to send funds to a derived account id (or interact with it as a "vault") mirrors the exact real-world lure vector in the source report. The `AccountId` deploy mode's documented mutability additionally allows a bait-and-switch after initial trust is established.

### Recommendation
- On the tooling/UX side (wallets, explorers, SDKs), clearly warn users when interacting with accounts whose contract is backed by `GlobalContractIdentifier::AccountId` (mutable, owner-controlled) rather than an immutable `CodeHash`-referenced contract, since funds sent to such accounts can be redirected by future code updates.
- Consider protocol-level provenance/warning surfaces (e.g., RPC/view-account metadata flagging `AccountContract::GlobalByAccount` vs `AccountContract::Global`) so clients can distinguish "immutable, audited-once" code from "mutable, owner-controlled" code before a user funds it, similar to the report's recommendation to warn front-end users about custom (unvetted) strategies before they fund a pool.

### Proof of Concept
1. Adversary calls `DeployGlobalContract` with `GlobalContractDeployMode::AccountId` and malicious WASM code that, on a later method call, transfers the account's balance to the adversary (mirrors `StratergyCustom`'s `receive()`/drain logic) [3](#0-2) .
2. Adversary crafts a `DeterministicAccountStateInit` referencing that `GlobalContractIdentifier::AccountId(adversary)` and computes the deterministic receiver account id, publicizing it as a "pool"/"vault" address [5](#0-4) .
3. Victim submits a `DeterministicStateInitAction` (or simply a `Transfer`/`FunctionCall`) with a deposit to that account id, causing `action_deterministic_state_init` → `deploy_deterministic_account` to bind the account to the adversary's global contract and settle the deposit into it [6](#0-5) .
4. Adversary invokes a method on the now-controlled account (or, since deploy mode is `AccountId`, later republishes different malicious code under the same identifier) to transfer out the victim's deposited balance.

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition. "uninit" here is the
        // NEP-616 sense, a deterministic account with no contract yet, not
        // `Account::Uninitialized`: a `0u` id can never reach this, because
        // `validate_deterministic_state_init` pins the receiver to the derived
        // `0s` id.
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }
    if result.result.is_err() {
        return Ok(());
    }

    settle_state_init_deposit(
        account,
        action.deposit,
        account_id,
        receipt,
        &apply_state.config,
        result,
    )
}
