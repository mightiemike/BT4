### Title
Nonce Consumed Without Execution in `validate_delegate_action_key` When `DepositWithFunctionCall` Error Falls Through to Nonce Update - (File: `runtime/runtime/src/actions.rs`)

---

### Summary

In `validate_delegate_action_key`, before protocol version 85, a missing early return after setting the `DepositWithFunctionCall` error allows execution to fall through to the nonce-update block. When the inner `FunctionCall` has `deposit > 0` but the `receiver_id` and `method_name` both satisfy the `FunctionCallPermission` constraints, the sender's access-key nonce is permanently advanced in the trie even though the action is rejected and no receipt is generated. The invariant "a rejected action must not consume the sender's nonce" is broken.

---

### Finding Description

`validate_delegate_action_key` in `runtime/runtime/src/actions.rs` enforces `FunctionCallPermission` restrictions on `DelegateAction` (meta-transaction) payloads. The check sequence is:

1. **Deposit check** (line 637): if `function_call.deposit > 0`, set `result.result = Err(DepositWithFunctionCall)`.
2. **Early return** (lines 645–649): only present when `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` is enabled (protocol version ≥ 85). Before the fix, there is **no `return Ok(())`** here.
3. **Receiver-id check** (line 651): if `receiver_id` matches, no error is set and execution continues.
4. **Method-name check** (line 661): if `method_names` is empty (unrestricted), no error is set and execution continues.
5. **Nonce update** (lines 685–699): `set_access_key` / `set_gas_key_nonce` is called unconditionally. [1](#0-0) 

When `deposit > 0`, `receiver_id` matches, and `method_names` is empty, the function returns `Ok(())` with `result.result = Err(DepositWithFunctionCall)` **after** the nonce has already been written to the trie. The caller `apply_delegate_action` then sees `result.result.is_err()` and returns without generating a receipt: [2](#0-1) 

The nonce is permanently consumed; no inner action executes.

The fix (`FixDelegateActionDepositWithFunctionCallError`) was introduced at protocol version 85 and adds the missing `return Ok(())` immediately after setting the `DepositWithFunctionCall` error: [3](#0-2) [4](#0-3) 

The legacy code path remains in the binary for nodes running protocol versions 83–84 (the minimum supported version is 83): [5](#0-4) 

---

### Impact Explanation

The broken invariant is: **a `DelegateAction` that fails access-key permission validation must not advance the sender's nonce**.

Concrete corrupted value: `access_key.nonce` (or the gas-key nonce row) is incremented via `set_access_key` / `set_gas_key_nonce` even though `result.result` is `Err(DepositWithFunctionCall)`. The sender loses a nonce slot permanently. Their next valid meta-transaction must use a strictly higher nonce. If the sender is operating near the nonce upper bound (`block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`), repeated exploitation exhausts the usable nonce space, permanently blocking further meta-transactions from that key.

This is **transaction manipulation**: the on-chain nonce state is mutated in a way the sender did not authorize (they expected either execution or a clean rejection with no state change).

---

### Likelihood Explanation

Trigger conditions (all must hold simultaneously):
- Protocol version 83 or 84 (minimum supported = 83, fix at 85).
- Sender holds a `FunctionCallPermission` access key with `receiver_id = X` and empty `method_names`.
- Sender signs a `DelegateAction` targeting `receiver_id = X` with `deposit > 0`.
- A relayer submits the signed meta-transaction.

The sender may sign such an action inadvertently (e.g., testing a 1-yoctoNEAR authentication pattern via a meta-transaction) or a malicious relayer may submit a previously signed but not-yet-submitted DelegateAction. On mainnet at protocol version 86 the fix is active; nodes running 83–84 remain vulnerable.

---

### Recommendation

The fix is already present and gated at protocol version 85 (`FixDelegateActionDepositWithFunctionCallError`). No further code change is needed for protocol version ≥ 85. To harden the invariant going forward:

1. Add a runtime assertion after the permission-check block and before the nonce-update block: `debug_assert!(result.result.is_ok(), "nonce must not be updated on permission failure")`.
2. Add a simulation/property-based test that verifies: for any `DelegateAction` where `validate_delegate_action_key` sets `result.result = Err(...)`, the access-key nonce in the trie is identical before and after the call.

---

### Proof of Concept

The existing test `test_delegate_deposit_with_function_call_reports_receiver_mismatch_before_fix` in `runtime/runtime/src/actions.rs` demonstrates the error-overwrite half of the bug. The nonce-consumption half can be demonstrated as follows (protocol version 84, i.e., one below the fix):

```
access_key = FunctionCallPermission {
    allowance: None,
    receiver_id: "token.test.near",   // matches delegate_action.receiver_id
    method_names: [],                  // unrestricted
}
delegate_action = DelegateAction {
    sender_id: "bob.test.near",
    receiver_id: "token.test.near",    // matches access_key.receiver_id
    actions: [FunctionCall {
        method_name: "ft_transfer",
        deposit: 1,                    // nonzero → triggers DepositWithFunctionCall
        gas: 30 TGas,
        args: ...,
    }],
    nonce: current_nonce + 1,
    ...
}
```

Before the fix:
- `DepositWithFunctionCall` is set (line 638).
- No early return (line 645–649 not taken).
- `receiver_id` matches → no overwrite, no return (line 651).
- `method_names` empty → no overwrite, no return (line 661).
- `set_access_key` is called with `nonce = current_nonce + 1` (line 688).
- `apply_delegate_action` sees `result.result.is_err()` and returns without generating a receipt.

**Result**: nonce advanced from `current_nonce` to `current_nonce + 1`; no `ft_transfer` receipt created; deposit not moved. [6](#0-5)
