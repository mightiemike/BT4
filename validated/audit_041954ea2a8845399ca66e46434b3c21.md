### Title
Unbounded per-address `AccountAssetStore.getAllAssets` prefix scan allows attacker-inflated TRC10 key-space to degrade every subsequent `GetAccount` read - ([File: chainbase/src/main/java/org/tron/core/store/AccountAssetStore.java])

### Summary
`AccountAssetStore.getAllAssets(account)` performs an unbounded `prefixQuery(address)` over the `account-asset` column family, iterating one entry per distinct TRC10 asset ID ever held by that address. Every `GetAccount`/`GetAccountById` RPC and HTTP call unconditionally triggers this scan via `AccountCapsule.importAllAsset()`, so an unprivileged account holder who accumulates a large number of distinct TRC10 asset types under one address permanently inflates the read cost of every future query against that address.

### Finding Description
`Wallet.getAccount` and `Wallet.getAccountById` call `accountCapsule.importAllAsset()` unconditionally on every read [1](#0-0) , which delegates to `AssetUtil.importAllAsset` → `AccountAssetStore.getAllAssets(account)` [2](#0-1) .

When `account.getAssetOptimized()` is true (the normal state once asset-optimization is enabled network-wide), `getAllAssets` performs `prefixQuery(account.getAddress().toByteArray())`, iterating every key in the `account-asset` store whose prefix is the account's address, one entry per distinct held TRC10 asset ID: [3](#0-2) . The underlying `prefixQuery` in `Chainbase` merges root DB and snapshot results with no size cap or pagination [4](#0-3) .

Each distinct asset ID held by an address creates one row `Bytes.concat(address, assetId)` in `account-asset`, populated via `AccountAssetStore.getAssets`/`putAccount` whenever an account's `AssetV2Map` is persisted [5](#0-4) . An unprivileged attacker can grow N by having tokens transferred to their address: `TransferAssetActuator.execute` calls `toAccountCapsule.addAssetAmountV2(...)`, which adds a new `AssetV2Map` entry for any new token ID with no cap on the number of distinct asset types an account may hold [6](#0-5) . `TransferAssetActuator.calcFee()` returns 0, so transferring an existing distinct asset type into an address costs no per-transfer fee (only bandwidth and, once, a new-account fee) [7](#0-6) .

To seed N distinct token types, the attacker (or colluding accounts) must issue N distinct TRC10 tokens via `AssetIssueActuator`, each paying `calcFee() = dynamicStore.getAssetIssueFee()` [8](#0-7) , since "An account can only issue one asset" per owner address [9](#0-8) . None of the standard checks (`validateSignature`, `DecodeUtil.addressValid`, actuator `validate()`, fork gates, bandwidth/energy accounting) constrain the total number of distinct asset types an address may accumulate or cap the cost of the `prefixQuery` scan performed on every subsequent read.

### Impact Explanation
This is a DoS via RPC-API: once N is large, every `GetAccount`/`GetAccountById` call (gRPC `WalletSolidityApi.getAccount`/HTTP `GetAccountServlet`) against the target address performs an O(N) prefix scan with no pagination or cap, permanently degrading query latency/CPU for the serving node on every subsequent read of that account. The inflated key-space persists indefinitely (no pruning/expiry mechanism exists for stale asset entries), so the cost is paid by the node on every future query, not just once.

### Likelihood Explanation
The attack is fully reachable by an unprivileged actor using only standard, unprivileged, fee-paying operations (`AssetIssueContract`, `TransferAssetContract`); no witness/SR/operator privilege is required. It is rate-limited economically by `AssetIssueFee` per new distinct token type (paid once per token, not per transfer or per query), meaning the attacker's one-time cost scales linearly with N while the ongoing degradation is imposed indefinitely on every reader of that account, independent of the attacker's continued participation. Because the fee is a fixed, moderate, non-recurring cost and can be amortized/accumulated over time across many accounts/transactions, building up a large N is feasible for a motivated attacker, though the fee makes rapid, cheap escalation to extremely large N impractical.

### Recommendation
Cap or paginate `AccountAssetStore.getAllAssets`/`prefixQuery` result size, or bound the number of distinct TRC10 asset types an account may hold at the actuator `validate()` level; alternatively, restructure `GetAccount` to fetch assets lazily/paginated (e.g., a separate `GetAccountAssets` API with limit/offset) rather than always inlining a full unbounded asset list into the base account read path.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/db/AccountAssetStoreDosTest.java
@Test
public void testGetAllAssetsScalesLinearlyWithAssetCount() {
  AccountCapsule account = ...; // account with AssetOptimized = true
  int[] sizes = {100, 1000, 10000};
  for (int n : sizes) {
    for (int i = 0; i < n; i++) {
      byte[] key = Bytes.concat(account.getAddress().toByteArray(),
          String.valueOf(i).getBytes());
      accountAssetStore.put(key, Longs.toByteArray(1L));
    }
    long start = System.nanoTime();
    Map<String, Long> assets = accountAssetStore.getAllAssets(account.getInstance());
    long elapsed = System.nanoTime() - start;
    // Assert elapsed grows ~linearly with n, no cap enforced
    System.out.println("n=" + n + " elapsedNs=" + elapsed + " assets.size=" + assets.size());
  }
}
```
Expected result: latency of `getAllAssets` (and therefore every `GetAccount` RPC/HTTP call for that address) grows linearly and unboundedly with the number of synthetic asset keys, with no cap enforced anywhere in the call path.

  public Map<String, Long> getAllAssets(Protocol.Account account) {
    Map<String, Long> assets = new HashMap<>();
    if (account.getAssetOptimized()) {
      Map<WrappedByteArray, byte[]> map = prefixQuery(account.getAddress().toByteArray());
      map.forEach((k, v) -> {
        byte[] assetID = ByteArray.subArray(k.getBytes(),
                account.getAddress().toByteArray().length, k.getBytes().length);
        assets.put(ByteArray.toStr(assetID), Longs.fromByteArray(v));
      });
    }
    account.getAssetV2Map().forEach((k, v) -> assets.put(k, v));
    return assets;
  }

  public Map<WrappedByteArray, byte[]> prefixQuery(byte[] key) {
    Map<WrappedByteArray, byte[]> result = prefixQueryRoot(key);
    Map<WrappedByteArray, byte[]>  snapshot = prefixQuerySnapshot(key);
    result.putAll(snapshot);
    result.entrySet().removeIf(e -> e.getValue() == null);
    return result;
  }

  private Map<WrappedByteArray, byte[]> prefixQueryRoot(byte[] key) {
    Map<WrappedByteArray, byte[]> result = new HashMap<>();
    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {
      result = ((LevelDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    } else if (((SnapshotRoot) head.getRoot()).db.getClass() == RocksDB.class) {
      result = ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    }
    return result;
  }
