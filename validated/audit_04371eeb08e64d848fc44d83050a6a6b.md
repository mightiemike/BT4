## Title
Aggregate‑ratio shrink candidate selection permanently drops moderately‑dead storages once the global target is met, causing unbounded dead‑byte accumulation - ([File: accounts-db/src/accounts_db.rs])

## Summary
The reported DeFi bug is an economic-incentive failure: liquidators only act when the gas cost of processing a position is smaller than the reward, so small under-collateralized positions are never liquidated and bad debt accumulates silently. The analogous mechanism in `agave` is `AccountsDb`'s shrink-candidate selection, which decides whether the "cost" of reclaiming a storage's dead bytes is "worth" doing based on an *aggregate* ratio rather than evaluating each storage on its own merit. Once the aggregate target is satisfied, remaining dead-byte-bearing storages are discarded from consideration entirely (not deferred), so their garbage is never reclaimed unless unrelated future writes happen to touch them again.

## Finding Description
`select_candidates_by_total_usage` sorts all shrink candidates by `alive_ratio` (sparsest first) and walks the list accumulating `total_alive_bytes` vs `total_bytes` until the running `alive_ratio` exceeds the configured `shrink_ratio` (default `0.80`, `DEFAULT_ACCOUNTS_SHRINK_RATIO`): [1](#0-0) 

Once the aggregate target is reached, the loop `break`s (line 3060), and only entries whose *individual* `alive_ratio` is below `shrink_ratio` and were processed *before* the break are re-queued into `shrink_slots_next_batch`: [2](#0-1) 

Any candidate that the sorted iteration never reached (because the aggregate goal was already satisfied by other, sparser stores) is dropped completely — it is not shrunk in this pass, and it is not carried into `shrink_slots_next_batch`, so it is permanently removed from `self.shrink_candidate_slots`: [3](#0-2) [4](#0-3) 

A storage only re-enters `shrink_candidate_slots` when *additional* accounts within it die and `remove_dead_accounts` re-inserts it via `is_shrinking_productive` / `is_candidate_for_shrink`: [5](#0-4) 

If a rooted slot's storage has a moderate but static fraction of dead bytes (e.g., 30–70% dead, analogous to a "small position" whose reclaim value doesn't justify processing under the current aggregate budget) and no further accounts in that slot ever die afterward, it is silently and permanently excluded from shrink consideration the moment any shrink pass satisfies the 0.80 ratio using other, more attractive (sparser) candidates. Just like liquidators skip a $5 position because gas outweighs profit, `AccountsDb`'s shrink logic skips these storages because reclaiming their bytes isn't needed to hit the current aggregate target — but unlike a deferred retry, the candidate is dropped outright rather than queued for a future pass. The ancient-append-vec packer has the equivalent gate: storages that are neither sparse enough to be `should_shrink` nor already near `ideal_storage_size` are excluded from `all_infos` outright: [6](#0-5) 
and shrink eligibility inside a pass is further capped by `percent_of_alive_shrunk_data` / `max_resulting_storages`, deliberately leaving "should_shrink" cleared for excess candidates beyond the per-pass I/O budget: [7](#0-6) 

## Impact Explanation
Each shrink pass optimizes for a global alive-ratio threshold rather than guaranteeing progress on every dead-byte-bearing storage. Storages that fall just short of being "worth" reclaiming in a given pass, and whose ratios don't change afterward, keep their dead bytes forever. Across the fleet of rooted slots this produces disproportionate, unbounded storage growth (and the associated CPU/I/O cost of scanning/loading those extra bytes during clean, snapshotting, and account loads) with no mechanism to force eventual reclamation — a disproportionate storage and CPU cost problem for long-running validators, matching the accepted impact category.

## Likelihood Explanation
This triggers under ordinary validator operation whenever the shrink candidate set contains a mix of very sparse and moderately-dead storages: as soon as the sparsest ones satisfy the aggregate `shrink_ratio`, the moderately-dead ones are simply dropped. Because slots do not receive new writes once rooted, a storage whose accounts stop churning after this point never becomes a candidate again, making the "loss" of these candidates a naturally-occurring, not adversarially-forced, condition of steady-state operation.

## Recommendation
Change the selection algorithm so that candidates skipped due to the aggregate-ratio break are re-queued into `shrink_slots_next_batch` (or a persistent "eligible" list) rather than being dropped outright, ensuring every storage that is a documented shrink candidate (`is_candidate_for_shrink`) is eventually revisited on a subsequent pass regardless of whether the aggregate target was already met by other stores in the current round.

## Proof of Concept

2. Call `select_candidates_by_total_usage` with `shrink_ratio = 0.6`: store A is selected and shrunk (it is needed to reach 0.6), store B (`0.5 < 0.6`) is queued to `shrink_slots_next_batch`, but any additional candidate beyond the point where the aggregate ratio already exceeds 0.6 (simulate with a 4th, moderately-dead store D whose own ratio also happens to be below 0.6 but is iterated after the aggregate ratio already surpassed the target) is dropped from consideration entirely rather than added to `shrink_slots_next_batch`.
3.     fn clear_should_shrink_after_cutoff(&mut self, tuning: &PackedAncientStorageTuning) {
        let mut bytes_to_shrink_due_to_ratio = Saturating(0);
        // shrink enough slots to write 'percent_of_alive_shrunk_data'% of the total alive data
        // from slots that exceeded the shrink threshold.
        // The goal is to limit overall i/o in this pass while making progress.
        // Simultaneously, we cannot allow the overall budget to be dominated by ancient storages that need to be shrunk.
        // So, we have to limit how much of the total resulting budget can be allocated to re-packing/shrinking ancient storages.
        let threshold_bytes =
            (self.total_alive_bytes_shrink.0 * tuning.percent_of_alive_shrunk_data / 100).min(
                u64::from(tuning.max_resulting_storages)
                    * u64::from(tuning.ideal_storage_size)
                    * tuning.percent_of_alive_shrunk_data
                    / 100,
            );
        // At this point self.shrink_indexes have been sorted by the
        // largest amount of dead bytes first in the corresponding
        // storages.
        self.best_slots_to_shrink = VecDeque::with_capacity(self.shrink_indexes.len());
        for info_index in &self.shrink_indexes {
            let info = &mut self.all_infos[*info_index];
            self.best_slots_to_shrink
                .push_back((info.slot, info.written_bytes));
            if bytes_to_shrink_due_to_ratio.0 >= threshold_bytes {
                // we exceeded the amount to shrink due to alive ratio, so don't shrink this one just due to 'should_shrink'
                // It MAY be shrunk based on total capacity still.
                // Mark it as false for 'should_shrink' so it gets evaluated solely based on # of files.
                info.should_shrink = false;
            } else {
                bytes_to_shrink_due_to_ratio += info.alive_bytes;
            }
        }

#[test]
fn test_select_candidates_by_total_usage_3_way_split_condition() {
    // three candidates, one selected for shrink, one is put back to the candidate list and one is ignored
    let mut candidates = ShrinkCandidates::default();
    let db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);

    let (_temp_dirs, common_store_path) = get_temp_accounts_paths(1).unwrap();
    let account_size = 100;
    let store_file_size = account_size + 10_000;
    let account = AccountSharedData::new(1, account_size as usize, &Pubkey::default());

    let store1_slot = 11;
    let store1 = Arc::new(AccountStorageEntry::new(
        &common_store_path[0],
        store1_slot,
        store1_slot as AccountsFileId,
        store_file_size,
        db.accounts_file_provider,
    ));
    store1
        .accounts
        .write_accounts(&(store1_slot, [(&Pubkey::new_unique(), &account)].as_slice()));
    db.storage.insert(Arc::clone(&store1));
    store1.num_alive_bytes.store(0, Ordering::Release);
    candidates.insert(store1_slot);

    let store2_slot = 22;
    let store2 = Arc::new(AccountStorageEntry::new(
        &common_store_path[0],
        store2_slot,
        store2_slot as AccountsFileId,
        store_file_size,
        db.accounts_file_provider,
    ));
    store2
        .accounts
        .write_accounts(&(store2_slot, [(&Pubkey::new_unique(), &account)].as_slice()));
    db.storage.insert(Arc::clone(&store2));
    store2
        .num_alive_bytes
        .store(store2.written_bytes() as usize / 2, Ordering::Release);
    candidates.insert(store2_slot);

    let store3_slot = 33;
    let store3 = Arc::new(AccountStorageEntry::new(
        &common_store_path[0],
        store3_slot,
        store3_slot as AccountsFileId,
        store_file_size,
        db.accounts_file_provider,
    ));
    store3
        .accounts
        .write_accounts(&(store3_slot, [(&Pubkey::new_unique(), &account)].as_slice()));
    db.storage.insert(Arc::clone(&store3));
    store3
        .num_alive_bytes
        .store(store3.written_bytes() as usize, Ordering::Release);
    candidates.insert(store3_slot);

    // Set the target alive ratio to 0.6 so that we can just get rid of store1, the remaining two stores
    // alive ratio can be > the target ratio: the actual ratio is 0.75 because of 150 alive bytes / 200 total bytes.
    // The target ratio is also set to larger than store2's alive ratio: 0.5 so that it would be added
    // to the candidates list for next round.
    let target_alive_ratio = 0.6;
    let (selected_candidates, next_candidates) =
        db.select_candidates_by_total_usage(&candidates, target_alive_ratio);
    assert_eq!(1, selected_candidates.len());
    assert!(selected_candidates.contains(&store1_slot));
    assert_eq!(1, next_candidates.len());
    assert!(next_candidates.contains(&store2_slot));
}
