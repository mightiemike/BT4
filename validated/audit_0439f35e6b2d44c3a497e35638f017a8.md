## Title
Non-atomic canonical-head pointer update vs. in-memory block-index update creates a transient window where `CanonicalInMemoryState` returns inconsistent "canonical" data - (File: `crates/chain-state/src/in_memory.rs`, `crates/chain-state/src/chain_info.rs`, `crates/engine/tree/src/tree/mod.rs`)

### Summary
`on_canonical_chain_update` in the engine tree performs the canonical-chain switch in two separate, non-atomic steps: it first mutates the block index (`canonical_in_memory_state.update_chain(...)`, which swaps `blocks`/`numbers` maps) and only afterwards calls `canonical_in_memory_state.set_canonical_head(...)`, which writes a *different* lock (`ChainInfoTracker::canonical_head`). [1](#0-0)  This is structurally analogous to CL-2020-24's root cause: two logically-coupled updates ("weights" vs. "node relations" in proto-array; here, "block index" vs. "head pointer") are performed as separate critical sections instead of one atomic sweep.

### Finding Description
`InMemoryState` explicitly documents the invariant that `blocks` and `numbers` maps must be updated together under one critical section so that "readers don't observe partially updated state." [2](#0-1)  That invariant is honored *within* `update_blocks`. [3](#0-2)  However, the canonical head field lives in a completely separate structure, `ChainInfoTracker`, guarded by its own `RwLock`/`AtomicU64`. [4](#0-3)  `set_canonical_head` on the tracker is a distinct lock acquisition from `update_chain`'s lock acquisition on `blocks`/`numbers`. [5](#0-4) 

In `on_canonical_chain_update`, these two updates are issued sequentially with no shared lock or barrier between them:
```
self.canonical_in_memory_state.update_chain(chain_update);      // updates blocks/numbers
self.canonical_in_memory_state.set_canonical_head(tip.clone()); // updates chain_info_tracker
``` [6](#0-5) 

The same pattern repeats in `apply_canonical_ancestor_via_reorg` (unwind path) and `handle_chain_advance_or_same_height`. [7](#0-6) [8](#0-7) 

`CanonicalInMemoryState` is an `Arc`-shared, multi-reader structure consumed concurrently by RPC, the transaction pool's canonical-state listener, and providers (`BlockchainProvider`/`ConsistentProvider`). Because `blocks`/`numbers` are updated first and `chain_info_tracker.canonical_head` second, any concurrent reader that calls `get_canonical_head()` (returns the *old* head) and then looks up state by number/hash via `state_by_number`/`hash_by_number` (which already reflects the *new* chain, since `numbers`/`blocks` were already swapped) observes two different "views" of the canonical chain at the same instant — the head pointer says block N (old), but the numbers map at height N already resolves to the new post-reorg block. In a reorg of equal length, this specifically means `hash_by_number(N)` returns a hash that does **not** match `get_canonical_head().hash()`, even though both claim to describe "the canonical chain."

### Impact Explanation
If any consumer relies on this pair of accessors together to determine "the current canonical head's state" (e.g. constructing a state provider by combining `get_canonical_head()`'s metadata with a `state_by_number`/`state_by_hash` lookup, or RPC's `eth_getBlockByNumber("latest")` racing an in-flight reorg), it can transiently read a block/state that diverges from the head the tracker itself reports as canonical — i.e., a state read that differs from the parent's/head's committed post-state at a single point in time. This matches the report's required equality break ("a state read that differs from the parent's committed post-state"). The window is bounded (closed as soon as `set_canonical_head` runs, no scheduling/yield occurs between the two calls on the same thread), so the blast radius is limited to concurrent readers on other threads/tasks, not the engine's own single-threaded state.

### Likelihood Explanation
Likelihood is low. The window between the two lock acquisitions is extremely short (no `await` point occurs between `update_chain` and `set_canonical_head` in `on_canonical_chain_update`), and triggering an externally-visible divergence requires a concurrent reader to race precisely inside this narrow, uninstrumented gap while a reorg replaces a block at the exact same height as the previous head. No code path was found that actually reads `get_canonical_head()` and `hash_by_number`/`state_by_number` together to build a canonical view without first taking a consistent snapshot (RPC/txpool consumers observed use `CanonStateNotification` broadcasts rather than racing raw accessors). This significantly reduces exploitability versus a genuine reachable bug.

### Recommendation
Merge the two updates into a single critical section (or have `CanonicalInMemoryState::update_chain` also update `chain_info_tracker.canonical_head` while holding the `blocks`/`numbers` write locks), so a single atomic "sweep" updates both the block index and the head pointer, eliminating any window where the two disagree — mirroring the eventual real fix for CL-2020-24 (single consistent sweep instead of two decoupled ones).

### Proof of Concept
Not confirmed with a runnable reproduction; this requires a background reader thread/task interleaving with `on_canonical_chain_update` at the exact instruction boundary between the `update_chain` and `set_canonical_head` calls, which could not be demonstrated with the available static analysis. No consumer in the reachable in-scope crates was found to combine these two accessors without an intervening consistent snapshot, so this should be treated as a low-confidence structural analog rather than a proven, independently reachable vulnerability.

/// # Locking behavior on state updates
///
/// All update calls must acquire all locks at once before modifying state to ensure the internal
/// state remains consistent. This prevents readers from observing partially updated state where
/// the numbers and blocks maps are out of sync.
/// Update functions ensure that the numbers write lock is always acquired first, because lookup by
/// numbers first read the numbers map and then the blocks map.
/// By acquiring the numbers lock first, we ensure that read-only lookups don't deadlock updates.
/// This holds, because only lookup by number functions need to acquire the numbers lock first to

    fn update_blocks<I, R>(&self, new_blocks: I, reorged: R)
    where
        I: IntoIterator<Item = ExecutedBlock<N>>,
        R: IntoIterator<Item = ExecutedBlock<N>>,
    {
        {
            // acquire locks, starting with the numbers lock
            let mut numbers = self.inner.in_memory_state.numbers.write();
            let mut blocks = self.inner.in_memory_state.blocks.write();

            // we first remove the blocks from the reorged chain
            for block in reorged {
                let hash = block.recovered_block().hash();
                let number = block.recovered_block().number();
                blocks.remove(&hash);
                numbers.remove(&number);
            }

            // insert the new blocks
            for block in new_blocks {
                let parent = blocks.get(&block.recovered_block().parent_hash()).cloned();
                let block_state = BlockState::with_parent(block, parent);
                let hash = block_state.hash();
                let number = block_state.number();

                // append new blocks
                blocks.insert(hash, Arc::new(block_state));
                numbers.insert(number, hash);
            }

            // remove the pending state
            self.inner.in_memory_state.pending.send_modify(|p| {
                p.take();
            });
        }
        self.inner.in_memory_state.update_metrics();
    }
