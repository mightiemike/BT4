### Title
Stale market `index-cache` entry not invalidated when a vault's index moves via direct `deposit`/`redeem`, understating debt and misrepresenting position health - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` caches each vault's borrow/liquidity index per `{timestamp: stacks-block-time, aid}` in `index-cache`, and treats a hit as authoritative for the remainder of that timestamp (block). However, a vault's index/lindex can also move by direct, unauthenticated calls to the vault's own `deposit`/`redeem` entry points, which invoke the vault's own `accrue` and update its state without ever touching `market.clar`'s cache. If the market's cache was already primed for the current timestamp before such a direct vault call, all subsequent market operations in that same timestamp/block read the stale cached index instead of the vault's true, advanced index.

### Finding Description
`accrue-and-cache` in `mainnet/contracts/market/v0-4-market.clar` implements a cache-then-trust pattern: [1](#0-0) 

```
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

This cache is used by `accrue-user-debts`/`accrue-user-collateral`, and by `resolve-ztoken`'s `get-cached-indexes` lookup used in oracle price resolution, and by `convert-to-scaled-debt`, `find-and-resolve-asset-value`, and `collateral-add`'s capacity check (`cache-primed`) among others. [2](#0-1) [3](#0-2) 

The value bound is `{index, lindex}` for a vault, cached the first time any market function touches that `aid` in a given `stacks-block-time`. The event that invalidates it never occurs within the same timestamp: each vault contract (`v0-vault-stx.clar`, etc.) exposes `deposit` and `redeem` as public functions with no caller-authorization gate — only the depositor/redeemer identity is derived from `contract-caller`, but no `check-caller-auth`/`is-authorized-contract` restriction exists on who may call them. [4](#0-3) [5](#0-4) 

Both entry points execute `(try! (accrue))` directly on the vault, which recomputes and stores fresh `index`/`lindex`/`last-update` in the vault's own state, entirely independent of `market.clar`'s `index-cache` map: [6](#0-5) 

The later use is any subsequent market operation in the same block/timestamp (e.g., another `borrow`, `collateral-remove`, `liquidate`, or price/health evaluation) that calls `accrue-and-cache(aid)` and gets a cache HIT, silently returning the value captured before the vault's direct `deposit`/`redeem` moved the index. The interleaving is straightforward under Clarity's per-transaction, per-block execution model: transactions execute sequentially within a block but each is a separate top-level call, and `index-cache` is persistent contract storage that survives across transactions in the same block as long as `stacks-block-time` is unchanged:

1. Tx 1 (attacker or anyone): calls any `market.clar` function touching asset `aid` (e.g., `collateral-add`, `borrow`) → `accrue-and-cache(aid)` cache MISS → vault accrues, `{index, lindex}` cached under `{timestamp: T, aid}`.
2. Tx 2 (same block, same `T`, attacker-controlled — no auth needed): calls `vault-<aid>.deposit` or `.redeem` directly → vault's own `accrue()` recomputes a newer, larger `index`/`lindex` and stores it in the vault, but `market.clar`'s cache entry for `{T, aid}` is untouched.
3. Tx 3 (same block, same `T`, attacker): calls a `market.clar` function that depends on `aid`'s debt/liquidity index (e.g., `borrow`, `collateral-remove`, or a health check ahead of a further borrow) → `accrue-and-cache(aid)` returns the stale cached value from step 1, understating actual accrued debt (`convert-to-scaled-debt`, `calculate-asset-notional-value`) or misvaluing zToken collateral (`resolve-ztoken`).

Because debt notional value is computed as `debt_scaled * cached_index`, and `cached_index` is stale-low relative to the vault's true, already-advanced index, the market underestimates the position's true debt-in-USD, making the position appear healthier than it actually is. Root cause is the omission of any cache-invalidation/versioning check tying `index-cache` entries to the vault's own state version, combined with the vaults' `deposit`/`redeem` being unauthenticated, direct-callable mutators of the very state the cache is supposed to mirror.

### Impact Explanation
An artificially healthier-looking position lets the attacker: (a) borrow more than their real collateral value supports, or (b) withdraw collateral / avoid liquidation while actually underwater. Both let debt accrue beyond what collateral can cover, directly leading to bad debt against vault suppliers — protocol insolvency and theft of user/supplier funds at rest, which is a Critical-impact class per the rules.

### Likelihood Explanation
The precondition — that vault `deposit`/`redeem` are publicly, unauthenticated, callable and update vault index state independent of the market's cache — is directly verifiable in the vault contract code, and no special privilege or DAO action is required; the attacker only needs to sequence three ordinary calls within a single block. Real-world timestamp collisions across sequential transactions in the same block are the normal case (block time only changes once per block), so this is readily reachable, not a rare edge case.

### Recommendation
Either (a) invalidate/bypass `index-cache` whenever a vault's `deposit`/`redeem` (or any other function that calls the vault's `accrue`) executes — e.g., have the vault push its post-accrual `{index, lindex}` back into the market's cache, or have `market.clar` always re-derive the index by directly reading the vault's live `index`/`lindex` vars rather than trusting a cache that can be invalidated by a third party; or (b) require all vault state mutations to route exclusively through `market.clar` (removing/gating public `deposit`/`redeem` on the vault) so the market's cache can never diverge from vault truth within the same timestamp.

### Proof of Concept
1. Attacker calls `market.borrow` (or any collateral/debt op) for asset `aid`, priming `index-cache` for `{timestamp: T, aid}` with the current vault index.
2. In the same block, attacker calls `vault-<aid>.deposit` (or `.redeem`) directly — a public, unauthenticated entry point — forcing the vault to accrue and advance its real `index`/`lindex` beyond what's cached in the market.
3. Attacker calls `market.borrow` again (or `collateral-remove`) for the same `aid`; `accrue-and-cache` returns the stale, lower cached index, so the attacker's computed debt-in-USD is understated relative to the vault's true index, letting the attacker borrow past their genuine capacity/health threshold or withdraw collateral that should have been blocked.
