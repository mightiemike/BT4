### Title
Missing zero-address validation in `AccountPermissionUpdateActuator` allows self-inflicted, irrevocable loss of account control - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The `AccountPermissionUpdateActuator`, which processes the unprivileged, self-signed `AccountPermissionUpdateContract` broadcast transaction, validates permission key addresses only through `DecodeUtil.addressValid`, which merely checks address length and network prefix byte — it never rejects the all-zero ("burn"/null) address. This mirrors the reported `Staking.sol` class of bug (missing zero-value checks on critical administration parameters, e.g. `setOwner`), except here the unvalidated value is a permission key address that determines who can ever administer the account again.

### Finding Description
`checkPermission()` iterates over each `Key` in a `Permission` and validates the address with: [1](#0-0) 

`DecodeUtil.addressValid` only checks that the address is 21 bytes long and starts with the correct network prefix byte; it does not exclude the degenerate case where the remaining 20 bytes are all zero: [2](#0-1) 

Because of this, a value such as `0x41` followed by twenty `0x00` bytes (a prefix-valid but keyless "zero address") passes validation everywhere it is used, including as the sole key of the `Owner` permission in `AccountPermissionUpdateContract`: [3](#0-2) 

If the resulting `Owner` (or `Active`) permission's key set is composed solely of this zero address (or a combination whose accumulated weight requires it to satisfy the threshold), no private key exists that can ever produce a valid signature for that address, so no future transaction requiring that permission — including a corrective `AccountPermissionUpdateContract` — can ever be authorized again.

### Impact Explanation
This is directly analogous to the reported `setOwner` issue: a single unvalidated zero-value administrative parameter converts a routine operation into an irrecoverable loss of privileged access. For an on-chain TRON account, losing the ability to satisfy the `Owner` permission threshold means the account becomes permanently unable to change its own permissions, vote, freeze/unfreeze, or perform any operation gated by that permission — a permanent, self-inflicted denial of service on the account's administrative capability, with no path to appeal since consensus rules provide no owner-recovery mechanism.

### Likelihood Explanation
The path is reachable by any unprivileged user via a normal signed broadcast transaction (`AccountPermissionUpdateContract`), with no special role or node access required. It requires either user/wallet-tooling error (an uninitialized/zeroed key field, mirroring the "Alice loses ownership" exploit scenario in the report) or a malicious client library / compromised front-end that emits a permission update containing the zero address, since the actuator itself performs no defense against it.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission` (and anywhere else `DecodeUtil.addressValid` is relied upon to gate security-critical fields), explicitly reject the all-zero address in addition to the existing length/prefix check, e.g. add a check such as `!Arrays.equals(key.getAddress().toByteArray(), zeroAddressOfSameLength)` before accepting a `Key`. More broadly, add a zero-value/zero-address guard to `DecodeUtil.addressValid` or a dedicated helper used consistently by all actuators that write immutable or hard-to-recover administrative state.

### Proof of Concept
1. Attacker/careless wallet constructs an `AccountPermissionUpdateContract` for account `A` where the `Owner` permission has a single key: address = `0x41` + 20 zero bytes, `weight = threshold`.
2. Broadcast the transaction, signed validly by `A`'s current owner key (satisfying today's existing permission, since this is the first legitimate use of the function).
3. `AccountPermissionUpdateActuator.validate()` calls `checkPermission(owner)`, which calls `DecodeUtil.addressValid()` on the zero address — validation passes because length and prefix are correct.
4. `execute()` commits `account.updatePermissions(...)`, replacing the account's `Owner` permission with one requiring a signature from the zero address.
5. No corresponding private key exists; account `A` can never again produce a transaction satisfying the `Owner` permission threshold, permanently losing administrative control, matching the "loss of privileged access" impact described in the source report.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
