### Title
Unchecked return value of `AccountCapsule.addAssetAmountV2()` allows silent asset-accounting corruption in `TransferAssetActuator` and `ParticipateAssetIssueActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
The reported bug class in the WiseLending report is that `_safeTransferFrom()` calls a helper (`_callOptionalReturn`) that returns a boolean success flag, but the caller never checks it, so a failed balance-changing operation is silently treated as success, letting an unprivileged caller mutate state (collateral/deposit balances) without an actual corresponding transfer. In `java-tron` the analogous pattern exists around `AccountCapsule.reduceAssetAmountV2()` / `AccountCapsule.addAssetAmountV2()`, both of which return a `boolean` indicating success/failure of a TRC10 asset balance mutation. Several actuators check the return value of `reduceAssetAmountV2()` but do not check the return value of `addAssetAmountV2()` for the same transaction, even though both are boolean-returning, fallible balance operations.

### Finding Description
`TransferAssetActuator.execute()` checks the debit side of the transfer but not the credit side: [1](#0-0) 

`ownerAccountCapsule.reduceAssetAmountV2(...)` failure is checked and reverts with `ContractExeException`, but `toAccountCapsule.addAssetAmountV2(...)` return value is discarded — if it returns `false` (e.g., on an internal overflow/consistency check inside the capsule), the actuator still calls `accountStore.put(toAddress, toAccountCapsule)` and reports `code.SUCESS`, persisting a transaction that looks successful while the recipient's asset balance was not actually credited (or was left in an inconsistent state), even though the sender's balance was already reduced.

The same unchecked pattern appears in `ParticipateAssetIssueActuator.execute()`: [2](#0-1) 

Here `ownerAccount.addAssetAmountV2(key, exchangeAmount, ...)` (line 79) is unchecked while `toAccount.reduceAssetAmountV2(key, exchangeAmount, ...)` (line 85) is checked and throws on failure. This is the same asymmetric-validation pattern flagged in the external report: one side of a value-transfer is defensively checked while the other, equally fallible, side is not.

I was not able to fully inspect the body of `AccountCapsule.addAssetAmountV2()` in this pass (only confirmed its signature returns `boolean` via `grep_search`), so I cannot state with certainty every internal condition under which it returns `false` rather than throwing. This is a gap in my verification.

### Impact Explanation
If `addAssetAmountV2()` can return `false` under any reachable condition (e.g., asset map size/overflow guard, `V2` map inconsistency, or the account's asset balance overflow at `Long.MAX_VALUE`), then:
- In `TransferAssetActuator`: the sender's TRC10 balance is debited via `reduceAssetAmountV2()` and the fee is charged, but the recipient's credit may silently fail, and the transaction still reports `SUCESS`, causing token supply/accounting to diverge across accounts — real value could be burned or "lost" without any revert, corrupting a broadcastable, unprivileged asset transfer.
- In `ParticipateAssetIssueActuator`: the depositor's TRX is spent and the issuer's asset amount is reduced (checked), but the depositor's newly acquired token isn't guaranteed to actually be credited, again with `SUCESS` returned. This directly enables asset/accounting corruption reachable from a normal broadcast transaction, matching the impact bar for "asset or accounting corruption" in unprivileged, contract-adjacent actuators.

### Likelihood Explanation
Both `TransferAssetContract` and `ParticipateAssetIssueContract` are ordinary, unprivileged, broadcastable transactions available to any account holding TRC10 assets — no special permission or malicious peer/node behavior is required. The likelihood of successfully triggering a `false` return specifically depends on internal conditions of `addAssetAmountV2()` I could not confirm from the available index (e.g., whether it can return `false` other than by throwing/asserting), so likelihood should be treated as **uncertain/unverified** pending inspection of `AccountCapsule.addAssetAmountV2()`'s full implementation.

### Recommendation
- Check the return value of `addAssetAmountV2()` in `TransferAssetActuator.execute()` and `ParticipateAssetIssueActuator.execute()` symmetrically with how `reduceAssetAmountV2()` is already checked, throwing `ContractExeException` on `false` to guarantee atomicity of the underlying asset-balance mutation before persisting state and marking `code.SUCESS`.
- Audit all other actuators (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeTransactionActuator`, `ExchangeWithdrawActuator`, `MarketSellAssetActuator`, `UnfreezeAssetActuator`) that call `addAssetAmountV2`/`reduceAssetAmountV2` to ensure both sides of any balance mutation are checked consistently.
