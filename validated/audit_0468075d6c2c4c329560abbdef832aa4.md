### Title
Case-sensitive email matching in `LDAPServerStateSyncer.Work` allows a demoted user's `ldap_user_api_tokens` row to retain its stale Admin role indefinitely - ([File: core/sessions/ldapauth/sync.go])

### Summary
`Work()` builds `upstreamUserStateMap` from raw, non-lowercased LDAP `uid=` values returned by `ldapGroupMembersListToUser`, while `ldap_user_api_tokens.user_email` is stored lowercased (via `FindUser`'s `strings.ToLower` and `CreateSession`'s explicit lowercasing). The purge and role-update logic in `Work()` matches these two email sources with case-sensitive Go map lookups and case-sensitive SQL `WHEN user_email = $n` clauses, so any casing mismatch between the directory-supplied `uid` and the stored lowercase email causes the corresponding API token row to be silently skipped by both the purge step and the role-downgrade step, leaving a stale Admin-scoped token active.

### Finding Description
In `sync.go`, `ldapGroupMembersListToUser` (reused from `ldap.go` lines 711-771) extracts the email straight from the LDAP `uniqueMember` DN string's `uid=` component with no `strings.ToLower` normalization [1](#0-0) . These raw-case emails become the keys of `upstreamUserStateMap` in `Work()` [2](#0-1) .

Meanwhile, `ldap_user_api_tokens.user_email` is populated via `SetAuthToken`, using `user.Email`, which is sourced from `FindUser`, which explicitly lowercases the email (`email = strings.ToLower(email)`) before returning the `sessions.User{Email: email}` result [3](#0-2) , and is then persisted as-is by `SetAuthToken`'s INSERT [4](#0-3) .

`Work()` then performs the purge check `if _, ok := upstreamUserStateMap[ldapSession.UserEmail]; !ok` against `existingAPITokens` (DB, lowercase) using the raw-case map key [5](#0-4) , and the role-update loop looks up `existingAPITokensMap[email]` using the same raw-case `email` from `upstreamUserStateMap` before building the parameterized `CASE WHEN user_email = $n THEN '<role>'` SQL update applied to `ldap_user_api_tokens` [6](#0-5) .

If the demoted/removed user's `uid` attribute in the directory has different casing than the lowercase email cached locally (a routine possibility since LDAP directories commonly preserve the case as entered for `uid`/mail attributes), then:
- The row is not detected as "missing" (no case-insensitive purge), and
- The row is not matched by the `WHEN user_email = $n` role-update clause (case-sensitive exact match), so `ELSE user_role END` preserves the old (stale) Admin role.

`FindUserByAPIToken` then simply trusts the cached `user_role` column with no further upstream validation and no case handling of its own [7](#0-6) , so the stale Admin-scoped token continues to authorize job/spec management, bridge configuration, and key-export endpoints indefinitely (subject only to the unrelated `UserAPITokenDuration()` expiry, not to role revalidation).

### Impact Explanation
A user who is demoted or removed from the upstream Admin group retains full Admin API privileges via their long-lived API token as long as their directory `uid` casing differs from the cached lowercase email — this is a privilege-escalation/stale-credential issue enabling continued unauthorized programmatic access to job/spec CRUD, bridge configuration, and key export via the Chainlink node's HTTP API, which matches "broken access control / privilege escalation" bounty impact categories.

### Likelihood Explanation
Requires only a routine upstream directory operation (group membership change) plus a directory that stores/returns `uid` values with case differing from the locally cached lowercase email — a common real-world LDAP configuration scenario, not requiring any exploit-specific attacker action beyond having previously obtained an Admin-scoped API token (a legitimate action while still Admin). The sync runs automatically on every configured interval, so the bug is deterministic and repeatable once the casing mismatch condition holds.

### Recommendation
Normalize email casing consistently at the point where LDAP directory values are consumed: lowercase the extracted `uid` value in `ldapGroupMembersListToUser` (or immediately when populating `upstreamUserStateMap`) so it matches the persisted lowercase `user_email` columns. Additionally, make the purge and role-update lookups (`existingSessionsMap`, `existingAPITokensMap`, and the SQL `WHEN user_email = $n`) explicitly case-insensitive (e.g. `lower(user_email) = lower($n)`), consistent with the case-insensitive comparisons already used elsewhere (`FindUser`, `ClearNonCurrentSessions`, `SetPassword`).

### Proof of Concept
Integration test in `core/sessions/ldapauth`:
1. Mock `LDAPClient`/`LDAPConn` so an initial `Work()` call returns the target user as a member of the Admin group via a `uniqueMember` value `uid=Test.User@Example.com,...` (mixed case).
2. Call `SetAuthToken` for `sessions.User{Email: "test.user@example.com", Role: sessions.UserRoleAdmin}` to insert an `ldap_user_api_tokens` row with lowercase email and `user_role = 'admin'`.
3. Reconfigure the mocked LDAP connection so the user is now only a member of the Edit group (still same mixed-case `uid=Test.User@Example.com`), simulating demotion.
4. Call `Work(ctx)`.
5. Assert: querying `ldap_user_api_tokens` directly shows `user_role` is still `'admin'` (not updated to `'edit'`), and `FindUserByAPIToken(ctx, token)` returns `sessions.UserRoleAdmin` instead of the expected de-escalated `UserRoleEdit` — demonstrating the stale-admin-token persistence bug.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}
