# State-Integrity Analog Finding

### Title
Unchecked subtraction in `DeltaHistory::validate_against_base_value` can underflow/panic or silently corrupt aggregator (delayed-field) overflow validation - (File: `aptos-move/aptos-aggregator/src/delta_math.rs`)

### Summary
The Solidity bug reduces to one invariant: an error-correction/threshold value that can legitimately exceed the quantity it's subtracted from is subtracted using unchecked arithmetic, causing either a revert (unsigned underflow) or a corrupted result. The same invariant is broken in the Aptos aggregator/delayed-field validation logic, where `DeltaHistory::validate_against_base_value` performs `max_value - min_overflow_positive_delta` with plain `-`, while `min_overflow_positive_delta` is populated from a raw, attacker/user-controlled `delta` value that is *not* bounded by `max_value`.

### Finding Description
`DeltaHistory` tracks, per-aggregator, the smallest delta that overflowed a `try_add` during speculative execution: [1](#0-0) 

`record_overflow` is called with the raw `delta` value passed to the aggregator operation — this is demonstrated by `BoundedMath::unsigned_add_delta`, which returns `Overflow` even when the attempted `delta` is far larger than `max_value` (e.g. `max_value = 100`, `delta = 950`): [2](#0-1) [3](#0-2) 

That raw, unbounded `delta` (e.g. `950`, or in practice any Move-supplied `u128` up to `u128::MAX`) is stored verbatim as `min_overflow_positive_delta`, with no clamp to `max_value`.

Later, when validating a transaction's speculative aggregator base value against recorded history (used to decide whether a speculatively-computed aggregator result can be safely committed or must be re-executed), the code does: [4](#0-3) 

`max_value - min_overflow_positive_delta` is **plain, unchecked** `u128` subtraction. Since `min_overflow_positive_delta` can exceed `max_value` (as shown above), this subtraction underflows:
- In builds with overflow checks enabled, this panics (`attempt to subtract with overflow`).
- In standard release builds (`overflow-checks = false`, Rust's default release profile), it silently wraps around to a value near `u128::MAX`, turning the check `base_value <= max_value - min_overflow_positive_delta` into `base_value <= (~u128::MAX)`, which is satisfied by virtually any `base_value`.

This is the same bug class as the external report: an error/threshold quantity that can exceed the base it's subtracted from, subtracted without a bounds check, in code that gates whether a computed value is accepted into committed state.

### Impact Explanation
`validate_against_base_value` (via `merge_data_and_delta` and `offset_and_merge_history`/`merge_two_deltas`) is on the block-execution/commit path for aggregators and delayed fields, i.e. it determines whether a parallel/speculative execution result for a resource touched by an aggregator can be committed as-is or must trigger re-validation/re-execution: [5](#0-4) [6](#0-5) 

- If it panics, any transaction that causes an aggregator `try_add`/`try_sub` overflow with a delta larger than the aggregator's `max_value` can crash the executing node process during commit-time validation — a direct DoS on block execution, analogous to `_rebalance()` reverting unconditionally once `lastLUSDLossError_Offset != 0` in the referenced report.
- If it silently wraps (typical release build), the overflow-consistency check is effectively neutralized (`base_value <= ~u128::MAX` is nearly always true), meaning the validator can incorrectly treat a speculative aggregator/delayed-field result as invalid (perpetually forcing failure/re-validation) or, depending on the surrounding control flow, accept a result that violates the intended commutativity/overflow invariant — corrupting the semantics that keep parallel execution results consistent with sequential VM execution.

### Likelihood Explanation
The triggering condition — a Move transaction calling an aggregator/delayed-field `try_add` with a delta value larger than the aggregator's configured `max_value` — is an ordinary, unprivileged operation reachable by any user of aggregator-based Move code (coin supply counters, concurrent counters, etc.). No special permissions are required; the aggregator only needs an overflow to occur once during speculative parallel execution, which BlockSTM performs routinely.

### Recommendation
Replace the unchecked subtraction with a saturating/checked variant, treating `min_overflow_positive_delta > max_value` as an unconditional overflow case:
```rust
if let Some(min_overflow_positive_delta) = self.min_overflow_positive_delta {
    if min_overflow_positive_delta > max_value
        || base_value <= max_value - min_overflow_positive_delta
    {
        return Err(...);
    }
}
```
or use `max_value.checked_sub(min_overflow_positive_delta)` and treat `None` as "always overflow" (skip/short-circuit consistent with the constraint that a delta already known to exceed `max_value` always overflows regardless of `base_value`).

### Proof of Concept
1. Create/observe an aggregator with `max_value = 100`.
2. During speculative execution of a transaction, call `try_add` with `delta = 950` (or any value `> max_value`). `BoundedMath::unsigned_add` returns `Err(Overflow)` as shown by the unit test at `bounded_math.rs:167-170`.
3. The caller records this via `DeltaHistory::record_overflow(950)`, setting `min_overflow_positive_delta = Some(950)`.
4. On commit/validation, `validate_against_base_value(base_value, 100)` is invoked. At `delta_math.rs:175`, `max_value - min_overflow_positive_delta` computes `100 - 950`, underflowing `u128` — panicking in checked builds, or wrapping to `u128::MAX - 849` in release builds and neutralizing the overflow-consistency check.

**Uncertainty note:** I was not able to fully trace, within the available iterations, the exact call site in `aptos-move/aptos-aggregator/src/delayed_field_extension.rs` that invokes `record_overflow`/`record_underflow` with the raw Move-supplied delta (grep confirmed `try_add`/`try_sub` references there but I did not read the file body). The core arithmetic flaw and its reachability via `BoundedMath::unsigned_add_delta` returning `Overflow` for deltas far exceeding `max_value` is directly confirmed in `bounded_math.rs` and `delta_math.rs`, but confirming the precise production call path from Move bytecode into `record_overflow` would benefit from further review of `delayed_field_extension.rs`.
