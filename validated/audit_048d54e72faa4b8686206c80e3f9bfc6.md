### Title
Unbounded `contract.getTypeValue()` used as array index in `WalletUtil.checkPermissionOperations` can throw uncaught `IndexOutOfBoundsException` instead of `PermissionException` - (File: chainbase/src/main/java/org/tron/common/utils/WalletUtil.java)

### Finding Description
`WalletUtil.checkPermissionOperations` reads `contract.getTypeValue()` directly from the wire-level protobuf `Contract.type` field and uses it unchecked as a bit index into the fixed 32-byte `operations` bitmap: [1](#0-0) 

Because `getTypeValue()` (not `getType()`) is used, the enum-mapping step is skipped entirely — protobuf3 allows any int32 value to be carried on the wire for an enum field, and `getTypeValue()` returns that raw integer even for values with no corresponding `ContractType` constant. If `contractType >= 256`, `contractType / 8 >= 32`, which is out of bounds for the 32-byte `operations` `ByteString`, and `operations.byteAt(...)` throws an unchecked `IndexOutOfBoundsException` rather than the intended `PermissionException`.

The account-side guard in `AccountPermissionUpdateActuator.checkPermission` only validates that bits set in the *stored* `operations` bitmap correspond to types recognized in `dynamicStore.getAvailableContractType()` at permission-creation time: [2](#0-1) 

This only constrains what the *account owner* may configure in the 256-bit operations mask; it does nothing to constrain the `type` field of a *later, unrelated* transaction that gets checked against that mask. The bound violation is caused entirely by the incoming transaction's contract type, which is attacker (transaction submitter) controlled data, not by the permission's own configuration.

### Impact Explanation
An unhandled `IndexOutOfBoundsException` thrown from deep inside permission-checking logic, if not caught by a generic top-level handler in the transaction-processing/broadcast path, can abort processing of that transaction ungracefully instead of yielding a clean validation failure. Scoped impact is limited to breaking the "availability invariant" for validation of a maliciously-crafted, out-of-range-type contract targeting a specific account with a non-default (permission_id != 0) Active permission — this is a code-quality/robustness defect (missing input bound-check before array indexing) rather than a broader consensus or fund-safety issue.

### Likelihood Explanation
Confirmed with certainty: `checkPermissionOperations` performs no range check on `contractType` before dividing by 8 and indexing into `operations`, so any `Contract.type` value ≥ 256 will deterministically trigger an out-of-bounds read. What I could **not** fully verify within the available tool budget is the exact call order in `TransactionCapsule` (specifically whether `validateSignature`/permission-checking against `checkPermissionOperations` is reached before or after any earlier code path rejects unrecognized/unsupported `ContractType` values, e.g. via `ActuatorFactory` dispatch or `TransactionUtil.validContractProto`). If an earlier validation step in `TransactionCapsule` or `Manager.pushTransaction` rejects any contract whose `type` doesn't map to a known, supported `ContractType` before reaching the permission-check step, this bug would be unreachable from the described entrypoint (an out-of-range type transaction would never get this far). I was unable to confirm this ordering because `TransactionCapsule.java` could not be fully read before the iteration budget was exhausted.

### Recommendation
In `WalletUtil.checkPermissionOperations`, validate `contractType` is within `[0, operations.size() * 8)` before indexing, and throw a `PermissionException` (or equivalent `ContractValidateException`) for out-of-range values instead of letting an `IndexOutOfBoundsException` propagate:
```java
int contractType = contract.getTypeValue();
if (contractType < 0 || contractType / 8 >= operations.size()) {
  throw new PermissionException("contract type " + contractType + " is not supported");
}
```

```java

@Test
public void testCheckPermissionOperationsOutOfRangeType() {
  Permission permission = Permission.newBuilder()
      .setOperations(ByteString.copyFrom(new byte[32])) // all-zero, size 32 as required
      .build();
  Transaction.Contract contract = Transaction.Contract.newBuilder()
      .setTypeValue(300) // no corresponding ContractType enum constant, unrecognized on wire
      .build();

  // Expected: PermissionException should be thrown for an unsupported/out-of-range type
  // Actual (bug): java.lang.IndexOutOfBoundsException is thrown by ByteString.byteAt
  assertThrows(PermissionException.class,
      () -> WalletUtil.checkPermissionOperations(permission, contract));
}
```
Given the uncertainty noted above about whether an earlier validation stage in `TransactionCapsule`/`Manager` filters out unrecognized contract types before this code is reached, a full end-to-end reproduction would additionally require: (1) an account owner submitting `AccountPermissionUpdateContract` to set a non-zero-`permissionId` Active permission on their own account, then (2) crafting a raw serialized `Transaction` (e.g. via a raw-broadcast API bypassing protobuf enum-level construction) whose `Contract.type` field is set to 300, and asserting that `TransactionCapsule.validateSignature` (or wherever `checkPermissionOperations` is invoked) surfaces a `PermissionException`/`ContractValidateException` rather than an unhandled `IndexOutOfBoundsException`.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
