Based on the investigation, I found a genuine analog to the reported bug class — an inconsistent/incomplete verification check in a proof-binding path, but in the Aptos backup/restore verification code rather than in an on-chain RNG auction.

### Title
`EpochHistory::verify_ledger_info` silently skips ledger-info signature/chain verification for epochs beyond the loaded epoch history, allowing unverified `LedgerInfoWithSignatures` to anchor transaction and state-snapshot restore - (File: `storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
`EpochHistory::verify_ledger_info` is the function used during backup restore to authenticate the `LedgerInfoWithSignatures` that anchors both transaction-chunk restoration and state-snapshot restoration. When the ledger info's epoch is greater than the number of epoch-ending records currently loaded into `EpochHistory`, the function does **not** perform any signature/consistency check — it logs a warning and returns `Ok(())` unconditionally, exactly the kind of check inconsistency described in the seed report (a guard that fails to account for all code paths that should be gated by the same invariant).

This function is the sole authentication gate for two critical restore paths:
- Transaction restore, where the untrusted backup's `LedgerInfoWithSignatures` is used to verify a `TransactionAccumulatorRangeProof` covering the actual transactions/write-sets being restored: [2](#0-1) 
- State-snapshot restore, where the same ledger info's accumulator/state-checkpoint hash is trusted to validate the restored state root: [3](#0-2) 

In both call sites, `epoch_history.verify_ledger_info(&li)` is treated as the trust anchor before the code proceeds to trust `li.ledger_info()`'s accumulator hash / state-checkpoint hash for verifying the proof of the actual restored data. But `verify_ledger_info` only performs real cryptographic verification (against a trusted waypoint, or against the previous epoch's `next_epoch_state` quorum-certified validator set) when `epoch <= self.epoch_endings.len()`. If the epoch of the ledger info being restored exceeds the number of epoch-ending records the `EpochHistory` was built with (e.g., because `skip_epoch_endings` was used, epoch-ending backups don't fully cover the target range, or the epoch-ending records loaded stop short of the transaction chunk being processed), the function silently succeeds without ever checking validator signatures or chaining to a trusted epoch state.

Since `TransactionAccumulatorRangeProof::verify` and `TransactionInfoWithProof::verify` only prove *internal consistency* between the given transactions and the given `LedgerInfo`'s root hash — they do not prove the `LedgerInfo` itself is authentic — skipping `verify_ledger_info`'s actual signature check means the restore pipeline will accept an arbitrary, attacker-supplied `LedgerInfoWithSignatures` (with an attacker-chosen accumulator root hash and matching attacker-chosen write-sets/transactions) as if it were a real, consensus-committed ledger state.

### Impact Explanation
An operator restoring a node from a compromised or malicious backup storage backend (`BackupStorage` trait implementation, e.g., a shared/public S3 bucket or third-party snapshot service) can have completely fabricated transactions, write-sets, and state values committed into the restored `AptosDB` as though they were authentic, consensus-verified ledger history, whenever the restored chunk's epoch is not covered by the epoch-ending records that were loaded (a normal/expected condition when using `--skip-epoch-endings`, partial epoch ranges, or replay-only restores). This corrupts durable ledger data at the storage layer — a state-commitment integrity violation matching the "Committed state that differs from the correct VM result or corrupts durable ledger data" and "wrong accumulator root ... accepted as valid" categories. If the node subsequently serves API requests or proofs from this restored DB before fully catching up via consensus-verified state sync, it would serve corrupted, wrongly-authenticated data.

### Likelihood Explanation
This is gated by the operator's choice to use `skip_epoch_endings` or a target range where epoch-ending records don't extend through the restore range — both are documented, ordinarily-used options in `RestoreCoordinator` (see `self.skip_epoch_endings`, `storage/backup/backup-cli/src/coordinators/restore.rs`), so the "epoch too new" branch is readily reachable in real restore operations, not merely a theoretical edge case. Exploitation requires control over (or a compromise of) the backup storage the operator points their restore tool at, which is a realistic threat model for public/third-party snapshot services. The code's own `TODO(aldenhu): fix this from upper level` comment confirms this is a known-unresolved gap.

### Recommendation
`verify_ledger_info` should never unconditionally return `Ok(())` when it cannot verify. Instead, when `epoch > self.epoch_endings.len()`, it should either: (1) return an error and halt the restore step so the caller can obtain more epoch-ending backups before proceeding, or (2) explicitly track that the ledger info is "unverified" and refuse to use its accumulator/state-checkpoint hash to authenticate the transaction/state data being restored, forcing the caller to source verification from another trusted anchor (e.g., a `trusted_waypoint` for that exact version) before trusting the chunk.

### Proof of Concept
1. An attacker controls (or compromises) the `BackupStorage` backend used by `TransactionRestoreController`/`StateSnapshotRestoreController`.
2. The operator restores using `--skip-epoch-endings` or a target range whose loaded `EpochHistory.epoch_endings` doesn't reach the epoch of the transaction chunk / state snapshot being restored (see `storage/backup/backup-cli/src/coordinators/restore.rs` lines 219-231, 289-300, where `epoch_history` may legitimately have fewer entries than needed).
3. The attacker crafts a `TransactionChunk`'s proof file containing an arbitrary `LedgerInfoWithSignatures` (any signatures, even garbage) whose accumulator hash matches attacker-chosen fabricated transactions/write-sets, per [2](#0-1) .
4. `LoadedChunk::load` calls `epoch_history.verify_ledger_info(&ledger_info)`; because `epoch > self.epoch_endings.len()`, this returns `Ok(())` without checking any signature.
5. `txn_list_with_proof.verify(ledger_info.ledger_info(), ...)` succeeds because it only checks the transactions are consistent with the (forged) ledger info's own accumulator hash.
6. The fabricated transactions/write-sets are committed to the restored `AptosDB` as authentic ledger history.

impl EpochHistory {
    pub fn verify_ledger_info(&self, li_with_sigs: &LedgerInfoWithSignatures) -> Result<()> {
        let epoch = li_with_sigs.ledger_info().epoch();
        ensure!(!self.epoch_endings.is_empty(), "Empty epoch history.",);
        if epoch > self.epoch_endings.len() as u64 {
            // TODO(aldenhu): fix this from upper level
            warn!(
                epoch = epoch,
                epoch_history_until = self.epoch_endings.len(),
                "Epoch is too new and can't be verified. Previous chunks are verified and node \
                won't be able to start if this data is malicious."
            );
            return Ok(());
        }
        if epoch == 0 {
            ensure!(
                li_with_sigs.ledger_info() == &self.epoch_endings[0],
                "Genesis epoch LedgerInfo info doesn't match.",
            );
        } else if let Some(wp_trusted) = self
            .trusted_waypoints
            .get(&li_with_sigs.ledger_info().version())
        {
            let wp_li = Waypoint::new_any(li_with_sigs.ledger_info());
            ensure!(
                *wp_trusted == wp_li,
                "Waypoints don't match. In backup: {}, trusted: {}",
                wp_li,
                wp_trusted,
            );
        } else {
            self.epoch_endings[epoch as usize - 1]
                .next_epoch_state()
                .ok_or_else(|| anyhow!("Shouldn't contain non- epoch bumping LIs."))?
                .verify(li_with_sigs)?;
        };
        Ok(())
    }
