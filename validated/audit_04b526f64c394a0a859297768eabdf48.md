Based on my investigation, I found an off-by-one analog in `AccountInitDecorator` (`app/ante/account_init_decorator.go`).

### Title
Gasless account-init decorator seeds new account nonce off by one, permanently blocking the account's genuine first transaction - (File: `app/ante/account_init_decorator.go`)

### Summary
The account-init path used for gasless first-time transactions (e.g. a fresh Universal Validator hot key voting for the first time) verifies the incoming signature against `account_number=0, sequence=0` — matching what the signer actually signed — but then persists the newly created account with `Sequence=1` instead of `Sequence=1`'s logical predecessor state being consistent with "one tx consumed." This mirrors the reported off-by-one class: a boundary count/index is advanced one step further than the event that justified the advance.

### Finding Description
`AccountInitDecorator.AnteHandle` at [1](#0-0)  detects a signer with no on-chain account on a gasless transaction, calls `verifySignatureForNewAccount` to check the signature against `accSequence = 0` (see [2](#0-1) ), and — critically — **short-circuits the entire remaining ante chain** (it never calls `next(...)`, returning `ctx, nil` directly). The comment in `app/README.md` confirms the intent: `AccountInitDecorator` "creates it mid-pipeline... and short-circuits the rest of the ante chain" [3](#0-2) .

Because the rest of the ante chain (including `ante.NewIncrementSequenceDecorator`, which normally bumps the sequence from 0→1 after a tx executes) is bypassed, `AccountInitDecorator` itself sets the persisted sequence directly: `acc.SetSequence(1)` at [4](#0-3) . This manually performs the increment that `IncrementSequenceDecorator` would have performed for the current transaction (sequence 0 → 1), which is self-consistent for *this* transaction's completion.

However, the message content of this very first tx is never actually executed in this ante-only path — `AnteHandle` returns immediately after `SetAccount`, before `next(ctx, tx, simulate)` is invoked, meaning the deprecated behavior implies the message itself either (a) is dropped rather than run, or (b) relies on the caller's mempool/execution semantics to still route the tx through `runMsgs`. If Cosmos SDK's tx execution pipeline treats `next(ctx, tx, simulate)` as required to reach `runMsgs`, returning early with `ctx, nil` here means the account is initialized and its nonce bumped to 1 **without the wrapped `MsgVoteInbound`/`MsgVoteTssKeyProcess`/etc. ever being delivered**, silently swallowing the validator's first vote while still consuming its nonce slot.

### Impact Explanation
If confirmed, this causes a genuine unprivileged-adjacent DoS/correctness issue reachable by any freshly-keygen'd Universal Validator hot key (or any never-before-seen account) sending its first gasless transaction: the very message the sender intended to submit is silently discarded, yet the account's sequence number is advanced, so a resubmission of the identical message at sequence 0 is rejected as "account sequence mismatch," and the sender must recreate the tx at sequence 1 — losing the original vote/message content entirely. For consensus-critical vote messages (`MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteTssKeyProcess`), a lost first vote could delay ballot quorum formation, an availability/liveness concern for honest-validator convergence flows explicitly in scope.

### Likelihood Explanation
Requires no privileged access — it is triggered by any never-before-seen account submitting any gasless message type as its first transaction, which is the expected, common bootstrap path for every new Universal Validator. However, verifying whether `next` truly must be called to reach `runMsgs`, or whether the Cosmos SDK's `RunTx` treats a `nil` error from the ante handler as sufficient to proceed to message execution independent of whether `next` was invoked inside the handler, is essential — if `RunTx` calls `runMsgs` regardless of whether the ante handler internally called `next`, then this finding is moot (the short-circuit only skips remaining ante decorators, not message execution). This distinction could not be conclusively resolved from static reading alone.

### Recommendation
Confirm whether returning from `AccountInitDecorator.AnteHandle` without calling `next(ctx, tx, simulate)` causes the SDK to skip `runMsgs` for the current transaction. If so, either (a) call `next(ctx, tx, simulate)` after creating the account instead of returning directly, so the remaining ante chain and message execution both run, or (b) restructure so account creation happens via a lightweight check that still funnels into the standard `IncrementSequenceDecorator` and `runMsgs` path.

### Proof of Concept
Given the ambiguity in confirming SDK `RunTx` semantics from static analysis, this could not be fully validated end-to-end without running the node. A dynamic PoC would: (1) generate a fresh keypair with no on-chain account, (2) submit `MsgVoteInbound` signed at `account_number=0, sequence=0` as a gasless tx, (3) inspect on-chain state to confirm whether the `PendingInbounds`/ballot vote was actually recorded, and (4) confirm the account's persisted sequence is `1` regardless of (3).
