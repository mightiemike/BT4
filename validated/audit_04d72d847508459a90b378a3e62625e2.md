### Title
Reflected HTML/script injection via `dangerouslySetInnerHTML={{__html: error.data}}` in `boundary.error` helper - (File: `packages/apps/shopify-app-remix/src/server/boundary/error.tsx` and `packages/apps/shopify-app-react-router/src/server/boundary/error.tsx`)

### Summary
Both `shopify-app-remix` and `shopify-app-react-router` ship an `errorBoundary` helper (`boundary.error`) that renders a thrown route `ErrorResponse`'s `.data` field directly into the DOM via `dangerouslySetInnerHTML`, with no validation, escaping, or type check on the content. [1](#0-0) [2](#0-1) 

### Finding Description
This is structurally the same bug class as the reported `img.initia.xyz` issue: an unfiltered, attacker-influenceable string is bound directly to a raw-HTML rendering sink without sanitization. Here, instead of an `<img src>`, the sink is React's `dangerouslySetInnerHTML`:

```tsx
export function errorBoundary(error: any) {
  if (
    error.constructor.name === 'ErrorResponse' ||
    error.constructor.name === 'ErrorResponseImpl'
  ) {
    return (
      <div
        dangerouslySetInnerHTML={{__html: error.data || 'Handling response'}}
      />
    );
  }
  throw error;
}
``` [1](#0-0) 

This helper is documented and intended for app developers to call from `ErrorBoundary` components as `boundary.error(useRouteError())`, per the package's own examples. [3](#0-2) 

`error.data` is populated from whatever body was passed to a thrown React Router/Remix `Response`/`data()` call anywhere in the route tree (loaders, actions, or nested layouts) that produced the caught `ErrorResponse`. Any code path — application code or third-party middleware — that throws a `Response` whose body reflects request-controlled content (query params, form data, headers, etc.) will have that content rendered as **raw HTML** by this helper, with no whitelisting of tags/schemes and no escaping, exactly analogous to the reported proxy accepting an unfiltered `data:text/html;base64,...` payload and rendering it verbatim.

I confirmed (from what I could search) that the library's own internal auth/webhook/app-proxy handlers throw `Response` objects in many places (`auth-code-flow.ts`, `webhooks/authenticate.ts`, `appProxy/authenticate.ts`, `validate-shop-and-host-params.ts`, etc.), but I was not able to fully verify from the indexed code whether any of those internal throws place raw, unsanitized request-controlled data into the `Response` body (as opposed to static messages). This is a limitation of the codebase index used for this analysis — a full audit of every `throw new Response(...)` call site across the auth/webhook/app-proxy/billing modules would be needed to conclusively prove first-party reachability with attacker data in the body.

### Impact Explanation
If any thrown `Response` body anywhere in an app's route tree (including future/third-party library additions, or app developer loaders that follow the documented pattern) reflects request input into its body, calling `boundary.error(useRouteError())` — the officially recommended pattern — will execute that content as HTML/JS in the merchant's browser inside the embedded app iframe. This could lead to session token theft, App Bridge action forgery, or other admin-context script execution, which is High impact if reachable, consistent with the original report's severity rating.

### Likelihood Explanation
Likelihood is Low-to-Uncertain: exploitation requires a concrete call site (either in the library or in typical app code following the docs) that throws a `Response` with attacker-controlled body content. I could not confirm such a call site exists in the current shopify-app-js codebase from what was indexed; the sink itself is unconditionally unsafe, but a source feeding it attacker data was not conclusively located within the auth/webhook/app-proxy/session paths reachable from anonymous requests.

### Recommendation
- Change `errorBoundary` to render `error.data` as text content (e.g., via `{error.data}` in JSX, which is auto-escaped) rather than `dangerouslySetInnerHTML`, unless HTML rendering is a hard requirement.
- If HTML rendering must be preserved for legitimate use cases, sanitize `error.data` with a strict allow-list HTML sanitizer (e.g., DOMPurify) before binding it to `dangerouslySetInnerHTML`.
- Audit all internal `throw new Response(...)` call sites in `packages/apps/shopify-app-remix/src/server/authenticate/**` and `packages/apps/shopify-app-react-router/src/server/authenticate/**` to ensure none place raw request-controlled strings (query params, headers, shop/host values) into response bodies that could reach this boundary.
- Update the JSDoc/examples for `boundary.error` to explicitly warn against putting untrusted data into thrown `Response` bodies.

### Proof of Concept
Conceptual PoC (dependent on confirming a body-reflecting throw site, which was not verified in this analysis):
1. A route (library-internal or app-authored) throws `throw new Response(request.url.searchParams.get('somevalue'), {status: 400})` where `somevalue` is attacker-controlled.
2. The app's `ErrorBoundary` component calls `boundary.error(useRouteError())` as documented.
3. `errorBoundary` renders `error.data` (the raw query value) via `dangerouslySetInnerHTML`.
4. An attacker crafts a URL such as `?somevalue=<img src=x onerror=alert(document.cookie)>` to achieve script execution in the merchant's embedded-app session. [1](#0-0) [2](#0-1)
