### Title
Missing "zero-address" check on `to_address` in `TransferActuator`/`TransferAssetActuator` allows funds to be sent to an unspendable address - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
The EthBridge report flags that `depositERC20To`'s `_to` parameter is not checked against `address(0)`, allowing deposited tokens to be sent to an address that can never be controlled/withdrawn from. The analogous pattern exists in java-tron's core TRX/TRC10 transfer actuators: `DecodeUtil.addressValid()` only validates address length and the network prefix byte, never that the remaining 20 bytes are non-zero, so a transaction with `to_address = 0x41 + 20×0x00` is accepted as "valid."

### Finding Description
`DecodeUtil.addressValid` performs only two checks — array length and prefix byte — and does not reject an address whose 20-byte payload is all zeros: [1](#0-0) 

`TransferActuator.validate()` and `TransferActuator.execute()` rely solely on this check (plus a same-address check against `ownerAddress`) before creating a brand-new account at `toAddress` and crediting it with the transferred balance: [2](#0-1) [3](#0-2) 

`TransferAssetActuator` (TRC10 token transfer) exhibits the identical pattern — `DecodeUtil.addressValid(toAddress)` plus an owner/self check, with no rejection of the all-zero payload address — and will silently create a new account holding the asset balance at that unspendable address: [4](#0-3) [5](#0-4) 

No java-tron address (e.g., `0x41` followed by 20 zero bytes) has, or can plausibly have, a discoverable ECDSA private key, so any TRX or TRC10 balance sent there is permanently unspendable/unrecoverable — functionally equivalent to the EthBridge "deposited but unable to receive" scenario.

### Impact Explanation
Any anonymous user can broadcast a `TransferContract` or `TransferAssetContract` transaction with `to_address` set to the zero-payload address and have it accepted by the network without error. This can lead to permanent, irreversible loss of TRX or TRC10 token balance for whoever holds the funds (self-inflicted by the signer, or via a wallet/exchange bug that fails to filter this address before broadcasting). This is a fund-loss/accounting-corruption class issue (assets become permanently locked at an address nobody controls), reachable directly through a normal broadcast transaction — no privileged role required.

### Likelihood Explanation
Likelihood is moderate: the transaction is trivially constructible by anyone and always succeeds because `validate()` never special-cases the zero-payload address, so it is easy to trigger, whether accidentally (fat-fingered/malformed integration) or via a malicious script tricking a service into transferring to this fixed address. However, actual loss requires a signer to (deliberately or by bug) choose this specific degenerate address, so real-world occurrence is lower than for more commonly-mistyped addresses.

### Recommendation
Add an explicit check in `TransferActuator.validate()` and `TransferAssetActuator.validate()` (and any other actuator that accepts a caller-supplied destination address, such as `DelegateResourceActuator`/`UnfreezeBalanceActuator`'s `receiver_address`) rejecting an all-zero 20-byte payload in addition to the existing `DecodeUtil.addressValid()` length/prefix check, e.g. reject `toAddress` when `Arrays.equals(toAddress, new byte[]{addressPreFixByte, 0,0,...,0})`, mirroring the pattern already used for the self-transfer check (`Arrays.equals(toAddress, ownerAddress)`).

### Proof of Concept
1. Construct a `TransferContract` with `owner_address` = a funded account and `to_address` = `0x41` followed by 20 zero bytes (a syntactically valid but keyless address).
2. Sign and broadcast the transaction via the gRPC/HTTP API.
3. `TransferActuator.validate()` passes (`DecodeUtil.addressValid` returns true, and `toAddress != ownerAddress`), so `execute()` runs, creates a new account at the zero-payload address, and credits it with the transferred TRX.
4. The funds are now held at an address with no corresponding private key and can never be spent or recovered. The same PoC applies to `TransferAssetActuator` for TRC10 tokens. [1](#0-0) [6](#0-5) [7](#0-6)

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
