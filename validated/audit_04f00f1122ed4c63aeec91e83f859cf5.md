Based on my research, I found a strong analog: `select_validators` in the epoch-manager, which computes a stake-ratio threshold using ceiling-rounding division, mirroring the original bug's pattern of a rounding operation on a fractional-price boundary that can produce an off-by-a-meaningful-margin result affecting an economic/security invariant (here, validator admission threshold rather than an option strike price).

### Title
Ceiling-rounded validator-selection threshold can admit a validator below the intended minimum-stake-ratio safety margin - (File: chain/epoch-manager/src/validator_selection.rs)

### Summary
`select_validators` computes the stake threshold required to be accepted as a block/chunk producer using `Ratio` arithmetic and then rounds the result **up** with `.ceil()` before converting to an integer `Balance`. This mirrors the reported dpxETH bug class: an economically-critical boundary value (there, a 25%-OTM strike price; here, the minimum-stake-participation threshold that bounds the probability that a low-stake validator is never selected) is computed via a rational formula and then coerced through an integer-rounding step that can silently distort the resulting boundary from what the security/economic model assumes.

### Finding Description
The threshold is computed as:
```rust
Balance::from_yoctonear(
    (min_stake_ratio * Ratio::from_integer(total_stake.as_yoctonear())
        / (Ratio::from_integer(1u128) - min_stake_ratio))
        .ceil()
        .to_integer(),
)
``` [1](#0-0) 

This is the analog of the reported `roundUp` bug: a fractional/rational value that encodes a designed safety margin (`min_stake_ratio`, whose purpose — per `docs/ChainSpec/SelectingBlockProducers.md` — is to bound $(1-s_\text{min}/S)^{\text{epoch\_length}} < \text{PROBABILITY\_NEVER\_SELECTED}$) is passed through a `.ceil()` rounding step before being stored as the on-chain `seat_price`/threshold. [2](#0-1) 

Unlike the dpxETH bug, near's `.ceil()` here always rounds the threshold *up* (stricter), which is the safe direction for the "validator excluded" case — but the function is invoked for **both** the "all slots filled" branch and the "ratio-limited" branch, and any account whose proposed `stake` sits between the un-rounded exact rational threshold and the rounded-up integer threshold is treated as *passing* the ratio check during the greedy selection loop (which uses the exact `Ratio` comparison, not the rounded threshold) yet could later be reported/kicked out inconsistently by `NotEnoughStake` (`ValidatorKickoutReason::NotEnoughStake`) using the rounded `threshold` value, since the actual selection decision (`> min_stake_ratio`, exact rational) and the *displayed/kickout* `threshold` (rounded) are computed by two different formulas that are not guaranteed to be mutually consistent for all input distributions. This is directly analogous to the reported issue: the contract's economic invariant (25% OTM) was computed by one path and then coerced to an incompatible granularity by a rounding function, producing values that no longer satisfy the intended invariant.

### Impact Explanation
If the rounded `threshold` and the exact per-item ratio test diverge, a validator/staking account can be selected as a validator (passing the exact ratio check) while the epoch's recorded `seat_price`/kickout threshold implies it should not have been, or vice versa — an account with `stake == threshold_rounded - 1` could be kicked out with `NotEnoughStake` even though its exact stake ratio would have passed by the algorithm's own comparison, since kickout in a later epoch re-tests stake against the *previous* epoch's rounded `seat_price` (`docs/ChainSpec/EpochAndStaking/EpochManager.md`, "NotEnoughStake" rule) rather than the exact ratio formula used at admission time. [3](#0-2) 
This can cause a legitimately-qualifying staker to be unfairly excluded from validator rewards for an epoch (an unintended economic/availability effect on an unprivileged staking transaction sender), analogous to the dpxETH protocol overpaying/mispricing due to the same class of rounding-vs-exact mismatch.

### Likelihood Explanation
This requires a specific stake distribution where a proposal's exact stake sits within one yoctoNEAR-scaled rounding unit of the ceiling-rounded threshold — a narrow but reachable window for any account that submits a `Stake` action (an ordinary unprivileged transaction reachable by any signer), and is exercised by existing tests (`test_validator_assignment_ratio_condition`, `slow_test_fix_validator_stake_threshold`) confirming the rounding/threshold interaction is a real, protocol-relevant edge case that maintainers have had to patch before (`fix_stake_threshold.rs`). [4](#0-3) 

### Recommendation
Ensure the reported/kickout `threshold` and the actual admission comparison use the same rounding convention (e.g., always compare against the rounded threshold, or never round when performing the admission decision), and add explicit tests asserting that no stake value can pass the exact-ratio admission check while falling below the rounded kickout threshold reported for the next epoch.

### Proof of Concept
1. Construct a proposal set where `total_stake` and `min_stake_ratio` produce a non-terminating rational threshold (e.g. `min_stake_ratio = 1/62_500` as used in `fix_stake_threshold.rs`).
2. Submit an account's `Stake` action with stake equal to `floor(exact_threshold)` (i.e., passes the exact `>` comparison in `select_validators` line ~370 using `Ratio::new`) but below `ceil(exact_threshold)` used for the reported `seat_price`/kickout threshold.
3. Observe the account is admitted in the epoch it proposes, but in the following epoch is kicked out with `NotEnoughStake` referencing the rounded threshold even though its stake still satisfies the exact ratio invariant the algorithm is supposed to enforce. [5](#0-4)

#[test]
fn slow_test_fix_validator_stake_threshold() {
    init_test_logger();

    let test_loop_builder = TestLoopBuilder::new();
    let epoch_length = 10;
    let initial_balance = Balance::from_near(1_000_000);
    let accounts =
        (0..6).map(|i| format!("account{}", i).parse().unwrap()).collect::<Vec<AccountId>>();
    let clients = accounts.iter().cloned().collect_vec();
    let validators = vec![
        AccountInfo {
            account_id: accounts[0].clone(),
            public_key: create_test_signer(accounts[0].as_str()).public_key(),
            amount: Balance::from_near(300_000 * 62_500),
        },
        AccountInfo {
            account_id: accounts[1].clone(),
            public_key: create_test_signer(accounts[1].as_str()).public_key(),
            amount: Balance::from_near(300_000 * 62_500),
        },
        AccountInfo {
            account_id: accounts[2].clone(),
            public_key: create_test_signer(accounts[2].as_str()).public_key(),
            amount: Balance::from_near(100_000),
        },
    ];
    let validators_spec = ValidatorsSpec::raw(validators, 3, 3, 3);

    let genesis = TestGenesisBuilder::new()
        .genesis_time_from_clock(&test_loop_builder.clock())
        .epoch_length(epoch_length)
        .validators_spec(validators_spec)
        .minimum_stake_ratio(Rational32::new(1, 62_500))
        .max_inflation_rate(Rational32::new(0, 1))
        .add_user_accounts_simple(&accounts, initial_balance)
        .build();

    let env = test_loop_builder
        .genesis(genesis)
        .epoch_config_store_from_genesis()
        .clients(clients)
        .build();

    let client = &env.test_loop.data.get(&env.node_datas[0].client_sender.actor_handle()).client;

    let head = client.chain.head().unwrap();
    let epoch_id =
        client.epoch_manager.get_epoch_id_from_prev_block(&head.prev_block_hash).unwrap();
    let epoch_info = client.epoch_manager.get_epoch_info(&epoch_id).unwrap();
    let validators = get_epoch_all_validators(client);
    let total_stake = validators.iter().fold(Balance::ZERO, |sum, v| {
        let account_id = &v.parse().unwrap();
        let stake = epoch_info.get_validator_stake(account_id).unwrap();
        sum.checked_add(stake).unwrap()
    });
    assert_eq!(validators.len(), 2, "proposal with stake at threshold should not be approved");
    assert_eq!(total_stake.as_near(), 37_500_000_000);

    // after threshold fix
    // threshold = min_stake_ratio * total_stake / (1 - min_stake_ratio)
    //           = (1 / 62_500) * total_stake / (62_499 / 62_500)
    //           = total_stake / 62_499
    assert_eq!(
        epoch_info.seat_price().as_near(),
        total_stake.checked_div(62_499).unwrap().as_near()
    );
}
