## Finding: `TransactionOutput::ensure_match_transaction_info` skips state-root verification, silently accepting corrupted state roots during replay-verify

### Title
Replay-verify integrity check omits state/hot-state checkpoint hash comparison, allowing a corrupted state root to pass verification - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-response comparator used by replay/verify tooling (`db-tool replay-on-archive` and `aptos-debugger`) to confirm that a freshly re-executed transaction output matches the transaction info that was actually committed on-chain. The function validates status, gas, write-set hash (`state_change_hash`), and event root hash, but explicitly and knowingly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that authenticate the Sparse Merkle Tree root of world state at checkpoints.

### Finding Description
`ensure_match_transaction_info` checks: [1](#0-0) 

But then explicitly stops, with the code's own comment acknowledging the gap: [2](#0-1) 

The comment states verbatim: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole correctness gate used by the replay-verify path: [3](#0-2) 

`TransactionInfo` carries `state_checkpoint_hash` as the Sparse Merkle Tree root committed to the ledger accumulator: [4](#0-3) [5](#0-4) 

Because the comparator never re-derives and compares the actual state-checkpoint root produced by re-execution against the historically-committed `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, any divergence in world-state root computation (e.g., from a VM bug, a storage/state-view bug, or a hard-fork execution semantics change) at a checkpoint boundary will not be detected by this tool. Only the write-set hash (`state_change_hash`, hash of the raw write set) and event root are checked — not the actual authenticated Merkle root of the resulting global state.

### Impact Explanation
The state checkpoint hash is the authenticated binding between a transaction's execution and the resulting global ledger state (the Sparse Merkle Tree root), ultimately anchoring into the block/ledger info that validators sign. This replay-verify tool exists specifically to catch state-commitment divergence between archived/committed data and re-execution — which is exactly the hard-fork/deterministic-replay integrity property the task asks about. With this check omitted, a state-root divergence bug (whether from a subtle VM/storage bug or an unintended non-determinism) would go undetected by the audit tool meant to catch it, i.e., corrupted/incorrect state roots are accepted as "verified" for a range of versions. This directly undermines confidence in the replay/restore integrity pipeline described in the "Proof And Storage Pivots" section.

### Likelihood Explanation
This is not a hypothetical: the code author left an explicit TODO documenting the exact scenario ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"), and gates the fix behind enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. The check is unconditionally skipped for every version processed by `replay_on_archive` and `aptos-debugger` today, regardless of feature flags, so the gap is live in the current codebase.

### Recommendation
In `ensure_match_transaction_info`, compute the resulting state checkpoint root(s) from the transaction output (when the transaction is a checkpoint) and assert equality with `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` where applicable) before returning `Ok(())`, rather than leaving the comparison as a TODO gated on an unrelated feature flag.

### Proof of Concept
Not directly exploitable by an external attacker to corrupt mainnet state (this is a verification-tool gap, not a consensus-path acceptance gap), but demonstrable statically: call `ensure_match_transaction_info` with a `TransactionOutput` whose write set/events match `txn_info` exactly, but where the underlying execution state view diverges from the archived value at a state-checkpoint boundary (differing `state_checkpoint_hash`). The function returns `Ok(()))` because lines 2197-2203 never compare these fields, so `replay_on_archive`'s `execute_and_verify` at [6](#0-5)  reports no failure despite the state root mismatch.
