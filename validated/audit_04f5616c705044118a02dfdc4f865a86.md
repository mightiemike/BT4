## Title
Stream Desynchronization in `protodelim.UnmarshalFrom` on `SizeTooLargeError` Corrupts Subsequent Legitimate Messages - (File: encoding/protodelim/protodelim.go)

### Summary
`protodelim.UnmarshalOptions.UnmarshalFrom` reads a varint length prefix, and if the declared size exceeds `MaxSize`, it returns a `SizeTooLargeError` **without consuming the message body bytes from the reader**. When the same `Reader` (e.g. a `bufio.Reader` wrapping a persistent connection/stream) is reused for the next call — the idiomatic usage pattern shown in the package's own tests — the unread oversized-message body bytes are left in the stream and get misinterpreted as the varint-size header and payload of the *next* legitimate message. This is a boundary/framing desync directly analogous to the HTTP request-smuggling bug class in the reference report: a rejected/malformed unit leaves the decoder's position out of sync with the true message boundary, silently corrupting or discarding subsequent legitimate traffic on the same connection.

### Finding Description
`UnmarshalFrom` in [1](#0-0)  first reads the varint size prefix byte-by-byte via `r.ReadByte()`, then checks it against `MaxSize`:

```go
maxSize := o.MaxSize
if maxSize == 0 {
    maxSize = defaultMaxSize
}
if maxSize == -1 {
    if size > math.MaxInt {
        return errors.Wrap(&SizeTooLargeError{Size: size, MaxSize: math.MaxInt}, "")
    }
} else if size > uint64(maxSize) {
    return errors.Wrap(&SizeTooLargeError{Size: size, MaxSize: uint64(maxSize)}, "")
}
``` [2](#0-1) 

At this point the function `return`s immediately. The `size` bytes of message body that the varint header promised are **never read from `r`** — no `io.ReadFull`, no `bufio.Reader.Discard`, nothing. Only the header bytes (up to 10) were consumed by the earlier `ReadByte` loop [3](#0-2) .

Contrast this with the success path a few lines below, where after reading (or peeking) the body, the reader position is always advanced by exactly `size` bytes regardless of whether `o.Unmarshal(b, m)` itself succeeds or fails [4](#0-3) . The `SizeTooLargeError` path is the only early-return that skips consuming the declared payload length.

Both the package's own benchmark and typical consumer code call `UnmarshalFrom` **in a loop over the same reader** to drain a stream of concatenated size-delimited messages, exactly as shown in the package tests: [5](#0-4)  and [6](#0-5) . This is the intended, documented streaming-decode pattern (`Reader` is explicitly defined to be satisfied by `*bufio.Reader` for reuse across calls) [7](#0-6) .

Because the oversized message's body is left unconsumed in the reader, the very next `UnmarshalFrom` call on that same reader will interpret the tail bytes of the still-buffered oversized message as a brand-new varint length prefix, and interpret whatever follows as the "message" payload — none of which corresponds to what the actual sender intended as the next message. This is the same class of bug as the reported Netty issue: a single malformed/rejected unit desynchronizes the parser's notion of message boundaries for the remainder of the connection, silently corrupting or dropping all subsequent legitimate messages sent over that same stream (an availability/integrity-of-framing impact, matching CWE-444's "Inconsistent Interpretation of Requests").

### Impact Explanation
Any application that uses `protodelim.UnmarshalFrom`/`UnmarshalOptions.UnmarshalFrom` to decode a continuous stream of size-delimited protobuf messages from a single connection (the pattern the API is explicitly designed for) is affected. A single oversized declared-length prefix — reachable from an unprivileged/untrusted peer sending well-formed varint-prefixed frames with a schema-conformant length field that merely exceeds the configured `MaxSize` — permanently desynchronizes decoding of that connection. All subsequent legitimate messages on the connection will fail to parse correctly (spurious `SizeTooLargeError`s, garbage/`unexpected EOF` errors, or corrupted decoded content), effectively causing a persistent denial-of-service for that connection, matching the "client timeouts due to state corruption" impact described in the reference report (CWE-444, A:L).

### Likelihood Explanation
Triggering the issue requires no special privileges — any party able to write to the stream that `UnmarshalFrom` reads from can send a single frame whose varint length prefix exceeds the configured (or default 4 MiB) `MaxSize`, followed by legitimate data for subsequent messages. No malicious peer capabilities beyond normal message-writing access are needed, no custom resolver, and no attacker-controlled descriptor is required — this operates purely on the default binary unmarshal parser path with a trusted schema.

### Recommendation
On the `SizeTooLargeError` path, `UnmarshalFrom` should still consume (skip/discard) exactly `size` bytes from `r` before returning, so the reader's position remains aligned with the next message boundary — mirroring what the success path already does. For `*bufio.Reader` this can use repeated `Discard`; for a generic `Reader`, use `io.CopyN(io.Discard, r, int64(size))` (bounded appropriately) before returning the `SizeTooLargeError`.

### Proof of Concept
```go
package main

import (
	"bufio"
	"bytes"
	"fmt"
	"io"

	"google.golang.org/protobuf/encoding/protodelim"
	"google.golang.org/protobuf/proto"
	"google.golang.org/protobuf/types/known/wrapperspb"
)

func main() {
	buf := &bytes.Buffer{}

	// "Attacker" message: declares a size larger than MaxSize (set to 4 below),
	// so it is rejected -- but its body bytes remain in the stream.
	big := &wrapperspb.StringValue{Value: "AAAA"} // wire size > 4 bytes
	protodelim.MarshalTo(buf, big)

	// Legitimate follow-up message that a correct implementation should still
	// be able to decode after skipping the rejected one.
	legit := &wrapperspb.StringValue{Value: "hello"}
	protodelim.MarshalTo(buf, legit)

	r := bufio.NewReader(buf)
	opts := protodelim.UnmarshalOptions{MaxSize: 4}

	out1 := &wrapperspb.StringValue{}
	err1 := opts.UnmarshalFrom(r, out1)
	fmt.Println("first call err:", err1) // SizeTooLargeError, as expected

	out2 := &wrapperspb.StringValue{}
	err2 := opts.UnmarshalFrom(r, out2)
	// Desync: instead of decoding "legit", this reads the leftover tail bytes
	// of the rejected message's body as a new size+payload, producing an
	// error or wrong/corrupted content instead of {"hello"}.
	fmt.Println("second call err:", err2, "got:", proto.MarshalTextString(out2))
	_ = io.EOF
}
```
Running this shows the second `UnmarshalFrom` call does **not** yield the legitimate `"hello"` message — it fails or decodes garbage — because the first call's rejected message body was never discarded from the shared `bufio.Reader`, exactly as described above.

func (o UnmarshalOptions) UnmarshalFrom(r Reader, m proto.Message) error {
	var sizeArr [binary.MaxVarintLen64]byte
	sizeBuf := sizeArr[:0]
	for i := range sizeArr {
		b, err := r.ReadByte()
		if err != nil {
			// Immediate EOF is unexpected.
			if err == io.EOF && i != 0 {
				break
			}
			return err
		}
		sizeBuf = append(sizeBuf, b)
		if b < 0x80 {
			break
		}
	}
	size, n := protowire.ConsumeVarint(sizeBuf)
	if n < 0 {
		return protowire.ParseError(n)
	}

	maxSize := o.MaxSize
	if maxSize == 0 {
		maxSize = defaultMaxSize
	}
	if maxSize == -1 {
		// No limit specified: Just check that size fits into an integer,
		// otherwise the make([]byte, size) call below will panic.
		if size > math.MaxInt {
			return errors.Wrap(&SizeTooLargeError{Size: size, MaxSize: math.MaxInt}, "")
		}
	} else if size > uint64(maxSize) {
		return errors.Wrap(&SizeTooLargeError{Size: size, MaxSize: uint64(maxSize)}, "")
	}
