### Title
Per-request QPS rate limiting on `/wallet/estimateenergy` ignores internal VM-execution amplification, allowing CPU-bound DoS within the nominal quota - ([File: framework/src/main/java/org/tron/core/services/http/EstimateEnergyServlet.java])

### Summary
`EstimateEnergyServlet` is protected only by `RateLimiterServlet`'s per-endpoint and global limiters, both of which are simple Guava `RateLimiter` token buckets that count one permit per HTTP request regardless of the computational cost the request will incur. Since `estimateenergy` performs an internal binary-search of full VM executions (multiple `TransactionTrace`/`runtime.execute()` calls per request, as established elsewhere in this review), an attacker who never exceeds the configured QPS can still drive far more aggregate VM/CPU work than the limiter was calibrated for.

### Finding Description
`RateLimiterServlet.service()` acquires exactly one permit per incoming HTTP request from the per-endpoint `IRateLimiter` (built via `buildAdapter`, defaulting to `DefaultBaseQqsAdapter`/`QpsRateLimiterAdapter` backed by `QpsStrategy`) and then one permit from `GlobalRateLimiter`, both of which are plain `com.google.common.util.concurrent.RateLimiter` token buckets keyed only on request count: [1](#0-0) [2](#0-1) [3](#0-2) 

Neither `RuntimeData` (the object passed into `acquirePermit`) nor the strategy classes inspect the request body/contract bytecode to weight the cost of the call; a `triggerconstantcontract` request and an `estimateenergy` request against a worst-case, deeply-branching, storage-heavy contract consume the identical single token. `EstimateEnergyServlet.doPost` then calls `wallet.estimateEnergy(...)`, which internally performs repeated full VM executions to binary-search the minimum energy — the amplification factor referenced in the sibling questions in this set. [4](#0-3) 

Because the rate limiter's unit of accounting is "requests admitted," not "VM-execution units consumed," an attacker operating exactly at the documented/configured QPS for this endpoint can still saturate node CPU by ensuring every admitted request maximizes the internal binary-search iteration count, since the limiter provides no mechanism to detect or throttle on the actual execution cost.

### Impact Explanation
This is a DoS-via-RPC-API class impact: sustained CPU exhaustion on FullNode/SolidityNode HTTP API instances while the node operator's rate-limiting configuration nominally appears to bound request throughput. Because energy/bandwidth accounting does not apply to `estimateenergy` (it is a read-only/local call, not a broadcast transaction), there is no additional economic cost gating repeated calls beyond the QPS quota itself, so the only throttle in place is the request-count-based limiter shown above, which is exactly what the question identifies as failing to account for the amplification factor.

### Likelihood Explanation
The precondition is only the default or any documented QPS configuration for `EstimateEnergyServlet`/`GlobalRateLimiter` — no privileged access, no fees, and no transaction broadcast are required since `estimateenergy` is invoked purely as a local HTTP call. An unprivileged remote client can trivially construct a worst-case contract (per the amplification analysis in the related questions) and issue requests at the permitted QPS indefinitely, making this fully repeatable and low-cost to sustain.

### Recommendation
Introduce cost-aware throttling for `EstimateEnergyServlet` (and similarly expensive endpoints such as `triggerconstantcontract`), e.g., by weighting permits by an estimated cost metric (bytecode size, expected iteration bound of the binary search, or measured wall-clock/energy cost of the just-completed call) rather than a flat one-token-per-request model, or by adding a dedicated low-QPS/limited-concurrency adapter specifically for `estimateenergy` that reflects its higher per-call cost relative to `triggerconstantcontract`.
