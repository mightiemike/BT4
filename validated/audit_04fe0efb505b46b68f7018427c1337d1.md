**Analysis:** The behavior described is by design, not a flaw. `ClaimedEntryFunction.function` is explicitly typed as `Option<Identifier>` [1](#0-0) , and `try_into_decrypted`'s check intentionally treats `function: None` as "claim only the module, not a specific function" — this is a deliberate partial-disclosure mechanism, not a bypassed check: [2](#0-1) 

When the claim's `function` field is `None`, the code correctly skips the function-name comparison because there is no claim to compare against — this is exactly what the `Option` type signals. The resulting `Decrypted` state stores the *actual* decrypted `EntryFunction`, and everything downstream (VM execution, write-set generation, API serialization via `into_api_claimed_entry_function`) operates on this actual decrypted payload, not on the claim [3](#0-2) . There's no path where the write set is computed from the claim rather than the decrypted plaintext.

Searching for all usages of `claimed_entry_fun` across the codebase shows it is used only for: (1) the mismatch check itself in `try_into_decrypted`, (2) API/JSON display of both the original claim and the actual decrypted function side-by-side, and (3) test helpers [4](#0-3) . It is not used in consensus for censorship, batching, gas-estimation enforcement, or any other decision that would bind ledger state to the claim's specific function. There's no evidence it feeds into fee/gas metering, execution routing, or storage commitment in a way where a module-only claim followed by execution of an unclaimed function within that module produces a "write set inconsistent with any claim the sender advertised" in a security-relevant sense — the claim is an optional hint field, and the write set always correctly reflects what was actually decrypted and executed.

Since the sender fully controls both the claim and the ciphertext contents in the first place (nothing about `claimed_entry_fun` is attested by a third party or relied upon by consensus for correctness), and the actual executed function's write set is always consistent with what was actually decrypted (never with the claim), there is no state-integrity, proof-integrity, or authenticated-response corruption here.
