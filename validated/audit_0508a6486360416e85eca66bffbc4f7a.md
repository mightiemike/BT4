### Title
Many-ref account slot-ordering invariant can be violated by bin-packing fragmentation in ancient repack, causing silent stale-account overwrite - (`accounts-db/src/ancient_append_vecs.rs`)

### Summary
`AccountsDb::many_ref_accounts_can_be_moved` estimates the number of packed storages a set of "many-ref, newest-alive" accounts will require using a naive `alive_bytes / ideal_storage_size + 1` formula, but the actual bin-packing performed by `PackedAncientStorage::pack` can require substantially more storages when accounts don't tile evenly (fragmentation). Because `write_packed_storages` maps packed-storage index `i` to `target_slots_sorted` reversed (highest slot first) purely by position, an attacker who controls account sizes and multi-slot writes (to inflate `ref_count`) can force fragmentation that pushes the lowest-slot portion of "many-ref newest" data into a packed storage mapped to a target slot lower than that account's original slot, breaking the "highest slot defines most recent account" invariant with no panic.

### Finding Description
`many_ref_accounts_can_be_moved` (accounts-db/src/ancient_append_vecs.rs:390-415) computes:
```
required_ideal_packed = (alive_bytes / ideal_storage_size) + 1
highest_slot = target_slots_sorted[len - required_ideal_packed]
assert all(many.slot <= highest_slot)
```
This assumes the actual packer needs at most `required_ideal_packed` storages to hold all `many_refs_newest` bytes, and that these will occupy the *highest* `required_ideal_packed` target slots (since `write_packed_storages` zips `target_slots_sorted.iter().rev()` with `packed_contents` in generation order, and `PackedAncientStorage::pack` places `many_refs_newest` first in its iterator chain — see `combine_ancient_slots_packed_internal`, lines 465-504).

However, `PackedAncientStorage::pack` (lines 1009-1094) never splits an individual stored account across storages. When the next account does not fit in the remaining space of the current storage (`new_size > ideal_size && bytes_total > 0`), it marks the storage `full` and defers the account to a new storage, even if a large fraction of the current storage's capacity is unused. This is a straightforward "greedy first-fit, no-splitting" bin packer, which can need far more bins than `ceil(total_bytes / bin_size)` when items are sized just over half the bin size (classic bin-packing fragmentation, e.g. accounts of size `ideal_storage_size/2 + 1`: two such accounts never fit together, so each consumes an entire storage even though `alive_bytes / ideal_storage_size` predicts roughly half as many storages).

An attacker fully controls:
- Account data size (hence `stored_size()`),
- Which pubkeys get multiple slot-list entries with `ref_count > 1` (by rewriting the same pubkey across many rooted slots that later become ancient),
- Which of those entries is "newest alive" (highest slot in the index) — classified into `many_refs_this_is_newest_alive` by `ShrinkCollectAliveSeparatedByRefs::add` (accounts_db.rs:214-235).

By crafting many such many-ref/newest-alive accounts sized to defeat bin-packing (e.g., slightly over `ideal_storage_size/2`), the attacker can make the real number of packed storages needed for `many_refs_newest` exceed `required_ideal_packed`. The lowest-slot entries within `many_refs_newest` (processed last by `pack`, since the list is sorted highest-to-lowest) then spill into a packed-storage index beyond the guaranteed high-slot window, which `write_packed_storages` maps to a target slot *below* `highest_slot` — and potentially below that account's own original slot. The only post-pack safety check is `pack.len() > accounts_to_combine.target_slots_sorted.len()`, which only guards against *total* storage overflow, not against this specific per-account misplacement, since spare capacity from other (one-ref) accounts can keep the total count within budget.

Because the account write path (`write_ancient_accounts` → `store_accounts_for_squash`) updates the AccountsIndex to record the account at its new (lower) target slot, this results in a stale/older instance of a pubkey's data being indexed as if it were newer than another surviving instance in a genuinely higher slot — a silent, undetected wrong-version account state, exactly matching the invariant violation called out in the code's own comment at accounts_db.rs / ancient_append_vecs.rs:879-886.

### Impact Explanation
This is a silent state-corruption bug: the account index can end up associating an older account snapshot with a slot number implying it's the latest, causing future reads (and consequently accounts-hash/capitalization computation) to use stale lamports/data for that pubkey. This falls under "silent stale or wrong-version account load / silent balance change / hash-capitalization divergence" per the audit's Validate criteria, since it is not caught by any existing guard and produces no panic.

### Likelihood Explanation
Exploitation requires only an unprivileged user who: (1) creates/writes to a pubkey repeatedly across many slots to build up `ref_count > 1` entries, (2) sizes account data to defeat the packer's naive first-fit bin estimate, and (3) waits for ancient repack (`combine_ancient_slots_packed`) to run over the affected slot range — a background process AccountsDb performs automatically on old/rooted slots, not requiring special privileges or timing precision, though enough many-ref/large-account volume needs to accumulate to create the fragmentation gap, and the ancient slot set must actually be selected for combination together.

### Recommendation
Replace the naive `alive_bytes / ideal_storage_size + 1` estimate in `many_ref_accounts_can_be_moved` with an actual simulation/count of the number of storages `PackedAncientStorage::pack` would produce for `many_refs_newest` alone (or make `pack` deterministic and query its real output length before deciding target-slot assignment), and/or add a post-pack invariant check that asserts every many-ref/newest account's assigned target slot is `>=` its original slot, aborting (not panicking) the packing pass if violated.

### Proof of Concept
Rust unit test to add to `accounts-db/src/ancient_append_vecs.rs` tests module, extending `test_many_ref_accounts_can_be_moved`/`test_pack_ancient_storages_varying` style harnesses:

```rust
#[test]
fn test_many_ref_slot_invariant_broken_by_fragmentation() {
    // ideal_storage_size chosen so 2 accounts of `big_size` cannot share a storage,
    // but naive alive_bytes/ideal_size+1 estimate assumes they can.
    let ideal_storage_size = 1000u64;
    let big_size = 501usize; // > ideal_storage_size/2

    // Construct many_refs_newest: N AliveAccounts entries, each representing
    // a distinct original slot, each holding one `big_size` account, sorted
    // highest-to-lowest slot as production code does.
    let n = 4;
    let base_slot = 100;
    let many_refs_newest: Vec<AliveAccounts> = (0..n)
        .map(|i| AliveAccounts {
            slot: base_slot + (n - i) as Slot, // descending across entries
            bytes: big_size,
            accounts: /* one AccountFromStorage of size `big_size` */ vec![],
        })
        .collect();

    let tuning = PackedAncientStorageTuning {
        ideal_storage_size: NonZeroU64::new(ideal_storage_size).unwrap(),
        ..default_tuning()
    };

    let alive_bytes: usize = many_refs_newest.iter().map(|a| a.bytes).sum();
    let required_ideal_packed =
        (alive_bytes as u64 / tuning.ideal_storage_size + 1) as usize;

    // target_slots_sorted has exactly `required_ideal_packed` slots, all above
    // every many-ref account's original slot, per what the guard demands.
    let target_slots_sorted: Vec<Slot> =
        ((base_slot + n as Slot + 1)..).take(required_ideal_packed).collect();

    assert!(AccountsDb::many_ref_accounts_can_be_moved(
        &many_refs_newest,
        &target_slots_sorted,
        &tuning,
    )); // guard says "safe to move"

    // But actual packing needs `n` storages (one per big account) due to
    // fragmentation, not `required_ideal_packed` (~n/2).
    let pack = PackedAncientStorage::pack(many_refs_newest.iter(), tuning.ideal_storage_size);
    assert!(
        pack.len() > required_ideal_packed,
        "pack needed {} storages but guard only reserved {}",
        pack.len(),
        required_ideal_packed
    );

    // Since write_packed_storages only has `required_ideal_packed`-worth of
    // "safe" high target slots, the extra pack entries (holding the lowest
    // -slot many-ref account(s)) would be assigned to a target slot BELOW
    // that account's original slot if additional lower target slots exist,
    // violating LOAD_FRESHNESS (highest-slot-wins).
}
```
