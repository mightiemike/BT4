This is a genuine, intentional (but unmitigated for the untrusted-relayer case) design property of NEAR's meta-transaction / function-call access key model, functionally identical in shape to the reported bug: a restricted permission (`allowance`, meant to cap what a key can spend) can be completely bypassed by routing the same authorized action through a different privileged execution path (`enableTradingWithWeights`/`enableTradingRiskingArbitrage` in the report ↔ meta-transactions in NEAR).

### Title
Function-call access key `allowance` restriction is fully bypassable via meta-transactions (`DelegateAction`) - (File: `runtime/runtime/src/actions.rs`)

### Summary
A NEAR account owner can restrict a function-call access key to a tiny `allowance` (e.g. "this key may only ever spend 1 yoctoNEAR-worth of gas") intending to bound the financial exposure of that key, exactly like `allowance()` in the reported Aera Vault bug is meant to bound what an owner can withdraw. Just as the vault owner routes around the withdrawal cap by using `enableTradingWithWeights()`/`enableTradingRiskingArbitrage()` — different, still-authorized entry points that reach the same privileged state without the `allowance()` check — a holder of a restricted function-call key can route the exact same authorized `FunctionCall` action through a `Delegate`/`DelegateV2` (meta-transaction) receipt instead of a plain signed transaction, and the allowance check is skipped entirely.

### Finding Description
`FunctionCallPermission.allowance` is documented as the balance limit that access key can ever spend on gas/fees: "Allowance is a balance limit to use by this access key to pay for function call gas and transaction fees" [1](#0-0) .

When a transaction is signed directly with such a key, `verify_and_charge_tx_ephemeral` computes `check_and_compute_new_allowance` and rejects the transaction if the allowance is insufficient [2](#0-1) , and `verify_function_call_permission` also enforces the `receiver_id`/`method_names` restriction [3](#0-2) .

However, when the identical `FunctionCall` action is instead wrapped in a `Delegate`/`DelegateV2` receipt (meta-transaction) and relayed, `validate_delegate_action_key` enforces the `receiver_id` and `method_names` restrictions [4](#0-3)  but performs **no allowance check whatsoever** — the allowance field is never read in this path. The project's own architecture docs confirm this is deliberate, not accidental: "For allowance, however, there is no check. All costs have been covered by the relayer. Hence, even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work... if someone were to limit a function access key to one trivial action by setting a very small allowance, that is circumventable by going through a relayer." [5](#0-4) .

This is corroborated by an integration test that explicitly relies on the bypass: `meta_tx_fn_call_access_key_insufficient_allowance` sets an allowance of `1 yoctoNEAR` (less than one gas unit) and asserts the call **still succeeds** through the meta-transaction path, with the comment "this should still succeed because we use the gas of the relayer, not of the access key" [6](#0-5) .

### Impact Explanation
The `allowance` field is the *only* protocol-level mechanism to bound how much value a restricted (non-full-access) key can authorize on an account's behalf. Any application, custodial service, or key-delegation scheme built on the assumption that a `FunctionCallPermission.allowance` caps financial exposure of that key (analogous to `allowance()` bounding a vault owner's withdrawals in the referenced report) is silently defeated the moment an untrusted or compromised holder of that key can reach any relayer willing to wrap the same call in a `Delegate` action — the receiver/method restriction still holds, but the intended spend-limiting guarantee is void, since a relayer bears the gas/fee cost instead of the key's allowance being decremented. This does not itself move relayer funds without consent (the relayer must sign/pay), but it invalidates the confidentiality of the access-key's designed security boundary for any protocol assuming allowance-based value caps at the runtime level.

### Likelihood Explanation
This is 100% reproducible and requires no adversarial validator, network condition, or race — only a single meta-transaction and a cooperating (or automated/public) relayer, i.e. reachable purely via ordinary RPC-submitted transactions from an unprivileged holder of a restricted function-call key.

### Recommendation
This is already known and explicitly acknowledged as a design trade-off in NEAR's own documentation (comparable to Gauntlet's "won't fix for V1" stance in the source report) [5](#0-4) , so no further remediation is expected unless the protocol changes its meta-transaction trust model to also enforce (or explicitly re-verify) `allowance` decrements against the *sender's* key even when a relayer pays gas, or documentation/wallet UX is strengthened to warn that `allowance` is not a hard cap once meta-transactions are enabled.

### Proof of Concept
1. Account `alice` adds a `FunctionCall` access key with `receiver_id = "carol.near"`, `method_names = ["reserve_trip"]`, and `allowance = 1 yoctoNEAR` (far below the gas cost of one call), intending this key to be essentially unusable/negligible in value.
2. A direct transaction signed with this key and calling `reserve_trip` fails with `InvalidAccessKeyError::NotEnoughAllowance`, per `check_and_compute_new_allowance` in `runtime/runtime/src/verifier.rs`.
3. Instead, `alice`'s key signs a `DelegateAction` containing the same `FunctionCall{ method_name: "reserve_trip" }` action and submits it to any relayer `bob`, who wraps it as `Action::Delegate`/`DelegateV2` and pays for it.
4. `validate_delegate_action_key` in `runtime/runtime/src/actions.rs` checks only `receiver_id`/`method_names` (both satisfied) and never inspects `allowance`; the call succeeds and the key's allowance is untouched, exactly as demonstrated by `meta_tx_fn_call_access_key_insufficient_allowance` in `integration-tests/src/tests/features/delegate_action.rs`.
