### Title
Bad-debt socialization fold aborts the entire `liquidate()` transaction on a single per-asset failure, permanently blocking liquidation of multi-asset debt positions - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate()` handles positions with debt spread across multiple assets by folding `socialize-debt-asset` over the borrower's remaining debt entries once collateral is exhausted [1](#0-0) . The fold uses a short-circuit "absorb failure" accumulator, and the caller then asserts on the aggregate success flag, reverting the *whole* `liquidate()` call — including the collateral seizure and debt repayment that already succeeded earlier in the same transaction — if socialization of just one debt asset fails [2](#0-1) . This mirrors the reported Solidity pattern where a single failing sub-call (there: the operator's fee transfer; here: one asset's debt write-down) reverts the entire multi-party transaction, denying rewards/settlement to everyone involved (liquidator, protocol, and the position that needed to be liquidated).

### Finding Description
`liquidate()` computes `no-collateral-left` and, when true, builds `fresh-debt-list` from the borrower's remaining debt entries and folds `socialize-debt-asset` over them:

```
(let ((socialization-result (fold socialize-debt-asset
                                  fresh-debt-list
                                  { borrower: borrower, success: true })))
  (asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)
  ...)
``` [3](#0-2) 

`socialize-debt-asset` is defined to absorb any prior failure by passing the accumulator through unchanged, and to mark failure (without reverting immediately) if `vault-socialize-debt` or `debt-remove-scaled` errors for the current entry:

```
(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((failed-status { borrower: borrower, success: false }) ...)
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ...
            (unwrap! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-debt asset-id) failed-status)
          acc)))
``` [4](#0-3) 

Because Clarity public functions are atomic, an `(err ...)` return from `liquidate()` rolls back *every* state change made earlier in that same call — the collateral removal (`collateral-remove`) and the primary debt repayment (`vault-system-repay`, `debt-remove-scaled` for the initially-targeted asset) that had already succeeded via `try!` [5](#0-4) . So if socialization of just *one* of the borrower's other outstanding debt assets in `fresh-debt-list` fails for any reason, the liquidator's entire attempt — including the part of the position that was perfectly liquidatable — is reverted.

This directly parallels the report's mechanism: a single reverting/failing sub-operation in a multi-party settlement path is allowed to nuke the whole transaction rather than being isolated and flagged. Here the "operator" role is played by whichever debt-asset entry in the fold encounters a failure condition in its own vault's `socialize-debt` or in `market-vault`'s `debt-remove-scaled`, and the "withdrawer/treasury" harmed are the liquidator (loses gas, no incentive) and the protocol (the insolvent position remains unliquidated and continues accruing bad debt).

### Impact Explanation
If a borrower's position accumulates debt in multiple assets and reaches a state where liquidation would need to write down one of those assets via `socialize-debt-asset`, and that particular asset's socialization path is unable to succeed (e.g. because the target vault's socialization function is independently paused, or a scaled-debt bookkeeping mismatch causes an internal assertion in `debt-remove-scaled`/`remove-user-scaled-debt` to fail), then `liquidate()` for that borrower can never complete: every attempt reverts atomically at the final `asserts!`, no matter who calls it or how much debt/collateral is otherwise correctly resolvable in the same call. This is a permanent freeze of the ability to close out the position and stop bad-debt accrual — landing on **permanent freezing of funds / protocol insolvency** since the write-down mechanism (`socialize-debt`) exists specifically to protect protocol solvency and is the only path that clears bad debt for `no-collateral-left` positions.

### Likelihood Explanation
Likelihood is moderate and depends on being able to reach a state where one asset's socialization step is unable to succeed while the rest of the liquidation is valid (e.g. that vault's `socialize-debt` being paused independently of the other vaults touched by the same `liquidate()` call, or a rounding/ordering mismatch between the scaled amounts cached in `pos-full` at the top of `liquidate()` and the live scaled-debt entry read inside `remove-user-scaled-debt` at execution time). I was not able to fully trace every failure branch of `vault-socialize-debt`/`debt-remove-scaled` before running out of investigation budget, so the exact triggering precondition for the per-asset failure is not fully confirmed — this is the main open uncertainty.

### Recommendation
Do not let a single per-asset socialization failure abort the entire `liquidate()` transaction. Either: (1) make bad-debt socialization for each asset independent (its own `try!`/isolated call boundary, e.g. via a separate `as-contract?`-scoped sub-transaction) so a failure on one asset only skips that asset's write-down and emits a diagnostic event, while the collateral seizure and repayment already computed still commit; or (2) ensure the fold cannot silently skip remaining, otherwise-successful entries once one entry fails, and instead retry/report failures per-asset without gating the whole liquidation's success on all of them succeeding together.

### Proof of Concept
1. Borrower supplies collateral and borrows against two different debt assets (asset A and asset B) in the same position.
2. Collateral value drops such that the position becomes eligible for full liquidation.
3. A liquidator calls `liquidate()` targeting asset A with `debt-amount` sized to consume all remaining collateral (`coll-removed = 0`), which sets `no-collateral-left` = true and causes `fresh-debt-list` to include the still-outstanding debt for asset B [6](#0-5) .
4. During the fold, `socialize-debt-asset` for asset B's entry hits a failure in `vault-socialize-debt` or `debt-remove-scaled` (e.g. that vault has `socialize-debt` paused, or the scaled amount doesn't match live storage), setting `success: false` in the accumulator [7](#0-6) .
5. `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` fires, and Clarity's atomicity rolls back the entire `liquidate()` call, undoing the already-valid repay/collateral-seizure for asset A [8](#0-7) .
6. Every subsequent `liquidate()` call on this borrower repeats the same failure, permanently blocking liquidation and bad-debt write-down for the position.
