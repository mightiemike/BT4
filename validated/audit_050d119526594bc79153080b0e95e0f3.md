## Finding

Based on the investigation, I found a concrete client-side analog to the M-2 bug-class: a **fixed, once-computed wall-clock expiry** (`SigningDeadline`) that is not re-synchronized with the block-height-based TSS session lifecycle, and whose enforcement is **inconsistently implemented per chain type**.

### Title
Signing deadline is computed once at outbound-creation time and never refreshed across TSS session retries, and is entirely unenforced on the EVM broadcast/resolve path — (File: `x/uexecutor/keeper/create_outbound.go`, `universalClient/tss/sessionmanager/sessionmanager.go`, `universalClient/tss/txresolver/evm.go`)

### Summary
`attachOutboundsToUtx` computes `signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())` a single time, when the outbound is created and written into `PendingOutbounds` [1](#0-0) . This value is embedded into the message the TSS validators sign, and is expected to be authoritative on the destination chain (this is exactly what the SVM `IsAlreadyExecuted`/resolver logic relies on) [2](#0-1) .

However, the surrounding TSS coordination lifecycle is governed by **block-height**, not wall-clock time: `SessionManager.checkExpiredSessions` expires a session purely based on a local wall-clock timer (`sessionExpiryTime`, default 2 minutes) and then reschedules the SAME event for retry at `currentBlock + blockDelay` (default 60 blocks) [3](#0-2) , and `DefaultTssProcessExpiryAfterBlocks` gates keygen/quorum-change processes at 500 blocks [4](#0-3) . None of these retry/expiry mechanisms consult or refresh `SigningDeadline`, because `SigningDeadline` was fixed once at outbound-creation and is carried unchanged through every retry cycle in the event payload.

Compounding this, deadline-awareness is **not symmetric across VM types**: the SVM broadcaster (`broadcastOutboundSVM`) and SVM resolver (`resolveSVM`) both explicitly gate broadcast/resolve decisions on `SigningDeadline` versus cluster time, with staleness/slack buffers [5](#0-4) [6](#0-5) . The EVM resolver (`resolveOutboundEVM`), however, contains **no reference to `SigningDeadline` at all** — it determines REVERT purely from on-chain nonce-consumption state [7](#0-6) , and the EVM broadcast path in `broadcaster.go` dispatches straight to chain submission with no pre-broadcast deadline check [8](#0-7) .

### Finding Description
This mirrors the M-2 root cause precisely: an expiry value computed from one clock (wall time, fixed at creation) is trusted to remain consistent with a lifecycle governed by a different clock (block height, with unbounded retry rescheduling), and nothing keeps the two synchronized or re-derives the deadline on retry.

### Impact Explanation
Because `SigningDeadline` is embedded once and never refreshed, an outbound whose TSS session is delayed or must retry (congestion, coordinator rotation, session timeouts) can be signed and broadcast carrying a deadline that has already elapsed relative to the destination chain's clock. For EVM chains, since neither the broadcaster nor the resolver inspects `SigningDeadline`, this condition is not self-detected client-side; whether it results in fund loss ultimately depends on the (out-of-scope) EVM gateway contract's own deadline enforcement, which I could not verify from this repository. This is a genuine architectural gap and asymmetry versus the SVM path, but I could not confirm a fully-reachable, unprivileged, concrete fund-loss trigger purely within this repo's scoped code without visibility into the EVM gateway contract's on-chain deadline check.

### Likelihood Explanation
Requires ordinary network conditions (TSS session retries/delays) rather than any privileged or malicious action — reachable through the standard outbound signing pipeline triggered by any user deposit/bridge transaction.

### Recommendation
Recompute or extend `SigningDeadline` whenever a `SIGN_OUTBOUND` event is retried/re-queued after session expiry, and add explicit deadline gating to the EVM broadcast and resolve paths analogous to the existing SVM implementation, so an expired-deadline signature is never blindly (re)submitted.

### Proof of Concept
Not independently verifiable end-to-end from this repository alone, because confirming actual fund loss requires the destination-chain EVM gateway contract's deadline-check behavior, which is outside `push-chain-node--019`'s scoped code. The client-side asymmetry (SVM deadline-aware vs. EVM deadline-blind) is directly confirmed by the cited files.

**Note on confidence**: I was not able to fully verify whether this asymmetry produces a materially exploitable, unprivileged fund-loss/freezing outcome strictly within the scoped repository (the missing piece is the EVM gateway contract's on-chain deadline enforcement, which lives outside this codebase). Given the strict validation bar in the task (concrete corrupted value + fully in-repo reachable root cause), I present this as a discovered architectural gap rather than a fully certain vulnerability.

// broadcastEvent dispatches to the appropriate handler based on event type.
func (b *Broadcaster) broadcastEvent(ctx context.Context, event *store.Event) {
	switch event.Type {
	case store.EventTypeSignOutbound:
		b.broadcastOutbound(ctx, event)
	case store.EventTypeSignFundMigrate:
		b.broadcastFundMigration(ctx, event)
	default:
		b.logger.Warn().Str("event_id", event.EventID).Str("type", event.Type).
			Msg("unknown signed event type, skipping")
	}
}

// ---------------------------------------------------------------------------
// Outbound broadcast (parsing + chain dispatch)

// broadcastOutbound parses outbound event data and delegates to chain-specific broadcast.
func (b *Broadcaster) broadcastOutbound(ctx context.Context, event *store.Event) {
	var data txflow.SignedOutboundData
	if err := json.Unmarshal(event.EventData, &data); err != nil {
		b.logger.Warn().Err(err).Str("event_id", event.EventID).Msg("failed to parse signed outbound data")
		return
	}
	if data.SigningData == nil {
		b.logger.Warn().Str("event_id", event.EventID).Msg("signing_data missing from outbound event")
		return
	}

	chainID := data.DestinationChain
	if !b.chains.IsChainOutboundEnabled(chainID) {
		b.logger.Warn().Str("chain", chainID).Str("event_id", event.EventID).
			Msg("outbound disabled, skipping broadcast")
		return
	}

	if b.chains.IsEVMChain(chainID) {
		b.broadcastOutboundEVM(ctx, event, &data, chainID)
	} else {
		b.broadcastOutboundSVM(ctx, event, &data, chainID)
	}
}
