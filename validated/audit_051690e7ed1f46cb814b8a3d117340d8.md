**Analysis:** The premise of the exploit question actually describes correct, expected cryptographic behavior rather than a flaw. `PrivateKey::to_bytes` in `crates/aptos-crypto/src/secp256r1_ecdsa/secp256r1_ecdsa_keys.rs` simply serializes the raw 32-byte scalar via SEC1 encoding with no negotiation logic that could be manipulated. [1](#0-0) 

Public key derivation (`From<&PrivateKey> for PublicKey`) is a pure deterministic function of the private-key scalar, and signature verification (`Signature::verify_arbitrary_msg`) always checks the signature against the `PublicKey` object that is explicitly passed in — i.e., the one embedded in the `SignedTransaction`/`KeylessSignature`/`EphemeralPublicKey`, never a locally re-derived one. [2](#0-1) [3](#0-2) 

If an attacker alters even one byte of a serialized `EphemeralPublicKey::Secp256r1Ecdsa` in transit, `EphemeralPublicKey`/`PublicKey` deserialization (`from_sec1_bytes`) either rejects the malformed point outright, or — if it happens to decode to a different valid curve point — produces a `PublicKey` whose byte representation differs from the one embedded in the committed transaction, which then fails `AnySignature::verify`/`EphemeralSignature::verify_arbitrary_msg` deterministically because the point no longer corresponds to the signing key that produced the signature. [4](#0-3) [5](#0-4) 

This is exactly the behavior verified by existing test coverage — e.g. `verify_real_partial_authenticator_assertion_response_failure` explicitly checks that verification fails when an incorrect public key is substituted, confirming there is no silent key-substitution path. [6](#0-5) 

There is no code path where a corrupted/altered public key byte could bind signature verification to "the wrong public-key state object" — verification is always keyed directly off the `public_key` value passed alongside the signature (which itself comes from the authenticator embedded in the `SignedTransaction` being verified), not from any separately-derived or cached value that could diverge. No state-commitment, proof-integrity, or authenticated-response binding issue results from this design; the deterministic failure described in the question's own "proof idea" is the correct, safe outcome, not an exploit.
