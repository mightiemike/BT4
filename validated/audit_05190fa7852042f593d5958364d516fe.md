### Title
Duplicated Amsterdam (EIP-8037) two-lane gas admission check in the BAL parallel executor can diverge from serial `EthBlockExecutor` verdicts - (File: crates/engine/tree/src/tree/payload_processor/bal/execute.rs)

### Summary
The BAL (Block Access List) parallel-execution commit loop does not call the canonical per-transaction admission entry point (`execute_transaction_without_commit`) that the serial `EthBlockExecutor` uses to enforce the two-lane Amsterdam/EIP-8037 gas budget (`regular` vs `state` gas). Instead, `BlockGasTracker::validate_tx_limit` in `crates/engine/tree/src/tree/payload_processor/bal/execute.rs` independently re-implements this check to "mirror" the executor, as the code comment itself states: *"the check must be replayed here for BAL and serial execution to reach the same block validity verdict."* Any subtle divergence between this re-implementation and the actual execution-specs `check_block_gas_capacity` semantics used by the serial executor breaks the equality "BAL/parallel block validity verdict == serial block validity verdict," which is exactly the non-deterministic parallel-vs-serial class called out in the impact criteria.

### Finding Description
`BlockGasTracker::validate_tx_limit` [1](#0-0)  re-derives the two-budget Amsterdam admission rule (regular lane capped by `tx_gas_limit_cap`, state lane uncapped) purely from locally-tracked counters (`block_regular_gas_used`, `block_state_gas_used`, `cumulative_tx_gas_used`), rather than invoking the actual `EthBlockExecutor::execute_transaction_without_commit` entry point that performs this admission check during normal serial execution. This same two-lane logic is *also* independently duplicated in three other places: the payload builder [2](#0-1) , the pending-block builder [3](#0-2) , and `eth_simulate` [4](#0-3) .

This is structurally the same bug class as the BadgerDAO BCCR issue: the "buffered" check (BCCR path) was a bespoke re-derivation of a health condition that was supposed to match the canonical "did TCR actually decrease" condition but used a different, non-equivalent comparison (`ICR <= BUFFERED_CCR` alone, without gating on `newTCR < oldTCR`), causing the buffered path to fire in cases the authors didn't intend. Here, the risk is analogous: the BAL executor's local tracker must match the *exact* two-lane arithmetic and ordering of checks (regular-lane-first, then state-lane, both against `self.block_gas_limit`, not a shared cumulative counter) that the canonical serial executor performs. Any accidental mismatch — e.g. in rounding, in which counter feeds which budget, in `saturating_sub` vs raw subtraction edge cases, or in future changes to the canonical EIP-8037 semantics not mirrored into all four duplicate sites — makes the BAL/parallel commit path accept a transaction that the serial path would reject (or vice versa), producing a **different block validity verdict for the same block depending on which execution path is used** (BAL/parallel vs. serial single-threaded execution).

The test suite for `BlockGasTracker` (`gas_tracker_amsterdam_enforces_state_gas_budget`, `gas_tracker_non_amsterdam_uses_cumulative_gas`) only validates the tracker's *self-consistency*, not that it stays byte-for-byte equivalent to whatever the real `EthBlockExecutor`/execution-specs `check_block_gas_capacity` does; there is no shared, single source of truth for this arithmetic — it is copy/pasted across four locations independently, and comments in the code explicitly acknowledge this is a manually maintained mirror rather than a shared, tested abstraction.

### Impact Explanation
If the BAL/parallel commit-loop admission check diverges even slightly from the serial executor's canonical rule (through independent future edits to only one of the four duplicated sites, or a subtly incorrect port of execution-specs semantics), a block that is valid when executed serially could be rejected when executed via the BAL/parallel path, or a block that should be invalid could be wrongly admitted by the parallel path. This falls squarely under "non-deterministic execution between cached/prewarmed/JIT/parallel and serial paths," a High-impact class, because it can produce a node-internal inconsistency in block validity depending on the code path taken (BAL vs. serial), and in the builder paths (payload/pending-block) can cause a reth-built block to include a transaction that the executor itself would reject at commit time — risking a self-built invalid block.

### Likelihood Explanation
The likelihood is elevated by the fact that this is not a one-off duplication but a *pattern* duplicated across four independent files (`bal/execute.rs`, `ethereum/payload/lib.rs`, `pending_block.rs`, `simulate.rs`), each maintained by hand rather than sharing one canonical implementation. Any future change to EIP-8037/Amsterdam gas-budget semantics (a plausible source of near-term protocol evolution, given Amsterdam is an actively developed fork in this codebase) requires simultaneously and correctly updating all four sites; a missed or subtly wrong update in exactly one of them reproduces the BadgerDAO-style "similar but non-equivalent condition" bug and directly breaks BAL/serial equivalence. The BAL path's own code comments already flag this as a manually-synchronized "mirror," which is the same category of risk that produced the original BadgerDAO defect (a hand-copied condition that silently diverged from its origin).

### Recommendation
Refactor the two-lane Amsterdam gas-admission arithmetic into a single shared function callable from `EthBlockExecutor::execute_transaction_without_commit`, `BlockGasTracker::validate_tx_limit`, the payload builder, the pending-block builder, and `eth_simulate`, so there is one canonical source of truth instead of four hand-synchronized copies. Add a cross-path regression test that executes the same block/transaction set once via the serial executor and once via the BAL/parallel path (as already partially done in `execute.rs`'s tests) and asserts identical accept/reject verdicts and identical `(transaction_gas_limit, block_available_gas)` error payloads for every EIP-8037 budget combination, not just self-consistency within `BlockGasTracker`.

### Proof of Concept
Concrete exploitation requires introducing a divergence between the four duplicated implementations (e.g., a future patch that updates the canonical `EthBlockExecutor` admission check for a new EIP-8037 nuance but misses updating `BlockGasTracker::validate_tx_limit`). No divergence currently exists that I could positively confirm from static reading alone — I could not access the exact body of `EthBlockExecutor::execute_transaction_without_commit`/`check_block_gas_capacity` in the indexed portion of the `evm`/`revm` crates within scope to byte-for-byte diff it against `BlockGasTracker::validate_tx_limit`. This is a structural/maintainability finding about the duplicated-invariant pattern (the same root-cause pattern as the BadgerDAO report) rather than a demonstrated concrete present-day mismatch; I flag this uncertainty explicitly rather than asserting an active divergence exists today.

    /// Verifies that the transaction's gas limit fits the block's remaining gas budget(s): the
    /// admission check `EthBlockExecutor::execute_transaction_without_commit` performs before
    /// executing a transaction.
    ///
    /// The commit loop never calls that entry point — workers execute speculatively and their
    /// results are committed directly via `commit_transaction` — so the check must be replayed
    /// here for BAL and serial execution to reach the same block validity verdict.
    ///
    /// Pre-Amsterdam there is one budget: the tx gas limit, capped by `tx_gas_limit_cap`
    /// (EIP-7825), must fit `block_gas_limit - cumulative_tx_gas_used`.
    ///
    /// Amsterdam (EIP-8037) splits gas into two lanes, each budgeted at `block_gas_limit`:
    /// - regular: the capped tx gas limit must fit the remaining regular budget
    /// - state: the full, uncapped tx gas limit must fit the remaining state budget, since state
    ///   gas is drawn from the reservoir above `tx_gas_limit_cap` (execution-specs
    ///   `check_block_gas_capacity`)
    fn validate_tx_limit(&self, tx_gas_limit: u64) -> Result<(), BlockExecutionError> {
        let block_gas_used = if self.enable_amsterdam_eip8037 {
            self.block_regular_gas_used
        } else {
            self.cumulative_tx_gas_used
        };
        let block_available_gas = self.block_gas_limit.saturating_sub(block_gas_used);
        let tx_min_gas_limit =
            self.tx_gas_limit_cap.map_or(tx_gas_limit, |cap| tx_gas_limit.min(cap));

        if tx_min_gas_limit > block_available_gas {
            return Err(BlockValidationError::TransactionGasLimitMoreThanAvailableBlockGas {
                transaction_gas_limit: tx_gas_limit,
                block_available_gas,
            }
            .into());
        }

        if self.enable_amsterdam_eip8037 {
            let state_gas_available =
                self.block_gas_limit.saturating_sub(self.block_state_gas_used);
            if tx_gas_limit > state_gas_available {
                return Err(BlockValidationError::TransactionGasLimitMoreThanAvailableBlockGas {
                    transaction_gas_limit: tx_gas_limit,
                    block_available_gas: state_gas_available,
                }
                .into());
            }
        }

        Ok(())
    }
