### Title
Unbounded recursive JSON parsing in the JSON-RPC endpoint allows stack-overflow crash of a validator/RPC node via a single request - ([File: chain/jsonrpc/src/lib.rs])

### Summary
The Suricata CVE-2026-22260 bug class is "attacker-controlled data drives unbounded/uncontrolled recursion during input decoding, causing a stack overflow and process crash." The closest reachable analog in nearcore is the JSON-RPC ingestion path: `rpc_handler()` extracts the request body directly into a `serde_json`-backed `Message`/`Value` tree via Axum's `Json` extractor, with only a byte-size cap (10 MB) and no nesting-depth limit.

### Finding Description
`rpc_handler` deserializes every POST body straight into `Message` using Axum's `Json` extractor, which is backed by `serde_json`: [1](#0-0) 

`Message`/`Request` store the JSON-RPC `params` as an untyped `serde_json::Value`: [2](#0-1) 

`serde_json::Value`'s deserializer is a classic recursive-descent parser: each nested array/object level (`[`, `{`) recurses one more Rust stack frame before returning. There is no depth counter or `recursion_limit` configured anywhere in the RPC stack — the only protection documented is a flat request-body size cap: [3](#0-2) 

Because the size limit bounds bytes, not nesting depth, an attacker can send a body such as `{"jsonrpc":"2.0","method":"status","id":1,"params": [[[[[[...]]]]]]}` consisting almost entirely of the single character `[` repeated many tens/hundreds of thousands of times — well within a 10 MB budget — and drive the parser's recursion far past the thread's stack limit before the byte cap is ever reached. This mirrors the Suricata bug class exactly: a single-shot untrusted input triggers unbounded recursive decoding with no depth guard, producing a stack overflow.

This is distinct from the internal trie/traversal code in `near-store`, which the codebase has already hardened against this exact bug class by converting recursive descent into explicit stack/queue-based iteration (e.g. `TrieRecorder::get_subtree_size`, `TrieStorageUpdate::flatten_nodes`, `TrieIteratorImpl`), and from the state-part decompression path (`core/primitives/src/state_part.rs`), which enforces explicit byte and entry-count limits before/while decompressing: [4](#0-3) [5](#0-4) 
The JSON-RPC ingress path received no equivalent depth-bounding treatment.

### Impact Explanation
`neard` typically runs the RPC server in the same process as the client/chunk-producer/validator actors. A stack overflow in the Tokio worker thread handling the JSON deserialization aborts the whole `neard` process (Rust stack overflows are not catchable panics — they trigger an immediate process abort/SIGSEGV). Any account holder or anonymous caller with network access to the node's RPC port (default `0.0.0.0:3030`) can crash that node with a single HTTP POST, with no signed transaction, gas payment, or authentication required. If sent to a validator's RPC endpoint, this removes that validator from block/chunk production until restarted — a transaction/request-triggered halt of node liveness reachable by any unprivileged RPC caller, which is explicitly one of the categories this scan is asked to evaluate.

### Likelihood Explanation
High: the request requires no special privileges, no funds, and no protocol knowledge beyond forming a deeply nested JSON array — a few dozen KB of `[` characters suffices to exceed typical 1–8 MB thread stack sizes at ~tens of bytes per recursive `serde_json::Value` parse frame. The 10 MB body-size limit does not mitigate this since nesting depth, not payload size, drives the crash.

### Recommendation
- Configure a JSON deserialization depth/recursion limit before or during body parsing (e.g., reject payloads whose bracket/brace nesting exceeds a small bound such as 64–128, checked with a streaming scan prior to full deserialization, or by switching the top-level extractor away from unguarded `serde_json::Value` parsing for untrusted input).
- Alternatively, run request-body JSON deserialization in a context with a bounded, monitored stack (e.g., a dedicated thread with `std::thread::Builder::stack_size` and a supervising watchdog) so a stack overflow cannot take down the whole `neard` process.
- Apply the same treatment to `chain/jsonrpc-primitives/src/message.rs::from_slice`/`from_str`, which are reused by non-Axum callers (e.g. tests, `client/lib.rs`).

### Proof of Concept
1. Start a `neard` node with the JSON-RPC server enabled on the default port.
2. Send: `curl -X POST http://<node>:3030/ -H 'Content-Type: application/json' --data-binary @payload.json`, where `payload.json` is generated as `{"jsonrpc":"2.0","method":"status","id":1,"params":` followed by ~200,000 `[` characters, matching `]` characters, and `}` — total well under 10 MB.
3. Observe the `neard` process crash (stack overflow / abort) while parsing the request body in `rpc_handler`, before any RPC method logic executes.
