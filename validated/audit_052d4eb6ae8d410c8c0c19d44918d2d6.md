Based on my analysis, I found a valid analog to the described bug class in the `shopify-api` package's token exchange implementation.

### Title
Session token `dest` claim not verified against caller-supplied `shop` in token exchange - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
The BLS bug pattern is: one code path validates a claim (e.g., a public key/identity) individually, while a second downstream path uses a *different, unreconciled* source of the same conceptual value to perform the security-sensitive action. `tokenExchange` exhibits the same divergence: it cryptographically validates the session token's signature/expiry/audience, but then completely discards the token's `dest` (shop) claim and instead trusts an independently supplied `shop` parameter for the actual OAuth exchange and for the shop value written into the resulting `Session`.

### Finding Description
`tokenExchange` decodes and validates the session token purely for its signature/exp/nbf/aud, but never checks that `payload.dest` (the shop the token was minted for) matches the `shop` parameter used to build the outbound request and the resulting `Session`: [1](#0-0) 

The two "validations" are:
1. `decodeSessionToken(config)(sessionToken)` — verifies the JWT signature and `aud` (API key), but its return value (containing `dest`) is discarded.
2. `sanitizeShop(config)(shop, true)` — only checks that the caller-supplied `shop` string is a syntactically valid Shopify domain; it does not compare it to the token's `dest`.

The resulting `Session` object is built using the caller-supplied `shop`, not the token's `dest`: [2](#0-1) 

Notably, the package's own published documentation instructs integrators to source `shop` from `req.query.shop` — a value fully independent of the session token — rather than deriving it from the token's `dest` claim: [3](#0-2) 

By contrast, the framework-level consumers in this monorepo (`shopify-app-remix`, `shopify-app-react-router`, `shopify-app-express`) all correctly derive `shop` from the validated token's `dest` claim before calling `tokenExchange`, e.g.: [4](#0-3) [5](#0-4) 

So the vulnerable divergence exists only in the lower-level `shopify.auth.tokenExchange` primitive exposed by `@shopify/shopify-api`, and is directly reachable by any custom (non-framework) integration built exactly as documented.

### Impact Explanation
If an app built directly on `@shopify/shopify-api` follows the official documentation and takes `shop` from a query/body parameter separately from the session token (as shown in the docs example), an attacker can supply a session token valid for shop A alongside an arbitrary `shop=B` value. The mismatch is never locally rejected — the request is dispatched to `https://B/admin/oauth/access_token` with `subject_token` minted for A. Client-side, the resulting `Session` object (if the request is accepted) is created and could be persisted keyed by shop B, corrupting session storage / creating cross-tenant confusion; even if Shopify's OAuth server rejects the mismatch, apps that don't explicitly branch on this failure could store misleading state or leak the fact that shop A is installing / interacting with shop B in logs and session storage lookups.

### Likelihood Explanation
Any app author who copies the documented pattern (`shop` from `req.query.shop`, independent of the session token) is exposed by default, since the library provides no server-side guard rail cross-checking `shop` against `payload.dest`. This does not require a privileged actor — a single anonymous/customer-controlled request to a public `/auth` token-exchange endpoint that reads `shop` from the query string is sufficient to trigger the divergence locally, even though ultimate acceptance depends on Shopify's remote OAuth server enforcing the `dest`/domain match (which is outside this repo's control and not verifiable here).

### Recommendation
In `tokenExchange` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), use the decoded session token's `dest` claim as the source of truth for the shop, or explicitly assert `sanitizeShop(config)(shop) === sanitizeShop(config)(new URL(payload.dest).hostname)` before proceeding, throwing an `InvalidJwtError`/`InvalidShopError` on mismatch — mirroring what the framework packages already do internally. Update the documentation example accordingly so it no longer suggests taking `shop` from an independent, unauthenticated query parameter.

### Proof of Concept
1. Attacker installs/opens the target app on `attacker-shop.myshopify.com`, obtaining a legitimate, validly-signed session token (`dest = attacker-shop.myshopify.com`).
2. Attacker calls the app's token-exchange endpoint (built per the documented pattern) with `shop=victim-shop.myshopify.com` and `Authorization: Bearer <token for attacker-shop>`.
3. `tokenExchange` validates the JWT signature/audience/expiry successfully (step 1 of the analog) but never compares `payload.dest` to `victim-shop.myshopify.com` (step 2 of the analog uses the untrusted value), and issues the exchange request against `https://victim-shop.myshopify.com/admin/oauth/access_token` and would construct/store a `Session{shop: 'victim-shop.myshopify.com', ...}` locally if any response is returned, without ever having verified the two "shop" concepts agree.
