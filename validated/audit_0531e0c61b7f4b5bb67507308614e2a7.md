I found a genuine rounding-inequality mismatch analogous to the reported bug class: the node-side threshold used in block validation (`NakamotoBlockHeader::compute_voting_weight_threshold`) uses ceiling division, while the signer-side agreement check in `GlobalStateEvaluator::reached_agreement` uses floor division on the *same* `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` constant against the same `total_weight`.

### Title
Signer global-state agreement threshold uses floor division while node block-approval threshold uses ceiling division, causing signer/node consensus-weight disagreement - (File: libsigner/src/v0/signer_state.rs)

### Summary
`NakamotoBlockHeader::compute_voting_weight_threshold` (node-side, used to validate a block's signature weight, `stackslib/src/chainstate/nakamoto/mod.rs:1194-1207`) rounds the required threshold **up** (`ceil(total_weight * 7 / 10)`), whereas `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` (signer-side global state machine consensus, `libsigner/src/v0/signer_state.rs:171-183`) rounds **down** (`vote_weight >= total_weight * 7 / 10`, integer floor). Both consume the identical constant `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` and the same `total_weight`, but compute two different boundary values whenever `total_weight * 7` is not a multiple of 10. [1](#0-0) [2](#0-1) 

### Finding Description
The node's block-header validation function `verify_signer_signatures` computes:
```
threshold = ceil(total_weight * 7 / 10)
```
and requires `total_weight_signed >= threshold` to accept a block's signature set. [3](#0-2) 

The signer's `GlobalStateEvaluator`, which every signer uses to determine the network's agreed-upon state (miner selection, burn view, protocol version, tx-replay set) from StackerDB gossip, computes:
```
reached_agreement(w) := w >= floor(total_weight * 7 / 10)
``` [4](#0-3) 

For any `total_weight` where `total_weight * 7 % 10 != 0` (i.e., most values), `ceil` and `floor` differ by exactly 1. Concretely, for `total_weight = 13`: `13*7=91`, `91/10=9` (floor) vs `ceil=10`. A signer subset with combined weight `9` satisfies `reached_agreement` (signer-side "we have consensus") but the identical weight `9` would be rejected by the node's `compute_voting_weight_threshold` (needs `10`). This exact same rounding-boundary flaw is the root cause class reported in the external finding: two different pieces of logic that should encode the same fractional threshold diverge because one rounds up and the other rounds down.

### Impact Explanation
This causes a minority-triggerable divergence between the signer set's internal state-machine consensus (used to decide who the "current miner" is, what burn view is canonical, and what tx-replay set is active) and the node's block-acceptance threshold. A boundary-weight coalition (just below the node's ceiling threshold but at/above the signer's floor threshold) can cause signers to believe global agreement on a state/miner has been reached and act on it (e.g., approve/extend a tenure, treat a burn view as canonical) while a node validating a block signed with that same weight would reject it as under-threshold — producing a temporary tip/state disagreement across the network. This matches the "minority-triggerable ... signer weight below threshold ... temporary tip disagreement" impact class (High).

### Likelihood Explanation
Likelihood is Medium: the divergence is deterministic and triggers whenever the weighted vote total lands exactly in the floor/ceiling gap (which happens for the large majority of `total_weight` values, since only multiples of 10/gcd(7,10)=10 avoid it). It requires only that a subset of signers (not the majority) hold weight in that boundary band — no privileged party or majority coalition is needed, just an adversarial or coincidental distribution of stacked weight across signers.

### Recommendation
Unify the rounding behavior between `NakamotoBlockHeader::compute_voting_weight_threshold` and `GlobalStateEvaluator::reached_agreement`/`reached_disagreement`. Both should use the same ceiling (or floor) semantics against `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD`, ideally by sharing a single threshold-computation helper function.

### Proof of Concept
1. Set `total_weight = 13` (e.g., 13 units of stacked weight distributed across signers).
2. Node-side: `compute_voting_weight_threshold(13)` → `(13*7)/10 + ceil_adjustment` = `9 + 1 = 10` (since `91 % 10 = 1 != 0`). [5](#0-4) 
3. Signer-side: `reached_agreement(9)` → `9 >= (13*7)/10 = 9` → `true`. [6](#0-5) 
4. A signer coalition with weight `9` is judged by the `GlobalStateEvaluator` to have reached global agreement (e.g., on the current miner or burn view), but a Nakamoto block signed by that same weight-9 coalition would be rejected by `verify_signer_signatures` with "Not enough signatures. Needed at least 10 but got 9" [7](#0-6) . This produces a state where signers act as if consensus exists while nodes reject the corresponding block — a verifiable tip/state disagreement bounded to the fee/tenure-selection layer.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
```
