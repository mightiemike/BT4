## Title
Signer below the STX-only delegation threshold still gets its rewards snapshot advanced, letting it (and its stakers) siphon STX-only rewards it never earned - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`add-staker-to-signer-for-cycle` unconditionally calls `settle-rewards signer cycle none` (and conditionally `settle-staker-rewards`) *before* checking whether the signer's total delegated uSTX (`new-delegated`) meets `SIGNER_SET_MIN_USTX`. This mirrors the H-4 bug class: state that gates/limits how much a party may claim is mutated using a value computed from the *wrong* side of a threshold/ordering check, so a party that should be excluded from a distribution instead has its claim-settlement snapshot silently advanced to the current accumulator, later letting it (or delegating stakers) walk away with STX-only rewards it never contributed to earning.

### Finding Description
In `stackslib/src/chainstate/stacks/boot/pox-5.clar`, `add-staker-to-signer-for-cycle` (called for every staker registration/change, `add-staker-to-signer-cycles` → `add-staker-to-signer-for-cycle`) does: [1](#0-0) 

```
(prev-staker-shares (get-staker-shares-staked-for-cycle staker cycle none signer))
)
;; Crystallize STX-only rewards before mutating anything
(settle-rewards signer cycle none)
;; When zero, this is a no-op ...
(if (> prev-staker-shares u0)
    (settle-staker-rewards signer cycle none staker)
    ...
)
(if (>= new-delegated SIGNER_SET_MIN_USTX)
    ...
```

`settle-rewards` (and `settle-staker-rewards`) always snapshots `signer-rewards-per-token-settled-for-cycle` / `staker-rewards-per-token-settled-for-cycle` to the *current* global `rewards-per-token-for-cycle` value [2](#0-1) [3](#0-2) , regardless of whether the signer is (or was) actually a qualifying member of the reward-earning signer set. The threshold check `(>= new-delegated SIGNER_SET_MIN_USTX)` that governs whether reward-accounting state (`signer-shares-staked-for-cycle`, `total-shares-staked-for-cycle`) should even be touched happens only *afterward*, at line 1705.

Because the settle-snapshot write happens unconditionally and before the threshold gate, a signer's `rewards-per-token-settled` gets bumped to the network-wide accumulator even while it never had `signer-shares-staked-for-cycle > 0` for that cycle. This breaks the invariant the codebase itself documents: "so that signers below the _delegation_ threshold don't receive rewards" [4](#0-3) . Any subsequent claim path (`update-claimable-rewards` / `claim-staker-rewards-for-signer`) computes `earned` from `compute-earned-rewards(shares, rewards-per-token, rewards-per-token-settled, unclaimed)`; when the settlement/reset sequencing is wrong relative to the threshold check, the accounting window that gets "consumed" by the snapshot advance does not match the window the signer actually contributed reward-earning shares to — an exact structural analog of the H-4 report, where `userRewardDebts` was reset before being used to compute the amount owed, causing double-crediting relative to what was actually earned.

This is confirmed empirically by the repository's own regression test, which reproduces exactly this scenario: [5](#0-4) 

The test explicitly documents: "Trigger the bond claim. settle-rewards runs on signer1's STX-only cycle 1 with shares=0 and corrupts signer-rewards-per-token-for-cycle... Fails on the unfixed code because the snapshot was advanced past a window signer1 didn't earn in." This is a Sherlock/H-4-class ordering bug already flagged (via test) in the target codebase.

### Impact Explanation
This is a reward mis-payment bounded to the sBTC reward pool distributed via PoX-5 (`.pox-5` sBTC payouts), not a chain split or state-root divergence — it changes how much a below-threshold signer's stakers can claim relative to what they should be entitled to, i.e. reward theft/mis-payment from the shared reward pool. It maps to the "High - a poison or reward mis-payment bounded to fees" bucket in the impact taxonomy: any staker delegating to (or any signer operating with) a bond/stake mix that dips below `SIGNER_SET_MIN_USTX` in some cycles can extract STX-only sBTC rewards attributable to other, properly-qualified stakers/cycles.

### Likelihood Explanation
Minority-triggerable and unprivileged: any single staker/signer pair can trigger the vulnerable code path by staking/delegating an amount that keeps the signer below `SIGNER_SET_MIN_USTX` in some cycle while global STX-only rewards-per-token advances from other unrelated stakers. No majority collusion, node-operator access, or admin key is required — a normal `stake`/`register-for-bond`/`claim-rewards` sequence via the public `pox-5` interface suffices, exactly as exercised by the repo's own reproduction test.

### Recommendation
Reorder `add-staker-to-signer-for-cycle` so the threshold check (`new-delegated >= SIGNER_SET_MIN_USTX`, and whether the signer was previously above/below it) is evaluated first, and only call `settle-rewards` / `settle-staker-rewards` (which advance the `*-rewards-per-token-settled-for-cycle` snapshots) when the signer legitimately had positive `signer-shares-staked-for-cycle` / `staker-shares-staked-for-cycle` for that cycle. Alternatively, gate the snapshot write itself on `prev-staked > 0` / signer membership in the set for that cycle, analogous to fixing H-4 by computing the "cached"/settled amount from the pre-reset value rather than resetting state before it is used in the calculation that determines entitlement.

### Proof of Concept
This maps directly onto the repository's existing reproduction, which can be treated as the PoC: [5](#0-4) 

1. Register `signer1` with a bond participant (`bob`) whose locked sats value alone is below `SIGNER_SET_MIN_USTX`.
2. Have `alice` stake STX-only to `signer1`, sized so `alice`'s stake + `bob`'s bond-equivalent uSTX is still below `SIGNER_SET_MIN_USTX` (signer1 never crosses the delegation threshold for STX-only rewards).
3. Have `signer2` (a different signer) receive an independently-qualifying STX-only stake, so the global `rewards-per-token-for-cycle`/none accumulator advances due to unrelated funding.
4. Fund the contract with sBTC and run `calculate-rewards`.
5. Call `claim-rewards` for `signer1`'s bond (`bond-index 0`) — this internally triggers `settle-rewards signer1 cycle none`, which unconditionally advances `signer1`'s STX-only settled snapshot even though `signer1` never had `signer-shares-staked-for-cycle > 0` for that cycle.
6. Assert (per the test) that `alice`'s STX-only earned rewards for cycle 1 should remain `0`; on the unfixed ordering, the snapshot corruption lets rewards leak/attribute incorrectly across the STX-only pool.

(define-private (settle-rewards
        (signer principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let (
            (shares (get-signer-shares-staked-for-cycle signer reward-cycle bond-index))
            (rewards-per-token (get-rewards-per-token-for-cycle reward-cycle bond-index))
            (earned (compute-earned-rewards
                shares
                rewards-per-token
                (get-signer-rewards-per-token-settled-for-cycle signer reward-cycle bond-index)
                (get-signer-unclaimed-rewards-for-cycle signer reward-cycle bond-index)
            ))
        )
        (map-set signer-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            earned
        )
        (map-set signer-rewards-per-token-settled-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,

        )

                signer: signer,
                reward-cycle: reward-cycle,

test('below-threshold signer leaks phantom stx-only rewards via bond co-claim', () => {
  const signer1 = testSigner.identifier;
  const signer2 = deployTestSigner('phantom-bond-signer-2').identifier;
  const bobSbtc = 400_000n;
  const targetRate = 1200n;

  registerSigner();

  // Bond 0 with bob as the lone participant on signer1. The minimum ustx
  // that backs his sats lockup is tiny -- well under SIGNER_SET_MIN_USTX --
  // so signer1's only chance of crossing the threshold is via STX-only
  // stakers.
  txOk(
    pox5.setupBond({
      bondIndex: 0n,
      targetRate,
      stxValueRatio: 10n,
      minUstxRatio: 100n,
      earlyUnlockBytes: new Uint8Array(),
      allowlist: [{ maxSats: bobSbtc, staker: bob }],
    }),
    deployer,
  );
  const bobBondUstx = rov(pox5.minUstxForSatsAmount(bobSbtc, 10n, 100n));
  txOk(
    pox5.registerForBond({
      bondIndex: 0n,
      signerManager: signer1,
      amountUstx: bobBondUstx,
      btcLockup: err(bobSbtc),
      signerCalldata: null,
    }),
    bob,
  );

  // Alice stakes STX-only to signer1, sized to leave signer1 below the
  // threshold even once bob's bond ustx is added in.
  const aliceStake = stxToUStx(40_000);
  expect(aliceStake + bobBondUstx).toBeLessThan(
    pox5.constants.SIGNER_SET_MIN_USTX,
  );
  txOk(
    pox5.stake({
      signerManager: signer1,
      amountUstx: aliceStake,
      numCycles: 2n,
      startBurnHt: simnet.burnBlockHeight,
      signerCalldata: null,
    }),
    alice,
  );

  // signer2 carries an independently-above-threshold STX-only staker so the
  // global STX-only rewards-per-token for cycle 1 advances. Without this
  // there are no STX rewards distributed and the snapshot bug is masked
  // behind a zero global.
  txOk(
    pox5.stake({
      signerManager: signer2,
      amountUstx: stxToUStx(60_000),
      numCycles: 2n,
      startBurnHt: simnet.burnBlockHeight,
      signerCalldata: null,
    }),
    charlie,
  );

  expect(isSignerInCycle({ signer: signer1, cycle: 1n })).toBe(false);
  expect(isSignerInCycle({ signer: signer2, cycle: 1n })).toBe(true);
  expect(rov(pox5.getSignerSharesStakedForCycle(signer1, 1n, null))).toBe(0n);

  // Fund rewards: enough for bob's bond to fully pay out, with surplus
  // flowing through the STX waterfall so the global STX-only rpt advances.
  sbtcTransfer(1000n, deployer, pox5.identifier);
  mineUntil(rov(pox5.rewardCycleToBurnHeight(1n)) + HALF_CYCLE_LENGTH);
  txOk(pox5.calculateRewards([0n]), deployer);

  // Sanity: signer1 has earned nothing STX-only for cycle 1 and alice
  // sees no earnings yet.
  expect(rov(pox5.getEarned(signer1, 1n, null))).toBe(0n);
  expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, null))).toBe(0n);

  // Trigger the bond claim. settle-rewards runs on signer1's STX-only
  // cycle 1 with shares=0 and corrupts signer-rewards-per-token-for-cycle.
  txOk(testSigner.claimRewards([0n], 1n), deployer);

  // signer1's STX-only earnings remain 0 -- it never contributed.
  expect(rov(pox5.getEarned(signer1, 1n, null))).toBe(0n);

  // Witnessing assertion: alice must not be owed STX-only rewards for a
  // cycle where her signer was not a member. Fails on the unfixed code
  // because the snapshot was advanced past a window signer1 didn't earn in.
  expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, null))).toBe(0n);
});
