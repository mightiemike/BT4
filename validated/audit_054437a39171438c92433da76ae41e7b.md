### Title
Unauthenticated Bootstrap-Declare Bypass via Sentinel Sender Address — ([File: crates/starknet_api/src/executable_transaction.rs])

### Summary
The reported Solidity bug is a class of vulnerability where a privileged/system code path is entered whenever a value in the request matches a hard-coded "self" sentinel, without verifying the caller actually has the right to trigger that special path. `crates/starknet_api/src/executable_transaction.rs` `DeclareTransaction::is_bootstrap_declare` and its usage in `AccountTransaction::execute_raw` implement an analogous pattern: any Declare V3 transaction whose `sender_address` equals the public, hard-coded constant `bootstrap_address()` (the felt encoding of the string `'BOOTSTRAP'`), with `nonce == 0` and `charge_fee == false`, skips `__validate_declare__`, skips nonce bookkeeping, and skips fee charging entirely, directly writing the class declaration to state.

### Finding Description
`DeclareTransaction::bootstrap_address()` returns a fixed, publicly known constant: [1](#0-0) 

`is_bootstrap_declare` only checks three purely-attacker-controlled fields of the transaction (`sender_address`, `nonce`, and the `charge_fee` execution flag derived from resource bounds) — there is no signature check, no ACL check, and no verification that the caller is the genesis/operator process: [2](#0-1) 

This predicate is consumed directly in the blockifier's transaction execution path to entirely skip `perform_pre_validation_stage`, the `__validate_declare__` call, and fee handling, going straight to declaring the class: [3](#0-2) 

The identical special-case exists in the Starknet OS Cairo re-execution code, gated only by `sender_address == 'BOOTSTRAP' and tx_info.nonce == 0` and a zero `max_possible_fee`: [4](#0-3) 

`charge_fee` for gateway-submitted transactions is computed purely from the transaction's own resource bounds via `enforce_fee`, which the attacker also controls by crafting a Declare V3 with all-zero resource bounds: [5](#0-4) 

The only guard that would normally reject a zero-fee transaction is `validate_resource_bounds` in the stateless validator, and the code comments explicitly document that this check is meant to be disabled during "the systems bootstrap phase": [6](#0-5) [7](#0-6) 

This is exactly the bug class in the report: a "special case" branch (`txnSender == address(this)` in the original; `sender_address == bootstrap_address()` here) is used to bypass the normal sender/authorization check, and the special value is not restricted to only be reachable by the legitimately privileged actor (the network operator performing genesis bootstrap) — it is a fixed constant that any transaction sender can place in the `sender_address` field of an ordinary RPC Declare transaction.

### Impact Explanation
While the operator is running genesis bootstrap with `validate_resource_bounds` disabled (as the code explicitly supports and documents), any unprivileged user who submits a Declare V3 transaction with `sender_address = bootstrap_address()`, `nonce = 0`, and zero resource bounds can:
- Get a class declared for free, with zero fee charged and no `__validate_declare__` executed (bypassing all authorization intended for the declare flow).
- Race the operator's legitimate bootstrap declarations: since the class-hash storage write uses `dict_update` with `prev_value == 0` enforced (a class may be declared only once) both in blockifier and the Starknet OS, an attacker who front-runs the operator's intended bootstrap declaration of a given class hash will cause the operator's subsequent legitimate bootstrap declare of the same class to fail/revert, corrupting or blocking the genesis bootstrap sequence for that class. This can manifest as an inability to complete network bootstrap, i.e., a network unable to confirm/apply the intended genesis transactions.
- Consume sequencer compilation/declare resources (CPU, storage, mempool slots) for free during the bootstrap window, since no fee is charged and no account validation gates the request.

This matches the required "concrete loss/freezing" or "honest-node divergence"/"network unable to confirm new transactions" bar, scoped strictly to the bootstrap window during which `validate_resource_bounds` is disabled by design.

### Likelihood Explanation
The likelihood is conditioned on the bootstrap window being reachable by public transaction submission (i.e., the gateway accepting RPC transactions with `validate_resource_bounds = false` before/while genesis declares are performed) and on whether `check_declare_permissions` (an `authorized_declarer_accounts` allow-list observed in `crates/apollo_gateway/src/gateway.rs` and `gateway_test.rs`) also restricts the `bootstrap_address()` sentinel specifically. I was not able to fully verify, within the tool-call budget, whether `check_declare_permissions` closes this gap by rejecting `sender_address == bootstrap_address()` for non-operator callers, or whether `validate_resource_bounds` is guaranteed to be re-enabled before the gateway accepts any public traffic. If either of those additional gates fully closes the window, the practical severity is reduced to a genesis/bootstrap-only edge case; if not, this is directly reachable by any external transaction sender during network bootstrap, exactly like the original report's PoC (crafting a transaction whose "sender" field is set to the privileged sentinel value).

### Recommendation
Do not rely solely on a value comparison (`sender_address == bootstrap_address()`) as the trust boundary for skipping validation, fee, and nonce enforcement. Instead:
- Gate the bootstrap-declare bypass on an explicit, out-of-band authorization mechanism (e.g., only accept it via a dedicated genesis/administrative API path, not the general `add_tx`/gateway RPC entrypoint), analogous to the report's remediation of moving the check to the entry function (`submitSlowModeTransaction`) rather than relying on a permissive internal condition.
- If the bootstrap flow must go through the generic gateway, ensure `check_declare_permissions`/`authorized_declarer_accounts` (or an equivalent allow-list) unconditionally denies `bootstrap_address()` sender transactions from any non-operator source, and ensure `validate_resource_bounds` cannot be left disabled while the gateway is publicly reachable.
- Add an explicit test asserting that an arbitrary unprivileged RPC transaction using `sender_address = bootstrap_address()` is rejected by the gateway/mempool layer before reaching blockifier/OS execution.

### Proof of Concept
1. During the genesis bootstrap phase (when `StatelessTransactionValidatorConfig::validate_resource_bounds` is `false`, as documented in `stateful_transaction_validator.rs`), craft an RPC Declare V3 transaction with:
   - `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150` — the felt encoding of `'BOOTSTRAP'`),
   - `nonce = 0`,
   - all resource bounds set to zero (as done in `generate_bootstrap_declare` in `crates/mempool_test_utils/src/starknet_api_test_utils.rs`, lines 585–595),
   - an arbitrary valid `class_hash`/`compiled_class_hash` pair for a class not yet declared.
2. Submit it via the public gateway `add_tx` endpoint.
3. `enforce_fee` computes `charge_fee = false` from the zero resource bounds, `is_bootstrap_declare` returns `true`, and `AccountTransaction::execute_raw` skips `perform_pre_validation_stage`, `__validate_declare__`, and fee charging, declaring the class directly.
4. If the operator later submits their own legitimate bootstrap declare for the same `class_hash`, the `dict_update` `prev_value == 0` assertion fails because the attacker already declared it, breaking the intended genesis flow.
