### Title
Systemic Precision Loss in Vote-Reward VI Accumulation Leads to Unclaimable/Permanently Lost Witness Rewards - (File: chainbase/src/main/java/org/tron/core/service/RewardViCalService.java, chainbase/src/main/java/org/tron/core/store/DelegationStore.java)

### Summary
The reward-index ("VI") accounting used to split a super representative's (SR's) block/transaction-fee reward among its voters computes the per-cycle delta index using integer (`BigInteger`) floor division: `deltaVi = reward * DECIMAL_OF_VI_REWARD / voteCount`. Because this division truncates, the aggregate amount later reconstructible by voters (`deltaVi * userVote / DECIMAL_OF_VI_REWARD`, also floor-divided) is systematically less than the `reward` value that was credited to the SR's reward bucket via `DelegationStore.addReward`. The shortfall is never tracked, never paid to anyone, and there is no admin/sweep function to recover it — directly analogous to the `notifyRewardAmount` precision-loss bug in the referenced report, where `rate = amount / duration` truncation leaves undistributed funds permanently stuck.

### Finding Description
`DelegationStore.addReward(cycle, srAddress, value)` records a witness's earned reward for a cycle as a plain `long` [1](#0-0) . This reward is credited from real economic value (block rewards / transaction fee rewards) via `MortgageService.payBlockReward` / `payTransactionFeeReward` → `payReward`, which calls `delegationStore.addReward(cycle, witnessAddress, value)` [2](#0-1) .

To let voters claim their proportional share, the protocol accumulates a per-witness reward index (`Vi`) using floor (truncating) integer division:
```
BigInteger deltaVi = BigInteger.valueOf(reward)
    .multiply(DECIMAL_OF_VI_REWARD)
    .divide(BigInteger.valueOf(voteCount));
``` [3](#0-2) 
The same pattern (and constant `DECIMAL_OF_VI_REWARD = 10^18`) appears in `RewardViCalService.accumulateWitnessVi` [4](#0-3) .

When a voter later withdraws/queries their reward, the amount actually paid is computed by reversing this with another floor division:
```
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
```
This exact pattern is used in three independently reachable paths:
- `MortgageService.computeReward` — used by `withdrawReward`/`queryReward`, invoked from normal TRX-layer actuators such as `WithdrawBalanceActuator`/`UnfreezeBalanceV2Actuator` via broadcast transactions [5](#0-4) 
- `RewardViCalService.getNewRewardAlgorithmReward`, used as a fallback path for old-algorithm cycles [6](#0-5) 
- `VoteRewardUtil.computeReward`, used by TVM native contract processors (`freezeBalanceV2`/`unfreezeBalanceV2`/`withdrawReward` precompiles), i.e., directly triggerable via a contract call from an anonymous TVM execution [7](#0-6) 

Because both the accumulation step (`reward * 10^18 / voteCount`) and the redemption step (`deltaVi * userVote / 10^18`) floor-divide independently, for any voter whose `voteCount` does not evenly divide `reward * 10^18`, and any `userVote` for which `deltaVi * userVote` is not an exact multiple of `10^18`, the sum of rewards actually claimable by all of a witness's voters is strictly less than the `reward` value that was originally credited via `addReward`. There is no code path that redistributes, tracks, or allows an admin/witness to reclaim this residual value — it is permanently and silently lost, exactly mirroring the `StakedEXA.notifyRewardAmount` bug class where `rate * duration < amount`.

### Impact Explanation
Although `DECIMAL_OF_VI_REWARD` (`10^18`) makes the per-transaction rounding error tiny in relative terms, this computation runs on every SR's reward for every maintenance cycle across the entire network's lifetime, and the resulting dust is unrecoverable (no sweep function, no reconciliation, no error accounting). Over the life of the chain, this results in a systemic, monotonically growing amount of previously-minted TRX that is permanently unclaimable by any account, constituting an accounting/economic-integrity defect that matches the "asset or accounting corruption" acceptance criterion. It is not a full node RCE or key-disclosure bug, and any single occurrence is economically negligible, but the compounding effect across all witnesses/cycles is a legitimate accounting-corruption class analog to M-13.

### Likelihood Explanation
This occurs automatically and unconditionally on every reward accumulation and every reward withdrawal for every vote/witness pair — it requires no privileged actor, no malicious peer, and is reachable via ordinary `WithdrawBalanceContract`/`UnfreezeBalanceV2Contract` broadcast transactions as well as TVM `freezeBalanceV2`/`unfreezeBalanceV2`/vote-reward native contract calls. Likelihood of triggering the precision loss is effectively 100% (any non-power-of-two `voteCount`/`userVote` combination), though the individual per-occurrence value lost is small.

### Recommendation
- Track the intentional truncation remainder per cycle/witness (e.g., carry-forward the modulo remainder from `reward % voteCount` into the next cycle's reward pool rather than discarding it), similar to carrying rounding error forward, or
- Use higher-precision fixed-point accounting with a final reconciliation step that flushes any accumulated remainder back into the witness's/voters' claimable balance, or
- Add a mechanism (or periodic system transaction) that computes and either redistributes or explicitly and transparently burns the residual dust, rather than allowing it to silently disappear from the accounting without any trace.

### Proof of Concept
Conceptual (cannot be run without on-chain state, but demonstrates the arithmetic):
```
reward = 7            // SR's reward for cycle
voteCount = 3          // total votes for SR that cycle
DECIMAL_OF_VI_REWARD = 10^18

deltaVi = (7 * 10^18) / 3   // BigInteger floor division
        = 2333333333333333333   (exact value 2.333...e18 truncated)

// voter A has userVote = 1, voter B has userVote = 1, voter C has userVote = 1
voterReward = deltaVi * 1 / 10^18 = 2   (each voter gets floor(2.333) = 2)

totalPaidOut = 2 + 2 + 2 = 6   // < original reward of 7

// 1 unit of the original 7 credited to the SR's reward bucket
// is never paid to any voter and is not recoverable by any admin call.
```
This is the same structural bug as M-13's `rate = amount / duration` truncation: a value intended for full distribution is split via a lossy division with no reconciliation, and the shortfall becomes permanently unclaimable.

    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record

      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
