## Title
Unrestricted-content asset description/URL and account name fields enable stored XSS payloads on-chain - (File: `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`)

### Summary
The `AssetIssueActuator` validates the `AssetIssueContract`'s `description` and `url` fields using `TransactionUtil.validAssetDescription` and `TransactionUtil.validUrl`, both of which only enforce a maximum byte length and do not restrict the byte/character content of the field. [1](#0-0)  This is functionally the same "unvalidated user-supplied string later rendered by a client" bug class described in the external report about `tokenSymbol`, except here it applies to `description`/`url` (and account names), which — unlike `assetName`/`abbr` — are explicitly intended to be shown to end users by wallets/explorers.

### Finding Description
`TransactionUtil` implements two distinct validators for on-chain string fields:
- `validReadableBytes` restricts bytes to the printable ASCII range `0x21`–`0x7E`, used for `assetName` and `abbr`. [2](#0-1) 
- `validBytes` only checks the byte-array length, with no character restriction, used for `description` (`validAssetDescription`), `url` (`validUrl`), and account names (`validAccountName`). [3](#0-2) 

Because `validAssetDescription`/`validUrl` accept arbitrary bytes (including HTML/JS markup, control characters, or any binary content) up to 200/256 bytes respectively, a user creating a TRC10 asset via `AssetIssueActuator.validate()` can embed arbitrary payloads into `description` and `url`, which are accepted and persisted into the `AssetIssueStore`/`AssetIssueV2Store` on-chain state. [1](#0-0)  The same unrestricted-content issue applies to account names via `validAccountName`, which is also backed by length-only `validBytes`. [4](#0-3) 

These fields are explicitly designed to be human-facing metadata (description text, a URL link, account display name) — unlike `assetName`, which the client comment in the report explicitly notes is "used for mapping" internally and not displayed. Off-chain consumers (block explorers, wallets, dApp frontends) that query and render these fields verbatim (as is standard practice for TRC10 token descriptions/URLs) would reflect unsanitized on-chain content directly into their UI, exactly matching the stored-XSS root cause pattern in the external report.

### Impact Explanation
Any unprivileged account can issue a TRC10 asset (subject to paying the `AssetIssueFee`) with a `description` or `url` containing script/markup payloads that get permanently stored on-chain and are reachable by any off-chain reader (via `wallet/GetAssetIssueByName`-style APIs) for the lifetime of the token. If a downstream explorer or wallet displays these fields without sanitizing/escaping (a common assumption on-chain content is "just a string"), this leads to stored XSS against any user viewing that asset's page, potentially compromising session data or triggering unauthorized actions in that frontend context.

### Likelihood Explanation
High for reachability: issuing a TRC10 asset is a standard unprivileged-user operation, and the vulnerable fields are validated purely on length, not content, so no special conditions are needed to embed arbitrary payloads. However, the actual XSS trigger depends on a downstream off-chain application failing to sanitize output — analogous to the original report, this is a defense-in-depth gap in the contract-layer validation rather than an implementation bug in java-tron's consensus logic itself.

### Recommendation
Restrict `description` and `url` (and `accountName`) to a safe character set (or explicitly disallow angle brackets / script-relevant characters), similar to the `validReadableBytes` restriction already applied to `assetName`/`abbr`, or clearly document that all on-chain string fields must be treated as untrusted and sanitized (e.g., with an HTML-sanitization library) by any consumer before rendering.

### Proof of Concept
1. Submit an `AssetIssueContract` transaction with `description` set to bytes such as `<script>alert(1)</script>` (29 bytes, well under the 200-byte `MAX_ASSET_DESCRIPTION_LEN`) and/or `url` set to a similar payload (under 256 bytes).
2. `AssetIssueActuator.validate()` passes because `validAssetDescription`/`validUrl` only check `bytes.length <= maxLength`. [5](#0-4) 
3. The asset is created and the payload is persisted in `AssetIssueStore`.
4. Any off-chain reader querying this asset and rendering `description`/`url` without sanitization executes the embedded script in the viewer's browser context.

  private static boolean validBytes(byte[] bytes, int maxLength, boolean allowEmpty) {
    if (ArrayUtils.isEmpty(bytes)) {
      return allowEmpty;
    }
    return bytes.length <= maxLength;
  }

  private static boolean validReadableBytes(byte[] bytes, int maxLength) {
    if (ArrayUtils.isEmpty(bytes) || bytes.length > maxLength) {
      return false;
    }
    // b must be readable
    for (byte b : bytes) {
      if (b < 0x21) {
        return false; // 0x21 = '!'
      }
      if (b > 0x7E) {
        return false; // 0x7E = '~'
      }
    }
    return true;
  }
