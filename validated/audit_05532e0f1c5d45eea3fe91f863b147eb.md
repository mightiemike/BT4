# No vulnerability found for this question.

The claim rests on a misunderstanding of how the batched verification's soundness argument works, and the implementation explicitly guards against exactly the failure mode described.

**Why duplicate `A[i] == A[j]` cannot cause cancellation:**

In `sigma_protocol::verify`, the batched check computes
`\sum_{i \in [m]} \beta^i (A_i + e f_i(X) - \psi_i(\sigma)) = 0` [1](#0-0) 

The `betas` vector is not derived from the *values* of `A[i]`, but is simply `[1, β, β², ..., β^{m-1}]` for a single scalar `β` — the position `i` in the vector determines the exponent, not the value of `A[i]`. So even if `A[i] == A[j]` for `i ≠ j`, their corresponding weights `β^i` and `β^j` are generically *different* scalars (they only coincide if `i == j`). Duplicate commitment points therefore do not introduce any algebraic relation that lets two error terms `e_i = A_i + e f_i(X) - \psi_i(\sigma)` and `e_j` cancel each other via the weights — cancellation would require the attacker to solve `β^i e_i + β^j e_j + ... = 0` for the *specific* `β` that will be derived, before that `β` exists. [2](#0-1) 

**Why the prover can't pick `β` adaptively:**

Critically, `β` is derived from a Fiat-Shamir hash that includes both the commitment `compressed_A` *and* the response `sigmas` (i.e., `σ`, which itself encodes the witness-dependent responses):

```
seed.append(bcs::to_bytes(sigmas));
let beta = new_scalar_uniform_from_64_bytes(sha2_512(seed)).extract();
``` [3](#0-2) 

This means the attacker must fully commit to `A` and `σ` (and therefore to the fixed, at-that-point-determined error terms `e_i`) *before* `β` is computed. Since `\sum_i \beta^i e_i` is a polynomial in `β` of degree `< m` that is not identically zero unless every `e_i = 0`, by the Schwartz-Zippel lemma the probability that a *given, already-fixed* nonzero coefficient vector happens to vanish at the actual (hash-derived, effectively random) `β` is negligible — this holds regardless of whether `A` contains duplicate points, because duplication only affects which coefficient vectors are achievable, not the unpredictability of `β` itself.

This exact security property — that `β` (and thus batching soundness) must depend on `σ` and be fixed before the prover has freedom to shape it — is explicitly documented and regression-tested in `sigma_protocol_fiat_shamir.move`:

> "Soundness of the aggregated check ... requires β to be unpredictable to the prover at the moment σ is committed. That requires σ to be part of the Fiat-Shamir transcript that derives β." [4](#0-3) 

**Conclusion:** Producing a proof that passes the batched `verify` while failing the per-equation `verify_slow` check would require the attacker to invert SHA2-512 (find `A`, `σ` such that the resulting `β` satisfies a specific polynomial equation chosen in advance) — this is a standard, cryptographically sound random-linear-combination batching technique, and duplicate `A[i] == A[j]` entries provide no exploitable structural degeneracy. No unprivileged input path corrupts committed state, proof material, or authenticated responses under this scenario.
