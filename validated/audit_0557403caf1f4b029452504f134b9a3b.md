### Title
Non-atomic `has_in_flight_tx` reset lets a panicking promise callback permanently brick the NEAR Wallet Contract - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The bug-class hint describes a `nonReentrant` guard whose state is not correctly cleared across a required re-entry point, permanently blocking the intended flow. The nearest reachable analog in the in-scope nearcore surface is the `WalletContract`'s `has_in_flight_tx` guard, which is reset only as the *first statement* of each promise callback. Because NEAR discards all state writes of a receipt that fails/panics (`runtime/runtime/AGENTS.md:64` — "When a receipt fails, its state changes are rolled back using `TrieUpdate`"), any panic occurring anywhere in a callback body after the `self.has_in_flight_tx = false;` write causes that write to be rolled back along with everything else, leaving the flag permanently `true`.

### Finding Description
`WalletContract::rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`) is the sole entry point for a user's relayed Ethereum-style transaction. It guards against concurrent execution with a boolean flag: [1](#0-0) 

Once a transaction is accepted, `has_in_flight_tx` is set to `true` and a promise chain is scheduled (`address_check_callback`, `nep_141_storage_balance_callback`, or `rlp_execute_callback`, depending on transaction kind — see the dispatch in `inner_rlp_execute`, `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:412-470`). Each of these `#[private]` callbacks resets the flag to `false` as its very first statement, e.g.: [2](#0-1) [3](#0-2) 

but only performs subsequent state-mutating work (nonce increments, new promise chaining, refunds) after that point. In NEAR's execution model, state changes are visible only if the executing receipt completes successfully; if the same receipt later panics/fails for any reason (out-of-gas, an unhandled arithmetic/logic error, a malformed cross-contract response that is not defensively handled, etc.), *all* of that receipt's state changes — including the earlier `has_in_flight_tx = false` write — are discarded: [4](#0-3) 

Because the `true` value was already durably committed when `rlp_execute` (or an intermediate callback) originally dispatched the promise, a callback that fails after clearing the flag in memory leaves the on-chain flag stuck at `true` forever. Every subsequent call to `rlp_execute` will then hit the early-return guard and be permanently rejected: [5](#0-4) 

This is structurally the same failure mode as the Renzo `OperatorDelegator` bug: a reentrancy/one-in-flight guard whose clearing is entangled with the very code path that is expected to legitimately complete the operation, such that a failure in that path leaves the guard poisoned permanently rather than being reset independently and atomically.

### Impact Explanation
If the flag becomes permanently stuck at `true`, the wallet contract account (an eth-implicit account holding the user's funds and permissions) can never again process an `rlp_execute` call. Since this is the only entry point through which the Ethereum-style user issues Near actions (transfers, function calls, key management) from this account, the account's assets and access become effectively frozen — an unprivileged relayer or the interacting NEP-141 token contract can trigger this denial merely by causing the scheduled callback receipt to fail. This matches the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Triggering requires only an unprivileged actor (a relayer submitting `rlp_execute`, or a NEP-141 token contract that the wallet interacts with during an `ERC20Transfer` emulation) to cause the dispatched callback receipt to fail after the flag has been logically cleared but before the receipt commits — e.g., attaching insufficient gas to the callback so the callback runs out of gas partway through, or a token contract returning an oversized/malformed `storage_balance_of` response that trips an unhandled panic path deeper in `nep_141_storage_balance_callback`'s follow-up promise construction. This does not require validator, network, or operator privileges; it is reachable purely through the public transaction/contract-call surface. Confirming the exact panicking sub-path (e.g., exact gas accounting for `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) would require deeper simulation than the indexed context allows, so the precise trigger condition is not fully verified here — the systemic risk is the architecture (state cleared mid-execution rather than atomically/independently of receipt success), not necessarily an already-identified exploitable panic in the current callback bodies.

### Recommendation
Do not rely on state mutated mid-execution of a callback to represent the "no transaction in flight" invariant when that same execution can subsequently fail. Instead:
- Reset `has_in_flight_tx` in a way that is independent of the callback's success/failure, e.g., by giving each callback a guaranteed-to-succeed tail step, or by tracking in-flight status via receipt/promise indices that are inherently consistent with the runtime's rollback semantics.
- Alternatively, add a recovery/reset mechanism (e.g., an owner-callable "force reset" that requires proof the in-flight promise actually resolved or timed out) so that a permanently stuck flag cannot brick the account irrecoverably.

### Proof of Concept
Not independently verified end-to-end due to index limitations (exact gas-accounting/panic conditions of `nep_141_storage_balance_callback`/`address_check_callback` were not fully traced). The reasoning is grounded in the documented rollback-on-failure semantics of the NEAR runtime (`runtime/runtime/AGENTS.md:64`) combined with the callback structure in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:194-317`, where `has_in_flight_tx = false` is written before any operation in the same execution that could still fail. A full PoC would require deploying the wallet contract plus a malicious/misbehaving NEP-141 token on a local NEAR sandbox, issuing an `rlp_execute` ERC20-transfer emulation, and constructing a callback-gas/response condition that causes `nep_141_storage_balance_callback` to fail after entry, then confirming subsequent `rlp_execute` calls are permanently rejected.
