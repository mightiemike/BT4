Confirmed: `scrape_timestamp` is derived from `L1EventsScraper::fetch_events` as `self.clock.unix_now()` at the moment of each poll [1](#0-0) , so every `L1HandlerTransaction` scraped within a single polling window (bounded only by `max_blocks_per_fetch`, default 1000 L1 blocks per fetch, default 30s polling interval) shares the exact same `scrape_timestamp` key, and `TransactionManager::maintain_indices` appends each to the same `Vec<TransactionHash>` bucket in `proposable_index` [2](#0-1) . ### Title
Unbounded per-timestamp `proposable_index` bucket enables O(n²) L1 handler transaction manager DoS - (File: crates/apollo_l1_events/src/transaction_manager.rs)

### Summary
`TransactionManager::proposable_index` groups pending L1 handler transactions by `scrape_timestamp` into `Vec<TransactionHash>` buckets. An L1 message sender (in-scope, unprivileged actor) can flood many `sendMessageToL2` calls within a single scraper polling window, causing thousands of transaction hashes to land in a single bucket. Every subsequent state transition that removes a tx from that bucket does an unbounded linear scan (`iter().position()`) over the whole vector, degrading to O(n) per removal and O(n²) overall as the backlog of L1 handler transactions is processed across many blocks.

### Finding Description
`fetch_events` computes one `scrape_timestamp = self.clock.unix_now()` per poll and stamps it on every `Event::L1HandlerTransaction` produced from that poll's `eth_getLogs` window [1](#0-0) . The window can span up to `max_blocks_per_fetch` (1000) L1 blocks per poll [4](#0-3) , so a large L1-side burst of messages can all be scraped together and assigned identical `scrape_timestamp`s.

`L1EventsProvider::add_events` feeds each such event into `TransactionManager::add_tx` unconditionally, which is permissionless with respect to volume — there is no cap on the number of L1 handler transactions that can be registered [5](#0-4) .

`maintain_indices` inserts the new tx hash into `self.proposable_index.entry(scrape_timestamp).or_default()` [6](#0-5) . All txs scraped in the same poll accumulate into one shared `Vec<TransactionHash>`.

When a tx becomes non-proposable (committed via `commit_txs`, cancelled via `finalize_cancellation`, or consumed via `consume_tx`, all of which route through `with_record` → `maintain_indices`), removal from that bucket is:
```
if let Some(index_in_vec) = tx_hashes.iter().position(|&h| h == tx_hash) {
    tx_hashes.remove(index_in_vec);
    ...
}
``` [3](#0-2) 

This is the same bug class as the referenced report: an unbounded array grown by external/adversarial input, with per-element removal implemented as a linear scan (`Vec::remove`/`position` instead of a keyed structure), so the cost of removing one element from a bucket is proportional to the size of the whole poisoned bucket, and total cost to drain the backlog is quadratic.

The code even documents awareness of a *small* expected fan-out ("Linear scan, but we expect this to be a small number of transactions (< 10 roughly)") for the separate `get_txs` cutoff-scan [7](#0-6) , but this assumption is not enforced — an adversary directly controls how many L1 handler txs get assigned to the same `scrape_timestamp` bucket by simply emitting many `sendMessageToL2` calls in the L1 blocks covered by one poll.

### Impact Explanation
Every block, `commit_txs` is invoked with the set of L1 handler txs committed/rejected in that block [8](#0-7) , and each of these calls `with_record` → `maintain_indices`, which performs the O(bucket-size) scan. If an attacker inflates one bucket to e.g. tens of thousands of entries, every block that processes even a single L1 handler tx from that poll pays an O(bucket-size) cost, and processing the whole poisoned backlog costs O(n²) CPU time on the sequencer. This can meaningfully slow down block building/commit (`Batcher`/`L1Provider::commit_block`) for every node, potentially causing the sequencer to fall behind block-production timing — a resource-exhaustion/liveness-degradation issue reachable purely from an L1 message sender, without any need for a malicious operator, proposer, or validator collusion.

### Likelihood Explanation
Reachable with only ordinary L1 access: sending many cheap `sendMessageToL2` calls (each requiring only a small L1 fee) within the ~30s/1000-block scraper window is inexpensive relative to the sequencer-side cost imposed. No special contract behavior (unlike the Visor NFT example) is even needed — plain repeated legitimate L1→L2 messages suffice, matching the judge's observation in the original report that "it doesn't need a malicious actor to happen... can happen by simply being very successful."

### Recommendation
Do not key `proposable_index` buckets solely by coarse wall-clock `scrape_timestamp`; either (a) bound the size of any bucket the poller can create per scrape by chunking events with, e.g., a synthetic sub-timestamp/sequence counter so buckets stay small, or (b) replace the `Vec<TransactionHash>` bucket with an order-preserving indexed structure (e.g., `IndexSet<TransactionHash>` or a secondary hashmap from `TransactionHash` to its position) so removal from `maintain_indices` is O(1) instead of O(n).

### Proof of Concept
1. An attacker calls the L1 `sendMessageToL2` (or equivalent) function many times (e.g., 50,000 times) within the L1 block range that a single scraper poll will cover (bounded by `max_blocks_per_fetch`, default 1000 blocks, easily reachable within one ~12s-block-time window given `polling_interval_seconds` default 30s).
2. `L1EventsScraper::fetch_events` scrapes all these `LogMessageToL2` events in one call and stamps them all with the same `scrape_timestamp` [1](#0-0) .
3. `add_events`/`add_tx` inserts all 50,000 hashes into a single `proposable_index` bucket [6](#0-5) .
4. As the sequencer proposes/commits blocks including these L1 handler txs over subsequent blocks, each `commit_txs` call triggers a `position()` linear scan over the shrinking-but-still-large bucket for every committed hash [3](#0-2) , causing cumulative O(n²) CPU cost on the block-commit path across the ~50,000/`max_l1_handler_txs_per_block`-many blocks needed to drain the backlog.
