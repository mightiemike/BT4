## Finding

The Aptos analog to the Dexe "inconsistent decimal treatment" bug is an inconsistent treatment of which fields of `TransactionInfo` are actually verified when comparing a locally-computed `TransactionOutput` against an authenticated, proof-covered `TransactionInfo`. Just as Dexe checked some fields (`totalTokenProvided`) after normalization while skipping normalization elsewhere, Aptos's `ensure_match_transaction_info` checks status, gas, write-set hash, and event root hash, but **silently skips the state-checkpoint-hash fields** — the very fields that assert the correctness of the accumulated ledger state (JMT) root.

### Title
`TransactionOutput::ensure_match_transaction_info` never validates `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, allowing replay-verification to pass despite a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the function used by replay-verification tooling to confirm that locally re-executed transactions match the authenticated, backed-up `TransactionInfo` for that version. It checks execution status, gas used, write-set hash (`state_change_hash`), and event root hash, but it never compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against anything computed locally. This gap is explicitly acknowledged in a TODO comment in the same function [2](#0-1) , but the comment understates the scope: `state_checkpoint_hash` (the primary Sparse-Merkle/JMT root of the *entire* world state after a checkpoint) is unconditionally unverified, not only the trading-native fields.

### Finding Description
`ensure_match_transaction_info` is called from `ChunkExecutor::verify_execution`, the routine backing `db-tool replay-on-archive` and `aptos-debugger`'s replay-verify path [3](#0-2) . In that flow, historical transactions are re-executed from scratch via `DoGetExecutionOutput::by_transaction_execution`, and each resulting `TransactionOutput` is compared directly against the archived, ledger-info-signed `TransactionInfo` using `ensure_match_transaction_info` — **without routing through `DoStateCheckpoint`**, which is the only place that actually recomputes and checks the accumulated state-tree root against `known_state_checkpoints` derived from `TransactionInfo` [4](#0-3) .

Because `verify_execution` bypasses `DoStateCheckpoint`, the only integrity checks performed on the replayed output are for the write set of the *current* transaction (`state_change_hash`), events, gas, and status — none of which certify that the *cumulative* Sparse-Merkle/JMT root produced by replay matches the archived, ledger-info-authenticated `state_checkpoint_hash`. A bug confined to the JMT construction/commit path (sharded JMT assembly, hot-state merge, or the "position"/trading-native state tree introduced alongside this code) that corrupts the accumulated state root — while leaving individual write sets, events, gas, and status unchanged — would go completely undetected by replay-verify, even though `TransactionInfo::state_checkpoint_hash` is precisely the field meant to catch exactly this class of divergence [5](#0-4) .

This differs materially from the API's own conversion path (`into_transaction_info`, `types/src/proof/definition.rs`), which propagate/authenticate the correct hash fields, and from the accumulator/proof verification code (`AccumulatorProof::verify`, `TransactionInfoListWithProof::verify`) which correctly binds proofs to root hashes. It also differs from `TransactionOutputListWithProof::verify` — used by the live state-sync "apply outputs" path — which also omits `state_checkpoint_hash` checking, but that path is separately protected because `DoStateCheckpoint::get_state_checkpoint_hashes` cross-checks the computed root against `known_state_checkpoints` sourced from the proof-verified `TransactionInfo` [6](#0-5) . The `verify_execution`/replay-verify path has no equivalent safety net.

### Impact Explanation
Replay-verify (`db-tool replay-on-archive`, `aptos-debugger`) is the primary mechanism used to certify, before a software/VM upgrade reaches validators, that new execution logic reproduces byte-identical, root-identical historical ledger state. Because `ensure_match_transaction_info` never checks the state-checkpoint hash, replay-verify can report a clean, successful replay of mainnet history even when the underlying committed state root (JMT/state-tree) has silently diverged from the authenticated on-chain value. This is a genuine "replay ... proof verification" integrity gap per the state-integrity gate: a wrong accumulated state root can be accepted as a correct replay result, undermining the safety guarantee replay-verify exists to provide before code ships to consensus.

### Likelihood Explanation
This is not a hypothetical: it is a documented, currently-shipping gap in the one function whose entire purpose is cross-checking replayed output against authenticated ledger data. Any state-tree-construction bug (as opposed to a VM/write-set bug) — including ones introduced by ongoing work in the sharded-JMT/hot-state/"trading-native" state summary code visible nearby in `do_state_checkpoint.rs` — would silently pass replay-verify today.

### Recommendation
Extend `ensure_match_transaction_info` (and ideally `TransactionOutputListWithProof::verify`) to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values wherever those are available, or route `verify_execution` through `DoStateCheckpoint` so the state-tree root is independently recomputed and compared, mirroring the protection already present in the chunk-apply path.

### Proof of Concept
1. Instrument/modify the state-tree commit path (e.g., the sharded-JMT merge in `DoStateCheckpoint::run`/`compute_position_checkpoint`) so it computes a JMT root that is byte-different from the correct one, while leaving per-transaction write sets, events, gas, and status untouched (e.g., swap the order two leaves are merged in a way that changes the root hash but not any single write op).
2. Run `db-tool replay-on-archive` (or `aptos-debugger`) against a real backup, driving `ChunkExecutor::verify_execution` at `execution/executor/src/chunk_executor/mod.rs:648-707`.
3. Observe that `txn_out.ensure_match_transaction_info(...)` returns `Ok(())` for every transaction because it never inspects `txn_info.state_checkpoint_hash()`, even though the locally computed state root differs from the one recorded in the archived, ledger-info-signed `TransactionInfo`.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())

    fn verify_execution(
        &self,
        transactions: &[Transaction],
        persisted_aux_info: &[PersistedAuxiliaryInfo],
        transaction_infos: &[TransactionInfo],
        write_sets: &[WriteSet],
        event_vecs: &[Vec<ContractEvent>],
        begin_version: Version,
        end_version: Version,
        verify_execution_mode: &VerifyExecutionMode,
    ) -> Result<Version> {
        // Execute transactions.
        let parent_state = self.commit_queue.lock().latest_state().clone();
        let state_view = self.state_view(parent_state.latest())?;
        let txns = transactions
            .iter()
            .take((end_version - begin_version) as usize)
            .cloned()
            .map(|t| t.into())
            .collect::<Vec<SignatureVerifiedTransaction>>();

        let auxiliary_info = persisted_aux_info
            .iter()
            .take((end_version - begin_version) as usize)
            .map(|persisted_aux_info| AuxiliaryInfo::new(*persisted_aux_info, None))
            .collect::<Vec<_>>();
        let onchain_config = chunk_onchain_config(&state_view)?;
        let execution_output = DoGetExecutionOutput::by_transaction_execution::<V>(
            &V::new(),
            txns.into(),
            auxiliary_info,
            &parent_state,
            state_view,
            onchain_config,
            TransactionSliceMetadata::chunk(begin_version, end_version),
        )?;
        // not `zip_eq`, deliberately
        for (version, txn_out, txn_info, write_set, events) in multizip((
            begin_version..end_version,
            &execution_output.to_commit.transaction_outputs,
            transaction_infos.iter(),
            write_sets.iter(),
            event_vecs.iter(),
        )) {
            if let Err(err) = txn_out.ensure_match_transaction_info(
                version,
                txn_info,
                Some(write_set),
                Some(events),
            ) {
                return if verify_execution_mode.is_lazy_quit() {
                    error!("(Not quitting right away.) {}", err);
                    verify_execution_mode.mark_seen_error();
                    Ok(version + 1)
                } else {
                    Err(err)
                };
            }
        }
        Ok(end_version)
