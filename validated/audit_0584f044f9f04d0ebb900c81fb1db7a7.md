## Title
Bouncer floor-division builtin gas cost derivation systematically under-counts real proving cost, letting a block exceed its configured `proving_gas` capacity - (File: crates/blockifier/src/bouncer.rs)

### Summary
`BuiltinInstanceLimits::induced_gas_costs` derives a fixed per-instance proving-gas cost for every Cairo builtin/opcode as `cost = floor(proving_gas / limit)` [2](#0-1) . This value is used both to charge each transaction's marginal contribution to the block's `proving_gas` weight in `get_tx_weights`/`try_update`/`verify_tx_weights_within_max_capacity` [3](#0-2)  and is additively accumulated per transaction into `Bouncer.accumulated_weights` and checked against `bouncer_config.has_room` before admitting each transaction into the proposed block [4](#0-3) .

Because `cost` is rounded down (`floor`) from the "true" proportional cost `proving_gas / limit`, the sum of per-instance charges for any builtin whose usage approaches its per-block `limit` under-counts the real fractional cost by up to `limit * (fractional remainder)` — bounded by nearly a full unit of rounding error per instance, aggregated across up to `limit` instances of that single builtin. This mirrors the `votingPower` rounding bug: the discretized "shares" (per-instance gas costs) that are summed up do not add up to the true total (`proving_gas`) the block-capacity check is meant to enforce.

### Finding Description
`BouncerConfig::builtin_gas_costs()` calls `induced_gas_costs(self.block_max_capacity.proving_gas)`, deriving one fixed `u64` cost per Cairo primitive (builtin/opcode) from `proving_gas.0 / limit.get()` (integer floor division) [5](#0-4) . This per-instance rate is subsequently multiplied by the number of instances a transaction actually uses (via `cairo_primitives_to_gas`, used inside `proving_gas_from_cairo_primitives_and_sierra_gas`) to compute the transaction's contribution to the block's `proving_gas` bouncer weight, which is added to the accumulated block weights and checked with `has_room` before the transaction is admitted [6](#0-5) [7](#0-6) .

Since `floor(proving_gas/limit)` discards the fractional remainder, using `limit`-many instances of that builtin (the maximum a fully-packed block permits) is charged `limit * floor(proving_gas/limit)` gas units, which is strictly less than the intended `proving_gas` (the true budget). The regression test confirms real-world magnitude of this rounding: at a 6B proving-gas budget, `range_check` (limit 66,666,666) derives a per-instance cost of only 90, and `keccak` (limit 10,000) derives exactly 600,000 [8](#0-7) ; for `range_check`, `66,666,666 * 90 = 5,999,999,940`, already ~60 gas short of the nominal 6,000,000,000 budget for a single builtin type, and the shortfall compounds when multiple builtin types are simultaneously packed near their limits across many transactions in the same block, or across a full block of transactions each individually maximizing rounding-favorable builtin ratios.

A transaction sender fully controls how many instances of each builtin their Cairo/Sierra code invokes (e.g., via `range_check`, `bitwise`, `keccak`, etc., reachable from ordinary contract calls executed by the blockifier). By crafting transactions that saturate the block's bouncer capacity using builtins whose `limit` does not evenly divide `proving_gas`, an attacker can get the bouncer to admit a set of transactions into a single block whose true required proving resources exceed the block's configured `proving_gas` capacity, while `Bouncer::try_update`'s check against `bouncer_config.has_room` still reports room.

### Impact Explanation
The bouncer's `proving_gas` cap exists to bound the actual proving cost/time of a block so the network can reliably generate proofs and progress. If the accounted `proving_gas` systematically under-represents the true cost due to the floor-division derivation, a maliciously-crafted set of ordinary transactions can cause the batcher/sequencer to build (and consensus to accept) a block whose real proving cost exceeds the intended capacity. This can degrade block-proving throughput or, in aggregate across builtin types, meaningfully strain the prover, risking delayed block finalization — i.e., the network's ability to reliably confirm new transactions within the configured resource envelope, which is the category of impact explicitly allowed ("a network unable to confirm new transactions").

### Likelihood Explanation
The rounding error is deterministic and reachable by any unprivileged transaction sender who controls the Cairo/Sierra code executed (invoking builtins like `range_check`, `bitwise`, `keccak`, etc., in high volume). No special privileges, node compromise, or network-level attack is required — only ordinary transaction submission designed to exploit builtins whose `limit` doesn't evenly divide the configured `proving_gas` budget, as demonstrably the case for the shipped default `BuiltinInstanceLimits` [9](#0-8) .

### Recommendation
Track a running/residual remainder (similar to the report's suggested "last claimant gets the remainder" fix) when deriving and charging per-instance builtin gas costs, or use ceiling-based accounting combined with a global running total capped at `proving_gas`, so that the sum of all per-instance charges for a builtin never diverges from the true proportional budget. Alternatively, compute the exact fractional cost accumulation using rational arithmetic (as already done elsewhere in the codebase, e.g. `ResourceCost`/`Ratio`-based costs in `fee_utils.rs`) rather than a single pre-floored `u64` per-instance rate.

### Proof of Concept
1. Compute `induced_gas_costs` for the default `BuiltinInstanceLimits` against the default `proving_gas` budget (`GasAmount(6_000_000_000)`), as in the existing snapshot test [10](#0-9) : e.g., `range_check` cost = 90 per instance for limit 66,666,666.
2. Note `66,666,666 * 90 = 5,999,999,940 < 6,000,000,000` — a 60-unit shortfall for this single builtin type alone at max instance usage.
3. Craft (or accumulate across the block) transactions that drive `range_check` usage to its `limit`, while simultaneously maximizing usage of other builtins (`keccak`, `bitwise`, `ecdsa`, etc.) that have similarly non-evenly-dividing limits, each contributing its own shortfall.
4. Because `Bouncer::try_update` sums these under-priced per-instance contributions and compares only against the nominal `block_max_capacity.proving_gas` [11](#0-10) , the block is accepted as within capacity even though the true (non-floored) proportional proving cost across all builtins used exceeds the configured budget.

        cairo_primitives_to_gas(cairo_primitives_counters, proving_builtin_gas_costs);

        sierra_gas_to_steps_gas(sierra_gas, cairo_primitives_counters, sierra_builtin_gas_costs);

    steps_proving_gas.checked_add_panic_on_overflow(cairo_primitives_proving_gas)
}
