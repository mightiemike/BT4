### Title
isCEA inbound deposits that fail on `depositPRC20` are permanently unrecoverable — no revert, retry, or refund path exists - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
For `isCEA` inbounds, `ExecuteInboundFundsAndPayload` never sets `shouldRevert = true` when `depositPRC20` fails, and the code explicitly documents this as intentional ("isCEA failures never create an INBOUND_REVERT outbound"). The same asymmetry is repeated in the pre-execution validation path in `handleFailedInboundValidation`. This means any `isCEA` inbound whose deposit reverts on the EVM leaves the corresponding `UniversalTx` permanently in a `FAILED` `PCTx` state with no revert outbound, no retry mechanism, and no refund — even though the value was already observed/locked on the source chain. [1](#0-0) 

### Finding Description
In the `isCEA` branch, `Recipient` is attacker-supplied and can point to any address — including a UEA, an arbitrary deployed smart contract, or an EOA: [2](#0-1) 

When `depositPRC20` returns an error on this path, `execErr` is set but `shouldRevert` stays `false`: [3](#0-2) 

Compare this to the non-`isCEA` branch, where the identical `depositPRC20` failure explicitly sets `shouldRevert = true` and `revertReason`, causing a `buildRevertOutbound`/`attachOutboundsToUtx` call so the user's funds are returned on the source chain: [4](#0-3) [5](#0-4) 

The same asymmetric treatment is duplicated in the pre-execution validation failure handler, which schedules a revert for non-`isCEA` inbounds but explicitly skips it for `isCEA`: [6](#0-5) 

Because `Recipient` for `isCEA` inbounds can be an attacker-controlled smart contract (per the second branch of the three-way check, "Recipient is a deployed smart contract (not UEA) → deposit + executeUniversalTx"), an attacker can deliberately choose a `Recipient`/`AssetAddr` pairing that causes the PRC20 mint/transfer performed inside `depositPRC20`'s EVM call to revert deterministically (e.g., a contract without the expected receive/callback semantics, or one that intentionally reverts). Once that happens, the `UniversalTx` gets one `FAILED` `PCTx` entry and execution simply returns, with no outbound created and no other code path found (within the reviewed scope) offering a retry, refund, or manual reclaim mechanism for `isCEA` deposit failures.

### Impact Explanation
This breaks the stated protocol invariant that every failed deposit is retried, reverted, or refunded. Value that was already recognized/locked on the source chain via the finalized inbound ballot has no path back to the user and no path to be credited on Push Chain — it becomes permanently unaccounted for, matching the "permanent freezing of user funds" and "canonical UniversalTx state corruption" impact categories in scope.

### Likelihood Explanation
The `isCEA` flag and `Recipient` field are both attacker-supplied inputs reachable through the ordinary inbound-deposit flow, and `ValidateForExecution` only checks that `Recipient` is syntactically a valid hex address — it does not verify that a deposit to that address will actually succeed on the EVM: [7](#0-6) 
Any attacker who can also cause the underlying `depositPRC20` EVM call to revert for that recipient (e.g., a crafted contract) can trigger this path deterministically and repeatedly.

### Recommendation
Treat `depositPRC20` failures on the `isCEA` path the same as the non-`isCEA` path: either set `shouldRevert = true` to generate a revert outbound back to the source-chain sender, or implement an explicit refund/retry mechanism for `isCEA` deposit failures so that the "all failed deposits are retried/reverted/refunded" invariant holds regardless of the `isCEA` flag. If this asymmetry is intentional, it should be paired with a compensating recovery mechanism rather than leaving the `UniversalTx` in an unrecoverable terminal `FAILED` state.

### Proof of Concept
1. Attacker submits/observes an inbound deposit on a supported source chain with `IsCEA = true`, `TxType = FUNDS_AND_PAYLOAD` (or `FUNDS`), and `Recipient` set to an address of a smart contract the attacker deployed on Push Chain that is guaranteed to make the `depositPRC20` EVM call revert (e.g., a contract whose associated PRC20 receive hook/callback unconditionally reverts).
2. Honest validators finalize the ballot; `ExecuteInboundFundsAndPayload` runs with `utx.InboundTx.IsCEA == true`, hits `depositPRC20`, and gets `execErr != nil` from the EVM revert.
3. Because this is the `isCEA` branch, `shouldRevert` remains `false`; only a `FAILED` `PCTx` is appended to the `UniversalTx`, and the function returns with no outbound attached.
4. Query the `UniversalTx` afterward: it shows a terminal `FAILED` deposit `PCTx`, no `OutboundTx` of type `INBOUND_REVERT`, and no other recovery mechanism — the value locked/observed on the source chain is permanently unaccounted for on Push Chain.

			"amount", inbound.Amount,

				return nil
			}); storeErr != nil {
