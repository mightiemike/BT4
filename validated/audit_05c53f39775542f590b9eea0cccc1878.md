### Title
Unmetered, Anonymous `estimateEnergy`/`triggerConstantContract` RPC Calls Enable CPU-Exhaustion DoS with Query-Amplification - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`estimateEnergy` and `triggerConstantContract` are unauthenticated, feeless RPC/HTTP/JSON-RPC endpoints that trigger full TVM execution on the node. Because constant calls bypass energy/bandwidth billing by design, an attacker can force the node to burn CPU cycles up to the configured per-call deadline with zero financial cost, and `estimateEnergy` multiplies this cost per external request via an internal binary-search loop that re-executes the VM many times. This mirrors the reported bug class: requests that consume backend resources without any economic penalty for the requester, enabling denial of service.

### Finding Description
`Wallet.callConstantContract` executes the VM for a `triggerConstantContract`/`triggerContract`(view) request without charging fees or bandwidth, since `isConstantCall`/read-only calls skip the billing path in `VMActuator.execute` (`isConstantCall` branch returns immediately after `VM.play` without commit/fee bookkeeping): [1](#0-0) [2](#0-1) 

Each such call is allowed to run for up to `constantCallTimeoutMs` (or the shared network CPU deadline if unset), computed in `VMActuator.calculateCpuLimitInUs`: [3](#0-2) 

`estimateEnergy` amplifies this: for a single external RPC/HTTP call, it performs an initial constant-call execution plus a full binary search over the fee range (`low`/`high`), each iteration re-invoking `cleanContextAndTriggerConstantContract` → `triggerConstantContract` → full VM execution, with retries up to `estimateEnergyMaxRetry` on top of that: [4](#0-3) 

These endpoints are reachable anonymously through gRPC (`RpcApiService`), HTTP (`EstimateEnergyServlet`, `TriggerConstantContractServlet`), the Solidity/PBFT read-only mirrors, and Ethereum-compatible JSON-RPC (`eth_call`/`eth_estimateGas`): [5](#0-4) [6](#0-5) [7](#0-6) 

The only mitigation present is generic, cost-agnostic rate limiting (QPS/IP-QPS/concurrency-permit adapters), which applies uniformly regardless of how CPU-expensive the underlying contract call is: [8](#0-7) [9](#0-8) 

There is no per-request compute-cost accounting or requirement that the caller stake/pay anything proportional to the CPU time consumed — exactly the "excessive requests without financial penalty" pattern described in the report, applied here to TVM execution instead of oracle jobs.

### Impact Explanation
An attacker who deploys (or reuses) a contract with an expensive but non-reverting view function can repeatedly call `estimateEnergy`/`triggerConstantContract`/`eth_call`/`eth_estimateGas` from many source IPs to bypass the per-IP QPS limiter, driving sustained CPU saturation on FullNode/SolidityNode RPC workers. Because `estimateEnergy` runs an entire binary-search of VM executions per external call, the attacker gets substantial CPU-time amplification per network request, making the attack materially cheaper than the cost imposed on the node. This can degrade or deny legitimate RPC service (block queries, broadcast processing, other constant calls) — a node-level DoS via the RPC-API surface.

### Likelihood Explanation
The endpoints are enabled by default configuration knobs (`vm.supportConstant`, `vm.estimateEnergy`) that public FullNodes commonly turn on to serve wallets/dApps, are unauthenticated by protocol design, and require no on-chain transaction or fee — only network access to the HTTP/gRPC/JSON-RPC port. The default protections are QPS-based and per-IP, easily distributed across multiple source addresses, matching the exact bypass described in the original report ("rate limit can be easily bypassed by sending requests from several IPs simultaneously").

### Recommendation
- Introduce compute-cost-aware throttling for constant-call endpoints (e.g., a global/per-IP energy-time budget, not just QPS), independent of the generic `rate.limiter` QPS adapters.
- Bound `estimateEnergy`'s internal amplification (cap total VM executions per external call, or add a distinct, stricter time/QPS budget for it separate from `triggerConstantContract`).
- Consider requiring a lightweight, cheap-to-verify proof-of-work or session-based cost for high-frequency constant-call callers, or exposing `constantCallTimeoutMs` tuned conservatively by default with a dedicated concurrency cap (`GlobalPreemptibleAdapter`) pre-configured for `EstimateEnergyServlet`/`TriggerConstantContractServlet` instead of relying on the default `DefaultBaseQqsAdapter`.

### Proof of Concept
1. Deploy a contract with a `view`/`pure` function containing a loop that consumes CPU time close to the constant-call deadline (`vm.constantCallTimeoutMs` or shared `maxCpuTimeOfOneTx` deadline) without reverting.
2. From N distinct source IPs, concurrently flood `/wallet/estimateenergy` (or gRPC `EstimateEnergy`, or JSON-RPC `eth_estimateGas`) targeting that function.
3. Each request triggers an initial constant call plus a binary-search loop of further constant calls (see `Wallet.estimateEnergy`), each burning near-maximal CPU time, at zero cost to the caller (no fee, no energy debited, no on-chain footprint).
4. Because per-IP/global limiters are QPS-based, distributing across IPs bypasses effective throttling, and sustained CPU consumption degrades the node's ability to serve other RPC/HTTP/JSON-RPC clients.
