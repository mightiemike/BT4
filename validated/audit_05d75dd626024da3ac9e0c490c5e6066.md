## Title
Panic-inducing `.unwrap()` on `receiver_shard_id()` in delayed-receipt processing causes a transaction-triggered chain halt for stale `GlobalContractDistribution` receipts across resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`ReceiptSinkV2`/delayed-receipt-queue code calls `receiver_shard_id(&shard_layout)` and immediately `.unwrap()`s the result in `receipt_filter_fn` [1](#0-0)  . For a `GlobalContractDistribution` receipt, `receiver_shard_id` returns `Err(EpochError::ShardingError(...))` when the receipt's stored `target_shard` cannot be resolved via `resolve_to_current_shard` in the *current* shard layout [2](#0-1)  . `resolve_to_current_shard` only walks the split history contained in the *current* layout's `shards_split_map`, so a receipt that has been sitting in the delayed queue across **two or more resharding events** can end up pointing at a shard id that no longer appears anywhere in the current layout's split-history chain, causing `Err` and thus the `.unwrap()` panic. This mirrors CVE-2017-18199's bug class: a stored/serialized structure (there, an ISO symlink record; here, a receipt's `target_shard`) becomes stale/inconsistent with the surrounding structure and a null/unhandled-error path is blindly unwrapped, producing a crash.

### Finding Description
`GlobalContractDistribution` receipts are created whenever *any* unprivileged account deploys a global contract (`DeployGlobalContract` action) — this is a normal, permissionless transaction. The distribution receipt propagates to every shard and can be delayed in a shard's delayed-receipt queue if that shard is busy or congested.

When the runtime pops receipts off the delayed queue, it calls `receipt_filter_fn`, which computes `receiver_shard_id(&shard_layout)` for the receipt and unconditionally unwraps it:
```
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
``` [1](#0-0) 

For `GlobalContractDistribution`, `receiver_shard_id` looks up `target_shard` in the current layout, and if absent, tries `shard_layout.resolve_to_current_shard(target_shard)`, returning an `EpochError::ShardingError` if that also fails:
```
ReceiptEnum::GlobalContractDistribution(receipt) => {
    let target_shard = receipt.target_shard();
    if shard_layout.shard_ids().contains(&target_shard) {
        target_shard
    } else {
        let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard) else {
            return Err(EpochError::ShardingError(format!(...)));
        };
        current_shard
    }
}
``` [2](#0-1) 

`resolve_to_current_shard` recursively follows `shards_split_map`, which is rebuilt fresh at each `ShardLayoutV3::derive`/`derive_with_layout_history` call from the *current* layout's known ancestry [3](#0-2) [4](#0-3) . If a receipt has been delayed long enough to span **two independent resharding events** (the shard the receipt was originally targeting is split, and then one of its children is split again, or the split-history chain the target came from is not fully carried forward), `target_shard` can become a shard id that is neither present in the current shard list nor reachable via the current split-map, causing `resolve_to_current_shard` to return `None` and the outer call to return `Err`. The `.unwrap()` in `receipt_filter_fn` then panics.

This exact scenario is explicitly modeled by an in-repo regression test that force-triggers two sequential resharding events on the shard holding a `GlobalContractDistribution` receipt and asserts the chain does not stall/panic while draining the delayed queue: `test_stale_global_contract_distribution_after_double_resharding` [5](#0-4) [6](#0-5) . The test's own comment states plainly: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old `target_shard` after two resharding generations." [7](#0-6) 

### Impact Explanation
`receipt_filter_fn` runs inside `Runtime::apply`'s delayed-receipt draining path (`pop`), which is on the consensus-critical chunk-application path executed by every validator/chunk-producer node. A panic here crashes the node process (or at minimum aborts chunk production/application for that shard) for every honest node that reaches the same delayed receipt at the same point in the chain — i.e., a **transaction-triggered chain halt**, since the receipt is a normal protocol artifact created by a permissionless `DeployGlobalContract` action and its shard-remapping path is entirely determined by protocol-level resharding scheduling, not by any attacker needing special privileges. This matches the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Exploitability requires: (1) an unprivileged account deploying a global contract to generate a `GlobalContractDistribution` receipt, (2) that receipt becoming delayed (e.g., via congestion) in a shard, and (3) that shard undergoing at least two resharding events before the receipt is dequeued, with the receipt's `target_shard` falling outside the resolvable split-history chain in the layout at dequeue time. Dynamic/forced resharding scenarios (as exercised by the regression test) make this readily reproducible in a test environment; on a live network the likelihood depends on how frequently resharding occurs relative to delayed-receipt backlogs, which can be influenced by an attacker congesting a shard right before/across scheduled reshardings. Given nearcore already carries a dedicated regression test asserting the panic must not occur, this is a recognized, previously-identified class of bug in this exact code path.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (and any other blind `.unwrap()` on `receiver_shard_id`/`shard_layout` lookups in the delayed/incoming receipt draining paths) with graceful error propagation via `Result`/`RuntimeError`, treating an unresolvable `target_shard` as `StorageInconsistentState` or a similarly handled non-panicking error (consistent with how other stale-receipt cases are already handled, e.g. `runtime/runtime/src/lib.rs:2500`). Additionally, ensure `shards_split_map`/`resolve_to_current_shard` retain full split ancestry across arbitrarily many resharding generations rather than only the layout-local view, so multi-generation staleness cannot produce `None`.

### Proof of Concept
The nearcore test suite already contains a deterministic PoC: `test_stale_global_contract_distribution_after_double_resharding` forces two sequential shard splits (`force_split_shards: vec![first_split_shard, second_split_shard]`) such that the shard holding the deployed contract's `GlobalContractDistribution` receipt is split twice while the receipt sits in a saturated delayed queue, then drains the queue and asserts the chain does not stall [8](#0-7) [6](#0-5) . Whether this test currently passes (i.e., whether the underlying fix for `resolve_to_current_shard`/`receipt_filter_fn` is already fully effective for all delayed-receipt aging scenarios) could not be verified from static code inspection alone within the tool constraints available here — this would require running the test suite, which is outside the scope of this read-only analysis.
