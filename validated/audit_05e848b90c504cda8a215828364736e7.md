### Title
`finalize_cancellation` unconditionally removes an L1 handler transaction record even when it is `Pending`/staged, causing validators to diverge on block validity - (File: `crates/apollo_l1_events/src/transaction_manager.rs`)

### Summary
`TransactionManager::finalize_cancellation` deletes an L1 handler transaction's `TransactionRecord` from the manager's `records` map as soon as an L1 "cancellation finalized" event arrives, **regardless of the transaction's current lifecycle state**. The code's own comment acknowledges this is unsafe: it deletes the record "even if it was Pending and ready to be proposed (which is not supposed to happen, hence the warning)" [1](#0-0) . This is the direct analog of the reported `StakingModule.removePlugin` issue: an entity ("plugin"/L1 handler tx record) is removed without checking whether it still has a valid outstanding "claim" (a pending, proposable, or in-flight-staged transaction).

### Finding Description
`finalize_cancellation` is invoked in response to an L1 event that any account which sent an L1→L2 message can trigger on the L1 core contract (the unprivileged "L1 message sender" reachable path). The function only logs a `warn!` if `record.state != CancellationStartedOnL2`, but proceeds unconditionally to call `mark_cancellation_finalized_on_l1()` and `self.records.remove(&tx_hash)`:

```
crates/apollo_l1_events/src/transaction_manager.rs:221-245
    if record.state != TransactionState::CancellationStartedOnL2 {
        warn!(...);
    }
    // This will also call maintain_indices to remove the tx from the proposable index.
    self.with_record(tx_hash, |r| r.mark_cancellation_finalized_on_l1());
    self.records.remove(&tx_hash);
```

There is no check that:
- the transaction is not currently `Pending` and sitting in `proposable_index` (about to be, or already, proposed by this node via `get_txs`), or
- the transaction is not currently staged in an in-flight block (`try_mark_staged` was already called for the current epoch, i.e. it's part of a proposal being built or validated right now).

Once the record is deleted, `validate_tx` (called by every validating node for every L1Handler tx received in a proposal) falls through to `InvalidValidationStatus::NotFound` because `with_record` returns `None` for a missing hash [2](#0-1) .

Because different sequencer nodes ingest L1 events with independent timing (each node runs its own L1 scraper), the moment at which `finalize_cancellation` is applied for a given `tx_hash` is not synchronized across the network. This produces a race:

- Node A (proposer) calls `get_txs`, gets the tx from `proposable_index` while it is still `Pending`, and includes it in a proposal (`ValidateTransactionProvider`/`ProposeTransactionProvider` flow, see `docs/diagrams/06-l1-handler-flow.md:112-152`).
- Node B (validator) processes the L1 "cancellation finalized" event slightly earlier and has already removed the record via `finalize_cancellation`.
- Node B then receives the proposal containing that L1Handler tx and calls `validate(tx_hash, height)` → `validate_tx` → `NotFound` → `TransactionProviderError::L1HandlerTransactionValidationFailed` [3](#0-2)  → the batcher's `add_txs_to_executor` treats this as `FailOnErrorCause::L1HandlerTransactionValidationFailed` and aborts block validation for that node [4](#0-3) .
- Node C, which has not yet processed the cancellation event, validates the same proposal successfully.

This yields honest-node divergence on the validity of an otherwise legitimate proposal, purely as a function of local L1-event ingestion timing, not of any real double-spend/double-consumption condition.

### Impact Explanation
This directly matches the required impact classes:
- **Honest-node divergence**: different honest validators reach different validity verdicts (`Validated` vs `NotFound`) for the same proposed block, based only on the relative timing of L1 event processing, not on any true state inconsistency.
- **Network unable to confirm new transactions**: if a sufficient subset of validators reject the proposal due to `NotFound` while others accept it, the round can fail to reach quorum, stalling block production/finalization for that height and requiring a re-propose/timeout cycle. Repeated races (e.g., an adversarial L1 message sender deliberately timing the cancellation finalization to coincide with block building) could be used to grief consensus rounds involving that L1 handler tx.
- Additionally, once removed, the record is gone forever (`Records::remove` performs a `swap_remove_entry`), so if this transaction is legitimately re-proposed later (e.g., after the failed round, other proposers still hold it queued from `get_txs`/local caches), `validate_tx` will keep returning `NotFound` for it on any node that already processed the cancellation, permanently blocking that node from validating any block containing this tx, even if it does eventually get executed and committed by others — leading to a further consistency gap (that node's local `TransactionManager` will never see it marked `Committed`; it will simply not exist).

### Likelihood Explanation
The trigger is fully reachable by an unprivileged actor: any account that initiated the original L1→L2 message can call the L1 core contract's cancellation flow (start + finalize after the required L1-side timelock). No sequencer privilege is needed. The race window depends only on the relative delay between:
1. This node's `get_txs`/staging of the transaction in an active proposal, and
2. This node's (or another validating node's) local scraping/processing of the "cancellation finalized" L1 event.

Since each apollo node's L1 scraper polls/ingests events independently, and the code path explicitly proceeds "regardless of the state of the tx in the record" (per the author's own comment, which flags this exact scenario as something that "is not supposed to happen" but is not actually prevented), the bug is a genuine, code-acknowledged gap rather than a purely theoretical edge case. Likelihood is Medium-to-High given it only requires ordinary asynchronous propagation delay of L1 events across nodes, without any special attacker capability beyond owning the original L1→L2 message.

### Recommendation
In `finalize_cancellation`, do not unconditionally delete the record. Before removing:
- If `record.state == TransactionState::Pending` (i.e., `is_proposable()` is true) or the record is currently staged for the active epoch, treat this as an inconsistency: either defer the deletion until the transaction is no longer proposable/staged (e.g., after the current staging epoch's proposal/validation round completes), or explicitly reject/ignore the L1 finalization event and require it to be re-processed once state settles, rather than removing the record while it may still be legitimately included in an in-flight or upcoming proposal.
- At minimum, promote the existing `warn!` to a hard invariant check with a bounded retry/deferred-removal mechanism, so a currently pending/staged transaction is never silently dropped from `records` while still eligible for inclusion in a block.

### Proof of Concept
1. Node A and Node B both track the same L1 handler transaction `tx_hash` in `TransactionState::Pending`.
2. On L1, the original sender of the message calls `startL1ToL2MessageCancellation`, then after the L1 timelock, `cancelL1ToL2Message`.
3. Node A's L1 scraper has not yet observed the finalization event; Node A calls `get_txs`, which returns `tx_hash` from `proposable_index` (still `Pending`), and Node A proposes a block containing it (`crates/apollo_l1_events/src/transaction_manager.rs:72-114`).
4. Node B's L1 scraper observes the finalization event first and calls `finalize_cancellation(tx_hash)`, which removes the record unconditionally (`crates/apollo_l1_events/src/transaction_manager.rs:221-245`).
5. Node B receives Node A's proposal and calls `validate(tx_hash, height)` → `validate_tx` → record not found → `InvalidValidationStatus::NotFound` (`crates/apollo_l1_events/src/transaction_manager.rs:116-145`).
6. Node B's batcher aborts validation of the block (`crates/apollo_batcher/src/block_builder.rs:496-510`), while Node C (which hasn't processed the L1 event yet) validates it successfully — demonstrating honest-node divergence purely from L1-event ingestion timing.

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    pub fn finalize_cancellation(&mut self, tx_hash: TransactionHash) {
        let Some(record) = self.records.get(&tx_hash) else {
            info!(
                "Attempted to finalize cancellation for non-existent transaction: {tx_hash}. This \
                 can happen if the transaction was too old to be scraped (e.g. it was created \
                 before we started scraping)."
            );
            return;
        };

        // Regardless of the state of the tx in the record, if we get the cancellation event from
        // the L1 contract, we delete this tx from the records and from the proposable index, even
        // if it was Pending and ready to be proposed (which is not supposed to happen, hence the
        // warning).
        if record.state != TransactionState::CancellationStartedOnL2 {
            warn!(
                "Attempted to finalize cancellation for transaction {tx_hash} that is not in the \
                 cancellation started on L2 state, but in the {:?} state.",
                record.state
            );
        }
        // This will also call maintain_indices to remove the tx from the proposable index.
        self.with_record(tx_hash, |r| r.mark_cancellation_finalized_on_l1());
        self.records.remove(&tx_hash);
    }
