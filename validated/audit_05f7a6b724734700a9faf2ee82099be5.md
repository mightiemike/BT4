## Analog Found

### Title
Enabling hardened resource-accounting math (`AllowHardenResourceCalculation`) converts previously-tolerated `long` overflow into an uncaught `ArithmeticException`, permanently bricking bandwidth/energy accounting for large accounts - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
The Sherlock report describes a class of bug where an accounting routine that historically depended on silent numeric wraparound (UniswapV2/Solidity 0.6.6 style) is later executed under a strict/checked arithmetic regime (Solidity ≥0.8.0), causing legitimate overflow to `revert()` instead of wrapping, which then permanently DoSes the contract. java-tron's `ResourceProcessor` (parent of `BandwidthProcessor` and `EnergyProcessor`) contains the same structural pattern: a legacy `long`-arithmetic path that silently overflows/wraps, and a governance-toggleable "hardened" path that replaces it with `BigInteger` arithmetic terminated by `.longValueExact()` / `StrictMathWrapper.addExact()`, which throws `ArithmeticException` on overflow instead of wrapping.

### Finding Description
`ResourceProcessor.increase(...)`, `increaseV2(...)`, `getUsage(...)`, `getNewWindowSize(...)`, and `calculateGlobalNetLimit`/`calculateGlobalLimitV2` all branch on `hardenCalculation()`: [1](#0-0) [2](#0-1) 

When the "unhardened" (legacy) path is active, `lastUsage * precision`, `usage * windowSize`, etc. are computed with raw `long` multiplication, which silently overflows/wraps in Java (analogous to Solidity 0.6.6's unchecked math). When the on-chain governance parameter `ALLOW_HARDEN_RESOURCE_CALCULATION` is enabled via a committee proposal, this switches to `BigInteger` math ending in `longValueExact()`, which throws `ArithmeticException` the moment the true value exceeds `Long.MAX_VALUE` — this is precisely the "checked arithmetic now reverts on values that used to silently wrap" pattern described in the report.

This flag is a real on-chain, committee-settable proposal parameter (not test-only): [3](#0-2) 
It is referenced in `ProposalService`, `Wallet`, and `DynamicPropertiesStore`, confirming it is a live consensus-governed toggle rather than a test-only flag.

These `increase`/`getUsage`/`getNewWindowSize` calls sit directly in the hot path of every transaction's bandwidth/energy accounting — `BandwidthProcessor.consume()`, `useAccountNet()`, `useFreeNet()`, `consumeBandwidthForCreateNewAccount()`, and `EnergyProcessor.updateUsage()`: [4](#0-3) [5](#0-4) 

None of these call sites catch `ArithmeticException`. A test confirms the throw behavior explicitly: [6](#0-5) 

### Impact Explanation
If the hardened-math proposal is activated while an account (or the network-wide `totalEnergyAverageUsage`/`totalNetUsage` accumulators) holds sufficiently large `lastUsage`/`frozenBalance` values such that `lastUsage * precision` (precision is a large constant, e.g. `TRX_PRECISION`) exceeds `Long.MAX_VALUE`, `divideCeilExact`/`getUsage` will throw an uncaught `ArithmeticException` inside `increase`/`increaseV2`. Since this is called on every transaction that touches that account's bandwidth/energy, and also in block-level aggregate accounting (`updateTotalEnergyAverageUsage`), this can permanently and unrecoverably fail bandwidth/energy processing for the affected account or for the whole chain's adaptive resource limit updates — the account/chain can no longer process transactions relying on that path, mirroring the "permanent DoS / broken pool, locked funds" impact in the report, translated to "broken resource accounting, transactions unprocessable."

### Likelihood Explanation
This requires (1) the committee to pass the `ALLOW_HARDEN_RESOURCE_CALCULATION` proposal (a real governance action, not privileged-attacker-only, and one the project appears to be actively rolling out given the extensive hardening code and tests), and (2) an account or global counter to accumulate `lastUsage`/`frozenBalance` values large enough to overflow after multiplication by `precision`. Given `precision` and windowSize constants and the very large TRX supply/frozen amounts possible on TRON, reaching multiplication overflow of a signed 64-bit long is a tail scenario but not implausible over long chain lifetimes or with malicious resource-delegation stacking, structurally identical to the "far future / large-ratio" tail case accepted as Medium in the original report.

### Recommendation
Wrap all committee-toggleable "hardened" arithmetic call sites in `ResourceProcessor`/`BandwidthProcessor`/`EnergyProcessor` with explicit exception handling that degrades gracefully (e.g., clamp to `Long.MAX_VALUE`, or reject only the single offending transaction/resource-consumption attempt) rather than allowing an uncaught `ArithmeticException` to propagate out of core accounting paths that execute on every block/transaction. Alternatively, validate/bound `lastUsage`, `frozenBalance`, and window sizes so the intermediate product can never exceed `Long.MAX_VALUE` before enabling the hardened path network-wide.

### Proof of Concept
The existing test suite already demonstrates the exact overflow-to-exception transition when hardening is toggled on: [7](#0-6) 
`testIncreaseOverflowDetectedWithHardening` shows `processor.increase(Long.MAX_VALUE/10, 1L, 9990L, 9995L, 28800L)` throws `ArithmeticException` when `AllowHardenResourceCalculation=1`, while `testIncreaseOverflowSilentWithoutHardening` shows the identical inputs silently wrap without hardening. In production, this call is unguarded inside `BandwidthProcessor.useAccountNet`/`EnergyProcessor.updateUsage`, so once the proposal is live and an account/global counter reaches this magnitude, every subsequent transaction touching that resource counter throws uncaught, halting further processing for that path.

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }

  private long getUsage(long usage, long windowSize) {
    if (hardenCalculation()) {
      return BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize))
          .divide(BigInteger.valueOf(precision)).longValueExact();
    }
    return usage * windowSize / precision;
  }

      logger.debug("Net usage is running out, now use free net usage."
              + " Bytes: {}, netLimit: {}, newNetUsage: {}.",
          bytes, netLimit, newNetUsage);
      return false;
    }

    long latestOperationTime = chainBaseManager.getHeadBlockTimeStamp();
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newNetUsage = increase(newNetUsage, bytes, now, now);
    } else {
      // Participate in calculation and flush disk persistence
      newNetUsage = increase(accountCapsule, BANDWIDTH, netUsage, bytes, latestConsumeTime, now);
    }

    accountCapsule.setNetUsage(newNetUsage);

    accountCapsule.setLatestConsumeTime(now);
