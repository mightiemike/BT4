### Title
Uncaught `TypeError` in `sanitizeHost` from malformed decoded host causes unhandled exception instead of returning null - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` only validates that the raw `host` query parameter matches the base64 charset regex before calling `new URL(`https://${decodeHost(sanitizedHost)}`)`, without a try/catch around the URL construction. Since `decodeHost` (`atob`) can decode arbitrary bytes/characters into the resulting string, an attacker can supply base64 that decodes into a string containing forbidden host code points (e.g. NUL, control characters, spaces, `#`, `\`), causing the `URL` constructor to throw a `TypeError` that propagates uncaught out of `sanitizeHost`, instead of returning `null` or `InvalidHostError` as callers expect.

### Finding Description
`sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` performs the following: [1](#0-0) 

```
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
  ...
``` [2](#0-1) 

The `base64regex` (`/^[0-9a-zA-Z+/]+={0,2}$/`) only ensures the raw parameter uses the base64 character set — it does not validate what the *decoded* content looks like. `decodeHost` is a trivial wrapper around `atob`: [3](#0-2) 

`atob` can decode arbitrary bytes into a string, including NUL bytes, control characters, spaces, and other WHATWG-forbidden host code points (`#`, `/`, `:`, `?`, `@`, `[`, `]`, backslash, etc.). When such a decoded string is placed directly into `https://${decodeHost(...)}` and passed to `new URL()`, the WHATWG URL parser throws a `TypeError: Invalid URL` if a forbidden character appears in the host portion (before any path delimiter). This call is not wrapped in try/catch, so the exception escapes `sanitizeHost` entirely — it is neither caught to return `null` nor converted into `InvalidHostError`.

All callers of `sanitizeHost` (e.g. `validateShopAndHostParams` in shopify-app-remix/shopify-app-react-router, `redirectToShopifyOrAppRoot`, `redirect-to-auth` in shopify-app-express) only check for a falsy return value or catch `InvalidHostError`; they do not anticipate a raw `TypeError` bubbling out of the utility: [4](#0-3) 

Since this code runs on an unauthenticated request path (before OAuth/session validation), an attacker with no credentials can reach it via `GET /app?shop=valid-shop.myshopify.com&host=<crafted-base64>`.

### Impact Explanation
The unhandled exception thrown from `sanitizeHost` on an unauthenticated request path can crash or 500 the request handler in host applications that do not add their own generic error boundary around the authenticate/login flow, resulting in a denial-of-service on a pre-authentication endpoint. This matches Shopify's "DoS in an authentication handler" impact class described in the scope — it is a crash triggerable purely from attacker-controlled input with no privileges required.

### Likelihood Explanation
- Precondition: default config, endpoint reachable without credentials — satisfied, since `sanitizeHost` is invoked prior to authentication (e.g. in `validateShopAndHostParams`, `redirectToShopifyOrAppRoot`, `redirect-to-auth`).
- Attacker capability: only needs to send one crafted GET request with a `host` parameter containing base64 that decodes to a string with forbidden host characters (e.g. a NUL byte, space, or `#`/`\`).
- Feasibility: trivial to construct (`Buffer.from('bad\x00host.myshopify.com/admin').toString('base64')`), fully repeatable, no timing or race conditions involved.

### Recommendation
Wrap the `new URL(...)` construction (and `decodeHost` call) in `sanitizeHost` in a try/catch, treating any thrown error the same as an invalid host: set `sanitizedHost = null` (or throw `InvalidHostError` when `throwOnInvalid` is true), matching the existing error-handling contract of the function.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';
import {InvalidHostError} from '../../error';

test('sanitizeHost does not throw an unhandled TypeError for malformed decoded host', () => {
  const shopify = shopifyApi(testConfig());

  // decodes to "bad\x00host.myshopify.com/admin" - NUL byte is a forbidden host code point
  const maliciousBase64 = Buffer.from(
    'bad\x00host.myshopify.com/admin',
  ).toString('base64');

  // Expected (safe) behavior: returns null / throws InvalidHostError
  expect(shopify.utils.sanitizeHost(maliciousBase64)).toBeNull();
  expect(() =>
    shopify.utils.sanitizeHost(maliciousBase64, true),
  ).toThrow(InvalidHostError);

  // Actual behavior today: `new URL()` throws a raw TypeError that escapes
  // sanitizeHost uncaught, failing the assertions above.
});
```
Request-level equivalent: `GET /app?shop=valid-shop.myshopify.com&host=YmFkAGhvc3QubXlzaG9waWZ5LmNvbS9hZG1pbg==` (base64 of `bad\x00host.myshopify.com/admin`) sent to any route that calls `sanitizeHost`/`validateShopAndHostParams` before authentication.
