### Title
Compiled-class-hash-v2 migration bypasses concurrent-execution read tracking, causing wrong committed state diff - ([File: crates/blockifier/src/concurrency/versioned_state.rs])

### Summary
The Xen CVE is a "stale TLB entry" bug: after a page-table modification, a cached address-translation entry is not invalidated/re-validated, so a guest can act on stale mappings and corrupt privileged memory. The structural analog in the sequencer's concurrent (Block-STM style) executor is `VersionedStateProxy::get_compiled_class_hash_v2`, which reads directly from the *unversioned* `initial_state` instead of going through the same versioned-storage / read-tracking path used by every other state accessor (`get_storage_at`, `get_nonce_at`, `get_class_hash_at`, `get_compiled_class_hash`, `get_compiled_class`). This value is never recorded into the transaction's read-set and is never invalidated or re-validated against concurrent writes performed by other transactions in the same chunk.

### Finding Description
Every other `StateReader` method on `VersionedStateProxy` follows the same pattern: check the versioned storage for a write visible at `tx_index`, and if absent, read from `initial_state`, cache it as an "initial value" so it can be included in the transaction's read-set for `validate_reads`: [1](#0-0) 

`get_compiled_class_hash_v2`, however, skips this mechanism entirely and reads straight from `initial_state`, with no versioned-storage lookup and no `set_initial_value` call: [2](#0-1) 

Because the value is never inserted into `StateCache.initial_reads`/`reads` (compare with the tracked fields enumerated in `StateMaps`/`validate_reads`), it is not part of the read-set checked by `VersionedState::validate_reads`: [3](#0-2) 

This value feeds into the CASM-hash-v1→v2 migration logic (`should_migrate`, `CasmHashMigrationData::from_state`), which is invoked during block execution/bouncer accounting to decide, per executed class, whether the block's state diff must include a `compiled_class_hashes` migration write: [4](#0-3) [5](#0-4) 

`get_compiled_class_hash_v2` is ultimately backed by a real cache with its own invalidation semantics (`ContractClassManager`/`TrivialClassManager`/`NativeClassManager`, `StateReaderAndContractManager::get_compiled_class_hash_v2`), which is populated the first time any transaction (in any worker thread, possibly executed out of commit order) requests it: [6](#0-5) 

Because the versioned-execution layer never records or re-validates this read, a transaction can be speculatively (re-)executed with a `compiled_class_hash_v2` value that was computed/cached before a relevant concurrent write (e.g. a Declare transaction updating `compiled_class_hashes` for the same class, or a re-execution that changes which contract class is associated with the class hash) is applied by a lower-indexed transaction — and the scheduler's Block-STM validation, which is the sole mechanism protecting against exactly this class of staleness for every other field, has no way to detect or force a re-execution, because the read was never entered into the read-set in the first place. This is precisely the shape of the Xen bug: a cached "translation" (here, class-hash → CASM-hash-v2 mapping) that is used without going through the invalidation/validation path that every other cached mapping in the same subsystem uses.

### Impact Explanation
If a stale/incorrect `compiled_class_hash_v2` is used for the migration decision or the state-diff computation for `class_hash_to_compiled_class_hash` migration entries, the committed block's state diff (and therefore the state root / class-hash commitment) can diverge from what an honest, sequentially-executing node would produce for the same set of unprivileged transactions (an ordinary Declare + Invoke sequence triggers `should_migrate`/migration bookkeeping). This causes honest-node state-root divergence, which the rules explicitly list as an acceptable impact (wrong committed root / honest-node divergence), reachable purely by submitting ordinary Declare and Invoke transactions that get scheduled concurrently by the sequencer's own multi-worker executor — no malicious operator/proposer/node behavior is required, since the concurrency scheduling and re-execution ordering is a normal internal sequencer mechanism.

### Likelihood Explanation
The bug is deterministic given the right interleaving: it requires (a) `concurrency_config.enabled` (multi-worker execution) and (b) `enable_casm_hash_migration` to be active, and (c) two or more transactions in the same execution chunk that interact with the same class hash such that one is re-executed/validated after the migration-relevant class-hash mapping is cached from a stale execution. The `WorkerExecutor` code explicitly supports and tests out-of-order execution/re-execution scenarios (`worker_logic_test.rs::test_worker_validate`, `test_commit_tx`), demonstrating that transactions are routinely executed out of order and re-executed on validation failure — the exact conditions under which a read bypassing `validate_reads` becomes stale. This is a genuine, but narrow, configuration-and-timing-dependent condition; I could not fully trace every intermediate caller (e.g., exactly which code path re-reads `get_compiled_class_hash_v2` during a *re-execution* vs. relying on a separately-clean per-tx cache) within the tool budget available, so the precise reachability/triggering interleaving inside `CasmHashMigrationData::from_state` during concurrent chunk execution is not fully proven end-to-end.

### Recommendation
Route `get_compiled_class_hash_v2` in `VersionedStateProxy` through the same versioned-storage read/write/validate pipeline used for `compiled_class_hashes`/`compiled_contract_classes` (record the read in `initial_reads`, include it in `StateMaps`/`validate_reads`, and re-validate/invalidate it like every other field), or otherwise ensure the migration decision is derived only from state that is fully protected by the Block-STM read-set validation before it is used to compute the committed state diff.

### Proof of Concept
Not independently reproduced; based on static code-path analysis of `crates/blockifier/src/concurrency/versioned_state.rs` (`get_compiled_class_hash_v2`, `validate_reads`), `crates/blockifier/src/state/utils.rs` (`should_migrate`), `crates/blockifier/src/bouncer.rs` (`CasmHashMigrationData::from_state`), and the concurrent-execution/re-execution flow in `crates/blockifier/src/concurrency/worker_logic.rs`. A concrete PoC would require constructing a chunk with a Declare transaction and a dependent Invoke/Declare transaction on the same class hash under `concurrency_config.enabled = true` and `enable_casm_hash_migration = true`, forcing an out-of-order execution/re-execution similar to `test_worker_validate`, and observing whether `compiled_class_hashes_for_migration` differs between concurrent and sequential execution of the identical transaction set — this was not verified in this session.

    fn validate_reads(&mut self, tx_index: TxIndex, reads: &StateMaps) -> bool {
        // If is the first transaction in the chunk, then the read set is valid. Since it has no
        // predecessors, there's nothing to compare it to.
        if tx_index == 0 {
            return true;
        }
        // Ignore values written by the current transaction.
        let tx_index = tx_index - 1;
        for (&(contract_address, storage_key), expected_value) in &reads.storage {
            let value =
                self.storage.read(tx_index, (contract_address, storage_key)).expect(READ_ERR);

            if &value != expected_value {
                return false;
            }
        }

                return false;

// Class should migrate if his compiled class hash v2 is different from the one in the state.
/// Returns a map of class hashes to their compiled class hashes for migration if the class should
/// migrate, otherwise returns None.
pub fn should_migrate(
    state_reader: &impl StateReader,
    class_hash: ClassHash,
) -> StateResult<Option<(ClassHash, CompiledClassHashV2ToV1)>> {
    let state_compiled_class_hash = state_reader.get_compiled_class_hash(class_hash)?;
    match state_compiled_class_hash {
        // Class hash does not exist in the state, or is a Cairo 0 class.
        CompiledClassHash(hash) if hash == StarkHash::ZERO => Ok(None),
        state_compiled_class_hash => {
            let compiled_class_hash_v2 = state_reader.get_compiled_class_hash_v2(
                class_hash,
                &state_reader.get_compiled_class(class_hash)?,
            )?;
            // If the state compiled class hash is compiled class hash v2, the class should not
            // migrate.
            if state_compiled_class_hash == compiled_class_hash_v2 {
                return Ok(None);
            }
            Ok(Some((class_hash, (compiled_class_hash_v2, state_compiled_class_hash))))
        }
    }
}

    /// Builds a migration aggregation from the current state.
    /// Returns empty if migration is disabled.
    /// Otherwise, iterates over `executed_class_hashes`, selects classes that should migrate
    /// via `should_migrate`, and accumulates their migration resources.
    fn from_state<S: StateReader>(
        state_reader: &S,
        executed_class_hashes: &HashSet<ClassHash>,
        versioned_constants: &VersionedConstants,
    ) -> TransactionExecutionResult<Self> {
        if !versioned_constants.enable_casm_hash_migration {
            return Ok(Self::empty());
        }

        executed_class_hashes.iter().try_fold(Self::empty(), |mut migration_data, &class_hash| {
            if let Some((class_hash, casm_hash_v2_to_v1)) =
                should_migrate(state_reader, class_hash)?
            {
                // Add class hash mapping to the migration data.
                migration_data.class_hashes_to_migrate.insert(class_hash, casm_hash_v2_to_v1);

                // Accumulate the class's migration resources.
                let class = state_reader.get_compiled_class(class_hash)?;
                migration_data.resources +=
                    &class.estimate_compiled_class_hash_migration_resources();
            }
            Ok(migration_data)
        })
    }

    /// Returns the compiled class hash v2 for the given class hash.
    /// The function assumes that the class hash is already declared,
    /// and of cairo1 contract class.
    fn get_compiled_class_hash_v2(
        &self,
        class_hash: ClassHash,
        compiled_class: &RunnableCompiledClass,
    ) -> StateResult<CompiledClassHash> {
        // First, try getting from class manager cache.
        match self.contract_class_manager.get_compiled_class_hash_v2(&class_hash) {
            Some(compiled_class_hash) => Ok(compiled_class_hash),
            None => {
                // Not in cache → fetch from state reader.
                let compiled_class_hash =
                    self.state_reader.get_compiled_class_hash_v2(class_hash, compiled_class)?;
                // Verify that the returned compiled_class_hash_v2 is not the default value.
                // default value is used to mark classes that are not declared or cairo0 classes.
                assert_ne!(
                    compiled_class_hash,
                    CompiledClassHash::default(),
                    "Default compiled class hash is for marking classes that are not declared or \
                     cairo0 classes. class_hash: {class_hash:?}"
                );
                // Store in cache.
                self.contract_class_manager
                    .set_compiled_class_hash_v2(class_hash, compiled_class_hash);

                Ok(compiled_class_hash)
            }
        }
    }
