### Title
Reward-cycle (and thus signer-set) selection for unprocessed Nakamoto blocks falls back to the local burnchain tip instead of the block's own sortition period, causing wrongful signature-verification failures - (File: `stackslib/src/net/unsolicited.rs`)

### Summary
`PeerNetwork::find_nakamoto_block_reward_cycle` and its caller `is_nakamoto_block_bufferable` decide which reward cycle's signer set to use when pre-validating an unsolicited `NakamotoBlock` whose sortition has not yet been processed locally. When the block's own sortition is unknown, the code substitutes the *current local burnchain tip's* reward cycle instead of the reward cycle the block's own tenure sortition will actually belong to. This is structurally the same defect as the Telepathy `LightClient` bug: a "wrapping"/currently-known state (the burnchain tip) is used to pick the signer/committee set that should really be keyed off the "nested"/not-yet-finalized state (the block's own sortition), and near a reward-cycle boundary the two can diverge.

### Finding Description
`find_nakamoto_block_reward_cycle` tries to resolve the sortition for the incoming block's `consensus_hash`. If it is not found (the block's sortition has not been processed by this node yet), it falls back to `self.burnchain_tip` to compute the reward cycle: [1](#0-0) 

That returned `sn_rc` is then used directly to look up the reward/signer set and verify the block's signer signatures in `is_nakamoto_block_bufferable`: [2](#0-1) 

`check_nakamoto_block_signer_signature` uses this `reward_cycle` to fetch `self.current_reward_sets.get(&reward_cycle)` and calls `verify_signer_signatures` against it: [3](#0-2) 

The correct reward cycle for signature verification is the one belonging to the sortition of the block's own tenure (its `consensus_hash`), exactly analogous to how the "wrapping"/attested slot in the Telepathy bug should have driven sync-committee selection instead of the "nested"/finalized slot. Here it's inverted: the code needs the *block's own* (not-yet-processed) sortition's reward cycle, but substitutes the locally-known burnchain tip's reward cycle when that information isn't yet available. Near a reward-cycle boundary (e.g., the local node is a few burn blocks behind the peer that produced/relayed the block, or vice versa), `self.burnchain_tip`'s reward cycle and the eventual sortition's reward cycle can differ by one cycle, i.e., they will resolve to different signer sets.

By contrast, the fully-solicited relay path in `stackslib/src/net/relay.rs` correctly keys the reward cycle off the block's own sortition snapshot before calling `verify_signer_signatures`: [4](#0-3) 

### Impact Explanation
When `sn_rc` computed from `self.burnchain_tip` does not match the reward cycle that will ultimately be assigned to the block's actual sortition, `check_nakamoto_block_signer_signature` will look up the wrong `RewardSet`. `verify_signer_signatures` will then fail to recover any of the submitted signatures against member public keys in that (wrong) set, and the block will be treated as invalid at this node — it is neither buffered nor accepted for later retry, even though it is a legitimately-signed block. This causes an unprivileged, minority-triggerable temporary verdict disagreement between nodes at different burnchain-view heights: some nodes (behind on burnchain sync) drop/refuse to buffer a valid unsolicited block that other, more up-to-date nodes accept and relay normally, delaying block/tenure propagation to the lagging node in a way that mirrors the AMB relay delay described in the source report. This does not corrupt the canonical chain (the authoritative signature check still happens later, correctly, in `stackslib/src/net/relay.rs` once the sortition is known), so the impact is bounded to a temporary tip/propagation disagreement rather than a chain split.

### Likelihood Explanation
This requires no majority collusion, no admin key, and no special privilege — it is triggered purely by normal network timing: any node whose burnchain view lags (or leads) relative to when it receives an unsolicited Nakamoto block near a reward-cycle boundary can hit the fallback path in `find_nakamoto_block_reward_cycle`. Because reward-cycle boundaries recur periodically and unsolicited block delivery races with burnchain sync routinely in a distributed network, this is a plausible, naturally-occurring (not merely theoretical) condition, though it self-heals once the peer's burnchain view catches up and the block is (re)delivered/synced through other channels (e.g., inventory sync).

### Recommendation
In `find_nakamoto_block_reward_cycle`, avoid substituting `self.burnchain_tip`'s reward cycle when the block's own sortition is not yet known. Instead, either: (1) skip signer-signature verification for the "cannot yet process" branch and rely solely on buffering plus the authoritative check that already happens once the sortition is processed (as in `relay.rs`), or (2) if a cycle must be estimated, deterministically compute the reward cycle that the *pending* sortition would belong to (e.g., from the block's own tenure-change payload or from the burnchain height the sortition would occur at) rather than reusing the possibly-mismatched local tip's cycle. Add regression tests that construct unsolicited blocks whose sortition lands exactly at a reward-cycle boundary while the receiving node's burnchain tip is one cycle behind/ahead, verifying that such blocks are buffered (not dropped) pending sortition processing.

### Proof of Concept
1. Node A's burnchain view is one reward cycle behind the burnchain tip that actually selected Node B's newly mined Nakamoto block's tenure (i.e., Node A has not yet processed the sortition for the block's `consensus_hash`).
2. Node B relays the new `NakamotoBlocksData` message unsolicited to Node A.
3. Node A calls `is_nakamoto_block_bufferable` → `find_nakamoto_block_reward_cycle`; since `SortitionDB::get_block_snapshot_consensus` fails to find the block's `consensus_hash` snapshot, the function falls back to `self.burnchain_tip.block_height`'s reward cycle (`reward_set_sn_rc`), which is one cycle earlier than the reward cycle the block's real sortition belongs to. [5](#0-4) 
4. `check_nakamoto_block_signer_signature(sn_rc, ...)` fetches the reward set for the wrong (earlier) cycle and calls `verify_signer_signatures`, which fails to recover any valid signer public keys from the block's signatures (signed by the new cycle's signer set) against the old cycle's signer set.
5. `is_nakamoto_block_bufferable` returns `false`, so the legitimately signed block is dropped by Node A rather than buffered for retry, delaying its propagation until Node A independently catches up via other sync mechanisms.

        &self,
        sortdb: &SortitionDB,
        nakamoto_block: &NakamotoBlock,
    ) -> (Option<u64>, bool) {
        let (reward_set_sn, can_process) = match SortitionDB::get_block_snapshot_consensus(
            sortdb.conn(),
            &nakamoto_block.header.consensus_hash,
        ) {
            Ok(Some(sn)) => (sn, true),
            Ok(None) => {
                debug!(
                    "No sortition {} for block {}",
                    &nakamoto_block.header.consensus_hash,
                    &nakamoto_block.block_id()
                );
                // we don't have the sortition for this, so we can't process it yet (i.e. we need
                // to buffer)
                // load the tip so we can load the current reward set data
                (self.burnchain_tip.clone(), false)
            }
            Err(e) => {
                info!(
                    "{:?}: Failed to query block snapshot for {}: {:?}",
                    self.get_local_peer(),
                    &nakamoto_block.header.consensus_hash,
                    &e
                );
                return (None, false);
            }
        };

        if !reward_set_sn.pox_valid {
            info!(
                "{:?}: Failed to query snapshot for {}: not on the valid PoX fork",
                self.get_local_peer(),
                &nakamoto_block.header.consensus_hash
            );
            return (None, false);
        }

        let reward_set_sn_rc = self
            .burnchain
            .block_height_to_reward_cycle(reward_set_sn.block_height)
            .expect("FATAL: sortition has no reward cycle");

        return (Some(reward_set_sn_rc), can_process);
