### Title
Explicit `debug_redact` field-option annotation is not enforced by any Debug/Text/JSON formatting path, causing developer-flagged sensitive fields to be exposed in debug logs and traces - ([File: types/descriptorpb/descriptor.pb.go])

### Summary
`google.protobuf.FieldOptions.debug_redact` (and the equivalent `EnumValueOptions.debug_redact`) exists specifically so schema authors can mark a field (e.g. an API token, webhook URL, or credential) as "must not be printed in debug formats." [1](#0-0)  The same contract exists for enum values. [2](#0-1)  However, a repo-wide search shows the flag is defined and only referenced in generated descriptor code, `internal/genid`, doc comments, and example/test files — never read by the actual text/JSON/Debug-string encoders (`encoding/prototext`, `encoding/protojson`, or the generated `String()`/`protoimpl.X.MessageStringOf` path). This is the same bug class as GHSA-4mjx-2gh5-ph8h: a library exposes a value through its debug/`Display`-style output that the caller explicitly asked to have redacted.

### Finding Description
Every generated message's `String()` method calls `protoimpl.X.MessageStringOf(x)`, which formats the message using the library's internal debug-text machinery, and `prototext.Marshal`/`protojson.Marshal` are also commonly invoked (directly or via `%v`/`%+v` logging, error wrapping, or tracing middleware) on live request/response messages. [3](#0-2)  None of these code paths consult `FieldDescriptor.Options().(*descriptorpb.FieldOptions).GetDebugRedact()` before emitting a field's value — the option's getter exists purely as a passive accessor. [4](#0-3)  Consequently, any application that defines a `.proto` schema with `[debug_redact = true]` on a sensitive field (mirroring exactly the intended use case documented in the field comment) gets no actual protection: the value is printed in full whenever the message is logged, traced, or formatted with `%v`, exactly like the unredacted webhook URLs in the original Slack advisory.

### Impact Explanation
Confidentiality impact: sensitive values (tokens, webhook URLs, credentials) that a service owner explicitly annotated for redaction still leak into logs/traces/error output whenever a proto message containing them is formatted for debugging — the exact scenario the `debug_redact` option and the referenced advisory are meant to prevent.

### Likelihood Explanation
High likelihood of triggering: normal, unprivileged operation of any service that (a) defines a schema with `debug_redact` on a sensitive field, and (b) logs/traces incoming or outgoing messages (a very common Go pattern, e.g. `log.Printf("%v", req)`, gRPC interceptor logging, or error wrapping that calls `.String()`). No attacker input manipulation, malicious peer, or privileged access is required — it is a passive, always-on gap in the trusted-schema formatting path.

### Recommendation
Have `prototext.Marshal`, `protojson.Marshal`, and the internal debug-string formatter check `fieldDescriptor.Options().(*descriptorpb.FieldOptions).GetDebugRedact()` (and the enum-value equivalent) for each field/value before emitting it, replacing redacted values with a placeholder (e.g. mirroring upstream protobuf's `<redacted>` marker), consistent with the documented intent of the option.

### Proof of Concept
```go
// schema.proto
message Webhook {
  string url = 1 [debug_redact = true];
}
```
```go
w := &pb.Webhook{Url: "https://hooks.slack.com/services/T000/B000/XXXXSECRETXXXX"}
log.Printf("incoming webhook: %v", w) // or fmt.Sprintf("%+v", w), or w.String()
// Output still contains the full secret URL because no formatting path
// checks GetDebugRedact() before printing the field value.
```

Note: I was unable to fully inspect the internal implementation of `protoimpl.X.MessageStringOf` and the exact `prototext`/`protojson` marshal loops within the available context window (only match counts, not full bodies, were retrievable), so the "never enforced" conclusion is based on the absence of any `DebugRedact`/`redact` token in `encoding/prototext`, `encoding/protojson`, or `internal/impl` across the repo-wide grep. If a Devin session with full file access is available, it should confirm this by reading `encoding/prototext/encode.go`, `encoding/protojson/encode.go`, and `internal/impl/message_reflect.go`/`api_export.go` in full before treating this as conclusively verified.
