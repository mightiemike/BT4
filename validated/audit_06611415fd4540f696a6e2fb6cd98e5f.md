### Title
Uncaught `ArithmeticException` from SM2 signature recovery in `checkWeight` allows DoS of legitimate multisig `addSign` calls - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
`TransactionCapsule.addSign` calls `checkWeight` over the full existing signature list of a shared multisig transaction before appending the new co-signer's signature. The signature-recovery routine used to validate each existing signature (`SM2.recoverPubBytesFromSignature`) performs `sig.s.add(sig.r).modInverse(n)`, which throws an unchecked `ArithmeticException` ("BigInteger not invertible") whenever `r + s ≡ 0 (mod SM2_N)`. Since `addSign` only declares/handles `PermissionException`, `SignatureException`, and `SignatureFormatException`, this `ArithmeticException` is not caught anywhere in the call chain, so a single poisoned signature planted by an unprivileged third party can abort the entire `addSign` invocation for a legitimate co-owner.

### Finding Description
In `addSign` (chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java, lines 597-633), when `this.transaction.getSignatureCount() > 0`, the method calls: [1](#0-0) 

`checkWeight` iterates the existing signature list and recovers the signer's public key/address for each signature to compute weight/approval. That recovery ultimately goes through `SM2.recoverPubBytesFromSignature`: [2](#0-1) 

`sig.s.add(sig.r).modInverse(n)` throws `java.lang.ArithmeticException: BigInteger not invertible` whenever `gcd(r+s, n) != 1`, which is guaranteed when `r + s ≡ 0 (mod n)`. This is a standard degenerate/malformed EC signature case, not the legitimate output of a normal signing routine, but it is trivially craftable by anyone who can pick `r` and `s` values (no valid private key required to construct such a byte blob — it's a 65-byte structurally-valid-looking signature that just fails the modular-inverse step).

`addSign`'s method signature only declares checked exceptions `PermissionException, SignatureException, SignatureFormatException`; it performs no try/catch of its own around the `checkWeight` call. Any caller that wraps `addSign` in `catch (SignatureException | PermissionException | SignatureFormatException e)` (the pattern used elsewhere in this class, e.g. `validatePubSignature`, lines 671-676) will **not** catch the unchecked `ArithmeticException`, letting it propagate up as an unhandled runtime exception through whatever service thread invoked the multisig signing flow (e.g., the RPC/HTTP servlet backing `getTransactionSignWeight`/co-signing endpoints).

Because signature appending to a shared, not-yet-broadcast transaction is a normal part of the documented multisig collaborative-signing workflow, any account (not necessarily a permission-list member) that can submit a signature blob into that shared transaction object can plant this malformed entry before a legitimate owner calls `addSign`, causing that owner's approval attempt to blow up with an uncaught exception instead of a clean, expected `PermissionException`/`SignatureException`.

### Impact Explanation
This is a Denial-of-Service against the multisig approval workflow: an unprivileged attacker (any funded account, no permission-key membership required) can permanently block a legitimate co-owner's ability to complete `addSign` for a specific multisig transaction by seeding one poisoned signature into the shared, mutable signature list. Depending on how the calling service handles unexpected `RuntimeException`s, this can also destabilize the servicing thread/API handler for signing-related RPC calls. This maps to TRON's "DoS via RPC-API / DoS via the TRON protocol implementation" bounty impact class.

### Likelihood Explanation
- Precondition: the transaction must still be a mutable, collaboratively-signed multisig transaction (a supported, common workflow) reachable via signature-appending RPCs.
- Attacker cost: negligible — crafting a 65-byte blob with `r + s ≡ 0 mod SM2_N` requires no private key and no special access, only picking two BigIntegers satisfying a simple modular relation, then submitting it through the normal signature-append RPC path used during multisig collaboration.
- Repeatable: the attacker can do this to any in-flight multisig transaction they can observe/append to.
- No existing check intercepts this: `checkPermission`, `getWeight`, and the caller's catch clauses only cover `PermissionException`/`SignatureException`/`SignatureFormatException`, not `ArithmeticException`.

### Recommendation
In `SM2.recoverPubBytesFromSignature` (and analogously in `ECKey`'s ECDSA recovery path if it has the same pattern), catch `ArithmeticException` around the `modInverse` call and treat it as a failed/invalid recovery (return `null`), consistent with how `SM2.verify`/`verifyMessage` already guard against `NullPointerException` from malformed inputs. Additionally, harden `TransactionCapsule.checkWeight`/`addSign` (and any other caller iterating over externally-supplied signature lists) to catch generic `RuntimeException` around per-signature recovery/validation and skip or reject the offending signature instead of allowing it to abort the whole operation.
