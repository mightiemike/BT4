### Title
Tokens returning `false` on failed transfer will cause protocol to proceed as if successful - (`x/uexecutor/keeper/evm.go`)

### Summary
The Push Chain node executes ERC20 transfers (PRC20) via the `UniversalCore` (Handler) contract using `DerivedEVMCall`. For tokens that do not revert on failure but instead return `false` (e.g., ZRX), the current implementation in `x/uexecutor` fails to check the boolean return value. This results in the protocol recording a `SUCCESS` status in the `UniversalTx` state even when the actual token transfer failed, leading to lost funds for users or incorrect accounting of protocol-controlled assets.

### Finding Description
In `x/uexecutor/keeper/evm.go`, the functions `CallPRC20Deposit` [1](#0-0)  and `CallPRC20DepositAutoSwap` [2](#0-1)  perform EVM calls to the `UniversalCore` contract to move PRC20 tokens. These calls eventually invoke `transfer` or `transferFrom` on the underlying ERC20 contracts.

The `DerivedEVMCall` returns a `*evmtypes.MsgEthereumTxResponse`. The keeper logic in `ExecuteInboundFundsAndPayload` [3](#0-2)  and `ExecuteInboundGasAndPayload` [4](#0-3)  only checks if the EVM call itself errored (reverted). It does not unpack the `Ret` bytes to verify the boolean success value returned by the `depositPRC20Token` or `depositPRC20WithAutoSwap` methods.

If a "return-false" token is used and the transfer fails (e.g., due to a blacklisted address or insufficient balance in the bridge), the EVM execution will complete without reverting. The `execErr` will be `nil`, and the protocol will proceed to mark the deposit as `SUCCESS` [5](#0-4) , even though no tokens were actually moved.

### Impact Explanation
- **Loss of Funds:** Users depositing tokens that return `false` on failure will have their `UniversalTx` marked as successful on Push Chain. The protocol will attempt to execute the payload or credit the UEA, but the actual PRC20 tokens will never have arrived in the recipient's account.
- **Accounting Corruption:** The `UniversalTx` state will permanently record a `SUCCESS` status for a failed transfer [6](#0-5) , making it impossible for automated recovery or refund systems to identify the discrepancy.
- **Unauthorized Execution:** In `FUNDS_AND_PAYLOAD` flows, the payload execution proceeds only if the deposit is successful. By ignoring the `false` return, the protocol may execute logic that assumes funds are present when they are not.

### Likelihood Explanation
Low. While most modern tokens revert on failure, several high-profile tokens (like ZRX or older USDT implementations) return `false`. The Push Chain's universal execution model is designed to support a wide range of external assets via PRC20 mapping, increasing the surface area for encountering such tokens.

### Recommendation
Update `CallPRC20Deposit` and `CallPRC20DepositAutoSwap` in `x/uexecutor/keeper/evm.go` to unpack the boolean return value from the `MsgEthereumTxResponse.Ret` and return an error if the value is `false`.

```go
// Example fix for CallPRC20Deposit:
receipt, err := k.evmKeeper.DerivedEVMCall(...)
if err != nil { return nil, err }
results, err := abi.Methods["depositPRC20Token"].Outputs.Unpack(receipt.Ret)
if err != nil { return nil, err }
if !results[0].(bool) { return nil, fmt.Errorf("PRC20 transfer failed") }
return receipt, nil
```

### Proof of Concept
1. An attacker or user initiates an `Inbound` with a PRC20 token that returns `false` on failed `transferFrom` (e.g., ZRX).
2. The `UniversalCore` contract's `depositPRC20Token` is called via `CallPRC20Deposit` [7](#0-6) .
3. The underlying token transfer fails (e.g., the bridge's allowance was revoked), returning `false`.
4. `UniversalCore` returns `false` to the keeper.
5. `ExecuteInboundFundsAndPayload` receives `execErr == nil` [8](#0-7)  because the EVM did not revert.
6. The protocol records `depositPcTx.Status = "SUCCESS"` [5](#0-4)  and appends it to the `UniversalTx`.
7. The system proceeds to execute the user's payload [9](#0-8) , despite the deposit having failed.

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
