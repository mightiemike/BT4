Based on my investigation, I found a genuine state-integrity gap in transaction-output verification that is self-documented in the code but never enforced.

### Title
`ensure_match_transaction_info` silently skips state/hot-state/position checkpoint hash verification, allowing undetected state-root divergence during replay/fast-sync verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole function used across the codebase to confirm that a locally re-executed transaction produces the *same ledger state* as the transaction info that is authenticated by an accumulator proof / signed `LedgerInfo`. It checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` carried on `TransactionInfo`.

### Finding Description [1](#0-0) 

The function body computes and checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (hash of `self.write_set()`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but the trailing comment explicitly acknowledges the gap: [2](#0-1) 

No comparison is ever made against `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` on `TransactionInfo`, even though these fields are the durable JMT/hot-state/position Merkle roots that the storage layer actually commits to disk at checkpoint boundaries.

This function is relied upon as the *only* correctness gate in multiple integrity-sensitive paths:
- Chunk executor replay/fast-sync verification, which re-executes a downloaded chunk and compares it against the trusted, proof-verified `transaction_infos`: [3](#0-2) 
- Offline archive replay-verification tooling that is specifically meant to catch state divergence on historical/archive nodes: [4](#0-3) 
- CLI/debugger replay tooling: [5](#0-4) [6](#0-5) 

### Impact Explanation
Because the checkpoint-hash fields are skipped, any local execution engine bug or storage-layer defect that causes the locally computed state root (JMT root, hot-state root, or position-state root) to diverge from the authenticated `TransactionInfo.state_checkpoint_hash` — while incidentally producing the same write-set hash, event root, gas, and status — will be reported as a *successful match*. This is exactly the "hard-fork-only divergence during commit/replay/restore" class: the node (or replay-verify/db-tool auditing pipeline meant to catch such divergences before they reach production) proceeds as if execution is correct, silently persisting/accepting state whose durable root diverges from the chain-agreed value. Since `TransactionOutputListWithProofV2`/`TransactionOutputListWithProof::verify` (accumulator-proof verification) binds the *whole* `TransactionInfo` hash (including checkpoint hashes) against the signed ledger info, this doesn't let an attacker forge a fraudulent proof — but it does defeat the redundant application-level "does local execution match" safety net that fast-sync verification and archive replay-verify tooling depend on to detect determinism bugs before they cause a chain split.

### Likelihood Explanation
Likelihood of an actual state-corrupting bug tripping this exact blind spot is not high on its own (it requires write-set/events/gas/status to match while checkpoint roots differ), but this is precisely the scenario introduced by new features that touch the "hidden" Merkle structures (hot-state, position state) without touching the visible write set — which is why the code comment calls out `COMPUTE_TRADING_NATIVE_STATE_ROOTS` by name as the trigger for enabling stricter checks. Until that validation is added, any regression in hot-state or position-state root computation is fundamentally undetectable by the tooling designed to catch it.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`-derived (or caller-supplied) `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields on `txn_info` whenever those values are computable/available at the call site, before any feature that depends on hot-state/position-state correctness (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled on mainnet.

### Proof of Concept
Not directly exploitable by external unprivileged input (the accumulator proof already binds the full `TransactionInfo` including checkpoint hashes), so no standalone repro producing a forged proof is possible. The demonstrable defect is a code-level invariant violation: construct two `TransactionOutput`/`TransactionInfo` pairs with identical `write_set`, `events`, `gas_used`, and `status`, but different `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) values on the `TransactionInfo`, and observe that `ensure_match_transaction_info` returns `Ok(())` for both, i.e., it cannot detect the divergence in the committed ledger root that these hashes represent.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
