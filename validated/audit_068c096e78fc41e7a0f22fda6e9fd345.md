**Analysis:**

The view function filter check and the actual module/function resolution both operate on the exact same in-memory `ViewFunction` struct decoded once via `bcs::from_bytes_with_limit`. In `api/src/view_function.rs`, the filter check at <cite repo="patrichyt/aptos-core--035" path="api/src/view_function.rs" start="139-152" end="139-152" /> uses `view_function.module.address()`, `view_function.module.name().as_str()`, and `view_function.function.as_str()` directly, and the same cloned struct fields are passed into `AptosVM::execute_view_function` immediately afterward at <cite repo="patrichyt/aptos-core--035" path="api/src/view_function.rs" start="154-161" end="154-161" />. There is no re-decoding, re-parsing, or separate normalization step between the check and the execution — both operate on the identical `ModuleId`/`Identifier` values produced by the single BCS deserialization.

`ModuleId` equality/lookup is a plain byte-exact struct comparison of `AccountAddress` (fixed 32 bytes) and `Identifier` (a `Box<str>`), with no case-folding or encoding normalization anywhere in the comparison path: [1](#0-0) . The `ViewFilter::allows` implementation performs a straightforward `==` comparison against configured `ViewFunctionId` entries: [2](#0-1) .

One notable detail: `Identifier` derives `Serialize`/`Deserialize` directly on `Box<str>` rather than routing through `Identifier::new` (which enforces `is_valid`) [3](#0-2) , so a crafted BCS payload could in principle produce an `Identifier` containing characters that wouldn't pass `Identifier::new`. However, this does not create a filter-bypass: the loader/module resolution path (`dispatch_loader!` / `load_instantiated_function` in `aptos_vm.rs`) uses the exact same `Identifier` value for lookup as the filter check used, so whatever bytes are in the string, both the filter comparison and the module resolution see identical bytes — there is no divergence point where the filter could see one encoding and the loader another. [4](#0-3) 

Because the filter check and the executed function reference are the same deserialized values with no intermediate re-interpretation, there is no path for a crafted BCS payload to pass the filter while resolving to a different (blocklisted) module at execution time. This closes off the TOCTOU-style bypass hypothesized in the question.

    pub fn allows(&self, address: &AccountAddress, module: &str, function: &str) -> bool {
