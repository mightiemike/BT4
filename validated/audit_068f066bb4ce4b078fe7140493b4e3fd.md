### Title
DoS on transaction admission via self-induced shard congestion (front-running a victim's time-sensitive transaction) - (File: `core/primitives/src/congestion_info.rs`)

### Summary
NEAR's cross-shard congestion control gates new-transaction admission to a shard purely on an aggregate, attacker-influenceable metric (`CongestionInfo`), with no per-account isolation. An unprivileged account can flood a target shard with self-funded transactions to push `congestion_level` to 1.0 ("fully congested"), which causes `shard_accepts_transactions()` to reject *any* new transaction whose `receiver_id` maps to that shard — including a victim's own time-sensitive transaction submitted moments later. This is the direct structural analog of the Sherlock M-4 finding, where an attacker manipulates a shared "utilization" state variable via their own (cheap) transaction to make a targeted, time-sensitive protocol action (there: liquidation `seize`) revert/be rejected.

### Finding Description
Shard congestion is computed from aggregate, protocol-visible counters (`delayed_receipts_gas`, `buffered_receipts_gas`, `receipt_bytes`) that any account can grow simply by submitting gas-heavy transactions/receipts targeting (or routed through) that shard: [1](#0-0) 

`shard_accepts_transactions()` computes `congestion_level` as the max of incoming/outgoing/memory/missed-chunks fractions and rejects all new transactions to the shard once the level is at or above `reject_tx_congestion_threshold` (0.8 by default): [2](#0-1) 

This gate is enforced both at RPC-side transaction validation and at chunk-producer transaction selection, so a congested shard rejects incoming transactions network-wide, not just for the flooding account: [3](#0-2) [4](#0-3) 

There is an existing test that demonstrates exactly this attack primitive: an account submits 1,000 100-Tgas function calls to intentionally drive the receiver shard to full congestion, after which even a distinct account's ordinary transaction to that shard is rejected with `InvalidTxError::ShardCongested`: [5](#0-4) 

This mirrors the Sherlock bug pattern precisely: in the referenced report, an attacker manipulates a shared utilization/liquidity state variable (`floatingBackupBorrowed + floatingDebt vs newFloatingAssets`) via a cheap, unprivileged transaction so that a victim's critical, time-sensitive call (`liquidate`/`seize`) is rejected by a liquidity check. Here, the "utilization" analog is `congestion_level`, and the "critical call that gets rejected" analog is any transaction — potentially the victim's own time-sensitive transaction — targeting the congested shard.

### Impact Explanation
While congestion control is an intentional backpressure mechanism, its purely aggregate nature means it can be weaponized: an attacker who knows a victim needs to land a time-sensitive transaction on a specific shard (e.g., to react to a price move, claim a reward window, or otherwise act before a deadline) can flood that shard just beforehand to guarantee the victim's transaction is rejected at admission (`ShardCongested`) for as long as the attacker sustains the flood. Because rejection happens at both RPC validation and chunk-producer selection, this is a shard-wide availability impact on a "time-sensitive function," which is exactly the basis on which the analogous Sherlock issue was judged (Medium severity — DoS impacting availability of a time-sensitive function, without meeting the "loss of funds for >1 week" bar for High).

### Likelihood Explanation
The "red-light" design guarantees eventual progress (only the deterministically-rotating `allowed_shard` may still forward when fully congested, per `finalize_allowed_shard`/`get_new_allowed_shard`), so the DoS is bounded rather than permanent — this parallels the Sherlock precedent, which was ultimately judged Medium rather than High. Likelihood is non-trivial because:
- The attacker only needs enough of their own gas budget to push `delayed_receipts_gas`/`buffered_receipts_gas` past `max_congestion_incoming_gas`/`max_congestion_outgoing_gas` for the targeted shard, which is demonstrably achievable with a bounded burst of self-funded transactions (as shown by the existing `test_rpc_client_rejection` test).
- The mechanism has no notion of "whose transaction is congesting whom" — the effect is indiscriminate across all senders targeting that shard, so a victim's transaction is blocked as collateral damage even though the victim did nothing wrong.

### Recommendation
Consider adding per-sender or per-priority admission accounting (rather than a purely aggregate shard-level threshold) so a single account cannot unilaterally push a shard to the rejection threshold and block unrelated senders' time-sensitive transactions. At minimum, document and monitor for this griefing vector, and evaluate whether `reject_tx_congestion_threshold`/`max_congestion_incoming_gas`/`max_congestion_outgoing_gas` provide sufficient headroom against a single actor's realistic gas budget.

### Proof of Concept
The existing test in the codebase already demonstrates the primitive end-to-end: [5](#0-4) 

1. Attacker account submits a burst of 1,000 high-gas (100 Tgas each) function-call transactions targeting accounts on the victim's shard.
2. Wait a few blocks for receipts to arrive and accumulate in the receiver shard's delayed/buffered queues, driving `congestion_level` to 1.0.
3. Immediately after, submit (or have the victim submit) an ordinary transaction to that same shard — the RPC node rejects it with `InvalidTxError::ShardCongested`, exactly as asserted in the test at lines 533–538.
4. An attacker aware of a victim's need to land a specific time-sensitive transaction can time step (1)–(2) to precede the victim's submission, ensuring rejection during the critical window.

    /// Whether we can accept new transaction with the receiver set to this shard.
    ///
    /// If the shard doesn't accept new transaction, provide the reason for
    /// extra debugging information.
    pub fn shard_accepts_transactions(&self) -> ShardAcceptsTransactions {
        let incoming_congestion = self.incoming_congestion();
        let outgoing_congestion = self.outgoing_congestion();
        let memory_congestion = self.memory_congestion();
        let missed_chunks_congestion = self.missed_chunks_congestion();

        let congestion_level = incoming_congestion
            .max(outgoing_congestion)
            .max(memory_congestion)
            .max(missed_chunks_congestion);

        // Convert to NotNan here, if not possible, the max above is already meaningless.
        let congestion_level =
            NotNan::new(congestion_level).unwrap_or_else(|_| NotNan::new(1.0).unwrap());
        if *congestion_level < self.config.reject_tx_congestion_threshold {
            return ShardAcceptsTransactions::Yes;
        }

        let reason = if missed_chunks_congestion >= *congestion_level {
            RejectTransactionReason::MissedChunks { missed_chunks: self.missed_chunks_count }
        } else if incoming_congestion >= *congestion_level {
            RejectTransactionReason::IncomingCongestion { congestion_level }
        } else if outgoing_congestion >= *congestion_level {
            RejectTransactionReason::OutgoingCongestion { congestion_level }
        } else {
            RejectTransactionReason::MemoryCongestion { congestion_level }
        };
        ShardAcceptsTransactions::No(reason)
    }

/// Returns true if the transaction passes the congestion control checks. The
/// transaction will be accepted if the receiving shard is not congested or its
/// congestion level is below the threshold.
fn congestion_control_accepts_transaction(
    epoch_manager: &dyn EpochManagerAdapter,
    runtime_config: &RuntimeConfig,
    epoch_id: &EpochId,
    prev_block: &PrepareTransactionsBlockContext,
    validated_tx: &ValidatedTransaction,
) -> Result<bool, Error> {
    let receiver_id = validated_tx.receiver_id();
    let receiving_shard = account_id_to_shard_id(epoch_manager, receiver_id, &epoch_id)?;
    let congestion_info = prev_block.congestion_info.get(&receiving_shard);
    let Some(congestion_info) = congestion_info else {
        return Ok(true);
    };

    let congestion_control = CongestionControl::new(
        runtime_config.congestion_control_config,
        congestion_info.congestion_info,
        congestion_info.missed_chunks_count,
    );
    let shard_accepts_transactions = congestion_control.shard_accepts_transactions();
    Ok(shard_accepts_transactions.is_yes())
}

/// Test that RPC clients stop accepting transactions when the receiver is

#[test]
fn test_rpc_client_rejection() {
    init_test_logger();

    let sender_id: AccountId = "test0".parse().unwrap();
    let mut env = setup_congestion_env();

    setup_contract(&mut env);

    let signer: Signer = InMemorySigner::test_signer(&sender_id);

    // Check we can send transactions at the start.
    let mut nonce = env.validator().get_next_nonce(&sender_id);
    let block_hash = env.validator().head().last_block_hash;
    let fn_tx = new_fn_call_100tgas(&mut nonce, &signer, block_hash);
    assert_eq!(process_tx(&env, fn_tx), ProcessTxResponse::ValidTx);

    // Congest the network with a burst of 100 PGas.
    submit_n_100tgas_fns(&env, 1_000, &mut nonce, &signer);

    // Allow transactions to enter the chain and receipts to arrive at the
    // receiver shard for it to become congested.
    for _ in 0..9 {
        env.validator_runner().run_for_number_of_blocks(1);
    }

    // Check that congestion control rejects new transactions.
    let block_hash = env.validator().head().last_block_hash;
    let fn_tx = new_fn_call_100tgas(&mut nonce, &signer, block_hash);
    assert_matches!(
        process_tx(&env, fn_tx),
        ProcessTxResponse::InvalidTx(InvalidTxError::ShardCongested { .. })
    );
}
