### Title
Delegated resource accounting for a receiver can be corrupted/lost by any single delegator when the receiver account is deleted and recreated - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
Multiple TRX holders can independently delegate bandwidth/energy to the same `receiverAddress` via `DelegateResourceProcessor`, each contribution being accumulated into a single shared counter on the receiver's `AccountCapsule` (`AcquiredDelegatedFrozenV2BalanceForBandwidth`/`...ForEnergy`). If the receiver account is later deleted (e.g. via TVM `SUICIDE` on a contract that was previously a normal account receiving delegations) and subsequently recreated, this shared counter is reset while the individual `DelegatedResourceCapsule` records tracking each delegator's contribution are **not** cleared. Any one of the original delegators can then call `unDelegateResource`, and the code's defensive fallback for this exact situation zeroes out the receiver's shared "Acquired" counter — even though that counter may by then legitimately hold balance freshly delegated by a completely unrelated delegator. This causes loss/corruption of that other delegator's resource accounting, analogous to the Remora forwarder griefing pattern where a shared aggregate state (the forwarder's `calculatedPayout`) gets wiped by an unrelated party's action.

### Finding Description
`DelegateResourceProcessor.delegateResource()` accumulates every owner's delegated amount into the **same** receiver `AccountCapsule` field: [1](#0-0) 

This is a shared aggregate across all delegators pointing at the same receiver, just like Remora's forwarder `calculatedPayout` aggregates payouts from all holders forwarding to the same address.

`UnDelegateResourceProcessor.execute()` explicitly documents and handles the case where the receiver account was deleted and later recreated (e.g. by a TVM contract `SUICIDE`/re-creation flow): [2](#0-1) 

The comment "A TVM contract suicide, re-create will produce this situation" confirms this is a known, reachable production scenario, not a hypothetical. When the receiver's tracked `AcquiredDelegatedFrozenV2BalanceForBandwidth` is less than the amount the caller is now un-delegating (because it was wiped by account deletion), the code simply forces it to `0` instead of validating whose contribution is actually being removed. If, in the interim, a **different**, unrelated delegator has already re-delegated resources to the recreated receiver (raising the counter back above the caller's un-delegate amount), the `< unDelegateBalance` branch is skipped and the code instead subtracts the caller's `unDelegateBalance` from the counter that now legitimately represents the other delegator's contribution: [3](#0-2) 

Either branch corrupts the shared receiver counter relative to the actual, unrelated delegator's true contribution — either zeroing it out entirely or silently decrementing it by an amount that has nothing to do with that delegator's own resources. The per-pair `DelegatedResourceCapsule` (owner→receiver) records are untouched by this bug, so the corruption is isolated to the receiver's aggregate `Acquired...` counters, which drive bandwidth/energy usage accounting (`transferUsage`, `newNetUsage`/`newEnergyUsage`) for the receiver.

The project's own tests demonstrate exactly this loss of legitimately-tracked balance: [4](#0-3) [5](#0-4) 

Here a recreated receiver with a legitimately-set `AcquiredDelegatedFrozenV2BalanceForBandwidth = 10` (representing another delegator's contribution) ends up at `0` after an unrelated owner's unfreeze/undelegate operation goes through the "reset to 0" branch — the 10 units of tracked delegation belonging to whoever contributed them is silently lost.

### Impact Explanation
This corrupts the receiver's shared delegated-resource accounting (`AcquiredDelegatedFrozenV2BalanceForBandwidth`/`ForEnergy`), which underpins how much bandwidth/energy usage is attributed to and transferable for that receiver. A single delegator's un-delegate action (triggered directly, or indirectly by causing/observing a receiver contract's suicide+recreation) can zero out or corrupt tracking for resources actually delegated by other, unrelated accounts, leading to incorrect resource usage accounting for the receiver and desynchronization between the aggregate counter and the sum of individual `DelegatedResourceCapsule` entries. This is a resource-accounting integrity issue reachable from ordinary broadcast transactions (`DelegateResourceContract`/`UnDelegateResourceContract`, and TVM `delegateResource`/`unDelegateResource` opcodes), not requiring any privileged role.

### Likelihood Explanation
Requires a receiver address that: (1) received delegated resources as a normal account, (2) becomes a TVM contract and self-destructs (or otherwise has its `AccountCapsule` deleted) causing the aggregate counter to be wiped, and (3) is recreated and receives new delegations from another party before the original delegator calls `unDelegateResource`. The `SUICIDE`/re-create path is explicitly anticipated by the codebase's own comments and tests, indicating the maintainers consider it a real, occurring scenario, though it depends on specific ordering of delegate/suicide/recreate/undelegate transactions.

### Recommendation
Do not rely on the receiver's current aggregate `Acquired...` counter as a proxy for "is this the same logical delegation." Instead, before resetting or decrementing the receiver's aggregate counter in `UnDelegateResourceProcessor`, verify that the value being cleared truly corresponds to the calling owner's own `DelegatedResourceCapsule` record rather than blindly comparing against the current shared total, or maintain a per-owner acquired-balance mapping that cannot be conflated with unrelated delegators' contributions after account deletion/recreation.

### Proof of Concept
The project's existing test already demonstrates the corruption pattern (a legitimately-tracked `AcquiredDelegatedFrozenV2BalanceForBandwidth` value belonging to a delegation that is not the caller's own gets wiped/corrupted by an unrelated un-delegate/unfreeze call): [6](#0-5)
