### Title
Deposits can silently mint 0 vault shares while the underlying is still collected, permanently diluting the depositor's funds - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
The `deposit` entrypoint of every mainnet vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) computes the shares to mint via `convert-to-shares-preview`, checks only a slippage bound against a caller-supplied `min-out`, and never rejects a resulting share amount of zero. This mirrors the reported Hyperdrive bug class: a share-mint pathway that permits `amount == 0`, letting a liquidity/asset contribution be silently absorbed with zero shares issued to the depositor.

### Finding Description
In `deposit`, the mint amount `inkind` is derived once from `convert-to-shares-preview amount` and used for both the slippage guard and the actual mint: [1](#0-0) 

The only checks performed are:
- `(> amount u0)` — the underlying deposit amount is non-zero.
- `(>= inkind min-out)` — a slippage bound, which is satisfied trivially when the caller passes `min-out u0` (the default/common case for many integrators) even if `inkind` itself rounds down to `0`.

There is no analogous `(> inkind u0)` guard on the deposit path. Compare this to `redeem`, in the same contracts, which explicitly guards against a zero output: [2](#0-1) 

Because `convert-to-shares-preview` is a ratio computation (`amount * total-shares / total-assets`-style rounding), whenever the vault's `assets` pool is large relative to a deposit amount, `inkind` rounds down to `0`. When that happens:
1. `(> amount u0)` passes (the underlying amount deposited is non-zero).
2. `(>= inkind min-out)` passes when `min-out` is `0` (or any caller-tolerated slippage that accepts 0).
3. `(try! (receive-underlying amount account))` pulls the depositor's real tokens into the vault.
4. `(try! (ft-mint? zft inkind recipient))` mints `0` shares to the depositor — a mutation is executed even though the "guard" that should have blocked a zero-value mint was never written for this path.
5. `(var-set assets (+ current-assets amount))` permanently folds the depositor's contribution into the shared asset pool, proportionally diluting/enriching all *other* existing shareholders.

This is a single-transaction, self-contained bug: the mutation (`ft-mint?` with amount 0, plus the `assets` pool update) is evaluated without the guard that exists on the symmetric `redeem` path, exactly the analog class described in the external report ("a function that allows minting when the amount is equal to 0").

### Impact Explanation
The depositor's underlying tokens are transferred into the vault (`receive-underlying`) and folded into `assets`, but they receive `0` `zft` shares, i.e., no claim on the vault whatsoever. Their contribution becomes permanently and irretrievably absorbed by the vault (silently redistributed to all other current LPs pro-rata), with no way for the depositor to reclaim it. This is a permanent loss of the depositor's principal, matching the in-scope Critical impact class of "permanent freezing of funds" (functionally indistinguishable from direct theft of the deposited principal since the victim can never recover it through any protocol-provided function).

### Likelihood Explanation
This can be triggered by any single caller in one transaction and requires no privileged access, oracle manipulation, or interference with another user — it only requires that the vault's already-accumulated `assets` be large enough relative to the deposit amount that `convert-to-shares-preview` rounds the resulting shares down to `0`, combined with the caller (or an integrating contract/UI) passing `min-out` of `0` or otherwise tolerating the rounding. As vault TVL grows over the life of the protocol, and any integrator that defaults `min-out` to `0` for convenience, this scenario becomes increasingly reachable without any adversarial setup.

### Recommendation
Add an explicit zero-output guard to `deposit`, symmetric to the one already present in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed before the mint call in every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`), so a deposit that would compute to `0` shares reverts instead of silently forfeiting the depositor's underlying tokens.

### Proof of Concept
1. Vault `v0-vault-stx.clar` has accumulated a large `assets` balance and a correspondingly large `zft` total supply (normal operation over time).
2. A user calls `deposit` with a small `amount` (relative to the vault's asset base) and `min-out u0` (default in most integrations/UI flows that don't set explicit slippage protection). [1](#0-0) 
3. `convert-to-shares-preview amount` rounds down to `inkind = u0` due to the ratio-based share calculation.
4. `(> amount u0)` passes since the raw deposit amount is non-zero; `(>= inkind min-out)` passes since `0 >= 0`.
5. `receive-underlying` pulls the user's tokens into the vault; `ft-mint? zft u0 recipient` mints zero shares to the user; `assets` is incremented by the user's full deposited amount.
6. The user now holds `0` additional `zft` shares despite having transferred real underlying tokens into the vault — their contribution is permanently redistributed to existing shareholders with no recovery path.
