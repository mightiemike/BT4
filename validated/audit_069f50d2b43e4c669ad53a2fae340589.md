## Analog Found: Liquidity Cap on `TokenConfig` Is Never Enforced During PRC20 Minting

### Title
Registry-declared `liquidity_cap` for a token is never checked during inbound PRC20 minting, allowing unbounded PRC20 issuance past the configured cap - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/execute_inbound_funds.go`)

### Summary
The reported bug class is a maximum-amount safeguard (`tfMaxAmount`) that exists in configuration/state but is not actually enforced against the real cumulative effect it is meant to bound, letting ordinary, unprivileged transaction flow silently exceed the intended cap. The Push Chain analog is the `liquidity_cap` field on `x/uregistry`'s `TokenConfig`, documented as the "max supply cap for this token" [1](#0-0)  but never read, compared, or enforced anywhere in the PRC20 deposit/minting path.

### Finding Description
`TokenConfig.LiquidityCap` is validated only for non-emptiness at registration time [2](#0-1) ; it is never used to bound how much PRC20 can actually be minted. The inbound-funds execution path calls `depositPRC20`, which loads the `TokenConfig` purely to resolve the PRC20 contract address and then unconditionally calls `CallPRC20Deposit` for whatever amount the inbound carries — no comparison against `LiquidityCap` or any tracked cumulative minted amount occurs: [3](#0-2) 

`ExecuteInboundFunds`, which drives this on the standard funds-inbound flow, likewise performs no cap check before or after calling `depositPRC20` [4](#0-3) . The same is true of the FUNDS_AND_PAYLOAD/GAS_AND_PAYLOAD deposit calls [5](#0-4) . Repository tests confirm multiple inbounds simply accumulate balance with no ceiling check, e.g. `TestSolanaInboundFunds`'s "multiple solana FUNDS inbounds accumulate balance" case mints 2x the per-inbound amount without any cap-related assertion or rejection [6](#0-5) , and the equivalent EVM test does the same [7](#0-6) .

This mirrors the report's bug class precisely: a "maximum amount" concept is defined in configuration (`tfMaxAmount` / `liquidity_cap`) to bound value for a given token, but the enforcement code never exists in the execution path that actually moves/mints value, so the boundary is either bypassable via repeated transfers (as reported) or — in this case — entirely absent regardless of how many transfers are used.

### Impact Explanation
The `liquidity_cap` is the protocol's declared risk ceiling for how much PRC20 representation of an external asset should ever exist on Push Chain. Because ordinary, honest-validator-attested inbound votes drive minting with no reference to this cap, the total minted PRC20 supply for any registered token can grow without bound purely through repeated ordinary user deposits — corrupting the PRC20 accounting invariant the registry is supposed to guarantee ("Registry and accounting path... must not misroute value or attach the wrong asset semantics"). This is reachable by any unprivileged external-chain user simply sending more deposits; no privileged or malicious-validator behavior is required.

### Likelihood Explanation
High. No code changes or edge cases are needed to trigger it — every ordinary inbound funds deposit already goes through this unguarded path with honest validators voting on real (but arbitrarily numerous) source-chain events.

### Recommendation
Track cumulative minted PRC20 supply per `TokenConfig` (or query the PRC20 contract's `totalSupply`) and enforce it against `LiquidityCap` inside `depositPRC20` (or its callers) before calling `CallPRC20Deposit`, rejecting/reverting inbound execution when the cap would be exceeded — consistent with the existing pattern of surfacing failures as a `FAILED` `PCTx` plus revert-outbound rather than dropping votes.

### Proof of Concept
1. Register a `TokenConfig` with `LiquidityCap = "1000000000000000000000000"` (as done in all test setups, e.g. `test/integration/uexecutor/inbound_solana_test.go`).
2. Submit N inbound FUNDS votes from honest UVs for the same token/source chain, each individually well under the cap, until the cumulative minted PRC20 balance for the recipient (or total supply) exceeds `LiquidityCap`.
3. Observe (as in `TestSolanaInboundFunds`'s "multiple solana FUNDS inbounds accumulate balance" subtest) that `depositPRC20`/`ExecuteInboundFunds` mint every inbound with no cap check, so the aggregate PRC20 supply surpasses the configured `liquidity_cap` with no error, exactly as the reported `tfMaxAmount` bypass allowed exceeding the intended transfer ceiling via multiple sub-cap transfers.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```
