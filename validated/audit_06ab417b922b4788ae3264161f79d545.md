I found a clear, self-documented, and locally-provable integrity gap.

### Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, letting replay-verify accept a divergent committed state root - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info()` is the authenticated-invariant check used by replay/debugger tooling to confirm that a locally re-executed `TransactionOutput` matches the trusted, previously-committed `TransactionInfo` (the leaf object bound into the transaction accumulator and ultimately signed in a `LedgerInfo`). The function validates status, gas used, write-set hash, and event root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that authenticate the actual world-state (and "trading-native" position) Merkle roots. This means a local re-execution that produces the *correct* write set/events/gas/status, but a *different* state root (e.g., due to a state Merkle/JMT computation divergence, a hard-fork mismatch, or an inconsistent state-checkpoint transaction), is reported as "matching" and passes verification.

### Finding Description [1](#0-0) 

The function checks four things: `status`, `gas_used`, `write_set_hash` vs `txn_info.state_change_hash()`, and `event_root_hash` vs `txn_info.event_root_hash()`. It never reads or compares `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` against any locally computed state root. This gap is explicitly acknowledged in the trailing comment: "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

`TransactionInfo` is the object stored in, and hashed into, the transaction accumulator [2](#0-1) , and `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are the fields meant to bind a checkpoint transaction's `TransactionInfo` to the actual computed state root [3](#0-2) . Since this equality is never enforced by `ensure_match_transaction_info`, the function's guarantee ("outputs match the committed, proof-bound transaction info") is incomplete precisely on the state-root fields — the ones that matter most for detecting silent state divergence.

This check is consumed directly by:
- `storage/db-tool/src/replay_on_archive.rs` (replay-verify tooling against archived/mainnet data),
- `aptos-move/cli/src/commands.rs` (CLI transaction replay for system transactions),
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`. [4](#0-3) 

### Impact Explanation
Replay-verify is one of the primary mechanisms used to detect state-computation bugs, hard-fork-only divergences, and VM/state-Merkle-tree regressions before/after they hit mainnet (it's explicitly referenced by the "trading-native"/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` state root work). Because `ensure_match_transaction_info` silently omits the checkpoint-hash comparisons, a build/version whose locally computed state checkpoint root (or hot-state/position state root) diverges from the one committed on-chain will still report "replay succeeded." This directly matches the state-integrity gate's "committed state that differs from the correct VM result... accepted as valid" and "hard-fork-only divergence during commit/replay" categories — the verification tool is the authenticated gate meant to catch exactly this class of bug, and it structurally cannot.

### Likelihood Explanation
This is not a hypothetical edge case: it fires on every checkpoint transaction that replay-verify or the CLI/debugger processes, silently, with no error or warning distinguishing "not checked" from "checked and passed." Any latent state-computation bug (JMT computation error, hot-state computation error, the new "position" state root path) that preserves write-set/event/gas/status equivalence but produces a wrong Merkle root will pass unnoticed through this gate.

### Recommendation
Extend `ensure_match_transaction_info` to compute the local state checkpoint root(s) at checkpoint boundaries and assert they equal `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` whenever those fields are present in `txn_info`, mirroring the treatment already given to `state_change_hash` and `event_root_hash`. At minimum, gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or equivalent) behind this validation being implemented, as the existing comment recommends, rather than shipping replay tooling with this authentication hole open.

### Proof of Concept
1. Take any checkpoint transaction whose committed `TransactionInfo` (`V1`) carries a real `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
2. Run `db-tool replay-on-archive` (or the CLI system-transaction replay path in `aptos-move/cli/src/commands.rs`) against a build whose state-Merkle/hot-state/position computation is intentionally perturbed (e.g., patch the position state root builder to return a different-but-structurally-valid hash) while keeping write set, events, gas, and status identical.
3. Observe `ensure_match_transaction_info` at [5](#0-4)  returns `Ok(())` because none of the checkpoint-hash fields are ever read, even though the state root diverges from the authenticated on-chain value.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
