### Title
Malicious relayer with an unrevocable-in-practice `FunctionCall` access key can drain the NEAR Wallet Contract's balance via repeated "user-error" calls - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (an eth-implicit-account wallet used to relay Ethereum-style signed transactions) grants a relayer a persistent `FunctionCall` access key with **unlimited allowance** (`is_limited_allowance: false` → `allowance: None`) restricted to calling `rlp_execute` on the wallet account itself. [1](#0-0)  This is structurally the same pattern as the Teller `approveMarketForwarder()` bug: a third party (the relayer) is granted persistent authority to act through the victim account, and that authority is only revoked reactively, after damage may already have occurred, rather than being bounded up front.

### Finding Description
`register_relayer`/the wallet's `AddKey` action path creates a `FunctionCall` access key with `allowance: None` (unlimited) for the relayer, scoped to the `rlp_execute` method on the wallet contract account. [2](#0-1)  Since this is a `FunctionCall` access key, all gas and fee costs for each call are paid from the **wallet account's own NEAR balance** (per NEAR's access-key model, "both account balance and the allowance is decreased by the same value") [3](#0-2) , not from the relayer's own account.

The contract's self-defense mechanism only bans (revokes) the relayer when `inner_rlp_execute`/`rlp_execute` returns an `Error::Relayer(_)` variant while the signer is the current account (i.e., the relayer used its granted access key):
```
Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
    let promise = create_ban_relayer_promise(current_account_id);
    ...
}
``` [4](#0-3) 

Critically, `Error::User(_)` variants are explicitly **not** treated as ban-worthy — the code increments the nonce and returns the error without revoking the key:
```
Err(err @ Error::User(_)) => {
    // Increment nonce on all user errors to prevent replay.
    *nonce = nonce.saturating_add(1);
    return Err(err);
}
``` [5](#0-4) 

Because a compromised/malicious relayer fully controls which inputs it submits, it can repeatedly craft `tx_bytes_b64` payloads that deterministically fail with `Error::User(_)` (e.g., unsupported actions, malformed but "user-classified" inputs) rather than `Error::Relayer(_)`. Each such call is a legitimate `rlp_execute` invocation authorized by the relayer's still-valid access key, consumes attached gas paid from the wallet account's balance (allowance is unlimited), and never triggers `ban_relayer`. The only serialization guard is `has_in_flight_tx`, which prevents concurrent in-flight calls but does not prevent an unbounded sequence of sequential calls over time. [6](#0-5) 

This mirrors the Teller finding precisely: approval of a forwarder/relayer has no expiry and no proactive limit, revocation is reactive and only covers a narrowly-defined subset of misbehavior ("Relayer" errors), and a determined or compromised holder of the approval can exploit the gap (here, "User"-classified failure paths) to keep spending the victim's funds indefinitely.

### Impact Explanation
A single relayer account, once granted the unlimited-allowance `FunctionCall` key via `register_relayer`, can repeatedly call `rlp_execute` with inputs engineered to fail as `Error::User` and never get banned, burning the wallet account's NEAR balance on gas fees transaction after transaction. This is unauthorized value drain (gas fees paid by the victim account without ever completing the user's intended action) directly reachable by an unprivileged relayer/RPC caller holding the granted key — no validator, network, or operator privilege required.

### Likelihood Explanation
Likelihood is Medium: it requires the relayer key to first be granted (an expected part of the Wallet Contract's intended flow) and then either compromised or dishonestly operated. Given the design explicitly anticipates a "faulty relayer" and bans it only for `Relayer`-classified errors, any relayer that intentionally (or via a bug) triggers `User`-classified failures repeatedly evades the ban entirely, making exploitation straightforward for anyone who controls or compromises a registered relayer key.

### Recommendation
- Rate-limit or cap total gas/allowance consumable by a relayer key per unit time or per number of failed calls, regardless of error classification.
- Treat unexpectedly frequent `Error::User` failures from the same relayer-held key as suspicious and ban the key as well (fail-closed rather than fail-open on error-type classification).
- Consider giving the wallet owner a straightforward way to revoke a relayer key proactively (equivalent to Teller's recommended "add method to revoke approval") rather than relying solely on the contract's own reactive ban logic.

### Proof of Concept
1. Owner (or an app on their behalf) calls `rlp_execute` with an `AddKey` RLP-encoded action authorizing a `FunctionCall` access key for `relayer.near`, with `allowance: None` and `method_names: ["rlp_execute"]`, per `register_relayer`. [1](#0-0) 
2. `relayer.near`'s key is compromised or the relayer turns malicious.
3. The relayer repeatedly calls `rlp_execute` on the wallet contract with `tx_bytes_b64` payloads crafted to deterministically produce `Error::User(_)` (e.g., referencing unsupported actions/types recognized by `internal::parse_rlp_tx_to_action` as user errors) with `max_gas()` attached.
4. Each call increments the nonce and returns a failure response but does **not** invoke `create_ban_relayer_promise`, per the `Err(err @ Error::User(_))` branch. [5](#0-4) 
5. Gas for every call is paid from the wallet account's own balance (unlimited allowance `FunctionCall` key), and the relayer key remains valid indefinitely, letting the relayer repeat step 3 to continuously drain the account's NEAR balance.

Note: I was unable to fully inspect `internal.rs`'s `parse_rlp_tx_to_action` and the exact `UserError` variants/trigger conditions within the final iteration (index truncation prevented reading the full file), so the precise set of attacker-controllable inputs that produce `Error::User` versus `Error::Relayer` should be verified directly in `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs` and `types.rs` before treating this as fully confirmed.
