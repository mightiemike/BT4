### Title
Stale global class-cache entry lets a `Cairo0` class be treated as "declared" without state re-validation - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` serves compiled classes from a **process-global**, cross-block `ContractClassManager` cache (backed by `GlobalContractCache`, see [1](#0-0)  and [2](#0-1) ). Because this cache is not scoped to a single committed block, the code itself acknowledges a cache entry "might contain a declared class from a reverted block" and therefore re-validates against the authoritative `StateReader::is_declared` — but **only for non-`V0` (Cairo1) classes**. `RunnableCompiledClass::V0` (Cairo0) entries bypass this check entirely, matching the MongoDB "stale privilege after authorized change" bug class: an authorization fact ("this class is declared") is cached and reused after the authoritative source (committed chain state) has changed/reverted it away.

### Finding Description
In `get_compiled_from_class_manager`: [3](#0-2) 

The `match` arm explicitly special-cases `V0` to do nothing, while the fallback arm (Cairo1/native) calls `self.state_reader.is_declared(class_hash)` before trusting the cached value, with the comment making clear this guard exists specifically because the cache can outlive the state it was populated from.

The cache is populated on any miss via `contract_class_manager.set_and_compile(...)` [4](#0-3) , which is driven purely by `StateReader::get_compiled_class` calls made during transaction execution — including **speculative** execution of block proposals (e.g. `BlockBuilder`/`TransactionExecutor`/`WorkerExecutor` runs) that may later be aborted, superseded by another leader's block, or otherwise never committed (this scenario is explicitly modeled in mempool tests such as `test_commit_block_from_different_leader` [5](#0-4) , illustrating that a sequencer's local speculative state can diverge from what ultimately gets committed). `ContractClassManager`/`GlobalContractCache` is never invalidated on block abort/rewind — only the per-block `CachedState`/`VersionedState` is discarded.

Consequently: if a `Declare` transaction for a Cairo0 class is executed speculatively (by the node's own batcher during proposal building, or during gateway/mempool validation flows that read the class) but the containing block/proposal is discarded (lost to another leader, bounced, or the class hash later becomes technically "undeclared" from the canonical state's point of view), the Cairo0 class entry remains resident in the global cache. Any subsequent, unrelated transaction (Invoke, Deploy, or another Declare referencing the same `class_hash`) that calls `get_compiled_class` for that hash will hit the cache and — because the `V0` branch performs no re-validation — receive the compiled class as if it were validly declared in the current committed state, with no check against `state_reader.is_declared`/`get_compiled_classes` from the authoritative reader.

### Impact Explanation
This allows an account/contract execution flow (deploy, `library_call`, `replace_class`, or direct invocation) to proceed using a class hash that is not actually declared in the committed state on this node. Because `is_declared` is state-derived and part of block state (Patricia tree) commitments, a node that has this stale positive cache entry can compute a different execution result (and thus a different state diff / state root) than a node that does not have the stale entry (e.g. a freshly synced node, or a node that never happened to execute the aborted proposal). This is a **honest-node divergence / wrong committed root** risk: two correctly-behaving sequencer/validator nodes can disagree on whether a transaction reverts (`UndeclaredClassHash`) or succeeds, purely as a function of unrelated, non-deterministic local execution history (which proposals they happened to speculatively execute and cache). This satisfies the "wrong committed root or honest-node divergence" impact bar.

### Likelihood Explanation
Reachable from a single submitted transaction sequence with no special privileges: (1) submit or observe a `Declare` transaction for a Cairo0 class that gets speculatively executed by a node's batcher but not committed (lost proposal, contested nonce, aborted block — all normal, permissionless network conditions), then (2) submit a follow-up transaction referencing that same `class_hash` to any node whose global class cache still holds the stale entry. No malicious operator/proposer/peer behavior is required — this can occur under ordinary competitive block-building since only V0 lacks the guard that V1 already has (the V1 guard's existence proves the authors identified the general risk).

### Recommendation
Apply the same `is_declared` (or equivalent authoritative check) re-validation to the `RunnableCompiledClass::V0` branch that already exists for the Cairo1/native branch in `get_compiled_from_class_manager`, i.e. remove the `V0(_) => {}` no-op special case and unconditionally verify declaration status against `self.state_reader` before trusting any cached compiled class, regardless of Cairo version.

### Proof of Concept
Conceptual repro (would need to be validated against a full node/batcher integration harness, which was not available in this read-only investigation):
1. Node executes (speculatively, as part of proposal building) a `Declare` tx for a Cairo0 class `C`. This calls `get_compiled_class(C)` → cache miss → `set_and_compile` populates the global `ContractClassManager` cache with `CompiledClasses::V0`.
2. The proposal/block is discarded (e.g. another leader's competing block wins, per the pattern in `test_commit_block_from_different_leader`), so `C` is never actually declared in committed state.
3. A later, unrelated transaction (e.g. `Invoke` calling `deploy_syscall`/`library_call` with `class_hash = C`, or the syscall path in `syscall_base.rs::replace_class` [6](#0-5) ) triggers `get_compiled_class(C)` again on the same node.
4. `get_compiled_from_class_manager` hits the cache, matches `RunnableCompiledClass::V0(_) => {}` (no re-check), and returns the class successfully — despite `C` never having been declared in the canonical, committed state.

Confidence caveat: I could not fully trace whether `ContractClassManager`'s cache is explicitly cleared on `abort_block`/proposal rejection within the time available; this affects how easily attacker-controlled proposals populate the cache, but does not change the core finding that the `V0` branch is missing the `is_declared` guard that the `V1`/native branch has, which the code's own comment identifies as necessary specifically for this class of staleness.
