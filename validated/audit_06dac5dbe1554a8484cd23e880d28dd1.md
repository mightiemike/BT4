### Title
Stale block-scoped index-cache after bad-debt socialization allows overvalued zToken collateral to be used for borrows/withdrawals within the same block - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar` caches each vault's `{index, lindex}` in a persistent map `index-cache`, keyed by `{timestamp: stacks-block-time, aid}`, so that all operations touching the same vault within the same block reuse the cached value instead of re-accruing. ` [1](#0-0) ` However, `socialize-debt` on the vault contracts writes down `lindex` directly with `var-set`, completely bypassing `accrue`/`accrue-and-cache`, so the market's cache is never refreshed when bad debt is socialized. ` [2](#0-1) ` Because the cache key only changes once per block (not per-transaction), the stale, pre-socialization (higher) `lindex`/`index` remains readable by any other transaction in the same block that touches that vault, over-valuing zToken collateral or debt priced from it.

### Finding Description
1. `liquidate` primes the market's `index-cache` for the borrower's collateral/debt assets *before* it performs bad-debt socialization: `(u-debt (accrue-user-debts (get debt pos-full))) (u-coll (accrue-user-collateral (get collateral pos-full)))` runs first, populating `index-cache` for `{timestamp: stacks-block-time, aid}` via `accrue-and-cache`. [3](#0-2) 
2. Later in the same `liquidate` call, when the borrower has no collateral left, the market socializes remaining bad debt by folding `socialize-debt-asset` over the debt list, which calls into the vault's `socialize-debt`. [4](#0-3) 
3. The vault's `socialize-debt` directly mutates `lindex` (`var-set lindex new-lindex`) to write down the liquidity index for the loss, without going through `accrue`, and without any callback into the market to invalidate `index-cache`. [2](#0-1) 
4. `index-cache` is a persistent Clarity map keyed by `{timestamp, aid}` where `timestamp = stacks-block-time`; this timestamp is constant for the entire block, so the cache entry created in step 1 (before the write-down) remains a cache HIT for the rest of the block, for any transaction, not just the current one. `accrue-and-cache` returns the cached entry as-is on a hit: `(match cached? cached-indexes (ok cached-indexes) ...)`. [1](#0-0) 
5. `resolve-ztoken` prices zToken collateral purely from this cached `lindex` (`(scaled (* p cached-lindex)) ...`), so a subsequent transaction in the same block that supplies, borrows against, or withdraws that vault's zToken collateral will use the pre-socialization, inflated `lindex` instead of the true, written-down value. [5](#0-4) 

The cached value is `index-cache[{stacks-block-time, aid}] = {index, lindex}`, bound by the first `accrue-and-cache` call for that vault in the block; the invalidating event is `socialize-debt`'s direct `var-set lindex` bypassing accrual; the later use is any subsequent `borrow`/`collateral-add`/`collateral-remove`/`liquidate` transaction in the same block that calls `get-cached-indexes`/`accrue-and-cache` for the same `aid` and gets a cache hit with the stale, higher `lindex`.

### Impact Explanation
An overvalued `lindex` for a socialized vault makes zToken collateral backed by that vault appear worth more than it actually is post-write-down. Any user (not necessarily the liquidator) who interacts with the market in the same block — e.g., borrowing against zToken collateral of that vault, or withdrawing other collateral while relying on an inflated total collateral valuation for the health check — can pass a health check that should have failed, extracting more value than the position actually backs. This directly enables under-collateralized borrowing/withdrawal against real backing, i.e., theft of protocol funds / protocol insolvency, which falls in the Critical impact category.

### Likelihood Explanation
This requires: (a) a liquidation that triggers bad-debt socialization on a vault whose underlying token also has an active zToken used as collateral elsewhere, and (b) a second transaction in the same block that touches the same vault's cached index for pricing or debt calculation. Bad-debt socialization events themselves are rare (deep undercollateralization), but once one occurs, exploiting the stale cache only requires submitting a normal `borrow`/`collateral-add`/`collateral-remove` transaction in the same block — achievable by any user (including the liquidator) with standard block-inclusion timing, no special privileges needed.

### Recommendation
Invalidate or refresh the market's `index-cache` entry for an `aid` whenever that vault's `socialize-debt` (or any other out-of-band index mutation) is triggered within the same transaction/block, e.g., by having `socialize-debt` return the fresh `{index, lindex}` and having the market immediately `map-set` the cache with the new value (mirroring what `accrue-and-cache` does for normal accrual), or by removing/overwriting the stale cache entry for that `aid` right after the socialization fold completes in `liquidate`.

### Proof of Concept
1. Block N, Tx 1: Attacker/liquidator calls `liquidate` on a fully underwater borrower whose debt vault is `vault-stx` and who has zSTX (zToken on `vault-stx`) posted as collateral by other users.
2. Inside this `liquidate` call, `accrue-user-debts`/`accrue-user-collateral` populate `index-cache[{T, STX}] = {index0, lindex0}` (pre-loss values) before any state changes.
3. Because the borrower has no other collateral left, the fold over `socialize-debt-asset` calls `vault-stx.socialize-debt`, which `var-set`s `lindex` to a lower `new-lindex` reflecting the bad-debt loss — but market's `index-cache[{T, STX}]` is never updated.
4. Block N, Tx 2 (same block, submitted by any user): calls `market.borrow` or `market.collateral-add` using zSTX as collateral. The market calls `accrue-and-cache(STX)`, gets a cache HIT returning the stale `lindex0` (higher than the vault's actual post-socialization `lindex`), and `resolve-ztoken` overvalues the zSTX collateral.
5. The inflated collateral valuation lets the health check in `borrow`/`collateral-remove` pass for a position that would fail against the true, written-down `lindex`, letting the user borrow/withdraw more than their real collateral backs — until the next block's `stacks-block-time` changes and the cache is naturally invalidated.

Note: I was not able to independently execute this scenario in a live/test environment; the analysis is based on static code review of `market.clar`'s caching logic and the vaults' `socialize-debt` implementation, which are consistent across all vault variants (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`).

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

```text
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
```
