### Title
`ensure_match_transaction_info` in the archive replay-verify path skips checkpoint-hash comparison, allowing corrupted/divergent state roots to pass verification as a valid replay - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by `db-tool replay-on-archive` via `storage/db-tool/src/replay_on_archive.rs` and by the chunk executor's `verify_execution` diagnostic path in `execution/executor/src/chunk_executor/mod.rs`) checks transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against the archived `TransactionInfo`, but explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only four fields: execution status, gas used, write-set hash, and event root hash. The function's own comment documents the gap: [2](#0-1) 

This means that if local re-execution during archive replay computes a `state_checkpoint_hash` (the JMT state root after applying the write set) that differs from the value recorded on-chain in the authenticated `TransactionInfo`, this divergence is **not detected** by this check. This function is invoked in two places I confirmed in this codebase snapshot:
- `storage/db-tool/src/replay_on_archive.rs`, in `execute_and_verify`, at [3](#0-2) 
- `execution/executor/src/chunk_executor/mod.rs`, in `verify_execution` (used by "replay-verify" tooling paths), at [4](#0-3) 

Both tools exist specifically to detect state-root divergence between historical on-chain execution and re-execution against a new binary/VM (i.e., to catch hard-fork-class bugs before they reach mainnet). Since the state-checkpoint hash — the actual state-commitment root — is the one field that would reveal a wrong VM/JMT computation not otherwise reflected in gas/status/events/write-set hash equality, skipping it defeats the primary purpose of these tools for this class of bug.

### Impact Explanation
This does not corrupt consensus-committed data directly (the normal block-commit path computes and persists `state_checkpoint_hash` via `DoStateCheckpoint::run` independently, per [5](#0-4) , and this is not what's being bypassed here). The impact is that the **safety-net tooling** meant to catch a state root divergence (a hard-fork-only bug) before an upgrade goes live can silently pass a binary that would corrupt the mainnet state root on real traffic, because it only re-validates write-set/event/gas/status equality, not the resulting checkpoint hash. This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" category in the required impact list, since a validator or the Aptos team could run `replay-on-archive` (or use `verify_execution` chunk replay-verify), see it pass, and unknowingly deploy code that computes a different (wrong) state root, corrupting the durable ledger once run live.

### Likelihood Explanation
Likelihood is moderate: the bug requires (1) an actual VM/state-application defect that changes the JMT root without changing the write-set content itself (e.g. bugs in nibble/versioning logic, an unrelated existing DB key colliding, or JMT node-key/version handling bugs), and (2) reliance on the affected verify path to catch it before mainnet deployment. This is exactly the scenario the TODO comment in the code anticipates ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), indicating the Aptos team is already aware this gap needs to be closed before enabling checkpoint-hash-dependent features, but the current code still ships without the check active for either the existing `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`'s locally computed `state_checkpoint_hash` (and, where applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against `txn_info`'s corresponding fields whenever the transaction is a checkpoint transaction, failing verification on mismatch, consistent with the TODO already present in the source.

### Proof of Concept
Not applicable as a runtime exploit — this is a tooling/verification-logic gap rather than a directly triggerable state corruption. The "proof" is the code itself: `ensure_match_transaction_info` at [1](#0-0)  never reads `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`, while `TransactionInfo` and its `TransactionInfoV1` variant do carry these fields ( [6](#0-5) ), confirming the check is structurally incapable of catching a checkpoint-hash divergence.

**Caveat:** I could not fully verify whether any other, higher-privilege consensus/commit code path (outside `db-tool`/chunk-executor `verify_execution`) also relies on this exact comparator for committing state without checkpoint-hash validation elsewhere; the normal block-commit path (`DoStateCheckpoint`) appears to independently compute and persist the checkpoint hash, so I limited the impact claim to the replay-verify/`db-tool` tooling paths I directly confirmed use this function.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
