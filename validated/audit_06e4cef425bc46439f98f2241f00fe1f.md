### Title
DeleteAccount action does not verify beneficiary existence before irreversibly deleting the account, permanently burning the account's balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` lets an account owner (or a contract acting via a promise batch) delete their own account and route the remaining balance to an arbitrary `beneficiary_id`. Validation of this action only checks the syntactic validity of `beneficiary_id`, never its existence. Execution unconditionally removes the account and pushes a system refund receipt to `beneficiary_id`. This is directly analogous to the reported `TransferHelper.safeTransfer` bug: a low-level "transfer" is issued to a target without confirming the target exists, and because refund receipts (`predecessor_id == "system"`) are barred from implicitly creating any account, a transfer to a non-existent `beneficiary_id` is guaranteed to fail and, per the protocol's refund semantics, the funds are burnt rather than returned to the deleting account.

### Finding Description
`validate_delete_action` in `runtime/runtime/src/action_validation.rs` only runs `validate_action_account_id(&action.beneficiary_id)`, a format check, with no existence check. `action_delete_account` in `runtime/runtime/src/actions.rs` computes `account_balance = account_ref.amount()` and unconditionally pushes `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` before irrevocably removing the account (`remove_account`). Because `Receipt::new_balance_refund` sets `predecessor_id: "system"`, the follow-up `Transfer` action to `beneficiary_id` is evaluated by `check_account_existence`/`implicit_creation_allowed` with `is_refund = true`, which always returns `false` regardless of account type — refunds can never create an account. If `beneficiary_id` was never created, was already deleted, or is otherwise absent from state at execution time, this refund receipt fails with `ActionErrorKind::AccountDoesNotExist`. Per `docs/RuntimeSpec/Refunds.md`, "If the execution of a refund fails, the refund amount is burnt", meaning the deleted account's balance is permanently destroyed instead of being preserved anywhere.

### Impact Explanation
Any unprivileged transaction signer (or a contract issuing `promise_batch_action_delete_account` on itself) who deletes their own account with a beneficiary that does not exist causes their entire remaining NEAR balance to be permanently burnt, with no recovery path — no error surfaces synchronously to the user showing the loss occurred against a specific typo'd account, since the delete itself succeeds and only the asynchronous system refund receipt fails. This matches the "permanently frozen funds" impact class. It is a stronger, more reachable analog to the original bug than the ERC-20 case: no separate "malicious pairing" step or third-party contract self-destruct is needed — a single transaction from the affected account, or a benign mistake (e.g., a beneficiary account expiring/being deleted concurrently, or a typo caught only by format-level validation), suffices.

### Likelihood Explanation
Reachable via a plain `DeleteAccount` transaction/action from any account holder, or via `promise_batch_action_delete_account` from a contract. The severity is naturally bounded to the deleter's own balance (self-inflicted loss), similar to how the original report was downgraded to Medium because it required a specific external precondition (a self-destructible paired token). Here the precondition is simply "beneficiary_id does not exist at execution time," which is entirely plausible (typo, race with another deletion, or reuse of an already-deleted/never-created account id) and not otherwise guarded against beyond format validation.

### Recommendation
Add an existence check for `beneficiary_id` at validation or execution time (e.g., require that the account exist in state before generating the refund, or fall back to burning explicitly with a clear execution error rather than silently deleting the source account first). Alternatively, defer account removal until the beneficiary transfer succeeds, or reject the `DeleteAccount` action outright when the beneficiary is known not to exist, mirroring the C4 recommendation to "check the existence of the contract before every transaction."

### Proof of Concept
1. Account `alice.near` holds a balance and calls `DeleteAccount { beneficiary_id: "nonexistent.near" }` where `nonexistent.near` has never been created (or was previously deleted).
2. `validate_delete_action` accepts the action since `"nonexistent.near"` is a syntactically valid `AccountId` [1](#0-0) .
3. `action_delete_account` runs: it pushes `Receipt::new_balance_refund(&"nonexistent.near", account_balance)` and immediately calls `remove_account`, deleting `alice.near` from state [6](#0-5) .
4. The generated system refund receipt targets `nonexistent.near` with `is_refund = true`; `implicit_creation_allowed` returns `false` unconditionally for refunds [3](#0-2) , so `check_account_existence` rejects the `Transfer` action with `AccountDoesNotExist`.
5. Per the refund-failure rule ("If execution of a refund fails, the refund amount is burnt", `docs/RuntimeSpec/Refunds.md:12`), `alice.near`'s entire balance is burnt. Neither `alice.near` (now deleted) nor `nonexistent.near` (never created) ever receives the funds — a permanent, unrecoverable loss triggered by a single ordinary transaction.
