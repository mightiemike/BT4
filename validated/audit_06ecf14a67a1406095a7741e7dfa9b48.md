This bug class (a deferred/queued event dereferencing a resource that can be invalidated by intervening state changes) has a direct, already-patched analog in nearcore's `GlobalContractDistribution` receipt handling, and the fix confirms the vulnerability was real and reachable from a single user's transactions.

### Title
NULL-pointer-equivalent panic on stale `GlobalContractDistribution` receipts during resharding — (already fixed; historical analog) - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`receipt_filter_fn` in `DelayedReceiptQueueWrapper` (used to filter delayed receipts by current shard after a resharding event) previously called `receiver_shard_id()` and immediately `.unwrap()`'d the result: [1](#0-0) 
Just like `udc_event_xfer_out_done()` dereferencing `buf` from `udc_buf_get()` without checking for `NULL`, this code dereferenced (`.unwrap()`'d) the result of `receiver_shard_id()` without accounting for the case where the referenced state (the receipt's `target_shard`) had been invalidated by an asynchronous, host/protocol-driven event — here, a resharding split that occurred *between* when the receipt was created and when it was popped off the delayed queue.

### Finding Description
A user submits a `DeployGlobalContract` action, which creates a `ReceiptEnum::GlobalContractDistribution` receipt carrying a `target_shard` field pinned to the shard layout at receipt-creation time (`core/primitives/src/receipt.rs:447-463`, `Receipt::receiver_shard_id`). If that receipt becomes delayed (queued because the target shard was over its compute budget) and two resharding events occur before it is drained, its `target_shard` no longer maps to any shard in the current or even the split-history layout. `receiver_shard_id()` returns `Err(EpochError::ShardingError(...))` in that case: [2](#0-1) 
`DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn` on every popped delayed receipt to decide whether it belongs to the current shard after ReshardingV3: [3](#0-2) 
Before the fix, `receipt_filter_fn` unwrapped that `Result`, so encountering a stale receipt whose `target_shard` had no descendant in the current layout caused an unconditional panic during `apply()`, i.e., a **transaction-triggered chunk-application panic**, deterministically reproducible on every honest validator processing that chunk. This is the direct analog to the Zephyr USB bug class: a value queued for later, asynchronous processing (delayed receipt) is dereferenced without validating that the referenced resource is still consistent with the current state (current shard layout), because the invalidating event (resharding) happens on a different timeline than the original enqueue.

A dedicated regression test in the repository, `test_stale_global_contract_distribution_after_double_resharding`, exercises exactly this path (deploy global contract → saturate the shard so the receipt is delayed → force two sequential resharding splits → drain the queue) and asserts the chain does **not** stall/panic: [4](#0-3) 
The current implementation of `receiver_shard_id` also adds a `resolve_to_current_shard` fallback for exactly this scenario: [5](#0-4) 

### Impact Explanation
If this were still unhandled, it would be a chunk-application panic reachable by any account able to submit a `DeployGlobalContract` transaction combined with enough load to delay the resulting distribution receipt across two resharding boundaries — a transaction-triggered halt of chunk production for the affected shard on every honest validator (deterministic crash, matching "transaction-triggered halt" in the validation criteria). This is Medium/High severity by the same reasoning as the Zephyr CVE: an unprivileged caller (any transaction signer/contract deployer) can, through ordinary usage plus timing tied to a protocol-level resharding event, force validators into an unhandled `Result::unwrap()` panic path.

### Likelihood Explanation
This is a **historical/already-mitigated** issue in the current snapshot of this repository — `receipt_filter_fn` still calls `.unwrap()` on `receiver_shard_id()`, but `receiver_shard_id()` itself was hardened to resolve stale `target_shard` values via `resolve_to_current_shard` before returning `Err` only when truly unrecoverable, and a regression test explicitly guards against the previously-panicking scenario. I could not find current tool access to a git blame/history to confirm exactly which commit introduced `resolve_to_current_shard`, so I can't state with certainty whether any residual unwrap-panic path remains for shard histories deeper than what `resolve_to_current_shard` can resolve (e.g., more than two resharding generations, or shard layouts without full split-history retention, as hinted by the test's comment "the fix only works with V3 shard layouts (dynamic resharding)... static resharding doesn't maintain a full split history").

### Recommendation
- Confirm `ShardLayout::resolve_to_current_shard` correctly resolves `target_shard` across an arbitrary number of resharding generations, not just two, since delayed `GlobalContractDistribution` receipts can in principle sit in the queue across many epochs.
- Replace the remaining `.unwrap()` calls in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`, both the `shard_layout` and `receiver_shard_id` unwraps) with proper `Result` propagation (`?` returning `RuntimeError`/`StorageError::StorageInconsistentState`) so that any future edge case in shard-layout resolution degrades to a handled error rather than an unconditional panic, consistent with how other "inconsistent state" conditions are handled elsewhere in `runtime/runtime/src/lib.rs` (e.g. `StorageError::StorageInconsistentState` on missing postponed/promise-yield state).
- Extend `test_stale_global_contract_distribution_after_double_resharding` (or add a new test) covering three-or-more sequential reshardings and static (non-dynamic, V1/V2) shard layouts to verify no code path still relies on an unchecked `unwrap()`.

### Proof of Concept
The existing test in the repository is itself the proof of concept for the underlying bug class and its fix:
1. Deploy a contract on `user0`'s shard, then submit a `DeployGlobalContract` transaction from `user0`, creating a `GlobalContractDistribution` receipt with `target_shard` = `user0`'s shard.
2. Saturate `user0`'s shard's compute budget every block via `burn_gas_raw` calls so the distribution receipt is pushed into the delayed queue and stays there.
3. Configure `DynamicReshardingConfig` to force two sequential shard splits, both of which occur while the receipt is delayed, such that `target_shard` no longer maps directly onto any shard in the current layout.
4. Stop saturating and let the delayed queue drain; assert the chain height keeps advancing past the point where the stale receipt would be popped and filtered (`test-loop-tests/src/tests/global_contracts_distribution.rs:163-185`) — if the old unwrap-based `receipt_filter_fn`/`receiver_shard_id` behavior were reinstated (or if `resolve_to_current_shard` failed to resolve the shard), this assertion would fail because the chain would stall on a panic in `Runtime::apply`.     fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
