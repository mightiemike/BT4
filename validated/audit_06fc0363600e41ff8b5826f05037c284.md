### Title
GasKeyNonce Write Rolled Back on Subsequent Action Failure Enables DelegateActionV2 Replay — (`runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
When a receipt contains a `DelegateV2` action followed by any action that fails, the gas key nonce advancement written by `validate_delegate_action_key` is silently reverted by `state_update.rollback()`. The same signed `DelegateActionV2` can then be re-submitted and accepted, violating the invariant that a consumed nonce cannot be reused.

### Finding Description

`apply_action_receipt` commits a `ActionReceiptProcessingStarted` checkpoint before executing any actions, then runs all actions in a loop with no intermediate commits. On any failure it calls `state_update.rollback()`, which discards every state write since that checkpoint. [1](#0-0) 

The gas key nonce is written inside the action loop: [2](#0-1) 

The rollback that follows a receipt-level failure reverts it: [3](#0-2) 

`validate_actions_with_mode` only rejects **two** `Delegate`/`DelegateV2` actions in the same list; it does not prevent combining one `DelegateV2` with other actions: [4](#0-3) 

The test at lines 1085–1096 explicitly confirms `[CreateAccount, Delegate]` is valid: [5](#0-4) 

### Impact Explanation

A relayer (unprivileged) who holds a valid `SignedDelegateActionV2` from a sender can:

1. Submit a transaction with actions `[DelegateV2(signed_by_sender), FailingAction]` where `FailingAction` is any deterministically-failing action (e.g., `AddKey` for a key that already exists, or `Stake` below the minimum).
2. The receipt executes: `DelegateV2` succeeds and `set_gas_key_nonce` writes the advanced nonce; `FailingAction` fails; `rollback()` reverts the nonce write.
3. The relayer re-submits the identical `DelegateV2` in a new transaction. The nonce check passes because the stored nonce was rolled back.
4. The sender's inner actions (e.g., `Transfer`) execute again without the sender's knowledge or consent.

This enables unauthorized repeated execution of the sender's signed actions, leading to balance manipulation and unauthorized transactions.

### Likelihood Explanation

The relayer already possesses the signed `DelegateActionV2` — that is the normal meta-transaction flow. No additional key compromise or privileged access is required. The only cost to the attacker is gas for the outer transaction on each replay. The attack is repeatable until the sender's account is drained or the signed action expires (`max_block_height`).

### Recommendation

The gas key nonce (and the regular access key nonce for `DelegateNonceUpdate::AccessKey`) must be advanced **before** the `ActionReceiptProcessingStarted` commit, or committed in a separate sub-commit that is not rolled back on subsequent action failure. One approach: commit the nonce write immediately after `validate_delegate_action_key` succeeds, using a dedicated `StateChangeCause`, so it survives the receipt-level rollback. Alternatively, enforce that a `Delegate`/`DelegateV2` action must be the **sole** action in a receipt (not merely the only delegate action), eliminating the multi-action rollback scenario entirely.
