## Analog Found

### Title
Timing-dependent `create_account_charge` fee bypass when a receipt's gas was purchased before an `AccountCostIncrease` price surplus existed - (File: `runtime/runtime/src/lib.rs`)

### Summary
The Symmetrical report describes a liquidation-fee deduction that is silently reduced (down to zero) whenever the "pot" it is drawn from (`availableBalance`) is smaller than the fee itself, so a *faster* liquidation (bigger pot, bigger deduction) refunds partyA less than a *slower* one (smaller/negative pot, zero deduction). The nearcore analog is the `account_creation_charge` deduction in `Runtime::refund_unspent_gas_and_deposits`, which is capped by `min(amount_to_charge, burned_gas_refund)` where `burned_gas_refund` is itself a timing-dependent quantity (the gas-price surplus between the block that purchased the gas and the block that burns it).

### Finding Description
When a new account is created under `AccountCostIncrease`, the runtime tries to collect `account_creation_charge` (mainnet ~0.007 N) out of the gas-price surplus refund: [1](#0-0) 

`burned_gas_refund` is `gas_refund_result.price_surplus`, i.e. the difference between the price at which the gas was purchased (`gas_purchase_price`, fixed at the time the receipt/transaction was converted) and `gas_burn_price` (`min(gas_purchase_price, apply_state.gas_price)` at execution time): [2](#0-1) 

The amount actually charged is `min(amount_to_charge, burned_gas_refund)` — exactly the same "clamp fee to whatever is left in the pot" pattern as the Symmetrical `remainingLf` calculation. If the receipt's gas was purchased before the `AccountCostIncrease` protocol upgrade (at the old, lower price) but executes after the upgrade activates, there is no price surplus available (`burned_gas_refund` is `0` or small), so `amount_actually_charged` is reduced or zero, and the account is still created — the fee is bypassed rather than deducted: [3](#0-2) 

This exact behavior — and its dependence on the relative timing of transaction conversion vs. receipt execution across the upgrade boundary — is demonstrated by the test itself: [4](#0-3) [5](#0-4) 

Just as in the Symmetrical bug, the deduction is not sourced from a fixed, protocol-guaranteed value; it is sourced from an incidental byproduct (`price_surplus`) whose magnitude depends on relative timing (here: gas price movement across a version upgrade, and cross-shard scheduling delay) rather than on the actual cost the network is trying to recover.

### Impact Explanation
An account-creating receipt whose gas was purchased at a lower, pre-upgrade price and executes post-upgrade (a cross-shard receipt delayed by one or more blocks across the upgrade boundary) has its `account_creation_charge` reduced or entirely bypassed (`cost < account_creation_charge`, per the test assertion), while the account is nonetheless created. This is a fee bypass: the actor obtains the resource (a new, storage-backed account) without paying the fee the protocol was designed to collect for it. The magnitude is bounded to `account_creation_charge` (~0.007 N) per account and only during the narrow window while a chunk's receipts straddle a protocol-version upgrade — but it is deterministically reachable by any transaction signer who creates accounts via a cross-shard `CreateAccount`/implicit-creation receipt timed around a known upgrade.

### Likelihood Explanation
Protocol upgrades on NEAR happen at every epoch boundary once enough stake votes for the new version, and upgrade schedules/epoch boundaries are publicly observable. A user (or bot) can deliberately submit cross-shard account-creation transactions in the last blocks before an upgrade so that the transaction is converted pre-upgrade (locking in the old, lower gas price) while the resulting receipt executes on the receiving shard post-upgrade. This requires no validator or node misbehavior — only ordinary transaction submission timed around a known, public event — making it fully reachable from an unprivileged signer.

### Recommendation
Do not derive the `account_creation_charge` from the incidental `price_surplus`. Instead, charge it directly against the account's balance (or as a fixed additional burn independent of gas-price surplus) so its collection does not depend on whether the receipt happens to straddle a price/version boundary. At minimum, when `burned_gas_refund < amount_to_charge`, recover the shortfall from another guaranteed source (e.g., the account's own balance via `LackBalanceForState`-style enforcement) rather than silently accepting a reduced or zero charge.

### Proof of Concept
1. Shortly before a scheduled protocol-version upgrade that activates `AccountCostIncrease`, submit a `CreateAccount` (or implicit-creation `Transfer`) transaction whose receiver is on a different shard than the signer, so the transaction converts to a receipt in the current (pre-upgrade) block at the old, lower `gas_purchase_price`.
2. Ensure (via normal cross-shard scheduling delay) that the receipt executes one or more blocks later, after the shard's epoch has adopted the upgraded protocol version with `AccountCostIncrease` enabled.
3. At execution time, `gas_burn_price = min(gas_purchase_price_old, apply_state.gas_price_new)` yields little or no `price_surplus`/`burned_gas_refund`.
4. `refund_unspent_gas_and_deposits` computes `amount_actually_charged = min(amount_to_charge, burned_gas_refund)`, which is less than the full `account_creation_charge` (potentially `0`).
5. The account is created successfully with `total_tokens_burnt(outcome) < account_creation_charge`, exactly as asserted by the existing test `test_create_account_cost_protocol_upgrade`'s `(false, true)` "crossing" case. [6](#0-5)

        if created_account && ProtocolFeature::AccountCostIncrease.enabled(protocol_version) {
            // This is how much creating an account should cost
            let desired_cost = config.account_creation_charge;

            let create_account_gas_cost =
                config.fees.fee(ActionCosts::create_account).exec_fee().gas;
            // The cost of the gas that was burned already
            let burned_cost = safe_gas_to_balance(gas_burn_price, create_account_gas_cost)?;

            // We would like to charge as much as needed to reach desired_cost
            let amount_to_charge = desired_cost.saturating_sub(burned_cost);

            // We can't charge more than `burned_gas_refund`.
            // `burned_gas_refund < amount_to_charge` could happen for receipts where the gas was
            // purchased in protocol versions before `ProtocolFeature::AccountCostIncrease`, at a lower
            // gas price that isn't enough to cover the cost of creating an account.
            let amount_actually_charged = std::cmp::min(amount_to_charge, burned_gas_refund);

            // sanity check: purchasing gas at `min_gas_purchase_price` should be enough to cover
            // the cost of creating an account.
            debug_assert!(
                safe_gas_to_balance(config.min_gas_purchase_price, create_account_gas_cost)
                    .unwrap()
                    >= desired_cost
            );

            // sanity check: as long as the purchase price is high enough, there should always be
            // enough refund balance to cover the cost of creating an account.
            if gas_purchase_price >= config.min_gas_purchase_price {
                debug_assert!(burned_gas_refund >= amount_to_charge);
