Based on my investigation, I found a structural analog to the reported bug class in `UnDelegateResourceActuator`.

### Title
Resource accounting discrepancy in `UnDelegateResourceActuator` allows owner to recover more frozen balance than the receiver actually still holds - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
The reported bug describes a pattern where a system caps the *actual* transferred/settled amount to what is available, but still credits the *full requested* amount into an accounting field used for future balance calculations — creating a phantom surplus. In `UnDelegateResourceActuator.execute()`, the same discrepancy pattern exists between the receiver-side deduction (which is capped/zeroed when insufficient) and the owner-side credit (which is always increased by the full requested `unDelegateBalance`, unconditionally).

### Finding Description
When `UnDelegateResourceActuator.execute()` runs, the receiver side is only decremented if it actually has enough delegated balance; if the receiver's `AcquiredDelegatedFrozenV2Balance` for the resource is less than `unDelegateBalance`, the code simply zeroes it out instead of subtracting the requested amount: [1](#0-0) 

However, regardless of what happened on the receiver side, the owner side is unconditionally credited the full `unDelegateBalance`: [2](#0-1) 

This mirrors the reported bug's root cause exactly: on one side of an accounting relationship, the actual value moved is capped by what is genuinely available (`availableCollateralInDiamond` in the report; `AcquiredDelegatedFrozenV2Balance` here), while on the other side the full requested/nominal amount is recorded unconditionally (`realizedTradingFeesCollateral` in the report; `FrozenBalanceForBandwidthV2`/`FrozenBalanceForEnergyV2` here). The validation only checks the `DelegatedResourceCapsule` ledger entry (`delegatedResourceCapsule.getFrozenBalanceForBandwidth()` / `getFrozenBalanceForEnergy()`), not whether the receiver account's actual `AcquiredDelegatedFrozenV2Balance` still matches: [3](#0-2) 

The code comments themselves acknowledge this divergence can occur ("A TVM contract suicide, re-create will produce this situation" / "A TVM contract receiver, re-create will produce this situation"), confirming this is a known, reachable edge case rather than a theoretical one — a receiver contract can `suicide()` (clearing its account state, including `AcquiredDelegatedFrozenV2Balance`), then be re-created at the same address, after which the original delegator un-delegates.

### Impact Explanation
The owner's `FrozenBalanceForBandwidthV2`/`FrozenBalanceForEnergyV2` (which backs freezable TRX and can subsequently be unfrozen back to spendable TRX via `UnfreezeBalanceV2`) is increased by the full `unDelegateBalance` even though the receiver never actually returned that much delegated capacity. This inflates the owner's frozen resource balance beyond what is actually backed by real frozen TRX in the system, which can eventually be unfrozen and withdrawn as TRX — an accounting/settlement divergence that allows extraction of value not backed by real collateral, analogous to the vault loss in the original report.

### Likelihood Explanation
Medium: it requires a receiver contract to `suicide()` (clearing its account/resource state) and be re-created at the same address (a well-known and previously-handled TVM edge case in this same codebase, as the inline comments show), followed by the original delegator calling `UnDelegateResource`. This is achievable by an unprivileged user controlling both the delegator and a suicidable/re-creatable contract receiver, with no special permissions required.

### Recommendation
Before crediting the owner's full `unDelegateBalance` back into `FrozenBalanceForBandwidthV2`/`FrozenBalanceForEnergyV2`, verify that the receiver's actual `AcquiredDelegatedFrozenV2Balance` was sufficient to cover the request; if it was insufficient/zeroed, only credit back the amount that was actually recovered from the receiver (mirroring the receiver-side capping), or otherwise reconcile the discrepancy so the total delegated/frozen accounting remains balanced.

### Proof of Concept
Conceptual PoC path (not executed, derived from code paths reviewed):
1. Account A delegates BANDWIDTH/ENERGY balance `X` to contract address C via `DelegateResourceContract`, creating a `DelegatedResourceCapsule` entry and increasing C's `AcquiredDelegatedFrozenV2BalanceForBandwidth/Energy` by `X`.
2. Contract C `suicide()`s (or is otherwise cleared), zeroing its account state including `AcquiredDelegatedFrozenV2Balance...`.
3. C is re-created at the same address (e.g., via `CREATE2` or normal re-deployment flow supported in TVM).
4. Account A calls `UnDelegateResourceContract` for balance `X` targeting C. Validation only checks `DelegatedResourceCapsule.getFrozenBalanceForBandwidth/Energy()` (still `X`), which passes.
5. In `execute()`, since `receiverCapsule.getAcquiredDelegatedFrozenV2Balance...() < unDelegateBalance` (it is 0 after suicide/recreate), the receiver-side branch only zeroes the receiver's balance (no actual `X` recovered from C) — yet the owner-side unconditionally executes `ownerCapsule.addFrozenBalanceForBandwidthV2(unDelegateBalance)` / `addFrozenBalanceForEnergyV2(unDelegateBalance)`, crediting A with the full `X` regardless.
