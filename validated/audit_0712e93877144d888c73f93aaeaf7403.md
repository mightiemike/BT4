### Title
Storage can be bloated with dust `DelegatedResource` entries via delegate/undelegate-to-dust - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`, `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
`DelegateResource`/`UnDelegateResource` enforce a minimum of `1 TRX` (`TRX_PRECISION` sun) to *create* a `DelegatedResource` storage entry, but enforce no minimum on the balance left behind after an `UnDelegateResource`. An attacker can delegate the minimum 1 TRX to any existing account, then immediately undelegate all but 1 sun, leaving a permanent dust entry in `DelegatedResourceStore` at a cost of 1/1,000,000th of the intended minimum, and repeat this against every account on the chain.

### Finding Description
`DelegateResourceActuator.validate()` and `DelegateResourceProcessor.validate()` enforce a minimum delegate amount of `TRX_PRECISION` (1 TRX = 1,000,000 sun): [1](#0-0) 

This creates a new `DelegatedResourceCapsule` keyed by `(owner, receiver)` and persists it in `DelegatedResourceStore`: [2](#0-1) 

The receiver only needs to be any existing, non-contract account — it does not need to belong to or cooperate with the attacker: [3](#0-2) 

When undelegating, `UnDelegateResourceActuator.validate()` only checks that `unDelegateBalance > 0` and does not exceed the available delegated balance — there is no floor requiring the remaining amount to stay above `TRX_PRECISION` or drop to exactly zero: [4](#0-3) 

The storage entry is only deleted when the remaining balance is exactly zero for both bandwidth and energy: [5](#0-4) 

The same pattern exists in the TVM-callable native contract path (`UnDelegateResourceProcessor`), reachable from a smart contract via the `UnDelegateResource` precompile: [6](#0-5) 

An attacker can:
1. Call `DelegateResource` with `balance = 1,000,000` sun (the minimum) targeting an arbitrary existing account as receiver.
2. Immediately call `UnDelegateResource` with `unDelegateBalance = 999,999`, leaving `1` sun of `frozenBalanceForBandwidth`/`frozenBalanceForEnergy` in the `DelegatedResourceCapsule`.
3. Since the remaining balance is non-zero, the entry is never removed and permanently occupies a slot in `DelegatedResourceStore`.
4. Repeat against every other account on chain to create one dust entry per `(owner, receiver)` pair, since the key is `createDbKeyV2(ownerAddress, receiverAddress, lock)`.

### Impact Explanation
This allows an attacker to bloat `DelegatedResourceStore` at 1/1,000,000th (0.0001%) of the intended cost per entry (analogous to the referenced Omnipool `MinimumPoolLiquidity` bypass). Because the receiver need not cooperate, the attacker can target every active account in the network with a single controlled owner account, producing unbounded persistent storage growth for negligible TRX cost (only bandwidth/energy fee plus 1 sun locked per entry), degrading full-node storage/database performance over time — a resource-exhaustion/DoS vector on the chain state.

### Likelihood Explanation
Likelihood is high: the actions (`DelegateResource`, `UnDelegateResource`) are ordinary, unprivileged, broadcastable transactions requiring no special permission beyond having 1 TRX and bandwidth/energy for fees; the receiver can be any pre-existing account. No collusion or privileged role is required.

### Recommendation
Enforce that after an `UnDelegateResource` (via both `UnDelegateResourceActuator` and `UnDelegateResourceProcessor`), the remaining `frozenBalanceForBandwidth`/`frozenBalanceForEnergy` for that key must either be `0` or `>= TRX_PRECISION` (mirroring the creation minimum), rejecting undelegations that would leave dust. Alternatively, when the remaining amount is below the minimum threshold, force it to zero (fully unlock) and delete the `DelegatedResourceCapsule` entry instead of persisting a sub-threshold balance.

### Proof of Concept
1. Account A (owner) has ≥1 TRX frozen for bandwidth/energy V2 (`FreezeBalanceV2`).
2. A broadcasts `DelegateResourceContract{owner=A, receiver=B, resource=BANDWIDTH, balance=1_000_000}` where B is any existing normal account — passes `validate()` per `DelegateResourceActuator.java:147-150` and creates a `DelegatedResourceCapsule` in `DelegatedResourceStore`.
3. A broadcasts `UnDelegateResourceContract{owner=A, receiver=B, resource=BANDWIDTH, balance=999_999}` — passes `validate()` since `999_999 <= 1_000_000` and no floor check exists (`UnDelegateResourceActuator.java:265-303`); execution leaves `frozenBalanceForBandwidth = 1`, which is `!= 0`, so the entry at `170-176` is retained via `delegatedResourceStore.put(unlockKey, unlockResource)` instead of being deleted.
4. Repeat step 2-3 with a new receiver `B'` for the same owner `A` (or new owners) to create arbitrarily many permanent 1-sun dust entries in `DelegatedResourceStore`.
