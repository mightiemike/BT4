Based on my investigation, I found a concrete, locally-provable state-integrity gap in the transaction-output verification path used by the replay-verification tooling.

### Title
Replay-verify's `ensure_match_transaction_info` never validates the state checkpoint hash, letting a diverged state root pass verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness oracle used by `replay_on_archive`'s `Verifier::execute_and_verify` to confirm that re-execution of historical transactions reproduces the authenticated ledger. It compares status, gas used, write-set hash, and event root hash against the trusted `TransactionInfo`, but explicitly and knowingly skips comparing the `state_checkpoint_hash` (and hot-state/position-state checkpoint hashes). As a result, a re-execution whose resulting state tree root diverges from the one committed and signed by validators will be reported by the tool as a successful, verified replay.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  checks status, gas, write-set hash, and event-root hash, but the function's own trailing comment states the gap plainly:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is invoked as the only per-transaction check in `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, right after re-executing a chunk of historical transactions with `AptosVMBlockExecutor`:

```rust
if let Err(err) = executed_outputs[idx].ensure_match_transaction_info(
    version,
    &expected_txn_infos[idx],
    Some(&expected_writesets[idx]),
    Some(&expected_events[idx]),
) {
``` [3](#0-2) 

Because `state_checkpoint_hash()` (i.e., `txn_info.state_change_hash()`'s sibling field carrying the JMT/state-tree root at that version) is never compared, if the re-executed transaction's resulting state tree root differs from what was actually committed and signed in the `LedgerInfo` — e.g., due to a non-determinism bug, a storage-schema/restore-path defect, or any divergence in how state is folded into the Merkle tree — the tool will still report the transaction as correctly replayed, since write-set hash, event hash, gas, and status alone do not encode the state tree root.

### Impact Explanation
`replay_on_archive` (and other callers of `ensure_match_transaction_info`, e.g. `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`) is the authenticated re-verification path operators and node runners use to confirm that archived/committed ledger state matches deterministic VM re-execution. Silently accepting a divergent state root as "verified" means proof-integrity/state-commitment corruption (whatever the root cause) becomes undetectable by the very tool designed to catch it. This falls squarely into the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong accumulator root ... accepted as valid" impact categories: a corrupted or forked state root is authenticated as correct by the verification tool.

### Likelihood Explanation
The gap is deterministic and always present (not conditional on a race or attacker input) whenever replay-verify is run: the comparator structurally omits state_checkpoint_hash regardless of feature flags. Its trigger condition is that some other independent defect causes a state-root divergence; this comparator's role is exactly to detect that class of bug, so its absence directly negates the safety net for the state-commitment invariant, and the code comment itself confirms the authors are aware the check is missing before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality between the recomputed state checkpoint hash (and, once available, hot-state/position-state checkpoint hashes) of the transaction output and `txn_info.state_checkpoint_hash()` before treating a replay as validated, rather than deferring this to a future flag-gated change.

### Proof of Concept
Not applicable as a runtime exploit PoC — the defect is a verification-tool logic gap, demonstrated directly by the code: `ensure_match_transaction_info` at [4](#0-3)  never calls `txn_info.state_checkpoint_hash()` for comparison, and `replay_on_archive.rs`'s `execute_and_verify` at [5](#0-4)  relies exclusively on that function's `Ok(())`/`Err` result to decide pass/fail for each replayed transaction, so any run where write-set/event/gas/status match but the state tree root diverges is reported as a clean pass.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
