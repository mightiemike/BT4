### Title
Legacy per-cycle vote reward calculation truncates to zero for small voters relative to total witness votes, causing silent loss of voter rewards - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` calculates each voter's share of a super-representative's cycle reward as `voteRate = userVote / totalVote` (a `double`) and accumulates `reward += voteRate * totalReward` into a `long` accumulator [1](#0-0) . Because `reward` is declared as `long`, the compound assignment `reward += voteRate * totalReward` performs an implicit narrowing (truncating) conversion back to `long` on every loop iteration. If a single voter's proportional share (`voteRate * totalReward`) is less than `1.0` — which happens whenever `userVote` is small relative to `totalVote` (an SR with a very large number of small-stake voters, analogous to the "large number of steps" scenario in the reported vesting bug) — the entire contribution for that voter/cycle is truncated to `0` and permanently lost, rather than being accumulated with fractional precision or rounded fairly.

### Finding Description
This mirrors the reported StepVesting issue conceptually: instead of `releaseRate = totalAmount / numSteps` rounding down to `0` when `numSteps` is large relative to `totalAmount`, here `voteRate * totalReward` rounds down to `0` when `totalVote` (analogous to `numSteps`) is large relative to a given voter's `userVote` share of `totalReward` (analogous to the vested amount). This code path is the "old reward algorithm", used for cycles prior to `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()` [3](#0-2) , and is also used unconditionally by `getOldReward` whenever `allowOldRewardOpt()` is disabled, looping cycle by cycle and calling `computeReward(cycle, votes)` directly [4](#0-3) . `computeReward` is reachable from `withdrawReward(byte[] address)` and `queryReward(byte[] address)`, both of which are invoked from `VoteWitnessActuator.countVoteAccount` (via `mortgageService.withdrawReward(ownerAddress)`) [5](#0-4)  and from the public `GetReward` HTTP/gRPC API, both of which are reachable by any anonymous account via a broadcast `VoteWitnessContract` transaction or a `GetReward` query.

### Impact Explanation
Unlike the newer VI-based algorithm which uses `BigInteger` arithmetic with an explicit `DECIMAL_OF_VI_REWARD` scaling factor precisely to avoid this rounding-to-zero problem [6](#0-5) , the legacy `computeReward(long cycle, ...)` path has no such protection. A voter whose vote count is small relative to the total vote for a witness (which is common for many small holders voting for a popular SR) can have their entire per-cycle reward silently rounded to zero and permanently lost — no accounting error is raised, and the difference is simply absorbed (the sum of individually truncated shares never equals `totalReward`, so the "lost" reward is effectively retained by the protocol/witness rather than paid out). This directly causes small-stake voters to lose real TRX reward income across all cycles the legacy algorithm covers, matching the "loss of beneficiary funds" impact class from the reference report.

### Likelihood Explanation
Likelihood is limited by the fact that this only affects cycles before `newRewardAlgorithmEffectiveCycle` (a historical/legacy window) or nodes/configurations where `allowOldRewardOpt()` is not enabled, and it also requires the specific ratio condition (`userVote/totalVote * totalReward < 1`), i.e., a witness with a very large number of tiny voters and a modest per-cycle reward pool. It is a naturally occurring condition rather than one requiring special exploitation, so it can occur silently as a byproduct of ordinary DPoS voting activity for widely-voted SRs during the affected historical cycles.

### Recommendation
Replace the double-based `voteRate * totalReward` computation with exact integer arithmetic (e.g., `BigInteger` multiply-then-divide: `userVote * totalReward / totalVote`), consistent with the approach already used for the new VI-based reward algorithm, to avoid systematic truncation-to-zero for small voters, or track and redistribute rounding remainders.

### Proof of Concept
Given `totalVote = 1_000_000_000`, `totalReward = 500_000` (a plausible per-cycle SR reward pool), and a small voter with `userVote = 500`:
```
voteRate = 500.0 / 1_000_000_000 = 5.0E-7
voteRate * totalReward = 5.0E-7 * 500_000 = 0.25
reward += 0.25  // implicit (long) truncation -> reward stays 0
```
The voter's reward for that cycle truncates to `0` and is never recovered, even though the voter genuinely contributed votes and is entitled to a proportional share, reproducing the same rounding-to-zero fund-loss pattern described in the reference report but in `computeReward(long cycle, List<Pair<byte[], Long>> votes)` at [1](#0-0) .

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
