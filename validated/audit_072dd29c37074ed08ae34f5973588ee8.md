### Title
Wallet Contract's `ADDRESS_REGISTRAR_ACCOUNT_ID` is hardcoded to a single mainnet-only account and is never re-templated for testnet/localnet builds, causing address-check cross-contract calls to always fail off mainnet - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/ADDRESS_REGISTRAR_ACCOUNT_ID])

### Summary
The near-wallet-contract build process templates the EVM `CHAIN_ID` per target network (mainnet/testnet/localnet) but does **not** do the same for the address registrar account ID that the contract calls out to during transaction execution. The registrar account is baked into every network's WASM binary as the single literal string `address-map.near`.

### Finding Description
`build.rs` builds three variants of the wallet contract WASM (mainnet, testnet, localnet) and, for each, rewrites the `CHAIN_ID` source file to the network-appropriate EVM chain id before invoking the docker build, then restores it: [1](#0-0) [2](#0-1) 

However, `build.rs` never touches or re-templates the `ADDRESS_REGISTRAR_ACCOUNT_ID` source file for any of the three builds - only `CHAIN_ID` is swapped. The registrar file contains a single hardcoded value for all networks: [3](#0-2) 

This constant is compiled directly into the contract and parsed into an `AccountId` at runtime, then used to construct a cross-contract call to the registrar's `lookup` method: [4](#0-3) [5](#0-4) 

The comment on `address_check_callback` confirms this call is a required protocol step (checking whether an eth-implicit target address actually corresponds to an existing named account, to ensure relayers can't bypass named-account routing): [6](#0-5) 

Because Near account namespaces are strictly per-network (mainnet accounts and testnet accounts are entirely separate state trees, and testnet convention typically uses `.testnet`-suffixed or otherwise distinct top-level accounts), an account literally named `address-map.near` deployed on mainnet has no corresponding, correctly-configured counterpart guaranteed to exist under the same account ID on testnet or localnet. Since the testnet and localnet WASM builds embed the exact same `address-map.near` string as the mainnet build, any `rlp_execute` call on a testnet- or localnet-deployed wallet contract that triggers the `EOABaseTokenTransfer` path with `address_check: Some(address)` will issue a cross-contract call to `address-map.near` on that network. If that account does not exist (or exists but is not the intended registrar contract) on testnet/localnet, the call returns `PromiseResult::Failed`, and `address_check_callback` unconditionally reports failure: [7](#0-6) 

This mirrors the reported bug class exactly: a single hardcoded external address/account baked in regardless of the deployment network, causing calls from the contract to revert/fail with an empty or missing return value once used on any network other than the one the hardcoded value was actually valid for.

### Impact Explanation
Any relayer-submitted or self-submitted Ethereum-style transaction (`rlp_execute`) that performs a base-token transfer requiring an address check (i.e., transferring to a target that must be verified against the address registrar) will systematically fail on any deployment where `address-map.near` is not the correct/live registrar account for that network - which is the case for testnet and localnet by construction, since the build never customizes this value per network. Because `inner_rlp_execute`'s nonce-increment logic explicitly defers incrementing the nonce for this exact code path pending the registrar lookup result, a failed registrar call combined with relayer-behavior heuristics can also lead to relayer banning (`create_ban_relayer_promise`) even when the relayer behaved correctly - it's the hardcoded account, not the relayer, that is at fault. This is a transaction-triggered, protocol-level denial of a category of user transactions (self-transfers/base-token transfers with named-account targets) on all non-mainnet Near networks, and can also cause honest relayers to be wrongly banned, which is a state change with real economic effect (loss of relayer access key/reputation) triggered purely by a single submitted transaction.

### Likelihood Explanation
High likelihood: this is not a byzantine/malicious-actor-dependent condition - it triggers deterministically any time an eth-implicit account holder submits (or a relayer submits on their behalf) a qualifying `EOABaseTokenTransfer` with `address_check: Some(...)` on the testnet or localnet wallet-contract build, which is the normal, expected usage path for this feature.

### Recommendation
Template `ADDRESS_REGISTRAR_ACCOUNT_ID` per network the same way `CHAIN_ID` is templated in `build.rs` (i.e., write the correct registrar account for `wallet_contract_mainnet`, `wallet_contract_testnet`, and `wallet_contract_localnet` before each docker build and restore afterward), or otherwise ensure the registrar identifier is chain-aware rather than a single global compile-time constant.

### Proof of Concept
1. Build the wallet contract for testnet via `build.rs` (`build_contract(..., "wallet_contract_testnet", TESTNET_CHAIN_ID)`), noting only `CHAIN_ID` is rewritten before the docker build: [8](#0-7)  and [2](#0-1) .
2. Deploy the resulting `wallet_contract_testnet.wasm` to a testnet eth-implicit account.
3. Submit an RLP-encoded transaction via `rlp_execute` representing an `EOABaseTokenTransfer` whose target resolves to `address_check: Some(address)` (target is an eth-implicit account, requiring a named-account lookup).
4. Observe that `inner_rlp_execute` calls out to `ADDRESS_REGISTRAR_ACCOUNT_ID` = `address-map.near` (hardcoded, unchanged for testnet build): [9](#0-8) .
5. Since `address-map.near` is a mainnet account ID and is not guaranteed/expected to be the correct registrar on testnet, the cross-contract call fails, and `address_check_callback` returns `"Call to Address Registrar contract failed"`, aborting the user's transaction (and potentially triggering relayer banning logic): [7](#0-6) .

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
