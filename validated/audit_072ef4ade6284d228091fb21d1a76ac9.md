### Title
Node-local wall-clock resource limits during block-proposal validation cause a minority of signers to permanently blacklist a valid, honest transaction - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
The report describes a class of bug where a resource limit that is *not* part of the deterministic, consensus-metered cost model (EVM `gasleft()`/63-64 rule) causes an operation that would otherwise succeed to be treated as "failed," wrongly penalizing an honest party. The Stacks analog is the per-transaction **wall-clock** execution/analysis time budgets used during block-proposal validation (`block_proposal_max_tx_execution_time_secs`, `block_proposal_max_tx_analysis_time_secs`). These are independent of Clarity's deterministic execution-cost metering and are configured per-node, so identical, cost-legal transactions can be classified `Problematic` by some signers and `Success` by others, purely as a function of local machine speed/load.

### Finding Description
Block-proposal validation enforces per-tx wall-clock deadlines that are separate from the deterministic `ExecutionCost` budget: [1](#0-0) 

If a transaction's execution or analysis phase exceeds these *local* time budgets, it is not merely skipped — it is classified as `Problematic`, and the whole block proposal is rejected with `ValidateRejectCode::ProblematicTransaction`, blaming that specific txid: [2](#0-1) 

The classification into "Problematic" happens through `TransactionResult::is_problematic`, which explicitly treats `ExecutionResourceBudgetExceeded`/`AnalysisResourceBudgetExceeded` (time/memory-bound, not cost-bound) the same as a genuinely invalid transaction: [3](#0-2) 

These time limits are documented as node-local, non-consensus values, configurable independently on each node: [4](#0-3) [5](#0-4) 

This is confirmed by an explicit code comment/test-annotation stating that the deterministic execution-cost limiter (`ExecutionResourceBudgetExceeded`) is unlimited (a no-op) on all consensus-critical code paths, and is enforced *only* here, on the block-proposal (signer-facing) validation path and miner-local mempool filtering: [6](#0-5) 

Once a `ProblematicTransaction` rejection propagates to the coordinating miner, per-signer rejection weight is tallied, and if the weight of signers reporting a given txid as "problematic" exceeds the **blocking minority** (i.e., >30% of total signer weight, since the pre-commit/signature threshold is 70%), that txid is **permanently excluded** from all future block proposals in the tenure — not merely delayed: [7](#0-6) 

There are existing tests confirming exactly this non-deterministic-timeout → `Problematic` → txid-blaming pathway for both the execution phase and the contract-analysis phase, and that a `0`s deadline immediately trips regardless of the actual (legitimate) cost consumed: [8](#0-7) [9](#0-8) 

Because `block_proposal_max_tx_execution_time_secs`/`..._analysis_time_secs` are wall-clock, node-local settings (not derived from the deterministic Clarity `ExecutionCost`), any honest, cost-legal transaction that happens to sit close to this time budget on a fraction of signer nodes (due to slower hardware, heavier concurrent load, GC pauses, or simply a conservatively-configured operator) will be judged `Problematic` there while other, faster/less-loaded signer nodes accept the very same transaction as `Success`. This breaks the equality that "a static-validation verdict should be reproducible by every honest node given the same block and transaction" — the verdict now depends on non-consensus, machine-specific timing.

### Impact Explanation
This matches the "High" bucket: *"a minority-triggerable sortition/VRF/static-validation divergence... temporary tip disagreement."* A minority (just over 30% signer weight) experiencing slower validation for a cost-legal transaction is enough to:
1. Cause split validation verdicts among honest signers for the same honest block/transaction (temporary tip/consensus disagreement, forcing the miner to drop/retry).
2. **Permanently** exclude the honest transaction's txid from all further proposals in the tenure via `permanently_excluded_txids`, denying an entirely valid, non-malicious user's transaction inclusion — directly mirroring the original report's "honest users penalized when they shouldn't be."

No majority collusion, admin/operator privilege, or another party's key is required; only ordinary variance in signer hardware/load (or a conservatively low, but legitimately configured, `block_proposal_max_tx_execution_time_secs`) combined with a legitimately somewhat-heavy but cost-budget-compliant transaction.

### Likelihood Explanation
Moderately likely under specific conditions: it requires a transaction whose execution/analysis time sits close to the per-node wall-clock budget while remaining within the deterministic cost limit, and requires that signers' local timing/hardware/load differ enough to produce divergent verdicts. This is more likely to arise under network stress, heterogeneous signer hardware, or if an operator sets `block_proposal_max_tx_execution_time_secs` conservatively low (which is explicitly configurable per node), or if a user/attacker crafts a transaction deliberately near this threshold (analogous to the original report's frontrunning tactic, here the "attacker" simply needs to submit a heavy-but-legal transaction, no frontrunning needed since the harm falls on themselves or on any tx sharing the block).

### Recommendation
Decouple the "Problematic"/permanent-blacklist consequence from non-deterministic wall-clock/timing-based rejections. Specifically:
- Do not classify `ExecutionResourceBudgetExceeded`/`AnalysisResourceBudgetExceeded` errors that arise purely from local wall-clock or memory soft-limits as `Problematic` (which leads to permanent txid blacklisting); instead treat them like a block-full/skip condition so the tx can be retried in a future proposal rather than permanently banned.
- Alternatively, require a much higher weight threshold (closer to full signer-set agreement) before a txid is moved to `permanently_excluded_txids` specifically for `ProblematicTransaction` reasons that stem from local timing, versus reasons that stem from deterministic, reproducible errors (e.g., a genuine `ClarityError` that would invalidate the block for everyone).
- Ensure the default/recommended `block_proposal_max_tx_execution_time_secs`/`..._analysis_time_secs` carries generous headroom above the worst-case time implied by the deterministic cost budget, so that no cost-legal transaction can plausibly trip it on reasonably provisioned hardware.

### Proof of Concept
1. An honest user submits a contract-call/deploy that is well within the network's deterministic `ExecutionCost` block-budget but takes, e.g., several seconds of real wall-clock time to execute/analyze (e.g. many MARF reads, as already exercised by the `make_big_read_count_contract`/`test_block_proposal_validation_execution_time_expired_blames_tx` tests) [10](#0-9) .
2. A miner includes it in a Nakamoto block proposal, having validated it fine locally (its own `max_analysis_time_secs`/execution time budget is generous, e.g. `u64::MAX` as configured in the analogous analysis-phase test) [11](#0-10) .
3. A subset (>30% weight) of signers running slower or more heavily-loaded nodes, or a conservative `block_proposal_max_tx_execution_time_secs`/`..._analysis_time_secs`, validate the exact same block via `/v3/block_proposal` and their local timer fires before the deterministic cost limit would ever be reached, so `TransactionResult::is_problematic` marks the tx `Problematic` [12](#0-11) , and their `BlockValidateReject` blames that specific txid with `ValidateRejectCode::ProblematicTransaction` [13](#0-12) .
4. The coordinating miner accumulates this rejection weight; because `info.problematic_weight` exceeds the blocking minority, the honest transaction's txid is moved into `permanently_excluded_txids` and never reconsidered for the remainder of the tenure [14](#0-13) , despite a majority of signers (up to 70%) having found it perfectly valid — a wrongful, minority-triggered penalty against an honest user with no consensus-level fault on their part.
