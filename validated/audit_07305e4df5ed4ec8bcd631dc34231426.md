### Title
Unmetered `VotesStore` iteration during automatic maintenance cycle allows on-demand chain halt via cheap vote spam - ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
`MaintenanceManager.doMaintenance()` is invoked automatically by consensus block application whenever a block crosses the maintenance-time boundary (the DPoS analog of `BeginBlock`), and its `countVote()` helper performs a full, unbounded iteration over the entire `VotesStore` with no gas/energy/step metering, deleting each entry as it goes.

### Finding Description
`Manager.processBlock()` calls `consensus.applyBlock(block)` for every block [1](#0-0) . This eventually triggers `MaintenanceManager.doMaintenance()` once the block's timestamp passes `nextMaintenanceTime` — a scheduled, non-transaction-driven hook analogous to Cosmos SDK's `BeginBlock`. Inside `doMaintenance()`, `countVote(votesStore)` performs a raw iterator walk over the *entire* `VotesStore` database:

```
Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
while (dbIterator.hasNext()) {
  Entry<byte[], VotesCapsule> next = dbIterator.next();
  VotesCapsule votes = next.getValue();
  votes.getOldVotes().forEach(...);
  votes.getNewVotes().forEach(...);
  ...
  votesStore.delete(next.getKey());
}
``` [2](#0-1) 

This loop is called unconditionally at the start of `doMaintenance()` [3](#0-2) , and there is no limit on the number of entries in `VotesStore` — one entry is created per distinct account that casts a `VoteWitnessContract` transaction, and each such transaction is only metered by ordinary bandwidth/energy fees for that single transaction, not by the cost this entry imposes on the subsequent, unmetered maintenance-time scan. An attacker who creates many low-balance accounts (bounded only by the cheap `CREATE_NEW_ACCOUNT_FEE_IN_SYSTEM_CONTRACT`/account-creation cost) and casts one vote from each can inflate `VotesStore` to an arbitrary size within a single ~6-hour maintenance window. When the maintenance boundary is crossed, `doMaintenance()` must synchronously iterate and delete every one of those entries before block processing/consensus can complete — this is directly analogous to the reported `AllocateRewards`/`GetAllBalances` issue, where a permissionless, cheaply repeatable action (sending many token denominations to a plan address / casting many votes from many accounts) inflates a collection that is later iterated without metering inside a scheduled, non-transaction-gated block-processing hook.

### Impact Explanation
If `VotesStore` is inflated to a very large number of entries, `countVote()`'s iteration (with nested `forEach` over `oldVotes`/`newVotes` and a store `delete` call per entry) executing during `doMaintenance()` can take an amount of time proportional to attacker-controlled state size, executed synchronously as part of applying every block that crosses the maintenance boundary. Since this runs for every full node processing that block (not just the block producer), and blocking/slow processing here directly delays or halts block production/consensus across the network, this matches the "chain halt on-demand of arbitrary length" impact class from the source report.

### Likelihood Explanation
Likelihood is bounded mainly by the cost of creating many accounts and casting votes, which is an ordinary, permissionless, moderately cheap action (standard transaction/account-creation fees, no privileged access required). Unlike the original TRC10/asset-balance vector (which was explicitly confirmed and fixed upstream in the referenced project), I was not able to fully confirm within the available time whether `VotesStore` entries are also created/refreshed by other mechanisms, nor precisely quantify per-entry cost versus iteration cost in java-tron, so the severity/likelihood should be validated with a proof-of-concept measuring `doMaintenance()` duration versus `VotesStore` size before treating this as confirmed-exploitable.

### Recommendation
- Bound or amortize the maintenance-time vote-counting workload, e.g., process `VotesStore` entries incrementally across multiple blocks rather than in one synchronous pass, or cap the number of entries processed per maintenance cycle.
- Consider requiring a non-trivial, non-refundable cost per `VoteWitnessContract` proportional to the amortized cost of processing that vote at maintenance time, rather than only ordinary bandwidth fees.
- Add instrumentation/metrics for `VotesStore` size and `doMaintenance()` execution time to detect this condition before it becomes a consensus-wide stall.

### Proof of Concept
Not independently reproduced against this repository within the scope of this review. Suggested test outline (analogous to the original report's Go PoC): in a test extending the existing `DelegationServiceTest`/`VoteWitnessActuatorTest` fixtures, programmatically create N accounts (e.g., tens of thousands), cast a `VoteWitnessContract` from each within a single maintenance cycle, then invoke `MaintenanceManager.doMaintenance()` directly and measure wall-clock time as N grows, to confirm the iteration cost scales with attacker-controlled `VotesStore` size.   private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
