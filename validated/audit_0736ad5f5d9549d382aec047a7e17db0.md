Based on my investigation, I found a concrete, code-documented state-integrity gap in the transaction-output verification path used by replay and chunk-execution flows.

### Title
`TransactionOutput::ensure_match_transaction_info` omits state/hot-state/position checkpoint hash checks, letting divergent state roots pass replay and chunk verification - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to validate that a locally-computed `TransactionOutput` (write set, events, gas, status) matches the authenticated `TransactionInfo` carried in an accumulator-proven transaction/output list. It is called from `execution/executor/src/chunk_executor/mod.rs` (state-sync/chunk replay), `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. The function checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the authenticated `TransactionInfo`.

### Finding Description [1](#0-0) 

The function's own comment acknowledges the gap: [2](#0-1) 

`TransactionInfo` carries `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` as authenticated fields (proven via the transaction accumulator and ledger-info signatures), but `ensure_match_transaction_info` never compares these against the checkpoint root that local execution/replay actually produced. Only `state_change_hash` (the per-transaction write-set hash) and `event_root_hash` are checked—neither of which reflects the cumulative Merkle root of the full state tree after applying the write set.

This function is consumed by state-integrity-relevant callers, most notably `execution/executor/src/chunk_executor/mod.rs`, which is part of the output-based chunk execution/replay path used during state sync and replay verification (`db-tool replay_on_archive`).

### Impact Explanation
If the local state tree root computed after applying a chunk's write sets diverges from the `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` embedded in the authenticated `TransactionInfo` (e.g., due to a state-tree computation bug, sharding/position-subsystem inconsistency, or an execution divergence that still produces byte-identical write sets), `ensure_match_transaction_info` will report success. This means:
- `db-tool replay_on_archive` can report a clean replay while the locally computed state root has silently diverged from the authenticated ledger state, undermining its purpose as an integrity check.
- In the chunk executor path, a state root divergence in the "position" state subsystem (or hot-state) is not caught by this specific check, meaning storage can end up committing/serving state that does not match the version's authenticated root.

This matches the required "wrong state root accepted as valid" / "state-view output bound to the wrong version or proof context" impact category, and represents a real gap in the audited replay/proof-binding path rather than a restatement of the external RWA/chainlink report.

### Likelihood Explanation
This is not a remotely-triggerable attack by itself (no external attacker input is described here); rather, it's a coverage gap in the check that is supposed to catch execution/replay divergence. Likelihood of the underlying divergence occurring depends on other bugs (e.g., in the sharded "position" state or hot-state computation) actually producing a different root while write sets remain identical — which is plausible when state roots are computed from more inputs than just the raw write set (e.g., hotness promotions, native position updates). I was not able to fully confirm within the available time whether `do_state_checkpoint.rs` independently re-validates `state_checkpoint_hash` elsewhere in the exact chunk-executor commit path, so I cannot state with certainty that this gap is fully unmitigated in all callers — see caveat below.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) between the locally computed values and the authenticated `TransactionInfo`, consistent with the TODO comment already present in the code (referencing `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), and ensure this check is active on all replay/chunk-execution/backup-verification code paths, not just as a documented future improvement.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
