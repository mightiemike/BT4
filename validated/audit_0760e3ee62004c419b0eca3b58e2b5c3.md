### Title
Replay-verify tooling accepts corrupted state/hot-state/position checkpoint roots as valid - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) is the correctness check used by the `db-tool replay-verify` / `replay_on_archive` tooling (invoked from `execution/executor/src/chunk_executor/mod.rs::verify_execution`, line ~692) to confirm that locally re-executed transactions match the `TransactionInfo` objects fetched from an (untrusted) archive/backup. The function validates `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`, but explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — a gap the code itself documents in a TODO comment (lines 2197-2202).

### Finding Description
`ensure_match_transaction_info` is the sole per-transaction correctness gate for the replay-verify flow that operators/auditors use to confirm an archive's committed ledger state actually corresponds to correct VM execution: [1](#0-0) 

It checks status, gas, the write-set hash, and the event root hash, then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` against values recomputed from local execution: [2](#0-1) 

This is invoked from the chunk executor's `verify_execution`, which re-executes transactions with the VM and calls `ensure_match_transaction_info` against `TransactionInfo`s taken from the external/backup source under verification: [3](#0-2) 

Because the state-checkpoint hash (the Sparse-Merkle-Tree root of world state) and the newer position/hot-state checkpoint hashes are never cross-checked here, an archive/backup whose stored `TransactionInfo.state_checkpoint_hash` (or the new `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields) has been corrupted or diverges from what correct execution would produce will still pass `replay-verify`/`replay_on_archive` as long as write-set bytes, events, gas, and status match. In other words, the "authenticated" state root that this tool is meant to authenticate is not actually authenticated.

### Impact Explanation
This breaks the state-commitment integrity guarantee for the replay-verify auditing path: an operator running `db-tool replay-verify` against a backup/archive to confirm the archive's state roots are correct (e.g., before using it to bootstrap a new node or trusting its state proofs) can be told "replay succeeded" even though the archived `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` is wrong or has been tampered with. Any node or index bootstrapped from such a "verified" archive would end up trusting an incorrect world-state root, and any state proofs served relative to that root would be silently wrong. This matches the "Wrong accumulator root/state proof accepted as valid" and "authenticated API/proof-bearing response bound to wrong root" impact classes, scoped specifically to the replay-verify / restore auditing tool rather than the consensus commit path (which is independently protected by `ensure_transaction_infos_match`'s full-struct equality check).

### Likelihood Explanation
This requires an untrusted or compromised backup/archive source being fed to the replay-verify tool — which is exactly the threat model that `replay-verify` is designed to guard against (verifying archives before trusting them). The gap is unconditional (not behind a feature flag) and is explicitly acknowledged in the code's own TODO comment, indicating it is a known, provable, currently-live gap rather than a hypothetical one.

### Recommendation
In `ensure_match_transaction_info`, additionally recompute the expected state-checkpoint root (and hot-state/position-state checkpoint roots when `transaction_info_v1`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` apply) from local execution and assert equality against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, exactly as the TODO comment specifies, before returning `Ok(())`.

### Proof of Concept
1. Take a backup/archive and, for one `TransactionInfo` at a state-checkpoint boundary, replace `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) with an arbitrary `HashValue` while leaving the transaction, write set, and events untouched.
2. Run `db-tool replay-verify` / `replay_on_archive` against this archive with `VerifyExecutionMode::verify()` enabled.
3. `chunk_executor::verify_execution` re-executes the transaction and calls `ensure_match_transaction_info`, which checks status/gas/`state_change_hash`/`event_root_hash` only — all still valid — and returns `Ok(())`, reporting a successful replay despite the corrupted checkpoint hash.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
