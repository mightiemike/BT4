### Title
Delegated `WithdrawFromGasKey` bypasses the pending-transaction-queue's per-account gas-key funding accounting, allowing a signer to drain a gas key beyond what the admission layer believes is available - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
The KyberSwap report describes a case where an access-control gate (`refundEth`/`unwrapWeth`) is defined once in a base contract and is expected to be re-checked/overridden by every derived contract that inherits it, but one derived contract (`BasePositionManager`) never re-asserts the check, so the "shared" logic silently becomes reachable without authorization. The closest analog in nearcore is a shared/duplicated validation surface for `Action::WithdrawFromGasKey`: the actual balance-authorization check lives in `runtime/runtime/src/access_keys.rs::action_withdraw_from_gas_key` and `check_actor_permissions` (`runtime/runtime/src/actions.rs:755-800`), which correctly requires `actor_id == account_id`. But the *admission-time* accounting that decides whether a transaction may even be accepted into a chunk — `chain/client/src/pending_transaction_queue.rs::check_pending` — re-implements its own, narrower scan of the same action for a different purpose (bounding pending gas-key withdrawals) and only looks at *top-level* actions of the transaction, not at actions nested inside a `Delegate`/`DelegateV2` action.

### Finding Description
`check_pending` in `chain/client/src/pending_transaction_queue.rs:510-593` tracks, per gas key, how much balance is expected to be withdrawn by transactions that are already pending in the chunk-production session, via `session_gas_key_withdrawals`:
```rust
for action in tx.transaction.actions() {
    if let Action::WithdrawFromGasKey(withdraw) = action {
        let entry = self
            .session_gas_key_withdrawals
            .entry((signer_id.clone(), (&withdraw.public_key).into()))
            .or_insert(Balance::ZERO);
        *entry = entry.saturating_add(withdraw.amount);
    }
}
```
This loop iterates `tx.transaction.actions()` directly — i.e. only the *top-level* actions of the transaction. It does not recurse into a `Delegate`/`DelegateV2` action's inner action list. The engineers themselves documented this exact gap as the rationale for the `RejectWithdrawFromGasKeyInDelegate` protocol feature (`core/primitives-core/src/version.rs:462-465`):
> "The SPICE pending transaction queue scans only the top level actions of a transaction for `WithdrawFromGasKey`, so a nested one drains a gas key that the queue still counts as funded."

Before that feature activates, a `Delegate` action whose inner action is `WithdrawFromGasKey` is a legal, self-authorized action (`check_actor_permissions` passes because `actor_id == sender_id == account_id`, and the balance is subtracted correctly at execution in `access_keys.rs::action_withdraw_from_gas_key`). The bug is not in the authorization of *who* can withdraw — it is that `check_pending`'s admission-time accounting undercounts the gas key's outstanding, already-admitted withdrawals whenever they are wrapped in a delegate action, because it inherited/duplicated the "scan actions for `WithdrawFromGasKey`" logic without covering the nested/`Delegate` case that the authoritative runtime-execution path does handle. This is exactly the "inheritance/duplication misuse" pattern from the report: a security-relevant check that exists in one place (chunk producer's transaction admission gate meant to bound gas-key balance usage across concurrently-pending transactions) fails to mirror the semantics of the authoritative execution-time check, letting a code path (nested delegate) slip through unaccounted.

This is confirmed to have been an active gap that the protocol had to explicitly close with `RejectWithdrawFromGasKeyInDelegate` (rejecting any `WithdrawFromGasKey` nested in a `Delegate` action at validation time, `runtime/runtime/src/action_validation.rs` `test_validate_action_delegated_withdraw_from_gas_key_rejected_in_new_receipt`), and the regression test `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs` explicitly demonstrates that pre-upgrade, "the nested withdrawal should have drained the gas key" as a documented pre-fix behavior.

### Impact Explanation
While the fund movement itself (withdrawing from one's own gas key back to one's own account balance) is not a theft of someone else's funds, it does let a single signer submit multiple transactions in the same chunk-production window that collectively withdraw more from a gas key than the admission layer's `paid_from_gas_key` constraint believes is outstanding (`PendingConstraints::paid_from_gas_key`, consumed by `verify_and_charge_gas_key_tx_ephemeral` in `runtime/runtime/src/verifier.rs:383`). Because the accounting gate that other pending transactions rely on to avoid over-admitting gas-key spends (avoiding `NotEnoughGasKeyBalance` at execution and superfluous chunk space usage) is bypassed, several transactions relying on the same gas key balance can be simultaneously admitted into a chunk under an assumption of available balance that is stale/wrong, and the runtime is left to fail some of them at execution (with wasted gas/chunk space) or, depending on timing/order, allow a withdrawal sequence that the admission layer never accounted for. In the worst case this affects fair chunk-space allocation and gas-key balance bookkeeping consistency between the optimistic admission path and the authoritative runtime execution path — a state-transition-adjacent inconsistency reachable purely from a signer submitting ordinary transactions containing a `Delegate` action.

### Likelihood Explanation
High reachability: any account holder with a gas key can construct this today (pre-upgrade) with nothing more than a signed transaction containing a `Delegate` action whose inner action is `WithdrawFromGasKey` targeting their own gas key — exactly as shown in `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs:26-54`. No validator or peer collusion, no special privileges, and no sandbox/adversarial harness are required — this is a plain, single-transaction, RPC-submitted flow. The protocol has already had to add a dedicated feature-gated rejection rule to close it, which corroborates that this was a genuinely exploitable gap prior to `RejectWithdrawFromGasKeyInDelegate` activation.

### Recommendation
Ensure `check_pending`'s gas-key-withdrawal scan in `chain/client/src/pending_transaction_queue.rs` walks nested `Delegate`/`DelegateV2` action lists (not just top-level actions) so pending accounting matches the authoritative execution semantics, in addition to (or as defense-in-depth alongside) the protocol-level `RejectWithdrawFromGasKeyInDelegate` rejection. More generally, any duplicated "scan actions for action X" logic that exists purely for admission/accounting purposes should share a single recursive action-walking implementation with the authoritative execution/validation code, rather than being independently re-implemented with different (narrower) traversal semantics — precisely the "inheritance/duplication misuse" root cause identified in the reference report.

### Proof of Concept
1. Attacker/account holder `alice` adds a gas key and funds it via `TransferToGasKey`.
2. `alice` builds a `SignedTransaction` whose single top-level action is `Action::Delegate(SignedDelegateAction)`, where the inner `DelegateAction::actions` contains `Action::WithdrawFromGasKey { public_key: gas_key, amount: WITHDRAW_AMOUNT }`, per `delegated_withdraw_tx` in `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs:26-54`.
3. On a protocol version prior to `RejectWithdrawFromGasKeyInDelegate` (`core/primitives-core/src/version.rs`), `check_pending` (`chain/client/src/pending_transaction_queue.rs:576-585`) iterates `tx.transaction.actions()`, sees only the top-level `Delegate` action, and never records the nested `WithdrawFromGasKey` amount against `session_gas_key_withdrawals`.
4. `alice` submits several such delegate-wrapped withdrawal transactions concurrently within one chunk-production session; each is individually admitted because the admission layer's per-gas-key outstanding-withdrawal tracking never increments, even though the authoritative runtime execution (`action_withdraw_from_gas_key`) does actually debit the gas key balance each time.
5. As shown by the test's assertion (`"the nested withdrawal should have drained the gas key"`), the gas key's balance is drained through a path that admission-time accounting does not track, demonstrating the divergence between the optimistic admission model and actual state transitions.
