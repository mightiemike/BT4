### Title
Unbounded blocking on shared `CountDownLatch` in `RewardViCalService.getNewRewardAlgorithmReward` allows thread-pool exhaustion DoS during migration window - (File: chainbase/src/main/java/org/tron/core/service/RewardViCalService.java)

### Summary
`RewardViCalService.getNewRewardAlgorithmReward` blocks the calling thread on `lock.await()` with no timeout whenever the reward-VI migration is not yet finished (`isDone()` false). Since this method is reachable from multiple unauthenticated read-only entrypoints (`/wallet/getReward`, `walletsolidity/getReward`, `walletpbft/getReward`, and internally from `MortgageService.queryReward`), any number of concurrent public callers during the migration window will each occupy an HTTP/gRPC worker thread until the one-time migration completes.

### Finding Description
`RewardViCalService` holds a single `CountDownLatch lock = new CountDownLatch(1)` [1](#0-0) . When `getNewRewardAlgorithmReward` is invoked and `isDone()` (i.e. `rewardViStore.has(IS_DONE_KEY)`) is false, every calling thread blocks indefinitely on `lock.await()` with no timeout: [2](#0-1) . The latch is only released via `clearUp()`, invoked from the scheduled `maybeRun()` task after `startRewardCal()` finishes iterating the entire `witnessStore`/`delegationStore` and computing VI values for every witness across every historical cycle up to the migration cycle [3](#0-2) .

This path is reachable from unauthenticated HTTP: `GetRewardServlet.doGet` -> `Manager.getMortgageService().queryReward(address)` -> `MortgageService.getOldReward` -> `rewardViCalService.getNewRewardAlgorithmReward` [4](#0-3) [5](#0-4) . The same `MortgageService.queryReward`/`getOldReward` chain is also invoked from `walletsolidity/getReward` (`GetRewardOnSolidityServlet`) and `walletpbft/getReward` (`GetRewardOnPBFTServlet`), and from the TVM `RewardBalance` precompile via `VoteRewardUtil`/`Program` [6](#0-5)  — all of which are unauthenticated, public entrypoints with no rate/cost control tied to this blocking behavior. `RateLimiterServlet` on `GetRewardServlet` limits per-IP/global request rate but does not prevent the underlying thread from occupying a worker slot for the full duration of the latch wait once admitted, and an attacker distributing requests across many source IPs or accounts easily exceeds the limiter's protection.

Since no timeout is applied to `lock.await()`, every concurrent request made during the migration window consumes one HTTP/gRPC worker thread for the entire duration of `startRewardCal()`, which is proportional to the number of witnesses times the number of historical cycles processed — this can be substantial on a long-lived chain. If concurrent request volume exceeds the size of the servlet/RPC thread pool, all worker threads become blocked, and the node cannot serve *any* other HTTP/gRPC requests (not just reward queries) until the migration completes.

### Impact Explanation
During the (bounded but potentially lengthy, depending on chain height/witness count) migration window where `rewardViStore` lacks `IS_DONE_KEY`, flooding `GetRewardServlet`/`walletsolidity`/`walletpbft`/gRPC `GetRewardInfo`/`RewardBalance` precompile calls can saturate the finite HTTP/gRPC thread pool, denying service to all API consumers node-wide for the duration of the migration — a real, reproducible node-wide DoS triggered purely by unauthenticated read requests at essentially zero attacker cost.

### Likelihood Explanation
The migration window is deterministic (triggered once per node when `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` becomes active and the checkpoint condition is met, per `maybeRun`/`enableNewRewardAlgorithm`) and its timing is publicly knowable around a scheduled hard fork/upgrade, making the attack window predictable and repeatable across every node in the network during the same upgrade event. The attack requires no special privileges — only the ability to send public read-only API requests — and per-request cost is trivial compared to the thread-blocking cost imposed on the server, satisfying "materially underpriced public work below true request cost."

### Recommendation
- Apply a bounded timeout to `lock.await(timeout, TimeUnit)` in `RewardViCalService.getNewRewardAlgorithmReward`, returning a clear "service not ready / retry later" error instead of blocking indefinitely.
- Alternatively, avoid blocking the calling (servlet/RPC/precompile) thread at all: return an explicit "not ready" status/error immediately when `!isDone()`, and let clients retry, rather than parking the thread on a latch.
- Ensure `RateLimiterServlet`/API gateway limits account for worst-case per-request thread occupancy time, or dispatch the migration wait onto a bounded/async executor decoupled from the request-handling thread pool so pool exhaustion cannot occur.

              clearUp(true);
            } else {

            }
          }

          clearUp(false);
          logger.info("rewardViCalService is no need to run");
        }
      }
    } catch (Exception e) {

      throw new TronError(e, TronError.ErrCode.REWARD_VI_CALCULATOR);
    }
  }
