### Title
Inbound execution mints PRC20 for tokens without checking `TokenConfig.Enabled` - ([File: x/uexecutor/keeper/handler.go])

### Summary
The reported THENA bug is a class of "disabled/killed entity still usable" flaw: a boolean deactivation flag (`isAlive`) exists on the gauge but is not checked on the vote path, only on a separate `isGauge` existence check, letting users interact with an entity the protocol operators intended to disable. The Push Chain analog is `TokenConfig.Enabled` in `x/uregistry`: tokens can be marked disabled (`enabled = false`, presumably by an admin wanting to pull a compromised/deprecated token from bridging), but the inbound deposit path that mints PRC20 (`depositPRC20` in `x/uexecutor/keeper/handler.go`) only checks that `NativeRepresentation` is set — it never checks `TokenConfig.Enabled`.

### Finding Description
`x/uregistry` models `TokenConfig.Enabled` as "Whether this token is enabled for minting/bridging" [1](#0-0) . Analogous to `ChainConfig.Enabled` (`IsInboundEnabled`/`IsOutboundEnabled`), which is explicitly enforced at the very top of `VoteInbound` before any state mutation [2](#0-1)  and at outbound creation via `IsChainOutboundEnabled` [3](#0-2) , the equivalent per-token flag is not enforced at the point where funds are actually minted.

`depositPRC20`, which is invoked during inbound execution to mint PRC20 tokens to a recipient's UEA, fetches the token config purely to resolve the native PRC20 contract address and immediately calls the mint EVM call — it does not read or check `tokenConfig.Enabled` anywhere in this function: [4](#0-3) 

This means once a source-chain inbound ballot for a given `(chain, tokenAddress)` reaches quorum among honest validators (an ordinary, unprivileged user flow — a user just needs to send funds on the source chain gateway that any honest UV will observe and vote on), the mint proceeds regardless of whether an admin has since flipped `TokenConfig.Enabled = false` for that token — mirroring exactly the THENA pattern where `isGauge` (existence) was checked but `isAlive` (active status) was not.

### Impact Explanation
If `Enabled=false` is meant to be Push Chain's mechanism for pulling a token from active bridging (e.g., because the token proved malicious/broken, its liquidity cap needs enforcing, or its `NativeRepresentation` contract is being rotated), an inbound observed and voted on by honest validators for that token still results in unauthorized minting of PRC20 to the recipient. This is unauthorized module-originated EVM execution / accounting corruption for a token administrators believed was disabled, and depending on why the token was disabled, could result in unauthorized mint against a compromised PRC20 or route funds through a config the registry no longer considers valid.

### Likelihood Explanation
This requires no privileged action beyond ordinary user activity: a user submits a legitimate inbound (deposit) on the source chain for a token that the admin has since disabled; honest UVs still observe and vote it per the existing consensus flow, and the keeper deposit code has no gate on `Enabled`. This is directly reachable via the default `MsgVoteInbound` → `VoteInbound` → inbound execution → `depositPRC20` path with no additional preconditions.

### Recommendation
Add an explicit `tokenConfig.Enabled` check inside `depositPRC20` (or earlier, in the inbound execution flow before invoking it), mirroring the `IsChainInboundEnabled`/`IsChainOutboundEnabled` pattern already used for chains, so that inbound execution rejects (or records a `FAILED` PCTx, consistent with the existing "no state silently stuck" design used for missing token configs) when the token is disabled.

### Proof of Concept
Not independently verified end-to-end due to remaining ambiguity in the exact inbound-execution call graph (`execute_inbound_funds.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas.go` were identified as callers of the deposit path but their full bodies were not inspected in this session, so I cannot confirm with certainty whether an `Enabled` check exists further up the call chain before `depositPRC20` is invoked). Given the index limits reached, I recommend a Devin session trace the full call path from `VoteInbound` → ballot finalization → `execute_inbound*.go` → `depositPRC20` to confirm no `TokenConfig.Enabled` gate exists anywhere in that path before treating this as a confirmed, unguarded vulnerability.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```
