### Title
Uncaught exception in `sanitizeHost`/`decodeHost` on malformed `host` param can crash the request/process (analogous DoS to stellar-strkey panic) - (File: `packages/apps/shopify-api/lib/auth/decode-host.ts`)

### Summary
`embedAppIntoShopify` in `packages/apps/shopify-app-express/src/middlewares/ensure-installed-on-shop.ts` catches its exception, but the underlying `sanitizeHost`/`decodeHost` code path is used in several other unprivileged, anonymous-request-facing places that do **not** wrap the call in try/catch, and can throw on attacker-controlled input.

### Finding Description
`sanitizeHost` only checks that the `host` string matches the character class `[0-9a-zA-Z+/]+={0,2}` before calling `decodeHost`, which is a thin wrapper around the global `atob`: [1](#0-0) [2](#0-1) 

That regex does not enforce that the base64 payload length is a multiple of 4 (mod-4 remainder of 1 is invalid per the forgiving-base64 algorithm that `atob` implements). A value such as `host=A` (length 1) passes the regex but causes `atob()` to throw an uncaught `DOMException`/`SyntaxError` — this is structurally the same bug class as the stellar-strkey issue: a "looks valid" length check that doesn't validate the real constraint needed by the decoding routine, causing the decoder to throw/panic on crafted input.

This code path is reachable pre-authentication from an anonymous HTTP request through multiple call sites, e.g.: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

None of these call sites wrap `sanitizeHost`/`decodeHost` in try/catch (only `embedAppIntoShopify` in the express `ensureInstalledOnShop` middleware does).

### Impact Explanation
In the Remix/React Router adapters, a thrown error inside a loader/action is typically converted into a framework error boundary response (500), limiting impact to a single failed request rather than a process crash. However, in the Express adapter (`redirectToAuth` → `clientSideRedirect` → `sanitizeHost`), the call sits inside an `async` middleware function that Express does not automatically wrap; an exception thrown there becomes an unhandled promise rejection unless the app's global error-handling middleware or Node's `unhandledRejection` handling intercepts it. Depending on the developer's Express error-handling setup and Node.js version defaults, an unhandled rejection can terminate the Node process, producing a real denial-of-service. Even when contained to a single request, this is at minimum an unhandled-exception/DoS vulnerability in an auth-adjacent request-handling path reachable by any anonymous visitor supplying a crafted `host` query parameter.

### Likelihood Explanation
Exploitation requires only a single unauthenticated GET request with `host` set to a string that satisfies the base64-charset regex but has an invalid base64 length (e.g., `host=A`, or any base64 alphabet string whose length mod 4 equals 1). No secrets, sessions, or privileged access are needed, making this trivially reachable by any external actor hitting an app's auth/login/embed routes.

### Recommendation
- In `sanitizeHost` (`packages/apps/shopify-api/lib/utils/shop-validator.ts`), validate the base64 length constraint (length % 4 !== 1, and reasonable max length) before calling `decodeHost`, or wrap the `decodeHost` call in a try/catch and treat decode failures as an invalid host (return `null` / throw `InvalidHostError` consistently), matching the stellar-strkey patch approach of bounding/validating length before performing the decode.
- Audit every caller of `sanitizeHost`/`decodeHost`/`getEmbeddedAppUrl` (Express, Remix, React Router adapters) to ensure decode failures are caught and converted into a normal 4xx response rather than propagating as an unhandled exception/rejection.

### Proof of Concept
```
GET /auth?shop=my-shop.myshopify.com&host=A&embedded=1
```
Sent to an Express app configured with `redirectToAuth`/`ensureInstalledOnShop` (or any embedded app route calling `sanitizeHost`/`decodeHost` without a surrounding try/catch): the single-character `host=A` value passes `base64regex.test('A')` (matches `[0-9a-zA-Z+/]+={0,2}`), then `decodeHost('A')` calls `atob('A')`, which throws because a base64 string of length 1 (mod 4 = 1) is invalid per the forgiving-base64 algorithm. Since `clientSideRedirect`/`redirectToAuth` do not catch this, the exception propagates as an unhandled exception/promise rejection in the request-handling path.

import {redirect} from '@remix-run/server-runtime';

import type {BasicParams} from '../../../types';

export async function redirectToShopifyOrAppRoot(
  request: Request,
  params: BasicParams,
  responseHeaders?: Headers,
): Promise<never> {
  const {api} = params;
  const url = new URL(request.url);

  const host = api.utils.sanitizeHost(url.searchParams.get('host')!)!;
  const shop = api.utils.sanitizeShop(url.searchParams.get('shop')!)!;

  const redirectUrl = api.config.isEmbeddedApp
    ? await api.auth.getEmbeddedAppUrl({rawRequest: request})
    : `/?shop=${shop}&host=${encodeURIComponent(host)}`;

  throw redirect(redirectUrl, {headers: responseHeaders});
}
