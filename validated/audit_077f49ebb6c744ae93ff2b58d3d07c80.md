Found: this points to a genuine analog in the NEAR Wallet Contract's ERC-20 emulation path.

### Title
ERC-20 emulation forwards raw wei-scale `value` to `ft_transfer` without adjusting for the NEP-141 token's actual decimals - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/eth_emulation.rs`)

### Summary
The Wallet Contract's `try_emulation` function decodes the Ethereum ABI `value` from an ERC20 `transfer(address,uint256)` call and passes it verbatim as the NEP-141 `amount` string, with no scaling based on the target contract's declared `ft_metadata().decimals`.

### Finding Description
In `try_emulation`, the `ERC20_TRANSFER_SELECTOR` branch decodes `(to, value): (Address, u128)` directly from calldata and builds the `ft_transfer` args using that raw `value` unmodified: [1](#0-0) 
This mirrors the ERC4626 bug class exactly: the code assumes a fixed relationship between two different unit systems (Ethereum's implicit 18-decimal convention for token amounts vs. the target NEP-141 token's own `ft_metadata().decimals`, which can be any value — e.g., 6, 8, 24) and never queries or accounts for the actual decimals of the receiving contract, unlike the deliberate, well-documented 18→24 decimal handling done for the native token in `internal.rs`: [2](#0-1) 
The comment/tests confirm the wallet contract explicitly reasons about decimal scale for $NEAR (24) vs $ETH (18) conversions in `MAX_YOCTO_NEAR = 1_000_000`, but no equivalent scaling exists for ERC20-emulated tokens whose underlying NEP-141 decimals are unknown at parse time and are never fetched or checked in `eth_emulation.rs`.

### Impact Explanation
Because the raw `uint256` value from the RLP-encoded Ethereum transaction is passed straight through as the NEP-141 `amount`, any token with decimals different from what an Ethereum wallet/tooling assumes will receive wildly incorrect transfer amounts — e.g., a user intending to send "1 token" (scaled per their wallet's assumed 18 decimals) against a NEP-141 token with 6 decimals would transfer 10^12× the intended amount, or the reverse mis-scaling could transfer negligible dust. Since the wallet-contract directly issues `ft_transfer` calls that move real token balances, this can cause unauthorized/unintended value movement between accounts controlled by users who are relying on standard Ethereum tooling to interact with NEAR-native fungible tokens through the eth-implicit account/wallet-contract path.

### Likelihood Explanation
Every RLP-encoded transaction with the `ERC20_TRANSFER_SELECTOR` submitted through `rlp_execute` reaches this code path; it requires no special privilege, only a validly signed Ethereum-formatted transaction routed through the wallet contract's relayer flow (`inner_rlp_execute` → `parse_rlp_tx_to_action` → `try_emulation`), making it reachable by any user/relayer sending a standard transaction.

### Recommendation
Before emitting the `ft_transfer` action, fetch (or cache) the target NEP-141 contract's `ft_metadata().decimals` and apply the appropriate scale factor relative to the decimal convention assumed by the Ethereum-side tooling (analogous to how `MAX_YOCTO_NEAR` scales native $NEAR/$ETH), or explicitly document/enforce that only tokens with a fixed, verified decimals value are supported for ERC20 emulation, rejecting transfers to tokens whose decimals don't match the assumed convention.

### Proof of Concept
1. Deploy a NEP-141 token with `decimals = 6` (e.g., USDC-style) as the `target` for `rlp_execute`.
2. Construct an RLP-encoded Ethereum transaction with data `ERC20_TRANSFER_SELECTOR || abi.encode(to, value)` where `value` is chosen per an 18-decimal-assuming wallet (e.g., "1.0 token" = `10^18`). [1](#0-0) 
3. Submit via `rlp_execute`; the wallet contract calls `ft_transfer` with `amount = "1000000000000000000"` verbatim, i.e., 10^12 times the intended 1,000,000 (6-decimal) unit amount, moving far more of the token than the user intended — demonstrating the unaccounted decimals mismatch causes incorrect (and here, unauthorized-scale) value movement.
