### Title
Replay verification silently ignores state/hot-state/position checkpoint hashes, allowing corrupted state roots to pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative check used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/cli/src/commands.rs`) to confirm that locally re-executed transaction results match the authenticated `TransactionInfo` committed in the ledger's transaction accumulator. It only compares status, gas used, write-set hash (`state_change_hash`), and event root hash. It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the three fields that authenticate the actual Merkle state root(s) produced by the transaction.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`. The function's own comment admits the gap: [2](#0-1)  states that the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`) are ignored, so "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole verification oracle used by two production replay/audit tools:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` per transaction to decide pass/fail: [3](#0-2) .
- `aptos-move/cli/src/commands.rs`'s system-transaction replay path, which likewise treats a passing `ensure_match_transaction_info` call as proof the replay matched: [4](#0-3) .

Because the write set hash check only covers the *value writes* portion (`state_change_hash`), any divergence that only manifests in the Jellyfish Merkle / sparse-Merkle state root, the hot-state root, or the native-position state root at a checkpoint boundary — e.g. from a bug in `DoStateCheckpoint`'s root computation (`execution/executor/src/workflow/do_state_checkpoint.rs`), a JMT commit bug, or a `NativeStateCommitter`/position pipeline defect (`storage/aptosdb/src/native_state_committer.rs`, `storage/aptosdb/src/db/aptosdb_native_position.rs`) — will not be caught by `execute_and_verify`/replay-verify even though it corrupts the authenticated, consensus-committed state root that downstream light clients, state-proof consumers, and bootstrapping nodes rely on.

### Impact Explanation
This breaks the "proof and storage pivot" invariant that replay/verification paths must independently confirm committed state matches the correct VM result. A silent state-root divergence (whether from a latent bug in the new `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` code paths, storage corruption, or non-determinism) in the checkpoint hash fields would go undetected by the primary automated tool operators use to catch exactly such corruption in mainnet archives, letting a corrupted ledger state be reported as "verified" and potentially propagate through backup/restore or downstream systems that trust replay-verify's pass result.

### Likelihood Explanation
The likelihood of the checkpoint hash actually diverging depends on other, separate bugs; but the gap is triggered automatically and silently any time `ensure_match_transaction_info` is invoked on a transaction with a checkpoint hash (state, hot-state, or position). The code comment explicitly flags this as needing a fix "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`", i.e., the authors are aware this must be closed before the native-trading state-root feature is safe to rely on for verification.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s recomputed `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` (when the transaction is a checkpoint boundary) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()`, mirroring the treatment already given to `state_change_hash` and `event_root_hash`, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are relied upon in production replay-verify flows.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1` and `HOT_STATE_ROOT_IN_TXN_INFO` (or `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) on a chain, producing `TransactionInfoV1` entries with populated `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
2. Introduce (or trigger, via an independent bug) a state root divergence that only affects the hot-state or position-state Merkle root at a checkpoint transaction, while leaving the write set, events, gas, and status unchanged.
3. Run `storage/db-tool/src/replay_on_archive` (or `aptos move replay` for a system transaction) against the archive covering that version.
4. Observe that `execute_and_verify`/`ensure_match_transaction_info` reports success for the transaction because it never compares the checkpoint hash fields, even though the recomputed state root differs from the authenticated one in `TransactionInfo`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
