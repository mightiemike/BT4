### Title
Repeated `FreezeBalanceContract` calls silently reset the unlock time of an account's entire previously-frozen balance - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.execute()` (the legacy TRON Power v1 freeze path) merges a new freeze request into the account's single existing `Frozen` record and always overwrites its `expireTime` with the newly computed `now + duration`, regardless of how much of the previous lock period had already elapsed. This is structurally the same bug class as the VaderBond report: a "deposit" (here, a freeze) that adds to an existing position overwrites the stored unlock/vesting timestamp instead of preserving or independently tracking the prior schedule, forcing the depositor's *entire* balance — including the portion that was close to becoming withdrawable — to wait out a brand-new lock period.

The underlying capsule mutator `setFrozenForBandwidth` (and its Energy/TronPower analogs) stores only a single `Frozen` entry per resource and always replaces it in place, overwriting the previous `expireTime`: [3](#0-2) 

Because there is only one `Frozen` record per resource type, and every new freeze transaction unconditionally rewrites its `expireTime` to `now + newDuration`, any previously accumulated frozen balance — even balance that was about to become unlockable — has its unlock time pushed out to match the newest freeze. There is no validation in `FreezeBalanceActuator.validate()` that compares the new expiry against the remaining time of the existing lock (unlike `DelegateResourceActuator`, which explicitly calls `validRemainTime()` to reject a delegate-lock renewal that would shorten the existing unlock date — showing the team is aware such checks are needed for this exact class of issue, but it is absent here for self-freezing).

### Impact Explanation
A user who has an existing frozen balance nearing its unlock time and submits a new `FreezeBalanceContract` transaction (even a small top-up) will have the unlock time for their *entire* frozen balance for that resource silently reset to the new, later expiry. This mirrors the VaderBond issue where a deposit resets the entire vesting schedule for previously-accrued, soon-claimable funds — the user loses the ability to unfreeze/withdraw funds they could otherwise have redeemed shortly, and must wait out the full new lock duration for the combined balance. This is a state-corruption/accounting issue affecting fund availability rather than fund loss, matching the "informational/acknowledged" severity of the original report.

### Likelihood Explanation
Any account holder can trigger this unintentionally by freezing again (e.g., topping up bandwidth/energy) before their existing freeze expires — this requires no privileged access and is reachable via a standard broadcast `FreezeBalanceContract` transaction. It is highly likely to occur incidentally in normal usage patterns (users freeze more TRX periodically without realizing it resets the shared unlock clock for the whole pooled balance).

### Recommendation
- Track frozen balance and expiry per freeze operation (or track the earliest/individual unlock schedule) instead of a single merged `Frozen` record with one shared `expireTime`, similar to how the V2 model (`FreezeBalanceV2Contract` / `UnfreezeBalanceV2Contract`) already separates freezing from a list-based unfreeze schedule.
- At minimum, add validation analogous to `DelegateResourceActuator.validRemainTime()` that prevents/resets the unlock date only when it does not reduce previously accrued unlock eligibility, or clearly document/warn (as the Vader team did) that repeated freezing resets the unlock time for the full balance.

### Proof of Concept
1. User calls `FreezeBalanceContract` for `BANDWIDTH` with `frozenDuration = 3` days. `expireTime = now + 3 days` is stored via `setFrozenForBandwidth`.
2. 2 days and 23 hours later (just before unlock), the user calls `FreezeBalanceContract` again for the same resource with a small additional amount and `frozenDuration = 3` days.
3. `FreezeBalanceActuator.execute()` computes `newFrozenBalanceForBandwidth = frozenBalance + accountCapsule.getFrozenBalance()` and calls `accountCapsule.setFrozenForBandwidth(newFrozenBalanceForBandwidth, expireTime)` with the new `expireTime = now + 3 days`.
4. `setFrozenForBandwidth` overwrites the single stored `Frozen` record, so the original balance that was ~1 hour from being unfreezable now has its unlock time reset to a full new 3-day period along with the newly added amount — reachable purely via a normal broadcast transaction with no special privileges.

    Frozen newFrozen = Frozen.newBuilder()
        .setFrozenBalance(frozenBalance)
        .setExpireTime(expireTime)
        .build();

    long frozenCount = getFrozenCount();
    if (frozenCount == 0) {
      setInstance(getInstance().toBuilder()
          .addFrozen(newFrozen)
          .build());

      setInstance(getInstance().toBuilder()
