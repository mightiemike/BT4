## Local finding: replay-verify silently ignores authenticated position-state divergence

### Title
`TransactionOutput::ensure_match_transaction_info` omits the `position_state_checkpoint_hash` (and hot-state) comparison, letting replay-verify tooling accept a corrupted native-position state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant check used by replay/debugger tooling to confirm that a locally re-executed transaction reproduces the authenticated on-chain `TransactionInfo`. When `TransactionInfoV1`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled, `TransactionInfoV1` carries a `position_state_checkpoint_hash` field that is consensus-verified as part of block commitment, but the comparator function explicitly does **not** check it (nor the `hot_state_checkpoint_hash`), per its own TODO comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates status, gas, write-set hash, and event root hash against a given `TransactionInfo`, but explicitly skips the state-checkpoint, hot-state-checkpoint, and `position_state_checkpoint_hash` fields: [2](#0-1) 

This is called from `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `execution/executor/src/chunk_executor/mod.rs`. These are exactly the "replay" and audit paths the task scope calls out as in-scope ("Hard-fork-only divergence during commit, replay, restore, or proof verification").

The `position_state_checkpoint_hash` is a real, consensus-authenticated root: it is computed in `DoStateCheckpoint::compute_position_checkpoint` [3](#0-2)  and folded into `TransactionInfoV1` via `assemble_transaction_infos` [4](#0-3) , which becomes part of the transaction-info hash committed into the transaction accumulator and thus into the `LedgerInfo` signed by validators. So a bug in the native-position tree computation (e.g. in `ProvablePositionStateSummary`, the `NATIVE_POSITION`/`NATIVE_ORDERBOOK`/`NATIVE_COLLATERAL` write paths, or the position JMT/pruner) would change this root — but the tool that is supposed to catch exactly this kind of divergence between "authenticated chain state" and "locally recomputed state" is blind to it.

### Impact Explanation
Because `ensure_match_transaction_info` is the terminal correctness check used by `replay_on_archive` and the Aptos debugger to assert "local execution reproduces the authenticated ledger", any real corruption of the native-position/trading-native state tree (wrong root due to a computation bug, a missed write, or a storage/restore inconsistency) will pass replay-verify undetected. This directly matches the state-integrity gate's "Wrong accumulator root, Merkle proof, transaction proof… accepted as valid" and "Authenticated API or state-view output bound to the wrong version, object, or proof context" categories, since the tool reports a match even though the authenticated `position_state_checkpoint_hash` differs from what was actually recomputed. This masks state corruption from operators/auditors relying on replay-verify to detect chain-state divergence (a precursor to detecting/avoiding a hard fork), rather than corrupting the ledger itself (the committed root itself is still checked at commit time in `verify_chunk_result`/accumulator construction) — the impact is specifically in the audit/replay integrity guarantee, not double-committing bad state through consensus.

### Likelihood Explanation
This gap is unconditional whenever `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled and someone runs `replay_on_archive` or the debugger against history containing native-position/hot-state activity — no attacker action is needed to trigger the blind spot itself, only a separate (even accidental) computation bug in the trading-native/hot-state subsystem needs to exist for it to go unnoticed. The code's own TODO comment confirms the authors are aware the check is incomplete and plan to fix it "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS," i.e., they self-identify this as a real gap that must be closed prior to mainnet activation of the feature.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on `txn_info`) against locally recomputed values, and thread the corresponding checkpoint hashes into the callers (`replay_on_archive`, `aptos_debugger`, chunk executor). Until this is done, `COMPUTE_TRADING_NATIVE_STATE_ROOTS` should not be treated as fully replay-verifiable in production tooling.

### Proof of Concept
Not independently exploitable by an unprivileged actor to corrupt committed state — this is a detection/audit gap, not a consensus bug. Demonstration path: enable `COMPUTE_TRADING_NATIVE_STATE_ROOTS` + `TRANSACTION_INFO_V1`, introduce (or have) a divergence in the native-position tree computation between two executions of the same transaction (e.g., differing `ProvablePositionStateSummary` base), then run `replay_on_archive`/`aptos-debugger` replay over that version range — `ensure_match_transaction_info` will report success despite `position_state_checkpoint_hash` differing, because the comparator never inspects that field [5](#0-4) .

Note: I could not fully trace whether `execution/executor/src/chunk_executor/mod.rs`'s call site independently re-validates `position_state_checkpoint_hash` elsewhere (e.g., via `verify_chunk_result` in `chunk_result_verifier.rs`) before invoking `ensure_match_transaction_info`, since my final tool calls to inspect that file and confirm line context were cut off by the iteration limit. If that call site does perform the check via `known_position_state_checkpoints` comparison in `DoStateCheckpoint` (as the earlier `chunk_executor/mod.rs` snippet suggests it does, via `maybe_known_position_state_checkpoints`), then the state-sync/chunk-execution commit path itself is likely safe, and the confirmed gap is isolated to the offline replay/debugger tooling (`replay_on_archive`, `aptos-debugger`, `cli/src/commands.rs`) — which is still in scope per the task's "replay" category but has lower severity than a commit-time gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
