### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verification report false success on a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to check that a locally re-executed transaction matches an authoritative `TransactionInfo` obtained via proof/replay data. It validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that commit to the resulting state/hot-state/native-position Merkle roots. The developers left an explicit TODO admitting this gap.

### Finding Description
`ensure_match_transaction_info` is defined and documented as verifying that a `TransactionOutput` matches its `TransactionInfo`: [1](#0-0) 

It checks `status`, `gas_used`, and `state_change_hash` (write-set hash) and `event_root_hash`, but its own comment states: [2](#0-1) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

`state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` are real fields of `TransactionInfo` and are populated from the actual computed state/hot-state/position Merkle roots during normal block execution: [3](#0-2) 

These checkpoint hashes are part of the authenticated `TransactionInfo` that is hashed into the transaction accumulator and ultimately signed by validators in the `LedgerInfo`. The comparator function is the one place designed to catch a *local* divergence from that authenticated value when re-executing/replaying against a proof (used by `aptos-move/cli/src/commands.rs` replay tooling, and by db-tool's `replay_on_archive`). Because the comparator omits the checkpoint-hash fields, a divergence between the locally computed state/hot-state/native-position root and the authenticated one will not be flagged as a mismatch — the tool will report the replay as successful even though the resulting ledger state differs from the correct value.

### Impact Explanation
This directly weakens the proof/state-commitment integrity guarantee that replay and verification tooling must catch: "committed state that differs from the correct VM result... or corrupts durable ledger data" and "replay paths ... must not reinterpret committed data into a different ledger state." If a bug in state/hot-state/native-position root computation exists elsewhere in the code (e.g., in the trading-native/`compute_trading_native_state_roots` feature path gated by `types/src/on_chain_config/aptos_features.rs` and consumed in `execution/executor/src/block_executor/mod.rs` and `storage/aptosdb/src/db/aptosdb_reader.rs`), replay-verification tooling built on `ensure_match_transaction_info` cannot detect it, since the very field meant to catch that divergence is never compared. This is a genuine gap in an authenticated-response/verification invariant, though its blast radius is currently scoped to the not-yet-fully-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/native-position feature and to off-chain replay/audit tooling rather than to live consensus (validators still independently compute and sign the correct `TransactionInfo` hash, so the accumulator/consensus proof itself is not directly forgeable by this gap alone).

### Likelihood Explanation
The comparator is unconditionally missing this check today — it doesn't need an attacker to trigger; any latent bug in the (currently opt-in) native-position/hot-state root computation, or a malicious full node serving replay data through `db-tool` outputs, silently passes verification. The likelihood of the checkpoint-hash divergence itself occurring depends on the correctness of the still-gated `compute_trading_native_state_roots` path, but the detection gap is unconditional and present now.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed equivalents (mirroring the logic in `do_ledger_update.rs`'s `assemble_transaction_infos`) before the trading-native/native-position state-root feature is enabled, exactly as the existing TODO recommends.

### Proof of Concept
1. Enable (or simulate) `compute_trading_native_state_roots`/native-position state roots so that `TransactionInfo` carries a real `position_state_checkpoint_hash` (see `types/src/transaction/mod.rs` builder_v1 fields and `do_ledger_update.rs` lines 95-121).
2. Introduce (or have present) a bug in native-position/hot-state root computation such that the locally computed root differs from the authoritative one already committed in the signed `TransactionInfo`/accumulator.
3. Run the replay-verify tool (`db-tool`'s `replay_on_archive`, or the CLI paths in `aptos-move/cli/src/commands.rs` that call `ensure_match_transaction_info`) against real chain data.
4. Because `ensure_match_transaction_info` never compares the checkpoint hash fields, the tool reports the replay as a match/success even though `self.write_set`/state-root divergence occurred — silently corrupting the guarantee that replay-verify tooling detects ledger-state divergence.

Note: I was unable to open the exact call sites inside `aptos-move/cli/src/commands.rs` (only the file header was retrievable via the available tools before the iteration budget ran out), so the precise line numbers of the CLI call sites are not confirmed — only that `ensure_match_transaction_info` is referenced twice in that file per `grep_search`. This does not affect confidence in the root-cause gap in `types/src/transaction/mod.rs`, which is confirmed directly from source and its own TODO comment.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
