## Analysis

The reported bug class is a *weighted-average recomputation that always rounds toward the value that benefits the party executing the update*, exploitable by repeatedly forcing the update with many small fills so the rounding error accumulates into a material drift.

The closest concrete analog in `Thankgoddavid56/java-tron--031` is the `windowSize` weighted-average merge used by the bandwidth/energy resource accounting engine.

### Title
Floor-rounding in the bandwidth/energy `windowSize` weighted-average merge lets an account drift its resource-recovery window downward, granting itself faster free-resource recovery - ([File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java])

### Summary
`ResourceProcessor.getNewWindowSize()` recomputes an account's `windowSize` (the time-window over which consumed bandwidth/energy "usage" decays back to zero, i.e., the rate at which free network resources are replenished) as a usage-weighted average of the account's existing window and an incoming window contributed by a delegation/transfer. Just like the `open_price` bug in the external report, this weighted-average is computed with integer division that truncates toward zero (floor), and — unlike every *other* weighted-average/decay computation in the very same file — this truncation is **not** protected by the ceiling-rounding ("harden") logic that the file otherwise consistently applies.

### Finding Description
`getNewWindowSize` implements exactly the same mathematical shape as the vulnerable `open_price` update:

```
new_open_price = (p0 * s + pn * f) / (s + f)          // external report
newWindowSize  = (lastUsage*lastWindowSize + usage*windowSize) / newUsage   // java-tron
``` [1](#0-0) 

Both the legacy path and the "hardened" `BigInteger` path truncate the division (floor), even though every neighboring rounding-sensitive computation in the same class (`divideCeil`/`divideCeilExact` in `increase`, `increaseV2`, `unDelegateIncreaseV2`) deliberately rounds *up* specifically to avoid favoring the caller: [2](#0-1) [3](#0-2) 

`getNewWindowSize` is reached from two unprivileged, user-triggerable paths:

1. Every normal resource-consuming transaction, via `increase(AccountCapsule, ...)` when `supportUnfreezeDelay()` is active — the window is recombined on essentially every transaction that spends bandwidth/energy: [4](#0-3) 

2. `unDelegateIncrease`, called from `UnDelegateResourceActuator` and the TVM native `UnDelegateResourceProcessor`, both of which are ordinary account-level actuators/contracts: [5](#0-4) [6](#0-5) [7](#0-6) 

A smaller `windowSize` makes recorded usage decay ("recover") faster, since decay in `increase()` is computed as `(windowSize - delta)/windowSize`: [8](#0-7) 

So systematically truncating `newWindowSize` downward biases the account toward *faster* free-bandwidth/energy replenishment than the correct weighted average would produce — the same direction of benefit as the `open_price` bug (lower value = advantage to the actor performing the update). As with the original PoC, this can be driven by many small delegate/consume/undelegate operations rather than one large one, letting the rounding-favorable remainder accumulate call after call.

### Impact Explanation
This is an invalid-state/accounting divergence in the free-resource (bandwidth/energy) model that underlies TRON's fee-avoidance mechanism: bandwidth and energy quotas are the mechanism by which normal transactions avoid burning TRX. A `windowSize` that drifts below its true weighted-average value causes usage to decay faster than intended, letting an account recover free bandwidth/energy sooner than the protocol design allows — effectively underpricing consumption of a public, shared resource (`totalNetWeight`/`totalEnergyWeight` accounting is a zero-sum shared pool). This does not directly steal funds, but it corrupts deterministic state that other nodes must agree on and lets an attacker extract more free resource capacity than entitled, at the expense of the shared resource pool/other stakers.

### Likelihood Explanation
The affected code path (`increase()` under `supportUnfreezeDelay()`, and `unDelegateIncrease`) is exercised by completely ordinary, unprivileged operations (regular transactions consuming bandwidth/energy, and `UnDelegateResource`/TVM `unDelegateResource`), requiring no special privilege. The drift per call is small (bounded by `1/newUsage`), so meaningful exploitation requires many repeated small operations, mirroring the original report's "spamming purposefully crafted transactions" caveat — this raises cost but does not eliminate viability, especially for energy/bandwidth delegation which is cheap to repeat.

### Recommendation
Change `getNewWindowSize` to round in the direction that disfavors the account being updated (ceiling), consistent with the `divideCeil`/`divideCeilExact` helpers already used elsewhere in `ResourceProcessor.java` for the same reason:
```java
// hardened path
BigInteger[] dr = bi.divideAndRemainder(BigInteger.valueOf(newUsage));
return dr[1].signum() > 0 ? dr[0].longValueExact() + 1 : dr[0].longValueExact();
// legacy path: use divideCeil(...) instead of plain integer division
```

### Proof of Concept
Analogous to the reported Rust PoC: repeatedly delegate a small amount of bandwidth/energy to a receiver and then call `UnDelegateResource` for a small `transferUsage` many times in succession (or repeatedly trigger ordinary bandwidth/energy consuming transactions while `supportUnfreezeDelay` is enabled). Each call recomputes:
```
newWindowSize = floor((ownerUsage*remainOwnerWindowSize + transferUsage*remainReceiverWindowSize) / newOwnerUsage)
``` [9](#0-8) 
Because the division always truncates, `newWindowSize` is systematically ≤ the true weighted average; after many repetitions the cumulative shortfall meaningfully lowers the account's `windowSize`, accelerating its usage decay beyond the intended rate — the same "drift low through spamming small transactions" pattern from the original report, applied to TRON's resource-window accounting instead of a perp `open_price`.

  private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,
      long windowSize, long newUsage) {
    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(lastUsage).multiply(BigInteger.valueOf(lastWindowSize))
          .add(BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize)));
      return bi.divide(BigInteger.valueOf(newUsage)).longValueExact();
    }
    return (lastUsage * lastWindowSize + usage * windowSize) / newUsage;
  }

    BigInteger[] divRem = numerator.divideAndRemainder(denominator);

    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
