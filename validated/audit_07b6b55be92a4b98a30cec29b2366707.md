### Title
`ensure_match_transaction_info` never validates the state-checkpoint/root hashes, letting `replay-verify` accept an execution that diverges from the authenticated ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness gate used by replay/debug tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a freshly re-executed `TransactionOutput` matches the authenticated `TransactionInfo` pulled from an already-committed/backed-up ledger. It checks status, gas used, write-set hash, and event root hash, but it deliberately skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually commit to the resulting state tree/root. The code even carries a `TODO` acknowledging this gap.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates status, gas, write-set hash and event root hash against `txn_info`, but its trailing comment explicitly states the comparator ignores the checkpoint hashes: [2](#0-1) 

This function is the actual enforcement point used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` to decide pass/fail for each replayed transaction: [3](#0-2) 

It is also used by `aptos-debugger`'s `print_mismatches` path when comparing locally re-executed output against a `TransactionInfo` fetched from a validator/REST interface: [4](#0-3) 

Because `state_checkpoint_hash` (and, when V1 is active, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) is never compared, a locally recomputed execution whose final state root diverges from the value bound into the archived, ledger-info-signed `TransactionInfo` will still be reported as "matching" as long as write set bytes, events, gas and status happen to agree. This breaks the proof/commitment invariant that replay-verify is supposed to enforce: the tool's job is specifically to confirm that local computation reproduces the authenticated state root, and this is the one root-hash field it does not check.

### Impact Explanation
`replay-verify` (`db-tool replay-on-archive`) is the primary tool node operators, the Foundation, and auditors use to detect state divergence bugs (e.g., a JMT/state-tree computation bug, an incorrectly ordered write, or a nondeterministic Move execution path) between a new binary and already-committed, backup-derived ledger history. Because the state/hot-state/position checkpoint hashes are excluded from the comparison, a state-root-divergence bug in a candidate release could pass replay-verify with zero errors even though the resulting state tree is wrong. This directly undermines the "authenticated response bound to correct root" invariant called out by the state-integrity gate: a divergent state proof root would be accepted as "verified" by the one tool built to catch exactly that class of corruption before it reaches mainnet.

### Likelihood Explanation
This is not a hypothetical edge case — the comparator is unconditionally missing this check for every invocation, not gated behind a rare condition, and the code's own `TODO` documents that `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-style validation needs to be added before it can be trusted. Any bug introduced elsewhere in state-checkpoint computation (state tree, hot-state tree, or the new position-state tree) that happens to leave the write set, events, gas, and status unchanged would be silently missed. Given how central replay-verify is to catching consensus-affecting divergence prior to deployment, the likelihood of this exact blind spot mattering during a future regression is realistic, though it requires a separate root-cause bug in state-root computation to actually trigger observable harm (i.e., this weakness on its own does not corrupt state, but it removes the safety net that would otherwise catch such corruption before it is committed by real validators).

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality of `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` against the recomputed values (recomputed the same way `execution/executor/src/workflow/do_ledger_update.rs::assemble_transaction_infos` derives them), or otherwise require callers to supply the recomputed checkpoint hash(es) and fail loudly if they diverge from the authenticated `TransactionInfo`. At minimum, gate `replay_on_archive` and `aptos-debugger` on this stricter check before it is used to certify new releases against mainnet history.

### Proof of Concept
1. Run `db-tool replay-on-archive` against an archived range of mainnet history using a build that contains a hypothetical bug only affecting state-tree assembly (e.g. an incorrect state-checkpoint root computed in `DoStateCheckpoint`) while leaving write sets, events, gas, and status identical.
2. `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs:392` calls `ensure_match_transaction_info`, which — per `types/src/transaction/mod.rs:2139-2203` — never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
3. The tool reports zero verification failures for the affected range even though the locally computed state root diverges from the one bound into the ledger-info-signed `TransactionInfo`, demonstrating that the replay-verify invariant ("recomputed state matches the authenticated state root") is not actually enforced.

Note: I was not able to independently confirm within the given tool budget whether any other code path (outside this comparator) performs an equivalent state-root check during `replay_on_archive`/`aptos-debugger` runs; if such a check exists elsewhere it would mitigate this finding, but no such check was found in the reachable call sites (`replay_on_archive.rs`, `aptos_debugger.rs`, `cli/src/commands.rs`) during this review.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
