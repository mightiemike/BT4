### Title
Market contract hardcodes deprecated Pyth oracle contract addresses with no migration path when Pyth infrastructure is upgraded - ([File: local-testing/contracts/market/market.clar])

### Summary
`market.clar` resolves Pyth prices by calling hardcoded, literal contract references (`.pyth-storage-v4`, `.pyth-oracle-v4`, `.pyth-pnau-decoder-v3`) baked directly into `call-pyth` and `write-feed`. Meanwhile, `pyth-governance-v3.clar` explicitly supports migrating each of these components (`update-pyth-oracle-contract`, `update-pyth-decoder-contract`, `update-pyth-storage-contract`) via VAA-governed execution-plan updates. If Pyth migrates its infrastructure to new contract versions, `market.clar` has no function to update its hardcoded references and will keep querying the deprecated, no-longer-updated contracts indefinitely, exactly mirroring the `CurveConvex2Token` immutable-reward-pool defect in the referenced report.

### Finding Description
`write-feed` submits price-feed updates to a hardcoded proxy/storage/decoder/wormhole set: [1](#0-0) 

`call-pyth`, used by every price resolution, reads from a hardcoded `.pyth-storage-v4` reference: [2](#0-1) 

There is no `update-oracle`/`set-oracle` public function anywhere in `market.clar` to change these bound addresses; a `grep` across the market contract for oracle-address setters returns no results. In contrast, `pyth-governance-v3.clar` maintains a mutable `current-execution-plan` var and exposes governance-gated functions to migrate each component when Pyth deprecates a contract version: [3](#0-2) [4](#0-3) 

This is the same structural defect as H-5: an upstream system (Pyth/Convex) exposes a proper migration mechanism, but a downstream consumer contract (`market.clar`/`CurveConvex2Token`) binds to the old dependency's address as an immutable/hardcoded reference rather than reading it dynamically, so the consumer's behavior silently diverges from the new canonical state the moment the upstream migrates. All price freshness validation in `price-resolve` depends on this hardcoded call succeeding and returning fresh data: [5](#0-4) 

### Impact Explanation
Once Pyth deprecates `pyth-storage-v4`/`pyth-oracle-v4`/`pyth-pnau-decoder-v3` in favor of new versions, that old contract stops receiving fresh price pushes from the network. `market.clar` keeps calling only the old, stale contract. `price-resolve` enforces `oracle-timestamp-fresh` against `max-staleness`, so once staleness is exceeded every price-dependent call reverts with `ERR-ORACLE-INVARIANT`: [6](#0-5) 

Any operation requiring price resolution (borrow, liquidation, health checks) becomes permanently blocked since `market.clar` has no migration path and is not upgradeable in place. This traps under-collateralized/at-risk positions from being liquidated (protocol insolvency risk) and blocks new borrows indefinitely — a permanent freezing of protocol functionality dependent on price data.

### Likelihood Explanation
Requires only the external precondition that Pyth deprecates its current oracle/storage/decoder contract set and migrates to new versions — a realistic, foreseeable event given that `pyth-governance-v3.clar` was purpose-built to handle exactly this migration scenario. No attacker action or privileged compromise is needed; it is triggered by ordinary protocol evolution on Pyth's side.

### Recommendation
Replace the hardcoded `.pyth-storage-v4`/`.pyth-oracle-v4`/`.pyth-pnau-decoder-v3` contract references in `market.clar`'s `call-pyth` and `write-feed` with DAO-updatable data-vars (mirroring the mutable `current-execution-plan` pattern in `pyth-governance-v3.clar`), and add a governance function to update them so the market can be migrated in lockstep with any Pyth infrastructure upgrade.

### Proof of Concept
1. Pyth governance calls `update-pyth-storage-contract` (or `update-pyth-oracle-contract`/`update-pyth-decoder-contract`) on `pyth-governance-v3.clar`, moving `current-execution-plan` to new contract instances. [4](#0-3) 
2. Price feed updates now flow only to the new storage contract; the old `.pyth-storage-v4` referenced by `market.clar` no longer receives updates.
3. `market.clar`'s `call-pyth` continues to `contract-call?` the old `.pyth-storage-v4` because the reference is hardcoded, not read from the governance execution plan. [2](#0-1) 
4. Once the returned price timestamp exceeds `max-staleness`, `price-resolve`'s `oracle-timestamp-fresh` check fails and every borrow/liquidate call reverts with `ERR-ORACLE-INVARIANT`, freezing those operations with no on-chain remediation available in `market.clar`. [7](#0-6)

(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
