### Title
Off-chain accounts lt-hash update path silently corrupts the accounts lattice hash on duplicate pubkeys in release builds - ([File: runtime/src/bank/accounts_lt_hash.rs])

### Summary
`Bank::enqueue_off_chain_accounts_lt_hash_updates` only checks for duplicate pubkeys in the input batch when `cfg!(debug_assertions)` is true. In a release/production validator build the duplicate check compiles out entirely, and any caller that passes a `StorableAccounts` batch containing the same pubkey twice will silently mix the account's lt-hash contribution in/out multiple times, corrupting the accounts lattice hash without any error or revert.

### Finding Description
This mirrors the USDT `approve()` bug class: a function assumes a precondition ("no duplicates in the input") holds, and rather than defensively enforcing/deduplicating it at all times, it only *asserts* the precondition under a build flag that is disabled in production. When the precondition is violated in production, the operation still proceeds and silently produces wrong accumulated state instead of failing loudly (the USDT analog: the second `approve()` call reverts instead of being handled defensively; here, the analog is inverted but equally dangerous — the check that *would* catch the problem is simply absent in the build that matters).

`enqueue_off_chain_accounts_lt_hash_updates` explicitly documents the precondition it depends on: [1](#0-0) 

The duplicate detection is gated entirely behind `cfg!(debug_assertions)`: [2](#0-1) 

When no duplicate check runs (release build), each occurrence of the same pubkey in `accounts` independently loads the "previous" on-disk/cache version and mixes it out, then mixes the "current" batch version in: [3](#0-2) 

Because `prev_account` is loaded fresh via `load_with_fixed_root_do_not_populate_read_cache` for *each* occurrence of the duplicate pubkey (not just once), and the actual account write itself is deduplicated (or not) independently by the downstream `store_accounts_par`/write-cache path, a duplicate entry causes the lt-hash accumulator to `mix_out` the same previous value multiple times and/or `mix_in` different "current" values from different indices of the batch for the same pubkey — none of which matches what actually gets persisted. The result is an accounts lt-hash value that no longer matches the real account state, with **no panic, no error, and no visible symptom** in production.

The precondition itself is fragile: it's the caller's responsibility ("Callers must ensure there are no duplicates") in every code path that reaches this function, e.g.: [4](#0-3) 
including partitioned epoch-reward distribution, which builds a `Vec<StakeReward>` (indexed by `stake_pubkey`) across a partition and stores it directly: [5](#0-4) 
and reward-commission account storage, which also stores a caller-provided vector of `(Pubkey, RewardInfo, AccountSharedData)` without dedup: [6](#0-5) [7](#0-6) 

If a future refactor, a bug in `hash_rewards_into_partitions`, or an off-chain snapshot/administrative code path ever produces a `StorableAccounts` batch with a repeated pubkey (e.g., a stake account appearing in a partition twice due to a partitioning bug, or a commission account also present in a stake-reward batch for the same slot), the release build will not catch it — the debug-only assertion is the *only* safety net, and the actual computation silently diverges from what was stored.

### Impact Explanation
This falls into the "hash/capitalization divergence" category described in the validation rules. The accounts lt-hash (lattice hash, used for the experimental accumulator-hash / incremental account-hash verification) is part of consensus-relevant, hash-checked state maintained per-`Bank`. Silent divergence between the value tracked in `self.accounts_lt_hash` and the true state of the accounts index/storage would:
- Cause `verify_accounts_lt_hash_at_startup`/related verification routines to fail unexpectedly on a healthy node (false-positive corruption detection), or
- Worse, if the divergence happens consistently for all validators following the same code path, it can propagate into snapshot verification and cross-node hash mismatches, undermining the guarantee the lt-hash is designed to provide.
Because the corruption is silent (no panic in release), it could persist for a long time before being discovered, unlike the debug build which panics immediately.

### Likelihood Explanation
Likelihood is low-to-moderate: the *documented* invariant (no duplicate pubkeys in a single `StorableAccounts` batch passed to this off-chain path) is currently believed to hold for existing callers (partitioned stake rewards keyed uniquely by `stake_pubkey`, single-account `store_account` calls, etc.). However:
- The safety net (the assertion) is entirely disabled in production, so any future regression, edge case (e.g., a stake account and a commission account happening to coincide, or a bug in reward partitioning producing a repeated index) would go undetected by validators running release binaries — exactly the class of "silent-until-it-isn't" bug the USDT report warns about (an implicit precondition that isn't actually enforced when it matters).
- This is a systemic design gap, not a narrow theoretical edge case: the check exists specifically because the author anticipated this could go wrong, yet chose to compile it out for the build most validators run.

### Recommendation
- Enforce the "no duplicate pubkeys" invariant unconditionally in production builds, not just under `cfg!(debug_assertions)`, or restructure the function to deduplicate defensively (mirroring `enqueue_on_chain_accounts_lt_hash_updates`, which explicitly deduplicates by iterating in reverse and tracking `seen_accounts`) rather than relying on caller-supplied guarantees.
- Alternatively, make `enqueue_off_chain_accounts_lt_hash_updates` itself dedupe accounts (keeping the last occurrence, matching the on-chain path's semantics) so correctness does not depend on every current and future caller manually upholding an undocumented-at-the-type-level invariant.

### Proof of Concept
Conceptual repro (cannot be executed here, but derivable from the code paths cited):
1. Construct a `StorableAccounts` implementation whose backing `Vec` contains the same pubkey at two different indices with two different `AccountSharedData` values (e.g., by directly calling `Bank::store_accounts` with a manually built slice containing a duplicate, bypassing normal transaction-processing dedup).
2. Build in release mode (`cfg!(debug_assertions)` = false).
3. Call `bank.store_accounts(...)` with the duplicated batch.
4. Observe that `enqueue_off_chain_accounts_lt_hash_updates` processes both entries: it mixes out the *same* previously-loaded value twice and mixes in two different "current" values, while `store_accounts_par` persists only the actual final on-disk value for that pubkey.
5. Compare `bank.accounts_lt_hash` after `finish_accounts_lt_hash_updates()`/`freeze()` against `calculate_accounts_lt_hash_at_startup_from_index()` (the from-scratch recomputation used in tests such as `test_calculate_accounts_lt_hash_at_startup_from_index` at `runtime/src/bank/accounts_lt_hash.rs:740-782`) — the two values diverge, whereas in a debug build step 3 would instead panic with "duplicate accounts were enqueued for hashing".
