### Title
Unchecked EVM-level execution failure (`VmError`/revert) on `DerivedEVMCall`/`CallEVM` receipts treated as success across `x/uexecutor` accounting - (File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go, x/uexecutor/keeper/evm.go, x/uexecutor/keeper/outbound.go, x/uexecutor/keeper/execute_payload.go)

### Summary
Every call site that issues an EVM state-transition via `k.evmKeeper.DerivedEVMCall` / `CallEVM` (deposit PRC20, execute UEA payload, execute universal tx on a contract, refund unused gas, revert re-mint) only checks the Go-level `error` return value, never the returned `*evmtypes.MsgEthereumTxResponse`'s EVM-level failure indicator. This is the same class of bug as the reported SushiMakerAuction issue: a call that can "fail" without returning a Go error (an EVM-level revert reported only via the response object, analogous to an ERC20 `transfer()` returning `false` instead of reverting) is not checked, so the caller records `"SUCCESS"` PCTx/UTX state and proceeds with downstream accounting (outbound creation, gas refunds, revert suppression) even though the actual on-chain effect (mint, transfer, payload execution) did not happen.

### Finding Description
`DerivedEVMCall` and `CallEVM` are the sole primitives `x/uexecutor` uses to mutate EVM state as a module or on behalf of a user (see `DERIVED_TRANSACTIONS.md`, and `x/uexecutor/types/expected_keepers.go` lines 32-56 defining both methods only in terms of `(*types.MsgEthereumTxResponse, error)`). Throughout the keeper, every consumer of the returned receipt inspects only the Go `error`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

In none of these paths is the `MsgEthereumTxResponse` inspected for an EVM-level revert/failure indicator distinct from the Go `error`. A repository-wide search for `VmError`, `.Failed()`, `receipt.Failed`, `resp.Failed`, or `.Reverted` returns zero matches anywhere in `x/uexecutor` — the only "failure" concept the codebase recognizes is a non-nil Go `error` from `DerivedEVMCall`/`CallEVM`. Cosmos-evm's `MsgEthereumTxResponse` (the type imported as `evmtypes "github.com/cosmos/evm/x/vm/types"` here) carries a `VmError` field precisely so that callers can distinguish "the EVM message was applied but the inner call reverted" from "the call could not be applied at all" — `ApplyMessage`/`CallEVM` in cosmos-evm commonly return `err == nil` with `VmError` populated for ordinary EVM reverts (out-of-gas mid-execution, `require`/`revert` in the called contract, insufficient PRC20 balance during `transfer`, etc.), by design, so that gas-consumption and receipts can still be produced/observed. The Push Chain fork's `DerivedEVMCall` is explicitly built to always populate a real, observable receipt (see `DERIVED_TRANSACTIONS.md` lines 66-74) — which is only meaningful if callers actually read `VmError`/failure status from it, but none do.

The practical accounting effect:
- `depositPRC20` → `CallPRC20Deposit` → `DerivedEVMCall(... "depositPRC20Token" ...)`. If the module-sent `depositPRC20Token` call on `UniversalCore` internally emits a PRC20 mint via a low-level call that reverts inside a try/catch, or the whole tx reverts due to an internal `require` while `commit=true` still returns a receipt with `err==nil` and `VmError` set, `execute_inbound_funds_and_payload.go` line 176-177 marks `depositPcTx.Status = "SUCCESS"` purely because `execErr == nil`. The `UniversalTx`/`PCTx` state is now recording a successful mint that never happened — a corrupted canonical UTX / PRC20 accounting record.
- `ExecutePayloadV2` (`execute_payload.go` lines 40-56) calls `writeCache()` (committing EVM state) whenever `execErr == nil`, without checking whether the underlying `executeUniversalTx` call on the UEA reverted at the EVM level; the deposit above it is already committed regardless of whether the payload actually executed.
- `handleFailedOutbound` (`outbound.go` lines 119-146) treats `err == nil` from `CallPRC20Deposit` as `pcTx.Status = "SUCCESS"` for the re-mint-on-revert flow — if the mint silently fails at the EVM level, funds are recorded as returned to the user but are not, a permanent-loss scenario for the affected asset.
- `applyGasRefund` (`outbound.go` lines 223-253) records `refundPcTx.Status = "SUCCESS"` from `CallUniversalCoreRefundUnusedGas` under the same `err == nil` check.

### Impact Explanation
This falls under "corruption of PRC20 or native asset accounting, gas fee accounting, refund accounting... or canonical UniversalTx state" and potentially "permanent loss...of user or protocol-controlled funds" in the allowed impact gate. If any of the module-originated calls (`depositPRC20Token`, `executeUniversalTx`, `refundUnusedGas`) can revert at the EVM level without cosmos-evm's `CallEVM`/`DerivedEVMCall` surfacing that as a Go `error` — which is the standard, documented behavior of EVM `VmError` in this class of fork — then the on-chain `UniversalTx` ledger will diverge from actual PRC20/native balances: deposits marked `SUCCESS` that never credited the recipient, gas refunds marked `SUCCESS` that never paid out, and inbound-revert re-mints marked `SUCCESS` that left the user's funds unrecovered. Because `UniversalTx` is the canonical, validator-agreed record of crosschain state (per `app/README.md`), this false-success status is also what all honest nodes converge on, making the corrupted record part of consensus rather than a benign log discrepancy.

### Likelihood Explanation
Reachability requires no privileged actor: it is exercised on the default inbound/outbound execution path for any ordinary user deposit or payload (e.g. any `MsgVoteInbound`-driven `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload`, or any outbound voted via `MsgVoteOutbound` that triggers `handleFailedOutbound`/`applyGasRefund`). The trigger condition — an EVM-level revert inside a module-originated call that does not propagate as a Go error from `CallEVM`/`DerivedEVMCall` — depends on the exact semantics of the pinned `github.com/pushchain/evm` fork's `ApplyMessage` implementation, which I was not able to directly inspect in this indexed codebase (its source is external, in a `replace`-directed module, and not present in the index). I could not confirm with certainty whether this fork's `DerivedEVMCall`/`CallEVM` returns a non-nil Go `error` for every VM-level revert, or whether — like stock cosmos-evm and go-ethereum's `ApplyMessage` — it can return `err == nil` with a failure encoded only in the response object. Given zero code in this repository ever reads such a field, I judge the guard to be either absent or provided entirely by the external fork; this needs verification against the `pushchain/evm` fork's `DerivedEVMCall`/`CallEVM` implementation before treating it as a confirmed, currently-exploitable divergence.

### Recommendation
Confirm the exact failure-signaling contract of `github.com/pushchain/evm`'s `CallEVM`/`DerivedEVMCall` (whether `VmError`/equivalent is ever populated with `err == nil`). If so, every call site that records `PcTx`/`OutboundTx` status from a receipt (`execute_inbound_funds_and_payload.go`, `execute_inbound_gas_and_payload.go`, `execute_payload.go`, `outbound.go`, `evm_hooks.go`, `create_outbound.go`) must explicitly check the response's EVM-level failure/`VmError` field in addition to the Go `error`, and treat a reverted result identically to a returned error (mark `FAILED`, trigger the same revert/rescue/abort paths) rather than defaulting to `SUCCESS` whenever `err == nil`.

### Proof of Concept
Not constructible from this repository alone: exploitation depends on the internal revert behavior of `UniversalCore.depositPRC20Token` / `executeUniversalTx` / `refundUnusedGas` and on the un-inspectable `pushchain/evm` fork's `CallEVM`/`DerivedEVMCall` implementation returning `err == nil` on an EVM-level revert. A concrete PoC would require: (1) verifying that fork behavior, and (2) crafting an inbound/payload/outbound scenario where the target contract call reverts (e.g., insufficient allowance/balance inside `UniversalCore`, or a UEA payload that reverts mid-execution) while `DerivedEVMCall` still returns `nil` error, then confirming the resulting `UniversalTx.PcTx[].Status` is recorded `"SUCCESS"` while the corresponding PRC20/native balance did not change.
