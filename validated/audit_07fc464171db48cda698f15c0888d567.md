### Title
Attached deposit silently consumed on eth-implicit early-return in `AddressRegistrar::register` — (`runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary

`AddressRegistrar::register` is marked `#[payable]` and accepts an attached deposit, but the eth-implicit guard at line 42–46 returns `None` without reading `env::attached_deposit()` and without issuing a refund promise. Any deposit attached to that call is permanently retained by the contract.

### Finding Description

The function has two distinct paths that correctly handle deposits and two that do not:

**Correct — `Entry::Occupied` (collision) path** issues an explicit refund: [1](#0-0) 

**Broken — eth-implicit early-return path** returns before `attached_deposit()` is ever read: [2](#0-1) 

`env::attached_deposit()` is only called at line 52, which is unreachable when the eth-implicit branch fires: [3](#0-2) 

In NEAR, when a `#[payable]` function returns normally (no panic), the runtime does **not** auto-refund the deposit. The deposit is credited to the contract's account before execution begins and stays there unless the contract explicitly creates a transfer promise back to `predecessor_account_id`. The `Entry::Occupied` branch demonstrates the correct pattern; the eth-implicit branch omits it entirely.

The existing test for this path (`test_register_eth_implicit_account`) calls `register` with **no deposit**, so it does not exercise the loss path: [4](#0-3) 

### Impact Explanation

Any caller who attaches a non-zero deposit and passes an eth-implicit `account_id` permanently loses that deposit. The contract balance increases by the full deposit amount with no storage written and no refund issued. This is a direct, irreversible loss of funds for the caller.

### Likelihood Explanation

The function is `#[payable]` and the deposit check (lines 54–61) is positioned *after* the eth-implicit guard, so a reasonable caller reading the function signature would expect to need a deposit. A user who attaches the storage deposit before learning their account type is rejected will lose it. The path requires no privileges — any account can call `register` on the deployed address-registrar contract.

### Recommendation

Read `env::attached_deposit()` before the early return and issue a refund promise if the deposit is non-zero, mirroring the `Entry::Occupied` pattern:

```rust
if is_eth_implicit(&account_id) {
    env::log_str(&format!("Refuse to register eth-implicit account {account_id}"));
    let deposit = env::attached_deposit();
    if deposit.as_yoctonear() > 0 {
        let refund = env::promise_batch_create(&env::predecessor_account_id());
        env::promise_batch_action_transfer(refund, deposit);
    }
    return None;
}
```

### Proof of Concept

Call `register` with `account_id = "0x8fd379246834eac74b8419ffda202cf8051f7a03"` and `deposit = 1 NEAR`. The function logs the refusal and returns `None`. No refund promise is created. The contract's balance increases by 1 NEAR; the caller's balance decreases by 1 NEAR plus gas costs. The existing test at line 237 passes a zero-deposit call and therefore does not detect this.
