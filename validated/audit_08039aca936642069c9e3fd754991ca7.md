No vulnerability exists here — the codebase already enforces the invariant the question worries about, by construction rather than by chance.

### Why the described attack fails

The durable-nonce advance does not happen "as an instruction that executes last and could be starved of compute." It happens up front, during transaction validation, before instruction execution and before CU metering begins: [1](#0-0) 

`validate_transaction_nonce` loads the nonce account, verifies the stored durable nonce matches the transaction's `recent_blockhash`, and if valid, immediately advances the nonce account's in-memory state to the *next* durable nonce — this happens unconditionally as part of fee-payer/nonce validation, prior to program execution: [2](#0-1) 

This already-advanced `NonceInfo` is then captured into `RollbackAccounts` (via `RollbackAccounts::new`) at the point where the fee is deducted from the payer: [3](#0-2) 

Regardless of what happens afterward during actual instruction execution — including compute-unit exhaustion producing an `InstructionError` on the `AdvanceNonceAccount` instruction itself, or on any other instruction — the commit path unconditionally persists the pre-computed `rollback_accounts` (which contains the *already advanced* nonce state) whenever the execution result is `Err`: [4](#0-3) 

So there is no scenario where the fee is charged but the stored nonce blockhash remains unchanged — the nonce advance is bound atomically to the same rollback-accounts write that also charges the fee, and both are computed/staged before execution even starts. Calibrating filler instructions to exhaust CU exactly at the `AdvanceNonceAccount` instruction has no bearing on this, because that instruction's on-chain effect (advancing state) was already decided during pre-execution nonce validation — the runtime does not rely on the `AdvanceNonceAccount` system-program instruction actually executing successfully to know the nonce should advance; it treats nonce transactions specially.

### Confirmed by existing tests

This exact "fee charged but nonce should still advance despite instruction failure" scenario is already covered by bank-level regression tests, which explicitly assert the nonce changes and replay is rejected: [5](#0-4) [6](#0-5) 

The `NonceInfo` doc-comment itself states the design intent directly: [7](#0-6) 

Because the nonce-hash check and the nonce advance both occur in the same pre-execution validation step (`validate_transaction_nonce`), and because the resulting state is what's committed on any failure path (not the pre-advance state), there is no window where CU exhaustion on `AdvanceNonceAccount` can leave the old nonce hash intact while the fee is still charged. Replay with the identical transaction after such a failure correctly returns `TransactionError::BlockhashNotFound`, as demonstrated in the cited tests.
