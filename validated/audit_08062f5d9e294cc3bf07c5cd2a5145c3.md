## Title
Unbounded per-scan rebuild of `AccountStorageEntry::excluded_offsets()` from an ever-growing obsolete/tombstone list causes disproportionate CPU cost on every storage scan - (File: `accounts-db/src/account_storage_entry.rs`)

## Summary
`AccountStorageEntry::scan_accounts` and `scan_accounts_without_data` compute `excluded_offsets()` on every single call, which iterates over the *entire historical* `ObsoleteAccounts.accounts` `Vec` (accumulated via repeated `mark_accounts_obsolete` calls across many `clean_accounts()` cycles) plus the full `tombstone_offsets` set, and collects them into a fresh `IntSet` each time. Nothing bounds or amortizes the size of this list until the storage is finally shrunk or purged, so a storage that survives many clean/flush cycles while accumulating obsolete entries pays an ever-growing, unamortized cost on every scan of that storage (index generation, shrink, hash/snapshot read paths).

## Finding Description
`ObsoleteAccounts::mark_accounts_obsolete` only ever appends to `self.accounts` [1](#0-0) , and this vector is not compacted in place; it is rebuilt/reduced only when the storage entry itself is shrunk away or dropped (see `remove_dead_accounts`, which calls `mark_accounts_obsolete` repeatedly across successive `clean_accounts()` passes) [2](#0-1) .

Every time `AccountStorageEntry::scan_accounts` or `scan_accounts_without_data` is invoked, `excluded_offsets()` is recomputed from scratch by iterating `obsolete_accounts_read_lock().filter_obsolete_accounts(None)` (a full linear scan of the obsolete list) and extending it with the full `tombstone_offsets_read_lock()` set: [3](#0-2) 

This is analogous to the reported `projectCost()` bug: rather than maintaining a running/cached value that is updated incrementally as obsolete/tombstone entries are added, the code re-derives the full cost (here, the exclusion set) from the complete historical list on every read-path call, with no mechanism to cap it. Any slot/storage that stays alive across many `clean_accounts()` cycles (each of which can mark additional accounts obsolete in that storage while newer, superseding writes keep the slot from being fully purged) keeps growing this list, and every subsequent scan of the storage — used in index generation on restart (`generate_index_for_slot`, which calls `storage.scan_accounts`) [4](#0-3) , in shrink candidate collection [5](#0-4) , and in the snapshot/verification read path (`AccountStorageReader::new`, which separately duplicates similar obsolete/tombstone bookkeeping work) [6](#0-5)  — must redo the full-list work again.

The `sweep_slots_after_snapshot` logic explicitly documents that a storage is only purged once it becomes "only tombstones," meaning storages that are partially obsolete/tombstoned but still contain live accounts can persist across many clean cycles, continuing to accumulate obsolete/tombstone entries between shrinks [7](#0-6) .

## Impact Explanation
This causes disproportionate CPU cost: the per-scan cost of a storage entry grows with the total number of obsolete+tombstone entries ever recorded against it, not with the amount of work actually needed for the current scan. Because this function is on the hot path for account index generation at startup, shrink, and snapshot verification, a storage that accumulates many obsolete entries over its lifetime (through ordinary churn of accounts within a slot across repeated clean cycles before that slot's storage is finally shrunk) forces repeated, ever more expensive full-list rebuilds each time it is touched, rather than a single bounded cost.

## Likelihood Explanation
This requires ordinary account write/clean activity (not a privileged path) to accumulate a large `ObsoleteAccounts` vector on a storage entry that is not yet eligible for shrink/purge (e.g., because it isn't "only tombstones" yet, per the `sweep_slots_after_snapshot` gate). It does not require malicious input beyond generating enough account churn to grow the obsolete/tombstone lists before the storage is shrunk, which is a normal usage pattern rather than a crafted attack, making the growth path reachable but the per-call cost only becomes disproportionate once obsolete/tombstone lists become large relative to a fast repeated-scan cadence.

## Recommendation
Cache the computed exclusion set (or track alive/excluded byte and offset counts incrementally as entries are marked obsolete/tombstoned) on `AccountStorageEntry` instead of rebuilding the full `IntSet` from the entire historical `ObsoleteAccounts`/`tombstone_offsets` lists on every `scan_accounts`/`scan_accounts_without_data` call, updating the cached set incrementally in `mark_accounts_obsolete` / `batch_insert_tombstone_offsets` rather than at read time.

## Proof of Concept
Not concretely reproduced with a runnable exploit script (no terminal/execution access in this session); the analysis is based on static code tracing: `mark_accounts_obsolete` only appends [1](#0-0) , `remove_dead_accounts` invokes it repeatedly across `clean_accounts()` cycles [2](#0-1) , and `excluded_offsets()` unconditionally rebuilds the full set from these accumulated lists on every `scan_accounts` call [3](#0-2) .

    /// Collect the offsets that should be excluded from scans
    fn excluded_offsets(&self) -> IntSet<Offset> {
        let mut offsets: IntSet<_> = self
            .obsolete_accounts_read_lock()
            .filter_obsolete_accounts(None)
            .map(|(offset, _)| offset)
            .collect();
        offsets.extend(self.tombstone_offsets_read_lock().iter().copied());
        offsets
    }

    /// Iterate over the alive accounts in this storage, excluding obsolete accounts and tombstones.
    /// The return value is the number of values excluded from the scan.
    pub(crate) fn scan_accounts<'a>(
        &'a self,
        reader: &mut impl RequiredLenBufFileRead<'a>,
        mut callback: impl for<'local> FnMut(Offset, StoredAccountInfo<'local>),
    ) -> Result<u64, AccountsFileError> {
        let excluded_offsets = self.excluded_offsets();
        let mut num_excluded = 0;
        self.accounts.scan_accounts(reader, |offset, account| {
            if excluded_offsets.contains(&offset) {
                num_excluded += 1;
                return;
            }
            callback(offset, account);
        })?;
        Ok(num_excluded)
    }
