## Title
TRC10 Bancor-style Exchange pool deposits/withdrawals are susceptible to sandwich attacks due to missing slippage bounds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

## Summary
java-tron implements a legacy Bancor-formula constant-supply AMM for TRC10 token pairs (`ExchangeCapsule`, `ExchangeProcessor`/`SafeExchangeProcessor`). Any unprivileged account can trade against a pool via `ExchangeTransactionContract`/`ExchangeTransactionActuator`, which shifts the pool's `firstTokenBalance`/`secondTokenBalance` ratio and hence its spot price. The pool creator can add or remove liquidity via `ExchangeInjectContract`/`ExchangeWithdrawContract`. Unlike the trade actuator, which includes an `expected` minimum-output slippage-protection field, the inject/withdraw actuators compute the paired-token amount purely from the pool's on-chain balances at execution time, with no caller-supplied bound. This is architecturally identical to the AeraVaultV1 `deposit()`/`withdraw()` sandwich-attack bug class: an attacker can manipulate the pool's spot price immediately before the creator's inject/withdraw executes, and reverse the manipulation immediately after, extracting value at the creator's expense.

## Finding Description
`ExchangeInjectActuator.doValidate()`/`execute()` computes the second (paired) token amount required for an injection strictly from the exchange's current `firstTokenBalance`/`secondTokenBalance` ratio: [1](#0-0) 

There is no parameter in `ExchangeInjectContract` allowing the creator to bound the acceptable ratio or the resulting `anotherTokenQuant`, and no check that the pool balances have not changed within the same block: [2](#0-1) 

Similarly, `ExchangeWithdrawActuator` computes the paired-token payout strictly from the current pool ratio at execution time: [3](#0-2) 

Its validation only checks a fixed rounding-precision tolerance (`"Not precise enough"`), not a caller-supplied price bound: [4](#0-3) 

Meanwhile, any unprivileged account can shift the pool ratio by trading through `ExchangeTransactionContract`, which does have slippage protection (`expected`) for the *trader*, but that protection does nothing to protect the *counterparty inject/withdraw transaction* that gets sandwiched: [5](#0-4) [6](#0-5) 

The Bancor `exchange()` formula that determines the swap output, and thus the manipulable spot ratio, is defined here: [7](#0-6) 

This is the exact bug class from the external report: a legitimate participant (the pool "creator", analogous to the AeraVaultV1 "Treasury") submits a deposit/withdraw at the current spot price with no price bound; an attacker front-runs with a trade to skew the ratio, lets the deposit/withdraw execute at the skewed ratio, then back-runs to restore the ratio and pocket the difference.

## Impact Explanation
This is an accounting/settlement impact: the exchange creator can be forced to deposit an excessive amount of the paired token (inject) or receive a reduced amount of the paired token (withdraw) relative to the pool's fair/unmanipulated ratio, while the attacker captures the difference risk-free within a short window (ideally same block/few blocks, similar to MEV sandwiching on Ethereum). Value is transferred from the legitimate liquidity-providing account to an unprivileged attacker purely through price-manipulation of public, unprivileged trade calls (`ExchangeTransactionContract`), with no changes to consensus rules being required — a concrete underpriced/incorrect-accounting settlement issue.

## Likelihood Explanation
Medium. It requires the attacker to have capital to move the pool ratio and to control transaction ordering around the creator's inject/withdraw transaction (e.g., by submitting adjacent transactions, similar to mempool-based sandwiching). This is a generally known MEV-class risk for any AMM without slippage protection, and TRC10 Exchange pools are small/thin liquidity pools in practice, making them cheaper to manipulate than deep DeFi pools, increasing feasibility for an attacker with modest capital.

## Recommendation
- Add slippage-bound parameters (e.g., minimum/maximum `anotherTokenQuant`, or minimum/maximum acceptable ratio) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce them in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, mirroring the `expected` field already present in `ExchangeTransactionContract`.
- Alternatively/additionally, reject inject/withdraw if the pool balance was modified in the same block (an equivalent to the `lastChangeBlock` mitigation referenced in the external report).
- Consider disallowing large single-block ratio deviations for inject/withdraw or requiring the caller to specify an acceptable price range before execution.

## Proof of Concept
1. Pool P has TOKEN_A/TOKEN_B balances 1,000,000 / 3,000,000 (ratio 1:3).
2. Creator submits `ExchangeInjectContract` to inject 300,000 TOKEN_A, expecting ~900,000 TOKEN_B required (per current ratio), per the computation at `ExchangeInjectActuator.java:71-83`.
3. Attacker front-runs with `ExchangeTransactionContract`, selling a large amount of TOKEN_B into the pool via `ExchangeCapsule.transaction()` (`ExchangeCapsule.java:124-168`), skewing the ratio so TOKEN_A becomes relatively cheaper (e.g., ratio moves toward 1:6).
4. Creator's inject transaction executes at the skewed ratio, computing `anotherTokenQuant` (`ExchangeInjectActuator.java:73-80`) far higher than intended (e.g. ~1,800,000 TOKEN_B) and debiting the creator's account accordingly (`ExchangeInjectActuator.java:94-99`).
5. Attacker back-runs, trading back through `ExchangeTransactionContract` to restore the ratio near 1:3, extracting the excess TOKEN_B value the creator was forced to contribute, minus normal bancor swap fees.
6. No caller-controlled bound exists anywhere in `ExchangeInjectContract`/`ExchangeWithdrawContract` to prevent this (contrast with `ExchangeTransactionContract.expected` at `ExchangeTransactionActuator.java:217-221`), so the transaction succeeds and the value transfer is realized on-chain.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
