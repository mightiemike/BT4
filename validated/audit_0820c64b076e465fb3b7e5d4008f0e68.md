Confirmed: `MarketUtils.multiplyAndDivide` at [1](#0-0)  performs floor-division (`floorDiv`) with no minimum-output guard, and this result is used unguarded in the "taker == maker" branch of `matchSingleOrder`.

### Title
Unchecked floor-division rounding to zero lets a taker drain a maker's full remaining sell quantity for free in `MarketSellAssetActuator.matchSingleOrder` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
In the TRC10 order-book market module, `matchSingleOrder` computes the payment a maker receives via `MarketUtils.multiplyAndDivide`, which does integer floor division. In the branch where the taker's desired-buy quantity exactly equals the maker's remaining sell quantity ("taker == maker" case), the computed `makerBuyTokenQuantityReceive` is never checked for `== 0`, unlike the other two branches in the same function which explicitly guard against a zero result. This mirrors the reported JIT-minting bug class: small remaining quantities cause the payment calculation to round down to zero, but the token transfer to the counterparty proceeds anyway.

### Finding Description
`matchSingleOrder` in `MarketSellAssetActuator.java` computes three possible match outcomes depending on the relative size of `takerBuyTokenQuantityRemain` and `makerOrderCapsule.getSellTokenQuantityRemain()`:

- "taker < maker" branch (lines 440-452): no rounding computation for the maker's payment there, since `takerBuyTokenQuantityRemain` is used directly.
- "taker > maker" branch (lines 453-482): explicitly checks `if (makerBuyTokenQuantityReceive == 0)` and returns the sell tokens to the maker instead of proceeding, avoiding a zero-payment mint.
- "taker == maker" branch (lines 418-439): computes
```java
makerBuyTokenQuantityReceive = MarketUtils
    .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity,
        this.disableJavaLangMath());
takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();
```
but has **no check** that `makerBuyTokenQuantityReceive > 0` before proceeding. `multiplyAndDivide` performs `floorDiv(a*b, c)` [1](#0-0) , so when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`, the result floors to 0.

Concretely, with a maker order selling 199 A for 100 TRX (a non-integer price ratio) and `makerSellRemainQuantity = 1`: `makerBuyTokenQuantityReceive = floor(1*100/199) = 0`. If a taker's remaining buy amount exactly matches this `1` remaining unit (achievable by a taker order sized so `floor(takerSellRemainQuantity*199/100) == 1`), execution enters the "taker == maker" branch:
- `takerBuyTokenQuantityReceive = 1` (maker's full remaining A tokens, given to taker)
- `makerBuyTokenQuantityReceive = 0` (maker receives nothing)
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` — the maker's order is fully closed and removed from the order book
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0` — the taker's own sell balance is **not reduced at all**

The function then unconditionally calls `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, ...)` and `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive, ...)` [2](#0-1) , crediting the taker with the maker's tokens while crediting the maker with zero, and closing out the maker's order.

### Impact Explanation
This is a genuine on-chain accounting divergence: the maker's remaining sell-token balance is transferred to the taker while the maker's expected payment silently rounds down to zero and the taker's own paying balance is untouched. Repeated construction of maker orders with residual quantities near this rounding boundary (an attacker can act as both maker and taker, or target existing maker orders with such tail amounts) allows systematically extracting tokens from other users' locked/matched orders without providing consideration — the same "free tokens via rounding to zero" root cause as the referenced JIT-minting vulnerability, just in java-tron's Market order-book actuator instead of a Solidity order book. The already-existing zero-check in the "taker > maker" branch of the very same function confirms the developers were aware of this exact rounding hazard but missed applying the identical guard to the "taker == maker" branch.

### Likelihood Explanation
Triggering requires constructing sell/buy quantity ratios (which are fully attacker-controlled via `MarketSellAssetContract`) such that the residual match produces a maker payment that floors to zero, and arranging a taker order whose computed `takerBuyTokenQuantityRemain` exactly equals the maker's remaining sell quantity. Both quantities are attacker-chosen inputs (`sellTokenQuantity`, `buyTokenQuantity`, `quantity` in `MarketSellAssetContract`), and orders can be split into arbitrarily small pieces across multiple `MarketSellAsset` transactions, making this reachable by any unprivileged account without special permissions.

### Recommendation
Add the same guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, treat it as a residual too small to fill and return the maker's remaining sell tokens (`returnSellTokenRemain`) instead of transferring the full remaining quantity to the taker for free. Alternatively, enforce a minimum fillable quantity so that rounding-to-zero payments can never occur.

### Proof of Concept
1. Create a maker sell order: sell 199 units of token A for 100 TRX (`MarketSellAssetContract` with `sellTokenQuantity=199`, `buyTokenQuantity=100`), then let it partially fill down to `sellTokenQuantityRemain = 1`.
2. Submit a taker order (buy A with TRX) sized so that `MarketUtils.multiplyAndDivide(takerSellRemainQuantity, 199, 100)` evaluates to exactly `1` (e.g. `takerSellRemainQuantity` such that `floor(takerSellRemainQuantity*199/100) == 1`).
3. In `matchSingleOrder`, `takerBuyTokenQuantityRemain (1) == makerOrderCapsule.getSellTokenQuantityRemain() (1)` → enters the "taker == maker" branch [3](#0-2) .
4. `makerBuyTokenQuantityReceive = floor(1*100/199) = 0`; taker receives the maker's full remaining `1` A token via `addTrxOrToken`, maker's order is closed with zero TRX credited, and taker's TRX balance is left undeducted (`takerSellTokenLeft` unchanged).
5. Repeating this pattern against multiple maker orders with tail-end residual quantities lets an attacker accumulate tokens from other users' order books without paying.
