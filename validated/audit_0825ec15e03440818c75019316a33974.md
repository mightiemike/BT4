### Title
Panic-inducing `unwrap()` on `receiver_shard_id()` in `receipt_filter_fn` causes chunk-application halt after multiple reshardings - (File: runtime/runtime/src/congestion_control.rs)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally unwraps the `Result` returned by `Receipt::receiver_shard_id`, which returns `Err(EpochError::ShardingError(...))` when a `GlobalContractDistributionReceipt`'s stale `target_shard` cannot be resolved via `resolve_to_current_shard` after the shard's split-history has been exceeded (e.g. after repeated dynamic reshardings). This is directly analogous to the CVE-2021-46236 bug class: an attacker-influenced code path reaches an unguarded panic-on-null/error condition, causing a Denial of Service.

### Finding Description
`receiver_shard_id` (`core/primitives/src/receipt.rs:437-466`) resolves a `GlobalContractDistribution` receipt's target shard by first checking membership in the current `shard_layout.shard_ids()`, and if not found, falling back to `shard_layout.resolve_to_current_shard(target_shard)`. If that also fails (target shard has no descendant recorded in the current layout's split history — which can happen if the receipt is delayed long enough to span more resharding generations than the layout retains, or the shard's ancestor chain has been pruned), the function returns `Err(EpochError::ShardingError(...))`.

`receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs:874-878` calls this function and immediately `.unwrap()`s the result:
```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```
This function is called from `pop()` (line 905) while draining the delayed receipt queue during every chunk's `Runtime::apply` (see `process_delayed_receipts`/`DelayedReceiptQueueWrapper::pop`), and from `peek_iter()` (line 919). Both are reached deterministically by every validator applying the chunk — no privileged or adversarial-node access is required; any account can deploy a global contract (creating a `GlobalContractDistribution` receipt) and drive dynamic resharding activity (or simply wait) so the receipt remains delayed across enough resharding generations to exceed the layout's tracked split history.

The codebase's own regression test, `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs:30-186`, documents exactly this scenario: it deploys a global contract, saturates the target shard's compute to force the resulting `GlobalContractDistribution` receipt into the delayed queue, drives two sequential dynamic-resharding splits, and then asserts the chain does not stall — with an explicit comment: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations." [3](#0-2) 

### Impact Explanation
A panic inside `Runtime::apply` during receipt processing aborts the chunk-application task on every node that must apply that shard's chunk — this is not a benign transaction failure but a process-level panic reached deterministically from committed chain state (the delayed receipt queue), so it affects all honest validators/chunk producers tracking that shard identically. This produces a transaction-triggered halt of block/chunk production for the affected shard, matching the "transaction-triggered halt" acceptance criterion. Because it is deterministic given the same delayed-queue state, it is not merely a single-node crash but a systemic liveness failure across the validator set for that shard.

### Likelihood Explanation
Triggering requires: (1) a `GlobalContractDistribution` receipt (created by any account calling `DeployGlobalContract`) getting delayed via congestion/compute saturation, and (2) enough resharding events occurring while it remains delayed that its `target_shard` falls outside `resolve_to_current_shard`'s recorded split-history window. Under an actively resharding chain (dynamic resharding is a live protocol feature), an attacker who can cheaply saturate a shard's compute budget with `FunctionCall` receipts can keep a distribution receipt delayed indefinitely and wait out multiple resharding cycles, or accelerate this via repeated global-contract deployments across many resharding boundaries. This is reachable purely through standard permissionless transactions (contract deploy + compute-burning calls); no validator/operator/network-level privilege is needed.

### Recommendation
Change `receipt_filter_fn` to propagate the error instead of unwrapping:
```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> Result<bool, RuntimeError> {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id)?;
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout)?;
    Ok(receipt_shard_id == self.shard_id)
}
```
and update `pop()`/`peek_iter()` call sites to handle the `Result`, converting an unresolvable target shard into a `RuntimeError::StorageError(StorageError::StorageInconsistentState(...))` (or another well-defined recoverable error) rather than panicking, consistent with how other stale-state conditions are already handled elsewhere in `runtime/runtime/src/lib.rs` (e.g. `StorageInconsistentState` on inconsistent postponed-receipt state).

### Proof of Concept
1. Deploy a global contract from an account on shard `S_A` via `DeployGlobalContract`, producing a `GlobalContractDistributionReceipt` with `target_shard = S_A`.
2. Saturate `S_A`'s compute budget every block with cheap `FunctionCall` receipts (e.g. `burn_gas_raw`) so the distribution receipt is pushed into, and remains in, the delayed receipt queue.
3. Configure/drive dynamic resharding to force at least two sequential shard-split events on `S_A`'s lineage while the receipt stays delayed (as reproduced by `test_stale_global_contract_distribution_after_double_resharding`, `test-loop-tests/src/tests/global_contracts_distribution.rs:32-186`).
4. Stop saturating and let the delayed queue drain; `receipt_filter_fn` invokes `receiver_shard_id(&shard_layout).unwrap()` on the stale receipt, whose `target_shard` is no longer resolvable to a current shard, causing `Err` → `.unwrap()` panic and halting chunk application for that shard on every validator.
