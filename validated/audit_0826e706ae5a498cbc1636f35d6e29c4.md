### Title
Attached NEAR deposit permanently lost in wallet-contract `address_check_callback` failure paths - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR wallet contract's `#[payable] rlp_execute` entry point accepts an attached NEAR deposit from any external caller and tracks it as a `CallerDeposit` so it can be refunded if the underlying cross-contract call fails. However, in the address-registrar lookup path (`address_check_callback`), three early-return failure branches drop the `caller_deposit` value entirely — neither forwarding it to the intended action nor refunding it to the caller — resulting in the deposit being permanently stuck in the wallet contract, analogous to `BoringBatchable.sol`'s payable `batch()` function that accepts ETH with no way to reclaim it.

### Finding Description
`rlp_execute` is `#[payable]` and computes a `caller_deposit` via `CallerDeposit::new`, which tracks `env::attached_deposit()` whenever the predecessor differs from the wallet's own account (i.e., any external caller/relayer): [1](#0-0) 

When the parsed transaction is an `EOABaseTokenTransfer` with `address_check: Some(address)`, `inner_rlp_execute` schedules a call to the address registrar followed by `address_check_callback`, passing along `caller_deposit`: [2](#0-1) 

Inside `address_check_callback`, there are three branches that return an error `ExecuteResponse` directly (`PromiseOrValue::Value`) without ever consuming or refunding `caller_deposit`:
1. The registrar lookup call fails (`PromiseResult::Failed`).
2. The registrar response fails to deserialize.
3. The registrar returns `Some(account_id)` (target resolves to a named account) and the caller is not the wallet itself (i.e., it's a relayer/external caller, not a self-ban case). [3](#0-2) 

By contrast, the sibling callback `rlp_execute_callback`, which handles the "normal" failure case, explicitly issues a `Promise::transfer` to refund `caller_deposit` on `PromiseResult::Failed`: [4](#0-3) 

This confirms the wallet contract's intended design is to always refund the caller's attached deposit whenever the requested action does not go through — but `address_check_callback`'s three early-return branches violate that invariant, silently dropping `caller_deposit` and leaving those yoctoNEAR permanently on the wallet contract's balance with no code path to recover them.

### Impact Explanation
Any account (an unprivileged relayer or a user calling `rlp_execute` directly with an attached deposit) that submits a `FunctionCall` to a wallet contract's `rlp_execute` with a base-token-transfer Ethereum transaction requiring the address-check flow (`address_check: Some(address)`), and where the registrar lookup either fails, returns malformed data, or resolves to an existing named account while the caller is not the wallet itself, will have their attached NEAR deposit burnt/stuck in the wallet contract permanently. This is a concrete "permanently frozen funds" outcome triggered by a single ordinary transaction, matching the reachable path constraints (an unprivileged transaction signer / RPC caller / relayer).

### Likelihood Explanation
The registrar-lookup failure and malformed-response branches can occur under ordinary conditions (e.g., registrar contract downtime, unexpected response format, or gas exhaustion on the registrar call), and the "target resolves to an existing account" branch is a normal, non-adversarial occurrence when a relayer submits a transaction whose target eth-implicit address happens to correspond to a registered named account — something the honest relayer is expected to check beforehand but isn't guaranteed to. Because attaching a deposit to `rlp_execute` for a base-token transfer is a standard usage pattern (the deposit funds the transfer), this is easily triggered without any malicious actor.

### Recommendation
In all three early-return branches of `address_check_callback` (registrar call failed, malformed registrar response, and "invalid target" when caller isn't self), refund `caller_deposit` to `caller_deposit.account_id` via `env::promise_batch_action_transfer`, mirroring the refund logic already implemented in `rlp_execute_callback`, before returning the `ExecuteResponse`.

### Proof of Concept
1. A relayer/account calls `wallet_contract.rlp_execute(target, tx_bytes_b64)` attaching a non-zero NEAR deposit, where `tx_bytes_b64` encodes an RLP Ethereum transaction representing an `EOABaseTokenTransfer` with a `to` address that doesn't directly match `target`'s own address (triggering `address_check: Some(address)`, per `inner_rlp_execute`) — see [2](#0-1) .
2. This produces a promise chain to `address_registrar.lookup(address)` then `address_check_callback(target, action, caller_deposit)`.
3. If the registrar lookup returns `Some(existing_account_id)` (the address happens to correspond to a registered named account) and the transaction signer isn't the wallet contract itself, `address_check_callback` returns `PromiseOrValue::Value(ExecuteResponse { success: false, ... })` at [5](#0-4)  without ever spending or refunding `caller_deposit`.
4. The attached NEAR deposit remains on the wallet contract's account balance permanently, with no subsequent call path able to recover it for the original caller.
