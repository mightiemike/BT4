### Title
Cross-tenant webhook spoofing via unsigned `X-Shopify-Shop-Domain` header replay - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
`validateFactory` verifies webhook authenticity by checking the HMAC over `rawBody` only, then separately extracts the `X-Shopify-Shop-Domain` header without any cryptographic binding between the two. Because the app's `apiSecretKey` is shared across every shop that installs the app, any valid `(rawBody, hmac)` pair obtained from one shop's webhook delivery remains "valid" when replayed with an arbitrary `X-Shopify-Shop-Domain` header, letting an attacker make `authenticateWebhookFactory` load and act on behalf of a different, unrelated shop's offline session.

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` first calls `validateHmacFromRequestFactory` (from `packages/apps/shopify-api/lib/utils/hmac-validator.ts`), which validates the HMAC exclusively against `rawBody`: [1](#0-0) 

The domain header is never part of the signed input. After the HMAC check passes, `checkWebhookHeaders`/`checkWebhooksHeaders` simply reads `X-Shopify-Shop-Domain` from the (unsigned) headers and returns it as `domain` in the validation result, with no cross-check against the HMAC or any other trusted binding: [2](#0-1) 

Downstream, `authenticateWebhookFactory` (e.g. `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts`) trusts `check.domain` completely and uses it to load an offline session and build an authenticated admin client: [3](#0-2) 

`ensureValidOfflineSession` then loads/refreshes the session strictly keyed by that attacker-controlled `shop` string: [4](#0-3) 

Since `apiSecretKey` is a single per-app secret (not per-shop), any `(rawBody, hmac)` pair that is valid for shop A's webhook is *also* a valid HMAC for the exact same bytes regardless of which domain header accompanies it. An attacker who is a merchant on shop A (or otherwise legitimately receives/observes one webhook delivery for shop A) can capture that raw body and its `X-Shopify-Hmac-Sha256` header, then resend it to the same webhook route with `X-Shopify-Shop-Domain` swapped to shop B (also installed on the app). `validHmacResult.valid` stays `true` because HMAC validation only checks `rawBody`, and `check.domain` becomes `shop-b.myshopify.com`, causing the library to fetch and use shop B's offline access token/session to process a payload the attacker fully controls (from their own captured webhook body).

### Impact Explanation
This allows cross-tenant session/token access: the app processes attacker-supplied webhook content (reused body) under a victim shop's identity and offline access token, executing whatever business logic the app's webhook handler performs (e.g., API calls, data mutation) using shop B's credentials. This maps to Shopify's "cross-tenant data/state access" impact class.

### Likelihood Explanation
The attack requires only that the attacker has at some point legitimately received one webhook (trivial if the attacker installs the app on their own store) and that a second, unrelated shop is also installed on the same app — both realistic, low-privilege preconditions with no secret theft or non-default config required. The header swap and replay is a single crafted HTTP POST, fully repeatable for any topic/body the attacker already has a valid signature for.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or any other header) as an identity input unless it can be cryptographically tied to the signed body, or unless the shop identity is cross-checked against the topic/webhook-id via a call back to Shopify (e.g. re-verifying webhook existence/ownership through the Admin API), or unless per-shop webhook secrets are used instead of a single shared `apiSecretKey`. At minimum, document that `check.domain` is untrusted input and require host apps to validate it against their own session storage state (e.g., confirm a session already exists for that shop) before granting any privileged action, and consider rejecting requests whose `domain` doesn't match an expected/allow-listed value tied to the delivery context.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/webhooks/__tests__/domain-spoof.test.ts
import {shopifyApi} from '../../..';
import {testConfig} from '../../__tests__/test-config';

test('HMAC validity is independent of X-Shopify-Shop-Domain header', async () => {
  const shopify = shopifyApi(testConfig());
  const rawBody = '{"id":123}';
  const hmac = await shopify.utils.hmacSign(rawBody); // or precomputed valid HMAC for shop A

  const resultForShopA = await shopify.webhooks.validate({
    rawBody,
    rawRequest: new Request('https://app.example.com/webhooks', {
      method: 'POST',
      headers: {
        'X-Shopify-Hmac-Sha256': hmac,
        'X-Shopify-Topic': 'orders/create',
        'X-Shopify-Shop-Domain': 'shop-a.myshopify.com',
        'X-Shopify-Api-Version': '2024-01',
        'X-Shopify-Webhook-Id': 'abc',
      },
      body: rawBody,
    }),
  });

  const resultForShopB = await shopify.webhooks.validate({
    rawBody,
    rawRequest: new Request('https://app.example.com/webhooks', {
      method: 'POST',
      headers: {
        'X-Shopify-Hmac-Sha256': hmac, // same HMAC, same body
        'X-Shopify-Topic': 'orders/create',
        'X-Shopify-Shop-Domain': 'shop-b.myshopify.com', // swapped domain
        'X-Shopify-Api-Version': '2024-01',
        'X-Shopify-Webhook-Id': 'abc',
      },
      body: rawBody,
    }),
  });

  expect(resultForShopA.valid).toBe(true);
  expect(resultForShopB.valid).toBe(true); // same signature accepted for a different shop
  expect((resultForShopA as any).domain).toBe('shop-a.myshopify.com');
  expect((resultForShopB as any).domain).toBe('shop-b.myshopify.com');
});
```
This demonstrates that `validateFactory` accepts the identical `(rawBody, hmac)` pair for two different `domain` values, which then flows unchecked into `authenticateWebhookFactory`'s `ensureValidOfflineSession(params, check.domain)` call.
