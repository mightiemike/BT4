Confirmed: `createOrLoadOfflineSession(params, shop)` loads/creates a real session (with a valid stored offline access token) keyed purely by the `shop` string passed in — which comes straight from the unauthenticated `domain` header, and `hmac(secret, body)` in the test helper confirms the HMAC is computed over `body` alone, with no shop/domain/topic binding whatsoever.

### Title
Webhook HMAC is not bound to the shop domain, allowing cross-tenant session hijack via forged `X-Shopify-Shop-Domain` header - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
The webhook signature verification in this SDK validates only the raw request body against `X-Shopify-Hmac-Sha256`/`X-Shopify-Hmac-Sha256` (or the Events equivalent), while the `X-Shopify-Shop-Domain` header — which is later used to look up and attach a live, authenticated admin/session client for that shop — is never included in the signed data and is trusted verbatim. This mirrors the `LiquidityPool::requestRedeemWithPermit` finding: a cryptographically valid signature (permit/HMAC) that is legitimately obtainable by an unprivileged actor is not scoped to the specific resource (liquidity pool / shop) it is later applied to, letting that actor redirect the valid signature's effect onto a different resource of their choosing.

### Finding Description
`validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` computes and checks the HMAC solely over `rawBody`: [1](#0-0) 

`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` calls this HMAC check, and once it passes, separately (and without any cryptographic linkage) extracts `domain`, `topic`, and `webhookId` directly from request headers via `checkWebhooksHeaders`/`checkEventsHeaders`: [2](#0-1) [3](#0-2) 

Downstream, `authenticateWebhookFactory` (react-router and remix packages) takes `check.domain` — the unauthenticated header value — and uses it directly to fetch a live offline session, then attaches an authenticated admin API client built from that session to the webhook context handed to app code: [4](#0-3) 

`ensureValidOfflineSession` / `createOrLoadOfflineSession` loads the stored session purely by the `shop` string it is given: [5](#0-4) 

Because the HMAC never covers `domain`/`topic`/`webhookId`, any `(rawBody, hmac)` pair that Shopify has ever legitimately produced for the app's shared secret remains valid for that same body forever, regardless of which `X-Shopify-Shop-Domain` header accompanies it. An unprivileged actor — a merchant who has installed the app on their own store — can trivially obtain such a pair (e.g., by pointing the webhook subscription/relay at infrastructure they control, or by inspecting outbound webhook deliveries from their own shop), since the HMAC only proves "Shopify signed this body with this app's secret," not "Shopify sent this body for this shop." The attacker then replays the exact `rawBody` + `hmac` to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` for a victim shop that also has the app installed. `validate()` reports `valid: true` with `domain` set to the victim shop, and `authenticate()` loads the victim's real offline session/access token and hands the attacker's crafted payload (with attacker-controlled `topic`/`webhookId`) to the app's webhook handler code as if it legitimately originated from the victim.

### Impact Explanation
This is a cross-tenant confused-deputy vulnerability: an attacker who has never had any privileged relationship with the victim shop can cause the app to (a) execute webhook handler business logic under the victim's authenticated `admin`/`storefront` client, and (b) fabricate arbitrary webhook topics/payloads "from" the victim shop. Depending on what the app's webhook handlers do with the payload (write data, sync inventory, issue refunds, trigger Admin API mutations using `session`/`admin` from the context), this can result in unauthorized data modification, disclosure, or side effects performed against the victim's store using the victim's own access token — a direct cross-tenant access/authorization break reachable from a single anonymous/unprivileged webhook POST.

### Likelihood Explanation
Moderate-to-high: the attacker does not need to break any cryptography or leak any secret — they only need one genuine `(rawBody, hmac)` pair from their own shop's webhook traffic (trivially observable since they control their own store and can register/observe their own app's webhook endpoint traffic), plus knowledge of the target victim's `*.myshopify.com` domain (public/guessable). The only constraint is that the replayed body is fixed (can't be freely chosen), which limits — but does not eliminate — impact for payload-driven handlers, and does not reduce the severity of a spoofed `topic`/`webhookId` causing a specific handler branch to run against the victim's authenticated session.

### Recommendation
Bind the shop domain (and ideally topic/webhookId) cryptographically to the HMAC verification step, or otherwise cross-check the header-derived `domain` against an independently-verified source of truth before using it to load a session. Concretely: include the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header values as part of the data validated by `validateHmacFromRequestFactory`/`validateHmacString`, matching Shopify's guidance to treat the header-derived shop as untrusted until covered by the signature, rather than passing it straight into `ensureValidOfflineSession`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and configures a webhook (e.g. `products/create`) to be intercepted (their own endpoint, or a debugging proxy) so they capture a genuine `(rawBody, X-Shopify-Hmac-Sha256)` pair Shopify sent for their shop.
2. Attacker POSTs to the app's real webhook endpoint with:
   - Body: the captured `rawBody` (unchanged, so the HMAC still validates)
   - `X-Shopify-Hmac-Sha256`: the captured HMAC (unchanged)
   - `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com`
   - `X-Shopify-Topic`: any topic the attacker wants the handler to treat this as
3. `validateFactory` (`packages/apps/shopify-api/lib/webhooks/validate.ts`) HMAC-checks only the body → passes → returns `{valid: true, domain: 'victim-shop.myshopify.com', topic: <attacker-chosen>}`.
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's real stored offline session and attaching an authenticated `admin` client for the victim to the webhook context passed to the app's handler. [6](#0-5)

export async function ensureValidOfflineSession(
  params: BasicParams,
