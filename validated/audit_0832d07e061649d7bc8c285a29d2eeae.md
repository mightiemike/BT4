### Title
Signer sortition-view refresh silently resets `miner_status`, losing "invalidated" state - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionsView` mirrors the Witch.sol pattern: it caches a piece of derived state (`SortitionMinerStatus`, analogous to `vaultOwners[vaultId]`) that records a locally-important decision (a miner was declared invalid) separately from the canonical source of truth. When the same "slot" (here, `cur_sortition`/`last_sortition`) is refreshed a second time via `reset_view`, that locally-tracked status is unconditionally overwritten back to `Valid`, exactly as `vaultOwners[vaultId]` is unconditionally overwritten on a second `grab`.

### Finding Description
`SortitionsView::check_proposal` marks `cur_sortition.miner_status` (or `last_sortition.miner_status`) as `SortitionMinerStatus::InvalidatedBeforeFirstBlock` when it independently determines the current miner has timed out or chose a bad parent tenure: [1](#0-0) [2](#0-1) 

This `miner_status` field is the only place this signer's "I already rejected this miner" decision is recorded; it never gets persisted anywhere else and there is no `SortitionMinerStatus::InvalidatedBeforeFirstBlock`-preserving merge path.

If any proposal arrives whose `consensus_hash` does not match either the cached `cur_sortition` or `last_sortition`, the code refreshes the whole view from the node and immediately re-checks the (now stale) proposal against it: [3](#0-2) 

`reset_view` re-fetches `CurrentAndLastSortition` from the node and reconstructs both `SortitionState`s via `TryFrom<SortitionInfo>`, which **always** initializes `miner_status: SortitionMinerStatus::Valid`, with no attempt to preserve the previously-recorded invalidation for the same consensus hash: [4](#0-3) [5](#0-4) 

This is functionally the same bug class as Witch.sol: a "second grab" (second fetch of the same slot) silently discards the earlier state (`vaultOwners[vaultId]` / `miner_status = InvalidatedBeforeFirstBlock`) that other logic (`buy` / the `ProposedBy::CurrentSortition`/`ProposedBy::LastSortition` match arm) depends on to make a correctness-critical decision: [6](#0-5) 

The refresh path is reachable from ordinary block-proposal processing with `reset_view_if_wrong_consensus_hash = true`: [7](#0-6) 

Triggering it only requires sending the signer any `NakamotoBlock` proposal message whose header carries a self-consistent (attacker-controlled) signature and an unrelated `consensus_hash` — `recover_miner_pk()` succeeds for any valid ECDSA-recoverable signature, it does not require the sender to actually be a legitimate miner, and this check runs *before* the `proposed_by` mismatch/reset branch: [8](#0-7) 

### Impact Explanation
A single signer that has locally invalidated the current tenure's miner (due to a timeout it alone observed, or a bad-parent-tenure determination) can have that invalidation silently erased by an unrelated, attacker-supplied stray proposal. After the reset, that signer will treat the previously-invalidated miner as `Valid` again and may sign/approve a block that other signers — who never received the stray trigger and thus never underwent a spurious refresh — continue to reject as coming from an invalidated miner. This creates a genuine divergence in per-signer local state for the same tenure, i.e., a minority-triggerable, unprivileged break of the equality "all signers agree on whether the current tenure's miner is valid," which can manifest as temporary tip/vote disagreement among signers.

### Likelihood Explanation
The trigger requires no special privilege or majority collusion: any party able to submit a syntactically valid, self-signed `NakamotoBlock` proposal with an arbitrary `consensus_hash` to a subset of signers can force `reset_view` on those signers at will (`reset_view_if_wrong_consensus_hash = true` in the production call site). The dependent condition (a signer having already locally marked a miner invalid before the reset lands) is a normal, expected runtime state during tenure timeouts/reorg-choice validation, so the race window is realistic, not purely theoretical.

### Recommendation
When refreshing/re-fetching a `SortitionState` for a consensus hash that the view already has an in-memory record for, preserve the existing `miner_status` (particularly `InvalidatedBeforeFirstBlock`/`InvalidatedAfterFirstBlock`) instead of unconditionally re-initializing it to `Valid` in `TryFrom<SortitionInfo>`/`reset_view`. Alternatively, persist the invalidation decision in `SignerDb` keyed by consensus hash so it survives any in-memory view refresh, mirroring the report's suggested "keep the prior state if it already represents a decision that must not be lost."

### Proof of Concept
1. Signer S has `cur_sortition` for tenure `CH_A`, status `Valid`.
2. `check_proposal` is invoked for a legitimate block still targeting `CH_A`; the timeout check at lines 144-163 fires and sets `cur_sortition.miner_status = InvalidatedBeforeFirstBlock` (miner A is now considered invalid by S).
3. Attacker crafts any `NakamotoBlock` with header `consensus_hash = CH_X` (unrelated, non-existent/garbage) and a valid self-signature, and sends it to S as a miner-message/proposal.
4. In `check_proposal`, `CH_X` matches neither `cur_sortition` (`CH_A`) nor `last_sortition`; since `reset_view_if_wrong_consensus_hash = true` at the real call site, `self.reset_view(client)` is invoked.
5. `reset_view` re-fetches `CurrentAndLastSortition` from the node — which still reports `CH_A` as `cur_sortition` — and rebuilds it via `TryFrom<SortitionInfo>`, resetting `miner_status` back to `Valid`.
6. A later legitimate proposal for `CH_A` from miner A is now accepted by S (via `ProposedBy::CurrentSortition` with `miner_status == Valid`), while other signers who never processed the attacker's stray message still hold `InvalidatedBeforeFirstBlock` for `CH_A` and reject it — producing signer disagreement on the same tenure/block.

    /// Reset the view to the current sortition and last sortition
    pub fn reset_view(&mut self, client: &StacksClient) -> Result<(), ClientError> {
        let CurrentAndLastSortition {
            current_sortition,
            last_sortition,
        } = client.get_current_and_last_sortition()?;

        let cur_sortition = SortitionState::try_from(current_sortition)?;
        let last_sortition = last_sortition
            .map(SortitionState::try_from)
            .transpose()
            .ok()
            .flatten();

        self.cur_sortition = cur_sortition;
        self.last_sortition = last_sortition;
        Ok(())
    }
