Confirmed: the `shopify-app-express` package explicitly sets a `500kb` body-size limit via `express.text({type: '*/*', limit: '500kb'})` in `packages/apps/shopify-app-express/src/webhooks/index.ts`, but the `shopify-app-remix` and `shopify-app-react-router` packages call `request.text()` directly with no size limit before HMAC validation, in the webhook, flow, fulfillment-service, and app proxy authenticate handlers.

### Title
Unbounded request body buffering before HMAC validation enables memory-exhaustion DoS on webhook/flow authentication handlers - (File: packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts, packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts, and sibling flow/fulfillment-service authenticate handlers)

### Summary
The remix and react-router webhook, flow, and fulfillment-service authentication factories read the entire incoming request body into memory via `await request.text()` before any authenticity check (HMAC/signature validation) is performed. There is no size cap enforced by the library, unlike the equivalent Express package which explicitly limits webhook bodies to `500kb`.

### Finding Description
`authenticateWebhookFactory` in both the remix and react-router packages performs `const rawBody = await request.text();` immediately upon receiving a POST request, prior to calling `api.webhooks.validate` (which performs HMAC verification): [1](#0-0) [2](#0-1) 

The same unbounded pattern exists in the Flow authenticate handler: [3](#0-2) 

and in the fulfillment-service authenticate handler (same `request.text()` pattern per the grep results). None of these routes require any prior authentication — they are the entry points that anonymous callers (or anyone who can reach the app's public webhook/flow/fulfillment-service URL) hit directly, since the whole point of these routes is to receive unauthenticated Shopify-originated (or spoofable) HTTP calls that get authenticated only after the body is read.

By contrast, the `shopify-app-express` package's `processWebhooks` explicitly bounds the body read with Express's `text()` middleware `limit: '500kb'` option: [4](#0-3) 

This shows the project is aware that body-size limiting matters for this exact code path in one framework integration, but the equivalent remix/react-router integrations lack it. `request.text()` on the Fetch `Request` object buffers the entire body into memory with no built-in size limit; the underlying runtime (Node's fetch, Cloudflare Workers, etc.) will happily stream and buffer arbitrarily large payloads before the function resolves, and only afterward does the code attempt HMAC validation and potentially reject the request.

This matches the class of vulnerability described in the referenced report: a low-cost anonymous request (a single large POST) causes disproportionate resource consumption (memory buffering of the full body) on the server before any authenticity/cost check is applied, exactly the "protect itself from abusive clients" concern about performing expensive work before validating that the request is legitimate.

### Impact Explanation
An anonymous attacker (no merchant install, no valid HMAC secret) can send large POST bodies to the app's public `/webhooks`, `/flow`, or fulfillment-service routes. Each request forces the Node/Workers process to buffer the full body in memory before the (cheap) HMAC check rejects it. Repeated or concurrent large requests can exhaust process memory or degrade performance for legitimate traffic — a resource-exhaustion (DoS) condition on a request-authentication handler that is reachable pre-authentication, directly analogous to the report's "should protect itself from abusive clients" concern.

### Likelihood Explanation
The webhook, flow, and fulfillment-service authenticate routes are, by design, publicly reachable HTTP endpoints (they exist precisely to receive external POSTs before any session exists). No merchant install or credentials are needed to reach them — only knowledge of the app's public URL, which is typically discoverable from the app's `shopify.app.toml` / webhook subscription configuration or by probing common paths. Sending large bodies requires no special tooling.

### Recommendation
Enforce an explicit maximum body size before or while reading the body in the remix/react-router `authenticate.webhook`, `authenticate.flow`, and `authenticate.fulfillmentService` (and app proxy) factories — e.g., check `Content-Length`, or stream-read with a byte cap and abort/reject (413) once exceeded — mirroring the `500kb` limit already applied in `shopify-app-express`. Apply the same limit uniformly across all runtime adapters to close the gap between framework integrations.

### Proof of Concept
1. Deploy a shopify-app-remix (or shopify-app-react-router) app with a webhook route wired to `shopify.authenticate.webhook`.
2. Send an anonymous POST request directly to the app's webhook URL (no valid HMAC header) with a very large body, e.g.:
```
curl -X POST https://victim-app.example.com/webhooks \
  --data-binary @large_payload.bin \  # e.g. several hundred MB, or repeat concurrently
  -H "X-Shopify-Topic: PRODUCTS_CREATE" \
  -H "X-Shopify-Hmac-Sha256: invalid" \
  -H "X-Shopify-Shop-Domain: attacker.myshopify.com" \
  -H "X-Shopify-Webhook-Id: 1" \
  -H "X-Shopify-API-Version: 2024-01"
```
3. `authenticate()` calls `await request.text()` and buffers the entire payload into memory before `api.webhooks.validate` rejects it for an invalid HMAC.
4. Repeating this concurrently from multiple connections drives up process memory/CPU with no library-enforced cap, unlike the express package's `500kb` limit for the equivalent route.
