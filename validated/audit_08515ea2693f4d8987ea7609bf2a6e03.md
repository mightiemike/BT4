### Title
Missing signature malleability check (`s` not constrained to lower half of secp256k1 order) in `ECDSASignature.validateComponents` - (File: `crypto/src/main/java/org/tron/common/crypto/ECKey.java`)

### Summary
The `unpackSignature`-analog validation in java-tron, `ECDSASignature.validateComponents`, performs partial signature-shape validation (checks `v ∈ {27,28}`, `r,s ≥ 1`, and `r,s < N`) but never enforces that `s` is in the lower half of the secp256k1 curve order, unlike OpenZeppelin's `ECDSA.tryRecover`. This is the same class of omission described in the external report for `RegistrarController.unpackSignature`.

### Finding Description
`ECDSASignature.validateComponents` is the canonical signature-shape check used throughout the signature-recovery pipeline: [1](#0-0) 

Note it checks `v`, and that `r`/`s` are within `[1, SECP256K1N)`, but does **not** reject `s > SECP256K1N/2`. The curve already defines `HALF_CURVE_ORDER` and a `toCanonicalised()` helper that performs exactly this check, but that helper is never invoked from the validation/recovery path: [2](#0-1) 

This `validateComponents()` (no-arg overload) is called directly from the TVM `ECRecover` precompile: [3](#0-2) 

and from the shared helper `recoverAddrBySign`, used by the `BatchValidateSign` and `ValidateMultiSign` precompiles that on-chain contracts rely on for multisig weight/threshold checks: [4](#0-3) 

Because `s` and `N - s` (with the complementary `v`) both pass `validateComponents()` and recover to the identical signer address, any signature accepted by these paths has a second, distinct byte-level representation that recovers to the same signer — the classic ECDSA malleability the OpenZeppelin `ECDSA` library (and the referenced Beranames fix) specifically guards against.

### Impact Explanation
Any unprivileged user-supplied signature reaching `ecrecover` (opcode/precompile at address `0x1`) or the TRON-specific `BatchValidateSign`/`ValidateMultiSign` precompiles can be transformed into a second valid encoding (`s' = N - s`, flipped `v`) that recovers to the same address. Smart contracts built on TVM that use the raw signature bytes (rather than the recovered address) as a replay-protection/uniqueness key, or that count/dedupe multisig signatures by raw signature bytes, are directly exploitable for signature replay or double-counting of a single authorization. This mirrors the impact class flagged in the external report (replay/malleability enabling security bypasses in downstream consumer contracts).

### Likelihood Explanation
The missing check is reachable by any unprivileged caller of the `ecrecover` opcode, the `ECRecover` precompile, or the `BatchValidateSign`/`ValidateMultiSign` precompiles — no privileged role is required, and crafting `s' = N - s` with the complementary `v` is a two-line computation for an attacker holding one valid signature. The main mitigating factor is that impact severity is entirely dependent on how a specific deployed contract consumes the recovered/validated signature (i.e., whether it relies on signature-byte uniqueness rather than the recovered address).

### Recommendation
Add an explicit lower-half check for `s` (`s.compareTo(HALF_CURVE_ORDER) <= 0`) inside `ECDSASignature.validateComponents(BigInteger r, BigInteger s, byte v)` in `crypto/src/main/java/org/tron/common/crypto/ECKey.java`, mirroring OpenZeppelin's `ECDSA` malleability guard, so that all callers (`ECRecover` precompile, `BatchValidateSign`, `ValidateMultiSign`, and any future consumer of `validateComponents()`) reject non-canonical signatures by default.

### Proof of Concept
1. Obtain any valid ECDSA signature `(r, s, v)` over hash `h` for signer `A`, where `s ≤ N/2` (canonical form).
2. Compute `s' = N - s` and `v' = 27 ^ 28 ^ v` (i.e., flip 27↔28).
3. Submit `(r, s', v')` to the `ECRecover` precompile (`address 0x1`) or to `BatchValidateSign`/`ValidateMultiSign` alongside/in place of the original.
4. `ECDSASignature.validateComponents(r, s', v')` returns `true` (since `s' < N`), and `SignUtils.signatureToAddress` recovers the same address `A`, confirming a second, distinct byte encoding is accepted for the same signer/message as valid, demonstrating the missing lower-half canonicalization check.     public static boolean validateComponents(BigInteger r, BigInteger s,
        byte v) {

      if (v != 27 && v != 28) {
        return false;
      }

      if (BIUtil.isLessThan(r, BigInteger.ONE)) {
        return false;
      }
      if (BIUtil.isLessThan(s, BigInteger.ONE)) {
        return false;
      }

      if (!BIUtil.isLessThan(r, SECP256K1N)) {
        return false;
      }
      return BIUtil.isLessThan(s, SECP256K1N);
    }

    public ECDSASignature toCanonicalised() {
      if (s.compareTo(HALF_CURVE_ORDER) > 0) {
        // The order of the curve is the number of valid points that
        // exist on that curve. If S is in the upper
        // half of the number of valid points, then bring it back to
        // the lower half. Otherwise, imagine that
        //    N = 10
        //    s = 8, so (-8 % 10 == 2) thus both (r, 8) and (r, 2)
        // are valid solutions.
        //    10 - 8 == 2, giving us always the latter solution,
        // which is canonical.
        return new ECDSASignature(r, CURVE.getN().subtract(s));
      } else {
        return this;
      }
    }
