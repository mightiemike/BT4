## Title
Class caches (`GlobalContractCache` / `CachedClassStorage`) are bounded only by entry count, not by byte size, letting a stream of maximum-size Declare transactions inflate sequencer/gateway memory far beyond the intended cache budget - ([File: crates/starknet_api/src/class_cache.rs])

### Summary
The class caches used by the class manager and the blockifier (`GlobalContractCache`, wrapping `cached::SizedCache`) are dimensioned purely by number of entries (`class_cache_size`, `contract_cache_size`, etc.), with no accounting for the actual byte size of the cached Sierra/CASM/native payloads. An unprivileged account can submit Declare transactions for distinct classes sized at (or just under) the configured `max_contract_class_object_size`/`max_compiled_contract_class_object_size` limits, forcing every cache slot to hold a near-maximum-size entry instead of the "typical" size the cache was sized for. This mirrors the reported Besu `FutureMessageBuffer` issue: a structurally valid, per-item-size-checked but cumulatively unbounded cache, capped only by count.

### Finding Description
`GlobalContractCache<T>` is a thin wrapper over `SizedCache<ClassHash, T>` that evicts purely by LRU count, never by aggregate bytes: [1](#0-0) 

`CachedClassStorage` instantiates four such caches (`classes`, `executable_classes`, `executable_class_hashes_v2`, `deprecated_classes`) sized only from `CachedClassStorageConfig.class_cache_size` / `deprecated_class_cache_size`: [2](#0-1) 

Similarly, the blockifier's per-node "global contract cache" (`RawClassCache = GlobalContractCache<CompiledClasses>`), used by the gateway's stateful validator and the batcher, is sized only by `contract_cache_size` (a count): [3](#0-2) [4](#0-3) 

The only size checks that exist are *per-transaction* stateless validations, capping a single class's Sierra/CASM object size (`max_contract_bytecode_size`, `max_contract_class_object_size`) - they do not track or bound the *sum* of bytes retained across all cached entries: [5](#0-4) 

Because eviction is LRU-by-count, an attacker who repeatedly declares distinct classes (unique Sierra programs, e.g. via padding/dummy code) each sized at the maximum allowed (`max_contract_class_object_size` ≈ 4 MB, `max_compiled_contract_class_object_size` ≈ 4 MB, per deployed config) can force every slot in `classes`, `executable_classes`, and `deprecated_classes` to simultaneously hold near-maximum-size payloads. The deployed defaults compound this: [6](#0-5) 

With `class_cache_size = 128` and `deprecated_class_cache_size = 128`, and each of the `classes` + `executable_classes` + `deprecated_classes` caches able to hold ~4 MB entries, the worst-case resident footprint for these caches alone (`128 * 4MB * 3 ≈ 1.5GB`) is many times the memory the cache size was presumably tuned for under "typical" class sizes (which are much smaller in practice). The same pattern repeats independently in the blockifier's own `RawClassCache` (`contract_cache_size`, default used by gateway/batcher), which stores both compiled CASM and the retained `Arc<SierraContractClass>` per V1 entry, doubling the per-entry worst case.

This is directly reachable by any contract declarer: repeatedly submitting valid, size-limit-compliant Declare transactions for distinct classes is exactly the "unprivileged transaction sender/contract deployer/class declarer" path called out as in-scope, and does not require a malicious peer, proposer, or operator.

### Impact Explanation
An attacker who can afford Declare transaction fees can force the class caches on gateway and/or batcher/sequencer nodes to retain their full cache count worth of maximum-size entries. Because the caches were presumably sized assuming realistic average class sizes, an attacker choosing to always submit maximum-size classes multiplies the actual memory consumed relative to the sizing assumption, degrading process memory headroom and potentially triggering OOM or GC/allocator pressure on gateway or sequencer nodes, which can affect availability of tx admission or block building - a resource-exhaustion condition well beyond the cache's intended budget. This matches the Medium severity class of the referenced advisory (bounded by count, not bytes, permits outsized memory use via legitimate-looking but adversarially sized inputs).

### Likelihood Explanation
Likelihood is fairly high for the effort involved: the attacker only needs to author/declare distinct Sierra classes at or near the size limits already enforced by `stateless_transaction_validator.rs` (`max_contract_bytecode_size`, `max_contract_class_object_size`), and pay the associated declare fees/gas — no special privileges, network position, or protocol violation is required. Repeating this `class_cache_size` (or `contract_cache_size`) times is sufficient to fully "poison" the caches with maximum-size entries.

### Recommendation
Track aggregate byte size of cached entries (similar to how `apollo_mempool` already tracks `capacity_in_bytes` via `total_bytes()`/`size_in_bytes()`) and evict based on a byte budget rather than (or in addition to) entry count, for `GlobalContractCache` (`crates/starknet_api/src/class_cache.rs`), `CachedClassStorage` (`crates/apollo_class_manager/src/class_storage.rs`), and the blockifier's `RawClassCache` (`crates/blockifier/src/state/global_cache.rs`, `contract_class_manager.rs`, `native_class_manager.rs`). Alternatively/also, size caches conservatively for the worst case (`cache_size * max_object_size`) rather than assuming average-sized entries, and expose a metric for total cached bytes to detect drift.

### Proof of Concept
1. Deploy/observe a node with default config (`class_cache_size = 128`, `max_contract_class_object_size ≈ 4 MB`, `max_compiled_contract_class_object_size ≈ 4 MB` from `crates/apollo_deployments/resources/app_configs/class_manager_config.json` and `gateway_config.json`).
2. From an account (or multiple accounts) with sufficient fee balance, submit ≥128 distinct Declare V3 transactions, each with a unique Sierra program crafted to be as close as possible to `max_contract_bytecode_size`/`max_contract_class_object_size` (e.g. large dead-code arrays), all of which individually pass `validate_class_length` in `crates/apollo_gateway/src/stateless_transaction_validator.rs:315-337`.
3. Observe that `CachedClassStorage`'s `classes`/`executable_classes`/`deprecated_classes` caches in `crates/apollo_class_manager/src/class_storage.rs` (and the blockifier's `RawClassCache`) fill entirely with maximum-size entries, since `GlobalContractCache::set` (`crates/starknet_api/src/class_cache.rs:27-29`) only tracks count via `SizedCache`, never aggregate bytes.
4. Measure process RSS for the class manager / gateway / batcher process before and after; it grows to approach `cache_size * max_object_size` per cache instance, well above memory usage observed under representative real-world class sizes, demonstrating the count-only bound does not protect against adversarially-sized legitimate inputs.

pub struct GlobalContractCache<T: Clone>(pub Arc<Mutex<ContractLRUCache<T>>>);

impl<T: Clone> GlobalContractCache<T> {
    /// Locks the cache for atomic access. Although conceptually shared, writing to this cache is
    /// only possible for one writer at a time.
    pub fn lock(&self) -> LockedClassCache<'_, T> {
        self.0.lock().expect("Global contract cache is poisoned.")
    }

    pub fn get(&self, class_hash: &ClassHash) -> Option<T> {
        self.lock().cache_get(class_hash).cloned()
    }

    pub fn set(&self, class_hash: ClassHash, contract_class: T) {
        self.lock().cache_set(class_hash, contract_class);
    }

    pub fn clear(&mut self) {
        self.lock().cache_clear();
    }

    pub fn new(cache_size: usize) -> Self {
        Self(Arc::new(Mutex::new(ContractLRUCache::<T>::with_size(cache_size))))
    }
