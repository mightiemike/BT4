### Title
Gas fee accounting truncates to zero when the network base fee is below 1 `upc`, letting payload execution run free — (File: `x/uexecutor/keeper/fees.go`)

### Summary
`Pallet::repay_borrow_internal`'s bug class — resetting an accrual index to the "current" value without ever accruing/charging what was owed — has a native analog in Push Chain's `x/uexecutor` gas-fee accounting path. `CalculateGasCost` unwraps the `LegacyDec`-encoded base fee back into whole `upc` units via integer division by `1e18` **before** using it to price gas, and `DeductGasFeesFromReceipt` silently skips fee deduction whenever the computed cost is `<= 0`. Any base fee smaller than `1e18` internal units (i.e. less than 1 `upc`) truncates to `0`, so a real `executeUniversalTx` call that consumes real EVM gas can be charged **zero** fee — exactly like the Substrate report's zero-repay letting a user reset the borrow index without paying anything.

### Finding Description
`CalculateGasCost` computes the effective gas price like this: [1](#0-0) 
`baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` truncates any fractional-`upc` base fee down to `0` before it is ever compared against `maxFeePerGas` or multiplied by `gasUsed`.

`DeductGasFeesFromReceipt` then treats a zero (or negative) computed cost as "nothing to charge" and returns without deducting or even logging a failure: [2](#0-1) 

The only early-out guard is `receipt.GasUsed == 0`, which does not protect against this case — `receipt.GasUsed` can be large (real EVM execution happened) while `gasCost` is still zero purely because of the truncating division. `DeductGasFeesFromReceipt` is invoked from the `MsgExecutePayload` path (any unprivileged user, gasless Cosmos message) documented in `x/uexecutor/README.md`: [3](#0-2) 

So whenever the on-chain `feemarket` base fee (as returned by `k.feemarketKeeper.GetBaseFee`) is non-zero but represents less than 1 whole `upc` — which is exactly the state produced by `no_base_fee: true` / `base_fee: "0.000000000000000000"` genesis configurations seen in the repo's own e2e harness — every payload execution through a UEA is executed with real state changes and real EVM gas consumption but bills the UEA's balance nothing.

### Impact Explanation
This corrupts gas-fee accounting for module-originated EVM execution (`DerivedEVMCall`/`CallUEAExecutePayload`), one of the explicitly in-scope invariants ("corruption of ... gas fee accounting ... revert destination ... or canonical UniversalTx state"). An attacker who can drive or find the network into a low/zero-base-fee regime gets free EVM execution paid for by validators' actual compute resources without ever paying the protocol, systematically draining the intended fee revenue and breaking the "gas must always be billed to the executing account" invariant relied on elsewhere in the codebase (e.g. `applyGasRefund`, which assumes `GasFee` was actually charged upstream).

### Likelihood Explanation
Reachability depends entirely on network configuration: production deployments set `min_gas_price`/`base_fee` to `1e9` (well above the 1-`upc` truncation floor), which as configured prevents this from being reachable under normal operating conditions. It is only directly demonstrable when `no_base_fee` is enabled or the base fee has decayed under 1 `upc` — a state the repo's own interchaintest defaults intentionally create. Because whether this is exploitable in a live deployment hinges on operator-controlled `feemarket` parameters rather than a purely code-level guarantee, likelihood is best characterized as configuration-dependent rather than universally reachable by an unprivileged attacker against default hardened settings.

### Recommendation
- Do not truncate the base fee to whole `upc` before pricing; keep full `LegacyDec` precision through the gas-cost calculation and only round once, at the very end, always rounding up (`Ceil`) rather than down, so residual value under 1 `upc` is still billed rather than dropped.
- Change `DeductGasFeesFromReceipt`'s early-out to distinguish "gasCost computed as exactly zero because baseFee is truly zero (by design/no_base_fee)" from "gasCost truncated to zero due to precision loss when GasUsed > 0" — the latter should still charge at least 1 `upc` (or fail loudly) rather than silently skip.
- Add unit tests mirroring the report's recommendation for edge cases: sub-1-`upc` base fee with non-zero `GasUsed`, and `no_base_fee=true` genesis, asserting fees are either correctly computed with full precision or explicitly and intentionally free (not accidentally free via truncation).

### Proof of Concept
1. Configure (or drive via sustained low EVM block utilization under `no_base_fee=false`) `feemarketKeeper.GetBaseFee` to return a `LegacyDec` value less than `1e18` (e.g. `5e17`, i.e. 0.5 `upc`), or set `no_base_fee: true` as in `interchaintest/setup.go`.
2. Submit an ordinary `MsgExecutePayload` whose payload performs a real state-changing call through the sender's UEA (e.g. an ERC20 transfer), with any valid `maxFeePerGas`.
3. Observe the receipt: `GasUsed > 0` and real state changes were committed via `CallUEAExecutePayload`/`DerivedEVMCall`.
4. Observe `DeductGasFeesFromReceipt`: `CalculateGasCost` returns `0` because `baseFeeBig.Div(baseFeeBig, 1e18)` truncated the base fee to `0`; the function returns `nil` without touching the recipient's balance — the UEA owner paid nothing for real, gas-consuming execution.
