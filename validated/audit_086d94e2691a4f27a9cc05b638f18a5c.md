### Title
Panic inside `WorkerExecutor` while holding the shared `ThreadSafeVersionedState` mutex poisons the lock and permanently halts/aborts concurrent block execution — (File: `crates/blockifier/src/concurrency/versioned_state.rs`)

### Summary
The concurrent transaction executor guards all versioned state (storage, nonces, class hashes, declared contracts) behind a single `Arc<Mutex<OptionalVersionedState<S>>>` shared by every worker thread. Several state-mutating operations execute internal consistency `assert_eq!` checks *while the mutex is held*. A crafted transaction that drives the versioned state into an inconsistent condition triggers one of these asserts, panics while the lock is held, and poisons the `Mutex`. Every other worker thread that subsequently calls `.lock()` on the same mutex (via `VersionedStateProxy::state()`) then panics as well, because `.lock()` on a poisoned mutex returns `Err`, and the code unconditionally `.expect()`s success. This is the direct analog to CVE-2020-14848's class of bug: an internal invariant violation reachable by an external, lower-privileged actor (a transaction sender/contract) that causes a hang/crash of the server component (here, the sequencer's block-building/execution engine) rather than data corruption.

### Finding Description
`ThreadSafeVersionedState<S>` wraps a `VersionedState<S>` in `Arc<Mutex<OptionalVersionedState<S>>>` [1](#0-0) . Every read/write access from a `VersionedStateProxy` (used by every worker thread executing a transaction concurrently) goes through:

```
fn state(&self) -> LockedVersionedState<'_, S> {
    self.state.lock().expect("Failed to acquire state lock.")
}
``` [2](#0-1) 

`VersionedState::apply_writes` and `VersionedState::validate_reads` — both called *while the mutex is locked* — contain internal invariant assertions:

```
for (&key, &value) in &writes.declared_contracts {
    self.declared_contracts.write(tx_index, key, value);
    assert_eq!(
        value,
        self.compiled_contract_classes.read(tx_index, key).is_some(),
        "The declared contracts mapping should match the compiled contract classes mapping."
    );
}
``` [3](#0-2) 

and an equivalent `assert_eq!` in `validate_reads`: [4](#0-3) 

These are called from `execute_tx`/`validate`/`commit_tx` in `worker_logic.rs`, all of which are reached directly from executing a submitted transaction inside a concurrently-executed block: [5](#0-4) [6](#0-5) 

If any of these asserts fails while the shared mutex is held, the panic unwinds through the `MutexGuard`'s `Drop`, which marks the `Mutex` as poisoned (standard Rust `std::sync::Mutex` semantics). Every other worker thread's subsequent call to `self.state.lock()` — in `VersionedStateProxy::state()`, `ThreadSafeVersionedState::into_inner_state()`, and all `StateReader`/`UpdatableState` trait methods implemented for `VersionedStateProxy` — will now also panic via `.expect("Failed to acquire state lock.")`: [7](#0-6) [8](#0-7) 

`WorkerPool::_run_executor` catches the initial panic with `panic::catch_unwind`, but the recovery path itself calls `worker_executor.scheduler.halt()` (which may again touch shared state) guarded by an `AbortIfPanic` sentinel whose `Drop` calls `std::process::abort()` if *that* code panics, and then unconditionally `panic::resume_unwind(err)`s the original error, tearing down that worker thread: [9](#0-8) 

Because every worker thread shares the same `WorkerExecutor`/`ThreadSafeVersionedState` for the in-progress chunk, a poisoned mutex or a torn-down thread cascades: all sibling threads attempting to access state for the same block will themselves panic (each caught individually by their own `_run_executor`, each again calling `halt()`/potentially hitting `AbortIfPanic`), and `WorkerPool::check_panic()`/`run_and_wait` will subsequently `panic!("One of the threads panicked.")` at the call site in `TransactionExecutor`/`ConcurrentTransactionExecutor`, propagating up into the batcher's block-building path.

### Impact Explanation
This is a hang/crash denial-of-service of the sequencer's block-building component, directly analogous to CVE-2020-14848 (a hang/crash of MySQL InnoDB caused by an internal consistency violation reachable via normal operations). Concretely: once triggered, the mutex-poisoning cascades to every concurrently-executing worker thread for the current chunk, the current block build is aborted via cascading panics, and — depending on which code path panics next while holding `AbortIfPanic` — the process can be terminated outright via `std::process::abort()`. Either outcome (repeated panics that keep failing new blocks, or a hard process abort) satisfies "a network unable to confirm new transactions" for that node, since a crashed/aborted sequencer process cannot build or propose blocks until restarted.

### Likelihood Explanation
The trigger requires reaching one of the `assert_eq!` invariant violations in `VersionedState::apply_writes`/`validate_reads` regarding the declared-contracts vs. compiled-contract-classes mapping consistency. This is gated behind concurrency-mode execution (`concurrency_config.enabled`), and the exact transaction shape needed to desynchronize `declared_contracts` from `compiled_contract_classes` under concurrent re-execution/abort/retry semantics was not fully traced in this investigation — specifically, I could not confirm from the available code whether a normal class-declaration + abort/re-execute sequence under contention can actually desynchronize the two versioned maps, or whether the invariant is unconditionally maintained by construction. This uncertainty means likelihood cannot be assessed as concretely "easy" without further tracing of `delete_writes`/abort/retry interleavings in `scheduler.rs` and `worker_logic.rs` under the exact chunk/scheduler state machine.

### Recommendation
- Ensure that any mutating operation performed on `VersionedState` while the shared `Mutex` is held cannot panic on attacker-influenced input; convert internal invariant `assert_eq!`s in `apply_writes`/`validate_reads` (crates/blockifier/src/concurrency/versioned_state.rs) into recoverable errors (e.g., `VersionedStateError`) that are propagated instead of panicking.
- Avoid calling `.expect()` on `Mutex::lock()` results in `VersionedStateProxy::state()`/`ThreadSafeVersionedState::into_inner_state()`; either use `parking_lot::Mutex` (which does not poison) for this shared state, or explicitly recover from `PoisonError` by extracting the inner guard.
- Audit `worker_pool.rs`'s panic-recovery path so a panic inside one worker's transaction execution cannot poison state shared with other in-flight workers for the same chunk, and cannot itself trigger `std::process::abort()` via `AbortIfPanic` as a side effect of ordinary transaction-triggered invariant violations.

### Proof of Concept
Not fully reproducible from static analysis alone. The theoretical trigger is: submit a class declaration (or a mix of declare + subsequent calls) whose execution/abort/retry cycle under the optimistic concurrency scheduler (`crates/blockifier/src/concurrency/scheduler.rs`) causes `VersionedState::apply_writes` or `validate_reads` to observe `declared_contracts` and `compiled_contract_classes` in a state where the equality assumed by the `assert_eq!` at [3](#0-2)  no longer holds (e.g., through an abort that calls `delete_writes` on one map but not fully synchronized with the other, or a re-execution ordering where `set_initial_value` for one map races the write on the other). Confirming an exact transaction sequence would require instrumenting/tracing `VersionedStorage::delete_write`/`write`/`read` interactions across `execute_tx` → `validate` → abort → re-execute cycles, which was not completed in this pass — this should be validated by a dynamic test (e.g., a fuzz/property test driving the scheduler flow test in `flow_test.rs` with declare transactions and forced aborts) before treating this as confirmed-exploitable rather than a structural risk.

pub type LockedVersionedState<'a, S> = MutexGuard<'a, OptionalVersionedState<S>>;

impl<S: StateReader> ThreadSafeVersionedState<S> {
    pub fn new(versioned_state: VersionedState<S>) -> Self {
        ThreadSafeVersionedState(Mutex::new(OptionalVersionedState(Some(versioned_state))).into())

    pub fn pin_version(&self, tx_index: TxIndex) -> VersionedStateProxy<S> {
        VersionedStateProxy { tx_index, state: self.0.clone() }
    }

    pub fn into_inner_state(&self) -> VersionedState<S> {
        let mut opt_version_state = self.0.lock().expect("Failed to acquire state lock.");
        opt_version_state.0.take().expect("Versioned state was already consumed.")
    }

    fn validate(&self, tx_index: TxIndex, commit_phase: bool) -> Result<bool, VersionedStateError> {
        self.metrics.count_validate();
        let tx_versioned_state = self.state.pin_version(tx_index);
        let Some(execution_output) = self.lock_execution_output_opt(tx_index) else {
            // If the execution output is missing, it means that the transaction was already
            // committed. This can happen if `commit_tx` precedes the `validation_index` run.
            // In this case, treat it as valid.
            assert!(!commit_phase, "Missing execution output in commit phase.");
            let status = self.scheduler.get_tx_status(tx_index);
            assert_eq!(
                status,
                TransactionStatus::Committed,
                "Missing execution output with tx_status={status:?}",
            );
            return Ok(true);
        };
        let reads = &execution_output.reads;
        let reads_valid = tx_versioned_state.validate_reads(reads)?;

        let aborted = !reads_valid && self.scheduler.try_validation_abort(tx_index, commit_phase);
        if aborted {
            self.metrics.count_abort();
            tx_versioned_state
                .delete_writes(&execution_output.state_diff, &execution_output.contract_classes)?;
            self.scheduler.finish_abort(tx_index);
        }
        Ok(reads_valid)

    fn _run_executor(&self, worker_executor: &WorkerExecutor<S>) {
        if self.a_thread_panicked.load(Ordering::Acquire) {
            panic!("Another thread panicked. Aborting.");
        }

        // Making sure that the program will abort if a panic occurred while halting
        // the scheduler.
        let abort_guard = AbortIfPanic;
        // If a panic is not handled or the handling logic itself panics, then we
        // abort the program.
        let res = panic::catch_unwind(panic::AssertUnwindSafe(|| {
            worker_executor.run();
        }));
        if let Err(err) = res {
            // First, set the panic flag. This must be done before halting the scheduler.
            self.a_thread_panicked.store(true, Ordering::Release);

            // If the program panics here, the abort guard will exit the program.
            // In this case, no panic message will be logged. Add the cargo flag
            // --nocapture to log the panic message.

            worker_executor.scheduler.halt();
            abort_guard.release();
            panic::resume_unwind(err);
        }

        abort_guard.release();
    }
