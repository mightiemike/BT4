## Analog Found: Non-Injective Key Derivation Allows Field-Boundary Collision in UTX/Outbound Identity Hashing

### Title
Colon-delimited, non-injective hashing in `GetInboundUniversalTxKey` / `GetPcUniversalTxKey` / `GetOutboundRevertId` / `GetRescueFundsOutboundId` can let one field's content shift the key boundary and collide with a different logical tuple — ([File: x/uexecutor/types/keys.go])

### Summary
The external report's bug class is: a delimiter-joined value (`name:value`) is hashed/parsed without validating that the components can't themselves contain the delimiter, so one field can "leak" into a neighboring field's territory. `x/uexecutor/types/keys.go` contains the exact same pattern for a critical identity primitive — the canonical `UniversalTx` key — right next to the codebase's own purpose-built fix for this exact problem (`hashFields`), which it does not use.

### Finding Description
`GetInboundUniversalTxKey` builds the canonical UTX identity as: [1](#0-0) 
i.e. `sha256(fmt.Sprintf("%s:%s:%s", chain, txHash, logIndex))`. The same repository defines `hashFields`, explicitly built to prevent exactly this class of collision: [2](#0-1) 
The comment states plainly: *"Per-field hashing makes it injective — a sub-hash can't contain ':', so no field value can shift a boundary and collide with a different tuple."* `GetInboundBallotKey` and `GetOutboundBallotKey` use `hashFields` correctly: [3](#0-2) [4](#0-3) 
But `GetInboundUniversalTxKey`, `GetPcUniversalTxKey`, `GetOutboundRevertId`, and `GetRescueFundsOutboundId` do not: [5](#0-4) [6](#0-5) 

The fields fed into these naive concatenations (`SourceChain`, `TxHash`, `LogIndex`) are only "lenient-canonicalized," and the canonicalizers explicitly fall back to the **raw, trimmed, unrestricted input** whenever the value doesn't match the strict per-namespace form: [7](#0-6) [8](#0-7) 
For any namespace other than `eip155`/`solana` (the `default:` branch), or for any value that fails strict validation, the function returns the value untouched — colons and all. `Inbound.ValidateBasic()` only requires `SourceChain` to *contain* a colon and `LogIndex`/`TxHash` to be non-empty; it never restricts the character set or colon count: [9](#0-8) 

This is structurally identical to the report: the "header field name" (here, `chain`/`txHash`) is trusted not to contain the delimiter, but nothing enforces that, and the consuming function (`GetInboundUniversalTxKey`) hashes the raw joined string instead of hashing fields independently.

### Impact Explanation
If two logically distinct `(source_chain, tx_hash, log_index)` tuples can be made to serialize to the same `chain:txHash:logIndex` string (e.g. `chain="A", txHash="B:C", logIndex="D"` vs. `chain="A:B", txHash="C", logIndex="D"`), they hash to the identical UTX key. `VoteInbound` treats `HasUniversalTx(ctx, universalTxKey)` as the sole existence guard before creating a new UTX: [10](#0-9) 
A collision here would let one already-finalized UTX record block/short-circuit — or be mistaken for — a distinct logical inbound event, corrupting canonical UniversalTx identity, which the module documents as "the only object ... that the rest of the protocol needs to read." This falls squarely under "corruption of ... canonical UniversalTx state" and "cross-linked inbound ... state accepted through user-reachable flows."

### Likelihood Explanation
Low-to-uncertain for the two namespaces currently wired up in production (`eip155`, `solana`): `CanonicalizeEVMHash` strictly requires 32-byte hex and `canonicalizeSolanaTxHash` strictly requires base58/hex, so a genuine on-chain EVM/Solana transaction hash cannot itself contain a colon, and honest UVs report real chain data — so today's practical exploitation requires either (a) a chain configured under a different/generic CAIP-2 namespace (the code's own `default:` fallback branches, and the `UniversalAccountId` test fixtures referencing a `"cosmos"` namespace, suggest this is an anticipated extension point) where tx-hash/address format isn't constrained at all, or (b) a value that fails strict EVM/Solana parsing and therefore falls through to the unrestricted raw-trimmed path. I could not confirm from the indexed code whether any currently-registered `ChainConfig` uses a non-EVM/non-SVM namespace, so I cannot assert this is exploitable today without further investigation — but the underlying primitive is provably non-injective and inconsistent with the same file's own documented safe pattern.

### Recommendation
Route `GetInboundUniversalTxKey`, `GetPcUniversalTxKey`, `GetOutboundRevertId`, and `GetRescueFundsOutboundId` through the existing `hashFields` helper (per-field hashing) instead of `fmt.Sprintf("%s:%s:%s", ...)` + single `sha256`, so that no combination of `chain`/`txHash`/`logIndex` content can shift a field boundary. Alternatively, enforce that these fields can never contain `:` (or any delimiter) at `ValidateBasic`/canonicalization time, mirroring the report's recommendation to validate the untrusted "name" component rather than trust it implicitly.

### Proof of Concept
Not independently verified end-to-end (would require confirming a live `ChainConfig` under a namespace whose `LenientCanonicalizeTxHash`/`CanonicalizeAddressByNamespace` default branch accepts arbitrary strings). Conceptually:
1. Register/observe a chain under a namespace not `eip155`/`solana` (or a chain where the tx hash fails strict format checks) so `LenientCanonicalizeTxHash` returns the raw, colon-preserving string.
2. Craft `Inbound{SourceChain:"X", TxHash:"Y:Z", LogIndex:"W"}` and `Inbound{SourceChain:"X:Y", TxHash:"Z", LogIndex:"W"}`.
3. Both produce `sha256("X:Y:Z:W")` via `GetInboundUniversalTxKey`, colliding on the same UTX key despite representing different logical events.

Given the uncertainty about current namespace reachability, this should be treated as a real but not fully confirmed-exploitable-today architectural gap; verifying it requires checking the live `uregistry` `ChainConfig` set and `VmType` enum for non-EVM/non-SVM entries, which was not fully resolvable from the indexed code alone.

// hashFields = sha256( hex(sha256(domain)) : hex(sha256(f0)) : ... ). Per-field
// hashing makes it injective — a sub-hash can't contain ':', so no field value
// can shift a boundary and collide with a different tuple.
func hashFields(domain collections.Prefix, parts ...string) string {
	hashed := make([]string, 0, len(parts)+1)
	d := sha256.Sum256(domain.Bytes())
	hashed = append(hashed, hex.EncodeToString(d[:]))
	for _, p := range parts {
		sum := sha256.Sum256([]byte(p))
		hashed = append(hashed, hex.EncodeToString(sum[:]))
	}
	final := sha256.Sum256([]byte(strings.Join(hashed, ":")))
	return hex.EncodeToString(final[:])
}

// CanonicalizeAddressByNamespace canonicalizes an address for the given
// CAIP-2 chain. Empty input passes through (optional fields).
func CanonicalizeAddressByNamespace(chain, addr string) (string, error) {
	addr = strings.TrimSpace(addr)
	if addr == "" {
		return "", nil
	}
	switch CAIP2Namespace(chain) {
	case namespaceEVM:
		return CanonicalizeEVMAddress(addr)
	case namespaceSolana:
		return canonicalizeSolanaValue(addr)
	default:
		return addr, nil
	}
}

// CanonicalizeTxHashByNamespace canonicalizes a transaction hash/signature
// for the given CAIP-2 chain. Empty input passes through (e.g. failed
// outbound observations carry no hash).
func CanonicalizeTxHashByNamespace(chain, txHash string) (string, error) {
	txHash = strings.TrimSpace(txHash)
	if txHash == "" {
		return "", nil
	}
	switch CAIP2Namespace(chain) {
	case namespaceEVM:
		return CanonicalizeEVMHash(txHash)
	case namespaceSolana:
		return canonicalizeSolanaTxHash(txHash)
	default:
		return txHash, nil
	}
}

// Lenient variants for the vote-ingress / key-derivation path: canonical form
// when the value parses, trimmed input otherwise (never an error). Used there
// because that path must never drop a vote — a malformed inbound still has to
// produce an on-chain UTX record (with a failed PCTx / revert), and
// execution-level validation, not key derivation, is what rejects it. Honest
// observers of the same value still converge (same trimmed string), and the
// injective hashFields digest keeps even malformed values collision-safe.
// Strict (error-returning) variants are for admin/config paths where bad input
// should be rejected before it is persisted.

// LenientCanonicalizeAddress canonicalizes addr for chain, falling back to
// the trimmed input when it does not parse.
func LenientCanonicalizeAddress(chain, addr string) string {
	canon, err := CanonicalizeAddressByNamespace(chain, addr)
	if err != nil {
		return strings.TrimSpace(addr)
	}
	return canon
}

// LenientCanonicalizeTxHash canonicalizes txHash for chain, falling back to
// the trimmed input when it does not parse.
func LenientCanonicalizeTxHash(chain, txHash string) string {
	canon, err := CanonicalizeTxHashByNamespace(chain, txHash)
	if err != nil {
		return strings.TrimSpace(txHash)
	}
	return canon
}

func (p Inbound) ValidateBasic() error {
	// Validate source_chain (must follow CAIP-2 format) — needed for UTX key
	chain := strings.TrimSpace(p.SourceChain)
	if chain == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain cannot be empty")
	}
	if !strings.Contains(chain, ":") {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "source chain must be in CAIP-2 format <namespace>:<reference>")
	}

	// Validate tx_hash — needed for UTX key
	if strings.TrimSpace(p.TxHash) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "tx_hash cannot be empty")
	}

	// Validate sender — needed for revert recipient fallback
	if strings.TrimSpace(p.Sender) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "sender cannot be empty")
	}

	// Validate log_index — needed for UTX key
	if strings.TrimSpace(p.LogIndex) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "log_index cannot be empty")
	}

	// Validate tx_type enum — needed to route execution
	if _, ok := TxType_name[int32(p.TxType)]; !ok || p.TxType == TxType_UNSPECIFIED_TX {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid tx_type: %v", p.TxType)
	}

	return nil
}
