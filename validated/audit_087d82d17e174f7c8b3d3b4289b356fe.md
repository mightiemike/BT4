### Title
Unbounded iteration over attacker-growable `VotesStore` in `MaintenanceManager.doMaintenance()` risks consensus-critical DoS - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
`MaintenanceManager.doMaintenance()` is invoked deterministically by every full node/witness once per maintenance cycle (`~6h`) via `applyBlock()` [1](#0-0) . It calls `countVote(votesStore)`, which performs a full, unbounded iteration over every entry in `VotesStore` [2](#0-1) . Any unprivileged account that casts a `VoteWitnessContract` creates or updates one `VotesStore` entry keyed by the voter's address [3](#0-2) . Because address creation and freezing a minimal amount of TRX for voting power are cheap and unbounded operations available to any unprivileged user, the size of `VotesStore` — and thus the cost of the mandatory per-cycle `countVote` loop executed by every node — is attacker-controllable, mirroring the "unbounded for loop over attacker-inflatable set" bug class described in the report.

### Finding Description
The reported bug class is an unbounded loop whose iteration count is controlled by an unprivileged actor (minting many token holders), causing `distributeDividends` to exceed gas limits. The closest concrete analog in java-tron is the DPoS maintenance step:

- `MaintenanceManager.doMaintenance()` is called automatically at each maintenance cycle boundary from `applyBlock()`, which is called from block-application logic used by every node (`DposService.applyBlock` → `maintenanceManager.applyBlock(blockCapsule)`) [4](#0-3) .
- `doMaintenance()` calls `countVote(votesStore)`, which does `Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator(); while (dbIterator.hasNext()) {...}` — an unbounded, full-table scan over every voter that touched their vote during the epoch [2](#0-1) .
- `VotesStore` entries are written by any account calling `VoteWitnessActuator.countVoteAccount()` (one entry per distinct voter address per epoch, not per-vote): `votesStore.put(ownerAddress, votesCapsule)` [5](#0-4) . This is a normal, unprivileged, low-cost user operation (`VoteWitnessContract`), not a trusted-role or admin action.
- The number of possible distinct voter addresses is unbounded — TRON allows arbitrarily many accounts, and each only needs a small amount of frozen TRX (via `FreezeBalanceV2Contract`) to obtain nonzero "tron power" and satisfy `VoteWitnessActuator.validate()`'s check that `sum <= tronPower` [6](#0-5) .
- Similarly, `doMaintenance()` also unconditionally iterates `consensusDelegate.getAllWitnesses()` multiple times, but that set is naturally bounded by the cost of creating a witness, so it is not the attacker-controllable factor; `VotesStore` is the unbounded one because `votesStore` entries are removed and can be freshly recreated every epoch by cheap voting transactions.

This is directly analogous to the reported pattern: an attacker generates many low-cost "holders" (here, voter accounts with minimal frozen TRX) to inflate the size of a data structure that a privileged, deterministic system routine (analogous to `distributeDividends`) must fully iterate.

### Impact Explanation
`doMaintenance()` executes synchronously as part of block application for every full node and witness in the network at the maintenance-cycle boundary. If the `VotesStore` is inflated to a very large number of entries by an attacker creating many cheap accounts and casting votes, the per-cycle `countVote()` scan (and subsequent forEach loops using `countWitness`) could take substantially longer to execute, potentially exceeding the time budget for block production/validation at that specific block, causing block-production delays, missed slots, or state divergence between nodes with different processing speeds. This falls into the "invalid-state/divergence/halt" impact category described in the validation criteria, because `doMaintenance()` is deterministic core-consensus code executed by every node, not an off-chain/admin path.

### Likelihood Explanation
The attack requires only unprivileged, permissionless actions: account creation and `FreezeBalanceV2Contract` + `VoteWitnessContract` transactions, both available to any user with a small amount of TRX for account activation and minimal freeze amounts (no code-level minimum freeze amount was confirmed in the `FreezeBalanceV2Actuator` snippets found in the index; freezing an arbitrarily small nonzero balance appears sufficient to make voting power positive). The main cost constraint is the TRX needed to activate new accounts and pay bandwidth for the freeze/vote transactions, which bounds the practical scale of the attack but does not eliminate it — this is a resource-cost/economic mitigation rather than an algorithmic one, matching the original report's core problem (unbounded loop with no algorithmic cap), for which the Bridges team's own recommended fix was to remove the `for` loop dependency entirely rather than rely on economic cost alone.

### Recommendation
Refactor `MaintenanceManager.countVote()` / the vote-count accumulation to avoid a full-table scan of `VotesStore` on every maintenance cycle, e.g., by maintaining incremental witness vote deltas as they are cast (similar in spirit to the "points-per-share" pattern referenced in the report), or by capping/batching the number of `VotesStore` entries processed per maintenance cycle to keep the cost bounded regardless of the number of distinct voters.

### Proof of Concept
1. Programmatically create N new accounts (activate each with minimal TRX).
2. For each account, submit `FreezeBalanceV2Contract` with a minimal `frozenBalance` for `BANDWIDTH`/`TRON_POWER`, then submit a `VoteWitnessContract` voting for an existing witness with a tiny vote count — this creates/updates one entry per account in `VotesStore` [5](#0-4) .
3. Repeat for a very large N (bounded only by TRX available to the attacker for account activation/freeze/bandwidth fees).
4. At the next maintenance-cycle boundary, `MaintenanceManager.doMaintenance()` is invoked and `countVote(votesStore)` must iterate all N entries synchronously as part of block application [7](#0-6) [2](#0-1) , measurably increasing block-application latency proportional to N — full exploitation to a network-halting scale was not verified in this analysis due to unknown exact freeze-amount minimums and bandwidth costs, which would need empirical measurement on a testnet to establish the practical attacker cost vs. resulting node-side delay.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
