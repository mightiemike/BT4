### Title
Unbounded gzip decompression of user-supplied Cairo0 declare program allows memory-exhaustion DoS - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
`decompress_program` in the RPC layer decompresses a base64-encoded gzip blob supplied directly by an RPC caller (as part of a Cairo0 `BroadcastedDeclareV1Transaction.contract_class.compressed_program`) with no bound on decompressed size or decompression time, unlike the size-limited decompression helpers used elsewhere in the codebase for equivalent inputs.

### Finding Description
`decompress_program` decodes base64 then wraps the bytes in a `GzDecoder` and calls `read_to_end`, with an explicit `// TODO(dan): add time and size limits.` marking the missing bound: [1](#0-0) 

This function is invoked from `user_deprecated_contract_class_to_sn_api`, which is called during conversion of a `BroadcastedDeclareTransaction::V1` — a transaction type accepted directly from an RPC client via `estimateFee`, `simulateTransactions`, and declare submission flows: [2](#0-1) 

Elsewhere in the same codebase, the equivalent operation for attacker-controlled Sierra/Cairo0 program payloads is implemented with an explicit, enforced size cap: `decode_and_decompress_with_size_limit` in `starknet_api::compression_utils`, which caps output at `max_size` bytes and errors with `SizeLimitExceeded` if exceeded: [3](#0-2) 

That size-limited helper is used, for instance, for the gateway/RPC deprecated declare-transaction path (`convert_to_sierra_contract_class`) and for protobuf class conversion with a `MAX_CAIRO0_PROGRAM_SIZE`: [4](#0-3) [5](#0-4) 

`decompress_program`, however, bypasses this pattern entirely: it calls `GzDecoder::read_to_end` unboundedly, exactly mirroring the CVE-2026-40036 bug class (`zlib.decompress()` without a maximum output size on attacker-controlled compressed input).

### Impact Explanation
A small, highly-compressible gzip payload embedded in a Cairo0 declare transaction's `compressed_program` field can expand to gigabytes in memory when a node processes `starknet_estimateFee`, `starknet_simulateTransactions`, or a declare submission carrying a V1 declare transaction. This causes uncontrolled memory allocation on the node handling the RPC request, which can exhaust process memory and crash or degrade the RPC/sequencer node — a network-availability impact matching "a network unable to confirm new transactions" if it affects sequencer-adjacent RPC/execution nodes processing submitted transactions. Because there is no size or time bound, the attack requires only a single unauthenticated RPC call.

### Likelihood Explanation
High. `BroadcastedDeclareV1Transaction` is a standard, currently-supported request type accepted from any RPC client without special privileges; constructing a gzip decompression bomb is trivial (as shown in the reference PoC) and requires no on-chain state, no fees paid, and no prior interaction.

### Recommendation
Replace the unbounded `GzDecoder::read_to_end` in `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) with a size-limited decompression, consistent with `decompress_with_size_limit`/`decode_and_decompress_with_size_limit` already implemented in `starknet_api::compression_utils`, e.g. wrap the reader with `.take(MAX_SIZE + 1)` before `read_to_end` and reject with an error if the result exceeds the configured maximum (as already done for Cairo0/Sierra program decompression elsewhere in the codebase). Also add a decompression time bound if feasible.

### Proof of Concept
1. Generate a highly compressible payload (e.g., `zlib`/`gzip` of `\x00` repeated for target size) and gzip-compress it at max compression level, producing a small compressed blob with a very high compression ratio (as in the reference PoC's `create_compression_bomb`).
2. Base64-encode the compressed blob and place it as the `compressed_program` field of a `BroadcastedDeclareV1Transaction.contract_class`.
3. Submit this as the `request` parameter to `starknet_estimateFee` or `starknet_simulateTransactions` (or as a declare transaction) against a node exposing the RPC API.
4. The node's `user_deprecated_contract_class_to_sn_api` → `decompress_program` path decompresses the payload with no size bound, allocating memory proportional to the decompressed size (potentially gigabytes from a KB-sized request), causing memory exhaustion/DoS on the node.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}

/// Decodes the provided data with size limits.
// TODO(dan): consider limiting the time it takes to decompress.
pub fn decode_and_decompress_with_size_limit<T: DeserializeOwned>(
    value: &str,
    max_size: usize,
) -> Result<T, CompressionError> {
    let decoded_data = base64::decode(value)?;
    let decompressed_data = decompress_with_size_limit(decoded_data, max_size)?;
    Ok(serde_json::from_reader(decompressed_data.as_slice())?)
}
