### Title
Unbounded `new byte[length]` allocation in `CALLDATACOPY` before bounds/overflow validation - (File: `actuator/src/main/java/org/tron/core/vm/program/invoke/ProgramInvokeImpl.java`)

### Summary
`ProgramInvokeImpl.getDataCopy` allocates `new byte[length]` using an attacker-controlled `length` derived from `lengthData.intValueSafe()` **before** it validates `offset` against `msgData.length`, and the subsequent truncation check `offset + length > msgData.length` is plain `int` addition that can overflow/wrap. This allows a contract executing `CALLDATACOPY` with a large length word (up to `Integer.MAX_VALUE`, since `intValueSafe()` clamps to that value rather than throwing) to force an immediate ~2GB array allocation attempt regardless of the real calldata size.

### Finding Description
The relevant method: [1](#0-0) 

```java
public byte[] getDataCopy(DataWord offsetData, DataWord lengthData) {
  int offset = offsetData.intValueSafe();
  int length = lengthData.intValueSafe();

  byte[] data = new byte[length];   // <-- allocated BEFORE any bounds check

  if (msgData == null) { return data; }
  if (offset > msgData.length) { return data; }
  if (offset + length > msgData.length) {   // <-- plain int addition, can overflow
    length = msgData.length - offset;
  }
  System.arraycopy(msgData, offset, data, 0, length);
  return data;
}
```

Two distinct issues compound here:
1. `data = new byte[length]` executes unconditionally, before any validation that `offset`/`length` are sane relative to the actual `msgData` size. Since `length` comes straight from `lengthData.intValueSafe()`, an attacker who sets the CALLDATACOPY length word to a large value (bounded only by the clamp behavior of `intValueSafe()`, typically up to `Integer.MAX_VALUE` in ethereumJ-derived `DataWord` implementations) forces an allocation of nearly 2GB on every such call — independent of whether `offset` is later found to be out of bounds.
2. The truncation guard `offset + length > msgData.length` uses ordinary `int` arithmetic. If both `offset` and `length` are close to `Integer.MAX_VALUE`, their sum wraps to a negative number, which is not `> msgData.length`, so the truncation branch is skipped. In that specific case the code falls through to `System.arraycopy(msgData, offset, data, 0, length)` with an `offset` that is itself checked against `msgData.length` earlier (`offset > msgData.length` returns early), so a full overflow-driven out-of-bounds `arraycopy` is guarded for `offset`, but the **unconditional huge allocation** in point (1) is not guarded at all.

I was not able to fully verify, within the scope of this investigation, the exact energy-charging order for `CALLDATACOPY` (i.e., whether `EnergyCost.java`/`OperationRegistry.java` compute and deduct energy for the copy length using an overflow-safe (e.g., `BigInteger`-based) memory-expansion formula *before* `Program.java` invokes `getDataCopy`). If the energy formula for CALLDATACOPY's memory-expansion cost also relies on a similarly clamped/overflow-prone value, or if the deduction happens after invoking this method, the huge allocation in point (1) could occur before sufficient energy has been verified/charged for it — this is the "faithful metering" violation the question targets. This ordering could not be confirmed with the tools available in this session.

### Impact Explanation
Regardless of the energy-charging ordering, the unconditional `new byte[length]` allocation is a clear defect: it lets a contract force allocation of an array sized by an attacker-chosen 32-byte length word (clamped only to `Integer.MAX_VALUE`) on every `CALLDATACOPY` execution, independent of the true `msgData` size. Repeated or combined with other opcodes in a single transaction, this can cause significant transient memory pressure on a full node evaluating the transaction — a DoS-via-protocol-implementation impact class, matching "DoS via the TRON protocol implementation" rather than a chain-halting consensus bug.

### Likelihood Explanation
Any unprivileged account can deploy a contract containing `CALLDATACOPY` with a crafted length operand and broadcast a transaction invoking it — no privileged role or special network position is required. The exact feasibility (whether it survives energy accounting and how much energy an attacker must pay to reach the vulnerable allocation) depends on the CALLDATACOPY gas/energy formula in `EnergyCost.java`/`OperationRegistry.java`, which was not confirmed here. If that formula bounds achievable `length` tightly to the attacker's paid energy, exploitability is reduced to a cost/benefit question rather than a free DoS; if it does not, the issue is trivially and cheaply repeatable.

### Recommendation
- In `ProgramInvokeImpl.getDataCopy`, validate and clamp `offset`/`length` against `msgData.length` (and against zero/negative values) **before** allocating `data`, and compute `offset + length` using a wider type (e.g., `long`) to avoid `int` overflow in the bounds check.
- Ensure the energy/gas cost for `CALLDATACOPY` is computed and charged using an overflow-safe (e.g., `BigInteger` or `long`) formula strictly before invoking `getDataCopy`, so no allocation proportional to an unvalidated attacker-supplied length can occur ahead of a matching energy deduction.
