The reported bug class is specific to the Linux kernel's manual `hlist_bl` dentry-cache hash table, where `d_add()`/`__d_rehash()` unconditionally re-links a `dentry->d_hash` node into a bucket without checking whether it is already hashed, corrupting the linked list and causing an infinite loop in `__d_lookup()`. This requires a custom, non-idempotent hash-table implementation where re-insertion of an already-present node corrupts pointers.

protobuf-go's map handling paths (`proto.UnmarshalOptions.unmarshalMap` in `proto/decode.go`, `consumeMap`/`consumeMapOfMessage` in `internal/impl/codec_map.go`, and `mapReflect.Set` in `internal/impl/convert_map.go`) all delegate to Go's built-in `map[K]V` type via `reflect.Value.SetMapIndex` or native map assignment. [1](#0-0) [2](#0-1) [3](#0-2) 

Go's runtime map assignment is idempotent and safe regardless of whether the key already exists — it does not manually manipulate hash bucket linked lists the way the kernel's `hlist_bl_add_head_rcu` did, and there is no equivalent "unhashed vs. hashed" dentry-reuse state to violate. protojson's map decoder also explicitly rejects duplicate keys via `mmap.Has(pkey)` before calling `Set`, which is unrelated to any hash-corruption hazard. [4](#0-3) 

There is no reachable code path in protobuf-go where a message or field cache entry that is already present in an internal hash/linked structure gets unconditionally re-inserted in a way that corrupts that structure and causes an unbounded loop, so this bug class does not have a valid analog in this codebase.
