## Analysis

Reducing the external report's core invariant: a "protective comparison" (slippage min-out check) can be silently bypassed because the check is either skipped or compares against attacker/caller-controlled parameters instead of an independently derived value. The Aptos-native analog I traced is the **replay/proof-verification comparison in `ensure_match_transaction_info`**, which is documented in the code itself as skipping several fields it should be comparing.

### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification during replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay-verify tooling (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/cli/src/commands.rs`) to confirm that locally re-executed transaction outputs match the authenticated `TransactionInfo` recorded on-chain. The function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of the consensus-committed `TransactionInfoV1` and therefore part of the accumulator-proven ledger state.

### Finding Description [1](#0-0) 

The function computes and verifies `write_set_hash` against `state_change_hash` and `event_root_hash` against the recomputed event accumulator root, but the state-checkpoint-related hashes are never compared, as acknowledged by the inline TODO: [2](#0-1) 

These checkpoint hashes are meaningful ledger commitments: `state_checkpoint_hash` and `hot_state_checkpoint_hash` are Sparse-Merkle-Tree roots of world state, and `position_state_checkpoint_hash` is the native-trading position-state root computed only when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled [3](#0-2) . These roots are produced by `DoStateCheckpoint::run`/`compute_position_checkpoint` and folded into `TransactionInfoV1`, which is hashed into the transaction accumulator via `assemble_transaction_infos` [4](#0-3) . In other words, these fields are proof-bearing and accumulator-committed, yet the one function whose stated job is to catch a divergence between local execution and the authenticated ledger data silently ignores them.

### Impact Explanation
Any bug in state-checkpoint-hash computation (e.g., in `do_state_checkpoint.rs`'s `compute_position_checkpoint`, or in the main/hot SMT update path) that causes a node's locally computed state root to diverge from the value actually committed to consensus would not be detected by replay-verify tooling. This is a hard-fork-class blind spot: replay-verify (used by db-tool's `replay_on_archive` and the debugger's transaction-replay path) is precisely the mechanism meant to catch determinism divergence across binary versions/upgrades before it becomes an unnoticed silent fork. Because the comparator returns `Ok(())` even when the state/hot-state/position root diverges, an actual state-commitment bug could pass "verified" replay while the ledger's authenticated root is wrong or a divergent node believes it agrees with the network when it does not.

### Likelihood Explanation
This is a passive, non-exploit-driven latent gap rather than an attacker-triggerable single-transaction bug: it requires a separate, genuine state-root-computation defect to exist for this comparator's blind spot to matter. I could not, within available tool access, find or confirm a concrete state-root computation bug in `do_state_checkpoint.rs`/`sharded_jmt_state.rs` that this gap would currently be masking — the divergence-detection failure is proven, but a concrete corrupting root-cause elsewhere is not confirmed from local code alone.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/enabled) against independently recomputed values before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` in production replay tooling, as the existing TODO already recommends.

### Proof of Concept
Not applicable as a single-transaction exploit — the issue is a verification-coverage gap, not directly attacker-triggerable. Demonstrating real impact requires pairing it with an actual state-root computation defect, which I did not independently confirm in this pass.

**Caveat:** This finding documents a real, code-confirmed gap (the TODO comment itself corroborates it), but because it requires a *second*, independently-proven root-cause bug in state-root computation to produce concrete mainnet impact, and I could not confirm such a companion bug from available context, I flag this with reduced confidence relative to a fully self-contained finding.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
