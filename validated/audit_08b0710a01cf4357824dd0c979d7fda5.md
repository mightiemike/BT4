Based on my investigation, I found a genuine architectural gap, but I could not independently verify a full exploitable chain to a wrong committed root within the time available — the replay/reconciliation logic in `TransactionRestoreBatchController`/`ChunkExecutor` that consumes KV-only-restored state was not fully traced, so I cannot confirm whether downstream transaction replay or accumulator/ledger-info verification would ultimately catch a tampered KV-only restore before it becomes part of a "committed", API-authenticated state. I'm reporting the strongest local candidate I could substantiate, but flagging the unresolved part explicitly.

### Title
`StateSnapshotRestoreMode::KvOnly` restore path writes raw state K/V data to durable storage without verifying the supplied `SparseMerkleRangeProof` against the expected root hash - ([File: storage/aptosdb/src/state_restore/mod.rs])

### Summary
`StateSnapshotRestore::add_chunk` branches on `restore_mode`. For `StateSnapshotRestoreMode::Default` and `StateSnapshotRestoreMode::TreeOnly`, the chunk's value hashes are passed through `JellyfishMerkleRestore::verify_chunk`, which reconstructs the accumulator/Merkle path and checks it against `expected_root_hash` before anything is committed. For `StateSnapshotRestoreMode::KvOnly`, `add_chunk` calls only `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)` and never touches the `proof: SparseMerkleRangeProof` argument at all. [1](#0-0) 

### Finding Description
`StateValueRestore::add_chunk` (the KV-only writer) performs no cryptographic check between the key/value pairs it receives and any Merkle root — it only tracks a monotonically increasing key-hash "progress" cursor and directly persists the chunk via `StateValueWriter::write_kv_batch`. [2](#0-1) 

This is invoked from the restore coordinator's "phase 1.a", which restores a KV-only snapshot selected independently of, and potentially at an earlier version than, the tree snapshot used later for `TreeOnly` verification: [3](#0-2) 

Because `kv_snapshot` and `tree_snapshot` are two independently selected backup manifests/versions, and the `KvOnly` code path performs zero proof verification, any tampering of the KV-only manifest's chunk contents (e.g., a compromised or malicious `BackupStorage` implementation, corrupted download, or bit-flip) would be silently accepted and persisted as the base state at `kv_snapshot.version`. The `TreeOnly` restore that runs later verifies a *different* manifest/version's tree structure and does not re-validate that the earlier KV bytes match any hash it can check — the tree only ever sees leaf hashes, never the raw KV bytes stored by the KV-only phase.

### Impact Explanation
If exploitable end-to-end, this breaks the "restore paths must not reinterpret committed data into a different ledger state" invariant: an operator restoring from an untrusted or compromised backup source could get durably-persisted state values that were never checked against any accumulator/Merkle root, then have subsequent transaction replay (phase 1.b, "only replay KV") execute against this unverified base state. If replay does not independently re-derive and check the intermediate/final state root against a trusted, previously-verified value, this could result in committed state or an authenticated API view diverging from the correct VM/ledger result — a High/Critical-class impact per the gate's proof/commit invariants.

### Likelihood Explanation
I could not confirm the full likelihood because I ran out of investigation budget before tracing:
1. Whether `TransactionRestoreBatchController` with `only_replay_kv`/`kv_only_replay` cross-checks the reconstructed state root against a trusted value before/after replay.
2. Whether `ChunkExecutor`/`TransactionReplayer` independently recompute and verify a state root that would surface a mismatch caused by tampered KV-only input.
3. Whether this restore flow is reachable by anyone other than a node operator who already fully trusts their configured `BackupStorage` (which would make this an operator-trust issue rather than an unprivileged integrity break).

Given (3) in particular, this may fall outside the "unprivileged root cause" requirement of the scan — restore is an administrative/operational flow, and `BackupStorage` is typically operator-configured and implicitly trusted. I was not able to rule this out, so I cannot assert this meets the bar with full confidence.

### Recommendation
- Either verify KvOnly chunks against the same `SparseMerkleRangeProof`/expected root as the paired tree restore (e.g., require and check a hash manifest tying `kv_snapshot.version` data to a trusted root), or clearly document/enforce that `KvOnly` mode must only be used with an already-verified/trusted backup source, and add an explicit reconciliation step after phase 1.b replay that recomputes and checks the resulting root hash against the `tree_snapshot`'s already-verified root before proceeding to phase 2.
- Trace and unit-test the replay-KV-only path (`TransactionRestoreBatchController`, `ChunkExecutor::replay`) to confirm it does or does not catch a corrupted starting KV state, and add an explicit check if it doesn't.

### Proof of Concept
Not constructed — this requires an integration-level PoC (a `BackupStorage` mock that serves a corrupted KV-only chunk while a legitimate tree snapshot/root at a later version is used) plus tracing through `TransactionRestoreBatchController`'s KV-only replay to see whether a state-root mismatch is ever detected. I was unable to build/run this within the available tool budget, so the impact chain beyond `state_restore/mod.rs`'s missing verification is unconfirmed.

struct StateValueRestore<K, V> {
    version: Version,
    db: Arc<dyn StateValueWriter<K, V>>,
}

impl<K: Key + CryptoHash + Eq + Hash, V: Value> StateValueRestore<K, V> {
    pub fn new<D: 'static + StateValueWriter<K, V>>(db: Arc<D>, version: Version) -> Self {
        Self { version, db }
    }

    pub fn add_chunk(&mut self, mut chunk: Vec<(K, V)>) -> Result<()> {
        // load progress
        let progress_opt = self.db.get_progress(self.version)?;

        // skip overlaps
        if let Some(progress) = progress_opt {
            let idx = chunk
                .iter()
                .position(|(k, _v)| CryptoHash::hash(k) > progress.key_hash)
                .unwrap_or(chunk.len());
            chunk = chunk.split_off(idx);
        }

        // quit if all skipped
        if chunk.is_empty() {
            return Ok(());
        }

        // save
        let mut usage = progress_opt.map_or(StateStorageUsage::zero(), |p| p.usage);
        let (last_key, _last_value) = chunk.last().unwrap();
        let last_key_hash = CryptoHash::hash(last_key);

        // In case of TreeOnly Restore, we only restore the usage of KV without actually writing KV into DB
        for (k, v) in chunk.iter() {
            usage.add_item(k.key_size() + v.value_size());
        }

        // prepare the sharded kv batch
        let kv_batch: StateValueBatch<K, Option<V>> = chunk
            .into_iter()
            .map(|(k, v)| ((k, self.version), Some(v)))
            .collect();

        self.db.write_kv_batch(
            self.version,
            &kv_batch,
            StateSnapshotProgress::new(last_key_hash, usage),
        )
    }

    fn add_chunk(&mut self, chunk: Vec<(K, V)>, proof: SparseMerkleRangeProof) -> Result<()> {
        match self.restore_mode {
            StateSnapshotRestoreMode::KvOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            },
            StateSnapshotRestoreMode::TreeOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_add_chunk"]);
                self.tree_restore
                    .lock()
                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks
                // from min(kv_progress, tree_progress)) would land bytes in (kv_progress,
                // tree_progress] that the tree side skips and therefore does not re-verify.
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_verify_chunk"]);
                    self.tree_restore
                        .lock()
                        .as_mut()
                        .unwrap()
                        .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;
                }
            },
        }

        Ok(())
    }
