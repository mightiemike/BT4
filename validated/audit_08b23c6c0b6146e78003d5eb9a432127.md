### Title
Corrupted revert-info original values on Cairo0 entry-point failure due to un-restored moved state - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
`DeprecatedSyscallHintProcessor::new` moves (`mem::take`s) the `original_values` map out of `context.revert_infos.0[revert_info_idx]` into the handler for the duration of a Cairo0 entry-point call, and only moves it back via `finalize()` when the call finishes successfully. If the call errors out anywhere between creation of the handler and `finalize()`, the corresponding `EntryPointRevertInfo.original_values` entry in the shared `context.revert_infos` vector is left empty, even though the vector entry itself is not removed.

### Finding Description
`DeprecatedSyscallHintProcessor::new` (crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:237-275) does: [1](#0-0) 
This takes ownership of `original_values` out of the shared `context.revert_infos` stack (which is indexed by `revert_info_idx`), leaving an empty map behind in the vector entry, and tracks changes locally in the handler for the duration of the call. The intent is for `finalize()` to move it back: [2](#0-1) 

`finalize()` is only invoked from `finalize_execution` in crates/blockifier/src/execution/deprecated_entry_point_execution.rs, as the last step before building `CallInfo`: [3](#0-2) 

`execute_entry_point_call` uses Rust's `?` to propagate the errors of `run_entry_point` (VM execution failure) and of `validate_run`/other steps inside `finalize_execution` before reaching `syscall_handler.finalize()`: [4](#0-3) [5](#0-4) 

In either error path, `syscall_handler` (and the `original_values` it holds) is dropped, and `context.revert_infos.0[revert_info_idx].original_values` remains the empty map installed by `mem::take` at construction time — the pre-call original storage values captured for that frame are permanently lost from the shared `context.revert_infos` structure, exactly mirroring the reported bug class: a stack/registry entry is pushed (here, values are "checked out") and the matching restore/cleanup step is skipped on any error path reachable via `?`.

This matters because `context.revert_infos` is consulted by:
- `EntryPointExecutionContext::revert` (crates/blockifier/src/execution/entry_point.rs:532-548), which restores `original_values` into storage when an *outer* call reverts a range of frames (`drain(revert_idx..)`), and
- `DeprecatedSyscallHintProcessor::set_contract_storage_at` (crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:401-437), which searches sibling/inner frames' `original_values` (`.skip(self.revert_info_idx + 1)`) to find the "true" pre-write value for a storage key when a caller frame writes to a key that an inner (now-corrupted) frame already touched.

If a Cairo0 inner call fails with a VM/`PostExecutionError` after having written storage (writes go directly to `state` — see `set_contract_storage_at` line 434 — regardless of subsequent failure), and that inner call's frame's `original_values` is subsequently wiped to `{}` by this bug instead of holding the true pre-write values, then a later revert of an *ancestor* frame that includes this frame's index range will restore `state.set_storage_at` using whatever a *sibling* find-or-state-fallback determines — since the map is empty, `set_contract_storage_at` for an ancestor's own write to the same key would fall back to re-reading `state.get_storage_at` (which now contains the failed inner call's leftover writes) instead of the original value from before the inner call started. `EntryPointExecutionContext::revert` (lines 534-537) also simply skips restoring that key for the corrupted frame, since its `original_values` is empty, leaving the (uncommitted-per-protocol) storage write from the failed inner call in place when the range is later reverted.

### Impact Explanation
This can result in storage writes made by a Cairo0 entry point call that failed (and should have no effect) surviving a later revert of an ancestor call/transaction segment, because the bookkeeping needed to know what to roll back to has been silently discarded. This is a state-consistency bug that can lead to storage values differing from what the protocol intends after a revert — a form of the "inconsistent transaction stack" described in the report, applied to blockifier's Cairo0 (deprecated) execution's revert-info bookkeeping.

### Likelihood Explanation
Reachable purely from a normal transaction: any Cairo0 contract entry point (call_contract / library_call / delegate_call / deploy syscalls, or nested constructor calls) that writes storage and then fails (VM error, security validation error in `validate_run`, resource errors, etc.) before its own `finalize()` runs triggers this. Cairo0 contracts are still supported/declarable and callable in this codebase (`CairoVersion::Cairo0` is exercised throughout `blockifier`'s test suite), so the path is reachable by an ordinary contract call from an unprivileged sender without special privileges.

### Recommendation
Do not use ownership-transfer-plus-explicit-restore for `original_values`. Either:
- Use a Drop guard on `DeprecatedSyscallHintProcessor` (or a dedicated RAII wrapper) that always writes `original_values` back into `context.revert_infos.0[revert_info_idx]` on drop, regardless of the success/failure path, or
- Keep `original_values` accessed by reference (e.g., via index) rather than taken out via `mem::take`, so no separate "put back" step is required, mirroring how `context.tracked_resource_stack.push`/`pop` in `execute_entry_point_call_wrapper` (crates/blockifier/src/execution/execution_utils.rs:73-75) is guarded by the comment "no return statements should be added between the push and the pop" — the same invariant needs to hold (or be structurally enforced) for the `original_values` take/finalize pair.

### Proof of Concept
Conceptually (cannot execute a live PoC here, but the logical trace is):
1. Contract A (Cairo0) is called; `CallEntryPoint::execute` pushes a fresh `EntryPointRevertInfo` for A (crates/blockifier/src/execution/entry_point.rs:211-216).
2. A's execution creates `DeprecatedSyscallHintProcessor` (hint_processor.rs:238-275), taking A's `original_values` map out of `context.revert_infos`.
3. A calls `storage_write` on key `k`, which lazily records the pre-write value of `k` into the handler's *local* `original_values` (hint_processor.rs:401-437), then writes `k` directly to `state` (line 434).
4. A's execution subsequently fails with a VM error or `PostExecutionError` (e.g. a security validation failure in `validate_run`), so `execute_entry_point_call` / `finalize_execution` return `Err` via `?` before calling `syscall_handler.finalize()` (deprecated_entry_point_execution.rs:62, 243-247, 275). The handler (and its populated `original_values` for `k`) is dropped, leaving `context.revert_infos.0[idx].original_values` as the empty map from step 2.
5. If an ancestor call later reverts a range that includes A's frame index (`EntryPointExecutionContext::revert`, entry_point.rs:532-548), the loop finds no entry for `k` in A's (now-empty) `original_values` and therefore does not restore `k`, leaving A's write to `k` in place in `state` even though the whole subtree containing A was supposed to be rolled back.         for contract_revert_info in self.revert_infos.0.drain(revert_idx..).rev() {
