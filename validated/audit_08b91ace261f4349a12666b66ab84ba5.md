### Title
Active-permission delegation of `AccountPermissionUpdateContract` allows non-owner key to rewrite Owner/Witness/Active permissions, enabling witness key hijack - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator.checkPermission` validates a submitted `Permission.Witness` block only for `keysCount==1` and a valid weight/threshold, but never confirms that the transaction updating permissions was itself authorized by the account's Owner permission. Because `AccountPermissionUpdateContract` is not excluded from the set of contract types an Active permission's `operations` bitmap may legally include, an attacker holding only an Active key whose bitmap includes that bit can broadcast a self-authorized `AccountPermissionUpdateContract` and overwrite the account's Owner, Witness, and Active permissions, including replacing the Witness permission's sole key with an address of their choosing.

### Finding Description
`TransactionCapsule.validateSignature` (chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java, lines 468-496) resolves the permission to check purely from `contract.getPermissionId()`. If `permissionId != 0`, `checkPermission(permissionId, permission, contract)` (lines 635-645) only demands that the resolved permission `getType() == Active` and that `checkPermissionOperations(permission, contract)` shows the relevant `ContractType` bit set — there is no special-case requirement that `AccountPermissionUpdateContract` must be signed under the Owner permission (`permissionId == 0`). [1](#0-0) [2](#0-1) 

On the actuator side, `AccountPermissionUpdateActuator.checkPermission` validates the `operations` bitmap of an Active permission being *set* against `dynamicStore.getAvailableContractType()` — i.e., it only rejects bits that are not "known" contract types, and does not exclude `AccountPermissionUpdateContract` from being a delegable active operation. [3](#0-2) 

The test `checkAvailableContractTypeCorrespondingToCode` confirms that only `ClearABIContract` and `UpdateBrokerageContract` are excluded from the "available" bitmap — `AccountPermissionUpdateContract` is *not* excluded, so it can legally be one of the bits set in an Active permission's operations. [4](#0-3) 

Once signature/weight validation passes (via the attacker's Active key), `AccountPermissionUpdateActuator.execute` unconditionally calls `account.updatePermissions(...)` with whatever Owner/Witness/Active permission fields were supplied in the contract, with no re-check that the caller held Owner-level weight. [5](#0-4) 

Separately, and compounding the issue, the Witness-branch check itself never verifies the single supplied Witness key belongs to the actual witness signer — it only checks `keysCount == 1`, a valid address, positive weight, and threshold ≤ weight sum. [6](#0-5) 

Combined, if a witness account's owner ever grants an Active permission whose operations bitmap includes the `AccountPermissionUpdateContract` bit (which is a legal/available bit, not blacklisted), the holder of that Active key alone — without any Owner-level signature — can submit an `AccountPermissionUpdateContract` transaction (`permissionId` pointing at their own Active permission) that rewrites the account's Owner permission, Active permissions, and Witness permission (setting the sole Witness key to an address the attacker controls or an unrelated address), completely bypassing the intended Owner-only control over permission structure changes.

### Impact Explanation
This is an authorization-enforcement bypass: permission-structure mutation (which should require Owner-level signing weight) can be performed with only Active-level signing weight, as long as the bitmap for `AccountPermissionUpdateContract` was ever granted to that Active permission. Concrete impact matches the scoped question: an attacker with only an active key of a witness account can silently reassign or brick that witness's block-signing key, and can also rewrite the Owner permission itself (an unauthorized account-permission state change), which maps to TRON's "unauthorized account operations" bounty class.

### Likelihood Explanation
Exploitability hinges entirely on whether the target witness account's Active permission bitmap includes the `AccountPermissionUpdateContract` bit. This bit is not excluded by protocol default-exclusion logic (only `ClearABIContract`/`UpdateBrokerageContract` are excluded), so any owner who grants a broad/"all-operations" Active permission to a delegate/co-signer (a common multisig-delegation pattern) is exposed. No special privilege beyond holding such an Active key is required, cost is a single normal transaction fee, and it is fully repeatable/deterministic. This is not automatically exploitable against every witness — it requires the specific precondition that the account owner previously configured an Active permission with that bit set — but the actuator/validation code provides no defense-in-depth against it even when that precondition is met.

### Recommendation
- In `TransactionCapsule.checkPermission`/`validateSignature`, hard-require `permissionId == 0` (Owner) for `ContractType.AccountPermissionUpdateContract`, regardless of the Active permission's operations bitmap.
- In `AccountPermissionUpdateActuator.checkPermission`, explicitly exclude `AccountPermissionUpdateContract` (and ideally `WitnessCreateContract`/other permission-affecting types) from the set of operations permitted in an Active permission's bitmap, mirroring the existing exclusion pattern used for `ClearABIContract`/`UpdateBrokerageContract`.
- Additionally, for the Witness branch, verify the sole Witness-permission key corresponds to the account's registered witness signing key (or require Owner-signature-only for Witness permission changes) to prevent silent reassignment even under a legitimate Owner-authorized update.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
