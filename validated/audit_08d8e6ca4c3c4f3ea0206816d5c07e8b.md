### Title
Per-request O(n log n) full-table load/sort in `getpaginatedassetissuelist` regardless of `limit` — CPU/memory DoS - ([File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java])

### Summary
`GetPaginatedAssetIssueListServlet.fillResponse` → `Wallet.getAssetIssueList(offset, limit)` → `AssetIssueStore.getAssetIssuesPaginated(offset, limit)` always calls `getAllAssetIssues()` to load every `AssetIssueCapsule` from the DB and sorts the entire list before slicing out `[offset, offset+limit)`. `limit` only bounds the size of the *returned* slice, not the work performed, so a small `limit=1` request costs the same O(n log n) CPU and O(n) memory as a full dump when n (total asset count) is large.

### Finding Description
`AssetIssueStore.getAssetIssuesPaginated(long offset, long limit)` calls `getAllAssetIssues()` unconditionally: [1](#0-0) 
`getAllAssetIssues()` streams the entire underlying LevelDB/RocksDB `asset-issue` table into a `List`, and `getAssetIssuesPaginated` then sorts that full list by name/order before taking a sub-list — this is O(n) iteration + O(n log n) sort + O(n) heap allocation per call, independent of `limit`, capped only on the output side by `ASSET_ISSUE_COUNT_LIMIT_MAX`.

This is reached directly from the HTTP endpoint `/wallet/getpaginatedassetissuelist` (and its Solidity/PBFT variants) with no privilege required: [2](#0-1) 
which calls `Wallet.getAssetIssueList(offset, limit)`: [3](#0-2) 

The servlet extends `RateLimiterServlet`, whose `service()` method only throttles *request rate* (QPS or concurrency permits), not *per-request cost*: [4](#0-3) 
By default, any servlet without an explicit config entry gets `DefaultBaseQqsAdapter` with `qps=1000` (see `reference.conf`), i.e., 1000 requests/sec are permitted by default — each one loading/sorting the full asset table if attacker supplies `limit=1`. There is no check anywhere that scales allowed QPS inversely with table size, nor any cap on `offset`/dataset size before the full load+sort happens.

Existing protections do not stop this: `ASSET_ISSUE_COUNT_LIMIT_MAX` only limits the *returned* slice size, not the pre-sort work; there is no actuator/signature check involved since this is a read-only GET/POST query endpoint with no transaction, so bandwidth/energy accounting (which only applies to on-chain transactions) is irrelevant and provides no cost to the attacker for hitting this endpoint.

The attack requires that a large number of assets (N) already exist on-chain. Issuing N=100k assets via `createassetissue` is not free — each issuance is a signed transaction subject to the configured `AssetIssueFee` (a dynamic property, non-zero on default config) and normal bandwidth/energy accounting for the issuing account. This raises the bar for populating the table to a large N, but once N is large (whether attacker-funded or organically grown over the chain's lifetime), the *query* side has zero additional cost gate.

### Impact Explanation
This is a Denial-of-Service against the RPC/HTTP-API surface: node-wide CPU exhaustion and increased GC/heap pressure from repeatedly loading and sorting the full `asset-issue` table on every paginated request, independent of the `limit` parameter. Under concurrent flooding with `limit=1`, worker/servlet threads spend O(n log n) time and O(n) memory per request, which can starve other API consumers and degrade full-node responsiveness. This matches the "DoS via RPC-API" bounty impact class — it does not affect consensus, funds, or private keys.

### Likelihood Explanation
- No privileged role needed: any anonymous HTTP client can call `/wallet/getpaginatedassetissuelist`.
- The per-request cost bug is unconditionally present in `getAssetIssuesPaginated`; it does not depend on any node misconfiguration.
- The main precondition is a large N of existing on-chain assets. This can arise either from attacker-funded mass issuance (costs total issuance fees × N plus bandwidth) or simply because a live chain like TRON already carries a large number of issued tokens (in the real network, tens of thousands of TRC10 assets already exist), making this immediately exploitable against existing chains without any pre-funding.
- Default rate limiting (`qps=1000` per servlet, no per-endpoint override configured for `GetPaginatedAssetIssueListServlet` in `reference.conf`) does not account for the O(n) cost per call, so the limiter is ineffective at bounding aggregate work.
- Fully repeatable — every call reproduces the same cost; no state consumption or nonce required by the attacker.

### Recommendation
- Avoid loading and sorting the entire table per request: maintain a persistently sorted index (e.g., store assets in a data structure keyed by the sort order, or cache the sorted list and invalidate only on writes) so pagination is O(offset+limit) instead of O(n log n).
- At minimum, cache the sorted `List<AssetIssueCapsule>` (invalidated on asset create/update) so repeated paginated calls do not resort from scratch.
- Add a per-endpoint rate limiter configuration for `GetPaginatedAssetIssueListServlet` (e.g., `IPQPSRateLimiterAdapter` with a low qps) in `reference.conf`, and/or reject requests where `offset` exceeds a sane bound relative to known table size.
- Consider a global CPU/memory budget guard in `RateLimiterServlet` for endpoints whose backing store size can grow unbounded from user-driven state (asset issuance, proposals, exchanges use the same pagination pattern and should be checked too).

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
