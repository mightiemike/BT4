### Title
Front-runnable asset-name collision causes griefing DoS in `createAssetIssue` - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
The reported bug class is: a state-changing entry point accepts a caller-supplied identifier, checks a mapping keyed by that identifier for pre-existence, and reverts if it is already used — allowing an attacker who observes a pending transaction in the mempool to front-run it (same identifier, higher fee/priority) so the legitimate transaction reverts. The strongest reachable analog in java-tron is the `AssetIssueContract` "asset name" uniqueness check inside `AssetIssueActuator.validate()`/`execute()`, which is directly reachable by any anonymous account via a broadcast `AssetIssueContract` transaction.

### Finding Description
`AssetIssueActuator.validate()` rejects an asset-issuance transaction if the caller-chosen `name` already exists in `assetIssueStore`: [1](#0-0) 

The `name` is fully attacker-observable/predictable because it is a plaintext field of the broadcast (unsigned-until-included) transaction, not derived from the sender's address or any per-account nonce/seed. Any observer of the pending transaction pool can copy the exact `name` (and other fields) into their own `AssetIssueContract` transaction, submit it with a higher bandwidth/energy priority, and get it included first. Because `assetIssueStore.get(name)` is then non-null for the victim's later-processed transaction, `validate()` throws `ContractValidateException("Token exists")` and the victim's transaction fails — exactly the same root cause as the report's `isUserLoanActive(loanId)` check in `LoanManager.createUserLoan`, which reverts with `UserLoanAlreadyCreated` when a front-runner claims the same `loanId` first.

The fix suggested in the report (derive the identifier from a hash of a user seed and the sender's own address) is the same mitigation pattern already used elsewhere in java-tron for collision-prone identifiers — e.g., contract-creation addresses are derived from `sha3(txId || ownerAddress)` in `WalletUtil.generateContractAddress` and from `sha3(senderAddress || salt || sha3(code))` for `CREATE2` in `WalletUtil.generateContractAddress2`, both of which bind the address to the transaction's own signer/context, rather than being a fully attacker-guessable literal field like the asset `name`. [2](#0-1) 

### Impact Explanation
This is a griefing/DoS vector: any account can watch the p2p transaction pool for pending `AssetIssueContract` transactions and repeatedly front-run desired token names, always causing the legitimate issuer's transaction to fail with "Token exists" while consuming the victim's TRX for the failed broadcast attempt (fee/bandwidth spent) and blocking their ability to issue that specific token name. This is analogous to the reported `createUserLoan` griefing but for TRC10 asset issuance — matching the "no profit motive, but damage to users/protocol" impact category the report itself claims.

### Likelihood Explanation
Moderate. Exploitability depends on the `AllowSameTokenName` dynamic parameter being `0` (same-token-name-disabled mode), since the uniqueness check is gated by `dynamicStore.getAllowSameTokenName() == 0`: [1](#0-0) 
On current TRON mainnet this dynamic parameter has long since been switched to allow-same-token-name (a one-way, non-reversible chain parameter), so the "Token exists" collision path is dead in that specific network's live state. I could not verify from the indexed source alone whether this flag defaults to `0` or `1` on a fresh/private/testnet deployment (the getter/default is defined in `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java`, which the available index did not let me fully resolve), so the practical reachability of this exact branch is uncertain on any specific network instance and should be validated against the target network's actual `getAllowSameTokenName()` value before treating this as high severity.

### Recommendation
- If the goal is to eliminate front-runnable identifier collisions generically, prefer identifiers derived by hashing a caller-chosen seed together with the transaction signer's own address/account id (as already done for contract addresses in `WalletUtil.generateContractAddress`/`generateContractAddress2`), rather than accepting a bare user-supplied string/bytes as the sole uniqueness key.
- For `AssetIssueActuator` specifically (when `AllowSameTokenName == 0` is in effect on a given network), consider making name reservation atomic per-owner (e.g., scoping the uniqueness check by `(ownerAddress, name)` or requiring a commit-reveal) instead of a purely global `name -> null` check that any anonymous account can race against.
- Confirm on the target network whether `AllowSameTokenName` is `0`; if it is permanently `1` (as on TRON mainnet), this specific analog has no live impact and should be reclassified as historical/no-impact for that deployment.

### Proof of Concept
Not independently reproduced against a running node; based on static code reading only:
1. Attacker monitors the mempool/broadcast RPC for a pending `AssetIssueContract` transaction containing a desired `name` (e.g., via `/wallet/broadcasttransaction` observation or full-node p2p relay).
2. Attacker submits their own `AssetIssueContract` transaction with the identical `name` field but with higher priority/energy so it lands in an earlier block position.
3. When the victim's original transaction is executed, `AssetIssueActuator.validate()` finds `assetIssueStore.get(name) != null` and throws `ContractValidateException("Token exists")`, reverting the victim's transaction: [1](#0-0)

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
