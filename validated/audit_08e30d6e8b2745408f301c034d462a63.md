### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, letting replay-verify accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-comparison routine used by replay/verify tooling to confirm that a locally re-executed `TransactionOutput` matches an archived, ledger-committed `TransactionInfo`. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the corresponding fields on the locally computed state. This mirrors the seed report's pattern (a value that should be validated at its "maximal"/strict form is instead accepted in a weaker form), except here the weakened check is a proof/commitment-binding check rather than a price rounding direction.

### Finding Description
The function contains a self-documenting gap: [1](#0-0) 

Specifically:
- It hashes and compares `write_set` against `txn_info.state_change_hash()`.
- It recomputes and compares the event-accumulator root against `txn_info.event_root_hash()`.
- It compares `gas_used` and `status`.
- It then has a `TODO(trading-native)` comment stating verbatim that the comparator **ignores the checkpoint hashes** (state/hot-state and `position_state_checkpoint_hash`), and that this allows replay-verify tooling (specifically `db-tool`'s `replay_on_archive`) to "report a successful replay even when the authenticated position state root diverges from local execution."

This function is consumed directly by the replay verification tool: [2](#0-1) 

`execute_and_verify` re-executes archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` to decide pass/fail for each transaction. Because the checkpoint hash fields are excluded from the comparison, a divergence in the Sparse Merkle Tree state-checkpoint root, hot-state checkpoint root, or the newer "position state" checkpoint root (`position_state_checkpoint_hash`, part of `TransactionInfoV1`) — [3](#0-2)  — will not cause `ensure_match_transaction_info` to return an error. The tool will report the replay as successful (`Ok(())`) even though the recomputed durable ledger state (or the newer position-state root introduced for the "trading-native" position feature, per `execution/executor-types/src/state_checkpoint_output.rs`) does not match what is authenticated on-chain in the `TransactionInfo`.

### Impact Explanation
This is an authenticated-verification bypass in a proof/commitment-binding invariant: `TransactionInfo` is precisely "the object stored in the transaction accumulator" that binds a version to its execution result, and `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are part of that committed, hashed record (see `TransactionInfoV0`/`TransactionInfoV1` definitions at `types/src/transaction/mod.rs:2388-2461`). Silently excluding these fields from the replay-verify comparator means a state-root divergence introduced by a bug, a non-deterministic execution path, or a malicious/corrupted archive backup will not be detected by the very tool designed to catch such divergences. Since `replay_on_archive` is one of the primary integrity-auditing mechanisms for archived history, this weakens the guarantee that stored/replayed data matches the correct VM result — directly matching the "committed state that differs from correct VM result" and "hard-fork-only divergence during replay/restore" impact categories.

### Likelihood Explanation
High for triggering the code path (every replay-verify run exercises this exact comparator), but the *consequence* (an actual undetected divergence) only manifests when there is an underlying nondeterminism or corruption in state-checkpoint/hot-state/position-state computation — which this comparator would have caught if checked. The code's own TODO comment confirms the gap is known and currently unmitigated: `state/hot-state and position_state_checkpoint_hash` are unconditionally skipped regardless of whether the relevant features (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) are enabled.

### Recommendation
Extend `ensure_match_transaction_info` to accept expected `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` and to compare the locally computed checkpoint hashes against `txn_info`'s corresponding fields whenever they are `Some` (i.e., at checkpoint-boundary transactions), returning an error on mismatch just as is done for the write-set and event-root hashes. Until this is done, `replay_on_archive` and any other consumer of this function cannot be relied on to detect state-root/proof divergence.

### Proof of Concept
Not independently exploitable in isolation as a standalone PoC — the finding is a static code-review proof: the comparator's implementation (`types/src/transaction/mod.rs:2139-2204`) and its sole non-test call site (`storage/db-tool/src/replay_on_archive.rs:388-406`) show that any state-checkpoint hash mismatch between a freshly re-executed transaction and its archived `TransactionInfo` produces `Ok(())`, because no comparison of `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` occurs in the function body. Constructing a concrete triggering scenario (e.g., an archive with a tampered or divergent `position_state_checkpoint_hash`) requires a running node/backup harness (`storage/db-tool`), which is outside the scope of static index-based verification — I was not able to execute the tool to confirm the runtime behavior beyond what the code and its own TODO comment already state.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
