### Title
Attached deposit ($NEAR) sent to `WalletContract::rlp_execute` is permanently lost on early validation errors - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `#[payable]` entry point `WalletContract::rlp_execute` accepts an attached NEAR deposit from any predecessor and records it in a `CallerDeposit` intended for refund if the downstream cross-contract promise later fails. However, several early error paths inside `inner_rlp_execute` return `Err(...)` *before* any promise (and therefore any refund) is created, while `rlp_execute` converts that `Err` into a normal, non-panicking `PromiseOrValue::Value(...)`. Because the call completes successfully at the protocol level, NEAR's automatic deposit-refund mechanism (which only triggers on receipt failure) never fires, and the attached deposit is silently absorbed by the wallet contract with no path to recovery.

### Finding Description
`rlp_execute` is marked `#[payable]`, so any predecessor may attach a NEAR deposit when calling it: [1](#0-0) 

Inside `inner_rlp_execute`, an `ExecutionContext` is built from the attached deposit and a `CallerDeposit` is computed to allow a later refund of that deposit if a subsequent cross-contract call fails: [2](#0-1) 

`CallerDeposit::new` only produces `Some(..)` (i.e. tracks a refundable deposit) when the predecessor is different from the current account and the attached deposit is non-zero: [3](#0-2) 

If parsing/validation of the RLP transaction fails (`Error::User`, `Error::Relayer`, or an `AccountId` error), `inner_rlp_execute` returns immediately with `Err(err)` — the `caller_deposit` binding is simply dropped, and no refund promise is ever scheduled: [4](#0-3) 

Back in `rlp_execute`, this `Err` is converted into a normal, successful return value rather than a panic: [5](#0-4) 

Because the function call to `rlp_execute` completes *successfully* (it returns `ExecuteResponse{success:false,...}` as a normal value, it does not panic), the NEAR protocol's automatic deposit-refund logic — which only creates a refund receipt for a *failed* action receipt — never triggers (see `docs/RuntimeSpec/Refunds.md`, "Deposit refunds are generated when an action receipt fails to execute"). The attached deposit is therefore permanently credited to the wallet contract's account balance with no code path that returns it to the caller. The only refund path that exists is inside `rlp_execute_callback`, which only fires when a *promise created after successful parsing* later fails: [6](#0-5) 

This is precisely analogous to the reported Solidity bug class: a contract accepts value into its "execute"-style entry point but has no correct handling/refund path for that value on the failure branch, resulting in funds becoming stuck. Here, instead of "cannot receive ETH", the wallet contract "receives $NEAR but cannot return it" whenever transaction parsing/validation fails.

### Impact Explanation
Any relayer, or any account holding a `FunctionCallPermission` access key restricted to `rlp_execute` (or the account owner itself acting as its own relayer), can attach a NEAR deposit when calling `rlp_execute`. If the supplied RLP-encoded Ethereum transaction is malformed, has a bad signature, wrong nonce, or otherwise fails early validation (all `Error::User`/`Error::Relayer`/`AccountId` cases), the attached deposit is irrecoverably absorbed into the wallet contract's balance. This constitutes a permanent loss of funds for the caller who attached the deposit — funds movement occurs (deposit is transferred to and retained by the wallet contract) with no corresponding intended effect and no way to reclaim it, matching the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
This is easily triggerable by any account that is permitted to call `rlp_execute` (a relayer using a `FunctionCallPermission` key, or the account itself). It does not require a malicious validator, network-layer control, or any privileged access — a normal transaction sender simply needs to attach a deposit to a call whose `tx_bytes_b64` fails validation (e.g., due to an off-by-one nonce race between competing relayers, a malformed payload, or a genuinely malicious/buggy relayer implementation). Given that relayers are expected by design to attach value to fund refunds/fees, and validation failures (nonce mismatches, replay races, malformed payload from any external submitter) are a normal occurrence in this flow, the likelihood of loss is realistic rather than purely theoretical.

### Recommendation
In every early-return `Err` branch of `inner_rlp_execute` (`Error::User`, `Error::Relayer`, `AccountId` errors), if `caller_deposit` (or the raw attached deposit) is `Some`, generate a refund `Promise::new(caller).transfer(deposit)` before returning the error, exactly as is already done in `rlp_execute_callback`'s failure branch. Alternatively, restructure `rlp_execute` so that these early validation failures cause an actual panic (rather than returning a normal `ExecuteResponse` value) so the protocol's automatic deposit-refund mechanism applies — while ensuring this does not conflict with the documented intent of persisting state changes (e.g. banning a relayer) on error paths.

### Proof of Concept
1. Deploy the `WalletContract` for an ETH-implicit account and register a relayer's access key with `FunctionCallPermission{receiver_id: <eth_implicit_account>, method_names: ["rlp_execute"]}`, following the flow in `test_wallet_contract_interaction`.
2. Relayer calls `rlp_execute(target, tx_bytes_b64)` attaching a non-zero NEAR deposit (e.g. 1 NEAR), where `tx_bytes_b64` is crafted to fail validation — e.g. supply a nonce different from `expected_nonce`, or an ill-formed RLP payload that triggers `Error::User(UserError::InvalidAbiEncodedData)` in `parse_rlp_tx_to_action`/`validate_tx_relayer_data` (see `internal.rs` lines 43-52).
3. Observe that `rlp_execute` returns normally (`PromiseOrValue::Value(ExecuteResponse{success:false,...})`), the transaction receipt succeeds (no panic), and per `docs/RuntimeSpec/Refunds.md` no deposit-refund receipt is generated.
4. Query the wallet contract account balance before and after: the attached 1 NEAR remains credited to the wallet contract and is never returned to the relayer's account — confirming permanent loss of the attached deposit.
