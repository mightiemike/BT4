### Title
Unauthorized/uncounted gas-key balance drain via `WithdrawFromGasKey` nested in a `Delegate` (meta-transaction) action bypasses pending-queue funding checks - ([File: runtime/runtime/src/action_validation.rs])

### Summary
`WithdrawFromGasKeyAction` moves balance from a gas key back to the owning account's main balance [3](#0-2) . This is directly analogous to the reported `AvailBridge::withdrawFees`: a token-moving operation reachable without the intended guard rail (there, an admin-only role check; here, the pending-transaction-queue's funding/admission accounting), so it can be invoked in a way the protection layer does not see and does not count, letting the balance be moved/drained beyond what the safeguard permits.

### Finding Description
At stable protocol version 86 in this tree, `validate_delegate_action` only rejects a `WithdrawFromGasKey` action nested inside a `Delegate`/`DelegateV2` action once `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is enabled [4](#0-3) , but that feature only activates at protocol version 87 [1](#0-0) . Since `STABLE_PROTOCOL_VERSION` in this tree is 86, the guard is not active, and a top-level `Action::Delegate` whose inner actions include `Action::WithdrawFromGasKey` is accepted as valid.

The root cause is explicitly documented in the code: "the SPICE pending transaction queue scans only the top level actions of a transaction for `WithdrawFromGasKey`, so a nested one drains a gas key that the queue still counts as funded" [5](#0-4) . Concretely, `PendingTransactionQueue::check_pending` tracks `WithdrawFromGasKey` amounts only by iterating `tx.transaction.actions()` at the top level [6](#0-5) ; when the withdrawal is nested inside a `Delegate` action's inner action list instead, this loop never sees it, so `session_gas_key_withdrawals`/`paid_from_gas_key` accounting used for optimistic pending-chunk admission stays wrong, understating what has already been committed to leave the gas key.

The functional test in this same repo demonstrates the concrete mechanics and directly states the pre-fix behavior is exploitable: "Before the upgrade the nested withdrawal is admitted and moves balance out of the gas key, which is the hole this rule closes" [7](#0-6) .

### Impact Explanation
This breaks the intended invariant that the pending-transaction queue accurately tracks in-flight gas-key balance commitments before chunk production admits further transactions, exactly as `check_pending` intends via `session_gas_key_withdrawals`/`paid_from_gas_key` [8](#0-7) . Because nested delegated withdrawals are invisible to this accounting, an account holder can submit multiple pending withdrawal-bearing meta-transactions against the same gas key within one chunk-production window that the admission logic believes are still fully funded, allowing the aggregate withdrawn amount to exceed what the optimistic funding check permits — an accounting bypass on value movement out of a gas key, which the runtime documentation confirms is treated as a protocol-level bug requiring an explicit version-gated fix (`RejectWithdrawFromGasKeyInDelegate`).

### Likelihood Explanation
Reachable trivially and deterministically from a single unprivileged account: any signer who owns a gas key can wrap a `WithdrawFromGasKeyAction` inside a `Delegate`/`DelegateV2` action and submit it as a normal (or relayed) transaction; no special privilege, validator, or network position is required, and the existing test in-repo proves it succeeds pre-fix [9](#0-8) . Given the current tree's `STABLE_PROTOCOL_VERSION` is 86 and the fix activates only at 87, this is live in this tree's stable configuration.

### Recommendation
Enable/backport `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` at or before the currently deployed stable protocol version (or otherwise ensure `validate_delegate_action`'s nested-`WithdrawFromGasKey` rejection at [4](#0-3)  is unconditionally active), and/or fix `PendingTransactionQueue::check_pending` to recursively scan delegate-action payloads for `WithdrawFromGasKey` so the pending-funding accounting at [6](#0-5)  is not bypassed by nesting.

### Proof of Concept
The in-repo test constructs exactly this exploit path: build a `DelegateAction` with `sender_id`/`receiver_id` set to the victim account and an inner `Action::WithdrawFromGasKey` targeting the sender's own gas key, sign it as a V1 delegate action, and submit it wrapped in `Action::Delegate` from a relayer [10](#0-9) . Running it pre-upgrade shows the withdrawal succeeds and drains the gas key balance by the withdrawn amount [9](#0-8) , confirming the bypass is exploitable at any protocol version below 87, including this tree's `STABLE_PROTOCOL_VERSION = 86`.

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
}
