### Title
Precision loss in resource accounting due to double/mixed-order arithmetic instead of multiply-before-divide, gated behind a disabled hardening flag - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
The Sherlock report describes `claim_batch()` computing a per-claim amount by dividing first (`batch.amount * release_amount / 1e18`) and then multiplying by the number of periods, which truncates precision and can zero out the claimable amount entirely. java-tron contains an analogous class of bug in its resource-accounting math (bandwidth/energy weight-to-limit and usage-to-balance conversions), where the *default, currently-active* code path performs floating-point (`double`) arithmetic instead of the safe "multiply first, then divide once" pattern. The project itself has already written a hardened (`BigInteger`, multiply-before-divide) replacement for this exact computation, but it is gated behind a dynamic-property flag (`allowHardenResourceCalculation`) that must be turned on by committee proposal, meaning the imprecise legacy path remains live by default.

### Finding Description
`RepositoryImpl.usageToBalance()` converts consumed bandwidth/energy usage into an equivalent TRX balance: [1](#0-0) 

When `hardenResourceCalculation()` is false (the default until a committee proposal enables it), the calculation collapses `usage * totalWeight / totalLimit * TRX_PRECISION` into a single `double` expression. `double` only has 52 bits of mantissa (~9.0e15 exact-integer range); once the intermediate product `usage * totalWeight` exceeds that range — realistic for large frozen-balance accounts and heavy TVM users — the division-then-multiplication order combined with floating point rounding silently diverges from the exact integer result, exactly mirroring the "divide first, then multiply" precision-loss pattern in the reported `claim_batch()` bug.

The same class of legacy, unhardened computation exists in the sibling energy/bandwidth limit calculators: [2](#0-1) [3](#0-2) 

The project's own regression test proves the divergence is real and material, not theoretical: [4](#0-3) 

This confirms that at `usage=1e8`, `totalWeight=1e11`, `totalLimit=5e10` the double-based legacy formula and the exact `BigInteger` multiply-then-divide formula produce different results — the same root cause (precision loss from unsafe division ordering / limited numeric precision) as the reported vulnerability, just manifesting in TVM resource accounting instead of a vesting contract's claim amount.

### Impact Explanation
`usageToBalance()` and `calculateGlobalEnergyLimit()`/`calculateGlobalLimitV1` underlie how much energy/bandwidth a frozen TRX balance is worth and how usage is converted back to a TRX-equivalent, which is exercised on every TVM contract call and freeze/unfreeze/delegate-resource operation by any unprivileged account. A systematic under- or over-estimation from floating point precision loss can let an account with a large enough frozen balance/usage receive more (underpriced) free energy/bandwidth than it is entitled to, or conversely have its legitimately available resource under-reported — a resource-accounting divergence directly in scope under "resources" per the assessment rules. Because this is consensus-critical state (`accountCapsule.setEnergyUsage`, `totalEnergyWeight`), any divergence between nodes running with/without `allowHardenResourceCalculation` enabled, or between the "correct" hardened value and the currently-live legacy value, is a state/accounting-divergence issue, not merely cosmetic.

### Likelihood Explanation
The unsafe (legacy, double-precision) code path is the current default and reachable by any unprivileged user simply by freezing large TRX amounts and issuing transactions consuming bandwidth/energy — no privileged role required. The precision-loss condition requires the intermediate products to exceed the `double` mantissa's exact range, which is plausible for accounts with large frozen balances relative to global weight/limit values, and the project's own test demonstrates a concrete triggering input set.

### Recommendation
Enable `allowHardenResourceCalculation` by default (or make the BigInteger, multiply-before-divide path unconditional) rather than gating the fix behind an optional committee proposal, so the precision-safe computation in `calculateGlobalLimitV1`/`calculateGlobalLimitV2`/hardened `usageToBalance` is always used instead of the legacy double-based formula.

### Proof of Concept
Using the values from the existing regression test: [4](#0-3) 
With `hardenResourceCalculation()` disabled (default), calling `usageToBalance(usage=1e8, totalWeight=1e11, totalLimit=5e10)` via the legacy `double` path returns a value diverging from the exact `BigInteger.valueOf(usage).multiply(totalWeight).multiply(TRX_PRECISION).divide(totalLimit)` result computed in the test — demonstrating the same divide/multiply-order precision-loss failure mode as the reported `claim_batch()` bug, currently active because the hardening flag is not enabled by default.

  private long usageToBalance(long usage, long totalWeight, long totalLimit) {
    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(usage)
          .multiply(BigInteger.valueOf(totalWeight))
          .multiply(BigInteger.valueOf(TRX_PRECISION))
          .divide(BigInteger.valueOf(totalLimit))
          .longValueExact();
    }
    return (long) ((double) usage * totalWeight / totalLimit * TRX_PRECISION);
  }
