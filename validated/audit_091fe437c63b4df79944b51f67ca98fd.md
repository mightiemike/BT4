### Title
Restore path persists unauthenticated `WriteSet` bytes without binding them to the proof-covered `TransactionInfo.state_change_hash` - ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
The transaction-backup restore flow reads `(txn, aux_info, txn_info, events, write_set)` records from a backup chunk, but only feeds `txns`/`events`/`txn_infos` into `TransactionListWithProofV2::verify()` against the accumulator-proof-authenticated `LedgerInfo`. The `write_sets` vector is loaded and kept out-of-band and is never checked against the corresponding `txn_info.state_change_hash()` before being written to `LedgerDb`/state via `restore_utils::save_transactions`.

### Finding Description
In `LoadedChunk::load` [1](#0-0) , each backup record deserializes a `write_set` alongside `txn`, `txn_info`, and `events`, and it is pushed into a separate `write_sets` vector. The verification step that follows only constructs a `TransactionListWithProofV2` from `txns`, `event_vecs`, and the accumulator `range_proof`+`txn_infos`, explicitly excluding `write_sets`: [2](#0-1) 

`TransactionListWithProof::verify()` only checks that transaction hashes match `txn_info.transaction_hash()` and that events match `txn_info.event_root_hash()`; it has no `write_set` field at all, so it cannot and does not check `state_change_hash` [3](#0-2) . This differs from `TransactionOutputListWithProof::verify()`, which does correctly bind write sets to `state_change_hash` when outputs are used instead of raw write sets [4](#0-3) .

Once loaded, the unauthenticated `write_sets` are handed directly to `restore_utils::save_transactions` / `save_transactions_impl`, which persists them via `WriteSetDb::put_write_set` with no hash check against `txn_info.state_change_hash()` [5](#0-4) . If `kv_replay` is enabled, these same unauthenticated write sets are also fed into `state_store.calculate_state_and_put_updates(...)`, which derives and commits new Jellyfish Merkle Tree state updates from them [6](#0-5) .

This is the direct analog of the reported bug class: two related pieces of data (a "pair") — here, `TransactionInfo.state_change_hash` (the proof-anchored commitment) and the actual `WriteSet` bytes (the data applied to storage) — are registered/persisted through separate paths without a linkage check, exactly like the missing `pairNFT.l2Contract == l2Contract` check between `L1StandardERC721` and `pairNFTInfo`.

### Impact Explanation
If a backup manifest/chunk is corrupted, tampered with, or served incorrectly by the (untrusted or misconfigured) `BackupStorage` backend, or if the write_set file within a chunk is truncated/reordered/mismatched relative to the accumulator-proof-verified `txn_infos`, the restore flow silently accepts the mismatched write set as long as the transaction and event hashes/proof still validate. This lets storage ingest a `WriteSet` whose hash does not match `state_change_hash` committed in the (correctly-proven) `TransactionInfo`, corrupting durable ledger state without detection — precisely the "committed state that differs from the correct VM result / corrupts durable ledger data" impact called out as in-scope. When `kv_replay` is used, this also produces an incorrect JMT/state root computed from bogus write-set content, i.e., a wrong state root silently accepted as valid during restore. Because restored data becomes part of the permanent ledger DB (write-set DB, state KV DB), like the "pair cannot be updated/fixed" concern in the report, there's no self-healing mechanism once persisted.

### Likelihood Explanation
Likelihood depends on backup-integrity assumptions: restore normally trusts the operator-provided backup, so this is not remotely triggerable without control over/corruption of a node's backup storage or restore-time file handling. However, unlike the accumulator/ledger-info path (which is independently authenticated), the write-set bytes have zero binding to the proof chain, so any bit-flip, reordering bug, decompression bug, or malicious backup provider silently produces state divergence rather than a hard verification failure — this is a structural gap rather than a narrow edge case.

### Recommendation
In `LoadedChunk::load` (and/or `restore_utils::save_transactions_impl`), after loading `write_sets`, assert `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every `(write_set, txn_info)` pair before they are accepted into the verified chunk, mirroring the check already performed in `TransactionOutput::ensure_match_transaction_info` / `TransactionOutputListWithProof::verify`. This closes the same class of "unchecked pairing between an authenticated commitment and unauthenticated payload" identified in the external report.

### Proof of Concept
Not independently executed in this session (no filesystem/terminal access). Conceptually:
1. Take a valid transaction backup chunk (manifest + transactions file + proof file).
2. In the transactions file, replace the `write_set` bytes of one record with an arbitrary but well-formed `WriteSet` (leaving `txn`, `txn_info`, `events` untouched so hashes still line up with the proof).
3. Run `TransactionRestoreController`/`TransactionRestoreBatchController` against this corrupted chunk.
4. Observe that `LoadedChunk::load`'s `txn_list_with_proof.verify(...)` succeeds (transactions/events/proof still validate), and the tampered `write_set` is persisted via `restore_utils::save_transactions` into `WriteSetDb`, and (with `kv_replay`) into state KV/JMT, without any hash-mismatch error being raised.

Note: I was unable to fully trace `save_transactions_impl`'s complete body or `TransactionRestoreBatchController::run_impl` in this session due to tool-call limits, so I cannot rule out an additional validation step elsewhere in the pipeline (e.g., inside `ChunkExecutorTrait`/`TransactionReplayer` when `replay_from_version` is set, or in `db-tool`'s verify-execution mode) that might re-derive/check write sets independently for the replay path. The gap is clearly present for the non-replay "save" path shown above; whether it is fully mitigated when replay/verify-execution mode is always forced is unresolved and should be checked in a follow-up session with full repository access.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
