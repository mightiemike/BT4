### Title
Webhook HMAC only signs the raw body, letting one installed merchant forge the `X-Shopify-Shop-Domain` header and hijack another shop's offline session/access token - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
Webhook authenticity in `shopify-app-js` is verified with `validateHmacFromRequestFactory`, which computes the HMAC exclusively over the raw request body using the app's single, app-wide `apiSecretKey`. None of the webhook headers — including `X-Shopify-Shop-Domain` (or the Events equivalent) — are included in the signed data. Downstream authentication helpers (`authenticateWebhookFactory` in `shopify-app-remix`/`shopify-app-react-router`) trust this unsigned `domain` header to decide *which shop's* stored offline session/access token to load and hand to the webhook callback. Because the same `apiSecretKey` is shared by every shop that installs the app, any single merchant can obtain a validly-HMAC'd body (by triggering their own webhook) and then replay that body with a forged `domain` header pointing at a victim shop, causing the app to authenticate the request as coming from the victim and to expose the victim's `admin`/`session` context to the (attacker-controlled) payload processing logic.

### Finding Description
`validateHmacFromRequestFactory` only hashes `rawBody` against `config.apiSecretKey` and compares it to the `X-Shopify-Hmac-Sha256`/events HMAC header: [1](#0-0) 

`checkWebhookHeaders`/`checkWebhooksHeaders` then read the `domain`, `topic`, `apiVersion`, and `webhookId` headers and pass them through as trusted, "valid" fields — with no cryptographic binding to the HMAC that was just verified: [2](#0-1) 

`authenticateWebhookFactory` (present identically in `shopify-app-remix` and `shopify-app-react-router`) uses `check.domain` — the unsigned header value — directly as the `shop` to look up the stored offline session/access token, and attaches an authenticated `admin` client for that shop to the webhook context that is handed to the app's callback along with the attacker-controlled `rawBody` payload: [3](#0-2) [4](#0-3) 

The `apiSecretKey` used for HMAC generation is a single, app-wide config value, not a per-shop secret — it is the same value for every merchant that installs the app: [5](#0-4) 

This mirrors the "market" pattern from the referenced report: a check that only proves *"this caller possesses valid credentials"* (a listed market / a correctly-HMAC'd body) is then used to authorize an action against an **arbitrary, attacker-chosen victim identity** (`_beneficiary`/`_from` there; the `shop`/`domain` here) that was never itself covered by the authorization check.

### Impact Explanation
An attacker who is a legitimate (but malicious) merchant of the app can:
1. Trigger a webhook event in their own store (e.g., `products/update`) to receive a body with a genuinely valid `X-Shopify-Hmac-Sha256` value, computed with the shared `apiSecretKey`.
2. Replay that exact body + HMAC header to the app's webhook endpoint, but substitute `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's domain and a topic the app handles sensitively (e.g., `app/uninstalled`, `customers/data_request`, `orders/create`).
3. `validateFactory`/`validateHmacFromRequestFactory` will report the request as valid (HMAC only checks body), and `authenticateWebhookFactory` will load the **victim's** offline session and access token via `ensureValidOfflineSession(params, check.domain)`, then invoke the app's webhook handler with `shop: <victim>`, a valid `admin` client scoped to the victim, and attacker-controlled `payload`.

Depending on what the app's webhook handlers do (delete data, cancel orders, revoke access, write to the victim's store via the `admin` client, trigger GDPR data deletion, etc.), this can result in cross-tenant data manipulation or destructive actions against a victim merchant's store using their own access token, triggered entirely by an unrelated, unprivileged merchant.

### Likelihood Explanation
No compromise of Shopify, no leaked secrets, and no privileged role are required — only that the attacker themselves has installed the app (a normal, single-merchant capability), a scenario explicitly in scope. Forging arbitrary HTTP headers on a POST request while keeping a previously-observed valid body/HMAC pair is straightforward. The main variable is the sensitivity of the app's own webhook handler logic for the spoofed topic/shop, which is app-specific but commonly includes state-changing operations (uninstall cleanup, GDPR redaction, order/customer processing).

### Recommendation
Bind the header values that determine *whose* session/access token is used (at minimum `domain`/shop, and ideally `topic`, `webhook-id`) into the same value that is HMAC-verified, e.g. by including canonicalized header values in the signed payload used for comparison, or by independently confirming the domain against Shopify (e.g., verifying the `webhookId` via the Admin API for that shop) before trusting it to select session storage. At minimum, document and mitigate by having `authenticateWebhookFactory` cross-check the header-derived shop against another Shopify-verifiable signal before it is used to load session storage.

### Proof of Concept
1. As Merchant A (an app installer), trigger any subscribed webhook topic (e.g., update a product) so Shopify sends `POST /webhooks` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(apiSecretKey, B)`.
2. Capture `B` and `H`.
3. Send a new `POST /webhooks` request with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and, if desired, a different `X-Shopify-Topic`.
4. `validateHmacFromRequestFactory` recomputes the HMAC over `B` using the shared `apiSecretKey` and it matches `H`, so `webhookCheck.valid === true` with `check.domain === 'victim-shop.myshopify.com'`.
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's real offline access token, and invokes the app's webhook callback with an authenticated `admin` client for the victim and the attacker's payload `B`.

```typescript
export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
```

```typescript
function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };
```
