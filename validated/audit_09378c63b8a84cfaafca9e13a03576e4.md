### Title
Missing zero-address check on CEA inbound `Recipient` permanently burns bridged user funds - (File: x/uexecutor/types/inbound.go, x/uexecutor/keeper/execute_inbound_funds_and_payload.go)

### Summary
The external report's bug class is "immutable/critical addresses are accepted without a zero-address check, permanently misdirecting funds." The Push Chain analog is the `Recipient` field on a `CEA` (Custom Execution Address) inbound: it is validated only for non-emptiness and hex-format, never for being the EVM zero address, before being used as the literal mint/deposit target for bridged PRC20 tokens.

### Finding Description
`Inbound.ValidateForExecution` in [1](#0-0)  only checks that `Recipient` is non-empty and passes `utils.IsValidAddress(p.Recipient, utils.HEX)` — a hex-format check, not a semantic non-zero check. There is no rejection of `0x0000000000000000000000000000000000000000`.

Once a `MsgVoteInbound` ballot with `IsCEA=true` and `Recipient="0x0000...0000"` finalizes, `ExecuteInboundFundsAndPayload` converts it directly with `common.HexToAddress(utx.InboundTx.Recipient)` [2](#0-1) . The keeper then checks whether that address is a UEA via `CallFactoryGetOriginForUEA` (false for the zero address) and whether it has contract code via `GetCodeHash` (also false, since the zero address is never a deployed contract) [3](#0-2) . Falling through the "neither UEA nor contract" (EOA) branch, the code proceeds to mint the bridged PRC20 representation directly to the zero address via `depositPRC20` → `CallPRC20Deposit` [4](#0-3) [5](#0-4) .

This mirrors the report's core defect exactly: a fund-routing address is accepted from an external/attacker-influenced source (the user's own inbound gateway call on the source chain, relayed faithfully by honest UVs as a "dumb relay" — see the comment in `Inbound.ValidateBasic` [6](#0-5) ) without a zero-address guard, and it is then used as an immutable-for-that-transaction fund destination.

Note on the codebase's own sentinel usage: `NormalizeForTxType` explicitly assigns `p.Recipient = EvmZeroAddress` for non-CEA payload flows as an intentional "don't care" sentinel [7](#0-6) , which confirms the zero address is treated as a syntactically "valid" hex address throughout this code path rather than being special-cased as invalid.

**Uncertainty**: I could not fully inspect `utils.IsValidAddress`'s source in `utils/address.go` before running out of tool budget, so I cannot 100% confirm it never special-cases the zero address. However, all test cases I found for `ValidateForExecution` (e.g. `"invalid recipient address for FUNDS type"` using `"0xzzzzzzzz"`, `"not-a-hex-address"`) only exercise format-invalidity, never a zero-address rejection case, which is consistent with the function performing pure format validation.

### Impact Explanation
If triggered, a user's own bridged funds (PRC20 mint) are sent to the EVM zero address, which is unrecoverable — permanent loss of user-controlled funds. This satisfies the in-scope impact category "permanent loss ... of user or protocol-controlled funds" and "corruption of PRC20 ... accounting."

### Likelihood Explanation
The trigger requires an inbound gateway event on the source chain with `Recipient` set to the zero address inside a CEA-flagged deposit — this is attacker/user-controlled input, requires only ordinary/malicious use of the public bridging flow (a user or attacker crafting a source-chain transaction), and does not require any privileged or malicious-validator behavior, since honest UVs simply relay what happened on the source chain and honest validators would all vote the same ballot value. However, it is most plausibly self-inflicted (a griefing/burn against one's own inbound) rather than a way to steal others' funds, which limits practical incentive/severity somewhat.

### Recommendation
Add an explicit zero-address rejection for `Recipient` in `Inbound.ValidateForExecution` (and ideally in `ExecuteInboundFundsAndPayload`/`depositPRC20` as defense-in-depth) analogous to a `require(recipient != address(0))` guard, so CEA inbounds with a zero-address recipient are treated as a validation failure (recorded as a FAILED PCTx as with other invalid-recipient cases) rather than proceeding to mint tokens to an unrecoverable address.

### Proof of Concept
1. Attacker (or careless bridging client) submits a source-chain gateway `addFunds`-style event with `isCEA=true`, a nonzero `Amount`, and `Recipient="0x0000000000000000000000000000000000000000"`.
2. Honest Universal Validators relay this faithfully via `MsgVoteInbound`; `ValidateBasic` and `ValidateForExecution` both pass because the address is a syntactically valid 20-byte hex string.
3. Ballot finalizes; `ExecuteInboundFundsAndPayload` resolves `ueaAddr = common.Address{}` (zero address), determines it is neither a UEA nor a deployed contract, and calls `depositPRC20` to mint the bridged token amount to the zero address.
4. The user's bridged funds are now held by an address with no controlling key — permanently lost.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
