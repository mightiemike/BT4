### Title
Webhook HMAC digest omits the shop domain, enabling cross-shop webhook replay/spoofing - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
`validateHmacFromRequestFactory` computes the webhook HMAC exclusively over the raw request body using the app's single, shared `apiSecretKey`. Because the `X-Shopify-Shop-Domain` (or `X-Shopify-Events-*`-equivalent) header is not included in the signed material, any HMAC that is valid for one shop's webhook body is equally valid for the identical body claimed to originate from any other shop, since the same `apiSecretKey` is used for every merchant that has installed the app.

### Finding Description
`validateHmacFromRequest` in [1](#0-0)  only reads the HMAC header and calls `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` ( [3](#0-2) ), which hashes `rawBody` with `config.apiSecretKey` — the domain/topic/webhook-id headers play no role in the digest. `validateFactory` in [4](#0-3)  runs this HMAC check first, and only afterward extracts `domain`, `topic`, `webhookId`, etc. from headers via `checkWebhooksHeaders`/`checkEventsHeaders` ( [5](#0-4) ) — these header values are trusted outright once the body HMAC passes, with no binding between them and the signature. Downstream, `authenticateWebhookFactory` uses `check.domain` directly to call `ensureValidOfflineSession(params, check.domain)` and attaches the resulting session/admin client to the webhook context ( [6](#0-5) ).

Because every shop that has the same app installed shares the identical `apiSecretKey` (the app's client secret, not a per-shop key), a genuine webhook HMAC generated by Shopify for shop A's payload is a valid HMAC for the *same byte-for-byte payload* claimed to be from shop B — the digest never encodes which shop it belongs to.

### Impact Explanation
A user/attacker who has installed the app on their own shop (an unprivileged, single-merchant actor — no special access needed) receives genuine, validly-HMAC-signed webhook deliveries for their own store. They can capture such a delivery and replay it toward the app's webhook endpoint while swapping only the `X-Shopify-Shop-Domain` header (and any other unsigned identifying headers) to point at a *different* shop that also has the app installed. Since the digest is computed over the body only, the library still reports `valid: true` and resolves `check.domain` to the attacker-chosen shop. The webhook handler and any embedded `admin`/`session` client then operate under the victim shop's identity/session with attacker-controlled payload content, enabling cross-tenant data confusion, spoofed events (e.g., forged `orders/create`, `app/uninstalled`, GDPR, or billing-related topics) being processed as if they originated from a different merchant.

### Likelihood Explanation
Exploitation requires only: (1) attacker has legitimate access to a webhook delivery/signature for any shop using the same app (trivially obtained by installing the app on a shop the attacker controls), and (2) the app's webhook receiving endpoint being reachable over plain HTTP without additional per-shop binding checks beyond what `shopify-app-js` itself performs — which is the common case, since `authenticateWebhookFactory` and the underlying `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` packages all rely purely on the library's `validate()`/`validateHmacFromRequestFactory` result to trust `domain`. No secret leakage or privileged position is required, matching the "unprivileged actor, anonymous/HTTP webhook request" analog criteria.

### Recommendation
Bind the shop-identifying header(s) into the HMAC digest (or otherwise cryptographically tie `domain`/`webhookId`/`topic` to the signature) before trusting them, e.g. include `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Webhook-Id`) as part of the signed material verified in `validateHmacFromRequestFactory`, or re-derive/verify the shop identity independently (for instance by checking that the resolved offline session's stored shop was the one that actually installed the app and rejecting on mismatch) rather than trusting the header value once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on Shop A (attacker-controlled) and Shop B (victim), both apps sharing the same `apiSecretKey` client secret configured in `shopify-app-js`.
2. Trigger a webhook delivery to Shop A (e.g., `products/create`) and capture the raw POST body plus the `X-Shopify-Hmac-Sha256` header — this HMAC is valid per `validateHmacString(config, rawBody, hmac, HashFormat.Base64)`.
3. Replay the exact same request to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with Shop B's domain (and, if desired, adjust `X-Shopify-Webhook-Id`/`X-Shopify-Topic` to a topic of choice — these headers are not part of the signed digest).
4. Observe that `shopify.webhooks.validate()`/`authenticateWebhookFactory` returns `valid: true` with `domain` set to Shop B, loads Shop B's offline session, and invokes the registered handler as if the event genuinely originated from Shop B.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
