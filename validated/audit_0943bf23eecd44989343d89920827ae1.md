### Title
Unsaturated subtraction in `AccountStorageEntry::get_obsolete_bytes` can underflow/panic or corrupt storage-size accounting - (File: `accounts-db/src/account_storage_entry.rs`)

### Summary
`AccountStorageEntry::get_obsolete_bytes` computes, for each obsolete account offset, `self.accounts.calculate_stored_size(data_len).min(self.accounts.len() - offset)`, mirroring the Mochi report's pattern where a raw/undiscounted value is subtracted against a value that is not guaranteed to stay consistent with it, producing an underflow instead of a properly clamped result.

### Finding Description
`get_obsolete_bytes` is defined as:
```rust
pub fn get_obsolete_bytes(&self, slot: Option<Slot>) -> usize {
    let obsolete_bytes: usize = self
        .obsolete_accounts_read_lock()
        .filter_obsolete_accounts(slot)
        .map(|(offset, data_len)| {
            self.accounts
                .calculate_stored_size(data_len)
                .min(self.accounts.len() - offset)
        })
        .sum();
    obsolete_bytes
}
``` [1](#0-0) 

Every other similar computation in the same struct (and elsewhere in `accounts_db`) explicitly uses `saturating_sub` to guard against this exact class of mismatch, e.g. `alive_bytes_exclude_zero_lamport_single_ref_accounts` at the same file:
```rust
pub(crate) fn alive_bytes_exclude_zero_lamport_single_ref_accounts(&self) -> usize {
    let zero_lamport_dead_bytes = self
        .accounts
        .dead_bytes_due_to_zero_lamport_single_ref(self.num_zero_lamport_single_ref_accounts());
    self.alive_bytes().saturating_sub(zero_lamport_dead_bytes)
}
``` [2](#0-1) 

and `is_shrinking_productive`/`should_not_shrink`/`select_candidates_by_total_usage` in `accounts_db.rs` also consistently `saturating_sub`. [3](#0-2) [4](#0-3) 

`get_obsolete_bytes` is the one outlier that performs a raw `self.accounts.len() - offset` without saturation. `offset` here comes from `ObsoleteAccounts::filter_obsolete_accounts`, which returns offsets that were recorded when an account was marked obsolete (rewritten to a newer slot, or zero-lamported and older than the last full snapshot) [5](#0-4) . `self.accounts.len()` reflects the *current* length of the backing `AccountsFile`, which can be reduced independently by reopening/truncating/shrinking operations (`reopen_as_readonly`, shrink rewriting into a smaller/differently-sized file, etc.) [6](#0-5) . Because the obsolete-offset bookkeeping (`obsolete_accounts`) and the physical file length (`self.accounts.len()`) are tracked through separate code paths that are not atomically kept in lock-step the way `num_alive_bytes`/`num_alive_accounts` are (which use an explicit assert in `remove_accounts` to guard against exactly this kind of mismatch [7](#0-6) ), any state where a recorded obsolete `offset` is greater than the observed `self.accounts.len()` at call time produces a subtraction of a larger value from a smaller one — exactly analogous to `details[_id].debt -= _usdm` underflowing in the Mochi report because the discounted `debt` and the undiscounted `_usdm` diverge.

### Impact Explanation
In a debug build this triggers an arithmetic-underflow panic (a node panic on an honest/unprivileged path — snapshot generation/serialization reads obsolete bytes via this API, per its call sites in `runtime/src/serde_snapshot/obsolete_accounts.rs` and `runtime/src/serde_snapshot/storage.rs`). In a release build (where overflow checks are typically disabled) the subtraction silently wraps to a huge `usize`, and the subsequent `.min(...)` and `.sum()` then produce a grossly incorrect (and potentially overflowing/summing-wrapped) obsolete-byte total. That total feeds size accounting used during snapshot serialization of obsolete-account metadata, so a wrong value here can silently corrupt the recorded storage size/metadata written into a snapshot, producing a snapshot-vs-replay/hash mismatch on nodes that hit this state, or a disproportionate/incorrect size computation.

### Likelihood Explanation
This is a narrow-window bug: it only manifests when `obsolete_accounts` offsets are stale relative to `self.accounts.len()` (e.g., after a reopen/shrink changes the backing file length without offset records being corrected first, or an offset recorded against one storage generation being read against a later generation). I was not able to fully trace, within the available context, a concrete call sequence that guarantees `offset > self.accounts.len()` at the exact moment `get_obsolete_bytes` is invoked (that would require tracing all producers/consumers of `obsolete_accounts` and `reopen_as_readonly`/shrink-rewrite in full, which exceeded what I could verify with the tools available). This should be treated as a plausible-but-unconfirmed root cause requiring further tracing by an engineer with full-repo access (e.g., a Devin session) rather than a proven, reproduced bug.

### Recommendation
Change the subtraction to use `saturating_sub`, consistent with every other byte-accounting computation in this file and in `accounts_db.rs`:
```rust
self.accounts
    .calculate_stored_size(data_len)
    .min(self.accounts.len().saturating_sub(offset))
```
This eliminates the panic/wraparound risk regardless of whether the two values can legitimately diverge, matching the defensive pattern already used everywhere else in this subsystem.

### Proof of Concept
Not independently reproduced. The report is based on static code inspection of `get_obsolete_bytes` [1](#0-0)  compared against the saturating patterns used elsewhere in the same file/module, by direct analogy to the Mochi Vault issue where an un-discounted value was subtracted from a discounted one. Confirming an actual trigger path (a concrete sequence of clean/shrink/reopen operations that produces `offset > self.accounts.len()`) requires deeper tracing than available in this session and should be validated with full codebase access.

             {num_accounts}",
            self.slot,
            self.id,
        );

        // SAFETY: subtraction is safe since we just asserted num_accounts <= prev_num_accounts
        prev_num_alive_accounts - num_accounts
    }

    /// Returns the expected alive bytes after shrinking `store`.
    pub(crate) fn alive_bytes_after_shrink(&self, store: &AccountStorageEntry) -> usize {
        // Obsolete accounts are already excluded from `store.alive_bytes()`.
        // Zero-lamport single-ref accounts are counted as alive until shrink can purge them,
        // which is gated by the latest full snapshot slot.
        if self.can_purge_zero_lamport_single_ref_after_shrink(store.slot()) {
            store.alive_bytes_exclude_zero_lamport_single_ref_accounts()

            store.alive_bytes()
        }
    }
