### Title
Transaction-triggered chain halt via unchecked `.unwrap()` on receipt-to-shard remapping in delayed receipt processing - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `.unwrap()` on both the epoch's shard layout lookup and on `Receipt::receiver_shard_id(&shard_layout)` without any fallback, even though `receiver_shard_id` is a fallible, `Result`-returning operation elsewhere in the same file. This mirrors the CVE-2024-58012 bug class: an object association (there, a DAI widget; here, a receipt's target shard) is used without validating it actually resolved successfully, leading to an unhandled fault instead of a graceful rejection/skip.

### Finding Description
`receipt_filter_fn` is used to decide whether a delayed receipt popped from (or peeked in) the `DelayedReceiptQueue` belongs to the shard currently applying the chunk: [1](#0-0) 

Unlike the other call site in the same file (`forward_or_buffer_receipt`), which propagates the error from `receiver_shard_id` with `?`: [2](#0-1) 

`receipt_filter_fn` instead does:
```rust
let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
```
This function is invoked from `pop()` (used every time a receipt is dequeued for execution during `process_receipts`) and from `peek_iter()`: [3](#0-2) 

Both are on the core "runtime apply" path that every honest validator/chunk-producer executes deterministically while applying a chunk, and `pop()` is reached unconditionally whenever the delayed receipt queue is non-empty, which itself can be populated by any account's cross-shard receipts (e.g. `GlobalContractDistribution` receipts created by an unprivileged user's global-contract deploy transaction, or ordinary cross-shard action receipts).

The codebase's own regression test acknowledges this exact failure mode: a `GlobalContractDistribution` receipt whose `target_shard` becomes "stale" after two successive dynamic-resharding generations is specifically constructed to try to trigger a panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old shard id: [4](#0-3) 

The comment inside `DelayedReceiptQueueWrapper` explicitly documents that "it's possible for a chunk to have delayed receipts that technically belong to the sibling shard before a resharding event" and that resharding duplicates the delayed receipt queue across child shards — i.e., this is a known, reachable, protocol-level condition, not a hypothetical: [5](#0-4) 

Because `receipt_filter_fn` unconditionally `.unwrap()`s, any receipt whose shard cannot be remapped through the current epoch's shard layout — whether due to multi-generation resharding edge cases beyond the one case the existing test exercises, a corrupted/desynced shard-layout config, or any other future path that leaves a stale `receiver_id`/`target_shard` in a delayed receipt — will cause every honest validator applying that chunk to panic deterministically, since `apply()` and `process_receipts()` are called by all validators processing the same chunk.

### Impact Explanation
A panic here occurs inside the deterministic runtime-apply path (`process_receipts` → `DelayedReceiptQueueWrapper::pop`/`peek_iter` → `receipt_filter_fn`), which every validator executes identically when applying the same chunk. Because the trigger condition (a receipt whose shard mapping can't be resolved under the current shard layout) is derived from protocol-visible data (shard layout + receipt receiver), all honest nodes would panic in lockstep, producing a chain-wide halt for the affected shard — a transaction/receipt-triggered denial of service. This matches the required "transaction-triggered halt" impact category.

### Likelihood Explanation
The existing test in `global_contracts_distribution.rs` demonstrates that a normal, unprivileged flow — deploying a global contract, saturating gas to force the resulting `GlobalContractDistribution` receipt into the delayed queue, and forcing two dynamic-resharding events — can produce exactly the "stale shard" condition this code guards against. The dedicated regression test suggests the maintainers are aware of and actively mitigating one instance of this class of bug, but the underlying `receipt_filter_fn` implementation itself still performs the two unconditional `.unwrap()` calls rather than validating/handling the error, so any additional edge case that produces an un-mappable shard id (further resharding generations, other receipt types placed in the delayed queue, or divergent behavior of `receiver_shard_id`) remains capable of triggering the panic. I was not able to fully inspect `Receipt::receiver_shard_id`'s implementation (in `core/primitives/src/receipt.rs`) within the available tool budget to confirm every code path that can return `Err` here, so the precise set of conditions that still reach the `.unwrap()` is not fully enumerated.

### Recommendation
Replace both `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (return a `Result` from `receipt_filter_fn` and thread it through `pop()`/`peek_iter()`), or apply defensive handling (e.g., treat an unmappable shard id as "not belonging to this shard" and log/metric it) instead of panicking, consistent with how `forward_or_buffer_receipt` already propagates the `receiver_shard_id` error with `?`.

### Proof of Concept
The repository's own test demonstrates the trigger conditions end-to-end: [6](#0-5) 
1. An unprivileged user deploys a global contract, creating a `GlobalContractDistribution` receipt targeting their own shard.
2. The user (or any account) saturates chunk gas so the receipt is pushed into the delayed receipt queue and remains there across chunk applications.
3. Two sequential dynamic-resharding events occur while the receipt sits in the queue, changing the shard layout twice.
4. When the delayed queue drains, `process_receipts` calls `pop()` → `receipt_filter_fn`, which calls `receiver_shard_id(&shard_layout).unwrap()` on the now-stale receipt; if remapping fails, this panics on every validator applying that shard's chunks, halting the chain (as documented in the test's own comment at lines 165-168 of that file).

    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }
