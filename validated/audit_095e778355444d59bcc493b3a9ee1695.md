### Title
Unbounded growth of `zero_lamport_accounts_to_purge_after_full_snapshot` via repeated zero/non-zero toggling of a single account - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::filter_zero_lamport_clean_for_incremental_snapshots` inserts `(slot, pubkey)` tuples — not just `pubkey` — into `zero_lamport_accounts_to_purge_after_full_snapshot` whenever a zero-lamport account's most recent rooted slot is newer than `latest_full_snapshot_slot`. Because the set is only drained/deduplicated when a full-snapshot-advance event triggers the gated `retain` in `construct_candidate_clean_keys`, an unprivileged attacker who repeatedly toggles a single account between zero and non-zero lamports across many rooted slots (funded by ordinary, self-paid transfers) can cause a new, distinct `(slot, pubkey)` entry to be inserted on every clean cycle in which that account is captured, while all previously-inserted, now-orphaned entries for the same pubkey remain in the set until the next full snapshot advances past them.

### Finding Description
`zero_lamport_accounts_to_purge_after_full_snapshot` is defined as a `DashSet<(Slot, Pubkey)>` [1](#0-0) .

During `clean_accounts`, candidates are keyed per-pubkey (`HashMap<Pubkey, CleaningInfo>`), and the scan reclaims superseded/older slot entries for a pubkey independently of this set, via `should_collect_reclaims`/`collect_reclaims`/`handle_reclaims` [2](#0-1) . This reclaim path removes stale index/storage entries but never touches `zero_lamport_accounts_to_purge_after_full_snapshot`.

`filter_zero_lamport_clean_for_incremental_snapshots` then takes the *current* highest rooted slot for the candidate pubkey and, if that slot is newer than `latest_full_snapshot_slot`, inserts a fresh `(slot, pubkey)` tuple into the set: [3](#0-2) 

The only place this set is drained is inside `construct_candidate_clean_keys`, gated by the one-shot `latest_full_snapshot_slot_advanced_since_clean` flag: [4](#0-3) . This `retain` only executes once per full-snapshot-advance event (the flag is `swap(false, ...)`), and only removes entries with `slot <= latest_full_snapshot_slot`.

Exploit flow: an attacker owns/controls an account and, across many rooted slots between two full-snapshot boundaries (full snapshot intervals are typically tens of thousands of slots), repeatedly: (1) sends lamports to zero out the account, (2) refunds it to non-zero, (3) zeroes it again at a later slot. Each time the account is selected as a clean candidate while its current zero-lamport slot exceeds `latest_full_snapshot_slot`, a *new* `(slot, pubkey)` tuple is inserted. The old `(older_slot, pubkey)` entry from a prior clean cycle is never removed by this insertion — it is only removed when a *new* full-snapshot-advance event later fires the gated retain, and even then only if the new tuple's slot is `<= latest_full_snapshot_slot`. Because clean cycles run far more frequently than full-snapshot boundary advances (clean runs roughly every accounts-background-service tick; a full snapshot is taken roughly every `snapshot_interval_slots` slots), the number of stale `(slot, pubkey)` tuples that accumulate for a *single* pubkey scales with the number of toggle events the attacker performs, not with the number of unique accounts touched. This breaks the intended invariant that the set only ever holds one "pending purge" record per account (its current, single, cannot-purge zero-lamport version) and instead grows as O(toggle count).

None of the existing invariant checks catch this: the `debug_assert!` at construct_candidate_clean_keys only asserts the set is empty when snapshots are disabled [5](#0-4) , not that it stays bounded in size relative to unique accounts.

### Impact Explanation
This is a resource-exhaustion/disproportionate-cost issue local to `AccountsDb`: the `DashSet<(Slot, Pubkey)>` grows unbounded in memory (each entry ~40 bytes plus DashSet overhead) proportional to attacker-controlled write/toggle frequency rather than to the number of unique accounts or fees paid, and every subsequent `clean_accounts` call additionally pays CPU cost iterating/retaining this growing set. Because the growth rate (and thus the point at which it becomes a problem) depends on each node's own clean-cycle cadence and how recently its full snapshot slot advanced, different honest nodes accumulate this bloat at different rates — a resource-exhaustion drift matching the "disproportionate storage and CPU cost" bounty category, confined to the node processing the attacker's transactions (no consensus-breaking hash/capitalization divergence is caused, since the set only affects internal bookkeeping, not the account's actual lamports/hash).

### Likelihood Explanation
Fully reachable by an unprivileged attacker: only requires normal, self-funded transfer transactions that zero and re-fund one or more accounts repeatedly across rooted slots, with no special privileges, no validator/leader control, and no more than ordinary fee-paying transaction submission. It is deterministically repeatable — the longer the interval between full snapshots and the more toggle cycles performed, the larger the stale-entry backlog for that pubkey, bounded only by the attacker's transaction throughput/fee budget.

### Recommendation
Store at most one pending-purge record per pubkey (e.g., use `DashMap<Pubkey, Slot>` and overwrite/replace the entry with the latest observed cannot-purge slot instead of accumulating multiple `(slot, pubkey)` tuples), or explicitly remove any prior `(old_slot, pubkey)` entry for the same pubkey when a newer entry is inserted or when the pubkey's older slot list entries are reclaimed via `collect_reclaims`/`handle_reclaims`.

### Proof of Concept
Rust integration test outline (in `accounts-db/src/accounts_db/tests/impl.rs`):
```rust
#[test]
fn test_zero_lamport_purge_set_bounded_by_unique_accounts() {
    let db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    db.set_latest_full_snapshot_slot(0);

    let pubkey = Pubkey::new_unique();
    let one_lamport = AccountSharedData::new(1, 0, &Pubkey::default());
    let zero_lamport = AccountSharedData::new(0, 0, &Pubkey::default());

    // Toggle the SAME account between non-zero and zero across many slots,
    // running clean after each zero-write, without ever advancing the full
    // snapshot slot (simulating the interval between full snapshots).
    for i in 0..1000 {
        let slot = 1 + i * 2;
        db.store_for_tests((slot, &[(&pubkey, &one_lamport)][..]));
        db.add_root_and_flush_write_cache(slot);
        db.store_for_tests((slot + 1, &[(&pubkey, &zero_lamport)][..]));
        db.add_root_and_flush_write_cache(slot + 1);
        db.clean_accounts(Some(slot + 1), false);
    }

    // Expect the set to hold at most 1 entry (one unique account),
    // but the bug causes it to grow with the number of toggles.
    assert!(
        db.zero_lamport_accounts_to_purge_after_full_snapshot.len() <= 1,
        "set size {} grew proportional to toggle count, not unique accounts",
        db.zero_lamport_accounts_to_purge_after_full_snapshot.len()
    );
}
```
Expected (bug present): the set's length grows to ~1000 (one stale entry per toggle cycle) instead of staying at 1, demonstrating O(toggle count) growth rather than O(unique accounts).
