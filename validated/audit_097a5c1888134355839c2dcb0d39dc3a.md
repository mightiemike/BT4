## Finding

### Title
Unbounded recursion in `bytecode_hash_node` allows a malicious declared class to stack-overflow the sequencer during compiled-class-hash computation - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
The compiled-class hash algorithm recursively walks the `NestedIntList`/`bytecode_segment_lengths` structure that describes how a contract's CASM bytecode is segmented. This structure is derived from the Sierra program supplied by an untrusted contract declarer, and the walk has no depth limit. A crafted declared class that compiles into a deeply-nested segment structure can exhaust the native call stack of the sequencer process that computes the hash, crashing the component before any size/resource limit is applied to that step.

### Finding Description
`bytecode_hash_node` recurses once per nesting level of the segment tree with no depth bound: [1](#0-0) 

It is invoked from `bytecode_hash` → `hash_inner` → the public `HashableCompiledClass::hash` trait method: [2](#0-1) 

This hash is computed in-process (not inside the sandboxed compiler subprocess) every time a class is declared, both in the class-manager/Sierra-compiler service right after compilation: [3](#0-2) 

and again during blockifier/OS transaction validation, which re-derives and checks the compiled class hash against the declared value: [4](#0-3) 

The `NestedIntList` (`bytecode_segment_lengths`) originates from the Sierra→CASM compilation of the attacker-supplied `SierraContractClass`, and its nesting can be arbitrarily deep — a related internal reconstruction routine `NestedFeltCounts::new_inner` even documents/enforces the "depth at most 1" assumption with a hard `assert!`, implying the segment structure is *not* generally bounded to shallow depth by design and any violation panics rather than failing gracefully: [5](#0-4) 

Only `max_bytecode_size` (default 80 × 1024 = 81,920 felts) bounds the total number of leaves/felts in the structure: [6](#0-5) 

Because each `Node` can wrap as little as a single felt, an attacker can construct a Sierra program (via deeply nested function-call/closure structures) whose compiled `bytecode_segment_lengths` is a long, thin chain of nested `Node`s (tens of thousands of levels) while still respecting the felt-count limit. `bytecode_hash_node` and `NestedFeltCounts::new_inner` will then recurse to that same depth natively, which is enough to overflow the thread stack of the class-manager/compile-to-casm/blockifier process on every honest node that processes the declare transaction (gateway validation, mempool re-validation on propagation, block building, and Starknet OS re-execution all invoke this hash).

### Impact Explanation
A stack overflow in this code path aborts the process (or the executing thread) handling the declare transaction. Since every honest sequencer node performs this same hash computation when validating/propagating/executing the declare transaction (gateway, class manager, blockifier, and OS re-execution all call `HashableCompiledClass::hash`), a single malicious declare transaction can reliably crash the relevant component network-wide, preventing the network from confirming this and subsequent transactions — a concrete denial-of-service impacting availability of the sequencer.

### Likelihood Explanation
The attack requires only a single Declare transaction from any unprivileged account with a specially crafted contract (deeply nested function/closure structure compiled by the standard, trusted Sierra→CASM compiler) — no special privileges, node compromise, or p2p-level manipulation needed. The felt-count based bytecode-size limit does not bound recursion depth of the segment tree, so the attack is feasible within existing size constraints.

### Recommendation
Convert `bytecode_hash_node` (and `NestedFeltCounts::new_inner`) to an iterative, explicit-stack algorithm, or enforce and validate a maximum nesting depth for `NestedIntList`/`bytecode_segment_lengths` immediately after Sierra→CASM compilation, rejecting classes whose segment tree exceeds a safe depth before any recursive hashing/processing is performed.

### Proof of Concept
1. Author a Cairo 1 contract whose control-flow/closures are structured so that the Sierra→CASM compiler emits a `bytecode_segment_lengths` (`NestedIntList`) consisting of a long chain of singly-nested `Node`s (depth in the tens of thousands), while keeping total bytecode length under `max_bytecode_size`.
2. Submit this contract as a `Declare` transaction to the gateway.
3. Observe that when the sequencer calls `casm.hash(&HashVersion::V2)` (via `SierraCompiler::compile` in `apollo_compile_to_casm`, or `check_compile_class_hash_v2_declaration` in `executable_transaction.rs`), the recursive `bytecode_hash_node` walk overflows the native stack, crashing the handling process/thread.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

/// Computes the compiled class hash for a given hashable class using the specified hash algorithm.
fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}

        Ok(())
    }

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }
