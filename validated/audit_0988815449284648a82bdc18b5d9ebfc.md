### Title
Unprivileged user can create a permanently-stuck `PendingOutbounds` entry that blocks `MsgInitiateFundMigration` for a chain indefinitely - (File: `x/utss/keeper/msg_initiate_fund_migration.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
This is the same structural bug class as the FactoryDAO finding: a privileged/critical batch-completion operation is gated on "all outstanding items must be resolved," and a single item controlled by an unprivileged, low-cost attacker can be made permanently unresolvable, freezing the gate forever.

### Finding Description
`InitiateFundMigration` (used to move funds from an old TSS key to the new key after a `KEYGEN`) requires that a specific chain have **zero** pending outbounds before it will proceed: [1](#0-0) 

The check is implemented by walking every entry in `PendingOutbounds` and matching on `DestinationChain`: [2](#0-1) 

Per the module's own documentation, `PendingOutbounds` entries are **only** removed when validators reach ballot consensus on an `OutboundObservation` (success or failure) — expiry does **not** remove them, and this is explicitly called out as intentional, with resolution left to manual/governance intervention if an outbound gets stuck: [3](#0-2) 

Any unprivileged holder of a UEA can trigger a bridge/outbound call through `MsgExecutePayload` (gasless, callable by anyone delivering an owner-signed payload) targeting any chain that is currently outbound-enabled: `BuildOutboundsFromReceipt` only validates that the destination chain has outbound enabled — it performs no other sanity checks on the outbound parameters (gas limit, gas price, recipient, payload) before creating the `PendingOutbounds` entry: [4](#0-3) [5](#0-4) 

The off-chain resolution/broadcast path (`universalClient/tss/txresolver/evm.go`, coordinator nonce assignment) is explicitly designed with "the nonce IS the give-up signal; there is no max-retry counter": [6](#0-5) 

If an attacker can craft outbound parameters (e.g. a malformed/extreme `GasLimit`, `GasPrice`, or payload) that cause every validator's local signing-request construction to permanently error out **before** a transaction is ever broadcast on the destination chain, the nonce for that outbound is never consumed, and per the documented give-up model there is no other exit condition — the entry never resolves and is never removed from `PendingOutbounds`.

### Impact Explanation
While a stuck `PendingOutbounds` entry does not itself directly drain funds, it permanently blocks the only mechanism (`MsgInitiateFundMigration`) available to move already-locked chain funds from an old TSS key to a new one after a security-driven `KEYGEN` rotation, for that specific chain. This can indefinitely stall a critical security operation (fund migration off a rotated/potentially-compromised key) and leaves user-owned crosschain funds under the stale TSS key for longer than intended, purely as a consequence of one attacker-created outbound that never terminates. This mirrors the original report's core defect: a single, cheap, attacker-controlled item that can never resolve permanently blocks a privileged, all-or-nothing completion gate that other users' funds/security ultimately depend on.

### Likelihood Explanation
Medium-to-low confidence/likelihood. It is confirmed that (a) the migration gate is a strict "all pending outbounds for chain == 0" check, and (b) `PendingOutbounds` entries are documented as never being cleaned up except via honest-validator ballot consensus. What is **not fully verified** from the available code (coordinator/DKLS signing-request construction and nonce assignment logic were only partially inspected) is whether there exists a concrete outbound parameter an unprivileged user can set that causes the off-chain resolver/coordinator to loop forever without ever assigning/consuming a nonce, as opposed to eventually surfacing a vote (even a failure vote, which would still clear the entry per `msg_vote_outbound.go`). This gap should be verified with a Devin session inspecting `universalClient/tss/coordinator/coordinator.go` in full and the EVM `tx_builder.go` signing-request path for unhandled malformed-input cases.

### Recommendation
- Add validation on outbound parameters (gas limit bounds, payload size, recipient format) at outbound-creation time (`BuildOutboundsFromReceipt`) so malformed values that could never be signed/broadcast are rejected before entering `PendingOutbounds`.
- Add an explicit, validator-driven "unresolvable / expired" terminal state for `PendingOutbounds` entries (similar to `RevertStuckInbound`'s ballot-expiry admin path for inbounds) so a stuck outbound can be administratively cleared without requiring a live vote on a destination-chain transaction that will never exist.
- Consider decoupling `MsgInitiateFundMigration`'s per-chain gate from strictly "count of pending outbounds == 0" to instead allow migration to proceed for provably-stuck/expired entries under a documented admin escape hatch.

### Proof of Concept
Conceptual, not fully verified end-to-end due to unexplored coordinator internals:
1. Attacker (any unprivileged account) submits a `MsgExecutePayload` invoking their UEA's bridge/withdraw path with a payload amount that emits `UniversalTxOutbound` to a real, outbound-enabled chain, but with adversarially-chosen `GasLimit`/`GasPrice`/payload data.
2. `BuildOutboundsFromReceipt` accepts it (only checks that outbound is enabled for the chain) and `attachOutboundsToUtx` inserts a `PendingOutboundEntry` keyed by chain.
3. If the Universal Client's signing-request construction for that outbound cannot ever succeed (malformed inputs), no nonce is ever assigned/consumed, so per the documented "nonce is the only give-up signal" no vote is ever cast and the entry is never removed.
4. Admin later calls `MsgInitiateFundMigration` for that chain (e.g., after a `KEYGEN`); `HasPendingOutboundsForChain` finds the stuck entry and the migration is permanently rejected until manual, out-of-band intervention.

```go
// HasPendingOutboundsForChain checks if there are any pending outbounds for a given chain.
// It walks PendingOutbounds and joins against UniversalTx to check destination_chain.
// Returns true on first match. This is O(n) but only called during admin-initiated migration.
func (k Keeper) HasPendingOutboundsForChain(ctx context.Context, chain string) (bool, error) {
	var found bool
	err := k.PendingOutbounds.Walk(ctx, nil, func(outboundId string, entry types.PendingOutboundEntry) (bool, error) {
		utx, exists, err := k.GetUniversalTx(ctx, entry.UniversalTxId)
		if err != nil {
			return true, err
		}
		if !exists {
			return false, nil
		}
		for _, ob := range utx.OutboundTx {
			if ob.DestinationChain == chain && ob.Id == outboundId {
				found = true
				return true, nil // stop walking
			}
		}
		return false, nil
	})
	if err != nil {
		return false, err
	}
	return found, nil
}
```

```markdown
### `PendingOutbounds`

- **Created** by chain code at outbound creation in `create_outbound.go` —
  BEFORE any validator vote. The chain knows the outbound exists because it
  generated the destination-chain transaction itself; validators are tasked
  with observing whether/how it landed.
- **Keyed** by deterministic chain-derived `outbound_id`.
- **Variant-aware:** validator votes append `OutboundObservationVariant`s as
  they arrive (`RecordOutboundVote` inside `VoteOutbound`). Multiple variants
  per outbound indicate validator divergence on the destination-chain
  observation (different `success`/`tx_hash`/`error_msg`/`gas_fee_used`).
- **Removed ONLY when validators reach consensus** (existing inline
  `PendingOutbounds.Remove` in `msg_vote_outbound.go` on `PASSED`).
- **Ballot expiry does NOT remove the entry** — this is intentional. The
  destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
  driven, not chain-driven.
```

```go
// Decision flow for EVM-broadcasted events (outbound and fund migration both
// follow this shape):
//
//   - VerifyBroadcastedTx error                      → stay BROADCASTED (retry)
//   - Tx found, insufficient confirmations           → stay BROADCASTED (retry)
//   - Tx found, status=1 (success)                   → COMPLETED / vote success
//   - Tx found, status=0 (reverted on chain)         → REVERT  / vote failure with tx hash
//   - Tx not found, signed nonce < finalized nonce   → REVERT  / vote failure (another tx
//                                                                consumed our nonce slot)
//   - Tx not found, signed nonce >= finalized nonce  → rewind to SIGNED so the broadcaster
//                                                      re-broadcasts (covers mempool drop)
//   - Tx not found, nonce check unavailable          → stay BROADCASTED (retry)
//
// The nonce IS the give-up signal; there is no max-retry counter. The two
// flows differ only in (a) which vote function records success/failure and
// (b) where the signer address comes from — current TSS for outbound, OLD TSS
// (derived from the event's old pubkey) for fund migration.
//
// Shared types (SignedOutboundData / SigningData) and helpers (DecodeSigningData,
// ReadSignedNonce, ReadFundMigrationSigner, CheckNonce, NonceVerdict) live in
// tss/txflow so the broadcaster applies the exact same rules.
```
