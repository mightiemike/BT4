### Title
Webhook shop-domain header is not cryptographically bound to the HMAC signature, enabling cross-tenant session/admin-client impersonation - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`)

### Summary
Shopify webhook HMAC validation in this library authenticates only the raw request body; the `X-Shopify-Shop-Domain` header used to select which tenant's offline session/admin client gets attached to the webhook handler is read straight from headers and never included in the signed material. This mirrors the reported Oracle bug class: a value that determines *whose* privileged resource (there: `proposer`'s bonded tokens; here: a merchant's offline session/access token) gets acted upon is supplied by an unauthenticated/uncorrelated channel instead of being bound to the cryptographic proof of authorization.

### Finding Description
`validateHmacFromRequestFactory` computes the HMAC exclusively over `rawBody`: [1](#0-0) 

Once the body HMAC passes, `checkWebhooksHeaders`/`checkEventsHeaders` simply reads the `domain`, `topic`, `webhookId`, and `apiVersion` values from unauthenticated headers and returns them as trusted fields, with no cryptographic linkage between those header values and the verified body: [2](#0-1) 

Downstream, the framework packages take `check.domain` verbatim and use it to look up (and attach) an offline session and build an authenticated admin/storefront client for the webhook handler: [3](#0-2) 

The same pattern exists in the React Router integration: [4](#0-3) 

Because `hmac` only covers `rawBody`, any request whose body+HMAC pair is valid for the app's secret (which an attacker can obtain by triggering a real webhook delivery on **their own** installed shop) can be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a **different, victim** shop. The HMAC check still passes (body unchanged), `checkWebhooksHeaders` returns the attacker-chosen `domain`, and `ensureValidOfflineSession`/`adminClientFactory` build a privileged session/admin client scoped to the victim shop — exactly the "arbitrary actor substitution accepted despite a validation step" pattern from the report, where the dispute-module-supplied `proposer` bypassed the intended per-caller check.

### Impact Explanation
If exploited, an attacker who has installed the app on any shop they control can forge webhook deliveries "from" any other shop that has an existing offline session in the app's session storage. The webhook handler then executes with `shop`/`session`/`admin` context pointing at the victim tenant, letting the attacker trigger app business logic (and any privileged admin-API calls the handler performs) under the victim's access token — a cross-tenant authentication/authorization bypass.

### Likelihood Explanation
The attacker only needs: (1) their own app installation to obtain one legitimately-signed webhook body/HMAC pair (trivial, self-triggered), and (2) knowledge or guessing of a target shop domain that already has an active offline session in the app's storage (the domain is often guessable/public, e.g., `<store>.myshopify.com`). No secrets need to be leaked and no MITM is required, making this a realistic, reachable path from a single merchant/attacker-controlled request.

### Recommendation
- Do not trust header-derived identifiers (`domain`, `webhookId`, `topic`) for session/authorization decisions unless they are cryptographically bound to the signed payload. Consider deriving the tenant identity solely from data embedded in the HMAC-signed body (e.g., signing a canonical string that includes the domain, similar to OAuth/app-proxy HMAC construction which does include `shop`).
- Short term, document/enforce that `checkWebhookHeaders` output must not be treated as authenticated for authorization purposes without additional binding, and add replay protection (e.g., correlate `webhookId`/`eventId` with expected shop, reject duplicate/mismatched delivery IDs).
- Long term, adopt a specification requiring every value used to select a privileged actor/session (analogous to the report's recommendation to allowlist modules per oracle) to be included in the signed material, closing the class of "signature covers X but authorization decision uses unrelated Y" bugs.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic to receive a legitimately Shopify-signed request `(rawBody, X-Shopify-Hmac-Sha256)`.
2. Capture that request.
3. Re-POST the identical `rawBody` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com` (a shop known to have installed the app).
4. `validateHmacFromRequestFactory` validates the (unchanged) body HMAC successfully. [1](#0-0) 
5. `checkWebhooksHeaders` returns `domain: 'victim.myshopify.com'` as part of the "valid" result. [5](#0-4) 
6. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` and attaches an `admin` client for `victim.myshopify.com` to the webhook context passed to the app's handler. [6](#0-5) 

Note: I could not fully inspect `ensureValidOfflineSession`'s implementation (index size limits may have truncated it in the index); confirming the exact refresh/validation logic it performs on the loaded session would benefit from a full review in a Devin session with complete file access.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };
