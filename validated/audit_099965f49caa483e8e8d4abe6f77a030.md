### Title
`ensure_match_transaction_info` omits the state/hot-state/position checkpoint hashes from replay verification — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the local (non-consensus) authenticated-response check used by `db-tool`'s `replay_on_archive`/`replay_verify` and by `aptos-debugger`/CLI transaction-replay to confirm that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed to the ledger accumulator. The function checks status, gas used, write-set hash, and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents but does not fix.

### Finding Description
`ensure_match_transaction_info` [1](#0-0)  validates only 4 of the fields that make up `TransactionInfoV1`: execution status, gas used, write-set hash (`state_change_hash`), and event root hash [2](#0-1) . It ends with an explicit acknowledgement that it skips the state-root fields entirely: [3](#0-2) 

This means the function silently accepts a `TransactionOutput` whose resulting state (main state, hot state, or native-position state) diverges from the state root that was actually committed on-chain and authenticated via `TransactionInfoV1.state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`. The check is wired into the primary re-execution/replay-verification tools:
- `storage/db-tool/src/replay_on_archive.rs` calls it after re-executing each chunk against archived `TransactionInfo`s [4](#0-3) .
- `aptos-move/cli/src/commands.rs` uses it for both user-transaction and system-transaction replay verification via the `aptos move replay` / debugger commands [5](#0-4) [6](#0-5) .

The trading-native state root feature is real and already gateable via the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag [7](#0-6) , and once enabled the execution pipeline commits a `position_state_checkpoint_hash` into `TransactionInfoV1` that is meant to be consensus-verified [8](#0-7) . However, this authenticated field is never independently re-validated by the replay/audit tool path described above — only the in-protocol executor path (`DoStateCheckpoint`/`DoLedgerUpdate`, which does compare against `known_position_state_checkpoints`) performs that check during normal block/chunk execution [9](#0-8) . The off-chain/audit-facing `ensure_match_transaction_info` path — the one operators and auditors use to confirm archived history is correct — has no such check.

### Impact Explanation
This is a proof/state-integrity gap in the authenticated-response verification surface, not in the consensus-critical hot path. If a corrupted or forked state root (main state, hot state, or native-position state) were ever committed to a `TransactionInfoV1` (e.g., due to a divergent full node, a storage bug, or a malicious archive operator serving tampered `TransactionInfo`s alongside correct events/gas/status/write-set hash), `ensure_match_transaction_info` would report the replay as **matching** even though the actual state root diverges from what local re-execution computed. This directly undermines the guarantee that `db-tool replay-on-archive` / `replay-verify` (Aptos's primary tool for auditing historical DB integrity and catching state divergence bugs) can detect corruption of the state-checkpoint/hot-state/position-state roots. Since this is the trust mechanism operators and the Aptos team rely on to catch exactly this class of bug post-hoc, silently passing over these fields could let a genuine state-commitment divergence go undetected during audits, which is a high-severity gap in the proof/verification tooling even though it does not itself corrupt live consensus state.

### Likelihood Explanation
The gap is deterministic and always present — it does not depend on adversarial timing. Any invocation of `ensure_match_transaction_info` (used by every replay-verify/replay-on-archive run and by CLI/aptos-debugger transaction replay) will unconditionally skip checking these three hash fields, regardless of whether `TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, or `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled. The comment in the code confirms the aptos-core authors are aware of this gap and have not yet closed it, explicitly noting it must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`."

### Recommendation
Extend `ensure_match_transaction_info` to compute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when available), and `position_state_checkpoint_hash` (when available) against the corresponding fields on `txn_info`, mirroring how `DoStateCheckpoint`/`get_state_checkpoint_hashes` validates these during normal execution. At minimum, gate replay-verify/replay-on-archive so it refuses to silently succeed on transactions where `TransactionInfoV1` carries a non-`None` state-root field that isn't independently re-derived and compared.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1`, `HOTNESS_IN_EPILOGUE`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` so `TransactionInfoV1.position_state_checkpoint_hash` is populated and consensus-authenticated.
2. Construct/obtain an archived `TransactionInfo` at some version whose `position_state_checkpoint_hash` (or `state_checkpoint_hash`) does not match what local re-execution of the corresponding transaction would produce (e.g., simulate a storage/index bug that corrupts a native-position write before commit, or hand-craft a test `TransactionInfo` with a mutated hash while keeping status/gas/write-set-hash/event-root-hash intact).
3. Run `db-tool replay-on-archive` (or the CLI replay path) against this version; observe that `Verifier::execute_and_verify` → `ensure_match_transaction_info` [4](#0-3)  returns `Ok(())` because status, gas, write-set hash, and event root hash all still match, even though the state root diverges.
4. This demonstrates that the tool would report "replay succeeded" for a version where the authenticated state root does not match local execution — exactly the scenario the code's own TODO warns about.

Note: I was unable to fully confirm whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` are currently enabled on Aptos mainnet or only staged for future activation; if neither is enabled yet, the `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` portion of this gap has no live impact today, but the `state_checkpoint_hash` omission applies regardless of these flags and is present in the current code as shown above.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );
