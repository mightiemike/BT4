### Title
Missing `is-in-voting-window` check in `vote-for-aggregate-public-key` allows the DKG total-weight cache to be poisoned before the signer set is finalized, letting a minority of real signer weight approve an aggregate public key - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
`signers-voting.clar` defines a private helper `is-in-voting-window` that is supposed to gate voting to the correct reward cycle and prepare phase, but it is never invoked anywhere in the contract, including in the only public entry point, `vote-for-aggregate-public-key`. `grep` confirms the function symbol `is-in-voting-window` appears exactly twice in the whole codebase - both inside its own definition - meaning it is dead code that nothing calls. This mirrors the Passages.sol report's bug class exactly: a state guard exists in the code base, but the state-changing function that should honor it is missing the corresponding check, so an action ("vote") can proceed in a window when it should be blocked.

### Finding Description
`vote-for-aggregate-public-key` is the sole way signers cast DKG votes and cache the total weight for a reward cycle: [1](#0-0) 

`is-in-voting-window` checks that (a) the `.signers` contract has already finalized the signer set for the *given* `reward-cycle` (`last-cycle == reward-cycle` via `get-last-set-cycle`), and (b) the current burn height is within the prepare phase. Neither condition is enforced in `vote-for-aggregate-public-key`: [2](#0-1) 

The checks that *are* present are: key not already approved, key length, key novelty, no duplicate vote, and round increments by at most one. None of these substitute for confirming the signer set for `reward-cycle` has actually been finalized before votes (and the weight cache) are accepted.

The consequence is in `get-and-cache-total-weight`, which is memoized per `reward-cycle` the first time it's called: [3](#0-2) 

Because nothing prevents `vote-for-aggregate-public-key` from being called for a `reward-cycle` before `.signers` has set that cycle's final signer roster, `get-signers` can be queried and cached prematurely, potentially returning an incomplete/empty/stale signer set. The `cycle-total-weight` cache is set-once (via `map-set` inside a `match ... total (ok total)` fallthrough) and is never recomputed afterward — even once the real signer set becomes available. `get-threshold-weight` (used to decide when a key is "approved") is computed directly from that permanently-cached total: [4](#0-3) 

If the cached total is understated relative to the real, finalized total signer weight, then far less than 70% of the actual signer set's weight is needed to reach `threshold-weight` and get `map-insert aggregate-public-keys reward-cycle key` to succeed — i.e., a minority of real signer weight can force approval of an aggregate public key for the cycle.

### Impact Explanation
This is the "signer weight below threshold or from the wrong set" analog explicitly called out as in-scope. The `.signers`/`signers-voting` approved aggregate public key is the consensus-critical value used to validate the threshold BLS/FROST signature over Nakamoto blocks for that reward cycle. If a minority of signer weight can force `aggregate-public-keys` to be set for a cycle before all voting weight is correctly accounted for, the chain's block-signature verification for that cycle can be anchored to a key that does not represent 70% of the real signer weight, which is precisely the guarantee the threshold-consensus mechanism is meant to provide. This is a High-severity, minority-triggerable divergence from the intended signer-weight threshold rule, bounded to the signer-selection/DKG-approval mechanism (not requiring a majority or Bitcoin-consensus defect, and not an economic/price assumption).

### Likelihood Explanation
Exploitability depends on whether `.signers get-signers reward-cycle` returns a non-empty but incomplete signer list (or zero) prior to that reward cycle's signer set finalization, and whether a signer/party can invoke `vote-for-aggregate-public-key` for a future `reward-cycle` argument ahead of the prepare phase. `get-signer-weight` (called before the missing-window checks) already requires the caller to be a valid signer *for that reward-cycle* per `.signers get-signer-by-index`, which constrains who can trigger the premature cache, but does not block early/invalid-timing calls once such a signer entry exists for the given cycle. The dead `is-in-voting-window` helper's mere existence, unused, strongly indicates this was an intended guard that was dropped during refactors — i.e., a real regression rather than a false positive, though full confirmation requires tracing `.signers` contract state transitions (`set-signers` cycle boundaries) to pin the exact exploitable window, which is out of the indexed excerpt available here.

### Recommendation
Add the missing guard to `vote-for-aggregate-public-key`, mirroring the intent of `is-in-voting-window`:
```clarity
(asserts! (is-in-voting-window burn-block-height reward-cycle) (err ERR_OUT_OF_VOTING_WINDOW))
```
placed before `get-and-cache-total-weight` is invoked, so that the total-weight cache can only ever be populated once the signer set for `reward-cycle` is finalized and the reward cycle is in its prepare phase. Additionally, consider whether `cycle-total-weight` should be recomputed (rather than cached once) if it can legitimately change after being first read, to remove the class of bug entirely rather than relying solely on the window check.

### Proof of Concept
Conceptual PoC (Clarity contract call trace, since a live simnet harness would be needed to fully execute):
1. Before `.signers` has finalized the signer roster for `reward-cycle = N` (i.e., `get-last-set-cycle` returns something other than `N`, so `is-in-voting-window` would return `false` if it were checked), have a signer that is nonetheless already registered as signer-index `i` for cycle `N` (e.g., carried over from a prior registration or a partial roster) call:
   `(contract-call? .signers-voting vote-for-aggregate-public-key i malicious-key round0 N)`
2. This call succeeds because no `is-in-voting-window` assertion exists; `get-and-cache-total-weight` is invoked and caches `cycle-total-weight[N]` based on whatever `.signers get-signers N` returns at this premature point (potentially a small/partial list summing to a low total).
3. Subsequent votes from the same minority of signers (or the same signer casting through the allowed round increments) accumulate weight against this artificially low cached total until `new-total >= threshold-weight` (`get-threshold-weight` computed off the poisoned cache), causing `(map-insert aggregate-public-keys N malicious-key)` to succeed — approving `malicious-key` for reward cycle `N` using far less than 70% of the true, later-finalized signer weight.
4. `cycle-total-weight[N]` is never recomputed afterward, so the approval is permanent for that cycle even after honest nodes see the true, larger signer set. [5](#0-4)

(define-private (is-in-voting-window (height uint) (reward-cycle uint))
    (let ((last-cycle (unwrap-panic (contract-call? .signers get-last-set-cycle))))
        (and (is-eq last-cycle reward-cycle)
            (is-in-prepare-phase height))))

(define-private (sum-weights (signer { signer: principal, weight: uint }) (acc uint))
    (+ acc (get weight signer)))

(define-private (get-and-cache-total-weight (reward-cycle uint))
    (match (map-get? cycle-total-weight reward-cycle)
        total (ok total)
        (let ((signers (unwrap! (contract-call? .signers get-signers reward-cycle) (err ERR_FAILED_TO_RETRIEVE_SIGNERS)))
                (total (fold sum-weights signers u0)))
            (map-set cycle-total-weight reward-cycle total)
            (ok total))))
