### Title
Off-by-one in `DelegateAction` expiry check allows execution at `max_block_height` — (File: runtime/runtime/src/actions.rs)

### Summary
`apply_delegate_action` uses a strict greater-than (`>`) comparison to test whether a delegate action has expired, but the protocol spec and the field's own documentation require a greater-than-or-equal (`>=`) comparison. This lets a malicious relayer execute a user-signed delegate action at the exact block the user expected it to have expired, enabling unauthorized fund transfers.

### Finding Description
In `apply_delegate_action` at line 435 the expiry guard is:

```rust
if apply_state.block_height > delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
```

The `DelegateAction.max_block_height` field is documented as:

> "The maximal height of the block in the blockchain **below which** the given DelegateAction is valid."

"Below which" means valid only for blocks with height **strictly less than** `max_block_height`. At `block_height == max_block_height` the action should already be expired.

The protocol spec in `docs/RuntimeSpec/Actions.md` is explicit:

> "If the current block is **equal or greater than** `max_block_height`" → `DelegateActionExpired`

The code uses `>` (strict), so when `block_height == max_block_height` the condition is `false` and the action executes. The existing test `test_delegate_action_validate_sender_account` confirms this: it sets `apply_state = create_apply_state(max_block_height)` and does **not** expect `DelegateActionExpired`, proving the action is still live at that height. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The `DelegateActionExpired` error variant's own comment also contradicts the code: it says "max_block_height is **less than** actual block height" (i.e. `max_block_height < block_height`, equivalently `block_height > max_block_height`), which matches the code but contradicts the field description and the Actions.md spec. [5](#0-4) 

### Impact Explanation
A user signs a `DelegateAction` with `max_block_height = H` and hands it to a relayer, expecting the action to be unexecutable at or after block H. A malicious relayer withholds the action until block H, then submits it. The runtime evaluates `H > H` → `false`, so the action is not expired and executes. Any `Transfer`, `FunctionCall`, or other action inside the delegate action runs at block H, debiting the user's balance or executing contract logic the user believed was no longer authorised. This is an unauthorized transaction from the user's perspective and constitutes balance manipulation / unauthorized transaction execution.

### Likelihood Explanation
Every meta-transaction user who relies on `max_block_height` as a cancellation deadline is affected. No special privilege is required: any relayer simply delays submission by one block. The window is exactly one block, but in NEAR's ~1-second block time that is a concrete, exploitable interval, especially for time-sensitive DeFi or payment delegate actions.

### Recommendation
Change the comparison from `>` to `>=` in `apply_delegate_action`:

```rust
// runtime/runtime/src/actions.rs, line 435
if apply_state.block_height >= delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
```

Update `test_delegate_action_max_height` to also assert expiry at `max_block_height` (not only at `max_block_height + 1`), and align the `DelegateActionExpired` error comment to read "max_block_height is less than or equal to actual block height." [6](#0-5) 

### Proof of Concept

1. User creates `DelegateAction { max_block_height: H, actions: [Transfer { deposit: 100 NEAR }], … }` and signs it.
2. User gives the signed action to a relayer, expecting it to be invalid at block H.
3. Relayer waits until block H and submits the enclosing transaction.
4. `apply_delegate_action` evaluates `apply_state.block_height (H) > max_block_height (H)` → `false`.
5. The expiry branch is skipped; `validate_delegate_action_key` succeeds; a new receipt is created and the 100 NEAR transfer executes.
6. The user's account is debited 100 NEAR at block H, one block after they believed the action had expired. [7](#0-6)
