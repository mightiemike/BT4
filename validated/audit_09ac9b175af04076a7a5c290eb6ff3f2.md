## Analysis

The external report's bug class is: **a division performed before a multiplication truncates a legitimate non-zero value to zero, which is then propagated through downstream logic that misinterprets "zero" as a valid, real economic quantity, corrupting an accounting outcome.**

The matching analog in this repository is in `CalculateGasCost` in [1](#0-0) , which computes the gas fee charged for module-originated `DerivedEVMCall`/`ExecutePayloadV2` executions.

### Title
Premature truncation of sub-1-upc base fee to zero in `CalculateGasCost` allows free UEA payload execution and corrupts gas fee accounting - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost` converts the feemarket's `LegacyDec` base fee to a whole-`upc` `*big.Int` by dividing by `1e18` **before** multiplying by `gasUsed`. Any base fee value that is non-zero but represents less than 1 whole `upc` per gas unit (e.g. `0.5upc`) is floored to `0` by this early division, so the subsequent multiplication `effectiveGasPrice * gasUsed` always yields `0`, regardless of `gasUsed`. This is the same defect pattern as the referenced UniswapV3 report: dividing before multiplying discards precision that should have been preserved until after scaling, silently zeroing out a value that is not actually zero.

### Finding Description [2](#0-1) :
```go
baseFeeBig := baseFee.BigInt()
// ... base fee is always a whole number of upc -- no fractional upc exists.
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
```
`baseFee.BigInt()` returns the raw internal representation of the `LegacyDec` (value × 10^18). The code assumes the base fee is always a whole-`upc` integer, but nothing in the scoped code enforces that invariant — the feemarket's base fee is a continuously adjusted `LegacyDec` (standard EIP-1559 style additive/multiplicative adjustment each block based on gas utilization), and it can legitimately hold fractional values below `1e18` in its internal encoding (i.e. an economically real base fee strictly between `0` and `1 upc`). When that happens, `baseFeeBig.Div(..., 1e18)` truncates to `0` **before** it is ever multiplied by `gasUsed` in step 4: [3](#0-2) .

The resulting `gasCost` of `0` is then handled by `DeductGasFeesFromReceipt`, which explicitly treats non-positive gas cost as "nothing to bill" and skips fee deduction entirely: [4](#0-3) .

This is reachable from ordinary, unprivileged user flows: `ExecutePayloadV2` — invoked for `MsgExecutePayload` and for module-derived inbound payload execution — always calls `DeductGasFeesFromReceipt` after running the user's EVM call via the UEA: [5](#0-4) . If the base fee state happens to be sub-1-upc at execution time, the EVM call's real gas usage is fully executed and committed (`writeCache()`), but zero `upc` is ever transferred/burned as a fee, silently breaking the "gas fee accounting" invariant explicitly called out as in-scope.

Crucially, the base fee reaching this sub-1-upc state does not require any privileged or malicious actor: a standard EIP-1559 base fee mechanism decays the base fee geometrically toward zero during periods of low block gas utilization. Absent enforcement of a floor tied to this specific consuming code path, sustained low-usage periods alone (no attacker action required) can drive the tracked base fee arbitrarily close to zero, at which point this truncation bug becomes active for every unprivileged user submitting `MsgExecutePayload`/payload-carrying inbound messages.

### Impact Explanation
While the base fee is in the vulnerable range, every unprivileged user gets free, uncharged execution of arbitrary UEA/CEA-derived EVM calls through `ExecutePayloadV2`. This is a corruption of gas fee accounting (an explicitly listed in-scope impact): expected fees are neither deducted from the user nor burned, and the module offers unlimited free compute to anyone who submits payloads while conditions hold, which can also be leveraged to amplify unprivileged resource consumption at zero cost.

### Likelihood Explanation
The trigger condition (base fee dec value < 1 upc) is a state-dependent precondition rather than an always-on bug, so likelihood depends on the feemarket's actual floor/minimum behavior in production configuration. However, the code contains no independent enforcement of the "always whole-upc" assumption it relies on, and the standard EIP-1559 decay mechanism can approach this state without any privileged actor — it only requires sustained low network utilization, which is an ordinary, non-adversarial condition.

### Recommendation
Do not divide the base-fee `LegacyDec` down to whole-`upc` precision before multiplying by `gasUsed`. Instead, perform the multiplication in the higher-precision `LegacyDec` domain (`baseFee.MulInt64(int64(gasUsed))` or equivalent big-int arithmetic that multiplies the raw 18-decimal-scaled value by `gasUsed` first) and only divide by `10^18` (with appropriate rounding, e.g. ceiling to protect the protocol) as the very last step, mirroring the audited report's fix of deferring the division until after the multiplication.

### Proof of Concept
1. Let the feemarket base fee decay (via sustained low block utilization, an ordinary/non-privileged condition of the EIP-1559 mechanism) to a value `0 < baseFee < 1upc`, e.g. `0.5upc` (`LegacyDec` internal value `5e17`).
2. An unprivileged user submits `MsgExecutePayload` (or triggers a `DerivedEVMCall` via an inbound) with a `universalPayload` whose EVM call consumes substantial `gasUsed`.
3. `CalculateGasCost` computes `baseFeeBig = 5e17`, then `baseFeeBig.Div(5e17, 1e18) = 0`, so `effectiveGasPrice = 0` and `gasCost = 0 * gasUsed = 0`.
4. `DeductGasFeesFromReceipt` sees `gasCost.Sign() <= 0` and returns `nil` without deducting or burning any fee.
5. `ExecutePayloadV2` commits the EVM state changes (`writeCache()`) while zero `upc` was ever charged, even though `gasUsed` was non-trivial — repeatable by any user for as long as the base fee remains in this range.
