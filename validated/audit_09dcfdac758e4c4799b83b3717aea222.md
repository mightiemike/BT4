### Title
`ProposalStore.getAllProposals` uses a non-contract-compliant comparator that can throw `IllegalArgumentException` on the public proposal-listing RPC - ([File: chainbase/src/main/java/org/tron/core/store/ProposalStore.java])

### Summary
`ProposalStore.getAllProposals()` sorts proposals with the lambda `(a, b) -> a.getCreateTime() <= b.getCreateTime() ? 1 : -1`, which violates the `Comparator` contract because `compare(a, a)` returns `1` instead of `0` and equal elements are never treated as equal. `Collections.sort`/`Stream.sorted` in Java use TimSort, which can detect such contract violations on sufficiently large inputs and throw `IllegalArgumentException: Comparison method violates its general contract!`, crashing the read path (`ListProposals` via `Wallet`).

### Finding Description
The comparator in `getAllProposals` is defined as: [1](#0-0) 

For any two capsules `a, b` with equal `createTime`, `compare(a,b)` returns `1` and `compare(b,a)` also returns `1`, violating the required `sgn(compare(x,y)) == -sgn(compare(y,x))` antisymmetry property, and `compare(a,a)` returns `1` instead of the required `0`. `getAllProposals` is reachable from the public `ListProposals` RPC through `Wallet` (confirmed the reference in `framework/src/main/java/org/tron/core/Wallet.java`). `createTime` is set from `getLatestBlockHeaderTimestamp()` in `ProposalCreateActuator.execute`, so all proposals created in the same block share an identical `createTime`: [2](#0-1) 

Java's `TimSort` (backing `Collections.sort`/`Stream.sorted` for object arrays) performs an internal consistency check while merging runs and throws `IllegalArgumentException("Comparison method violates its general contract!")` when it detects an inconsistent comparator. However, this check is only exercised when TimSort actually performs a merge of multiple runs, which requires the input array to exceed the `MIN_MERGE` threshold (32 elements by default); for arrays smaller than that, TimSort falls back to binary insertion sort, which does not perform the contract-violation check and will not throw regardless of comparator inconsistency. Therefore the exact precondition claimed in the prompt (`>=3` proposals with equal `createTime`) is **not sufficient** to reliably trigger the exception — a much larger number of proposals (realistically dozens, comparable to or above the TimSort merge threshold) sharing the same `createTime` (or an overall list large enough to trigger merging, with the offending elements positioned across run boundaries) would be needed, and even then the exact reproduction is comparator-implementation- and JDK-version-dependent, not deterministic from `>=3` duplicates alone.

The comparator bug itself is real and a legitimate defect (violates `Comparator` contract, non-transitive/non-reflexive), but the specific DoS claim as scoped (triggerable with only 3 same-timestamp proposals) is not accurate given TimSort's actual behavior on small lists. Whether the vulnerability is practically exploitable also depends on whether the total number of live (non-expired, non-deleted) proposals in the store can realistically reach the dozens required — proposal creation is gated by requiring the creator to be a registered witness (`chainBaseManager.getWitnessStore().has(ownerAddress)`), so this is not exploitable by an arbitrary unprivileged address, only by (potentially colluding) witnesses: [3](#0-2) 

Since witnesses are a privileged consensus role, not "any address," and the number of witnesses (and thus proposals that can be created within one block/timestamp) is bounded and typically small, reaching the volume needed to trigger the merge-sort contract-violation path within a single shared `createTime` window in practice is not straightforward, and the question's premise that "any address" or ordinary usage can trigger this deterministically with just 3 duplicates is not supported by TimSort's actual mechanics.

### Impact Explanation
If triggered, `getAllProposals()` throwing an uncaught `IllegalArgumentException` would cause the `ListProposals`/`ListProposalsPaginated` RPC calls to fail for callers hitting that specific node, which is a legitimate (if narrow) availability concern for a read API. It does not affect consensus, funds, or write-path state.

### Likelihood Explanation
Low/uncertain as scoped. Creating a proposal requires the caller to be a registered witness account, which is a privileged role, not an arbitrary attacker address. Even with witness collusion, achieving enough proposals (likely dozens, well beyond the "3" claimed) with identical `createTime` to actually hit TimSort's merge-time contract check is not guaranteed and depends on JDK sort implementation internals not demonstrated in the report's proof idea.

### Recommendation
Fix the comparator to be contract-compliant, e.g. use `Long.compare(a.getCreateTime(), b.getCreateTime())` (or `Comparator.comparingLong(ProposalCapsule::getCreateTime)`), which correctly returns `0` for equal timestamps and is properly antisymmetric/transitive. Apply the same fix to the similar comparator in `getSpecifiedProposals` for consistency and safety: [4](#0-3) 

### Proof of Concept
Unit test plan (not confirmed to reproduce reliably at only 3 elements — would need to insert a large number, e.g. 50+, of `ProposalCapsule`s with identical `createTime` into a test `ProposalStore`/list, then call `getAllProposals()` and assert whether `IllegalArgumentException` is thrown or not, to empirically determine the actual reproduction threshold on the target JDK version):
```java
List<ProposalCapsule> proposals = new ArrayList<>();
for (int i = 0; i < 64; i++) {
  ProposalCapsule p = new ProposalCapsule(ByteString.copyFrom(new byte[21]), i);
  p.setCreateTime(1000L); // identical createTime for all
  proposals.add(p);
}
// Directly exercise the comparator used in ProposalStore.getAllProposals
assertDoesNotThrow(() ->
    proposals.stream()
        .sorted((a, b) -> a.getCreateTime() <= b.getCreateTime() ? 1 : -1)
        .collect(Collectors.toList()));
```
Regardless of whether the exception reproduces at a given list size, replacing the comparator with `Long.compare(...)` should be verified to never throw for any input size or ordering.
