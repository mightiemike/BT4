### Title
Stale-sized fork-stats array causes `ArrayIndexOutOfBoundsException` in `ForkController.downgrade` when the active-witness set changes size - (File: `chainbase/src/main/java/org/tron/common/utils/ForkController.java`)

### Summary
`ForkController` tracks per-hard-fork-version witness "vote" bytes in a `byte[]` (`stats`) persisted via `DynamicPropertiesStore.statsByVersion`. The array is sized to `witnesses.size()` only at the moment a given version's stats array is created, and it is only re-created when the *same* version's stats happen to be re-read with a mismatched size in `update()`. Other, not-yet-passed versions' stats arrays are mutated in `downgrade()` using an index (`slot`) computed against the *current* active-witness list, without ever checking that the stale array is still large enough. This is analogous to the CouncilMember bug: an auxiliary array (`balances` / `stats`) is decoupled from the size of the “id space” it is indexed by (`tokenId` / witness `slot`), and later writes performed with the now-larger id/slot silently go out of the old array's bounds.

### Finding Description
In `update()`:
```java
List<ByteString> witnesses = manager.getWitnessScheduleStore().getActiveWitnesses();
int slot = witnesses.indexOf(witness);
...
downgrade(version, slot);

byte[] stats = manager.getDynamicPropertiesStore().statsByVersion(version);
if (Objects.isNull(stats) || stats.length != witnesses.size()) {
  stats = new byte[witnesses.size()];   // only THIS version's array is resized
}
``` [1](#0-0) 

`downgrade()` operates on *other* fork versions (`versionValue > version`) whose stats arrays were created at an earlier point in time with whatever `witnesses.size()` was then:
```java
private void downgrade(int version, int slot) {
  for (ForkBlockVersionEnum versionEnum : ForkBlockVersionEnum.values()) {
    int versionValue = versionEnum.getValue();
    if (versionValue > version && !pass(versionValue)) {
      byte[] stats = manager.getDynamicPropertiesStore().statsByVersion(versionValue);
      if (Objects.nonNull(stats)) {
        stats[slot] = VERSION_DOWNGRADE;   // no bounds check against slot
        manager.getDynamicPropertiesStore().statsByVersion(versionValue, stats);
      }
    }
  }
}
``` [2](#0-1) 

`upgrade()` has the same class of issue: it reuses an existing, possibly-stale `stats` array and only replaces it if it is `null`/empty, otherwise it writes `Arrays.fill(stats, VERSION_UPGRADE)` over an array whose length no longer matches the current witness count:
```java
byte[] stats = manager.getDynamicPropertiesStore().statsByVersion(versionValue);
if (stats == null || stats.length == 0) {
  stats = new byte[slotSize];
}
Arrays.fill(stats, VERSION_UPGRADE);
``` [3](#0-2) 

`reset()` similarly only resizes an array if it is non-null and the version hasn't passed, and uses `size = manager.getWitnessScheduleStore().getActiveWitnesses().size()` at reset time, which can again drift from the size used for `slot` indexing in a later `update()` call before the next `reset()`: [4](#0-3) 

The active-witness list (`WitnessScheduleStore.getActiveWitnesses()`) is not a fixed-length structure — it is recomputed and re-saved every maintenance cycle in `MaintenanceManager.doMaintenance()` via `DposService.updateWitness()`, which can save an active-witness list whose size is smaller than `MAX_ACTIVE_WITNESS_NUM` (e.g., when there are fewer eligible/voted candidates than the maximum) and can grow again in a subsequent cycle: [5](#0-4) [6](#0-5) 

Because `slot = witnesses.indexOf(witness)` is computed against the *current* size, but `downgrade()`/`upgrade()` write into `stats` arrays that may have been created/sized against a *previous, smaller* witness-set size, a witness whose slot index exceeds the length of a stale, not-yet-resized `stats` array will trigger `stats[slot] = ...` on an array too short for that index — an `ArrayIndexOutOfBoundsException`.

### Impact Explanation
`ForkController.update()` is called from block-processing/`Manager` logic on every applied block (each `BlockCapsule` carries `blockHeader.rawData.version`), which is fully reachable from normal chain operation and from any block broadcast by a witness. An unhandled `ArrayIndexOutOfBoundsException` thrown mid-block-application is not caught anywhere in this code path, so it would propagate up through block processing, crashing/halting the applying node (or, if only some nodes hit the divergent-size stats array due to differing local witness-schedule state, causing consensus/state divergence between nodes). This qualifies as a DoS/consensus-divergence-class defect in a core protocol component (hard-fork activation tracking), not a peripheral utility.

### Likelihood Explanation
Likelihood is moderate: the active-witness set size is only guaranteed to be stable when there are always ≥ `MAX_ACTIVE_WITNESS_NUM` (27) fully-voted SR candidates; on networks (private/consortium chains, or during periods with fewer eligible candidates) where the active set can shrink below 27 and later regrow, this exact "array sized at an earlier smaller witness count, later indexed by a slot valid for a larger witness count" condition can occur naturally across maintenance cycles, without requiring any privileged or malicious actor — it is a protocol-logic bug reachable purely through normal witness churn and fork-version voting.

### Recommendation
In `downgrade()` and `upgrade()`, always validate/resize the fetched `stats` array against the current `witnesses.size()` (or the caller-supplied `slotSize`) before indexing into it, mirroring the size-check already done in `update()` for the primary version's own array — e.g. reallocate (and re-migrate old byte values) whenever `stats.length != witnesses.size()`, and add explicit bounds checking (`slot < stats.length`) before any write, skipping/logging instead of throwing when the array cannot yet represent the current witness index.

### Proof of Concept
Conceptual reproduction (exact reproduction requires driving `MaintenanceManager.doMaintenance()`/`DposService.updateWitness()` across cycles, not verified end-to-end in this review):
1. Configure/drive the chain so the active-witness list has N1 members; produce a block with a new (not-yet-passed) higher `ForkBlockVersionEnum` value V using `ForkController.update()` → `stats` (for V) gets created with length N1, and `stats` arrays for any lower not-yet-passed version get touched by `downgrade()` sized against N1.
2. Trigger a maintenance cycle where `DposService.updateWitness()` saves a new active-witness list of length N2 > N1 (e.g., due to more addresses reaching the vote threshold), including a witness whose position in the new list yields `slot >= N1`.
3. Produce another block with that witness for some version V2 > V (still not passed) that goes through `downgrade(V2, slot)`; the fetched `stats` array for the intervening version was sized N1 in step 1 and is fetched and indexed with `slot >= N1` in `downgrade()`, throwing `ArrayIndexOutOfBoundsException` during block application.
