### Title
Meta-transaction `receiver_id` mismatch bypasses `DeterministicStateInitAction` receiver check pre-`FixDelegatedDeterministicStateInit` (protocol v85) - ([File: runtime/runtime/src/action_validation.rs])

### Summary
The reported Gitcoin bug is a class of "identifier not verified against the address/target it should be bound to" — a caller supplies two related values (`_projectId` and `_grantAddress`) that are supposed to correspond, but the contract never checks that correspondence, so funds/state can go to the wrong target while records reference the "correct" ID. The nearcore analog is the (now-fixed) `DeterministicStateInit` meta-transaction receiver check: `SignedTransaction`/outer-tx validation checked the wrong field (`outer_tx.receiver_id`) instead of `delegate_action.receiver_id` when validating that a `DeterministicStateInitAction`'s target account matches the account derived from its `state_init`.

### Finding Description
`DeterministicStateInitAction` creates/initializes a deterministic account whose id is derived from its `state_init` payload via `derive_near_deterministic_account_id`. When such an action is wrapped in a `DelegateAction` (a NEP-366 meta transaction), the actual execution receiver should be `delegate_action.receiver_id` — the account the inner actions are applied against — not the outer relayer transaction's `receiver_id`. Before the `FixDelegatedDeterministicStateInit` protocol feature (activated at protocol version 85, per `core/primitives-core/src/version.rs`), the initial transaction-validation path checked the wrong `receiver_id`, so an attacker could craft a `DelegateAction` whose `receiver_id` points at a *different* deterministic account (`det_account_a`) than the one actually derivable from the `state_init` payload (`det_account_b`), and the outer tx would still pass initial validation. This is directly reproduced by the regression test `try_meta_tx_deterministic_receiver_exploit` in `test-loop-tests/src/tests/deterministic_account_id.rs:179-262`, and the pre-fix/post-fix behavior is asserted in `test_deterministic_state_init_meta_tx_receiver_check_pre_fix` and `test_deterministic_state_init_meta_tx_receiver_check` (same file, lines 137-171). The fix introduces `ActionsValidationError::InvalidDeterministicStateInitReceiver`, enforced in `runtime/runtime/src/action_validation.rs`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation
If this defect were live (pre-v85 protocol), a relayer/meta-tx-sender pairing could cause a `DeterministicStateInitAction` to pass initial tx-validation with a `receiver_id` that does not match the account derivable from the embedded `state_init`, i.e. analogous to the "vote for `projectID` while sending funds to an unrelated `grantAddress`" bug — an action bound for one deterministic account could initially validate against a mismatched target, which could break invariants relied upon for deterministic-account addressing (state divergence / incorrect account initialization) before being caught later at receipt validation. This maps to "invalid state transition acceptance" during the earlier `verify_and_charge` phase, distinct from the later, correctly-failing receipt validation.

### Likelihood Explanation
Uncertain/likely already mitigated: the code in this repository shows the fix (`FixDelegatedDeterministicStateInit`) is already implemented and gated behind protocol version 85, per `core/primitives-core/src/version.rs` and `runtime/runtime/src/action_validation.rs`. The wiki notes in `protocol-model/spec/accounts-keys.md:98` list `FixDelegatedDeterministicStateInit` as a v85 feature that is separate from the "always enabled" deprecated/folded-in gates (`MIN_SUPPORTED_PROTOCOL_VERSION = 83`), meaning it is conditionally active depending on whether the live network's `PROTOCOL_VERSION` has reached 85. I could not verify from available context whether the currently deployed/base `PROTOCOL_VERSION` in this repo is ≥ 85 (i.e., whether the fix is unconditionally active today) — this would need to be confirmed against `core/primitives-core/src/version.rs`'s `PROTOCOL_VERSION` constant, which I was not able to fully inspect due to tool budget. If the live protocol version is already ≥ 85, this issue is fully mitigated and not exploitable; if it is exactly 83 or 84, the exploit path described by `try_meta_tx_deterministic_receiver_exploit` and asserted by `test_deterministic_state_init_meta_tx_receiver_check_pre_fix` would still be reachable by any transaction signer using a crafted meta-transaction.

### Recommendation
Confirm the live/base `PROTOCOL_VERSION` is ≥ the `FixDelegatedDeterministicStateInit` activation version (85). If not yet activated, prioritize enabling this feature, since it fixes exactly the "identifier used to derive/validate a target does not match the value actually referenced during execution" bug class described in the report. If it is already active, no further action is needed for this specific analog; the existing regression tests (`test_deterministic_state_init_meta_tx_receiver_check`, `test_deterministic_state_init_meta_tx_receiver_check_pre_fix`) should be retained to guard against protocol-version regressions.

### Proof of Concept
See `try_meta_tx_deterministic_receiver_exploit` in `test-loop-tests/src/tests/deterministic_account_id.rs:179-262`: it deploys two distinct deterministic accounts (`det_account_a`, `det_account_b`), grants `det_account_b` a full-access key, then crafts a `DelegateAction` with `sender_id = det_account_b`, `receiver_id = det_account_a`, but an inner `DeterministicStateInitAction` whose `state_init` derives to `det_account_b`. `test_deterministic_state_init_meta_tx_receiver_check_pre_fix` (lines 136-155) asserts that at `fix_version - 1` this tx passes initial validation and only fails later at `NewReceiptValidationError`/`InvalidDeterministicStateInitReceiver`, confirming the mismatch bypasses the earlier check pre-fix. /// Ensure there is no exploit with invalid deterministic account ids through
/// meta transactions.
///
/// With the old (buggy) code, `validate_delegate_action` used
/// `outer_tx.receiver_id` instead of `delegate_action.receiver_id` when
/// checking inner actions. The exploit tx therefore passes initial tx
/// validation. The exploit is prevented by a following `validate_receipt` check
/// when the meta transaction is unpacked.
#[test]
fn test_deterministic_state_init_meta_tx_receiver_check_pre_fix() {
    let fix_version = ProtocolFeature::FixDelegatedDeterministicStateInit.protocol_version();
    let outcome = try_meta_tx_deterministic_receiver_exploit(fix_version - 1)
        .expect("without the fix, exploit tx passes initial tx validation");

    assert_matches!(
        outcome.status,
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
            kind: ActionErrorKind::NewReceiptValidationError(
                ReceiptValidationError::ActionsValidation(
                    ActionsValidationError::InvalidDeterministicStateInitReceiver { .. }
                )
            ),
            ..
        })),
        "expected InvalidDeterministicStateInitReceiver in NewReceiptValidationError, got: {:?}",
        outcome.status
    );
}

/// With `FixDelegatedDeterministicStateInit` in place, the exploit should
/// already be caught at the first tx validation.
#[test]
fn test_deterministic_state_init_meta_tx_receiver_check() {
    let fix_version = ProtocolFeature::FixDelegatedDeterministicStateInit.protocol_version();
    let err = try_meta_tx_deterministic_receiver_exploit(fix_version)
        .expect_err("exploit tx must be rejected at tx validation with the fix");
    assert_matches!(
        err,
        InvalidTxError::ActionsValidation(
            ActionsValidationError::InvalidDeterministicStateInitReceiver { .. }
        ),
        "wrong error: {err:?}"
    );
}

fn try_meta_tx_deterministic_receiver_exploit(
    protocol_version: ProtocolVersion,
) -> Result<FinalExecutionOutcomeView, InvalidTxError> {
    let mut env = TestEnv::setup_with_version(Balance::from_near(100), protocol_version);
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let (_state_init_a, det_account_a) = env.new_deterministic_account_with_data(small());
    let (state_init_b, det_account_b) = env.new_deterministic_account_with_data(big());
    assert_ne!(det_account_a, det_account_b);

    // Deploy det_account_b and add a full-access key so it can act as meta_tx_sender.
    let user_signer = create_user_test_signer(&env.user_account());
    let storage_balance = env.balance_for_storage(state_init_b.clone());
    let deploy_tx = SignedTransaction::deterministic_state_init(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        env.get_tx_block_hash(),
        state_init_b.clone(),
        storage_balance,
    );
    env.run_tx(deploy_tx);

    let meta_tx_sender_signer = create_user_test_signer(&det_account_b);
    let pk_base64 = near_primitives_core::serialize::to_base64(
        &borsh::to_vec(&meta_tx_sender_signer.public_key()).unwrap(),
    );
    let add_key_args = serde_json::json!([
        { "batch_create": { "account_id": det_account_b.as_str() }, "id": 0 },
        {
            "action_add_key_with_full_access": {
                "promise_index": 0,
                "public_key": pk_base64,
                "nonce": 0
            },
            "id": 0,
            "return": true
        }
    ]);
    let add_key_tx = SignedTransaction::call(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        Balance::from_near(2),
        "call_promise".to_owned(),
        serde_json::to_vec(&add_key_args).unwrap(),
        Gas::from_teragas(300),
        env.get_tx_block_hash(),
    );
    env.run_tx(add_key_tx);

    // Craft the exploit: outer_tx.receiver = det_account_b = derive(state_init_b).
    // Old check: det_account_b == derive(state_init_b) passes.
    // The delegate action targets det_account_a, which is the wrong account.
    // In no protocol version can this ever be allowed to be executed successfully.
    let relayer = env.independent_account();
    let relayer_signer = create_user_test_signer(&relayer);
    let inner_action = Action::DeterministicStateInit(Box::new(DeterministicStateInitAction {
        state_init: state_init_b,
        deposit: Balance::ZERO,
    }));
    let delegate_nonce = env.next_nonce_for(&det_account_b);
    let delegate_action = DelegateAction {
        sender_id: det_account_b.clone(),
        receiver_id: det_account_a,
        actions: vec![NonDelegateAction::try_from(inner_action).unwrap()],
        nonce: delegate_nonce,
        max_block_height: 1_000_000,
        public_key: meta_tx_sender_signer.public_key(),
    };
    let signed_delegate_action =
        SignedDelegateAction::sign(&meta_tx_sender_signer, delegate_action);
    let tx = SignedTransaction::from_actions(
        env.next_nonce(),
        relayer,
        det_account_b,
        &relayer_signer,
        vec![Action::Delegate(Box::new(signed_delegate_action))],
        env.get_tx_block_hash(),
    );
    env.try_execute_tx(tx)
}
