### Title
`remove_deposits` strips reverted deposits from the FIFO mempool with no re-add path - ([File: crates/sequencer/src/runner.rs])

### Summary
`produce_l2_block_inner` calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the full, unfiltered `deposit_data` fetched at the start of block production, not the subset of deposits whose `SystemEvent::BridgeDeposit` transaction actually succeeded and was included in the block. `process_sys_txs` explicitly reverts and `continue`s (skipping inclusion in `all_txs`) for any deposit whose EVM tx fails with `EvmSystemTransactionNotSuccessful`, but the caller in `produce_l2_block_inner` never intersects `deposit_data` with the successfully-applied set before removal.

### Finding Description
The binding that must hold: `deposit ∈ deposits_removed_from_mempool ⟺ deposit's BridgeDeposit tx ∈ all_txs (successfully applied to L2 block)`.

Trace:
- `fetch_deposits` returns the FIFO deposits without removing them [1](#0-0) .
- `produce_l2_block_inner` fetches `deposit_data` and passes it through `dry_run_transactions` → `produce_and_run_system_transactions` → `process_sys_txs` [2](#0-1) .
- In `process_sys_txs`, each deposit is applied inside a checkpointed working set; if it fails with `EvmSystemTransactionNotSuccessful` the working set is reverted and the loop `continue`s without pushing the tx into `all_txs` — i.e., the deposit is silently dropped from the block [3](#0-2) .
- Critically, `all_txs` (the filtered, successfully-applied set) is never propagated back to gate what gets removed from the deposit mempool. Instead, after the block is committed, `produce_l2_block_inner` unconditionally calls `remove_deposits(&deposit_data)` using the original, full `deposit_data` list fetched before any success/failure was known [4](#0-3) .
- `remove_deposits` has no concept of success/failure — it simply strips any deposit whose txid matches the input list from `accepted_deposit_txs` and `pending_deposits`, and there is no compensating re-add call anywhere in the runner [5](#0-4) .

So if D2's `BridgeDeposit` system tx reverts in-block (for any state-dependent reason that differs between the `eth_call` simulation time and actual sequential-in-block execution time — e.g., contract-level state consumed by D1 first), D2 is dropped from `all_txs` but is still present in the `deposit_data` vector used for `remove_deposits`, so it gets permanently evicted from the mempool with no way to re-submit (since `add_deposit_tx` derives the dedup key from the deposit's Bitcoin `moveTx` fields, and the depositor has no mechanism to force re-inclusion once evicted; nothing marks it in the mempool for retry).

This holds independent of whether the specific Solidity `deposit()` function in the current `Bridge.sol` has a "shared counter" that one deposit consumes affecting another distinct, valid deposit — the important root cause is architectural: the sequencer code path unconditionally removes *all* fetched deposits after block production, regardless of which ones were actually applied.

### Impact Explanation
This is a mempool bookkeeping bug in a component that is fully within the unprivileged attacker's request surface (`citrea_sendRawDepositTransaction` is called by anyone, including Clementine's aggregator, but nothing prevents any party from calling it), and it can also be triggered by legitimate deposit flows without any malice — a deposit that passes the pre-submission `eth_call` simulation could still revert during actual block application for reasons other than a contract-level ordering conflict (e.g., non-deterministic-relative-to-simulation-time state such as `whenNotPaused`, gas dynamics, or future contract logic with shared mutable state). Regardless of the exact revert trigger, once a fetched deposit's system tx reverts during `process_sys_txs`, it is (a) dropped from the produced block and (b) removed from the mempool anyway, with no re-add. The underlying Clementine-presigned Bitcoin move-to-vault UTXO exists, but its Citrea-side crediting is permanently lost from the sequencer's queue — this breaks the binding "cBTC credited by a SYSTEM_SIGNER Bridge deposit == exactly one Bitcoin move-to-vault output Clementine presigned, counted once," in the direction of under-crediting (a legitimate deposit never gets credited and can never be resubmitted through this mempool). This matches the Critical impact category ("funds permanently frozen" / a Bitcoin-side deposit that should have minted cBTC but never does).

### Likelihood Explanation
No special privilege is needed to trigger the removal bug itself — any scenario where a queued deposit's system tx reverts during actual application (as opposed to when it was validated via `eth_call` against pending state) reproduces it, and `process_sys_txs`'s revert-and-continue branch is explicitly written to handle "deposits to non-EOA addresses can revert," proving reverts during block application are an anticipated, non-rare occurrence, not a theoretical edge case. Whether an *attacker* can deliberately engineer two deposits whose simulate-time success diverges from apply-time success depends on Bridge.sol's actual state dependencies between distinct deposits, which is uncertain from what was inspected (Bridge.sol's `deposit()` uses `processedTxIds[txId]` keyed uniquely per Bitcoin tx, so two distinct legitimate deposits don't obviously share mutable state that only one can pass) — I could not confirm a concrete Solidity-level mechanism for the specific "D1 consumes shared allowance/counter causing D2 to revert" premise within the time available. However, the mempool-side removal bug is unconditional and file-verifiable, so even the non-adversarial trigger case (any deposit failing in `process_sys_txs` for an unrelated reason, e.g. a receiver contract rejecting funds) is enough to permanently evict a still-real, still-pending deposit from the sequencer's bookkeeping.

### Recommendation
Track which deposits' system transactions actually succeeded and were included in `all_txs` inside `process_sys_txs`/`produce_and_run_system_transactions`, return that successful subset back to `produce_l2_block_inner`, and call `remove_deposits` only with that subset instead of the full `deposit_data` fetched at the start of the block. Deposits whose system tx reverted should remain in the FIFO mempool (or be explicitly re-queued) so they can be retried in a later block.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
