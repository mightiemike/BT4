### Title
Signature verification is fully performed (and can require dozens of ECDSA recoveries) before any bandwidth/energy/fee is charged, allowing free CPU-cost DoS on invalid multi-sig transactions - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`, `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
The Trail-of-Bits finding on Arbitrum Stylus describes a class of bug where an expensive, arbitrarily-triggerable operation (Brotli decompression during WASM activation) is performed *before* gas is charged, so a crafted input that makes the operation fail lets the attacker walk away without paying for the work. The equivalent pattern in java-tron's transaction-processing pipeline is signature verification: `Manager.processTransaction()` performs full transaction/permission signature verification (`TransactionCapsule.validateSignature` → `validatePubSignature` → ECDSA recovery, potentially over multiple signatures for multi-sig accounts) strictly *before* `consumeBandwidth`/`consumeMultiSignFee`/`consumeMemoFee` are invoked. If verification fails, a `ValidateSignatureException` is thrown and the transaction is rejected with zero bandwidth, energy, or fee ever charged for the CPU work already performed.

### Finding Description
In `Manager.processTransaction`, the ordering is: [1](#0-0) 

`validateTapos`, `validateCommon`, and `validateDup` are cheap. `trxCap.validateSignature(...)` is the expensive step — it performs ECDSA public-key recovery for every signature attached to the transaction (up to `dynamicPropertiesStore.getTotalSignNum()`, which is a chain parameter, not hardcoded to 1) via `validatePubSignature`: [2](#0-1) 

Only *after* this signature validation succeeds does the code proceed to `consumeBandwidth(trxCap, trace)`, `consumeMultiSignFee(trxCap, trace)`, and `consumeMemoFee(trxCap, trace)`: [3](#0-2) 

If any signature in the set fails to recover to a permissioned address (i.e. `validateSignature` returns false / throws), the entire flow exits with `ValidateSignatureException` and none of the resource-consumption methods (`consumeBandwidth`, `consumeMultiSignFee`, `consumeMemoFee`) is ever reached — no bandwidth points, no energy, and no TRX fee are deducted, even though the node already paid the full CPU cost of the invalid ECDSA recoveries. This mirrors the WASM report's root cause exactly: an expensive, attacker-controlled operation is executed to completion (or to failure) *before* the pricing/charging step, so a crafted failing input is free for the attacker.

This is also reachable via `pushTransaction` (mempool ingestion), which calls `trx.validateSignature(...)` directly before any resource accounting or block inclusion: [4](#0-3) 

### Impact Explanation
An attacker can construct transactions carrying the maximum allowed number of signatures (bounded by `getTotalSignNum()`, a governance-adjustable dynamic property) where the signatures are syntactically valid (correct length/format) but do not recover to an authorized permission key. Each such transaction forces full-cost ECDSA signature recovery for every attached signature, consuming witness/full-node CPU, yet is rejected with `ValidateSignatureException` before any bandwidth, energy, or TRX fee is deducted from any account. Submitted at volume (via `pushTransaction`/mempool spam or included as part of blocks with many failing multi-sig transactions), this allows an attacker to impose real, unpriced CPU cost on network nodes — a denial-of-service vector functionally identical to the "underpriced public work" class flagged in the WASM activation report.

### Likelihood Explanation
The path is reachable by any unprivileged user submitting ordinary transactions; it requires no special privileges, no on-chain state manipulation, and no contract deployment. The only constraints are the network's own limits on signature count (`getTotalSignNum()`) and transaction size/mempool rate limiting, which are DoS mitigations rather than pricing fixes — they do not charge the attacker for the CPU already spent. Because signature crafting (garbage bytes shaped as valid-length ECDSA signatures) is trivial and cheap for the attacker, and the expensive recovery step unconditionally executes before any charge, the likelihood of practical exploitation (bounded by whatever throughput the mempool/signature count caps allow) is realistic, though the overall severity is capped by these existing caps.

### Recommendation
- **Short term:** Reorder or restructure the transaction pipeline so that some minimal resource charge (e.g., bandwidth/fee based on transaction/signature byte size) is reserved or deducted *before* performing ECDSA signature recovery, mirroring the "charge gas as early as possible, even on failure" recommendation from the original report. Alternatively, charge a per-signature-recovery-attempt cost from the sender's account (if resolvable) prior to invoking `validatePubSignature`/`checkWeight`.
- **Long term:** Audit all other computationally expensive, user-triggerable operations that execute prior to fee/resource accounting throughout `Manager.processTransaction`, `pushTransaction`, and actuator `validate()` methods (e.g., large multi-sig `checkWeight` loops, ABI/permission parsing) to ensure CPU cost is always bounded by an already-charged or size-based cost, not contingent on eventual success.

### Proof of Concept
Conceptual PoC (cannot be executed in this read-only environment):
1. Set/observe `getTotalSignNum()` (e.g., default network value, commonly configured up to ~5-20).
2. Build a `TransferContract` transaction from an account with a single-key permission (`threshold = 1`).
3. Append `N = getTotalSignNum()` syntactically valid but incorrect 65-byte signatures (random `r,s,v` bytes that pass basic format checks but do not recover to the owner's address).
4. Submit repeatedly via `Wallet.broadcastTransaction` → `Manager.pushTransaction` → `trx.validateSignature(...)`.
5. Observe: each submission forces `N` full ECDSA public-key recoveries (`SignUtils`/`ECKey.signatureToAddress`) inside `validatePubSignature`/`checkWeight` before the code reaches `consumeBandwidth`/`consumeMultiSignFee`; the transaction is rejected with `ValidateSignatureException` and zero balance/bandwidth is deducted from any account, confirming the CPU cost was incurred for free.   /**
   * validate signature
   */
  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }
