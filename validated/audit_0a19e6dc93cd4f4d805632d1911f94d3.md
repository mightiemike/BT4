## Analog Found

### Title
FunctionCall access key allowance cap is silently bypassed when the key signs a meta-transaction (`Delegate`/`DelegateV2` action) - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEAR's `FunctionCallPermission` allows an account owner to grant a scoped access key that can only call a specific `receiver_id`/`method_names` and whose spending is capped by an `allowance: Option<Balance>` [1](#0-0) . This allowance is meant to bound how much of the account's balance that specific key can ever consume for gas/fees [2](#0-1) . When the same key is used to sign a meta-transaction (`Delegate`/`DelegateV2`) instead of a direct transaction, the runtime's delegate-action handler validates `receiver_id`, `method_names`, and rejects non-zero deposits, but never calls the allowance-checking logic, so the cap is never enforced on that path.

### Finding Description
For a direct transaction, `verify_and_charge_tx_ephemeral` enforces the allowance via `check_and_compute_new_allowance`, failing with `NotEnoughAllowance` when the key's balance cap is exceeded [3](#0-2) .

For a meta-transaction, the inner action is unwrapped and validated in `apply_delegate_action` (`runtime/runtime/src/actions.rs`). That function checks `RequiresFullAccess`, `DepositWithFunctionCall`, `ReceiverMismatch`, and `MethodNameMismatch` for a `FunctionCall`-permissioned key [4](#0-3) , but at no point calls `check_and_compute_new_allowance` or otherwise consults `FunctionCallPermission.allowance`. A repo-wide search confirms `check_and_compute_new_allowance`/`NotEnoughAllowance` only appear in `runtime/runtime/src/verifier.rs` (the direct-tx path) — never in `actions.rs`'s delegate-action handling.

This is explicitly acknowledged in the project's own architecture documentation: "For allowance, however, there is no check. All costs have been covered by the relayer. Hence, even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work." [5](#0-4) 

This mirrors the reported Morpho-Aave bug class precisely: a protective constraint (turning off collateral / capping a key's allowance) is enforced on one execution path (direct Aave liquidation checks / direct transaction verification) but is not propagated to a second, related execution path built on the same underlying primitive (Morpho's repay-and-withdraw liquidation / NEAR's meta-transaction delegate-action execution), silently defeating the control.

### Impact Explanation
`FunctionCallPermission.allowance` is a documented security control: dapps and wallets issue small-allowance function-call keys specifically to bound the "blast radius" if such a key is exposed (e.g., embedded in a browser session, a game client, or a third-party integration) — the owner's expectation is that even a fully leaked key cannot spend more than the configured allowance. Because the allowance is never checked in the `Delegate`/`DelegateV2` path, any holder of such a key (the legitimate app, or an attacker who obtains the key) can pair it with any relayer (including themselves acting as their own relayer) to invoke the permitted method an unbounded number of times, with the relayer footing the gas bill instead of the allowance. If the receiver contract exposes state-changing methods that move value based on caller identity/method-permission rather than per-call cost (e.g., repeated `claim`, `transfer`, `withdraw`, `vote`, or governance-adjacent calls gated only by "this key may call this method"), the intended allowance-based rate/spend limit that the account owner relied on as a safety boundary is completely circumvented, enabling unauthorized value movement or actions far beyond what the owner authorized when minting the key.

### Likelihood Explanation
This requires no protocol-level attacker: any account holder can trivially test it by wrapping a limited-allowance `FunctionCall` transaction inside a self-relayed `SignedDelegateAction`, which is a standard, fully-supported feature (meta-transactions, NEP-366) reachable by any transaction signer via ordinary RPC submission. No node compromise, validator collusion, or network-layer capability is needed — it is purely a client-submitted transaction/receipt path issue in `runtime/runtime/src/actions.rs`.

### Recommendation
Enforce the `FunctionCallPermission.allowance` cap inside `apply_delegate_action` for inner `FunctionCall` actions signed by a `FunctionCall`-permissioned key, mirroring `check_and_compute_new_allowance` used in the direct-transaction path (`runtime/runtime/src/verifier.rs`). Alternatively, explicitly document (and gate behind a protocol feature so behavior is consensus-consistent) that allowance is not a meaningful spend-limit for meta-transactions, and steer application developers away from relying on it as a security boundary against relayer-assisted replay/abuse.

### Proof of Concept
1. Account `A` adds a `FunctionCall` access key `K` with `allowance = 1` yoctoNEAR (effectively disabling direct use since it can't cover any gas), `receiver_id = "app.near"`, `method_names = ["claim"]`.
2. A direct transaction signed by `K` calling `app.near::claim()` fails at verification with `InvalidTxError::NotEnoughAllowance` per `verify_and_charge_tx_ephemeral` [3](#0-2) .
3. The same call, wrapped in a `SignedDelegateAction` signed by `K` and relayed by any account `R` (including `A` itself), reaches `apply_delegate_action`, which validates receiver/method/deposit only [4](#0-3)  and never rejects for insufficient allowance — the call to `app.near::claim()` succeeds, with `R` paying gas, repeatable without limit.
