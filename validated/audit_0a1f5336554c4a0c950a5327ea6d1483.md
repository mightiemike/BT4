### Title
Missing negative-value check in `extractDestGasAmountFromMap` allows uint32 wraparound of `DestGasAmount` - ([File: core/capabilities/ccip/ccipsolana/executecodec.go])

### Summary
`extractDestGasAmountFromMap` only rejects `int64` values greater than `math.MaxUint32`, but never checks for negative values before casting to `uint32`. A negative `int64` (e.g. `-1`) silently wraps to a large positive `uint32` (e.g. `4294967295`) via Go's two's-complement conversion, instead of being rejected as invalid.

### Finding Description
In `core/capabilities/ccip/ccipsolana/executecodec.go`, `extractDestGasAmountFromMap` handles the `int64` case as follows: [1](#0-0) 

The only bound check is `v > math.MaxUint32`. For a negative `v` (e.g. `-1`), this condition is `false` since `-1` is not greater than `4294967295`, so execution falls through to `return uint32(v), nil`, silently wrapping `-1` into `4294967295`. This value flows directly into `ccip_offramp.Any2SVMTokenTransfer.DestGasAmount` via `Encode`: [2](#0-1) 

and also feeds `CalculateMessageMaxGasWithError`'s gas-overhead accumulation: [3](#0-2) 

The `int64` branch exists to accommodate values that pass through the gRPC-compatible `ExtraDataCodecBundle`/`ExtraDataCodecRegistry` interface, where the map value type may not be preserved as `uint32` through cross-process (de)serialization boundaries: [4](#0-3) 
So while the concrete per-chain decoders (EVM's `abiDecodeUint32`, Solana's `binary.BigEndian.Uint32`, Aptos's BCS `U32`) return unsigned `uint32` values directly, the generic map value can be re-typed to `int64` once it crosses this interface boundary, making the `int64` branch of `extractDestGasAmountFromMap` a reachable code path, not dead code.

### Impact Explanation
A negative `int64` value in the decoded `DestExecData` map bypasses the intended overflow guard and silently wraps into a near-maximum `uint32` (`4294967295` for `-1`). This is used directly as `Any2SVMTokenTransfer.DestGasAmount` for on-chain Solana offramp execution and is summed into `CalculateMessageMaxGasWithError`'s total gas estimate, producing an incorrect and inflated gas budget rather than a clean rejection. This matches the "unsafe transaction submission with incorrect gas budgeting" impact described in the question, though it is a silent-wraparound defect rather than a truncation-toward-zero issue.

### Likelihood Explanation
The bug requires that `extractDestGasAmountFromMap` receive an `int64`-typed value for `destgasamount`, which is only possible when the value crosses the gRPC/type-erased `ExtraDataCodecBundle` boundary; the built-in per-chain decoders (`ccipevm`, `ccipsolana`, `ccipaptos`, `ccipsui`) always produce `uint32` directly and would hit the `case uint32` branch instead. There is no evidence in the reviewed code that an ordinary unprivileged sender can force this exact `int64` typing through the raw `DestExecData` bytes for these codecs — the type transformation is a property of the marshaling layer, not directly attacker-selectable from message bytes. This significantly limits practical exploitability from a plain source-chain message; it is a real logic gap in the validation function, but confirming full end-to-end reachability from unprivileged input would require additional tracing of the gRPC/plugin marshaling code that is not present in the indexed files.

### Recommendation
Add an explicit negative-value check to the `int64` branch of `extractDestGasAmountFromMap`, e.g.:
```go
case int64:
    if v < 0 || v > math.MaxUint32 {
        return 0, fmt.Errorf("destGasAmount out of uint32 range, got %d", v)
    }
    return uint32(v), nil
```
Apply the same fix to any other copies of this function (`ccipevm`, `ccipaptos`, `ccipsui` variants) if they share the same pattern.

### Proof of Concept
Add a unit test in `core/capabilities/ccip/ccipsolana/executecodec_test.go` (or a new `extractDestGasAmountFromMap` test):
```go
func TestExtractDestGasAmountFromMap_NegativeInt64(t *testing.T) {

    _, err := extractDestGasAmountFromMap(m)

}

func TestExtractDestGasAmountFromMap_MaxUint32PlusOne(t *testing.T) {

    require.Error(t, err) // currently passes
}

func TestExtractDestGasAmountFromMap_MaxUint32(t *testing.T) {

    require.Equal(t, uint32(math.MaxUint32), v)
}
```
Expected: the negative-value test currently fails (no error, silent wraparound to `4294967295`), demonstrating the missing bounds check; after applying the recommended fix, all three assertions pass.
