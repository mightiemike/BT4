### Title
Missing `supportUnfreezeDelay` Gate in `UnfreezeBalanceActuator` Allows Legacy Unfreeze After FreezeV2 Migration - ([File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java])

### Summary
`FreezeBalanceActuator` and `UnfreezeBalanceActuator` form a paired "deposit/withdraw"-style state machine for TRON's legacy freeze mechanism (locking TRX for bandwidth/energy/TRON_POWER and later reclaiming it). When the committee enables FreezeV2 (`supportUnfreezeDelay()` returns true), `FreezeBalanceActuator.validate()` explicitly rejects any new legacy freeze transaction with `"freeze v2 is open, old freeze is closed"` [1](#0-0) . However, the paired reverse operation, `UnfreezeBalanceActuator`, never checks `supportUnfreezeDelay()` in its `validate()`/`execute()` path, as confirmed by the fact that a repository-wide search for `supportUnfreezeDelay` returns no hits in `UnfreezeBalanceActuator.java`, while it is present in `FreezeBalanceActuator.java`, `FreezeBalanceV2Actuator.java`, `UnfreezeBalanceV2Actuator.java`, and `WithdrawExpireUnfreezeActuator.java`. This is the same class of bug as the report: the "deposit" side (`FreezeBalanceActuator`) enforces the pause/migration gate, but the "withdraw" side (`UnfreezeBalanceActuator`) does not.

### Finding Description
`FreezeBalanceActuator` locks this behavior down once FreezeV2 is active: it refuses to accept `FreezeBalanceContract` transactions [1](#0-0) . This is designed as a hard cut-over: legacy freeze/unfreeze accounting (`Frozen` list, `AccountResource.getFrozenBalanceForEnergy()`, `TronPowerFrozen`) is meant to be retired in favor of the V2 model (`FreezeBalanceV2Actuator`, which itself gates on `supportUnfreezeDelay()` in the opposite direction, requiring the flag to be `true`) [2](#0-1) .

`UnfreezeBalanceActuator`, which performs the corresponding legacy unfreeze/withdraw of previously-frozen balances and directly mutates `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` and account balances [3](#0-2) , contains no equivalent gate. Its `execute()` unconditionally calls `mortgageService.withdrawReward(ownerAddress)` and processes legacy frozen balances regardless of whether the chain has already switched to FreezeV2 [4](#0-3) . This asymmetry mirrors the reported Move `gateway.move` bug exactly: one side of a paired flow enforces a state-transition gate while the mirrored side does not.

### Impact Explanation
After the network migrates to FreezeV2 (a one-way, committee-controlled switch intended to fully retire the old freeze bookkeeping), any account still holding legacy frozen balances or delegated legacy resources can continue to broadcast `UnfreezeBalanceContract` transactions. This keeps mutating `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` and delegated-resource indices through code paths that were supposed to be frozen off, alongside the V2 accounting paths that are now the source of truth. This is a resource/reward accounting corruption risk: total weight adjustments computed under the legacy path (`dynamicStore.allowNewReward() ? decrease : -unfreezeBalance / TRX_PRECISION`) can diverge from what the V2-only design assumes, since the deposit (freeze) side is fully closed off but the withdraw (unfreeze) side is not, creating an inconsistent, one-directional state that is reachable by any ordinary account via a normal broadcast transaction — no privileged role is required.

### Likelihood Explanation
High reachability: any account that froze balance under the legacy `FreezeBalanceContract` before FreezeV2 activation retains the ability to submit `UnfreezeBalanceContract` transactions indefinitely afterward, since `UnfreezeBalanceActuator` performs no `supportUnfreezeDelay()` check comparable to its sibling `FreezeBalanceActuator`. This requires no special permission — it is a standard user-signed transaction accepted by the normal broadcast/actuator pipeline.

### Recommendation
Add the same state-transition gate used in `FreezeBalanceActuator` to `UnfreezeBalanceActuator.validate()` (and/or clarify intended behavior): if `dynamicStore.supportUnfreezeDelay()` is true, either reject new legacy `UnfreezeBalanceContract` transactions consistently with the freeze-side gate, or, if legacy unfreeze must remain available strictly to let existing frozen balances be reclaimed, ensure that this asymmetry is deliberate and does not silently continue mutating global weight totals in ways inconsistent with the V2 accounting model. The two actuators' pause/migration semantics should be made explicitly symmetric and documented.

### Proof of Concept
Not applicable — the analog is derived from static comparison of `FreezeBalanceActuator.validate()` (which contains the `supportUnfreezeDelay()` gate) versus `UnfreezeBalanceActuator` (which does not), both cited above; no dynamic PoC was constructed.
