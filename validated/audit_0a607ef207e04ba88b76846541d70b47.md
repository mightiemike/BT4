### Title
Unchecked double-precision Bancor math in TRC10 `ExchangeTransactionContract` allows an unprivileged trader to drain an exchange pool's reserves - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The Arrakis H-3 finding shows that a pool's reserve-dependent share-pricing math can be exploited to mint/receive assets worth far more than what was deposited, because the code path that updates reserves lacks a check that the resulting reserves stay non-negative/consistent. Java-tron's TRC10 `Exchange` (a bonding-curve AMM built into the protocol) has the same missing-invariant pattern in its default execution path: `ExchangeCapsule.transaction()` only validates that post-trade reserves are non-negative when `hardenedCalc` is `true`, and `hardenedCalc` is derived from the `allowHardenExchangeCalculation` dynamic property, which defaults to disabled. In the default (non-hardened) path, the trade amount is computed via the double-precision `ExchangeProcessor` (`Math.pow`/floating point) with no bound relating the computed `buyTokenQuant` to the actual `buyTokenBalance`, and no post-trade sanity check.

### Finding Description
`ExchangeTransactionActuator` is reachable by any account holding the traded asset via a broadcast `ExchangeTransactionContract` transaction — there is no creator/owner restriction (unlike `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, which do check `!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`). [1](#0-0) 

The trade output is computed by `ExchangeCapsule.transaction()`, which by default (`hardenedCalc == false`) uses `ExchangeProcessor`, a Bancor-formula implementation built entirely on `double`/`Math.pow` arithmetic, and only performs the "reserves must stay ≥ 0" check when `hardenedCalc` is true: [2](#0-1) 

`ExchangeProcessor.exchange()` derives the output purely from double-precision `Math.pow` computations over the current reserves, with no explicit clamp ensuring `buyTokenQuant <= buyTokenBalance`: [3](#0-2) 

Whether the safety check is active is gated by `allowHarden()`, which reads the `allowHardenExchangeCalculation` dynamic property — a value the tests explicitly enable with `saveAllowHardenExchangeCalculation(1)` and reset to `0` afterward, confirming it is off by default: [4](#0-3) 

The project's own regression tests demonstrate the exact failure mode this analog concerns: with `hardenedCalc` disabled (the default), a corrupted/extreme reserve ratio (e.g., a huge first-token balance vs. a tiny second-token balance) is not caught before an overflow/negative-balance state is reached; the guard is only exercised when hardened mode is explicitly turned on: [5](#0-4) 

This mirrors the Arrakis root cause precisely: a reserve-dependent pricing formula is executed and its output is applied to update reserves/mint value without validating that the resulting state respects the pool's actual balances, letting an unprivileged caller extract value disproportionate to what they deposited.

### Impact Explanation
An attacker who identifies an `Exchange` pool with a skewed reserve ratio (which can itself be engineered over multiple unprivileged `ExchangeTransactionContract` calls, since each trade shifts the ratio and no invariant check exists in the default path) can submit a trade whose double-precision computed `buyTokenQuant` exceeds the true `secondTokenBalance`/`firstTokenBalance`. Because the non-hardened branch never validates `newFirstTokenBalance`/`newSecondTokenBalance >= 0`, the actuator will still credit the attacker's account via `addAssetAmountV2`/`setBalance` with more tokens than the pool actually holds, corrupting the exchange's on-chain balance bookkeeping (`ExchangeCapsule`) and draining pool reserves — an asset/accounting corruption impact directly analogous to the Arrakis vault drain.

### Likelihood Explanation
Reachable by any account via a standard, unprivileged broadcast transaction (`ExchangeTransactionContract`) — no special role, key, or peer trust is required, satisfying the "unprivileged/RPC-reachable" requirement. Exploitability depends on finding or engineering a reserve ratio and trade size where the double-precision Bancor computation diverges enough from the exact/integer expectation to exceed the actual reserve; the codebase's own hardened-mode tests (`SafeExchangeProcessor`, `StrictMathWrapper`) were added specifically to guard against overflow/precision issues in this exact code path, which is corroborating evidence that the underlying computation is fragile in the default configuration.

### Recommendation
Enable and enforce the non-negative-reserve invariant unconditionally in `ExchangeCapsule.transaction()` regardless of the `allowHardenExchangeCalculation` flag (i.e., make the hardened check mandatory rather than proposal-gated), and/or switch the default trade computation to the exact `BigDecimal`-based `SafeExchangeProcessor` rather than the floating-point `ExchangeProcessor`. Additionally, clamp `buyTokenQuant` to never exceed the actual opposing reserve before applying balance updates in `ExchangeTransactionActuator.execute()`.

### Proof of Concept
Not independently reproducible from the indexed code alone (would require constructing/using an on-chain `Exchange` with a specific skewed reserve ratio and issuing a crafted `ExchangeTransactionContract`); however, the repository's own test `hardenedExecuteOverflowThrowsArithmeticException` demonstrates that a corrupted/extreme-ratio pool combined with the default (non-hardened) path bypasses the reserve-consistency guard, which is the exact precondition needed for this analog: [6](#0-5)

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

    pool.setBalance(Long.MAX_VALUE - 5L, 10_000_000L);
    dbManager.getExchangeV2Store().put(pool.createDbKey(), pool);
