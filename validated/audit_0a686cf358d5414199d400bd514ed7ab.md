### Title
Exchange pool balance overflow via `ExchangeCapsule.transaction`'s non-hardened arithmetic when `allowHardenExchangeCalculation` is disabled (default) - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
When `allowHardenExchangeCalculation` is at its default value of `0`, both `ExchangeTransactionActuator.doValidate()`'s balance-limit check and `ExchangeCapsule.transaction()`'s pool-balance update use plain `+`/`-` arithmetic instead of `StrictMathWrapper`, and the resulting negative/overflow-guard (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) is only evaluated `if (hardenedCalc)`. An unprivileged attacker who issues a token with a near-`Long.MAX_VALUE` supply, creates/uses an exchange pool for it, and sells a crafted near-`Long.MAX_VALUE` quantity can overflow the pool's `int64` balance fields, silently corrupting the exchange's persisted state.

### Finding Description
`ExchangeTransactionActuator.doValidate()` computes: [1](#0-0) 
using `addExact()` from `AbstractExchangeActuator`, which itself degrades to plain `x + y` when `allowHarden()` is false: [2](#0-1) 
`allowHarden()` returns `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()`, whose default value is `0` (disabled) unless a chain-wide proposal enables it: [3](#0-2) 

If `tokenBalance` (existing pool balance) is large and `tokenQuant` is crafted near `Long.MAX_VALUE`, the plain `+` wraps to a negative value, so `tokenBalance > balanceLimit` evaluates `false` and the balance-limit guard is silently bypassed.

The actual pool mutation happens in `ExchangeCapsule.transaction()`: [4](#0-3) 
Here, when `hardenedCalc` is `false` (the default), `newFirstTokenBalance`/`newSecondTokenBalance` are computed with plain `+`/`-` and the safety check `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) throw ...` is skipped entirely because it is gated on `hardenedCalc`. The overflowed/negative balances are then committed directly into the persisted `Exchange` protobuf via `setFirstTokenBalance`/`setSecondTokenBalance` with no further validation, and `ExchangeTransactionActuator.execute()` persists this capsule via `Commons.putExchangeCapsule(...)`.

The remaining pre-condition — the attacker needs to actually hold a near-`Long.MAX_VALUE` quantity of a token to pass `accountCapsule.assetBalanceEnoughV2(tokenID, tokenQuant, dynamicStore)` — is achievable because asset issuance (`AssetIssueContract.totalSupply`, an `int64` field) is an unprivileged, attacker-controlled action; an attacker can issue a token to themselves with supply near `Long.MAX_VALUE`, then create or use an exchange pool for it (`ExchangeCreateContract`), then broadcast `ExchangeTransactionContract` selling that near-max quantity.

The unit tests in the repo already demonstrate that only the *hardened* path is protected — `testHardenedTransactionNegativeBalanceThrows` and `hardenedExecuteOverflowThrowsArithmeticException` confirm `ArithmeticException`/`ContractValidateException` are thrown only when `allowHardenExchangeCalculation=1`: [5](#0-4) [6](#0-5) 
There is no equivalent test validating that the *non-hardened* (default) path safely rejects or clamps overflow — because it does not.

### Impact Explanation
A successful overflow corrupts the exchange pool's `firstTokenBalance`/`secondTokenBalance` (persisted `int64` fields) to negative or wrapped values, violating the internal accounting invariant that pool balances must stay consistent and non-negative. This breaks the AMM bonding-curve math for all subsequent trades against that exchange (since `ExchangeProcessor.exchange()` is fed corrupted balances), potentially enabling value creation/destruction in the exchange pool and denial-of-service/inconsistent-state for that exchange going forward. Impact is scoped to the affected exchange's pool and interacting accounts' asset/TRX balances.

### Likelihood Explanation
Requires `dynamicStore.allowHardenExchangeCalculation()` to be disabled, which is the on-chain default (`orElse(0L)`) unless a governance proposal has activated it. The attacker needs to be able to issue an asset with a large total supply and hold it (unprivileged, ordinary `AssetIssueContract` action) and craft an `ExchangeTransactionContract` with `quant` near `Long.MAX_VALUE`. This is fully reachable via standard broadcast transactions (`ExchangeCreate`/`AssetIssue` then `ExchangeTransaction`), with no special privilege required, making it a realistic, repeatable exploit on any network where the hardening proposal has not been activated.

### Recommendation
Remove the `hardenedCalc` gate on the negative-balance check in `ExchangeCapsule.transaction()` so the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` (and ideally overflow-detection via `Math.addExact`/`Math.subtractExact`) check is always enforced regardless of the `allowHardenExchangeCalculation` flag. Likewise, `AbstractExchangeActuator.addExact`/`subtractExact` used in `doValidate()`'s balance-limit check should always use overflow-checked arithmetic, independent of the governance-controlled hardening flag, since this is a core safety invariant rather than an optional consensus upgrade.

### Proof of Concept
Extend `ExchangeCapsuleTest` with a differential test showing the non-hardened path is unsafe:
```java
@Test
public void testNonHardenedOverflowNotDetected() throws Exception {
  ExchangeCapsule capsule = new ExchangeCapsule(
      ByteString.copyFromUtf8("owner"), 200L, 0L,
      "abc".getBytes(), "def".getBytes());
  // Large pre-existing balance
  capsule.setBalance(100_000_000L, 100_000_000L);

  long sellQuant = Long.MAX_VALUE - 50_000_000L; // near-max, attacker-controlled asset supply

  // Non-hardened (default) path: no overflow guard fires
  long buyQuant = capsule.transaction("abc".getBytes(), sellQuant, true, false);
  // Demonstrates silent wraparound: resulting balance is negative/corrupted
  // instead of throwing, unlike the hardened path.
  Assert.assertTrue("Non-hardened path silently produces corrupted (negative) balance",
      capsule.getFirstTokenBalance() < 0);

  // Contrast: hardened path on identical input throws instead of corrupting state
  ExchangeCapsule hardened = new ExchangeCapsule(
      ByteString.copyFromUtf8("owner"), 201L, 0L,
      "abc".getBytes(), "def".getBytes());
  hardened.setBalance(100_000_000L, 100_000_000L);
  Assert.assertThrows(ArithmeticException.class,
      () -> hardened.transaction("abc".getBytes(), sellQuant, true, true));
}
```
Expected assertion failure confirms the invariant violation: the non-hardened branch must either throw `ContractValidateException`/`ArithmeticException` or produce the same safe result as the hardened branch, but instead it silently persists a corrupted (negative) pool balance.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
