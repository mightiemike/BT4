## Analysis Result

### Title
Unbounded Recursive Bytecode-Segment Hashing on Attacker-Influenced Compiled Class Structure - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
The compiled-class hash computation recursively walks a nested bytecode-segment tree (`NestedIntList`) with no recursion-depth limit. The segment tree's shape is derived from the Sierra program's control-flow structure at compile time, so a class declarer who crafts a Sierra program with deeply nested function/branch structure can force an arbitrarily deep segment tree. This is analogous to CVE-2016-6131, where a demangler recursively walked an attacker-influenced nested/cyclic type structure with no depth bound, causing a stack overflow crash.

### Finding Description
`bytecode_hash_node` in [1](#0-0)  recurses once per level of the `NestedIntList` segment structure, with no maximum-depth guard: [1](#0-0) 

This function is invoked from `HashableCompiledClass::hash` → `hash_inner` → `bytecode_hash`, which is the standard code path used to compute a class's compiled-class hash: [2](#0-1) .

This hashing is triggered on the declare path in the Sierra compiler service, immediately after compiling an attacker-submitted class and *outside* the resource-limited compiler subprocess: [3](#0-2) 

The subprocess compile step itself does have CPU/memory resource limits: [4](#0-3) , but the hash computation that follows (`executable_class.hash(&HashVersion::V2)`) runs directly in the `SierraCompiler`/`ClassManager` process, unprotected by those subprocess limits: [5](#0-4) .

The segment tree (`bytecode_segment_lengths`) is produced by the external `cairo-lang-starknet-classes`/`cairo-lang-sierra-to-casm` compiler based on the Sierra program's function/branch nesting; a Sierra program with deep, non-optimizable nested branching can therefore produce an arbitrarily deep segment tree, up to limits imposed only by `max_bytecode_size` (bounded bytecode size, not tree depth): [6](#0-5) .

I was not able to fully confirm, within the scope of this investigation, the exact worst-case tree depth achievable relative to `max_bytecode_size`, nor whether the actual sequencer stack size (`RUST_MIN_STACK` set to 4 MiB for `native_blockifier`: [7](#0-6) ) is sufficient to absorb the worst-case recursion depth for a class near `max_bytecode_size`. This is a meaningful gap in the analysis; confirming it requires either running the actual `cairo-lang-sierra-to-casm` compiler against a crafted deeply-nested Sierra program to observe generated segment-tree depth, or reading the (external, not-indexed) segment-generation logic in `cairo-lang-sierra-to-casm`.

### Impact Explanation
If a crafted class can produce a sufficiently deep segment tree, the unbounded recursion in `bytecode_hash_node` could overflow the stack of the `SierraCompiler`/`ClassManager` process during `add_class`, crashing that component. Since this same hashing code path is reachable by any declarer submitting a class through the ordinary declare-transaction flow, a repeated crash on class re-processing (e.g., on restart/retry of the same malicious pending declare) could degrade or halt class declaration/compilation service availability network-wide — a potential "network unable to confirm new transactions" scenario for declare transactions specifically.

### Likelihood Explanation
Likelihood is uncertain and depends on details I could not verify: (1) whether the external Sierra-to-CASM compiler can actually be forced to emit a segment tree deep enough (relative to the enforced `max_bytecode_size`) to exceed the process stack size, and (2) whether any existing depth guard elsewhere in the pipeline (e.g., in `cairo-lang-sierra-to-casm` itself) already bounds segment nesting. Absent confirmation of these two points, this should be treated as a **plausible but unconfirmed** analog rather than a proven vulnerability.

### Recommendation
- Convert `bytecode_hash_node` (and its blake/poseidon Cairo counterparts if the OS-side execution has an analogous unbounded pattern) to an iterative, explicit-stack-based traversal, or enforce a hard maximum recursion/nesting depth consistent with `max_bytecode_size`, rejecting classes whose segment tree exceeds it.
- Ensure that all post-compilation processing of an untrusted class (including hash computation) is performed under the same resource isolation/limits as the Sierra→CASM compilation subprocess itself, not just the compiler invocation.

### Proof of Concept
Not verifiable within the scope of this investigation — reproducing the crash requires generating a Sierra program (via the external `cairo-lang-sierra-to-casm` compiler, whose segment-generation algorithm is not in this repo's index) with control-flow nesting deep enough to produce a segment tree whose depth exceeds the process stack capacity, and observing that `SierraCompiler::compile` or `HashableCompiledClass::hash` crashes rather than erroring gracefully. I could not confirm this end-to-end due to lack of access to run the external compiler and measure actual achievable segment-tree depth.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

/// Computes the compiled class hash for a given hashable class using the specified hash algorithm.
fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}

            Some(self.config.max_cpu_time),
            None,

            compiler_binary_path,
            contract_class,
            additional_args,
            resource_limits,
        )?;
