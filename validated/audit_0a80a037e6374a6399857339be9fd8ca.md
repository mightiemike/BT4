This confirms the vulnerability path. `DestExecData` is a message field that originates from the source chain reader/onramp state and flows unvalidated into `DecodeTokenAmountDestExecData`, which dispatches by chain family to `ccipsolana.ExtraDataDecoder.DecodeDestExecDataToMap`. That call site is reached from `msghasher.go` `Hash()` [1](#0-0) , `executecodec.go` `Encode()` [2](#0-1) , `gas_helpers.go` `CalculateMessageMaxGasWithError` [3](#0-2) , and the OCR `decodeExecData` used by `SVMExecCalldataFunc` in the contract transmitter [4](#0-3)  — all of these are core CCIP OCR commit/execute report processing paths where `DestExecData` bytes are attacker-influenced content coming from a Solana-sourced message's `TokenAmounts[].DestExecData`.

The sibling EVM decoder validates length via `abiDecodeUint32`/ABI unpacking and returns wrapped errors on short input, as demonstrated by the existing test asserting `"length insufficient 4 require 32"` [5](#0-4) , and the Aptos decoder enforces a `Remaining()!=4` check before decoding. The Solana `ExtraDataDecoder.DecodeDestExecDataToMap` has no such guard and calls `binary.BigEndian.Uint32(destExecData)` directly [6](#0-5) .

### Title
Unbounded-length `destExecData` causes panic in `ExtraDataDecoder.DecodeDestExecDataToMap` - (File: core/capabilities/ccip/ccipsolana/extradatacodec.go)

### Summary
`ccipsolana.ExtraDataDecoder.DecodeDestExecDataToMap` calls `binary.BigEndian.Uint32(destExecData)` without checking `len(destExecData) >= 4`, unlike the EVM (`abiDecodeUint32`) and Aptos (`des.Remaining()!=4`) implementations of the same interface method, which return errors for malformed input. A `destExecData` byte slice shorter than 4 bytes causes an unrecovered index-out-of-range panic.

### Finding Description
`SourceChainExtraDataCodec.DecodeDestExecDataToMap` is called via `ExtraDataCodecMap.DecodeTokenAmountDestExecData` [7](#0-6) , dispatching by `SourceChainSelector`'s chain family to the Solana codec whenever the message's source chain is Solana. This is invoked directly on the untrusted `msg.TokenAmounts[i].DestExecData` bytes in: `MessageHasherV1.Hash` (used by both commit and execute report hashing) [1](#0-0) , `ExecutePluginCodecV1.Encode` (used when encoding execute plugin reports) [2](#0-1) , `EstimateProvider.CalculateMessageMaxGasWithError`/`CalculateMessageMaxGas` (which panics anyway on error, but demonstrates reach) [8](#0-7) , and `decodeExecData` inside the OCR transmitter's `SVMExecCalldataFunc` path [9](#0-8) .

The implementation itself does no bounds checking:
```go
func (d ExtraDataDecoder) DecodeDestExecDataToMap(destExecData cciptypes.Bytes) (map[string]any, error) {
	return map[string]any{
		svmDestExecDataKey: binary.BigEndian.Uint32(destExecData),
	}, nil
}
```
`binary.BigEndian.Uint32` internally does `_ = b[3]` and slices `b[0:4]`; if `len(destExecData) < 4`, this panics with index out of range, and the panic is not recovered anywhere in this call chain (unlike `EstimateProvider.CalculateMessageMaxGas`, which itself deliberately panics but only after wrapping errors returned from lower-level functions — this panic is a raw runtime panic, not a controlled one). The sibling EVM implementation returns a clean error via `abiDecodeUint32` (ABI decode length check) and Aptos checks `Remaining()!=4`, so the invariant "chain-specific decode functions never panic on malformed untrusted bytes" is violated only in the Solana codec.

The exact origin of `destExecData` (whether it comes from on-chain contract state read by the Solana chain reader, or is otherwise attacker-influenced) was not fully traced in this session, but the interface contract and existing test suite for the sibling codecs explicitly treat `destExecData` as untrusted, attacker-relayed message data requiring validation before decode.

### Impact Explanation
An unhandled panic inside a goroutine processing commit/execute plugin OCR reports (message hashing, gas estimation, report encoding, or execute calldata construction for Solana-sourced lanes) will crash that goroutine. Depending on whether the panic occurs inside a recovered top-level OCR runner goroutine or not, this can crash the node process or halt CCIP OCR report generation/verification for Solana lanes, producing a denial-of-service condition scoped to Solana-source CCIP lanes across the node.

### Likelihood Explanation
No privileged access is needed to trigger the code path: any message with a `TokenAmounts[].DestExecData` field of length 0–3 originating from (or attributed to) a Solana source chain will trigger this on every node running the CCIP Solana plugin that processes that message, making it fully deterministic and repeatable once such a malformed value reaches the decode call.

### Recommendation
Add a length check at the top of `DecodeDestExecDataToMap` mirroring the EVM/Aptos implementations, e.g.:
```go
func (d ExtraDataDecoder) DecodeDestExecDataToMap(destExecData cciptypes.Bytes) (map[string]any, error) {
	if len(destExecData) != 4 {
		return nil, fmt.Errorf("dest exec data invalid length: %d, expected 4", len(destExecData))
	}
	return map[string]any{
		svmDestExecDataKey: binary.BigEndian.Uint32(destExecData),
	}, nil
}
```
