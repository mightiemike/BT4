### Title
Reference-Equality (`==`) Comparison on `ByteString` Owner Address Bypasses Issuer-Bandwidth Fast Path, Corrupting Asset Free-Bandwidth Pool Accounting - (File: `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`)

### Summary
`BandwidthProcessor.useAssetAccountNet()` is supposed to detect when the sender of a `TransferAssetContract` is the asset's own issuer and, in that case, short-circuit into `useAccountNet()` so the issuer consumes only its own regular bandwidth quota. The detection is implemented with Java reference equality (`==`) on two `com.google.protobuf.ByteString` objects instead of `.equals()`. Because the two `ByteString` instances are read from different store lookups, they are never the same object reference, so the branch is effectively dead code and every issuer self-transfer instead falls through into the shared "public/free asset bandwidth" accounting path.

### Finding Description
In `useAssetAccountNet`: [1](#0-0) 

```java
if (assetIssueCapsule.getOwnerAddress() == accountCapsule.getAddress()) {
  return useAccountNet(accountCapsule, bytes, now);
}
```

`assetIssueCapsule.getOwnerAddress()` and `accountCapsule.getAddress()` are both `ByteString` values obtained from independent `AssetIssueStore`/`AccountStore` lookups (via `AccountCapsule`/`AssetIssueCapsule` protobuf accessors). `ByteString.equals()` performs a byte-content comparison, but `==` performs Java object identity comparison. Two `ByteString` instances holding identical bytes but produced from separate deserializations are distinct objects, so this condition is essentially always `false`, even when the transferring account is in fact the asset issuer.

As a result, this fast path is unreachable in practice, and the code always falls into the shared "public free asset net limit" / "free asset net limit" accounting further below: [2](#0-1) 

That path consumes the per-account `freeAssetNetLimit` and the token-wide `publicFreeAssetNetLimit` pool, and separately re-fetches and debits the issuer's own regular bandwidth (`issuerNetUsage`) again through `chainBaseManager.getAccountStore().get(assetIssueCapsule.getOwnerAddress()...)`. This is reachable from any ordinary, unprivileged broadcast transaction: any account can call `AssetIssueActuator` to issue a TRC10 token (self-created, unprivileged) and then send `TransferAssetContract` transfers of that token to itself or others, unconditionally triggering the faulty branch on every such transfer. [3](#0-2) 

### Impact Explanation
Because the issuer-identity check never fires, every transfer of a TRC10 token by its own issuer consumes bandwidth twice: once against the issuer's normal frozen-bandwidth/free-bandwidth quota (as intended for a "normal" account transferring someone else's asset) and a second, unintended debit against the shared per-token free/public asset bandwidth pool (`freeAssetNetLimit` / `publicFreeAssetNetLimit`) that is meant to be reserved for *other* holders of that token. This corrupts resource accounting for the asset: the issuer's own activity depletes the public free-bandwidth pool that legitimate third-party holders rely on for free transfers of that asset, which is an accounting-corruption / partial denial-of-service condition against other token holders' free-bandwidth allowance. It is not the same as Vether's "escape all fees" bug (this bug does not let anyone dodge fees they'd otherwise owe); instead it silently misallocates and can exhaust a shared resource pool via a completely unprivileged, reachable broadcast-transaction path.

### Likelihood Explanation
High likelihood of being triggered unintentionally: any account that issues a TRC10 asset (a fully permissionless action available to any funded account) and subsequently transfers that same asset will always hit this code path, since the intended bypass condition can never evaluate to `true`. No special privilege, malicious peer, or protocol-level access is required — a single ordinary broadcast `TransferAssetContract` transaction is sufficient to reproduce it deterministically.

### Recommendation
Replace the identity comparison with a content comparison, e.g.:
```java
if (assetIssueCapsule.getOwnerAddress().equals(accountCapsule.getAddress())) {
  return useAccountNet(accountCapsule, bytes, now);
}
```
This restores the intended behavior where the issuer's own transfers consume only their own regular bandwidth quota and do not touch the shared free/public asset bandwidth pool.

### Proof of Concept
1. Account `A` issues a TRC10 asset via `AssetIssueContract` (`AssetIssueActuator`), setting a non-zero `freeAssetNetLimit`/`publicFreeAssetNetLimit`.
2. Account `A` broadcasts a `TransferAssetContract` sending that asset to any recipient (including itself).
3. In `Manager`'s bandwidth consumption flow, `BandwidthProcessor.consume()` invokes `useAssetAccountNet(contract, accountCapsule, now, bytesSize)` for the `TransferAssetContract` type.
4. Inside `useAssetAccountNet`, `assetIssueCapsule.getOwnerAddress() == accountCapsule.getAddress()` evaluates to `false` (distinct `ByteString` object instances despite identical byte content), even though account `A` is indeed the issuer.
5. Execution proceeds to debit `publicFreeAssetNetUsage` and the account's `freeAssetNetUsage`/`freeAssetNetUsageV2` for the token, in addition to debiting the issuer's own `NetUsage` — verifiable by comparing the resulting `AssetIssueCapsule`/`AccountCapsule` state fields against what `useAccountNet` alone would have produced.
