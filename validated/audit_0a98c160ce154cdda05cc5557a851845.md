### Title
Unbounded per-account delegation index list causes O(n) storage-write loop in `DelegatedResourceAccountIndexStore.convert()`, risking a resource-exhaustion DoS - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegatedResourceAccountIndexCapsule` stores an account's entire set of delegation counterparties (`toAccountsList`/`fromAccountsList`) as unbounded repeated fields inside a single storage record. Prior to the `AllowDelegateOptimization` hard fork, `FreezeBalanceActuator.delegateResource()` allowed an owner to accumulate one entry per distinct `receiverAddress` in this list with no upper bound check [1](#0-0) . After the fork, `DelegatedResourceAccountIndexStore.convert()` migrates that entire legacy list to the new per-pair key format by iterating over it and calling `delegate()` (two `store.put()` operations) for every element [2](#0-1) . This `convert()` call is unconditionally invoked from user-triggered actuators such as `UnfreezeBalanceActuator.execute()` whenever the new resource model is in effect [3](#0-2) .

### Finding Description
The bug class from the external report is a for-loop that performs a storage operation per iteration over a user-controlled, unbounded list, causing unpredictable and potentially very high transaction cost, and denying legitimate operations (DoS) once the list is large enough. The java-tron analog is structurally identical: `convert(address)` reads the full `toAccountsList` and `fromAccountsList` of a `DelegatedResourceAccountIndexCapsule` and, for each element, performs a `delegate()` call which writes two rows to the `DelegatedResourceAccountIndexStore` [2](#0-1) . Nothing in `FreezeBalanceActuator.validate()`/`execute()` bounds the number of distinct `receiverAddress` values an owner can delegate to over multiple transactions before the fork [4](#0-3) , so an account (or an attacker targeting itself, or coordinating many delegations to a single receiver so the receiver's `fromAccountsList` grows) could accumulate an arbitrarily large list. Once the `AllowDelegateOptimization`/`supportUnfreezeDelay` hard forks are active, any later user-submitted transaction touching that account (e.g. `UnfreezeBalanceActuator` for the old model, still valid post-V2) triggers `convert(ownerAddress)`/`convert(receiverAddress)`, forcing the node to migrate the entire historical list synchronously inside a single transaction's execution, with no fee accounting proportional to the list size (`FreezeBalanceActuator.calcFee()` returns 0 and `UnfreezeBalanceActuator`'s fee model does not scale with list length).

### Impact Explanation
An account with a sufficiently large legacy `toAccountsList`/`fromAccountsList` becomes effectively unable to complete the migration transaction (Unfreeze/UnDelegate) if the induced storage-write workload exceeds practical block/transaction processing limits, or it disproportionately burdens block producers processing that transaction (since the cost is not billed via a size-scaled fee). This matches the reported bug's "severity: high — investor denied ability to receive tokens back due to unbounded per-item storage cost with no way around it," mapped here to TRX resource delegation bookkeeping instead of NFT staking.

### Likelihood Explanation
Likelihood depends on how many accounts on the live network actually accumulated large legacy delegation lists before the `AllowDelegateOptimization` hard fork activated; for any such account the very next old-model unfreeze/legacy-triggering transaction pays the entire migration cost unconditionally and irrevocably (`convert()` unconditionally processes the whole list, with no chunking or resumability). Because there was historically no cap on the number of distinct delegation counterparties per account, this is plausible for high-volume resource-delegation services/exchanges that delegate to many different receiver addresses.

### Recommendation
Bound the number of distinct delegation counterparties tracked per account (mirroring the pattern already used to cap `UnfreezeBalanceV2Actuator.UNFREEZE_MAX_TIMES`), or make `DelegatedResourceAccountIndexStore.convert()` incremental/resumable across multiple transactions/blocks rather than performing the full O(n) migration synchronously in one user transaction, and account for its cost in the actuator's fee calculation so the cost is proportional to work performed.

### Proof of Concept
1. Before the `AllowDelegateOptimization` fork is enabled, have account `A` repeatedly submit `FreezeBalanceContract` transactions with distinct `receiverAddress` values (bandwidth/energy delegation), each call appending to `A`'s `DelegatedResourceAccountIndexCapsule.toAccountsList` via `FreezeBalanceActuator.delegateResource()` [1](#0-0) .
2. After `AllowDelegateOptimization`/`supportUnfreezeDelay` activate, have account `A` submit an `UnfreezeBalanceContract` transaction (old-model unfreeze remains valid post-fork).
3. Observe that `UnfreezeBalanceActuator.execute()` calls `delegatedResourceAccountIndexStore.convert(ownerAddress)`, which iterates the entire accumulated `toAccountsList`/`fromAccountsList` and performs two `store.put()` writes per entry [2](#0-1) , with the per-transaction cost growing linearly with the historical list size and no corresponding fee.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
