## Title
Unauthenticated Request-ID Collision Enables Griefing/DoS of Other Users' Confidential Relay Gateway Requests - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
The `confidentialrelay` Gateway handler stores in-flight requests in a single map keyed only by the caller-supplied JSON-RPC `req.ID` string, with no per-owner or per-workflow namespacing. Any user reaching this handler can pick an arbitrary `ID` value. If an attacker submits a request using the same `ID` as a legitimate user's request, the legitimate request will be rejected outright with a "request ID already exists" error — mirroring the reported `addCandidate` hash-collision griefing pattern, where any actor can pre-empt a hash/identifier to block someone else's legitimate action.

### Finding Description
`newActiveRequest` is the single gate for admitting a request into the handler's live-request table: [1](#0-0) 

```go
func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	...
	h.activeRequests[req.ID] = ar
	return ar, nil
}
```

`HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 characters before calling `newActiveRequest` — it does not bind the ID to the caller's identity, workflow, or any authenticated owner value: [2](#0-1) 

This is functionally identical to the `addCandidate` pattern from the external report: `assert self.candidates[hash].owner == ZERO_ADDRESS` guards entry creation on a caller-chosen identifier, and whoever claims the identifier first wins, permanently (until expiry) locking out anyone else who picks the same identifier. Here, the "hash" is the caller-supplied `req.ID`, and there is no cryptographic binding (e.g., a nonce derived from the sender's authenticated identity) preventing a second, unrelated party from reusing it.

The sibling `vault` handler in the same codebase demonstrates the correct mitigation: it prefixes the raw request ID with the caller's `authorizedOwner` (derived from authentication) before it is used as a map key, so collisions can only occur within a single authenticated owner's own requests, not across users: [3](#0-2) 

The `confidentialrelay` handler has no analogous owner-prefixing step, so its ID space is shared globally across all callers of the DON's `MethodSecretsGet` / `MethodCapabilityExec` methods.

### Impact Explanation
An attacker who can reach the Gateway's confidential relay endpoint (a workflow-facing, non-privileged-node trust boundary) can deny service to a specific legitimate request by submitting a colliding `ID` first. Because the map is not scoped by owner, this griefing works across different users/workflows, not just against the same caller retrying — this is a genuine cross-tenant DoS on a gateway/capability routing path, unlike simple self-collision (which would be a caller's own bug). The affected request is dropped with a hard error rather than being queued or serviced, causing a legitimate confidential relay / secrets-get / capability-exec request to fail.

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or observe the victim's `req.ID` before the victim's request is processed (e.g., short-lived race, predictable ID generation by an SDK, or IDs leaked/observable via logs/telemetry). This lowers likelihood relative to a fully blind attack, but the underlying code provides no structural defense (no per-owner namespace, no replay/ownership binding) once such an ID is known or guessed, which is exactly the low-difficulty "Data Validation" classification the original report describes for `addCandidate`.

### Recommendation
Namespace the `activeRequests` map key by an authenticated identity/nonce (as already done in `core/capabilities/vault/gateway_vault_request_processor.go`'s `authorizeAndStamp`, which prefixes IDs with `authorizedOwner`), rather than trusting the raw client-supplied `req.ID` as a globally unique key. Short term, document that `req.ID` collisions across callers are possible and can be exploited for griefing.

### Proof of Concept [4](#0-3) 

```go
func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {
	t.Parallel()
	h, cb, don, _ := setupHandler(t, 4)
	don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)

	params := json.RawMessage(`{"workflow_id":"wf1"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "req-dup",
		Method: MethodCapabilityExec,
		Params: &params,
	}

	err := h.HandleJSONRPCUserMessage(t.Context(), req, cb)
	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}
```
This existing test demonstrates the exact collision behavior: a second `HandleJSONRPCUserMessage` call using the same `ID` is unconditionally rejected. Nothing in the code differentiates "same caller retried" from "different, unrelated caller chose the same ID first" — an attacker who submits `req-dup` ahead of the victim causes the victim's genuinely distinct request to fail with `request ID already exists`.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}
