Found a concrete analog: `sanitizeHost()`/`decodeHost()` call `atob()` on unvalidated attacker-controlled input, and several call sites invoke it **without a try/catch**, so a malformed `host` query parameter causes an uncaught exception (DoS), directly analogous to `safeSymbol()` assuming a return type and reverting on malformed input.

### Title
Uncaught `atob()` exception in `sanitizeHost`/`decodeHost` causes unhandled exception (DoS) in unauthenticated redirect/auth paths - (File: packages/apps/shopify-api/lib/auth/decode-host.ts, packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`decodeHost()` blindly calls the global `atob()` on the `host` value without any error handling, assuming the input is well-formed base64 [1](#0-0) . `sanitizeHost()` validates the string against a base64 *character-set* regex (`^[0-9a-zA-Z+/]+={0,2}$`) before calling `decodeHost`, but this regex does not enforce valid base64 *length* (multiple-of-4, or the WHATWG forgiving-base64 length%4 ∈ {0,2,3} rule) [2](#0-1) . A string like a single character (`host=a`) passes the regex but makes `atob()` throw an `InvalidCharacterError`/`DOMException`, which propagates out of `sanitizeHost` uncaught.

### Finding Description
This is the same bug class as the `safeSymbol()` finding: a helper function assumes its input conforms to an expected encoding/type and blindly decodes it with a call that can throw (`abi.decode()` for ERC20 symbols vs. `atob()` for base64 host params), without guarding against malformed input from an untrusted source. Several production call sites of `sanitizeHost`/`getEmbeddedAppUrl`/`buildEmbeddedAppUrl` do not wrap the call in try/catch:
- `redirectToShopifyOrAppRoot` middleware calls `api.utils.sanitizeHost(req.query.host as string)!` directly, with no try/catch around it [3](#0-2) .
- `redirect-to-auth.ts`'s `clientSideRedirect` calls `api.utils.sanitizeHost(req.query.host as string)` with no try/catch [4](#0-3) .
- `validateShopAndHostParams` (remix/react-router) calls `api.utils.sanitizeHost(...)` with no try/catch [5](#0-4) .

By contrast, `embedAppIntoShopify` in `ensure-installed-on-shop.ts` *does* wrap `getEmbeddedAppUrl` (which also calls `sanitizeHost`→`decodeHost`) in a try/catch, showing the library authors are aware this call can throw but did not apply the same defensive pattern consistently everywhere [6](#0-5) .

All of these code paths are reachable by a single anonymous HTTP GET request (e.g. hitting the app root, the exit-iframe/redirect path, or the OAuth begin path with `embedded=1`) supplying a crafted `host` query parameter — no authentication is required.

### Impact Explanation
In frameworks/adapters where the uncaught exception is not otherwise caught by a top-level error boundary (e.g., a raw Express route not wrapped by Express's own error handling for synchronous throws inside async handlers, or serverless/worker `fetch` handlers without global try/catch), this becomes an unhandled promise rejection / thrown exception that returns a generic 500 or, in worse deployments, crashes the process/isolate — a Denial-of-Service against the app's install/redirect/auth entry points, achievable by any unauthenticated actor by controlling the `host` query string.

### Likelihood Explanation
High reachability: `host` is a normal query parameter that Shopify includes on embedded-app requests, but nothing prevents an attacker from directly hitting these routes with an arbitrary `host` value (these are public, pre-auth entry points such as the app root or the exit-iframe/login redirect route). The character-set regex in `sanitizeHost` gives a false sense of validation while not preventing all malformed-length inputs from reaching `atob()`.

### Recommendation
Wrap the `atob()` call in `decodeHost()` in a try/catch and return `null`/throw a typed `InvalidHostError` consistently, and ensure `sanitizeHost()` validates base64 length constraints (e.g., `length % 4 !== 1`) before calling `atob`, mirroring the defensive `try { ... } catch` pattern already used in `embedAppIntoShopify`. Apply the same try/catch guard at every call site of `sanitizeHost`/`getEmbeddedAppUrl`/`buildEmbeddedAppUrl` that currently lacks it (`redirect-to-shopify-or-app-root.ts`, `redirect-to-auth.ts`, `validate-shop-and-host-params.ts` in both remix and react-router packages).

### Proof of Concept
1. As an anonymous user, send `GET /?shop=test.myshopify.com&host=a` (or any embedded-app root/exit-iframe route that triggers `redirectToShopifyOrAppRoot`, `redirect-to-auth`'s `clientSideRedirect`, or `validateShopAndHostParams`).
2. `host=a` passes the `base64regex` check in `sanitizeHost` (single alphanumeric char, no `=` needed) [7](#0-6) .
3. `decodeHost('a')` calls `atob('a')`, which throws because length 1 is invalid for base64 decoding [1](#0-0) .
4. Because the calling middleware (e.g. `redirectToShopifyOrAppRoot`) has no try/catch around `sanitizeHost`, the exception propagates unhandled, producing an unexpected 500 error (or an unhandled rejection depending on runtime), rather than a controlled `InvalidHostError`.
