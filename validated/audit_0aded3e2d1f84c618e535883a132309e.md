## Title
OAuth callback validates HMAC against a different `shop` value than the one used for the token exchange - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
In the OAuth callback handler, the `shop` value that is HMAC-verified is derived differently from the `shop` value that is actually used to perform the sensitive access-token exchange request. When the `shop` query parameter is duplicated, `URLSearchParams.get()` returns the *first* occurrence while `Object.fromEntries(query.entries())` collapses duplicates to the *last* occurrence — so the check and the use can silently diverge, exactly analogous to the reported `_withdraw()` bug where one variable is validated but a different variable is acted upon.

### Finding Description
In `callback()`: [1](#0-0) 

```ts
const query = new URL(request.url, ...).searchParams;
const shop = query.get('shop')!;
```

The HMAC/state validation is performed on `authQuery`, built from `Object.fromEntries(query.entries())`: [2](#0-1) 

For a duplicated key, `Object.fromEntries` keeps the **last** value (later `Object.assign`-like writes overwrite earlier ones), so `authQuery.shop` is the *last* `shop=` occurrence. `validateHmac()` computes the local HMAC from this plain object without doing any duplicate-key detection, because that guard only applies to `URLSearchParams` instances / the `appProxy` signator: [3](#0-2) 

Then, after the HMAC check passes, the code that actually performs the token exchange reuses the *original* `URLSearchParams` object and calls `.get('shop')` again, which returns the **first** occurrence: [4](#0-3) 

```ts
const cleanShop = sanitizeShop(config)(query.get('shop')!, true)!;
...
`https://${cleanShop}/admin/oauth/access_token`
```

This `cleanShop` is also what gets stored as the resulting `Session.shop`. [5](#0-4) 

So: the value that is verified against Shopify's real HMAC signature (last `shop=` occurrence) is not the same value that is used to build the outgoing `/admin/oauth/access_token` request and the session's `shop` field (first `shop=` occurrence).

### Impact Explanation
A user who legitimately completes OAuth for their own shop (and thus possesses a real, Shopify-issued `hmac`/`state`/`code` for that callback) can append a duplicate `shop` parameter to their own callback request: `?shop=<attacker-chosen>&shop=<real-shop>&hmac=<real-hmac>&state=...&code=...`.
- `authQuery.shop` (last value) == real shop → the real HMAC still validates.
- `query.get('shop')` (first value) == attacker-chosen shop → this is what's used for `cleanShop`, the `/admin/oauth/access_token` request target, and the stored `Session.shop`.

This causes the app's `client_secret` and the real, single-use authorization `code` to be sent to an attacker-influenced shop's `/admin/oauth/access_token` endpoint rather than the shop that actually authorized the app, and results in a `Session` object being created/labeled for a shop that never actually completed authorization (shop confusion / cross-tenant session mislabeling). Because `sanitizeShop` restricts the shop to Shopify-owned domains (`myshopify.com`, `shopify.com`, `myshopify.io`, `shop.dev`, or configured `domainTransformations`), the blast radius is bounded to Shopify's own infrastructure or configured custom domains rather than an arbitrary attacker server, but it still breaks the intended one-to-one binding between the verified request and the shop that is acted upon.

### Likelihood Explanation
Exploitation only requires a single actor performing a normal OAuth install for a shop they control and rewriting the query string of their own callback GET request (trivial with any HTTP client/browser dev tools) before it reaches the app server — no privileged access, secrets, or MITM are required. The state-cookie check does not protect against this because it validates `authQuery.state`, which is subject to the exact same last-value collapsing as `shop`.

### Recommendation
Derive the `shop` used for HMAC validation and the `shop` used for the token exchange/session creation from the **same** normalized representation, and reject requests containing duplicate security-relevant parameters (`shop`, `hmac`, `state`, `code`, `timestamp`) for the admin/OAuth callback path, the same way `hmac-validator.ts` already guards against duplicated `APP_PROXY_SINGLE_VALUE_PARAMS` for the `appProxy` signator. Concretely, extend the duplicate-parameter rejection in `normalizeQuery`/`callback()` to the `admin` signator as well, and use `authQuery.shop` (the validated value) consistently for `cleanShop`, instead of re-reading `query.get('shop')`.

### Proof of Concept
1. Attacker begins OAuth for their own store `attacker-shop.myshopify.com`; Shopify redirects back to `GET /auth/callback?code=REALCODE&hmac=REALHMAC&shop=attacker-shop.myshopify.com&state=REALSTATE&timestamp=...`.
2. Attacker intercepts this request in their own browser/tooling and rewrites the query string to:
   `?code=REALCODE&hmac=REALHMAC&shop=victim-shop.myshopify.com&shop=attacker-shop.myshopify.com&state=REALSTATE&timestamp=...`
3. `authQuery` (via `Object.fromEntries`) collapses to `shop=attacker-shop.myshopify.com` (last), so `validateHmac`/`safeCompare` still pass with the original, real `REALHMAC`/`REALSTATE`.
4. `cleanShop = sanitizeShop(query.get('shop'))` resolves to `victim-shop.myshopify.com` (first occurrence), and the app performs `POST https://victim-shop.myshopify.com/admin/oauth/access_token` with the app's `client_secret` and `REALCODE`, and later creates a `Session` labeled `shop: victim-shop.myshopify.com`. function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }
