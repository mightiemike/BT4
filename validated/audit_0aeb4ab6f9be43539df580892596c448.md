## Analysis Result

### Title
Unbounded, un-evictable growth of the global `ProgramCache` via tombstones for arbitrary attacker-referenced accounts - ([File: program-runtime/src/loaded_programs.rs])

### Summary
Any unprivileged transaction can reference an arbitrary, already-existing (or attacker-created) account as an instruction's `program_id`. If that account is not a valid loader/program account, the SVM permanently inserts a "tombstone" entry for that pubkey into the validator's process-global `ProgramCache`. Unlike normal `Loaded` program entries, tombstones (`Closed`, `FailedVerification`, `DelayVisibility`) are explicitly exempt from the cache's only size-bounding mechanism (probabilistic/LFU eviction), so the `entries: HashMap<Pubkey, Vec<Arc<ProgramCacheEntry>>>` index can only shrink via fork-pruning of non-canonical branches — never for entries that are already rooted. This is structurally the same bug class as the reported libp2p issue: an attacker-fed deduplication/lookup map with no size cap and no GC path for adversarial keys, driven purely from unprivileged input.

### Finding Description
When a transaction references an account as an executable program, the SVM resolves and caches it via `load_program_with_pubkey`: [1](#0-0) 
If the account exists but is not a valid program/loader account, `ProgramAccountLoadResult::InvalidAccountData(owner)` is returned and a permanent `Closed` tombstone is created and returned, keyed by that pubkey: [2](#0-1) 
This entry is inserted into the validator-global `ProgramCache.index` map (`entries.entry(key).or_default()...slot_versions.insert(...)`), regardless of whether the pubkey is a legitimate program: [3](#0-2) 

`ProgramCacheEntryType` explicitly defines tombstone variants (`FailedVerification`, `Closed`, `DelayVisibility`) as first-class, indefinitely retained members of the cache: [4](#0-3) [5](#0-4) 

The cache's only memory-bounding mechanism, `evict_using_random_selection`/`unload_program_entry`, only converts `Loaded` entries to `Unloaded` — tombstones are never touched by this path: [6](#0-5) 
This is confirmed by the test suite's own documentation of intended behavior: "Tombstones and unloaded entries are expected to not be evicted." [7](#0-6) 

The only other cleanup path is `prune()`, which removes entries only "on orphan fork or overshadowed on the rooted fork" — i.e., forks that get discarded during rerooting — not entries that are simply tombstones for random non-program accounts on the canonical, rooted chain. Once such a transaction lands, the corresponding pubkey's tombstone entry becomes permanent for the lifetime of the validator process, exactly like the never-garbage-collected libp2p protocol-string map in the original report.

Since an attacker only needs to reference *any pre-existing* account (a wallet, token account, PDA, etc. — of which billions already exist on a live cluster) as a bogus instruction `program_id`, no expensive account creation is required to poison the cache; the attacker only pays the base transaction fee (and the transaction is expected to fail with `InstructionError::UnsupportedProgramId`/`IncorrectProgramId`, which is inexpensive and doesn't require special privilege).

### Impact Explanation
Each poisoned pubkey permanently occupies memory (`Arc<ProgramCacheEntry>` plus `HashMap`/`Vec` overhead) in the validator's global, unbounded, in-process `ProgramCache`. An attacker can enumerate large numbers of distinct, already-existing account pubkeys and reference each once as a bogus instruction program id across many cheap transactions, causing continuous, un-evictable memory growth on every validator that processes these transactions. Because this is driven by ordinary transaction traffic (not privileged, not requiring code execution), it can be replayed against the entire fleet simultaneously, leading to gradual OOM pressure and eventual crashes on affected nodes — a fleet-wide degradation/DoS scenario analogous to the "bring down large parts of the network" impact of the original CL-2026-07 report. It does not cause consensus divergence (this cache isn't part of consensus state) but is a genuine unbounded-memory / cluster-availability risk.

### Likelihood Explanation
High. No special privileges, deployed programs, or CPI depth are required — a single, ordinary, cheap transaction with an instruction pointing at any pre-existing, non-program account as its `program_id` triggers the vulnerable code path. The attack is trivially scriptable and scales with the number of existing accounts on the cluster and the attacker's fee/bandwidth budget, similar in structure to the original report's characterization of the libp2p attack being bandwidth-bound.

### Recommendation
- Bound the total number of tombstone entries retained in `ProgramCache`, or apply an eviction/expiry policy to tombstones (e.g., LRU-based removal, or a hard cap on unique non-program pubkeys tracked).
- Consider not persisting a permanent per-pubkey cache entry for `InvalidAccountData`/`FailedVerification` results at all when the account is clearly not owned by any BPF loader — such lookups can be treated as ephemeral misses rather than cached tombstones.
- Include tombstone entries in the `evict_using_random_selection`/`sort_and_unload` retention-scoring so they are subject to the same size cap as `Loaded`/`Unloaded` entries, rather than being explicitly excluded as seen in `unload_program_entry`.

### Proof of Concept
1. On a live cluster, enumerate N distinct existing pubkeys that are not valid BPF-loader-owned program accounts (e.g., ordinary wallet addresses, SPL token accounts — trivially obtainable via RPC `getProgramAccounts`/`getSignaturesForAddress`).
2. For each pubkey `P`, construct and send a transaction containing an instruction whose `program_id` field is `P` (this will fail sanitization/execution with `InstructionError::UnsupportedProgramId`/`IncorrectProgramId`, but is accepted and processed by the runtime up to that point).
3. Each such transaction invokes `TransactionBatchProcessor::replenish_program_cache` → `load_program_with_pubkey(P, ...)`, inserting a permanent `Closed`/`FailedVerification` tombstone for `P` into the validator-global `ProgramCache`.
4. Repeat for a large number of unique `P` values (paying only the base fee per transaction, no compute/program execution cost). Observe the validator process's memory usage grow monotonically and never shrink for these entries, since `evict_using_random_selection`/`unload_program_entry` ( [6](#0-5) ) never removes non-`Loaded` entries, and `prune()` will not remove them since they remain on the canonical rooted fork.

    /// This function removes the given entry for the given program from the cache.
    /// The function expects that the program and entry exists in the cache. Otherwise it'll panic.
    fn unload_program_entry(
        &mut self,
        id: Pubkey,
        _last_modification_slot: Slot,
        remove_entry: &Arc<ProgramCacheEntry>,
    ) {
        match &mut self.index {
            IndexImplementation::V1 { entries, .. } => {
                let second_level = entries.get_mut(&id).expect("Cache lookup failed");
                let candidate = second_level
                    .iter_mut()
                    .find(|entry| Arc::ptr_eq(entry, remove_entry))
                    .expect("Program entry not found");

                // Only loaded entries shall be unloaded by eviction.
                if let ProgramCacheEntryType::Loaded(_) = candidate.program
                    && let Some(unloaded) = candidate.to_unloaded()
                {
                    if candidate.stats.uses.load(Ordering::Relaxed) == 1 {
                        self.stats.one_hit_wonders.fetch_add(1, Ordering::Relaxed);
                    }
                    self.stats
                        .evictions
                        .entry(id)
                        .and_modify(|c| *c = c.saturating_add(1))
                        .or_insert(1);
                    *candidate = Arc::new(unloaded);
                }
            }
        }
    }

/// Actual payload of [ProgramCacheEntry].
#[derive(Default)]
pub enum ProgramCacheEntryType {
    /// Tombstone for programs which currently do not pass the verifier but could if the feature set changed.
    FailedVerification(ProgramRuntimeEnvironment),
    /// Tombstone for programs that were either explicitly closed or never deployed.
    ///
    /// It's also used for accounts belonging to program loaders, that don't actually contain program code (e.g. buffer accounts for LoaderV3 programs).
    #[default]
    Closed,
    /// Tombstone for programs which have recently been modified but the new version is not visible yet.
    DelayVisibility,
    /// Successfully verified but not currently compiled.
    ///
    /// It continues to track usage statistics even when the compiled executable of the program is evicted from memory.
    Unloaded(ProgramRuntimeEnvironment),
    /// Verified program.
    ///
    /// It may or may not be JIT compiled.
    Loaded(Executable<InvokeContext<'static, 'static>>),
    /// A built-in program which is not stored on-chain but backed into and distributed with the validator
    Builtin(BuiltinProgram<InvokeContext<'static, 'static>>),
}
