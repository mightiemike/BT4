### Title
Unconditional `L1Address`→`EthAddress` panic in `send_message_to_l1` receipt/summary construction on L3 chains - (File: crates/blockifier/src/execution/call_info.rs, crates/apollo_rpc_execution/src/objects.rs)

### Summary
On L3 chains (`chain_info.is_l3 == true`), the `send_message_to_l1` syscall skips the Ethereum-address-range validation of the message `to_address`, allowing any 252-bit felt to be recorded as the destination `L1Address`. However, code paths that later convert this `L1Address` into a strict 20-byte `EthAddress` for building `StarknetAPIMessageToL1`/receipts and RPC execution objects use `.expect(...)` on the fallible conversion instead of propagating an error, causing a panic when the felt does not fit into 20 bytes.

### Finding Description
The `send_message_to_l1` syscall validates the `to_address` only conditionally: [1](#0-0) 

The check `EthAddress::try_from(message.to_address)?` is explicitly skipped `if !is_l3`, meaning on an L3 chain configuration a contract may legitimately call `send_message_to_l1` with an arbitrary out-of-Ethereum-range felt (up to the full `L1Address`/felt domain) as `to_address`, and the syscall succeeds and records the message: [2](#0-1) 

This is confirmed by the corresponding test, which explicitly asserts success for `is_l3 = true` with an out-of-range address: [3](#0-2) 

However, when the recorded `OrderedL2ToL1Message` (holding the permissive `L1Address`) is later converted into the canonical `StarknetAPIMessageToL1` representation used for transaction execution summaries/receipts, the conversion unconditionally calls `.expect("Failed to convert L1Address to EthAddress")`: [4](#0-3) 

The same unconditional `.expect(...)` pattern exists in the RPC execution objects builder used to construct L2-to-L1 messages for `apollo_rpc_execution`: [5](#0-4) 

`EthAddress::try_from(L1Address)` requires the upper 12 bytes of the felt to be zero; any felt exceeding the 160-bit Ethereum address range fails this conversion: [6](#0-5) 

Because the syscall-level guard that would normally prevent such out-of-range values is deliberately disabled for `is_l3 = true` chains, but the downstream conversion assumes the invariant always holds, a single unprivileged contract call on an L3 sequencer can reach a `.expect()`-induced panic while building the call summary/receipt or serving RPC execution results.

### Impact Explanation
A panic triggered from within transaction execution summary construction (`to_ordered_tuple`, invoked when building `StarknetAPIMessageToL1` fee/receipt objects) or in the RPC execution layer would abort/crash the node process or worker thread handling that call. If this occurs during block building/execution on an L3 sequencer, it can halt block production for that node, and if triggered deterministically by a transaction included by an honest proposer, it can be reproduced by every node importing/re-executing that block, causing the network built on this codebase to be unable to confirm new transactions (denial of service reachable from an ordinary, unprivileged transaction).

### Likelihood Explanation
Any contract deployed on an L3-configured chain can call `send_message_to_l1` with a `to_address` felt larger than `2^160-1`; the syscall itself imposes no restriction in that mode, as proven by the existing unit test asserting success in that exact case. No special privileges are required beyond deploying/invoking a contract with a Cairo `send_message_to_l1` call — a standard, permissionless capability for any contract deployer/caller.

### Recommendation
Make the `L1Address`→`EthAddress` conversions in `to_ordered_tuple` (`crates/blockifier/src/execution/call_info.rs`) and in `OrderedL2ToL1Message::from` (`crates/apollo_rpc_execution/src/objects.rs`) fallible instead of using `.expect(...)`, returning a proper execution/serialization error, or alternatively re-apply the `is_l3` conditional validation consistently at every point where `L1Address` is narrowed to `EthAddress`, so the invariant assumed by the `.expect()` calls is actually guaranteed for every chain configuration that reaches these code paths.

### Proof of Concept
1. Configure/run a sequencer node with `chain_info.is_l3 = true` (an L3/appchain configuration).
2. Deploy any Cairo contract exposing a `send_message_to_l1(to_address, payload_len, payload)` entry point (e.g., the existing `TestContract` used in `send_message_to_l1.rs`).
3. Submit a transaction invoking that entry point with `to_address = felt!("0x10000000000000000000000000000000000000000")` (exceeds 160 bits), mirroring the test setup in `crates/blockifier/src/execution/syscalls/syscall_tests/send_message_to_l1.rs:88-131`, but instead of only checking `execute_directly_given_block_context` (which succeeds for `is_l3 = true`), continue to the step where the resulting `CallInfo`/`OrderedL2ToL1Message` is summarized via `to_ordered_tuple` (`call_info.rs:100-116`) for receipt/fee construction, or served through `apollo_rpc_execution`'s `OrderedL2ToL1Message::from` (`objects.rs:457-473`).
4. Observe the `.expect("Failed to convert L1Address to EthAddress")` panic instead of a graceful transaction-level error.

        if !self.context.tx_context.block_context.chain_info.is_l3 {
            EthAddress::try_from(message.to_address)?;

        let ordered_message_to_l1 =

        self.l2_to_l1_messages.push(ordered_message_to_l1);
        self.context.n_sent_messages_to_l1 += 1;

        Ok(())
    }

impl TryFrom<Felt> for EthAddress {
    type Error = StarknetApiError;
    fn try_from(felt: Felt) -> Result<Self, Self::Error> {
        const COMPLIMENT_OF_H160: usize = std::mem::size_of::<Felt>() - H160::len_bytes();

        let bytes = felt.to_bytes_be();
        let (rest, h160_bytes) = bytes.split_at(COMPLIMENT_OF_H160);
        if rest != [0u8; COMPLIMENT_OF_H160] {
            return Err(StarknetApiError::OutOfRange { string: felt.to_string() });
        }

        Ok(EthAddress(H160::from_slice(h160_bytes)))
    }
}
