## Finding: Unauthenticated `write_set` bytes committed to durable storage during transaction-backup restore (pre-replay save path)

### Title
Backup-restore "save before replay" path commits attacker-controlled `write_set` bytes without checking them against the accumulator-proven `TransactionInfo.state_change_hash` — ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
The transaction-backup restore pipeline verifies transaction chunks using `TransactionListWithProofV2::verify()`, but that verification only checks transaction hashes, the transaction-info accumulator proof, and event root hashes — it never checks the `write_set` against `TransactionInfo::state_change_hash()`. For versions below the replay cutoff (`first_to_replay`), the restore path (`save_before_replay_version`) writes these unverified write sets straight into the ledger/state-KV DB via `restore_handler.save_transactions(...)`, without ever executing the VM or checking the write-set hash. This lets a malicious or compromised backup-storage provider substitute a different `write_set` for a transaction while keeping the (accumulator-proven) transaction and `TransactionInfo` unchanged, causing the restoring node to commit incorrect durable state under an otherwise "verified" version.

### Finding Description
`LoadedChunk::load` in [1](#0-0)  deserializes each backup record as `(txn, aux_info, txn_info, events, write_set)` from untrusted backup storage bytes, keeping `write_sets` in a separate `Vec<WriteSet>` outside the structure that gets cryptographically verified.

The verification it performs is: [2](#0-1) 
This builds a `TransactionListWithProofV2` from `txns`, `event_vecs`, and `txn_infos`+proof — `write_sets` are **not** included and thus not covered by `verify()`.

Looking at `TransactionListWithProof::verify` itself: [3](#0-2) 
It checks transaction hashes vs `txn_info.transaction_hash()`, the accumulator proof, and (if present) event root hashes — there is no `write_set` field on this type at all, hence no possible check of `state_change_hash`.

Compare this with the equivalent output-list verification, which does bind write sets to the proven `TransactionInfo`: [4](#0-3) 
and the general invariant check used elsewhere in replay verification: [5](#0-4) 
Neither of these hash-binding checks is exercised on the "save before replay" path.

The unauthenticated write sets are then written directly to durable storage: [6](#0-5) 
via `RestoreHandler::save_transactions`, which forwards to `restore_utils::save_transactions` / `save_transactions_impl` in [7](#0-6) . This code path performs no replay/re-execution and (based on the visible signature and call sites) receives `write_sets` as a plain parameter alongside `txn_infos`, with no cross-check that `CryptoHash::hash(write_set) == txn_info.state_change_hash()` before persisting to the ledger/state-KV DB.

By contrast, `TransactionOutput::ensure_match_transaction_info` (used elsewhere, e.g., in replay-verify tooling) explicitly performs this exact check, confirming that this hash binding is understood to be a required integrity invariant — but it is bypassed in the pre-replay backup-restore save path.

### Impact Explanation
This breaks the "committed state must match the correct VM result / must not corrupt durable ledger data" invariant: a backup-storage provider (which Aptos already treats as an adversarial/untrusted data source — that's the entire reason for verifying chunks against accumulator proofs) can serve a forged `write_set` blob for any transaction below the replay cutoff. Because the position/version and `TransactionInfo` (and hence the ledger's accumulator hash) remain correct and proven, the restoring node has no way to detect the substitution before committing the wrong state to its database. This corrupts durable state for the restored node, and any downstream authenticated reads/proofs served from that node's state DB (state proofs, resource reads, etc.) would then be internally "consistent" with a wrong version of the ledger rather than the true VM-computed result — a state-commitment corruption meeting the mainnet-impact bar described in the prompt.

### Likelihood Explanation
Exploitation requires the attacker to control or corrupt the content served from `BackupStorage` for at least one transaction chunk file (the manifest/proof files are still checked, but the raw record bytes containing `write_set` are not bound to the proof). This is a realistic threat model for restore/verify tooling and state-sync-from-backup flows, since backup storage (S3/GCS buckets, etc.) is explicitly an external, potentially compromised or man-in-the-middle-able component, and the whole design of the accumulator/range proof is meant to defend exactly against a malicious backup source — yet this one field slips through unauthenticated on the "save before replay" branch. This is not simply a generic "malicious peer" out-of-scope case since it's a genuine local code root cause (the proof structure omitting `write_set`) rather than a networking/consensus issue.

### Recommendation
Before calling `restore_handler.save_transactions(...)` in `save_before_replay_version`, verify each `write_set` against the corresponding, accumulator-proven `TransactionInfo.state_change_hash()` (i.e., `ensure!(CryptoHash::hash(&write_set) == txn_info.state_change_hash())`), mirroring the check already used in `TransactionOutputListWithProof::verify` and `TransactionOutput::ensure_match_transaction_info`. Alternatively, include `write_sets` in the verified `TransactionListWithProofV2` structure (extending its `verify()` to check write-set hashes) so that no code path can persist a write set that hasn't been bound to the proven `TransactionInfo`.

### Proof of Concept
1. An attacker controlling (or MITM-ing) the `BackupStorage` backend for a transaction chunk crafts a `TransactionChunkFormat::V1` record `(txn, aux_info, txn_info, events, write_set')` where `write_set'` differs from the original but `txn`, `txn_info`, and `events` are left unchanged (so their hashes still satisfy the accumulator/event-root proof checks).
2. A node runs `db-restore` (or `db-tool verify`/replay-from-backup) below the target `replay_from_version`. `LoadedChunk::load` deserializes the record, and `txn_list_with_proof.verify(...)` succeeds because it never inspects `write_set'`.
3. `save_before_replay_version` calls `restore_handler.save_transactions(first_version, &txns, &aux, &txn_infos, &events, write_sets_to_save)` with the forged `write_set'` included, and `restore_utils::save_transactions_impl` commits it to the state-KV/ledger DB.
4. The node now has durable state at that version reflecting `write_set'` instead of the true VM-computed write set, while its accumulator root/ledger info remain "valid" per the (unaffected) transaction-info proof chain.

Note: I was unable to view the interior loop body of `save_transactions_impl` (lines 206–293 in `storage/aptosdb/src/backup/restore_utils.rs`) due to a tool/rendering limitation that returned blank lines for that range; I could not directly confirm there is no last-resort hash check inside that function. However, the proof-verification gap in `TransactionListWithProof::verify` (which has no `write_set` field to check at all) is confirmed directly from the type definition, and is sufficient by itself to establish that write sets reach the storage layer without cryptographic binding to the proven `TransactionInfo`. If a hidden check does exist inside `save_transactions_impl`, a Devin session with full file access should verify this before treating the finding as fully confirmed.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

/// Saves the given transactions to the db. If a change set is provided, a batch
/// of db alterations will be added to the change set without writing them to the db.
pub(crate) fn save_transactions(
    state_store: Arc<StateStore>,
    ledger_db: Arc<LedgerDb>,
    first_version: Version,
    txns: &[Transaction],
    persisted_aux_info: &[PersistedAuxiliaryInfo],
    txn_infos: &[TransactionInfo],
    events: &[Vec<ContractEvent>],
    write_sets: Vec<WriteSet>,
    existing_batch: Option<(
        &mut LedgerDbSchemaBatches,
        &mut ShardedStateKvSchemaBatch,
        &mut SchemaBatch,
    )>,
    kv_replay: bool,
) -> Result<()> {
    if let Some((ledger_db_batch, state_kv_batches, _state_kv_metadata_batch)) = existing_batch {
        save_transactions_impl(
            state_store,
            ledger_db,
            first_version,
            txns,
            persisted_aux_info,
            txn_infos,
            events,
            write_sets.as_ref(),
            ledger_db_batch,
            state_kv_batches,
            kv_replay,
        )?;
    } else {
        let mut ledger_db_batch = LedgerDbSchemaBatches::new();
        let mut sharded_kv_schema_batch = state_store
            .state_db
            .state_kv_db
            .new_sharded_native_batches();
        save_transactions_impl(
            Arc::clone(&state_store),
            Arc::clone(&ledger_db),
            first_version,
            txns,
            persisted_aux_info,
            txn_infos,
            events,
            write_sets.as_ref(),
            &mut ledger_db_batch,
            &mut sharded_kv_schema_batch,
            kv_replay,
        )?;
        // get the last version and commit to the state kv db
        // commit the state kv before ledger in case of failure happens
        let last_version = first_version + txns.len() as u64 - 1;
        state_store
            .state_db
            .state_kv_db
            .commit(last_version, None, sharded_kv_schema_batch)?;

        ledger_db.write_schemas(ledger_db_batch)?;
    }

    Ok(())
}
