### Title
`replay_on_archive` verification tool silently ignores state-checkpoint / hot-state / position-state root divergence - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness check used by the `db-tool replay-on-archive` verifier to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` fetched from the backup/archive. It checks status, gas, write-set hash, and event root hash, but — per the comment in the code itself — deliberately skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`. This is the direct Aptos analog of the Tokemak bug class: a verification/withdraw-style code path has an "optional parameter" (the checkpoint hash comparison) that is missing for one call site, causing that path to falsely report success while a real state divergence exists.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates only status, gas_used, write_set_hash and event_root_hash, and explicitly documents that it skips the checkpoint-hash comparisons: [2](#0-1) 

This function is invoked from `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which is the entire correctness gate of the `replay-on-archive` tool used in the `replay-verify` CI/testing pipeline referenced by `testsuite/replay-verify/`: [3](#0-2) 

Because the comparator never checks `state_checkpoint_hash` (the Jellyfish-Merkle state root committed for that transaction, and — when `HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` features are active — the hot-state and position-state roots), a locally re-executed transaction whose *state changes* diverge from the archived `TransactionInfo` (while still producing the same write-set bytes' hash by coincidence is not required — rather, the state_checkpoint_hash is a root computed from the whole state tree, independent of a single txn's write set hash, and is not re-derived/re-verified anywhere else in this tool) will pass verification as "matching" even though the resulting global state root diverges.

### Impact Explanation
`replay-on-archive`/`replay-verify` is the mechanism Aptos uses to confirm that VM execution against historical inputs reproduces the exact same committed ledger state (state roots) recorded on an archive/backup — this is precisely the "committed state differs from correct VM result" and "hard-fork-only divergence during replay" class called out as in-scope. Because the state-checkpoint root families are never compared, a consensus/state-divergence bug (e.g., an execution nondeterminism, a hot-state or position-state-tree bug, or a malicious/corrupted archive with a mismatched state root) would go undetected by this tool, even though write-set hash and event hash still matched. This directly undermines the guarantee that "VM outputs, transaction infos ... must survive executor-to-storage handoff unchanged" for the state-root fields specifically, and the "authenticated API and proof-bearing responses must stay bound to the right ... root" invariant, since operators/CI rely on this tool to catch state divergence before promoting a build.

### Likelihood Explanation
The gap is unconditional and code-documented (not a rare edge case): every call to `ensure_match_transaction_info` from `replay_on_archive.rs` skips the checkpoint-hash checks regardless of feature flags. Any state-root divergence introduced by a VM/execution bug, or any archive tampering that leaves write-set/event hashes intact but flips the recorded state-checkpoint hash, will not be caught by this specific tool. The likelihood of the underlying divergence event is separate from this bug (this is a detection-gap bug, not itself a state-corruption primitive), so severity is bounded by whether other paths (e.g. `state_checkpoint_output` computed during normal `do_ledger_update`/chunk-executor commit, or accumulator-based proof verification in `TransactionAccumulatorProof`/`TransactionInfoWithProof`) independently re-derive and check the checkpoint hash. I was not able to fully confirm within the available searches whether `chunk_executor::mod.rs`'s commit path (as opposed to this standalone debugging tool) separately re-verifies state_checkpoint_hash against actual re-computed roots during normal chunk execution/commit — that would determine whether this gap is confined to the offline `replay-on-archive` tool only, or also affects any live state-sync/commit acceptance path.

### Recommendation
Extend `ensure_match_transaction_info` (or add a stricter variant used specifically by `replay_on_archive.rs`) to also compare `txn_info.state_checkpoint_hash()`, and when applicable `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, against the actual post-execution state-checkpoint hash computed for that batch (as done in `DoLedgerUpdate::assemble_transaction_infos` via `state_checkpoint_output.state_checkpoint_hashes`). Until fixed, treat `replay-on-archive`/`replay-verify` pass results as *not* proving state-root parity, only write-set/event/gas/status parity.

### Proof of Concept
1. Take an archived version range where the recorded `TransactionInfo.state_checkpoint_hash` corresponds to a specific global state root `R`.
2. Construct (or simulate via a VM bug) a local re-execution whose write set is byte-identical (same `write_set_hash`), same events, gas, and status, but whose downstream state tree, after checkpointing, actually produces a different root `R'` (e.g. because a preceding write set incorrectly encodes a value that hashes the same under `CryptoHash` circumstantially, or more realistically because a bug in state-checkpoint materialization/hot-state promotion corrupts unrelated keys not reflected in this txn's own write set hash).
3. Run `storage/db-tool/src/replay_on_archive.rs`'s verifier over this range; `execute_and_verify` calls `ensure_match_transaction_info` [4](#0-3)  which returns `Ok(())` because it never inspects `state_checkpoint_hash`.
4. The tool reports zero failed transactions for this range, even though the resulting state root diverges from the archive-committed root — a false "verified" result for a genuine state-integrity divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
