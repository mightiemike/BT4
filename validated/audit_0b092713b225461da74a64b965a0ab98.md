### Title
Dynamic Energy Factor Miscalculates When Contract Cycle Catch-up Is Delayed - ([File: chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java])

### Summary
The `catchUpToCycle` method in `ContractStateCapsule` computes a per-contract dynamic energy price factor (`EnergyFactor`) used by TRON's dynamic energy fee mechanism. This is the java-tron analog of the reported Lido Hurdle-rate bug: a rate/factor that should be applied consistently on a per-cycle basis is instead updated lazily, only when a contract is next touched. Because the "increase" branch and the "decrease" branch of the same catch-up computation are handled asymmetrically with respect to the number of skipped cycles, delaying the update across multiple maintenance cycles produces a different (and generally lower) final factor than what would result from updating every cycle promptly — exactly the timing-dependent compounding-effect bug class described in the report.

### Finding Description
`catchUpToCycle` is responsible for bringing a contract's `ContractState` (its dynamic `EnergyFactor` and `UpdateCycle`) up to date with the current DPoS maintenance cycle number whenever the contract is invoked again: [1](#0-0) 

- If `getEnergyUsage() > threshold` (i.e., the contract was heavily used in its last recorded cycle), the factor is increased by a single step (`lastCycle += 1`), regardless of how many cycles have actually elapsed since the last update: [2](#0-1) 
- The decrease that follows is compounded over the *entire* remaining `cycleCount = newCycle - lastCycle` using `pow(decreasePercent, cycleCount, ...)`: [3](#0-2) 

This creates an asymmetry identical in spirit to the Lido issue: the "increase" side of the calculation is applied at most once per catch-up call no matter how many cycles were skipped while usage was above threshold, while the "decrease" side properly compounds across every skipped cycle. If updates to a contract's state are delayed for multiple cycles (e.g., the contract is not invoked, or invocations are deferred due to congestion/high fees, similar to the offchain-bot-delay scenario in the report), the resulting `EnergyFactor` diverges from the value that would have been computed had each cycle been processed individually — under-representing sustained congestion increases while still fully applying decay. Since `EnergyFactor` directly scales the energy price charged for calling that contract (TVM execution/energy metering), the timing of when `catchUpToCycle` happens to be invoked (which is a function of arbitrary user-triggered contract calls) changes the fee outcome for economically equivalent usage histories.

### Impact Explanation
This affects the resource/energy metering system that determines contract call costs on-chain. A delayed catch-up (multiple skipped cycles) systematically produces a *lower* compounded energy factor than prompt per-cycle catch-up would, because the increase step is capped at "+1" per invocation while decrease scales with the full `cycleCount`. This can let heavily-used contracts under-pay the dynamic energy surcharge intended to throttle sustained congestion, or conversely let idle-then-reactivated contracts see inconsistent pricing depending purely on invocation timing rather than actual historical usage. This is an accounting-correctness issue in the TVM dynamic energy fee mechanism, not a memory-safety or authentication bypass; it does not grant unauthorized account operations but distorts fee/resource accounting in a manner analogous to the reported hurdle-rate compounding issue.

### Likelihood Explanation
Likelihood is low-to-moderate: `catchUpToCycle` is only invoked when a contract is actually called (lazy update model), so any contract with irregular call patterns across multiple maintenance cycles (6 hours each by default) will exhibit this divergence. No privileged access or malicious actor is required — a normal contract caller triggers the catch-up path, and the divergence is a deterministic consequence of the code path rather than an edge case requiring adversarial conditions. However, exploiting it for meaningful fee arbitrage requires deliberately timing contract calls to skip multiple cycles, which is plausible but not trivially profitable without further modeling of `increaseFactor`/`threshold` parameters.

### Recommendation
Make the increase branch cycle-aware and compounding in the same way as the decrease branch — i.e., compute the number of cycles for which `EnergyUsage` was above threshold (or otherwise bound the increase to the actual elapsed cycles) and apply `pow(increasePercent, cycleCount)` analogous to the decrease calculation, rather than a single fixed "+1 cycle" step regardless of how many cycles were actually skipped. Alternatively, process `EnergyFactor` updates every cycle during `doMaintenance()` for all active contracts (similar to `accumulateWitnessVi`) instead of lazily on next invocation, so the result is independent of when the contract happens to be called again.

### Proof of Concept
Not exploitable purely from the indexed context without confirming the caller site in `actuator/src/main/java/org/tron/core/vm/program/Program.java`, which the index could not fully resolve (file content appears truncated/excluded from the index). Conceptually:
1. Contract A generates `EnergyUsage` above `threshold` in cycle N, then is not called again until cycle N+5 (skipping 4 cycles).
2. On catch-up, `EnergyFactor` receives only a single "+1 cycle" increase step (based on the stale usage recorded at cycle N), then is compounded downward by `decreasePercent^4`.
3. Compare against a hypothetical scenario where the contract were called every cycle (N+1, N+2, N+3, N+4, N+5) with the same aggregate usage pattern — the per-cycle increase steps would compound multiplicatively via repeated `catchUpToCycle` calls, producing a different (generally higher) final `EnergyFactor`/energy price than the delayed single-call scenario.
This matches the existing unit test `framework/src/test/java/org/tron/core/capsule/ContractStateCapsuleTest.java` [4](#0-3)  which already demonstrates that `catchUpToCycle` behaves differently depending on how many cycles are skipped in a single call versus applied incrementally — confirming the timing-dependent divergence described above.

  public boolean catchUpToCycle(
      long newCycle, long threshold, long increaseFactor, long maxFactor,
      boolean useStrictMath, boolean disableMath
  ) {
    long lastCycle = getUpdateCycle();

    // Updated within this cycle
    if (lastCycle == newCycle) {
      return false;
    }

    // Guard judge and uninitialized state
    if (lastCycle > newCycle || lastCycle == 0L) {
      reset(newCycle);
      return true;
    }

    final long precisionFactor = DYNAMIC_ENERGY_FACTOR_DECIMAL;

    // Increase the last cycle
    // fix the threshold = 0 caused incompatible
    if (getEnergyUsage() > threshold) {
      lastCycle += 1;
      double increasePercent = 1 + (double) increaseFactor / precisionFactor;
      this.contractState = ContractState.newBuilder()
          .setUpdateCycle(lastCycle)
          .setEnergyFactor(min(
              maxFactor,
              (long) ((getEnergyFactor() + precisionFactor) * increasePercent) - precisionFactor,
              disableMath))
          .build();
    }

    // No need to decrease
    long cycleCount = newCycle - lastCycle;
    if (cycleCount <= 0) {
      return true;
    }

    // Calc the decrease percent (decrease factor [75% ~ 100%])
    double decreasePercent = pow(
        1 - (double) increaseFactor / DYNAMIC_ENERGY_DECREASE_DIVISION / precisionFactor,
        cycleCount, useStrictMath
    );

    // Decrease to this cycle
    // (If long time no tx and factor is 100%,
    //  we just calc it again and result factor is still 100%.
    //  That means we merge this special case to normal cases)
    this.contractState = ContractState.newBuilder()
        .setUpdateCycle(newCycle)
        .setEnergyFactor(max(
            0,
            (long) ((getEnergyFactor() + precisionFactor) * decreasePercent) - precisionFactor,
            disableMath))
        .build();

    return true;
  }
