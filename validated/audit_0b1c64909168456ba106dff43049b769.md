### Title
Storage-cache entries for a same-tx-created-then-selfdestructed contract survive when the address had no prior code, letting later reads observe stale storage from a destroyed incarnation - ([File: crates/engine/execution-cache/src/cached_state.rs])

### Summary
`ExecutionCache::insert_state` decides how to invalidate the cross-block execution cache for a destroyed account based solely on whether the account's *start-of-block* `original_info` had a non-empty code hash. When it didn't (e.g. the address was previously a plain EOA), the code only removes the entry from `account_cache` and explicitly skips clearing `storage_cache`, relying on the comment "Since EIP-6780, SELFDESTRUCT only works within the same transaction where the contract was created, so we don't need to handle clearing the storage." This reasoning is wrong for the well-known "prefunded CREATE2" pattern: a `CREATE2` contract can be deployed and self-destructed in the *same* transaction (EIP-6780 exception) at an address that previously held only ETH (no code) but writes storage slots during its brief lifetime before destructing. Because `had_code` is computed from the pre-block `original_info`, this case takes the "remove account only" branch and never clears the storage slots that were written and cached during that transaction's execution.

### Finding Description
In `ExecutionCache::insert_state` [1](#0-0) :

```
if account.was_destroyed() {
    let had_code =
        account.original_info.as_ref().is_some_and(|info| !info.is_empty_code_hash());
    if had_code {
        ... self.clear(); return Ok(())
    }
    self.0.account_cache.remove(addr);
    continue;
}
```

`had_code` only reflects the account's code hash **before this block**. It says nothing about whether the account had *code and storage during this transaction*. The `prefunded_create2_selfdestruct` e2e test in `crates/ethereum/node/tests/e2e/eip6780.rs` demonstrates exactly this pattern [2](#0-1) : an address is prefunded as a plain EOA in an earlier block, then a `CREATE2` factory deploys `selfdestruct_initcode` to that address, which writes `0x42` to storage slot 0 and then self-destructs within the *same* transaction as its creation (satisfying the EIP-6780 same-tx exception). The bundle's `original_info` for this address is the EOA's info (empty code hash), so `had_code` evaluates to `false`, and `insert_state` takes the "remove account only" branch — it does **not** clear the `(address, slot0)` entry in `storage_cache` that was populated while the short-lived contract executed its `SSTORE`.

The doc comment on `ExecutionCache` explicitly assumes this case cannot leave stale storage: "Since EIP-6780, SELFDESTRUCT only works within the same transaction where the contract was created, so we don't need to handle clearing the storage" [3](#0-2) . That assumption only accounts for the "had code before" branch; it misses the case where an address becomes a contract and is destroyed within a single transaction while never having had code at the *start* of the block, which is precisely the "prefunded CREATE2" incident this test suite is designed to reproduce (per the file's own module doc, referencing a real revm bug of the same shape) [4](#0-3) .

Any subsequent read of that storage slot through the `CachedStateProvider`/`ExecutionCache` (e.g. by a later block's EVM execution, prewarming, or a fresh contract deployed to the same address before the account is otherwise re-touched) would hit the stale `storage_cache` entry containing `0x42` instead of the correct zero value, since the account-level "was destroyed" state is not consulted when serving storage reads — only the flat `(Address, StorageKey)` map is consulted via `get_or_try_insert_storage_with`.

This is the direct analog of the reported "deleted admin can still sign in" bug class: an entity (the storage of a destroyed contract incarnation) that should have been invalidated/deleted remains readable through a cache that was never told to forget it, because the invalidation decision used the wrong point-in-time signal (pre-block code hash instead of "did this transaction ever write code/storage to this address before destroying it").

### Impact Explanation
If a later read of the address's storage (via the execution cache, feeding either a subsequent block's execution, prewarming, or a state provider) returns the stale, pre-destruction storage value instead of the correct post-destruction zero, execution diverges from the serial/full-recompute state. That breaks the equality "cached/prewarmed output must match serial execution / the parent's committed post-state," which can manifest as an incorrect state root for a block built or validated using the polluted cache, or a discrepancy between prewarmed execution and canonical serial execution. Per the rules, a wrong state root or divergence between cached and serial execution is a Critical/High class of bug (consensus split or non-deterministic execution between cached and serial paths).

### Likelihood Explanation
This requires only an unprivileged transaction sequence reachable by any user: fund an address (no privilege needed), then deploy-and-selfdestruct a contract at that address via `CREATE2` in a single transaction (a standard, well-known EIP-6780 pattern that stores to storage before self-destructing). The repository's own e2e test (`prefunded_create2_selfdestruct`) constructs this exact scenario, confirming it is a realistic and directly reachable code path, though that specific test does not currently assert on the storage-cache's internal state (it only checks RPC-visible values after re-touching the account), so the residual stale cache entry is not caught by existing coverage.

### Recommendation
In `ExecutionCache::insert_state`, base the storage-invalidation decision not just on `original_info`'s code hash, but also account for whether the account had non-empty storage at any point during the current bundle (i.e., check `account.storage` non-emptiness or track whether the account ever had code during this transaction/bundle, not just at block-start). Safer options:
- Always clear the specific address's storage-cache entries when `was_destroyed()` is true and `account.storage` is non-empty, regardless of `original_info`'s code hash.
- Or, conservatively, always do a full/partial storage invalidation for `addr` on any `Destroyed` status instead of relying solely on the pre-block code hash heuristic.

### Proof of Concept
1. In an earlier block, send ETH to `destroyed = create2_address(salt, initcode)` where `initcode` is `selfdestruct_initcode(target)` (stores `0x42` at slot 0, then `SELFDESTRUCT`) — this makes `destroyed` a plain funded EOA with empty code hash.
2. In a later block, call the `CREATE2` factory to deploy `initcode` to `destroyed` (same tx creates and self-destructs, satisfying EIP-6780). During execution, `SSTORE` writes `0x42` to slot 0 at `destroyed`, and this write is populated into `ExecutionCache::storage_cache` via `CachedStateProvider`/prewarming.
3. `ExecutionCache::insert_state` processes the bundle: `account.was_destroyed() == true`, `original_info` (the EOA) has empty code hash ⇒ `had_code == false` ⇒ only `account_cache.remove(destroyed)` is called; `storage_cache` entry for `(destroyed, slot0)` is left as `0x42`.
4. Before anything else repopulates or invalidates `storage_cache` for that address (e.g. reading storage through the cached provider path, such as a subsequent block referencing this address's storage without a full account rewrite that reuses the same cache instance), a query for slot 0 of `destroyed` through the execution cache returns the stale `0x42` instead of `0` — diverging from the true post-destruction state that a full/serial recompute would produce.
   (Verifying the divergence to end-to-end RPC output was not conclusively traced within the available context/iterations; the existing e2e test only checks RPC-visible values after an additional plain transfer re-touches the account, which happens to repopulate `account_cache` but does not exercise a direct storage read against the stale cache entry. This residual uncertainty should be validated in a live environment by directly querying `ExecutionCache.storage_cache` state or `eth_getStorageAt` immediately after step 3, before any account-level repopulation, to confirm exploitability end-to-end.)

/// The incident reproducer: an address is prefunded in an earlier block, then a
/// contract is `CREATE2`-deployed there whose initcode selfdestructs. The account had prior
/// state, so its deletion must be represented correctly all the way into the persisted trie.
async fn prefunded_create2_selfdestruct<P: Provider>(ctx: &mut SuiteCtx<P>) -> eyre::Result<()> {
    let initcode = selfdestruct_initcode(beneficiary(1));
    let destroyed = ctx.create2_address(salt(1), &initcode);

    let receipts = ctx.mine_block(vec![transfer_tx(destroyed, eth_tenths(10))]).await?;
    assert_eq!(ctx.balance(destroyed).await?, eth_tenths(10));
    // EIP-7708: plain transfers emit a transfer log once Amsterdam is active
    assert_eq!(
        !receipts[0].inner.logs().is_empty(),
        ctx.fork >= EthereumHardfork::Amsterdam,
        "transfer log emission must match EIP-7708 activation"
    );

    ctx.mine_block(vec![factory_create_tx(ctx.factory, false, salt(1), &initcode, eth_tenths(5))])
        .await?;

    assert_eq!(ctx.slot0(ctx.factory).await?, address_word(destroyed), "creation should succeed");
    ctx.assert_destroyed(destroyed, "prefunded create2").await?;
    assert_eq!(ctx.balance(beneficiary(1)).await?, eth_tenths(15));
    // the account existed in the database before this block, so the bundle must mark it as
    // destroyed with no post-block info
    let account = ctx.bundle_account(destroyed).expect("prefunded account must be in the bundle");
    assert!(account.was_destroyed(), "prefunded create2: bundle must mark account destroyed");
    assert!(account.info.is_none(), "prefunded create2: destroyed account must have no info");

    // touching the address again must start from a clean account
    ctx.mine_block(vec![transfer_tx(destroyed, eth_tenths(3))]).await?;
    assert_eq!(ctx.balance(destroyed).await?, eth_tenths(3), "old balance must not resurface");
    assert!(ctx.provider.get_code_at(destroyed).await?.is_empty());

    Ok(())
}
