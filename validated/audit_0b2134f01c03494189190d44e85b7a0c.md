### Title
Wallet Contract `has_in_flight_tx` flag can be permanently stuck at `true`, freezing the account, if any private callback receipt fails/reverts - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (`WalletContract`) uses a `has_in_flight_tx` boolean to serialize execution of RLP-encoded Ethereum-style transactions: `rlp_execute` refuses new work whenever the flag is `true`, and every promise chain it creates ends in a `#[private]` callback that is supposed to reset the flag to `false` before returning a final `ExecuteResponse`. This mirrors the reported `emergencyResume`/`afterDepositCancellation` bug class: a state machine sets a "busy" flag before dispatching an asynchronous continuation, and assumes that continuation will always run to completion and clear the flag — but NEAR's own execution model allows that assumption to be violated.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` immediately before returning a `Promise` [1](#0-0) . The only places that ever reset the flag to `false` are the tops of the `#[private]` callbacks `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, and `ban_relayer` [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) . The struct's own doc comment states the exact invariant being relied upon: "`has_in_flight_tx` must be `true` when a mutable method ... returns a promise and `false` otherwise" [6](#0-5) .

This is an assumption of success identical to the reported bug: the flag-clearing statement is the *first* line of each callback function, so it is only durable if that callback's receipt completes successfully. But per nearcore's core execution semantics, "a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting" [7](#0-6) , and concretely, "Commit or rollback: success commits with `ReceiptProcessing`; failure calls `state_update.rollback()`, discarding all state changes from the receipt" [8](#0-7) . If any of these callback receipts itself fails (e.g. exhausts its attached static gas doing string formatting/refund-promise creation, or panics on an unanticipated code path such as the "Invariant violation" branch in `rlp_execute_callback` when `n > 1` promise results are observed [9](#0-8) , or panics inside `env::promise_batch_create`/`env::promise_batch_action_transfer` for the caller-deposit refund), the `has_in_flight_tx = false` write at the top of that function is rolled back along with everything else in the receipt.

Because `rlp_execute` is the sole external entry point and it unconditionally rejects any call while `has_in_flight_tx == true` [10](#0-9) , and there is no other method in the contract capable of clearing the flag from outside the failed promise chain, the account becomes permanently unable to execute any further RLP/Ethereum-style transaction. This is functionally identical to the reported vault scenario: an assumed-success continuation is the only path back to a usable state, and if that specific continuation ever reverts, the resource (vault liquidity / wallet's transaction capability and any assets only reachable through it) is permanently locked with no recovery path.

### Impact Explanation
Any single submitted RLP transaction to `rlp_execute` (by the account owner, or a relayer holding a function-call access key on this account) reaches this code path. If the terminal private callback for that transaction fails, the wallet contract's `has_in_flight_tx` invariant breaks and stays `true` forever. From that point:
- The account can never again call `rlp_execute` — every subsequent call returns `"transaction already in progress, please try again later."` regardless of how much time passes, since nothing ever clears the flag [10](#0-9) .
- Since this contract is the intended sole interface for eth-implicit accounts to move value/perform actions (base-token transfers, NEP-141 transfers, key management), this constitutes a permanent freeze of funds/functionality controlled by that account — matching the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
The likelihood hinges on causing the specific terminal callback receipt (not the outer `rlp_execute` receipt, and not the inner target-contract call) to fail while the earlier stage(s) of the promise chain already completed and consumed the account's one "in-flight" slot. Because the callback's own logic is minimal (JSON parsing already guarded with `match`/`Err` branches, not panics), the most plausible trigger is the explicit self-detected invariant violation in `rlp_execute_callback` when `promise_results_count() > 1` [9](#0-8)  — note that branch currently *returns* a failure `ExecuteResponse` rather than panicking, so it does NOT trigger the lock by itself; the exploitable gap is any other, currently-unenumerated panic surface inside the private callbacks (e.g., a caller-supplied `receiver_id`/`account_id` producing a malformed batch action, or gas math edge cases as protocol fees change). The report itself documents this as a real design fragility via its own invariant comment, indicating the developers were aware this could be broken but did not add a recovery mechanism.

### Recommendation
Do not rely on the callback receipt succeeding to reset `has_in_flight_tx`. Options:
- Reset `has_in_flight_tx = false` in a step that is guaranteed to commit independent of the callback's success (e.g., have the *scheduling* receipt register a fallback/timeout mechanism, or split flag-clearing into its own always-succeeding action).
- Add an explicit recovery/reset method (e.g., admin-free timeout-based unlock, analogous to allowing `emergencyResume` to be retried) that lets the account owner clear a stuck `has_in_flight_tx` flag after some block-height/timeout has elapsed, without requiring the original failed callback to have committed.
- Audit and eliminate all panic surfaces inside `address_check_callback`, `nep_141_storage_balance_callback`, and `rlp_execute_callback`, and ensure static gas allocations are provably sufficient under all valid inputs so the callback can never itself fail before clearing the flag.

### Proof of Concept
1. Submit a `rlp_execute(target, tx_bytes_b64)` call whose parsed action routes through a multi-step promise chain ending in `rlp_execute_callback` (e.g. an ERC-20 transfer needing `storage_deposit`, chained via `nep_141_storage_balance_callback` → `action_to_promise` → `.then(ext.rlp_execute_callback(...))`) [11](#0-10) .
2. Craft inputs (e.g. `caller_deposit` with an account id/amount combination, or conditions causing `env::promise_batch_action_transfer` in the `Failed` branch of `rlp_execute_callback`) that cause the final callback receipt itself to fail/panic, after the earlier steps (which already set `has_in_flight_tx = true`) have committed.
3. Observe that the callback receipt's `Err` result rolls back its `self.has_in_flight_tx = false` write per nearcore's per-receipt rollback semantics [8](#0-7) .
4. Call `rlp_execute` again and observe it is permanently rejected with `"transaction already in progress, please try again later."`, with no method available to clear the flag — reproducing the same class of stuck state described in the `emergencyResume`/`afterDepositCancellation` report, but here freezing the wallet contract's transaction capability indefinitely.
