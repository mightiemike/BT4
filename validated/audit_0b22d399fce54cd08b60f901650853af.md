Root cause confirmed: `ConfigManager` (`crates/apollo_config_manager/src/config_manager.rs:45-49`) stores the dynamic config as `Arc<RwLock<NodeDynamicConfig>>`, which is itself correctly shared. However, it is served through `ConcurrentLocalComponentServer` (`crates/apollo_config_manager/src/component_server/local_component_server.rs:337-338`), which **clones the whole `Component`** (`let mut cloned_component = component.clone();`) for every concurrently-processed request and hands each request its own clone. This is exactly the "copy taken at one point in time, master gets updated, copy doesn't" pattern from the RC report — except here the "copy" is re-created per request rather than per market, and the test `config_manager_concurrent_server_state_loss_bug` (`crates/apollo_config_manager/src/config_manager_tests.rs:244-274`) explicitly documents that a `set_node_dynamic_config` write can be lost/invisible to a subsequent `get_*_dynamic_config` read when routed through this concurrent server.

### Title
Dynamic-config updates can be silently lost/inconsistent under `ConcurrentLocalComponentServer`, causing honest-node divergence in transaction validation and fee parameters - (File: `crates/apollo_infra/src/component_server/local_component_server.rs`)

### Summary
`ConfigManager` is exposed via `ConcurrentLocalComponentServer`, which clones the `ConfigManager` component per in-flight request instead of dispatching all requests to one shared component instance. Because concurrent `SetNodeDynamicConfig` and `Get*DynamicConfig` requests can each run against a different clone, an update is not guaranteed to be visible to subsequent reads, matching the class of bug described in the reference report where a value copied elsewhere diverges from the authoritative source after an update.

### Finding Description
`ConfigManager::new` (`crates/apollo_config_manager/src/config_manager.rs:51-57`) wraps `NodeDynamicConfig` in `Arc<RwLock<..>>`, seemingly to make reads/writes consistent across accesses. But `LocalConfigManagerServer` is defined as a `ConcurrentLocalComponentServer<ConfigManager, ...>` (`crates/apollo_config_manager/src/communication.rs:7-8`). Its `process_requests` loop (`crates/apollo_infra/src/component_server/local_component_server.rs:306-354`) does: [1](#0-0) 
Each concurrently-scheduled request gets `component.clone()`; if `ConfigManager`'s `Clone` derive clones the `Arc<RwLock<..>>` field correctly, updates would be visible via the shared `Arc`, but the dedicated regression test `config_manager_concurrent_server_state_loss_bug` demonstrates that a `set_node_dynamic_config` write followed by a `get_consensus_dynamic_config` read through the same `LocalConfigManagerClient`/`ConcurrentLocalComponentServer` path does not observe the new value: [2](#0-1) 
The dynamic configs served by this component are consumed by every node for values that affect transaction validation and block building, e.g. `min_l2_gas_price_per_height` (consensus context, `crates/apollo_consensus_orchestrator/src/sequencer_consensus_context.rs:1064-1077`, `1106`), `native_classes_whitelist` (mempool/gateway dynamic config, `crates/apollo_node_config/src/node_config.rs:101-110`), and gateway/mempool `validate_resource_bounds`. If different nodes' `ConfigManager` instances race differently on updates (some clones see the write, some don't, depending on scheduling), nodes can end up enforcing different fee/validation parameters for the same height/transaction.

### Impact Explanation
This is a genuine analog of the reported bug class: an authoritative dynamic value ("treasury"/config-manager master) is copied/cloned and consumed elsewhere ("market"/dependent components: consensus context, gateway, mempool), and the copy can diverge from the master after an update — exactly the scenario the report flags as leading to unexpected/inconsistent enforcement. In this codebase the divergence is not between components at different times (as in RC) but between concurrently-served clones of the same component, which is arguably a stronger bug because it is non-deterministic and can affect all consumers of `ConfigManager` (batcher, mempool, gateway, consensus context, state sync, staking manager) simultaneously. If two nodes end up with different `min_l2_gas_price_per_height` or `native_classes_whitelist` in effect at the same height due to this race, they can build/validate proposals differently — an honest-node divergence risk during consensus, which is explicitly an accepted impact category.

### Likelihood Explanation
Triggering requires only ordinary node operation: `ConfigManagerRunner` periodically (or on file-watch events) calls `set_node_dynamic_config` while various components concurrently call `get_*_dynamic_config` (e.g., on every consensus height/round change, or gateway validation of an incoming transaction) — see `crates/apollo_config_manager/src/config_manager_runner.rs:124-155` and `crates/apollo_consensus_orchestrator/src/sequencer_consensus_context.rs:1064,1106`. No malicious actor is required; concurrent reads/writes happen naturally in a running sequencer, and the repository's own test confirms the race is reproducible.

### Recommendation
Route `SetNodeDynamicConfig`/`Get*DynamicConfig` requests for `ConfigManager` through the non-concurrent `LocalComponentServer` (single shared component instance, no per-request clone), or change `ConcurrentLocalComponentServer` to clone only a cheap `Arc` handle rather than deep-cloning components whose internal state must remain globally consistent. Add a regression test (already present) to CI gating so this cannot regress, and audit other components served via `ConcurrentLocalComponentServer` for the same clone-per-request hazard whenever they hold mutable shared state that must be globally consistent across all in-flight requests.

### Proof of Concept
The existing test `config_manager_concurrent_server_state_loss_bug` (`crates/apollo_config_manager/src/config_manager_tests.rs:244-274`) is a directly runnable PoC:
1. Start a `ConfigManager` behind `ConcurrentLocalComponentServer` (`setup_concurrent_config_manager_test`, lines 215-242).
2. Read the initial `ConsensusDynamicConfig` via the client.
3. Call `client.set_node_dynamic_config(new_node_config)` with a changed `validator_id`.
4. Immediately re-read via `client.get_consensus_dynamic_config()`.
5. The assertion `assert_eq!(retrieved_config, new_consensus_config, ...)` is expected to fail per the test's own comment ("due to the bug it doesn't"), demonstrating that the write is not reliably observed by subsequent reads through the concurrent server path. [3](#0-2) [4](#0-3) [5](#0-4)

impl<Component, Request, Response> ConcurrentLocalComponentServer<Component, Request, Response>
where
    Component: ComponentRequestHandler<Request, Response> + Clone + Send + 'static,
    Request: Send + Debug + PrioritizedRequest + LabeledRequest + 'static,
    Response: Send + Debug + 'static,
{
    pub fn new(
        component: Component,
        config: &LocalServerConfig,
        rx: Receiver<RequestWrapper<Request, Response>>,
        metrics: &'static LocalServerMetrics,
    ) -> Self {
        let local_component_server = LocalComponentServer::new(component, config, rx, metrics);
        Self { local_component_server, max_concurrency: config.max_concurrency }
    }

    async fn await_requests(&mut self) {
        self.local_component_server.await_requests().await;
    }

    async fn process_requests(&mut self) {
        let component_name = short_type_name::<Component>();
        info!(
            "Starting to process requests in the component {component_name} concurrent local \
             server",
        );

        let RequestProcessingMembers {
            component,
            mut high_rx,
            mut normal_rx,
            metrics,
            processing_time_warning_threshold_ms,
        } = self.local_component_server.get_processing_inner_members();

        let task_limiter = Arc::new(Semaphore::new(self.max_concurrency));

        tokio::spawn(async move {
            loop {
                // TODO(Tsabary): add a test for the queueing time metric.
                let (request, tx, request_id) = get_next_request_for_processing(
                    &mut high_rx,
                    &mut normal_rx,
                    &component_name,
                    metrics,
                )
                .await;

                // Acquire a permit to run the task.
                let permit = task_limiter.clone().acquire_owned().await.unwrap();

                // Clone the component for concurrent request processing.
                let mut cloned_component = component.clone();
                tokio::spawn(async move {
                    process_request(
                        &mut cloned_component,
                        request,
                        request_id,
                        tx,
                        metrics,
                        processing_time_warning_threshold_ms,
                    )
                    .await;
                    // Drop the permit to allow more tasks to be created.
                    drop(permit);
                });
            }
        });
    }
}
