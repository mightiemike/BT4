## Title
`ensure_match_transaction_info` skips state-checkpoint hash validation, allowing replay/execution divergence to go undetected - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the core invariant used to confirm that a locally re-executed/re-derived `TransactionOutput` matches an authenticated `TransactionInfo` (i.e., a transaction info that has already been proven against a ledger-info-signed accumulator root). It checks status, gas used, write-set hash, and event root hash, but it explicitly does **not** check `state_checkpoint_hash` (the state/hot-state Merkle root) or `position_state_checkpoint_hash`. This mirrors the reported TWAP bug's structure: a function whose name and call sites imply it performs a real integrity comparison, but whose actual computation omits the one check that matters, making it pass regardless of the state a divergent execution produced.

### Finding Description
`ensure_match_transaction_info` compares locally computed values (status, gas, write-set hash, event root hash) against the fields of a `TransactionInfo` that was already authenticated via `TransactionAccumulatorProof`/ledger info signatures: [1](#0-0) 

The function's own comment discloses the gap directly: [2](#0-1) 

This function is used in two integrity-relevant contexts:
1. Chunk executor's `verify_execution`, which re-executes transactions during (lazy) execution verification / replay and compares each output to the target `TransactionInfo`: [3](#0-2) 
2. `aptos-debugger`'s replay/mismatch tooling, which uses the same comparator to decide whether replayed execution matches the historical chain: [4](#0-3) 

Because the comparator never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a re-execution that produces an identical write set, event root, gas, and status, but a **different resulting state tree** (e.g., due to a bug in state summary/Jellyfish Merkle update logic, a hot-state or "trading-native"/position-state root computation bug, or a hard-fork-only divergence in how the state tree is built from the same write set) would still pass `ensure_match_transaction_info`. The state root is only meant to be checked elsewhere (accumulator proof over `TransactionInfo`, and the state-checkpoint computation path in `do_state_checkpoint.rs`), but the whole point of `ensure_match_transaction_info` in the replay/verify-execution path is to catch exactly this class of divergence when *re-deriving* the output rather than trusting a proof chain.

The bug-class parallel to the TWAP finding is precise: like `validatePrice()` claiming to compute a TWAP but algebraically collapsing to the spot price (i.e., dropping the one term that would make the check meaningful), `ensure_match_transaction_info` claims ("does not match TransactionInfo") to validate output-to-info consistency but omits comparison of exactly the field (`state_checkpoint_hash`) whose divergence is the paradigm case of a state-integrity break.

### Impact Explanation
If a state-checkpoint/state-root computation bug or hard-fork-only divergence exists anywhere in the state-summary path (hot state, position/"trading-native" state, or regular state root), replay-verification and chunk-execution-verification tooling built on `ensure_match_transaction_info` would not detect it, because this comparator is the terminal invariant check for those flows. This could let a corrupted or divergent state root be accepted as "matching" during backup/replay verification (`db-tool replay-verify`) or during a chunk-executor `verify_execution` pass, which is squarely in scope under "Replay paths and restore helpers must not reinterpret committed data into a different ledger state" and "Hard-fork-only divergence during commit, replay, restore, or proof verification."

However, I could not confirm within the available context that this comparator is the *sole* gate for the affected code paths, nor could I fully verify (within tool-call limits) whether `compute_trading_native_state_roots`/`hot_state_root_in_txn_info` are enabled on mainnet today, or whether a separate, independent state-root check exists elsewhere in the `verify_execution` call chain that would still catch such divergence. The comment in the code itself frames this as a known, pre-existing gap to be closed "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS" — i.e., the Aptos developers are already aware of this exact gap and gate the affected state-root type (position/trading-native state) behind that feature flag, which appears to not yet be broadly enabled. That significantly weakens the case that this is an actively exploitable, high/critical, unprivileged mainnet vulnerability today, as opposed to a documented incompleteness in an unreleased feature.

### Likelihood Explanation
Low-to-moderate today: the gap is self-documented as intentional/known and tied to a feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that is guarded and, per the comment, not yet safe to enable for this very reason. For the plain `state_checkpoint_hash` (non-trading-native) case, I was not able to fully confirm (within iteration limits) whether other code paths independently re-validate the state root wherever `ensure_match_transaction_info` is relied upon as the terminal check, so I cannot assert this is currently exploitable on mainnet with full confidence.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when known/applicable) against the locally computed roots, consistent with how write-set and event-root hashes are already validated, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any dependent state-root feature) is enabled. Add regression tests asserting that a re-execution producing a divergent state root — with identical write set/events/gas/status — is rejected by this comparator.

### Proof of Concept
Not independently verified end-to-end due to tool-call limits: I confirmed the exact missing checks via source inspection (see citations above) and its two call sites, but did not construct or run a concrete divergent-state-root replay scenario to empirically demonstrate the bypass, and could not confirm the on-chain/default status of `compute_trading_native_state_roots`/`hot_state_root_in_txn_info` flags to establish current mainnet exploitability. Given the code's own acknowledgment of this gap and the inability to confirm an independently-exploitable, currently-live path, I present this with reduced confidence rather than as a fully proven Critical/High finding.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
