## Confirmation

Default disk-index drives fall back to `TempDir::new()` (system temp dir, e.g. `/tmp`) when no explicit `--accounts-index-path` is configured [1](#0-0) , and even when explicitly configured the on-disk bucket files are opened without `O_EXCL`/`create_new` semantics.

### Title
Disk-backed AccountsIndex bucket files opened with non-atomic `create(true)` allow pre-planted file to be silently adopted (TOCTOU) - (File: bucket_map/src/bucket_storage.rs)

### Summary
`BucketStorage::map_open_file` opens/creates on-disk index bucket files using `OpenOptions::new().read(true).write(true).create(create).open(&path)` rather than `create_new(true)` [2](#0-1) . This mirrors the reported EthStaker bug class: a file is created/opened and then unconditionally treated as fresh storage (its length is forced with `set_len` and it is mmapped), without verifying that the path didn't already exist as an attacker-controlled file.

### Finding Description
`BucketStorage::new_map` picks a bucket file path as `drives[random_drive].join(random_u128)` and calls `map_open_file(file, true, bytes, stats)` [3](#0-2) . Inside `map_open_file`, the file is opened with `.create(create)` (not `.create_new(true)`), so if a file already exists at that path when the daemon tries to create it, `open()` succeeds against the *existing* file instead of failing [4](#0-3) . The code then calls `data.set_len(create_bytes)` (which only grows/truncates, but does not zero pre-existing bytes below that length) and immediately memory-maps the file to be used as raw `IndexBucket`/`DataBucket` element storage, trusting the on-disk bytes as valid occupancy bitmaps and index entries [5](#0-4) .

This is the exact pattern flagged in the report: "creating a file with themselves as the owner before [the process] writes to the path" leads to attacker-controlled content being adopted as trusted storage, because the create call is not atomic/exclusive (`O_EXCL`-equivalent).

By contrast, `AppendVec::new` (which stores raw account bytes on disk) correctly uses `OpenOptions::new().create_new(true)` [6](#0-5) , and the bucket-map's own `Restart::new_map` (used for the restart-persistence file) also correctly uses `create_new(true)` [7](#0-6) . Only `BucketStorage::map_open_file`, which backs the actual index/data buckets, is missing this protection.

### Impact Explanation
If an attacker (any local unprivileged user with write access to the configured/default bucket-map drive directory — including the default `TempDir` fallback under `/tmp`) can pre-create a file at the (randomly named, but attacker-writable-directory-dependent) path before the validator creates its bucket file, the validator will adopt that file as live `IndexBucket`/`DataBucket` storage. Because `BucketOccupied::is_free`/`occupy` and `IndexEntry` interpretation trust raw bytes read straight from the mmap without validation [8](#0-7) , attacker-controlled bytes can be interpreted as valid occupancy/refcount/pubkey-to-storage-offset entries in the accounts index. This can corrupt the secondary (disk) accounts index used to resolve pubkey → `AppendVec` offset lookups, producing stale or wrong-version account loads and hash/capitalization divergence versus other honest nodes that use a purely in-memory index or a freshly created bucket file.

### Likelihood Explanation
Exploitability is gated on: (1) the bucket-map drive directory being writable by an unprivileged local attacker (true by default when no `--accounts-index-path` is set, since it falls back to the shared system temp directory), and (2) the attacker being able to predict or race the randomly-generated 128-bit file name before the validator's `create()` call. The random name (`rng().random_range(0..u128::MAX)`) makes blind guessing infeasible, so practical exploitation likely requires either a misconfigured world-writable index directory shared with other processes/users, or some other primitive to observe/predict the generated name. This bounds likelihood to configuration-dependent, moderate-difficulty scenarios rather than a trivially remote-triggerable bug — consistent with the original report's own "High difficulty / Configuration" classification.

### Recommendation
Change `BucketStorage::map_open_file` to use `OpenOptions::new().read(true).write(true).create_new(true)` (mirroring `AppendVec::new` and `Restart::new_map`) when creating a fresh bucket file, and treat any resulting `AlreadyExists` error as fatal (regenerate a new random name / bail) instead of silently opening a pre-existing file. This closes the TOCTOU window described in the report and centralizes safe-create semantics across all AccountsDB/bucket-map file-creation call sites, consistent with the report's "centralize file creation" long-term recommendation.

### Proof of Concept
1. Configure the validator with `--accounts-index-path` pointing at a directory writable by another local user (or rely on the default `/tmp`-based `TempDir` fallback in a shared/multi-tenant environment).
2. As the attacker, create a file at a guessed/observed path inside that directory containing crafted bytes that decode as a plausible `IndexBucket`/`DataBucket` header plus fabricated `IndexEntry` records (attacker-chosen pubkey → arbitrary `AccountInfo`/offset mapping), sized to match `cell_size`.
3. Trigger validator startup or an index bucket grow/resize (`BucketStorage::new_with_capacity` → `new_map`) so it selects that same path.
4. Observe that `map_open_file` opens the pre-existing attacker file (via `.create(true)` rather than `.create_new(true)`), `set_len` extends it, and it is mmapped and used directly as bucket storage, causing the accounts index to be built with attacker-controlled entries [2](#0-1) .
