### Title
`DbStateView::get` silently skips proof verification on read error and returns an unverified value from a separate, non-atomic DB read - (File: `storage/storage-interface/src/state_store/state_view/db_state_view.rs`)

### Summary
`DbStateView::get` is supposed to serve state reads that are checked against a trusted state root (`maybe_verify_against_state_root_hash`), similarly to how `sellVotes()` should have been bound to a caller-verified expected outcome. Instead, the verification call and the value-returning call are two independent DB queries, and verification failures are swallowed rather than propagated.

### Finding Description [1](#0-0) 

```
fn get(&self, key: &StateKey) -> StateViewResult<Option<(Version, StateValue)>> {
    if let Some(version) = self.version {
        if let Some(root_hash) = self.maybe_verify_against_state_root_hash {
            if let Ok((value, proof)) =
                self.db.get_state_value_with_proof_by_version(key, version)
            {
                proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
            }
        }
        Ok(self
            .db
            .get_state_value_with_version_by_version(key, version)?)
    } else {
        Ok(None)
    }
}
```

Two independent invariant breaks are visible:
1. `if let Ok((value, proof)) = self.db.get_state_value_with_proof_by_version(...)` discards the `Err` branch instead of propagating it. If the proof-bearing read errors (e.g., pruned range, transient storage error), verification is skipped entirely — no error surfaces to the caller — yet the function proceeds to the second call and returns a value as though it had been authenticated against `root_hash`.
2. Even in the success path, the value actually verified by `proof.verify(...)` comes from `get_state_value_with_proof_by_version`, while the value actually *returned* to the caller comes from a second, separate call `get_state_value_with_version_by_version`. These are not the same read operation, so nothing in this code guarantees the two calls observe the same underlying state (e.g., across pruning or a concurrent state update between the two DB accesses).

This is constructed via `VerifiedStateViewAtVersion::verified_state_view_at_version`, which sets `maybe_verify_against_state_root_hash` to the `state_checkpoint_hash` bound to a specific ledger version after verifying a `TransactionWithProof` against a `LedgerInfo`: [2](#0-1) 

### Impact Explanation
If this path is reachable with attacker- or fork-adjacent conditions (e.g., during pruning races or transient read errors), a state value returned from a nominally "verified" state view could be unbound from the proof-verified root, meaning code trusting `DbStateView` as an authenticated state view could observe state that was never actually checked against `root_hash`. This matches the "authenticated API or state-view output bound to the wrong version/root" impact category. However, I could not confirm from the available snippets whether this state view is used on a security-critical mainnet path (e.g., serving RPC/API proofs or feeding into VM execution) versus only test/tooling code — the only confirmed caller I found was in `execution/executor-test-helpers`, which is a test helper crate, not a production path.

### Likelihood Explanation
Low-to-moderate confidence overall. The bug pattern (silently discarding a fallible verification, and splitting "verify" and "read" into two non-atomic calls) is real in the code as shown, but:
- I was not able to fully confirm all production call sites of `verified_state_view_at_version` / `DbStateView` due to tool failures in this final iteration.
- It's unclear whether `get_state_value_with_proof_by_version` and `get_state_value_with_version_by_version` can actually diverge in practice (e.g., whether the underlying DB guarantees snapshot consistency across the two reads via MVCC/versioned storage, which would make this theoretical rather than exploitable).

### Recommendation
- Propagate errors from `get_state_value_with_proof_by_version` instead of silently ignoring them via `if let Ok(...)`.
- Fetch the value once (from the proof-bearing call) and reuse that same value both for verification and for the return path, rather than issuing a second independent DB read.

impl VerifiedStateViewAtVersion for Arc<dyn DbReader> {
    fn verified_state_view_at_version(
        &self,
        version: Option<Version>,
        ledger_info: &LedgerInfo,
    ) -> StateViewResult<DbStateView> {
        let db = self.clone();

        if let Some(version) = version {
            let txn_with_proof =
                db.get_transaction_by_version(version, ledger_info.version(), false)?;
            txn_with_proof.verify(ledger_info)?;

            let state_root_hash = txn_with_proof
                .proof
                .transaction_info
                .state_checkpoint_hash()
                .ok_or_else(|| StateViewError::NotFound("state_checkpoint_hash".to_string()))?;

            Ok(DbStateView {
                db,
                version: Some(version),
                maybe_verify_against_state_root_hash: Some(state_root_hash),
            })
        } else {
            Ok(DbStateView {
                db,
                version: None,
                maybe_verify_against_state_root_hash: None,
