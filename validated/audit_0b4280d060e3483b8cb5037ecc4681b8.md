## No vulnerability found for this question.

**Rationale:**

The premise of the question — that `poison_recipient_opt` resolution depends on "local mempool/report visibility" that could differ between two nodes observing the *same* fork — is incorrect. Tracing the actual data flow:

1. `find_mature_miner_rewards` computes `poison_recipient_opt` by calling `StacksChainState::get_poison_microblock_report(clarity_tx, reward_height)`, which reads from the Clarity DB via `clarity_tx.with_clarity_db_readonly(|db| db.get_microblock_poison_report(height))`. [1](#0-0) [2](#0-1) 

2. This is not mempool data — it is MARF-committed consensus state. The report is only written by `handle_poison_microblock`, which executes as part of processing a `TransactionPayload::PoisonMicroblock` transaction that was included in an actual, already-mined Stacks block (via `StacksChainState::process_transaction` → `clarity_tx.run_poison_microblock`). [3](#0-2) [4](#0-3) 

3. Because `get_poison_microblock_report` is keyed to a specific block height and reads from the MARF as of the currently-processing `clarity_tx` state (which incorporates the full, agreed-upon block history up to that point), any two nodes that have accepted and processed the identical sequence of blocks up to and including `reward_height` will read back the identical `(reporter, seq)` tuple — deterministically, by construction of the MARF. There is no "unconfirmed mempool visibility" input to this read path; the poison report only exists in the Clarity DB if a specific block containing the PoisonMicroblock transaction was already validated and committed.

4. An attacker filing a poison report that "is visible on fork A but not fork B" only matters if the actual block containing that transaction is present in fork A but absent in fork B. In that case, forks A and B are, by definition, different blocks with different transaction sets — which is ordinary, expected blockchain fork divergence (each fork has its own valid, internally-consistent, reproducible state root). This is not a bug: two nodes that are following different forks are *expected* to have different state; two nodes following the *same* fork (same `StacksBlockId` history) will always compute identical `poison_recipient_opt` and identical rewards, because the computation is a pure deterministic function of already-committed MARF state, not of local node mempool contents.

There is no code path in `accounts.rs` or `transactions.rs` where two nodes agreeing on the same tip/fork can disagree on `poison_recipient_opt`, so the claimed equality break does not occur under the stated attacker model (unprivileged, non-majority). No further action needed.
