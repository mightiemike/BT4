## Title
Wall-clock–bounded Clarity analysis timeout in block-proposal validation causes signers to reach non-deterministic accept/reject verdicts on the same block - ([File: stackslib/src/net/api/postblock_proposal.rs])

## Summary
The PocketMine-MP advisory describes a bug class where processing a single attacker-supplied payload consumes CPU time in a way that isn't bounded by a deterministic, reproducible metric, letting variable server load/hardware determine how much damage is done. The reachable analog here is the new **wall-clock** `block_proposal_max_tx_analysis_time_secs` budget used during Nakamoto block-proposal validation: unlike the Clarity runtime cost tracker (a deterministic, hardware-independent metric), this check is keyed to `Instant::now()`, so the exact same block proposal, containing the exact same transaction, can be accepted by a fast/idle signer node and rejected as "problematic" by a slow/loaded signer node.

## Finding Description
`NakamotoBlockProposal::validate` computes per-tx deadlines from wall-clock `Instant`s: `block_deadline`, `per_tx_max_execution_time`, and `per_tx_max_analysis_time` are all `Instant`/`Duration`-based budgets fed into `TransactionResourceBudgets` [1](#0-0) . As each transaction is processed, `builder.try_mine_tx_with_len` is invoked with these budgets, and if a transaction's Clarity contract-analysis phase does not complete before its wall-clock deadline, the transaction is classified `TransactionResult::Problematic`, and the *entire block* is rejected with `ValidateRejectCode::ProblematicTransaction` [2](#0-1) .

This mechanism, and the analogous miner-side `max_analysis_time_secs`, is explicitly documented as being independent of the consensus-critical replay/execution path: "A transaction whose analysis exceeds the deadline is treated as problematic (deterministic replay and block commit remain unbounded)" [3](#0-2) . The corresponding config defaults are `DEFAULT_BLOCK_PROPOSAL_MAX_TX_ANALYSIS_TIME_SECS = 30` and `DEFAULT_BLOCK_PROPOSAL_MAX_TX_EXECUTION_TIME_SECS = 30` [4](#0-3) , and the check fires purely on wall time relative to `Instant::now()`, with no correlation to a deterministic Clarity cost unit.

Because the pass/fail decision is a function of real elapsed CPU time rather than a deterministic cost metric, the *same* block proposal containing a tx whose analysis phase is engineered to sit near the 30-second boundary can:
- Complete within budget on a fast, idle signer node → `BlockValidateOk` → the signer signs/approves the block.
- Exceed budget on a slower, more heavily loaded, or busier signer node (e.g. one also serving RPC/mining/other validation work concurrently) → `ValidateRejectCode::ProblematicTransaction` → the signer sends a rejection for that block [5](#0-4) .

This is precisely the equality this design implicitly assumes holds but does not enforce: "every honest signer running correct software reaches the same accept/reject verdict for a given block proposal." The existing tests only demonstrate the deterministic edges of the mechanism (budget set to `0` vs `u64::MAX`), not the realistic near-boundary case where legitimate machine-to-machine variance is the actual attack lever [6](#0-5) .

## Impact Explanation
A single unprivileged miner/transaction-submitter (minority-triggerable, no majority or admin access needed) can craft a contract whose static-analysis/type-checking phase takes an amount of wall-clock time deliberately close to the 30s default budget (e.g., via deeply nested or combinatorially complex types that are known to blow up analysis time in typed languages). Submitting this transaction in a block proposal causes some signers to accept and some to reject the identical proposal, splitting the signer set's votes on that specific block. This is a "validation verdict two nodes disagree on" — an in-scope, High-severity analog (temporary tip disagreement / signer-set split), since the same input yields different local verdicts depending on non-consensus factors like hardware speed and concurrent load, rather than a reproducible chain rule.

## Likelihood Explanation
Likelihood is moderate: it requires no special privileges, only a contract whose Clarity type-checking cost is disproportionate to its size/fee, and it depends on natural variance across the signer set's hardware/load, which is expected to exist across any real, decentralized signer set (this is exactly the scenario `block_proposal_max_tx_analysis_time_secs` and `block_proposal_max_tx_execution_time_secs` were introduced to bound, but bounding it with a wall clock reintroduces machine-dependent non-determinism instead of removing it).

## Recommendation
Replace (or supplement) the wall-clock analysis/execution deadlines used in `NakamotoBlockProposal::validate` and in miner assembly with a deterministic, machine-independent cost metric (e.g., an analysis-cost unit derived from the existing Clarity cost tracker, similar to how `ast_parse_cost` is used elsewhere) so that the "problematic" classification for a given transaction is reproducible across all signer nodes regardless of hardware or concurrent load, rather than depending on `Instant::now()`.

## Proof of Concept
1. Deploy/propose a contract whose type-checking phase takes ~28–32 seconds of wall-clock CPU time on typical signer hardware (e.g., deeply nested tuple/list types known to cause super-linear type-checker blowup), keeping it just below the 30s `block_proposal_max_tx_analysis_time_secs` default on fast/idle hardware.
2. Have the miner include this transaction in a block proposal and broadcast it to the signer set as usual.
3. Observe that signers under momentary additional load (e.g., serving other RPC/API requests, or on slower hardware) exceed the wall-clock budget and reject the block via `ValidateRejectCode::ProblematicTransaction` per the code path at [7](#0-6) , while idle/faster signers accept it, matching the divergent-verdict test scaffold already present at [8](#0-7)  but with a realistic near-boundary timing instead of the artificial `0`/`u64::MAX` extremes.

/// Certifies that when a miner proposes a block containing a contract-publish whose
/// **analysis phase** exceeds the node's `block_proposal_max_tx_analysis_time_secs`,
/// the signers **reject** the proposal during validation with `ProblematicTransaction`.
#[test]
#[ignore]
fn signer_rejects_contract_publish_on_analysis_time_expired() {
    if env::var("BITCOIND_TEST") != Ok("1".into()) {
        return;
    }

    let num_signers = 5;
    let sender_sk = StacksPrivateKey::from_seed(&[121; 32]);
    let sender_addr = to_addr(&sender_sk);
    let deploy_fee = 1_000_000;

    info!("------------------------- Test Setup -------------------------");
    let signer_test: SignerTest<SpawnedSigner> = SignerTest::new_with_config_modifications(
        num_signers,
        vec![(sender_addr.clone(), deploy_fee * 10)],
        |_| {},
        |node_config| {
            // Miner builds blocks with no analysis limit, so it WILL include and propose
            // the contract-publish...
            node_config.miner.max_analysis_time_secs = u64::MAX;
            // ...but the node's block-proposal validation (which the signers invoke) bounds
            // per-tx analysis to 0s, so the contract's type-checking phase is already over
            // budget => the tx is Problematic => the proposal is rejected.
            node_config
                .connection_options
                .block_proposal_max_tx_analysis_time_secs = 0;
        },
        None,
        None,
    );

    signer_test.boot_to_epoch_3();

    info!("------------------------- Mine a normal Nakamoto block -------------------------");
    signer_test.mine_nakamoto_block(Duration::from_secs(30), true);

    info!("------------------------- Submit the analysis-gated contract-publish -------------------------");
    let (txid_hex, _deploy_nonce) = signer_test
        .submit_contract_deploy(
            &sender_sk,
            deploy_fee,
            "(define-constant my-const u1)",
            "dummy-analysis",
        )
        .expect("Failed to submit contract deploy");
    let publish_txid = Txid::from_hex(&txid_hex).expect("Failed to parse publish txid");

    info!("------------------------- Ensure signers reject the proposal containing it -------------------------");
    // The miner proposes a block containing the publish; the signers' node
    // validates it with a 0s per-tx analysis budget and rejects the tx as Problematic.
    wait_for(60, || {
        Ok(get_stackerdb_signer_messages()
            .into_iter()
            .any(|(_chunk, message)| {
                let SignerMessage::BlockResponse(BlockResponse::Rejected(rejection)) = message
                else {
                    return false;
                };
                rejection.response_data.failed_txid.as_ref() == Some(&publish_txid)
                    && rejection.response_data.reject_reason
                        == RejectReason::ValidationFailed(
                            ValidateRejectCode::ProblematicTransaction,
                        )
            }))
    })
    .expect(
        "Timed out waiting for signers to reject the contract-publish with ProblematicTransaction \
         (analysis time expired)",
    );

    info!("------------------------- Shutdown -------------------------");
    signer_test.shutdown();
}
