### Title
Sequencer-wide panic (DoS) when loading a declared class whose CASM bytecode segmentation has nesting depth > 1 - ([File: crates/blockifier/src/execution/contract_class.rs])

### Summary
`NestedFeltCounts::new_inner`, used every time a compiled class (CASM) is materialized into a `CompiledClassV1` for execution, hard-asserts that the bytecode segmentation tree has depth ≤ 1. However, the real bytecode-segmentation structure produced by the Sierra→CASM compiler (and consumed elsewhere in the very same codebase, without any depth restriction) is a general `NestedIntList` tree that can legitimately be nested to arbitrary depth. A declared class whose CASM carries a segmentation structure deeper than 1 level causes an unconditional `assert!` panic the moment the class is loaded for use, crashing the sequencer process that is executing/declaring/invoking it.

### Finding Description
`CompiledClassV1`'s constructor builds `bytecode_segment_felt_sizes` from the class's `bytecode_segment_lengths` field: [1](#0-0) 

That structure is built via `NestedFeltCounts::new`, which recurses through `new_inner` and panics as soon as recursion depth exceeds 1: [2](#0-1) 

```
assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");
```

This assumption is false for the general model of bytecode segmentation used elsewhere in the same repo:
- The Starknet OS bytecode-hashing hint builder (`create_bytecode_segment_structure_inner`) handles arbitrarily deep `NestedIntList` trees with no depth limit, and its own test suite explicitly exercises depth-3 nesting: [3](#0-2) [4](#0-3) 
- The generic bytecode-hash routine used for compiled-class-hash computation (`bytecode_hash_node`) is likewise fully recursive with no depth cap: [5](#0-4) 
- Blockifier's own `get_visited_segments` walks `NestedFeltCounts::Node` recursively without any depth restriction: [6](#0-5) 

Only the fee/hash-cost-estimation path (`NestedFeltCounts::new_inner`, feeding `casm_hash_estimation.rs`) artificially restricts nesting to depth 1, and it does so with a hard `assert!`/`panic!` rather than a recoverable error: [7](#0-6) 

Because segmentation is derived from the trusted Sierra→CASM compiler based on the contract's control-flow structure (functions segmented, and functions further segmented by branch, which is exactly the two levels illustrated in the Cairo OS comments: "the bytecode may be divided into functions and each function can be divided according to its branches"), a sufficiently large/branchy—but otherwise valid—Cairo 1 contract can legitimately compile to a CASM class whose `bytecode_segment_lengths` nests beyond depth 1. Declaring (or later invoking) such a class causes the class-loading code path to hit the `assert!` and panic, crashing the sequencer/node process that performs the loading (declare validation/execution, fee estimation, or later invocation of the class).

### Impact Explanation
A panic during class construction is not a recoverable `Result` error — it unwinds/aborts the executing thread/process. Since class loading happens in the hot transaction-processing path (gateway/mempool fee-estimation, blockifier execution of `Declare`/`Invoke`/`DeployAccount`, and Starknet OS re-execution), a single malicious but syntactically valid declared class can repeatedly crash the sequencer whenever any transaction touches it. This is a network-liveness/DoS impact: the sequencer becomes unable to process further transactions until manually restarted, and if the crash recurs deterministically for the offending class (e.g., once it is in mempool/pending state or once any Invoke targets it), the sequencer can be kept persistently unable to confirm new transactions — matching the CVE's own impact class (repeatable crash / complete DoS from an easily reachable path).

### Likelihood Explanation
Reaching this bug requires only submitting one `Declare` transaction (or subsequently invoking the deployed contract) with a class whose compiled bytecode segmentation is nested beyond one level — no special privileges are needed, and the segmentation structure is a natural byproduct of contract size/branching complexity, not an artificially crafted malformed field. The compilation and hashing pipeline elsewhere in the codebase clearly anticipates and supports deeper nesting, confirming this is a realistic, reachable structural case rather than a purely theoretical one.

### Recommendation
Remove the hard depth restriction in `NestedFeltCounts::new_inner` (and its `assert!`) and generalize the CASM-hash-estimation cost model (`estimated_resources_of_bytecode_hash_internal_node_leaf_case` and friends in `casm_hash_estimation.rs`) to handle arbitrarily nested `NestedIntList`/`NestedFeltCounts` trees, mirroring the recursive, depth-agnostic handling already used in `bytecode_hash_node` and `create_bytecode_segment_structure_inner`. At minimum, convert the `assert!`/`panic!` into a recoverable `Result` error that causes the offending declare/class-load to be rejected rather than crashing the process.

### Proof of Concept
1. Author (or compile via the standard Cairo 1 toolchain) a contract whose functions are large/branchy enough that the Sierra→CASM compiler's bytecode segmentation produces a `bytecode_segment_lengths` tree with `NestedIntList::Node` nested at depth ≥ 2 (functions divided into branch-level sub-segments), consistent with the segmentation scheme documented in [8](#0-7) .
2. Submit this class as a `Declare` transaction (or as the class for a `DeployAccount`) through the gateway like any regular user.
3. When the node converts the resulting `VersionedCasm` into `CompiledClassV1` (during declare validation/execution, fee estimation, or when the class is later loaded to execute an `Invoke`), `NestedFeltCounts::new` → `new_inner` panics with `"Only supported for segmentation depth at most 1."`, crashing the executing sequencer process/thread.

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }

fn get_visited_segments(
    segment_lengths: &NestedFeltCounts,
    visited_pcs: &mut Vec<usize>,
    bytecode_offset: &mut usize,
) -> Result<Vec<usize>, TransactionExecutionError> {
    let mut res = Vec::new();

    match segment_lengths {
        NestedFeltCounts::Leaf(length, _) => {
            let segment = *bytecode_offset..*bytecode_offset + length;
            if visited_pcs.last().is_some_and(|pc| segment.contains(pc)) {
                res.push(segment.start);
            }

            while visited_pcs.last().is_some_and(|pc| segment.contains(pc)) {
                visited_pcs.pop();
            }
            *bytecode_offset += length;
        }
        NestedFeltCounts::Node(segments) => {
            for segment in segments {
                let segment_start = *bytecode_offset;
                let next_visited_pc = visited_pcs.last().copied();

                let visited_inner_segments =
                    get_visited_segments(segment, visited_pcs, bytecode_offset)?;

                if next_visited_pc.is_some_and(|pc| pc != segment_start)
                    && !visited_inner_segments.is_empty()
                {
                    return Err(TransactionExecutionError::InvalidSegmentStructure(
                        next_visited_pc.unwrap(),
                        segment_start,
                    ));
                }

                res.extend(visited_inner_segments);
            }
        }
    }
    Ok(res)

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

// Returns the hash of the contract class bytecode according to its segments.
//
// The hash is computed according to a segment tree. Each segment may be either a leaf or divided
// into smaller segments (internal node).
// For example, the bytecode may be divided into functions and each function can be divided
// according to its branches.
//
// The hash of a leaf is the Blake2s hash of the data.
// The hash of an internal node is `1 + blake2s(len0, hash0, len1, hash1, ...)` where
// len0 is the total length of the first segment, hash0 is the hash of the first segment, and so on.
//
// For each segment, the *prover* can choose whether to load or skip the segment.
// When full_contract is TRUE, all segments are loaded regardless of their usage.
//
// * Loaded segment:
//   For leaves, the data will be fully loaded into memory.
//   For internal nodes, the prover can choose to load/skip each of the children separately.
//
// * Skipped segment:
//   The inner structure of that segment is ignored.
//   The only guarantee is that the first field element is enforced to be -1.
//   The rest of the field elements are unconstrained.
//   The fact that a skipped segment is guaranteed to begin with -1 implies that the execution of
//   the program cannot visit the start of the segment, as -1 is not a valid Cairo opcode.
//
// In the example above of division according to functions and branches, a function may be skipped
// entirely or partially.
// As long as one function does not jump into the middle of another function and as long as there
// are no jumps into the middle of a branch segment, the loading process described above will be
// sound.
