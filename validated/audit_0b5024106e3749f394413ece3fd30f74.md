**Reasoning:**

The premise that an attacker can "supply `event_data` bytes" to `Transfer::try_from_bytes` doesn't correspond to any exposed unprivileged input path. `Transfer` events are strongly-typed Move events emitted exclusively by the framework's `object::transfer_raw_inner` function, which reads the real on-chain `ObjectCore.owner` and the actual object address before emitting, and only emits when `object_core.owner != to` [1](#0-0) . There is no API, transaction, or bytecode path where a caller controls the raw BCS bytes of `event_data` independent of actual VM execution and the real resource state — the VM's type system and struct-emission intrinsic enforce that `object`, `from`, and `to` reflect the genuine transfer being performed, not attacker-chosen values.

`Transfer::try_from_bytes` itself is a thin BCS decode wrapper with no additional invariant checks [2](#0-1) , but that's expected: business-logic invariants (e.g., `from != to`, `object` being a real resource address) are enforced at the point of emission in Move, not at deserialization time.

Separately, the only consumer of this decoder in the reviewed scope is `TransferTranslator::translate_event_v2_to_v1` in the storage indexer [3](#0-2) , which operates on `ContractEventV2` values already read back from the main DB after consensus commit [4](#0-3) . This is a non-consensus, best-effort internal indexer feature (`InternalIndexerDBService`) that reconstructs V1-style event keys for legacy API compatibility [5](#0-4) ; it does not touch the write set, transaction info, event/state Merkle proofs, or accumulator roots. A malformed or semantically implausible `Transfer` (even if one could somehow be committed) would at worst cause a translation failure, which is explicitly handled as non-fatal (`Ok(None)`, event skipped with a warning) [6](#0-5)  — it cannot corrupt authenticated ledger state, misbind a proof, or diverge consensus.

Since (1) there is no unprivileged path to inject arbitrary `event_data` bytes independent of genuine VM-enforced emission, and (2) the only consumer is a non-authoritative, off-consensus indexing convenience path that cannot affect committed state, proofs, or authenticated responses bound to a ledger version/root, this does not meet the Decision Standard for acceptance.

### Event V2→V1 translation (`event_v2_translator.rs`)

Module events (`ContractEventV2`) carry no event key or sequence number, but old API queries are keyed on them. `EventV2TranslationEngine` holds a registry of per-`TypeTag` `EventV2Translator` impls (coin deposit/withdraw, token/collection events, etc.). Each translator reconstructs the V1 `EventKey` and sequence number by reading the corresponding on-chain resource's event handle from the main DB's latest state checkpoint view, then the result is stored in `TranslatedV1EventSchema` and mirrored into the event-by-key/version indices.

- Sequence numbers are tracked in an in-memory `DashMap` cache backed by `EventSequenceNumberSchema`; `get_next_sequence_number` falls back to the on-chain handle count.
- Translation failure is non-fatal: the event is skipped (`Ok(None)`) with a warning. "Resource not found" for Mint/Burn is expected and silently ignored (ConcurrentSupply collections have no V1-style supply resource).
