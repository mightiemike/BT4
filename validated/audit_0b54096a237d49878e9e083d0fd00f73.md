## Analysis Summary

Based on my research, I found a concrete analog to the M-01 report: Push Chain's TSS outbound signing pipeline already implements the exact mitigation Klaster describes ("the node will not accept to execute the bundle if the deadline is too short") — but it appears to only be implemented for the SVM chain, not the EVM chain.

Note on completeness: I ran out of tool-call budget before I could read the full contents of `universalClient/tss/txbroadcaster/evm.go` and `universalClient/tss/txresolver/evm.go` directly. My conclusion is based on `grep_search` finding zero occurrences of `deadline`/`Deadline`/`SigningDeadline` in those two files (versus multiple occurrences in the corresponding `svm.go` files), plus the fact that `universalClient/chains/evm/tx_builder.go` has only a single match for `deadline` (versus SVM's `tx_builder.go` which threads `SigningDeadline` through message construction, execution checks, and revert logic). This is strong but not 100%-confirmed evidence of the gap — a Devin session with full file access should verify the exact EVM broadcast/resolve code before treating this as certain.

### Title
Missing signing-deadline enforcement in EVM outbound broadcast/resolve path causes stale-signature broadcasts and possible false REVERT votes - (File: `universalClient/tss/txbroadcaster/evm.go`, `universalClient/tss/txresolver/evm.go`)

### Summary
`x/uexecutor/keeper/create_outbound.go` computes a `SigningDeadline` for every outbound (`attachOutboundsToUtx`, using `ChainConfig.TssSigningDeadline`) and embeds it in the `OutboundCreatedEvent` that TSS validators sign over. [1](#0-0) 
For Solana destinations, the universalClient's broadcaster and resolver explicitly gate broadcast/revert decisions on this deadline plus the destination cluster's own clock, precisely to avoid the "simulation succeeds, on-chain execution fails" scenario described in the external report. [2](#0-1) [3](#0-2) 

No equivalent `deadline`/`SigningDeadline` handling was found via search in the EVM counterparts (`universalClient/tss/txbroadcaster/evm.go`, `universalClient/tss/txresolver/evm.go`, `universalClient/chains/evm/tx_builder.go`), suggesting the EVM outbound path does not check `SigningDeadline` before broadcasting a TSS-signed outbound transaction or before deciding COMPLETED/REVERTED.

### Finding Description
The `SigningDeadline` is chain-config-driven (`TssSigningDeadline` duration, added to block time), and is deliberately included in outbound events so it can gate node-side execution risk — this is the node's own implementation of exactly the mitigation Klaster describes in the external report ("the node will not accept to execute an iTx bundle with a tight deadline"). [4](#0-3) 
For SVM outbounds, `broadcastOutboundSVM` checks `now > deadline` and consults the cluster's own clock via `IsAlreadyExecuted` before deciding to broadcast, treat-as-executed, or give up; the resolver similarly refuses to vote REVERT until the cluster clock confirms the deadline has passed (with slack and staleness guards). [5](#0-4) [6](#0-5) 

If the EVM broadcaster does not perform an analogous check, a signed outbound whose `deadline` (also part of the on-chain gateway contract's signed-message verification, per the SVM comment: "the gateway contract reconstructs the same message on-chain and verifies the signature matches") has already expired by broadcast time will still be submitted to the destination EVM chain. If that chain's gateway contract enforces the deadline on-chain (the natural analog to the Solana gateway program), the transaction reverts on-chain, and the relayer (Universal Validator/node) has spent real destination-chain gas for nothing — the direct financial-loss scenario from the M-01 report. Absent an equivalent resolver-side deadline+cluster-time gate, the resolver could also either false-REVERT a tx that is actually still within a valid window (destination chain congestion, RPC clock skew) or, conversely, retry indefinitely without a principled cutoff, unlike the SVM path's staleness/slack-bounded logic.

### Impact Explanation
Financial loss falls on the node/Universal Validator set operating the relayer (gas spent broadcasting a doomed transaction), and, more importantly from the "Push Chain Allowed Impact Gate" scope, a missing deadline gate creates a path for honest UVs to diverge on outbound finalization outcomes (`OutboundTx.observed_tx`/`outbound_status`) between chains that do enforce this consistently (SVM) and chains that don't (EVM) — i.e., "wrong outbound" / "wrong TSS event" convergence as called out explicitly in the required impact gate.

### Likelihood Explanation
Medium. The TSS signing round trip (multi-party ceremony across Universal Validators) introduces meaningful latency between when `SigningDeadline` is computed and when the transaction is actually broadcast, especially under network stress, chain congestion, or when TSS session retries occur (`checkExpiredSessions`, `sessionExpiryBlockDelay`). This is not attacker-privileged — it's a natural consequence of ordinary cross-chain outbound processing timing, matching the report's threat model exactly.

### Recommendation
Add the same deadline-aware guard used in `broadcastOutboundSVM`/`resolveSVM` to the EVM broadcaster (`universalClient/tss/txbroadcaster/evm.go`) and resolver (`universalClient/tss/txresolver/evm.go`): before broadcasting, compare `time.Now()` (or a destination-chain block-time oracle) against `data.SigningDeadline`; if expired, verify against the destination chain's own clock/finalized-block-time before giving up, mirroring the SVM cluster-time confirmation pattern, rather than relying solely on local wall-clock or omitting the check entirely.

### Proof of Concept
Not independently reproducible from the indexed context alone — this finding is derived from the asymmetry between the well-documented SVM deadline-gating logic (`universalClient/tss/txbroadcaster/svm.go`, `universalClient/tss/txresolver/svm.go`) and the absence of matching `deadline` references in the EVM broadcaster/resolver/tx-builder files found via `grep_search`. A Devin session with full repository access should directly inspect `universalClient/tss/txbroadcaster/evm.go` and `universalClient/tss/txresolver/evm.go` to confirm whether `SigningDeadline` is read and enforced there, and whether the EVM gateway contract enforces a deadline on-chain (as the Solana gateway program does) before this can be treated as a confirmed, exploitable gap rather than a documentation/indexing artifact.

func (b *Broadcaster) broadcastOutboundSVM(ctx context.Context, event *store.Event, data *txflow.SignedOutboundData, chainID string) {
	log := b.logger.With().Str("event_id", event.EventID).Str("chain", chainID).Logger()

	client, err := b.chains.GetClient(chainID)
	if err != nil {
		log.Warn().Err(err).Msg("failed to get chain client")
		return
	}
	builder, err := client.GetTxBuilder()
	if err != nil {
		log.Warn().Err(err).Msg("failed to get tx builder")
		return
	}
	signingReq, signature, err := txflow.DecodeSigningData(data.SigningData)
	if err != nil {
		log.Warn().Err(err).Msg("failed to decode signing data")
		return
	}

	outboundData := data.OutboundCreatedEvent
	txID := outboundData.TxID
	deadline := data.SigningDeadline
	now := time.Now().Unix()

	// Past local deadline — confirm with the cluster before giving up.
	if now > deadline {
		executed, clusterTime, checkErr := builder.IsAlreadyExecuted(ctx, txID)
		dlog := log.With().Int64("signing_deadline", deadline).Int64("cluster_block_time", clusterTime).Logger()

		switch {
		case checkErr != nil:
			dlog.Debug().Err(checkErr).Msg("SVM cluster check failed at deadline, retry next tick")
			return
		case executed:
			dlog.Debug().Msg("SVM tx executed by peer past local deadline, marking BROADCASTED")
			b.markBroadcasted(event, chainID, "")
			return
		case clusterTime > deadline:
			dlog.Debug().Msg("SVM deadline cluster-confirmed expired, marking BROADCASTED for resolver REVERT")
			b.markBroadcasted(event, chainID, "")
			return
		}
		// Cluster says still inside the window (or freshness unknown) — broadcast.
	}

		return

		return
