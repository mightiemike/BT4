## Title
DeleteAccount fails to purge account-scoped receipt state (PromiseYield/PostponedReceipt/PendingDataCount/ReceivedData/YieldId mappings), enabling stale-receipt execution against a re-created account — (`File: core/store/src/utils/mod.rs`)

### Summary
`remove_account` — the routine `action_delete_account` uses to erase an account — only deletes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries. It never expires or removes the account-scoped receipt bookkeeping (`PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout` queue entries, `YieldIdToDataId`/`DataIdToYieldId`, `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`) that still key on the deleted `account_id`. This is structurally the same bug class as ALPINE-CVE-2026-39316: an object (`cupsd_printer_t` / here, a NEAR account) is deleted without first expiring the external references (subscriptions / here, promise-yield and postponed-receipt bookkeeping) that point at it, leaving dangling entries that get dereferenced later.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) calls `remove_account(state_update, account_id)` to erase the account: [1](#0-0) 

`remove_account` only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `ContractData`: [2](#0-1) 

It never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldTimeout`/`PromiseYieldIndices`, `TrieKey::YieldIdToDataId`/`DataIdToYieldId`, `TrieKey::PostponedReceipt`/`PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::ReceivedData` — all of which are keyed by `(receiver_id, data_id/receipt_id)` where `receiver_id == account_id` being deleted. The existence of a dedicated `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` list (used only by resharding boundary-splitting logic) confirms these are recognized as account-scoped columns, yet `remove_account` — the actual account-deletion path — ignores that list entirely: [3](#0-2) 

Later, when the corresponding `PromiseResume` receipt or a queued `PromiseYieldTimeout` fires, the runtime only checks whether the state entry still exists — never whether the target account (still) belongs to the same "incarnation" that created it: [4](#0-3) [5](#0-4) 

`apply_action_receipt` then re-fetches whatever account currently sits at that `account_id` and executes the stale, attacker-authored callback actions against it, with no incarnation check: [6](#0-5) 

Because a deleted named account can legitimately be re-created at the identical `AccountId` (creation only requires `account.is_none()`, enforced in `check_account_existence`), an attacker can: [7](#0-6) 

1. As the owner of account `X`, call a contract on `X` that runs `promise_yield_create`, registering a callback receipt (attacker-chosen actions, e.g. `AddKey`/`Transfer`/`FunctionCall`) parked under `PromiseYieldReceipt{receiver_id: X, data_id}` plus a `PromiseYieldTimeout` entry.
2. Delete account `X` (refunding its balance to the attacker) via `DeleteAccount`. The parked yield receipt, its status, and the timeout queue entry are **not** cleared.
3. Wait for `X` to be re-created (by the attacker or a third party who is unaware the name is "poisoned" — e.g. a deterministic/implicit id, or a sub-account the attacker's own parent account later re-issues to someone else) and funded.
4. The still-pending timeout (`resolve_promise_yield_timeouts`, `lib.rs:3113`) or a delayed `PromiseResume` fires automatically, finds the residual `PromiseYieldReceipt` still keyed to `X`, and executes the attacker's original callback actions (e.g. adding an attacker-controlled full-access key, or transferring the new account's balance) against the **fresh** account now occupying `X`, since `apply_action_receipt` never distinguishes "this receiver existed when the yield was created" from "this receiver is a brand-new account".

The resharding test suite even documents that dangling `PromiseYield`/delayed-receipt trie values are a known correctness hazard in this codebase (for GC/resharding), underscoring that this class of "account-scoped queue entry outlives the account" bug is already acknowledged, just not fixed for the plain `DeleteAccount` path: [8](#0-7) 

### Impact Explanation
This allows unauthorized state mutation/value movement against a re-created account using actions the *previous* owner of the same `AccountId` chose before deleting it — e.g. silently granting the attacker a full-access key or diverting a transfer, once the reused account is funded. This is a transaction-triggered invalid state transition / unauthorized value movement, reachable purely from an ordinary account holder issuing `FunctionCall` (`promise_yield_create`) + `DeleteAccount` — no privileged, validator, or network-layer access required.

### Likelihood Explanation
Reaching the vulnerable state only requires two ordinary actions from any account (`yield_create` then `DeleteAccount` within `MAX_ACCOUNT_DELETION_STORAGE_USAGE`), both fully within reach of a single transaction signer/contract deployer. The remaining precondition — the exact `AccountId` being reused/re-funded later — is a real but narrower condition (most natural for deterministic/implicit account ids, or sub-accounts an attacker's own parent later reassigns), which is why this is best characterized as Medium severity rather than trivially always-exploitable.

### Recommendation
When `action_delete_account`/`remove_account` deletes an account, also purge (or explicitly expire/cancel) all account-scoped receipt bookkeeping keyed to that `account_id`: `PromiseYieldReceipt`, `PromiseYieldStatus`, any `PromiseYieldTimeout` queue entries referencing it, `YieldIdToDataId`/`DataIdToYieldId`, `PostponedReceipt`/`PostponedReceiptId`, `PendingDataCount`, and `ReceivedData`. Alternatively, tag accounts with a per-incarnation nonce/epoch and have `apply_action_receipt`/`resolve_promise_yield_timeouts` verify the target account's incarnation matches the one recorded when the yield/postponed receipt was created, refusing to execute (and instead discarding/refunding) stale entries whose incarnation no longer matches.

### Proof of Concept
1. Attacker account `X` deploys a contract and calls a method that invokes `promise_yield_create`, registering a callback batch containing `Action::AddKey { public_key: attacker_key, access_key: FullAccess }` (or a `Transfer`/`FunctionCall` draining balance).
2. In the same or a later block, attacker sends `DeleteAccount { beneficiary_id: attacker }` from `X`. `remove_account` (`core/store/src/utils/mod.rs:504`) removes the `Account`/keys/contract data but leaves `PromiseYieldReceipt{X, data_id}`, its `PromiseYieldStatus`, and its `PromiseYieldTimeout` entry in the trie.
3. `X` is re-created (e.g., a third party creates the same sub-account name, or `X` is a deterministic/implicit account id) and funded with real balance.
4. At the pre-computed timeout height, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3113-3161`) finds the residual entry still present, synthesizes a `PromiseResume`, and the runtime executes the attacker's original `AddKey`/`Transfer` actions against the newly funded `X` (`runtime/runtime/src/lib.rs:1568-1616`, `907-910`), granting the attacker access to / funds from an account they no longer legitimately control.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

    action: &Action,
    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    receipt_shape: ReceiptShape,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            }

                return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
