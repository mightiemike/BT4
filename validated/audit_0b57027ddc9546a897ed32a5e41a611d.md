## Verdict: Valid Finding (Real, but Moderate-Severity Complexity Issue)

### Title
Unindexed `PendingInbounds.Walk` full scan on every ballot-terminal event causes superlinear per-block cost with concurrent pending deposits - (`x/uexecutor/keeper/ballot_hooks.go`)

### Summary
`afterInboundBallotTerminal` performs a full, unindexed scan of the entire `PendingInbounds` collection every single time any inbound ballot reaches a terminal state (PASSED/REJECTED/EXPIRED), because ballot IDs are one-way digests that cannot be mapped back to their `PendingInboundEntry` key. This scan cost is paid on *every* terminal transition, and terminal transitions for many ballots can be triggered together within a single transaction via the pre-existing `ExpireBallotsBeforeHeight` expiry sweep.

### Finding Description
`afterInboundBallotTerminal` locates the owning `PendingInboundEntry` by scanning the entire `PendingInbounds` collection with a nil-range `Walk`: [1](#0-0) 

This hook fires from `fireBallotTerminalHook`, called by both `MarkBallotExpired` and `MarkBallotFinalized`: [2](#0-1) [3](#0-2) 

Critically, `MarkBallotExpired` is called in a batch from `ExpireBallotsBeforeHeight`, which is itself invoked at the start of every `CreateBallot` call (i.e., whenever any new distinct inbound event needs a ballot — an ordinary occurrence driven purely by unprivileged depositor activity on a source chain): [4](#0-3) [5](#0-4) 

Because `expiryAfterBlocks` is typically a fixed protocol parameter, ballots created from a burst of deposits (e.g., many depositors interacting with a high-throughput source chain within a similar time window) will tend to expire in a similar height window. When a subsequent deposit's vote triggers `CreateBallot` → `ExpireBallotsBeforeHeight`, it can collect and expire many ballots in one call (`toExpire` loop), and each `MarkBallotExpired(id)` fires the terminal hook, which performs a full `O(n)` scan over `PendingInbounds` (where `n` is the number of currently-pending distinct inbound entries). With `M` ballots expiring together against a pending set of size `n`, the aggregate hook cost for that single transaction is `O(M·n)` — quadratic in the number of concurrently pending, honestly-submitted deposits, with no attacker-controlled malformed input required.

The code comment explicitly assumes "the pending set is small and transient," which is an unenforced assumption — there is no cap on `PendingInbounds` size, and it grows directly with legitimate deposit throughput and TSS/UV voting latency.

### Impact Explanation
This is a computation-cost (gas/CPU) amplification issue reachable purely by ordinary, honest depositors submitting genuine deposits on a busy source chain — no malformed input, malicious relayer, or validator collusion is needed. As pending inbound volume grows, the marginal cost of processing ballot terminal events grows non-linearly, which can materially increase block-processing time/gas for `EndBlock`/`DeliverTx` paths that trigger ballot expiry, potentially degrading node performance under organic high load. This falls under the "non-network-level DoS reachable without privileged control" impact category, since it is a computational-complexity defect in in-process state scanning, not a network/packet-level attack.

However, it does not itself cause fund loss, unauthorized execution, or state corruption — its worst-case effect is degraded liveness/performance under adversarial-scale organic load, bounded by how large `PendingInbounds` and simultaneous batch-expiry counts can realistically grow relative to block gas limits and finalization latency in practice.

### Likelihood Explanation
Likelihood is moderate: triggering it requires accumulating a large number of concurrently pending, not-yet-finalized inbound entries whose ballots expire together, which depends on real-world UV voting latency, `expiryAfterBlocks` parameter size, and deposit throughput. An attacker cannot single-handedly force this deterministically without controlling deposit volume/spread, but "many ordinary depositors" on a busy chain is a realistic, unprivileged scenario as posed in the question.

### Recommendation
Replace the linear `Walk` lookup with an index mapping `ballotID → utxKey` (e.g., a secondary `collections.Map`) populated when each variant/ballot is created (in `RecordInboundVote`) and cleaned up when the `PendingInboundEntry` is removed. This turns the terminal-hook lookup into an `O(1)` operation regardless of `PendingInbounds` size, eliminating the batch-expiry amplification entirely.

### Proof of Concept
Conceptual benchmark (matches the question's proof idea):
1. Populate `PendingInbounds` with `n` distinct entries (simulating `n` concurrent, honest depositors), each with a ballot whose `expiryAfterBlocks` places its expiry at the same future height.
2. Advance to that height and submit one more deposit vote, triggering `CreateBallot` → `ExpireBallotsBeforeHeight`, which collects and expires all `n` ballots in the `toExpire` loop.
3. Measure total `PendingInbounds.Walk` invocations and total scanned elements: each of the `n` `MarkBallotExpired` calls fires `afterInboundBallotTerminal`, each scanning the (shrinking) pending set — aggregate scan operations are `O(n²)`.
4. Compare against an indexed lookup baseline (`O(n)` total) to quantify the amplification factor, which grows linearly with `n` itself (i.e., unbounded as pending deposit backlog grows).

func (k Keeper) MarkBallotExpired(ctx context.Context, id string) error {
	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as expired",
		"ballot_id", id,
		"expiry_height", ballot.BlockHeightExpiry,
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.ExpiredBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = types.BallotStatus_BALLOT_STATUS_EXPIRED
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, types.BallotStatus_BALLOT_STATUS_EXPIRED)
	return nil
}

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}

	// Close iterator explicitly before mutation phase to release the IAVL snapshot
	iter.Close()

	if len(toExpire) > 0 {
		k.Logger().Debug("expiring stale ballots", "count", len(toExpire), "current_height", currentHeight)
	}

	// Phase 2: expire collected ballots (safe — iterator is closed)
	for _, id := range toExpire {
		if err := k.MarkBallotExpired(ctx, id); err != nil {
			return err
		}
	}

	return nil
}
