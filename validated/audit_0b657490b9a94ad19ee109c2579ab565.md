### Title
Missing frozenDuration validation in `FreezeBalanceProcessor.execute` leads to integer overflow of freeze expiry time - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
`FreezeBalanceProcessor`, the native-contract handler invoked from TVM smart-contract freeze operations, never validates the bounds of `param.getFrozenDuration()` before using it in an unchecked multiplication, unlike the RPC-facing `FreezeBalanceActuator`, which enforces `minFrozenTime`/`maxFrozenTime` bounds in `validate()`.

### Finding Description
`FreezeBalanceProcessor.validate()` checks `frozenBalance`, `frozenCount`, `resourceType`, and delegation rules, but contains **no check at all on `frozenDuration`**: [1](#0-0) . Then `execute()` computes the expire time using an unchecked plain multiplication: [2](#0-1) 

This is structurally identical to the reported vault bug: a user-controlled step/duration value is multiplied by a fixed constant (`tick_spacing` in the report, `FROZEN_PERIOD` here) with no upstream bound validation, producing a silent long overflow that corrupts a state value (`expireTime` here, `check_rebalance` tick bounds there).

By contrast, the equivalent RPC-facing actuator `FreezeBalanceActuator.validate()` does bound-check `frozenDuration` against `minFrozenTime`/`maxFrozenTime` before the same multiplication is performed in `execute()`: [3](#0-2)  and [4](#0-3) . The native-contract path lacks this parity, so a smart contract invoking the freeze precompile can pass an arbitrary `frozenDuration` (e.g., a very large `long`) that overflows `nowInMs + param.getFrozenDuration() * FROZEN_PERIOD`, producing a wrapped-around (potentially negative or small) `expireTime`.

### Impact Explanation
An overflowed `expireTime` written into `accountCapsule.setFrozenForBandwidth`/`setFrozenForEnergy` (or into the delegated resource capsule via `delegateResource`) corrupts on-chain resource-accounting state: frozen balances may appear to expire immediately (undermining resource-lock guarantees) or, depending on the wrap value, at an unintended far-future/near time, mismatched from the balance actually deducted from the caller's account. This affects consensus-relevant state (`AccountCapsule` frozen balances, total net/energy weight) reached via a contract call, which is an unprivileged, RPC-reachable transaction path (any account can deploy/call a contract that invokes this native contract).

### Likelihood Explanation
Reachable from any account triggering a smart contract that calls the freeze native contract with attacker-chosen `frozenDuration`; no special privileges are required. The only real barrier is whatever range TVM opcode/precompiled-contract wrapper imposes on the duration argument before constructing `FreezeBalanceParam`, which was not confirmed in this codebase (the invoking `Program.java` freeze opcode plumbing could not be located/verified with available search results). This uncertainty should be resolved by checking the TVM opcode handler that constructs `FreezeBalanceParam` for any pre-existing duration bound.

### Recommendation
Add the same `minFrozenTime`/`maxFrozenTime` bound check used in `FreezeBalanceActuator.validate()` to `FreezeBalanceProcessor.validate()`, and/or use a checked multiplication (e.g., `Math.multiplyExact`/`StrictMathWrapper`, as already used elsewhere in the codebase such as `AssetIssueActuator`'s `StrictMathWrapper.addExact` overflow guard) when computing `expireTime` in `FreezeBalanceProcessor.execute()`.

### Proof of Concept
1. Deploy or call a smart contract that invokes the TVM freeze-balance native contract with a very large `frozenDuration` value (close to `Long.MAX_VALUE / FROZEN_PERIOD`), a valid `frozenBalance >= 1 TRX`, and `resourceType = BANDWIDTH` or `ENERGY`.
2. `FreezeBalanceProcessor.validate()` performs no check on `frozenDuration`, so validation passes.
3. `execute()` computes `expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD`, which overflows `long`, yielding a wrapped/incorrect expire timestamp stored into the account's frozen-balance state — analogous to the overflow described in the vault report's `check_rebalance` multiplication of `tick_step * tick_spacing`.
