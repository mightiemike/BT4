### Title
Unbounded, fee-free iteration over Proposals in `processBlock` allows permissionless chain halt - ([File: framework/src/main/java/org/tron/core/consensus/ProposalController.java])

### Summary
`ProposalController.processProposals()` walks backwards from `latestProposalNum` down to `1`, reading every proposal from the `ProposalStore` on every maintenance-cycle block until it finds one already processed. This work happens inside `Manager.processBlock()`, which is unmetered consensus-critical execution (no gas/energy is charged for it), analogous to the reported `BeginBlock`/`AllocateRewards` iteration bug. Any account that becomes a witness can call `ProposalCreateActuator` to create proposals at effectively zero marginal fee (`calcFee()` returns `0`), letting an attacker flood the `ProposalStore` with an unbounded number of entries that must be linearly scanned every maintenance period, threatening a chain halt.

### Finding Description
`ProposalController.processProposals()` performs: [1](#0-0) 
a `while (proposalNum > 0)` loop that decrements one at a time from `latestProposalNum`, doing a `ProposalStore.get()` (RocksDB/LevelDB read) for every id, until a proposal already marked `APPROVED`/`DISAPPROVED` is encountered, at which point it `break`s.

This method is invoked unconditionally from `Manager.processBlock()` whenever the maintenance time has been reached: [2](#0-1) 
This is executed as part of block application (the java-tron analog of Cosmos `BeginBlock`), with no gas metering — it is native Java consensus code, not TVM-metered execution.

Crucially, the "break" optimization only helps if proposals are processed in strictly increasing/contiguous fashion; any newly created `PENDING` proposal with an id below the highest processed id, or a long unbroken run of never-yet-processed ids, forces the loop to walk further back linearly, and each of these iterations does its own DB `get()` call — this is the same “linear iteration exposes a store-scan-based chain halt” pattern flagged in the external report.

The gating cost is negligible:
- `ProposalCreateActuator.calcFee()` returns `0` — a proposal costs nothing beyond ordinary transaction bandwidth: [3](#0-2) 
- The only gate on `ProposalCreateActuator.validate()` is that the owner address must be a registered witness: [4](#0-3) 
- Becoming a witness is itself permissionless and just requires paying a one-time `AccountUpgradeCost` fee via `WitnessCreateActuator`: [5](#0-4) 

Once an attacker pays the single, fixed witness-registration fee, they can submit an unbounded number of `ProposalCreateContract` transactions across many blocks at essentially zero marginal cost (only ordinary bandwidth/energy for a small transaction), each incrementing `latestProposalNum` and inserting one row into `ProposalStore`. There is no cap in `ProposalCreateActuator.validate()` on the total number of pending/outstanding proposals per account or globally. When the maintenance time arrives, `processProposals()` must walk the entire backlog, doing one `ProposalStore.get()` per id, with no gas/time budget enforced.

### Impact Explanation
Because `processProposals()` executes inside block-application logic (equivalent to `BeginBlock`), a sufficiently large backlog of unprocessed/pending proposals causes the per-block (or per-maintenance-cycle) processing time to grow linearly and unboundedly with attacker-controlled input, with no metering to bound execution. This can stall block production/validation network-wide — a full consensus-level Denial of Service, matching the "Impact" class explicitly accepted by the validation rules (DoS via protocol implementation / store iteration).

### Likelihood Explanation
Likelihood is high:
- The fee to create a proposal (`calcFee() == 0`) provides no economic disincentive to spamming, unlike a legitimately-scaled cost.
- The only prerequisite — witness registration — is a one-time, fixed-price, fully permissionless action (`WitnessCreateActuator`), not a privileged role assignable only by governance; anyone who pays `AccountUpgradeCost` becomes eligible to spam proposals indefinitely afterward.
- No limit exists on the number of outstanding/pending proposals a witness (or the network) may accumulate, so the attack is purely a function of how many low-cost transactions the attacker is willing to broadcast over time.
- The vulnerable code runs unconditionally in the hot block-processing/maintenance path used by every node, so the attack is reproducible deterministically by any full node reaching that block height/time.

### Recommendation
- Introduce a scaling fee (or hard cap) for `ProposalCreateContract`, e.g., basing `calcFee()`/an explicit gas charge on the number of currently pending/unprocessed proposals for that account or globally, similar to the `ctx.GasMeter().ConsumeGas(BaseGasFeeForNewPlan * numExistingPlans)` pattern recommended in the reference report.
- Enforce a maximum number of concurrently pending proposals (per witness and/or system-wide) in `ProposalCreateActuator.validate()`.
- Bound `ProposalController.processProposals()` to a fixed maximum number of iterations/time budget per maintenance cycle, deferring the remainder to subsequent cycles instead of processing the full backlog in one unmetered pass.

### Proof of Concept
Conceptual PoC (analogous to the reference report's Go test), expressed against the existing Java test scaffolding:
1. Use `WitnessCreateActuator` to register one attacker-controlled witness (one-time fixed fee via `createWitness()`), see `actuator/src/main/java/org/tron/core/actuator/WitnessCreateActuator.java`.
2. Loop broadcasting `ProposalCreateContract` transactions from that witness address across many blocks — each call to `ProposalCreateActuator.execute()` costs `fee = calcFee() == 0` and simply does `chainBaseManager.getProposalStore().put(...)` plus `saveLatestProposalNum(id)` (see lines 37-64 of `ProposalCreateActuator.java`), so tens of thousands of proposals can be inserted for negligible cost.
3. Advance the chain to the next maintenance time so `Manager.processBlock()` invokes `proposalController.processProposals()` (`Manager.java` lines 1919-1923).
4. Observe that `processProposals()` must walk back through the entire id space performing one `ProposalStore.get()` per proposal (`ProposalController.java` lines 37-70), with execution time scaling linearly with the number of proposals created, exactly mirroring `ProposalControllerTest.testProcessProposals()` (`framework/src/test/java/org/tron/core/witness/ProposalControllerTest.java` lines 115-158) but at attacker-controlled scale (tens of thousands instead of five), demonstrating the unbounded, unmetered block-processing delay.

  public void processProposals() {
    long latestProposalNum = manager.getDynamicPropertiesStore().getLatestProposalNum();
    if (latestProposalNum == 0) {
      logger.info("latestProposalNum is 0, return");
      return;
    }

    long proposalNum = latestProposalNum;

    ProposalCapsule proposalCapsule = null;

    while (proposalNum > 0) {
      try {
        proposalCapsule = manager.getProposalStore()
            .get(ProposalCapsule.calculateDbKey(proposalNum));
      } catch (Exception ex) {
        logger.error("", ex);
        proposalNum--;
        continue;
      }

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    long cost = dynamicStore.getAccountUpgradeCost();
    adjustBalance(accountStore, witnessCreateContract.getOwnerAddress().toByteArray(), -cost);
    if (dynamicStore.supportBlackHoleOptimization()) {
      dynamicStore.burnTrx(cost);
    } else {
      adjustBalance(accountStore, accountStore.getBlackhole(), +cost);
