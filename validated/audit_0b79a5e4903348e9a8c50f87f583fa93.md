### Title
LiquidityCap field on TokenConfig is validated but never enforced against actual minted supply, allowing unbounded PRC20 minting once a chain/token is registered - (File: x/uexecutor/keeper/handler.go)

### Summary
The external report's bug class is "a control that is documented/intended to gate a privileged action (minting) is never actually enforced, so the action is unconditionally permitted." The closest reachable analog in this repository is the `LiquidityCap` field on `uregistry.TokenConfig`. `LiquidityCap` is required to be a non-empty numeric string at registration time (`x/uregistry/types/token_config.go` `ValidateBasic`), documented as "max supply cap for this token," but the inbound PRC20 minting path (`x/uexecutor/keeper/handler.go:depositPRC20` → `CallPRC20Deposit` → `depositPRC20Token` on the `UNIVERSAL_CORE`/Handler contract) never reads or checks `LiquidityCap` against the cumulative minted amount before minting.

### Finding Description
`AddTokenConfig`/`UpdateTokenConfig` (`x/uregistry/keeper/msg_add_token_config.go`, `msg_update_token_config.go`) require a `LiquidityCap` string and reject empty values, implying that once a token is registered with a cap of, say, `1000000000000000000000000`, deposits/mints for that token on Push Chain are supposed to be capped by that liquidity ceiling.

However, the actual mint/deposit path — `depositPRC20` in `x/uexecutor/keeper/handler.go` — only:
1. Fetches `TokenConfig` for `(sourceChain, assetAddr)`.
2. Confirms `NativeRepresentation != nil`.
3. Parses the inbound `amountStr` into a `big.Int`.
4. Calls `k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)`.

At no point is `tokenConfig.LiquidityCap` read, nor is the current total minted supply of the PRC20 contract queried and compared against it. The same is true across all `ExecuteInbound*` flows (`execute_inbound_funds_and_payload.go`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`) — all of which call `depositPRC20` / `gasAndPayloadDepositAutoSwap` with attacker/UV-observed inbound amounts but no cap check. Because `MsgVoteInbound` is a gasless, unprivileged-reachable message (any account can be the "sender" that funds are addressed to, and an honest/attacker-controlled external-chain transaction determines `Amount`), an attacker who bridges enough asset from the source chain (or repeatedly triggers small legitimate-looking deposits) can mint PRC20 tokens on Push Chain in a quantity that exceeds the registered `LiquidityCap`, with no on-chain guard preventing it — mirroring the original report's pattern where a stated protection ("only governance mints" / "capped supply") is not actually wired into the code path that performs the privileged action.

### Impact Explanation
If `LiquidityCap` is meant to bound how much of a bridged asset can exist as PRC20 on Push Chain (e.g., to limit blast radius of a compromised or buggy source-chain gateway, or to cap liquidity exposure for a new/experimental token), the absence of enforcement means an unprivileged user can mint unlimited PRC20 supply for any registered token via ordinary inbound deposit flows, defeating the stated safety control. This corrupts PRC20 supply accounting relative to the declared liquidity ceiling and could enable oversized withdrawals/redemptions or swap manipulation (via `depositPRC20WithAutoSwap`) beyond what governance intended when setting the cap.

### Likelihood Explanation
High reachability: any user who can get a valid, quorum-confirmed inbound observed by honest Universal Validators (i.e., simply performing a legitimate bridge deposit on a supported external chain) can mint PRC20 on Push Chain, since `depositPRC20` performs no cap check. No privileged action, malicious validator, or compromised key is required — only ordinary use of the documented bridging flow at a volume above the configured cap.

### Recommendation
Enforce `LiquidityCap` in the minting path: before calling `CallPRC20Deposit` / `CallPRC20DepositAutoSwap`, query the PRC20 contract's current total supply (or track cumulative minted amount in `uregistry`/`uexecutor` state) and reject (or clamp/revert) deposits that would push total minted supply above `tokenConfig.LiquidityCap`. Alternatively, if `LiquidityCap` is not intended to be an enforced invariant, remove or clearly re-document the field so operators do not mistakenly rely on it as a safety control.

### Proof of Concept
Not independently reproduced against a running node in this session (ask-only investigation); based on static code review:
1. Admin registers a `TokenConfig` for `eip155:11155111` USDC with `LiquidityCap: "1000000000000000000000000"` (1e24) via `MsgAddTokenConfig`.
2. Attacker performs (or arranges) a real deposit on the source chain for far more than the cap (or many deposits summing above the cap).
3. Universal Validators honestly observe and vote `MsgVoteInbound` to quorum for each; `ExecuteInboundFundsAndPayload`/`ExecuteInboundGas` call `depositPRC20` (`x/uexecutor/keeper/handler.go:12-46`), which mints via `CallPRC20Deposit` (`x/uexecutor/keeper/evm.go:262-303`) with no reference to `tokenConfig.LiquidityCap`.
4. Total PRC20 supply on Push Chain for that token now exceeds the registered `LiquidityCap`, with no error or revert at any layer.

Note: I was unable to fully verify whether the Solidity `Handler`/`UniversalCore.depositPRC20Token` contract itself performs any liquidity-cap check off-chain (the contract source was not indexed here — only its ABI call sites in the Go keeper). If the cap is enforced solely inside that EVM contract, and Push Chain's node code has no independent check, this would still mean the "chain-level" registry cap is purely advisory and not corroborated anywhere in the reachable scoped module code (`x/uregistry`, `x/uexecutor`). Given the size limits on the codebase index, the Solidity contract implementing `depositPRC20Token` was not available for direct inspection — a Devin session with full repository access would be needed to confirm definitively whether liquidity-cap enforcement exists inside the EVM contract layer.
