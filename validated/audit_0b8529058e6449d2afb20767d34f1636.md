### Title
Reward Sniping via Vote-Snapshot Timing Allows Uncompensated Reward Extraction in Cycle-Based Voting Reward Accounting - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The DPoS voting-reward accounting model computes rewards per cycle using a witness-level value index (`VI`) multiplied by an account's *snapshotted* vote count for that cycle, rather than by how long the account actually held the vote during the cycle. Because a fresh vote snapshot is taken every time `withdrawReward()` executes (invoked implicitly by `VoteWitnessActuator`/`VoteWitnessProcessor` on every vote/unvote), a user can cast a vote right before the end of a cycle, immediately trigger a snapshot (by voting/unvoting again), and later withdraw a full cycle's reward for a witness — despite holding the vote for only a fraction of that cycle. This mirrors the reported `stake()`/`instantUnstakeReserve` arbitrage: acting right at a reward-accrual boundary captures a disproportionate reward share and dilutes/overdraws rewards meant for genuine long-term voters.

### Finding Description
`MortgageService.withdrawReward()` (and its TVM-native twin `VoteRewardUtil.withdrawReward()`) implements a cycle-based reward-claim mechanism: [1](#0-0) 

Key facts:
- `MaintenanceManager.doMaintenance()` computes each witness's `VI` for the *just-completed* cycle using the vote count `witness.getVoteCount()` that was in effect **before** new votes cast during that cycle are applied (`accumulateWitnessVi` runs prior to `countVote()`), then only *after that* applies the incoming vote deltas and stores the resulting count as the vote-weight for the *next* cycle: [2](#0-1) 
- A user's own reward-claim path never checks *when* within a cycle they held the vote. `withdrawReward()` simply stores whatever vote list the account currently has as the snapshot for the current cycle (`delegationStore.setAccountVote(endCycle, address, accountCapsule)`), and on the next call, `computeReward(beginCycle, endCycle, snapshotAccount)` grants `deltaVi * userVoteCount` for the *entire* elapsed cycle based on that snapshot: [3](#0-2) 
- Every vote-related actuator/processor implicitly calls `withdrawReward()` first, meaning simply calling `VoteWitnessContract` (on-chain) or the TVM `vote`/`unvote` precompile snapshots the current vote list for the current cycle as a side effect: [4](#0-3) [5](#0-4) 

Because reward accrual is a pool (`delegationStore.addReward(cycle, witnessAddress, value)`) divided among voters purely by `deltaVi * userVoteCount` with no accounting for the fraction of the cycle actually held, and because the sniper's newly-added vote is *not* included in the `witnessVote` denominator used to compute `deltaVi` for that cycle (their vote is only reflected in the witness's total vote count starting the *next* cycle), the sniper's claim is additive on top of the reward split that the pool was already sized for among the pre-existing voters — an unbudgeted extraction from the witness reward pool.

### Impact Explanation
This corrupts the resource/reward accounting for the DPoS voting-reward system: an attacker can repeatedly (1) vote for a witness near the end of a cycle, (2) trigger a vote-list snapshot for that cycle (e.g., by immediately submitting another vote/unvote transaction, which calls `withdrawReward()` first), and (3) unvote shortly after, yet still receive a full cycle's `VI`-based reward when eventually calling `WithdrawBalanceContract`/`withdrawReward()`. Because the reward pool per witness per cycle (`delegationStore.getReward(cycle, srAddress)`) is a fixed amount funded from block/transaction-fee rewards, and the `deltaVi` denominator does not include the sniper's late vote, honest long-term voters' rewards are effectively diluted/overpaid-against — an accounting leak analogous to the Yieldy `stake()`-before-`rebase()` arbitrage, satisfying the "resource and reward accounting" analog and "asset or accounting corruption" impact bar. This is reachable by any address via ordinary `VoteWitnessContract` transactions or the TVM `vote`/`withdrawReward` precompiles — no privileged role required.

### Likelihood Explanation
Likelihood is Medium: the attack requires no special permissions, capital lockup is minimal (only enough TRX/tron-power to cast a vote), and the actions (vote → snapshot via subsequent vote/withdraw call → unvote) are all ordinary, unprivileged transactions available to any account. The main constraint is timing relative to the maintenance/cycle boundary, which is publicly observable (`getNextMaintenanceTime()`), making the attack schedulable and repeatable every cycle.

### Recommendation
Track vote-weighted time (e.g., a per-cycle time-weighted average vote count, or a minimum holding-period requirement before a vote counts toward reward-snapshot eligibility) instead of snapshotting whatever vote list happens to be present at the moment `withdrawReward()` is called. Alternatively, require that reward eligibility for a cycle be tied to the vote list captured at the *start* of that cycle (post-maintenance) rather than a snapshot taken on-demand at an arbitrary point during the cycle.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
