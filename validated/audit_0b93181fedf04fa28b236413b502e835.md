Found a solid analog: a hardcoded, chain-specific constant that is *not* actually specific to the target chain it's used on, breaking the "deployment address" invariant across networks.

### Title
ETH-implicit accounts on mocknet get assigned the mainnet Wallet Contract's global-contract hash, permanently bricking the account - (File: runtime/near-wallet-contract/src/lib.rs)

### Summary
`eth_wallet_global_contract_hash(chain_id)` hardcodes the expected global-contract code hash per chain, similarly to how `PriceOracle` hardcoded a single `UNISWAP_V3_FACTORY` address assumed valid across all deployment targets. For `chains::MOCKNET` the function does not use a mocknet-specific hash; instead it silently reuses the **mainnet** constant: [1](#0-0) 

### Finding Description
`eth_wallet_global_contract_hash` returns a hardcoded `CryptoHash` per chain id, used when the `EthImplicitGlobalContract` protocol feature is enabled to decide which globally-deployed contract an ETH-implicit account should reference: [2](#0-1) 

`chains::MOCKNET` is explicitly matched to the same branch as `chains::MAINNET`, reusing the mainnet hash constant: [3](#0-2) 

This is imported and consumed in the runtime's action-application code path that creates ETH-implicit accounts (triggered by an ordinary, permissionless `Transfer` action to an ETH-implicit account id): [4](#0-3) 

Unlike `chains::TESTNET` (which has its own distinct hash) or the fallback `_` branch (which computes the hash live from the embedded local WASM, so it is always self-consistent), `MOCKNET` is pinned to a hash that corresponds to a *different* network's deployed contract. If the actual global contract deployed on mocknet under that owner/mechanism does not match this exact byte-for-byte hash (e.g., because mocknet runs a different build, or the mainnet contract simply was never distributed as a global contract on mocknet), any newly created ETH-implicit account on mocknet will be pointed at a global contract hash that does not resolve to executable code on that network.

### Impact Explanation
Per the account model, ETH-implicit accounts "can only be used by calling the methods of the Wallet Contract. It cannot be deleted, nor can a full access key be added": [5](#0-4) 

If the referenced global contract hash does not correspond to deployed code on mocknet, every subsequent `rlp_execute`/wallet-contract call against such an account fails, and — because the account can never be deleted or given a full access key — any NEAR tokens sent to it via the initiating zero/non-zero `Transfer` are **permanently frozen**. This matches the "permanently frozen funds" / "invalid state transition acceptance" impact classes for this scan.

### Likelihood Explanation
Reachable by any unprivileged user: a single `Transfer` action to an ETH-implicit account id is sufficient to trigger implicit-account creation and global-contract-hash assignment (see `test_eth_implicit_account_creation` for the exact mechanism on other chains): [6](#0-5) 

No special privileges, validator status, or network-layer control are needed — only a signed transaction, matching the "unprivileged transaction signer" reachability requirement. The bug is deterministic and chain-specific (mocknet only), which is the same "deployment-target mismatch" root cause as the reported Solidity issue.

### Recommendation
Do not alias `chains::MOCKNET` to the mainnet constant. Either give mocknet its own pinned hash (computed from whatever WASM is actually distributed as the mocknet global contract), or route it through the same live-hash fallback used for other non-mainnet/testnet chains, exactly as `wallet_contract_magic_bytes` already treats unmatched chains via the `_ => LOCALNET` branch: [7](#0-6) 

### Proof of Concept
1. Run a mocknet node/network with the `EthImplicitGlobalContract` protocol feature enabled and `chain_id == "mocknet"`.
2. Submit a `Transfer` action from any funded account to a fresh ETH-implicit account id (`0x...` derived from an arbitrary Secp256k1 public key), exactly as done in `test_eth_implicit_account_creation`.
3. Observe that the resulting account's `global_contract_hash` equals the mainnet constant (`2zodJZK2e4nnv5AqwCRnenNSmkikXhEd7PPY6BmfTmW4`) rather than any contract actually deployed on mocknet under that hash: [8](#0-7) 
4. Attempt to call `rlp_execute` on the account; the call fails to resolve executable code, and since the account cannot be deleted or given a full access key, any balance sent to it is unrecoverable.

Note: I could not view the exact call-site lines in `runtime/runtime/src/actions.rs` where `eth_wallet_global_contract_hash` is invoked (only import-line visibility was available due to index truncation); a Devin session with full repo access should confirm the precise account-creation code path before remediation.

/// Tests that ETH-implicit account is created correctly, with Wallet Contract hash.
#[test]
fn test_eth_implicit_account_creation() {
    let genesis = Genesis::test(vec!["test0".parse().unwrap(), "test1".parse().unwrap()], 1);
    let mut env = TestEnv::builder(&genesis.config).nightshade_runtimes(&genesis).build();
    let genesis_block = env.clients[0].chain.get_block_by_height(0).unwrap();
    let chain_id = &genesis.config.chain_id;

    let signer = InMemorySigner::test_signer(&"test0".parse().unwrap());
    let eth_implicit_account_id = eth_implicit_test_account();

    // Make zero-transfer to ETH-implicit account, invoking its creation.
    let transfer_tx = SignedTransaction::send_money(
        1,
        signer.get_account_id(),
        eth_implicit_account_id.clone(),
        &signer,
        Balance::ZERO,
        *genesis_block.hash(),
    );
    assert_eq!(
        env.rpc_handlers[0].process_tx(transfer_tx, false, false),
        ProcessTxResponse::ValidTx
    );
    for i in 1..5 {
        env.produce_block(0, i);
    }

    // Verify the ETH-implicit account has zero balance and appropriate code hash.
    // Check that the account storage fits within zero balance account limit.
    let request = QueryRequest::ViewAccount { account_id: eth_implicit_account_id };
    match view_request(&env, request).kind {
        QueryResponseKind::ViewAccount(view) => {
            assert!(view.amount.is_zero());
            assert_eq!(view.global_contract_hash, Some(eth_wallet_global_contract_hash(chain_id)));
            assert!(view.storage_usage <= ZERO_BALANCE_ACCOUNT_STORAGE_LIMIT)
        }
        _ => panic!("wrong query response"),
    }
}
