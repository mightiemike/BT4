### Title
Unsigned subtraction in `calculate_new_difficulty` causes wraparound and wrong difficulty-adjustment direction, breaking equality between the light client's computed Bitcoin target and Bitcoin's real target - ([File: crates/bitcoin-da/src/verifier.rs])

### Summary
`calculate_new_difficulty` computes `actual_timespan` for a Bitcoin difficulty-adjustment epoch using plain `u32` subtraction (`last_timestamp - epoch_start_time`) instead of Bitcoin Core's signed `int64` subtraction. When the last block of an epoch has an earlier timestamp than the epoch's first block (a legitimate, historically-observed condition on Bitcoin because block timestamps are only constrained by the median-time-past rule, not strict monotonicity), the subtraction underflows and wraps to a huge `u32` value, which the subsequent clamp routes to the **wrong** bound (`expected_epoch_timespan * 4`, i.e. maximum difficulty decrease) instead of Bitcoin Core's actual clamp (`expected_epoch_timespan / 4`, minimum difficulty decrease) for a negative timespan.

### Finding Description
`calculate_new_difficulty` is invoked from `verify_header_chain_signet` (and structurally the same helper is used by the mainnet/testnet4 header-chain verification paths) each time a Bitcoin epoch boundary (`BLOCKS_PER_EPOCH - 1`) is crossed while verifying the header chain inside the DA verifier: [1](#0-0) 

The subtraction itself: [2](#0-1) 

`epoch_start_time` is the timestamp of the first block of the epoch, and `last_timestamp` is the timestamp of the last block of the epoch (block 2015 in the cycle). Real Bitcoin consensus only requires each block's timestamp to be greater than the median of the previous 11 blocks' timestamps: [3](#0-2) 

This rule does not guarantee monotonic ordering across an entire 2016-block epoch, so `last_timestamp < epoch_start_time` is a legitimate state that Bitcoin's own mainnet consensus code explicitly handles (via a signed `int64` subtraction that can go negative and is clamped to the *minimum* timespan). Here, the equivalent computation is done in unsigned `u32` arithmetic, so a negative real timespan underflows to a value near `u32::MAX`, which then satisfies `actual_timespan > expected_epoch_timespan * 4` and gets clamped to the *maximum* timespan — the opposite of Bitcoin's intended clamp direction.

The resulting (wrong) `actual_timespan` feeds directly into the new target/`bits` calculation: [4](#0-3) 

The wrongly-computed `current_target_bits` is stored in `LatestDaState` and becomes the `expected_bits` used to validate every subsequent block header via `verify_header_chain_common`'s Check 4: [5](#0-4) 

Because the light client's computed target now diverges from Bitcoin's actual next-epoch target (which real Bitcoin nodes compute correctly using signed arithmetic), every subsequent genuine Bitcoin block header presented to the light client will fail `Check 4: valid bits` and be rejected as `InvalidBlockBits`, even though it is a perfectly valid Bitcoin block. This breaks the required equality: `bits computed by BitcoinVerifier == bits actually enforced by the Bitcoin network for that epoch`.

### Impact Explanation
This is not a role-gated bug — it is triggered purely by naturally-occurring Bitcoin block timestamps at an epoch boundary, which requires no attacker privilege, hashrate majority, or malicious action at all. Once triggered, the DA verifier (used both natively for header-chain tracking and inside the light-client zkVM circuit) permanently diverges from the real Bitcoin chain's difficulty target. From that point forward, all genuine Bitcoin blocks fail the DA header-chain verification (`InvalidBlockBits`), which halts L1 syncing for the light client / bridge, effectively freezing the rollup's view of Bitcoin and any bridge logic (deposits, withdrawals, sequencer commitment inclusion proofs) that depends on light-client-verified DA state — matching the Critical impact class "honest nodes converging on an unproved root" / "a true [chain] state made unprovable."

### Likelihood Explanation
Likelihood depends on whether an epoch boundary with `last_timestamp < epoch_start_time` occurs on the target network. This condition has occurred historically on real Bitcoin mainnet (negative retarget periods are a documented, if rare, occurrence caused by miner clock skew), and is even more likely on the custom, fast-block signet described in this file (`EXPECTED_EPOCH_TIMESPAN_SIGNET` ~5.5 hours with 10-second blocks), where clock skew relative to block interval is proportionally larger. No attacker action is required; this is a latent correctness bug that will eventually trigger on its own.

### Recommendation
Replace the `u32` subtraction with signed arithmetic mirroring Bitcoin Core (e.g., compute `last_timestamp as i64 - epoch_start_time as i64`, clamp between `expected_epoch_timespan / 4` and `expected_epoch_timespan * 4` using signed comparisons), then cast the clamped, always-positive result back to `u32` before use in the target calculation. Add regression tests covering `last_timestamp < epoch_start_time`.

### Proof of Concept
1. During header-chain verification, arrange (or wait for) an epoch where the last block's timestamp (`block_header.time()` at `epoch_block == BLOCKS_PER_EPOCH - 1`) is less than the epoch's first block's timestamp (`epoch_start_time`), which is permitted by the median-time-past rule enforced in `verify_timestamp`.
2. `calculate_new_difficulty` computes `actual_timespan = last_timestamp - epoch_start_time` in `u32`, underflowing to a value close to `u32::MAX`. [2](#0-1) 
3. The clamp branch `actual_timespan > expected_epoch_timespan * 4` is taken, setting `actual_timespan = expected_epoch_timespan * 4` — the maximum-decrease clamp instead of the minimum-decrease clamp Bitcoin Core would apply for a negative timespan.
4. The resulting `current_target_bits` no longer matches the real Bitcoin network's next-epoch `bits`, so subsequent genuine Bitcoin block headers fail `Check 4: valid bits` in `verify_header_chain_common`, permanently halting DA header-chain verification for the light client.
