### Title
Blocking global rate limiter (`GlobalRateLimiter.acquire`) can exhaust HTTP/gRPC handler thread pools under default config - (File: `framework/src/main/java/org/tron/core/services/ratelimiter/GlobalRateLimiter.java`)

### Summary
`GlobalRateLimiter.acquirePermit()` dispatches to the blocking `acquire()` path whenever `rate.limiter.apiNonBlocking` is `false`, which is the compiled-in default. [1](#0-0)  Both `RateLimiterServlet.service` (HTTP/JSON-RPC) and `RateLimiterInterceptor.interceptCall` (gRPC) call this method directly on the request-handling thread before doing any work, so any unauthenticated flood of requests that exceeds the single global QPS budget causes the calling threads to block inside `RateLimiter.acquire()`. [2](#0-1) [3](#0-2) 

### Finding Description
`GlobalRateLimiter.acquire(RuntimeData)` calls the per-IP `RateLimiter.acquire()` and then the single static `rateLimiter.acquire()`, both of which are Guava blocking calls with no timeout:

```java
public static boolean acquire(RuntimeData runtimeData) {
  String ip = runtimeData.getRemoteAddr();
  if (!Strings.isNullOrEmpty(ip)) {
    RateLimiter r = loadIpLimiter(ip);
    if (r == null) return false;
    r.acquire();
  }
  rateLimiter.acquire();
  return true;
}
``` [4](#0-3) 

`acquirePermit()` picks this blocking path whenever `Args.getInstance().isRateLimiterApiNonBlocking()` is `false` [5](#0-4) , and the `apiNonBlocking` field defaults to `false` in `RateLimiterConfig` [1](#0-0) , meaning this is the out-of-the-box configuration, not a hardened/non-default opt-in.

Both entry points call `GlobalRateLimiter.acquirePermit()` synchronously on the request-handling thread, before the request has been authenticated or validated in any way:
- `RateLimiterServlet.service()` for every HTTP/JSON-RPC servlet request. [2](#0-1) 
- `RateLimiterInterceptor.interceptCall()` for every gRPC call. [6](#0-5) 

Because the global `RateLimiter` is a single, shared, static instance (`private static RateLimiter rateLimiter = RateLimiter.create(QPS)`), every concurrent request funnels through the same blocking gate. [7](#0-6)  Guava's `RateLimiter.acquire()` does not reject or cap wait time — as more callers pile up beyond the configured QPS, each subsequent caller's computed wait time (based on the accumulated "debt" of reserved future permits) grows, and the calling thread blocks for that entire duration. Since HTTP servlet containers (Jetty/Tomcat) and the gRPC server both use bounded worker thread pools to service incoming connections/calls, and the blocking call happens *before* any request-specific work or per-endpoint dispatch, an attacker who sustains request volume above the global QPS ceiling can keep growing numbers of handler threads permanently parked in `acquire()`, exhausting the pool and denying service to all other legitimate clients — including on completely unrelated, cheap endpoints — because the rate limiting itself, not request processing, is the bottleneck consuming the thread.

None of the existing checks mitigate this: there is no admission-time queue-length cap, no timeout variant of `acquire()` is used (Guava offers `tryAcquire(timeout)` but it is not used here for the blocking branch), and the per-IP limiter (`loadIpLimiter`) is also blocking and does not protect the shared thread pool since it runs on the same handler thread before the global check even begins.

### Impact Explanation
This matches the "DoS via RPC-API" bounty class: an unauthenticated client (or small number of clients across several source IPs to bypass per-IP throttling) can, purely by issuing more requests than the configured global QPS, cause increasingly long thread blocking across the HTTP and gRPC handler pools, ultimately denying RPC-API/JSON-RPC/gRPC service to all legitimate users of a full node running default configuration.

### Likelihood Explanation
- Precondition: `rate.limiter.apiNonBlocking=false`, which is the shipped default. [1](#0-0) 
- Attacker needs no credentials, no funded account, no special permissions — any anonymous HTTP/gRPC client can send requests.
- Cost is minimal: sending raw HTTP/gRPC requests that exceed a fixed global QPS quota (default global QPS is a fixed config value, e.g. 50000 in `GlobalConfig`, but any sustained flood above whatever value an operator configures triggers the effect) — no on-chain fee, bandwidth, or energy cost is incurred since the block happens before any blockchain-level validation.
- Repeatable indefinitely as long as the flood is sustained; effect scales with the number of concurrent excess requests.
- The main uncertainty is the exact size of the Jetty/gRPC worker thread pools in a given deployment (not fully confirmed from the indexed files), which determines how many concurrent blocked callers are needed to fully exhaust the pool; regardless of exact pool size, the mechanism (thread blocking growing unboundedly with excess load) is present in the code.

### Recommendation
Avoid blocking the request-handling thread itself in the rate limiter's default mode. Options:
- Use `RateLimiter.tryAcquire(timeout, TimeUnit)` with a bounded timeout instead of the unbounded `acquire()`, and reject the request (as the non-blocking path does) when the timeout expires.
- Move the blocking/queueing logic off the servlet/gRPC handler thread onto a separate bounded executor/queue so handler threads are never held hostage by the rate limiter.
- Reconsider the safety of defaulting `apiNonBlocking` to `false`; document/switch the default to non-blocking (reject fast) behavior, since blocking is inherently vulnerable to thread-pool exhaustion under flood conditions.

### Proof of Concept
```java
// JUnit-style PoC demonstrating that acquire() blocks the calling (handler) thread
// and that sustained concurrent excess load grows blocking time without bound.
@Test
public void acquireBlocksCallingThreadUnderFlood() throws Exception {
  // Configure a very low global QPS to simulate flood conditions cheaply.
  Field qpsField = GlobalRateLimiter.class.getDeclaredField("QPS");
  qpsField.setAccessible(true);
  qpsField.set(null, 1.0); // 1 request/sec global budget

  Field rlField = GlobalRateLimiter.class.getDeclaredField("rateLimiter");
  rlField.setAccessible(true);
  rlField.set(null, RateLimiter.create(1.0));

  Args.getInstance().setRateLimiterApiNonBlocking(false); // default

  int concurrentAttackers = 50; // simulates 50 unauthenticated clients from distinct IPs
  ExecutorService pool = Executors.newFixedThreadPool(concurrentAttackers);
  CountDownLatch startedAll = new CountDownLatch(concurrentAttackers);
  long start = System.nanoTime();

  List<Future<?>> futures = new ArrayList<>();
  for (int i = 0; i < concurrentAttackers; i++) {
    final int idx = i;
    futures.add(pool.submit(() -> {
      RuntimeData rd = runtimeDataFor("attacker-ip-" + idx); // distinct IPs bypass per-IP limiter
      startedAll.countDown();
      GlobalRateLimiter.acquirePermit(rd); // BLOCKS here — occupies the "handler" thread
    }));
  }

  // All 50 threads are consumed by acquirePermit(); none are free to service
  // legitimate requests until their turn on the 1 QPS budget arrives (~50s later).
  for (Future<?> f : futures) f.get(60, TimeUnit.SECONDS);
  long elapsedMs = (System.nanoTime() - start) / 1_000_000;

  // Demonstrates unbounded, linearly-growing thread-occupancy time as flood size grows,
  // confirming thread-pool exhaustion is reachable purely from unauthenticated input.
  Assert.assertTrue("Expected blocking proportional to flood size", elapsedMs > 40_000);
  pool.shutdownNow();
}
```
Expected result: all 50 simulated "handler threads" remain blocked inside `GlobalRateLimiter.acquire` for tens of seconds under a deliberately low QPS budget, demonstrating that a real deployment's bounded Jetty/gRPC thread pool would be fully occupied by blocked rate-limiter calls under a real flood, denying service to legitimate concurrent requests.
