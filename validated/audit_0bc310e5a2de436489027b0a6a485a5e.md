### Title
`GetAssetIssueListByNameServlet` performs an unbounded O(n) full asset-store scan with per-record bandwidth accounting, materially underpriced relative to per-request rate limiting - ([File: framework/src/main/java/org/tron/core/services/http/GetAssetIssueListByNameServlet.java])

### Summary
`GetAssetIssueListByNameServlet.fillResponse` calls `Wallet.getAssetIssueListByName`, which retrieves the entire asset-issue store via `getAllAssetIssues()` and filters it in Java, rather than performing an indexed lookup as `getAssetIssueById` does. This makes each request's CPU/IO cost scale linearly with the total number of assets ever issued on-chain (`N`), while the endpoint is rate-limited only by a flat per-request QPS counter, not by `N`.

### Finding Description
`GetAssetIssueListByNameServlet.fillResponse` (lines 45-57) calls `wallet.getAssetIssueListByName(...)`, which in `Wallet.java` performs: [1](#0-0) 
This retrieves the full `List<AssetIssueCapsule>` from `AssetIssueStore`/`AssetIssueV2Store` via `getAllAssetIssues()`, which iterates the entire underlying RocksDB column family and materializes every entry: [2](#0-1) 
The full list is then linearly filtered by name equality in a Java stream, and for every match `BandwidthProcessor.updateUsage(issueCapsule)` is invoked before appending to the response builder: [3](#0-2) 

By contrast, `getAssetIssueById` performs a single indexed key lookup (`chainBaseManager.getAssetIssueV2Store().get(...)`), which is O(1) regardless of store size: [4](#0-3) 

This servlet, like all HTTP servlets, extends `RateLimiterServlet`, whose `service()` method enforces only a flat per-endpoint QPS/permit check (default `DefaultBaseQqsAdapter`/`QpsRateLimiterAdapter` with a configured or default QPS), with no accounting for the size of the underlying data scanned per request: [5](#0-4) 
The rate limiter is purely request-count-based (QPS), defined per servlet class name via config or a default QPS constant, and has no notion of "cost per request" tied to store size: [6](#0-5) 

Because the rate limiter only throttles request *count*, and the per-request cost of this endpoint grows linearly with the number of assets ever created network-wide (an attacker-uncontrolled but publicly known and monotonically growing value), an unprivileged attacker sending unauthenticated GET/POST requests at the endpoint's configured QPS ceiling causes the node to perform `O(QPS × N)` work per unit time — while endpoints like `getassetissuebyid` cost `O(QPS × 1)` for equivalent request volume. This is a genuine underpriced-work asymmetry between two API endpoints intended for similar lookup purposes.

### Impact Explanation
Each request to `/getassetissuelistbyname` forces a full iteration of the asset-issue RocksDB store (`getAllAssetIssues()`), deserializing every `AssetIssueCapsule`, plus a `BandwidthProcessor.updateUsage` call for each name-matching entry. As the number of on-chain assets grows over time, this endpoint's cost grows without bound, but the QPS-based rate limiter treats it identically to O(1) endpoints. A remote, unauthenticated caller can repeatedly invoke this endpoint at the permitted QPS, sustaining CPU/DB-read load proportional to `QPS × N` on any full node exposing the HTTP API (including Solidity/PBFT variants that reuse the same servlet), degrading node responsiveness for other legitimate API and P2P traffic. This is a node-level resource-exhaustion concern rather than any consensus, funds, or authorization compromise.

### Likelihood Explanation
This requires no privileges beyond default access to a publicly exposed full-node HTTP API port (default enabled unless explicitly disabled), which is the intended threat model for HTTP API DoS assessment. It is fully repeatable: any GET/POST to `/getassetissuelistbyname` triggers the scan regardless of the `value` parameter (even a non-matching or empty name still requires the full `getAllAssetIssues()` scan before filtering). The cost scales with the live `N` — as of any given point in java-tron's history, `N` is in the tens of thousands (asset issuances are cheap on-chain), so the per-request cost, while today bounded, grows unfavorably against a flat QPS ceiling that does not adapt to `N`.

### Recommendation
Replace the linear scan-and-filter in `Wallet.getAssetIssueListByName` with an indexed lookup analogous to `getAssetIssueById`/`getAssetIssueByName` (e.g., maintain a name→ids index, or since asset names in java-tron are not guaranteed unique, maintain a name→list-of-ids secondary index) so the lookup cost is O(matches) rather than O(total assets). Alternatively, cap/paginate the underlying store scan (similar to `getAssetIssuesPaginated`) and/or introduce a request-cost-aware rate limiter (e.g., `IPQPSRateLimiterAdapter` combined with a stricter, size-independent QPS ceiling, or a dedicated per-request compute budget) for O(n) full-store-scan endpoints.

      AssetIssueCapsule c = mock(AssetIssueCapsule.class);

    when(chainBaseManager.getAssetIssueV2Store()).thenReturn(assetIssueV2Store);

    Wallet wallet = new Wallet();
    // inject chainBaseManager via reflection as needed by test harness...

    long start = System.nanoTime();
    wallet.getAssetIssueListByName(ByteString.copyFromUtf8("nonexistent-name"));
    return System.nanoTime() - start;
  }
