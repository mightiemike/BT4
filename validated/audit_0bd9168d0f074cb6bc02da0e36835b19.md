## Title
Silent gas underflow collapses `proving_gas` to zero instead of erroring, allowing the bouncer to under-account transaction weight - (File: crates/blockifier/src/bouncer.rs)

### Summary
`sierra_gas_to_steps_gas` in `crates/blockifier/src/bouncer.rs` performs a `checked_sub` and, on failure (underflow), silently substitutes `GasAmount::ZERO` instead of propagating an error, analogous to the reported `borgCore.sol` pattern where a failed bound check causes the intended value to be silently rewritten with an "empty" value rather than reverting. [1](#0-0) 

### Finding Description
`sierra_gas_to_steps_gas` computes `sierra_gas.checked_sub(cairo_primitives_gas)`. If `cairo_primitives_gas` (the gas attributed to builtins/opcodes such as `blake`) exceeds `sierra_gas`, the function does not return an error; it logs a debug message and returns `GasAmount::ZERO`: [1](#0-0) 

This value feeds `proving_gas_from_cairo_primitives_and_sierra_gas`, which adds the (possibly zeroed) steps-proving-gas to the cairo-primitives proving gas to compute a transaction's `proving_gas`: [2](#0-1) 

That result flows through `compute_proving_gas` → `get_tx_weights` → `BouncerWeights.proving_gas`, which is the quantity the bouncer uses to decide whether a transaction fits in the remaining block capacity (`try_update` / `has_room`): [3](#0-2) [4](#0-3) 

Rather than causing the sequencer to reject the malformed/underflowing computation (as `checked_add_panic_on_overflow`-style helpers do elsewhere in the same file for overflow, e.g. `vm_resource_to_gas_amount` panics on overflow), the underflow path silently substitutes zero, understating the transaction's true proving-gas cost.

### Impact Explanation
`proving_gas` is a core bouncer resource dimension enforced against `block_max_capacity` to keep a block within provable/executable bounds. If a crafted or unusual transaction (e.g., one exercising the `blake` opcode/builtin counters in a way that inflates `cairo_primitives_gas` relative to `sierra_gas`) can trigger this underflow, the sequencer will silently under-charge that transaction's proving-gas contribution instead of rejecting or correctly accounting for it. Because the bouncer accepts transactions based on this understated weight, a block can be built whose actual aggregate proving-gas exceeds the intended `block_max_capacity`, risking a block that cannot be proven or is inconsistent with resource limits — a correctness/liveness concern for block building and potential source of honest-node divergence if the underflow condition is data/path dependent and not deterministically reproduced identically across implementations.

### Likelihood Explanation
Reachability requires only a normal transaction whose execution produces builtin/primitive counters that outweigh its computed Sierra gas in the specific accounting used here — a state achievable by a transaction sender crafting calldata/contract calls to skew builtin usage (e.g., heavy use of the `blake` opcode) relative to Sierra gas metering, without any privileged access. The severity is bounded by how large a discrepancy an attacker can realistically induce and whether the discrepancy is large enough to meaningfully violate the block's proving-gas budget; this could not be fully confirmed without deeper verification of the exact relationship between `sierra_gas` accounting and the cairo-primitives gas costs for `blake`/other builtins that are not directly bounded by the same metering.

### Recommendation
Change `sierra_gas_to_steps_gas` (and any similarly structured `unwrap_or_else(|| GasAmount::ZERO)` fallback on `checked_sub` in resource/fee accounting) so that an underflow either (a) propagates a hard error causing the tx to be rejected/failed cleanly, or (b) is proven structurally impossible (i.e., add an invariant/assertion establishing `cairo_primitives_gas <= sierra_gas` upstream, and enforce it), rather than silently substituting zero for a value used in resource-accounting decisions such as bouncer capacity checks.

### Proof of Concept
Not independently reproduced within the scope of this review; the analysis is based on static code-path tracing from `sierra_gas_to_steps_gas` through `get_tx_weights`/`Bouncer::try_update`. Confirming exploitability requires constructing a transaction whose `CairoPrimitiveCounterMap`-derived gas (particularly for the `blake` builtin) exceeds the corresponding `sierra_gas` figure computed in `compute_sierra_gas`, which was not verified against the exact versioned-constants gas-cost tables in this session.

/// Computes the steps gas by subtracting the builtins' contribution from the Sierra gas.
pub fn sierra_gas_to_steps_gas(
    sierra_gas: GasAmount,
    cairo_primitives_counters: &CairoPrimitiveCounterMap,
    sierra_builtin_gas_costs: &BuiltinGasCosts,
) -> GasAmount {
    let cairo_primitives_gas =
        cairo_primitives_to_gas(cairo_primitives_counters, sierra_builtin_gas_costs);

    sierra_gas.checked_sub(cairo_primitives_gas).unwrap_or_else(|| {
        log::debug!(
            "Sierra gas underflow: cairo primitives gas exceeds total. Sierra gas: \
             {sierra_gas:?}, Cairo primitives gas: {cairo_primitives_gas:?}, Cairo primitives: \
             {cairo_primitives_counters:?}"
        );
        GasAmount::ZERO
    })
}
