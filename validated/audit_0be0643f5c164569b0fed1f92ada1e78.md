### Title
Missing Validation of `beneficiary_id` in `DeleteAccountAction` Permanently Burns Refunded Balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` unconditionally creates a balance-refund receipt addressed to the caller-supplied `beneficiary_id`, without checking that this account exists (only its syntactic validity is checked at admission). Because the generated receipt is a "system" refund receipt, if `beneficiary_id` does not exist (or cannot be implicitly created in that context), the transfer fails and the deleted account's entire remaining balance is permanently burned rather than returned to the signer or the beneficiary.

### Finding Description
`DeleteAccountAction { beneficiary_id: AccountId }` only requires `beneficiary_id` to be a syntactically valid account id (`validate_action_account_id`); nothing checks that the account actually exists on-chain at execution time. When the delete action executes, `action_delete_account` pays out the account's remaining balance by pushing a refund receipt to `beneficiary_id` unconditionally: [1](#0-0) 

This receipt is created via `Receipt::new_balance_refund`, which — like all refund receipts — is a system-predecessor receipt (`predecessor_id == "system"`), confirmed by the runtime's own refund-execution logic which treats such receipts specially: [2](#0-1) 

When the receiver of a Transfer action does not exist, `check_account_existence`/`implicit_creation_allowed` rejects account creation specifically for refund receipts ("Refund can never create an account"): [3](#0-2) 

And when a refund receipt fails (e.g., because the beneficiary account does not exist), the deposited amount is not returned to anyone — it is burned: [4](#0-3) 

This is directly analogous to the reported Napier bug class: a critical, caller-supplied "destination" parameter (`rebalancer` in the report; `beneficiary_id` here) is accepted without verifying it is a valid/usable target, and the omission leads to unrecoverable loss of value. The existing test suite explicitly documents and exercises this exact failure mode for a plain refund receipt to a non-existent account: [5](#0-4) 

and separately documents that tests must fund an existing beneficiary specifically to avoid triggering this burn: [6](#0-5) 

### Impact Explanation
Any unprivileged account owner submitting a self-authored `DeleteAccount` transaction can specify an arbitrary syntactically-valid but non-existent `beneficiary_id` (a typo, a never-created sub-account, an account that was itself deleted between signing and execution, etc.). Instead of the delete failing safely or the funds returning to the signer, the entire remaining account balance is irrecoverably burned — a direct, protocol-level "permanently frozen/lost funds" outcome triggered by a single ordinary transaction, with no privileged access required. Since token burn reduces the total supply, this is also a real (if attacker-self-inflicted or accidental-user) value-destruction bug, not merely a UX foot-gun, and it can be repeated by any account.

### Likelihood Explanation
High for accidental occurrence (typo'd beneficiary, referencing an account that no longer exists, or a beneficiary account being deleted in the same or an earlier chunk) and trivially reproducible by anyone: a normal user only needs to submit one `DeleteAccountAction` naming a non-existent — but well-formed — account id. No special privileges, timing races across validators, or malicious peers are required.

### Recommendation
Before executing a `DeleteAccount` action, verify that `beneficiary_id` refers to an account that exists (or reject up front if it is not resolvable), or alternatively route the payout through a mechanism that is not treated as an unrecoverable "refund" burn on failure — e.g., fail the whole `DeleteAccount` action with an explicit error (`BeneficiaryAccountDoesNotExist`) if the beneficiary account cannot be found in state, rather than allowing the delete to succeed and the payout receipt to silently burn the funds.

### Proof of Concept
1. Account `alice.near` has non-zero balance and no locked stake.
2. `alice.near` signs and submits `DeleteAccount { beneficiary_id: "nonexistent-typo.near" }` on itself (self-delete), where `nonexistent-typo.near` has never been created.
3. `action_delete_account` deletes `alice.near` and enqueues `Receipt::new_balance_refund("nonexistent-typo.near", alice_balance)` — see `runtime/runtime/src/actions.rs:380-386`.
4. When that refund receipt executes, `check_account_existence`/`implicit_creation_allowed` reject account creation for a refund (`is_refund => false`), the Transfer action fails with `AccountDoesNotExist`.
5. Because the failing receipt's predecessor is `system` (a refund receipt), `runtime/runtime/src/lib.rs:1047-1054` adds `alice_balance` to `other_burnt_amount` instead of refunding it anywhere.
6. `alice.near`'s entire balance is permanently destroyed with no recovery path, confirmed by the existing regression test `refund_may_not_create_universal_account` (`runtime/runtime/src/tests/apply.rs:6882-6926`), which demonstrates the identical fail-then-burn mechanics for a refund receipt sent to a non-existent account.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
