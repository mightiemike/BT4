## Title
`ensure_match_transaction_info` does not validate hot-state/position-state checkpoint hashes, allowing replay-verify and chunk-verify to accept a divergent authenticated state root - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info` is the single invariant that binds a freshly-executed `TransactionOutput` to the previously-committed, accumulator-proven `TransactionInfo` during chunk-executor verification (`execution/executor/src/chunk_executor/mod.rs::verify_execution`) and archive replay (`storage/db-tool/src/replay_on_archive.rs::execute_and_verify`). The function explicitly checks status, gas, write-set hash, and event-root hash, but — as its own inline comment states — it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)". This is directly analogous to the external report's pattern: a validation function exists and looks complete, but omits a check that is required to guarantee the operation is safe, so a value that should fail validation is accepted, and downstream commitment/authentication silently diverges from the real correct value.

## Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates the recomputed `TransactionOutput` against a trusted `TransactionInfo` (obtained from a proof or from prior storage) by checking:
- execution status
- gas used
- write-set hash (`state_change_hash`)
- event root hash

but it explicitly does **not** verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as documented in its own TODO comment: [2](#0-1) 

This function is the sole verification gate used in two integrity-critical flows:

1. **Chunk executor verify-execution** (`execution/executor/src/chunk_executor/mod.rs::verify_execution`), used when re-executing and verifying transactions from a trusted source (e.g., state-sync catching up, or verify mode) against previously-persisted `TransactionInfo`s/write-sets/events: [3](#0-2) 

2. **`db-tool replay-on-archive`** (`storage/db-tool/src/replay_on_archive.rs::execute_and_verify`), the tool operators use to confirm that replaying transactions from a backup archive against local execution reproduces the exact same, authenticated ledger state: [4](#0-3) 

Both call sites treat `ensure_match_transaction_info` returning `Ok(())` as proof that "local execution == authenticated on-chain result." But because the state-checkpoint-derived hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are never compared, a locally-computed state root that differs from the one actually committed/proven on-chain will not be detected by this check — as long as the write-set (deltas) and events are unchanged. The `position_state_checkpoint_hash` and `hot_state_checkpoint_hash` are carried inside `TransactionInfoV1` (see `types/src/transaction/mod.rs:2352-2364`) and flow from `DoStateCheckpoint`/`DoLedgerUpdate` (`execution/executor/src/workflow/do_ledger_update.rs:30-45`, `execution/executor/src/chunk_executor/mod.rs:373-394`) into the accumulator-hashed `TransactionInfo`. These are exactly the fields this comparator skips.

## Impact Explanation
This breaks the "proof and storage pivot" invariant that VM outputs and derived state roots must survive verification unchanged and stay bound to the correct authenticated root:
- In chunk-executor `verify_execution`, a bug in the JMT/position-state/hot-state root computation (e.g., in `DoStateCheckpoint`, sharded merklization, or the native-position tree) that changes the computed checkpoint root but preserves write-set/event/gas/status equivalence would pass verification silently, since only write-set and event hashes are checked, not the derived state root.
- In `replay_on_archive`, an operator relying on a "clean" replay-verify result to confirm database integrity or detect a fork/divergence would get a false "verified" result even though the position/hot-state root diverges from the archived, ledger-info-authenticated value — undermining the primary purpose of the tool (detecting exactly this class of divergence, including potential non-determinism or storage bugs).
- Because `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` are part of `TransactionInfoV1`, which is hashed into the transaction accumulator and ultimately into the `LedgerInfo` root that validators sign, any code path that treats a passing `ensure_match_transaction_info` as sufficient evidence of correctness (rather than performing the full accumulator-hash comparison) is at risk of accepting or propagating a state that does not match the committed, signed ledger.

This is high impact under the state-commitment/proof-integrity gate: it is a real, silent gap in verification of authenticated state roots in a production code path (chunk-executor verify + db-tool used by operators), though the comment shows the authors are aware and the feature (`compute_trading_native_state_roots`) is gated and not fully deployed/enabled by default.

## Likelihood Explanation
Likelihood is moderate, not automatic: exploiting this requires an actual divergence to exist between the locally-recomputed checkpoint/position/hot-state root and the authenticated one, while write-set and event hashes still match (e.g. a bug in tree merklization, a non-deterministic ordering issue, or a sharding bug affecting only the summarized root but not the flat write-set). The comparator gap doesn't itself create a corrupting write; it removes a would-be detection mechanism for such corruption, and the authors' own comment ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS") indicates this is a known, pre-existing gap tied to a not-yet-fully-enabled feature. It is a latent verification weakness rather than an immediately triggerable state-corruption bug from an unprivileged actor.

## Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when present in the recomputed side), and `position_state_checkpoint_hash` against the corresponding values recomputed locally, failing verification on mismatch — consistent with how `write_set_hash` and `event_root_hash` are already checked. This should be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state features are enabled on mainnet, per the code's own TODO.

## Proof of Concept
Not independently reproducible from static analysis alone: triggering the divergence requires a bug in state/hot-state/position-state root computation that is independent of write-set contents (out of scope to construct here). The concrete, verifiable finding is the structural gap in `ensure_match_transaction_info` itself — confirmed by its own inline comment and by tracing both of its call sites (`chunk_executor::verify_execution` and `replay_on_archive::execute_and_verify`), both of which rely on it as their complete correctness check.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
