### Title
`ensure_match_transaction_info()` skips checkpoint-hash comparison, letting a diverged position/hot-state root pass replay verification - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the authenticated-integrity check used by replay/backup verification tooling (`db-tool`'s `replay_on_archive` and `aptos-debugger`) to confirm that a locally re-executed transaction output matches the committed `TransactionInfo` pulled from a trusted backup/archive. The function only compares status, gas used, write-set hash (`state_change_hash`), and event root hash — it explicitly does not compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields carried by `TransactionInfo`/`TransactionInfoV1`.

### Finding Description [1](#0-0) 

The comment on the function itself acknowledges the gap: [2](#0-1) 

This mirrors the external report's root cause exactly: a state-tracking check ("`preTradeBalance`") is computed/verified for only a subset of the relevant branches, so divergence in an unchecked branch is silently accepted downstream. Here, `ensure_match_transaction_info` is the "pre/post" integrity comparator between the re-executed local result and the trusted expected `TransactionInfo`, but it only asserts equality on `state_change_hash` (write-set hash) and `event_root_hash`; it never asserts equality on `state_checkpoint_hash` (the periodic Sparse Merkle Tree root over world state), `hot_state_checkpoint_hash`, or the newer `position_state_checkpoint_hash` (native "trading" state root gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`).

This function is called from two verification call sites:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which re-executes historical transactions from a backup and calls `ensure_match_transaction_info` per transaction to decide pass/fail for the whole replay-verify run. [3](#0-2) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`, used for offline debugging/verification against a validator interface.

Because the comparator never checks `state_checkpoint_hash`/`position_state_checkpoint_hash`, if VM execution (or the state-checkpoint/native-position pipeline in `execution/executor/src/workflow/do_state_checkpoint.rs` and `do_ledger_update.rs`, which do assemble these hashes into `TransactionInfo`) produces a divergent state root — e.g., due to a bug in accumulating/merklizing native position state, a hard-fork/version-skew bug, or corrupted intermediate state — `replay_on_archive`/`aptos-debugger` will still report the replay as successful as long as the write-set hash and event root happen to match.

### Impact Explanation
This breaks the proof/commitment-integrity invariant this tool exists to enforce: replay-verify is Aptos's independent-recomputation check that a version's committed ledger state is the correct VM result. A tool that is supposed to catch state-root divergence but structurally cannot detect divergence in `state_checkpoint_hash`/`position_state_checkpoint_hash` means a corrupted or bugged state-checkpoint/proof root (e.g., from a native-position accumulator bug) could exist in the archive and go completely undetected by replay-verify, i.e., an authenticated proof/root value diverges from the correct VM result and is accepted as "verified" — precisely the category the gate calls out ("Wrong accumulator root... accepted as valid", "Hard-fork-only divergence during commit, replay, restore, or proof verification").

### Likelihood Explanation
The gap is deterministic and always present (not a race or timing issue) — any run of `replay_on_archive` or `aptos-debugger` against a payload whose write-set/events match but whose checkpoint/position state root differs will pass silently. Its trigger, however, depends on a separate root-cause bug elsewhere (in state-checkpoint or native-position root computation) actually producing a wrong root; this comparator does not itself corrupt data, it only fails to detect corruption. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`position_state_checkpoint_hash` is a newer feature path referenced across `execution/executor-types/src/state_checkpoint_output.rs`, `execution/executor/src/workflow/do_ledger_update.rs`, and `types/src/transaction/mod.rs`, increasing the chance this verification gap is currently live and unaddressed.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed `TransactionInfo` and the expected one whenever both sides have these fields populated (accounting for the periodic/None nature of `state_checkpoint_hash`), so replay-verify tooling cannot silently pass over a divergent state or native-position root. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` more broadly, per the existing TODO.

### Proof of Concept
1. Author a `TransactionInfoV1` locally-computed test double whose `write_set`/`events` match the expected `TransactionInfo` exactly (so `state_change_hash`/`event_root_hash` match) but whose `state_checkpoint_hash`/`position_state_checkpoint_hash` differ (simulating a divergent state-checkpoint/position root from a buggy accumulator).
2. Call `TransactionOutput::ensure_match_transaction_info(version, &expected_txn_info, ..)` with this mismatched pair.
3. Observe the call returns `Ok(())` despite the checkpoint/position roots differing — confirming the comparator does not detect this class of divergence, exactly as `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` would when consuming real archived data.

Note: I could not fully trace whether any other independent guard (outside this comparator) currently re-validates `position_state_checkpoint_hash` during `replay_on_archive`/`aptos-debugger` runs; my search of call sites found only the three references above, and no additional checkpoint-hash assertion in those tools.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
