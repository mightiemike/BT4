### Title
`TransactionOutput::ensure_match_transaction_info` never validates state/hot-state/position checkpoint hashes, letting chunk-execution accept outputs whose committed root diverges from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
The Sherlock report is about a "gate" check that is supposed to reject an operation when a resolved/committed state doesn't match expectations, but due to an indirection/format defect the gate always evaluates to the wrong (permissive) answer, silently letting stale/incorrect state through. In `aptos-core`, `TransactionOutput::ensure_match_transaction_info` is the local, self-documented analog: it is the function used at chunk-execution / replay time to check that a locally produced `TransactionOutput` matches the accumulator-authenticated `TransactionInfo`, but it explicitly omits comparing the checkpoint-root fields, so a divergent locally-computed state root can pass this "match" gate.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) checks status, gas used, write-set hash (`state_change_hash`), and event root hash against the trusted `TransactionInfo`, but the function's own trailing comment admits: [1](#0-0) 
states that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)", i.e. it never verifies that the checkpoint-root fields carried in the authenticated `TransactionInfoV1` (bound into the transaction accumulator and thus proof-verified by peers/light clients) equal anything computed locally.

This function is invoked from the chunk executor's commit-verification path: [2](#0-1) 
(call site confirmed via `ensure_match_transaction_info` usage in `execution/executor/src/chunk_executor/mod.rs`), as well as from `aptos-debugger` and the CLI replay tooling. `TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as authenticated, accumulator-proven fields: [3](#0-2) 

The checkpoint hashes are computed and cross-checked in a *separate* pipeline stage, `DoStateCheckpoint::run` / `get_state_checkpoint_hashes`, but only when the caller supplies `known_state_checkpoints` / `known_hot_state_checkpoints` / `known_position_state_checkpoints` derived from the proof: [4](#0-3) 
Any caller (debugger, CLI replay/verify tool, or a future/incomplete chunk-executor code path) that calls `ensure_match_transaction_info` without independently and correctly feeding through that separate checkpoint-hash cross-check has no invariant left protecting the checkpoint roots — the "match" assertion silently succeeds even though the underlying Merkle/JMT checkpoint state (main state, hot state, or the new native-position tree) actually diverges from the authenticated ledger.

This is structurally the same defect class as the Solidity report: a gate meant to detect "has the authoritative/resolved state diverged from what we're about to accept" is evaluated using an incomplete/incorrect binding to the authenticated value, so the check passes when it should fail.

### Impact Explanation
If a node's local re-execution produces a `TransactionOutput` whose state checkpoint root (or hot-state / native-position root, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` are enabled) differs from the value proven in the accumulator-authenticated `TransactionInfo`, `ensure_match_transaction_info` will report a match anyway. Any code path relying solely on this function (debugger-driven simulations, CLI-based `replay_on_archive`/verify tooling, or any chunk-execution helper that doesn't also route through `DoStateCheckpoint`'s `known_*_checkpoints` cross-check) will treat a corrupted/incorrect state root as validated. This directly falls under the state-commitment/proof-integrity gate: an authenticated, proof-bound value (`state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) is not actually verified where the code claims to be checking "does output match transaction info."

### Likelihood Explanation
The defect is not gated behind attacker input — it's a straightforward missing check in a widely-reused verification helper, only bounded by how many call sites actually rely on it as the sole cross-check. It is explicitly acknowledged by the code's own TODO, which reduces "surprise" but confirms it as a real, currently-uncorrected gap that must be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`". Given `HOT_STATE_ROOT_IN_TXN_INFO` and `TRANSACTION_INFO_V1` are being rolled out as permanent features, any interim reliance on this comparator (debugging/replay tooling, or partial chunk-executor logic) is exposed today; full chunk-execution commit safety appears to still depend on the parallel `DoStateCheckpoint` known-checkpoint mechanism being correctly wired everywhere this comparator is used.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` against the corresponding locally-computed checkpoint roots whenever those fields are `Some`, rather than relying on callers to separately thread `known_*_checkpoints` through `DoStateCheckpoint`. Add a regression test that constructs a `TransactionOutput`/`TransactionInfo` pair with mismatched checkpoint hashes and asserts `ensure_match_transaction_info` returns an error before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet.

### Proof of Concept
1. Build a `TransactionInfoV1` with `state_checkpoint_hash = Some(H1)` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` set) representing the authenticated, accumulator-proven checkpoint root.
2. Construct a `TransactionOutput` from a locally re-executed transaction whose actual checkpointed state Merkle root is `H2 != H1` (e.g. simulate a bug/divergence in hot-state or native-position materialization), but with matching status, gas, write-set hash, and event root hash.
3. Call `txn_output.ensure_match_transaction_info(version, &txn_info, None, None)` as done in `execution/executor/src/chunk_executor/mod.rs` / `aptos-debugger` / CLI replay tooling.
4. Observe `Ok(())` is returned despite `H1 != H2`, i.e., the function reports a match even though the authenticated checkpoint root diverges from the locally computed one — confirming the gap noted in the code's own comment at `types/src/transaction/mod.rs:2197-2203`.

Note: I was unable to fully trace every call site of `ensure_match_transaction_info` (particularly whether the current mainline chunk-executor commit path always separately validates checkpoint hashes via `DoStateCheckpoint`'s `known_*_checkpoints` before ever reaching this comparator, or whether some paths — debugger/CLI replay especially — use it as the sole check). This uncertainty affects whether the gap is exploitable on current mainnet paths versus only in debugging/replay tooling and future feature rollouts; further tracing through `execution/executor/src/chunk_executor/mod.rs` and `aptos-debugger` call graphs would be needed to confirm end-to-end mainnet reachability.
