### Title
L1→L2 Messages Are Irrevocably Consumed Even When Execution Reverts Due to Fixed Resource Bounds, Permanently Freezing the Intended State Change - ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs])

### Summary
Like the Taiko `QuotaManager` bug where a fixed cap (`consumeQuota`) is enforced asymmetrically — checked on withdrawal but not on the corresponding recall path — Starknet's L1 handler execution enforces a fixed, non-configurable-per-message resource ceiling (`l1_handler_max_amount_bounds`) *after* the L1→L2 message has already been irrevocably marked as consumed. If the transaction requires resources exceeding these bounds, execution is reverted and rolled back, but the message consumption is not reversible — there is no mechanism analogous to a "recall" that lets the L1 sender retry or reclaim the intended action/funds.

### Finding Description
When an `L1HandlerTransaction` is executed, the sequencer consumes the corresponding L1→L2 message as an unconditional first step of the OS transaction flow: `consume_l1_to_l2_message(execution_context=tx_execution_context, nonce=nonce);` runs before the entry point is even attempted [1](#0-0) .

In the Rust-side executor, `L1HandlerTransaction::execute_raw` runs the entry point with a hard-capped `remaining_gas` bound taken from `block_context.versioned_constants.os_constants.l1_handler_max_amount_bounds` [2](#0-1) . After execution, a **post-execution** check enforces that actual gas usage stays within these bounds via `FeeCheckReport::check_all_gas_amounts_within_bounds`; if the resources needed by the L1 message's intended call exceed the bound, the execution state is aborted (`execution_state.abort()`), the transaction is treated as reverted, and no state change is committed for the intended action [3](#0-2) .

Crucially, the batcher records this transaction as consumed regardless of whether it reverted: `execution_data.consumed_l1_handler_tx_hashes.insert(tx_hash)` is called unconditionally for any `InternalConsensusTransaction::L1Handler`, before checking whether the execution result was `Ok` or `Err` [4](#0-3) . This is explicitly validated by the test `failed_l1_handler_transaction_consumed`, which asserts that even a failed/erroring L1 handler transaction ends up in `consumed_l1_handler_tx_hashes` [5](#0-4) , and by `test_l1_handler_resource_bounds`, which shows a message exceeding the L2 gas bound is reverted post-execution with zero fee and no state change [6](#0-5) .

This mirrors the structure of the Taiko bug precisely: a fixed resource ceiling (`quota` ↔ `l1_handler_max_amount_bounds`/`L1_HANDLER_L2_GAS_MAX_AMOUNT`) is enforced on one leg of a cross-domain message flow (execution), while the irreversible bookkeeping step (quota consumption ↔ L1 message nonce consumption) happens independent of whether the operation actually succeeds. Once the L1 message's nonce is consumed on L2, the L1 sender has no way to "recall" or resubmit the same message with more resources — the message is permanently spent and the intended cross-layer action (e.g., minting/crediting L2 state on behalf of an L1 depositor) never occurs.

### Impact Explanation
Any L1 message whose target contract requires more Sierra gas / builtins / L1 data gas than the fixed `l1_handler_max_amount_bounds` will always revert on L2, yet the message nonce is permanently consumed. Since these bounds are versioned constants fixed by the network (not configurable per-message and not enforced pre-consumption on L1), any legitimate cross-layer operation whose gas needs exceed the bound is permanently lost — matching "permanent freezing of funds" / inability of a legitimate L1 message sender to have their message honored, with no recovery path once consumed.

### Likelihood Explanation
This triggers whenever a contract handling `l1_handler` calls (e.g., deposit handlers on L2 for a bridge built by users) has logic whose gas cost can exceed the current `l1_handler_max_amount_bounds` (e.g., due to complex recipient contract logic, large state diffs, or many storage writes). Since `l1_handler_max_amount_bounds` is a network-wide constant, any dApp author is unaware of the exact bound until it silently reverts and consumes the message; this is reachable by any L1 message sender (an explicitly in-scope actor per this review's rules) without any privileged access.

### Recommendation
Consider validating, prior to consuming the L1→L2 message, that the estimated/maximum resource usage for the target call cannot exceed `l1_handler_max_amount_bounds`, or provide a mechanism to reclaim/retry a message whose execution failed due to exceeding these bounds (analogous to Taiko's suggestion to validate against quota before allowing an operation that cannot later be reversed).

### Proof of Concept
1. Deploy an L2 contract with an `l1_handler` entry point whose execution (for certain inputs) requires L2 gas usage above `l1_handler_max_amount_bounds.l2_gas` (see `os_constants.l1_handler_max_amount_bounds`, exercised in `test_l1_handler_resource_bounds` [6](#0-5) ).
2. Send a message from L1 targeting that entry point with such inputs.
3. The sequencer processes the resulting `L1HandlerTransaction`: it consumes the L1→L2 message via `consume_l1_to_l2_message` [7](#0-6) , then executes and hits the post-execution bound check, causing `execution_state.abort()` and a reverted receipt with `fee == Fee(0)` [8](#0-7) .
4. The batcher nonetheless records the tx hash in `consumed_l1_handler_tx_hashes` [9](#0-8) , permanently marking the L1 nonce as used with no interior state change ever applied and no way for the L1 sender to resubmit.

#[rstest]
#[case(L1Gas, GasAmount(1))]
// Sufficient to pass execution (enough gas to run the transaction), but fails post-execution
// resource bounds check.
#[case(L2Gas, GasAmount(200000))]
#[case(L1DataGas, GasAmount(1))]
fn test_l1_handler_resource_bounds(#[case] resource: Resource, #[case] new_bound: GasAmount) {
    let test_contract = FeatureContract::TestContract(CairoVersion::Cairo1(RunnableCairo1::Casm));

    // Set to true to ensure L1 data gas is non-zero.
    let use_kzg_da = true;

    let mut block_context = BlockContext::create_for_account_testing_with_kzg(use_kzg_da);
    let chain_info = block_context.chain_info.clone();
    let mut state = test_state(&chain_info, BALANCE, &[(test_contract, 1)]);
    let contract_address = test_contract.get_instance_address(0);

    // Modify the resource bound for the tested resource.
    let os_constants = Arc::make_mut(&mut block_context.versioned_constants.os_constants);
    match resource {
        L1Gas => os_constants.l1_handler_max_amount_bounds.l1_gas = new_bound,
        L2Gas => os_constants.l1_handler_max_amount_bounds.l2_gas = new_bound,
        L1DataGas => os_constants.l1_handler_max_amount_bounds.l1_data_gas = new_bound,
    }

    let tx = l1handler_tx(Fee(1), contract_address);

    let execution_info = tx.execute(&mut state, &block_context).unwrap();

    assert_matches!(
        execution_info,
        TransactionExecutionInfo {
            validate_call_info: None,
            execute_call_info: None,
            fee_transfer_call_info: None,
            revert_error: Some(RevertError::PostExecution(FeeCheckError::MaxGasAmountExceeded {
                resource: r,
                max_amount,
                actual_amount
            })),
            // TODO(Arni): consider checking other fields of the receipt.
            receipt: TransactionReceipt { fee, .. },
        } if r == resource && new_bound == max_amount && actual_amount > max_amount && fee == Fee(0)
    );
}
