### Title
`IdempotentPromiseHandler` marks the `afterAuth` hook as "run" before it succeeds, letting a failed token-exchange auth flow return success without completing `afterAuth` - ([File: packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts])

### Summary
`IdempotentPromiseHandler.handlePromise` records an `identifier` (the session token JWT) as "already handled" synchronously, *before* awaiting the wrapped promise (the app's `afterAuth` hook). If that promise later rejects, the identifier is never removed from the map — it only expires after a 60-second TTL. Any subsequent token-exchange request using the same session token within that window will see the identifier as already claimed and will silently skip calling `afterAuth`, yet the surrounding authentication flow proceeds to treat the request as fully authenticated. This mirrors the reported bug class: an action is marked "used/done" independently of, and before, the actual critical side-effect (here, `afterAuth`) actually completing.

### Finding Description
`isPromiseRunnable` marks the identifier used immediately: [1](#0-0) 

This is invoked from the token-exchange auth strategies used by `shopify-app-remix` and `shopify-app-react-router` (and the analogous Express middleware) to wrap the `afterAuth` hook, keyed by the raw session token: [2](#0-1) [3](#0-2) 

`triggerAfterAuthHook` is what actually runs the developer-supplied `afterAuth` hook (often used for essential setup like webhook registration or billing enforcement, per the library's own docs): [4](#0-3) 

Sequence of events:
1. A token-exchange request comes in with `sessionToken` T. `authenticate()` exchanges the token, stores the offline/online session, then calls `handleAfterAuthHook`, which calls `idempotentPromiseHandler.handlePromise({identifier: T, ...})`.
2. `isPromiseRunnable(T)` returns `true` and **immediately marks T as claimed** in the map, then `promiseFunction()` (the `afterAuth` hook) is awaited.
3. If `afterAuth` throws (e.g., a transient network error registering webhooks, a billing check failure, or any application error), the outer `try/catch` in `authenticate()` converts this into a `500 Internal Server Error` response: [5](#0-4) 
   But **T remains marked as claimed** in `IdempotentPromiseHandler.identifiers` — nothing rolls it back on failure.
4. Any subsequent authenticate call using the same session token T (a client retry, a second concurrent tab, or a duplicate app-bridge request — all are the same "unprivileged" merchant/customer session) within the 60-second TTL window will call `handlePromise` again. `isPromiseRunnable(T)` now returns `false`, so `promiseFunction()` (the `afterAuth` hook) is **never invoked at all**, and `handlePromise` resolves successfully.
5. `authenticate()` sees no exception, returns `newSession`, and the caller proceeds as if the authentication (including `afterAuth`) fully succeeded — even though `afterAuth` never ran to completion (or ran and failed) on this identifier.

This is the same root cause described in the report: a critical, asynchronously-executed side effect is marked "done" independently of whether it actually finished successfully, and a second, unprivileged request path can observe the "done" marker and skip re-executing the action while the overall request is treated as successful.

### Impact Explanation
The `afterAuth` hook is documented as the place where apps perform install-time setup — registering webhooks, and per the library's migration docs, enforcing billing (`ensureBilling`) before allowing further app usage: [6](#0-5) 

Because the same JWT session token is reused as the idempotency key, and a first failed attempt "poisons" that identifier for up to 60 seconds, a single unprivileged actor (the installing merchant, or their embedded-app browser client which naturally retries fetches) can end up in a state where:
- The HTTP response to the client indicates the auth/token-exchange flow succeeded (a valid `Session` is returned and used downstream).
- The `afterAuth` hook — which may perform mandatory webhook registration or billing enforcement — is silently never executed for that attempt.

This can manifest as a **DoS of the auth handler's completion guarantees**: legitimate installs can silently skip mandatory setup logic, or (if the hook enforces billing) result in bypassing that enforcement, without any error being surfaced to the app or the merchant on the second/retried request.

### Likelihood Explanation
Triggering the first failure does not require special privileges — any transient error in `afterAuth` (network blip calling Shopify APIs, a webhook-registration failure, a thrown error in application code) suffices, and this is easily reproducible by an app installer who can force retries (e.g., duplicate requests from App Bridge, double-clicking install, or simply having a flaky network) using their own, legitimately-obtained session token. No forged credentials or cross-tenant access is needed — only a plausible failure path in the `afterAuth` hook combined with a retried request bearing the same session token during the 60-second window.

### Recommendation
`IdempotentPromiseHandler` should only mark an identifier as "done" after `promiseFunction()` resolves successfully; on rejection it should remove/never insert the identifier (or track failure state distinctly) so that a subsequent request with the same identifier retries the action, and the outer response should not be treated as a full success while the guarded action has not completed. Recommended change:

```ts
// packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts
async handlePromise({promiseFunction, identifier}: IdempotentHandlePromiseParams) {
  if (!this.isPromiseRunnable(identifier)) return;
  try {
    await promiseFunction();
  } catch (error) {
    this.identifiers.delete(identifier); // allow retry on failure
    throw error;
  } finally {
    this.clearStaleIdentifiers();
  }
}
```
Apply the same fix in the Express and React Router copies of this class.

### Proof of Concept
1. Configure an app with `hooks.afterAuth` that fails on its first invocation (e.g., simulate a transient failure by throwing once, or rely on a real flaky webhook-registration call).
2. Perform token exchange with a session token `T` (embedded app / App Bridge flow) — `authenticate()` runs, `afterAuth` throws, and the client receives a `500` response. Note that `IdempotentPromiseHandler.identifiers` now contains `T`.
3. Immediately retry the request with the **same** session token `T` (still valid, well within its ~1 minute JWT lifetime and within the 60s TTL).
4. Observe that the second request succeeds (a valid `Session` is returned, `next()`/the loader proceeds), but `afterAuth` is never invoked on this second call — confirmable by adding a call counter/log inside the hook, which will show it was called once (and failed) yet the app proceeds as fully authenticated on the retry.

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }
