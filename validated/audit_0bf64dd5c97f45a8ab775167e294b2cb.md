## Analysis: Missing shop/token binding check in `tokenExchange()`

The reported bug pattern — validation logic that receives data needed to bind an operation to the correct identity, but never actually uses it, producing an installation/operation that trusts an unverified caller-supplied value — has a structural analog in the shopify-app-js token exchange flow.

### Root cause

`tokenExchange()` in [1](#0-0)  decodes the session token purely to validate its signature/audience, but never cross-checks the decoded payload's shop claim (`dest`) against the `shop` parameter supplied by the caller: [2](#0-1) 

`shop` is taken as-is from the caller, sanitized for format only via `sanitizeShop`, and used to build the outbound token-exchange request: [3](#0-2) 

The decoded JWT `payload` (which contains `dest`, the shop the token was actually issued for) is discarded immediately after the signature check — its `dest`/`iss` claim is never compared to the `shop` argument, the same "provided-but-unused validation data" pattern as `_enablePolicies()` failing to consume `allowedERC7739Content`.

### Why this matters

The library's own documentation explicitly instructs developers to derive `shop` from the request query string, not from the token itself: [4](#0-3) 

That means any app built directly against the documented public API (`shopify.auth.tokenExchange`) — rather than the higher-level `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router` wrappers — passes an attacker-controllable `shop` (from `req.query.shop`, an anonymous, unauthenticated HTTP parameter) alongside a session token, with **no code path in `tokenExchange()` verifying they refer to the same shop**.

By contrast, the higher-level packages avoid this exact issue by deriving `shop` from the decoded payload's `dest` instead of the query string, e.g. [5](#0-4)  and [6](#0-5) . This inconsistency confirms the omission is a genuine gap in the core `tokenExchange()` function rather than intentional design — the safe binding logic exists elsewhere in the codebase but was not applied here.

### Caveat

Whether this is practically exploitable to obtain a cross-tenant access token depends on Shopify's remote OAuth token-exchange endpoint independently rejecting a `subject_token` whose issuer doesn't match the target shop's domain — a server-side control outside this repository that I cannot verify. Within `shopify-app-js` itself, the missing dest/shop binding check is a concrete, provable root-cause defect: `tokenExchange()` receives the data needed to bind the operation to a specific shop and simply never uses it, matching the reported bug class exactly, but I cannot confirm end-to-end cross-tenant impact without visibility into Shopify's server-side enforcement.

### Title
Unverified shop/session-token binding in `tokenExchange()` allows shop-parameter spoofing - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
`tokenExchange()` decodes the caller-supplied session token only to validate its signature and audience, but never compares the token's `dest` claim (the shop it was actually issued for) against the separately supplied `shop` argument, which the library's own documentation instructs developers to source from an anonymous request's query string.

### Finding Description [7](#0-6)  shows `decodeSessionToken` is awaited solely for its side effect of throwing on invalid/expired/wrong-audience tokens; its return value (containing `dest`) is discarded. The `shop` used to build the `subject_token` exchange request is instead the raw, format-sanitized caller-supplied value from [8](#0-7) . The documented calling convention feeds this `shop` directly from `req.query.shop`, an anonymous/unauthenticated request parameter, per [4](#0-3) .

### Impact Explanation
If Shopify's remote token-exchange endpoint does not independently enforce that the `subject_token`'s issuer domain matches the shop being addressed, an app built directly on the documented `shopify.auth.tokenExchange` API (rather than the `shopify-app-remix`/`shopify-app-express`/`shopify-app-react-router` wrappers, which safely derive `shop` from the JWT `dest` claim instead of the query string) could have a token minted or a session stored under an attacker-chosen shop identifier, misassociating credentials across tenants.

### Likelihood Explanation
Requires a developer to follow the library's own documented usage pattern literally (deriving `shop` from the query string) instead of using the safer higher-level packages, and requires the remote Shopify OAuth server to not perform its own issuer/shop consistency check — the latter is outside this repository's visibility.

### Recommendation
Have `tokenExchange()` decode the session token, derive `shop` from `payload.dest` (as the higher-level packages already do), and either ignore/validate the caller-supplied `shop` against it, throwing if they disagree — mirroring how `perform-token-exchange.ts` and `getSessionTokenContext` bind shop identity to the token's own claims rather than caller input.

### Proof of Concept
Not independently reproducible from this repository alone, since confirming exploitability requires observing whether Shopify's production `/admin/oauth/access_token` endpoint rejects a `subject_token` whose `dest` does not match the shop in the request URL. The code-level defect — using `req.query.shop`-sourced `shop` for the exchange target while discarding the token's own `dest` claim — is directly demonstrated by [1](#0-0)  combined with the documented calling convention in [4](#0-3) .
