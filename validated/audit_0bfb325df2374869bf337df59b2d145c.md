### Title
Uncaught `ArithmeticException` from `BigInteger.modInverse(0,…)` in `Fp12.inverse()` chain causes non-deterministic precompile crash - ([File: crypto/src/main/java/org/tron/common/crypto/zksnark/Fp12.java])

### Finding Description
`PairingCheck.finalExponentiation()` unconditionally calls `el.inverse()` on the accumulated Miller-loop product without checking `el.isZero()`: [1](#0-0) 

`Fp12.inverse()` computes the "norm" `t2 = t0.sub(t1.mulByNonResidue())` and then calls `t2.inverse()` on the resulting `Fp6`, which recurses into `Fp2.inverse()` and ultimately `Fp.inverse()`, which calls `v.modInverse(P)`: [2](#0-1) [3](#0-2) 

`BigInteger.modInverse` throws `ArithmeticException` when the value is `0`. Algebraically, for a genuinely nonzero `Fp12` element this cannot happen (the norm form is anisotropic over a correctly-constructed field tower), so the only way to hit this path is if the Miller-loop product `el` itself becomes exactly `Fp12.ZERO`.

I traced a concrete code path that can produce `Fp12.ZERO` mid-loop: `Fp12.mulBy024()` is used to fold in each line-function evaluation `(ell0, ellVW, ellVV)` computed by `PairingCheck.flippedMillerLoopMixedAddition()`: [4](#0-3) 

If the running accumulator `addend` happens to equal `base` at a mixed-addition step (`x1 == x2*z1`, `y1 == y2*z1`), then `d = e = 0`, which forces `ell0 = ellVW = ellVV = 0`. Feeding `x0 = x2 = x4 = 0` into `mulBy024()` makes every output coordinate `0` regardless of the current value of `f`: [5](#0-4) 

This zeroes the Miller-loop accumulator for the rest of the computation, so `finalExponentiation()` is invoked with `el = Fp12.ZERO`, which drives `Fp.inverse()` to call `BigInteger.ZERO.modInverse(P)`, throwing `ArithmeticException`.

`addend == base` during the loop is a degenerate condition normally excluded by requiring `g2` to be a point of the correct large prime order (the canonical G2 subgroup). If curve/subgroup validation of the raw G2 encoding submitted to the pairing precompile is limited to an on-curve check (not a subgroup-order check), an attacker-supplied G2 point of small order could cause the doubling ladder to revisit `base`, triggering the zero line-function case. I was unable to fully confirm the exact validation performed on submitted G1/G2 encodings before `PairingCheck.millerLoop()` is invoked (`BN128G1`/`BN128G2`/`PrecompiledContracts` point-parsing logic), since I ran out of tool budget before inspecting `BN128G1.java`, `BN128G2.java`, and the precompile entrypoint in `PrecompiledContracts.java` in detail. My grep for `catch(` inside `PrecompiledContracts.java` found no matches, which is consistent with (but does not prove) an absence of a try/catch guard around the pairing check.

### Impact Explanation
If reachable, an uncaught `ArithmeticException` thrown deep inside `Fp.inverse()` during EVM `ecPairing`/`altBN128Pairing` execution would propagate out of the intended `boolean`/`Pair.of(false, …)` result path. Depending on how (or whether) the calling precompile dispatcher catches generic exceptions, this could abort transaction processing unexpectedly, and if exception handling differs across code paths/JVMs, it could produce non-deterministic behavior across nodes — a serious consensus-safety concern for any blockchain precompile.

### Likelihood Explanation
This requires the attacker to construct a specific low-order or otherwise degenerate `G2` point (and possibly a matching `G1` point) such that the Miller-loop's internal accumulator collides with the base point during a mixed-addition step. This is a non-trivial but well-known class of "missing subgroup check" issue in BN254 pairing implementations. I could not verify from the available context whether existing point-decoding/validation logic in `BN128G1`/`BN128G2` rejects such inputs (e.g., via an explicit subgroup-order check), which is the deciding factor for exploitability. Without that confirmation, likelihood cannot be conclusively assessed.

### Recommendation
- In `PairingCheck.finalExponentiation()` (or `Fp12.inverse()`/`Fp6.inverse()`/`Fp2.inverse()`), explicitly check `isZero()` before calling `inverse()` and treat a zero element as pairing failure rather than letting `BigInteger.modInverse` throw.
- Additionally/alternatively, verify that submitted G2 points belong to the correct prime-order subgroup (not just "on curve") before running the Miller loop, eliminating the degenerate `addend == base` recurrence.
- Wrap the precompile's pairing-check invocation in a catch for `ArithmeticException`/`RuntimeException` and map it to a deterministic failure result, ensuring the guarantee that `execute()` never throws uncaught exceptions regardless of upstream fixes.

  private static Precomputed flippedMillerLoopMixedAddition(BN128G2 base, BN128G2 addend) {

    Fp2 x1 = addend.x, y1 = addend.y, z1 = addend.z;
    Fp2 x2 = base.x, y2 = base.y;

    Fp2 d = x1.sub(x2.mul(z1));             // d = x1 - x2 * z1
    Fp2 e = y1.sub(y2.mul(z1));             // e = y1 - y2 * z1
    Fp2 f = d.squared();                    // f = d^2
    Fp2 g = e.squared();                    // g = e^2
    Fp2 h = d.mul(f);                       // h = d * f
    Fp2 i = x1.mul(f);                      // i = x1 * f
    Fp2 j = h.add(z1.mul(g)).sub(i.dbl());  // j = h + z1 * g - 2 * i

    Fp2 x3 = d.mul(j);                           // x3 = d * j
    Fp2 y3 = e.mul(i.sub(j)).sub(h.mul(y1));     // y3 = e * (i - j) - h * y1)
    Fp2 z3 = z1.mul(h);                          // z3 = Z1*H

    Fp2 ell0 = TWIST.mul(e.mul(x2).sub(d.mul(y2)));     // ell_0 = TWIST * (e * x2 - d * y2)
    Fp2 ellVV = e.negate();                             // ell_VV = -e
    Fp2 ellVW = d;                                      // ell_VW = d

    return Precomputed.of(
        new BN128G2(x3, y3, z3),
        new EllCoeffs(ell0, ellVW, ellVV)
    );
  }

  Fp12 mulBy024(Fp2 ell0, Fp2 ellVW, Fp2 ellVV) {

    Fp2 z0 = a.a;
    Fp2 z1 = a.b;
    Fp2 z2 = a.c;
    Fp2 z3 = b.a;
    Fp2 z4 = b.b;
    Fp2 z5 = b.c;

    Fp2 x0 = ell0;
    Fp2 x2 = ellVV;
    Fp2 x4 = ellVW;

    Fp2 t0, t1, t2, s0, t3, t4, d0, d2, d4, s1;

    d0 = z0.mul(x0);
    d2 = z2.mul(x2);
    d4 = z4.mul(x4);
    t2 = z0.add(z4);
    t1 = z0.add(z2);
    s0 = z1.add(z3).add(z5);

    // For z.a_.a_ = z0.
    s1 = z1.mul(x2);
    t3 = s1.add(d4);
    t4 = Fp6.NON_RESIDUE.mul(t3).add(d0);
    z0 = t4;

    // For z.a_.b_ = z1
    t3 = z5.mul(x4);
    s1 = s1.add(t3);
    t3 = t3.add(d2);
    t4 = Fp6.NON_RESIDUE.mul(t3);
    t3 = z1.mul(x0);
    s1 = s1.add(t3);
    t4 = t4.add(t3);
    z1 = t4;

    // For z.a_.c_ = z2
    t0 = x0.add(x2);
    t3 = t1.mul(t0).sub(d0).sub(d2);
    t4 = z3.mul(x4);
    s1 = s1.add(t4);
    t3 = t3.add(t4);

    // For z.b_.a_ = z3 (z3 needs z2)
    t0 = z2.add(z4);
    z2 = t3;
    t1 = x2.add(x4);
    t3 = t0.mul(t1).sub(d2).sub(d4);
    t4 = Fp6.NON_RESIDUE.mul(t3);
    t3 = z3.mul(x0);
    s1 = s1.add(t3);
    t4 = t4.add(t3);
    z3 = t4;

    // For z.b_.b_ = z4
    t3 = z5.mul(x2);
    s1 = s1.add(t3);
    t4 = Fp6.NON_RESIDUE.mul(t3);
    t0 = x0.add(x4);
    t3 = t2.mul(t0).sub(d0).sub(d4);
    t4 = t4.add(t3);
    z4 = t4;

    // For z.b_.c_ = z5.
    t0 = x0.add(x2).add(x4);
    t3 = s0.mul(t0).sub(s1);
    z5 = t3;

    return new Fp12(new Fp6(z0, z1, z2), new Fp6(z3, z4, z5));
  }
