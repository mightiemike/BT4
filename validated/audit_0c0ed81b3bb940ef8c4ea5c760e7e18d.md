### Title
Reachable panic on `RuntimeError::ReceiptValidationError` turns a cross-shard receipt-validation mismatch into a chunk-producing node crash - ([File: chain/chain/src/runtime/mod.rs])

### Summary
`Runtime::apply` validates every *incoming* (cross-shard) receipt with `validate_receipt(..., ValidateReceiptMode::ExistingReceipt)` before executing it [1](#0-0) . If that validation ever fails for a receipt that has already left the sending shard (i.e. it passed the stricter `NewReceipt` check at creation time but fails the supposedly-more-lenient `ExistingReceipt` check on arrival), the error is not handled gracefully at the chain layer: it is converted straight into a `panic!`, crashing the node process [2](#0-1) . This is structurally the same bug class as CVE-2021-46339: an internal invariant ("every receipt reaching this point has already been validated / is well-formed") is enforced with a hard assertion/panic instead of a recoverable error, and the data feeding that invariant check ultimately originates from attacker/user-controlled input (a receipt generated by executing a transaction's actions).

### Finding Description
`validate_receipt` is called twice for every action receipt in its lifetime:

1. Immediately after a receipt is created by `apply_action_receipt`, with `ValidateReceiptMode::NewReceipt` — the strict mode [3](#0-2) . A failure here becomes an `ActionErrorKind::NewReceiptValidationError`, i.e. a *graceful* failed-action outcome, not a panic.
2. Again when the receipt is received on the destination shard as an *incoming* receipt, with `ValidateReceiptMode::ExistingReceipt` — documented as intentionally more lenient, specifically to tolerate legacy receipts affected by a known oversize-receipt bug (#12606) [4](#0-3) . A failure here is propagated as `RuntimeError::ReceiptValidationError` [1](#0-0) .

The comment on `ExistingReceipt` explicitly documents that this leniency exists *because* the codebase has previously shipped a bug that produced non-compliant receipts, and that the runtime "has to handle them gracefully" [5](#0-4) . Despite that stated goal, the call site that actually receives `RuntimeError::ReceiptValidationError` from `Runtime::apply` in the chain crate does **not** handle it gracefully — it panics the process:

```rust
// TODO(#2152): process gracefully
RuntimeError::ReceiptValidationError(e) => panic!("{}", e),
``` [6](#0-5) 

The delayed-receipt path (receipts stored in the trie from a previous chunk) has the same shape: a `validate_receipt` failure there is turned into `StorageError::StorageInconsistentState`, which is likewise fatal at the chunk-application boundary [7](#0-6) . Both incoming and delayed receipts are receipts that were produced by the execution of some earlier, attacker/user-submitted transaction (a `FunctionCall` action creating a promise/receipt to another shard, or any action producing an outgoing receipt) — they are not internal-only data. If any asymmetry exists between the `NewReceipt` check performed on the sending shard and the `ExistingReceipt` check performed on the receiving shard (across a protocol-version boundary, a future validation-rule change, or a not-yet-discovered edge case analogous to #12606), a single transaction that creates such a receipt is enough to make every honest node that later processes that receipt panic — a chunk/shard-wide halt triggered by one submitted transaction, not by a malicious peer or validator.

This mirrors the JerryScript CVE precisely: `ecma_new_ecma_string_from_utf8` assumed input was already validated as CESU-8 by the caller and used a hard `assert`, so a caller-supplied string that slipped past the assumed-but-unenforced precondition crashed the engine. Here, `Runtime::apply`/the chain layer assumes an incoming receipt is "already validated" (having passed `NewReceipt` on another shard), and any counter-example is turned into a hard `panic!` rather than a recoverable error, even though the code comments acknowledge this exact class of counter-example has occurred before (#12606).

### Impact Explanation
A successful trigger causes `panic!` inside chunk application on every node that processes the receipt on its destination shard — this is a "transaction-triggered halt" as defined in the acceptance criteria: chunk production on the affected shard stops, and depending on deployment (whether the panic is caught at a higher supervisory level or brings down the whole node process) it can degrade to a broader node crash. Because incoming receipts are processed identically by every honest node applying that chunk, this affects the whole validator set tracking the shard, not just one node — a state-transition-halting bug reachable from ordinary user transactions, matching the "Medium" bar for a reachable-assertion/DoS class bug in a blockchain runtime.

### Likelihood Explanation
The bug is *not* trivially triggerable today: normal execution paths validate a receipt strictly (`NewReceipt`) before it ever leaves the shard, and `ExistingReceipt` is designed to be strictly more permissive, so under the currently known set of validation rules `NewReceipt`-valid receipts should also pass `ExistingReceipt`. The likelihood therefore hinges on whether any of the following currently-open conditions can produce a receipt that is valid at creation but invalid at consumption:
- protocol-version-dependent account-id/action validation rules diverging between the two `validate_receipt` calls (creation vs. consumption, potentially at different heights/epochs for cross-shard receipts that traverse a protocol upgrade boundary),
- a second instance of the historical class of bug referenced by #12606 (a receipt-construction path that produces an out-of-spec receipt that nonetheless gets past `NewReceipt`).
I was not able to fully confirm from the indexed code whether such a divergence currently exists (the exact differences between `validate_actions_with_mode`'s `NewReceipt` and `ExistingReceipt` branches were not retrievable within the available search budget), so I cannot assert this is *currently* exploitable — only that the failure-handling code path (`panic!` on `RuntimeError::ReceiptValidationError`) is itself a live design flaw: it converts a case the codebase's own comments say "has to be handled gracefully" into a hard crash, and it is explicitly marked with a `TODO(#2152): process gracefully`, i.e. the developers themselves flag this as unfinished/incorrect error handling rather than an intentional invariant.

### Recommendation
- Do not `panic!` on `RuntimeError::ReceiptValidationError` in `chain/chain/src/runtime/mod.rs`. Since this error can originate from data that traveled across shards (i.e., ultimately attacker-influenced), treat it the same way `InvalidTxError` is treated — as a recoverable/rejectable condition (e.g., reject the chunk / receipt without crashing the process), consistent with the `TODO(#2152)` already present in the code.
- Audit `validate_receipt`'s two modes (`NewReceipt` vs `ExistingReceipt`) and the two protocol-version contexts in which they are invoked (creation-time vs. consumption-time, which can be at different heights) to confirm `NewReceipt`-valid ⇒ `ExistingReceipt`-valid holds for every current and historical protocol version, and add regression tests for any protocol-version-dependent validation rule (e.g. `AccountIdValidityRulesVersion`) that could otherwise diverge across an epoch boundary.
- Apply the same treatment to the `StorageInconsistentState` conversion for delayed receipts failing `validate_receipt` on dequeue.

### Proof of Concept
A concrete, currently-reachable PoC was not established within the available investigation — the code paths that would need to diverge (`NewReceipt` vs `ExistingReceipt` validation across a protocol-version transition, or the exact conditions of the historical #12606 bug) could not be fully traced with the remaining tool budget. What is concretely demonstrated by the code itself:
1. `runtime/runtime/src/lib.rs:2697-2703` — every incoming receipt is checked with `validate_receipt(..., ExistingReceipt)`; any `Err` becomes `RuntimeError::ReceiptValidationError`.
2. `chain/chain/src/runtime/mod.rs:372` — that error variant is handled by `panic!("{}", e)`, explicitly marked `// TODO(#2152): process gracefully`.
3. `runtime/runtime/src/verifier.rs:727-739` — the doc comment for `ExistingReceipt` confirms this exact class of error ("receipts that are above the size limit… Runtime has to handle them gracefully") has occurred in production before (referencing near/nearcore#12606), establishing that receipts violating the stricter creation-time rules can and have reached the consumption-time check.

This is sufficient to establish the flawed error-handling design (a `panic!` where the same file's own documentation says graceful handling is required) but not a self-contained exploit transaction; a full PoC would require identifying a currently-live divergence between the two validation calls (e.g. a protocol-version-gated account-id or action validation rule) or a fresh receipt-construction bug analogous to #12606.

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // We retain these checks here as to maintain backwards compatibility
    // with AccountId validation since we illegally parse an AccountId
    // in near-vm-runner/src/wasmtime_runner/logic.rs#fn(read_and_parse_account_id)
    AccountId::validate(receipt.predecessor_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidPredecessorId {
            account_id: receipt.predecessor_id().to_string(),
        }
    })?;
    AccountId::validate(receipt.receiver_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidReceiverId { account_id: receipt.receiver_id().to_string() }
    })?;

    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt)
        | VersionedReceiptEnum::PromiseYield(action_receipt) => validate_action_receipt(
            limit_config,
            action_receipt,
            receipt.receiver_id(),
            current_protocol_version,
            mode,
        ),
        VersionedReceiptEnum::Data(data_receipt)
        | VersionedReceiptEnum::PromiseResume(data_receipt) => {
            validate_data_receipt(limit_config, &data_receipt)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(()), // Distribution receipt can't be issued without a valid contract
    }
}

pub enum ValidateReceiptMode {
    /// Used for validating new receipts that were just created.
    /// More strict than `OldReceipt` mode, which has to handle older receipts.
    NewReceipt,
    /// Used for validating older receipts that were saved in the state/received. Less strict than
    /// NewReceipt validation. Tolerates some receipts that wouldn't pass new validation. It has to
    /// be less strict because:
    /// 1) Older receipts might have been created before new validation rules.
    /// 2) There is a bug which allows to create receipts that are above the size limit. Runtime has
    ///    to handle them gracefully until the receipt size limit bug is fixed.
    ///    See https://github.com/near/nearcore/issues/12606 for details.
    ExistingReceipt,
}
