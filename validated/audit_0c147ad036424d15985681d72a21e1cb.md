### Title
ML-DSA-65 gas-key host-function exec fee reservation/settlement mismatch causes silent token destruction - (File: `runtime/near-vm-runner/src/logic/logic.rs`, `runtime/runtime/src/config.rs`)

### Summary
The Uranium exploit stemmed from an invariant check (`K`) that used a *different magic scale constant* (`1000` vs `10000`) than the one actually used to compute the swap fee, letting the check silently pass while values diverged. The nearcore analog is the ML-DSA-65 gas-key cost accounting: the gas *reserved* for a `TransferToGasKey`/`AddKey`(gas-key) action dispatched from a contract via host functions is computed with one length metric (`public_key.len()`, the wire length), while the gas actually *burnt/settled* for the same action when it executes is computed with a different length metric (`public_key.trie_id_len()`, the on-trie length). For ML-DSA-65 keys these two lengths differ enormously (1953 bytes vs 33 bytes), and the repository's own regression test documents that the resulting gap is "neither burnt nor refunded," i.e. tokens are destroyed without being accounted for.

### Finding Description
Two independent code paths compute the "byte length" input to the same `gas_key_transfer_exec_fee` formula, and they are not kept in sync unless a protocol-version feature flag (`fix_ml_dsa_cost_charging`, activated only at PV 87) is enabled:

- At host-function dispatch time (`promise_batch_action_transfer_to_gas_key`, `promise_batch_action_add_gas_key_with_function_call`, etc. in `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`), the gas to reserve is computed via `gas_key_exec_pk_len`: [1](#0-0) 
which, when `fix_ml_dsa_cost_charging` is **disabled** (the state on the current stable protocol version, PV 86), falls back to `pk_len` — the full wire length of the decoded public key (1953 bytes for ML-DSA-65).

- When the resulting `TransferToGasKey`/`WithdrawFromGasKey` action is actually executed by the runtime, the exec fee is computed unconditionally with `action.public_key.trie_id_len()` (33 bytes for ML-DSA-65), independent of the feature flag: [2](#0-1) 

Both call into the same formula: [3](#0-2) 

Because pre-PV87 the *reservation* path prices on the large wire length and the *settlement* path always prices on the small trie length, gas is over-reserved at dispatch and only a fraction of it is later recognized as burnt. The repository's own test explicitly documents this as a live "silent total-supply leak" bug class, fixed only by the PV 87 feature flag: [4](#0-3) [5](#0-4) 

This is structurally identical to the Uranium bug class: a value-conservation invariant depends on two computations of "the same quantity" sharing a scale/constant, and one of the two code paths uses the wrong one, silently breaking the invariant that reserved gas must equal burnt-plus-refunded gas.

### Impact Explanation
Any account can reach this from an ordinary contract call: deploy or call a contract that issues `promise_batch_action_add_gas_key_with_full_access` / `promise_batch_action_transfer_to_gas_key` with an ML-DSA-65 (post-quantum) public key. Before PV 87 is voted in (the code in this tree corresponds to PV 86 stable, per `protocol-model/spec/economics.md`), the discrepancy between reserved and settled exec gas is neither burnt (recorded in `tx_burnt_amount`) nor refunded to the signer — it disappears from the paying account's balance without being accounted for anywhere, which is a genuine (if narrow) value-destruction bug reachable by any unprivileged transaction signer / contract caller using the ML-DSA-65 key type. It also creates a discrepancy vs. the runtime's own balance-conservation invariant described in `docs/RuntimeSpec/Components/RuntimeCrate.md`'s "Balance checker" section.

### Likelihood Explanation
The bug is only triggered by contracts choosing to add/fund gas keys with ML-DSA-65 (post-quantum) public keys via host functions, which is a specific but fully permissionless, self-serve action any account can perform against its own account. The condition is gated purely by protocol version, not by any validator/operator privilege, and the repository itself documents the exact defect and its trigger conditions in the PV 87 changelog comment and the dedicated regression test.

### Recommendation
Confirm which side (`PROTOCOL_VERSION`) is actually live in the target deployment. If `fix_ml_dsa_cost_charging` (PV 87) is not yet active, either backport the fix (make the host-function reservation path `gas_key_exec_pk_len` unconditionally use `trie_id_len()`, matching the always-consistent direct-action `exec_fee` path) or ensure any unspent/mis-reserved gas from this mismatch is properly refunded rather than dropped, and extend `test_gas_key_add_key_conserves_supply` to run under the pre-PV87 configuration to catch regressions.

### Proof of Concept
1. On a network running with `fix_ml_dsa_cost_charging = false` (pre-PV 87 / current stable PV 86), deploy a contract exposing a method that calls `promise_batch_action_add_gas_key_with_full_access` (or `promise_batch_action_transfer_to_gas_key`) with an ML-DSA-65 public key, mirroring `test_gas_key_add_key_conserves_supply`: [6](#0-5) 
2. Run the receipt cascade to completion and measure `alice`'s balance drop versus the sum of `tx_burnt_amount + slashed_burnt_amount + other_burnt_amount - subsidized_amount - gas_deficit_amount` reported by `apply_result.stats.balance`, exactly as the test does: [7](#0-6) 
3. Observe that the measured balance drop exceeds the recorded "destroyed" amount — the gap is the silently lost gas reservation, confirming the supply leak.

pub(crate) fn gas_key_exec_pk_len(
    public_key_res: &Result<near_crypto::PublicKey>,
    config: &Config,
    pk_len: usize,
) -> usize {
    match public_key_res {
        // Exec (storage) fee should reflect how many bytes the key occupies in
        // storage, not on the wire.
        Ok(pk) if config.fix_ml_dsa_cost_charging => pk.trie_id_len(),
        // Preserve the existing behavior if the fix is not enabled (or the key
        // failed to decode); changing it would break protocol consensus.
        _ => pk_len,
    }
}

/// Exec fee for TransferToGasKey / WithdrawFromGasKey actions.
/// Based on the access key trie key length + estimated value length (what the
/// receiver needs to read/write in the trie).
pub fn gas_key_transfer_exec_fee(
    cfg: &RuntimeFeesConfig,
    account_id_len: usize,
    public_key_len: usize,
) -> GasKeyTransferFee {
    let base = cfg.fee(ActionCosts::gas_key_transfer_base).exec_fee();
    let trie_key_len = access_key_key_len(account_id_len, public_key_len);
    let estimated_value_len = AccessKey::min_gas_key_borsh_len();
    let per_byte = cfg
        .fee(ActionCosts::gas_key_byte)
        .exec_fee()
        .checked_mul((trie_key_len + estimated_value_len) as u64)
        .unwrap();
    GasKeyTransferFee { base, per_byte }
}
