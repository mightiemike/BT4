### Title
No incentive for early SR (witness) voting enables last-block vote manipulation of the Super Representative election - (File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java)

### Summary
Java-tron's Super Representative (witness) election is a stake-weighted "voting" mechanism analogous to Hermez's bidding auction. Votes cast via `VoteWitnessContract` only take effect when tallied at the end of a maintenance cycle in `MaintenanceManager.doMaintenance()`, and voting weight (TRON Power) is available immediately after freezing TRX. Because all pending votes/transactions are publicly visible before the cycle boundary and there is no decreasing weight over time, any actor holding sufficient liquid TRX can wait until the last block(s) of a cycle, observe the current standings, freeze balance and cast (or overwrite) votes to flip the SR election outcome, exactly mirroring the Hermez "no incentive to vote earlier" timing flaw.

### Finding Description
`VoteWitnessActuator.validate()`/`execute()` accept a vote transaction at any point during a maintenance cycle and immediately record it as the account's current vote (overwriting the previous vote via `accountCapsule.clearVotes()`), based on `accountCapsule.getTronPower()`/`getAllTronPower()` at the time of the transaction: [1](#0-0) 

The actual vote counting/tally, which determines the active witness set for the next cycle, only happens once per maintenance cycle in `MaintenanceManager.doMaintenance()` -> `countVote()`: [2](#0-1) 

Voting power (TRON Power) becomes available to the account as soon as `FreezeBalanceActuator`/`FreezeBalanceV2Actuator` executes — there is no waiting period before frozen TRX can be used to vote: [3](#0-2) 

Because (1) all in-flight transactions are visible in the mempool/blockchain before confirmation, (2) votes are only tallied at the fixed maintenance-cycle boundary, and (3) there is no weighting mechanism that decays the value of a vote submitted right before the boundary, this is structurally the same problem described in the Hermez report: a participant with sufficient liquid capital can wait until the very last moment of the cycle, see exactly how many votes are needed to overtake a rival witness candidate, freeze the necessary TRX, and submit a vote transaction in the final block(s) before `nextMaintenanceTime`, denying earlier voters any chance to react or counter-bid.

### Impact Explanation
The SR/witness election directly controls block production rights, consensus, and block rewards in the DPoS chain. An actor able to reliably flip the election in the final moments of every cycle can capture SR seats (and the associated block-production/consensus power) cheaper and more reliably than honest participants who vote early, without needing to sustain the largest total stake throughout the cycle — only at the tally instant. This can centralize control of block production and consensus among last-minute, capital-rich actors, a systemic governance/consensus-integrity risk.

### Likelihood Explanation
Any account can call `FreezeBalanceContract`/`FreezeBalanceV2Contract` followed by `VoteWitnessContract` unprivileged, and both actuators are reachable from ordinary broadcast transactions. The only requirement is sufficient liquid TRX and timing awareness of `getNextMaintenanceTime()` (a value exposed via the public `GetNextMaintenanceTimeServlet`/API), making the attack straightforward to execute for any well-funded actor, though it requires meaningful capital to actually swing an election.

### Recommendation
Consider incentivizing/weighting early voting relative to last-minute voting for SR elections — e.g., a time-decayed vote weight within a cycle, a vote-locking/commit-reveal scheme, or requiring frozen TRX to "age" for a minimum period before it counts toward vote weight for the current cycle's tally — to raise the cost of last-block election manipulation. Long term, track blockchain governance research on front-running-resistant, time-fair voting/bidding schemes.

### Proof of Concept
1. Observe current vote standings for witness candidates via public RPC (all `VotesCapsule`/`WitnessCapsule` state and `getNextMaintenanceTime()` are queryable).
2. Shortly before `nextMaintenanceTime`, broadcast `FreezeBalanceContract` (or `FreezeBalanceV2Contract`) to obtain sufficient TRON Power, which is credited immediately per `FreezeBalanceActuator.execute()`.
3. In the same or following block, broadcast a `VoteWitnessContract` transaction voting exactly enough to overtake the leading candidate; `VoteWitnessActuator.countVoteAccount()` overwrites the account's prior vote unconditionally.
4. At `nextMaintenanceTime`, `MaintenanceManager.doMaintenance()` tallies all `VotesStore` entries and updates witness vote counts, finalizing the election with the last-minute vote counted at full weight, same as any early vote — giving no time for other participants to counter-bid.
