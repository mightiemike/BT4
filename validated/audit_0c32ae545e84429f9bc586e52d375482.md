## Finding

Based on the code I was able to trace, the mechanism described is real and matches the intended design of `RemoteTxnWrite`, but I could not fully verify one link in the chain (`CrossShardCommitSender::send_remote_update_for_success`'s exact write-op lookup logic), which I flag below.

### Title
Cross-shard `RemoteTxnWrite(None)` for an aborted source transaction is misinterpreted as an explicit deletion instead of "value unchanged" - (File: `aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_state_view.rs`)

### Summary
`RemoteTxnWrite` is explicitly documented to carry `write_op: None` "if the transaction is aborted" [1](#0-0) . When `CrossShardCommitReceiver` relays this to `CrossShardStateView::set_value`, the `None` is stored verbatim as the resolved value for that key [2](#0-1) , and every subsequent `get_state_value` call for that key in the current round returns `Ok(None)` without ever falling back to `base_view` [3](#0-2) . This conflates two semantically distinct situations under one `None` encoding: "the key was actually written with a tombstone/deletion" vs. "the transaction aborted/never wrote this key, so its value is whatever it was before this round." The `CrossShardStateView` code implements only the first interpretation.

### Finding Description
`CrossShardStateView` is constructed once per round from the state view of the previous round/base ledger, pre-populated with `Waiting` placeholders for every cross-shard dependency key [4](#0-3) . As soon as any value (including `None`) is pushed via `set_value`, that becomes the permanent resolved value for the round; `get_state_value` never re-consults `base_view` for a key once it is present in `cross_shard_data` [3](#0-2) .

`CrossShardCommitSender::on_transaction_committed` is invoked for every committed (kept) transaction that has a dependent edge, regardless of whether the transaction's `TransactionStatus` was a success or a `MoveAbort`/execution failure kept in the block [5](#0-4) . An aborted-but-kept transaction (e.g., a `MoveAbort`) typically produces a `TransactionOutput` write set that does not contain the storage location the dependent shard is waiting on, since the intended resource mutation never happened. The `RemoteTxnWrite` message's own doc-comment states this exact case sends `write_op: None` [1](#0-0) .

The correct semantics for a dependent shard reading that key should be: "the value is whatever existed before this round" (i.e., what `base_view` would return), because the source transaction did not actually mutate storage. Instead, `set_value(key, None)` permanently marks the key as absent/deleted for the remainder of the round's execution on the dependent shard, since `get_state_value` short-circuits on the `cross_shard_data` entry and never consults `base_view` [3](#0-2) .

This causes the dependent transaction to observe "resource does not exist" (`None`) instead of the real prior value that a non-sharded, single-execution reference (or the global-shard fallback) would observe, producing a diverging code path in the VM and thus a different `TransactionOutput` write set, which is the value handed off to storage commit.

### Impact Explanation
If sharded execution is used to produce the canonical `TransactionOutput`s that get committed to the ledger, this divergence corrupts the write set relative to the deterministic single-execution VM semantics: an aborted upstream transaction on a required key silently converts that key to "does not exist" for downstream dependent transactions in the same round, instead of preserving its true prior value. That is a hard-fork-class divergence between sharded and canonical (single-shard) execution, since sharded and non-sharded nodes computing the same block would derive different `TransactionOutput`s / state roots for the same input block. This falls under the "hard-fork-only divergence" acceptance criterion.

### Likelihood Explanation
Triggering an abort is trivial for any unprivileged sender (e.g., submit a Move call that fails an assertion) as long as the affected key participates in a cross-shard `required_edges`/`dependent_edges` relationship established by the block partitioner [6](#0-5) . The partitioner builds these edges purely from the transaction's read/write set overlaps across shards [7](#0-6) , which an attacker can engineer by choosing keys/resources touched by their transaction. No trusted-operator error is required.

### Recommendation
Distinguish "aborted / not written" from "explicitly deleted" in `RemoteTxnWrite`/`RemoteStateValue`, and have `CrossShardStateView` fall back to `base_view.get_state_value` (the true pre-round value) when a dependency's write is absent due to abort, rather than caching a bare `None` as the resolved value.

### Proof of Concept
1. Partition a block into ≥2 shards such that transaction `T_src` (shard 0, round 0) writing key `K` has a dependent edge to `T_dst` (shard 1, round 1) reading `K` [8](#0-7) .
2. Craft `T_src` so it aborts (e.g., a Move assertion failure) after being selected as kept-with-abort, while `K` already holds a real value from a prior committed round/ledger state.
3. Shard 0 executes `T_src`; its output write set has no entry for `K`; `on_transaction_committed` fires and sends `RemoteTxnWrite{state_key: K, write_op: None}` [5](#0-4) .
4. Shard 1's `CrossShardCommitReceiver` calls `CrossShardStateView::set_value(K, None)` [2](#0-1) .
5. `T_dst` reads `K` via `get_state_value`, observing `None` instead of the real prior value [3](#0-2) , producing a `TransactionOutput` for `T_dst` that diverges from what a single-shard/non-sharded execution of the same block would produce for the identical input.

**Caveat**: I was unable to fully view `CrossShardCommitSender::send_remote_update_for_success` (the code that decides exactly when `write_op: None` vs `Some` is sent) due to a truncated file read in this session, so I cannot 100% confirm there isn't an additional guard elsewhere (e.g., re-deriving the value from a prior round's committed state rather than sending `None` outright) that would neutralize this. If such a check does not exist, the above holds as described. A Devin session with full file access should verify `send_remote_update_for_success`'s exact write-op derivation before treating this as fully confirmed.

#[derive(Default, Debug, Clone, Serialize, Deserialize, Eq, PartialEq)]
/// Represents the dependencies of a transaction on other transactions across shards. Two types
/// of dependencies are supported:
/// 1. `required_edges`: The transaction depends on the execution of the transactions in the set. In this
/// case, the transaction can only be executed after the transactions in the set have been executed.
/// 2. `dependent_edges`: The transactions in the set depend on the execution of the transaction. In this
/// case, the transactions in the set can only be executed after the transaction has been executed.
/// Dependent edge is a reverse of required edge, for example if txn 20 in shard 2 requires txn 10 in shard 1,
/// then txn 10 in shard 1 will have a dependent edge to txn 20 in shard 2.
pub struct CrossShardDependencies {
    pub required_edges: CrossShardEdges,
    pub dependent_edges: CrossShardEdges,
}

    /// Take a txn out, wrap it as a `TransactionWithDependencies`.
    pub(crate) fn take_txn_with_dep(
        &self,
        round_id: RoundId,
        shard_id: ShardId,
        txn_idx: PrePartitionedTxnIdx,
    ) -> TransactionWithDependencies<AnalyzedTransaction> {
        let ori_txn_idx = self.ori_idxs_by_pre_partitioned[txn_idx];
        let txn = self.txns[ori_txn_idx].write().unwrap().take().unwrap();
        let mut deps = CrossShardDependencies::default();

        // Build required edges.
        let write_set = self.write_sets[ori_txn_idx].read().unwrap();
        let read_set = self.read_sets[ori_txn_idx].read().unwrap();
        for &key_idx in write_set.iter().chain(read_set.iter()) {
            let tracker_ref = self.trackers.get(&key_idx).unwrap();
            let tracker = tracker_ref.read().unwrap();
            if let Some(txn_idx) = tracker
                .finalized_writes
                .range(..ShardedTxnIndexV2::new(round_id, shard_id, 0))
                .last()
            {
                let src_txn_idx = ShardedTxnIndex {
                    txn_index: *self.final_idxs_by_pre_partitioned[txn_idx.pre_partitioned_txn_idx]
                        .read()
                        .unwrap(),
                    shard_id: txn_idx.shard_id(),
                    round_id: txn_idx.round_id(),
                };
                deps.add_required_edge(src_txn_idx, tracker.storage_location.clone());
            }
        }

        // Build dependent edges.
        for &key_idx in self.write_sets[ori_txn_idx].read().unwrap().iter() {
            if Some(txn_idx) == self.last_writer(key_idx, SubBlockIdx { round_id, shard_id }) {
                let start_of_next_sub_block = ShardedTxnIndexV2::new(round_id, shard_id + 1, 0);
                let next_writer = self.first_writer(key_idx, start_of_next_sub_block);
                let end_follower = match next_writer {
                    None => ShardedTxnIndexV2::new(self.num_rounds(), self.num_executor_shards, 0), // Guaranteed to be greater than any invalid idx...
                    Some(idx) => ShardedTxnIndexV2::new(idx.round_id(), idx.shard_id() + 1, 0),
                };
                for follower_txn_idx in
                    self.all_txns_in_sub_block_range(key_idx, start_of_next_sub_block, end_follower)
                {
                    let final_sub_blk_idx =
                        self.final_sub_block_idx(follower_txn_idx.sub_block_idx);
                    let dst_txn_idx = ShardedTxnIndex {
                        txn_index: *self.final_idxs_by_pre_partitioned
                            [follower_txn_idx.pre_partitioned_txn_idx]
                            .read()
                            .unwrap(),
                        shard_id: final_sub_blk_idx.shard_id,
                        round_id: final_sub_blk_idx.round_id,
                    };
                    deps.add_dependent_edge(dst_txn_idx, vec![self.storage_location(key_idx)]);
                }
            }
        }

        TransactionWithDependencies::new(txn, deps)
    }
}
