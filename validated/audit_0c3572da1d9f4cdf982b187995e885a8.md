### Title
`createContractImpl()` skips remaining-energy refund when contract creation fails with an exception - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
In `Program.createContractImpl()`, when the CREATE/CREATE2 sub-call's execution result carries an exception, the function pushes zero onto the stack and returns early, bypassing the call to `refundEnergyAfterVM()` that would otherwise credit back the caller's unused energy from the internal call's energy budget.

### Finding Description
`createContractImpl()` allocates a fixed sub-call energy budget (`energyLimit`, derived via `getCreateEnergy()`) and spends it up front from the calling frame via `spendEnergy(energyLimit.longValue(), "internal call")` [1](#0-0) . The nested VM execution (`VM.play`) then runs against that budget and produces a `createResult` [2](#0-1) .

After execution, the intended flow is that whatever energy was NOT consumed by the sub-call out of the `energyLimit` allotment should be refunded back to the parent frame via `refundEnergyAfterVM(energyLimit, createResult)`, called unconditionally at the end of the method [3](#0-2) . That helper computes `refundEnergy = energyLimit - result.getEnergyUsed()` and calls `refundEnergy(...)` if positive [4](#0-3) .

However, when `createResult.getException() != null || createResult.isRevert()` is true, the failure-handling branch runs `stackPushZero()` and then, specifically in the `getException() != null` sub-case, executes a bare `return;` [5](#0-4) . This early `return` exits the method before reaching line 977, so `refundEnergyAfterVM()` is never invoked for exception-terminated contract-creation sub-calls. In contrast, the `isRevert()` (no exception) sub-case falls through to `returnDataBuffer = ...` and continues to the refund call, and the success branch also falls through to the refund call. Only the exception path is denied the refund.

This mirrors the reported Atlas bug class exactly: an early return, triggered specifically by an "expected-refund" failure condition, skips the call that performs the reimbursement/credit-back to the party that pre-paid the resource (here, the calling frame that pre-spent `energyLimit` for the internal CREATE call).

### Impact Explanation
Any unused energy within the CREATE/CREATE2 sub-call's pre-allocated budget is permanently lost from the caller's execution context whenever the inner contract creation fails with an exception (e.g., `notEnoughSpendEnergy`, `invalidCodeException`, `BytecodeExecutionException`, stack/opcode errors, etc.), rather than being returned to the parent for further use in the same transaction. Since energy directly maps to TRX-denominated fees (`SUN_PER_ENERGY`) billed to the transaction's caller/origin account at the end of the transaction via `TransactionTrace.pay()` / `ReceiptCapsule.payEnergyBill()`, this causes the transaction sender to be overcharged relative to actual work performed whenever a contract deliberately or incidentally triggers an exception-terminated nested CREATE. This is a resource/accounting-correctness bug reachable from any ordinary contract-call transaction that performs an internal CREATE that fails with an exception — no privileged role is required.

### Likelihood Explanation
Triggering this path only requires deploying/calling a smart contract that performs a CREATE/CREATE2 opcode whose child initcode intentionally or naturally causes an exception-class failure (e.g., insufficient energy to save the created code, or an opcode/stack error) rather than a plain `REVERT`. This is trivially reachable by any user submitting a `TriggerSmartContract` transaction referencing attacker-controlled bytecode, making the condition easy and cheap to reproduce on-chain.

### Recommendation
Move the `refundEnergyAfterVM(energyLimit, createResult)` call so it executes unconditionally for every exit path of `createContractImpl()` — e.g., call it immediately after `getResult().merge(createResult)` and before branching on `getException()`/`isRevert()`, or restructure the exception branch to call `refundEnergyAfterVM()` before the `return`.

### Proof of Concept
1. Deploy a contract `A` whose function performs `CREATE` with initcode `B` sized/crafted such that `B`'s constructor execution finishes successfully but the resulting deployed code causes `notEnoughSpendEnergy` to be set on `createResult` (i.e., remaining energy after constructor execution is insufficient to pay `saveCodeEnergy` for the returned code length) — this sets `createResult.getException() != null` at line 938-940.
2. Call `A`'s function with an energy limit comfortably larger than what the CREATE sub-call actually consumes before failing (so there is leftover energy within `energyLimit` that should be refunded).
3. Observe that `refundEnergyAfterVM()` is never invoked (early `return` at line 963), so the parent frame's `getEnergyLimitLeft()` is not credited with the leftover energy from the internal CREATE budget.
4. Compare total `EnergyUsageTotal` reported in `TransactionTrace`/`ReceiptCapsule` against the same scenario forced to end via plain `REVERT` (no exception) with equivalent energy consumption up to the failure point — the exception path bills strictly more energy to the caller than the revert path for equivalent internal-call energy consumption, confirming the missing refund.
