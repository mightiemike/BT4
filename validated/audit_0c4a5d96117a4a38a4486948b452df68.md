# No vulnerability found for this question.

**Analysis:** The premise fails once the actual key semantics are traced. `inner_get_matured_miner_payments` looks up rows keyed by `parent_index_block_hash`/`child_index_block_hash`, which are `StacksBlockId` values [1](#0-0) . A `StacksBlockId` is derived from the block's own `(consensus_hash, block_hash)` — i.e., it identifies one specific, immutable block, not a "tip" or fork pointer. Two different forks can only produce the *same* `child_block_id`/`parent_block_id` pair if they are referring to the literal same historical block (a true common ancestor), because any divergence in tenure, transactions, or microblocks changes the block hash.

`find_mature_miner_rewards` resolves the matured miner's `MinerPaymentSchedule` via `get_matured_miner_reward_schedules`, which uses the fork-aware `get_header_by_coinbase_height(tip_index_hash, matured_coinbase_height)` to locate the specific ancestor header, then reads its `MinerPaymentSchedule` by that ancestor's own `index_block_hash` via `get_scheduled_block_rewards_at_block` [2](#0-1) . Since that ancestor block's content (and therefore its `MinerPaymentSchedule`, epoch, and poison-report state) is immutable and independent of whichever tip is later used to reach it, any node whose current tip shares that ancestor computes an identical reward.

This is not an oversight: `inner_insert_matured_miner_reward` explicitly documents and enforces the invariant that two forks may legitimately write the same reward for a shared ancestor, and it hard-asserts equality (`assert_eq!(rw, reward, "FATAL: tried to insert multiple distinct matured parent block reward records")`) if it ever observes a mismatch [3](#0-2) . So the global-by-id lookup in `get_matured_miner_payment` is safe precisely because the id itself encodes the immutable block content, and `find_mature_miner_rewards`'s inputs (`MinerPaymentSchedule`, epoch, poison report) for that ancestor are fork-invariant. There is no code path by which node A and node B, sharing an ancestor block id, could compute or read differing matured-reward values for that same id — the equality the question posits as "broken" is in fact structurally guaranteed by how `StacksBlockId` is constructed and by the assert in the insert path.
