### Title
Predictable/Attacker-Guessable `yield_id` Enables Unauthorized Injection of Resume Data into Pending PromiseYield Receipts - (File: `runtime/runtime/src/ext.rs`)

### Summary
NEAR's `promise_yield_create_with_id` / `promise_yield_resume_with_yield_id` host-function pair lets a contract developer replace the runtime's cryptographically-derived, unguessable `data_id` with an arbitrary, fully user-specified 32-byte `yield_id` that acts as the sole credential required to inject resume data into a pending yielded promise. Exactly like the reported Vercel Workflow bug (a guessable webhook `token` used as the sole authentication for resuming a workflow with attacker-controlled data), any unprivileged transaction sender who can predict or observe the `yield_id` chosen for a pending yield can call the resume path and inject an attacker-controlled payload, with no binding to the original caller's identity.

### Finding Description
`promise_yield_create_with_id` allows a contract's own WASM code to create a `PromiseYield` receipt keyed by a caller-supplied `YieldId` rather than a runtime-generated `CryptoHash`: [1](#0-0) 

The bidirectional mapping is stored only under `receiver_id` + `yield_id` — there is no field recording *which caller/predecessor* is authorized to resume it: [2](#0-1) 

Resuming is a pure lookup by `yield_id`, with no authorization check on the calling context beyond the fact that the resuming code is executing as the same `receiver_id` account: [3](#0-2) 

The host-function entry point simply forwards attacker-suppliable bytes (`yield_id`, `payload`) straight into that lookup, with no freshness/nonce/signature requirement — any WASM call path that reaches this host function can resume any pending yield on the same account if it knows/guesses the `yield_id`: [4](#0-3) 

The creation side documents this "user-provided" and unauthenticated nature explicitly: [5](#0-4) [6](#0-5) 

This is the same root cause class as GHSA-9r75-g2cr-3h76: a "resume"/"webhook" style callback mechanism whose sole authorization is a value fully controlled by the party creating the pending operation, with the runtime providing no default randomness requirement and no caller-identity binding for the resume step. Where the runtime's default `promise_yield_create` derives an unguessable `data_id` (analogous to Workflow's safe default `nanoid`), `promise_yield_create_with_id` reintroduces exactly the vulnerable pattern the Vercel advisory patched: a developer-chosen, potentially predictable identifier (e.g. sequential order IDs, timestamps, or other business identifiers) that serves as the entire authorization for injecting the resume payload.

### Impact Explanation
Contracts using `promise_yield_create_with_id`/`promise_yield_resume_with_yield_id` to implement asynchronous off-chain resolution patterns (oracle callbacks, cross-chain bridge confirmations, deferred settlement, etc.) are exposed if the `yield_id` chosen is predictable, reused, or otherwise exposed (e.g., visible in a prior transaction, derivable from public state, or sequential). Any unprivileged transaction sender who can guess/observe that `yield_id` and route it to the contract's resume path can inject an attacker-controlled `payload` as the resolved data for that yield. Because the resumed contract logic (the original callback method) executes trusting this data as if it came from the legitimate resolver, this can cause unauthorized state transitions such as releasing funds, approving withdrawals, or completing a transfer based on forged data — i.e., concrete unauthorized value movement driven entirely by a single crafted transaction.

### Likelihood Explanation
Reachable directly from an unprivileged, unauthenticated transaction sender via a single `FunctionCall` action to any deployed contract that exposes (directly or indirectly) `promise_yield_resume_with_yield_id` with attacker-influenced `yield_id`/`payload` arguments — precisely the mechanism exercised by the project's own test helper `call_promise` dispatcher (`yield_resume_with_yield_id` op), demonstrating the exact call shape is a first-class, supported feature: [7](#0-6) 

The likelihood of exploitation is contingent on a contract author choosing a guessable `yield_id` (which the API neither prevents nor discourages via any built-in entropy/authorization requirement), mirroring the exact precondition ("official documentation recommended predictable token patterns") that made the original Vercel bug practically exploitable.

### Recommendation
- Require `promise_yield_resume_with_yield_id` callers to additionally verify `predecessor_account_id` matches an expected authorized resolver inside the contract logic (document this loudly, since the runtime provides no such guarantee).
- Consider binding the `YieldIdToDataId` mapping to the `predecessor_id` that created the yield and enforcing that only that account (or a set the contract nominates) is treated as trusted, or exposing an explicit runtime-level warning/config gate for this feature.
- At minimum, update host-function documentation to explicitly warn contract authors never to use guessable/sequential values for `yield_id`, and recommend deriving it from a secret/nonce known only to the authorized resolver, analogous to the Workflow SDK's fix of removing user-suppliable tokens in favor of always-random identifiers.

### Proof of Concept
1. Deploy a contract that (a) on some public method, calls `promise_yield_create_with_id` with a `yield_id` derived from a public/predictable value (e.g., an order counter reflected in an emitted log/view call), attaching a callback that trusts the resumed payload to authorize a fund transfer.
2. Attacker observes/predicts the `yield_id` (e.g., by reading the emitted log or incrementing a known counter) before the legitimate off-chain resolver responds.
3. Attacker sends a single `FunctionCall` transaction invoking the contract's method that forwards to `promise_yield_resume_with_yield_id` with the guessed `yield_id` and an attacker-crafted `payload`.
4. The `PromiseResume` receipt is generated and applied by `apply_action_receipt`, delivering the attacker's payload as though it were the legitimate resolver's data (see `runtime/runtime/src/lib.rs` lines 1554-1616), causing the callback to execute business logic (e.g., release of funds) based on forged input.
