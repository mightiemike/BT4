### Title
Witness cycle rewards are permanently lost when `voteCount == 0` at maintenance time - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
`DelegationStore.accumulateWitnessVi()` is the java-tron equivalent of `LiquidityGauge._checkpoint()`'s reward-integral update: it turns a cycle's accumulated reward into a per-vote reward index (`Vi`) that voters later use to compute their claimable share. When the divisor (`voteCount`) is zero, the function silently skips the accumulation step instead of preserving the reward for later distribution, so the reward recorded for that cycle is never reflected in `Vi` and can never be claimed by any voter, exactly mirroring the reported `totalSupply == 0` bug class.

### Finding Description
`DelegationStore.accumulateWitnessVi()` computes the reward-per-vote delta as:

```java
public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
  BigInteger preVi = getWitnessVi(cycle - 1, address);
  long reward = getReward(cycle, address);
  if (reward == 0 || voteCount == 0) { // Just forward pre vi
    if (!BigInteger.ZERO.equals(preVi)) {
      setWitnessVi(cycle, address, preVi);
    }
  } else { // Accumulate delta vi
    BigInteger deltaVi = BigInteger.valueOf(reward)
        .multiply(DECIMAL_OF_VI_REWARD)
        .divide(BigInteger.valueOf(voteCount));
    setWitnessVi(cycle, address, preVi.add(deltaVi));
  }
}

This is called once per witness, once per maintenance cycle, from `MaintenanceManager.doMaintenance()`:

```java

Rewards for a witness's produced blocks are accrued into `DelegationStore` via `MortgageService.payReward()`, independent of whether that witness currently has any votes:

```java
private void payReward(byte[] witnessAddress, long value) {
  long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
  int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
  double brokerageRate = (double) brokerage / 100;
  long brokerageAmount = (long) (brokerageRate * value);
  value -= brokerageAmount;
  delegationStore.addReward(cycle, witnessAddress, value);
  adjustAllowance(witnessAddress, brokerageAmount);
}
``` [3](#0-2) 

The non-brokerage portion (`value`) is exactly the pool intended to be split among voters proportionally, mirroring `d_reward` in the LiquidityGauge report. If at the end of that cycle the witness's `voteCount` is `0` (e.g., all voters withdraw their votes mid-cycle, or the witness is elected while having zero votes during bootstrap/edge conditions where the active/standby set is not strictly vote-gated), `accumulateWitnessVi` takes the `voteCount == 0` branch and does not fold that cycle's `reward` into `Vi`. Because voter rewards are always computed as `deltaVi * userVote / DECIMAL`, and `deltaVi` for that cycle is zero, the reward recorded via `addReward` for that cycle/witness is never reflected in any voter's claimable amount in `computeReward()`:

```java
BigInteger deltaVi = endVi.subtract(beginVi);
if (deltaVi.signum() <= 0) {
  continue;
}
long userVote = vote.getValue();
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
``` [4](#0-3) 

There is no admin-only recovery path for this stranded value, and the raw `getReward(cycle, address)` value that was recorded but never folded into `Vi` is unreachable by any subsequent computation.

### Impact Explanation
The voter-share portion of a witness's block/transaction-fee reward for any cycle in which that witness's `voteCount` snapshot is `0` at maintenance time is permanently excluded from the reward-index accumulator and can never be claimed by any account, causing silent accounting loss in the DPoS reward-distribution subsystem. This is analogous to, but distinct in root cause detail from, an intentional design choice ("no voters, no voter reward"); the concern is that the value is not reclaimed, returned to a reward pool, or otherwise accounted for — it simply disappears from the ledger.

### Likelihood Explanation
This path is reached automatically by the consensus engine's own maintenance-cycle logic — no privileged actor, malicious peer, or attacker-controlled transaction is required. It requires a witness's `voteCount` to be `0` at the maintenance boundary while it produced blocks and earned rewards during that cycle (e.g., a witness losing all its votes mid-cycle, or entering the active/standby set with zero votes during network bootstrap or low-participation periods). I was not able to fully confirm from the indexed code whether the witness-selection logic in `DposService`/`WitnessScheduleStore` can place a zero-vote witness into the active set under normal mainnet conditions versus only in edge/bootstrap cases — this would need further verification in `consensus/src/main/java/org/tron/consensus/dpos/DposService.java` and `chainbase/src/main/java/org/tron/core/store/WitnessScheduleStore.java`, which the index did not return in enough detail this session.

### Recommendation
In `DelegationStore.accumulateWitnessVi()` and `RewardViCalService.accumulateWitnessVi()`, when `voteCount == 0` but `reward > 0`, do not silently discard the reward: either (a) roll the reward forward to be combined with the next cycle's reward for that witness so it can eventually be distributed once `voteCount > 0` again, or (b) redirect it to a recoverable pool (e.g., add it to the witness's own brokerage/allowance, or a claimable community fund) rather than leaving it unreferenced in the per-cycle `reward` key.

### Proof of Concept
1. Witness `W` is part of the active/standby witness set with `voteCount == 0` (e.g., its only voter unvotes right before the maintenance cycle boundary).
2. `W` produces blocks during cycle `N`; `MortgageService.payBlockReward`/`payTransactionFeeReward` → `payReward` accrues the non-brokerage remainder into `delegationStore.addReward(N, W, value)`. [5](#0-4) 
3. At the next maintenance boundary, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, W, 0)` since `W.getVoteCount() == 0`. [2](#0-1) 
4. Inside `accumulateWitnessVi`, `voteCount == 0` triggers the "just forward pre vi" branch — `Vi` for cycle `N` is not incremented by the accrued `reward`. [1](#0-0) 
5. Any future voter of `W` computing rewards via `computeReward(beginCycle, endCycle, ...)` will see `deltaVi` for cycle `N` unaffected by the discarded reward, so that portion of the reward is permanently unclaimable by anyone. [6](#0-5)

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
