Confirmed root cause. The mechanism is fully documented and code-verified:

- `DeleteAccountAction::beneficiary_id` is a user/contract-controlled `AccountId` field only checked for lexical validity (`AccountId::validate`), never checked for existence, at `runtime/runtime/src/action_validation.rs:602-608` and `runtime/runtime/src/verifier.rs:701-708`.
- `action_delete_account` unconditionally emits `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` carrying the account's *entire* remaining balance, without checking that `beneficiary_id` exists: [1](#0-0) 
- That refund receipt has `predecessor_id == "system"`, i.e. `is_refund = true`, and `check_account_existence`/`implicit_creation_allowed` categorically forbid a refund from ever creating an account, no matter the account-id type: [2](#0-1) 
- When that refund receipt then fails with `AccountDoesNotExist` because `beneficiary_id` doesn't exist, the runtime does not retry, requeue, or return the funds to the deleted account (which no longer exists) — it permanently burns the deposit: [3](#0-2) 
- This "failed refund → burn" behavior is explicitly documented as protocol design: [4](#0-3) 

This is a very close structural analog to the reported bug class: a permissionless, user-signed action (`DeleteAccount`, reachable directly by any transaction signer or via `promise_batch_action_delete_account`/meta-transactions) takes an unvalidated-for-existence destination identifier and, on the wrong input, causes complete, irreversible loss (burn) of the account's balance with no recovery path — exactly analogous to the BitVM Bridge `burn`/`_btc_addr` issue.

### Title
Unvalidated `beneficiary_id` in `DeleteAccount` action permanently burns the account's entire balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction.beneficiary_id` is a free-form `AccountId` supplied by the transaction signer (or by a contract via `promise_batch_action_delete_account`, or through a meta-transaction). It is only validated for lexical correctness, never for existence. If the beneficiary account does not exist, the balance-refund receipt generated to pay it out unconditionally fails and the funds are permanently burned rather than returned to the user in any way.

### Finding Description
`action_delete_account` computes the deleting account's full balance and, without verifying that `beneficiary_id` refers to a live account, pushes a system-refund receipt (`Receipt::new_balance_refund`) addressed to it: [1](#0-0) . The account itself is then removed in the same action (`*account = None;`) before the refund receipt is even executed: [5](#0-4) .

Because the generated receipt has `predecessor_id == "system"` (a refund), `check_account_existence`'s `implicit_creation_allowed` helper unconditionally forbids it from creating any missing account of any type (named, near-implicit, eth-implicit, deterministic, or universal): [6](#0-5) . So if `beneficiary_id` does not exist at the moment the refund is processed, the receipt execution fails with `ActionErrorKind::AccountDoesNotExist`.

The runtime's handling of a failed refund is to burn the deposit outright: [3](#0-2) , matching the documented protocol behavior "If the execution of a refund fails, the refund amount is burnt": [4](#0-3) . Since the source account was already deleted, there is no account left to which the funds could bounce back — the tokens are gone permanently.

Existing tests explicitly acknowledge this trap: the comment "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" in `delete_after_init_removes_account` shows engineers must special-case beneficiary existence to avoid triggering the burn: [7](#0-6) , and `estimator_context.rs` treats such burns as an expected, allowed outcome of self-deleting accounts: [8](#0-7) .

### Impact Explanation
Any account holder can lose their entire account balance permanently and irrecoverably by a single typo, a stale/unregistered `beneficiary_id`, or a contract bug in a batched promise that calls `promise_batch_action_delete_account` with a bad id. This is a direct, concrete "permanently frozen/burnt funds" outcome triggerable purely by an ordinary transaction signer, with no on-chain recourse (the source account is already gone, and refunds to a nonexistent id are categorically disallowed from creating it).

### Likelihood Explanation
`DeleteAccount` is a normal, permissionless action available to any signer, to any `FunctionCall`-permission contract via `promise_batch_action_delete_account`, and through meta-transactions/relayers (as shown by `meta_tx_delete_account`: [9](#0-8) ). No special privileges, timing, or validator behavior are required — only supplying a beneficiary id that happens to not exist (e.g., a typo, a never-created near-implicit/eth-implicit hex id, or a name that hasn't been registered yet).

### Recommendation
Before executing `DeleteAccount`, verify that `beneficiary_id` corresponds to an existing account (or otherwise refuse the delete/refund) rather than silently burning the balance on a failed system refund; alternatively, route a failed delete-account refund back to a recoverable location (e.g., treat it as a deposit refund to the deleting account's predecessor before the account is removed) instead of unconditionally burning it.

### Proof of Concept
1. Create account `victim.near` with a nonzero balance.
2. `victim.near` submits `DeleteAccount { beneficiary_id: "typo-nonexistent.near" }` (a syntactically valid but never-created account id), as the sole/final action.
3. `action_delete_account` deletes `victim.near` and emits a `Receipt::new_balance_refund("typo-nonexistent.near", balance)` (`runtime/runtime/src/actions.rs:380-386`).
4. The refund receipt (`predecessor_id == "system"`) is processed; `check_account_existence` rejects the implicit `Transfer` since refunds may never create an account (`runtime/runtime/src/actions.rs:928-947`), yielding `AccountDoesNotExist`.
5. `apply_action_receipt` sees the refund failed and adds the full amount to `stats.balance.other_burnt_amount` (`runtime/runtime/src/lib.rs:1047-1054`) — the funds are permanently burned; `victim.near` no longer exists to receive anything back.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
