Based on my investigation, I found a genuine analog to the reported bug class in the vault pause/accrual mechanism, matching the "clock advanced only on change" pattern explicitly permitted by the scan rules.

### Title
Unpausing accrual silently discards interest owed for the entire paused duration by jumping `last-update` forward - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`)

### Summary
`set-pause-states` in the USDC vault (and mirrored in the other `v0-vault-*.clar` contracts) advances the `last-update` clock to `stacks-block-time` only when the `accrue` pause flag transitions from paused to unpaused, without ever running the interest-rate model over the elapsed paused window. This permanently drops the interest that should have accrued to lenders (and been charged to borrowers) for the entire paused period, analogous to the Convex report's "value received/owed but with no path to reconcile it," except here the lost value is index-based yield rather than an ERC20 token balance.

### Finding Description
The pause-state setter contains this logic: [1](#0-0) 

```
(define-public (set-pause-states (states {deposit: bool, redeem: bool, borrow: bool, repay: bool, accrue: bool, flashloan: bool}))
  (begin
    (try! (check-dao-auth))
    (let ((current (var-get pause-states))
          (was-paused (get accrue current))
          (now-paused (get accrue states)))
      ;; When pausing accrue, accrue first to capture pending interest
      (if (and (not was-paused) now-paused)
          (begin (try! (accrue)) false)
          false)
      ;; When unpausing accrue, jump last-update to now to skip paused period
      (if (and was-paused (not now-paused))
          (var-set last-update stacks-block-time)
          false)
      (var-set pause-states states)
      ...
```

The `accrue` step on entering pause correctly captures interest up to the pause point. However, on exit from pause, instead of computing/accruing interest for the elapsed paused interval (or leaving `last-update` untouched so the next `accrue()` call charges/credits interest for the full period), the code force-sets `last-update` to the current `stacks-block-time`. This is exactly the "clock advanced only on change" pattern: the timestamp used by the interest-rate model to compute elapsed time is mutated based on a state transition (unpause) rather than being derived from actual elapsed accrual, permanently erasing the record that time passed while accrue was paused.

Because `deposit`, `redeem`, `borrow`, and `repay` are controlled by independent pause flags in the same `pause-states` tuple, a DAO operator can pause only `accrue` (e.g., during an oracle incident or interest-model migration) while leaving `deposit`/`borrow`/`repay` active. Positions continue to change size during the pause window, but because `last-update` is fast-forwarded on unpause, the interest-rate model (keyed off `stacks-block-time - last-update`) never sees the elapsed duration and never accrues interest for it.

### Impact Explanation
Any interest that should have accrued to zToken holders (suppliers) for the paused duration is permanently lost — it can never be recovered because the timestamp record used to compute it is destroyed. This is a permanent freezing/loss of unclaimed yield for depositors, matching the "High" impact category (permanent freezing of unclaimed yield), the same impact class as the Convex report (stuck/unrecoverable yield). Depending on how long `accrue` remains paused and how much activity happens in that window, the amount of lost yield scales with vault TVL and the pause duration.

### Likelihood Explanation
This triggers deterministically any time the DAO toggles the `accrue` pause flag off after having toggled it on, which is a normal operational lever exposed by `set-pause-states` (guarded only by `check-dao-auth`, not by any invariant preventing this sequence). No malicious external actor input is required; the loss occurs purely from the intended pause/unpause workflow.

### Recommendation
On unpausing `accrue`, do not simply overwrite `last-update`. Instead, either (a) run the accrual calculation using the pre-pause `last-update` value first so the paused interval is properly settled before advancing the clock, or (b) leave `last-update` unchanged on unpause and let the next natural `accrue()` call compute interest across the full paused span, exactly as is already done symmetrically on the pause transition (`(try! (accrue))`).

### Proof of Concept
1. DAO calls `set-pause-states` with `accrue: true` (others false) — `accrue` runs once, capturing interest up to now, `last-update = T0`. [2](#0-1) 
2. Time passes (`stacks-block-time` advances to `T1`), and deposits/borrows continue against the vault since only `accrue` is paused.
3. DAO calls `set-pause-states` again with `accrue: false` — `last-update` is force-set to `T1` rather than being derived from an accrual computation spanning `T0` to `T1`. [3](#0-2) 
4. Interest for the `[T0, T1]` window is never charged to borrowers nor credited to suppliers, and cannot be recovered since the only stateful record of elapsed time was overwritten.

I could not fully trace whether every other vault contract (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`) contains byte-identical logic due to remaining tool-call budget; the pattern was verified directly only in `v0-vault-usdc.clar`, though the shared architecture description suggests it is duplicated across all vault implementations.
