This confirms the analog: no minimum inbound amount is enforced anywhere in scope, and `afterInboundBallotTerminal` performs a full unbounded `Walk` over the entire `PendingInbounds` collection on every single ballot terminal transition.

### Title
Unbounded `PendingInbounds.Walk` scan in `afterInboundBallotTerminal` lets an attacker DoS inbound-ballot finalization by spamming dust cross-chain deposits - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
The external report's core bug class — an attacker inflating an unbounded, attacker-influenced list that a privileged/periodic function must fully iterate, causing DoS — has a direct analog in Push Chain's inbound ballot finalization hook. `afterInboundBallotTerminal` performs a full linear `Walk` over the entire `PendingInbounds` collection every time any single inbound ballot reaches a terminal state (`PASSED`/`EXPIRED`/`REJECTED`), just to find which entry owns the given `ballotID`. Because there is no minimum-amount gate on inbound deposits anywhere in `x/uexecutor`, an unprivileged attacker can cheaply create arbitrarily many distinct dust cross-chain deposits on a source chain, each producing a unique `utx_key` and a fresh `PendingInboundEntry` that honest, honestly-behaving Universal Validators will faithfully observe and vote on per protocol duty (no malicious validator assumption required).

### Finding Description
`RecordInboundVote` (`x/uexecutor/keeper/inbound.go:27-88`) creates one `PendingInboundEntry` per unique `utx_key = sha256(source_chain:tx_hash:log_index)` the first time any validator votes on it [1](#0-0) . There is no minimum deposit/amount validation gating this — any inbound observed by validators, however small, creates an entry.

Each entry's ballot, once it reaches quorum or expires, fires `AfterBallotTerminal` → `afterInboundBallotTerminal`, which does:
```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [2](#0-1) 

This is an unbounded, full-collection scan performed synchronously inside `VoteInbound` message processing (via `CheckIfFinalizingVote` → `MarkBallotFinalized` → `fireBallotTerminalHook`) for *every* ballot that becomes terminal [3](#0-2) . The comment in the code explicitly assumes "the pending set is small and transient" — an assumption an attacker directly controls and can violate [4](#0-3) .

An attacker who fires N distinct dust inbound events (from many source-chain EOAs or many tx_hash/log_index combinations) that validators are actively voting on but that haven't all reached quorum yet inflates `PendingInbounds` to size N. Each subsequent ballot finalization (of any of these N entries, or of any unrelated inbound ballot that races them) then costs O(N) work, turning the aggregate processing of N pending inbounds into O(N²) state-machine work executed inside ordinary transaction processing (`MsgVoteInbound`), which is itself a gasless, whitelisted message type [5](#0-4) .

### Impact Explanation
This directly parallels the "[H-05]" bug class: an attacker-inflatable, unbounded list is fully iterated by a downstream finalization function, and there is no minimum-value floor to raise the attack cost. Here the impact is a liveness/DoS risk against the honest-validator inbound finalization path — as the attacker grows the number of concurrently pending (not-yet-fully-finalized) inbound observations, per-ballot finalization cost grows linearly and aggregate cost grows quadratically, degrading block processing time for `MsgVoteInbound` transactions and potentially delaying or starving legitimate inbound finalizations (funds effectively stuck pending finalization for longer, and validator resource exhaustion). Because `MsgVoteInbound` is a gasless whitelisted message, the *voting* side already carries no fee-based rate limiting, and because there is no minimum inbound amount, the *triggering* side (dust deposits on the source chain) is cheap too.

### Likelihood Explanation
Moderate-to-high. It requires generating many distinct source-chain events, which costs whatever gas/fee the source chain charges per dust transaction (can be cheap on low-fee chains), and it relies on honestly-behaving Universal Validators continuing to observe and vote per their normal protocol duty — no malicious validator or admin assumption needed, matching the "unprivileged external attacker" and "honest validators" constraints of the scope.

### Recommendation
- Avoid a full-collection `Walk` in `afterInboundBallotTerminal`; instead, maintain and pass through a reverse index from `ballotID` → `utx_key` (populated alongside `RecordInboundVote`) so the hook can do an O(1)/O(log n) lookup instead of an O(N) scan.
- Consider bounding the number of concurrently outstanding `PendingInbounds` entries or enforcing a minimum economically-meaningful inbound amount/value threshold (mirroring the external report's "raise minimum deposit" mitigation) to raise the cost of generating spam entries.

### Proof of Concept
1. Attacker submits many small-value cross-chain transfers on a supported source chain (e.g., 1 wei/lamport equivalents), each with a distinct `tx_hash`/`log_index`, keeping each just below the vote quorum threshold (e.g., by controlling timing so votes trickle in slowly) so many `PendingInboundEntry` records accumulate simultaneously in `PendingInbounds`.
2. Honest Universal Validators, following protocol, submit `MsgVoteInbound` for each observed event, calling `RecordInboundVote` and growing the `PendingInbounds` collection to size N [1](#0-0) .
3. As ballots for these (or any other concurrent) inbound events reach quorum/expiry, each triggers `afterInboundBallotTerminal`'s full `PendingInbounds.Walk`, each costing O(N) [2](#0-1) , degrading validator/full-node processing time for `MsgVoteInbound` transactions as N grows, unbounded by any minimum-deposit-amount check.

func (k Keeper) CheckIfFinalizingVote(ctx context.Context, b types.Ballot) (types.Ballot, bool, error) {
	ballot, isFinalizing := b.IsFinalizingVote()
	if !isFinalizing {
		return b, false, nil
	}

	k.Logger().Debug("ballot reached finalization threshold",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)

	if err := k.MarkBallotFinalized(ctx, ballot.Id, ballot.Status); err != nil {
		return ballot, false, errors.Wrap(err, "failed updating finalized ballot")
	}

	k.Logger().Debug("ballot finalized",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)
	return ballot, true, nil
```
