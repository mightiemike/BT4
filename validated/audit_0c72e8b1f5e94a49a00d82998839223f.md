### Title
Unbounded Gzip Decompression in RPC Declare-Transaction Path Allows Memory-Exhaustion DoS - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The `decompress_program` function used to decode Cairo-0 `compressed_program` data from user-submitted `DECLARE_TXN_V1` (broadcasted declare) requests decompresses attacker-supplied gzip data with **no size limit and no CPU/time bound**, unlike every other decompression routine in this codebase (`apollo_storage::compression_utils::decompress` uses `MAX_DECOMPRESSED_SIZE`, `starknet_api::compression_utils::decompress_with_size_limit` enforces `max_size`). This is the same bug class as CVE-2019-10094 (Apache Tika `RecursiveParserWrapper` — "Allocation of Resources Without Limits or Throttling", CWE-770): a small, cheaply-produced compressed payload can decompress to an arbitrarily large output, exhausting memory/CPU of the node handling it.

### Finding Description
`decompress_program` in [1](#0-0)  base64-decodes and then gzip-decompresses (`GzDecoder::read_to_end`) an attacker-controlled `compressed_program` field with an explicit `// TODO(dan): add time and size limits.` comment acknowledging the missing guard. `read_to_end` will keep growing the output `Vec<u8>` until the entire decompressed stream is consumed or the process runs out of memory — there is no `take()` limiter as used elsewhere.

This function is reached from `user_deprecated_contract_class_to_sn_api`, which is invoked when converting a `BroadcastedDeclareV1Transaction` (an attacker-supplied Cairo-0 declare payload) into an `ExecutableTransactionInput::DeclareV1`, via the `TryFrom<BroadcastedDeclareTransaction> for ExecutableTransactionInput` implementation: [2](#0-1) . This conversion path is exercised by RPC methods that accept broadcasted transactions for local execution/estimation (e.g. `estimate_fee`/`simulate`/`call`-style endpoints implemented via `TryFrom<BroadcastedTransaction> for ExecutableTransactionInput`, [3](#0-2) ) — i.e. any unauthenticated RPC caller can submit a crafted `BroadcastedDeclareV1Transaction` whose `contract_class.compressed_program` is a small, highly-compressed gzip blob that expands to gigabytes, before any resource-bound validation (max_fee/step limits) is applied to the decompressed `Program`.

By contrast, the codebase's other decompression call-sites for the exact same kind of payload (Sierra program compression, storage-layer contract class compression, proof decompression) all impose explicit size limits: [4](#0-3) , [5](#0-4) , [6](#0-5) . `decompress_program` is the one un-throttled outlier.

### Impact Explanation
An unprivileged RPC client can send a crafted, small declare-transaction payload that triggers unbounded memory allocation on the node process handling the RPC request (the node running `apollo_rpc`). This can crash or OOM the RPC-serving process, degrading or halting that node's ability to serve RPC calls (a denial-of-service against a sequencer/full-node RPC endpoint). Because `apollo_rpc` executes the transaction locally (not committed on-chain), this does not directly corrupt state or cause honest-node divergence, but it can starve resources on the process (which, depending on deployment topology, may co-host gateway/mempool components), degrading network liveness/availability for RPC-served transaction submission.

### Likelihood Explanation
Likelihood is high for triggering the code path: the vulnerable function is reachable directly from a single, unauthenticated, user-supplied broadcasted declare-transaction JSON payload with no special permissions, no prior state, and requires only crafting a gzip bomb (well-understood technique, e.g., nested/OOB compression ratio). No mempool admission, fee payment, or on-chain confirmation is required to trigger the decompression, since it happens during local RPC-side conversion before further validation.

### Recommendation
Add a bounded-size decompression guard to `decompress_program`, mirroring the pattern already used elsewhere in the codebase (e.g. `starknet_api::compression_utils::decompress_with_size_limit`), by wrapping the `GzDecoder` read with `.take(max_size)` and rejecting the payload if the decompressed length reaches/exceeds the configured maximum before returning. Additionally, consider adding a CPU/time budget or streaming size check to further mitigate CPU-bound decompression amplification.

### Proof of Concept
1. Craft a `DeprecatedContractClass` with a `compressed_program` field containing a gzip stream that is small (e.g., a few KB) but decompresses to several hundred MB or GB (a classic "gzip/zip bomb", e.g., highly repetitive zero-byte input compressed at max ratio).
2. Submit a `BroadcastedDeclareV1Transaction` containing this contract class to an RPC endpoint that triggers `TryFrom<BroadcastedDeclareTransaction> for ExecutableTransactionInput` (e.g., a fee-estimation/simulation RPC call accepting broadcasted transactions).
3. Observe that `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) calls `decoder.read_to_end(&mut decompressed)` with no bound, causing the RPC-serving process to allocate memory proportional to the decompressed size, leading to excessive memory consumption / OOM / crash of the node process.

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.
    let mut decoder = GzDecoder::new(compressed_data.as_slice());
    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
