### Title
Non-atomic two-phase index + cache read in `calculate_accounts_lt_hash_at_startup_from_index`/`calculate_capitalization_at_startup_from_index` can lock in a stale account version, producing a wrong lattice-hash/capitalization - (File: `accounts-db/src/accounts_db.rs`)

### Summary
The audit finding describes a "value locked in at one point in time" bug class: `fulfillRedeem` reads the price-per-share once and never re-validates it against subsequent state changes, so a stale valuation is later used as if it were current, causing the ledger to become internally inconsistent. The same "read now, reuse later without re-validating" pattern exists in `AccountsDb::calculate_accounts_lt_hash_at_startup_from_index` and its sibling `calculate_capitalization_at_startup_from_index`, which compute a value by making two *independent, non-atomic* passes over an account's state — once via the accounts index, and once via the write cache — and combine them as if they were a single consistent snapshot.

### Finding Description
`calculate_accounts_lt_hash_at_startup_from_index` first walks every index bin and mixes in the lt-hash of whatever version the index currently points to: [1](#0-0) 

It then performs a *second, separate* pass over `accounts_cache.cached_pubkeys()`, re-reading the index (`get_with_and_then`) to "mix out" the version the first pass counted, and then calling `self.load(...)` to "mix in" the cache's current version: [2](#0-1) 

The doc comment on the function explicitly acknowledges the fragility of this design: "NOT safe to call concurrently with flush operations": [3](#0-2) 

Because the index-walk phase and the cache-patch phase are not one atomic operation, any account mutation (a new store, or a cache→storage flush) that lands between the two phases is either double-counted (index has version A, cache-patch mixes-out version A but mixes-in version B that was already superseded by the time of mix-out lookup) or missed (an account leaves the cache between `cached_pubkeys()` being snapshotted and the mix-out re-lookup, so `get_with_and_then` finds nothing to mix out even though the earlier index pass already counted the old value, or `self.load` fails to find the cache entry at all and the mix-in is skipped). This mirrors the report's root cause exactly: a value ("PPS"/lt-hash contribution) is captured from one read and is combined with a second read of the *same logical entity* without the two reads being coupled to a single consistent point in time, so state that changes in between is silently mis-accounted.

`calculate_capitalization_at_startup_from_index` has the identical structural flaw — it separately reads `stored_lamports(pubkey)` from the index and `cached_lamports` from `self.load(...)`, then subtracts to compute a delta: [4](#0-3) 

If the account's cache/storage location changes between those two independent reads, the computed delta no longer matches any real point-in-time state of the account.

### Impact Explanation
Both functions feed directly into consensus-relevant invariants:
- `calculate_accounts_lt_hash_at_startup_from_index` is used by `Bank::verify_accounts` to check the accounts lattice hash against the value carried in the bank during startup/ledger-tool verification: [5](#0-4)  — a mismatch here produces `"Verifying accounts failed: accounts lattice hashes do not match"` and can abort startup/verification.
- `calculate_capitalization_at_startup_from_index` (via the equivalent index-generation path) underlies capitalization checks used when loading a bank from a snapshot; a wrong value there triggers `SnapshotError::MismatchedCapitalization`, causing the node to fail to start: [6](#0-5) 

This matches the category of concrete impact called for: a genuine hash/capitalization divergence or node panic caused by combining two reads of account state that are not coupled to the same instant, exactly as the SukukFi report describes value being "locked in" from one snapshot in time and then treated as valid against a later, changed state.

### Likelihood Explanation
The doc comment on `calculate_accounts_lt_hash_at_startup_from_index` itself states the precondition for correctness — no concurrent flush — meaning the authors are aware this function is unsound if that precondition is violated. The function is reachable outside of pure "startup with no concurrent activity": `SnapshotMinimizer::minimize` calls `calculate_accounts_lt_hash_at_startup_from_index` on a live `Bank` during `create-snapshot --minimize`, after `force_flush_accounts_cache()` but with no guarantee that no other write path (e.g., a concurrent scan repopulating the write cache, or an in-flight store) touches the cache in between the two phases: [7](#0-6) . Likelihood is bounded by the fact that most call sites are startup/verification paths, so the race window and adversarial control over timing are limited, but the mechanism itself is a clear violation of "read a value once, reuse it later as if unchanged."

### Recommendation
Make the two phases into one atomic read per pubkey, rather than a "read index, then separately read cache" reconciliation:
- Read each pubkey exactly once via a single locked lookup path (e.g., through `do_load`'s existing write-cache-first semantics) so the lt-hash/capitalization contribution is computed from one consistent version, instead of computing an index-based value and a cache-based delta from two independent point-in-time reads.
- Alternatively, hold a lock/guard (e.g., a flush-inhibiting guard) for the full duration of the calculation so the "NOT safe to call concurrently with flush operations" precondition documented in the comment is actually enforced by code, not just by convention.
- Add a debug-mode consistency assertion that the account state observed by the index-pass and the cache-pass for a given pubkey correspond to the same write-cache "epoch"/version, panicking loudly instead of silently mis-hashing when violated.

### Proof of Concept
Not directly exploitable by an unprivileged network attacker (this is a local reconciliation bug in an internal accounting routine, not a network-attacker-controlled account), so no adversarial transaction sequence PoC is provided; the root cause is demonstrated structurally above by the split between the index pass and cache pass in `calculate_accounts_lt_hash_at_startup_from_index`: [8](#0-7) , together with the explicit non-concurrency-safety disclaimer in its own doc comment: [3](#0-2) .

    pub fn calculate_capitalization_at_startup_from_index(&self, ancestors: &Ancestors) -> u64 {
        let stored_lamports = |pubkey: &Pubkey| {
            self.accounts_index
                .get_with_and_then(pubkey, ancestors, false, |(slot, account_info)| {
                    (!account_info.is_zero_lamport()).then(|| {
                        self.get_account_accessor(slot, &account_info.storage_location())
                            .get_loaded_account(|loaded_account| loaded_account.lamports())
                            // SAFETY: The index said this pubkey exists, so
                            // there must be an account to load.
                            .unwrap()
                    })
                })
                .flatten()
                .unwrap_or(0)
        };

        let storage_capitialization = self
            .accounts_index
            .account_maps
            .par_iter()
            .map(|accounts_index_bin| {
                accounts_index_bin
                    .keys()
                    .into_iter()
                    .map(|pubkey| stored_lamports(&pubkey))
                    .try_fold(0, u64::checked_add)
            })
            .try_reduce(|| 0, u64::checked_add)
            .expect("capitalization cannot overflow");

        // Sum as i128 because there is potential (although unlikely) for the cache updates to
        // overflow i64::MAX. For example, if the cache has multiple transactions that transfer a
        // large amount of lamports from one account to another, it could sum all of the transfers
        // from accounts first, overflow i128. Wrapping logic could also handle this properly (ie.
        // come to the correct answer), but then detection of overflow would be broken.
        let cached_update = self
            .accounts_cache
            .cached_pubkeys()
            .iter()
            .map(|pubkey| {
                // subtract out whatever older version the index walk produced (if any)
                let stored_lamports = stored_lamports(pubkey);

                // add in the cached amount of lamports
                let cached_lamports = self
                    .load(
                        ancestors,
                        pubkey,
                        LoadHint::FixedMaxRoot,
                        PopulateReadCache::False,
                    )
                    .map(|(account, _slot)| account.lamports())
                    .unwrap_or(0);

                cached_lamports as i128 - stored_lamports as i128
            })
            .sum::<i128>();

        i128::from(storage_capitialization)
            .checked_add(cached_update)
            .and_then(|result| u64::try_from(result).ok())
            .expect("capitalization cannot overflow")
    }
