### Title
Cross-network replay of council-signed `BatchProofMethodId` upgrades between `Network::Nightly` and `Network::TestNetworkWithForks` due to non-injective `citrea_network_to_chain_id` and shared default authority keys - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the identical chain id `5665`, and the default (env-var-unset) fallback method-id upgrade authority public keys for these two networks in `initial_values.rs` are byte-for-byte identical. Consequently, a genuine, council-signed `BatchProofMethodId` inscription produced for `TestNetworkWithForks` passes every check in `run_l1_block`'s `DataOnDa::BatchProofMethodId` branch when replayed verbatim on a `Network::Nightly`-configured light client circuit.

### Finding Description
The binding the code is supposed to enforce is: *a method-id upgrade accepted on network N == a body the council actually signed for N*. The circuit approximates this binding only through `chain_id`: [1](#0-0) 

and `citrea_network_to_chain_id` is not injective — it returns the same value `5665` for both `Network::Nightly` and `Network::TestNetworkWithForks`: [2](#0-1) 

Because both networks map to the same `chain_id`, the `circuit_chain_id != body.chain_id` guard cannot distinguish a body the council intended for `TestNetworkWithForks` from one intended for `Nightly`. The remaining check, `verify_method_id_security_council`, is keyed on `method_id_upgrade_authority_da_public_keys`, which by default is identical between the two networks when the `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` env vars are unset: [3](#0-2) [4](#0-3) 

Both constant blocks fall back to the exact same five hex pubkeys (`0313c4ff...`, `03b15df9...`, `03fb89fd...`, `037d415a...`, `022fad51...`) unless the operator explicitly overrides them at compile time.

Exploit flow: attacker observes a real, validly-signed `BatchProofMethodId` DA inscription that the security council published for `TestNetworkWithForks` (a publicly visible Bitcoin transaction). The attacker copies the raw blob bytes verbatim and inscribes a new Bitcoin transaction with identical bytes, submitted to/mined on whatever chain a `Nightly`-configured light client prover monitors. When that prover processes the block in `run_l1_block`:
- `activation_l2_height` check passes if the copied body's activation height exceeds Nightly's current watermark (plausible given independent height progression on the two networks).
- `circuit_chain_id != body.chain_id` passes because both equal `5665`.
- `verify_method_id_security_council` passes because Nightly's default authority keys are identical to those the council actually used to sign the `TestNetworkWithForks` body.

The upgrade is then inserted into `BatchProofMethodIdAccessor` for Nightly: [5](#0-4) 

No other guard in this code path checks anything network-specific beyond `chain_id` and the authority key set, both of which collide by default between these two networks.

### Impact Explanation
This is a method-id upgrade accepted on `Network::Nightly` that the council never specifically authorised for `Nightly` — it was authorised for a different network (`TestNetworkWithForks`) whose test/staging method IDs and activation schedule are not vetted for Nightly's actual chain state. This lets an unprivileged attacker (who need only observe a public Bitcoin inscription and pay fees to re-inscribe it) force Nightly's light client circuit to switch to a batch proof method id it was never meant to run, which can desynchronize provers/nodes on what constitutes a valid batch proof, or cause an already-known/test method id (with weaker guarantees) to become authoritative on Nightly. This matches the Critical category "a sequencer commitment or method-id upgrade accepted that was never authorised." It is repeatable for every future `TestNetworkWithForks` method-id inscription as long as operators leave the `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` env vars unset for both networks.

### Likelihood Explanation
Preconditions are narrow but realistic: both networks must be run with the default (unset) `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` env vars, which is the out-of-the-box behavior documented directly in `initial_values.rs`. Given that, the attack costs only ordinary Bitcoin inscription fees and requires no privileged key material — the attacker reuses a signature the council already produced. This is a real, currently-reachable configuration bug in shipped constants rather than a purely theoretical one, since `Network::Nightly` and `Network::TestNetworkWithForks` explicitly share both the fallback chain id (`5665`) and fallback authority keys.

### Recommendation
Give `Network::Nightly` and `Network::TestNetworkWithForks` distinct chain ids in `citrea_network_to_chain_id`, and/or use disjoint default authority public keys for the two networks in `initial_values.rs` so a body signed (and chain_id-tagged) for one network can never satisfy the checks for the other. Do not rely on `chain_id` equality alone as a network-authorization proxy when two `Network` variants can share the same value.

pub fn citrea_network_to_chain_id(network: sov_rollup_interface::Network) -> u64 {
    match network {
        sov_rollup_interface::Network::Mainnet => 4114,
        sov_rollup_interface::Network::Testnet => 5115,
        sov_rollup_interface::Network::Devnet => 62298,
        sov_rollup_interface::Network::Nightly => 5665,
        sov_rollup_interface::Network::TestNetworkWithForks => 5665,
    }
}
