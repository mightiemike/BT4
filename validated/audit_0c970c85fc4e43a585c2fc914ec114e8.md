## Finding

### Title
Witness block/transaction-fee rewards are permanently lost for cycles with zero voter participation - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
The DPoS reward-per-vote (`Vi`) accounting mechanism accumulates a witness's block and transaction-fee rewards into a running per-vote index (`Vi`) once per maintenance cycle. If the witness's snapshot vote count for that cycle is `0`, the reward earned during the cycle is silently dropped instead of being carried forward or refunded — exactly the "rewards permanently lost when supply/stake is zero" bug class described in the referenced report, where `rewardPerToken()` fails to accumulate the reward and the timestamp/cycle still advances past it.

### Finding Description
`MortgageService.payReward()` credits a witness's reward bucket for the *current cycle* purely based on brokerage settings, with no dependency on whether the witness currently has any votes: [1](#0-0) 

At the next maintenance boundary, `MaintenanceManager.doMaintenance()` accumulates that cycle's reward into the per-vote index `Vi` for every witness, passing in the witness's live vote count captured *before* the current cycle's vote tally is applied: [2](#0-1) 

`DelegationStore.accumulateWitnessVi()` is the analog of `rewardPerToken()`/`updateReward()` in the reported bug: if `voteCount == 0` (the “totalSupply == 0” condition), the accrued `reward` for that cycle is discarded — `Vi` is merely forwarded unchanged instead of accumulating the reward — and the per-cycle `reward` value stored via `addReward` is never read again after this point: [3](#0-2) 

This is precisely the pattern in the report: elapsed “time” (here, cycle progression, which is unconditionally advanced every maintenance in `dynamicPropertiesStore.saveCurrentCycleNumber(nextCycle)`) keeps moving forward while the zero-stake condition (`voteCount == 0`) prevents the reward from ever being folded into the distributable index. Since `Vi` for that cycle is never touched again by any later computation (`computeReward` in `MortgageService`/`VoteRewardUtil` only reads deltas between snapshot cycles going forward), the reward is unrecoverable by any future voter of that witness. [4](#0-3) 

This mirrors the second half of the report too ("rewards are added at the same time that ibTokens are allowed to be deposited... the longer it goes before the first deposit the more tokens that are lost"): a freshly created witness (`WitnessCreateContract`, an unprivileged/user-triggered transaction) starts with `voteCount == 0`. Any block/transaction-fee reward it accrues in cycles before it accumulates its first non-zero vote tally (e.g., during initial network bootstrap where the active/top witness set can include witnesses with zero or tied votes) is guaranteed to be dropped by `accumulateWitnessVi`, with no way for later voters to reclaim it.

### Impact Explanation
This causes a permanent accounting loss of witness reward funds that were already deducted from the block/tx-fee reward pool via `payReward`/`addReward` but never become claimable by any voter through `withdrawReward`/`queryReward`. It is a real, silent value-loss/accounting-corruption bug in the on-chain reward distribution system, not merely a griefing vector — TRX is effectively burned from the protocol's promised reward pool without any explicit burn accounting.

### Likelihood Explanation
The zero-vote-count condition naturally occurs whenever a witness is newly created (0 votes by default) yet is still part of the active/elected witness set producing blocks (most plausible during network bootstrap, small private/test networks with fewer candidates than slots, or a witness that temporarily loses all its votes between snapshot points). No special privilege is required — witness creation and vote clearing are both regular unprivileged transactions (`WitnessCreateContract`, `VoteWitnessContract`), so triggering the zero-vote/reward-accrual window is achievable by any user, though the amount of reward lost per occurrence is bounded by the reward paid during that single cycle window.

### Recommendation
When `voteCount == 0` in `DelegationStore.accumulateWitnessVi` (and its `RewardViCalService` counterpart), do not silently discard `reward`; either carry it forward to be merged into the next cycle that has a non-zero vote count, or explicitly account for/burn it with an auditable log, rather than leaving it as unread dead state in `getReward(cycle, address)`.

### Proof of Concept
1. Create a new witness account via `WitnessCreateContract` (unprivileged transaction) with `voteCount == 0`.
2. Ensure it is part of the active witness set for at least one cycle (e.g., small witness count network, or genesis-adjacent state) so it produces blocks and receives `payBlockReward`/`payTransactionFeeReward`, both of which call `MortgageService.payReward` → `delegationStore.addReward(cycle, witnessAddress, value)` unconditionally. [5](#0-4) 
3. At the next `doMaintenance()`, `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` is called with `voteCount == 0` (since no vote has yet been tallied for the witness), causing the accrued reward for that cycle to be dropped instead of accumulated into `Vi`. [6](#0-5) 
4. Even after voters later vote for this witness and rewards begin accumulating normally, `computeReward`/`VoteRewardUtil.computeReward` only ever compute deltas of `Vi` between cycle snapshots going forward — the discarded cycle's reward is never recoverable by anyone. [3](#0-2)

    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
