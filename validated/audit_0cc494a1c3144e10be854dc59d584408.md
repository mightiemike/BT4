Found here: `throwFailedRequest` in `packages/apps/shopify-api/lib/clients/common.ts` is called from the `GraphqlClient.request()` method whenever `response.errors` is truthy (from `@shopify/admin-api-client`'s `request()` result), with `response` itself passed in as `body`. Inside `throwFailedRequest`, when `response.status === StatusCode.Ok` (200), the code does `body.errors.graphQLErrors` without first checking that `body.errors` is non-null/defined, which is the same unchecked-nested-field dereference pattern the external report flags (`restorationProofResult.RestoredBalance` accessed without a null check).

### Title
Unchecked `body.errors` field access in `throwFailedRequest` can crash the request handler on malformed Shopify API responses - (File: `packages/apps/shopify-api/lib/clients/common.ts`)

### Summary
`throwFailedRequest(body, atMaxRetries, response)` dereferences `body.errors.graphQLErrors` when `response.status === StatusCode.Ok`, but the surrounding logic guarantees `response` exists — not that `body.errors` exists or is an object. [1](#0-0) 

### Finding Description
The `GraphqlClient.request()` method calls `throwFailedRequest(response, retries>0, fetchResponse)` whenever the admin-api-client's parsed response object has a truthy `errors` field. [2](#0-1) 
The upstream response parsing (`processJSONResponse`) sets `errors` on the returned object based on GraphQL-layer conditions (`errors || !data`), and the `response.status` passed through is the original HTTP status of the Shopify Admin API call — which can be `200 OK` even when the GraphQL payload itself is malformed (e.g., `{}` with neither `data` nor `errors`, or a response shape where `errors` exists but isn't the expected `{graphQLErrors, message, ...}` object). [3](#0-2) 
In `throwFailedRequest`, when `response.status === StatusCode.Ok`, the code unconditionally evaluates `body.errors.graphQLErrors` — if `body.errors` is `undefined` (a state reachable when the object is a synthetic "no data or errors" error, or any other shape not matching the expected schema), this throws an unhandled `TypeError: Cannot read properties of undefined (reading 'graphQLErrors')` instead of throwing the intended `ShopifyErrors.*` typed exception. [4](#0-3) 

### Impact Explanation
This code path is reached by any authenticated app request that issues a GraphQL admin API call, whenever the Shopify Admin API (or a proxy/CDN/network intermediary sitting between the app and Shopify) returns a `200`-status response whose JSON body doesn't match the expected `{data, errors, extensions}` schema. A crash here throws an untyped `TypeError` instead of a handled `ShopifyErrors.HttpResponseError`/`GraphqlQueryError`, which — depending on the app framework's error boundary — can result in an unhandled exception and process-level crash of the request handler, a denial-of-service condition analogous to the reported `RestoredBalance` nil-pointer panic. This is a defensive-coding gap rather than a directly attacker-forged-session or credential-theft bug: the attacker-controllable surface is limited to what a network path to Shopify's own API can influence.

### Likelihood Explanation
Likelihood is low-to-medium: it requires the Shopify Admin API itself (or something on the network path) to return a 200 response with a malformed/unexpected JSON error shape, which is not attacker-controlled from an anonymous HTTP/webhook/app-proxy request in the normal case. This differs from the original report's model (server directly trusts an operator-configured, potentially malicious `gethclient`), so this shopify-app-js analog is weaker and mostly a robustness/defensive-programming issue rather than a directly exploitable remote DoS from an untrusted party.

### Recommendation
In `packages/apps/shopify-api/lib/clients/common.ts`, guard the `StatusCode.Ok` branch with an explicit check, e.g. `if (response.status === StatusCode.Ok && body?.errors?.graphQLErrors)`, and ensure `body.errors` is validated/typed before use elsewhere in the function (e.g., `body.errors` at line 129 also assumes an object convertible via `JSON.stringify`, which is safe, but the `graphQLErrors` access at line 118/121 is not).

### Proof of Concept
1. An app makes a GraphQL request via `shopify.clients.Graphql`/`GraphqlClient.request()`.
2. The underlying `admin-api-client` returns a `Response` with HTTP status `200` and a JSON body that does not contain a `data` field and does not populate `errors` in the exact `{graphQLErrors, message, response}` shape expected (this can happen if the fetch/network layer or a caching proxy alters/truncates the body while preserving the 200 status).
3. `GraphqlClient.request()` sees `response.errors` truthy (per `processJSONResponse`'s `!data` fallback) and calls `throwFailedRequest(response, ..., fetchResponse)`. [2](#0-1) 
4. Because `fetchResponse.status === 200`, `throwFailedRequest` evaluates `body.errors.graphQLErrors`; if `body.errors` was set to a plain "no data or errors" descriptor object rather than one always containing `graphQLErrors`, further malformed shapes (e.g., if `body.errors` were ever `undefined` through an alternate calling path) would throw a raw `TypeError` rather than the intended typed Shopify error, crashing the request context. [5](#0-4) 

Note: I was unable to fully verify all call sites (`rest/client.ts`, `storefront/client.ts`, OAuth flows) within the remaining budget to confirm whether any of them can pass a `body` with a genuinely `undefined`/`null` `.errors` alongside `response.status === 200`; this would need further tracing of `@shopify/admin-api-client`'s internal `processJSONResponse` guarantees to fully confirm reachability of the crash versus it being purely theoretical/defensive.

```typescript
export function throwFailedRequest(
  body: any,
  atMaxRetries: boolean,
  response?: Response,
): never {
  if (typeof response === 'undefined') {
    const message = body?.errors?.message ?? '';
    throw new ShopifyErrors.HttpRequestError(
      `Http request error, no response available: ${message}`,
    );
  }

  const responseHeaders = canonicalizeHeaders(
    Object.fromEntries(response.headers.entries() ?? []),
  );

  if (response.status === StatusCode.Ok && body.errors.graphQLErrors) {
    throw new ShopifyErrors.GraphqlQueryError({
      message:
        body.errors.graphQLErrors?.[0].message ?? 'GraphQL operation failed',
      response: response as Record<string, any>,
      headers: responseHeaders,
      body: body as Record<string, any>,
    });
  }
```

```typescript
async function processJSONResponse<TData = any>(
  response: Response,
): Promise<ClientResponse<TData>> {
  const {errors, data, extensions} = await response.json<any>();

  return {
    ...getKeyValueIfValid('data', data),
    ...getKeyValueIfValid('extensions', extensions),
    headers: response.headers,

    ...(errors || !data
      ? {
          errors: {
            networkStatusCode: response.status,
            message: formatErrorMessage(
              errors ? GQL_API_ERROR : NO_DATA_OR_ERRORS_ERROR,
            ),
            ...getKeyValueIfValid('graphQLErrors', errors),
            response,
          },
        }
      : {}),
  };
```
