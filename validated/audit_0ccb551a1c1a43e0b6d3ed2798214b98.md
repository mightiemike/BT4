### Title
Unbounded exchange quant in legacy bancor formula allows negative/overflowed virtual supply and non-deterministic `Math.pow` output - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The reported AMM bug is a class of "unbounded coefficient fed into an exponential/log function" issue: a governance-settable smoothing factor was checked only for a lower bound (`> 0`) but not an upper bound (`<= 1 WAD`), so `1 - alpha` could become zero or negative before being passed into a natural-log function. The nearest reachable, unprivileged-user analog in java-tron is the legacy (non-hardened) bancor-style exchange formula in `ExchangeProcessor`, reachable via `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, where a user-controlled quantity is used as the base/exponent input of `Math.pow` without full bound enforcement on the internal virtual `supply` variable, and the result is cast from `double` to `long` without any sanity check.

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  dispatches to either the legacy `ExchangeProcessor` (default, when `ALLOW_HARDEN_EXCHANGE_CALCULATION` is not enacted) or `SafeExchangeProcessor` (hardened path), based on `hardenedCalc`.

In the legacy path, `ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute: [2](#0-1) 

`exchangeFromSupply` unconditionally does `supply -= supplyQuant;` with no check that `supplyQuant <= supply`, and then computes `Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, useStrictMath)`. If `supply` becomes zero or negative (division by a shrunk/negative `supply`), the base of `pow` can become negative, zero, or otherwise produce `NaN`/`Infinity`, exactly analogous to `emaAlpha2Ln` receiving an out-of-range/negative input in the reported bug because the upstream value (`emaAlpha`) was not upper-bounded.

The actuators that invoke this path (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) validate `tokenQuant` only against `exchangeBalanceLimit` for the balance side of the *real* token pool [3](#0-2) , but they do not validate the derived intermediate "virtual supply" value used internally by `ExchangeProcessor`, which is a separate internal state (`supply = 1_000_000_000_000_000_000L` reset per call) not exposed to or checked by the validate step. This mirrors the AMM report precisely: an internal derived quantity used as an exponent/log-style input is unguarded even though the "surface" input passed a check.

The output of the unguarded `Math.pow` call is cast directly to `long` with no `NaN`/`Infinity`/negative sanity check: [4](#0-3) 
`(long) issuedSupply` and `(long) exchangeBalance` will silently produce `0`, `Long.MIN_VALUE`, or `Long.MAX_VALUE` when the underlying `double` is `NaN`/`Infinity`, which then flows straight into `exchangeCapsule.setBalance(...)` in the actuator's `execute()` [5](#0-4)  without further bound checks (unlike the hardened path, which explicitly rejects negative resulting balances: `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) { throw ... }` [6](#0-5) ).

### Impact Explanation
If a legacy (non-hardened) exchange's internal virtual `supply` accounting is driven to an edge state, `Math.pow` on a floating-point base near/at 0 or negative can yield `NaN`/`Infinity`, which truncates to a garbage `long` (including negative values) that is written straight into the on-chain `ExchangeCapsule` balances via `setBalance` with no post-hoc bound check. This can corrupt AMM-style exchange-pool accounting (state divergence / incorrect balances), and because non-hardened `Math` calls are also flagged elsewhere in the codebase as being cross-platform non-deterministic (see the doc comment on `Maths` recommending `StrictMathWrapper` "for cross-platform consistency" [7](#0-6) ), divergent results across nodes running different JIT/JVM implementations could also cause a consensus-relevant state mismatch.

### Likelihood Explanation
This is difficult to trigger under the current explicit validation, because `tokenQuant` is bounded per-call by `exchangeBalanceLimit` and each `ExchangeProcessor` instance resets its `supply` to a large constant (`10^18`) per transaction, which in practice keeps `supplyQuant/newBalance` small. I was not able to fully verify, within the available context, a concrete transaction sequence (e.g., repeated `ExchangeTransactionActuator` calls draining `secondTokenBalance` toward zero, or combining with `ExchangeWithdrawActuator`/`ExchangeInjectActuator` in a single block) that forces `supply` negative or `newBalance` in `exchangeToSupply` toward zero to trigger the bad `Math.pow` input. This is the same root-cause pattern (unbounded value feeding an exponential/log function without upper/lower guard, with unguarded cast of the result), but I could not conclusively demonstrate reachability of the exact malformed state with the tools available in this session.

### Recommendation
Enforce the same pattern already used in `SafeExchangeProcessor`/hardened calculation path for all exchange calculations (not just when `ALLOW_HARDEN_EXCHANGE_CALCULATION` is active): validate that intermediate values fed into `Math.pow`/`StrictMathWrapper.pow` remain within safe bounds, reject `NaN`/`Infinity`/negative results explicitly instead of silently truncating via `(long)` cast, and reject resulting balances that go negative. Longer-term, deprecate/retire the legacy `ExchangeProcessor` double-arithmetic path entirely in favor of the `SafeExchangeProcessor` BigDecimal-based implementation, as recommended generically for "safe operating ranges" enforcement.

### Proof of Concept
Not conclusively demonstrated. A full PoC would require constructing a sequence of `ExchangeCreateActuator` → `ExchangeInjectActuator`/`ExchangeWithdrawActuator` → `ExchangeTransactionActuator` calls (with `ALLOW_HARDEN_EXCHANGE_CALCULATION` disabled) that drives the token-pool balances and/or the per-call virtual `supply` in `ExchangeProcessor` toward a boundary where `1.0 + quant/balance` or `1.0 + supplyQuant/supply` becomes zero or negative, and observing whether `Math.pow`'s `NaN`/`Infinity` output silently corrupts `ExchangeCapsule` balances after the unchecked `(long)` cast. This requires runtime/test-harness verification beyond static code review.

    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
