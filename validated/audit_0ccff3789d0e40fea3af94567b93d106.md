### Title
Unbounded, unpruned growth of `LatestValidatorVotesForFrozenBanks` maps via cheap unstaked vote-account churn - (File: core/src/consensus/latest_validator_votes_for_frozen_banks.rs)

### Finding Description
`check_add_vote` inserts a new `HashMap<Pubkey, (Slot, Vec<Hash>)>` entry for every previously-unseen `vote_pubkey` that casts a frozen vote, via the `Entry::Vacant` branch [1](#0-0) . There is no stake check, no size cap, and no removal path anywhere in this struct — the only acknowledgement of this gap is the code's own TODO comment: `// TODO: Clean outdated/unstaked pubkeys from this list.` [2](#0-1) . Entries are consumed for fork-choice bookkeeping but are never deleted when the corresponding vote account is later closed on-chain; `take_votes_dirty_set` only drains the separate `fork_choice_dirty_set` (filtered by root slot), leaving `max_gossip_frozen_votes` / `max_replay_frozen_votes` permanently populated [3](#0-2) .

An unprivileged attacker can create a fresh vote account (a new `Pubkey`, cheap/refundable rent), submit one vote transaction that gets replayed on a frozen bank (triggering `check_add_vote` via `ReplayStage`/`ClusterInfoVoteListener`), then close the vote account and recover the rent, and repeat. Each iteration permanently adds one entry to the map regardless of whether the vote account remains live or the validator has any stake — this repo does not filter on stake before calling `check_add_vote` at this layer.

### Impact Explanation
This is real but bounded by economics: each iteration still costs the attacker transaction fees for `CreateAccount`/`InitializeAccount`/vote transaction/`CloseAccount` (non-refundable), and each vote transaction must be included in a real block by some leader, which is rate-limited by normal transaction throughput and fee-market pressure — it is not literally free per Pubkey. However, the per-account rent is fully recoverable, and there is no cap or pruning logic tied to account lifecycle, stake, or map size, so the in-memory map does grow monotonically and unboundedly relative to the number of vote transactions ever observed, independent of currently-live stake or accounts. This matches a disproportionate/unbounded memory growth resource-exhaustion class of issue rather than a critical consensus-safety bug, since `max_gossip_frozen_votes`/`max_replay_frozen_votes` only affect fork-choice heuristics, not balances, hashes, or capitalization.

### Likelihood Explanation
Feasible for any user with enough SOL to pay ongoing transaction fees and rent float, and fully repeatable — no special privileges, staked-node control, or leader control needed. The rate is bounded by however fast the attacker can get vote transactions replayed into frozen banks (limited by cluster block production/slot time and normal fee-paying transaction throughput), so it is not instantaneous but is unbounded over time.

### Recommendation
Implement the TODO: periodically prune entries for pubkeys that are no longer current vote accounts of any staked (or any existing) validator, e.g., during root advancement (similar to `progress_with_new_root_bank`/`prune_stale_slots` patterns already used in `cluster_info_vote_listener.rs`), or bound map size / require minimum stake before inserting into `max_gossip_frozen_votes` / `max_replay_frozen_votes`.

### Proof of Concept
Integration/unit test plan (extending the existing test module in `latest_validator_votes_for_frozen_banks.rs`):
```rust
#[test]
fn test_stale_entries_accumulate_after_account_closure() {
    let mut tracker = LatestValidatorVotesForFrozenBanks::default();
    let n = 1000;
    for i in 0..n {
        let vote_pubkey = Pubkey::new_unique(); // simulates a freshly created, later-closed vote account
        let (added, _) = tracker.check_add_vote(
            vote_pubkey, i as u64, Some(Hash::new_unique()), /*is_replay_vote=*/true,
        );
        assert!(added);
        // In a full integration test: submit CreateAccount+InitializeVote, cast one vote via
        // ReplayStage-driven path, then CloseAccount to reclaim rent, before next iteration.
    }
    // No pruning tied to on-chain account closure exists.
    assert_eq!(tracker.max_replay_frozen_votes().len(), n);
}
```
This demonstrates map size grows 1:1 with the number of one-shot vote pubkeys regardless of whether the originating accounts are still live on-chain, confirming stale-entry accumulation independent of account lifecycle.
