### Title
Third-party `TransferToGasKey` inflates gas key balance above `MAX_BALANCE_TO_BURN`, blocking `DeleteKey` and `DeleteAccount` for the key owner — (`runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/actions.rs`)

---

### Summary

Any unprivileged account can send a `TransferToGasKey` action targeting another account's gas key. Because `action_delete_key` and `action_delete_account` gate deletion on the gas key balance being ≤ `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR), a third party can push that balance above the threshold and cause every plain `DeleteKey` or `DeleteAccount` receipt from the victim to fail with `GasKeyBalanceTooHigh`. The victim must know to compose a `WithdrawFromGasKey` + `DeleteKey` in the same receipt to escape; a plain deletion is permanently broken as long as the attacker keeps re-funding.

---

### Finding Description

**Unrestricted third-party funding.** `TransferToGasKeyAction` carries only `{ public_key, deposit }` and is executed against the receipt's `receiver_id`. No check enforces that the signer or predecessor is the key owner. Any account can therefore send a transaction to `alice.near` with `TransferToGasKey { public_key: alice_gas_key_pk, deposit: 1.1 NEAR }` and credit Alice's gas key balance. [1](#0-0) 

**Balance-gated deletion.** `action_delete_key` calls `delete_gas_key`, which checks:

```rust
if gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN {
    result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh { ... });
    return Ok(());
}
``` [2](#0-1) 

`MAX_BALANCE_TO_BURN` is 1 NEAR. [3](#0-2) 

`action_delete_account` calls `compute_gas_key_balance_sum` (the aggregate across all gas keys) and applies the same threshold: [4](#0-3) 

`compute_gas_key_balance_sum` iterates every gas key trie entry for the account and sums their balances: [5](#0-4) 

**Attack path.**

1. Alice creates a gas key (`AddKey` with `GasKeyFullAccess`).
2. Bob sends `TransferToGasKey { public_key: alice_gas_key_pk, deposit: 1.1 NEAR }` to `alice.near`. This succeeds unconditionally.
3. Alice submits `DeleteKey { public_key: alice_gas_key_pk }`. The runtime reads `gas_key_info.balance = 1.1 NEAR > 1 NEAR` and returns `GasKeyBalanceTooHigh`. The receipt fails.
4. Alice submits `DeleteAccount { beneficiary_id: ... }`. `compute_gas_key_balance_sum` returns 1.1 NEAR > 1 NEAR; same failure.
5. Bob can repeat step 2 whenever Alice drains the key, keeping the balance above the threshold indefinitely at a cost of >1 NEAR per cycle (the NEAR is burned as gas when Alice uses the key).

---

### Impact Explanation

The invariant broken is: **an account owner must always be able to delete their own keys and account**. A third party with no special privilege can violate this invariant by funding a gas key above the burn threshold. Every plain `DeleteKey` or `DeleteAccount` receipt from the victim reverts with `GasKeyBalanceTooHigh`. The victim's account lifecycle operations are disrupted.

A partial escape exists: Alice can compose `[WithdrawFromGasKey { amount: full_balance }, DeleteKey]` in a single receipt, which atomically drains then deletes. However:
- This requires knowledge of the workaround.
- Bob can re-fund between separate transactions (though not within a single atomic receipt).
- For `DeleteAccount` with multiple gas keys, Alice must include one `WithdrawFromGasKey` per key, all in the same receipt.

The impact maps to **contract execution flow breakage** and **non-network-level denial of service fixable without a hardfork** (the fix is to remove or restructure the `MAX_BALANCE_TO_BURN` gate, or to allow atomic drain-and-delete without requiring the workaround).

---

### Likelihood Explanation

- The attacker needs only a funded account and knowledge of the victim's gas key public key (publicly visible on-chain via `view_access_key_list`).
- The attack costs the attacker >1 NEAR per cycle (the funded balance is eventually burned as gas by the victim or lost to the attacker).
- Gas keys are a new SPICE feature; users and tooling are unlikely to know the `WithdrawFromGasKey` workaround.
- Likelihood is **low-medium**: the attack is costly but fully reachable by any unprivileged account.

---

### Recommendation

1. **Remove the `MAX_BALANCE_TO_BURN` gate from `DeleteKey` and `DeleteAccount`**, and instead burn the full gas key balance unconditionally on deletion (already done for balances ≤ 1 NEAR; extend to all balances). The cap was introduced to limit accidental burns, but it creates this griefing surface.
2. **Alternatively**, before checking the threshold in `action_delete_key`, automatically drain the gas key balance to the account balance (equivalent to an implicit `WithdrawFromGasKey`), so the deletion always succeeds regardless of third-party funding.
3. **If the cap must be retained**, restrict `TransferToGasKey` so that only the key owner's account (i.e., `predecessor_id == receiver_id`) can fund a gas key, eliminating the third-party funding vector.

---

### Proof of Concept

```
// Setup
alice creates gas key K with GasKeyFullAccess(num_nonces=3)

// Attack
bob sends tx:
  signer_id = bob
  receiver_id = alice
  actions = [TransferToGasKey { public_key: K, deposit: 1_100_000_000_000_000_000_000_000 }]  // 1.1 NEAR
// Succeeds: alice's gas key K now has balance 1.1 NEAR

// Victim's operation fails
alice sends tx:
  signer_id = alice
  receiver_id = alice
  actions = [DeleteKey { public_key: K }]
// Fails: GasKeyBalanceTooHigh { balance: 1.1 NEAR, max: 1 NEAR }

// Bob repeats TransferToGasKey whenever alice drains the key via transactions
// alice's DeleteKey is blocked indefinitely at >1 NEAR cost per cycle to bob
```

```rust
pub fn compute_gas_key_balance_sum(
    state_update: &TrieUpdate,
    account_id: &AccountId,
) -> Result<Balance, StorageError> {
    let mut total = Balance::ZERO;
    let lock = state_update.trie().lock_for_iter();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if nonce_index.is_some() {
            continue;
        }
        if let Some(balance) = get_access_key_by_handle(state_update, account_id, &key_handle)?
            .as_ref()
            .and_then(|access_key| access_key.gas_key_info())
            .map(|gas_key_info| gas_key_info.balance)
        {
            total = total.checked_add(balance).ok_or_else(|| {
                StorageError::StorageInconsistentState("gas key balance overflow".to_string())
            })?;
        }
    }
    Ok(total)
}
