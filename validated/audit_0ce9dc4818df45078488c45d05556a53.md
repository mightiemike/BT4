### Title
Unbounded Gzip Decompression in `decompress_program` Enables CPU/Memory Exhaustion DoS - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The RPC helper `decompress_program` decodes a base64 payload and decompresses it via `GzDecoder::read_to_end` with no size or time limit, unlike the analogous storage/gateway decompression paths in this codebase which enforce explicit size caps.

### Finding Description
`decompress_program` in [1](#0-0)  reads an attacker-supplied base64 string, decompresses it with `flate2::read::GzDecoder`, and calls `read_to_end` on an unbounded `Vec<u8>` buffer with a `// TODO(dan): add time and size limits.` comment acknowledging the missing safeguard. This is structurally analogous to the exiv2 `Jp2Image::readMetadata()` bug class: attacker-controlled compressed input drives an unbounded decode loop with no resource cap, producing high CPU/memory consumption.

By contrast, every other decompression path in this codebase enforces explicit limits:
- `apollo_storage`'s `decompress` bounds output via `zstd::bulk::decompress(data, MAX_DECOMPRESSED_SIZE)` [2](#0-1) .
- `starknet_api::compression_utils::decompress_with_size_limit` uses `.take(max_size + 1)` before `read_to_end` and errors if the limit is exceeded [3](#0-2) .

`decompress_program` skips this pattern entirely, allowing a highly-compressed "gzip bomb" (a small base64 payload that expands to gigabytes) to consume unbounded memory and CPU time on the node handling the RPC request.

### Impact Explanation
An RPC node processing a call that reaches `decompress_program` (used for decompressing a Cairo `Program` in trace/execution-related RPC methods, confirmed referenced from `execution_test.rs`) can be driven into unbounded memory allocation and CPU consumption by a single crafted request. Depending on where this function is exposed, this can degrade or crash the serving node, impacting availability of RPC/execution services — a resource-exhaustion class DoS.

### Likelihood Explanation
Low complexity: constructing a gzip-bomb payload (small compressed size, huge decompressed size) is trivial and requires no privileges beyond calling the affected RPC method. However, I was not able to fully confirm within the available tool budget which RPC method(s) call `decompress_program` and whether that endpoint is reachable by an untrusted network peer versus only local trusted callers/tests — the only call sites found were in `execution_test.rs` and `api/mod.rs` itself. Given the rules require excluding "no-impact" / test-only paths, and that RPC servers are often reachable by external users, this should be treated as at least a plausible resource-exhaustion issue, but confirmation of the exact production call path (and whether it maps to the "gateway validation / mempool / execution" reachable-by-transaction-sender scope required by the rules) is uncertain and should be verified with full codebase access.

### Recommendation
Apply the same pattern already used elsewhere in the codebase: wrap the `GzDecoder` read in a `.take(max_size)` bound (as in `starknet_api::compression_utils::decompress_with_size_limit`) and return an error if the decompressed size exceeds a configured maximum, removing the outstanding `TODO(dan)` comment by implementing it.

### Proof of Concept
Not independently reproducible with the tools available (no execution/runtime access). Conceptually: craft a gzip payload that decompresses to several GB from a KB-sized compressed input (a "zip bomb"), base64-encode it, and submit it to the RPC method that invokes `decompress_program`; observe unbounded memory growth and CPU usage during decompression, since no size or time limit is enforced in that function.

**Note on confidence**: I could not conclusively trace which specific RPC method (and whether it is externally reachable without authentication/trust assumptions) calls `decompress_program` beyond its definition and test usage, due to tool-call limits reached during this investigation. This should be verified with a full Devin session that can trace call sites and exposure surface.

fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
