## Analysis

I traced this to `liquidate-multi` in `market.clar` / `v0-4-market.clar`, which wraps a `map` over the internal `liquidate` calls and *always* returns `(ok ...)` regardless of whether individual liquidations succeeded: [1](#0-0) 

Within `liquidate` itself, before the bad-debt socialization step, the function has already:
1. Repaid debt to the vault: `(try! (vault-system-repay ...))`
2. Removed the borrower's scaled debt: `debt-remove-scaled`
3. Removed and transferred the borrower's collateral to the liquidator: `collateral-remove` [2](#0-1) 

Only *after* these irreversible transfers does the code attempt bad-debt socialization via a `fold` over `socialize-debt-asset`, which can fail partway through (each iteration does an `unwrap!`, and once one fails, later iterations are skipped via the early-return guard): [3](#0-2) [4](#0-3) 

If socialization fails, `liquidate` does `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)`, which returns an `err` **from that one `liquidate` call**. When `liquidate` is invoked directly (not via `liquidate-multi`), this propagates to the top-level transaction and everything reverts — safe.

However, `liquidate-multi` invokes `liquidate` through `call-liquidate` inside a plain `map`, not `try!`: [5](#0-4) 

`map` collects each `(response ...)` result (ok or err) into a list without propagating failure, and `liquidate-multi` always wraps the final list in `(ok ...)`. This means the *outer* transaction is never marked failed, so Clarity commits all state mutations that occurred during evaluation — including the already-executed `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` for the position whose bad-debt socialization subsequently failed. The failure is absorbed into an `err` element inside the returned list, but the collateral has already left the protocol and the borrower's debt records are now inconsistent (partially removed debt, but the bad-debt write-down that was supposed to socialize the shortfall across LPs did not complete).

This is exactly the "fold/map that absorbs failure" pattern called out in scope: a batch entry point where a deep failure inside one sub-operation doesn't roll back the earlier steps of that same sub-operation, because the enclosing function structurally can't fail.

### Title
`liquidate-multi` commits partial liquidation state (collateral seizure without completed bad-debt socialization) when a batched position's socialization fails - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate-multi` calls `liquidate` for each position via `map`, then unconditionally wraps the result list in `(ok ...)`. If bad-debt socialization inside one position's `liquidate` call fails after collateral has already been seized and debt already partially removed, the overall transaction still succeeds, permanently committing the inconsistent partial state instead of reverting it.

### Finding Description
`liquidate` performs collateral removal/transfer and scaled-debt removal (`vault-system-repay`, `debt-remove-scaled`, `collateral-remove`) *before* attempting bad-debt socialization for any remaining unsecured debt [6](#0-5) . Socialization uses `fold socialize-debt-asset`, whose accumulator pattern silently skips remaining iterations once one fails [4](#0-3) , and the enclosing `liquidate` propagates that as `ERR-BAD-DEBT-SOCIALIZATION-FAILED` via `asserts!` [7](#0-6) .

When `liquidate` is called standalone this `err` return reverts the entire transaction (Clarity's standard top-level rollback). But `liquidate-multi` invokes `liquidate` through `call-liquidate` inside a `map`, and the final expression is `(ok (map call-liquidate positions))` [8](#0-7) . Since the top-level public function always returns `ok`, Clarity commits the transaction, including all state mutations performed inside the failed sub-call before its internal `err` was produced — i.e., the collateral transfer to the liquidator and the scaled-debt removal for that borrower's debt asset already happened and are not undone, even though the corresponding bad-debt socialization (which is supposed to make the LPs whole for the unsecured remainder) never completed.

### Impact Explanation
This can leave the protocol with debt records removed/understated relative to actual outstanding vault liabilities while the corresponding collateral has already been paid out to the liquidator, without the compensating bad-debt write-down (`socialize-debt`) being applied to the vault's index. This is an accounting mismatch between vault liabilities and pledged collateral, i.e., unaccounted bad debt sitting in the system — a protocol insolvency vector, since vault depositors' claims are no longer fully backed by tracked collateral/debt state.

### Likelihood Explanation
This requires a position that ends with no remaining collateral and multiple debt assets where socialization of a later debt entry fails (e.g., `vault-socialize-debt` returns an error for one asset while an earlier one already succeeded) — a state reachable through normal batched liquidation of deeply underwater multi-asset positions, not requiring privileged access. It is more likely to be triggered incidentally during real liquidation waves (e.g., partial vault state issues, cap/pause interactions) than as a deliberately engineered attack, but a liquidator who understands this can also intentionally structure batched liquidate-multi calls with malformed follow-on debt assets to leave the protocol under-socialized while walking away with seized collateral.

### Recommendation
`liquidate-multi` should not silently swallow failures from `liquidate`. Options: (a) use `try!`/proper propagation so any position failing mid-way reverts the whole batch (losing the "partial batch success" feature but restoring atomicity for each position), or (b) restructure `liquidate` so all mutating vault/market-vault calls for a given position happen only after bad-debt socialization is guaranteed to succeed (compute-then-commit ordering), so a socialization failure never occurs after collateral has already left the contract.

### Proof of Concept
1. Borrower has a multi-asset debt position (e.g., debt in USDC and USDH) fully collateralized by a single collateral asset that will be entirely seized by this liquidation (`no-collateral-left` becomes true).
2. Liquidator calls `liquidate-multi` with this borrower's position included in the batch.
3. Inside `call-liquidate` → `liquidate`: `vault-system-repay`, `debt-remove-scaled` for the primary debt asset, and `collateral-remove` (sending seized collateral to the liquidator) all execute successfully [2](#0-1) .
4. `no-collateral-left` is true, so bad-debt socialization is attempted over the borrower's remaining debt list via `fold socialize-debt-asset` [9](#0-8) ; the second debt asset's `vault-socialize-debt` or `debt-remove-scaled` call fails (e.g., that vault is paused for `socialize-debt`, or a cap/edge condition triggers an error), causing the fold accumulator to short-circuit with `success: false`.
5. `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` fires inside `liquidate`, returning `err` from that single `liquidate` invocation only.
6. `call-liquidate` returns this `err` element into the `map` result list; `liquidate-multi` still returns `(ok (list ... (err u400021) ...))` [10](#0-9) .
7. The overall transaction succeeds. The liquidator has already received the borrower's collateral and the primary debt entry has been removed from the borrower's obligations, but the second debt asset's socialization never completed — leaving unbacked debt/liability inconsistency in the protocol's books.

**Uncertainty note**: I was not able to fully verify the exact failure conditions under which `vault-socialize-debt` or `debt-remove-scaled` return an `err` inside `socialize-debt-asset` (e.g., specific pause states or cap checks in the vault contracts), since the full body of `socialize-debt` in each vault contract and `debt-remove-scaled` in `v0-market-vault.clar` was not completely inspected in this session. The core control-flow issue — `liquidate-multi` unconditionally returning `ok` over a `map` of potentially-failing sub-liquidations, after those sub-liquidations already performed irreversible collateral/debt mutations — is confirmed directly from the cited source.
