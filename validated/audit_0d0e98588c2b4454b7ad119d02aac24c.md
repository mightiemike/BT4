### Title
Unconditional `mix_out` of index-visible zero-lamport accounts corrupts `calculate_accounts_lt_hash_at_startup_from_index` — ([File: accounts-db/src/accounts_db.rs])

### Summary
The external report's bug class is "a value obtained from an oracle/index is used without validating a precondition that a parallel code path *does* validate, causing a wrong/divergent result." In `sUSDeOracle::getPrice()`, `usdePriceInUsd` was never checked to be non-zero even though correctness required it. The analogous flaw in agave exists in `AccountsDb::calculate_accounts_lt_hash_at_startup_from_index`, where the same "is this account zero-lamport" predicate is applied inconsistently between two loops that must otherwise stay symmetric, producing a corrupted lattice hash.

### Finding Description
`calculate_accounts_lt_hash_at_startup_from_index` computes the accounts lt-hash in two passes:

1. It iterates all accounts-index bins and mixes in the lt-hash of every pubkey's index-visible version, but only if it is **not** zero-lamport: [1](#0-0) 

2. It then iterates every pubkey currently present in the write cache (`accounts_cache.cached_pubkeys()`), looks up the same index-visible version, and unconditionally mixes it **out** (to cancel the contribution from pass 1) before mixing in the fresher cache version: [2](#0-1) 

The `mix_out` call at lines 4703–4709 has no `is_zero_lamport()` guard, unlike the `mix_in` in pass 1 (line 4669: `(!account_info.is_zero_lamport()).then(...)`). If a pubkey's index-visible entry (given `ancestors`) is zero-lamport — which is a normal, reachable state, since `do_flush_slot_cache` will flush a zero-lamport account to storage/index when an older index entry for that pubkey already exists — pass 1 contributes **nothing** for that pubkey (correctly skipped). But pass 2 still computes `lt_hash_account` for that same zero-lamport version and unconditionally `mix_out`s it, subtracting a value that was never added. Because `LtHash::mix_out` is the algebraic inverse of `mix_in`, subtracting a value never mixed in does not cancel to identity; it leaves a spurious residual term in the final accumulator that has nothing to do with the actual account set.

### Impact Explanation
This corrupts the "calculated" accounts lattice hash returned by this function. It is consumed by `Bank::verify_accounts`, which compares it against the `expected_accounts_lt_hash` stored on the bank: [3](#0-2) 

A mismatch causes `verify_accounts` to log `"Verifying accounts failed: accounts lattice hashes do not match"` and return `false`, which is the exact "honest-node snapshot-vs-replay/hash divergence" class this task calls for: an honest node whose accounts state is actually correct fails the lattice-hash consistency check purely due to this calculation bug, not due to any real state corruption. This path is exercised by `run_final_hash_calc` (used by ledger-tool for final hash verification) and by startup/ledger-tool verification flows that call `calculate_accounts_lt_hash_at_startup_from_index` when no precomputed lt-hash is available from index generation.

### Likelihood Explanation
The triggering condition — a pubkey whose most-recent flushed (index) version is zero-lamport while a newer write for the same pubkey still sits in the unflushed write cache — is a normal consequence of the accounts write-cache/flush design (zero-lamport accounts with a pre-existing index entry are stored rather than skipped, per the flush logic), so this is reachable in ordinary validator/ledger-tool operation whenever this startup/verification code path runs, not a contrived edge case.

### Recommendation
Add the same `is_zero_lamport()` guard used in pass 1 to the `mix_out` closure in pass 2, i.e. only call `get_loaded_account`/`mix_out` when `!account_info.is_zero_lamport()`, so that the two passes stay symmetric and only cancel contributions that were actually mixed in.

### Proof of Concept
Conceptual repro (cannot be executed in this environment):
1. Create account `pubkey` in slot 0 with non-zero lamports; root and flush slot 0 (creates an index entry).
2. In slot 1, write `pubkey` with 0 lamports; root and flush slot 1 (per `do_flush_slot_cache`, since an index entry for `pubkey` already exists, the zero-lamport update is stored, making the index-visible version zero-lamport).
3. In slot 2 (not yet flushed, still in the write cache), write `pubkey` again with non-zero lamports; root slot 2 but do not flush.
4. Call `calculate_accounts_lt_hash_at_startup_from_index(&ancestors)` including slot 2.
   - Pass 1 sees the zero-lamport index entry for `pubkey` and correctly contributes nothing.
   - Pass 2 sees `pubkey` in `cached_pubkeys()`, unconditionally computes `lt_hash_account` for the same zero-lamport index entry, and calls `mix_out` on it — subtracting a term never added — before mixing in the slot-2 cache value.
5. The resulting `AccountsLtHash` differs from the hash computed by the incremental (transaction-processing-time) update path, causing `Bank::verify_accounts`/`check_lt_hash` to report a mismatch for a perfectly valid account state. [4](#0-3)
