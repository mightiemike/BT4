### Title
Global panic-to-process-exit hook turns any reachable panic from a single transaction into a full sequencer node crash - (File: `crates/apollo_node/src/main.rs`)

### Summary
The upstream LibreChat bug class is: an unhandled exception thrown while processing a single external request escapes all error-handling and kills the whole server process. This sequencer repo has a structurally identical (and broader) analog: `apollo_node`'s `main()` installs a global panic hook that unconditionally calls `std::process::exit(1)` after *any* panic anywhere in the process, before Rust's normal unwind/`catch_unwind` machinery gets a chance to contain it. Since gateway/mempool/blockifier transaction-processing code runs in the same process and is reachable from a single submitted transaction, any panic triggered by attacker-controlled transaction fields crashes the entire node, not just the failing request.

### Finding Description
`apollo_node`'s entry point installs this hook at startup: [1](#0-0) 

Because a panic hook runs *before* stack unwinding begins, this hook fires even for panics that call sites elsewhere in the codebase are explicitly designed to catch and recover from. For example, the blockifier's concurrent execution worker pool wraps transaction execution in `panic::catch_unwind` specifically so a single bad transaction cannot bring down the whole executor: [2](#0-1) 

That defensive design is defeated by the global hook in `main.rs`: the hook's `std::process::exit(1)` runs regardless of whether the panic will ultimately be caught downstream, so any panic anywhere (gateway HTTP handler, mempool insertion, blockifier fee/gas computation, syscalls) kills the process outright.

The transaction path is rich with `.unwrap()`/`.expect()`/`assert!`/`panic!` on values derived from, or closely tied to, external transaction input, e.g.:
- `GasVector::cost` panics on arithmetic overflow when multiplying/adding gas amounts by prices (fed by transaction `resource_bounds`, i.e. attacker-supplied `max_amount` / `max_price_per_unit`): [3](#0-2) 
called from `crates/blockifier/src/fee/fee_utils.rs`.
- Mempool internal invariants are enforced with panicking `assert!`/`expect()` on the insertion of a just-added transaction, assuming duplicates were already filtered out earlier in the same call chain: [4](#0-3) [5](#0-4) 

Any of these panicking paths, if triggered by a crafted transaction that violates the implicit assumption the `assert!`/`unwrap()` encodes (e.g., an overflow condition, or a race/edge case that produces a duplicate key), does not just fail the one request — it terminates the entire sequencer process via the `main.rs` hook.

### Impact Explanation
This is a Denial of Service on the whole node: a single malicious/malformed transaction submitted to the gateway can kill the entire `apollo_node` binary (which hosts gateway, mempool, and other transaction-processing components), interrupting all in-flight transaction processing and requiring a restart. If the same crafted transaction is broadcast/submitted to multiple sequencer nodes, it can knock out multiple nodes simultaneously, matching the "network unable to confirm new transactions" impact bar. This also nullifies purpose-built resiliency code such as the blockifier worker pool's `catch_unwind`/`AbortIfPanic` design, which was clearly intended to contain panics to a single transaction/thread rather than the whole process.

### Likelihood Explanation
Reaching *some* panic in the transaction-processing pipeline from a single attacker-controlled transaction is plausible given the number of `unwrap()`/`expect()`/`assert!` calls operating on transaction-derived values throughout gateway, mempool, and blockifier code (several examples cited above). I was not able to fully confirm, within the available tool budget, the exact numeric conditions needed to trigger `GasVector::cost`'s overflow panic from externally supplied `resource_bounds` end-to-end (i.e., whether earlier saturating/bounded validation in the stateless/stateful validators prevents the specific multiplication from overflowing before reaching this code path). That specific arithmetic trigger should be treated as an illustrative, not fully verified, example. What is fully verified is the root cause itself: the process-wide exit-on-panic hook in `main.rs`, which converts every panic reachable from a request — however that panic is caused — into a full-node crash.

### Recommendation
- Remove or scope the global panic hook in `crates/apollo_node/src/main.rs` so it does not call `std::process::exit(1)` for panics that occur inside per-request/per-transaction task boundaries (e.g., `tokio::spawn`ed request handlers, mempool `add_tx`, blockifier execution threads that already use `catch_unwind`). Reserve process-exit-on-panic for genuinely unrecoverable panics (e.g., in the top-level supervisory tasks such as `spawn_with_exit_on_panic` in `crates/apollo_infra_utils/src/tasks.rs`, which already implements a scoped version of this pattern).
- Audit gateway/mempool/blockifier code paths reachable from a single transaction and replace `.unwrap()`/`.expect()`/`assert!`/`panic!` on transaction-derived values with `Result`-based error handling, per the project's own documented guideline ("Never panic on data reachable from requests"): [6](#0-5) 
- Specifically verify whether `GasVector::cost` (`crates/starknet_api/src/execution_resources.rs:155-186`) can be reached with attacker-controlled `resource_bounds` values large enough to overflow `u128` before any saturating bound check applies, and if so, convert it to saturating arithmetic consistent with `ValidResourceBounds::max_possible_fee`, which already uses `saturating_mul`/`saturating_add` for the same class of computation (`crates/starknet_api/src/transaction/fields.rs:393-414`).

### Proof of Concept
Not fully constructible with the available evidence — the exact transaction payload needed to trigger `GasVector::cost`'s overflow panic (or another reachable panic site) end-to-end through gateway validation was not confirmed within the tool budget available for this analysis. A full PoC would require tracing `crates/blockifier/src/fee/fee_utils.rs`'s call into `GasVector::cost` and confirming what bounds, if any, the stateless/stateful transaction validators (`crates/apollo_gateway/src/stateless_transaction_validator.rs`, `stateful_transaction_validator.rs`) place on `resource_bounds.max_amount` / `max_price_per_unit` before that computation runs. Recommend a Devin session with full repo access to construct and test a concrete transaction payload against the `add_tx`/`add_rpc_tx` HTTP endpoints in `crates/apollo_http_server/src/http_server.rs`.

    /// Runs a single worker executor.
    fn _run_executor(&self, worker_executor: &WorkerExecutor<S>) {
        if self.a_thread_panicked.load(Ordering::Acquire) {
            panic!("Another thread panicked. Aborting.");
        }

        // Making sure that the program will abort if a panic occurred while halting
        // the scheduler.
        let abort_guard = AbortIfPanic;
        // If a panic is not handled or the handling logic itself panics, then we
        // abort the program.
        let res = panic::catch_unwind(panic::AssertUnwindSafe(|| {
            worker_executor.run();
        }));
        if let Err(err) = res {
            // First, set the panic flag. This must be done before halting the scheduler.
            self.a_thread_panicked.store(true, Ordering::Release);

            // If the program panics here, the abort guard will exit the program.
            // In this case, no panic message will be logged. Add the cargo flag
            // --nocapture to log the panic message.

            worker_executor.scheduler.halt();
            abort_guard.release();
            panic::resume_unwind(err);
        }

### Never panic on data reachable from requests
- Code reachable from HTTP handlers or external input must never use `.unwrap()`, `.expect()`, or unchecked indexing on values derived from that input
- Reserve panics for compile-time invariants where failure is a programmer bug, not a runtime possibility
- Return `Result` with a descriptive error variant, or use saturating/capping alternatives
