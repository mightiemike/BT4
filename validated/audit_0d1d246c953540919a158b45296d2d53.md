### Title
Zero-cost order-spam DoS of TRC10 Market trading via `MAX_MATCH_NUM` cap when `MarketSellFee` is set to 0 - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
Similar to the Beedle `borrowerFee = 0` DoS, java-tron's TRC10 order-book market (`MarketSellAssetActuator`) charges an on-chain, committee-configurable fee (`dynamicStore.getMarketSellFee()`) for creating an order. When this fee is set to `0` (a plausible protocol-encouragement setting, exactly as in the analog report), an attacker can cheaply flood the order book of a given token pair with many tiny maker orders at successive price points. Any subsequent legitimate taker order that needs to match against more than `MAX_MATCH_NUM = 20` price levels will revert with `"Too many matches. MAX_MATCH_NUM = 20"`, permanently blocking normal trading on that pair at near-zero cost to the attacker (only network resource cost, no protocol fee).

### Finding Description
`MarketSellAssetActuator.execute()` charges `fee = calcFee()` which equals `dynamicStore.getMarketSellFee()`: [1](#0-0) 

This fee is deducted from the account balance and burned/sent to the blackhole address before the order is created and matched: [2](#0-1) 

The matching engine (`matchOrder`) walks maker price levels and orders one by one, incrementing `matchOrderCount`, and hard-reverts the whole transaction once more than `MAX_MATCH_NUM` maker orders/price levels are consumed in a single taker transaction: [3](#0-2) 

```java
private static int MAX_MATCH_NUM = 20;
``` [4](#0-3) 

If `MarketSellFee` is set to `0` by governance (the exact "encourage adoption" scenario described in the analog report), an attacker can place many small-quantity sell orders across many distinct price points on a given `(sellToken, buyToken)` pair for free (aside from bandwidth). Because a single account can hold up to `MAX_ACTIVE_ORDER_NUM = 100` open orders, and the matcher throws once it must traverse more than 20 maker price levels to fill a taker order, an attacker can deliberately fragment liquidity across >20 distinct price levels. Any subsequent legitimate taker who tries to sell into this pair with an order that would need to walk through those >20 levels will have their transaction fail with `ContractExeException`/`"Too many matches"`, exactly mirroring the reported bug class: a free-to-execute action (feeless order creation) that produces a state (order book / pool composition) which deterministically blocks a core financial primitive (trading) for other unprivileged users.

Unlike the Beedle case where the DoS is a full liquidity drain, here the mechanism is a "matching complexity" DoS enabled by the same root cause: the protocol fee that would normally make repeated order placement/cancellation costly is reduced to zero, so the attack becomes essentially free and repeatable indefinitely (the attacker can keep replenishing fragmented orders after each is consumed or expired).

### Impact Explanation
This blocks the TRC10 decentralized exchange/market functionality — one of java-tron's core actuators — for a targeted token pair, denying legitimate users, at negligible attacker cost, when governance sets `MarketSellFee` to `0`. This matches an availability/DoS impact on a public financial primitive, analogous to blocking "borrow" in the reference report.

### Likelihood Explanation
Likelihood is contingent on the committee actually setting `MarketSellFee` to `0` via governance proposal — a plausible, legitimate incentive-alignment decision (as explicitly discussed in the original report as a realistic scenario), not a compromise of privileged roles. Once that condition holds, the exploit itself requires no privileged access and is executable by any account with minimal token/TRX holdings, making the attack itself trivial and repeatable — bounded only by `MAX_ACTIVE_ORDER_NUM = 100` per account and gas/bandwidth cost, which is proportionally very low compared to the value of the market disrupted.

### Recommendation
- Enforce a non-zero minimum bound on `MarketSellFee` (or introduce a small fixed order-placement/cancellation cost independent of the fee parameter) so spamming the order book with many price levels remains economically costly regardless of governance fee settings.
- Alternatively/additionally, bound the number of *distinct price levels* an account may occupy per pair (not just total open orders), and/or allow a taker to specify a max-match limit with partial fill + graceful continuation instead of a hard revert once `MAX_MATCH_NUM` is exceeded, so legitimate takers aren't fully blocked by adversarial order-book fragmentation.

### Proof of Concept
1. Governance sets `MarketSellFee = 0` via proposal (as referenced by `dynamicStore.getMarketSellFee()` used in `calcFee()`). [1](#0-0) 
2. Attacker submits >20 `MarketSellAssetContract` orders for pair `(TokenA -> TokenB)`, each with a distinct price and minimal quantity, up to the `MAX_ACTIVE_ORDER_NUM = 100` cap, costing effectively nothing since `calcFee()` returns 0. [5](#0-4) 
3. A legitimate user submits a normal-size sell order for `TokenB -> TokenA` that would need to traverse the fragmented maker book.
4. `matchOrder()` increments `matchOrderCount` while consuming each attacker maker order and price level; once it exceeds `MAX_MATCH_NUM = 20`, it throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")`, which propagates out of `execute()` as a `ContractExeException`, failing the legitimate user's transaction. [6](#0-5) 
5. Attacker repeats this cheaply/perpetually (re-injecting fragmented orders as they get consumed or expire), permanently denying normal trading on that pair.
