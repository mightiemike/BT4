### Title
Full TVM `unDelegateResource` leaves an empty-value index entry instead of deleting it, corrupting `getV2Index` results - (`actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
`UnDelegateResourceProcessor.execute` clears a fully-unwound V2 delegation index by writing `new DelegatedResourceAccountIndexCapsule(new byte[0])` through `repo.updateDelegatedResourceAccountIndex`, rather than deleting the key as `DelegatedResourceAccountIndexStore.unDelegateV2` does for the same operation reached via the classic actuator path. Because `getV2Index` is served by `getWithPrefix`/`prefixQuery` rather than the single-key `get()` (which explicitly nulls out empty values), the leftover empty-valued key is still enumerated and decoded into a phantom `ByteString.copyFrom(new byte[0])` account entry.

### Finding Description
In `UnDelegateResourceProcessor.execute`, when a delegation's `frozenBalanceForBandwidth` and `frozenBalanceForEnergy` both reach zero, the code writes empty capsules for the from/to index keys instead of deleting them: [1](#0-0) 

By contrast, the store-level equivalent used elsewhere explicitly deletes both keys: [2](#0-1) 

The `get()` method used for direct lookups masks this divergence by treating an empty stored value as `null`: [3](#0-2) 

However, `getV2Index` (the method backing the wallet/RPC `GetDelegatedResourceAccountIndexV2`-style query) does not go through `get()`. It uses `getWithPrefix`, which performs a prefix scan (`prefixQuery`) over the raw key space and decodes every value it finds into a `DelegatedResourceAccountIndexCapsule`, sorted by timestamp: [4](#0-3) 

An empty byte array is a valid (default-instance) protobuf payload, so `DelegatedResourceAccountIndexCapsule(new byte[0])` decodes without error and yields `getAccount() == ByteString.EMPTY`. Since the key itself (`V2_FROM_PREFIX/V2_TO_PREFIX + owner/receiver + receiver/owner`) is never removed from the underlying revoking DB by the TVM path, a prefix scan over `owner`'s (or `receiver`'s) namespace will surface this stale key/value pair as a legitimate-looking entry with an empty account, polluting `fromAccountsList`/`toAccountsList`.

This is reachable by any unprivileged account: deploy or call a contract that invokes the `unDelegateResource` precompile (`Program.unDelegateResource` → `UnDelegateResourceProcessor.execute`) to fully unwind a delegation to a given receiver for both bandwidth and energy. No signature/permission bypass, fork gate, or privileged role is involved — this is normal precompile usage available to any TVM caller who holds an active delegation.

### Impact Explanation
This is a state-representation/query-correctness bug, not a fund-theft or consensus-divergence bug: the underlying `frozenBalanceForBandwidth`/`frozenBalanceForEnergy` accounting fields on `DelegatedResourceCapsule` and `AccountCapsule` are updated correctly; only the auxiliary `DelegatedResourceAccountIndexStore` index used for `getV2Index` diverges from actual delegation state. Concrete impact is corruption of the read-side index: `getV2Index(owner)`/`getV2Index(receiver)` can return phantom entries containing an empty account (`ByteString.copyFrom(new byte[0])`) mixed with legitimate delegation partners, which is relied upon by wallet UIs and exchange tooling that enumerate delegation relationships via this RPC. This maps to a data-integrity/state-divergence class issue rather than a direct loss-of-funds or consensus-halt issue.

### Likelihood Explanation
Trivially reproducible by any funded account: delegate a small amount of TRX-derived bandwidth/energy to any receiver via a contract call to the delegate precompile, then fully undelegate it (bringing both frozen balances to zero) via the undelegate precompile. Cost is limited to normal transaction fees/energy for two precompile calls; no special preconditions beyond having an active delegation. The stale empty-value key persists indefinitely unless a later delegation reuses the exact same `(owner, receiver)` key (which overwrites and "heals" that specific entry) — so the corruption is most durable/observable when the attacker undelegates fully from one receiver and does not redelegate to that exact same receiver again, while other delegations under the same owner/receiver prefix remain, making the phantom entry visible in prefix-scan results.

### Recommendation
In `UnDelegateResourceProcessor.execute`, when both frozen balances reach zero, delete the from/to index keys instead of writing an empty-valued capsule (mirror `DelegatedResourceAccountIndexStore.unDelegateV2`'s semantics). This likely requires adding a delete capability to the `Repository`/`ContractState` caching layer (or a repository method such as `deleteDelegatedResourceAccountIndex`) so the TVM native-contract path can express key deletion consistently with the store-level actuator path, and ensuring the commit/flush logic actually issues a `delete` against the underlying revoking DB rather than a `put` with an empty value.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
