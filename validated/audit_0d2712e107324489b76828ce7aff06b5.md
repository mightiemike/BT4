## Analysis Result

Based on the evidence gathered, I found a strong analog for this bug class in nearcore's `DeleteAccount` action handling.

### Title
Operator error in `DeleteAccount`'s `beneficiary_id` causes irrecoverable, permanent loss of account funds - ([File: runtime/runtime/src/actions.rs])

### Summary
The `DeleteAccount` action lets an unprivileged account owner (a plain transaction signer) irreversibly delete their account and route the remaining balance to a `beneficiary_id` of their choosing. Unlike the Solidity report's two-step "operator sets data, then irreversible flag" pattern, the analogous root cause here is the same class of bug: a single operator-controlled input (`beneficiary_id`) is *not validated for existence* before an irreversible state transition (account deletion) is committed, and the fallback path (refund receipt) is architecturally forbidden from creating the missing target, so the funds cannot be recovered.

### Finding Description
`action_delete_account` in [1](#0-0)  unconditionally deletes the account and creates a `Receipt::new_balance_refund` addressed to `delete_account.beneficiary_id` for the account's remaining balance, then removes the account from state: [2](#0-1) 

The only validation performed on `beneficiary_id` is that it is a syntactically valid `AccountId` — there is no check that the beneficiary account actually exists, as documented in [3](#0-2) .

Critically, the balance payout is a **refund receipt** (system-originated, `is_refund: true`), and refund receipts are explicitly forbidden from implicitly creating a missing account, by design: [4](#0-3) 

This is confirmed by an existing regression test which asserts a refund to a missing account fails with `AccountDoesNotExist` and the account is never created: [5](#0-4) 

The protocol-model documentation further states that failed refund receipts are not retried or bounced back to the sender — they are irrecoverably burned: *"a failed refund burns its deposit into `other_burnt_amount` rather than refunding"*, [6](#0-5) .

So the sequence is:
1. Account owner submits `DeleteAccountAction { beneficiary_id }` where `beneficiary_id` is a syntactically valid but non-existent (e.g., mistyped) `AccountId`.
2. `action_delete_account` immediately deletes the account and enqueues a `Receipt::new_balance_refund(beneficiary_id, account_balance)` — this happens before the beneficiary is ever checked.
3. When that refund receipt is later processed, `check_account_existence`/`implicit_creation_allowed` rejects it because refunds can never create accounts.
4. The failed refund's deposit is burned (`other_burnt_amount`) rather than returned to the original owner or any account.

This mirrors the reported bug's structure exactly: an "operator" (here, the unprivileged account owner) supplies an input that determines the destination of funds; a subsequent irreversible action (account deletion, analogous to `isReadyForPayout`) commits before/without verifying that input is usable; and once triggered, there is no path to recovery, resulting in permanently lost funds — a stronger, more severe outcome than "frozen," since the funds are burned, not merely locked.

### Impact Explanation
Any account holder can, through a single mistake or malicious self-inflicted action (typo in `beneficiary_id`, using an account that has not yet been created, or one that is deleted between signing and execution), cause their entire remaining account balance to be permanently and unrecoverably burned rather than transferred or refunded. This is a direct, transaction-triggered loss of value with no possibility of recovery, satisfying "concrete unauthorized value movement" / "permanently frozen (destroyed) funds" from the validation criteria. It requires no privileged role, no validator, and no node-level compromise — a single signed transaction from the account owner is sufficient to reach this path.

### Likelihood Explanation
Likelihood is non-trivial: `beneficiary_id` is a free-form `AccountId` chosen by the caller with no existence check at signing time or at execution time before the delete is committed. A simple typo, a not-yet-created named account, or a race where the beneficiary account is deleted concurrently is sufficient to trigger irrecoverable loss. Because `DeleteAccount` must be the final action in a receipt (`DeleteActionMustBeFinal`), there is no way to combine it with a prior validation step in the same receipt to guard against this.

### Recommendation
Before committing account deletion, validate that `beneficiary_id` refers to an existing, initialized account (or explicitly document/require that callers pre-verify this via a view call, and consider surfacing a distinct execution error such as `BeneficiaryAccountDoesNotExist` rather than silently deleting the account and burning the refund on failure). Alternatively, defer the account removal from state until the beneficiary refund receipt has been confirmed to succeed, or fall back to returning funds to the deleting account/predecessor rather than burning them when the beneficiary is unreachable.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance.
2. Submit a transaction with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "ghost.near".parse().unwrap() })` where `ghost.near` does not exist (analogous to `delete_account_with_beneficiary_set` helper used in tests, [7](#0-6) ).
3. `action_delete_account` deletes `alice.near` and enqueues `Receipt::new_balance_refund("ghost.near", balance)`.
4. When that refund receipt is applied, `check_account_existence` rejects it (`ReceiptShape { is_refund: true, .. }` → `implicit_creation_allowed` returns `false`), producing `AccountErrorKind::AccountDoesNotExist`, as demonstrated by the existing test [8](#0-7) .
5. The failed refund's balance is burned into `other_burnt_amount`; `alice.near` no longer exists; no account anywhere holds the funds. The loss is permanent and unrecoverable.

**Note on uncertainty:** I was not able to directly view the exact code path in `runtime/runtime/src/lib.rs` around lines 929/972 that performs the "burn on failed refund" (the file is large and my tool budget was exhausted before confirming the exact burn mechanics at that line), so this detail relies on the `protocol-model/spec/runtime-execution.md` documentation rather than a directly cited code line. If more certainty is needed on the exact accounting of the burned amount, a Devin session with full repository access should verify `runtime/runtime/src/lib.rs` near the refund-processing/burn logic referenced in that spec.
