## Finding confirmed

`FeatureVerifier::verify_field_definition` and its callee `verify_signature_token` do **not** recurse into nested type arguments, while the sibling function `verify_signatures` for the module's signature pool **does** recurse (via `preorder_traversal`). This is a real asymmetry in the code.

### Title
Struct field type feature-gate bypass via non-recursive `verify_signature_token` in `FeatureVerifier` - (File: `third_party/move/move-bytecode-verifier/src/features.rs`)

### Summary
`FeatureVerifier::verify_struct_defs` calls `verify_field_definition`, which checks only the *top-level* `SignatureToken` of a field, never descending into nested type arguments such as `Vector<T>`'s inner token, `StructInstantiation`'s type-argument list, or `Reference`'s inner token.

### Impact Explanation
This is a genuine logic bug: the feature-gating invariant ("every `SignatureToken`, however nested, must be checked against enabled features") is broken specifically for struct field definitions. A module author can declare a struct field whose type nests a `SignatureToken::Function` inside a `Vector` or generic `Struct`/`StructInstantiation`, and this check will not reject it even when the function-value feature is disabled on-chain.

However, I could not fully verify within this review whether other independent layers (the binary deserializer config, `signature_v2::verify_module`, or the type-safety/loader passes) would independently reject or safely no-op on such a token before it reaches execution. If those layers also fail to reject it, the module would be accepted with a field type the runtime type-layout/serialization code may not expect when the feature is toggled off, which could manifest as a VM invariant violation or panic during layout building/serialization of that struct — behavior that is deterministic across all validators (since `enable_function_values` is a chain-wide governance feature applied uniformly at a given ledger version), so it would not by itself cause cross-validator state divergence. It could still, however, cause avoidable transaction aborts/invariant violations that should have been rejected earlier at verification time.

### Likelihood Explanation
Requires only an unprivileged module author to publish a module with such a crafted field signature; no privileged access needed. Whether it is exploitable to actual harm depends on downstream handling, which I was unable to fully trace in this pass (deserializer-level gating for `Function` tokens, `signature_v2.rs`, `type_safety.rs`, and the loader's type-layout builder were not fully inspected here).

### Recommendation
Fix `verify_field_definition` to traverse nested tokens the same way `verify_signatures` does, e.g.:
```rust
fn verify_field_definition(&self, struct_idx: usize, field: &FieldDefinition) -> PartialVMResult<()> {
    for t in field.signature.0.preorder_traversal() {
        self.verify_signature_token(t)
            .map_err(|e| e.at_index(IndexKind::StructDefinition, struct_idx as u16))?;
    }
    Ok(())
}
```

    fn verify_signatures(&self) -> PartialVMResult<()> {
        if !self.config.enable_function_values {
