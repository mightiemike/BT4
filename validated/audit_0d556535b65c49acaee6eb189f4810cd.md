### Title
`tokenExchange` does not verify that the caller-supplied `shop` parameter matches the shop embedded in the session token before exchanging it - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
The `assignTeam`-style bug in the report is a case where a privileged assignment/validation step accepts a value without checking it against the already-established identity (the user's existing team), letting the caller override which entity receives credit. The analog here is `tokenExchange` in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`, which decodes and validates the session token, but never cross-checks the decoded token's shop (`dest`) against the `shop` argument supplied separately by the caller before using that caller-supplied `shop` to build the outbound access-token request URL and to construct the resulting `Session`.

### Finding Description
`tokenExchange` takes both a `sessionToken` and an independent `shop` string as parameters: [1](#0-0) 

The implementation calls `decodeSessionToken(config)(sessionToken)` purely to validate the token's signature/claims, but discards the returned payload entirely — it never compares `payload.dest` (the shop the token was actually issued for) to the `shop` parameter: [2](#0-1) 

The `shop` argument (sanitized only for format, not for consistency with the token) is then used directly to build the outbound request to `https://${cleanShop}/admin/oauth/access_token` and to populate the resulting `Session.shop`: [3](#0-2) 

This mirrors the `assignTeam` flaw structurally: a validated identity (`userTeams[_user]` / the token's `dest`) exists, but a second, independently supplied value (`_team` / `shop`) is accepted and used without being checked against it, so the wrong entity ends up being credited/recorded.

By contrast, the two consumers I was able to inspect derive `shop` directly from the decoded payload rather than accepting it independently, e.g. `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts` computes `shop` from `payload.dest` before calling the exchange helper: [4](#0-3) 

However, `shopify.auth.tokenExchange` is a **public API** documented for direct use by app developers, where `shop` and `sessionToken` are described as independently sourced (`shop` from `req.query.shop`, `sessionToken` from a header or URL param) — see `packages/apps/shopify-api/docs/reference/auth/tokenExchange.md` lines 14-27. This means an app built directly against this documented API, rather than through the `shopify-app-remix`/`shopify-app-react-router`/`shopify-app-express` wrappers, could pass a `shop` value that does not match the token's `dest` without the library rejecting the mismatch.

### Impact Explanation
If an app author (or a component of the app that accepts an externally influenced `shop` query parameter, e.g., from a document request) calls `tokenExchange` with `shop` sourced from the request query string while `sessionToken` is a valid token for a *different* shop the same merchant/browser holds (e.g., in a multi-tenant testing environment, or a merchant with access to multiple stores), the resulting session could be persisted under the wrong shop record, i.e. `teamDeposits`-style cross-tenant misattribution of a valid, legitimately obtained offline/online access token into another shop's session slot in `sessionStorage`. Ultimately the actual admin API call to `https://${cleanShop}/admin/oauth/access_token` is likely to be rejected server-side by Shopify if the token's audience doesn't correspond to that shop, which limits real-world exploitability — I could not confirm from the codebase alone whether Shopify's OAuth endpoint enforces this, since that enforcement is external to this repository.

### Likelihood Explanation
Exploitability depends entirely on how a downstream app wires the public `tokenExchange` API — if `shop` is taken from an untrusted, independently-controlled source (as the official docs example shows: `shopify.utils.sanitizeShop(req.query.shop, true)`) rather than derived from the decoded token, the mismatch is trivial to trigger from an anonymous request. Within this repo's own middleware wrappers (Express/Remix/React Router), `shop` is always derived from the decoded payload, so the practical exposure is limited to direct/custom consumers of the public API and I could not verify further call sites due to tool errors in the final research step.

### Recommendation
Update `tokenExchange` in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` to use the payload returned from `decodeSessionToken` and either derive `shop` exclusively from `payload.dest`, or explicitly validate that the caller-supplied `shop` matches `payload.dest` and throw (e.g., `InvalidJwtError` or a new `ShopMismatchError`) if they differ, before making the outbound request or constructing the session.

### Proof of Concept
Not independently verified with a runnable exploit — this requires confirming (1) whether Shopify's `/admin/oauth/access_token` endpoint rejects a mismatched `shop`/token audience server-side, and (2) whether any app-facing consumer in this monorepo (or a third-party integrator using the public API directly) passes an untrusted `shop` value distinct from the token's `dest` into `tokenExchange`. I was unable to complete this verification because file-read tool calls failed in the final research iteration (`ensure-valid-offline-session.ts`, `validate-shop-and-host-params.ts`, `auth-code-flow.ts`), so confidence in real-world exploitability is moderate rather than confirmed.

```typescript
export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
```
