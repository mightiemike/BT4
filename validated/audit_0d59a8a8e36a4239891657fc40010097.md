### Title
Hard-coded gas constants in the Near Wallet Contract can strand ETH-implicit account funds if future protocol gas-cost changes make them insufficient - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
### Finding Description
The reported ENS bug is that `.transfer()`/`.send()` hard-codes a 2300 gas stipend for the recipient's fallback, and any future EVM opcode repricing can make that stipend insufficient, causing the transfer to revert and break dependent functionality.

The closest reachable analog in nearcore is the **Wallet Contract** (NEP-518), which is the on-chain contract that ETH-implicit accounts run to translate Ethereum-style signed transactions into native NEAR actions, reachable by any unprivileged relayer/RPC caller submitting an `rlp_execute` transaction [1](#0-0) . Instead of forwarding a fixed *gas stipend*, the Wallet Contract hard-codes fixed **static gas budgets** for chained cross-contract promises it constructs on the user's behalf — e.g. `RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_DEPOSIT_GAS`, `NEP_141_STORAGE_BALANCE_OF_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, and `REGISTRAR_LOOKUP_GAS`, used when building the promise chain for base-token transfers, ERC-20 (NEP-141) emulation, and address-registrar lookups [2](#0-1) [3](#0-2) .

These constants are conceptually identical to Solidity's fixed 2300-gas stipend: they are values baked into deployed contract bytecode (as a **global contract** shared by every ETH-implicit account, per `EthImplicitGlobalContract`) that assume the current cost of gas for host functions/actions (`ActionCosts::transfer`, `ActionCosts::function_call_base`, wasm op costs, etc.) will remain stable. Those underlying costs are exactly the parameters this codebase tracks as protocol-tunable values in `core/parameters/src/cost.rs` and `core/parameters/res/runtime_configs/parameters.yaml`, and they are explicitly expected to change over protocol versions (e.g., NEP-536's `gas_refund_penalty`, `AccountCostIncrease`, `FixContractLoadingCost`) [4](#0-3) . If a future protocol version raises the gas cost of `new_action_receipt`, `function_call_base`, `storage_deposit`/`storage_balance_of` calls, or wasm execution generally (the "gas repricing" analog to Ethereum's SLOAD change), the wallet contract's fixed callback gas budgets can become insufficient for the promise chain to complete.

### Impact Explanation
Because the Wallet Contract cannot be upgraded per-account (ETH-implicit accounts run the shared global contract and cannot be redeployed with a full-access key, per the account-type description) [5](#0-4) , a protocol-wide gas repricing that invalidates these hard-coded constants would deterministically break `rlp_execute` for every ETH-implicit account simultaneously, for every relayer transaction that hits a code path where a chained cross-contract call's callback runs out of gas (e.g. `nep_141_storage_balance_callback`, `address_check_callback`, `rlp_execute_callback`) [6](#0-5) . Failures in these callbacks would leave the promise chain incomplete: for ERC-20/NEP-141 emulated transfers, an out-of-gas failure at `nep_141_storage_balance_callback` or in the follow-up `storage_deposit`/transfer chain could burn the attached deposit without completing the underlying token transfer, and the deposit-refund path is itself gated behind a *further* cross-contract transfer inside `rlp_execute_callback` that could also fail if the failure is due to gas exhaustion rather than promise rejection [7](#0-6) . This is a transaction-triggered halt of a critical account-type's core functionality, and in some emulated-payment paths it risks stuck/lost deposits rather than a clean revert, which the campaign accepts as valid impact categories (transaction-triggered halt, frozen funds).

### Likelihood Explanation
This requires a future protocol-parameter change (a gas repricing) to actually manifest — similar to how the original ENS finding required an EVM gas-cost change to trigger. It is not exploitable today by a single malicious transaction under current parameters; it is a latent design fragility. Given nearcore's history of deliberately evolving gas-cost parameters across protocol versions (NEP-536, `AccountCostIncrease`, `FixContractLoadingCost`, universal/deterministic account cost tuning), and that the same reference implementation (`near-wallet-contract`) is used unmodified by every ETH-implicit account as a global contract, the likelihood of the assumption eventually breaking is non-trivial, but it is judgment-dependent on protocol roadmap decisions and cannot be independently confirmed from this repository snapshot alone.

### Recommendation
Avoid embedding fixed numeric gas constants for cross-contract promise chains in the Wallet Contract. Instead, either (a) derive callback/child-call gas dynamically from `prepaid_gas`/remaining gas at execution time using `GasWeight`-based split (as is already done for `ban_relayer` via `function_call_weight`) [8](#0-7) , or (b) make the constants a governance-controlled/config-driven value that can be safely bumped via a global-contract redeploy synchronized with any gas-repricing protocol upgrade, and add protocol-level monitoring/tests (similar to `fix_contract_loading_cost_protocol_upgrade` tests) that assert the wallet contract's promise chains still complete successfully after each gas-cost parameter change.

### Proof of Concept
Not directly reproducible from static analysis alone — it depends on a hypothetical future protocol version raising gas costs for the actions used inside the promise chains (`function_call`, `new_action_receipt`, `storage_deposit`/`storage_balance_of` external calls). The reachable path is: an unprivileged relayer submits an `rlp_execute` transaction encoding an ERC-20-style transfer or base-token transfer with an address check to an ETH-implicit account; this triggers `rlp_execute` → `action_to_promise`/`build_promise` using the fixed gas constants (`NEP_141_STORAGE_BALANCE_OF_GAS`, `NEP_141_STORAGE_DEPOSIT_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `RLP_EXECUTE_CALLBACK_GAS`) [9](#0-8) ; under a hypothetical higher-gas-cost protocol version, the fixed budget would be insufficient for the chained call/callback to complete, causing the receipt chain to fail deterministically for all ETH-implicit accounts using the unmodifiable shared global contract, analogous to the ENS `.transfer()` 2300-gas issue where a future gas-cost change breaks a hard-coded gas assumption baked into immutable/hard-to-upgrade contract code.

Note: This is a lower-confidence analog than a direct code-level bug; it is presented because it is the closest structural match (immutable, unmodifiable contract code with hard-coded gas constants assuming stable gas-cost parameters, reachable by an unprivileged transaction signer) found in the in-scope reachable surface. I was not able to fully inspect the complete `lib.rs` file (constant definitions, all promise-chain construction sites) due to a tool error in the final iteration, so the exact numeric values of each gas constant and all call sites could not be independently verified — a full review of `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` in a Devin session is recommended to confirm every affected code path.

### Wallet Contract

The Wallet Contract (see [NEP-518](https://github.com/near/NEPs/issues/518) for more details) functions as a user account and is designed to receive, validate, and execute Ethereum-compatible transactions on the NEAR blockchain.

Without going into details, an Ethereum-compatible wallet user sends a transaction to an RPC endpoint, which wraps it and passes it to the Wallet Contract (on the target account) as an `rlp_execute(target: AccountId, tx_bytes_b64: Vec<u8>)` contract call.
Then, the contract parses `tx_bytes_b64` and verifies it is signed with the private key matching the target [ETH-implicit account ID](#eth-implicit-account-id) on which the contract is hosted.

Under the hood, the transaction encodes a NEAR-native action. Currently supported actions are:

- Transfer (from ETH-implicit account).
- Function call (call another contract).
- Add `AccessKey` with `FunctionCallPermission`. This allows adding a relayer's public key to an ETH-implicit account, enabling the relayer to pay the gas fee for transactions from this account. Still, each transaction has to be signed by the owner of the account (corresponding Secp256K1 private key).
- Delete `AccessKey`.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
