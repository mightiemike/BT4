### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant admin session hijack via webhook replay - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts, packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts)

### Summary
The webhook authentication pipeline validates the `X-Shopify-Hmac-Sha256` signature only over the raw request **body**, using the single API secret shared by every shop that installed the app. The `X-Shopify-Shop-Domain` header — which the framework uses to select *whose* offline access token/admin session to attach to the request — is never included in the signed data. A merchant who has installed the app on their own store can therefore generate a validly-signed webhook body (by triggering an event on their own shop) and replay that same body/HMAC pair while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header, causing the library to authenticate the (attacker-shaped) payload against the victim shop's session and admin client.

### Finding Description
Webhook signature validation is implemented in `validateHmacFromRequestFactory`, which only signs/verifies the raw body: [1](#0-0) 

The `domain` field is read straight from an unauthenticated header (`X-Shopify-Shop-Domain` / `shopify-shop-domain`) in `checkWebhooksHeaders`/`checkEventsHeaders`, with no cryptographic binding to the HMAC: [2](#0-1) 

That unauthenticated `check.domain` value is then used directly to look up/create the offline session and to build an authenticated Admin API client that is handed to the app's webhook handler: [3](#0-2) [4](#0-3) 

The same pattern exists in the react-router package: [5](#0-4) 

Because a single API secret is shared across all shops that install the app, `HMAC(body)` is identical for every shop for the same body content. An attacker who controls their own shop installation can:
1. Trigger a webhook on their own shop with a body they can partially influence (e.g. product/order fields, metafields, notes) to obtain a genuinely Shopify-signed `(body, hmac)` pair.
2. Replay that exact `body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain` to a victim shop that also has the app installed.
3. `validateHmacFromRequestFactory` verifies successfully (it never looks at the domain header), so `check.valid === true` and `check.domain` is the attacker-chosen victim domain.
4. `ensureValidOfflineSession(params, check.domain)` loads the victim's offline session/access token, and the webhook handler runs the attacker-shaped payload with the victim's authenticated `admin` client.

This mirrors the root cause of the referenced Particle finding: a security check validates only part of the attacker-influenced input (the swap `data`/here the request body) while a companion parameter that determines *where value/authority flows* (which pool/here which shop's token is used) is left outside that verification and fully attacker-controlled.

### Impact Explanation
An attacker who is a legitimate (even free-trial) merchant of the app can forge webhook deliveries "from" any other shop that has the same app installed, causing the app to run webhook business logic using the victim shop's Admin API access token with attacker-influenced payload content. Depending on what the app's webhook handlers do (write data, issue refunds, sync inventory, call third-party systems, etc.), this enables cross-tenant state corruption, unauthorized Admin API actions performed with the victim's token, and information disclosure, without ever compromising the victim or leaking any secret.

### Likelihood Explanation
Exploitation only requires becoming an app user (installing the app on one's own store, which is typically open to any merchant) and knowing/guessing another shop's domain that has the app installed (often discoverable, e.g. via public storefront, app reviews, or brute-forcing predictable `myshopify.com` handles). No access to the API secret, no MITM, and no privileged role is required — only a single ordinary merchant account is needed to attack another single merchant, matching the "single merchant" threat model.

### Recommendation
Bind the shop domain to the signed material, e.g.:
- Derive the "current shop" strictly from a value that Shopify does authenticate (there currently isn't one for webhooks other than the body/HMAC), or
- Compute/verify the HMAC over `domain + body` (or otherwise include the header value inside the signed payload) instead of `body` alone, matching how OAuth/app-proxy HMACs include `shop` as a signed field, or
- At minimum, cross-check `check.domain` against an expected set of shops (e.g. only accept a domain for which a session already exists and additionally require the domain to match a shop-specific webhook subscription's known URL/shop, rather than trusting the header value provided in the same unauthenticated request), and add webhook replay protection (nonce/timestamp binding) so a captured `(body, hmac)` pair from one shop cannot be reused indefinitely for a different target shop.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com` (or simply know that `victim.myshopify.com` already has the app installed).
2. On `attacker.myshopify.com`, trigger a webhook topic whose payload content the attacker can shape (e.g. by editing a product/order note field) to capture a legitimate `(rawBody, X-Shopify-Hmac-Sha256)` pair from Shopify.
3. Send a POST to the app's webhook endpoint with the captured `rawBody` and `X-Shopify-Hmac-Sha256` unchanged, but with `X-Shopify-Shop-Domain: victim.myshopify.com`, matching the flow validated in [6](#0-5) 
4. `api.webhooks.validate` returns `valid: true, domain: 'victim.myshopify.com'` because HMAC verification (`validateHmacFromRequestFactory`) never inspects the domain header, per [1](#0-0) 
5. The framework loads `victim.myshopify.com`'s offline session/access token and hands the attacker-crafted payload plus victim's authenticated `admin` client to the app's webhook handler.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
