### Title
Silent zero/incorrect vote-reward computation when witness Vi accumulator has not yet been recorded for a cycle — `MortgageService.computeReward` / `VoteRewardUtil.computeReward` - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
The ZcToken bug pattern is: a state variable (`maturityRate`) that should be set by a triggering event is read directly in a withdrawal-value calculation; when the variable has not yet been set (still its zero default), the multiplication collapses to `0`, silently paying the user nothing instead of reverting or falling back to a correct value. The same "unset accumulator defaults to zero and is trusted as if valid" pattern exists in java-tron's new voting-reward algorithm, where `DelegationStore.getWitnessVi` returns `BigInteger.ZERO` whenever no Vi value has been persisted for the queried cycle, and this default is used directly in reward-delta math without validating that the accumulator was actually computed for that cycle.

### Finding Description
The new reward algorithm tracks a per-witness cumulative reward index (`Vi`) per cycle, stored via `DelegationStore.setWitnessVi`/`getWitnessVi`: [1](#0-0) 

`getWitnessVi` has no way to distinguish "cycle N has Vi = 0 because nothing has accrued yet" from "cycle N's Vi has simply never been computed/persisted" — both cases return `BigInteger.ZERO`. This value is then used directly, without any staleness/liveness check, in the reward computation used for both live queries and actual withdrawals: [2](#0-1) [3](#0-2) 

The Vi values for a cycle are populated by `MaintenanceManager.doMaintenance()`, which calls `delegationStore.accumulateWitnessVi(curCycle, ...)` only for the **currently ending** cycle, and only while `dynamicPropertiesStore.useNewRewardAlgorithm()` is enabled: [4](#0-3) 

If a user's `beginCycle`/`endCycle` window spans into a cycle whose Vi has not yet been written for that witness/cycle pair — e.g., because the witness had no vote/reward for that cycle (so `accumulateWitnessVi` may skip persisting when `preVi` is zero, per the "Zero vi will not be record" comment), or because the new-algorithm switch-over boundary (`getNewRewardAlgorithmEffectiveCycle`) causes `beginCycle - 1` to read a Vi slot that predates the algorithm's activation and was never populated — `getWitnessVi` silently returns `0`. `deltaVi = endVi.subtract(beginVi)` then becomes `0` (or an incorrect, understated delta if only one side is spuriously zero), and the `continue` branch causes that portion of the reward to be dropped: [2](#0-1) 

Critically, `withdrawReward`/`VoteRewardUtil.withdrawReward` then unconditionally advances `beginCycle`/`endCycle` bookkeeping regardless of whether the computed reward was correct: [5](#0-4) 

This mirrors the ZcToken flaw precisely: an implicit-zero default for an accumulator/rate value is trusted as authoritative in a payout calculation, and the state is advanced/consumed as if the payout were correct — but unlike ZcToken (where a later call recovers the correct amount because `maturityRate` gets set once and stays valid), here `beginCycle` is permanently moved forward past the affected cycle, so reward for that cycle range is **permanently lost**, not merely delayed.

### Impact Explanation
This directly affects unprivileged users calling `WithdrawBalanceContract`/`withdrawReward` (also reachable from TVM via `Program.withdrawReward()` / `WithdrawRewardProcessor`) and voting reward queries. If the impacted scenario is reachable, a voter can receive systematically less allowance than entitled, and once `beginCycle` is advanced, that discrepancy cannot be corrected retroactively — a real accounting/underpayment issue in a market/consensus-reward flow, matching the "settlement" impact category.

### Likelihood Explanation
The likelihood is bounded by uncertainty over whether `accumulateWitnessVi` genuinely produces gaps for typical vote/withdraw sequences observed by ordinary users — the "Zero vi will not be record" skip-logic combined with `getWitnessVi` defaulting to zero is the concrete root cause supported by code, but confirming an end-to-end reachable exploit (e.g., a specific vote/withdraw ordering around the `newRewardAlgorithmCycle` boundary or a witness's zero-vote cycles) requires tracing `getOldReward`/`min(...)` boundary handling in `computeReward` (lines 199-230) further than the available index allows me to fully verify.

### Recommendation
Add an explicit marker (distinct from `BigInteger.ZERO`) for "Vi not yet computed for this cycle" in `DelegationStore`/`RewardViCalService`, and have `computeReward` treat a missing Vi as a computation deferred/error condition rather than a valid zero, preventing `beginCycle` from advancing until the correct Vi is available.

### Proof of Concept
Not independently reproducible from the indexed code alone — the analysis is based on tracing `getWitnessVi`'s zero-default behavior [1](#0-0)  into `computeReward`'s unconditional consumption of that value [2](#0-1)  and `accumulateWitnessVi`'s conditional skip-persistence logic [6](#0-5) . Confirming exploitability requires a running node/test harness to construct the exact vote/cycle sequence, which is beyond what can be verified via static code search alone.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
