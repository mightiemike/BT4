### Title
Unbounded iteration over `VotesStore` during DPoS maintenance can degrade or stall block processing - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager.doMaintenance()` calls `countVote(votesStore)`, which iterates over **every entry** in `VotesStore` with no upper bound, cap, or batching, mirroring the Axis Finance EMPAM settlement bug where the contract iterated over all bids without a limit until it exceeded the gas limit.

### Finding Description
At the end of every voting cycle, all java-tron nodes execute `MaintenanceManager.doMaintenance()`, which calls the private `countVote()` method: [1](#0-0) 

This method walks a full `Iterator` over `votesStore` with `while (dbIterator.hasNext())`, performing per-entry work (map lookups/updates for both old and new votes) and then deleting every visited entry — there is no `MAX_*` constant, batch size, or early-exit condition bounding how many entries can be processed in one maintenance cycle: [2](#0-1) 

The number of entries in `votesStore` is directly controlled by anonymous, broadcastable transactions: any account can submit a `VoteWitnessContract` (handled by `VoteWitnessActuator.countVoteAccount` / `VoteWitnessProcessor.execute`), which creates or updates a `VotesCapsule` keyed by voter address: [3](#0-2) 

Because a fresh entry is created per unique owner address once it votes in a cycle, an attacker who controls many funded (even minimally frozen) accounts can trivially inflate `votesStore` to a large size before a maintenance boundary is reached, forcing every node to iterate that entire unbounded set synchronously as part of processing the maintenance block — a step that is mandatory and cannot be skipped or parallelized away.

This directly parallels the Sherlock/Axis-Finance M-8 finding: EMPAM's settlement loop iterated over all submitted bids without a hard cap, causing gas exhaustion; here, `countVote()` iterates over all vote records without a hard cap, causing potentially unbounded CPU/wall-clock time consumption during a consensus-critical maintenance step.

By contrast, other order/queue-processing code in this codebase (e.g. `MarketSellAssetActuator.matchOrder`) explicitly caps iteration with `MAX_MATCH_NUM` and throws a validation exception once exceeded: [4](#0-3) 

`countVote()`/`doMaintenance()` has no equivalent bound.

I was unable to fully confirm, within the available search iterations, the exact call site that invokes `doMaintenance()` during block application (it is referenced from consensus/DPoS block-processing code but the specific caller and its position relative to block time budgets/CPU-time checks could not be located in this pass). This detail would need to be verified in a full repository checkout to establish precisely how much wall-clock budget is available before this unbounded loop could cause a node to fall behind or fail its block deadline.

### Impact Explanation
If `votesStore` grows very large (through mass, low-cost voting from many addresses), every node must synchronously iterate the entire store during `doMaintenance()` at each maintenance cycle. Since maintenance is part of block-boundary processing and (unlike `MarketSellAssetActuator`) has no cap, this can:
- Increase per-cycle processing time for all nodes, risking delayed block production/propagation across the network (a network-wide DoS-like effect on consensus liveness), and
- Increase resource (CPU/memory) usage proportional to attacker-controlled input size, with no built-in ceiling — the type of "settlement of batch operation can exceed a resource limit" issue described in the source report.

This is a shared/consensus-critical component (not a single sender's transaction execution), so unlike a normal per-transaction gas limit failure, degraded performance here could affect the whole network's block cadence rather than a single actor's funds.

### Likelihood Explanation
Moderate. Creating many `VotesCapsule` entries requires many distinct funded accounts each submitting a `VoteWitnessContract` (or holding TRON Power), which has some cost but is not prohibitively expensive at scale, and voting is a normal, anonymous, permissionless operation. There is no existing rate limit or maximum entry count on `votesStore` size analogous to `MAX_ACTIVE_ORDER_NUM`/`MAX_MATCH_NUM` used elsewhere in the codebase for similar unbounded-iteration risks.

### Recommendation
- Add a hard cap (with corresponding validation/rejection or deferred processing) on the number of `votesStore` entries processed per maintenance cycle, analogous to `MAX_MATCH_NUM` in `MarketSellAssetActuator`.
- Alternatively, process `votesStore` in bounded batches across multiple maintenance cycles or blocks rather than a single unbounded pass.
- Consider rate-limiting/capping the number of new voter entries (unique addresses) that can be created within a single voting cycle, or aggregating vote deltas incrementally at vote-time rather than at maintenance time to avoid an unbounded backlog.

### Proof of Concept
Conceptual PoC (not executed, due to lack of local execution environment access in this analysis):
1. Create N (e.g., 100,000) distinct accounts, each with the minimal frozen balance/TRON Power required to cast a vote.
2. From each account, broadcast a `VoteWitnessContract` transaction voting for a valid witness before the next maintenance boundary, so each creates a distinct entry in `votesStore` (as created in `VoteWitnessActuator.countVoteAccount`, `VoteWitnessActuator.java:171-176`).
3. At the maintenance boundary, observe `MaintenanceManager.doMaintenance()` → `countVote(votesStore)` iterating all N entries (`MaintenanceManager.java:165-195`), and measure the wall-clock time taken by this step versus a normal-sized `votesStore`, comparing against available block-processing time budgets.

This proof of concept requires further verification in a running testnet/devnet to precisely quantify performance degradation and confirm reachability of any protective bound (none observed in the code reviewed).

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

    }

    if (!votesStore.has(ownerAddress)) {

    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
