### Title
Cost-unaware uniform rate limiting allows sustained DoS via full-store-scan gRPC methods (e.g. `GetAssetIssueList`) called at default 1000 QPS - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/RateLimiterInterceptor.java])

### Summary
`RateLimiterInterceptor.init()` registers the same `DefaultBaseQqsAdapter(QpsStrategy.DEFAULT_QPS_PARAM)` (default 1000 QPS) for *every* gRPC method unless a component-specific override exists in `rate.limiter.rpc`. Unbounded, O(n) store-scanning handlers such as `Wallet.getAssetIssueList()` (no offset/limit variant) inherit this same generous ceiling, letting an anonymous client sustain full-database iterations at up to 1000 requests/sec.

### Finding Description
`RateLimiterInterceptor.init()` iterates every registered `ServerServiceDefinition`/`ServerMethodDefinition` on the gRPC server and unconditionally installs a `DefaultBaseQqsAdapter` built from `QpsStrategy.DEFAULT_QPS_PARAM` [1](#0-0) . `QpsStrategy.DEFAULT_QPS_PARAM` is derived from `rate.limiter.global.api.qps`, defaulting effectively to 1000 [2](#0-1) . Only methods explicitly listed under `rate.limiter.rpc` in config with a non-empty `strategy` get a stricter per-component limiter installed afterward [3](#0-2) ; the shipped `config.conf` contains no `rate.limiter` block at all, so this override path is unused by default and every method — cheap or expensive — is capped only by the same global 1000 QPS ceiling.

`WalletSolidity.GetAssetIssueList` (an `EmptyMessage` RPC requiring no arguments and no signature/fee) is served by `Wallet.getAssetIssueList()`, which calls `getAllAssetIssues()` and performs a full iteration over the entire `AssetIssueStore` on every single call [4](#0-3) , backed by `AssetIssueStore.getAllAssetIssues()` which streams the whole underlying store with no pagination or cap [5](#0-4) . `getAssetIssueByAccount()` similarly loads the full store list and filters in memory [6](#0-5) .

Because the rate limiter is purely count-based ("QPS") and identical across all endpoints, an attacker calling `GetAssetIssueList` at close to the default 1000 QPS ceiling forces up to 1000 full-store scans per second — a workload the limiter treats as fully compliant, but which is far beyond what the underlying LevelDB/RocksDB iteration can sustain, degrading CPU and I/O for the whole node. The interceptor's per-call checks (`acquirePermit`, `GlobalRateLimiter.acquirePermit`) only gate call *count*, never call *cost*, so no existing mechanism (bandwidth/energy accounting doesn't apply to read-only gRPC queries, and there is no query-size/complexity limiter) prevents this.

### Impact Explanation
This is a DoS via the RPC-API: sustained calls to store-iterating handlers at the default global QPS quota can exhaust CPU/I/O capacity of the full node, degrading or stalling responsiveness for all API clients, without violating any configured rate limit. It matches the "DoS via RPC-API" bounty impact class since it requires only an unprivileged, unauthenticated gRPC client and does not require breaking any signature/permission/economic check.

### Likelihood Explanation
Preconditions match the default, out-of-the-box node configuration (`config.conf` ships no `rate.limiter.rpc` overrides), so any publicly reachable full node with the gRPC API enabled is affected. The attack is trivial to execute: a client only needs to send unauthenticated `EmptyMessage` requests to `GetAssetIssueList` (or similar unbounded query methods) at close to 1000 QPS, which is well within reach of a single machine with modest bandwidth. No fees, signatures, or special account state are required since these are pure read-only gRPC queries.

### Recommendation
Make the rate limiter cost-aware rather than purely QPS-based: assign lower default QPS ceilings (or a distinct, more restrictive `DefaultBaseQqsAdapter` strategy) to handlers known to perform unbounded or O(n) store scans (e.g. `GetAssetIssueList`, `getAssetIssueByAccount`, and any similar full-iteration APIs), and/or add hard pagination limits enforced server-side (not just advisory) for these methods so a single call cannot scan the whole store. Consider introducing a per-method "cost weight" concept in `RateLimiterInterceptor`/`QpsStrategy` so the global default of 1000 QPS is only applied to genuinely O(1)/cheap handlers, with expensive handlers requiring an explicit, much lower default entry in `rate.limiter.rpc`.

### Proof of Concept
```java
// Conceptual load test against a default-configured full node's gRPC API.
// Sustained calls to an unbounded full-store-scan endpoint at the default QPS ceiling.
ManagedChannel channel = ManagedChannelBuilder.forAddress(host, 50051).usePlaintext().build();
WalletSolidityGrpc.WalletSolidityBlockingStub stub = WalletSolidityGrpc.newBlockingStub(channel);

ExecutorService pool = Executors.newFixedThreadPool(50);
AtomicLong sent = new AtomicLong();
long start = System.currentTimeMillis();
while (System.currentTimeMillis() - start < 60_000) {
  pool.submit(() -> {
    stub.getAssetIssueList(EmptyMessage.newBuilder().build()); // full AssetIssueStore scan per call
    sent.incrementAndGet();
  });
  Thread.sleep(1); // throttle client-side to stay near ~1000 QPS, the node's own default ceiling
}
// Expected observation: node CPU/I/O utilization rises sharply and handler
// latency for GetAssetIssueList (and other RPCs sharing the executor pool)
// degrades significantly over the sustained window, while
// RateLimiterInterceptor never rejects the calls (RESOURCE_EXHAUSTED count stays ~0),
// confirming the limiter is count-aware but not cost-aware.
```

  public AssetIssueList getAssetIssueByAccount(ByteString accountAddress) {
    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues();

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }
