## Title
`ExecutePayload` blocks all self-service UEA transactions (including fund withdrawal/migration) whenever the owner's origin chain has `IsInboundEnabled=false`, permanently freezing already-resident funds - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
The referenced Beta Finance bug is a class where a self-service user action (`repay()`) is blocked by an operational "paused" flag that was never meant to gate it, risking user fund loss with no alternative recourse. Push Chain's `x/uexecutor` keeper has a structurally identical pattern: `Keeper.ExecutePayload` — the **only** entry point through which a user's Universal Executor Account (UEA) can be driven (transfers, contract calls, and even UEA implementation migration) — unconditionally rejects the call whenever `ChainConfig.Enabled.IsInboundEnabled` is `false` for the owner's origin chain, regardless of whether the submitted payload has anything to do with a new inbound at all.

### Finding Description
`MsgExecutePayload` is documented as the sole authorized path for a user to act through their UEA: [1](#0-0)  ("contract-only binding" model — the Cosmos signer merely *delivers* the owner's pre-signed payload; the UEA contract enforces authorization). There is no other message that lets an owner move funds held by their own UEA or call the UEA's migration entry point: [2](#0-1) .

Inside `Keeper.ExecutePayload`, before any EVM work is performed, the keeper resolves the chain config for the owner's origin chain namespace and hard-fails if inbound is disabled for that chain: [3](#0-2) 

This check is not scoped to inbound-triggered payloads — it is executed for *every* `MsgExecutePayload`, including payloads that only touch funds/state already resident on Push Chain (e.g., a plain PRC20/native transfer out of the UEA, or a call to the UEA's own migration function) and require no new source-chain observation whatsoever. The integration test suite confirms this behavior explicitly and that it fires purely from the `IsInboundEnabled` flag, independent of payload semantics: [4](#0-3) [5](#0-4) .

Once `IsInboundEnabled` is toggled off for a chain — an ordinary, admin-curated operational lifecycle action supported by `x/uregistry` (`MsgUpdateChainConfig`) [6](#0-5)  and expected to happen (chain deprecation, security incident on the source chain, gateway migration, etc.) — every user whose UEA origin chain namespace matches that chain loses the *only* mechanism to move funds already sitting in their UEA. There is no separate "withdraw" or "self-rescue" message that bypasses this gate; `RevertStuckInbound` is explicitly admin-only and only applies to inbounds stuck in ballot voting, not to funds already finalized on-chain [7](#0-6) .

### Impact Explanation
This matches the "permanent freezing... of user or protocol-controlled funds" impact category. Any native PC or PRC20 balance already credited to a UEA (from a prior successful inbound) becomes inaccessible to its owner for the entire duration that the chain's `IsInboundEnabled` flag is `false`, with no alternative user-initiated exit path. Unlike the original OmniPool bug (temporary freeze until unpause), here the freeze duration is entirely dependent on how long the chain stays disabled, which per the design notes can be indefinite (deprecated/decommissioned chains).

### Likelihood Explanation
Toggling `ChainConfig.Enabled.IsInboundEnabled` is a normal, expected operational action (not abuse) documented as part of the chain lifecycle, and multiple upgrade notes/tests treat it as routine: [8](#0-7) . No attacker action is required beyond simply having previously deposited funds into a UEA tied to a chain that is later disabled — a fully realistic operational scenario, making this readily reachable.

### Recommendation
Scope the `IsInboundEnabled` check in `Keeper.ExecutePayload` to only the cases that actually depend on new inbound processing (if any), or introduce a dedicated "chain disabled" state that still permits self-service withdrawal/migration payloads through the UEA. At minimum, decouple "no new inbounds will be observed for this chain" from "the owner may no longer act through their own already-deployed UEA."

### Proof of Concept
1. UV votes finalize an inbound for `eip155:11155111`, minting PRC20/native funds into `owner`'s UEA on Push Chain (`x/uexecutor` inbound execution flow, per `x/uexecutor/README.md` lifecycle walkthrough).
2. Admin later sets `ChainConfig.Enabled.IsInboundEnabled = false` for `eip155:11155111` via `MsgUpdateChainConfig` (routine operational action).
3. Owner submits `MsgExecutePayload` with `UniversalAccountId.ChainId = "11155111"` and a payload that simply transfers the UEA's existing PRC20/native balance elsewhere — no new inbound involved.
4. `Keeper.ExecutePayload` rejects with `"inbound is disabled for chain eip155:11155111"` before ever reaching the UEA call, exactly as exercised by `TestExecutePayload_ChainEnabled` [5](#0-4) .
5. The owner has no other on-chain message to move these already-resident funds; they remain frozen for as long as the flag stays disabled.

```markdown
### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```
