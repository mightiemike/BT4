### Title
Gas-key balance limit check bypassed by nesting `WithdrawFromGasKey` inside a delegate action (SPICE `PendingTransactionQueue` under-accounting) - (File: `chain/client/src/pending_transaction_queue.rs`)

### Summary
The SPICE pending-transaction-queue admission control enforces a "remaining balance" style limit — a gas key's available balance must cover all balance-affecting effects of transactions that are pending (submitted but not yet certified) before a new transaction spending from the same gas key is admitted. This tracking is built by scanning only the **top-level** actions of each pending transaction for `Action::WithdrawFromGasKey` and accumulating the withdrawn amount into `pending_gas_key_costs` / `session_gas_key_withdrawals`. A `WithdrawFromGasKey` action nested inside a `DelegateAction` (meta-transaction) is invisible to this scan, so its effect on the gas key's balance is never counted by the admission check, even though it still executes and drains the gas key on-chain. This mirrors the reported Sherlock bug class: a capacity/limit check ("protection amount ≤ remaining lent principal") that is bypassed because the accounting only considers one code path (`buyProtection`'s direct params) and never accumulates/considers other operations that consume the same underlying resource (multiple purchases against the same position). Here, the "same resource" is gas-key balance, and the "other operation" that isn't accounted for is a delegated (meta-tx) `WithdrawFromGasKey`.

### Finding Description
`PendingTransactionQueue::add_chunk_transactions` builds per-gas-key withdrawal totals by iterating `tx.actions()` and matching `Action::WithdrawFromGasKey` directly: [1](#0-0) 

This only sees actions at the top level of the transaction. `PendingTxSession::check_pending`, used for optimistic admission during chunk production/RPC, performs the identical top-level-only scan for the session-local component of the same accounting: [2](#0-1) 

The resulting `paid_from_gas_key` constraint (`snapshot.pending_gas_key_cost + session_gas_key_withdrawal`) is what `verify_and_charge_gas_key_tx_ephemeral` in `runtime/runtime/src/verifier.rs` uses to decide whether a *subsequent* pending transaction has enough gas-key balance left, via `available_gas_key_balance < gas_cost` checks (as seen at `runtime/runtime/src/verifier.rs:594-600`). If a `WithdrawFromGasKey` action is wrapped inside a `DelegateAction` (a meta-transaction), the top-level scan in both `add_chunk_transactions` and `check_pending` misses it entirely, so the queue's belief about "how much of this gas key's balance is already committed by pending transactions" is understated. The runtime itself does execute the nested withdrawal (via the delegate-action dispatch in `runtime/runtime/src/actions.rs`), so the gas key balance is actually reduced on-chain by an amount the admission layer never subtracted from its "remaining" computation.

The codebase itself documents this exact gap as a known, named issue via the `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` enum variant, whose doc comment states plainly: "The SPICE pending transaction queue scans only the top level actions of a transaction for `WithdrawFromGasKey`, so a nested one drains a gas key that the queue still counts as funded." [3](#0-2) 

That feature's presence indicates the intended fix is to *reject* `WithdrawFromGasKey` nested in a delegate action outright (rather than to fix the scan), which confirms the bypass is real and reachable, and is mitigated only once that gate is activated on a given protocol version. A related sibling case, `RejectDelegateV2`, documents the identical structural gap for nonce/balance commitments of the whole delegated sender: [4](#0-3) 

### Impact Explanation
An account holding a gas key can submit multiple pending transactions in the same certification window: some using top-level `WithdrawFromGasKey` (correctly tracked) or — critically — a delegate action (meta-transaction) that nests a `WithdrawFromGasKey` targeting the same gas key. Because the second class is invisible to the admission accounting in both `add_chunk_transactions` and `check_pending`, the queue will continue to admit further transactions funded "from" that gas key believing more balance remains than actually does. When these pending transactions are eventually applied by the runtime, the on-chain `verify_and_charge_gas_key_tx_ephemeral`/`GasKey` balance updates could be pushed into an inconsistent state relative to what the admission layer assumed, allowing more gas-key-funded transaction admission (and thus more computation/spending) to be optimistically accepted than the key's true remaining balance supports. This is an accounting/limit-bypass in the same family as the reported bug — a resource cap check that fails to account for all code paths capable of consuming the tracked resource — and can manifest as transactions being admitted into blocks that the true balance cannot cover, a state-transition/consensus-relevant discrepancy between the pending-queue's optimistic view and actual runtime-enforced balances.

### Likelihood Explanation
This requires only an ordinary account that owns a gas key and the ability to construct a `DelegateAction` (meta-transaction) whose inner action is `WithdrawFromGasKey` targeting that gas key, then submit it alongside other pending transactions funded by the same key within the same pending-transaction window — all reachable by an unprivileged transaction submitter via the RPC/transaction-pool path. No validator or peer misbehavior is required. The severity is gated by whether `RejectWithdrawFromGasKeyInDelegate` (and `RejectDelegateV2`, which independently disables gas-key delegate flows) is active for the protocol version in question; where inactive, the gap described above is directly exploitable through the documented code path.

### Recommendation
Extend the pending-transaction-queue's `WithdrawFromGasKey` scan (`add_chunk_transactions` and `check_pending`) to recursively inspect actions nested inside `DelegateAction`/`DelegateV2`, not just top-level actions, so gas-key withdrawal commitments are fully accumulated regardless of where the action appears; alternatively, ensure `RejectWithdrawFromGasKeyInDelegate` and `RejectDelegateV2` are unconditionally active before any protocol version that permits gas keys, closing the bypass at the validation layer rather than relying on scan completeness.

### Proof of Concept
1. Create an account with a funded gas key (balance `B`).
2. Submit transaction T1: a top-level `WithdrawFromGasKey` for amount `B/2` from the account's access key — the queue's scan in `add_chunk_transactions`/`check_pending` correctly records this and reduces the gas key's counted "available" balance.
3. Submit transaction T2: a `SignedDelegateAction`/meta-transaction whose inner action is `WithdrawFromGasKey` for amount `B/2` targeting the same gas key, relayed by any relayer account. Because the scan in both `add_chunk_transactions` (`chain/client/src/pending_transaction_queue.rs:311-320`) and `check_pending` (`:576-585`) only inspects `tx.actions()` at the top level of the outer (relayer) transaction, the nested `WithdrawFromGasKey` inside the `DelegateAction` payload is never matched, so `pending_gas_key_costs`/`session_gas_key_withdrawals` for that gas key are not incremented by T2's withdrawal.
4. Submit transaction T3, a gas-key transaction spending gas funded by the same gas key. `check_pending`'s `paid_from_gas_key` constraint reflects only T1's withdrawal, understating actual committed usage by the amount withdrawn in T2. T3 is admitted as if the full remaining `B/2` (post-T1) were still available, even though T2 will also consume gas-key balance once applied — reproducing the "buy more protections to bypass the remaining-capacity check" pattern by hiding the resource-consuming operation inside an unscanned code path (the delegate action).
