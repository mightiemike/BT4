### Title
Unbounded growth of per-shop session-id index arrays in KV/Redis session storage enables DoS of session lookup - ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
The `KVSessionStorage` and `RedisSessionStorage` adapters maintain a per-shop index (a JSON array of session ids) that is appended to on every `storeSession` call and iterated in full on every `findSessionsByShop` call. `KVSessionStorage.addShopIds` never checks for duplicates before appending, and both adapters never cap the index size, mirroring the `activeTransactionBlocks` pattern in the referenced report: a legitimate, attacker-triggerable action repeatedly appends to an array with no bound, and a downstream loop over that array becomes progressively more expensive, eventually degrading or denying service.

### Finding Description
`storeSession` in `KVSessionStorage` always calls `addShopIds(session.shop, [session.id])`, which concatenates the new id onto the existing array without checking whether it is already present: [1](#0-0) [2](#0-1) 

`storeSession` is invoked repeatedly for the *same, deterministic* offline-session id (`offline_<shop>`, built by `getOfflineId`) from the token-exchange auth flow every time a request's cached session is missing, expired, or invalidated: [3](#0-2) 

A 401 from the Admin API (which an app frontend/user can trigger, e.g., by making an authenticated request that the shop later revokes, or simply by the token expiring) causes `invalidateAccessToken` to clear the token and call `storeSession` again for the same session id, re-triggering the append: [4](#0-3) [5](#0-4) 

Because `addShopIds` performs no `includes()` check (unlike `RedisSessionStorage.addKeyToShopList`, which does dedup), every one of these repeated `storeSession` calls for the *same* session id grows the shop's index array by one entry, forever. The array is then fully materialized and iterated with a `Promise.all` in `findSessionsByShop`: [6](#0-5) 

`findSessionsByShop` is used by `AppInstallations.includes`/`AppInstallations.delete` in the Express package, which are used in installation-check/uninstall-webhook code paths: [7](#0-6) 

The `RedisSessionStorage` variant does dedup via `includes()`, but its `findSessionsByShop` still performs a fully sequential, unbounded `for` loop with one `await` per stored id, so any unrelated unbounded growth of that shop's key list (e.g., from many distinct online sessions, one per user, each with its own random/derived id, never cleaned up) degrades linearly with no cap: [8](#0-7) 

### Impact Explanation
An app user (or the app itself under normal-but-adversarial conditions such as repeated 401s/expired tokens) can cause the KV-backed shop session index to grow without bound, since each `storeSession` for the offline session appends a duplicate id every single time with no deduplication or cap. Every subsequent call to `findSessionsByShop` (used in install-state checks and uninstall/webhook processing) must read and iterate the entire — ever-growing — key/value blob, causing increasing latency and eventually resource exhaustion/timeouts in that shop's auth-adjacent storage lookups, a Denial of Service condition scoped to session-storage-consuming code paths for that shop.

### Likelihood Explanation
Reachable via a normal, unprivileged usage pattern: any condition that causes `performTokenExchange` to treat the cached offline session as inactive/expired (which happens naturally on token expiry, or is forced on any 401 from the Admin API) triggers another `storeSession` call and thus another duplicate append, with no authentication or privilege required beyond having a working session token for the shop being targeted. No rate limiting or cap exists on this loop, making sustained triggering straightforward.

### Recommendation
- In `KVSessionStorage.addShopIds` (and any similarly structured adapter), check for existing membership before appending, as `RedisSessionStorage.addKeyToShopList` already does.
- Introduce an upper bound / TTL-based pruning on per-shop session-id index arrays, and prefer a data structure/native store feature that supports O(1) add/remove/dedup (e.g., a Set-like KV structure or the store's native list/set primitives) instead of read-modify-write of a single unbounded JSON array.
- Ensure stale/expired session ids are proactively removed from the per-shop index rather than only relying on explicit `deleteSession` calls.

### Proof of Concept
1. Configure an app to use `KVSessionStorage` with `useOnlineTokens: false` (or `true`, either path stores an offline session per token-exchange auth flow).
2. As an authenticated app user, send repeated requests through `performTokenExchange` while the session is treated as expired/invalid (e.g., simulate expiry via `WITHIN_MILLISECONDS_OF_EXPIRY` window or force a 401 from the mocked Admin API to trigger `invalidateAccessToken`).
3. Each iteration calls `config.sessionStorage.storeSession(offlineSession)` with the same `offline_<shop>` id.
4. Inspect the KV entry for `shop:<shop>` (`getShopSessionIdsKey`) after N iterations — observe it contains N duplicate copies of the same session id, confirming unbounded growth: [9](#0-8) 
5. Call `findSessionsByShop(shop)` and observe it performs N redundant `loadSession` calls via `Promise.all`, with latency scaling linearly with the number of duplicate appends, demonstrating the DoS potential in any code path that depends on this method (e.g., `AppInstallations.includes`/`delete`).

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    await this.ready;

    const idKeysArrayString = await this.client.get(shop);
    if (!idKeysArrayString) return [];

    const idKeysArray = JSON.parse(idKeysArrayString);
    const results: Session[] = [];
    for (const idKey of idKeysArray) {
      const rawResult = await this.client.get(idKey, false);
      if (!rawResult) continue;

      const session = Session.fromPropertyArray(JSON.parse(rawResult), true);
      results.push(session);
    }

    return results;
  }
