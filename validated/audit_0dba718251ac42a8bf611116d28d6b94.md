### Title
Quadratic-time `Operation` list rescan/rebuild in `AccountStore.recordBalance` allows CPU-cost/energy-charge mismatch under `historyBalanceLookup` - ([File: chainbase/src/main/java/org/tron/core/store/AccountStore.java])

### Summary
When `historyBalanceLookup` is enabled, every balance-changing `put()` on `AccountStore` (including each internal TVM balance transfer) invokes `recordBalance`, which rescans the entire `Operation` list with a stream `max()` and then rebuilds the whole `TransactionBalanceTrace` protobuf via `toBuilder().addOperation().build()`. Both operations are O(n) in the number of operations already recorded for that transaction, so n internal transfers in one transaction cost O(n²) CPU, while TVM opcode gas for balance transfers (`CALL`/native transfer) is charged at a fixed, linear-per-call rate.

### Finding Description
`AccountStore.put`/`delete` call `recordBalance(item, diff)` whenever `CommonParameter.isHistoryBalanceLookup()` is true and the account balance changed [1](#0-0) . Inside `recordBalance`, the code computes the next `operationIdentifier` by streaming over the *entire* existing operation list to find the max, then rebuilds the `TransactionBalanceTrace` by calling `toBuilder().addOperation(operation).build()` [2](#0-1) . Because `TransactionBalanceTrace` is an immutable protobuf message, `toBuilder()` and `build()` both copy the full underlying repeated `Operation` field, making each call O(n). This function is invoked once per balance mutation within a single transaction (e.g., every internal TRX transfer performed by a TVM contract via `addBalance`/`subBalance` inside `Program.java`/`RepositoryImpl`), so for a transaction that triggers n internal transfers, the store layer performs work proportional to 1+2+...+n = O(n²), while the TVM only charges linear per-transfer energy (fixed gas cost per `CALL`-style transfer opcode) that is bounded by the block/transaction energy limit. No cap exists in `recordBalance`, `BalanceTraceStore`, or `TronStoreWithRevoking` on the number of operations per `TransactionBalanceTrace`, and this path is fully reachable by an ordinary unprivileged contract deployer/caller.

### Impact Explanation
This is a CPU-cost/energy-charge asymmetry: an attacker who deploys/calls a contract that performs many native-TRX internal transfers to itself (bounded only by the energy limit per transaction/block) forces the node to do quadratic work in the balance-trace bookkeeping path, disproportionate to the energy the attacker paid. On nodes with `historyBalanceLookup` enabled, this can measurably increase per-transaction/per-block processing time relative to the energy charged, which is a resource-accounting/DoS-via-protocol-implementation concern (violates the "faithful metering" expectation that CPU cost tracks charged energy). It does not corrupt balances or forge signatures, and does not affect nodes running with default (`historyBalanceLookup` disabled) configuration.

### Likelihood Explanation
Preconditions: the node operator must have explicitly enabled `historyBalanceLookup` (not the default), a non-default configuration flag under `CommonParameter`/`Args`. Given that, an unprivileged attacker only needs to deploy/call a contract that performs many internal TRX transfers within a single transaction's energy budget — a straightforward, cheap, and fully repeatable operation requiring only normal transaction fees and energy. The severity is capped by the per-transaction/block energy limit, so the attainable n (number of operations per tx) is bounded, but the confirmed quadratic disk/CPU cost still exceeds what is charged. Because this requires a non-default configuration (`historyBalanceLookup=true`), it does not affect default node deployments, which somewhat lowers overall likelihood/blast radius across the network.

### Recommendation
Replace the O(n) rescan/rebuild pattern in `recordBalance` with an O(1) amortized approach: maintain a running `nextOperationIdentifier` counter alongside `currentTransactionBalanceTrace` in `BalanceTraceStore` (incremented on each `recordBalance` call) instead of recomputing `max()` over the list each time, and consider building the `TransactionBalanceTrace`/`Operation` list with a mutable builder retained across calls (only converting to the immutable message once, when the transaction trace is finalized in `resetCurrentTransactionTrace`) rather than calling `toBuilder().build()` on every single operation. Additionally, consider bounding the number of operations recorded per transaction (or charging additional energy proportional to internal-transfer count) if `historyBalanceLookup` is enabled, to keep CPU cost linear in charged energy.

  private void recordBalance(AccountCapsule accountCapsule, long diff) {
    TransactionBalanceTrace transactionBalanceTrace = balanceTraceStore.getCurrentTransactionBalanceTrace();

    if (transactionBalanceTrace == null) {
      return;
    }

    long operationIdentifier;
    OptionalLong max = transactionBalanceTrace.getOperationList().stream()
        .mapToLong(Operation::getOperationIdentifier)
        .max();
    if (max.isPresent()) {
      operationIdentifier = max.getAsLong() + 1;
    } else {
      operationIdentifier = 0;
    }

    ByteString address = accountCapsule.getAddress();
    Operation operation = Operation.newBuilder()
        .setAddress(address)
        .setAmount(diff)
        .setOperationIdentifier(operationIdentifier)
        .build();
    transactionBalanceTrace = transactionBalanceTrace.toBuilder()
        .addOperation(operation)
        .build();
    balanceTraceStore.setCurrentTransactionBalanceTrace(transactionBalanceTrace);
  }
