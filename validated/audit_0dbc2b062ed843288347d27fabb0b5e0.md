Order of operations in `redeem` follows burn-then-transfer (correct CEI order), so that path is not the analog. The strongest genuine single-transaction ordering issue found is the `accrue` pause pass-through combined with the timestamp-keyed index cache in `market.clar`, which is the closest match to the allowed bug classes ("a pause that passes through instead of reverting" combined with "a cached value not invalidated when its source moves").

### Title
Paused vault `accrue` silently returns stale indexes that get cached and consumed for health/liquidation math - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`accrue` in each vault contract (e.g. `mainnet/contracts/vault/v0-vault-usdc.clar:833-839`) does not revert when the `accrue` pause flag is set — it passes through and returns the *last stored* `index`/`lindex` as if they were current: `(if (get accrue states) (ok { index: idx, lindex: lidx }) ...)`. `market.clar`'s `accrue-and-cache` [1](#0-0)  takes whatever `vault-accrue` returns and unconditionally stores it in `index-cache` keyed only by `{ timestamp: stacks-block-time, aid }`. Every subsequent read in the same transaction (via `get-cached-indexes`) trusts that cached value with no re-check of the pause flag, so a stale/pass-through index becomes the authoritative value for collateral valuation, debt valuation, borrowing, and liquidation math for the remainder of the call.

### Finding Description
1. `accrue` is called at the top of `collateral-add`, `borrow`, `repay`, and `liquidate` via `accrue-and-cache`/`vault-accrue` [2](#0-1) .
2. If the underlying vault has `accrue` paused (DAO can pause per-vault via `set-pause-states`), `vault-accrue`/`accrue` returns `(ok { index: idx, lindex: lidx })` using the *last persisted* `var-get index` / `var-get lindex` rather than recomputing from `last-update`, i.e. it does not revert and does not reflect real accrued interest [3](#0-2) .
3. `accrue-and-cache` stores this pass-through value into `index-cache` for the current `stacks-block-time` with no flag indicating it is stale/frozen [1](#0-0) .
4. Every later step of the *same* market operation (e.g. `get-cached-indexes`, `convert-to-scaled-debt`, ztoken price resolution via `resolve-ztoken`, and the health checks in `borrow`/`collateral-add`/`liquidate`) reads this cached tuple as ground truth, with no re-check of `(get accrue states)` before consuming it.
5. Because the vault's `accrue` pause is a distinct switch from `deposit`/`redeem`/`borrow`/`repay` pauses, an admin (or an attacker abusing an already-paused-accrue vault) can have `borrow`/`liquidate` fully operable while `accrue` silently freezes the index used for valuing debt/collateral of that asset for the whole transaction, even though the docs claim "Always accrue before borrow/repay... Prevents stale data exploits" [4](#0-3) .

### Impact Explanation
If `accrue` is paused for a debt-bearing vault while `borrow` remains enabled, a borrower's health check in the same transaction uses a frozen (lower-than-real) `borrow-index`, understating actual debt and permitting borrowing beyond the position's real capacity — a form of temporary freezing/mis-accounting of protocol funds (insolvency risk on that vault) since actual accrued interest is not reflected in the scaled-debt conversion `convert-to-scaled-debt` for that call. This lands in the **temporary freezing of funds / protocol insolvency risk** category tied to core lending math, not a deliberate safety decision (the pass-through masks reality rather than blocking the action).

### Likelihood Explanation
Requires the vault's `accrue` pause flag to be set while `borrow`/`repay`/`liquidate` remain unpaused — a plausible operational state (e.g., DAO pausing interest-accrual updates during an oracle/index migration without also pausing borrow/liquidate), not a DAO compromise. Likelihood is Medium: it depends on an admin operational configuration rather than pure attacker control, and I could not confirm from the indexed files whether DAO tooling enforces pausing all flags together.

### Recommendation
Either have `accrue` return an error (revert) when the `accrue` pause flag is set instead of silently returning the last stored index, or have `accrue-and-cache`/all consumers of `get-cached-indexes` explicitly check and reject stale/paused index values before using them in health, borrow, or liquidation math.

### Proof of Concept
Not independently verifiable from the indexed files alone (requires runtime simulation of DAO pause-state transitions, which I could not execute). The trace above is based on static reading of `v0-vault-usdc.clar` and `v0-4-market.clar`; behavior of `set-pause-states` combined with `borrow` should be validated with `local-testing` vitest suites to confirm the exact numeric impact.

**Confidence note:** I was unable to fully trace whether DAO governance tooling always pauses `accrue` together with `borrow`/`repay`/`liquidate` (which would neutralize this issue) — this would require reviewing `dao-multisig`/`dao-executor` proposal templates, which were not returned in my searches. If such coupling is enforced, this finding should be downgraded or rejected.
