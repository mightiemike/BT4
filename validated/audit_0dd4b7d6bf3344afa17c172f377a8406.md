### Title
Mempool component's remote RPC entry point bypasses Gateway authorization and validation - ([File: crates/apollo_mempool/src/communication.rs])

### Summary
The reported CVE pattern is that a security control (an authorization/validation annotation) exists at a documentation/declaration layer but is never actually enforced on the runtime-reachable handler, letting an unauthenticated caller invoke privileged/validating logic directly. The Starknet sequencer has an analogous structural flaw: transaction authorization and validation (declarer allow-list, `block_declare`, stateless format/resource checks, and stateful balance/nonce/signature validation) are implemented only inside `apollo_gateway`'s `add_tx_inner` path, while the actual mutation point — `Mempool::add_tx` reached through `MempoolCommunicationWrapper::add_tx` — performs none of these checks. In a distributed/hybrid deployment where the Mempool runs as its own component behind a `RemoteComponentServer` (per `crates/apollo_infra/src/component_server/remote_component_server.rs`), any client capable of reaching that component's HTTP/2 endpoint can submit an `AddTransactionArgsWrapper` request straight to the mempool, skipping the Gateway entirely.

### Finding Description
`GenericGateway::add_tx_inner` in `crates/apollo_gateway/src/gateway.rs:214-298` is the only place that:
- Enforces declarer authorization/blocking via `check_declare_permissions` (`crates/apollo_gateway/src/gateway.rs:407-433`), which checks `self.config.static_config.block_declare` and `is_authorized_declarer`.
- Runs `self.stateless_tx_validator.validate(&tx)` (format, resource-bounds, size, DA-mode, proof-consistency checks).
- Runs stateful validation (`extract_state_nonce_and_run_validations`), which invokes the Blockifier's `validate` entry point (balance, signature, account nonce correctness).

None of this logic exists inside the Mempool crate. `MempoolCommunicationWrapper::add_tx` (`crates/apollo_mempool/src/communication.rs:120-142`) only performs FIFO block-metadata bookkeeping and then calls `self.mempool.add_tx(args_wrapper.args.clone())`, which in turn (`crates/apollo_mempool/src/mempool.rs:466-514`) only validates nonce ordering, fee escalation, and pool capacity — never authorization or signature/format soundness.

The component framework (`apollo_infra`) supports exposing the Mempool as an independent, network-reachable component via `RemoteComponentServer`, whose documented protections (per the Component Client/Server Framework wiki) are limited to body-size limits, keepalive/connection eviction, and priority queuing — there is no authentication or caller-identity enforcement described or found in `remote_component_server.rs`. Consequently, in any deployment topology where the Mempool component's remote endpoint is reachable independently of the Gateway's HTTP server (hybrid/distributed topologies are explicitly supported, per `deployments/sequencer/docs` and `crates/apollo_deployments`), the authorization check that is supposed to gate every transaction (especially the declarer allow-list and `block_declare` circuit breaker) can be trivially bypassed by talking to the Mempool component directly with a crafted `MempoolRequest::AddTx`.

### Impact Explanation
An attacker who can reach the Mempool component's remote endpoint (its own bound IP:port distinct from the Gateway's HTTP server) can:
- Submit `Declare` transactions from addresses that are explicitly *not* in `authorized_declarer_accounts`, defeating the `UnauthorizedDeclare` control (`crates/apollo_gateway/src/gateway.rs:420-431`, tested in `gateway_test.rs:798-820`).
- Submit transactions even while `block_declare` is set (an operational kill-switch), defeating `test_block_declare_config` semantics.
- Inject transactions that never passed stateless validation (oversized signatures, invalid resource bounds, malformed DA modes) or stateful validation (unsigned/invalid `validate()` entry point execution, insufficient balance) directly into the pool, from where the Batcher later includes them in a block proposal (`get_txs` in `mempool.rs`) and Blockifier execution processes them.

This can cause the sequencer to admit and later execute or attempt to execute unauthorized/invalid transactions, producing incorrect execution results, wasted/incorrect fee accounting, or inconsistent mempool/consensus state between nodes that do vs. don't expose the mempool directly — a form of unauthorized account action and honest-node divergence risk if such nodes propose blocks containing improperly-validated transactions.

### Likelihood Explanation
Exploitability is contingent on deployment topology: if the Mempool component is run in `Local` execution mode within the same process as Gateway (as in the default consolidated topology), this path is not externally reachable and the finding does not apply. However, the codebase explicitly supports and documents hybrid/distributed topologies where components including the Mempool run as separate services accessed via `RemoteComponentClient`/`RemoteComponentServer`, and the remote server enforces no caller authentication — only size/connection limits. In such topologies (which the project markets as a first-class deployment mode), this is directly and trivially reachable by any network client that can resolve the mempool's configured host/port, requiring only a validly-serialized `AddTransactionArgsWrapper`/`MempoolRequest` — no signature or credential of any kind.

### Recommendation
- Move (or duplicate) the authorization and validation checks — `check_declare_permissions`, `StatelessTransactionValidator::validate`, and the stateful `validate()` call — into the Mempool's `add_tx` handling path itself (or into the `RemoteComponentServer`/`ComponentRequestHandler` layer as a mandatory pre-dispatch hook for `MempoolRequest::AddTx`), so that authorization is enforced regardless of ingress route.
- Alternatively/additionally, ensure that in every supported deployment topology the Mempool component's remote endpoint is never independently reachable by untrusted clients (e.g., restrict its listener to internal-only network paths and require mutual authentication for inter-component RPC), and add an explicit runtime assertion/test that fails a build/deployment if a `Declare`/`Invoke`/`DeployAccount` transaction can reach `Mempool::add_tx` without having first passed through Gateway's `add_tx_inner`.
- Add integration tests analogous to `test_unauthorized_declare_config` and `test_block_declare_config` that submit transactions via the Mempool's remote/component-client interface directly (bypassing Gateway) and assert they are rejected.

### Proof of Concept
1. Deploy the sequencer in a hybrid/distributed topology where `apollo_mempool` runs as an independent component with its own `RemoteComponentServer` (per supported config in `crates/apollo_node/resources/config_schema.json` and `crates/apollo_deployments`).
2. Configure the Gateway with `authorized_declarer_accounts = [0x1]` and/or `block_declare = true`.
3. From an external client (not the Gateway), construct a `MempoolRequest::AddTx(AddTransactionArgsWrapper { args: AddTransactionArgs { tx: <Declare tx from unauthorized address>, account_state }, p2p_message_metadata: None })`, bincode-serialize it, and POST it directly to the Mempool's `RemoteComponentServer` HTTP/2 endpoint.
4. Observe that `MempoolCommunicationWrapper::add_tx` → `Mempool::add_tx` accepts the transaction (subject only to nonce/fee/capacity checks), despite the Gateway's `check_declare_permissions` and `block_declare`/allow-list settings that would have rejected it — confirming the authorization/validation bypass.     fn check_declare_permissions(
        &self,
        declare_tx: &RpcDeclareTransaction,
    ) -> Result<(), StarknetError> {
        // TODO(noamsp): Return same error as in Python gateway.
        if self.config.static_config.block_declare {
            return Err(StarknetError {
                code: StarknetErrorCode::UnknownErrorCode(
                    "StarknetErrorCode.BLOCKED_TRANSACTION_TYPE".to_string(),
                ),
                message: "Transaction type is temporarily blocked.".to_string(),
            });
        }
        let RpcDeclareTransaction::V3(declare_v3_tx) = declare_tx;
        if !self.config.is_authorized_declarer(&declare_v3_tx.sender_address) {
            return Err(StarknetError {
                code: StarknetErrorCode::KnownErrorCode(
                    KnownStarknetErrorCode::UnauthorizedDeclare,
                ),
                message: format!(
                    "Account address {} is not allowed to declare contracts.",
                    &declare_v3_tx.sender_address
                ),
            });
        }
        Ok(())
    }

    ) -> MempoolResult<()> {

            let tx_hash = args_wrapper.args.tx.tx_hash();
            if !self.fetch_and_update_tx_block_metadata(tx_hash).await {
                warn!("Failed to fetch tx block metadata for tx {}, skipping transaction", tx_hash);
                return Ok(());
            }
        }

        self.mempool.add_tx(args_wrapper.args.clone())?;

        // TODO(AlonH): Verify that only transactions that were added to the mempool are sent.
        if let Err(p2p_client_err) =
            self.send_tx_to_p2p(args_wrapper.p2p_message_metadata, args_wrapper.args.tx).await
        {
            warn!("Failed to send transaction to P2P: {:?}", p2p_client_err);
        }

        Ok(())
    }

    pub fn add_tx(&mut self, args: AddTransactionArgs) -> MempoolResult<()> {
        // First remove old transactions from the pool.
        let mut account_nonce_updates = self.remove_expired_txs();
        if !self.is_fifo() {
            self.add_ready_declares();
        }

        let tx_reference = TransactionReference::new(&args.tx);
        self.add_tx_validations(tx_reference, &args.tx, args.account_state.nonce)
            .inspect_err(|err| self.log_add_tx_error(err, &args))?;

        MEMPOOL_TRANSACTIONS_RECEIVED.increment(
            1,
            &[(LABEL_NAME_TX_TYPE, InternalRpcTransactionLabelValue::from(&args.tx.tx).into())],
        );

        // May override a removed queued nonce with the received account nonce or the account's
        // state nonce.
        account_nonce_updates.insert(
            args.account_state.address,
            self.state.resolve_nonce(args.account_state.address, args.account_state.nonce),
        );

        let should_delay_declare =
            matches!(&args.tx.tx, InternalRpcTransactionWithoutTxHash::Declare(_))
                && !self.is_fifo();
        if should_delay_declare {
            self.delayed_declares.push_back(self.clock.now(), args);
        } else {
            self.add_tx_inner(args);
        }

        self.update_accounts_with_gap(account_nonce_updates);
        self.update_state_metrics();
        Ok(())
    }

#[rstest]
#[tokio::test]
async fn test_unauthorized_declare_config(mut mock_dependencies: MockDependencies) {
    let authorized_address = contract_address!("0x1");
    mock_dependencies.config.static_config.authorized_declarer_accounts =
        Some(vec![authorized_address]);

    let gateway = mock_dependencies.gateway();
    let rpc_declare_tx = declare_tx();

    // Ensure the sender address is different from the authorized address.
    assert_ne!(
        rpc_declare_tx.calculate_sender_address().unwrap(),
        authorized_address,
        "Sender address should not be authorized"
    );

    let gateway_output_code_error = gateway.add_tx(rpc_declare_tx, None).await.unwrap_err().code;
    let expected_code_error =
        StarknetErrorCode::KnownErrorCode(KnownStarknetErrorCode::UnauthorizedDeclare);

    assert_eq!(gateway_output_code_error, expected_code_error);
}
