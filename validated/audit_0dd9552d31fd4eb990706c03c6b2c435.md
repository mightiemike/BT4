### Title
Single-slot `NativeCodeContext.requested_module_bundle` lets a multi-call script desynchronize `PackageRegistry` metadata from the actually-published module bytecode - (File: `aptos-move/framework/natives/src/code.rs`)

### Summary
`NativeCodeContext` stores at most one pending publish request in `requested_module_bundle: Option<PublishRequest>` [1](#0-0) . It is only cleared at session `start()` and consumed once via `extract_publish_request()` [2](#0-1) . The Move entrypoint `code::publish_package` is a `public fun` (not `entry`), so it can be invoked more than once inside a single Move script/multi-agent transaction. Each call to `publish_package` first mutates the on-chain `PackageRegistry` resource and emits a `PublishPackage` event, then calls the native `request_publish`/`request_publish_with_allowed_deps` [3](#0-2) .

### Finding Description
Because the native context holds only a single `Option<PublishRequest>` slot, a second call to `request_publish` within the same transaction overwrites the first. When the VM later resolves the pending publish via `resolve_pending_code_publish_and_finish_user_session`, it calls `session.extract_publish_request()` exactly once and processes only the surviving (last) `PublishRequest` [4](#0-3)  and [5](#0-4) .

Meanwhile, `code.move`'s `publish_package` already committed the first call's registry mutation (adding the first package's `PackageMetadata` into `PackageRegistry` at the first destination address) and emitted its `PublishPackage` event before the native call is even reached [6](#0-5) . Those resource writes and events are captured by the Move VM data cache/event context regardless of which `PublishRequest` ultimately survives in the native extension slot.

The result: the first target address's `PackageRegistry` resource (and the write set derived from it) is durably updated to claim a package/module set exists there, and a `PublishPackage` event is emitted for it — but the actual module bytecode for that package is never written to the module write set, because only the second (overwriting) `PublishRequest`'s bundle is processed.

### Impact Explanation
This causes committed on-chain resource state (`PackageRegistry`) to reference modules that were never actually deployed to code storage for the first-processed package. This is not merely an "event-only mismatch" — the durable `PackageRegistry` resource state itself is corrupted relative to correct VM semantics (metadata says code exists; code storage disagrees), and any later attempt to load/execute those "registered" modules, or govern by upgrade_number, would be based on state disconnected from actual code. It also affects package-dependency/coexistence bookkeeping (`check_coexistence`/`check_upgradability`) for subsequent publishes at that address, since the registry entry exists without matching bytecode.

### Likelihood Explanation
The requesting party must be able to construct a Move script/multi-agent transaction calling `code::publish_package` (or `publish_package_object`/similar wrappers, if they exist) more than once, targeting distinct destination addresses in one transaction, each with signer authority over those addresses (self-published or multi-agent signers). No privileged operator action is required — only unprivileged transaction submission with valid signer capability over each target address is needed, matching the "unprivileged transaction ... bytecode ... input" scope.

### Recommendation
Make `NativeCodeContext` reject or accumulate multiple publish requests instead of silently overwriting: return an error (e.g. `E_MULTIPLE_PUBLISH_REQUESTS_IN_ONE_TRANSACTION`) from `request_publish`/`request_publish_with_allowed_deps` if `requested_module_bundle` is already `Some(..)`, or extend `NativeCodeContext` to hold a collection of `PublishRequest`s and have `resolve_pending_code_publish_and_finish_user_session` process all of them, ensuring every `PublishPackage` event corresponds to an actually-written module bundle.

### Proof of Concept
1. Craft a Move script (or multi-agent transaction) with two signers `s1` (owns `addr1`) and `s2` (owns `addr2`).
2. Script body: `code::publish_package(s1, metadata1, code1); code::publish_package(s2, metadata2, code2);`
3. During execution, `PackageRegistry` at `addr1` is updated with `metadata1`, event `PublishPackage{addr1,...}` is emitted, native slot set to `PublishRequest(addr1, code1, ...)`.
4. Second call updates `PackageRegistry` at `addr2` with `metadata2`, emits `PublishPackage{addr2,...}`, and overwrites the native slot with `PublishRequest(addr2, code2, ...)`.
5. `resolve_pending_code_publish_and_finish_user_session` extracts only the `addr2` request; the module write set contains only `code2`'s bytecode for `addr2`.
6. Post-commit: `PackageRegistry` at `addr1` lists modules from `metadata1` and an emitted `PublishPackage` event claims success, yet no bytecode for those modules was ever written to code storage at `addr1`.

**Verification caveat:** the exact body of the native `request_publish`/`request_publish_with_allowed_deps` functions (lines ~39-190 of `code.rs`) was not retrievable through the available search/read tools (index truncation), so I could not directly confirm the absence of an `is_some()` guard in that specific function body — this conclusion is inferred from the `Option<PublishRequest>` field type, its reset-only-on-`start()` lifecycle [2](#0-1) , and the single `extract_publish_request()` consumption point in the VM [4](#0-3) . A Devin session with full file access would be needed to confirm the exact native function body before treating this as fully verified.
