### Title
`liquidity_cap` on `TokenConfig` is stored but never enforced during PRC20 deposit minting - (File: x/uexecutor/keeper/handler.go)

### Summary
`TokenConfig.LiquidityCap` is the Push Chain analog of `expectedLiquidityLimit`: a string-encoded `big.Int` value meant to bound how much of a given cross-chain asset can be represented as PRC20 on Push Chain. `ValidateBasic` only checks the field is a non-empty string, never that it parses to a positive integer, and the actual deposit/minting path (`depositPRC20` → `CallPRC20Deposit`) never reads or compares against `LiquidityCap` at all.

### Finding Description
`TokenConfig.LiquidityCap` is defined as `// max supply cap for this token (string big.Int format)` [1](#0-0)  and validated only for non-emptiness: [2](#0-1) 

This means an admin-set (or even genesis-default) `LiquidityCap` of `"0"` passes `ValidateBasic` unchanged — the same class of defect as `expectedLiquidityLimit` being left at zero because no positivity check exists.

More importantly, unlike the referenced Gearbox bug (which is about the value being uninitialized), here the deeper problem is that the field is entirely decorative: nowhere in the deposit/mint path is `LiquidityCap` read. `depositPRC20` looks up the `TokenConfig` only to resolve the PRC20 contract address, then calls `CallPRC20Deposit` with the raw inbound `amount`, with no cap comparison: [3](#0-2) 

`ExecuteInboundFunds` similarly passes the inbound amount straight to `depositPRC20` without any supply-cap check: [4](#0-3) 

A grep across `x/uexecutor/keeper/*.go` confirms `LiquidityCap`/`totalSupply` are never referenced in the deposit-related keeper files beyond the registry lookup — the cap field is written to state and returned by `AllTokenConfigs`/`TokenConfig` queries, but plays no role in gating how much PRC20 supply an inbound flow can mint.

### Impact Explanation
If `LiquidityCap` is intended (per the field's own comment) to bound total PRC20 supply per external asset, its absence from the enforcement path means an ordinary user submitting honestly-voted, quorum-finalized inbound deposits (no privileged action, no malicious validators required) can mint PRC20 supply for a token without any bound tied to `liquidity_cap`. This is a corruption-of-accounting issue matching the "Registry and accounting path" pivot: PRC20 minting is decoupled from the token-config value that is supposed to constrain it, undermining whatever risk/backing assumption `liquidity_cap` was meant to encode (e.g., limiting exposure to an under-collateralized or newly-added asset). Depending on how the value is consumed by off-chain risk tooling or future features, this could allow unbounded unauthorized minting relative to intended limits — a native analog of the "cap variable exists but has no effect" bug class from the report.

### Likelihood Explanation
High likelihood of the gap being reachable: any ordinary, honestly-voted inbound `FUNDS`/`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` deposit that reaches quorum triggers `depositPRC20` regardless of accumulated PRC20 supply versus `LiquidityCap`, since no code path reads that field during minting. This requires no privileged actor, malicious validator, or edge-case config — it is the default behavior of every deposit.

### Recommendation
Enforce `LiquidityCap` at mint time: before calling `CallPRC20Deposit`, look up (or track) the current total minted supply for the PRC20 representation of `(sourceChain, assetAddr)` and reject/cap the deposit if `currentSupply + amount > LiquidityCap`. Additionally, harden `TokenConfig.ValidateBasic` to parse `LiquidityCap` as a `big.Int` and reject non-positive or unparseable values, mirroring the constructor-time fix recommended in the source report.

### Proof of Concept
Not directly exploitable as a "drain funds" PoC from the available indexed code — this is a missing-enforcement gap rather than a broken check. Reproduction path: (1) admin adds a `TokenConfig` with any `LiquidityCap` (including `"0"`, which passes `ValidateBasic`); (2) submit repeated honestly-voted inbound `FUNDS` events for that `(chain, asset)` pair, each reaching quorum via `VoteInbound`; (3) observe via `x/uregistry` queries that `LiquidityCap` never changes and `depositPRC20`/`CallPRC20Deposit` (`x/uexecutor/keeper/handler.go:12-46`, `x/uexecutor/keeper/execute_inbound_funds.go:24-30`) mint PRC20 for every such deposit with no comparison against `LiquidityCap`, regardless of cumulative minted amount.

**Uncertainty note:** I was not able to fully trace whether `LiquidityCap` is enforced elsewhere (e.g., inside the PRC20 smart contract itself, off-chain by Universal Validators before voting, or in a component not covered by the indexed search results). Due to index size limits, some file contents (particularly the PRC20 contract source, if it lives in a separate contracts repo, and any economics/risk-module code) may not be available here. If `LiquidityCap` enforcement genuinely lives entirely off-chain or in an external contracts repository outside this codebase's index, this finding's severity should be reassessed — I recommend confirming with a full-repository Devin session before treating this as a definitive vulnerability.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```
