### Title
Unbounded duplicate growth in Cloudflare KV shop-session index due to missing existence check before array push - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.addShopIds` appends a session id into the shop's session-id index array without checking whether that id is already present, unlike the sibling Redis implementation which explicitly deduplicates before pushing.

### Finding Description
`storeSession` unconditionally calls `addShopIds(session.shop, [session.id])` on every store, and `addShopIds` simply concatenates the new id onto whatever list is already stored under the `shop:<shop>` key without checking for an existing entry: [1](#0-0) [2](#0-1) 

This is the same root-cause pattern as the reported bug class: pushing a value into an array without checking whether it already exists, so the same identifier can appear multiple times in the index array. By contrast, the Redis adapter for the same interface explicitly guards against this: [3](#0-2) 

`storeSession` for a given session id is not a one-time event — it is re-invoked on every OAuth re-authentication and, notably, on every token-exchange flow whenever the cached session is missing or near expiry (an unprivileged, normal-usage path reachable by any embedded-app request from a merchant/customer): [4](#0-3) 

Each such call re-appends the same `session.id` to the shop's KV index array, so the array grows without bound as long as the session keeps needing to be refreshed (expired online tokens, repeated re-auth attempts, etc.). `findSessionsByShop` then iterates the entire (growing, duplicate-laden) id list and issues one KV `get` per entry: [5](#0-4) 

### Impact Explanation
Unlike the original Solidity bug (where a stale/zero-amount entry is silently used instead of the real one), here `loadSession(id)` always fetches the latest value for a given key, so the duplicate ids do not by themselves cause incorrect session data to be used. The concrete impact is instead:
- Unbounded growth of the `shop:<shop>` KV value with duplicate ids, eventually risking KV value-size limits and write failures for `storeSession`/`addShopIds`.
- Increasingly expensive `findSessionsByShop` calls (O(n) redundant KV `get`s and duplicated `Session` objects returned), degrading or ultimately denial-of-servicing this session-storage/auth-adjacent handler for a shop that re-authenticates frequently.

This does not on its own enable a forged session, cross-tenant access, or credential leakage — it is a resource-exhaustion / correctness-degradation issue confined to the KV adapter's shop index.

### Likelihood Explanation
Moderate. It requires no attacker privilege beyond normal, expected traffic patterns already built into the framework (token exchange runs automatically whenever a cached session token session is absent or near expiry), so it can occur organically for any shop using `@shopify/shopify-app-session-storage-kv`, and can be accelerated by an attacker or bot repeatedly forcing re-authentication/token-exchange flows for the same shop.

### Recommendation
Mirror the Redis adapter's approach: before pushing, check whether the id is already present in the `shopIds` array (e.g. `Set`-based dedupe) in `addShopIds`, and consider deduplicating on read in `findSessionsByShop` as a defense-in-depth measure.

### Proof of Concept
1. Configure an embedded app using `KVSessionStorage` for session storage.
2. Simulate repeated near-expiry/expired session token exchanges for the same shop (as happens naturally via `TokenExchangeStrategy.authenticate` whenever `session.isActive(...)` is false), each call invoking `config.sessionStorage.storeSession(offlineSession)` with the same `session.id`.
3. After N repeated exchanges, inspect the KV value under key `shop:<shop>` — it will contain the same session id N times instead of once.
4. Call `findSessionsByShop(shop)` and observe N KV `get` calls and N duplicate `Session` objects returned for what should be a single session, demonstrating unbounded growth/resource cost as re-authentication frequency increases.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }
