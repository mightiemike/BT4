## Title
Attacker-controlled isCEA inbound `Recipient` of the EVM zero address bypasses UEA/contract routing and permanently locks minted PRC20 funds - (File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go)

### Summary
For `isCEA` inbounds, the `Recipient` field is taken verbatim from the source-chain gateway event (fully attacker-controlled, since the attacker calls the gateway contract on the external chain and can set the recipient argument to anything). `ValidateForExecution` only checks that the recipient is a non-empty, well-formed hex string via `utils.IsValidAddress(p.Recipient, utils.HEX)` [2](#0-1) , which accepts the zero address `0x000...000`. Nothing downstream rejects `address(0)` before `depositPRC20` mints PRC20 tokens to it.

### Finding Description
In `ExecuteInboundFundsAndPayload` (and the analogous `ExecuteInboundGasAndPayload`), when `IsCEA` is true, the recipient is taken directly from `utx.InboundTx.Recipient` and converted to `ueaAddr := common.HexToAddress(...)` with only a `"0x"` prefix check, no zero-address check [3](#0-2) . The keeper then calls `CallFactoryGetOriginForUEA` to see if the address is a known UEA; the zero address is never a registered UEA, so `isUEA` is `false`, and the code falls into the "EOA" branch (`GetCodeHash` for `address(0)` is empty), which still calls `depositPRC20(..., ueaAddr, ...)` unconditionally when `inboundAmount.Sign() > 0` [4](#0-3) . `depositPRC20` resolves the token config and calls `CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)` which issues a `DerivedEVMCall` to the PRC20 contract's `depositPRC20Token(prc20Address, amount, to)` with `to = address(0)` [5](#0-4) [6](#0-5) .

This mirrors the `M-02` bug class: the analog invariant here is "PRC20 mint destination must never be `address(0)`." Whether this results in an actual on-chain revert depends on the (out-of-repo) PRC20/Handler Solidity contract's own zero-address guard in `depositPRC20Token`/ERC20 mint logic — that contract is not part of this repository's scope and could not be inspected here, so it is uncertain whether the EVM call reverts or silently mints to the burn address. If the PRC20 contract does not itself guard against `to == address(0)` (many minimal ERC20 mint implementations don't), the deposited PRC20 balance becomes permanently unspendable/burned, since the depositor was never authenticated as owning the zero address and there is no path to recover funds sent there. Because this is an `isCEA` inbound, the failure path (`execErr` only set for `CallFactoryGetOriginForUEA`/other explicit errors) does **not** create an `INBOUND_REVERT` outbound — the code comment explicitly states "isCEA failures never create an INBOUND_REVERT outbound" — and a successful deposit-to-zero is not even treated as a failure, so no refund flow is triggered at all.

### Impact Explanation
If the underlying PRC20 contract permits minting to `address(0)`, this results in permanent, unrecoverable loss of user-bridged funds triggerable by any external actor with no privileged access — simply by crafting a source-chain gateway event with `recipient = 0x000...000`. This matches the in-scope "permanent loss ... of user or protocol-controlled funds" and "corruption of PRC20 ... accounting" categories.

### Likelihood Explanation
Low-to-Medium: it requires (a) the PRC20/Handler contract's `depositPRC20Token` to not itself validate `to != address(0)`, which is outside this repository's scope and unverified here, and (b) the attacker to deliberately craft a malformed/self-harming gateway call, since the funds lost would typically be the attacker's own bridged deposit (self-griefing) unless combined with a scenario where a third party's funds get routed to the zero address, e.g. an inbound where the source-chain event's recipient field is misparsed or defaulted. The chain-side code offers no defense-in-depth regardless of the contract's behavior.

### Recommendation
Add an explicit zero-address check in `Inbound.ValidateForExecution()` for the `isCEA` recipient path (and mirror it in the `TxType_FUNDS`/`TxType_GAS` recipient check), rejecting `Recipient == types.EvmZeroAddress` alongside the existing `utils.IsValidAddress` check, so malformed/zero recipients produce a `FAILED` PCTx (and revert outbound, where applicable) instead of silently reaching `depositPRC20`.

### Proof of Concept
1. Attacker calls the external-chain gateway contract's deposit method, setting the emitted event's recipient field to `0x0000000000000000000000000000000000000000`, `IsCEA = true`, `TxType = FUNDS_AND_PAYLOAD` (or `FUNDS`/`GAS_AND_PAYLOAD`), and a positive amount.
2. Honest Universal Validators observe and vote `MsgVoteInbound` with this data; `ValidateBasic` passes (no recipient check) [7](#0-6) ; post-quorum `ValidateForExecution` passes because `IsValidAddress("0x000...000", HEX)` returns `true` [2](#0-1) .
3. `ExecuteInboundFundsAndPayload` treats `address(0)` as a non-UEA EOA and calls `depositPRC20` with `to = address(0)` [8](#0-7) .
4. `CallPRC20Deposit` issues the mint via `DerivedEVMCall("depositPRC20Token", prc20Address, amount, address(0))` [9](#0-8) .
5. If the PRC20 contract does not reject `to == address(0)`, the tokens are minted to the zero address and are permanently unspendable; the UTX shows a "SUCCESS" PCTx and no revert outbound is scheduled since `isCEA` suppresses reverts.

func IsValidAddress(addr string, at AddressType) bool {
	switch at {
	case COSMOS:
		_, err := sdk.AccAddressFromBech32(addr)
		return err == nil
	case HEX:
		return common.IsHexAddress(addr)
	case EITHER:
		_, err := ConvertAnyAddressToBytes(addr)
		return err == nil
	default:
		return false
	}
}

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
