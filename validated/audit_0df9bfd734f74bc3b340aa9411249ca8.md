### Title
Unbounded `GetAssetIssueList` RPC/HTTP endpoint enables memory/response-size DoS - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`Wallet.getAssetIssueList()` retrieves and serializes **every** `AssetIssueCapsule` stored in the node's asset-issue database with no cap on the number of items returned. This method is directly reachable via the anonymous, unauthenticated gRPC call `GetAssetIssueList (EmptyMessage) returns (AssetIssueList)` and the equivalent HTTP endpoint `/wallet/getassetissuelist`, on both the FullNode and SolidityNode/PBFT wallets. This mirrors the reported CoreDAO `ReadHeaderRange` issue: a range/collection accessor with no sanity limit, reachable from an anonymous request, that can be abused to exhaust node resources.

### Finding Description
`Wallet.getAssetIssueList()` calls `AssetIssueStore.getAllAssetIssues()` (or `getAssetIssueStoreFinal(...).getAllAssetIssues()`), which does a full iteration over the underlying store and materializes the entire result set into a `List<AssetIssueCapsule>` in memory: [2](#0-1) 

`getAssetIssueList()` then iterates this full, unbounded list, running `BandwidthProcessor.updateUsage` per item and building a single `AssetIssueList` protobuf response containing every asset issue on the chain: [1](#0-0) 

Unlike the sibling method `getAssetIssueList(offset, limit)` (backing `GetPaginatedAssetIssueList`), which is capped via `AssetIssueStore.getAssetIssuesPaginated` and `ASSET_ISSUE_COUNT_LIMIT_MAX` (see `Commons.ASSET_ISSUE_COUNT_LIMIT_MAX`), the non-paginated `getAssetIssueList()` has no such bound. It is exposed unauthenticated through multiple transports:
- gRPC `Wallet/GetAssetIssueList`, `WalletSolidity/GetAssetIssueList`, `WalletPBFT/GetAssetIssueList` (`RpcApiService.java` lines 1756-1761 and the Solidity/PBFT delegation wrappers).
- HTTP `GetAssetIssueListServlet` (`/wallet/getassetissuelist`), which simply forwards to `wallet.getAssetIssueList()` with no query-time limit: [4](#0-3) 

Because token/asset issuance count on TRON grows over time and any account can issue new assets, the size of the underlying store — and therefore the size of every `GetAssetIssueList` response and the memory/CPU cost of computing it — is attacker-influenceable and grows unboundedly, with no per-call cap comparable to `BLOCK_LIMIT_NUM` (used by `getBlockByLimitNext`) or `WITNESS_COUNT_LIMIT_MAX` (used by `getPaginatedNowWitnessList`).

### Impact Explanation
Repeated anonymous calls to `GetAssetIssueList` force the node to iterate the full asset-issue key space, build a full in-memory capsule list, run bandwidth-usage accounting on every entry, and serialize the entire set into a single protobuf/JSON response on every call. As the number of issued assets increases, this becomes an increasingly expensive, unbounded operation that can degrade or exhaust node CPU/memory/network resources, causing a denial of service condition for the RPC/HTTP API — consistent with the accepted risk class described in the reference report (unbounded accessor invoked without a sanity limit).

### Likelihood Explanation
The endpoint requires no authentication or special privilege — it is a plain `EmptyMessage` RPC/HTTP GET reachable by any client. Likelihood of abuse is straightforward: an attacker only needs network access to the node's API port and can issue the request repeatedly or concurrently to amplify load; the underlying dataset size itself can also be inflated over time simply by issuing many assets on-chain (a permissionless action, subject only to the normal asset-issue fee), which permanently increases the cost of every subsequent unauthenticated `GetAssetIssueList` call.

### Recommendation
Apply the same limiting technique already used elsewhere in the codebase (e.g. `ASSET_ISSUE_COUNT_LIMIT_MAX` in `getAssetIssueList(offset, limit)` / `AssetIssueStore.getAssetIssuesPaginated`, `BLOCK_LIMIT_NUM` in `getBlockByLimitNext`) to the unpaginated `getAssetIssueList()` accessor: either deprecate/remove the unbounded RPC/HTTP path in favor of the paginated variant, or internally cap the number of entries returned/iterated per call, and/or require callers to use `GetPaginatedAssetIssueList`.

### Proof of Concept
1. Populate (or wait for organic growth of) a large number of asset issues in the target node's `asset-issue` store (permissionless, e.g. via repeated `AssetIssueContract` transactions).
2. Send repeated anonymous requests: `curl http://<node>:8090/wallet/getassetissuelist` or a gRPC `GetAssetIssueList(EmptyMessage)` call.
3. Observe that each call triggers a full store iteration, per-item bandwidth accounting, and a full-size serialized response with no limit, unlike `GetPaginatedAssetIssueList`/`GetBlockByLimitNext`, which enforce `ASSET_ISSUE_COUNT_LIMIT_MAX`/`BLOCK_LIMIT_NUM`. Repeating this concurrently amplifies CPU/memory/network load on the node.

  public AssetIssueList getAssetIssueList() {
    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();

    getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
        chainBaseManager.getAssetIssueStore(),
        chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues()
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }
