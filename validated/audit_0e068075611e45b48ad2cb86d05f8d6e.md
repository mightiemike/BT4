## Finding

### Title
Chunky DKG `encryption_key` is not covered by the aggregate signature and its re-derivation check is silently skipped without `DIGEST_KEY`, letting an unauthenticated key reach committed state and the API - (File: `types/src/dkg/chunky_dkg.rs`, `aptos-move/aptos-vm/src/validator_txns/chunky_dkg.rs`, `api/types/src/transaction.rs`)

### Summary
`CertifiedChunkyDKGOutput` bundles a quorum-signed `certified_transcript` with a separate, **unsigned** `encryption_key` field. The only code path that binds `encryption_key` to the transcript is a re-derivation check in `AptosVM::process_chunky_dkg_result_inner`, and that check is conditionally executed only `if let Some(digest_key) = DIGEST_KEY.as_ref()`. Because fullnodes are *designed* to never load a `DIGEST_KEY` ("Non-validator nodes (fullnodes) should not have a digest key since they don't participate in decryption"), any node lacking the key accepts and commits whatever `encryption_key` value is present in the transaction, unchecked. The API layer then echoes this on-chain value verbatim as `HexEncodedBytes` in `ChunkyDKGResultTransaction`, with no independent verification.

### Finding Description
The multi-signature verification only covers the deserialized transcript, not the encryption key: [1](#0-0) 

The subsequent check that ties `encryption_key` to the certified transcript is gated behind local key availability, and is skipped entirely otherwise ("trust consensus"): [2](#0-1) 

Whichever value survives (verified or not) is then passed directly into the Move function that commits it into ledger state: [3](#0-2) 

`DIGEST_KEY` resolution is explicitly documented to be absent for fullnodes by design, and can also be `None` for a validator if the blob file is missing/misconfigured or fails to deserialize: [4](#0-3) [5](#0-4) 

The raw, on-chain `CertifiedChunkyDKGOutput.encryption_key` is then surfaced by the API completely unchecked, straight from the committed `ValidatorTransaction` variant: [6](#0-5) [7](#0-6) 

The struct definitions confirm the binding gap at the data-model level: `encryption_key` is a sibling field of `certified_transcript`, not part of the signed `CertifiedAggregatedChunkySubtranscript`: [8](#0-7) 

### Impact Explanation
This breaks the invariant that all deterministic-VM-execution nodes must reach identical `TransactionStatus`/write-set results for the same input. A node without `DIGEST_KEY` (by design, every fullnode) will `Executed`-commit an `encryption_key` that a node with `DIGEST_KEY` would have `Discard`ed via `ExpectedFailure::EncryptionKeyMismatch`. That is a hard-fork-class divergence in committed ledger state for the on-chain Chunky DKG resource, not merely a display bug. In addition, the authenticated `ChunkyDKGResultTransaction` API object is bound to an `encryption_key` value that has no cryptographic tie to the quorum-certified `certified_transcript` it is packaged with, so unprivileged REST clients can receive a key that is not actually the one the validator quorum agreed to via `certified_transcript`'s signature.

### Likelihood Explanation
Any of the following unprivileged/uncontrolled trigger conditions suffice: (a) a fullnode replaying/bootstrapping the ledger (guaranteed to lack `DIGEST_KEY`), or (b) any validator whose digest-key blob file is missing/corrupted (`DIGEST_KEY` silently becomes `None` rather than erroring hard), or (c) a single proposer/relay reassembling `CertifiedChunkyDKGOutput` with a mismatched `encryption_key` next to an honestly quorum-signed transcript, since the signature never covers that field. None of these require compromising a majority of validators or trusted governance — the field is structurally unauthenticated.

### Recommendation
- Include `encryption_key` inside the data that is multi-signed by the validator quorum (e.g., fold it into `AggregatedSubtranscript`/the signed payload) so the aggregate signature cryptographically binds both fields together.
- Make the re-derivation check unconditional/mandatory for any node performing real VM execution/commit; if `DIGEST_KEY` is unavailable, the transaction must be treated as unverifiable and not committed as `Executed`, rather than silently trusted.
- Before serializing `ChunkyDKGResultTransaction` in the API, do not simply pass through `dkg_output.encryption_key`; instead surface (or additionally expose) the fact of whether that key is signature-bound, so API consumers cannot be misled by an unauthenticated value.

### Proof of Concept
1. Take a legitimately quorum-signed `CertifiedAggregatedChunkySubtranscript` (correct `transcript_bytes` + valid `AggregateSignature`).
2. Construct `CertifiedChunkyDKGOutput { certified_transcript, encryption_key: <arbitrary_bytes> }` where `encryption_key != AggregatedSubtranscript::derive_encryption_key_bytes(...)`.
3. Feed this into `AptosVM::process_chunky_dkg_result` on a node where `DIGEST_KEY` is `None` (e.g., any fullnode, per `initialize_digest_key`'s documented behavior in `types/src/dkg/chunky_dkg.rs:258-277`) — the `if let Some(digest_key) = DIGEST_KEY.as_ref()` branch at `aptos-move/aptos-vm/src/validator_txns/chunky_dkg.rs:159-168` is skipped, `FINISH_WITH_CHUNKY_DKG_RESULT` executes and commits the arbitrary key.
4. Query that node's transactions API; the resulting `ChunkyDKGResultTransaction.encryption_key` (`api/types/src/transaction.rs:1014-1023`) reflects the arbitrary, unverified bytes, while a node with `DIGEST_KEY` present would have discarded the same transaction — demonstrating both the state divergence and the unauthenticated API echo.

/// Production DigestKey: checks override first, then reads from file path.
/// Returns `None` if neither was configured or if reading/deserializing fails.
/// TEST_DIGEST_KEY is only evaluated here (on first access), not at boot.
pub static DIGEST_KEY: Lazy<Option<Arc<DigestKey>>> = Lazy::new(|| {
    match DIGEST_KEY_OVERRIDE.get() {
        Some(DigestKeyOverride::TestFallback) => {
            return Some(Arc::clone(&TEST_DIGEST_KEY));
        },
        Some(DigestKeyOverride::Explicit(key)) => {
            return Some(Arc::clone(key));
        },
        None => {},
    }
    let path = DIGEST_KEY_PATH.get()?;
    let start = Instant::now();
    let key: DigestKey = match digest_key_file::read_digest_key(path) {
        Ok(k) => k,
        Err(e) => {
            tracing::error!("[DigestKey] failed to read file: {}", e);
            return None;
        },
    };
    let elapsed = start.elapsed();
    tracing::info!(
        "[DigestKey] loaded from {} in {:?}",
        path.display(),
        elapsed,
    );
    Some(Arc::new(key))
});

/// Initialize the DigestKey source. Checks metadata only (no file read).
/// On test chains without an explicit path, sets the test key override
/// for validator nodes only. Non-validator nodes (fullnodes) should not
/// have a digest key since they don't participate in decryption.
pub fn initialize_digest_key(chain_id: ChainId, is_validator: bool) -> DigestKeySource {
    if let Some(path) = DIGEST_KEY_PATH.get() {
        match std::fs::metadata(path) {
            Ok(meta) => DigestKeySource::WillLoadFromFile {
                path: path.clone(),
                file_size: meta.len(),
            },
            Err(_) => DigestKeySource::NotAvailable,
        }
    } else if chain_id == ChainId::test() && is_validator {
        let _ = DIGEST_KEY_OVERRIDE.set(DigestKeyOverride::TestFallback);
        DigestKeySource::TestKeyFallback
    } else {
        DigestKeySource::NotAvailable
    }
}
