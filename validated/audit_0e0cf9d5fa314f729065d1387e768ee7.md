### Title
Anyone Can Front-Run Exchange Pool Creation to Set an Arbitrary Initial Price Ratio - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`ExchangeCreateActuator` is the on-chain, unauthenticated equivalent of an unprotected `initialize()` function: any account with sufficient balance can call `ExchangeCreateContract` to create the first (and only) liquidity/exchange pool for an arbitrary TRC10 token pair, and freely choose the initial `firstTokenBalance`/`secondTokenBalance` ratio, which becomes the pool's baseline exchange rate for all subsequent `ExchangeTransactionContract` trades.

### Finding Description
`ExchangeCreateActuator.execute()` and `doValidate()` never check whether the caller is the token issuer, an authorized party, or the "intended" creator of the market for a given token pair — the only checks are on balances, token ID validity, and duplicate-token checks. [1](#0-0) 
Once created, `ExchangeCapsule.setBalance(firstTokenBalance, secondTokenBalance)` permanently fixes the pool's initial reserves, and `id` is assigned sequentially via `dynamicStore.getLatestExchangeNum()+1`, so whichever transaction is included first "wins" the pool/id for that token pair. [2](#0-1) 
This mirrors the CSFeeOracle bug class: a state-defining, one-time setup action reachable by any unprivileged account with no ownership/whitelist gate, where whoever's transaction lands first fixes long-lived parameters (here, the AMM-style price ratio via `ExchangeProcessor.exchange()`'s constant-supply bonding curve) that all later participants must trade against. [3](#0-2) 

### Impact Explanation
An attacker observing a legitimate, pending `ExchangeCreateContract` transaction in the mempool for a newly-issued token can front-run it with their own `ExchangeCreateContract` for the same `firstTokenId`/`secondTokenId` pair (or the swapped order) using a heavily skewed ratio (e.g., depositing a minimal amount of the new token against a large TRX amount, or vice versa). Because `ExchangeTransactionActuator` computes swap output purely from `exchangeCapsule.transaction()`'s bonding-curve math over the attacker-chosen reserves, the legitimate project's real exchange never gets created with the intended price (the legitimate creator's transaction fails or creates a duplicate/secondary market with an id that traders may not know about), while the attacker's mispriced pool absorbs trades from unsuspecting users, letting the attacker buy the token cheaply or dump it at an inflated price. This is an accounting/market-manipulation exposure rather than a memory-safety or consensus bug, but it does allow direct value extraction from unprivileged callers with no owner/whitelist check reachable via a plain broadcast transaction.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to observe a specific pending `ExchangeCreateContract` in the transaction pool (or predict a project's launch) and successfully front-run it before it is packed into a block — achievable by any node operator/relayer since java-tron transactions and their contents are visible in the public mempool prior to confirmation, requiring no privileged access, leaked keys, or insider knowledge.

### Recommendation
Since the underlying design intentionally allows any account to create an exchange (this is a permissionless AMM-style feature, not a bug per se), the most direct analog fix mirroring the "acknowledge, don't fix" posture in the original report is not applicable here without protocol-level changes; however, if this class of front-running is judged in-scope, consider requiring the token issuer's authorization (e.g., verifying `assetIssueContract.getOwnerAddress() == exchangeCreateContract.getOwnerAddress()`) for the first pool of a given asset, or supporting commit-reveal / minimum-liquidity-lock mechanisms to raise the cost of hostile front-running.

### Proof of Concept
1. Party A issues TRC10 token `X` and broadcasts an `ExchangeCreateContract` with `firstTokenId="X"`, `secondTokenId="_"` (TRX), `firstTokenBalance=1_000_000`, `secondTokenBalance=1_000_000_000000` (fair 1:1,000,000 price) — visible in the mempool before confirmation.
2. Attacker B observes this transaction, immediately broadcasts their own `ExchangeCreateContract` for the same pair with `firstTokenBalance=1`, `secondTokenBalance=1_000_000_000000` (extremely skewed ratio), with a higher fee/priority so it lands in an earlier block position, as validated purely by `doValidate()`'s balance checks. [4](#0-3) 
3. B's exchange gets `id=1` and becomes the reference pool traders discover first; subsequent `ExchangeTransactionContract` calls against it execute at B's manipulated bonding-curve rate via `ExchangeCapsule.transaction()`, letting B extract value from any trader who swaps against pool 1 before realizing A's intended pool exists at a different id. [5](#0-4)

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
