### Title
Consumption of L1-to-L2 Messages Prior to Successful L2 Execution Leads to Permanent Loss of Bridged Value on Reverted L1 Handler Transactions - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo])

### Summary
The Starknet OS/sequencer consumes an L1-to-L2 message (marks its nonce as used and treats it as "consumed" for L1/L2 messaging bookkeeping) **before** attempting to execute the corresponding `L1Handler` entry point on L2. If the entry point call subsequently reverts (bad calldata, wrong selector, contract logic failure, etc.), the message is still recorded as consumed both in the OS output and in the batcher/L1-events-provider commit flow, while none of the intended L2 state changes (e.g., crediting a bridged deposit) persist. This mirrors the Scroll report's root cause: consumption of the cross-layer message is decoupled from successful completion of its payload, and there is no protocol-level refund path once the message has been executed-and-reverted (only pre-consumption cancellation exists).

### Finding Description
In the Starknet OS, `execute_l1_handler_transaction` calls `consume_l1_to_l2_message` unconditionally, before invoking the target entry point: [1](#0-0) 

`consume_l1_to_l2_message` unconditionally writes the message to `outputs.messages_to_l2`, regardless of the outcome of the subsequent `non_reverting_select_execute_entry_point_func` call: [2](#0-1) 

The only "skip" path (`is_reverted`) applies to transactions rejected entirely (e.g., due to post-execution resource-bound failures found in the blockifier), not to a normal Cairo panic/revert inside the L1-handler entry point itself, which is handled as `non_reverting_select_execute_entry_point_func` (a name that itself signals the entry point is executed in a "non-reverting" wrapper — i.e., failures inside are swallowed/absorbed rather than aborting the transaction and its message consumption).

This is corroborated on the Rust/blockifier side: `L1HandlerTransaction::execute_raw` returns `Ok(...)` with a populated `revert_error` even when `run_execute` fails, rather than treating the transaction as unexecutable: [3](#0-2) 

At the batcher level, `collect_execution_results_and_stream_txs` inserts every `L1Handler` transaction hash into `consumed_l1_handler_tx_hashes` unconditionally (before checking whether the execution `result` was `Ok`/reverted or `Err`/rejected): [4](#0-3) 

Only transactions that fail to even produce an execution result (`Err(err)`) are placed into `rejected_tx_hashes`, and only those are excluded from being treated as consumed by the L1 events provider: [5](#0-4) [6](#0-5) 

A transaction whose L2 entry point reverts (Cairo panic) is still `Ok(...)` from the executor's perspective, so it is treated as **consumed**, not rejected — exactly the class of transaction that a real Starknet bridge/user would expect to be "not effective" but which is nonetheless irreversibly marked as processed. Once marked consumed, the L1-side cancellation flow (`MessageToL2CancellationStarted` / `MessageToL2Canceled`, implemented in this repo's L1 events provider/transaction manager) is no longer available, since cancellation is only meaningful for un-consumed, pending messages: [7](#0-6) 

Any test contract that models this exact scenario already exists in the repository, confirming this is a reachable, first-class code path rather than a hypothetical: [8](#0-7) 

### Impact Explanation
Any L1 message sender (e.g., a bridge or arbitrary dApp relaying a message to L2 via `sendMessageToL2`) whose payload triggers a revert on L2 (malformed calldata, wrong selector, contract paused/upgraded between sending and inclusion, insufficient L2 state, etc.) will have their message irrevocably marked as consumed once it is included and executed (even though reverted) by the sequencer. Since consumption is final and no in-protocol refund/replay-with-different-calldata mechanism exists after execution, any value or intent tied to that specific message (e.g., L1-locked collateral awaiting a matching L2 mint) is permanently unrecoverable through the messaging layer itself. This is a concrete, permanent freezing-of-funds class of impact for applications built on top of the L1<>L2 messaging bridge, precisely analogous to the cited Scroll report.

### Likelihood Explanation
This is trivially triggerable by any L1 account with the ability to call the Starknet core contract's `sendMessageToL2` — no privileged role, sequencer misbehavior, or race condition is required. A single malformed or stale L1-to-L2 message (e.g., outdated calldata format after an L2 contract upgrade, or a typo/bug in the L1-side sender) reliably reproduces the issue every time such a message is processed.

### Recommendation
Consider decoupling "message consumption" (nonce invalidation / marking as processed) from unconditional consumption at dispatch time. Options include: reflecting the transaction's revert status as an explicit "not effectively delivered" state usable by higher-level (bridge) contracts and/or exposing a protocol-level flow allowing recovery only for reverted L1 handlers (distinct from ordinary successful executions) so applications can build safe refund/retry paths, and clearly documenting the current "consume-then-execute" semantics so integrators design their L1-handler entry points to be maximally defensive (idempotent, unable to panic on attacker-controlled payload) since no protocol-level safety net exists after inclusion.

### Proof of Concept
1. An L1 contract calls `sendMessageToL2(l2_contract, entry_point_selector, payload)` targeting an `L1Handler`-annotated Cairo function such as `l1_handler_set_value_and_revert` in the test contract, or any real contract whose entry point can revert on certain payloads: [8](#0-7) 
2. The L1 events scraper picks up the `LogMessageToL2` event and the sequencer proposes/executes the resulting `L1HandlerTransaction`.
3. During OS execution, `consume_l1_to_l2_message` records the message as consumed before the entry point runs: [1](#0-0) 
4. The entry point panics (`panic_with_felt252('revert in l1 handler')`), causing `execute_raw` to still return `Ok(...)` with a `revert_error`: [3](#0-2) 
5. The batcher includes the tx hash in `consumed_l1_handler_tx_hashes` (not `rejected_tx_hashes`), and `commit_block` in the L1 events provider marks it committed/consumed, permanently removing any possibility of cancellation or replay: [9](#0-8) [10](#0-9) 
6. Any L1-side value intended to be finalized by that specific L2 call (e.g., a bridge deposit credit) is now stuck, with no available refund mechanism.

// Adds 'tx' with the given 'nonce' to 'outputs.messages_to_l2'.
func consume_l1_to_l2_message{outputs: OsCarriedOutputs*}(
    execution_context: ExecutionContext*, nonce: felt
) {
    assert_not_zero(execution_context.calldata_size);
    // The payload is the calldata without the from_address argument (which is the first).
    let payload: felt* = execution_context.calldata + 1;
    tempvar payload_size = execution_context.calldata_size - 1;

    tempvar execution_info = execution_context.execution_info;

    // Write the given transaction to the output.
    assert [outputs.messages_to_l2] = MessageToL2Header(
        from_address=[execution_context.calldata],
        to_address=execution_info.contract_address,
        nonce=nonce,
        selector=execution_info.selector,
        payload_size=payload_size,
    );

    let message_payload = cast(outputs.messages_to_l2 + MessageToL2Header.SIZE, felt*);
    memcpy(dst=message_payload, src=payload, len=payload_size);

    let (outputs) = os_carried_outputs_new(
        messages_to_l1=outputs.messages_to_l1,
        messages_to_l2=outputs.messages_to_l2 + MessageToL2Header.SIZE +
        outputs.messages_to_l2.payload_size,
    );
    return ();
}

    fn apply_commit_block(
        &mut self,
        consumed_txs: IndexSet<TransactionHash>,
        rejected_txs: IndexSet<TransactionHash>,
    ) {
        debug!("Applying commit_block to height: {}", self.current_height);
        let (rejected_and_consumed, committed_txs): (Vec<_>, Vec<_>) =
            consumed_txs.iter().copied().partition(|tx| rejected_txs.contains(tx));
        self.tx_manager.commit_txs(&committed_txs, &rejected_and_consumed);

        self.current_height = self.current_height.unchecked_next();
    }

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();
        }
        for &tx_hash in rejected_txs {
            self.with_record(tx_hash, |r| r.mark_rejected()).expect(
                "Rejected L1 handler tx has no record. Unreachable: all L1 handler txs in a \
                 committed block were validated as known (validation rejects unknown hashes), \
                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",
            );
        }
    }
