### Title
Wallet Contract `has_in_flight_tx` flag can become permanently stuck to `true`, permanently bricking ETH-implicit accounts - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (deployed on every ETH-implicit account, per NEP-518) uses a boolean flag `has_in_flight_tx` to serialize `rlp_execute` calls: `rlp_execute` sets it to `true` before returning a promise, and each downstream callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) is supposed to reset it to `false` as its first action. If any of these `#[private]` callbacks fails to complete successfully (e.g., due to insufficient attached gas, or any other panic), the runtime rolls back *all* of that receipt's state changes atomically, including the `has_in_flight_tx = false` write that happened at the top of the function. This leaves the flag permanently `true`, and since ETH-implicit accounts "cannot be deleted, nor can a full access key be added" (per `docs/DataStructures/Account.md`), there is no recovery path — every future call to `rlp_execute` will immediately short-circuit on the `has_in_flight_tx` check and return an error, permanently bricking the account and any funds/tokens held by it.

### Finding Description
`WalletContract::rlp_execute` guards against concurrent execution with an in-memory boolean: [1](#0-0) 

`self.has_in_flight_tx = true` is committed to state as part of the current receipt's successful execution, then a promise chain is scheduled. The chain always ends by invoking one of these `#[private]` callback methods, each of which resets the flag as its very first statement: [2](#0-1) [3](#0-2) [4](#0-3) 

The comment on the field itself states the invariant this relies on: [5](#0-4) 

This design assumes the reset-callback *always* completes successfully. But nearcore's runtime treats a failed `FunctionCall` action atomically: if the action errors (including running out of gas), **all** state writes made during that receipt — including ones made before the point of failure — are discarded via `state_update.rollback()`: [6](#0-5) 

This is a documented invariant of the runtime: [7](#0-6) 

So if any of the reset-callback functions itself fails/panics after being invoked (out-of-gas being the most direct unprivileged trigger — the callback gas is statically fixed at small values like `RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, only partly scaled by the user/relayer-controlled `action.gas()`), the `has_in_flight_tx = false` write is rolled back along with everything else in that receipt, and `has_in_flight_tx` remains `true` forever: [8](#0-7) 

Because the callback deserializes attacker/relayer-influenced data (`serde_json::from_slice` on cross-contract call results in `nep_141_storage_balance_callback` and `address_check_callback`) and constructs further promises/actions, its actual gas usage is not tightly bounded relative to the small static gas reservation, so a legitimately-sized or maliciously-crafted transaction routed through a relayer with marginal gas provisioning can exhaust the callback's gas mid-execution and trigger this failure path organically, not just via contrived adversarial input.

Once `has_in_flight_tx` is stuck `true`, every subsequent `rlp_execute` call immediately short-circuits: [9](#0-8) 

Since this method is the *only* entry point through which an ETH-implicit account owner can act (they cannot add a full access key or delete the account, per the design docs), the account becomes permanently unusable.

This is directly analogous to the SYMM-IO Party B liquidation bug: a status flag (`partyBLiquidationStatus`/`has_in_flight_tx`) is set to indicate "operation in progress," gating all future operations via a guard (`notLiquidated`/`has_in_flight_tx` check), and is only supposed to be cleared by a follow-up step (signature verification/promise callback). If that follow-up step reverts/fails for any reason unrelated to the guard's own logic, the flag is stuck forever with no recovery mechanism, permanently freezing functionality (and, in the NEAR case, funds, since the account cannot be recovered any other way).

### Impact Explanation
An ETH-implicit (Wallet Contract) account, once its `has_in_flight_tx` flag becomes stuck at `true`, permanently loses the ability to execute any further Ethereum-emulated transaction via `rlp_execute`. Since ETH-implicit accounts have no full access key and cannot be deleted, all NEAR balance and any tokens (NEP-141) held by that account become permanently inaccessible/frozen — matching the "permanently frozen funds" impact category. This is triggerable by ordinary transaction/relayer activity (a `FunctionCall` to `rlp_execute` with gas that is sufficient for the initial dispatch but insufficient for the reset callback to complete), reachable by any unprivileged sender who can call `rlp_execute` on the account (the account owner themselves, or any relayer, honest or otherwise).

### Likelihood Explanation
Likelihood is moderate-to-high: the callback gas budgets (`RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`) are small, fixed constants (5–10 Tgas range) that must cover variable-cost work (JSON deserialization of untrusted cross-contract responses, promise construction, `serde_json`/ABI decoding) whose cost scales with response/argument size. A relayer or user who under-provisions gas for a transaction that routes through the NEP-141/address-registrar callback paths (multi-step promise chains) can trigger this deterministically. It does not require any protocol-level bug or malicious validator — only a single crafted or badly-gassed `FunctionCall` action from an unprivileged caller.

### Recommendation
- Do not rely on a callback's own execution succeeding to clear a "lock" flag that gates future usability of the account. Instead, use a `#[near_bindgen]` "guaranteed" cleanup pattern: e.g., have the outer promise batch include an unconditional final step (using `Promise::then` with `GasWeight` reserved specifically and validated to always be sufficient, or splitting the "clear flag" write into a separate always-scheduled receipt that cannot itself fail from ABI-decoding/variable-cost work).
- Bound/validate the gas actually required by `address_check_callback` / `nep_141_storage_balance_callback` / `rlp_execute_callback` more conservatively, and reject `rlp_execute` up front (before setting `has_in_flight_tx = true` and dispatching promises) if the attached `prepaid_gas` does not leave a safe margin above the statically reserved callback gas for cross-contract response processing.
- Add a protocol/contract-level recovery path: e.g., allow `has_in_flight_tx` to be reset by a timeout-based mechanism (analogous to NEAR's own `PromiseYieldTimeout`), or allow the account owner to force-clear the flag once no genuinely pending receipt exists, rather than making a single guard byte a permanent single point of failure with no fallback.

### Proof of Concept
1. Deploy an ETH-implicit account (Wallet Contract) and fund it with NEAR and a NEP-141 token balance.
2. Have the owner (or a permissioned relayer) sign an RLP transaction whose target is an ERC-20 emulated transfer to an unregistered receiver (`EthEmulationKind::ERC20Transfer`), so `inner_rlp_execute` schedules: `storage_balance_of` → `nep_141_storage_balance_callback` (gas `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`) → (if unregistered) `storage_deposit` + `ft_transfer` → `rlp_execute_callback`.
3. Submit `rlp_execute` with `prepaid_gas` just sufficient for the initial dispatch/parsing but leaving `nep_141_storage_balance_callback`'s actual execution (JSON parsing of the NEP-141 `storage_balance_of` response plus follow-up promise construction) with less gas than it needs.
4. When `nep_141_storage_balance_callback` executes, it enters, sets `self.has_in_flight_tx = false`, then runs out of gas while processing the response/building the next promise.
5. Because the callback's `FunctionCall` action failed, `runtime/runtime/src/lib.rs`'s `apply_action_receipt` calls `state_update.rollback()`, discarding the `has_in_flight_tx = false` write along with everything else in that receipt — leaving `has_in_flight_tx == true` in the account's persisted state.
6. Any subsequent call to `rlp_execute` on this account now immediately returns `"Error: transaction already in progress, please try again later."` forever, since there is no code path that can ever set `has_in_flight_tx` back to `false` (no full access key can be added, and the account cannot be deleted) — permanently freezing the account and its funds.
