### Title
`BankHashStats` is restored verbatim from an untrusted snapshot field instead of being recalculated from the actual stored accounts - (File: `runtime/src/serde_snapshot.rs`, `runtime/src/bank.rs`)

### Summary
During snapshot reconstruction, `capitalization` and `accounts_lt_hash` are both recomputed by walking every account in `AccountsDb::generate_index` and are then cross-checked against the values embedded in the snapshot, causing a hard failure (`SnapshotError::MismatchedCapitalization`, lt-hash mismatch panic) if they disagree. [1](#0-0) [2](#0-1)  `BankHashStats`, however, is simply copied from the deserialized snapshot fields into the reconstructed bank with no recomputation or cross-check against the accounts actually present in the loaded storages. [3](#0-2) 

### Finding Description
`BankHashStats` is documented as "serialized and stored in the snapshot" and holds `num_updated_accounts`, `num_removed_accounts`, `num_lamports_stored`, `total_data_len`, and `num_executable_accounts` — a per-bank running tally that is incrementally updated on every `update_bank_hash_stats` call as transactions modify accounts. [4](#0-3) [5](#0-4) 

When a bank is rebuilt from a snapshot, `reconstruct_accountsdb_from_fields` extracts `snapshot_bank_hash_info.stats` from the deserialized `SnapshotAccountsDbFields` and returns it unchanged as part of `ReconstructedAccountsDbInfo`; this is the same code path that also produces `calculated_capitalization` and `calculated_accounts_lt_hash` by actually scanning the storages via `generate_index`. [6](#0-5)  `reconstruct_bank_from_fields` then assigns this untouched stats blob directly onto `bank_fields.bank_hash_stats` before constructing the `Bank`. [3](#0-2) 

By contrast, `calculated_capitalization` is compared against `bank.capitalization()` in both `bank_from_snapshot_archives` and `bank_from_snapshot_dir`, and a mismatch is treated as a fatal error (unless slot-count limiting is active). [1](#0-0) [7](#0-6)  Likewise `calculated_accounts_lt_hash` is compared against the bank's accounts lt hash via `verify_accounts`/`verify_snapshot_bank`. [2](#0-1)  No equivalent validation exists for `BankHashStats` — the value stored in `AccountsDbFields`/`BankFieldsToDeserialize` is trusted as-is, exactly analogous to the reported bug where a stateful, derivable quantity (`fee`) was instead accepted directly from an untrusted external input rather than being computed/validated against the true underlying state.

Because `Accounts::verify_bank_hash_and_lamports_new` and hash-verification tooling reference `bank_hash_stats()` when reasoning about accounts state during verification/repair flows, and it is accumulated forward on every subsequent transaction via `BankHashStats::accumulate`, once a bank is reconstructed with a wrong/stale stats value the divergence silently propagates into all descendant banks derived from it. [8](#0-7) 

### Impact Explanation
On an honest node this manifests when a snapshot is generated/loaded across a code path where the incremental `BankHashStats` accumulation in the running bank drifts from what actually ends up written to storage (e.g., minimized snapshots via `SnapshotMinimizer`, obsolete-account handling paths that mutate storages independently of `update_bank_hash_stats`, or any bank-rebuild path that skips slots via `limit_load_slot_count_from_snapshot`). Because capitalization and lt-hash divergences are caught by explicit verification but `BankHashStats` is not, a node can silently carry an incorrect `num_lamports_stored`/`total_data_len`/account counters after a snapshot-restart, without any panic or error being raised, unlike the parallel capitalization/lt-hash checks. This is a stale/wrong-version account-derived-state load whose divergence is never detected, matching the "silent...divergence" class called out in the validation rules.

### Likelihood Explanation
This requires no adversarial input; it is triggered purely by normal snapshot save/restore operations performed by any validator operator (an unprivileged, non-consensus-critical operation), the same "restart from snapshot" flow exercised continuously in production. The asymmetry between how capitalization/lt-hash are protected and how `BankHashStats` is not is a structural gap in the reconstruction code, not something needing a maliciously crafted snapshot.

### Recommendation
Recompute `BankHashStats` from the actual accounts loaded into `AccountsDb` during `generate_index` (mirroring how `calculated_capitalization` and `calculated_accounts_lt_hash` are derived), and cross-check it against the value embedded in the snapshot, failing loudly (as is already done for capitalization) on mismatch instead of silently trusting the serialized snapshot field.

### Proof of Concept
Not independently reproduced; conclusion is derived from static code-flow analysis showing `bank_hash_stats` bypasses the recompute-and-verify pattern used for `capitalization`/`accounts_lt_hash` in `reconstruct_accountsdb_from_fields` / `reconstruct_bank_from_fields`. Confirming an actual divergence scenario (e.g., via `SnapshotMinimizer` or obsolete-account paths) and its downstream consequences on `verify_bank_hash_and_lamports` would require deeper tracing of all `bank_hash_stats` accumulation call sites and how/whether it's consumed by consensus-relevant hash verification, which was not fully completed within available search budget — this should be validated further via a Devin session with full repository access.

/// Account stats for computing the bank hash
/// This struct is serialized and stored in the snapshot.
#[repr(C)]
#[cfg_attr(feature = "frozen-abi", derive(AbiExample, StableAbi, StableAbiSample))]
#[derive(Clone, Default, Debug, Serialize, Deserialize, PartialEq, Eq, SchemaRead, SchemaWrite)]
pub struct BankHashStats {
    pub num_updated_accounts: u64,
    pub num_removed_accounts: u64,
    pub num_lamports_stored: u64,
    pub total_data_len: u64,
    pub num_executable_accounts: u64,
}

impl BankHashStats {
    pub fn update<T: ReadableAccount>(&mut self, account: &T) {
        if account.lamports() == 0 {
            self.num_removed_accounts += 1;
        } else {
            self.num_updated_accounts += 1;
        }
        self.total_data_len = self
            .total_data_len
            .wrapping_add(account.data().len() as u64);
        if account.executable() {
            self.num_executable_accounts += 1;
        }
        self.num_lamports_stored = self.num_lamports_stored.wrapping_add(account.lamports());
    }
