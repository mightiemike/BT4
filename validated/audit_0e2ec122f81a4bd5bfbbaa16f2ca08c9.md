### Title
Missing declared-class check in `execute_replace_class` allows unauthenticated state divergence between Blockifier and Starknet OS - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The Starknet OS Cairo implementation of the `replace_class` syscall (`execute_replace_class`) writes an arbitrary caller-supplied `class_hash` into `contract_state_changes` without verifying that a contract class with that hash has actually been declared. The Rust `blockifier` implementation of the same syscall does perform this check (and additionally rejects Cairo0/deprecated classes), so the two execution engines can diverge on the same transaction.

### Finding Description
Any contract's Cairo code can invoke the `replace_class` syscall with an attacker-chosen `class_hash` — this requires no special privilege, just a normal transaction from any account calling into a contract that performs `replace_class_syscall(class_hash)`. In the Rust blockifier, `syscall_base::meta_tx_v0`'s sibling function `replace_class` explicitly enforces both preconditions before mutating state: [1](#0-0) 

```
pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
    // Ensure the class is declared (by reading it), and of type V1.
    let compiled_class = self.state.get_compiled_class(class_hash)?;
    if !is_cairo1(&compiled_class) {
        return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
    }
    self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
    Ok(())
}
```

`get_compiled_class` will fail if `class_hash` was never declared, and `is_cairo1` rejects deprecated (Cairo0) classes — so in blockifier, calling `replace_class` with an undeclared or Cairo0 class hash causes the syscall (and typically the whole transaction, unless caught) to fail/revert.

In contrast, the Starknet OS Cairo implementation of the identical syscall performs neither check — the check is explicitly marked as a `TODO` and never implemented: [2](#0-1) 

```
// Replaces the class.
func execute_replace_class{
    range_check_ptr,
    syscall_ptr: felt*,

    alloc_locals;
    let request = cast(syscall_ptr + RequestHeader.SIZE, ReplaceClassRequest*);
    ...
    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.

    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,
        prev_value=cast(state_entry, felt),
        new_value=cast(new_state_entry, felt),
    );
    ...
```

The same missing check exists in the deprecated (Cairo0) syscall path as well: [3](#0-2) 

Because the STARK proof of block execution is generated by running this exact Cairo program (the "Starknet OS"), and STARK soundness only guarantees that the constraints actually written into the Cairo code hold, the absence of a "class is declared" constraint here means the OS accepts (and proves as valid) a state transition in which a contract's `class_hash` is set to an arbitrary, non-existent, or forbidden (Cairo0) value — a transition that the sequencer's own execution engine (blockifier) would reject.

### Impact Explanation
This is a divergence between the two components that must agree bit-for-bit on the resulting state: the sequencer's `blockifier`, which decides whether a transaction reverts and what state diff is produced, and the Starknet OS, which re-executes/proves the block and produces the committed state root and output. If the class-declared check is only enforced in one component:
- An honest sequencer running blockifier will revert a `replace_class` call to an undeclared/invalid class hash, producing state diff A.
- The Starknet OS, run by a prover for the same block, lacks the constraint and will happily accept the state transition, producing a *different* committed contract-state entry (class_hash) for that contract — state diff B.
- This is exactly the class of bug the rules classify as high-impact: "wrong committed root or block hash, honest-node divergence." A contract's on-chain class could effectively be "bricked" or replaced with a value that was never declared/authorized, and the resulting state root accepted by the OS/proving pipeline would not match what an honest re-execution via blockifier alone would produce.

### Likelihood Explanation
Triggering the vulnerable code path requires only:
1. Deploying (or using an existing) contract whose Cairo code calls `replace_class_syscall(class_hash)` with attacker-controlled `class_hash`.
2. Submitting a single ordinary `INVOKE` transaction from any account (no special permission, no admin key, no proposer/prover role) that reaches that call.

This is directly reachable from a single unprivileged transaction sender, matching the required threat model. The missing check is explicit in the code (marked with a dated `TODO`), so there's no ambiguity about whether the check exists elsewhere in the OS pipeline for this specific syscall.

### Recommendation
Add the missing declared-class check (and the "must be Cairo1/non-deprecated" check, mirroring blockifier's `is_cairo1` check) inside `execute_replace_class` in both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo`, using the OS's declared-classes dictionary/hint mechanism (analogous to how other syscalls validate class hashes, e.g. in `deploy_contract.cairo`) before performing the `dict_update` on `contract_state_changes`. This constraint must be enforced identically to the blockifier's `replace_class` implementation to guarantee that the OS's proven state transition matches the sequencer's actual execution result.

### Proof of Concept
1. Deploy `TestContract` (or any contract exposing `test_replace_class`/`replace_class_syscall`), as already used in the blockifier's own negative-flow unit test: [4](#0-3) 
which shows that calling `replace_class` with an undeclared class hash (`felt!(1234_u16)`) in blockifier produces an error ("is not declared").
2. Submit the equivalent transaction/calldata against the Starknet OS re-execution/proving path (`execute_replace_class` in `syscall_impls.cairo` / `deprecated_execute_syscalls.cairo`): because no declared-class check exists there, the `dict_update` on `contract_state_changes` succeeds and commits the undeclared `class_hash` into the contract's state entry, whereas the same call in blockifier would revert.
3. Compare the two committed state diffs for the contract address: blockifier produces no class-hash change (transaction reverted), while the OS-proven output commits the new (invalid) `class_hash` — demonstrating the divergence.
