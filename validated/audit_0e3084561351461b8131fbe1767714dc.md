### Title
Receipts can be created above `max_receipt_size` after validation, breaking size-based congestion/witness guarantees - ([File: runtime/runtime/src/lib.rs], [File: runtime/runtime/src/congestion_control.rs], [File: runtime/runtime/src/verifier.rs])

### Summary
A `FunctionCall` action receipt that is exactly at `max_receipt_size` when created passes `validate_receipt` (which enforces the size check only on the freshly-created receipt at that point in time), but is later mutated by appending `output_data_receivers` in `apply_action_receipt`, pushing its serialized size above `max_receipt_size` *after* validation already succeeded. This mirrors the reported `BuyCrowdfundBase._buy()` bug: a value that must never exceed a maximum bound is computed/mutated without re-checking the bound, and downstream code merely "pretends" the bound holds instead of enforcing it.

### Finding Description
`validate_receipt` checks receipt size only when creating a `NewReceipt` [1](#0-0) . However, after a function call's new receipts are validated, `apply_action_receipt` mutates an already-validated new receipt by appending the *caller's* `output_data_receivers` onto it when the call returns a `ReceiptIndex` via `promise_return`, growing the receipt's serialized size beyond what was checked [2](#0-1) . Because this mutation happens after `validate_receipt` was called, the resulting oversized receipt is never re-validated against `max_receipt_size`.

The runtime is aware of this and has to work around it downstream instead of fixing the root cause: `try_forward` in the congestion/bandwidth-forwarding path explicitly "pretends" any receipt above `max_receipt_size` is exactly `max_receipt_size` for the purpose of size-limit comparisons [3](#0-2) , and a dedicated `ExistingReceipt` validation mode exists solely to "tolerate" receipts that violate the very limit `NewReceipt` mode is supposed to enforce [4](#0-3) . This is the exact same pattern as the reported issue: the maximum bound (`maximumPrice` / `max_receipt_size`) is defined, but the value that must respect it (`settledPrice` / receipt serialized size) can be computed or mutated in a code path that never re-clamps or re-validates against that bound, and the fix applied is a downstream workaround ("pretend" it's capped) rather than actually enforcing the invariant at the source.

This exact defect is already tracked and reproduced in-repo as issue #12606, with explicit test cases demonstrating it is reachable by an ordinary contract call (no special privileges) [5](#0-4) [6](#0-5) .

### Impact Explanation
An oversized receipt breaks the size accounting invariants that `max_receipt_size` exists to guarantee: the `docs/misc/state_witness_size_limits.md` budget of ~21MiB for `ChunkStateWitness` is derived assuming every receipt is bounded by `max_receipt_size` [7](#0-6) . Oversized receipts also interact incorrectly with the bandwidth scheduler's size grants and with `outgoing_receipts_usual_size_limit` / `outgoing_receipts_big_size_limit`, since `try_forward`'s size clamp is only a bookkeeping "pretend" and the actual bytes forwarded/stored are larger than accounted for — this can degrade cross-shard bandwidth fairness/liveness assumptions and inflate witness/state sizes beyond the limits validators are required to enforce, a "transaction-triggered" deviation from intended resource bounds reachable by any regular contract caller via `promise_return`/large value returns.

### Likelihood Explanation
Reachable directly by any account submitting an ordinary `FunctionCall` transaction that uses `promise_return` (or returns a large value/yields with large args) to grow a receipt already at the size boundary — no elevated privileges, validator, or network position required, as demonstrated by the existing test suite reproducing it deterministically.

### Recommendation
Re-validate (or re-check) the receipt's serialized size against `max_receipt_size` after any post-creation mutation (e.g., after `output_data_receivers` is extended in `apply_action_receipt`) and reject/fail the action if the bound is exceeded, rather than relying on downstream code to "pretend" the size is capped. Remove or tighten the `ExistingReceipt` validation carve-out once the root-cause mutation path is fixed, so the size cap is enforced uniformly instead of patched around in the forwarding logic.

### Proof of Concept
Use the in-repo reproduction: deploy a contract, then call a method that creates a promise DAG `A -then-> B` where `A` (inside its own execution) creates a third promise `C` and does `promise_return`, with `C`'s receipt already sized at exactly `max_receipt_size` before the caller's `output_data_receivers` are appended — the resulting `C` receipt exceeds `max_receipt_size` and is never rejected [8](#0-7) . A second reproduction returns a value sized at `max_receipt_size`, which becomes an oversized `Data` receipt once wrapped, again passing through unchecked [9](#0-8) .

fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
