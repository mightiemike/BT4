### Title
gRPC `GetPaginatedProposalList` throws unhandled NPE on out-of-range offsets while the HTTP servlet returns a safe empty object for the same input - ([File: framework/src/main/java/org/tron/core/services/RpcApiService.java])

### Finding Description
`Wallet.getPaginatedProposalList(offset, limit)` returns `null` whenever `offset < 0`, `limit < 0`, or `offset >= latestProposalNum` [1](#0-0) . The HTTP entrypoint `GetPaginatedProposalListServlet.fillResponse` explicitly checks for this `null` and writes `"{}"` back to the client, avoiding any downstream error [2](#0-1) .

The gRPC entrypoint, however, passes the raw (possibly `null`) result of `wallet.getPaginatedProposalList(...)` directly to `responseObserver.onNext(...)` with no null check and no `try/catch`, unlike other adjacent handlers such as `getMemoFee` in the same class which wrap the call in `try { ... } catch (Exception e) { responseObserver.onError(getRunTimeException(e)); }` [3](#0-2) . `getPaginatedExchangeList` right below it has the identical unguarded pattern [4](#0-3) .

Any unauthenticated gRPC client can call `GetPaginatedProposalList` (defined in `api.proto` with no auth requirement) [5](#0-4)  with `offset >= latestProposalNum` (e.g. `offset=0` on a chain with no proposals, or `offset=Long.MAX_VALUE`), causing `wallet.getPaginatedProposalList` to return `null`, which then flows into `responseObserver.onNext(null)`. gRPC's generated stub/message serializer will attempt to serialize a `null` `ProposalList` message, which is not permitted and results in a `NullPointerException` thrown from within the service handler thread instead of a graceful error or empty response. Because there is no surrounding `try/catch`, this exception is not converted into a controlled `Status.INTERNAL` via `getRunTimeException`; the call fails ungracefully compared to the identical logical request over HTTP, which returns `"{}"` with a 200 response.

### Impact Explanation
This creates divergent, less-safe availability behavior for the gRPC public API surface versus the HTTP API surface for a functionally identical, easily-triggered edge case. It is a low-privilege input causing an unhandled exception path on a public RPC endpoint, rather than a clean empty response — an "invalid state/divergence" issue scoped to this single RPC (and the sibling `getPaginatedExchangeList`), not a full node crash, since gRPC's `ServerCallImpl` will typically catch the exception at the framework level and return an INTERNAL error to that one client, but this still represents inconsistent and unintended server behavior directly caused by missing null-handling that exists on the HTTP side.

### Likelihood Explanation
Trivially reachable by any unprivileged client with gRPC access to the Full/Solidity node: sending `offset=0` when no proposals exist yet, or `offset` at/above `latestProposalNum`, deterministically triggers the `null` return in `Wallet.getPaginatedProposalList` and is 100% repeatable.

### Recommendation
Add the same null-check (or wrap in try/catch consistent with `getMemoFee`) in `RpcApiService.getPaginatedProposalList` and `getPaginatedExchangeList`, e.g. build and send an empty `ProposalList`/`ExchangeList` when the wallet method returns `null`, matching the HTTP servlet's defensive behavior.
