### Title
TRC10 Exchange/Market pricing math ignores per-asset `precision`, letting attackers create decimal-mismatched pools/pairs to skew AMM ratios and order-book prices - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`, `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
Every user can issue a TRC10 token via `AssetIssueContract` with a self-declared `precision` between 0 and 6 [1](#0-0) . That `precision` value is stored on the asset but is never read, scaled against, or checked by any of the on-chain trading primitives: the TRX/TRC10 Bancor-style `Exchange` (create/inject/withdraw/transaction) and the TRC10/TRC10 `Market` order book. Both subsystems treat the raw `long` `quant`/`balance` fields of any two paired tokens as if they were in the same unit scale, exactly mirroring the ClearingHouse bug class where notional/margin values from differently-scaled sources are mixed "as if they are PRECISION scaled" without rescaling.

### Finding Description
`ExchangeCreateActuator.doValidate()`/`execute()` accept `firstTokenID`/`secondTokenID` and their balances directly as `long` amounts with no reference to each token's `precision`, then seed the constant-product-like pool via `ExchangeCapsule.setBalance` [3](#0-2) . The relay-based swap math in `ExchangeCapsule.transaction`/`SafeExchangeProcessor.exchange` and the ratio math in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` (`bigFirstTokenBalance.multiply(bigTokenQuant).divide(bigSecondTokenBalance)`) all operate purely on these raw integer balances [4](#0-3) [5](#0-4) [6](#0-5) .

Likewise, `MarketSellAssetActuator.matchSingleOrder` calls `MarketUtils.multiplyAndDivide` and `MarketUtils.priceMatch`→`MarketComparator.comparePrice` to compute exchange ratios and order matching purely from `sellTokenQuantity`/`buyTokenQuantity` longs, with no decimals normalization [7](#0-6) [8](#0-7) .

If asset A is issued with `precision=0` (1 unit = 1 whole token) and asset B with `precision=6` (1 unit = 1e-6 token, TRX-like), any pool/order book pairing A and B will treat "1 unit of A" as economically equal to "1 unit of B" in all ratio math, even though B's raw unit is 1,000,000x smaller in real value than A's. This is the direct analog of the `ClearingHouse` bug: values are combined "linear decimals wise" from each source, then mixed together in ratio/comparison logic "without rescaling, as if they are [the same] scaled."

### Impact Explanation
An attacker can issue two TRC10 tokens with different `precision` values, create an `Exchange` pool or `Market` order pairing them, and set up highly favorable initial ratios/prices that appear balanced numerically but are off by up to 10^6 in real economic terms. Because TRX itself is fixed at 6-decimal SUN and other TRC10 tokens can freely choose 0–6 decimals, any counterparty (or naive integrator/front-end) trading against such a pool/order using face-value quantities will receive or pay an amount that is off by orders of magnitude, i.e., underpriced-work/economic drain on the counterparty and value extraction for the attacker — a concrete accounting/settlement flaw rather than a theoretical one.

### Likelihood Explanation
High: asset issuance (`AssetIssueContract`), exchange creation/inject/withdraw, and market order placement/matching are all unprivileged, permissionless actions available to any account with enough TRX for fees [1](#0-0) [9](#0-8) . No validation anywhere cross-checks `precision` between the two paired tokens before allowing pool creation, injection, withdrawal, or order matching.

### Recommendation
Either (a) normalize all token quantities to a common base precision (e.g., 6 decimals) before performing exchange/market ratio math and store/display the scaled values consistently, or (b) enforce at `ExchangeCreateActuator`/`MarketSellAssetActuator` validation time that paired tokens must share identical `precision`, rejecting creation/orders otherwise. Precision-awareness should be threaded through `ExchangeCapsule`, `SafeExchangeProcessor`, and `MarketUtils` so ratio, price-comparison, and matching logic operate on economically comparable values rather than raw storage units.

### Proof of Concept
1. Issue token A via `AssetIssueContract` with `precision=0`, `totalSupply=1_000_000`.
2. Issue token B via `AssetIssueContract` with `precision=6`, `totalSupply=1_000_000_000_000` (same real value, scaled by 1e6).
3. Call `ExchangeCreateContract` to create a pool with `firstTokenBalance=1000` (token A) and `secondTokenBalance=1000` (token B) — accepted because `ExchangeCreateActuator.doValidate()` never compares `precision` [10](#0-9) .
4. Because token B's 1000 raw units represent only 0.001 real B-token (versus A's 1000 whole units), the pool is instantly mispriced by 1e6x; any subsequent `ExchangeTransactionContract` swap or `MarketSellAssetContract` order pays/receives amounts skewed by that same factor, letting the pool creator drain counterparties trading at "face value."

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public static int comparePrice(long price1SellQuantity, long price1BuyQuantity,
                                 long price2SellQuantity, long price2BuyQuantity) {
    try {
      return Long.compare(StrictMath.multiplyExact(price1BuyQuantity, price2SellQuantity),
          StrictMath.multiplyExact(price2BuyQuantity, price1SellQuantity));

      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger price1BuyQuantityBI = BigInteger.valueOf(price1BuyQuantity);
    BigInteger price1SellQuantityBI = BigInteger.valueOf(price1SellQuantity);
    BigInteger price2BuyQuantityBI = BigInteger.valueOf(price2BuyQuantity);
    BigInteger price2SellQuantityBI = BigInteger.valueOf(price2SellQuantity);

    return price1BuyQuantityBI.multiply(price2SellQuantityBI)
        .compareTo(price2BuyQuantityBI.multiply(price1SellQuantityBI));
