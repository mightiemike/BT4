### Title
Attacker-Forced Head-of-Line Blocking of a Shard's Outgoing Receipt Buffer via Oversized Receipts — ([File: runtime/runtime/src/congestion_control.rs])

### Summary
The OpenQ bug lets an unprivileged attacker permanently deny a specific victim's future action (funding a bounty) by cheaply saturating a small, shared, FIFO-like capacity that the protocol trusts to always make forward progress. The closest reachable nearcore analog is the acknowledged "oversized receipt" workaround in the cross-shard congestion-control / outgoing-receipt-buffer pipeline: `ReceiptSinkV2::try_forward` and `buffer_receipt` treat any receipt larger than `max_receipt_size` as if it were exactly `max_receipt_size` purely for the *admission comparison*, while the receipt's *actual* size is what gets pushed into the shard's FIFO `OutgoingReceiptBuffer` (`ShardsOutgoingReceiptBuffer`, `core/store/src/trie/receipts_column_helper.rs`). Because that structure is a strict FIFO queue drained head-first (`forward_from_buffer_to_shard`, `congestion_control.rs:338-395`), a receipt that is genuinely too large to ever be granted enough bandwidth can sit at the head of a receiver shard's buffer indefinitely, blocking every other user's receipt destined for that same shard behind it — an unprivileged, transaction-triggered griefing vector directly analogous to the ERC20 "fill the limited slot with junk to lock out legitimate users" pattern.

### Finding Description
`ReceiptSinkV2::try_forward` (`runtime/runtime/src/congestion_control.rs:403-462`) is supposed to guarantee liveness for every receipt by comparing `size` against a per-receiver `OutgoingLimit`. To cope with a known bug (referenced as near/nearcore#12606) that "allows to create receipts that are above the size limit," the code clamps the *comparison* value: [1](#0-0) 

only `size` (used for the `forward_limit.size >= size` check) is clamped — the receipt object itself, with its true (oversized) byte length, is what gets forwarded or buffered. If the bandwidth grant available to the shard is (by design) capped near `max_receipt_size` and never any higher, an oversized receipt can pass the clamped admission check yet still be one that a downstream consumer (e.g., a peer’s message-size limits, or a subsequent shard’s own re-validation) cannot actually move, or — more critically for this repo's own model — it is pushed as-is into the persistent, trie-backed FIFO `OutgoingReceiptBuffer` for that receiver shard: [2](#0-1) 

`ShardsOutgoingReceiptBuffer`/`OutgoingReceiptBuffer` is a strict `TrieQueue` (`core/store/src/trie/receipts_column_helper.rs:63-120`) drained only from `first_index` forward — `pop_front`/`pop_n` cannot skip an un-forwardable head item. `forward_from_buffer_to_shard` (`congestion_control.rs:338-395`) walks the buffer in order and `break`s the moment `try_forward` returns `NotForwarded` for the head item: [3](#0-2) 

This means any single receipt that is stuck at the head of a shard's buffer (whether due to the acknowledged #12606 size-limit-bypass bug, or any other future discrepancy between the "as-if-clamped" admission size and the receipt's true size/behavior) stalls the *entire* buffer to that receiver shard — every other account's receipts to that shard, submitted by innocent users, are withheld behind it. The doc comment for `try_forward` even states the pretense is "a bug workaround" whose entire purpose is to avoid receipts "getting stuck," implicitly acknowledging that without the clamp, receipts do get permanently stuck in exactly this FIFO structure.

### Impact Explanation
If a receipt larger than the shard's actual deliverable bandwidth/size ever reaches the head of a receiver shard's outgoing buffer (via the acknowledged #12606 bug, a future protocol-version size-limit reduction, or any code path that creates a receipt whose true cost the size-clamp heuristic under-estimates), all receipts to that shard — from any account — are frozen indefinitely behind it. This is a transaction-triggered, protocol-level halt of cross-shard receipt delivery to a specific shard: legitimate users' transfers, contract calls, and defi/bridge operations directed at accounts on that shard would never execute, i.e., "permanently frozen funds" and "receipt loss" (indefinite non-delivery) for every other account, triggered by a single attacker-submitted transaction — the same "small number of unprivileged, cheap, or worthless entries block everyone else from a shared limited resource" structure as the OpenQ report, but expressed as head-of-line blocking of a FIFO delivery queue rather than exhaustion of a whitelist-count array.

### Likelihood Explanation
The core admission-size clamp exists specifically because the developers know oversized receipts can already be created (#12606); the fix only patches the *comparison*, not the underlying ability to create/forward a receipt whose real size the bandwidth scheduler can never fully satisfy. The `test_max_receipt_size` test in `test-loop-tests/src/tests/max_receipt_size.rs` shows the primary boundary check (rejecting a receipt-generation call above `max_receipt_size`) is enforced today, so a straightforward attempt to create a too-large receipt is currently caught at receipt-creation time. However, the presence of a dedicated workaround in `try_forward`/`generate_bandwidth_request` for receipts *that already exceeded the limit* is a strong signal that the invariant "no receipt ever exceeds `max_receipt_size`" is not airtight across all code paths (e.g., protocol-version transitions that lower `max_receipt_size`, or any receipt-construction path not covered by the same validation as `generate_large_receipt`). I was not able to fully verify, within available tool budget, an exact unprivileged transaction that currently bypasses `ReceiptValidationError::ReceiptSizeExceeded` and reaches `try_forward`/`buffer_receipt` with a truly oversized receipt — this would need direct code tracing of every receipt-construction path (e.g., delegate actions, global-contract distribution receipts, or receipts constructed after a lowered `max_receipt_size` during a protocol upgrade) to confirm reachability from a single external transaction today.

### Recommendation
- Ensure the size clamp used for admission accounting in `try_forward` and `generate_bandwidth_request` can never diverge from a receipt's true deliverable size; instead of "pretending" a receipt fits, actively prevent any oversized receipt from ever being buffered in a per-shard FIFO in the first place (e.g., reject/redirect/refund it instead of enqueuing).
- Add a validated invariant, enforced at every receipt-construction site (not just the one exercised in `generate_large_receipt`), that no `Receipt` above `max_receipt_size` can ever be created — including via `DelegateAction`, `GlobalContractDistribution`, or a protocol-version reduction of `max_receipt_size` after receipts already sized for a larger prior limit exist in a buffer.
- As defense-in-depth, allow the FIFO drain to skip a permanently un-forwardable head-of-queue receipt (e.g., moving it to a dead-letter/refund path) instead of unconditionally blocking the whole shard's outgoing queue on `NotForwarded`.

### Proof of Concept
Not independently reproduced within the scope of this analysis. The concrete trigger would require constructing a receipt whose true size exceeds `max_receipt_size` via a path not covered by the same `ReceiptSizeExceeded` validation exercised in `test-loop-tests/src/tests/max_receipt_size.rs` (for example, via a lowered `max_receipt_size` runtime-config parameter after a protocol upgrade while an outgoing buffer already holds receipts sized against the old, larger limit), then observing that `forward_from_buffer_to_shard` never drains past that receipt for the affected receiver shard, while all other receipts destined for the same shard remain buffered/unforwarded across subsequent chunks. Confirming exploitability under the *current* validation set requires further code tracing beyond what was completed here.

    /// Put a receipt in the outgoing receipt buffer of a shard.
    fn buffer_receipt(
        &mut self,
        receipt: Receipt,
        size: u64,
        gas: Gas,
        state_update: &mut TrieUpdate,
        shard: ShardId,
        use_state_stored_receipt: bool,
    ) -> Result<(), RuntimeError> {
        let receipt = match use_state_stored_receipt {
            true => {
                let metadata =
                    StateStoredReceiptMetadata { congestion_gas: gas, congestion_size: size };
                let receipt = StateStoredReceipt::new_owned(receipt, metadata);
                let receipt = ReceiptOrStateStoredReceipt::StateStoredReceipt(receipt);
                receipt
            }
            false => ReceiptOrStateStoredReceipt::Receipt(std::borrow::Cow::Owned(receipt)),
        };

        self.own_congestion_info.add_receipt_bytes(size)?;
        self.own_congestion_info.add_buffered_receipt_gas(gas)?;

        if receipt.should_update_outgoing_metadatas() {
            self.outgoing_metadatas.update_on_receipt_pushed(
                shard,
                ByteSize::b(size),
                gas,
                state_update,
            )?;
        }

        self.outgoing_buffers.to_shard(shard).push_back(state_update, &receipt)?;
        self.stats.buffered_receipts.entry(shard).or_default().add_receipt(size, gas);
        Ok(())
    }
