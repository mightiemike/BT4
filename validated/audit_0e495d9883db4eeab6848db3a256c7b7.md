### Title
FORBID_TRANSFER_TO_CONTRACT governance restriction is enforced only in actuators, and is bypassable via TVM value-transfer opcodes - (File: `actuator/src/main/java/org/tron/core/vm/utils/VMUtils.java`)

### Summary
The `FORBID_TRANSFER_TO_CONTRACT` committee-controlled restriction is checked in `TransferActuator` and `TransferAssetActuator`, but the actual TRX/TRC10 value-transfer logic used inside TVM execution (`CALL`/`CREATE`/`CREATE2`/`SELFDESTRUCT`) goes through `VMUtils.validateForSmartContract` / `MUtil.transfer`, neither of which enforces this flag. Any address can bypass the restriction simply by routing the transfer through a smart contract call instead of a plain `TransferContract`/`TransferAssetContract`, exactly the same class of bug as the SpiritFactory report: the pause/restriction check lives in the "factory"-equivalent layer (the actuators) while the actual value-moving primitive (TVM's `Program`/`MUtil`, analogous to `PancakePair.swap()`) has unrestricted access and ignores it.

### Finding Description
`TransferActuator.validate()` explicitly rejects TRX transfers to contract accounts when the committee has enabled `FORBID_TRANSFER_TO_CONTRACT`: [1](#0-0) 

`TransferAssetActuator.validate()` performs the identical check for TRC10 asset transfers: [2](#0-1) 

However, all TRX/TRC10 value movement performed by TVM execution — `CALL`/`CALLCODE`/`DELEGATECALL` (`Program.callToAddress`), contract creation with an endowment (`Program.createContractImpl`), calls to precompiled contracts (`Program.callToPrecompiledAddress`), and `SELFDESTRUCT` (`Program.suicide`) — validates the transfer only through `VMUtils.validateForSmartContract`, which never reads `getForbidTransferToContract()`: [3](#0-2) 

These call sites are reachable from an ordinary `TriggerSmartContract` transaction: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

`getForbidTransferToContract()` itself is defined only in `DynamicPropertiesStore` and is consulted solely by the two actuators (confirmed by grep: only `TransferActuator.java` and `TransferAssetActuator.java` reference it, besides the store/config/proposal machinery that sets the value): [8](#0-7) 

By contrast, note that a *related* restriction — the `ALLOW_TVM_COMPATIBLE_EVM`/contract-version check — is likewise enforced only in `TransferActuator`, further confirming that the actuators are treated as the sole gatekeepers while TVM's own transfer primitives were never updated to respect these committee-level policies: [9](#0-8) 

### Impact Explanation
When the community/committee enables `FORBID_TRANSFER_TO_CONTRACT` (a real, currently-deployed governance parameter, `ALLOW_CREATION_OF_CONTRACTS`-gated per `ProposalUtil`), the intent is that TRX (and TRC10 tokens) cannot land on smart-contract accounts via ordinary transfers. Any unprivileged user can defeat this policy end-to-end by deploying/calling a trivial contract that performs `address(x).transfer(...)`, `.call.value(...)`, or `(new C).value(...)()`, moving TRX/TRC10 into arbitrary contract accounts despite the restriction being active. This undermines whatever protocol invariant the committee relied on `FORBID_TRANSFER_TO_CONTRACT` for, and demonstrates that a security control intended to be chain-wide is silently limited to one entry path while an equally-reachable "swap"-equivalent path (TVM execution) has unrestricted access — the same architectural flaw the external report flags.

### Likelihood Explanation
High. The bypass requires only a standard `TriggerSmartContract` transaction from any account — no privileged role, leaked key, or malicious peer/node behavior is needed. It is trivially reproducible using any Solidity contract with a `.transfer`/`.call.value`/`selfdestruct`.

### Recommendation
Enforce `getForbidTransferToContract()` (and, for consistency, the `ALLOW_TVM_COMPATIBLE_EVM` version check) inside the single choke point used by all TVM value transfers — `VMUtils.validateForSmartContract` (and/or `MUtil.transfer`) — rather than only in `TransferActuator`/`TransferAssetActuator`. Alternatively, if TVM-originated transfers were intentionally meant to be exempt from this restriction, that exemption should be explicitly documented, since currently it looks like an oversight rather than a deliberate design decision.

### Proof of Concept
1. Committee enables `FORBID_TRANSFER_TO_CONTRACT = 1` via proposal (`ProposalService`/`ProposalUtil`).
2. Attacker deploys a contract `Helper` with `function push(address payable to) public payable { to.transfer(msg.value); }`.
3. Attacker calls `Helper.push(victimContractAddress)` via `TriggerSmartContract` with a TRX value — this goes through `Program.callToAddress` → `VMUtils.validateForSmartContract`, which does not check `getForbidTransferToContract()`, so the transfer succeeds and TRX lands on `victimContractAddress` (a smart contract account) even though the exact same transfer via `TransferContract` would be rejected with `"Cannot transfer TRX to a smartContract."` [1](#0-0) [10](#0-9)

  public static boolean validateForSmartContract(Repository deposit, byte[] ownerAddress,
      byte[] toAddress, byte[] tokenId, long amount) throws ContractValidateException {
    if (deposit == null) {
      throw new ContractValidateException("No deposit!");
    }

    byte[] tokenIdWithoutLeadingZero = ByteUtil.stripLeadingZeroes(tokenId);

    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid ownerAddress");
    }
    if (!DecodeUtil.addressValid(toAddress)) {
      throw new ContractValidateException("Invalid toAddress");
    }

    if (amount <= 0) {
      throw new ContractValidateException("Amount must greater than 0.");
    }

    if (Arrays.equals(ownerAddress, toAddress)) {
      throw new ContractValidateException("Cannot transfer asset to yourself.");
    }

    AccountCapsule ownerAccount = deposit.getAccount(ownerAddress);
    if (ownerAccount == null) {
      throw new ContractValidateException("No owner account!");
    }

    if (deposit.getAssetIssue(tokenIdWithoutLeadingZero) == null) {
      throw new ContractValidateException("No asset !");
    }
    if (!Commons.getAssetIssueStoreFinal(deposit.getDynamicPropertiesStore(),
        deposit.getAssetIssueStore(), deposit.getAssetIssueV2Store())
        .has(tokenIdWithoutLeadingZero)) {
      throw new ContractValidateException("No asset !");
    }

    Long assetBalance = ownerAccount.getAsset(deposit.getDynamicPropertiesStore(),
            ByteArray.toStr(tokenIdWithoutLeadingZero));
    if (null == assetBalance || assetBalance <= 0) {
      throw new ContractValidateException("assetBalance must greater than 0.");
    }
    if (amount > assetBalance) {
      throw new ContractValidateException("assetBalance is not sufficient.");
    }

    AccountCapsule toAccount = deposit.getAccount(toAddress);
    if (toAccount != null) {
      assetBalance = toAccount.getAsset(deposit.getDynamicPropertiesStore(),
              ByteArray.toStr(tokenIdWithoutLeadingZero));
      if (assetBalance != null) {
        try {
          addExact(assetBalance, amount,
              VMConfig.disableJavaLangMath()); //check if overflow
        } catch (Exception e) {
          logger.debug(e.getMessage(), e);
          throw new ContractValidateException(e.getMessage());
        }
      }
    } else {
      throw new ContractValidateException(
          "Validate InternalTransfer error, no ToAccount. And not allowed to create account in smart contract.");
    }

    return true;
  }

  public void saveForbidTransferToContract(long value) {
    this.put(FORBID_TRANSFER_TO_CONTRACT,
        new BytesCapsule(ByteArray.fromLong(value)));
  }

  public long getForbidTransferToContract() {
    return Optional.ofNullable(getUnchecked(FORBID_TRANSFER_TO_CONTRACT))
        .map(BytesCapsule::getData)
        .map(ByteArray::toLong)
        .orElseThrow(() -> new IllegalArgumentException("not found FORBID_TRANSFER_TO_CONTRACT"));
  }
