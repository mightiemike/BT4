## Title
Backup restore accepts unverified `LedgerInfoWithSignatures` (and therefore an unverified state/accumulator root) when the epoch is beyond the locally-known epoch history - (File: `storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
`EpochHistory::verify_ledger_info` — the function meant to bind every `LedgerInfoWithSignatures` consumed during backup restore to a validator-signed chain of trust — silently short-circuits to `Ok(())`, skipping *all* cryptographic verification, whenever the ledger info's epoch is newer than what the locally built `epoch_endings` history covers. Both the state-snapshot restore path and the transaction-chunk restore path load their `LedgerInfoWithSignatures` directly from the (untrusted) `BackupStorage` and rely on this function as the sole check that the ledger info (and thus the state root / accumulator root it certifies) is authentic. When the bypass condition is hit, an attacker who controls the backup storage blob (or can substitute the manifest/proof files) can supply an arbitrary, self-consistent but otherwise unauthenticated `LedgerInfoWithSignatures` + root hash, and the restore pipeline will accept and durably commit it.

This is the exact structural analog of the reported Oracle bug: a validation gate exists (checking that a supplied authority value — here the ledger-info signatures/waypoint, there the oracle address) is authentic, but the check is conditionally skippable, and the caller trusts the (attacker-influenced) value once the check is bypassed.

Both consumers treat this function as the authoritative binding step:

- State snapshot restore, `storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs`: [2](#0-1) 

`txn_info_with_proof.verify(li.ledger_info(), ...)` and the `root_hash == manifest.root_hash` check are purely **internal consistency** checks — they prove the proof is consistent with the *supplied* `li`, not that `li` itself is authentic. Authenticity is supposed to come exclusively from `epoch_history.verify_ledger_info(&li)`.

Same pattern: `txn_list_with_proof.verify` only checks that the transactions/accumulator range proof are self-consistent with the given `ledger_info`; it never checks that `ledger_info` itself was signed by the real validator set unless `epoch_history.verify_ledger_info` does so.

`epoch_endings` is populated by `EpochHistoryRestoreController::run_impl`, which is built strictly from the epoch-ending backup manifests that were selected up to `target_version` (`storage/backup/backup-cli/src/coordinators/restore.rs`, `select_epoch_ending_backups(target_version)`), so it never covers the current, still-open epoch, and can trivially be shorter than required in any scenario where:
- `--skip-epoch-endings` is not used but the epoch-ending backup set passed to the restore run doesn't extend to the epoch of the chunk/snapshot being restored (e.g., a state snapshot inside the currently open epoch, or a partial/incremental restore invocation of `StateSnapshotRestoreController`/`TransactionRestoreBatchController` with a truncated `epoch_history`).

Once the bypass triggers, both `li` (hence `manifest.root_hash`, the JMT root that will be persisted) and the transaction/accumulator data in the chunk are accepted from the untrusted backup store with **zero** signature or waypoint verification, and are committed to durable storage via `restore_utils::save_transactions` / `finalize_state_snapshot` / `AptosDB` write paths.

### Impact Explanation
This breaks the fundamental proof-binding invariant for restore flows: state and transaction data recovered from an external, potentially adversarial backup store must be provably signed by the real validator set for the epoch in question. When the bypass condition is met, the restored node's Jellyfish Merkle root, transaction accumulator root, and committed transactions/write-sets can be fully attacker-controlled without any consensus-derived authenticity check, i.e. the node commits a wrong/corrupted ledger state that it believes to be validated. This is the "Wrong accumulator root ... accepted as valid" / "Committed state that differs from the correct VM result or corrupts durable ledger data" class of impact called out as in-scope.

### Likelihood Explanation
The trigger condition (`epoch > self.epoch_endings.len()`) is reachable through normal, documented restore usage patterns — partial/incremental restores, snapshot-only restores of the currently open epoch, or any invocation where the epoch-ending backup manifests supplied don't extend as far as the chunk being restored — not just misuse. The code even carries a `TODO(aldenhu): fix this from upper level` acknowledging the gap, but the upper-level fix (guaranteeing epoch history always fully covers what's being restored) is not implemented/enforced here, so the unsafe fallback remains live in the shipped code path.

### Recommendation
Remove the silent `Ok(())` fallback. `EpochHistory::verify_ledger_info` should never treat "epoch not yet in local history" as automatically valid. Instead:
- Either require the caller to guarantee (and `ensure!`) that `epoch_history` always fully covers every epoch touched by the current restore/verify batch before invoking any restore step, failing loudly otherwise, or
- Perform the waypoint/signature verification against the currently-known validator set for the too-new epoch (if available) rather than skipping verification, and hard-fail if no trusted reference point exists for that epoch.

### Proof of Concept
1. Prepare a backup restore where `epoch_history` is built only up to epoch `E-1` (e.g. run `StateSnapshotRestoreController` directly, or a `TransactionRestoreBatchController` with an epoch-ending backup list that stops short of the target epoch `E`).
2. Host a malicious `BackupStorage` (or intercept the real one) that serves, for the state-snapshot/transaction manifest whose ledger info is at epoch `E`:
   - An arbitrary `manifest.root_hash` / write-set / transaction set,
   - A self-consistent `TransactionInfoWithProof`/`TransactionAccumulatorRangeProof` built purely from these attacker-chosen values,
   - A `LedgerInfoWithSignatures` at epoch `E` with an empty/garbage/self-signed signature set (no real validator signatures required).
3. Run the restore. `txn_info_with_proof.verify(...)` / `txn_list_with_proof.verify(...)` pass because they only check internal consistency against the attacker-supplied `li`. `epoch_history.verify_ledger_info(&li)` hits `epoch (E) > epoch_endings.len() (E-1)`, logs a warning, and returns `Ok(())`.
4. The attacker-controlled root hash/state/transactions are committed to the local `AptosDB` as if fully verified, corrupting the restored node's ledger state with no cryptographic authenticity behind it.

```rust
    pub fn verify_ledger_info(&self, li_with_sigs: &LedgerInfoWithSignatures) -> Result<()> {
        let epoch = li_with_sigs.ledger_info().epoch();
        ensure!(!self.epoch_endings.is_empty(), "Empty epoch history.",);
        if epoch > self.epoch_endings.len() as u64 {
            // TODO(aldenhu): fix this from upper level
            warn!(
                epoch = epoch,
                epoch_history_until = self.epoch_endings.len(),
                "Epoch is too new and can't be verified. Previous chunks are verified and node \
                won't be able to start if this data is malicious."
            );
            return Ok(());
        }
        if epoch == 0 {
            ensure!(
                li_with_sigs.ledger_info() == &self.epoch_endings[0],
                "Genesis epoch LedgerInfo info doesn't match.",
            );
        } else if let Some(wp_trusted) = self
            .trusted_waypoints
            .get(&li_with_sigs.ledger_info().version())
        {
            let wp_li = Waypoint::new_any(li_with_sigs.ledger_info());
            ensure!(
                *wp_trusted == wp_li,
                "Waypoints don't match. In backup: {}, trusted: {}",
                wp_li,
                wp_trusted,
            );
        } else {
            self.epoch_endings[epoch as usize - 1]
                .next_epoch_state()
                .ok_or_else(|| anyhow!("Shouldn't contain non- epoch bumping LIs."))?
                .verify(li_with_sigs)?;
        };
        Ok(())
    }
```
