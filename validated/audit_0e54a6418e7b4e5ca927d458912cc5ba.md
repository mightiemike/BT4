### Title
GEiC PrivilegedWebContents enables full raw MojoJS bindings for any origin committed in its main frame without checking against the capability allowlist - ([File: chrome/browser/geic/geic_pwc_manager.cc])

### Summary
`GeicPwcManager::TabEntry` and `ChromeContentBrowserClient::ShouldAllowMojoJsBindingsForFrame` grant `EnableMojoJsBindings()` to the primary main frame of a GEiC `PrivilegedWebContents` (PWC) based solely on frame position (outermost main frame of a PWC), without verifying that the frame's *committed origin* is a member of the PWC's capability allowlist. This mirrors the reported bug class — a permission/authorization check that is supposed to gate access to a restricted capability is skipped, letting a context that should not qualify obtain access anyway.

### Finding Description
`GeicPwcManager::TabEntry::RenderFrameCreated` and `ReadyToCommitNavigation` unconditionally call `render_frame_host->EnableMojoJsBindings(/*features=*/nullptr)` for any frame that `IsInPrimaryMainFrame()`, with an explicit code comment acknowledging the gap: [1](#0-0) 

The same shortcut exists in the content-embedder hook `ChromeContentBrowserClient::ShouldAllowMojoJsBindingsForFrame`, which returns `true` for the outermost main frame of *any* `PrivilegedWebContents`, again without checking the committed origin against the capability allowlist: [2](#0-1) 

Enabling MojoJS bindings is a broad grant: it exposes the entire raw `Mojo.bindInterface` JavaScript surface registered for that frame (via `PopulateChromeFrameBinders`) to the committed document, rather than gating access to the single intended interface (`geic::mojom::GeicApi`). By contrast, the dedicated Mojo interface binder for `GeicApi` itself does perform a proper origin/capability check via `pwc::EnforceCapabilityGate` and terminates the renderer on violation: [3](#0-2) 

But that check only protects the narrow `GeicApi` binder — it does nothing to prevent `EnableMojoJsBindings` from being turned on for the frame in the first place. Once MojoJS is enabled for the frame's `RenderFrame`, the committed document can call `Mojo.bindInterface()` directly from script for *any* interface exposed via `PopulateChromeFrameBinders` to that renderer process (e.g. `blink::mojom::CredentialManager`, `translate::mojom::ContentTranslateDriver`, etc., seen registered unconditionally in the same binder map): [4](#0-3) 

If the primary main frame of a GEiC PWC ever commits a document whose origin is not the intended guest origin (e.g., via an open redirect on the guest page, a same-process navigation bug, or any future relaxation of the PWC's navigation policy), that non-allowlisted content still receives the full MojoJS interface surface, because the origin is never re-checked at the `EnableMojoJsBindings` call sites. The authors' own comment states this plainly: "the committed origin is not checked against the capability allowlist here" — an explicit, currently-unpatched TODO (`crbug.com/539909218`).

### Impact Explanation
This is analogous to the reported Discourse bug class: a capability meant to be restricted to a specific, vetted context (the admin-restricted report / here, the specific privileged GEiC guest origin) is instead granted to a broader set of contexts because the authorization check is missing at the point the capability is actually turned on. Here the consequence is more severe than a data-export bypass: enabling raw MojoJS bindings for an unintended origin is a stepping stone to full renderer-side access to privileged browser-process Mojo interfaces, which can lead to cross-origin data disclosure or further sandbox-adjacent compromise if any origin other than the allowlisted GEiC guest ever loads as that frame's document.

### Likelihood Explanation
Exploitation requires the PWC's own navigation-restriction layer (whatever mechanism keeps the PWC's main frame confined to the allowlisted origin) to fail or be bypassed — the code at the `EnableMojoJsBindings` call sites provides no independent defense. Given the explicit "prototype shortcut" comments and the associated open bug (`crbug.com/539909218`), the authors themselves treat this as a known, currently-unmitigated gap rather than a defense-in-depth already covered elsewhere, which raises likelihood relative to a typical redundant check.

### Recommendation
Before calling `EnableMojoJsBindings` (in both `GeicPwcManager::TabEntry::RenderFrameCreated`/`ReadyToCommitNavigation` and `ChromeContentBrowserClient::ShouldAllowMojoJsBindingsForFrame`), verify the frame's (or pending navigation's) origin against the PWC's capability allowlist (the same check performed by `pwc::EnforceCapabilityGate`), and refuse/disable the binding — or terminate the renderer via `bad_message` — when the origin does not match, consistent with how `BindGeicApi` and `BindGeicBrowserHost` already validate the origin before binding.

### Proof of Concept
Not applicable in the strict sense of a working exploit chain, since triggering it depends on an as-yet-unidentified way to make the GEiC PWC's main frame commit a non-allowlisted origin (the code comments indicate the PWC's navigation policy is expected to prevent this today). The vulnerability is the missing defense-in-depth check itself: any future navigation-policy bug in the PWC (redirect handling, renderer-initiated navigation edge case, etc.) that lets a non-guest origin commit in that main frame would immediately grant that origin the entire MojoJS interface surface, because `EnableMojoJsBindings` performs no origin re-validation of its own, as shown at [5](#0-4) .

void GeicPwcManager::TabEntry::RenderFrameCreated(
    content::RenderFrameHost* render_frame_host) {
  // TODO(crbug.com/539909218): Prototype shortcut. This exposes the entire
  // Mojo surface rather than only GeicApi, and the committed origin is not

    render_frame_host->EnableMojoJsBindings(/*features=*/nullptr);
  }

void BindGeicApi(content::RenderFrameHost* render_frame_host,
                 mojo::PendingReceiver<mojom::GeicApi> receiver) {
  // The shared gate enforces the full capability policy (and terminates the
  // renderer itself on a renderer-controllable violation); null simply means
  // do not bind.
  pwc::PrivilegedWebContents* privileged =
      pwc::EnforceCapabilityGate(render_frame_host);
  if (!privileged) {
    return;
  }

  // The gate is component-agnostic; GeicApi additionally requires the
  // component to be GEIC. A request from another component's frame is again a
  // compromised renderer.
  if (privileged->component() != pwc::PrivilegedComponent::kGeic) {
    bad_message::ReceivedBadMessage(render_frame_host->GetProcess(),
                                    bad_message::PWC_BRIDGE_UNQUALIFIED_FRAME);
    return;
  }

void PopulateChromeFrameBinders(

    map->Add<geic::mojom::GeicApi>(&geic::BindGeicApi);
  }
  map->Add<image_annotation::mojom::Annotator>(&BindImageAnnotator);

  map->Add<blink::mojom::ScriptToolHost>(
      &actor::ActorScriptToolReceiver::Create);

      &NavigationPredictor::Create);

      &predictors::LCPCriticalPathPredictorHost::Create);

      &BindDistillabilityService);
