Based on my investigation, the strongest local, high-confidence analog to the external "authorization is checked one layer removed from where the actual privileged action happens" bug class is a **verification-bypass gap in the replay-verify/state-divergence check**, where a comparator function is supposed to be the authoritative gate for "does committed data match the correct VM result" but silently skips the specific proof fields (state checkpoint hashes) that would actually catch a divergence.

### Title
Replay-verification comparator omits state/hot-state/position checkpoint hash checks, masking state divergence - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the function used by the two offline/archival tools whose entire purpose is to detect divergence between locally re-executed VM results and previously committed, authenticated `TransactionInfo` records (`storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`). It checks status, gas, write-set hash, and event root hash, but never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against locally recomputed values.

### Finding Description
`ensure_match_transaction_info` validates only four fields of the recomputed `TransactionOutput` against the archived `TransactionInfo`: [1](#0-0) 

It explicitly acknowledges, in a code comment, that it ignores the checkpoint hashes that bind the actual global state-tree root (and future hot-state/position state roots) to the committed `TransactionInfo`: [2](#0-1) 

This function is the sole verification call in the replay-verify tool's execute-and-compare loop: [3](#0-2) 

`TransactionInfo` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class, separately-hashed fields distinct from `state_change_hash` (the write-set hash): [4](#0-3) 

`state_change_hash` (checked) is only the hash of the *write set produced by this one transaction*; it says nothing about whether that write set was applied correctly to produce the *global Jellyfish Merkle / sparse-merkle state root* recorded as `state_checkpoint_hash`. The state root is computed independently in the executor's checkpoint pipeline (`DoStateCheckpoint`/`get_state_checkpoint_hashes`) and is a completely separate integrity invariant: [5](#0-4) 

Because `ensure_match_transaction_info` never re-derives or compares this root, replay-verify (and the debugger's use of the same function) can silently pass even when:
- the locally recomputed global state tree diverges from the historically committed/authenticated one (e.g. due to a bug in state-tree merklization, hot-state computation, or the new "trading-native" position-state root path referenced directly in the comment), or
- a corrupted archive/backup was fed in with a tampered `state_checkpoint_hash` but a write set that still hashes correctly (write-set hash binds only the write ops, not the resulting merklized root, so this is not automatically implied).

### Impact Explanation
Replay-verify and the debugger's replay-verification path are the primary offline tools operators use to confirm that historical/backed-up ledger data and the deterministic VM replay match. This gap means a real state-root divergence introduced anywhere in the executor's checkpoint/merklization pipeline (including newly added hot-state and position-state roots) is silently not detected by the very tool intended to catch exactly this class of hard-fork-causing bug. This falls squarely in the accepted "hard-fork-only divergence during commit, replay, restore" category: an undetected state-root divergence in production could go unnoticed until nodes fork on-chain, at which point the standard tooling used to triage/confirm the fork gives a false "PASS."

### Likelihood Explanation
The gap is deterministic and guaranteed to trigger (not probabilistic) whenever a state-root-affecting divergence exists but the transaction's own write set is unaffected — this is realistic for bugs in tree-merklization, hot-state eviction bookkeping, or the newly-introduced native-position summary computation (`position_summary_at_commit` / `NativeStateCommitter`), all of which are separate from per-transaction write-set construction. The comment in the code itself flags this as a known, currently real gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), confirming the maintainers are aware the check is currently absent, i.e. it is not a false positive from misunderstanding intended behavior.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the values carried in the supplied `TransactionInfo`, mirroring the reconciliation logic already present in `DoStateCheckpoint::get_state_checkpoint_hashes`. This should be done before any feature (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that depends on these roots is enabled, as the existing TODO comment recommends.

### Proof of Concept
Not directly exploitable as an unprivileged attack path against a live mainnet node (this is a gap in offline tooling, not a consensus-bypass), so no transaction-level PoC applies. The reproduction is: (1) introduce/have a state-root-affecting bug that does not change any single transaction's write set (e.g. in hot-state eviction bookkeeping or the position/native state summary path shown in `storage/aptosdb/src/native_state_committer.rs`); (2) run `replay_on_archive` over the affected version range; (3) observe that `execute_and_verify` returns `Ok(None)` (no failure) despite the state root being wrong, because `ensure_match_transaction_info` never inspects `state_checkpoint_hash`.

**Note on confidence:** I could not fully trace whether any *consensus-critical* (not just offline tooling) code path also relies on this same comparator without independently verifying state-checkpoint hashes elsewhere (e.g., inside `ChunkExecutor`'s commit path); the `ChunkExecutor`/`StateSyncChunkVerifier` code I examined verifies proofs via `TransactionOutputListWithProof::verify`, which itself also does not check `state_checkpoint_hash` — but that field is normally `None` except on the last transaction of a block/checkpoint, and I was not able to fully confirm within the tool-call budget whether some other mainnet-path check independently re-validates the checkpoint hash before commit. This should be verified further before treating the impact as extending beyond offline replay-verify tooling.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
