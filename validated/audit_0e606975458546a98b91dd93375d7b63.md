### Title
Global-contract owner can front-run a pending call to swap in malicious code and steal the attached deposit - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
`DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` lets an account publish WASM code that other accounts reference indefinitely by that account's `AccountId` via `UseGlobalContractAction`, rather than by an immutable code hash [1](#0-0) . Because the reference is mutable, the deploying account can redeploy different code at any time and it takes effect for every account referencing it, exactly the "front-run before the counterparty's transfer completes" pattern from the FootiumClub report: a victim decides to send a deposit based on currently-observed contract behavior, and the owner swaps the logic before the victim's receipt executes.

### Finding Description
`action_use_global_contract` only stores a `GlobalContractIdentifier::AccountId(id)` pointer on the consuming account; it never pins a specific code hash or version [2](#0-1) . The referenced code lives at a single mutable trie slot (`TrieKey::GlobalContractCode`) that the owning account can overwrite by issuing another `DeployGlobalContractAction`; the runtime's own documentation states this is intentional: "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users" [3](#0-2) .

`initiate_distribution` spawns a `GlobalContractDistributionReceipt` that is applied to the current shard's state immediately via `apply_distribution_current_shard`, which unconditionally overwrites the existing code at that identifier's trie key as soon as the receipt is processed [4](#0-3) , then forwards the update to remaining shards over subsequent blocks [5](#0-4) . There is no mechanism requiring consuming accounts' pending FunctionCall receipts to be resolved against the code version that existed when the caller signed/sent their transaction — the pipelining code even calls out that a code-identity change mid-chunk is a known hazard for in-flight function calls and only mitigates it for *within-chunk* preparation ordering, not for the cross-block window an attacker actually needs [6](#0-5) .

### Impact Explanation
An attacker who deploys a global contract in `AccountId` mode and gets other accounts to adopt it (e.g., as a shared "audited" escrow/vault/library contract) can wait until a victim signs and submits a `FunctionCall` with an attached deposit that will be executed by that shared code, then redeploy malicious code to the same `AccountId` identifier before the victim's receipt is processed on the target shard. Because receipts are asynchronous and cross-shard delivery is not atomic with the deploy, this gives the attacker a window — potentially spanning several blocks while the update propagates shard-by-shard — during which they fully control what code runs against the victim's attached balance, enabling outright theft of the deposit (unauthorized value movement) with no on-chain signal to the victim that the logic changed between signing and execution.

### Likelihood Explanation
Reachable by any ordinary transaction signer: deploying a global contract (`AccountId` mode) and referencing it via `UseGlobalContractAction` are both unprivileged actions available to any account, and redeploying is just another signed `DeployGlobalContractAction` from the owner — no special permissions, validator, or network position required.

### Recommendation
Require accounts to pin the specific code version (e.g., a hash captured at `UseGlobalContractAction` time, refreshed only via an explicit opt-in re-binding action) rather than perpetually resolving through a mutable `AccountId` pointer, or add a mandatory activation delay/notification window for `AccountId`-mode redeployments so in-flight receipts against the old code cannot be silently retargeted.

### Proof of Concept
1. Attacker account `A` deploys global contract `V1` in `AccountId` mode; account `B` calls `UseGlobalContractAction` to bind to `GlobalContractIdentifier::AccountId(A)` and publicizes `B` as a trustworthy vault running `V1`'s logic (`runtime/runtime/src/global_contracts.rs:65-98`).
2. Victim `C` inspects `V1`'s code, signs a `FunctionCall` to `B` with a large deposit expecting `V1`'s deposit-handling logic, and broadcasts the transaction.
3. Before `C`'s receipt is applied on `B`'s shard, `A` submits `DeployGlobalContractAction` with malicious code `V2` under the same `AccountId` identifier; `apply_distribution_current_shard` overwrites the shared code as soon as its distribution receipt lands on that shard (`runtime/runtime/src/global_contracts.rs:191-227`).
4. `C`'s `FunctionCall` receipt now executes against `V2`, which redirects or withholds `C`'s deposit to/for `A`, replicating the FootiumClub-style bait-and-switch at the protocol level.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };

fn apply_distribution_current_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
) -> Result<Compute, RuntimeError> {
    let identifier = match &global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => GlobalContractCodeIdentifier::CodeHash(*hash),
        GlobalContractIdentifier::AccountId(account_id) => {
            GlobalContractCodeIdentifier::AccountId(account_id.clone())
        }
    };

    let is_nonce_fresh = check_and_update_nonce(global_contract_data, &identifier, state_update)?;
    if !is_nonce_fresh {
        return Ok(0);
    }

    let config = apply_state.config.wasm_config.clone();
    let trie_key = TrieKey::GlobalContractCode { identifier };
    let code_len = global_contract_data.code().len() as u64;
    state_update.set(trie_key, global_contract_data.code().to_vec());

    // Record the deploy so a same-chunk call can find the code without a warm cache.
    let code_hash = match global_contract_data.id() {
        GlobalContractIdentifier::CodeHash(hash) => Some(*hash),
        GlobalContractIdentifier::AccountId(_) => None,
    };
    if ProtocolFeature::GlobalContractSameChunkCallFix.enabled(apply_state.current_protocol_version)
    {
        state_update.record_global_contract_deploy(ContractCode::new(
            global_contract_data.code().to_vec(),
            code_hash,
        ));
    }

    state_update.commit(StateChangeCause::ReceiptProcessing { receipt_hash: receipt.get_hash() });
