## Analysis

The strongest reachable analog to the WETHGateway "amount > available → should revert but doesn't" bug class is in the workflow **metering/credit accounting** subsystem, not in a gateway/vault/CCIP trust boundary but in `core/services/workflows/metering`, which enforces per-workflow-execution credit spend limits (the mechanism that prevents a workflow from consuming more paid credits than it has been allotted).

### Root cause

`Report.Settle` earmarks a `step.Deduction` amount during `Deduct`, then later reconciles the actual spend (`spentCredits`, aggregated from capability node `ResponseMetadata.Metering` values) against that earmark: [1](#0-0) 

When `spentCredits > step.Deduction`, `step.Deduction.Sub(spentCredits)` is negative, and `balanceStore.Add` explicitly rejects negative inputs: [2](#0-1) 

So `r.balance.Add(...)` returns `ErrInvalidAmount`. Instead of treating this as a hard failure that halts the workflow or forces a fail-closed/reserve top-up, the code merely logs and continues:

```go
if err := r.balance.Add(step.Deduction.Sub(spentCredits)); err != nil {
    // invariant: capability should not let spend exceed reserve
    r.lggr.Info("invariant: spend exceeded reserve")
}

r.balance.AddSpent(spentCredits)
```

This mirrors the reported pattern exactly: an over-limit condition (`repayAmount > amount` / `spentCredits > step.Deduction`) that the code comments even acknowledge as an invariant violation, but which results in silently skipping the correction rather than reverting/failing the operation.

### Why this matters

- `spentCredits` is derived from `SpendValue` fields reported by capability responses (`capabilities.MeteringNodeDetail`) via `ResponseMetadata.Metering`, which is data returned during a DON capability call, not something the local node fully controls at settlement time.
- Because the local balance is never actually decremented by the excess when this invariant fires, the node's local credit-tracking state understates true consumption, `r.balance.AddSpent(spentCredits)` still records the inflated spend for reporting, but the deductible balance used for subsequent `Deduct` calls in the same execution is left stale/too-high.
- Practically this weakens the local fail-fast guard (`ErrInsufficientBalance` in `balance_store.go`) that is supposed to stop workflow executions once credits are exhausted, letting execution continue on an inaccurate balance rather than halting.

### Caveat

Note that this is a **local, in-node accounting cache**; the authoritative billing record is submitted separately via `SubmitWorkflowReceipt` to the billing service, so the blast radius of this specific code path is limited to the local fail-fast/limit-enforcement mechanism inside the node rather than a direct final financial settlement. I want to flag this uncertainty rather than overstate the severity. [3](#0-2) 

Given the rules of this exercise (only accept concrete auth bypass / unauthorized privileged action / unsafe workflow execution / misreporting), this qualifies as a **misreporting / local spend-limit bypass** analog, but it's a much weaker/lower-impact instance than the original WETHGateway bug (no direct on-chain asset transfer occurs here — it's an internal accounting invariant that fails open with only a log message).

### Title
Metering `Report.Settle` silently swallows spend-exceeds-reserve invariant instead of failing the execution - (File: `core/services/workflows/metering/metering.go`)

### Summary
`Report.Settle` computes `step.Deduction.Sub(spentCredits)` and calls `balance.Add()` to refund/adjust the local credit balance. When aggregated capability spend exceeds the amount earmarked at `Deduct` time, `balance.Add` returns `ErrInvalidAmount` (since the argument is negative), and this error path only logs `"invariant: spend exceeded reserve"` without correcting the balance, aborting the step, or failing the workflow execution.

### Finding Description [4](#0-3)  shows the swallowed-error path. The negative-amount rejection comes from [2](#0-1) . `spentCredits` is built from capability-reported `SpendValue` fields processed earlier in `Settle` [5](#0-4) .

### Impact Explanation
The local balance tracking (used to enforce `ErrInsufficientBalance` in subsequent `Deduct` calls within the same workflow execution) is not corrected when the over-limit invariant fires, so the node's fail-fast credit-limit guard can be silently bypassed for the remainder of the execution, while `AddSpent` still records the full (possibly inflated) spend for reporting purposes — a misreporting/limit-enforcement gap rather than a direct fund loss, since final billing truth is reconciled server-side via `SubmitWorkflowReceipt`.

### Likelihood Explanation
Requires a capability response reporting `SpendValue` greater than what was earmarked in `Deduct` for that step; this is explicitly called out in the code's own comment as something that "should not" happen, suggesting it's an edge case rather than a common occurrence, and it depends on capability-side reporting rather than a directly attacker-supplied primitive.

### Recommendation
Treat the `spentCredits > step.Deduction` condition as a hard error: switch the report into metering/fail-open mode explicitly (as done elsewhere via `switchToMeteringMode`) or fail the step/execution, rather than only logging, so the local balance state cannot silently diverge from actual consumption.

### Proof of Concept
Not applicable as a concrete exploit — the path requires a capability response with `SpendValue` exceeding the reserved `step.Deduction`, which is normally bounded by rate-card conversions rather than directly attacker-controlled input; this is flagged as a code-level invariant violation observed via ` [6](#0-5) ` rather than a demonstrated exploit chain.

// Add increases the current credit balance.
func (bs *balanceStore) Add(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	bs.balance = bs.balance.Add(amount)

	return nil
}
