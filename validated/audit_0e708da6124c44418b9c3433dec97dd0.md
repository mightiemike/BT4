Based on my investigation, I found a concrete analog to the reported bug class within `runtime/near-wallet-contract`, which is explicitly in scope per the rules (NEAR wallet contract).

### Title
External-caller deposit is never partially refunded on `rlp_execute` success, even if the forwarded action consumes less than the attached deposit - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point is `#[payable]` and accepts an `attached_deposit` from any external caller/relayer, which is tracked in a `CallerDeposit` struct for potential refund [1](#0-0) . The deposit is refunded to the caller only if the resulting cross-contract promise fails [2](#0-1) . If the promise succeeds, no refund logic exists at all — the entire attached deposit is retained by the wallet contract regardless of whether the actual forwarded Near action (a `Transfer` or `FunctionCall`) required less than what was attached.

### Finding Description
`CallerDeposit::new` only tracks deposits from external (non-self) callers [3](#0-2) . `rlp_execute_callback` refunds this deposit in full only in the `PromiseResult::Failed` branch; the `PromiseResult::Successful` branch simply returns `ExecuteResponse { success: true, .. }` without ever touching `caller_deposit` [4](#0-3) . This is confirmed by the contract's own test suite: `test_caller_refunds` explicitly documents "External caller does not get a refund when their tokens are spent" for the success path, asserting the balance decrease is `>= deposit_amount` [5](#0-4) .

This exactly mirrors the WETHGateway bug class: a caller attaches an amount intended to cover a downstream operation's cost; the amount actually consumed by the downstream operation can be less than what was attached (e.g., a `FunctionCall` action's `deposit` field is a fixed, action-specific value independent of the caller's attached NEAR deposit — see `Action::FunctionCall`/`Action::Transfer` parsing in `internal.rs::parse_tx_data`, where the `yocto_near` embedded in the Ethereum-emulated calldata is capped by `MAX_YOCTO_NEAR` and is a separate, smaller value than what a relayer might attach as `attached_deposit` in the outer Near transaction). Any surplus between the attached NEAR deposit and what the constructed action actually forwards is permanently absorbed by the wallet contract on success, with no skim/reconciliation mechanism.

### Impact Explanation
Any relayer or caller invoking `rlp_execute` with an attached deposit larger than what the wallet contract's parsed action actually requires permanently loses the excess to the eth-implicit account (wallet contract) once the promise succeeds. This is a direct, unauthorized retention of caller funds by the destination account — a concrete unauthorized value movement matching the "Validate" criteria (unauthorized value movement / permanently frozen funds from the caller's perspective). Given that `rlp_execute` is callable by any relayer sending a signed transaction on behalf of a user (not requiring privileged access), and given relayers are expected to attach deposits to cover the emulated ETH `value`, a bug or over-estimation in relayer logic (or a malicious/careless caller overpaying) results in silent fund loss with no recovery path, unlike the failure path which is fully refunded.

### Likelihood Explanation
Medium-High. Any unprivileged relayer or user submitting a `FunctionCall` to `rlp_execute` with `attached_deposit` can trigger this by simply attaching more than strictly required by the constructed action (which is easy given the deposit value is computed off-chain from an RLP-encoded Ethereum transaction, is capped at `MAX_YOCTO_NEAR`, and mismatches are not validated against the outer attached deposit anywhere in `parse_rlp_tx_to_action` or `ExecutionContext`). No special permission or validator/relayer trust is required — a normal external caller (the "caller" in `test_caller_refunds`) reaches this path directly through a standard `FunctionCall` transaction.

### Recommendation
In `rlp_execute_callback` (and the `SelfBaseTokenTransfer`/direct no-promise paths), compute the actual NEAR amount consumed by the dispatched action versus `caller_deposit.yocto_near`, and refund the difference to `caller_deposit.account_id` regardless of promise success, mirroring the deposit-refund logic already used on failure. Alternatively, validate/reject `attached_deposit` values that exceed what the parsed action requires, and/or add an explicit refund-excess step analogous to `Receipt::new_balance_refund` semantics used elsewhere in the runtime's own accounting model.

### Proof of Concept
1. Deploy the wallet contract for an eth-implicit account (as in `test_wallet_contract_interaction`) [6](#0-5) .
2. As an external caller (any account, not the current/self account), call `rlp_execute` with `target` set to some account and `attached_deposit` set to an amount `D` larger than the `yocto_near`/`value` actually encoded in the signed Ethereum transaction's calldata (e.g., a `Transfer`/`FunctionCall` action whose `try_into_near_action` value is `V < D`).
3. Ensure the resulting cross-contract call succeeds (e.g., target a valid, registered account as in the second half of `test_caller_refunds` [7](#0-6) ).
4. Observe: `rlp_execute_callback` returns `success: true` and never issues any promise/transfer back to the caller for the `D - V` surplus; the caller's balance decreases by the full `D` (or more) instead of `V`, and the excess remains permanently in the wallet contract's account.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
