## Analysis

The Sherlock report's root cause is: a mechanism intended for a narrow, implicitly-trusted set of callers (`claimVouch`, meant to bootstrap testers) has no on-chain restriction tying it to that set, so *any* unprivileged caller can invoke it, repeatedly, for free, consuming a shared/unbounded resource. The Push Chain analog is `AccountInitDecorator` in the gasless ante pipeline. [1](#0-0) 

`AccountInitDecorator.AnteHandle` (`app/ante/account_init_decorator.go`) is documented as existing so a freshly-keygen'd Universal Validator hot key can vote for the first time without being pre-funded. In practice the decorator gates only on `IsGaslessTx(tx)` and `!aid.ak.HasAccount(ctx, newAccAddr)` — it never checks that the signer is an actual bonded Universal Validator, nor that the tx's message is one of the vote messages meant for UVs: [2](#0-1) 

`IsGaslessTx` treats `MsgExecutePayload` and `MsgMigrateUEA` as gasless for *any* signer by design (documented explicitly as "Any account may submit the message"): [3](#0-2) [4](#0-3) 

Because the account-init check only requires the tx to be gasless and the signer to be new, any external attacker can:
1. Generate an arbitrary fresh secp256k1 keypair (no funds required, no registration required).
2. Construct a well-formed `MsgExecutePayload` (or `MsgMigrateUEA`) referencing any already-registered chain config (public information) — `ValidateBasic` only checks structural well-formedness, not that the payload will actually succeed later: [5](#0-4) 
3. Self-sign it with account_number=0/sequence=0 and broadcast.
4. `AccountInitDecorator` verifies that self-signature (trivially valid, since the attacker controls both key and message) and unconditionally calls `aid.ak.NewAccountWithAddress` + `SetAccount`, persisting a brand-new account in state — before the message itself is ever dispatched. Even if the subsequent `ExecutePayload` message handler later fails (e.g. "UEA is not deployed"), that failure only rolls back message-level state; the ante-level account creation already committed.

This lets an unprivileged attacker mint unlimited new on-chain accounts at zero token cost, with no per-account or per-block cap, no linkage to UV membership, and no economic cost beyond CPU/bandwidth to sign and broadcast — a direct structural analog of "any user can claim an unbounded amount [of a resource gated for a narrow trusted set] because the code never checks that the caller belongs to that set."

### Title
Unbounded free account creation via `AccountInitDecorator` on `MsgExecutePayload`/`MsgMigrateUEA` gasless txs - (File: app/ante/account_init_decorator.go)

### Summary
`AccountInitDecorator` was designed to let a not-yet-funded Universal Validator hot key submit its first vote transaction without holding gas tokens. However, the decorator gates purely on "is this tx gasless" + "does the signer already have an account," with no check that the signer is an actual bonded UV or that the message is a UV-only vote type. Since `MsgExecutePayload` and `MsgMigrateUEA` are gasless for *any* signer by design, any unprivileged external actor can generate unlimited fresh keypairs and use this path to create unlimited new accounts on-chain for free.

### Finding Description
`IsGaslessTx` marks `MsgExecutePayload`, `MsgMigrateUEA`, `MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, `MsgVoteTssKeyProcess`, and `MsgVoteFundMigration` as gasless without differentiating "vote-only, UV-restricted" messages from "any signer" messages such as `MsgExecutePayload`/`MsgMigrateUEA`. `AccountInitDecorator.AnteHandle` runs before all signature/fee verification for any gasless tx, and if the sole signer has no existing account, it verifies a self-signature over fixed `account_number=0, sequence=0` and then unconditionally creates the account (`NewAccountWithAddress`/`SetAccount`). No check ties this privilege to UV membership, to the specific vote message types the mechanism was designed for, or to any rate limit / cap per signer or per block. The commented rationale ("lets a freshly-keygen'd UV hot key vote on its very first tx") is not enforced in code.

### Impact Explanation
An unprivileged attacker can persist arbitrary numbers of new accounts in canonical chain state at zero monetary cost, using only self-generated keys and structurally valid (but functionally irrelevant/failing) `MsgExecutePayload`/`MsgMigrateUEA` payloads. This is unbounded state growth caused entirely by ordinary, unprivileged transaction submission — a non-network-level denial-of-service/state-bloat vector against the account keyspace, achievable without any privileged role, key compromise, or validator collusion.

### Likelihood Explanation
High reachability: no special permissions, no UV bonding, no token balance, and no successful downstream execution are required — only a fresh keypair and a self-signed gasless tx. The attack is trivially automatable and repeatable per block up to the block gas/tx-count limit, with no economic cost to the attacker.

### Recommendation
Restrict `AccountInitDecorator`'s account-bootstrapping behavior to the specific message types that legitimately need it for unfunded first-time signers (ideally scoped to the UV vote messages: `MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`), and additionally verify the signer is (or is about to become) a registered Universal Validator before creating the account. Alternatively, add a cap on new-account creations per block or a proof-of-relationship requirement so that arbitrary self-generated keys used only for `MsgExecutePayload`/`MsgMigrateUEA` cannot trigger free account creation.

### Proof of Concept
1. Generate N arbitrary secp256k1 keypairs offline (no funding required).
2. For each keypair, build a `MsgExecutePayload` with `UniversalAccountId.ChainNamespace/ChainId` pointing at any already-registered chain config and a syntactically valid `UniversalPayload`/`VerificationData` (values do not need to make the payload succeed downstream — only `ValidateBasic` structural checks must pass, per `x/uexecutor/types/msg_execute_payload.go`).
3. Self-sign the tx with `account_number=0, sequence=0` and broadcast.
4. `AccountInitDecorator.AnteHandle` verifies the self-signature and calls `aid.ak.NewAccountWithAddress`/`SetAccount`, persisting the account — regardless of whether `ExecutePayload`'s later message-level logic (e.g. "UEA is not deployed") fails.
5. Repeat with a fresh keypair each time; each iteration adds one permanent account to state at zero token cost.

```go
func (aid AccountInitDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	if !txpolicy.IsGaslessTx(tx) {
		// Skip account initialization for non-gasless transactions
		ctx.Logger().Debug("account init decorator: non-gasless tx, skipping account init")
		return next(ctx, tx, simulate)
	}

	sigTx, ok := tx.(authsigning.Tx)
	if !ok {
		return ctx, errorsmod.Wrap(sdkerrors.ErrTxDecode, "invalid transaction type")
	}

	signers, err := sigTx.GetSigners()
	if err != nil || len(signers) != 1 {
		ctx.Logger().Debug("account init decorator: could not get unique signer, passing to next handler",
			"num_signers", len(signers),
			"error", err,
		)
		return next(ctx, tx, simulate)
	}

	newAccAddr := signers[0]
	if !aid.ak.HasAccount(ctx, newAccAddr) {
		ctx.Logger().Debug("account init decorator: new account detected on gasless tx, verifying signature",
			"address", sdk.AccAddress(newAccAddr).String(),
			"simulate", simulate,
		)
		// if account does not exist on chain, bypass rest of ante chain (especially gas and signature verification) here.
		// Perform signature verification on account number e and sequence number e instead.
		if err := aid.verifySignatureForNewAccount(ctx, tx, simulate); err != nil {
			ctx.Logger().Debug("account init decorator: signature verification failed for new account",
				"address", sdk.AccAddress(newAccAddr).String(),
				"error", err,
			)
			return ctx, err
		}

		acc := aid.ak.NewAccountWithAddress(ctx, newAccAddr)
		acc.SetSequence(1)
		aid.ak.SetAccount(ctx, acc)
		ctx.Logger().Info("account init decorator: new account created via gasless tx",
			"address", sdk.AccAddress(newAccAddr).String(),
		)
		return ctx, nil
	}
```

```markdown
`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```

```go
func (msg *MsgExecutePayload) ValidateBasic() error {
	// Validate signer
	if _, err := sdk.AccAddressFromBech32(msg.Signer); err != nil {
		return errors.Wrap(err, "invalid signer address")
	}

	// Validate universalAccountId
	if msg.UniversalAccountId == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal account cannot be nil")
	}

	// Validate universal payload
	if msg.UniversalPayload == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal payload cannot be nil")
	}

	// Validate verificationData
	if len(msg.VerificationData) == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "verificationData cannot be empty")
	}
	if _, err := hex.DecodeString(strings.TrimPrefix(msg.VerificationData, "0x")); err != nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "invalid verificationData hex")
	}

	// Validate universalAccountId structure
	if err := msg.UniversalAccountId.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universalAccountId")
	}

	// Validate universal payload structure
	if err := msg.UniversalPayload.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universal payload")
	}

	return nil
}
```
