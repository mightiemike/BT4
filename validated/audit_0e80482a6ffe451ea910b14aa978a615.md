### Title
Named-account `DeleteAccount.beneficiary_id` is never checked for existence, letting a signer irrecoverably burn their own remaining balance - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` deletes an account and forwards its entire remaining balance to `beneficiary_id` in a single, irreversible step, with no confirmation and only syntactic validation of that field. This mirrors the reported bug class: a critical, non-recoverable operation (here, "self-destruct + fund transfer") is performed atomically with a user-supplied destination address, and an incorrect value (a mistyped or non-existent account) leads to permanent, unrecoverable loss — analogous to `VotingEscrow.transfer_ownership` sending ownership to an unintended/invalid address.

### Finding Description
`validate_delete_action` only checks that `beneficiary_id` is a syntactically valid `AccountId` — it never checks that the account actually exists: [1](#0-0) 

`action_delete_account` then unconditionally builds a `Transfer` refund receipt to that `beneficiary_id` for the account's full remaining balance and immediately removes the deleting account, with no existence check performed before or during this step: [2](#0-1) 

The generated refund is a `Receipt::new_balance_refund`, a system-predecessor `Transfer` action: [3](#0-2) 

When that refund receipt is later processed, `check_account_existence` for `Action::Transfer` only allows implicit creation of the receiver account for accounts whose id is an *implicit* address (hash-derived); for an ordinary named (non-implicit) `beneficiary_id` that does not exist, the transfer fails with `AccountDoesNotExist`: [4](#0-3) 

A test confirms this exact failure mode for refund receipts targeting a non-existent account — the account is not created and the outcome is `AccountDoesNotExist`: [5](#0-4) 

Critically, when a refund receipt (`predecessor_id == "system"`) fails, its deposit is **burned** rather than returned to anyone, and the account that would have received the refund is already deleted from state and cannot be recovered: [6](#0-5) 

The comment in the sanity test suite even documents the precondition explicitly: "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund," and separately sets up a real, funded beneficiary specifically so the delete doesn't lose funds: [7](#0-6) 

Put together: `DeleteAccountAction` is a one-shot, non-reversible operation (the docs describe it as deleting the account and all its state) whose only guard on the fund-destination field is a format check, not an existence check: [8](#0-7) 

### Impact Explanation
An unprivileged transaction signer who submits `Action::DeleteAccount { beneficiary_id }` with a mistyped, unregistered, or otherwise non-existent named `AccountId` (a very plausible user error, exactly like Bob's `0x0` mistake in the referenced report) will have their entire remaining account balance permanently burned: the account is deleted immediately and unconditionally, the refund transfer to the missing beneficiary subsequently fails, and failed system refunds are burned rather than returned. This is a permanent, self-inflicted loss of funds triggered by a single transaction with no two-step/confirmation mechanism and no existence check on the critical parameter — directly matching the "permanently frozen/lost funds" impact class.

### Likelihood Explanation
High likelihood of accidental triggering: `beneficiary_id` is a free-form user-supplied `AccountId` on a common, frequently-used action (deleting/cleaning up accounts, contract self-destruct flows, wallet cleanup tools). Any typo, use of a not-yet-created subaccount, or stale/incorrect beneficiary reference is enough. No malicious actor, validator, or privileged role is required — a normal signer or a contract via `promise_batch_action_delete_account` can trigger it against themselves in one transaction, with irreversible effect once submitted.

### Recommendation
Add existence validation (or fail closed) for `DeleteAccountAction.beneficiary_id` before deleting the source account and issuing the balance-transfer receipt — e.g., verify the beneficiary account exists in state at execution time and reject the action (leaving the account intact) if it does not, rather than deleting the account first and only discovering the missing beneficiary after the point of no return. More generally, treat `DeleteAccount` (and any other action that irreversibly destroys state while moving funds to a user-specified address) as a candidate for stronger validation or a two-phase pattern (e.g., require the beneficiary to be confirmed/registered, or perform the existence check as part of the same atomic operation instead of via a follow-up receipt that can fail and burn funds).

### Proof of Concept
1. Alice controls `alice.near` with balance `B` and no locked stake.
2. Alice signs and submits a transaction to `alice.near` with a single action: `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "aliced.near" })`, where `aliced.near` is a syntactically valid but never-created account (typo for an intended destination).
3. `validate_delete_action` accepts the action since `aliced.near` parses as a valid `AccountId` (`runtime/runtime/src/action_validation.rs:447-451`).
4. `action_delete_account` executes: it computes `account_balance = B`, pushes `Receipt::new_balance_refund("aliced.near", B)`, then calls `remove_account` and clears `alice.near` from state (`runtime/runtime/src/actions.rs:380-405`).
5. The refund receipt is later processed as an `Action::Transfer` to `aliced.near`. Since `aliced.near` is a non-implicit account id and does not exist, `check_account_existence` rejects it with `AccountDoesNotExist` (`runtime/runtime/src/actions.rs:842-850`), matching the behavior already asserted in `refund_may_not_create_universal_account` (`runtime/runtime/src/tests/apply.rs:6910-6926`).
6. Because this is a system/refund receipt and it failed, its deposit (`B`) is added to `other_burnt_amount` rather than returned to Alice (`runtime/runtime/src/lib.rs:1047-1054`).
7. Result: `alice.near` no longer exists, `aliced.near` was never created, and Alice's entire balance `B` is permanently burned — an irrecoverable mistake from a single, unconfirmed action, directly analogous to the reported `VotingEscrow.transfer_ownership` scenario.
