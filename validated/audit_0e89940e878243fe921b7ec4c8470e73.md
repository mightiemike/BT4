### Title
OAuth callback shop-parameter confusion between HMAC/state validation and token exchange due to duplicate `shop` query parameters - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
In the OAuth `callback()` handler, the `shop` value used for HMAC/state validation can diverge from the `shop` value actually used to perform the OAuth token exchange, because the two code paths extract duplicate query parameters differently (`URLSearchParams.get()` returns the *first* occurrence, while `Object.fromEntries(query.entries())` collapses duplicates to the *last* occurrence). This is structurally the same bug class as the reported InfinityExchange issue: a security-relevant check is performed against one representation of the ambiguous input while the code subsequently acts on a different, unvalidated representation of that same input.

### Finding Description
`callback()` in [1](#0-0)  extracts `shop` from the request URL using `query.get('shop')!`, which returns the **first** value when a query parameter is repeated.

Later, HMAC and `state` validation is performed against `authQuery`, which is built via `Object.fromEntries(query.entries())` — this collapses duplicate keys to the **last** occurrence: [2](#0-1) .

Finally, the actual token-exchange request target is built again from `query.get('shop')!` (first occurrence), independent from the value that was HMAC/state validated: [3](#0-2) .

`validQuery()` only checks HMAC and `state` against the `authQuery` object, and never re-derives or cross-checks the `shop` value that will actually be used for the request: [4](#0-3) .

This is analogous to the `normalizeQuery` HMAC-validator logic, which explicitly hardens *app proxy* requests against duplicate/array-valued security parameters (`hmac`, `shop`, `signature`, `timestamp`) but does **not** apply the same rejection for the *admin* (OAuth) signator when duplicate values collapse via plain-object semantics: [5](#0-4) . The CHANGELOG entry confirms this hardening (commit `857c598`) was scoped only to app-proxy authentication, not admin OAuth: [6](#0-5) .

In other words: exactly like the ETH/ERC20 bug — where the code checked `msg.value >= totalPrice` (one condition) but never verified that the unrelated `currency` selection matched what was actually being transferred — here the code validates HMAC/state against one interpretation of `shop` (last duplicate) but performs the sensitive action (choosing which merchant domain to exchange the OAuth `code` and `client_secret` against) using a different interpretation (first duplicate) of the same nominally-single-valued field.

### Impact Explanation
An attacker who can get a victim's browser to load a crafted OAuth callback URL (e.g., via a link, redirect, or open-redirect chaining) with a duplicated `shop` parameter can cause the app's HMAC/state validation to authenticate against one shop domain while the subsequent `/admin/oauth/access_token` request — including the app's `client_secret` — is issued against a different, attacker-chosen domain. This breaks the invariant that "the shop that was cryptographically validated is the shop the app talks to," which is the foundation of the OAuth callback's trust model. Depending on how the receiving endpoint interprets the mismatched `code`/`shop` pair, this can manifest as failed/undefined-behavior token exchanges (DoS of the auth handler) or, in more permissive request-parsing environments than `URLSearchParams`/`Object.fromEntries` (e.g., frameworks that merge duplicate query keys differently), full shop-value confusion in a security-relevant path.

### Likelihood Explanation
Reachable by any anonymous/unauthenticated actor who can influence the callback URL a victim's browser requests — no privileged access or leaked secret is required, only crafting a URL with a duplicated `shop=` parameter. The class of "duplicate/repeated security query parameters" was already recognized as an active threat by the maintainers for the app-proxy path (see the `857c598` hardening commit and its accompanying tests, e.g. "rejects a repeated security param" and "Throws a 400 response if the shop param appears more than once"), but the equivalent protection was not extended to the admin OAuth callback path.

### Recommendation
Derive the `shop` value used for the token exchange from the same normalized/validated query object (`authQuery`) that passed HMAC and state verification, rather than re-reading it independently via `query.get('shop')`. Additionally, apply the same duplicate/array-valued rejection used for `APP_PROXY_SINGLE_VALUE_PARAMS` in `normalizeQuery` to the `admin` signator's single-value security parameters (`hmac`, `shop`, `state`, `timestamp`, `code`), so that any duplicate occurrence of these parameters causes an immediate `InvalidOAuthError`/`InvalidHmacError` instead of being silently resolved via inconsistent "first" vs. "last" semantics.

### Proof of Concept
1. Complete OAuth `begin()` normally for a shop the attacker controls (e.g., `attacker-shop.myshopify.com`), obtaining a valid state cookie and receiving a legitimately Shopify-signed callback redirect containing `shop=attacker-shop.myshopify.com&code=...&hmac=...&state=...&timestamp=...`.
2. Craft a URL that duplicates the `shop` parameter, placing the victim's domain first and the attacker's legitimately-signed value second, e.g.:
   `.../auth/callback?shop=victim-shop.myshopify.com&shop=attacker-shop.myshopify.com&code=...&hmac=...&state=...&timestamp=...`
3. Deliver this URL to a victim session that has the matching `shopify_app_state` cookie for the attacker's flow (or replay in attacker's own browser to observe the divergence).
4. Observe: `shop` (line 147, used for logging) and `cleanShop` (line 194, used for the actual token-exchange request URL) both resolve to `query.get('shop')` → `"victim-shop.myshopify.com"` (first value), while `authQuery.shop` used inside `validQuery`/`validateHmac` (line 178) resolves via `Object.fromEntries` → `"attacker-shop.myshopify.com"` (last value) — the value that actually matches the signed HMAC. The security check and the security-sensitive action operate on two different `shop` values derived from the same raw query string.

Note: I was not able to trace how every adapter (`abstractConvertRequest`) normalizes raw incoming query strings across every supported runtime, so I cannot confirm with certainty whether all deployment targets preserve duplicate `shop` parameters through to `request.url` unmodified; this should be verified in a live environment before treating exploitability as fully confirmed.

```typescript
function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
```
