### Title
Unpinned mutable `AccountId`-mode global contracts let an untrusted third party silently swap the code that reinterprets a victim's persisted contract state, causing loss of funds - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
The InsuranceFund report describes a class of bug where an address the contract depends on (`vusd`) can be changed by a privileged actor at any point between a user's deposit and withdrawal, so the withdrawal is settled against a different, unrelated contract than the one the deposit was made under. The nearcore analog is the `GlobalContractDeployMode::AccountId` mechanism: any account can reference shared WASM code by the *identity of its deployer* (`GlobalContractIdentifier::AccountId`) rather than by immutable code hash. Whoever currently owns that deployer `AccountId` can redeploy new code under the same identifier at any time, and every account that resolved its `AccountContract` to `GlobalByAccount(id)` — including deterministic accounts (NEP-616) and universal accounts (`0u…`) that embed this identifier permanently in their `code` field — will execute the new code against their old, already-persisted storage data on their very next call, with no consent, versioning pin, or migration check.

### Finding Description
A `DeployGlobalContractAction` with `deploy_mode: AccountId` publishes code keyed by the deploying account's id rather than by a content hash: [1](#0-0) 

`initiate_distribution` computes the identifier from the `deploy_mode`, and for `AccountId` mode it is always the *same* identifier (`GlobalContractIdentifier::AccountId(account_id)`) across repeated deployments; each redeploy only bumps an internal nonce used purely for idempotent/ordered propagation of the *new* code, not to let consumers pin an old version: [2](#0-1) 

Any account that calls `UseGlobalContract` (or is created via `DeterministicStateInitAction` / `UniversalStateInitAction`) with `contract_identifier: GlobalContractIdentifier::AccountId(owner)` gets `AccountContract::GlobalByAccount(owner)` written into its account record: [3](#0-2) 

Crucially, this is not a snapshot — it is a live pointer. Every subsequent `FunctionCall` on that account re-resolves `GlobalByAccount(id)` to whatever code is *currently* stored under that `AccountId` at execution time: [4](#0-3) [5](#0-4) 

This is confirmed by the test that intentionally exercises the update path: the same `AccountId` identifier resolves to trivial no-op code, then after redeployment resolves to a fully different contract, with *existing* referencing accounts (`account_shard_0`, `account_shard_1`) picking up the swap automatically: [6](#0-5) 

Deterministic accounts make this substantially worse because the `AccountId` reference is baked permanently into the account's identity and cannot be re-chosen: `DeterministicAccountStateInitV1.code: GlobalContractIdentifier` is fixed at creation via `derive_near_deterministic_account_id`, and `deploy_deterministic_account` calls the same `use_global_contract` to install a live pointer, then writes the caller-supplied `data` key/value pairs into the account's persistent contract storage: [7](#0-6) 

Universal accounts (`0u…`) follow the identical pattern via `install_universal_account`/`use_global_contract`: [8](#0-7) 

The consequence mirrors the InsuranceFund bug precisely: a user's account holds persisted state (e.g. a recorded balance/share count written under the semantics of code version N, deployed by some `owner` account), and at any later moment the `owner` account — which is not the victim, not a validator, and requires no special privilege beyond having deployed the original global contract — redeploys different code under the same `AccountId`. The victim's *next* call is executed under the new code against the *old* persisted data, exactly as Alice's withdrawal was settled against `VUSDv2` after her deposit was recorded against `VUSD`. If the new code interprets a stored `data` key differently (different units, different authorization checks, different accounting formula), funds recorded under the old contract's accounting can be misread, misappropriated, or become unwithdrawable — with no way for the affected account to detect or opt out of the swap, since the identifier that was chosen at account-creation time (and for deterministic/universal accounts, embedded in the account id itself) cannot be changed.

### Impact Explanation
Any account that adopts a mutable `AccountId`-mode global contract (via `UseGlobalContract`, `DeterministicStateInitAction`, or `UniversalStateInitAction`) is permanently exposed to unilateral, unauthenticated-by-the-victim code substitution by the identifier owner. Because the account's persisted contract storage (`data`) survives the swap untouched while its interpretation changes, this is a direct analog of the reported "governance changes `vusd` mid-flight" bug: a single third-party action (redeploy) sitting between two of the victim's own transactions can cause concrete, unauthorized value movement or permanent loss of funds recorded in that account's storage. This satisfies "concrete unauthorized value movement... or permanently frozen funds" from the validation criteria.

### Likelihood Explanation
The trigger requires only a standard, permissionless `DeployGlobalContractAction` with `deploy_mode: AccountId` from any account that was ever chosen as a global-contract identifier by a victim — no validator, operator, or protocol-level access is needed. Any dApp encouraging users to create deterministic/universal accounts pinned to a third party's `AccountId`-mode contract (to save per-account storage cost, which is the explicit design incentive: "Global costs a fixed 32-byte identifier and GlobalByAccount costs the publisher id's length" vs. paying for full local code) is exposed. The exploit is a plain two-transaction sequence reachable from RPC/transaction submission alone.

### Recommendation
- For any account intending long-term custody of value (deterministic accounts, universal accounts, or general `UseGlobalContract` adopters), strongly prefer `GlobalContractDeployMode::CodeHash` / `GlobalContractIdentifier::CodeHash`, which is immutable by construction, over `AccountId` mode.
- Consider protocol-level safeguards for `AccountId`-mode global contracts consumed by deterministic/universal accounts: e.g., pin the *nonce* observed at adoption time and require an explicit re-`UseGlobalContract` action to accept a newer version, rather than transparently following the latest code on every call.
- Document loudly (in NEP-616/global-contract docs) that `AccountId`-mode is a live, owner-controlled pointer and is unsuitable for accounts holding persistent value/state whose semantics depend on a specific contract version.

### Proof of Concept
1. Account `owner` deploys global contract V1 (`GlobalContractDeployMode::AccountId`) implementing `deposit`/`withdraw` that records a `shares`/`balance` value in the caller's contract storage under key `"balance"`.
2. Victim account `alice` (or a deterministic/universal account whose `code` is `GlobalContractIdentifier::AccountId(owner)`) calls `UseGlobalContract`/`DeterministicStateInitAction` referencing `owner`, then calls V1's `deposit`, persisting `balance = 1_000_000` in her own account storage (as shown reachable end-to-end in `test_global_contract_update`, `test-loop-tests/src/tests/global_contracts.rs:71-106`).
3. `owner` redeploys new code V2 under the same `AccountId` (`initiate_distribution`, `runtime/runtime/src/global_contracts.rs:143-171`) that reinterprets the `"balance"` key differently (e.g. treats it as a raw yoctoNEAR-scaled index rather than an accounted share count, or omits an authorization check present in V1).
4. `alice` calls `withdraw()` on her account; the runtime resolves her `AccountContract::GlobalByAccount(owner)` to the *current* code, V2 (`runtime/runtime/src/lib.rs:684-700`), which executes against her unchanged persisted `"balance"` data — producing an incorrect payout, permitting an unauthorized drain, or bricking the withdrawal, mirroring exactly the `Alice deposits VUSD → Gov swaps vusd → Alice withdraws 0 VUSDv2` sequence in the original report.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

fn deploy_deterministic_account(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    state_init: &DeterministicAccountStateInit,
    result: &mut ActionResult,
    storage_usage_config: &StorageUsageConfig,
) -> Result<(), RuntimeError> {
    // Step 1: set contract code (includes storage usage accounting)
    use_global_contract(state_update, account_id, account, state_init.code(), result)?;
    if result.result.is_err() {
        return Ok(());
    }

    // Step 2: insert provided key-value pairs
    let mut required_storage_usage = account.storage_usage();
    for (key, value) in state_init.data() {
        let trie_key = TrieKey::ContractData { account_id: account_id.clone(), key: key.to_vec() };

        let value_bytes = value.len() as u64;
        let key_bytes = key.len() as u64;
        let extra_per_record_bytes = storage_usage_config.num_extra_bytes_record;

        let new_bytes = value_bytes
            .checked_add(key_bytes)
            .and_then(|acc| acc.checked_add(extra_per_record_bytes))
            .ok_or(IntegerOverflowError {})?;
        state_update.set(trie_key, value.clone());
        required_storage_usage =
            required_storage_usage.checked_add(new_bytes).ok_or(IntegerOverflowError {})?;
    }
    account.set_storage_usage(required_storage_usage);

    Ok(())
}
