### Title
Unbounded full-keyspace scan in `AssetIssueStore.getAllAssetIssues()` / `RockStoreIterator` reachable via `GetAssetIssueByAccount`/`GetAssetIssueList` gRPC/HTTP APIs - ([File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java])

### Summary
`Wallet.getAssetIssueByAccount`, `Wallet.getAssetIssueList()` (no-arg), and `Wallet.getAssetIssueListByName` all call `AssetIssueStore.getAllAssetIssues()`, which streams the *entire* RocksDB column family via `RockStoreIterator` with no pagination, unlike the paginated variant `getAssetIssueList(offset, limit)`/`getAssetIssuesPaginated`. Since asset issuance via `AssetIssueContract` is a normal, self-funded, unprivileged transaction, an attacker can grow the store size and make each unbounded call proportionally expensive.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` does: [1](#0-0) 
This is a full iteration with `Streams.stream(iterator())`, backed by `RockStoreIterator.hasNext()/next()` which walks the RocksDB keyspace via `dbIterator.seekToFirst()`/`dbIterator.next()` with no limit: [2](#0-1) 

`Wallet.getAssetIssueByAccount` and the no-arg `Wallet.getAssetIssueList()` both call `getAllAssetIssues()` (not the paginated variant) and then filter/iterate in memory over the whole result set: [3](#0-2) 

These are exposed directly via gRPC (`WalletSolidityApi.getAssetIssueList`, `RpcApiService` `getAssetIssueByAccount`) and HTTP (`GetAssetIssueListServlet`): [4](#0-3) [5](#0-4) 

A paginated version (`getAssetIssuesPaginated`/`getAssetIssueList(offset, limit)`) exists in the same class but is not used by `getAssetIssueByAccount` or the no-arg `getAssetIssueList`: [6](#0-5) 

Asset issuance (`AssetIssueContract` via `AssetIssueActuator`) is a standard signed transaction paid for by the issuer's own account balance/bandwidth/energy — no special permission is required beyond normal transaction signing and balance sufficiency: [7](#0-6) 

Rate limiting exists at the gRPC layer (`RateLimiterInterceptor`, default per-endpoint QPS + global QPS + per-IP QPS), which bounds *request rate* but not *per-request cost*: [8](#0-7) 
Because query cost scales with the attacker-controlled size of the `asset-issue` column family (N), even a rate-limited stream of requests (e.g., default 1000 QPS per-endpoint) each triggering an O(N) full scan violates bounded-latency/FAITHFUL_METERING expectations as N grows, since the rate limiter only caps request frequency, not the cost per request.

### Impact Explanation
This is a query-cost amplification / algorithmic-complexity DoS against the RPC-API: each `GetAssetIssueByAccount` or `GetAssetIssueList` call does O(N) work (RocksDB full-column-family scan + protobuf deserialization + list construction) where N is entirely attacker-inflatable by issuing many low-cost assets. Concurrent bursts of such calls can drive sustained CPU/I/O load on the FullNode/SolidityNode RPC service, degrading availability for legitimate RPC clients — matching a "DoS via RPC-API" impact class. It does not corrupt consensus state, steal funds, or leak keys; the impact is bounded to RPC-API resource exhaustion.

### Likelihood Explanation
- Preconditions: no privileged role needed; any funded account can broadcast `AssetIssueContract` transactions repeatedly (paying whatever `AssetIssueActuator` fee applies, adjusted from the issuer's own balance) to grow N.
- The attack is directly reachable through public, unauthenticated read-only RPC/HTTP endpoints (`GetAssetIssueByAccount`, `GetAssetIssueList`, `GetAssetIssueListByName`) that require no special permission.
- The existing gRPC rate limiter (default QPS-based, or IP-based if configured) reduces but does not eliminate the risk, since it does not scale limits by store size and defaults are configurable but not bound to O(1) query cost; an attacker within the default QPS budget (e.g., up to the configured global/IP/API QPS ceiling) can still generate sustained O(N) work per call.
- Repeatability is high: once N is large, every subsequent call by any client (not just the attacker) is slow, meaning the effect is persistent and cheap to trigger repeatedly.

### Recommendation
- Make `Wallet.getAssetIssueByAccount`, `Wallet.getAssetIssueList()` and `Wallet.getAssetIssueListByName` use bounded/paginated access paths instead of `AssetIssueStore.getAllAssetIssues()`, e.g. maintain a secondary index (owner-address → asset ids) rather than a full scan-and-filter.
- Enforce `ASSET_ISSUE_COUNT_LIMIT_MAX`-style caps consistently across all `getAllAssetIssues()` call sites, not just the explicitly paginated API.
- Consider capping/charging additional bandwidth/fee cost proportional to result set size for these read APIs, and/or applying a stricter default rate-limit strategy (e.g., `IPQPSRateLimiterAdapter` with low qps) specifically for `GetAssetIssueByAccount`/`GetAssetIssueList` in `rate.limiter.rpc`/`rate.limiter.http` config.
- Consider imposing an issuance rate limit or increasing/adjusting the asset-issuance fee so that N cannot be trivially inflated to attack-relevant sizes.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  @Override
  public boolean hasNext() {
    if (close.get()) {
      return false;
    }
    boolean hasNext = false;
    // true is first item
    try {
      if (first) {
        dbIterator.seekToFirst();
        first = false;
      }
      if (!(hasNext = dbIterator.isValid())) { // false is last item
        close();
      }
    } catch (Exception e) {
      logger.error(e.getMessage(), e);
      try {
        close();
      } catch (Exception e1) {
        logger.error(e1.getMessage(), e1);
      }
    }
    return hasNext;
  }

  @Override
  public Entry<byte[], byte[]> next() {
    if (close.get()) {
      throw new NoSuchElementException();
    }
    byte[] key = dbIterator.key();
    byte[] value = dbIterator.value();
    dbIterator.next();
    return new Entry<byte[], byte[]>() {
      @Override

        return key;
      }

        return value;

  public AssetIssueList getAssetIssueByAccount(ByteString accountAddress) {
    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues();

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }

      String cName = item.getStrategy();
      String component = item.getComponent();
