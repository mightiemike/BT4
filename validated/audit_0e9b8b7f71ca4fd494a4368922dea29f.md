## Title
Uncached, Untrusted `scalingFactor()` Return Value From Shielded TRC-20 Contract Is Used to Derive Confidential Note Amounts, Enabling Mint/Burn Accounting Divergence - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.checkPublicAmount()` converts a user's transparent `fromAmount`/`toAmount` into the scaled shielded note values that get permanently bound into a zk-SNARK note commitment, by dividing the amount with a `scalingFactor` fetched via a single, uncached `triggerConstantContract` call to the attacker-controllable shielded-TRC20 contract address supplied in the RPC request. Because `scalingFactor()` is treated as an immutable constant but is actually just another external-call return value from an arbitrary, unverified contract, a malicious "shielded TRC-20" contract can return a different `scalingFactor` at proof-build time versus at on-chain execution time, causing the resulting confidential note value baked irreversibly into the shielded pool's Merkle tree to diverge from the transparent amount the contract will actually move on-chain.

### Finding Description
`Wallet.getShieldedContractScalingFactor()` performs an ordinary constant TVM call to `scalingFactor()` on the caller-supplied `shieldedTRC20ContractAddress`: [1](#0-0) 

This value is treated as an authoritative, immutable constant by `checkPublicAmount`, which uses it to derive `scaledFromAmount`/`scaledToAmount` used to build the shielded note that gets committed into the zk proof: [2](#0-1) 

`checkPublicAmount` is invoked once per `createShieldedContractParameters`/`createShieldedContractParametersWithoutAsk` RPC call, and the resulting `scaledFromAmount`/`scaledToAmount` are asserted to exactly equal the receive/spend note values that get bound into the SNARK proof and note commitment (irreversibly, once minted into the shielded pool's Merkle tree): [3](#0-2) 

The value used by the actual on-chain shielded contract when it later executes `mint`/`transfer`/`burn` (triggered separately via `getTriggerInputForShieldedTRC20Contract`, a distinct RPC call, and finally broadcast/executed on-chain) is computed independently by that same contract at execution time, again via its own `scalingFactor()` logic. Nothing in java-tron pins the two reads together or verifies they are consistent. Since the shielded contract's address is fully attacker-supplied/attacker-deployed, `scalingFactor()` is not guaranteed to be an immutable getter — exactly the untrusted-constant-mutation bug class from the report ("`EvilToken.decimals()` returning `block.timestamp % 18`"). An adversarial contract can implement `scalingFactor()` to return one value when queried by the RPC's constant call (used to build/validate the proof and note commitment) and a different value during the actual state-changing execution of `mint()`/`burn()` inside the TVM (e.g., by branching on `msg.sender == precompiled caller` vs a real transaction sender, on block timestamp, or on any other mutable state the contract controls).

This is the java-tron-side analog of the report's core claim: an external "constant" (`decimals()`/`scalingFactor()`) is fetched fresh via an untrusted external call and used, unchecked and uncached, for balance/amount accounting — with no mechanism to guarantee the value used to construct the confidential commitment matches the value the contract will actually enforce on-chain.

### Impact Explanation
The scaled note value derived from a possibly-manipulated `scalingFactor()` is what gets committed into the shielded pool's note commitment tree via `MINT`/`BURN`/`TRANSFER` parameter building. Note values inside the shielded pool cannot be altered after the SNARK proof is generated. If the deployer of the shielded contract crafts `scalingFactor()` to diverge between the off-chain constant-call (used by wallets/full nodes to build parameters through `Wallet.checkPublicAmount`) and the on-chain execution context, users interacting with that pool can be made to mint shielded notes whose committed value does not correspond to the transparent TRC-20 amount actually deposited/withdrawn — a funds-conservation/accounting break in the shielded-transaction feature (over/under-crediting of confidential balances relative to real token movement, or permanent inconsistency that breaks the pool's invariant that shielded value == deposited transparent value). This is a concrete accounting/settlement divergence impact within an unprivileged, publicly reachable wallet/API + shielded-flow code path.

### Likelihood Explanation
Any user can deploy their own "shielded TRC-20" contract (the address is a fully attacker-controlled RPC parameter) and induce victims to interact with it through wallet software that calls `createShieldedContractParameters`/`createShieldedContractParametersWithoutAsk`. No special privileges are required — the attacker only needs to author a Solidity contract whose `scalingFactor()` behaves differently depending on call context, which is trivial (analogous to the report's `EvilToken` PoC). The likelihood of successful exploitation depends on victims using an attacker-supplied/attacker-deployed shielded contract, which is the standard threat model for this bug class (permissionless/malicious ERC-20-like tokens).

### Recommendation
Do not treat `scalingFactor()` (or any other externally-supplied "constant") as trustworthy without validation. At minimum:
- Fetch `scalingFactor()` once, and re-verify at the point the on-chain trigger input is generated (`getTriggerInputForShieldedTRC20Contract`) that it matches the value used to build the zk parameters (i.e., re-check `scalingFactor` consistency before submitting the trigger data), aborting the flow if it changed.
- Where possible, pin `scalingFactor` to the value observed at the specific block used to build the proof, and have the actual on-chain call assert equality rather than silently recomputing independently.
- Document to shielded-pool integrators/users that contracts supplying `scalingFactor()` must be treated as trusted, audited, and immutable, since java-tron's RPC layer cannot itself guarantee this property is honored by arbitrary user-supplied contracts.

### Proof of Concept
1. Attacker deploys a "ShieldedTRC20-like" contract at address `X` whose `scalingFactor()` function returns `1` when called as a constant/static call from `triggerConstantContract` (detectable via `STATICCALL`-style read context or simply via a counter/timestamp heuristic), but returns `1000000` when invoked in the actual state-changing `mint`/`burn` call context.
2. Victim calls `createShieldedContractParameters` with `shieldedTRC20ContractAddress = X` and `fromAmount = 1000000`. `checkPublicAmount` queries `scalingFactor()` (via `getShieldedContractScalingFactor`, `framework/src/main/java/org/tron/core/Wallet.java:4265-4319`), gets back `1`, so `scaledFromAmount = 1000000`. This value is committed into the shielded note (`framework/src/main/java/org/tron/core/Wallet.java:3658-3669`).
3. Victim submits the on-chain transaction (built via `getTriggerInputForShieldedTRC20Contract`) that invokes contract `X`'s `mint()`. On execution, `X` internally computes/uses `scalingFactor() = 1000000`, so it only requires/records a transparent deposit of `1000000 / 1000000 = 1` unit — 1,000,000x less than the amount the victim believes was shielded (as committed in the note now sitting in the shielded pool).
4. Net effect: the shielded pool now contains a note claiming a much larger confidential balance than the transparent tokens actually deposited, breaking the pool's fund-conservation invariant. [2](#0-1) [4](#0-3)

  /**
   * trigger contract to get the scalingFactor, and check the public amount,
   */
  private long[] checkPublicAmount(byte[] address, BigInteger fromAmount, BigInteger toAmount)
      throws ContractExeException, ContractValidateException {
    checkBigIntegerRange(fromAmount);
    checkBigIntegerRange(toAmount);

    BigInteger scalingFactor;
    try {
      byte[] scalingFactorBytes = getShieldedContractScalingFactor(address);
      scalingFactor = ByteUtil.bytesToBigInteger(scalingFactorBytes);
    } catch (ContractExeException e) {
      throw new ContractExeException("Get shielded contract scalingFactor failed");
    }
    if (scalingFactor.compareTo(BigInteger.ZERO) <= 0) {
      throw new ContractValidateException("scalingFactor must be positive");
    }

    // fromAmount and toAmount must be a multiple of scalingFactor
    if (!(fromAmount.mod(scalingFactor).equals(BigInteger.ZERO)
        && toAmount.mod(scalingFactor).equals(BigInteger.ZERO))) {
      throw new ContractValidateException("fromAmount or toAmount invalid");
    }

    long[] ret = new long[2];
    try {
      ret[0] = fromAmount.divide(scalingFactor).longValueExact();
      ret[1] = toAmount.divide(scalingFactor).longValueExact();
    } catch (ArithmeticException e) {
      throw new ContractValidateException("fromAmount or toAmount invalid");
    }

    return ret;
  }

  public byte[] getShieldedContractScalingFactor(byte[] contractAddress)
      throws ContractExeException {
    String methodSign = "scalingFactor()";
    byte[] selector = new byte[4];
    System.arraycopy(Hash.sha3(methodSign.getBytes()), 0, selector, 0, 4);

    TriggerSmartContract.Builder triggerBuilder = TriggerSmartContract.newBuilder();
    triggerBuilder.setContractAddress(ByteString.copyFrom(contractAddress));
    triggerBuilder.setData(ByteString.copyFrom(selector));
    TriggerSmartContract trigger = triggerBuilder.build();

    TransactionExtention.Builder trxExtBuilder = TransactionExtention.newBuilder();
    Return.Builder retBuilder = Return.newBuilder();
    TransactionExtention trxExt;

    try {
      TransactionCapsule trxCap = createTransactionCapsule(trigger,
          ContractType.TriggerSmartContract);
      Transaction trx = triggerConstantContract(trigger, trxCap, trxExtBuilder, retBuilder);

      retBuilder.setResult(true).setCode(response_code.SUCCESS);
      trxExtBuilder.setTransaction(trx);
      trxExtBuilder.setTxid(trxCap.getTransactionId().getByteString());
      trxExtBuilder.setResult(retBuilder);
    } catch (ContractValidateException | VMIllegalException e) {
      retBuilder.setResult(false).setCode(response_code.CONTRACT_VALIDATE_ERROR)
          .setMessage(ByteString.copyFromUtf8(CONTRACT_VALIDATE_ERROR + e.getMessage()));
      trxExtBuilder.setResult(retBuilder);
      logger.warn(CONTRACT_VALIDATE_EXCEPTION, e.getMessage());
    } catch (RuntimeException e) {
      retBuilder.setResult(false).setCode(response_code.CONTRACT_EXE_ERROR)
          .setMessage(ByteString.copyFromUtf8(e.getClass() + " : " + e.getMessage()));
      trxExtBuilder.setResult(retBuilder);
      logger.warn("When run constant call in VM, failed for reason: " + e.getMessage());
    } catch (Exception e) {
      retBuilder.setResult(false).setCode(response_code.OTHER_ERROR)
          .setMessage(ByteString.copyFromUtf8(e.getClass() + " : " + e.getMessage()));
      trxExtBuilder.setResult(retBuilder);
      logger.warn("Unknown exception caught: " + e.getMessage(), e);
    } finally {
      trxExt = trxExtBuilder.build();
    }

    String code = trxExt.getResult().getCode().toString();
    if ("SUCCESS".equals(code)) {
      List<ByteString> list = trxExt.getConstantResultList();
      byte[] listBytes = new byte[0];
      for (ByteString bs : list) {
        listBytes = ByteUtil.merge(listBytes, bs.toByteArray());
      }
      return listBytes;
    } else {
      throw new ContractExeException("trigger contract to get scaling factor error.");
    }
  }
