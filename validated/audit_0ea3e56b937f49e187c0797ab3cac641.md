### Title
Disabled-API filter bypass via leading double-slash in servlet path shifting `split("/")` index - (File: framework/src/main/java/org/tron/core/services/filter/HttpApiAccessFilter.java)

### Summary
`HttpApiAccessFilter.isDisabled` extracts the API name to check against `disabledApiList` by calling `endpoint.split("/")[2]` after `URI.create(endpoint).normalize()`. `URI.normalize()` only removes `.`/`..` segments; it does not collapse a leading `//`, and Java's `String.split("/")` does not merge consecutive delimiters, so a servlet path like `//wallet/getaccount` produces `["", "", "wallet", "getaccount"]`, making index `[2]` resolve to `"wallet"` instead of the intended API name `"getaccount"`.

### Finding Description
`isDisabled` is invoked on every HTTP request via `doFilter`: [1](#0-0) 

The vulnerable check: [2](#0-1) 

For a normal request such as `/wallet/getaccount`, `endpoint.split("/")` yields `["", "wallet", "getaccount"]`, so `[2]` correctly equals `"getaccount"` and is compared against the operator-configured `disabledApiList`. If an unprivileged HTTP client sends a request whose servlet path begins with a doubled slash, e.g. `//wallet/getaccount`, `URI.create("//wallet/getaccount")` parses this as a network-path reference (authority = `"wallet"`, path = `"/getaccount"`), and `.normalize()` performs no dot-segment removal here, so `toString()` still yields `//wallet/getaccount`. Splitting that string by `"/"` produces `["", "", "wallet", "getaccount"]`, shifting index `[2]` to `"wallet"` rather than `"getaccount"`. Since `disabledApiList` only ever contains lowercase method names (e.g. `getaccount`, `getnowblock`, as configured/tested in `HttpApiAccessFilterTest`), `"wallet"` never matches, so `disabled` stays `false` and the request is forwarded to the real servlet, completely bypassing the operator's intended API-disable configuration.

The existing unit tests only cover path-traversal normalization (`/wallet/a/../b/../getnowblock`) and never test a leading double slash, so this bypass is not caught by current coverage: [3](#0-2) 

Additionally, the surrounding `try/catch` fails open: any exception (e.g., an `ArrayIndexOutOfBoundsException` from a shorter path) leaves `disabled` at its initialized value of `false`, so malformed/edge-case paths are never blocked, reinforcing the fail-open design.

Reachability of this bug from the network depends on whether the fronting servlet container (Jetty, embedded in java-tron's HTTP API service) preserves a leading `//` in `HttpServletRequest.getServletPath()` rather than normalizing it before dispatch; I could not fully confirm the exact Jetty URI-compliance configuration used by java-tron within the available context, so container-level normalization behavior remains a caveat for full end-to-end confirmation. The logic bug in `isDisabled` itself, however, is directly demonstrable in isolation.

### Impact Explanation
If reachable end-to-end, this allows any unprivileged remote HTTP client to invoke a wallet/solidity/PBFT API endpoint that the node operator has explicitly disabled via `disabledApiList` (a security/operational control, e.g. to hide sensitive or resource-heavy endpoints), by simply prefixing the path with an extra `/`. This defeats a public-facing access-control mechanism.

### Likelihood Explanation
The `isDisabled` logic flaw is deterministic and requires no special privileges — only crafting an HTTP request path with a leading `//`. The only uncertain precondition is whether the embedded Jetty server passes such a path through unmolested to `getServletPath()`; this needs verification in a live/integration environment.

### Recommendation
Do not derive the API name via raw `split("/")` and a fixed index. Instead, strip a normalized leading slash prefix (collapse repeated leading slashes explicitly), or parse path segments with `URI.getPath()` and filter out empty segments before indexing, e.g. split with `Pattern.compile("/+")` or use a `List<String>` of non-empty segments and take the first meaningful segment. Also make the failure mode fail-closed (treat parse errors as disabled) if operators rely on this filter as a security boundary.

### Proof of Concept
```java
// Add to HttpApiAccessFilterTest.java
@Test
public void testIsDisabledDoubleSlashBypass() throws Exception {
  List<String> list = new ArrayList<>();
  list.add("getaccount");
  CommonParameter.getInstance().setDisabledApiList(list);
  Method privateMethod = httpApiAccessFilter.getClass()
          .getDeclaredMethod("isDisabled", String.class);
  privateMethod.setAccessible(true);

  // Normal path is correctly blocked
  boolean normal = (boolean) privateMethod.invoke(httpApiAccessFilter, "/wallet/getaccount");
  Assert.assertTrue(normal);

  // Same logical endpoint with a leading double slash bypasses the block
  boolean bypass = (boolean) privateMethod.invoke(httpApiAccessFilter, "//wallet/getaccount");
  Assert.assertFalse(bypass); // demonstrates disabled-API bypass
}
```
Expected result: `normal` is `true` (blocked as intended) while `bypass` is `false`, proving that `//wallet/getaccount` evades the `disabledApiList` check even though it targets the same disabled `getaccount` endpoint.

  private boolean isDisabled(String endpoint) {
    boolean disabled = false;

    try {
      endpoint = URI.create(endpoint).normalize().toString();
      List<String> disabledApiList = CommonParameter.getInstance().getDisabledApiList();
      if (!disabledApiList.isEmpty()) {
        disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
      }
    } catch (Exception e) {
      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());
    }

    return disabled;
  }
