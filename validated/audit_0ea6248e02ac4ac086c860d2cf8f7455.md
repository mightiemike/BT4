### Title
Repeated partial resource un-delegation systematically under-transfers usage via floor-rounded division, causing resource-accounting drift - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator#execute` (and its TVM-native mirror `UnDelegateResourceProcessor#execute`) computes `transferUsage`, the fraction of a receiver's consumed bandwidth/energy usage that must move back to the owner when a delegated resource is partially undelegated, using floating-point multiplication truncated to a `long`. Like the reported `LiquidityPool#repay` bug — where `tempDebt` is floor-rounded on every partial repayment, letting dust accumulate against depositors — this calculation floor-rounds on every partial undelegation, letting dust accumulate in the receiver's favor (and against the owner/network's usage accounting) each time it is invoked.

### Finding Description
When an owner partially undelegates BANDWIDTH/ENERGY resources it previously delegated, the actuator must move a proportional share of the receiver's already-consumed usage back to the owner so aggregate usage accounting stays consistent: [1](#0-0) 

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
...
long newNetUsage = receiverCapsule.getNetUsage() - transferUsage;
```

The identical pattern exists in the ENERGY branch and in the TVM-native `UnDelegateResourceProcessor.execute` [2](#0-1) .

`transferUsage = (long)(usage * ratio)` truncates towards zero. This means:
- The receiver's remaining usage (`netUsage - transferUsage`) is always rounded up (kept slightly higher than the mathematically exact proportional remainder).
- The usage credited back to the owner via `unDelegateIncrease`/`processor.unDelegateIncrease` is always slightly less than the exact proportional share it is entitled to.

This exactly mirrors the root cause in the referenced Solidity finding: a proportional "amount remaining after a partial operation" is computed with floor-rounding division, so the party retaining the larger share (here, the receiver, analogous to the depositor pool absorbing dust) is systematically favored while the other party (the owner reclaiming resource, analogous to the pool that should recapture full value) is shortchanged by rounding on every partial operation.

Notably, other, adjacent parts of the resource-accounting subsystem (`ResourceProcessor.increase`, `getUsage`, `divideCeil`, `divideCeilExact`) were specifically hardened with `BigInteger` and ceiling-division (`divideCeilExact`) to eliminate exactly this class of precision loss [3](#0-2) , and `RepositoryImpl` documents that `calculateGlobalLimitV2` was "hardened" to avoid truncation drift [4](#0-3) . The `transferUsage` computation in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor`, however, still relies on raw `double` floor truncation and was not brought under the same hardening umbrella, leaving this specific accounting path exposed to the same rounding-direction issue the hardening effort elsewhere in the codebase was meant to eliminate.

### Impact Explanation
Impact is Low/informational rather than a direct fund-theft bug: the quantities involved are bandwidth/energy "usage" counters (not TRX balances), and each individual truncation error is at most 1 unit. However, because `UnDelegateResourceActuator` can be invoked repeatedly and cheaply (partial undelegation is a normal, low-cost operation), an owner/receiver pair that repeatedly performs small partial undelegate operations will cause the receiver's recorded usage to drift persistently higher than it should be relative to the owner's, and the sum of `ownerCapsule.getNetUsage() + receiverCapsule.getNetUsage()` after repeated partial undelegations will diverge from what it would be under exact proportional accounting. This is an invalid-state/accounting-divergence issue: the two accounts' resource usage windows no longer reflect the actual historical consumption split, which can let an attacker who controls both the owner and receiver accounts marginally under-report usage on the side that matters for future free bandwidth/energy computation, effectively obtaining slightly underpriced resource capacity over many repetitions.

### Likelihood Explanation
Likelihood is High for the rounding drift to occur (it fires on essentially every partial-balance undelegate call whenever `unDelegateBalance` is not an exact divisor of `getAllFrozenBalanceForBandwidth()`/`getAllFrozenBalanceForEnergy()`), consistent with the "High likelihood" rating given to the analogous Solidity finding. It requires no special privilege — `UnDelegateResourceActuator` is invoked by any account via a standard `UnDelegateResourceContract` transaction, and the TVM-native path is reachable by any contract exercising the resource-delegation precompile/native contract.

### Recommendation
Round the `transferUsage` (and the corresponding `unDelegateMaxUsage`) calculations using integer/`BigInteger` ceiling-division consistent with the hardening already applied elsewhere in `ResourceProcessor`/`RepositoryImpl` (e.g., using `divideCeilExact`-style BigInteger arithmetic instead of `(long)(double * double)` truncation), so that the receiver's usage transferred back to the owner is never systematically under-reported. Apply the fix symmetrically in both `UnDelegateResourceActuator.execute` and `UnDelegateResourceProcessor.execute`.

### Proof of Concept
Exact end-to-end drift quantification (i.e., a numeric worked example showing cumulative divergence in `netUsage`/`energyUsage` across N partial-undelegate calls) was not verified against a running node/test harness in this session; the existing test suite (`UnDelegateResourceActuatorTest#testPartialUnDelegateForBandwidth`, `#testPartialUnDelegatedForCpu`) exercises single partial-undelegate calls with divisor-friendly numbers (`delegateBalance / 2`) that do not surface the truncation, so the rounding-drift behavior is inferred directly from the source code's use of `(long)(double)` truncation rather than confirmed via a failing test. A concrete PoC would need to choose `unDelegateBalance`/`getAllFrozenBalanceForBandwidth()` ratios that don't divide evenly and perform repeated partial `UnDelegateResourceContract` calls while asserting the sum of owner+receiver usage against the theoretical exact value.
