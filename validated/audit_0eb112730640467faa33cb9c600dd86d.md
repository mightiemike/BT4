## Finding

### Title
Unbounded memory growth from unlimited gzip decompression of client-supplied program data - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
The RPC layer's `decompress_program` function decompresses a gzip-compressed, base64-encoded Cairo program supplied via a client-controlled input (a deprecated/Cairo 0 contract class `program` field) with **no size or time limit**, directly mirroring the Suricata CVE-2025-64334 bug class (attacker-controlled compressed payload decompressed without a bound, causing unbounded memory growth).

### Finding Description
`decompress_program` base64-decodes the input, then feeds it into a `flate2::read::GzDecoder` and calls `read_to_end` on an unbounded `Vec<u8>`, with an explicit TODO acknowledging the missing guard: [1](#0-0) 

```rust
pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.
    let mut decoder = GzDecoder::new(compressed_data.as_slice());
    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}
```

This is unlike the properly-bounded decompression paths found elsewhere in the codebase, which explicitly cap decompressed output:
- `starknet_api::compression_utils::decompress_with_size_limit`, which uses `.take(max_size + 1)` before `read_to_end` and errors if the limit is exceeded: [2](#0-1) 
- `apollo_storage::compression_utils::decompress`, which bounds zstd decompression via `zstd::bulk::decompress(data, MAX_DECOMPRESSED_SIZE)`: [3](#0-2) 
- The HTTP gateway's `RequestDecompressionLayer`, deliberately wrapped with `RequestBodyLimitLayer` both before and after decompression to bound decompressed body size ("preventing zip bombs from expanding in memory"): [4](#0-3) 

`decompress_program` is the outlier: it is called when converting a client-provided `ApiContractClass::DeprecatedContractClass` (Cairo 0 class, e.g. via declare-transaction simulation/estimate/trace RPC methods that accept a `program` payload) — a value under direct control of the RPC caller/transaction submitter — and the compressed program bytes are decompressed into an unbounded `Vec<u8>`. A small, highly-compressible payload (a classic "zip bomb") can therefore expand to a very large size in memory during a single RPC call, since neither the decompressed size nor decompression time is bounded.

### Impact Explanation
An attacker can submit a small gzip-compressed payload (compression ratios well over 1000:1 are trivially achievable with gzip) as the `program` field of a Cairo 0 contract class in an RPC call that triggers `decompress_program` (e.g., `estimate_fee`/`simulate_transaction`/trace endpoints handling a declare transaction). Each such call causes the RPC-serving process to allocate and fill an unbounded buffer, exhausting memory and potentially crashing or degrading the sequencer's RPC/read service. Repeated or concurrent requests amplify the effect. This is a resource-exhaustion / availability issue reachable by any unprivileged transaction submitter or class declarer through a documented RPC surface, consistent in bug class to the reported Suricata CVE (decompression without a size cap leading to unbounded memory growth).

### Likelihood Explanation
High. No authentication or special privilege is required — any client able to call the affected RPC method with a crafted Cairo 0 class `program` field can trigger it. The vulnerable code path is explicitly flagged as missing controls (`// TODO(dan): add time and size limits.`), and analogous code paths elsewhere in the same codebase already implement proper size-limited decompression, confirming that this omission is atypical for this codebase and not an intentionally-accepted risk.

### Recommendation
Apply the same bounded-decompression pattern already used in `starknet_api::compression_utils::decompress_with_size_limit` (or `apollo_storage::compression_utils::decompress`) to `decompress_program`: wrap the `GzDecoder` reader with a hard byte cap (e.g., `.take(max_size + 1)`) before calling `read_to_end`, and reject the input with an explicit error if the decompressed size exceeds the configured maximum program size. Also consider adding a decompression time budget as the existing TODO suggests.

### Proof of Concept
1. Construct a Cairo 0 `program` object and gzip-compress an extremely repetitive/large JSON body (e.g., a few KB compresses to a very small size but expands to hundreds of MB or more when decompressed).
2. Base64-encode the compressed bytes and submit it as the `program` field of a `DeprecatedContractClass` in an RPC call path that reaches `decompress_program` (e.g., simulate/estimate/trace call embedding a declare transaction with this class).
3. Observe the RPC server process's memory usage grow unbounded during `decoder.read_to_end(&mut decompressed)` in `crates/apollo_rpc/src/v0_8/api/mod.rs` line 680, with no cap or early termination, potentially exhausting available memory.

Note: I was unable to confirm from the index alone the exact call site that feeds attacker-controlled `program` bytes into `decompress_program` (the second occurrence of this symbol was not fully retrievable due to index truncation), so the precise RPC method name(s) reaching this function could not be fully enumerated — a Devin session with full repo access would be needed to trace the exact call chain and confirm which RPC methods are affected.

```rust
/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
```
