### Title
Callers overpaying `rlp_execute`'s attached deposit lose the excess permanently on success — no refund for over-attached NEAR - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point is a `#[payable]` method that any unprivileged caller (typically a relayer, but reachable by any account) can call, attaching an arbitrary NEAR deposit to fund the underlying emulated Ethereum action (transfer, function call, ERC-20 transfer, etc.). The contract only tracks this deposit for a refund path that fires **when execution fails**; when the wrapped action **succeeds**, none of the attached deposit is refunded to the caller — even if the amount attached vastly exceeds what the action actually required. This mirrors the Cally `buyOption()` bug class: a caller-supplied payment amount is checked/consumed leniently (accepted deposit ≥ actual cost) with no mechanism to return the excess to the payer, so the surplus is captured by an unintended party (here, the wallet contract / underlying account owner) instead of the caller who overpaid.

### Finding Description
`rlp_execute` is `#[payable]`, so any caller can attach any `attached_deposit()` value: [1](#0-0) 

The deposit is captured into a `CallerDeposit` purely to support **failure** refunds: [2](#0-1) 

`inner_rlp_execute` builds the `ExecutionContext` from `env::attached_deposit()` and threads `caller_deposit` through every promise chain (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) regardless of whether the actual on-chain action (a `Transfer`/`FunctionCall` with its own, independently-specified `yocto_near`/`deposit` value decoded from the RLP transaction) needs anywhere near that much NEAR: [3](#0-2) 

The contract's own test suite documents and asserts this exact behavior — the caller's attached deposit is retained in full once the wrapped action executes successfully, with no check that the deposit matches (or is refunded down to) the actual cost of the action: [4](#0-3) 

In the test, `deposit_amount` of 3 NEAR is attached to a `FunctionCall` action whose own encoded value (`yocto_near: 0`) requires no deposit at all. On the failure path the caller is refunded (asserted at line 210-213), but on the success path the assertion explicitly confirms the caller's balance drops by **at least** the full `deposit_amount` (line 222-226) — i.e., the entire over-attached deposit is consumed/retained rather than returned, exactly analogous to `buyOption()` accepting `msg.value >= premium` and forwarding the whole `msg.value` to the vault creator instead of only the exact `premium`.

### Impact Explanation
Any unprivileged relayer or third-party caller invoking `rlp_execute` on a Wallet Contract account can lose real NEAR value if they attach more than strictly necessary to cover the emulated Ethereum transaction's value + gas costs. Because there is no `==`-style exactness check nor an excess-refund path on the success branch, that surplus balance is transferred into the wallet contract's underlying account (controlled by the Ethereum-derived key holder) with no reimbursement — a concrete, protocol-level unauthorized value transfer from the caller to an unintended beneficiary. This is especially dangerous for automated relayer infrastructure that must estimate deposits conservatively (attaching buffer amounts to be safe against gas/storage-deposit variability, as seen in the NEP-141 relay-fee flows), since every successful call with a conservative overestimate permanently donates the difference to the wallet owner.

### Likelihood Explanation
High reachability: `rlp_execute` is a public, payable method callable by any account with a single transaction; no special privileges, keys, or validator/relayer trust assumptions are required to trigger the loss — only miscalculating (or intentionally padding) the attached deposit relative to the actual action cost, which is a normal operational hazard for relayer software given variable gas/storage-deposit requirements (e.g. the NEP-141 `storage_deposit` top-up flow).

### Recommendation
On the success path, compute the exact NEAR cost consumed by the wrapped action (transfer amount, function-call deposit, and any relayer fee already accounted for) and refund any remainder of the `CallerDeposit` back to `caller_deposit.account_id`, mirroring the refund-on-failure code path. Alternatively, require `attached_deposit()` to equal the computed required cost exactly (rejecting overpayment) rather than silently accepting and retaining any surplus.

### Proof of Concept
The existing test `test_caller_refunds` in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs` (lines 170-229) is itself the proof of concept: a caller attaches 3 NEAR to fund a `register` `FunctionCall` action whose own value field is `yocto_near: 0`; when that call succeeds, the test asserts the caller's balance decreases by the *entire* attached amount, confirming no excess refund occurs — demonstrating the overpayment/no-refund vulnerability class.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
