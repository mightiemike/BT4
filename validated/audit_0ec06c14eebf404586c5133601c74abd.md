### Title
Attacker-controlled `action.gas()` can abort the Wallet Contract's promise callback before it resets `has_in_flight_tx`, permanently bricking the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (the eth-implicit-account emulation contract that lets an Ethereum-style signed transaction drive a NEAR action) computes the static gas attached to its own callback as `ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())` and `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`, where `action.gas()` is the gas value decoded directly from the user-submitted (or relayer-submitted) RLP-encoded Ethereum transaction. This is analogous to the reported Solidity issue of hard-coding/relying on a fixed, externally influenced gas budget for a follow-up call: instead of a 2300-gas `transfer()` stipend that is too small, here the "stipend" for the *callback that must reset critical contract state* is inflated by attacker-controlled input, which can make the callback exceed the gas actually available and abort before it can reset `has_in_flight_tx`. [1](#0-0) [2](#0-1) 

### Finding Description
`rlp_execute` sets `has_in_flight_tx = true` before returning a promise chain, and this flag is only ever reset back to `false` inside the private callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), as the very first statement of each: [3](#0-2) [4](#0-3) 

For two transaction kinds (`EOABaseTokenTransfer` with `address_check`, and `ERC20Transfer`), the contract schedules a lookup/`storage_balance_of` call `.then()`-chained to its own callback, and it funds that callback's static gas as `ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())` or `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`: [5](#0-4) [6](#0-5) 

`action` is derived from `internal::parse_rlp_tx_to_action`, i.e. decoded from the raw RLP bytes the caller supplies to `rlp_execute` as `tx_bytes_b64` — an unprivileged transaction/RLP submitter fully controls the encoded gas field of the emulated action (e.g. the gas attached to the emulated `ft_transfer` FunctionCall for an ERC20Transfer). Static gas attached via `Promise::then(...).with_static_gas(..)` is deducted from the *current* receipt's remaining prepaid gas budget when the outgoing action is appended (the same mechanism documented for `promise_batch_action_function_call`/`GasExceeded`, see `docs/architecture/how/gas.md` and the gas-counter tests, where exceeding available prepaid gas for an outgoing action aborts the whole function call with `GasExceeded`): [7](#0-6) [8](#0-7) 

The wallet contract itself already demonstrates and tests this exact abort behavior for `rlp_execute` (insufficient gas aborts the whole call with "Exceeded the prepaid gas."): [9](#0-8) 

If a user (or a malicious/faulty relayer acting on the user's signed RLP transaction) supplies a large `action.gas()` value in the emulated transaction — either because the encoding permits values up to `u64::MAX`/300 Tgas or simply larger than the unspent gas left in `address_check_callback`/`nep_141_storage_balance_callback` at the point the outer `.then()` is scheduled — the outgoing `.then(ext.address_check_callback(...))`/`.then(ext.nep_141_storage_balance_callback(...))` action creation can fail with `GasExceeded` inside `inner_rlp_execute`, or, more critically, the *second*-stage callback itself (`address_check_callback`/`nep_141_storage_balance_callback`) can abort with `GasExceeded` when it tries to schedule `.then(ext.rlp_execute_callback(...))` using `callback_gas` derived the same way, because a `GasExceeded` panic reverts *all* state changes made in that receipt's execution, including the line `self.has_in_flight_tx = false;` that was supposed to run first.

Because `has_in_flight_tx` gating is checked unconditionally at the top of `rlp_execute`: [10](#0-9) 

...once a receipt that was supposed to clear this flag aborts instead of completing, there is no other contract method that can ever reset `has_in_flight_tx` back to `false`. Every future `rlp_execute` call, from any relayer or the account owner directly, will unconditionally return `"transaction already in progress"` forever. The account (and any NEAR/NEP-141 tokens or eth-implicit balance controlled by this wallet contract) becomes permanently unusable — a transaction-triggered permanent halt of the account's execution path.

### Impact Explanation
This matches the allowed "permanently frozen funds" / "transaction-triggered halt" impact class: the account controlled by the Wallet Contract becomes permanently unable to execute any further Ethereum-emulated transaction (base-token transfers, ERC-20 transfers, or arbitrary NEAR actions routed through `rlp_execute`), since `has_in_flight_tx` can never be cleared again. This is triggerable by a single crafted transaction from an unprivileged signer/relayer submitting an RLP-encoded transaction with an oversized `gas` field for the emulated action, requiring no validator or node compromise.

### Likelihood Explanation
Likelihood depends on: (1) whether `parse_rlp_tx_to_action` bounds/clamps the decoded gas value before constructing `action`, and (2) whether `ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())` can realistically exceed the unspent gas of the enclosing call given NEAR's 300 Tgas `max_total_prepaid_gas` ceiling. I was not able to fully verify the exact bounds/clamping logic inside `parse_rlp_tx_to_action` / `eth_emulation.rs` / `types.rs` within the available tool budget — these files define how the RLP-decoded gas value is turned into `action.gas()` and whether any explicit cap is applied there. This is the key remaining uncertainty for confirming exploitability versus the contract already defending against it (e.g., via a hard-coded gas cap for FunctionCall actions in emulated ERC-20 transfers).

### Recommendation
- Reset `has_in_flight_tx = false` unconditionally as early as possible and make the recovery path independent of whether the subsequent `.then()` call gets funded successfully — e.g., persist/clear the in-flight flag in a step that cannot fail due to gas exhaustion caused by attacker-supplied `action.gas()`.
- Clamp `action.gas()` to a safe, protocol-aware maximum before using it to compute `callback_gas`, so `ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())` (and the NEP-141 equivalent) can never exceed the gas actually available to the current call.
- Add an explicit, recoverable "unstick" mechanism (e.g., a privileged or time-boxed self-call) that can reset `has_in_flight_tx` if a chained promise fails to resolve, instead of relying solely on every callback completing successfully.

### Proof of Concept
1. Attacker (or the account owner) crafts an RLP-encoded Ethereum transaction representing an `ERC20Transfer` (or `EOABaseTokenTransfer` with `address_check`) where the encoded gas field is set to a very large value.
2. Attacker calls `rlp_execute(target, tx_bytes_b64)` on the Wallet Contract. `inner_rlp_execute` sets up `.then(ext.nep_141_storage_balance_callback(...))` (or `.then(ext.address_check_callback(...))`) with `callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` [11](#0-10) .
3. `has_in_flight_tx` is already set to `true` by `rlp_execute` before the promise resolves [12](#0-11) .
4. When the chained callback executes and itself tries to schedule the next `.then(ext.rlp_execute_callback(...))` using the same inflated gas value, if the requested static gas exceeds the unspent prepaid gas of that receipt, the call aborts with `GasExceeded` (as demonstrated for `rlp_execute` itself in `test_insufficient_gas`) [13](#0-12) , reverting the `self.has_in_flight_tx = false;` write that was supposed to happen at the top of that callback.
5. Every subsequent call to `rlp_execute` on this account now unconditionally returns the "transaction already in progress" error [14](#0-13) , permanently freezing the account's ability to transact through the Wallet Contract.

Note: this PoC's exploitability hinges on confirming that `action.gas()` is not clamped during RLP parsing (in `internal.rs`/`eth_emulation.rs`) to a value that always keeps `callback_gas` within the receipt's available gas — I could not fully verify this bound within the current investigation and flag it as the main open question for validation.

                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();

            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

### Gas in Contract Calls

A function call has a fixed gas cost to be initiated. Then the execution itself
draws gas from the `attached_gas`, sometimes also called `prepaid_gas`, until it
reaches zero, at which point the function call aborts with a `GasExceeded`
error. No changes are persisted on chain.

async fn test_insufficient_gas() -> anyhow::Result<()> {

        &wallet_sk,

        .inner
        .call(crate::tests::RLP_EXECUTE)
