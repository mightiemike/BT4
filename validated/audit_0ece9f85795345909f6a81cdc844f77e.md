### Title
`CLEAN_INTERVAL`/`SHRINK_INTERVAL` in `AccountsBackgroundService` assume a fixed slot-time, causing disproportionate storage growth as protocol slot-time decreases - (File: runtime/src/accounts_background_service.rs)

### Summary
`AccountsBackgroundService`'s main loop paces `clean_accounts` and `shrink_candidate_slots`/`shrink_ancient_slots` using fixed wall-clock durations (`CLEAN_INTERVAL = 50s`, `SHRINK_INTERVAL = 1s`) that were sized under an assumed average slot time. The codebase now supports multiple feature-gated slot-time regimes down to 200ms (`runtime/src/slot_params.rs`), meaning the number of slots (and therefore append-vec storages/dirty state) produced within a fixed wall-clock interval can be up to 2x what the interval was tuned for, without the background-cleaning cadence being adjusted. This mirrors the reported bug class: a protocol behavior gated on wall-clock time implicitly assumes a fixed block time, and when the real block time diverges, the behavior becomes proportionally wrong and the divergence accumulates because the timers are never rescaled.

### Finding Description
`MIN_LOOP_INTERVAL`, `CLEAN_INTERVAL`, and `SHRINK_INTERVAL` are hardcoded `Duration` wall-clock constants: [1](#0-0) 

The comment directly states the sizing rationale is time-based, tied to an assumed slot cadence: "Set the clean interval duration to be approximately how long before the next incremental snapshot request is received... The default incremental snapshot interval is 100 slots, which ends up being 40 seconds plus buffer" [2](#0-1) . This 40-second-for-100-slots derivation assumes ~400ms/slot (the `LEGACY_SLOT_PARAMS.ns_per_slot = 400_000_000` baseline) [3](#0-2) .

These timers directly gate the frequency of `clean_accounts`, `shrink_candidate_slots`, and `shrink_ancient_slots` calls in the main service loop: [4](#0-3) 

The runtime already supports feature-gated slot-time reductions to 350ms/300ms/250ms/200ms, each with its own `ns_per_slot` and `slots_per_year`: [5](#0-4) , and `SLOT_TIME_REDUCTION_PARAMS` activates these via feature gates in sequence: [6](#0-5) . Once such a feature activates, `ns_per_slot` drops (e.g., to 200_000_000, i.e., 2x faster than the 400ms baseline the `CLEAN_INTERVAL` comment assumes), yet `CLEAN_INTERVAL`/`SHRINK_INTERVAL` remain unchanged constants — they are not derived from `SlotParams::ns_per_slot()` or `Bank::slot_params_at_slot`.

As a direct consequence, in a 200ms-slot regime, twice as many slots (and thus roughly twice the number of AppendVec storages, dirty-store entries, and shrink candidates) accumulate within the same 50-second `CLEAN_INTERVAL` window compared to what the interval was tuned for. This is functionally identical to the reported issue: a fixed-duration parameter implicitly encodes an assumed time-per-block, and when the real time-per-block changes, the intended cadence of storage/index maintenance work becomes proportionally wrong. Unlike the interest-rate case, this does not corrupt balances or hashes, but it does directly increase `AccountsDb` storage retention windows and CPU burst size when clean/shrink finally executes, since more dirty slots/candidates get batched.

### Impact Explanation
This falls under "disproportionate storage and CPU cost," an accepted impact category. With shorter slot times, `dirty_stores`, `shrink_candidate_slots`, and uncleaned-pubkey backlog can grow roughly proportionally more between clean/shrink passes (see `sweep_slots_after_snapshot` and `shrink_candidate_slots` batching logic at [7](#0-6) ), increasing peak storage retained on disk and the size/duration of each clean/shrink burst — worsening latency spikes and validator resource usage disproportionate to what the interval constants were designed for.

### Likelihood Explanation
Likelihood is currently low-to-moderate: the 200ms/250ms/300ms/350ms slot-time reduction features exist in `runtime/src/slot_params.rs` but their cluster-wide activation status is not verifiable from this index. If/when any of these features activate on mainnet, every validator running this code is affected simultaneously and continuously — this is not a race condition or attacker-triggered edge case, but a systemic, deterministic effect of the feature activating, matching the "no manual adjustment happens automatically" concern in the original report.

### Recommendation
Derive `CLEAN_INTERVAL`/`SHRINK_INTERVAL` (and any other wall-clock-based scheduling in `AccountsBackgroundService`) from the bank's current `ns_per_slot`/`SlotParams` (already exposed via `Bank::slot_params_at_slot` / `current_slot_params`, per `runtime/src/bank.rs`) rather than hardcoded `Duration` constants, so the clean/shrink cadence scales automatically with slot-time-reduction feature activations instead of requiring a manual constant update.

### Proof of Concept
Not directly exploitable by an external actor; this is a systemic scaling issue triggered by feature activation, not a crafted input. To demonstrate:
1. Activate `feature_set::reduce_slot_time_to_200ms` (or inspect `runtime/src/bank/tests.rs` test `test_update_clock_slot_range_duration`, which already exercises a 200ms slot-time feature at [8](#0-7) ).
2. Run `AccountsBackgroundService` with this bank and observe that `CLEAN_INTERVAL`/`SHRINK_INTERVAL` (still `Duration::from_secs(50)`/`Duration::from_secs(1)`) now correspond to 2x the number of slots/roots produced versus the 400ms baseline the constants were tuned for, at [9](#0-8)  and [4](#0-3) , resulting in a proportionally larger backlog of dirty stores/shrink candidates per clean/shrink pass.
