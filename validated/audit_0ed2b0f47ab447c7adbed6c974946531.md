### Title
Ballot rejection uses a too-strict NO-vote threshold instead of the "mathematically unreachable" condition, letting doomed ballots (inbound/outbound/chain-meta/TSS/fund-migration) stay `PENDING` far longer than they should - (`File: x/uvalidator/types/ballot.go`)

### Summary
Push Chain's generic ballot machine defines two different rejection conditions for the same invariant. The correct, documented condition — "no path to threshold" — lives in `ShouldReject()`: `eligibleVoters - noVotes < votingThreshold`. But the function that is actually wired into the live voting path, `IsFinalizingVote()`, uses a stricter, different condition: `noVotes >= votingThreshold`. `ShouldReject`/`ShouldPass` are only referenced from unit tests, never from the production keeper flow. [1](#0-0) [2](#0-1) 

### Finding Description
`VoteOnBallot` → `AddVoteToBallot` → `CheckIfFinalizingVote` → `b.IsFinalizingVote()` is the single canonical path used by every ballot type (inbound, outbound, chain-meta, TSS key process, fund migration) as documented in the module README. [3](#0-2) [4](#0-3) 

`IsFinalizingVote` only transitions to `BALLOT_STATUS_REJECTED` once the literal count of NO votes reaches the voting threshold itself:
```go
if int64(noVotes) >= b.VotingThreshold {
    b.Status = BallotStatus_BALLOT_STATUS_REJECTED
    return b, true
}
``` [5](#0-4) 

This is the wrong convergence condition. The correct, mathematically-sound rejection condition — used by `ShouldReject()` and stated explicitly in the module README — is that rejection should trigger the moment YES can no longer possibly reach threshold, i.e. `len(EligibleVoters) - noVotes < VotingThreshold`: [6](#0-5) 

Example: with 5 eligible voters and `votingThreshold = 4` (the `(2*n)/3+1` quorum formula used everywhere), a ballot that receives 2 NO votes already has only 3 possible remaining YES votes — mathematically unreachable, so it should reject immediately per `ShouldReject()`. But `IsFinalizingVote()` requires `noVotes >= 4`, so the ballot stays `BALLOT_STATUS_PENDING` even though its outcome is already decided. It will remain pending, consuming `ActiveBallotIDs` storage and blocking re-observation of the same event, until either (a) enough additional NO votes eventually accumulate to literally hit the threshold, or (b) the ballot's expiry height is reached and it's swept into `EXPIRED` by `MarkBallotExpired`. [7](#0-6) 

This is a direct analog of the reported `_bisectUnderlyingNeeded` bug: an overly strict boundary/convergence condition (`< threshold-of-actual-count` instead of the semantically-correct "outcome-is-already-determined" test) causes the state machine to fail to reach its correct terminal state promptly, instead limping along until an unrelated fallback (expiry, in this case; unbounded iteration count in the original report) eventually resolves it.

The impact is amplified for fund migrations, whose ballots use a 100,000,000-block expiry window: [8](#0-7) 
A fund-migration ballot that is already unreachable for PASS (e.g., honest validators observe a failed migration tx and vote FAILURE, but not enough of them to hit the literal NO threshold) will sit `PENDING` for practically the lifetime of the chain instead of transitioning to `REJECTED`, since `VoteOnFundMigrationBallot` routes through the same `VoteOnBallot`/`IsFinalizingVote` path. [9](#0-8) 

### Impact Explanation
This is a liveness/state-machine-correctness defect in the shared ballot finalization primitive used by every crosschain observation type (inbound tx, outbound tx, chain-meta, TSS key process, fund migration). Ballots whose outcome is already mathematically decided as REJECTED are left dangling in `PENDING`/`ActiveBallotIDs` instead of moving to the canonical `REJECTED` terminal state via `MarkBallotFinalized`. Depending on how downstream consumers key off `BALLOT_STATUS_REJECTED` versus `BALLOT_STATUS_EXPIRED` (I was not able to fully trace every consumer of ballot status within the remaining search budget — e.g., whether inbound/outbound reprocessing, retry, or refund logic branches differently on `REJECTED` vs. `EXPIRED`), this can delay or effectively suppress the correct downstream handling of a failed crosschain observation for a very long window (up to the fund-migration module's ~100,000,000-block expiry), which is a form of non-network-level, unprivileged-reachable denial of timely finalization within the in-scope invariant set ("state transitions in universal execution flows" / TSS coordination correctness).

### Likelihood Explanation
No privileged action is required to trigger this: it is reached purely through the ordinary, honest voting flow of Universal Validators observing a real crosschain event and reporting FAILURE via `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration`. The condition manifests naturally whenever a mixed set of YES/NO votes causes the "no-path-to-pass" state to be reached before the raw NO-count itself reaches `VotingThreshold` — a common outcome when `VotingThreshold` is set via the `(2n/3)+1` supermajority formula and the vote split is not lopsided enough to hit the NO threshold directly. This is a deterministic code-path bug, not a probabilistic edge case, and is exercised by every ballot type in the codebase.

### Recommendation
Replace the boundary condition in `IsFinalizingVote()` with the same semantics already implemented (but unused) in `ShouldReject()`: reject as soon as `int64(len(b.EligibleVoters) - noVotes) < b.VotingThreshold`, rather than waiting for `noVotes >= b.VotingThreshold`. Align `IsFinalizingVote` to delegate to (or match) `ShouldPass`/`ShouldReject` so there is a single, tested source of truth for finalization semantics, and add regression tests asserting that a ballot is finalized as `REJECTED` in the same block that its outcome becomes mathematically unreachable, not merely when the raw NO count reaches threshold.

### Proof of Concept
1. Create a ballot (via any `Msg*Vote*` message, e.g. `MsgVoteFundMigration`) with 5 eligible Universal Validators and `votingThreshold = 4` (standard `(2*5)/3+1` quorum).
2. Have 2 validators honestly vote FAILURE (`VoteResult_VOTE_RESULT_FAILURE`).
3. At this point `potentialYesVotes = 5 - 2 = 3 < 4`, so `ShouldReject()` would return `true` — the outcome is already decided.
4. Observe that `IsFinalizingVote()` (the function actually invoked by `CheckIfFinalizingVote`/`VoteOnBallot`) returns `false` because `noVotes(2) < votingThreshold(4)`; the ballot remains `BALLOT_STATUS_PENDING` and stays in `ActiveBallotIDs` instead of moving to `FinalizedBallotIDs` with status `REJECTED`.
5. For the fund-migration ballot type specifically, this pending state persists for up to `fundMigrationExpiryBlocks = 100_000_000` blocks before the fallback expiry sweep resolves it, confirming the incorrect convergence condition materially delays correct finalization.

// ShouldReject returns true if the NO votes make it impossible to reach the threshold.
func (b Ballot) ShouldReject() bool {
	_, noVotes := b.CountVotes()
	potentialYesVotes := len(b.EligibleVoters) - noVotes
	return potentialYesVotes < int(b.VotingThreshold)
}

// CheckIfFinalizingVote inspects whether the just-cast vote pushes the ballot
// over its threshold and, if so, drives the finalization through
// MarkBallotFinalized — the single canonical write path for terminal status
// transitions, which applies CEI-style ordering on the secondary indexes.
func (k Keeper) CheckIfFinalizingVote(ctx context.Context, b types.Ballot) (types.Ballot, bool, error) {
	ballot, isFinalizing := b.IsFinalizingVote()
	if !isFinalizing {
		return b, false, nil
	}

	k.Logger().Debug("ballot reached finalization threshold",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)

	if err := k.MarkBallotFinalized(ctx, ballot.Id, ballot.Status); err != nil {
		return ballot, false, errors.Wrap(err, "failed updating finalized ballot")
	}

	k.Logger().Debug("ballot finalized",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)
	return ballot, true, nil
}

```markdown
A ballot is created lazily on the first vote, indexed in `ActiveBallotIDs`, and finalizes the moment either:
- `yesVotes >= votingThreshold` -> `BALLOT_STATUS_PASSED`
- `eligibleVoters - noVotes < votingThreshold` (the threshold is now mathematically unreachable) -> `BALLOT_STATUS_REJECTED`

On finalization, the ballot is moved from `ActiveBallotIDs` -> `FinalizedBallotIDs`. Expired ballots that never reached threshold are moved to `ExpiredBallotIDs`.
