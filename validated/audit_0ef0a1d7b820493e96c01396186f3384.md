## Title
Missing Slippage Control on `ExchangeInjectContract` (Add-Liquidity) Allows Value Loss From Ratio Front-Running — (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

## Summary
`ExchangeInjectContract`, the on-chain "add liquidity" operation for TRON's Bancor-style TRX/TRC10 `Exchange` AMM pools, lets a user specify only the amount of one token (`quant`) to deposit. The paired amount of the other token that must simultaneously be pulled from the user's balance (`anotherTokenQuant`) is computed automatically at execution time from the pool's *current* first/second token balances [2](#0-1) . Unlike `ExchangeTransactionContract`, which has an explicit `expected` field enforced as a minimum-received check in `doValidate()` [3](#0-2) , `ExchangeInjectContract`/`ExchangeInjectActuator` has no analogous bound field or check on `anotherTokenQuant` [4](#0-3) . This mirrors exactly the reported bug class ("No Slippage Control on Deposit"): the number of the paired token pulled from the depositor can change between transaction signing/broadcast and block inclusion because other exchange operations (`ExchangeTransactionContract` swaps, other `ExchangeInjectContract`/`ExchangeWithdrawContract` calls) can alter the pool ratio first.

## Finding Description
The `ExchangeInjectContract` protobuf only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — no minimum/maximum bound for the paired token amount. In `ExchangeInjectActuator.execute()`, `anotherTokenQuant` is derived purely from the *current on-chain* pool ratio at execution time:

```
anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance);
``` [5](#0-4) 

The same unconstrained computation is repeated in `doValidate()` [6](#0-5) , and the only checks performed are that the derived amount is `> 0` and within the global `exchangeBalanceLimit`, and that the user's balance is sufficient to cover it [7](#0-6) . There is no user-supplied ceiling on `anotherTokenQuant` that would let the transaction fail safely if the ratio moved unfavorably before inclusion.

Because the pool ratio (`firstTokenBalance` / `secondTokenBalance`) is mutable state that any other account can shift by broadcasting an `ExchangeTransactionContract` (swap), `ExchangeInjectContract` (inject), or `ExchangeWithdrawContract` (withdraw) that gets included first, a pending inject transaction is exposed to front-running: an attacker observing the pending inject in the mempool can execute a swap that skews the ratio, causing the victim's inject to be executed at that skewed ratio and pull a larger-than-expected amount of the paired token from the victim's balance for the same `tokenQuant` deposited.

## Impact Explanation
A victim's `addLiquidity`-equivalent transaction (`ExchangeInjectContract`) can be executed at a ratio worse than what the victim observed when signing, causing the victim to deposit more of the paired asset than intended for the same primary-token quantity — an accounting/asset loss analogous to the reported ERC4626-style "fewer shares than expected" issue, translated to TRON's Bancor exchange pools. This is reachable by any account via ordinary broadcast transactions (no privileged role, leaked key, or malicious peer required) and can be systematically exploited via mempool front-running/sandwiching.

## Likelihood Explanation
Exploitation requires only broadcasting ordinary transactions (`ExchangeCreateContract` is not even needed by the attacker — any existing TRX/token exchange pool suffices) and observing the victim's pending `ExchangeInjectContract` in the mempool/network before block inclusion, then racing a swap ahead of it. This is a standard MEV/front-running pattern requiring no special privileges, matching the "unprivileged, reachable from broadcast transaction" bar.

## Recommendation
Add a `expected`-style minimum/maximum bound field to `ExchangeInjectContract` analogous to the one already present on `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` (e.g., reject if the computed `anotherTokenQuant` exceeds a user-specified maximum). The same fix should be applied symmetrically to `ExchangeWithdrawActuator` for withdrawals.

## Proof of Concept
1. Attacker/observer watches the mempool for a victim's `ExchangeInjectContract(exchange_id=X, token_id=first, quant=Q)` targeting pool X with current balances `(firstBal, secondBal)`.
2. Attacker broadcasts an `ExchangeTransactionContract` swap against pool X that shifts the ratio unfavorably for the victim's pending inject (e.g., increases `secondBal` relative to `firstBal`), and ensures it lands in an earlier position in the block (or a prior block).
3. Victim's inject transaction executes using the post-swap balances: `anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` [8](#0-7)  — now larger than the victim expected — is deducted from the victim's balance/assets with `accountCapsule.reduceAssetAmountV2(anotherTokenID, anotherTokenQuant, ...)` [9](#0-8) , with no validation check available to abort the transaction since no expected/minimum bound exists for this contract type.
