### Title
OAuth callback shop-parameter confusion via duplicate `shop` query key - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
The reported Paladin bug class is about state being indexed by a non-unique key (`fromBlock`), which lets different lookup paths in the same codebase resolve to *different* entries for the same nominal key — enabling result manipulation. The `callback()` handler in `oauth.ts` reproduces the same structural flaw: it derives the authoritative `shop` value from the same incoming query string using two different extraction strategies that disagree when the `shop` parameter is repeated.

### Finding Description
In `callback()`:
```
const query = new URL(request.url, ...).searchParams;
const shop = query.get('shop')!;               // FIRST occurrence
...
const authQuery: AuthQuery = Object.fromEntries(query.entries()); // LAST occurrence wins
if (!(await validQuery({config, query: authQuery, stateFromCookie}))) { ... }
...
const cleanShop = sanitizeShop(config)(query.get('shop')!, true)!;  // FIRST occurrence again
``` [1](#0-0) [2](#0-1) [3](#0-2) 

`URLSearchParams.get()` always returns the **first** value for a repeated key, while `Object.fromEntries(query.entries())` collapses duplicates so that the **last** value wins. `validQuery` recomputes the HMAC and does the state comparison against `authQuery` (last-value semantics) via `validateHmac(config)(query)`: [4](#0-3) 

`hmac-validator.ts`’s `normalizeQuery` only rejects duplicate security parameters (`hmac`, `shop`, `signature`, `timestamp`) for the `appProxy` signator; for the `admin` signator (used by OAuth) no such rejection exists, so a duplicated `shop` silently passes through: [5](#0-4) 

The net effect: the value used to validate the HMAC/state (`authQuery.shop`, last duplicate) can differ from the value used to identify the shop for logging/cookie context and — critically — for the outbound token-exchange request (`cleanShop`, first duplicate). This is exactly the "one-to-many mapping between a lookup key and the record used" pattern from the reference report, just manifesting as divergent query-parsing semantics instead of divergent binary-search results.

### Impact Explanation
An attacker who owns a legitimate `hmac`-signed OAuth callback for their own shop (easily obtained by installing/authorizing their own app instance) can inject a second, decoy `shop` parameter ahead of their real one. Because HMAC/state validation reads `authQuery.shop` (last value = attacker's real, correctly-signed shop) while the token-exchange call reads `query.get('shop')` (first value = attacker-controlled arbitrary shop string), the server can be made to:
- Send the app's `client_id`/`client_secret` and the attacker's authorization `code` to a `/admin/oauth/access_token` endpoint on a domain the attacker chose as the first duplicate (subject to `sanitizeShop`'s domain-format restriction), rather than the shop that produced the valid HMAC.

This is a shop-confusion / secret-disclosure primitive rooted in inconsistent duplicate-parameter handling between the HMAC/state validation path and the token-exchange path.

### Likelihood Explanation
Moderate-to-low confidence in full end-to-end exploitability: the OAuth `state` check (`safeCompare(query.state!, stateFromCookie)`) still requires the attacker to know the victim-browser's signed state cookie value, which limits practical exploitation to scenarios where the attacker can also influence which OAuth flow the victim's browser has open (e.g., via CSRF-starting `/auth/begin`) or is analyzing their own flow. I was not able to fully verify `sanitizeShop`/`shop-validator.ts`'s exact allow-list behavior (e.g., whether `domainTransformations` could permit non-`myshopify.com` hosts) within this session, which affects how far the SSRF-like effect could reach. This should be validated directly against `packages/apps/shopify-api/lib/utils/shop-validator.ts`.

### Recommendation
- In `callback()`, derive `shop` exactly once (e.g., from the same `authQuery` used for HMAC/state validation) and reuse that single value consistently for cookie identification, logging, and the token-exchange request — do not mix `URLSearchParams.get()` (first-match) and `Object.fromEntries()` (last-match) semantics for the same logical field.
- Extend `normalizeQuery` in `hmac-validator.ts` to reject repeated single-value security parameters (`hmac`, `shop`, `state`, `timestamp`, `code`) for the `admin` signator the same way it already does for `appProxy` (see the existing hardening at [6](#0-5) ).

### Proof of Concept
1. Attacker completes a normal OAuth flow for their own store `attacker.myshopify.com`, capturing the real Shopify-issued callback URL: `.../auth/callback?code=C&hmac=H&shop=attacker.myshopify.com&state=S&timestamp=T`.
2. Attacker crafts: `.../auth/callback?shop=victim-target.myshopify.com&shop=attacker.myshopify.com&code=C&hmac=H&state=S&timestamp=T` and gets it loaded by the app (e.g., as an authenticated request from their own session, or via any transport where the state cookie is available to them).
3. `authQuery.shop` (from `Object.fromEntries`) resolves to `attacker.myshopify.com`, so `validateHmac`/state checks pass using the legitimately signed values.
4. `cleanShop` (from `query.get('shop')`) resolves to `victim-target.myshopify.com`, so the app's server issues the token-exchange POST — including `client_id`/`client_secret` — to `https://victim-target.myshopify.com/admin/oauth/access_token` instead of the shop that actually produced the valid HMAC.

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
