### Title
Front-runnable BOOTSTRAP declare allows unauthorized hijack of genesis class declarations - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo)

### Summary
The sequencer implements a special "BOOTSTRAP" declare-transaction path intended to let an operator declare genesis classes without fees, signatures, or nonce validation when starting a new Starknet system. Because this path is keyed only on a hardcoded, publicly-known sender address (`'BOOTSTRAP'`) and requires **no signature/validate call and no fee**, any unprivileged party who can submit a transaction to the mempool can construct an equivalent bootstrap-declare transaction themselves. This is directly analogous to the reported Solidity bug class: an "initializer" (a privileged, one-time state-setting function) that lacks access control and can therefore be executed/front-run by anyone racing to be first.

### Finding Description
The bootstrap declare flow is defined in two places:

1. Rust side, `DeclareTransaction::is_bootstrap_declare` / `bootstrap_address`: [1](#0-0) 

This shows that a declare transaction is treated as a privileged, no-validation "bootstrap" declare purely based on: `sender_address == bootstrap_address()` (a fixed constant felt for the string `'BOOTSTRAP'`), `nonce == 0`, and `charge_fee == false`. There is no signature check, no owner/permission check tied to any real key.

2. This condition is honored in the executor: [2](#0-1) 

When the condition holds, `run_execute`/`try_declare` is invoked directly, **skipping validate and fee-charging entirely** — i.e., skipping exactly the steps ("permission enforcement") that would normally restrict who can perform this declaration.

3. The Starknet OS mirrors the same unauthenticated bootstrap path in Cairo, where the class hash is declared with a one-time guard (`prev_value=0`) enforcing "a class may be declared only once": [3](#0-2) 

Because `sender_address == 'BOOTSTRAP'`, `nonce == 0`, and `max_possible_fee == 0` are the only conditions, and none of these values are secret or access-controlled, **any unprivileged transaction sender can craft an identical bootstrap declare transaction** (choosing any `class_hash`/`compiled_class_hash` pair they like) and submit it to the mempool/gateway before the legitimate operator's bootstrap declare is included in a block.

The mempool explicitly acknowledges bootstrap declares are special (never increment nonce, remain resubmittable): [4](#0-3) 
and the mempool's own test suite gates their acceptance only behind a config flag (`validate_resource_bounds`/`allow_bootstrap`), not behind any cryptographic authorization: [5](#0-4) 

### Impact Explanation
Since class declaration is enforced to succeed only once per `class_hash` (`prev_value=0` check in `dict_update`), an attacker who front-runs the legitimate bootstrap declare with the same `class_hash` but an attacker-chosen `compiled_class_hash` can permanently claim that class-hash-to-CASM mapping. When the legitimate operator's bootstrap declare transaction for the same class hash later executes, the `dict_update` with `prev_value=0` will fail because the class is already declared — causing the intended genesis declaration to be rejected/reverted. This is a permanent-freezing-of-initialization type impact: the sequencer's intended genesis class (e.g., the fee-token contract class or an account class needed to bootstrap the whole chain) can never be correctly declared once hijacked, which can prevent the network from reaching a working genesis state or force operators to use a different, non-deterministic bootstrap path. This satisfies the "permanent freezing" / "network unable to confirm new transactions" bar in the validation rules, since bootstrapping is a prerequisite for the chain to become operational.

### Likelihood Explanation
Likelihood is high for any environment that still allows bootstrap declares to be submitted through the normal gateway/mempool ingestion path (as evidenced by `allow_bootstrap_txs()` test helper and mempool config flag `validate_resource_bounds`). All parameters needed to construct a competing bootstrap declare (`sender_address = bootstrap_address()`, `nonce = 0`, zero fee/resource bounds, and a target `class_hash`) are public and reproducible by anyone with mempool/gateway access — no signature or private key is required, unlike ordinary account transactions. An attacker simply needs to observe (or predict) the operator's intended genesis `class_hash` and submit their own bootstrap declare with a higher priority/faster inclusion.

### Recommendation
- Do not gate privileged "no validation / no fee" declare semantics purely on a well-known public constant (`'BOOTSTRAP'`) reachable from ordinary transaction ingestion. Restrict acceptance of bootstrap declares to a genesis-only phase (e.g., only accept them before the chain has produced its first block / before any state exists), and reject them once the system is live.
- Alternatively/additionally, require the bootstrap declare transaction to be signed by an actual, chain-configured genesis key, or to be injected via a privileged/administrative path (e.g., only accepted directly from the sequencer node's own genesis-block-building logic) rather than through the public mempool/gateway.
- In the gateway/mempool, explicitly disable acceptance of transactions from `bootstrap_address()` once the mempool/state indicates bootstrapping has completed (e.g., once any class has already been declared, or after block 0), closing the front-running window entirely.

### Proof of Concept
1. Attacker monitors the network configuration or chain-spec to learn the `class_hash` the operator intends to bootstrap-declare (e.g., a standard account/ERC20 fee contract class hash is often publicly known/standardized).
2. Attacker crafts a Declare V3 transaction with:
   - `sender_address = DeclareTransaction::bootstrap_address()` (public constant, felt of `'BOOTSTRAP'`)
   - `nonce = 0`
   - `resource_bounds` set for zero fee (as in `ValidResourceBounds::create_for_testing_no_fee_enforcement()` / `AllResourceBounds::new_unlimited_gas_no_fee_enforcement()`)
   - `class_hash` = the same target class hash the legitimate operator plans to use
   - `compiled_class_hash` = attacker-chosen value corresponding to attacker's own CASM
3. Attacker submits this transaction to the gateway/mempool before the operator's legitimate bootstrap declare, and it satisfies `is_bootstrap_declare` (`sender_address == bootstrap_address() && nonce == 0 && !charge_fee`), so it bypasses `__validate_declare__` and fee charging entirely (`crates/blockifier/src/transaction/account_transaction.rs:899-911`).
4. Once sequenced, the OS's `execute_declare_transaction` performs `dict_update{...}(key=[class_hash_ptr], prev_value=0, new_value=compiled_class_hash)`, permanently associating the target `class_hash` with the attacker's CASM (`transaction_impls.cairo:768-772`).
5. When the operator's legitimate bootstrap declare for the same `class_hash` is later processed, the `prev_value=0` precondition fails (class already declared), causing that declaration to be rejected — the intended genesis class can never be correctly established through the bootstrap path.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }

        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
