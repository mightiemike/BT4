### Title
Replay-verify (`ensure_match_transaction_info`) skips checkpoint-hash validation, allowing a diverging position/state root to be accepted as a successful replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` — the function used by `db-tool replay-on-archive`, `aptos-debugger`, and the `aptos` CLI to verify that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` fetched from an archive/full node — only checks status, gas used, write-set hash (`state_change_hash`), and event root hash. It does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, a gap the code itself documents as a known TODO.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates a re-executed `TransactionOutput` against a trusted, proof-carrying `TransactionInfo` by comparing:
- `status`
- `gas_used`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It explicitly does not compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or the newer `position_state_checkpoint_hash` fields carried in `TransactionInfoV1` (see the struct definition at [2](#0-1) ). The code comment makes this explicit: [3](#0-2) 

This matters because these checkpoint hashes are exactly the fields that bind the accumulator-verified `TransactionInfo` to the Merkle root of world state (main state, hot state, and — per the in-progress "trading native" position state feature — the position-state JMT) at that version. `state_checkpoint_hash` is populated from `DoStateCheckpoint::run` at [4](#0-3)  and, when position roots are computed, `position_state_checkpoint_hash` from [5](#0-4) . These are hashed into the `TransactionInfo` leaf that the transaction accumulator commits to (`assemble_transaction_infos` in [6](#0-5) ), i.e. they are part of what the accumulator/ledger-info signature actually authenticates.

`ensure_match_transaction_info` is used as the correctness oracle by replay/debug tooling: [7](#0-6)  (via `AptosVM`/`AptosDebugger`), `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. If a validator, storage layer, or a new state-root computation path (e.g. the trading-native `compute_trading_native_state_roots` feature under construction, gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in `types/src/on_chain_config/aptos_features.rs`) produces a state/hot-state/position-state root that diverges from what the archived, signed `TransactionInfo` commits to, `ensure_match_transaction_info` will still report success as long as the write set, events, gas, and status match. This is a real state-commitment/proof-integrity gap: the checked-in comment states this directly — "replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

### Impact Explanation
`ensure_match_transaction_info` is the mechanism that operators, auditors, and the debugger use to confirm that independently re-executed history matches the authenticated, accumulator-committed ledger. Silently ignoring the state/hot-state/position-state checkpoint hashes means a genuine consensus/state-computation divergence (e.g. a JMT computation bug, a hot-state or position-state root bug, or corrupted durable data) would not be caught by this tool even though it directly changes the durable, authenticated state root — this is precisely a "committed state that differs from the correct VM result" / "wrong ... state proof accepted as valid" scenario in the state-integrity gate, surfaced through the verification tooling rather than through consensus itself. As the position-state ("trading native") feature is still gated (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) and under active development, this gap is a real risk during its rollout, and it already silently omits the long-standing `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields for any replay path today.

### Likelihood Explanation
The gap is 100% deterministic and code-confirmed (not merely theoretical): the comparator simply omits these fields, and the code's own comment acknowledges the exact failure mode. It requires a pre-existing divergence in state-root computation to be actually exploitable/harmful (i.e., it is a "verification blind spot" that hides other bugs rather than a root cause of ledger corruption on its own) — so its severity is best framed as a proof/verification-integrity weakness rather than a standalone commit-corruption bug. Because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is not yet broadly enabled, likelihood of near-term mainnet impact from the position-state part specifically is lower today, but the `state_checkpoint_hash`/`hot_state_checkpoint_hash` omission applies to the existing, currently-live replay/verify tooling.

### Recommendation
Extend `ensure_match_transaction_info` to also assert:
- `state_checkpoint_hash` matches the recomputed main-state root when the transaction has a checkpoint,
- `hot_state_checkpoint_hash` matches the recomputed hot-state root when `HOT_STATE_ROOT_IN_TXN_INFO` is enabled,
- `position_state_checkpoint_hash` matches the recomputed position-state root when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled,
before enabling reliance on this comparator for any of these new roots, per the TODO already left in the code at [3](#0-2) .

### Proof of Concept
Not applicable / not constructed — this is a static code-review finding based on the function's own logic and its self-documented TODO comment; no dynamic PoC was built. The gap can be confirmed by inspecting [1](#0-0)  and noting the absence of any comparison involving `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn assemble_transaction_infos(

        transaction_info_v1: bool,

        hot_state_checkpoint_hashes: Option<&[Option<HashValue>]>,
        position_state_checkpoint_hashes: Option<&[Option<HashValue>]>,
    ) -> (Vec<TransactionInfo>, Vec<HashValue>) {
        let _timer = OTHER_TIMERS.timer_with(&["assemble_transaction_infos"]);

        (0..to_commit.len())
            .into_par_iter()
            .with_min_len(optimal_min_len(to_commit.len(), 64))
            .map(|i| {
                let txn = &to_commit.transactions[i];
                let txn_output = &to_commit.transaction_outputs[i];
                let persisted_auxiliary_info = &to_commit.persisted_auxiliary_infos[i];
                // Use the auxiliary info hash directly from the persisted info
                let auxiliary_info_hash = match persisted_auxiliary_info {
                    PersistedAuxiliaryInfo::None => None,
                    PersistedAuxiliaryInfo::V1 { .. } => {
                        Some(CryptoHash::hash(persisted_auxiliary_info))
                    },
                    PersistedAuxiliaryInfo::TimestampNotYetAssignedV1 { .. } => None,
                };
                let state_checkpoint_hash = state_checkpoint_hashes[i];
                let event_hashes = txn_output
                    .events()
                    .iter()
                    .map(CryptoHash::hash)
                    .collect::<Vec<_>>();
                let event_root_hash =
                    InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash();
                let write_set_hash = CryptoHash::hash(txn_output.write_set());

                    .status()
                    .as_kept_status()
                    .expect("Already sorted.");
