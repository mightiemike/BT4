## Finding: `ensure_match_transaction_info` never validates the state-checkpoint (Merkle root) hash during replay/state-sync verification

### Title
Replay/backup verification accepts transaction outputs whose committed state-checkpoint root diverges from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single generic invariant check used by both `db-tool replay-on-archive` and the `chunk_executor` to confirm that a re-executed/replayed `TransactionOutput` matches the authenticated `TransactionInfo` recorded in the transaction accumulator. It checks status, gas, the write-set hash (`state_change_hash`) and the event root hash, but it never compares the locally computed state-checkpoint (Sparse-Merkle-Tree) root against `txn_info.state_checkpoint_hash()`.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` is documented as validating that a `TransactionOutput` "does not match `TransactionInfo`," and is the authoritative comparator used by backup/replay tooling:

- `storage/db-tool/src/replay_on_archive.rs` calls it directly on freshly re-executed outputs against `expected_txn_infos` fetched from backup/archive storage, to decide whether a discrepancy (fork/bug/corruption) is reported. [2](#0-1) 
- The same helper is invoked from `execution/executor/src/chunk_executor/mod.rs` for chunk-based replay verification.

Yet the function itself only checks:
1. `status()` vs. `txn_info.status()`
2. `gas_used()` vs. `txn_info.gas_used()`
3. `CryptoHash::hash(write_set)` vs. `txn_info.state_change_hash()`
4. computed event-root-hash vs. `txn_info.event_root_hash()`

It never reads or compares `txn_info.state_checkpoint_hash()` (the Sparse Merkle Tree root summarizing world state at a checkpoint) against anything computed from the replayed execution. The code even documents this gap explicitly in a TODO right where the function returns success: [3](#0-2) 

which states: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." The comment frames the gap as being about the not-yet-enabled `position_state_checkpoint_hash`/trading-native feature, but as written, the function skips *all* checkpoint-hash fields unconditionally — including the ordinary `state_checkpoint_hash` that every full node computes and stores from its own Jellyfish Merkle Tree for every checkpoint version. This check happens to be independently enforced elsewhere in the *live* execution pipeline (`do_state_checkpoint.rs`'s `get_state_checkpoint_hashes`, which does compare `known_state_checkpoints` against locally computed roots during block/chunk execution — see `execution/executor/src/workflow/do_state_checkpoint.rs:192-220`), so a running validator/full-node consensus/chunk-execution path is not silently accepting a wrong state root. However, the standalone `db-tool replay_on_archive` verification path re-executes historical transactions and relies solely on `ensure_match_transaction_info` as its pass/fail oracle — and that oracle structurally cannot detect a state-root divergence, since it never inspects `state_checkpoint_hash` at all.

### Impact Explanation
`replay_on_archive` (and the `chunk_executor` verify path using the same function) is one of the primary tools operators and infrastructure providers use to confirm that historical/backup blockchain data reproduces the authenticated ledger state (e.g., to detect a hard-fork-only divergence, a JMT computation bug, or corrupted backup data). Because the comparator only validates the write-set hash and event root, a bug or corruption that affects only the state-checkpoint root computation (SMT/JMT update logic, incorrect hot-state root wiring, or corrupted `state_store` snapshot commit) would go completely undetected by this verification tool even though the write-set and event hashes match. This directly violates the required invariant "Accumulators, Jellyfish Merkle structures, versioned state views ... must preserve deterministic proof binding" and "Committed state that differs from the correct VM result ... must be flagged," since the verification tool built to catch exactly this class of divergence structurally cannot.

### Likelihood Explanation
Likelihood of the check being relied upon and silently failing is real but narrow in scope: it only affects the standalone replay/verify tooling path (`db-tool replay-on-archive`, and any chunk-executor consumer of the same function), not the primary consensus/execution commit path, since block/chunk execution independently re-derives and checks state-checkpoint hashes via `DoStateCheckpoint`/`get_state_checkpoint_hashes`. The gap is also explicitly acknowledged in-code as a known TODO rather than a silent unknown bug, which somewhat reduces novelty, but it remains an unresolved, exploitable blind spot in the primary tool operators use to independently audit historical ledger integrity.

### Recommendation
Extend `ensure_match_transaction_info` to accept (or recompute) the state-checkpoint root for checkpoint-boundary transactions and assert it against `txn_info.state_checkpoint_hash()` (and, when enabled, `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`), so that `replay_on_archive` and any other caller of this generic comparator cannot report a "successful" verification when the authenticated state root diverges from locally recomputed state.

### Proof of Concept
Conceptual PoC (cannot be executed without a full node/backup fixture):
1. Take a backup transaction stream and corresponding `TransactionInfo` list containing a correct `state_checkpoint_hash`.
2. Introduce a state-store bug (or corrupt backup data) that changes the *content* of a state value written at a checkpoint version while leaving the write-set bytes (and thus `state_change_hash`) and events unchanged — e.g. a metadata-only or storage-slot corruption that does not change the serialized write op bytes hashed into `state_change_hash`, but does change the state actually committed to the JMT.
3. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`, `execute_and_verify` → `ensure_match_transaction_info`) over this range.
4. Observe that verification reports success because `ensure_match_transaction_info` never inspects `state_checkpoint_hash`, even though the state root computed from the corrupted data would differ from the one recorded in the authenticated `TransactionInfo`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
