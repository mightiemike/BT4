## Finding

### Title
Market order cancellation can be front-run by a matching `MarketSellAssetContract`, causing unwanted order execution instead of cancellation - (File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java)

### Summary
`MarketCancelOrderActuator` cancels an active TRON DEX order (`MarketOrderCapsule`) by checking `orderCapsule.isActive()` at validation time and marking it `CANCELED` at execution time. This check-then-act pattern is not atomic with respect to other transactions targeting the same order book price level. Any account can submit a `MarketSellAssetContract` that matches against the very order the owner is trying to cancel, consuming it (partially or fully) before the cancellation transaction executes, exactly as described in the report's front-running scenario for `cancel_recovery`/`finish_recovery`.

### Finding Description
`MarketCancelOrderActuator.execute()` reads the order, marks it `CANCELED`, and returns the remaining sell tokens to the owner: [1](#0-0) 

Validation only requires the order to currently be active and to belong to the caller: [2](#0-1) 

Meanwhile, `MarketSellAssetActuator.execute()` creates a new taker order and immediately matches it against existing maker orders in the order book via `matchOrder`/`matchSingleOrder`, mutating the maker's `MarketOrderCapsule` (reducing `sellTokenQuantityRemain`, setting state to `INACTIVE`) and crediting/debiting both accounts: [3](#0-2) [4](#0-3) 

Any account can submit a `MarketSellAssetContract` (via the `MarketSellAsset` RPC or `/wallet/marketsellasset` HTTP endpoint) that matches at the exact price the owner's order sits at. If this matching transaction is processed by a block producer before the owner's `MarketCancelOrderContract`, the order is filled/consumed instead of canceled — the owner's cancellation intent is defeated by transaction ordering, structurally identical to the report's "someone calls `finish_recovery` before `cancel_recovery` is mined" scenario. There is no mechanism (e.g., a cancel-lock, nonce, or optimistic-cancel guard) preventing a third party's matching transaction from executing first.

### Impact Explanation
If the order owner intends to cancel an order because it is no longer favorable (e.g., market price moved), a front-run match forces an unwanted trade execution at the stale order price, causing the owner to receive an asset exchange they were actively trying to avoid. This is an economic/asset-accounting impact reachable by any unprivileged account broadcasting an ordinary transaction, matching the "may pose a threat" branch of the reported bug class (canceling to prevent unwanted finalization, but finalization occurs anyway due to a race).

### Likelihood Explanation
This requires only that another party broadcast a matching `MarketSellAssetContract` at the correct price/pair before the block producer processes the cancel transaction. Since TRON transaction ordering within blocks is controlled by SRs (and no priority-fee auction exists to let the canceller "outbid"), the owner has no reliable way to ensure their cancel executes first once broadcast, making the race practically exploitable by any party monitoring order-book activity — but it also requires that a matching counter-order exists/be submitted at the right moment, so likelihood is moderate rather than trivial.

### Recommendation
This is inherent to any on-chain order book without commit-reveal or per-order cancel priority, and is analogous to the reported "intentional functionality" for `cancel_recovery`. If deemed undesirable, consider documenting it as expected DEX behavior (as the original report's update did for the recovery contract), or introduce mechanisms such as a short cancel-priority window, batch auctions, or requiring cancellations to be processed ahead of new matching orders within the same block.

### Proof of Concept
1. Account A creates a sell order via `MarketSellAssetContract` (e.g., sell 100 TOKEN_A for 200 TOKEN_B), which rests in the order book because no match exists — see `createAndSaveOrder`/`saveRemainOrder` flow in `MarketSellAssetActuator.execute()` [5](#0-4) .
2. Market conditions change; Account A broadcasts `MarketCancelOrderContract` to cancel this order via `MarketCancelOrderActuator`.
3. Before that transaction is included, Account B broadcasts a `MarketSellAssetContract` for TOKEN_B/TOKEN_A at a matching price.
4. If B's transaction is processed first, `matchOrder` consumes A's order (state becomes `INACTIVE`/quantity reduced) as shown in `matchSingleOrder` [6](#0-5) , and A's subsequent cancel transaction then fails validation (`"Order is not active!"`) [7](#0-6)  — the cancellation is defeated and the trade executes against A's wishes.

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0

        byte[] orderId = orderIdListCapsule.getHead();

          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
        }

  private void matchSingleOrder(MarketOrderCapsule takerOrderCapsule,
      MarketOrderCapsule makerOrderCapsule, TransactionResultCapsule ret,
      AccountCapsule takerAccountCapsule)
      throws ItemNotFoundException {

    long takerSellRemainQuantity = takerOrderCapsule.getSellTokenQuantityRemain();
    long makerSellQuantity = makerOrderCapsule.getSellTokenQuantity();
    long makerBuyQuantity = makerOrderCapsule.getBuyTokenQuantity();
    long makerSellRemainQuantity = makerOrderCapsule.getSellTokenQuantityRemain();

    // according to the price of maker, calculate the quantity of taker can buy
    // for makerPrice,sellToken is A,buyToken is TRX.
    // for takerPrice,buyToken is A,sellToken is TRX.

    // makerSellTokenQuantity_A/makerBuyTokenQuantity_TRX =
    //   takerBuyTokenQuantityCurrent_A/takerSellTokenQuantityRemain_TRX
    // => takerBuyTokenQuantityCurrent_A = takerSellTokenQuantityRemain_TRX *
    //   makerSellTokenQuantity_A/makerBuyTokenQuantity_TRX

    long takerBuyTokenQuantityRemain = MarketUtils
        .multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity,
            this.disableJavaLangMath());

    if (takerBuyTokenQuantityRemain == 0) {
      // quantity too small, return sellToken to user
      takerOrderCapsule.setSellTokenQuantityReturn();
      MarketUtils.returnSellTokenRemain(takerOrderCapsule, takerAccountCapsule,
          dynamicStore, assetIssueStore);
      MarketUtils.updateOrderState(takerOrderCapsule, State.INACTIVE, marketAccountStore);
      return;
    }

    long takerBuyTokenQuantityReceive; // In this match, the token obtained by taker
    long makerBuyTokenQuantityReceive; // the token obtained by maker

    if (takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()) {
      // taker == maker

      // makerSellTokenQuantityRemain_A/makerBuyTokenQuantityCurrent_TRX =
      //   makerSellTokenQuantity_A/makerBuyTokenQuantity_TRX
      // => makerBuyTokenQuantityCurrent_TRX = makerSellTokenQuantityRemain_A *
      //   makerBuyTokenQuantity_TRX / makerSellTokenQuantity_A

      makerBuyTokenQuantityReceive = MarketUtils
          .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity,
              this.disableJavaLangMath());
      takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();

      long takerSellTokenLeft =
          takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
      takerOrderCapsule.setSellTokenQuantityRemain(takerSellTokenLeft);
      makerOrderCapsule.setSellTokenQuantityRemain(0);

      if (takerSellTokenLeft == 0) {
        MarketUtils.updateOrderState(takerOrderCapsule, State.INACTIVE, marketAccountStore);
      }
      MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore);
