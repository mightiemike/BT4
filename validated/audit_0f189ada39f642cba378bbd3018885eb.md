### Title
Uncontrolled memory allocation via unchecked array-size felt in deprecated syscall array reader - (File: `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`)

### Summary
`read_felt_array` in the Cairo0 (deprecated) syscall hint processor reads an attacker-supplied `array_size` felt directly from VM memory and converts it to a `usize` with no upper-bound check, then immediately uses it to read a range of that many felts from the VM's memory segments. A malicious/hand-crafted Cairo0 contract that calls any deprecated syscall taking an array argument (e.g. `emit_event`, `send_message_to_l1`, `library_call` payloads) can supply an arbitrarily large size value, causing the sequencer to attempt to materialize a huge `Vec<Felt>` before any gas/resource metering is applied to that length.

### Finding Description
`read_felt_array` reads the `array_size` felt and converts it with `usize::try_from(array_size.to_biguint())?`, which succeeds for any value up to `usize::MAX` (~2^64-1 on 64-bit systems) — no comparison against a sane maximum (e.g. remaining gas, calldata limits, or segment size) is performed: [1](#0-0) 

The resulting size is passed straight into `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)` to build a `Vec<Felt>` of that length: [2](#0-1) 

Because the caller (a deployed Cairo0 contract, entirely controlled by the transaction's declarer/deployer) writes both the `array_size` felt and the data pointer into VM memory before invoking the syscall, the `array_size` value is fully decoupled from the amount of data actually available at the pointer. There is no validation step (such as comparing against `max_calldata_length`, remaining segment size, or a fixed protocol maximum) before the allocation-driving call is made — mirroring the root cause of CVE-2020-18899, where a length field taken from untrusted input (`subBox.length`) was used to size a buffer allocation without a sanity bound.

This differs from the well-guarded RPC/gateway paths, which do enforce explicit size caps (e.g. `max_calldata_length`, `max_contract_bytecode_size`) before processing: [3](#0-2) 
No equivalent bound exists for array arguments read inside deprecated-syscall execution.

### Impact Explanation
An attacker can deploy a Cairo0 contract whose bytecode (not necessarily produced by the standard compiler) sets a huge array-length felt for a syscall argument (e.g. `emit_event`'s keys/data length, `send_message_to_l1`'s payload length, or `library_call` calldata length) and then invoke it via a normal transaction. When the sequencer executes this call in `blockifier`, `read_felt_array` will attempt to materialize a `Vec<Felt>` sized to the attacker-chosen value before any gas exhaustion check applies to that specific allocation, risking an out-of-memory abort/crash of the executing sequencer node — a network-wide denial-of-service condition ("a network unable to confirm new transactions") if it can be triggered broadly across nodes executing the same block/transaction (including during Starknet OS re-execution, which replays the same execution deterministically on every node).

### Likelihood Explanation
Reachable directly from a single, unprivileged transaction (an `INVOKE`/`L1_HANDLER` call into a previously deployed Cairo0 class using a deprecated syscall), requiring only the ability to deploy or reuse an existing Cairo0 class with crafted bytecode. No special privileges, staking, or operator/proposer role is needed — the deployer/sender fully controls calldata/program bytecode that is executed inside `blockifier`.

### Recommendation
Add an explicit upper bound check on `array_size` in `read_felt_array` (e.g., against the transaction's remaining calldata/gas budget or a fixed protocol-level maximum array length) before calling `felt_range_from_ptr`/`vm.get_integer_range`, returning a syscall error instead of attempting the allocation when the declared size is implausible.

### Proof of Concept
1. Deploy a Cairo0 class whose entry point invokes a deprecated syscall that uses `read_felt_array` (e.g. `emit_event`), but instead of writing the true keys/data length, writes an out-of-range felt (e.g. `2**40`) as the array-size argument while pointing the data pointer at an arbitrary (even otherwise-valid) memory address.
2. Submit an `INVOKE` transaction that calls this entry point.
3. During execution, `read_felt_array` converts the felt to `usize` successfully (still far below `usize::MAX`) and calls `felt_range_from_ptr(vm, ptr, size)` → `vm.get_integer_range(ptr, size)`, forcing the VM to attempt to read/allocate a `Vec<Felt>` of the attacker-chosen size, consuming excessive memory before any per-element gas cost is charged.

```rust
pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
```

```rust
pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
```
