### Title
Deterministic accounts claim "fixed code" but `GlobalContractIdentifier::AccountId` code binding is mutable, letting the global-contract owner rug-pull funds sent to deterministic accounts - (File: `core/primitives-core/src/deterministic_account_id.rs`, `runtime/runtime/src/deterministic_account_id.rs`, `runtime/runtime/src/global_contracts.rs`)

### Summary
The external report describes bidders trusting a sale-creator-supplied vesting/timelock contract whose code the creator can silently swap for one that pulls out "locked" funds on demand. The structurally analogous pattern in nearcore is deterministic accounts (NEP-616): documentation states deterministic accounts have "fixed code and fixed initial state" [1](#0-0) , and a user can only create/initialize one via `DeterministicStateInitAction` whose `state_init.code` references a `GlobalContractIdentifier` [2](#0-1) . However, when that identifier is `GlobalContractIdentifier::AccountId(id)` rather than `CodeHash`, the referenced code is explicitly documented as owner-updatable: "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users" [3](#0-2) .

### Finding Description
A deterministic account's ID is derived only from the borsh-encoding of `DeterministicAccountStateInit` (the `GlobalContractIdentifier` and initial `data`), not from the actual WASM bytes when that identifier is an `AccountId` [4](#0-3) . When such a deterministic account is initialized, `deploy_deterministic_account` sets the account's `AccountContract` to reference the global-contract owner's account id via `use_global_contract`, and the actual code is fetched indirectly through that pointer [5](#0-4) .

Because `GlobalContractDeployMode::AccountId` global contracts are mutable by design ("Users will be able reference it by that account id. This allows the owner to update the contract for all its users") [6](#0-5) , any account previously used as the `code` reference in `DeterministicAccountStateInit` can redeploy entirely different, malicious WASM at any later time via a subsequent `DeployGlobalContract` action with `deploy_mode: AccountId` and the same identifier. All existing deterministic accounts that pinned their code to that `AccountId` — including ones that were funded by depositing NEAR via `Transfer` before/along with `DeterministicStateInitAction` [7](#0-6)  — will silently begin executing the new, attacker-controlled code the next time they are invoked, without any action from the deterministic account's controller or funder.

This mirrors the external report's root cause precisely: a party who is not the counterparty/beneficiary of locked value controls a reference (the vesting contract address / here, the `AccountId`-mode global contract) whose code can be swapped after users have already committed funds, enabling the "trusted" logic to be replaced with code that drains balances (e.g., via a `Transfer`/`FunctionCall` promise back to the attacker) once invoked.

### Impact Explanation
Any funds transferred into a deterministic account that references a mutable (`AccountId`-mode) global contract can be redirected/drained by the global-contract owner redeploying malicious code at that identifier, at a time of their choosing (analogous to "claim before cliff" timing in the original report). This is a concrete unauthorized value movement / frozen-funds vector reachable purely through ordinary, unprivileged transactions: `DeployGlobalContract` (AccountId mode) followed later by a redeploy, combined with any counterparty using `DeterministicStateInitAction` referencing that account id and transferring funds to the resulting deterministic account.

### Likelihood Explanation
Medium: it requires (1) an application/protocol to choose `GlobalContractIdentifier::AccountId` (rather than the immutable `CodeHash`) when constructing deterministic accounts that will hold value, and (2) users/relayers to deposit funds into such deterministic accounts before the owner rugs the code. Nothing in the runtime prevents building `DeterministicAccountStateInit` with an `AccountId` identifier for value-holding accounts, and the documentation's blanket claim of "fixed code" for deterministic accounts does not call out this caveat, making misuse likely for integrators who don't realize `AccountId`-mode contracts are mutable.

### Recommendation
- Update documentation to explicitly warn that deterministic accounts only have truly immutable code when `state_init.code` is `GlobalContractIdentifier::CodeHash`; `AccountId`-mode references remain mutable by the global contract owner and must not be used for deterministic accounts intended to hold value trustlessly.
- Consider disallowing (or gas/UX-flagging) `DeterministicStateInitAction` with an `AccountId`-mode `GlobalContractIdentifier` when the deterministic account is expected to receive funds, or require an explicit opt-in acknowledging the mutability, to prevent accidental construction of "fixed code" accounts whose code can actually change post-funding.

### Proof of Concept
1. Attacker account `owner.near` deploys a benign global contract in `AccountId` mode: `DeployGlobalContract { code: benign_wasm, deploy_mode: AccountId }` [8](#0-7) .
2. A victim (or relayer) constructs `DeterministicAccountStateInit::V1 { code: GlobalContractIdentifier::AccountId("owner.near"), data }`, derives the deterministic account id via `derive_near_deterministic_account_id` [4](#0-3) , and submits `DeterministicStateInitAction` with a deposit to fund it, per the documented flow [9](#0-8) .
3. The victim/relayer sends additional `Transfer`s to the deterministic account, believing its "fixed code" will only ever do what the benign contract permits.
4. `owner.near` later submits another `DeployGlobalContract { code: malicious_wasm, deploy_mode: AccountId }` for the same account id — this is fully permitted and simply increments the distribution nonce [10](#0-9) .
5. The next function call to the deterministic account executes `malicious_wasm`, which can, e.g., issue a `Promise::transfer` to `owner.near`, draining the deterministic account's balance — funds the victim believed were protected by immutable, deterministic logic.

Note: I was unable to fully trace whether any additional protocol-level check (e.g., a specific `ProtocolFeature` gate) restricts using `AccountId`-mode identifiers specifically for `DeterministicStateInitAction` beyond what is shown in `deterministic_account_id.rs`/`global_contracts.rs`; the index did not surface such a restriction, but a full-repo review (e.g., via a Devin session) would be needed to rule it out with certainty.

```rust
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
```

```rust
pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;
```

```rust
fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}
```
