### Title
Unhandled `atob()` decode exception in `sanitizeHost` allows DoS of unauthenticated auth/embedded-redirect handlers - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
`sanitizeHost` only validates the `host` query parameter's *character set* with a base64-alphabet regex before decoding it with `atob()` via `decodeHost`, but never validates that the string has a length that is actually decodable as base64. This mirrors the reported bug class: two individually-"valid-looking" values (a regex-accepted base64 charset string) are combined into an operation (`atob`) whose accepted domain is narrower than what the validator checks, so a value that passes the pre-check can still make the downstream primitive throw. Because `sanitizeHost` and its callers never wrap the decode step in a `try/catch`, an attacker-controlled `host` param on an anonymous request can throw an uncaught exception inside auth/redirect handlers.

### Finding Description
`sanitizeHost` in `shop-validator.ts` does:
```ts
const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
  ...
``` [1](#0-0) 

`decodeHost` simply calls the global `atob(host)`: [2](#0-1) 

The regex only checks that every character belongs to the base64 alphabet (`[0-9a-zA-Z+/]` plus optional `=` padding) — it does not enforce that the string length is a valid base64 length. Node's WHATWG-compliant `atob()`/`Buffer` base64 decode throws an `InvalidCharacterError`-style exception when, after removing padding, the remaining length mod 4 equals 1 (e.g. a single character like `"A"`, or any string whose un-padded length ≡ 1 mod 4). Such a string passes the regex (it's a legal base64-alphabet string) but makes `decodeHost`/`atob` throw. There is no `try/catch` anywhere in `sanitizeHost`, `decodeHost`, or in its direct callers, so the exception propagates uncaught.

This function is called directly on the raw, unauthenticated `host` query parameter in multiple entry points reachable before any session/HMAC validation, e.g.:
- `redirect-to-auth.ts` (`clientSideRedirect`) in `shopify-app-express`, invoked from the OAuth-begin flow with `req.query.host`: [3](#0-2) 
- `redirect-to-shopify-or-app-root.ts` middleware, also using `req.query.host` directly with no try/catch: [4](#0-3) 
- `validate-shop-and-host-params.ts` in `shopify-app-remix`/`shopify-app-react-router`, called during `authenticate.admin()` on `url.searchParams.get('host')`: [5](#0-4) 

None of these call sites, nor `sanitizeShop`/`sanitizeHost` themselves, catch a thrown exception from `atob`/`new URL`.

### Impact Explanation
A single anonymous/unauthenticated HTTP request to an app's OAuth-begin route or embedded-redirect route with a crafted `host` query parameter (e.g. `host=A`) can throw an uncaught synchronous exception inside these handlers before any authentication is performed. In Express-based apps (`shopify-app-express`), this occurs inside `async` route/middleware functions; if the surrounding router does not have generic async-error handling, the resulting rejected promise is unhandled, which can crash the process or leave the request hanging, denying availability of the auth flow for that instance. In `shopify-app-remix`/`shopify-app-react-router`, the exception surfaces as an unhandled error in the `authenticate.admin()` path used on every embedded app page load, effectively blocking merchants from installing/using the app until fixed. This matches the report's DoS-of-auth-handler impact class, though it does not lead to a bypass of authentication or credential leakage — it is an availability issue on the auth path.

### Likelihood Explanation
The trigger requires no privileges: any anonymous request with a one- or five-character (mod-4≡1) base64-alphabet `host` value is enough, and `host` is a normal, attacker-controlled query parameter on public, pre-auth routes (`/auth`, and any embedded route hitting `authenticate.admin()`), so likelihood is high for anyone probing the app's auth endpoints.

### Recommendation
- In `sanitizeHost` / `decodeHost`, wrap the `atob(...)` call (and the subsequent `new URL(...)`) in a `try/catch`, treating any decode failure as an invalid host (return `null` or throw `InvalidHostError` per the `throwOnInvalid` contract) instead of letting the exception propagate.
- Tighten `base64regex` to only accept strings whose un-padded length is a valid base64 length (i.e., reject lengths ≡ 1 mod 4) before attempting to decode.
- Audit all direct callers of `sanitizeHost`/`decodeHost` to confirm they no longer rely on an implicit assumption that this function cannot throw.

### Proof of Concept
1. Send `GET /auth?shop=test-shop.myshopify.com&host=A&embedded=1` to an app built with `shopify-app-express` (hits `redirectToAuth` → `clientSideRedirect` → `api.utils.sanitizeHost('A')`).
2. `base64regex.test('A')` returns `true` (single alphanumeric char, no padding required by the regex).
3. `decodeHost('A')` calls `atob('A')`, which throws because the un-padded length (1) mod 4 equals 1.
4. The exception is not caught anywhere in `sanitizeHost`, `decodeHost`, or `clientSideRedirect`/`redirectToAuth`, producing an unhandled error/rejected promise in the OAuth-begin handler for that request. The same can be reproduced against `validate-shop-and-host-params.ts` in the Remix/React Router adapters by loading the embedded app URL with `?host=A`.
