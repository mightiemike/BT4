### Title
Broken `Cookies.deleteCookie()` uses a hardcoded `path: '/'`, so the OAuth `state` cookie is never actually cleared for non-root `callbackPath` values, weakening the single-use nonce protection - (File: `packages/apps/shopify-api/runtime/http/cookies.ts`)

### Summary
`Cookies.deleteCookie()` always issues the deletion `Set-Cookie` with a hardcoded `path: '/'`, regardless of the path attribute that was used to originally set the cookie. The OAuth `state` cookie (`STATE_COOKIE_NAME`) is set in `begin()` with `path: callbackPath` but is "revoked" in `callback()` via `deleteCookie(STATE_COOKIE_NAME)`, which uses `'/'` instead. When `callbackPath` is not `/` (the normal case, e.g. `/auth/callback`), the deletion targets a *different* cookie than the one the browser is actually storing, so the real state cookie is never invalidated by this call — an exact structural analog of the reported `revokeDelegate()` bug, where the revoke operation hashed a different key than the one used to create the delegation, leaving the original registration live.

### Finding Description
In `begin()`, the anti-CSRF nonce is stored in a signed cookie scoped to the callback path: [1](#0-0) 

In `callback()`, after validating the request, the code attempts to invalidate that same cookie: [2](#0-1) 

`cookies.deleteCookie(STATE_COOKIE_NAME)` calls into the shared `Cookies` implementation: [3](#0-2) 

Browsers key cookies by `(name, domain, path)`. Because `deleteCookie` hardcodes `path: '/'`, the expiring `Set-Cookie` header it emits does not match the cookie that was actually stored (which has `path: callbackPath`). Whenever `callbackPath !== '/'` — the normal configuration for essentially every real app (`/auth/callback`, `/api/auth/callback`, etc.) — the deletion is a no-op against the real cookie: the browser keeps the original, already-used `state`/`state.sig` cookie pair alive at its real path until its own `expires` timestamp (60 seconds after `begin()` was called), rather than being invalidated immediately once consumed by `callback()`.

This directly mirrors the external report's root cause: a "revoke" call constructs its lookup key differently from how the record was created, so the invalidation silently fails and the old data remains valid to be reused.

### Impact Explanation
The `state` cookie is the sole App CSRF nonce used by `validQuery()` (via `safeCompare(query.state!, stateFromCookie)`) to accept an OAuth callback as legitimate. Failure to actually clear it after first use means the nonce is *not* single-use in the way its "consume, then delete" design intends — it remains valid to reuse in a second, forged `/auth/callback` request for up to the remainder of its 60‑second lifetime instead of being invalidated the instant it's spent. This weakens the anti-replay/anti-CSRF guarantee of the OAuth flow and is a genuine, root-cause bug in shared cookie-handling code (`packages/apps/shopify-api/runtime/http/cookies.ts`) used by every OAuth flow in this monorepo (`shopify-api`, `shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router` auth-code-flow strategies).

### Likelihood Explanation
The `path` mismatch is deterministic and will occur on essentially any real deployment, since apps virtually never configure their OAuth callback route at `/` — it will always be some non-root path such as `/auth/callback`. No privileged access or dependency compromise is needed to trigger the mismatch; it happens automatically on every OAuth `begin`/`callback` cycle. However, actual exploitation of the un-cleared nonce is time-boxed to the cookie's own 60-second `expires` window set at creation time, and the same-named cookie is naturally overwritten by the next legitimate `begin()` call, which narrows — but does not eliminate — the practical CSRF replay window.

### Recommendation
Make `deleteCookie()` accept (or otherwise track/propagate) the same `path` (and `domain`) attributes that were used when the cookie was set, so the expiring `Set-Cookie` header actually matches and clears the original cookie. Concretely:
- Change `deleteCookie(name: string, opts?: Partial<Pick<CookieData, 'path' | 'domain'>>)` and merge `opts` into the deletion cookie instead of hardcoding `path: '/'`.
- Update call sites (`oauth.ts`'s `callback()`, and `deleteInvalidCookies()`) to pass the path the cookie was originally created with (`callbackPath` for `STATE_COOKIE_NAME`, `cookiePath` for `SESSION_COOKIE_NAME`).
- Add a regression test verifying that a `state` cookie set with a non-root `path` is actually removed (i.e., the deletion `Set-Cookie` path matches) after a successful `callback()`.

### Proof of Concept
1. Configure an app with `callbackPath: '/auth/callback'` (any non-root path — the default in all templates).
2. Call `shopify.auth.begin({..., callbackPath: '/auth/callback'})`. The response sets `shopify_app_state` and `shopify_app_state.sig` with `path=/auth/callback` and `expires=<now+60s>`.
3. Complete a valid `shopify.auth.callback()` using that state. Inspect the response headers: the deletion `Set-Cookie: shopify_app_state=; path=/; expires=Thu, 01 Jan 1970 ...` is emitted, at `path=/`.
4. Because the original cookie was stored at `path=/auth/callback`, the browser retains it, unexpired, until its original 60-second `expires` elapses.
5. Within that window, an attacker who can obtain the still-valid `state` value (e.g., via referrer/log leakage or a race with the victim's own flow) can replay a second forged request to `/auth/callback?state=<same-value>&hmac=<valid>&...`; `validQuery()`'s `safeCompare` will still succeed because the stale cookie was never actually cleared, even though the nonce should have been single-use.
