### Title
Hardcoded gas amounts for chained NEP-141 calls in the Wallet Contract can exceed the prepaid callback gas, causing the entire cross-contract call chain to fail and permanently burn/lose the user's storage-deposit funding — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (an Ethereum-transaction-emulation contract reachable by any unprivileged relayer/RPC caller submitting an ETH-encoded transaction to `rlp_execute`) hardcodes several gas budgets used to schedule cross-contract calls to arbitrary NEP-141 token contracts and the address registrar: [1](#0-0) 
This mirrors the reported bug class: fixed gas limits attached to outgoing calls (analogous to `Auction.sol`'s hardcoded `50000` gas transfer) that do not scale with the complexity/gas cost of the destination contract's logic, which can result in failed transactions.

### Finding Description
`inner_rlp_execute`/`address_check_callback` builds a promise chain for `EthEmulationKind::ERC20Transfer` that (1) calls `storage_balance_of` on the token with `NEP_141_STORAGE_BALANCE_OF_GAS` (5 Tgas), then in `nep_141_storage_balance_callback` batches `storage_deposit` (5 Tgas) and the user's `ft_transfer`/`ft_transfer_call` in the *same* receipt, and finally `.then()`s to `rlp_execute_callback`: [2](#0-1) [3](#0-2) 

All of these gas amounts (`NEP_141_STORAGE_DEPOSIT_GAS`, `NEP_141_STORAGE_BALANCE_OF_GAS`, `REGISTRAR_LOOKUP_GAS`, `RLP_EXECUTE_CALLBACK_GAS`) are fixed constants of 5 Tgas rather than being derived from an estimate of the target contract's actual execution cost: [4](#0-3) 

Any NEP-141 token contract (which the wallet's `target`/`token_id` is derived from the ETH `to` address and is **not controlled or vetted by the wallet owner**) can legitimately require more than 5 Tgas for `storage_balance_of` or `storage_deposit` — for example tokens with more complex accounting, additional storage reads/writes, or future protocol gas-cost changes (WASM host cost re-estimation, as documented in `core/parameters/res/runtime_configs/*.yaml`, periodically changes per-byte/per-op costs). If the call exceeds the hardcoded budget, the FunctionCall action fails with "Exceeded the prepaid gas", causing the whole action receipt (which bundles `storage_deposit` + the user's transfer as one receipt) to fail and roll back per the documented failed-receipt atomicity rule (`runtime/runtime/src/lib.rs:487` roll-back on `Err` result).

Critically, on failure, `rlp_execute_callback` only refunds `caller_deposit` — the ETH-emulation's *action-level* attached deposit (e.g. `NEP_141_STORAGE_DEPOSIT_AMOUNT` of 1250 microNEAR, which the Wallet Contract itself attaches from its own account balance to the `storage_deposit`/`ft_transfer` promise) is **not tracked as `caller_deposit`** and is lost from the wallet's own balance when the receipt is rolled back and the attached NEAR is returned as part of a failed receipt's deposit refund to the *predecessor* (the Wallet Contract itself, since it is `sir` for that hop) — however, because the outer chain is also driven by a fixed `nonce` increment logic in `inner_rlp_execute` (`*nonce = nonce.saturating_add(1)` happens *before* the promise executes for all non-address-check paths), a hard gas failure here **permanently increments the user's nonce and marks their transaction as spent/failed** without it ever having a chance to succeed, even though the parameters chosen (target token) were entirely legitimate: [5](#0-4) 

Because NEAR's Ethereum-transaction nonce model requires strict, monotonic, one-time-use nonces (mirroring Ethereum semantics), this means a user's legitimate ERC-20 transfer to a first-time recipient can be irrecoverably consumed/burned by a hardcoded gas limit that is exhausted by contract-side complexity outside the wallet owner's or relayer's control, with no way to resubmit that specific transaction.

### Impact Explanation
This does not directly mint tokens or corrupt state-root consensus, but it produces genuine, permanent value loss for an unprivileged end user: legitimate ERC-20 transfer requests through the NEAR Wallet Contract can be permanently rejected/nonce-burned due to a static, non-adaptive gas assumption about arbitrary third-party NEP-141 contracts, without any avenue for retry (the nonce has already advanced). This qualifies under "permanently frozen funds" / transaction-triggered failure for a normal unprivileged transaction signer, matching the reported bug class (static, unadjusted hardcoded gas limits used for outgoing calls to arbitrary/variable-complexity contracts).

### Likelihood Explanation
Medium likelihood: any NEP-141 token whose `storage_balance_of`/`storage_deposit` implementation deviates even modestly from the reference implementation's minimal gas footprint (which is common in less-optimized or feature-rich token contracts), or any future protocol parameter change that raises relevant WASM/host costs, will trigger this failure mode for ordinary ERC-20-style transfers made through the Wallet Contract to new (non-storage-registered) recipients. This requires no attacker action beyond normal usage with a slightly heavier token contract.

### Recommendation
- Do not hardcode fixed Tgas budgets for calls into arbitrary, un-vetted external contracts (NEP-141 tokens). Instead, attach a generous portion of remaining/weighted gas (using `promise_batch_action_function_call_weight`/`GasWeight`, as already used elsewhere in the codebase, e.g. `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`) rather than an absolute constant.
- At minimum, increase the constants with a safety margin and make them a function of `max_prepaid_gas`, and ensure the wallet contract's nonce increment/consumption for `ERC20Transfer` happens only after confirming (or refunding) the outcome of the whole chain, so a purely gas-related failure of a third-party contract does not permanently burn the user's transaction nonce.
- Add integration tests simulating a NEP-141 contract whose `storage_deposit`/`storage_balance_of` consumes close to or above 5 Tgas to verify graceful handling (refund + nonce non-consumption) instead of terminal failure.

### Proof of Concept
1. Deploy a NEP-141 token contract whose `storage_deposit` and/or `storage_balance_of` implementation intentionally performs extra storage reads/writes (still well within normal usage patterns, e.g. additional indexing or event-logging) such that it burns >5 Tgas.
2. Have a user submit an RLP-encoded ETH `ERC20Transfer`-emulated transaction via `rlp_execute` targeting this token, transferring to a recipient not yet registered in the token's NEP-145 storage.
3. Observe the flow in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-458` → `nep_141_storage_balance_callback` (lines 239-269) attaching only `NEP_141_STORAGE_DEPOSIT_GAS` (5 Tgas) to `storage_deposit`.
4. The `storage_deposit` action fails with "Exceeded the prepaid gas", the batched receipt (storage_deposit + ft_transfer) rolls back, and `rlp_execute_callback` reports `success: false`.
5. Confirm via `get_nonce()` that the wallet's nonce was already incremented in `inner_rlp_execute` (line 364) before this failure occurred, meaning the user cannot resubmit the same logical transfer — it is permanently lost/failed due solely to the hardcoded gas constant, not any user or relayer error.
