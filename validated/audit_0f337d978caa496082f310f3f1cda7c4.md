## Finding: No subgroup validation on chunky PVSS transcript points before `aggregate_with` accumulates them into the aggregated dealt public key

### Title
Chunky PVSS `Subtranscript` points are deserialized with `Validate::No` and never subgroup-checked before `SubtranscriptProjective::aggregate_with` sums them into `V0_proj` - ([File: crates/aptos-dkg/src/pvss/chunky/subtranscript.rs])

### Summary
The chunky weighted PVSS `Subtranscript<E>` (which carries the dealt public key component `V0`, per-player shares `Vs`, and ElGamal ciphertext components `Cs`/`Rs`) is deserialized using `ark_de`, which explicitly passes `Validate::No` to `CanonicalDeserialize`. No code path in the chunky PVSS verification or aggregation pipeline performs an explicit subgroup-membership check on these points before `SubtranscriptProjective::aggregate_with` accumulates them via `self.V0_proj += other.V0` (and similarly for `Vs_proj`, `Cs_proj`, `Rs_proj`).

### Finding Description
`Subtranscript<E>` fields are annotated with `#[serde(serialize_with = "ark_se", deserialize_with = "ark_de")]`: [1](#0-0) 

`ark_de` deserializes with `Validate::No`: [2](#0-1) 

This means an attacker who crafts a transcript (or malicious subtranscript received over the network) can supply a `V0` (or `Vs`/`Cs`/`Rs`) point that lies on the curve but not in the correct prime-order subgroup — a classic small-subgroup/cofactor attack input. Neither `Validate::Yes` deserialization nor any explicit `is_in_correct_subgroup_assuming_on_curve()`-style call exists anywhere in the chunky PVSS code: `verify_weighted_preamble` only checks vector-length shapes, not group membership: [3](#0-2) 

The subsequent verification steps (SCRAPE low-degree test, range proof, sigma-protocol PoK, pairing/MSM checks) all operate as generic elliptic-curve arithmetic and do not reject points outside the correct-order subgroup: [4](#0-3) 

Finally, `SubtranscriptProjective::aggregate_with` performs only length `ensure!` checks (`Cs_proj.len()`, `Vs_proj.len()`, `Rs_proj.len()` against the config and against `other`), and then blindly accumulates: [5](#0-4) 

This is invoked directly on peer-submitted, unprivileged transcript data in the DKG aggregation path (`ChunkyTranscriptAggregationState::add`), where `subtranscript` from a just-deserialized peer transcript is fed into `aggregate_with` without any subgroup check having occurred: [6](#0-5) [7](#0-6) 

The `Aggregatable::aggregate`/`Aggregated::aggregate_with` trait contract itself has no subgroup obligation either: [8](#0-7) 

Note: the `das` (BLS-based) PVSS path uses `blstrs`'s own `TryFrom<&[u8]>` for `DealtPubKey`, whose comment claims `GroupEncoding::from_bytes` "already performs the necessary point validation," so that specific path is not confirmed vulnerable here (unverified whether blstrs' validation includes subgroup checks) [9](#0-8) . The confirmed gap is specifically in the arkworks-based chunky weighted PVSS path (`Subtranscript<E>`/`SubtranscriptProjective<E>`), which is the type actually feeding `aggregate_with`.

### Impact Explanation
If a subgroup-invalid point is injected as `V0` (or `Vs`/`Cs`/`Rs`) in a submitted subtranscript and passes into `aggregate_with` unchecked, the resulting `V0_proj` accumulator — and hence the final aggregated dealt public key and per-player share commitments derived from `normalize()` — diverges from the value that would be computed if only valid-subgroup contributions were summed. Since this dealt public key becomes part of the committed DKG session state (`DealtPubKeyShares`, `AggregatedSubtranscript`) that is signed, certified, and used by all validators, this corrupts a value that is supposed to be deterministically and identically derived by every honest validator, and could bias/corrupt derived DKG/randomness key material. This matches the "committed state differs from the VM/protocol output that honest validators should derive" failure mode described in the prompt.

### Likelihood Explanation
This does not require a trusted operator mistake — any validator (an "unprivileged" transcript-submitting party in the DKG broadcast protocol) can submit a specially crafted transcript with a subgroup-invalid point; deserialization (`Validate::No`) and the shape-only `verify_weighted_preamble`/LDT/range-proof/PoK checks do not reject such a point on their own (no explicit subgroup check exists in this code path). Whether the SCRAPE LDT, sigma-protocol PoK, or the final G1/G2 MSM pairing-equality check happen to indirectly reject a specific choice of subgroup-invalid point is not fully proven here — that would need to be verified empirically (see Proof of Concept) since these are linear/algebraic identities over field elements that may or may not be sensitive to cofactor components, depending on the exact points chosen.

### Recommendation
Add explicit subgroup-membership checks (`is_in_correct_subgroup_assuming_on_curve()` or use `Validate::Yes` during `CanonicalDeserialize`) for all group elements in `Subtranscript<E>` (`V0`, `Vs`, `Cs`, `Rs`) either at deserialization time or as an explicit pre-check inside `verify_weighted_preamble`/`SubtranscriptProjective::aggregate_with`, before any accumulation occurs.

### Proof of Concept
1. Construct a `Subtranscript<E>` where `V0` is a point that is on-curve (satisfies the curve equation) but not in the prime-order subgroup (e.g., a low-order point from the complementary cofactor subgroup of BLS12-381 G2).
2. Serialize it with `ark_se`/BCS as done for `ChunkyTranscript`, and submit it via the peer transcript path (`ChunkyTranscriptAggregationState::add` → `deserialize_chunky_transcript_and_verify`).
3. Observe that deserialization succeeds (`Validate::No`) and trace whether `transcript.verify(...)` (SCRAPE LDT + range proof + PoK + MSM checks) accepts or rejects it — if any parameter choice causes the checks to still pass, the point flows into `SubtranscriptProjective::aggregate_with`'s `self.V0_proj += other.V0`, producing an aggregated `V0_proj`/dealt public key that differs from what would result had the invalid point been rejected pre-aggregation.
