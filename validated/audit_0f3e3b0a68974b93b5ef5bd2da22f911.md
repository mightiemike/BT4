### Title
Attached NEAR Deposit Permanently Locked in `WalletContract::rlp_execute` on Early-Return Error Paths — (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

---

### Summary

The `rlp_execute` entry point of the `WalletContract` (the global contract deployed on every ETH-implicit account) is marked `#[payable]` and accepts attached NEAR deposits from external callers. The `CallerDeposit` mechanism exists specifically to track and refund those deposits when a downstream cross-contract call fails. However, several early-return paths inside `rlp_execute` and its callbacks return a `PromiseOrValue::Value(...)` directly — bypassing the callback chain entirely — without issuing any refund. Any NEAR attached in those paths is permanently credited to the wallet contract's own balance with no retrieval mechanism.

---

### Finding Description

`rlp_execute` is the sole public mutable entry point of `WalletContract`:

```rust
#[payable]
pub fn rlp_execute(
    &mut self,
    target: AccountId,
    tx_bytes_b64: String,
) -> PromiseOrValue<ExecuteResponse> {
``` [1](#0-0) 

**Path 1 — `has_in_flight_tx` guard (lines 97–104):**

```rust
if self.has_in_flight_tx {
    return PromiseOrValue::Value(ExecuteResponse { ... });
}
``` [2](#0-1) 

This returns immediately before `inner_rlp_execute` is called, so `CallerDeposit` is never constructed and no refund promise is ever scheduled. Any NEAR attached to this call is absorbed by the wallet contract.

**Path 2 — Non-relayer error returns from `inner_rlp_execute` (line 126):**

```rust
Err(e) => PromiseOrValue::Value(e.into()),
``` [3](#0-2) 

`inner_rlp_execute` returns `Err(Error::User(_))` for invalid Ethereum transactions (wrong chain ID, invalid signature, unsupported action type, etc.) and `Err(Error::AccountNonceExhausted)` when the nonce is exhausted. In both cases the function returns a value directly. `caller_deposit` is computed inside `inner_rlp_execute` but the error path exits before any refund promise is attached: [4](#0-3) 

**Path 3 — `address_check_callback` early returns (lines 142–157):**

When the address-registrar cross-contract call fails or returns unparseable data, the callback returns `PromiseOrValue::Value(...)` without touching `caller_deposit`: [5](#0-4) 

**Path 4 — `nep_141_storage_balance_callback` early returns (lines 204–220):**

Same pattern: the `storage_balance_of` call failure or parse error returns early without refunding `caller_deposit`: [6](#0-5) 

The `CallerDeposit` refund only fires inside `rlp_execute_callback` when the downstream promise fails:

```rust
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(refund_promise, ...);
    }
``` [7](#0-6) 

All four paths above never reach `rlp_execute_callback`, so the refund is never issued.

The `CallerDeposit` type itself confirms the intent: it is constructed only for external (non-self) callers with a non-zero deposit, and its purpose is explicitly to enable refunds on failure: [8](#0-7) 

---

### Impact Explanation

Any NEAR tokens attached to `rlp_execute` by an external caller that hits one of the four paths above are permanently credited to the ETH-implicit account's balance. Because ETH-implicit accounts cannot have full-access keys added and cannot be deleted, and because `rlp_execute` is the only mutable entry point, there is no mechanism for the wallet owner or the caller to recover those funds. This is a direct loss-of-funds impact for the depositing party.

The `WalletContract` is deployed as a global contract on every ETH-implicit account (a core protocol feature activated at v83): [9](#0-8) 

---

### Likelihood Explanation

- **Path 1** (`has_in_flight_tx`): Requires a concurrent call while a transaction is in flight. Unlikely in normal usage but reachable by any unprivileged caller who races or is tricked into attaching a deposit during an in-flight window.
- **Path 2** (user errors): Any external caller who attaches a deposit and whose embedded Ethereum transaction fails validation (wrong chain ID, bad signature, unsupported action) loses the deposit. A malicious relayer can deliberately submit an invalid transaction to drain a caller's attached deposit.
- **Paths 3 & 4** (callback early returns): Triggered by transient failures of the address-registrar or NEP-141 `storage_balance_of` calls, which are external contracts and can fail or return unexpected data.

---

### Recommendation

In every early-return path inside `rlp_execute` and its callbacks, compute `CallerDeposit` before the guard and issue a refund transfer promise before returning. Concretely:

1. In the `has_in_flight_tx` guard, read `env::attached_deposit()` and `env::predecessor_account_id()` before the check; if a non-zero deposit exists from an external caller, schedule a `Transfer` refund promise before returning the error value.
2. In the `Err(e) => PromiseOrValue::Value(e.into())` arm of `rlp_execute`, use the already-computed `caller_deposit` (which is available inside `inner_rlp_execute` before the error is returned) to schedule a refund.
3. In `address_check_callback` and `nep_141_storage_balance_callback`, refund `caller_deposit` in every early-return arm, mirroring the pattern already used in `rlp_execute_callback`.

---

### Proof of Concept

1. Deploy a fresh ETH-implicit account (wallet contract is auto-deployed).
2. Start a long-running transaction via `rlp_execute` (e.g., a cross-contract call with high gas), setting `has_in_flight_tx = true`.
3. While the transaction is in flight, call `rlp_execute` again from any external account, attaching e.g. 5 NEAR as a deposit.
4. The `has_in_flight_tx` guard fires and returns immediately.
5. Observe that the 5 NEAR is now part of the wallet contract's balance and cannot be recovered by the caller or the wallet owner.

Alternatively (Path 2, no race required):

1. Call `rlp_execute` from an external account with 5 NEAR attached.
2. Pass a `tx_bytes_b64` that encodes an Ethereum transaction with an unsupported action (e.g., `AddFullAccessKey`), which triggers `Error::User(UserError::UnsupportedAction(...))`.
3. `inner_rlp_execute` returns `Err(Error::User(_))`; `rlp_execute` returns `PromiseOrValue::Value(e.into())` with no refund.
4. The 5 NEAR is permanently locked in the wallet contract.

The existing test `test_caller_refunds` confirms the refund mechanism works for downstream promise failures but does not cover the early-return paths described above: [10](#0-9)

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
```

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
