### Title
Unhandled `TypeError: Invalid URL` in `sanitizeHost()` from attacker-controlled `host` query param crashes/500s the request path - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost()` calls `new URL('https://' + decodeHost(sanitizedHost))` on attacker-supplied base64 data with no `try/catch`, and none of its callers (`validateShopAndHostParams` in shopify-app-remix/react-router, `redirectToAuth`/`clientSideRedirect` in shopify-app-express) wrap the call either. Because `atob` can decode to arbitrary bytes (control characters, spaces, etc.) that are "forbidden host code points" per the WHATWG URL spec, the `URL` constructor throws a `TypeError`, which propagates uncaught instead of the library's own `InvalidHostError`.

### Finding Description
`sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` (lines 52-90) validates the base64 shape of `host` with `base64regex` at line 54, then unconditionally calls: [1](#0-0) 
`decodeHost` simply does `atob(host)`: [2](#0-1) 
`atob` decodes any well-formed base64 string to an arbitrary byte sequence — including NUL, control characters, or spaces — since base64 encoding is byte-agnostic. When such bytes end up in the string passed to `new URL('https://' + decoded)`, the WHATWG URL host parser throws `TypeError: Invalid URL` for forbidden host code points (e.g. space, `\x00`, tab, `<`, `>`, backslash, etc.) rather than returning a parse failure the code can handle. There is no `try/catch` around this call, and the library's declared failure path (`InvalidHostError`, gated behind `throwOnInvalid`) is never reached for this class of input — the process instead throws an unrelated, unhandled `TypeError`.

None of the identified callers guard against this:
- `validateShopAndHostParams` in shopify-app-remix and shopify-app-react-router calls `api.utils.sanitizeHost(...)` directly with no try/catch: [3](#0-2) 
- `redirectToAuth`/`clientSideRedirect` in shopify-app-express also calls it unguarded: [4](#0-3) 

Existing unit tests for `sanitizeHost` only cover malformed base64 strings and disallowed domains (`INVALID_HOSTS` in `shop-validator.test.ts`), never bytes that are illegal in a URL authority, so this failure mode is untested: [5](#0-4) 

### Impact Explanation
The concrete impact is an unhandled exception thrown out of a host-app request handler for any single request carrying a crafted `host` parameter. In Express (a fully synchronous handler chain calling `clientSideRedirect`), this throw would propagate as an unhandled error out of `redirectToAuth`'s async execution unless the caller wraps it — I could not fully confirm from the code inspected whether all callers of `redirectToAuth` (e.g. `ensure-installed-on-shop.ts`, `auth-callback.ts`) wrap it in try/catch or rely on an Express error-handling middleware, so I cannot conclusively state this crashes the whole process versus surfacing as an unhandled promise rejection/500 for the single request. In Remix/React Router, thrown errors from loaders are generally caught by the framework's own error boundary and rendered as a 500 response for that request, which is the framework's normal error-handling behavior rather than a process crash. Either way, the correct, intended fail-closed behavior (`InvalidHostError`) is bypassed, meaning validation "fails closed" only by accident (via the framework's default un-caught-exception handling) rather than via the library's explicit contract. This is a scoped DoS at most against a single request in the affected handler; I found no evidence in the reachable code that it escalates to full application crash within the shopify-api/shopify-app-express/shopify-app-remix packages themselves.

### Likelihood Explanation
No privileged access is required — any anonymous client can trigger this by sending a GET request with a crafted `host` query parameter to any embedded-app route or the auth/login path that calls `sanitizeHost`. Constructing the payload only requires base64-encoding a string containing a forbidden host code point (e.g. a NUL byte, space, or backslash) so it passes `base64regex` but fails `new URL()` host parsing. This is trivially repeatable and requires no secret or non-default configuration.

### Recommendation
Wrap the `new URL(...)` call inside `sanitizeHost` in a `try/catch`, treating any parse failure the same as an invalid host (set `sanitizedHost = null`, and only throw `InvalidHostError` when `throwOnInvalid` is true), e.g.:
```ts
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  try {
    const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
    // ... existing regex checks
  } catch (_err) {
    sanitizedHost = null;
  }
}
```
This ensures `sanitizeHost` always fails closed with the library's documented `InvalidHostError`/`null` contract instead of leaking an unrelated `TypeError` to callers, removing the dependency on each downstream framework's implicit exception handling.

```ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost should not throw an uncaught TypeError for illegal host bytes', () => {
  const shopify = shopifyApi(testConfig());

  // "\x00.myshopify.com/admin" base64-encoded — passes base64regex,
  // but decodes to a NUL byte, a forbidden host code point.
  const maliciousHost = Buffer.from('\x00.myshopify.com/admin').toString(
    'base64',
  );

  // Currently this throws `TypeError: Invalid URL` instead of returning null.
  expect(() => shopify.utils.sanitizeHost(maliciousHost)).not.toThrow();
  expect(shopify.utils.sanitizeHost(maliciousHost)).toBeNull();
});
```
Expected (current/buggy) result: the test fails because `sanitizeHost` throws `TypeError: Invalid URL` instead of returning `null`.
