## Analysis

The exploit path is real and traces cleanly through the scoped code, but not exactly as framed in the question. The zero-amount deposit skip itself is an intentional, documented design choice (`ValidateForExecution` explicitly allows `Amount == "0"` for `GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` — "skip deposit, still execute payload"). The actual bug is that this zero-amount payload path can be aimed at **any already-deployed UEA/CEA chosen by the attacker**, and gas fees for the (failed) execution attempt are billed to that victim account regardless of whether the attacker's payload passes signature verification. [1](#0-0) 

For `IsCEA == true`, `ValidateForExecution` only requires `Recipient` to be a non-empty valid hex address — there is no check that the recipient belongs to the sender/attacker: [2](#0-1) 

In `ExecuteInboundGasAndPayload` (and the equivalent `ExecuteInboundFundsAndPayload`), when `IsCEA` is true, `Recipient` is used verbatim as `ueaAddr`, verified only to be *a* UEA via the factory, with no ownership binding to the inbound sender: [3](#0-2) 

Since `amount.Sign() > 0` is false, the deposit/autoswap step is skipped entirely, and execution proceeds straight to `ExecutePayloadV2` against the attacker-chosen (victim) UEA: [4](#0-3) 

`ExecutePayloadV2` calls `CallUEAExecutePayload` and then **unconditionally** attempts `DeductGasFeesFromReceipt` against `ueaAddr`, independent of whether `execErr != nil` (i.e., independent of whether the UEA's internal signature check on `verificationData` rejected the attacker's forged payload): [5](#0-4) 

`DeductGasFeesFromReceipt` bills `receipt.GasUsed` at the network `baseFee` (not attacker-controlled `maxFeePerGas`) directly out of the recipient UEA's own bank balance, then burns it: [6](#0-5) 

## Assessment

Because a reverted/failed EVM call (e.g., a signature-verification failure inside the UEA when the attacker cannot produce a valid signature for the victim's key) still returns a `receipt` with non-zero `GasUsed`, an unprivileged attacker who has never funded or interacted with the victim can:

1. Submit any qualifying source-chain event they control (they are always able to be the "sender" of their own inbound), with `TxType = GAS_AND_PAYLOAD`, `IsCEA = true`, `Amount = "0"`, and `Recipient` set to a victim's already-deployed UEA.
2. Attach an arbitrary/garbage `UniversalPayload` + `VerificationData` that will fail the UEA's internal signature check.
3. Cause `ExecuteInboundGasAndPayload` → `ExecutePayloadV2` to run with zero attacker-supplied value, skip the deposit entirely, and still invoke the victim's UEA.
4. Have the resulting (failed) call's gas cost billed against and burned from the victim's UEA native `upc` balance via `DeductGasFeesFromReceipt`, with no consent or benefit to the victim.

This is repeatable at low cost to the attacker and does not require any privileged role — only an honestly-observed source-chain event that they themselves originate, which the honest UV set will faithfully vote on and finalize as-is. The impact is unauthorized loss (burn) of a victim's funds sourced entirely from the victim's own UEA balance, triggered by an attacker who supplied zero value and no valid authorization — this matches the "Required Impacts" category of unauthorized/loss of user funds and corruption of gas-fee accounting.

The one bound on severity is that the fee rate is pinned to `baseFee` rather than attacker-controlled `maxFeePerGas` (see `CalculateGasCost`), so a single call cannot arbitrarily drain the account in one shot — but it can be repeated to grind the balance down over many zero-amount inbound submissions.

### Title
Attacker-chosen zero-amount `IsCEA` inbound lets unprivileged sender force gas-fee burn from any victim UEA without valid authorization — (File: `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/execute_payload.go`, `x/uexecutor/keeper/fees.go`)

### Summary
`ValidateForExecution` permits `Amount = "0"` for `GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD`. Combined with the `IsCEA` path's unrestricted `Recipient` field (not bound to the inbound's `Sender`), an unprivileged attacker can target any already-deployed victim UEA, skip the deposit step, and force a payload-execution attempt against it. `ExecutePayloadV2` bills EVM gas usage of that attempt to the target UEA's own balance even when the UEA's own signature check causes the call to fail.

### Finding Description
`ValidateForExecution` intentionally allows zero amount for payload tx types [1](#0-0) , and for `IsCEA` inbounds does not require `Recipient` to correspond to the `Sender`'s own account [2](#0-1) . `ExecuteInboundGasAndPayload` treats `Recipient` as the target UEA to execute the payload on, confirmed only via a factory "is this a UEA" check, and skips the deposit/autoswap when amount is zero [3](#0-2) . Execution then proceeds to `ExecutePayloadV2` for that UEA [4](#0-3) . `ExecutePayloadV2` calls `DeductGasFeesFromReceipt` against `ueaAddr` regardless of `execErr` [5](#0-4) , which pulls `gasCost` funds directly from the target's bank balance and burns them [7](#0-6) .

### Impact Explanation
A victim's UEA can have its native `upc` balance burned without consent by an attacker who never deposited anything and never obtained valid authorization to act on the victim's account — this is unauthorized loss of user funds accessible to any unprivileged attacker.

### Likelihood Explanation
High: the attacker only needs to originate a real, low-value source-chain event with `IsCEA=true`, `Amount=0`, and `Recipient` set to any known deployed UEA address — no special privileges, keys, or validator collusion required.

### Recommendation
Bind `Recipient` in `IsCEA` inbounds to require prior explicit authorization from the recipient (e.g., an allow-list or owner-consent record), and/or skip `DeductGasFeesFromReceipt` when the underlying `CallUEAExecutePayload` failed due to authorization/signature verification rather than a legitimate authorized execution failure, so that gas is only billed to a UEA when the caller proved ownership.

### Proof of Concept
1. Deploy/observe a victim's UEA (address is public/derivable via factory).
2. As attacker, submit a source-chain transaction/event that the UVs will faithfully observe and vote as an inbound with: `TxType=GAS_AND_PAYLOAD`, `IsCEA=true`, `Amount="0"`, `Recipient=<victim UEA address>`, and a `UniversalPayload`/`VerificationData` with garbage/invalid signature.
3. After finalization, `ExecuteInboundGasAndPayload` skips deposit (amount is 0) and calls `ExecutePayloadV2` against the victim's UEA.
4. `CallUEAExecutePayload` fails signature verification inside the UEA and reverts, but returns a receipt with `GasUsed > 0`.
5. `DeductGasFeesFromReceipt` deducts `GasUsed * baseFee` from the victim UEA's balance and burns it — confirm via bank balance query that victim UEA balance decreased despite the attacker supplying zero value and the payload being rejected.

```go
func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}
```
