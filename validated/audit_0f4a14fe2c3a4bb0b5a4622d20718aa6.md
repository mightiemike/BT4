### Title
Signature malleability enables duplicate weight counting in `ValidateMultiSign` precompile - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The external report concerns a missing `0 < s < secp256k1n/2 + 1` canonical-range check for ECDSA signatures, allowing malleable signatures where `(r, s)` and `(r, n-s)` both validly recover to the same address. In java-tron, the core signature-component validator, `ECDSASignature.validateComponents()` in `crypto/src/main/java/org/tron/common/crypto/ECKey.java`, only checks `0 < r < SECP256K1N` and `0 < s < SECP256K1N` [1](#0-0) . It does not enforce the canonical "low-s" restriction (`s <= n/2`) — that restriction only exists in `toCanonicalised()`, which is used at signing time to normalize a locally-produced signature, not at verification time [2](#0-1) . This means any two byte-distinct signatures `(r, s, v)` and `(r, n-s, v')` that recover to the same address are both accepted as "valid" by every verification path (`ECRecover` precompile, multisig weight-checking, etc).

### Finding Description
The `ValidateMultiSign` precompiled contract (used by TVM smart contracts to validate on-chain multisig authorization for TRON accounts) recovers an address for each supplied signature and accumulates permission "weight" per unique recovered address:

```java
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
``` [3](#0-2) 

The dedup check `matrixContains(executedSignList, sign)` compares `recoveredAddr || signatureBytes`, not just `recoveredAddr`. If `recoveredAddr` was already seen (already in `executedSignList`) but the *exact byte-for-byte* `sign` blob is different — which is trivially achievable via signature malleability by flipping `s` to `n - s` and adjusting the recovery id `v` — the `continue` is skipped, `MUtil.checkCPUTime()` runs, and the code falls through to add `weight` again for the same address. Because signature validation only checks `s < SECP256K1N` (the full curve order) rather than `s <= n/2` (`ECKey.ECDSASignature.validateComponents`), an attacker holding one legitimately obtained multisig signature can trivially derive a second, syntactically distinct but cryptographically valid, signature from the same key and use both to double-count that key's weight toward the multisig `threshold`.

### Impact Explanation
This is an accounting/authorization-bypass issue reachable by any unprivileged caller invoking the `ValidateMultiSign` precompile from a smart contract (address `0x0...0e` / TVM precompile), which underlies TRON's on-chain multisig verification (`validatemultisign(address,uint256,bytes32,bytes[])`). By supplying `k` distinct signers' signatures plus one or more malleable duplicates of a single signer's signature, an attacker can inflate `totalWeight` beyond what the actual set of distinct co-signers authorized, potentially reaching `permission.getThreshold()` with fewer real signers than the permission model requires. This directly undermines the security guarantee of TRON's multi-signature permission system for any contract relying on `ValidateMultiSign` to gate privileged actions (fund release, governance, etc.), constituting an authorization/accounting-bypass impact.

### Likelihood Explanation
Likelihood is high for any contract/integration that (a) uses `ValidateMultiSign` and (b) sets `permission.threshold` such that fewer than `permission.getKeysCount()` are normally sufficient to authorize (which is the entire point of weighted multisig). Deriving `(r, n-s)` from a known `(r,s)` is a standard, well-known, computationally trivial operation (no private key needed), and `v`/recovery id can be brute-forced (0–3) as the code already iterates `recId` when recovering. The only precondition is that the attacker already possesses one valid signature from the target key over the relevant hash — a realistic scenario in any multisig flow where signatures are shared among cosigners before submission.

### Recommendation
Enforce canonical low-s (`s <= CURVE.getN().shiftRight(1)`, i.e., `HALF_CURVE_ORDER`) inside `ECDSASignature.validateComponents()` (or at minimum inside the `ValidateMultiSign`/`BatchValidateSign` precompiles before accepting a recovered signature), and change the multisig dedup logic in `PrecompiledContracts.ValidateMultiSign.execute` to key exclusively on `recoveredAddr` (drop weight for any second occurrence of the same recovered address regardless of the raw signature bytes), rather than on the concatenation of address + raw signature bytes.

### Proof of Concept
1. Signer A holds private key `kA` with weight `wA` under a `Permission` with `threshold = wA + wB` (i.e., normally requires both A and B).
2. Signer A signs `hash` once, producing `sigA1 = (r, s, v)`. `recoverAddrBySign(sigA1, hash)` recovers `addrA`.
3. Attacker (anyone with `sigA1`, no private key needed) computes `s' = n - s` and determines the corresponding recovery id `v'` (0–3 brute-force via `recoverPubBytesFromSignature`), producing `sigA2 = (r, s', v')` — a distinct byte sequence recovering to the same `addrA`.
4. Attacker calls `validatemultisign(address, permissionId, hash, [sigA1, sigA2])`.
5. In `ValidateMultiSign.execute`, iteration 1 adds `addrA`/weight `wA` to `executedSignList`. Iteration 2: `recoveredAddr == addrA` is already in `executedSignList`, but `sign = merge(addrA, sigA2)` is NOT in `executedSignList` (different signature bytes) so `continue` is skipped; `weight = wA` is added again, making `totalWeight = 2*wA`.
6. If `2*wA >= threshold`, the call returns `DATA_ONE` (success) even though only signer A actually authorized, bypassing the requirement for signer B's participation.

        // The order of the curve is the number of valid points that
        // exist on that curve. If S is in the upper
        // half of the number of valid points, then bring it back to
        // the lower half. Otherwise, imagine that
        //    N = 10
        //    s = 8, so (-8 % 10 == 2) thus both (r, 8) and (r, 2)

      }
    }
