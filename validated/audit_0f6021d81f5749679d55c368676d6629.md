### Title
Exchange pool balances can go negative and be silently persisted when the hardened-calculation proposal is disabled - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes new first/second token balances for a Bancor-style exchange pool and only validates that the resulting balances are non-negative when `hardenedCalc` is `true`. When `hardenedCalc` is `false` (the legacy/default path, gated by the `allowHardenExchangeCalculation` proposal), a negative balance is written directly into the `Exchange` protobuf without any check, exactly mirroring the reported Vyper bug where `new_total_value` is assumed non-negative.

### Finding Description
`ExchangeCapsule.transaction()` selects between two processors: the legacy `ExchangeProcessor` (double/float math) and `SafeExchangeProcessor` (`BigDecimal` math), depending on `hardenedCalc`: [1](#0-0) 

The negative-balance guard is conditioned only on `hardenedCalc`:
```java
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [2](#0-1) 

`hardenedCalc` is derived from `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()` via `AbstractExchangeActuator.allowHarden()`: [3](#0-2) 

This flag is a chain proposal switch (see `ProposalUtil.java` / `ProposalService.java`), meaning on any chain/testnet where this proposal has not been activated, all exchange actuators (`ExchangeTransactionActuator`, `ExchangeWithdrawActuator`, `ExchangeInjectActuator`, `ExchangeCreateActuator`) run the legacy, unguarded path. In that path, `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` use `double` arithmetic which can produce results that, combined with `firstTokenBalance - buyTokenQuant` or `secondTokenBalance - buyTokenQuant`, yield a negative `long`: [4](#0-3) 

Unlike the Vyper case (where `convert(negative, uint256)` reverts, causing at worst a DoS), here the balance field is a signed `int64` in the `Exchange` protobuf, so a negative value is not rejected by the type system — it is silently written and persisted via `Commons.putExchangeCapsule`, corrupting the pool's accounting state for all subsequent trades.

### Impact Explanation
A corrupted (negative) `firstTokenBalance`/`secondTokenBalance` in the `Exchange` store would corrupt subsequent Bancor-formula pricing (`exchangeToSupply`/`exchangeFromSupply` divide by these balances), potentially enabling further pricing manipulation or arithmetic exceptions (`ArithmeticException` from `longValueExact()` in `ExchangeWithdrawActuator`/`ExchangeInjectActuator` validate paths) on every future trade against that exchange pair, effectively bricking the trading pair (accounting corruption / DoS of that exchange).

### Likelihood Explanation
Likelihood depends on whether `allowHardenExchangeCalculation` has been activated on the target chain; if not activated (its default/initial state prior to proposal approval), any user broadcasting `ExchangeTransactionContract`/`ExchangeWithdrawContract` transactions with quantities engineered to drive the float-based Bancor computation past the available balance can trigger this, making it reachable from an unprivileged, ordinary broadcast transaction.

### Recommendation
Remove the `hardenedCalc` condition and always enforce the non-negative invariant on `newFirstTokenBalance`/`newSecondTokenBalance` in `ExchangeCapsule.transaction()`, regardless of the `allowHardenExchangeCalculation` flag, or reject the transaction in `doValidate()` of the exchange actuators before committing the new balances to the store.

### Proof of Concept
1. Ensure `allowHardenExchangeCalculation` proposal is not yet activated on the target chain (legacy path active), so `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, ..., allowHarden())` with `hardenedCalc = false`.
2. Create/find an `Exchange` pool with small token balances via `ExchangeCreateContract`.
3. Broadcast an `ExchangeTransactionContract` with a `quant` chosen so that the float-based `ExchangeProcessor.exchange()` computation returns a `buyTokenQuant` exceeding the pool's opposite-side balance.
4. `newFirstTokenBalance`/`newSecondTokenBalance` becomes negative in `ExchangeCapsule.transaction()`; since `hardenedCalc` is `false`, the guard at lines 160-162 is skipped, and the negative balance is persisted via `Commons.putExchangeCapsule`, corrupting the exchange pool state.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
