### Title
Unbounded-recursion JSON sort during Cairo0 hinted-class-hash computation can stack-overflow the Starknet OS re-execution / class-hash pipeline - ([File: crates/starknet_os/src/hints/class_hash/hinted_class_hash.rs])

### Summary
`compute_cairo_hinted_class_hash` in `crates/starknet_os/src/hints/class_hash/hinted_class_hash.rs` deserializes an untrusted deprecated (Cairo0) contract class into `serde_json::Value` and recursively normalizes it with `sort_json_value`, a plain (non-tail-recursive) recursive function with no depth bound, before hashing it. Multiple fields that feed this function - `abi` ("Contract ABI, which has no schema definition"), and the program's `attributes`, `identifiers`, `hints`, and `reference_manager` - are all typed as raw `serde_json::Value` and are attacker-controlled content of a `DECLARE` transaction's `contract_class`. A declarer can submit a Cairo0 class containing a deeply nested JSON structure (e.g., nested arrays/objects thousands of levels deep) inside any of these fields, causing `sort_json_value` to recurse until the call stack is exhausted, crashing the process computing the hinted class hash.

### Finding Description
`sort_json_value` is defined as: [1](#0-0) 

It is invoked unconditionally inside `compute_cairo_hinted_class_hash`, which is the routine used to compute the "hinted" (legacy) class hash of a declared Cairo0 contract: [2](#0-1) 

The struct being sorted, `CairoContractDefinition`/`CairoProgram`, deliberately keeps several fields as opaque `serde_json::Value` because they are explicitly documented as having "no schema definition": [3](#0-2) [4](#0-3) 

The underlying `starknet_api::deprecated_contract_class::ContractClass`/`Program` types that carry these fields from a submitted `DECLARE` transaction are likewise untyped `serde_json::Value`: [5](#0-4) [6](#0-5) 

`compute_cairo_hinted_class_hash` is invoked from the deprecated-compiled-class hint implementation used by the Starknet OS during (re-)execution of declare transactions: [7](#0-6) 

Because `sort_json_value` recurses once per level of JSON nesting for both `Value::Object` and `Value::Array` variants with no depth or size cap, and `serde_json`'s own value parser has no default recursion-depth limit, an attacker-crafted, sufficiently deep JSON value embedded in the class's `abi`, `attributes`, `identifiers`, `hints`, or `reference_manager` fields will drive the recursive call stack past its limit, aborting the process with a stack overflow (a hard crash, not a catchable panic). This is analogous in root cause to CVE-2018-3280 (crash/hang triggered by processing untrusted structured/JSON-like input in a server-side component) — here the untrusted input is a declared contract class's opaque JSON sub-structures, processed without depth limiting.

### Impact Explanation
A stack overflow in Rust from unbounded recursion is not a normal panic that can be caught with `catch_unwind`; it aborts the process. If this code path executes inside the sequencer/OS component that computes hinted class hashes for Cairo0 declarations (needed to validate the class hash and produce block commitments), a single malicious `DECLARE` (v0/v1/v2 Cairo0-class) transaction can crash that component, disrupting block production / re-execution and potentially causing the sequencer to be unable to process the block, which maps to "network unable to confirm new transactions" for that path.

### Likelihood Explanation
Exploitability depends on whether Cairo0 (`deprecated_contract_class`) declarations are still accepted end-to-end by the running sequencer (gateway static config `block_declare`, and any deprecation of V0/V1/V2 declare types) and whether hinted-class-hash computation is invoked synchronously in a security-critical path (mempool admission, block building, or OS re-execution) rather than only in offline/test tooling. I was not able to fully confirm from the indexed code whether the sequencer's live gateway/mempool path currently computes `compute_cairo_hinted_class_hash` for incoming user declares versus only during Starknet OS re-execution/verification of already-included transactions (the call sites found are in `starknet_os`, which is exercised during OS proof/re-execution rather than gateway admission). This uncertainty affects whether the crash is reachable pre-block-inclusion (higher severity) or only during OS re-execution of an already-accepted block (still causes honest-node divergence/inability to progress, but requires the class to have already been declared/accepted).

### Recommendation
- Add an explicit recursion-depth limit (or convert `sort_json_value` to an iterative, explicit-stack algorithm) before processing any JSON value derived from a declared contract's `abi`/`attributes`/`identifiers`/`hints`/`reference_manager` fields.
- Enforce a maximum nesting depth (and overall size) on these `serde_json::Value` fields as part of `StatelessTransactionValidator`/declare validation, before the class is accepted into the mempool or handed to the hinted-class-hash computation.
- Consider running hinted-class-hash computation for untrusted classes with a bounded stack (similar to the existing `stack_size` guard used for Cairo-native execution) so that a stack overflow becomes a controlled failure rather than a process abort.

### Proof of Concept
1. Craft a Cairo0 `DECLARE` transaction whose `contract_class.abi` (or `program.attributes`/`identifiers`/`hints`/`reference_manager`) is a JSON value nested to a very large depth, e.g. `[[[[[...]]]]]` with on the order of 100,000+ levels (well within typical stack limits for a plain recursive function operating on heap-allocated `serde_json::Value` nodes).
2. Submit the transaction so that its class is accepted/declared and later processed by the Starknet OS (or any component that calls `compute_cairo_hinted_class_hash` on it), which calls `sort_json_value` on the parsed value: [8](#0-7) 
3. The recursive traversal in `sort_json_value` exhausts the call stack and aborts the process, rather than returning an error.

/// Recursively sorts all JSON objects by their keys.
/// This ensures deterministic serialization regardless of the `preserve_order` feature in
/// serde_json.
fn sort_json_value(value: serde_json::Value) -> serde_json::Value {
    match value {
        serde_json::Value::Object(map) => {
            let sorted: BTreeMap<String, serde_json::Value> =
                map.into_iter().map(|(k, v)| (k, sort_json_value(v))).collect();
            serde_json::Value::Object(sorted.into_iter().collect())
        }
        serde_json::Value::Array(arr) => {
            serde_json::Value::Array(arr.into_iter().map(sort_json_value).collect())
        }
        other => other,
    }
}

    contract_class: &ContractClass,

    // Serialize to Value, sort all objects by keys for deterministic output, then to bytes.
    // The sorting is necessary because serde_json with `preserve_order` feature enabled
    // maintains insertion order instead of sorting keys.
    // TODO(Meshi): Compute hinted hashes when loading serialized contracts from storage, before
    // deserializing, to avoid back-and-forth serde.
    let contract_value = serde_json::to_value(contract_class)?;
    let sorted_contract_value = sort_json_value(contract_value);
    let contract_definition_vec = serde_json::to_vec(&sorted_contract_value)?;
    let contract_definition: CairoContractDefinition<'_> =
        serde_json::from_slice(&contract_definition_vec)?;

    let mut string_buffer = vec![];

    let mut ser = serde_json::Serializer::with_formatter(&mut string_buffer, PythonJsonFormatter);
    contract_definition.serialize(&mut ser)?;
