## Title
Wallet Contract hard-codes the NEP-141 `storage_deposit` amount instead of reading the token's `storage_balance_bounds`, permanently blocking ERC-20-emulated transfers to unregistered recipients on any token that requires a higher minimum deposit - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

## Summary
The `near-wallet-contract` (the global contract deployed on every ETH-implicit account per NEP-518) emulates ERC-20 transfers by calling the target NEP-141 token's `storage_deposit` and `ft_transfer` in one promise batch. Instead of querying the token's actual `storage_balance_bounds`, the contract hard-codes the amount attached to `storage_deposit` as a compile-time constant, exactly analogous to the Yearn `YearnAdapter._protocolWithdraw` bug that hard-codes the `maxLoss` parameter instead of letting it be supplied by the caller.

## Finding Description
`inner_rlp_execute` handles `EthEmulationKind::ERC20Transfer` by first checking `storage_balance_of` on the token, and if the receiver is unregistered, `nep_141_storage_balance_callback` builds a promise batch that calls `storage_deposit` with a fixed constant amount before calling the transfer method: [1](#0-0) 

```
const NEP_141_STORAGE_DEPOSIT_AMOUNT: NearToken = NearToken::from_yoctonear(1_250 * MICRO_NEAR);
```

This constant is attached unconditionally to the `storage_deposit` call: [2](#0-1) 

The comment at the constant's definition acknowledges the trade-off explicitly: it is "the one used by the standard NEP-141 implementation, which essentially all tokens use" - i.e., the author already knows not all NEP-141 tokens use exactly this bound, but chose to hard-code it "to avoid the extra on-chain call to `storage_balance_bounds`" and to defend against malicious tokens with abnormally high bounds. No RLP-encoded Ethereum transaction field allows the signer/relayer to override this value; it is baked into the global contract code that is shared by every ETH-implicit account and cannot be customized per-account or per-token.

Because `storage_deposit` and the subsequent transfer call are both actions inside the same promise batch, a `Promise::new(token_id).function_call("storage_deposit", ..., NEP_141_STORAGE_DEPOSIT_AMOUNT, ...)` that fails a token's own `assert!` on `storage_balance_bounds.min` (or `.max`) causes the entire batch, including the intended `ft_transfer`/`ft_transfer_call`, to fail. `rlp_execute_callback` treats the whole thing as `PromiseResult::Failed` and only refunds the `caller_deposit` if present; it cannot retry with a different amount, and nothing in the contract state changes to work around the fixed constant on a future attempt: [3](#0-2) 

Since ETH-implicit accounts can never be deleted nor granted a full-access key, and the wallet contract's logic is not something an individual account or relayer can patch, this is a structural, permanent condition rather than a one-off failure: [4](#0-3) 

## Impact Explanation
For any NEP-141 token whose `storage_balance_bounds` does not match the hard-coded `1_250 * MICRO_NEAR`, every ERC-20-emulated transfer routed through an ETH-implicit account's Wallet Contract to a not-yet-registered receiver will fail forever with no possible remediation, since the amount is a fixed constant in immutable, globally-shared contract code rather than a caller-supplied or on-chain-derived parameter. This mirrors the Yearn finding's core defect class: omitting/hard-coding a safety parameter for an external call instead of deriving it dynamically or letting the caller supply it, causing the operation to permanently and unconditionally fail for legitimate use once the real-world value diverges from the hard-coded assumption.

## Likelihood Explanation
Reachable by any unprivileged RPC caller/relayer who submits an `rlp_execute` transaction (or via any relayer with a `FunctionCall` access key on the wallet contract) representing an ERC-20 transfer to an unregistered receiver on any NEP-141 token whose registration bound differs from the hard-coded value - no special privilege is required, and this is a normal, expected interaction pattern for ETH-implicit accounts using non-canonical or newer NEP-141 implementations (e.g., tokens with higher registration deposits due to longer keys, additional per-account metadata, or updated economics).

## Recommendation
Instead of hard-coding `NEP_141_STORAGE_DEPOSIT_AMOUNT`, query the target token's `storage_balance_bounds` (as is already done for `storage_balance_of`) before constructing the `storage_deposit` call, and attach the token-reported `min` amount (bounded by a sane upper cap to retain the anti-griefing protection the constant was originally meant to provide against malicious tokens with unreasonably high bounds).

## Proof of Concept
1. Deploy (or use) a NEP-141 token whose `storage_balance_bounds.min` is greater than `1_250 * MICRO_NEAR` (a legitimate, standards-compliant variation is possible, e.g. due to longer max account-id support or added per-account fields).
2. Have an ETH-implicit account (Wallet Contract) hold a balance of that token.
3. Submit (via any relayer) an RLP-encoded Ethereum transaction representing an ERC-20 `transfer` from the ETH-implicit account to a brand-new, unregistered `receiver_id`.
4. `nep_141_storage_balance_callback` builds the batch with the fixed `NEP_141_STORAGE_DEPOSIT_AMOUNT`; the token's `storage_deposit` implementation panics because the attached deposit is below its `min` bound.
5. The whole promise batch fails; `rlp_execute_callback` reports failure; the underlying `ft_transfer` never executes.
6. Repeat indefinitely — the outcome never changes because the constant cannot be adjusted by the transaction signer, relayer, or account owner, permanently blocking this class of transfer for that token via the Wallet Contract path.
