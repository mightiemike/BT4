### Title
Off-by-one boundary comparison in `JsonRpcApiUtil.parseEnergyFee` can misreport `gasPrice` for blocks at an energy-fee change boundary - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcApiUtil.java])

### Summary
`BlockResult`'s constructor computes the `energyFee` used to build `TransactionResult.gasPrice` for every transaction in a block by calling `wallet.getEnergyFee(blockCapsule.getTimeStamp())`, which is backed by `JsonRpcApiUtil.parseEnergyFee` [1](#0-0) . That helper walks the `energyPriceHistory` string from newest to oldest and selects a price using a strict `timestamp > time` comparison [2](#0-1) . If a block's timestamp is exactly equal to a recorded price-change boundary, this strict inequality skips the newly-effective price entry and falls back to the prior (stale) price, even though the actual VM execution/receipt pricing for that same block used the current `DynamicPropertiesStore` energy-fee value in effect at that timestamp.

### Finding Description
The reported `gasPrice` field returned by JSON-RPC APIs (via `TransactionResult`, constructed inside `BlockResult`'s `fullTx` branch) is derived from a *post-hoc reconstruction* of historical energy price using `parseEnergyFee`, rather than from the actual fee value that was applied at execution time and stored in the transaction's receipt [3](#0-2) . The reconstruction logic in `parseEnergyFee` uses `if (timestamp > time) { return price; }`, which is a strict inequality against a list of `time:price` entries presumably ordered chronologically [4](#0-3) . Any block whose timestamp exactly equals a recorded price-change boundary time will fail the `>` test for that entry and instead match an older, lower/higher entry further down the loop — returning the price that was in effect *before* the change rather than the one active *at* that timestamp. Since real fee application during transaction execution (in `VMActuator`/`ReceiptCapsule`, which consult `DynamicPropertiesStore` directly rather than this string-based history) is not gated by this same boundary logic, this creates a divergence between the actually-charged fee for a transaction and the fee value later reported through the JSON-RPC `gasPrice` field for that same block/transaction.

This is a reporting/observability path only — it does not affect consensus, actual TRX debited from accounts, or transaction execution, all of which occur independently in `VMActuator`/`ReceiptCapsule` before this JSON-RPC-side recomputation ever runs.

### Impact Explanation
External tooling, exchanges, or gas estimators relying on `eth_getBlockByNumber`/`eth_getTransactionReceipt`-style `gasPrice` fields for blocks at an energy-price-change boundary will see a stale (incorrect) price rather than the price actually charged, causing under- or over-estimation of the true TRX cost of a transaction. This is a data-integrity/observability issue in the JSON-RPC compatibility layer, not a consensus or fund-safety issue, since the underlying account debits and receipts are unaffected.

### Likelihood Explanation
The bug is deterministic and triggers whenever a block's timestamp exactly equals an energy-price-change timestamp recorded in `energyPriceHistory` — a boundary that is reachable naturally whenever a committee-controlled energy-fee proposal takes effect (attacker does not need any privilege to observe or be affected by it, only to query the JSON-RPC API for a block at that exact boundary). It is fully reproducible and does not depend on adversarial transaction timing beyond querying the affected block.

### Recommendation
Change the comparison in `parseEnergyFee` from `timestamp > time` to `timestamp >= time` (or otherwise align the boundary semantics with however `energyPriceHistory` entries are recorded relative to the block that first applies a new price), and add a unit test verifying that a block whose timestamp equals a price-history entry returns the same energyFee value that `TransactionTrace`/`ReceiptCapsule` actually applied for that block.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/services/jsonrpc/JsonRpcApiUtilTest.java
@Test
public void testParseEnergyFeeBoundary() {
  // history: fee=100 before t=1000, fee=200 from t=1000 onward
  String history = "0:100,1000:200";

  // Block timestamp exactly equal to the boundary should use the NEW fee (200),
  // matching what TransactionTrace/ReceiptCapsule actually charged for that block.
  long feeAtBoundary = JsonRpcApiUtil.parseEnergyFee(1000L, history);
  Assert.assertEquals(200L, feeAtBoundary); // FAILS today: returns 100L due to strict '>' 

  // Block timestamp just after boundary should also use 200
  long feeAfterBoundary = JsonRpcApiUtil.parseEnergyFee(1001L, history);
  Assert.assertEquals(200L, feeAfterBoundary); // passes today

  // Block timestamp just before boundary should use 100
  long feeBeforeBoundary = JsonRpcApiUtil.parseEnergyFee(999L, history);
  Assert.assertEquals(100L, feeBeforeBoundary); // passes today
}
```
Cross-check by constructing a `BlockCapsule` with `timestamp == 1000`, executing a transaction through `TransactionTrace`/`ReceiptCapsule` with the dynamic-store energy fee set to 200 at that instant, and asserting that `TransactionResult.gasPrice` computed via `BlockResult` equals the receipt's actual charged fee (200), not the stale value produced by today's `parseEnergyFee`.

  public static long parseEnergyFee(long timestamp, String energyPriceHistory) {
    String[] priceList = energyPriceHistory.split(",");

    for (int i = priceList.length - 1; i >= 0; i--) {
      String[] priceArray = priceList[i].split(":");
      long time = Long.parseLong(priceArray[0]);
      long price = Long.parseLong(priceArray[1]);
      if (timestamp > time) {
        return price;
      }
    }

    return -1;
  }
