### Title
Delegated `WithdrawFromGasKey` drains gas-key balance without the pending-transaction-queue accounting for it - ([File: runtime/runtime/src/action_validation.rs])

### Summary
The `PendingTransactionQueue`/`PendingTxSession` mechanism that gates SPICE chunk-transaction admission tracks `WithdrawFromGasKey` amounts only by scanning the **top-level actions** of a submitted transaction. A `WithdrawFromGasKey` action nested inside a `DelegateAction` (meta-transaction) is invisible to this scan, so the queue's gas-key balance commitment never reflects the drain, letting a signer withdraw more from a gas key than the concurrently-admitted, uncertified transaction set accounts for. The fix (`ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`) rejects such nested actions at validation time, but it only activates at protocol version 87 — above `STABLE_PROTOCOL_VERSION = 86` used by this tree — so on the currently deployed protocol version the vulnerable path is live.

### Finding Description
`validate_delegate_action` in `runtime/runtime/src/action_validation.rs:222-248` only rejects a nested `WithdrawFromGasKey` action when `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(current_protocol_version)` is true: [1](#0-0) 

The protocol-feature comment explains the root cause precisely: the SPICE pending-transaction queue's chunk scanner only looks at outer-transaction actions for `WithdrawFromGasKey`: [2](#0-1) 

This is confirmed in the queue implementation itself — `add_chunk_transactions` iterates `tx.actions()` (the outer transaction's action list) to find `Action::WithdrawFromGasKey` and add it to `pending_gas_key_costs`; a `WithdrawFromGasKey` wrapped inside `Action::Delegate(...)` is never inspected by this loop: [3](#0-2) 

The same blind spot exists in the per-session tracker `PendingTxSession::check_pending`, which likewise only scans `tx.transaction.actions()`: [4](#0-3) 

The protocol feature that closes this hole is gated to activate at protocol version 87: [5](#0-4) 

but the base of the tree is documented (in the cross-shard-congestion spec) as running with `STABLE_PROTOCOL_VERSION = 86`: [6](#0-5) 

The repo's own regression test demonstrates the exploit end-to-end pre-upgrade: a relayer submits a meta-transaction wrapping `WithdrawFromGasKey`, and the withdrawal is admitted and succeeds, draining the sender's gas key, before the fixing feature activates: [7](#0-6) 

The actual balance-moving logic executed once the receipt runs is `action_withdraw_from_gas_key`, which unconditionally subtracts from the gas key's `balance` and credits the account's spendable `amount`: [8](#0-7) 

Because the accounting gap is in `chain/client` (the pending transaction queue used for **transaction admission/chunk production**, not a validator-set/mocked/adversarial-only path) and the trigger is a single meta-transaction from a normal transaction signer, this is reachable exactly the class of actor allowed by the rules (an unprivileged transaction signer / meta-transaction sender).

### Impact Explanation
Concurrently-admitted, not-yet-certified transactions can double-spend a gas key's balance: the queue believes the gas key still has funds available (because it never subtracted the delegated withdrawal), and admits further gas-key-funded transactions on top of it. This is a state-transition/accounting-invariant violation reachable from an ordinary meta-transaction, producing unauthorized value movement (spendable balance credited beyond what the concurrent admission window actually accounts for) and can cause the runtime to accept transactions it should have rejected for insufficient gas-key balance, leading to inconsistent balance accounting across the uncertified chunk window.

### Likelihood Explanation
High reachability: any account holder with a gas key and any relayer willing to submit a meta-transaction can trigger this by simply wrapping `WithdrawFromGasKey` inside a `DelegateAction`; no special privileges, validator status, or adversarial network position are required. The nearcore engineers themselves flagged and are actively closing this exact hole via `RejectWithdrawFromGasKeyInDelegate`, and their own test (`test_reject_delegated_gas_key_withdraw_protocol_upgrade`) explicitly demonstrates the vulnerable behavior occurs "before the upgrade."

### Recommendation
Backport/accelerate activation of `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` (or otherwise reject `WithdrawFromGasKey` nested in `DelegateAction` unconditionally at `validate_delegate_action`) rather than gating it to protocol version 87, since the exploitable window exists at the current stable protocol version 86. Alternatively, fix the root cause by making `PendingTransactionQueue::add_chunk_transactions` and `PendingTxSession::check_pending` recursively scan actions inside `Action::Delegate` payloads for `WithdrawFromGasKey`, so the balance commitment is accurate regardless of nesting.

### Proof of Concept
The existing test in the repository is a full PoC: [9](#0-8) 
It builds a `DelegateAction` whose inner action is `WithdrawFromGasKey`, signs it with the sender's regular access key, wraps it as `Action::Delegate` in an outer transaction sent via a relayer, and shows that pre-upgrade (protocol version < 87) the transaction succeeds and drains the gas key balance while the pending-transaction-queue's top-level-only scan never accounts for it: [7](#0-6)
