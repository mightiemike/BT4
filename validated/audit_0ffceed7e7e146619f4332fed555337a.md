### Title
Attacker-controlled auth-mechanism selection allows JWT-to-allowlist downgrade via empty `req.Auth` - ([File: core/capabilities/vault/authorizer.go])

### Summary
`authorizer.authorizeRequest` selects between `JWTBasedAuth` and `AllowListBasedAuth` purely based on whether the attacker-supplied `req.Auth` field is empty, with no server-side policy pinning the DON to JWT-only when Auth0 is configured. This lets any unprivileged caller strip the `Auth` field from a JSON-RPC vault request to force evaluation through the weaker allowlist path instead of the JWT/tenant-scoped path.

### Finding Description
`(a *authorizer) authorizeRequest` at [1](#0-0)  branches solely on `req.Auth == ""`, routing to `authorizeAllowListBasedAuth` when empty and to `authorizeJWTBasedAuth` otherwise. Both `NewGatewayHandler` [2](#0-1)  and `NewHandler` in the gateway vault handler [3](#0-2)  construct the `authorizer` with **both** `allowListBasedAuth` and `jwtBasedAuth` set whenever `cfg.Auth0`/`auth0` is configured, meaning the allowlist path remains live and reachable even on a DON that intends to enforce JWT-based tenant/org scoping. `req.Auth` is a plain field on the attacker-supplied JSON-RPC envelope with no cryptographic binding forcing its presence, so an attacker can simply omit it (or set it to `""`) to route around JWT verification. If `NewAllowListBasedAuth`'s workflow-registry-syncer-backed digest matching can be satisfied with a stale or foreign allowlisted digest (e.g., an old workflow's allowlist entry that hasn't been revoked, or one belonging to a different, unrelated but still-allowlisted workflow), the request is authorized under weaker, non-tenant-scoped semantics — bypassing the tenant/org isolation that JWT auth is meant to enforce. Existing checks (`replayGuard.CheckAndRecord`, `validateSecretOwnersMatchAuthorized`) operate downstream of this selection and do not re-validate that the selected auth mechanism was the one mandated by DON configuration; they only check digest replay and owner-string matching within whichever mechanism was already chosen.

### Impact Explanation
This is an authentication-mechanism downgrade / auth bypass: a DON operator who intentionally configures Auth0 to require per-tenant JWT scoping still exposes the legacy allowlist path to any caller who omits `Auth`. If a stale/foreign allowlist digest exists (e.g., not yet cleaned up on the workflow registry), an unprivileged attacker can gain vault access (create/update/delete/list secrets) bound to that allowlisted `workflowOwner` without ever presenting a valid JWT for the correct org/tenant — a privilege escalation into the weaker auth surface, matching a Chainlink bounty "authentication bypass" / "unauthorized secret access" class.

### Likelihood Explanation
Preconditions: a DON with `cfg.Auth0` configured (intending JWT-only enforcement) that also still wires up `allowListBasedAuth` (which, per the current constructors, is always true — both paths are always active together), and at least one allowlisted digest still resolvable by `workflowRegistrySyncer` (e.g., stale/legacy entries, or a foreign workflow's entry). The attacker only needs to control the JSON-RPC request body sent to the gateway (an ordinary, unauthenticated capability compared to a legitimate JWT holder) and set `Auth: ""`. This is fully reachable from any external caller able to reach the gateway's `MethodSecretsCreate`/etc. endpoints — no operator/admin privilege or key leakage required. The comment in the code explicitly documents this as intentional ("Existing clients do not populate the auth field yet"), confirming the fallback is by design rather than incidental, which increases confidence this is exploitable today wherever both authorizers coexist.

### Recommendation
Make the auth mechanism selection server-controlled, not attacker-controlled: thread the DON's `Auth0`/JWT-required configuration into the `authorizer` struct, and when JWT is configured/required, reject (rather than fall back) any request with empty `req.Auth`. Only allow the allowlist path when the DON is explicitly configured without Auth0 (mutually exclusive modes), or introduce an explicit `RequireJWT bool` flag set from `cfg.Auth0 != nil` that causes `authorizeRequest` to return an error like `"JWT auth required for this DON"` when `req.Auth == ""`.

### Proof of Concept
Unit test in `core/capabilities/vault/authorizer_test.go`:
1. Construct `allowListBasedAuth` mock that returns a valid `AuthResult` for a stale/foreign `workflowOwner`/digest (simulating a workflow-registry-syncer entry that hasn't been revoked).
2. Construct `jwtBasedAuth` mock (never expected to be called in the exploit case).
3. Build `a := vault.NewAuthorizer(allowListBasedAuth, jwtBasedAuth, logger.TestLogger(t))` — mirroring production wiring in `gw_handler.go`/`handler.go` where both are non-nil when Auth0 is configured.
4. Call `a.AuthorizeRequest(ctx, req)` with `req.Auth == ""` and `req.Method == vaulttypes.MethodSecretsCreate`.
5. Current behavior: `authResult` is returned successfully via the allowlist path (`allowListBasedAuth.AuthorizeRequest` invoked), asserting the vulnerability — `jwtBasedAuth.AssertNotCalled(...)` succeeds and `require.NoError(t, err)` passes, when it should instead be rejected with an error such as `"JWT auth required"` once a DON-level `RequireJWT`/Auth0-configured flag is enforced.

func (a *authorizer) authorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	// Requests without req.Auth continue using the allowlist-based path for backwards compatibility.
	// Existing clients do not populate the auth field yet, so treating an empty value as JWT would break them.
	if req.Auth == "" {
		return a.authorizeAllowListBasedAuth(ctx, req)
	}
	return a.authorizeJWTBasedAuth(ctx, req)
}
