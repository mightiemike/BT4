### Title
Panic-on-`.unwrap()` in `DelayedReceiptQueueWrapper::receipt_filter_fn` when a stale `GlobalContractDistribution` receipt's `target_shard` cannot be resolved across resharding generations - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs` calls `.unwrap()` on `Receipt::receiver_shard_id(&shard_layout)`, which for `GlobalContractDistribution` receipts returns `Err(EpochError::ShardingError(...))` whenever `target_shard` can no longer be resolved to a descendant in the current shard layout. This mirrors the CVE-2019-12312 pattern (a bogus/late message in an otherwise-normal state sequence triggers an unhandled `NULL`/panic path deep in daemon logic instead of a normal error return), except here the "daemon" is the NEAR runtime state-transition function shared deterministically by all validators for a shard.

### Finding Description
`Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437-466`) computes the target shard for a receipt. For ordinary receipts it uses `account_id_to_shard_id`, which cannot fail. But for `ReceiptEnum::GlobalContractDistribution`, if the stored `target_shard` is not in the current shard layout, it calls `shard_layout.resolve_to_current_shard(target_shard)`; if that returns `None` (i.e., the shard is not a descendant reachable in the split history retained by the current layout), it returns `Err(EpochError::ShardingError(...))` instead of panicking.

That `Result` is then consumed unsafely in `congestion_control.rs`: [1](#0-0) 

Both call sites that use `receipt_filter_fn` — `pop()` (delayed-receipt-queue draining during every chunk apply) and `peek_iter()` — will propagate this `.unwrap()` panic straight out of `Runtime::apply`'s delayed-receipt processing path, i.e. inside the deterministic state-transition function executed by every validator applying that shard's chunk.

A test explicitly documents this exact vulnerability shape and reproduces the setup needed to trigger it (deploy a global contract targeting a shard, then force two sequential dynamic-resharding splits while the `GlobalContractDistribution` receipt sits in the delayed-receipt queue long enough that its `target_shard` becomes unreachable from the current layout after two resharding generations): [2](#0-1) 

The reachable trigger is entirely attacker-controlled from a normal transaction sender's perspective: any account can submit a `DeployGlobalContract` action (creating a `GlobalContractDistribution` receipt with a `target_shard`), then keep the receiving shard congested (e.g. via `burn_gas_raw` calls) so the receipt stays queued in the delayed-receipt queue across multiple resharding events. When the queue is finally drained, `receipt_filter_fn`'s `.unwrap()` panics.

### Impact Explanation
A panic inside `Runtime::apply`/`process_receipts` is not a graceful error — it aborts the validator/chunk-producer process applying that chunk. Because this is the deterministic state-transition function, every honest validator tracking the affected shard hits the identical panic when draining the delayed queue at the same point, producing a **transaction-triggered halt** of chunk production for that shard (and potentially the whole chain if enough validators/chunk producers for the shard crash simultaneously). This satisfies the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Triggering requires (a) submitting a `DeployGlobalContract` transaction targeting a specific shard, and (b) causing/waiting for at least two dynamic-resharding splits of that shard's lineage while the resulting `GlobalContractDistribution` receipt remains undelivered (e.g., by keeping the target shard congested with gas-heavy transactions so the receipt stays in the delayed-receipt queue). Both actions are available to any unprivileged transaction sender/contract deployer; the only external dependency is that dynamic resharding (`DynamicResharding`, protocol feature v85, enabled at stable v86 per the network's `EpochConfigStore`) actually occurs at least twice for the target shard's lineage before the receipt drains — a condition the network reaches naturally under `ShardLayoutConfig::Dynamic`, not something requiring malicious validators or operator collusion.

### Recommendation
Handle the `Err` case in `receipt_filter_fn` instead of `.unwrap()`ing: propagate a `RuntimeError`/`StorageError` (or equivalent recoverable error) from `pop()`/`peek_iter()` so the apply function can fail cleanly (and, more importantly, fix the underlying gap so `resolve_to_current_shard` can always resolve a `target_shard` regardless of how many resharding generations have elapsed, e.g. by retaining full split-ancestry chains in `ShardLayout::V3` or by re-targeting/rewriting `GlobalContractDistribution` receipts at each resharding boundary rather than only patching `receiver_shard_id` lookups after the fact).

### Proof of Concept
1. Deploy a global contract from account `A` whose account maps to shard `S_A` in the base layout — this produces a `GlobalContractDistribution` receipt with `target_shard = S_A`.
2. Configure/force dynamic resharding so `S_A`'s lineage is split twice (two sequential `force_split_shards` boundary events), while continuously submitting compute-heavy transactions (e.g. `burn_gas_raw`) to the shard so the distribution receipt is pushed into and remains in the delayed-receipt queue across both resharding epochs.
3. Once both splits complete, stop saturating the shard and let the delayed queue drain. On the drain step, `DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn`, which calls `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()`; because `target_shard` is now two generations removed from the current layout and unreachable via `resolve_to_current_shard`, the `Err(EpochError::ShardingError(..))` causes the `.unwrap()` to panic, crashing chunk application for that shard.
This exact scenario, including the two-resharding-generation staleness condition, is encoded in the existing regression test: [3](#0-2)

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
