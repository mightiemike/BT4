### Title
Unbounded per-pubkey secondary-index scan causes disproportionate CPU/gas cost in a single call - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::index_scan_accounts` iterates sequentially over **every pubkey** returned by a secondary index (`ProgramId`, `SplTokenMint`, `SplTokenOwner`) and performs a full `do_load` (index lookup + storage read) for each one, one at a time, with no bound on the number of entries processed. This mirrors the reported Incentives.sol pattern: a function that loops over an externally-influenced, unbounded array, where cost grows linearly (or worse) with array size and only an after-the-fact, byte-based limit exists (not a count-based one), so the loop itself can still be forced to walk an arbitrarily large number of entries in a single call.

### Finding Description
`index_scan_accounts` builds its iteration set from `self.accounts_index.get_index_key_pubkeys(&index_key)` and then loops: [1](#0-0) 

Each iteration performs an index lookup and a full account load (`do_load`) before the caller-supplied `scan_func` even runs. The only escape hatch is `config.is_aborted()`, which is driven by an optional **byte** size limit accumulated from already-loaded accounts: [2](#0-1) 

Critically, the abort check only fires *after* an account has passed the caller's filter and been loaded and counted — there is no bound on the number of pubkeys registered under a single secondary-index key (`ProgramId`, `SplTokenMint`, `SplTokenOwner`) that must be walked and loaded before that happens. `SecondaryIndex::get` simply returns the full `Vec<Pubkey>` for the key with no cap: [3](#0-2) 

This is invoked from bank-level scan APIs used by RPC (`get_filtered_indexed_accounts`, `get_filtered_program_accounts` for `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByMint`) as well as internal supply computation (`calculate_non_circulating_supply`, which unconditionally scans all `ProgramId` = stake-program accounts once per epoch/scan): [4](#0-3) [5](#0-4) [6](#0-5) 

Because any account can be assigned any owner program and any SPL-token-like account can point at an arbitrary "mint" pubkey, an unprivileged user can create a large number of accounts (e.g., under a single program ID or a single fabricated "mint" address) purely by paying normal account-creation rent/fees, growing the secondary-index bucket for that one key without bound (functionally identical to the reported "allTokens array" growing unboundedly). A single subsequent index-key scan for that key must sequentially load every one of those accounts before the byte-limit abort can even trigger, producing CPU cost disproportionate to the useful work performed in one call — the same bug class as the reported finding, just measured in CPU time on a single node rather than gas on a single tx.

### Impact Explanation
This causes disproportionate CPU/storage-read cost for a single RPC/internal scan call, tying up a validator/RPC node thread proportional to attacker-controlled index-key population size, which is explicitly one of the accepted impact categories (disproportionate storage and CPU cost). Because `calculate_non_circulating_supply` is also invoked internally (not purely on RPC request), pathological growth of the `ProgramId(stake::program::id())` bucket by an unprivileged actor also degrades internal, non-RPC codepaths that use the same secondary-index scan machinery in `accounts_db.rs`/`accounts.rs`, which is in-scope AccountsDB index code.

### Likelihood Explanation
Any unprivileged user can create accounts under an arbitrary owner or with data mimicking an SPL token account referencing an arbitrary "mint" pubkey; each such account adds an entry to the relevant secondary index (`ProgramId`/`SplTokenMint`/`SplTokenOwner`) with no per-key cap enforced anywhere in `SecondaryIndex`/`accounts_index.rs`. Growing one key's bucket to a very large size requires no special privilege — only ordinary account creation, matching the "no upper bound on allTokens-like array" pattern from the report.

### Recommendation
Enforce a count-based (not just byte-based) upper bound on the number of pubkeys pulled from `get_index_key_pubkeys` and processed per `index_scan_accounts` invocation, aborting the scan (with a clear `ScanError`) once the count limit is exceeded, similar to the existing `byte_limit_for_scan` mechanism, and consider chunked/parallel loading with early-exit checks performed *before* the expensive `do_load` rather than only after.

### Proof of Concept
1. As an unprivileged user, create N accounts (e.g., N = several hundred thousand) that are either (a) owned by the same arbitrary `program_id`, or (b) have SPL-token-account-shaped data referencing the same fabricated "mint" pubkey, so they populate a single bucket of the `ProgramId`/`SplTokenMint` secondary index (see `SecondaryIndex::get` at `accounts-db/src/accounts_index/secondary.rs:252-258`).
2. Trigger one call into `index_scan_accounts` for that index key (e.g., `getProgramAccounts(program_id)` with the `ProgramId` secondary index enabled, or `getTokenAccountsByMint`), or wait for `calculate_non_circulating_supply` to run internally against the `stake::program::id()` bucket.
3. Observe that `accounts-db/src/accounts_db.rs:3398-3410` sequentially performs a `do_load` for every one of the N pubkeys before the byte-based abort in `accounts-db/src/accounts.rs:367-432` can trigger, causing CPU time and I/O proportional to N in a single call/invocation.

    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }

    pub async fn get_filtered_indexed_accounts(
        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;
        if sort_results {
            // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
            accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
        }
        Ok(accounts)
    }
