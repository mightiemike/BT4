### Title
Wall-clock deadline in Nakamoto block-proposal validation causes signer nodes to disagree on the same block's validity - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
`NakamotoBlockProposal::validate_nakamoto_block` (the handler behind the `/v3/block_proposal` signer RPC endpoint) enforces the block validation budget using a real wall-clock `Instant` deadline rather than a deterministic, consensus-derived cost limit. A single crafted block whose transaction execution time straddles this wall-clock boundary can be judged valid on faster/idle signer nodes and invalid ("Block validation timed out") on slower/loaded signer nodes, breaking the equality that all honest signers evaluating the same block proposal must reach the same accept/reject verdict.

### Finding Description
`validate_nakamoto_block` computes `let block_deadline = Instant::now() + Duration::from_secs(timeout_secs);` [1](#0-0)  and then, for every transaction in the block, checks `if Instant::now() >= block_deadline` before attempting to mine/apply it, rejecting the entire block with `ValidateRejectCode::InvalidBlock` / "Block validation timed out before tx {i} could be processed" if the wall-clock deadline has passed [2](#0-1) .

This is the same bug class as the referenced report: an operation whose termination/outcome depends on an attacker-influenceable, unbounded-cost loop (iterating and executing every tx in the block) combined with a resource ceiling that is *not* part of the deterministic protocol rules (a raw system clock `Instant`, which varies by CPU speed, load, I/O contention, and per-operator config value `timeout_secs`/`max_tx_execution_time_secs`), instead of a shared, reproducible cost metric (like the Clarity `ExecutionCost` budget used elsewhere in mining, e.g. `try_mine_tx_with_len`'s `CostOverflowError` handling [3](#0-2) ).

Before the attacker's block: all signers, given the same block, deterministically reach the same accept/reject verdict because validation is driven only by the Clarity cost budget.
After the attacker's block: a miner (a single, unprivileged actor - no majority needed) submits a block proposal containing transactions engineered to execute for a duration close to the configured timeout. Because `timeout_secs`/`max_tx_execution_time_secs` are local operator-configurable values (`stackslib/src/config/mod.rs`) and the check uses real elapsed time rather than a deterministic cost counter, different signers (different hardware, different concurrent load, different configured timeouts) can independently reach opposite conclusions on the very same block bytes — some sign it, some reject it via `BlockValidateRejectReason`.

### Impact Explanation
This breaks the required equality "a validation verdict two nodes disagree on," which the analog rules classify as High severity. A minority-triggerable divergence in signer verdicts on an identical block proposal can prevent the signer set from reaching the weighted threshold in a timely way, or cause a subset of signers to reject a block that the majority accepts (or vice versa), producing temporary tip/consensus disagreement among signers and potentially stalling block production or forcing miner/signer retries, without requiring any majority collusion or privileged access.

### Likelihood Explanation
Any block proposer (a normal miner) can trigger this by crafting transactions whose execution time is engineered to sit near the `block_deadline`/`per_tx_max_execution_time` boundary; no special privileges or majority coordination are required, only knowledge/reasonable assumption of typical signer node timeout configuration and performance characteristics, which is realistic since `timeout_secs` and `max_tx_execution_time_secs` are operator-configured but generally align with recommended/default values across the network.

### Recommendation
Replace or gate the wall-clock `Instant`-based abort in `validate_nakamoto_block` with a deterministic, protocol-defined resource metric (the same `ExecutionCost`/read-write budget already used for mining and Clarity cost accounting) so that all signer nodes evaluating an identical block reach an identical, reproducible verdict regardless of local hardware speed or transient load. If a wall-clock safety valve must remain (e.g., to bound RPC latency), it should only be used to abort validation locally without asserting `InvalidBlock`/rejecting the block on protocol grounds — it must not feed into the recorded verdict that is broadcast/signed.

### Proof of Concept
1. A miner crafts a Nakamoto block whose transactions collectively take just under the default `block_deadline` (`timeout_secs`) on a "fast" node but just over it on a "slow"/busy node (e.g., by including a transaction near the per-tx analysis/execution budget, `per_tx_max_analysis_time`/`per_tx_max_execution_time`, that a slower validator machine or one under concurrent proposal-validation load will not finish before `Instant::now() >= block_deadline`).
2. The miner submits this identical block proposal to the full signer set via `/v3/block_proposal`.
3. Fast/idle signers process all `self.block.txs` within `timeout_secs` and return a normal accept/reject verdict based on tx content.
4. Slow/loaded signers hit `Instant::now() >= block_deadline` mid-loop and reject with `"Block validation timed out before tx {i} could be processed"` regardless of whether the remaining transactions were otherwise valid [4](#0-3) .
5. The signer set now holds two different verdicts for the same block bytes, which can prevent reaching the weighted `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` computed in `compute_voting_weight_threshold` [5](#0-4)  in a timely manner, or cause inconsistent signer behavior/tip disagreement across the network.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
