### Title
Unbounded per-account growth of `zero_lamport_accounts_to_purge_after_full_snapshot` causes disproportionate CPU cost in background `clean_accounts` - (File: accounts-db/src/accounts_db.rs)

### Summary
`AccountsDb` maintains a `DashSet<(Slot, Pubkey)>` named `zero_lamport_accounts_to_purge_after_full_snapshot` that accumulates one entry for every zero-lamport account whose slot is newer than the latest full snapshot slot [1](#0-0) . This set is only drained in a single `retain()` pass inside `construct_candidate_clean_keys`, and only when a full snapshot has just advanced [2](#0-1) . Between full snapshots (which occur periodically, e.g. every `--full-snapshot-interval-slots`), any number of zero-lamport accounts created network-wide are unconditionally inserted into this set with no cap [3](#0-2) .

### Finding Description
Every time `filter_zero_lamport_clean_for_incremental_snapshots` determines that a zero-lamport account's slot is newer than `latest_full_snapshot_slot`, it inserts `(slot, pubkey)` into `zero_lamport_accounts_to_purge_after_full_snapshot` and defers purging it [3](#0-2) . This insertion path is reachable by any user simply by transferring an account's balance to zero — a trivially cheap, ordinary operation, analogous to the "miniscule LP deposit" in the reported bug that cheaply grew `usersBridges`.

Unlike the per-transaction runtime work (which is metered by the compute budget), the `clean_accounts` background pass that eventually iterates this set runs in `AccountsBackgroundService`, entirely outside of any per-transaction compute-unit limit [4](#0-3) . Between full snapshots, the set is not bounded, retried, or capped — it simply grows with the count of matching zero-lamport accounts across the whole cluster's traffic (an attacker can dominate this by continuously zeroing large numbers of cheaply created accounts). Once a full snapshot advances, `construct_candidate_clean_keys` performs a single `retain()` closure invocation over the *entire* accumulated set in one call, calling `insert_candidate` for every matching entry [5](#0-4) , directly mirroring the `distributeDividends` unbounded `for`-loop pattern: cheap, attacker-controllable list growth feeding a single unbounded iteration in code that all validators must execute to keep processing state.

This is the closest reachable Agave analog to the reported class within the permitted scope (AccountsDB storage/index, clean/shrink, and snapshot generation), since it is an actual unbounded collection populated by attacker-cheap account state changes and consumed by a single non-batched loop in a background service not gated by per-transaction compute metering.

### Impact Explanation
If the set grows very large between full snapshots (e.g., due to sustained spam of zero-lamport account creation across many pubkeys), the deferred `retain()`/`insert_candidate` pass that runs once the next full snapshot advances performs disproportionately large CPU and memory work in one background-service iteration. Because `AccountsBackgroundService`'s loop also performs `shrink_candidate_slots`, `clean_accounts`, and eventually snapshot packaging in the same loop iteration [6](#0-5) , a spike here can delay clean/shrink/snapshot cadence, causing disproportionate storage and CPU cost relative to the attacker's cost, and risk falling behind on snapshot generation cadence for the validator.

### Likelihood Explanation
Likelihood is moderate: it requires (1) sustained creation and zeroing of many accounts by an attacker across the interval between two full snapshots, and (2) the network-wide full-snapshot interval to be long enough for accumulation to matter. Solana's existing rent/fee-per-transaction model raises the cost floor compared to the original EVM analog (a single cheap deposit), somewhat limiting the practicality of the attack, but there is no explicit cap, batching, or incremental-processing mechanism in this code path to bound the growth or the size of the single retain-and-insert pass.

### Recommendation
Bound and/or batch the deferred zero-lamport purge set: process `zero_lamport_accounts_to_purge_after_full_snapshot` incrementally across multiple `clean_accounts` calls (e.g., a fixed number of entries per pass) rather than draining the whole set in a single `retain()` when a full snapshot advances, and consider capping/metrics-alerting on the set's size so operators can detect abnormal growth. This mirrors the "process in smaller batches" and "pointsPerShare"-style mitigation recommended in the original report, adapted to Agave's clean/shrink pipeline.

### Proof of Concept
Not concretely reproducible from static code review alone — a full PoC would require running a local validator/test cluster, spamming account creation-and-zeroing across many pubkeys spread over multiple slots prior to a full snapshot, then measuring the CPU/time spent in `construct_candidate_clean_keys`'s `zero_lamport_accounts_to_purge_after_full_snapshot.retain()` call once the next full snapshot advances [7](#0-6) . This would require live execution which is outside the scope of static analysis; the impact is inferred from the unbounded, unbatched nature of the collection and its single-pass consumption.
