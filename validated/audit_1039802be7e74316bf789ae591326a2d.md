### Title
Unbounded growth of per-shop session-id index in `KVSessionStorage` enables denial-of-service of the OAuth/session-lookup path - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession` appends the session id to a shop-keyed index array on every call without checking whether that id is already present, unlike the equivalent Redis adapter which explicitly de-duplicates before appending. Because `storeSession` is invoked on every session persistence event (including routine online-session refreshes and repeated OAuth/token-exchange flows that any unprivileged app user can trigger), the per-shop id array can be made to grow without bound. This array is later iterated in full by `findSessionsByShop`, which is used by session/installation-lookup logic in the auth flow, so an attacker can force ever-growing, unbounded work on that lookup path — the same "attacker cheaply grows a queue that an honest actor/handler must fully drain" pattern described in the reference report.

### Finding Description
`addShopIds` reads the existing array of session ids for a shop and blindly concatenates the new id(s), with no `includes`/dedup check: [1](#0-0) 

This is called unconditionally from `storeSession` on every session write: [2](#0-1) 

By contrast, the Redis adapter's equivalent function guards against duplicate entries before pushing: [3](#0-2) 

The KV adapter's `findSessionsByShop` then reads and fully iterates that unbounded array, issuing one KV read per stored id via `Promise.all`: [4](#0-3) 

`findSessionsByShop` is a required part of the session-storage contract and is consumed directly by installation-state checks in the auth flow (`AppInstallations.includes`/`delete`), which are used to decide whether a shop needs to re-run OAuth: [5](#0-4) 

Because `storeSession` (and thus `addShopIds`) fires on every session persistence — including repeated online-session creation/refresh during normal (unprivileged) app usage or repeated OAuth callbacks for the same shop/user — a single actor can drive the shop's id array to an arbitrarily large size at negligible cost (each KV `put` only appends a short string). Every subsequent `findSessionsByShop` call for that shop then has to perform a proportionally large number of KV reads, degrading or effectively denying the installation-check/session-lookup path for that shop — directly analogous to the sequential-queue griefing pattern in the report, where cheap repeated enqueue operations force expensive drain operations on a shared, unbounded, sequentially-processed list.

### Impact Explanation
This is a resource-exhaustion / griefing vector rather than a funds-theft or auth-bypass bug: it does not grant unauthorized access, but it can make the shop's session lookup (and therefore installation-status checks tied to the OAuth begin/callback flow) arbitrarily slow or costly, potentially causing timeouts or increased KV read costs for that shop, similar in spirit to the "Theft of gas / unbounded resource consumption" Medium-severity classification given to the original finding.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that use `@shopify/shopify-app-session-storage-kv`: `storeSession` is called by the library's normal session-persistence flow on installs, re-installs, and online-session issuance/refresh, none of which require elevated privileges — any user who can complete the OAuth/token-exchange flow repeatedly (a normal, unprivileged action) can grow the array. The `id` uniqueness of repeated calls is what triggers duplication; if the online/offline session id used for a given shop/user is stable across repeated logins, each re-login appends another duplicate rather than being deduped as it would be in the Redis adapter.

### Recommendation
In `KVSessionStorage.addShopIds` (and the corresponding `removeShopIds` cleanup path), de-duplicate before writing, mirroring the Redis adapter's `includes` check, e.g. only push ids not already present in `shopIds`, and consider capping/pruning stale entries during `findSessionsByShop`/`storeSession` to bound the list size.

### Proof of Concept
1. Configure an app to use `KVSessionStorage`.
2. Repeatedly complete the OAuth/token-exchange flow for the same shop as an ordinary (unprivileged) user/session, each time calling `storeSession` with the same session `id`.
3. Observe (via inspection or instrumentation) that `shopify_sessions:<shop>` (the shop key) accumulates duplicate copies of the same id indefinitely, since `addShopIds` never checks for existing membership: [1](#0-0) 
4. Call `findSessionsByShop(shop)` (or trigger `AppInstallations.includes`/`delete` during the auth flow) and observe the number of KV reads/Promise.all fan-out grows linearly with the number of times `storeSession` was called, not with the number of distinct sessions — demonstrating the unbounded-queue growth and consequent handler cost inflation.

      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),

  }
