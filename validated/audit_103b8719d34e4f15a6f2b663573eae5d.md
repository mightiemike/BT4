### Title
Attacker-controlled voucher/tree structure in `createShieldedTransaction` produces a variable-length Merkle path passed unchecked into `librustzcashSaplingSpendProof`, risking native out-of-bounds access - ([File: framework/src/main/java/org/tron/core/zen/ZenTransactionBuilder.java])

### Summary
The RPC-exposed `Wallet.createShieldedTransaction`/`createShieldedTransactionWithoutSpendAuthSig` build an `IncrementalMerkleVoucherContainer` directly from a client-supplied `IncrementalMerkleVoucher` protobuf (`SpendNote.getVoucher()`), with no structural validation of the tree/parents list. `ZenTransactionBuilder.generateSpendProof` then calls `spend.voucher.path().encode()` and passes the resulting byte array as `voucherPath` straight into the native FFI call `librustzcashSaplingSpendProof`, which expects a fixed-size buffer for the Merkle authentication path.

### Finding Description
`Wallet.createShieldedTransaction` (framework/src/main/java/org/tron/core/Wallet.java:2347-2354) constructs the voucher this way:
```
IncrementalMerkleVoucherContainer voucherContainer =
    new IncrementalMerkleVoucherCapsule(spendNote.getVoucher()).toMerkleVoucherContainer();
builder.addSpend(expsk, baseNote, spendNote.getAlpha().toByteArray(),
    spendNote.getVoucher().getRt().toByteArray(), voucherContainer);
```
`spendNote.getVoucher()` is taken directly from the client's `PrivateParameters` request with no bound checks. The only pre-validation performed is `checkCmValid` (framework/src/main/java/org/tron/core/Wallet.java:2225-2255), which only checks the count and non-negativity of spend/receive notes — it does **not** validate the shape of the voucher's underlying `IncrementalMerkleTree` (`left`/`right`/`parents`).

`IncrementalMerkleTreeContainer.wfcheck()` (chainbase/src/main/java/org/tron/common/zksnark/IncrementalMerkleTreeContainer.java:38-59), which is the only method that enforces `parents.size() < DEPTH`, is never invoked in this build path — it's only referenced from `ShieldedTransferActuator` and tests, not from `Wallet.createShieldedTransaction` / `ZenTransactionBuilder.generateSpendProof`.

When `spend.voucher.path()` is called (`IncrementalMerkleVoucherContainer.path()` → `IncrementalMerkleTreeContainer.path(Deque)`, chainbase/.../IncrementalMerkleTreeContainer.java:234-276), the authentication path is built by iterating directly over `treeCapsule.getParents()`:
```java
int d = 1;
for (PedersenHash parent : treeCapsule.getParents()) {
  ...
  d++;
}
while (d < DEPTH) { ... d++; }
```
Because `getParents()` reflects the attacker-supplied repeated protobuf field with no cap, an attacker can supply an oversized (or undersized/malformed) `parents` list, producing a `path`/`index` list whose length differs from the expected fixed `DEPTH` (32). `MerklePath.encode()` (chainbase/.../MerklePath.java:77-106) serializes whatever length it is handed, with no fixed-size assertion beyond an `assert` (disabled by default in production JVMs) that `authenticationPath.size() == index.size()`.

This variable-length byte array is then passed as `voucherPath` to `SpendProofParams` and ultimately to the native `librustzcashSaplingSpendProof` (chainbase/src/main/java/org/tron/common/zksnark/JLibrustzcash.java:123-128), which is called via JNA into native Rust/C code that (per the test fixture `LibrustzcashTest.benchmarkCreateSpend`) expects a specific fixed-size buffer (~1065 bytes for a depth-32 Merkle path). A shorter or longer buffer than expected can cause the native routine to read out of bounds of the Java-allocated byte array memory.

### Impact Explanation
If the native FFI reads past the bounds of the supplied `voucherPath` buffer based on a hardcoded expected length while the Java array is smaller/larger, this is a memory-safety violation in native code invoked from the full node process, potentially causing a node crash (DoS) or, depending on the JNA/native memory layout, an out-of-bounds read that could leak adjacent heap data or destabilize the node process. This matches "DoS via RPC-API" / potential node crash impact classes.

### Likelihood Explanation
This is reachable by any unprivileged caller of the `createShieldedTransaction` / `createShieldedTransactionWithoutSpendAuthSig` gRPC/HTTP RPCs (gated only by `checkAllowShieldedTransactionApi()`, a feature flag, not an authorization check). No signed/broadcast transaction, no special account, no fees are required to reach `generateSpendProof` — it executes during **node-side transaction construction before signing/broadcast**. The attacker only needs to supply a crafted `voucher` protobuf field (`IncrementalMerkleVoucher`) with a manipulated `parents` list length. This makes exploitation straightforward and repeatable, limited only by whatever length/size restrictions gRPC/protobuf message parsing imposes (which are typically large, e.g., megabyte-scale).

### Recommendation
- Call `IncrementalMerkleTreeContainer.wfcheck()` (or an equivalent full structural/size validation of `parents`, and depth bound enforcement) immediately after deserializing a client-supplied voucher, before it is used to build a spend or call `path()`/`root()`.
- In `MerklePath.encode()`, assert (with runtime `if`/exception, not Java `assert`) that `authenticationPath.size() == DEPTH` before serialization.
- In `JLibrustzcash.librustzcashSaplingSpendProof`, validate `voucherPath.length` against the exact size expected by the native binding before invoking the native call, throwing a `ZksnarkException` instead of passing malformed input to native code.

### Proof of Concept
```java
// Illustrative JUnit test showing the missing size validation
@Test
public void testMalformedVoucherParentsProducesWrongPathLength() throws Exception {
  IncrementalMerkleTreeCapsule treeCapsule = new IncrementalMerkleTreeCapsule();
  // Simulate a malicious client-supplied protobuf where "parents" has far more
  // entries than the fixed DEPTH permits (normally guarded by wfcheck(), which
  // is never invoked on this path).
  for (int i = 0; i < 500; i++) {
    treeCapsule.addParent(somePresentPedersenHash()); // crafted, present hashes
  }
  treeCapsule.setLeft(somePedersenHash());
  treeCapsule.setRight(somePedersenHash());

  IncrementalMerkleVoucherCapsule voucherCapsule = new IncrementalMerkleVoucherCapsule();
  voucherCapsule.setTree(treeCapsule);
  IncrementalMerkleVoucherContainer voucher =
      new IncrementalMerkleVoucherContainer(voucherCapsule);

  byte[] encodedPath = voucher.path().encode();
  // Expected native fixed size (per LibrustzcashTest.benchmarkCreateSpend fixture) is 1065 bytes
  // for a DEPTH=32 tree. Demonstrate the size is NOT enforced/fixed:
  Assert.assertNotEquals(1065, encodedPath.length);
  // Passing `encodedPath` into JLibrustzcash.librustzcashSaplingSpendProof(...) without
  // a length check would hand a mis-sized buffer to the native FFI call.
}
```

  public void wfcheck() throws ZksnarkException {
    if (treeCapsule.getParents().size() >= DEPTH) {
      throw new ZksnarkException("tree has too many parents");
    }
    if (!treeCapsule.parentsIsEmpty()) {
      PedersenHashCapsule parentCompressCapsule =
          new PedersenHashCapsule(
              treeCapsule.getParents().get(treeCapsule.getParents().size() - 1));
      if (!parentCompressCapsule.isPresent()) {
        throw new ZksnarkException("tree has non-canonical representation of parent");
      }
    }

    if ((!leftIsPresent()) && rightIsPresent()) {
      throw new ZksnarkException("tree has non-canonical representation; right should not exist");
    }

    if ((!leftIsPresent()) && treeCapsule.getParents().size() > 0) {
      throw new ZksnarkException(
          "tree has non-canonical representation; parents should be empty");

    Deque<PedersenHash> fillerHashes = new ArrayDeque<>();

  }

  /**
   * construct whole path from bottom right to root. if not present in treeCapsule, choose
   * fillerHashes
   *
   * @return list of PedersenHash, list of existence, reversed.
   */
  public MerklePath path(Deque<PedersenHash> fillerHashes) throws ZksnarkException {
    if (!leftIsPresent()) {
      throw new ZksnarkException(
          "can't create an authentication path for the beginning of the tree");
    }
    PathFiller filler = new PathFiller(fillerHashes);
    List<PedersenHash> path = new ArrayList<>();
    List<Boolean> index = new ArrayList<>();
    if (rightIsPresent()) {
      index.add(true);
      path.add(treeCapsule.getLeft());
    } else {
      index.add(false);
      path.add(filler.next(0));
    }

    int d = 1;
    for (PedersenHash parent : treeCapsule.getParents()) {
      PedersenHashCapsule parentCompressCapsule = new PedersenHashCapsule(parent);
      if (parentCompressCapsule.isPresent()) {
        index.add(true);
        path.add(parent);
      } else {
        index.add(false);
        path.add(filler.next(d));
      }
      d++;
    }

    while (d < DEPTH) {
      index.add(false);
      path.add(filler.next(d));
      d++;
    }

    List<List<Boolean>> merklePath = new ArrayList<>();
    for (PedersenHash b : path) {
      merklePath.add(ByteUtil.convertBytesVectorToVector(b.getContent().toByteArray()));
    }
    merklePath = Lists.reverse(merklePath);
    index = Lists.reverse(index);
    return new MerklePath(merklePath, index);
  }
