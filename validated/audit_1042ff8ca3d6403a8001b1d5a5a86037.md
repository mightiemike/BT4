### Title
Missing outbound-enabled check on rescue-fund outbounds allows attacker to force TSS signing/broadcast for a paused/disabled chain - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`BuildOutboundsFromReceipt` (normal outbound creation path) enforces `IsChainOutboundEnabled` for the destination chain before an outbound is attached to a `UniversalTx`. `AttachRescueOutboundFromReceipt`, which handles the `RescueFundsOnSourceChain` gateway event, builds and attaches an `OutboundTx` with `DestinationChain: originalUtx.InboundTx.SourceChain` but performs no equivalent `IsChainOutboundEnabled` check.

### Finding Description
The pause/enable flag `ChainConfig.Enabled.IsOutboundEnabled` is the admin's mechanism to stop TSS-signed value from being sent to a given destination chain (e.g. because it is compromised, exploited, or its bridge parameters are unsafe). This is enforced in one code path (`BuildOutboundsFromReceipt`, line 50) but not in the sibling code path that creates rescue outbounds (`AttachRescueOutboundFromReceipt`). Both paths ultimately produce an `OutboundTx` appended via the same `attachOutboundsToUtx` helper [3](#0-2) , which writes the outbound into `PendingOutbounds` for TSS signing/broadcast regardless of which construction path produced it.

An attacker who can get a UTX into rescue-eligible state (CEA deposit failed, or the auto-generated `INBOUND_REVERT` outbound reached `REVERTED` status) and then trigger a `RescueFundsOnSourceChain` gateway event can force the creation of a `TxType_RESCUE_FUNDS` outbound targeting `originalUtx.InboundTx.SourceChain` even if the admin has since disabled outbound flows to that chain via `IsOutboundEnabled = false`. The chain's outbound-enabled flag is meant to gate exactly this kind of value movement (TSS-signed asset release) to a chain, but the enum/flag check that exists elsewhere is simply absent here — directly analogous to the `unpaused(p)` bypass in the referenced report, where a check present in one function is omitted in a sibling function operating on attacker-influenced state.

### Impact Explanation
If admins pause outbound for a chain (e.g., because the gateway/bridge contract there is compromised or the chain is under attack), rescue-fund flows can still create a `PENDING` outbound destined for that chain, and downstream TSS coordination (`universalClient/tss/coordinator`, `txbroadcaster`, `txresolver`, all of which reference `IsChainOutboundEnabled` in other guard points) may end up signing/broadcasting funds to a chain the admin explicitly disabled. This defeats the intended kill-switch and can result in loss of protocol/user funds if the destination chain or its gateway is unsafe — matching the in-scope impact "unauthorized release ... of user or protocol-controlled funds" and "corruption of ... revert destination" from the finalized state.

### Likelihood Explanation
Reaching rescue eligibility requires either a failed CEA deposit or a reverted `INBOUND_REVERT` outbound — both of which are ordinary, unprivileged consequences of normal inbound processing (e.g. deposit fails because token config lookup fails, or the destination TSS signing/broadcast simply fails/expires). No privileged or validator-collusion assumption is required beyond honest UVs observing the real `RescueFundsOnSourceChain` event, which is itself attacker-triggerable by calling the gateway's rescue function on the source chain after a failed deposit. This makes the missing check readily reachable by an ordinary user driving an inbound to failure and then invoking the rescue path.

### Recommendation
Add the same `IsChainOutboundEnabled` guard used in `BuildOutboundsFromReceipt` to `AttachRescueOutboundFromReceipt` before attaching the rescue outbound, e.g.:
```go
outboundEnabled, err := k.uregistryKeeper.IsChainOutboundEnabled(ctx, originalUtx.InboundTx.SourceChain)
if err != nil {
    return fmt.Errorf("rescue: failed to check outbound enabled for chain %s: %w", originalUtx.InboundTx.SourceChain, err)
}
if !outboundEnabled {
    return fmt.Errorf("rescue: outbound is disabled for chain %s", originalUtx.InboundTx.SourceChain)
}
```
placed immediately before the `attachOutboundsToUtx` call at line 331.

### Proof of Concept
1. Admin sets `ChainConfig.Enabled.IsOutboundEnabled = false` for chain X after detecting it is unsafe.
2. A user submits/observes an inbound from chain X whose CEA deposit fails (or whose auto-`INBOUND_REVERT` outbound reaches `REVERTED`), making the UTX rescue-eligible per the checks at [4](#0-3) .
3. The attacker triggers a `RescueFundsOnSourceChain` gateway event on Push Chain referencing that UTX.
4. `AttachRescueOutboundFromReceipt` builds and attaches a `TxType_RESCUE_FUNDS` outbound with `DestinationChain: chain X` without ever calling `IsChainOutboundEnabled(ctx, "X")`, unlike the normal-outbound path.
5. This outbound is written to `PendingOutbounds` and becomes eligible for TSS signing/broadcast to chain X, bypassing the admin's pause.

Note: I was unable to fully trace how `universalClient/tss/coordinator`, `txbroadcaster`, and `txresolver` re-validate `IsChainOutboundEnabled` at signing/broadcast time (only one match each was found and not read in full) — if one of those layers independently re-checks and rejects disabled-chain outbounds before actual TSS signing, the practical impact would be reduced to state pollution (a permanently `PENDING` outbound record) rather than fund release. This should be verified against `universalClient/tss/coordinator/coordinator.go` and `universalClient/tss/txbroadcaster/broadcaster.go` before treating this as a full fund-loss issue.
