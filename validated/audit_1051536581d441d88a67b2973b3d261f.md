## Analysis: Analog Found

The GPAC NULL-pointer-dereference/DoS bug class (an unchecked `Option`/error path that crashes the process on attacker-influenced input) has a concrete analog in nearcore's cross-shard receipt/resharding path, reachable from an ordinary `DeployGlobalContract` transaction combined with normal chain resharding.

### Title
Unrecoverable `receipt_filter_fn` panic on stale `GlobalContractDistribution` receipts under legacy (V1/V2) resharding causes a transaction-triggered chain halt - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
An unprivileged account can deploy a global contract, generating a `GlobalContractDistribution` receipt whose `target_shard` is snapshotted at deploy time. If this receipt is delayed (e.g., via congestion) across two or more shard-splitting events while the network is still on a legacy `ShardLayoutV1`/`V2` layout (single-generation split history), the shard-remapping helper `resolve_to_current_shard` cannot resolve the now-doubly-stale `target_shard`, causing `receiver_shard_id` to return `Err`. That `Err` is `.unwrap()`ed inside `receipt_filter_fn`, panicking every node that applies the chunk containing that receipt — an unrecoverable, transaction-triggered chain halt, analogous to the GPAC NULL dereference DoS.

### Finding Description
`GlobalContractDistributionReceipt::target_shard()` records the destination shard at forward time [1](#0-0) . When a chunk is applied, delayed receipts are popped through `DelayedReceiptQueueWrapper::pop`, which filters receipts using `receipt_filter_fn`: [2](#0-1) 

`receipt_filter_fn` calls `receiver_shard_id(&shard_layout).unwrap()` directly, with no error handling [3](#0-2) .

`Receipt::receiver_shard_id` handles `GlobalContractDistribution` specially: if the recorded `target_shard` is no longer part of the current shard layout, it calls `shard_layout.resolve_to_current_shard(target_shard)`, and returns `Err(EpochError::ShardingError(...))` only if that call returns `None`: [4](#0-3) 

`ShardLayout::resolve_to_current_shard` dispatches per layout version: [5](#0-4) 

- For `V3` layouts (used only once dynamic resharding is enabled), the cumulative `shards_split_map` records **all** historical splits, so `resolve_to_current_shard` can walk arbitrarily many generations back and will basically always succeed [6](#0-5) .
- For legacy `V0`/`V1`/`V2` layouts, it falls back to `get_children_shards_ids(shard_id).map(|c| c[0])` — a **single-generation** lookup [5](#0-4) . If the receipt's `target_shard` predates the *current* layout by two or more resharding generations, this returns `None`, `receiver_shard_id` returns `Err`, and `receipt_filter_fn`'s `.unwrap()` panics.

The project's own regression test explicitly documents that the fix (full split-history resolution) is a V3-only guarantee, and that legacy/static resharding remains exposed: [7](#0-6) [8](#0-7) 

("The fix only works with V3 shard layouts (dynamic resharding). With static resharding, the shard layout doesn't maintain a full split history.")

### Impact Explanation
A single unprivileged transaction (`DeployGlobalContract`) can, given a network still running static (V1/V2) resharding and two subsequent resharding events while the resulting distribution receipt sits delayed/buffered, cause every validator/RPC node applying the affected shard's chunk to `panic!` inside `Runtime::apply` → `process_receipts` → `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn`. Because this occurs deterministically for all nodes applying that shard (it's part of consensus state transition), it manifests as a chain halt at that shard — a protocol-level denial of service, not a single-node crash. This satisfies the "transaction-triggered halt" bar for this scan.

### Likelihood Explanation
Likelihood depends on network configuration: it requires (a) a network still on legacy V1/V2 static shard layouts (V3/dynamic resharding not yet enabled), (b) the target shard being resharded twice while the distribution receipt is delayed. Two static reshardings historically occur only across rare protocol-version upgrades, and delaying a receipt for that long requires sustained congestion on the specific shard. This is a narrow but real timing/config window; the codebase authors flagged it directly.

### Recommendation
- Replace the `.unwrap()` in `receipt_filter_fn` with graceful error propagation (`?`) so a resolution failure surfaces as a `RuntimeError` rather than a panic.
- Extend `resolve_to_current_shard` for legacy `V0`/`V1`/`V2` layouts to walk multi-generation split history (e.g., by consulting `EpochManagerAdapter::get_shard_layout_history`), matching the V3 behavior, or block static resharding from proceeding while unresolved `GlobalContractDistribution` receipts targeting doomed shards remain outstanding.
- Add a fuzz/regression test analogous to `test_stale_global_contract_distribution_after_double_resharding` but exercising the static (V1/V2) resharding path to confirm no panic occurs.

### Proof of Concept
1. Configure a test network on a legacy (non-dynamic) shard layout with two scheduled static reshardings (protocol-version-gated layout changes) targeting the shard containing `deploy_user`.
2. From `deploy_user`, submit `DeployGlobalContract`, producing a `GlobalContractDistributionReceipt` with `target_shard = S_A`.
3. Saturate compute on `S_A` every block (as in the existing test's `burn_gas_raw` loop) so the receipt is pushed into and stays in the delayed queue through both resharding boundaries.
4. Once both static reshardings complete, stop saturating and let the delayed queue drain: `receipt_filter_fn` calls `receiver_shard_id` → `resolve_to_current_shard` (legacy single-generation fallback) → `None` → `Err` → `.unwrap()` panics, halting the shard's chunk application on every node.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

    /// For V3 layouts this uses the complete `shards_split_map`.

    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {

        }
    }

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }
