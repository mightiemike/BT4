## Finding

Based on the investigation, the closest reachable analog to the "Steward Program" bug (internal state marked for one epoch's transition while external state is already mutated, with no synchronization guard) is in `x/utss/keeper/msg_vote_tss_key_process.go`.

### Title
Stale-process TSS vote acceptance can finalize a `TssKey` with mismatched participants/status - (File: x/utss/keeper/msg_vote_tss_key_process.go)

### Summary
`VoteTssKeyProcess` never verifies that the `processId` argument supplied by the voting Universal Validator matches the `Id` of the `CurrentTssProcess` it fetches from state [1](#0-0) . `CurrentTssProcess` can legitimately change out from under an in-flight vote: `InitiateTssKeyProcess` force-expires the existing pending process and installs a brand-new one (with a different participant set) the moment the validator set changes, e.g. immediately after `RemoveUniversalValidator` fires the `AfterValidatorRemoved`/`AfterValidatorStatusChanged` hooks [2](#0-1) [3](#0-2) .

### Finding Description
`VoteTssKeyProcess`:
1. Loads whatever process is currently `CurrentTssProcess` (`process`) — not the process identified by the caller-supplied `processId`.
2. Passes the caller's `processId` into `VoteOnTssBallot` and into `FinalizeTssKeyProcess`, and stamps the resulting `TssKey.ProcessId` with that same `processId`.
3. But builds `tssKey.Participants` and drives the post-finalization validator-lifecycle loop (`PENDING_JOIN → ACTIVE`, `PENDING_LEAVE → INACTIVE`) using `process.Participants`/`process.ProcessType`, i.e. the **current** process, not the process the vote was actually cast for. [4](#0-3) 

Because `InitiateTssKeyProcess` can supersede `CurrentTssProcess` synchronously within the same block as a validator-removal/-addition admin action (force-expiring the old process and writing a new one with a new `Id` and a new `Participants` set) [5](#0-4) , a `MsgVoteTssKeyProcess` referencing the just-force-expired `processId` (e.g. broadcast by a UV before it observed the supersession) is not rejected by an `Id` mismatch check — the code only checks block-height expiry of whatever `CurrentTssProcess` happens to be at call time [1](#0-0) . If that vote still reaches quorum via `VoteOnTssBallot`, the module ends up minting a `TssKey` record whose `ProcessId` refers to a defunct process while its `Participants` and lifecycle side effects are drawn from a *different*, unrelated `CurrentTssProcess`. This is structurally the same invariant violation as the reported bug class: one subsystem (the ballot/vote bookkeeping keyed by `processId`) advances based on stale identity while another subsystem (`CurrentTssProcess`, which gates participant computation and drives validator ACTIVE/INACTIVE transitions) has already moved on, and there is no halting/flagging mechanism forcing these two pieces of state to stay pinned to the same process before finalization is allowed.

### Impact Explanation
If exploitable, this could corrupt `CurrentTssKey`/`TssKeyHistory` (wrong `Participants` recorded against a `ProcessId`) and drive incorrect validator lifecycle transitions (activating/deactivating the wrong universal validators relative to the key that was actually finalized), which underpins TSS coordination for all outbound signing. A wrong `Participants` list on the canonical `TssKey` record is a state-machine integrity break in the TSS coordination path called out in the allowed-impact gate.

### Likelihood Explanation
Uncertain / not fully confirmed. I was not able to inspect `VoteOnTssBallot` and `FinalizeTssKeyProcess` (in `x/utss/keeper/voting.go` and `x/utss/keeper/tss_key_process.go`) before running out of tool budget, so it is unverified whether `VoteOnTssBallot` internally re-validates `processId` against a per-process ballot lookup (which could make the surface-level absence of a check in `VoteTssKeyProcess` benign), or whether `FinalizeTssKeyProcess` independently guards against operating on an already-expired/force-expired process ID. Additionally, votes are restricted to bonded, non-tombstoned Universal Validators (an honest-validator/permissioned message type per the module's gasless vote-message design), which narrows — but given the scope's "honest validators" framing does not eliminate — the practical attack surface, since the trigger condition here is a race/reordering scenario (stale vote landing after a hook-driven supersession) rather than a forged message from an arbitrary unprivileged actor.

### Recommendation
Explicitly reject `MsgVoteTssKeyProcess` when `processId != process.Id` of the loaded `CurrentTssProcess`, and reconcile `FinalizeTssKeyProcess`/`TssKey` construction to consistently use one canonical process record (looked up by the caller's `processId` via `ProcessHistory`, not implicitly via `CurrentTssProcess`) for both the vote tally and the participants/lifecycle side effects — mirroring the remediation pattern from the source report (flag the stale process for immediate rejection rather than allowing a vote to silently graft onto a different in-flight process).

### Proof of Concept
Conceptual, not fully verified end-to-end due to unread `VoteOnTssBallot`/`FinalizeTssKeyProcess` internals:
1. Admin removes an ACTIVE universal validator via `MsgRemoveUniversalValidator`; `RemoveUniversalValidator` transitions it to `PENDING_LEAVE` and fires hooks [6](#0-5) .
2. The `x/utss` hook immediately calls `InitiateTssKeyProcess(QUORUM_CHANGE)`, which force-expires the existing `CurrentTssProcess` (old `Id`=N) and installs a new one (`Id`=N+1, different `Participants`) in the same block [7](#0-6) .
3. A UV's `MsgVoteTssKeyProcess` still carrying `processId = N` (submitted just before the supersession) is processed: `VoteTssKeyProcess` loads `CurrentTssProcess` (now `Id`=N+1) but never checks it against the supplied `processId = N` [1](#0-0) .
4. If quorum is reached, `TssKey{ProcessId: N, Participants: process.Participants}` is persisted with process N+1's participants attached to process N's ID, and validator lifecycle transitions are driven off process N+1's participant list even though the finalized record claims to belong to process N.
