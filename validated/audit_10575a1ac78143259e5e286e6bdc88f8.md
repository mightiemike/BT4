### Title
Panic on legitimately-nested bytecode segment structures in `CompiledClassV1::try_from` causes sequencer/node crash on class load - ([File: crates/blockifier/src/execution/contract_class.rs])

### Summary
`NestedFeltCounts::new_inner`, used whenever a compiled (CASM) class is converted into the blockifier's runnable `CompiledClassV1` representation, hard-codes an assumption that the bytecode segmentation produced by the Sierra→CASM compiler never nests more than one level deep. Any class whose `bytecode_segment_lengths` metadata legitimately contains nested `NestedIntList::Node` structures deeper than depth 1 (a structure the OS's own Rust implementation explicitly supports and is exercised in its own test fixtures) will trigger an `assert!` panic, and unchecked slice indexing in the same function can panic on out-of-bounds access as well. This is directly analogous to CVE-2014-8140: a length/structure field taken from parsed metadata is trusted and indexed into a buffer without validating it fits, causing a crash instead of a graceful error.

### Finding Description
`NestedFeltCounts::new_inner` is defined as: [1](#0-0) 

It contains:
```
fn new_inner(
    bytecode_segment_lengths: &NestedIntList,
    bytecode: &[BigUintAsHex],
    segmentation_depth: usize,
) -> (Self, usize) {
    assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");
    match bytecode_segment_lengths {
        NestedIntList::Leaf(len) => {
            let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
            ...
        }
        NestedIntList::Node(segments_vec) => {
            for segment in segments_vec {
                let (segment, felt_count) = Self::new_inner(segment, &bytecode[total_felt_count..], segmentation_depth + 1);
                ...
            }
        }
    }
}
```

Two separate memory-safety/robustness issues exist here, both stemming from trusting a length/structure field without validating it against the actual buffer size before indexing — the same bug class as CVE-2014-8140 (a crafted "extra field" length in a zip header that does not match the real data length, leading to an out-of-bounds read):

1. **Unchecked slice indexing on `len`**: `&bytecode[..*len]` and `&bytecode[total_felt_count..]` will panic if `len`/`total_felt_count` exceeds `bytecode.len()`, instead of returning a graceful compilation/validation error.
2. **Hard-coded depth limit of 1**: the `assert!(segmentation_depth <= 1, ...)` will panic for any `NestedIntList` with nesting deeper than one level. The Starknet OS's own Rust re-implementation of the identical bytecode-segmentation structure imposes **no such depth restriction** and is tested with 3-level-deep nesting: [2](#0-1) 

and the corresponding recursive builder in the OS crate handles arbitrary nesting without a depth assertion: [3](#0-2) 

This shows that deeply-nested segment structures are a valid, expected shape for `bytecode_segment_lengths` elsewhere in the same codebase, but `blockifier`'s `NestedFeltCounts::new_inner` cannot handle them.

`NestedFeltCounts::new` (and thus `new_inner`) is invoked unconditionally when constructing a `CompiledClassV1` from a compiled CASM class: [4](#0-3) 

specifically:
```
let bytecode_segment_felt_sizes =
    NestedFeltCounts::new(&class.get_bytecode_segment_lengths(), &class.bytecode);
```

`class.get_bytecode_segment_lengths()` returns the `bytecode_segment_lengths: Option<NestedIntList>` field taken directly from the `CasmContractClass` produced by compiling the Sierra program supplied in a **Declare transaction** (via `SierraCompiler::compile` / `apollo_compile_to_casm`), i.e. attacker-influenced input reachable by any contract declarer: [5](#0-4) [6](#0-5) 

`CompiledClassV1::try_from` is reached whenever the class is loaded for execution — i.e., on the declaring transaction's own validation/deployment path and on every subsequent invocation of that class by any account.

### Impact Explanation
A panic inside `TryFrom<VersionedCasm> for CompiledClassV1` occurring during block building, transaction validation, or Starknet OS re-execution will abort/crash the processing sequencer or full node (Rust `panic!`/`assert!` unwinds the thread and, depending on how the call site handles panics, can crash the whole process or poison shared state). Since this is triggered deterministically by data derived from a single Declare transaction's Sierra program (once compiled to CASM with a legitimately nested segmentation), it can be used to:
- Crash sequencer nodes attempting to build/validate a block containing the declared class or any invocation of it, disrupting the network's ability to confirm new transactions.
- Cause honest-node divergence during Starknet OS re-execution/verification if some code paths (OS Rust re-implementation) tolerate deep nesting while `blockifier`'s native path does not, producing inconsistent behavior between execution and re-execution/verification layers.

This satisfies the "network unable to confirm new transactions" / "honest-node divergence" impact criteria and is reachable purely via a contract declarer submitting a single Declare transaction — no privileged operator/proposer access required.

### Likelihood Explanation
Likelihood depends on whether the specific Sierra→CASM compiler (`cairo_lang_starknet_classes`) used by the sequencer ever emits `NestedIntList` structures with depth > 1 for real, large/complex contracts (the segmentation feature is designed to reduce hashing/loading cost for very large functions/contracts, and the codebase's own test fixtures demonstrate 3-level nesting is a valid shape for this exact data structure). Because compilation of the user-submitted Sierra program is not sandboxed against this specific invariant, and because the invariant is silently violated only inside `blockifier` (not enforced or rejected earlier in the pipeline, e.g. at gateway validation), a contract author could craft or simply happen to compile a sufficiently large/nested contract that trips this assertion.

### Recommendation
- Replace the `assert!(segmentation_depth <= 1, ...)` and the unchecked slice indexing in `NestedFeltCounts::new_inner` with proper bounds/structure validation that returns a `Result`/compilation error instead of panicking.
- Align the depth handling of `blockifier`'s `NestedFeltCounts` with the Starknet OS's unrestricted recursive structure (`create_bytecode_segment_structure_inner`) so behavior between execution and OS re-execution is consistent.
- Add a fuzz/property test that generates `NestedIntList` structures of varying depth (as already done in `starknet_os`'s test suite) and asserts `CompiledClassV1::try_from` never panics, only returns errors for malformed data.

### Proof of Concept
1. Compile (via the sequencer's `SierraCompiler`) a Sierra program large/complex enough that `cairo_lang_starknet_classes::casm_contract_class::CasmContractClass::bytecode_segment_lengths` naturally produces a `NestedIntList::Node` containing another `NestedIntList::Node` (nesting depth ≥ 2) — this is the same kind of structure exercised by `get_dummy_compiled_class(contract_segmentation: true)` in `crates/starknet_os/src/hints/hint_implementation/compiled_class/compiled_class_test.rs:213-225`.
2. Submit this class in a Declare transaction (or trigger execution of an already-declared such class).
3. When the sequencer converts the resulting `CasmContractClass`/`VersionedCasm` into `CompiledClassV1` (`crates/blockifier/src/execution/contract_class.rs:667-668`), `NestedFeltCounts::new` → `new_inner` is invoked with `segmentation_depth` reaching 2, hitting `assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.")`, panicking and crashing the process handling that transaction.

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
