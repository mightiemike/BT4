### Title
`MsgExecutePayload` is gasless with an attacker-controlled, unbounded EVM `gasLimit` that is never charged intrinsic/computational cost at the Cosmos layer - (File: `app/txpolicy/gasless.go`, `x/uexecutor/types/universal_payload.go`, `x/uexecutor/keeper/evm.go`)

### Summary
The external finding is about `minievm` never charging Ethereum-style intrinsic gas (base tx cost + calldata + access-list cost) before executing a transaction, letting an attacker consume real EVM computation while paying only the much cheaper Cosmos-side, size-based gas fee. Push Chain's `MsgExecutePayload` path has the same root cause: the message is unconditionally placed in the gasless allowlist (`app/txpolicy/gasless.go`), which causes the Cosmos ante pipeline to skip `DeductFeeDecorator` and `MinGasPriceDecorator` entirely (`app/ante/fee.go:60-64`, `app/cosmos/min_gas_price.go:81-84`). The actual computational budget for the message, `UniversalPayload.GasLimit`, is a fully attacker-controlled uint256 string that is validated only for being a non-negative integer (`x/uexecutor/types/universal_payload.go:41-58`, `ValidateBasic`) — there is no upper bound, and it is fed directly as the EVM `gasLimit` into `DerivedEVMCall` (`x/uexecutor/keeper/evm.go:172-192`, `CallUEAExecutePayload`). Only *after* the EVM sub-call executes is any fee ever computed, via `DeductGasFeesFromReceipt` (`x/uexecutor/keeper/fees.go:97-148`), and that charge is billed to the **UEA owner's** on-chain balance, not to the Cosmos tx signer who submitted the (fee-free) transaction.

### Finding Description
`MsgExecutePayload` is in the gasless whitelist alongside `MsgMigrateUEA`, `MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`, `MsgVoteChainMeta` (`app/txpolicy/gasless.go:17-25`). Being gasless means:
- `DeductFeeDecorator.AnteHandle` returns immediately, without requiring or deducting any Cosmos fee (`app/ante/fee.go:59-64`).
- `MinGasPriceDecorator.AnteHandle` also short-circuits the minimum-fee check (`app/cosmos/min_gas_price.go:81-84`).

The only remaining anti-spam control common to every tx is `ante.NewConsumeGasForTxSizeDecorator` (`app/ante/ante_cosmos.go:39`), which — exactly as `berndartmueller` demonstrated for the minievm access-list case — charges gas proportional to raw tx *byte size*, not to the actual EVM computation the message will trigger.

The message's own execution flow (`x/uexecutor/README.md:211-237`, `x/uexecutor/keeper/execute_payload.go:17-64`) then calls `CallUEAExecutePayload`, which:
1. Parses `universal_payload.GasLimit` as an arbitrary-size `big.Int` with no maximum bound check (`x/uexecutor/keeper/evm.go:172-176`).
2. Passes it straight through to `evmKeeper.DerivedEVMCall(..., gasLimit, true /*commit*/, false /*gasless*/, false /*isModuleSender*/, ...)` (`x/uexecutor/keeper/evm.go:178-192`), which performs a real, committed EVM state transition against the UEA contract.
3. Only after execution does `DeductGasFeesFromReceipt` compute `gasCost = effectiveGasPrice * receipt.GasUsed` and burn it from the UEA owner's balance (`x/uexecutor/keeper/fees.go:97-148`) — this fee is billed to the payload owner, never to the Cosmos-tx `Signer` who submitted the free transaction and triggered the compute.

Because the `Signer` and the UEA `Owner` are intentionally different roles (`x/uexecutor/README.md:211-218`), an attacker who is also the owner of their own UEA can self-sign a `MsgExecutePayload` with a very large `GasLimit`, submit it as a completely gasless Cosmos transaction (no fee, no min-gas-price check), and force real EVM computation to run and be committed to state — the only Cosmos-side "cost" charged upfront is the trivial `ConsumeGasForTxSizeDecorator` byte fee, exactly the gap the original report identified for access-list gas.

### Impact Explanation
This is a Denial-of-Service class issue reachable by an ordinary, unprivileged user (no validator/relayer/admin role needed — anyone can deploy their own UEA and self-sign payloads). Because `MsgExecutePayload` is fully gasless at the Cosmos layer, an attacker can:
- Submit many such transactions across blocks with large `GasLimit` values, forcing honest validators to spend real EVM execution/storage-write time processing them, while paying essentially nothing at the Cosmos fee layer (only the negligible tx-size gas).
- Do this without exhausting their own UEA balance meaningfully relative to compute consumed, since the "sensible" break on cost only exists after the fact (a failed `DeductAndBurnFees` due to insufficient UEA balance does not roll back the EVM state change if `execErr` is nil — the `writeCache()` in `ExecutePayloadV2` commits before the deduction failure would matter only if fee deduction fails, in which case the whole cache including EVM state is discarded; so an attacker without funds cannot commit state for free, but an attacker who *does* fund their own UEA with a small balance can still repeatedly force costly EVM computation while paying only whatever gas is actually used at the post-hoc EIP-1559-style rate, never anything closer to genuine "intrinsic"/base overhead that a non-gasless transaction type would otherwise require up front).

This matches the allowed "denial of service... not network-level and reachable without privileged control" impact category. It does not, by itself, demonstrate direct fund theft, since `DeductGasFeesFromReceipt` does bill the actual `receipt.GasUsed`, and UEA-vs-signer separation is a documented, deliberate design; however, the complete absence of any Cosmos-side base/intrinsic gas cost for gasless `MsgExecutePayload`/`MsgMigrateUEA` submissions is the same structural gap the source report flags for minievm.

### Likelihood Explanation
Moderate-to-high. No privileged role is required, and the mechanics (self-fund a UEA, submit self-signed payloads with large gas limits, repeat) are straightforward and fully within the "unprivileged external attacker, honest validators/nodes" scope. The main mitigating factor is that the attacker still needs enough UEA balance to cover the post-hoc `gasCost = effectiveGasPrice * gasUsed` for the transaction to actually commit; if that balance is insufficient, `DeductGasFeesFromReceipt` fails and the whole (including EVM) side effects roll back via the `CacheContext`/`writeCache` pattern (`x/uexecutor/keeper/execute_payload.go:35-56`), which caps the practical worst case to "attacker must actually pay effective gas price × gas used" rather than getting free unlimited compute. This significantly reduces (but does not eliminate) the severity relative to the original minievm finding, because there the attacker paid literally nothing extra for access-list opcodes; here the attacker does eventually pay `gasUsed * effectiveGasPrice`, just with no separate/base "intrinsic" surcharge and zero Cosmos-level tx fee, which is a narrower gap than the original report.

### Recommendation
- Charge a Cosmos-side gas cost proportional to the declared `UniversalPayload.GasLimit` (or a portion of it) at the ante/ValidateBasic layer, or reject `GasLimit` values above a governance-configured maximum, before the message reaches `CallUEAExecutePayload`.
- Consider requiring `MsgExecutePayload` (and `MsgMigrateUEA`) to still consume from the SDK gas meter proportional to `GasLimit`, rather than being fully exempt via `IsGaslessTx`, so that CheckTx/mempool admission reflects the real computational budget being requested.
- Bound `UniversalPayload.GasLimit` in `ValidateBasic` (`x/uexecutor/types/universal_payload.go`) to a sane maximum tied to the chain's block gas limit.

### Proof of Concept
1. Attacker deploys/derives their own UEA (owner = attacker) and funds it with a small amount of `upc`.
2. Attacker crafts a `UniversalPayload` with `GasLimit` set to a very large value (e.g., near the EVM block gas limit) and self-signs the `VerificationData` (they own the UEA key).
3. Attacker submits `MsgExecutePayload` as a gasless Cosmos tx (any `Signer`, since `Signer != Owner` is explicitly allowed). Ante pipeline skips `MinGasPriceDecorator` and `DeductFeeDecorator` entirely (`IsGaslessTx` returns true), charging only the trivial `ConsumeGasForTxSizeDecorator` fee based on tx byte size.
4. `ExecutePayloadV2` → `CallUEAExecutePayload` → `DerivedEVMCall` executes a real, committed EVM call with the attacker-chosen `gasLimit`, consuming real validator compute/storage resources.
5. Repeating this across many blocks lets the attacker force sustained EVM computation on honest validators while paying no Cosmos-level fee and only the post-hoc `gasUsed * effectiveGasPrice` from their own UEA balance — no separate charge is ever applied for the *declared* gas budget or any intrinsic/base cost, mirroring the minievm gap between "gas actually consumed and billed" and "gas that should be reserved/charged upfront for admitting the transaction."

Note: I could not inspect the actual gas-metering internals of the forked `github.com/pushchain/evm` module referenced by `DerivedEVMCall` (it lives in a separate repository, not indexed here), so I cannot confirm whether that fork independently enforces EIP-2929/2930-style intrinsic gas inside the EVM state transition itself. My analysis is scoped strictly to the Cosmos-side ante/fee handling and `x/uexecutor` message flow visible in this repository, where the gasless bypass and unbounded `GasLimit` field are the concretely reachable, script-visible root cause.
