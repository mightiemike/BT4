### Title
Malformed/invalid JSON HTTP API responses via unescaped control characters in self-type name fields (account_name, url, description, memo, token ids) - (File: framework/src/main/java/org/tron/core/services/http/JsonFormat.java)

### Summary
`JsonFormat.escapeBytesSelfType` validates untrusted bytes for name-type fields (`account_name`, `asset_issued_name`, `url`, `description`, `memo`, `sell_token_id`, etc.) by wrapping them in a throwaway JSON test string and calling fastjson's `JSON.parseObject`, then blindly re-embeds the *raw, unescaped* bytes into the actual HTTP JSON response if that ad-hoc check does not throw. Because fastjson's parser can be more lenient than strict JSON (accepting things like unescaped control characters within a quoted string) and because the escaping logic only quote-escapes (`"` → `\"`) without escaping backslashes or control characters, an attacker who sets such a field (e.g., via `AccountUpdateContract`) to bytes containing raw control characters can cause the node to emit HTTP/JSON-RPC responses that are not valid per RFC 8259.

### Finding Description
`escapeBytesSelfType` is reached from `JsonFormat.printFieldValue`'s `BYTES` case via `escapeBytes(value, fieldName, selfType)` whenever a protobuf message is printed with `selfType=true` (`JsonFormat.printToString(msg, true)`), which is used for `visible=true` API responses such as `Util.printAccount`. [3](#0-2) [4](#0-3) 

For fields registered in `HttpSelfFormatFieldName.NameFieldNameMap` — which includes `protocol.Account.account_name`, `protocol.Account.asset_issued_name`, `protocol.Note.memo`, `protocol.MarketOrder.sell_token_id`/`buy_token_id`, `protocol.AssetIssueContract.description`/`url`, etc. — the value is converted to a Java `String` from raw bytes, only double-quote characters are escaped, and the result is validated by embedding it in `{"key":"<result>"}` and calling `JSON.parseObject`; if parsing does not throw, the raw (only-quote-escaped) string is returned verbatim and printed directly into the final response, without further escaping of backslashes or ASCII control characters (0x00–0x1F). [5](#0-4) [6](#0-5) 

The bytes for `account_name` are attacker-controlled and pass validation with only a length check (`validAccountName` → `validBytes`, max 200 bytes, no charset restriction), unlike `validAccountId`/`validAssetName`/`validTokenAbbrName`, which restrict to printable ASCII via `validReadableBytes`. [7](#0-6) 
`UpdateAccountActuator.validate()`/`execute()` write the raw bytes straight to `AccountCapsule` with no further sanitization. [8](#0-7) 

Because fastjson's `JSON.parseObject` is known to be substantially more permissive than strict JSON (it historically tolerates constructs like unescaped control characters, non-standard escapes, etc.), a validation pass by fastjson does not guarantee the emitted text conforms to RFC 8259, which strict JSON consumers (e.g., Python's `json.loads`, JavaScript's `JSON.parse`, other language SDKs) require. The naive `"` -> `\"` regex escaping also does not escape backslashes, meaning the safety of this scheme depends entirely on fastjson's leniency happening to match strict-JSON safety, an unverified/undocumented assumption baked into the ad-hoc design.

### Impact Explanation
This is a data-integrity/availability issue at the HTTP API boundary rather than a memory-safety or consensus bug: any client/integration (wallets, exchanges, explorers) that fetches `/wallet/getaccount?visible=true` (or other `visible=true` endpoints exposing these fields) for an attacker-controlled account can receive a response body that fails to parse under strict JSON parsers, breaking downstream automated processing — a form of "DoS via RPC-API" against consumers of the node's HTTP interface. It does not permit node RCE, key leakage, unauthorized on-chain state change, or consensus divergence, since the corrupted output is confined to the JSON *presentation* layer used only in `selfType=true` responses; the underlying protobuf/chain state remains internally consistent.

### Likelihood Explanation
Preconditions: an ordinary funded account (needs only enough TRX to pay bandwidth for one `AccountUpdateContract` transaction, no special permission). Cost: negligible (single normal-fee transaction), and the operation is a one-time account name set per default node config (`allowUpdateAccountName` typically 0). Repeatability: limited to once per account by default unless `allowUpdateAccountName` is enabled by the chain, but multiple accounts can be created cheaply to repeat this against different targets, and other fields in `NameFieldNameMap` (`url`, `description`, `memo`, market token ids) offer additional, less-restricted vectors. The exact reliability of the exploit (i.e., whether fastjson's `JSON.parseObject` truly accepts a specific malformed byte sequence that a strict-JSON consumer rejects) depends on fastjson's precise lenient-parsing behavior, which was not runtime-verified in this analysis — this is a design-level weakness (relying on an undocumented leniency assumption) rather than a fully confirmed byte-for-byte PoC.

### Recommendation
Do not use a third-party lenient JSON parser as a correctness oracle for producing safe embedded JSON string content. Instead, properly and completely escape the raw bytes per RFC 8259 rules (escape `\`, `"`, and all control characters 0x00–0x1F, e.g. via `\uXXXX` or defined short escapes) before embedding them, decoupled from whatever leniency `fastjson`'s parser exhibits, and drop the "validate via JSON.parseObject then reuse raw" pattern in `escapeBytesSelfType`.
