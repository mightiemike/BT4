### Title
Vote batch reverts entirely when a single witness candidate is invalid or unregistered - (File: `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

### Summary
`VoteWitnessActuator.validate()` iterates over every `Vote` entry inside a single `VoteWitnessContract` transaction and throws a `ContractValidateException` the moment it finds one invalid or non-witness address in the list. Since Tron transactions are atomic and this check runs before `execute()`, a single bad/removed entry in the vote list aborts the *entire* transaction, discarding votes to all other, perfectly valid witnesses in the same call — mirroring the reported class of bug where one broken component in a batch operation reverts unrelated, healthy operations bundled with it.

### Finding Description
A caller can submit a `VoteWitnessContract` with up to `MAX_VOTE_NUMBER` votes distributed across multiple witness (SR) candidates in one transaction. During validation, the code loops through all votes and unconditionally throws if any single target fails checks: [1](#0-0) 

Specifically, if a witness address that the account previously voted for is later removed/unregistered from `WitnessStore` (e.g., an SR withdraws or is dropped) between the time the user builds the transaction and it's broadcast/packed, the `!witnessStore.has(witnessCandidate)` check fails and throws: [2](#0-1) 

Because this check lives inside a single loop over the whole `votesList` with no per-vote isolation (no try/catch or skip-and-continue), one invalid witness poisons validation for the *entire* transaction, causing all votes to other valid, healthy witnesses to be rejected as well — the exact "one broken adapter breaks all others" pattern from the referenced report, applied to Tron's witness-voting batch instead of Union Finance's money-market adapters.

The same all-or-nothing pattern is duplicated in the TVM-native path used by smart contracts calling `voteWitness`, in `VoteWitnessProcessor.execute()`, which throws `ContractExeException` on the first invalid witness found in the vote map, aborting processing of the remaining votes in the same call: [3](#0-2) 

### Impact Explanation
Any unprivileged TRX holder who batches votes for multiple SR candidates in a single `VoteWitnessContract` transaction can have their entire vote submission fail because of one stale/removed candidate, even though votes to the remaining valid candidates should be perfectly executable. This denies legitimate governance participation (voting/TRON Power delegation) and can be triggered passively (an SR withdrawing/being dropped) without any malicious action by the voter, causing unnecessary transaction failures and fee loss (though `calcFee()` returns 0 here, failed validation still wastes bandwidth/energy and requires resubmission), and blocks state changes (vote updates, reward cycle bookkeeping via `MortgageService.withdrawReward`) for otherwise-valid witnesses bundled in the same call.

### Likelihood Explanation
This is straightforward to trigger: witnesses can and do become unregistered/withdraw from the standby/active set over time, and users commonly vote for multiple SRs in one transaction to save fees. Any user who has an outdated vote list including a since-removed witness, or who is racing against an SR's own withdrawal transaction, will hit this failure deterministically on every retry until they manually filter out the offending address.

### Recommendation
Instead of throwing on the first invalid witness in the loop, skip/ignore invalid or unregistered witness candidates (similar to how zero-vote-count entries are already removed via `iterator.remove()`) and only revert the transaction if the vote list becomes fully empty of valid targets, or if a truly transaction-fatal condition (e.g., tron power exceeded) is detected. Apply the equivalent fix to `VoteWitnessProcessor.execute()` in the TVM-native path.

### Proof of Concept
1. Account A holds enough TRON Power and previously constructs a `VoteWitnessContract` with two entries: `[SR_valid, SR_about_to_be_removed]`.
2. Before A's transaction is packed into a block, `SR_about_to_be_removed` withdraws/unregisters, removing itself from `WitnessStore`.
3. A's transaction is processed by `VoteWitnessActuator.validate()`; the loop reaches `SR_about_to_be_removed`, `witnessStore.has(witnessCandidate)` is `false`, and a `ContractValidateException` is thrown at `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java:116-119`.
4. The whole transaction fails — A's vote for the still-valid `SR_valid` is also discarded, even though it was entirely legitimate and unrelated to the removed witness.
