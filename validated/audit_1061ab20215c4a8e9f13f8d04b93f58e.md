### Title
Webhook shop/topic identity is taken from unsigned headers, allowing HMAC-replay cross-tenant spoofing - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
`validateHmacFromRequestFactory` computes and verifies the webhook HMAC over `rawBody` only [1](#0-0) , while the shop domain and topic that `process` later trusts and passes to app handler callbacks are read directly from the `X-Shopify-Shop-Domain`/`X-Shopify-Topic` HTTP headers in `checkWebhooksHeaders`, with no cryptographic binding to the signed body [2](#0-1) . Because Shopify webhook HMACs are computed with the app's single `apiSecretKey` shared across every shop that installs the app, any merchant who legitimately received one authentic (body, HMAC) pair for their own shop can replay that exact body/HMAC while substituting a different shop's domain header, and `process` will accept it as coming from the victim shop.

### Finding Description
- `validateFactory` calls `validateHmacFromRequestFactory(config)` with `{type, rawBody, webhookType, ...adapterArgs}`. That factory reads only the HMAC header and `rawBody`, and verifies `safeCompare(hmac, HMAC-SHA256(apiSecretKey, rawBody))` [3](#0-2) . No header (domain, topic, webhook-id, api-version) is included in the signed material.
- After HMAC validation succeeds, `validateFactory` calls `checkWebhookHeaders`, which pulls `domain`, `topic`, `webhookId`, `apiVersion` straight from request headers with `getRequiredHeader`, and returns them in the `WebhookValidationValid` result without any comparison to the signed payload [2](#0-1) .
- `process` in `packages/apps/shopify-api/lib/webhooks/process.ts` then invokes the app's registered handler with `webhookCheck.domain` and `webhookCheck.topic` taken from that header-derived object, treating them as the trusted, verified origin: `handler.callback(webhookCheck.topic, webhookCheck.domain, rawBody, webhookId, ...)` [4](#0-3) .
- `apiSecretKey` is the app's single client secret and is identical for every shop that installs the app — it is not shop-specific. Therefore any merchant/tenant that has installed the app can obtain a genuine `(rawBody, X-Shopify-Hmac-Sha256)` pair from their own real webhook delivery, then resend the identical body and HMAC value to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) headers to claim to be a different, victim shop. Because the HMAC check never touches those headers, `validateHmacFromRequestFactory` still returns valid, and `checkWebhookHeaders` accepts the attacker-controlled domain claim at face value.
- The result: the app's webhook handler executes attacker-supplied body content believing it originates from and pertains to the victim shop (`webhookCheck.domain`), enabling cross-tenant state changes/data access if the handler uses the domain to select which shop's session/data to act on (a normal and expected usage pattern for webhook handlers).

### Impact Explanation
This breaks the fundamental invariant that a validated webhook signature guarantees the shop/topic identity of the request. An attacker who has legitimately installed the app on their own store can forge the shop-domain claim of any other store, causing the app's webhook handler to perform actions or process data as if received from a different, unrelated tenant. This is a cross-tenant forged-authenticated-request/state-change vulnerability consistent with the described "Cross-tenant webhook action" impact class.

### Likelihood Explanation
The precondition is minimal: the attacker only needs to be a legitimate, unprivileged installer of the target app (which triggers real webhook deliveries with a valid HMAC to capture), and knowledge of a victim shop's domain (which is often public, e.g. `victim.myshopify.com`). No secret key, MITM, or elevated role is required — only a replayed request with a modified header. The attack is deterministic and repeatable for every webhook topic the attacker's own shop receives, as long as the app's handler logic keys off `domain`/`topic` from the callback parameters.

### Recommendation
Bind the shop/topic identity to the verified signature instead of trusting header claims independently:
- Prefer resolving the shop identity from server-side state (e.g., look up the installed shop/session by an app-generated correlation, or cross-check the `domain` header against the shop that owns the `webhookId`/subscription via the Admin API or stored webhook registration) rather than trusting the raw header.
- At minimum, include the critical headers (`X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) in the HMAC-signed data computed and verified in `validateHmacFromRequestFactory`, or verify that these headers match values independently retrieved for the given webhook subscription, so a captured body+HMAC pair cannot be replayed under a different shop's identity.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/webhooks/__tests__/cross-tenant-replay.test.ts
import {shopifyApi, LATEST_API_VERSION} from '../..';
import {testConfig} from '../../__tests__/test-config';
import {createSHA256HMAC} from '../../../runtime/crypto';
import {HashFormat} from '../../../runtime/crypto/types';

test('replayed body+HMAC with forged shop domain is accepted', async () => {
  const shopify = shopifyApi(testConfig());
  const rawBody = '{}'; // empty/fixed body genuinely delivered to attacker's own shop

  const hmac = await createSHA256HMAC(
    shopify.config.apiSecretKey,
    rawBody,
    HashFormat.Base64,
  );

  // Attacker replays the SAME body + HMAC, but claims a victim shop's domain
  const forgedRequest = {
    method: 'POST',
    url: '/webhooks',
    headers: {
      'X-Shopify-Topic': 'orders/create',
      'X-Shopify-Hmac-Sha256': hmac,
      'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com', // not attacker's real shop
      'X-Shopify-Api-Version': LATEST_API_VERSION,
      'X-Shopify-Webhook-Id': 'forged-id',
    },
  };

  const result = await shopify.webhooks.validate({
    rawBody,
    rawRequest: forgedRequest,
  });

  // Vulnerability: HMAC passes and domain is accepted as 'victim-shop.myshopify.com'
  // even though the signature never covered that header.
  expect(result.valid).toBe(true);
  expect((result as any).domain).toBe('victim-shop.myshopify.com');
});
```
Expected (vulnerable) result: `result.valid === true` and `result.domain === 'victim-shop.myshopify.com'`, despite the request never having originated from that shop — demonstrating that `process` will invoke the app's handler believing the action pertains to the victim tenant.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
