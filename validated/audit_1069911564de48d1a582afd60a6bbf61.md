### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify accept a diverged state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by replay/verification tooling to confirm that a freshly re-executed transaction output matches the `TransactionInfo` recorded on the authenticated ledger (accumulator-proven, signed by validators). The function validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but it explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually commit to the post-execution state root (state Merkle tree root). This gap is called out in the code itself as a known TODO, but it remains live in the current tree and is exercised by `storage/db-tool/src/replay_on_archive.rs`.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  checks status equality, gas-used equality, and write-set hash equality against `txn_info.state_change_hash()`, and separately event root hash. It does not touch `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` at all, as explicitly documented by the in-code comment: [2](#0-1) .

This function is the sole per-transaction correctness gate used by the archive replay-verification tool. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` re-executes historical transactions with `AptosVMBlockExecutor` and calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))` [3](#0-2) , treating an `Ok(())` result as proof that local re-execution matches the authenticated, on-chain-committed `TransactionInfo`.

Because `state_checkpoint_hash` (the Sparse Merkle Tree root of world state) is never compared, a transaction whose write set happens to hash identically (or whose divergence is confined to state-checkpoint computation logic outside the write set, e.g. hot-state or position-state bookkeeping introduced by `TransactionInfoV1`) will pass `ensure_match_transaction_info` even though the actual committed state root diverges from what local execution produces. The corrupted/omitted value is exactly `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` on `TransactionInfo`, defined in [4](#0-3) .

### Impact Explanation
Replay-verify is one of the primary tools relied on to detect state-root divergence bugs (including hard-fork-class divergence) between different validator/full-node software versions before or after mainnet deployment. Since the checkpoint hash — the actual authenticated state commitment — is excluded from the comparison, a bug in state-checkpoint/state-root computation (independent of write-set hashing) would not be flagged by `replay_on_archive`, giving false confidence that historical execution is consistent. This directly weakens the state-proof-integrity guarantee the tool is supposed to provide: an authenticated `TransactionInfo`'s state-root field could differ from the true VM/state result without detection.

### Likelihood Explanation
The gap is deterministic and always present — it is not conditioned on adversarial input, only on running the replay-verify tool, and the code even documents it as a known blind spot tied to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (referenced in `storage/aptosdb/src/db/aptosdb_writer.rs` and `aptosdb_reader.rs`, and `types/src/on_chain_config/aptos_features.rs`), implying new state-root logic is expected to land without this safety net currently validating it.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the re-executed output/checkpoint computation and `txn_info`, and thread the expected checkpoint hash into `replay_on_archive.rs`'s call site before enabling any new state-root feature gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
Not independently reproducible from static analysis alone — the gap is confirmed by direct code inspection of `ensure_match_transaction_info` ( [5](#0-4) ) and its sole caller in the replay tool ( [6](#0-5) ): no test in the shown code path constructs a case where `state_checkpoint_hash` diverges while write-set/events/status/gas match, so I could not confirm from the available index whether the omission is currently exploitable in mainnet consensus/commit paths versus only in the offline `db-tool` replay utility. Given the index-size limits on this codebase and that I was unable to fully trace where `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is set/consumed in `aptosdb_writer.rs`/`aptosdb_reader.rs`, I recommend a Devin session with full repo access to confirm whether this gap is reachable in the primary consensus/execution commit path or is confined to the offline archive-replay debugging tool (which would lower the severity to a tooling gap rather than a mainnet state-commitment defect).

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
