### Title
Undefined-behavior write through an immutable-reference-derived pointer in `BucketStorage::copy_contents` - (`bucket_map/src/bucket_storage.rs`)

### Summary
`BucketStorage::copy_contents`, which is used whenever a bucket-map index or data bucket is grown (`grow_index`/`grow_data`/`new_resized`), performs its byte copy by taking `.as_ptr()` of two shared (`&[u8]`) slice references and casting the destination pointer to `*mut u8` before calling `std::ptr::copy_nonoverlapping`. This mirrors the reported class of bug in the external report: code that manually reaches for raw-pointer/assembly-level operations without respecting the language's memory-safety invariants, so the compiler is free to assume things about the underlying memory that the code then silently violates.

### Finding Description
In `bucket_map/src/bucket_storage.rs`, `copy_contents` is defined as:

```rust
fn copy_contents(&mut self, old_bucket: &Self) {
    ...
    let old_ix = i * old_bucket.cell_size as usize;
    let new_ix = old_ix * index_grow;
    let dst_slice: &[u8] = &self.mmap[new_ix..new_ix + old_bucket.cell_size as usize];
    let src_slice: &[u8] = &old_map[old_ix..old_ix + old_bucket.cell_size as usize];

    unsafe {
        let dst = dst_slice.as_ptr() as *mut _;
        let src = src_slice.as_ptr();
        std::ptr::copy_nonoverlapping(src, dst, old_bucket.cell_size as usize);
    };
}
``` [1](#0-0) 

`dst_slice` is created as a *shared* reference (`&[u8]`) into `self.mmap`, even though `self` is held as `&mut Self`. The code then casts `dst_slice.as_ptr()` to a mutable pointer and writes through it via `copy_nonoverlapping`. Under Rust's aliasing model, writing through a pointer derived from a shared reference is undefined behavior unless the memory is wrapped in an `UnsafeCell` (which a plain mmap byte slice is not). This is directly analogous to the Solidity report: the code performs a low-level memory operation (`unsafe` raw-pointer write / assembly write) while failing to uphold the invariants the compiler assumes hold for the memory region it touches (here, "not mutated while only a `&[u8]` is live" rather than "only writes within the 64-byte scratch space"). The compiler's optimizer is permitted to treat reads of `dst_slice`/`self.mmap[..]` elsewhere as invariant across the call, or to reorder/elide the write, since nothing in the type system indicates mutation is occurring.

This routine backs `BucketStorage::new_resized`, which is invoked from `Bucket::grow_index` and the data-bucket grow path in `bucket_map/src/bucket.rs`, i.e., every time an on-disk index or data bucket in the accounts index's disk-backed bucket map is resized. Bucket-map entries store the account index's slot lists, ref counts, and storage offsets/locations, so corruption here directly affects `AccountsIndex` lookups used to find the correct slot/storage location for an account.

### Impact Explanation
If the compiler (now or after a future LLVM/rustc update, or under different optimization levels) exploits the aliasing violation, the copied index/data-bucket entries could be corrupted or the write could be miscompiled/elided. Because these entries encode the account index's slot list, ref counts, and storage offsets, corruption can lead to stale or wrong-version account loads, an incorrect ref-count/tombstone state, or a validator panic on invariant violations discovered later (e.g., `assert!` failures in bucket occupancy tracking). This is rated Medium impact because miscompilation is compiler/version dependent and not reliably triggerable today, but the code pattern is unambiguously unsound per Rust's memory model, the same class of latent-but-real correctness hazard as the reported Solidity "memory-safe" assembly violation.

### Likelihood Explanation
Likelihood is Medium: `copy_contents` runs on every bucket-map grow operation, which happens routinely as the accounts index disk buckets fill up on any validator using disk index. The unsound aliasing exists on every such call, but actual miscompilation depends on optimizer behavior, which is not guaranteed to manifest with current toolchains, matching the "Medium/Medium" severity of the source report.

### Recommendation
Avoid deriving a mutable pointer from a shared slice reference. Obtain the destination pointer directly from a mutable borrow of `self.mmap` (e.g., via `self.mmap[new_ix..].as_mut_ptr()` taken while `self` is exclusively borrowed, or by restructuring to slice `&mut self.mmap` once and computing both sub-ranges via split/mutable indexing) so the write is performed through a pointer that the compiler knows may alias/mutate that memory:

```rust
let src_slice: &[u8] = &old_map[old_ix..old_ix + old_bucket.cell_size as usize];
let dst_slice: &mut [u8] = &mut self.mmap[new_ix..new_ix + old_bucket.cell_size as usize];
dst_slice.copy_from_slice(src_slice);
```
This removes the need for `unsafe` entirely for this copy, eliminating the aliasing-violation hazard while preserving identical semantics (the ranges are non-overlapping since `self.mmap` and `old_map` are distinct allocations).

### Proof of Concept
Not applicable as a runtime PoC (the issue is a latent aliasing-rule violation, not a currently-reproducible crash); the unsoundness is demonstrated by the code excerpt above: `dst_slice: &[u8]` is cast to `*mut _` and written to via `std::ptr::copy_nonoverlapping`, which is UB per Rust's reference aliasing model regardless of whether the current compiler happens to generate correct code for it.     /// copy contents from 'old_bucket' to 'self'
    /// This is used by data buckets
    fn copy_contents(&mut self, old_bucket: &Self) {
        let mut m = Measure::start("grow");
        let old_cap = old_bucket.capacity();
        let old_map = &old_bucket.mmap;

        let increment = self.contents.capacity_pow2() - old_bucket.contents.capacity_pow2();
        let index_grow = 1 << increment;
        (0..old_cap as usize).for_each(|i| {
            if !old_bucket.is_free(i as u64) {
                self.copying_entry((i * index_grow) as u64, old_bucket, i as u64);

                {
                    // copying from old to new. If 'occupied' bit is stored outside the data, then
                    // occupied has to be set on the new entry in the new bucket.
                    let start = self.get_start_offset_with_header((i * index_grow) as u64);
                    self.contents
                        .occupy(&mut self.mmap[start..], i * index_grow);
                }
                let old_ix = i * old_bucket.cell_size as usize;
                let new_ix = old_ix * index_grow;
                let dst_slice: &[u8] = &self.mmap[new_ix..new_ix + old_bucket.cell_size as usize];
                let src_slice: &[u8] = &old_map[old_ix..old_ix + old_bucket.cell_size as usize];

                unsafe {
                    let dst = dst_slice.as_ptr() as *mut _;
                    let src = src_slice.as_ptr();
                    std::ptr::copy_nonoverlapping(src, dst, old_bucket.cell_size as usize);
                };
            }
        });
        m.stop();
        // resized so update total file size
        self.stats.resizes.fetch_add(1, Ordering::Relaxed);
