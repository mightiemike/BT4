### Title
Unfreeze cooldown timers are locked in at the parameter value active when `UnfreezeBalanceV2` is executed, so governance increases of `UNFREEZE_DELAY_DAYS` do not apply to already-scheduled unfreeze requests - (File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java)

### Summary
This is the same bug class as the reported Backstop LP issue: a withdrawal cooldown timer's unlock time is computed and permanently fixed at the moment the timer is started, using whatever cooldown-duration parameter value is in effect at that instant. If governance later raises the cooldown duration to strengthen security, requests that were already scheduled under the old (shorter) value are not re-evaluated and keep their original, shorter unlock time.

### Finding Description
`UnfreezeBalanceV2Actuator.calcUnfreezeExpireTime()` computes the unlock time as `now + unfreezeDelayDays * FROZEN_PERIOD`, reading `unfreezeDelayDays` from `DynamicPropertiesStore.getUnfreezeDelayDays()` at execution time, and this absolute value is stored in the account's `UnFreezeV2.unfreezeExpireTime` field: [1](#0-0) [2](#0-1) 

The equivalent VM native-contract path (`UnfreezeBalanceV2Processor`, reachable from a smart contract via `Program.unfreezeBalanceV2`) does the exact same thing: [3](#0-2) [4](#0-3) 

`UNFREEZE_DELAY_DAYS` is a chain parameter that is changed via a governance proposal and is applied globally and immediately to the `DynamicPropertiesStore`, with no retroactive adjustment of already-created `UnFreezeV2` entries: [5](#0-4) 

Withdrawal of the unfrozen amount (`WithdrawExpireUnfreezeActuator` / `WithdrawExpireUnfreezeProcessor`, also reachable from smart contracts via `Program.withdrawExpireUnfreeze`) is gated purely on comparing the stored `unfreezeExpireTime` to the current block timestamp — it never re-checks whether the currently configured `UNFREEZE_DELAY_DAYS` would require a longer wait: [6](#0-5) [7](#0-6) 

This mirrors the reported pattern exactly: `announceBackstopLpWithdraw()` locks in a schedule based on the cooldown value active at call time, and a subsequent increase of the cooldown parameter does not retroactively re-arm already-scheduled timers, allowing early unlock relative to the newly-intended cooldown.

### Impact Explanation
Any account holder (or a smart contract calling `unfreezeBalanceV2`) can pre-emptively unfreeze funds while `UNFREEZE_DELAY_DAYS` is low, locking in a short unlock time. If the committee later raises `UNFREEZE_DELAY_DAYS` to enforce a longer security/cooldown window (e.g., in response to a security incident or to slow down large-scale resource churn), users who unfroze earlier can withdraw immediately at the old, shorter unlock time, defeating the purpose of the parameter increase. This does not directly steal others' funds, but it undermines an economic-security/governance control on resource withdrawal timing, which can matter for network-stability assumptions tied to `UNFREEZE_DELAY_DAYS` (e.g., anti-flash-unfreeze protections).

### Likelihood Explanation
Likelihood is moderate: it requires (a) a change to `UNFREEZE_DELAY_DAYS` via a passed committee proposal, and (b) users acting opportunistically by unfreezing in advance of an anticipated parameter increase. This is plausible and low-cost for any account, and does not require any privileged access — it's a normal `UnfreezeBalanceV2Contract` transaction or TVM `unfreezeBalanceV2` call available to any user/contract.

### Recommendation
When computing the applicable cooldown for a scheduled unfreeze request, either (a) always use the maximum of the parameter value at schedule time and at withdrawal time, or (b) re-validate/re-compute the unlock time for pending `UnFreezeV2` entries whenever `UNFREEZE_DELAY_DAYS` changes, or (c) disallow the parameter from being effectively bypassed by storing the parameter version alongside each entry and enforcing the larger of "then" vs "now" delay at withdrawal time in `WithdrawExpireUnfreezeActuator`/`WithdrawExpireUnfreezeProcessor`.

### Proof of Concept
1. `UNFREEZE_DELAY_DAYS` is set to 1 day (or 0, permitted range needs checking) via governance.
2. Account A calls `UnfreezeBalanceV2Contract` (or a contract calls `unfreezeBalanceV2`) to unfreeze BANDWIDTH; `calcUnfreezeExpireTime` stores `unfreezeExpireTime = now + 1 day`.
3. Committee passes a proposal raising `UNFREEZE_DELAY_DAYS` to 14 days via `ProposalService.process` (case `UNFREEZE_DELAY_DAYS`), intending to slow down all future/pending unfreezes.
4. After 1 day (well before the new 14-day cooldown would allow), Account A calls `WithdrawExpireUnfreezeContract`/`withdrawExpireUnfreeze()`; `getTotalWithdrawUnfreeze`/`getTotalWithdrawList` only compares `unfreezeExpireTime <= now`, so the funds are released immediately, bypassing the newly-enforced 14-day cooldown.

  public long execute(UnfreezeBalanceV2Param param, Repository repo) {
    byte[] ownerAddress = param.getOwnerAddress();
    long unfreezeBalance = param.getUnfreezeBalance();
    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();

    long unfreezeExpireBalance = this.unfreezeExpire(accountCapsule, now);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    long expireTime = this.calcUnfreezeExpireTime(now, repo);
    accountCapsule.addUnfrozenV2List(param.getResourceType(), unfreezeBalance, expireTime);

    this.updateTotalResourceWeight(accountCapsule, param.getResourceType(), unfreezeBalance, repo);
    this.updateVote(accountCapsule, param.getResourceType(), ownerAddress, repo);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && !accountCapsule.oldTronPowerIsInvalid()) {
      accountCapsule.invalidateOldTronPower();
    }

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return unfreezeExpireBalance;
  }

  private long getTotalWithdrawUnfreeze(List<Protocol.Account.UnFreezeV2> unfrozenV2List, long now) {
    return getTotalWithdrawList(unfrozenV2List, now).stream()
        .mapToLong(Protocol.Account.UnFreezeV2::getUnfreezeAmount).sum();
  }

  private List<Protocol.Account.UnFreezeV2> getTotalWithdrawList(List<Protocol.Account.UnFreezeV2> unfrozenV2List, long now) {
    return unfrozenV2List.stream().filter(unfrozenV2 -> unfrozenV2.getUnfreezeExpireTime() <= now)
        .collect(Collectors.toList());
  }

  public long execute(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = ownerCapsule.getInstance().getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze <= 0) {
      return 0;
    }
    ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
        .setBalance(ownerCapsule.getBalance() + totalWithdrawUnfreeze)
        .build());
    List<Protocol.Account.UnFreezeV2> newUnFreezeList = getRemainWithdrawList(unfrozenV2List, now);
    ownerCapsule.clearUnfrozenV2();
    ownerCapsule.addAllUnfrozenV2(newUnFreezeList);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    return totalWithdrawUnfreeze;
  }
