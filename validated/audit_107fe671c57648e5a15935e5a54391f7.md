### Title
Missing Slippage/Minimum-Output Protection in `ExchangeWithdrawContract` Causes Silent Fund Loss on Pool Ratio Changes - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` computes the proportional "another token" payout from the current bancor-relay-exchange pool ratio and pays it out with no minimum-acceptable-output parameter. Unlike `ExchangeTransactionContract`, which carries an `expected` field used to enforce a minimum received amount, `ExchangeWithdrawContract` (and `ExchangeInjectContract`) has no such field, so a withdrawer/injector has zero on-chain slippage protection and receives whatever ratio the pool has at execution time.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` reads `firstTokenBalance`/`secondTokenBalance` from the exchange pair and computes `anotherTokenQuant` proportionally: [1](#0-0) 
This same ratio-based computation is independently redone in `execute()` against the exchange pool state read at execution time: [2](#0-1) 
Because `validate()` and `execute()` each re-fetch the `ExchangeCapsule` from the store independently, and because other transactions in the same block (e.g. `ExchangeTransactionActuator` trades, `ExchangeInjectActuator`/other `ExchangeWithdrawActuator` calls on the same `exchange_id`) can mutate `firstTokenBalance`/`secondTokenBalance` between the two reads, the payout ratio realized in `execute()` can differ from what was checked in `doValidate()`.

Critically, the protocol message itself provides no way for the caller to bound this risk. Compare the three exchange contracts: [3](#0-2) 
`ExchangeTransactionContract` has an `expected` field that `ExchangeTransactionActuator.doValidate()` enforces (`anotherTokenQuant < tokenExpected` rejects the transaction): [4](#0-3) 
But `ExchangeWithdrawContract` has no equivalent `expected`/minimum-output field, so there is no way to guard the withdraw against an unfavorable pool ratio shift — the actuator simply pays out whatever the formula yields at execution time. This is the same bug class as the reported ZetaChain issue: an internally-computed exchange amount from a pool/AMM-like ratio is used to move funds with no caller-supplied slippage bound, so any ratio movement between quote-time and execution-time is silently absorbed by the user.

### Impact Explanation
An exchange creator (the only account authorized to withdraw, per the creator check) who submits an `ExchangeWithdrawContract` can receive a materially different `anotherTokenQuant` payout than intended if the pool ratio shifts due to interleaving transactions on the same `exchange_id` within the same block (e.g., a large `ExchangeTransactionActuator` trade or another withdrawal/injection). Because there is no `expected` field to enforce a floor, the withdrawal executes and finalizes regardless of how unfavorable the realized ratio is, resulting in permanent loss of expected value with no on-chain recourse. This matches the "leak of value" classification from the referenced report.

### Likelihood Explanation
Reachable via a standard broadcast `ExchangeWithdrawContract` transaction from any account that created an exchange pair — no privileged access is required. The precondition (pool ratio changing between validate-time expectations and execute-time realization) requires other transactions touching the same `exchange_id` to land in the same or an adjacent block, which is plausible for actively-traded TRC10 exchange pairs, especially since block producers can order transactions.

### Recommendation
Add a minimum-acceptable-output field (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeWithdrawContract` (and `ExchangeInjectContract`), and enforce it in `ExchangeWithdrawActuator.execute()`/`doValidate()` by rejecting the transaction if the computed `anotherTokenQuant` at execution time falls below the caller-specified minimum.

### Proof of Concept
1. Account A creates an exchange pair via `ExchangeCreateContract` and is its creator.
2. Account A submits `ExchangeWithdrawContract` for `tokenQuant` of `firstTokenID`, expecting `anotherTokenQuant` computed from the pool ratio observed at submission time (no `expected`/minimum field exists to protect this expectation).
3. Before A's transaction executes, another transaction (e.g., `ExchangeTransactionActuator` trade against the same `exchange_id`) shifts `firstTokenBalance`/`secondTokenBalance` within the same block.
4. `ExchangeWithdrawActuator.execute()` recomputes `anotherTokenQuant` from the now-shifted balances (lines 74-89 in `ExchangeWithdrawActuator.java`) and pays out that value unconditionally — there is no field in `ExchangeWithdrawContract` (see `exchange_contract.proto` lines 24-29) that would let A require a minimum payout, so the withdrawal completes with a worse-than-expected result and no error is raised.
