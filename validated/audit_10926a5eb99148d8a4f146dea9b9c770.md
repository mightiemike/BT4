Confirmed: in the Starknet OS Cairo program, `execute_call_contract` (modern, `syscall_impls.cairo:191-194`) explicitly rejects any `call_contract` targeting the `__execute__` selector, but `execute_library_call` in the same file has no equivalent check. This mirrors the report's bug class exactly: an authorization/restriction guard is enforced on one reachable code path (the "guild-level" analog: `call_contract`) but not on a sibling path that reaches the same protected resource (the "channel-level" analog: `library_call`), letting an unprivileged caller bypass the restriction.

### Title
Missing `__execute__` entry-point restriction on the `library_call` syscall bypasses the direct-execute-call guard - (File: `crates/blockifier/src/execution/syscalls/hint_processor.rs`, `crates/blockifier/src/execution/native/syscall_handler.rs`, `crates/apollo_starknet_os_program/.../execution/syscall_impls.cairo`)

### Summary
The `block_direct_execute_call` protocol rule is meant to make the `__execute__` entry point unreachable through any syscall — it must only ever run as the top-level call driven by the OS/transaction flow. This is enforced for the `call_contract` syscall (and `meta_tx_v0` has its own dedicated, controlled path to `__execute__`), but the `library_call` syscall performs no equivalent selector check in blockifier or in the Starknet OS Cairo program, allowing any contract to invoke a target class's `__execute__` code via `library_call`.

### Finding Description
`call_contract` explicitly blocks the `__execute__` selector: [1](#0-0) 
which is invoked from the native and CASM `call_contract` syscall handlers: [2](#0-1) 
and from the deprecated syscall's `call_contract`: [3](#0-2) 

The Starknet OS Cairo program mirrors this for `call_contract` in both the Cairo1 (`syscall_impls.cairo`) and Cairo0/deprecated paths: [4](#0-3) [5](#0-4) 

However, `library_call` (which loads an arbitrary class's code and executes it via `CallType::Delegate`, keeping the caller's own `storage_address`/`caller_address`) performs no such selector check anywhere in the stack:
- blockifier CASM handler: [6](#0-5) 
- blockifier native handler: [7](#0-6) 
- deprecated syscalls: [8](#0-7) 
- Starknet OS Cairo program: [9](#0-8) 
- Starknet OS deprecated Cairo0 flow: [10](#0-9) 

The dedicated tests and versioned-constant flag `block_direct_execute_call` exist specifically to guarantee `__execute__` is unreachable outside the top-level transaction flow: [11](#0-10) [12](#0-11) [13](#0-12) 

None of these tests exercise `library_call` with the `__execute__` selector, confirming the guard is not applied on that path.

### Impact Explanation
Because the guard is missing consistently in both blockifier execution and the Starknet OS re-execution (Cairo program), there is no honest-node divergence — both sides agree that `library_call` with the `__execute__` selector succeeds. This means the protocol invariant "`__execute__` can only be reached as the top-level transaction entry point" is violated by design in a reachable syscall path from ordinary invoke transactions. Any contract can, through `library_call`, execute the `__execute__` code of an arbitrary declared class, running its logic against the caller's own storage/state and its own `caller_address`/execution context rather than through the controlled top-level flow (bypassing whatever assumptions the protocol/accounts make about `__execute__` only running once, with nonce/fee accounting already finalized, and never being re-entered via a syscall). This can enable unauthorized account actions/logic reuse within a contract's own storage that the protocol explicitly tries to prevent for `call_contract`, and could be leveraged against account contracts (or other) whose `__execute__` implementation assumes it is never invoked as a delegate/library call (e.g. it may skip caller checks specifically because it expects to run only as the top-level entry point).

### Likelihood Explanation
Trivially reachable: any account can submit a normal invoke transaction whose calldata drives a `library_call` syscall targeting a class hash of its choice with the `__execute__` selector, exactly as already demonstrated by existing test helpers (`test_library_call` in feature contracts). No special privileges, no operator/prover assumptions, and no p2p/network conditions are required — a single transaction sender triggers it.

### Recommendation
Add the same `maybe_block_direct_execute_call` (or equivalent selector check against `EXECUTE_ENTRY_POINT_NAME`/`EXECUTE_ENTRY_POINT_SELECTOR`) check to the `library_call` syscall implementations in blockifier (`hint_processor.rs`, `native/syscall_handler.rs`, deprecated `hint_processor.rs`) and to `execute_library_call` in both the Cairo1 and Cairo0 Starknet OS programs (`syscall_impls.cairo`, `deprecated_execute_syscalls.cairo`), mirroring exactly what `execute_call_contract`/`call_contract` already does, so `__execute__` is uniformly unreachable via any syscall.

### Proof of Concept
1. Declare/deploy a contract `A` whose class defines `__execute__` (e.g., any account class).
2. Deploy a caller contract `B` (or use any contract with a `library_call_syscall` wrapper such as `test_library_call` in the test contracts).
3. Submit an invoke transaction whose calldata drives `B` to call `library_call_syscall(class_hash_of_A, selector!("__execute__"), calldata)`.
4. Observe that, unlike an equivalent `call_contract_syscall(A, selector!("__execute__"), calldata)` call (which reverts with `Invalid argument` per `test_direct_execute_call`), the `library_call` invocation succeeds and executes `A`'s `__execute__` logic against `B`'s own storage/context, with both blockifier execution and the Starknet OS agreeing (no state root/consensus mismatch, but a bypass of the intended protocol restriction).
