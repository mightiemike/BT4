### Title
`replay_on_archive` verification ignores `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, letting corrupted checkpoint/proof roots pass replay-verify as valid - (File: `types/src/transaction/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the routine used by the `db-tool replay-on-archive` verifier (and by chunk executor code paths) to confirm that re-executed output matches the authenticated `TransactionInfo` pulled from a backup/archive, only checks status, gas, write-set hash (`state_change_hash`), and event root hash. It explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that carry the Sparse-Merkle/Jellyfish state root, hot-state root, and native-position state root into the transaction accumulator.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs` (lines ~2139-2204) is documented in-repo with its own admission of the gap: [1](#0-0) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
```

The function only asserts on status, gas, write-set hash, and event-root hash: [2](#0-1) 

`storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` re-executes archived transactions with `AptosVMBlockExecutor` and calls exactly this function to compare re-executed outputs against the `expected_txn_infos` loaded from the backup: [3](#0-2) 

Because `state_checkpoint_hash` (the JMT/SMT state root committed into `TransactionInfo` and thus into the transaction accumulator/ledger proof), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` are skipped, a divergence between locally-recomputed state roots and the authenticated `TransactionInfo` root stored in the backup/archive will not be flagged as a replay failure. The accumulator root itself is still whatever was persisted in the backup (unchanged), so this is not a live-consensus forgery, but it defeats the purpose of `replay_on_archive` as an integrity oracle: an operator (or automated CI) relying on this tool to detect a state-divergent bug (e.g., a bad protocol upgrade, a non-deterministic native extension, or corruption introduced in the position/hot-state subsystems noted elsewhere in this codebase) will get a false "PASS" even though the state root committed to the ledger accumulator does not match what correct VM execution actually produces.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... accepted as valid" and "hard-fork-only divergence during commit, replay... accepted as valid" invariants named in the state-integrity gate. `replay_on_archive` is the tool used to independently validate that historical execution results (and their proof-bearing `TransactionInfo`/state roots) are internally consistent; silently accepting a state-root mismatch means a real consensus-breaking divergence in the state/hot-state/position-state Merkle roots would go undetected until much later (e.g., during actual chain sync where a real full accumulator/state proof check would eventually catch it, or possibly never, if the bug were confined to non-verified replay tooling used for audits/monitoring). Given `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` are newer/optional features gated by feature flags, this comparator gap specifically undermines assurance for those new state-root commitments.

### Likelihood Explanation
The gap is unconditionally present whenever `replay_on_archive` is run (no attacker action needed) — it's a missing check, not a race or malicious-input trigger. However, this is a verification/auditing-tool defect rather than a live mainnet-execution or proof-verification defect: it does not let an adversary forge an accepted state proof at the protocol/consensus level, only lets a bug in state-root computation slip through this particular offline-verification pass. The severity is bounded by the fact that live proof verification (accumulator inclusion proofs, `TransactionInfoWithProof::verify`, JMT range-proof `add_chunk`/`verify_chunk`) is unaffected — those paths independently verify hashes against ledger-info signatures. Likelihood of exploitation as a "state corruption slips past all safety nets" scenario is Medium (it degrades one specific safety net), not High/Critical at the consensus layer itself.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally re-executed checkpoint output and `txn_info`, as the existing TODO comment prescribes, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1` + `HOT_STATE_ROOT_IN_TXN_INFO` (or `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) on a test chain and produce a backup that contains a `TransactionInfoV1` whose `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` is corrupted (or produced by a buggy alternate implementation that miscalculates the hot-state/position root while still producing byte-identical write sets and events).
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`) against that backup.
3. Observe that `execute_and_verify` → `ensure_match_transaction_info` returns `Ok(())` (no failed txn reported) despite the state/hot-state/position-state root mismatch, because those fields are never compared: [4](#0-3) 

Note: I could not fully verify how the corrupted `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` would be introduced in the first place (e.g., whether an independent bug in `DoStateCheckpoint`/`ProvablePositionStateSummary` construction, referenced in `execution/executor/src/chunk_executor/mod.rs` lines 380-413, could realistically diverge without also breaking the write-set/event comparisons) — this would need a background agent with full build/test access to construct a concrete failing scenario end-to-end.
