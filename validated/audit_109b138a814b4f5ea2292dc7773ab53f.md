### Title
Missing slippage control in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` allows front-run/sandwich loss of pooled tokens - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's on-chain Bancor-style token-exchange feature computes the paired-token amount to be injected into or withdrawn from a liquidity pool (`ExchangeCapsule`) purely from the pool's live token ratio at execution time, with no user-supplied minimum/maximum bound. This is the same bug class described in the external report for `RewardPoolManager.depositIntoRewardPool()`/`withdrawFromRewardPool()`: a deposit/withdraw operation whose exchange rate is fixed at execution time is exploitable via front-running, because the actor cannot express "do not exceed this much slippage."

### Finding Description
`ExchangeInjectActuator.execute()` calculates `anotherTokenQuant` (the amount of the paired token consumed) directly from the current on-chain pool balances at execution time: [2](#0-1) 
The corresponding `ExchangeInjectContract` protobuf message only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/bound field to cap `anotherTokenQuant`.

Symmetrically, `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` (the amount of paired token returned) the same way from live pool ratios, and `ExchangeWithdrawContract` also has no bound field: [3](#0-2) 

Notably, the codebase already demonstrates awareness of this exact bug class: `ExchangeTransactionContract` (regular buy/sell against the pool) does carry an `expected` field, and `ExchangeTransactionActuator.doValidate()` explicitly rejects the transaction if the computed output is less than the caller-specified minimum: [4](#0-3) 
This slippage-protection mechanism was never applied to `ExchangeInjectContract`/`ExchangeWithdrawContract`, even though both mutate the pool ratio and compute a counter-amount exactly like the transaction contract does.

The only actor-eligibility check on inject/withdraw is that the caller must be the exchange's `creator_address`: [5](#0-4) [6](#0-5) 
This "creator" role is not a privileged/governance role — anyone can call the permissionless `ExchangeCreateActuator` to create a pool and become its creator by simply paying the creation fee and depositing initial liquidity: [1](#0-0) 
so this is functionally equivalent to an ordinary unprivileged DeFi user, matching the report's characterization of the `veALCX`-restricted caller as still an ordinary/unprivileged actor with respect to reward-pool share pricing.

### Impact Explanation
Because both `Inject` and `Withdraw` transactions are broadcast to the mempool before being packed into a block, another party (including a block-producing witness) can observe a pending inject/withdraw transaction and submit their own `ExchangeTransactionContract` (buy/sell) ahead of it in the same block to shift the pool ratio, then optionally submit a reverse trade after. This sandwiches the pool creator's inject/withdraw and causes them to receive/lock a worse counter-token amount than intended — a direct value-extraction vector against a fully unprivileged, permissionless on-chain AMM feature, matching "Theft of unclaimed yield" / degraded promised-return impact from the source report.

### Likelihood Explanation
Any account can create an exchange pool and later call inject/withdraw, and TRON's Solidity Node-observable pending-transaction pool combined with the deterministic constant-ratio formula make the manipulated-ratio front-run straightforward to construct — no special privilege or contract flaw beyond the missing bound check is required.

### Proof of Concept
1. Attacker/creator observes their own or a third party's pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction targeting exchange pair `X`.
2. Attacker submits an `ExchangeTransactionContract` trade against pair `X` with high priority/fee to shift `firstTokenBalance`/`secondTokenBalance` before the inject/withdraw executes.
3. The inject/withdraw executes using the now-skewed ratio in `ExchangeInjectActuator.execute()` / `ExchangeWithdrawActuator.execute()`, producing an `anotherTokenQuant` far from what the creator expected, with no `expected`-style check to block it.
4. Attacker optionally reverses their trade, extracting the difference at the creator's expense.

### Recommendation
Add an `expected`/bound field (minimum acceptable `anotherTokenQuant` for inject, minimum acceptable `anotherTokenQuant` for withdraw, or a maximum, depending on direction) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` exactly as already done for `ExchangeTransactionActuator`.
