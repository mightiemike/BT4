### Title
SVM event listener accepts `Program data:` logs from any program in a gateway-invoking transaction as canonical gateway events - (`universalClient/chains/svm/event_listener.go`)

### Summary
The SVM event listener parses Solana transaction logs to produce the inbound/outbound observations that honest Universal Validators vote on. It iterates `tx.Meta.LogMessages` and dispatches any `Program data:` entry to `ParseEvent`, but it never attributes the log to the gateway program and `ParseEvent` has no program-ID parameter. [1](#0-0) [2](#0-1)  Because a transaction returned by `getSignaturesForAddress(gatewayAddr)` can contain instructions to many programs, an unprivileged attacker can stuff the transaction with an extra instruction to a malicious program that emits a forged `Program data:` log. [3](#0-2)  The listener treats that log as a real gateway event, stores it, and the confirmation/voting pipeline finalizes a forged observation, corrupting `UniversalTx` state and potentially causing unauthorized mints, executions, or loss of outbound funds.

### Finding Description
`processSignatureBatch` fetches every transaction whose signature list includes the gateway address and loops over all of its logs. [4](#0-3)  It builds a map from the 8-byte event discriminator (drawn from `gatewayMethods`) to the event type, so the discriminator alone decides which parser runs. [5](#0-4)  `ParseEvent` and the per-event parsers (`parseSendFundsEvent`, `parseOutboundObservationEvent`) decode the base64 payload after checking only the `Program data: ` prefix; none of them accept or verify the emitting program ID. [6](#0-5) [7](#0-6)  Consequently, any program in the same transaction can emit a log whose first 8 bytes match a known gateway discriminator and have the rest of the log interpreted as a valid `send_funds`, `finalize_universal_tx`, `revert_universal_tx`, or `funds_rescued` event.

### Impact Explanation
A forged inbound `send_funds` log creates a `store.Event` of type `Inbound` with attacker-controlled `sender`, `recipient`, `token`, and `amount`. [8](#0-7)  After the confirmer reaches the required slot depth, the event processor submits `MsgVoteInbound`; once the ballot passes, `x/uexecutor` executes the inbound, minting PRC20 representation or running the supplied payload. [9](#0-8)  A forged outbound `finalize_universal_tx` log creates an `OutboundEvent` with a chosen `txID`, `universalTxId`, and `gas_used`. [10](#0-9)  `VoteOutbound` canonicalizes the observed hash and, if the ballot reaches the 2/3 threshold, marks the `OutboundTx` as `OBSERVED` and calls `FinalizeOutbound`. [11](#0-10) [12](#0-11) [13](#0-12)  Because the gateway never actually executed the outbound, the user’s funds are not released and the success vote suppresses the refund path, producing permanent loss or freezing of the outbound amount. [14](#0-13)  This matches the allowed impact gate: forged inbound/outbound state accepted through user-reachable flows with honest validators, corruption of PRC20/native asset accounting, and unauthorized state transitions in universal execution.

### Likelihood Explanation
The attack requires only the ability to submit a Solana transaction that references the gateway program and a custom program. [3](#0-2)  The gateway address, event discriminators, and Borsh event layouts are public in chain config and in `event_parser.go`. [15](#0-14) [16](#0-15)  The attacker does not need a malicious UV, validator, relayer, or admin key. The malicious program can be invoked in the same successful transaction as a benign gateway instruction, so the fake log is cheap to produce and indistinguishable from a real event at the parsing layer.

### Recommendation
Track the active program ID while iterating `tx.Meta.LogMessages`. Only call `ParseEvent` for `Program data:` entries that occur between a `Program <gatewayAddr> invoke` log and its matching `Program <gatewayAddr> success` or `Program <gatewayAddr> fail` log. Alternatively, verify that the log was emitted by an instruction whose `program_id` equals the gateway address by inspecting `Message.Instructions` and inner instructions. If `ParseEvent` is kept program-agnostic, the caller must filter before dispatch.

### Proof of Concept
1. Attacker deploys a Solana program that logs `Program data: <base64(discriminator + crafted Borsh event)>`. [6](#0-5) 
2. Attacker submits a transaction with two instructions: (i) any instruction that references the Push gateway program, so the tx appears in `getSignaturesForAddress(gatewayAddr)`, and (ii) an instruction to the attacker program that emits a `send_funds` log with `recipient = attacker EVM address`, `amount = 1000`, and a valid token mint. [3](#0-2) 
3. The SVM `EventListener` fetches the tx, iterates `tx.Meta.LogMessages`, matches the discriminator, and calls `parseSendFundsEvent`, storing an `Inbound` event. [1](#0-0) [8](#0-7) 
4. After confirmations, the event processor submits `MsgVoteInbound`; honest UVs vote and the ballot passes. [9](#0-8) 
5. `x/uexecutor` executes the inbound, minting 1000 PRC20 tokens to the attacker even though no real deposit occurred on Solana.

Outbound variant:
1. Attacker reads a pending `OutboundTx` from Push Chain to obtain its `txID` and `universalTxId`. [14](#0-13) 
2. Attacker submits a gateway-invoking transaction whose malicious program emits a `finalize_universal_tx` log with those IDs and a plausible `gas_used`. [7](#0-6) 
3. The listener stores an `Outbound` event; the processor votes `MsgVoteOutbound`. [10](#0-9) 
4. The outbound ballot finalizes as success, `FinalizeOutbound` is called, and the user’s refund path is skipped because the outbound is marked `OBSERVED`. [12](#0-11) [13](#0-12)
