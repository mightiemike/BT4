### Title
Unbounded per-account delegation index list scanned linearly on every freeze/delegate call causes DoS - (File: `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`, `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`DelegatedResourceAccountIndexCapsule` stores an account's set of delegation counterparties in plain, unbounded protobuf repeated fields (`toAccounts`/`fromAccounts`), with no cap on size. Any unprivileged account can grow these lists without limit simply by broadcasting `FreezeBalanceContract` transactions that delegate resource to a large number of distinct receiver addresses, and every single delegation call performs a linear `List.contains()` scan over the growing list before appending, mirroring exactly the "unbounded Vec scanned on every insert/lookup" bug class described in the Swafe report.

### Finding Description
`FreezeBalanceActuator.delegateResource` (legacy delegation path, used when `DynamicPropertiesStore.supportAllowDelegateOptimization()` is false) fetches the owner's `DelegatedResourceAccountIndexCapsule`, reads `toAccountsList`, and checks membership with `contains()` before appending a new receiver address: [1](#0-0) 

The same pattern is repeated for the receiver's `fromAccountsList`. Both lists are plain `repeated` protobuf fields wrapped by `DelegatedResourceAccountIndexCapsule`, with no size limit anywhere in the capsule: [2](#0-1) 

`removeFromAccount`/`removeToAccount` (invoked from `UnfreezeBalanceActuator` when a delegation is fully withdrawn) also perform a linear `contains()` check followed by a full `ArrayList` copy and `remove()` scan, so cost grows with the number of distinct counterparties an account has ever delegated to/received from: [3](#0-2) 

Because `FreezeBalanceContract.calcFee()` returns `0` for this operation, and there is no cap on the number of distinct `receiverAddress` values a caller may target across repeated broadcasts, an attacker can grow their own `toAccountsList` (or an arbitrary victim's `fromAccountsList`, since the victim need not consent to receive delegated resource) to an arbitrary size at negligible cost. Each subsequent freeze/delegate/unfreeze operation touching that account then re-scans the full list, and `DelegatedResourceAccountIndexStore.convert()` — triggered lazily the first time the new delegation model touches an old index — iterates the entire `toList`/`fromList` in one pass: [4](#0-3) 

This is directly analogous to the Swafe `RecoveryStateV0.assoc: Vec<AssociationsV0>` issue: an unprivileged actor can unboundedly grow a per-account list via a public, low-cost operation (`add_association` vs. `FreezeBalanceContract` delegation), and every subsequent read/verify path (`initiate_recovery`/`verify_update` vs. `delegateResource`/`removeFromAccount`/`convert`) performs an O(n) scan over that same list.

### Impact Explanation
An attacker can inflate the `toAccountsList`/`fromAccountsList` of their own account (or a victim account, via the `fromAccounts` side which is populated purely by the sender's action) to a large size with many cheap `FreezeBalanceContract` transactions to distinct receiver addresses. Every future freeze, delegate, or unfreeze transaction touching that account incurs linear-time list scans and full-list rebuilds/serialization, increasing block processing time and stored state size for that account, and degrading throughput for legitimate operations on the account. Because `calcFee()` for this contract is zero, the attack has effectively no economic cost, and the affected list is a per-account column of the consensus-critical `AccountStore`/`DelegatedResourceAccountIndexStore`, so bloating it burdens every node that replays or serves this account's state.

### Likelihood Explanation
This is reachable purely by broadcasting ordinary `FreezeBalanceContract` transactions from an anonymous/unprivileged account signing with its own key — no elevated permission, malicious peer, or leaked key is required. The only precondition is that the legacy (`!supportAllowDelegateOptimization()`) code path be in effect; this is a live, in-tree code path, not test-only or deprecated dead code, and the cap of zero on distinct receivers/senders and zero fee make the attack trivially cheap to execute at scale.

### Recommendation
- Bound the number of distinct entries permitted in `toAccounts`/`fromAccounts` per account (e.g., reject further delegations once a fixed cap is reached, or require expiry/cleanup of stale entries before adding more).
- Replace the `List.contains()`/full-copy-and-remove idiom in `DelegatedResourceAccountIndexCapsule` with an indexed/keyed lookup structure so membership checks and removals are not O(n).
- Consider migrating fully off the legacy list-based index in favor of the already-existing prefix-keyed `delegate`/`unDelegate`/`delegateV2` scheme, which avoids storing an unbounded list per account.

### Proof of Concept
1. Disable/never enable `AllowDelegateOptimization` (or target a network state prior to that fork) so `FreezeBalanceActuator.delegateResource`'s legacy branch is active.
2. From an unprivileged account with sufficient TRX, repeatedly broadcast `FreezeBalanceContract` transactions with `resource=BANDWIDTH` (or `ENERGY`) and a distinct `receiverAddress` each time, each freezing a minimal balance.
3. Observe that `ownerIndexCapsule.getToAccountsList()` and each receiver's `fromAccountsList` grow without bound, and that each call performs a `contains()` scan over the current list before appending — see [5](#0-4) .
4. Measure increasing latency of subsequent `FreezeBalanceContract`/`UnfreezeBalanceContract` operations on the same account as the list grows, confirming linear-time degradation with no fee or size cap to stop it.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
