**Analysis:** `validateSessionToken` calls `api.session.decodeSessionToken(token, {checkAudience})` with `checkAudience` defaulting to `true` [1](#0-0) . Inside `decodeSessionToken`, `jose.jwtVerify` validates `exp`/`nbf` as part of JWT verification itself (with a 10-second clock tolerance), and any expired or not-yet-valid token throws `InvalidJwtError` before the function even reaches the `aud` check [2](#0-1) . The `aud !== config.apiKey` check is independent of `exp`/`nbf` validation — it is not "weakened" or "skipped" based on token expiry; rather, an expired/premature token fails validation entirely regardless of `aud`, and a valid (non-expired, activated) token still has `aud` checked against `apiKey` when `checkAudience` is `true` (the default in all callers found) [3](#0-2) . The existing test suite confirms both behaviors: expired/`nbf`-future tokens are rejected, and `aud` mismatch is only tolerated when a caller explicitly opts out via `checkAudience: false`, which is not the default and not attacker-controlled [4](#0-3) . No reachable path allows an attacker to submit an expired/not-yet-valid JWT that bypasses the `aud` check under default configuration.
