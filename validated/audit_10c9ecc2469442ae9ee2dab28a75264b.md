### Title
State-snapshot restore silently skips Merkle proof verification in `KvOnly` mode, allowing unverified key-value data to be committed to durable storage - ([File: storage/aptosdb/src/state_restore/mod.rs])

### Summary
`StateSnapshotRestore::add_chunk` dispatches on `restore_mode` to decide how a state-snapshot chunk is processed. In `Default` mode, every chunk is cryptographically verified against the `expected_root_hash` via `JellyfishMerkleRestore::verify_chunk` before it is written. In `KvOnly` mode, the exact same `SparseMerkleRangeProof` argument is accepted but **never checked** — the chunk is written straight to `state_kv_db` with no relationship established to `expected_root_hash`. This is used in production by the backup-restore coordinator to restore a "KV-only" snapshot from a `BackupStorage` (e.g. S3/GCS), which is a data source the report's threat model explicitly calls out as an in-scope "restore flow."

### Finding Description
`StateSnapshotRestore::add_chunk`: [1](#0-0) 

For `StateSnapshotRestoreMode::KvOnly`, the code path is:
```
StateSnapshotRestoreMode::KvOnly => {
    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
},
```
The `proof: SparseMerkleRangeProof` parameter passed by the caller is completely discarded — it is never passed to `tree_restore.verify_chunk`, unlike the `Default` and `TreeOnly` arms which do call `verify_chunk`/`add_chunk_impl` with the proof against `self.expected_root_hash`.

This mode is exercised in the backup restore coordinator: [2](#0-1) 

The manifest's overall root hash is checked once, at a coarse level, before any chunk is streamed: [3](#0-2) 

That check only proves that `manifest.root_hash` is the value attested to by a `TransactionInfoWithProof`/`LedgerInfoWithSignatures`. It does **not** prove that the individual `(key, value)` chunks subsequently streamed from `BackupStorage` and fed into `add_chunk` actually hash-reduce to that root — that binding is supposed to be established per-chunk by `SparseMerkleRangeProof::verify`, and that call is skipped entirely in `KvOnly` mode.

Consequently, if the backup storage medium (untrusted or compromised object storage, corrupted local file, or an operator-supplied manifest/chunk mismatch) supplies chunk contents that differ from what actually produces `manifest.root_hash`, the KV-only restore path accepts and durably commits that data into `state_kv_db` with **no cryptographic check that it matches the proven root**. The `Default` and `TreeOnly` modes on the same struct show this proof binding is a first-class invariant elsewhere in the same file — it is simply omitted for `KvOnly`.

### Impact Explanation
This is a genuine proof/commitment-integrity gap: authenticated backup data is supposed to be bound to a Merkle root proven against a ledger info, but the `KvOnly` restore path breaks that binding. A node restored via `KvOnly` (used by `RestoreCoordinator::run_impl` for any "phase 1" KV snapshot restore prior to the tree snapshot) can end up with `state_kv_db` entries that were never checked against any proof, i.e., a "committed state that differs from the correct/attested result" per the impact gate. Because subsequent transaction replay only mutates keys that are actually touched by replayed transactions, any untouched keys silently retain the unverified/corrupted values forever, producing a durably wrong ledger view on that node (wrong balances/resources returned by that node's APIs, or divergence from consensus if this node participates in validation).

### Likelihood Explanation
Likelihood is limited to operators/tools performing DB bootstrap from a state-snapshot backup using the `KvOnly` mode (this is not on the hot execution/consensus path and requires that the backup storage be attacker-influenced or corrupted independently of the height-committed proof). The requirement of a compromised/corrupted backup source keeps likelihood "low," similar to the zkSync finding's own assessment ("high impact... but low probability").

### Recommendation
In `StateSnapshotRestore::add_chunk`, always verify the chunk's `SparseMerkleRangeProof` against `expected_root_hash` before writing to `state_kv_db`, even in `KvOnly` mode (e.g., temporarily maintain minimal accumulator state needed for verification, or require `KvOnly` restores to be paired with an already-verified tree so the same proof can be validated). At minimum, do not silently drop the caller-supplied `proof` argument — either use it or make the API refuse to compile/run without a companion tree-verification step.

### Proof of Concept
1. Start a `KvOnly` restore for a manifest with `expected_root_hash = R` (attested by a valid `TransactionInfoWithProof`).
2. Call `add_chunk(chunk, forged_or_mismatched_proof)` with `chunk` containing key/value pairs that do **not** actually hash into `R` (e.g., tampered values from a compromised backup store).
3. Observe: `StateSnapshotRestore::add_chunk` (`storage/aptosdb/src/state_restore/mod.rs:213-253`) routes to the `KvOnly` arm, calls only `kv_restore.add_chunk(chunk)`, and returns `Ok(())` — the tampered data is written to `state_kv_db` with no error, despite never being validated against `R`.

    fn add_chunk(&mut self, chunk: Vec<(K, V)>, proof: SparseMerkleRangeProof) -> Result<()> {
        match self.restore_mode {
            StateSnapshotRestoreMode::KvOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            },
            StateSnapshotRestoreMode::TreeOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_add_chunk"]);
                self.tree_restore
                    .lock()
                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks
                // from min(kv_progress, tree_progress)) would land bytes in (kv_progress,
                // tree_progress] that the tree side skips and therefore does not re-verify.
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_verify_chunk"]);
                    self.tree_restore
                        .lock()
                        .as_mut()
                        .unwrap()
                        .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;
                }
            },
        }

        Ok(())
    }
