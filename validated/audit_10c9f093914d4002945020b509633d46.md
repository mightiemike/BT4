### Title
`ensure_match_transaction_info` skips checkpoint-hash validation during chunk-replay verification, letting a corrupted/omitted state root be accepted as a valid replay - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole per-transaction integrity check used by the chunk executor's `verify_execution` path (used for state-sync/backup replay verification, e.g. `replay_on_archive`, restore verify, and `aptos-debugger`). It checks status, gas, write-set hash (`state_change_hash`), and event root hash, but it explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` carried in `TransactionInfo`. [1](#0-0) 

### Finding Description
`verify_execution` in the chunk executor re-executes a batch of transactions via the VM and, for every version, calls `txn_out.ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))` to confirm the freshly computed `TransactionOutput` matches the historical/authenticated `TransactionInfo` before accepting it during replay: [2](#0-1) 

Inside `ensure_match_transaction_info`, only `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash` are compared. The function's own comment admits the state/hot-state checkpoint hash and the newly introduced `position_state_checkpoint_hash` are intentionally left unchecked pending a future feature flag `COMPUTE_TRADING_NATIVE_STATE_ROOTS`: [3](#0-2) 

Because a state checkpoint hash is the Sparse-Merkle-Tree root summarizing the entire world state at a checkpoint boundary (periodically, e.g. per block), this is the one field that actually authenticates *global* ledger state, as opposed to per-transaction write sets. Skipping it means: if a replayed/rebuilt state tree differs from the originally-committed one (due to a bug in state-tree construction, hot-state logic, or the new `position_state_checkpoint_hash` mechanism), `ensure_match_transaction_info` will still return `Ok(())` as long as per-transaction write-set/event hashes match, which they can even when the aggregated Merkle root diverges (e.g., if the SMT batching/leaf-hotness handling produces a different root while individual writes are unchanged).

The comment explicitly documents that `db-tool`'s `replay_on_archive` (backed by this same code path via `TransactionReplayer`/`ChunkExecutor`) can therefore report success even when "the authenticated position state root diverges from local execution."

### Impact Explanation
This breaks the proof/commitment invariant that authenticated checkpoint roots (state root, hot-state root, position-state root) must be independently re-derivable and verified during replay — not merely inferred from individual write-set hashes. A silent divergence here means:
- Backup/restore replay verification (`storage/backup/backup-cli`, which calls `enqueue_chunks`/`verify_execution_mode.should_verify()`) and `replay_on_archive` tooling can certify a chain of blocks as correctly replayed while the actual world-state root at checkpoints is wrong, undermining confidence in disaster-recovery and forensic/audit tooling built on this verification.
- Because the gap is scoped to be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`", any interim window where this new position/hot-state checkpoint mechanism is exercised without the corresponding validation is a real detection gap for state-commitment corruption, which the Proof and Storage Pivots section calls out directly ("Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state").

This is a detection/verification gap rather than a live consensus-safety bypass (mainnet consensus does not currently invoke `ensure_match_transaction_info`), so its severity is bounded to replay/restore-verification tooling correctness rather than direct fork-inducing consensus divergence.

### Likelihood Explanation
The gap is unconditionally present in current code — it is not behind a feature flag itself, only the reason for closing it is tied to a flag. Any bug in hot-state/position-state root computation logic (a new, actively-developed area given the surrounding `TODO(trading-native)` comments) would go undetected by every call site of `ensure_match_transaction_info` (`chunk_executor::verify_execution`, `aptos-debugger`, CLI commands), making this a realistic and currently-live blind spot rather than a purely theoretical one.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on the `TransactionInfo` variant) against the recomputed/expected checkpoint roots from the replayed `TransactionOutput`/execution output, rather than deferring this to a future flag-gated change.

### Proof of Concept
Not applicable as an exploit PoC — this is a verification-logic gap, not an attacker-triggerable state mutation. The code-level proof is the explicit TODO comment combined with the actual comparison list in `ensure_match_transaction_info` (lines 2139–2204) versus its real call site in `verify_execution` (lines 684–707), which never receives/checks checkpoint hashes.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
