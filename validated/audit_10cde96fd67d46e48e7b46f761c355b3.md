### Title
Unsorted append to `energyPriceHistory`/`bandwidthPriceHistory`/`memoFeeHistory` breaks the sorted-order assumption used by `parseEnergyFee` - (File: framework/src/main/java/org/tron/core/consensus/ProposalService.java)

### Summary
`ProposalService.process()` appends a new `expirationTime:value` pair onto the `ENERGY_FEE`/`TRANSACTION_FEE`/`MEMO_FEE` price-history strings via plain string concatenation each time a corresponding proposal is approved and processed, without ever re-sorting the resulting sequence. [1](#0-0)  This is the same bug class described in the external report: a value is appended (`push_back`/string concat) to a sequence that a downstream reader implicitly assumes is sorted, without any step that guarantees the sequence stays sorted.

### Finding Description
The one place that legitimately builds this history in a guaranteed-sorted order is `ProposalStore.getSpecifiedProposals`, which explicitly comments "return in asc order by expired time" and sorts by `getExpirationTime()` before use in `EnergyPriceHistoryLoader.parseProposalsToStr()`. [2](#0-1) [3](#0-2) 

However, the runtime incremental-update path in `ProposalService.process()` for `ENERGY_FEE` (and analogously `TRANSACTION_FEE`/bandwidth and `MEMO_FEE`) simply does `history + "," + proposalCapsule.getExpirationTime() + ":" + entry.getValue()` and writes it back — it does not re-derive the string from a sorted proposal list, nor does it verify the new `expirationTime` is greater than the last stored entry. [1](#0-0) 

The reader, `JsonRpcApiUtil.parseEnergyFee(timestamp, energyPriceHistory)`, assumes the string is strictly ordered ascending by time: it scans from the last entry backward and returns the first (i.e. largest-time) entry whose `time < timestamp`. [4](#0-3)  If proposals are approved/processed in an order where a later-processed proposal has an earlier `expirationTime` than an already-appended entry (which is plausible since multiple proposals can be approved/finalized within the same or nearby maintenance cycles, and `expirationTime` is fixed at proposal-creation time rather than at approval-processing time), the resulting history string is no longer monotonically increasing. This is functionally identical to the reported `add_vote_ledger`/`checkpoint` flaw: an append-only sequence that a lookup routine assumes is sorted, with no code path enforcing that invariant at write time.

`Wallet.getEnergyFee(long timestamp)` is the consumer of this history and is documented as safe to call "after EnergyPriceHistoryLoader done," reflecting that its correctness depends entirely on the assumed sort order of this string. [5](#0-4) 

### Impact Explanation
An unsorted `energyPriceHistory` (or the analogous bandwidth/memo fee histories) can cause `parseEnergyFee` to return a stale or incorrect historical energy price for a given timestamp, since the backward-scan "first match" logic no longer finds the true nearest-preceding entry once ordering is violated. This corrupts any accounting/reporting path that relies on `getEnergyFee(timestamp)` to reconstruct the correct historical fee for a transaction, producing wrong values for callers of that API without any attacker action required — the state itself becomes internally inconsistent once two proposals are approved out of the expected time order.

### Likelihood Explanation
I could not fully verify, given available context, whether `ProposalController`/`Manager` invariably processes approved proposals in strictly ascending `expirationTime` order at maintenance time (the file `ProposalController.java` was not retrieved before the tool budget ran out). If proposal processing order is guaranteed monotonic by `expirationTime`, this specific append path might coincidentally stay sorted, and only the general design fragility (no explicit invariant enforcement, unlike `getSpecifiedProposals`) would remain a latent risk for future refactors. This uncertainty should be resolved before treating this as a confirmed, actively triggerable bug.

### Recommendation
Do not build the price-history strings by ad hoc concatenation in `ProposalService.process()`. Instead, either (a) always regenerate the history from `ProposalStore.getSpecifiedProposals()`, which already guarantees ascending order by `expirationTime`, or (b) explicitly validate/sort before writing, e.g., reject/re-sort if the new `expirationTime` is not greater than the last recorded entry's time, mirroring the recommended fix of sorting `vote_ledgers` after `push_back` in the source report.

### Proof of Concept
Conceptual reproduction (pending confirmation of `ProposalController`'s processing order):
1. Create Proposal A with a long voting/effective period so its `expirationTime` is far in the future, containing an `ENERGY_FEE` change.
2. Create Proposal B shortly after, with a shorter effective period so its `expirationTime` is earlier than Proposal A's, also containing an `ENERGY_FEE` change.
3. If both proposals get approved and processed such that A's `process()` call executes before B's (e.g., due to processing/iteration order rather than strict `expirationTime` order), the resulting `energyPriceHistory` string becomes `...,<A.expirationTime>:<priceA>,<B.expirationTime>:<priceB>` with `B.expirationTime < A.expirationTime`, breaking ascending order.
4. Subsequent calls to `Wallet.getEnergyFee(timestamp)` for timestamps between the two expiration times, via `JsonRpcApiUtil.parseEnergyFee`, will return an incorrect price because the backward-scan-for-first-match logic assumes monotonicity. [4](#0-3)

   * note: return in asc order by expired time

  public List<ProposalCapsule> getSpecifiedProposals(State state, long code) {
    return Streams.stream(iterator())
        .map(Map.Entry::getValue)
        .filter(proposalCapsule -> proposalCapsule.getState().equals(state))
        .filter(proposalCapsule -> proposalCapsule.getParameters().containsKey(code))
        .sorted(
            (ProposalCapsule a, ProposalCapsule b) -> a.getExpirationTime() > b.getExpirationTime()
                ? 1 : -1)
        .collect(Collectors.toList());
  }

  public static long parseEnergyFee(long timestamp, String energyPriceHistory) {
    String[] priceList = energyPriceHistory.split(",");

    for (int i = priceList.length - 1; i >= 0; i--) {
      String[] priceArray = priceList[i].split(":");
      long time = Long.parseLong(priceArray[0]);
      long price = Long.parseLong(priceArray[1]);
      if (timestamp > time) {
        return price;
      }
    }

    return -1;
  }
