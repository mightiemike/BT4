### Title
Stale per-block liquidity-index cache in `market.clar` is not invalidated when a vault's `socialize-debt` writes down `lindex` directly - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` caches each vault's `{index, lindex}` in the `index-cache-` map keyed only by `{timestamp: stacks-block-time, aid}` so that multiple operations within the same block can reuse a single accrual result instead of re-calling the vault [1](#0-0) . However, the vault's `socialize-debt` function mutates `lindex` directly — outside of the normal `accrue`/`next-liquidity-index` path that the cache is built from — to write down the liquidity index when bad debt is socialized [2](#0-1) . Because the cache is never invalidated or refreshed when `socialize-debt` runs, any subsequent transaction in the *same block* that hits the cache for that `aid` will read the pre-write-down (inflated) `lindex`, mispricing zToken collateral for unrelated users until the block timestamp changes.

### Finding Description
The market maintains a per-timestamp cache to avoid repeated cross-contract calls to vaults for interest-index / liquidity-index reads:

```clarity
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)               ;; cache HIT -> stale return
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [1](#0-0) 

The cache's implicit invariant is that a vault's `{index, lindex}` pair only changes when `vault-accrue` is called and block time advances. Collateral valuation for zTokens explicitly relies on this cache: `collateral-add` primes it before pricing newly-added zToken collateral ("Prime cache for new zToken collateral underlying if not already cached") [3](#0-2) , and debt notional valuation reads the cached `index` directly for pricing outstanding debt [4](#0-3) .

That invariant is broken by `socialize-debt`, which is called by the market (via `check-caller-auth`) to socialize bad debt after a liquidation leaves a borrower with no remaining collateral. It directly overwrites the vault's `lindex` with a reduced value to reflect the realized loss, bypassing `accrue`/`next-liquidity-index` entirely:

```clarity
(define-public (socialize-debt (scaled-amount uint))
  (let (...
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
    (try! (check-caller-auth))
    ...
    (var-set lindex new-lindex)
    ...
``` [2](#0-1) 

Because `market.clar`'s `index-cache-` map is keyed only on `stacks-block-time` and `aid`, and Clarity contract state persists across transactions within the same block, the sequence below is possible:

1. **Value bound (Tx 1, block N):** Any market operation for asset `USDC` (e.g. an unrelated `collateral-add`/`borrow`/health check) calls `accrue-and-cache(USDC)`, which misses the cache, calls `vault-accrue`, and stores the fresh `{index, lindex}` under key `{timestamp: T, aid: USDC}` [5](#0-4) .
2. **Event that invalidates it (Tx 2, same block N):** A liquidation of a different borrower leaves them with no remaining collateral; the market's liquidation logic socializes the residual bad debt by calling the USDC vault's `socialize-debt`, which writes a lower `lindex` directly into vault state [6](#0-5) . This mutation never touches `market.clar`'s `index-cache-` map.
3. **Later use (Tx 3, same block N):** A third, unrelated user holding `zUSDC` collateral calls `collateral-add`/`borrow`/any health-check path. `accrue-and-cache(USDC)` is invoked again with the same key `{timestamp: T, aid: USDC}`, which is still present from Tx 1, so the cache **hits** and returns the old, higher `lindex` — not the value just written by `socialize-debt` in Tx 2 [7](#0-6) .

Because zToken collateral pricing depends on this liquidity index (the cache is explicitly primed before pricing zToken collateral additions, and the docs describe zToken oracle pricing as index-driven) [8](#0-7) , the user's zUSDC collateral is valued as if the vault still held the assets that were just written off by `socialize-debt`.

Under Clarity's evaluation model this interleaving is possible because: (a) `stacks-block-time` is constant for the whole block, making the cache key identical across all transactions in that block; (b) `index-cache-` entries persist in contract state across transactions within a block; (c) `socialize-debt` is a distinct public entry point from `accrue`/`accrue-and-cache` and has no code path that clears or updates `index-cache-`.

### Impact Explanation
This is a temporary freezing/mispricing-of-funds and insolvency risk: a stale, inflated `lindex` overstates the redeemable value of zUSDC (or any zToken) collateral for the remainder of the block after a socialize-debt event. Users can use this inflated valuation to pass health checks for new borrows or collateral additions against value the protocol no longer actually holds (the corresponding assets were written off in the bad-debt socialization), pushing the protocol further toward insolvency and enabling users to extract more borrowing capacity than their real collateral backs. This lands in the **temporary freezing of funds / protocol insolvency** category described by the Elytra report's core bug class (mispriced share/receipt token from an un-synced allocation/value tracker).

### Likelihood Explanation
Likelihood is moderate: it requires (1) a liquidation event that triggers bad-debt socialization for a given asset's vault, and (2) at least one other market interaction touching the same asset's cache within the same block, both before and after the socialization call. Bad-debt socialization is intended to be rare, but on a busy chain with multiple transactions per block touching the same asset (a common vault like USDC/USDH), the ordering needed to trigger this is easily achievable without any special privilege — it only requires normal transaction ordering within a block, not attacker-controlled timing tricks.

### Recommendation
Invalidate or refresh the `index-cache-` entry for an asset whenever its vault's `lindex`/`index` is mutated outside the normal `accrue` path. Concretely:
- Have `socialize-debt` (and any other vault function that mutates `lindex`/`index` directly) call back into the market to update/clear `index-cache-` for that `aid` at the current `stacks-block-time`, or
- Have `market.clar` re-fetch/re-cache the index whenever it calls `socialize-debt`, storing the returned fresh value in `index-cache-` immediately after the vault call, so no later transaction in the same block can read a pre-socialization value.

### Proof of Concept
1. Block N, Tx 1: User A calls `collateral-add` with `zUSDC` for an unrelated deposit; `accrue-and-cache(USDC)` misses, calls `vault-accrue`, and caches `{timestamp: T, aid: USDC} -> {index: I0, lindex: L0}`.
2. Block N, Tx 2: Liquidator liquidates Borrower B who has USDC bad debt and zero remaining collateral; market's liquidation flow calls the USDC vault's `socialize-debt`, which sets `lindex` to `L1 < L0` on-chain in the vault, but does not touch `index-cache-`.
3. Block N, Tx 3: User C, holding `zUSDC` collateral, calls `borrow` for another asset; `accrue-and-cache(USDC)` is invoked again with the same key `{timestamp: T, aid: USDC}` and returns the cached `L0` (stale), not `L1`. User C's zUSDC collateral is valued using `L0`, letting a borrow through that would fail a health check computed with the correct, lower `L1`.

Note: the exact call site inside the liquidation function that invokes vault `socialize-debt` was inferred from the "bad-debt-socialized"/`socialize-debt` naming and `check-caller-auth` guard seen in the vault contract and liquidation flow context; full end-to-end line-level confirmation of the liquidation → `socialize-debt` call wiring in `market.clar` was not completely retrieved due to file-size truncation, but the core mechanism — an unconditioned cache keyed only by block timestamp, and a vault entry point (`socialize-debt`) that mutates the cached value's source without notifying the cache — is directly confirmed in the cited code.
