### Title
Missing bounds validation on `EXCHANGE_CREATE_FEE` (and `ENERGY_FEE`) governance parameters allows negative-fee-driven TRX inflation - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator` is the java-tron analog of the reported `resolveReparam`/`Parameterizer` re-parameterization flow: witnesses vote on chain parameters, and once a proposal passes, `ProposalService.process` writes the new value into `DynamicPropertiesStore` unconditionally for parameters that lack a value check. Two market-relevant parameters, `EXCHANGE_CREATE_FEE` and `ENERGY_FEE`, fall into a switch branch that performs no sanity/range check at all, exactly the missing-invariant bug class described in the report (unchecked SPREAD/STAKE-style parameters).

### Finding Description
`ProposalUtil.validator` validates almost every chain parameter with an explicit `[min, max]` range, but `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` are grouped into a case that does nothing but `break`: [1](#0-0) 

Once such a proposal collects enough witness approvals, `ProposalController.processProposal` calls `setDynamicParameters` → `ProposalService.process`, which persists the raw value straight into `DynamicPropertiesStore` with no additional clamping: [2](#0-1) [3](#0-2) 

`getExchangeCreateFee()` simply returns whatever `long` was stored, including negative values, with no lower-bound guard: [4](#0-3) 

`ExchangeCreateActuator.validate()` uses this fee only as a lower-bound balance check (`getBalance() < calcFee()`), which is trivially satisfied when `calcFee()` is negative: [5](#0-4) 

`ExchangeCreateActuator.execute()` then does `newBalance = subtractExact(accountCapsule.getBalance(), fee)`; subtracting a negative fee is equivalent to *adding* `|fee|` to the caller's balance, and the "fee" is finally sent to the black-hole/burn path rather than debited from the user: [6](#0-5) [7](#0-6) 

This mirrors the report's Scenario 2 (manipulating `price_floor`/`spread`/`list_reward` to gain unfair economic advantage) — here the analogous unchecked parameter is `EXCHANGE_CREATE_FEE`, and the impact is direct TRX creation for any unprivileged account that submits `ExchangeCreateContract` transactions after the malicious proposal passes. `ENERGY_FEE`, which prices TVM energy consumption for every contract call, suffers the same missing-bounds defect and could similarly be driven to an extreme/invalid value to distort resource pricing economy-wide.

### Impact Explanation
If a witness majority (or colluding witnesses reaching the approval threshold) passes a proposal setting `EXCHANGE_CREATE_FEE` to a negative value, every subsequent unprivileged user who calls `ExchangeCreateContract` receives free TRX equal to `|fee|` per call, an unbounded, repeatable TRX-supply inflation/accounting-integrity break. This is a concrete accounting/settlement impact, not merely theoretical, since the actuator code path directly performs `subtractExact(balance, fee)` with an attacker-influenced sign.

### Likelihood Explanation
Exploitation requires a proposal to pass witness voting (the same "Madman"/collusion threat model as the original report — a well-resourced or colluding set of witnesses achieving `hasMostApprovals`). This is the same governance-abuse precondition assumed by the original finding, and is the intended java-tron on-chain governance path (`ProposalCreateActuator`/`ProposalApproveActuator`/`ProposalController`), not a privileged/internal-only code path. Once passed, exploitation by *any* unprivileged account is trivial and repeatable.

### Recommendation
Add explicit non-negative (and reasonable upper-bound) range checks for `EXCHANGE_CREATE_FEE` and `ENERGY_FEE` in `ProposalUtil.validator`, consistent with the other fee-style parameters (e.g., the `[0, LONG_VALUE]` pattern already used for `ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, etc.), and audit all other parameters funneled through the empty `break` branches for the same gap.

### Proof of Concept
1. A witness (or colluding witness set) submits `ProposalCreateContract` with parameter code `12` (`EXCHANGE_CREATE_FEE`) and value `-1_000_000_000` (i.e., -1000 TRX in sun).
2. `ProposalUtil.validator` reaches the `EXCHANGE_CREATE_FEE` case and does not reject the negative value (only `break;`), so `ProposalCreateActuator.validate()` succeeds.
3. Sufficient witnesses approve; `ProposalController.processProposal` → `ProposalService.process` stores `EXCHANGE_CREATE_FEE = -1_000_000_000` via `saveExchangeCreateFee`.
4. Any unprivileged account submits `ExchangeCreateContract`. `ExchangeCreateActuator.doValidate()`'s check `accountCapsule.getBalance() < calcFee()` is vacuously true-passing since `calcFee()` is negative.
5. `execute()` computes `newBalance = subtractExact(accountCapsule.getBalance(), fee)` = `balance + 1_000_000_000`, crediting the caller 1000 TRX per exchange-create call, repeatable indefinitely.
