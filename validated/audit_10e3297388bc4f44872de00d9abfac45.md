### Title
Escrowed PromiseYield deposit is permanently burnt when the yielding account self-deletes before resume/timeout - ([File: runtime/runtime/src/lib.rs])

### Summary
`promise_yield_create_with_id` lets a contract attach a NEAR deposit to the callback of a yielded promise; the deposit is deducted from the account's balance immediately at creation time, before the callback ever executes [1](#0-0) . The parked `PromiseYield` receipt (carrying that deposit as a `FunctionCallAction`) is stored in state keyed by `(receiver_id, data_id)` and is only executed later, either by an explicit `promise_yield_resume` or by the automatic timeout path `resolve_promise_yield_timeouts`, which synthesizes a `PromiseResume` receipt back to the very same account [2](#0-1) . Nothing in `action_delete_account`/`check_actor_permissions` blocks self-deletion while such a pending yield exists. Refund receipts (`predecessor_id == "system"`) can never implicitly re-create an account, and per the refunds specification, "if the execution of a refund fails, the refund amount is burnt" [3](#0-2) , and `implicit_creation_allowed` explicitly returns `false` for any account type when the receipt is a refund [4](#0-3) .

### Finding Description
An unprivileged transaction signer/contract can:
1. Call its own contract to invoke `promise_yield_create_with_id` with a non-zero `amount`. This immediately deducts `amount` from the account's balance (escrowing it for the eventual callback) [5](#0-4) , and the resulting `PromiseYield` receipt (holding the deposit action) is stored under `(account_id, data_id)` awaiting resume [6](#0-5) .
2. In a subsequent action (same or later transaction), call `DeleteAccount` on the same account, transferring its (now-reduced) remaining balance to a beneficiary. `check_actor_permissions`/`action_delete_account` have no check against outstanding `PromiseYieldReceipt`/`PromiseYieldStatus` entries for the account; the only listed constraint is zero locked stake [7](#0-6) . The account is removed from the trie while the escrowed deposit — already subtracted from `amount` — is not part of what is sent to the beneficiary.
3. When the yield resolves (either via the automatic timeout queue `resolve_promise_yield_timeouts`, which always fires eventually and cannot be permanently suppressed [8](#0-7) , or via an attempted resume), the runtime executes the parked `PromiseYield`/`PromiseResume` as an `ActionReceipt` addressed to the now-deleted account. `check_account_existence` rejects the `FunctionCall`+attached-deposit action because the receiver named account no longer exists and named accounts can never be implicitly created [9](#0-8) . This produces a failed receipt, which generates a deposit-refund receipt back to the (now nonexistent) `predecessor_id`.
4. That deposit-refund receipt is itself a `Transfer` action with `predecessor_id == "system"` targeting the deleted account. Because `is_refund` forces `implicit_creation_allowed` to `false` unconditionally [10](#0-9) , this second-level refund also fails with `AccountDoesNotExist`. Per the documented refund invariant, a refund receipt whose execution fails has its deposit **burnt** rather than refunded [3](#0-2) , and the runtime implementation folds a failed system-predecessor receipt's total deposit into `other_burnt_amount` [11](#0-10) .

The net effect: value that was legitimately owned by the account (deducted from its balance at yield-creation time) is neither returned to the beneficiary at deletion nor ever paid out to any callback, and ends up burnt/irrecoverably destroyed as `other_burnt_amount` — a state-transition-visible, permanent loss of funds directly analogous to the Hegic incident's "permanently locked funds in unexercised options," except here the mechanism is protocol-level burning rather than contract-level locking.

### Impact Explanation
This is a concrete, permanent value-destruction bug reachable purely by an unprivileged account performing two ordinary actions on itself (`FunctionCall` invoking yield-create-with-deposit, then `DeleteAccount`). No cross-account exploit or privileged access is required, and the loss is deterministic once the sequence is executed — it is not a timing race that can be avoided, since the automatic timeout queue guarantees the stale `PromiseYield`/`PromiseResume` eventually executes against the deleted account. The amount at risk is fully attacker/user-controlled (bounded only by the account's balance at yield-creation time), making this a Medium-severity fund-loss bug consistent with the Hegic "permanently locked/lost funds" bug class, though the near analog manifests as an on-chain burn rather than a contract-trapped balance.

### Likelihood Explanation
Likelihood is high for any account that combines yield/resume usage with self-deletion logic (e.g., an upgrade/migration/relayer contract that yields on an external callback and later tears itself down), and is trivially reproducible by a hostile actor purely to grief their own funds or to demonstrate unexpected token burning that affects total-supply accounting invariants checked by the balance checker. It requires only two ordinary, unprivileged actions and no adversarial timing beyond normal chunk/block progression, since the yield-timeout mechanism is fully automatic and cannot be starved indefinitely except by protocol-level compute/proof-size limits (which only delay, not prevent, the burn).

### Recommendation
Before allowing `DeleteAccount` to complete, check for outstanding `PromiseYieldReceipt`/`PromiseYieldStatus` entries keyed to the account (mirroring the existing zero-locked-stake check in `check_actor_permissions`) and reject deletion (or force resolution/refund of yields) while any are pending. Alternatively, when a `PromiseYield`/`PromiseResume` action receipt fails with `AccountDoesNotExist` because its receiver was self-deleted, route the deposit refund to the account's recorded beneficiary (or otherwise avoid a second-level system-refund failure) instead of allowing it to fall into the burn path.

### Proof of Concept
1. Deploy a contract on account `A` with a method that calls `promise_yield_create_with_id` attaching a deposit `d > 0` to its own callback (per the host-function tests) [5](#0-4) .
2. Submit a transaction from `A` invoking that method; observe `A`'s balance drop by `d` and a `PromiseYield` receipt stored in state [6](#0-5) .
3. Submit a second transaction from `A` performing `DeleteAccount { beneficiary_id: B }`; observe `A` is removed and `B` receives only `A`'s post-yield-creation balance (i.e., without `d`).
4. Advance blocks until `yield_timeout_length_in_blocks` elapses so `resolve_promise_yield_timeouts` synthesizes the `PromiseResume` for `A`'s stale yield [2](#0-1) .
5. Observe the resulting receipt execution fails with `AccountDoesNotExist`, its deposit refund also fails (refund can't implicitly re-create `A`), and `d` is added to `other_burnt_amount` per the failed-refund burn path [11](#0-10)  — confirming `d` is permanently and unrecoverably lost from circulation.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

### 8. Promise yield / resume (parking and timeout)

A `PromiseYield` receipt, when processed, is simply stored keyed by
`(receiver_id, data_id)` and awaits resume (`process_receipt`, `lib.rs:1431-1434`,
`set_promise_yield_receipt`). Yields are **instant receipts** (`is_instant_receipt`,
`receipt.rs:474`) and confined to a single account, so they never cross shard
boundaries and count as zero congestion gas (`congestion_control.rs:696`).
