Based on my investigation, I found the reachable path: `AppInstallations` (used in `deleteAppInstallationHandler`, wired to the `APP_UNINSTALLED` webhook via `mountWebhooks`) calls `findSessionsByShop` and then dereferences each returned "session" without checking for `undefined`, and the `KVSessionStorage` adapter's `findSessionsByShop` implementation can return an array containing `undefined` entries typed as `Session` due to a non-null assertion, exactly mirroring the reported bug class (a function is trusted to guarantee availability of a resource, but it does not, and the caller crashes on the unchecked result).

### Title
Unhandled exception / DoS in webhook-triggered `AppInstallations.delete`/`includes` due to unchecked stale session IDs in `KVSessionStorage.findSessionsByShop` - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`AppInstallations.includes`/`AppInstallations.delete` in `packages/apps/shopify-app-express/src/app-installations.ts` assume every `Session` object returned by `sessionStorage.findSessionsByShop()` is a fully valid, dereferenceable `Session`. [1](#0-0)  The `KVSessionStorage` adapter's `findSessionsByShop` implementation, however, does not guarantee this: it looks up an index of session IDs per shop and then maps each ID through `loadSession`, force-unwrapping the result with a non-null assertion even though `loadSession` can legitimately return `undefined` (e.g., a session was deleted, expired, or evicted from the KV namespace while the shop-index key still lists its ID): [2](#0-1) . This is the same bug shape as the vault report: a helper (`redeemRequiredBaseAssets()` / `findSessionsByShop()`) is trusted by its caller to return only usable/available results, but the helper's underlying primitive (`previewRedeem()` / `loadSession()`) can legitimately fail to deliver what was expected, and the caller performs an unchecked operation (ERC-20 `transfer()` / `session.accessToken` property access) that then throws.

### Finding Description
`AppInstallations` is constructed once at webhook-mounting time and passed into `deleteAppInstallationHandler`, which is registered as the callback for the `APP_UNINSTALLED` webhook: [3](#0-2) . When Shopify delivers this webhook (an unauthenticated-by-the-app-code HTTP POST that is HMAC-verified but whose payload/shop is otherwise attacker/merchant controlled at the protocol level), `deleteAppInstallationHandler` calls `appInstallations.delete(shop)`: [4](#0-3) .

`AppInstallations.delete` and `AppInstallations.includes` both call `sessionStorage.findSessionsByShop!(shopDomain)` and then iterate the results, dereferencing `session.accessToken` or `session.id` without a null check: [1](#0-0) .

If the app is configured with `KVSessionStorage` (e.g., Cloudflare Workers KV), `findSessionsByShop` reads the shop's session-ID index and maps every ID to a session via `loadSession`, but force-unwraps the (possibly `undefined`) result:
```ts
public async findSessionsByShop(shop: string): Promise<Session[]> {
  const sessionIds = await this.namespace.get<string[]>(...);
  if (!sessionIds) return [];
  return Promise.all(
    sessionIds.map(async (id) => (await this.loadSession(id))!),
  );
}
``` [2](#0-1) 

KV storage is eventually consistent and has TTL/eviction semantics, and the index (`shop:<shop>`) is updated separately from the individual session keys in `addShopIds`/`removeShopIds`: [5](#0-4) . It is therefore possible for the index to list a session ID whose underlying record no longer exists (expired, evicted, or removed by a concurrent `deleteSession` that fails between the `namespace.delete` and `removeShopIds` calls, or simply due to KV read-after-write inconsistency). In that case `loadSession(id)` legitimately returns `undefined`, and the non-null assertion `!` merely silences TypeScript — the array element really is `undefined` at runtime.

When `AppInstallations.delete`/`includes` then execute `session.accessToken` or `sessionShopSessions.map((session) => session.id)` over that array, they throw `TypeError: Cannot read properties of undefined`. This is functionally identical to the reported bug: a "guarantee" function (`redeemRequiredBaseAssets`/`findSessionsByShop`) does not verify actual data availability, and the caller's unchecked follow-on operation (ERC-20 transfer/`session.accessToken` access) throws.

### Impact Explanation
An uncaught exception inside `deleteAppInstallationHandler` (invoked from the webhook processing pipeline) will propagate through `api.webhooks.addHandlers`/`process()` request handling, causing the `APP_UNINSTALLED` webhook callback to fail with a 500 rather than completing cleanup of a shop's sessions. Because Shopify retries failed webhook deliveries, this can repeatedly fail for the affected shop, leaving stale sessions un-deleted (a persistent state-cleanup DoS) and generating error responses to Shopify's webhook delivery system. This is scoped to apps that choose `KVSessionStorage` and does not affect other included adapters (e.g., `MemorySessionStorage`, `DynamoDBSessionStorage`, SQL-based adapters checked filter out `undefined`/missing rows before returning).

### Likelihood Explanation
Likelihood is moderate and depends on: (1) the app being deployed with `@shopify/shopify-app-session-storage-kv`, and (2) natural KV eventual-consistency/TTL behavior or a race between `storeSession`/`deleteSession` and `addShopIds`/`removeShopIds` producing an index/session mismatch. This can occur without any malicious actor, purely from normal operation (session expiry, app reinstall/uninstall cycles, or concurrent requests), making it a realistic operational condition rather than a purely theoretical one, though it does require the specific storage adapter to be in use.

### Recommendation
In `KVSessionStorage.findSessionsByShop`, filter out sessions that fail to load instead of asserting non-null, and proactively prune stale IDs from the shop index:
```diff
 public async findSessionsByShop(shop: string): Promise<Session[]> {
   const sessionIds = await this.namespace.get<string[]>(
     this.getShopSessionIdsKey(shop),
     {type: 'json'},
   );
   if (!sessionIds) {
     return [];
   }
-  return Promise.all(
-    sessionIds.map(async (id) => (await this.loadSession(id))!),
-  );
+  const sessions = await Promise.all(
+    sessionIds.map((id) => this.loadSession(id)),
+  );
+  return sessions.filter((session): session is Session => session !== undefined);
 }
```
Additionally, harden `AppInstallations.includes`/`delete` in `packages/apps/shopify-app-express/src/app-installations.ts` to defensively skip `undefined`/falsy entries regardless of the storage adapter in use, so no single non-conforming `SessionStorage` implementation can crash the webhook handler.

### Proof of Concept
1. Configure the app with `KVSessionStorage` as `sessionStorage`.
2. Store a session for `shop` via `storeSession`, which adds the ID to the shop index (`addShopIds`).
3. Simulate eviction/expiry: directly delete the session key from the KV namespace (or let the record's underlying storage TTL expire) without going through `deleteSession`, so the shop index (`shop:<shop>`) still contains the (now-missing) session ID.
4. Trigger the `APP_UNINSTALLED` webhook for `shop` (or call `appInstallations.delete(shop)`/`includes(shop)` directly).
5. `findSessionsByShop` returns an array containing `undefined` at the stale ID's position; `AppInstallations.delete` then executes `shopSessions.map((session) => session.id)` over it, throwing `TypeError: Cannot read properties of undefined (reading 'id')`, causing the webhook callback to fail (500) instead of completing session cleanup.
