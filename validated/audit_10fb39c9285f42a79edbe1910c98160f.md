### Title
Unrestricted, permanently-reusable "BOOTSTRAP" declare backdoor allows unlimited free class declarations if fee-enforcement is left disabled post-genesis - (File: `crates/starknet_api/src/executable_transaction.rs`)

### Summary
The sequencer implements a special-cased "genesis bootstrap" path for `Declare` transactions: any transaction whose `sender_address` equals the hard-coded constant `bootstrap_address()` (`'BOOTSTRAP'`), with `nonce == 0` and zero resource bounds/`charge_fee == false`, skips `__validate_declare__`, nonce incrementing, and fee charging entirely, and just writes the class hash to state. This mirrors the C4 finding's root cause: a privileged "initialization" code path that has no intrinsic access control or one-time-use enforcement in the state machine itself — its safety is entirely dependent on an *external, operator-controlled configuration flag* (`gateway_config.static_config` fee/resource-bound enforcement) being correctly toggled off only for genesis and back on afterward.

### Finding Description
The bootstrap check lives in the Starknet OS Cairo hints and in the Rust blockifier and is symmetric between them: [1](#0-0) [2](#0-1) [3](#0-2) 

`is_bootstrap_declare` only checks `sender_address == bootstrap_address() && nonce == 0 && !charge_fee`. There is no check anywhere in this function, or in the blockifier execution path, that the chain is actually at genesis (e.g., block number 0, or "no state yet"). The only thing standing between an attacker and free, nonce-less, unlimited declarations is whether the gateway's stateless/stateful validators reject zero-resource-bound transactions, which is controlled by a static config knob: [4](#0-3) 

`validate_non_zero_resource_bounds = !allow_bootstrap_txs` — i.e., to bootstrap a real chain at all, an operator *must* run the gateway at least once with resource-bound/fee validation disabled so the funded account and ERC20 contracts can be declared for free. Nothing in the protocol state machine or gateway automatically re-enables this validation once genesis has completed; it is a manually-managed static configuration value: [5](#0-4) 

If an operator leaves this relaxed configuration in place (or a config-management error re-applies it) after genesis, any unprivileged sender can submit `Declare` V3 transactions with `sender_address = 'BOOTSTRAP'`, `nonce = 0`, and zero resource bounds/fee, indefinitely. Because the bootstrap branch never increments the sender's nonce, the same "sender" can be reused forever for arbitrarily many distinct class hashes (the `prev_value=0` guard only prevents re-declaring the *same* class hash, not reuse of the bootstrap sender itself). The mempool test/comment confirms the "sender never advances" nonce behavior is expected: [6](#0-5) 

This is the direct analog of the C4-021 report: an initialization-only pathway (there, `initialize()`; here, the bootstrap-declare fast path) has "no check over who calls it" and no protocol-level restriction limiting it to the actual initialization/genesis event — safety depends entirely on external operational diligence (there: not racing the deploy script; here: remembering to flip `validate_non_zero_resource_bounds`/gateway resource-bound enforcement back on after genesis and never misconfiguring it).

### Impact Explanation
If the fee/resource-bound gate is left open post-genesis (misconfiguration, config-management regression, or a node deployed for a test/devnet chain that later becomes production-adjacent), any unprivileged transaction sender can:
- Declare unlimited classes for free, bypassing the entire fee mechanism (loss of expected protocol fee revenue).
- Flood the gateway's Sierra-to-CASM compilation pipeline and mempool with fee-free declares (resource exhaustion / spam vector against the declare-compilation semaphore), since these declares never get evicted from the mempool by normal nonce-based invalidation in the way regular declares do.
This matches the "loss of funds" / "protocol integrity" impact class from the original report, gated behind an operational misconfiguration exactly as the original finding was.

### Likelihood Explanation
Exploitability requires the operator-controlled `validate_non_zero_resource_bounds` (`block_declare`/resource-bounds enforcement) to remain disabled beyond genesis — this is not automatically re-armed by any block-height or state-based check in the code I found. Given that genesis bootstrapping via this exact mechanism is a documented, intended operational step (see `bootstrap_declare` integration test and `create_gateway_config`), it is plausible for real deployments to inherit a "bootstrap-friendly" config from a template or forget to flip it back, making this a realistic operational hazard rather than a purely theoretical one — directly analogous to the original C4 report's acknowledged medium-severity, deployment-dependent impact.

### Recommendation
Do not rely solely on the gateway's static fee/resource-bound flag to gate the bootstrap path. Add a protocol-level, self-enforcing restriction to `is_bootstrap_declare`/the OS hint, e.g., only allow the bootstrap branch when the block/state is provably at genesis (e.g., `block_number == 0` or state root is the empty/default root), and/or track a one-time "bootstrap completed" flag in state that is set on first bootstrap declare and checked (and rejects) on all subsequent bootstrap-shaped transactions, so the fast path cannot be reused indefinitely regardless of gateway configuration.

### Proof of Concept
1. Operator runs a sequencer node with `gateway_config.static_config` resource-bound/fee enforcement disabled (as required to bootstrap a new chain, per `create_gateway_config(chain_info, validate_non_zero_resource_bounds=false)`), and never re-enables it after genesis contracts are declared.
2. An external, unfunded user crafts a `Declare` V3 transaction with `sender_address = bootstrap_address()` (`'BOOTSTRAP'`), `nonce = 0`, and zero resource bounds, targeting an arbitrary new Sierra class/compiled_class_hash they control.
3. The gateway's stateless/stateful validators accept it (no fee/resource-bound check active); `execute_raw` in `crates/blockifier/src/transaction/account_transaction.rs:899-911` detects `is_bootstrap_declare(charge_fee=false) == true` and short-circuits straight to `run_execute`, skipping `__validate_declare__` and fee charging.
4. The class is declared into state via `dict_update` with `prev_value=0` (first-time for that class hash) at zero cost and without incrementing any nonce, per `transaction_impls.cairo:764-776`.
5. The attacker repeats step 2–4 with new class hashes indefinitely, since the bootstrap sender's nonce never advances, achieving unlimited free declarations as long as the operator's config remains permissive.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }
}

        // This flow is used for the sequencer to bootstrap a new system.

        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
