### Title
Unbounded internal-transaction growth in `callConstantContract()` causes disproportionate response-size/memory DoS - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.callConstantContract()` unconditionally copies every `InternalTransaction` recorded by the VM into the `TransactionExtention` response builder, regardless of the `saveInternalTx` config flag that gates this same data on the persisted-transaction path. Because internal transaction generation via low-cost `CALL`/`STATICCALL` opcodes costs as little as ~40 energy each, an attacker can craft a constant-call contract that emits millions of internal transactions within the default `maxEnergyLimitForConstant` (100,000,000) budget, producing a multi-hundred-MB serialized response from a single cheap RPC request.

### Finding Description
`TriggerConstantContractServlet.doPost()` accepts an unauthenticated HTTP POST and calls `Wallet.triggerConstantContract()` → `Wallet.callConstantContract()`: [1](#0-0) 

Inside `callConstantContract()`, after `VMActuator.execute()` runs, every entry in `result.getInternalTransactions()` is unconditionally converted and appended to the gRPC response builder: [2](#0-1) 

This is different from the persisted-transaction path in `TransactionUtil.buildTransactionInfoInstance()`, which only records internal transactions when `CommonParameter.getInstance().isSaveInternalTx()` is true: [3](#0-2) 

So the `saveInternalTx` control that is meant to bound this list has no effect on the constant-call RPC response, meaning it is always populated in `callConstantContract()`.

Root cause on the cost side: each `CALL`/`STATICCALL`/`DELEGATECALL` costs only `CALL_ENERGY = 40` base energy (plus negligible memory expansion cost for small buffers), as defined in `EnergyCost.getCallCost()`/`getStaticCallCost()`: [4](#0-3) 

Each such call appends one `InternalTransaction` to `ProgramResult` via `Program.addInternalTx()` / `ProgramResult.addInternalTransaction()`, with no cap on list size: [5](#0-4) [6](#0-5) 

`VMActuator` constrains only the energy budget for constant calls (`maxEnergyLimitForConstant`, default 100,000,000, further reduced by `trx.getRawData().getFeeLimit()` if set), not the number or size of side-effect artifacts such as internal transactions: [7](#0-6) 

With ~40 energy per call, a contract issuing a tight loop of `STATICCALL`s to itself (or to a trivial address/precompile) can generate on the order of 100,000,000 / 40 ≈ 2,500,000 internal transactions within the default constant-call energy ceiling. Each serialized `Protocol.InternalTransaction` (hash, caller address, transfer-to address, call-value info, note, extra) is on the order of 100+ bytes, so the response payload can reach hundreds of megabytes for a single HTTP POST that costs the caller nothing (constant calls are free — no broadcast, no fee charged) and requires no special privilege. The only size gate found (`Util.checkBodySize`) applies to the inbound request body, not to the outbound response.

I was unable to find in the indexed code any additional guard (list-size cap, response-size cap, per-opcode internal-tx counting toward energy, or rate limiter tied to internal-transaction volume) that would stop this; the only rate limiting present on the endpoint is the generic `RateLimiterServlet` base class, which limits request frequency, not per-request payload size.

### Impact Explanation
This is a Denial-of-Service vector via the RPC API: a single free `triggerconstantcontract` HTTP request can force the node to allocate, populate, and serialize an internal-transaction list scaling linearly with attacker-chosen loop count, consuming disproportionate CPU/memory/network resources relative to the energy actually metered for the call (bounded only by `maxEnergyLimitForConstant`, unrelated to response size). Repeated concurrent requests amplify this into node-level memory pressure/stall, matching the "DoS via RPC-API" bounty impact class. This does not cause consensus divergence or asset loss — it is confined to a resource-exhaustion/availability issue on nodes exposing the HTTP/gRPC constant-call API.

### Likelihood Explanation
- Preconditions: `vm.supportConstant = true` (default off in `reference.conf`/`config.conf`, but commonly enabled on full nodes serving dApps/wallets since `triggerconstantcontract` is a core read API). `vm.saveInternalTx` is irrelevant since the constant-call path ignores it entirely.
- Attacker cost: zero — constant calls are not broadcast, consume no bandwidth/energy from the caller's account, and require only deploying (or reusing an already-deployed) contract with a loop of cheap `CALL`/`STATICCALL` opcodes.
- Feasibility: high. Bytecode construction is trivial (a bounded loop of `STATICCALL(gas, address(this), 0, 0, 0, 0)`), and the request is a single unauthenticated HTTP POST, fully repeatable and scriptable.
- The main variable/uncertainty is whether a given node's HTTP layer imposes a global response-size or write timeout that would truncate the effect before full serialization completes; I found no such limit in the reviewed code paths.

### Recommendation
- Gate internal-transaction inclusion in `callConstantContract()`'s response behind the same `saveInternalTx`/`saveFeaturedInternalTx` configuration used in `TransactionUtil.buildTransactionInfoInstance()`, so operators can disable this by default for public-facing nodes.
- Introduce an explicit cap (e.g., a new `maxInternalTransactionsForConstant` parameter, or reuse a fixed hard cap) on the number of internal transactions recorded/serialized per constant call, independent of the energy budget, and truncate/reject with a clear error once exceeded.
- Consider charging additional energy per internal transaction recorded (proportional to serialized size) so the cost model reflects the true resource cost, aligning metering with response payload size.

### Proof of Concept
1. Deploy a contract whose `view`/`pure` function executes a loop of cheap self-calls, e.g. (Solidity sketch):
```solidity
function spam(uint n) public view returns (bool) {
    for (uint i = 0; i < n; i++) {
        (bool ok, ) = address(this).staticcall("");
        require(ok || true);
    }
    return true;
}
```
Each `staticcall` costs ~40 energy (`EnergyCost.getStaticCallCost`), so with `n` chosen such that `40 * n` stays under `maxEnergyLimitForConstant` (100,000,000), e.g. `n = 2,000,000`.

2. POST to `/wallet/triggerconstantcontract`:
```json
{
  "owner_address": "<any funded/unfunded address hex>",
  "contract_address": "<deployed contract address hex>",
  "function_selector": "spam(uint256)",
  "parameter": "<abi-encoded 2000000>"
}
```

3. Expected assertions for a JUnit-level reproduction against `Wallet.callConstantContract()`:
```java
Transaction tx = wallet.callConstantContract(trxCap, builder, retBuilder, false);
assertTrue(builder.getInternalTransactionsCount() > 1_000_000);
assertTrue(builder.build().getSerializedSize() > 100_000_000); // ~100MB+
assertTrue(builder.getEnergyUsed() <= CommonParameter.getInstance().getMaxEnergyLimitForConstant());
```
This demonstrates `getInternalTransactionsCount()` and serialized response size scaling linearly with `n` while `energyUsed` remains within the normal single-call energy budget, confirming disproportionate resource cost relative to metered energy.
