### Title
Uncaught TypeError in `sanitizeHost` from malformed decoded host crashes callers instead of returning null - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`sanitizeHost` decodes the attacker-supplied base64 `host` parameter with `atob()` and passes the raw decoded bytes directly into `new URL()` without a try/catch. Since `atob()` can produce forbidden host code points (control characters, `<>"#%?@[\]^`, etc.), the URL constructor throws an uncaught `TypeError`, crashing whichever caller invoked `sanitizeHost` instead of receiving `null`/`InvalidHostError`.

### Finding Description
`sanitizeHost` in [1](#0-0)  only validates that `host` is syntactically valid base64 via `base64regex`, then calls `decodeHost(sanitizedHost)` (a plain `atob()` in [2](#0-1) ) and immediately feeds the decoded string into `new URL(\`https://${decoded}\`)` with no try/catch anywhere in the function. Because base64 decoding is agnostic to the resulting byte content, an attacker can craft a base64 string that decodes to a hostname segment containing forbidden host code points per the WHATWG URL spec (NUL, control chars, `<`, `>`, `"`, `#`, `%`, `?`, `@`, `[`, `\`, `]`, `^`, or whitespace). Node's `URL` constructor throws `TypeError [ERR_INVALID_URL]` for such input, and since nothing in `sanitizeHost` catches it, the exception propagates to the caller unhandled.

This function is called directly, unguarded, from request-authentication code paths that read the `host` query parameter straight from the request URL — e.g. `validateShopAndHostParams` in `shopify-app-remix` ( [3](#0-2) ) and the equivalent helpers in `shopify-app-react-router` and `shopify-app-express`, as well as `buildEmbeddedAppUrl`/`getEmbeddedAppUrl` ( [4](#0-3) ), which run during embedded-app authentication/redirect flows before any session or HMAC check occurs. None of these call sites wrap the `sanitizeHost` call in try/catch, so a crafted `host` value will surface as an unhandled exception rather than a controlled `InvalidHostError`/redirect-to-login.

### Impact Explanation
An unauthenticated attacker can trigger an unhandled `TypeError` in an authentication/embedded-app-URL-resolution code path by supplying a crafted `host` query parameter, with no credentials required. Depending on the host framework's error handling, this can manifest as an unhandled promise rejection or uncaught synchronous exception, causing a request failure or, in frameworks without global error boundaries, worker/process-level instability — a Denial-of-Service class impact in an authentication-adjacent handler.

### Likelihood Explanation
Trivial and fully repeatable: the attacker needs only to base64-encode a string containing a forbidden host character (e.g. a NUL byte or `%00`, `<`, `#`) and pass it as `?host=...` to any endpoint that calls `sanitizeHost`/`buildEmbeddedAppUrl` (login route, embedded app URL resolution, admin authentication middleware). Default configuration is sufficient; no secrets or special privileges are needed.

### Recommendation
Wrap the `decodeHost`/`new URL` logic in `sanitizeHost` in a try/catch, treating any thrown error (invalid base64 decode, invalid URL) as an invalid host — return `null` or throw `InvalidHostError` per `throwOnInvalid`, consistent with the rest of the function's fail-closed contract. Also consider validating the decoded string doesn't contain control/forbidden characters before constructing the `URL`.
