Confirmed: `TokenConfig.LiquidityCap` is defined in the proto/type layer but is never read or enforced anywhere in the `x/uexecutor` deposit path (`depositPRC20`, `CallPRC20Deposit`, `CallPRC20DepositAutoSwap`) or in `x/uregistry`'s `AddTokenConfig`/`UpdateTokenConfig` keeper logic. This is the closest scoped analog to the CoinFabrik `preallocate` finding.

### Title
Inbound PRC20 minting never enforces `TokenConfig.LiquidityCap`, allowing unbounded token issuance - (File: x/uexecutor/keeper/handler.go)

### Summary
`TokenConfig` carries a `liquidity_cap` field intended to bound how much synthetic/native representation of a bridged asset can exist on Push Chain [1](#0-0) . Like the CoinFabrik `preallocate` bug (missing amount, receiver, state, and cap checks before minting), the Push Chain inbound-funds execution path deposits (mints) PRC20 tokens for every validated inbound without ever consulting this cap.

### Finding Description
`ValidateForExecution` on `Inbound` validates amount format (non-negative uint256, positive unless the tx type explicitly allows zero) and recipient/asset-address well-formedness, but does not check the deposit amount against any cap [2](#0-1) .

The actual mint call, `depositPRC20`, only resolves the `TokenConfig` for its `NativeRepresentation.ContractAddress` and converts the amount string to a `big.Int` — it never reads `tokenConfig.LiquidityCap` or compares it to any running total minted [3](#0-2) .

`CallPRC20Deposit`, the `DerivedEVMCall` wrapper that actually mints on the `UniversalCore`/PRC20 contract as the module account, takes the raw `amount` and forwards it verbatim with no upper-bound check [4](#0-3) . The same is true of the auto-swap deposit variant `CallPRC20DepositAutoSwap` [5](#0-4) .

A grep across the entire `x/` tree shows `LiquidityCap`/`liquidity_cap` is only referenced in generated protobuf code, `TokenConfig.ValidateBasic()` (which merely checks the string is non-empty, not that it's respected at mint time) [6](#0-5) , and test fixtures — there is no keeper-side accounting of cumulative minted supply per token anywhere in `x/uexecutor` or `x/uregistry`.

### Impact Explanation
An unprivileged external attacker who can get any amount of an already-whitelisted asset observed as an inbound (e.g., by bridging tokens through the external gateway, which is entirely user-controlled) can cause Push Chain to mint PRC20 tokens without any bound. If the `liquidity_cap` value configured per-token (visible in `config/**/tokens/*.json`, e.g. `1000000000000000000000000`) is meant to represent an economic/backing limit for that asset's synthetic representation, an attacker driving deposits past that cap breaks the intended 1:1 backing invariant between the external-chain-locked asset and the Push-Chain-side PRC20 supply — this is "unauthorized mint" / "corruption of PRC20 accounting" as scoped. This does not require any privileged validator, admin, or TSS behavior; it only requires the standard honest-validator quorum finalizing a normal inbound observation of a real bridging event.

### Likelihood Explanation
High reachability: every `FUNDS`, `FUNDS_AND_PAYLOAD`, and `GAS_AND_PAYLOAD` inbound that reaches quorum flows through `ExecuteInboundFunds` / `ExecuteInboundFundsAndPayload` / `ExecuteInboundGasAndPayload`, all of which call `depositPRC20`/`CallPRC20Deposit` with no cap check [7](#0-6) . Any user who can bridge real value on the external chain (unprivileged, no special access) can push cumulative minted amounts arbitrarily, limited only by how much they can actually move/lock on the external chain — this is a standard user action, not an edge case.

Caveat: I could not verify whether the destination Solidity contract (`UniversalCore`/PRC20, in the separate `push-chain-core-contracts` repo, not present in this codebase) enforces the cap on its own before executing `depositPRC20Token`/`depositPRC20WithAutoSwap`. If the cap is enforced at that contract layer, the missing Cosmos-side check is a defense-in-depth gap rather than an exploitable vulnerability, and the on-chain revert would simply surface as a `FAILED` PCTx. This repository's Go code, however, provides no such enforcement, and the field exists specifically to express this invariant, suggesting it was intended to be checked but is currently dead data on the node side.

### Recommendation
Track cumulative minted supply per `(chain, asset)` or per PRC20 address in `x/uexecutor` (or read it from the PRC20 contract via `CallEVM`) and, in `depositPRC20` (or earlier, in `Inbound.ValidateForExecution`), reject/route-to-revert any deposit that would push the cumulative minted amount past `TokenConfig.LiquidityCap`, mirroring the CoinFabrik fix pattern of validating amount, receiver, and cap before allowing the privileged mint path to execute.

### Proof of Concept
Not independently reproducible from static analysis alone since the enforcement point in the external Solidity contract (`UniversalCore.depositPRC20Token`) is outside this repository. Conceptually: repeatedly submit valid, quorum-reaching `FUNDS`/`FUNDS_AND_PAYLOAD` inbounds for the same `(sourceChain, assetAddr)` with amounts whose sum exceeds the configured `TokenConfig.LiquidityCap` (e.g., `1000000000000000000000000` per the sample configs in `config/testnet-donut/*/tokens/*.json`); each individual inbound passes `ValidateForExecution` and `depositPRC20` unconditionally, since neither function reads `LiquidityCap`.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
