### Title
Wallet Contract permanently freezes funds via stuck `has_in_flight_tx` when hardcoded callback gas constants become insufficient - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR wallet contract (used to let Ethereum-style transactions control an eth-implicit NEAR account) relies on several hardcoded gas constants for its promise callbacks and per-action gas allocations, mirroring the exact bug class in the report: fixed, "should be enough" gas/fee amounts that can silently stop being sufficient as the underlying execution cost model changes, breaking the protocol.

### Finding Description
`WalletContract::rlp_execute` sets `self.has_in_flight_tx = true` before dispatching a promise chain, and this flag is only ever reset back to `false` inside the *callback* methods (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`) [1](#0-0) . Every subsequent call to `rlp_execute` is unconditionally rejected while this flag is `true`, with no other reset path [2](#0-1) .

The gas given to those callback receipts is computed from hardcoded constants: `RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, and `NEP_141_STORAGE_DEPOSIT_GAS` [3](#0-2) , plus a fixed 2 Tgas allotted for any non-`FunctionCall` action (`Transfer`, `AddKey`, `DeleteKey`) via `Action::gas()` [4](#0-3) . These constants are added together to size the static gas reserved for the callback promise, e.g. `callback_gas = ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())` and `callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` [5](#0-4) .

This is the same anti-pattern flagged in the report for Solidity's `.transfer()`: a fixed gas stipend baked into the contract logic that is assumed to always be "enough," without accounting for future changes to per-operation gas costs (analogous to EIP-1884 changing SLOAD cost and breaking `.transfer()`'s 2300-gas assumption). On NEAR, gas costs for WASM execution, syscalls, and storage operations are protocol parameters that can and do change across protocol versions (see `runtime/runtime/src/config.rs` fee tables and `core/parameters` version-gated cost tables). If a future protocol version raises the cost of the operations performed inside `rlp_execute_callback` (nonce bump, `ExecuteResponse` construction, `env::promise_result` handling) or `address_check_callback`/`nep_141_storage_balance_callback` (JSON `serde_json` deserialization, promise creation) above the hardcoded reserved gas, the callback receipt will run out of gas mid-execution.

Unlike a normal contract call, a callback receipt that fails due to gas exhaustion has **all of its state changes rolled back** — including the line that resets `self.has_in_flight_tx = false`. Because this flag is the sole gate for accepting new `rlp_execute` calls, once it is stuck at `true` due to a gas-exhausted callback, the wallet contract permanently rejects all future transactions on that account, including any transfer attempting to move the NEAR balance out.

### Impact Explanation
Any eth-implicit account controlled by this wallet contract could become **permanently frozen** — its NEAR balance becomes unrecoverable because the only exit path (submitting a further `rlp_execute` transaction, including one attempting to withdraw funds) is blocked by the stuck `has_in_flight_tx` flag. This matches the "permanently frozen funds" acceptance criterion. The freeze is triggered purely by an ordinary user/relayer transaction combined with a future (or parameter-drift) change in gas costs, not by any privileged or malicious-node action.

### Likelihood Explanation
The immediate trigger requires either (a) a future protocol gas-cost increase for the specific WASM/host operations performed inside the callbacks, or (b) an attacker deliberately engineering an action/target combination whose deserialization/processing inside the callback is unusually expensive relative to the fixed reserve (e.g., large `AddKey`/`FunctionCall` payloads routed through the same fixed constants used for lightweight actions). Because the constants are shared across action types via `saturating_add`, and are not derived from measured worst-case costs with a safety margin tied to protocol version, likelihood is non-trivial and grows over time as the protocol evolves — exactly the "may break in the future" framing of the original report.

### Recommendation
- Do not rely on hardcoded/static gas reservations for callback logic whose cost may change with protocol upgrades; instead attach a generous, explicitly-documented safety margin and/or use `GasWeight` to receive any leftover prepaid gas rather than a fixed static amount.
- Ensure the state mutation that clears `has_in_flight_tx` cannot be rolled back due to gas exhaustion — e.g., perform it in a way that is robust to partial failure, or add a recovery/unlock mechanism (e.g., a time-locked reset) that does not depend on a specific callback successfully completing.
- Periodically re-validate the hardcoded gas constants against current protocol cost parameters as part of protocol upgrade review, similar to how the `.transfer()` recommendation in the original report suggests moving away from fixed-gas patterns entirely.

### Proof of Concept
Conceptual sequence (cannot be executed without a protocol version that raises the relevant op costs, but the code path is deterministic):
1. A relayer submits an `rlp_execute` transaction with an ETH-emulated `AddKey` or ERC-20 `Transfer` action, routing through `nep_141_storage_balance_callback` or `address_check_callback` [6](#0-5) .
2. `has_in_flight_tx` is set to `true` before the promise chain is dispatched [7](#0-6) .
3. The callback receipt is granted exactly `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` / `ADDRESS_CHECK_CALLBACK_GAS` gas [8](#0-7) .
4. Under a future/altered gas cost schedule (or an unusually costly payload for the shared-constant action types), the callback exceeds this fixed budget and its receipt fails with an out-of-gas `FunctionCallError`.
5. Because the receipt failed, the state change `self.has_in_flight_tx = false` is rolled back, leaving the flag `true` forever.
6. All subsequent `rlp_execute` calls immediately short-circuit with `"transaction already in progress"` [9](#0-8) , permanently locking the account's funds.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

impl Action {
    pub fn gas(&self) -> Gas {
        match self {
            Self::FunctionCall(fn_call) => fn_call.gas,
            // 2 Tgas is sufficient for any non-function call action
            Self::Transfer(_) | Self::AddKey(_) | Self::DeleteKey(_) => Gas::from_tgas(2),
        }
    }
