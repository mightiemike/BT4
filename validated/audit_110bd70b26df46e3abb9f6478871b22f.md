### Title
Arrival-order-dependent `validate_shadow_parent_burnchain` check permanently diverges chainstate between nodes - (File: `stackslib/src/chainstate/nakamoto/shadow.rs`)

### Summary
`NakamotoChainState::validate_shadow_parent_burnchain` only rejects a normal block whose `header.parent_block_id` points at a shadow block but whose block-commit has `parent_vtxindex != 0` / a mismatched `parent_block_ptr` if the shadow parent's header is *already present* in the local `nakamoto_staging_blocks` table. If a node has not yet staged the shadow parent, the check vacuously returns `Ok(())`, the malformed block is stored in staging, and — critically — the check is never re-run when the block is later processed via `append_block`. A node that already staged the shadow parent rejects and never stores the same block. The result is a permanent, arrival-order-dependent divergence in chainstate between honest nodes.

### Finding Description
The broken equality is: `accept_block(node_A, block) == accept_block(node_B, block)` for the identical malformed Nakamoto block, where node A has not yet staged the shadow-tenure parent header and node B has.

Code path:
- `NakamotoChainState::accept_block` (`stackslib/src/chainstate/nakamoto/mod.rs:2829-2896`) calls `validate_normal_nakamoto_block_burnchain` (`mod.rs:2739-2817`), which calls `Self::validate_shadow_parent_burnchain(staging_db, db_handle, block, &block_commit)` at `mod.rs:2771`.
- `validate_shadow_parent_burnchain` (`stackslib/src/chainstate/nakamoto/shadow.rs:217-256`) looks up the parent header via `staging_db.get_nakamoto_block_header(&block.header.parent_block_id)`. If it returns `None` (parent not yet staged locally), the function returns `Ok(())` immediately: [1](#0-0) 
- Only if the parent header *is* present and is a shadow block does it enforce `block_commit.parent_vtxindex == 0` and `block_commit.parent_block_ptr == parent_sn.block_height`: [2](#0-1) 
- Crucially, this check is never repeated during actual block processing. `NakamotoChainState::append_block` (`mod.rs:5026` onward) performs its own set of checks (`check_sortition_exists`, `check_tenure_continuity`, `check_block_commit_vrf_seed`, burn-total checks) but does **not** call `validate_shadow_parent_burnchain` or otherwise verify the block-commit's `parent_vtxindex`/`parent_block_ptr` against the actual Stacks parent linkage: [3](#0-2) 

Root cause: the burnchain-level block-commit consistency check (leader-key/parent pointer fields) and the Stacks-block-level parent linkage (`header.parent_block_id`) are independently attacker-controlled. The only code that cross-checks them is `validate_shadow_parent_burnchain`, and it is gated on local staging-DB state rather than canonical burnchain state, making its outcome dependent on message arrival order. An attacker can craft a `LeaderBlockCommit` with a normal, non-zero `parent_vtxindex` pointing at some legitimately existing prior commit (satisfying the burn-level "has_parent" check in `stackslib/src/chainstate/burn/operations/leader_block_commit.rs:1247-1271`, since `maybe_shadow_block` is false when `parent_vtxindex != 0`), while separately crafting the Nakamoto block so that `header.parent_block_id` points at the shadow tenure's block. Both objects are independently well-formed and pass burnchain-op acceptance; only `validate_shadow_parent_burnchain` is meant to catch the mismatch.

A node that has not yet received/staged the shadow block (e.g., recently booted, resyncing, or briefly behind on shadow-tenure propagation) stages the malformed block via `accept_block` returning `Ok(true)`. Once the shadow parent later arrives, is staged and processed, the malformed child becomes eligible via `next_ready_nakamoto_block` (`staging_blocks.rs:465-528`, which only requires `parent.processed = 1`) and is processed by `append_block` without the shadow-linkage check ever being re-evaluated. A node that already had the shadow parent staged rejects the block outright at `accept_block` and never stores it.

### Impact Explanation
Node A permanently incorporates a block into its canonical chainstate (new chain tip, MARF root, tenure records) that node B and any node that staged the shadow parent before the malformed block will always reject with `ChainstateError::InvalidStacksBlock`. Because `append_block` never revisits this check, node A's acceptance is irrevocable once processed — it is not a transient disagreement but a permanent divergence in canonical chainstate, matching the "invalid block accepted... / chain split" Critical category, since honest nodes end up with different, non-reconcilable, chain tips/state roots for the same tenure sequence.

### Likelihood Explanation
Preconditions: an emergency shadow tenure must exist upstream (a rare but supported/real feature in this codebase), and the attacker needs only a single miner slot / minority BTC spend to place a normally-valid `LeaderBlockCommit` (with a legitimate, non-shadow, non-zero `parent_vtxindex`) and to broadcast a crafted Nakamoto block whose `parent_block_id` targets the shadow block. No majority stake, signer collusion, or privileged role is required — timing relative to shadow-block propagation is the only variable, and an attacker can deliberately race this by broadcasting to a subset of nodes before shadow-block gossip completes. This is repeatable at every emergency shadow-tenure boundary.

### Recommendation
Re-validate the shadow-parent/block-commit consistency (`parent_vtxindex == 0` and `parent_block_ptr == shadow_parent_sortition_height`) inside `append_block` at the point where the parent header is definitively known and processed, not only in `accept_block`/`validate_normal_nakamoto_block_burnchain`. Alternatively, defer/re-run `validate_shadow_parent_burnchain` when the parent header transitions from absent to present (e.g., re-validate all `burn_attachable` children when their parent becomes available), so the check's outcome cannot depend on the order in which blocks are staged.

### Proof of Concept
Rust integration test plan (two-node harness, extending patterns in `stackslib/src/chainstate/nakamoto/tests/node.rs`):
1. Build a chain with an emergency shadow tenure `S` (using `NakamotoBlockBuilder::make_shadow_tenure` as in `shadow_chainstate_repair`).
2. Craft a normal `LeaderBlockCommitOp` `C` with `parent_vtxindex != 0` pointing at some legitimate prior (non-shadow) winning commit, and `parent_block_ptr` NOT equal to `S`'s sortition block height; ensure `C` passes burnchain-op acceptance (`leader_block_commit.rs` checks).
3. Craft the corresponding `NakamotoBlock` `B` for `C`'s tenure with `header.parent_block_id = S.block_id()`.
4. Node A: do NOT stage `S` yet. Call `NakamotoChainState::accept_block(chainstate_A, &B, ..)`. Assert `Ok(true)` (staged).
5. Node B: stage and process `S` first. Call `NakamotoChainState::accept_block(chainstate_B, &B, ..)`. Assert `Err(ChainstateError::InvalidStacksBlock(_))`.
6. On node A, stage and process `S`, then call `process_next_nakamoto_block` until `B` is processed. Assert `B` becomes part of node A's canonical chain tip (`NakamotoChainState::get_canonical_block_header` returns `B`).
7. Assert the two nodes' canonical tips/chain state (e.g., `get_canonical_block_header`) permanently differ, demonstrating `accept_block(A, B) != accept_block(B, B)` and a resulting chain-state split.
