### Title
Inconsistent delegated-resource balance check in TVM-native `UnDelegateResourceProcessor` causes spurious reverts / diverging behavior from the BalanceContract path - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java)

### Summary
The TVM-callable `undelegateResource` native contract validates and executes an un-delegation using only the "unlocked" `DelegatedResourceCapsule` (`isLock=false`), while the equivalent user-facing `UnDelegateResourceContract` path (`UnDelegateResourceActuator`) additionally accounts for the "locked" `DelegatedResourceCapsule` (`isLock=true`) once its lock period has expired. This is structurally the same bug class as the reported AMO issue: a validation function checks a narrower balance/sub-state than what is actually available (and what the sibling code path considers available), causing legitimate operations to be rejected inconsistently depending on the entry point used.

### Finding Description
For TRC-10/TRX resource delegation, `java-tron` maintains two `DelegatedResourceCapsule` records per (owner, receiver) pair: an "unlock" record (`isLock=false`) and a "lock" record (`isLock=true`) used for locked delegations with an expiration time.

The `UnDelegateResourceActuator` (triggered by a normal broadcast `UnDelegateResourceContract` transaction) correctly combines both sources of available balance when validating an un-delegation request: [1](#0-0) 

It sums `unlockResourceCapsule.getFrozenBalanceForBandwidth()` with `lockResourceCapsule.getFrozenBalanceForBandwidth()` when the lock has already expired (`lockResourceCapsule.getExpireTimeForBandwidth() < now`), and only then compares against the requested `unDelegateBalance`. At execution time, it explicitly calls `delegatedResourceStore.unLockExpireResource(...)` to migrate the expired locked balance into the unlock bucket before applying the withdrawal: [2](#0-1) 

In contrast, the TVM-native contract path — invoked when a smart contract calls the `undelegateResource` precompile/opcode, reachable from any account via a broadcast contract-call transaction — uses `UnDelegateResourceProcessor`, whose `validate()` only fetches the unlock-key capsule and checks the requested amount against it alone, with no consideration of any expired lock balance: [3](#0-2) 

Its `execute()` similarly re-fetches only the unlock-key capsule and never invokes `unLockExpireResource(...)` to fold in an expired lock balance: [4](#0-3) 

This mirrors exactly the AMO pattern from the external report: `stakedBalance()` (a narrower subset of available funds) was checked instead of the true available balance that `withdrawAndUnwrap()` could actually draw from (staked + held). Here, the TVM native contract checks only the "unlock" delegated balance instead of the true total available balance (unlock + expired lock) that the sibling actuator path correctly computes and that `unLockExpireResource()` would make available.

### Impact Explanation
A smart contract that has locked-delegated resources from an owner, once the lock period expires, should be un-delegatable for the full expired-lock amount plus any existing unlock amount. Calling `undelegateResource` via the TVM precompile with a `unDelegateBalance` that is satisfiable only when including the expired lock balance will incorrectly revert with `"insufficient delegatedFrozenBalance(...)"`, even though the exact same operation would succeed via a normal `UnDelegateResourceContract` broadcast transaction. This is a functional inconsistency / availability (DoS-style) defect for contract-driven resource management flows: legitimate un-delegation calls from contracts fail non-deterministically depending on which code path (native TVM opcode vs. wallet-broadcast transaction) is used, and no separate mitigation (equivalent to the AMO's `getTotalBalance()`) exists in this native contract path. It does not directly enable fund theft or unauthorized transfer, since the check is overly conservative (reverts) rather than under-restrictive, but it breaks correctness/availability guarantees for the delegate-resource feature when invoked from contracts.

### Likelihood Explanation
This path is reachable by any contract that calls the `undelegateResource` native/precompiled operation with a `receiverAddress` that has locked delegated resources whose lock has expired but has not yet been migrated to the unlock bucket by any other means (e.g., another `UnDelegateResourceContract` transaction or an on-chain refresh that calls `unLockExpireResource`). This is a fairly common realistic scenario for any account using locked resource delegation and later relying on smart-contract logic to manage/undelegate that resource, since lock expiration naturally occurs over time and contracts are a normal way to automate resource management.

### Recommendation
Update `UnDelegateResourceProcessor.validate()` and `execute()` to mirror `UnDelegateResourceActuator`'s logic: fetch both the unlock (`isLock=false`) and lock (`isLock=true`) `DelegatedResourceCapsule` records, include the lock balance in the available-balance calculation when its expire time has passed, and call `delegatedResourceStore.unLockExpireResource(...)` (or equivalent repository-level migration) prior to computing/consuming the balance, so that the TVM-native code path behaves consistently with the BalanceContract actuator path.

### Proof of Concept
1. Owner delegates a locked amount of BANDWIDTH (or ENERGY) resource to a receiver contract with `lock=true` and an expiration timestamp `T`.
2. Time advances past `T` (lock expired), and the owner has performed no other un-delegate transaction, so the expired lock balance still resides in the `isLock=true` `DelegatedResourceCapsule` and has not been migrated to the `isLock=false` record.
3. The owner's account (or the receiver contract acting on behalf) calls the `undelegateResource` TVM opcode requesting a `unDelegateBalance` that exceeds the current unlock-bucket balance but is fully covered when including the expired lock balance.
4. `UnDelegateResourceProcessor.validate()` reads only the unlock-key `DelegatedResourceCapsule` [5](#0-4)  and throws `"insufficient delegatedFrozenBalance(BANDWIDTH)"`, reverting the internal transaction.
5. The exact same logical request, submitted instead as an `UnDelegateResourceContract` broadcast transaction through `UnDelegateResourceActuator.validate()` [1](#0-0) , succeeds because it correctly aggregates the unlock and expired-lock balances — demonstrating the inconsistency between the two validation paths for what should be an identical operation.
