### Title
Signer protocol v1 uses a stricter (globally-accepted-only) duplicate-tenure-start check than v2, producing accept/reject divergence on the same tenure-change block - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`validate_tenure_change_payload` exists in two parallel implementations, one per signer protocol version. Both are meant to enforce the same equality: "reject a tenure-change block if we have already accepted a competing block that starts this tenure." v1's implementation checks only `get_last_globally_accepted_block`, while v2's checks `get_last_signed_block` (which also covers locally-accepted, not-yet-globally-confirmed blocks). This is exactly the `batchMatchOrders`/`matchOrder` bug class: two entry points intended to perform the same "match"/validation, but one silently omits a capability (state) the other checks, so the same input can pass on one path and fail on the other.

### Finding Description
`SortitionsView::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` performs the duplicate-tenure-start check with: [1](#0-0) 
which calls `signer_db.get_last_globally_accepted_block(...)`.

The v2 equivalent, `SortitionsView::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v2.rs`, performs the same check with: [2](#0-1) 
which calls `signer_db.get_last_signed_block(...)` — a strictly broader predicate that also matches blocks the local signer has merely *locally* accepted (signed but not yet confirmed on-chain).

This divergence is explicitly called out in the project's own documentation of the shared chainstate checks: [3](#0-2) 

Both functions are invoked from the version-specific `check_proposal` entry points (`v1.rs:319-326`, `v2.rs:176-184`) as the sole place this duplicate-block-found guard runs during proposal evaluation; it is never re-run at validate-ok or at signing time (documented at `docs/signer-flows.md:435-437`). So a signer running the v1 code path will *accept* (as far as this check is concerned) a second, competing tenure-start block for a tenure in which it has only *locally* accepted (but not yet seen globally confirmed) a prior tenure-start block — precisely the case a v2 signer would reject with `RejectReason::DuplicateBlockFound`.

### Impact Explanation
Because signer protocol version can differ across the network's signer fleet (the docs explicitly describe "mixed-version fleets," e.g. `docs/signer-flows.md:377-383`), an adversarial or careless miner can propose a second tenure-start block for the same tenure while the first competing block is only locally (not yet globally) accepted. v1 signers will pass this proposal into signature counting (subject only to the other tenure-change checks), while v2 signers reject it outright with `DuplicateBlockFound`. This creates a validation-verdict divergence between two conformant, honest, unprivileged signer nodes on the exact same block — the kind of two-nodes-disagree condition that can fragment signer weight across competing tenure-start blocks and produce a temporary tip/tenure disagreement (a fork attempt) bounded by however much weight is still running v1. This matches the "High: minority-triggerable static-validation divergence... temporary tip disagreement" impact tier.

### Likelihood Explanation
No majority or admin privilege is required; a single miner (unprivileged in the protocol sense of not needing signer keys) simply needs to broadcast two competing tenure-start proposals for the same tenure while enough v1 signers are still live to matter. This can occur naturally during a protocol version rollout without any attacker at all, and can be deliberately triggered by any miner who observes a locally-accepted-but-not-yet-globally-accepted tenure-start block and proposes a competitor.

### Recommendation
Unify the duplicate-tenure-start predicate across `chainstate/v1.rs` and `chainstate/v2.rs` so both versions use the same acceptance criterion (`get_last_signed_block`, matching v2's stricter/broader check), or explicitly document and gate the weaker v1 behavior so it cannot coexist with v2 signers during a live tenure decision. At minimum, ensure the two implementations of `validate_tenure_change_payload` are kept behaviorally identical for any predicate that feeds into a network-wide accept/reject decision, and add a cross-version regression test (mirroring `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs`) for the v1 path with the equivalent locally-accepted-only scenario to confirm parity.

### Proof of Concept
1. Miner proposes tenure-start block `B1` for tenure `T`. Enough signer weight (but not yet a globally-confirmed acceptance) signs `B1`, marking it "locally accepted" in each signer's `SignerDb` (`mark_locally_accepted`).
2. Before `B1` becomes globally accepted on-chain, the miner (or a competing miner) proposes a second tenure-start block `B2` for the same tenure `T`.
3. A signer running protocol v2 evaluates `B2` via `chainstate/v2.rs`'s `validate_tenure_change_payload`, calls `get_last_signed_block(T)`, finds `B1` (locally accepted counts), and rejects `B2` with `RejectReason::DuplicateBlockFound` (as demonstrated by the existing regression test `check_tenure_change_rejects_when_locally_accepted_block_exists` at `stacks-signer/src/chainstate/tests/v2.rs:756-850`).
4. A signer running protocol v1 evaluates the identical `B2` via `chainstate/v1.rs`'s `validate_tenure_change_payload`, calls `get_last_globally_accepted_block(T)`, finds nothing (since `B1` was only locally accepted), and does **not** reject `B2` on this ground — allowing it to continue toward signature collection.
5. v1-weighted signers and v2-weighted signers now disagree on whether `B2` is a valid proposal for tenure `T`, splitting signature weight between `B1` and `B2` and creating a temporary fork/tip disagreement in tenure `T`.
