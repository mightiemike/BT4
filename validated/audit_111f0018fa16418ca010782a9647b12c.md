### Title
`ensure_match_transaction_info` omits state-checkpoint / hot-state / position-state root comparison, letting replay-verify accept a divergent post-state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-vs-computed comparator used by all replay/verification tooling (`db-tool`'s `replay_on_archive` and `execute_and_verify`, `execution/executor/src/chunk_executor/mod.rs::verify_execution`, `aptos-move/cli/src/commands.rs`, and `aptos-debugger`). It checks status, gas used, write-set hash (`state_change_hash`), and event-root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the locally re-computed values. The code itself flags this with a `TODO(trading-native)` comment acknowledging the gap.

### Finding Description
`TransactionInfo` (both `V0` and `V1`) carries a `state_checkpoint_hash` (Sparse-Merkle-Tree root of world state) and, in `V1`, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` (the native-position/trading state root) [1](#0-0) . These fields are populated at commit-time from `StateCheckpointOutput` (`state_checkpoint_hashes`, `hot_state_checkpoint_hashes`, `position_state_checkpoint_hashes`) and folded into the accumulator-hashed `TransactionInfo` in `DoLedgerUpdate::assemble_transaction_infos` [2](#0-1) .

However, `TransactionOutput::ensure_match_transaction_info` — the function whose entire purpose is to assert that a *locally re-executed* `TransactionOutput` is consistent with the *authenticated* `TransactionInfo` obtained from a backup/archive/proof — only asserts equality of `status`, `gas_used`, `write_set_hash` (== `state_change_hash`), and `event_root_hash`: [3](#0-2) 

It stops short of comparing `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` against any value derived from the replay. The comment left in the code explicitly states the consequence: *"this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."* [4](#0-3) 

This function is wired into every replay/verification consumer as the sole correctness gate for re-executed output vs. the trusted, proof-backed `TransactionInfo`:
- `db-tool`'s archive verifier, which walks an entire backup and calls this exact check per transaction: [5](#0-4) 
- The chunk executor's `verify_execution_mode` path used during backup restore/verify: [6](#0-5) 
- The `aptos-debugger` and `aptos move` CLI replay commands: [7](#0-6) [8](#0-7) 

Because the comparator entirely skips the state/hot-state/position-state root fields, any divergence between the locally computed post-state (Jellyfish Merkle Tree root, hot-state root, or native-position state root) and the authenticated value carried by the ledger's `TransactionInfo` will pass silently. This is distinct from `TransactionOutputListWithProof::verify` (the on-chain, consensus-authenticated accumulator-proof path used by state-sync/light-client verification), which likewise does not check these checkpoint hashes either — it only checks events, write-set hash, gas, status, and transaction hash [9](#0-8) , meaning any consumer relying on `TransactionOutputListWithProof`/`TransactionOutputListWithProofV2` for authenticated state roots has no cryptographic assurance that the state-checkpoint/hot-state/position roots embedded in `TransactionInfo` correspond to the actual state produced by the transaction, only that they are *part of a hash* covered by the accumulator (the outer accumulator proof covers `TransactionInfo.hash()`, which does include these fields, but nothing locally checks that the value inside actually reflects the correct state, other than the executor's own internal state-checkpoint computation at commit time).

The primary, concretely provable gap is in the **replay-side** integrity check (`ensure_match_transaction_info`): it is the exact mechanism meant to catch consensus-vs-replay divergence for state roots and it structurally cannot, by construction, catch a state-checkpoint-hash or position-state-root divergence, since those fields are never read from `txn_info` in the function body.

### Impact Explanation
State-checkpoint hashes are the SMT/JMT root of the post-transaction global state and (for `V1`) the hot-state and native-position ("trading-native") state roots — i.e., exactly the proof-integrity values callouts like "wrong accumulator root, Merkle proof... state proof accepted as valid" and "hard-fork-only divergence during commit, replay, restore" are meant to guard. Since replay/restore verification tooling built on `ensure_match_transaction_info` cannot detect a mismatch in these fields, a bug in the state-checkpoint computation path (e.g., in `DoStateCheckpoint`, JMT/position-state pipeline, or hot-state materialization) that silently corrupts the committed state root would go undetected by all of `replay_on_archive`, `chunk_executor::verify_execution` (backup restore verification), and CLI/debugger replay tooling — even though these tools are explicitly relied upon operationally to catch exactly this class of divergence before/after hard forks or during archive-node consistency audits.

### Likelihood Explanation
This is a code-completeness gap rather than an actively exploited attacker-triggerable bug: it does not by itself corrupt consensus-committed state (validators still compute and gossip the correct roots through the normal state-checkpoint/ledger-update pipeline, and the accumulator hash still covers the full `TransactionInfo` including these fields). The risk materializes only if/when the state-checkpoint or position-state computation itself has (or develops) a bug — at that point, this comparator would be the safety net that operators rely on to catch it during replay-verify, and it structurally cannot. The in-repo `TODO` comment confirms the authors are aware and intend to close this before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (currently gated by that on-chain feature flag), which limits current exposure to the native-position/trading-native rollout but does not address the pre-existing gap for regular `state_checkpoint_hash`/`hot_state_checkpoint_hash`.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` to also compare a locally-recomputed `state_checkpoint_hash` (only at checkpoint-index boundaries, consistent with how `DoLedgerUpdate`/`DoStateCheckpoint` populate it), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields on the supplied `txn_info`, threading through whatever checkpoint-hash inputs are available to callers (`replay_on_archive`, `chunk_executor::verify_execution`, CLI/debugger). At minimum, gate enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and any future hot-state-in-consensus rollout) on closing this comparator gap, as the code comment itself specifies.

### Proof of Concept
Not independently exploitable as a live attack; the code path itself is the proof: `ensure_match_transaction_info`'s body [3](#0-2)  never reads `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`, and it returns `Ok(())` unconditionally once status/gas/write-set/event checks pass. Constructing a `TransactionOutput` whose write set, events, gas, and status match a given `TransactionInfo`, but which was computed under a mutated/incorrect state-checkpoint or position-state root, would pass `ensure_match_transaction_info` and thus pass `db-tool`'s `execute_and_verify`/`replay_on_archive` verification unnoticed [10](#0-9) , and would similarly pass `chunk_executor`'s backup-verify path [11](#0-10) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
