### Title
Missing beneficiary-existence check in `DeleteAccountAction` causes deleted account's balance to be permanently burned - ([File: runtime/runtime/src/actions.rs])

### Summary
`DeleteAccountAction::beneficiary_id` is only validated for syntactic correctness (`validate_action_account_id`), never for whether the account actually exists or is capable of being auto-created. When an account is deleted, its remaining balance is sent as a `Receipt::new_balance_refund` to `beneficiary_id`. If that account does not exist and is not an implicit-account id (so it cannot be created on the fly), the resulting transfer receipt fails with `AccountDoesNotExist`, and — because refund receipts are treated specially — the funds are simply burned instead of being returned to anyone. This is the direct nearcore analog of the Sherlock report's missing zero-address check: an unprivileged signer can pick a "receiver" that cannot actually receive the funds, and there is no validation stopping the transaction, resulting in permanent loss of the deleted account's balance.

### Finding Description
- `validate_delete_action` only checks that `beneficiary_id` is a syntactically valid `AccountId`; it performs no existence check: [1](#0-0) 

- When the `DeleteAccount` action executes, the account's remaining balance is unconditionally pushed as a balance-refund receipt to `beneficiary_id`, with no check that the beneficiary account exists: [2](#0-1) 

- That refund is a `Receipt::new_balance_refund`, whose `predecessor_id` is `"system"` — i.e. treated as a refund receipt at execution time: [3](#0-2) 

- `check_account_existence` explicitly disallows implicit creation of a nonexistent account when it is a `Transfer` action inside a refund receipt whose target account type is not implicit — confirmed by the dedicated regression test `refund_may_not_create_universal_account`, which shows that a `Receipt::new_balance_refund` targeting a nonexistent, non-implicit account id fails with `ActionErrorKind::AccountDoesNotExist` and the account is never created: [4](#0-3) [5](#0-4) 

- Finally, when a refund receipt (predecessor is "system") fails, the deposit amount is not retried or returned anywhere — it is added to `stats.balance.other_burnt_amount`, permanently removing it from circulation: [6](#0-5) 

Put together: any account owner can submit a `DeleteAccountAction` naming a syntactically-valid but nonexistent, non-implicit `beneficiary_id` (e.g. `"nonexistent-name.near"`). The account is deleted, its balance is packaged into a balance-refund receipt to that beneficiary, that receipt fails because the account doesn't exist and can't be auto-created, and the balance is burned rather than transferred or returned to the original (now-deleted) account. This mirrors the reported bug class: no check that the "receiver" of a fund transfer can actually receive it, leading to unrecoverable loss of user funds.

### Impact Explanation
This causes permanent, unrecoverable loss of user funds equal to the entire remaining balance of the deleted account. Because there is no zero-/invalid-receiver check, and the failure mode for a refund receipt is silent token burning rather than an error returned to the submitter before execution, users (or relayers building this transaction on a user's behalf, e.g. via meta-transactions) can accidentally (or a malicious relayer could deliberately) cause deletion of an account with an unreachable beneficiary, destroying the deleted account's entire balance. This is a concrete, unauthorized value-destruction bug reachable by a single transaction from an unprivileged signer — satisfying "permanently frozen/lost funds."

### Likelihood Explanation
Likelihood is fully within reach of an ordinary user or relayer: `DeleteAccountAction` is directly triggerable by any account holder via a standard `SignedTransaction` or via a meta-transaction/delegate action (see `meta_tx_delete_account` test showing a relayer can submit this on a user's behalf). No special privileges, staking, or state manipulation are required — only a `beneficiary_id` that passes format validation but does not correspond to an existing (non-implicit) account, which is trivial to construct (e.g. any not-yet-registered `some-name.near`). The scenario could occur accidentally through user/relayer error (typo in beneficiary) or be deliberately induced, e.g. by a malicious/faulty relayer front-ending a delete-account meta-transaction with an unreachable beneficiary.

### Recommendation
Add an existence check for `beneficiary_id` prior to (or as part of) executing `DeleteAccountAction`, analogous to how `Transfer` actions validate account existence/implicit-creation eligibility. Options:
- Reject the `DeleteAccount` action outright at validation/execution time if the beneficiary account does not exist and is not implicit-creatable (return an explicit action error to the submitter rather than silently burning funds), or
- If the beneficiary account does not exist, refund the balance back to the deleted account's original `actor_id`/predecessor via a non-refund transfer receipt (which supports proper error surfacing/implicit-account creation) instead of a system-refund receipt that burns on failure.

### Proof of Concept
1. Create account `alice.near` and fund it with N.
2. Submit `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nobody-registered.near" })` for `alice.near`, where `nobody-registered.near` is a syntactically valid `AccountId` that has never been created and is not an implicit-account id.
3. `validate_delete_action` passes (format is valid).
4. `action_delete_account` deletes `alice.near` and enqueues `Receipt::new_balance_refund(&"nobody-registered.near", N)`.
5. During execution of that refund receipt, `check_account_existence` rejects the `Transfer` because the account does not exist and is not implicit-creatable → receipt fails with `AccountDoesNotExist` (as demonstrated by the existing test `refund_may_not_create_universal_account`, which specifically asserts this outcome and that no account is created).
6. Because `receipt.predecessor_id().is_system()` is true and the result is an error, the deposit `N` is added to `other_burnt_amount` and permanently removed from any account's balance — `alice`'s original funds are unrecoverably lost.
