### Title
Token exchange trusts an unverified caller-supplied `shop` parameter instead of the session token's own `dest` claim - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
`tokenExchange()` decodes and cryptographically verifies the `sessionToken` (audience/signature only) but then **discards the verified payload** and uses a separately supplied `shop` argument to build both the outbound OAuth request URL and the resulting `Session` object. Nothing cross-checks that the caller-supplied `shop` actually matches the `dest` claim embedded in the verified session token, mirroring the Hyperdrive bug where a caller-supplied identity parameter (`_lp`) was used for a privileged action instead of the verified actor (`msg.sender`/token claim).

### Finding Description
In `tokenExchange()`, the session token is verified only for signature and audience via `decodeSessionToken(config)(sessionToken)`, and its return value (which contains the trustworthy `dest` claim identifying the shop the token was actually issued for) is never used: [1](#0-0) 

The `shop` used to build the outbound request domain and the resulting `Session.shop` comes entirely from the caller-supplied `shop` parameter, sanitized only for format, not cross-validated against the token's `dest`: [2](#0-1) 

This exact "verify the credential, but perform the privileged action using a different, attacker-controlled identity parameter" pattern is what the analog report identifies (using `_lp` for the transfer while never validating it against `msg.sender`).

This pattern is also present, unauthenticated, in the ShopifyAdmin distribution branch of the React Router adapter, where `shop` is read directly from the request URL query string with no signature/claim binding, then passed straight into the token-exchange strategy: [3](#0-2) [4](#0-3) 

Compare this to the non-ShopifyAdmin branch, which correctly derives `shop` from the verified `payload.dest`, showing the mismatched trust boundary is a genuine inconsistency rather than intended design: [5](#0-4) 

The library's own documentation reinforces this unsafe pattern for direct API consumers, showing `shop` taken from `req.query.shop` independently of the session token used in the same call: [6](#0-5) 

### Impact Explanation
If an attacker who holds a legitimately-issued session token for their own shop (e.g., from having installed the app on a shop they control) sends a request with a different, victim `shop` value, `tokenExchange()` will build an OAuth `access_token` request against `https://{attacker-chosen-shop}/admin/oauth/access_token` using the attacker's own subject token, and — regardless of what the Shopify token endpoint decides — will construct and persist a local `Session` object whose `shop` field is the attacker-chosen value rather than the value cryptographically bound to the token (`payload.dest`). Any code path that trusts `Session.shop` as the tenant identifier (session storage keying, `getOfflineId`/`getJwtSessionId`, admin API client construction) can then be fed a mismatched shop/session pairing, i.e., a session-storage integrity/cross-tenant confusion issue rooted entirely in this package's local logic.

### Likelihood Explanation
Reachable by any actor holding a valid session token for any shop where the app is installed (a normal, unprivileged merchant/customer under the app), simply by supplying an arbitrary `shop` value alongside their own token — exactly as demonstrated in the library's own documented `/auth` usage and exercised automatically in the `AppDistribution.ShopifyAdmin` code path, which reads `shop` straight from the URL query string with no cryptographic binding.

### Recommendation
In `tokenExchange()`, use the verified payload returned from `decodeSessionToken` to derive the shop (`new URL(payload.dest).hostname`) instead of trusting the caller-supplied `shop` parameter, or explicitly assert `sanitizeShop(config)(shop, true) === new URL(payload.dest).hostname` and reject the exchange otherwise. Apply the same cross-check in `getSessionTokenContext`'s `AppDistribution.ShopifyAdmin` branch before using the URL `shop` parameter for any session-storage or token-exchange operation.

### Proof of Concept
1. Attacker installs the app on `evil.myshopify.com` and obtains a valid Shopify session token (`aud` = app's API key, `dest` = `https://evil.myshopify.com`).
2. Attacker issues a request to the app with `?shop=victim.myshopify.com` and `Authorization: Bearer <attacker-token>` (or via the documented `/auth?shop=victim.myshopify.com&id_token=<attacker-token>` pattern).
3. `decodeSessionToken` verifies the token's signature/audience successfully (it is a legitimate, unexpired token, just for a different shop) and its payload is discarded.
4. `tokenExchange()` proceeds using `shop = 'victim.myshopify.com'` to build the request URL and, on any successful/erroneous-but-handled response, to construct/store a `Session` with `shop: 'victim.myshopify.com'` while the token's actual verified identity (`evil.myshopify.com`) is never checked against it.
