### Title
SVM inbound listener trusts any "Program data" log matching a known discriminator without binding it to the actual gateway program invocation, enabling forged `send_funds` inbounds — (File: `universalClient/chains/svm/event_listener.go`, `universalClient/chains/svm/event_parser.go`)

### Summary
The SVM gateway event listener discovers candidate transactions via `GetSignaturesForAddress(gatewayAddr)` [1](#0-0) , then iterates over **every** log line of the fetched transaction (`tx.Meta.LogMessages`) and classifies each line purely by whether it starts with `"Program data: "` and decodes to a payload whose first 8 bytes match a known event discriminator [2](#0-1) [3](#0-2) . Nothing in `determineEventType`, `ParseEvent`, or `parseSendFundsEvent` associates the matched log line with which program actually invoked the `sol_log_data` syscall that produced it, nor with any inner-instruction/token-balance evidence of real value moving into the gateway [4](#0-3) .

### Finding Description
`GetSignaturesForAddress` on Solana returns any transaction where the given address appears in the account key list, whether or not that address's program was ever invoked. An unprivileged attacker can:
1. Read the public `GatewayMethods.EventIdentifier` discriminators for `send_funds` from `x/uregistry` chain config (this is public registry data).
2. Deploy their own Solana program (no privilege required) or use any program that lets them emit an arbitrary `sol_log_data` payload.
3. Submit a single transaction that (a) lists the real gateway program address as one of the transaction's accounts (so it is indexed by `getSignaturesForAddress`), and (b) invokes their own program, which emits `"Program data: " + base64(discriminator || attacker_sender || attacker_recipient || attacker_token || attacker_amount || ...)"` with the `send_funds` discriminator and completely attacker-chosen Borsh fields.
4. Because `processSignatureBatch` fetches the whole transaction and scans **all** `LogMessages` regardless of which program emitted them [2](#0-1) , and `determineEventType`/`parseSendFundsEvent` only check the discriminator bytes and the log's syntactic prefix, this forged log is accepted identically to a real gateway emission and turned into a `store.Event` of `store.EventTypeInbound` with attacker-controlled `sender`, `recipient`, `bridge_token`, `bridge_amount`, `payload`, and `revert_recipient` fields [4](#0-3) .

Because every honest Universal Validator runs the identical `universalClient` code against the identical, immutable Solana ledger, they will **all** independently observe the same forged log and submit the same `MsgVoteInbound` with matching fields (the ballot key is a canonical hash over sender/recipient/amount/asset, so identical forged data converges on one ballot) [5](#0-4) [6](#0-5) . Quorum is reached honestly (2/3+ of UVs voting identical, attacker-forged data), and `VoteInbound` proceeds to `ExecuteInbound`, minting/crediting the attacker-specified recipient — with no independent check that real tokens were locked into the gateway's vault/account, since `x/uexecutor`'s inbound validation only checks chain/token whitelisting and structural correctness, not proof of an actual asset transfer within the observed transaction.

I was not able to fully verify from the index whether `ValidateForExecution`/`NormalizeForTxType` in `x/uexecutor/types/inbound.go` perform any additional cross-check against the SVM transaction's real token balance deltas (e.g., `PreTokenBalances`/`PostTokenBalances`) before minting — a `grep_search` for such correlation in `universalClient/chains/svm/**` returned no matches, indicating the client-side parser itself performs no such binding. This is the load-bearing gap.

### Impact Explanation
If confirmed, this allows an unprivileged attacker to mint/credit unlimited value on Push Chain (or trigger arbitrary payload execution routed through the UEA, since `payload`/`RawPayload` is also attacker-controlled) without ever depositing real funds into the SVM gateway, purely by crafting a transaction whose logs mimic the gateway's event encoding. This is a direct unauthorized-mint / fund-fabrication vulnerability, matching the "Required Impacts" of unauthorized mint/unauthorized module-originated EVM execution from a forged inbound accepted through user-reachable flows with fully honest validators/nodes.

### Likelihood Explanation
High, if the described program/log semantics hold: it requires no validator, TSS, or admin collusion — only the ability to submit an ordinary Solana transaction that references the gateway address as an account and to know the public discriminator value. Both are available to any unprivileged actor.

### Recommendation
Bind matched `"Program data: "` log lines to the specific gateway program invocation that produced them (e.g., by tracking `Program <gatewayAddr> invoke [n]` / matching `success` frames, or using `Meta.InnerInstructions`/simulated CPI stack to ensure the log was emitted while the gateway program was the active frame), rather than scanning the flattened `LogMessages` array irrespective of program origin. Additionally, cross-validate `send_funds` inbound amounts/tokens against actual SPL token balance deltas (`PreTokenBalances`/`PostTokenBalances`) or vault-account state changes in the same transaction before allowing the event to reach ballot voting.

### Proof of Concept
Not independently executable from the indexed code alone (would need a local validator + deployed attacker program to emit a crafted `sol_log_data` line, then run the real `EventListener`/`parseSendFundsEvent` against it and confirm `store.Event` is produced identically to a genuine gateway emission — matching the suggested "Fast validation" in the question). Given the repository's size limits, I could not confirm the full downstream `ValidateForExecution` logic in `x/uexecutor/types/inbound.go` line-by-line to rule out a late-stage balance-proof check; a Devin session with full file access should verify that file before finalizing severity.

// determineEventType determines the event type based on the log discriminator
func (el *EventListener) determineEventType(log string) string {
	if !strings.HasPrefix(log, "Program data: ") {
		return ""
	}

	eventData := strings.TrimPrefix(log, "Program data: ")
	decoded, err := base64.StdEncoding.DecodeString(eventData)
	if err != nil {
		return ""
	}

	if len(decoded) < 8 {
		return ""
	}

	discriminator := strings.ToLower(hex.EncodeToString(decoded[:8]))

	// Look up event type from discriminator map
	eventType, ok := el.discriminatorToEventType[discriminator]
	if !ok {
		return ""
	}

	return eventType

// parseSendFundsEvent parses a sendFunds event as UniversalTx
func parseSendFundsEvent(log string, signature string, slot uint64, logIndex uint, chainID string, logger zerolog.Logger) *store.Event {
	if !strings.HasPrefix(log, "Program data: ") {
		return nil
	}

	eventData := strings.TrimPrefix(log, "Program data: ")
	decoded, err := base64.StdEncoding.DecodeString(eventData)
	if err != nil {
		return nil
	}

	if len(decoded) < 8 {
		return nil
	}

	// Create EventID in format: signature:LogIndex
	eventID := fmt.Sprintf("%s:%d", signature, logIndex)

	logger.Debug().
		Str("event_id", eventID).
		Str("signature", signature).
		Uint("log_index", logIndex).
		Uint64("slot", slot).
		Msg("processing sendFunds event")

	// Create store.Event
	event := &store.Event{
		EventID:           eventID,
		BlockHeight:       slot,
		Type:              store.EventTypeInbound, // Gateway events from external chains are INBOUND
		Status:            store.StatusPending,
		ExpiryBlockHeight: 0, // Will be set based on confirmation type if needed
	}

	// Parse event data from this log
	parseUniversalTxEvent(event, decoded, logIndex, chainID, logger)

	return event
}

	}
