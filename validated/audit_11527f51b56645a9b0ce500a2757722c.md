Found and confirmed a strong analog: the `docs/architecture/how/meta-tx.md` documentation explicitly describes a **known, currently-active, designed-in inconsistency** matching the FIAT-DAO bug class exactly — a restriction on a sender's account (function-call access key allowance limit) that is enforced when the sender acts directly, but is silently **not checked at all** when the same privileged action is routed indirectly through a delegated/relayed path.

### Title
Function-call access-key allowance restriction is bypassed entirely when the action is routed through a meta-transaction (DelegateAction) - (File: `runtime/runtime/src/actions.rs`, function `validate_delegate_action_key`)

### Summary
NEAR's `FunctionCallPermission` access key allows an account owner to limit a key's spending power via an `allowance` field, enforced on direct transactions in `verify_and_charge_tx_ephemeral` via `check_and_compute_new_allowance`. When the exact same access key signs a `DelegateAction` (NEP-366 meta-transaction) instead, `validate_delegate_action_key` checks receiver, method name, and deposit constraints, but never checks or debits the allowance, because the relayer pays for gas/fees on its own shard, not the sender's. This is the same "inconsistent enforcement of an owner-level restriction across two code paths (direct vs. delegated) that should apply the same invariant" pattern as the referenced FIAT-DAO `VotingEscrow.increaseUnlockTime` bug, where a check applied on the direct path is skipped when the action is instead executed through a delegated identity.

### Finding Description
- Direct-transaction path: `verify_and_charge_tx_ephemeral` (`runtime/runtime/src/verifier.rs:312-404`) calls `check_and_compute_new_allowance` (`runtime/runtime/src/verifier.rs:282-303`), which fails the transaction with `NotEnoughAllowance` if `total_cost` exceeds the key's remaining allowance, and otherwise debits the allowance. [1](#0-0) [2](#0-1) 
- Delegated-transaction path: `validate_delegate_action_key` (`runtime/runtime/src/actions.rs:574-728`), which is the function that validates the same `FunctionCallPermission` access key when it signs a `DelegateAction`, checks nonce, deposit-with-function-call, receiver mismatch, and method-name mismatch — but contains **no call whatsoever** to `check_and_compute_new_allowance` or any allowance debiting logic. [3](#0-2) 
- This is not accidental oversight in review — it is explicitly documented behavior in `docs/architecture/how/meta-tx.md`, which states plainly: *"For allowance, however, there is no check... even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work."* [4](#0-3) 
- The root cause parallels the FIAT-DAO M-03 pattern precisely: an owner-imposed spending/permission restriction is enforced on the account's *own* signing path, but the code path that handles the *delegated* identity (bob/relayer analog) omits the check entirely, letting an unprivileged holder of a restricted key bypass the very restriction the key was created to enforce.

### Impact Explanation
An app or user that issues a `FunctionCall`-only access key with a small `allowance` (intending to cap how much NEAR balance/gas that key can ever authorize spending of from the owner's account) has that guarantee completely voided the moment any relayer is willing to wrap the same key's action in a `DelegateAction`. The key holder — who may be a semi-trusted bot, browser session, or third-party integration meant to be capped at, say, 0.01 NEAR of spend — can use a public/self-hosted relayer to execute unlimited calls under that key with no allowance ever being decremented or checked, defeating the security boundary the allowance was designed to provide. This does not create new tokens or forge signatures, but it is a concrete bypass of an access-control invariant (a fee/gas-authorization limit) that application developers rely on for economic safety of delegated keys.

### Likelihood Explanation
Trivial to trigger by any unprivileged holder of a `FunctionCall`-permission access key: they only need to construct a `SignedDelegateAction` with that key and submit it to any relayer (including a self-controlled account acting as its own relayer, paying its own gas). No special privileges, validator status, or race conditions are required — this is a straightforward, always-reachable protocol behavior on the standard meta-transaction execution path (`apply_delegate_action` → `validate_delegate_action_key`).

### Recommendation
Enforce the same allowance semantics in `validate_delegate_action_key` as in `check_and_compute_new_allowance`/`verify_and_charge_tx_ephemeral`: when the signing access key has a `FunctionCallPermission` with `Some(allowance)`, compute the relevant cost attributable to the sender's key usage (or, at minimum, document/gate this as a deliberate, bounded-risk protocol decision requiring wallets/dApps to never rely on `allowance` as a hard cap once a key can be used via meta-transactions) and reject/debit accordingly, mirroring the direct-transaction path so the invariant "an allowance-limited key can spend at most `allowance`" holds uniformly regardless of whether the action reaches the runtime via a direct transaction or a `DelegateAction`.

### Proof of Concept
1. Owner `alice` creates a `FunctionCall` access key for `alice`, scoped to `receiver=bob`, `method=log_something`, with `allowance = 1 yoctoNEAR` (an amount insufficient to cover even one direct call's gas/cost).
2. A holder of that key constructs `DelegateAction{ sender_id: alice, receiver_id: bob, actions: [FunctionCall(log_something)], public_key: <that key> }`, signs it, and submits it wrapped by any relayer account (e.g., a throwaway self-funded account) via `Action::Delegate`.
3. `apply_delegate_action` → `validate_delegate_action_key` validates receiver/method/nonce successfully and returns `Ok`, with no allowance check performed; the call executes successfully.
4. Confirmed by the existing test `meta_tx_fn_call_access_key_insufficient_allowance` in `integration-tests/src/tests/features/delegate_action.rs:397-431`, which asserts the call **succeeds** ("this should still succeed because we use the gas of the relayer, not of the access key") despite the allowance being only 1 yoctoNEAR — demonstrating the allowance restriction is unconditionally bypassable via the delegated path. fn check_and_compute_new_allowance(
```rust
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
```

```markdown
## Function access keys in meta transactions

Assume alice sends a meta transaction and signs with a function access key.
How exactly are permissions applied in this case?

Function access keys can limit the allowance, the receiving contract, and the
contract methods. The allowance limitation acts slightly strange with meta
transactions.

But first, both the methods and the receiver will be checked as expected. That
is, when the delegate action is unwrapped on Alice's shard, the access key is
loaded from the DB and compared to the function call. If the receiver or method
is not allowed, the function call action fails.

For allowance, however, there is no check. All costs have been covered by the
relayer. Hence, even if the allowance of the key is insufficient to make the call
directly, indirectly through meta transaction it will still work.

This behavior is in the spirit of allowance limiting how much financial
resources the user can use from a given account. But if someone were to limit a
function access key to one trivial action by setting a very small allowance,
that is circumventable by going through a relayer. An interesting twist that
comes with the addition of meta transactions.
```
