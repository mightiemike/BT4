### Title
Wrong `receiver_id` Used in `validate_delegate_action` for `DeterministicStateInit` Inner-Action Validation — (`runtime/runtime/src/action_validation.rs`)

### Summary

`validate_delegate_action` passes the **outer transaction's `receiver_id`** instead of the **`DelegateAction`'s own `receiver_id`** when recursively validating inner actions. For `DeterministicStateInit` actions, this means the receiver-derivation check (`derive(state_init) == receiver_id`) is performed against the wrong account, breaking the authorization invariant that the validated identity must match the entity that will actually execute the action.

### Finding Description

In `runtime/runtime/src/action_validation.rs`, `validate_delegate_action` selects the `inner_receiver` to pass to `validate_actions_with_mode`:

```rust
let inner_receiver =
    if ProtocolFeature::FixDelegatedDeterministicStateInit.enabled(current_protocol_version) {
        delegate_action.receiver_id()   // correct
    } else {
        receiver                        // BUG: outer tx receiver_id, not delegate's receiver_id
    };
``` [1](#0-0) 

`validate_deterministic_state_init` then checks:

```rust
let derived_id = derive_near_deterministic_account_id(&action.state_init);
if derived_id != *receiver_id {
    return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver { ... });
}
``` [2](#0-1) 

When the outer transaction's `receiver_id` (the meta-tx sender / relayer target) differs from the `DelegateAction`'s `receiver_id` (the actual inner-action target), the check is performed against the wrong account. This is the direct analog of the ERC20 bug: the wrong identity (`outer_tx.receiver_id` instead of `delegate_action.receiver_id`) is used in the authorization check.

The exploit scenario is documented in the test suite:

> "Craft the exploit: `outer_tx.receiver = det_account_b = derive(state_init_b)`. Old check: `det_account_b == derive(state_init_b)` passes. The delegate action targets `det_account_a`, which is the wrong account." [3](#0-2) 

### Impact Explanation

Two concrete effects:

1. **Contract execution flow breakage (legitimate meta-transactions blocked):** Any user who submits a valid meta-transaction where `outer_tx.receiver_id ≠ delegate_action.receiver_id` and the inner action is `DeterministicStateInit` targeting the correct derived account will have their transaction rejected at tx validation with `InvalidDeterministicStateInitReceiver`. This makes `DeterministicStateInit` inside meta-transactions completely unusable on pre-fix protocol versions.

2. **Gas drain on relayers (malicious path):** An attacker can craft a meta-transaction where `outer_tx.receiver_id = derive(state_init_b)` (passes the wrong check) but `delegate_action.receiver_id = det_account_a` (wrong target). The transaction passes initial validation, the relayer pays gas, but the receipt fails at the secondary `validate_receipt` check with `NewReceiptValidationError::ActionsValidation(InvalidDeterministicStateInitReceiver)`. [4](#0-3) 

The codebase itself documents: *"The bug cannot be abused [for fund theft], if someone crafts a state init that passes validation here, it will fail when it is checked as incoming receipt."* The primary in-scope impact is **contract execution flow breakage** — legitimate meta-transactions with `DeterministicStateInit` are blocked.

### Likelihood Explanation

Any unprivileged user can trigger this by submitting a meta-transaction (via the standard JSON-RPC `broadcast_tx_async` / `broadcast_tx_commit` endpoints) containing a `DelegateAction` with a `DeterministicStateInit` inner action. No special privileges, validator access, or key compromise is required. The trigger is a normal transaction submission path.

### Recommendation

Use `delegate_action.receiver_id()` — not the outer `receiver` — when validating inner actions of a `DelegateAction`. The fix is already present in the codebase gated behind `ProtocolFeature::FixDelegatedDeterministicStateInit` (protocol version 85):

```rust
// Correct: always use the delegate's own receiver_id
let inner_receiver = delegate_action.receiver_id();
validate_actions_with_mode(limit_config, &actions, inner_receiver, ...)?;
``` [5](#0-4) 

### Proof of Concept

The repository contains a complete integration test demonstrating both the pre-fix and post-fix behavior:

- `test_deterministic_state_init_meta_tx_receiver_check_pre_fix`: confirms the exploit transaction passes initial tx validation on protocol version < 85, then fails at receipt validation.
- `test_deterministic_state_init_meta_tx_receiver_check`: confirms the fix catches the exploit at tx validation on protocol version ≥ 85. [6](#0-5) 

The exploit transaction structure:
- `outer_tx.receiver_id = det_account_b` where `derive(state_init_b) = det_account_b`
- `delegate_action.receiver_id = det_account_a` (wrong target)
- Inner action: `DeterministicStateInit { state_init: state_init_b, deposit: 0 }`

With the bug: `validate_deterministic_state_init` checks `derive(state_init_b) == det_account_b` (outer receiver) → passes. The receipt then targets `det_account_a`, which fails the secondary check. Legitimate meta-transactions with the correct `delegate_action.receiver_id` are rejected because `derive(state_init) != outer_tx.receiver_id`. [7](#0-6)

fn try_meta_tx_deterministic_receiver_exploit(
    protocol_version: ProtocolVersion,
) -> Result<FinalExecutionOutcomeView, InvalidTxError> {
    let mut env = TestEnv::setup_with_version(Balance::from_near(100), protocol_version);
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let (_state_init_a, det_account_a) = env.new_deterministic_account_with_data(small());
    let (state_init_b, det_account_b) = env.new_deterministic_account_with_data(big());
    assert_ne!(det_account_a, det_account_b);

    // Deploy det_account_b and add a full-access key so it can act as meta_tx_sender.
    let user_signer = create_user_test_signer(&env.user_account());
    let storage_balance = env.balance_for_storage(state_init_b.clone());
    let deploy_tx = SignedTransaction::deterministic_state_init(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        env.get_tx_block_hash(),
        state_init_b.clone(),
        storage_balance,
    );
    env.run_tx(deploy_tx);

    let meta_tx_sender_signer = create_user_test_signer(&det_account_b);
    let pk_base64 = near_primitives_core::serialize::to_base64(
        &borsh::to_vec(&meta_tx_sender_signer.public_key()).unwrap(),
    );
    let add_key_args = serde_json::json!([
        { "batch_create": { "account_id": det_account_b.as_str() }, "id": 0 },
        {
            "action_add_key_with_full_access": {
                "promise_index": 0,
                "public_key": pk_base64,
                "nonce": 0
            },
            "id": 0,
            "return": true
        }
    ]);
    let add_key_tx = SignedTransaction::call(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        Balance::from_near(2),
        "call_promise".to_owned(),
        serde_json::to_vec(&add_key_args).unwrap(),
        Gas::from_teragas(300),
        env.get_tx_block_hash(),
    );
    env.run_tx(add_key_tx);

    // Craft the exploit: outer_tx.receiver = det_account_b = derive(state_init_b).
    // Old check: det_account_b == derive(state_init_b) passes.
    // The delegate action targets det_account_a, which is the wrong account.
    // In no protocol version can this ever be allowed to be executed successfully.
    let relayer = env.independent_account();
    let relayer_signer = create_user_test_signer(&relayer);
    let inner_action = Action::DeterministicStateInit(Box::new(DeterministicStateInitAction {
        state_init: state_init_b,
        deposit: Balance::ZERO,
    }));
    let delegate_nonce = env.next_nonce_for(&det_account_b);
    let delegate_action = DelegateAction {
        sender_id: det_account_b.clone(),
        receiver_id: det_account_a,
        actions: vec![NonDelegateAction::try_from(inner_action).unwrap()],
        nonce: delegate_nonce,
        max_block_height: 1_000_000,
        public_key: meta_tx_sender_signer.public_key(),
    };
    let signed_delegate_action =
        SignedDelegateAction::sign(&meta_tx_sender_signer, delegate_action);
    let tx = SignedTransaction::from_actions(
        env.next_nonce(),
        relayer,
        det_account_b,
        &relayer_signer,
        vec![Action::Delegate(Box::new(signed_delegate_action))],
        env.get_tx_block_hash(),
    );
    env.try_execute_tx(tx)
}
