### Title
Rate-limiter key exhaustion DoS via unnormalized `msg.Body.Sender` string keying vs. normalized allowlist address check - ([File: core/services/gateway/handlers/functions/handler.functions.go])

### Finding Description
`functionsHandler.HandleLegacyUserMessage` performs the allowlist check on a *normalized* address (`common.HexToAddress(msg.Body.Sender)`), but keys `h.userRateLimiter.Allow(...)` on the *raw, un-normalized* `msg.Body.Sender` string: [1](#0-0) 

`go-ethereum`'s `common.HexToAddress` derives the address by hex-decoding the string and taking only the last 20 bytes (`BytesToAddress` truncates from the left), and is case-insensitive. This means many distinct raw strings (differing in case, leading zero-padding, or extra leading bytes) all collapse to the *same* allowed 20-byte address for the allowlist check, yet each distinct raw string is a *different* key in `h.userRateLimiter`, which creates a brand-new per-sender limiter bucket for every previously-unseen string (confirmed by the analogous, structurally identical per-sender limiter implementation at [2](#0-1) , which unconditionally inserts a new `rate.Limiter` into a `map[string]*rate.Limiter` for any unseen key with no eviction).

Critically, signature validation only happens later, inside `handleRequest` -> `hc.ValidatedRequestFromMessage`, *after* the rate limiter (and the bounded `pendingRequests` cache) has already been consulted: [3](#0-2) 

Because on-chain allowlisted addresses (Functions consumer contracts) are public information, an attacker does not need the private key of an allowlisted sender to pass the allowlist gate — they only need a string that `HexToAddress` parses down to a legitimate allowlisted address. By varying case/padding/extra leading hex bytes, an attacker can generate effectively unbounded distinct `msg.Body.Sender` strings that all pass the allowlist check but each allocate a new, permanent bucket in `h.userRateLimiter`. The `pendingRequests` cache is bounded by `MaxPendingRequests`, but the rate-limiter map growth happens independently and earlier, and is not capped by that config.

Separately, if `OnchainAllowlist` is left unconfigured (a supported, documented configuration — "Not specifying OnchainAllowlist config disables allowlist checks"), the allowlist gate is skipped entirely and any arbitrary attacker-chosen string reaches `h.userRateLimiter.Allow`, trivially producing unbounded keys.

### Impact Explanation
Each unique key creates a persistent in-memory `rate.Limiter` object with no expiry/cleanup mechanism visible in the codebase, leading to unbounded memory growth in the Functions gateway handler process. Sustained exploitation can degrade or crash the gateway node (denial of service on the DON-facing Functions request path), affecting availability for legitimate users of that DON.

### Likelihood Explanation
Feasible and repeatable by an unprivileged network attacker able to send legacy gateway messages: no signing key, no node-operator privilege, and no social engineering required. The attacker only needs (a) a DON with `OnchainAllowlist` unset, or (b) knowledge of any single publicly-known allowlisted consumer address, which is on-chain public data. Generating thousands of case/padding variants of that address string is trivial and cheap client-side.

### Recommendation
Normalize `msg.Body.Sender` (e.g., via `common.HexToAddress(...).Hex()`) before using it as the rate-limiter key, so it matches the same canonical identity used for allowlist authorization. Additionally, consider bounding the total number of per-sender buckets in the rate limiter (LRU eviction or TTL-based cleanup) and moving the rate-limit check to occur only for already-allowlisted, canonicalized senders.

### Proof of Concept
Unit/fuzz test plan for `handler.functions_test.go`:
1. Configure `functionsHandler` with an `OnchainAllowlist` mock that returns `true` for one canonical address `0xAAAA...AAAA` (via `sender.Hex()` comparison) and a `UserRateLimiter` with small `PerSenderBurst`/`PerSenderRPS`.
2. Fuzz `msg.Body.Sender` with thousands of syntactic variants that `common.HexToAddress` normalizes to `0xAAAA...AAAA` (mixed case, leading zero-padding, extra leading hex bytes beyond 20 bytes), each below the per-sender rate limit.
3. Call `HandleLegacyUserMessage` for each variant and assert that all pass the allowlist check (`ErrNotAllowlisted` not returned).
4. Instrument or expose the internal `perSender` map size of `h.userRateLimiter` (or measure heap growth via `runtime.MemStats`) and assert it grows linearly with the number of distinct variants sent, demonstrating unbounded key/memory growth despite all variants representing the same authorized address and none possessing a valid signature.

func (h *functionsHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	sender := common.HexToAddress(msg.Body.Sender)
	if h.allowlist != nil && !h.allowlist.Allow(sender) {
		h.lggr.Debugw("received a message from a non-allowlisted address", "sender", msg.Body.Sender)
		promHandlerError.WithLabelValues(h.donConfig.DonId, ErrNotAllowlisted.Error()).Inc()
		return ErrNotAllowlisted
	}
	if h.userRateLimiter != nil && !h.userRateLimiter.Allow(msg.Body.Sender) {
		h.lggr.Debugw("rate-limited", "sender", msg.Body.Sender)
		promHandlerError.WithLabelValues(h.donConfig.DonId, ErrRateLimited.Error()).Inc()
		return ErrRateLimited
	}

		h.lggr.Warnw("handleRequest: error adding new request", "sender", msg.Body.Sender, "err", err)
		promHandlerError.WithLabelValues(h.donConfig.DonId, err.Error()).Inc()
		return err
	}

func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
