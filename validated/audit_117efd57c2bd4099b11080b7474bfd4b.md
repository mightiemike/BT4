## Finding

### Title
Unrestricted generic `from_bytes<T>` forges arbitrary object capability structs (e.g. `ExtendRef`) for pre-existing objects - (File: `aptos-move/framework/natives/src/util.rs`)

### Summary
`native_from_bytes` in `aptos-move/framework/natives/src/util.rs` deserializes an arbitrary byte string into a value of caller-supplied type `T` purely by matching the BCS layout of `T`, with no notion of which module "owns" `T`, no provenance check, and no restriction on which types can be targeted [1](#0-0) . Because Move's generic type-substitution rules let any module name a foreign struct type as a type argument (field privacy only blocks struct-literal construction/pattern-matching, not naming the type), a caller can instantiate `from_bytes<object::ExtendRef>(bytes)` and get back a fully-formed `ExtendRef{ self: <attacker-chosen address> }` without ever going through `object::generate_extend_ref`, which is the only sanctioned constructor [2](#0-1) .

The sibling function `aptos_std::from_bcs::from_bytes<T>` is explicitly documented as dangerous for this exact reason and is therefore declared `native friend fun`, restricted to two trusted friend modules (`aptos_std::any`, `aptos_std::copyable_any`) [3](#0-2) . The `util` module's native (backed by the same Rust deserialization logic) does not carry that friend restriction in the framework, and the Rust native itself performs no type-identity or friend/visibility check — it only checks BCS-layout well-formedness [4](#0-3) .

Once an attacker holds a forged `ExtendRef` pointing at the address of an object that already exists (owned by someone else), `object::generate_signer_for_extending` unconditionally mints a `signer` for that address with no check that the `ExtendRef` was produced by the legitimate constructor path: [5](#0-4) . That forged signer can then be handed to any public API (e.g. `move_to`, resource-mutating entry functions, `object_code_deployment::upgrade`-style flows) that trusts "a signer at this address means the caller controls this object," letting the attacker mutate committed resource state at an address they never legitimately created.

### Finding Description
- `util::from_bytes<T>` has no ability or friend constraint tying `T` to the calling module, so it can target any struct defined anywhere in the framework, including single-field wrapper "capability" structs like `ExtendRef { self: address }`.
- BCS encoding of `ExtendRef` is just the 32-byte address, so an attacker only needs to supply the raw address bytes of a target object to synthesize a capability for it.
- `generate_signer_for_extending` (and analogous `DeleteRef`/`TransferRef` consumers) never re-validates that the ref's underlying object was created through `ConstructorRef::generate_extend_ref`; it trusts the struct's `self` field at face value [6](#0-5) .
- This breaks the capability-based authorization model the Object framework depends on: possession of an `ExtendRef`/`TransferRef` value is supposed to be proof of legitimate object ownership at construction time, but `from_bytes` lets that proof be fabricated out of thin air for any already-existing object address.

### Impact Explanation
If exploitable end-to-end, an unprivileged transaction could obtain a signer for any object address on mainnet and use it to `move_to`/mutate resources under `ObjectGroup`-style resource groups belonging to other users' objects (e.g., forging authority over fungible-asset stores, token metadata objects, or `ManagingRefs` used by `object_code_deployment`), corrupting committed resource state without holding the real capability. This is a state-integrity break, not merely a presentation issue.

### Likelihood Explanation
Likelihood depends entirely on: (1) whether `aptos_std::util::from_bytes` is declared `public` (unrestricted) rather than `friend`-gated in the deployed Move source, and (2) whether `ExtendRef`/`TransferRef` carry the `store` (or otherwise BCS-layout-derivable) ability so `type_to_type_layout` can produce a layout for them. I was able to confirm the Rust native imposes no such restriction and that the sibling `from_bcs::from_bytes` was deliberately friend-restricted specifically to prevent this class of forgery, which strongly suggests the risk is understood by the framework authors. However, I could not directly locate and read `aptos-move/framework/aptos-stdlib/sources/util.move` in this index to confirm its exact visibility/ability declaration for `from_bytes`, nor the literal `struct ExtendRef has ...` ability line in `object.move` in this repo snapshot — both were outside what my searches returned. This is a real limitation of the index, not a confirmation that the util-side restriction is absent.

### Recommendation
- Confirm in the actual framework source whether `aptos_std::util::from_bytes` is `public` or `friend`-restricted, and audit whether it is reachable with `T = object::ExtendRef` (or any other capability-bearing struct with only primitive fields) from unprivileged code.
- If reachable, restrict `util::from_bytes` the same way `from_bcs::from_bytes` is restricted (friend-only, or add ability/marker-trait bounds), or make `object`-module capability structs impossible to forge (e.g., wrap the address with a module-private marker/counter that can't be reconstructed from bytes alone, or have `generate_signer_for_extending` re-verify via a stored, non-forgeable on-chain marker at `self`).
- Add negative tests asserting `from_bytes<object::ExtendRef>`/`from_bytes<object::TransferRef>` either fail to compile (ability/friend violation) or fail at runtime against pre-existing objects.

### Proof of Concept
```
Given: target already-existing object address `A` (owned by victim), NOT created by attacker.

1. attacker constructs bytes = bcs::to_bytes(&A)          // 32 raw address bytes
2. forged_ref: object::ExtendRef = util::from_bytes<object::ExtendRef>(bytes)
3. victim_signer: signer = object::generate_signer_for_extending(&forged_ref)
4. move_to(&victim_signer, AttackerControlledResource { ... })
   // or call any entry fn expecting "owner signer of object A" using victim_signer

Expected (secure) behavior: step 2 or 3 aborts because forged_ref was never
produced via object::generate_extend_ref on a ConstructorRef the attacker owns.

Observed (if util::from_bytes is public/unrestricted for this T): step 2/3
succeed, giving attacker a signer for object A they never legitimately created,
enabling state mutation at A without holding the real capability.
```

Note: I could not fully verify the exact Move-level visibility of `util::from_bytes` or the ability annotations on `ExtendRef` in this repository snapshot due to index coverage limits — starting a full Devin session against the complete repository would let you directly inspect `aptos-move/framework/aptos-stdlib/sources/util.move` and the `struct ExtendRef has ...` declaration to close out this uncertainty.

fn native_from_bytes(
    context: &mut SafeNativeContext,
    ty_args: &[Type],
    mut args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    debug_assert_eq!(ty_args.len(), 1);
    debug_assert_eq!(args.len(), 1);

    // TODO(Gas): charge for getting the layout
    let layout = context.type_to_type_layout(&ty_args[0])?;

    let bytes = safely_pop_arg!(args, Vec<u8>);
    context.charge(
        UTIL_FROM_BYTES_BASE + UTIL_FROM_BYTES_PER_BYTE * NumBytes::new(bytes.len() as u64),
    )?;

    let function_value_extension = context.function_value_extension();
    let max_value_nest_depth = context.max_value_nest_depth();
    let val = match ValueSerDeContext::new(max_value_nest_depth)
        .with_legacy_signer()
        .with_func_args_deserialization(&function_value_extension)
        .deserialize(&bytes, &layout)
    {
        Some(val) => val,
        None => return Err(SafeNativeError::abort(EFROM_BYTES)),
    };

    Ok(smallvec![val])
}
