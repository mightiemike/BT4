### Title
Rounding-down `transferUsage` in resource undelegation lets an attacker reclaim delegated TRX capacity while dumping the associated bandwidth/energy usage debt onto the receiver - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Summary
`UnDelegateResourceProcessor.execute` computes `transferUsage` — the portion of the receiver's already-consumed bandwidth/energy usage that must move back to the delegating owner in proportion to the amount of TRX being undelegated — using double-precision arithmetic truncated to a `long`. Because this computation floors to zero for small `unDelegateBalance` values relative to the receiver's total frozen balance, an owner can split a large undelegation into many small ones, each returning `transferUsage = 0`, while each call still fully removes `unDelegateBalance` from the receiver's backing capacity (`AcquiredDelegatedFrozenV2BalanceForBandwidth`/`...ForEnergy`) and fully credits it back to the owner as unencumbered fresh capacity.

### Finding Description
In `execute()`: [1](#0-0) 
the code computes:
```
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
```
This is a floating-point multiplication followed by a truncating cast to `long` — i.e., rounded down. If `unDelegateBalance` is small relative to `receiverCapsule.getAllFrozenBalanceForBandwidth()` (which is easy to arrange when a receiver has substantial total frozen/delegated balance from many sources, or when the owner simply calls `UnDelegateResource` repeatedly with the minimum allowed amount, 1 TRX, per `validate()`'s only constraint `unDelegateBalance > 0`), `transferUsage` rounds to `0`.

Regardless of whether `transferUsage` is 0, the receiver's backing capacity is unconditionally reduced by the *full* `unDelegateBalance`: [2](#0-1) 
and the owner unconditionally regains the *full* `unDelegateBalance` as fresh capacity: [3](#0-2) 
while the usage-transfer step (`processor.unDelegateIncrease(...)`) is skipped entirely when `transferUsage <= 0`: [4](#0-3) 

This is structurally identical to the reported bug class: one side of a two-sided accounting operation ("seized"/reclaimed value — here, `unDelegateBalance` moved fully to the owner) is executed unconditionally and in full, while the other, proportionally-rounded side ("repaid shares" — here, `transferUsage`, meant to keep usage and capacity proportionally consistent between owner and receiver) can be rounded down to zero. Splitting the operation into many tiny transactions lets an attacker (the delegating owner) repeatedly trigger the zero-rounding case, so that in aggregate they reclaim 100% of the delegated TRX as fresh, usage-free capacity, while the receiver is left holding the full previously-accrued usage debt against a now-reduced capacity base (`AcquiredDelegatedFrozenV2BalanceForBandwidth`/`AllFrozenBalanceForBandwidth`).

The same pattern is duplicated for the `ENERGY` branch: [5](#0-4) 

### Impact Explanation
The receiver's effective bandwidth/energy budget (`calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`, driven by `getAllFrozenBalanceForBandwidth`/`ForEnergy`) shrinks in exact proportion to every undelegation, but the receiver's `netUsage`/`energyUsage` (the consumed debt) is not correspondingly reduced when `transferUsage` rounds to zero. Splitting the undelegation into many minimal-size (1 TRX) calls to `UnDelegateResource`/`UnDelegateResourceContract` (reachable directly via a broadcast transaction or TVM native contract call, no privileged role required) systematically forces `transferUsage = 0` on every step while the owner still recovers the full delegated principal as fresh capacity. Net effect: the receiver's usage-to-limit ratio degrades (their remaining free bandwidth/energy shrinks or goes negative relative to what it should be), while the delegating owner effectively launders back their full delegated TRX without inheriting any of the proportional usage debt that should accompany it under the intended accounting model. This is a resource-accounting integrity/DoS-adjacent issue for the receiver (degraded resource availability) caused purely by rounding, exploitable by any account with an existing delegation relationship, without needing incentives, favorable prices, or privileged access — directly analogous to the reported liquidation issue's "attacker splits into tiny operations, each rounding the counter-balancing value to zero while executing the primary value transfer in full."

### Likelihood Explanation
High reachability: `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` (native contract, reachable both from ordinary `UnDelegateResourceContract` transactions and from TVM contract calls) requires only that a delegation relationship already exists and `unDelegateBalance > 0`. The validation logic imposes no minimum-relative-size check between `unDelegateBalance` and the receiver's total frozen balance, and no check that `transferUsage` is proportionally consistent with the seized capacity. An attacker fully controls the split size and repetition count of their own undelegation calls, so triggering the rounding-to-zero condition repeatedly is trivial and requires no cooperation from the receiver or any external market conditions.

### Recommendation
Round `transferUsage` up (ceiling) instead of down, or use integer/BigInteger arithmetic that avoids losing the fractional usage share, analogous to the report's recommendation of ensuring the seized value is not greater than the repaid value. Concretely, mirror the receiver's frozen-balance reduction with a usage reduction that is rounded up (rather than truncated down) so that:
```
transferUsage = ceilDiv(receiverCapsule.getNetUsage() * unDelegateBalance,
                        receiverCapsule.getAllFrozenBalanceForBandwidth());
```
using `BigInteger`/ceiling-division (as already done elsewhere in the codebase, e.g. `divideCeil`/`divideCeilExact` in `RepositoryImpl.java`) so that any nonzero `unDelegateBalance` always transfers at least a proportional, non-zero share of usage when the receiver has nonzero usage, preventing the accumulation of unaccounted usage debt through repeated small undelegations.

### Proof of Concept
1. Attacker A delegates a large `FrozenV2BalanceForBandwidth` amount to receiver R (via `DelegateResource`), and R actively consumes bandwidth so `R.netUsage > 0` and `R.getAllFrozenBalanceForBandwidth()` is large (e.g., aggregated from multiple delegators).
2. A repeatedly calls `UnDelegateResource` (BANDWIDTH) with `unDelegateBalance = TRX_PRECISION` (the contract minimum, 1 TRX) many times.
3. On each call, in `UnDelegateResourceProcessor.execute`:
   - `transferUsage = (long)(R.netUsage * (1_000_000 / R.getAllFrozenBalanceForBandwidth()))` truncates to `0` whenever `R.getAllFrozenBalanceForBandwidth()` is sufficiently large relative to 1 TRX.
   - `R.getAcquiredDelegatedFrozenV2BalanceForBandwidth()` is decremented by the full `1_000_000` each call.
   - A's `FrozenBalanceForBandwidthV2` is incremented by the full `1_000_000` each call, with no usage debt attached (since `unDelegateIncrease` is skipped when `transferUsage == 0`).
4. After enough repetitions, A has reclaimed their entire delegated principal as fresh, unused capacity, while R's `netUsage` is unchanged and R's `AllFrozenBalanceForBandwidth` (and thus `calculateGlobalNetLimit`) has shrunk by the full undelegated amount — degrading R's available bandwidth relative to what the proportional accounting model intended.

Note: I was not able to fully trace `BandwidthProcessor.unDelegateIncrease`'s complete downstream effects (the read was truncated due to index size limits) to confirm every secondary consequence; a Devin session with full repository access would be needed to verify the exact numeric bounds under which `transferUsage` rounds to zero and to confirm there are no compensating checks further downstream.
