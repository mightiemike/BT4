### Title
Metering credit-balance drift between `Deduct` earmarking and `Settle` reconciliation allows overspend beyond reserved billing credits - (File: core/services/workflows/metering/metering.go)

### Summary
The CRE workflow-engine metering subsystem tracks a per-execution local credit balance (`balanceStore`) that mirrors credits reserved from the billing service (`SaiTub.ice`-analog). Just as the Sai bug computed `SaiTub.ice` and `SaiTub.tab(cup)` with different rounding/multiplication paths, the metering code computes the *earmarked* amount (`Deduct`) and the *actual settled* amount (`Settle`) using different mathematical paths (straight multiplication vs. median-aggregation + `CapDON_N` multiplication + per-unit conversion). When the settled amount exceeds the earmarked amount, the reconciliation step silently fails to apply the correction, leaving the local balance permanently inflated relative to true consumption.

### Finding Description
`ByResource` earmarks credits for a step by converting the requested amount directly: [1](#0-0) 

`Settle` later computes the *actual* spend independently: it aggregates per-node `SpendValue` strings via `medianSpend`, multiplies by `CapDON_N` (number of DON nodes), and only then converts to the credit balance via `ConvertToBalance`: [2](#0-1) 

The reconciliation step tries to return the difference between what was earmarked and what was actually spent to the local balance: [3](#0-2) 

`balanceStore.Add` explicitly rejects negative amounts instead of subtracting them: [4](#0-3) 

So when `spentCredits` (computed via median + `CapDON_N` + conversion) exceeds `step.Deduction` (computed via a simple multiplication in `ByResource`, or division/rounding in `ByDerivedAvailability`), `step.Deduction.Sub(spentCredits)` is negative, `Add` returns `ErrInvalidAmount`, and the local balance is left completely untouched — the overspend is never actually charged against `r.balance`. The code even acknowledges this is unexpected: `// invariant: capability should not let spend exceed reserve`, but only logs it at Info level and moves on: [5](#0-4) 

This is structurally the same bookkeeping flaw as the Sai report: two values that are supposed to stay entangled (`Deduction` vs. actual `spentCredits`) are computed via different formulas/roundings (exact multiply vs. median-then-multiply-then-convert, plus the `isGasSpendType` branch which applies `.Div(rate).Round(...)` in one direction and `.Mul(rate).Round(0)` in the other — not guaranteed to be inverses): [6](#0-5) 

Because `r.balance` (not the authoritative billing-service ledger) is what gates subsequent `Deduct` calls within the same execution (`ByResource`/`ByDerivedAvailability` call `r.balance.Minus(...)` and fail with `ErrInsufficientBalance` when balance is too low), an inflated local balance directly permits additional capability invocations to be earmarked that should have been blocked once the true reserved credit was exhausted.

### Impact Explanation
A workflow execution can locally believe it still has credit balance to spend on subsequent capability calls even after the reserved credit amount has effectively been exceeded by real, reported spend, because the reconciliation step silently no-ops instead of deducting the overspend. This lets a workflow (via ordinary, non-malicious rounding/aggregation drift or an anomalously-reporting node in the DON) run more paid capability invocations within one execution than its `ReserveCredits` allotment intended, i.e., a billing/credit-cap bypass driven purely by inconsistent internal accounting — not by any privileged action, matching the "misreporting/data tampering" impact category.

### Likelihood Explanation
The mismatch requires the settled spend (median of node-reported values × `CapDON_N`, converted through resource-specific rate logic) to exceed the originally earmarked deduction (computed through a different, simpler multiplication/conversion path). This is plausible whenever gas-token shifting/rounding (`Shift(18)`, `.Round(0)`, `.Round(defaultDecimalPrecision)`) or `CapDON_N` scaling produces a larger converted value than the initial `ConvertToBalance` estimate used at `Deduct` time — a rounding/formula divergence rather than an exotic edge case, consistent with the low-difficulty rating of the analogous Sai finding.

### Recommendation
- Ensure `Deduct` and `Settle` use the exact same mathematical formula/rounding to compute a resource amount's credit equivalent, so `step.Deduction` and `spentCredits` can never diverge due to formula differences.
- When `spentCredits > step.Deduction`, explicitly subtract the overage from `r.balance` (clamped at zero) instead of silently skipping the update on `Add` error, so the local balance always reflects true consumption and continues to gate further `Deduct` calls correctly.
- Add an invariant test asserting that for any sequence of `Deduct`/`Settle` calls, cumulative `spentCredits` can never exceed the sum of `step.Deduction` values without the local balance being correspondingly reduced.

### Proof of Concept
1. Reserve a fixed credit balance via `Reserve` (e.g., 100 credits) with a gas-token rate configured.
2. Call `Deduct("step1", ByResource(gasUnit, "", smallAmount))`, which earmarks `Deduction` using `convertToBalance`'s `Mul`/`Div` path.
3. Call `Settle("step1", metadata)` with `ResponseMetadata.Metering` values (and `CapDON_N`) chosen so that, after `Shift(18)`, `medianSpend`, `CapDON_N` multiplication, and `ConvertToBalance`'s gas-specific `.Round(0)`, the computed `spentCredits` exceeds `step.Deduction`.
4. Observe `r.balance.Add(step.Deduction.Sub(spentCredits))` returns `ErrInvalidAmount` (only logged, not surfaced), and `report.balance.balance` (verifiable via the exported `Get()`/internal test access as in `metering_test.go`) is unchanged rather than reduced by the overspend — demonstrating the local balance no longer reflects actual consumption, permitting an additional `Deduct` call that should have failed with `ErrInsufficientBalance`.

// convertToBalance converts a resource dimension amount to a credit amount.
// This method should only be used under a read lock.
func (bs *balanceStore) convertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[fromResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}

	// Special case for gas as gas token conversions are provided in amount per credit.
	// Other rates are provided as the inverse.
	if isGasSpendType(fromResourceType) {
		if rate.IsZero() {
			return decimal.Zero, nil
		}

		return amount.Div(rate).Round(defaultDecimalPrecision), nil
	}

	return amount.Mul(rate), nil
}

// ConvertToBalance converts a resource dimensions amount to a credit amount.
func (bs *balanceStore) ConvertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	bs.mu.RLock()
	defer bs.mu.RUnlock()

	return bs.convertToBalance(fromResourceType, amount)
}

// convertFromBalance converts a credit amount to a resource dimensions amount.
// This method should only be used under a read lock.
func (bs *balanceStore) convertFromBalance(toResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[toResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}

	// Special case for gas as gas token conversions are provided in amount per credit.
	// Other rates are provided as the inverse.
	if isGasSpendType(toResourceType) {
		return amount.Mul(rate).Round(0), nil
	}

	if rate.IsZero() {
		return decimal.Zero, nil
	}

	return amount.Div(rate), nil
}

// Add increases the current credit balance.
func (bs *balanceStore) Add(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	bs.balance = bs.balance.Add(amount)

	return nil
}
