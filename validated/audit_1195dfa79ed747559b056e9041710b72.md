### Title
`TransactionOutput::ensure_match_transaction_info` omits checkpoint-hash checks, letting `db-tool replay-verify` accept a divergent state/hot-state/position root - (File: `types/src/transaction/mod.rs`, used by `storage/db-tool/src/replay_on_archive.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  validates status, gas used, write-set hash and event-root hash of a locally re-executed transaction against the archived `TransactionInfo`, but it explicitly skips the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields, as documented in its own trailing comment. This function is the sole correctness oracle used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` to decide whether re-executed output matches the historical, ledger-accumulator-committed `TransactionInfo`.

### Finding Description
`ensure_match_transaction_info` checks four things and then stops: [2](#0-1) 

The trailing TODO makes the gap explicit: [3](#0-2) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as consensus-committed, accumulator-leaf-hashed fields [4](#0-3) . These roots are produced by `DoStateCheckpoint::run` from the authoritative Merkle/position state trees [5](#0-4)  and threaded into `TransactionInfo` by `DoLedgerUpdate::assemble_transaction_infos` [6](#0-5) . They are exactly the fields the report-analog's "Proof And Storage Pivots" calls out as required to survive executor-to-storage handoff and remain bound to the correct proof context.

`replay_on_archive.rs::execute_and_verify` calls `ensure_match_transaction_info` as its only pass/fail gate after re-executing archived transactions with the current VM: [7](#0-6) 

Because the comparator never re-derives or compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the values recomputed by local re-execution, a replay whose write set, gas, status, and events happen to match but whose resulting state root (or hot-state root, or native-position root) diverges from the archived, ledger-info-signed value will be reported as a **successful replay**.

### Impact Explanation
`replay-verify` is the tool operators and Aptos Labs itself use to confirm that a given VM/execution build reproduces historical, consensus-committed ledger state exactly — i.e., it is the detection mechanism for state-divergence bugs (execution bugs, hard forks, storage-schema reinterpretation bugs) before or after they land on mainnet. Silently ignoring the state-checkpoint and (once enabled) hot-state/position-state root comparisons means a real state-divergence — the exact class of bug this tool exists to catch, and the exact class of bug the "State-Integrity Gate" targets — can pass `db-tool replay-on-archive` undetected. This does not itself corrupt the live chain, but it removes the safety net that verifies write-set/state-root correctness across VM upgrades, letting an undetected state-divergent VM build reach production. Given that `TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are being rolled out (feature flags 122/123, permanent lifetime, per [8](#0-7) ), this gap will directly affect verification of these new consensus-committed roots once they activate.

### Likelihood Explanation
The gap is deterministic and always present — it is not conditioned on config or an attacker; any re-execution divergence in the state/hot-state/position roots (e.g., from a subtly incorrect VM change, a JMT/hot-state update bug, or a native-position tree bug) will pass silently through this exact code path every time `replay_on_archive` is run. The comment in the code itself flags it as a known, not-yet-fixed gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), which is local, first-party evidence of the root cause rather than speculation.

### Recommendation
Extend `ensure_match_transaction_info` to also recompute and compare `state_checkpoint_hash` (and, once the corresponding features are live, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) between the locally re-executed state and the archived `TransactionInfo`, failing verification on any mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet.

### Proof of Concept
1. Archive contains a `TransactionInfoV1` at version `V` with `state_checkpoint_hash = H_committed` (and eventually `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`), produced by the original, correct execution.
2. Run `db-tool replay-on-archive` with a VM build whose state-checkpoint computation is bugged such that it produces `H_local != H_committed`, while write set, gas, status, and events for the transaction happen to be identical (e.g., a bug only in Merkle root aggregation or hot-state promotion logic, not in the write-op values themselves).
3. `execute_and_verify` in [9](#0-8)  calls `ensure_match_transaction_info`, which checks status/gas/write-set-hash/event-root-hash only [2](#0-1)  — all of which still match — and returns `Ok(())`.
4. The tool reports the chunk as verified with zero errors, even though the recomputed state/hot-state/position root diverges from the ledger-committed root at version `V`, masking a real state-integrity bug from replay verification.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
