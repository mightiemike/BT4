### Title
Unbounded gzip decompression of attacker-controlled `compressed_program` in `decompress_program` allows RAM exhaustion - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
The JSON-RPC execution path that turns a `BroadcastedDeclareV1Transaction` into an `ExecutableTransactionInput` decompresses the attacker-supplied, base64-encoded, gzip-compressed `compressed_program` field with no size or time limit. A malicious declare-transaction submitter (via `simulateTransactions`, `estimateFee`, or any other RPC call that accepts a `BroadcastedTransaction`) can supply a small, highly-compressible gzip stream ("gzip bomb") that expands to an enormous amount of memory, exhausting the node's RAM. This is the same bug class as the pypdf `FlateDecode`/predictor advisory: attacker-controlled compressed input is decompressed without any bound on output size.

### Finding Description
`decompress_program` reads the entire decompressed output into memory via `decoder.read_to_end(&mut decompressed, ...)` with an explicit `// TODO(dan): add time and size limits.` comment acknowledging the missing guard: [1](#0-0) 

This function is reached from the conversion of a `BroadcastedDeclareTransaction::V1` (attacker-supplied, unauthenticated declare transaction data) into an `ExecutableTransactionInput`, via `user_deprecated_contract_class_to_sn_api`, called directly from the `TryFrom<BroadcastedDeclareTransaction>` implementation used by execution-facing RPC methods (e.g. simulate/estimate-fee): [2](#0-1) 

Notably, other decompression call-sites in the same codebase already apply explicit size limits — `decompress_with_size_limit` in `starknet_api::compression_utils` bounds output via `.take(max_size + 1)` and errors if exceeded, and `apollo_storage::compression_utils::decompress` bounds output via `zstd::bulk::decompress(data, MAX_DECOMPRESSED_SIZE)`: [3](#0-2) [4](#0-3) 

The RPC path's `decompress_program`, however, has no such bound — the attacker fully controls the compressed input string, and gzip permits extremely high compression ratios (a few KB of input can expand to GBs of output), so `read_to_end` will keep allocating until the process runs out of memory or is killed by the OS.

### Impact Explanation
This matches CWE-789 (uncontrolled memory allocation), the same class as the referenced pypdf advisory. Any unprivileged caller able to submit a `DECLARE` V1 transaction to a node's execution/simulation RPC endpoints (`simulateTransactions`, `estimateFee`, and any other call that constructs an `ExecutableTransactionInput` from a `BroadcastedTransaction`) can trigger unbounded memory allocation, crashing the node process (OOM) or severely degrading it. If this affects a sequencer-adjacent node used for transaction simulation/estimation prior to block building, repeated exploitation can deny service, impacting the ability of legitimate transactions to be validated/estimated and included, matching the "network unable to confirm new transactions" impact bar for this class of finding.

### Likelihood Explanation
Likelihood is high for any node exposing these RPC methods: no authentication or special privilege is required — only the ability to submit a broadcasted declare transaction body to the RPC method, which is by design open to any external client. Constructing a gzip bomb that decompresses to a huge size from a small payload is trivial and well documented.

### Recommendation
Apply the same defensive pattern already used elsewhere in the codebase (`decompress_with_size_limit` in `starknet_api::compression_utils`) to `decompress_program`: cap the decompressed output size (e.g., via `Read::take(max_size + 1)`) and reject/₋error out transactions whose decompressed program exceeds a sane maximum before continuing to `read_to_end`, removing the outstanding `// TODO(dan): add time and size limits.` gap.

### Proof of Concept
1. Craft a gzip stream that decompresses to a very large size from a tiny compressed input (a classic gzip/zip bomb, e.g. repeating a zero-filled buffer compressed at max ratio).
2. Base64-encode this compressed data and place it in `contract_class.compressed_program` of a `BroadcastedDeclareV1Transaction`.
3. Submit this transaction body to an RPC method that triggers execution/simulation (e.g., `starknet_estimateFee` / `starknet_simulateTransactions`), which converts it via `TryFrom<BroadcastedDeclareTransaction>` → `user_deprecated_contract_class_to_sn_api` → `decompress_program`.
4. `decoder.read_to_end(&mut decompressed, ...)` in `decompress_program` (crates/apollo_rpc/src/v0_8/api/mod.rs:678-680) allocates memory proportional to the decompressed size with no cap, exhausting the node's RAM.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
