## Analog Found: No Escape Hatch for Stuck `OUTBOUND_TX` Ballots — Permanently Frozen User Funds

### Title
Permanent freezing of burned PRC20 funds when an outbound ballot never reaches consensus — ([File: x/uexecutor/keeper/pending_outbound.go], [File: x/uexecutor/keeper/create_outbound.go], [File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
The external report's core theme — a system-critical recovery mechanism (`exitAdministrator`) that is not guaranteed to exist, leaving user funds permanently stuck when it's absent — has a direct analog in Push Chain's outbound flow. Push Chain has already built (and tested) an explicit admin escape hatch for stuck **inbound** ballots (`MsgRecomputeBallotQuorum` + `MsgRevertStuckInbound`), but the equivalent recovery path is deliberately absent for **outbound** ballots.

### Finding Description
When a user withdraws bridged value from Push Chain, `BuildOutboundsFromReceipt` ( [1](#0-0) ) decodes the `UniversalTxOutboundEvent` emitted by the `UniversalGatewayPC` contract — meaning the user's PRC20/native representation has already been burned/deducted on Push Chain by the time the `OutboundTx` (status `PENDING`) is created and indexed in `PendingOutbounds` ( [2](#0-1) ).

From this point, the *only* path back to the user is for Universal Validators to reach ballot consensus on the destination-chain observation via `MsgVoteOutbound` / `RecordOutboundVote`, which either finalizes the outbound as `OBSERVED` (success) or triggers `handleFailedOutbound` to re-mint the funds ( [3](#0-2) ).

However, `x/uexecutor`'s `BallotHooks` explicitly documents that `OUTBOUND_TX` ballots are **not** handled by any terminal-state cleanup/recovery logic — only `INBOUND_TX` ballots are: [4](#0-3) 

And the integration tests confirm the intended (but consequential) behavior: an expired `OUTBOUND_TX` ballot leaves the `PendingOutbounds` entry in place forever, with no in-protocol message to revert, re-vote, or refund it: [5](#0-4) [6](#0-5) 

Contrast this with the `INBOUND_TX` path, where Push Chain built exactly the escape hatch the external report recommends: `MsgRecomputeBallotQuorum` (drives a stuck `PENDING` ballot to `EXPIRED` when eligible voters have dropped to zero) followed by `MsgRevertStuckInbound` (admin-signed, mints a revert outbound to refund the user) — see `x/uvalidator/keeper/ballot.go` `RecomputeBallotQuorum` ( [7](#0-6) ) and `x/uexecutor/keeper/admin_revert.go` `RevertStuckInbound` ( [8](#0-7) ). No equivalent `RevertStuckOutbound`/quorum-recompute pairing exists for `OUTBOUND_TX` ballots anywhere in `x/uexecutor` or `x/uvalidator`.

The only recorded remediation path for a permanently-expired outbound ballot is a one-time chain-binary **upgrade handler** (`app/upgrades/purge-expired-outbounds/upgrade.go`), not a live, user- or admin-reachable message: [9](#0-8) 

This mirrors the Sonic report precisely: a privileged recovery mechanism exists conceptually (`exitAdministrator` / admin escape hatch), but it is **not guaranteed to be present at the moment it's needed** — here, by design, for the outbound leg of the bridge.

### Impact Explanation
If the Universal Validator set drops below the quorum needed to finalize a specific `OUTBOUND_TX` ballot (e.g., churn, downtime, or divergent observations across validators that never converge on a single variant reaching 2/3), the already-burned funds represented by that `OutboundTx` are permanently frozen — with no on-chain message capable of reverting or re-driving the ballot to resolution, unlike the symmetric `INBOUND_TX` case. This is a genuine, unrecoverable-without-a-chain-upgrade loss of user funds, matching "permanent freezing... of user or protocol-controlled funds" in the allowed impact gate.

### Likelihood Explanation
This does not require a malicious validator — ordinary liveness degradation (e.g., validator set shrinking due to normal unbonding/removal flows, as already modeled in the `RecomputeBallotQuorum` tests for inbound) is sufficient to strand an outbound ballot. Because `PendingOutbounds` entries are explicitly documented as intentionally never auto-removed on ballot expiry, this is a structural, deterministic gap rather than a rare edge case.

### Recommendation
Implement an outbound-side analog of the existing inbound escape hatch: extend `RecomputeBallotQuorum` (already generic over ballot ID) to be invokable against stuck `OUTBOUND_TX` ballots, and add a `MsgRevertStuckOutbound` (or extend `handleFailedOutbound`) that can be triggered once the corresponding ballot is driven to `EXPIRED`, re-minting the PRC20/native funds back to the original sender — mirroring `RevertStuckInbound`'s pattern exactly.

### Proof of Concept
1. User calls the gateway to withdraw funds; `BuildOutboundsFromReceipt` creates a `PENDING` `OutboundTx` and burns/deducts the corresponding PRC20 balance on Push Chain.
2. Validator set eligible to vote on this specific outbound's ballot shrinks to below quorum (e.g., via ordinary `RemoveUniversalValidator` unbonding flow, not requiring malice) before consensus is reached.
3. The `OUTBOUND_TX` ballot expires; per `BallotHooks` ( [4](#0-3) ) and the audit-trail test ( [10](#0-9) ), the `PendingOutbounds` entry is **not** removed and no refund/revert path exists.
4. No `MsgRevertStuckOutbound` or equivalent message exists in `x/uexecutor`'s `Msg` service to recover the funds; the only remediation is a coordinated chain-binary upgrade (`purge-expired-outbounds`), which is not a normal operational/user-facing recovery mechanism.

// RecomputeBallotQuorum rebuilds a pending ballot's eligible-voter list and
// voting threshold against the current eligible-voter set, preserving votes
// from voters still eligible and dropping votes from voters no longer eligible.
//
// If the recomputed eligible count is zero, the ballot is marked EXPIRED (no
// path to finalization). Otherwise it stays PENDING with the new parameters;
// downstream UVs must re-vote on the same ballot to trigger finalize+execute
// via the normal flow.
//
// Returns the old/new counts and threshold for the response.
func (k Keeper) RecomputeBallotQuorum(ctx context.Context, ballotID string) (
	oldEligibleCount, newEligibleCount, oldThreshold, newThreshold int64,
	newStatus types.BallotStatus,
	err error,
) {
	ballot, err := k.Ballots.Get(ctx, ballotID)
	if err != nil {
		return 0, 0, 0, 0, 0, fmt.Errorf("ballot %s not found: %w", ballotID, err)
	}

	if ballot.Status != types.BallotStatus_BALLOT_STATUS_PENDING {
		return 0, 0, 0, 0, 0, fmt.Errorf("ballot %s is not pending (status=%s); only pending ballots can be recomputed", ballotID, ballot.Status.String())
	}

	oldEligibleCount = int64(len(ballot.EligibleVoters))
	oldThreshold = ballot.VotingThreshold

	// Build the current eligible-voter set in the same valoper-bech32 format
	// the ballot already uses. The voting flow (VoteOnInboundBallot/VoteOnOutboundBallot)
	// passes CoreValidatorAddress strings directly into VoteOnBallot, so the
	// stored EligibleVoters list contains valoper bech32 addresses.
	eligibleUVs, err := k.GetEligibleVoters(ctx)
	if err != nil {
		return 0, 0, 0, 0, 0, fmt.Errorf("failed to fetch eligible voters: %w", err)
	}

	newVoters := make([]string, 0, len(eligibleUVs))
	for _, uv := range eligibleUVs {
		if uv.IdentifyInfo == nil || uv.IdentifyInfo.CoreValidatorAddress == "" {
			k.Logger().Warn("recompute: skipping UV with missing identity info")
			continue
		}
		newVoters = append(newVoters, uv.IdentifyInfo.CoreValidatorAddress)
	}
	newEligibleCount = int64(len(newVoters))

	// Zero eligible voters: no path to finalization. Mark EXPIRED.
	if newEligibleCount == 0 {
		if err := k.MarkBallotExpired(ctx, ballotID); err != nil {
			return 0, 0, 0, 0, 0, fmt.Errorf("failed to mark ballot expired on zero-eligible recompute: %w", err)
		}
		k.Logger().Info("ballot recompute: zero eligible voters → marked expired",
			"ballot_id", ballotID,
			"old_eligible", oldEligibleCount,
		)
		return oldEligibleCount, 0, oldThreshold, 0, types.BallotStatus_BALLOT_STATUS_EXPIRED, nil
	}
