### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay-verify tooling accept a divergent state root - ([File: types/src/transaction/mod.rs])

### Summary
The db-tool replay-verify path (`replay_on_archive`, `aptos-debugger` transaction replay, `aptos move replay-transaction`) validates a re-executed `TransactionOutput` against a backup/authenticated `TransactionInfo` solely through `TransactionOutput::ensure_match_transaction_info`. That comparator checks execution status, gas used, write-set hash (`state_change_hash`), and event root hash, but — by its own inline TODO — it intentionally omits comparing `state_checkpoint_hash` (and `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`). This means the one Merkle root that authenticates the actual world-state (used by light clients, state-proof consumers, and fast-sync) is never independently re-derived and checked during this "replay verified against ledger data" tooling path.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs` (around lines 2139-2203) explicitly documents the gap: [1](#0-0) 

It hashes and compares `write_set` against `state_change_hash`, and events against `event_root_hash`, but the function body's trailing comment states:

"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole cross-check invoked in three consumer call sites:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))` [2](#0-1) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`'s `print_mismatches` [3](#0-2) 
- `aptos-move/cli/src/commands.rs` replay-transaction command [4](#0-3) 

None of these call sites independently reconstitute and compare the state Merkle root (`state_checkpoint_hash`) against the value computed by the actual execution/state-checkpoint pipeline (`DoStateCheckpoint::run` in `execution/executor/src/workflow/do_state_checkpoint.rs`, which is what produces `state_checkpoint_hashes` from a `LedgerStateSummary`). The replay-verify tool path bypasses the DB-writing chunk-executor commit pipeline (`ChunkExecutorInner`/`update_ledger`/`commit`), which does maintain and verify accumulator/state roots for genuine full-node sync, and instead performs an ad-hoc re-execution + comparison via `ensure_match_transaction_info` alone. Because that comparator never touches `state_checkpoint_hash`, a state-tree divergence (e.g. from an unnoticed nondeterminism bug, a state-value serialization/interpretation bug elsewhere in write-set handling, or corrupted archived state data) will not be flagged by `replay_on_archive`, `aptos-debugger`, or the CLI replay command, even though write-set and event hashes matched.

### Impact Explanation
This breaks the state-commitment/proof-integrity invariant that authenticated (Merkle-proof-bound) state roots must be independently verifiable against locally re-executed results. Tools whose entire purpose is "verify archived data replays to the same state" (`db-tool replay-verify`, `replay_on_archive`) can silently report success while the actual account/resource-level state tree diverges from the one committed and signed into the `LedgerInfo`. Operators and auditors relying on these tools to detect nondeterminism, storage corruption, or hard-fork-only divergence lose their only automated signal for state-root drift, allowing a wrong committed state to go undetected during audits/replays even though it is bound to a "verified" ledger version. This is a real gap in the class of "authenticated response bound to wrong root" that the state-integrity gate targets, though its severity is bounded because it affects auditing/verification tooling rather than the live consensus/commit path (the actual `AptosDB`/`ChunkExecutor` commit and accumulator-verification code paths shown earlier — e.g. `chunk_result_verifier.rs`, `LedgerUpdateOutput::ensure_transaction_infos_match`, `TransactionOutputListWithProof::verify` — do perform full write-set-hash and accumulator verification, and per `execution/executor/src/workflow/do_state_checkpoint.rs`, the state-checkpoint root is genuinely recomputed during normal execution).

### Likelihood Explanation
This is not a remotely triggerable "arbitrary transaction" vulnerability in the classic sense; it's a deterministic gap in verification tooling code that is reached on every use of the affected replay tools whenever a checkpoint transaction is replayed, and the comment inside the code confirms the maintainers are aware of it as an open TODO gating a not-yet-enabled feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`). It requires no adversarial input to trigger the missing check — it simply never runs, in every execution of these tools today.

### Recommendation
Extend `ensure_match_transaction_info` (or add a parallel check in each call site) to independently recompute the state Merkle root for the replayed output (using the same checkpoint logic as `DoStateCheckpoint::run`) and compare it against `txn_info.state_checkpoint_hash()` (and, when applicable, `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`) before reporting success in `replay_on_archive`, `aptos-debugger`, and the CLI `replay-transaction` command.

### Proof of Concept
Not applicable as a live-network exploit — this is a code-inspection finding based on the maintainers' own inline comment and the absence of any state-checkpoint-hash check in `ensure_match_transaction_info` at `types/src/transaction/mod.rs:2139-2203`, confirmed by tracing all three call sites (`replay_on_archive.rs:392`, `aptos_debugger.rs:243`, `commands.rs:2653`) and finding no supplementary state-root comparison in any of them. I was not able to fully verify whether any currently-enabled downstream check elsewhere (outside these three call sites) independently re-validates `state_checkpoint_hash` for these specific tool paths; the codebase's own TODO comment indicates the authors consider this check currently absent and necessary before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.
