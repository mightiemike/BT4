### Title
Unpaginated `getAssetIssueList()` forces a full asset-issue store iteration and sort with no size cap, making it a strictly worse DoS variant of the paginated endpoint - ([File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java])

### Summary
Both the paginated (`getAssetIssuesPaginated(offset, limit)`) and unpaginated (`getAllAssetIssues()`) code paths perform a full iteration of the entire asset-issue store and, in the paginated case, a full sort of that list before slicing to the requested `limit`. Since `getAssetIssueList()` (backing `GetAssetIssueListServlet` / gRPC `GetAssetIssueList`) calls `getAllAssetIssues()` directly with zero pagination, it incurs the same full-store iteration cost as the paginated call while additionally returning the entire unbounded result set, making it strictly worse from both a CPU and a bandwidth/memory standpoint.

### Finding Description
`AssetIssueStore.getAllAssetIssues()` streams the entire underlying store into a `List<AssetIssueCapsule>` with no bound: [1](#0-0) .

`getAssetIssuesPaginated(offset, limit)` calls this same unbounded `getAllAssetIssues()` first, then sorts the *entire* returned list, and only afterward slices to the caller-supplied `limit` (capped at `ASSET_ISSUE_COUNT_LIMIT_MAX`): [2](#0-1)  and [3](#0-2) .

This confirms the premise: the `limit`/`offset` parameters only affect the final `subList` truncation — they do nothing to reduce the underlying store scan (`iterator()` over the full DB) or the `O(n log n)` sort cost. Therefore `getAssetIssuesPaginated(0, 1)` and the fully unpaginated `getAllAssetIssues()` (used by `getAssetIssueList()`) both pay for a complete DB iteration and, additionally, a full in-memory sort when going through the paginated variant. The unpaginated variant is reachable anonymously via `GetAssetIssueListServlet` (HTTP, unauthenticated, rate-limited only by `RateLimiterServlet`'s default limiter) and gRPC `GetAssetIssueList`, per the servlet: [4](#0-3) .

No actuator validation, signature checks, or fee/energy accounting apply to read-only RPC/HTTP query endpoints like this — the only gate is the generic rate limiter servlet, which does not scale limits with response size or store cardinality.

### Impact Explanation
This is a resource-exhaustion / disproportionate-cost issue rather than a distinct new bug: it is the same underlying "full-store iteration on every call regardless of requested limit" defect already present in the paginated store method, just without even the marginal mitigation of a bounded response payload. Repeated anonymous calls scale CPU cost linearly with total on-chain asset-issue count and, unlike the paginated endpoint, also scale network/serialization cost with the same factor, since the full list (uncapped) is serialized and returned. This maps to a TRON bounty "DoS via RPC-API" impact class — degraded node responsiveness for legitimate API/RPC clients under sustained anonymous load, not consensus divergence or fund loss.

### Likelihood Explanation
Any anonymous HTTP/gRPC client can invoke this endpoint with no authentication, no fee, and no energy/bandwidth cost (read-only query API). The only friction is the generic `RateLimiterServlet` limiter, which is a per-endpoint request-rate control, not a cost-aware limiter, so it does not prevent an attacker from issuing sustained calls at whatever rate the limiter allows, each of which is disproportionately expensive as the store grows. This is highly feasible and repeatable as long as the node exposes the HTTP/gRPC full-node API with default configuration.

### Recommendation
Apply the same fix used for the paginated variant to both call paths: push `offset`/`limit` down into the store iteration (e.g., iterate with an early-exit/bounded cursor, or maintain a sorted secondary index) rather than materializing and sorting the entire store on every call. Additionally, either deprecate the unpaginated `getAssetIssueList()` / `GetAssetIssueListServlet` in favor of the paginated endpoint, or internally cap it to `ASSET_ISSUE_COUNT_LIMIT_MAX` so it cannot return/scan an unbounded result set.

### Proof of Concept
```java
// JUnit-style illustration (conceptual, using AssetIssueStore directly)
@Test
public void testUnpaginatedVsPaginatedCostParity() {
  seedStoreWithLargeAssetIssueSet(assetIssueStore, 200_000);

  long t0 = System.nanoTime();
  List<AssetIssueCapsule> full = assetIssueStore.getAllAssetIssues(); // getAssetIssueList() path
  long fullCost = System.nanoTime() - t0;

  long t1 = System.nanoTime();
  List<AssetIssueCapsule> paged = assetIssueStore.getAssetIssuesPaginated(0, 1); // getAssetIssueList(0,1)
  long pagedCost = System.nanoTime() - t1;

  // paged should sort + scan the same 200,000 entries, only trimming at the end
  assertTrue(Math.abs(fullCost - pagedCost) < fullCost * 0.3); // near-identical cost
  assertEquals(200_000, full.size());
  assertEquals(1, paged.size()); // radically smaller response despite same cost
}
```
At the RPC layer, sending repeated unauthenticated `GET /wallet/getassetissuelist` requests (or gRPC `GetAssetIssueList`) against a node with a large asset-issue table demonstrates equivalent CPU time per call to `GetPaginatedAssetIssueListServlet?offset=0&limit=1`, confirming the disproportionate-cost characteristic extends unmitigated (and worse, due to unbounded response size) to the unpaginated endpoint.

```java
  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
```
