### Title
Faulty-relayer ban promise batches `delete_key` and `ban_relayer` in one receipt, so a `DeleteKeyDoesNotExist` failure permanently freezes the Wallet Contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`create_ban_relayer_promise` builds a single-receipt batch of `delete_key` followed by `function_call_weight("ban_relayer", ...)` on the same `Promise::new(current_account_id)` object (not a `.then()` chain). Because NEAR actions in one receipt execute in order and abort the whole receipt on the first failure, if the `delete_key` action fails, `ban_relayer` never executes, and `has_in_flight_tx` is never reset to `false`. This permanently locks the Wallet Contract account, identical in class to the Lybra bug where a mis-wired call path makes a critical state-resetting operation permanently unreachable.

### Finding Description
`inner_rlp_execute` and `address_check_callback` both call `create_ban_relayer_promise` on relayer errors: [1](#0-0) 

This constructs `Promise::new(current_account_id).delete_key(pk).function_call_weight("ban_relayer", ...)` — both actions are batched into the *same* promise/receipt, rather than `delete_key` being followed by a `.then()`-chained separate receipt. `rlp_execute` and `address_check_callback` set `self.has_in_flight_tx = true` immediately before returning this promise: [2](#0-1) [3](#0-2) 

Only `ban_relayer` (and the other callbacks) reset `has_in_flight_tx = false`: [4](#0-3) 

The comment on `has_in_flight_tx` states the invariant that it must be `true` exactly when a promise is outstanding and `false` otherwise: [5](#0-4) 

The protocol confirms that actions inside a receipt execute strictly in order and any failure aborts the remaining actions in that same receipt, rolling back all its state changes: [6](#0-5) [7](#0-6) [8](#0-7) 

If `delete_key(pk)` fails with `DeleteKeyDoesNotExist` — reachable, for instance, if the signer's key was already removed by a concurrent/duplicate ban attempt, or by any other path that deletes the key before this receipt executes (e.g., the user separately deletes the relayer's access key, or another in-flight promise chain races to remove it first) — the whole receipt fails and rolls back, so `ban_relayer` never runs and `has_in_flight_tx` remains permanently `true`. Every subsequent `rlp_execute` call then hits the "transaction already in progress" guard forever: [9](#0-8) 

### Impact Explanation
This permanently freezes the ETH-implicit account's Wallet Contract: no further `rlp_execute` call (transfers, function calls, key management) can ever succeed once `has_in_flight_tx` is stuck `true`, because it is a state field with no other mutator. This is a transaction-triggered halt of the account and constitutes permanently frozen funds/functionality for that account (matching the "impossibility to change / permanent DoS via a mis-batched interface/call" bug class from the Lybra report).

### Likelihood Explanation
The trigger only requires that `delete_key` on the signer's public key fail when the ban path is invoked — plausible in races where the same key is targeted for deletion by more than one concurrently in-flight receipt (e.g., overlapping faulty-relayer detections from different call paths, `rlp_execute`'s direct ban vs. `address_check_callback`'s ban), or if a user/relayer independently deletes the access key between transaction submission and execution. Given asynchronous, non-atomic cross-shard/receipt execution on NEAR, such races are realistically reachable by an unprivileged relayer or user controlling transaction timing, without requiring any privileged/validator role.

### Recommendation
Split `delete_key` and the `ban_relayer` call into separate receipts using `.then()` so that the `ban_relayer` callback (which resets `has_in_flight_tx`) always executes regardless of whether `delete_key` succeeds, or make `ban_relayer` tolerant by not depending on the batched `delete_key`'s success (e.g., issue `delete_key` as its own promise and unconditionally chain `ban_relayer` afterward via `.then()`, ignoring the `delete_key` receipt's outcome).

### Proof of Concept
1. Register a relayer access key via `register_relayer`-style flow so `has_in_flight_tx` can later be triggered into the ban path.
2. Race two receipts that each try to delete the same relayer public key concurrently through the wallet's ban paths (e.g., trigger `rlp_execute`'s direct relayer-error ban and, in a separate submitted transaction/receipt, an independent `delete_key` action or another faulty-relayer detection referencing the same key) so that one receipt's `delete_key(pk)` executes after the key has already been removed by the other.
3. Observe the second ban receipt fails with `DeleteKeyDoesNotExist`, the whole receipt (including the batched `function_call_weight("ban_relayer", ...)`) is rolled back, and `has_in_flight_tx` remains `true`.
4. Any subsequent `rlp_execute` call on that account now permanently returns `"Error: transaction already in progress, please try again later."`, confirming the account is bricked.
