## Finding

### Title
`EVMHooks.PostTxProcessing` reverts unrelated EVM transactions on rescue/outbound bookkeeping errors - (File: `x/uexecutor/keeper/evm_hooks.go`)

### Summary
Push Chain's `EVMHooks.PostTxProcessing` is the direct analog of Canto's vulnerable `PostTxProcessing` hook: it runs after **every** EVM transaction on Push Chain and, if any of its internal bookkeeping calls (`CreateUniversalTxFromReceiptIfOutbound`, `AttachRescueOutboundFromReceipt`) return an error, that error propagates up and causes the entire EVM transaction to be reverted — even for logs/state changes that have nothing to do with the caller's actual intent.

### Finding Description
`PostTxProcessing` is documented as being "invoked after every EVM transaction execution" [1](#0-0) . It unconditionally propagates any error from its two sub-calls:

```go
if err := h.k.CreateUniversalTxFromReceiptIfOutbound(ctx, protoReceipt, pcTx); err != nil {
    return err
}
return h.k.AttachRescueOutboundFromReceipt(ctx, protoReceipt, pcTx)
``` [2](#0-1) 

Both functions scan the tx's *entire* log set (including logs from nested/internal contract calls) for `UniversalGatewayPC` events, and both can return hard errors driven purely by Cosmos-side bookkeeping state that a Solidity contract cannot validate on its own:

- `BuildOutboundsFromReceipt` returns `"outbound is disabled for chain %s"` if the destination chain in a `UniversalTxOutbound` log is disabled, or propagates `GetTokenConfigByPRC20` lookup errors. [3](#0-2) 
- `AttachRescueOutboundFromReceipt` returns hard errors for a `RescueFundsOnSourceChain` log whenever the referenced `universalTxId` doesn't exist, has no failed CEA deposit, has no reverted auto-revert outbound, or already has an active rescue outbound: [4](#0-3) [5](#0-4) 

Critically, these eligibility conditions (`IsCEA` deposit status, reverted-auto-revert status, active-rescue-in-progress) live entirely in Push Chain's Cosmos SDK state and cannot be pre-validated by the `UniversalGatewayPC` Solidity contract emitting the event. Any EVM call chain that causes the Gateway to emit a `RescueFundsOnSourceChain` or `UniversalTxOutbound` log referencing an ineligible/nonexistent/already-processed ID will make the *whole* enclosing transaction fail at the hook level — reverting every other successful EVM state change bundled in that same transaction, per the confirmed test `outbound disabled returns error`. [6](#0-5) 

This is confirmed to also apply to the user-facing `MsgExecutePayload` path (not just raw EVM txs): `ExecutePayload` calls the same two functions and returns their error directly, reverting the entire payload execution (including the UEA's already-succeeded internal EVM logic). [7](#0-6) 

### Impact Explanation
Because the hook inspects logs across the *entire* transaction receipt (not just top-level calls), any transaction whose call graph happens to touch the Gateway contract in a way that emits one of these events with data that fails Push Chain's Cosmos-side eligibility checks will have its entire EVM execution reverted — including unrelated state changes performed earlier in the same transaction/payload. This matches the Canto M-02 pattern precisely: a module-internal bookkeeping failure (not an EVM correctness failure) causes the whole transaction to be non-atomic-safely discarded. Reachable impact is denial-of-service against a transaction/payload that would otherwise have succeeded, without any privileged actor involved, on the standard `MsgExecutePayload` and general EVM tx paths.

### Likelihood Explanation
Medium. The Gateway's rescue/outbound event decoding relies purely on log data supplied by whoever calls the Gateway contract (topics/data are attacker or third-party-influenced call arguments); the Cosmos SDK eligibility checks (UTX existence, deposit-failed status, no-active-rescue) are checks the EVM-side contract structurally cannot enforce. Any caller supplying an ineligible `universalTxId`/chain — whether through direct interaction, a buggy integration, or a malicious intermediary contract embedded in a larger call — triggers the hard-error path and reverts the full transaction.

### Recommendation
In `PostTxProcessing` (and the equivalent call sites in `ExecutePayload`), do not propagate internal-bookkeeping errors as fatal transaction reverts. Log the error and return `nil` (or otherwise decouple event log processing from EVM execution success), so that eligibility/config failures for rescue or outbound processing cannot unwind unrelated, already-valid EVM state changes in the same transaction.

### Proof of Concept
The existing integration test already demonstrates the mechanism: a synthetic `UniversalTxOutbound` event referencing a chain with `IsOutboundEnabled: false` causes `hooks.PostTxProcessing` to return an error containing `"outbound is disabled"` [8](#0-7) , which in production would cause the entire EVM transaction's `VmError`/revert result to be set, discarding any other actions performed in that same transaction. The analogous case for `AttachRescueOutboundFromReceipt` (e.g. calling rescue on an already-rescued or ineligible `universalTxId`) returns the same class of hard error [5](#0-4) , with identical revert-propagation behavior through `PostTxProcessing`.
