### Title
`Bank::withdraw` decrements account lamports without updating `capitalization`, causing bank-hash/capitalization divergence - ([File: runtime/src/bank.rs])

### Summary
`Bank::withdraw` mirrors the reported `perp_withdraw` bug class: it mutates an account balance (`account.checked_sub_lamports(lamports)`) and persists it via `self.store_account(pubkey, &account)`, but never touches `self.capitalization`, the bank-wide cached aggregate that must track the sum of all lamports. Every other lamport-debiting path in the same file (`store_account_and_update_capitalization`, `distribute_transaction_fee_details`, fee burn logic, `update_captalization` in core-bpf migration) explicitly adjusts `self.capitalization` in lockstep with the balance change. `withdraw` is the one path that silently skips this, leaving the cached `capitalization` value stale relative to the true summed account balances.

### Finding Description
`Bank::withdraw` at [1](#0-0)  loads the account, subtracts `lamports` from it, and calls `self.store_account(pubkey, &account)` — but it never calls `self.capitalization.fetch_sub(...)` (or otherwise reconciles `self.capitalization`).

Contrast this with the sibling function `store_account_and_update_capitalization`, which treats capitalization as a cached derived value that must be kept in sync with every lamport change: [2](#0-1) . That function explicitly computes the lamport delta and calls `self.capitalization.fetch_add`/`fetch_sub` before storing the account, precisely the "update the cached derived value" step that is missing from `withdraw`.

The codebase itself documents that this stale-capitalization condition is a known, reproducible consequence of calling `withdraw` without a matching capitalization update — the test suite directly asserts the mismatch: [3](#0-2)  shows `bank.withdraw(&mint_keypair.pubkey(), 10)` followed immediately by `assert_ne!(bank.capitalization(), bank.calculate_capitalization_for_tests())` — i.e., after `withdraw`, the cached `capitalization` value provably diverges from the true, freshly recomputed capitalization, and only a subsequent `deposit`/account-store call that itself updates capitalization repairs it.

This is the exact "stale cached derived value after a balance-changing operation" bug class from the external report: `perp_withdraw` decreased `info.funds` (which feeds `total_funds`/edge price) without invoking `change_edge_px` to refresh the cached liquidation price. `Bank::withdraw` decreases an account's lamports (which feeds total supply) without invoking any capitalization-refresh step, leaving `self.capitalization` — a cached, atomically-tracked aggregate consulted throughout consensus and tooling — stale.

### Impact Explanation
`capitalization` is not a cosmetic counter: it is compared against `calculate_capitalization_for_tests`/full recomputation in numerous invariant checks throughout `bank/tests.rs`, and it is the value ledger-tool's `capitalization` subcommand reports and cross-checks (`ledger-tool/src/main.rs` capitalization subcommand at [4](#0-3) , and the `set_capitalization_for_tests`/`calculate_capitalization_for_tests` reconciliation logic at [5](#0-4) ). A stale/incorrect `capitalization` value is a form of the accepted bug class "hash/capitalization divergence": any consumer relying on `bank.capitalization()` as ground truth for total supply (auditing tools, snapshot verification against declared capitalization, warp-epoch capitalization skew detection) will observe an incorrect value that no longer matches the actual sum of on-chain lamports, without any error being raised at the time `withdraw` is called.

### Likelihood Explanation
`withdraw` is an internal `Bank` API (not a signed on-chain instruction reachable directly by an unprivileged transaction), so the trigger requires an internal caller that debits lamports via `withdraw` and never issues a matching capitalization-aware operation before the value is consumed (e.g., before ledger-tool's `capitalization` check or before an assertion that trusts `bank.capitalization()`). The repository's own test suite demonstrates the exact divergence is trivially reproducible with a single `withdraw` call and persists until a later `store_account_and_update_capitalization`-style call happens to correct it — indicating the omission is real and easily triggered by any code path that reuses `withdraw` for a lamport debit outside the fee-collection accounting that normally offsets it elsewhere.

### Recommendation
Make `Bank::withdraw` update `self.capitalization` symmetrically with the lamport debit, mirroring `store_account_and_update_capitalization`'s pattern (`self.capitalization.fetch_sub(lamports, Relaxed)` alongside the `checked_sub_lamports` call), or clearly document/assert that `withdraw` must only be called from contexts where the capitalization delta is separately and atomically accounted for, and add a debug-time invariant check that flags any caller path leaving `capitalization` stale.

### Proof of Concept
The existing regression test already demonstrates the divergence end-to-end: [3](#0-2)  — `bank.withdraw(&mint_keypair.pubkey(), 10)` is called, the write cache is flushed/rooted, and `assert_ne!(bank.capitalization(), bank.calculate_capitalization_for_tests())` passes, proving the cached `capitalization` field no longer equals the true recomputed total after the withdrawal, exactly analogous to the reported stale-edge-price-after-withdraw pattern.

    pub fn withdraw(&self, pubkey: &Pubkey, lamports: u64) -> Result<()> {
        match self.get_account_with_fixed_root(pubkey) {
            Some(mut account) => {
                let min_balance = match get_system_account_kind(&account) {
                    Some(SystemAccountKind::Nonce) => self
                        .rent_collector
                        .rent
                        .minimum_balance(nonce::state::State::size()),
                    _ => 0,
                };

                lamports
                    .checked_add(min_balance)
                    .filter(|required_balance| *required_balance <= account.lamports())
                    .ok_or(TransactionError::InsufficientFundsForFee)?;
                account
                    .checked_sub_lamports(lamports)
                    .map_err(|_| TransactionError::InsufficientFundsForFee)?;
                self.store_account(pubkey, &account);

                Ok(())
            }
            None => Err(TransactionError::AccountNotFound),
        }
    }
