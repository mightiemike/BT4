### Title
Missing upper-bound validation on `ENERGY_FEE` / `EXCHANGE_CREATE_FEE` chain parameters enables fee-based Denial-of-Service - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator()` is the central gate that checks proposed chain-parameter values before they are committed by `ProposalApproveActuator`/`ProposalCreateActuator`. Most fee-related parameters (`ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, `TRANSACTION_FEE`, `ASSET_ISSUE_FEE`, etc.) are bounded to `[0, LONG_VALUE]` [1](#0-0) . However, `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` fall through with no bound at all: `case ENERGY_FEE: case EXCHANGE_CREATE_FEE: break;` [2](#0-1) . This is the same bug class as the reported `BathToken.setFeeBPS()` issue: a privileged fee-setting entry point with no cap, which can be pushed to an absurd value and cause a functional Denial-of-Service for all subsequent users of that feature.

### Finding Description
- `ENERGY_FEE` sets the SUN-per-energy-unit price used throughout smart contract (TVM) execution to compute the TRX cost of energy consumption for every transaction on the network.
- `EXCHANGE_CREATE_FEE` sets the flat TRX fee required to create a TRC10 Exchange pair, consumed in `ExchangeCreateActuator.calcFee()` [3](#0-2) .
- Both parameters are set exclusively via `ProposalUtil.validator()`, which enforces bounds for nearly every other fee-type parameter (see the `[0, LONG_VALUE]` block just above), but explicitly skips validation for these two cases, meaning any non-negative or even negative `long` value can be proposed and, if approved, becomes the live network fee.
- Unlike the well-guarded analog `UpdateBrokerageContract`, which explicitly checks `brokerage < 0 || brokerage > ActuatorConstant.ONE_HUNDRED` in `UpdateBrokerageActuator.validate()` [4](#0-3) , and the market fees (`MARKET_SELL_FEE`/`MARKET_CANCEL_FEE`) which are documented with an explicit valid range comment (`// 0 [0,10_000_000_000]`) even though the enforcement code for those particular cases could not be located in `ProposalUtil.java`, `ENERGY_FEE`/`EXCHANGE_CREATE_FEE` have no such protection whatsoever.
- If `ENERGY_FEE` were set to an extreme value, every TVM transaction on the network (all `TriggerSmartContract` calls) would require an economically infeasible amount of TRX for energy, functionally halting smart contract execution chain-wide — a network-level halt/DOS impact.
- If `EXCHANGE_CREATE_FEE` were set to an extreme value, `ExchangeCreateActuator.validate()`'s balance check (`ownerAccount.getBalance() < addExact(...)` style logic) would reject essentially all exchange-creation transactions, permanently blocking that feature.

### Impact Explanation
This maps to the "invalid-state/divergence/halt" and "underpriced/overpriced public-work" impact categories: an unbounded, committee-settable fee parameter can render a core public-facing feature (TVM contract execution, or TRC10 exchange creation) permanently unusable for the entire network, mirroring the original finding's DOS impact on `BathToken.withdraw()`.

### Likelihood Explanation
Changing `ENERGY_FEE` or `EXCHANGE_CREATE_FEE` requires a chain-parameter proposal to be approved by a super-majority of Super Representatives (the java-tron governance/committee mechanism), which is a higher bar than a single contract owner as in the original Solidity report. This is analogous to, but more restrictive than, the original "owner" role — the underlying root cause (no cap enforced in code) is identical and would allow a misconfiguration or malicious governance majority to trigger the DOS without any additional code-level safeguard, since the validator provides zero defense-in-depth here even though it does so for nearly every other fee field.

### Recommendation
Add an explicit upper-bound (and non-negative) check for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` in `ProposalUtil.validator()`, consistent with the `[0, LONG_VALUE]` pattern already used for sibling fee parameters (`ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, etc.), so that a proposal cannot push the network's energy price or exchange-creation cost to values that make the corresponding feature unusable.

### Proof of Concept
1. A proposal is created with `code = ENERGY_FEE` (or `EXCHANGE_CREATE_FEE`) and an extreme `value` (e.g., `Long.MAX_VALUE` or a value far beyond any realistic economic bound).
2. `ProposalUtil.validator()` reaches `case ENERGY_FEE: case EXCHANGE_CREATE_FEE: break;` and returns without throwing `ContractValidateException`, unlike the sibling fee cases which are bounded to `[0, LONG_VALUE]` [1](#0-0) .
3. Once approved by the required witness quorum, `DynamicPropertiesStore` persists this fee, and it is read by `ExchangeCreateActuator.calcFee()` [3](#0-2)  or by the energy-fee consumption logic used across TVM execution.
4. All subsequent user transactions relying on that fee (exchange creation, or any smart-contract call requiring energy) fail balance checks, effectively DOS-ing that feature network-wide.
