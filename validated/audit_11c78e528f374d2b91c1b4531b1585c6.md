### Title
Integer division rounding down in `MarketSellAssetActuator.matchSingleOrder` lets a taker order fully drain a maker's remaining TRC10 balance while paying zero tokens - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
The TRON on-chain order book (`MarketSellAssetActuator`) computes the amount a maker receives from a trade using integer division via `MarketUtils.multiplyAndDivide`. In the "taker == maker" branch of `matchSingleOrder`, this computed amount (`makerBuyTokenQuantityReceive`) is never checked for a zero result before the trade is settled, unlike the sibling "taker > maker" branch which explicitly guards against it. This omission lets a taker fully consume a maker's remaining sell-token balance while the maker receives zero payment, mirroring the JIT-minting rounding bug in the referenced report.

### Finding Description
`matchSingleOrder` computes the amount the taker can buy at the maker's price using floor division: [1](#0-0) 

When `takerBuyTokenQuantityRemain` exactly equals the maker's remaining sell quantity ("taker == maker" branch), the code computes the maker's payout with the same floor-division helper but does **not** check whether the result rounds to zero before finalizing the trade: [2](#0-1) 

Compare this to the "taker > maker" branch, which explicitly guards the same computation against a zero result and safely returns the maker's remaining tokens instead of completing the trade: [3](#0-2) 

The underlying division helper is a plain floor division that silently rounds toward zero for small numerators: [4](#0-3) 

Because `makerSellRemainQuantity` naturally shrinks to a small "dust" value after repeated partial fills (this is exactly what happens in a live order book once a maker order is mostly consumed), and `takerBuyTokenQuantityRemain` is itself derived from the same floor-division helper, it is straightforward for `takerBuyTokenQuantityRemain` to equal a tiny `makerSellRemainQuantity` value while `makerBuyQuantity < makerSellQuantity` (i.e., the maker is selling more of its asset per unit of the buy asset). In that case:
```
makerBuyTokenQuantityReceive = floor(makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity) = 0
```
Execution proceeds regardless: the maker's order is fully closed and set to `INACTIVE`, `makerOrderCapsule.getSellTokenQuantityRemain()` is transferred in full to the taker via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, ...)`, and only `0` tokens are credited back to the maker via `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)`. [5](#0-4) 

The code's own comment for the analogous guarded branch acknowledges the rounding-to-zero condition is mathematically possible and must be defended against ("the quantity is too small, return the remain of sellToken to maker"), but this defense was never applied to the "taker == maker" branch: [6](#0-5) 

### Impact Explanation
An attacker who is a taker in `MarketSellAssetActuator.execute` → `matchOrder` → `matchSingleOrder` can craft (or wait for/repeatedly submit) sell orders such that the residual quantity of a matched maker order rounds its payout to zero. When this happens, the maker's fully-locked TRC10/TRX balance is transferred to the taker for free, corrupting on-chain asset accounting and directly stealing from the maker without their consent. This is reachable purely through broadcasting standard `MarketSellAssetContract` transactions from unprivileged accounts, requiring no special permissions.

### Likelihood Explanation
The vulnerable condition requires (a) an existing maker order whose remaining sell quantity has been reduced to a small "dust" amount through prior partial fills (a routine, frequent state in any active order book), and (b) a maker price ratio where `makerBuyQuantity < makerSellQuantity`. Both conditions are common and can be engineered by an attacker who also places the initial maker order themselves, then submits a second account's taker order (or self-trades across two of their own accounts) to trigger the exact-match branch. No privileged access or timing race is needed, making this readily exploitable.

### Recommendation
Add the same zero-result guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, return the maker's remaining sell tokens instead of finalizing the trade (or reject/skip the match), so that no trade can be settled where one side of `matchSingleOrder` receives assets while the other side's computed payout is zero.

### Proof of Concept
1. Attacker (or colluding accounts) creates a maker sell order via `MarketSellAssetActuator` with `sellTokenQuantity = S`, `buyTokenQuantity = B` such that `B < S` (e.g., `S = 1000`, `B = 1`).
2. Through one or more prior taker fills, the maker order's `sellTokenQuantityRemain` is reduced to a small dust value `r` (e.g., `r = 1`) such that `r * B / S` floors to `0` (`1 * 1 / 1000 = 0`).
3. Attacker submits a final taker sell order whose computed `takerBuyTokenQuantityRemain` (via `MarketUtils.multiplyAndDivide`) exactly equals `r`, hitting the `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` branch in `matchSingleOrder` at `MarketSellAssetActuator.java:418`.
4. `makerBuyTokenQuantityReceive` computes to `0` at line 427-428; no zero-check exists in this branch.
5. `takerBuyTokenQuantityReceive` is set to the maker's full remaining sell quantity `r` (line 429) and credited to the taker at line 489, while the maker is credited `0` at line 490 and its order is marked `INACTIVE` (line 439), permanently losing the `r` tokens with no compensation.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
