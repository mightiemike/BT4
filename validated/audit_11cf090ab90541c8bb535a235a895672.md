### Title
Unguarded `.unwrap()` on `RecoveryId::from_i32` in `Secp256K1Signature::recover` panics on recovery byte > 3 — (`core/crypto/src/signature.rs`)

### Summary
`Secp256K1Signature::recover` calls `RecoveryId::from_i32(i32::from(self.0[64])).unwrap()` with no prior validation of byte 64. Any value > 3 causes an unconditional Rust panic. The `TryFrom<&[u8]>` constructor for `Secp256K1Signature` accepts all 65-byte inputs without checking byte 64. If `VMLogic::ecrecover` does not independently validate byte 64 before calling `recover()`, an unprivileged contract caller can trigger this panic.

### Finding Description
In `Secp256K1Signature::recover`: [1](#0-0) 

`RecoveryId::from_i32` returns `None` for any argument outside `{0, 1, 2, 3}`. The `.unwrap()` converts that `None` into a panic. There is no guard anywhere in the `recover()` function body, and the `TryFrom<&[u8]>` impl: [2](#0-1) 

only validates length, not the value of byte 64. The `ecrecover` host function is reachable from any deployed contract via `VMLogic::ecrecover` in: [3](#0-2) 

### Impact Explanation
- **If the panic propagates past the Wasm runner without being caught**: the node process crashes — a non-network-level DoS / consensus flaw reachable from ordinary user contract calls.
- **If wasmtime catches the panic as a trap**: the contract execution aborts abnormally — contract execution flow breakage, still in scope.

Either outcome is caused by a single unprivileged contract call passing a 65-byte signature with byte 64 set to any value `> 3` (e.g., `4`).

### Likelihood Explanation
Any account can deploy a contract or call an existing contract that invokes the `ecrecover` host function with attacker-controlled signature bytes. No privileged role is required. The trigger is a single byte value outside `[0, 3]`.

### Recommendation
Replace the `.unwrap()` with proper error propagation:

```rust
let rec_id = secp256k1::ecdsa::RecoveryId::from_i32(i32::from(self.0[64]))
    .ok_or_else(|| crate::errors::ParseSignatureError::InvalidData {
        error_message: format!("invalid recovery id: {}", self.0[64]),
    })?;
``` [4](#0-3) 

### Proof of Concept

#[test]
fn test_recover_invalid_recovery_byte_does_not_panic() {
    use near_crypto::Secp256K1Signature;
    let mut bytes = [0u8; 65];
    bytes[64] = 4; // invalid recovery id, must be 0-3
    let sig = Secp256K1Signature::from(bytes);
    // Must return Err, not panic
    let result = sig.recover([0u8; 32]);
    assert!(result.is_err(), "expected Err for invalid recovery byte, got Ok");
}

**Caveat**: The one unverified link is whether `VMLogic::ecrecover` independently validates byte 64 before calling `recover()`. If it does, the panic is unreachable from the host function path and the bug is confined to direct callers of `Secp256K1Signature::recover`. The `.unwrap()` itself is unambiguously wrong regardless.
