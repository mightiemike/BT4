### Title
Stale cached vault liquidity index used for ztoken pricing after `socialize-debt` mutates it in the same block - (File: `local-testing/contracts/market/market.clar`, `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
`market.clar` caches vault `index`/`lindex` values keyed only by `{timestamp: stacks-block-time, aid}` via `accrue-and-cache`, and reuses that cached value for the remainder of the block for pricing ztoken collateral and computing debt. However, a vault's `lindex` can be mutated directly and immediately by `socialize-debt`, a path that does not go through `accrue-and-cache` and therefore never invalidates or updates the cache entry already stored for that `{timestamp, aid}` key. Any later call in the same block that hits the cache will use the pre-socialization (stale, higher) `lindex`, mispricing that vault's ztoken.

### Finding Description
`market.clar` implements a per-timestamp cache for vault indexes to reduce cross-contract calls: [1](#0-0) 

This cache returns a cache hit unconditionally whenever an entry for `{timestamp: stacks-block-time, aid}` already exists, without re-verifying the vault's current on-chain state:
```
(match cached?
  cached-indexes (ok cached-indexes)   ;; cache HIT: returns stale value if present
  ...)
```

The cache is only populated/refreshed via `vault-accrue`, which calls the vault's public `accrue` function. That function only advances `index`/`lindex` based on elapsed time (`time-delta`), so within the same block (same `stacks-block-time`), `accrue` is a no-op for interest purposes: [2](#0-1) 

However, `market.clar` also routes a completely separate mutation path directly to the vault, bypassing `accrue-and-cache` entirely: [3](#0-2) 

That routes to the vault's `socialize-debt`, which writes down `lindex` **directly** and unconditionally (independent of time delta), to reflect a realized loss in the vault's backing assets: [4](#0-3) 

Because `socialize-debt` never touches `index-cache`, and the cache is keyed only by `{timestamp, aid}` (not by any state-mutation counter), any market-side operation earlier in the same block that already populated the cache entry for that `aid` will cause every subsequent operation in the same block to read the old, pre-loss `lindex` from the cache — even though the vault's true `lindex` has since dropped. Per the protocol's own documentation, this cached `lindex` is exactly what is used to price ztoken collateral via callcode transformation ("Retrieves indexes from cache for ztoken price resolution").

### Impact Explanation
An attacker (or even an ordinary sequence of unrelated transactions) can, within a single block:
1. Trigger any market operation referencing `aid=X` (e.g., a health check, borrow, or repay by any user) — this populates `index-cache` for `{timestamp: T, aid: X}` with the current (pre-loss) `lindex`.
2. Trigger (or wait for) a liquidation that calls `vault-socialize-debt` for the same `aid=X`, which reduces the vault's real `lindex` to reflect a bad-debt write-down — this happens without touching or invalidating the cache.
3. Within the same block (same `stacks-block-time`), post a borrow/health-check operation that uses zX as collateral; the market's ztoken price resolution hits the stale cache and values zX collateral using the higher, pre-loss `lindex`.
4. The attacker's health check passes on inflated collateral value, allowing the attacker to borrow more debt than the truly-backed collateral supports.

This results in the protocol extending debt against overvalued (already-socialized-loss) collateral, i.e., protocol insolvency / bad debt creation — an in-scope Critical impact.

### Likelihood Explanation
This requires two conditions that are both realistically reachable in a single block: (a) any market interaction touching the affected `aid` earlier in the block (which is common — health checks are ubiquitous), and (b) a `socialize-debt` call for the same `aid` later in the same block. Liquidations and socialize-debt calls, and unrelated market activity, routinely interleave within the same block on a live chain, making the ordering achievable without any privileged access — a bot merely needs to act after observing a liquidation/socialize-debt transaction is pending or has landed in the same block.

### Recommendation
Invalidate or refresh the `index-cache` entry whenever `socialize-debt` (or any other function that mutates `index`/`lindex` outside of the standard `accrue` time-based path) is invoked for that `aid`, e.g. by writing the updated indexes into `index-cache` at the same `{timestamp, aid}` key immediately after `socialize-debt` executes, or by having `accrue-and-cache` always re-verify against the vault's live state rather than trusting the timestamp-only cache key.

### Proof of Concept
1. Block N, Tx1: User A calls a market operation (e.g., `borrow`) referencing `aid = STX`. This calls `accrue-and-cache(STX)`, caching `{timestamp: T, aid: STX} → {index: I0, lindex: L0}` [1](#0-0) .
2. Block N, Tx2: A liquidator triggers a liquidation that results in market calling `vault-socialize-debt(STX, scaled-amount)` [3](#0-2) , which writes `lindex` down to `L1 < L0` directly in the vault, bypassing the cache [4](#0-3) .
3. Block N, Tx3 (same block, same `stacks-block-time` T): Attacker uses zSTX as collateral in a borrow/health-check call; market's ztoken price resolution reads `index-cache` for `{T, STX}`, gets a cache HIT returning stale `L0` instead of the true `L1`.
4. Attacker's collateral is overvalued using `L0`, allowing the attacker to pass the health check and borrow more than the true (post-loss) collateral value supports, leaving the protocol undercollateralized/insolvent for that position.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

```text
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
```
