### Title
Unmetered `GetAllBalances`/`DecCoins` iteration over `FeeCollector` in `x/uvalidator` `BeginBlocker` can be inflated by cheap fee-denom spam to stall block production - (File: `x/uvalidator/abci.go`)

### Summary
`x/uvalidator`'s `BeginBlocker` runs the same class of unmetered "iterate over an attacker-influenced coin balance in `BeginBlock`" pattern flagged in the MilkyWay report. Instead of a rewards-pool address, the balance in question here is the `FeeCollector` module account, whose full `sdk.Coins` set is fetched with `GetAllBalances` and then repeatedly folded over `sdk.DecCoins` operations inside a per-validator loop — all outside of gas metering, once every block, before consensus, before the standard `distribution` module's `BeginBlocker` even runs.

### Finding Description
`AllocateTokens` in `x/uvalidator/abci.go` is invoked from `BeginBlocker` every block (for `height > 1`): [1](#0-0) 

It reads the entire coin set of the `FeeCollector` account and converts it to `DecCoins`: [1](#0-0) 

Then, for **every bonded/UV validator vote**, it performs `DecCoins` arithmetic (`MulDecTruncate`, implicit `Add`) over the *entire* `feesCollected` set: [2](#0-1) 

Each `DecCoins` operation (`MulDecTruncate`, `Add`, `TruncateDecimal`, `SafeSub`) is `O(number of distinct denoms)`. Because the loop runs once per active Universal Validator, the total cost of `AllocateTokens` is `O(numUVs × numDistinctDenomsInFeeCollector)`, and none of it is charged against any transaction's gas meter — the entire call happens in `BeginBlock`, before any user transaction executes, exactly like the reward-termination pattern in the original report.

The `FeeCollector` balance is not bounded to a single denom: `DeductFeeDecorator` (`app/ante/fee.go`) moves whatever coins the transaction declares as its fee into `FeeCollector` via `SendCoinsFromModuleToModule`/`SendCoinsFromAccountToModule`-style transfers, which — unlike ordinary `SendCoins` — are not filtered by the bank keeper's `BlockedAddr` recipient check the way user-to-user transfers are. An unprivileged user can pay transaction fees in an arbitrary, cheaply-mintable denom (e.g. a `tokenfactory` denom it just created, or an IBC voucher of negligible value) and can do so across many transactions/blocks. Each unique denom used as a fee adds one more entry that `AllocateTokens` must iterate over indefinitely, since `FeeCollector`'s balance is only fully drained proportionally to `extraCoins`/`remainingFinal`, and dust/leftover or non-designated denoms are not evicted.

### Impact Explanation
If the number of distinct denoms accumulated in `FeeCollector` grows large (an attacker can generate this cheaply by minting many token-factory or IBC denoms and paying fees with 1-unit amounts of each), `AllocateTokens`'s per-UV `DecCoins` folding becomes proportionally expensive. Since this cost is incurred in `BeginBlock`, unmetered, and multiplied by the number of active Universal Validators, it can materially slow or stall block production chain-wide — a denial-of-service reachable purely through ordinary, unprivileged fee-paying transactions, matching the "denial of service... reachable without privileged control" allowed-impact category.

### Likelihood Explanation
Requires an attacker to be able to (a) create or acquire many distinct denominations cheaply (token factory denoms are permissionless to create on most Cosmos chains; IBC vouchers can also be diversified) and (b) have those denoms accepted as valid transaction fee denoms by the chain's fee-market/ante configuration. I was not able to fully confirm within the available tool budget whether Push Chain's fee-denom validation (`app/ante/fee.go`, `app/cosmos/min_gas_price.go`) restricts fees to a single allow-listed denom (e.g. `upc`) — if it does, this specific vector is significantly harder to exploit and would require another route to inflate `FeeCollector`'s denom count. This uncertainty should be verified directly against `app/ante/fee.go` and the fee-market params before treating this as high-likelihood.

### Recommendation
- Cap or fix the number of denoms `AllocateTokens` will process per block (e.g., only operate on the chain's canonical fee/staking denom, ignoring/skipping any other denom present in `FeeCollector`).
- Alternatively, restrict `FeeCollector` to a single recognized fee denom at the ante-handler level so it can never accumulate attacker-chosen denoms.
- If multi-denom fees must be supported, add an explicit bound on distinct denoms processed, or perform this accounting metered (i.e., not in `BeginBlock`), so a large denom set degrades service in a bounded way rather than stalling consensus.

### Proof of Concept
Conceptual PoC (mirrors the original report's structure):
1. Attacker permissionlessly creates N `tokenfactory` denoms (or acquires N distinct IBC voucher denoms) cheaply.
2. Attacker submits N transactions, each specifying a `1`-unit fee in a different one of these denoms (assuming the ante/fee-market config accepts non-`upc` fee denoms — needs confirmation).
3. Each of these fee payments lands in the `FeeCollector` module account via the ante `DeductFeeDecorator`, which is not subject to the recipient `BlockedAddr` check applied to ordinary `SendCoins`.
4. On the next block, `x/uvalidator`'s `BeginBlocker` → `AllocateTokens` calls `GetAllBalances(FeeCollector)` and then iterates the resulting `DecCoins` set once per active Universal Validator via `MulDecTruncate`/`Add`, at `O(numUVs × N)` unmetered cost, degrading block production time proportionally to N. func BeginBlocker(ctx sdk.Context, uvalidatorKeeper keeper.Keeper) error {
	defer telemetry.ModuleMeasureSince(types.ModuleName, time.Now(), telemetry.MetricKeyBeginBlocker)

	ctx.Logger().Debug("uvalidator BeginBlocker started", "block_height", ctx.BlockHeight())

	// determine the total power signing the block
	var previousTotalPower int64
	for _, voteInfo := range ctx.VoteInfos() {
		previousTotalPower += voteInfo.Validator.Power
	}

	// full amount will be allocated to community pool by distribution module itself
	if previousTotalPower == 0 {
		ctx.Logger().Debug("uvalidator BeginBlocker: no voting power, skipping token allocation", "block_height", ctx.BlockHeight())
		return nil
	}

	height := ctx.BlockHeight()
	if height > 1 {
		ctx.Logger().Info("uvalidator BeginBlocker: allocating tokens",
			"block_height", height,
			"total_previous_power", previousTotalPower,
			"vote_infos_count", len(ctx.VoteInfos()),
		)
		if err := AllocateTokens(ctx, previousTotalPower, ctx.VoteInfos(), uvalidatorKeeper); err != nil {
			ctx.Logger().Error("uvalidator BeginBlocker: token allocation failed",
				"block_height", height,
				"error", err.Error(),
			)
			return err
		}
		ctx.Logger().Info("uvalidator BeginBlocker: token allocation complete", "block_height", height)
	}

	return nil
}
