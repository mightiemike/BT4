### Title
Exchange (Bancor-style TRC10 AMM) can be permanently bricked by driving `first_token_balance`/`second_token_balance` to zero or negative when hardened math is not enforced - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The `Exchange` on-chain AMM (created via `ExchangeCreateContract`, traded via `ExchangeTransactionContract`) computes new pool balances from the Bancor-style relay-token formula in `ExchangeCapsule.transaction()`, but the resulting balances are only checked for going below zero when the *hardened* calculation flag is active. When `hardenedCalc` is `false`, a large sell can push one side of the pool exactly to zero (or negative, silently accepted), after which every actuator that reads the exchange (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) unconditionally rejects further operations once a balance is zero, permanently bricking the pool — mirroring the levETH “cannot be bought back once supply hits zero” bug class: a missing bound during the state-mutating (sell/burn) path allows a value to reach zero, and the only zero-guard exists on the read/mitigation side, too late to prevent the trap.

### Finding Description
`ExchangeCapsule.transaction()` computes the new pool balances from the AMM math and only validates non-negativity when `hardenedCalc` is true: [1](#0-0) 

```java
public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
    boolean hardenedCalc) throws ContractValidateException {
  ...
  if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
    throw new ContractValidateException("Exchange balance must be >=0 after transaction");
  }
  this.exchange = this.exchange.toBuilder()
      .setFirstTokenBalance(newFirstTokenBalance)
      .setSecondTokenBalance(newSecondTokenBalance)
      .build();
  return buyTokenQuant;
}
```

`hardenedCalc` is supplied by `allowHarden()`, which is gated behind the dynamic-properties/proposal flag `allowHardenExchangeCalculation()`: [2](#0-1) 

So whenever this proposal-controlled flag is not active (e.g. on chains/networks where it has not yet been activated, or historically before it existed), `ExchangeTransactionActuator.execute()` invokes `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` with `hardenedCalc=false`, and the non-negativity bound is skipped entirely: [3](#0-2) 

The only zero-balance protection in the whole subsystem is a *pre-condition* check performed in `doValidate()` of the three actuators, which rejects the transaction if the balance is **already** zero — it does nothing to stop a transaction from **making** it zero: [4](#0-3) [5](#0-4) [6](#0-5) 

This is structurally identical to the Plaza Finance root cause: `Pool.sol#_redeem` burns levETH without checking whether the resulting `totalSupply` would hit zero, and only the downstream `getCreateAmount()` guards against `assetSupply == 0` by reverting — by the time the zero state is reached, the pool is unusable. Here, `ExchangeCapsule.transaction()` (the “burn”/balance-mutation path) lacks the bound unless hardened math is turned on, while the zero-guard living in the three `doValidate()` methods (the “price calculation”/read path) can only refuse future trades once the damage is already done — it can never repair the pool.

### Impact Explanation
Once `first_token_balance` or `second_token_balance` reaches zero (or, absent the hardened check, even negative, since `long` subtraction wraps/underflows silently in non-hardened mode), the exchange becomes permanently unusable:
- `ExchangeTransactionActuator` rejects all future trades ("Token balance in exchange is equal with 0, the exchange has been closed").
- `ExchangeInjectActuator` rejects any attempt by the creator to replenish it with the same message.
- `ExchangeWithdrawActuator` likewise rejects withdrawal-side rebalancing.

This permanently locks whatever TRX/TRC10 reserves remain on the other side of the pool and destroys the exchange's core functionality — an unprivileged trader can trigger this by simply executing a normal large sell via `ExchangeTransactionContract`, no privileged role required.

### Likelihood Explanation
Any unprivileged account holding either paired asset (TRX or a TRC10 token) can call `ExchangeTransactionContract` to sell into the pool; achieving an exact/near-zero remaining balance requires sizing the sell relative to the pool's current balances, which is fully observable on-chain (`getFirstTokenBalance()`/`getSecondTokenBalance()` are public state). The condition is only avoided while `allowHardenExchangeCalculation()` is active network-wide; on any deployment or historical chain state where that committee-approved hardening proposal has not been passed, the vulnerable path is live and reachable by ordinary users.

### Recommendation
Remove the `hardenedCalc &&` qualifier so the non-negativity bound in `ExchangeCapsule.transaction()` is enforced unconditionally (both in the legacy math path and the hardened one), and reject the transaction outright rather than silently persisting an out-of-range balance:

```java
if (newFirstTokenBalance <= 0 || newSecondTokenBalance <= 0) {
  throw new ContractValidateException("Exchange balance must be >0 after transaction");
}
```

This mirrors the recommended Plaza Finance fix of validating the resulting state *before* committing the burn/balance update, instead of only detecting the zero state afterward when it is already unrecoverable.

### Proof of Concept
1. Create an exchange with a small `second_token_balance` relative to available liquidity, e.g. `ExchangeCreateContract{first_token_id: TRX, first_token_balance: 100_000_000, second_token_id: <TRC10>, second_token_balance: 100_000_000}`.
2. Ensure `allowHardenExchangeCalculation()` is not active (default/legacy chain parameter state) so `allowHarden()` returns `false`.
3. Submit an `ExchangeTransactionContract` selling a sufficiently large `tokenQuant` of the first token such that `ExchangeProcessor.exchangeFromSupply` computes `buyTokenQuant` equal to (or exceeding, due to floating point in the legacy path) `secondTokenBalance`. Because `hardenedCalc` is `false`, `ExchangeCapsule.transaction()` at [7](#0-6)  skips the bound check and commits `newSecondTokenBalance <= 0`.
4. Any subsequent `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` referencing this `exchange_id` now fails validation with "Token balance in exchange is equal with 0, the exchange has been closed" at [4](#0-3) , permanently bricking the pool and stranding the remaining reserve of the other token.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
