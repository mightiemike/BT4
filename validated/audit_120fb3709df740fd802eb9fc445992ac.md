The CVE describes an infinite loop in MuPDF's `fz_skip_space` where the read position could fail to advance on certain crafted PDF bytes, causing indefinite looping. Searching for the analogous invariant in protobuf-go's parsers — the JSON decoder's `consume` function [1](#0-0) , the text decoder's `consume` function [2](#0-1) , and the `skipJSONValue` loop used for Any/well-known-type handling [3](#0-2)  — shows that in each case the underlying byte slice `d.in` is monotonically truncated on every iteration (via slicing `b[n:]` or `b[1:]`), and the loop only continues while `len(b) > 0`. This guarantees termination for any finite input, unlike the MuPDF bug where the position pointer could stall without consuming bytes.

The `Decoder.Read()` paths in both JSON and text decoders always either advance the input pointer via `consumeToken`/`consume` or return an error (including an explicit `unexpected EOF` guard in `skipJSONValue` for the case where `Read` returns `EOF` unexpectedly) [4](#0-3) . There is no code path where whitespace/space-skipping can loop without consuming input, so there is no reachable analog to the `fz_skip_space` infinite-loop bug on a trusted-schema, default binary/ProtoJSON parsing path.

// consume consumes n bytes of input and any subsequent whitespace or comments.
func consume(b []byte, n int) []byte {
	b = b[n:]
	for len(b) > 0 {
		switch b[0] {
		case ' ', '\n', '\r', '\t':
			b = b[1:]
		case '#':
			if i := bytes.IndexByte(b, '\n'); i >= 0 {
				b = b[i+len("\n"):]
			} else {
				b = nil
			}
		default:
			return b
		}
	}
	return b
}

func (d decoder) skipJSONValue() error {
