### Title
Unchecked integer arithmetic in resource/energy and exchange accounting paths defaults to silent overflow unless a chain-parameter "harden" flag is enabled - (File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java)

### Summary
Large parts of java-tron's resource (bandwidth/energy) accounting, exchange math, and TVM energy-limit calculations perform raw `long`/`double` arithmetic (`*`, `/`, `+`, `-`) with no overflow protection unless a runtime-controlled feature flag (`allowHardenResourceCalculation()` / `allowHardenExchangeCalculation()` / `disableJavaLangMath()`/`useStrictMath`) is turned on. This mirrors the GEB "not using SafeMath" report: the unsafe path is silent-overflow-prone and is the one exercised by default, while the safe (BigInteger/`*Exact`) path exists but is opt-in.

### Finding Description
The codebase contains a parallel "hardened" implementation (using `BigInteger`/`Math.addExact`/`multiplyExact`) alongside a legacy unguarded implementation, selected by `hardenCalculation()`/`hardenResourceCalculation()`/`allowHardenExchangeCalculation()`, which read from `DynamicPropertiesStore` chain parameters that are off by default and only flippable via a witness proposal (not by an ordinary user in a single transaction). Examples of the unguarded arithmetic that executes by default:

- `ResourceProcessor.increase`/`increaseV2`/`unDelegateIncreaseV2`: `averageLastUsage = divideCeil(lastUsage * this.precision, oldWindowSize)`, `newWindowSize = divideCeil(remainUsage * remainWindowSize + usage * this.windowSize * WINDOW_SIZE_PRECISION, newUsage)` [1](#0-0) , and `getUsage`: `return usage * windowSize / precision;` [2](#0-1) .
- `EnergyProcessor.calculateGlobalEnergyLimit`: `return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));` when not hardened, versus the `BigInteger` path when hardened [3](#0-2) ; `scaleByRate`: `return value * numerator / denominator;` [4](#0-3) .
- `ExchangeProcessor` (legacy AMM math, still selected whenever `hardenedCalc` is false) does plain `long`/`double` arithmetic without overflow checks: `long newBalance = balance + quant;` and casts `double` results back to `long` [5](#0-4) , contrasted with the `SafeExchangeProcessor` that uses `StrictMathWrapper`/`BigDecimal` [6](#0-5) .
- `ExchangeCapsule.transaction` chooses between the two processors based on the caller-supplied `hardenedCalc` boolean, and even in "hardened" mode still computes `firstTokenBalance + sellTokenQuant` / `secondTokenBalance - buyTokenQuant` with plain operators when `hardenedCalc` is false [7](#0-6) .
- `RepositoryImpl.calculateGlobalEnergyLimit`/`getUsage` use the same dual-path pattern with the legacy branch doing raw `usage * windowSize / precision` and `energyWeight * ((double) totalEnergyLimit / totalEnergyWeight)` [8](#0-7) .

The existing project test suite itself documents that the unguarded path silently overflows/loses precision (e.g. `testIncreaseOverflowSilentWithoutHardening`, `testGetUsageCorrectAcrossOverflowBoundary` showing the non-hardened result diverges from the exact `BigInteger` result) [9](#0-8) , and `testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio` explicitly asserts the legacy formula (`10000L * (totalEnergyLimit / totalEnergyWeight)`) is "buggy" and differs from the correct value [10](#0-9) .

### Impact Explanation
These arithmetic paths compute account energy/bandwidth usage windows and AMM (Exchange) swap amounts that are reachable from ordinary broadcast transactions (`TriggerSmartContract`, `DelegateResource`/`UnDelegateResource`, `ExchangeInject`/`Withdraw`/`Transaction`) and from TVM execution during energy metering for any contract call. Since the safe (`BigInteger`/`*Exact`) code path is gated behind chain parameters that default to disabled and require a super-representative/witness-approved proposal to flip, the arithmetic that actually executes for ordinary users is the unguarded legacy path. Silent overflow or precision loss in resource accounting can corrupt an account's bandwidth/energy "usage window" bookkeeping (potentially granting more free resource than entitled, i.e., resource accounting corruption), and precision loss/overflow in the AMM math can produce incorrect swap outputs in `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction`, corrupting token pool balances.

### Likelihood Explanation
Triggering intermediate values large enough to overflow a `long` (order 2^63) requires extreme but not impossible input combinations (e.g., very large `usage`/`windowSize`/`precision` products, or very large TRX/asset balances approaching `Long.MAX_VALUE`), and the "hardened" default-off gating means this is the code path exercised in production today. However, actually causing overflow generally requires either very large account balances/usage values that accumulate over time or attacker-influenced parameters within existing validation bounds (e.g., asset quantities up to `Long.MAX_VALUE`, as demonstrated by the project's own `ParticipateAssetIssueActuatorTest` overflow tests), so likelihood is moderate rather than trivially exploitable in a single transaction.

### Recommendation
Make the "hardened" (`BigInteger`/`*Exact`) arithmetic the unconditional default in `ResourceProcessor`, `EnergyProcessor`, `RepositoryImpl`, and `ExchangeProcessor`/`ExchangeCapsule`, rather than an opt-in chain parameter, so that overflow/precision-loss protection is not dependent on governance action. At minimum, add explicit bounds checks on `usage`, `windowSize`, `precision`, token balances, and quantities before performing multiplication/division so intermediate overflow cannot occur regardless of the harden flag's state.

### Proof of Concept
Not independently reproducible from static review alone; the repository's own hardening test suite (`ResourceProcessorHardenTest`, `RepositoryImplHardenTest`, `CalculateGlobalLimitHardenTest`) already demonstrates the divergence between hardened and non-hardened arithmetic under large `usage`/`windowSize`/`totalWeight` values, e.g. `testGetUsageCorrectAcrossOverflowBoundary` shows the non-hardened `getUsage` result differs from the exact `BigInteger` computation [11](#0-10) , confirming the unguarded default path is exploitable given sufficiently large (but reachable) account resource values.
