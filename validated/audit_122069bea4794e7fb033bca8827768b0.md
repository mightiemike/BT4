### Title
`DelegateAction` Signed Payload Omits Chain Identifier, Enabling Cross-Network Replay of Meta-Transactions — (`core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

---

### Summary

`DelegateAction` (NEP-366 meta-transactions) and `DelegateActionV2` (NEP-611) produce their signing hash from a payload that contains no chain/network identifier. A signed delegate action created for NEAR testnet is cryptographically valid on NEAR mainnet (or any other NEAR-based network) if the same account and key exist there, the nonce is still acceptable, and `max_block_height` has not been exceeded. A malicious relayer — an ordinary, unprivileged NEAR account — can replay the testnet-intended delegate action on mainnet, executing the inner actions (e.g., a `Transfer`) against the sender's mainnet balance without their consent.

---

### Finding Description

`DelegateAction::get_nep461_hash()` constructs the signed payload as:

```
SHA-256( borsh( MessageDiscriminant(NEP-366) || sender_id || receiver_id || actions || nonce || max_block_height || public_key ) )
``` [1](#0-0) 

`VersionedDelegateActionPayload::get_nep461_hash()` (for V2) does the same with `SignableMessageType::DelegateActionV2`: [2](#0-1) 

`SignableMessage` serializes only a `MessageDiscriminant` (a fixed NEP-number constant) and the message body — no chain identifier of any kind: [3](#0-2) 

The discriminant values are compile-time constants (`NEP_366_META_TRANSACTIONS = 366`, `NEP_611_GAS_KEYS = 611`) that are identical on every NEAR network: [4](#0-3) 

By contrast, a regular `SignedTransaction` commits to a `block_hash` field, which is chain-specific (different genesis → different block hashes). `DelegateAction` replaces that with `max_block_height`, a plain integer that carries no network identity. [5](#0-4) 

`apply_delegate_action` verifies the signature, checks `max_block_height`, and validates the nonce — but performs no check that the action was intended for the current network: [6](#0-5) 

---

### Impact Explanation

A malicious relayer (an ordinary NEAR account) who receives a signed `DelegateAction` intended for testnet can submit it verbatim to mainnet. If the sender's mainnet account holds the same key and the nonce is still valid, the runtime will accept the signature, advance the nonce, and execute the inner actions — including `Transfer`, `FunctionCall`, `AddKey`, or `DeleteAccount` — against the sender's **mainnet** balance and state, without any further authorization from the sender. This constitutes an unauthorized transaction and potential loss of real funds.

---

### Likelihood Explanation

- Developers routinely reuse the same ED25519 key pair across testnet and mainnet.
- NEAR mainnet and testnet are both at block heights in the hundreds of millions; a `max_block_height` set to `current_testnet_height + N` will almost always be valid on mainnet as well.
- The nonce in a `DelegateAction` must exceed the current access-key nonce on the target chain. For a user who is more active on testnet than mainnet, the testnet nonce will be higher, making the testnet-signed action valid on mainnet.
- The relayer is the only party who needs to act maliciously; the victim user performs no unusual action.

---

### Recommendation

Include the network's `chain_id` string (available from genesis config, e.g., `"mainnet"`, `"testnet"`) in the Borsh-serialized payload that is hashed for the `DelegateAction` signature. This mirrors how `SignedTransaction` binds to a specific chain via `block_hash`. Concretely, add a `chain_id: String` field to `DelegateAction` / `DelegateActionV2`, or extend `SignableMessage` with a chain-binding prefix, and gate acceptance on a new protocol version.

---

### Proof of Concept

1. Alice holds account `alice.near` on both testnet and mainnet with the same ED25519 key. Her mainnet access-key nonce is 5; her testnet nonce is 10.
2. Alice signs a `DelegateAction` on testnet: `sender_id = alice.near`, `receiver_id = bob.near`, `actions = [Transfer(100 NEAR)]`, `nonce = 11`, `max_block_height = testnet_height + 200`, `public_key = alice_key`.
3. She hands the `SignedDelegateAction` to a relayer she trusts for testnet use.
4. The relayer wraps it in a mainnet `SignedTransaction` (outer tx: `signer = relayer.near`, `receiver = alice.near`) and broadcasts it to mainnet.
5. `apply_delegate_action` on mainnet:
   - Recomputes `get_nep461_hash()` — identical to the testnet hash because no chain_id is included. [7](#0-6) 
   - Signature verifies. [8](#0-7) 
   - `max_block_height` check passes (mainnet is at a similar height). [9](#0-8) 
   - Nonce 11 > mainnet nonce 5 → valid.
6. 100 mainnet NEAR is transferred from `alice.near` to `bob.near` without Alice's consent.

    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }

    /// Delegate action hash used for NEP-461 signature scheme which tags
    /// different messages before hashing
    ///
    /// For more details, see: [NEP-461](https://github.com/near/NEPs/pull/461)
    pub fn get_nep461_hash(&self) -> CryptoHash {
        let signable = SignableMessage::new(&self, SignableMessageType::DelegateActionV2);
        let bytes = borsh::to_vec(&signable).expect("failed to serialize");
        hash(&bytes)
    }
