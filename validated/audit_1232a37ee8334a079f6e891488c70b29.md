### Title
Unbounded Recursive JSON Deserialization in JSON-RPC Request Handler Causes Stack-Overflow Process Crash - (File: chain/jsonrpc/src/lib.rs)

### Summary
The NEAR JSON-RPC server deserializes every inbound POST body into a `Message`/`Request` type using Axum's `Json<T>` extractor, which is backed by `serde_json`'s recursive-descent parser. `serde_json`'s `Value` type (used for the `params` field of a JSON-RPC request) has no built-in recursion-depth limit, so an attacker-controlled, syntactically valid but deeply nested JSON payload (e.g. millions of nested arrays `[[[[...]]]]`) can drive the parser into unbounded recursion. In Rust, a native stack overflow is not a recoverable panic — it aborts the whole process via SIGSEGV/illegal instruction. This mirrors CVE-2017-1000118 (Akka HTTP), where recursive parsing of an attacker-controlled `Accept` header caused a `StackOverflowError` and crashed the service; here, recursive parsing of attacker-controlled JSON causes the entire `neard` process, including validator/chunk-producer logic sharing that process, to crash.

### Finding Description
`rpc_handler()` in [1](#0-0)  extracts the request body with `Json<Message>`, which internally uses `serde_json` to deserialize into the `Message`/`Request` structure defined in `near_jsonrpc_primitives::message`. The `Request::params` field is a generic `serde_json::Value`, confirmed by its usage in `handle_unknown_block()` (`request.params.get("block_id")`) at [2](#0-1) .

`serde_json::Value`'s deserializer is a classic recursive-descent parser: each nested `[` or `{` token recurses one stack frame deeper with no depth ceiling. The RPC-layer documentation states a request body size limit exists (default 10MB) as middleware, but no depth-limiting parser (e.g. `serde_json` with a `RecursionLimit`, or `serde_stacker`) is used anywhere in the RPC parameter-parsing pipeline (`chain/jsonrpc/src/api/mod.rs` `Params<T>` helper at [3](#0-2)  only wraps `serde_json::from_value`, which does not impose a depth limit either). A 10MB body consisting solely of the two-byte-per-level pattern `[` repeated millions of times comfortably fits under the body-size limit while producing several-million levels of recursion — far beyond typical native thread stack sizes (commonly 2–8MB), guaranteeing a stack overflow.

This is directly analogous to the reported Akka HTTP bug class: unauthenticated, attacker-supplied structured text is fed into a recursive parser with no depth bound, and the resulting stack exhaustion is not a catchable exception in the target language — it terminates the process.

### Impact Explanation
Any unprivileged network caller who can reach the JSON-RPC HTTP endpoint (`POST /`, the primary interface exposed on port 3030 by every node, including validators) can crash the entire `neard` process with a single crafted request. Because JSON-RPC, ClientActor, and validator/chunk-producing logic run in the same OS process, this is a transaction/RPC-triggered halt of the node — not merely a thread/connection-level failure. If exploited broadly (e.g. against multiple validators simultaneously), this could degrade or halt block production network-wide, which is a High severity availability impact consistent with the CVSS 3.0 AV:N/AC:L/PR:N/UI:N/S:U/A:H rating of the original advisory.

### Likelihood Explanation
High. The JSON-RPC endpoint requires no authentication, no funds, and no special privileges — any RPC caller can send a POST request. Constructing the payload only requires generating a repeating character pattern, which is trivial and requires no protocol-level knowledge (no valid transaction, signature, or account is needed since the crash occurs during body deserialization, before method dispatch or transaction validation).

### Recommendation
- Impose an explicit maximum JSON nesting depth before/while deserializing RPC request bodies (e.g., via a depth-checked parsing wrapper, `serde_stacker`, or a pre-parse structural scan that rejects overly nested input) in `rpc_handler()` at `chain/jsonrpc/src/lib.rs` and in `Params<T>`/`RpcRequest::parse` in `chain/jsonrpc/src/api/mod.rs`.
- Apply the same protection to the Rosetta RPC server (`chain/rosetta-rpc/src/lib.rs`), which also uses `Json<T>` extractors on unauthenticated endpoints.
- Consider running the request-body deserialization on a dedicated worker thread with a bounded stack, so an overflow terminates only that worker rather than the whole process (defense in depth), and/or increase resilience by catching stack-overflow conditions via a guard page thread strategy.

### Proof of Concept
1. Start a `neard` node with the JSON-RPC server enabled on the default port (3030).
2. Send a POST request to `/` with a body such as:
   ```
   {"jsonrpc":"2.0","id":"1","method":"status","params": <N million repetitions of '['> <N million repetitions of ']'> }
   ```
   generated e.g. with Python: `body = b'{"jsonrpc":"2.0","id":"1","method":"status","params":' + b'[' * 5_000_000 + b']' * 5_000_000 + b'}'`
3. Observe that the `neard` process crashes (stack overflow / SIGSEGV) while `serde_json` recursively deserializes the `params: Value` field inside the `Json<Message>` extractor used by `rpc_handler()`, rather than returning a JSON-RPC parse error.
