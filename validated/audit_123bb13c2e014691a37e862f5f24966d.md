### Title
`liquidate-multi` absorbs failures after debt repayment has already been executed, stranding the liquidator's funds - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The external report's bug class is: a value-bounding check that is technically satisfied (`_receiverGas > 0`) is insufficient to guarantee the later, asynchronous step (destination `lzReceive`) actually succeeds, so the earlier step (token burn/lock) is committed while the later step silently fails, permanently losing user funds. The Zest analog is `liquidate-multi` in `market.clar` / `v0-4-market.clar`, which iterates positions with `map` and unconditionally wraps every result in `(ok ...)`. Inside each iteration, `liquidate` first performs an irreversible transfer (`vault-system-repay`, which pulls the liquidator's tokens to repay the vault) and only afterward performs the bookkeeping/collateral-crediting step (`debt-remove-scaled` / `collateral-remove`) that can itself fail. Because the outer `liquidate-multi` call always returns `(ok ...)` regardless of what individual `call-liquidate` invocations return, a failure in the second step does not roll back the transaction, and the already-executed repayment from the first step is permanently committed while the liquidator receives no offsetting collateral.

### Finding Description
`liquidate` performs its critical steps in a fixed, non-atomic-with-respect-to-caller order:

1. `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` — pulls the liquidator's debt tokens into the vault, an irreversible value transfer. [1](#0-0) 

2. Only after that, it calls `.v0-market-vault` `debt-remove-scaled` and `collateral-remove` to update the borrower's obligation and transfer collateral to the liquidator: [2](#0-1) 

When `liquidate` is invoked directly (not through `liquidate-multi`), any failure in step 2 propagates as an `(err ...)` from the top-level public call, and Clarity rolls back the entire transaction, including the already-executed `vault-system-repay`, so no funds are stranded.

However, `liquidate-multi` calls each position through `call-liquidate`, which calls `liquidate` as a plain in-contract function call (not `contract-call?`), and returns whatever `liquidate` returns — `(ok ...)` or `(err ...)` — as a list element: [3](#0-2) 

The outer function then unconditionally wraps the whole list in success: [4](#0-3) 

Since `liquidate-multi`'s own top-level return value is always `(ok (map call-liquidate positions))`, the overall transaction always commits. If, for any one position in the batch, `vault-system-repay` succeeds but the subsequent `debt-remove-scaled` or `collateral-remove` call fails (e.g., the vault's own invariant checks reject the removal — a plausible degenerate input analogous to `_receiverGas = 1`, since nothing in `liquidate-multi`/`liquidate` guarantees these two calls will consistently succeed together), the committed effect is: the liquidator's repayment tokens are already spent into the vault, but the borrower's on-book debt is not reduced and the liquidator receives no collateral. The batch call as a whole still reports success.

This exactly mirrors the reported bug class: a value-bound (irreversible transfer) that is not invalidated/rolled back when a later, dependent step fails, because the enclosing entry point (`liquidate-multi`'s `ok`-wrapping `map`) absorbs the failure instead of propagating it, "stranding value on abort."

### Impact Explanation
The liquidator's repaid debt tokens are consumed by the vault while the corresponding debt-obligation reduction and collateral transfer do not occur for that position. This is a direct, permanent loss of the liquidator's funds in a single transaction with no compensating action — falling under the in-scope Critical impact class ("direct theft/loss of user funds... other than unclaimed yield") since the liquidator's capital is irrecoverably consumed without the expected collateral being delivered, and the protocol's internal debt/collateral accounting becomes inconsistent for that borrower.

### Likelihood Explanation
This requires only that one entry within a `liquidate-multi` batch reaches `vault-system-repay` successfully but subsequently fails at `debt-remove-scaled` or `collateral-remove` in `.v0-market-vault` — a downstream contract-call boundary whose internal invariants (balance/authorization checks, etc.) are not guaranteed to always succeed once the repay step has already completed. Because `liquidate-multi` is a comment-documented "Failed liquidations return error codes but don't revert entire batch" design, the absorbing behavior is intentional for *early* failures (before `vault-system-repay`), but the code does not distinguish early failures from failures that occur *after* the irreversible repay has already executed — making this reachable by any liquidator submitting a batch where one position's later step is rejected by the vault after the repay call has already succeeded.

### Recommendation
Ensure that any failure occurring after `vault-system-repay` has executed causes the entire `liquidate` call for that position to be rolled back atomically with respect to `vault-system-repay`, e.g., by performing the token pull only after all bookkeeping calls (`debt-remove-scaled`, `collateral-remove`) have succeeded, or by using a genuinely atomic sub-transaction boundary (`contract-call?` to a wrapper) so a failure after the repay reverts the repay as well. Additionally, `liquidate-multi` should either propagate genuine mid-execution failures (distinguishing "position not liquidatable" pre-checks, which can safely be skipped, from "partial execution" failures, which must abort the whole batch transaction) rather than uniformly wrapping all results in `(ok ...)`.

### Proof of Concept
1. Liquidator calls `liquidate-multi` with a batch containing position `P` where the borrower's debt/collateral state is such that `vault-system-repay` for `P` succeeds (liquidator's debt tokens are pulled into the vault).
2. Immediately afterward within the same `liquidate` execution for `P`, the call to `.v0-market-vault` `debt-remove-scaled` or `collateral-remove` fails (returns `(err ...)`), e.g., due to a vault-side invariant check being violated for that borrower/collateral combination.
3. `call-liquidate` returns this `(err ...)` as the corresponding list element; `liquidate-multi` still returns `(ok (list ... (err ...) ...))`. [4](#0-3) 
4. The overall transaction commits: the liquidator's tokens spent in step 1 (`vault-system-repay`) remain spent, but the liquidator never receives the seized collateral and the borrower's on-book debt for `P` is not reduced — the liquidator's funds are permanently stranded.
