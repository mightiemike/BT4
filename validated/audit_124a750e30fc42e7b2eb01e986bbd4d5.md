## Analog Vulnerability Found

### Title
HMAC canonicalization collision in App Proxy signature verification allows query-parameter forgery - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The `SuperVaultAggregator` bug class — building a security-critical hash by concatenating variable-length fields with `abi.encodePacked()` and no delimiters — has a direct structural analog in the App Proxy HMAC canonicalization logic. `stringifyQueryForAppProxy` builds the string that is HMAC-signed/verified by directly concatenating `key=value` pairs with **no separator** between successive pairs, exactly the pattern that causes ambiguous/colliding serializations.

### Finding Description
`stringifyQueryForAppProxy` builds the canonical string for app-proxy signature verification as: [1](#0-0) 

```ts
function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}
```

Note two things:
1. Successive `key=value` pairs are concatenated with **no delimiter** at all (unlike `stringifyQueryForAdmin`, which uses `ProcessedQuery`/`URLSearchParams`, producing a proper `&`-delimited, percent-encoded query string: [2](#0-1)  and [3](#0-2) ).
2. Multi-value (repeated) parameters are joined with a bare `,` — the exact "packed concatenation of variable-length values" pattern flagged in the report.

This concatenation scheme is verified against the incoming `signature`/`hmac` in `validateHmac`: [4](#0-3) . Duplicate-parameter protection is applied only to a fixed allowlist of security fields (`hmac`, `shop`, `signature`, `timestamp`); any other repeated key — including application-relevant identity fields such as `logged_in_customer_id` or `path_prefix` — is silently merged into the canonical string with a comma via `normalizeQuery`: [5](#0-4) [6](#0-5) 

Because neither the pair separator nor the value separator is unambiguous, two semantically different query-parameter sets can serialize to byte-identical canonical strings, and therefore produce/validate against the identical HMAC.

### Impact Explanation
Since Shopify's App Proxy forwards the *entire* incoming query string (Shopify-appended security fields plus arbitrary pass-through fields chosen by the anonymous storefront visitor who constructed the proxy link) and signs that combined set, an attacker who controls the non-reserved query parameters of an app-proxy request can choose key names/values whose sorted concatenation collides with a different, more sensitive parameter split (e.g., shifting characters across a key/value boundary, or supplying a duplicate non-allowlisted key such as `logged_in_customer_id` that gets silently comma-joined). A signature that Shopify legitimately computes for the attacker's chosen (spoofed) parameter layout will also validate when the app's business logic parses the *same bytes* as a different, unintended key/value split — e.g. altering how `logged_in_customer_id` or `path_prefix` is interpreted downstream — while `validateHmac` still reports the request as authentic. This is the "accepted forged Shopify request" class: the verifier accepts a request whose effective (parsed) content differs from what was actually authorized/signed as intended, potentially enabling identity confusion for the customer/session context an app proxy handler relies on.

### Likelihood Explanation
Reachable by any anonymous/unauthenticated actor: app-proxy endpoints are triggered by ordinary storefront requests, and the vulnerable canonicalization path (`signator: 'appProxy'`) is exercised on every such request. No privileged access, leaked secret, or MITM is required — only crafting a URL with attacker-chosen extra query parameter names/values, which Shopify will faithfully sign and forward. Only the fixed 4-item allowlist (`hmac`, `shop`, `signature`, `timestamp`) is hardened against duplicate/boundary abuse (per the `857c598` changeset noted in the changelog); all other parameters, including ones apps commonly treat as security-relevant (`logged_in_customer_id`, `path_prefix`), remain susceptible to the ambiguous, delimiter-less concatenation.

### Recommendation
1. Use an unambiguous, delimited, and properly escaped serialization for the app-proxy canonical string (e.g., percent-encode keys/values and join pairs with `&`, mirroring `stringifyQueryForAdmin`'s use of `ProcessedQuery`), instead of raw `${acc}${key}=${value}` concatenation — analogous to switching from `abi.encodePacked()` to `abi.encode()`.
2. Extend duplicate/ambiguity protection beyond the four hardcoded security keys to all query parameters (or explicitly document/enforce that any parameter an app treats as trust-bearing, such as `logged_in_customer_id`, must be treated as single-value and rejected if duplicated), closing the "silently comma-joined" collision surface in `normalizeQuery`.

### Proof of Concept
Given the current implementation, these two distinct parameter sets serialize to the identical canonical string and thus the identical signature:

- Set A: `{"a": "1", "ab": "2"}` → sorted → `"a" + "=" + "1" + "ab" + "=" + "2"` = `a=1ab=2`
- Set B: `{"a": "1a", "b": "2"}` → sorted → `"a" + "=" + "1a" + "b" + "=" + "2"` = `a=1ab=2`

Both produce the canonical string `a=1ab=2`, so `createSHA256HMAC(apiSecretKey, "a=1ab=2", ...)` is identical for both, meaning a signature Shopify computes for one parameter layout will pass `validateHmac` for the other, differently-parsed layout. The same boundary-shifting technique applies to real app-proxy fields (e.g. `path_prefix`/`logged_in_customer_id`) and to the comma-joined array case, e.g. `{"foo": "a,b"}` vs `{"foo": ["a","b"]}` both serialize to `foo=a,b`, as already demonstrated for the *security* param set in the repo's own tests: [7](#0-6) .

export function validateHmac(config: ConfigInterface) {
  return async (
    query: HmacQuery,
    {signator}: {signator: HMACSignator} = {signator: 'admin'},
  ): Promise<boolean> => {
    const normalizedQuery = normalizeQuery(query, signator);

    if (signator === 'admin' && !normalizedQuery.hmac) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain an HMAC value.',
      );
    }

    if (signator === 'appProxy' && !normalizedQuery.signature) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain a signature value.',
      );
    }

    validateHmacTimestamp(normalizedQuery);

    const hmac =
      signator === 'appProxy'
        ? normalizedQuery.signature
        : normalizedQuery.hmac;
    const localHmac = await generateLocalHmac(config)(
      normalizedQuery,
      signator,
    );

    return safeCompare(hmac as string, localHmac);
  };
}
