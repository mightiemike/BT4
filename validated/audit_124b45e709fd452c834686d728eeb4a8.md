### Title
Permissionless, unbounded growth of `DelegatedResourceAccountIndex` via low-cost `FreezeBalanceContract` delegation enables DoS of resource-delegation index reads - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator` allows any account to freeze as little as 1 TRX and delegate the resulting bandwidth/energy to an arbitrary `receiverAddress` it does not control. In the legacy (`!supportAllowDelegateOptimization()`) code path, this permissionless action appends the receiver's address to the caller's own index and — critically — appends the caller's address into the **receiver's** `DelegatedResourceAccountIndexCapsule` (`fromAccounts`/`toAccounts` lists) with no upper bound and no opt-in from the receiver.

### Finding Description
`delegateResource()` in `FreezeBalanceActuator` unconditionally reads, mutates, and re-serializes the full `DelegatedResourceAccountIndexCapsule` for both the owner and the receiver: [1](#0-0) 
The receiver has no way to prevent being targeted — `validate()` only checks that the receiver account exists and is not a contract, not that it consents: [2](#0-1) 
The economic barrier is negligible: only `frozenBalance >= 1 TRX` is required, and freezing is fully refundable after the frozen period expires: [3](#0-2) 
`DelegatedResourceAccountIndexCapsule.addFromAccount`/`addToAccount` append without any size limit: [4](#0-3) 
An attacker can create many distinct owner wallets (or reuse one and freeze repeatedly for the `TRON_POWER`/other resource paths, or use many receivers), each freezing 1 TRX and delegating to the same victim receiver address, causing the receiver's single index record to grow unboundedly. Every subsequent read (`GetDelegatedResourceAccountIndex` RPC/HTTP, exposed in `Wallet.java`, `RpcApiService.java`, `GetDelegatedResourceAccountIndexServlet.java`) must deserialize the entire growing protobuf list, and every future delegate/undelegate operation touching that receiver must read-modify-write the whole capsule. This is directly analogous to the reported `VotingPowerProvider`/`KeyRegistry` issue: a permissionless, cheap, unbounded-array-appending function that DoSes downstream aggregation/view functions.

### Impact Explanation
This causes unbounded state growth attributable to a victim address that the victim did not choose to be associated with. Reads of that victim's delegated-resource index (`GetDelegatedResourceAccountIndex` and its Solidity/PBFT variants) become progressively more expensive/slow (RPC timeout risk) and the on-chain read/write cost for any future delegate/undelegate operation touching that account grows linearly with the number of spam entries, degrading availability of a public state-accounting API without proportional cost to the attacker. This matches the "underpriced-public-work" / invalid-state-growth impact class validated for this bug family.

### Likelihood Explanation
Likelihood is high for an attacker willing to pay the trivial 1 TRX minimum freeze fee repeatedly across many created accounts (account creation itself is cheap) or against a single high-value receiver address (e.g., an exchange or witness) to grind its `DelegatedResourceAccountIndex` into an unusably large record. No special privileges are required — this is reachable by any funded account.

### Recommendation
Add pagination to `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` reads, and/or cap the number of entries permitted in a single `DelegatedResourceAccountIndexCapsule`, and/or require receiver consent (or use only the V2, prefix-indexed per-pair storage instead of a single growing list) for the legacy delegation index path.

### Proof of Concept
Not executed (analysis based on static code review only). Conceptually: repeatedly submit `FreezeBalanceContract{ frozenBalance = 1 TRX, receiverAddress = victim, resource = BANDWIDTH }` from many distinct funded owner addresses, then observe `GetDelegatedResourceAccountIndex(victim)` response size/latency grow unbounded.

Note: I was not able to independently confirm inside `Wallet.java` the exact line where `getDelegatedResourceAccountIndex` is implemented (the grep for that identifier in `Wallet.java` returned no matches despite other files referencing `wallet.getDelegatedResourceAccountIndex(...)`), so the precise read-path implementation in `Wallet.java` should be verified further; this does not affect the root-cause finding in `FreezeBalanceActuator`/`DelegatedResourceAccountIndexCapsule`, which is confirmed directly from source.
