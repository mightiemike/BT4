### Title
`InitializeBuffer` Sets Buffer Authority Without Requiring The Authority To Sign, Enabling Front-Run Takeover - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The `bpf_loader_upgradeable` builtin's `InitializeBuffer` instruction handler sets the `authority_address` of a newly created (but still `Uninitialized`) buffer account to whatever pubkey is passed as instruction account index 1, without requiring that account to be a signer of the transaction. This mirrors the reported `CSFeeOracle.initialize()` class of bug — a state-setting "initialize" entrypoint that lacks access control and is therefore front-runnable by any unprivileged actor who can observe the target account's public key before the legitimate initialization transaction lands.

### Finding Description
`process_loader_upgradeable_instruction` handles `UpgradeableLoaderInstruction::InitializeBuffer` as follows: [1](#0-0) 

The only precondition checked is that the buffer account's state is `UpgradeableLoaderState::Uninitialized`; the pubkey supplied as the "authority" account (instruction account index 1) is read and stored as the buffer's `authority_address` with **no `is_instruction_account_signer` check**. By contrast, every subsequent instruction that mutates the buffer (`Write`) does correctly require the stored authority to sign: [2](#0-1) 

The buffer account itself is created via a separate `system_instruction::create_account` call (the buffer pubkey must sign that instruction), and tooling such as `solana_loader_v3_interface::instruction::create_buffer` bundles `CreateAccount` + `InitializeBuffer` into a single message intended to be submitted atomically: [3](#0-2) 

However, nothing in the runtime enforces that these two instructions must be submitted together. `CreateAccount` and `InitializeBuffer` are independent, ordinary instructions reachable from any client. Once the `CreateAccount` transaction for a buffer is broadcast (and its target pubkey is thereby publicly known, e.g., from mempool/gossip or from the confirmed transaction itself, before the legitimate deployer's own `InitializeBuffer` transaction lands), any unprivileged attacker can race a competing transaction that invokes `InitializeBuffer` on that same buffer account with **any pubkey of the attacker's choosing** as the authority — no signature from the true intended authority is required.

### Impact Explanation
If the attacker's `InitializeBuffer` transaction confirms first, the buffer transitions from `Uninitialized` to `Buffer { authority_address: Some(attacker_pubkey) }`. The legitimate deployer's own `InitializeBuffer` call will then fail with `AccountAlreadyInitialized`, and any subsequent `Write`/`DeployWithMaxDataLen` calls the legitimate party attempts against that buffer will fail with `IncorrectAuthority`/`MissingRequiredSignature`, permanently locking out the intended owner from the buffer account they paid rent to create. The attacker, now holding the authority, can also write arbitrary bytecode into the buffer and control its future disposition (e.g. closing it), since all further access-control decisions for the account are keyed off the attacker-supplied `authority_address` set during this unauthenticated initialization. This is a concrete, reachable privilege-hijack of an account whose rent was funded by an unprivileged victim, directly analogous to the reported "front-runnable, access-control-free `initialize()`" bug class.

### Likelihood Explanation
Exploitation requires only the ability to observe a pending or newly-created buffer account's pubkey and to submit a competing transaction naming that pubkey with `InitializeBuffer` before the legitimate follow-up transaction confirms — no special privileges, validator access, or non-standard transaction crafting are needed. This is realistically triggerable by any unprivileged client racing ordinary `solana program deploy`/`upgrade` workflows.

### Recommendation
Require the account supplied as the buffer authority in `InitializeBuffer` to be a signer of the instruction (mirroring the check already present in the `Write` handler), or require that `InitializeBuffer` be atomically bundled with the `CreateAccount` instruction and validated as such, so an unauthenticated third party cannot claim authority over a buffer account it did not create.

### Proof of Concept
1. Victim submits `system_instruction::create_account(payer, buffer_pubkey, ..., owner = bpf_loader_upgradeable::id())` to create an `Uninitialized` buffer account (buffer_pubkey is now public).
2. Before the victim's paired `InitializeBuffer` (naming `victim_authority` as account index 1) confirms, attacker submits their own transaction: `InitializeBuffer` instruction with accounts `[buffer_pubkey (writable), attacker_pubkey (not required to sign)]`.
3. Per `process_loader_upgradeable_instruction` (lines 158–172), this succeeds because there is no signer check on account index 1; buffer state becomes `Buffer { authority_address: Some(attacker_pubkey) }`.
4. Victim's subsequent `InitializeBuffer`/`Write` calls against `buffer_pubkey` now fail (`AccountAlreadyInitialized` / `IncorrectAuthority`), confirming the attacker has hijacked control of an account the victim funded, exactly reproducing the "anyone can call initialize" front-running scenario from the external report.
