### Title
Insufficient/misconfigurable L1 finality window allows reorg-vulnerable L1→L2 message inclusion - (File: crates/apollo_l1_events_config/src/config.rs)

### Summary
The `L1EventsScraperConfig::finality` field controls how many L1 blocks the scraper waits before treating an L1 block (and the L1→L2 messages emitted in it) as safe to scrape and forward to the `L1EventsProvider`. Its code-level default is `0`, meaning the scraper would accept L1 events with zero confirmations if not explicitly overridden, mirroring the reported class of bug: a fixed/insufficiently-tailored confirmation depth that does not account for the target chain's actual reorg risk.

### Finding Description
`L1EventsScraperConfig` defines `finality: u64` and its `Default` impl sets it to `0`: [1](#0-0) 

There is no `#[validate(range(min = ...))]` or other lower-bound enforcement on `finality` (unlike `max_blocks_per_fetch`, which has `#[validate(range(min = 1))]`), so a value of `0` is accepted by config validation.

`fetch_start_block` and `fetch_events` both subtract `finality` from the latest observed L1 block number to determine the block up to which it is safe to scrape: [2](#0-1) [3](#0-2) 

With `finality = 0`, `latest_l1_block_number` is used unmodified as the scraping boundary — i.e., the scraper immediately treats the tip of the chain as final and scrapes L1→L2 messages from it. The scraper does have a reorg-detection guard (`assert_no_l1_reorgs`, `L1_MESSAGE_SCRAPER_REORG_DETECTED` metric, `L1EventsScraperError::L1ReorgDetected`) that checks whether the block hash it *previously* scraped from is still canonical on the next poll: [4](#0-3) 

However, this only detects a reorg *after the fact*, when the scraper's own `scrape_from_this_l1_block` head no longer matches the chain — it aborts the process (`return Err(e)` in `run()`), it does not retroactively undo an L1-derived message that has already been forwarded to the `L1EventsProvider` and potentially already included/committed in an L2 block before the reorg was detected. Deployment configs override the default to `10` blocks: [5](#0-4) 

but this is a fixed, environment-agnostic value applied uniformly regardless of which L1 base layer (or which specific chain/finality characteristics) the sequencer is deployed against, and the code-level default (`0`) provides no safety margin at all if any deployment path omits the override — exactly the class of issue in the report: a static confirmation count not tailored to the actual finality/reorg depth of the target chain.

### Impact Explanation
If `finality` is set too low (or left at the unsafe default of `0`) relative to the true reorg depth of the underlying L1/base layer, an L1→L2 message can be scraped and forwarded to the provider, become eligible for inclusion in a proposed L2 block, and be permanently committed to the Starknet state before the L1 block that emitted it is actually final. If that L1 block is later reorged out, the L2 chain has irreversibly executed a message that never canonically existed on L1 — an unauthorized L1-triggered state transition on L2 that cannot be rolled back, since Starknet blocks are final once committed. This is a concrete loss/integrity issue: unauthorized contract execution on L2 driven by a transient, non-final L1 event.

### Likelihood Explanation
Triggering requires only sending a normal L1→L2 message (available to any L1 message sender) around the time of a natural L1 reorg of depth greater than the configured `finality`. No malicious operator, validator, or protocol-level compromise is required — this is a standard chain-reorg scenario, the same threat model the original report addresses for VRF confirmations. Likelihood scales inversely with the configured `finality` value and is highest wherever `finality` is `0` (code default) or set too low for the deployed L1/base layer's actual reorg characteristics.

### Recommendation
Enforce a safe non-zero minimum for `finality` via config validation (e.g., `#[validate(range(min = ...))]`) rather than allowing `0` as the default/accepted value, and document/require operators to set `finality` based on the specific base layer's empirically observed reorg depth (analogous to Chainlink's per-chain confirmation guidance) rather than relying on a single hardcoded deployment value across all environments.

### Proof of Concept
1. Deploy (or misconfigure) an `L1EventsScraperConfig` with `finality` left at or set to `0` (the code default, and the value accepted by validation since no lower bound is enforced) — see `Default` impl at `crates/apollo_l1_events_config/src/config.rs:106-139`.
2. Send an L1→L2 message; it lands in the current L1 block tip.
3. `fetch_events` (`crates/apollo_l1_events/src/l1_scraper.rs:271-290`) treats the current tip (`finality = 0` subtracted) as final and forwards the event to the `L1EventsProvider` on the very next poll.
4. The L2 sequencer includes the corresponding L1 handler transaction in a block and commits it (per `crates/apollo_l1_events/tests/flow_test_finality.rs`, which demonstrates that with `finality = 3`, a message only becomes `Validated` after 3 additional blocks — showing the mechanism directly gates on this parameter).
5. If the L1 block reorganizes before the equivalent real finality is reached, the message is still permanently committed on L2 despite never being canonical on L1; `assert_no_l1_reorgs` only detects the divergence on the *next* scrape cycle and aborts the scraper — it does not revert the already-forwarded/committed message.

#[derive(Clone, Debug, Serialize, Deserialize, Validate, PartialEq)]
pub struct L1EventsScraperConfig {
    #[serde(deserialize_with = "deserialize_float_seconds_to_duration")]
    pub startup_rewind_time_seconds: Duration,
    #[validate(custom(function = "validate_ascii"))]
    pub chain_id: ChainId,
    pub finality: u64,
    #[serde(deserialize_with = "deserialize_float_seconds_to_duration")]
    pub polling_interval_seconds: Duration,
    pub set_provider_historic_height_to_l2_genesis: bool,
    #[serde(deserialize_with = "deserialize_float_seconds_to_duration")]
    pub l1_block_time_seconds: Duration,
    /// Maximum number of L1 blocks fetched per `events` (eth_getLogs) request. Caps the catch-up
    /// window so a large backlog is drained over successive polls instead of one unbounded
    /// request.
    #[validate(range(min = 1))]
    pub max_blocks_per_fetch: u64,
}

impl Default for L1EventsScraperConfig {
    fn default() -> Self {
        Self {
            startup_rewind_time_seconds: Duration::from_secs(60 * 60),
            chain_id: ChainId::Mainnet,
            finality: 0,
            polling_interval_seconds: Duration::from_secs(30),
            set_provider_historic_height_to_l2_genesis: false,
            l1_block_time_seconds: Duration::from_secs(12),
            // Conservative default: well under the common public-RPC eth_getLogs block-range caps
            // (~1k-10k) and the 1s base-layer timeout. Operators on permissive private RPCs may
            // raise it.
            max_blocks_per_fetch: 1000,
        }
    }

    /// Scrape recent events and send them to the L1 provider.
    pub async fn send_events_to_l1_events_provider(
        &mut self,
    ) -> L1EventsScraperResult<(), BaseLayerType> {
        if self.scrape_from_this_l1_block.is_none() {
            panic!(
                "Scraper initialization was skipped. Must provide a value for \
                 scrape_from_this_l1_block. Value is given by a call to fetch_start_block() in \
                 run(). Did you forget to call run()?"
            )
        }
        self.assert_no_l1_reorgs().await?;

        let (latest_l1_block, events) = self.fetch_events().await?;
        // TODO(guyn): remove these _every_n_ms because the polling interval is longer.
        trace!("scraped up to {latest_l1_block:?}");
        info_every_n_ms!(1_000, "scraped up to {latest_l1_block:?}");

        // Sending even if there are no events, to keep the flow as simple/debuggable as possible.
        // Perf hit is minimal, since the scraper is on the same machine as the provider (no
        // network). If this gets spammy, short-circuit on events.empty().
        let add_events_result = self.l1_events_provider_client.add_events(events).await;
        handle_client_error(add_events_result)?;

        L1_MESSAGE_SCRAPER_LATEST_SCRAPED_BLOCK.set_lossy(latest_l1_block.number);
        // Successfully scraped events up to latest l1 block.
        self.scrape_from_this_l1_block = Some(latest_l1_block);

        Ok(())
    }
