### Title
Reverted nested CALL/DELEGATECALL storage writes leak into parent repository via aliased `Storage` object when `ENERGY_LIMIT_HARD_FORK` is false - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
`RepositoryImpl.getStorage(byte[] address)` only deep-copies the parent's `Storage` object when `StorageUtils.getEnergyLimitHardFork()` is true; otherwise it hands the child repository the exact same `Storage` reference held by the parent's `storageCache`. Because `Storage.put()`/`getValue()` mutate `rowCache` in place on that shared object, any nested call that writes to storage corrupts the parent's view immediately — independent of whether the child ever calls `commit()` — so a subsequent REVERT/exception in the child does not undo the storage mutation in the parent.

### Finding Description
`RepositoryImpl.getStorage(byte[] address)` [1](#0-0)  retrieves the parent's `Storage` instance via `parent.getStorage(address)` and either deep-copies it (`new Storage(parentStorage)`) or assigns it directly (`storage = parentStorage`) based on `StorageUtils.getEnergyLimitHardFork()` [2](#0-1) . In the non-deep-copy branch, the returned `Storage` object is the identical Java object already stored in the parent's `storageCache` map (populated either at that call or from a previous lookup), and the child also inserts this same reference into its own `storageCache` via `getStorageInternal` [3](#0-2) .

`Storage.put()` and `Storage.getValue()` mutate the shared `rowCache` map directly on that object [4](#0-3) . Since both the parent's and child's `storageCache` entries point at the same `Storage` instance, any write performed through the child (e.g. via `putStorageValue`) is visible through the parent's own cache reference *immediately*, without going through `commitStorageCache`/`deposit.putStorage()` propagation at all.

The revert/rollback design in `Program.callToAddress` and `VMActuator.execute` assumes that a failed nested call's changes are discarded simply by never calling `deposit.commit()` on the child repository (only `internalTx.reject()` and `callResult.rejectInternalTransactions()` are invoked on failure) [5](#0-4) . That assumption only holds if the child repository's caches are private/copy-on-write relative to the parent. When `getEnergyLimitHardFork()` is false, this invariant is broken for `Storage`: the mutation already happened on the object the parent still references, so discarding the child's `storageCache` map (a different `HashMap`, but holding the same `Storage` object) does not undo anything.

### Impact Explanation
On any chain/test configuration where `ENERGY_LIMIT_HARD_FORK` is false (its default value in `CommonParameter` [6](#0-5)  until a dynamic-property-driven proposal activates it), a malicious contract can perform a `CALL`/`DELEGATECALL` to another (possibly attacker-controlled) contract that writes storage and then reverts (or throws). Under the shared-reference path, those storage writes persist into the outer transaction's committed state even though the inner call is nominally rolled back — violating atomicity of reverted state and causing silent, unauthorized state corruption of storage slots for the target contract. This can be leveraged to desynchronize on-chain accounting logic implemented via contract storage (allowances, counters, escrow states, etc.) that a contract expects to roll back on failure.

### Likelihood Explanation
Reaching the vulnerable branch does not require any privileged access — a normal transaction triggering a smart contract that makes an inner `CALL`/`DELEGATECALL` (as `Program.callToAddress` shows is a `deposit.getContractState().newRepositoryChild()`-based path reachable from ordinary contract execution) is sufficient. The only precondition is that `StorageUtils.getEnergyLimitHardFork()` returns false for the executing block/context — this is not attacker-toggleable per-transaction, but it is the default/initial value and remains false until the corresponding hard-fork proposal is activated network-wide, and there is an existing (currently `@Ignore`d) test, `StorageTest.testParentChild`, explicitly exercising this parent/child `Storage` sharing/copy semantic [7](#0-6) , indicating the divergent behavior is a known area of concern in the codebase.

### Recommendation
Remove the conditional branching on `StorageUtils.getEnergyLimitHardFork()` in `RepositoryImpl.getStorage` and always perform the deep copy (`new Storage(parentStorage)`) for child repositories, regardless of hard-fork state, so that nested repository levels never share a mutable `Storage` instance with their parent. Alternatively, if the shared-reference path must be retained for backward compatibility with historical/pre-fork blocks, ensure it is only used in code paths that cannot be reached during current or future block processing (i.e., confirm and enforce that `getEnergyLimitHardFork()` is permanently frozen `true` for all live/replayable chain contexts before allowing any transaction execution).

### Proof of Concept
```java
// Differential test in framework/src/test/java/org/tron/common/runtime/vm/StorageTest.java style
@Test
public void nestedRevertStorageLeakDifferentialTest() throws Exception {
  byte[] address = Hex.decode(OWNER_ADDRESS);
  DataWord key = new DataWord("k".getBytes());
  DataWord originalVal = new DataWord("orig".getBytes());
  DataWord mutatedVal = new DataWord("mutated".getBytes());

  for (boolean hardFork : new boolean[]{false, true}) {
    CommonParameter.setENERGY_LIMIT_HARD_FORK(hardFork);

    Repository root = RepositoryImpl.createRoot(StoreFactory.getInstance());
    root.putStorageValue(address, key, originalVal);
    root.commit();

    Repository root2 = RepositoryImpl.createRoot(StoreFactory.getInstance());
    Repository child = root2.newRepositoryChild();

    // trigger read to force getStorage() sharing/copy decision
    child.getStorageValue(address, key);
    // simulate nested call mutating storage then reverting
    child.putStorageValue(address, key, mutatedVal);
    // simulate revert: child is discarded, NOT committed
    // (no child.commit() call, mimicking Program.callToAddress on revert)

    DataWord parentViewAfterRevert = root2.getStorageValue(address, key);

    if (hardFork) {
      Assert.assertEquals("deep-copy: parent must be unaffected by reverted child",
          originalVal, parentViewAfterRevert);
    } else {
      // demonstrates the bug: shared reference leaks mutation despite "revert"
      Assert.assertEquals("aliasing bug: mutated value leaked into parent despite no commit",
          mutatedVal, parentViewAfterRevert);
    }
  }
  CommonParameter.setENERGY_LIMIT_HARD_FORK(false);
}
```
Expected result confirming the bug: with `hardFork=false`, `root2.getStorageValue` returns `mutatedVal` even though `child.commit()` was never invoked, proving the reverted child's write leaked into the parent's committed-visible state — divergent from the `hardFork=true` deep-copy behavior, which correctly isolates it.
