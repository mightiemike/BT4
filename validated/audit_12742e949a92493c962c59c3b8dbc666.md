### Title
Missing `orderStore.put()` for the maker order after a dust-remainder "sell-token return" branch leaves stale ACTIVE order data, enabling double-crediting via `MarketCancelOrderContract` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder()` has an early-return branch (the "taker > maker, dust amount" case) that mutates the maker's `MarketOrderCapsule` in memory (marks it `INACTIVE`, zeroes its remaining sell quantity, credits the return amount to the owner's balance) and removes it from the account's active-order list, but returns before the `orderStore.put(makerOrderCapsule...)` call that persists the final state. The stale, still-`ACTIVE` order record with its original non-zero `sellTokenQuantityRemain` is left in `MarketOrderStore`. This is directly analogous to the DittoETH bug where a partially-filled position is left without its authoritative market-side record updated, allowing later privileged actions (cancel/exit) against inconsistent state.

### Finding Description
In `matchSingleOrder()` (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:453-483`), when `takerBuyTokenQuantityRemain > makerOrderCapsule.getSellTokenQuantityRemain()` ("taker > maker"), the code computes `makerBuyTokenQuantityReceive`. If it is `0` (dust too small to fill): [1](#0-0) 
it calls `MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore)` (which persists removal from the owner's active-order list in `MarketAccountStore`), then `makerOrderCapsule.setSellTokenQuantityReturn()` and `returnSellTokenRemain(makerOrderCapsule)` (which credits the owner's balance/asset and sets `sellTokenQuantityRemain = 0` in the in-memory capsule), and then `return`s.

Because the method returns here, execution never reaches: [2](#0-1) 
which is the only line that writes the maker's updated `MarketOrderCapsule` back into `MarketOrderStore`. Consequently `orderStore` still contains the pre-match version of the maker order: `State.ACTIVE`, the original non-zero `sellTokenQuantityRemain`, and `sellTokenQuantityReturn = 0`.

The order-book bookkeeping in the caller, `matchOrder()`, only removes the order from the price-level list (`pairPriceToOrderStore`) using the in-memory (mutated) object reference: [3](#0-2) 
so the order disappears from the order book and from the owner's active-order list in `MarketAccountStore`, but the canonical `orderStore` entry is never corrected.

`MarketCancelOrderActuator.validate()` and `execute()` read the order purely from `orderStore`: [4](#0-3) 
Since the stale record still shows `State.ACTIVE`, `marketOrderCapsule.isActive()` passes validation. `execute()` then calls `MarketUtils.returnSellTokenRemain(...)` again using the stale, non-zero `sellTokenQuantityRemain`: [5](#0-4) 
crediting the owner's balance/asset a second time for tokens that were already returned once inside the earlier `matchSingleOrder` dust branch, before it attempts to locate the (already-deleted) `pairPriceToOrderStore` entry for that order's price key.

### Impact Explanation
This is an unprivileged, RPC-reachable accounting-corruption bug: any user who places a `MarketSellAssetContract` order that becomes a "maker" in a trade where the taker's fill leaves the maker a residual amount too small to produce a non-zero `makerBuyTokenQuantityReceive` will end up with a stale `ACTIVE` order record. That user can then broadcast `MarketCancelOrderContract` for the same order ID, causing `returnSellTokenRemain` to run a second time and double-credit the account's TRX balance or TRC10 asset balance for the sell-token remainder — a direct asset/accounting corruption reachable purely through ordinary broadcast transactions, matching the report's bug class (partial-fill state not consistently finalized, enabling later state-dependent actions to misbehave).

### Likelihood Explanation
The dust-fill branch (`makerBuyTokenQuantityReceive == 0`) is explicitly discussed in the code's own comments as a real, reachable scenario ("it needs to be satisfied the following conditions... and this comports with the fact that X is integer"), i.e., it is not a theoretical dead branch — any user can construct sell/buy quantities that trigger it deterministically. The double-credit path additionally depends on whether the later `pairPriceToOrderStore.get(pairPriceKey)` call in `MarketCancelOrderActuator` throws `ItemNotFoundException` before or after the state/balance writes are already applied to the store; the account-balance and order-state writes execute before that lookup, so likelihood of the accounting inconsistency being persisted is high, though full confirmation of transaction-level atomicity/rollback semantics in java-tron's actuator execution pipeline would require deeper engine-level verification.

### Recommendation
In the dust branch of `matchSingleOrder()`, persist the maker order's final state before returning, e.g. call `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule)` immediately after `returnSellTokenRemain(makerOrderCapsule)` and before the early `return`, mirroring the persistence done at line 486 for the normal path. Additionally, `MarketCancelOrderActuator` should defensively re-validate that `sellTokenQuantityRemain > 0` and that the order still exists in `pairPriceToOrderStore` before crediting tokens, to guard against any other code paths that leave inconsistent `orderStore` records.

### Proof of Concept
1. Create maker sell order A: sell 200 unit T for 100 TRX (`sellTokenQuantity=200, buyTokenQuantity=100`).
2. Let the maker order be partially filled down to `sellTokenQuantityRemain = 1` by prior trades (per the code's own comment, achievable with `sellQuantity=200, buyQuantity=100`, when `sellRemain=1`).
3. Submit a taker `MarketSellAssetContract` whose computed `takerBuyTokenQuantityRemain` exceeds the maker's remaining sell amount such that `makerBuyTokenQuantityReceive` computes to `0` (per the arithmetic comment, `X = 199/2` is not integer, forcing this exact edge case is reachable by choosing quantities that satisfy the integer-division floor to zero).
4. `matchSingleOrder` executes the dust branch: sets maker order `INACTIVE`, removes it from `MarketAccountStore`, credits the maker's balance/asset for the returned `sellTokenQuantityRemain`, and returns — `orderStore` for order A retains stale `State.ACTIVE`, `sellTokenQuantityRemain=1` (or original value), `sellTokenQuantityReturn=0`.
5. Maker broadcasts `MarketCancelOrderContract` with order A's ID. `validate()` reads the stale record, `isActive()` is `true`, validation passes.
6. `execute()` calls `returnSellTokenRemain` again, crediting the maker's balance/asset a second time for the same remainder, then sets state `CANCELED` and persists — the double credit is committed to `AccountStore` before the subsequent `pairPriceToOrderStore.get()` call (which may throw since the price-key list was already deleted), so the asset/TRX double-credit is not visibly guarded against.
