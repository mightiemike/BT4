### Title
Replay-verify comparator ignores state/hot-state/position checkpoint hashes, allowing silent state-root divergence to pass verification - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay-verify tooling (db-tool's `replay_on_archive`, the chunk executor's `verify_execution`, and the Aptos debugger) to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` pulled from backups/archive. This is conceptually the same "silent-divergence" bug class as the zAuction report: an authoritative reference (the accumulator-proven `TransactionInfo`) can diverge from what is actually being accepted/served (the locally computed state), and the code path that should catch such divergence explicitly skips it.

### Finding Description
`ensure_match_transaction_info` checks status, gas used, write-set hash (`state_change_hash`), and event root hash against the authenticated `TransactionInfo`, but it explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`: [1](#0-0) 

The comment in the code itself documents the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution.
```

This function is invoked as the sole per-transaction correctness check in:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which drives backup replay-verification (`VerifyExecutionMode::Verify`) used by `storage/backup/backup-cli` and `storage/db-tool`: [2](#0-1) 
- `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`, both of which exist specifically to detect state-computation regressions before they reach mainnet.

The `state_checkpoint_hash` fields being skipped are exactly the state-merkle-root commitments produced during ledger update, computed in `assemble_transaction_infos`: [3](#0-2) 

These checkpoint hashes are also part of the hashed `TransactionInfo` that is bound into the transaction accumulator and thus into ledger-info signatures — meaning a genuine divergence here corresponds directly to "wrong state proof / wrong accumulator leaf content," the exact class of impact this scan is meant to surface.

### Impact Explanation
If the state-computation logic that produces `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` (i.e., the JMT/hot-state root logic) contains a non-consensus-breaking bug — for example under the newer `hot_state_root_in_txn_info` / `compute_trading_native_state_roots` feature paths — replay-verify tooling that is supposed to catch exactly such divergence will report success even though the locally recomputed state root differs from the one that was actually committed and authenticated by validator signatures. This undermines the guarantee that replay/restore tooling can be trusted to detect ledger-state corruption, which is one of the explicitly in-scope impacts ("hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated API or state-view output bound to the wrong version, object, or proof context"). Because these state roots feed into state proofs served over the authenticated API (`get_state_proof_by_version_ext`, `get_state_value_with_proof_by_version_ext`), an undetected divergence could propagate into clients trusting proofs anchored to a corrupted state root without replay tooling ever raising an alarm.

### Likelihood Explanation
This is not exploitable by an external attacker directly — it requires an actual bug in the state-checkpoint-hash computation path (e.g. hot-state or "trading-native" state root logic, both recently introduced feature-gated code) to exist simultaneously with someone relying on `replay_on_archive`/chunk-executor verification to catch such a bug. The likelihood is therefore tied to how much protection operators expect from replay-verify: the TODO comment shows the aptos-core team is aware this comparator is incomplete, meaning today it provides a false sense of security for the checkpoint-hash-related invariants specifically, even though it correctly catches write-set/event/gas/status divergence.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed transaction info and the authenticated one, as the existing TODO already suggests, before broadly enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / hot-state-in-txn-info features. Alternatively, until that check is added, replay-verify tooling documentation/output should clearly flag that checkpoint-hash divergence is not detected, so operators do not treat a "successful replay" as proof of full state-root correctness.

### Proof of Concept
Not applicable as an externally triggerable exploit — this is a code-level verification gap, demonstrated by the existing TODO and control flow:
1. `assemble_transaction_infos` computes `state_checkpoint_hash` (and the two other checkpoint hashes when enabled) as part of building each committed `TransactionInfo`. [4](#0-3) 
2. During replay-verify, `verify_execution` calls `ensure_match_transaction_info(version, txn_info, ...)` on freshly re-executed output vs. the authenticated `txn_info` pulled from backup. [5](#0-4) 
3. `ensure_match_transaction_info` never reads or compares `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, so any mismatch there — however produced — cannot cause `verify_execution` to fail. [6](#0-5) 

I was not able to fully trace whether `hot_state_root_in_txn_info` / `compute_trading_native_state_roots` are currently enabled on mainnet or still gated off; that determines the immediate real-world severity, but the code path itself is present and reachable via db-tool/backup-cli today.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
