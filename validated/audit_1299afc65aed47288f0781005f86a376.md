### Title
Cross-network method-id upgrade replay between `Network::Nightly` and `Network::TestNetworkWithForks` due to shared `chain_id` and shared default council keys - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the identical value `5665`, and `run_l1_block`'s replay guard only checks `circuit_chain_id == batch_proof_method_id.body.chain_id` with no additional per-network domain separator. Because the default (unset-env-var) `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` constants for Nightly and TestNetworkWithForks are also byte-for-byte identical, a `BatchProofMethodId` blob signed by the council for one of these two networks is a valid, fully-verifying blob for the other if both instances read the same DA blob.

### Finding Description
The binding the code is supposed to enforce is:
`body.chain_id == citrea_network_to_chain_id(network_instance_processing_this_blob)` uniquely identifies the network the signers intended.

In practice this reduces to `citrea_network_to_chain_id(Nightly) == citrea_network_to_chain_id(TestNetworkWithForks) == 5665` [1](#0-0) , so the equality holds for *both* networks simultaneously for the same signed body, defeating the very purpose stated in the doc comment ("to prevent cross network replay attacks").

The check site in `run_l1_block` only compares the chain id and then verifies the council signatures against `method_id_upgrade_authority_da_public_keys` supplied by the caller for that network instance: [2](#0-1) 

The default constants (used whenever the corresponding `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` env vars are not set at compile time) are identical between Nightly and TestNetworkWithForks: [3](#0-2) [4](#0-3) 

Given both preconditions (shared chain_id 5665, shared default pubkeys), an attacker who observes a genuine council-signed `BatchProofMethodId` blob broadcast for a Nightly instance can copy the identical bytes (`body` + `signatures_with_index`) unchanged and inscribe them into a Bitcoin transaction read by a TestNetworkWithForks light-client instance (or vice versa), sharing the same DA layer. Since `body.chain_id` was fixed at signing time to `5665` for both networks, and `verify_method_id_security_council` is a pure signature check against the same 5 pubkeys, the second network's `run_l1_block` will accept the exact same blob as a valid council-approved upgrade for itself, at whatever `activation_l2_height` the body specifies (subject only to the "must be greater than last activation height" monotonic check, which is per-network state and thus does not prevent the replay).

The activation-height/last-height check does not stop this because it is network-local state, not a signer/network binding; the only intended anti-replay mechanism is the chain-id equality, which is broken by the shared constant `5665`.

### Impact Explanation
If deployed with default keys, this allows an unauthorised method-id upgrade to be inserted into one network's `BatchProofMethodIdAccessor` using a signature/body that the council only intended for the other network. This matches the Critical category "a sequencer commitment or method-id upgrade accepted that was never authorised" — a method-id upgrade changes which batch-proof RISC0/SP1 ELF is trusted for future proof verification, meaning an attacker (or the shared-key operator's mistake) can cause one network to trust a batch-proof method id intended only for the sibling network, corrupting state-transition verification for all subsequent batch proofs on that network. This is repeatable for every future method-id upgrade broadcast as long as the deployment keeps chain-id and keys shared, and it affects every full node / light-client-prover instance following the affected network.

### Likelihood Explanation
Exploitability strictly depends on operational configuration: it only manifests if a deployer actually runs both `Nightly` and `TestNetworkWithForks` light-client instances against the same Bitcoin DA chain **and** leaves the `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` env vars unset for both (so both fall back to the identical hardcoded defaults). `TestNetworkWithForks` is explicitly documented as "used for testing purposes only," so whether it is ever deployed in a shared-DA, shared-default-key configuration alongside Nightly in a real environment is uncertain and could not be confirmed from the repo alone. The attacker's action itself (re-inscribing already-public blob bytes into a new Bitcoin transaction) is cheap and unprivileged — it costs only Bitcoin inscription fees, requires no signing key, and is trivially repeatable for any observed council broadcast.

### Recommendation
Assign `TestNetworkWithForks` a distinct chain id (currently duplicated with `Nightly` at `5665`) in `citrea_network_to_chain_id`, and/or mandate that the two networks never share identical `method_id_upgrade_authority_da_public_keys` in any deployment (fail-fast assertion if they match at startup when both networks are active against the same DA key set).

```rust
// crates/light-client-prover/src/circuit/method_id_verifier.rs (new test)
#[test]
fn test_cross_network_chain_id_collision() {
    use crate::circuit::citrea_network_to_chain_id;
    use sov_rollup_interface::Network;

    // Binding under test: chain ids must uniquely identify the network.
    let nightly_id = citrea_network_to_chain_id(Network::Nightly);
    let twf_id = citrea_network_to_chain_id(Network::TestNetworkWithForks);

    // This currently PASSES, demonstrating the collision (should be an inequality).
    assert_eq!(nightly_id, twf_id, "chain ids collide: {} == {}", nightly_id, twf_id);

    // Given the same body.chain_id (5665) and default upgrade-authority keys shared
    // between the two networks (see initial_values.rs Nightly vs TestNetworkWithForks
    // default constants), a BatchProofMethodIdBody signed once passes
    // run_l1_block's `circuit_chain_id != body.chain_id` guard identically for both
    // networks, and verify_method_id_security_council succeeds identically for both
    // sets of default pubkeys, confirming the replay is accepted on both.
}
```
This proves the equality `citrea_network_to_chain_id(Nightly) == citrea_network_to_chain_id(TestNetworkWithForks)` holds, which is the exact condition the question asked to validate; combined with the identical default pubkey constants shown in `initial_values.rs`, a signed body for one network passes verification unmodified for the other.

pub fn citrea_network_to_chain_id(network: sov_rollup_interface::Network) -> u64 {
    match network {
        sov_rollup_interface::Network::Mainnet => 4114,
        sov_rollup_interface::Network::Testnet => 5115,
        sov_rollup_interface::Network::Devnet => 62298,
        sov_rollup_interface::Network::Nightly => 5665,
        sov_rollup_interface::Network::TestNetworkWithForks => 5665,
    }
}
