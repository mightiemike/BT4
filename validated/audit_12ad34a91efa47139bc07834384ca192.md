## Title
Panic-based DoS via unchecked empty calldata in `l1_handler_message_hash` - (File: crates/starknet_api/src/hash.rs)

### Summary
This is the same bug class as CVE-2023-52678: code assumes a collection is non-empty and calls a "get first element" accessor without validating emptiness first, causing a panic/crash instead of a graceful error. In `sequencer--006`, `l1_handler_message_hash` in `crates/starknet_api/src/hash.rs` calls `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")`, which panics if `calldata` is empty.

### Finding Description
`l1_handler_message_hash` computes the L1↔L2 message hash for an `L1HandlerTransaction`: [1](#0-0) 

It unconditionally does:
```
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
```
If `calldata.0` is empty, `split_first()` returns `None` and `.expect(...)` panics. This mirrors the kernel bug: `list_first_entry`/first-element access without an explicit non-empty check first.

`L1HandlerTransaction::calc_msg_hash` calls this directly: [2](#0-1) 

I was unable to fully trace, within the available tool budget, whether the sequencer's L1-handler ingestion path (`apollo_l1_events` / `apollo_l1_scraper` or the RPC layer in `apollo_rpc/src/v0_8/api/api_impl.rs`, both of which reference `calc_msg_hash`/`l1_handler_message_hash`) enforces non-empty calldata *before* this function is reached. Starknet's protocol convention requires the L1 handler's first calldata element to be the L1 `from_address`, and this is normally guaranteed by the L1 core contract / the scraper that constructs the calldata. If, however, any code path constructs or accepts an `L1HandlerTransaction` with attacker-influenced or malformed empty calldata (e.g. a permissionless-relay or malformed-event path) and then calls `calc_msg_hash`/`l1_handler_message_hash` before or without validating calldata length elsewhere, this becomes a reachable panic.

### Impact Explanation
A panic in transaction-hash computation reachable from processing an L1 message (or a malformed L1 event) can crash the process, causing denial of service — "a network unable to confirm new transactions" if this code path executes during normal sequencer block-building/L1 message consumption. This matches the accepted severity bar (network availability impact) if the path is indeed reachable without operator/validator privilege.

### Likelihood Explanation
Likelihood is uncertain and NOT confirmed here: this function's only confirmed uses are in `apollo_rpc` (read-path, presumably formatting already-validated on-chain transactions) and `apollo_l1_events`/`apollo_l1_scraper` (L1 event ingestion). Whether the scraper/OS/mempool path can encounter empty calldata for a real (or forged) L1-to-L2 message before this hash is computed — as opposed to it always being called on already-well-formed data sourced from L1 contract logs — could not be confirmed with the tools available. Without confirming an attacker-reachable empty-calldata input to this function, I cannot assert this rises to a validated, exploitable vulnerability in the sequencer as opposed to an internal invariant that's actually always upheld upstream.

### Recommendation
Regardless of current reachability, harden `l1_handler_message_hash` to return a proper `Result`/error instead of panicking when `calldata.0` is empty, consistent with how other parts of the codebase (e.g., `stateless_transaction_validator.rs`) reject malformed transactions with typed errors rather than panics.

### Proof of Concept
Not fully constructible without confirming the exact caller reachability from an untrusted L1 message; conceptually: constructing/ingesting an `L1HandlerTransaction` with `calldata = Calldata(vec![].into())` and calling `.calc_msg_hash()` will panic: [3](#0-2) 

**Caveat**: Given the uncertainty in confirming attacker-reachability of empty calldata into this function through the sequencer's actual L1-handler ingestion pipeline, I recommend treating this as a **candidate, not a confirmed** finding. Due to index size limits, I could not view the full contents of `apollo_l1_events/src/l1_events_provider.rs`, `apollo_l1_events/src/l1_scraper.rs`, and `apollo_rpc/src/v0_8/api/api_impl.rs` to confirm whether calldata is validated as non-empty before these call sites — a Devin session with full repository access would be needed to trace this conclusively.
