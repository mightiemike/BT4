## Title
L1-handler transactions with insufficient L1-paid fee are marked "consumed" and permanently dropped even though execution effects were already committed, with no operator recourse to retry - ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs])

## Summary
This is a Starknet-specific analog of the Ondo "even admin has no control over locked funds" bug class: an unconditional, unbypassable check embedded deep in transaction execution (analogous to `checkKYC()`/`_checkAddressesKYC()`) causes the L1→L2 message to be treated as processed forever, with no path — not even by a trusted sequencer/operator action — to retry or make the user whole, while the state effects of running the message have already been merged into the parent state.

## Finding Description
`L1HandlerTransaction::execute_raw` in `crates/blockifier/src/transaction/l1_handler_transaction.rs` executes the L1-handler payload against a `TransactionalState`, and only *after* calling `execution_state.commit()` does it check whether any fee was actually paid on L1: [1](#0-0) 

If `paid_fee_on_l1 == Fee(0)`, the function returns `Err(TransactionExecutionError::TransactionFeeError(...))` — but this happens strictly *after* `execution_state.commit()` on line 100, i.e. after the entry-point's storage writes and the L1→L2 message consumption (`consume_l1_to_l2_message`, invoked inside `run_execute`) have already been folded into `state`.

At the batcher level, `collect_execution_results_and_stream_txs` in `crates/apollo_batcher/src/block_builder.rs` unconditionally inserts the L1-handler's tx hash into `consumed_l1_handler_tx_hashes` *before* looking at whether the executor returned `Ok` or `Err`: [2](#0-1) 

An `Err` result (as opposed to an in-band revert, i.e. `Ok(execution_info_with_revert_error)`) additionally routes the tx hash into `rejected_tx_hashes`: [3](#0-2) 

So for the "insufficient fee" code path (which is the exact real-world scenario for any L1 handler where the L1 contract's declared/attached fee is `0`, an edge case the code explicitly still checks for as "covered by the starknet core contract" per the inline `TODO`), the transaction hash is *simultaneously* placed in both `consumed_l1_handler_tx_hashes` and `rejected_tx_hashes`. Documentation of the intended flow (`docs/diagrams/06-l1-handler-flow.md`) describes the batcher "Filter[ing] rejected_l1_handler_tx_hashes" before commit, implying rejected transactions are supposed to be excluded from the consumed set and kept `Pending` for a future retry: [4](#0-3) 

I was not able to fully verify, within available tool budget, the exact code that performs this "filter rejected_l1_handler_tx_hashes" step and confirm whether it correctly excludes transactions that are in *both* sets (consumed-and-rejected) before calling `commit_block`/`apply_commit_block` in `apollo_batcher/src/batcher.rs` and `apollo_l1_events/src/l1_events_provider.rs`. This is the crux of the bug: if the filter only subtracts "purely rejected" hashes and doesn't handle the dual-membership case (a legitimate `Err` executor result still nonetheless gets `consumed_l1_handler_tx_hashes.insert()`'d unconditionally), the L1 message would be reported to the `TransactionManager`/`L1EventsProvider` as `consumed`, which per `crates/apollo_l1_events/src/l1_events_provider_tests.rs` permanently deletes the record from `records` (asserted via `consuming_consumed_tx_panics`). Once deleted, the L1-originated deposit/message can never be retried on L2, and there is no operator/admin mechanism (analogous to `MANAGER_ADMIN`) to force redelivery — the funds/message effects are permanently lost, mirroring the "even admin has no control over it" finding from the CashManager report.

Separately, even if the filtering logic is later shown to correctly exclude this case from `consumed`, the fact that `execution_state.commit()` happens *before* the fee-sufficiency guard means state effects (storage writes, event emission, message-consumption side effects performed inside `run_execute`) are applied to the parent transactional `state` prior to the function returning an error — an ordering issue that risks inconsistent state commitment independent of the L1 event bookkeeping question above.

## Impact Explanation
If the dual-membership scenario is not correctly filtered, an L1-handler message that is legitimately paid `Fee(0)` on L1 (or is otherwise flagged with `InsufficientFee`) is irrevocably marked "consumed" in the `TransactionManager`, permanently freezing the corresponding L1→L2 message/funds with no path to re-submission — a permanent freezing-of-funds outcome reachable from a single L1 message, matching the "Medium/High, permanent freezing of funds" impact bar for this analog scan. It would also risk state-commitment divergence if the commit-before-fee-check ordering causes effects to be applied inconsistently relative to how the tx is bookkept as rejected.

## Likelihood Explanation
Reachability requires only a single L1→L2 message (an unprivileged, permissionless action from any L1 sender) whose associated `paid_fee_on_l1` is zero or otherwise fails the post-execution fee check — this is explicitly anticipated by the existing code comment ("For now, assert only that any amount of fee was paid") and covered by existing negative-flow unit tests (`crates/blockifier/src/transaction/transactions_test.rs:2940-2962`), confirming this is a reachable, tested code path rather than a purely theoretical one.

## Recommendation
1. Move the `paid_fee_on_l1 == Fee(0)` check (and any other conditions that can cause `execute_raw` to return `Err`) to *before* `execution_state.commit()`, so no state effects are committed when the transaction is going to be treated as rejected/failed.
2. Audit `apollo_batcher::block_builder` and `apollo_batcher::batcher` to guarantee that any L1-handler tx hash present in `rejected_tx_hashes` is excluded from `consumed_l1_handler_tx_hashes` before `commit_block` is called, so that a rejected L1-handler message remains `Pending` in the `TransactionManager` and can be retried in a future block, rather than being permanently deleted as "consumed."
3. Add an explicit regression test exercising the "L1 handler with `Fee(0)` / insufficient fee returns `Err`" path end-to-end through `collect_execution_results_and_stream_txs` and `commit_block`, asserting the transaction is retryable (remains `Pending`) and not silently dropped.

## Proof of Concept
1. Submit an L1→L2 message via the Starknet core contract's `sendMessageToL2` with `paid_fee_on_l1` effectively read as `Fee(0)` by the sequencer (or otherwise triggering `TransactionFeeError::InsufficientFee` post-execution).
2. The batcher scrapes and proposes this transaction; `L1HandlerTransaction::execute_raw` executes the handler, commits `execution_state` (line 100), then returns `Err(TransactionExecutionError::TransactionFeeError(...))` (lines 106-113).
3. In `collect_execution_results_and_stream_txs`, the tx hash is added to `consumed_l1_handler_tx_hashes` unconditionally (lines 644-649) and then also to `rejected_tx_hashes` because the executor result is `Err` (lines 707-716).
4. Trace whether `commit_block`/`apply_commit_block` in `apollo_batcher::batcher` and `apollo_l1_events::l1_events_provider` correctly strip this hash from the consumed set given its dual membership; if not, `TransactionManager::commit_txs` marks it `Committed`/deletes its record, and the L1 message can never be replayed, permanently losing the associated funds/effect with no admin override available (analogous to the CashManager finding).
