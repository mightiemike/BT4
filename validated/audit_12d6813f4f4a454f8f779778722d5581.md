Found: `receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs:874-878` calls `receiver_shard_id(&shard_layout).unwrap()` on every delayed receipt popped from state during `pop()` and `peek_iter()`. This is the direct analog to the CVE's `vc_cfgread` missing-null-check crash: a value derived from stored/attacker-influenced data is force-unwrapped without checking whether it is valid, and a failure there crashes/panics the process instead of returning an error.

### Title
Unwrap-triggered chunk-processing panic on stale delayed receipts after resharding - (File: runtime/runtime/src/congestion_control.rs)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally unwraps the result of `receipt.get_receipt().receiver_shard_id(&shard_layout)` [1](#0-0)  when popping (`pop`, called from every chunk application) and when iterating (`peek_iter`) the delayed receipt queue. If a delayed receipt's target account cannot be mapped to a shard in the *current* epoch's shard layout (e.g. because the layout has changed across a resharding boundary and the mapping fails or errors instead of returning a shard id), this `unwrap()` panics, which aborts the chunk-apply process — a transaction/receipt-triggered node crash rather than a graceful error.

### Finding Description
Delayed receipts persist in trie-backed state across chunk boundaries and across resharding events; `pop()` explicitly documents that "it's possible for a chunk to have delayed receipts that technically belong to the sibling shard before a resharding event" [2](#0-1) , meaning the whole reason `receipt_filter_fn` exists is to tolerate cross-shard delayed receipts after a shard split. However the filter first computes `receiver_shard_id(&shard_layout)` and unwraps it before doing the actual comparison. Any circumstance under which this call cannot resolve a shard for the receipt's receiver (as opposed to resolving to the *wrong but valid* shard) turns the recovery path itself into a panic. The codebase already contains a regression test, `test_stale_global_contract_distribution_after_double_resharding`, built specifically around a documented failure mode where "processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations" [3](#0-2) , confirming this exact call site is a known crash vector under multi-generation dynamic resharding.

`pop()` is invoked unconditionally by the runtime apply loop while draining the delayed-receipt backlog for every chunk (`process_receipts`, ordered local → delayed → incoming, per `protocol-model/spec/runtime-execution.md`), so any account whose delayed receipts hit this code path on a shard whose layout has since diverged reaches the vulnerable `unwrap()`.

### Impact Explanation
A panic inside chunk application is a chunk-producer/validator crash, not merely a rejected transaction: because the delayed queue is deterministic replicated state, every honest node applying the same chunk hits the identical panic, producing a synchronized, transaction/receipt-triggered halt of chunk processing for the affected shard. This matches the "transaction-triggered halt" acceptance criterion — an attacker only needs to get a receipt enqueued (e.g. via a global contract deployment or other action creating a receipt targeting an account) whose delayed processing crosses a resharding boundary and later fails to remap.

### Likelihood Explanation
Reaching this bug requires dynamic/multiple resharding events plus a delayed receipt that outlives them — a scenario the codebase's own test suite reproduces deliberately with `force_split_shards` across two sequential splits [4](#0-3) . This is dependent on network-level resharding configuration/timing rather than a single arbitrary transaction, so likelihood is moderate: it is deterministically reachable under dynamic resharding but not from a single isolated RPC call without that surrounding condition.

### Recommendation
Replace the `unwrap()` in `receipt_filter_fn` with a fallible path: propagate a `RuntimeError`/`StorageError` (or otherwise gracefully drop/re-route unresolvable stale receipts) instead of panicking, mirroring the `Result`-returning style already used elsewhere in `congestion_control.rs` (e.g. `IntegerOverflowError` handling). Ensure both `pop()` and `peek_iter()` callers handle the new error path without crashing the apply loop.

### Proof of Concept
1. Configure `DynamicReshardingConfig` with `force_split_shards` targeting two shards sequentially (as in the existing test) so a shard undergoes two resharding generations.
2. Submit a transaction/receipt (e.g. a global contract deployment, or any action that produces a receipt targeting an account on the shard about to be split) and saturate compute on that shard so the resulting receipt is pushed into the delayed-receipt queue and persists across both resharding events, per `push` [5](#0-4) .
3. Stop saturating and let the delayed queue drain; when `pop()` calls `receipt_filter_fn` on the stale receipt, `receiver_shard_id(&shard_layout).unwrap()` panics if the old target shard cannot be remapped through two layout generations, halting chunk application on all honest nodes, exactly as exercised by `test_stale_global_contract_distribution_after_double_resharding` [6](#0-5) .

    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
