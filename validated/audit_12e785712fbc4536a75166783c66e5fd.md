## Title
Super Representative can unilaterally set `brokerage` to 100% with no timelock, expropriating voters' pending rewards - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
`UpdateBrokerageContract`/`UpdateBrokerageActuator` lets any Super Representative (SR) — a role any TRX holder can obtain by freezing stake and being voted in, analogous to the permissionless "cred creator" role in the reference bug — change the percentage of block/vote rewards it keeps (`brokerage`, 0-100%) at any time, with no cooldown, no rate limit, and no advance-notice window for voters who have already delegated (voted) TRX to that SR.

### Finding Description
`UpdateBrokerageActuator.execute()` writes the new brokerage value directly into `DelegationStore` under the "current" key (`cycle = -1`) with a single bounds check `0 <= brokerage <= 100`: [1](#0-0) [2](#0-1) 

`DelegationStore.setBrokerage(address, brokerage)` stores this at the generic key, and `MaintenanceManager.doMaintenance()` (run every maintenance cycle, default 6 hours) simply copies this "current" value forward into the specific reward cycle used for reward accounting: [3](#0-2) [4](#0-3) 

`MortgageService.payReward()` then applies this brokerage ratio to split every block/standby reward between the SR (`brokerageAmount`) and the pool that is later distributed to voters, with no minimum share guaranteed to voters: [5](#0-4) 

There is no mechanism analogous to the recommended "request + delayed approval" pattern, and no way for a voter to react by un-voting before the change takes effect at the very next maintenance cycle — the only "delay" is the incidental maintenance interval, not a deliberate protection.

### Impact Explanation
Any SR (an unprivileged, permissionless, elected role — not a core admin/DAO role) can set `brokerage = 100` at any time. From the next maintenance cycle onward, all TRX holders who have voted for that SR receive `0` reward from that SR's blocks/standby pay, despite having frozen/delegated their TRX believing a lower (e.g. default 20%) or previously-set cut applied. This directly parallels the reference finding: an economically-motivated, quasi-trusted party unilaterally changing a fee/split parameter to the maximum allowed value, causing accounting loss to unprivileged users who cannot react in time, with no timelock protecting them.

### Likelihood Explanation
Likelihood is moderate-to-high: becoming an SR only requires enough votes/stake, `updateBrokerage` has no cooldown or notice period in `UpdateBrokerageActuator.validate()`, and the change is applied to voter rewards automatically at the next maintenance interval (as short as the configured `MAINTENANCE_TIME_INTERVAL`, default ~6h) with no opt-out for voters already delegated to that SR.

### Recommendation
Introduce a request/approval-with-delay pattern for `UpdateBrokerageContract` similar to the report's recommendation: require brokerage increases to be scheduled N cycles in advance (e.g., via a `pendingBrokerage` + `effectiveCycle` field validated in `UpdateBrokerageActuator`), giving voters a window to un-vote before the new, higher brokerage takes effect, and/or cap the maximum per-update delta.

### Proof of Concept
1. SR `S` is voted for by many token holders; `DelegationStore.getBrokerage(cycle, S)` currently returns the default `20`.
2. `S` submits `UpdateBrokerageContract{brokerage=100}` — `UpdateBrokerageActuator.validate()` only checks `0 <= brokerage <= 100`, no timelock, and `execute()` immediately calls `delegationStore.setBrokerage(S, 100)` (key cycle = -1).
3. At the next `doMaintenance()` run, `delegationStore.setBrokerage(nextCycle, S, delegationStore.getBrokerage(S))` copies `100` into the reward-cycle-specific slot.
4. From `nextCycle` onward, `MortgageService.payReward()` computes `brokerageAmount = value * 100/100 = value`, leaving `value -= brokerageAmount = 0` for `delegationStore.addReward(cycle, S, value)`.
5. Voters who already voted for `S` (via `VoteWitnessActuator`) and are still within the reward accrual window (`MortgageService.computeReward` / `withdrawReward`) receive `0` reward for that cycle onward, with no prior warning and no chance to un-vote before the change becomes binding.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
