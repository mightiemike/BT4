### Title
Missing overflow guard in ABI dynamic-offset arithmetic can panic the EVM inbound-event parser — ([File: universalClient/chains/evm/event_parser.go])

### Summary
`readDynamicBytes` in `universalClient/chains/evm/event_parser.go` computes `absOff+32` and `dataStart+byteLen` on attacker-influenceable `uint64` values without checked arithmetic, mirroring the Pico `Elf::new()` pattern (`offset + i + j` cast to `usize` without overflow checks). A crafted `dataOffset` near `math.MaxUint64` wraps the bounds check, after which slicing `data[absOff:absOff+32]` with a huge/overflowed index causes a Go runtime panic instead of a clean parse error.

### Finding Description
`parseUniversalTxEvent` reads a raw ABI "offset" word straight out of log data: [1](#0-0) 
and passes it into `decodePayload`/`readDynamicBytes`: [2](#0-1) 

`readDynamicBytes` guards with `absOff+32 > uint64(len(data))`, but this addition itself can overflow (wrap to a small number) when `absOff` is close to `math.MaxUint64`, letting a wildly out-of-range offset pass the check and reach the slice expression `data[absOff:absOff+32]`, which panics at runtime (Go slice-bounds-out-of-range) rather than returning the intended `false`. This is the same unchecked-addition-before-bounds-check defect as the Pico report, just in Go instead of Rust.

However, the event listener only processes logs whose topics match the whitelisted Gateway/Vault event signatures, and it is not evident from available code that the observer filters by exact contract *address* (only by `chainID` and event topic), which is the detail needed to fully confirm attacker reachability from an arbitrary contract on the source chain. This could not be fully verified due to index limitations on `event_listener.go`'s log-fetch/query construction — the file's log-fetching call site was not visible in the retrieved context.

### Impact Explanation
If reachable from an unprivileged, arbitrary contract (i.e., if the observer does not filter by Gateway contract address, only by event topic hash), an attacker could emit a fake event with the right topic and a crafted 32-byte "offset" word to panic the per-chain EVM event-parsing goroutine of the Universal Client. Depending on whether callers wrap event processing in `recover()` (no `recover()` was found anywhere under `universalClient/`), this could crash that chain's watcher process, a local/node-level DoS rather than fund theft — it does not by itself corrupt ballot state, UTX accounting, or mint/burn logic, since a panic prevents the event from ever being turned into a vote.

### Likelihood Explanation
Likelihood is uncertain and could not be confirmed as unprivileged/attacker-reachable with the available index: it hinges on whether `event_listener.go`'s log-fetch call restricts to the configured `gatewayAddress`/`vaultAddress` (in which case only the legitimate, presumably honestly-coded Gateway contract can produce this data, making the "attacker crafts a fake event" step effectively require either a compromised/malicious external contract or governance-approved gateway — both out of scope) or fetches by topic across all contracts on the chain (in which case any user could deploy a contract emitting the colliding topic with attacker-chosen data, making it directly triggerable).

### Recommendation
Regardless of reachability, add defense-in-depth in `readDynamicBytes`/`decodePayload`:
```go
func readDynamicBytes(data []byte, absOff uint64) (string, bool) {
    end, ok := checkedAdd(absOff, 32)
    if !ok || end > uint64(len(data)) {
        return "", false
    }
    ...
}
```
using `math/bits`-based checked addition (or bound `absOff` to `len(data)` before adding) so overflow can never bypass the bounds check, and wrap event-parsing goroutines with `recover()` so a malformed/adversarial log can never take down the watcher process.

### Proof of Concept
Not executed against the running binary; conceptually: construct an EVM log whose `Data[64:96]` (the `dataOffset` word) encodes a value such as `2^64 - 16` and whose topic matches `EventTypeSendFunds`. Feed it to `parseUniversalTxEvent` → `decodePayload` → `readDynamicBytes`; `absOff+32` wraps to `16`, `16 > len(data)` is false, so the code proceeds to `data[absOff:absOff+32]` with `absOff = 2^64-16`, which Go's runtime slice-bounds check panics on.

```go
// readDynamicBytes decodes ABI-encoded dynamic bytes at the given absolute offset in data.
func readDynamicBytes(data []byte, absOff uint64) (string, bool) {
	if absOff+32 > uint64(len(data)) {
		return "", false
	}
	byteLen := new(big.Int).SetBytes(data[absOff : absOff+32]).Uint64()
	dataStart := absOff + 32
	dataEnd := dataStart + byteLen
	if dataEnd > uint64(len(data)) {
		return "", false
	}
	return "0x" + hex.EncodeToString(data[dataStart:dataEnd]), true
}
```
