### Title
Fixed-overhead callback gas budgeting in the NEAR wallet contract can permanently lock `has_in_flight_tx`, freezing the account - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`inner_rlp_execute` computes callback gas as a small fixed constant plus the user-supplied `action.gas()`, and attaches that as the *static* gas for the private callback (`address_check_callback` / `nep_141_storage_balance_callback`). The fixed portion must cover both the callback's own execution work and the base cost of scheduling the next receipt. If the callback's own work exceeds that fixed portion, it panics with `GasExceeded`, which rolls back the `has_in_flight_tx = false` reset it performs first — leaving the flag permanently `true` as committed by the parent `rlp_execute` receipt. This mirrors the reported class of bug: a privileged-path call is executed under an artificially bounded/fixed gas budget, and if that proves insufficient, the following irreversible state effect (funds availability for the wallet) is permanently broken instead of gracefully failing.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` and returns a promise chain without further guarding against the possibility that the chain never reaches its terminal callback: [1](#0-0) 

For the `EOABaseTokenTransfer` flow with an address check, the callback gas is sized as a small fixed constant plus the caller-controlled `action.gas()`: [2](#0-1) 

The fixed constant is only 10 Tgas total (`ADDRESS_CHECK_CALLBACK_GAS = 5 Tgas + RLP_EXECUTE_CALLBACK_GAS(5 Tgas)`): [3](#0-2) 

That fixed budget must simultaneously cover (a) the `address_check_callback` function's own execution (deserializing the registrar response, hex-encoding, constructing the nested `Promise`/`.then()`), and (b) the 5 Tgas forwarded statically to the terminal `rlp_execute_callback`. `action.gas()` is *not* available to the callback's own logic — it is earmarked entirely for the nested cross-contract call created inside `action_to_promise`: [4](#0-3) 

If the callback's own bookkeeping work exceeds the ~5 Tgas remaining headroom (e.g., adversarially large `AddKey` `method_names` list causing an expensive `join(",")`, or a large ERC-20 receiver/token id string formatted via `format!`), the WASM execution aborts with `GasExceeded` before ever creating the nested promise. The identical structural risk exists for the ERC-20 path, whose fixed headroom is only marginally larger (15 Tgas) despite doing strictly more work (two chained `function_call`s plus JSON/string formatting): [5](#0-4) 

Per NEAR's atomic function-call semantics, a panicking receipt (including `GasExceeded`) discards **all** state writes made during that execution — including the `self.has_in_flight_tx = false` write performed as the very first statement of the callback: [6](#0-5) 

Because the parent `rlp_execute` receipt already durably committed `has_in_flight_tx = true` before dispatching the promise chain, and the callback's rollback discards its own reset, the flag is left permanently `true`. Every subsequent call to `rlp_execute` for this account will be rejected up front: [7](#0-6) 

There is no other public method that can reset `has_in_flight_tx` back to `false` — `ban_relayer` also unconditionally requires being reached as a receipt in the same broken chain, so the account is left in an unrecoverable state.

### Impact Explanation
Any funds attached to or intended to flow through this NEAR eth-implicit wallet account become permanently inaccessible: `rlp_execute` is the sole entry point for the account owner to authorize actions (transfers, function calls, key management), and once `has_in_flight_tx` is stuck `true`, all such actions are rejected indefinitely. This matches the "permanently frozen funds" / transaction-triggered halt category — a single crafted transaction submitted by an ordinary relayer/user can durably disable the wallet contract for its owner.

### Likelihood Explanation
The trigger is a single RLP-encoded Ethereum-style transaction routed through `rlp_execute` by any relayer (no special privilege needed) that hits the address-check or ERC-20 branches with inputs sized to push the callback's own compute cost close to or past the small fixed gas headroom (5–15 Tgas) reserved for it. Because the fixed headroom is a hardcoded constant independent of the actual size of user-controlled fields (target account id length, access-key method-name lists, ERC-20 receiver id length), an attacker/relayer has direct control over the variables that determine whether the callback's own work exceeds its budget, making this practically reachable rather than purely theoretical, though the exact gas margin needed to trigger it would require empirical measurement against `regular_op_cost`/host-fn costs.

### Recommendation
Do not size a privileged callback's own execution budget as a small fixed constant computed once at design time; instead, either (a) reserve gas for the callback's own logic using `GasWeight`/unspent-gas distribution (as already supported by `promise_batch_action_function_call_weight`) so it always receives a share proportional to what remains, or (b) bound the size of attacker-influenced inputs (method-name lists, account id strings) that feed the callback's pre-promise-creation logic, or (c) move the `has_in_flight_tx = false` reset (and any other unlock logic) so it does not depend on the same receipt successfully completing all downstream promise construction — e.g., commit the unlock as an independent, gas-cheap first action, or add a compensating recovery path that does not require re-executing the full callback logic.

### Proof of Concept
1. Deploy/impersonate a `near-wallet-contract` account and craft an RLP transaction whose decoded action is a `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { address_check: Some(addr), .. })` with an `AddKey` action carrying a very large `method_names` list (or otherwise inflate the work done by `address_check_callback` before it creates the nested promise).
2. Submit `rlp_execute(target, tx_bytes_b64)` with `attached_deposit` and enough attached gas to *create* the promise chain (so `inner_rlp_execute` succeeds and `has_in_flight_tx` is committed `true`), but where `action.gas()` plus `ADDRESS_CHECK_CALLBACK_GAS` still leaves the callback with insufficient real headroom for its own bookkeeping.
3. Observe that `address_check_callback` panics with `GasExceeded` before reaching `action_to_promise(...).then(...)`, so `rlp_execute_callback`/`ban_relayer` is never scheduled and `has_in_flight_tx` remains `true`.
4. Submit any subsequent `rlp_execute` call for the same account and observe it is rejected with `"Error: transaction already in progress, please try again later."` indefinitely.
