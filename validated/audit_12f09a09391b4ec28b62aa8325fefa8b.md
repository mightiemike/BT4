## Title
`DeleteAccountAction` with an invalid/non-existent `beneficiary_id` permanently burns the account's balance instead of refunding it - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` accepts an attacker/user-controlled `beneficiary_id` without verifying that the target actually exists (or can be created) before committing to delete the source account and queue the balance transfer. If `beneficiary_id` does not exist and is not a valid implicit-account id, the follow-up transfer receipt fails and the funds are burned rather than returned — an unrecoverable, permanent loss of value that a single transaction (or meta-transaction) signer can trigger, mirroring the "unmatched order" bug class where a caller-supplied but unverified target address causes real user funds to be irreversibly destroyed.

### Finding Description
`action_delete_account` takes the account's current balance and unconditionally schedules a system-refund receipt to `delete_account.beneficiary_id`, with **no check that this account exists**: [1](#0-0) 

This refund is generated via `Receipt::new_balance_refund`, which is a `predecessor_id == "system"` receipt: [2](#0-1) 

When that refund receipt is later applied, `check_account_existence` is invoked for the `Transfer` action against the (possibly missing) `beneficiary_id` account. Whether the missing account can be implicitly created depends on `implicit_creation_allowed`, which explicitly forbids creation when the receipt is a refund: [3](#0-2) [4](#0-3) 

So if `beneficiary_id` is a *named* account that doesn't exist (or otherwise ineligible for implicit creation), the refund receipt fails with `AccountDoesNotExist`. Because the failing receipt's `predecessor_id` is `"system"`, the runtime's refund-failure path burns the deposit instead of retrying or bouncing it back to the deleted account (which, by that point, no longer exists to receive it anyway): [5](#0-4) 

This is confirmed by an internal test comment acknowledging the destructive fallback behavior: "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" — but a refund of a refund is not possible; a failed system-refund is burned, not returned, per the code path above. [6](#0-5) 

The `DeleteAccountAction.beneficiary_id` is fully attacker/user-controlled input, validated only for well-formedness (`InvalidAccountId`) — never for existence — at validation time, per the spec: [7](#0-6) 

### Impact Explanation
Any account holder (or a relayer executing a signed meta-transaction/delegate action containing `DeleteAccount`, per NEP-366) can cause an account's entire remaining NEAR balance to be irrecoverably burned by specifying a `beneficiary_id` that does not exist as a named account. There is no recovery path: the account is deleted first, and the "refund" receipt that carries its balance is dropped as burnt tokens on execution failure. This is a permanent, protocol-visible loss of value triggered by a normal, unprivileged transaction — matching the "permanently frozen/lost funds" impact class from the reference report (fake/invalid target causing funds routed to an unusable destination and burned forever).

### Likelihood Explanation
High reachability: this requires only a single `DeleteAccount` action from any signer who owns or controls (via delegate action) the account being deleted, with an arbitrary `beneficiary_id`. No special permission, staking, or validator role is needed — it is directly reachable from `SignedTransaction` or a NEP-366 meta-transaction. It can happen accidentally (typo in beneficiary) or be exploited deliberately by a malicious relayer/dApp that constructs the delete transaction on a user's behalf with a bad or unreachable beneficiary id, silently destroying the user's balance while looking like a normal account-closing operation.

### Recommendation
Before committing to delete the source account, verify that `beneficiary_id` refers to an account that exists (or is a validly-creatable implicit account), and reject the action (e.g., a new `ActionErrorKind::BeneficiaryAccountDoesNotExist`) if not, similar to how `check_account_existence` already gates `Transfer`. Alternatively, disallow "refund can never create an account" from silently burning value: route failed system-refunds from `DeleteAccount` to a well-defined, always-valid sink (e.g., fail the whole delete action atomically) rather than burning as a side effect of a downstream receipt failure.

### Proof of Concept
1. Alice controls `alice.near` with balance `N` NEAR and no locked stake.
2. Alice (or a relayer acting via a signed delegate action on her behalf) submits `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near" })` where `nonexistent.near` has never been created.
3. `action_delete_account` computes `account_balance = N`, pushes `Receipt::new_balance_refund("nonexistent.near", N)`, and deletes `alice.near` (`runtime/runtime/src/actions.rs:380-386,404`).
4. The delete-account transaction/action itself succeeds (`SuccessReceiptId`).
5. The queued system refund receipt is applied against `nonexistent.near`; `check_account_existence` for `Action::Transfer` rejects it (`AccountDoesNotExist`) because `implicit_creation_allowed` returns `false` for refund receipts (`runtime/runtime/src/actions.rs:842-850, 928-933`).
6. The failed refund's deposit (`N` NEAR) is added to `other_burnt_amount` per `runtime/runtime/src/lib.rs:1047-1054` — permanently and irrecoverably removed from circulation, with no error surfaced on the original `DeleteAccount` transaction outcome.
