## Title
`liquidate-multi` silently absorbs partial-liquidation failures, letting debt be written down without collateral seizure - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` iterates positions with `map` over a private helper `call-liquidate` that directly invokes the public function `liquidate` (an intra-contract call, not a `contract-call?`). `liquidate-multi` unconditionally wraps the result list in `(ok ...)`, so the top-level transaction always "succeeds" regardless of whether any individual `liquidate` invocation errored out partway through its own sequence of state mutations.

### Finding Description
`liquidate` performs its debt/collateral bookkeeping as a sequence of separate `contract-call?`s to `.v0-market-vault`, each of which is its own Clarity atomicity boundary: [1](#0-0) 

```
(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))
(let ((debt-updated (try! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-to-remove debt-aid)))
      (actual-receiver (match collateral-receiver recv recv liquidator))
      (coll-removed (try! (contract-call? .v0-market-vault collateral-remove borrower coll-final collateral-ft coll-aid actual-receiver)))
      ...
```
(mirrors [2](#0-1) )

- `vault-system-repay` (liquidator pays debt tokens into the vault) executes and commits.
- `debt-remove-scaled` (borrower's recorded scaled debt is reduced in `market-vault`) executes and commits.
- `collateral-remove` (borrower's collateral is seized and sent to the liquidator/receiver) executes last.

Each of these is a separate `contract-call?` to `.v0-market-vault`, so each one that *returns ok* has its effects committed independently once it returns — Clarity only rolls back a contract-call's own effects when *that* call itself errors, and rolls back the *entire* transaction only when the outermost transaction-level call ultimately returns `err`.

When `liquidate` is invoked directly (as the outermost call of a transaction), if `collateral-remove` later fails (e.g. `ERR-PAUSED` from `market-vault`'s `collateral-remove` guard, or an internal balance-accounting failure in `remove-user-collateral`), the propagated `err` from `try!` makes the whole outer `liquidate` call return `err`, and since this is the top-level call, the *entire* transaction (including the already-committed `vault-system-repay` and `debt-remove-scaled` calls) is rolled back. This is safe in the single-liquidation path.

However, `liquidate-multi` breaks this safety net: [3](#0-2) 

```
;; Liquidates multiple positions atomically
...
;; Returns list of responses - one per position (ok/err)
;; Failed liquidations return error codes but don't revert entire batch
(define-public (liquidate-multi
                (positions (list 64 { borrower: principal, ... })))
  (ok (map call-liquidate positions)))
```

`call-liquidate` calls `liquidate` as an ordinary intra-contract function reference (not via `contract-call?`): [4](#0-3) 

```
(define-private (call-liquidate (position { borrower: principal, ... }))
  (liquidate (get borrower position)
             (get collateral-ft position)
             (get debt-ft position)
             (get debt-amount position)
             (get min-collateral-expected position)
             none
             none))
```

Because `liquidate` is entered here through a plain function reference rather than `contract-call?`, there is no atomicity boundary introduced between `liquidate-multi`/`map`/`call-liquidate` and the body of `liquidate`. The only atomicity boundaries inside `liquidate`'s execution remain the individual `contract-call?`s to `.v0-market-vault`. Since `liquidate-multi` unconditionally returns `(ok (list ...))`, the top-level transaction always succeeds — so the transaction-level rollback that would normally undo `vault-system-repay` + `debt-remove-scaled` never triggers, even though the position's `collateral-remove` step failed and the position's overall `liquidate` return value is `err`.

Net effect for that one failed position inside the batch: the liquidator's repayment (`vault-system-repay`) and the borrower's debt write-down (`debt-remove-scaled`) are committed, while `collateral-remove` never executes — debt is forgiven without collateral being seized to back it, and the liquidator's paid tokens are not compensated with any collateral.

### Impact Explanation
This is a protocol-insolvency / fund-freezing class issue: the borrower's tracked debt is reduced without corresponding collateral seizure, breaking the collateral/debt invariant the protocol relies on for solvency, and the liquidator's repayment funds are consumed without receiving the collateral they paid for (their funds are effectively lost/stranded inside the vault with no offsetting seized collateral credited to them). This matches the "protocol insolvency" / "temporary or permanent freezing of funds" impact classes, since repeated exploitation (or even accidental triggering, e.g. via a paused-collateral-remove race, or an edge-case in `remove-user-collateral`) silently erodes the collateral backing debt across the system while reporting overall transaction success.

### Likelihood Explanation
Likelihood depends on being able to make `collateral-remove` fail on `.v0-market-vault` *after* `debt-remove-scaled` has already succeeded within the same `liquidate` call. This can be triggered whenever the market-vault's `collateral-remove` guard trips (e.g., its `ERR-PAUSED` check, or an internal shortfall in `remove-user-collateral` versus the amount computed by `liquidate`), while `debt-remove-scaled`'s own preconditions are still satisfied. Since `liquidate-multi` is a public, permissionless, batch-composing entry point explicitly designed to keep going after per-position failures ("Failed liquidations return error codes but don't revert entire batch"), any liquidator/attacker who can engineer or observe such a mid-sequence failure for one position in a batch benefits from (or can be griefed by) the resulting inconsistent state, without needing any privileged access.

### Recommendation
- Route `call-liquidate`'s invocation of `liquidate` through `as-contract? contract-call?` (i.e., treat it as a genuine cross-boundary call) so that a failing position's `liquidate` invocation is fully and atomically rolled back on its own, independent of the batch's overall success.
- Alternatively, reorder `liquidate`'s mutations so that `collateral-remove` (or an equivalent "can we seize collateral" check) is validated/executed *before* `vault-system-repay` and `debt-remove-scaled` are committed, ensuring partial completion cannot leave debt reduced without matching collateral seizure.
- Add an explicit check in `liquidate-multi` that inspects each `call-liquidate` result and reverts (or clearly documents/limits) any batch entries whose internal contract-calls partially committed before failing.

### Proof of Concept
Conceptual sequence (exact triggering condition for `collateral-remove`'s failure was not independently verified in this pass — the codebase index did not let me confirm every internal guard in `remove-user-collateral`, so this should be validated with a live Devin session):
1. Attacker/liquidator submits `liquidate-multi` with one position `P` where `debt-amount`/`min-collateral-expected` are chosen so that `vault-system-repay` and `debt-remove-scaled` succeed against `market-vault`'s current state.
2. Engineer a condition where `collateral-remove` on `.v0-market-vault` for the same position then fails (e.g., DAO/ops toggling the `collateral-remove` pause flag mid-block via a preceding transaction in the same block, or an edge case where `remove-user-collateral`'s stored balance is less than `coll-final` due to a stale computation versus vault state).
3. `liquidate`'s `try!` on `collateral-remove` returns `err`, causing `liquidate`'s own execution to return `err`.
4. `call-liquidate` (direct function call, no `contract-call?` boundary) returns this `err` value into the `map` result list.
5. `liquidate-multi` still returns `(ok (list ... err ...))` — the top-level transaction succeeds.
6. Result: borrower `P`'s scaled debt has been reduced and the liquidator's repayment tokens were pulled into the vault, but no collateral was ever seized from `P` or transferred to the liquidator — a debt write-down inconsistent with any collateral movement, persisting on-chain.
