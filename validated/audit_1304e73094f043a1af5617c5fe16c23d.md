### Title
Nakamoto block acceptance never verifies coinbase VRF proof against the committed leader key's VRFPublicKey - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoChainState::append_block` only calls `check_block_commit_vrf_seed` (which internally calls `NakamotoBlock::validate_vrf_seed`) to confirm that the block-commit's `new_seed` hashes from the *parent* tenure's VRF proof. It never calls `check_normal_coinbase_tx`/`validate_normal_against_burnchain`, the only function that actually runs `VRF::verify(leader_vrf_key, vrf_proof, sortition_hash)` to bind the current block's coinbase VRF proof to the `VRFPublicKey` from the `LeaderKeyRegisterOp` consumed by the winning commit. As a result, a Nakamoto block's coinbase VRF proof bytes are stored and chained forward (via seed-hashing) but never cryptographically validated against the leader key that was supposedly used to produce them.

### Finding Description
The intended equality is: `VRF_proof_verify(leader_key.public_key, sortition_hash, coinbase.vrf_proof) == true`, enforced by `NakamotoBlock::check_normal_coinbase_tx` [1](#0-0) , which is only ever invoked from `validate_normal_against_burnchain` [2](#0-1) .

The actual block-acceptance path, `NakamotoChainState::append_block`, instead calls `Self::check_block_commit_vrf_seed(chainstate_tx.as_tx(), burn_dbconn, block)` when `is_new_tenure` is true [3](#0-2) . That function only fetches the block-commit and calls `block.validate_vrf_seed(...)`, which checks `block_commit.new_seed.is_from_proof(&parent_vrf_proof)` — i.e., that the seed the miner committed to on Bitcoin is derived from the *parent* tenure's stored VRF proof bytes [4](#0-3) [5](#0-4) . This is purely a hash-chaining check between two proof byte-strings; at no point does it call `VRF::verify` with any `VRFPublicKey`, and it never looks up `get_leader_key_at` to fetch the leader's registered VRF public key for this block's own coinbase proof.

`validate_normal_against_burnchain`/`check_normal_coinbase_tx` — the only code that performs the actual `VRF::verify(leader_vrf_key, proof, sortition_hash)` binding — has no call sites in the codebase outside of unit tests [6](#0-5) . It is dead code with respect to the real Nakamoto block-processing pipeline in `append_block`.

Consequently, an attacker who wins a sortition slot (a single miner slot, no majority stake required) can submit a coinbase transaction containing an arbitrary 80-byte value in the VRF-proof field — not a valid VRF proof produced by the private key corresponding to the `VRFPublicKey` registered in their `LeaderKeyRegisterOp` — as long as any future block's `new_seed` is correctly derived (via `VRFSeed::from_proof`) from those same bytes. `check_block_commit_vrf_seed`/`validate_vrf_seed` will report `Ok(())` because it only checks proof-byte consistency across tenures, not cryptographic validity against the leader key.

### Impact Explanation
Because every honest node runs the identical (incomplete) validation logic, all nodes will uniformly accept the same block regardless of whether the VRF proof is cryptographically valid — this does not, by itself, cause disagreement between two honest nodes' fork choice, since the check (or lack thereof) is deterministic and identical across the network. However, it defeats the core security property of VRF-based sortition: the unpredictability and non-malleability of the seed used to select the next leader. A miner can supply an unverifiable "proof" whose derived seed they control, undermining the guarantee that sortition outcomes are bound to secret VRF keys registered on-chain. This is a protocol-level cryptographic-binding failure in consensus-critical code, but under the stated severity taxonomy it does not clearly manifest as an inter-node state divergence, invalid-block-accepted-vs-rejected disagreement, or reward theft, since no two honest nodes disagree on the resulting chain state.

### Likelihood Explanation
Preconditions: the attacker only needs to win a single sortition (one Bitcoin block-commit with their own BTC and a valid leader-key registration slot) — no majority stake, no signer collusion, no privileged role. This is directly reachable via normal mining participation and is repeatable every tenure the attacker wins.

### Recommendation
Invoke the equivalent of `check_normal_coinbase_tx` (VRF proof verification against the leader key's `VRFPublicKey`, obtained via `get_leader_key_at` using the winning commit's `key_block_ptr`/`key_vtxindex`) inside `NakamotoChainState::append_block`, alongside `check_block_commit_vrf_seed`, before accepting the block. Ensure `validate_normal_against_burnchain` (or an equivalent Nakamoto-aware check) is actually wired into the production block-acceptance path rather than only exercised in tests.

### Proof of Concept
1. Set up a two-node/local-chainstate integration test using the harness in `stackslib/src/chainstate/nakamoto/tests/node.rs`.
2. Have the attacker miner register a `LeaderKeyRegisterOp` with `VRFPublicKey` A, win the sortition with a `LeaderBlockCommitOp`.
3. Construct the coinbase's VRF proof using a *different* keypair B (or arbitrary bytes) instead of A, while making the block-commit's `new_seed` consistent with parent's recorded proof bytes.
4. Call `NakamotoChainState::check_block_commit_vrf_seed(&mut chainstate.index_conn(), sortdb.conn(), &block)` and assert it returns `Ok(())` despite `VRF::verify(&A, &proof_generated_under_B, sortition_hash)` returning `false`/error, demonstrating the missing binding — compare against `block.check_normal_coinbase_tx(&A, &sortition_hash)`, which correctly returns `Err(...)`, showing the discrepancy between the (unused) correct check and the (used) incomplete check in `append_block`.

    /// Verify that the VRF seed of this block's block-commit is the hash of the parent tenure's
    /// VRF seed.
    pub fn validate_vrf_seed<SDBI: StacksDBIndexed>(
        &self,
        sortdb_conn: &Connection,
        chainstate_conn: &mut SDBI,
        block_commit: &LeaderBlockCommitOp,
    ) -> Result<(), ChainstateError> {
        // the block-commit from the miner who created this coinbase must have a VRF seed that
        // is the hash of the parent tenure's VRF proof.
        // Do the query relative to the parent block ID, since this block may not be processed yet.
        let parent_vrf_proof = NakamotoChainState::get_parent_vrf_proof(
            chainstate_conn,
            &self.header.parent_block_id,
            sortdb_conn,
            &self.header.consensus_hash,
            &block_commit.txid,
        )?;
        if !block_commit.new_seed.is_from_proof(&parent_vrf_proof) {
            warn!("Invalid Nakamoto block-commit: seed does not match parent VRF proof";
                  "consensus_hash" => %self.header.consensus_hash,
                  "stacks_block_hash" => %self.header.block_hash(),
                  "stacks_block_id" => %self.block_id(),
                  "parent_block_id" => %self.header.parent_block_id,
                  "commit_seed" => %block_commit.new_seed,
                  "proof_seed" => %VRFSeed::from_proof(&parent_vrf_proof),
                  "parent_vrf_proof" => %parent_vrf_proof.to_hex(),
                  "block_commit" => format!("{:?}", &block_commit)
            );
            return Err(ChainstateError::InvalidStacksBlock(
                "Invalid Nakamoto block: bad VRF proof".into(),
            ));
        }
        Ok(())
    }

    /// Verify that if this block has a coinbase, that its VRF proof is consistent with the leader
    /// public key's VRF key. If there is no coinbase tx, then this is a no-op.
    fn check_normal_coinbase_tx(
        &self,
        leader_vrf_key: &VRFPublicKey,
        sortition_hash: &SortitionHash,
    ) -> Result<(), ChainstateError> {
        assert!(!self.is_shadow_block());

        // If this block has a coinbase, then verify that its VRF proof was generated by this
        // block's miner.  We'll verify that the seed of this block-commit was generated from the
        // parnet tenure's VRF proof via the `validate_vrf_seed()` method, which requires that we
        // already have the parent block.
        if let Some(coinbase_tx) = self.get_coinbase_tx() {
            let (_, _, vrf_proof_opt) = coinbase_tx
                .try_as_coinbase()
                .expect("FATAL: `get_coinbase_tx()` did not return a coinbase");

            let vrf_proof = vrf_proof_opt.ok_or(ChainstateError::InvalidStacksBlock(
                "Nakamoto coinbase must have a VRF proof".into(),
            ))?;

            // this block's VRF proof must have been generated from the last sortition's sortition
            // hash (which includes the last commit's VRF seed)
            let valid = match VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes()) {
                Ok(v) => v,
                Err(e) => {
                    warn!(
                        "Invalid Stacks block header {}: failed to verify VRF proof: {}",
                        self.header.block_hash(),
                        e
                    );
                    false
                }
            };

            if !valid {
                warn!("Invalid Nakamoto block: leader VRF key did not produce a valid proof";
                    "consensus_hash" => %self.header.consensus_hash,
                    "stacks_block_hash" => %self.header.block_hash(),
                    "stacks_block_id" => %self.header.block_id(),
                    "leader_public_key" => %leader_vrf_key.to_hex(),
                    "sortition_hash" => %sortition_hash
                );
                return Err(ChainstateError::InvalidStacksBlock(
                    "Invalid Nakamoto block: leader VRF key did not produce a valid proof".into(),
                ));
            }
        }
        Ok(())
    }

    /// Verify that a nakamoto block's block-commit's VRF seed is consistent with the VRF proof.
    /// Specifically, it must be the hash of the parent tenure's VRF proof.
    pub(crate) fn check_block_commit_vrf_seed<SDBI: StacksDBIndexed>(
        chainstate_conn: &mut SDBI,
        sortdb_conn: &Connection,
        block: &NakamotoBlock,
    ) -> Result<(), ChainstateError> {
        if block.is_shadow_block() {
            // no-op
            return Ok(());
        }

        // get the block-commit for this block
        let sn =
            SortitionDB::get_block_snapshot_consensus(sortdb_conn, &block.header.consensus_hash)?
                .ok_or(ChainstateError::NoSuchBlockError)
                .inspect_err(|_e| {
                    warn!("No block-commit for block";
                        "consensus_hash" => %block.header.consensus_hash,
                        "stacks_block_hash" => %block.header.block_hash(),
                        "stacks_block_id" => %block.header.block_id()
                    );
                })?;

        let block_commit =
            get_block_commit_by_txid(sortdb_conn, &sn.sortition_id, &sn.winning_block_txid)?
                .ok_or(ChainstateError::NoSuchBlockError)
                .inspect_err(|_e| {
                    warn!("No block-commit for block";
                        "consensus_hash" => %block.header.consensus_hash,
                        "stacks_block_hash" => %block.header.block_hash(),
                        "stacks_block_id" => %block.header.block_id()
                    );
                })?;

        // N.B. passing block.block_id() here means that we'll look into the parent tenure
        block.validate_vrf_seed(sortdb_conn, chainstate_conn, &block_commit)
    }
