### Title
Unbounded linear scan in `Manager.getTxFromPending` reachable via unauthenticated `GetTransactionFromPendingServlet` allows CPU-cost amplification - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`GetTransactionFromPendingServlet.doGet`/`doPost` forward attacker-supplied transaction IDs directly to `Manager.getTxFromPending(String)` with no other gating beyond `RateLimiterServlet`, which only throttles request frequency, not the cost of each request. If `getTxFromPending` performs a linear scan of `pendingTransactions`/`rePushTransactions`, the per-request cost grows with the size of those queues, which an unprivileged client can grow by broadcasting many low-fee transactions.

### Finding Description
The servlet takes the `value` parameter and calls `manager.getTxFromPending(input)` unconditionally, with no query-size limits, pagination, or bound on the underlying queue traversal: [1](#0-0) 
The servlet extends `RateLimiterServlet`, whose protection is limited to request-rate throttling and does not account for the size of `pendingTransactions`/`rePushTransactions` that `getTxFromPending` must traverse per call. `Manager.java` does reference `pendingTransactions`/`rePushTransactions` extensively (confirmed via search matches), consistent with `getTxFromPending` iterating these collections to find a matching transaction ID; I was not able to retrieve the exact method body within the available tool budget to confirm the precise loop bounds or any early-exit/size-cap logic that might mitigate this.

### Impact Explanation
If confirmed, the concrete impact is degraded RPC-API responsiveness/CPU burn proportional to pending-pool size, i.e., a "DoS via RPC-API" class issue — repeated calls to this single HTTP endpoint could consume CPU proportional to queue length, and because pool size can be inflated by ordinary low-fee broadcasts, an attacker who is only a funded account (no privileged role) could combine "flood queue" + "poll endpoint" to sustain elevated latency for this RPC path.

### Likelihood Explanation
Exploitability depends on unverified factors: (1) whether `pendingTransactions`/`rePushTransactions` have an enforced maximum size elsewhere in `Manager` (e.g. pool-size checks in `pushTransaction`), and (2) whether bandwidth/energy costs of broadcasting many transactions make sustained queue inflation economically impractical for an attacker. Without confirming these bounds in the actual `Manager.java` source (which I could not fully load in this session), I cannot establish that the queue is genuinely unbounded in practice or that the resulting CPU cost is severe enough to constitute a real DoS beyond a minor, self-limiting overhead absorbed by normal per-account bandwidth throttling.

### Recommendation
Add an explicit size cap / early-exit and/or an index (e.g., a `Map<Sha256Hash, TransactionCapsule>`) for pending/re-push lookups instead of a linear scan, and consider rate-limiting or size-limiting `GetTransactionFromPendingServlet` based on current pending-pool size rather than only request frequency.

### Proof of Concept
Not fully verifiable in this session — a definitive PoC requires confirming the actual implementation of `Manager.getTxFromPending` (loop structure, any size caps on `pendingTransactions`/`rePushTransactions`) which could not be retrieved with the available tools. Recommend a JUnit test as described in the question (reflectively inflate `pendingTransactions` to N=100k `TransactionCapsule` entries, measure `getTxFromPending` latency vs. queue size) be run directly against the repository to confirm whether latency scales linearly and unbounded before treating this as a confirmed, exploitable DoS.
