### Title
Unvalidated incoming receipt can trigger an unrecoverable `panic!` in chunk apply instead of a graceful rejection - ([File: chain/chain/src/runtime/mod.rs])

### Summary
The external report describes `Tranche.issue()` reverting because a downstream dependency (`RocketDepositPool.deposit()`) enforces a precondition (`getDepositEnabled()`) that the calling adapter never checks, so a normal user call fails deep in the call stack with an unhandled revert. The nearcore analog is the receipt-validation path: `Runtime::apply` can return `RuntimeError::ReceiptValidationError` for receipts that fail `validate_receipt`, and the sole caller in the production chunk-application path converts that error class into an unconditional `panic!`, rather than treating it as a normal rejected transaction/receipt.

### Finding Description
`validate_receipt` in [1](#0-0)  enforces receipt-shape invariants (size limit, account-id validity, action validation) and is invoked with two modes: `ValidateReceiptMode::NewReceipt` (strict, used for receipts freshly produced during execution) and `ValidateReceiptMode::ExistingReceipt` (lenient, used for receipts that already exist in state/were received, explicitly because "there is a bug which allows creation of receipts above the size limit… Runtime has to handle them gracefully", as documented at [2](#0-1) ).

For **newly created** receipts, a validation failure is deliberately caught and converted into a graceful `ActionErrorKind::NewReceiptValidationError`, which only fails the specific receipt/action rather than the whole chunk, as seen in `apply_action_receipt`: [3](#0-2) .

However, when a `RuntimeError::ReceiptValidationError` does propagate out of `Runtime::apply` (i.e., is not intercepted and converted to an `ActionError` somewhere in the receipt-processing pipeline), it reaches the single production call-site in the chain layer, which explicitly performs `panic!("{}", e)` with a `TODO(#2152): process gracefully` comment instead of returning an `Error` that would fail just the transaction: [4](#0-3) .

The same anti-pattern also converts `RuntimeError::UnexpectedIntegerOverflow` into a `panic!` at the same call site, and `apply_chunk` panics on any other `StorageError` variant that isn't one of the two whitelisted recoverable kinds: [5](#0-4) .

This is structurally the same bug class as the report: a downstream function's precondition/error (here, the receipt-validation invariant) is not caught and converted into a normal failure at the boundary that a single user-submitted transaction/receipt can reach; instead it surfaces as an unconditional `panic!` in the chunk-apply path used by every validator applying that chunk.

### Impact Explanation
If any reachable path can cause `Runtime::apply` to surface `RuntimeError::ReceiptValidationError` (rather than have it downgraded to an `ActionError` inside receipt processing) for a receipt that a normal transaction/RPC caller can get included in a chunk, then every node that applies that chunk hits the `panic!("{}", e)` at `chain/chain/src/runtime/mod.rs:372`. Because this code path runs identically on every validator/chunk-producer/chunk-validator processing the chunk, this is a **transaction-triggered halt**: it crashes (or aborts) the node process applying the chunk, deterministically, for anyone running the affected code. This matches the "transaction-triggered halt" acceptance criterion directly. It does not require any privileged role — only the ability to get a receipt included in a chunk, i.e., ordinary transaction submission via JSON-RPC.

### Likelihood Explanation
The likelihood hinges on whether an ordinary user-submitted transaction/receipt can produce a receipt that fails `validate_receipt` while bypassing the graceful `ActionErrorKind::NewReceiptValidationError` conversion and instead surfaces as a top-level `RuntimeError::ReceiptValidationError`. The codebase's own comments acknowledge exactly this class of gap: issue #12606 notes there is "a bug which allows to create receipts that are above the size limit" that necessitated the lenient `ExistingReceipt` validation mode, and the `TODO(#2152): process gracefully` marker on the panic site is a direct acknowledgment by the maintainers that this error is not supposed to reach production as a panic. This indicates the boundary between "receipt validation failures that are safely converted to ActionError" and "receipt validation failures that leak into `Runtime::apply`'s top-level `Result` and panic" is an area of ongoing bug-fixing (see also the `test-loop-tests/src/tests/max_receipt_size.rs` tests explicitly built to assert "the runtime shouldn't die when it encounters a large receipt"). I could not fully trace, within the available tool budget, every code path that returns `Err(RuntimeError::ReceiptValidationError(...))` directly (as opposed to catching it inline) to prove a concrete transaction-reachable trigger exists today; the existing regression tests suggest known instances of this exact class have been fixed, but the panic-on-error design at the `Runtime::apply` boundary remains present as defense that has not been removed, implying the failure mode is still architecturally reachable if any call site is missed.

### Recommendation
- Audit every internal call path that can produce a `RuntimeError::ReceiptValidationError` (or `UnexpectedIntegerOverflow`) during `Runtime::apply`, and ensure each one is intercepted inline and converted to a per-receipt `ActionError`/no-op outcome (as already done for new receipts in `apply_action_receipt`), rather than allowed to escape to the top-level `Result<ApplyResult, RuntimeError>`.
- Remove or replace the `panic!` branches in `chain/chain/src/runtime/mod.rs` (`RuntimeError::UnexpectedIntegerOverflow` and `RuntimeError::ReceiptValidationError`) with an `Error` variant that fails only the offending chunk/transaction gracefully, resolving the long-standing `TODO(#2152)`.
- Add regression tests (in the spirit of `test-loop-tests/src/tests/max_receipt_size.rs`) that specifically attempt to smuggle a receipt through every insertion point (postponed receipts, delayed receipts, promise yield/resume, incoming cross-shard receipts) that could fail `validate_receipt` in `ExistingReceipt` mode, verifying none of them cause `Runtime::apply` to return the panic-triggering error variants.

### Proof of Concept
A full working PoC transaction was not constructed within the available investigation; the concrete trigger condition (a specific action/receipt shape that escapes the `NewReceiptValidationError` interception and surfaces as top-level `RuntimeError::ReceiptValidationError`) requires further tracing of all `validate_receipt` call sites in `runtime/runtime/src/lib.rs` (11 matches) that was not completed before the iteration budget was exhausted. The root-cause code locations proving the *unsafe panic pattern* itself are cited above and are concrete and verifiable; what remains unverified is whether a currently-unfixed call path allows a user-submitted transaction to reach it (as opposed to the already-fixed instances covered by `max_receipt_size.rs`).

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // We retain these checks here as to maintain backwards compatibility
    // with AccountId validation since we illegally parse an AccountId
    // in near-vm-runner/src/wasmtime_runner/logic.rs#fn(read_and_parse_account_id)
    AccountId::validate(receipt.predecessor_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidPredecessorId {
            account_id: receipt.predecessor_id().to_string(),
        }
    })?;
    AccountId::validate(receipt.receiver_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidReceiverId { account_id: receipt.receiver_id().to_string() }
    })?;

    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt)
        | VersionedReceiptEnum::PromiseYield(action_receipt) => validate_action_receipt(
            limit_config,
            action_receipt,
            receipt.receiver_id(),
            current_protocol_version,
            mode,
        ),
        VersionedReceiptEnum::Data(data_receipt)
        | VersionedReceiptEnum::PromiseResume(data_receipt) => {
            validate_data_receipt(limit_config, &data_receipt)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(()), // Distribution receipt can't be issued without a valid contract
    }
}
