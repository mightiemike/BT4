Based on my research, I found a concrete, code-acknowledged integrity gap rather than a speculative one — it maps well onto the "commit-before-verification" bug class from the external report, but manifests differently: a **verification function that omits state-root fields it claims to validate**, undermining replay/restore integrity checks rather than the commit path itself.

### Title
Replay/restore integrity check silently skips state-checkpoint (JMT) root validation - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by chunk-executor replay, `aptos-debugger`, and the `aptos` CLI to verify that a locally re-executed `TransactionOutput` matches an authenticated, previously-committed `TransactionInfo`, checks status, gas, write-set hash, and event-root hash — but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` is the authoritative equality check between a freshly computed `TransactionOutput` and the `TransactionInfo` that was actually committed/authenticated on-chain (embedded in the transaction accumulator). [1](#0-0) 
It validates `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash, but stops there — it never compares `txn_info.state_checkpoint_hash()` (the JMT/global state root committed at checkpoint boundaries) against anything computed locally. The code itself documents this omission in a TODO immediately following the checks: [2](#0-1) 

This function is invoked from tooling whose entire purpose is to independently confirm ledger-state integrity:
- `execution/executor/src/chunk_executor/mod.rs` (transaction replayer path)
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`
- `aptos-move/cli/src/commands.rs` (`replay-past-txn` / debug utilities) [3](#0-2) 

Because `state_checkpoint_hash` (and, when the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature ships, `position_state_checkpoint_hash`) is never compared, this verification path can report a transaction as "matching" its authenticated `TransactionInfo` even when the locally recomputed state root diverges from the one actually committed and accumulated into the ledger's Merkle accumulator.

### Impact Explanation
This does not corrupt the actual consensus-committed ledger (the real state root is still bound into the transaction accumulator and verified elsewhere, e.g. `DoStateCheckpoint::get_state_checkpoint_hashes` during normal chunk execution/state-sync, which does perform this comparison). [4](#0-3) 
The impact is scoped to independent verification/debugging tooling (`db-tool replay_on_archive`, `aptos-debugger`, CLI replay commands) — a divergence between the archived/replayed state root and the authenticated one would silently pass verification, giving operators, auditors, or bisection tooling false assurance that historical execution matches the authenticated chain state, exactly the class of "authenticated response bound to wrong version/root accepted as valid" called out in the state-integrity gate.

### Likelihood Explanation
Moderate-to-low today: exploiting this requires an actual state-root divergence to already exist (e.g., from a VM/storage bug, or from enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` without also patching this comparator, as the TODO explicitly warns). I could not fully confirm within this session whether any currently-shipped code path relies on `ensure_match_transaction_info` as its sole state-root integrity guarantee (versus using it only for supplementary checks alongside `DoStateCheckpoint`'s own validation) — this needs further tracing of every call site's surrounding logic.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, and (when applicable) `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, against the corresponding locally-recomputed roots, exactly as the existing TODO comment specifies, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network.

### Proof of Concept
Not applicable as an on-chain exploit — this is a verification-logic gap, demonstrable by inspection: call `ensure_match_transaction_info` with a `TransactionOutput` whose write set/events/status/gas all match `txn_info` but whose resulting state root would differ (e.g., due to a divergent prior state); the function returns `Ok(())` despite the state-root mismatch, since no field in the comparison covers `state_checkpoint_hash`.

**Note on confidence**: This finding is weaker against the gate's "committed state differs from correct VM result" bar than a true commit-path bug, since the actual commit/accumulator path (`DoStateCheckpoint`) does perform root validation. I'm flagging it because it's a genuine, TODO-acknowledged, unprivileged gap in authenticated-state verification tooling, but recommend a Devin session with fuller call-graph tracing (all callers of `ensure_match_transaction_info` and whether any gates consensus-relevant decisions) before treating this as high/critical.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
