## Analysis Result

I found one concrete local candidate worth reporting, though it self-documents as an acknowledged limitation rather than a full working exploit (`ensure_match_transaction_info` in `types/src/transaction/mod.rs`). I'll present it as the strongest analog, while flagging its limits honestly.

### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay/verify tooling to accept a diverged state root as correct - (File: `types/src/transaction/mod.rs`)

### Summary
The Venus report's core lesson is that a value used to gate trust/accounting (the exchange rate) can silently diverge from the value the protocol *should* be enforcing when a check that "looks complete" is actually missing a critical comparison. The Aptos-native analog is in the replay/verification comparator `ensure_match_transaction_info`, which is meant to assert that a locally re-executed `TransactionOutput` matches an authenticated, already-proof-verified `TransactionInfo`. The function checks status, gas, write-set hash, and event-root hash, but explicitly and admittedly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` is the authoritative comparator used by both `execution/executor/src/chunk_executor/mod.rs::verify_execution` (`ChunkExecutorInner::verify_execution`) and `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, to confirm that locally computed `TransactionOutput`s match the trusted `TransactionInfo`s obtained via a proven `TransactionInfoListWithProof` (state-sync/backup restore/replay-verify paths). [1](#0-0) 

Within the function body, only `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash` are asserted to match: [2](#0-1) 

The comment left directly above the function's `Ok(())` return explicitly documents the gap: [3](#0-2) 

This means the state checkpoint hash (main JMT state root), the hot-state checkpoint hash, and the newly introduced `position_state_checkpoint_hash` (native-trading position-tree root, gated by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature) are never independently re-verified by this comparator against locally recomputed values, even though these are the fields written into the on-chain `TransactionInfoV1` and folded into the transaction-accumulator root that consensus/light-clients trust: [4](#0-3) 

The comparator is used both by db-tool's `replay_on_archive` and by `ChunkExecutorInner::verify_execution` in the executor: [5](#0-4) [6](#0-5) 

### Impact Explanation
`replay_on_archive` and `verify_execution` (used with `VerifyExecutionMode::verify_all()` during transaction-restore/replay-verify tooling) are the tools operators rely on to detect if a local VM/executor build produces a different result than what's committed on the authenticated chain — this is precisely the "hard-fork-only divergence during commit, replay, restore, or proof verification" category in scope. Because the checkpoint-hash fields are excluded from the comparison, a divergence confined to `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` (e.g., a bug in state-checkpoint computation, hot-state promotion logic, or the new native-position state root) would **not** be caught by this tool even though the trusted `TransactionInfo` used for the comparison came from a verified accumulator proof. The tool would report a "successful replay" while the locally recomputed authoritative root actually diverges from the chain's committed root — i.e., an authenticated proof-bearing value (`TransactionInfo`) is treated as validated against local execution when a critical field was never actually checked.

However, I could not independently confirm within this session that any code path actually *produces* a wrong checkpoint hash — I only confirmed that the verification/replay tooling has an admitted blind spot for detecting such a divergence. The severity therefore depends on whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` is enabled in production and whether the underlying state-checkpoint computation is itself correct (I did not find a concrete corrupting bug in `DoStateCheckpoint` in this pass).

### Likelihood Explanation
Low-to-moderate on its own: this is a gap in an operator-facing verification/debugging tool (`replay_on_archive`, replay-verify chunk executor), not a bug in the consensus-critical commit path itself. The comment indicates the maintainers are aware and gated the affected feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is presumably not yet enabled in mainnet given the explicit "before enabling" caveat. This reduces the likelihood of real-world impact today but represents a genuine state-integrity blind spot that would matter as soon as that feature (or hot-state root in txn info) is turned on, since a real corruption in those roots would go undetected by replay-verify.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against `txn_info`'s corresponding fields whenever those checkpoints are expected (i.e., using the same state-checkpoint/hot-state/position summaries already computed in the executor pipeline), before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or `HOT_STATE_ROOT_IN_TXN_INFO` is enabled on any environment relying on `replay_on_archive` or `verify_execution` for integrity assurance.

### Proof of Concept
Not independently reproducible from static analysis alone — a concrete PoC would require constructing a `TransactionOutput` whose write-set/events/status/gas match a given `TransactionInfo` bit-for-bit but whose recomputed state/hot-state/position checkpoint root differs (e.g., by feeding `ensure_match_transaction_info` a forged/incorrect `state_checkpoint_hash` in the compared `TransactionInfo`) and confirming `Ok(())` is still returned. I did not execute this against the live codebase in this session; this is based on direct code/comment inspection only.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
