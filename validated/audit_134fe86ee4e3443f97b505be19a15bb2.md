### Title
Shared `last-update` timestamp lets frequent, permissionless `accrue()` calls permanently suppress LP `lindex` growth while `index` keeps accruing normally - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` — identical pattern in every `v0-vault-*.clar`)

### Summary
The vault's `accrue()` function drives two separate interest indices — a borrower debt index (`index`) and an LP liquidity index (`lindex`) — off a single, shared `last-update` timestamp. Because the borrower index rounds up (`calc-multiplier-delta ... true`) and the liquidity index rounds down (`calc-multiplier-delta ... false`), the borrower index almost always changes on any non-zero `time-delta`, while the liquidity index can round to exactly zero when the effective liquidity rate is low relative to the interval. `accrue()` resets `last-update` whenever *either* index changes, so every time the borrower index ticks (which happens on virtually every call), the liquidity index's un-materialized fractional time is discarded — permanently, since the clock never rewinds. A caller can spam `accrue()` (a public, unauthenticated function) at a cadence tuned to keep the liquidity-index increment at zero forever, freezing LP yield growth while the borrower side (and thus their debt) still accrues.

### Finding Description
`accrue()` computes `next = next-index()` (borrower debt index, round-up) and `nliq = next-liquidity-index()` (LP liquidity index, round-down), then only re-arms the shared clock if something changed: [1](#0-0) 

Both `next-index` and `next-liquidity-index` compute `time-delta` from the *same* `last-update` var, and both call the shared `calc-multiplier-delta`, just with the `round-up` flag flipped: [2](#0-1) 

`calc-multiplier-delta` uses `mul-div-up` for the borrower path and `mul-div-down` for the liquidity path: [3](#0-2) 

Since `mul-div-up(x,y,z) = (x*y + z-1)/z`, any non-zero `rate * time-delta` numerator rounds up to at least `1`, so `next-index` almost always strictly exceeds `index` (the borrower debt index only grows over time, so `idx ≥ INDEX-PRECISION`, guaranteeing the resulting `calc-index-next` delta is `≥ 1`). In contrast, the LP-side `liquidity-rate` is deliberately scaled down from the borrow rate by both utilization and `(1 - reserve-factor)`: [4](#0-3) 

so during low-utilization and/or high-reserve-factor conditions (a normal, non-adversarial operating state — e.g. shortly after deployment, after a large withdrawal, or simply a quiet market), `liquidity-rate` can be small enough that `mul-div-down(liquidity-rate, time-delta*INDEX-PRECISION, SECONDS-PER-YEAR-BPS)` rounds to `0` for a meaningfully long `time-delta` window (roughly `time-delta < SECONDS-PER-YEAR-BPS / (liquidity-rate * INDEX-PRECISION)` seconds). Any actor can then call the public, unauthenticated `accrue()` at an interval just under that threshold: the borrower index ticks (forcing `last-update := stacks-block-time`) while the liquidity index computes a zero increment and is silently reset to "start counting from now" — over and over, so its true elapsed time is discarded forever rather than carried forward.

### Impact Explanation
This suppresses growth of `lindex`, which underlies LP share pricing (`total-assets-preview`/`calc-treasury-lp-preview` and ultimately the exchange rate paid on redeem). LPs are underpaid relative to the real elapsed time and real liquidity rate, i.e., unclaimed yield owed to LPs is temporarily/permanently frozen/diluted, while the borrower's owed debt keeps accruing on schedule (or slightly favorably, due to rounding up). This is a "theft/freezing of unclaimed yield" class impact (High), achievable with no privileged access, no capital, and no counterparty interaction — only repeated cheap calls to a public function.

### Likelihood Explanation
Likelihood is conditional but realistic: it requires the effective `liquidity-rate` to be small relative to the attacker's call cadence, which happens naturally whenever utilization is low or the reserve factor is high — common, expected states rather than contrived edge cases. `accrue()` takes no arguments and has no auth check, so any address (or a cheap bot) can drive the exploit indefinitely at near-zero cost, and the effect compounds the longer the campaign runs.

### Recommendation
- Track independent `last-update` timestamps per index (one for `index`, one for `lindex`) so that resetting the clock for one index does not discard unrealized fractional time for the other.
- Alternatively, accumulate the truncated remainder/dust across calls (carry-forward accounting) instead of resetting the elapsed-time baseline whenever any change occurs.
- Consider increasing internal precision for `liquidity-rate`/`INDEX-PRECISION` so that legitimate call cadences essentially never round to zero, similar to the recommendation in the referenced audit finding.

### Proof of Concept
1. Deploy/observe a vault (e.g. `v0-vault-usdc.clar`) in a state with low utilization and/or a non-trivial `fee-reserve`, such that `calc-liquidity-rate` yields a small `liquidity-rate` (e.g. a few bps).
2. Compute the rounding threshold `T ≈ SECONDS-PER-YEAR-BPS / (liquidity-rate * INDEX-PRECISION)` seconds using the constants at [5](#0-4) .
3. Repeatedly call the public `accrue()` function every `~T - ε` seconds for an extended period. On each call: `next-index` (round-up) ticks and differs from `index`, forcing `(var-set last-update stacks-block-time)`; `next-liquidity-index` (round-down) computes the same `nliq == lindex` (zero increment) because its elapsed-time numerator never accumulates past the rounding threshold before being reset.
4. Compare `lindex` after the campaign against a control scenario where `accrue()` is called just once after the same total wall-clock time elapses. The spammed scenario yields a strictly lower `lindex` (and thus lower LP share value / owed assets) than the single clean accrual, mirroring the referenced report's PoC pattern but manifesting specifically on the LP liquidity index due to the shared `last-update` timestamp.
