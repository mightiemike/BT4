Found a strong analog in the NEAR Wallet Contract's nonce validation, which mirrors the exact-match-against-a-value-that-changes-underneath-you pattern from the Venus liquidation bug.

### Title
Wallet Contract `rlp_execute` bans a relayer whose nonce becomes stale due to prior in-flight transaction resolution timing, permanently revoking a legitimate relayer's access key - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
`validate_tx_relayer_data` in the NEAR Wallet Contract requires the Ethereum-emulated transaction's `nonce` field to exactly equal `expected_nonce`, the contract's current stored `nonce` at execution time [1](#0-0) . Any mismatch is classified as `RelayerError::InvalidNonce`, which is a fatal, non-recoverable relayer error.

### Finding Description
The wallet contract only allows one in-flight transaction at a time (`has_in_flight_tx`) [2](#0-1) , and `rlp_execute` compares the Ethereum-style signed transaction's `nonce` against the contract's on-chain `nonce` counter at the moment the receipt actually executes [3](#0-2) . This is the same shape of bug as the Venus liquidation issue: the value being checked (`expected_nonce`, analogous to `borrowBalance`) is read from state at the block/receipt in which the call actually lands, not at the time the user pre-signs the underlying Ethereum-style transaction (analogous to `repayAmount` being computed off-chain ahead of time).

Because a user signs the RLP-encoded Ethereum transaction off-chain with a nonce value fixed at signing time, and the transaction is relayed as a NEAR `FunctionCall`, there is a race: if any other transaction for the same wallet successfully advances `self.nonce` between the time the user signs and the time the relayed call actually executes (for example, a concurrent legitimate relayer, or the same relayer's own earlier in-flight transaction that resolves), the nonce comparison at `internal.rs:357` fails. Per `rlp_execute`'s error-handling branch, an `Error::Relayer(_)` failure — precisely what `InvalidNonce` is — triggers `create_ban_relayer_promise`, permanently revoking the relayer's access key on the wallet account [4](#0-3) .

The design comment explicitly frames this as a fault of a misbehaving relayer ("Relayers should always check the nonce before sending") [5](#0-4) , but — just as in the Venus report where the liquidator cannot guarantee which exact block their transaction lands in — an honest relayer cannot guarantee its nonce-checked call will be the very next one applied against the contract's current stored nonce, because block inclusion order and receipt execution timing are not fully under the relayer's control once multiple transactions are outstanding for the same wallet.

### Impact Explanation
Unlike the Venus report (rated Medium: availability/DoS only, no fund loss, retryable), here a spurious nonce mismatch does not just fail the individual call — it invokes `ban_relayer`, permanently revoking the relayer's `FunctionCall` access key from the wallet account [6](#0-5) . This is a harsher, non-retryable consequence than the Venus liquidation failure: a benign timing race causes the relayer's authorization to be destroyed, which can render the ETH-implicit account's registered relayer path permanently unusable until a new relayer key is manually re-registered (itself requiring the wallet's own signature and going through the same at-risk nonce path).

### Likelihood Explanation
This requires a scenario where more than one relayer-submitted, wallet-signed transaction for the same account can be in flight or racing at nonce-check time. Given the explicit one-in-flight-transaction guard (`has_in_flight_tx`), the primary window is between when a user (or an alternate relayer) signs a transaction off-chain and when it is submitted, if another transaction for the same wallet completes first and advances the nonce. Likelihood is bounded by this design guard, which is why the report is presented as a plausible design gap analog rather than a definitively demonstrated exploit within this codebase.

### Recommendation
Do not treat every nonce mismatch inside `rlp_execute` as an unconditionally fatal relayer offense warranting an irreversible ban. Consider: (1) tolerating a nonce that is behind current-but-was-valid-at-signing-time within some bound, similar to the recommended shortfall-based looser check in the Venus report, or (2) separating "nonce reused / clearly replayed" (ban-worthy) from "nonce stale due to ordinary state advancement between signing and inclusion" (retry-worthy, no ban), so an honest relayer racing against normal, non-malicious state progression is not permanently locked out.

### Proof of Concept
1. Deploy the Wallet Contract as global code for an ETH-implicit account and register a relayer key as in `test_register_relayer` [7](#0-6) .
2. Have the user sign an RLP transaction with `nonce = N` at time T0, based on `get_nonce()` observed at T0.
3. Before that call executes, submit and successfully execute another transaction for the same wallet contract that advances `self.nonce` past `N` (e.g., another action from a second relayer, or an earlier queued call resolving out of the order assumed by the user at signing time).
4. Submit the RLP transaction signed at step 2; `validate_tx_relayer_data` observes `expected_nonce != N` and returns `Error::Relayer(RelayerError::InvalidNonce)` [1](#0-0) .
5. `rlp_execute` sees the `Error::Relayer(_)` variant and calls `create_ban_relayer_promise`, permanently revoking the relayer's key [4](#0-3) , even though the relayer behaved honestly and merely lost a benign race against normal on-chain nonce advancement.

async fn test_register_relayer() -> anyhow::Result<()> {
    let TestContext { worker, mut wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let relayer_pk = wallet_contract.register_relayer(&worker).await?;
    let key = wallet_contract.inner.as_account().view_access_key(&relayer_pk).await?;
    match &key.permission {
        AccessKeyPermission::FunctionCall(access) => {
            assert_eq!(access.allowance, None);
