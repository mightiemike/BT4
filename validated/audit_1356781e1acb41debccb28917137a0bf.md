### Title
`ensure_match_transaction_info` never checks state/hot-state/position checkpoint hashes, allowing replay-verify to accept a divergent committed state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single sanity check used by replay/verification tooling to assert that a freshly re-executed transaction output matches the transaction info that was actually committed to the ledger accumulator. It checks status, gas used, write-set hash, and event root hash, but by its own documented `TODO`, it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This means any divergence in the state Merkle root (main state, hot state, or the new native-position tree) between local execution and the authenticated on-chain `TransactionInfo` is silently ignored by every caller of this function.

### Finding Description
`TransactionInfo` (V1) commits multiple root hashes into the transaction accumulator that consensus signs off on: `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` [1](#0-0) . These are the actual state-commitment fields — the whole point of accumulator/ledger-info verification is to bind a version to these roots.

`ensure_match_transaction_info` is the function that is supposed to validate a locally-recomputed `TransactionOutput` against the authenticated `TransactionInfo` for a version. It validates status, gas, write-set hash, and event root hash, but explicitly skips the checkpoint hashes, with an inline comment acknowledging the gap: [2](#0-1) 

The comment says verbatim: *"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."*

This function is the sole verification gate used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes transactions from backup/archive data and calls `ensure_match_transaction_info` to decide pass/fail [3](#0-2) . It is also used by `aptos-debugger` and the Move CLI (per earlier grep results) for similar replay/verification purposes.

Because the write-set hash check (`state_change_hash`) only covers the transaction's own write set, not the resulting Merkle-tree root that the write set is applied into, a bug in state-checkpoint computation (e.g. in `DoStateCheckpoint`, `position_summary_at_commit`, or the trading-native root computation gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`) would go completely undetected by any tool relying on this comparator.

### Impact Explanation
This breaks a core proof-integrity invariant: an authenticated, accumulator-committed root (state root, hot-state root, or native-position root) can silently diverge from what local execution actually produces, and the standard replay-verification tooling will report success anyway. Any hard-fork-only divergence, storage bug, or malicious/erroneous root computation in the state-checkpoint pipeline for main state, hot state, or the new native-position tree would not be caught by replay verification — which is exactly the safety net meant to detect exactly this class of consensus-vs-storage divergence. This directly matches the "wrong accumulator root ... accepted as valid" and "hard-fork-only divergence during commit, replay ... verification" impact categories, since replay/verify tooling is one of the few defenses against such state-commitment corruption reaching mainnet undetected.

### Likelihood Explanation
The gap is triggered automatically any time `ensure_match_transaction_info` is invoked with a `TransactionInfoV1` that carries checkpoint hashes — no attacker interaction is required, and no privileged assumption is needed; it's a passive verification omission. The likelihood of the omission itself is certain (confirmed by code and the author's own TODO comment); the resulting *practical* impact depends on some other bug independently causing a state-root divergence, which this code fails to catch. This is a reduced-detection / defense-in-depth gap rather than a bug that itself corrupts state, but it materially increases the risk that a mainnet state-commitment bug (especially in the newly added trading-native / hot-state / position-tree roots) goes unnoticed by replay tooling before or after a hard fork.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, and when present, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, against values recomputed from the locally re-executed chunk's `StateCheckpointOutput`/`DoStateCheckpoint` results, mirroring how `assemble_transaction_infos` builds these fields at commit time [4](#0-3) . At minimum, gate enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on completing this validation, as the code comment itself instructs.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or `HOT_STATE_ROOT_IN_TXN_INFO`) so `TransactionInfoV1.position_state_checkpoint_hash` (or `hot_state_checkpoint_hash`) is populated and accumulator-committed.
2. Introduce (or trigger via an independent bug) a divergence between the locally re-computed position/hot-state root and the committed `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` in the archived `TransactionInfo`.
3. Run `db-tool replay-on-archive`, which calls `execute_and_verify` → `ensure_match_transaction_info` [5](#0-4) .
4. Because `ensure_match_transaction_info` never compares the checkpoint-hash fields, the call returns `Ok(())` even though the state root diverges, and the replay tool reports the chunk as verified successfully — masking the state-commitment divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
