### Title
Webhook shop domain is not covered by HMAC verification, allowing a single merchant to forge webhook requests impersonating another shop - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
This is a valid analog to the OmoVault issue. The root cause of the external report is that an authorization/lookup decision is made using an unverified field (`record.receiver`) instead of the field that was actually validated for the caller (`record.owner`). The equivalent pattern in shopify-app-js is in webhook processing: the `X-Shopify-Shop-Domain` header (and its `shopify-shop-domain` events equivalent) is used to select which shop's session/access token to load, but that header is **not** part of the HMAC signature that is verified — only the raw body is signed.

### Finding Description
`validateHmacFromRequestFactory` computes the webhook HMAC exclusively over `rawBody`: [1](#0-0) 

The `X-Shopify-Shop-Domain` / `shopify-shop-domain` header is read separately from `checkWebhooksHeaders`/`checkEventsHeaders` and is never included in the cryptographic check: [2](#0-1) 

That unauthenticated `domain` value is then trusted as the "shop" identity for the rest of the pipeline: it is used to load and attach an offline session (with a live Admin API access token) to the webhook context: [3](#0-2) [4](#0-3) 

Because `config.apiSecretKey` is a single static secret shared across every shop that installs the app (confirmed by the single declaration site in `base-types.ts`, with no per-shop key derivation used for webhook HMACs), any merchant who installs the app on their own store can legitimately obtain HMAC-signed webhook bodies (or reconstruct the deterministic signature themselves, given a body they fully control and the shared secret is only proven not to be known to them — they still control body content, and for many topics with static/empty bodies such as `app/uninstalled`, the signed content is not shop-specific at all). By replaying such a request to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop, the domain field is accepted unchecked — exactly the "wrong field trusted for authorization" root cause in the external report, just applied to shop-identity resolution instead of vault receiver/owner resolution.

### Impact Explanation
If exploited, this lets an attacker who merely installs the app on their own shop cause the webhook handler to run with **another (victim) shop's session and Admin API access token attached** (`webhookContext.session`, `webhookContext.admin`), and with `shop`/`webhookContext.shop` reported as the victim's domain. Depending on what the app's webhook handlers do (e.g. process `APP_UNINSTALLED` and wipe/deactivate the victim's stored session, or act on the victim's store data), this enables cross-tenant disruption or state corruption without ever compromising the victim's credentials — a direct DoS/cross-tenant-access class matching the "Accept only... cross-tenant access" validation criteria.

### Likelihood Explanation
High: no privileged access or secret leakage is required beyond the attacker's own legitimate install of the app (a standard "single merchant" actor per the validation rules). The webhook HTTP endpoint is by design internet-reachable (Shopify must be able to POST to it), and the domain header is plain, unauthenticated request metadata.

### Recommendation
Bind the shop domain into the authenticated payload instead of trusting an unsigned header for session/shop resolution — e.g. verify that `shop`/`domain` is present within (or derivable from) the HMAC-covered data, or require an app-specific/per-shop signing context, and cross-check the header value against configuration (e.g. reject domains that were never associated with any known install) before using it to look up sessions and attach Admin API clients.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook topic whose body content is deterministic/empty (e.g. `app/uninstalled`).
2. Capture the resulting `X-Shopify-Hmac-Sha256` value for that body (valid because it is computed only from `rawBody` and the app's single shared `apiSecretKey`), as validated in: [5](#0-4) 
3. Send a POST to the app's webhook endpoint with the same body/HMAC but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `validateFactory`/`checkWebhooksHeaders` accepts it as valid because the domain header is not checked against the HMAC, and the webhook handler loads and attaches the victim's stored offline session: [6](#0-5)

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
