## Title
Missing Zero-Check Before Field Inversion in BN128 Tower-Extension Arithmetic (`Fp2`/`Fp6`/`Fp12`) - (File: `crypto/src/main/java/org/tron/common/crypto/zksnark/Fp2.java`, `Fp6.java`, `Fp12.java`)

### Summary
java-tron's BN128 pairing library contains the exact bug class described in the external report: the tower-extension field inversion routines compute an intermediate field element and call `.inverse()` on it without first checking whether that intermediate value is zero. This mirrors `fq2.rs`/`fq6.rs`/`fq12.rs` in zksync-crypto. This code is not a vendored curiosity — it backs the public, unprivileged-user-reachable `BN128Add`/`BN128Mul`/`BN128Pairing` TVM precompiled contracts at addresses `0x06`/`0x07`/`0x08`.

### Finding Description
`Fp2.inverse()` computes `t2 = t0.sub(Fp.NON_RESIDUE.mul(t1))` and then calls `t2.inverse()` with no check that `t2` is non-zero: [1](#0-0) 

`Fp6.inverse()` similarly computes `t6 = a.mul(c0).add(...).inverse()` without checking `t6` (an `Fp2`) for zero before calling `.inverse()`: [2](#0-1) 

`Fp12.inverse()` computes `t2 = t0.sub(t1.mulByNonResidue())` (an `Fp6`) and calls `t3 = t2.inverse()` with no zero check: [3](#0-2) 

At the base of the tower, `Fp.inverse()` simply calls `BigInteger.modInverse(P)`: [4](#0-3) 

`BigInteger.modInverse` throws `ArithmeticException: BigInteger not invertible` when invoked on zero (`gcd(0, P) = P ≠ 1`). Because none of `Fp2.inverse`, `Fp6.inverse`, or `Fp12.inverse` guard against a zero intermediate before recursing into the next inversion, a degenerate intermediate value anywhere in the tower propagates down to an unguarded `Fp.inverse()` call and throws an uncaught `ArithmeticException`.

Unlike `BN128.toAffine()`, which does explicitly guard `z.inverse()` behind an `isZero()` check: [5](#0-4) 

...no equivalent guard exists inside the `Fp2`/`Fp6`/`Fp12` tower-field inversion routines themselves, or at their call sites in `PairingCheck.finalExponentiation()`, which unconditionally calls `el.inverse()` on the accumulated Miller-loop product: [6](#0-5) 

This `finalExponentiation` is invoked from `PairingCheck.run()`, which is the core of the `BN128Pairing` precompiled contract: [7](#0-6) 

That precompiled contract is directly reachable by any unprivileged account through a `CALL` opcode to TVM address `0x0000...0008` from a smart contract, with attacker-fully-controlled G1/G2 point pair bytes: [8](#0-7) 

### Impact Explanation
If an attacker can craft (or the natural arithmetic of certain pairs of curve points can produce) an intermediate field value of zero at any level of the `Fp2`/`Fp6`/`Fp12` tower during Miller-loop accumulation or final exponentiation, the precompiled-contract call throws an unhandled `ArithmeticException` inside `PrecompiledContracts.BN128Pairing.execute()` rather than returning the expected `Pair.of(false, EMPTY_BYTE_ARRAY)` failure result that other malformed-input paths return (e.g., invalid point decoding at lines 1013/1028). This is an invalid-state condition: instead of a controlled revert/failure return value understood uniformly by all nodes, an unexpected runtime exception is thrown from deep inside VM execution of a public precompile. Depending on how this exception is caught (or not) further up the TVM execution stack, this can manifest as inconsistent node behavior around this code path (or a node crash) compared to nodes that handle it differently, which is a correctness/availability risk for a security-critical, publicly reachable contract used for zk-SNARK/BLS-style verification on-chain.

### Likelihood Explanation
The vulnerable pattern is present in production code reachable by any unprivileged account issuing a transaction that invokes precompile `0x08` (or via `0x06`/`0x07` if their computations ever hit an unguarded intermediate zero through the same `Fp` tower). No special privileges, mocked services, or internal-only code paths are involved — the entire `BN128Fp`/`BN128G2`/`PairingCheck` call chain is standard, user-triggerable EVM/TVM behavior. The exact numeric inputs required to force an intermediate zero at the `Fp2`/`Fp6`/`Fp12` inversion sites were not concretely derived within this analysis (this would require solving for specific curve points/degenerate encodings that hit `t2==0`/`t6==0`/`t3==0`), so likelihood of triggering it with a simple, off-the-shelf input is not proven — only the code-level absence of the guard (matching the reported bug class 1:1) is confirmed.

### Recommendation
Add explicit zero checks before every internal `.inverse()` call in the tower-extension arithmetic:
- In `Fp2.inverse()`, check `t2.isZero()` before calling `t2.inverse()`.
- In `Fp6.inverse()`, check the computed `Fp2` value before `.inverse()`.
- In `Fp12.inverse()`, check `t2.isZero()` before calling `t2.inverse()`.

Have each `inverse()` method return a sentinel (e.g., `null`) or throw a well-defined, caught exception when the operand (or intermediate) is zero, and ensure `PairingCheck.finalExponentiation()` and precompile `execute()` methods catch and convert that into the standard `Pair.of(false, EMPTY_BYTE_ARRAY)` failure response, consistent with how other malformed-input cases are already handled in `PrecompiledContracts.BN128Pairing`/`BN128Addition`/`BN128Multiplication`.

### Proof of Concept
Not concretely constructed: producing calldata for `BN128Pairing`/`BN128Multiplication`/`BN128Addition` (precompile addresses `0x06`/`0x07`/`0x08`) that forces one of `Fp2.inverse()`'s `t2`, `Fp6.inverse()`'s `t6`, or `Fp12.inverse()`'s `t2` to be exactly zero requires solving specific algebraic conditions over the BN128 tower fields, which was not performed here. The finding is based on confirmed static absence of the zero-guard in the exact functions analogous to the reported `fq2.rs`/`fq6.rs`/`fq12.rs` bug, and confirmed reachability of these functions from unprivileged, user-supplied precompile input.

  public static class BN128Pairing extends PrecompiledContract {

    private static final int PAIR_SIZE = 192;

    @Override
    public long getEnergyForData(byte[] data) {
      if (VMConfig.allowTvmIstanbul()) {
        return getEnergyForDataIstanbul(data);
      }
      if (data == null) {
        return 100000;
      }
      return 80000L * (data.length / PAIR_SIZE) + 100000;
    }

    private long getEnergyForDataIstanbul(byte[] data) {
      if (data == null) {
        return 45000;
      }
      return 34000L * (data.length / PAIR_SIZE) + 45000;
    }

    @Override
    public Pair<Boolean, byte[]> execute(byte[] data) {

      if (data == null) {
        data = EMPTY_BYTE_ARRAY;
      }

      // fail if input len is not a multiple of PAIR_SIZE
      if (data.length % PAIR_SIZE > 0) {
        return Pair.of(false, EMPTY_BYTE_ARRAY);
      }

      PairingCheck check = PairingCheck.create();

      // iterating over all pairs
      for (int offset = 0; offset < data.length; offset += PAIR_SIZE) {

        Pair<BN128G1, BN128G2> pair = decodePair(data, offset);

        // fail if decoding has failed
        if (pair == null) {
          return Pair.of(false, EMPTY_BYTE_ARRAY);
        }

        check.addPair(pair.getLeft(), pair.getRight());
      }

      check.run();
      int result = check.result();

      return Pair.of(true, new DataWord(result).getData());
    }

    private Pair<BN128G1, BN128G2> decodePair(byte[] in, int offset) {

      byte[] x = parseWord(in, offset, 0);
      byte[] y = parseWord(in, offset, 1);

      BN128G1 p1 = BN128G1.create(x, y);

      // fail if point is invalid
      if (p1 == null) {
        return null;
      }

      // (b, a)
      byte[] b = parseWord(in, offset, 2);
      byte[] a = parseWord(in, offset, 3);

      // (d, c)
      byte[] d = parseWord(in, offset, 4);
      byte[] c = parseWord(in, offset, 5);

      BN128G2 p2 = BN128G2.create(a, b, c, d);

      // fail if point is invalid
      if (p2 == null) {
        return null;
      }

      return Pair.of(p1, p2);
    }
  }
