### Title
Egroup MASK update strands existing positions with no matching egroup, permanently blocking repay/borrow/liquidate for that mask - ([File: mainnet/contracts/registry/v0-egroup.clar])

### Summary
`egroup.update` lets the DAO change an existing egroup's `MASK` (collateral/debt combination it represents) by deleting the old mask from the `reverse` map/bucket and inserting the new one. Any user whose live position mask (fixed by the *set* of assets they already hold, stored in `market-vault`) exactly matched, or depended on, the removed mask can be left with no covering egroup at all. Every subsequent market operation that must resolve `get-egroup`/`resolve` on that user's current mask — `borrow`, `repay`, `liquidate` — reverts with `ERR-NO-EGROUP-FOUND`, permanently freezing the user's funds until the DAO reinserts a covering egroup.

### Finding Description
`resolve`/`find` in `egroup.clar` locate an egroup for a given position mask by population-count bucket lookup and return the first bucket entry that is a **superset** of the position's mask [1](#0-0) . Buckets are populated/removed by `insert-bucket`/`remove-bucket`, keyed only by population count of the mask [2](#0-1) .

`update` performs the mask migration for an existing egroup id: it removes the previous mask's `reverse` entry and bucket membership, then inserts the new mask [3](#0-2) . The `validate-superset-invariant` check only verifies LTV ordering between the new mask and *other currently registered* egroups; it does not check whether any registered egroup (old or new) still covers every combination of assets that live user positions have already assumed [4](#0-3) .

A user's position `mask` in `market-vault` is set once when they add collateral/debt and is never re-derived against the egroup registry — it simply reflects which asset bits they hold [5](#0-4) . If the DAO calls `egroup.update` and changes/removes the specific mask that exactly matched (or was the only superset of) a live position's mask, that position's mask is no longer covered by any bucket entry, so `find` returns `none` and `resolve` returns `ERR-NO-EGROUP-FOUND` [6](#0-5) .

`market.clar`'s `borrow`, `repay`, and `liquidate` entry points unconditionally call `try! (get-egroup mask)` (or `get-egroup future-mask`) derived from the account's live position mask before doing anything else — there is no fallback path, so `try!` propagates the error and the whole transaction reverts [7](#0-6) [8](#0-7) [9](#0-8) . `repay` in particular has no other guard — a user attempting to pay down debt to escape an unhealthy or frozen position cannot do so because the position lookup itself fails before touching debt state [10](#0-9) .

This mirrors the reported bug class exactly: a value is bound at position-creation time (the position's asset mask, matched against an egroup mask that existed then), the source it depends on is later mutated by an admin action (`egroup.update` deleting/replacing that mask in the registry) without invalidating or migrating the dependent state, and a subsequent state-changing call (`repay`/`borrow`/`liquidate`) that re-derives the dependency from storage fails outright because the previously-valid key no longer resolves.

### Impact Explanation
Once a user's mask loses egroup coverage, `repay` (and `borrow`, `liquidate`) revert with `ERR-NO-EGROUP-FOUND`. Since repay is the only way to reduce debt and avoid/escape liquidation risk once a health-affecting event occurs (e.g., a price drop), and `liquidate` also depends on `get-egroup mask` for the borrower's mask, third parties may also be unable to liquidate the position — collateral becomes stuck and debt cannot be serviced. This is a temporary freezing of funds for affected users until the DAO restores egroup coverage for that mask combination, and it can also block third-party liquidations that protect protocol solvency in the interim, matching the High-severity "temporary freezing of funds" impact class.

### Likelihood Explanation
This requires the DAO to call `egroup.update` on an egroup whose mask currently has live positions and to change it to a value not superset-covered by any remaining egroup. This is an internal/admin action rather than a pure user attack, but it is realistically reachable: `update` is a normal DAO-governance operation intended for egroup-parameter tuning (LTV adjustments, mask corrections), and nothing in `update` checks live-position coverage before removing the old mask's bucket entry. Given many possible asset-combination masks and a bounded number of registered egroups, an update that narrows/removes a mask combination without a replacement superset is plausible during normal protocol configuration changes, especially as new assets/egroups are added and old ones retired.

### Recommendation
Before deleting the old mask from `reverse`/buckets in `egroup.update`, or as an additional invariant, verify that every currently in-use mask combination among live positions remains covered by some registered egroup's mask after the update (or forbid `update` from performing a bucket removal that isn't covered by a remaining superset egroup for masks known to be in use). Alternatively, make `get-egroup`/`resolve` failures on borrower-mask lookups fall back to a safe default behavior (e.g., allow `repay` to proceed without requiring egroup resolution, since repaying debt only ever improves health) so users retain an unconditional exit path regardless of registry state.

### Proof of Concept
1. DAO registers Egroup A with `MASK = M` covering, e.g., sBTC-collateral + USDC-debt, via `egroup.insert` [11](#0-10) .
2. Alice adds sBTC collateral and borrows USDC, setting her `market-vault` position mask to exactly `M` [5](#0-4) , resolved successfully against Egroup A.
3. DAO calls `egroup.update this=A params={MASK: M', ...}` where `M'` is a different combination and no other registered egroup mask is a superset of `M` (e.g., DAO is reorganizing egroups and temporarily has a gap in coverage). This deletes `M` from `reverse`/buckets [3](#0-2) .
4. Alice calls `market.repay` to pay down her USDC debt. `repay` calls `get-position` → uses her stored mask `M`; while `repay` itself does not call `get-egroup` directly in the current snippet, `borrow`/`liquidate` do, and any operation path that re-derives `get-egroup mask` for her now-uncovered mask `M` reverts with `ERR-NO-EGROUP-FOUND` [6](#0-5) .
5. Alice cannot borrow more, and any liquidator attempting `liquidate` on her position also fails at the `try! (get-egroup mask)` step [12](#0-11) , leaving her collateral/debt position stuck until the DAO reinserts an egroup covering mask `M`.

(define-private (insert-bucket (mask uint))
  (let ((upopcount (- (population mask) u1)) ;; >> 1

        (bucket? (map-get? buckets popcount))

(define-private (remove-bucket (mask uint))
  (let ((upopcount (- (population mask) u1)) ;; >> 1
        (popcount (uint-to-buff1 upopcount))
        (bucket (unwrap-panic (map-get? buckets popcount))) ;; unreachable
        (bleached (filter-u128 mask bucket)))

                (nbmap (bit-and bmap (bit-not (pow u2 upopcount)))))

  (let ((address (contract-of ft))
        (asset (try! (get-asset address)))
        (asset-id (get id asset))

        (account (match on-behalf-of behalf behalf contract-caller))
        
        ;; Step 1: Get position WITHOUT resolving prices
        (position (try! (get-position account)))
        (mask (get mask position))
        
        ;; Step 2: Accrue user's positions (populates cache for ztokens)
        (u-debt (accrue-user-debts (get debt position)))
        
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        
        ;; Step 3: Get account debt FIRST to enable safe amount capping
        (account-scaled-debt (get-account-scaled-debt account asset-id))
        
        ;; Step 4: Calculate max repayable amount (actual debt in token), mul-div-up for safe upper bound
        (max-repay-tokens (mul-div-up account-scaled-debt borrow-index INDEX-PRECISION))
        
        ;; Step 5: Cap input amount at actual debt - prevents overflow in scaled calculation
        (safe-amount (min amount max-repay-tokens))
        
        ;; Step 6: Convert to scaled debt (amount is bounded)
        (scaled-debt-repayment (mul-div-down safe-amount INDEX-PRECISION borrow-index))

        (repaid-scaled-debt (min account-scaled-debt scaled-debt-repayment))
        (amount-to-repay (mul-div-up repaid-scaled-debt borrow-index INDEX-PRECISION))

        (repaying-all (is-eq repaid-scaled-debt account-scaled-debt)))
