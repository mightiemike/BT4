### Title
`liquidate-multi` swallows a downstream bad-debt-socialization failure while earlier repay/collateral-seizure sub-calls already committed - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` maps `call-liquidate` (a plain in-contract call, not `contract-call?`) over a batch of positions and always returns `(ok (map call-liquidate positions))` [1](#0-0) , so the *outer* transaction always succeeds regardless of any per-position `(err ...)`. Inside `liquidate`, several cross-contract mutations (`vault-system-repay`, `debt-remove-scaled`, `collateral-remove`) are executed and individually committed via `contract-call?` **before** a later bad-debt-socialization step that can itself fail and force `liquidate` to return `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [2](#0-1) [3](#0-2) . Because Clarity's atomic rollback is scoped to the outermost public call's overall result, and that outermost call (`liquidate-multi`) reports `ok`, the already-committed repay/seizure effects from the "failed" position persist even though the caller sees an `err` entry for it — the exact class of bug described in the report (sub-state committed, then a later step fails and the failure signal is misreported/absorbed instead of reflecting reality).

### Finding Description
`liquidate` performs, in order:
1. `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` — debt asset pulled from liquidator into the vault, vault debt reduced. This is a `contract-call?`, so it is individually atomic and, on success, is committed as part of the enclosing call.
2. `(try! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-to-remove debt-aid))` — removes the primary debt entry from the borrower's obligation [4](#0-3) .
3. `(try! (contract-call? .v0-market-vault collateral-remove borrower coll-final collateral-ft coll-aid actual-receiver))` — seizes collateral and transfers it to the liquidator [5](#0-4) .
4. Only afterwards, if `no-collateral-left`, does `liquidate` fold over the borrower's remaining debts via `socialize-debt-asset` and require `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [3](#0-2) . `socialize-debt-asset` is itself a fold that unwraps into a `failed-status` accumulator on the first failing debt entry, silently absorbing whichever earlier debt entries in the same fold already succeeded [6](#0-5) .

If step 4 fails, `liquidate` returns `(err ...)`. When `liquidate` is invoked directly (single transaction), Clarity's transaction-wide atomicity would normally roll back everything, including steps 1–3. But when invoked through `liquidate-multi` → `call-liquidate` → `liquidate` as a **plain function call** (not `contract-call?`) [7](#0-6) , and `liquidate-multi` unconditionally wraps the whole result list in `(ok ...)`, the *outermost* call succeeds. Clarity only reverts state when the outermost public call itself returns `err`; here it does not. Consequently, steps 1–3 (real repay + real collateral transfer to the liquidator) are committed to chain state even though the caller sees that specific list entry reported as `err`, misrepresenting that nothing happened for that position — mirroring the CVE's "substate committed, then later `record_external_operation`-style step fails, and the failure is reported instead of Succeeded, but the commit already happened."

### Impact Explanation
The borrower's primary debt is repaid and their collateral is transferred out to the liquidator (real value movement) while the secondary debt that was supposed to be written off via bad-debt socialization remains fully outstanding in vault accounting with no backing collateral left. Because `liquidate-multi`'s per-position result is `err`, external tooling / keepers treat that position as "not liquidated" and will not retry the now partially-processed position correctly, leaving unbacked debt permanently stuck in the vault's books — a form of protocol insolvency (unbacked debt) and lost accounting integrity, which is not recoverable by the normal liquidation flow since the position has no more collateral to seize against that residual debt.

### Likelihood Explanation
Requires a borrower position with a `no-collateral-left` condition (i.e., only collateral asset being liquidated, or all other collateral already zero) and at least one other outstanding debt asset such that `socialize-debt-asset`'s fold hits a failure on any iteration (e.g., a transient/expected failure path in `vault-socialize-debt` or `vault-accrue` for one of the remaining debt assets), while triggered via the batch entrypoint `liquidate-multi`. This is reachable by any permissionless caller of `liquidate-multi` and does not require DAO compromise, leaked keys, or oracle manipulation, but does depend on a specific multi-debt-asset, zero-remaining-collateral position existing and one socialization sub-call failing — a non-trivial but realistic combination for a protocol supporting multiple collateral/debt assets per position.

### Recommendation
Do not allow `liquidate-multi` to unconditionally return `(ok ...)` when an individual `liquidate` invocation performed committed cross-contract mutations before failing later in its own execution. Either (a) make `liquidate`'s bad-debt socialization the *first* operation attempted (fail fast before any repay/collateral transfer), or (b) invoke each position's liquidation through an actual `contract-call?` boundary (so a failing sub-call reverts its own effects) instead of a plain in-contract function call, or (c) make the accounting for bad-debt socialization failure non-fatal to the whole `liquidate` call while ensuring the vault bookkeeping and reported result stay consistent with whatever partial state was actually committed.

### Proof of Concept
1. Set up a borrower with two debt positions: `debt-aid` (to be liquidated) and a second debt asset `debt-aid-2`, and a single collateral asset fully covering `debt-aid`'s liquidation such that after seizure `no-collateral-left` evaluates true.
2. Cause `vault-socialize-debt`/`vault-accrue`/`debt-remove-scaled` for `debt-aid-2` inside the `socialize-debt-asset` fold to fail (e.g., a pause state or precondition on the second vault at the time of the call).
3. Call `liquidate-multi` with a list containing this borrower's position (and optionally other unrelated, healthy positions to fill the batch).
4. Observe: `vault-system-repay`, `debt-remove-scaled` (for `debt-aid`), and `collateral-remove` all execute and commit (liquidator receives collateral, vault debt reduced) since they are individual successful `contract-call?`s.
5. `socialize-debt-asset` fails on `debt-aid-2`, causing `liquidate` to return `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`; `call-liquidate` returns this value unmodified; `liquidate-multi` returns `(ok (list ... (err u...) ...))`.
6. Confirm on-chain: the borrower's collateral is gone and `debt-aid` is cleared from their obligation, but `debt-aid-2` remains outstanding with no collateral backing it and no automatic re-processing, while the caller-visible result for that entry is `err`, hiding that state changes already occurred.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
