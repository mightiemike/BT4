## Analysis

The reported Solidity bug is a class of "reward accounting orphaned when the distribution denominator is zero" — `notifyRewardAmount()` credits a period's `totalEmissions` without checking `globalTotalVotes > 0`, so `_distribute()`'s division `ps.totalEmissions * ps.gaugeTotalVotes[_gauge] / ps.globalTotalVotes` can never be reached/claimed and the funds are stranded.

java-tron has a structurally identical pattern in its Super Representative (witness) voter-reward accounting.

### Title
Witness block/transaction-fee rewards are permanently stuck when a witness has zero recorded votes for a cycle - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payBlockReward()` / `payTransactionFeeReward()` unconditionally deposit the voter-share portion of a witness's earnings into `DelegationStore` for the *current cycle*, without checking whether any votes exist for that witness in that cycle. When the per-cycle vote snapshot is `0` (or unset/`REMARK`), the reward can never be claimed by any voter and is never carried forward, permanently orphaning the funds — the same accounting flaw as `Voter.notifyRewardAmount()` crediting `totalEmissions` without checking `globalTotalVotes > 0`.

### Finding Description
`payReward()` computes the SR's brokerage cut and stores the remainder as the voters' reward pool for the current cycle unconditionally: [1](#0-0) 

This value is written via `DelegationStore.addReward(cycle, witnessAddress, value)`, keyed only by cycle and witness address, with no check of the vote total for that cycle: [2](#0-1) 

The per-cycle vote snapshot used as the distribution denominator is set independently, once per maintenance cycle, from the witness's live `voteCount`: [3](#0-2) 
`getWitnessVote()` returns `REMARK` (`-1`) if never set for that cycle, or `0` if the witness genuinely had no votes.

When voters later attempt to claim rewards, `computeReward()` explicitly skips any cycle where the vote total is zero or unset, exactly mirroring the reported `globalTotalVotes == 0` gap: [4](#0-3) 

Under the newer Vi-based algorithm, the same zero-vote condition causes the reward to be silently dropped instead of accumulated into the voter index, with no carry-over mechanism: [5](#0-4) 
and is invoked unconditionally every maintenance cycle for every witness, including those with zero votes: [6](#0-5) 

In both the old and new reward algorithms, the value stored via `addReward()`/`getReward()` for a zero-vote cycle is never zeroed out, refunded, or rolled into a subsequent cycle's pool — it simply remains an unreachable key in `DelegationStore`, functionally identical to `Voter`'s stuck `totalEmissions`.

### Impact Explanation
Block rewards and transaction-fee rewards are core protocol emissions intended to be shared with a witness's voters. Any cycle in which a witness's per-cycle vote snapshot is `0` (e.g., a freshly-applied/registered witness that becomes active before votes are recorded for that cycle, or any witness whose vote count is `0` at the maintenance snapshot boundary) causes that cycle's entire voter-reward share to become permanently unclaimable — no voter can ever redeem it and it is not carried to the next cycle. This is a fund-accounting/invalid-state defect in a widely-exercised, unprivileged-triggerable reward path (any account can become a witness via `WitnessCreateContract`/apply-to-become-witness without special privilege).

### Likelihood Explanation
The zero-vote condition is not an edge case requiring privileged access — it naturally occurs whenever a witness has not yet accumulated votes in a given cycle snapshot (new witnesses, or witnesses whose voters fully unvote), and the reward-crediting functions (`payBlockReward`/`payTransactionFeeReward`) run unconditionally on every block for the active witness set. No special conditions beyond ordinary DPoS operation are needed to hit this path.

### Recommendation
Before crediting `DelegationStore.addReward(cycle, witnessAddress, value)`, verify that the current cycle's vote snapshot (`getWitnessVote(cycle, witnessAddress)`) is greater than zero; if not, either (a) route the full reward to the witness's own allowance via `adjustAllowance` instead of the unclaimable voter pool, or (b) accumulate the reward into a forward-carried balance that gets included once the witness has a non-zero vote snapshot, mirroring the suggested fix of tracking undistributed rewards and carrying them to the next period.

### Proof of Concept
1. Account `W` applies to become a witness (unprivileged action) and is admitted to the active/standby witness set before any votes have been cast for it in the current cycle, so `DelegationStore.getWitnessVote(currentCycle, W) == 0` (or `REMARK` if unset).
2. `W` produces a block; `Manager` calls `MortgageService.payBlockReward(W, value)` → `payReward()` → `delegationStore.addReward(currentCycle, W, voterShare)`.
3. At the next maintenance cycle, if `useNewRewardAlgorithm` is enabled, `DelegationStore.accumulateWitnessVi(currentCycle, W, 0)` runs — since `voteCount == 0`, it only forwards the previous Vi and never folds in `voterShare`.
4. Any voter who later delegates to `W` and calls `withdrawReward()` will compute rewards via `computeReward()`, which for that specific cycle finds `totalVote == 0`/`REMARK` and `continue`s, skipping the credited amount entirely.
5. The `voterShare` deposited in step 2 remains permanently stored under the `cycle-W-reward` key with no code path that ever pays it out or carries it forward — functionally identical to the reported stuck-emissions bug.

```java
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
```

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void addReward(long cycle, byte[] address, long value) {
    byte[] key = buildRewardKey(cycle, address);
    BytesCapsule bytesCapsule = get(key);
    if (bytesCapsule == null) {
      put(key, new BytesCapsule(ByteArray.fromLong(value)));
    } else {
      put(key, new BytesCapsule(ByteArray
          .fromLong(ByteArray.toLong(bytesCapsule.getData()) + value)));
    }
  }

    BytesCapsule bytesCapsule = get(buildRewardKey(cycle, address));
    if (bytesCapsule == null) {
      return 0L;
    } else {
      return ByteArray.toLong(bytesCapsule.getData());
    }
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
