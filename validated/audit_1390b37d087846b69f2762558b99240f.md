### Title
PoX-4 reward-set parsing silently coerces malformed `signer` buffers to an all-zero key, letting unrelated minority stackers merge weight under one unownable signing key - (File: `stackslib/src/chainstate/nakamoto/signer_set.rs`)

### Summary
`RawRewardSetEntry::from_pox_4_tuple` reads the `signer` field returned by the PoX-4 contract as a `(buff 33)` Clarity value and expects it to be exactly `SIGNERS_PK_LEN` (33) bytes — a valid compressed secp256k1 public key. When the length doesn't match, instead of rejecting the entry (as every other field in this function does via `ChainstateError::Expects`), the code silently substitutes an all-zero 33-byte array and continues to build a `NakamotoSignerEntry` from it. [1](#0-0) 

### Finding Description
`(buff 33)` in Clarity is a *maximum*-length constraint, not an exact-length constraint — the code even documents this itself: [2](#0-1) 

So a staker calling PoX-4's `stack-stx`/`stack-aggregation-commit`/etc. can supply a `signer-key` argument shorter than 33 bytes (e.g. a 0- or 1-byte buffer) and it type-checks fine and is stored verbatim in the reward-set map. When `from_pox_4_tuple` later reads it back:

```
let pk_bytes = if signer.len() == SIGNERS_PK_LEN {
    ...
} else {
    [0; SIGNERS_PK_LEN]
};
```

any non-33-byte buffer collapses to the same sentinel value, `[0u8; 33]`, which is not a valid point on the secp256k1 curve and therefore corresponds to **no private key that anyone controls**.

This `signer` field becomes `entry.signer_key` in the downstream aggregation step, `make_signer_set` (in `stackslib/src/chainstate/stacks/boot/mod.rs`), which groups reward-set entries **by signing key** and sums their `amount_stacked`: [3](#0-2) 

Because the map key is the (attacker-influenced) `signing_key` rather than the stacker's principal, any number of unrelated, minority stakers can each submit a malformed `signer-key` buffer and have their individually-below-threshold stacked amounts merged into one artificial "signer" entry that reaches `weight >= 1` (or crosses the pox-5 reward-slot threshold in the analogous `pox_5_make_signer_set` aggregation at `stackslib/src/chainstate/nakamoto/signer_set.rs:852-856`). The resulting `NakamotoSignerEntry` is then written into the `.signers` boot contract and used to compute `total_signing_weight` / the block-approval threshold in `NakamotoBlockHeader::compute_voting_weight_threshold` and `verify_signer_signatures`. [4](#0-3) 

The equality this breaks: a `NakamotoSignerEntry.signing_key` in the reward/signer set is supposed to correspond 1:1 to a single stacker's real public key that they alone control, and the *total_weight* used for the two-thirds/70% approval threshold is supposed to only include weight from keys capable of producing valid signatures. With this bug, several unprivileged, unrelated stackers can inflate a single, unownable signing key's weight (and thus `total_weight`), consuming reward slots / voting weight that no private key can ever sign for.

### Impact Explanation
This is a minority-triggerable divergence in the sortition/signer-set membership function — the "wrong set" case explicitly in scope: weight is attributed to a signing key that does not belong to (and cannot be controlled by) any of the contributing stackers. Consequences include:
- Inflating `total_weight` with unsignable weight, making the `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` (70%) harder or impossible for the legitimate signer set to reach, since the block-approval threshold in `compute_voting_weight_threshold` is computed from `total_weight` including this bogus entry — degrading availability of block approval.
- Multiple uncoordinated, individually sub-threshold minority stakers combining into a nominal "signer" that displaces a legitimately-elected signer's reward slot, since `pox_5_make_signer_set`/`make_signer_set` allocate a bounded number of slots (`reward_slots`) by weight.

This matches the CVSS High "minority-triggerable sortition/VRF/static-validation divergence" category: the attack requires no majority collusion, only that a handful of otherwise-independent stakers each submit a slightly malformed transaction.

### Likelihood Explanation
Likelihood is moderate-to-high because:
- Triggering it only requires calling a public PoX-4 stacking function with a `signer-key` buffer shorter than 33 bytes — no special privileges, no majority stake, and no cooperation beyond independently choosing to submit malformed buffers.
- The type system does not prevent it, by the code's own admission ("(buff 33) only enforces max size, not min size").
- The only constraint is that each participant must independently discover/exploit the same fallback behavior, which is straightforward once known.

### Recommendation
In `RawRewardSetEntry::from_pox_4_tuple`, when `signer.len() != SIGNERS_PK_LEN`, return `Err(ChainstateError::Expects(...))` (consistent with how `total-ustx` and `stacker` are validated in the same function) instead of substituting `[0; SIGNERS_PK_LEN]`. This ensures malformed signer-key buffers abort reward-set computation for that entry (or the whole cycle) rather than being silently coerced into a shared sentinel identity that multiple unrelated stakers can collide into.

### Proof of Concept
1. Stacker A calls PoX-4 `stack-stx` (or `stack-aggregation-commit`) supplying `signer-key` as a 1-byte buffer `0x00`, with `amount-ustx` just under the per-signer weight-1 threshold.
2. Stacker B (unrelated, independent) does the same with a different 1-byte (or any non-33-byte) `signer-key` buffer and a similarly sub-threshold amount.
3. At reward-set computation time, `RawRewardSetEntry::from_pox_4_tuple` reads both entries' `signer` fields; since `signer.len() != 33` for both, `pk_bytes` becomes `[0u8; 33]` for both entries.
4. `Self::make_signer_set` groups by `signing_key` and sums `amount_stacked` for both entries into the same `BTreeMap` bucket keyed on `[0u8; 33]`, potentially producing `weight >= 1` for a `NakamotoSignerEntry { signing_key: [0;33], ... }` that neither A nor B (nor anyone) can produce a valid signature for.
5. This entry is written to the `.signers` contract and included in `total_signing_weight` used by `NakamotoBlockHeader::compute_voting_weight_threshold`/`verify_signer_signatures`, consuming a reward slot and inflating the unsignable portion of `total_weight`.
