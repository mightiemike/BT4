## Title
Missing zero-address (null address) validation in `AccountPermissionUpdateActuator` allows permanent loss of account control - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The `AccountPermissionUpdateActuator`, which handles the `AccountPermissionUpdateContract` used to configure multi-signature owner/witness/active permissions on a TRON account, validates permission key addresses only through `DecodeUtil.addressValid()`, a purely format-level check (length + address prefix byte). It never rejects the all-zero address. This is the direct analog of the reported `Proxy._setOwner` bug: format validation is performed, but there is no explicit check that the target address is not `address(0)`, which can lead to permanent, irreversible loss of control.

### Finding Description
`checkPermission()` validates each `Key` in a `Permission` only against `DecodeUtil.addressValid()`: [1](#0-0) 

`DecodeUtil.addressValid()` only checks that the address is non-empty, exactly 21 bytes, and starts with the correct network prefix byte — it does not exclude the all-zero address (`0x41` followed by 20 zero bytes), which is syntactically a "valid" TRON address: [2](#0-1) 

Because of this, a `Permission.Key` with address equal to the zero address passes `checkPermission()` as long as weight/threshold rules are satisfied. `validate()` performs no additional check on the owner/witness/active permission key addresses beyond `checkPermission()`: [3](#0-2) 

`execute()` then unconditionally persists the new permission set to the account via `AccountCapsule.updatePermissions()`: [4](#0-3) [5](#0-4) 

If a user (or a wallet/SDK with a bug that defaults an unset address field to null, exactly the scenario called out in the original report) submits an `AccountPermissionUpdateContract` whose `Owner` permission contains a key with the zero address and sufficient weight/threshold, the transaction validates successfully and is committed on-chain. Since no private key is realistically known for the null address, the account's owner permission (and, analogously, witness/active permissions) becomes permanently uncontrollable — the account owner can never again submit a valid `AccountPermissionUpdateContract` to fix it, because doing so itself requires satisfying the now-broken owner permission.

### Impact Explanation
This results in permanent, irreversible loss of control over an account's permission structure, directly analogous to the `Proxy._setOwner` zero-address bug in the original report. Consequences include:
- Permanent lock-out from `AccountPermissionUpdateContract` (no way to ever update permissions again).
- If witness permission is bricked in this way, the witness can no longer produce/sign blocks with a valid key, disrupting consensus participation for that node.
- If the sole active/owner permission key set is the zero address with the account's full authority, funds and resources controlled by that account become effectively frozen/unspendable through the standard permission path.

This falls under "unauthorized account operation / asset or accounting corruption" via a standard broadcast transaction path, reachable by any account holder (including unintentionally via faulty client tooling), with no privileged access required.

### Likelihood Explanation
Likelihood is moderate: the multi-sign feature must be enabled (`getAllowMultiSign() == 1`), which is already true on mainnet. Triggering the bug requires only constructing and broadcasting a normal `AccountPermissionUpdateContract` — no special privileges, keys, or network position are needed. The report explicitly notes that some client libraries can default unset address fields to null, making accidental triggering plausible in addition to any deliberate self-inflicted, or social-engineered account bricking.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()` (and anywhere else `DecodeUtil.addressValid()` is relied upon as the sole address check for permission-critical fields), explicitly reject the all-zero address for each `Key.getAddress()`, in addition to the existing length/prefix validation. Consider adding a shared helper (e.g., `DecodeUtil.addressValid()` variant or a new `isZeroAddress()` check) applied consistently to all actuators that persist addresses which grant control/authority over on-chain accounts, resources, or governance state, per the general recommendation in the report to add null/zero-address checks throughout the codebase.

### Proof of Concept
1. Create/own an account `A` with multi-sign enabled (`AllowMultiSign == 1`).
2. Build an `AccountPermissionUpdateContract` for `A` where:
   - `owner` permission has `type = Owner`, `threshold = 1`, and a single `Key` with `address = 0x41 0000000000000000000000000000000000000000` (21-byte zero address with correct network prefix byte) and `weight = 1`.
   - `actives` contains at least one syntactically valid active permission (to satisfy `getActivesCount() > 0`).
3. Submit/broadcast the transaction. `AccountPermissionUpdateActuator.validate()` passes because:
   - `DecodeUtil.addressValid()` returns `true` for the zero address (correct length/prefix).
   - All other `checkPermission()` checks (keys count, threshold, weight sum, distinct addresses) pass trivially with one key.
4. `execute()` commits the new owner permission (whose only key is the unowned zero address) via `AccountCapsule.updatePermissions()`.
5. Account `A`'s owner authority is now permanently bound to the zero address; no future `AccountPermissionUpdateContract` signed by the real owner can be validated against this broken owner permission, resulting in permanent loss of control.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
