### Finding

The sender-check the question asks about exists exactly at `crates/light-client-prover/src/circuit/mod.rs`, in the `DataOnDa::SequencerCommitment` arm of `run_l1_block`'s transaction dispatch: [1](#0-0) 

```rust
DataOnDa::SequencerCommitment(commitment) => {
    log!("Found sequencer commitment with index {}", commitment.index);
    if blob.sender().as_ref() != sequencer_da_public_key {
        log!(
            "Sequencer commitment sender is not sequencer, wtxid={:?}",
            blob.wtxid()
        );
        continue;
    }
    if SequencerCommitmentAccessor::<S>::get(commitment.index, &mut working_set)
        .is_none()
    {
        SequencerCommitmentAccessor::<S>::insert(
            commitment.index,
            commitment,
            &mut working_set,
        )
    }
}
```

This compares `blob.sender()` against `sequencer_da_public_key` directly — not merely checking JMT presence — and skips (`continue`s) the entry entirely if the sender doesn't match, before any call to `SequencerCommitmentAccessor::insert`. This is exactly the binding the question hypothesizes might be missing, and it is present and enforced.

The binding claimed to be broken — `SequencerCommitmentAccessor` entries in the JMT == only commitments whose Bitcoin transaction sender key equals `sequencer_da_public_key` — is exactly what this code enforces, both before and after the check: a commitment blob is inserted into `SequencerCommitmentAccessor` if and only if `blob.sender().as_ref() == sequencer_da_public_key`.

This is also explicitly covered by existing tests that assert this exact scenario (a non-sequencer sender attempting to inscribe a commitment is rejected and never stored): [2](#0-1) 

```rust
let commitment =
    SequencerCommitmentAccessor::get(1, &mut working_set).expect("Should be available");

// As the first commitment pubkey was correct, this was set
assert_eq!(commitment.index, 1);
assert_eq!(commitment.l2_end_block_number, 30);
assert_eq!(commitment.merkle_root, [1; 32]);

let commitment = SequencerCommitmentAccessor::get(2, &mut working_set);

// ignored commitment from wrong pubkey
assert_eq!(commitment, None);
```

This test (`wrong_pubkey_sequencer_commitment_should_not_work`) directly reproduces the proof-of-concept idea in the question: it inscribes a `SequencerCommitment` blob with a non-sequencer sender key (`MockAddress::new([54u8; 32])` vs. `sequencer_da_pub_key = [45; 32]`), and confirms `SequencerCommitmentAccessor::get` returns `None` afterward — i.e., rejected, not stored.

An end-to-end version of the same scenario also exists at the integration-test level, confirming the batch proof built over such a rejected commitment does not cause any state transition: [3](#0-2) 

Since the `blob.sender() != sequencer_da_public_key` check runs before `SequencerCommitmentAccessor::insert` is ever reached, an attacker inscribing a `SequencerCommitment` with an arbitrary index (e.g., 10000) from a non-sequencer key would have their entry skipped, never populate the JMT, and any later batch proof referencing index 10000 would fail the `SequencerCommitmentAccessor::<S>::get` lookup in `verify_batch_proof_seq_comm_relation` (returning `None` → rejection), exactly as shown at: [4](#0-3)
