### Title
Silent, unrecoverable fund loss when `AttachOutboundsToExistingUniversalTx` fails after an already-committed UEA payload withdraw — ([File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go])

### Summary
When a `FUNDS_AND_PAYLOAD` inbound is executed, the payload is run through the UEA with a real, already-committed `DerivedEVMCall` (`commit=true`). If that payload triggers a withdraw on the `UniversalGatewayPC` contract (a `UniversalTxOutbound` event, e.g. burning/moving the user's PRC20), the keeper then tries to parse that already-committed receipt and attach a corresponding `OutboundTx` record via `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt`. If this attach step fails (chain outbound disabled, token config lookup miss, decode error), the code does **not** roll back or compensate the already-executed on-chain withdraw — it just stores a string in `UniversalTx.RevertError` and returns `nil`. No `OutboundTx` is ever created, so the TSS/outbound pipeline that would deliver funds to the destination chain never runs, and there is no other mapping or retry path that reconstructs the lost outbound. This directly mirrors the reported bug class: a fallback/error branch after an irreversible fund-moving action fails to persist the record a later step depends on, causing permanent loss with only a text side-channel to indicate that something went wrong.

### Finding Description
The payload execution path is:

1. `ExecuteInboundFundsAndPayload` calls `k.ExecutePayloadV2(...)` which internally issues `CallUEAExecutePayload`, a `DerivedEVMCall` with `commit=true`, i.e. a real, immediately-committed EVM transaction [1](#0-0)  — this is not something that can be rolled back afterward.
2. On success, the keeper parses the resulting receipt for `UniversalTxOutbound` events and tries to attach the resulting outbound(s) to the UTX: [2](#0-1) 
3. `AttachOutboundsToExistingUniversalTx` calls `BuildOutboundsFromReceipt`, which can fail for reasons entirely independent of whether the on-chain withdraw actually happened — e.g. `IsChainOutboundEnabled` returning false or `GetTokenConfigByPRC20` erroring: [3](#0-2)  and the wrapper: [4](#0-3) 
4. When `attachErr` is non-nil, the only observable effect is a string written into `UniversalTx.RevertError`; the function then returns `nil` — no outbound is retried, no compensating mint/refund is issued, and the burned/withdrawn PRC20 amount referenced by the gateway event is never turned into a deliverable `OutboundTx`: [5](#0-4) 

This is structurally identical to the reported bug: an irreversible fund-affecting action (the EVM-side withdraw/burn call) already succeeded and is final, but the bookkeeping record the withdrawal-completion flow depends on (`OutboundTx` inside `UniversalTx.OutboundTx`, analogous to `withdrawalRequests[msg.sender]`) is never populated on that particular failure branch. The presence of `UniversalTx.RevertError` gives no automated remedy — per the module's own README, expired/rejected inbound ballots get a documented "escape-hatch refund flow" via `ExpiredInbounds`, but there is no analogous mechanism for a failed *outbound-attach* step following an already-executed payload.

### Impact Explanation
This causes real, permanent loss of user funds: value already moved/burned on the EVM side via the UEA's payload execution is never surfaced as a deliverable outbound, and the on-chain gateway state that would let a destination chain payout occur is dropped with only a diagnostic error string. This falls squarely within the in-scope impact of "permanent loss ... of user or protocol-controlled funds" and "corruption of ... canonical UniversalTx state," since the UTX's `OutboundTx[]` — the sole source of truth for "what's happening" per the module's own documentation — permanently omits the outbound that should exist.

### Likelihood Explanation
This is reachable by an ordinary unprivileged user: any user submitting a `FUNDS_AND_PAYLOAD`/payload-driven withdraw whose destination chain happens to have outbound disabled in `x/uregistry`, or whose PRC20/token-config mapping is momentarily missing/misconfigured for that chain, will trigger `BuildOutboundsFromReceipt` to error after the withdraw call has already committed. No malicious validator, TSS participant, or privileged actor is required — only the payload targeting a chain/token combination that isn't (or is no longer) properly registered in `x/uregistry` at execution time.

### Recommendation
Wrap the payload execution and the outbound-attach step so they succeed or fail atomically (e.g. execute the UEA payload call in a cache context and only commit once `BuildOutboundsFromReceipt`/`attachOutboundsToUtx` succeed), or, if atomic rollback of the already-committed derived EVM call is not feasible, add an explicit, retryable "pending outbound reconstruction" record keyed by the receipt/log so operators (or an automated job) can rebuild the missing `OutboundTx` from the emitted `UniversalTxOutbound` event instead of relying solely on the opaque `RevertError` string.

### Proof of Concept
1. A user's UEA executes a payload that calls the gateway's withdraw function for `PRC20` token `T` destined for chain `C`, emitting `UniversalTxOutbound`. `CallUEAExecutePayload` commits this as a real EVM transaction (`x/uexecutor/keeper/evm.go:178-192`), meaning the withdraw side effects (e.g. token burn on the gateway) are already final.
2. Governance (or misconfiguration) has chain `C` marked outbound-disabled in `x/uregistry`, or the `PRC20→external token` mapping for `C` is missing at that exact height.
3. `ExecuteInboundFundsAndPayload` calls `AttachOutboundsToExistingUniversalTx(receipt, utx)` → `BuildOutboundsFromReceipt`, which hits `IsChainOutboundEnabled` returning `false` and returns an error (`create_outbound.go:49-57`).
4. Back in `execute_inbound_funds_and_payload.go:318-325`, `attachErr != nil`, so the code stores `RevertError` on the UTX and returns `nil`. No `OutboundTx` was ever created for the withdraw that already executed on-chain in step 1.
5. Query `GetUniversalTx` for this UTX: `OutboundTx` is empty/does not contain the withdraw, yet the gateway event/receipt from step 1 shows funds were moved. There is no code path that later reconstructs or refunds this — the funds are stuck permanently.

func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
