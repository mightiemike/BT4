### Title
Non-hardened floating-point divide-then-multiply in resource delegation validation causes truncated `v2NetUsage`/`v2EnergyUsage`, allowing users to over-delegate frozen bandwidth/energy - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java`)

### Summary
`DelegateResourceActuator.validate()` and its TVM-precompile analog `DelegateResourceProcessor.validate()` compute a user's V2 bandwidth/energy usage by performing a `double` **division first** (`totalWeight / totalLimit`) and then multiplying by `netUsage`/`energyUsage`, exactly the pattern flagged in the referenced ABDKMath64x64 report ("multiplication on results of division"). This is the same bug class the project has already remediated elsewhere (via `allowHardenResourceCalculation`/BigInteger paths in `ResourceProcessor`, `BandwidthProcessor.calculateGlobalNetLimit`, `EnergyProcessor.calculateGlobalEnergyLimit`, `RepositoryImpl.usageToBalance/getUsage`), but the delegate-resource validation code paths were never given an equivalent hardened/BigInteger fallback.

### Finding Description
In `DelegateResourceActuator.validate()`: [1](#0-0) 
and the identical pattern for energy: [2](#0-1) 

and in the TVM precompiled-contract path `DelegateResourceProcessor.validate()`: [3](#0-2) 

The calculation `(long) (netUsage * TRX_PRECISION * ((double) totalWeight / totalLimit))` divides two large `long` global chain counters (`getTotalNetWeight()`/`getTotalNetLimit()`, or `getTotalEnergyWeight()`/`getTotalEnergyCurrentLimit()`) as a `double` *before* multiplying by the account's `netUsage`/`energyUsage`. Doing the division first collapses precision into a 52-bit mantissa before the multiplication, which can round the ratio down (or up) relative to the mathematically exact `usage * totalWeight * TRX_PRECISION / totalLimit`. The result, `v2NetUsage`/`v2EnergyUsage` (via `FreezeV2Util.getV2NetUsage`/`getV2EnergyUsage`), is then subtracted from `getFrozenV2BalanceForBandwidth()`/`getFrozenV2BalanceForEnergy()` to gate how much stake the caller is allowed to delegate: [4](#0-3) [5](#0-4) 

By comparison, the project already recognizes and has fixed this exact bug class for the *related* global-limit computations by adding a `hardenCalculation()`/BigInteger path: [6](#0-5) [7](#0-6) 
but `DelegateResourceActuator`/`DelegateResourceProcessor`/`UnDelegateResourceActuator`/`UnDelegateResourceProcessor`/`Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize` still use the raw `double` divide-then-multiply order without any hardened equivalent.

### Impact Explanation
The estimated `v2NetUsage`/`v2EnergyUsage` value directly gates the `ContractValidateException` check that prevents an account from delegating more stake than it has actually earmarked for that resource type: [8](#0-7) 
If the double division-then-multiplication truncates `v2NetUsage` lower than the mathematically exact value, the check `getFrozenV2BalanceForBandwidth() - v2NetUsage < delegateBalance` becomes looser than intended, letting a user validate (and then execute) a `DelegateResourceContract`/`UnDelegateResourceContract` (or trigger the equivalent TVM precompiled `delegateResource`/`unDelegateResource` opcode) that delegates resource allocations inconsistent with their actual remaining frozen balance. This is an accounting-consistency bug in resource/energy metering reachable directly from a broadcast transaction (`DelegateResourceContract`) and from arbitrary smart contract code (via the TVM native precompile), i.e., unprivileged, anonymous-caller reachable.

### Likelihood Explanation
Reaching this code path requires nothing more than calling `DelegateResourceContract`/`UnDelegateResourceContract` from any account with frozen V2 balance, or invoking the corresponding TVM precompile from a contract - both are standard, unprivileged operations available to any address. The magnitude of the truncation is bounded by IEEE-754 double precision (~1 part in 2^52) relative to the exact integer ratio, so on typical current-mainnet magnitudes (`totalNetWeight`/`totalNetLimit` roughly in the 10^9–10^11 range) the divergence from the exact BigInteger computation is small per call, but it is systematic and cumulative across many calls/accounts, and the pattern is already proven to matter in this codebase (see the project's own hardened-vs-legacy parity tests demonstrating measurable discrepancies for comparable magnitudes): [9](#0-8) 

### Recommendation
Apply the same hardening pattern already used elsewhere in the codebase (`hardenCalculation()`/`allowHardenResourceCalculation()` gating a `BigInteger`-based multiply-then-divide) to:
- `DelegateResourceActuator.validate()` (both `BANDWIDTH` and `ENERGY` branches),
- `UnDelegateResourceActuator.execute()` (both branches),
- `DelegateResourceProcessor.validate()`,
- `UnDelegateResourceProcessor.execute()`,
- `Wallet.calcCanDelegatedBandWidthMaxSize` / `calcCanDelegatedEnergyMaxSize`.

Specifically, replace `(long) (usage * TRX_PRECISION * ((double) totalWeight / totalLimit))` with a `BigInteger.valueOf(usage).multiply(BigInteger.valueOf(TRX_PRECISION)).multiply(BigInteger.valueOf(totalWeight)).divide(BigInteger.valueOf(totalLimit)).longValueExact()` computation (multiplication before division), consistent with `RepositoryImpl.usageToBalance` and `ResourceProcessor.calculateGlobalLimitV2`.

### Proof of Concept
1. Observe `DelegateResourceActuator.validate()`:
```java
long netUsage = (long) (accountNetUsage * TRX_PRECISION * ((double)
    (dynamicStore.getTotalNetWeight()) / dynamicStore.getTotalNetLimit()));
long v2NetUsage = getV2NetUsage(ownerCapsule, netUsage, this.disableJavaLangMath());
if (ownerCapsule.getFrozenV2BalanceForBandwidth() - v2NetUsage < delegateBalance) { ... }
```
2. Choose `accountNetUsage`, `totalNetWeight`, `totalNetLimit` such that `totalNetWeight / totalNetLimit` as a `double` rounds down relative to the exact rational value (as demonstrated generically for this pattern by the project's own `testUsageToBalanceCorrectAcrossDoublePrecision` test, which shows the double-based formula diverging from the exact `BigInteger` result for comparable magnitudes: `usage=1e8, totalWeight=1e11, totalLimit=5e10`).
3. Because the resulting `netUsage`/`v2NetUsage` is truncated low, `getFrozenV2BalanceForBandwidth() - v2NetUsage` becomes larger than the true available balance, permitting a `delegateBalance` amount that should have failed validation.
4. The same construction applies to the `ENERGY` branch and to the `DelegateResourceProcessor`/`UnDelegateResourceProcessor` TVM precompile paths, which are reachable from any smart contract without special privilege.

Note: I could not fully quantify the exact magnitude of exploitable drift for current live-network `totalNetWeight`/`totalNetLimit` values from the index alone; a background Devin session with full repository/test access would be needed to run the equivalent of `RepositoryImplHardenTest`/`CalculateGlobalLimitHardenTest` against these specific delegate-resource code paths to confirm concrete numeric divergence and craft an end-to-end funded PoC transaction.

  public static long getV2NetUsage(AccountCapsule ownerCapsule, long netUsage, boolean
      disableJavaLangMath) {
    long v2NetUsage= netUsage
        - ownerCapsule.getFrozenBalance()
        - ownerCapsule.getAcquiredDelegatedFrozenBalanceForBandwidth()
        - ownerCapsule.getAcquiredDelegatedFrozenV2BalanceForBandwidth();
    return max(0, v2NetUsage, disableJavaLangMath);

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
