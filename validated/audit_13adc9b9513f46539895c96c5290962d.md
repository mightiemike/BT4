### Title
Excess attached deposit in `AddressRegistrar::register` is permanently locked with no refund path - (File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs)

### Summary
`AddressRegistrar::register` is a `#[payable]` method reachable by any transaction signer (including relayers acting on behalf of the NEAR Wallet Contract). It requires `attached_deposit >= required_deposit` (computed from the storage cost of the address→account mapping) but only refunds the caller's deposit on the `Entry::Occupied` (collision) branch. On the successful `Entry::Vacant` insertion branch, any deposit sent above the exact storage cost is neither used nor refunded, permanently locking the excess NEAR in the contract, which has no admin/withdraw method.

### Finding Description
In `register`, the required deposit is computed exactly from the bytes needed to store the `address -> account_id` mapping: [1](#0-0) 

The caller must send at least `required_deposit`, but there is no upper bound check, and any excess (`given_deposit - required_deposit`) is not tracked. When the entry is newly inserted (the common, successful path), the code just logs and returns without any refund logic: [2](#0-1) 

Only the collision branch (`Entry::Occupied`) explicitly refunds `given_deposit` back to `predecessor_account_id`: [3](#0-2) 

Since NEAR credits the attached deposit of a `FunctionCall` action to the receiving contract's account balance before the method executes (this is standard `#[payable]` semantics, analogous to `msg.value` in the audited Solidity report), any amount sent above `required_deposit` on a successful registration becomes part of the `AddressRegistrar` contract's balance. The contract exposes no `withdraw`, `owner`, or similar recovery method anywhere in its implementation, so that excess is unrecoverable by the caller or anyone else.

This is reachable by any unprivileged RPC caller / transaction signer that calls `register` (directly, or indirectly via the NEAR Wallet Contract's `rlp_execute` flow which calls into the registrar as part of Ethereum-transaction emulation), and it requires no special privilege.

### Impact Explanation
Any caller who attaches more than the exact `required_deposit` when calling `register()` on a first-time (non-colliding) registration permanently loses the difference — the funds remain locked in the `AddressRegistrar` contract's balance with no method to retrieve them. Because callers determine the deposit off-chain (before knowing the exact final storage cost with certainty, and because slight overestimation is a common practice to avoid `Insufficient deposit` panics), such overpayment is a realistic, likely occurrence, not a contrived edge case. This matches the "permanently frozen funds" impact category.

### Likelihood Explanation
Likelihood is high in practice: callers (or the Wallet Contract's relayer-driven emulation flow that calls `register`) must estimate `required_deposit` themselves before submitting the transaction, and the exact byte cost depends on `account_id.len()`, so any imprecision or safety margin added by the caller results in an unrecoverable loss. No malicious actor is required — this triggers on ordinary, honest use whenever the attached deposit is not the exact minimum.

### Recommendation
After confirming `given_deposit >= required_deposit` and successfully inserting the new entry, compute and refund the excess (`given_deposit - required_deposit`) to `env::predecessor_account_id()`, mirroring the refund logic already present in the `Entry::Occupied` branch. Alternatively, add an explicit check that `given_deposit == required_deposit` (rejecting overpayment) or add an owner-controlled withdrawal method as a safety net for any legacy locked balances.

### Proof of Concept
1. Deploy `AddressRegistrar` and call `register("some.near")`.
2. Compute `required_deposit = storage_byte_cost * (20 + len("some.near"))`.
3. Call `register` again for a new, non-colliding account (e.g., `"other.near"`) attaching `required_deposit + 1 yoctoNEAR` (or any amount greater than required).
4. Observe: the call succeeds (`Entry::Vacant` branch), the mapping is inserted, and the extra `1 yoctoNEAR` (or larger overpayment) is added to the registrar contract's balance with no way for the caller to reclaim it, since no refund is issued in this branch and the contract exposes no withdrawal function: [2](#0-1)
