### Title
Cheap, self-funded congestion flood lets any tx sender lock legitimate users out of a shard for an extended period - (File: `core/primitives/src/congestion_info.rs`)

### Summary
The external report describes a bridge contract that lacks a fee, letting an attacker who merely pays ordinary L2 gas exhaust a shared, time-based daily limit and block every other user from using the bridge for 24 hours. The nearcore analog is NEP-539 congestion control's transaction-admission gate: `CongestionControl::shard_accepts_transactions` [1](#0-0)  rejects **all** new transactions whose receiver lives on a shard once that shard's `congestion_level` reaches `reject_tx_congestion_threshold` (0.8 in mainnet params) [2](#0-1) . Any ordinary, unprivileged account can drive a shard's `incoming_congestion` or `memory_congestion` toward this threshold by submitting normal, fee-paying transactions/receipts that pile up in that shard's delayed-receipt queue, exactly as the bridge attacker exhausts `maxTransferAmountPerDay` by simply using the contract as intended, at full (but "only gas") cost.

### Finding Description
`CongestionControl::congestion_level` is the max of four fractions — incoming, outgoing, memory, missed-chunks — each derived from queue occupancy relative to config maxima [3](#0-2) . `shard_accepts_transactions` uses this same level to decide, for every incoming transaction targeting the shard, whether the shard will accept it at all: once `congestion_level >= reject_tx_congestion_threshold`, the shard returns `ShardAcceptsTransactions::No(...)` for **every** transaction, not just the attacker's [4](#0-3) . This is invoked from the chunk-producer/runtime transaction validation path in `chain/chain/src/runtime/mod.rs`.

Nothing in this mechanism requires the attacker to pay more than normal transaction/action fees — there is no separate anti-congestion fee or bond, mirroring the reported bridge's lack of a teleportation fee. An attacker who controls (or targets) accounts on a specific shard can submit a stream of ordinary transactions whose resulting receipts populate the delayed-receipt queue and/or outgoing buffers of that shard (e.g., receipts that are cheap to *send* but pile up execution/memory cost on the *receiving* shard, per `compute_receipt_congestion_gas`, which even assigns **zero** congestion gas to `Data`/`PromiseYield`/`PromiseResume`/`GlobalContractDistribution` receipts [5](#0-4) ), pushing `incoming_congestion` or `memory_congestion` above 0.8. Once that happens, `shard_accepts_transactions` blocks every other user's transactions to any account on that shard until the backlog drains — draining is bounded by the per-chunk compute/gas budget (`process_delayed_receipts`, `process_incoming_receipts`) [6](#0-5) , which can take a substantial, attacker-extendable amount of time if the attacker keeps re-submitting.

This is directly analogous to the reported bug class: a shared, periodically-replenished capacity limit (daily transfer cap ↔ per-shard congestion budget) that an unprivileged, fee-paying actor can consume using only the protocol's normal cost model, thereby denying the resource to everyone else for an extended window.

### Impact Explanation
While congestion control is an intentional NEP-539 mechanism (not inherently a bug), the tx-admission cutoff it drives is a hard, shard-wide denial of service: it rejects transactions from users who had nothing to do with the congestion, for every account whose receiver shard is congested, for as long as the queue takes to drain. This can be triggered by a single account paying only standard gas fees (no privileged role, no protocol-level throttling of the *attacker's own* ability to keep submitting more congesting receipts beyond normal gas costs), so it satisfies the "transaction-triggered halt" class of impact called out in the validation rules — a targeted, attacker-triggered halt of transaction admission for an entire shard, which is a Medium/High severity availability impact on a live protocol.

### Likelihood Explanation
Any account can submit transactions and receipts; no special privileges, staking, or validator status are required. The only barrier is the aggregate gas cost of pushing a shard's congestion metric above the 0.8 threshold, which — like the original report's characterization ("relatively cheap, only costing L2 gas") — is bounded by ordinary usage cost rather than any anti-abuse fee. This makes the attack economically similar in kind to the reported one: proportional cost, but no cost specifically designed to prevent the denial-of-service, and the blocking radius (an entire shard's transaction admission) is broader than the attacker's own targeted account.

### Recommendation
Consider adding congestion-aware pricing or a per-sender rate limit so that the cost of contributing to a shard's congestion scales super-linearly (or is explicitly priced) rather than being purely proportional to ordinary gas usage, similar to the report's own recommendation of "charging a fee to mitigate DOS." Concretely: reconsider assigning zero congestion gas to `Data`/`PromiseYield`/`PromiseResume`/`GlobalContractDistribution` receipts (`compute_receipt_congestion_gas`) so an attacker cannot cheaply grow queue occupancy using receipt kinds that bypass the incoming-gas metric while still consuming memory/processing capacity, and audit whether `reject_tx_congestion_threshold` combined with `process_tx_limit` throttling gives enough lead time/graceful degradation before hard-rejecting unrelated users' transactions.

### Proof of Concept
1. Identify (or create) several accounts whose receiver shard is the target shard `S`.
2. From an unprivileged account, submit a sustained stream of ordinary transactions/receipts targeting accounts on `S` designed to maximize queue occupancy relative to gas spent (e.g., receipts with large `input_data_ids`/postponed dependencies, or zero-congestion-gas `Data`/`PromiseYield` receipt chains as described in `compute_receipt_congestion_gas`).
3. Monitor `CongestionInfo` for shard `S` (exposed via block/chunk headers or RPC) until `congestion_level` computed by `CongestionControl::congestion_level` reaches/exceeds `reject_tx_congestion_threshold` (0.8).
4. Submit a transaction from an unrelated, honest account targeting any account on shard `S`; observe it rejected via `ShardAcceptsTransactions::No(...)` returned by `shard_accepts_transactions`, confirming that legitimate users are locked out purely as a side effect of the attacker's ordinary, fee-paying transaction volume, with no dedicated anti-abuse fee involved.

```rust
    /// Whether we can accept new transaction with the receiver set to this shard.
    ///
    /// If the shard doesn't accept new transaction, provide the reason for
    /// extra debugging information.
    pub fn shard_accepts_transactions(&self) -> ShardAcceptsTransactions {
        let incoming_congestion = self.incoming_congestion();
        let outgoing_congestion = self.outgoing_congestion();
        let memory_congestion = self.memory_congestion();
        let missed_chunks_congestion = self.missed_chunks_congestion();

        let congestion_level = incoming_congestion
            .max(outgoing_congestion)
            .max(memory_congestion)
            .max(missed_chunks_congestion);

        // Convert to NotNan here, if not possible, the max above is already meaningless.
        let congestion_level =
            NotNan::new(congestion_level).unwrap_or_else(|_| NotNan::new(1.0).unwrap());
        if *congestion_level < self.config.reject_tx_congestion_threshold {
            return ShardAcceptsTransactions::Yes;
        }

        let reason = if missed_chunks_congestion >= *congestion_level {
            RejectTransactionReason::MissedChunks { missed_chunks: self.missed_chunks_count }
        } else if incoming_congestion >= *congestion_level {
            RejectTransactionReason::IncomingCongestion { congestion_level }
        } else if outgoing_congestion >= *congestion_level {
            RejectTransactionReason::OutgoingCongestion { congestion_level }
        } else {
            RejectTransactionReason::MemoryCongestion { congestion_level }
        };
        ShardAcceptsTransactions::No(reason)
    }
```
