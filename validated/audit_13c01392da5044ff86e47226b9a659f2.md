### Title
Missing meaningful slippage protection in `ExchangeTransactionActuator` allows AMM-pool value extraction via price manipulation - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionActuator` implements TRON's on-chain bancor-style AMM exchange. Any account can broadcast an `ExchangeTransactionContract` to trade against a shared liquidity pool (`ExchangeCapsule`), specifying a `quant` (amount to sell) and an `expected` (minimum amount to receive) field. The only validation performed on `expected` is that it is strictly greater than zero, exactly mirroring the flaw described in the referenced report where GMX's `minUsdg`/`minGlp` parameters only needed to be non-zero to pass validation.

Because `tokenExpected` merely needs to be `>= 1`, from the perspective of real token units (which routinely use 6 or 18 decimals in TRON's TRC10/TRC20 ecosystem) this is "virtually zero," exactly as flagged in the external report for GMX's `minUsdg`/`minGlp`. The actual output is computed by the bancor relay-token formula in `ExchangeCapsule.transaction()`, which reads and mutates the pool's live `firstTokenBalance`/`secondTokenBalance` state: [3](#0-2) 

This pool state is shared across all traders and evolves with every executed `ExchangeTransactionContract`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` call. Because the on-chain price (i.e., the ratio of `firstTokenBalance`/`secondTokenBalance`) is entirely determined by prior transactions within the same or an adjacent block, an attacker who controls block/transaction ordering (or who executes a manipulating trade immediately before the victim's trade lands) can shift the pool ratio, execute the victim-controlled or attacker-controlled swap with the trivially-satisfied `expected=1` check, and extract value from the pool — precisely the "minimum amount check is virtually zero" pattern in the external report.

### Impact Explanation
Unlike a typical AMM where weak slippage protection primarily harms only the trader who set it too low, TRON's Exchange pool is a persistent, shared, on-chain state object (`ExchangeCapsule`) that any account can trade against via unprivileged, broadcastable `ExchangeTransactionContract` transactions. Because `expected` need only be `>=1`, any transaction is effectively "unprotected" from slippage/sandwiching once it enters the network, and since the pool balances persist and compound across transactions, a manipulated trade permanently and irreversibly corrupts the pool's balance/price for subsequent legitimate traders — an accounting/asset-value corruption reachable purely from broadcast transactions, matching the accepted impact classes (asset/accounting corruption via protocol implementation).

### Likelihood Explanation
Any account can construct and broadcast the sequence of transactions needed (a manipulating trade followed by the victim/attacker trade with `expected=1`) with no special privilege, matching the "anonymous broadcast transaction" reachability requirement. The constraint of setting `expected` near-zero is not an edge case — the actuator's own test suite explicitly demonstrates this exact pattern (calling with `expected=1`) as a standard, successfully-validated flow. [4](#0-3) 

### Recommendation
Do not rely solely on caller-supplied `expected` (or the trivial `> 0` check) for economic safety. Consider:
- Enforcing a minimum meaningful slippage bound relative to the trade size/pool depth rather than an absolute `> 0` check.
- Adding TWAP-based or multi-block price checks before large trades are permitted against the pool.
- Rate-limiting or capping the price impact allowed within a single block for a given exchange pair, similar to the `balanceLimit` check already present.

### Proof of Concept
1. Attacker (or any account) observes/initiates a large trade against exchange pool `X` that shifts `firstTokenBalance`/`secondTokenBalance` significantly via `ExchangeTransactionActuator` (validated by the checks at [5](#0-4) ).
2. In the same or next block, a victim transaction (or the attacker's own follow-up transaction) executes `ExchangeTransactionContract` with `expected=1`, which trivially passes the check at lines 190-192 and 219-221.
3. `exchangeCapsule.transaction()` computes the output using the now-manipulated pool ratio, extracting value from the pool at a price far worse than the pre-manipulation price, exactly as demonstrated by the "TokenRequiredNotEnough" tests confirming the check only compares against attacker-chosen `expected`.   public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
