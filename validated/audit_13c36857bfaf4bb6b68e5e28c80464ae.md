### Title
Truncated u16 length field in MemTrie extension encoding causes length/data mismatch panic (chunk-triggered halt) - (File: core/store/src/trie/mem/flexible_data/extension.rs)

### Summary
`EncodedExtensionHeader` encodes a trie extension path's length in a `u16` field, but the actual extension byte slice can originate from a `max_length_storage_key` of up to 4 MiB — far larger than `u16::MAX` (65,535). When `from_input` truncates `extension.len()` into the `u16` field, the allocation size computed from the truncated header no longer matches the length of the slice later passed to `encode_flexible_data`, which calls `target.raw_slice_mut().copy_from_slice(&extension)` with no length check.

### Finding Description
`EncodedExtensionHeader::from_input` computes the fixed-size header purely from `extension.len() as u16`: [1](#0-0) 
and `flexible_data_length()` — used by `RawEncoder::encode_flexible` to size the arena allocation — returns `self.length as usize`, i.e., the truncated value: [2](#0-1) 
`encode_flexible_data` then does an unchecked `copy_from_slice` of the full, non-truncated `extension` slice into a target buffer sized according to the truncated header: [3](#0-2) 
`Vec::copy_from_slice`/slice `copy_from_slice` panics if the source and destination slices differ in length (it does not silently overflow like the kernel's `memcpy`, but it is the direct Rust analog of the same root cause: a length value used for allocation gets desynchronized from the length of the data actually copied). This is directly analogous to `mwifiex_cmd_append_vsie_tlv()`'s `memcpy` mismatch between an allocated TLV buffer size and the actual VSIE length.

The extension path fed into this code originates from `TrieKey` encodings such as `TrieKey::ContractData { account_id, key }`, which concatenates the account id and the raw contract storage `key` supplied by a contract call: [4](#0-3) 
`max_length_storage_key` is configured at 4,194,304 bytes (4 MiB), well beyond `u16::MAX`: [5](#0-4) 
So a single `storage_write` host call from any deployed WASM contract, using a key close to the configured maximum, can create a trie leaf/extension node whose uncompressed path length exceeds 65,535 bytes when it becomes a compressed extension in the in-memory trie (`MemTrie`).

### Impact Explanation
If a `u16` truncation actually occurs for a real extension path, the mismatch between the (truncated) allocated arena slice length and the actual extension byte slice length being copied triggers a panic inside `copy_from_slice`, which aborts trie construction. Because `MemTrie` construction/insertion runs inside every validating node's chunk-apply path, this would manifest as a transaction-triggered node crash/halt across all honest nodes processing that chunk — the "transaction-triggered halt" impact category explicitly listed as in-scope.

### Likelihood Explanation
I could not fully verify whether `max_length_storage_key` combined with account-id length and trie compression logic realistically produces an *uncompressed* extension segment longer than 65,535 bytes in the current MemTrie construction path (`core/store/src/trie/mem/construction.rs`, `core/store/src/trie/nibble_slice.rs`) — extension compression could keep individual segments shorter in typical cases, and I was not able to trace the exact worst-case extension length produced from a single maximal-length key within the remaining budget. This is a real, unchecked truncation defect (`as u16` with no bounds assertion, unlike `EncodedValueHeader` which does assert consistency), but I cannot confirm with full certainty from static review alone that a single transaction can force an extension segment past 65,535 bytes without also exercising the actual trie insertion algorithm, which I was unable to fully trace in the time available.

### Recommendation
Add an explicit bounds check/assert in `EncodedExtensionHeader::from_input` (and any other `as u16`/`as u32` truncating casts feeding `flexible_data_length`) that the input length fits in the header's integer type, returning a hard error (or asserting in a way that is validated before any trie mutation) instead of allowing a silent truncation to later panic deep inside arena-slice `copy_from_slice`. Additionally, add a fuzz/property test that constructs `ContractData` keys near `max_length_storage_key` and confirms MemTrie insertion succeeds without truncation-induced panics.

### Proof of Concept
Not fully constructible from static analysis alone without tracing exact NibbleSlice/extension-compression behavior for a maximal `max_length_storage_key` value; would require running MemTrie insertion in `core/store/src/trie/mem/construction.rs` with a `ContractData` key sized near 4 MiB (via a contract issuing `storage_write` with such a key) and observing whether the resulting extension node's flexible-data length exceeds `u16::MAX`, which is not proven here.
