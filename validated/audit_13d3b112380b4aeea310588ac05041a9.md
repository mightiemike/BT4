### Title
Zero-payment token theft in TRC10 DEX order matching due to missing rounding-to-zero guard in the "taker == maker" branch - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchSingleOrder()` computes, for each of the three possible relationships between the taker's buy amount and the maker's remaining sell amount, how many tokens each side receives using integer division (`MarketUtils.multiplyAndDivide`, a floor division). The "taker > maker" branch explicitly guards against the division rounding `makerBuyTokenQuantityReceive` down to `0` [1](#0-0) , but the "taker == maker" branch performs the identical calculation with no such guard [2](#0-1) . This mirrors the reported D3Trading pattern where a `payFromAmount` of `0` was accepted to receive tokens for free — here `makerBuyTokenQuantityReceive` (the maker's payment) can round to `0` while the taker still receives the maker's full remaining sell tokens.

### Finding Description
In `matchSingleOrder`, when `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` (the "taker == maker" case), the code computes:
```
makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)
takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();
long takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
takerOrderCapsule.setSellTokenQuantityRemain(takerSellTokenLeft);
makerOrderCapsule.setSellTokenQuantityRemain(0);
``` [3](#0-2) 

`multiplyAndDivide` performs `floor(a*b/c)` [4](#0-3) , so `makerBuyTokenQuantityReceive` can be `0` when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`. Because the equality trigger (`takerBuyTokenQuantityRemain == makerSellRemainQuantity`) is computed from the *inverse* ratio (`makerSellQuantity/makerBuyQuantity`), it is possible to pick maker/taker order ratios such that:
- `takerBuyTokenQuantityRemain` exactly equals `makerSellRemainQuantity` (entering this branch), while
- `makerBuyTokenQuantityReceive = floor(makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity) == 0`.

Concretely: maker order sells token A for token B with `makerSellQuantity = 5`, `makerBuyQuantity = 3`, and `makerSellRemainQuantity = 1` (attacker fully controls/crafts this remainder by first partially filling their own maker order). A taker order (attacker-controlled) sells B to buy A with `takerSellRemainQuantity = 1`. Then `takerBuyTokenQuantityRemain = floor(1*5/3) = 1`, which equals `makerSellRemainQuantity = 1`, triggering the "taker == maker" branch. But `makerBuyTokenQuantityReceive = floor(1*3/5) = 0`.

Effect:
- `takerBuyTokenQuantityReceive = 1` → taker is credited 1 unit of token A via `addTrxOrToken(takerOrderCapsule, 1, takerAccountCapsule)` [5](#0-4) .
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` — the maker's order is fully drained, but the maker is credited `addTrxOrToken(makerOrderCapsule, 0)` — zero tokens B.
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0` — the taker's own reserved sell quantity is **not decremented**, and since `takerSellTokenLeft != 0` the taker's order stays `ACTIVE` in the order book, available to repeat the same free-drain against other small maker remainders.

This is the direct analog of the D3Trading bug: the "pay" leg (`makerBuyTokenQuantityReceive`) can be zero while the "receive" leg (`takerBuyTokenQuantityReceive`) is non-zero, and unlike the sibling "taker > maker" branch, there is no re-check/return-to-owner fallback here.

### Impact Explanation
Any account can call the `MarketSellAssetContract` (broadcastable by anonymous users via normal transactions) to create maker/taker orders with attacker-chosen `sellTokenQuantity`/`buyTokenQuantity` pairs and can also self-fill a maker order down to a crafted tiny remainder. By repeatedly triggering this branch, an attacker can drain TRC10 token balances escrowed in other users' maker orders (or their own crafted ones against victims) for zero payment, and can repeatedly reuse the un-decremented taker order to steal from multiple maker orders. This directly corrupts token accounting/asset balances handled by the on-chain `MarketOrderCapsule`/`AccountCapsule` state — an asset/accounting corruption reachable purely through normal signed transactions.

### Likelihood Explanation
Triggering requires crafting specific integer ratios (`makerSellQuantity`, `makerBuyQuantity`, remainder) so that `takerBuyTokenQuantityRemain == makerSellRemainQuantity` while the reverse-ratio division rounds to 0. This is fully within attacker control since they can create and partially fill their own orders to produce the desired remainder before submitting the matching taker order, so the likelihood of a knowledgeable attacker constructing valid parameters is high; it does not depend on any privileged actor or race condition.

### Recommendation
Add the same zero-quantity guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0` after the division, do not zero out the maker's remaining quantity (or return the affected token quantities to their owners / treat the fill as size `0`), mirroring the handling at lines 466–477 [6](#0-5) .

### Proof of Concept
1. Attacker creates maker order O1: sell token A, buy token B, `sellTokenQuantity=5`, `buyTokenQuantity=3` (via `MarketSellAssetContract`).
2. Attacker (or a colluding/self-controlled second account) fills O1 down to `sellTokenQuantityRemain = 1` using additional matching orders (fully attacker-controlled, no third party needed).
3. Attacker creates taker order O2: sell token B, buy token A, `sellTokenQuantity=1` (i.e., `takerSellRemainQuantity=1`).
4. In `matchSingleOrder`, `takerBuyTokenQuantityRemain = floor(1*5/3) = 1 == makerSellRemainQuantity(1)` → enters "taker == maker" branch [7](#0-6) ; `makerBuyTokenQuantityReceive = floor(1*3/5) = 0`.
5. Result: taker account is credited 1 unit of token A, maker order O1 is closed having received 0 token B, and taker's order remains open/unchanged for reuse.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
