Confirmed: `validateHmacFromRequestFactory` computes the HMAC solely over `rawBody` [1](#0-0) , and the `domain` header is read separately, completely outside the HMAC-covered data, in `checkWebhooksHeaders`/`checkEventsHeaders` [2](#0-1) . This matches Shopify's actual documented webhook signing scheme (HMAC over body only), so it is not a library-introduced bug — it is how Shopify's real webhook protocol always worked, and `authenticate.ts` in shopify-app-remix just trusts `check.domain` as attacker/deliverer-supplied metadata, feeding it directly into `ensureValidOfflineSession(params, check.domain)` [3](#0-2) .

However, for this to be exploitable per the rules ("no MITM... unprivileged attacker... no privileged access, no leaked secret"), the attacker must produce a `(rawBody, hmac)` pair that is valid under the app's real `apiSecretKey` for an arbitrary `domain` value without ever knowing that secret. Since HMAC is keyed by `apiSecretKey`, and the attacker has no way to mint a fresh valid `(rawBody, hmac)` pair without the secret, the only path is *replaying a genuine webhook Shopify already sent* (for the attacker's own shop) with the domain header swapped. That requires the attacker to already be a legitimate installed merchant capturing their own genuine webhook deliveries and re-POSTing them with a forged `X-Shopify-Shop-Domain`/`shopify-shop-domain` header value pointing at a different (victim) shop, while keeping the original body+hmac intact.

This is a real, reproducible design gap: `check.domain` is unauthenticated, attacker-controllable metadata relative to the signed payload, and `authenticateWebhookFactory` uses it directly as the session-storage lookup key with no cross-check that the domain matches a shop the webhook body/topic was actually meant for.

### Title
Webhook `domain` header is not covered by HMAC, allowing cross-tenant session binding via webhook replay - (File: packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts)

### Summary
`api.webhooks.validate` computes the HMAC only over the raw request body [1](#0-0) , never over the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, so `check.domain` is unauthenticated attacker-controllable metadata. `authenticateWebhookFactory.authenticate` passes this unauthenticated value directly into `ensureValidOfflineSession(params, check.domain)` [4](#0-3) , which is then used to key session storage lookups and to build the `admin` API client passed to the app's webhook handler.

### Finding Description
`checkWebhooksHeaders`/`checkEventsHeaders` extract `domain` purely from request headers with no cryptographic binding to the signed body [2](#0-1) . The HMAC check in `validateHmacFromRequestFactory` only validates `rawBody` against the header HMAC using `apiSecretKey`; it never mixes in the domain header [5](#0-4) . Consequently `check.valid === true` says only "this body was signed by our secret at some point," not "this body belongs to this domain."

`authenticateWebhookFactory.authenticate` then does `const session = await ensureValidOfflineSession(params, check.domain)` [4](#0-3) , which resolves to `getOfflineId(shop)` → `offline_${sanitizeShop(shop,true)}` and loads that session from storage [6](#0-5) . If an attacker (an unprivileged merchant who has installed the app on their own shop) captures a genuine webhook delivery — body + valid HMAC — sent to their own endpoint, and replays that exact `(rawBody, hmac)` pair while substituting a different, victim shop's domain in the header, `check.valid` still returns `true` because the HMAC never covered the domain. `webhookContext.shop`, `session`, and `admin` are then built for the victim shop, even though the payload content is the attacker's captured (and effectively attacker-controlled at capture time) data.

### Impact Explanation
This lets a shop-owner attacker cause the app's webhook handler to execute business logic against a different tenant's offline session/access token, using data the attacker controls (their own webhook payload content, which for topics with attacker-influenced fields, e.g. product/order webhooks they trigger on their own store, can be shaped before capture). This is a cross-tenant confused-deputy: the app processes attacker-influenced webhook content under the victim's `admin` GraphQL/REST client and access token. Scoped impact matches Shopify's "cross-tenant data/state access" bounty class, though it is bounded by the app's own webhook handler logic (the vulnerability is a platform/library-level authorization gap, not a direct data return to the attacker).

### Likelihood Explanation
Requires: (1) the attacker to be a merchant with the app installed on some shop (unprivileged, no secret needed), (2) knowledge of a target victim domain (public information, e.g. `victim-shop.myshopify.com`), and (3) that the app relies on `authenticate.webhook`/`ensureValidOfflineSession` and that the victim shop has an existing offline session in the same storage backend. This is fully reproducible with the test secret in Jest as described, since it only exercises the isolation invariant of `check.domain` vs. HMAC coverage, not real secret compromise.

### Recommendation
Bind the domain to the HMAC-verified context: either (a) have Shopify's signing scheme cover the domain (platform-level, out of this library's control), or (b) within the library, cross-check `check.domain` against a registered/expected shop context before returning a session (e.g., verify the shop has an active app installation record separate from blind session-storage lookup, or require the webhook topic/shop pair to be validated against Shopify's registry before granting `admin`/`session` in the webhook context). At minimum, document that `check.domain` is unauthenticated and must not be trusted as a tenant boundary without additional verification.
