### Title
Declare-flood exhaustion of the process-global `declare_compilation_semaphore` denies Declare submission for all users - (File: crates/apollo_gateway/src/gateway.rs)

### Summary
The gateway bounds concurrent Sierra-to-CASM compilations with a single, process-wide `Semaphore` sized by `max_concurrent_declare_compilations` (default 40). Any unprivileged account can submit `Declare` transactions whose conversion/compilation step is slow (large/near-max-size Sierra programs, expensive to compile), holding a permit for the full compilation duration. By repeatedly submitting such transactions (a "submit" cycle analogous to the reported submit/withdraw cycling) an attacker can keep all permits occupied, causing every other user's legitimate Declare submissions to be rejected with `TransactionLimitExceeded` until the attacker's compilations finish or time out.

### Finding Description
`GenericGateway` holds one shared semaphore across all gateway request-handling tasks: [1](#0-0) 
It is sized once at construction from a static config value and never scales with load or per-sender identity: [2](#0-1) 

In `add_tx_inner`, any incoming `RpcTransaction::Declare` attempts to acquire a permit with `try_acquire` before doing the Sierra→CASM compilation via `convert_rpc_tx_to_internal_and_executable_txs`; if no permit is available it is rejected immediately, and the permit is only released after the (potentially expensive) compilation completes: [3](#0-2) 

There is no per-account or per-tx-hash budgeting on this resource — it is a pure, unauthenticated first-come-first-served pool shared by every sender to the node. This mirrors the reported bug class: a global, shared "action limit" (there, submit/withdraw slots; here, declare-compilation permits) that any single unprivileged actor can monopolize by repeatedly performing the gated action, causing denial of the action for everyone else. The existing test confirms the mechanic precisely: a single in-flight Declare holding the lone permit causes a second, unrelated Declare to be rejected outright: [4](#0-3) 

Compilation time scales with the size/complexity of the submitted Sierra program (bounded only by `max_contract_class_object_size` / `max_sierra_program_size`, which are set in the tens of megabytes per the gateway/http-server config), so an attacker can craft near-maximum-size or intentionally complex classes to maximize the time each permit is held, and pipeline many such declares from many nonces/accounts to occupy all 40 default permits simultaneously and indefinitely (cycled as each compilation finishes and a new one is submitted).

### Impact Explanation
This constitutes a network-availability denial: while the attack is sustained, no legitimate Declare transaction can be admitted through the affected gateway/sequencer instance (`TransactionLimitExceeded` for all callers, including declares from unrelated, honest accounts). Since Declare is required for deploying new classes, this can stall onboarding of new contract classes network-wide if the attack is sustained against enough sequencer instances, or against a solo/centralized sequencer. It does not corrupt state or cause loss of funds, but it satisfies the "network unable to confirm new transactions" bar for the targeted transaction type (Declare) as long as the attacker keeps cycling submissions.

### Likelihood Explanation
High. The attack requires nothing more than the ability to submit standard Declare transactions (an unprivileged capability), a modest amount of fees/gas to submit them, and control over Sierra program size/content to inflate compilation time. `max_concurrent_declare_compilations` defaults to a small fixed number (40) that is process-global and not scoped per sender, so a single actor issuing a burst of declares can trivially reach and hold the cap continuously by re-submitting as permits free up.

### Recommendation
- Scope compilation concurrency fairly per-sender (e.g., per-account or per-IP quotas) in addition to the global cap, so a single actor cannot occupy the entire pool.
- Bound worst-case compilation time more tightly (e.g., lower per-compilation CPU/wall-clock timeouts tied to program size) so a stuck/slow compile cannot indefinitely hold a permit.
- Consider queuing with fairness (e.g., round-robin per sender) rather than immediate rejection keyed only on a shared semaphore, or scale `max_concurrent_declare_compilations` dynamically with observed per-sender declare rate.
- Add metrics/alerting on sustained semaphore saturation attributable to a small set of senders to allow rate-limiting or blocking abusive accounts.

### Proof of Concept
1. Attacker crafts N ≥ `max_concurrent_declare_compilations` (default 40) valid `Declare` transactions from N distinct nonces/accounts, each with a Sierra program near `max_contract_class_object_size`/`max_sierra_program_size` limits designed to maximize compilation time.
2. Attacker submits all N declares concurrently to the gateway's `add_tx`. Each acquires one of the 40 semaphore permits and begins Sierra→CASM compilation (see `crates/apollo_gateway/src/gateway.rs:243-255`).
3. While these compilations are in flight, any other honest user's `Declare` submission calls `try_acquire`, finds no permits available, and is rejected immediately with `TransactionLimitExceeded` (reproduced deterministically by the existing test `test_declare_compilation_concurrency_limit` in `crates/apollo_gateway/src/gateway_test.rs:711-758`, generalized from 1 permit to 40).
4. Attacker resubmits new large declares as soon as prior ones finish compiling, keeping all permits perpetually occupied and denying Declare submission to all other users for as long as the campaign continues.

#[tokio::test(flavor = "multi_thread")]
async fn test_declare_compilation_concurrency_limit(mut mock_dependencies: MockDependencies) {
    mock_dependencies.config.static_config.max_concurrent_declare_compilations = 1;

    // Both declares run stateless validation, so replace the fixture's single-call mock with one
    // that accepts repeated calls.
    let mut mock_stateless_transaction_validator = MockStatelessTransactionValidatorTrait::new();
    mock_stateless_transaction_validator.expect_validate().returning(|_| Ok(()));
    mock_dependencies.mock_stateless_transaction_validator = mock_stateless_transaction_validator;

    // The first declare's conversion performs the Sierra-to-CASM compilation while holding the
    // single permit. Make that conversion block so the second declare arrives while the permit is
    // still held: `compilation_started_sender` signals that the permit is held, and the conversion
    // then parks on `release_compilation_receiver` until the test lets it finish.
    let (compilation_started_sender, compilation_started_receiver) =
        tokio::sync::oneshot::channel();
    let (release_compilation_sender, release_compilation_receiver) = std::sync::mpsc::channel();
    mock_dependencies
        .mock_transaction_converter
        .expect_convert_rpc_tx_to_internal_rpc_tx()
        .return_once(move |_| {
            compilation_started_sender.send(()).unwrap();
            release_compilation_receiver.recv().unwrap();
            // Fail the conversion so the first declare short-circuits here instead of running the
            // full admission path; its outcome is irrelevant, so the specific error is arbitrary.
            Err(TransactionConverterError::ClassNotFound { class_hash: ClassHash::default() })
        });

    let gateway = Arc::new(mock_dependencies.gateway());

    // Spawn the first declare and wait until it holds the permit inside compilation.
    let first_declare_task = {
        let gateway = gateway.clone();
        tokio::spawn(async move { gateway.add_tx(declare_tx(), None).await })
    };
    compilation_started_receiver.await.unwrap();

    // The second declare cannot acquire a permit and must be rejected immediately.
    let second_declare_error = gateway.add_tx(declare_tx(), None).await.unwrap_err();
    assert_eq!(
        second_declare_error.code,
        StarknetErrorCode::KnownErrorCode(KnownStarknetErrorCode::TransactionLimitExceeded)
    );
