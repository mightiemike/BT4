### Title
Unsynchronized concurrent refresh of offline access tokens causes token/session corruption - ([File: packages/apps/shopify-app-express/src/helpers/ensure-offline-token-is-not-expired.ts])

### Summary
`ensureOfflineTokenIsNotExpired` (and its `shopify-app-remix`/`shopify-app-react-router` equivalents) reads a shop's offline `Session` from shared session storage, and when it is within 5 minutes of expiry calls the OAuth refresh-token endpoint and writes the resulting session back to storage, with no mutual exclusion between concurrent requests for the same shop. [1](#0-0)  This mirrors the reported bug class: a shared mutable credential/header-like field (`session.accessToken`/`session.refreshToken`) is read by one code path while concurrently mutated by another, without a `sync.RWMutex`-equivalent guard, in a routine that runs on every authenticated request. [2](#0-1) 

### Finding Description
When `future.expiringOfflineAccessTokens` is enabled, every incoming authenticated request for a shop independently loads the same offline session and, if it is close to expiry, calls `refreshToken()` with the currently stored `refreshToken` value. [3](#0-2)  `refreshToken` posts to `/admin/oauth/access_token` with `grant_type: 'refresh_token'` and the caller-supplied refresh token, then builds and returns a brand-new `Session` (with a rotated `access_token`/`refresh_token` pair from Shopify), which is stored via `config.sessionStorage.storeSession(...)`. [4](#0-3) 

There is no per-shop lock, mutex, or idempotency guard around this read-refresh-write sequence, unlike the token-exchange path which explicitly deduplicates concurrent calls via `idempotentPromiseHandler` keyed on the session token. If two or more requests for the same shop arrive concurrently while the token is within the 5-minute expiry window (a common, unprivileged, legitimately-triggerable scenario — e.g., an embedded app making several parallel `fetch` calls, or overlapping webhook/background jobs using `ensureValidOfflineSession`), each request independently: reads the same stale `refreshToken` from storage, issues its own refresh request to Shopify, and unconditionally overwrites the stored session with its own response. [5](#0-4) 

Because Shopify's refresh_token endpoint issues (and typically rotates) a new refresh token on each successful call, whichever response is persisted last "wins," and the other request's returned `accessToken`/`refreshToken` pair is silently discarded from storage even though it was used in that response and may already have superseded the other token server-side. The next request that reads the "losing" refresh token (if it was already handed out and cached anywhere, or if the storage write ordering is reversed relative to Shopify's rotation) will present a token that Shopify already invalidated, causing the offline access token to become unusable until another 5-minute-expiry refresh cycle triggers — and that same lost-update race can repeat indefinitely under sustained concurrent load.

### Impact Explanation
This causes intermittent denial of service against an app's offline-token-authenticated request path (webhooks, background jobs, `ensureValidOfflineSession`, `validateAuthenticatedSession`) for the affected shop, and can produce a corrupted/inconsistent session record (mismatched `accessToken`/`refreshToken` pair) in session storage, requiring the merchant to re-authenticate or the app to detect and self-heal. It does not require any privileged access — the race is triggered purely by ordinary concurrent request volume against a single merchant's session, once `future.expiringOfflineAccessTokens` is enabled.

### Likelihood Explanation
Requires the `expiringOfflineAccessTokens` future flag to be enabled and requires two or more requests for the same shop to land within the same ~5-minute expiry window with overlapping in-flight refresh calls — realistic for busy apps, apps with multiple background workers, or clustered webhook delivery, but not guaranteed on every request. Likelihood is therefore moderate and load-dependent, matching the "Medium Risk" classification of the original report.

### Recommendation
Serialize the read-refresh-write sequence per shop (e.g., an in-process/distributed lock or promise-memoization keyed by shop id, similar to the existing `idempotentPromiseHandler` used for token exchange) so that only one refresh call is in flight per shop at a time, and all concurrent requests for that shop await and reuse the same in-flight refresh result rather than issuing independent refresh calls and independently overwriting `sessionStorage`.

### Proof of Concept
1. Enable `future: {expiringOfflineAccessTokens: true}` and set a short offline-token expiry window in a test app.
2. Store an offline `Session` whose `expires` is within `WITHIN_MILLISECONDS_OF_EXPIRY` (5 minutes) with a valid `refreshToken`. [6](#0-5) 
3. Fire two concurrent authenticated requests for the same shop (e.g., two `fetch` calls from the embedded app or two overlapping webhook deliveries) so both hit `validateAuthenticatedSession` before either has stored its refreshed session. [2](#0-1) 
4. Observe both requests independently call the OAuth refresh endpoint with the same original `refreshToken`, each get back a distinct rotated token pair, and each call `storeSession()`; the final stored session reflects only one of the two responses, and depending on write ordering vs. Shopify-side rotation, the discarded token pair may already be the one Shopify's servers now consider current, leaving the app's persisted session unusable on the next request.

// 5 minutes
export const WITHIN_MILLISECONDS_OF_EXPIRY = 5 * 60 * 1000;

export async function ensureOfflineTokenIsNotExpired(
  params: ApiAndConfigParams,
  session: Session,
): Promise<Session> {
  const {config} = params;

  if (
    config.future?.expiringOfflineAccessTokens &&
    session.isExpired(WITHIN_MILLISECONDS_OF_EXPIRY) &&
    session.refreshToken
  ) {
    const offlineSession = await refreshToken(
      params,
      session.shop,
      session.refreshToken,
    );

    await config.sessionStorage.storeSession(offlineSession);
    return offlineSession;
  }

export function refreshToken(config: ConfigInterface): RefreshToken {
  return async ({shop, refreshToken}: RefreshTokenParams) => {
    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      refresh_token: refreshToken,
      grant_type: RefreshTokenGrantType,
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };
  };

export async function ensureOfflineTokenIsNotExpired(
  session: Session,
  params: BasicParams,
  shop: string,
) {
  const {config} = params;
  if (
    config.future?.expiringOfflineAccessTokens &&
    session.isExpired(WITHIN_MILLISECONDS_OF_EXPIRY) &&
    config.distribution !== AppDistribution.ShopifyAdmin &&
    session.refreshToken
  ) {
    const offlineSession = await refreshToken(
      params,
      shop,
      session.refreshToken,
    );

    await config.sessionStorage!.storeSession(offlineSession);
    return offlineSession;
  }
  return session;
}
