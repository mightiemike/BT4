## Analysis

The reported bug class is an unbounded "push-pattern" loop over a user-growable list of participants, executed inside a critical settlement/finalization function, causing DoS/fund-lock once the list becomes large enough that the loop cannot complete within the available gas/time budget.

The closest analog in java-tron is the vote-tallying loop in `MaintenanceManager.doMaintenance()` / `countVote()`, which iterates over **every entry of `VotesStore`** — one entry per distinct account that cast a `VoteWitnessContract` in the current epoch — every time the maintenance (epoch) boundary is crossed. This method runs automatically as part of block processing (not as a discretely-gas-metered user transaction), so its cost is not paid for by whoever causes it to grow. [1](#0-0) 

This is invoked unconditionally from `doMaintenance()`, itself invoked from `DposService.applyBlock()`→`MaintenanceManager.applyBlock()`, which is called synchronously inside `Manager.processBlock()` while producing/applying every block that crosses a maintenance-time boundary. [2](#0-1) [3](#0-2) 

Any unprivileged account can add an entry to `VotesStore` by submitting a `VoteWitnessContract`. `VoteWitnessActuator.countVoteAccount()` unconditionally writes a `VotesCapsule` keyed by the voter's own address into `VotesStore` — there is no limit on the number of *distinct voting accounts*, only on the number of witnesses one account can vote for (`MAX_VOTE_NUMBER`). [4](#0-3) [5](#0-4) 

Since account creation is cheap and any account with even minimal frozen TRX (any nonzero TRON Power) can cast a vote, an attacker can create a large number of accounts and submit one `VoteWitnessContract` transaction per account within a single epoch, each transaction paid for individually at ordinary transaction cost but each only adding a fixed-size, cheap DB write. The cumulative cost of processing all these entries is deferred to the single, unmetered `countVote()` loop executed once at the next maintenance boundary — a classic "underpriced public work" pattern matching the reported push-pattern bug class: cost of an operation triggered by many independent unprivileged actors is paid by the protocol at settlement time rather than by the actors who caused it.

### Title
Unbounded VotesStore iteration in `MaintenanceManager.doMaintenance()`/`countVote()` allows attacker-inflated per-epoch vote-tally cost, risking block-processing slowdown/halt - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager.countVote()` iterates over the entire `VotesStore` — one entry per distinct voting account in the current epoch — synchronously during block processing at every maintenance boundary. Any unprivileged account can add an entry to `VotesStore` at negligible fixed per-transaction cost via `VoteWitnessActuator`, and there is no limit on the total number of distinct voters counted per epoch. This mirrors the reported "push pattern" defect: an unbounded loop over a user-inflatable collection embedded in a critical, automatically-triggered settlement routine.

### Finding Description
`VoteWitnessActuator.countVoteAccount()` writes a `VotesCapsule` into `VotesStore` keyed by the caller's own address whenever any account submits a `VoteWitnessContract`, subject only to a per-transaction cap on the number of witnesses voted for (`MAX_VOTE_NUMBER`), not a cap on the number of distinct voting accounts system-wide or per epoch.

At every epoch boundary, `MaintenanceManager.doMaintenance()` calls `countVote(votesStore)`, which opens a full iterator over `VotesStore` and processes every entry (`votes.getOldVotes()`/`getNewVotes()` per entry, then deletes it). This runs inline inside `Manager.processBlock()` (via `consensus.applyBlock()` → `DposService.applyBlock()` → `MaintenanceManager.applyBlock()`), i.e., as part of normal block application, not as a separately gas-metered/fee-charged user transaction.

Because block production/application must complete within the network's block-interval budget, an attacker who creates many low-cost accounts (minimal TRX frozen is enough to vote) and submits one vote transaction per account within a single epoch can inflate `VotesStore` to an attacker-chosen size. The cost of tallying all of these votes is deferred entirely to the single maintenance-boundary block, which must process the whole store in one pass with no early exit, no batching, and no fee recovered proportional to that processing cost.

### Impact Explanation
If the number of distinct voters in an epoch grows large enough, the `countVote()` loop (and the subsequent `forEach` loops over `countWitness` and `getAllWitnesses()` in `doMaintenance()`) can materially increase the time required to apply the maintenance-boundary block. Since this is invoked synchronously within `processBlock()`, an sufficiently inflated `VotesStore` risks delaying or failing to complete block production/application within the expected block interval — a chain-level invalid-state/halt risk analogous to the "critical funds get stuck due to unprocessable for-loop" impact described in the report, except here it affects witness reward/vote settlement and consensus liveness rather than a single dApp's fund distribution. This is an underpriced-public-work condition: attackers pay only ordinary per-transaction fees to create work whose true cost is borne by the whole network at epoch boundaries.

### Likelihood Explanation
Likelihood is moderate: creating many accounts and issuing one `VoteWitnessContract` per account is a straightforward, unprivileged, and comparatively cheap operation (bounded by ordinary account-creation and transaction fees), and there is no protocol-level cap on the number of distinct voters counted in `countVote()` per epoch. The attack requires sustained transaction volume within a single epoch window and would be visible on-chain, but nothing in the validated code path (`VoteWitnessActuator.validate()`/`execute()`, `MaintenanceManager.doMaintenance()`) prevents or throttles the number of distinct voting accounts.

### Recommendation
Bound the per-epoch cost of vote tallying, e.g., by capping/throttling the number of distinct voters processed per maintenance cycle, amortizing `countVote()` work across multiple blocks instead of a single block boundary, or charging a fee for `VoteWitnessContract` that scales with system-wide load, so that the settlement cost imposed on the protocol at maintenance time cannot be inflated by unprivileged users faster than they pay for it.

### Proof of Concept
1. Programmatically create N accounts (large N), each funded with the minimal balance required to freeze for TRON Power.
2. From each account, submit a `VoteWitnessContract` (validated/executed by `VoteWitnessActuator`, see lines 41-59 and 152-191) voting for any existing witness with `voteCount = 1`.
3. Each transaction succeeds independently at ordinary fee cost and adds one entry to `VotesStore`.
4. At the next maintenance-time boundary, `Manager.processBlock()` triggers `consensus.applyBlock()` → `MaintenanceManager.applyBlock()` → `doMaintenance()` → `countVote(votesStore)`, which must iterate all N entries synchronously while applying that single block.
5. Measure the wall-clock time of block application at the maintenance boundary as N grows, demonstrating unbounded growth in per-block processing time driven entirely by unprivileged, cheaply-generated transactions from a prior epoch.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
