### Title
Deposits that revert inside `process_sys_txs` are unconditionally purged from the deposit mempool, permanently freezing the depositor's BTC — (File: `crates/sequencer/src/runner.rs`)

### Summary
`citrea_sendRawDepositTransaction` only validates a deposit against pending-block state via `eth_call` at submission time, but the sequencer later applies the deposit against a different state in `process_sys_txs`. When that later apply reverts, `process_sys_txs` correctly reverts the working-set checkpoint for that deposit, but `produce_l2_block_inner` still calls `remove_deposits(&deposit_data)` with the *entire* fetched list — not the subset that actually succeeded — so the failed deposit is deleted from the mempool as if it had been minted.

### Finding Description
The broken binding: `deposit accepted by remove_deposits() at block-finalization time == deposit actually applied successfully by process_sys_txs()`. These two must be equal for a depositor's real BTC to correspond 1:1 with a minted-or-retried cBTC deposit; the code breaks this.

Path:
1. Attacker/depositor calls `citrea_sendRawDepositTransaction`. `send_raw_deposit_transaction` builds `dep_tx` and runs `evm.get_call(dep_tx, Some(BlockId::pending()), ...)` against the *current pending* state; if it succeeds it calls `deposit_mempool.lock().add_deposit_tx(...)`. [1](#0-0) 
2. On block production, `produce_l2_block_inner` fetches the full pending list via `fetch_deposits(...)` into `deposit_data` (this does not remove anything, and does not distinguish future success/failure). [2](#0-1) 
3. `deposit_data` is turned into `SystemEvent::BridgeDeposit` events and applied later, potentially against materially different state (other deposits/system events/user txs already applied, different EVM nonce, different bridge/vault state) inside `process_sys_txs`. [3](#0-2) 
4. If the actual apply reverts with `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful` for a deposit, `process_sys_txs` reverts the checkpoint, decrements the sov-tx `nonce`, leaves `evm_nonce` untouched, and simply `continue`s — this deposit is **not** added to `all_txs` and no error/flag propagates upward. [4](#0-3) 
5. Despite that, once the block is produced successfully, `produce_l2_block_inner` unconditionally calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the original full `deposit_data` list fetched in step 2 — including the deposit(s) that reverted in step 4 and were never actually included in `all_txs`. [5](#0-4) 

`remove_deposits` deletes matching entries from `pending_deposits`/`accepted_deposit_txs` by tx id regardless of whether that deposit was ever successfully executed. [6](#0-5) 

Root cause: `deposit_data` (the pre-fetch snapshot) is reused for mempool eviction instead of the post-execution `all_txs`/success set returned by `process_sys_txs`. There is no guard anywhere (`is_system_caller`, `Auth`, JMT witness, fork rule) that reconciles simulated-at-submission-time success with actual-at-apply-time success; the RPC-time `eth_call` is purely advisory and the failure path silently discards the deposit forever with no re-derivation, resubmission, or client notification. The depositor's Bitcoin move-to-vault transaction is already final on L1; once the deposit blob is evicted from the L2 mempool with no cBTC minted, there is no remaining path in this codebase to mint the corresponding cBTC unless the depositor manually detects the failure (RPC returned `Ok(())`, they have no signal) and re-submits identical data (which the mempool would treat as fresh only if it isn't rejected for other reasons, and by then vault/bridge state may again diverge).

### Impact Explanation
BTC funds locked in the vault for that deposit become permanently unmintable as cBTC (frozen) — the deposit record is deleted from the only queue (`DepositDataMempool`) that would otherwise re-attempt it, and `process_sys_txs` never re-adds discarded deposits. This matches the "funds permanently frozen" Critical category. It is repeatable for every deposit whose actual `process_sys_txs` execution state differs from its RPC-time `eth_call` pending-state simulation (e.g., due to intervening deposits/system events/nonce changes, or an attacker deliberately causing other state-mutating transactions to land between simulation and inclusion), affecting each victim depositor independently and requiring no elevated privilege.

### Likelihood Explanation
No special privilege is required: any unprivileged party can submit `citrea_sendRawDepositTransaction`, and any unprivileged party (including the attacker) can submit ordinary EVM/system-affecting transactions that shift pending state between the `eth_call` simulation and the deposit's real turn in `process_sys_txs` (which can be several blocks later given `deposit_mempool_fetch_limit` and FIFO ordering). The only real-world cost is the depositor's normal BTC deposit fee; the attacker's cost is ordinary L2 tx fees. The bug is deterministic given the state-divergence precondition and is triggered purely by existing sequencer code paths (`send_raw_deposit_transaction`, `process_sys_txs`, `produce_l2_block_inner`), not by mempool/DoS behavior.

### Recommendation
Track which deposits from `deposit_data` were actually included/succeeded in `process_sys_txs` (e.g., return the set of applied deposit payloads alongside `all_txs`) and only call `remove_deposits` with that successful subset; leave reverted deposits in the mempool (or explicitly re-queue/flag them and surface failure to the depositor) so they are retried in a later block rather than silently dropped.

// crates/sequencer/tests/deposit_race.rs (conceptual)
#[test]
fn deposit_simulated_success_but_actual_apply_failure_is_dropped_from_mempool() {
    // 1. Build a deposit blob D whose eth_call succeeds against pending state S0
    //    (mirrors send_raw_deposit_transaction: evm.get_call(dep_tx, Some(BlockId::pending()), ..))
    let sim_result = evm.get_call(make_deposit_tx(&deposit_bytes), Some(BlockId::pending()), None, None, &mut ws_s0, &ledger);
    assert!(sim_result.is_ok()); // LHS of binding: simulated == success

    // 2. Mutate working-set state (e.g. apply another deposit/system event consuming
    //    the same nonce/bridge state) so that the *same* deposit_bytes now reverts
    //    when process_sys_txs actually applies it as a SystemEvent::BridgeDeposit.
    mutate_state_between_sim_and_apply(&mut ws_s1);

    // 3. Run process_sys_txs with deposit_data = [deposit_bytes] against ws_s1
    let (all_txs, ws_after) = sequencer.process_sys_txs(&l2_block_info, ws_s1, &mut nonce, &evm, vec![SystemEvent::BridgeDeposit(deposit_bytes.clone())]).unwrap();
    assert!(all_txs.is_empty()); // RHS of binding: actual == failure (reverted & skipped)

    // 4. Simulate produce_l2_block_inner's finalization step:
    //    deposit_data (pre-fetch list) still contains deposit_bytes even though
    //    it was never included in all_txs.
    let removed = deposit_mempool.lock().remove_deposits(&[deposit_bytes.clone()]);
    assert_eq!(removed, 1); // BUG: deposit is purged from mempool despite never succeeding

    // Binding broken: simulated_success (true) != actual_apply_success (false),
    // yet mempool treats it as consumed -> CUSTODY never credited, BTC frozen.
    assert_ne!(sim_result.is_ok(), !all_txs.is_empty());
}

    /// Removes specific deposits from the mempool after they have been successfully included in a block
    ///
    /// # Arguments
    /// * `deposits_to_remove` - The deposits that were successfully included
    ///
    /// # Returns
    /// The number of deposits actually removed
    #[instrument(level = "trace", skip_all, ret)]
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });
