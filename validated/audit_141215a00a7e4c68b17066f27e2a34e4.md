This confirms the finding is invalid. `commit_transactions` stores accounts to accounts-db (`self.rc.accounts.store_accounts_seq`) using `collect_accounts_to_store`, computed from `processing_results` (the real `ExecutedTransaction`/`RollbackAccounts` data), and this is what feeds `update_bank_hash_stats` and the accounts lt-hash used for consensus. The `TransactionBalancesSet`/`BalanceCollector` pipeline is entirely separate and non-consensus: `BalanceCollector::collect_pre_balances`/`collect_post_balances` in `svm/src/transaction_balances.rs` read from the same `AccountLoader` used during execution, and `collect_post_balances` is invoked immediately after `account_loader.update_accounts_for_successful_tx`/`update_accounts_for_failed_tx` within the same per-transaction loop in `svm/src/transaction_processor.rs`, so it reflects the committed post-execution state, not a stale snapshot. [1](#0-0) [2](#0-1) [3](#0-2) 

Critically, `compile_collected_balances`/`TransactionBalancesSet` is only sent to `TransactionStatusSender` for RPC/status reporting — it is never read back by any subsequent transaction's CPI or sysvar logic within the same block. Any same-block CPI reading "tx1's account" reads the actual committed `AccountSharedData` from the accounts store/cache (via `AccountLoader`/`InvokeContext`), not the balance-collector snapshot, so there is no mechanism for the balance-reporting timing to leak into consensus-relevant execution or bank hash. The premise that a mis-timed balance snapshot could produce a CPI-visible lamport divergence between leader and replaying validators has no code path support. [4](#0-3) [5](#0-4)
