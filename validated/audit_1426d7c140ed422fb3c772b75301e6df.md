## Title
Overflow in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` execute-time multiply-before-divide can diverge from validate-time BigInteger/BigDecimal math and abort already-validated exchange transactions - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator.execute()` recomputes `anotherTokenQuant` using plain 64-bit `multiplyExact`/`floorDiv` on raw pool balances and the injected quantity, whereas `doValidate()` computes the very same quantity using `BigInteger` multiplication/division, which cannot overflow. This is the same bug class as the reported `getMaxLiquidityForAmount0Precise` issue: the intermediate numerator (`balance * quant`) is computed in a narrower type than what is safe for the input domain, before the division that would bring the result back into range.

### Finding Description
In `ExchangeInjectActuator`, `doValidate()` uses `BigInteger` math to compute `anotherTokenQuant` and validates it against `dynamicStore.getExchangeBalanceLimit()`: [1](#0-0) 

However `execute()` independently recomputes the same value with plain `long` arithmetic: [2](#0-1) 

The numerator `multiplyExact(secondTokenBalance, tokenQuant)` (or `firstTokenBalance * tokenQuant`) is computed in full before the division by the other balance. Because `firstTokenBalance`, `secondTokenBalance`, and `tokenQuant` are each bounded only by `dynamicStore.getExchangeBalanceLimit()` (independently checked post-hoc in `doValidate()`, not pre-checked for the multiplication itself), their product can exceed `Long.MAX_VALUE` even when the final quotient (`anotherTokenQuant`) is small and well within the balance limit — exactly the "multiply-then-divide" overflow pattern described in the report for `getMaxLiquidityForAmount0Precise`. `ExchangeWithdrawActuator.execute()` has the identical pattern using `BigInteger` in execute but the underlying arithmetic mismatch with `doValidate()`'s `BigDecimal`-based precision check exists there too: [3](#0-2) 

The core issue: `doValidate()` is the safe/wide-precision path that decides whether a transaction is admitted to a block, while `execute()` — which actually mutates state — uses a narrower/different computation. Any divergence (from overflow in the narrow path, or from rounding differences between `BigInteger`/`floorDiv` and `BigDecimal`/`divideToIntegralValue`) means a transaction that passed validation can throw `ArithmeticException` during `execute()`, which is caught and turned into `ContractExeException`: [4](#0-3) 

### Impact Explanation
This maps to the "asset or accounting corruption / DoS via protocol implementation" category. A broadcast `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction that is judged valid by consensus-critical `validate()` logic can still fail deterministically (all nodes will agree, so this is not itself a consensus divergence) inside `execute()` due to the differing arithmetic path, causing the actuator to reject a transaction the protocol's own validation logic deemed legal. In `ExchangeInjectActuator`, since `calcFee()` is invoked and `ret.setStatus(fee, code.FAILED)` is set before the exception propagates, block-inclusion fee/bandwidth for the sender may still be consumed for a transaction that should have succeeded, producing a loss for the caller and an inconsistency between "provably valid" and "actually executable" transactions — directly analogous to Alice losing funds in the referenced report when her legitimately-sized liquidity mint aborts due to overflow in the unsafe multiplication path.

### Likelihood Explanation
Exploitability requires the exchange pool balances and injected/withdrawn quantity to be large enough that `balance * quant` exceeds `2^63-1` while the resulting quotient stays under `getExchangeBalanceLimit()`. This requires an exchange pool with a very large balance ratio between the two tokens (e.g., a low-precision/high-supply TRC10 token paired against TRX), which is plausible for legitimate large-scale market makers but not guaranteed to occur under normal usage; I could not fully confirm the exact numeric value of `getExchangeBalanceLimit()` from the index in this session (default config not retrieved), so I cannot state definitively whether normal balance limits make this reachable in practice on mainnet-configured limits. This should be verified against `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java`'s `getExchangeBalanceLimit()` default/config value.

### Recommendation
- In `ExchangeInjectActuator.execute()` and `ExchangeWithdrawActuator.execute()`, use the same wide-precision (`BigInteger`) computation for `anotherTokenQuant` as is used in `doValidate()`, rather than recomputing independently with `multiplyExact`/`floorDiv` on `long`. This eliminates the possibility of `execute()` throwing where `validate()` succeeded.
- More generally, ensure `validate()` and `execute()` always share a single, common calculation function for financial quantities in `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java` and `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, so there is one source of truth and no risk of divergent overflow/rounding behavior between admission and execution.
- Add fuzz/property tests asserting `validate()`'s computed `anotherTokenQuant` always exactly equals `execute()`'s computed value across the full range of `long` balances and quantities.

### Proof of Concept
Not independently executable in this session (no sandbox access), but the arithmetic overflow condition can be demonstrated analytically: choose `firstTokenBalance` and `secondTokenBalance` such that `secondTokenBalance * tokenQuant > Long.MAX_VALUE` while `secondTokenBalance * tokenQuant / firstTokenBalance` stays below `dynamicStore.getExchangeBalanceLimit()` — e.g., `secondTokenBalance ≈ 3_000_000_000L`, `tokenQuant ≈ 3_500_000_000L` (product ≈ 1.05e19 > `Long.MAX_VALUE` ≈ 9.22e18), with `firstTokenBalance` large enough that the quotient remains within the exchange balance limit. `doValidate()` computes this safely via `BigInteger`, passes, but `execute()`'s `multiplyExact(secondTokenBalance, tokenQuant)` throws `ArithmeticException`, caught at: [4](#0-3) 
turning an otherwise-valid transaction into a failed one.
