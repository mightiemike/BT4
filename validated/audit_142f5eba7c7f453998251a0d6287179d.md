### Title
Account-ID Lexicographic Tie-Breaking in Kickout Exemption Allows Validators to Avoid Kickout and Retain Staking Rewards — (`chain/epoch-manager/src/lib.rs`)

### Summary

When the `validator_max_kickout_stake_perc` safety cap is active and multiple validators share identical online ratios and identical stakes, `compute_validators_to_reward_and_kickout` uses the account ID as the final deterministic tie-breaker to decide which validators are exempted from kickout. Because account IDs are freely chosen by users at account creation, a validator can select a lexicographically large account ID (e.g., `zzz...`) to guarantee priority in the exemption list, allowing them to avoid kickout and continue earning staking rewards even while performing below the kickout threshold.

### Finding Description

`compute_validators_to_reward_and_kickout` in `chain/epoch-manager/src/lib.rs` sorts all validators by a three-level comparator:

```
(online_ratio ASC, stake ASC, account_id ASC)
``` [1](#0-0) 

`compute_exempted_kickout` then iterates this sorted list **in reverse** (highest to lowest), adding validators to the exempt set until the exempt stake reaches `(100 - validator_max_kickout_stake_perc)%` of total stake: [2](#0-1) 

When two validators have the same online ratio and the same stake, the one with the **lexicographically larger** account ID appears later in the ascending sort and therefore earlier in the reversed iteration — it is exempted first. The validator with the smaller account ID is kicked out.

This behavior is explicitly tested and confirmed: [3](#0-2) 

The test comment reads: *"so we select the exempted validator based on the ordering of the account id"* — `test3` (lexicographically larger) is exempted while `test2` (lexicographically smaller) is kicked out, despite identical performance and stake.

A separate but related tie-break exists in validator **selection** (`OrderedValidatorStake`), which uses `Reverse(account_id)` — the opposite direction — meaning a lexicographically **smaller** account ID wins a seat when stakes are equal: [4](#0-3) 

These two tie-breaks pull in opposite directions, so a single account cannot simultaneously optimize for both. The kickout-exemption path is the more exploitable one because it allows a validator to retain their position and rewards while deliberately underperforming.

### Impact Explanation

An exempted validator that performed below the kickout threshold:
1. Is **not** kicked out for the next epoch.
2. Continues to earn staking rewards proportional to their (sub-threshold) performance.
3. Remains assigned to produce blocks and chunks, potentially degrading chain liveness.

Validators kicked out for `NotEnoughBlocks`/`NotEnoughChunks`/`NotEnoughChunkEndorsements` have their stats removed before reward calculation. An exempted validator retains their stats and earns rewards they would otherwise forfeit. This constitutes **balance manipulation** — the validator's locked stake grows via rewards that should not have been issued.

### Likelihood Explanation

The conditions required are:
1. **The stake cap must be active**: `validator_max_kickout_stake_perc` must be set such that the total stake of underperforming validators exceeds the cap. This only occurs during network instability when many validators are simultaneously offline.
2. **Online ratio tie**: The attacker's online ratio must equal that of other validators being considered for exemption. In practice, online ratios are rational numbers derived from produced/expected counts, so exact ties are possible but not guaranteed.
3. **Stake tie**: The attacker's stake must equal that of the competing validator. Stake amounts are continuous values that grow with rewards, making exact ties rare but possible (especially early in an epoch before rewards diverge).

Likelihood is **low** in normal operation but **elevated** during network instability events — precisely the scenario the safety cap is designed to handle.

### Recommendation

Replace the account-ID tie-breaker in `validator_comparator` with a pseudorandom ordering seeded from the epoch's `rng_seed` (already available in `EpochInfo`). This is consistent with how nearcore already handles other ordering decisions (e.g., `ValidatorMandates::sample` shuffles validators using a ChaCha20 RNG seeded by `hash(rng_seed || height)`): [5](#0-4) 

Alternatively, apply the same fix to `OrderedValidatorStake::key` in `validator_selection.rs` for consistency.

### Proof of Concept

The existing test `test_chunk_validators_with_same_endorsement_ratio_and_stake` already demonstrates the mechanism:

- `test2` (stake 500, endorsement 65/100) and `test3` (stake 500, endorsement 65/100) are identical in every performance metric.
- `validator_max_kickout_stake_perc = 30` triggers the cap.
- Result: `test2` is kicked out; `test3` is exempted — solely because `"test3" > "test2"` lexicographically.

An attacker registers as `zzzzzzzzzzzzzzzzzzzzzzzzzzzzzzz.near`, stakes the minimum required, and deliberately produces blocks/chunks at just below the kickout threshold. During any epoch where the stake cap is hit and other validators share the same sub-threshold performance, the attacker's account ID guarantees exemption, allowing them to retain their validator seat and continue accumulating staking rewards.     fn compute_exempted_kickout(
        epoch_info: &EpochInfo,
        accounts_sorted_by_online_ratio: &Vec<AccountId>,
        total_stake: Balance,
        exempt_perc: u8,
        prev_validator_kickout: &HashMap<AccountId, ValidatorKickoutReason>,
    ) -> HashSet<AccountId> {
        // We want to make sure the total stake of validators that will be kicked out in this epoch doesn't exceed
        // config.validator_max_kickout_stake_ratio of total stake.
        // To achieve that, we sort all validators by their average uptime (average of block and chunk
        // uptime) and add validators to `exempted_validators` one by one, from high uptime to low uptime,
        // until the total excepted stake exceeds the ratio of total stake that we need to keep.
        // Later when we perform the check to kick out validators, we don't kick out validators in
        // exempted_validators.
        let mut exempted_validators = HashSet::new();
        let min_keep_stake = Balance::from_yoctonear(
            (U256::from(total_stake.as_yoctonear()) * U256::from(exempt_perc as u128)
                / U256::from(100u128))
            .as_u128(),
        );
        let mut exempted_stake = Balance::ZERO;
        for account_id in accounts_sorted_by_online_ratio.into_iter().rev() {
            if exempted_stake >= min_keep_stake {
                break;
            }
            if !prev_validator_kickout.contains_key(account_id) {
                let validator_stake = epoch_info
                    .get_validator_by_account(account_id)
                    .map(|v| v.stake())
                    .unwrap_or_default();
                exempted_stake = exempted_stake.checked_add(validator_stake).unwrap();
                exempted_validators.insert(account_id.clone());
            }
        }
        exempted_validators
    }

        // Compares validator accounts by applying comparators in the following order:
        // First by online ratio, if equal then by stake, if equal then by account id.
        let validator_comparator =
            |left: &(BigRational, &AccountId), right: &(BigRational, &AccountId)| {
                let cmp_online_ratio = left.0.cmp(&right.0);
                cmp_online_ratio.then_with(|| {
                    // Note: The unwrap operations below must not fail because the accounts ids are
                    // taken from the validators in the same epoch info above.
                    let cmp_stake = epoch_info
                        .get_validator_stake(left.1)
                        .unwrap()
                        .cmp(&epoch_info.get_validator_stake(right.1).unwrap());
                    cmp_stake.then_with(|| {
                        let cmp_account_id = left.1.cmp(&right.1);
                        cmp_account_id
                    })
                })
            };

        let mut sorted_validators = validator_block_chunk_stats
            .iter()
            .map(|(account, stats)| (get_sortable_validator_online_ratio(stats), account))
            .collect_vec();

fn test_chunk_validators_with_same_endorsement_ratio_and_stake() {

    // Test 0-1 are block+chunk producers and 2-3 are chunk validators only.
    let accounts = vec![
        ("test0".parse().unwrap(), Balance::from_yoctonear(1000)),
        ("test1".parse().unwrap(), Balance::from_yoctonear(1000)),
        ("test2".parse().unwrap(), Balance::from_yoctonear(500)),
        ("test3".parse().unwrap(), Balance::from_yoctonear(500)),
    ];
    let epoch_info = epoch_info(
        0,
        accounts,
        vec![0, 1, 2, 3],
        vec![vec![0, 1, 2], vec![0, 1, 3]],
        PROTOCOL_VERSION,
        ShardLayout::multi_shard(num_shards, 0),
    );
    let block_validator_tracker = HashMap::from([
        (0, ValidatorStats { produced: 100, expected: 100 }),
        (1, ValidatorStats { produced: 100, expected: 100 }),

/// We store stakes in max heap and want to order them such that the validator
/// with the largest state and (in case of a tie) lexicographically smallest
/// AccountId comes at the top.
#[derive(Eq, PartialEq)]
struct OrderedValidatorStake(ValidatorStake);
impl OrderedValidatorStake {
    fn key(&self) -> impl Ord + '_ {
        (self.0.stake(), std::cmp::Reverse(self.0.account_id()))
    }
}
impl PartialOrd for OrderedValidatorStake {
    fn partial_cmp(&self, other: &Self) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}
impl Ord for OrderedValidatorStake {
    fn cmp(&self, other: &Self) -> Ordering {
        self.key().cmp(&other.key())
    }
}
