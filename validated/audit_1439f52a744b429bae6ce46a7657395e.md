### Title
Unbounded per-storage `ObsoleteAccounts` vector causes linear-scan cost on every scan/shrink/snapshot rebuild - (File: `accounts-db/src/obsolete_accounts.rs`, `accounts-db/src/account_storage_entry.rs`)

### Summary
`AccountStorageEntry` keeps an unbounded, un-deduplicated `Vec<ObsoleteAccountItem>` (`obsolete_accounts`) that records every account offset made obsolete within that storage's slot by ordinary rewrites/zero-lamporting. There is no cap and no compaction: every one of these entries persists until the whole storage is shrunk or removed, and every account-storage scan (`scan_accounts`, `scan_accounts_without_data`) rebuilds an `IntSet` from the *entire* obsolete list via `excluded_offsets()` before it can iterate the storage's live accounts.

### Finding Description
`ObsoleteAccounts::mark_accounts_obsolete` (`accounts-db/src/obsolete_accounts.rs:20-34`) simply pushes new `ObsoleteAccountItem`s onto `self.accounts: Vec<ObsoleteAccountItem>` with no bound, no deduplication, and no eviction: [1](#0-0) 

This vector is populated on the normal "rewrite" hot path: whenever `remove_dead_accounts` reclaims a slot's stale account version because it was rewritten to a newer slot (via `clean_accounts`/`remove_dead_accounts`), the old offset is appended to that storage's `obsolete_accounts` list: [2](#0-1) 

Every scan of that storage — used for shrink candidate collection, snapshot rebuild, and index verification — must first materialize the exclusion set by iterating the *entire* obsolete list via `filter_obsolete_accounts`, which is a plain linear `Vec::iter().filter()`: [3](#0-2) [4](#0-3) 

Because a normal user can cheaply cause many rewrites to distinct accounts that happen to land in the same not-yet-shrunk storage/slot (ordinary transaction traffic touching many accounts in the same slot, later superseded before that storage is shrunk), the obsolete list for a given `AccountStorageEntry` can grow proportionally to the number of accounts ever rewritten while that storage remains un-shrunk, with no upper bound analogous to the `MAX_ASSOCIATIONS` cap added in the referenced Swafe mitigation.

### Impact Explanation
`excluded_offsets()` is invoked on every `scan_accounts`/`scan_accounts_without_data` call for a storage, which are the core primitives used by:
- Shrink's `load_accounts_index_for_shrink`/`shrink_collect` path (`accounts_db.rs:2404-2486`) and the general `scan_account_storage` used for hashing/rebuild (`accounts_db.rs:3423-3456`).
- Snapshot/index generation and rebuild-from-storage code (`accounts_db.rs:5703-5787`), which scans every account in every un-shrunk storage at startup.

As the un-shrunk-storage's obsolete list grows, each of these operations pays an O(n) cost to build the exclusion `IntSet` before doing any useful work, and this cost repeats on every scan of that same storage (shrink candidate evaluation, snapshot generation, hash verification), disproportionately inflating CPU cost relative to the actual number of live accounts being processed. This matches the "disproportionate storage and CPU cost" impact category for a structure grown entirely by unprivileged account-rewrite activity.

### Likelihood Explanation
Likelihood is moderate: normal validator operation already bounds the size of a single storage's obsolete list by triggering shrink/clean regularly, similar to how `clean_accounts` naturally limits `slot_list` growth. However, unlike a hard per-key cap (as added for the Swafe association vector), there is no explicit limit on `ObsoleteAccounts` length independent of background clean/shrink cadence, so any slowdown or backlog in shrink scheduling directly and linearly increases the cost of every subsequent scan of the affected storage, without an enforced ceiling.

### Recommendation
- Track obsolete offsets in the same `IntSet<Offset>` structure used for `zero_lamport_single_ref_offsets`/`tombstone_offsets` (already O(1) lookup) instead of a linear `Vec`, so `excluded_offsets()` does not need to iterate+collect on every scan.
- Consider proactively triggering shrink for storages whose obsolete-item count/ratio exceeds a threshold, independent of the normal shrink-ratio heuristics, to bound the list size similarly to the `MAX_ASSOCIATIONS` cap pattern used in the referenced mitigation.

### Proof of Concept
1. Create an `AccountStorageEntry` and write N accounts to slot `S` (as in `test_scan_accounts_excludes_obsolete_and_tombstones`, `accounts-db/src/account_storage_entry.rs:365-431`).
2. Repeatedly rewrite subsets of these accounts to newer slots and run `clean_accounts`, causing `remove_dead_accounts` to call `mark_accounts_obsolete` and grow slot `S`'s `obsolete_accounts.accounts` vector without bound (`accounts_db.rs:5110-5123`).
3. Without triggering shrink of slot `S` (e.g., because it doesn't yet cross the shrink ratio threshold), repeatedly call `storage.scan_accounts(...)` or `scan_accounts_without_data(...)` (as exercised during snapshot generation/rebuild) and observe that `excluded_offsets()`'s cost grows linearly with the accumulated obsolete-item count on every call, even though the number of live accounts scanned stays constant.

    /// Collect the offsets that should be excluded from scans
    fn excluded_offsets(&self) -> IntSet<Offset> {
        let mut offsets: IntSet<_> = self
            .obsolete_accounts_read_lock()
            .filter_obsolete_accounts(None)
            .map(|(offset, _)| offset)
            .collect();
        offsets.extend(self.tombstone_offsets_read_lock().iter().copied());
        offsets
    }

    /// Iterate over the alive accounts in this storage, excluding obsolete accounts and tombstones.
    /// The return value is the number of values excluded from the scan.
    pub(crate) fn scan_accounts<'a>(
        &'a self,
        reader: &mut impl RequiredLenBufFileRead<'a>,
        mut callback: impl for<'local> FnMut(Offset, StoredAccountInfo<'local>),
    ) -> Result<u64, AccountsFileError> {
        let excluded_offsets = self.excluded_offsets();
        let mut num_excluded = 0;
        self.accounts.scan_accounts(reader, |offset, account| {
            if excluded_offsets.contains(&offset) {
                num_excluded += 1;
                return;
            }
            callback(offset, account);
        })?;
        Ok(num_excluded)
    }
