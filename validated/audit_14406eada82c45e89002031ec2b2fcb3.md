### Title
Unbounded old-reward-algorithm loop in `MortgageService` can cause reward withdrawal to fail or degrade node performance for long-inactive voters - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.withdrawReward()` / `queryReward()`, which back the reward-withdrawal path used by `WithdrawBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`, and the TVM `WithdrawRewardProcessor`, can execute a loop whose cost scales with `(newAlgorithmCycle - beginCycle) * numberOfVotes` when the legacy (pre-VI) reward algorithm path is taken. This is the same bug class as the C4 finding: an unbounded/attacker-influenceable loop reachable from an ordinary user action (withdraw) that can make the transaction prohibitively expensive or fail.

### Finding Description
`withdrawReward()` computes rewards from `beginCycle` (the cycle since the account's last withdrawal/vote update) up to `currentCycle`: [1](#0-0) 

The core computation, `computeReward(beginCycle, endCycle, accountCapsule)`, splits into an "old algorithm" segment (for cycles before `newRewardAlgorithmEffectiveCycle`) and a "new algorithm" (VI-based, O(votes)) segment: [2](#0-1) 

For the old segment, `getOldReward()` either delegates to the O(votes) `RewardViCalService.getNewRewardAlgorithmReward()` **only if** `allowOldRewardOpt()` is enabled; otherwise it falls back to a per-cycle loop that iterates every single cycle in the range and, inside each cycle, iterates every vote the account has cast: [3](#0-2) [4](#0-3) 

This is structurally identical to the reported `LiquidityFarming.getUpdatedAccTokenPerShare()` loop over `rewardRateLog`: a per-user reward-settlement function that loops over "elapsed time since last update" instead of a fixed-size structure. Here the loop bound is `endCycle - beginCycle` (cycles elapsed since the user's last vote/withdraw interaction) multiplied by the vote-list size, both of which grow with account inactivity and vote count and are not otherwise capped in this code path.

`beginCycle` for an account is only advanced when the account calls withdraw/vote/unfreeze (i.e., interacts with the delegation system); an account that votes once and never interacts again keeps `beginCycle` pinned at that early cycle: [5](#0-4) 

When such an account eventually withdraws (or is forced through this path via `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`/`VoteWitnessActuator`, all of which invoke `withdrawReward`), the old-algorithm branch must walk every cycle between the stale `beginCycle` and `newRewardAlgorithmEffectiveCycle`.

### Impact Explanation
Unlike the original Solidity `LiquidityFarming` case where the impact is an out-of-gas revert, in java-tron the reward computation runs as part of normal actuator execution during block processing on every full node, not metered by an independent user-supplied gas budget in the same way for account-level actuators (`WithdrawBalanceActuator`, `VoteWitnessActuator`, `UnfreezeBalanceActuator`). A sufficiently large `(endCycle - beginCycle) * votes` product can:
- Cause the TVM-triggered path (`WithdrawRewardProcessor`, reachable from smart-contract "vote for TRC20" style calls) to run out of the caller-supplied energy, reverting the transaction and effectively freezing the account's accrued reward/allowance behind an unaffordable computation, mirroring the reported "funds frozen" impact.
- Cause excessive CPU time being spent on a single transaction during block validation for the non-TVM actuator paths, which is a state-processing/availability concern for the node in the worst case, though this is gated by `allowOldRewardOpt` and the fixed historical range up to `newRewardAlgorithmEffectiveCycle` (so the range cannot grow unboundedly into the future once the VI algorithm's effective cycle has passed, unlike the original C4 issue where `rewardRateLog` grows forever).

Because the vulnerable segment is bounded above by `newRewardAlgorithmEffectiveCycle` (a fixed historical checkpoint) rather than "now", this is a real but self-limiting instance of the same bug class: it can degrade/DoS an individual account's reward withdrawal (and consume disproportionate resources for that transaction) for the specific population of accounts that voted long before the VI switch and never interacted since, but it cannot grow indefinitely into the future the way the original `rewardRateLog` loop could.

### Likelihood Explanation
Likelihood depends entirely on whether `allowOldRewardOpt()` is enabled on the network in question (a committee-governed proposal parameter, `common/src/main/java/org/tron/core/config/args/CommitteeConfig.java`, `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`). On networks/times where this optimization has not yet been turned on, the vulnerable loop is live for any account satisfying the inactivity precondition; this is a normal, unprivileged usage pattern (vote once, forget to withdraw for a long time) rather than an adversarial setup, making it plausible without any attacker cooperation, though it requires long real-world elapsed time (many cycles) to become expensive.

### Recommendation
- Ensure `allowOldRewardOpt` is enabled for all networks (mainnet/testnets) so `getOldReward()` always uses the O(votes) VI-based `RewardViCalService.getNewRewardAlgorithmReward()` path instead of the O(cycles×votes) loop.
- If the flag cannot be universally enforced, add a cap on the number of cycles processed per call in the legacy branch of `getOldReward()`/`computeReward()` in `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, and require multiple incremental withdrawals for accounts whose `beginCycle` is far behind `newRewardAlgorithmEffectiveCycle`, rather than computing the entire backlog in one call.

### Proof of Concept
1. On a network/config where `allowOldRewardOpt` is false, create an account, vote for several Super Representatives (up to `maxVoteNumber`), and let many cycles pass without calling `WithdrawBalance`, `FreezeBalance`/`UnfreezeBalance`, or re-voting, so `beginCycle` stays far below `newRewardAlgorithmEffectiveCycle`.
2. Call `WithdrawBalance` (or trigger `WithdrawRewardProcessor` via TVM `vote reward` withdrawal from a contract) for that account.
3. `MortgageService.withdrawReward()` → `computeReward()` → `getOldReward()` executes the loop at [6](#0-5)  once per cycle in the stale range, each iteration re-scanning the full vote list; the larger the inactivity window and vote count, the higher the CPU/energy cost, potentially exhausting the energy budget for the TVM-triggered path or noticeably slowing block processing for the direct actuator path.

Note: I was unable to fully verify the current default/mainnet state of `allowOldRewardOpt` (whether it is already permanently enabled on production networks) within the available search iterations; this materially affects whether the vulnerable code path is actually reachable today versus only historically/on misconfigured networks.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }
