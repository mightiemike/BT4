### Title
Denial of service via contract with many globals/data/element segments — unbounded per-call instantiation cost not covered by gas - ([File: runtime/runtime-params-estimator/src/vm_estimator.rs])

### Summary
The reported jose4j bug is a CPU-consumption DoS where an attacker supplies a cheap-to-transmit parameter (`p2c`) that forces disproportionately expensive server-side computation. The nearcore analog: a contract deployer can craft a small WASM module declaring a very large number of globals, active data segments, or active element segments. Loading/instantiating that module on every `FunctionCall` invocation performs work proportional to those counts, but the protocol's contract-loading gas fee is charged only per compiled-code byte, not per global/segment count — matching the codebase's own documented gap.

### Finding Description
`near-test-contracts` ships helper constructors — `contract_with_num_globals`, `many_data_segments_contract`, `many_element_segments_contract` — used by the gas estimator specifically to characterize this gap: [1](#0-0) [2](#0-1) 

The estimator functions that measure these costs are explicit that this is *invocation* cost (instantiation overhead on every call, not one-time compile cost): [3](#0-2) 

Each of the `Cost` enum doc-comments states plainly that this per-call cost is "not covered by gas": [2](#0-1) 

Contract loading is charged via `contract_loading_base + contract_loading_bytes * code_len`, i.e. purely a function of the compiled byte size of the module, independent of how many globals/data-segments/element-segments it declares: [4](#0-3) 

Meanwhile a related regression test confirms globals do incur real, non-trivial per-instance cost (1.6MB of `VMContext` memory for 100k globals) and that the *only* backstop that currently exists is the Wasmtime pooling-allocator's `max_core_instance_size` limit, which triggers a hard `LoadingError`/abort rather than a proportional gas charge: [5](#0-4) 

Because the wasm binary encoding of a global declaration, data segment, or element segment is only a few bytes each, an attacker can encode tens of thousands of these entries in a contract that is still small in on-disk/wire size (and therefore cheap under the byte-based loading fee), while every subsequent call to that contract forces the VM backend to spend CPU time re-initializing all of those globals/segments at instantiation — exactly the "small input parameter, large CPU cost" pattern from the jose4j `p2c` (PBES2 iteration count) vulnerability.

### Impact Explanation
Any account holder can deploy such a contract via a normal `DeployContract` action and then have any RPC caller (or their own subsequent transactions) invoke it via `FunctionCall`. Every such call burns disproportionately more validator CPU time than the gas it actually paid for, because the instantiation cost scales with segment/global count while the fee only scales with code-byte size. Repeated invocation (which any signer can trigger cheaply and repeatedly, and which is also reachable via `view` / RPC `call_function` per the adjacent `view_call_gas_limit.rs` regression note about unmetered per-call CPU) can be used to slow down chunk application across the network — a chunk/CPU-consumption DoS analogous to the jose4j CWE-400 class, without requiring any privileged role.

### Likelihood Explanation
Likelihood is high for a determined attacker: crafting a wasm module with tens of thousands of globals/data-segments/element-segments is straightforward (the test-contract generators in this very codebase demonstrate exactly how), and deployment/invocation only requires normal transaction signing rights — no validator or operator privilege needed. The severity is bounded by the `TooManyGlobals`/related `PrepareError` limits and by the Wasmtime pooling allocator's `max_core_instance_size` (which the codebase's own test shows can already be hit at 100k globals), so the practical exploitation window is the range between the per-byte-fee-cheap threshold and the hard structural limit — but the codebase's own `Adversarial*` estimator comments confirm this window currently exists and is uncharged.

### Recommendation
Charge gas fees for contract instantiation proportional to the number of globals, active data segments, and active element segments declared in the module (in addition to/instead of the flat per-byte `contract_loading_bytes` fee), mirroring how `max_blocks_per_function`/`max_functions_number_per_contract` are already limited and priced. Alternatively, tighten `LimitConfig` bounds (`max_globals_per_contract` and equivalent caps for data/element segments) low enough that worst-case instantiation cost stays proportional to the charged loading fee, and add regression coverage (parallel to `test_max_core_instance_size_breached`) verifying that the gas charged for loading a contract at the limit bounds the actual CPU/instantiation cost.

### Proof of Concept
Conceptual PoC, built from code already present in the repository's test-contract generators:
1. Use `near_test_contracts::contract_with_num_globals(N)` / `many_data_segments_contract(N)` / `many_element_segments_contract(N)` (or hand-craft an equivalent minimal wasm binary) with `N` in the tens of thousands — the resulting wasm binary remains small (a handful of bytes per entry) and thus cheap under the byte-based `contract_loading_bytes` fee. [1](#0-0) 
2. Deploy this contract on-chain via a normal `DeployContract` action from any funded account.
3. Submit a `FunctionCall` action (or `view` RPC `call_function`) invoking its exported `main`/trivial method.
4. Measure `measure_instantiation_overhead`-style timing as done by the estimator itself — the estimator's own harness demonstrates the call incurs CPU cost scaling with `N`, decoupled from the gas charged for the call: [6](#0-5) 
5. Repeat the call cheaply (each call pays only the small byte-based loading fee) to accumulate outsized CPU consumption on validators applying the chunk, analogous to sending many JWEs with large `p2c` values to a jose4j-based service.

/// Many tiny active data segments, each writing 1 byte to memory offset 0.
pub fn many_data_segments_contract(num_segments: u32) -> Vec<u8> {
    let mut module = Module::new();
    let mut types = TypeSection::new();
    types.ty().function([], []);
    module.section(&types);
    let mut funcs = FunctionSection::new();
    funcs.function(0);
    module.section(&funcs);
    let mut memories = MemorySection::new();
    memories.memory(MemoryType {
        minimum: 1,
        maximum: None,
        memory64: false,
        shared: false,
        page_size_log2: None,
    });
    module.section(&memories);
    let mut exports = ExportSection::new();
    exports.export("main", ExportKind::Func, 0);
    module.section(&exports);
    let mut data = DataSection::new();
    for i in 0..num_segments {
        data.active(0, &ConstExpr::i32_const(0), [i as u8]);
    }
    module.section(&data);
    let mut code = CodeSection::new();
    let mut f = Function::new([]);
    f.instruction(&Instruction::End);
    code.function(&f);
    module.section(&code);
    module.finish()
}

/// Warm the compile cache, then measure N invocations (instantiation + trivial execution).
/// The function body is a bare `end`, so execution cost is negligible.
fn measure_instantiation_overhead(
    metric: GasMetric,
    vm_kind: VMKind,
    contract_bytes: &[u8],
) -> GasCost {
    let config_store = RuntimeConfigStore::new(None);
    let mut config = config_store.get_config(PROTOCOL_VERSION).wasm_config.as_ref().clone();
    config.vm_kind = vm_kind;
    let config = Arc::new(config);
    let fees = Arc::new(RuntimeFeesConfig::test());
    let code = ContractCode::new(contract_bytes.to_vec(), None);
    let cache = MockContractRuntimeCache::default();
    let mut fake_external = near_vm_runner::logic::mocks::mock_external::MockedExternal::with_code(
        code.clone_for_tests(),
    );

    let mut run_once = || {
        let context = create_context(vec![]);
        let gas_counter = context.make_gas_counter(&config);
        vm_kind
            .runtime(config.clone())
            .unwrap()
            .prepare(&fake_external, Some(&cache), gas_counter, "main")
            .run(&mut fake_external, &context, Arc::clone(&fees))
            .expect("fatal_error")
    };

    // Warm: compiles and caches the module; subsequent calls only instantiate + execute.
    run_once();

    let n = 10_usize;
    let start = GasCost::measure(metric);
    for _ in 0..n {
        run_once();
    }
    start.elapsed() / n as u64
}

/// Compile and load a contract with 100k globals.
///
/// Each defined global occupies 16 bytes of a core instance's `VMContext`, so
/// globals alone add ~1.6 MB. That breaches the 1MiB `max_core_instance_size`
/// slot of the Wasmtime pooling allocator, so loading the module at
/// `Module::deserialize` fails.
///
/// With `max_globals_per_contract` set to 100k this contract still passes
/// `prepare` and is caught by the Wasmtime backstop at load time.
///
/// Pre-`FixContractLoadingError` this surfaces as `VMRunnerError::LoadingError`,
/// which the runtime maps to a zero-gas nop — the contract-loading work is left
/// uncharged. Post-feature the same failure finalizes as a gas-bearing abort
/// that charges the contract-loading fee. Either way it must not panic / crash
/// the node.
