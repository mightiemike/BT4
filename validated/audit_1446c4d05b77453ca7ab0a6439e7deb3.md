## Finding

### Title
`TransactionOutput::ensure_match_transaction_info` never checks the state-checkpoint / hot-state / position-state root hashes, letting replay-verify accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
The Astaria bug is fundamentally a "the code trusts a derived/authenticated value without re-validating the specific field that actually protects the asset" problem. The Aptos analog is in the replay/consistency check that is supposed to bind a locally re-executed `TransactionOutput` to the already-authenticated `TransactionInfo` for that version: it checks status, gas, the write-set hash, and the event-root hash, but silently skips the state-checkpoint hash fields entirely — a gap the code itself documents but does not fix.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is the function used to assert that a `TransactionOutput` produced by local execution matches the `TransactionInfo` for that version (the object whose hash is what's actually chained into the transaction accumulator and attested by validator signatures): [1](#0-0) 

It validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It never compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` to anything computed locally. The code has a TODO acknowledging this exact gap: [2](#0-1) 

This function is used as a replay/consistency check in production tooling and the chunk executor: `aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `execution/executor/src/chunk_executor/mod.rs` all call it. [3](#0-2) 

Compare this to `TransactionInfo::ensure_state_checkpoint_hash`/`state_checkpoint_hash()` accessors that exist and are used elsewhere (e.g. `do_state_checkpoint.rs`'s `get_state_checkpoint_hashes` does compare the *computed* checkpoint hash against *known* hashes from `TransactionInfo` during normal ledger update): [4](#0-3)  — showing that the codebase does have, and elsewhere does use, exactly this comparison, but `ensure_match_transaction_info` (the function specifically invoked by replay-verify tooling like `aptos-debugger` and `cli/commands.rs`, i.e. `replay_on_archive`-style flows that re-execute historical transactions and check them against already-committed/authenticated `TransactionInfo`s fetched from a node/archive) omits it.

### Impact Explanation
Replay-verify tooling (`aptos db-tool`/`aptos-debugger` replay-on-archive flows, and any chunk-executor path relying on this consistency check) is meant to catch state divergence between a node's local VM execution and the canonical, validator-signed ledger state for historical transactions. Because the state/hot-state/position-state checkpoint hashes are excluded from the comparison, a transaction whose write-set hash and event hash happen to match, but whose resulting Merkle/JellyfishMerkleTree state root diverges (e.g. due to a non-deterministic bug in state-checkpoint construction, an out-of-band feature like `COMPUTE_TRADING_NATIVE_STATE_ROOTS`'s position-state root, or a hot-state root computation bug), will be reported as a "successful replay" even though the authenticated state root has silently diverged from local execution. This exactly matches the required impact class "Hard-fork-only divergence during commit, replay, restore, or proof verification": the divergence is undetectable by the tool whose entire purpose is to detect it.

### Likelihood Explanation
This is not a hypothetical: it is the code's own documented limitation, gating the safe rollout of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` [5](#0-4) . Any bug in position-state/hot-state root computation (a newer, less battle-tested code path per the surrounding `do_state_checkpoint.rs` "trading-native" logic) would go completely unflagged by this specific safety net, even though the primary purpose of replay-verify tooling is to catch exactly this class of divergence before/instead of a hard fork.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally-computed state-checkpoint hash (and, when applicable, hot-state and position-state checkpoint hashes) against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, consistent with how `do_state_checkpoint.rs::get_state_checkpoint_hashes` already performs this comparison in the main execution pipeline. Do this before further enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production, as the code comment itself recommends.

### Proof of Concept
Not directly exploitable as a fund-loss PoC (unlike the Solidity bug); the proof is structural/code-level: `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) is invoked by `aptos-debugger`/CLI replay-verify and chunk-executor paths, and its body demonstrably never reads `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` from the `TransactionInfo` argument — confirmed by the function body and by its own inline TODO stating this precise gap.

Note on scope/confidence: I could not fully trace every call site's downstream consequence (in particular whether `chunk_executor/mod.rs`'s single call site is on a path that can persist state without independently re-verifying the accumulator, versus a path where the accumulator check elsewhere would separately catch a mismatched `TransactionInfo`). The finding is strongest and self-proven for the replay-verify tooling use case (`aptos-debugger`, CLI `replay_on_archive`), which is explicitly what the code's own TODO comment calls out as broken.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
