## Analog Finding

### Title
Oversized-receipt size clamp in `try_forward` under-charges the true bytes sent, letting a single receipt oversell its shard's granted bandwidth — ([File: runtime/runtime/src/congestion_control.rs])

### Summary
The Knox bug is: the final order that crosses a sell-out threshold is fully executed at its real size, but the bookkeeping variable (`totalContractsSold`) is capped to the threshold instead of tracking the real total, so the vault ends up holding more obligations than its capped counter shows, causing insolvency. The direct analog in nearcore is `ReceiptSinkV2::try_forward`, which admits an oversized receipt against a byte budget (`OutgoingLimit.size`, seeded by the bandwidth scheduler's `GrantedBandwidth`) but decrements that budget using a *clamped* size instead of the receipt's real size, letting the shard actually send more bytes than it was granted.

### Finding Description
`try_forward` in [1](#0-0)  explicitly "pretends" any receipt whose real size exceeds `max_receipt_size` is only `max_receipt_size` for the purpose of the forwarding check: [2](#0-1) 

It then compares this clamped `size` against `forward_limit.size` and, on success, decrements the limit by the same clamped value rather than the receipt's true wire size: [3](#0-2) 

`forward_limit.size` originates from the bandwidth scheduler's per-link grant (`GrantedBandwidth`, seeded into `OutgoingLimit.size`) which is the deterministic, agreed-upon byte budget for how many receipt bytes a sender shard may push to a receiver shard in one chunk, as documented in [4](#0-3) . The scheduler's grant math (`try_grant_bandwidth`, `grant_more_bandwidth`) assumes every unit of granted bandwidth corresponds to one real byte forwarded [5](#0-4) .

If a receipt's real, borsh-serialized size exceeds `max_receipt_size` — which the code itself acknowledges is possible due to a known bug (issue #12606, referenced directly in the comment) — then forwarding it consumes `real_size` bytes of actual network/state bandwidth while only `max_receipt_size` bytes are deducted from the tracked budget. This is exactly the Knox pattern: the "final order" (the oversized receipt) is filled in full at its true size, but the accounting counter is capped at the threshold (`max_receipt_size`), leaving the shard's remaining "budget" artificially inflated by `real_size - max_receipt_size`. Subsequent receipts can then be forwarded on top of that inflated remaining budget, so the link's true cumulative bytes sent this chunk can exceed the amount the bandwidth scheduler actually granted for that link.

The same clamp-to-`max_receipt_size` logic is also applied when generating the next height's bandwidth *requests* from buffered receipt-group sizes [6](#0-5) , so an attacker's oversized receipt is permanently under-represented in both admission and future request generation.

### Impact Explanation
The bandwidth-scheduler invariant that "bytes actually forwarded on a link ≤ bytes granted on that link" is the backpressure mechanism protecting a receiving shard from being flooded with more receipt bytes than it planned to receive and validate this chunk, and it is one of the two budgets (with congestion-control gas) that bound the size of `ChunkStateWitness` documented at [7](#0-6) . A contract that can trigger creation of an oversized outgoing receipt (via the pre-existing #12606 gap) can use this under-accounting to push more real bytes onto a shard link than the bandwidth scheduler computed room for, contributing to state-witness/memory bloat beyond the size budget the protocol relies on for liveness and stateless-validation feasibility. This is a resource/backpressure-bypass rather than a direct fund-theft bug, and the underlying trigger (creating an oversized receipt) is itself a distinct, already-tracked issue (#12606) rather than something newly introduced here — the clamp in `try_forward` is a deliberate, acknowledged mitigation to avoid such receipts getting permanently stuck, at the cost of this under-accounting.

### Likelihood Explanation
Reaching this path requires first exploiting the separate, already-known #12606 gap to produce a receipt whose real size exceeds `max_receipt_size`; `try_forward`'s clamp then applies automatically whenever `forward_limit.size` for the link is at least `max_receipt_size` (e.g., the "allowed shard" with `outgoing_receipts_big_size_limit`). Since the root cause (oversized-receipt creation) is a pre-existing, documented issue rather than a new discovery, and the clamp behavior is an intentional, called-out workaround rather than an overlooked accounting bug, the practical likelihood of this compounding into an unbounded/impactful oversell is low to moderate and bounded by however large #12606 lets a single receipt grow.

### Recommendation
When forwarding a receipt whose real size exceeds `max_receipt_size`, decrement `forward_limit.size` by the receipt's true wire size (saturating at zero) instead of the clamped value, so the tracked remaining budget always reflects actual bytes sent; alternatively, close the underlying #12606 gap so no receipt can ever exceed `max_receipt_size` in the first place, making the clamp path unreachable.

### Proof of Concept
1. Craft a contract call sequence that triggers the #12606 gap to produce a single outgoing receipt whose borsh-serialized size is `max_receipt_size + N` bytes (destined for a shard for which the current sender is the "allowed shard", so `forward_limit.size` starts at `outgoing_receipts_big_size_limit`, e.g. 4.5 MiB).
2. When `try_forward` processes this receipt, `size` is clamped to `max_receipt_size`; since `forward_limit.size >= max_receipt_size`, the receipt is forwarded and `forward_limit.size -= max_receipt_size` (not `-= real_size`).
3. The remaining `forward_limit.size` is now `N` bytes higher than it should be, allowing the sender to forward `N` additional bytes of subsequent receipts on the same link this chunk beyond what the bandwidth scheduler granted, exceeding the deterministic per-link byte budget that other invariants in the system assume is respected.     fn try_forward(
        receipt: Receipt,
        gas: Gas,
        mut size: u64,
        shard: ShardId,
        outgoing_limit: &mut HashMap<ShardId, OutgoingLimit>,
        outgoing_receipts: &mut Vec<Receipt>,
        apply_state: &ApplyState,
        stats: &mut ReceiptSinkStats,
    ) -> Result<ReceiptForwarding, RuntimeError> {
        // There is a bug which allows to create receipts that are above the size limit. Receipts
        // above the size limit might not fit under the maximum outgoing size limit. Let's pretend
        // that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
        // See https://github.com/near/nearcore/issues/12606
        let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
        if size > max_receipt_size {
            tracing::debug!(
                target: "runtime",
                receipt_id=?receipt.receipt_id(),
                size,
                max_receipt_size,
                "try_forward observed a receipt with size exceeding the size limit",
            );
            size = max_receipt_size;
        }

        // Default case set to `Gas::MAX`: If no outgoing limit was defined for the receiving
        // shard, this usually just means the feature is not enabled. Or, it
        // could be a special case during resharding events. Or even a bug. In
        // any case, if we cannot know a limit, treating it as literally "no
        // limit" is the safest approach to ensure availability.
        let default_gas_limit = Gas::MAX;

        // Since bandwidth scheduler, a shard is not allowed to send any receipts if it doesn't have a grant.
        let default_size_limit = 0;

        let default_outgoing_limit =
            OutgoingLimit { gas: default_gas_limit, size: default_size_limit };
        let forward_limit = outgoing_limit.entry(shard).or_insert(default_outgoing_limit);

        let admission_gas = if ProtocolFeature::ClampOutgoingGasAdmission
            .enabled(apply_state.current_protocol_version)
        {
            gas.min(apply_state.config.congestion_control_config.allowed_shard_outgoing_gas)
        } else {
            gas
        };

        if forward_limit.gas >= admission_gas && forward_limit.size >= size {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "forwarding buffered receipt");
            outgoing_receipts.push(receipt);
            forward_limit.gas = forward_limit.gas.saturating_sub(gas);
            forward_limit.size -= size;
            stats.forwarded_receipts.entry(shard).or_default().add_receipt(size, gas);

### 7. Bandwidth scheduler

Congestion control limits *gas*; the bandwidth scheduler limits *bytes per link*. It
runs once at the start of chunk apply (`run_bandwidth_scheduler`,
`bandwidth_scheduler/mod.rs:44`; called at `lib.rs:1767`) and produces
`GrantedBandwidth` that seeds each `OutgoingLimit.size`. Determinism is essential:
every shard runs the identical algorithm on the identical inputs (bandwidth requests
+ shard statuses) and must compute the same grants; a `sanity_check_hash` over the
shard set is chained into the persistent state to catch divergence
(`mod.rs:124-137`).

    /// Try to grant some bandwidth on the link.
    /// On success returns TryGrantOutcome::Granted
    /// If granting more bandwidth is not possible because of some restrictions, returns TryGrantOutcome::NotGranted.
    fn try_grant_bandwidth(&mut self, link: &ShardLink, bandwidth: Bandwidth) -> TryGrantOutcome {
        if !self.is_link_allowed(link) {
            // Not allowed to send anything on this link. Receiver is too congested or had a missing chunk.
            return TryGrantOutcome::NotGranted;
        }

        let sender_budget = self.sender_budget.get(&link.sender).copied().unwrap_or(0);
        let receiver_budget = self.receiver_budget.get(&link.receiver).copied().unwrap_or(0);

        if sender_budget < bandwidth || receiver_budget < bandwidth {
            // Sender or receiver can't send this much as they would go over the per-shard budget.
            return TryGrantOutcome::NotGranted;
        }

        // Ok, grant the bandwidth
        self.sender_budget.insert(link.sender, sender_budget - bandwidth);
        self.receiver_budget.insert(link.receiver, receiver_budget - bandwidth);
        self.decrease_allowance(link, bandwidth);
        self.grant_more_bandwidth(link, bandwidth);

        TryGrantOutcome::Granted
    }

    /// Add new granted bandwidth to the link. Doesn't adjust allowance or budgets.
    fn grant_more_bandwidth(&mut self, link: &ShardLink, bandwidth: Bandwidth) {
        let current_granted = self.granted_bandwidth.get(link).copied().unwrap_or(0);
        let new_granted = current_granted.checked_add(bandwidth).unwrap_or_else(|| {
            tracing::warn!(target: "runtime", ?link, "granting bandwidth on link would overflow, this is unexpected, granting max bandwidth instead");
            Bandwidth::MAX
        });
        self.granted_bandwidth.insert(*link, new_granted);
    }

## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 21MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.
