## Title
Panic Handler Emits Ledger-Unbound Response, Breaking Response-to-Version Binding Invariant - (`api/src/error_converter.rs`)

### Summary
Every non-panic API response path (success and structured errors) attaches `X-Aptos-Chain-Id`, `X-Aptos-Ledger-Version`, `X-Aptos-Ledger-Oldest-Version`, `X-Aptos-Epoch`, etc., derived from the `LedgerInfo` used to serve the request, via the `generate_success_response!`/`generate_error_response!` macros. [1](#0-0) [2](#0-1)  But the panic path in `panic_handler`/`build_panic_response` builds a bare `AptosError` JSON payload with `into_response()` and never attaches any of these headers, regardless of whether the panicking handler had already fetched a valid `LedgerInfo` before panicking. [3](#0-2) 

### Finding Description
`CatchPanic::new().with_handler(panic_handler)` is installed as the outermost middleware layer around the entire route tree (per the code's own comment, the last `.with()` call is the outermost layer, executing first and wrapping everything below it, including all endpoint handlers and `HeadersSanityCheck`). [4](#0-3) 

Any unprivileged, malformed, or out-of-range request input that triggers a Rust panic inside a handler — for example an out-of-range index, bad table key/handle, malformed bytecode/view input, or any `unwrap()`/indexing panic reachable from user-controlled request data — is caught by this top-level `CatchPanic` layer and converted via `panic_handler` into a response built purely from `build_panic_response`, with none of the `X-Aptos-*` ledger headers set. [3](#0-2) 

This is architecturally different from every other error path in the API, which routes errors through the `BasicError`/`BasicErrorWith404`/etc. types generated by `generate_error_response!`, all of which require (and attach) a `LedgerInfo` reference so the returned error is explicitly version-bound. [5](#0-4)  The panic path bypasses this entirely, even in cases where the handler had already successfully resolved a `LedgerInfo` before panicking later in the same handler (e.g., while processing a bad index/table key against already-fetched ledger state).

### Impact Explanation
The API's documented invariant is that "every authenticated API response is bound to an explicit ledger version" — reflected in the OpenAPI spec, which declares `X-Aptos-Ledger-Version`/`X-Aptos-Chain-Id`/`X-Aptos-Epoch` as required response headers on virtually every status code, including error statuses like 400/403/404/500/503. [6](#0-5)  A panic-triggered 500 response silently violates this invariant by omitting all ledger-context headers. Clients or SDKs that assume these headers are always present on any response (as the spec promises) could misinterpret a version-unbound failure as belonging to whatever version they last observed, or crash/mis-cache when the expected headers are absent.

However, this is a response-metadata/consistency defect, not one that corrupts committed state, storage, or proof material: no accumulator root, Merkle proof, transaction/event proof, write set, or persisted state is affected. The underlying VM/storage/proof computations that occurred before the panic are unaffected; the bug is confined to the shape of the emitted HTTP error response object.

### Likelihood Explanation
Triggering this requires finding an unprivileged input that causes an actual Rust panic inside an API handler (e.g., an indexing panic, `unwrap()` on attacker-influenced data, or arithmetic overflow) — such panics are bugs in their own right and are not guaranteed to exist in the current handler code for any of the mentioned surfaces (index, table key, view, bytecode). The review did not identify a live panic-inducing input path in the current handlers; it only confirms that if such a panic exists, `panic_handler` would produce a header-incomplete response.

### Recommendation
Have `panic_handler`/`CatchPanic` propagate ledger context — e.g., store the current request's best-known `LedgerInfo` (or at least chain ID) in request-local extensions as soon as it is resolved in `Context`, and have `panic_handler` read it back to populate `X-Aptos-Chain-Id`/`X-Aptos-Ledger-Version`/etc. on the panic response, or explicitly document/clearly mark panic-path 500 responses as "unbound" so clients can distinguish them from version-bound failures.

### Proof of Concept
1. Identify (or introduce, for testing) a handler code path reachable from unprivileged input (e.g., a raw table item lookup with a malformed key) that panics after the handler has already read a valid `LedgerInfo`.
2. Send the crafted request; `CatchPanic::new().with_handler(panic_handler)` intercepts the panic and calls `panic_handler(err)`. [7](#0-6) 
3. Inspect the HTTP response: it will contain the JSON body from `build_panic_response("internal error")` with status matching `AptosErrorCode::InternalError`, but will lack `X-Aptos-Chain-Id`, `X-Aptos-Ledger-Version`, `X-Aptos-Epoch`, etc. [3](#0-2) 
4. Compare against any other 500 response produced via `BasicError::internal_with_code(...)`, which does include these headers, confirming the asymmetry.

pub fn panic_handler(err: Box<dyn Any + Send>) -> Response {
    error!("Panic captured: {:?}", err);
    build_panic_response("internal error".into())
}

fn build_panic_response(error_string: String) -> Response {
    Json(AptosError::new_with_error_code(
        error_string,
        AptosErrorCode::InternalError,
    ))
    .into_response()
}
