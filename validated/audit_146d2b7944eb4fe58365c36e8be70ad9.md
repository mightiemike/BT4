### Title
Nakamoto `calculate_matured_miner_rewards` silently drops `_user_burns`, permanently unminting user-burn-support participants' matured rewards during the epoch2→Nakamoto transition - (File: `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
`NakamotoChainState::calculate_matured_miner_rewards` calls the shared `find_mature_miner_rewards`, which returns `(recipient, user_burns, parent, reward_info)`, but discards `user_burns` and packages only `recipient`/`parent_reward` into `MaturedMinerRewards`. Because the Nakamoto persistence and payout paths (`finish_block`, block-header insertion) never call `insert_matured_child_user_reward` and never pass user rewards to `process_matured_miner_rewards`, any legitimate epoch2-style user-burn-support participant whose block reward matures while the tip is being processed by the Nakamoto code path has their earned coinbase/fee share permanently dropped (never minted, never credited).

### Finding Description
Equality that should hold: `total STX minted for a matured block == miner_share + parent_share + sum(user_burn_shares)`, where each share is computed by `StacksChainState::calculate_miner_reward` (`stackslib/src/chainstate/stacks/db/accounts.rs:804-980`) proportional to burnchain-commit-burn contribution.

In the epoch2.x code path (`stackslib/src/chainstate/stacks/db/blocks.rs:5099-5129` → `stackslib/src/chainstate/stacks/db/mod.rs:2823-2943`), all three components of the tuple returned by `find_mature_miner_rewards` are preserved end-to-end: the miner reward, every `user_payout` (looped and persisted via `insert_matured_child_user_reward`, `mod.rs:2928-2935`), and the parent reward.

In the Nakamoto code path, `calculate_matured_miner_rewards` (`stackslib/src/chainstate/nakamoto/mod.rs:385-411`) does:
```rust
Ok(Some((recipient, _user_burns, parent, reward_info))) => Some(MaturedMinerRewards {
    recipient,
    parent_reward: parent,
    reward_info,
}),
```
`_user_burns` is bound and immediately discarded (the underscore-prefix confirms deliberate non-use, not a placeholder). `MaturedMinerRewards` (`nakamoto/mod.rs:603-622`) has no field for user rewards at all, and its `consolidate()` only returns `[recipient, parent_reward]`. Downstream, `finish_block` (`nakamoto/mod.rs:4842-4859`) calls `process_matured_miner_rewards(clarity_tx, &rewards.recipient, &[], &rewards.parent_reward)` — the empty slice `&[]` is hard-coded where user rewards would go. Persistence-side, `nakamoto/mod.rs:4060-4086` only calls `insert_matured_child_miner_reward` and `insert_matured_parent_miner_reward`; there is no `insert_matured_child_user_reward` call anywhere in the Nakamoto module.

Root cause: `find_mature_miner_rewards` (shared, epoch-agnostic) still computes `user_rewards` for any `MinerPaymentSchedule` entries with `vtxindex > 0` (i.e., real user-burn-support participants) recorded in the `payments`/schedule data (`accounts.rs:1006, 1054-1068`). This scheduling data can legitimately contain such entries from epoch2.x blocks (created before Nakamoto activation, when `UserBurnSupportOp` was a valid consensus operation — still handled by `burn/distribution.rs`, `burn/sortition.rs`, `burnchains/burnchain.rs`). During the transition, `MINER_REWARD_MATURITY` (100 blocks) windows straddle the epoch3.0 boundary: a pre-Nakamoto (epoch2.x) block containing user-burn-support entries can mature while the *current tip* is already a Nakamoto block, causing maturation to be processed via `NakamotoChainState::calculate_matured_miner_rewards` instead of the epoch2 `blocks.rs` path.

Attacker's exact input: broadcast a `UserBurnSupportOp` (with own BTC, minority stake) supporting a miner's block-commit in a pre-Nakamoto tenure whose reward maturation window crosses the Nakamoto activation boundary. No privileged role, signer key, or majority stake is required — only a valid on-chain burn operation broadcast, which is within the defined attacker capability ("broadcast Bitcoin block-commits, leader keys and burn ops with their own BTC").

Existing guards do not catch this: `check_tenure_tx`, `verify_signer_signatures`, `validate_vrf_seed`, and the various `validate_*_static`/`common_validate_against_burnchain` checks validate block/tenure structure and signer quorum, not the reward-tuple handling internal to `calculate_matured_miner_rewards`; none of them re-derive or cross-check that `user_burns.len() == 0` is actually true for a matured schedule before discarding it.

### Impact Explanation
This is a bounded, non-chain-split reward mis-payment: the miner's own share is computed correctly (its denominator still includes the dropped users' burn amounts, so the miner is not overpaid relative to the coinbase-split formula), but the dropped user shares are simply never minted into the liquid STX supply and never credited to any account — a permanent, non-recoverable loss for the affected user-burn-support participant. This matches the "High" impact category: "a poison or reward mis-payment bounded to fees" — the impact is confined to specific participants' fee/coinbase share, not a network-wide invalid/valid-block divergence or chain split. Two honest nodes will agree on the resulting (deficient) chain state deterministically since both would run the same buggy Nakamoto code, so no fork/split occurs, but the affected user's funds are permanently frozen/unclaimed.

### Likelihood Explanation
Requires: (1) a `UserBurnSupportOp` legitimately submitted by an unprivileged participant supporting a miner's block-commit in an epoch2.x tenure, and (2) the `MINER_REWARD_MATURITY`-block maturation window for that specific block landing after the chain has transitioned to Nakamoto block-processing (i.e., a transitional-era scenario). This is deterministic and reproducible given those chainstate preconditions, requires only the cost of the attacker's own burn transaction (minority BTC, single op), and needs no majority stake or additional privilege. Its likelihood is bounded by how often `UserBurnSupportOp` is used in practice and by whether a live network's Nakamoto-activation transition window still had unmatured epoch2 user-burn-support entries at cutover — a narrow but real historical/transitional condition.

### Recommendation
Update `NakamotoChainState::calculate_matured_miner_rewards` and `MaturedMinerRewards` to retain and propagate `user_burns`: add a `user_rewards: Vec<MinerReward>` field to `MaturedMinerRewards`, pass it through `finish_block`'s call to `process_matured_miner_rewards` instead of `&[]`, and persist each entry via `insert_matured_child_user_reward` alongside `insert_matured_child_miner_reward`/`insert_matured_parent_miner_reward` in the Nakamoto block-append code path (`nakamoto/mod.rs:4060-4086`), mirroring the epoch2 handling in `stacks/db/mod.rs:2911-2942`.

### Proof of Concept

    /// Find the latest miner reward to mature, assuming that there are mature rewards.
    /// Returns a list of payments to make to each address -- miners and user-support burners -- as
    /// well as an info struct about where the rewards took place on the chain.
    pub fn find_mature_miner_rewards(
        clarity_tx: &mut ClarityTx,
        sortdb_conn: &Connection,
        tip_stacks_height: u64,
        mut latest_matured_miners: Vec<MinerPaymentSchedule>,
        parent_miner: MinerPaymentSchedule,
    ) -> Result<Option<(MinerReward, Vec<MinerReward>, MinerReward, MinerRewardInfo)>, Error> {
        let mainnet = clarity_tx.config.mainnet;
        if tip_stacks_height <= MINER_REWARD_MATURITY {
            // no mature rewards exist
            return Ok(None);
        }

        let reward_height = tip_stacks_height - MINER_REWARD_MATURITY;

        let latest_matured_miners_head = latest_matured_miners
            .first()
            .expect("latest_matured_miners should not be empty");
        assert!(latest_matured_miners_head.vtxindex == 0);
        assert!(latest_matured_miners_head.miner);

        let users = latest_matured_miners.split_off(1);
        let miner = latest_matured_miners
            .pop()
            .expect("BUG: no matured miners despite prior check");

        let reward_info = MinerRewardInfo {
            from_stacks_block_hash: miner.block_hash.clone(),
            from_block_consensus_hash: miner.consensus_hash.clone(),
            from_parent_stacks_block_hash: parent_miner.block_hash.clone(),
            from_parent_block_consensus_hash: parent_miner.consensus_hash.clone(),
        };

        // what epoch was the parent miner's block evaluated in?
        let parent_evaluated_snapshot =
            SortitionDB::get_block_snapshot_consensus(sortdb_conn, &parent_miner.consensus_hash)?
                .expect("FATAL: no snapshot for evaluated block");

        let parent_evaluated_epoch =
            SortitionDB::get_stacks_epoch(sortdb_conn, parent_evaluated_snapshot.block_height)?
                .expect("FATAL: no epoch for evaluated block");

        // was this block penalized for mining a forked microblock stream?
        // If so, find the principal that detected the poison, and reward them instead.
        let poison_recipient_opt =
            StacksChainState::get_poison_microblock_report(clarity_tx, reward_height)?
                .map(|(reporter, _)| reporter);

        if let Some(ref _poison_reporter) = poison_recipient_opt.as_ref() {
            test_debug!(
                "Poison-microblock reporter {} at height {}",
                &_poison_reporter.to_string(),
                reward_height
            );
        } else {
            test_debug!("No poison-microblock report at height {}", reward_height);
        }

        // calculate miner reward
        let (parent_miner_reward, miner_reward) = StacksChainState::calculate_miner_reward(
            mainnet,
            parent_evaluated_epoch.epoch_id,
            &miner,
            &miner,
            &users,
            &parent_miner,
            poison_recipient_opt.as_ref(),
        );

        // calculate reward for each user-support-burn
        let mut user_rewards = vec![];
        for user_reward in users.iter() {
            let (parent_reward, reward) = StacksChainState::calculate_miner_reward(
                mainnet,
                parent_evaluated_epoch.epoch_id,
                user_reward,
                &miner,
                &users,
                &parent_miner,
                poison_recipient_opt.as_ref(),
            );
            assert_eq!(parent_reward.total(), 0);
            user_rewards.push(reward);
        }

        Ok(Some((
            miner_reward,
            user_rewards,
            parent_miner_reward,
            reward_info,
        )))
    }
