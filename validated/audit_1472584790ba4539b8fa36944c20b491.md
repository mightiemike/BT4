### Title
`TransactionOutput::ensure_match_transaction_info` never validates the position-state / hot-state checkpoint hashes, letting `replay_on_archive` accept a diverged native-position state root as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the local-integrity check used by `db-tool`'s archive replay-verification path to confirm that a freshly re-executed `TransactionOutput` matches the authenticated `TransactionInfo` pulled from an archive/backup. It checks status, gas, write-set hash and event-root hash, but explicitly (per its own inline TODO) skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`. This means when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, the native-position Merkle root that is actually committed/authenticated in `TransactionInfoV1` is never cross-checked by replay verification against locally recomputed execution — a divergence in the position state root would go completely undetected.

### Finding Description
`TransactionInfoV1` (types/src/transaction/mod.rs, `builder_v1`) carries a `position_state_checkpoint_hash` field which is populated by `DoStateCheckpoint::compute_position_checkpoint` (execution/executor/src/workflow/do_state_checkpoint.rs) whenever `compute_trading_native_state_roots` is set, and this hash is hashed into `TransactionInfo` and therefore into the transaction accumulator root (`do_ledger_update.rs::assemble_transaction_infos`), i.e. it is part of the authenticated, consensus-committed ledger state.

`TransactionOutput::ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) is the function relied on by:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` — re-executes historical transactions from an archive and calls `ensure_match_transaction_info` to assert the freshly computed output matches the archived, ledger-info-proven `TransactionInfo`.
- `aptos-move/cli/src/commands.rs` — CLI replay/debug tooling using the same comparator.

The function validates `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`, but its own code comment states:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```
It then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` to anything locally computed.

This is a genuine break of the "proof and storage pivot" invariant that "restore paths / replay paths must not reinterpret committed data into a different ledger state" and "authenticated API and proof-bearing responses must stay bound to the right ... root": the archive-replay path is specifically the tool relied upon to catch a case where a validator (or the executor logic itself, e.g., a bug in `compute_position_checkpoint`'s SMT extension logic) produced a wrong native-position root that nonetheless got signed into a `LedgerInfoWithSignatures` by 2f+1 validators. Once that bad root is in the archive, replay-verify — the last line of defense for detecting exactly this class of divergence — silently passes.

### Impact Explanation
If the on-chain, consensus-committed `position_state_checkpoint_hash` for some version diverges from what correct VM/state execution would produce (due to any bug in the native-position SMT/checkpoint code, a storage corruption, or a malicious majority), `replay_on_archive`/CLI replay verification — the tool operators and auditors use to detect exactly such divergence against an archived, ledger-info-proven history — will report the replay as successful. This directly defeats the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong ... state proof accepted as valid" classes: a corrupted/incorrect committed native-position state root is accepted as valid by the verification tooling, hiding a wrong-committed-state bug that would otherwise require a hard fork to fix, potentially for an extended period before manual/other detection.

### Likelihood Explanation
The gap is unconditional whenever `ensure_match_transaction_info` is called on a `TransactionInfoV1` produced with `compute_trading_native_state_roots` on — no attacker action is needed to trigger the missing check; it's a structural gap in the verification tool itself. The comment in the code acknowledges the developers are aware of this and intend to fix it "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," which confirms the feature is still gated/experimental in this codebase and the check is a known-incomplete TODO. Because it depends on this native-position feature being enabled (not yet default per the code and comments elsewhere, e.g. `// TODO(HotState): this is currently None in testnet and mainnet`), current mainnet exposure is limited to when/if that feature is turned on, which the recommendation below should gate.

### Recommendation
Extend `ensure_match_transaction_info` to compute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionInfo` variant) against locally recomputed values before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on any network, exactly as the existing TODO comment already specifies. At minimum, `replay_on_archive.rs` should independently assert these fields are populated and consistent before reporting a chunk/version as successfully replayed.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-logic gap, not an exploitable state-transition bug per se. Demonstration path:
1. Enable `compute_trading_native_state_roots` (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`).
2. Construct/replay a chunk where the archived `TransactionInfoV1.position_state_checkpoint_hash` differs from what local execution via `DoStateCheckpoint::compute_position_checkpoint` would produce (e.g., by feeding a manipulated archive backup, or by having a bug in `compute_position_checkpoint`'s SMT extension produce a different root than what was originally committed).
3. Run `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` on that range.
4. Observe `ensure_match_transaction_info` returns `Ok(())` (assuming status/gas/write-set-hash/event-root-hash still match), because it never inspects `position_state_checkpoint_hash`, `state_checkpoint_hash`, or `hot_state_checkpoint_hash` — the replay is reported as verified even though the authenticated native-position root was never actually validated against local execution.
