### Title
Unbounded `listExchanges`/`ListExchangesServlet` RPC allows attacker-inflated `ExchangeStore`/`ExchangeV2Store` to cause per-request DoS - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getExchangeList()` calls `getExchangeStoreFinal(...).getAllExchanges()`, which iterates and sorts the *entire* exchange store with no cap, unlike its paginated sibling `getPaginatedExchangeList()` which enforces `EXCHANGE_COUNT_LIMIT_MAX`. Because `ExchangeCreateActuator` imposes only a flat fee (`getExchangeCreateFee()`) and no per-account or global cap on the number of exchanges, an unprivileged funded account can grow the store to attacker-chosen size and then repeatedly hit the public `listExchanges`/`GET /wallet/listexchanges` endpoint to force unbounded O(N log N) work (full iteration + sort + protobuf serialization) per request.

### Finding Description
- `ExchangeCreateActuator.execute()`/`doValidate()` only checks the caller's balance against `calcFee()` (`dynamicStore.getExchangeCreateFee()`) and basic token/balance sanity — there is no limit on how many exchange pairs one account (or the whole chain) may create. [1](#0-0)  Each successful transaction writes into both `exchangeStore`/`exchangeV2Store` via `Commons.putExchangeCapsule` semantics (directly inlined in the actuator) and increments `dynamicStore.getLatestExchangeNum()`. [2](#0-1) 
- `Commons.putExchangeCapsule` (used by `ExchangeInjectActuator`, `ExchangeTransactionActuator`, `ExchangeWithdrawActuator`) also writes to both stores unconditionally with no size checks. [3](#0-2) 
- The unpaginated read path, `Wallet.getExchangeList()`, calls `getExchangeStoreFinal(...).getAllExchanges()` and builds a response containing every exchange in the store — no bound at all. [4](#0-3) 
- `ExchangeStore.getAllExchanges()` performs a full iterator scan and a sort comparator over every record. [5](#0-4) 
- This method is directly reachable by unauthenticated clients via both gRPC `listExchanges` and HTTP `/wallet/listexchanges` (`ListExchangesServlet.doPost`/`doGet`), with no offset/limit and no exchange-count cap applied. [6](#0-5) [7](#0-6) 
- By contrast, the paginated variant `Wallet.getPaginatedExchangeList()` clamps `limit` to `EXCHANGE_COUNT_LIMIT_MAX`, proving the codebase itself recognizes the need for bounding but failed to apply it to `getExchangeList()`. [8](#0-7) 
- `ListExchangesServlet` extends `RateLimiterServlet`, which only throttles request *rate* (requests/sec), not the cost of each individual request; it does nothing to bound the O(N) work performed once a request is admitted.

None of the standard checks (`validateSignature`, permission weights, `DecodeUtil.addressValid`, fork gates) are relevant here since exchange creation is a normal, permitted operation for any funded account, and the vulnerability is in the unbounded read path, not the write path's authorization.

### Impact Explanation
This matches TRON's "DoS via RPC-API" bounty class: sustained CPU (full-store iteration + sort + protobuf marshalling) and memory (materializing full `List<ExchangeCapsule>` and building `ExchangeList` protobuf) consumption on every call to `listExchanges`/`/wallet/listexchanges`, scaling linearly (with sort overhead ~N log N) in the attacker-inflated store size N. Repeated invocation by the same or other unauthenticated clients can degrade or stall the node's RPC/API service for all users. Impact is scoped to the RPC/API layer; it does not corrupt consensus state or forge value.

### Likelihood Explanation
- Preconditions: attacker only needs a funded account and enough TRX to pay `getExchangeCreateFee()` per exchange creation, plus small token balances for the two sides of each pair (which can be minimized, e.g., using TRX vs. a self-issued asset with balance 1). No privileged role, no fork gate, no special config needed.
- Cost scales linearly with the number of exchanges the attacker wants to inject (K transactions × fee), which is a real but bounded, attacker-controlled expenditure — feasible for a moderately funded attacker over time since there is no cap preventing arbitrarily large K.
- Once the store is inflated, the attack is fully repeatable at near-zero marginal cost (unauthenticated GET/POST requests), and the amplification factor (small write cost vs. sustained large query cost) is characteristic of a DoS amplification bug.

### Recommendation
- Apply the same pagination/limit enforcement to `Wallet.getExchangeList()` (and the corresponding gRPC/HTTP `listExchanges` handlers) as already exists in `getPaginatedExchangeList()` — e.g., deprecate/remove the unbounded `listExchanges` API or internally cap it to `EXCHANGE_COUNT_LIMIT_MAX` and require pagination for larger result sets.
- Consider adding a global or per-account cap on the number of open exchanges created via `ExchangeCreateActuator`, or scale `getExchangeCreateFee()` to disincentivize mass creation.
- Consider caching/pre-sorting exchange lists incrementally at write time to avoid full-store sort on every read.

```java
@Test
public void unboundedListExchangesDoS() {
  int N = 200_000; // attacker-feasible via repeated ExchangeCreateContract txs
  DynamicPropertiesStore dps = dbManager.getDynamicPropertiesStore();
  for (int i = 0; i < N; i++) {
    ExchangeCapsule capsule = new ExchangeCapsule(
        ByteString.copyFromUtf8("attacker"), i, i,
        "_".getBytes(), ("tok" + i).getBytes());
    capsule.setBalance(1, 1);
    // simulate what ExchangeCreateActuator does for each accepted tx
    Commons.putExchangeCapsule(capsule, dps,
        dbManager.getExchangeStore(), dbManager.getExchangeV2Store(),
        dbManager.getAssetIssueStore());
  }
  dps.saveLatestExchangeNum(N);

  long start = System.currentTimeMillis();
  ExchangeList list = wallet.getExchangeList(); // unpaginated, unbounded
  long elapsed = System.currentTimeMillis() - start;

  // Expected (if bounded): elapsed and list size stay bounded regardless of N.
  // Actual: list.getExchangesList().size() == N, elapsed grows ~linearly/superlinearly with N,
  // demonstrating unbounded per-request work driven entirely by attacker-controlled store size.
}
```
Raw request-level reproduction: broadcast K `ExchangeCreateContract` transactions (each paying `getExchangeCreateFee()`), then repeatedly `POST http://<node>/wallet/listexchanges` and observe response latency/memory growing with K, with no server-side cap on returned entries.

```java
  public ExchangeList getPaginatedExchangeList(long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
    }
    limit =
        limit > EXCHANGE_COUNT_LIMIT_MAX ? EXCHANGE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestExchangeNum ? latestExchangeNum : end;

    ExchangeList.Builder builder = ExchangeList.newBuilder();
    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ExchangeCapsule::calculateDbKey).map(key -> {
      try {
        return getExchangeStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getExchangeStore(),
            chainBaseManager.getExchangeV2Store()).get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(exchangeCapsule -> builder
            .addExchanges(exchangeCapsule.getInstance()));
    return builder.build();
```
