### Title
Unchecked `long` Overflow in Resource-Usage (Bandwidth/Energy) Window Accumulator Can Silently Corrupt Accounting - (File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java)

### Summary
`ResourceProcessor` (the shared base class for `BandwidthProcessor` and `EnergyProcessor`, and duplicated for TVM-triggered resource accounting in `RepositoryImpl`) tracks each account's resource usage as a windowed, scaled accumulator, analogous to the TWAMM "scaled proceeds" pattern in the report: a raw value is multiplied by a fixed scaling constant (`precision` / `WINDOW_SIZE_PRECISION`) every time usage is recorded, and the accumulated value is later divided back down to recover real usage. By default this arithmetic is performed with plain, unchecked Java `long` multiplication/addition, which silently wraps around on overflow instead of throwing, exactly the failure mode described in the external report.

### Finding Description
`ResourceProcessor.increase()` computes the windowed average usage via: [1](#0-0) 
and `getNewWindowSize()`/`getUsage()` perform similarly unchecked multiplications and additions to merge usage and window sizes: [2](#0-1) 

Both paths are gated by a `hardenCalculation()` flag: when disabled, plain `long` arithmetic is used (silent wraparound on overflow); when enabled, the same computation is redone with `BigInteger` and `StrictMathWrapper.addExact`, which throws `ArithmeticException` on overflow instead. The exact same duplicated pattern exists in the TVM/actuator resource-delegation path used during contract execution: [3](#0-2) 

The project's own test suite confirms both behaviors explicitly, including a test named for the exact failure mode described in the report — silent overflow when the safe/"hardened" mode is off: [4](#0-3) 

This mirrors the TWAMM bug precisely: a scaling factor (`precision`, and for V2 windows, `WINDOW_SIZE_PRECISION`) is applied via unchecked arithmetic to accumulate/decay a running value across the lifetime of an account's resource window, and the correctness of the computation depends on no overflow occurring. Unlike the audited TWAMM contract, where the developers explicitly acknowledged and scoped the risk, java-tron's own hardening flag and dedicated overflow test (`testIncreaseOverflowSilentWithoutHardening`) show this exact overflow class was identified internally as a real risk requiring a `BigInteger`-based fix — but that fix is only active when the corresponding governance-controlled flag (`allowHardenResourceCalculation`, referenced throughout `ResourceProcessor`, `BandwidthProcessor`, `EnergyProcessor`, `RepositoryImpl`, and `ProposalUtil`) is turned on.

The equivalent pattern also exists in the TRC10 Bancor-style exchange math (`ExchangeProcessor` vs. `SafeExchangeProcessor`), again gated by a `useStrictMath`/`hardenedCalc` flag rather than always using safe arithmetic: [5](#0-4) [6](#0-5) 

### Impact Explanation
If the unhardened path remains the operative default on a running network (i.e., the `allowHardenResourceCalculation` / `allowHardenExchangeCalculation` committee proposal has not been activated), then reaching the overflow threshold in `increase()`, `increaseV2()`, or `getNewWindowSize()` would silently corrupt an account's bandwidth/energy usage window or the TRC10 exchange pool balance rather than raising an error. Consequences include:
- Incorrect resource-limit accounting (an attacker or a large staker could end up with an incorrectly negative/huge "used" value, effectively bypassing energy/bandwidth throttling — a DoS/fairness issue for the resource market), reachable via ordinary transaction broadcast and delegate/undelegate resource operations, and via any TVM contract call that consumes energy (`RepositoryImpl.increase`).
- Corrupted TRC10 exchange pool balances if `ExchangeProcessor`'s unchecked path (used by `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`) is exercised with extreme balances, matching the report's "exchange/market math" category.

### Likelihood Explanation
This is lower-confidence than the exact TWAMM scenario because I could not verify, in this pass, (a) the current on-chain/default value of the `allowHardenResourceCalculation` and `allowHardenExchangeCalculation` proposal flags in `DynamicPropertiesStore.java` (a search specifically for the default getters in that file did not return matches, so I cannot confirm whether the "hardened"/safe path is already the enforced default on the live network), and (b) the exact values of `WINDOW_SIZE_PRECISION`/`PRECISION`/`TotalEnergyLimit` needed to compute the realistic magnitude required to trigger overflow for a legitimate large-stake account. The presence of a dedicated internal test (`testIncreaseOverflowSilentWithoutHardening`) strongly suggests the java-tron team already identified and is actively mitigating this exact overflow class, which both validates the analog and suggests it may already be substantially hardened or scheduled for activation. Given this uncertainty, likelihood should be treated as Medium rather than confirmed-High until the live default value of the hardening flags and the precise overflow thresholds are checked directly against a running node/config.

### Recommendation
- Verify whether `allowHardenResourceCalculation` and `allowHardenExchangeCalculation` are active by default on mainnet; if not, prioritize activating them via the committee-proposal mechanism, since the unhardened path is provably capable of silent overflow (per the project's own test suite).
- Consider removing the unhardened, unchecked-`long` code path entirely (rather than gating it behind a proposal) for all future logic, since carrying a "known-unsafe" arithmetic mode as the default behavior for years mirrors exactly the risk pattern that caused the TWAMM incident (an acknowledged-but-unaddressed overflow surface persisting far longer than anticipated).
- Audit `RepositoryImpl.increase()`/`recover()` (the TVM-triggered duplicate of `ResourceProcessor.increase()`), since it is reachable directly from arbitrary smart-contract execution and does not appear to share the same test coverage as `ResourceProcessorHardenTest`.

### Proof of Concept
Not independently reproduced against a live/testnet node in this pass. The project's own regression test constitutes an in-repo proof that the unhardened path overflows silently under crafted `lastUsage`/`usage` inputs: [7](#0-6) 
A full external PoC would additionally need to demonstrate that `lastUsage`/`usage` values of this magnitude are reachable through normal freeze/delegate/undelegate/energy-consumption flows without requiring already-corrupted state, which was not confirmed in this analysis.

  private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,
      long windowSize, long newUsage) {
    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(lastUsage).multiply(BigInteger.valueOf(lastWindowSize))
          .add(BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize)));
      return bi.divide(BigInteger.valueOf(newUsage)).longValueExact();
    }
    return (lastUsage * lastWindowSize + usage * windowSize) / newUsage;
  }

  private long divideCeil(long numerator, long denominator) {
    return (numerator / denominator) + ((numerator % denominator) > 0 ? 1 : 0);
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }

  private long getUsage(long usage, long windowSize) {
    if (hardenCalculation()) {
      return BigInteger.valueOf(usage).multiply(BigInteger.valueOf(windowSize))
          .divide(BigInteger.valueOf(precision)).longValueExact();
    }
    return usage * windowSize / precision;
  }

  private long getUsage(long oldUsage, long oldWindowSize, long newUsage, long newWindowSize) {
    if (hardenCalculation()) {

          .add(BigInteger.valueOf(newUsage).multiply(BigInteger.valueOf(newWindowSize)));
      return bi.divide(BigInteger.valueOf(precision)).longValueExact();
    }
    return (oldUsage * oldWindowSize + newUsage * newWindowSize) / precision;

  private long increase(long lastUsage, long usage, long lastTime, long now, long windowSize) {
    long averageLastUsage;
    long averageUsage;
    if (hardenResourceCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize);
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision), biWindowSize);
    } else {
      averageLastUsage = divideCeil(lastUsage * precision, windowSize);
      averageUsage = divideCeil(usage * precision, windowSize);
    }

    if (lastTime != now) {
      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay, VMConfig.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {

        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
