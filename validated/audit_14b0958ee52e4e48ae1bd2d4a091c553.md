Confirmed root cause: `RuntimeContractIdentifier::resolve` in `runtime/runtime/src/contract_code.rs` resolves `AccountContract::GlobalByAccount(account_id)` to whatever code currently sits at `TrieKey::GlobalContractCode { identifier: AccountId }` at execution time — there is no pinning to a hash the user reviewed, and no delay/notice mechanism before the new code takes effect.

### Title
Global contract "AccountId" deploy mode lets the owner rug-pull dependent accounts' code with no timelock or notice - (File: runtime/runtime/src/global_contracts.rs, runtime/runtime/src/contract_code.rs)

### Summary
`DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` lets an account owner redeploy the code that *other* accounts have opted into via `UseGlobalContractAction`, and the new code becomes live for all dependents immediately — no warning period, no two-step commit, no ability for a dependent to freeze on the version they audited.

### Finding Description
`GlobalContractDeployMode::AccountId` is explicitly documented as allowing "the owner to update the contract for all its users" [1](#0-0) . Any account that references that contract via `UseGlobalContractAction { contract_identifier: GlobalContractIdentifier::AccountId(owner) }` stores a `AccountContract::GlobalByAccount(account_id)` pointer rather than a fixed code hash [2](#0-1) .

At execution time, `RuntimeContractIdentifier::resolve` re-reads the current code for that `AccountId` identifier from `TrieKey::GlobalContractCode` on every call — there's no snapshot or pinning of the version a dependent account originally trusted: [3](#0-2) 

The owner can redeploy new code for this identifier at any time via `action_deploy_global_contract`, which simply overwrites the trie value for the shared `GlobalContractCode` key once the nonce advances, with no waiting period, no two-phase commit, and no on-chain signal beyond the deploy transaction itself: [4](#0-3) 

This is precisely the "admin front-running / bad timing" class from the reference report: a party who controls a shared piece of state (here, the global-contract owner) can change behavior that other, unprivileged users depend on, and that change takes effect immediately and silently for everyone who has opted in via `UseGlobalContractAction`. A dependent account has no mechanism to require advance notice, review a queued update, or opt out before it becomes active. Unlike `CodeHash` mode, which is explicitly documented as immutable, `AccountId` mode offers no analogous safety valve.

### Impact Explanation
Any account (e.g., a wallet-abstraction provider, DAO tooling account, or shared library account) that many other accounts reference via `UseGlobalContractAction::AccountId` can have its logic swapped out instantly. Since function calls on a dependent account execute whatever code currently resolves for the referenced `AccountId` [5](#0-4) , an owner (or an attacker who compromises/purchases the owner's key) can publish a benign contract to build trust, wait for dependent accounts to attach deposits/permissions expecting known behavior, then redeploy malicious code that misappropriates deposits sent in subsequent function calls to those dependent accounts — a concrete unauthorized value-movement vector reachable purely by ordinary transaction senders (the global-contract owner and any account that opted in).

### Likelihood Explanation
Reaching this requires only two ordinary transactions any account can send: `DeployGlobalContractAction` (redeploy) and `UseGlobalContractAction`/`FunctionCall` (the victim's opt-in and subsequent calls) — no privileged role, validator, or network-level capability is needed. The pipelining code even explicitly acknowledges that code identity can change within a chunk and blocks colliding function calls only within the *same* chunk as the deploy [6](#0-5) ; it does nothing to protect calls in later chunks, which is the normal case for any real cross-account dependency.

### Recommendation
Introduce an explicit versioning/commit scheme for `GlobalContractDeployMode::AccountId`: require dependent accounts to reference a specific version/nonce (or hash) they've reviewed, and/or require a mandatory delay between a new deploy being broadcast and it becoming the resolved code for existing `UseGlobalContractAction` references, giving dependents a window to migrate away or re-approve before the swap takes effect.

### Proof of Concept
1. Owner account `O` deploys benign global contract `v1` via `DeployGlobalContractAction { deploy_mode: AccountId }` (see `action_deploy_global_contract` in `runtime/runtime/src/global_contracts.rs`).
2. Victim account `V` sends `UseGlobalContractAction { contract_identifier: AccountId(O) }`, binding `V`'s `AccountContract` to `GlobalByAccount(O)` [2](#0-1) .
3. `V` (or third parties interacting with `V`) sends deposits via `FunctionCall` to `V`, trusting `v1`'s logic (e.g., a deposit-then-refund flow).
4. `O` submits a new `DeployGlobalContractAction { deploy_mode: AccountId }` with malicious code `v2` that, e.g., transfers incoming deposits to an attacker-controlled account instead of refunding.
5. Because `RuntimeContractIdentifier::resolve` always reads the current `TrieKey::GlobalContractCode` for identifier `AccountId(O)` [7](#0-6) , the very next `FunctionCall` receipt against `V` executes `v2`, diverting the incoming deposit with no warning to the caller that the contract logic changed since `V` was set up.
