### Title
Division-by-zero / unbounded energy limit when `totalEnergyWeight` is zero but an account still has frozen balance in `EnergyProcessor.calculateGlobalEnergyLimit` - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit()` protects the "new reward" code path against a zero `totalEnergyWeight` denominator, but the legacy (`allowNewReward()==false`) path only relies on a Java `assert` statement, which is compiled out / disabled at runtime unless the JVM is started with `-ea`. If `totalEnergyWeight` is ever zero while an individual account still carries a non-zero frozen-for-energy balance, the subsequent division either throws an uncaught `ArithmeticException` (hardened path) or produces `Infinity`/`NaN` collapsing to an effectively unlimited energy grant (legacy double-math path). This mirrors the Carapace M-8 pattern of dividing by an aggregate ("totalSTokenUnderlying"/`totalEnergyWeight`) that can reach zero while a per-user quantity ("totalSupply"/frozen balance) remains non-zero.

### Finding Description
`calculateGlobalEnergyLimit` at [1](#0-0)  reads:

```java
long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
if (hardenCalculation()) {
  return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
} else {
  long energyWeight = frozeBalance / TRX_PRECISION;
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

The zero-guard (`return 0`) only fires when `allowNewReward()` is true. When that chain parameter is `false` (an older/legacy configuration still supported by the codebase), the code falls into the `else` branch and only has `assert totalEnergyWeight > 0;` as protection. Java assertions are disabled by default in production JVMs (no `-ea` flag), so this assertion is a no-op at runtime — it neither throws nor prevents execution from continuing with `totalEnergyWeight == 0`.

If execution continues with `totalEnergyWeight == 0`:
- In the hardened path, `calculateGlobalLimitV1` at [2](#0-1)  performs `BigInteger.valueOf(weight).multiply(...).divide(BigInteger.valueOf(totalWeight))`, which throws `ArithmeticException: BigInteger divide by zero` when `totalWeight == 0`.
- In the legacy (non-hardened) double-math path, `(double) totalEnergyLimit / totalEnergyWeight` evaluates to `Infinity` (since `totalEnergyLimit` is normally positive), and multiplying by `energyWeight` yields `Infinity`, which casts to `Long.MAX_VALUE` when the result is assigned to a `long` return type — effectively granting the account unlimited energy.

`calculateGlobalEnergyLimit` is invoked from `useEnergy()` at [3](#0-2) , which is on the hot path of every TVM contract-invoking transaction that consumes energy. No caller in this chain catches `ArithmeticException`.

The pattern is structurally identical to the reported Carapace bug: a per-account/per-share numerator (frozen balance / `totalSupply`-like quantity) remains non-zero while the aggregate denominator (`totalEnergyWeight`/`totalSTokenUnderlying`-like quantity) can become zero, and the code's only defense against the zero denominator is either an environment-specific/legacy-only guard or an assumption that later proves false, leading to a division-by-zero crash or unintended unlimited value.

### Impact Explanation
- If reached via the hardened path, any transaction touching `useEnergy()` for an account with legacy energy-limit calculation active will throw `ArithmeticException`, which is not caught anywhere up the call stack shown, causing that transaction (and potentially block-level processing depending on caller) to fail unexpectedly — a denial-of-service against energy accounting reachable from ordinary broadcast transactions executing smart contracts.
- If reached via the legacy double-math path, the account effectively receives unbounded energy (`Long.MAX_VALUE`), bypassing energy metering entirely — this is an accounting/resource-limit-bypass vulnerability that could be used to execute unmetered contract calls, undermining the resource-fee model of the network.

### Likelihood Explanation
This requires `dynamicPropertiesStore.allowNewReward()` to be `false` (a legacy configuration flag that may exist on chains that have not activated the new reward algorithm) together with `totalEnergyWeight` reaching `0` (or negative) while some account retains `frozeBalance > 0`. Because Java assertions are disabled by default in essentially all production deployments, the `assert` provides no actual protection once this state is reached. I was not able to conclusively trace, within the remaining budget, a concrete on-chain sequence of freeze/unfreeze events that forces `totalEnergyWeight` to zero while an individual account's frozen balance stays non-zero (this would require deeper analysis of how `TotalEnergyWeight` is aggregated/decremented across freeze/unfreeze/delegate/undelegate actuators, e.g. in `DelegateResourceActuator`, `UnfreezeBalanceV2Actuator`, and `Wallet`/`RepositoryImpl`). This should be verified further, but the code's own zero-guard logic (`allowNewReward() && totalEnergyWeight <= 0`) demonstrates that the maintainers already recognized `totalEnergyWeight <= 0` as a reachable state under the new-reward path — the same invariant is not durably enforced on the legacy path.

### Recommendation
Remove the reliance on `assert` for a production safety invariant. Replace:
```java
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
```
with an unconditional guard, e.g.:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
so that both the legacy and new-reward code paths are protected against a zero (or negative) denominator regardless of runtime assertion settings, consistent with the existing zero-guard already present in `calculateGlobalEnergyLimitV2` at [4](#0-3) .

### Proof of Concept
Not fully constructable within the available investigation: reproducing the zero-`totalEnergyWeight`-with-nonzero-`frozeBalance` state requires driving `DynamicPropertiesStore.getTotalEnergyWeight()` to `0` (via a sequence of freeze/unfreeze/delegate actuator calls, or a legacy/migration edge case) while `allowNewReward()` is `false` and an account's `AccountCapsule.getAllFrozenBalanceForEnergy()` remains positive, then invoking `useEnergy()` (e.g., by broadcasting a smart-contract-invoking transaction from that account). A minimal unit-level PoC would directly call `EnergyProcessor.calculateGlobalEnergyLimit(accountCapsule)` with `dynamicPropertiesStore.saveTotalEnergyWeight(0)`, `allowNewReward()` returning `false`, and `accountCapsule` having non-zero frozen energy balance, and observe either an uncaught `ArithmeticException` (hardened path) or a return value of `Long.MAX_VALUE`/negative overflow (legacy path).
