### Title
Unconditional Relayer Fee Transfer Executes Regardless of ERC-20/Base-Token Transfer Outcome — (`File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

---

### Summary

In `inner_rlp_execute`, the relayer fee is dispatched as an **independent** NEAR promise before the main `ft_transfer` (or base-token transfer) promise is even scheduled. Because the fee promise is not chained on the outcome of the main action, it executes and settles regardless of whether the underlying transfer succeeds or fails. A user whose ERC-20 transfer fails (e.g., insufficient NEP-141 balance, token contract panic, storage-deposit failure) still loses the full fee from their ETH-implicit wallet balance.

---

### Finding Description

In `inner_rlp_execute` (lines 374–384), when the parsed transaction is an `EthEmulationKind::ERC20Transfer` or `EthEmulationKind::EOABaseTokenTransfer` with a non-zero fee, the code creates an independent promise batch and immediately appends a `Transfer` action to the relayer:

```rust
// lib.rs lines 374-384
if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { fee, .. })
| TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
    &transaction_kind
{
    if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
        let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
        env::promise_batch_action_transfer(refund_promise, *fee);
    }
}
``` [1](#0-0) 

`env::promise_batch_create` creates a **standalone** receipt batch that is not linked to any other promise via `.then()`. In NEAR's execution model, independent promises execute unconditionally — they are not cancelled or rolled back if a sibling promise fails.

The main ERC-20 transfer action is built separately (lines 433–457) as a chained promise:

```
storage_balance_of → nep_141_storage_balance_callback → ft_transfer → rlp_execute_callback
``` [2](#0-1) 

The fee promise and the main transfer promise are two independent promise trees. The NEAR runtime schedules and executes them independently. If `ft_transfer` panics (insufficient balance, unregistered receiver after a race, token contract error), the fee receipt has already been committed and will still deliver `fee` yoctoNEAR to the relayer.

The fee amount is derived from the user's signed Ethereum transaction fields `gas_price * gas_limit`, converted to yoctoNEAR:

```rust
// internal.rs lines 59-64
let tx_fee = {
    let wei_amount = tx.max_fee_per_gas.saturating_mul(tx.gas_limit).min(VALUE_MAX).low_u128();
    NearToken::from_yoctonear(wei_amount.saturating_mul(MAX_YOCTO_NEAR as u128))
};
``` [3](#0-2) 

The `rlp_execute_callback` does check `promise_result(0)` and returns `success: false` on failure, but by that point the fee receipt has already been dispatched and cannot be recalled: [4](#0-3) 

---

### Impact Explanation

**Broken invariant:** A user should only pay the relayer fee if the underlying token transfer succeeds.

**Corrupted value:** The wallet contract's NEAR balance is reduced by `fee` yoctoNEAR even when the `ft_transfer` receipt fails. The relayer receives `fee` without having delivered the service.

**Scope match:** Loss of funds from an ETH-implicit account, reachable by an ordinary user submitting a signed Ethereum transaction through any relayer. The wallet contract is the production contract deployed for all ETH-implicit accounts on NEAR mainnet.

---

### Likelihood Explanation

The trigger conditions are:
1. User signs an ERC-20 transfer with a non-zero `gas_price` (common — relayers require compensation).
2. The `ft_transfer` fails at execution time. This can happen due to:
   - Insufficient NEP-141 token balance (user spent tokens between signing and execution).
   - The token contract panics for any reason.
   - The `storage_balance_of` call fails or returns an unexpected value, causing `nep_141_storage_balance_callback` to return early with `success: false` without ever calling `ft_transfer` — yet the fee promise was already dispatched. [5](#0-4) 

Condition 2 is reachable by any ordinary user action (spending tokens in a concurrent transaction) and requires no privileged access.

---

### Recommendation

Gate the relayer fee on the outcome of the main transfer. Instead of dispatching the fee as an independent promise, pass the fee amount into `rlp_execute_callback` (similar to how `CallerDeposit` is already passed) and only dispatch the fee transfer when `promise_result(0)` is `Successful`:

```rust
// In rlp_execute_callback, on success:
PromiseResult::Successful(value) => {
    if let Some(RelayerFee { account_id, yocto_near }) = relayer_fee {
        let fee_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(fee_promise, NearToken::from_yoctonear(yocto_near));
    }
    ExecuteResponse { success: true, success_value: Some(value), error: None }
}
```

This mirrors the existing `CallerDeposit` refund pattern already used in the same callback for the failure case. [6](#0-5) 

---

### Proof of Concept

1. Deploy the wallet contract for an ETH-implicit account `0xALICE`.
2. Mint 10 NEP-141 tokens to `0xALICE` on token contract `TOKEN`.
3. Alice signs an Ethereum ERC-20 `transfer(0xBOB, 10)` transaction with `gas_price > 0` and `gas_limit > 0` such that `fee = gas_price * gas_limit * MAX_YOCTO_NEAR` equals, say, 1 milliNEAR.
4. Before the relayer submits, Alice spends all 10 tokens in a separate NEAR transaction (draining her NEP-141 balance to 0).
5. The relayer submits the signed ERC-20 transfer via `rlp_execute`.
6. **Observed:** The fee promise (1 milliNEAR → relayer) executes and settles. The `ft_transfer` receipt fails with insufficient balance. `rlp_execute_callback` returns `success: false`.
7. **Expected:** No fee should be paid since the transfer was not delivered.
8. **Net effect:** Alice's wallet loses 1 milliNEAR; the relayer is paid; no tokens moved. [7](#0-6) [8](#0-7)
