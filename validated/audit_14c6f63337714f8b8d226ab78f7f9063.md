### Title
`Chainbase.getKeysNext` O(n) CPU blowup from attacker-controlled uncommitted market order writes - ([File: chainbase/src/main/java/org/tron/core/db2/core/Chainbase.java])

### Summary
`MarketPairPriceToOrderStore.getPriceKeysList` delegates to `Chainbase.getKeysNext(Snapshot, byte[], long)`, which computes `limitLevelDB = limit + collectionList.size()` where `collectionList` is built by `SnapshotImpl.collectUnique` over **every** uncommitted key mutation in the store's current snapshot chain, not just the target pair. An attacker can broadcast many `MarketSellAssetContract` transactions in the same block/uncommitted window to inflate `collectionList`, which forces every subsequent `matchOrder()` call (for any pair) to perform a proportionally larger LevelDB/RocksDB iterator scan and a proportionally larger `Stream` filter, while only paying a flat `MarketSellAssetContract` fee and normal bandwidth cost.

### Finding Description
`MarketSellAssetActuator.matchOrder` calls `pairPriceToOrderStore.getPriceKeysList(headKey, MAX_MATCH_NUM+1, makerPriceNumber, true)` once per transaction whenever the opposite pair has any existing orders [1](#0-0) . This routes through `MarketPairPriceToOrderStore.getPriceKeysList`/`getKeysNext` [2](#0-1)  into `Chainbase.getKeysNext(Snapshot, byte[], long)`:

- `collectUnique` walks the entire uncommitted snapshot chain of the store and builds a map of *every* key touched (across *all* pairs), not just the queried pair [3](#0-2) .
- The disk read size is `limitLevelDB = limit + collectionList.size()`, i.e., it grows linearly with the total number of uncommitted writes to this store, regardless of which pair triggered the call [4](#0-3) .
- After that oversized read, the code filters/streams/sorts the combined LevelDB/RocksDB and snapshot lists (`levelDBList`, `keyList`) [5](#0-4) .

Because `collectUnique`'s HashMap is rebuilt from scratch on every call (no caching across calls within the same uncommitted window), and its size scales with an attacker's own pending order count (which the attacker fully controls by broadcasting many `MarketSellAssetContract` transactions with unique — even GCD-reduced-to-1 — price ratios before the enclosing snapshot is committed/flushed), every subsequent `matchOrder()` invocation on *any* pair in that same uncommitted window pays CPU cost proportional to the attacker's total uncommitted order count.

The existing protection, `MAX_MATCH_NUM`, only bounds the number of *matched orders processed inside the while-loop* of a single transaction (see `exceedMaxMatchNumLimit` test) [6](#0-5) ; it does not bound the size of the single upfront `getPriceKeysList`/`getKeysNext` call, whose cost is driven by `collectionList.size()` — a value entirely outside the caller's control and unrelated to `MAX_MATCH_NUM`.

Fee/bandwidth accounting for this actuator is a flat `calcFee()` (`dynamicStore.getMarketSellFee()`) [7](#0-6)  plus ordinary transaction-size bandwidth — neither scales with the DB scan cost the transaction imposes on the node.

Note: the premise that "very large coprime ratios" make `findGCD` return 0 is incorrect — `MarketUtils.findGCD` returns 0 only when one operand is 0 (disallowed) and returns 1 for coprime pairs, as confirmed by `testFindGCD` [8](#0-7) . This does not change the underlying issue: distinctness of price keys (via unique ratios, GCD=1 or otherwise) is exactly what an attacker needs to create many distinct uncommitted keys in the store, inflating `collectionList.size()`.

### Impact Explanation
This is a DoS-via-protocol-implementation issue: an unprivileged account can, at ordinary transaction cost, force every full node processing subsequent market transactions (its own or anyone else's, on any trading pair) to perform CPU/I-O work proportional to the number of uncommitted market orders the attacker created, rather than proportional to the fee/bandwidth paid. This matches the "DoS via the TRON protocol implementation" bounty class — bandwidth-cheap transactions causing disproportionate CPU/iteration work on all full nodes processing the block.

### Likelihood Explanation
- No privileged role required: any funded account can broadcast `MarketSellAssetContract` transactions.
- Requires depositing enough of the sell asset to place many orders (economic cost bounded by the smallest tradable unit and bandwidth/fee per tx), and requires many transactions to land in the same block or before the snapshot layer is flushed/merged — feasible since TRON blocks can contain hundreds of transactions.
- The effect is repeatable each time the attacker accumulates new uncommitted orders.
- Severity is moderated by the number of transactions that actually fit in a block (bandwidth/energy limits, block size), but the per-call cost is still O(n) unbounded by any protocol-level cap distinct from block capacity itself.

### Recommendation
- In `Chainbase.getKeysNext(Snapshot, byte[], long)`, avoid growing `limitLevelDB` by the size of the *entire* uncommitted collection; instead compute the needed extra margin only from entries matching the target pair (already filtered into `snapshotList`), or restructure `collectUnique` to be scoped/prefixed by pair key up front rather than collecting all keys and filtering afterward.
- Cache/reuse the `collectUnique` result across multiple `getKeysNext` calls within the same head snapshot instead of rebuilding it on every call.
- Consider bounding the number of open (unmatched) orders a single account/pair can have pending in an uncommitted window, or charge fee/bandwidth proportional to current store congestion for `MarketSellAssetContract`.

### Proof of Concept
JUnit-style micro-benchmark (extending existing test infra such as `MarketSellAssetActuatorTest`/`RevokingDbWithCacheNewValueTest`):
```java
@Test
public void benchmarkMatchOrderScalesWithUncommittedOrderCount() throws Exception {
  InitAsset();
  String sellTokenId = TOKEN_ID_ONE;
  String buyTokenId = TOKEN_ID_TWO;

  // Phase 1: attacker floods N unique-price sell orders on token pair A/B,
  // all within the SAME uncommitted snapshot (no session commit between them).
  int[] Ns = {100, 1000, 5000};
  for (int n : Ns) {
    long start = System.nanoTime();
    for (int i = 0; i < n; i++) {
      addOrder(sellTokenId, 100L + i, buyTokenId, 300L + i, OWNER_ADDRESS_SECOND); // unique coprime ratio each time
    }
    // Phase 2: an unrelated matching sell order on the SAME (or different) pair
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, buyTokenId, 400L, sellTokenId, 100L));
    TransactionResultCapsule ret = new TransactionResultCapsule();
    actuator.validate();
    long t0 = System.nanoTime();
    actuator.execute(ret);
    long elapsed = System.nanoTime() - t0;
    System.out.println("N=" + n + " matchOrder elapsed(ns)=" + elapsed);
    // assert elapsed grows roughly linearly (or worse) with n, i.e. elapsed(N=5000)/elapsed(N=100) >> 1
  }
}
```
Expected result: `matchOrder()` execution time for the single "unrelated" transaction increases roughly linearly with the attacker's prior uncommitted order count `n`, even though each attacker transaction pays the same flat `MarketSellAssetContract` fee/bandwidth, demonstrating that metering is not commensurate with imposed CPU work.

      if (skip) {

  private List<byte[]> getKeysNext(Snapshot head, byte[] key, long limit) {
    if (limit <= 0) {
      return Collections.emptyList();
    }

    Map<WrappedByteArray, Operator> collectionList = new HashMap<>();
    if (head.getPrevious() != null) {
      ((SnapshotImpl) head).collectUnique(collectionList);
    }

    // just get the same token pair
    List<WrappedByteArray> snapshotList = new ArrayList<>();
    if (!collectionList.isEmpty()) {
      snapshotList = collectionList.keySet().stream()
          .filter(e -> MarketUtils.pairKeyIsEqual(e.getBytes(), key))
          .collect(Collectors.toList());
    }

    // for delete operation
    long limitLevelDB = limit + collectionList.size();

    List<WrappedByteArray> levelDBList = new ArrayList<>();
    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {

          .forEach(e -> levelDBList.add(WrappedByteArray.of(e)));

      ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().getKeysNext(key, limitLevelDB)
          .forEach(e -> levelDBList.add(WrappedByteArray.of(e)));
