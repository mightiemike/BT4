### Title
Deposited PRC20 funds become permanently stranded and unusable when the `isCEA` smart-contract callback (`executeUniversalTx`) fails, with no revert/refund path - (File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go)

### Summary
The C4 finding describes an immutable/config-driven branch (`callOnDepositCallback`) that, when false, causes deposited collateral to sit in the escrow without the accompanying mint callback ever firing — funds move, but the intended "activation" step never happens, and there is no recovery path. Push Chain's `isCEA` inbound-execution flow has the same shape: PRC20 deposit into a smart-contract recipient is committed unconditionally, while the subsequent "callback" (`executeUniversalTx`, the step that actually lets the recipient act on/consume those funds) is executed separately and can fail independently — and for `isCEA` inbounds the code explicitly skips the revert/refund path on failure.

### Finding Description
`ExecuteInboundFundsAndPayload` (and the analogous `ExecuteInboundGasAndPayload`) handles `isCEA` inbounds whose recipient is a smart contract (not a UEA) in two separate steps:

1. `depositPRC20` mints/credits PRC20 tokens to `ueaAddr` (the recipient) and is committed directly against `sdkCtx`. [1](#0-0) 

2. Only afterward, `CallExecuteUniversalTx` is invoked inside a `CacheContext`, and if it fails the whole cache (including any fee deduction) is discarded — but the deposit from step 1, already committed outside the cache, is *not* rolled back: [2](#0-1) 

Critically, for `isCEA` inbounds the code takes an explicit, separate branch that records only a `FAILED` PCTx and does **not** create an `INBOUND_REVERT` outbound, unlike the non-CEA path: [3](#0-2) [4](#0-3) 

The `isCEA` flag and `Recipient` address are both attacker-controlled: they come directly from the payload the user submits to the source-chain gateway, are decoded via `NormalizeForTxType`, and validated only for well-formedness, not for coherence between recipient/payload: [5](#0-4) [6](#0-5) 

This mirrors the C4 pattern precisely: deposit happens (money moves into user/protocol-controlled custody) but the accompanying "activation"/callback step that lets the funds be productively used is decoupled from the deposit, can independently fail, and — specifically for the `isCEA` branch — there is no compensating revert/refund mechanism at all. The deposited PRC20 becomes stuck at the recipient contract address with no on-chain record of failure other than a `FAILED` PCTx entry, and no automated or user-triggerable remediation path exists in this flow.

### Impact Explanation
Funds (PRC20 tokens representing bridged assets) are deposited to a recipient contract but the mechanism meant to notify/execute logic on that contract (`executeUniversalTx`) can fail (e.g., recipient contract intentionally or accidentally reverts, is out of gas, or the fee-deduction step fails causing the whole cache — including the intended contract logic — to be discarded) while the deposit itself is irreversible and no revert/refund outbound is ever created. This causes a partial, permanent breakdown of the intended universal-transaction semantics: value is transferred but the users’/protocol’s expected atomic "deposit + execute" guarantee is broken with no recovery path, which is a direct funds-availability/loss-of-functionality bug matching the "permanently frozen funds" impact category (funds sit at an address whose intended consumption mechanism never fires, and there is no PC-chain-side remediation flow visible in this code path).

### Likelihood Explanation
The `isCEA`, `Recipient`, and payload fields are fully attacker-controlled from the source chain gateway call, and reaching this branch only requires an ordinary bridge deposit designating a smart-contract recipient with `isCEA=true`. The failure conditions of `CallExecuteUniversalTx` (recipient contract reverting, running out of gas, or `DeductGasFeesFromReceipt` failing) are realistic and can be triggered unintentionally (a normal recipient contract bug) or deliberately. No special privileges are needed to construct such an inbound.

### Recommendation
Either (a) make the deposit and the `executeUniversalTx` call atomic (wrap both in the same `CacheContext` and only commit if both succeed), or (b) extend the `isCEA` revert path to also cover post-deposit `executeUniversalTx`/fee-deduction failures by creating a compensating `INBOUND_REVERT`/refund outbound (mirroring the non-CEA path), so that a failed callback does not leave funds stranded at the recipient with no recovery mechanism.

### Proof of Concept
1. Attacker deploys a smart contract on Push Chain that has no `executeUniversalTx` entrypoint (or one that always reverts / burns excess gas) and is not a UEA.
2. Attacker sends funds to the source-chain gateway contract with `isCEA=true`, `Recipient` = the attacker's smart contract, `TxType=FUNDS_AND_PAYLOAD`.
3. Universal Validators observe and vote the inbound in; ballot finalizes; `ExecuteInboundFundsAndPayload` runs:
   - `depositPRC20` succeeds, crediting PRC20 to the recipient contract [1](#0-0) .
   - `isSmartContract` branch runs `CallExecuteUniversalTx` inside a `CacheContext`; the call reverts, so `writeCache()` is never called and only a `FAILED` PCTx is recorded [7](#0-6) .
4. Because this is the `isCEA` branch, no `INBOUND_REVERT` outbound is ever created [3](#0-2) , leaving the deposited PRC20 sitting at the recipient with no automatic remediation.

Note: I was not able to fully trace whether any other downstream mechanism (e.g., manual admin rescue, or an off-chain relayer retry) exists to recover these funds; if such a path exists, the severity would be lower (griefing/temporary stuck funds rather than permanent loss). This should be verified against `x/uexecutor` rescue-fund flows (`rescue_funds_test.go` was seen in the repo but its logic was not reviewed) before finalizing severity.

func (p *Inbound) NormalizeForTxType() error {
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		// Payload types: recipient is only meaningful when isCEA
		if !p.IsCEA {
			p.Recipient = EvmZeroAddress
		}
		// Always clear universal_payload — whatever the UV sends is ignored.
		// Core validator decodes from raw_payload.
		p.UniversalPayload = nil

		// Decode raw_payload → universal_payload
		if p.RawPayload != "" {
			decoded, err := DecodeRawPayload(p.RawPayload, p.SourceChain)
			if err != nil {
				return fmt.Errorf("failed to decode raw payload: %w", err)
			}
			if decoded == nil {
				return fmt.Errorf("raw_payload decoded to nil for payload tx type")
			}
			p.UniversalPayload = decoded
			p.RawPayload = "" // clear after successful decode to save storage
		}
