## Analog Found

### Title
Wallet Contract `rlp_execute` Forwards Uncapped Attached Deposit Into the Emulated Action, Causing Loss of Excess Caller Funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs`)

### Summary
The `near-wallet-contract` (the on-chain component that lets an Ethereum-style address act as a NEAR account) accepts an arbitrary `attached_deposit` from any external caller/relayer calling the `#[payable]` `rlp_execute` method, and unconditionally adds that entire deposit into the emulated action's outgoing deposit with no validation that it matches (or is capped by) what the underlying signed Ethereum transaction actually requires. This mirrors the `buyPosition()` finding: a caller who sends more value than intended loses the excess with no recourse.

### Finding Description
`rlp_execute` is `#[payable]`, so a relayer (any unprivileged predecessor account) can attach any amount of NEAR when calling it: [1](#0-0) 

`inner_rlp_execute` captures the full `env::attached_deposit()` into the `ExecutionContext` and derives `CallerDeposit` from it, which is only meant to be refunded on outright *failure* of the cross-contract call: [2](#0-1) 

The attached amount (`additional_value`) is then folded directly into the action's `deposit` via `saturating_add` with no upper bound check against what the parsed Ethereum transaction's `yocto_near`/fee actually needs: [3](#0-2) 

`CallerDeposit::new` only tracks the deposit for a possible refund-on-failure path, but on *success* nothing refunds any excess back to the caller — the whole attached amount, whatever it was, has already been baked into the outgoing `Transfer`/`FunctionCall` deposit sent to the transaction's target: [4](#0-3) 

This is confirmed by the existing test `test_caller_refunds`, which explicitly asserts that "External caller does not get a refund when their tokens are spent" — i.e. once the promise chain succeeds, whatever was attached (regardless of how much more than necessary) is consumed and forwarded, never returned: [5](#0-4) 

### Impact Explanation
An external caller/relayer that attaches more NEAR than the emulated Ethereum transaction's value/fee actually requires (e.g. due to a decimal/unit mismatch, since the wallet contract converts between 18-decimal ETH `Wei` and 24-decimal NEAR yoctoNEAR — see `MAX_YOCTO_NEAR` handling in `create_rlp_execute_tx`) will have that entire excess forwarded to the transaction's target account instead of being refunded, exactly as in the `buyPosition()` finding where `msg.value` was not capped to `sellOrder.price`. This is a concrete unauthorized transfer of value away from the caller with no recovery path once the call succeeds.

### Likelihood Explanation
Any relayer calling `rlp_execute` on behalf of a wallet owner controls the attached deposit independently of the signed Ethereum transaction's content, and the contract performs no `require`/cap check that the attached deposit equals the amount actually needed by the parsed action. A single mis-computed or intentionally-inflated attached deposit from a relayer transaction is sufficient to trigger the loss, making this reachable by any unprivileged transaction sender interacting with the wallet contract.

### Recommendation
Validate that `attached_deposit` does not exceed the amount actually required by the parsed action (fee + `yocto_near`/transfer value) before folding it into the outgoing deposit; refund any excess above the required amount back to the caller (`predecessor_account_id`) regardless of whether the underlying cross-contract call succeeds, similar to the existing failure-path refund via `CallerDeposit`.

### Proof of Concept
1. A relayer calls `rlp_execute(target, tx_bytes_b64)` on a `near-wallet-contract` instance, attaching NEAR deposit `D` that is larger than required to cover the signed Ethereum transaction's `value`/fee.
2. `inner_rlp_execute` records `D` as `context.attached_deposit` / `CallerDeposit` (only used for failure refunds). [2](#0-1) 
3. `Action::try_into_near_action` computes the outgoing `Transfer`/`FunctionCall` deposit as `additional_value.saturating_add(yocto_near)`, i.e. the *entire* `D` plus the tx's specified value, with no cap. [3](#0-2) 
4. The cross-contract call succeeds; per `test_caller_refunds`'s documented behavior, no refund of the excess is issued to the relayer — the excess is now part of the balance transferred to `target`, permanently lost to the caller.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
