## Title
Unbounded, unmetered client-side proof verification allows resource-consumption DoS via the transaction ingestion (add_transaction) path - ([File: crates/apollo_transaction_converter/src/transaction_converter.rs])

## Summary
The gateway's transaction ingestion pipeline performs cryptographic proof verification (`starknet_proof_verifier::verify_proof`, backed by `privacy_circuit_verify_v1::verify_recursive_circuit`) for every `Invoke` V3 transaction carrying non-empty `proof_facts`/`proof`, and it does so **before** any state-based validation such as nonce/account-existence or fee-affordability checks, and with **no concurrency limiter** analogous to the one that protects Sierra→CASM declare compilation.

## Finding Description
In `add_tx_inner` [1](#0-0) , the flow is:
1. `stateless_tx_validator.validate(&tx)` — only checks sizes/format (`max_proof_size`, calldata length, proof/proof_facts non-empty consistency). It never actually verifies the proof or checks that the sender can pay/exists.
2. A concurrency-limiting semaphore is acquired **only for Declare transactions** to bound expensive Sierra→CASM compilation [2](#0-1) . No equivalent limiter exists for Invoke transactions carrying proofs.
3. `convert_rpc_tx_to_internal_and_executable_txs` → `transaction_converter.convert_rpc_tx_to_internal_rpc_tx` is called, which spawns/executes `verify_proof` [3](#0-2) .
4. `verify_proof` is a real cryptographic circuit verification call — `privacy_circuit_verify_v1::verify_recursive_circuit` [4](#0-3) .
5. Only **after** the proof verification result comes back does the gateway run `stateful_tx_validator.extract_state_nonce_and_run_validations`, which is where nonce validity and fee/resource-bound affordability against actual state are checked [5](#0-4) .

The stateless validator only checks that `proof_facts`/`proof` are both present/absent and that their sizes are within `max_proof_size` (up to 480,000 felts by default) [6](#0-5)  — it performs no actual cryptographic check. `run_proof_verification` calls `contains_proof` first (a cheap dedup lookup keyed by the *facts* hash) but for arbitrary/garbage facts this always misses, forcing the full `verify_proof` invocation on every submission [7](#0-6) .

This mirrors the reported bug class (HTTP RPC API endpoint that triggers expensive processing on attacker-controlled input before adequate gating), except here the analog is a Starknet sequencer's `add_transaction`/gateway ingestion path, where the "expensive resource" is a cryptographic circuit verification instead of a generic RPC handler operation.

## Impact Explanation
An unprivileged actor can submit HTTP-`add_transaction` (or P2P) Invoke V3 transactions with well-formed-but-bogus `proof_facts`/`proof` payloads sized close to `max_proof_size` (480,000 felts). Each such submission forces the gateway to run a full ZK circuit verification (`privacy_circuit_verify_v1::verify_recursive_circuit`) before the transaction is ever checked against the sender's real nonce/balance, and there is no per-node concurrency cap on this path (unlike the declare-compilation semaphore). Because these transactions are stateless-valid but will always fail proof verification/stateful validation and thus never reach the mempool or get executed, the sender pays nothing and is bound only by network-level constraints (multiple sender addresses/signatures, or P2P propagation). Repeated concurrent submissions can drive sustained CPU exhaustion on the sequencer's gateway component, degrading or halting transaction admission for legitimate senders — a resource-consumption/availability impact reachable from a single submitted transaction, consistent with "network unable to confirm new transactions" if sustained.

## Likelihood Explanation
Medium-high likelihood: this requires no privileged access, no valid account balance, and no successful transaction — only a stateless-valid Invoke V3 transaction with garbage but size/format-compliant proof data. The attack is cheap for the attacker (network bandwidth to send transactions with up to ~480K felts of payload) versus the cost imposed on the sequencer (full recursive-circuit verification per submission), and it can be parallelized across many submissions since there's no per-node limiter protecting this specific expensive step, unlike the analogous declare-compilation semaphore that the codebase already implements for a similar concern.

## Recommendation
- Add a bounded concurrency limiter (semaphore) around proof verification analogous to `declare_compilation_semaphore`, to cap the number of concurrent `verify_proof` calls.
- Move cheap, attacker-independent-of-state checks (e.g., minimal sanity/format checks already present) ahead, but more importantly, consider deferring or rate-limiting expensive proof verification until after cheaper state-dependent checks (e.g., nonce/account existence, fee affordability) are confirmed, so that unaffordable/invalid-nonce transactions are rejected before the expensive cryptographic work is performed.
- Consider per-sender-address rate limiting or a lightweight proof/PoW pre-check before allowing entry into the expensive verification pipeline.

## Proof of Concept
1. Craft an `RpcTransaction::Invoke(RpcInvokeTransaction::V3(...))` transaction with:
   - Valid signature/format so it passes `StatelessTransactionValidator::validate` (proper resource bounds, calldata within `max_calldata_length`, valid DA modes).
   - `proof_facts` populated with a well-formed but bogus felt array (`[PROOF_VERSION_V1, variant, program_hash, ...]`) and `proof` populated with random bytes up to `max_proof_size` (480,000 felts default).
2. Submit this transaction repeatedly (varying sender address/nonce/signature to avoid `DuplicateTransaction`/nonce-based mempool rejection) via the HTTP `add_transaction` endpoint or P2P gossip.
3. Each submission reaches `convert_rpc_tx_to_internal_rpc_tx` → `spawn_proof_verification` → `verify_proof` → `privacy_circuit_verify_v1::verify_recursive_circuit` before any nonce/fee state check occurs, consuming CPU on every call regardless of whether the sender's account exists or can pay fees.
4. Concurrently issuing many such requests (limited only by network/HTTP concurrency, not by any proof-verification semaphore) drives sustained CPU load on the gateway component, since — unlike declare transactions — there is no `Semaphore`-based admission control for this code path.

/// Verifies a submitted proof against the proof facts using the circuit verifier.
///
/// The first element of `proof_facts` must be V1, verified via `privacy-circuit-verify-v1`.
pub fn verify_proof(proof_facts: ProofFacts, proof: Proof) -> Result<(), VerifyProofError> {
    // Reject empty proof payloads before running the verifier.
    if proof.is_empty() {
        return Err(VerifyProofError::EmptyProof);
    }

    let proof_version_felt = proof_facts.0.first().copied().unwrap_or_default();
    let proof_version = ProofVersion::try_from(proof_version_felt)
        .map_err(|()| VerifyProofError::InvalidProofVersion { actual: proof_version_felt })?;

    let output_preimage = reconstruct_output_preimage(&proof_facts)?;
    // TODO(Avi): Avoid cloning the proof.
    let proof_bytes = proof.0.to_vec();

    match proof_version {
        // V0 proofs are no longer verifiable: the v0 circuit was removed. V0 proof facts are only
        // tolerated by the blockifier (gated per protocol version) for replaying historical blocks.
        ProofVersion::V0 => {
            return Err(VerifyProofError::InvalidProofVersion { actual: proof_version_felt });
        }
        ProofVersion::V1 => {
            let proof_output = privacy_circuit_verify_v1::PrivacyProofOutput {
                proof: proof_bytes,
                output_preimage,
            };
            privacy_circuit_verify_v1::verify_recursive_circuit(&proof_output)
                .map_err(|e| VerifyProofError::Verification(e.to_string()))?;
        }
    }

    Ok(())
}

    fn validate_proof_facts_and_proof_consistency(
        &self,
        tx: &RpcInvokeTransaction,
    ) -> StatelessTransactionValidatorResult<()> {
        let RpcInvokeTransaction::V3(tx) = tx;
        let has_proof_facts = !tx.proof_facts.is_empty();
        let has_proof = !tx.proof.is_empty();
        if has_proof_facts != has_proof {
            return Err(StatelessTransactionValidatorError::ProofFactsAndProofConsistency {
                has_proof_facts,
                has_proof,
            });
        }
        Ok(())
    }
