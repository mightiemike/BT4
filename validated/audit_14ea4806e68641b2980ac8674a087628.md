## Finding: Unauthenticated "Bootstrap" Declare Bypass Enables Free, Unsigned Class Declaration

This is an analog of CVE‑2019‑25066's class of bug: an API path that grants privileged treatment based on an unauthenticated/unauthorized identity marker rather than actual proof of authorization. Here, the sequencer's execution layer special‑cases any `Declare` transaction whose `sender_address` equals a fixed, publicly-known constant address (`'BOOTSTRAP'`), completely skipping signature validation, fee charging, and nonce enforcement — and this special identity is reachable by any ordinary, unprivileged transaction submitter through the normal gateway `add_tx` path.

### Finding Description
`DeclareTransaction::bootstrap_address()` returns a fixed address derived from the ASCII string `"BOOTSTRAP"` [1](#0-0) , and `is_bootstrap_declare` flags a tx as a bootstrap declare whenever `sender_address == bootstrap_address()`, `nonce == 0`, and `charge_fee` is false [2](#0-1) .

In `AccountTransaction::execute_raw`, if a `Declare` transaction satisfies `is_bootstrap_declare`, the code runs only `run_execute` (which declares the class) and returns immediately — completely bypassing `perform_pre_validation_stage` (nonce/fee checks) and the `__validate_declare__` entry point (signature/account authorization) that every other transaction must go through: [3](#0-2) . The same bypass exists in the Starknet OS Cairo program used for re-execution/proving [4](#0-3) .

The only state-level guard is that the class hash must not already be declared (`prev_value=0` in the dict update) [5](#0-4) .

Critically, this "BOOTSTRAP" identity is **not gated by any cryptographic key or on-chain deployment** — it's a magic constant that anyone can put in the `sender_address` field of a submitted `RpcDeclareTransaction`. Reaching this path through the gateway requires only:
1. `check_declare_permissions` passes, which by default allows all senders (`authorized_declarer_accounts` defaults to `None`, meaning `is_authorized_declarer` returns `true` for every address) [6](#0-5) , [7](#0-6) .
2. `validate_nonce` in the stateful validator requires `incoming_tx_nonce == account_nonce` for declares (when `reject_future_declare_txs` is enabled, which is the default) [8](#0-7) . Because bootstrap declares never increment the bootstrap address's nonce (the execution bypass in `execute_raw` never calls `perform_pre_validation_stage`, which is what increments nonce), the account nonce for this address remains `0` forever, so `nonce == 0` always satisfies this check — the comment in the integration test even documents this: "they are not removed from the mempool upon successful execution... will only be removed after being rejected during a subsequent attempt" [9](#0-8) .
3. `enforce_fee`/resource bounds simply need to compute a zero max possible fee, and the gateway's `run_validate_entry_point` computes `charge_fee` itself via `enforce_fee(executable_tx, only_query)` from the attacker-supplied resource bounds [10](#0-9) .

The test helper `generate_bootstrap_declare` demonstrates exactly how trivial this is to construct — an unsigned (`TransactionSignature::default()`), no-fee-enforcement declare transaction sent from the bootstrap address [11](#0-10) .

### Impact Explanation
Any unprivileged network participant can submit a `Declare` transaction with `sender_address = 'BOOTSTRAP'`, `nonce = 0`, `version = 3`, zero resource bounds, and a default/empty signature to have a Sierra class declared on-chain:
- With **no signature verification** (impersonating a privileged bootstrap identity without any credential).
- With **no fee payment** (bypassing the fee market entirely).
- **Repeatedly**, for any number of distinct, not-yet-declared classes (the only limiter is that a given class hash can only be declared once via this path).

This directly triggers CPU/memory-intensive Sierra→CASM compilation for free, consuming the gateway's bounded `declare_compilation_semaphore` (`max_concurrent_declare_compilations`, default 40) [12](#0-11)  and the `contract_class_manager` compiler fleet capacity, which can starve/deny legitimate paying declare submissions (`too_many_concurrent_declare_compilations` errors), degrading network availability. It also permanently grows global state (declared classes / compiled class hashes) at zero cost, undermining the fee-based resource-accounting model that the fee market is designed to enforce — an unauthorized, fee-bypassing account action with permanent on-chain effect.

### Likelihood Explanation
High. No special access, key material, or race condition is required — only knowledge of the well-documented bootstrap address constant (already public in source/tests) and standard RPC submission. All gating (`check_declare_permissions`, nonce validation, fee validation) is satisfied by construction using default node configuration.

### Recommendation
Restrict the bootstrap-declare bypass so it can never be triggered from externally submitted transactions in a live, non-genesis network:
- Gate the bootstrap-declare path behind an explicit, operator-controlled feature flag/config (e.g., disabled by default and only enabled during an actual genesis bootstrap procedure), independent of the currently-permissive default `authorized_declarer_accounts = None`.
- Alternatively/additionally, ensure `check_declare_permissions`/gateway ingestion explicitly rejects any declare transaction with `sender_address == bootstrap_address()` once the system is out of its bootstrap phase (e.g., block height > 0, or a persisted "bootstrap complete" flag), so the special-cased execution semantics in `execute_raw`/OS program can never be reached via ordinary transaction submission after genesis.
- Consider requiring the bootstrap address entry to be included in `authorized_declarer_accounts` and defaulting that allow-list to empty in production configs, rather than `None` (allow-all).

### Proof of Concept
1. Craft an `RpcDeclareTransaction::V3` with:
   - `sender_address = ContractAddress::from(0x424f4f545354524150_u128)` (`'BOOTSTRAP'`)
   - `nonce = 0`
   - `resource_bounds` yielding `max_possible_fee == 0` (e.g., `ValidResourceBounds::create_for_testing_no_fee_enforcement()`)
   - `signature = TransactionSignature::default()` (empty/unsigned)
   - a fresh Sierra class + matching `compiled_class_hash`
2. Submit via the gateway's `add_tx` (mirrors `generate_bootstrap_declare` in `mempool_test_utils/src/starknet_api_test_utils.rs`, lines 585–595).
3. `check_declare_permissions` passes (default config has no declarer allow-list) [13](#0-12) .
4. `validate_nonce` passes because the bootstrap account's on-chain nonce is always `0` [8](#0-7) .
5. On block execution, `execute_raw` detects `is_bootstrap_declare` and declares the class with zero fee and no `__validate_declare__` call [14](#0-13) .
6. Repeat with new class hashes indefinitely to flood the compilation pipeline for free.

        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.

                    tx_context.clone(),
                    self.execution_flags.charge_fee,

                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
            }
