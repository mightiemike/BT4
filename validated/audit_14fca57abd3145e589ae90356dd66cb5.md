### Title
Stale `AcquiredDelegatedFrozenBalance` accounting on receiver accounts whose `AccountType` changes causes unreconciled state and subtraction underflow on unfreeze - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`)

### Summary
The Biconomy bug is a class of "classification flag toggled without reconciling dependent aggregate accounting", which causes a subtraction underflow when a previously-excluded/delegated entity's aggregate counter no longer matches the per-pair ledger. Java-tron has a structurally analogous pattern: a receiver account's `AccountType` (Normal vs Contract) can change over time (Normal→Contract via `CREATE2` to a pre-funded address, Contract→Normal after `suicide`), and the code branches its resource-accounting logic on `receiverCapsule.getType()` at unfreeze/undelegate time rather than at delegate time, while the aggregate counter `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` is mutated with unguarded arithmetic in the legacy path.

### Finding Description
`UnfreezeBalanceActuator.execute` decides how to update the receiver's delegated-resource accounting based on the receiver's *current* `AccountType`: [1](#0-0) 

If `getAllowTvmConstantinople()==0` or the receiver is not currently a `Contract`, the code takes the branch that mutates `receiverCapsule.addAcquiredDelegatedFrozenBalanceForBandwidth(-unfreezeBalance)`/`...ForEnergy(-unfreezeBalance)` directly. The underflow-safe clamp (`setAcquiredDelegatedFrozenBalanceForBandwidth(0)`) is only applied when `dynamicStore.getAllowTvmSolidity059() == 1`: [2](#0-1) 

The comment in the sibling V2 processor confirms this is a real, acknowledged scenario in the codebase — an account's type can flip between `Normal` and `Contract` during its lifetime (e.g., via `CREATE2` deploying to a pre-existing address, or via `suicide` clearing a contract back to a plain account), which is exactly why the newer `UnDelegateResourceProcessor`/`DelegateResourceProcessor` code paths defensively clamp to zero instead of subtracting unconditionally: [3](#0-2) 

This is the same root cause as the Biconomy `WhitelistPeriodManager` bug: a classification/membership flag (`isExcludedAddress` there, `AccountType` here) is allowed to change after resources have already been delegated/staked under the old classification, and the aggregate counter that was incremented under one classification is decremented under different logic/guards depending on the classification at the time of the reverse operation. Where the defensive clamp (`getAllowTvmSolidity059() == 1`) is not active, the legacy branch performs raw subtraction on `AcquiredDelegatedFrozenBalanceForBandwidth/Energy`, which can go negative (underflow, since these are stored as protobuf `int64`/long fields with no built-in floor) if the receiver's aggregate counter has drifted below the amount being unwound — mirroring Bob's stuck LP-withdrawal underflow in the original report.

### Impact Explanation
If the aggregate `AcquiredDelegatedFrozenBalanceForBandwidth/Energy` on a receiver account drifts out of sync with the per-pair `DelegatedResourceCapsule` ledger (a plausible sequence given `AccountType` can be reclassified via `CREATE2`/`suicide`, and given the older V1 delegation path in `FreezeBalanceActuator` does not carry the same clamp used by the newer V2 processors), an owner attempting to `UnfreezeBalanceContract` (withdraw delegated TRX) can hit a negative/inconsistent state on the receiver's resource fields. This is an invalid-state/accounting-divergence bug: it does not directly steal funds, but it can corrupt bandwidth/energy weight accounting on-chain and potentially block or misaccount legitimate unfreeze operations for affected owner/receiver pairs, consistent with the C4 judge's characterization of the original finding as Medium severity (external condition dependent, state-divergence class, not a direct fund-theft bug).

### Likelihood Explanation
Likelihood is limited by two factors: (1) the guarded/safe clamp path is already gated behind `getAllowTvmSolidity059()`, and if that hardfork flag is active network-wide, the underflow is defused by the `setAcquiredDelegatedFrozenBalanceForBandwidth(0)` fallback; (2) triggering the divergence requires a specific sequence (delegate to a Normal account, that account subsequently becomes/was-recorded-as a Contract or vice versa, e.g. via `CREATE2`/`suicide`) which is an unprivileged but non-trivial multi-step scenario. This mirrors the original finding's "requires an external condition" caveat that led the C4 judge to downgrade severity to Medium.

### Recommendation
Ensure the underflow-safe clamp introduced for `getAllowTvmSolidity059()` is unconditional (not feature-flag gated) in `UnfreezeBalanceActuator`, and audit all legacy (V1) delegate/undelegate/freeze/unfreeze actuators (`FreezeBalanceActuator`, `UnfreezeBalanceActuator`, `DelegateResourceActuator`) to use the same `safeAdd*`-style clamped mutation methods that the V2 native-contract processors already use for `AcquiredDelegatedFrozenV2Balance*`. More broadly, reconcile aggregate delegation counters whenever `AccountType` is changed (`updateAccountType`) rather than relying on branch logic keyed off the account's *current* type at unwind time.

### Proof of Concept
Concrete reproduction requires constructing the specific account-type transition sequence (delegate to a Normal-type address, convert that address to a `Contract` via `CREATE2` targeting the same address, or vice versa via `suicide`, then trigger `UnfreezeBalanceContract` while `getAllowTvmSolidity059() == 0`) and is not verifiable purely from static review; a background Devin session with test-execution access would be needed to build and run this against `UnfreezeBalanceActuatorTest`/`FreezeV2Test` harnesses to confirm the underflow triggers in practice.
