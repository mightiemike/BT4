### Title
Metering balance is not decremented when actual capability spend exceeds the earmarked deduction, allowing workflow credit balance to be overstated - (File: core/services/workflows/metering/metering.go)

### Summary
`Report.Settle()` in the CRE workflow metering subsystem silently fails to account for capability spend that exceeds its earmarked (`Deduct`ed) credit amount. Because `balanceStore.Add` rejects negative amounts, the "refund the unspent difference" step becomes a silent no-op whenever a capability actually spends more credits than were reserved for it, leaving the in-memory local credit balance overstated relative to real consumption — a direct analog to the GeVault issue where unaccounted/excess amounts are not reflected in the value used to gate further spending.

### Finding Description
`Report.Deduct()` earmarks (subtracts) a maximum spend amount from the in-memory balance for a step: [1](#0-0) 

`Report.Settle()` is then called with the actual measured spend reported by capability/DON nodes (`metadata.Metering`), aggregates it into `spentCredits`, and attempts to refund the unused earmarked balance: [2](#0-1) 

The refund is computed as `step.Deduction.Sub(spentCredits)`. This is only valid when `spentCredits <= step.Deduction`. If a capability's real spend (e.g. actual on-chain gas cost reported for a write capability) exceeds what was earmarked, this expression is negative. `balanceStore.Add()` explicitly rejects negative inputs and returns `ErrInvalidAmount`: [3](#0-2) 

`Settle()` only logs this failure ("invariant: spend exceeded reserve") and takes no corrective action — it does not subtract the overspend from `bs.balance`: [4](#0-3) 

Regardless of whether the refund succeeded, `AddSpent(spentCredits)` still records the full actual spend into the separate `spent` counter used for the billing receipt (`GetSpent()`), so the amount billed to the org is correct. However, `bs.balance` — the value used to gate further in-execution spending via `getMaxSpendForInvocation` / `ByDerivedAvailability` — was already reduced only by `step.Deduction` at `Deduct()` time and is never further reduced by the extra amount actually consumed. The local balance therefore ends up overstated by exactly `spentCredits - step.Deduction` for every step where actual spend exceeds the earmark.

### Impact Explanation
Because subsequent capability `Deduct` calls (`ByDerivedAvailability`) split `r.balance.Get()` across remaining concurrent call slots to compute new spend limits, an inflated balance directly translates into permission for the workflow execution to draw down more real, billable credits than the amount originally reserved from the billing service (`ReserveCredits`). This is a resource/fund-accounting integrity issue: the local ledger diverges from actual consumption in a way that favors over-spending, analogous to the GeVault bug where un-reconciled leftover value was not reflected in the balance used for downstream calculations (TVL / withdrawal amount), enabling value to be inconsistently tracked and potentially misused. In the CRE/metering case, the practical effect is a workflow being able to consume more provisioned credits than it was granted before it is caught (only surfaced afterward via `SendReceipt`/`CreditsConsumed`, at which point the overspend has already occurred and cannot be prevented in-flight).

### Likelihood Explanation
This path is reachable in normal production operation, not just by a malicious actor: any capability that reports actual spend larger than its earmarked deduction (plausible for write/gas-consuming capabilities whose real on-chain cost is unknown ahead of time and estimated conservatively) triggers this branch. No special privileges are required beyond being a workflow author/capability whose reported `SpendValue` exceeds the earmark, which is an unprivileged, workflow/job-ingestion-level trust boundary (capability responses feeding into the DON's local billing engine).

### Recommendation
When `spentCredits` exceeds `step.Deduction`, explicitly subtract the overspend from `bs.balance` (i.e., call `Minus` with the absolute value of the negative difference, or extend `balanceStore` with a signed "settle" operation) rather than silently discarding the correction via a failed `Add`. Additionally, consider surfacing this invariant violation as an error/mode-switch (e.g., `switchToMeteringMode`) rather than only logging at `Info` level, so that overspend causes fail-safe behavior consistent with other invariant violations in this file.

### Proof of Concept
1. Call `Report.Reserve(ctx)` to initialize a nonzero balance.
2. Call `Report.Deduct(ref, ByResource("COMPUTE", "cap1", decimal.NewFromInt(10)))` — earmarks 10 credits, `balance -= 10`.
3. Call `Report.Settle(ref, metadata)` where `metadata.Metering` reports a `SpendValue` that converts to 15 credits (i.e., actual spend > earmark).
4. Observe: `step.Deduction.Sub(spentCredits)` = `10 - 15` = `-5`; `r.balance.Add(-5)` returns `ErrInvalidAmount` and is only logged; `r.balance.AddSpent(15)` still executes.
5. Inspect `r.balance.Get()`: it remains at the value after only the original `-10` deduction, instead of reflecting the true `-15` consumption — the balance is overstated by 5 credits relative to actual spend, which is then available for subsequent `Deduct` calls in the same execution.

// Add increases the current credit balance.
func (bs *balanceStore) Add(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	bs.balance = bs.balance.Add(amount)

	return nil
}
