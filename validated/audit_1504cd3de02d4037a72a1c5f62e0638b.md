## Verdict: Valid Finding

### Title
Truncated/forged SVM gateway logs silently decode to zero-valued critical fields and are accepted as Pending inbound `UniversalTx` events - (File: `universalClient/chains/svm/event_parser.go`)

### Summary
`decodeUniversalTxEvent` returns `(payload, nil)` — a non-error, "success" result — whenever the Borsh-encoded log data is truncated after `bridge_amount` but before `revert_recipient`, `tx_type`, `sigLen`/`VerificationData`, or `fromCEA`. `parseUniversalTxEvent` only checks `err != nil` before accepting the payload, so `parseSendFundsEvent` unconditionally builds a `store.Event{Status: store.StatusPending, Type: store.EventTypeInbound}` from a partially-decoded, zero-valued payload.

### Finding Description
In `decodeUniversalTxEvent` (`universalClient/chains/svm/event_parser.go:236-371`), every field after `bridge_amount` is guarded by a length check that, on failure, logs a warning and does `return payload, nil` instead of returning an error: [1](#0-0) [2](#0-1) 

The only caller, `parseUniversalTxEvent`, treats any non-error return as fully valid: [3](#0-2) 

`parseSendFundsEvent` then creates the `store.Event` with `Status: store.StatusPending` before calling `parseUniversalTxEvent`, and does not roll back or mark the event invalid based on how much of the payload was actually decoded: [4](#0-3) 

Critically, this bug is reachable by an unprivileged, external attacker because the SVM `EventListener` does not bind a log line to the program that actually emitted it. `processSignatureBatch` iterates over *every* log line (`tx.Meta.LogMessages`) of any transaction that merely references the configured gateway address, and `determineEventType` classifies a log purely by its first 8 bytes (a public, deterministic Anchor discriminator) — with no check that the log was emitted from a CPI frame belonging to the real gateway program: [5](#0-4) [6](#0-5) 

Since Solana lets any account list multiple instructions and any deployed program can emit an arbitrary `"Program data: <base64>"` log via `sol_log_data`, an attacker can: (1) include the real gateway address as a (read-only, non-signing) account so the transaction is returned by `GetSignaturesForAddress`, and (2) invoke their own program in the same transaction to emit a log whose first 8 bytes match the known `send_funds` discriminator, followed by attacker-chosen bytes for `sender`, `recipient`, `bridge_token`, `bridge_amount`, then truncate right after `bridge_amount`. This satisfies the exact "reach through ordinary transaction submission" requirement — no validator, relayer, or TSS compromise is needed.

### Impact Explanation
The resulting `store.Event` is inserted into the store as `Pending`/`Inbound` and will be picked up by the vote/finalization pipeline with:
- `RevertFundRecipient = ""` (zero value, no valid Solana pubkey),
- `TxType = 0` (defaults to "Funds" confirmation classification, forcing `ConfirmationFast`),
- `VerificationData = ""`.

Because `sender`, `recipient`, `bridge_token`, and `bridge_amount` are fully attacker-controlled (they are parsed before the truncation point and are not validated against on-chain balance movement in this file), the attacker can also fabricate arbitrary deposit amounts/recipients. Whether this converts into an actual unauthorized mint/release on the Push Chain side depends on additional validation inside the ballot/voting module (`x/`) — which was not available to inspect in this pass — but even absent full fund loss, this breaks the required invariant that "partially-decoded/ambiguous events must not be treated as valid votable inbound events," and creates a canonical `UniversalTx` with corrupted revert/verification/tx-type semantics that the honest-validator ballot pipeline is asked to converge on. An empty `RevertFundRecipient` combined with attacker-forced `TxType`/`ConfirmationFast` selection can misroute revert/refund flows and confirmation-timing guarantees for genuinely bridged funds too, since forged events share the same discriminator-matching path as real ones.

### Likelihood Explanation
High for an unprivileged attacker with basic Solana program-deployment capability (a normal, permissionless action): the entry point requires only (a) knowledge of the public Anchor event discriminator, and (b) the ability to submit a transaction that references the gateway address and emits a spoofed log from an attacker-owned program. No privileged role is required.

### Recommendation
1. `decodeUniversalTxEvent` must return a hard error (not `payload, nil`) whenever any field required by the on-chain event schema is missing/truncated, instead of silently defaulting.
2. `parseSendFundsEvent`/`parseUniversalTxEvent` must reject (not store as `Pending`) any event that failed to fully decode.
3. Independently of the truncation bug, `event_listener.go` must bind each log line to the actual invoking program (using the transaction's inner-instruction/CPI stack, not just presence of the gateway address in the account list) before trusting its discriminator, so attacker-deployed programs cannot inject spoofed gateway events.

### Proof of Concept
1. Deploy an attacker-controlled Solana program `Evil`.
2. Build a transaction with two instructions: (a) a no-op instruction referencing the real gateway program's address as an account (so `GetSignaturesForAddress(gatewayAddr, ...)` returns this signature), and (b) an instruction to `Evil` that calls `sol_log_data` with bytes = `send_funds` discriminator (8 bytes, public) || `sender`(32) || `recipient`(20) || `bridge_token`(32) || `bridge_amount`(8) — i.e., truncated exactly after `bridge_amount`, omitting `revert_recipient`, `tx_type`, `sigLen`, `fromCEA`.
3. Submit the transaction to the SVM chain.
4. `EventListener.processSignatureBatch` picks up the log line, `determineEventType` matches on the discriminator, `ParseEvent`→`parseSendFundsEvent`→`decodeUniversalTxEvent` returns `(payload, nil)` at line 322/312/342, and a `store.Event{Status: Pending, Type: Inbound}` is inserted with `RevertFundRecipient=""`, `TxType=0`, `VerificationData=""`, while `Sender`/`Recipient`/`Token`/`Amount` are fully attacker-chosen — despite no real funds ever moving through the genuine gateway program.

// determineEventType determines the event type based on the log discriminator
func (el *EventListener) determineEventType(log string) string {
	if !strings.HasPrefix(log, "Program data: ") {
		return ""
	}

	eventData := strings.TrimPrefix(log, "Program data: ")
	decoded, err := base64.StdEncoding.DecodeString(eventData)
	if err != nil {
		return ""
	}

	if len(decoded) < 8 {
		return ""
	}

	discriminator := strings.ToLower(hex.EncodeToString(decoded[:8]))

	// Look up event type from discriminator map
	eventType, ok := el.discriminatorToEventType[discriminator]
	if !ok {
		return ""
	}

	return eventType
}
