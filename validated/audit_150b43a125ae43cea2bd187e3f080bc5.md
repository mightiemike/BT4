### Title
Relayer fee is transferred unconditionally before the emulated action's success is known, causing unrecoverable fund loss on failure - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `near-wallet-contract` (used to emulate Ethereum EOA behavior on eth-implicit accounts) dispatches the relayer's compensation fee as an independent NEAR `Transfer` action *before* it knows whether the corresponding `ERC20Transfer` or `EOABaseTokenTransfer` action will actually succeed. Analogous to the reported ERC-20 pattern of moving value on the unchecked assumption that a transfer call "probably always" succeeds, here the wallet contract moves value (the fee) to the relayer without gating it on confirmation that the user's requested transfer completed.

### Finding Description
In `inner_rlp_execute`, once RLP parsing succeeds, the fee refund promise is created and submitted immediately and independently of the actual transfer promise: [1](#0-0) 

This `refund_promise` is built via `env::promise_batch_create` / `env::promise_batch_action_transfer` as a fire-and-forget receipt — it is never chained with `.then()` to the outcome of the actual action, so its execution is unconditional on the outcome of `action_to_promise(...)` / the `ERC20Transfer` chain that is constructed afterwards: [2](#0-1) 

The only failure handling that exists refunds the caller's attached NEAR *deposit* (`caller_deposit`) if the cross-contract call fails, but it never revokes or reclaims the already-sent relayer `fee`: [3](#0-2) 

For the `ERC20Transfer` case, the nonce is also incremented immediately (since the `address_check: Some(_)` guard only applies to `EOABaseTokenTransfer`), so the transaction cannot be resubmitted to "try again": [4](#0-3) 

This mirrors the audited pattern in the external report: a value-moving call (`transfer`) is issued on the assumption that a subsequent operation "probably" succeeds, without verifying/gating it on the actual result.

### Impact Explanation
Any relayer (a normal, unprivileged transaction/RPC submitter interacting with an eth-implicit account's `rlp_execute`) can cause the wallet owner to pay the signed relayer fee even when the underlying `ft_transfer` fails for any reason (receiver contract panics, insufficient token balance on the token contract's side, gas exhaustion in the `storage_deposit`+`ft_transfer` batch, temporary token contract pause, etc.). Because the fee-transfer receipt is independent and unconditional, and the nonce is already consumed, the user permanently loses the fee amount in NEAR with no corresponding service rendered and no path to recovery — a concrete unauthorized/unjustified value movement out of the user's account, reachable purely from a signed meta-transaction-like RLP payload submitted by any relayer.

### Likelihood Explanation
This is triggered by the normal operational flow of the wallet contract's core entry point `rlp_execute`, reachable by any account (including an adversarial but keyless relayer, since the code path explicitly allows "any relayer" to serve transfers) simply by submitting a valid RLP transaction whose downstream `ft_transfer` is made to fail (e.g., targeting a token/receiver combination expected to fail, or a token contract that reverts nondeterministically). No special privileges are required, making this readily reachable.

### Recommendation
Chain the fee-transfer action so that it executes only after the underlying action succeeds — e.g., move the `env::promise_batch_action_transfer` for `fee` into the `.then()` callback (`rlp_execute_callback` / `nep_141_storage_balance_callback`) after confirming `PromiseResult::Successful`, mirroring the existing `caller_deposit` refund-on-failure logic. This ensures the fee is only paid when the corresponding action actually completed, analogous to using checked/safe transfer semantics instead of assuming success.

### Proof of Concept
1. Deploy/own an eth-implicit wallet contract account with some ERC-20 (NEP-141) token balance and NEAR balance.
2. Sign an RLP-encoded `ERC20Transfer` transaction with a non-zero `fee`, targeting a `receiver_id`/token contract configuration engineered to make the eventual `ft_transfer` call fail after `storage_balance_of`/`storage_deposit` succeed (e.g., a token contract that reverts on transfer due to insufficient balance, or hits gas limits in the batched calls).
3. Any relayer submits this transaction via `rlp_execute`.
4. Observe: `inner_rlp_execute` immediately fires `env::promise_batch_action_transfer(refund_promise, *fee)` to the relayer (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:382-383`) and increments the nonce, before the `ft_transfer` chain resolves.
5. The `ft_transfer` chain subsequently fails; `rlp_execute_callback` reports `success: false` but the fee has already been irreversibly transferred to the relayer, and the nonce increment prevents retry — confirming unconditional, unrecoverable value loss independent of action success.
