## Title
Truncating Division in Delegated Resource Usage Transfer Allows Free Bandwidth/Energy via Small Un-Delegations - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
`UnDelegateResourceActuator.execute()` (and its TVM-native mirror `UnDelegateResourceProcessor.execute()`) computes `transferUsage` — the amount of resource-consumption debt that must move from a receiver back to the owner when a delegated TRX freeze is un-delegated — using floating-point multiplication cast to `long`, which truncates toward zero. When the un-delegated amount is small relative to the receiver's total frozen balance, `transferUsage` truncates to `0`, and the usage-transfer step is skipped entirely, exactly mirroring the reported "small principal / small ratio → truncated to zero" bug class.

### Finding Description
In `UnDelegateResourceActuator.execute()`: [1](#0-0) 

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
``` [2](#0-1) 

`transferUsage` is `(long)` cast (truncating, not rounding) from a `double` product. When `unDelegateBalance` is small relative to `receiverCapsule.getAllFrozenBalanceForBandwidth()` (analogous to the report's "small principal and small ratio"), the product truncates to `0`. The actuator then guards the usage transfer with `if (Objects.nonNull(receiverCapsule) && transferUsage > 0)`, so when `transferUsage == 0` the call to `processor.unDelegateIncrease(...)` — the routine that moves the corresponding usage debt onto the owner account — is skipped entirely: [3](#0-2) 

The identical pattern (and identical `(long)` truncation without rounding) exists in the TVM-native contract path used when a smart contract calls `UnDelegateResource` via the TVM's native precompiled contract mechanism: [4](#0-3) 

The actual debt-transfer logic that gets skipped, `ResourceProcessor.unDelegateIncrease` / `unDelegateIncreaseV2`, is what would otherwise burden the owner with the receiver's consumed usage proportional to the balance being reclaimed: [5](#0-4) 

Elsewhere in the same file, the codebase already demonstrates the correct pattern — using `divideCeil`/`divideCeilExact` to round up instead of truncating — showing that the truncation in the un-delegate usage-transfer path is an inconsistency with the rest of the resource-accounting code: [6](#0-5) 

### Impact Explanation
`FreezeBalanceV2Contract`/`DelegateResourceContract`/`UnDelegateResourceContract` are all unprivileged, anonymously broadcastable transactions. An attacker can freeze TRX for BANDWIDTH/ENERGY, delegate it (in full or in installments) to a second account they control, consume the delegated capacity (driving up `receiverCapsule.getNetUsage()`/`getEnergyUsage()`), and then issue a sequence of `UnDelegateResourceContract` transactions each sized so that `unDelegateBalance / receiverCapsule.getAllFrozenBalanceFor*()` truncates the computed `transferUsage` to `0`. In that case:
- The receiver's recorded usage is not reduced (correct), but more importantly the owner never inherits the proportional usage debt it should when reclaiming the balance (`unDelegateIncrease` is skipped).
- The reclaimed TRX can immediately be re-frozen/re-delegated to gain a fresh full resource allowance, while the previously-consumed usage debt has effectively vanished from the system's accounting rather than being carried by whichever account holds the balance.

Repeated in small increments, this lets an attacker recycle the same TRX to obtain bandwidth/energy allowances beyond what the protocol's resource-accounting model intends — a resource/asset accounting corruption analogous to the "interest-free loan" pattern (small amounts round the accrual/debt to zero while still being treated as a fully valid, consequence-free operation).

### Likelihood Explanation
High. All contracts involved (`FreezeBalanceV2Contract`, `DelegateResourceContract`, `UnDelegateResourceContract`) are ordinary, permissionless transaction types reachable via the standard broadcast-transaction RPC path, requiring no privileged role, leaked key, or malicious peer — only control of two ordinary accounts (owner and receiver, which can be the same actor's addresses). The exploit is fully automatable by choosing un-delegation amounts below the truncation threshold, and the identical flaw is reachable from smart-contract execution via the TVM native contract path (`UnDelegateResourceProcessor`), widening the attack surface to any contract call.

### Recommendation
Replace the truncating `(long)` cast in the `transferUsage`/`unDelegateMaxUsage` calculations in `UnDelegateResourceActuator.execute()` and `UnDelegateResourceProcessor.execute()` with a rounding-up (ceiling) integer computation — consistent with the `divideCeil`/`divideCeilExact` helpers already used elsewhere in `ResourceProcessor.java` — so that any nonzero usage debt is never silently dropped to zero. Alternatively, perform the multiplication in `BigInteger`/`BigDecimal` with explicit `RoundingMode.CEILING` before converting to `long`, mirroring the hardened calculation paths (`hardenCalculation()`) already present in the codebase.

### Proof of Concept
1. Attacker account A freezes a large TRX amount (e.g. 1,000,000 TRX) for BANDWIDTH via `FreezeBalanceV2Contract`, then delegates it in full to attacker-controlled account B via `DelegateResourceContract`.
2. B consumes bandwidth heavily via ordinary transfers/transactions, causing `receiverCapsule.getNetUsage()` to grow large relative to `getAllFrozenBalanceForBandwidth()`.
3. A repeatedly issues `UnDelegateResourceContract` transactions with `unDelegateBalance` chosen such that
   `receiverCapsule.getNetUsage() * unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth() < 1`
   (guaranteed by choosing small enough `unDelegateBalance`), causing `transferUsage` computed in `UnDelegateResourceActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java:83-85`) to truncate to `0`.
4. Because `transferUsage == 0`, the `processor.unDelegateIncrease(...)` call at line 146 is skipped, so A reclaims TRX in `getFrozenBalanceForBandwidthV2` without inheriting any of the usage debt that B accumulated while holding the delegation.
5. A re-delegates or re-uses the reclaimed TRX for a fresh full resource allowance, repeating the cycle to accumulate free bandwidth/energy beyond the intended accounting model.

      unDelegateIncreaseV2(owner, receiver, transferUsage, resourceCode, now);

    // Update itself first
    ownerUsage = increase(owner, resourceCode, ownerUsage, 0, lastOwnerTime, now);

    long remainOwnerWindowSize = owner.getWindowSize(resourceCode);
    long remainReceiverWindowSize = receiver.getWindowSize(resourceCode);
    remainOwnerWindowSize = remainOwnerWindowSize < 0 ? 0 : remainOwnerWindowSize;
    remainReceiverWindowSize = remainReceiverWindowSize < 0 ? 0 : remainReceiverWindowSize;

    long newOwnerUsage = ownerUsage + transferUsage;
    // mean ownerUsage == 0 and transferUsage == 0

      owner.setUsage(resourceCode, 0);
      owner.setLatestTime(resourceCode, now);

        remainReceiverWindowSize, newOwnerUsage);

    owner.setUsage(resourceCode, newOwnerUsage);
    owner.setLatestTime(resourceCode, now);

  private long divideCeil(long numerator, long denominator) {
    return (numerator / denominator) + ((numerator % denominator) > 0 ? 1 : 0);
  }

  private long divideCeilExact(BigInteger numerator, BigInteger denominator) {
    BigInteger[] divRem = numerator.divideAndRemainder(denominator);
    long result = divRem[0].longValueExact();
    if (divRem[1].signum() > 0) {
      result = StrictMathWrapper.addExact(result, 1);
    }
    return result;
  }
