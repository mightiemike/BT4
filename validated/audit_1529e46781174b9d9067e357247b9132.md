## Analysis

The external report describes an **if-condition/action mismatch**: a check tests one condition (`depositSlippageSlots`) while the code executed in that branch validates a semantically different thing (reallocation slippage). The native analog I found is a similar mismatch in the funds-related tx-type gate that decides whether bridged PRC20 tokens must be re-minted (refunded) when an outbound transaction fails.

### Title
Incomplete/mismatched TxType set in `handleFailedOutbound` causes bridged funds to be permanently lost for `GAS` outbound failures - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`handleFailedOutbound` decides whether to re-mint (refund) PRC20 that was already burned on Push Chain when an outbound withdrawal fails on the destination chain. The gate only re-mints for `TxType_FUNDS`, `TxType_GAS_AND_PAYLOAD`, and `TxType_FUNDS_AND_PAYLOAD`, silently excluding `TxType_GAS`, even though the surrounding comment states the intent is "revert bridged funds for funds-related tx types."

### Finding Description
`handleFailedOutbound` is invoked from `FinalizeOutbound` whenever a UV-observed outbound (`obs.Success == false`) is voted in via `MsgVoteOutbound`: [1](#0-0) 

The funds-recovery branch is gated by an explicit tx-type allowlist: [2](#0-1) 

If `outbound.TxType == types.TxType_GAS`, this branch is skipped entirely — no `CallPRC20Deposit` re-mint occurs — and the function falls straight through to marking the outbound `REVERTED` and only attempting a gas refund (which requires `obs.GasFeeUsed`/`outbound.GasFee`/`outbound.GasToken` to be non-empty, and refunds only the *excess* gas, not the bridged principal): [3](#0-2) [4](#0-3) 

Outbound records are built from `UniversalTxOutboundEvent` logs emitted by the Universal Gateway contract, which carries the token amount that was burned/locked on Push Chain to fund the destination-chain payout: [5](#0-4) 

Comparing to the sibling `ExecuteInboundGas` path, `TxType_GAS` inbound flows do carry real bridged value (PRC20 deposit + autoswap), so the corresponding outbound variant of `TxType_GAS` should carry equivalent bridged value that needs to be reverted on destination-chain failure: [6](#0-5) 

The omission of `TxType_GAS` from the re-mint allowlist in `handleFailedOutbound` is exactly the class of bug described in the external report: a condition intended to cover "all funds-bearing tx types" is checked against an incomplete/mismatched enumeration, so the actual remediation logic executed does not match what the surrounding intent (and comment) require.

### Impact Explanation
If an outbound of `TxType_GAS` fails on the destination chain (broadcast revert, insufficient gas, destination-side validation failure, etc. — all attacker-influenceable or naturally occurring conditions on the external chain, not requiring any privileged actor), the PRC20 principal that was already burned/locked on Push Chain to fund that withdrawal is never re-minted back to the user. The outbound is marked `REVERTED` and the flow completes "successfully" from the node's perspective, but the user's funds are permanently lost — this falls squarely into the "permanent loss of user or protocol-controlled funds" allowed-impact category, triggered via the ordinary `MsgVoteOutbound` honest-validator finalization path with no privileged actor required.

### Likelihood Explanation
Triggering an outbound destination-chain failure does not require any malicious or privileged party — external-chain congestion, insufficient destination gas, a reverting recipient contract, or a chain reorg can all cause `obs.Success == false` for a legitimate `GAS`-type withdrawal. Since honest UVs vote the outcome exactly as observed, the missing re-mint fires deterministically whenever a `GAS` outbound fails, making this a reliably reachable, non-privileged loss-of-funds path (assuming `TxType_GAS` is a value the outbound pipeline can legitimately carry for a bridged/burned token withdrawal — this repository snapshot does not let me fully confirm every code path that constructs a `GAS`-typed `OutboundTx` from the withdraw-event decoder, so this should be verified against `DecodeUniversalTxOutboundFromLog` and the Gateway contract's `TxType` enum mapping before treating this as a fully confirmed, in-production reachable case).

### Recommendation
Align the tx-type gate in `handleFailedOutbound` with the actual set of tx types that carry bridged/burned principal value on the outbound side (this likely should include `TxType_GAS` alongside `TxType_FUNDS`, `TxType_GAS_AND_PAYLOAD`, and `TxType_FUNDS_AND_PAYLOAD`, or be restructured to enumerate "non-funds-bearing" types explicitly, e.g. only excluding truly payload-only executions with zero principal). Add a regression test mirroring the existing `handleFailedOutbound` funds re-mint tests but for a `TxType_GAS` outbound failure, asserting that `CallPRC20Deposit` is invoked and `outbound.PcRevertExecution` is populated exactly as it is for `TxType_FUNDS`.

### Proof of Concept
1. A user submits (or an inbound flow creates) a `GAS`-type withdrawal that results in an `OutboundTx` with `TxType == types.TxType_GAS` and a non-zero `Amount`/`Prc20AssetAddr`, following the same `BuildOutboundsFromReceipt` path used for other tx types.
2. UVs observe the destination-chain broadcast fail (e.g., destination-chain revert) and submit `MsgVoteOutbound` with `Success = false`, reaching quorum honestly.
3. `FinalizeOutbound` → `handleFailedOutbound` runs; because `outbound.TxType == types.TxType_GAS` is not in the allowlist at [7](#0-6) , `CallPRC20Deposit` is never called.
4. The outbound is marked `Status_REVERTED` with no `PcRevertExecution`, and the previously burned PRC20 principal is not returned to the user — permanent fund loss with no error surfaced to operators.
