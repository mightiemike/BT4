### Title
`liquidity_cap` on `TokenConfig` is never enforced before minting PRC20 on inbound deposits - (File: x/uexecutor/keeper/handler.go)

### Summary
The Allora M-9 bug pattern is "a configured mint cap exists but the code path that actually mints tokens never checks the accumulated minted amount against that cap before minting." Push Chain's `uregistry.TokenConfig` has a `liquidity_cap` field explicitly documented as the "max supply cap for this token (string big.Int format)" [1](#0-0) , but across the whole repository this field is only read for `ValidateBasic` non-emptiness checks and never compared against cumulative minted supply anywhere in the inbound deposit / PRC20 minting flow.

### Finding Description
`TokenConfig.LiquidityCap` is validated only for non-emptiness at config-creation time: [2](#0-1) 

Every inbound deposit path that mints native-representation PRC20 tokens (`depositPRC20`, `CallPRC20Deposit`, `CallPRC20DepositAutoSwap`) reads the token config only to obtain the PRC20 contract address and pulls `Amount` straight from the (validator-quorum-approved) inbound observation, with no lookup or comparison against `LiquidityCap`: [3](#0-2) [4](#0-3) 

A grep across the entire codebase for `LiquidityCap` shows it appears only in generated protobuf code, test files, JSON config fixtures, and the `ValidateBasic` empty-string check — it is never read by any keeper logic that gates minting (`depositPRC20`, `CallPRC20Deposit`, `CallPRC20DepositAutoSwap`, `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`). There is also no running "total minted for this token" counter analogous to Allora's `EcosystemTokensMinted` maintained anywhere in `x/uregistry` or `x/uexecutor`.

This mirrors the Allora M-9 root cause exactly: a cap value is stored/configured, but the mutation that increases supply (`AddEcosystemTokensMinted` in Allora vs. `depositPRC20`/PRC20 mint in Push Chain) is invoked unconditionally without checking remaining headroom against that cap.

### Impact Explanation
Unlike Allora's monthly emission (bounded to once per month), this gap is reachable on **every single inbound bridging transaction**. An unprivileged external attacker who controls or observes a source-chain gateway deposit (e.g. locking funds on an EVM/SVM gateway contract) can cause honest validators to vote-finalize arbitrarily many inbound observations for the same registered token, each triggering an unconditional PRC20 mint via `depositPRC20` with no aggregate ceiling enforced on Push Chain's side. If `liquidity_cap` is intended to bound the native-representation PRC20 supply that can be minted against a given external asset (to keep it 1:1 backed and to bound loss exposure), its absence of enforcement means PRC20 supply can be minted without any correlation to the configured cap, corrupting PRC20 accounting invariants and defeating a documented protocol safety control (unauthorized/unbounded mint of PRC20 relative to configured supply ceiling).

### Likelihood Explanation
High reachability: it requires no privileged actor — only ordinary inbound bridge deposits that reach validator quorum through the standard, honest-validator ballot flow. The field is populated in every shipped token config (testnet-donut JSON fixtures all set a non-trivial `liquidity_cap`), showing the cap is intended to be a real, enforced control, yet no code path enforces it.

### Recommendation
Before minting in `depositPRC20` (and its auto-swap variant), fetch the token's cumulative-minted counter (introduce one if it does not exist, e.g. `MintedSupply` keyed by chain+asset in `x/uregistry` state) and reject/clamp the mint when `mintedSupply + amount > LiquidityCap`, mirroring the Sherlock recommendation of clamping to the remaining cap rather than minting unconditionally. Increment the counter atomically with the mint call, and expose it via query for auditability.

### Proof of Concept
1. Register a `TokenConfig` for chain `eip155:X` / asset `A` with `liquidity_cap = "1000000000000000000000000"` (as done in `config/testnet-donut/*/tokens/*.json`).
2. Have honest validators observe and vote-finalize an arbitrary number of legitimate inbound `FUNDS` events referencing asset `A` (each vote path executes normally per `x/uexecutor/keeper/execute_inbound_funds.go` → `depositPRC20` → `CallPRC20Deposit`).
3. Sum of minted PRC20 amounts across these inbounds exceeds `liquidity_cap`; no error, revert, or clamp occurs because no code in `handler.go`, `evm.go`, or `execute_inbound_funds*.go` ever reads or compares against `LiquidityCap`.
4. Confirmed by the absence of any `LiquidityCap`/cap-check reference in `x/uexecutor/keeper/*.go` beyond config validation in `x/uregistry/types/token_config.go`.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
