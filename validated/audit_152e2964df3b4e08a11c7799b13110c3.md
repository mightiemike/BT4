Confirmed: `GasPrice` on an `OutboundTx` is a **permanent snapshot** taken at outbound-creation time from the EVM `UniversalTxOutbound` event / `UniversalCore.getOutboundTxGasAndFees` call [1](#0-0) , baked into the `OutboundCreatedEvent` JSON that the coordinator re-reads on every retry [2](#0-1) , with no mechanism to re-fetch a fresher price later.

### Title
Permanent lock of a pending outbound (and its bridged funds) when the destination chain's oracle gas price is snapshotted as zero at outbound creation - (File: `x/uexecutor/keeper/create_outbound.go`, `universalClient/chains/evm/tx_builder.go`)

### Summary
`UniversalCore.getOutboundTxGasAndFees` returns whatever gas price is currently stored on-chain for the destination chain's namespace. That value is written into the `OutboundTx.gas_price` field once, at outbound creation, and is carried unchanged in the `OutboundCreatedEvent` JSON used by the TSS coordinator on every subsequent signing attempt. If the chain-meta oracle for that destination chain has not yet reached its bootstrap quorum (3 fresh votes) — or its last-known median has aged out and no fresh vote has landed — `gasPriceByChainNamespace` returns `0`, exactly like `collateralFactorBps == 0` in the referenced report. The EVM `TxBuilder.GetOutboundSigningRequest` then hard-rejects with `"gas price is zero or missing in outbound event"` [3](#0-2) , so `buildSignTransaction` fails on every coordinator retry [4](#0-3)  and the outbound never advances from `PENDING`.

### Finding Description
1. A user submits an ordinary inbound (deposit/payload) that produces an outbound to a destination chain whose gas-price oracle has not bootstrapped yet (e.g. a newly added chain, or one where all prior votes went stale past `chainMetaVoteStalenessSeconds` with fewer than `chainMetaMinVotesForFirstWrite = 3` fresh votes) [5](#0-4) .
2. `BuildOutboundsFromReceipt` decodes the gateway's `UniversalTxOutbound` event, which itself embeds `gasPrice` computed by the `UniversalCore` contract at the moment the outbound was created; if the oracle hasn't posted a median yet, this value is `0` [1](#0-0) .
3. This `0` is persisted permanently onto `OutboundTx.GasPrice` and re-serialized into every `OutboundCreatedEvent` the coordinator/session-manager re-reads for signing retries — it is never re-derived from a live oracle read [2](#0-1) .
4. Every attempt to build a signing request for this EVM outbound explicitly rejects zero gas price [6](#0-5) , so `SessionManager.verifyOutboundSigningRequest`/`Coordinator.buildSignTransaction` never produce a valid TSS signing session for this specific outbound, no matter how many times the oracle is subsequently bootstrapped.
5. Per the module's own documented lifecycle, `PendingOutbounds` entries are **only** removed on validator consensus of a destination-chain observation; ballot/signing expiry does **not** clean them up, and "resolution is governance-driven, not chain-driven" [7](#0-6) . There is no automatic re-derivation or refund path for an outbound that can never be signed because its baked-in gas price is `0`.

This mirrors the external report precisely: a numeric parameter (`collateralFactorBps` → oracle gas price) reaching `0` causes an *implicit* block deep in downstream logic (withdrawal limit calc → outbound signing gate) rather than an explicit, recoverable "paused" state, and the affected value is frozen in place rather than re-checked.

### Impact Explanation
The user's bridged funds/payload outcome tied to that outbound are stuck: the `OutboundTx` stays `Status_PENDING` forever, the TSS coordinator can never assemble a valid signing hash for it, and per the documented design no automatic revert/refund exists for stuck outbounds — this requires manual/governance intervention. This is a permanent freezing of protocol-flow state (not user's PC-side balance, but the destination-chain leg of their cross-chain transfer/withdrawal) reachable purely by ordinary use (submitting a transaction against a newly configured or price-stale chain) with no privileged action on the attacker's part.

### Likelihood Explanation
Requires a destination chain whose gas-price oracle has fewer than 3 fresh votes (cold-start / newly onboarded chain, or one where validator gas-price votes have gone stale for >300s with no fresh re-votes reaching quorum) — a plausible operational window during onboarding of a new destination chain or oracle disruption, not requiring any malicious/privileged actor. Any ordinary user transaction that triggers an outbound to that chain during this window is permanently affected.

### Recommendation
- Do not persist `gas_price = 0` as a permanent, immutable field baked into `OutboundCreatedEvent`; instead, allow `GetOutboundSigningRequest` to re-fetch/re-quote a live gas price from `UniversalCore` at signing time when the snapshotted value is `0` or stale.
- Alternatively, block outbound creation (`BuildOutboundsFromReceipt`) itself with an explicit, catchable error when the destination chain's gas-price oracle has not yet bootstrapped, so the inbound path can fail-fast (and revert/refund the user) instead of committing a doomed `PENDING` outbound.
- Add an explicit escape hatch/refund path for outbounds whose gas price was snapshotted as `0`/invalid, distinct from the destination-chain-observation-only removal path currently documented.

### Proof of Concept
1. Add a new `ChainConfig` for a destination chain with `IsOutboundEnabled = true`, but ensure fewer than `chainMetaMinVotesForFirstWrite` (3) fresh `MsgVoteChainMeta` votes have been submitted (or none at all), so `gasPriceByChainNamespace` on `UniversalCore` remains `0` (see bootstrap gating in `VoteChainMeta`) [8](#0-7) .
2. Submit an ordinary `MsgVoteInbound`/execute-payload flow whose payload triggers a `UniversalTxOutbound` event to that chain — `getOutboundTxGasAndFees` returns `gasPrice = 0`, which is written to `OutboundTx.GasPrice` and included in the `OutboundCreatedEvent` [1](#0-0) .
3. Observe the `PendingOutboundEntry`/`OutboundTx` is created with `Status_PENDING`.
4. Even after the oracle later bootstraps with a valid non-zero price (subsequent unrelated votes), the coordinator's `buildSignTransaction` for this specific outbound still fails every tick with `"gas price is zero or missing in outbound event"` because the JSON event data captured at creation time is reused verbatim [9](#0-8) , [3](#0-2) .
5. Confirm via `README.md`'s documented lifecycle that no automatic timeout/refund exists for `PendingOutbounds` [7](#0-6)  — the outbound (and any bridged value tied to it) remains stuck indefinitely absent manual operator action.

func (c *Coordinator) buildSignTransaction(ctx context.Context, eventData []byte, assignedNonce *uint64) (*common.UnsignedSigningReq, error) {
	if len(eventData) == 0 {
		return nil, fmt.Errorf("event data is empty")
	}

	var data uexecutortypes.OutboundCreatedEvent
	if err := json.Unmarshal(eventData, &data); err != nil {
		return nil, fmt.Errorf("failed to unmarshal outbound event data: %w", err)
	}

	if data.TxID == "" {
		return nil, fmt.Errorf("outbound event missing tx_id")
	}

	if data.DestinationChain == "" {
		return nil, fmt.Errorf("outbound event missing destination_chain")
	}

	if c.chains == nil {
		return nil, fmt.Errorf("chains manager not configured")
	}

	// Get the client for the destination chain
	client, err := c.chains.GetClient(data.DestinationChain)
	if err != nil {
		return nil, fmt.Errorf("failed to get client for chain %s: %w", data.DestinationChain, err)
	}

	// Get the builder from the client
	builder, err := client.GetTxBuilder()
	if err != nil {
		return nil, fmt.Errorf("failed to get tx builder for chain %s: %w", data.DestinationChain, err)
	}

	// Get the signing request (nonce is required for SIGN)
	if assignedNonce == nil {
		return nil, fmt.Errorf("assigned nonce is required for sign transaction")
	}
	signingReq, err := builder.GetOutboundSigningRequest(ctx, &data, *assignedNonce)
	if err != nil {
		return nil, fmt.Errorf("failed to get outbound signing request: %w", err)
	}

- **Removed ONLY when validators reach consensus** (existing inline
  `PendingOutbounds.Remove` in `msg_vote_outbound.go` on `PASSED`).
- **Ballot expiry does NOT remove the entry** — this is intentional. The
  destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
