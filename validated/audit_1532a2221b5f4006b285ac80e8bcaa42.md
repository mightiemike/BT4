## Analog Found: Free EVM Execution via `MsgExecutePayload` Revert Path (No Gas Charged, No Cosmos Fee)

### Title
Unbounded, gasless computational DoS via `MsgExecutePayload` — fee deduction and EVM execution are both rolled back on any revert - (File: `x/uexecutor/keeper/execute_payload.go`)

### Summary
`MsgExecutePayload` is whitelisted as a fully gasless Cosmos message [1](#0-0) , meaning any unprivileged account can submit it at zero Cosmos-level fee [2](#0-1) . The handler runs a real EVM call (`CallUEAExecutePayload`, sized by the attacker-supplied, unbounded `gas_limit` field) and only bills the resulting EVM gas to the target UEA's balance if the whole cached transaction commits. If the EVM call reverts for any reason (e.g. deliberately invalid `verificationData`), the cache — including the already-computed fee deduction — is discarded entirely, so the computational work is never paid for by anyone.

### Finding Description
`ExecutePayloadV2` wraps EVM execution and fee deduction in a single `CacheContext`: [3](#0-2) 

The control flow is:
1. `CallUEAExecutePayload` runs the EVM call inside the cache, consuming real computation up to the caller-supplied `gas_limit` before potentially reverting.
2. `DeductGasFeesFromReceipt` is invoked in the same cache and *can succeed* in computing/charging the gas cost.
3. If `execErr != nil` (the EVM call reverted, e.g. bad `verificationData`), the function returns immediately **without calling `writeCache()`** — discarding both the EVM state changes *and* the fee deduction that had just been computed in the same cache.

The `gas_limit` field on `UniversalPayload` has no upper bound — `ValidateBasic` only checks that it parses as a non-negative integer: [4](#0-3) . `CallUEAExecutePayload` passes this value straight through as the EVM call's gas limit: [5](#0-4) .

`MsgExecutePayload` deliberately does not require `Signer == Owner`, and any account can submit it targeting any `UniversalAccountId` — the README explicitly documents that a failed signature check produces "zero state change" and "costs the attacker nothing on chain," treating this purely as a funds-safety property, not a compute-cost property: [6](#0-5) .

Because the Cosmos-level fee is skipped entirely for gasless messages [7](#0-6)  and the EVM-level charge is only committed on a fully successful, non-reverting execution, an attacker can force the validator set to perform real EVM computation (bounded only by the attacker's chosen `gas_limit` and the UEA's revert point) at zero cost, repeatedly, by intentionally supplying invalid `verificationData`.

### Impact Explanation
This is a denial-of-service class matching the report's bug class exactly: a computationally expensive operation (arbitrary-gas-limit EVM execution) is only charged for on success, and failure — trivially and cheaply triggerable by an attacker — voids the charge. Because the Cosmos envelope itself is also fee-free (whitelisted gasless message), an unprivileged external attacker can flood the network with `MsgExecutePayload` transactions carrying large `gas_limit` values and garbage `verificationData`, consuming validator CPU/EVM execution resources for free, repeatedly, with no balance requirement and no Cosmos fee. This falls within the allowed "denial of service... reachable without privileged control" impact category.

### Likelihood Explanation
High. No special privileges, staking, or bonded-validator status are required — `MsgExecutePayload` is explicitly "any user, gasless" [8](#0-7) . Constructing an invalid `verificationData` is trivial (any malformed or mismatched signature). The `gas_limit` field is fully attacker-controlled with no cap enforced in `ValidateBasic`.

### Recommendation
- Short term: commit (or otherwise account for) the computed fee deduction even when the EVM call itself reverts, so real EVM computation consumed is always billed to the UEA regardless of `execErr`. At minimum, charge a minimum/base fee for the CPU cost of attempting execution before the revert, independent of the `writeCache()` gate.
- Impose an explicit upper bound (a chain param) on `UniversalPayload.GasLimit` accepted via `MsgExecutePayload` so that a single free/failed attempt cannot consume unbounded computation.
- Long term: review all other gasless message types (`MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, TSS vote messages) for the same "compute-first, charge-only-on-full-success" pattern, even though those are additionally gated by bonded-UV checks.

### Proof of Concept
1. Attacker submits `MsgExecutePayload` with:
   - `Signer`: attacker's own funded (or even unfunded, since the message is gasless) account.
   - `UniversalAccountId`: any existing UEA (does not need to belong to the attacker).
   - `UniversalPayload.GasLimit`: a large value (e.g. `"21000000"`, as seen in existing test fixtures [9](#0-8) ).
   - `VerificationData`: garbage bytes that will fail signature verification inside the UEA contract.
2. `ExecutePayloadV2` runs `CallUEAExecutePayload`, which executes real EVM computation up to the point of revert.
3. `execErr != nil` is returned by the EVM call (signature check failed inside `executeUniversalTx`).
4. Because `execErr != nil`, the function returns before `writeCache()`, discarding the cache — including any fee amount that `DeductGasFeesFromReceipt` had already computed and would have charged.
5. The attacker paid zero Cosmos fee (message is gasless) and zero EVM gas fee (rolled back on revert), yet real EVM computation occurred. Repeating this at scale consumes validator resources for free.

**Note:** I could not verify from the indexed code whether there is a separate, higher-level rate limit or a maximum `GasWanted`/SDK gas-meter cap applied uniformly to gasless Cosmos transactions that might partially mitigate spam volume — this would require inspecting `app/ante/ante_cosmos.go` and the SDK gas-meter setup decorator in full, which were not returned by the index. If such a cap exists, it would bound but not eliminate the underlying issue (uncharged EVM computation on revert).

```go
	// commit/revert together. If fee deduction fails, the EVM state changes
	// from CallUEAExecutePayload are discarded — closes the free-execution
	// gap when the UEA has no native UPC to cover gas.
	cacheCtx, writeCache := sdkCtx.CacheContext()
	receipt, execErr := k.CallUEAExecutePayload(cacheCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

	// Step 3: Try fee deduction in the same cache. DeductGasFeesFromReceipt
	// is a no-op if the receipt is nil or GasUsed == 0 (EVM call produced
	// nothing to bill).
	if feeErr := k.DeductGasFeesFromReceipt(cacheCtx, cacheCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
		// Cache discarded — EVM state and any partial fee work both roll back.
		return receipt, fmt.Errorf("gas fee deduction failed: %w", feeErr)
	}

	if execErr != nil {
		// EVM execution failed — cache discarded by not calling writeCache.
		return receipt, execErr
```

```markdown
#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
```
