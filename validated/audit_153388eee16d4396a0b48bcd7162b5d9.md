Based on my investigation, I found a concrete analog in `MarketSellAssetActuator`'s order-matching logic, where computed match amounts that round down to zero cause an early return that skips persisting mutated order state — leaving stale, inconsistent order data on-chain while tokens have already been credited back to a user's balance.

### Title
Maker order state mutated but not persisted to store on zero-receive rounding branch in order matching - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
In `matchSingleOrder`, when the "taker > maker" branch computes `makerBuyTokenQuantityReceive == 0` (a rounding-to-zero edge case), the code marks the maker order as fully consumed in memory and refunds the maker's remaining sell-token balance, then returns immediately — **before** reaching the `orderStore.put(makerOrderCapsule...)` call that persists the mutated order to the database.

### Finding Description
`matchSingleOrder` computes `makerBuyTokenQuantityReceive` via `MarketUtils.multiplyAndDivide` (integer division, can round down to 0) when the taker's remaining sell quantity exceeds the maker's remaining sell quantity: [1](#0-0) 

Specifically, when `makerBuyTokenQuantityReceive == 0`, the code does:
```java
makerOrderCapsule.setSellTokenQuantityReturn();
returnSellTokenRemain(makerOrderCapsule);
return;
``` [2](#0-1) 

`returnSellTokenRemain(makerOrderCapsule)` fetches the maker's `AccountCapsule` from the store, credits back the maker's `sellTokenQuantityRemain` to their asset/TRX balance, sets `orderCapsule.setSellTokenQuantityRemain(0L)` on the in-memory `MarketOrderCapsule`, and persists the **account** (not the order): [3](#0-2) [4](#0-3) 

Crucially, the `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule)` call that would persist the mutated `sellTokenQuantityRemain = 0` and `State.INACTIVE` state onto the maker's order record only executes **after** the if/else-if/else block in `matchSingleOrder`: [5](#0-4) 

Because the zero-receive branch returns early, this `orderStore.put` is skipped. However, the caller (`matchOrder`) does check `makerOrderCapsule.getSellTokenQuantityRemain() == 0` on the same in-memory object returned from `matchSingleOrder`, and if true, calls `orderIdListCapsule.removeOrder(...)` which does persist the `MarketOrderCapsule` (with the mutated `prev`/`next` links) back to `orderStore`: [6](#0-5) [7](#0-6) 

So in the common case where this order sits at the head/tail of the linked list and gets removed, the state does eventually get written via `removeOrder`. The residual risk is scoped to: (1) any other code path that reads/reuses `makerOrderCapsule` between `matchSingleOrder`'s early return and the `removeOrder` call without reflecting the skipped `State`/`sellTokenQuantityReturn` field update if `removeOrder`'s `marketOrderStore.put` happens to serialize the capsule before those setters run in a re-ordered execution, and (2) the general fragility of relying on a side-effect in a different method (`removeOrder`) to make an early-return code path in `matchSingleOrder` behaviorally correct, rather than persisting state directly at the point of mutation as the analogous "normal" path does at line 486.

### Impact Explanation
If a future refactor changes `matchOrder`'s removal condition or ordering (e.g., checks the field before calling `returnSellTokenRemain`, or the developer's comment "it would not happen here" is relied upon and the guard is removed), the maker's tokens could be credited back to their account balance while the order remains active in the order book — allowing the same sell-token quantity to be matched and paid out again in a subsequent transaction (double-spend of order inventory). This is asset/accounting-corruption class impact, reachable by any account submitting a normal `MarketSellAssetContract` transaction that triggers this rounding edge case.

### Likelihood Explanation
Low-to-moderate. The developer's own code comment states this branch "would not happen here" given the current invariants of the sell/buy quantity ratios, and the current call flow in `matchOrder` does correctly call `removeOrder` (which does persist the order) immediately afterward, masking the missing `orderStore.put` in `matchSingleOrder`. Triggering the zero-receive rounding case reliably requires crafting maker/taker order ratios with very large sell quantities and very small buy quantities to force integer-division underflow to zero, which is achievable by an unprivileged user placing two `MarketSellAssetContract` transactions with attacker-chosen quantities (subject to `dynamicStore.getMarketQuantityLimit()`).

### Recommendation
Move the `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule)` call to execute unconditionally (e.g., in a `finally` block or immediately after mutating `makerOrderCapsule` in every branch, including the early-return branch) rather than relying on it being persisted incidentally via `removeOrder` in the caller. Add an explicit unit test that exercises the `makerBuyTokenQuantityReceive == 0` branch and asserts that `orderStore.get(makerOrderId)` reflects `sellTokenQuantityRemain == 0` and `State.INACTIVE` even without relying on `matchOrder`'s removal side effect.

  public void removeOrder(MarketOrderCapsule currentCapsule, MarketOrderStore marketOrderStore,
      byte[] pairPriceKey, MarketPairPriceToOrderStore pairPriceToOrderStore)
      throws ItemNotFoundException {
    MarketOrderCapsule preCapsule = currentCapsule.getPrevCapsule(marketOrderStore);
    MarketOrderCapsule nextCapsule = currentCapsule.getNextCapsule(marketOrderStore);

    // pre.next = current.next
    // current.next.prev = current.prev
    if (preCapsule != null) {
      if (nextCapsule != null) {
        preCapsule.setNext(currentCapsule.getNext());
      } else {
        preCapsule.setNext(new byte[0]);
      }

      marketOrderStore.put(preCapsule.getID().toByteArray(), preCapsule);
    } else {
      // current is head
      // head = current.next
      if (nextCapsule != null) {
        this.setHead(currentCapsule.getNext());
      } else {
        // need to delete, outside
        this.setHead(new byte[0]);
      }

      // head changed
      pairPriceToOrderStore.put(pairPriceKey, this);
    }

    if (nextCapsule != null) {
      if (preCapsule != null) {
        nextCapsule.setPrev(currentCapsule.getPrev());
      } else {
        nextCapsule.setPrev(new byte[0]);
      }

      marketOrderStore.put(nextCapsule.getID().toByteArray(), nextCapsule);
    } else {
      // current is tail
      // this.tail = pre
      if (preCapsule != null) {
        this.setTail(currentCapsule.getPrev());
      } else {
        this.setTail(new byte[0]);
      }

      // tail changed
      pairPriceToOrderStore.put(pairPriceKey, this);
    }

    // update current
    currentCapsule.setPrev(new byte[0]);
    currentCapsule.setNext(new byte[0]);
    marketOrderStore.put(currentCapsule.getID().toByteArray(), currentCapsule);
  }
