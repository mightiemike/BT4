The strongest and best-documented analog is the meta-transaction function-access-key allowance bypass. This is a direct structural match to the FIINU bug: a spending limit (`allowance`) is enforced on the direct-call code path but not enforced when the same restricted key is used through an alternate submission path (a `Delegate`/`DelegateV2` meta-transaction), letting a relayer-cooperating account exceed the limit the protocol intends to enforce on that access key.

### Title
Function-call access key `allowance` limit is not enforced when the key is used via a meta-transaction (`Delegate`/`DelegateV2`) - (File: `runtime/runtime/src/actions.rs`)

### Summary
`FunctionCallPermission.allowance` is documented as "a balance limit to use by this access key to pay for function call gas and transaction fees" [1](#0-0)  and is enforced for ordinary transactions in `verifier.rs` via `NotEnoughAllowance` [2](#0-1) . However, when the same key is used to sign the inner `DelegateAction`/`DelegateV2` of a meta-transaction, `validate_delegate_action_key` checks receiver, method name, deposit, and nonce, but never checks or debits `allowance` [3](#0-2) . All gas/fee costs are instead charged to the relayer, so the allowance cap that was supposed to bound this key's usable value is silently skipped on this alternate path.

### Finding Description
This is architecturally identical to the reported bug class: a value/spend limit (`maxRaiseWei` in the report, `allowance` here) is enforced on one entry point (`investFIAT`/direct signed transaction) but omitted on a second entry point that produces the same economic effect (the missing `require` / the missing allowance check in `validate_delegate_action_key`).

- Direct-tx path: `verify_and_charge_transaction` computes `cost` and compares it against `access_key.allowance`, returning `InvalidAccessKeyError::NotEnoughAllowance` if exceeded, and decrements the allowance on success.
- Meta-tx path: `validate_delegate_action_key` (`runtime/runtime/src/actions.rs:579-728`) validates nonce, receiver, method name, and deposit for a function-call access key, but has no corresponding allowance check or decrement anywhere in that function or in `apply_delegate_action`.
- The project's own architecture doc confirms this is real, current behavior, not a hypothetical: "For allowance, however, there is no check... even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work" [4](#0-3) .
- Integration tests confirm the current shipped behavior exercises exactly this: a key with 1 yoctoNEAR allowance (less than 1 gas unit) succeeds via a meta-transaction, explicitly annotated "this should still succeed because we use the gas of the relayer, not of the access key" [5](#0-4) , and the allowance is confirmed unchanged after a successful meta-tx call [6](#0-5) .

### Impact Explanation
An account owner who restricts a function-call access key to a small `allowance` (e.g. to limit the blast radius of a leaked/shared key to a trivial, low-value action) has that limit completely bypassed the moment any relayer is willing to wrap the same call in a `Delegate`/`DelegateV2` action. The key can then invoke the exact same method/receiver combination an unlimited number of times (bounded only by nonce/relayer willingness), fully defeating the allowance-based access control the account owner configured. Method/receiver restrictions still hold, so this is not full key compromise, but the allowance safety valve — the mechanism meant to bound "how much financial resource the key can use" — is nullified for any restricted key whenever a cooperating relayer exists (relayers are permissionless and can be the attacker or the key holder itself), for any current or future protocol version.

### Likelihood Explanation
High reachability: `Delegate`/`DelegateV2` meta-transactions are a standard, currently-live, unprivileged feature reachable by any signer/relayer pair; no special permission is required, and the doc explicitly frames this as something "circumventable... An interesting twist that comes with the addition of meta transactions," i.e. an acknowledged, reproducible gap rather than a theoretical edge case.

### Recommendation
In `validate_delegate_action_key` (or `apply_delegate_action`), when the signing access key has a `FunctionCallPermission` with `Some(allowance)`, compute the cost of the inner action(s) as if charged to that key and enforce/decrement `allowance` the same way the direct-transaction path does in `verifier.rs`, returning a `DelegateActionAccessKeyError`/`NotEnoughAllowance`-equivalent error when insufficient. If the intended design is that meta-transactions are exempt (since the relayer pays), this should be an explicit, documented protocol decision rather than a silent gap, and the `allowance` field's semantics/documentation should be updated accordingly to avoid users relying on a guarantee the protocol does not provide.

### Proof of Concept
1. Account `alice` creates a function-call access key restricted to `receiver_id = "bob.near"`, `method_names = ["do_thing"]`, `allowance = 1 yoctoNEAR` (effectively unusable directly, since it's below one gas unit).
2. Directly signing a transaction with this key to call `bob.near::do_thing` fails with `InvalidAccessKeyError::NotEnoughAllowance`.
3. Instead, `alice` (or anyone possessing the key) signs a `DelegateAction`/`DelegateV2` with `sender_id = alice`, `receiver_id = bob.near`, action `FunctionCall { method_name: "do_thing", deposit: 0 }`, using that same restricted key, and any `relayer` wraps and submits it as `Action::Delegate` on a transaction whose `receiver_id = alice`.
4. `validate_delegate_action_key` validates nonce/receiver/method and finds no allowance check; `apply_delegate_action` proceeds; the call executes successfully with all gas paid by the relayer, exactly as demonstrated by the existing test `meta_tx_fn_call_access_key_insufficient_allowance` [7](#0-6) .
5. Repeating step 3 with an incrementing nonce lets the key be used an unbounded number of times, even though its configured `allowance` was meant to cap it to essentially zero usable value — demonstrating the limit is bypassed on this path exactly as `maxRaiseWei` was bypassed via `investFIAT` in the original report.
