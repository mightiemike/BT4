### Title
Unmetered full VotesStore iteration in `MaintenanceManager.doMaintenance()` can be cheaply inflated by voter spam to cause a chain-wide processing stall - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager.doMaintenance()` is invoked from `applyBlock()`, which runs on every full node as part of ordinary block application (the DPoS analog of an unmetered `BeginBlock`/end-of-epoch hook) whenever the maintenance boundary is crossed. Inside it, `countVote(votesStore)` performs a full, unbounded iteration over the entire `VotesStore` LevelDB/RocksDB table and deletes every entry, with no gas/energy metering and no cap on the number of entries processed.

### Finding Description
`doMaintenance()` calls `countVote(votesStore)`: [1](#0-0) 

This method opens a raw store iterator (`votesStore.iterator()`) and walks every entry in the store, accumulating vote deltas and then deleting each entry — with no bound on the number of entries and no execution-cost accounting, since it runs outside of any transaction's energy/bandwidth metering. It is triggered unconditionally at every maintenance-cycle boundary: [2](#0-1) [3](#0-2) 

The `VotesStore` is populated by `VoteWitnessActuator.countVoteAccount()`, which is executed as the actuator for `VoteWitnessContract` and, unlike a metered opcode loop, only costs the ordinary bandwidth/fee of a single transaction regardless of how many entries already exist in the store: [4](#0-3) 

Each distinct account address that casts a vote creates (or updates) exactly one `VotesStore` entry. An attacker can mass-create many accounts (each account creation itself is a cheap, fee-metered, per-transaction operation, see `CreateAccountActuator`/`TransferActuator` account-creation-fee path) and, from every one of them, submit a minimal `VoteWitnessContract` transaction (only one vote, smallest positive `voteCount`, which easily satisfies the tron-power check for an account holding minimal frozen/staked TRX). Each such vote transaction costs only ordinary, bounded transaction fees/bandwidth — there is no cost that scales with the eventual size of `VotesStore`. By spreading these cheap vote transactions across many blocks before the next maintenance boundary, an attacker can inflate `VotesStore` to a very large number of entries at negligible marginal cost per entry — directly analogous to the reported Cosmos SDK bug where cheap per-token spam deposits inflate an account's balance map that is later iterated without metering.

When the maintenance boundary is reached, every full node (not just the block producer) must synchronously execute `doMaintenance()` as part of normal block processing/state transition in order to stay in consensus, so the resulting O(N) unmetered iteration and deletion over the bloated `VotesStore` runs on every node simultaneously and blocks progression of that block's processing.

### Impact Explanation
This is a consensus-layer denial-of-service: the entire network of full nodes/witnesses executes the unmetered `countVote()` loop synchronously at the maintenance boundary. If the attacker has sufficiently inflated `VotesStore` beforehand (cheaply, over multiple blocks, using many low-cost accounts each casting one vote), the maintenance-cycle block processing time balloons for every node at the same wall-clock moment, which can cause block-production delays, missed block slots, or a full chain halt/stall — a permissionless, on-demand DoS against protocol liveness, matching the "concrete... DoS via... protocol implementation" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate-to-high: casting a vote requires only a funded account (minimal balance sufficient to satisfy the `tronPower >= sum` check in `VoteWitnessActuator.validate()`) and paying the standard bandwidth/transaction fee — there is no additional or scaling fee tied to the number of existing `VotesStore` entries. An attacker with modest capital can create a large number of throwaway accounts and cast one vote from each across a batch of blocks before a maintenance cycle triggers, at a cost that does not scale with the resulting `VotesStore` size. This mirrors the reported bug's core weakness: attacker-controlled growth of a structure that is iterated in full, without metering, at a predictable, permissionless trigger point (here, the maintenance-time boundary rather than every block).

### Recommendation
- Bound the cost of casting votes so that the fee/bandwidth consumed scales with (or reflects) the resulting size of `VotesStore`, or impose a hard cap on outstanding unprocessed vote entries per cycle.
- Alternatively, meter/charge the maintenance-cycle vote-counting work (e.g., account for it against a global gas-like budget, or process the `VotesStore` incrementally across multiple blocks with a bounded per-block work limit) rather than performing a single unbounded synchronous pass in `doMaintenance()`.
- Add monitoring/alerting on `VotesStore` size growth so operators can detect abnormal inflation before a maintenance boundary is reached.

### Proof of Concept
Conceptual reproduction (would need to be built into a `java-tron` integration/unit test harness, similar in spirit to the reported Cosmos SDK PoC):
1. Fund and create N throwaway accounts (`CreateAccountActuator`/`TransferActuator`), each with the minimal TRX/frozen balance needed to pass the `tronPower` check in `VoteWitnessActuator.validate()`.
2. From each account, submit one `VoteWitnessContract` transaction with a single vote for an existing witness, spread across multiple blocks to stay within per-block/per-account bandwidth limits — this populates `VotesStore` with N entries at minimal, non-scaling cost.
3. Advance the chain time/block height past `nextMaintenanceTime` so that `MaintenanceManager.applyBlock()` triggers `doMaintenance()`.
4. Measure the wall-clock time consumed by `countVote(votesStore)` (`consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java:165-195`) as N grows — as in the original report, the duration should scale linearly with N and this work is performed unmetered and synchronously by every full node at the same block, demonstrating the DoS potential.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
