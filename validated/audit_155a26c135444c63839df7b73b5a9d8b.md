## Analysis

The BadgerDAO report is about a **price feed used to mint/burn funds without any protection against transient manipulation or an outlier price** — the fix proposed was to check new price readings against a recent median/threshold before trusting them for fund-moving operations.

The closest Push Chain analog is in `x/uexecutor/keeper/evm.go`'s `GetSwapQuote`, consumed by the GAS / GAS_AND_PAYLOAD inbound execution paths (`x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`) and by the outbound gas refund path (`x/uexecutor/keeper/outbound.go`'s `applyGasRefund`/`getSwapQuoteForRefund`).

`GetSwapQuote` reads the instantaneous Uniswap V3 `QuoterV2.quoteExactInputSingle` spot price for the module's internal PRC20↔WPC pool: [1](#0-0) 

This single spot-price read is used, with only a flat 5% slippage margin computed *from that same reading*, to authorize a module-originated fund-moving EVM call: [2](#0-1) [3](#0-2) 

There is no reference to a moving-average, no cross-check against a second source, and no staleness/outlier filtering of the quote — the exact bug class flagged in the BadgerDAO report (a single externally-influenceable value trusted directly for a mint/burn/deposit operation). Because the `minPCOut` bound is derived from the very same instantaneous reading rather than an independent trusted reference, an attacker who can shift the pool's spot price in the same block just before the module's deterministic auto-swap executes (e.g., by getting a large swap transaction included earlier in the same block, which does not require validator collusion — only normal mempool/fee competition) can cause the deposit-auto-swap or gas refund swap to execute at a manipulated price while still satisfying its own (self-referential) slippage check. The same pattern is reused by the refund flow: [4](#0-3) 

This differs structurally from `x/uexecutor/keeper/chain_meta.go`'s `VoteChainMeta`, which *does* implement the report's exact recommended mitigation pattern — collecting multiple validator-signed observations, filtering by staleness, and using the median before writing to the EVM: [5](#0-4) . That path is not a valid analog since it already implements the fix. The Uniswap quoter path has no equivalent protection.

I do not have enough visibility into the on-chain Uniswap V3 pool's actual liquidity depth, the block-execution ordering guarantees for module-originated `DerivedEVMCall`s relative to ordinary user transactions in the same block, or whether these PRC20/WPC pools carry deep enough liquidity to make manipulation economically infeasible. Confirming exploitability (rather than just the missing invariant) requires checking those specifics, which are not fully covered in the indexed code — a Devin session with full repository and possibly on-chain state access would be needed to validate real-world feasibility and quantify the achievable value extraction before this can be finalized as a confirmed, high-confidence finding rather than a structural observation.

### Title
Unvalidated single-block AMM spot-price quote used to authorize module-originated deposit/refund swaps - (File: x/uexecutor/keeper/evm.go)

### Summary
`GetSwapQuote` fetches a single, instantaneous Uniswap V3 `QuoterV2` spot price and that same reading is used both to compute the `minPCOut` slippage floor and to authorize the module's `depositPRC20WithAutoSwap` / `refundUnusedGas` calls, with no independent reference price, no staleness/outlier check, and no protection against the price being manipulated immediately before the module's swap executes in the same block.

### Finding Description
`x/uexecutor/keeper/evm.go`'s `GetSwapQuote` (lines 500-538) performs a `quoteExactInputSingle` call against the configured Uniswap V3 Quoter and returns the raw `amountOut`. Both `ExecuteInboundGas` (execute_inbound_gas.go:126-153), `gasAndPayloadDepositAutoSwap` (execute_inbound_gas_and_payload.go:348-379), and `applyGasRefund`'s refund path (outbound.go:213-230) derive `minPCOut = quote * 95 / 100` directly from that quote and immediately pass it into a fund-moving, module-signed `DerivedEVMCall` (`CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas`). Because the slippage bound is computed from the same reading used to execute the trade, this offers no protection if the spot price itself was manipulated moments earlier — the report's fundamental complaint about `WrappedIbbtc`/`WrappedIbbtcEth` trusting an externally-updatable price without cross-checking it against recent history.

### Impact Explanation
If the pool backing a given PRC20↔WPC pair is manipulated in the same block prior to the module's automatic swap (e.g., via a large trade submitted with sufficient priority to land earlier in block ordering, without needing any validator or admin privilege), the module will execute the user's deposit swap or gas refund swap at the manipulated price, directly reducing the amount of PC that reaches the user's UEA (deposit case) or the refund recipient (refund case) — an unauthorized value transfer out of protocol/user-controlled funds into the manipulator's position, matching the "unauthorized… corruption of gas fee accounting/refund accounting" impact category.

### Likelihood Explanation
Likelihood depends on real-world liquidity depth of the specific PRC20/WPC pools and on transaction-ordering guarantees within a block that are not fully visible from the indexed code, so this should be treated as a structural weakness requiring further on-chain verification rather than a confirmed exploit.

### Recommendation
Do not derive the slippage bound solely from the instantaneous quote used to execute the trade. Use a TWAP or multi-observation median (the same pattern already implemented for `ChainMeta` gas-price voting) as the reference price, and/or cap the acceptable deviation between the just-in-time quote and that reference before allowing the module-originated swap to proceed.

### Proof of Concept
Not independently verified against live pool liquidity/ordering guarantees; requires further investigation with full repository and chain-state access (see caveat above) before a concrete exploit sequence can be demonstrated.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
