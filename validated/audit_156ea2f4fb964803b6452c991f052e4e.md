Confirmed: `action_to_promise(target, action)` in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:475-501` executes the Near action (including `AddKey`/`DeleteKey`) against `target`, not against `current_account_id`. This confirms the vulnerability I identified.

### Title
Wallet Contract accepts a relayer-chosen `target` account for `AddKey`/`DeleteKey` actions, allowing key operations on a foreign account - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs)

### Summary
NEAR's Ethereum-compatible Wallet Contract (`rlp_execute`) decodes an RLP-encoded, user-signed Ethereum transaction and converts it into a Near `Action` executed via `Promise::new(target)`. For `AddKey`/`DeleteKey`, the ABI-encoded calldata carries no explicit account target — the design intends these actions to always apply to the wallet's own account (`current_account_id`). However, the caller-supplied `target: AccountId` parameter of `rlp_execute` is validated only against the *address* encoded in the signed Ethereum transaction (`tx.to`), and when `target` resolves to `TargetKind::OtherNearAccount` the code never checks `target == current_account_id` before dispatching the action.

### Finding Description
`parse_tx_data` in [1](#0-0)  decodes `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` calldata into `ParsableTransactionKind::SelfNearNativeAction`, with no `receiver_id` field validated against `target` (unlike `FUNCTION_CALL_SELECTOR`/`TRANSFER_SELECTOR`, which explicitly check `target.as_str() != receiver_id.as_str()` at [2](#0-1) ).

In `parse_rlp_tx_to_action`, the `SelfNearNativeAction` branch only special-cases `TargetKind::EthImplicit` (converts to a harmless self-transfer); for any other `target_kind` (including `TargetKind::OtherNearAccount`) it falls through to using the original `AddKey`/`DeleteKey` action unmodified: [3](#0-2) 

`validate_tx_relayer_data` only checks that `target` is consistent with `tx.to` (via address match or `account_id_to_address(target)` hash match); it never enforces `target == current_account_id` for this case: [4](#0-3) 

Finally, the action is dispatched via `Promise::new(target)`, meaning `AddKey`/`DeleteKey` actually execute on `target`, not on the wallet's `current_account_id`: [5](#0-4) 

This mirrors the report's bug class: a validation routine checks that two distinct identifiers are *consistent with each other* (owner ↔ receiver signature scheme in the Solidity report; `target` ↔ `tx.to` here) but omits the specific additional constraint required for a particular action variant (owner ≠ receiver in the report; `target == current_account_id` for self-only actions here), letting an unprivileged caller (the relayer, who freely chooses `target`) redirect the action to an account it should never apply to.

### Impact Explanation
If `target` can be any named Near account that the caller controls (or any account whose `account_id_to_address` hash the caller can make `tx.to` equal — trivial since the caller chooses both `target` and constructs the RLP transaction being "relayed"), then a `DeleteKey` or (function-call-scoped) `AddKey` action intended to only ever apply to the wallet contract's own account can instead be dispatched against an arbitrary other account named in `target`, as long as that promise call is authorized by the wallet contract's outgoing cross-contract call permissions (the wallet contract itself must be the predecessor of the `AddKey`/`DeleteKey` action on `target`, which NEAR enforces via `check_actor_permissions` requiring `actor_id == account_id`). Since `Promise::new(target)` executes as an action receipt whose predecessor is the wallet contract account (not the `target` account itself), the runtime's `check_actor_permissions` (`runtime/runtime/src/actions.rs:755-801`, requiring `actor_id == account_id` for `AddKey`/`DeleteKey`) would reject an `AddKey`/`DeleteKey` where the wallet contract is not `target` itself, causing the receipt to fail rather than corrupt a foreign account. This significantly limits real-world exploitability to failed receipts/gas waste against unrelated accounts, rather than actual unauthorized key modification, because Near's native runtime action-actor check independently guards against this. I could not fully verify whether any state (e.g. wasted attached gas/deposit, nonce increments, or partial refund logic) is abused before the runtime rejects the mismatched actor, given the available context.

### Likelihood Explanation
Reaching this path only requires calling `rlp_execute` with attacker-chosen `target` and a self-crafted RLP payload — fully within reach of an unprivileged relayer/caller as described in scope. However, since `check_actor_permissions` in the core runtime independently blocks `AddKey`/`DeleteKey` where `actor_id != account_id`, the practical value-movement or state-corruption impact is unproven from the code reviewed.

### Recommendation
In `parse_rlp_tx_to_action` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`), explicitly reject `SelfNearNativeAction` payloads unless `target_kind == TargetKind::CurrentAccount`, instead of only special-casing `TargetKind::EthImplicit` and silently falling through for `TargetKind::OtherNearAccount`.

### Proof of Concept
Not fully constructable from available context: exploitation depends on whether `check_actor_permissions` in `runtime/runtime/src/actions.rs` (`actor_id == account_id` requirement for `AddKey`/`DeleteKey`) is bypassed anywhere in this flow, which I could not confirm produces exploitable unauthorized value movement given the tool budget. I recommend a Devin session with full repo access to trace the actual predecessor/actor_id used for the resulting receipt end-to-end and confirm whether this is fully mitigated by the runtime-level actor check or represents a real bypass.

fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }

    let nonce = if tx.nonce <= U64_MAX {
        tx.nonce.low_u64()
    } else {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    };
    if nonce != expected_nonce {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    }

    // Relayers must attach at least as much gas as the user requested.
    let gas_limit = if tx.gas_limit < U64_MAX { tx.gas_limit.as_u64() } else { u64::MAX };
    if env::prepaid_gas().as_gas() < gas_limit.saturating_mul(GAS_MULTIPLIER) {
        return Err(Error::Relayer(RelayerError::InsufficientGas));
    }

    Ok(target_kind)
}

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
}
