### Title
Unbounded array-size read in Cairo0 syscall deserialization can trigger an out-of-memory panic - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The Cairo0 (deprecated) syscall argument parser `read_felt_array` converts a caller-supplied felt directly into an allocation size and eagerly reads that many memory cells from the Cairo VM, with no upper bound check against the transaction's actual resource/gas budget before the read is attempted. This mirrors the Helm `strvals` bug class: an attacker-controlled length value is used to drive a large allocation/array read before the corresponding data is validated to exist, risking an out-of-memory panic.

### Finding Description
`read_felt_array` in the deprecated syscalls hint processor reads an `array_size` felt directly from VM memory (fully controlled by the executing Cairo0 contract's code, which is attacker-supplied at declare/deploy/invoke time), converts it to a `usize`, and passes it straight into `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)`: [1](#0-0) 

`felt_range_from_ptr` forwards `size` unchanged into the underlying VM memory-range read: [2](#0-1) 

The equivalent Cairo1 syscall path (`crates/blockifier/src/execution/syscalls/hint_processor.rs`) at least derives its array size from `(end_ptr - start_ptr)`, which is bounded by two pointers into an actually-allocated Cairo memory segment. In contrast, the Cairo0 path's `array_size` is an independent felt value that the contract writes next to the data pointer — it is not derived from real segment boundaries, so a malicious Cairo0 contract can set it to an arbitrary large value (e.g., close to `usize::MAX`) while writing only a couple of real memory cells: [3](#0-2) 

This `read_felt_array`/`read_calldata`/`read_call_params` path is invoked whenever a Cairo0 contract issues a syscall carrying an array-like argument (e.g. `call_contract`, `library_call`, `send_message_to_l1`), which is directly reachable by any account that declares a Cairo0 class and invokes it, or via any transaction whose execution path calls into such a class (e.g. through `library_call`).

### Impact Explanation
If the underlying `cairo-vm` `get_integer_range` implementation pre-allocates a `Vec` (or similar buffer) sized to the requested count before validating that the memory range is actually populated, a single crafted Cairo0 contract call can force the sequencer/node process to attempt an enormous allocation. Depending on the allocator's behavior this either aborts the process (Rust's global allocator aborts on allocation failure rather than returning an error, since `Vec::with_capacity`/`reserve` calls `handle_alloc_error` on failure) or causes severe memory pressure, taking down the sequencer/full node process handling that transaction — a denial of service reachable from an ordinary, unprivileged transaction. This matches the Medium severity DoS pattern in the reported Helm CVE (attacker input drives unchecked array/allocation size, causing an unrecoverable panic/abort).

### Likelihood Explanation
Likelihood depends on two factors I could not fully verify from this codebase alone (cairo-vm is an external dependency and its `get_integer_range` source is not vendored in this repo): (1) whether `get_integer_range` eagerly allocates a `Vec::with_capacity(size)` before checking bounds, and (2) whether an earlier gas/step-accounting check already bounds `size` to something proportional to consumed resources before this function is reached. If either mitigation exists, the practical impact is reduced to an ordinary bounded error rather than an OOM abort. Given the uncertainty around the exact allocation behavior of the pinned `cairo-vm` version, I flag this as a plausible but unconfirmed analog rather than a proven one.

### Recommendation
Add an explicit upper bound check on `array_size` in `read_felt_array` (deprecated_syscalls) before calling `felt_range_from_ptr`, capping it to a small multiple of the transaction's remaining gas/step budget or to a fixed protocol-level maximum (consistent with `max_calldata_length` enforced at the gateway for RPC transactions), and reject with a descriptive error if exceeded — mirroring the bound already implicitly provided by the pointer-difference approach in the Cairo1 `read_felt_array`.

### Proof of Concept
Conceptually: a declared Cairo0 contract whose bytecode, upon invocation, writes a syscall request segment of the form `[array_size = 0x1fffffffffffffff, data_ptr]` (two Cairo VM store operations, costing only a couple of execution steps) into memory before issuing `send_message_to_l1`/`call_contract`. When the syscall handler calls `read_felt_array`, `array_size` converts to a near-`usize::MAX` value that is passed to `vm.get_integer_range`, attempting to materialize an enormous felt vector, which can abort the executing node process. I was unable to execute or trace into the vendored `cairo-vm` crate to confirm the exact allocation strategy, so this PoC describes the expected trigger path rather than a confirmed crash reproduction.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
}

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
