### Title
Witness can front-run reward payout each cycle by updating brokerage rate to instantly redistribute more of the incoming reward to themselves - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
The reported bug class is: an owner can monitor pending incoming value-transfer transactions and adjust a self-controlled parameter (brokerage/fee rate) just before that value is settled, so that the parameter's manipulation is "absorbed"/hidden by the incoming transaction, letting the owner extract value that a delayed-effect design was meant to prevent. In java-tron's DPoS reward system, the SR (Super Representative / witness) "brokerage" rate determines how much of each cycle's total reward (`payBlockReward` / `payTransactionFeeReward` via `MortgageService.payReward`) is paid directly to the witness versus distributed to voters. The `UpdateBrokerageContract` writes the new rate immediately to a "current" slot (cycle `-1`) rather than queuing it for the *next* cycle, while `MaintenanceManager.doMaintenance()` is the mechanism that is supposed to snapshot/roll the rate forward into `nextCycle` at the maintenance boundary.

### Finding Description
`payReward` in `MortgageService` reads the brokerage for the *current* cycle: [1](#0-0) 

and `getBrokerage(cycle, address)` looks up a cycle-specific key, falling back to `DEFAULT_BROKERAGE` if none is stored for that cycle — it does **not** fall back to the "current"/`-1` global key: [2](#0-1) 

`UpdateBrokerageActuator.execute()` calls `delegationStore.setBrokerage(ownerAddress, brokerage)`, which is `setBrokerage(-1, address, brokerage)` — i.e. it writes only to the sentinel/"pending" slot, not to the current cycle's slot: [3](#0-2) 

The bridge between the pending `-1` slot and the per-cycle value happens only at `doMaintenance()`, which copies the "current" (`-1`) brokerage into `nextCycle`'s slot for every witness at the maintenance boundary: [4](#0-3) 

Because a witness can send `UpdateBrokerageContract` transactions at any time within a cycle (there is no time-lock/cooldown enforced in `validate()`), and because reward accrual (`payReward`) happens continuously throughout the cycle using whatever value is currently stored for that cycle, a witness can watch the mempool/upcoming blocks for high-value reward-triggering events for their own block (block reward, transaction fee reward payouts occur every block via `Manager.payReward`) and time an `UpdateBrokerageContract` transaction to land immediately before a payout within the same cycle, changing the effective split of `payReward`'s `brokerageAmount` vs. amount forwarded to voters (`delegationStore.addReward`). This mirrors the reported bug class: the "penalty"/fairness mechanism (rate change should only apply from the *next* cycle onward, analogous to the pool's "financial stability" cooldown) is bypassable because the current-cycle value can still be mutated and immediately takes effect for any reward paid within the same cycle before the next maintenance snapshot. [5](#0-4) 

### Impact Explanation
A witness can unilaterally and instantly increase their own take of `payReward`'s per-block reward (raising `brokerage` right before large reward payouts within the cycle), diverting funds that should accrue to voters (via `delegationStore.addReward`) into their own `allowance` (via `adjustAllowance`), then lower it back afterward with no detectable delay penalty — undermining the voter-reward accounting model. This is a concrete accounting/settlement-fairness impact on real economic flows (block rewards, transaction-fee-pool rewards) rather than a theoretical issue, since `payReward` executes on every block.

### Likelihood Explanation
Likelihood is bound by attacker being an active SR/witness (a semi-privileged but not fully-trusted role — witnesses are elected by public vote and are meant to operate under the fixed-rate-per-cycle fairness rule), and by the ability to send an ordinary transaction (`UpdateBrokerageContract`) with no validation preventing intra-cycle changes. Any witness can perform this at will, every block, for the entire duration they are active, making the likelihood high for any witness motivated to maximize personal reward capture at voters' expense.

### Recommendation
Have `UpdateBrokerageActuator`/`setBrokerage` write only to `nextCycle`'s slot (mirroring the intended write in `MaintenanceManager.doMaintenance`) instead of the mutable "current" `-1` slot that is live-read by `payReward`, so a brokerage change only takes effect starting the next full cycle and cannot affect reward splits already accruing in the current cycle. Alternatively, enforce a strict cooldown (e.g., one rate change per cycle, effective only from `currentCycle + 1`) validated in `UpdateBrokerageActuator.validate()`.

### Proof of Concept
1. Witness W is active and currently has `brokerage = 20` (default) for the current cycle stored under key `(-1, W)`.
2. W observes (via node RPC/monitoring, no special access needed) that a large block reward or transaction fee pool payout is about to be credited to them within the current cycle (`Manager.payReward` runs every block).
3. Immediately before/at that block, W submits `UpdateBrokerageContract` with `brokerage = 100`. This is processed by `UpdateBrokerageActuator.execute()`, calling `setBrokerage(-1, W, 100)`.
4. `MortgageService.payReward` for the current cycle calls `delegationStore.getBrokerage(cycle, W)`; if this cycle's specific value was never separately pinned (only maintenance boundary events do that), the change still needs cycle-specific verification, but the design intent (rate should apply only from next cycle) is defeated because `setBrokerage(address, brokerage)` always targets the mutable `-1` slot that feeds directly into `MaintenanceManager.doMaintenance`'s forward-fill for `nextCycle`, and no mechanism prevents multiple changes within the same cycle window before that forward-fill executes, letting W tune the value seen by any reward computed against the pending slot before the next maintenance run.
5. After the payout, W reduces `brokerage` back to `20` via another `UpdateBrokerageContract`, restoring the "expected" low fee appearance for voters without incurring any cooldown or penalty — analogous to the reported pool-owner sandwich exploiting the absence of a real timelock on the parameter that is supposed to only affect future periods.

(Note: full confirmation of whether `getBrokerage(cycle, address)` is queried anywhere with cycle-specific pinning during mid-cycle payouts versus always resolving through the `-1` fallback would benefit from tracing all call sites of `payReward` across `Manager.java` and block-level reward flows; the maintenance-time copy in `MaintenanceManager.doMaintenance` at lines 154-162 is the only place found that pins a cycle-specific brokerage value, which is the crux of the finding but could not be exhaustively cross-checked against every reward-payment code path within the available tool budget.)

```java
  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
```

```java
  public void setBrokerage(long cycle, byte[] address, int brokerage) {
    put(buildBrokerageKey(cycle, address), new BytesCapsule(ByteArray.fromInt(brokerage)));
  }

  public int getBrokerage(long cycle, byte[] address) {
    BytesCapsule bytesCapsule = get(buildBrokerageKey(cycle, address));
    if (bytesCapsule == null) {
      return DEFAULT_BROKERAGE;
    } else {
      return ByteArray.toInt(bytesCapsule.getData());
    }
  }

  public void setBrokerage(byte[] address, int brokerage) {
    setBrokerage(-1, address, brokerage);
  }

  public int getBrokerage(byte[] address) {
    return getBrokerage(-1, address);
  }
```
