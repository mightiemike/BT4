### Title
Exchange-subsystem pause (`rejectExchangeTransaction`) only guards `ExchangeTransactionContract`, leaving sibling actuators that mutate the same exchange balances unguarded - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
java-tron implements a "pause" for the exchange subsystem: after fork `VERSION_4_8_0_1`, every transaction in a block is checked by `rejectExchangeTransaction()`, which throws `ContractValidateException` if the contract is an `ExchangeTransactionContract` and `allowHardenExchangeCalculation` is not yet enabled by committee vote. This is functionally a market pause protecting the `ExchangeCapsule`'s `firstTokenBalance`/`secondTokenBalance` state from unsafe (non-strict-math) arithmetic until the hardened calculation path is turned on. However, the pause check is narrowly scoped to a single contract type and is not applied to the other actuators (`ExchangeWithdrawActuator`, and by the same code pattern `ExchangeInjectActuator`/`ExchangeCreateActuator`) that read and mutate the very same exchange balance state.

### Finding Description
The guard is implemented as: [1](#0-0) 

`isExchangeTransaction` only matches `ContractType.ExchangeTransactionContract` in its `switch`, and `rejectExchangeTransaction` is invoked per-transaction inside `processBlock`: [2](#0-1) 

The same check (`isExchangeTransaction`) is also used to reject exchange trades at the mempool entry point (`pushTransaction`) and to skip them during block packing (`generateBlock`): [3](#0-2) [4](#0-3) 

The purpose of this pause is clearly tied to the unsafe/hardened math distinction in the exchange balance-update code path, exposed via `AbstractExchangeActuator.allowHarden()` and `ExchangeCapsule.transaction(...)`: [5](#0-4) [6](#0-5) 

`ExchangeWithdrawActuator`, however, is a completely separate, unprivileged public actuator (`ExchangeWithdrawContract`) that reads/writes `firstTokenBalance`/`secondTokenBalance` on the same `ExchangeCapsule` and only conditionally applies stricter precision checks based on the same `allowHarden()` flag, without ever being checked by `isExchangeTransaction`/`rejectExchangeTransaction`: [7](#0-6) 

Because `rejectExchangeTransaction`'s `switch` statement enumerates only `ExchangeTransactionContract`, any other `ExchangeXXXContract` type transaction (Withdraw, Inject, Create) is never rejected regardless of the `allowHardenExchangeCalculation` flag, `processBlock`'s pause check, or `pushTransaction`'s pause check. This mirrors the reported bug class exactly: a pause primitive is applied to one code path that mutates protected state, while sibling public/external entry points that mutate the identical state are left completely unguarded — making it possible to continue mutating exchange-pool balances (and potentially trigger the same unsafe non-strict-math arithmetic the pause was meant to prevent) while the "exchange pause" is nominally in effect.

### Impact Explanation
While the network operator/committee believes exchange trading is halted (pre-`ALLOW_HARDEN_EXCHANGE_CALCULATION`) to prevent unsafe-math exploitation of `ExchangeCapsule` balances, any user can still call `ExchangeWithdrawContract` (and structurally, `ExchangeInjectContract`/`ExchangeCreateContract`) to change `firstTokenBalance`/`secondTokenBalance` using the same non-hardened arithmetic (`ExchangeCapsule.transaction(..., hardenedCalc=false)` semantics are mirrored in Withdraw's manual `BigDecimal`/non-strict branch). This undermines the intent of the pause: state accounting for exchange pools can continue to diverge or be manipulated during the window the protocol considers "paused," defeating the purpose of gating exchange trades behind a hardened-math governance flag and potentially reintroducing the accounting risk the pause was designed to close.

### Likelihood Explanation
High that the gap exists as coded: `isExchangeTransaction`'s `switch` unambiguously matches only one `ContractType`, so Withdraw/Inject/Create are provably unreachable by the guard for any state (`grep`/`codebase_search` found no other call site referencing these contract types in the reject/pause logic). Confirming actual overflow/inconsistency severity of `ExchangeWithdrawActuator`'s non-hardened branch under adversarial balances was not possible within the tool budget (I could not inspect `ExchangeInjectActuator`/`ExchangeCreateActuator` source, nor step through the historic vulnerability that `ALLOW_HARDEN_EXCHANGE_CALCULATION` was introduced to fix), so the concrete exploit magnitude of the bypass is not fully verified — only the fact that the pause mechanism itself does not cover these actuators.

### Recommendation
Broaden `isExchangeTransaction`'s `switch` (or add equivalent checks) to also match `ExchangeWithdrawContract`, `ExchangeInjectContract`, and `ExchangeCreateContract` so that `rejectExchangeTransaction` (called from `processBlock`) and the `pushTransaction`/`generateBlock` guards uniformly pause the entire exchange subsystem — not just trade contracts — until `allowHardenExchangeCalculation` is enabled. Audit all actuators touching `ExchangeCapsule` balances to ensure the hardened-math gate is enforced consistently across every entry point that can mutate that state.

### Proof of Concept
1. Deploy/observe a java-tron network post fork `VERSION_4_8_0_1` with `allowHardenExchangeCalculation = 0` (exchange trading believed "paused").
2. Attempt to broadcast an `ExchangeTransactionContract` transaction — it is rejected by `pushTransaction` ( [3](#0-2) ) and by `processBlock`'s `rejectExchangeTransaction` ( [2](#0-1) ).
3. Instead broadcast an `ExchangeWithdrawContract` transaction targeting the same exchange ID. Because `isExchangeTransaction`/`rejectExchangeTransaction` never inspect this `ContractType`, the transaction is accepted into the mempool, packed into blocks, and executed by `ExchangeWithdrawActuator`, mutating `firstTokenBalance`/`secondTokenBalance` on the exchange pool via the same non-hardened arithmetic path ( [7](#0-6) ) that the pause was intended to block.
4. This demonstrates the exchange balances continue to change through an unguarded sibling actuator while the trade-specific pause is active, confirming the bypass.

  private boolean isExchangeTransaction(Transaction transaction) {
    if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
      return false;
    }
    Contract contract = transaction.getRawData().getContract(0);
    switch (contract.getType()) {
      case ExchangeTransactionContract: {
        return true;
      }
      default:
        return false;
    }
  }

  private void rejectExchangeTransaction(Transaction transaction) throws ContractValidateException {
    if (isExchangeTransaction(transaction) && chainBaseManager.getForkController()
            .pass(Parameter.ForkBlockVersionEnum.VERSION_4_8_0_1)) {
      throw new ContractValidateException("ExchangeTransactionContract is rejected");
    }
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
