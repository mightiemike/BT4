### Title
Unbounded goroutine/HTTP-client spawn per on-chain OracleRequest event allows resource-exhaustion DoS - ([File: core/services/functions/listener.go], [File: core/services/functions/external_adapter_client.go])

### Summary
`functionsListener.processOracleEventsV1` spawns one unthrottled goroutine per `OracleRequest` log returned from `logPollerWrapper.LatestEvents`, and each goroutine eventually calls `externalAdapterClient.request`, which allocates a brand-new `retryablehttp.NewClient()` (with its own transport/connection pool and `RetryMax`/backoff) for every single call. There is no concurrency limiter, worker pool, or shared HTTP client anywhere in this path, so the node's goroutine count, open file descriptors, and outbound connections scale linearly and unboundedly with the volume of on-chain Functions requests.

### Finding Description
The event-processing loop reads all pending on-chain events on every tick and fires off a goroutine per request with no cap: [1](#0-0) 

`handleOracleRequestV1` → `handleRequest` then acquires a bridge client and calls `RunComputation` for every request, and potentially `getSecrets` as well, each of which funnels into `ea.request`: [2](#0-1) 

Inside `externalAdapterClient.request`, a fresh `retryablehttp.NewClient()` is constructed on every invocation, instead of reusing a shared, pooled client: [3](#0-2) 

There is no semaphore, worker pool, or `MaxConcurrent`-style config value anywhere in `core/services/functions/` bounding the number of simultaneous `handleOracleRequestV1`/`handleRequest`/`request()` invocations; a grep across the package found only per-request timeouts (`ListenerEventHandlerTimeoutSec`) and DB-level pruning limits (`PruneMaxStoredRequests`, `PruneBatchSize`), none of which bound in-flight concurrency. Each new `retryablehttp.Client` created via `StandardClient()` gets its own `http.Transport` with a default connection pool, so N concurrent requests can create up to N independent transports/connection pools rather than sharing one, multiplying idle-connection and file-descriptor usage compared to a properly pooled client.

The DB layer does perform request-ID deduplication (`ErrDuplicateRequestID` in `CreateRequest`), so an attacker cannot literally replay the same request ID, but each distinct on-chain `OracleRequest` (new tx) still results in a new goroutine + new HTTP client, uncapped.

However, reaching `handleOracleRequestV1` at scale is not literally "free": generating `OracleRequest` events requires transactions through the FunctionsRouter/Coordinator contracts, which in this repo's test fixtures require subscription creation, LINK funding (`SubscriptionDepositJuels: 9 LINK`, `SubscriptionDepositMinimumRequests: 10`), and per-tx gas costs, as seen in the integration test harness: [4](#0-3) 
This means the attack is bounded by on-chain economics (gas + subscription funding) and by block gas limits/throughput, not literally free or instant — it does not qualify as "low-cost flooding" in the strictest sense, but it does not require any node-operator privilege, and the node-side handling remains structurally unbounded regardless of the cost of generating events.

### Impact Explanation
If an attacker (owning or interacting with a permissionless `FunctionsConsumer`/subscription) submits many requests in a short window, the node's `processOracleEventsV1` loop will spawn a goroutine and a new `retryablehttp.Client`/`http.Transport` per request simultaneously, with no cap on concurrency. This can exhaust node goroutines, file descriptors, and outbound connections to the bridge, degrading or stalling the EA/OCR computation pipeline for the affected job and potentially impacting node stability more broadly (matches "repeated denial of key node functions" bounty impact). The severity is moderate rather than critical because generating the flood requires real gas expenditure and subscription funding, i.e., it is not a truly free attack, and impact is scoped to the Functions job/pipeline rather than global node compromise.

### Likelihood Explanation
- Preconditions: attacker needs a Functions subscription with sufficient LINK funding and gas to submit many `OracleRequest`-generating transactions within a short polling window (`ListenerEventsCheckFrequencyMillis`); no operator/admin privilege is required.
- Feasibility: creating hundreds/thousands of distinct on-chain requests is realistic for a moderately funded attacker, especially on low-gas L2 chains where Functions is commonly deployed.
- Repeatability: the flood can be repeated on every polling tick as long as funding/gas is available, since there is no server-side rate limit independent of on-chain volume.

### Recommendation
- Bound concurrency of `processOracleEventsV1`'s per-event goroutines with a worker pool or semaphore (e.g., `errgroup.Group` with `SetLimit`, or a buffered channel of workers), configurable via `PluginConfig`.
- Replace per-call `retryablehttp.NewClient()` in `externalAdapterClient.request` with a single shared, package/struct-level `retryablehttp.Client` (or `http.Client` with a bounded `Transport` / `MaxIdleConnsPerHost` / `MaxConnsPerHost`) reused across all requests to the same bridge URL.
- Consider adding an explicit rate limiter (e.g., `golang.org/x/time/rate`) or a maximum in-flight request count per job/contract, independent of on-chain event volume, so that node resource usage is capped regardless of how many `OracleRequest` events arrive per polling interval.

### Proof of Concept
Unit/integration test plan (extends `core/services/functions/listener_test.go` patterns):
1. Build a `FunctionsListenerUniverse` as in `TestFunctionsListener_HandleOracleRequestV1_Success`, but have `logPollerWrapper.On("LatestEvents", ...)` return a slice of several thousand synthetic, uniquely-ID'd `evmconfig.OracleRequest` entries on a single call.
2. Stub `bridgeAccessor.NewExternalAdapterClient` to return a real `externalAdapterClient` pointed at an `httptest.Server` that blocks (`<-done`) to keep connections/goroutines alive, similar to `TestRunComputation_ContextRespected`.
3. Start the listener (`servicetest.Run`) and, before unblocking the test server, sample `runtime.NumGoroutine()` and the number of open connections/transports to the mock server.
4. Assert that goroutine/connection growth is proportional to N with no upper bound applied by the listener (demonstrating the vulnerability), or — after applying the recommended fix — assert that concurrency is capped at a configured maximum regardless of N.
5. Close the test server (`close(done)`) and confirm the listener drains cleanly via `shutdownWaitGroup`.

```go
func (l *functionsListener) handleRequest(ctx context.Context, requestID RequestID, subscriptionId uint64, subscriptionOwner common.Address, flags RequestFlags, requestData *RequestData) error {
	startTime := time.Now()
	defer func() {
		duration := time.Since(startTime)
		promComputationDuration.WithLabelValues(l.contractAddressHex).Observe(float64(duration.Milliseconds()))
	}()
	requestIDStr := formatRequestId(requestID)
	l.logger.Infow("processing request", "requestID", requestIDStr)

	eaClient, err := l.bridgeAccessor.NewExternalAdapterClient(ctx)
	if err != nil {
		l.logger.Errorw("failed to create ExternalAdapterClient", "requestID", requestIDStr, "err", err)
		l.setError(ctx, requestID, INTERNAL_ERROR, []byte(err.Error()))
		return err
	}

	nodeProvidedSecrets, userErr, internalErr := l.getSecrets(ctx, eaClient, requestID, subscriptionOwner, requestData)
	if internalErr != nil {
		l.logger.Errorw("internal error during getSecrets", "requestID", requestIDStr, "err", internalErr)
		l.setError(ctx, requestID, INTERNAL_ERROR, []byte(internalErr.Error()))
		return internalErr
	}
	if userErr != nil {
		l.logger.Debugw("user error during getSecrets", "requestID", requestIDStr, "err", userErr)
		l.setError(ctx, requestID, USER_ERROR, []byte(userErr.Error()))
		return nil // user error
	}

	maxSecretsSize := l.getMaxSecretsSize(flags)
	if uint32(len(nodeProvidedSecrets)) > maxSecretsSize {
		l.logger.Errorw("secrets size too big", "requestID", requestIDStr, "secretsSize", len(nodeProvidedSecrets), "maxSecretsSize", maxSecretsSize)
		l.setError(ctx, requestID, USER_ERROR, []byte("secrets size too big"))
		return nil // user error
	}

	computationResult, computationError, domains, err := eaClient.RunComputation(ctx, requestIDStr, l.job.Name.ValueOrZero(), subscriptionOwner.Hex(), subscriptionId, flags, nodeProvidedSecrets, requestData)
```
