### Title
Unbounded growth of `zero_lamport_accounts_to_purge_after_full_snapshot` causes an ever-larger single-threaded `retain()` scan that stalls the accounts background service - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::zero_lamport_accounts_to_purge_after_full_snapshot` is a `DashSet<(Slot, Pubkey)>` that accumulates one entry every time `clean_accounts` finds a zero-lamport account whose update slot is newer than the latest full snapshot slot. Any unprivileged user can trivially and cheaply cause such entries to be added (fund then drain an account to zero, repeated across many rooted slots). The set is only drained by a single, non-parallel `DashSet::retain()` call, and only once a *full* snapshot has advanced — an event that, by default, happens roughly every tens of thousands of slots. Between full snapshots the set can grow essentially without bound, so the eventual `retain()` becomes an unbounded, single-threaded O(n) scan that runs inside `clean_accounts`, delaying the accounts background service's flush/clean/shrink/snapshot pipeline.

### Finding Description
The field is declared with a comment describing exactly this "keep alive until incremental snapshot support" purpose: [1](#0-0) 

It is populated in `filter_zero_lamport_clean_for_incremental_snapshots`, which is invoked on every `clean_accounts` call. Whenever a zero-lamport account's slot is newer than `latest_full_snapshot_slot`, the `(slot, pubkey)` pair is inserted and never removed until a subsequent full snapshot advances past it: [2](#0-1) 

The only place this set shrinks is a single `retain()` call gated behind `latest_full_snapshot_slot_advanced_since_clean`, i.e. it only runs once a *full* snapshot (not an incremental one) has been produced since the last clean pass: [3](#0-2) 

This `retain()` is a full, sequential iteration over the entire `DashSet`, run inline inside `construct_candidate_clean_keys`, which is itself part of `clean_accounts`. `clean_accounts` runs on the `AccountsBackgroundService`'s main loop, which sequentially handles flush, clean, shrink, and snapshot requests: [4](#0-3) 

Because full snapshots occur far less frequently than clean passes (which run roughly every `CLEAN_INTERVAL`), and because any account owner can create and immediately zero-out accounts as often and in as many distinct rooted slots as they like (the cost is only the fee/rent of a normal transaction), the `DashSet` can be grown to an arbitrarily large size between full snapshots. There is no cap, eviction policy, or incremental drain — only this all-at-once `retain()`.

### Impact Explanation
The `retain()` call cost is proportional to the number of accumulated `(Slot, Pubkey)` entries. As this set grows unbounded between full snapshots, the eventual drain becomes an increasingly expensive, single-threaded operation executed on the accounts background service thread, which also handles subsequent clean/shrink work and hands off snapshot requests. A sufficiently large backlog directly degrades validator performance at the moment a full snapshot completes — the worst possible time, since it is already a heavy operation — increasing the risk of the accounts background service falling behind, delaying subsequent clean/shrink cycles and snapshot generation. This matches the accepted "disproportionate CPU cost" impact category.

### Likelihood Explanation
Likelihood is low-to-medium: it requires sustained, repeated zero-lamport account churn by one or more unprivileged users across many rooted slots during the (long) interval between full snapshots, which costs normal transaction fees/rent but no special privilege. It does not require multiple clients or crafted snapshots, and is entirely achievable by an ordinary account holder over time.

### Recommendation
Bound the size of `zero_lamport_accounts_to_purge_after_full_snapshot` (e.g., cap total entries, or trigger a partial/periodic drain instead of only draining fully at the full-snapshot boundary), or parallelize/chunk the `retain()` so a single large backlog cannot stall the background service loop.

### Proof of Concept
1. Start a validator without a very short full-snapshot interval.
2. As an unprivileged user, repeatedly submit transactions that fund an account and then transfer its full balance out (returning it to zero lamports), using a fresh account/slot each time, for as many rooted slots as possible between full snapshots.
3. Each such zero-lamport update newer than `latest_full_snapshot_slot` adds one entry to `zero_lamport_accounts_to_purge_after_full_snapshot` via `filter_zero_lamport_clean_for_incremental_snapshots` (accounts_db.rs:2367-2368), and no entry is removed until the next full snapshot.
4. When the next full snapshot completes, observe the single-threaded `retain()` in `construct_candidate_clean_keys` (accounts_db.rs:1693-1702) taking proportionally longer as the accumulated set size grows, delaying subsequent clean/shrink/snapshot-request handling in `AccountsBackgroundService`.
