### Title
Borrower can self-reset `last-borrow-block` to permanently block liquidation of an unhealthy position - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`debt-add-scaled` in `v0-market-vault.clar` stamps `last-borrow-block` with `stacks-block-height` every time debt is added, and `liquidate` in `v0-4-market.clar` refuses to liquidate if `last-borrow-block` equals the current block. A borrower whose position has become unhealthy can call `borrow` again for a trivial amount in every new block, which resets `last-borrow-block` and makes the "same-block" anti-flash-loan guard active again, indefinitely delaying liquidation.

### Finding Description
`debt-add-scaled` unconditionally overwrites `last-borrow-block` on every borrow: [1](#0-0) 

`liquidate` reads that same field and reverts if the liquidator's transaction lands in the same block as `last-borrow-block`: [2](#0-1) 

The value bound is `last-borrow-block`, set to `stacks-block-height` by any `borrow` call. The event that invalidates the original intent of this guard (blocking only literal same-block flash-loan borrow→liquidate sequences) is a subsequent, unrelated `borrow` call by the same account in a later block, which re-arms the guard for that new block. The later use is the `same-block-check` inside `liquidate`, which is executed after the position's health has already degraded (e.g., price drop), meaning the borrower is using the guard defensively rather than as originally intended (protecting only against intra-block flash-loan manipulation).

This differs qualitatively from the `Shelter.sol` bug (an authorized "client" resetting an activation timestamp to bypass a grace-period deadline) in that here it is the position owner itself re-arming a same-block check every block, rather than resetting an expired deadline in one shot. It also is not "two different users interfering" — it's the same account (borrower) manipulating its own state to block a different actor (the liquidator) from executing a legitimate, unrelated operation.

However, note the practical constraint: to keep re-arming the guard the borrower must submit a valid `borrow` transaction in every single block, which requires health checks in `borrow` to still pass (`is-healthy` pre/post checks) — i.e. the borrower can only keep doing this if borrowing further doesn't push the position over the liquidation threshold in a way that fails `ERR-UNHEALTHY`. Once the position is already at/above `ltv-liq-partial` (liquidatable), an *additional* borrow would typically fail the `is-healthy` postcondition check in `borrow`: [3](#0-2) 

This significantly narrows the exploitable window: the guard reset requires a successful borrow, but a borrow that would keep the position healthy generally would not also be a position eligible for liquidation (liquidation requires `current-ltv >= ltv-liq-partial`, which is a laxer/different threshold than `borrow`'s `ltv-borrow` health check). There is a real "gap" LTV band between `ltv-borrow` (health check for new borrows) and `ltv-liq-partial` (liquidation threshold) — if the position's LTV sits in that band (unhealthy for further borrowing is not necessarily true; borrowing itself is blocked by `is-healthy` using `ltv-borrow`, not `ltv-liq-partial`), the borrower cannot borrow more once above `ltv-borrow`, closing this attack vector for most configurations. I was not able to fully verify from the indexed code whether `ltv-borrow < ltv-liq-partial` is a protocol invariant enforced anywhere (it would need to be, otherwise this griefing path is closed structurally) — this needs to be confirmed by reading the `egroup`/asset registry parameter-setting logic in full, which the index did not surface completely.

### Impact Explanation
If exploitable, this would allow a borrower to indefinitely block liquidation of their own already-unhealthy, undercollateralized position by re-triggering `last-borrow-block` every block, causing protocol insolvency risk (bad debt accrues while liquidation is blocked) — this would map to the Critical/High impact class ("protocol insolvency" or "temporary freezing of funds" for the collateral/liquidator side). However, this requires that a `borrow` transaction can still succeed once the position is already liquidatable, which depends on `ltv-borrow` vs `ltv-liq-partial` ordering that I could not conclusively verify from the available index.

### Likelihood Explanation
Low-to-uncertain. The attack requires the attacker to submit a borrow transaction in literally every block indefinitely (an unusual, costly, bot-like behavior), and it is contingent on the un-verified assumption that `borrow`'s health check threshold (`ltv-borrow`) is looser than the liquidation threshold (`ltv-liq-partial`) at the specific point where the position sits. In most reasonable protocol configurations, `ltv-borrow < ltv-liq-partial`, meaning once a position crosses into liquidatable territory it can no longer pass `borrow`'s own health check, closing the loophole.

### Recommendation
Given the uncertainty in exploitability, the safer fix — regardless of whether the health-check ordering closes the gap in current parameters — is to decouple the same-block anti-flash-loan check from a single mutable "last borrow" timestamp. Options: only re-arm `last-borrow-block` on the *asset* being liquidated (already done), and/or bound the check to protect only the specific debt asset+amount borrowed in that same block rather than blocking all liquidation of the account for the entire block; or track borrow blocks per-asset instead of per-account so unrelated borrows can't extend protection to unrelated debts.

### Proof of Concept
1. Borrower's position degrades toward the liquidation threshold (price drop).
2. Each block, borrower calls `market.borrow` for a minimal amount of any enabled debt asset for which they still pass the `is-healthy` pre/post checks; this resets `last-borrow-block` to the current `stacks-block-height` via `debt-add-scaled`.
3. Liquidator calls `market.liquidate`; `same-block-check` in `liquidate` (`v0-4-market.clar:1428-1431`) reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK` because `last-borrow-block` equals the current block.
4. Repeat every block to indefinitely stall liquidation — **contingent on step 2 remaining possible, which requires further verification of the `ltv-borrow` vs `ltv-liq-partial` relationship in the egroup registry that could not be fully confirmed from the indexed code.**
