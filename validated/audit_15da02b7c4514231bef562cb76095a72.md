### Title
Unrolled fee-deduction failure lets a UEA/CEA recipient consume real EVM execution without paying gas — via `ExecutePayloadV2` call sites that bypass the `CacheContext` protection applied to the smart-contract path - (File: `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
The external report's core defect is a **check that guards one dimension of a multi-step operation (balance) while leaving a second required guarantee (allowance) unenforced**, so a batch of dependent sub-operations can partially succeed and partially fail, leaving inconsistent state. The Push Chain analog lives in `x/uexecutor`'s gas-fee-accounting invariant: `DerivedEVMCall` execution of a UEA's `executeUniversalTx`/`ExecutePayloadV2` and the subsequent `DeductGasFeesFromReceipt` gas-fee debit are two sequential, independently-fallible sub-operations that must be atomic (execute only if it can be paid for). The code base itself documents (via commit message/comment `F-2026-16738`) that this exact "free execution" gap was previously exploitable and was patched — but only for **one** of the two structurally-identical call sites (the `isSmartContract` / CEA-to-contract branch). The parallel branch that executes the payload through a `UEA` contract via `ExecutePayloadV2` (used in both `ExecuteInboundGasAndPayload` and `ExecuteInboundFundsAndPayload`, non-smart-contract path) still performs the EVM call directly on `sdkCtx` and only afterward calls `DeductGasFeesFromReceipt`, with no `CacheContext` wrapping.

### Finding Description
Compare the two branches in `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`:

- **Smart-contract branch (patched, lines 216-284):** wraps `CallExecuteUniversalTx` + `DeductGasFeesFromReceipt` in a `sdkCtx.CacheContext()`, only calling `writeCache()` if fee deduction succeeds: [1](#0-0) 

- **UEA payload branch (unpatched, lines 286-334):** calls `ExecutePayloadV2` directly against `ctx`/`sdkCtx` (not a cache context), and there is no post-hoc fee-deduction call visible in this function at all before the PCTx is marked `SUCCESS`: [2](#0-1) 

The identical asymmetry exists in `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`: the `isSmartContract` branch is wrapped in `CacheContext` with the explicit comment "closes the free-execution gap when the recipient contract has no native UPC to cover gas," while the UEA-path branch below it calls `ExecutePayloadV2(ctx, ...)` directly: [3](#0-2) [4](#0-3) 

By contrast, `MsgExecutePayload`'s direct-message path (`msg_execute_payload.go`) does enforce the invariant, but by returning an error to roll back the *entire* Cosmos transaction rather than isolating just the EVM sub-state: [5](#0-4) 

`DeductGasFeesFromReceipt` itself performs the actual balance-insufficiency detection only as a side effect of `bankKeeper.SendCoinsFromAccountToModule` failing inside `DeductAndBurnFees` — there is no upfront allowance/sufficiency gate before the EVM call is committed: [6](#0-5) 

**I could not locate an `ExecutePayloadV2` implementation or an explicit `CacheContext`/fee-deduction call inside the UEA branch of these two functions within the index** — the branch (lines 286-334 and 285-326) ends with `ExecutePayloadV2(...)` returning `receipt, err`, and the PCTx is marked `SUCCESS` on any non-nil receipt with no error, without a visible corresponding `DeductGasFeesFromReceipt` call in that specific code path (unlike `msg_execute_payload.go`, which explicitly calls it). This is either (a) fee deduction happening inside `ExecutePayloadV2` itself (whose body I could not retrieve from the index), in which case the finding reduces to "same-context commit, no cache isolation" rather than "fee deduction is skipped entirely," or (b) an outright fee-skip bug. Given the index's coverage limits, I cannot fully confirm which of these is true from static inspection alone.

### Impact Explanation
If `ExecutePayloadV2` performs the EVM execution and fee debit in the same (non-cached) `sdkCtx`, then, mirroring the exact class of bug the `F-2026-16738` fix addressed for the smart-contract branch: an inbound with a `UniversalPayload` targeting a UEA whose EVM balance is insufficient to cover `gasCost` could have its EVM call's state changes persist (since they are not wrapped in a discardable `CacheContext`) even though the corresponding gas fee was never collected. This is unauthorized module-originated EVM execution without payment — a direct violation of the "gas fee accounting ... revert destination ... must preserve ... fund invariants" allowed-impact category, and matches "unauthorized UEA ... execution" if the fee debit can be bypassed by an attacker deliberately draining/never funding the UEA's native balance before submitting a payload-bearing inbound.

### Likelihood Explanation
Medium. This requires: (1) an attacker (or any unprivileged relayer of source-chain events) to submit or trigger an inbound with `TxType_GAS_AND_PAYLOAD` or `FUNDS_AND_PAYLOAD` whose UEA recipient has zero/insufficient native `upc` balance at the time of PCTx execution and whose deposited/auto-swapped PRC20 amount is zero or doesn't top up the UEA's native balance; and (2) confirmation that `ExecutePayloadV2` does not itself already wrap execution+fee-deduction in a `CacheContext` (which the code's own precedent — the `F-2026-16738` comment — suggests was needed elsewhere but which I could not verify is present here). Given honest validators vote based on real source-chain data, the attacker only needs to control gas/balance conditions on their own UEA, which is fully within an unprivileged actor's control.

### Recommendation
1. Audit `ExecutePayloadV2` (and any other call site producing a UEA-targeted `DerivedEVMCall` receipt) to confirm whether it wraps EVM execution and `DeductGasFeesFromReceipt` in the same atomic unit the way the `isSmartContract` branches already do.
2. If it does not, apply the identical `CacheContext`/`writeCache()` pattern used in the `isSmartContract` branches of both `execute_inbound_gas_and_payload.go` and `execute_inbound_funds_and_payload.go` to the UEA-payload branches, so that a failed `DeductGasFeesFromReceipt` discards the `executeUniversalTx`/payload execution's state changes.
3. Add an explicit pre-flight balance/allowance-style check (verify `bankKeeper.GetBalance(recipient) >= gasCost` before committing the EVM call) as defense-in-depth, analogous to the recommended `allowance >= totalAmount` check in the original report, rather than relying solely on `SendCoinsFromAccountToModule` failing after the fact.

### Proof of Concept
Not able to construct a concrete, verified PoC from the available index: the body of `ExecutePayloadV2` was not retrievable, so I cannot confirm whether it independently performs cached fee-deduction (in which case there is no vulnerability) or commits directly to `sdkCtx` (in which case the free-execution gap is live). 2. // DeductGasFeesFromReceipt calculates and deducts gas fees from a recipient address
```go
// based on the EVM receipt and universal payload parameters.
// Returns nil if receipt is nil (Go-level error, no EVM tx was created).
// Returns error with gas details if deduction fails (insufficient balance, etc).
func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}
```
