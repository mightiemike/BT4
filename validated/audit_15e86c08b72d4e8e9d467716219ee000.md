### Title
Missing slippage protection in `ExchangeWithdrawActuator` allows front-run value extraction from bancor-style TRC10 Exchange pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's built-in decentralized Exchange feature (TRC10 token pools using a bancor/constant-product-like formula) exposes `ExchangeWithdrawContract`, processed by `ExchangeWithdrawActuator`, allowing a pool creator to withdraw one side of the pool and receive a proportional amount of the other token, computed from the *current* pool ratio at execution time. Unlike the sibling `ExchangeTransactionContract` (regular trades), which carries an `expected` field enforcing a minimum-output/slippage check, `ExchangeWithdrawContract` has no analogous field, so a withdrawal's payout ratio is entirely dictated by whatever the pool state is at the moment the transaction executes.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` purely from the live pool balances (`firstTokenBalance`/`secondTokenBalance`) read at validation/execution time and only checks internal precision, not caller-specified min-out: [2](#0-1) 

Compare with `ExchangeTransactionActuator`, where the caller supplies `tokenExpected` and validation explicitly rejects an unfavorable ratio at execution time: [3](#0-2) 

Because `ExchangeWithdrawContract` provides only `token_id` and `quant` with no expected/minimum output for the "other" token, a pool creator submitting a withdrawal has no way to bound how much of the paired token they will receive: [4](#0-3) 

This mirrors the reported vault bug class exactly: any transaction that changes the pool's token ratio before the withdrawal executes — most directly an `ExchangeTransactionContract` (a normal buy/sell trade) submitted by another party and included earlier in the same block, or another party's own `ExchangeWithdrawContract`/`ExchangeInjectContract` — will change `firstTokenBalance`/`secondTokenBalance` used by the withdrawal calculation. Block producers order transactions within a block (mempool ordering is not FIFO/guaranteed), so an adversary observing a pending `ExchangeWithdrawContract` can submit a trade that is included first in the same block to skew the ratio, extracting value from the withdrawing party without their consent, exactly as Mallory does to Alice in the reported vault report.

Additionally, `ExchangeCapsule.transaction()` (used by trading) and the withdrawal math in `ExchangeWithdrawActuator` operate on the same mutable `ExchangeCapsule` balances, confirming that trades directly affect the ratio a subsequent withdrawal will observe: [5](#0-4) 

### Impact Explanation
A withdrawing exchange creator can receive materially less of the paired token than expected when withdrawing, because there is no minimum-output guard — an attacker can front-run the withdrawal with a trade (`ExchangeTransactionContract`) that skews the pool ratio unfavorably for the withdrawer, extracting value analogous to the value-leak in the cited report. Since `ExchangeWithdrawActuator` is reachable directly from any broadcast transaction (anonymous, unprivileged from the perspective of the protocol — any account holding an exchange it created can invoke it, and any account can submit trades against that same exchange to manipulate ratios), this is an unprivileged, RPC-reachable accounting/market-math defect. It results in the withdrawing party losing value relative to the expected exchange rate, i.e., an accounting/value-extraction issue.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an existing TRC10 `Exchange` pool with at least one pending withdrawal, and (b) an attacker able to submit a competing trade transaction that a block producer includes ahead of (or in the same block prior to) the withdrawal transaction. Since java-tron block producers control transaction ordering within a block and transactions are visible in the mempool/network prior to inclusion, this ordering manipulation is realistic, though it depends on witness cooperation or opportunistic ordering rather than a strict public mempool auction as on EVM chains. The precision checks (`allowHarden()` / "Not precise enough") in `doValidate()` only guard against integer rounding drift, not against ratio manipulation between submission and execution.

### Recommendation
Add a minimum-expected-output (slippage) field to `ExchangeWithdrawContract`, mirroring `ExchangeTransactionContract.expected`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the withdrawal if the computed `anotherTokenQuant` is below the caller-specified minimum.

### Proof of Concept
1. Pool creator holds an `Exchange` with `firstTokenBalance = 1000`, `secondTokenBalance = 1000` (1:1 ratio).
2. Creator broadcasts `ExchangeWithdrawContract` to withdraw `500` of `firstTokenId`, expecting ~`500` of `secondTokenId` based on current ratio, per `doValidate()`'s computation at [6](#0-5) .
3. An attacker observes the pending withdrawal and submits an `ExchangeTransactionContract` selling a large amount of `secondTokenId` into the pool, which a block producer includes before the withdrawal in the same block, sharply shifting `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()`.
4. When the withdrawal executes, `ExchangeWithdrawActuator.execute()` recomputes `anotherTokenQuant` from the now-skewed balances at [7](#0-6) , giving the creator far less `secondTokenId` than originally intended, with no on-chain mechanism to reject the unfavorable outcome.
