## Title
`ensure_match_transaction_info` fails to validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, allowing state-root divergence to pass replay/apply-chunk verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant-checking routine used across chunk-execution and replay-verify paths to confirm that a locally executed/applied `TransactionOutput` actually matches an externally supplied, proof-backed `TransactionInfo`. It explicitly checks status, gas, write-set hash, and event root hash, but a code comment in the function itself documents that it *intentionally* skips validating the state-checkpoint-related hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) that are part of `TransactionInfo`.

### Finding Description
`ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) validates:
- status/`TransactionStatus`
- `gas_used`
- `state_change_hash` (write-set hash)
- `event_root_hash`

but the function's own comment admits:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [1](#0-0) 

This function is called from three independently significant integrity-checking call sites in the chunk-executor and tooling paths:
1. `execution/executor/src/chunk_executor/mod.rs` `verify_execution`, used when the state-sync/backup restore chunk executor re-executes transactions locally and validates them against externally-supplied `TransactionInfo`/write-set/events before committing them via `remove_and_apply` → `enqueue_chunk` (`ReplayChunkVerifier`). [2](#0-1) 
2. `storage/db-tool/src/replay_on_archive.rs` `execute_and_verify`, the ledger-replay auditing tool that is expected to catch divergences between VM re-execution and the archived, ledger-committed `TransactionInfo`. [3](#0-2) 
3. `aptos-move/aptos-debugger` and `aptos-move/cli` debugging/verification tools.

Because the comparator omits the checkpoint hashes, any of these three paths will report the replayed/applied output as "matching" even when the committed `state_checkpoint_hash` (Sparse Merkle Tree world-state root at checkpoint boundaries), `hot_state_checkpoint_hash`, or the newer `position_state_checkpoint_hash` diverges from what local re-execution actually computes. `TransactionInfoV1` carries these fields explicitly as part of the authenticated, hashed `TransactionInfo` structure that is itself a leaf in the transaction accumulator and is proof-bound to the ledger (see `types/src/transaction/mod.rs:2440-2461`), so a divergence here is a genuine state-root/proof-context inconsistency, not a cosmetic one. [4](#0-3) 

Distinct from this is the "committer" path (`chunk_executor::update_ledger`, `DoStateCheckpoint`), which builds `known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints` from the incoming `TransactionInfo` and appears to feed them into checkpoint computation for validation there. [5](#0-4) 
This means the actual state-sync commit path (`enqueue_chunk` → `update_ledger` → `DoStateCheckpoint`) may still catch checkpoint-hash mismatches independently. This significantly narrows the exploitable surface of `ensure_match_transaction_info`'s gap to paths that rely on it *alone* as the integrity gate — specifically the standalone re-execution "verify_execution" step in remove-and-apply-chunk backup restore flows, and the `replay_on_archive` auditing tool, both of which are explicitly named in the code's own TODO as broken.

### Impact Explanation
This is a genuine, code-acknowledged proof/state-integrity gap: replay-verification tooling (`replay_on_archive`) and the chunk-executor's verify-before-apply path can both certify a chunk as "verified" / a replay as "successful" even when the locally recomputed world-state Merkle root (or hot-state / trading-native position-state root) diverges from the version bound in the authenticated `TransactionInfo`. This defeats the specific purpose of these tools — detecting state-root divergence during restore/replay/audit — and could mask a genuine state-commitment bug (e.g., a hard-fork-only divergence in checkpoint hash computation) that would otherwise be caught before affecting downstream consumers of `replay_on_archive` results or backup-restore integrity guarantees.

However, the severity is bounded: this gap does not, by itself, corrupt what actually gets committed to durable storage via the mainline state-sync commit path, because `DoStateCheckpoint`'s `known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints` machinery in `update_ledger` appears to independently validate checkpoint hashes before commit. The impact is therefore concentrated in false-negative validation results from replay-verify auditing and from the chunk-executor's `verify_execution` step used in epoch-boundary replay of backup data, rather than in wrong state actually being committed to the canonical ledger by the normal sync path.

### Likelihood Explanation
High likelihood of the condition being reachable: this is not a hypothetical edge case but a documented, static gap in a function that is unconditionally called on every batch of transactions in the affected paths. Any divergence in checkpoint-hash computation (e.g. from a bug in `DoStateCheckpoint`, a non-determinism in hot-state/position-state root computation, or an intentionally malicious archive source feeding `replay_on_archive`) would silently pass this check. The feature flag `COMPUTE_TRADING_NATIVE_STATE_ROOTS` referenced in the comment indicates this is an active, not-yet-fully-wired feature, increasing the chance that the gap is currently live in code paths gated by that flag or default-disabled but soon to be enabled.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the locally computed/known values whenever those fields are populated in the given `TransactionInfo`, consistent with the function's own TODO. This should be done prior to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, and the same validation should be added/audited independently of whether `DoStateCheckpoint`'s separate checkpoint-hash checks in the mainline commit path are believed to cover the same conditions, since `ensure_match_transaction_info` is the sole safety net in the `verify_execution` chunk-replay and `replay_on_archive` code paths.

### Proof of Concept
Not independently exploitable as a standalone PoC without access to a divergent checkpoint-hash-producing scenario (e.g., a bug in hot-state/position-state Merkle computation, or a maliciously crafted archive backup file fed into `replay_on_archive`). The vulnerability is a code-level integrity gap confirmed by static review of `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) and its three call sites; a concrete PoC would require constructing a `TransactionInfo`/`TransactionOutput` pair with matching status/gas/write-set/event hashes but a mismatched `state_checkpoint_hash` and demonstrating that `replay_on_archive`'s `execute_and_verify` (storage/db-tool/src/replay_on_archive.rs:392-405) or `chunk_executor::verify_execution` (execution/executor/src/chunk_executor/mod.rs:692-704) return `Ok` despite the mismatch.
