### Title
Unbounded-Depth JSON Deserialization in Legacy Declare Transaction (`Program`) Causes Stack-Overflow DoS in the Gateway/HTTP Server - (File: crates/starknet_api/src/deprecated_contract_class.rs)

### Summary
The `/gateway/add_transaction` (deprecated-gateway) HTTP endpoint deserializes the raw transaction body directly into `DeprecatedGatewayTransactionV3` via `serde_json::from_str` before any size or structural validation runs. For a `DECLARE` transaction this type embeds `starknet_api::deprecated_contract_class::Program`, whose `attributes`, `builtins`, `compiler_version`, and `data` fields are untyped `serde_json::Value`. `serde_json::Value` deserialization recurses once per nesting level with no depth limit, so a request containing a deeply nested JSON array/object (e.g. `[[[[[...]]]]]`) in one of these fields will recurse until the stack is exhausted — the same bug class as GHSA-h48w-c35p-6m8x/CVE-2020-27196 (eager body parsing of an untrusted payload with no recursion-depth guard).

### Finding Description
The gateway's legacy transaction path in [1](#0-0)  parses the raw HTTP body string with `serde_json::from_str(&tx)` into a `DeprecatedGatewayTransactionV3` before performing any of the `StatelessTransactionValidator` size/structure checks (`validate_class_length`, `validate_sierra_version`, etc., see [2](#0-1) ), which only run *after* successful deserialization.

For legacy (Cairo0) `DECLARE` transactions, the contract class embeds a `Program`: [3](#0-2) 
`attributes`, `builtins`, `compiler_version`, and `data` are typed as bare `serde_json::Value`. Deserializing a `serde_json::Value` from JSON is inherently recursive in `serde_json` — one Rust stack frame is consumed per level of array/object nesting, with no built-in recursion-depth limit. Standard `serde_json` documentation and the referenced upstream CVE both describe exactly this class of bug: a deeply nested but otherwise tiny JSON payload can exhaust the thread stack (`StackOverflowError`/SIGSEGV) during parsing, before the application gets a chance to apply any size limits.

The only guard present at this layer is a coarse byte-size limit on the raw HTTP body (`RequestBodyLimitLayer`/`DefaultBodyLimit`, see [4](#0-3) ), which bounds total payload bytes but does nothing to bound *nesting depth* — a payload like `{"data":` + `[`×N + `]`×N + `}` can be only a few hundred KB while still reaching tens of thousands of nesting levels, well within `max_request_body_size` yet enough to overflow a typical thread stack.

### Impact Explanation
A stack overflow inside the HTTP-server/gateway process handling incoming transactions crashes the process (or at minimum the request-handling thread, which in Rust with `serde_json`'s C-stack recursion typically aborts the whole process since stack overflow is not a catchable panic). If this can be triggered against gateway/HTTP-server instances broadly (not just a specific validator's own submission channel), it is a network-reachable Denial of Service: an unprivileged party who can submit a transaction JSON body can repeatedly crash gateway/http-server processes, preventing the sequencer from accepting new transactions — matching the "network unable to confirm new transactions" impact class.

### Likelihood Explanation
Likelihood is high in terms of ease of construction (a nested-array JSON payload is trivial to generate and requires no protocol/cryptographic knowledge), but the crash requires the payload to actually reach `serde_json::from_str::<DeprecatedGatewayTransactionV3>` before any depth/size validation can block it, and requires the underlying `serde_json` build in use to lack `serde_json`'s optional depth-limiting behavior. This is unverified against the exact `serde_json` version/feature flags pinned in the workspace `Cargo.lock`, which was not available for inspection — recent `serde_json` versions include some depth mitigations in certain code paths (e.g. via `serde_stacker`-style features in some ecosystems), but plain recursive `Value` deserialization in vanilla `serde_json` remains vulnerable to deep nesting without an explicit recursion_limit wrapper, which does not appear to be applied anywhere in this deserialization path.

### Recommendation
- Impose an explicit JSON nesting-depth limit before/while deserializing untrusted transaction bodies, e.g., by wrapping `serde_json::Deserializer` with a stack-safety guard (such as the `serde_stacker` crate) or by pre-scanning depth with a streaming tokenizer and rejecting payloads beyond a configured max depth, applied to both the RPC (`add_rpc_tx`) and deprecated (`add_tx`) endpoints in `crates/apollo_http_server/src/http_server.rs`.
- Replace the bare `serde_json::Value` fields in `Program` (`attributes`, `builtins`, `compiler_version`, `data`) with depth-bounded or schema-constrained deserialization where feasible, since these are the concrete unbounded-recursion sinks.
- Perform cheap structural/size validation (e.g., a fast pre-check on raw bytes for excessive bracket nesting) prior to invoking `serde_json::from_str` on attacker-supplied bodies.

### Proof of Concept
1. Construct a JSON body for the legacy `/gateway/add_transaction` endpoint representing a `DECLARE` V3 transaction whose `contract_class.program.data` (or `.attributes`) field is a deeply nested array, e.g. approximately:
```
{"type":"DECLARE","version":"0x3", ... ,"contract_class":{"program":{"data": [[[[[[ ... ]]]]]], "builtins":[], "attributes":[]}, "abi":[], "entry_points_by_type":{}}, ...}
```
   where the `data` value nests to on the order of 50,000–100,000 levels (`[` repeated N times, then `]` repeated N times) — small enough in byte size to pass `max_request_body_size`.
2. POST this body to `/gateway/add_transaction`.
3. `serde_json::from_str(&tx)` in [5](#0-4)  recursively deserializes the nested `Value`, consuming stack frames proportional to nesting depth, and crashes the handling thread/process before the request ever reaches `StatelessTransactionValidator`.

Note: I was unable to directly execute this PoC or inspect the pinned `serde_json` version/features in `Cargo.lock` to confirm the exact stack-overflow threshold in this build; this should be validated empirically (e.g., via a Devin session with build/execution access) before treating the severity as final.

        debug!("Error while converting deprecated gateway transaction into RPC transaction: {}", e);
    })?;
