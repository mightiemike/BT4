### Title
Division-by-zero in vault `system-repay` when total vault debt is zero bricks repay/liquidation for that asset - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`, mirrored in `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
Each Zest vault contract's `system-repay` computes `calc-principal-ratio-reduction` and `principal-repaid` by dividing by the vault's aggregate `debt` value inside the function's `let` bindings, **before** any `asserts!` guards run. Once all borrowers for a vault asset fully repay (a legitimate, ordinary path), `principal-scaled` — and therefore `total-debt` — becomes exactly `u0`. Any subsequent call into `system-repay` for that asset (from `repay` or from `liquidate`'s `vault-system-repay`) will divide by this zero `debt` value while evaluating the `let` bindings, reverting the transaction regardless of whether the caller, amount, and pause checks would otherwise pass. This mirrors the reported bug class: an aggregate value (`totalShares` in the original report, `total-debt`/`principal-scaled` here) that can legitimately reach zero, after which a downstream, unguarded operation reverts and bricks a code path that depends on it.

`calc-principal-ratio-reduction` and `mul-div-down` both divide by `debt`: [2](#0-1) 

`debt` is `total-debt`, derived from `principal-scaled`: [3](#0-2) 

In Clarity, `let` bindings are evaluated strictly, top-to-bottom, before the function body (which contains the `asserts!` guards) executes. Consequently, if `principal-scaled` (and thus `debt`) is `u0` — which happens whenever every borrower for that vault asset has fully repaid — the division `(mul-div-down amount scaled-principal debt-amount)` inside `calc-principal-ratio-reduction`, and the later `(mul-div-down capped-amount total-borrowed-amount debt)`, both divide by zero. This aborts the transaction with a runtime arithmetic error **before** `check-caller-auth`, `ERR-PAUSED`, or `ERR-AMOUNT-ZERO` are ever evaluated — i.e., the mutation (division) is evaluated before its guard.

This value (`debt == 0`) is the analog of `totalShares == 0` in the original report: a system-wide aggregate that legitimately reaches zero through normal user behavior (all borrowers repay), after which any code path performing a division by that value — which is not protected by a zero-check — reverts unconditionally.

### Impact Explanation
Once a vault's aggregate debt for an asset legitimately reaches zero (last borrower repays), any later attempt to invoke `system-repay` on that vault — whether from a user's `repay` call or from `liquidate`'s `vault-system-repay` step — reverts due to division by zero, regardless of validity of the call. This means:
- A liquidator cannot execute `liquidate` against an unhealthy position that requires `vault-system-repay` on that asset while `debt == 0` transiently holds (e.g., another repay in the same block already zeroed it), causing the liquidation to fail even though the position is legitimately unhealthy.
- Any legitimate repay attempt racing against the debt hitting zero similarly reverts.

This constitutes a temporary freezing of funds/functionality for the affected vault (repay and liquidation are blocked for that asset) until new debt is originated (a fresh borrow makes `principal-scaled > 0` again), matching the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
`principal-scaled` reaching `u0` is not an edge case requiring privileged access — it is the natural end state of a vault asset with no outstanding borrowers (which occurs at genesis before the first borrow, and recurs any time all borrowers repay in full). Any subsequent call attempting to repay/liquidate against that asset while `debt == u0` will trigger the division-by-zero panic. Likelihood is moderate-to-high for low-utilization or newly-listed vault assets, and increases around full-repayment events combined with pending liquidation calls in the same block.

### Recommendation
Add an explicit zero-check for `debt` at the top of `system-repay` (and any other function computing `mul-div-down`/`calc-principal-ratio-reduction` against `debt`), short-circuiting to a no-op or `ERR-AMOUNT-ZERO`-style rejection when `debt` is `u0`, before any division occurs. Ensure this guard is evaluated ahead of (or as part of) the arithmetic, not merely alongside it in the same `let` block, so that a zero-debt state cannot reach the unguarded division at all.

### Proof of Concept
1. A vault asset (e.g., sBTC vault) has exactly one outstanding borrower with `principal-scaled > 0`, so `total-debt > 0`.
2. That borrower fully repays via `repay` → `vault-system-repay`; `system-repay` executes normally (since `debt > 0` at binding-evaluation time), reducing `principal-scaled` to `u0`.
3. In the same block, a second transaction invokes `market.clar`'s `liquidate` against a different, legitimately unhealthy position that also borrowed the same asset kind (or a stale repay retry is submitted for the same asset).
4. `liquidate` calls `vault-system-repay` for that asset with `debt-to-repay > 0`; inside `system-repay`, `debt` is now `total-debt = u0` (per step 2).
5. Evaluating the `let` bindings computes `calc-principal-ratio-reduction capped-amount scaled-principal u0`, which divides by zero — Clarity aborts the transaction before `check-caller-auth`/`asserts!` execute.
6. The liquidation (or repay) transaction reverts even though the underlying position was unhealthy and all inputs were otherwise valid, temporarily freezing repay/liquidation functionality for that vault asset until a new borrow re-populates `principal-scaled`. [4](#0-3) [5](#0-4)
