## Title
Witness vote-rewards are permanently lost when a witness's vote count drops to zero before the reward is folded into the Vi accumulator - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
java-tron's SR (super-representative) reward-sharing mechanism mirrors the reported Wenwin bug class: rewards are accrued into a per-cycle pool keyed to a witness, but the pool's "reward-per-share" accumulator (`Vi`, analogous to Solidity's `rewardPerTokenStored`) is only advanced when the underlying "stake" (total votes for that witness) is non-zero. When the stake is zero at the moment the accumulator would be updated, the reward increment is silently dropped instead of being carried forward, so it can never be attributed to any current or future voter.

### Finding Description
Block/transaction-fee rewards for a witness are accrued via `MortgageService.payReward`, which deducts the brokerage share and stores the voter-share in `DelegationStore` keyed by cycle and witness address: [1](#0-0) 

That raw value is written with `addReward`, independent of whether the witness currently has any votes: [2](#0-1) 

Under the new reward algorithm, once per maintenance cycle, `MaintenanceManager.doMaintenance` folds each witness's accrued reward into the `Vi` accumulator using the witness's **current, live** vote count: [3](#0-2) 

The folding logic is `DelegationStore.accumulateWitnessVi` (mirrored in `RewardViCalService.accumulateWitnessVi`): [4](#0-3) 

If `reward != 0` but `voteCount == 0` at the moment maintenance runs (i.e., all voters have withdrawn their votes from that witness during the cycle even though the witness earned rewards while votes were non-zero), the code takes the "just forward preVi" branch — the reward is **not** folded into `deltaVi` at all. Since `Vi` is exactly the "reward-per-token" accumulator later used to compute every voter's proportional share (`deltaVi = endVi - beginVi`, multiplied by the voter's vote count), a reward increment that is never added to `Vi` can never be claimed by any voter, past or future: [5](#0-4) 

The old reward algorithm has the analogous failure mode: `computeReward` skips any cycle where `totalVote == 0`, discarding that cycle's stored reward with no path to reclaim or redistribute it: [6](#0-5) 

This is the same root cause as the Wenwin `Staking.rewardPerToken()` bug: the reward accumulator update is gated on `totalSupply`/`voteCount != 0`, so rewards that arrive while the "stake" is zero are neither carried forward nor redirected — they are simply orphaned.

### Impact Explanation
The accrued voter-share of a witness's block/transaction-fee reward becomes permanently unattributable once this happens: no voter's `Vi`-based reward calculation will ever include it, and there is no fallback mechanism (no sweep, no treasury redirection) to recover or reallocate it. This is an accounting-correctness defect in a core consensus-reward path (`DelegationStore`/`MortgageService`/`MaintenanceManager`) reachable purely through normal, unprivileged user actions (casting/withdrawing votes via the vote actuator) — no privileged role is required to trigger the condition.

### Likelihood Explanation
The trigger condition — voters withdrawing/redirecting all votes away from a witness within the same cycle in which that witness produced blocks and earned rewards — is a normal, permissionless action available to any TRX holder. Because SR membership/vote snapshots are only refreshed at maintenance boundaries, a witness can keep producing blocks (and accruing `addReward` entries) for a period after its live vote count has dropped to zero, making the zero-vote-at-maintenance-time window realistically reachable, similar to the "unlikely but can happen" characterization in the original report.

### Recommendation
When folding rewards into the `Vi` accumulator in `DelegationStore.accumulateWitnessVi` (and the old-algorithm `computeReward` path in `MortgageService`), do not silently drop rewards accrued while `voteCount == 0`/`totalVote == 0`. Either (1) carry the un-distributable reward forward until votes reappear so it can still be folded into `Vi` at that point, or (2) explicitly redirect/burn it through an accounted mechanism rather than leaving it as an inaccessible entry in `DelegationStore`.

### Proof of Concept
1. Witness `W` is elected into the active SR set with `voteCount > 0`.
2. `W` produces blocks; `MortgageService.payBlockReward`/`payTransactionFeeReward` repeatedly call `payReward`, which deducts brokerage and calls `delegationStore.addReward(cycle, W, value)` [1](#0-0) .
3. Before the next maintenance cycle boundary, all voters who voted for `W` withdraw/redirect their votes (permissionless `VoteWitnessContract`), so `W.getVoteCount()` becomes `0`, while `W` remains in the active set until the next maintenance.
4. `MaintenanceManager.doMaintenance` runs and calls `delegationStore.accumulateWitnessVi(curCycle, W, 0)` since `useNewRewardAlgorithm()` is enabled [3](#0-2) .
5. Inside `accumulateWitnessVi`, `reward = getReward(cycle, W) != 0` but `voteCount == 0`, so the "forward preVi" branch executes and the reward is never added to `Vi` [4](#0-3) .
6. The reward value remains stored under `DelegationStore`'s reward key but is permanently unreachable by any subsequent `withdrawReward`/`queryReward` computation, since those only ever read `Vi` deltas [5](#0-4) .

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
