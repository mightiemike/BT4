### Title
Owner-scoped workflow lookup accepts short/zero-padded workflowOwner values, enabling cross-owner workflow resolution - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`validateWorkflowOwner` delegates to `validateHexInput`, which only enforces a maximum length (`len(input) > expectedLength`) and never checks for an exact length match. `resolveWorkflowID` then calls `normalizeHex(workflowOwner, workflowOwnerLength)`, which left-pads any shorter hex string with zeros to reach the full 20-byte (42-char) address format before using it as a lookup key in `GetWorkflowID`.

### Finding Description
The call chain is: `validateTriggerParams` → `validateWorkflowFields` (`http_trigger_handler.go:238-242`) → `validateWorkflowOwner` (`http_trigger_handler.go:285-292`) → `validateHexInput` (`http_trigger_handler.go:258-274`). `validateHexInput` only checks `len(input) > expectedLength` (an upper bound) and validates hex/lowercase formatting — it never asserts `len(input) == expectedLength`. This means a short string like `"0xab"` or even `"0x0"` passes validation as a "workflowOwner" as long as it decodes as valid lowercase hex and is not longer than 42 characters.

Once validated, `resolveWorkflowID` (`http_trigger_handler.go:333-357`) calls `normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)` (`http_trigger_handler.go:324-331`), which strips any `0x` prefix and left-pads the remaining hex digits with `"0"` characters until it matches the full 40 hex-character (20-byte) address length, then re-adds `0x`. The padded, normalized value is then used directly as the exact-match owner key passed into `h.workflowMetadataHandler.GetWorkflowID(workflowOwner, workflowName, workflowTag)` (`http_trigger_handler.go:345-351`) to resolve a `workflowID` for the (owner, name, tag) tuple.

Because the padding is purely mechanical zero-extension and `validateHexInput` never enforces exact length, any attacker-supplied short suffix that happens to match the low-order hex digits of a legitimate, already-registered owner address whose high-order bytes are all zero will normalize to that victim's full address. The attacker does not need to guess or know a private key — they only need to know (or brute-force, since addresses with leading zero bytes are a public, observable on-chain fact once registered) that a victim's registered `workflowOwner` address has one or more leading zero bytes, and then submit the shorter suffix. `resolveWorkflowID` will then silently resolve `GetWorkflowID` against the victim's real owner scope, letting the attacker trigger an owner-scoped workflow lookup they never explicitly, fully specified.

This is a genuine length-validation gap: an owner identity field used purely for scoped identity/authorization lookup is validated with a "maximum length" check instead of an "exact length" check, allowing padding-induced identity confusion, exactly as the question describes.

### Impact Explanation
Impact is scoped to unauthorized owner-scoped workflow ID resolution: an unprivileged caller who correctly determines/knows that a victim-owned workflow's registered address has leading zero bytes can craft a short-form `workflowOwner` value that zero-pads into the victim's exact address, causing `GetWorkflowID` to return a workflowID belonging to that victim rather than one the attacker explicitly specified. Downstream, this feeds into `authorizeRequest` (`h.workflowMetadataHandler.Authorize`), so exploitation is bounded by whatever additional authorization/signature checks exist in `Authorize`; however, the core owner-identity lookup itself is confused, which is a distinct identity/authorization-boundary bug matching Chainlink's "unauthorized workflow execution / cross-tenant data exposure" bounty category for gateway/capability handlers.

### Likelihood Explanation
Exploitability requires that a real registered owner address in the workflow registry have enough leading zero bytes to be practically matched by a short attacker-supplied suffix — for an address to have `k` leading zero bytes occurs with probability `1/256^k`, so for k=1 (2 hex zero chars) this is roughly 1/256 of all addresses, which is plausible to occur across many registered owners at scale, and can be checked by an attacker via public/observable registry data (this is not a secret). No privileged access, signature forgery, or social engineering is needed — only a crafted JSON-RPC gateway request with a short `workflowOwner` string. The bug is deterministic and repeatable once such a victim address exists.

### Recommendation
Change `validateWorkflowOwner` (and `validateWorkflowID`, which has the identical flaw) to require exact length rather than a maximum:
```go
if len(input) != expectedLength {
    return fmt.Errorf("hex string must be exactly %d characters, got %d", expectedLength, len(input))
}
```
in `validateHexInput` (`http_trigger_handler.go:258-274`), removing the padding/normalization step (`normalizeHex`) as a source of identity confusion, or at minimum rejecting any input whose length does not already equal `expectedLength` before it ever reaches `normalizeHex`.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
	workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
	workflowName := "0x" + hex.EncodeToString([]byte(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)))
	workflowID, found := h.workflowMetadataHandler.GetWorkflowID(
		workflowOwner,
		workflowName,
		triggerReq.Params.Workflow.WorkflowTag,
	)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "Workflow not found. Provide either a valid 'workflowID' or a valid combination of 'workflowOwner', 'workflowName', and 'workflowTag'", callback)
		return "", errors.New("workflow not found")
	}
	return workflowID, nil
}
