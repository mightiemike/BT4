I found a concrete parameter-pollution analog in the OAuth callback path, which is functionally the same "missing duplicate/uniqueness check" root cause as the `addReceiver()` bug (an entity that should be treated as singular is instead allowed to occur multiple times, and different code paths disagree about which occurrence "wins").

### Title
OAuth callback `shop` query-parameter pollution allows HMAC bypass via mismatched dedup semantics between `shop` extraction and HMAC validation - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
`shopify-api`'s `admin`-signator HMAC validation path (used by the OAuth `callback()` handler) has no duplicate-parameter check, unlike the `appProxy` signator which was hardened to reject repeated `shop`/`hmac`/`signature`/`timestamp` params. In the OAuth callback, `shop` is read with `URLSearchParams.get('shop')` (which returns the **first** occurrence), while the object passed into HMAC validation is built with `Object.fromEntries(query.entries())`, which silently keeps the **last** occurrence of a duplicate key. If an attacker can get two `shop` values into the callback URL, the value validated by HMAC and the value used to create/target the session are drawn from different array positions.

This is the exact analog of the `_addReceiver()` bug: a value that the system implicitly assumes is unique (a fee receiver / a `shop` param) is allowed to appear more than once, and different parts of the code (allocTotal accounting / `shop` extraction vs. HMAC validation) independently and inconsistently consume that list, producing an outcome nobody explicitly authorized. The CHANGELOG confirms the maintainers identified and fixed this exact class of bug for the `appProxy` signator only: [4](#0-3) 
but did **not** extend the same duplicate-parameter rejection to the `admin` signator used by `oauth.callback()`.

### Impact Explanation
If an attacker can cause the OAuth callback URL to contain two `shop=` query parameters (e.g., by getting a merchant to click a crafted link, or via an open redirect/param-injection surface elsewhere that forwards to `/auth/callback`), the code that decides *whose* session gets created (`shop = query.get('shop')`, first value) can diverge from the value that is HMAC-validated (`authQuery.shop`, last value from `Object.fromEntries`). Since `validQuery()` only checks that `authQuery.hmac` matches a locally-computed HMAC over `authQuery` (which used the *last* `shop`) and that `state` matches the cookie, an attacker who legitimately owns a shop could construct a URL where the trailing `shop` (attacker-owned, HMAC-valid) authenticates the request while the leading `shop` (a victim's domain) is the one actually used for `sanitizeShop`/session creation later via `query.get('shop')` calls at lines 147 and 194. This is a session/account-binding confusion in the "OAuth CSRF/token theft, cross-tenant access" category called out as in-scope.

### Likelihood Explanation
Exploitation requires the attacker to control or inject a second `shop` query parameter into the OAuth callback URL that the victim's browser sends to the app (typically via a crafted install/callback link they get the target to click, since `state`/HMAC still bind to a real, valid installation initiated by the attacker for their own shop). This is a real-world reachable path for an anonymous single-merchant attacker crafting the callback link, but it is speculative until it is proven whether Shopify's actual OAuth redirect flow, `redirect_uri` echoing, or any embedded surface actually allows an attacker to inject an extra `shop=` parameter that survives to `callback()` unmodified. I could not verify from the available code whether any additional query-parsing/normalization occurs upstream (e.g., in framework adapters like `shopify-app-express`/`shopify-app-remix`) that might strip duplicate keys before `oauth.callback()` is invoked, so likelihood should be treated as **unconfirmed/moderate** pending further validation.

### Recommendation
- **Short term:** Document that `admin`-signator HMAC validation (OAuth callback, install flow) does not currently reject duplicate `shop`/`hmac`/`state`/`code`/`timestamp` query parameters, and audit whether `Object.fromEntries(query.entries())` vs `URLSearchParams.get()` usage can diverge in practice.
- **Long term:** Extend the same repeated-security-parameter rejection already implemented for the `appProxy` signator (`APP_PROXY_SINGLE_VALUE_PARAMS` check in `normalizeQuery`) to the `admin` signator, and make `oauth.callback()` derive `shop` from the same normalized/deduplicated query object used for HMAC validation rather than from a separately-parsed `URLSearchParams.get('shop')` call, so both code paths are guaranteed to agree on a single `shop` value.

### Proof of Concept
1. An attacker registers/owns `attacker-shop.myshopify.com` and begins a legitimate OAuth flow, obtaining a valid signed `state` cookie for the callback path.
2. The attacker crafts the callback URL as:
   `.../auth/callback?shop=victim-shop.myshopify.com&shop=attacker-shop.myshopify.com&state=<valid-state>&code=<code>&timestamp=<ts>&hmac=<hmac-computed-over-last-shop-value>`
3. Gets the victim (or their own browser session holding the victim's state cookie context, depending on delivery vector) to load this URL against the app's callback endpoint.
4. `shop = query.get('shop')` (line 147) evaluates to `victim-shop.myshopify.com` (first occurrence) and is used for logging/session targeting at multiple points, while `authQuery.shop` (via `Object.fromEntries`, line 178) evaluates to `attacker-shop.myshopify.com` (last occurrence) and is what is actually HMAC-validated — since the attacker computed a valid HMAC for their own shop value, `validQuery()` returns `true` despite the "acting" shop being different in other parts of the code.
5. This demonstrates the divergence; full weaponization into a cross-tenant session bind would require confirming which of the two `shop` references (`query.get('shop')` at line 147/194, used for `sanitizeShop` and the actual access-token exchange target) versus `authQuery.shop` actually drives the created session — this needs runtime verification, which was not possible from static code review alone.
