## Title
Uncaught panic in Gateway's `SyncStateReader` when a declared class is missing from the Class Manager - Denial of Service of transaction validation - (File: `crates/apollo_gateway/src/sync_state_reader.rs`)

### Summary
The external report describes a DoS pattern: code assumes an external/looked-up entity always satisfies an invariant (implements a required interface), and when that assumption is violated the call unconditionally reverts/panics with no way to recover, bricking the calling flow for all future invocations. The closest reachable analog in this sequencer is `SyncStateReader::get_contract_class_from_client` in `crates/apollo_gateway/src/sync_state_reader.rs`, which is invoked while validating/executing every incoming transaction in the Gateway component.

### Finding Description
`get_contract_class_from_client` first confirms via the state-sync client that a class hash `is_class_declared_at` a given block, and then fetches the executable class from the class manager client: [1](#0-0) 

If the class manager does not have the class (e.g. the local class-manager storage has not yet caught up with state sync, has a data inconsistency, or was restarted with a different/partial storage than the state-sync layer), the code does not return an error — it panics:
```
.unwrap_or_else(|| {
    panic!(
        "Class with hash {class_hash:?} doesn't appear in class manager even though \
         it was declared"
    )
});
```
This is analogous to the reported bug class: the code assumes an invariant about a dependency ("if declared on-chain, the class manager must have it") holds unconditionally, and instead of gracefully surfacing an error to reject only the offending transaction, it aborts the whole call path with a hard panic. Once a class hash is declared on L2 it is permanent (irreversible, exactly like the un-removable `DistributionConfig` entries in the report) — any node whose class-manager storage is out of sync for that specific class hash will panic on every transaction that references it, for as long as the mismatch persists, with no way to "remove" the offending class from state.

A test in the repo confirms this is by-design panic behavior, not accidental: [2](#0-1) 

### Impact Explanation
If reached, every subsequent transaction that touches the affected class hash (e.g. calls or is sent by an account using that class) causes an unhandled `panic!` inside the Gateway's transaction-validation code path (`get_contract_class_from_client` is used by `SyncStateReader`, which implements the `StateReader` trait consumed by blockifier's class-hash resolution during validation of every submitted transaction). Depending on how the panic propagates (whether the surrounding tokio task/thread catches the unwind or the process is configured to abort on panic), this can manifest as: (a) repeated rejection/failure of the specific request thread validating that transaction, effectively creating an easy vector to keep failing that request path, or (b) in the worst case, a crash of the validating component, halting the node's ability to admit new transactions referencing that class hash — a network liveness/availability impact matching "a network unable to confirm new transactions" for the affected class. This is a Medium-severity DoS analog: it is narrower in blast radius than the original Solidity finding (impacts transactions tied to one class hash, not the whole node), but it is unconditionally reachable by any unprivileged transaction sender who submits a transaction touching a class hash for which the class manager is out of sync with state sync, and it cannot be fixed by simply "removing" the declared class since class declarations are permanent on-chain state.

### Likelihood Explanation
The trigger condition (a class marked "declared" in state sync but absent from the class manager's storage) is not purely theoretical: it is exactly the kind of transient inconsistency that can arise from node restarts, partial catch-up, storage corruption, or component desynchronization between the state-sync and class-manager subsystems — subsystems that are explicitly decoupled and communicate asynchronously per the architecture (see the state-sync/class-manager streaming flow, where "Class Manager cannot compile Sierra→CASM" for some class variants and classes are streamed with a lag). Any unprivileged sender who submits (or resubmits) a transaction invoking such a class hash while the inconsistency exists will hit this exact code path.

### Recommendation
Replace the `panic!` with a typed, propagated `StateError` (mirroring the existing `StateError::UndeclaredClassHash` handling already used a few lines above for the "not declared" case) so that a single problematic/inconsistent class hash results in rejection of that specific transaction rather than an unrecoverable panic in the validation path. Additionally, consider adding retry/backoff or explicit reconciliation logic between the state-sync "declared" marker and the class-manager's local cache so that a lagging class manager does not manifest as a hard failure for user-submitted transactions.

2. An unprivileged user submits any transaction that resolves class hash `C` (e.g., an `invoke`/`declare`/`deploy_account` referencing a contract or account with class hash `C`) to the Gateway.
3. `SyncStateReader::get_contract_class_from_client` is invoked during transaction validation: [1](#0-0) 
4. Because `class_manager_client.get_executable(class_hash)` returns `None`, the `unwrap_or_else` branch executes `panic!(...)`, as reproduced deterministically by the existing unit test: [2](#0-1) 
5. Every subsequent transaction referencing class hash `C` repeats this panic until the class-manager/state-sync inconsistency is manually resolved, since the class declaration itself cannot be reverted from chain state.

A Devin session with full repository access would be needed to trace the exact call stack and Cargo panic profile to pin down whether the blast radius is "single request failure" (Medium) or "process crash / node-wide DoS" (High).

```rust
    fn get_contract_class_from_client(&self, class_hash: ClassHash) -> StateResult<ContractClass> {
        let is_class_declared = self
            .runtime
            .block_on(self.state_sync_client.is_class_declared_at(self.block_number, class_hash))
            .map_err(|e| StateError::StateReadError(e.to_string()))?;

        if !is_class_declared {
            return Err(StateError::UndeclaredClassHash(class_hash));
        }

        let contract_class = self
            .runtime
            .block_on(self.class_manager_client.get_executable(class_hash))
            .map_err(|e| StateError::StateReadError(e.to_string()))?
            .unwrap_or_else(|| {
                panic!(
                    "Class with hash {class_hash:?} doesn't appear in class manager even though \
                     it was declared"
                )
            });

        Ok(contract_class)
    }
```
