### Title
Malicious relayer can force meta-transaction failure and burn the user's nonce without triggering ban detection due to gas check omitting callback/dispatch overhead - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The NEAR Wallet Contract's meta-transaction relay path validates that a relayer attached "enough" gas using a simplified formula that only accounts for the user-requested `gas_limit`, not the additional static gas required for the multi-step promise/callback chain that actually executes the action. A malicious relayer holding a `rlp_execute`-scoped access key can pick an attached-gas value that passes this check yet is still insufficient for the full callback chain, causing the action to fail deep in execution (a generic `PromiseResult::Failed`) rather than through the `RelayerError` path that triggers ban/key-revocation. Because the nonce is incremented optimistically right after successful parsing—before the actual promise chain executes—this failure mode consumes the user's nonce and does not revoke the faulty relayer's key, unlike every other relayer-misbehavior path in this contract.

### Finding Description
`validate_tx_relayer_data` only checks that the caller has attached at least `gas_limit * GAS_MULTIPLIER` gas: [1](#0-0) 

This "requested gas" corresponds only to the EVM-emulated `gas_limit` field of the signed Ethereum transaction, converted via `GAS_MULTIPLIER`: [2](#0-1) 

However, the actual execution of the action requires substantially more gas than just the action's own cost: the contract schedules chained callbacks with fixed static gas budgets (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, plus lookup/storage costs), on top of `action.gas()`: [3](#0-2) [4](#0-3) [5](#0-4) 

None of this callback overhead is included in the `InsufficientGas` check performed in `validate_tx_relayer_data`. A relayer can therefore attach `prepaid_gas` that is barely above `gas_limit * GAS_MULTIPLIER` (satisfying the check) but too small to cover the full function-call chain, causing the runtime to exhaust gas mid-chain. This failure surfaces only as `PromiseResult::Failed` in `rlp_execute_callback`, which is treated as an ordinary failed cross-contract call, not a relayer fault: [6](#0-5) 

Crucially, for the common (non-ERC20/non-address-check) transaction kinds, the nonce is incremented immediately once parsing/validation succeeds—*before* the actual promise chain that performs the action is even created: [7](#0-6) 

By contrast, every other relayer-misbehavior path (`InvalidNonce`, `InvalidBase64`, `TxParsing`, `InvalidSender`, `InvalidTarget`, `InvalidChainId`, `InsufficientGas`) results in the nonce *not* being incremented and the relayer's access key being revoked via `create_ban_relayer_promise`: [8](#0-7) [9](#0-8) 

The gas-exhaustion-in-callback failure mode bypasses this ban logic entirely because it does not surface as `Error::Relayer(...)`; it is a runtime-level gas failure inside an already-dispatched promise. This is the direct analog of the Ambire `tryCatchLimit` issue: a malicious relayer can control the attached gas to force execution to fail in a way the surrounding logic cannot distinguish from an honest/expected failure, defeating the fault-detection/ban mechanism that exists specifically to prevent this class of griefing.

### Impact Explanation
This lets an untrusted, registered relayer (holding only a limited `rlp_execute` function-call access key) repeatedly grief a wallet owner: force the user's intended action to fail while advancing (burning) the nonce, all without being detected as faulty and without having its access key revoked. Since the Wallet Contract's whole security model for relayers relies on ban-on-misbehavior to bound the damage a malicious relayer can do (as explicitly noted in comments in `inner_rlp_execute`), this gap allows unlimited, repeated denial-of-service against the user's meta-transactions from a relayer that should have been banned after the first failed/malicious attempt.

### Likelihood Explanation
Exploitation requires the attacker to already be a registered relayer with a function-call access key scoped to `rlp_execute`—i.e., someone the wallet owner has authorized to relay transactions. Given that assumption, the attacker fully controls the `prepaid_gas` attached to their own top-level transaction call and can trivially compute a value that satisfies the simplistic `gas_limit * GAS_MULTIPLIER` check while still being insufficient once the fixed callback overhead (`ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `REGISTRAR_LOOKUP_GAS`, etc.) is subtracted, especially for the ERC-20/emulation code paths that add multiple extra hops.

### Recommendation
Include all fixed downstream callback/lookup gas costs (address registrar lookup, storage-balance checks, storage deposit, and the final `rlp_execute_callback`) in the gas sufficiency check performed in `validate_tx_relayer_data`, rather than only comparing against `gas_limit * GAS_MULTIPLIER`. Alternatively, perform an explicit, dedicated gas check immediately before scheduling each multi-hop promise chain (mirroring the exact static gas that will be attached), and treat any resulting insufficiency as a `RelayerError` (banning the relayer) rather than allowing it to degrade into a generic `PromiseResult::Failed`.

### Proof of Concept
1. Wallet owner registers a relayer with a `rlp_execute`-only function-call access key (as in `register_relayer`/`test_register_relayer`).
2. Owner signs an Ethereum-emulated transaction (e.g., an ERC-20 transfer or a base-token transfer to an unregistered eth-implicit address) whose EVM `gas_limit` is `G`.
3. Malicious relayer calls `rlp_execute` attaching `prepaid_gas` slightly above `G * GAS_MULTIPLIER` (satisfying the check in `validate_tx_relayer_data`, lines 361-365 of `internal.rs`) but below what is actually needed once `ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`REGISTRAR_LOOKUP_GAS` overhead is added (`lib.rs` lines 34-41, 417-457).
4. Validation passes; nonce is incremented (`lib.rs` lines 348-365); the promise chain is scheduled and later runs out of gas mid-chain.
5. `rlp_execute_callback` observes `PromiseResult::Failed` (lib.rs lines 296-311) and reports a generic failure — the relayer's key is never revoked, and the user's nonce has already advanced, so the originally intended action is now unrecoverable under that nonce.

/// Errors which should never happen if the relayer is honest.
/// If these errors happen then we should ban the relayer (revoke their access key).
/// An external caller (as opposed to a relayer with a Function Call access key) may
/// also trigger these errors by passing bad arguments, but this is not an issue
/// (there is no ban list for external callers) because they are paying the gas fees
/// for their own mistakes.
#[derive(Debug, PartialEq, Eq, Clone)]
pub enum RelayerError {
    /// Relayers should always check the nonce before sending
    InvalidNonce,
    /// Relayers should always encode the transaction correctly
    InvalidBase64,
    /// Relayers should always send valid transactions
    TxParsing(aurora_engine_transactions::Error),
    /// Relayers should always send correctly signed transactions
    InvalidSender,
    /// Relayers should always give the correct target account
    InvalidTarget,
    /// Relayers should always check the transaction is signed with the correct chain id.
    InvalidChainId,
    /// Relayers should always attach at least as much gas as the user requested.
    InsufficientGas,
}
