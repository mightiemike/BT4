### Title
Cairo Native syscall handler reachable `assert!` panic causes sequencer process termination on malicious transaction - ([File: crates/blockifier/src/execution/native/syscall_handler.rs])

### Summary
The ClamAV CVE (CVE-2024-20380) stems from a C-to-Rust FFI boundary issue where malformed, attacker-supplied input causes the scanning process to terminate (DoS). The sequencer has an analogous FFI boundary: Cairo Native compiles a Sierra contract to native machine code (via `cairo-native`/LLVM) that is then executed **in-process** and calls back into the Rust `NativeSyscallHandler` through the `StarknetSyscallHandler` FFI trait. Inside that handler, `handle_error` contains a reachable `assert!` that is not designed to tolerate all attacker-controlled call sequences, and there is no `catch_unwind` isolating this in-process native execution from the rest of the sequencer.

### Finding Description
`NativeSyscallHandler::handle_error` enforces the invariant that `unrecoverable_error` can be set at most once per call frame: [1](#0-0) 

This function is invoked from `execute_inner_call` whenever an inner `call_contract`/`library_call`/`deploy` syscall fails with a non-revert (`SelfOrRevert::Original`) error: [2](#0-1) 

The comment above `handle_error` acknowledges the fragility of this invariant ("if there is an unrecoverable error at call `n` it will create a `NativeExecutionError`... creating multiple wraps around the same error"), and the fix is only a best-effort `unwrap_native_error` helper — the `assert!` remains a hard failure path that a contract author does not control but a transaction sender can indirectly trigger by structuring nested calls (deploy/library_call/call_contract chains) that produce more than one unrecoverable (non-revert) error against the same `NativeSyscallHandler` instance before `pre_execute_syscall`'s early-return guard takes effect: [3](#0-2) 

Crucially, native contract execution runs synchronously in the same process as the rest of block production/validation, with the native-compiled binary calling directly into this Rust code across the FFI boundary in `entry_point_execution::execute_entry_point_call`: [4](#0-3) 

Unlike the Sierra→CASM and Sierra→Native *compilation* steps, which are deliberately isolated in a resource-limited subprocess specifically to contain crashes originating from untrusted input: [5](#0-4) [6](#0-5) 

...the *execution* of already-compiled native code has no such isolation. The sequential execution path merely pre-allocates a bigger stack in a scoped thread and joins it with `.expect(...)`, which will itself panic (and by default terminate the process) if the inner thread panicked: [7](#0-6) 

The concurrent worker-pool path is explicit that any unhandled panic during transaction execution is expected to potentially `std::process::abort()` the whole sequencer: [8](#0-7) 

### Impact Explanation
If a submitted transaction reaches Cairo Native execution and triggers the `assert!` in `handle_error`, the assertion panics inside the in-process, FFI-invoked native execution path. This is not caught by any `catch_unwind` at this layer, so it unwinds through `execute_entry_point_call` → block execution → the sequential/concurrent executor, ultimately aborting or crashing the executing sequencer process (batcher/gateway) — a network-wide denial-of-service if the same crafted transaction is broadcast and re-executed by all honest nodes running Cairo Native, exactly analogous to how CVE-2024-20380 let a crafted file crash the ClamAV scanning process via a C/Rust FFI defect.

### Likelihood Explanation
Medium: reaching Cairo Native execution requires deploying/declaring a Cairo 1 class and invoking it in Native mode (only active when `CairoNativeMode` is not `Off`, e.g., `WaitOnCompilation`/`LazyCompilation`), and requires crafting a call structure (nested `library_call`/`call_contract`/`deploy`) that produces two non-revert unrecoverable errors against the same `NativeSyscallHandler` frame before the `pre_execute_syscall` gate short-circuits further syscalls. The code's own comment acknowledges multiple unrecoverable-error wraps can occur across nested calls, indicating the invariant is not trivially guaranteed to hold, but exact triggering requires more precise call sequencing that could not be fully confirmed from static review alone.

### Recommendation
- Replace the `assert!` in `NativeSyscallHandler::handle_error` with a graceful, catchable error path (e.g., keep the first unrecoverable error, log and ignore subsequent ones) rather than panicking on an attacker-influenced invariant.
- Wrap in-process Cairo Native execution (`AotContractExecutor::run` and everything it calls back into) with `std::panic::catch_unwind`, converting any panic into an `EntryPointExecutionError`/transaction revert instead of letting it propagate and potentially crash the process, mirroring the isolation already applied to the Sierra→CASM/Native compilation subprocesses.
- Add fuzz/property tests that construct adversarial nested `call_contract`/`library_call`/`deploy` sequences under Cairo Native specifically targeting `handle_error`'s invariant.

### Proof of Concept
Not independently reproduced end-to-end within this analysis; conceptually, an attacker would declare and deploy a Cairo 1 contract designed to make sequential nested calls (e.g., `library_call` then `deploy` or `call_contract`) inside a single entry point such that two of them each fail with a non-revert `SyscallExecutionError` on the *same* `NativeSyscallHandler` instance (same call frame) before any subsequent syscall's `pre_execute_syscall` check can short-circuit — triggering the `assert!` in `handle_error` at crates/blockifier/src/execution/native/syscall_handler.rs:158-161 during real (non-`WaitOnCompilation`-test) Cairo Native execution.

    /// Apply the resource limits to a given command object. This moves the [`ResourceLimits`]
    /// struct into a closure that is held by the given command. The closure is executed in the
    /// child process spawned by the command, right before it invokes the `exec` system call.
    pub fn apply(self, command: &mut Command) -> &mut Command {
        if self.cpu_time.is_none() && self.file_size.is_none() && self.memory_size.is_none() {
            return command;
        }
        unsafe {
            // The `pre_exec` method runs a given closure after the parent process has been forked
            // but before the child process calls `exec`.
            //
            // This closure runs in the child process after a `fork`, which primarily means that any
            // modifications made to memory on behalf of this closure will **not** be visible to the
            // parent process. This environment is often very constrained. Normal operations--such
            // as using `malloc`, accessing environment variables through [`std::env`] or acquiring
            // a mutex--are not guaranteed to work, because after `fork`, only one thread exists in
            // the child process, while there may be multiple threads in the parent process.
            //
            // This closure is considered safe for the following reasons:
            // 1. The [`ResourceLimits`] struct is fully constructed and moved into the closure.
            // 2. No heap allocations occur in the `set` method.
            // 3. `setrlimit` is an async-signal-safe system call, which means it is safe to invoke
            //   after `fork`. This is established in the POSIX `fork` specification:
            //   > ... the child process may only execute async-signal-safe operations until such
            //    time as one of the `exec` functions is called.
            //   (See <https://pubs.opengroup.org/onlinepubs/9699919799/functions/fork.html>)
            command.pre_exec(move || self.set())
        }
    }

        &mut self,
        txs: &[Transaction],
        execution_deadline: Option<Instant>,
    ) -> Vec<TransactionExecutorResult<TransactionExecutionOutput>> {
        #[cfg(not(feature = "cairo_native"))]
        return self.execute_txs_sequentially_inner(txs, execution_deadline);
        #[cfg(feature = "cairo_native")]
        {
            // TODO(meshi): find a way to access the contract class manager config from transaction
            // executor.
            let txs = txs.to_vec();
            std::thread::scope(|s| {
                std::thread::Builder::new()
                    // when running Cairo natively, the real stack is used and could get overflowed
                    // (unlike the VM where the stack is simulated in the heap as a memory segment).
                    //
                    // We pre-allocate the stack here, and not during Native execution (not trivial), so it
                    // needs to be big enough ahead.
                    // However, making it very big is wasteful (especially with multi-threading).
                    // So, the stack size should support calls with a reasonable gas limit, for extremely deep
                    // recursions to reach out-of-gas before hitting the bottom of the recursion.
                    //
                    // The gas upper bound is MAX_POSSIBLE_SIERRA_GAS, and sequencers must not raise it without
                    // adjusting the stack size.
                    .stack_size(self.config.stack_size)
                    .spawn_scoped(s, || self.execute_txs_sequentially_inner(&txs, execution_deadline))
                    .expect("Failed to spawn thread")
                    .join()
                    .expect("Failed to join thread.")
            })
        }
    }

    /// Runs a single worker executor.
    fn _run_executor(&self, worker_executor: &WorkerExecutor<S>) {
        if self.a_thread_panicked.load(Ordering::Acquire) {
            panic!("Another thread panicked. Aborting.");
        }

        // Making sure that the program will abort if a panic occurred while halting
        // the scheduler.
        let abort_guard = AbortIfPanic;
        // If a panic is not handled or the handling logic itself panics, then we
        // abort the program.
        let res = panic::catch_unwind(panic::AssertUnwindSafe(|| {
            worker_executor.run();
        }));
        if let Err(err) = res {
            // First, set the panic flag. This must be done before halting the scheduler.
            self.a_thread_panicked.store(true, Ordering::Release);

            // If the program panics here, the abort guard will exit the program.
            // In this case, no panic message will be logged. Add the cargo flag
            // --nocapture to log the panic message.

            worker_executor.scheduler.halt();
            abort_guard.release();
            panic::resume_unwind(err);
        }

        abort_guard.release();
    }
