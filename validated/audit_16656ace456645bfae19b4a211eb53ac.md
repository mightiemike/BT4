## Title
Unbounded growth of `DelegatedResourceAccountIndex` to/from-account lists causes O(n) linear scans on every delegate/unfreeze operation, enabling CPU-exhaustion DoS with fixed fee cost - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`, `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
The external report describes a bug class where a user-controlled list is grown without bound and later fully iterated by another (unprivileged) action, causing disproportionate/failing computation relative to the fixed fee charged. An analogous, reachable pattern exists in java-tron's legacy resource-delegation bookkeeping: `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList`, which any account can grow arbitrarily large via ordinary `FreezeBalanceContract` (delegate) broadcast transactions, with no cap on the number of distinct receivers, and which is later scanned/rewritten with `List.contains()` / `List.remove()` (both O(n)) on every subsequent freeze/unfreeze call touching that account, while the transaction's bandwidth fee remains constant.

### Finding Description
When `supportAllowDelegateOptimization()` is disabled (the pre-optimization delegation model, still supported in code), `FreezeBalanceActuator.delegateResource()` maintains per-account lists of delegation partners: [1](#0-0) 

Each call with a new, distinct `receiverAddress` appends an entry via `addToAccount`/`addFromAccount` after an O(n) `contains()` check, with no upper bound on list size anywhere in `validate()` or `DelegatedResourceAccountIndexCapsule`: [2](#0-1) 

Later, `UnfreezeBalanceActuator` reads the *entire* list into an `ArrayList`, and performs `remove(Object)` — a full linear scan to find and delete a single entry: [3](#0-2) 

This mirrors the report's root cause precisely: an actor-controlled list (`cancellation` in the report ↔ `toAccountsList`/`fromAccountsList` here) is set/grown by one type of transaction (`setlistforlongtermrental` ↔ `FreezeBalanceContract` with delegation), and a second, differently-purposed transaction (`cancelreservation...` ↔ `UnfreezeBalanceContract`) is forced to iterate the whole list, with cost scaling with list length while the transaction fee/resource cost charged does not scale accordingly.

Unlike TVM opcodes, these actuators are not charged per-iteration energy; the "fee" is the fixed transfer/bandwidth fee returned by `calcFee()`. Consequently there is no gas-based cap on the work performed — the only cost to the block-producing/validating node is real CPU time and memory, independent of the fixed fee paid, which is the direct analog of the "out-of-gas"/disproportionate-cost class described in the report (here manifesting as unbounded per-transaction processing time rather than an EVM-style OOG revert).

### Impact Explanation
An attacker fully controls an account and can issue many `FreezeBalanceContract` transactions delegating tiny amounts of frozen balance to many distinct, attacker-controlled receiver addresses, inflating their own `DelegatedResourceAccountIndexCapsule.toAccountsList` (and the corresponding `fromAccountsList` on each receiver) to a very large size. Subsequently:
- Any `UnfreezeBalanceContract` (delegated) call from that account triggers an O(n) `contains`/`remove` scan over the bloated list during transaction execution/block processing, increasing per-transaction and per-block processing time for every full node validating the chain.
- The same lists are also fully returned by `getDelegatedResourceAccountIndex` gRPC/HTTP endpoints, so unbounded list growth can also be leveraged as a response-size/serialization amplification vector against RPC/HTTP API consumers.

This is a node-level performance-degradation / DoS vector reachable purely from ordinary broadcast transactions, requiring no privileged role — it degrades block processing and API responsiveness rather than corrupting consensus state or funds.

### Likelihood Explanation
Moderate. Exploitation requires the attacker to fund and broadcast a large number of low-value `FreezeBalanceContract` (delegate) transactions to accumulate a large list, and requires the legacy (`!supportAllowDelegateOptimization()`) delegation model to still be in effect. Newer chains have migrated to the optimized `DelegatedResourceAccountIndexStore` model (`convert`/`delegate`/`unDelegate` keyed store, avoiding the monolithic list) which is not affected by this scan pattern; the vulnerable path only remains reachable on deployments/historical state where the optimization flag is not yet enabled. The economic cost to the attacker (fee per delegation transaction) may make growing a list large enough to matter costly relative to the achieved disruption, which limits, but does not eliminate, likelihood.

### Recommendation
- Enforce (and default-enable) `supportAllowDelegateOptimization()` so delegation bookkeeping always uses the keyed `DelegatedResourceAccountIndexStore` (`FROM_PREFIX`/`TO_PREFIX` per-pair keys) instead of a single growing list per account.
- For the legacy path, cap the number of entries permitted in `toAccountsList`/`fromAccountsList` in `FreezeBalanceActuator.validate()`, rejecting new delegations once a reasonable maximum is reached.
- Replace `List.contains()`/`List.remove()` linear scans with a `Set`-backed or indexed structure, or migrate remaining callers fully to the V2 keyed-store APIs (`getV2Index`, `delegateV2`, `unDelegateV2`) which avoid full-list materialization.
- Cap the size of lists returned by `getDelegatedResourceAccountIndex` RPC/HTTP endpoints, or paginate results, to prevent response-size amplification.

### Proof of Concept
1. Deploy/attach to a network where `supportAllowDelegateOptimization()` is `0` (legacy delegation model active).
2. From attacker-controlled account `A`, broadcast N `FreezeBalanceContract` transactions, each specifying a distinct freshly-generated `receiverAddress` and a minimal `frozenBalance`/`duration`, invoking `FreezeBalanceActuator.delegateResource()` (`actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:319-345`). This grows `A`'s `DelegatedResourceAccountIndexCapsule.toAccountsList` to size N (and each receiver's `fromAccountsList` to size 1), with no validation limiting N.
3. Once N is large (e.g., tens of thousands), broadcast an `UnfreezeBalanceContract` transaction from `A` for any one of the delegated receivers. `UnfreezeBalanceActuator.execute()` (lines 156-192) copies the full N-entry list into a new `ArrayList` and calls `remove(ByteString)`, an O(N) scan, on every node validating the transaction/block — repeating this pattern for each subsequent unfreeze call from `A` while the transaction's bandwidth fee remains fixed regardless of N.
4. Repeat step 3 (or issue many such transactions across many bloated accounts) to impose sustained excess CPU cost on the network's full nodes disproportionate to the fees paid, and independently observe amplified response payloads via `getDelegatedResourceAccountIndex` RPC/HTTP calls returning the full N-entry list.

Note: I was unable to fully verify in this pass whether `supportAllowDelegateOptimization()` is enabled by default on the current mainnet/production configuration (this would materially affect real-world exploitability); this should be confirmed against the live `DynamicPropertiesStore` default/activation status before treating this as actionable on a specific deployed network.
