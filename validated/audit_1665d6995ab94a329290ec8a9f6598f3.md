### Title
Legacy (non-hardened) exchange bonding-curve math allows an attacker to drive an Exchange's token pool balance negative, permanently bricking all future trades on that pair - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes a new pool balance for the "bought" token side using a bonding-curve `ExchangeProcessor` without ever checking that the computed `buyTokenQuant` is bounded by the pool's actual balance, unless the committee-gated `allowHardenExchangeCalculation` flag is enabled. This mirrors the Cally bug class: an unprivileged, attacker-controlled parameter (here, `sellTokenQuant` in a broadcast `ExchangeTransactionContract`) can push accounting state into an invalid region that causes all subsequent operations on that market to permanently misbehave/revert, without the attacker needing any special privilege.

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  computes:

- `buyTokenQuant = processor.exchange(sellBalance, buyBalance, sellTokenQuant)`
- `newBuyBalance = buyBalance - buyTokenQuant` (legacy path, plain subtraction, no bound check)

The bound check `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) throw ...` is only executed when `hardenedCalc` is `true`. This flag comes from `allowHarden()` in `AbstractExchangeActuator`, which is gated by the dynamic property `allowHardenExchangeCalculation` — a value only settable via a committee proposal, i.e. **off by default**. In the default (legacy) configuration, the subtraction `secondTokenBalance - buyTokenQuant` (or the symmetric `firstTokenBalance - buyTokenQuant`) is performed with **no floor check**, exactly analogous to the unguarded `msg.value - fee` subtraction in the Cally report.

The actual value calculation is delegated to `ExchangeProcessor.exchange()` [2](#0-1) , a Bancor-like bonding-curve formula using `Math.pow` on doubles with a hard-coded `supply` reinitialized to `1_000_000_000_000_000_000L` on every single call (it's a local variable, not persisted across calls). For sufficiently large `sellTokenQuant` relative to the pool balances, this formula can return a `buyTokenQuant` **larger than the actual `secondTokenBalance` currently held in the pool**, because nothing in the formula or in `ExchangeCapsule.transaction()` caps the output to the available balance.

Critically, `ExchangeTransactionActuator.doValidate()` [3](#0-2)  only bounds the **sold**-token side against `dynamicStore.getExchangeBalanceLimit()`:
```
long tokenBalance = (Arrays.equals(tokenID, firstTokenID) ? firstTokenBalance : secondTokenBalance);
tokenBalance = addExact(tokenBalance, tokenQuant);
if (tokenBalance > balanceLimit) { throw ... }
```
There is **no check** that `anotherTokenQuant` (the bought-side amount, computed later at line 217-218 by actually invoking `exchangeCapsule.transaction(...)`) is less than or equal to the current balance on that side. `calcFee()` for this actuator is fixed at `0` [4](#0-3) , so any account (unprivileged, anonymous RPC caller broadcasting a normal transaction) can call this repeatedly.

Once a trade drives `firstTokenBalance` or `secondTokenBalance` negative in `ExchangeCapsule`, subsequent calls to `ExchangeProcessor.exchange()` feed a negative balance into `Math.pow(1 + quant/newBalance, 0.0005)` and `Math.pow(1 + supplyQuant/supply, 2000.0)`. `Math.pow` with a negative base and non-integer exponent returns `NaN`, and casting `NaN` to `long` in Java yields `0`. From that point forward, every trade on the exchange silently returns `0` tokens (or misbehaves unpredictably), and downstream consumers such as `ExchangeWithdrawActuator.doValidate()` [5](#0-4) , which rejects `anotherTokenQuant <= 0` with `"withdraw another token quant must greater than zero"`, will permanently reject withdrawals as well — the exchange (and any TRX/TRC10 balance locked in it) becomes permanently unusable, an accounting/DoS corruption reachable purely from a broadcast transaction.

### Impact Explanation
This is an accounting-corruption / DoS bug reachable by any unprivileged account (no committee/witness privilege needed) via a normal broadcast `ExchangeTransactionContract`. Once triggered against a given `Exchange` (which any user can create via `ExchangeCreateActuator`), it permanently corrupts that exchange's pool state, causing all future `ExchangeTransactionContract`/`ExchangeWithdrawContract` calls on it to fail or return `0`, effectively locking any tokens deposited in the pool (including the attacker's counterparties' funds) and denying legitimate trading — mirroring the "force future calls to revert" impact in the referenced report, but at the exchange/market-accounting layer rather than the token-owner layer.

### Likelihood Explanation
Likelihood is high in principle: `allowHardenExchangeCalculation` defaults to off (must be turned on by a witness-committee proposal), so the vulnerable legacy math path is the one exercised on real deployments. Only the sold-token side is limit-checked in `doValidate()`; the bought-side output is unconstrained. Whether attacker-supplied `sellTokenQuant` values (bounded below `getExchangeBalanceLimit()`) can practically drive `buyTokenQuant` above the current opposite-side balance depends on the exact numeric behavior of the double-precision Bancor curve for extreme ratios of `sellTokenQuant` to pool size; this requires numeric/fuzzing verification which was not performed here, so likelihood should be treated as plausible-but-unverified pending such testing.

### Recommendation
- Enforce the same non-negative balance invariant in the legacy (`hardenedCalc == false`) path of `ExchangeCapsule.transaction()` as is already done for the hardened path, rather than gating this basic safety check behind a committee-controlled feature flag.
- In `ExchangeTransactionActuator.doValidate()`, explicitly validate that the computed `anotherTokenQuant` does not exceed the current balance of the corresponding token in the exchange, in addition to the existing sold-side `balanceLimit` check.
- Consider making `allowHardenExchangeCalculation` (and equivalent bound checks) mandatory/default-on rather than opt-in via proposal, since the underlying issue is a correctness bug, not a behavior tunable.

### Proof of Concept
Conceptual reproduction path (numeric edge case not independently confirmed):
1. Attacker calls `ExchangeCreateActuator` to create a new Exchange with a small `firstTokenBalance`/`secondTokenBalance` pair (e.g., 1 TRX vs. some TRC10 token).
2. Attacker broadcasts an `ExchangeTransactionContract` selling a very large `tokenQuant` of the token whose balance is far below `balanceLimit`, chosen so that `ExchangeProcessor.exchange()`'s bonding-curve output `buyTokenQuant` exceeds the opposite side's current balance.
3. `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)` [6](#0-5) , which (legacy path) subtracts `buyTokenQuant` from the opposite balance without a floor check, driving it negative, and persists via `Commons.putExchangeCapsule(...)`.
4. Any subsequent `ExchangeTransactionContract` or `ExchangeWithdrawContract` on this exchange now operates on a negative pool balance; `Math.pow` with a negative base and fractional exponent returns `NaN`, `(long) NaN == 0`, so `anotherTokenQuant` becomes `0`, which `ExchangeWithdrawActuator.doValidate()` rejects (`"withdraw another token quant must greater than zero"`), permanently denying trading/withdrawal on that exchange. package org.tron.core.capsule;

import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.Maths;

@Slf4j(topic = "capsule")
public class ExchangeProcessor implements ExchangeCapsule.Processor {

  private long supply;
  private final boolean useStrictMath;

  public ExchangeProcessor(long supply, boolean useStrictMath) {
    this.supply = supply;
    this.useStrictMath = useStrictMath;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

}
