### Title
Unauthenticated Forgery of Admin Session via Unverified `shop` Query Parameter in Merchant Custom App Strategy - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/merchant-custom-app.ts`)

### Summary
For merchant/custom-distributed apps (`AppDistribution.ShopifyAdmin`/non-embedded flow), `authenticateAdmin` resolves the acting `shop` directly from the unauthenticated request query string and hands it to `MerchantCustomAuth.authenticate`, which builds a fully valid `Session` object from that string with **no cryptographic verification** (no session-token decode, no HMAC, no signature check) tying the value to the actual caller. This mirrors the reported bug class: an operation intended to act on a cryptographically verified identity (the "signer"/session-token subject) instead trusts an attacker-suppliable identifier (the "depositor"/`shop` field) to authorize the action.

### Finding Description
In the non-embedded/custom-app branch of `getSessionTokenContext`, `shop` is read straight from the URL without any signature or JWT verification: [1](#0-0) 

This is the same function that, for embedded apps, decodes and validates a session token (`validateSessionToken`) before extracting `shop` — that verification path is skipped entirely for the custom-app branch: [2](#0-1) 

That unverified `shop` is passed straight into `MerchantCustomAuth.authenticate`, which builds and returns a `Session` object purely from the string, with no additional check that the requester actually controls or was authenticated for that shop: [3](#0-2) 

`customAppSession` only sanitizes the shop format (must look like a `myshopify.com` domain) — it performs no authentication check that the caller is entitled to that shop: [4](#0-3) 

This is structurally identical to the SVM-Spoke bug: an action meant to be scoped to a caller whose identity is cryptographically proven (the SPL "signer") instead pulls its authorization target from an attacker-controlled field (the "depositor" account/here, the `shop` query param), with no delegation/verification step in between.

### Impact Explanation
Any unauthenticated party who can reach the merchant/custom-app admin authentication path can supply an arbitrary `shop=` value and receive back a fully-formed, "authenticated" `Session` object for that shop, with no proof of ownership of, or authorization for, that shop. Any downstream logic keyed off `session.shop` (webhook registration, business logic, per-shop authorization decisions, logging/audit trails) would treat the request as validly originating from that shop. This is a forged-session vulnerability: the session-construction path here provides no protection equivalent to what embedded apps get from session-token verification.

### Likelihood Explanation
Reaching this code path requires only an unauthenticated HTTP request to the admin authentication route of an app configured as a merchant custom (non-embedded, `AppDistribution.ShopifyAdmin`) app — no privileged access, secrets, or MITM position needed. The condition is gated on app configuration (custom/merchant distribution), so likelihood depends on how many apps use that distribution mode, but for those that do, the exploit is trivial (append/change a query parameter).

### Recommendation
Do not derive the authorization-scoping `shop` value for `MerchantCustomAuth.authenticate` from an unauthenticated query parameter. Require the same or equivalent verification used for embedded apps (e.g., verified session token, host/shop binding validated against a signed cookie, or configuration-bound shop value) before constructing a `Session`, and/or bind the custom-app access token to a specific, pre-configured shop rather than trusting a caller-supplied `shop` string.

### Proof of Concept
1. Configure or target an app using `AppDistribution.ShopifyAdmin` (merchant custom app) in `shopify-app-remix`.
2. Send an unauthenticated request to the app's admin route without a session-token header, e.g. `GET /app?shop=victim-shop.myshopify.com`.
3. `authenticateAdmin` (`authenticate.ts`) skips session-token validation for this distribution, extracts `shop` from the query string, and calls `MerchantCustomAuth.authenticate`, which returns `Session` for `victim-shop.myshopify.com` with no verification that the requester is associated with that shop.
4. The forged `Session` is used to build the authenticated admin context returned to the app's route handlers. [5](#0-4)
