### Title
Chunk executor accepts unverified intermediate state-checkpoint root hashes for non-final checkpoints in a multi-block chunk - (File: `execution/executor/src/workflow/do_state_checkpoint.rs`)

### Summary
`DoStateCheckpoint::get_state_checkpoint_hashes` is supposed to bind the per-transaction `state_checkpoint_hash` recorded in each `TransactionInfo` to the locally-recomputed Jellyfish Merkle root. When a chunk (as processed by the `ChunkExecutor`, used for state-sync / fast-sync / backup replay, which can span many blocks) contains more than one internal `StateCheckpoint` transaction, only the *last* checkpoint's hash is cross-checked against the locally computed root; every earlier ("intermediate") checkpoint hash is taken verbatim from the caller-supplied `known_state_checkpoints` vector with no independent verification.

### Finding Description
`DoStateCheckpoint::get_state_checkpoint_hashes` only validates one index: [1](#0-0) 

`known_state_checkpoints` is a vector with one entry per transaction in the chunk, but the `ensure!` only fires for `known[idx]` where `idx == last_checkpoint_index` (the last checkpoint in the *whole chunk*), even though a chunk can contain multiple `StateCheckpoint` boundaries (one per block it spans), as evidenced by `StateUpdateRefs`'s handling of `for_last_checkpoint`/`for_latest` splits and multi-block test cases: [2](#0-1) 

The `known_state_checkpoints` values themselves are populated in `ChunkExecutor::update_ledger` directly from the `TransactionInfo`s carried by the (untrusted, peer-supplied) chunk proof — i.e., from `chunk_verifier.transaction_infos()`: [3](#0-2) 

Those same, unverified-for-intermediate-indices values are then written straight back into the freshly assembled `TransactionInfo`s via `state_checkpoint_hashes[i]`: [4](#0-3) 

and the resulting `TransactionInfo` hash is what gets compared against the very same proof-supplied `transaction_infos` in `ChunkResultVerifier::verify_chunk_result` (`ensure_transaction_infos_match`) and in the accumulator-extension check `verify_extends_ledger`: [5](#0-4) 

Because the intermediate `state_checkpoint_hash` used to reconstruct the `TransactionInfo` is copied verbatim from the same source it is later diffed against, the comparison is tautological for every non-final checkpoint in the chunk: it can never detect a mismatch between what was locally computed by the JMT/state-summary machinery and what the (potentially stale, corrupted, or maliciously/faultily-served) proof claims. The only genuine cross-check against the locally computed root happens once per chunk, at the very last checkpoint index (`last_checkpoint.root_hash()` in `do_state_checkpoint.rs:42-49`).

### Impact Explanation
This breaks the "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and "proof binding" invariants: a locally-computed state root at an intermediate block boundary inside a multi-block chunk is never actually validated against the corresponding checkpoint hash before that hash (sourced from the syncing peer/proof) is persisted as ground truth in the node's `TransactionInfo` and accumulator. If the node's own JMT/state-summary computation for that intermediate version diverges from the canonical chain (e.g., due to a determinism bug, a race in the buffered-state incremental update path, or a corrupted/malicious data source for the chunk being replayed), the divergence is silently accepted and persisted at that version, and is only even theoretically catchable if it happens to also break the *final* checkpoint of the chunk (which it need not, since further transactions after the divergent checkpoint can still, by coincidence or exploit, converge the root at chunk end). Any authenticated state proof served for that intermediate version afterwards is bound to a checkpoint hash that was never independently confirmed against local computation, i.e., hard-fork-only silent divergence at exactly the state-commitment layer this scan is scoped to.

### Likelihood Explanation
This path is exercised whenever the `ChunkExecutor` (state-sync/fast-sync/backup-replay path) processes a chunk spanning more than one block, which is a routine, non-adversarial occurrence in normal fast-sync operation (chunks of hundreds/thousands of transactions typically span many blocks and thus many intermediate `StateCheckpoint` boundaries). No malicious actor is even strictly required — any correctness bug or non-determinism in the incremental `LedgerStateSummary::update` / buffered-state path for intermediate checkpoints would go completely undetected by this code, which is exactly the "no independent verification" gap. Triggering it does not require privileged access, malicious peer behavior is not necessary (though a compromised/faulty state-sync source would make it directly exploitable), so it sits squarely in-scope as a local, unprivileged, root-cause-provable gap in the code's own integrity check.

### Recommendation
In `DoStateCheckpoint::get_state_checkpoint_hashes` (and the mirrored logic in `compute_position_checkpoint`), independently recompute (or otherwise cryptographically re-derive) and verify **every** checkpoint hash in `all_checkpoint_versions`/`all_checkpoint_indices` against the locally computed intermediate state roots — not just the last one in the chunk — before accepting `known_state_checkpoints` as authoritative. This requires the state-checkpoint machinery (`LedgerStateSummary::update`) to expose the root hash at each intermediate checkpoint boundary within a chunk, not only the chunk-final one, so each `known[idx]` for every `idx` in `all_checkpoint_versions` can be checked with an `ensure!` identical to the one currently applied only to `last_checkpoint_index`.

### Proof of Concept
Conceptual trace (exact reproduction requires instrumenting `ChunkExecutor::update_ledger` with a chunk spanning ≥2 blocks and a JMT computation that is made to diverge at an intermediate checkpoint, which I could not fully execute in this read-only investigation):
1. Feed the `ChunkExecutor` a chunk (via `execute_chunk`/`update_ledger`) containing transactions from two blocks, i.e., two `StateCheckpoint` boundaries at indices `i1 < i2` (`i2` = last).
2. Construct/replay the chunk such that the node's own incremental state computation at version `i1` (first checkpoint) yields a JMT root `R_local != R_known` (the proof-supplied `known_state_checkpoints[i1]`), for example by injecting a fault into `LedgerStateSummary::update`'s incremental path, while the final checkpoint at `i2` still happens to equal the locally computed root (`R_local_final == known[i2]`).
3. Observe that `get_state_checkpoint_hashes` (`execution/executor/src/workflow/do_state_checkpoint.rs:206-221`) only asserts equality for `idx == last_checkpoint_index` (`i2`), so the divergent `known[i1]` is accepted unchanged and returned in `state_checkpoint_hashes`.
4. `DoLedgerUpdate::assemble_transaction_infos` builds the `TransactionInfo` at version `i1` using this unverified `state_checkpoint_hashes[i1]` (`execution/executor/src/workflow/do_ledger_update.rs:82,100`), and this info is committed to the ledger DB / accumulator without ever having been checked against `R_local`.
5. `ChunkResultVerifier::verify_chunk_result` / `ensure_transaction_infos_match` cannot catch this because the comparison is against the same proof-supplied `transaction_infos` that originated `known[i1]` in the first place (`execution/executor/src/chunk_executor/mod.rs:373-379`, `chunk_result_verifier.rs:53-64`).

Because I could not run the full executor test harness within this analysis, I was unable to produce a fully executed failing test; the finding is derived from tracing the exact data flow and confirming the tautological comparison at the source level cited above.
