### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting `db-tool replay-verify` accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash` / the position (hot-state / native) checkpoint hash, as flagged by its own `TODO(trading-native)` comment.

### Finding Description [1](#0-0) 

The function validates four fields between the locally computed `TransactionOutput` and the trusted `TransactionInfo` proof: transaction status, gas used, write-set hash (`state_change_hash`), and event root hash. It never compares `txn_info.state_checkpoint_hash()` (or the related `position_state_checkpoint_hash`) against any locally recomputed state/checkpoint root. The comment left in the code makes this gap explicit: [2](#0-1) 

This means the one authenticated field that actually attests to the *state root* (the Sparse/Jellyfish Merkle root committed for that version) is silently excluded from the equivalence check performed by replay tooling. `TransactionInfo` carries `state_checkpoint_hash` specifically so that a proof consumer can bind a version to the correct state root; skipping it breaks the proof-binding invariant that "committed state that differs from the correct VM result... must be detected."

### Impact Explanation
`storage/db-tool/src/replay_on_archive.rs` and the chunk executor's transaction-info matching path rely on `ensure_match_transaction_info` as the acceptance gate when replaying historical transactions against an archived DB to verify correctness. If the state/hot-state checkpoint root or the native "position" state checkpoint root computed during local re-execution diverges from what is recorded in the authenticated `TransactionInfo` (e.g., due to a state-projection bug, a native/position DB divergence, or a future protocol change gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), this comparator will still report success because it never inspects `state_checkpoint_hash`. This is a proof-integrity gap: a state root that differs from the correct VM result can pass replay verification silently, undermining the state-integrity guarantee that verification tooling and downstream consumers rely on to detect any consensus/state divergence.

### Likelihood Explanation
This is a genuine, currently-live gap in an unprivileged verification path — no privileged input is required, since the check simply omits data it should validate. Its exploitability depends on there already being a state-root mismatch (e.g., from a native/position-state bug or replay bug) for it to matter; it is a detection/guard gap rather than a primary corruption vector. The author's own `TODO` note ties it directly to an in-progress feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS` / native position state), indicating the gap is acknowledged but not yet closed, and is intended to be fixed before that feature is enabled — meaning it is a known, unresolved omission in the state-commitment verification chain.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `txn_info.state_checkpoint_hash()` against a locally recomputed checkpoint hash (state Merkle root and, if applicable, hot-state/position state checkpoint hash) whenever the transaction is expected to produce one, and fail loudly (as the other checks do) on mismatch before any code path (especially `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled that depends on native/position state correctness.

### Proof of Concept
Not directly demonstrable without a native/position-state divergence to trigger the gap; the flaw is a missing check on the codepath itself. Concrete demonstration: construct a `TransactionOutput` whose recomputed state (e.g., a locally maintained SMT/position state) differs from the checkpoint hash embedded in the archived `TransactionInfo`, but has matching status/gas/write-set hash/event root — `ensure_match_transaction_info` will return `Ok(())`, and `db-tool replay-verify` will report the transaction as successfully verified despite the state root mismatch.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
```
