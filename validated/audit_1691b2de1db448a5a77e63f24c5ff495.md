### Title
Overflow in hardened `calculateGlobalLimitV1`/`calculateGlobalLimitV2` energy-limit calculation can throw an uncaught `ArithmeticException`, permanently blocking energy usage for accounts with frozen balances - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`, `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
The C4 report describes `VTVLVesting._baseVestedAmount()` performing `_claim.linearVestAmount * truncatedCurrentVestingDurationSecs` in a fixed-width type (`uint112`) that overflows and reverts, permanently freezing vested tokens for large allocations. java-tron's frozen-balance-to-resource-limit calculation contains an analogous pattern: a multiplication of two economically-scaled `long` values (`frozenBalance-derived weight * totalEnergyLimit`) that, under the "hardened" calculation path, is deliberately checked with `BigInteger...longValueExact()` and will throw `ArithmeticException` on overflow instead of silently truncating.

### Finding Description
`EnergyProcessor.calculateGlobalEnergyLimit()` computes an account's energy limit from its frozen balance: [1](#0-0) 

When `hardenCalculation()` is enabled it delegates to `ResourceProcessor.calculateGlobalLimitV1`, which performs the multiplication in `BigInteger` and converts back to `long` with `longValueExact()`: [2](#0-1) 

`longValueExact()` throws `ArithmeticException` if the `BigInteger` result does not fit in a `long`. This is the exact analog of the Solidity fixed-width overflow in the report: instead of a `uint112` truncated-multiplication reverting, a `long`-sized intermediate product (`weight * totalEnergyLimit`) is checked and reverts (via unchecked Java exception) when the product exceeds `Long.MAX_VALUE` (~9.22e18).

The values involved are economically realistic, not merely theoretical:
- `weight = frozeBalance / TRX_PRECISION`. TRX total supply is on the order of ~1.0e17 sun, so `weight` can reach ~1.0e11 for a large single freezer.
- `totalEnergyLimit` is a governance-configurable network-wide parameter that can be tens of billions.
- The product `weight * totalEnergyLimit` can therefore reach ~5e21, well beyond `Long.MAX_VALUE`, exactly mirroring how the report showed that realistic vesting amounts (tens of millions of 18-decimal tokens) exceed `uint112`.

This computation is invoked from `EnergyProcessor.useEnergy()` and `getAccountLeftEnergyFromFreeze()`, both of which run for every transaction that consumes energy from an account holding frozen-for-energy balance: [3](#0-2) [4](#0-3) 

Tests in the repo explicitly document and exercise this exact overflow-detection behavior: [5](#0-4) 

The equivalent `calculateGlobalLimitV2` (used when `supportUnfreezeDelay()`/V2 freeze model is active) has the same structural risk: [6](#0-5) 

### Impact Explanation
If the hardened path (`allowHardenResourceCalculation`, a governance-controlled `DynamicPropertiesStore` flag) is enabled and the frozen-weight/energy-limit product for an account exceeds `Long.MAX_VALUE`, `calculateGlobalEnergyLimit()`/`calculateGlobalEnergyLimitV2()` throws an uncaught `ArithmeticException`. This is called deterministically by every full node while executing any transaction that touches that account's energy accounting (`useEnergy`, `getAccountLeftEnergyFromFreeze`), so the failure is consensus-wide and reproducible rather than isolated to one node. Because the exception is not shown to be caught anywhere between `EnergyProcessor` and the actuator/VM execution path that invokes it, this converts a resource-accounting edge case into either (a) a permanent inability for the affected account (and any account interacting with it in the same block) to have its transactions processed, or (b) — if uncaught further up in block application — a node-level failure while applying that block, i.e., a chain-halt/availability risk. This matches the accepted "invalid-state/divergence/halt" impact class, analogous to the original report's "permanent freeze of vested tokens."

### Likelihood Explanation
Likelihood is currently gated by two factors: (1) the vulnerable branch only activates when `allowHardenResourceCalculation` is turned on network-wide (it is off by default per the test scaffolding pattern `saveAllowHardenResourceCalculation(0/1)`), and (2) it requires an account to accumulate a frozen-for-energy balance large enough, combined with the prevailing `totalEnergyLimit`/`totalEnergyWeight` values, to push the product past `Long.MAX_VALUE`. Given TRX's actual total supply and observed `totalEnergyLimit` governance values, this is reachable by a small number of very large freezers/whales once hardening is enabled, but is not currently exploitable while the flag remains disabled. This is a real but conditionally-reachable bug rather than a bug exploitable today by an arbitrary unprivileged user.

### Recommendation
- Replace `longValueExact()` with a saturating/clamped conversion (e.g. clamp to `Long.MAX_VALUE`) or perform the entire energy-limit computation in `BigInteger`/wider precision throughout the consuming call chain (`useEnergy`, `getAccountLeftEnergyFromFreeze`, receipt/energy-cost accounting) so no exception can propagate.
- At minimum, wrap `calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` and their `ResourceProcessor` counterparts (`calculateGlobalLimitV1`, `calculateGlobalLimitV2`, `usageToBalance`, `getUsage`, `increase`) in defensive handling that degrades gracefully (e.g., falls back to the double-based legacy path or clamps the result) instead of letting `ArithmeticException` escape into transaction execution.
- Add bound checks/tests using realistic TRX-supply-scale `frozeBalance` and governance-configurable `totalEnergyLimit` values (not just synthetic `Long.MAX_VALUE/2`-style inputs) to confirm the hardened path cannot throw for any value achievable under real network parameters before `allowHardenResourceCalculation` is enabled on mainnet.

### Proof of Concept
1. Enable hardening: `dynamicPropertiesStore.saveAllowHardenResourceCalculation(1)`.
2. Set `totalEnergyLimit` to a large but realistic governance value, e.g. `50_000_000_000L`.
3. Freeze a large TRX balance for energy on an account such that `frozeBalance / TRX_PRECISION` (i.e., `weight`) times `totalEnergyLimit` exceeds `Long.MAX_VALUE` (~9.22e18) — e.g. `weight ≈ 2e8` with `totalEnergyLimit = 5e10` gives product `1e19 > Long.MAX_VALUE`.
4. Call `EnergyProcessor.calculateGlobalEnergyLimit(accountCapsule)` (directly, or indirectly via `useEnergy`/`getAccountLeftEnergyFromFreeze` during transaction execution).
5. Observe `ResourceProcessor.calculateGlobalLimitV1` throws `ArithmeticException` from `longValueExact()`, exactly as already demonstrated by the repo's own test `testGlobalNetLimitOverflowDetectedWithHardening`: [5](#0-4) 
6. Trace the call path (`useEnergy` → `calculateGlobalEnergyLimit`) to confirm no intervening catch block, so the exception propagates into transaction/block execution rather than being handled as a normal validation failure.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }
