### Title
Unvalidated legacy exchange balance subtraction allows negative pool balances / accounting corruption in `ExchangeCapsule.transaction` - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The reported bug class is: a value (`interestUsd`) is updated by unchecked addition/subtraction driven by external, mutable input (oracle price), and only one code path validates that the resulting balance cannot go negative, while the other path silently allows underflow, corrupting internal accounting and blocking legitimate operations. The same structural pattern exists in java-tron's TRX/TRC10 bancor-style `Exchange` (market) subsystem: `ExchangeCapsule.transaction()` computes new pool balances with subtraction/addition, but only validates non-negativity when the "hardened" calculation mode is active; the legacy branch, reachable by any account broadcasting an `ExchangeTransactionContract`, performs raw `long` subtraction with no negative-balance check at all.

### Finding Description
`ExchangeCapsule.transaction()` computes `newFirstTokenBalance`/`newSecondTokenBalance` via a bancor-relay formula and then applies the update: [1](#0-0) 

The non-negativity check is gated behind `hardenedCalc`: [2](#0-1) 

When `hardenedCalc` is `false` (the legacy behavior), `newFirstTokenBalance`/`newSecondTokenBalance` are computed as plain `long` subtraction/addition (`firstTokenBalance - buyTokenQuant`, etc.) with no check that the result is `>= 0`, and the mismatched/rounded double-precision bancor math (`exchangeToSupply`/`exchangeFromSupply` in `ExchangeProcessor`) can produce a `buyTokenQuant` that exceeds the actual pool balance for edge-case inputs, driving the balance negative: [3](#0-2) 

Whether the hardened check is applied is controlled by `allowHarden()`, itself driven by the `allowHardenExchangeCalculation()` dynamic chain property, gating both the negative-balance guard in `ExchangeCapsule` and the `addExact`/`subtractExact` overflow guards in `AbstractExchangeActuator`: [4](#0-3) 

`ExchangeTransactionActuator.execute()` is reachable directly from any broadcast transaction (anonymous RPC/gRPC `ExchangeTransactionContract`), calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`, and persists the resulting (potentially negative) pool balances back to the `ExchangeStore`/`ExchangeV2Store` without any further sanity check: [5](#0-4) 

This mirrors the reported bug exactly: an accounting variable is mutated through arithmetic driven by externally-influenced state (bancor relay/exchange rate here, oracle price in the report), and validation against going negative exists on only one of two code paths, so under the unguarded path the value can silently underflow, corrupting the tracked balance and (depending on downstream logic) making the market/pool unusable.

### Impact Explanation
A negative `firstTokenBalance`/`secondTokenBalance` stored in an `Exchange`/`ExchangeV2` object corrupts the TRC10/TRX exchange pool's accounting. Subsequent trades computed from a corrupted (negative) balance produce further nonsensical results (division/multiplication by negative numbers in `ExchangeProcessor`), and other actuators reading these balances (`ExchangeWithdrawActuator`, `ExchangeInjectActuator`) will operate on incorrect state, which can permanently break the affected exchange pair (denial of service for that market) or allow value extraction inconsistent with actual reserves — this is asset/accounting corruption within the node's on-chain state, not merely a UI/off-chain issue.

### Likelihood Explanation
Likelihood depends on whether `allowHardenExchangeCalculation` is enabled network-wide; I could not confirm the default value of this dynamic property within the available index (searches for its default in `DynamicPropertiesStore.java` returned no hits, likely due to index size limits). If the hardened calculation has not been activated via committee proposal on a given chain/testnet, any account can trigger the unguarded legacy path simply by broadcasting a normal `ExchangeTransactionContract` with quantities engineered (via the double-precision bancor formula) to produce a `buyTokenQuant` exceeding the counter-token pool balance.

### Recommendation
Remove the `hardenedCalc` conditional gating and always enforce the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check in `ExchangeCapsule.transaction()` regardless of the `allowHardenExchangeCalculation` flag, and always use overflow/underflow-safe arithmetic (`StrictMathWrapper.addExact/subtractExact`) in `AbstractExchangeActuator` rather than gating it behind a toggle. This closes the same class of bug the Debt DAO team fixed by removing unguarded interest-USD arithmetic.

### Proof of Concept
1. Ensure the chain has `allowHardenExchangeCalculation` disabled (legacy path), and an `Exchange`/`ExchangeV2` pool exists with small `firstTokenBalance`/`secondTokenBalance`.
2. Broadcast an `ExchangeTransactionContract` (via `ExchangeTransactionActuator`) with a `tokenQuant` chosen such that the double-precision bancor computation in `ExchangeProcessor.exchange()` returns a `buyTokenQuant` greater than the current counter-token pool balance. [6](#0-5) 
3. Because `hardenedCalc` is `false`, the resulting negative balance passes unchecked through `ExchangeCapsule.transaction()`. [7](#0-6) 
4. `ExchangeTransactionActuator.execute()` persists the corrupted `ExchangeCapsule` state via `Commons.putExchangeCapsule(...)`, permanently corrupting the pool's on-chain accounting. [8](#0-7)

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
