### Title
Relayer fee refund is paid unconditionally, before the wallet-contract action succeeds - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`inner_rlp_execute` in the NEAR Wallet Contract sends a relayer fee transfer as an independent, fire‑and‑forget promise batch *before* the actual action (base‑token transfer or emulated ERC‑20 transfer) is executed and its result checked. This is the nearcore analog of the "SafeERC20 not used" pattern: the report's contract moved ERC-20 tokens without checking the transfer outcome, and here the wallet contract moves $NEAR to the relayer without ever tying that payment to the outcome of the action it is supposed to compensate.

### Finding Description
In `inner_rlp_execute`, once the transaction is parsed into an `action`/`transaction_kind`, the code unconditionally creates a **separate** promise batch that transfers the relayer `fee` right away: [1](#0-0) 

This `refund_promise` is created with `env::promise_batch_create` and `env::promise_batch_action_transfer` directly — it is *not* chained with `.then()` to the promise that actually performs the requested action (built afterwards in the `match transaction_kind` block at lines 412-472: `EOABaseTokenTransfer`, `ERC20Transfer`, etc.): [2](#0-1) 

Because the fee-payment receipt and the action receipt are dispatched as two independent receipts from the same function-call execution, the fee is paid to the relayer regardless of whether the follow-up action (the base-token transfer, or the multi-step NEP-141 `storage_balance_of` → `storage_deposit` → `ft_transfer` chain in `nep_141_storage_balance_callback`, see lines 194-273) ultimately succeeds or fails: [3](#0-2) 

The `rlp_execute_callback`/`nep_141_storage_balance_callback` do handle `PromiseResult::Failed` for the *action* and issue a refund of `caller_deposit` (the attached NEAR sent along with the call) when the action fails, but there is no analogous mechanism to reclaim or condition the relayer `fee` that was already dispatched. This mirrors the audited bug: value is moved out of the account without verifying that the corresponding operation actually succeeded.

### Impact Explanation
If the wrapped action fails after the fee has already been dispatched (e.g., the ERC‑20 `ft_transfer` fails because of insufficient token balance, a paused/frozen token contract, or a receiver that rejects the transfer), the wallet contract owner has still paid the relayer's fee in $NEAR out of their own account balance for a transaction that produced no useful effect. This is a concrete unauthorized value movement: funds leave the user's account without the compensating action being completed, and there is no rollback path for the fee itself (only `caller_deposit` is refunded on failure). Given that a "faulty relayer" can also intentionally supply a target/action combination designed to fail after being paid (or race conditions in the state that make the action fail non-deterministically between message construction and its actual execution), this allows fee extraction with no service rendered.

### Likelihood Explanation
This path is reachable by any relayer submitting a `rlp_execute` call on behalf of any Wallet Contract account with a non-zero fee (the standard use case for meta-transactions is relayer-paid execution). No special privileges are required beyond being the transaction's predecessor account, which is exactly the "unprivileged transaction signer / meta-transaction sender" actor class. The scenario does not require a malicious validator or network-level manipulation — a normal, or even honest-but-unlucky, relayer submission where the wrapped action later fails is sufficient to trigger fee loss.

### Recommendation
Chain the relayer-fee transfer to the outcome of the wrapped action instead of dispatching it eagerly and unconditionally. For example, move the fee-payment action into the same promise batch as the wrapped action (so both succeed or fail atomically), or defer the fee transfer into the `rlp_execute_callback`/`nep_141_storage_balance_callback` so it is only sent once `PromiseResult::Successful` is observed for the underlying action.

### Proof of Concept
1. Owner signs an Ethereum-style `ft_transfer` (ERC20Transfer emulation) transaction with a non-zero `fee` for the relayer, intending to send tokens they believe they have.
2. A relayer submits `rlp_execute` with this transaction. `inner_rlp_execute` immediately creates and dispatches `refund_promise` transferring `fee` to the relayer. [4](#0-3) 
3. Concurrently, the owner's NEP-141 balance has already dropped below the transfer amount (e.g. a race with another wallet action, or the token contract enforces a max transfer or is paused), so the resulting `ft_transfer` call fails.
4. `nep_141_storage_balance_callback`/`rlp_execute_callback` observes `PromiseResult::Failed` and returns `success: false`, refunding only `caller_deposit` (the attached deposit) — never the already-sent relayer `fee`. [5](#0-4) 
5. Net effect: the owner's $NEAR balance is permanently reduced by `fee`, despite the requested action never taking effect.

            let address_registrar = {
                let account_id = ADDRESS_REGISTRAR_ACCOUNT_ID
                    .trim()
                    .parse()
                    .unwrap_or_else(|_| env::panic_str("Invalid address registrar"));
                ext_registrar::ext(account_id).with_static_gas(REGISTRAR_LOOKUP_GAS)
            };
            let address = format!("0x{}", hex::encode(address));
            address_registrar.lookup(address).then(ext.address_check_callback(
                target,
                action,
                caller_deposit,
            ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
        }
        _ => {
