### Title
`ensure_match_transaction_info` skips checkpoint-hash verification per transaction, letting replay/db-tool accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
The external report is about a single slippage parameter being incorrectly reused/omitted per-item in a batch, causing wrong acceptance criteria for different items in the batch. The Aptos-native analog is `TransactionOutput::ensure_match_transaction_info`, a per-transaction verification routine used by replay/verification tooling, which checks transaction status, gas used, write-set hash, and event-root hash against the authenticated `TransactionInfo`, but explicitly and knowingly omits verifying the state/hot-state checkpoint hash and the `position_state_checkpoint_hash` for that same transaction.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates `status`, `gas_used`, write-set hash, and event-root hash of a re-executed `TransactionOutput` against a `TransactionInfo` fetched/authenticated from the ledger (or backup). However, the function body ends with an explicit `TODO` acknowledging that it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)" and returns `Ok(())` regardless of whether those fields match: [2](#0-1) 

This function is used by tooling that is supposed to authenticate that a locally re-executed transaction output is consistent with a trusted, proof-bound `TransactionInfo`: the chunk executor's replay path (`execution/executor/src/chunk_executor/mod.rs`), the `aptos-debugger` (`aptos-move/aptos-debugger/src/aptos_debugger.rs`), and the CLI replay/verify commands (`aptos-move/cli/src/commands.rs`). None of these call sites independently re-check the checkpoint hash fields that `ensure_match_transaction_info` skips.

### Impact Explanation
`TransactionInfo::state_checkpoint_hash()` and `position_state_checkpoint_hash()` bind a version to the correct global state root (including the newer "trading native" position state root, gated by `compute_trading_native_state_roots`, see `types/src/block_executor/config.rs`). Because `ensure_match_transaction_info` never compares these fields, a divergence between the locally recomputed state root and the authenticated `TransactionInfo`'s checkpoint hash — e.g., from an executor bug, a bad backup snapshot, or a maliciously/incorrectly modified `TransactionOutput` during replay — will not be detected by this check. Any tool relying solely on this function (`replay_on_archive`, debugger-based verification, CLI simulate/verify) can report "successful replay/verification" even though the actual state (specifically the position/native-state root) diverges from the authenticated ledger commitment. This is exactly the class of proof/authenticated-response binding failure called out in the task ("Authenticated API or state-view output bound to the wrong version, object, or proof context" / "Hard-fork-only divergence during commit, replay ... verification").

### Likelihood Explanation
This is not a hypothetical gap — the code contains an explicit `TODO` written by the Aptos team acknowledging the missing check is a real, known deficiency, which raises confidence that the omission is real and currently shipped. It requires a state divergence to actually exist for the impact to manifest (i.e., it's a "silent verifier," not a currently-exploitable state corruption on its own), and I could not fully trace, within the tool budget, whether `compute_trading_native_state_roots`/native position state is enabled on mainnet or gated behind an unlaunched feature flag — that determines whether the impact is live-mainnet-relevant today or forward-looking (once the feature activates).

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()` (when present), and `position_state_checkpoint_hash()` (when `compute_trading_native_state_roots` is enabled) between the recomputed output/state summary and the authenticated `TransactionInfo`, returning an error on mismatch, consistent with how the other fields (write-set hash, event-root hash) are already checked.

### Proof of Concept
Not independently reproducible from static analysis alone within the available tool budget: exploiting this gap requires constructing a scenario where the locally recomputed position/state checkpoint hash differs from the `TransactionInfo` supplied to `ensure_match_transaction_info` (e.g., replaying with a corrupted `write_set`/state update that changes the position-state root but preserves the base write-set hash and event hash) and confirming that `aptos-debugger`/CLI/chunk-executor replay paths report success. I was not able to trace whether any of the three call sites perform an independent, redundant checkpoint-hash check outside this function that would neutralize the gap — this should be manually confirmed against `aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `execution/executor/src/chunk_executor/mod.rs` before treating this as fully confirmed.
