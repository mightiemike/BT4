### Title
`ensure_match_transaction_info` skips verifying the position-state checkpoint hash, letting replay-verify accept a corrupted trading-native state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay/replay-verify tooling to confirm that a locally re-executed transaction output matches the `TransactionInfo` that was actually committed to the ledger accumulator. The function validates status, gas, write-set hash, and event root hash, but it never validates the position-state checkpoint hash (or hot-state hash), even though `TransactionInfoV1` and the state-checkpoint pipeline compute and commit that hash when the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature is enabled.

### Finding Description
`DoStateCheckpoint::run` computes a `position_state_checkpoint_hashes` vector whenever `execution_output.compute_trading_native_state_roots` is set [1](#0-0) , and `DoLedgerUpdate::run` feeds those hashes into `assemble_transaction_infos`, which builds the `TransactionInfo`s that get hashed into the transaction accumulator [2](#0-1) . This means the position-state (native-trading) root is a first-class, consensus-committed part of `TransactionInfoV1`, on par with the write-set and event hashes.

However, `ensure_match_transaction_info` — the function whose job is to prove a `TransactionOutput` is consistent with a given `TransactionInfo` — only checks status, gas, write-set hash and event-root hash, and explicitly documents that it skips the checkpoint hashes:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
``` [3](#0-2) 

This is the same integrity-invariant class as the seed report: a proof/verification field that is supposed to reflect updated state actually still reflects an earlier/legacy computation and is silently accepted. Here, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on, the position-state root becomes part of the authenticated, accumulator-committed `TransactionInfo`, but the one function responsible for cross-checking re-executed output against that committed `TransactionInfo` never inspects the field, so a mismatch is never surfaced as an error.

### Impact Explanation
`ensure_match_transaction_info` is used by `db-tool`'s `replay_on_archive` verifier (`storage/db-tool/src/replay_on_archive.rs`) to attest that a chain segment replays deterministically to the committed ledger [4](#0-3) , and by the debugger/CLI replay paths (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) that reference the same helper. Because the comparator never checks the position-state checkpoint hash, any divergence between locally re-executed trading-native state and the historically committed, accumulator-bound position-state root (e.g. from a storage bug, a non-deterministic native-trading computation, or corrupted archived data) will pass replay-verify as "OK". This defeats the entire purpose of the state-integrity gate for this subsystem: a wrong accumulator/proof-bound value is accepted as valid by the tooling meant to catch exactly that class of corruption. This is gated behind the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag [5](#0-4) , so today it is a latent gap rather than an active mainnet divergence, but the code, comment, and feature-flag plumbing all confirm the exact defect and its downstream detection blind spot.

### Likelihood Explanation
Low likelihood today because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is off by default; the gap only becomes exploitable/relevant once that feature is turned on for the native-trading state roots. However, the code explicitly documents this as a known TODO that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`", indicating the team is aware the omission would become a real problem at that point, and any premature enablement (or reliance on replay-verify results in the interim on a build that has the flag on) would silently hide state-root corruption.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `txn_info.state_checkpoint_hash()`/hot-state hash and, specifically, `position_state_checkpoint_hash` against the values computed from local re-execution, and fail loudly on mismatch — as the existing TODO comment already prescribes — before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled in production.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-logic gap, not an execution-time attack. The proof is the code path itself: `DoStateCheckpoint`/`DoLedgerUpdate` commit `position_state_checkpoint_hash` into `TransactionInfoV1` and the transaction accumulator [1](#0-0) [2](#0-1) , while `ensure_match_transaction_info` — the function relied on by replay-verify tooling — never reads or compares that field [3](#0-2) . Any test that (1) enables `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, (2) constructs a `TransactionOutput` whose native-trading writes hash to a different position-state root than the one baked into a given `TransactionInfo`, and (3) calls `ensure_match_transaction_info` would observe `Ok(())` instead of an error, demonstrating the gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
