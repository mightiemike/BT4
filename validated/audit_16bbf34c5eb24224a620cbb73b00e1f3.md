### Title
Legacy double-precision Bancor-formula math in `ExchangeProcessor` causes systematic swap-output miscalculation and fund loss - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Sherlock report describes a fee-calculation subsystem that combines two independent, small rounding/truncation steps into a compounded, sometimes 100%-magnitude error, because the underlying math is done with a low-precision representation (fixed integer `DENOM` and integer-only percentage buckets) instead of full precision, and consistently rounds in one direction. `java-tron`'s TRC10 `Exchange` (Bancor-style AMM) swap math has an equivalent structural weakness: the default/legacy code path in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` performs the entire bonding-curve calculation with IEEE-754 `double` arithmetic and `Math.pow`, then truncates to `long` with `(long) issuedSupply` / `(long) exchangeBalance`. This is reachable from any anonymous broadcast transaction (`ExchangeTransactionContract`), and the repository itself contains a hardened, `BigDecimal`-based replacement (`SafeExchangeProcessor`) that is only used when a chain-governance proposal (`ALLOW_HARDEN_EXCHANGE_CALCULATION`) has been passed — i.e. the imprecise path is the default, exactly analogous to the Sherlock finding where a fee subsystem silently underpays/overpays due to unaddressed precision loss until hardened.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations based on a `hardenedCalc` boolean: [1](#0-0) 

The default (legacy) `ExchangeProcessor` performs the entire Bancor bonding-curve calculation using `double`: [2](#0-1) 

This mirrors the report's two compounding sources of loss:
1. Like the fixed `DENOM` in `math.vy`, the `double` type has finite (53-bit) mantissa precision; combined with `Math.pow`'s inherent floating-point error for the fractional exponents `0.0005` and `2000.0`, the result diverges from the exact bonding-curve value, especially for extreme balance ratios.
2. The final truncation `(long) issuedSupply` / `(long) exchangeBalance` always rounds toward zero, which — exactly like the utilization/`scale` truncation in the report — silently discards fractional token units on every single swap, systematically biasing the pool.

The project's own regression test proves the divergence is not negligible: for the same swap inputs, the legacy `ExchangeProcessor` (`useStrictMath=false` or `true`) produces a **different** result than the `BigDecimal`-based `SafeExchangeProcessor`, across dozens of realistic-sized swaps: [3](#0-2) 

The hardened, precision-preserving replacement already exists in the codebase: [4](#0-3) 

but it is gated behind a dynamic property that is only flipped by an approved governance proposal, exactly like the "hardening" flags seen elsewhere in this repo for the same class of bug (`allowHardenExchangeCalculation`, `allowHardenResourceCalculation`): [5](#0-4) 

Until that proposal is passed on-chain, every `ExchangeTransactionContract` swap (any TRC10/TRX pair, invoked by any account via a normal broadcast transaction, no privileges required) executes through the imprecise, truncating `double` path.

### Impact Explanation
Every `ExchangeTransactionContract` swap through an `Exchange` pool that has not yet had the hardening proposal applied computes `buyTokenQuant` via lossy floating-point math and floor-truncation. This is directly analogous to the report's "fee precision loss": each individual swap's error may look small, but it is systematic (always in the direction of `(long)` truncation toward zero) rather than random, so it compounds across many swaps against the same pool. Because `firstTokenBalance`/`secondTokenBalance` are updated using the (already lossy) `buyTokenQuant` on every transaction, and later swaps' outputs are derived from these polluted balances, the pool's internal `supply` and reserve accounting can drift from the mathematically correct invariant over time — i.e., real value can leak from (or be systematically extracted from) the liquidity pool, corresponding to the report's "loss of funds" / "underpaid parties" impact class, and is exchange/market-math accounting corruption reachable from an unprivileged broadcast transaction.

### Likelihood Explanation
High reachability: `ExchangeTransactionContract` is a standard, permissionless transaction type that any account can broadcast against any active `Exchange` pool; no special key, node role, or peer position is required. The only condition is that the hardening proposal (`ALLOW_HARDEN_EXCHANGE_CALCULATION`) has not been passed for that chain/pool, which is the default state and the repository's own test suite demonstrates the legacy path yields a different (i.e., wrong per the project's own hardened reference implementation) result on ordinary-sized inputs, not just edge cases — so the divergence occurs routinely, not merely under contrived extremes.

### Recommendation
Make the `BigDecimal`-based `SafeExchangeProcessor` (or an equivalent full-precision integer/BigInteger implementation) the unconditional default for all `Exchange` transaction/inject/withdraw math rather than gating it behind a proposal that must be separately voted in; if backward compatibility requires a transition proposal, ensure it is enabled by default for new chains/mainnet parity and add continuous fuzz/differential testing (as already begun in `ExchangeProcessorTest`) comparing the legacy and hardened paths across the full input domain to quantify and bound the accumulated pool drift before hardening is enabled.

### Proof of Concept
The existing repository test already demonstrates the core divergence (legacy vs. hardened math yielding different swap outputs for identical inputs): [6](#0-5)

    long newBalance = balance + quant;

    long out = (long) issuedSupply;
    supply += out;

    return out;

        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
