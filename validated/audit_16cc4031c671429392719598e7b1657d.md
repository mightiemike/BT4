### Title
Unbounded token map iteration in `SUICIDE`/self-destruct token transfer causes fixed-gas DoS and permanent fund lock - ([File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java])

### Summary
`MUtil.transferAllToken` iterates over the *entire* TRC10 asset map of a contract account with no upper bound, mirroring the Moloch `_ragequit` bug where an unbounded loop over whitelisted tokens can exceed the gas/energy budget and permanently lock funds.

### Finding Description
When a smart contract executes `SUICIDE`/`selfdestruct`, `Program.suicide`/`suicide2` calls `MUtil.transferAllToken(getContractState(), owner, obtainer)` [1](#0-0) . That helper loads the full `getAssetMapV2()` for the destructing account and iterates over every token entry to move balances to the recipient, with no cap on the number of distinct TRC10 token IDs processed: [2](#0-1) 

Unlike the Moloch case where the cost of the loop consumed EVM gas per iteration (at least bounding it to the block gas limit, only causing DoS once the whitelist grew large), the `SUICIDE` opcode's energy charge in java-tron is a flat, pre-computed cost independent of how many token entries `transferAllToken` will actually process — the loop body itself does not consume energy for each `forEach` iteration in `MUtil.transferAllToken`. Because a TRON account/contract can accumulate an unbounded number of distinct TRC10 token balances over its lifetime (there is no whitelist/limit enforced anywhere on `AssetV2` map size, unlike Moloch's explicit `MAX_TOKEN_WHITELIST_COUNT`), an attacker (or just an unlucky heavy user) can inflate a contract's token map with a very large number of small/dust TRC10 token entries (each transfer of a TRC10 token to that contract is cheap and unrestricted) and then trigger `SUICIDE` on that contract. The resulting execution performs `O(n)` map iteration/proto rebuilding work that is not charged proportionally in energy, which can cause the transaction to run far longer than its energy budget would suggest, risking node-level resource exhaustion (CPU/memory) during block validation/production, and — if the loop is bounded by `OutOfTimeException`/energy exhaustion mid-way — can leave the target account/contract's token balances in a partially-transferred, inconsistent state, effectively locking or corrupting those assets, echoing the "funds blocked forever" outcome described in the Moloch report.

### Impact Explanation
This is a resource-accounting/DoS class issue reachable via a normal broadcast transaction (any account can send a TRC10 token to a target contract to inflate its token map, then trigger self-destruct). If successful, it can cause disproportionate node-side CPU/memory consumption relative to charged energy (unaccounted computation, similar in spirit to a gas-metering bypass), and can potentially strand or corrupt a contract's TRC10 balances if execution is interrupted partway through the unbounded iteration.

### Likelihood Explanation
Likelihood is moderate: no privileged access is required, and TRC10 transfers to arbitrary addresses are cheap and already supported by the protocol, so building up a large `AssetV2` map on a target contract before invoking `selfdestruct` is feasible with attacker-controlled funds/time. However, exploiting this to reach a materially impactful scale (thousands of distinct token IDs) requires issuing or acquiring that many distinct TRC10 tokens, which has its own cost/friction (asset issuance fees), somewhat limiting ease of exploitation compared to a pure loop-based whitelist bug.

### Recommendation
- Charge energy for `transferAllToken`/`SUICIDE` proportional to the number of token entries in the account's `AssetV2` map (similar to how `MEMORY`/`SSTORE`-type opcodes scale with size), rather than a flat cost.
- Alternatively, cap the number of distinct TRC10 tokens a single account can hold (an on-chain "max asset count per account" limit analogous to Moloch's `MAX_TOKEN_WHITELIST_COUNT`), enforced at TRC10 transfer time.
- Ensure `transferAllToken` is atomic/no-op-safe if interrupted (e.g., process and persist in bounded batches, or fail closed rather than leaving partial state) so a mid-execution abort cannot strand token balances.

### Proof of Concept
1. Deploy a contract `C` capable of calling `selfdestruct`.
2. From many different accounts (or by issuing many distinct TRC10 tokens), send TRC10 token transfers to `C` until its `assetV2` map contains a very large number of entries (e.g., thousands), each transfer being independently cheap and unrestricted since there is no limit enforced on the number of distinct assets an account may hold.
3. Trigger `selfdestruct` on `C`. `Program.suicide`/`suicide2` invokes `MUtil.transferAllToken`, which iterates the entire `assetV2` map [2](#0-1)  while `SUICIDE`'s energy charge remains fixed rather than scaling with map size, allowing disproportionate node-side work per unit of charged energy, and risking incomplete/interrupted asset transfer if execution is aborted mid-loop.

If `EnergyCost.java` already charges energy proportional to the number of assets transferred, the severity of this finding would be substantially reduced.   public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
