Confirmed finding: `citrea_network_to_chain_id` maps `Network::Nightly` and `Network::TestNetworkWithForks` to the **same value, `5665`**, while `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` in `crates/light-client-prover/src/circuit/initial_values.rs` default to **byte-for-byte identical public keys** (same env-var fallbacks for all 5 members) unless operators override the `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` env vars for one of the deployments.

### Title
Cross-network replay of `BatchProofMethodId` inscriptions between `Network::Nightly` and `Network::TestNetworkWithForks` due to colliding `chain_id` and shared default council keys - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
`citrea_network_to_chain_id` returns `5665` for both `Network::Nightly` and `Network::TestNetworkWithForks`, so the chain-id check at `crates/light-client-prover/src/circuit/mod.rs:544-548` does not distinguish these two networks. Combined with `initial_values.rs` defaulting both networks' council public keys to identical constants, a `BatchProofMethodId` inscription signed by the council for one of these networks passes `verify_method_id_security_council` and the chain-id check on the other network's light-client-prover deployment.

### Finding Description
The binding claimed by the guard is: `circuit_chain_id (== citrea_network_to_chain_id(network of THIS deployment))` should equal `body.chain_id (== citrea_network_to_chain_id(network the council intended to authorize))`, and this equality should only hold when the deployment's network and the intended network are the same, per [1](#0-0) .

However, `citrea_network_to_chain_id` assigns `5665` to both `Network::Nightly` and `Network::TestNetworkWithForks`: [2](#0-1) . This means `body.chain_id` computed for a `TestNetworkWithForks` upgrade is numerically identical to one computed for `Nightly`, so the guard cannot tell them apart.

The second half of the check, `verify_method_id_security_council`, verifies signatures against `method_id_upgrade_authority_da_public_keys` passed into `run_l1_block` from `initial_values.rs`. The default (unoverridden) values of `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` are identical for all 5 members (same env-var names and same hardcoded fallback hex keys), per [3](#0-2)  versus [4](#0-3) .

If a `TestNetworkWithForks` deployment is run without setting the `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` env vars to distinct values from the Nightly deployment (both default to the same keys), a `BatchProofMethodId` inscription signed by the council for `Nightly` (`chain_id = 5665`, signed with the shared default keys) can be replayed verbatim onto a `TestNetworkWithForks` light-client-prover node (also `chain_id = 5665`, same default keys), and vice versa. The circuit's guards at `crates/light-client-prover/src/circuit/mod.rs:544-559` both pass, and `BatchProofMethodIdAccessor::insert` installs the method id on the "wrong" network.

### Impact Explanation
If exploited, an attacker (or anyone who can inscribe on Bitcoin and knows a Nightly/TestNetworkWithForks method-id upgrade transaction, which is public once broadcast) can replay it to install a batch-proof method id on the sibling network that the council never intended to authorize for that specific deployment. This is a "method-id upgrade accepted that was never authorised" style Critical impact per the rules, but it is scoped strictly to the relationship between `Nightly` and `TestNetworkWithForks` — both are test/staging networks, not `Mainnet` or `Testnet` (those have distinct chain ids: `4114`, `5115`, `62298`, and distinct default council keys). This does not affect Mainnet or Testnet since their chain ids and keys are unique.

### Likelihood Explanation
This depends entirely on operational key management that this repo does not fully control: `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` and the Nightly equivalents are populated from the *same* environment variable names (`METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1..5`), per [5](#0-4) . Whether a real deployment sets different keys per network at build/deploy time is a configuration matter I cannot verify from static code alone — if operators do differentiate keys per network via distinct env values at build time, the replay fails at `verify_method_id_security_council`. I could not find further evidence in the indexed portion of the repo (e.g., CI/deploy scripts, `resources/configs/*`) confirming whether Nightly and `TestNetworkWithForks` builds are given distinct override values in practice; this is a genuine limitation of the available index.

### Recommendation
Assign distinct chain ids to every `Network` variant in `citrea_network_to_chain_id` (Nightly and TestNetworkWithForks currently collide at `5665`), and ensure `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` uses its own distinct env-var names/fallbacks rather than reusing `NIGHTLY`'s.

use sov_rollup_interface::Network;
use crate::circuit::citrea_network_to_chain_id;

#[test]
fn chain_ids_are_pairwise_distinct() {
    let variants = [
        Network::Mainnet,
        Network::Testnet,
        Network::Devnet,
        Network::Nightly,
        Network::TestNetworkWithForks,
    ];
    for i in 0..variants.len() {
        for j in (i + 1)..variants.len() {
            assert_ne!(
                citrea_network_to_chain_id(variants[i]),
                citrea_network_to_chain_id(variants[j]),
                "chain id collision between {:?} and {:?}",
                variants[i], variants[j]
            );
        }
    }
    // FAILS today: Nightly (5665) == TestNetworkWithForks (5665)
}
