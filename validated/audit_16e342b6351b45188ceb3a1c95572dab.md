### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.fromAccountsList`/`toAccountsList` allows third-party DoS of resource delegation/undelegation for a victim account - (File: `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java`)

### Summary
When the legacy (pre-optimization) delegated-resource accounting path is active, `FreezeBalanceActuator` and `UnfreezeBalanceActuator` maintain, per account, a `DelegatedResourceAccountIndexCapsule` containing `fromAccountsList`/`toAccountsList` — plain repeated fields that are only ever appended to and linearly scanned with `List.contains()`. Any unprivileged account can call `freezebalance` with an arbitrary `receiverAddress`, which appends an entry to the *receiver's* `fromAccountsList` regardless of the receiver's consent. By repeating this from many distinct attacker-controlled owner accounts, a third party can inflate a victim account's index list without limit, exactly mirroring the Curves `ownedCurvesTokenSubjects` growth pattern (unbounded, storage-array, victim-uncontrollable, iterated with linear `contains()`/`remove()` operations).

### Finding Description
In the legacy delegation path (guarded by `!dynamicPropertiesStore.supportAllowDelegateOptimization()`), `FreezeBalanceActuator.delegateResource()` does: [1](#0-0) 

For every freeze-with-delegation call, the code loads the receiver's index capsule, checks with `List.contains()` whether the owner's address is already recorded, and if not, calls `addFromAccount()`, which unconditionally appends: [2](#0-1) 

Because `receiverAddress` is fully attacker-controlled and each new "owner" account is a fresh, freely creatable identity, an attacker can freeze a minimal balance from an arbitrary number of throwaway accounts and delegate to the same victim `receiverAddress` each time. Each call appends a new entry to the victim's `fromAccountsList` — the victim has no transaction that removes entries they didn't create, and removal only happens when the *specific delegating owner* later calls `unfreezeBalance`/undelegate for that pair: [3](#0-2) 

This is structurally identical to the reported Curves bug: (1) a storage-backed array grows without bound, (2) growth is driven by third parties acting on a chosen victim address, (3) the victim has no mechanism to prune entries added by others, and (4) list operations (`contains()`, `remove()`) are linear scans whose cost grows with the list size, degrading with every additional attacker-injected entry.

### Impact Explanation
Each subsequent freeze/delegate or unfreeze/undelegate operation touching the victim's index (as owner or receiver) becomes progressively more expensive due to the linear `contains()`/`remove()` scans over an attacker-inflated list, and the serialized `DelegatedResourceAccountIndex` protobuf grows without bound in the account's on-disk index store. This can degrade the responsiveness of resource-delegation operations for the targeted account and increase storage bloat, a Denial-of-Service class impact on legitimate delegation flows for the victim, analogous to the H-01 Curves finding (root cause acknowledged as valid, severity elevated because it's forceable by unprivileged third parties). Unlike the Curves case, this specific legacy path is only active while the `AllowDelegateOptimization` proposal is not enabled on the network, so the practical severity depends on that configuration flag's chain state.

### Likelihood Explanation
Exploitation only requires broadcasting ordinary `FreezeBalanceContract` transactions with delegation, an unprivileged and cheap action (bounded only by the minimal freeze amount and account creation cost), repeated against a fixed victim `receiverAddress`. No special permissions, keys, or node/peer compromise are needed. The likelihood is contingent on the chain still running with `AllowDelegateOptimization` disabled (i.e., the legacy accounting path in `FreezeBalanceActuator`/`UnfreezeBalanceActuator` still reachable) — this could not be fully confirmed within available tool calls, since the default/proposal state of `supportAllowDelegateOptimization` could not be verified from `DynamicPropertiesStore.java` in the time available.

### Recommendation
- Bound the size of `fromAccountsList`/`toAccountsList` or migrate all delegation accounting to the `V2` prefix-based scheme (`delegateV2`/`unDelegateV2` in `DelegatedResourceAccountIndexStore`) which does not maintain an in-place growing list per account, eliminating this legacy attack surface entirely.
- If legacy support must be retained, enforce a maximum list size per account and reject further delegations that would exceed it, or require the receiver's list entry to be prunable in O(1) via a set-like keyed store instead of an appended list.
- Ensure the `AllowDelegateOptimization` proposal is enabled network-wide and consider removing/deprecating the pre-optimization delegation code path.

### Proof of Concept
1. Attacker creates N throwaway accounts (`A1`...`AN`).
2. For each `Ai`, submit `FreezeBalanceContract` with `receiver_address = Victim` (delegated freeze), triggering `FreezeBalanceActuator.delegateResource()`.
3. Each call appends `Ai` to `Victim`'s `DelegatedResourceAccountIndexCapsule.fromAccountsList` via `addFromAccount()` since `Ai` was never previously recorded.
4. Repeating this at scale grows `Victim`'s index list unboundedly; subsequent freeze/unfreeze/undelegate operations involving `Victim` incur growing linear-scan costs (`contains()`/`remove()` over the inflated list), and the account's stored index entry grows in size — a third-party-driven, victim-uncontrollable resource degradation, mirroring the Curves `ownedCurvesTokenSubjects` DoS pattern.
