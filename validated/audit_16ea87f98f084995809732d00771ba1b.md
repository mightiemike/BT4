### Title
`AccountLocks::try_lock_transaction_batch` splits check and lock into two non-atomic passes, allowing multiple conflicting writers in the same batch to all succeed - ([File: accounts-db/src/account_locks.rs])

### Summary
`try_lock_transaction_batch` first runs `can_lock_accounts` for every transaction in the batch against the *pre-batch* lock state (this loop never mutates `self`), and only afterwards runs `lock_accounts` unconditionally for every transaction that passed. Because the first pass does not account for locks that other transactions in the same batch are about to take, N transactions in one batch that all write the same account W will all pass the check and all get locked, returning `Ok(())` for every one of them instead of only the first.

### Finding Description
```rust
pub fn try_lock_transaction_batch<'a>(
    &mut self,
    mut validated_batch_keys: Vec<TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>>,
) -> Vec<TransactionResult<()>> {
    validated_batch_keys.iter_mut().for_each(|validated_keys| {
        if let Ok(keys) = validated_keys.as_ref()
            && let Err(e) = self.can_lock_accounts(keys.clone())
        {
            *validated_keys = Err(e);
        }
    });

    validated_batch_keys
        .into_iter()
        .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
        .collect()
}
``` [1](#0-0) 

`can_lock_accounts` is a read-only check against `self.write_locks` / `self.readonly_locks` and does not mutate state: [2](#0-1) 

The first loop (lines 28-34) iterates the whole batch calling `can_lock_accounts` against `self`, but `self` is not updated between iterations — only entries already locked *before this call* are rejected. Consequently, if transaction #1 and transaction #2 in the same batch both write account W, and W was not already locked prior to the call, both pass `can_lock_accounts` in the first pass (both see W as free). The second loop (lines 36-39) then unconditionally calls `lock_accounts` (which just increments the write-lock counter, `lock_write`, line 107-109) for every entry that is still `Ok`, with no re-check. As a result, both transactions end up with `write_locks[W] == 2` and both return `Ok(())` from `try_lock_transaction_batch`, rather than only the first succeeding and the rest returning `AccountInUse`.

This breaks the fundamental exclusivity invariant that `AccountLocks` exists to enforce: within a single call, two transactions can simultaneously hold what should be an exclusive write lock on the same account, defeating the purpose of the "try" (check-then-act) locking API for anything but pre-existing (older-batch) conflicts.

### Impact Explanation
If a caller submits a batch (e.g., a group of transactions selected for parallel execution/scheduling) containing multiple write-conflicting transactions on the same account, this bug allows more than one of them to be considered "locked" and proceed to execution/commit concurrently, violating the single-writer guarantee that downstream execution and commit logic rely on. This is a correctness/concurrency-safety violation in a scope explicitly called out as "Critical" for `try_lock_transaction_batch`, matching the "double-writer race enabling theft/corruption of W" category and mapping to Solana's "cross-account/account corruption" and consensus-safety bounty classes if the code path is reachable from scheduling multiple transactions against the same account within one batch.

### Likelihood Explanation
No special privileges are required beyond being able to submit a batch of ordinary transactions writing to a common account — the batch construction/dispatch is internal to whichever caller invokes `try_lock_transaction_batch` (e.g., accounts.rs / scheduler), not attacker code. An attacker only needs to get several of their own write-conflicting transactions grouped into the same lock-batch. Whether this is reachable depends on the calling context in `accounts-db/src/accounts.rs`, which I was unable to fully inspect in this session due to tool budget — I could not confirm whether that caller pre-deduplicates conflicting writes within a batch before calling `try_lock_transaction_batch`, or whether batches are constructed such that conflicting writers can never co-occur (e.g., if the batch is always a single already-locked, already-conflict-free selection from a scheduler that guarantees no intra-batch conflicts). This uncertainty must be resolved by reading `accounts.rs`'s call site and the scheduler/replay code that constructs the `validated_batch_keys` argument before this can be confirmed as end-to-end exploitable on mainnet.

### Recommendation
Make the check-then-lock atomic per transaction within the same pass so that a transaction's lock success is visible to subsequent transactions in the same batch, e.g.:
```rust
validated_batch_keys
    .into_iter()
    .map(|keys| {
        keys.and_then(|keys| {
            self.can_lock_accounts(keys.clone())?;
            self.lock_accounts(keys);
            Ok(())
        })
    })
    .collect()
```
This ensures each transaction's lock decision incorporates all locks taken by earlier transactions in the same batch, not just locks that existed prior to the call.

### Proof of Concept
Add a unit test to `accounts-db/src/account_locks.rs`:
```rust
#[test]
fn test_try_lock_transaction_batch_conflicting_writes_same_batch() {
    let mut locks = AccountLocks::default();
    let w = Pubkey::new_unique();

    let batch: Vec<TransactionResult<_>> = (0..3)
        .map(|_| Ok(std::iter::once((&w, true))))
        .collect();

    let results = locks.try_lock_transaction_batch(batch);

    // Expected (correct) behavior: only the first transaction should lock W.
    assert_eq!(results[0], Ok(()));
    assert_eq!(results[1], Err(TransactionError::AccountInUse));
    assert_eq!(results[2], Err(TransactionError::AccountInUse));
}
```
Running this against the current implementation is expected to fail because `results[1]` and `results[2]` will also be `Ok(())`, demonstrating that multiple writers to `w` are simultaneously "locked" within a single `try_lock_transaction_batch` call.

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }
