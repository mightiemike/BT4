### Title
Rounding-inconsistent Bancor-formula exchange math in `ExchangeProcessor` allows dust-accumulation free-token extraction - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The legacy (default) TRC10 `Exchange` swap math in `ExchangeProcessor` computes swap outputs with double-precision floating point and truncates the result with a plain `(long)` cast in both `exchangeToSupply` and `exchangeFromSupply`. Because this truncation is applied identically regardless of swap direction, it does not guarantee the "round in favor of the pool" invariant that AMM-style formulas require (the same rounding-direction flaw described in the StableMath report). An attacker can exploit this by issuing a sequence of small `ExchangeTransactionContract` swaps (buy then sell back) via ordinary broadcast transactions and net a positive token balance extracted from the pool, exactly as in the reported "free swap" exploit pattern. [1](#0-0) 

### Finding Description
`ExchangeCapsule.transaction()` is the entry point used by `ExchangeTransactionActuator.execute()` when a user broadcasts an `ExchangeTransactionContract` to swap TRX/TRC10 tokens inside a bancor-formula liquidity pool (`Exchange`/`ExchangeV2` object). By default (unless the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter has been activated via a witness proposal), it selects `ExchangeProcessor` rather than `SafeExchangeProcessor`: [2](#0-1) 

`ExchangeProcessor.exchange()` performs a Bancor "relay token" conversion in two steps — `exchangeToSupply` (sell-token → internal relay supply) and `exchangeFromSupply` (relay supply → buy-token) — both of which compute a `double` and truncate toward zero via `(long) issuedSupply` / `(long) exchangeBalance`: [3](#0-2) 

This is structurally the same bug class as `StableMath._calcInGivenOut`/`_getTokenBalanceGivenInvariantAndAllOtherBalances`: the swap math is composed of two chained non-linear operations (here, two `pow()` calls through an internal invariant, "supply"), and each step's rounding/truncation is not consistently biased so that the pool never loses value. Because truncation always rounds toward zero rather than "down for the pool's benefit" on both legs of a round trip, a carefully chosen pair of swaps (sell token A for B, then sell the received B back for A) can yield more A back than was originally paid in, for suitably chosen dust-sized balances/quantities — mirroring the Eve exploit in the report (sell 1 wei, receive N wei, sell N wei back, receive more than 1 wei).

The project's own test suite acknowledges the double-precision method is imprecise and diverges from a `BigDecimal`-based "hardened" implementation (`SafeExchangeProcessor`) that explicitly documents rounding via `RoundingMode.DOWN`/`HALF_UP`, and that a `testStrictMath` test explicitly asserts the legacy floating results differ from the strict/hardened ones: [4](#0-3) 

The fix (`SafeExchangeProcessor` + `hardenedCalc`/`allowHarden()` gate driven by `ALLOW_HARDEN_EXCHANGE_CALCULATION`) exists in the codebase but is opt-in via governance proposal, meaning the vulnerable legacy path (`ExchangeProcessor`, plain double math) remains the default/active code path for existing and newly created `Exchange` pools until the proposal is passed by 2/3 of witnesses. [5](#0-4) [6](#0-5) 

### Impact Explanation
If exploitable, an attacker can drain value from a TRC10 `Exchange` liquidity pool (funded by other users via `ExchangeCreateContract`/`ExchangeInjectContract`) by repeatedly performing round-trip swaps that net a positive balance each cycle, extracting real TRX/TRC10 asset value at no cost. This is an unauthorized asset/accounting corruption within the on-chain exchange/market math subsystem, reachable purely via ordinary broadcast transactions (`ExchangeTransactionContract`) from any account — no privileged role required.

### Likelihood Explanation
Reaching the vulnerable code requires only a normal account broadcasting `ExchangeTransactionContract` transactions against an existing `Exchange` pool (many already exist on mainnet, created before/without the harden proposal). Finding profitable dust round-trip parameters requires numeric search (as in the original report's exploit scenario), so this is a "High difficulty" class issue rather than a trivial one — it needs specific balance/quantity combinations where accumulated truncation happens to favor the trader. It's more likely to be profitable when pool balances are small/imbalanced (small-liquidity or newly created pools), similar to the original report's example values.

### Recommendation
- For any `Exchange`/`ExchangeV2` object still routed through `ExchangeProcessor` (i.e., pools operating while `ALLOW_HARDEN_EXCHANGE_CALCULATION` is not yet active), audit whether small-balance pools can be driven into a dust round-trip profit state, and consider making the hardened `SafeExchangeProcessor` path mandatory (remove the double-precision legacy path) rather than opt-in via proposal.
- Ensure `SafeExchangeProcessor`'s two internal roundings (`exchangeToSupply` rounds the burned "relay" down for the seller's benefit via `RoundingMode.DOWN` after negation, `exchangeFromSupply` also rounds `DOWN`) are proven, ideally with a formal/fuzz (e.g., property-based or Echidna-equivalent for Java) test asserting that for any sequence of swaps, `sum(tokens_out) <= sum(tokens_in)` scaled by pool invariant, i.e., no round trip can ever yield net positive extraction.
- Add regression tests specifically targeting round-trip (buy-then-sell-back) sequences with small/dust quantities against both `ExchangeProcessor` and `SafeExchangeProcessor` to detect any residual free-token extraction, analogous to the Trail of Bits StableMath exploit scenario.

### Proof of Concept
Conceptual PoC (mirrors the external report's exploit shape), using the existing `ExchangeCapsule.transaction` API exercised by `ExchangeTransactionActuator`:
1. Attacker identifies (or creates via `ExchangeCreateContract`) a low-liquidity `Exchange` pool with balances `(balA, balB)`.
2. Attacker submits `ExchangeTransactionContract` selling a small `dust` amount of token A, receiving `q` of token B, via the legacy (non-hardened) `ExchangeProcessor.exchange()` path (default when `ALLOW_HARDEN_EXCHANGE_CALCULATION` is inactive).
3. Attacker immediately submits a second `ExchangeTransactionContract` selling the received `q` of token B back into the same pool.
4. Due to the independent double-precision truncations in `exchangeToSupply`/`exchangeFromSupply` on each leg, the attacker can receive back more of token A than was paid in step 2 for certain `(balA, balB, dust)` combinations — net free tokens, repeatable to drain the pool.

This cannot be fully confirmed as exploitable without running the exact numeric search (as ToB did for `StableMath`) against `ExchangeProcessor`'s formula; the code path, default-enabled status, and structural rounding inconsistency are all confirmed in the repository, but a concrete profitable `(balA, balB, dust)` triple was not computed as part of this analysis.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
