### Title
Unsigned-subtraction difficulty retarget miscalculation on time-warp header chains - (File: crates/bitcoin-da/src/verifier.rs)

### Summary
`calculate_new_difficulty` in `crates/bitcoin-da/src/verifier.rs` computes the actual timespan of a Bitcoin difficulty epoch as an unsigned `u32` subtraction, `last_timestamp - epoch_start_time`, mirroring Bitcoin Core's signed `int64_t nActualTimespan = pindexLast->GetBlockTime() - pindexFirst->GetBlockTime()`. Because Citrea's header-chain validation (`verify_timestamp`) only requires each block's timestamp to exceed the *median* of the previous 11 blocks' timestamps rather than being strictly monotonically increasing relative to the whole chain, it is consensus-legal for the last block of a 2016-block epoch to carry an earlier timestamp than the epoch's first block ("time-warp" pattern). When that happens, the unsigned subtraction underflows.

### Finding Description
`verify_header_chain_mainnet`/`verify_header_chain_signet` call `calculate_new_difficulty` on the last block of every epoch: [1](#0-0) 

```

    epoch_start_time: u32,
    last_timestamp: u32,
    ...
) -> [u8; 32] {
    let mut actual_timespan = last_timestamp - epoch_start_time;
    ...
}
``` [2](#0-1) 

The only timestamp check performed per-block is the median-time-past rule: [3](#0-2) 

This rule does not prevent `block_time` (the epoch's last block) from being *lower* than `epoch_start_time` (the epoch's first block), as long as it stays above the median of the most recent 11 timestamps. This is the same class of assumption error as the reference report: code assumes a timestamp field only ever advances relative to an earlier reference point, but the underlying protocol allows it to regress as long as a narrower, local monotonicity constraint is satisfied.

No `overflow-checks` profile setting is present anywhere in the workspace (`Cargo.toml`, guest crates), so in a release build (the mode in which guest ELFs/method-ids for the zkVM are actually built) the subtraction wraps instead of panicking, per Rust's default release semantics. The wrapped `actual_timespan` becomes a huge value close to `u32::MAX`, which is then clamped by the existing bound check to `expected_epoch_timespan * 4`, producing a spurious "maximum allowed" timespan instead of the correct near-zero/negative timespan that Bitcoin Core's signed arithmetic would compute and clamp to `expected_epoch_timespan / 4`.

### Impact Explanation
This corrupts the difficulty-retarget computation used by `verify_header_chain_common` for validating every subsequent epoch's proof-of-work target (`current_target_bits`), inside both the light-client circuit and, transitively, wherever `BitcoinVerifier::verify_header_chain_*` is trusted to establish the canonical DA header chain used to source sequencer commitments and batch proofs. A miscomputed (larger/looser) target lets a chain with materially less proof-of-work than genuine Bitcoin consensus requires be accepted as valid by `verify_target_hash`, breaking the DA-integrity binding between the light client's internally tracked Bitcoin PoW state and the real Bitcoin chain. This is the "forged DA inclusion" / accepted-false-header-chain class explicitly listed as Critical impact.

### Likelihood Explanation
Producing this specific miscalculation requires an epoch (2016 blocks, ~2 weeks) where the *last* block's timestamp is lower than the *first* block's timestamp while every individual block still satisfies the local median-time-past rule — this is the well-documented "time-warp" pattern from Bitcoin/altcoin history, achievable by a miner without needing majority hashrate, only patience in choosing timestamps within protocol-allowed bounds. It does not require a majority-hashrate attacker, a privileged role, or any deployment misconfiguration, so it is not excluded by the scan rules. However, triggering it against the real Bitcoin mainnet chain (whose timestamps are produced by many independent, mostly honest miners) is difficult in practice; it is realistically exploitable primarily by whoever controls block production on the chain being fed to the verifier (e.g., regtest/signet/testnet contexts, or a chain reorg/alternate branch an attacker fully controls), which is a genuine but narrower attack surface than mainnet itself.

### Recommendation
Compute `actual_timespan` using signed arithmetic (e.g. `i64`) as Bitcoin Core does, then clamp the result into `[expected_epoch_timespan/4, expected_epoch_timespan*4]` before casting back to an unsigned type for the difficulty calculation, so that negative/time-warped timespans are handled identically to Bitcoin Core rather than wrapping.

### Proof of Concept
Not executed against a live network; derived from static analysis of `calculate_new_difficulty` and `verify_timestamp`. Conceptually:
1. Attacker controls (or is) the miner sequence for one full 2016-block epoch on the DA chain being verified.
2. Each block's timestamp is chosen to be the minimum value satisfying `block_time > median(prev_11_timestamps)`, while overall drifting the timestamp sequence downward, so that by block 2015 of the epoch, `block_header.time()` is less than `epoch_start_time` (the epoch's first block time), yet every single block passed `verify_timestamp`.
3. On the final block of the epoch, `calculate_new_difficulty(epoch_start_time, last_timestamp, ...)` executes `last_timestamp - epoch_start_time` as `u32`, which underflows/wraps in a release build (no `overflow-checks` enabled anywhere in the workspace), yielding a timespan clamped to the maximum allowed (`expected_epoch_timespan * 4`) instead of the correct minimum, producing an incorrectly loosened `current_target_bits` for the next epoch.

Because this depends on an unusual, hard-to-verify-in-index timestamp sequence and workspace-wide Cargo profile behavior that could not be fully confirmed (I found no `[profile.release] overflow-checks = true` anywhere in `Cargo.toml` or the guest crates, but could not exhaustively rule out a build-time override), this should be validated with a live Devin session that can build the guest binaries and run a concrete regression test feeding a crafted header sequence into `BitcoinVerifier::verify_header_chain_mainnet`/`_signet`.
