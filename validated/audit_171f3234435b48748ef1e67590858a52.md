### Title
One-block maturity-boundary mismatch between `handle_poison_microblock`'s report-time check and `find_mature_miner_rewards`'s payment-time lookup lets a validly-accepted poison report silently fail to slash the coinbase - (File: `stackslib/src/chainstate/stacks/db/transactions.rs`, `stackslib/src/chainstate/stacks/db/accounts.rs`)

### Summary
`handle_poison_microblock` accepts a PoisonMicroblock report as long as `height + MINER_REWARD_MATURITY >= current_height` (i.e. it uses a non-strict boundary, rejecting only when strictly `<`), while the matured-reward payout in `find_mature_miner_rewards` is computed once, at the *start* of block processing for the block at `tip_stacks_height = height + MINER_REWARD_MATURITY`, before that same block's own transactions (including a just-in-time poison report) are applied. This creates exactly one block height at which a poison report is still validly accepted by the network but structurally too late to be seen by the reward computation that matures that exact miner's coinbase.

### Finding Description
The claimed equality is: a poison report accepted at report-time height `H_report` must always be visible to `find_mature_miner_rewards` exactly when `reward_height == mblock_pubk_height`. Tracing both sides:

- `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs:770-803`) rejects only if
```
height.checked_add(MINER_REWARD_MATURITY).expect(...) < current_height
``` [1](#0-0) 
so a report is *accepted* whenever `height + MATURITY >= current_height`, including the boundary case `current_height == height + MATURITY`. `current_height` is `env.global_context.database.get_current_block_height()`, which returns the height of the block currently being constructed/processed (`stackslib/src/clarity_vm/database/marf.rs:569-602`, `clarity/src/vm/database/clarity_db.rs:1185-1188`) [2](#0-1)  — i.e. the block that contains the report transaction itself.

- `find_mature_miner_rewards` (`stackslib/src/chainstate/stacks/db/accounts.rs:985-1041`) computes `reward_height = tip_stacks_height - MINER_REWARD_MATURITY` and looks up `get_poison_microblock_report(clarity_tx, reward_height)` to decide who gets the coinbase for the block being matured. [3](#0-2) 

- Crucially, this lookup runs at the *start* of block setup — for Nakamoto, `get_matured_miner_reward_schedules` / `calculate_matured_miner_rewards` are invoked in `inner_setup_block`, before the block's own transactions are processed (`stackslib/src/chainstate/nakamoto/mod.rs:4570-4579`, `4671-4684`; `stackslib/src/chainstate/nakamoto/tenure.rs:337-411`). [4](#0-3) [5](#0-4)  The equivalent ordering (rewards scheduled/read before the new block's own transactions execute) is the standing architecture for the epoch2.x path as well (`get_scheduled_block_rewards`/`find_mature_miner_rewards` at `stackslib/src/chainstate/stacks/db/blocks.rs:5099-5120`), though I was not able to fully re-confirm every intermediate call in that path within the remaining budget — this should be double-checked against `stackslib/src/chainstate/stacks/db/blocks.rs` around block-append time.

Given the block containing the report is `M = height + MATURITY` (the last block for which `handle_poison_microblock` will still accept the report), and the reward for that miner's block matures precisely when `tip_stacks_height = height + MATURITY = M`, the payout computation for block `M` reads the poison-report table *before* the report transaction inside block `M` is applied. The report is thus stored (validly, per consensus) but one block too late to be visible when `reward_height == mblock_pubk_height` is actually evaluated. Any report submitted at height `< M` is picked up correctly; only the exact boundary block `M` is affected. The check functions cited in the audit rules (`check_tenure_tx`, `verify_signer_signatures`, `validate_vrf_seed`, `validate_*_static`, `common_validate_against_burnchain`, MARF hashing) have no bearing on this maturity-arithmetic ordering issue and do not guard against it.

### Impact Explanation
When a PoisonMicroblock report is submitted in the single boundary block `M = mblock_pubk_height + MINER_REWARD_MATURITY`, the transaction is accepted as valid (not rejected as "matured relative to current height"), and the poison record is written into the trie — but the coinbase reward computation for the offending miner's block runs earlier in the same block's processing (before any of that block's own transactions, including the just-accepted report, are applied), so it never sees the report. The offending miner's coinbase is paid out to the miner unslashed, and the reporter never receives the `POISON_MICROBLOCK_COMMISSION_FRACTION` they would otherwise be entitled to. This is a genuine reward mis-payment/loss (the honest reporter's stake in exposing the fork is worthless at exactly this height, and the offending miner keeps a coinbase they should have forfeited), matching the "block-reward theft/loss" Critical category, since it is not fee-bounded but affects the full block coinbase.

### Likelihood Explanation
This requires no privileged role and no majority stake: any node that knows a microblock pubkey-hash height `H` and the constant `MINER_REWARD_MATURITY` can predict the boundary block `M = H + MATURITY` exactly. The offending miner (who signed the conflicting microblocks) trivially knows `H` for their own tenure. The failure mode is deterministic arithmetic (not probabilistic), so it reproduces on every fork/report whose acceptance transaction lands in block `M` specifically. The main uncertainty is whether an attacker/report submitter can reliably land their report transaction in exactly block `M` (mempool inclusion timing is not fully attacker-controlled), which somewhat limits deterministic exploitability by a third-party reporter, but a self-interested miner benefits passively any time this timing occurs naturally, and the underlying protocol bug is unconditionally present at that height regardless of intent.

### Recommendation
Make the two boundary computations use the same reference point and the same comparison operator. Concretely, either:
- Change `find_mature_miner_rewards`/`get_matured_miner_reward_schedules` to defer reward maturation by one additional block (so that block `M`'s own transactions, including any poison report at that exact height, are committed before the reward for height `M - MATURITY` is computed), or
- Change `handle_poison_microblock`'s acceptance check to strict `<=` becoming `<` one block earlier (reject when `height + MATURITY <= current_height`, i.e. shrink the acceptance window by one block) so that reports are never accepted in the same block where the corresponding reward matures.
Either fix should be accompanied by an explicit invariant/assertion tying the two boundaries together (e.g., a shared helper function) to prevent future regressions.

### Proof of Concept
Rust integration test plan (building on the existing `test_build_microblock_stream_forks` harness in `stackslib/src/chainstate/stacks/tests/block_construction.rs`):
1. Set up a chain with `MINER_REWARD_MATURITY` blocks (use the same small test constant as in existing poison-microblock tests).
2. Have miner A publish a forked microblock stream at block height `H` (recording `mblock_pubk_height = H` via `insert_microblock_pubkey_hash`).
3. Mine blocks up to, but not including, height `M = H + MINER_REWARD_MATURITY`, asserting via `get_poison_microblock_report` that no report yet exists.
4. At block `M`, have the reporter's `PoisonMicroblock` transaction included in that exact block (not earlier).
   - Assert `StacksChainState::process_transaction` succeeds (transaction is *accepted*, proving `handle_poison_microblock`'s report-time boundary check treats `height + MATURITY == current_height` as valid).
   - Assert `get_poison_microblock_report(&mut conn, H)` now returns `Some((reporter, seq))` (the report is durably stored).
5. Inspect the `payments`/matured-reward table (or `get_matured_miner_payment`) for the miner's coinbase at height `H`: assert that the recipient is still the **offending miner**, not the reporter — i.e., the poison-microblock commission was never applied, and the miner's full coinbase balance matches the un-slashed amount.
6. As a control, repeat the same scenario but submit the report at block `M - 1` instead, and assert that in this case the reward-payments table *does* redirect the coinbase (or the commission) to the reporter — demonstrating the one-block discrepancy exists only at the exact boundary `M`.
