## Verdict: Valid finding (algorithmic-complexity DoS)

### Title
Unbounded linear scan of all active ballots on every new-ballot creation enables quadratic-cost amplification via attacker-controlled distinct inbound events - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
`CreateBallot` unconditionally invokes `ExpireBallotsBeforeHeight`, which iterates the *entire* `ActiveBallotIDs` collection on every single new-ballot creation, regardless of how many ballots that particular caller cares about. Because ballot creation is triggered on the first vote for a distinct ballot key derived from attacker-influenced inbound event fields, an attacker who causes many distinct source-chain events to be observed by honest validators can force this O(active-ballot-count) scan to run repeatedly, turning what should be O(1)/O(new-events) work into O(active²) work over a burst window.

### Finding Description
`CreateBallot` (`x/uvalidator/keeper/ballot.go`) always calls `ExpireBallotsBeforeHeight(ctx, blockHeight)` before creating and persisting the new ballot: [1](#0-0) 

`ExpireBallotsBeforeHeight` fully iterates `k.ActiveBallotIDs` — every currently active ballot in the module, not just ballots related to the one being created — fetching each ballot record to check its expiry: [2](#0-1) 

`CreateBallot` is reached via `GetOrCreateBallot`, which is called from `VoteOnInboundBallot`/`VoteOnOutboundBallot` (`x/uexecutor/keeper/voting.go`) any time a universal validator submits the *first* vote for a distinct ballot key: [3](#0-2) 

The ballot key itself is derived from attacker-influenced fields of the inbound event (`GetInboundBallotKey`, keyed on `SourceChain/TxHash/LogIndex/Sender/Recipient/Amount/AssetAddr/RawPayload` per `VoteInbound` in `x/uexecutor/keeper/msg_vote_inbound.go`): [4](#0-3) 

Since honest validators automatically submit `MsgVoteInbound` upon observing any distinct source-chain event, an attacker does not need a malicious/privileged validator — they only need to produce many distinct genuine (or distinctly-keyed) source-chain deposit events. Each such event, once observed, triggers a first-vote → `GetOrCreateBallot` → `CreateBallot` → full scan of `ActiveBallotIDs`. If N ballots remain concurrently active (i.e., not yet finalized/expired) within the expiry window (`DefaultExpiryAfterBlocks`), each new ballot creation costs O(N), giving O(N²) aggregate cost for N distinct events created in that window — all executed synchronously inside `DeliverTx` processing of `MsgVoteInbound`.

### Impact Explanation
This falls under the allowed "non-network-level denial of service reachable without privileged control" category: it is triggered purely by ordinary (if numerous) user/attacker deposit behavior on a source chain, requires no malicious validator/relayer/admin action (validators behave exactly as designed), and adds unbounded per-transaction CPU work to the hot ballot-voting path used by every validator node. Sustained generation of many distinct inbound events within a single expiry window degrades per-block processing time for `MsgVoteInbound` handling across the whole network, which can slow finalization throughput.

### Likelihood Explanation
Moderate. The attacker's ability to grow the active-ballot set is rate-limited by how cheaply and quickly they can produce distinct, validator-observable source-chain events (real transactions on the external chain, or distinct payload/log-index variants), so this is not a "free" spam vector like a raw cosmos-tx flood. However, on cheap/low-fee source chains or via dust transfers with varying `LogIndex`/`RawPayload`, generating hundreds to thousands of distinct ballot keys within one expiry window is plausible and inexpensive, making the quadratic-scan cost realistically triggerable.

### Recommendation
- Avoid a full-collection scan on every `CreateBallot` call. Options: (a) maintain ballots indexed/bucketed by expiry height (e.g., a secondary index keyed by `BlockHeightExpiry`) so expiry sweeps only touch ballots actually due, rather than scanning the whole active set; (b) move expiry sweeping to `EndBlock`/`BeginBlock` (amortized, once per block) instead of inline on every ballot creation; (c) cap the number of active ballots swept per call and continue over multiple blocks if the backlog is large.

### Proof of Concept
Conceptual Go benchmark: seed the `uvalidator` keeper with N active ballots (each with a distinct id via `k.ActiveBallotIDs.Set` and `k.Ballots.Set`, expiry set beyond current height so none are pruned), then measure the latency of `k.CreateBallot(ctx, newID, ...)` for the (N+1)th distinct id, showing wall-clock/op-count growth linear in N (and therefore O(N²) for N sequential distinct-ballot creations) — confirming the unbounded scan in `ExpireBallotsBeforeHeight` executes fully on every call, driven only by the number of currently active ballots, not by the caller's own workload.

```go
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
```
