### Title
Aborted-transaction writes collapse to `None` and are cached as a hard "key does not exist" value in cross-shard reads, diverging sharded execution from sequential VM output - (aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs)

### Summary
`RemoteTxnWrite.write_op` is documented as `None` for both an explicit `WriteOp::Deletion` result and for a transaction that simply aborted and produced no write at all for the key [5](#0-4) . `CrossShardCommitReceiver::start` collapses this ambiguity further with `write_op.and_then(|w| w.as_state_value())`, producing `None` in both cases, and unconditionally caches it into `CrossShardStateView` via `set_value` [2](#0-1) . Once cached, `TStateView::get_state_value` for that key returns the cached `None` directly and never falls back to `base_view` [6](#0-5) , permanently masking the actual prior committed value for the remainder of the block's execution in the dependent shard.

### Finding Description
In sequential (reference) VM execution, an aborted transaction that was speculatively estimated to write key `K` produces no state mutation for `K` at all (aside from the sender's own gas/sequence-number account) — the "true" value of `K` for any subsequent transaction remains whatever it was prior to this transaction (i.e., the value visible in `base_view`/prior round).

In the sharded executor, the partitioner statically estimates dependency edges and assumes the source transaction will produce a write to `K`. When that source transaction actually aborts at execution time, `send_remote_update_for_success` (invoked from `on_transaction_committed`) still sends a `RemoteTxnWriteMsg` for `K`, but with `write_op = None` — the code comment even states this is the abort signaling convention [7](#0-6) [8](#0-7) .

On the receiving shard, `CrossShardCommitReceiver` unwraps this message and calls `cross_shard_state_view.set_value(&state_key, write_op.and_then(|w| w.as_state_value()))` [9](#0-8) . Because `write_op` is `None`, the expression evaluates to `None` regardless of the reason (abort vs. legitimate deletion), and `set_value` stores this `None` into the `cross_shard_data` map, replacing the `RemoteStateValue::waiting()` placeholder created in `CrossShardStateView::new` [10](#0-9) .

Any transaction in the dependent shard that subsequently calls `get_state_value(K)` hits the branch `if let Some(value) = self.cross_shard_data.get(state_key) { return Ok(value.get_value()); }`, which returns the cached `None` and **never falls through to `self.base_view.get_state_value(state_key)`** [11](#0-10) . The dependent transaction therefore observes `K` as nonexistent/deleted, whereas the correct (sequential-execution) value is whatever `base_view` (the pre-block or pre-round committed value) holds. This is exactly the divergence the exploit question hypothesizes: a `write_op: None` produced by an abort is indistinguishable from a real deletion once it passes through `as_state_value()` and is cached, and the caching path forecloses recovery of the true prior value.

### Impact Explanation
This produces a deterministic, protocol-level divergence between the sharded block executor's output and the reference sequential VM/state result for the same block: the dependent transaction's write set (and any downstream reads/writes chained off it) is computed against a wrong input state (`None` instead of the real prior value), so the resulting `TransactionOutput`, write set, and ultimately the computed state root for that block differ from what non-sharded (or correctly-shard-partitioned) execution of the identical transactions would produce. Because this is triggered purely by an ordinary Move-level abort in a transaction that an unprivileged user submits (no malicious validator or operator behavior required), any validator subset relying on sharded execution against another subset (or against replay/backup verification, which uses sequential execution) could compute differing state roots for the same block — a hard-fork-class divergence in committed state.

### Likelihood Explanation
Triggering an abort is trivial and fully within reach of any unprivileged account (e.g., calling into a Move module with an `assert!`/`abort` on a code path that was statically estimated by the block partitioner to write a shared/contended key). The only requirement is that the aborting transaction be selected by the partitioner as the source of a cross-shard write edge for a key subsequently read by a transaction in another shard/round — a condition the partitioner's dependency-edge heuristics can produce without any special crafting beyond ordinary conflicting-key transaction patterns.

### Recommendation
Distinguish "no write produced (abort/estimation mismatch)" from "explicit deletion" in the cross-shard protocol. `RemoteTxnWrite` should carry an explicit tri-state (e.g., `NoOp`, `Deleted`, `Value(StateValue)`) instead of collapsing both to `Option<WriteOp>` → `Option<StateValue>`. On the receiving side, `CrossShardStateView::set_value`/`get_state_value` should fall back to `base_view` when the signal is `NoOp`, and only cache a hard `None` for genuine deletions.

### Proof of Concept
1. Construct a block partitioned across ≥2 shards where transaction `A` (shard 0, round 0) is estimated by the partitioner to write key `K`, and transaction `B` (shard 1, round 1) reads `K` as a cross-shard dependency.
2. Craft `A` so it aborts at runtime (e.g., a Move `assert!` failure) after being estimated to write `K`, while `K` already holds a real value from a prior block/round (visible in `base_view`).
3. Run the sharded executor: `CrossShardCommitSender::on_transaction_committed` fires for `A`'s abort output, sends `RemoteTxnWrite{state_key: K, write_op: None}`; `CrossShardCommitReceiver` calls `set_value(K, None)`; `B` then reads `get_state_value(K) == Ok(None)`.
4. Run the same block sequentially through the normal VM/executor: `B` reads `get_state_value(K) == Ok(Some(prior_value))`.
5. Compare `B`'s materialized write set/output between the two runs — they differ for any logic in `B` that branches on `K`'s existence or value, demonstrating the state-commitment corruption.
