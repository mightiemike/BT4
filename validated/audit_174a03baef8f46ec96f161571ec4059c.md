### Title
Unsynchronized read/replace of shared `bloomFilters` array in `TxCacheDB` allows transaction-cache corruption / duplicate-transaction bypass - (File: `chainbase/src/main/java/org/tron/core/db2/common/TxCacheDB.java`)

### Summary
`TxCacheDB` maintains a two-element array of Guava `BloomFilter` objects, `bloomFilters[0]`/`bloomFilters[1]`, that is read by `get()` and mutated by `put()` without any locking. This is the same bug class as the reported `guageBuffered()` issue: a shared mutable buffer accessed by multiple call paths (a periodic/streaming path and a mutation path) with no mutex protecting the read. [1](#0-0) 

### Finding Description
`get()` reads both array slots without synchronization: [2](#0-1) 

`put()`, invoked for every processed/broadcast transaction via `Manager.processTransaction()` (`transactionCache.put(...)`), can rotate the active filter index and **replace the `BloomFilter` object reference** in `bloomFilters[currentFilterIndex]` with a brand-new instance once the active filter fills up: [3](#0-2) 

`put()` itself is called from `Manager.processTransaction()` on every transaction (broadcast or block-included): [4](#0-3) 

Because `bloomFilters` is a plain (non-volatile, non-`AtomicReferenceArray`) field and neither `get()` nor the array-replacement in `put()` is guarded by a lock, concurrent execution can produce:
- A stale/partially-published `BloomFilter` reference being read by `get()` on another thread (Java Memory Model visibility hazard — no synchronization/volatile guarantees the writing thread's replacement is visible to a reading thread).
- A race where `get()` reads `bloomFilters[currentFilterIndex]` at the exact moment `put()` swaps it for a fresh, empty filter, causing `mightContain()` to consult the wrong/empty filter and return a false negative for a transaction that was actually recorded.

This mirrors the reported class of bug precisely: `b.buffer`/`prices` accessed by `guageBuffered()` without a read lock while a separate path mutates the underlying buffer.

### Impact Explanation
`TxCacheDB.get()` backs the transaction-cache used to prevent duplicate transaction inclusion (`TransactionCache` / `TronStoreWithRevoking<BytesCapsule>` wrapping `TxCacheDB`). If a race causes `get()` to observe a stale or freshly-reset bloom filter, a duplicate-transaction check can spuriously miss an already-seen transaction ID, weakening the anti-replay/dup-transaction protection that this cache is designed to enforce. Because `put()` is invoked on the hot path for every transaction processed through `Manager.processTransaction()`, this is reachable from ordinary broadcast transactions, not merely privileged operations.

### Likelihood Explanation
`processTransaction()` runs concurrently with other reads of the same `TxCacheDB` instance (validation/dup-check paths and metrics/query paths), and the filter-rotation branch in `put()` triggers deterministically every `MAX_BLOCK_SIZE` (65,536) transactions-worth of block-number delta, so the unsynchronized array swap is a normal, recurring event rather than a rare corner case. The race window is narrow per-occurrence but recurs continuously as the node processes transactions, and no lock exists to prevent visibility issues or the swap-during-read race.

### Recommendation
Guard `bloomFilters` array reads and writes with a `ReadWriteLock` (read lock in `get()`, write lock around the reassignment/rotation logic in `put()`), or make the array `volatile`/use `AtomicReferenceArray<BloomFilter<byte[]>>` combined with a lock around the multi-field update (`filterStartBlock`, `currentFilterIndex`, `bloomFilters[idx]`) so that the triple is updated and observed atomically — analogous to how the Omni fix added a thread-safe `guageBuffered()`.

### Proof of Concept
Not independently verified with a runnable reproduction; this is inferred from the code paths cited above (unsynchronized read in `get()` at lines 181-188 vs. unsynchronized array replacement in `put()` at lines 190-221, both reachable via `Manager.processTransaction()`). A concrete PoC would require concurrently invoking `TxCacheDB.get()` on one thread while driving `put()` calls that cross the `MAX_BLOCK_SIZE` rotation boundary on another thread and observing a false-negative `mightContain()` result — this was not executed/tested here due to the ask-only/read-only nature of this investigation.

**Note on confidence:** I could not fully trace every caller of `TxCacheDB.get()` (e.g., whether it is invoked from a genuinely concurrent path relative to `put()`, such as JSON-RPC/HTTP handlers versus only single-threaded block application) within the available search iterations, so the concurrency reachability claim rests on the observed lack of synchronization primitives in the class itself plus the known multi-threaded nature of transaction broadcast handling in java-tron, rather than a fully confirmed thread-interleaving trace.
