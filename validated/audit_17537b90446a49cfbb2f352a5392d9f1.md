### Title
Unbounded per-request task fan-out in `LogBlockQuery.partialMatch` exhausts the shared `sectionExecutor` thread pool, causing JSON-RPC-wide DoS - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java])

### Summary
`LogBlockQuery.partialMatch` submits one `sectionExecutor.submit()` task per unique bloom bit index, per condition group, per section, with no cap on the total number of tasks generated by a single `eth_getLogs`/`eth_getFilterLogs` request. Because `sectionExecutor` is a single shared 5-thread `ExecutorService` instance used by every JSON-RPC client on the node, an unprivileged remote caller can craft a filter that queues tens of thousands of tasks in one call, starving all other concurrent `eth_getLogs`/`eth_getFilterLogs` requests.

### Finding Description
`TronJsonRpcImpl` creates exactly one `sectionExecutor` for the whole node: a fixed-size pool of 5 threads shared by all JSON-RPC clients: [1](#0-0) 

Each call to `eth_getLogs`/`eth_getFilterLogs` builds a `LogBlockQuery` bound to that same executor: [2](#0-1) 

`getConditions()` converts the filter into up to 5 condition groups (1 address group + up to 4 topic groups), each element hashed via `Bloom.create` into up to 3 bit indexes in a 2048-bit space: [3](#0-2) [4](#0-3) 

`getPossibleBlock()` iterates all groups and, for each, calls `subMatch`, which serially loops every section in `[minSection, maxSection]` and calls `partialMatch`: [5](#0-4) 

`partialMatch` collects the union of all bit indexes across the group's elements (`uniqueBitIndexes`, capped by construction at `BLOOM_BIT_SIZE`=2048) and submits one task to `sectionExecutor` per unique bit index before blocking on all the returned `Future`s: [6](#0-5) 

The section count is bounded by `jsonRpcMaxBlockRange` (default 5000) and `SectionBloomStore.BLOCK_PER_SECTION` (2048), giving ~3 sections by default: [7](#0-6) [8](#0-7) 

With **default** limits (`jsonRpcMaxAddressSize=1000`, `jsonRpcMaxSubTopics=1000`) this alone is enough: 1000 elements × 3 hash bits already saturate the 2048-slot bit space with high probability, so `uniqueBitIndexes` approaches the maximum of 2048 per group: [9](#0-8) [10](#0-9) [11](#0-10) 

Thus a single request with up to 5 condition groups × ~3 sections × up to 2048 unique bits can submit on the order of ~30,000 tasks to the 5-thread `sectionExecutor`. `Executors.newFixedThreadPool` (used by `ExecutorServiceManager.newFixedThreadPool`) uses an unbounded `LinkedBlockingQueue`, so all of these tasks queue rather than being rejected: [12](#0-11) 

Existing checks (`MAX_RESULT` in `getPossibleBlock`, `validateBlockRange`, `maxAddressSize`/`maxSubTopics` limits) only bound the *shape* of the query (block range, list sizes) — they do not bound or throttle the number of `sectionExecutor.submit` calls generated, and `MAX_RESULT` is checked only *after* all the executor work has already completed: [13](#0-12) 

There is no per-request task-count cap and no dedicated rate limiter for `eth_getLogs`/`eth_getFilterLogs` in the default rate-limiter config (only generic global QPS limits apply): [14](#0-13) 

### Impact Explanation
Because `sectionExecutor` is a single shared bean instance servicing all JSON-RPC clients (Full/Solidity/PBFT), a burst of tens of thousands of tasks from one attacker-controlled request occupies all 5 worker threads and fills the executor's queue. Any other legitimate `eth_getLogs`/`eth_getFilterLogs` call submitted concurrently is queued behind the attacker's tasks and stalls until they drain. This is a service-wide availability degradation of the JSON-RPC log-query subsystem (DoS via RPC-API), not a consensus or fund-safety issue.

### Likelihood Explanation
No non-default configuration is required — default `jsonRpcMaxAddressSize`/`jsonRpcMaxSubTopics` (1000) and `jsonRpcMaxBlockRange` (5000) are already large enough to produce a large fan-out (~5 groups × ~3 sections × up to 2048 unique bits). The attacker is a fully unprivileged, anonymous JSON-RPC/HTTP client — no signed transaction, fee, or on-chain cost is involved, and the request is trivially repeatable/parallelizable up to the generic global QPS limit (default 50000 global / 10000 per-IP), making sustained pressure on the 5-thread pool easy to achieve.

### Recommendation
Cap the number of `sectionExecutor.submit` calls issued per `LogBlockQuery`/`eth_getLogs` request (e.g., cap `uniqueBitIndexes` per group and/or total tasks across all groups/sections), size the sectionExecutor pool relative to expected concurrency with a bounded queue plus rejection, or process bit-index lookups synchronously/batched via a single call per section instead of one task per bit index. Additionally, consider dedicated rate-limiting for `eth_getLogs`/`eth_getFilterLogs` proportional to filter complexity (address/topic count × block range), not just raw QPS.

@Test
public void testPartialMatchFanOutDoS() throws Exception {
  // Build a filter with maxAddressSize (1000) addresses across a maxBlockRange (5000) range
  List<String> addresses = new ArrayList<>();
  for (int i = 0; i < 1000; i++) {
    addresses.add(ByteArray.toJsonHex(randomAddress(i)));
  }
  LogFilterWrapper wrapper = new LogFilterWrapper(
      new FilterRequest("0x0", "0x1388" /* 5000 */, addresses, null, null),
      CURRENT_MAX_BLOCK_NUM, null, true);

  AtomicInteger taskCount = new AtomicInteger();
  ExecutorService countingExecutor = new ThreadPoolExecutor(5, 5, 0L, TimeUnit.MILLISECONDS,
      new LinkedBlockingQueue<>(), r -> {
        taskCount.incrementAndGet();
        return new Thread(r);
      });

  LogBlockQuery query = new LogBlockQuery(wrapper, sectionBloomStore,
      CURRENT_MAX_BLOCK_NUM, countingExecutor);
  long start = System.nanoTime();
  query.getPossibleBlock();
  long elapsed = System.nanoTime() - start;

  // Assert task fan-out scales with filter complexity (expect thousands of tasks)
  Assert.assertTrue("expected large task fan-out, got " + taskCount.get(),
      taskCount.get() > 2000);
}

  private BitSet subMatch(int[][] bitIndexes) throws ExecutionException, InterruptedException {

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet subBitSet = new BitSet(capacity);

    for (int section = minSection; section <= maxSection; section++) {
      BitSet partialBitSet = partialMatch(bitIndexes, section);

      for (int i = partialBitSet.nextSetBit(0); i >= 0; i = partialBitSet.nextSetBit(i + 1)) {
        // operate on index i here
        if (i == Integer.MAX_VALUE) {
          break; // or (i+1) would overflow
        }
        int offset = (section - minSection) * SectionBloomStore.BLOCK_PER_SECTION + i;
        subBitSet.set(offset);
      }
    }

    return subBitSet;
  }

  private BitSet partialMatch(final int[][] bitIndexes, int section)
      throws ExecutionException, InterruptedException {
    // 1. Collect all unique bitIndexes
    Set<Integer> uniqueBitIndexes = new HashSet<>();
    for (int[] index : bitIndexes) {
      for (int bitIndex : index) { //normally 3, but could be less due to hash collisions
        uniqueBitIndexes.add(bitIndex);
      }
    }

    // 2. Submit concurrent requests for all unique bitIndexes
    Map<Integer, Future<BitSet>> bitIndexResults = new HashMap<>();
    for (int bitIndex : uniqueBitIndexes) {
      Future<BitSet> future
          = sectionExecutor.submit(() -> sectionBloomStore.get(section, bitIndex));
      bitIndexResults.put(bitIndex, future);
    }

    // 3. Wait for all results and cache them
    Map<Integer, BitSet> resultCache = new HashMap<>();
    for (Map.Entry<Integer, Future<BitSet>> entry : bitIndexResults.entrySet()) {
      BitSet result = entry.getValue().get();
      if (result != null) {
        resultCache.put(entry.getKey(), result);
      }
    }

  public int[][][] getConditions() {

    LogFilter logFilter = logFilterWrapper.getLogFilter();
    List<byte[][]> conditions = new ArrayList<>();
    if (ArrayUtils.isNotEmpty(logFilter.getContractAddresses())) {
      conditions.add(logFilter.getContractAddresses());
    }
    for (byte[][] topicList : logFilter.getTopics()) {
      if (ArrayUtils.isNotEmpty(topicList)) {
        conditions.add(topicList);
      }
    }

    int[][][] allConditionsIndex = new int[conditions.size()][][];

    for (int k = 0; k < conditions.size(); k++) {
      byte[][] conditionByte = conditions.get(k);

      int[][] bitIndexes = new int[conditionByte.length][];
      for (int j = 0; j < conditionByte.length; j++) {

        byte[] hash = Hash.sha3(conditionByte[j]);
        Bloom bloom = Bloom.create(hash);
        BitSet bs = BitSet.valueOf(bloom.getData());

        //number of nonZero positions may be equal or less than number(3) of hash function in Bloom
        List<Integer> bitIndexList = new ArrayList<>();
        for (int i = bs.nextSetBit(0); i >= 0; i = bs.nextSetBit(i + 1)) {
          // operate on index i here
          if (i == Integer.MAX_VALUE) {
            break; // or (i+1) would overflow
          }
          bitIndexList.add(i);
        }

        bitIndexes[j] = bitIndexList.stream().mapToInt(Integer::intValue).toArray();
      }
      allConditionsIndex[k] = bitIndexes;
    }

    return allConditionsIndex;
  }
