Based on my analysis, there's a plausible analog to the report's underlying bug class ("a multi-step entry point that strands value on abort" / "a fold that absorbs failure") in the `liquidate-multi` batch-liquidation flow.

### Title
`liquidate-multi` allows partial, uncompensated state commitment when a later step of a batched `liquidate` call fails - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` iterates over a list of liquidation requests with `map call-liquidate positions` and always returns `(ok (list ...))` at the top level, regardless of whether individual `liquidate` calls inside the list succeeded or failed [1](#0-0) . Because the *literal transaction entry point* (`liquidate-multi`) never itself returns `err`, Clarity's full-transaction rollback is never triggered, even though a nested `liquidate()` invocation may fail partway through after already committing real, cross-contract state changes.

### Finding Description
`call-liquidate` invokes the public function `liquidate` directly (not via `contract-call?`), so it is a plain function call within the same contract, not a sub-transaction boundary [2](#0-1) .

Inside `liquidate`, the debt repayment to the vault happens via a genuine cross-contract `contract-call?` (`vault-system-repay`), and *afterward* the function performs additional cross-contract calls that can still fail: removing scaled debt from the borrower's ledger, removing collateral, and — if the position is left with no collateral — a `fold` over `socialize-debt-asset` guarded by `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [3](#0-2) .

Per Clarity's documented semantics, when a *called* contract-call returns `err`, only *that specific call's* own state changes are rolled back; changes already committed by *earlier, successful* contract-calls in the same caller function are not automatically undone unless the actual top-level transaction entry point ultimately returns `err`. Since `liquidate-multi` unconditionally wraps its `map` results in `(ok ...)`, the overall transaction succeeds even when a constituent `liquidate()` call returns `err` partway through:

1. `vault-system-repay` succeeds — the liquidator's tokens are pulled and the vault's aggregate `total-borrowed`/`assets` accounting is reduced.
2. A later step fails — e.g. `debt-remove-scaled` on `market-vault`, `collateral-remove`, or the bad-debt-socialization `asserts!` — causing `liquidate` to return `(err ...)`.
3. `call-liquidate` (a direct call, not `contract-call?`) simply propagates that `err` value into the `map` result list.
4. `liquidate-multi` returns `(ok (list ... (err X) ...))` — a fully "successful" transaction from Clarity's perspective, so nothing is rolled back.

The net effect: the vault's aggregate debt accounting has already been decremented (real repayment consumed), but the specific borrower's individual scaled-debt record in `market-vault` was never reduced, and/or collateral was never transferred to the liquidator, and/or bad debt was never socialized. This creates a permanent mismatch between vault-level aggregate accounting and market-vault's per-position ledger, and the liquidator's repayment funds are consumed with no compensating debt reduction or collateral received.

### Impact Explanation
This lands on both theft-of-funds and protocol-insolvency impact classes: the liquidator's repayment is irrecoverably spent while receiving no collateral, and the mismatch between aggregate vault debt totals and market-vault's per-borrower debt ledger creates an insolvency gap that persists in protocol state after the "successful" transaction — this is not a caller/attacker fund at risk but real value permanently lost/misallocated, matching "protocol insolvency" and "temporary/permanent freezing of funds" thresholds.

### Likelihood Explanation
This does not require any privileged access — any user calling `liquidate-multi` with a batch containing at least one position that fails on the collateral-removal, debt-removal, or bad-debt-socialization step (a common real-world scenario, e.g., due to the same-block-liquidation guard, slippage/min-collateral checks, or a stale price condition affecting only one entry in the batch) will trigger this while other entries succeed and commit real repayment.

### Recommendation
Do not silently absorb `err` results from `liquidate` calls inside `liquidate-multi`. Either (a) make `liquidate-multi` propagate/abort the whole transaction if any sub-liquidation partially fails after committing an irreversible repayment, or (b) restructure `liquidate`'s internal ordering so that no cross-contract state-mutating call (especially the token-moving `vault-system-repay`) is executed until *all* later steps (debt-removal, collateral-removal, bad-debt socialization) have been validated as certain to succeed, or (c) wrap the entire per-position sequence in a construct that guarantees atomicity of the "repay → remove debt → remove collateral → socialize" chain per position, independent from the batch's outer success.

### Proof of Concept
1. Prepare two liquidatable positions, A and B, in a single `liquidate-multi` call.
2. Craft position B such that `vault-system-repay` succeeds but the subsequent `collateral-remove` (or `debt-remove-scaled`, or bad-debt socialization) call fails — e.g., by having B's collateral fully consumed by a concurrent operation captured in the same block, or setting `min-collateral-expected`/slippage parameters that pass an earlier check but fail a later derived condition.
3. Call `liquidate-multi` with `[A, B]`.
4. Observe: the transaction succeeds (`(ok (list (ok ...) (err ...)))`); position A is liquidated normally; for position B, the vault's aggregate `total-borrowed`/`assets` are reduced (tokens pulled from the liquidator) but B's individual scaled debt in `market-vault` is unchanged and B's collateral is not transferred — a permanent value/accounting mismatch.
