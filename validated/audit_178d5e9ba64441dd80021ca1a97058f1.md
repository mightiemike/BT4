### Title
L1Handler transactions that fail with a fatal execution error are still marked permanently "consumed", causing the bridged L1→L2 message and its funds to be irrecoverably lost - (File: crates/apollo_batcher/src/block_builder_test.rs / crates/apollo_l1_events/src/transaction_manager.rs)

### Summary
When building a block, if an `L1HandlerTransaction` fails with a fatal (non-revert) execution error such as `TransactionExecutorError::StateError`, the transaction is still reported as part of `consumed_l1_handler_tx_hashes` in the block execution artifacts, as shown by the test `failed_l1_handler_transaction_consumed` [1](#0-0) . This mirrors the audited auction bug where a single, irreversible terminal status transition (`Claimed`) permanently blocks a legitimate, unrelated recovery path (`claimBids`), leaving user funds stuck with no way back.

### Finding Description
`TransactionManager::consume_tx`/`TransactionRecord::mark_consumed` unconditionally overwrites the transaction's state to the terminal `TransactionState::Consumed`, and once consumed there is no way back: `is_validatable()` returns `false` for consumed transactions and the record is only removed via a fixed timelock, never re-included [2](#0-1) . The consumed/committed status returned by the block builder (`consumed_l1_handler_tx_hashes`) is then forwarded straight to the L1 events provider on block commit via `commit_block`, which calls `commit_txs`, permanently transitioning matching records out of `Pending` [3](#0-2) .

The test `failed_l1_handler_transaction_consumed` demonstrates that when an `L1HandlerTransaction`'s execution result is `Err(TransactionExecutorError::StateError(StateError::OutOfRangeContractAddress))` (a fatal, non-revert error), the resulting `execution_data.consumed_l1_handler_tx_hashes` still contains that transaction's hash [4](#0-3) . This is distinct from the normal "reverted" path modeled in `L1HandlerTransaction::execute_raw`, where a failed `run_execute` or a failed post-execution fee check still produces an `Ok(...)` execution info with a `revert_error`, meaning the state diff/receipt is committed and the L1 message is legitimately consumed even though the inner call reverted [5](#0-4) . A `StateError` from the executor, by contrast, is not a normal Cairo-level revert — it indicates the transaction could not be executed/committed to the state at all — yet it is nonetheless folded into the "consumed" set exactly like a successful or gracefully-reverted L1 handler transaction.

Because "consumed" is a terminal, irreversible status in the transaction manager (analogous to the audited contract's `Claimed` status overwriting `Settled` with no path back for bidders), any L1→L2 message whose execution hits this fatal-error path is recorded as fully handled on L2 forever, blocking any legitimate recovery mechanism (e.g., L1-side cancellation/refund flows or reproposal), while the intended state effect (e.g., crediting a bridged deposit) never actually lands in the committed state diff.

### Impact Explanation
Funds represented by an L1→L2 bridging message can be permanently frozen: the message is marked `Consumed` (a one-way terminal state that removes it from being retried and is never reversible) even though its state-changing effect never got applied to the chain, since the underlying execution never reached a normal `Ok`/reverted receipt but instead failed with a fatal executor-level state error. This matches the "permanent freezing of funds" criterion, and is directly analogous to the audited auction bug where a terminal status change (irreversible, one-directional) locked users out of reclaiming funds that were rightfully theirs.

### Likelihood Explanation
This is reachable purely from the perspective of an ordinary L1 message sender: any user who sends a message from L1 to L2 (e.g., a bridge deposit) that happens to trigger a fatal state error during L2 block building (out-of-range contract address, or any other `StateError` variant surfaced by the transaction executor for an L1Handler transaction) hits this path. No special sequencer/operator privilege is required to trigger it — only crafting an L1 message whose target/entry point produces such a state-level failure during execution.

### Recommendation
Distinguish fatal executor-level failures (`TransactionExecutorError::StateError` and similar) from normal Cairo-level reverts for `L1HandlerTransaction`s. Only include a transaction's hash in `consumed_l1_handler_tx_hashes` (and therefore transition its `TransactionManager` record to the terminal `Consumed` state) when it was actually included/committed in the block's state diff (success or graceful on-chain revert). For fatal executor errors, treat the transaction as not consumed so it remains eligible for legitimate recovery (retry, L1 cancellation, etc.), rather than allowing the immutable "consumed" bookkeeping to diverge from what was actually applied to the state.

### Proof of Concept
1. Construct an `L1HandlerTransaction` whose execution triggers a fatal `TransactionExecutorError::StateError` (e.g., `OutOfRangeContractAddress`) during block building, as reproduced by `failed_l1_handler_transaction_consumed` [6](#0-5) .
2. Observe that `result_block_artifacts.execution_data.consumed_l1_handler_tx_hashes` still contains the transaction's hash despite the fatal error [4](#0-3) .
3. On block commit, this hash flows into `commit_block`/`commit_txs`, permanently transitioning the record in `TransactionManager` away from `Pending` and eventually to a terminal, non-reversible state, since `mark_consumed`/`is_validatable` never allow moving back [7](#0-6) .
4. Because the state diff for this transaction was never actually committed (fatal error aborted its effect), the funds/logic the L1 message was meant to trigger never materialize on L2, yet the message can never be retried, refunded, or reconsidered, since its bookkeeping says "Consumed."

async fn failed_l1_handler_transaction_consumed() {
    let l1_handler_txs = test_l1_handler_txs(0..2);

    helper.expect_is_done(false);

    helper.expect_get_new_results_with_results(vec![
        Err(TransactionExecutorError::StateError(StateError::OutOfRangeContractAddress)),
        Ok((execution_info(), StateMaps::default())),
    ]);
    helper.expect_is_done(true);
    helper.expect_successful_get_new_results(0);

    helper.mock_transaction_executor.expect_close_block().times(1).return_once(|_| {
        Ok(BlockExecutionSummary {
            state_diff: Default::default(),
            compressed_state_diff: None,
            bouncer_weights: BouncerWeights::empty(),
            casm_hash_computation_data_sierra_gas: CasmHashComputationData::default(),
            casm_hash_computation_data_proving_gas: CasmHashComputationData::default(),
            compiled_class_hashes_for_migration: vec![],
            block_info: BlockInfo::create_for_testing(),
        })
    });

    let (_abort_sender, abort_receiver) = tokio::sync::oneshot::channel();
    let result_block_artifacts = run_build_block(
        helper.mock_transaction_executor,
        mock_tx_provider,
        None,
        false,
        abort_receiver,
        BLOCK_GENERATION_DEADLINE_SECS,
        DEFAULT_IDLE_TIMEOUT_MS,

        l1_handler_txs.iter().map(|tx| tx.tx_hash()).collect::<IndexSet<_>>()
    );
}

    /// Mark a transaction as consumed on L1.
    /// The timestamp is the L1 block timestamp where this tx was marked consumed.
    /// If tx was not already consumed (expected result), return None.
    /// If tx was already consumed (double consumption), return the time when it was previously
    /// consumed. Note that double consumption is a bug.
    pub fn mark_consumed(&mut self, timestamp: BlockTimestamp) -> Option<BlockTimestamp> {
        if self.is_committed() {
            debug!("Marking a committed transaction {} as consumed.", self.tx.tx_hash());
        } else {
            // TODO(guyn): check if this situation should be an error.
            // TODO(guyn): check other state combinations that may be worth an error/warning/debug
            // log.
            debug!(
                "Marking a non-committed transaction {} as consumed. Previous state: {:?}",
                self.tx.tx_hash(),
                self.state
            );
        }
        self.state = TransactionState::Consumed;
        // First check if the tx was already consumed. Double consumption is a bug!
        // If None, it wasn't previously consumed: mark the time and return None to signal
        // everything is ok. If Some, it was already consumed: report the time when it was
        // previously consumed, the caller decides what to do.
        match self.consumed_at {
            Some(existing) => Some(existing),
            None => {
                self.consumed_at = Some(timestamp);
                None
            }
        }
    }
