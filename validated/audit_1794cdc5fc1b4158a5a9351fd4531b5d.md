### Title
Job proposals from a Feeds Manager never expire and can be approved arbitrarily long after submission - ([File: core/services/feeds/service.go])

### Summary
Analogous to the Olympus `OlympusGovernance` issue where an "active" proposal never expires and can be voted on/executed indefinitely, Chainlink's Feeds Manager (FMS) job-proposal workflow has no time-bound validity for `SpecStatusPending` proposals. A proposal created via `ProposeJob` stays in `JobProposalStatusPending` / `SpecStatusPending` state indefinitely until a node operator calls `ApproveSpec` or `RejectSpec` — there is no expiration, staleness check, or re-validation against the freshness of the originating request.

### Finding Description
`ProposeJob` upserts a `JobProposal` with `Status: JobProposalStatusPending` and creates an associated `JobProposalSpec` with `Status: SpecStatusPending` [1](#0-0) . Nothing in the data model or in `isApprovable` enforces any time window on how long a spec may remain pending before it can be approved [2](#0-1) .

`ApproveSpec` can be invoked at any point after proposal creation — the only checks performed are on the current `JobProposalStatus` (not deleted/revoked) and `SpecStatus` (must be pending, or a limited case of cancelled) via `isApprovable`, with no check on how long the spec has been sitting idle [3](#0-2) . This mirrors the Olympus bug class precisely: a proposal, once introduced, remains perpetually actionable until superseded, with no automatic invalidation based on age.

Additionally, for `job.Workflow` and `job.CRESettings` job types, `ProposeJob` auto-approves the spec immediately via `s.ApproveSpec(ctx, specID, true)` [4](#0-3) , but for all other job types (OCR, Flux Monitor, CCIP, Gateway, etc.) the proposal is left pending indefinitely for manual approval, with no expiry mechanism to force re-review or automatic rejection of proposals that have gone stale.

### Impact Explanation
A job proposal submitted by a Feeds Manager can sit in `SpecStatusPending` for an arbitrary duration (weeks, months). If it is approved long after submission — for example after upstream conditions have changed (bridge/adapter behavior, contract addresses, pricing feeds, or job parameters that are no longer safe) — `ApproveSpec` will proceed to call `generateJob`, `AssertBridgesExist`, and ultimately `jobSpawner.CreateJob`, deploying a potentially stale/harmful job onto the node without any re-validation that the proposal is still current [5](#0-4) . This can result in unsafe job execution (e.g., outdated OCR configuration, forwarder address, or pipeline logic) being deployed onto a production Chainlink node long after it was reviewed, undermining the operator's ability to reason about the freshness/validity of what they are approving. This is a moderate-severity operational-integrity issue rather than a direct unauthorized-execution bug, since `ApproveSpec` still requires operator action, but is a direct analog of the reported bug class (no expiration of an "active"/pending governance-like state).

### Likelihood Explanation
Likelihood is low-to-moderate: the FMS pending-proposal state is normal in the feeds workflow, and staleness bugs manifest only when a proposal is deliberately or accidentally approved after significant elapsed time (e.g., operator processes a backlog, or malicious/compromised FMS connection re-surfaces an old proposal). There is no automated exploit path independent of an operator's approval action, and the codebase provides no built-in safeguard (expiry, staleness warning) to prevent this scenario, matching the disputed-but-acknowledged nature of the original Olympus finding.

### Recommendation
Add an expiration mechanism to `JobProposalSpec`/`JobProposal` in `core/services/feeds`:
- Track a `CreatedAt`/`UpdatedAt` timestamp already present, and add an explicit staleness/expiry policy (e.g., configurable TTL such as 2 weeks) after which a pending spec is automatically transitioned to `SpecStatusCancelled`/`SpecStatusExpired`.
- In `isApprovable` (core/services/feeds/service.go), reject approval of pending specs older than the configured TTL, returning an explicit error requiring re-proposal.
- Surface staleness warnings in the FMS UI/API responses (e.g., `ListPendingJobProposals`) so operators are alerted before approving old proposals [6](#0-5) .

### Proof of Concept
1. An FMS submits a job proposal via `ProposeJob`, creating a `JobProposalSpec` with `SpecStatusPending` [1](#0-0) .
2. The node operator does not act on it (or the FMS connection drops and reconnects later); the spec remains `SpecStatusPending` indefinitely, since no code path expires it.
3. Weeks/months later, external conditions that made the job spec appropriate have changed (e.g., bridge no longer trustworthy, contract address deprecated).
4. The operator (or an automated approval script, or a re-triggered auto-approval for workflow jobs) calls `ApproveSpec(ctx, id, force)`; `isApprovable` only checks `SpecStatusPending`, not age, and approval proceeds, generating and spawning the job on-chain-adjacent infrastructure [7](#0-6) [8](#0-7) .

func (s *service) isApprovable(ctx context.Context, propStatus JobProposalStatus, proposalID int64, specStatus SpecStatus, specID int64) error {
	if propStatus == JobProposalStatusDeleted {
		return errors.New("cannot approve spec for a deleted job proposal")
	}

	if propStatus == JobProposalStatusRevoked {
		return errors.New("cannot approve spec for a revoked job proposal")
	}

	switch specStatus {
	case SpecStatusApproved:
		return errors.New("cannot approve an approved spec")
	case SpecStatusRejected:
		return errors.New("cannot approve a rejected spec")
	case SpecStatusRevoked:
		return errors.New("cannot approve a revoked spec")
	case SpecStatusCancelled:
		// allow approval of a cancelled job if no other spec is approved
		specs, serr := s.orm.ListSpecsByJobProposalIDs(ctx, []int64{proposalID})
		if serr != nil {
			return errors.Wrap(serr, "failed to get latest spec")
		}

		for _, spec := range specs {
			if spec.Status == SpecStatusApproved {
				return fmt.Errorf("the job spec with version %d is already approved", spec.Version)
			}
		}

		slices.SortFunc(specs, func(a, b JobProposalSpec) int { return int(b.Version - a.Version) })
		cancelledIndex := 0
		for _, spec := range specs {
			if spec.ID == specID {
				if cancelledIndex >= 2 {
					return errors.New("only the last two cancelled spec versions may be approved")
				}
				return nil
			}
			if spec.Status == SpecStatusCancelled {
				cancelledIndex++
			}
		}

		return fmt.Errorf("failed to find spec %d associated with proposal %d", specID, proposalID)
	case SpecStatusPending:
		return nil
	default:
		return errors.New("invalid job spec status")
	}
}

// ListPendingJobProposals returns all job proposals whose latest spec has a
// pending status, across all job distributors registered on the node.
func (c *client) ListPendingJobProposals(ctx context.Context) ([]PendingJobProposal, error) {
	resp, err := generated.ListFeedsManagers(ctx, c.gqlClient)
	if err != nil {
		return nil, fmt.Errorf("failed to list job distributors: %w", err)
	}
	if resp == nil {
		return nil, errors.New("unexpected nil response from list job distributors")
	}

	var pending []PendingJobProposal
	for _, fm := range resp.FeedsManagers.Results {
		for _, jp := range fm.JobProposals {
			if jp.LatestSpec.Status == generated.SpecStatusPending {
				pending = append(pending, PendingJobProposal{
					ProposalID:       jp.Id,
					SpecID:           jp.LatestSpec.Id,
					ProposalStatus:   string(jp.Status),
					SpecStatus:       string(jp.LatestSpec.Status),
					Definition:       jp.LatestSpec.Definition,
					Version:          jp.LatestSpec.Version,
					JobDistributorID: fm.Id,
				})
			}
		}
	}
	return pending, nil
