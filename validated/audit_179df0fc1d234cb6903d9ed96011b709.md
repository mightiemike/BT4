## Analog Vulnerability Found

### Title
Relayer fee is paid unconditionally in `inner_rlp_execute` regardless of whether the underlying emulated transfer succeeds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Sherlock report flags `BlueBerryBank.sol` for calling `IERC20Upgradeable.approve()`/`ISoftVault.approve()` without checking the boolean return value, so a failed approval is silently treated as successful and later operations proceed on a false assumption. The reachable analog in this nearcore repository is the NEAR Wallet Contract's relayer-fee refund logic in `inner_rlp_execute`, which schedules and sends the relayer's fee **before** the actual emulated action (base-token transfer or ERC-20/NEP-141 transfer) is known to succeed, and does not condition that payment on the action's outcome.

### Finding Description
`inner_rlp_execute` parses an RLP-encoded Ethereum transaction into a Near `action`/`transaction_kind`. For `EOABaseTokenTransfer` and `ERC20Transfer` kinds carrying a non-zero `fee`, the code immediately creates an independent promise batch that transfers the fee to the predecessor (the relayer): [1](#0-0) 

This transfer is dispatched as its own receipt via `env::promise_batch_create` / `env::promise_batch_action_transfer`, completely independent of the promise chain built afterwards for the actual action: [2](#0-1) 

The eventual success/failure of that action promise is only checked later in `rlp_execute_callback`/`nep_141_storage_balance_callback`, via `env::promise_result(0)`: [3](#0-2) 

But that check only decides whether to refund the *caller's attached deposit* (`CallerDeposit`) — it has no effect on the relayer fee, which was already sent unconditionally in `inner_rlp_execute` before the action promise was even created. There is no `.then()` chaining, no re-check, and no clawback mechanism tying the fee payment to the actual success of the `ft_transfer` (ERC-20 emulation) or base-token transfer.

### Impact Explanation
Because the fee payment is not gated on the success return value/outcome of the transfer it is meant to compensate, a relayer can always collect the fee attached to a signed RLP transaction even when the underlying operation fails — e.g., the NEP-141 token's `ft_transfer` panics or is rejected (insufficient balance, blacklisted receiver, `storage_deposit` failing for a reason not accounted for, gas exhaustion in the callback chain, etc.), or the base-token transfer to another eth-implicit account fails validation. In all such cases the wallet owner's NEAR balance is drained for the fee while receiving nothing in return, which is unauthorized value movement out of the wallet contract account. This is directly analogous to the reported bug class: an operation's completion is assumed rather than verified before acting on that assumption (there paying/approving downstream logic on an unchecked `approve()`; here paying a relayer on an unchecked transfer outcome).

### Likelihood Explanation
Any unprivileged party who possesses (or is given) a validly signed RLP transaction for a wallet contract can act as the relayer and submit it via `rlp_execute`. Since the fee send happens synchronously within `inner_rlp_execute` before the action's async result is known, triggering a failure in the downstream action (which is easy for an uncooperative/malicious relayer to arrange, e.g. by picking a `target`/receiver that causes `ft_transfer` to fail, or racing the nonce/balance state) reliably yields fee payment without the promised transfer completing. This requires only crafting or submitting one transaction — no privileged access, validator collusion, or network-layer manipulation.

### Recommendation
Chain the relayer fee payment to the outcome of the actual action instead of sending it unconditionally up front. For example, create the fee-transfer promise as a `.then()` continuation (or as part of the same callback) that only executes after `env::promise_result` on the action's promise reports `PromiseResult::Successful`, mirroring the existing caller-deposit refund logic in `rlp_execute_callback`.

### Proof of Concept
1. Attacker (or any relayer) is handed/crafts a valid RLP-encoded `ERC20Transfer` (or `EOABaseTokenTransfer`) transaction for a wallet contract, signed by the wallet owner, with a non-zero `fee`.
2. Relayer submits it to the target's `target` account such that the downstream `ft_transfer` (or transfer) action will fail — e.g., target token requires registration that fails, or the receiver rejects the call, or insufficient token balance causes the NEP-141 contract to panic in `ft_transfer`.
3. `inner_rlp_execute` unconditionally creates the fee-refund promise to the relayer at lines 381-384 before the action promise is built.
4. The fee transfer receipt succeeds and delivers NEAR to the relayer's account.
5. The action promise later fails; `rlp_execute_callback` reports `success: false`, but the relayer has already been paid — the wallet owner lost the fee for a transfer that never happened.
