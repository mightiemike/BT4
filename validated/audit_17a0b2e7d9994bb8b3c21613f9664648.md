### Title
Excess `attached_deposit` from an external caller to the NEAR Wallet Contract's `AddKey`/`DeleteKey` actions is permanently burnt instead of refunded - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs`)

### Summary
The `GolomTrader.fillAsk()` bug locks excess `msg.value` because the contract only checks `>=` instead of consuming exactly what's needed and refunding the rest. The NEAR Wallet Contract (`WalletContract::rlp_execute`) has an analogous pattern: it accepts an arbitrary `attached_deposit` from an external, non-self predecessor, wraps the *entire* deposit in a `CallerDeposit` for refund purposes, but only refunds it if the resulting cross-contract promise **fails**. For `AddKey`/`DeleteKey` actions — which never consume any deposit (`Action::value()` returns `NearToken::from_yoctonear(0)` for both, and `try_into_near_action` ignores `additional_value` entirely for these variants) — a successful execution silently keeps the caller's full deposit with no path to reclaim it.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-410`) is reachable by any account calling the `#[payable]` `rlp_execute` method (`lib.rs:88-128`) with an attached deposit. It builds an `ExecutionContext` from `env::attached_deposit()` and constructs `caller_deposit = CallerDeposit::new(&context)` (`lib.rs:343-345`), which captures the caller's entire deposit for external (non-self) predecessors: [1](#0-0) 

For `AddKey` and `DeleteKey` actions, `Action::value()` is hard-coded to zero and `try_into_near_action` never applies the `additional_value` (i.e., the attached deposit) to these variants — it is simply dropped from the resulting `near_action::Action`: [2](#0-1) 

The only refund path is `rlp_execute_callback`, which refunds `caller_deposit` **exclusively on `PromiseResult::Failed`**: [3](#0-2) 

If the promise succeeds (the common case — an `AddKey`/`DeleteKey` action has no reason to fail if the RLP transaction is well-formed and correctly signed), the branch at `lib.rs:313-315` returns success and the caller's deposit is never returned. Unlike the deposit-carrying `FunctionCall`/`Transfer` paths — where the full attached deposit is deliberately forwarded as the action's `deposit` (so it is not "excess," it is spent by design) — for `AddKey`/`DeleteKey` there is no NEAR action to which the deposit can be attached; the value is neither transferred to any account nor burnt by protocol rules, it is simply retained as a balance increase on the wallet contract account itself, permanently unavailable to the external caller who sent it, exactly mirroring the Golom `fillAsk()` pattern (funds sent by a caller beyond what the operation consumes are irrecoverably locked because the code only handles the failure branch, never the "success but overpaid" branch).

### Impact Explanation
Any external account (a relayer, or any third party invoking `rlp_execute` on someone else's eth-implicit wallet account with a non-self `predecessor_id`) that mistakenly or intentionally attaches a deposit to an `AddKey`/`DeleteKey`-encoded Ethereum transaction has that entire deposit permanently absorbed into the wallet-contract account's balance on success, with no mechanism for the depositor to reclaim it. This is a concrete unauthorized value movement / permanently frozen funds condition: value moves from the caller to the wallet account without consent or compensation, and cannot be extracted back to the original depositor through the contract's own logic (there is no withdraw/refund entry point keyed to `CallerDeposit` once the promise succeeds).

### Likelihood Explanation
Likelihood is moderate: relayers (the intended external callers of `rlp_execute`) typically attach zero deposit for `AddKey`/`DeleteKey` operations since these actions carry no NEP-141/native value semantics, so in normal, well-behaved relayer flows this deposit is zero. However, nothing in the contract enforces this — a relayer or third-party caller that (by bug, misconfiguration, or blind sending of surplus deposit expecting protocol-level auto-refund, similar to the Golom reporter's exact framing that "it is common for contracts to return excess funds, so the user may reasonably expect this behaviour") attaches a non-zero deposit to such a call will have it silently locked whenever the call succeeds, which is the common/expected outcome for a well-formed `AddKey`/`DeleteKey` transaction.

### Recommendation
Track the deposit intended to be consumed by the resulting NEAR action separately from any deposit that has no corresponding sink (e.g., for `AddKey`/`DeleteKey`). Change `rlp_execute_callback` (and the intermediate callbacks that thread `caller_deposit`) to always refund a `CallerDeposit` when the target NEAR action does not itself require/consume the deposit, not only on promise failure. Concretely: compute the "unspent" portion of `context.attached_deposit` after `Action::value()`/`try_into_near_action` determine how much of it is actually attached to the outgoing promise, and unconditionally refund the remainder to `predecessor_account_id`, regardless of whether the inner promise succeeds or fails — mirroring the strict-equality fix recommended for `fillAsk()` (only consume exactly what's needed, refund the rest).

### Proof of Concept
1. Deploy the `WalletContract` on an eth-implicit account `E` (as in `integration-tests/src/tests/features/wallet_contract.rs`).
2. From an unrelated account `Attacker` (i.e., `predecessor_account_id != current_account_id`), call `E.rlp_execute(target = E, tx_bytes_b64 = <RLP tx encoding an AddKey or DeleteKey action>)` with `deposit = N` NEAR attached (`#[payable]` allows any deposit).
3. `CallerDeposit::new` captures `{ account_id: Attacker, yocto_near: N }` (`types.rs:180-191`).
4. `parse_rlp_tx_to_action` resolves to `Action::AddKey { .. }` or `Action::DeleteKey { .. }`; `Action::value()` = 0 and `try_into_near_action` never applies `N` to the produced `near_action::Action` (`types.rs:226-299`).
5. `action_to_promise` builds a promise for `AddKey`/`DeleteKey` with zero deposit (`lib.rs:475-501`); this promise succeeds under normal conditions (valid key, valid signature).
6. `rlp_execute_callback` receives `PromiseResult::Successful`, returns `ExecuteResponse{success:true,..}` and never triggers the refund branch at `lib.rs:296-305` (which only fires on `PromiseResult::Failed`).
7. Result: `N` NEAR remains permanently on account `E`'s balance; `Attacker` has no way to reclaim it via the contract's exposed methods — the funds have moved without the possibility of restitution, analogous to Golom's excess `msg.value` being locked in the trading contract.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

impl Action {
    pub fn value(&self) -> NearToken {
        match self {
            Action::FunctionCall { yocto_near, .. } => {
                NearToken::from_yoctonear((*yocto_near).into())
            }
            Action::Transfer { yocto_near, .. } => NearToken::from_yoctonear((*yocto_near).into()),
            Action::AddKey { .. } => NearToken::from_yoctonear(0),
            Action::DeleteKey { .. } => NearToken::from_yoctonear(0),
        }
    }

    pub fn try_into_near_action(
        self,
        additional_value: u128,
    ) -> Result<near_action::Action, Error> {
        let action = match self {
            Action::FunctionCall { receiver_id: _, method_name, args, gas, yocto_near } => {
                let action = FunctionCallAction {
                    method_name,
                    args,
                    gas: Gas::from_gas(gas),
                    deposit: NearToken::from_yoctonear(
                        additional_value.saturating_add(yocto_near.into()),
                    ),
                };
                near_action::Action::FunctionCall(action)
            }
            Action::Transfer { receiver_id: _, yocto_near } => {
                let action = TransferAction {
                    deposit: NearToken::from_yoctonear(
                        additional_value.saturating_add(yocto_near.into()),
                    ),
                };
                near_action::Action::Transfer(action)
            }
            Action::AddKey {
                public_key_kind,
                public_key,
                nonce,
                is_full_access,
                is_limited_allowance,
                allowance,
                receiver_id,
                method_names,
            } => {
                let public_key = construct_public_key(public_key_kind, &public_key)?;
                let access_key = if is_full_access {
                    AccessKey { nonce, permission: AccessKeyPermission::FullAccess }
                } else {
                    let allowance = if is_limited_allowance { Some(allowance) } else { None };
                    AccessKey {
                        nonce,
                        permission: AccessKeyPermission::FunctionCall(FunctionCallPermission {
                            allowance: allowance.map(NearToken::from_yoctonear),
                            receiver_id: receiver_id
                                .parse()
                                .map_err(|_| Error::User(UserError::InvalidAccessKeyAccountId))?,
                            method_names,
                        }),
                    }
                };
                let action = AddKeyAction { public_key, access_key };
                near_action::Action::AddKey(action)
            }
            Action::DeleteKey { public_key_kind, public_key } => {
                let action = DeleteKeyAction {
                    public_key: construct_public_key(public_key_kind, &public_key)?,
                };
                near_action::Action::DeleteKey(action)
            }
        };
        Ok(action)
    }
