Based on my investigation, I found a genuine, self-documented integrity gap that matches the requested bug class — two logically distinct authenticated roots being treated as equivalent/ignored in a verification check, rather than the LP token bug's two variables being assigned the same address.

### Title
`ensure_match_transaction_info` skips verifying state/hot-state checkpoint and position-state-root hashes, allowing replay/chunk verification to accept a `TransactionInfo` with a diverged authenticated root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check that binds a locally computed `TransactionOutput` to the authenticated `TransactionInfo` carried in the ledger/accumulator (status, gas, write-set hash, event-root hash). The function explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the locally computed values, even though these fields are the authenticated Sparse-Merkle/JMT roots embedded in `TransactionInfoV0`/`V1` and are part of what the transaction accumulator ultimately commits to. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` validates `status`, `gas_used`, `write_set_hash` (against `state_change_hash`), and `event_root_hash`, but the code contains an explicit acknowledgement that the state checkpoint / hot-state / position-state root hashes are not compared: [2](#0-1) 

These skipped fields are exactly the authenticated Merkle roots produced by `DoStateCheckpoint::run` (`state_checkpoint_hashes`, `hot_state_checkpoint_hashes`, `position_state_checkpoint_hashes`) and threaded into `TransactionInfo` construction in `DoLedgerUpdate::assemble_transaction_infos`: [3](#0-2) [4](#0-3) 

`ensure_match_transaction_info` is used as an on-path verification: consumers call it to confirm a re-executed/replayed `TransactionOutput` still matches an already-committed `TransactionInfo` (used by `aptos-debugger`, the CLI, and `storage/db-tool/src/replay_on_archive.rs`). [5](#0-4) 

Because the state/hot-state/position-state checkpoint hashes are excluded from the comparison, a local state root that diverges from the authenticated one (e.g., due to a JMT/position-state bug, an incorrect `parent_position_state_summary`, or a divergent `hot_state_updates` application) will not be flagged by this check — the verification reports success while the underlying committed Merkle root is wrong.

### Impact Explanation
This directly weakens a proof/commitment-integrity invariant: verification tooling built on `ensure_match_transaction_info` can certify that replayed execution matches a historical `TransactionInfo` even when the state (or, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, the position-state) Merkle root diverges. This masks state-commitment divergence exactly in the class of hard-fork-relevant bugs the report's gate calls out — a wrong accumulator/state root accepted as "matching" during replay/restore verification.

### Likelihood Explanation
The gap is only exercised when there actually is a state-root divergence between local recomputation and the authenticated `TransactionInfo` — which should not occur in correct execution — so this is a "silent verifier" bug rather than something exploitable by an ordinary transaction. Its likelihood of mattering is tied to the probability of an independent state-root computation bug (e.g., in `do_state_checkpoint.rs`'s hot-state/position-state root logic) slipping through unnoticed because this specific safety net does not check for it. The code comment itself flags this as a known, unresolved gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating awareness but no fix at the time of this snapshot.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when present), and `position_state_checkpoint_hash` (when present) against the locally recomputed values, returning an error on mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any hot-state root verification) is enabled in consensus-relevant or replay-verification code paths.

### Proof of Concept
Not independently reproducible from static analysis alone: the code makes the gap explicit via its own TODO comment rather than requiring an exploit chain, but I could not fully trace (given tool budget) which replay paths are consensus-critical vs. purely offline (`replay_on_archive`, `aptos-debugger`) — this affects the practical severity and should be confirmed by tracing all three call sites (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `storage/db-tool/src/replay_on_archive.rs`) before treating this as a mainnet-critical finding versus a tooling-only gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
