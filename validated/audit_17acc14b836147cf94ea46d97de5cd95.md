### Title
Zero-value witness-root/coinbase-depth sentinel confusion allows forged Bitcoin transaction inclusion proofs for unregistered blocks - (File: crates/evm/src/evm/system_contracts/src/BitcoinLightClient.sol)

### Summary
`BitcoinLightClient._verifyInclusion` (and by extension `verifyInclusion(blockHash,...)`/`verifyInclusion(blockNumber,...)`) treats the default (unset) mapping value `0` for both `witnessRoots[_blockHash]` and `coinbaseDepths[_blockHash]` as legitimate data rather than "block not recorded," mirroring the Gondi `_checkValidators` bug where an unvalidated zero sentinel let a check be skipped entirely.

### Finding Description
`setBlockInfo` populates `witnessRoots[_blockHash]` and `coinbaseDepths[_blockHash]` only for block hashes that have actually been recorded via the system caller [1](#0-0) . For any `_blockHash` that was never registered, Solidity's default mapping value is returned: `witnessRoots[_blockHash] == bytes32(0)` and `coinbaseDepths[_blockHash] == 0`.

`_verifyInclusion` does not check whether the block hash was actually registered — it uses these zero defaults directly in the proof check: [2](#0-1) 

If a caller supplies an unregistered `_blockHash`, `coinbaseDepths[_blockHash]` is `0`, so the check `require(_proof.length == coinbaseDepths[_blockHash] * HASH_LENGTH, ...)` is satisfied trivially by supplying an empty `_proof` (length 0). Then `ValidateSPV.prove(_wtxId, _witnessRoot, _proof, _index)` is called with `_witnessRoot = 0` and an empty proof; with a 0-length Merkle path, `ValidateSPV.prove` degenerates to a direct equality check between `_wtxId` and the (zero) root. Thus supplying `_wtxId = bytes32(0)` (the canonical, standard witness-txid of a Bitcoin coinbase transaction under BIP141) against *any never-registered block hash* returns `true` from `verifyInclusion`.

The contract's own doc comment acknowledges the ambiguity of a zero witness root but does not add any mitigation in the verification path itself: [3](#0-2) . This is the same root-cause pattern as the referenced Gondi finding: a legitimate "real" value (tokenId 0 / witness root 0) is indistinguishable from the "unset" sentinel, and the validating function's branch structure silently treats "unset" as "passes."

### Impact Explanation
`verifyInclusion` is the primitive `Bridge.sol`'s `validateAndCheckInclusion` relies on to assert that a `moveTx` (deposit) transaction was actually included in a specific Bitcoin block before minting cBTC [4](#0-3) . However, in `deposit()`/`replaceDeposit()` the block hash passed is always the one registered by `setBlockInfo`/`proof.blockHeight` resolved through `blockHashes[_blockNumber]`, which for an un-set block number is `bytes32(0)`; an attacker cannot control `proof.blockHeight` mapping to an arbitrary attacker-chosen hash inside `Bridge.sol` itself since it goes through the `blockHashes` mapping. The exploitable surface is the externally-callable `BitcoinLightClient.verifyInclusion(bytes32,...)` (the blockHash-keyed overload) and `verifyInclusion(uint256,...)`, which any third-party contract or off-chain integrator on Citrea may call directly, expecting `true` to mean "this witness transaction id is included in this specific Bitcoin block." Given the analog-scope restriction to rollup-binding breaks reachable without privileged roles, this degrades to a **honest node/consumer served a proof result that contradicts the real Bitcoin DA state** for any block hash never reported by the sequencer/system caller — i.e., `verifyInclusion` returns true for a block that was never proven to exist, which breaks the binding "the blob/tx set proved == the blob/tx set that actually happened in that Bitcoin block." Within the strict in-scope Solidity system-contract path this is a genuine DA-integrity violation of the light client's core guarantee, though it does not by itself let an attacker mint cBTC through `Bridge.sol`'s `deposit` flow (which is bounded to hashes recorded through `blockHashes`).

### Likelihood Explanation
Medium: the wtxId of a coinbase transaction is canonically `0x00...00` under BIP141, so an attacker doesn't need to find a preimage — they only need to pick a `_blockHash` value that was never passed to `setBlockInfo` (trivial, since any hash outside the small set of real recorded Bitcoin blocks qualifies) and call the public `verifyInclusion` function with an empty proof. No privileged role is required; this call is fully permissionless and unauthenticated at the contract level.

### Recommendation
Explicitly track which block hashes have been registered (e.g., a `mapping(bytes32 => bool) public isRegisteredBlockHash`, or check `blockHashes[proof.blockHeight] == _blockHash` inside `_verifyInclusion`) and revert if the block hash is unregistered, instead of relying on the ambient zero-default of `witnessRoots`/`coinbaseDepths` to imply "no such block."

### Proof of Concept
1. Deploy/observe the live `BitcoinLightClient` at `0x3100000000000000000000000000000000000001`; note only some block hashes have been registered via `setBlockInfo`.
2. Choose `attackerBlockHash` — any 32-byte value that has never been passed to `setBlockInfo` (e.g., `keccak256("never-registered")`).
3. Call `verifyInclusion(attackerBlockHash, bytes32(0), "", 0)`.
4. Inside `_verifyInclusion`: `coinbaseDepths[attackerBlockHash] == 0`, so `require(_proof.length == 0)` passes with the empty proof; `witnessRoots[attackerBlockHash] == bytes32(0)`, so `ValidateSPV.prove(bytes32(0), bytes32(0), "", 0)` returns `true` because the zero-length proof path degenerates to `_wtxId == _witnessRoot`.
5. The call returns `true`, asserting that wtxid `0x00..00` is included in `attackerBlockHash`, even though `attackerBlockHash` was never reported to the contract by the system caller — demonstrating a forged DA-inclusion result for a block that was never observed.

    function setBlockInfo(bytes32 _blockHash, bytes32 _witnessRoot, uint256 _coinbaseDepth) external onlySystem {
        uint256 _blockNumber = blockNumber;
        require(_blockNumber != 0, "Not initialized");
        blockHashes[_blockNumber] = _blockHash;
        blockNumber = _blockNumber + 1;
        witnessRoots[_blockHash] = _witnessRoot;
        coinbaseDepths[_blockHash] = _coinbaseDepth;
        emit BlockInfoAdded(_blockNumber, _blockHash, _witnessRoot, _coinbaseDepth);
    }

    function _verifyInclusion(bytes32 _blockHash, bytes32 _wtxId, bytes calldata _proof, uint256 _index) internal view returns (bool) {
        require(_proof.length == coinbaseDepths[_blockHash] * HASH_LENGTH, "Invalid proof length");
        bytes32 _witnessRoot = witnessRoots[_blockHash];
        return ValidateSPV.prove(_wtxId, _witnessRoot, _proof, _index);
    }

    function validateAndCheckInclusion(Transaction calldata txn, MerkleProof calldata proof) internal view returns (bytes32, uint256) {
        bytes32 wtxId = WitnessUtils.calculateWtxId(txn.version, txn.flag, txn.vin, txn.vout, txn.witness, txn.locktime);
        require(BTCUtils.validateVin(txn.vin), "Vin is not properly formatted");

        return (wtxId, nIns);
    }
