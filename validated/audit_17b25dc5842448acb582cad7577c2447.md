## Finding

### Title
Purged L1-handler transaction records allow a previously consumed/committed L1→L2 message to be re-added as pending and re-executed - (File: crates/apollo_l1_events/src/transaction_manager.rs)

### Summary
The `TransactionManager` in `apollo_l1_events` tracks the lifecycle of every L1→L2 message (`LogMessageToL2`) so that a message that has already been included in an L2 block (`Committed`) or consumed on L1 (`Consumed`) can never be proposed/validated again. This replay protection lives entirely in the in-memory `records: Records` map. Once a message's timelock passes, its record is unconditionally deleted (`clear_old_tx_from_consumed_queue`, `finalize_cancellation`). If the scraper subsequently re-observes the same `LogMessageToL2` event (re-scrape, L1 reorg replaying old blocks, or the scraper resuming from a stale checkpoint after a restart), `add_tx` finds no existing record and calls `create_record_if_not_exist`, which creates a brand-new `Pending`/proposable record for that hash - with no memory that the message was already consumed on L1 or already executed on L2. This is structurally the same failure mode as the Optimism H-2 bug: replay protection is enforced by reading a piece of state (`successfulMessages` / here, `records`) that is wiped/pruned, so once that state is gone the "already relayed" check silently passes and the message can be relayed (executed) a second time.

### Finding Description
`TransactionManager::consume_tx` marks a record `Consumed` and enqueues it in `consumed_queue`; `clear_old_tx_from_consumed_queue` later removes the record from `self.records` entirely once the consumption timelock has passed: [1](#0-0) [2](#0-1) 

Similarly, `finalize_cancellation` unconditionally removes the record from `self.records`: [3](#0-2) 

Once a record is gone, `add_tx` treats a subsequent scrape of the *same* `LogMessageToL2` event as brand new, creating a fresh `Pending` record and indexing it into `proposable_index` (making it eligible for `get_txs`/`validate_tx` and therefore inclusion in a future block): [4](#0-3) 

The code's own comment acknowledges the class of bug: "if we get the same full tx twice (from the scraper) it could indicate a double-scrape, and **may cause the tx to be re-added to the proposable index**" - but this guard only fires when the record is *still present* (`TransactionPayload::Full` branch); it provides no protection once the record has been purged. `validate_tx`'s replay check (`AlreadyIncludedOnL2` / `ConsumedOnL1`) is likewise entirely dependent on the record still existing: [5](#0-4) 

This exactly mirrors the Optimism report: an authoritative "already relayed" check (`successfulMessages[oldHash] == false` there, `records.get(&tx_hash)` here) is trusted to persist, but the underlying storage is deliberately pruned (predeploy wipe there, timelock-based `records.remove` here), so once pruned, the check can no longer detect a message that was already relayed/consumed, and a resubmission of the identical message is treated as fresh and proposable again.

### Impact Explanation
If a purged `LogMessageToL2` event is re-ingested (e.g. the scraper restarts from a checkpoint block-number below the point where the message was already consumed and its record pruned, or L1 reorg/log-replay causes the identical event to be re-delivered), the L1 handler transaction becomes `Pending` again and can be staged, validated, and executed by the batcher/blockifier a second time. Because L1-handler transactions typically mint/mint-and-transfer bridged ETH/ERC-20 tokens to an L2 contract_address based on the message payload, re-execution results in double-crediting the recipient - a direct double-spend of bridged assets, i.e. concrete loss of funds for the bridge/protocol.

### Likelihood Explanation
The purge is not an edge case: it is standard, expected behavior driven by the configured `l1_handler_consumption_timelock_seconds`, meaning every consumed message's record is guaranteed to be deleted eventually. Any subsequent re-delivery of the same on-chain event to the scraper - whether via checkpoint/restart behavior of the scraper's `last_scraped_block` tracking, a deep L1 reorg that the scraper re-processes, or an L1 RPC provider replaying historical logs - is sufficient to trigger the vulnerable path, with no attacker action against the sequencer itself required (the only "attacker-controlled" element is the original, legitimate L1 message). This requires no privileged actor, matching the rule to keep only analogs reachable via an ordinary L1 message sender.

### Recommendation
1. Do not rely solely on a pruned in-memory `records` map for permanent replay protection. Persist an append-only, non-expiring set of "ever consumed" / "ever committed" L1 message hashes (or nonces), and consult it in `add_tx`/`validate_tx` regardless of whether the full record still exists.
2. When `add_tx` is called for a hash that is not currently in `records`, check this durable "seen" set before creating a new `Pending` record; if the hash was previously consumed/committed, reject/ignore the event instead of silently re-admitting it.
3. Ensure the scraper's checkpoint (`last_scraped_block`)/L1Events provider state is durably persisted at least as far forward as any pruned/consumed record, so a restart cannot rescan a range containing already-purged messages.

### Proof of Concept
Conceptual reproduction using the existing test harness pattern (`crates/apollo_l1_events/tests/flow_test_consumed.rs`):
1. Emit a `LogMessageToL2` event for tx `T` → `add_tx` creates a `Pending` record for `T`.
2. `T` is proposed, executed, and committed → `commit_txs` marks `T` `Committed`.
3. Emit `ConsumedMessageToL2` for `T` → `consume_tx` marks it `Consumed` and schedules it in `consumed_queue`.
4. Advance the clock past `l1_handler_consumption_timelock_seconds` and trigger `clear_old_tx_from_consumed_queue` (called on the next `consume_tx`) → `T`'s record is deleted from `self.records`.
5. Re-deliver the identical `LogMessageToL2` event for `T` (simulating scraper restart from a stale checkpoint or L1 log replay) → `add_tx` sees no existing record, calls `create_record_if_not_exist`, and re-inserts `T` as `Pending`, adding it to `proposable_index`.
6. `T` is now returned by `get_txs`/passes `validate_tx` and can be executed a second time by the blockifier, double-crediting whatever asset the L1 handler mints/transfers on L2. [6](#0-5) [7](#0-6) 

*Note on confidence*: I was not able to fully verify within the available tooling whether the `apollo_l1_events` provider's scraper checkpoint (`last_scraped_block`/`start_height`) is durably persisted to disk in a way that always stays ahead of purged/consumed records, or whether some other safeguard elsewhere in the scraper (`crates/apollo_l1_events/src/l1_scraper.rs`) prevents re-delivery of already-processed L1 blocks after a restart. The vulnerability's root cause - `records` being the sole source of truth for replay detection and being unconditionally pruned - is confirmed directly in the code, but the exact reachability path (restart vs. reorg vs. provider-level log replay) would benefit from further runtime/integration verification.

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    /// Adds a transaction to the transaction manager, return true if the transaction was
    /// successfully added. If the transaction is occupied or already had its hash stored as
    /// committed, it will not be added, and false will be returned.
    // Note: if only the committed hash was known, the transaction will "fill in the blank" in the
    // committed txs storage, to account for commit-before-add tx scenario.
    pub fn add_tx(
        &mut self,
        tx: L1HandlerTransaction,
        block_timestamp: BlockTimestamp,
        scrape_timestamp: UnixTimestamp,
    ) {
        let tx_hash = tx.tx_hash;
        // If exists, return false and do nothing. If not, create the record as a HashOnly payload.
        let is_new_record = self.create_record_if_not_exist(tx_hash);
        // Replace a HashOnly payload with a Full payload. Do not update a Full payload.
        // A hash only payload can come from catching up from state sync, and then updated by
        // add_events from the scraper. However, if we get the same full tx twice (from the scraper)
        // it could indicate a double-scrape, and may cause the tx to be re-added to the proposable
        // index.
        self.with_record(tx_hash, move |record| match &record.tx {
            TransactionPayload::HashOnly(_) => {
                if !is_new_record {
                    info!(
                        "Transaction {tx_hash} already exists as a HashOnly payload. It was \
                         probably gotten via state sync component, and is now updated with a Full \
                         payload."
                    );
                }
                record.tx.set(tx, block_timestamp, scrape_timestamp);
                // Counts the HashOnly -> Full transition, regardless of whether the HashOnly
                // was just created here or pre-existed from state sync.
                L1_MESSAGE_SCRAPER_L1_HANDLER_TX_COUNT.increment(1);
            }
            TransactionPayload::Full { tx: _, created_at_block_timestamp: _, scrape_timestamp } => {
                warn!(
                    "Transaction {tx_hash} already exists as a Full payload, scraped at \
                     {scrape_timestamp}. This could indicate a double scrape. Ignoring the new \
                     transaction."
                );
            }
        });
    }

    pub fn finalize_cancellation(&mut self, tx_hash: TransactionHash) {
        let Some(record) = self.records.get(&tx_hash) else {
            info!(
                "Attempted to finalize cancellation for non-existent transaction: {tx_hash}. This \
                 can happen if the transaction was too old to be scraped (e.g. it was created \
                 before we started scraping)."
            );
            return;
        };

        // Regardless of the state of the tx in the record, if we get the cancellation event from
        // the L1 contract, we delete this tx from the records and from the proposable index, even
        // if it was Pending and ready to be proposed (which is not supposed to happen, hence the
        // warning).
        if record.state != TransactionState::CancellationStartedOnL2 {
            warn!(
                "Attempted to finalize cancellation for transaction {tx_hash} that is not in the \
                 cancellation started on L2 state, but in the {:?} state.",
                record.state
            );
        }
        // This will also call maintain_indices to remove the tx from the proposable index.
        self.with_record(tx_hash, |r| r.mark_cancellation_finalized_on_l1());
        self.records.remove(&tx_hash);
    }

    pub fn consume_tx(
        &mut self,
        tx_hash: TransactionHash,
        consumed_at: BlockTimestamp,
        unix_now: u64,
    ) -> Result<(), BlockTimestamp> {
        self.clear_old_tx_from_consumed_queue(unix_now);

        let Some(record) = self.records.get(&tx_hash) else {
            debug!(
                "Attempted to consume an unknown transaction: {tx_hash}. This can happen if the \
                 transaction was too old to be scraped (e.g. it was created before we started \
                 scraping)."
            );
            return Ok(());
        };

        // Double consumption is a bug.
        if let Some(previously_consumed_at) = record.get_consumed_at_timestamp() {
            return Err(previously_consumed_at);
        }

        // Mark the transaction as consumed.
        self.with_record(tx_hash, |record| record.mark_consumed(consumed_at));
        Ok(())
    }

    pub fn clear_old_tx_from_consumed_queue(&mut self, unix_now: u64) {
        let cutoff =
            unix_now.saturating_sub(self.config.l1_handler_consumption_timelock_seconds.as_secs());
        let still_timelocked = self.consumed_queue.split_off(&BlockTimestamp(cutoff));
        let passed_timelock = std::mem::replace(&mut self.consumed_queue, still_timelocked);
        for tx_hashes in passed_timelock.values() {
            for tx_hash in tx_hashes {
                self.records.remove(tx_hash);
