## Analog Found

### Title
Non-injective canonical key construction in `GetInboundUniversalTxKey` / `GetPcUniversalTxKey` allows field-boundary collisions between distinct UniversalTx identities - (File: `x/uexecutor/types/keys.go`)

### Summary
The reported MatterLabs bug is a classic "ambiguous field packing" defect: `pack_key` combined multiple sub-fields into one linear-combination value using the wrong bit offset, letting bits from one field bleed into another and corrupt the derived ordering key. Push Chain's `x/uexecutor` module has the same *bug class* — not bit-packing, but delimiter-based string packing — in the functions that derive on-chain identity keys for inbound/outbound transactions. Some of these functions concatenate variable-length fields with a fixed `":"` delimiter and hash the whole string once, instead of hashing each field independently before joining (the pattern the codebase itself documents and uses correctly elsewhere via `hashFields`).

### Finding Description
`GetInboundUniversalTxKey` derives the canonical identity of an inbound UniversalTx: [1](#0-0) 

and `GetPcUniversalTxKey` does the same for Push-originated (outbound) transactions: [2](#0-1) 

Both build the preimage with `fmt.Sprintf("%s:%s:...")` and hash the resulting string once. This is the same pattern MatterLabs fixed: because `SourceChain` (a CAIP-2 identifier such as `"eip155:11155111"`) already contains a `:`, and `TxHash`/`LogIndex` fall back to raw, un-canonicalized, trimmed strings whenever `CanonicalizeTxHashByNamespace` / `CanonicalizeAddressByNamespace` don't recognize the chain's namespace: [3](#0-2) [4](#0-3) 

two logically distinct `(source_chain, tx_hash, log_index)` tuples can serialize to the identical byte string if a delimiter character shifts across a field boundary (e.g. `chain="A", txHash="B:C", logIndex="D"` vs. `chain="A:B", txHash="C", logIndex="D"` both yield `"A:B:C:D"`). The `GetTssBallotKey` and `GetFundMigrationBallotKey` functions in `x/utss` share the identical unsafe pattern: [5](#0-4) 

The codebase's own `hashFields` helper — used for `GetInboundBallotKey` / `GetOutboundBallotKey` — explicitly documents why this matters and how it was fixed for the ballot digests: per-field hashing makes the digest injective because a sub-hash can never contain the `:` delimiter, so no field value can shift a boundary: [6](#0-5) 

This confirms the team already recognized and fixed exactly this bug class in one code path (ballot keys) but left the UTX-identity keys (`GetInboundUniversalTxKey`, `GetPcUniversalTxKey`) and the `utss` ballot keys on the older, non-injective construction.

### Impact Explanation
If two distinct inbound observations can be crafted (or coincidentally arise, e.g. through a chain whose namespace falls into the `default:` passthrough branch of `CanonicalizeTxHashByNamespace`/`CanonicalizeAddressByNamespace`) to serialize to the same preimage string, `GetInboundUniversalTxKey` would return the same UTX identity for two different underlying events. That collapses `PendingInbounds`/`UniversalTx` records keyed by this hash, potentially causing one event's vote accounting or execution state to be attributed to, or overwritten by, another — corrupting canonical UniversalTx identity and downstream vote/finalization logic that assumes the UTX key uniquely identifies one logical (source_chain, tx_hash, log_index) tuple.

### Likelihood Explanation
Likelihood is **low in practice today**. For the currently-supported namespaces (`eip155`, `solana`), `TxHash` is strictly canonicalized to a fixed-length hex string with no delimiter characters, and `SourceChain` values are drawn from a finite, admin-registered set of CAIP-2 identifiers in `x/uregistry` rather than being freely attacker-chosen. Exploitation would require either a registered chain whose namespace hits the `default:` passthrough (unvalidated, attacker-shaped `TxHash`/address strings) or a `LogIndex` value that is not constrained to digits before reaching `GetInboundUniversalTxKey`; I could not confirm from the available index whether `Inbound.ValidateBasic` enforces a numeric-only format for `LogIndex`, which materially affects real-world exploitability.

### Recommendation
Route `GetInboundUniversalTxKey`, `GetPcUniversalTxKey`, `GetTssBallotKey`, and `GetFundMigrationBallotKey` through the same injective `hashFields`-style construction (hash each field independently before joining with `:`) that is already used for `GetInboundBallotKey`/`GetOutboundBallotKey`, eliminating any field-boundary ambiguity regardless of future namespace additions or validation gaps.

### Proof of Concept
Conceptual (not confirmed exploitable end-to-end due to current input constraints):
```
Tuple A: SourceChain="chainX:1", TxHash="abc", LogIndex="0"  → "chainX:1:abc:0"
Tuple B: SourceChain="chainX",   TxHash="1:abc", LogIndex="0" → "chainX:1:abc:0"
sha256("chainX:1:abc:0") is identical for both → same GetInboundUniversalTxKey,
even though they represent different (chain, tx, log_index) triples.
```
This requires either a registered chain namespace that falls through `CanonicalizeTxHashByNamespace`'s `default:` branch (passthrough, no format enforcement) or confirmation that `LogIndex`/`TxHash` are not strictly digit/hex-validated before key derivation — both of which need direct code confirmation beyond what the indexed context provided.

// GetInboundUniversalTxKey: UTX identity from canonical (source_chain, tx_hash,
// log_index). Canonicalizes locals; caller's inbound is not mutated.
func GetInboundUniversalTxKey(inbound Inbound) string {
	chain := strings.TrimSpace(inbound.SourceChain)
	txHash := utils.LenientCanonicalizeTxHash(chain, inbound.TxHash)
	logIndex := strings.TrimSpace(inbound.LogIndex)
	data := fmt.Sprintf("%s:%s:%s", chain, txHash, logIndex)
	hash := sha256.Sum256([]byte(data))
	return hex.EncodeToString(hash[:]) // hash[:] converts [32]byte → []byte
}
```

// hashFields = sha256( hex(sha256(domain)) : hex(sha256(f0)) : ... ). Per-field
// hashing makes it injective — a sub-hash can't contain ':', so no field value
// can shift a boundary and collide with a different tuple.
func hashFields(domain collections.Prefix, parts ...string) string {
	hashed := make([]string, 0, len(parts)+1)
	d := sha256.Sum256(domain.Bytes())
	hashed = append(hashed, hex.EncodeToString(d[:]))
	for _, p := range parts {
		sum := sha256.Sum256([]byte(p))
		hashed = append(hashed, hex.EncodeToString(sum[:]))
	}
	final := sha256.Sum256([]byte(strings.Join(hashed, ":")))
	return hex.EncodeToString(final[:])
}
```

// CanonicalizeTxHashByNamespace canonicalizes a transaction hash/signature
// for the given CAIP-2 chain. Empty input passes through (e.g. failed
// outbound observations carry no hash).
func CanonicalizeTxHashByNamespace(chain, txHash string) (string, error) {
	txHash = strings.TrimSpace(txHash)
	if txHash == "" {
		return "", nil
	}
	switch CAIP2Namespace(chain) {
	case namespaceEVM:
		return CanonicalizeEVMHash(txHash)
	case namespaceSolana:
		return canonicalizeSolanaTxHash(txHash)
	default:
		return txHash, nil
	}
}

// LenientCanonicalizeTxHash canonicalizes txHash for chain, falling back to
// the trimmed input when it does not parse.
func LenientCanonicalizeTxHash(chain, txHash string) string {
	canon, err := CanonicalizeTxHashByNamespace(chain, txHash)
	if err != nil {
		return strings.TrimSpace(txHash)
	}
	return canon
}
