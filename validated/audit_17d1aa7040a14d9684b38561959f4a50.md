### Title
Unconditional Relayer Fee Payment in `WalletContract::rlp_execute` Not Gated on Underlying Action Success — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract emulates Ethereum EOA transactions and pays a relayer `fee` for base-token and ERC-20 (NEP-141) transfers. This fee is dispatched as an independent, unconditional promise created *before* the actual user-requested action (the base token transfer or the `ft_transfer`/`storage_deposit` + `ft_transfer` chain) is even attempted, and it is never linked to (or gated by) the success of that action. This mirrors the reported bug class: a caller acts on the assumption that an operation succeeded (or ignores whether it did) and moves value regardless of whether the underlying operation reverted/failed.

### Finding Description
In `inner_rlp_execute`, for `EthEmulationKind::EOABaseTokenTransfer` and `EthEmulationKind::ERC20Transfer` with a non-zero `fee`, the contract immediately creates a *separate* promise batch to pay the relayer, unconnected to the main promise chain: [1](#0-0) 

This `refund_promise` (the relayer's compensation) is fired off via `env::promise_batch_create` / `env::promise_batch_action_transfer` completely independently of the `promise` variable constructed afterward for the actual action (lines 412-471), which is the one whose result is eventually checked in `rlp_execute_callback`: [2](#0-1) 

Because the fee-paying promise is not `.then()`-chained to the action promise, its execution and the transfer of NEAR to the relayer proceed regardless of whether the follow-on action (`ft_transfer`, `storage_deposit`+`ft_transfer`, or the native `Transfer` action) ultimately fails. When the action does fail, `rlp_execute_callback` only refunds the `caller_deposit` (the `attached_deposit` value the user attached for the action itself, tracked via `CallerDeposit`) — it never returns or accounts for the `fee` that was already sent out: [3](#0-2) [4](#0-3) 

This is directly analogous to the reported Solidity bug: the router contract paid out (`safeTransfer`) as if `mToken.mint()` had succeeded, without checking its return value. Here, the wallet contract pays the relayer as if the transfer will succeed, without gating that payment on the actual `PromiseResult` of the transfer.

### Impact Explanation
Any transaction signer (an unprivileged EOA-emulated user) or a relayer submitting a signed transaction on their behalf can construct or encounter a scenario where:
1. The base-token `Transfer` action or the NEP-141 `ft_transfer` fails (e.g., insufficient token balance on the wallet, receiver-side `storage_deposit`/`ft_transfer` panics, gas exhaustion in the token contract call, or an intentionally malicious/unregistered `target`/token contract).
2. The `fee` NEAR is still unconditionally transferred out of the wallet contract's balance to the relayer (`predecessor_account_id`), because that promise was already dispatched before the outcome of the action was known.
3. `rlp_execute_callback` reports the failure and refunds only the `caller_deposit` (the action's attached deposit), but the fee is permanently gone — a real, unrecoverable loss of NEAR from the wallet's balance with no corresponding service rendered (no successful transfer occurred).

This constitutes unauthorized value movement out of the wallet contract: NEAR tokens leave the user's wallet balance to the relayer even though the transaction the user intended to pay for never executed successfully. A colluding or opportunistic relayer benefits from failed transactions at the wallet owner's expense.

### Likelihood Explanation
This is trivially reachable by any relayer/transaction submitter interacting with `rlp_execute` for `ERC20Transfer` or `EOABaseTokenTransfer` transaction kinds with a non-zero fee — no special privileges, validator status, or network-level position are required. A relayer only needs to submit (or be handed) a signed Ethereum-style transaction whose target action is set up to fail (e.g., transferring more tokens than the wallet holds, or targeting a token contract requiring unmet preconditions) while the `fee` field is non-zero.

### Recommendation
Chain the relayer-fee payment onto the same promise as the main action (or delay its dispatch until `rlp_execute_callback`), so it is only paid out conditionally on `PromiseResult::Successful`. Alternatively, refund the fee together with `caller_deposit` in the `PromiseResult::Failed` branch of `rlp_execute_callback` if the fee was already sent, or reserve/burn it from wallet balance only after confirming the action succeeded.

### Proof of Concept
1. Deploy a Wallet Contract instance and fund it with NEAR and NEP-141 tokens.
2. Construct an RLP-encoded Ethereum transaction representing an `ERC20Transfer` (or `EOABaseTokenTransfer`) with `fee > 0`, but set the transfer `amount` greater than the wallet's actual token balance (or point `target` at a token contract that will make `ft_transfer` panic).
3. Submit this transaction via `rlp_execute` through any relayer account.
4. Observe: `inner_rlp_execute` dispatches the `refund_promise` fee transfer to the relayer unconditionally (`lib.rs:381-384`); the subsequent `ft_transfer` (or native transfer) action fails; `rlp_execute_callback` returns `success: false` and refunds only `caller_deposit`, while the relayer has already been paid the `fee` from the wallet's NEAR balance, despite no token/value transfer having occurred.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
