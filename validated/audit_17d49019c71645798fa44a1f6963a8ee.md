### Title
Stale cached borrow-index reused after `vault-system-repay` mutates the real vault index in `liquidate()` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate()` in `v0-4-market.clar` populates a local index cache once at the start of the call via `accrue-user-debts`/`accrue-user-collateral`, and repeatedly reads it through `get-cached-indexes`. After the debt/collateral accounting is computed from this cache, the function calls `vault-system-repay`, which internally invokes the target vault's own `accrue()` and mutates the vault's on-chain `index` variable. The market contract's local cache is never refreshed after this mutation, yet it is read again afterward (`other-borrow-idx`) to compute `other-debt-repayable`, which feeds into the bad-debt-socialization decision (`no-collateral-left`).

### Finding Description
`liquidate()` begins by explicitly accruing and caching indexes for the purpose of resolving zToken prices/debt values: [1](#0-0) 

All debt/collateral notional and liquidation-size calculations (`process-debt-asset`, `scale-debt-for-liquidation`, `remaining-debt-to-repay`) read the borrow index through `get-cached-indexes`: [2](#0-1) 

The function then executes the actual repayment against the underlying vault: [3](#0-2) 

`vault-system-repay` routes to the underlying vault contract's `system-repay`, which (like `system-borrow`) calls `accrue()` first, mutating the vault's persisted `index`/`lindex` state variables: [4](#0-3) 

After this on-chain mutation, `liquidate()` computes `other-debt-repayable` for bad-debt socialization by reading the borrow index **again through the same unrefreshed local cache**: [5](#0-4) 

The `other-borrow-idx` binding here calls `get-cached-indexes debt-aid` — the identical cache populated before `vault-system-repay` ran, and never invalidated when the vault's real index moved as a side-effect of that call.

### Impact Explanation
`other-debt-repayable` directly determines `no-collateral-left`, which controls whether the protocol writes off (socializes) a borrower's remaining debt as bad debt. Using a stale, pre-repay index here means the write-off/no-write-off decision and the exact bad-debt amount can diverge from the true, freshly-accrued debt value. Over-estimating collateral coverage from a stale (lower) index can cause debt to be incorrectly written off, permanently misallocating protocol funds (socialized loss). This lands on "permanent freezing/insolvency of protocol funds" impact class, since it silently corrupts the bad-debt accounting used for socialization, an economically significant state mutation, not merely a cosmetic read.

### Likelihood Explanation
This triggers on every liquidation with `coll-remaining > 0`, i.e. whenever collateral is not entirely exhausted by the primary liquidation event, which is a common code path (not an edge case), all within a single transaction — no attacker interaction beyond calling `liquidate()` normally. The interleaving is deterministic under Clarity's left-to-right, sequential evaluation of `let` bindings and does not require any adversarial timing.

### Recommendation
Re-fetch (or force accrual/re-cache) the borrow index for `debt-aid` after `vault-system-repay` completes, before computing `other-debt-repayable`/`remaining-debt-to-repay`-dependent state, so that bad-debt socialization uses the post-repay, up-to-date index rather than the pre-repay cached value.

### Proof of Concept
1. Borrower has a liquidatable position with debt asset `debt-aid` and multiple collateral positions such that after paying the primary liquidation slice, `coll-remaining > 0`.
2. `liquidate()` caches `debt-aid`'s borrow index via `accrue-user-debts` at the top of the function.
3. All liquidation-size math (`debt-final`, `scaled-to-remove`, `debt-to-repay`) is computed from this cached index.
4. `vault-system-repay` is called, internally executing the vault's `accrue()` (a real state mutation increasing `index`/`lindex` by any elapsed-time based interest, and possibly minting treasury LP tokens).
5. Immediately after, `liquidate()` computes `other-borrow-idx` via `get-cached-indexes debt-aid` again — returning the pre-step-4 (stale) index instead of the vault's now-updated index.
6. `other-debt-repayable` (and therefore the bad-debt socialization outcome `no-collateral-left`) is computed off this stale index, diverging from the actual, currently-accrued debt figure. [6](#0-5) [4](#0-3)
