### Title
Unbounded recursive receipt-tree walk in `get_recursive_transaction_results` causes stack overflow on transaction-status queries - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` recursively walks the receipt-outcome tree produced by a transaction with **no depth limit**, unlike the functionally identical `GetReceiptToTx` chain-walk in the view client, which was explicitly capped at `MAX_DEPTH=1000` with a `DepthExceeded` error after the same unbounded-recursion risk was identified there. A transaction/contract can produce an arbitrarily long chain of dependent receipts (via chained cross-contract calls or yield/resume "self-recursion" patterns), and any unprivileged RPC caller querying that transaction's status (`tx`, `tx_status`, `EXPERIMENTAL_tx_status`) drives the node into this unbounded recursion, risking a native stack overflow and process crash — the same bug class as PaddlePaddle's `lu_unpack` recursive-decomposition stack overflow (GHSA-g57v-2687-jx33 / CVE-2023-52307).

### Finding Description
`get_recursive_transaction_results` recurses once per receipt id found in each outcome's `receipt_ids`: [1](#0-0) 

There is no depth counter, no iterative work-list, and no bound analogous to what protects the sibling code path. Compare this to `GetReceiptToTx`'s handler, which walks the *reverse* pointer chain (`ReceiptToTx` → parent) and explicitly guards against exactly this hazard: [2](#0-1) 

That test demonstrates the near team's own recognition that a 1000+ hop chain of receipt/tx references is achievable and dangerous enough to warrant an explicit `MAX_DEPTH` + `DepthExceeded` guard. `get_recursive_transaction_results` (used by `get_final_transaction_result`, which backs the `tx`/`tx_status`/`EXPERIMENTAL_tx_status` JSON-RPC methods via `ViewClientActor::get_tx_status` → `chain.get_partial_transaction_result_option`/`get_transaction_result_with_receipt`) has no such protection.

An attacker-controlled contract can produce a deep chain of dependent receipts through repeated cross-contract "self" calls, as demonstrated by the existing test contract method: [3](#0-2) 

which the integration test confirms can reach depths in the hundreds within a single transaction's gas budget: [4](#0-3) 

Because yield/resume lets a receipt pause for up to `yield_timeout_length_in_blocks` (200) blocks without the gas cost of a full new cross-contract dispatch, a contract can extend this same self-chaining pattern well beyond the ~221 hops achievable through plain promise chaining, pushing the receipt-outcome tree traversed by `get_recursive_transaction_results` past whatever stack depth a query-serving thread can tolerate. Any RPC caller who later asks for that transaction's status forces the node to walk (and stack-allocate a frame per level of) that entire chain.

### Impact Explanation
A successful trigger crashes the RPC-serving process (stack overflow aborts the thread/process) when any client queries the status of a maliciously crafted transaction. This is a transaction-triggered halt of a chunk-producing/RPC node reachable by an unprivileged contract deployer plus an unprivileged RPC caller — matching the "transaction-triggered halt" acceptance criterion, and directly analogous in root cause to the PaddlePaddle `lu_unpack` unbounded-recursion stack overflow.

### Likelihood Explanation
Medium: constructing a very deep chain requires deploying and driving a self-recursing/yield-looping contract over multiple blocks, and the exact frame count needed to actually overflow a given thread's stack is implementation/OS-dependent. However, the existence of a same-shaped, already-fixed bug (`GetReceiptToTx`'s `MAX_DEPTH=1000`) strongly indicates the nearcore team considers ~1000-hop chains realistically achievable in this exact class of receipt-chain recursion, and no equivalent guard exists on this path.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative, work-list-based traversal (as already done for `flatten_nodes`, `get_subtree_size`, and trie iteration elsewhere in the codebase), or add an explicit depth/hop limit with a `DepthExceeded`-style error, mirroring the fix already applied to `GetReceiptToTx`.

### Proof of Concept
1. Deploy a contract using the `max_self_recursion_delay`/yield-resume self-chaining pattern shown in `runtime/near-test-contracts/test-contract-rs/src/lib.rs:887-921`, but structured to re-yield on each resume so the chain extends across many blocks rather than being capped by a single prepaid-gas budget.
2. Submit the initiating transaction; let it execute across enough blocks/epochs to build a receipt-outcome chain deep enough to exceed the target node's stack budget for this recursive function (order of magnitude comparable to, or beyond, the 1000-hop threshold the team itself used for `GetReceiptToTx`'s fix).
3. As any unprivileged client, call `tx`/`tx_status`/`EXPERIMENTAL_tx_status` for that transaction hash.
4. The RPC/view-client node recurses through `get_recursive_transaction_results` without any depth bound, exhausting the call stack and crashing the node process that served the query.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);

        }

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}
