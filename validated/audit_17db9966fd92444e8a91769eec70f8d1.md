### Title
Relayer fee refund is paid unconditionally in the NEAR Wallet Contract regardless of whether the emulated transfer action actually succeeds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Mochi report flags `DutchAuctionLiquidator` treating an ERC20 `transfer`/`transferFrom` call as successful without checking its actual outcome, letting a failed value-transfer be accounted as valid. The reachable nearcore analog is in the `near-wallet-contract` (EVM-emulation wallet), where the relayer's compensation ("fee") for submitting a base-token or emulated ERC-20 (NEP-141) transfer is dispatched as an independent `Transfer` promise *before* the actual transfer action's cross-contract outcome is known or checked, so the fee is paid to the relayer even when the underlying transfer subsequently fails.

### Finding Description
In `inner_rlp_execute`, once the RLP transaction is parsed successfully, the code unconditionally creates and dispatches a separate promise batch to pay the relayer's fee, decoupled from the actual action promise: [1](#0-0) 

This fee-transfer promise is a standalone `promise_batch_create` + `promise_batch_action_transfer` call, not chained via `.then()` to the outcome of the emulated action's promise (`action_to_promise(...)`, the NEP-141 `ft_transfer`/`storage_deposit` calls, or the base-token `Transfer` action) built further below: [2](#0-1) 

The only outcome-aware handling that exists is `rlp_execute_callback`, which checks `env::promise_result(0)` and refunds the *caller's attached deposit* (`caller_deposit`, used to cover relayer gas costs for external, non-access-key relayers) on failure: [3](#0-2) 

However, this failure handling only covers `caller_deposit`; it never revisits or claws back the relayer `fee` that was already sent out as a separate receipt in `inner_rlp_execute`. Since all of these promises (the fee-transfer batch and the action batch) are created within the same synchronous execution of `rlp_execute`/`inner_rlp_execute` and are all dispatched as sibling receipts once the function returns `Ok`, the fee payment to the relayer is fully committed independent of whether the emulated ERC-20 transfer or base-token transfer later succeeds or fails asynchronously.

The code comments acknowledge the fee is paid before confirmation, but frame it only as a UX/trust tradeoff between an honest user and relayer ("Users should always verify the fee before signing... Relayers should also verify the fee..."), without accounting for the case where the *action itself* fails for reasons unrelated to the fee amount (e.g., insufficient FT balance, non-existent receiver on `ft_transfer`, or storage-deposit/registrar edge cases) — the exact "unchecked value-movement" class flagged in the report: an operation is compensated as if successful, while the corresponding movement of value (the emulated ERC-20/base-token transfer) can fail without any check gating the compensation.

### Impact Explanation
This allows a malicious relayer to intentionally craft/route a `target`/action that will make the underlying `ft_transfer` or base-token `Transfer` fail (deterministically), while still collecting the pre-committed relayer fee from the wallet-owner's balance. This is unauthorized value movement from the wallet owner's account: they pay for a service (fee) that was never rendered (the transfer never went through), and there is no path in the contract to detect this or later reclaim the fee.

### Likelihood Explanation
Reachable directly by any relayer (an unprivileged party who can submit `rlp_execute` transactions on behalf of a wallet owner, particularly relevant when using the fee-based path for third-party relayers without an access key) simply by choosing transaction parameters (target/receiver) that cause the downstream NEP-141 call or transfer to fail while the fee computation and dispatch logic in `inner_rlp_execute` still runs unconditionally.

### Recommendation
Chain the relayer fee-transfer promise to the outcome of the main action promise (via `.then()`/a shared callback) so the fee is only paid out if `env::promise_result` for the underlying action indicates success, mirroring the existing failure handling already used for `caller_deposit` in `rlp_execute_callback`.

### Proof of Concept
1. A wallet owner signs an RLP transaction representing an ERC-20 (`ft_transfer`) transfer with a non-zero relayer `fee`, targeting a NEP-141 token contract.
2. A relayer submits it via `rlp_execute`, causing `inner_rlp_execute` to build the fee-transfer promise (lines 381-384) unconditionally and separately from the `ft_transfer` action promise chain (lines 433-458).
3. The relayer arranges (or the token contract naturally rejects) conditions causing the eventual `ft_transfer`/`storage_deposit` call to fail (e.g., insufficient token balance).
4. `rlp_execute_callback` correctly reports failure and refunds `caller_deposit` if present, but the fee-transfer receipt to the relayer, already dispatched in step 2, is unaffected and succeeds regardless.
5. Result: the relayer is paid despite the user's intended transfer never completing. [1](#0-0) [3](#0-2)

        TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
            address_check: Some(address),
            ..
        }) => {
            let callback_gas = ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas());
            let ext = WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let address_registrar = {
                let account_id = ADDRESS_REGISTRAR_ACCOUNT_ID
                    .trim()
                    .parse()
                    .unwrap_or_else(|_| env::panic_str("Invalid address registrar"));
                ext_registrar::ext(account_id).with_static_gas(REGISTRAR_LOOKUP_GAS)
            };
            let address = format!("0x{}", hex::encode(address));
            address_registrar.lookup(address).then(ext.address_check_callback(
                target,
                action,
                caller_deposit,
            ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
        }
        _ => {
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))
        }
    };
