### Title
Unbounded gzip decompression of user-submitted legacy declare class enables memory-exhaustion DoS - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
The JSON-RPC execution path that converts a client-submitted `BroadcastedDeclareTransaction::V1` (a legacy Cairo-0 declare) into an `ExecutableTransactionInput` calls `decompress_program`, which decompresses a base64+gzip user-supplied `compressed_program` field with no size or time limit, unlike the equivalent path used by the real gateway's declare-transaction admission flow, which is properly bounded.

### Finding Description
The gateway's real transaction-admission path bounds Sierra program decompression via `decompress_with_size_limit`, which caps the decompressed output using `.take(max_size + 1)` regardless of the input's compression ratio: [1](#0-0) 

However, the RPC-server execution path (used for `starknet_estimateFee` / `starknet_simulateTransactions` / `starknet_call`-style flows on broadcasted transactions) converts a `BroadcastedDeclareTransaction::V1` into an executable input via: [2](#0-1) 

which calls `user_deprecated_contract_class_to_sn_api`, which in turn calls `decompress_program` on the attacker-controlled `compressed_program` field: [3](#0-2) 

`decompress_program` itself has **no** size or time bound — it decodes base64 and then calls `GzDecoder::read_to_end`, which will keep allocating memory for as long as the decompressor produces bytes: [4](#0-3) 

The `// TODO(dan): add time and size limits.` comment on this function confirms the missing bound is a known gap. This is precisely the bug class in the referenced Suricata CVE-2026-46387: a decompression sink with no effective upper bound on the output buffer, fed by attacker-controlled highly-compressed input (a gzip "decompression bomb"). A small base64-encoded gzip payload (e.g., a few KB) can expand to gigabytes when decompressed, since gzip supports compression ratios in excess of 1000:1 for repetitive data.

### Impact Explanation
Any unprivileged client submitting a `starknet_estimateFee`, `starknet_simulateTransactions`, or similar execution-simulation RPC request containing a `BroadcastedDeclareTransaction::V1` payload can trigger unbounded memory allocation in the RPC node process. Because RPC nodes back the Starknet full-node/sequencer's read/query interface, this can crash or exhaust the memory of the node process, denying legitimate reads and potentially destabilizing collocated sequencer components if run in the same process/host — a network-availability impact ("a network unable to confirm new transactions" via degraded/crashed node infrastructure), without requiring any special privileges.

### Likelihood Explanation
This requires only a single unauthenticated JSON-RPC request with a small, easily-crafted payload (a highly-compressible base64+gzip "program" string). No signature validation, fee payment, or stateful checks are needed before `decompress_program` executes, since the conversion happens before/independent of the mempool/gateway admission checks that bound the real Sierra program size. This makes the likelihood of exploitation high for any exposed RPC endpoint supporting broadcasted-declare-based simulation.

### Recommendation
Apply the same bounded decompression pattern already used elsewhere in the codebase (`decompress_with_size_limit` / `decode_and_decompress_with_size_limit` in `crates/starknet_api/src/compression_utils.rs`) to `decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs`: wrap the `GzDecoder` reader with a `.take(max_size + 1)` limit tied to the node's configured maximum program/class size, and reject the request if the decompressed size exceeds that bound, mirroring the fix pattern in Suricata 7.0.16/8.0.5 (bounding decompressed body size).

### Proof of Concept
1. Craft a `BroadcastedDeclareTransaction::V1` JSON body where `contract_class.program` is a base64-encoded gzip stream that decompresses to several GB from a small (few-KB) input (a standard "gzip bomb," e.g., gzip of a large run of zero bytes).
2. Submit it via the RPC node's `starknet_estimateFee` (or `starknet_simulateTransactions`) JSON-RPC method, which internally converts the broadcasted declare via `TryFrom<BroadcastedDeclareTransaction> for ExecutableTransactionInput` at [5](#0-4) .
3. Observe that `decompress_program` at [4](#0-3)  allocates memory proportional to the decompressed size with no cap, causing the RPC node process's memory usage to spike until OOM or severe degradation.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.
    let mut decoder = GzDecoder::new(compressed_data.as_slice());
    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}
