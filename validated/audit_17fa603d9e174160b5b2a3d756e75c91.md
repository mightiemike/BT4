### Title
Missing nonce/replay-protection in `meta_tx_v0` transaction-hash generation enables signature replay - (File: `crates/blockifier/src/execution/syscalls/syscall_base.rs`)

### Summary
The `meta_tx_v0` syscall lets any contract, mid-execution of a normal transaction, invoke another contract's `__execute__` entry point using an externally supplied signature, after building a synthetic transaction hash for that call. That hash is computed with `nonce` hard-coded to `0` and contains no per-call uniqueness (no nonce, no deadline), unlike every other transaction type in the protocol, which is validated and protected against replay by the mandatory nonce-increment logic (`handle_nonce`) that runs for real transactions. Because this hash-generation path bypasses `__validate__` and the sequencer's own nonce bookkeeping, a captured signature for a `meta_tx_v0` call can be replayed indefinitely by any caller, exactly mirroring the reported bug class: a protocol-level signature hash that omits a nonce, leaving replay protection entirely — and silently — up to a downstream component.

### Finding Description
`meta_tx_v0` is implemented in `SyscallHandlerBase::meta_tx_v0`: [1](#0-0) 

The synthetic transaction hash is computed via `InvokeTransactionV0::calculate_transaction_hash`, and the resulting `TransactionInfo` explicitly sets `nonce: Nonce(0.into())` regardless of the account's real, on-chain nonce state. The call then proceeds straight to `execute_inner_call`, calling the target's `__execute__` directly — `__validate__` is never invoked, so the protocol-level nonce read/increment path (`AccountTransaction::handle_nonce`) is never exercised for this call: [2](#0-1) 

The equivalent Cairo/SNOS hashing routine, `compute_meta_tx_v0_hash`, is likewise nonce-free: it hashes only `contract_address`, `entry_point_selector`, `calldata`, and `chain_id` (an emulation of the legacy V0 invoke hash, which predates the nonce field entirely): [3](#0-2) 

For every ordinary transaction type (invoke v1/v3, declare, deploy-account), the transaction hash includes the nonce (see `hash_tx_common_fields`, which unconditionally hashes `common_fields.nonce`), and the sequencer additionally performs an independent state-level nonce check/increment before execution: [4](#0-3) 

`meta_tx_v0` breaks that invariant: it is the one execution primitive in the sequencer where a signature-carrying "transaction" is constructed and dispatched to a contract's `__execute__` without any nonce field flowing through the protocol-enforced hash or the protocol-enforced nonce-increment path. Any contract that consumes `meta_tx_v0`-relayed calls and trusts `get_execution_info().tx_info.signature`/`transaction_hash` for authorization (the documented purpose of the syscall — see the feature-test contract `meta_tx_test_contract.cairo`, whose `__execute__` reads `tx_info.signature`/`transaction_hash` directly) has no protocol-level guarantee that the same signed payload cannot be submitted twice. This is precisely the bug class from the report: the entity that owns the hash-generation code (there, the Marketplace contract; here, the sequencer's `syscall_base.rs`/`transaction_hash.cairo`) omits the nonce from the hash, silently pushing replay-prevention responsibility onto every downstream consumer, with no way to opt out or revoke a previously "used" call.

### Impact Explanation
Because the hash used for a `meta_tx_v0` call never changes for a fixed `(contract_address, entry_point_selector, calldata, chain_id)` tuple and is never bound to the account's actual nonce, an attacker who observes or is handed a signature intended for a single relayed action (e.g., a signed transfer/approval meant to be executed once by a relayer contract) can invoke `meta_tx_v0` again — in the same or a later transaction — reproducing the identical hash and signature, causing the target account's logic to execute the same authorized action multiple times. This can result in unauthorized repeated account actions and direct loss of funds (e.g., double-spending a signed transfer) for any account/relayer contract built on this syscall, since the sequencer provides no baseline nonce protection for this execution path the way it does for every other transaction type.

### Likelihood Explanation
Likelihood is Medium: `meta_tx_v0` is a documented, generally reachable syscall (usable from any contract during `Execute` mode, blocked only in `Validate` mode), so exploitation requires only that (a) some deployed contract relies on `meta_tx_v0` to accept externally-signed relayed calls, and (b) that contract does not itself layer an application-level nonce/expiry on top (the syscall gives it no help doing so, since the hash it can inspect is nonce-less by construction). This mirrors the original report's likelihood assessment — the flaw is latent in the primitive and becomes exploitable whenever a consumer relies on the "signature = one-time authorization" assumption without adding its own replay guard.

### Recommendation
Include a genuine nonce (or another monotonically-increasing/one-time value, e.g., a per-account meta-tx nonce read from state and incremented as part of `meta_tx_v0` execution) in the transaction hash computed by `meta_tx_v0` / `compute_meta_tx_v0_hash`, and enforce nonce consumption at the protocol level (mirroring `AccountTransaction::handle_nonce`) rather than leaving it as an implicit, undocumented responsibility of the callee contract. At minimum, document explicitly and prominently that consumers of `meta_tx_v0` MUST implement their own replay protection, and consider exposing a first-class nonce parameter through the syscall so implementers have a canonical, protocol-verified mechanism rather than inventing ad hoc schemes.

### Proof of Concept
1. Deploy a contract `Relay` whose `__execute__` performs a privileged action (e.g., token transfer) gated only on `get_execution_info().tx_info.signature` matching a previously authorized signer for that specific `calldata` (following the pattern demonstrated in `meta_tx_test_contract.cairo`, which reads `tx_info.signature`/`transaction_hash` from a `meta_tx_v0` call). [5](#0-4) 
2. Off-chain, the account owner signs one authorization intended for a single execution (transfer of `X` tokens) over the hash produced by `compute_meta_tx_v0_hash`/`InvokeTransactionV0::calculate_transaction_hash` — this hash depends only on `(contract_address, entry_point_selector, calldata, chain_id)`.
3. Caller contract `A` invokes `meta_tx_v0_syscall(address=Relay, entry_point_selector=__execute__, calldata, signature)` once — the transfer executes.
4. Caller contract `A` (or any other contract, in the same or a subsequent block) invokes `meta_tx_v0_syscall` again with the identical arguments. Because `meta_tx_v0`'s hash computation in `SyscallHandlerBase::meta_tx_v0` hard-codes `nonce = 0` and never consults or increments any state-tracked nonce, the resulting hash and signature are identical to step 3, and `Relay.__execute__` executes the transfer a second time, unless `Relay` independently implemented its own replay guard (which the sequencer neither requires nor assists with). [6](#0-5)

    fn handle_nonce(
        state: &mut dyn State,
        tx_info: &TransactionInfo,
        strict: bool,
    ) -> TransactionPreValidationResult<()> {
        if tx_info.is_v0() {
            return Ok(());
        }

        let address = tx_info.sender_address();
        let account_nonce = state.get_nonce_at(address)?;
        let incoming_tx_nonce = tx_info.nonce();
        let valid_nonce = if strict {
            account_nonce == incoming_tx_nonce
        } else {
            account_nonce <= incoming_tx_nonce
        };
        if valid_nonce {
            return Ok(state.increment_nonce(address)?);
        }
        Err(TransactionPreValidationError::InvalidNonce {
            address,
            account_nonce,
            incoming_tx_nonce,
        })
    }
