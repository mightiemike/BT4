### Title
Unbounded per-shop session-ID array growth in Cloudflare KV session storage due to missing duplicate check - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession` unconditionally appends a session's `id` to a per-shop index array every time a session is stored, without checking whether that id is already present. This is analogous to the CKB dep-group bug, where out-points were pushed into a `Vec` without a duplicate check, letting an attacker repeatedly trigger appends to blow up memory usage.

### Finding Description
`storeSession` calls `addShopIds(session.shop, [session.id])` on every store: [1](#0-0) 

`addShopIds` reads the existing array for the shop key and blindly concatenates the new id(s) onto it with no `includes()`/dedup check: [2](#0-1) 

This is in stark contrast to the equivalent Redis implementation, `addKeyToShopList`, which explicitly guards against duplicates before pushing: [3](#0-2) 

`storeSession` is invoked from the token-exchange authentication path every time a request's session is missing/inactive, for both the remix and react-router strategy implementations, and the express middleware: [4](#0-3) [5](#0-4) 

Because the same session id (e.g. `offline_{shop}` from `api.session.getOfflineId(shop)`) is reused across repeated exchanges/refreshes (particularly with the `expiringOfflineAccessTokens` future flag where tokens are periodically refreshed automatically), each subsequent `storeSession` call for that same id adds another duplicate entry to the shop's KV index array rather than replacing/deduping it. The array — and thus the KV value size — grows without bound over repeated (legitimate, single-merchant-triggerable) authentication/refresh cycles.

### Impact Explanation
`findSessionsByShop` iterates every id in the (now duplicate-laden) array and performs a `loadSession` KV read per entry, building a `Session[]` with as many duplicate entries as there are stale ids: [6](#0-5) 

As the index array grows unbounded, both the KV storage footprint for that shop key and the number of KV reads/response payload size on every `findSessionsByShop` call increase linearly with the number of stores, leading to resource exhaustion (increased memory/CPU per lookup and storage bloat) for the app's session-storage backend — a denial-of-service condition analogous to the reported CKB dep-group memory exhaustion, where lack of duplicate-detection before array append let repeated legitimate operations balloon memory usage.

### Likelihood Explanation
This path is reachable by a single authenticated merchant/customer without any special privilege: it's exercised automatically as part of the standard token-exchange authentication flow, and is more readily triggerable when `future.expiringOfflineAccessTokens` is enabled (periodic automatic refresh calls `storeSession` again for the same offline session id). A malicious merchant could also accelerate growth by intentionally forcing repeated token-exchange calls (e.g., replaying/renewing session tokens against the app's authenticated endpoints), each of which re-triggers `storeSession` for the same session id whenever `session.isActive()` evaluates false.

### Recommendation
Update `KVSessionStorage.addShopIds` (and `removeShopIds` for symmetry) to deduplicate the id list before persisting, mirroring the Redis implementation's `includes()` guard, e.g.:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Enable `future.expiringOfflineAccessTokens` (or otherwise cause a shop's offline session to repeatedly fail `isActive()`).
2. Repeatedly trigger the token-exchange authenticated request path for the same shop (e.g., call an authenticated route while the stored offline session is expired/near-expiry), causing `performTokenExchange`/`authenticate` to call `config.sessionStorage.storeSession(offlineSession)` with the same `offline_{shop}` id each time: [7](#0-6) 
3. Each call appends another duplicate `offline_{shop}` entry to the shop's KV index array via `addShopIds` without dedup: [2](#0-1) 
4. Repeated over many cycles, the KV array and subsequent `findSessionsByShop` reads grow unbounded, exhausting KV storage and increasing read/memory cost per shop lookup.

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
