### Title
Missing declared-class check in Starknet OS `execute_replace_class` diverges from Blockifier's validated `replace_class` syscall - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The Cairo `execute_replace_class` function used by the Starknet OS (non-virtual path, invoked from `execute_syscalls.cairo` for `REPLACE_CLASS_SELECTOR`) writes a new class hash into `contract_state_changes` without first verifying that the target `class_hash` corresponds to a declared class. In contrast, the Rust Blockifier's `replace_class` syscall handler explicitly performs this check before mutating state.

### Finding Description
In the Blockifier (used by the sequencer to execute and build blocks), the deprecated syscall handler for `replace_class` reads the compiled class before writing it, which fails with an `UndeclaredClassHash`/"is not declared" error if the class hash was never declared: [1](#0-0) 

This is reinforced by tests confirming the Blockifier rejects `replace_class` calls with undeclared class hashes: [2](#0-1) [3](#0-2) 

However, the corresponding Cairo implementation in the Starknet OS program (`execute_replace_class` in `syscall_impls.cairo`, reached via `execute_syscalls.cairo`'s dispatch on `REPLACE_CLASS_SELECTOR`) has an explicit, unresolved `TODO` acknowledging the missing check, and proceeds to unconditionally overwrite the contract's class hash in `contract_state_changes`: [4](#0-3) 

The dispatch that reaches this unguarded code path from any transaction executing a `replace_class` syscall: [5](#0-4) 

The same missing check exists in the deprecated (Cairo0) OS syscall path: [6](#0-5) 

This is analogous to the reported bug class: a state-mutating operation is missing a required authorization/validity check that a parallel, more "trusted" implementation enforces (in the RFP report, `setPoolActive` is missing `onlyPoolManager`; here, the OS's `execute_replace_class` is missing the "class must be declared" guard that the Blockifier enforces). The result is that the OS accepts and commits a state transition — `class_hash` of a contract set to an undeclared value — that the Blockifier (the real-time execution engine used to build blocks) would reject with an error.

### Impact Explanation
Any contract can invoke the `replace_class` syscall with an undeclared/arbitrary `class_hash` felt via a single ordinary transaction. Because the OS re-execution path does not validate that the class is declared, while the Blockifier (used for block building and state validation) does, this creates a validity/consensus divergence:
- If block building (Blockifier) rejects a transaction attempting to replace a contract's class with an undeclared class hash, but the Starknet OS (used for proof generation / re-execution / echo verification) would accept and commit the same operation, the two systems can disagree on the resulting state root and revert semantics for the same transaction trace.
- This is a "wrong committed root" / "honest-node divergence" class issue affecting state commitment and OS re-execution correctness — a contract's `class_hash` could end up set to a hash with no corresponding compiled class in the committed state, breaking invariants relied upon elsewhere (e.g., subsequent calls to that contract, or Patricia tree/class-hash-based verification assuming declared classes only).

### Likelihood Explanation
This is reachable from a single unprivileged transaction: any deployed contract can call the `replace_class` syscall with an attacker-chosen `class_hash` felt as part of normal execution — no special privileges, staking, or operator/prover role required. The `TODO` comment in the code confirms this is a known-but-unaddressed gap, increasing confidence that it is a genuine gap rather than intentionally deferred/duplicated validation elsewhere in the OS pipeline (this could not be fully confirmed from the available context — it's possible an equivalent check exists elsewhere in the OS's class-hash bookkeeping/finalization stage that was not visible in the retrieved snippets).

### Recommendation
Add a declared-class existence check in `execute_replace_class` (both the current `syscall_impls.cairo` version and the deprecated Cairo0 `deprecated_execute_syscalls.cairo` version) mirroring the Blockifier's `get_compiled_class` validation, before writing the new `StateEntry` into `contract_state_changes`. This ensures the OS re-execution path enforces identical validity semantics as the Blockifier for the `replace_class` syscall, and resolves the outstanding `TODO(Yoni, 1/1/2026)`.

### Proof of Concept
1. Deploy a contract that calls `replace_class_syscall(some_undeclared_class_hash)` (e.g., analogous to `test_replace_class` in the feature-contract test helpers). [7](#0-6) 
2. In the Blockifier execution path, this call fails with `"... is not declared"` as demonstrated by the existing unit test. [2](#0-1) 
3. Trace the same transaction through the Starknet OS's `execute_syscalls` → `execute_replace_class` path: no equivalent "is declared" check exists before `contract_state_changes` is updated with the new (undeclared) class hash, so the OS would proceed to commit the state change rather than reject the transaction. [4](#0-3)
