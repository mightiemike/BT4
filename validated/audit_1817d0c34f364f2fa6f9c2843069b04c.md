## Finding

### Title
Backup restore accepts write sets unverified against the accumulator-proven `state_change_hash`, allowing corrupted/malicious write sets to be committed as ledger history - ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
The transaction-restore path loads `(txn, aux_info, txn_info, events, write_set)` tuples from a backup chunk and verifies them via `TransactionListWithProofV2::verify()`, but that verification path never checks that the loaded `write_set` hashes to `txn_info.state_change_hash()`. The `write_set` is carried alongside the verified structure and later persisted straight into `WriteSetDb`, and, in KV-replay mode, fed into `calculate_state_and_put_updates` to derive the restored state tree — all without ever being bound to the accumulator-proven transaction info that supposedly authenticates it.

### Finding Description
`LoadedChunk::load` in [1](#0-0)  reads `txns`, `persisted_aux_info`, `txn_infos`, `event_vecs`, and `write_sets` from the backup file as independent vectors, then builds a `TransactionListWithProofV2` from only `txns`, `event_vecs`, and `txn_infos` (`write_sets` is excluded) and calls `.verify(ledger_info.ledger_info(), ...)`.

`TransactionListWithProof::verify` (used inside `TransactionListWithProofV2::verify`) checks:
- transaction hash == `txn_info.transaction_hash()`
- `txn_infos` are proven against the ledger info's accumulator root
- event root hashes match [2](#0-1) 

It never checks `txn_info.state_change_hash()` against the hash of the corresponding `write_set`. Contrast this with `TransactionOutputListWithProof::verify`, the sibling verification routine used for output-based syncing, which explicitly enforces exactly that binding: [3](#0-2) 

After the `LoadedChunk` is "verified," `write_sets` — never checked against `state_change_hash` — is unpacked and threaded through `save_before_replay_version` → `RestoreHandler::save_transactions` / `save_transactions_and_replay_kv` → `restore_utils::save_transactions_impl`, which:
1. Persists the raw `write_set` into `WriteSetDb` for each version: [4](#0-3) 
2. When `kv_replay` is true, feeds the same unverified `write_sets` into `state_store.calculate_state_and_put_updates(...)` and commits the resulting `ledger_state` via `set_state_ignoring_summary`: [5](#0-4) 

Because the `TransactionInfo` objects are the only artifact cryptographically bound to the trusted `LedgerInfo`/accumulator root, and the restore code never checks `write_set` against `txn_info.state_change_hash()`, a backup source (compromised or corrupted backup storage) that supplies a `write_set` inconsistent with the version's committed `state_change_hash` will pass all restore-time verification and be written into durable storage / merklized as ground truth. The mismatch would only surface later, if at all, when a node tries to serve a value+proof against the on-chain accumulator/JMT root for that key, at which point the value written by restore may not correspond to the state actually committed during original execution — i.e., restored nodes converge on a different ledger state than honestly-executed nodes, with no immediate signal of divergence during restore.

### Impact Explanation
This breaks the core proof/storage invariant "VM outputs / write sets must survive executor-to-storage handoff / restore unchanged and provably bound to the accumulator root." A tampered backup archive (e.g., from a compromised backup storage bucket, MITM, or malicious backup-storage backend implementing `BackupStorage`) can cause a restoring node to persist state-key/value pairs that differ from what was actually executed and durably committed by the network, while the restore tool reports success (proof "verified"). This is a state-commitment integrity issue: the restored database can silently diverge from the correct VM result, corrupting the ledger data set used to serve state, state proofs, and future execution on that node.

### Likelihood Explanation
Requires control over, or corruption of, the backup storage/transport (implementing `BackupStorage`) used during a restore/bootstrap — an external, unprivileged-to-the-chain dependency, not requiring validator or governance privilege. Given that node operators regularly bootstrap/restore fullnodes and archive nodes from backups (including third-party or self-hosted `BackupStorage` implementations), this is a realistic, non-hypothetical trigger path once a backup source is untrusted or compromised, matching the "external requirements" medium/high-likelihood pattern from the seed report's booster-swap issue.

### Recommendation
In `LoadedChunk::load` (or in `TransactionListWithProof`/`TransactionListWithProofV2::verify`), add an explicit check that `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every transaction in the chunk before accepting/persisting `write_sets`, mirroring the check already present in `TransactionOutputListWithProof::verify`. This check should be enforced both on the raw restore path (`save_transactions`) and the KV-replay path (`save_transactions_and_replay_kv`), prior to any DB writes.

### Proof of Concept
1. Take a legitimate backup transaction chunk file and its accompanying `(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)` proof file.
2. Modify the `write_set` field of one record in the chunk (leaving `txn`, `txn_info`, `events` untouched) so it no longer hashes to that record's `txn_info.state_change_hash()`.
3. Point `RestoreHandler`/`TransactionRestoreController` at the modified chunk and run a restore (`run_impl` → `LoadedChunk::load`).
4. Observe that `txn_list_with_proof.verify(...)` succeeds (it only checks `txn`/`txn_info`/`event` consistency and the accumulator proof), and the tampered `write_set` is persisted via `save_transactions_impl` into `WriteSetDb` (and, with `kv_replay = true`, merklized into the restored state tree), producing a ledger state that a node believes is authenticated by the ledger info's accumulator root but is not.

Note: I was unable to fully inspect `go_through_verified_chunks`/`replay_transactions`/`verify_execution_mode` bodies due to index truncation, so I cannot rule out that some execution-replay-based verification modes independently re-derive and cross-check the write set later (which would reduce, but not eliminate, exposure for the non-replay `save_transactions` fast path). This should be confirmed by reading the full file directly.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
