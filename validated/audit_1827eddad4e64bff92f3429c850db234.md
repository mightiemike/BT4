### Title
NEAR's Wasmtime engine runs the vulnerable Winch backend with linear-memory guard pages disabled, turning `table.grow` type-confusion (CVE-2026-35186) into a live OOB memory access instead of Wasmtime's default DoS-only behavior - ([File: runtime/near-vm-runner/src/wasmtime_runner/mod.rs])

### Summary
`WasmtimeVM::new_for_target` explicitly configures the Wasmtime `Engine` to use `Strategy::Winch` on `x86_64` (the production architecture) and simultaneously disables the linear-memory guard-page mitigations (`guard_before_linear_memory(false)`, `memory_guard_size(0)`, `memory_reservation_for_growth(0)`) that the GHSA-f984-pcp8-v2p7 advisory explicitly says are the only thing preventing this bug from being more than a benign crash. [1](#0-0) 

### Finding Description
The upstream advisory states that Wasmtime's Winch backend mistypes the `table.grow` return value (tags a 32-bit result as 64-bit), which can be leveraged when that value is subsequently used as a memory address, causing an out-of-bounds access into the bytes immediately preceding linear memory. The advisory's own mitigating factor is: "Wasmtime's default compiler is Cranelift, not Winch, and Wasmtime's default settings are to place guard pages before linear memory... Wasmtime's default configuration is not affected... Disabling guard pages before linear memory is required to possibly leak up to 16-bytes of host data."

nearcore's `WasmtimeVM::new_for_target` does exactly the two things the advisory calls out as required to escalate this bug beyond a benign fault:
1. It selects `Strategy::Winch` as the compiler for the production target (`x86_64`), with Cranelift only used as an aarch64 development fallback: [2](#0-1) 
2. It explicitly disables the pre-linear-memory guard region and shrinks the memory reservation/guard size to zero, in order to elide bounds checks for performance: [3](#0-2) 

`table.grow`/`memory.grow` are reachable directly from any deployed WASM contract and are metered/instrumented like any other opcode by nearcore's `prepare_v3`/`instrument_v3` gas-cost logic, confirming the opcode is a normal, unprivileged, contract-triggerable operation (not test-only): [4](#0-3) 
Tests in `runtime_errors.rs` explicitly exercise `table.grow`, confirming this instruction is exercised on nearcore's production Wasmtime/Winch path for ordinary `FunctionCall` execution: [5](#0-4) 

Because nearcore has turned off the guard region that the advisory relies on to convert an OOB access into a detectable, aborting page fault, an OOB access from the Winch type-confusion bug on nearcore may not fault at all — it may read/write into whatever is actually mapped adjacent to the memory reservation (which, with `memory_reservation_for_growth(0)`, `memory_guard_size(0)`, and pooling-allocator slabs, is far more likely to be *other live process memory* — e.g., another contract instance's memory slab, engine metadata, or `VMContext`/host bookkeeping — rather than guaranteed-unmapped pages). This converts the advisory's "DoS + up to 16 bytes leaked before crashing" bound into a potentially open-ended OOB read/write against nearcore's own process memory, since the safety net (guard pages) that bounds the blast radius in Wasmtime's default configuration is absent here.

### Impact Explanation
If the pinned `wasmtime` dependency version used by nearcore falls in one of the affected ranges (`>=25,<36.0.7`, `>=37,<42.0.2`, `>=43,<43.0.1`), any contract deployer can submit a WASM module using `table.grow` in a way that triggers the Winch type-confusion, and because nearcore disables the guard pages Winch/Cranelift normally rely on for OOB containment, the resulting out-of-bounds memory access is not guaranteed to fault. On a validator/RPC node this could manifest as: (a) a node crash triggered by a single `FunctionCall` transaction (chain-halt-adjacent DoS reachable by any signer), or (b) — depending on what happens to be adjacent in the pooling-allocator's memory layout — corruption or disclosure of memory belonging to unrelated contract instances or host state within the same process, which could produce diverging non-deterministic behavior across validators (since the corrupted bytes are unmapped-adjacent heap contents, not protocol state, differing per-process). Both outcomes are Medium/High severity per the report's own classification and match the rules' bar (transaction-triggered halt / state-root divergence risk).

### Likelihood Explanation
Likelihood depends entirely on whether the vulnerable `wasmtime` crate version is actually pinned in `Cargo.lock`; I was not able to confirm the exact resolved version in the given repository index (Cargo.lock content wasn't retrievable via the available search tools, so this is unverified). What is verified and load-bearing regardless of the exact pinned patch version is that nearcore's engine configuration (a) makes Winch the primary production strategy on x86_64, and (b) removes the mitigating guard-page configuration the advisory says is required for the bug to be more than a same-crash DoS. This means if/while the pinned version is vulnerable, the exploit path is trivially reachable by any unprivileged contract deployer/caller (a single `table.grow` instruction in a deployed contract, invoked via ordinary `FunctionCall`), with no special privileges needed.

### Recommendation
- Verify the exact `wasmtime` version pinned in `Cargo.lock`/`Cargo.toml` against the advisory's affected ranges and upgrade to a patched release (`>=36.0.7`, `>=42.0.2`, or `>=43.0.1`) regardless of current risk assessment.
- Re-evaluate the `guard_before_linear_memory(false)` / `memory_guard_size(0)` / `memory_reservation_for_growth(0)` performance optimizations at `runtime/near-vm-runner/src/wasmtime_runner/mod.rs:538-548`; consider re-enabling guard regions (even a reduced size) so that future compiler-correctness bugs fail closed (deterministic trap) rather than potentially reading/corrupting adjacent process memory.
- Consider defaulting to `Strategy::Cranelift` in production until Winch's maturity/track record for memory-safety-relevant bugs (like this class of type confusion) is established, since nearcore's own guard-page choices remove the safety net Wasmtime upstream relies on to bound the impact of such bugs.

### Proof of Concept
1. Deploy a WASM contract containing a table and a function using `table.grow`, structured so that the (possibly `-1`/failure) 32-bit result is subsequently used, after a Winch-introduced 64-bit reinterpretation, as an address for a `load`/`store` operation immediately preceding the table/memory's guard-less linear-memory region — mirroring the load-scenario described in GHSA-f984-pcp8-v2p7.
2. Submit this contract via a normal `DeployContract` + `FunctionCall` transaction from any account; nearcore's Wasmtime backend compiles and executes it with `Strategy::Winch` on x86_64 nodes per `WasmtimeVM::new_for_target` (`runtime/near-vm-runner/src/wasmtime_runner/mod.rs:520-524`).
3. Because `guard_before_linear_memory(false)`/`memory_guard_size(0)` are set (`mod.rs:538-548`), the OOB access from the mistyped `table.grow` result reads/writes adjacent process memory rather than reliably faulting on an unmapped guard page — reproducing (and potentially worsening) the advisory's impact on a production nearcore node, pending confirmation of the exact pinned `wasmtime` version being in an affected range.
