### Title
Unauthorized gas-key balance injection via `AddKey` action bypasses deposit requirement - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`action_add_key` → `add_gas_key` in `runtime/runtime/src/access_keys.rs` writes the caller-supplied `GasKeyInfo` (which contains a `balance` field) to state without resetting or validating that balance to zero. Only the `nonce` field on the access key is server-overwritten; the `balance` field — which is supposed to represent a prepaid-gas pot that can only be legitimately funded through `action_transfer_to_gas_key` (which requires an attached, accounted deposit) — is persisted verbatim from user input.

### Finding Description
`AddKeyAction { public_key, access_key: AccessKey { nonce, permission } }` is a regular, unprivileged transaction/receipt action any account owner (or an authorized access key, including one obtained via a signed transaction or meta-transaction) can submit. When `permission` is `GasKeyFullAccess(GasKeyInfo)` or `GasKeyFunctionCall(GasKeyInfo, _)`, the `GasKeyInfo.balance` field is fully attacker-controlled at construction time: [1](#0-0) 

`action_add_key` dispatches to `add_gas_key` for any key carrying `gas_key_info()`: [2](#0-1) 

`add_gas_key` clones the caller-supplied `access_key`, forces only the on-key `nonce` to `0`, sets up the per-index nonce entries, computes storage cost, and then writes the access key — including the attacker-supplied `GasKeyInfo.balance` — to the trie via `set_access_key`: [3](#0-2) 

By contrast, the *only* other sanctioned way to fund a gas key's `balance` is `action_transfer_to_gas_key`, which requires the caller to actually attach a deposit (`action.deposit`) that is charged against the sender/receipt's economic accounting before being added to `gas_key_info.balance`: [4](#0-3) 

This mirrors the reported bug class exactly: a server-generated/protected field (the gas key's prepaid `balance`, meant to be populated only through an accounted deposit path) is not stripped/zeroed from user-supplied input on the "create" action (`AddKey`), allowing the caller to set it to an arbitrary value directly.

### Impact Explanation
If the balance is not sanitized before or during `add_gas_key`, an attacker can add a gas key to their own account with an arbitrary `GasKeyInfo.balance` (e.g. a very large value) without ever transferring real NEAR into it. That prepaid balance is later spendable to pay for gas via the gas-key transaction path (`verify_and_charge_gas_key_tx_ephemeral`), and — critically — can also be withdrawn back into the account's real `amount` via `action_withdraw_from_gas_key`, which credits the account balance from `gas_key_info.balance` with no linkage back to an actual prior deposit: [5](#0-4) 

If this path is reachable unmodified, it constitutes token supply inflation: value is created from nothing and can be moved into a real, spendable account balance, which is one of the explicitly in-scope severe outcomes (unauthorized value movement / supply inflation).

### Likelihood Explanation
The `AddKey` action is reachable directly by any account owner via a signed transaction, and via meta-transactions (`DelegateAction`) and cross-shard receipts (e.g. through a contract's `promise_batch_action_add_key_with_full_access`-style host calls, which also route through `action_add_key`). I was **not able to fully verify** whether `runtime/runtime/src/action_validation.rs` (which references `GasKeyInfo`/`GasKeyFullAccess`/`GasKeyFunctionCall` in two locations) performs an upstream check that rejects or zeroes a nonzero `balance` in an `AddKeyAction` before it reaches `add_gas_key`. That file's contents were not retrieved before the tool budget was exhausted, so this should be treated as a **root cause hypothesis requiring confirmation** against `action_validation.rs`, not a fully proven end-to-end exploit. If such a check exists and enforces `balance == 0` on `AddKeyAction`, this finding is invalidated.

### Recommendation
Confirm in `runtime/runtime/src/action_validation.rs` whether `AddKeyAction` validation already rejects/zeroes a nonzero `GasKeyInfo.balance`. If it does not, add an explicit check (mirroring the nonce reset in `add_gas_key`) that rejects `AddKeyAction`s specifying nonzero `GasKeyInfo.balance`, or forcibly zero the balance in `add_gas_key` before persisting the access key — analogous to how `access_key.nonce = 0` is already enforced there. Add a regression test asserting that an `AddKey` action with a nonzero `GasKeyInfo.balance` results in a stored gas key with `balance == 0`, and that no gas-key balance can be created except through `action_transfer_to_gas_key`.

### Proof of Concept
1. Submit a `SignedTransaction` from an attacker-controlled account containing a single `AddKeyAction` with `access_key.permission = AccessKeyPermission::GasKeyFullAccess(GasKeyInfo { balance: Balance::from_near(1_000_000), num_nonces: 1 })`.
2. Observe that `action_add_key` → `add_gas_key` (`runtime/runtime/src/access_keys.rs:194-228`) persists the access key with the attacker-chosen `balance` (only `nonce` is reset to `0`).
3. Submit a follow-up `WithdrawFromGasKeyAction` referencing the newly added public key; per `action_withdraw_from_gas_key`, the fabricated balance is credited to the account's real `amount`, realizing unbacked token supply into a spendable balance.
(Step 2's outcome depends on confirming no rejecting check exists in `action_validation.rs`, as noted above.)

pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}

fn add_gas_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    // For gas keys, nonce stored on access key is not used and should always be zero
    let mut access_key = access_key.clone();
    access_key.nonce = 0;
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    // Set up nonces for gas key
    let num_nonces = gas_key_info.num_nonces;
    let nonce = initial_nonce_value(block_height);
    for i in 0..num_nonces {
        set_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i, nonce);
    }

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(gas_key_storage_cost(fee_config, public_key, &access_key, num_nonces))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
