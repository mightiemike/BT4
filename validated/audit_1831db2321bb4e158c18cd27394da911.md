### Title
Inconsistent receipt sanitization between GetTransactionInfoById and GetTransactionInfoByBlockNum causes divergent energy/fee accounting for the same transaction - ([File: chainbase/src/main/java/org/tron/core/store/TransactionRetStore.java])

### Summary
`TransactionRetStore.getTransactionInfo(byte[] key)` (used by `Wallet.getTransactionInfoById`, reached via `GetTransactionInfoByIdServlet`) sanitizes the `ResourceReceipt` by clearing `originEnergyUsage` whenever `energyUsageTotal == 0`, but `TransactionRetStore.getTransactionInfoByBlockNum(byte[] key)` (used by `Wallet.getTransactionInfoByBlockNum`, reached via `GetTransactionInfoByBlockNumServlet`) returns the raw, unmodified `TransactionRetCapsule` without this correction. Consequently, two different public HTTP endpoints report two different `originEnergyUsage` values for the exact same on-chain transaction/receipt.

### Finding Description
In `TransactionRetStore.getTransactionInfo`, after locating the matching `TransactionInfo` by id, the code explicitly detects a "dirty" receipt state and rewrites it: [1](#0-0) 

This corrected `TransactionInfoCapsule` is what `GetTransactionInfoByIdServlet` (via `Wallet.getTransactionInfoById`) serves to callers.

In contrast, `getTransactionInfoByBlockNum` simply deserializes and returns the stored `TransactionRetCapsule` as-is, with no equivalent sanitization of any contained receipt's `originEnergyUsage`: [2](#0-1) 

`GetTransactionInfoByBlockNumServlet.doGet`/`doPost` call `wallet.getTransactionInfoByBlockNum(num)` and serialize every `TransactionInfo` in the block's list directly to JSON, without going through the fix-up path used for the by-id lookup: [3](#0-2) 

Both servlets are unauthenticated public HTTP endpoints reachable by any caller. If a stored receipt has `energyUsageTotal == 0` and `originEnergyUsage > 0` (a state the code comments call "dirty," implying it can legitimately occur in stored data, e.g. from historical/legacy encoding), querying the same transaction by id versus by block number yields two structurally different receipts for the identical settlement event.

### Impact Explanation
This is a data-integrity/consistency bug: the same transaction's finalized receipt is reported differently depending on which read API is used. Any off-chain consumer (exchange, indexer, smart-contract-adjacent reimbursement/reconciliation system) that trusts `originEnergyUsage` from `getTransactionInfoByBlockNum` while another system trusts the id-based lookup will compute divergent energy/fee figures for the same event, enabling arbitrage between systems or disputed/duplicated reimbursement claims based on which endpoint's figure is presented. The underlying ledger state (actual energy charged) is not altered — this is a reporting/API-level divergence, not a re-execution or double-spend of funds within the chain itself.

### Likelihood Explanation
Feasibility depends entirely on whether real receipts with `energyUsageTotal == 0` and `originEnergyUsage > 0` occur in the store; the code's own comment ("if query a result with dirty origin usage in receipt, we just reset it") indicates this state is known to occur in practice (likely from historical/legacy data or specific execution paths), making the precondition realistic rather than purely synthetic. No privileged access is required — both servlets are open HTTP endpoints, and the divergence is fully deterministic and repeatable for any transaction matching the precondition.

### Recommendation
Apply the same `originEnergyUsage` sanitization logic inside `getTransactionInfoByBlockNum` (or in a shared helper) before returning the `TransactionRetCapsule`/`TransactionInfoList`, iterating over every `TransactionInfo` in the block's list and clearing `originEnergyUsage` when `energyUsageTotal == 0`, so both read paths produce identical receipts for the same transaction.

### Proof of Concept
Java unit test in `chainbase`/`framework` test module, extending the existing `TransactionRetStoreTest`:
```java
@Test
public void testReceiptConsistencyBetweenLookups() throws Exception {
  // Build a TransactionInfo with receipt: energyUsageTotal = 0, originEnergyUsage = 100
  ResourceReceipt dirtyReceipt = ResourceReceipt.newBuilder()
      .setEnergyUsageTotal(0)
      .setOriginEnergyUsage(100)
      .build();
  TransactionInfo txInfo = TransactionInfo.newBuilder()
      .setId(ByteString.copyFrom(txId))
      .setReceipt(dirtyReceipt)
      .build();
  // Persist via TransactionRetCapsule at blockNumber, and record txId->blockNumber in transactionStore

  TransactionInfoCapsule byId = transactionRetStore.getTransactionInfo(txId);
  TransactionRetCapsule byBlock = transactionRetStore.getTransactionInfoByBlockNum(ByteArray.fromLong(blockNumber));

  ResourceReceipt receiptFromById = byId.getInstance().getReceipt();
  ResourceReceipt receiptFromBlock = byBlock.getInstance().getTransactioninfo(0).getReceipt();

  // Expected (if fixed): both should have originEnergyUsage == 0
  // Actual (bug): receiptFromById.getOriginEnergyUsage() == 0
  //               receiptFromBlock.getOriginEnergyUsage() == 100  -> divergence
  assertEquals(receiptFromById.getOriginEnergyUsage(), receiptFromBlock.getOriginEnergyUsage());
}
```
This test currently fails, demonstrating that `getTransactionInfo` and `getTransactionInfoByBlockNum` return inconsistent `originEnergyUsage` values for the identical stored receipt.
