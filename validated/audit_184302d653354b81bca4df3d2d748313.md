### Title
Unchecked return value of `SessionStorage.storeSession` in OAuth callback and token-exchange middleware leads to silent authentication-state desync - (File: `packages/apps/shopify-app-express/src/auth/auth-callback.ts`, `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`)

### Summary
`storeSession` is defined by the `SessionStorage` interface to return `Promise<boolean>`, where `false` signals the session was **not** persisted [1](#0-0) . In the OAuth callback handler and the token-exchange middleware, this return value is awaited but never checked, so a failed persist is treated identically to a successful one and the request proceeds to mark the session active and continue the authenticated flow.

### Finding Description
In `authCallback`, after a successful OAuth callback from Shopify, the session is stored and then immediately used to register webhooks and populate `res.locals.shopify.session` regardless of whether `storeSession` actually succeeded: [2](#0-1) 

Similarly, in `performTokenExchange`, after exchanging a session token for offline/online access tokens, the resulting `Session` (containing the access token) is stored without checking success, and the code immediately proceeds to call the `afterAuth` hook and attach the session to `res.locals.shopify`, allowing the request to continue as authenticated: [3](#0-2) 

Multiple reference `SessionStorage` implementations (Redis, MySQL, PostgreSQL, Drizzle) can return `false` from `storeSession` on transient failures without throwing — e.g. the Redis implementation always returns `true` after the calls but other adapters wrap writes in try/catch and return `false` on error [4](#0-3) , and this contract is explicitly documented as `false` meaning "not successfully stored" [1](#0-0) . Because the calling code in `shopify-app-express` never inspects this boolean, a storage failure is silently ignored, and the request is treated as if a valid, durably-persisted session/access-token now exists.

This is the direct analog of the reported `Visor.sol` finding: an operation whose return value indicates success/failure (`transferFrom` vs. `storeSession`) is awaited but not checked, causing the caller's internal bookkeeping (`timelockERC20Balances` vs. in-memory `res.locals.shopify.session`/subsequent middleware state) to diverge from the actual persisted state.

### Impact Explanation
If `storeSession` silently fails (e.g., a transient DB/Redis error caught internally and turned into `false`, as several storage adapters do), the app proceeds as though the offline/online access token session was durably saved:
- Webhooks get registered against a session that isn't actually retrievable from storage.
- `afterAuth` hooks run and the request is authenticated for the current call via `res.locals.shopify.session`, but subsequent requests calling `loadSession` will not find the session, forcing repeated OAuth/token-exchange cycles or leaving the app in an inconsistent state where downstream code assumes persisted access tokens exist.
- In multi-instance/production deployments backed by shared session storage (Redis/SQL), this can produce authentication state desync between app instances, since one instance believes storage succeeded while the underlying store never received the write.

This does not directly grant an attacker forged access, but it is a legitimate correctness/reliability bug in the authenticated-request path handling access-token persistence, matching the "unchecked return value causing inconsistent state" bug class from the report.

### Likelihood Explanation
This code path executes on every completed OAuth callback and every token-exchange request from a merchant's embedded app (a single, unprivileged actor's normal usage triggers it), so likelihood of the code path being hit is high; the failure itself depends on the session storage backend transiently failing (e.g., DB/connection errors), which is realistic in production but not attacker-controlled directly.

### Recommendation
Check the boolean returned by `storeSession` in both `authCallback` and `performTokenExchange`. On `false`, log an error and return a failure response (e.g., 500) instead of proceeding to register webhooks, run `afterAuth`, or mark the request as authenticated, mirroring the existing error handling already used for `loadSession` failures in `performTokenExchange`.

### Proof of Concept
1. Configure the app with a `SessionStorage` implementation whose `storeSession` can return `false` on failure (per the documented contract) instead of throwing.
2. Trigger OAuth callback (`GET /auth/callback`) or a token-exchange request from the embedded app while the storage backend is failing writes.
3. Observe that `authCallback`/`performTokenExchange` still proceed past the `storeSession` call, register webhooks / run `afterAuth`, and set `res.locals.shopify.session`, treating the request as fully authenticated even though the session was never persisted — confirmed by code inspection of [5](#0-4)  and [6](#0-5) , where no error path is taken based on the `storeSession` result.

    const row = this.sessionToRow(session);

    await this.db
      .insert(this.sessionTable)
      .values({...row})
      .onConflictDoUpdate({
        target: this.sessionTable.id,
        set: {...row},
      });
