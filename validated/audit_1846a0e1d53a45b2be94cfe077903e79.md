### Title
Single transaction's `TransactionConverterError` aborts the entire in-progress block proposal instead of being skipped - (File: `crates/apollo_batcher/src/block_builder.rs`)

### Summary
`BlockBuilder::add_txs_to_executor` converts every transaction in a freshly-fetched chunk to an executable blockifier transaction using `futures::future::try_join_all`, then feeds the whole chunk to the executor. Because `try_join_all` short-circuits on the first `Err`, one transaction that fails conversion (e.g. transient class-manager/proof-manager unavailability) causes the whole chunk's conversion to fail, propagating an error out of the block-building loop that makes `BlockBuilder::build_block` treat the **entire proposal** as failed and call `abort_block()`, discarding every transaction already executed in that proposal — not just the offending one.

### Finding Description
`add_txs_to_executor` fetches up to `n_concurrent_txs` transactions, immediately appends them to `self.block_txs`, and then converts them concurrently: [1](#0-0) 

The conversion closure calls `TransactionConverter::convert_internal_consensus_tx_to_executable_tx`, whose fallible dependency chain (`get_sierra`, `get_executable`, proof verification, etc.) can fail with several timing-sensitive/transient errors such as `ClassNotFound`, `ProofNotFound`, `ClassManagerClientError`, or `ProofManagerClientError`: [2](#0-1) [3](#0-2) 

`try_join_all` returns `Err` as soon as any single future in the batch fails, which is then propagated with `?` at the call site: [4](#0-3) 

That `?` bubbles up through the main `build_block_inner` loop (`self.add_txs_to_executor().await?` at line 381), through `build_block_inner`'s own error return, into the outer trait method `build_block`, which on *any* error unconditionally calls `abort_block()` on the executor for the whole block, not just the failing chunk: [5](#0-4) 

This is the same atomicity-cascade pattern described in the report: a per-item decode/validation failure (here, a per-transaction conversion failure) is not isolated, so it propagates through an un-mitigated `Result`-collecting combinator (`try_join_all`, functionally analogous to `aggregate3({allowFailure:false})`), and the lack of a catch/skip boundary around the outer loop (analogous to the missing `try/catch` around `onCronTrigger`) turns one bad item into a total-batch (here, total-proposal) failure.

### Impact Explanation
Any single transaction whose conversion transiently fails (e.g. a Declare transaction's class not yet visible via `class_manager_client.get_sierra`/`get_executable` due to gRPC/propagation latency, or a proof-verification/proof-manager RPC hiccup for a proving Invoke transaction) discards the entire block-building effort for that height/round: all previously-executed, perfectly valid transactions in the same proposal are aborted along with it via `abort_block()`. On the proposer this forces an empty/failed proposal for the round; on a validator it forces rejection of an otherwise-valid proposal it was building. Because this can recur every round while the transient condition persists (e.g. a persistently slow class-manager or proof-manager under load), it can repeatedly stall block production/validation, delaying confirmation of transactions network-wide — matching the report's "network unable to confirm new transactions" criterion — without any wrongdoing by the transaction sender.

### Likelihood Explanation
This is reachable by an ordinary, unprivileged transaction: any Declare transaction (class propagation timing) or client-side-proving Invoke transaction (proof storage/verification timing) can trigger a `TransactionConverterError`. These are exactly the kind of "normal API/infra latency" conditions cited in the original report as the most likely trigger (there, Data Streams API latency; here, inter-component RPC latency between gateway/consensus and the class manager or proof manager). No malicious behavior or privileged role is required — a legitimate transaction submitted under normal network conditions is sufficient.

### Recommendation
- In `add_txs_to_executor`, do not use `try_join_all` to convert the whole chunk atomically. Convert per-transaction with individual error handling (e.g., `futures::future::join_all` returning a `Vec<Result<_, _>>`), and for transactions that fail conversion, remove them from `self.block_txs` and skip/log them (with a metric) rather than failing the whole chunk.
- Ensure a single conversion failure does not propagate as a hard `BlockBuilderError` that triggers `abort_block()` for the entire proposal; reserve `abort_block()`/`FailOnError` for truly proposal-fatal conditions (e.g. L1 handler validation failures already handled distinctly at line 497-504).
- Consider retrying transient `TransactionConverterError` variants (`ClassManagerClientError`, `ProofManagerClientError`, `ClassNotFound`, `ProofNotFound`) with backoff before dropping the transaction, since these are often propagation-timing races rather than permanent invalidity.

### Proof of Concept
1. A client submits a normal Declare V3 transaction; the class becomes fully queryable via `class_manager_client.get_sierra`/`get_executable` a few hundred milliseconds after the gateway forwards it to the mempool, due to normal cross-component propagation latency.
2. During that latency window, the batcher (proposer or validator) polls the mempool/tx provider and includes this Declare transaction, along with several unrelated, fully-valid transactions, in the same `n_concurrent_txs` chunk in `add_txs_to_executor`.
3. `convert_internal_consensus_tx_to_executable_tx` for the Declare transaction calls `get_sierra`/`get_executable`, which returns `TransactionConverterError::ClassNotFound` because the class hasn't propagated to this node's class manager yet [6](#0-5) .
4. `futures::future::try_join_all` at `block_builder.rs:528` returns this `Err` immediately, discarding the successfully-converted results for the other, unrelated transactions in the chunk.
5. The `?` propagates out of `add_txs_to_executor`, out of the main loop in `build_block_inner`, and `build_block` catches the error and calls `abort_block()`, discarding the entire in-progress proposal/validation for that height/round [5](#0-4) .
6. The proposer must restart proposal building next round (or the validator rejects a legitimate proposal), delaying confirmation of all transactions that would otherwise have been included, purely due to one transaction's transient class-propagation timing.

    async fn add_txs_to_executor(&mut self) -> BlockBuilderResult<AddTxsToExecutorResult> {
        // Restrict the number of transactions to fetch such that the number of transactions in
        // progress is at most `n_concurrent_txs`.
        let n_concurrent_txs = self.execution_params.n_concurrent_txs;
        let n_txs_to_fetch = n_concurrent_txs - min(self.n_txs_in_progress(), n_concurrent_txs);

        if n_txs_to_fetch == 0 {
            return Ok(AddTxsToExecutorResult::NoNewTxs);
        }

        let next_txs = match self.tx_provider.get_txs(n_txs_to_fetch).await {
            Err(e @ TransactionProviderError::L1HandlerTransactionValidationFailed { .. })
                if self.execution_params.is_validator =>
            {
                warn!("Failed to validate L1 Handler transaction: {:?}", e);
                return Err(BlockBuilderError::FailOnError(L1HandlerTransactionValidationFailed(
                    e,
                )));
            }
            Err(err) => {
                error!("Failed to get transactions from the transaction provider: {:?}", err);
                return Err(err.into());
            }
            Ok(result) => result,
        };
