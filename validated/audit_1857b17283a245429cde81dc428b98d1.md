### Title
CORS Origin Allowlist Wildcard Matching Uses Naive Suffix Comparison, Enabling Origin Spoofing via Attacker-Registered Domains - (File: `core/services/gateway/network/httpserver.go`)

### Summary
The Chainlink Gateway's HTTP server implements its own CORS origin-allowlist check in `isAllowedOrigin` instead of relying on a hardened library. The wildcard-matching branch validates a wildcard entry like `*.example.com` by simply checking `strings.HasSuffix(originHost, allowedHost)` after stripping the `*.` prefix, with no check that the matched suffix is preceded by a literal dot (label boundary). This mirrors the bug class from the external report: origin/domain validation logic that is technically checking "does the string contain the right characters" rather than "is this actually a subdomain of the trusted domain," allowing attacker-controlled domains that merely share a trailing character sequence to be treated as trusted.

### Finding Description
`core/services/gateway/network/httpserver.go` defines: [1](#0-0) 

Specifically, the wildcard check:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```
strips `*.` from a configured allowlist entry (e.g. `*.ethereum.org` → `ethereum.org`) and then checks only that the request's `Origin` host string *ends with* that value. Because `strings.HasSuffix` performs a raw string suffix match, an attacker who registers (or otherwise controls) a domain such as `evilethereum.org`, `notethereum.org`, or `fakeethereum.org` would pass this check for an allowlist entry of `*.ethereum.org`, since `"evilethereum.org"` ends with the literal substring `"ethereum.org"` even though it is not a subdomain of `ethereum.org` at all — there is no DNS label boundary (`.`) enforced before the matched suffix.

This is directly analogous to the reported Solflare bug class: an origin-validation routine that appears to restrict access to a trusted domain and its subdomains, but which is implemented with insufficiently strict string/regex logic, allowing arbitrary attacker-registered domains to satisfy the check.

The `isAllowedOrigin` result gates whether the Gateway's `handleRequest` function echoes the request's `Origin` back in `Access-Control-Allow-Origin` (along with allowed methods/headers) for the user-facing Gateway HTTP endpoint: [2](#0-1) 

The existing test suite even documents intended-negative cases for exact suffixes without a dot boundary check, but does not cover the "shares a suffix without a dot" bypass case: [3](#0-2) 

### Impact Explanation
If a Gateway DON operator configures `CORSAllowedOrigins` with a wildcard entry (e.g. `*.chain.link`) to allow their own subdomains, an attacker who registers a similarly-suffixed domain (e.g. `notchain.link`) can craft a malicious web page that issues browser-based, credentialed cross-origin requests to the Gateway's user-facing HTTP API (`/user` path, JWT-based auth via `Authorization` header per `handleRequest`). Because the CORS check improperly treats the attacker's origin as trusted, the browser will permit the malicious page to read the JSON-RPC responses from the Gateway that would otherwise be blocked by the Same-Origin Policy. This can lead to disclosure of workflow/capability response data returned by the Gateway to an unauthorized third-party site and enables the general phishing/CSRF-style abuse pattern described in the source report (tricking a legitimate user's authenticated browser session into leaking data or performing gateway actions from an untrusted origin).

### Likelihood Explanation
Exploitation requires: (1) the Gateway operator configuring a wildcard entry in `CORSAllowedOrigins` (a documented, supported configuration pattern per `sample_config.toml`/`sample_config_tls.toml`), and (2) an attacker registering or controlling a domain that shares the trusted suffix without a dot boundary. Domain registration is trivial and inexpensive, and wildcard CORS entries are a normal real-world configuration choice (as also acknowledged as a common pattern in the original Solflare report). No authentication or insider access is required — this is exploitable by any external, unauthenticated network attacker who can get a victim's browser to visit their page.

### Recommendation
Replace the naive suffix check with a proper subdomain-boundary check, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".example.com" - keep the dot
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
(i.e., require that the origin host either equals the trusted domain, or ends with `"."+allowedHost` so that the matched suffix is guaranteed to be a real DNS label boundary). Additionally, consider migrating this custom origin-matching logic to a well-tested CORS library (similar to how `core/web/router.go`'s `uiCorsHandler` uses `github.com/gin-contrib/cors`) rather than maintaining a bespoke implementation, and add explicit tests for suffix-without-dot-boundary bypass attempts.

### Proof of Concept
1. Configure the Gateway's `UserServerConfig` with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.chain.link"]`.
2. From a browser, host a page at `https://notchain.link` (a domain fully controlled by the attacker, unrelated to `chain.link`).
3. Have the page issue a `fetch()`/`XMLHttpRequest` to the Gateway's `/user` endpoint with `Origin: https://notchain.link` and any required `Authorization` header/cookie the victim's browser already holds.
4. Observe that `isAllowedOrigin` returns `true` because `strings.HasSuffix("notchain.link", "chain.link")` is `true`, causing the server to respond with `Access-Control-Allow-Origin: https://notchain.link`, letting the attacker's page read the JSON-RPC response cross-origin — despite `notchain.link` never having been intended to match the `*.chain.link` wildcard.

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
