## Analog Found

### Title
Unhandled promise failure drops the caller's attached deposit in `near-wallet-contract`'s `address_check_callback` and `nep_141_storage_balance_callback` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `near-wallet-contract` (the NEAR wallet contract used to emulate Ethereum-style EOA accounts on NEAR) attaches an external caller's deposit (`caller_deposit`) so it can be refunded if a downstream cross-contract call fails. This refund logic is implemented correctly in the terminal callback, `rlp_execute_callback`, but two intermediate callbacks that are reachable first in a multi-hop promise chain — `address_check_callback` and `nep_141_storage_balance_callback` — return an error `ExecuteResponse` on failure **without forwarding or refunding `caller_deposit`**, silently dropping the caller's deposit exactly like the "handle error case" placeholder in the reported `swap-router` bug.

### Finding Description
`CallerDeposit` is created in `inner_rlp_execute` to track a non-self caller's attached deposit so it can be sent back if the eventual cross-contract call fails: [1](#0-0) 

For a plain single-hop action, `caller_deposit` is threaded into `rlp_execute_callback`, whose `PromiseResult::Failed` branch explicitly creates a refund promise back to the caller: [2](#0-1) 

However, for two multi-hop transaction kinds — an EOA base-token transfer that requires an address-registrar lookup, and an emulated ERC-20 transfer that requires a NEP-141 `storage_balance_of` check — `caller_deposit` is passed into intermediate callbacks instead of directly into `rlp_execute_callback`: [3](#0-2) 

In `address_check_callback`, when the address-registrar lookup promise fails, the function returns an error response and simply drops `caller_deposit` — it is never refunded nor forwarded: [4](#0-3) 

The same happens for a deserialization/"unexpected response" error in the same callback: [5](#0-4) 

`nep_141_storage_balance_callback` has the identical pattern: on `PromiseResult::Failed` for the `storage_balance_of` call, and on the "unexpected response" deserialization error, it returns a failure `ExecuteResponse` while dropping `caller_deposit`: [6](#0-5) 

In both callbacks, `caller_deposit` is only correctly threaded through to `rlp_execute_callback` on the *success* paths (`action_to_promise(...).then(ext.rlp_execute_callback(caller_deposit))` and similar), confirming the omission on the failure/error paths is not intentional but an oversight — the exact same class of bug as the reported `swap-router` PBC "handle error case" placeholder that discards state/funds on failure instead of reverting/refunding.

### Impact Explanation
Any unprivileged caller (a relayer submitting an Ethereum-emulated transaction on behalf of a user, or the wallet owner submitting a NEAR transaction directly) who attaches a deposit while calling `rlp_execute` on an eth-implicit account performing an emulated base-token transfer with `address_check` or an emulated ERC-20 transfer can lose that attached deposit permanently if the address-registrar lookup or NEP-141 `storage_balance_of` call fails (e.g., the registrar or token contract is temporarily out of gas, panics, or the target account genuinely doesn't exist). The deposit is neither returned to the caller nor consumed for its intended purpose — it is stranded in the wallet contract's balance with no code path to reclaim it, matching the "loss of funds / token lockup" impact category from the reported issue.

### Likelihood Explanation
This is reachable by any external account calling `rlp_execute` with a non-zero attached deposit on a wallet-contract-controlled account performing one of the two multi-hop transaction kinds (`EOABaseTokenTransfer` with `address_check`, or `ERC20Transfer`). No special privileges are required — any relayer or the account owner acting as an external caller can trigger it, and the failure condition (a failed cross-contract call to the registrar or a token contract) is not exotic — it can occur due to normal operational failures of the called contract, not just adversarial behavior.

### Recommendation
Thread `caller_deposit` through the failure and error-deserialization branches of `address_check_callback` and `nep_141_storage_balance_callback` exactly as is already done for `rlp_execute_callback`: on `PromiseResult::Failed` or malformed-response errors, issue a `promise_batch_action_transfer` refund to `caller_deposit.account_id` before returning the failed `ExecuteResponse`, mirroring the existing pattern in `rlp_execute_callback`.

### Proof of Concept
1. An external caller (not the wallet owner) submits `rlp_execute` with a non-zero `attached_deposit`, targeting an Ethereum-emulated base-token transfer whose destination requires an `address_check` (i.e., `target` hashes to a `to` address not already a named account).
2. `inner_rlp_execute` builds a `CallerDeposit` for the caller and schedules `address_registrar.lookup(address).then(address_check_callback(target, action, caller_deposit))` as shown at [7](#0-6) .
3. Cause the registrar lookup promise to fail (e.g., registrar contract panics or runs out of gas).
4. `address_check_callback` hits the `PromiseResult::Failed` branch at [8](#0-7)  and returns `ExecuteResponse { success: false, ... }` without ever creating a refund promise for `caller_deposit` — contrast with the correct handling in `rlp_execute_callback`'s `PromiseResult::Failed` arm at lines 296-312 of the same file. The caller's attached deposit remains stuck in the wallet contract with no remediation path.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
