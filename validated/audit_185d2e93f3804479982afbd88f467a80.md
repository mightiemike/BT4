## Title
Meta-transaction (NEP-366) deposit refunds are routed to the delegate's `sender_id` instead of the relayer who paid for the deposit, allowing a malicious sender to reliably reclaim relayer-funded deposits - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
This maps to the Sherlock M-1 bug class ("owner incurs loss/bad debt because the party that pre-pays costs is not the party that receives the refund/benefit when the action does not go through as expected"). In nearcore's meta-transaction (delegate action) flow, the relayer pre-pays both gas and any attached token deposit for the inner actions signed by the sender. If the inner action fails on the receiver's shard, the deposit refund goes to the delegate's `sender_id` (the predecessor), not to the relayer who actually funded the deposit. [1](#0-0) 

### Finding Description
`apply_delegate_action` explicitly documents and implements this behavior: the relayer prepays all fees and attached deposits for the inner actions, but if the inner action fails, the deposit is refunded to the predecessor (`sender_id` from the `DelegateAction`), not to the relayer: [2](#0-1) 

This is confirmed by `refund_unspent_gas_and_deposits`, which computes `deposit_refund` on failure and sends it via `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)` — the balance-refund receiver for a receipt whose predecessor is the sender's account resolves to that sender, not the relayer's account: [3](#0-2) [4](#0-3) 

The protocol documentation independently confirms this is a real, exploitable asymmetry and calls out the financial incentive it creates for the sender to abuse it: [5](#0-4) 

The general refund rule ("Deposit refunds ... sent as a refund to a `predecessor_id`") reinforces that this is the standard runtime path, not a bug limited to a special case: [6](#0-5) 

### Impact Explanation
A malicious sender (Alice) can sign a `DelegateAction` whose inner actions carry an attached deposit destined for a third party (Bob) but are engineered to fail deterministically on the receiver's shard (e.g., insufficient gas for receiver-side logic, a contract assertion that always reverts, or targeting a receiver that will reject the call). Because the relayer funds the deposit up front and the deposit refund is routed to `sender_id` (Alice) rather than to the relayer, Alice can extract the relayer-funded deposit back to herself with certainty, at zero cost to herself beyond crafting the delegate action. This is a concrete unauthorized value movement from the relayer to the sender — precisely the loss/bad-debt pattern described in the M-1 report, where the party bearing upfront cost (owner/relayer) is not guaranteed to recover value when the counterparty causes/chooses failure.

### Likelihood Explanation
This requires no privileged access — only a standard transaction signer acting as the "sender" side of a meta transaction, reachable by any account that a relayer is willing to sponsor. The relayer cannot fully prevent this without out-of-band trust/verification of the inner action's success probability, which the code comments themselves acknowledge ("Relayer should verify DelegateAction before submitting it because it spends the attached deposit"). This makes exploitation likelihood high for any general-purpose or semi-trusting relayer service, and the docs themselves flag it as a known but currently accepted design trade-off in the meta-transaction MVP.

### Recommendation
Route deposit refunds for delegate-action inner-action failures to the relayer (the actual payer of the deposit) instead of the `sender_id`/predecessor, or require the relayer to attach and reclaim deposits via a separate escrow/refund path that is not controllable by the sender causing failure. Alternatively, document and enforce a hard requirement that relayers dry-run/simulate delegate actions before submission, and consider rate-limiting or bonding sender accounts that repeatedly cause inner-action failures in delegated transactions.

### Proof of Concept
1. Alice (sender) crafts a `DelegateAction` with `sender_id = Alice`, `receiver_id = Bob`, containing an inner `FunctionCall` or `Transfer` action with an attached deposit, where the inner action is guaranteed to fail on Bob's shard (e.g., calling a method that always panics, or attaching insufficient gas for the receiver logic to complete).
2. Alice signs it and sends the `SignedDelegateAction` off-chain to a relayer.
3. The relayer wraps it in a transaction and submits it, paying gas and the attached deposit per `apply_delegate_action`: [7](#0-6) 
4. The inner action executes on Bob's shard and fails as designed.
5. `refund_unspent_gas_and_deposits` computes `deposit_refund = total_deposit` (since `result.result.is_err()`) and issues `Receipt::new_balance_refund` to the predecessor of that failed receipt, which is Alice (the `sender_id`), not the relayer: [8](#0-7) 
6. Alice receives back the deposit that the relayer funded, while Bob receives nothing and the relayer is out the deposit amount permanently — a repeatable, unauthorized transfer of value from relayer to sender.

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```

## Deposit Refunds

Deposit refunds are generated when an action receipt fails to execute. All attached deposit amounts are summed together and
sent as a refund to a `predecessor_id` (because only the predecessor can attach deposits).
