### Title
Uncontrolled Resource Consumption via Unbounded WASM Data/Element Segment Instantiation Cost - (File: `runtime/near-vm-runner/src/prepare/prepare_v3.rs`, `core/parameters/src/vm.rs`)

### Summary
NEAR's contract-preparation pass enforces a cap on the number of globals a contract can declare (`max_globals_per_contract` in `core/parameters/src/vm.rs`), but there is **no equivalent limit on the number of active data segments or active element segments** a contract may declare. The runtime's own cost-estimator code explicitly documents that these constructs cause "unbounded per-call ... initialization work not covered by gas". Any account can deploy a contract containing tens of thousands of tiny active data/element segments and then repeatedly invoke it with ordinary `FunctionCall` transactions, forcing every validator that executes the receipt to pay disproportionately high CPU/memory cost per unit of gas charged — a classic uncontrolled-resource-consumption analog to CVE‑2020‑8123 (excessive, attacker-triggerable resource consumption reachable by an ordinary, non-privileged actor).

### Finding Description
`LimitConfig` (`core/parameters/src/vm.rs:140-187`) defines optional per-contract shape limits enforced during `prepare_contract` (`runtime/near-vm-runner/src/prepare.rs:21`, dispatched to `prepare_v3`): `max_functions_number_per_contract`, `max_locals_per_contract`, `max_tables_per_contract`, `max_elements_per_contract_table`, `max_blocks_per_function`/`_contract`, `max_types_per_contract`, and (as of protocol version 157, `core/parameters/res/runtime_configs/157.yaml`) `max_globals_per_contract`. There is no `max_data_segments_per_contract` or `max_element_segments_per_contract` field in `LimitConfig` at all, and no corresponding check in `prepare_v3.rs`/`instrument_v3.rs`. [1](#0-0) [2](#0-1) 

The runtime's own params-estimator crate acknowledges the gap by name: `AdversarialLoadManyDataSegments` and `AdversarialLoadManyElementSegments` are defined specifically to "expose unbounded per-call data-segment initialization" and "unbounded per-call table-initialization work not covered by gas." [3](#0-2) 

The test helpers `many_data_segments_contract` (writes N tiny active data segments into linear memory) and (implicitly) a many-element-segments equivalent are used purely to measure — not bound — this cost, confirming these shapes pass `prepare_contract` unmodified up to the generic `max_contract_size` limit (4 MiB), independent of segment count. [4](#0-3) [5](#0-4) 

Gas charged for contract execution is dominated by `contract_loading_base`/`contract_loading_bytes` (linear in wasm byte size, `runtime/near-vm-runner/src/logic/gas_counter.rs:216-227`) plus per-instruction `regular_op_cost`. Neither cost component accounts for the cost the VM backend (Wasmtime/NearVM) actually pays at **every single call** to re-initialize memory/table contents from data/element segments during instantiation — this is exactly the gap the `contract-vm.md` architecture doc and the estimator "Adversarial" cost family were created to characterize, and the analogous `contract_with_num_globals` case (`test_max_core_instance_size_breached`) shows the class of bug is real and reachable even when eventually caught for one specific shape (globals); the equivalent caps for data/element segments simply do not exist. [6](#0-5) [7](#0-6) 

### Impact Explanation
Any unprivileged account can deploy such a contract with a single `DeployContract` action and then submit ordinary `FunctionCall` transactions calling it. Because gas is charged roughly per byte/instruction while the actual per-call instantiation cost scales with segment count in a way that is not linearly reflected in the fee, an attacker can force chunk producers/validators to spend far more wall-clock CPU time per unit of gas than intended. Submitted at scale (repeated calls across many receipts in a chunk), this degrades block/chunk production time uniformly for all honest validators, risking missed chunk/block production deadlines — a transaction-triggered denial-of-service on the network's liveness, directly analogous to the Strapi CVE's "arbitrary restart"/DoS via disproportionate resource use triggered by an in-scope actor (here, any transaction signer rather than an admin).

### Likelihood Explanation
Likelihood is moderate: deploying the crafted contract and calling it requires no special privilege beyond normal account/contract-deployment capability (near-ubiquitously available on NEAR), and the contract shapes (`many_data_segments_contract`, many-element-segments equivalent) are already implemented and validated as passing `prepare_contract` in this very codebase's test/estimator suite. The main uncertainty is the magnitude of the wall-clock/gas mismatch in absolute terms on current hardware/backends (Wasmtime vs NearVM), which this analysis could not quantify further without running the actual estimator; the codebase's own comments, however, assert the mismatch is real and "unbounded."

### Recommendation
Add explicit `LimitConfig` fields (e.g., `max_data_segments_per_contract`, `max_element_segments_per_contract`) enforced in `prepare_v3.rs`, mirroring the newly-added `max_globals_per_contract` check, and/or introduce a gas-metered cost for data/element segment count and total segment bytes during `add_contract_loading_fee`/instantiation so the fee scales with actual per-call instantiation work rather than only with raw code size.

### Proof of Concept
1. Use `near_test_contracts::many_data_segments_contract(50_000)` (already present in this repo's test helpers) to build a WASM module containing 50,000 tiny active data segments and a nearly-empty `main` export.
2. Deploy it via a normal `DeployContract` action from any funded account.
3. Repeatedly submit `FunctionCall("main")` transactions against the deployed contract with only the gas needed to cover the reported `contract_loading_base`/`contract_loading_bytes`/`regular_op_cost` fee.
4. As reproduced by `runtime/runtime-params-estimator/src/vm_estimator.rs::adversarial_load_many_data_segments` / `measure_instantiation_overhead`, each such call pays the Wasmtime/NearVM re-instantiation cost of writing all 50,000 segments into memory on every invocation, which the estimator itself flags as "not covered by gas" — confirming the fee-to-cost mismatch that an attacker can exploit at scale by submitting many such calls per chunk. /// Many tiny active data segments, each writing 1 byte to memory offset 0.
pub fn many_data_segments_contract(num_segments: u32) -> Vec<u8> {
    let mut module = Module::new();
    let mut types = TypeSection::new();
    types.ty().function([], []);
    module.section(&types);
    let mut funcs = FunctionSection::new();
    funcs.function(0);
    module.section(&funcs);
    let mut memories = MemorySection::new();
    memories.memory(MemoryType {
        minimum: 1,
        maximum: None,
        memory64: false,
        shared: false,
        page_size_log2: None,
    });
    module.section(&memories);
    let mut exports = ExportSection::new();
    exports.export("main", ExportKind::Func, 0);
    module.section(&exports);
    let mut data = DataSection::new();
    for i in 0..num_segments {
        data.active(0, &ConstExpr::i32_const(0), [i as u8]);
    }
    module.section(&data);
    let mut code = CodeSection::new();
    let mut f = Function::new([]);
    f.instruction(&Instruction::End);
    code.function(&f);
    module.section(&code);
    module.finish()
}

/// Warm the compile cache, then measure N invocations (instantiation + trivial execution).
/// The function body is a bare `end`, so execution cost is negligible.
fn measure_instantiation_overhead(
    metric: GasMetric,
    vm_kind: VMKind,
    contract_bytes: &[u8],
) -> GasCost {
    let config_store = RuntimeConfigStore::new(None);
    let mut config = config_store.get_config(PROTOCOL_VERSION).wasm_config.as_ref().clone();
    config.vm_kind = vm_kind;
    let config = Arc::new(config);
    let fees = Arc::new(RuntimeFeesConfig::test());
    let code = ContractCode::new(contract_bytes.to_vec(), None);
    let cache = MockContractRuntimeCache::default();
    let mut fake_external = near_vm_runner::logic::mocks::mock_external::MockedExternal::with_code(
        code.clone_for_tests(),
    );

    let mut run_once = || {
        let context = create_context(vec![]);
        let gas_counter = context.make_gas_counter(&config);
        vm_kind
            .runtime(config.clone())
            .unwrap()
            .prepare(&fake_external, Some(&cache), gas_counter, "main")
            .run(&mut fake_external, &context, Arc::clone(&fees))
            .expect("fatal_error")
    };

    // Warm: compiles and caches the module; subsequent calls only instantiate + execute.
    run_once();

    let n = 10_usize;
    let start = GasCost::measure(metric);
    for _ in 0..n {
        run_once();
    }
    start.elapsed() / n as u64
}

/// Compile and load a contract with 100k globals.
///
/// Each defined global occupies 16 bytes of a core instance's `VMContext`, so
/// globals alone add ~1.6 MB. That breaches the 1MiB `max_core_instance_size`
/// slot of the Wasmtime pooling allocator, so loading the module at

/// `prepare` and is caught by the Wasmtime backstop at load time.
///
/// Pre-`FixContractLoadingError` this surfaces as `VMRunnerError::LoadingError`,
/// which the runtime maps to a zero-gas nop — the contract-loading work is left
/// uncharged. Post-feature the same failure finalizes as a gas-bearing abort
/// that charges the contract-loading fee. Either way it must not panic / crash
/// the node.
