### Title
Light client proof method ID has no canonical/on-chain anchor, allowing honest provers to commit different `light_client_proof_method_id` values for the same L1 block - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
`LightClientProofCircuit::run_circuit` takes `light_client_proof_method_id` purely as untrusted circuit input, verifies the previous proof against it, and copies it verbatim into the new `LightClientCircuitOutput` without ever checking it against any build-time constant embedded in the guest ELF or any on-chain/security-council-signed value. Two honest provers running the identical guest ELF for the same L1 block but supplied with different `light_client_proof_method_id` values will both produce cryptographically valid proofs whose journals commit different method IDs, splitting the light client proof chain.

### Finding Description
Binding claimed to hold: `light_client_proof_method_id` committed by honest prover A for L1 block N == `light_client_proof_method_id` committed by honest prover B for L1 block N, when both run the same ELF over the same block data.

In `run_circuit` [1](#0-0) , the only checks performed on `input.light_client_proof_method_id` are:
1. It is used as the verification key to check the *previous* proof: `Z::verify_and_deserialize_output::<LightClientCircuitOutput>(&proof, &input.light_client_proof_method_id.into(), ...)`.
2. `assert_eq!(input.light_client_proof_method_id, prev_output.light_client_proof_method_id)` — self-consistency with the previous proof's *self-reported* value only.

Neither check anchors the value to anything derived from the actual ELF that is running, or to a signed/on-chain authority. The value is then copied straight to the output: [2](#0-1) .

This contrasts with the batch-proof method ID mechanism, which is hardcoded per-fork at compile time (`INITIAL_BATCH_PROOF_METHOD_IDS`) and only mutated by a security-council-signed transaction via `verify_method_id_security_council` [3](#0-2) . No equivalent mechanism exists for the light client proof's own method ID.

Confirming that the guest binary itself never validates or hardcodes this field: `light_client_proof_bitcoin.rs` reads the whole `LightClientCircuitInput` (including `light_client_proof_method_id`) straight from the host with `guest.read_from_host()` and passes it unchanged into `run_circuit`: [4](#0-3) . Unlike `INITIAL_BATCH_PROOF_METHOD_IDS`, `L2_GENESIS_ROOT`, etc., there is no `LIGHT_CLIENT_PROOF_METHOD_ID` constant baked into the guest for self-comparison.

The most critical instance of the gap is the *genesis* light client proof, where `previous_light_client_proof` is `None`: in that branch, `previous_light_client_proof_output` is simply `None` and none of the checks in lines 686-705 execute at all — `input.light_client_proof_method_id` is accepted unconditionally and committed to the output. From that point on, the value only needs to be self-consistent across a single prover's own proof chain (line 698-701), not consistent with any other honest prover's chain or with the true cryptographic image ID of the ELF (which is a completely separate, VM-internal value bound to the receipt's claim and never compared against this application-level field).

Consequently, prover A (fresh method-id constant X) and prover B (stale cached constant Y), both legitimately running the same ELF for L1 block N, produce two valid receipts whose claims are both anchored to the real ELF image ID, but whose journals commit `light_client_proof_method_id = X` and `= Y` respectively. Downstream, any consumer (e.g. Clementine's bridge circuit, or a node that pins a specific method ID) that expects one specific value will accept one honest prover's chain and reject the other's, even though both are otherwise valid state transitions over the same L1/L2 history.

### Impact Explanation
This splits the provable light client chain for the same L1 block height between two sets of otherwise-honest provers/configurations. Any downstream verifier (in particular Clementine's bridge proof verification, which the docs state is the primary consumer of the light client proof) that hardcodes or expects a specific method ID will accept exactly one of the two chains and reject the other, even though both represent the same correct L2/DA history. This matches the "light client proof split where two honest provers commit different outputs for the same L1 block" Critical impact category — it is a DETERMINISM violation of the light client proof chain, repeatable at any L1 height where such divergence starts (most trivially at genesis, and persistently for every subsequent block in each of the two forked chains, since the self-consistency check only propagates whichever value was chosen at genesis).

### Likelihood Explanation
No signature, on-chain authority, or hardcoded ELF constant enforces a single canonical `light_client_proof_method_id`; it is purely a runtime/host-configuration value threaded through `LightClientCircuitInput`. Any deployment/config drift between light client prover operators (e.g., stale cached constant vs. freshly rebuilt binary/config, or divergent `code_commitments` maps used by `input_builder.rs` [5](#0-4) ) is sufficient to trigger this — no Bitcoin fees, no malicious transaction, and no privileged role are required. This makes the divergence plausible from ordinary operational configuration differences rather than requiring an active attack.

### Recommendation
Bind `light_client_proof_method_id` to a value the guest can verify independently of host-supplied input — e.g., embed the expected method ID as a build-time constant in each guest ELF (as is already done for `INITIAL_BATCH_PROOF_METHOD_IDS`, `L2_GENESIS_ROOT`, DA public keys, etc.) and assert `input.light_client_proof_method_id == EXPECTED_METHOD_ID` inside `run_circuit`/the guest `main`, or otherwise anchor it to a security-council-authorized on-chain upgrade record analogous to the batch-proof method ID mechanism, rather than trusting the caller-supplied value even for the very first ("genesis") light client proof.

### Proof of Concept
```rust
// crates/light-client-prover/src/tests/mod.rs
#[test]
fn test_light_client_proof_split_via_mismatched_method_id() {
    let db_dir_a = tempdir().unwrap();
    let db_dir_b = tempdir().unwrap();
    let native_runner_a = NativeCircuitRunner::new(db_dir_a.path().to_path_buf());
    let native_runner_b = NativeCircuitRunner::new(db_dir_b.path().to_path_buf());
    let zk_circuit_runner = LightClientProofCircuit::<ZkStorage, MockDaSpec, MockZkGuest>::new();

    let da_verifier = MockDaVerifier {};
    let block_header_1 = MockBlockHeader::from_height(1);
    let l2_genesis_state_root = [1u8; 32];
    let batch_prover_da_pub_key = [9; 32];
    let sequencer_da_pub_key = [45; 32];

    // Identical da_block_header / inclusion_proof / completeness_proof for both provers,
    // ONLY the method id constant differs.
    let method_id_x = [1u32; 8]; // "fresh" constant
    let method_id_y = [2u32; 8]; // "stale cached" constant

    let make_input = |method_id: [u32; 8], runner: &NativeCircuitRunner| {
        runner.run(
            LightClientCircuitInput {
                previous_light_client_proof: None,
                light_client_proof_method_id: method_id,
                da_block_header: block_header_1.clone(),
                inclusion_proof: [1u8; 32],
                completeness_proof: vec![],
                witness: Default::default(),
            },
            l2_genesis_state_root,
            INITIAL_BATCH_PROOF_METHOD_IDS.to_vec(),
            &batch_prover_da_pub_key,
            &sequencer_da_pub_key,
            &METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS,
            Network::Nightly,
        )
    };

    let input_a = make_input(method_id_x, &native_runner_a);
    let input_b = make_input(method_id_y, &native_runner_b);

    let output_a = zk_circuit_runner
        .run_circuit(
            da_verifier.clone(), input_a, ZkStorage::new(), Network::Nightly,
            l2_genesis_state_root, INITIAL_BATCH_PROOF_METHOD_IDS.to_vec(),
            &batch_prover_da_pub_key, &sequencer_da_pub_key,
            &METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS,
        )
        .unwrap();

    let output_b = zk_circuit_runner
        .run_circuit(
            da_verifier, input_b, ZkStorage::new(), Network::Nightly,
            l2_genesis_state_root, INITIAL_BATCH_PROOF_METHOD_IDS.to_vec(),
            &batch_prover_da_pub_key, &sequencer_da_pub_key,
            &METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS,
        )
        .unwrap();

    // Both executions succeed (no panic, no error) for the same L1 block,
    // but produce different committed method ids -> chain split.
    assert_eq!(output_a.l2_state_root, output_b.l2_state_root);
    assert_ne!(
        output_a.light_client_proof_method_id,
        output_b.light_client_proof_method_id
    );
}
```
This test demonstrates that `run_circuit` places no constraint tying `light_client_proof_method_id` to anything beyond the caller-supplied value, allowing two otherwise-identical, honestly-executed runs to diverge on this committed field for the same L1 block.
