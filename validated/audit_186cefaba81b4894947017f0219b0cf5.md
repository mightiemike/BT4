## Analysis

The OtterSec finding describes an attacker filling a capacity-limited, supposedly cost-bearing list with fake/free entries because the system fails to enforce a meaningful minimum contribution per entry, degrading service for legitimate users at effectively zero cost. Searching Push Chain's node code for an analogous "let anyone create free persistent state records with no meaningful cost" pattern points at the gasless account-bootstrap path in the custom ante pipeline.

`app/ante/account_init_decorator.go`'s `AccountInitDecorator.AnteHandle` fires only for gasless transactions (`txpolicy.IsGaslessTx`, whose allowlist in `app/txpolicy/gasless.go` includes `MsgExecutePayload`, submittable by "any" signer per `x/uexecutor/README.md:204,215`). If the tx's signer account does not yet exist, the decorator verifies a self-consistent signature over `account_number=0, sequence=0` and then unconditionally does `aid.ak.NewAccountWithAddress(...)` / `aid.ak.SetAccount(...)`, returning `ctx, nil` **without invoking `next`**, i.e. bypassing `SetPubKeyDecorator`, `DeductFeeDecorator`'s later fee logic (already skipped earlier for gasless), and normal sequence checks. [1](#0-0) 

In `app/ante/ante_cosmos.go`, `NewAccountInitDecorator` runs after `DeductFeeDecorator` (which already exempted gasless txs from any fee) and before signature/sequence decorators, meaning the entire account-creation side effect happens with zero economic cost to the caller. [2](#0-1) 

Because Cosmos SDK's `runTx` commits AnteHandler-branch state changes (fee deduction, sequence increments, and here, account creation) independently of whether the wrapped `Msg` execution later succeeds or reverts, an attacker can generate an unlimited number of throwaway keypairs off-chain, sign one `MsgExecutePayload` each (with any/garbage `UniversalAccountId`/payload — the underlying message can legitimately fail and revert per `x/uexecutor/README.md:227,236` "Net effect: zero state change... The submission costs the attacker nothing on chain"), and have each transaction unconditionally persist a brand-new account entry in the `x/auth` account store at zero fee, since the whole point of the gasless allowlist is "no balance required" onboarding for first-time signers. [3](#0-2) [4](#0-3) 

This mirrors the OtterSec bug class: a mechanism meant to let genuine participants act cheaply (bonded UVs / gasless UEA users) has no minimum-cost or rate-limiting per created record, so an attacker can flood chain state with an unbounded number of free, meaningless account entries — growing the IAVL/account store, increasing snapshot/sync size and node resource requirements over time, i.e., a non-network-level, unprivileged-triggerable degradation vector.

I did not find, however, a hard numeric cap analogous to `MAX_NUMBER_OF_DELEGATIONS` anywhere in `x/uexecutor`, `x/uvalidator`, or `x/utss` — the `PendingInbounds`/`PendingOutbounds`/`Variants` growth paths that do have unbounded-list characteristics (`x/uexecutor/keeper/inbound.go`, `x/uexecutor/keeper/pending_outbound.go`) are only reachable via `MsgVoteInbound`/`MsgVoteOutbound`, which require `IsBondedUniversalValidator` (a privileged role explicitly out of scope per the report's rules), so those are not valid analogs. [5](#0-4) 

Given the effort-limited investigation, I can identify this candidate but have not fully confirmed (via runtime trace/test) that the SDK's `runTx` in this specific cosmos-evm fork commits ante-phase state on message failure, nor whether mempool-level fee-priority policies (`checkTxFeeWithValidatorMinGasPrices`, `MinGasPriceDecorator`) meaningfully throttle zero-fee gasless tx inclusion in practice. A deeper investigation (or a Devin session with repo access to run/trace this) is warranted before treating this as a confirmed, exploitable finding.

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
