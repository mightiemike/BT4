### Title
Global compiled-class cache skips the `is_declared` freshness check for Cairo0 (V0) classes, allowing undeclared bytecode to be treated as declared - (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` serves compiled classes from a long-lived, cross-block `ContractClassManager` cache keyed only by `class_hash`. For Cairo1 (V1/V1Native) classes it re-validates that the class hash is still actually declared in the authoritative state (`self.state_reader.is_declared(class_hash)?`) before trusting the cached entry, explicitly because "existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)". For Cairo0 (V0) classes this freshness check is skipped entirely - the cached value is returned as-is.

### Finding Description
`StateReaderAndContractManager` wraps the real `StateReader` used by block execution (`apollo_batcher`, `apollo_gateway`'s stateful validator, the transaction prover, and `native_blockifier`) with a `ContractClassManager` that caches compiled classes globally, independent of block/state versioning: [1](#0-0) 

The cache lookup branches on class kind:
- `RunnableCompiledClass::V0(_)`: returned directly from cache, no re-check against current state.
- Any Cairo1 variant: guarded by `self.state_reader.is_declared(class_hash)?`, with the comment noting the cache can hold "a declared class from a reverted block."

This is the same root-cause pattern as the audited Balancer bug: a value that was correct *at the time it was cached/derived* (an invariant computed from a since-changed amplification parameter; here, "this class hash was declared" observed at some earlier point) is reused later without re-validating it against the current authoritative source of truth, even though the authoritative state can have changed underneath it (a declare being reverted, a block reorganized, or - in the analogous mempool/RPC path - a class fetched during fee estimation/simulation before it was ever actually declared on-chain).

Because the cache is populated by any code path that calls `get_compiled_class`/`get_compiled_from_class_manager` (including simulation/estimate-fee/validation paths in the gateway's `apollo_stateful_transaction_validator`, not only committed execution), a Cairo0 class hash can enter the global cache without ever being committed as declared in the canonical state. A subsequent transaction (e.g., a `DeployAccount` or `InvokeFunction`/`Deploy` targeting that class hash) that reaches `get_compiled_class` will hit the cache and receive `Ok(RunnableCompiledClass::V0(...))` even though `is_declared(class_hash)` would return `false` for the current committed state - bypassing the "class must be declared before use" invariant that Starknet's execution model relies on for V0 classes specifically.

### Impact Explanation
If exploitable, this breaks the "must declare before deploy/use" invariant for Cairo0 classes: a contract could run code that is not reflected in the committed `declared_contracts` state diff, meaning the executed bytecode has no corresponding on-chain declaration entry. This is a wrong-committed-root class of bug - the state diff/state root produced by block building would not include the declaration that made execution possible, while a node that never happened to populate its local cache with that class hash (e.g., because it didn't previously process the reverted/simulated declare) would reject the same transaction as `UndeclaredClassHash`, producing honest-node divergence in block building and validation. It also constitutes unauthorized contract behavior: a class the deployer never legitimately declared and paid declare fees for gets executed as if declared.

### Likelihood Explanation
The main uncertainty is exploitability in practice: on Starknet mainnet, Cairo0 declarations are frozen (no new Cairo0 declares are accepted), which would sharply limit new attack surface via fresh V0 class hashes. However, the vulnerable code path itself is unconditional and reachable by any unprivileged actor whose transactions (Declare/Deploy/DeployAccount/Invoke) cause `get_compiled_class` to be invoked for a V0 class hash, including via RPC simulate/estimate-fee calls that populate the shared cache before a real declare/revert sequence occurs. Given the explicit comment acknowledging exactly this staleness risk for V1 but omitting the guard for V0, this looks like an unintentional asymmetry rather than a deliberate design choice, which raises confidence that it is a genuine defect rather than an intentionally-safe simplification. I was not able to fully verify, within the available iterations, whether some other layer (e.g. `is_declared` still gating entry into `set_and_compile`, or bouncer/OS re-execution) independently blocks this path for V0 - this needs to be confirmed by tracing all callers of `ContractClassManager::set_and_compile` and `get_runnable` across `apollo_batcher::block_builder`, `apollo_gateway::stateful_transaction_validator`, and `starknet_transaction_prover`.

### Recommendation
Apply the same `is_declared(class_hash)` (or equivalent freshness) check for `RunnableCompiledClass::V0` that is already applied to the Cairo1 branches in `get_compiled_from_class_manager`, so that a V0 cache hit is only trusted when the class is currently declared in the authoritative state, mirroring the fix recommended in the analogous report (always validate against the latest authoritative state rather than a value cached from a possibly-superseded point in time).

### Proof of Concept
Not independently reproduced against the live sequencer in this session; the analog is derived directly from the code and its own comment describing the staleness risk: [2](#0-1) 
A concrete PoC would need to: (1) trigger population of the global `ContractClassManager` cache with a Cairo0 class hash whose declaration is later reverted/never committed (e.g. via a simulate/estimate-fee call or a declare transaction in a block that gets reorganized), then (2) submit a `DeployAccount`/`Invoke` transaction referencing that class hash on a node whose cache still holds it, and observe that execution succeeds instead of failing with `StateError::UndeclaredClassHash`, while a fresh node without that cache entry rejects the same transaction - producing a state/consensus divergence. Constructing and running this PoC requires access to a running sequencer/test harness, which was outside the scope of this ask-only analysis.

impl<S: FetchCompiledClasses> StateReaderAndContractManager<S> {
    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }
        self.increment_cache_miss_metric();

        let compiled_class = self.state_reader.get_compiled_classes(class_hash)?;
        self.contract_class_manager.set_and_compile(class_hash, compiled_class.clone());
        // Access the cache again in case the class was compiled.
        let runnable_class = self
            .contract_class_manager
            .get_runnable(&class_hash, &self.native_classes_whitelist)
            .unwrap_or_else(|| {
                // Edge case that should not be happen if the cache size is big enough.
                // TODO(Yoni): consider having an atomic set-and-get.
                log::error!("Class is missing immediately after being cached.");
                compiled_class.to_runnable()
            });
        self.update_native_metrics(&runnable_class);
        Ok(runnable_class)
    }
