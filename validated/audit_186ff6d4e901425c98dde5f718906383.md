### Title
Hardcoded `paid_fee_on_l1 = Fee(1)` during consensus validation makes the L1Handler insufficient-fee check unenforceable - ([File: crates/apollo_transaction_converter/src/transaction_converter.rs])

### Summary
When a validator node receives an `L1Handler` transaction as part of a consensus proposal, `TransactionConverter::convert_consensus_l1_handler_to_internal_l1_handler` reconstructs the internal, executable `L1HandlerTransaction` and hardcodes the `paid_fee_on_l1` field to `Fee(1)` instead of using the actual fee that was paid on L1 for that message. [1](#0-0) 

### Finding Description
This mirrors the Synthetix `M-36` bug class: a downstream calculation (there, the margin computation; here, the fee-sufficiency check) is fed a placeholder/incorrect amount instead of the real, previously-established value (there, the actual `sUSD` received; here, the actual fee paid on L1 for the message).

Concretely, `convert_consensus_l1_handler_to_internal_l1_handler` builds the `executable_transaction::L1HandlerTransaction` via `L1HandlerTransaction::create(tx, &self.chain_id, Fee(1))`, with an explicit acknowledgment in the code that this is a stand-in:
```
// TODO(Gilad): Change this once we put real value in paid_fee_on_l1.
Fee(1),
``` [2](#0-1) 

That constructed transaction later reaches `blockifier`'s `L1HandlerTransaction::execute_raw`, which performs the *only* enforcement of L1-paid fee sufficiency:
```rust
let paid_fee = self.paid_fee_on_l1;
// For now, assert only that any amount of fee was paid.
if paid_fee == Fee(0) {
    return Err(TransactionExecutionError::TransactionFeeError(Box::new(
        TransactionFeeError::InsufficientFee { paid_fee, actual_fee: receipt.fee },
    )));
}
``` [3](#0-2) 

Because the sequencer path (`convert_consensus_tx_to_internal_consensus_tx` → `convert_consensus_l1_handler_to_internal_l1_handler`) always injects `Fee(1)`, the equality check `paid_fee == Fee(0)` can never be true for any `L1Handler` transaction reconstructed on this path, regardless of what was actually paid on L1 — the check is effectively a no-op comment-only stub, not a real value comparison as its own code comment ("assert only that any amount of fee was paid") indicates it was intended to at least loosely enforce.

This function is called from `convert_consensus_tx_to_internal_consensus_tx`, which is invoked by validators processing proposal parts during consensus (`apollo_consensus_orchestrator/src/validate_proposal.rs`) — i.e., it is on the path from an untrusted proposer's transaction data being converted for local re-execution by every validating node, not merely a test-only helper. [4](#0-3) 

### Impact Explanation
This weakens (effectively disables) the fee-sufficiency safety check for L1-originated messages executed by the sequencer during block validation/re-execution. However, the practical damage is limited by two factors: (1) the check itself is already commented as only a loose sanity check ("assert only that any amount of fee was paid"), not a strict accounting of `paid_fee` vs `actual_fee`; and (2) I could not fully verify (due to tool/iteration limits) whether the value used in actual block *building* (as opposed to consensus *validation*) comes from the same hardcoded stub or from a genuine L1-scraped fee value elsewhere (e.g., `apollo_consensus_orchestrator/src/cende/central_objects.rs`, `blockifier/src/test_utils/l1_handler.rs`, `starknet_transaction_prover/src/running/virtual_block_executor.rs` all reference `paid_fee_on_l1` too). If the block-building/proposing path uses a real fee value while only the validating path uses `Fee(1)`, honest validators would simply always pass this weak check without meaningfully verifying the proposer's claim — this could mask legitimately fee-insufficient L1 handler transactions, but since the check was already coarse (any non-zero fee passes), the security delta may be small rather than causing direct fund loss.

### Likelihood Explanation
This code path executes unconditionally for every `L1Handler` transaction seen by a validator in consensus — no special conditions or privileged access are needed, since the transaction data being converted originates from L1 messages relayed through the ordinary transaction/consensus pipeline. The TODO comment confirms this is a known, intentional placeholder not yet replaced with real data, indicating it is a live gap in the current codebase rather than a hypothetical scenario.

### Recommendation
Populate `paid_fee_on_l1` with the actual fee paid on L1 for the message (as tracked by the L1 event/message scraper) when reconstructing the executable `L1HandlerTransaction` during consensus conversion, matching whatever value is used during block proposal/building, so the sufficiency check in `blockifier::transaction::l1_handler_transaction::execute_raw` reflects the real amount instead of a hardcoded placeholder.
