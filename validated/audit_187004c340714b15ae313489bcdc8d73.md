## Analog Found: Attacker-Controlled CEA Inbound Bypasses UEA Signature Check to Spend Victim's PRC20 Funds

### Title
Unsigned, Attacker-Chosen `Recipient` in CEA Inbound Path Lets Module Execute Arbitrary Payloads on a Victim's UEA Without Owner Signature - ([File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go])

### Summary
The external report's root concern — a spender being able to move a user's ERC20-class tokens without the user's own explicit, per-transaction signature — has a direct on-chain analog in `x/uexecutor`. When an inbound is `IsCEA=true`, the `Recipient` UEA is taken directly from attacker-controlled source-chain event data and is completely decoupled from `Sender`/`UniversalAccountId.Owner`. After deposit, the keeper unconditionally calls `ExecutePayloadV2` against that `Recipient` UEA using the `uexecutor` module account as `evmFrom`. Per this repo's own documentation, the UEA contract skips owner-signature verification specifically when the EVM caller is `UNIVERSAL_EXECUTOR_MODULE`. Combining these two facts, an unprivileged external attacker who merely sends an ordinary transaction on a connected source chain (fully within their own control) can name *any* existing UEA as `Recipient` and supply an arbitrary `UniversalPayload`/`Data` and empty `VerificationData`, causing Push Chain to execute that payload *as* the victim's UEA — e.g. calling `transfer()`/`approve()` on a PRC20 held by that UEA — without the victim ever signing anything.

### Finding Description
- `ExecuteInboundFundsAndPayload` resolves `ueaAddr` for a CEA inbound purely from `utx.InboundTx.Recipient` (attacker-controlled field of the source-chain event), independent of `Sender`: [1](#0-0) 
- After the deposit step (or even when amount is zero — the deposit block is only executed `if inboundAmount.Sign() > 0`), and provided the recipient is a real deployed UEA (`isUEA == true`, so `isSmartContract` stays `false`), execution falls through unconditionally to: [2](#0-1) 
- `ExecutePayloadV2` invokes `CallUEAExecutePayload` with `evmFrom = ueModuleAddr` (the `uexecutor` module account) as the EVM sender against the victim's UEA: [3](#0-2) [4](#0-3) 
- The repository's own README states the UEA contract enforces the signature check only when `evmFrom != UNIVERSAL_EXECUTOR_MODULE`, implying the check is skipped when the module itself is the caller: [5](#0-4) 
- A test already demonstrates exactly this shape of scenario — `Sender` (person B) has no relation to the `Recipient` UEA (person A), the `UniversalPayload.Data` is a live PRC20 `transfer(address,uint256)` calldata targeting the UEA itself, and `VerificationData` is empty — yet the flow is expected to succeed: [6](#0-5)  The assertions in this test only check that the *deposit* landed at the recipient; they do not check whether the embedded `transfer()` payload subsequently executed and moved funds out of the victim UEA — which the code path (`ExecutePayloadV2` call at line 290 of `execute_inbound_funds_and_payload.go`) will attempt to do regardless.
- The same unconditional-fallthrough pattern exists in the `GAS_AND_PAYLOAD` inbound handler: [7](#0-6) 

Nothing in the Go keeper enforces that, for `IsCEA=true`, the `UniversalPayload.To`/`Data` must be benign with respect to the `Recipient` UEA's own asset custody, nor that `VerificationData` be a valid signature by the UEA's actual owner when the caller is the privileged module account. The invariant "every UEA-originated state change is authorized by the UEA owner's signature" — the exact invariant the external report asks to be enforced — is broken specifically for this CEA + module-sender combination.

### Impact Explanation
An unprivileged attacker who controls only an ordinary source-chain account can:
1. Submit a real transaction on a connected external chain (e.g. Ethereum) through the Push Gateway, specifying `Recipient = <any deployed victim UEA>` and a `UniversalPayload` whose `To`/`Data` invoke `transfer()`, `approve()`, or any other function on a PRC20/asset the victim's UEA already holds, sending funds to an attacker-controlled address.
2. Honest Universal Validators truthfully observe and vote on this real event (no malicious validator assumption needed) — quorum is reached because the event genuinely occurred.
3. Push Chain executes the attacker's payload as the victim's own UEA via the module-sender signature bypass, permanently and unauthorizedly draining PRC20 balances the victim previously accumulated in that UEA.

This is a direct "unauthorized UEA execution" / "unauthorized release of user-controlled funds" impact matching the highest-severity items in the allowed-impact gate, reachable purely from an ordinary unprivileged user's default cross-chain transaction submission path.

### Likelihood Explanation
High. No privileged role, validator collusion, or key compromise is required — only the ability to send an ordinary transaction on a connected external chain naming an arbitrary existing UEA as `Recipient`, which the isCEA design explicitly allows and is already exercised by the test suite for benign purposes (routing deposits to a third party's UEA).

### Recommendation
For the CEA (`IsCEA=true`) path, either:
- Never call `ExecutePayloadV2`/`CallUEAExecutePayload` against the `Recipient` UEA using the module-sender bypass unless `VerificationData` is independently validated as the UEA owner's genuine signature over that exact payload (i.e., do not rely on the module-sender bypass for attacker-suppliable `Recipient`/payload combinations), or
- Restrict the CEA payload-execution fallthrough so that it only ever targets non-UEA smart-contract recipients (the existing `executeUniversalTx` recipient-contract path), and require normal signature-gated `MsgExecutePayload` for any payload that targets a UEA's own funds.

### Proof of Concept
1. Attacker deploys/uses an ordinary EOA on a connected external chain (e.g. Sepolia).
2. Victim's UEA (`0xUEA_A`) already holds PRC20 USDC from an earlier legitimate deposit.
3. Attacker sends a Gateway transaction on the source chain with:
   - `Recipient = 0xUEA_A` (victim's UEA, not attacker's own)
   - `TxType = FUNDS_AND_PAYLOAD`, `IsCEA = true`
   - `UniversalPayload.To = 0xUEA_A`, `Data = transfer(attackerAddr, victimBalance)` ABI-encoded
   - `VerificationData = ""` (empty)
4. Honest UVs observe and vote this real event to quorum; `ExecuteInboundFundsAndPayload` runs, resolves `isUEA=true`, deposits (if any amount attached), then falls through to `ExecutePayloadV2(ctx, ueModuleAddr, 0xUEA_A, payload, "")`.
5. Because `evmFrom == UNIVERSAL_EXECUTOR_MODULE`, the UEA's `executeUniversalTx` skips owner-signature verification and executes the `transfer()` call as `0xUEA_A`, moving the victim's PRC20 balance to the attacker's address — mirroring the existing integration test's setup at [8](#0-7)  but with a target payload that drains rather than merely deposits.

// CallUEAExecutePayload executes a universal payload through UEA
func (k Keeper) CallUEAExecutePayload(
	ctx sdk.Context,
	from, ueaAddr common.Address,
	universal_payload *types.UniversalPayload,
	verificationData []byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	abi, err := types.ParseUeaABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UEA ABI")
	}

	abiUniversalPayload, err := types.NewAbiUniversalPayload(universal_payload)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal payload")
	}

	gasLimit := new(big.Int)
	gasLimit, ok := gasLimit.SetString(universal_payload.GasLimit, 10)
	if !ok {
		return nil, fmt.Errorf("invalid gas limit: %s", universal_payload.GasLimit)
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,
		ueaAddr,
		big.NewInt(0),
		gasLimit,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"executeUniversalTx",
		abiUniversalPayload,
		verificationData,
	)
}

**File:** x/uexecutor/README.md (L229-237)
```markdown
#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
```
