### Title
Market order matching rounds down the amount owed to the maker instead of rounding up, systematically underpaying makers - ([File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java])

### Summary
`MarketUtils.multiplyAndDivide` always performs a floor division (`floorDiv`) regardless of which side of an exchange calculation it is used for. In `MarketSellAssetActuator.matchSingleOrder`, this same floor-rounding function is used both to compute how much a taker receives (which should legitimately round down, favoring the resting maker order) and to compute how much the maker receives / the taker must pay (`makerBuyTokenQuantityReceive`), which — following the exact rounding-direction principle described in the ERC4626 report (amounts a party "has to provide/pay" should round up, favoring the protocol/counterparty) — should round up instead. Because it rounds down, the taker systematically underpays the maker by a fraction of a token unit on every partial match.

### Finding Description
`MarketUtils.multiplyAndDivide(a, b, c, disableMath)` computes `floorDiv(a*b, c)` unconditionally: [1](#0-0) 

In `MarketSellAssetActuator.matchSingleOrder`, this function is used to compute `makerBuyTokenQuantityReceive` — the amount of the buy-token that the maker is entitled to receive in exchange for the portion of `sellToken` consumed from the maker's resting order — in both the "taker == maker" and "taker > maker" branches: [2](#0-1) [3](#0-2) 

Conceptually this mirrors the flagged ERC4626 bug: `makerBuyTokenQuantityReceive` is "the amount the taker must provide (pay) to receive a given quantity of the maker's sell token" — per EIP-4626 rounding conventions this must round up to protect the value of the counterparty (here, the maker/order book), just as `previewWithdraw`/`previewMint` must round up in Sense's `AutoRoller.sol`. Instead, `floorDiv` truncates towards zero, meaning the computed payment to the maker is always `<=` the exact ratio, i.e. the taker pays strictly less than the fair-value amount whenever the division is inexact. The resulting shortfall (up to `c-1` units, or a fractional-token’s worth of value) is silently absorbed by the maker rather than returned or reconciled anywhere — there is no compensating "round up the payer's obligation" step, unlike `ExchangeWithdrawActuator`/`ExchangeInjectActuator`, which explicitly verify precision loss with a "Not precise enough" check.

The code comment at lines 466-474 shows awareness of rounding-related edge cases only for the "receive == 0" scenario (returning the sell-token remainder to the maker), but does not address the more general, always-present downward bias in nonzero cases.

### Impact Explanation
This affects the on-chain Market (Exchange V2 order-matching) actuator, reachable by any unprivileged account via a `MarketSellAssetContract` transaction. Every partial or full order match executed by `matchSingleOrder` computes `makerBuyTokenQuantityReceive` via floor division, so makers systematically receive marginally less value than they are contractually owed by the resting order's price ratio. An adversarial taker can structure sell orders (quantities chosen to maximize the floor-division remainder, and/or split into many small matches, bounded by `MAX_MATCH_NUM = 20` per transaction but repeatable across many transactions) to repeatedly skim the maximum possible rounding remainder from many maker orders at negligible additional cost (only the fixed `MarketSellFee`). This is a genuine value-leakage/accounting-integrity bug in the exchange settlement logic, not merely theoretical, because it is triggered on the default/common code path of every market trade, not a privileged or mocked-only branch.

### Likelihood Explanation
High likelihood of occurrence in normal operation — floor-division rounding loss occurs whenever `makerSellRemainQuantity * makerBuyQuantity` is not exactly divisible by `makerSellQuantity`, which is the common case for arbitrary user-chosen order quantities/prices. No special privileges are needed; any user can create sell/buy orders and trigger matches through `MarketSellAssetActuator`.

### Recommendation
Round up (`ceilDiv`) when computing amounts that represent what a counterparty must be paid/provided (e.g., `makerBuyTokenQuantityReceive`), while continuing to round down for amounts representing what a party receives at the protocol's/counterparty's discretion (e.g., `takerBuyTokenQuantityReceive`). Concretely, introduce a rounding-up variant of `MarketUtils.multiplyAndDivide` (e.g., `ceilDiv(a*b, c)`) and use it specifically for the maker-payment computations in `MarketSellAssetActuator.matchSingleOrder`, mirroring the ERC4626 fix pattern of using `mulDivUp` for "amount owed" calculations while keeping `mulDivDown`/`floorDiv` for "amount received" calculations.

### Proof of Concept
1. Maker places a sell order: sell 3 units of token A for 10 units of token B (`makerSellQuantity=3`, `makerBuyQuantity=10`).
2. Taker places a sell order consuming `makerSellRemainQuantity = 1` unit of A from the maker's order (partial match), triggering `matchSingleOrder`.
3. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 10, 3) = floorDiv(10, 3) = 3` (exact value is `3.33`), so the maker receives `3` instead of the fair-value `3.33..`, rounding in the taker's favor. Repeating this pattern (multiple small partial fills with `disableJavaLangMath` either on or off) across many orders accumulates a measurable, non-reconciled value transfer from makers to takers, with no corresponding "precision" validation as exists in `ExchangeWithdrawActuator.doValidate` (`Not precise enough` check) for the AMM-style exchange contracts.
