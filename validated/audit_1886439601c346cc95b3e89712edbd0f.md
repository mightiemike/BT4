### Title
Wallet Contract's `has_in_flight_tx` lock can be permanently stuck due to undersized fixed callback gas, permanently freezing the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The external report describes an untrusted, attacker-influenced hook (ERC777 `tokensToSend`) that executes synchronously inside a core state-changing function (`burn`), letting the untrusted party revert the whole call and thereby corrupt/DoS an in-progress operation for others. The closest reachable analog in nearcore is the NEAR Wallet Contract's `rlp_execute` flow, where an attacker-chosen `target` contract's cross-contract call result is processed by a fixed-gas `#[private]` callback that is responsible for resetting the contract's single "transaction in flight" lock (`has_in_flight_tx`). If that callback fails/aborts (e.g., because the untrusted target returned an oversized value that the callback cannot afford to process with its statically-reserved gas), the whole receipt — including the `has_in_flight_tx = false` state write — is rolled back, exactly as an unhandled revert rolls back all of a Solidity call's effects.

### Finding Description
`WalletContract::rlp_execute` enforces a single-in-flight-transaction invariant using the persisted boolean field `has_in_flight_tx`: [1](#0-0) 

`rlp_execute` sets `has_in_flight_tx = true` before returning a `Promise`, and refuses any further `rlp_execute` call while the flag is `true`: [2](#0-1) 

The flag is only ever reset back to `false` inside the `#[private]` callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), and in each case the reset is the *first* statement of the function: [3](#0-2) 

For the general/default action path (arbitrary `FunctionCall`/`Transfer`/`AddKey`/`DeleteKey` to an attacker-controlled `target`), the callback is scheduled with a fixed, non-scalable gas budget `RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, unlike the address-check path which adds `action.gas()` to its callback budget: [4](#0-3) [5](#0-4) 

Because NEAR rolls back *all* state changes made by a receipt/function-call execution if that execution later fails (e.g., out of gas) — the same "all-or-nothing" semantics that make the Solidity ERC777-hook revert dangerous — a `PromiseResult::Successful` value that is expensive to receive/process (copying/serializing a large returned value inside `rlp_execute_callback`, or JSON-deserializing a large value inside `address_check_callback`/`nep_141_storage_balance_callback`) can cause the callback to run out of its small, fixed gas allotment before it finishes. If that happens, the entire callback execution — including the earlier `self.has_in_flight_tx = false;` line — is discarded, and the flag remains permanently `true` in the persisted contract state.

Since `target` (and by extension the contract that ultimately produces the promise result consumed by the callback) is fully attacker/user-controlled input to `rlp_execute`, any unprivileged signer/relayer can trigger this by pointing `target` at a contract (which they may deploy themselves, or that already exists) that returns a large-but-within-protocol-limits value for the called method, combined with a `gas` value in the signed Ethereum-emulated transaction large enough to let that target execute successfully but leaving the fixed 5 Tgas callback budget unable to absorb the resulting promise-result processing.

Once `has_in_flight_tx` is stuck at `true`, every future call to `rlp_execute` on that wallet is unconditionally rejected at the very first check, regardless of caller, permanently disabling the wallet/account (denial of any further $NEAR/NEP-141/ETH-emulated transfers or actions from it).

### Impact Explanation
This satisfies the "permanently frozen funds" acceptance criterion: the wallet-contract account becomes permanently unable to execute any further transactions once the lock is stuck, freezing any $NEAR balance and any fungible tokens under its control, with no self-recovery path visible in the contract (there is no method to reset `has_in_flight_tx` other than through the callback that is itself broken by this condition). This is reachable purely from an unprivileged transaction signer or meta-transaction relayer submitting a normal `rlp_execute` call with attacker-chosen `target`/gas — fitting the allowed "transaction/RPC caller" and "NEAR wallet contract" scope.

### Likelihood Explanation
Reaching the vulnerable state requires the attacker (who fully controls `target` and the emulated transaction's `gas` field) to get a promise result whose processing cost in the callback exceeds `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas), while the target's own execution and gas usage stay within what is available. This is plausible because: (1) `target` can be any account, including one the same user/attacker deploys; (2) the callback processes the raw returned bytes (JSON round-trip or holding them for the final `ExecuteResponse`), so cost scales with the amount of data returned, and NEAR's max returned-data size (a multi-megabyte limit at the protocol layer per `max_length_returned_data`) is large relative to a 5 Tgas static budget. Exact numeric confirmation of the precise byte threshold at which 5 Tgas is insufficient could not be fully verified in this pass because the specific per-byte gas cost constants (e.g., `data_receipt_creation_base`, register/read costs) referenced in `parameters.yaml` were not retrieved before the tool budget was exhausted — this remains an assumption that should be validated against the exact runtime fee table before treating this as fully confirmed, but the structural bug (unscaled fixed-gas callback responsible for resetting a persistent lock, combined with rollback-on-failure semantics and attacker-controlled promise-result size) is clearly present in the code.

### Recommendation
- Scale the gas passed to `rlp_execute_callback` (and the other lock-resetting callbacks) with the size/complexity of data the callback may need to process, similar to how `address_check_callback`'s gas already accounts for `action.gas()`.
- Alternatively/additionally, do not couple the lock-reset to logic that can fail due to attacker-influenced data size: reset `has_in_flight_tx` in a way that is guaranteed to succeed regardless of the size of the promise result (e.g., perform the reset in a minimal, constant-cost operation before any data-dependent processing, or add a recovery/timeout mechanism that allows the lock to be cleared if a callback provably failed).
- Bound/validate the size of promise-result data actually copied or JSON-processed by the callback methods before committing to expensive operations, so gas exhaustion cannot occur unexpectedly in a way that reverts the lock-reset write.

### Proof of Concept
1. Attacker (any unprivileged account) deploys or identifies a contract `Malicious` with a method `big_return` that, when called with a modest amount of attached gas, returns a value close to the protocol's `max_length_returned_data` limit.
2. Attacker crafts and signs an RLP/EIP-2930-style Ethereum transaction (per `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs` test patterns) whose emulated action is a `FunctionCall` action to `Malicious::big_return`, with `to = target` set to `Malicious`'s eth-implicit address and enough `gas` for the call to succeed and return the large value.
3. Attacker (or any relayer) submits this transaction via `rlp_execute(target=Malicious, tx_bytes_b64=...)` on the victim/attacker's own `WalletContract`.
4. `inner_rlp_execute` falls into the generic branch, scheduling `action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))` with `ext` gas fixed at `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas): [6](#0-5) 
5. `Malicious::big_return` succeeds and returns its large payload as the promise result.
6. `rlp_execute_callback` is invoked with only 5 Tgas; processing/returning the large `PromiseResult::Successful(value)` exceeds the available gas, and the callback execution fails/aborts, rolling back its state changes — including the `self.has_in_flight_tx = false;` assignment that was the first line executed: [7](#0-6) 
7. `has_in_flight_tx` remains `true` in the persisted contract state.
8. Any subsequent call to `rlp_execute` on this wallet, from any signer, is now rejected: [8](#0-7) 
9. The wallet is permanently unable to process further Ethereum-emulated transactions, freezing all funds/tokens it controls.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
