### Title
Deterministic account identity commits to a mutable `GlobalContractIdentifier::AccountId` reference, letting the referenced owner rewrite code for every derived account after creation - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
Deterministic accounts (NEP-616) derive their account id from `DeterministicAccountStateInit`, which is advertised as making the account's code and initial state "fully defined" and fixed forever. However, when the embedded `code` field is a `GlobalContractIdentifier::AccountId` (as opposed to `CodeHash`), the id only commits to a reference (an `AccountId`) whose pointed-to code is mutable by design. This mirrors the reported Factory bug pattern: a value used as the immutable "identity/implementation" anchor for deterministic derivation is itself changeable, so consumers relying on the derived identity get silently different code over time.

### Finding Description
`derive_near_deterministic_account_id` hashes the borsh-encoded `DeterministicAccountStateInit`, which contains `code: GlobalContractIdentifier` [1](#0-0)  and [2](#0-1) . This identifier can be either `CodeHash` (immutable, content-addressed) or `AccountId` (owner-addressed, and explicitly documented as mutable: "This allows the owner to update the contract for all its users") [3](#0-2) .

When a deterministic account is created, `deploy_deterministic_account` calls `use_global_contract`, which stores the account's contract pointer as `AccountContract::GlobalByAccount(id)` rather than pinning a code hash [4](#0-3) [5](#0-4) .

At execution time, the actual code hash is *not* fixed at creation - it is re-resolved live from the trie every time via `RuntimeContractIdentifier::resolve`, which calls `GlobalContractIdentifier::hash()` and looks up the current value under `TrieKey::GlobalContractCode { identifier }` [6](#0-5) [7](#0-6) .

The owner behind that `AccountId` can redeploy at any later time: `DeployGlobalContractAction` with `deploy_mode: AccountId` derives the same `GlobalContractIdentifier::AccountId(account_id)` and simply overwrites the trie value at the same key, bumping only an internal freshness nonce [8](#0-7) [9](#0-8) .

The result: the deterministic account's id is a hash that commits to *who* controls the code, not to the code itself. Once created, the account's on-chain behavior can be arbitrarily replaced by a third party (the global-contract owner), even though the whole premise of NEP-616 deterministic accounts - as stated in the docs - is that "Deterministic accounts have a fixed code and fixed initial state" [10](#0-9) . This is the exact analog of the Factory bug: `troveManagerImpl`/`GlobalContractIdentifier::AccountId` is mutable, yet it is the value baked into a deterministic derivation (`predictDeterministicAddress` / `derive_near_deterministic_account_id`) that downstream logic and users treat as an immutable anchor.

### Impact Explanation
Any protocol, wallet, or counterfactual-address scheme that relies on a NEP-616 deterministic account id as a guarantee of fixed, audited code (e.g., pre-computing a deterministic escrow/vault address and directing deposits to it before the account exists) is exposed to a rug-pull: the global-contract owner can redeploy malicious code under the same `AccountId` identifier at any time, changing the executable code of every deterministic account that referenced that identifier - all without changing the account id anyone already trusted or transacted with. This can lead directly to unauthorized value movement/drained deposits held by such accounts, since callers and depositors have no on-chain assurance that "deterministic" implies "immutable" when the `AccountId` mode is used.

### Likelihood Explanation
Reachable by an ordinary, unprivileged transaction sender/contract deployer with no special network or validator privileges: (1) deploy a global contract in `AccountId` mode, (2) advertise/derive a deterministic account id from a `DeterministicAccountStateInit` referencing that `AccountId`, (3) get users/protocols to trust and fund the resulting deterministic account, (4) redeploy different code under the same `AccountId` mode global contract via a normal `DeployGlobalContractAction`. All steps use standard, already-exposed actions (`DeployGlobalContractAction`, `DeterministicStateInitAction`) with no consensus or node-compromise required.

### Recommendation
Do not treat `GlobalContractIdentifier::AccountId` as compatible with the "fixed code" guarantee of deterministic accounts. Either:
- Disallow `GlobalContractIdentifier::AccountId` inside `DeterministicAccountStateInit` and require `CodeHash` only (mirrors the Factory fix of deriving/verifying using the immutable, content-addressed value rather than the mutable reference), or
- Pin the *resolved* code hash into `AccountContract` at the time `deploy_deterministic_account`/`use_global_contract` executes (freeze to `AccountContract::Global(code_hash)` instead of `GlobalByAccount(id)`), so later redeployment under the same `AccountId` cannot retroactively change already-created accounts' executable code.

### Proof of Concept
Not independently executed (index-only analysis); the flow is derivable directly from source:
1. Attacker deploys global contract `codeA` with `GlobalContractDeployMode::AccountId` from `attacker.near` → identifier `GlobalContractIdentifier::AccountId(attacker.near)` [11](#0-10) .
2. Attacker (or victim, believing it's safe/audited) computes `DeterministicAccountStateInit{ code: AccountId(attacker.near), data }` and its derived id `det_account` via `derive_near_deterministic_account_id` [12](#0-11) .
3. Victim protocol funds/deploys `det_account` via `DeterministicStateInitAction`, which sets `AccountContract::GlobalByAccount(attacker.near)` [4](#0-3) .
4. Attacker submits a second `DeployGlobalContractAction{code: codeB (malicious), deploy_mode: AccountId}` from `attacker.near`, overwriting the trie entry for the same identifier [13](#0-12) .
5. Any subsequent call into `det_account` resolves and executes `codeB` (malicious), since resolution is live via `RuntimeContractIdentifier::resolve` [6](#0-5) , despite `det_account`'s id never changing and users continuing to trust it as "deterministic."

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }
