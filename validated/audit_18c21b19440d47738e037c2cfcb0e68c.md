This confirms the analog root cause and its concrete consequence: `validate_delete_action` in `runtime/runtime/src/action_validation.rs` only checks that `beneficiary_id` is a syntactically valid `AccountId`, with no check that it is not the account itself, that it exists, or that it isn't a non-implicit/never-creatable account. If a user submits a `DeleteAccountAction` naming a `beneficiary_id` that is (a) itself (the account being deleted, which is removed before the refund is processed), or (b) any non-existent named/implicit account, the resulting `Receipt::new_balance_refund` is a system/refund receipt whose `Action::Transfer` can **never** create an account (`implicit_creation_allowed` returns `false` for any `is_refund: true` receipt, confirmed by the `refund_may_not_create_universal_account` test), so it fails with `AccountDoesNotExist`, and per `docs/RuntimeSpec/Refunds.md`: "If the execution of a refund fails, the refund amount is burnt." This permanently destroys the deleted account's entire remaining balance.

### Title
Missing validation of `beneficiary_id` in `DeleteAccountAction` permanently burns account balance on delete - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
`validate_delete_action` only checks that `beneficiary_id` is a syntactically valid account id via `validate_action_account_id`, but never verifies that the beneficiary account exists or differs meaningfully from an unreachable target. Because the beneficiary payout is implemented as a `system`-predecessor refund receipt, which by design can never create a new account, any `DeleteAccountAction` naming a nonexistent/implicit `beneficiary_id` causes the entire remaining account balance to be irrecoverably burnt instead of delivered.

### Finding Description
`validate_delete_action` [1](#0-0)  performs only a format check on `beneficiary_id`. `action_delete_account` then unconditionally builds a refund receipt to that id and removes the source account in the same action: [2](#0-1) .

That refund receipt is a system/`is_refund` receipt. `check_account_existence`'s `Transfer` branch only creates a missing account if `implicit_creation_allowed` returns true [3](#0-2) , and `implicit_creation_allowed` unconditionally returns `false` whenever `is_refund` is set, for every account type [4](#0-3) , confirmed by the dedicated regression test `refund_may_not_create_universal_account` [5](#0-4) .

Consequently, if `beneficiary_id` does not already exist as an account (e.g., a typo'd/never-funded named or implicit account id, or the account being deleted itself, which is removed from state before its own refund receipt executes), the refund receipt fails with `AccountDoesNotExist`. Per the documented refund semantics, "If the execution of a refund fails, the refund amount is burnt" [6](#0-5) , and this is implemented at the runtime `apply` level: on a system-predecessor receipt whose result is an error, the full deposit amount is added to `other_burnt_amount` [7](#0-6) .

### Impact Explanation
An unprivileged account owner (or a relayer executing a meta-transaction/`DelegateAction` carrying a `DeleteAccount` action on the owner's behalf) can, through a single mistaken or malicious transaction, cause the entire remaining NEAR balance of the deleted account to be permanently burnt rather than transferred to any recoverable party. This is a direct, transaction-triggered, unrecoverable loss of funds — no honest-node divergence is required, and no privileged role is involved; it is reachable purely by a normal `DeleteAccount` action's `beneficiary_id` field being unchecked for reachability/self-reference.

### Likelihood Explanation
High likelihood of accidental triggering (any client, wallet, or relayer bug that supplies a wrong/self `beneficiary_id`) and it is trivially reachable by any signer, since `DeleteAccountAction` requires no special permission beyond a full-access key on the account being deleted, and delegate/meta-transactions allow a relayer to submit it on the user's behalf as well.

### Recommendation
In `validate_delete_action` (or in `action_delete_account` before generating the refund receipt), reject the action if `beneficiary_id == account_id` (self-beneficiary), and/or verify the beneficiary account exists (or is capable of being created by this refund) before allowing the delete, similar to how `check_account_existence` already gates `Transfer` receipts. Alternatively, change `action_delete_account` to fail the whole `DeleteAccount` action up front (before removing the account) if the beneficiary cannot receive funds, rather than silently burning the payout after the account has already been deleted.

### Proof of Concept
1. Alice controls account `alice.near` with balance `B > 0` and a full-access key.
2. Alice submits `SignedTransaction` with a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "alice.near" })` (self) or `beneficiary_id: "never-existed.near"` (an account that has never been created).
3. `validate_delete_action` accepts the action (format is valid) [1](#0-0) .
4. `action_delete_account` runs: `remove_account` deletes `alice.near` from state, and a `Receipt::new_balance_refund(beneficiary_id, B)` is queued [8](#0-7) .
5. The refund receipt (predecessor `system`) executes a `Transfer` to `beneficiary_id`, which does not exist; `check_account_existence` rejects it via `AccountDoesNotExist` because `implicit_creation_allowed` is `false` for refunds [9](#0-8) .
6. Because the refund failed, its deposit `B` is added to `other_burnt_amount` instead of being credited to any account [7](#0-6) .
7. Result: Alice's balance `B` is permanently destroyed with no recovery path.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
