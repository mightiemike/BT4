### Title
Paused `accrue` silently pass-throughs stale indexes, letting deposits made during the pause capture pre-pause depositors' deferred yield - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The external report's root cause is a *state that should have been re-validated against a changing external context but instead is accepted at face value*. The closest single-transaction analog in this Clarity codebase is the vault `accrue` function's pause behavior: instead of reverting when accrual is paused, it silently returns the stale `index`/`lindex` as if a normal accrual had happened, letting dependent share-pricing logic (`deposit`) operate on unrecognized, deferred interest.

### Finding Description
Every vault contract (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, and their `local-testing` counterparts) implements `accrue` as: [1](#0-0) 

When `pause-states.accrue` is `true`, the function does **not** revert — it returns `(ok { index: idx, lindex: lidx })` using the currently stored (stale) values, without calling `next-index()`/`next-liquidity-index()` and without advancing `last-update`. This is the "pause that passes through instead of reverting" pattern.

`deposit` (and `redeem`) call `accrue` first and then price shares using `convert-to-assets-preview`/`total-assets-preview`, which read the vault's `index`/`lindex` state: [2](#0-1) 

Because `accrue` never advances `last-update` while paused, once the pause is lifted the very next `accrue` call computes `next-index()` as a function of the *entire* elapsed time since the last real update — recognizing all of the deferred interest for the whole paused window in a single jump, distributed pro-rata across whatever shares exist at that moment (see `treasury-lp` calculation using `total-supply`): [3](#0-2) 

Sequence:
1. Vault is operating normally; `index`/`lindex` reflect interest that lenders are owed up to `last-update`.
2. `accrue` is paused (`pause-states.accrue = true`).
3. Real economic interest continues to accrue with the passage of blocks, but on-chain `index`/`lindex` are frozen because `accrue` returns the stale pair instead of reverting or reflecting the skipped period.
4. A user calls `deposit` during the pause window. `deposit`'s share-minting math (`convert-to-assets-preview`) uses the stale, understated `lindex`, so the new depositor receives shares priced as if no interest had accrued during the paused window.
5. `accrue` is unpaused. The next call to `accrue` computes the full deferred interest for the paused period in one step and mints `treasury-lp`/increases `index` based on `total-supply` at that time — which now includes the shares minted in step 4.
6. The depositor from step 4 shares in interest that economically accrued *before* they deposited, diluting the yield that should have gone entirely to pre-pause and pause-period depositors.

### Impact Explanation
This results in misallocation of unclaimed yield among lenders: value that should accrue exclusively to depositors who held shares throughout the paused window is instead diverted to new depositors who entered during the pause at a stale (discounted) share price. This falls under "theft of unclaimed yield" — a High-severity impact class per the rules, since it is a redistribution of yield away from its rightful holders without any legitimate economic basis, executable by any user simply timing a deposit around an admin-triggered `accrue` pause.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the `accrue` pause flag to be set (an operational/maintenance action) and a user to deposit during that specific window, then wait for the unpause-triggered catch-up accrual. There is no requirement for privileged access by the attacker — only an ordinary deposit — but it does depend on an admin-controlled pause event happening, which is a normal, expected operational lever rather than attacker-controlled state.

### Recommendation
When `accrue` is paused, either:
- Revert deposit/redeem/borrow/repay entry points instead of allowing them to proceed with stale indexes, or
- Snapshot and freeze `total-supply`/share issuance during the pause so that interest recognized on unpause is not diluted by shares minted while accrual was suspended, or
- Advance `last-update` to the pause point and compute a "held" delta so that catch-up interest is fairly apportioned only to shares that existed during the accrual gap.

### Proof of Concept
1. Vault has 1,000,000 zft outstanding, `index = 1.0`, `lindex = 1.0`, `last-update = T0`.
2. DAO pauses `accrue` for the vault at `T0`.
3. At `T0 + 30 days`, Attacker calls `deposit(1,000,000 units)`; `accrue()` pass-throughs `{index: 1.0, lindex: 1.0}` (no revert), so Attacker's shares are minted at the pre-pause (undiscounted) price, ignoring the 30 days of real economic interest that should have compounded.
4. DAO unpauses `accrue`.
5. Any subsequent call to `accrue()` computes `next-index()` over the full 30-day gap since `last-update` (T0), recognizing the deferred interest across the current `total-supply`, which now includes Attacker's freshly minted shares.
6. Attacker's shares participate in interest that accrued before their deposit, extracting yield that should have belonged solely to depositors who held shares during that 30-day window — confirmed by the `accrue` pass-through logic at [4](#0-3)  and the delta computation on unpause at [5](#0-4) .
