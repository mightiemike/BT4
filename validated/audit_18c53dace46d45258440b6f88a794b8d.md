### Title
Zero-Pubkey collision with blank on-disk bucket-map entries lets `occupy_if_matches` misroute a real account's index write to an unrelated slot, causing a stale entry to remain reachable — ([File: bucket_map/src/index_entry.rs])

### Summary
`IndexEntryPlaceInBucket::occupy_if_matches`, used by `Bucket::batch_insert_non_duplicates_reusing_file` when the on-disk AccountsIndex bucket file is reused across a validator restart (`reused_file_at_startup = true`), compares the raw `key` bytes stored at a candidate slot to the pubkey being inserted **without first checking whether that slot was ever legitimately occupied**. Because freshly-created/never-written mmap regions are zero-initialized, a never-used slot's `key` field is `Pubkey::default()` (all-zero bytes) — which is coincidentally the well-known `SystemProgram` account address. This mirrors the `address(0)`-as-sentinel bug class from the external report: an all-zero value that is meant to signal "nothing here" gets treated as a legitimate match for a real identity.

### Finding Description
Normal index lookups (`bucket_find_index_entry`, `find_index_entry_mut`) always check `index.is_free(ii)` **before** comparing keys, so free/never-initialized slots are correctly skipped regardless of what stale or zero bytes happen to sit in their `key` field: [1](#0-0) 

However, `occupy_if_matches`, invoked only in the disk-file-reuse fast path used during startup index generation, reads the entry's `key` and compares it to the target pubkey *first*, and only afterward inspects the occupied/enum tag: [2](#0-1) 

The test suite explicitly documents that this raw-byte comparison is unsafe for the all-zero pubkey, because a blank, untouched region of the mmap file is indistinguishable from a legitimately freed/reusable slot for that same pubkey: [3](#0-2) [4](#0-3) 

`batch_insert_non_duplicates_reusing_file` walks the hash-probe window and, at the *first* slot where `occupy_if_matches` reports `SuccessfulInit`, commits the new value there and stops (`continue 'outer`) without ever visiting the remaining slots in the window: [5](#0-4) 

This path is reached specifically because the disk bucket file is reused from a prior run rather than recreated: [6](#0-5) 

If, within a given probe window, a never-initialized slot (key bytes = all zero, enum tag = `Free` by construction) is encountered *before* the slot that genuinely, previously held the System Program's (or any other zero-keyed) account entry, `occupy_if_matches` at the blank slot matches by coincidence and claims it, writing the new value there and returning `SuccessfulInit`. The loop then moves to the next input pubkey, never visiting or freeing the pre-existing genuinely occupied slot for the same key further along in the probe window. The result: two entries in the on-disk bucket file both key on `Pubkey::default()` — one stale (never invalidated), one fresh — and because subsequent ordinary lookups (`bucket_find_index_entry`) return the **first** non-free match found while walking the same probe order starting at the same hash bucket, whichever of the two entries sits earlier in probe order is authoritative. If that happens to be the stale one, index reads for that pubkey silently resolve to the old slot/offset instead of the new one.

### Impact Explanation
This is a stale/wrong-version account load bug reachable through ordinary node restart and disk-index regeneration (accounts index rebuild), not through any privileged or attacker-controlled action. `Pubkey::default()` corresponds to the `SystemProgram` ID, an account that is present and repeatedly referenced/updated across virtually every slot on the network, making the all-zero key collision condition realistic rather than purely theoretical. If the stale duplicate ends up being the one returned by subsequent lookups, an honest validator could serve outdated data for the affected account after a restart, producing a snapshot-vs-replay/index divergence or an incorrect balance/state read for that account — exactly the failure mode called out as acceptable evidence ("concrete stale ... account loads").

### Likelihood Explanation
The bug requires: (1) the accounts-index bucket map to run with disk-index enabled (a supported, commonly used configuration for large validators), (2) a validator restart that triggers `Bucket::new` to reuse an existing on-disk bucket file (`reused_file_at_startup = true`), and (3) an insertion probe window during `generate_index`/`write_startup_info` where a genuinely blank (zero-keyed) slot precedes the real occupied slot for `Pubkey::default()` in the hash-probe sequence. This is a normal, unprivileged restart code path exercised on every validator boot with disk index enabled; whether the exact slot ordering triggers the divergence in a given run is probabilistic (depends on hashing/probe placement), which is why the codebase's own tests explicitly special-case and avoid the zero pubkey to prevent tripping over this exact behavior.

### Recommendation
In `occupy_if_matches` (and any other disk-reuse code path that inspects raw `key` bytes before checking occupancy), require the entry to be non-free (or otherwise validated as genuinely previously written) before treating a byte-level key match as authoritative, or clear/poison the `key` field to a value that cannot collide with a valid `Pubkey` when a slot is freed or newly allocated. Additionally, `batch_insert_non_duplicates_reusing_file` should continue scanning the remainder of the probe window (rather than stopping at the first match) to detect and reconcile any genuinely-occupied duplicate entry for the same pubkey elsewhere in the window, ensuring only one authoritative entry survives per key after index-file reuse.

### Proof of Concept
1. Start a validator with the disk-backed AccountsIndex enabled and let it run long enough that the `SystemProgram` account (`Pubkey::default()`, all-zero bytes) has a valid slot-list entry written into an on-disk bucket file at probe position `P` within its hash window.
2. Shut the validator down cleanly so the bucket file and its `Restart` metadata are preserved (`bucket_map/src/restart.rs` restart-file mechanism, confirmed at [7](#0-6) ).
3. On restart, `Bucket::new` reuses the file (`reused_file_at_startup = true`); `generate_index`/`write_startup_info` calls `batch_insert_non_duplicates` → `batch_insert_non_duplicates_internal(..., try_to_reuse_disk_data = true)` → `batch_insert_non_duplicates_reusing_file`, which is confirmed at [8](#0-7) .
4. If any untouched/never-written slot at probe position `P' < P` in the same window has key bytes of all-zero (which, per the code's own test comments, is the default state of any blank region), `occupy_if_matches` at `P'` returns `SuccessfulInit` for the `SystemProgram` pubkey and the loop moves on, leaving the true prior entry at `P` (with old slot/offset data) still marked occupied and unreferenced/uncleaned.
5. Subsequent reads via `bucket_find_index_entry` walk the same probe order starting at the bucket's hash index; if `P < P'` in probe order (i.e., the stale entry is encountered first), the read returns the pre-restart, stale slot/offset instead of the newly written one — an observable stale account read.

Note: I could not fully trace, within the remaining tool budget, whether a later full-bucket-map validation/rehash pass elsewhere in `accounts_db.rs::generate_index` (e.g., `populate_and_retrieve_duplicate_keys_from_startup`) definitively re-scans and reconciles duplicate zero-keyed entries across the *entire* bucket (not just the probe window) before the index is considered final; this would need explicit verification in a full source checkout to confirm whether existing downstream duplicate-detection logic already mitigates the described divergence.

    pub fn batch_insert_non_duplicates_reusing_file(
        index: &mut BucketStorage<IndexBucket<T>>,
        data_buckets: &[BucketStorage<DataBucket>],
        items: &[(Pubkey, T)],
        reverse_sorted_entries: &mut Vec<(u64, usize)>,
        duplicates: &mut Vec<(usize, T)>,
    ) {
        let max_search = index.max_search();
        let cap = index.capacity();
        let search_end = max_search.min(cap);
        let mut not_found = Vec::default();
        // pop one entry at a time to insert
        'outer: while let Some((ix_entry_raw, ix)) = reverse_sorted_entries.pop() {
            let (k, v) = &items[ix];
            // search for an empty spot starting at `ix_entry`
            for search in 0..search_end {
                let ix_index = (ix_entry_raw + search) % cap;
                let elem = IndexEntryPlaceInBucket::new(ix_index);
                match elem.occupy_if_matches(index, v, k) {
                    OccupyIfMatches::SuccessfulInit => {}
                    OccupyIfMatches::FoundDuplicate => {
                        // pubkey is same, and it is occupied, so we found a duplicate
                        let (v_existing, _ref_count_existing) =
                            elem.read_value(index, data_buckets);
                        // someone is already allocated with this pubkey, so we found a duplicate
                        duplicates.push((ix, *v_existing.first().unwrap()));
                    }
                    OccupyIfMatches::PubkeyMismatch => {
                        // fall through and look at next search value
                        continue;
                    }
                }
                continue 'outer; // this 'insertion' is completed - either because we found a duplicate or we occupied an entry in the file
            }
            // this pubkey did not exist in the file already and we exhausted the search space, so have to try the old way
            not_found.push((ix_entry_raw, ix));
        }
        // now add all entries that were not found
        // they were pushed in order since we popped off input
        // So, to keep them 'reversed', we need to reverse them here.
        // This isn't required for correctness, but fits the optimal iteration order.
        *reverse_sorted_entries = not_found.into_iter().rev().collect();
    }

    /// If the entry matches the pubkey and is unoccupied, then store `data` here and occupy the entry.
    pub(crate) fn occupy_if_matches(
        &self,
        index_bucket: &mut BucketStorage<IndexBucket<T>>,
        data: &T,
        k: &Pubkey,
    ) -> OccupyIfMatches {
        let index_entry = index_bucket.get::<IndexEntry<T>>(self.ix);
        if &index_entry.key == k {
            let enum_tag = index_bucket.contents.get_enum_tag(self.ix);
            if unsafe { &index_entry.contents.single_element } == data {
                assert_eq!(
                    enum_tag,
                    OccupiedEnumTag::Free,
                    "index asked to insert the same data twice"
                );
                index_bucket
                    .contents
                    .set_enum_tag(self.ix, OccupiedEnumTag::OneSlotInIndex);
                OccupyIfMatches::SuccessfulInit
            } else if enum_tag == OccupiedEnumTag::Free {
                // pubkey is same, but value is different, so update value
                self.set_slot_count_enum_value(index_bucket, OccupiedEnum::OneSlotInIndex(data));
                OccupyIfMatches::SuccessfulInit
            } else {
                // found occupied duplicate of this pubkey
                OccupyIfMatches::FoundDuplicate
            }
        } else {
            OccupyIfMatches::PubkeyMismatch
        }
    }
