### Title
Signer-local, independently configurable timeout windows (`block_proposal_timeout`, `tenure_idle_timeout`, etc.) let honest signers disagree on miner-inactivity/tenure-extend verdicts - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
The Sherlock finding argues that Buffer's forex option "creation window" is defined by an arbitrary, owner-configurable start/end time instead of a value derived consistently from chain/market state, so different observers can disagree about whether an option request falls "in window." The analogous pattern in this repo is `ProposalEvalConfig`, which is built per-signer from each operator's local `SignerConfig` (`block_proposal_timeout`, `tenure_idle_timeout`, `tenure_last_block_proposal_timeout`, `reorg_attempts_activity_timeout`, etc.) rather than from a value derived from consensus state. These durations gate whether a signer considers the current/previous miner "timed out" and therefore whether a competing tenure-extend or new-tenure block is a valid choice.

### Finding Description
`ProposalEvalConfig` is constructed straight from each signer's own `SignerConfig` values: [1](#0-0) 

These are wall-clock-relative, locally-configured windows (not agreed-upon consensus parameters), and the sample config file itself documents that they must be manually kept consistent with the miner's independently configured `tenure_extend_wait_timeout_ms`, warning that a mismatch changes the outcome: [2](#0-1) 

The same file explicitly states the conditional-verdict consequence: "If miner's value < this value: Miner extends BEFORE signer invalidates the new winner -> REJECTED. If miner's value >= this value: Signer invalidates new winner first, then accepts extend -> OK." This is the direct analog to "the creation window ... is configured by owner setting" rather than derived from a fixed, chain-consistent rule.

These timeouts feed into tenure-extend admissibility checks such as `validate_tenure_change_payload`/`check_parent_tenure_choice`, which decide whether a reorg of an unresponsive miner's tenure is a "valid choice": [3](#0-2) 

and the full/read-count tenure-extend admission logic that directly compares `get_epoch_time_secs()` (each signer's own wall clock) against a timeout computed from `self.config.tenure_idle_timeout` (each signer's own locally configured duration): [4](#0-3) 

Because `block_proposal_timeout`, `tenure_idle_timeout`, `tenure_idle_timeout_buffer`, and `reorg_attempts_activity_timeout` are all locally operator-configured (and only informally recommended, via comments, to be kept consistent with the miner's own independently-configured values), two honest, non-Byzantine signers can legitimately compute different `enough_time_passed` / miner-invalidation verdicts for the exact same block proposal at the exact same real-world moment, simply because their configs (and to a lesser extent, clock skew) differ. This breaks the equality that "all honest signers, given the same block proposal and the same chain state, produce the same validation verdict."

### Impact Explanation
This does not require a majority of malicious actors — it only requires that some signers are configured with different timeout values than others (a normal, permitted operational state; nothing in the protocol enforces uniform values across the signer set). The result is a bounded verdict split: some signers accept a tenure-extend/BlockFound as valid while others reject it as `InvalidTenureExtend`/`ReorgNotAllowed`, at least until enough real time passes for the slower configs to catch up. This matches the "High" bucket in the rubric: a minority-triggerable static-validation divergence producing temporary tip disagreement (delayed threshold convergence, stalled tenure changes, or a signer signing a tenure-extend that a subset of the signer set would reject), without requiring an admin/attacker key beyond normal, permitted per-node configuration differences. It is not Critical because the 70% weight threshold and re-validation before signing (`stacks-signer/src/v0/signer.rs` `store_and_process_block_signature`/`handle_block_pre_commit`) bound the damage to a temporary stall/disagreement rather than a silent, permanent chain split.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: these values are user-editable config fields (see `sample/conf/signer/mainnet-signer-conf.toml`) with only comment-level guidance to keep them consistent with the corresponding miner config; there is no on-chain or protocol-level enforcement of a single canonical value. Operators running heterogeneous, independently-tuned signer configs (which is realistic and even encouraged, e.g. differing `tenure_idle_timeout_buffer` for clock-skew tolerance) will routinely hit the boundary condition around tenure timeouts, especially under network delay or during active reorg-permission windows.

### Recommendation
Move the "is the previous miner considered inactive" determination away from purely-local, freely configurable wall-clock deltas and toward a value that is either (a) derived from consensus-visible state (e.g., number of confirmed burn blocks since the tenure started, rather than local elapsed wall-clock time), or (b) tightly bounded/clamped to a network-wide default with enforced min/max, so that legitimate configuration variance across signers cannot flip the accept/reject verdict for the same proposal. At minimum, document and enforce (not just recommend) a required relationship between signer-side and miner-side timeout configuration, and consider having signers exchange/agree on effective timeout values via `StateMachineUpdate` messages instead of relying on local config alone.

### Proof of Concept
1. Deploy a Nakamoto signer set where signer A is configured with `tenure_idle_timeout_secs = 30` (default) and signer B is configured with `tenure_idle_timeout_secs = 5` (a permitted, non-default local override), per `sample/conf/signer/mainnet-signer-conf.toml` (lines 103-121).
2. Miner completes its last block in a tenure at time T; both signers store the same block/tenure state.
3. A full tenure-extend block proposal arrives from the miner at time T+10s, with `changed_burn_view = false`.
4. Signer A computes `extend_timestamp = T + 30 (+buffer)`, so `enough_time_passed = false` -> rejects with `RejectReason::InvalidTenureExtend` (`stacks-signer/src/chainstate/v1.rs` lines 371-391).
5. Signer B computes `extend_timestamp = T + 5 (+buffer)`, so `enough_time_passed = true` -> accepts the same proposal.
6. Result: identical block proposal, identical chain state, but a verifiable split verdict across honest signers purely due to independently permitted local configuration — reproducing the "window inconsistent with common sense" class of bug (an unenforced, owner/operator-configurable temporal boundary substituting for a chain-consistent rule).

    pub tenure_last_block_proposal_timeout: Duration,

}
