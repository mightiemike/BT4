### Title
Unauthorized PRC20 minting for admin-disabled tokens via unchecked `TokenConfig.Enabled` flag - (File: x/uexecutor/keeper/handler.go)

### Summary
The external report describes a wallet that trusted an unvalidated data source (a manipulable server response) to decide which tokens were legitimate, instead of enforcing supported/enabled-token business rules server-side. The Push Chain analog is in the opposite direction: the "supported token" business rule (`TokenConfig.Enabled`) *is* correctly modeled and stored in `x/uregistry`, but the consuming code in `x/uexecutor` never reads it, so an ordinary user's inbound deposit is honored for any registered token regardless of its `enabled` state.

### Finding Description
`x/uregistry/types/types.proto`/`token_config.go` defines `TokenConfig.Enabled` explicitly as "Whether this token is enabled for minting/bridging" [1](#0-0) . This flag is the intended business-logic gate that lets the admin halt bridging for a specific token (e.g. after a depeg, an external-chain exploit, or a security incident) without removing the whole registry entry.

However, the actual mint path never checks it. `depositPRC20` in `x/uexecutor/keeper/handler.go` fetches the config via `GetTokenConfig` and immediately uses `NativeRepresentation.ContractAddress` to call `CallPRC20Deposit`, with no `Enabled` check: [2](#0-1) 

The same unchecked pattern repeats in the FUNDS execution path [3](#0-2) , in the FUNDS_AND_PAYLOAD path (both the direct deposit calls and the smart-contract `executeUniversalTx` branch) [4](#0-3) [5](#0-4) , and in the GAS/GAS_AND_PAYLOAD swap-and-deposit path [6](#0-5) .

Existing regression tests only exercise the "token config missing entirely" case (`RemoveTokenConfig` → `GetTokenConfig` fails → revert created) [7](#0-6) ; there is no test or code path that exercises "token config present but `Enabled: false`", because nothing in the executor consults that field. An unprivileged user who deposits into the gateway for a token the admin has flagged `Enabled: false` will still have their inbound vote-finalize normally (ballot logic is orthogonal to token enablement) and still get PRC20 minted into their UEA, exactly as if the token were still fully supported.

### Impact Explanation
This breaks the "unauthorized mint" and "business-logic validation" invariant in the allowed-impact gate: minting is meant to be gated on the token being admin-approved and currently enabled, but an ordinary user transaction bypasses that gate entirely. In an incident-response scenario (e.g., admin disables a token because its external-chain contract is compromised, its liquidity is depegged, or its `NativeRepresentation` needs rotation), users can continue to trigger PRC20 minting against the stale/disabled configuration, undermining the very purpose of the `Enabled` flag and potentially causing further unauthorized minting during a window the admin explicitly intended to close.

### Likelihood Explanation
High likelihood of reachability: `Enabled=false` is a first-class, documented admin action (`MsgUpdateTokenConfig`) [8](#0-7) , and any subsequent ordinary gateway deposit on that (chain, token) pair reaches `depositPRC20` unconditionally through the normal inbound vote → finalize → execute flow with only an honest-quorum requirement, not any privileged actor.

### Recommendation
Add an explicit `if !tokenConfig.Enabled { return error }` (or equivalent) check immediately after every `GetTokenConfig` call in the execution paths (`handler.go:depositPRC20`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, `execute_inbound_funds_and_payload.go`), causing disabled tokens to fail deposit and follow the existing FAILED-PCTx/`INBOUND_REVERT` handling that already exists for missing configs.

### Proof of Concept
1. Admin registers a token config for `(chain=eip155:X, address=T)` with `Enabled: true`, `NativeRepresentation.ContractAddress = PRC20`.
2. Admin later disables it via `MsgUpdateTokenConfig` setting `Enabled: false` (e.g. incident response).
3. An ordinary user sends funds through the chain-X gateway for token `T` as normal (`FUNDS` or `FUNDS_AND_PAYLOAD` inbound).
4. Universal Validators vote and finalize the inbound as usual (ballot logic doesn't look at `Enabled`).
5. `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload` calls `depositPRC20`, which calls `GetTokenConfig` (succeeds, row still exists) and proceeds to `CallPRC20Deposit`, minting PRC20 to the user's UEA — despite `Enabled: false`. [2](#0-1)

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

## Messages (`MsgServer`)

| Message | Authority | Purpose |
|---|---|---|
| `MsgAddChainConfig` | admin (`params.Admin`) | Register a new external chain |
| `MsgUpdateChainConfig` | admin | Modify an existing chain config |
| `MsgAddTokenConfig` | admin | Whitelist a token on a chain |
| `MsgUpdateTokenConfig` | admin | Modify a token config |
| `MsgRemoveTokenConfig` | admin | Remove a token from the whitelist |
| `MsgUpdateParams` | gov | Rotate the admin or update other params |

There is no validator-vote path here — chain and token additions are intentionally admin-curated. The expected workflow is gov passes `MsgUpdateParams` to install an admin key, and the admin executes config changes day-to-day.
