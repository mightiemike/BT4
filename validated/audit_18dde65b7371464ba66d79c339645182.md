More fundamentally, even setting aside the naming mismatch, the proposed exploit path calls `LedgerDb::write_pruner_progress`/`LedgerMetadataDb::write_pruner_progress` directly to inject a mismatched version [3](#0-2) . This function is only invoked internally by the pruner manager's own bookkeeping (`LedgerPrunerManager::save_min_readable_version`) after coordinated sub-pruner runs, not from any unprivileged transaction, API, package, view, bytecode, or proof input [4](#0-3) . There is no code path by which an unprivileged actor (transaction sender, API caller, etc.) can directly invoke this internal storage write or otherwise desynchronize sub-pruner progress values. The scope rules explicitly require the path to "begin from unprivileged transaction, package, API, view, bytecode, or proof input" and to reject anything depending on "trusted operator mistakes alone." Since the described proof of concept relies on directly calling an internal, trusted-only storage API (`write_pruner_progress`) rather than any unprivileged input, this does not meet the scope or decision standard for acceptance.
