## Title
Unprivileged front-running of `ExchangeTransactionActuator` can block the exchange creator's `ExchangeWithdrawActuator` withdrawal via a precision-check revert - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` allows only the exchange creator to withdraw liquidity from a TRC10 exchange pair, and its validation recomputes the withdrawal ratio from the pool's *current* `firstTokenBalance`/`secondTokenBalance` and rejects the transaction if the recomputed amount deviates from a tight tolerance ("Not precise enough"). Because any unprivileged account can call `ExchangeTransactionActuator` to trade against the same pool and instantly change its balances/ratio, an attacker can front-run the creator's withdraw transaction with a minimal trade to shift the ratio just enough to trip this check, causing the creator's legitimate withdrawal to revert — mirroring the PoolTogether `VaultBooster.setBoost()` griefing pattern where a permissionless `liquidate()` call front-runs and blocks a privileged configuration/state-changing transaction that depends on a mutable shared balance.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` reads the exchange's live token balances and recomputes the counterpart withdrawal amount and a rounding-tolerance check against them: [1](#0-0) [2](#0-1) 

Only the creator of the exchange is authorized to withdraw: [3](#0-2) 

However, `firstTokenBalance`/`secondTokenBalance` are freely mutable by *any* account through `ExchangeTransactionActuator`, which is fully permissionless and directly perturbs the pool ratio (unlike `ExchangeInjectActuator`, which is proportional): [4](#0-3) 

Because the creator constructs and broadcasts a withdraw transaction based on the pool state they observed, and the validation is re-evaluated against whatever the pool state is when the transaction is actually processed, an attacker can submit (and get included before the victim's transaction, e.g. by broadcasting slightly earlier or exploiting normal network/propagation race conditions) a minimal `ExchangeTransactionContract` trade that shifts the ratio outside the 0.01% tolerance window enforced at lines 232-234/260-262, or even trip the coarser `"exchange balance is not enough"` check at lines 221-222/248-249. This is directly analogous to the `VaultBooster.setBoost()` bug: a state-mutating action available to any unprivileged account can be used to invalidate the preconditions checked by a privileged/authorized party's pending transaction, causing it to revert.

### Impact Explanation
This lets any user grief a specific exchange's creator, indefinitely preventing them from withdrawing their liquidity (an accounting/settlement action) at negligible cost (a single minimal trade), similarly to how the original report describes an attacker maintaining control over a target contract's configurable state by repeatedly front-running with trivial amounts. Since `ExchangeWithdrawActuator` is the only path by which the creator can retrieve pool funds, sustained griefing can effectively lock creator funds in the exchange pool for as long as the attacker is willing to submit tiny trades before each retry.

### Likelihood Explanation
Likelihood is limited by TRON's lack of a public mempool/gas-auction ordering model (unlike EVM chains where front-running is trivial via gas-price bidding); an attacker must instead race transaction propagation/broadcast timing to get included in the same or an earlier block than the victim's withdraw transaction. This makes the attack less deterministic than the original Solidity report but still feasible, especially against low-liquidity exchange pairs where the precision tolerance is easy to breach with a small trade, and it is a repeatable griefing vector rather than a one-off issue.

### Recommendation
Add a slippage/tolerance parameter supplied by the creator in `ExchangeWithdrawContract` (similar to `tokenExpected` in `ExchangeTransactionContract`) so the withdrawal succeeds as long as the counterpart amount is within the creator's specified bounds, rather than deriving a rigid precision check purely from the live pool ratio at execution time. This removes the dependency on exact pool state matching the state observed at transaction-construction time.

### Proof of Concept
1. Account A creates a TRC10 exchange pair via `ExchangeCreateActuator` and becomes its `creatorAddress`.
2. Account A prepares an `ExchangeWithdrawContract` to withdraw liquidity, computed against the current pool ratio, per the logic in `ExchangeWithdrawActuator.doValidate()`.
3. Before Account A's transaction is packed into a block, Account B (unprivileged, unrelated to the exchange) calls `ExchangeTransactionActuator` with a minimal `quant` on the same `exchangeId`, shifting `firstTokenBalance`/`secondTokenBalance` per the logic at [4](#0-3) .
4. When Account A's withdraw transaction executes, `doValidate()` recomputes `anotherTokenQuant` and the precision-remainder check against the now-shifted balances at [2](#0-1) , throwing `ContractValidateException("Not precise enough")` and reverting Account A's withdrawal, exactly mirroring the front-running griefing mechanic in the referenced `VaultBooster.setBoost()` finding.
