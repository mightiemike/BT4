## Analysis

The external report's bug class ("no refund/retry mechanism for failing cross-chain transactions, leading to permanently lost user funds") maps directly onto Push Chain's `isCEA` smart-contract inbound-execution path in `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`.

### Title
Permanent loss of bridged funds when a CEA inbound's smart-contract-recipient `executeUniversalTx` call reverts after the PRC20 deposit already succeeded — ([File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go])

### Summary
For `isCEA` inbounds whose `Recipient` is a deployed smart contract (not a UEA), the keeper first deposits PRC20 tokens to that contract address, then separately calls `executeUniversalTx` on it. If the contract call reverts (unimplemented selector, business-logic revert, or gas-fee deduction failure), the failure is only recorded as a `FAILED` `PCTx` — no `INBOUND_REVERT` outbound is created, and the existing `RESCUE_FUNDS` fallback explicitly rejects this scenario because it requires the deposit itself to have failed. The already-minted PRC20 tokens are stranded at the recipient contract with no protocol path to recover them.

### Finding Description
In `ExecuteInboundFundsAndPayload` [1](#0-0) , when `IsCEA` is true and the recipient is a contract with code (`isSmartContract=true`), the flow is:
1. `depositPRC20` mints tokens directly to the attacker/user-specified `Recipient` address [2](#0-1) .
2. Separately, `CallExecuteUniversalTx` attempts to call `executeUniversalTx` on that same address inside a `CacheContext` [3](#0-2) .
3. If `contractErr != nil` or `feeErr != nil`, only a `FAILED` `PCTx` is appended and the function returns — no `INBOUND_REVERT` outbound is built, unlike the sibling failure branches elsewhere in the same function and in `execute_inbound_funds.go` / `handle_failed_inbound_validation.go` [4](#0-3) .

Because the deposit step is outside the `CacheContext` used for the contract call ("*The deposit (above this scope) stays committed regardless*" — comment at lines 233-238), the PRC20 mint is permanent even when the subsequent contract call fails.

The only other recovery mechanism, `AttachRescueOutboundFromReceipt`, explicitly requires that for CEA inbounds the very first `PCTx` (the deposit) have `Status == "FAILED"` [5](#0-4) . In this scenario the deposit `PCTx` (appended earlier at lines 161-185) is `SUCCESS` — only the later `executeUniversalTx` `PCTx` is `FAILED` — so rescue is unconditionally rejected with `"CEA deposit did not fail"`.

`RevertStuckInbound` (the admin escape hatch) is also inapplicable since it only operates on inbounds whose ballot never finalized [6](#0-5) ; here the ballot finalizes and the UTX executes normally, just with a failing downstream call.

### Impact Explanation
Any unprivileged user submitting a normal cross-chain deposit with `IsCEA=true` and a `Recipient` pointing to a contract that has code but does not correctly implement/accept `executeUniversalTx` (which includes essentially any pre-existing contract on Push Chain not purpose-built for this flow, or a purpose-built contract whose invariants reject the call for any of the many reasons enumerated in the original report — invalid amount, slippage, access control, deadline, etc.) causes the bridged PRC20 tokens to be permanently and irrecoverably minted to that contract with no on-chain refund, retry, or rescue path. This is a direct, unprivileged, permanent loss of user funds.

### Likelihood Explanation
Medium-to-High. It requires no validator/relayer/admin collusion — any ordinary CEA inbound whose target contract call fails after a successful deposit triggers this. Given the number of independent conditions that can cause `executeUniversalTx` or the subsequent gas-fee deduction to revert (per the original report's list: invalid amounts, contract-side checks, deadlines, insufficient native balance for gas, etc.), this is a routine, easily-triggered failure mode rather than an edge case.

### Recommendation
Treat a failed `executeUniversalTx`/fee-deduction on the smart-contract CEA path the same as other failure branches in this file: build and attach an `INBOUND_REVERT` outbound (re-minting the funds back to the source chain via `buildRevertOutbound`), or alternatively relax the `RESCUE_FUNDS` eligibility check in `AttachRescueOutboundFromReceipt` to also recognize "deposit succeeded but downstream execution failed" so an admin/relayer-driven rescue can recover the stranded PRC20 balance from the recipient contract.

### Proof of Concept
1. Attacker (or any user) initiates a CEA inbound on a source chain with `Recipient` set to any existing Push Chain contract address that has bytecode but does not implement a valid `executeUniversalTx(sourceChain, sender, payload, amount, prc20, txId)` selector (e.g., a plain ERC20 or an unrelated dApp contract).
2. Universal Validators observe and vote the inbound to quorum; `ExecuteInboundFundsAndPayload` runs.
3. `depositPRC20` succeeds, minting tokens to the target contract; `isSmartContract` is `true` (code hash check).
4. `CallExecuteUniversalTx` reverts (no matching function / logic revert) — `contractErr != nil`.
5. `callPcTx.Status = "FAILED"` is recorded; function returns `nil` with no outbound created.
6. Any later `AttachRescueOutboundFromReceipt` call for this UTX is rejected with `"rescue: UTX %s CEA deposit did not fail"` because `PcTx[0]` (the deposit) is `SUCCESS`.
7. Funds remain permanently locked in the target contract's PRC20 balance with no on-chain mechanism to recover them.

// RevertStuckInbound creates an INBOUND_REVERT outbound for an inbound whose
// ballot has expired without finalizing. The revert outbound enters the normal
// PendingOutbounds flow; UVs sign it via TSS and broadcast it to the source
// chain, refunding the user.
//
// Strict precondition: the ballot for the supplied inbound must be in EXPIRED
// state. Admin must run MsgRecomputeBallotQuorum first to drive a stuck ballot
// to EXPIRED if it isn't already (recompute auto-expires when no eligible
// voters remain).
//
// Returns the new UTX ID and revert outbound ID for telemetry.
func (k Keeper) RevertStuckInbound(ctx context.Context, inbound types.Inbound) (utxId, outboundId string, err error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Same canonical form as the vote path, so the admin-supplied payload
	// derives the same ballot key / UTX key the votes did.
	inbound.Canonicalize()

	if vErr := inbound.ValidateBasic(); vErr != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, vErr.Error())
	}

	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, fmt.Sprintf("failed to derive ballot key: %s", err))
	}

	ballot, err := k.uvalidatorKeeper.GetBallot(ctx, ballotKey)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrNotFound, fmt.Sprintf("ballot for inbound not found (key=%s): %s", ballotKey, err))
	}

	if ballot.Status != uvalidatortypes.BallotStatus_BALLOT_STATUS_EXPIRED {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest,
			fmt.Sprintf("ballot %s status is %s; admin revert requires EXPIRED (use MsgRecomputeBallotQuorum to drive a stuck pending ballot to EXPIRED)",
				ballotKey, ballot.Status.String()))
	}
