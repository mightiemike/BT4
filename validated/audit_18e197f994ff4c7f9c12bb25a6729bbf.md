### Title
Amsterdam BAL parallel-execution path lets a proposer's untrusted Block-Level Access List override real state reads, allowing a block to pass consensus with a state root that would differ from independent execution against the true parent state - (File: crates/engine/tree/src/tree/payload_processor/bal/execute.rs, crates/engine/tree/src/tree/payload_processor/bal/worker.rs)

### Summary
For EIP-7928 (Amsterdam) blocks, `execute_block_bal` spawns worker executors whose EVM database has the **received, attacker/proposer-supplied BAL** attached via `.with_bal(received_bal_revm)` [1](#0-0) . Per `attach_bal_before_tx`'s documented semantics, "the attached BAL takes precedence over committed state when serving reads" [2](#0-1) . Transactions are therefore executed against values declared in the untrusted BAL rather than the true parent state whenever the BAL claims coverage for an account/slot. The resulting `TxResult`s are committed directly into canonical state [3](#0-2) , and the only post-execution BAL check is that the **BAL rebuilt from this same tainted execution** hashes to the header's declared `block_access_list_hash` [4](#0-3) . This is exactly the TapiocaOFT bug class: one attacker-controlled value (the BAL's declared reads) is used to actually compute execution/state, while validation only checks an internally-derived, self-referential quantity — it never cross-checks the declared reads against the real committed parent state that per-transaction fragment checks would provide. The module's own doc explicitly notes this gap: "It does not yet run per-transaction fragment checks. It does not yet report rich undeclared-access diagnostics." [5](#0-4) 

### Finding Description
`execute_block_bal` is reached from `BasicEngineValidator::validate_block_with_state` when a block carries a decoded BAL and the BAL parallel-execution path is eligible [6](#0-5) . The BAL comes from `input.try_decoded_access_list()`, i.e., data embedded in the block/payload itself — supplied by whoever built the block [7](#0-6) . Before this executor path runs, the only checks performed are (a) that the BAL bytes decode, and (b) `validate_gas_limit` (an item-cost bound) [8](#0-7)  — there is no check that the *values* recorded in the BAL for any account/slot match the real parent state.

Inside `execute_block_inner`, each worker builds a `State` with `.with_bal(received_bal_revm)` where `received_bal_revm` is converted straight from the untrusted, attacker-supplied BAL [9](#0-8) [10](#0-9) . Because BAL-covered reads take precedence over the real database, a transaction whose execution branches on account balance, storage, nonce, or code (e.g. an ERC-20 balance check, an oracle price read, a conditional based on `SLOAD`) will execute using whatever value the block author declared in the BAL, not the true parent-state value obtained from the `StateProviderDatabase`.

The canonical executor never re-derives or validates these reads independently: it simply calls `commit_transaction(output.result)` on the worker-produced `TxResult` for each transaction, in order, and tracks the writes it observes purely to build its own BAL (`with_bal_builder`) [11](#0-10) . The post-execution check that exists — `take_built_bal_and_log_divergence` plus the consensus hash comparison — only compares the freshly rebuilt BAL (built from writes that were themselves computed off tainted reads) against the header's declared hash [12](#0-11) [4](#0-3) . This check is self-referential with respect to the tainted execution: because the same untrusted BAL drove the reads that produced the writes, the rebuilt BAL and the header's declared BAL hash can trivially agree even though the executed transactions never touched the real parent state for the BAL-covered items.

Non-BAL-covered reads correctly fall back to the true database [2](#0-1) , so the attack surface is bounded to state the attacker declares as "covered," but for any account/slot the attacker chooses to cover with a fabricated value, that value becomes authoritative for BAL-path execution.

### Impact Explanation
This breaks the core invariant that block execution must be a deterministic function of the true parent state and the transaction list. A block builder can supply a BAL that misrepresents some account's balance, nonce, storage, or code, causing the BAL execution path to compute a different `BundleState`/receipts/state root than an honest re-execution against the real parent state would produce. If accepted, this is a state root divergence relative to the spec (any two clients, or the same client on BAL-vs-serial paths, would disagree) — a Critical consensus-split scenario. It also matches the report's "credit/debit inconsistency": the value trusted for state mutation (BAL-declared read) is never reconciled against the value that should gate it (the real committed parent state), exactly mirroring `share` vs `amount` in the TapiocaOFT bug.

### Likelihood Explanation
Likelihood depends on runtime gating (`disable_bal_parallel_execution`, `disable_bal_parallel_state_root`) and whether the Amsterdam/EIP-7928 BAL feature is enabled in a given deployment; I was not able to fully confirm within the available context whether this path is enabled by default or still feature-flagged/experimental for mainnet (the code contains an explicit TODO: "extend with stronger gating before enabling on mainnet" and the fork check is only a proxy) [6](#0-5) . The in-code module doc explicitly documents the missing per-transaction fragment validation as a known, not-yet-implemented gap [5](#0-4) , which both confirms the root cause and suggests this may be tracked as a pre-mainnet TODO rather than a silent oversight — reducing novelty but not the underlying risk if/when this path is enabled without the missing checks.

### Recommendation
Before or during BAL-path execution, verify that every BAL-declared "read" value for an account/slot that a transaction actually consumes matches the true parent-state value (or, equivalently, run per-transaction fragment validation comparing declared vs. actual reads, as the module doc says is planned). Do not allow the final acceptance check to be purely a self-referential rebuilt-BAL-hash comparison; either reconcile BAL reads against the real database before honoring them, or fully re-verify the BAL path's output against a real (non-BAL-fed) execution before accepting the block.

### Proof of Concept
A complete PoC requires driving `BasicEngineValidator::validate_block_with_state` with a block whose embedded BAL declares a fabricated account balance/storage value diverging from the true parent state, and observing that `execute_block_bal` accepts it and produces committed state differing from serial execution's `assert_shadow_equal` harness already present in the tests (which only asserts agreement for *honest* BALs) [13](#0-12) . I was not able to fully construct and execute this end-to-end scenario within the available tool access (no code execution), so this remains a structural/code-review finding pending dynamic confirmation — specifically, whether `bal_path_eligible` and related feature flags are enabled in a production configuration should be confirmed before treating this as immediately exploitable.

    /// Returns true when the BAL execute path should be used for this block.
    // TODO: extend with stronger gating before enabling on mainnet:
    //   - Fork check: `Amsterdam.active_at_timestamp(env.evm_env.timestamp)`. Today a BAL only
    //     exists post-Amsterdam, so the BAL-presence check is a sufficient proxy. It is a proxy,
    //     not a guarantee.
    //   - Tx-count threshold (`bal_execute_path_min_tx_count`): below the parallelism break-even
    //     point, provider setup and worker scheduling overhead can exceed the gain. Tune
    //     empirically once workers are parallel; meaningless while the commit loop is sequential.
    fn bal_path_eligible(&self, bal: Option<&DecodedBal>) -> Result<bool, InsertBlockErrorKind> {
        let has_bal = bal.is_some();
        let parallel_execution = has_bal && !self.config.disable_bal_parallel_execution();
        if parallel_execution && self.config.disable_bal_parallel_state_root() {
            return Err(InsertBlockErrorKind::Other(
                "disabling parallel state root is impossible when parallel execution is enabled"
                    .into(),
            ));
        }

        Ok(parallel_execution)
    }
