### Title
Unmetered per-account trie iteration in `compute_gas_key_balance_sum` during `DeleteAccount` allows a single receipt to exceed the per-receipt storage-proof limit and burn no compensating gas/compute - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_delete_account` (`runtime/runtime/src/actions.rs:330`) calls `compute_gas_key_balance_sum(state_update, account_id)` (`core/store/src/utils/mod.rs:458`) *before* the `EnforcePerReceiptStorageProofLimit` check-point that guards `apply_action` (`runtime/runtime/src/lib.rs:982-998`), and unlike `remove_account`'s nonce-removal loop, the iteration inside `compute_gas_key_balance_sum` never adds anything to `result.compute_usage`. An account owner who has amassed a very large number of access/gas keys can make one `DeleteAccount` action perform an unbounded, effectively free (gas-wise) trie walk over every access-key/gas-key-nonce row for that account, similar in spirit to the reported `applyToRound`/`getApplicationIndexesByProjectID` unbounded-array DOS: the vulnerable operation is a helper that is invoked from a state-changing entry point and scales with an attacker-controlled, unbounded collection, with no metering tied to the scale of that collection at the point it is walked.

### Finding Description
- `action_delete_account` first bounds *storage usage* (`Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE = 10_000` bytes, `actions.rs:364`), but that check is on byte-size of storage usage, not on the *number of access keys/gas-key-nonce rows*, which are cheap to add (bounded only by ordinary storage staking economics) and can be numerous while staying under the byte-size cap only when keys are small - but even so, an attacker paying the storage-stake cost can create a large number of individual `AccessKey`/gas-key rows (each `AccessKey::NONCE_VALUE_LEN` etc. is small) before the storage-usage limit is hit, and each row requires a trie read. [1](#0-0) 
- `compute_gas_key_balance_sum` walks the entire `get_raw_prefix_for_access_keys(account_id)` range with a trie iterator, parsing every access-key/nonce row and issuing a `get_access_key_by_handle` lookup for each non-nonce key, purely to sum gas-key balances - with no gas/compute charge attributed to this iteration. [2](#0-1) 
- This call happens at `actions.rs:370`, prior to the account being actually removed (`remove_account`, `actions.rs:387`), and its cost is not reflected anywhere in `result.compute_usage`; only the *subsequent* removal (`remove_account`) charges compute via `storage_removes_compute` for nonces (`actions.rs:392-401`), and even that only accounts for gas-key nonce removal, not the full access-key-listing cost incurred by `compute_gas_key_balance_sum`. [3](#0-2) 
- The storage-proof (state-witness) growth caused by this iteration is only checked *after* the whole action list for the receipt completes, via `recorded_storage_size_upper_bound` diffing against `storage_proof_size_before_receipt`/`storage_proof_limit_for_all_actions` (`ProtocolFeature::EnforcePerReceiptStorageProofLimit`, PV 86). [4](#0-3) 
  That check can only *reject* the receipt after the proof has already grown to consume proof budget and CPU time for the walk - it does not prevent the read amplification/CPU cost from happening, and does not charge any compensating gas back to the sender. Because the walk's cost was never metered as gas/compute in the first place, an attacker's `DeleteAccount` receipt can consume disproportionate node-side CPU/IO and storage-proof budget relative to the gas it paid, while other, legitimate receipts in the same chunk get starved of the storage-proof budget or gas limit (`check_proof_size_limit_exceed`) that governs chunk-wide receipt processing (`runtime/runtime/src/lib.rs:2592`, `:2832`). [5](#0-4) 

### Impact Explanation
This is a gas/compute-metering bypass: work performed by the runtime scales with an attacker-controlled, unbounded collection (number of access/gas keys on an account) but is not charged proportionally in `compute_usage`/gas. This can (a) let one `DeleteAccount` receipt consume storage-proof budget and CPU time disproportionate to the gas paid, degrading the throughput of the containing chunk (self-inflicted resource exhaustion within a chunk, echoing the "getApplicationIndexesByProjectID" DOS pattern where a helper's cost scales with an unbounded attacker-controlled array), and (b) in combination with the PV-86 `EnforcePerReceiptStorageProofLimit` guard, cause the receipt to fail only *after* the expensive walk already happened, wasting validator/chunk-producer resources repeatedly if the transaction is resubmitted. This does not directly move value or corrupt state (the check ultimately rejects an over-limit receipt), so it falls short of unauthorized value movement or state-root divergence, but it is a real gas-accounting gap reachable by a single unprivileged `DeleteAccount` action.

### Likelihood Explanation
Moderate-to-low. Exploitation requires the attacker to first pay real NEAR to create and storage-stake a large number of access/gas keys on their own account (bounded loosely by `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE = 10_000` bytes and ordinary storage-staking costs), then issue one `DeleteAccount` action. The economic cost of building up enough keys to matter is nontrivial, which limits practical severity, but the underlying metering gap (unbounded iteration in `compute_gas_key_balance_sum` with zero attributed compute cost) is a genuine code defect independent of how expensive it is to trigger at scale.

### Recommendation
Meter `compute_gas_key_balance_sum`'s trie walk the same way `remove_account`'s nonce-removal loop is metered: track the number of rows/bytes visited and add a corresponding `storage_reads_compute`/`storage_removes_compute`-style charge to `result.compute_usage` in `action_delete_account`, ideally checked incrementally (not only after the fact via the PV-86 storage-proof limit) so the loop can bail out early via the normal gas-limit mechanism rather than only being caught by the post-hoc `ReceiptStorageProofSizeExceeded` check.

### Proof of Concept
1. Create an account and repeatedly call `AddKey` with `GasKeyFullAccess`/regular `AccessKey` permissions until the account holds many access keys / gas-key-nonce rows while staying under `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` (10,000 bytes) of storage usage - see `add_gas_key`/`add_regular_key` (`runtime/runtime/src/access_keys.rs:149-247`) for the storage-cost accounting that bounds how many keys fit under that byte cap.
2. Submit a `DeleteAccount` action against that account. `action_delete_account` (`runtime/runtime/src/actions.rs:330`) calls `compute_gas_key_balance_sum` (`core/store/src/utils/mod.rs:458`) which iterates every access-key/nonce trie row for the account, doing a `get_access_key_by_handle` read per key, with zero compute/gas charged for this iteration (`actions.rs:370`).
3. Observe that `result.compute_usage` only reflects the fixed `DeleteAccount` exec fee plus the later `remove_account`'s nonce-removal compute (`actions.rs:392-401`); the up-front balance-sum walk's read amplification and storage-proof growth are unaccounted for until the post-hoc `ReceiptStorageProofSizeExceeded` check (`runtime/runtime/src/lib.rs:982-998`), by which time the CPU/IO cost has already been paid by the node, not the sender.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

/// Computes the total balance across all gas keys for a given account.
pub fn compute_gas_key_balance_sum(
    state_update: &TrieUpdate,
    account_id: &AccountId,
) -> Result<Balance, StorageError> {
    let mut total = Balance::ZERO;
    let lock = state_update.trie().lock_for_iter();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if nonce_index.is_some() {
            continue;
        }
        if let Some(balance) = get_access_key_by_handle(state_update, account_id, &key_handle)?
            .as_ref()
            .and_then(|access_key| access_key.gas_key_info())
            .map(|gas_key_info| gas_key_info.balance)
        {
            total = total.checked_add(balance).ok_or_else(|| {
                StorageError::StorageInconsistentState("gas key balance overflow".to_string())
            })?;
        }
    }
    Ok(total)
}
