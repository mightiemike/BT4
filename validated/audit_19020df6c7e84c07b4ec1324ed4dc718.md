Based on my research, I found a concrete, code-documented analog in the nearcore codebase. It matches the bug-class pattern in the CVE: a *known* weakness where the system deliberately tolerates a validation failure instead of enforcing rejection, with the workaround chosen to preserve availability over strict correctness — exactly the same "fail-open by design, documented and accepted" tradeoff EVerest made with `terminate_connection_on_failed_response`.

### Title
Receipt-size-limit validation is intentionally bypassed for existing/forwarded receipts, allowing oversized receipts to be persisted and propagated in state - ([File: runtime/runtime/src/verifier.rs](runtime/runtime/src/verifier.rs))

### Summary
`validate_receipt` in the runtime enforces `max_receipt_size` only when validating a **newly created** receipt (`ValidateReceiptMode::NewReceipt`). For `ValidateReceiptMode::ExistingReceipt` — the mode used for delayed and incoming receipts already present in state or arriving cross-shard — the size check is skipped entirely, by design, as a known workaround for issue #12606.

### Finding Description
`validate_receipt` only checks `receipt_size > limit_config.max_receipt_size` when `mode == ValidateReceiptMode::NewReceipt`; this check is bypassed for `ExistingReceipt` mode, whose doc comment explicitly states it "has to be less strict" because "there is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed." [1](#0-0) 

This same accepted-workaround pattern is applied at the congestion/bandwidth layer: `ReceiptSinkV2::try_forward` explicitly clamps any receipt whose size exceeds `max_receipt_size` down to `max_receipt_size` "to avoid receipts getting stuck," rather than rejecting it. [2](#0-1)  The same clamp-instead-of-reject logic is repeated in bandwidth-request generation. [3](#0-2) 

Test code in the repository documents that a single unprivileged contract call can trigger this: a `FunctionCall` action returning a value via `promise_return`, or a data receipt carrying a large returned value, can grow a receipt above `max_receipt_size` **after** the initial `NewReceipt` size check has already passed, and the resulting oversized receipt is accepted rather than rejected — a bug the tests explicitly acknowledge is not fixed. [4](#0-3) [5](#0-4) 

The spec explicitly frames this as an accepted design tradeoff rather than an unintended defect: "receipts above `max_receipt_size` are treated as exactly `max_receipt_size` for both forwarding limits ... and bandwidth requests ... so they cannot get permanently stuck (issue #12606)." [6](#0-5) 

### Impact Explanation
This is the same bug class as the EVerest CVE: a known validation gap where the default/production behavior tolerates a should-be-rejected condition (oversized receipt / failed request) instead of enforcing the hard limit, because enforcing it strictly elsewhere is considered too disruptive. Here, a single account's contract call can create a receipt whose true size exceeds `max_receipt_size`, and that receipt is subsequently accepted into cross-shard receipt proofs, delayed queues, and bandwidth accounting under a "pretend it's within limit" policy rather than being rejected as an invalid state transition. This weakens the protocol's `max_receipt_size` invariant (a resource/consensus bound), since honest nodes at different points in the pipeline apply the bound inconsistently (strict for `NewReceipt`, lenient for `ExistingReceipt`).

### Likelihood Explanation
Reachable directly by any account submitting a `FunctionCall` transaction that triggers a promise chain with a large return value or `output_data_receivers` growth after the initial size check — as demonstrated by the existing repository tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`, which succeed in producing and observing an oversized receipt in the chain state. [7](#0-6) 

### Recommendation
Enforce `max_receipt_size` consistently regardless of `ValidateReceiptMode`, closing the gap between `NewReceipt` and `ExistingReceipt` validation, and remove the silent clamp-to-limit workarounds in `try_forward` / bandwidth-request generation in favor of properly rejecting/handling oversized receipts at their point of creation (i.e., fix issue #12606 at the source rather than tolerating it downstream).

### Proof of Concept
The repository's own test suite is a working PoC: `test_max_receipt_size_promise_return` deploys a contract, submits a `FunctionCall` transaction that builds a promise DAG whose returned/forwarded receipt grows past `max_receipt_size` after the initial check, and then calls `assert_oversized_receipt_occurred` which scans chain state and confirms a receipt exceeding `max_receipt_size` was actually persisted/propagated. [7](#0-6)

fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);

        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));
