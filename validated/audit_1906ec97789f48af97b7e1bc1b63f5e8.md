### Title
DeterministicStateInitAction can permanently strand pre-funded balances when the referenced GlobalContractIdentifier does not exist - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Summary
NEP-616 deterministic accounts (`0s...` ids) are NEAR's analog to Solidity `CREATE2` counterfactual deployment: the account id is derived off-chain/deterministically from a `DeterministicAccountStateInit` (a `GlobalContractIdentifier` `code` plus `data`), and a `Transfer` action can pre-fund that address before the `DeterministicStateInitAction` is ever executed, exactly like sending ETH to a not-yet-deployed CREATE2 address [1](#0-0) . As in the Sablier report, if the parameters used to "deploy" (initialize) the account reference a global contract that doesn't exist, the initialization action fails, and because the account id is a hash of those exact parameters, the funds sent to the pre-funded address cannot be recovered by retrying with different parameters.

### Finding Description
`action_deterministic_state_init` creates the account record (if absent) and then calls `deploy_deterministic_account`, which in turn calls `use_global_contract` to set the account's code to the `GlobalContractIdentifier` embedded in the `DeterministicAccountStateInit` [2](#0-1) . `use_global_contract` checks whether the referenced global contract identifier (a code hash or an owner account id) actually exists in the trie; if not, it sets `result.result = Err(ActionErrorKind::GlobalContractDoesNotExist)` and returns without creating the contract [3](#0-2) .

Crucially, the deterministic account id itself is derived by hashing the `DeterministicAccountStateInit` (which includes the `GlobalContractIdentifier`) via `'0s' + keccak256(bytes)[12:32]` [4](#0-3) . A user (or relayer) can pre-fund this address with a plain `Transfer` before the global contract referenced in `state_init.code` is deployed, or reference a global contract identifier that is later never deployed, is deployed by a different account under `GlobalContractDeployMode::AccountId` and later "redeployed"/removed, or simply typo'd/miscalculated off-chain. In all these cases `DeterministicStateInitAction` fails with `GlobalContractDoesNotExist`, exactly mirroring the Sablier bug where `createMerkleLT()` reverts if the tranches don't sum to 100%.

Because `DeterministicAccountStateInit` (and hence the account id) commits to the exact `GlobalContractIdentifier`, there is no way to retry with a different/available global contract and land on the same, already-funded account id — any change to `code` changes the derived `0s...` account id, just as changing tranche percentages changes the CREATE2 salt/address in the original report. The pre-funded balance sits on an account that can never be initialized with a working contract, and per NEP-616 rules a deterministic account cannot be created via `CreateAccount` or ordinary `Transfer` alone with different parameters to work around this [5](#0-4) .

The `implicit_creation_allowed` gate confirms that `NearDeterministicAccount` funding by transfer is a supported, intentional flow (transfer-only receipts create the account with `AccountContract::None` via `create_deterministic_account`), so pre-funding before state-init is a first-class supported pattern, not a misuse [6](#0-5) [7](#0-6) .

### Impact Explanation
Funds sent to a deterministic account address before (or in anticipation of) a working `DeterministicStateInitAction` can become permanently frozen if the referenced `GlobalContractIdentifier` never materializes or stops existing (e.g., wrong hash, contract not yet propagated to the shard, or an account-based global contract owner who never deploys). Unlike a normal failed transaction, there is no way to change the state-init parameters and still land on the same account id, since the id is a hash of those very parameters. This matches the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
This requires no privileged access — any transaction signer or relayer can pre-fund a deterministic account id computed off-chain, and can independently (or accidentally) construct a `DeterministicAccountStateInit` referencing a global contract identifier that turns out not to exist at execution time (propagation delay of `DeployGlobalContractAction` across shards, wrong hash calculation, or a global-contract-by-account-id owner who removes/never deploys). Given the multi-shard, multi-step nature of global contract distribution (`initiate_distribution`/`apply_global_contract_distribution_receipt`), transient non-existence is plausible even for a correctly-computed identifier if the transfer and the state-init race the global contract's shard-by-shard propagation [8](#0-7) .

### Recommendation
Do not let `DeterministicStateInitAction` fail unrecoverably when the referenced global contract is missing. Options include: (a) allowing retry with the *same* `state_init` once the global contract becomes available (already supported, since the id is fixed by the same params) — ensure documentation/tooling steers users to always retry with identical `state_init` rather than "fixing" parameters; (b) providing a refund/reclaim path (analogous to Sablier's clawback) so balances sent to a deterministic account whose state-init can provably never succeed (e.g., a `CodeHash` identifier that will never be deployed) can be recovered via a signed message from the derived account's future owner or a timeout-based reclaim; (c) providing an off-chain/view-only validation RPC that checks global contract existence before a user pre-funds a deterministic address, reducing the chance of stranding funds due to a race or typo.

### Proof of Concept
1. Off-chain, compute `state_init = DeterministicAccountStateInit::V1 { code: GlobalContractIdentifier::CodeHash(H), data }` for some hash `H` that is not (yet) deployed as a global contract, and derive `det_account = '0s' + keccak256(borsh(state_init))[12:32]`.
2. Send a `Transfer` action to `det_account` — this creates the account via `action_implicit_account_creation_transfer` → `create_deterministic_account`, with `AccountContract::None` [6](#0-5) .
3. Submit `DeterministicStateInitAction` with the same `state_init` targeting `det_account`. `action_deterministic_state_init` calls `deploy_deterministic_account` → `use_global_contract`, which finds no `TrieKey::GlobalContractCode` entry for `H` and sets `result.result = Err(GlobalContractDoesNotExist)` [9](#0-8) .
4. If `H` is never deployed as a global contract (e.g., the deployer changes their mind, or the identifier was mistyped/miscalculated), no other `state_init` value can be submitted that both (a) succeeds in deploying a contract and (b) hashes to the same `det_account`, so the balance transferred in step 2 is permanently stuck on an uninitializable account.

### Deterministic account ID

The account ID is derived from a `DeterministicAccountStateInit` instance.

To derive the deterministic account id, borsh-encode the `DeterministicAccountStateInit` enum instance into raw
bytes. Then use the following formula: `'0s' + keccak256(bytes)[12:32].hex()`.

### Deterministic account creation

Deterministic accounts cannot be created with a `CreateAccount` nor with a `Transfer` action.
A special action, `DeterministicStateInitAction`, is required.
This action validates that the account id matches its initial state.

As with all account types, you have to attach a large enough deposit to cover for the account storage. If the code and
initial state is small enough to fit below the zero-balance limit, no balance is required. The
`DeterministicStateInitAction` has a field to include a balance specifically to cover storage. Anything above the
required amount to cover storage requirements is refunded.

A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`. The account will not be usable,
however, until the `DeterministicStateInitAction` is also executed.

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition. "uninit" here is the
        // NEP-616 sense, a deterministic account with no contract yet, not
        // `Account::Uninitialized`: a `0u` id can never reach this, because
        // `validate_deterministic_state_init` pins the receiver to the derived
        // `0s` id.
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }
    if result.result.is_err() {
        return Ok(());
    }

    settle_state_init_deposit(
        account,
        action.deposit,
        account_id,
        receipt,
        &apply_state.config,
        result,
    )
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }

        unreachable!("given receipt should be an global contract distribution receipt")

        apply_state,
        epoch_info_provider,
        state_update,
        receipt_sink,
        receipt_to_tx,
    )?;

    Ok(compute)
}

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
