### Title
Missing Duplicate-Address Check in `EthBalMonSetWatchListConfig` Validation Allows Malformed MCMS Proposals for the EthBalanceMonitor Watchlist - (File: `deployment/vault/changeset/validation.go`)

### Summary
The `ValidateEthBalMonSetWatchListConfig` function, which gates the `EthBalMonSetWatchList` changeset used to build MCMS/timelock proposals for configuring the `EthBalanceMonitor` contract's `setWatchList`, validates address format, zero-address, and non-negative amounts, but never checks that `chainConfig.Addresses` contains no duplicate entries — unlike sibling validators in the same file (`ValidateSetWhitelistConfig` and `validateNativeTransfers`), which explicitly reject duplicate addresses.

### Finding Description
`ValidateEthBalMonSetWatchListConfig` iterates `chainConfig.Addresses`, `MinBalancesWei`, and `TopUpAmountsWei` and validates length parity, zero addresses, and non-negative amounts, but has no `addressSet`/duplicate-detection logic: [1](#0-0) 

This is inconsistent with the pattern used elsewhere in the exact same file for structurally identical inputs (address + amount lists), where duplicates are explicitly rejected: [2](#0-1) [3](#0-2) 

The unvalidated `Addresses`/`MinBalancesWei`/`TopUpAmountsWei` triple flows unchanged from the changeset input through the operation into the on-chain `SetWatchList` call used to build the MCMS batch transaction: [4](#0-3) 

If a duplicate address (with different `MinBalanceWei`/`TopUpAmountWei` values, e.g., from an authoring mistake or a merge of overlapping watchlist configs) is present, the check that should catch it at the validation stage (`VerifyPreconditions`, which calls `ValidateEthBalMonSetWatchListConfig`) is silently bypassed: [5](#0-4) 

This exactly mirrors the reported bug class: a list is consumed to build a privileged on-chain configuration action without checking for duplicate addresses, so a duplicated entry silently produces unintended/conflicting on-chain state instead of being rejected at validation time.

### Impact Explanation
The `EthBalMonSetWatchList` changeset produces an MCMS timelock proposal that, once executed by the timelock/multisig, directly reconfigures the on-chain `EthBalanceMonitor` contract's watchlist — the mechanism used to keep automation/keeper-related addresses funded. A duplicate address entry that is silently accepted (rather than rejected during precondition checks) means the deployment tooling builds and proposes a transaction whose semantics do not match operator intent: depending on the contract's internal indexing of the watchlist (last-write-wins for a given address, or duplicate top-up computation per cycle), this can cause an address to be over/under-funded relative to what was intended, or cause other addresses in the same batch to be dropped/misconfigured. Because this is baked into a timelock proposal that is expected to have been reviewed against validated inputs, operators would trust that basic sanity checks (like the ones present for the sibling whitelist/transfer changesets) already ran.

### Likelihood Explanation
Likelihood is low-to-moderate: this requires a mistake in constructing the `EthBalMonSetWatchListInput` config (e.g., merging watchlist entries from multiple sources, or copy-paste error), which is plausible in an operational/governance tooling context where watchlists are edited by hand or generated from multiple upstream configs. The missing check means such an error is not caught before a timelock proposal is created and possibly signed/executed.

### Recommendation
Add duplicate-address detection to `ValidateEthBalMonSetWatchListConfig`, consistent with the pattern already used in `validateNativeTransfers` and `ValidateSetWhitelistConfig` in the same file: build an `addressSet` per chain and return an error if an address is seen more than once, rejecting the config before an MCMS proposal is generated.

### Proof of Concept
Not applicable/exploitable as a live on-chain PoC from this codebase alone, since the `EthBalanceMonitor` Solidity contract source is not present in this repository (only the Go binding `eth_balance_monitor_wrapper` is used) — its exact on-chain handling of duplicate watchlist entries could not be directly inspected. func ValidateEthBalMonSetWatchListConfig(ctx context.Context, env cldf.Environment, cfg types.EthBalMonSetWatchListInput) error {
	if len(cfg.Chains) == 0 {
		return errors.New("no chains provided")
	}

	for chainSelector, chainConfig := range cfg.Chains {
		if _, ok := env.BlockChains.EVMChains()[chainSelector]; !ok {
			return fmt.Errorf("chain not found in environment: %d", chainSelector)
		}
		n := len(chainConfig.Addresses)
		if n == 0 {
			return fmt.Errorf("chain %d: addresses must not be empty", chainSelector)
		}
		if len(chainConfig.MinBalancesWei) != n || len(chainConfig.TopUpAmountsWei) != n {
			return fmt.Errorf(
				"chain %d: addresses, min_balance_wei, and topup_amounts_wei must have the same length (got %d, %d, %d)",
				chainSelector, n, len(chainConfig.MinBalancesWei), len(chainConfig.TopUpAmountsWei),
			)
		}
		for i, addr := range chainConfig.Addresses {
			if err := validateEthAddress(fmt.Sprintf("address %d", i), addr.Hex()); err != nil {
				return fmt.Errorf("chain %d: %w", chainSelector, err)
			}
			if addr == (common.Address{}) {
				return fmt.Errorf("chain %d: address at index %d is zero address", chainSelector, i)
			}
			// Check MinBalancesWei and TopUpAmountsWei are >= 0
			if chainConfig.MinBalancesWei[i].Cmp(big.NewInt(0)) < 0 {
				return fmt.Errorf("chain %d: min_balance_wei at index %d must be >= 0", chainSelector, i)
			}
			if chainConfig.TopUpAmountsWei[i].Cmp(big.NewInt(0)) < 0 {
				return fmt.Errorf("chain %d: topup_amounts_wei at index %d must be >= 0", chainSelector, i)
			}
		}
