### Title
Token Exchange Strategy Skips Scope-Change Revalidation That Auth Code Flow Enforces - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts])

### Summary
The bug class from the report (one code path enforces a security check while a parallel/analogous path omits it) is reproduced in the session-validity checks used by the two admin authentication strategies. `AuthCodeFlowStrategy.authenticate` validates a stored session with `session.isActive(config.scopes)`, explicitly requiring the session's granted scopes to match the app's currently configured scopes. `TokenExchangeStrategy.authenticate` (and its Express/React-Router equivalents) instead calls `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)`, passing `undefined` for scopes.

### Finding Description
`Session.isActive` computes validity as `!isScopeChanged && hasAccessToken && isTokenNotExpired`, and `isScopeChanged` explicitly short-circuits to `false` (i.e., "not changed") whenever `scopes` is `undefined`: [1](#0-0) 

The Auth Code Flow strategy passes the app's configured scopes, so a stored session whose granted scope set no longer matches the app's required scopes is correctly treated as inactive and forces re-authorization: [2](#0-1) 

The Token Exchange strategy instead calls `isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)`, meaning the scope check is entirely skipped and only expiry is checked: [3](#0-2) 

The same pattern (scope check present in Auth Code Flow, absent in Token Exchange) exists identically in the Express middleware pair: [4](#0-3) [5](#0-4) 

This inconsistency is analogous to the reported bug: two functions serving the same purpose (validating whether a stored access-token session should be honored) apply different security criteria, and the weaker one is reachable from a normal, unprivileged embedded-app request flow (token exchange is the default path for embedded apps that use `future.tokenExchange`/token-exchange auth).

### Impact Explanation
If an app's required OAuth scopes are reduced or changed (a routine operational event — e.g., removing a scope from `scopes` config, or a merchant re-approving with fewer permissions), the Auth Code Flow correctly detects the scope mismatch and forces re-authorization to obtain a token with the updated scope set. The Token Exchange path does not perform this check, so a stale session/access token whose granted scopes no longer match the app's declared requirements will continue to be treated as valid and reused for API calls (bypassing the scope-consistency guarantee that `isActive(scopes)` is designed to enforce elsewhere in the same codebase). This is a correctness/consistency gap in access-token freshness rather than a signature or token-forgery bypass — the token itself is still a legitimately-issued, valid access token, but the intended "you must re-request when scope requirements change" security control is silently disabled on the token-exchange path.

### Likelihood Explanation
Token exchange is the standard/default flow for modern embedded Shopify apps, so this path is broadly and routinely reachable by any merchant using the app — no privileged access or leaked secrets required. The gap will manifest anytime app scope configuration changes while old sessions still remain in storage with an unexpired token, which is a normal operational occurrence for actively maintained apps.

### Recommendation
Pass the app's configured scopes into the `isActive` check in the Token Exchange strategies to mirror `AuthCodeFlowStrategy`, e.g. change `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` to `session.isActive(config.scopes, WITHIN_MILLISECONDS_OF_EXPIRY)` in `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts`, the equivalent in `packages/apps/shopify-app-react-router/src/server/authenticate/admin/strategies/token-exchange.ts`, and `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` in `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`, so that a scope mismatch triggers a fresh token exchange instead of reusing a stale-scope session.

### Proof of Concept
1. Configure an app with `scopes: ['read_products', 'write_products']` and install it via token exchange, storing an offline session with `scope: 'read_products,write_products'`.
2. Reduce the app's configured scopes to `scopes: ['read_products']` (a routine scope reduction) without invalidating existing stored sessions.
3. A subsequent authenticated request through `shopify.authenticate.admin` using the Token Exchange strategy calls `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` — since `scopes` is `undefined`, `isScopeChanged` returns `false` regardless of the mismatch, so the stale session is reused and no new token exchange/scope reconciliation occurs, unlike what would happen under `AuthCodeFlowStrategy`, which would call `session.isActive(config.scopes)` and correctly force re-authorization.

  public isActive(
    scopes: AuthScopes | string | string[] | undefined,
    withinMillisecondsOfExpiry = 500,
  ): boolean {
    const hasAccessToken = Boolean(this.accessToken);
    const isTokenNotExpired = !this.isExpired(withinMillisecondsOfExpiry);
    const isScopeChanged = this.isScopeChanged(scopes);
    return !isScopeChanged && hasAccessToken && isTokenNotExpired;
  }

  /**
   * Whether the access token includes the given scopes if they are provided.
   */
  public isScopeChanged(
    scopes: AuthScopes | string | string[] | undefined,
  ): boolean {
    if (typeof scopes === 'undefined') {
      return false;
    }

    return !this.isScopeIncluded(scopes);
  }
