## Analog identified: `_release_all`-style all-or-nothing batch failure in `BuildOutboundsFromReceipt`

### Title
Single failing outbound event in a multi-outbound receipt discards all valid outbounds — funds already burned on Push Chain get no relay path - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`BuildOutboundsFromReceipt` iterates every `UniversalTxOutboundEvent` log emitted by the `UniversalGatewayPC` contract in a single EVM receipt and builds one `OutboundTx` per event [1](#0-0) . If the destination chain for any one of those events has outbound disabled, or if `GetTokenConfigByPRC20` fails for any one event, the function immediately `return nil, err` — discarding every `OutboundTx` already built for the other, valid events in the same loop [2](#0-1) . This is the exact push-payment failure mode from the report: one bad item in a batch reverts/drops the whole batch instead of processing the good items independently.

### Finding Description
This function backs both `AttachOutboundsToExistingUniversalTx` (used after successful payload execution to register outbounds for TSS pickup) and `CreateUniversalTxFromReceiptIfOutbound` (used from the EVM post-processing hook for any user-originated EVM transaction that calls the gateway) [3](#0-2) . A confirmed integration test shows that a single disabled-chain event causes the whole call to return an error: `err = hooks.PostTxProcessing(...); require.Error(t, err); require.Contains(t, err.Error(), "outbound is disabled")` [4](#0-3) .

The EVM side (`UniversalGatewayPC`) has already burned/locked the corresponding PRC20 amounts and emitted the `UniversalTxOutboundEvent` logs as part of the already-committed EVM state transition before this Go-side keeper logic runs. If an ordinary user's single transaction/payload triggers multiple gateway withdraw calls in one receipt — e.g. one to an enabled destination chain and one to a chain/token combination that is not yet configured or has outbound disabled — `BuildOutboundsFromReceipt` aborts on the bad event and returns an error for the *entire* receipt, meaning the valid outbound(s) are never appended to the UTX, never written to `PendingOutbounds`, and never picked up by Universal Validators for TSS signing/relay.

In the payload-execution flow, `AttachOutboundsToExistingUniversalTx`'s error is caught but not rolled back — it only records `u.RevertError` on the UTX and the function returns `nil` [5](#0-4) . This confirms the underlying EVM state (including the PRC20 burn that produced the event) is not rolled back merely because outbound attachment failed — the burn is already committed by the time `ExecutePayloadV2` returns a receipt.

### Impact Explanation
This falls squarely within "unauthorized burn" / "permanent freezing or loss of user or protocol-controlled funds" and "corruption of ... token mapping ... revert instructions" from the allowed impact gate. A user whose payload legitimately triggers multiple withdrawals in one transaction can have the *valid* withdrawal(s) silently and permanently dropped — no `OutboundTx` record, no `PendingOutbounds` entry, no revert path — while the PRC20 backing those funds was already burned by the gateway contract. There is no automatic remediation path analogous to `handleFailedInboundValidation`'s revert-outbound construction for this specific class of failure, since `BuildOutboundsFromReceipt` fails before any outbound (valid or invalid) is attached.

### Likelihood Explanation
Reachable by any unprivileged user who submits a `UniversalPayload` (or any EVM transaction) that triggers more than one gateway withdraw call in the same transaction, where at least one destination chain/token pair is disabled or unregistered. Whether an attacker can freely choose the failing branch's target chain/token depends on gateway contract-side validation (Solidity, out of this repo's Go scope) that I could not fully verify with the remaining budget — if the gateway contract itself already validates chain/token before emitting the event, this Go-side guard would be pure defense-in-depth and unreachable in practice. This is the key open uncertainty in this finding.

### Recommendation
Change `BuildOutboundsFromReceipt` to process each event independently: on a per-event validation failure (disabled chain, missing token config), skip/mark only that event (e.g., attach a synthetic failed/aborted outbound or emit a distinct alert event) rather than returning early and discarding all outbounds already built from prior events in the loop. Ensure any event that cannot produce a valid outbound gets some durable, queryable failure record so operators/users can detect and remediate stuck burned funds, mirroring the existing revert-outbound pattern used elsewhere in this module (e.g. `buildRevertOutbound`, `handleFailedInboundValidation`) [6](#0-5) .

### Proof of Concept
Not independently reproduced end-to-end in this pass (would require exercising the EVM `UniversalGatewayPC` contract directly, which is outside the Go index available here). The existing repo test demonstrates the core mechanic: a receipt containing outbound-triggering log(s) where one event's destination chain is outbound-disabled causes `BuildOutboundsFromReceipt`/`CreateUniversalTxFromReceiptIfOutbound` to return `"outbound is disabled for chain ..."` and abort [4](#0-3) . Extending that test with a receipt containing two `UniversalTxOutboundEvent` logs — one valid/enabled and one disabled — and asserting that the valid outbound is still attached would directly confirm or refute the "all outbounds dropped" behavior described here.

**Uncertainty flagged:** I was unable to confirm within the available tool budget (1) whether the Solidity-side `UniversalGatewayPC` contract already restricts which chain/token combinations can appear in emitted events (which would make this Go-side path unreachable by an attacker), and (2) whether `PostTxProcessing`'s returned error ultimately causes the whole EVM transaction (including the PRC20 burn) to revert at the ante/EVM-module level, which would eliminate the fund-loss impact entirely. Both points should be verified by a Devin session with full repository and contract-source access before treating this as a confirmed, exploitable vulnerability.

func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}

// CreateUniversalTxFromReceiptIfOutbound
// Creates a UniversalTx ONLY if outbound events exist in the receipt.
// Safe to call from ExecutePayload, EVM hooks
func (k Keeper) CreateUniversalTxFromReceiptIfOutbound(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalTxKey, err := k.BuildPcUniversalTxKey(ctx, pcTx)
	if err != nil {
		return errors.Wrap(err, "failed to create UniversalTx key")
	}

	outbounds, err := k.BuildOutboundsFromReceipt(ctx, universalTxKey, receipt)
	if err != nil {
		return err
	}

	if len(outbounds) == 0 {
		return nil
	}

	utx, err := k.CreateUniversalTxFromPCTx(ctx, pcTx)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}

package keeper

import (
	sdk "github.com/cosmos/cosmos-sdk/types"
	"github.com/pushchain/push-chain-node/x/uexecutor/types"
)

// handleFailedInboundValidation records a failed PCTx on the UTX and, for non-isCEA
// inbounds, schedules an INBOUND_REVERT outbound so the user's funds can be returned
// on the source chain. This is called when ValidateForExecution fails after the ballot
// has already been finalized and the UTX created.
func (k Keeper) handleFailedInboundValidation(sdkCtx sdk.Context, utx types.UniversalTx, validationErr error) error {
	inbound := utx.InboundTx
	_, ueModuleAddressStr := k.GetUeModuleAddress(sdkCtx)
	universalTxKey := utx.Id

	k.Logger().Warn("inbound validation failed",
		"utx_key", universalTxKey,
		"source_chain", inbound.SourceChain,
		"is_cea", inbound.IsCEA,
		"error", validationErr.Error(),
	)

	// Record the failed PCTx
	failedPcTx := types.PCTx{
		Sender:      ueModuleAddressStr,
		BlockHeight: uint64(sdkCtx.BlockHeight()),
		Status:      "FAILED",
		ErrorMsg:    validationErr.Error(),
	}

	if err := k.UpdateUniversalTx(sdkCtx, universalTxKey, func(utx *types.UniversalTx) error {
		utx.PcTx = append(utx.PcTx, &failedPcTx)
		return nil
	}); err != nil {
		return err
	}

	// For non-isCEA inbounds, schedule a revert outbound to return funds on source chain.
	// isCEA failures never create an INBOUND_REVERT outbound (consistent with execute_inbound_funds_and_payload.go).
	if !inbound.IsCEA {
		k.Logger().Info("scheduling inbound revert outbound",
			"utx_key", universalTxKey,
			"source_chain", inbound.SourceChain,
			"amount", inbound.Amount,
		)
		revertOutbound := k.buildRevertOutbound(sdkCtx, inbound)

		if attachErr := k.attachOutboundsToUtx(
			sdkCtx,
			universalTxKey,
			[]*types.OutboundTx{revertOutbound},
			validationErr.Error(),
		); attachErr != nil {
			// Store the revert failure reason on the UTX so it's queryable on-chain.
			// The FAILED PCTx is already recorded above — this adds why the revert wasn't attached.
			if storeErr := k.UpdateUniversalTx(sdkCtx, universalTxKey, func(utx *types.UniversalTx) error {
				utx.RevertError = attachErr.Error()
				return nil
			}); storeErr != nil {
				// UpdateUniversalTx only fails on infra issues — return to roll back and retry
				return storeErr
			}
		}
	}

	return nil
}
