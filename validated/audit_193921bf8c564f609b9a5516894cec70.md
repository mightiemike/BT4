This confirms the design has strict lamport-conservation invariants that make the described attack infeasible.

### Analysis

The premise misunderstands the SVM's rollback semantics. `collect_accounts_for_failed_tx` in `runtime/src/account_saver.rs` intentionally persists *only* the accounts referenced by `RollbackAccounts` (fee payer and/or nonce) when a transaction fails, discarding all other account mutations from the failed attempt — this is by design, not a bug. [1](#0-0) 

Two independent mechanisms prevent the described exploit:

1. **Per-instruction lamport conservation is enforced by the VM itself**, not by the commit path. `TransactionContext::pop()` checks `get_lamports_delta() != 0` at the end of every instruction and returns `InstructionError::UnbalancedInstruction` if any instruction created or destroyed lamports. [2](#0-1) 

Any "self-transfer duplicate" that fabricates lamports on the fee-payer alias in ix1 would itself fail with `UnbalancedInstruction` before the transaction could even proceed to the deliberately-failing ix2, since `add_lamports_delta` tracks every lamport change through `set_lamports`/`checked_add_lamports`/`checked_sub_lamports`. [3](#0-2) [4](#0-3) 

2. **Whole-transaction lamport conservation is checked in `execute_loaded_transaction`.** The sum of all account lamports is computed before execution (`lamports_before_tx`) and compared against the sum after execution; any mismatch produces `TransactionError::UnbalancedTransaction`. [5](#0-4) [6](#0-5) 

3. **Even setting aside lamport-fabrication feasibility, discarding non-rollback-account mutations on a failed transaction is the correct atomicity behavior**, not an inconsistency. The whole point of atomic execution is that a failing transaction's effects — other than fee collection and nonce advancement — must not be committed. This exact behavior is already covered by existing tests, e.g. `test_collect_accounts_to_store_skips_untouched_accounts` and `test_collect_accounts_for_failed_tx_rollback_separate_nonce_and_fee_payer`, which assert that only the rollback accounts are persisted and other writable accounts (even if touched) are rolled back to their pre-transaction state. [7](#0-6) [8](#0-7) 

The `test_one_tx_two_out_atomic_fail` test directly demonstrates this invariant on a real bank: when a multi-instruction transaction partially transfers lamports then fails, the mint (fee payer) balance is fully restored and the partial transfers are entirely discarded — no lamports are lost or gained. [9](#0-8) 

Since `RollbackAccounts::fee_payer()` in `svm/src/rollback_accounts.rs` (not `nonce_info.rs`, which only defines `NonceInfo`) is captured *before* execution begins (in `validate_transaction_fee_payer`, before the VM runs), it correctly represents the state that must be committed on failure — any writes made during execution to that same account via an alias reference are, by design, rolled back along with everything else in the failed transaction, and cannot desynchronize total lamport accounting because the VM would have already rejected an unbalanced instruction or transaction before commit is ever reached. [10](#0-9) [11](#0-10)

    /// Overwrites the number of lamports of this account (transaction wide)
    pub fn set_lamports(&mut self, lamports: u64) -> Result<(), InstructionError> {
        // An account not owned by the program cannot have its balance decrease
        if !self.is_owned_by_current_program() && lamports < self.get_lamports() {
            return Err(InstructionError::ExternalAccountLamportSpend);
        }
        // The balance of read-only may not change
        if !self.is_writable() {
            return Err(InstructionError::ReadonlyLamportChange);
        }
        // don't touch the account if the lamports do not change
        let old_lamports = self.get_lamports();
        if old_lamports == lamports {
            return Ok(());
        }

        let lamports_balance = (lamports as i128).saturating_sub(old_lamports as i128);
        self.transaction_context
            .accounts
            .add_lamports_delta(lamports_balance)?;

        self.touch()?;
        self.account.set_lamports(lamports);
        Ok(())
    }
