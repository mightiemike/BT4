### Title
Unbounded-recursion Stack-Overflow Denial-of-Service via Deeply Nested JSON in JSON-RPC Requests - ([File: chain/jsonrpc/src/lib.rs])

### Summary
The nearcore JSON-RPC server deserializes the entire body of any POST request to `/` into a `near_jsonrpc_primitives::message::Message`, whose `params` field is a raw `serde_json::Value` [1](#0-0)  parsed via `axum`'s `Json<Message>` extractor in `rpc_handler` [2](#0-1) . `serde_json::Value`'s deserializer recurses once per nesting level of arrays/objects in the input with no depth limit, which mirrors the Play Framework issue (CVE-2020-27196): a deeply nested JSON payload sent to any HTTP endpoint that eagerly parses JSON can exhaust the call stack and crash the process (`StackOverflowError`/SIGSEGV) before any validation of the payload's semantic content occurs.

### Finding Description
The RPC entry point deserializes the raw request body directly into the `Message` enum before any application-level bounds are applied:
- `Message` is `#[serde(untagged)]` over `Request`/`Response`/`Notification`/`Batch` [3](#0-2) .
- `Request.params` and `Notification.params` are typed as `serde_json::Value` with `#[serde(default, skip_serializing_if = "Value::is_null")]`, so any JSON shape is accepted at this stage [1](#0-0) .
- The HTTP handler `rpc_handler` uses `Json<Message>` as an Axum extractor argument, meaning deserialization of the full nested structure happens inside Axum's body-decoding path, before `JsonRpcHandler::process()` or any of nearcore's own semantic checks ever run [2](#0-1) .

`serde_json`'s `Value` deserialization is a recursive-descent implementation: each `[` or `{` encountered while decoding a `Value::Array`/`Value::Object` results in a nested call into the deserializer, growing the native call stack by one frame per nesting level. There is no `recursion_limit` configured anywhere in the codebase (confirmed by search — no `recursion_limit`/`set_recursion_limit` calls exist), and no explicit JSON-depth cap is applied before or during this parse. The RPC_ARCHITECTURE documentation only mentions a flat request body size limit (default 10MB) and CORS as the only middleware protections, with no mention of nesting-depth limits [4](#0-3) . A 10MB payload consisting almost entirely of repeated `[` characters (e.g. `"[[[[[...]]]]]"`) can encode on the order of several million nesting levels, which is far beyond what a typical thread stack (measured in KB–MB) can sustain during recursive descent, well before the 10MB size cap is reached.

This is architecturally analogous to the CVE-2020-27196 Play Framework issue: both eagerly and blindly parse a JSON payload according to its `Content-Type`/target type before any size- or depth-aware validation, and both use a recursive-descent JSON parser without a depth guard, allowing a single crafted request to trigger unbounded native-stack growth.

Note: the exact production request-body size limit (`DefaultBodyLimit`/`RequestBodyLimitLayer` configuration value) could not be conclusively located in this pass of the index; the RPC_ARCHITECTURE.md documentation cites a default of 10MB. If the actual configured/deployed limit differs, that would only change the required payload size, not the underlying architectural gap (absence of a JSON nesting-depth limit).

### Impact Explanation
The JSON-RPC HTTP port (default 3030) is reachable by any unauthenticated network caller — no signed transaction, account, or validator key is required. A stack overflow in the process handling the request typically results in the process being killed by the OS (SIGSEGV) or, depending on platform/allocator behavior, in memory corruption from stack-guard-page overrun before the signal is delivered. Because `JsonRpcHandler` runs inside the same node process as `ClientActor`/`ViewClientActor`/chunk production and other in-process actors, a crash of the RPC-serving process constitutes a remotely triggerable denial of service against the validator/RPC node — an unauthenticated, single-request halt of node operation, which meets the "transaction/request-triggered halt" impact bar.

### Likelihood Explanation
Likelihood is high for any node/RPC operator that exposes the default JSON-RPC HTTP endpoint to any caller (this is the standard nearcore RPC deployment model — it's the primary way wallets, explorers, and indexers interact with a node). Constructing a deeply nested JSON array/object of a few megabytes is trivial and requires no special privileges, keys, or protocol knowledge — only network access to the RPC port.

### Recommendation
- Configure `serde_json`'s deserializer with an explicit recursion/nesting-depth limit (or pre-scan/reject inputs whose bracket-nesting depth exceeds a small bound, e.g. via a streaming depth counter) before constructing `serde_json::Value` for both the top-level `Message` decode and any nested `params` value.
- Alternatively, replace the blind `Json<Message>` extractor with a bytes-limited + depth-limited custom deserialization path, and apply the depth check prior to routing/allocation.
- Add regression tests that POST deeply nested JSON payloads (e.g. 100k+ levels) to the JSON-RPC endpoint and assert a graceful `400 Bad Request`/parse error rather than a process crash.
- Audit other JSON parsing entry points that accept `serde_json::Value` untyped payloads (e.g., `chain/rosetta-rpc`, config file loaders) for the same missing depth bound, since they share the same underlying `serde_json` recursive-descent behavior.

### Proof of Concept
1. Start a nearcore node with the JSON-RPC HTTP server enabled (default port 3030).
2. Construct a payload of nested arrays sufficient to exceed the runtime's stack depth, e.g. (Python):
   ```python
   depth = 2_000_000
   payload = '{"jsonrpc":"2.0","id":1,"method":"query","params":' + '[' * depth + ']' * depth + '}'
   ```
3. Send it as the POST body to `http://<node>:3030/` with `Content-Type: application/json`:
   ```bash
   curl -X POST http://127.0.0.1:3030/ -H 'Content-Type: application/json' --data-binary @payload.json
   ```
4. Observe the node process aborting/crashing (stack overflow) while decoding the body into `Json<Message>` in `rpc_handler`, before any RPC method dispatch or validation logic executes.

    /// An RPC request.
    Request(Request),
    /// A response to a Request.
    Response(Response),
    /// A notification.
    Notification(Notification),
    /// A batch of more requests or responses.
    ///
    /// The protocol allows bundling multiple requests, notifications or responses to a single
    /// message.
    ///
    /// This variant has no direct constructor and is expected to be constructed manually.
    Batch(Vec<Message>),
    /// An unmatched sub entry in a `Batch`.
    ///
    /// When there's a `Batch` and an element doesn't conform to the JSONRPC 2.0 format, that one
    /// is represented by this. This is never produced as a top-level value when parsing, the
    /// `Err(Broken::Unmatched)` is used instead. It is not possible to serialize.
    #[serde(skip_serializing)]
    UnmatchedSub(Value),
}
