### Title
Unbounded per-address delegation index growth causes unbounded RPC-triggered iteration/sort - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegatedResourceAccountIndexStore` records, per account, every distinct counterparty address that account has delegated bandwidth/energy resources to (or received delegation from). Unlike votes, which are capped by `MAX_VOTE_NUMBER` [1](#0-0) , there is no cap on the number of distinct delegation counterparties an account may accumulate. Every counterparty relationship is a separate DB key, and reads of this index (used both internally by actuators and exposed via public wallet/RPC/HTTP endpoints) scan and sort the full, attacker-growable set.

### Finding Description
The legacy (non-optimized) delegation-index path appends every new distinct receiver/sender to a repeated field with only a linear `contains()` de-duplication check and no upper bound: [2](#0-1) 

The V2 (optimized) path stores each relationship as an independent prefixed key (`V2_FROM_PREFIX`/`V2_TO_PREFIX` concatenated with the two addresses), which similarly has no cap on the number of distinct relationships per address: [3](#0-2) 

Reading this index back — used by `getIndex`/`getV2Index` and reachable from public wallet/RPC/HTTP query methods — performs a full prefix scan of the underlying store followed by an in-memory sort over all matching entries, with no limit on result size: [4](#0-3) 

This is structurally the same bug class as `Controller.calcAccountEquity`: the number of "positions" (here, distinct delegation counterparties for one address) is bounded only by how many distinct addresses an attacker chooses to interact with, not by any protocol-enforced cap, and every subsequent read of that address's index must iterate/sort the entire, attacker-controlled set.

### Impact Explanation
An attacker who repeatedly issues cheap `FreezeBalance`/`DelegateResource` transactions to many distinct throwaway receiver addresses (each transaction only needs to move a minimal frozen balance) can grow their own account's (or a victim's, since delegation FROM many distinct senders is recorded on the receiver's index too) `DelegatedResourceAccountIndex` set to an arbitrarily large size. Every later query of that address's delegation index — via `wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` and their HTTP servlet/gRPC equivalents — then performs an unbounded prefix scan plus sort proportional to the number of accumulated relationships. Because this is exposed on public-facing RPC/HTTP query endpoints, repeated queries against such an inflated address can consume disproportionate node CPU/I/O, degrading node responsiveness (a resource-exhaustion/DoS vector against the query API), though it does not directly corrupt consensus state or funds.

### Likelihood Explanation
Medium: creating many distinct delegation relationships is cheap (each such transaction only costs the normal freeze/delegate fee and a small locked balance, no larger scaling cost is imposed), and the query endpoints are unauthenticated/public. However, actual impact severity depends on how many such relationships are practically achievable within reasonable cost/time and on the underlying RocksDB prefix-scan performance, which I could not fully quantify from static review alone.

### Recommendation
Apply the same mitigation pattern already used for votes (`MAX_VOTE_NUMBER` cap in `VoteWitnessActuator`) to delegation relationships: enforce a hard cap on the number of distinct `from`/`to` counterparties tracked per address in `DelegatedResourceAccountIndexStore`, reject new delegations once the cap is reached (or require replacing/expiring old ones), and/or bound `prefixQuery` results returned to RPC/HTTP callers with pagination limits so a single query cannot force an unbounded scan/sort.

### Proof of Concept
Not independently executed; based on code inspection: (1) call `DelegateResourceContract`/`FreezeBalanceContract` repeatedly from one owner address, each time targeting a freshly generated, distinct receiver address with the legacy non-optimized index path, growing `ownerIndexCapsule.getToAccountsList()` unboundedly as shown in the actuator test using 100+ receivers [5](#0-4) ; (2) repeat with the V2 path to grow the prefix-keyed relationship set; (3) invoke `getDelegatedResourceAccountIndexV2` against that address via RPC/HTTP and observe scan/sort cost scaling with the number of accumulated relationships.

  public DelegatedResourceAccountIndexCapsule getIndex(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = get(address);
    if (indexCapsule != null) {
      return indexCapsule;
    }
    return getWithPrefix(FROM_PREFIX, TO_PREFIX, address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
