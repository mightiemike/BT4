### Title
`accrue` pause pass-through returns stale index/liquidity-index instead of reverting, letting borrow/repay/deposit/redeem proceed on stale interest accounting - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) implements `accrue` so that when the `accrue` pause flag is set, it does not revert - it silently returns the last-stored `index`/`lindex` instead of computing the fresh, up-to-date values [1](#0-0) . Every state-mutating vault entrypoint (`system-borrow`, `system-repay`, `deposit`, `redeem`, flashloan, etc.) calls `(try! (accrue))` and then unconditionally proceeds to update `principal-scaled`, `total-borrowed`, mint/burn shares, and transfer funds using whatever index `accrue` handed back [2](#0-1) . Because `try!` only unwraps an `(ok ...)` response and the paused branch of `accrue` also returns `(ok ...)`, the pause is invisible to every caller: the call succeeds instead of reverting, and business logic keeps running against a stale index.

### Finding Description
`accrue` is structured as a pause check that feeds directly into the interest-accounting return value rather than gating the call:

```clarity
(if (get accrue states)
    ;; PAUSED: Pass-through without reverting
    (ok { index: idx, lindex: lidx })
    ;; NOT PAUSED: Normal accrual logic
    (let (...) ... (ok { index: next, lindex: nliq })))
``` [3](#0-2) 

This is the exact "pause that passes through instead of reverting" pattern. The comment even documents the intent explicitly ("PAUSED: Pass-through without reverting").

`system-borrow` (and equivalently `system-repay`, `deposit`, `redeem`) calls `accrue` via `try!` and then immediately reads `principal-scaled`, `index`, `total-debt`, `available-assets` from storage and mutates them, all without any check for whether accrual actually happened:

```clarity
(define-public (system-borrow (amount uint) (receiver principal))
  (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (CAP-DEBT (var-get cap-debt))
      (available-assets (get-available-assets))
      (scaled-principal (var-get principal-scaled))
      (idx (var-get index))
      (debt (total-debt))
      (scaled-amount (mul-div-up amount INDEX-PRECISION idx))
      (updated-scaled-principal (+ scaled-principal scaled-amount)))
    (try! (check-caller-auth))
    (asserts! (not (get borrow states)) ERR-PAUSED)
    ...
    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed (+ (var-get total-borrowed) amount))
    (try! (send-underlying amount receiver)) ...))
``` [2](#0-1) 

Note that `states` for the operation-specific pause (`borrow`, `repay`, `deposit`, `redeem`) is captured *before* `accrue` runs and is only used to assert that specific operation isn't paused - it never checks the `accrue` pause flag itself. Since `accrue`'s own pause branch returns `(ok ...)` (never an error), `try!` on `(accrue)` never fails when accrual is paused; execution simply continues with `idx`/`lidx` as they were last persisted, potentially many blocks/timestamps stale.

The `market.clar` layer that calls into these vaults (via `accrue-and-cache`, `vault-accrue`, health checks, liquidation, notional evaluation) also assumes `accrue-and-cache`/`vault-accrue` return current indexes for the same-block computation [4](#0-3) ; if a vault operator pauses `accrue` for one vault while other vault interactions in the same or later blocks continue, the market's health/liquidation math for zTokens backed by that vault silently uses the stale liquidity/borrow index rather than failing loudly.

### Impact Explanation
This lands on **temporary freezing/mis-accounting of funds**: while `accrue` is paused, every borrow, repay, deposit, and redemption on the affected vault is executed against a frozen interest index instead of being blocked. This means:
- Debt/interest that should have accrued is not reflected, so borrowers can withdraw/borrow at a stale (lower) cost, and depositors' shares are minted/burned at a stale exchange rate, causing value to leak from suppliers to whoever transacts during the pause window.
- Because the pause was clearly intended to halt this exact accounting path (as the comment states), and it instead lets it proceed with wrong numbers, it also undermines any operational safety pause the DAO relies on during an incident (e.g., an oracle glitch or accounting bug requiring accrual to be frozen) - operations keep mutating state instead of being blocked, defeating the purpose of pausing `accrue`.

### Likelihood Explanation
This triggers deterministically any time the DAO sets `accrue: true` in `pause-states` (a normal operational lever already implemented for incident response) and any user calls `deposit`, `redeem`, `system-borrow`, or `system-repay` afterward. No attacker collusion or special conditions are required - it is a single-transaction consequence of using the pause exactly as intended.

### Recommendation
Change the paused branch of `accrue` to return an error (e.g., `ERR-PAUSED`) instead of `(ok { index: idx, lindex: lidx })`, so that `try!` in every caller (`system-borrow`, `system-repay`, `deposit`, `redeem`, flashloan paths) correctly reverts the whole operation while accrual is paused, consistent with the pause's documented intent.

### Proof of Concept
1. DAO (or authorized admin) calls `set-pause-states` (or equivalent) to set `accrue: true` on `v0-vault-stx` (or any vault).
2. A user calls `system-borrow` (via `market.clar` `borrow`). Inside, `(try! (accrue))` is evaluated; because `accrue` is paused it returns `(ok {index: idx, lindex: lidx})` with the old, un-refreshed index rather than erroring [1](#0-0) .
3. `try!` succeeds (since the response is `ok`), so execution proceeds: `idx` (stale) is read from storage, `scaled-amount`/`updated-scaled-principal`/`debt` are computed off that stale index, and `var-set principal-scaled`, `var-set total-borrowed`, and the underlying token transfer all execute normally [2](#0-1) .
4. The borrow transaction succeeds despite `accrue` being paused, and all subsequent debt/interest math for that user is computed on the stale index - exactly the operation the pause was meant to block.
