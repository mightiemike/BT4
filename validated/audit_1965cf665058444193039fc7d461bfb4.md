### Title
Deposit can silently absorb user funds when `convert-to-shares-preview` rounds down to zero shares - ([File: mainnet/contracts/vault/v0-vault-usdc.clar], applies identically to all six vault contracts)

### Summary
The `deposit` entry point in every Zest vault (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`, and their `local-testing` twins) computes the share amount to mint (`inkind`) via `convert-to-shares-preview`, but never asserts that this value is non-zero before pulling in the underlying tokens and minting shares. This mirrors the referenced ERC5095 `mint` bug: a preview/conversion function can legitimately return `0` for a non-zero input, and the code proceeds to perform a real value transfer keyed off that zero result.

### Finding Description
In every vault's `deposit`, the sequence is: [1](#0-0) 

```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    ...
```

The guard list checks `amount > 0` (the *input*) but has no `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` check on the *computed output* `inkind`. Compare this with `redeem` in the very same contracts, which explicitly guards the analogous computed value: [2](#0-1) 

```
(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    ...
    (inkind (convert-to-assets-preview amount)))

  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  ...
```

`redeem` explicitly rejects a zero-valued conversion result with `ERR-OUTPUT-ZERO`, but `deposit` has no equivalent check for its own converted value `inkind`. If `convert-to-shares-preview amount` rounds down to `0` (a normal integer-division outcome once the exchange rate/index has inflated enough relative to a small `amount`, or once `min-out` is supplied as `0`), `deposit` still:
1. Passes all its asserts (since `inkind >= min-out` trivially holds when `min-out = 0`, and `amount > 0` still holds).
2. Executes `(try! (receive-underlying amount account))`, pulling the user's real underlying tokens into the vault.
3. Executes `(try! (ft-mint? zft inkind recipient))`, minting `0` zTokens to the depositor.
4. Executes `(var-set assets (+ current-assets amount))`, crediting the deposited amount to the vault's total assets pool — which backs the *existing* shareholders' zTokens, not the depositor's.

The depositor's `amount` is transferred out of their wallet with no compensating shares minted, and the value is absorbed into the shared asset pool, redistributing it to existing zToken holders.

### Impact Explanation
This is a direct, single-transaction loss of user funds: the depositor's underlying tokens leave their control and enter the vault's tracked `assets`, but they receive no `zft` claim on them. There is no way for the depositor to recover this value — it silently boosts the redemption value for every other existing zToken holder. This satisfies the "theft of user funds at rest or in motion" / "permanent freezing of funds" impact class, since the specific depositor's contributed capital becomes permanently unclaimable by them.

### Likelihood Explanation
Reachable in a single transaction by any user calling `deposit` with `min-out = 0` (or any `min-out` low enough to still pass) at a moment where the vault's share/asset exchange rate (driven by `index`/`lindex`, accrued via `accrue`) causes `convert-to-shares-preview` to round `amount` down to `0` shares. This requires no privileged access, no DAO action, and no oracle manipulation — only a sufficiently small `amount` relative to the current exchange rate, which is a state the interest-accrual mechanism (`accrue`) naturally drives toward over time as `index`/`lindex` grow.

### Recommendation
Add `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` to `deposit` in all six vault contracts, mirroring the existing check already present in `redeem`, so that a zero-share conversion reverts the entire deposit instead of silently transferring underlying tokens with no compensating mint.

### Proof of Concept
1. Vault accrues interest over time so that `index`/`lindex` grow, raising the assets-per-share exchange rate used inside `convert-to-shares-preview`.
2. A user calls `deposit` with a small `amount` (e.g. `amount = 1`) and `min-out = 0`.
3. `convert-to-shares-preview amount` computes `inkind = 0` due to integer-division rounding.
4. All asserts pass: `amount > 0` ✓, `inkind (0) >= min-out (0)` ✓, cap not exceeded ✓.
5. `receive-underlying` transfers the user's `1` unit of underlying into the vault; `ft-mint?` mints `0` zTokens to the user; `assets` is incremented by `1`.
6. The user has permanently lost their deposited unit with no corresponding claim, while all other zToken holders' redeemable value increases proportionally. [1](#0-0) [2](#0-1)
