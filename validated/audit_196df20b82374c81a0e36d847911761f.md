### Title
Replay-verification skips checkpoint-hash validation, letting a divergent state root pass as verified - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant check used by replay/verification tooling to confirm that a freshly re-executed transaction output matches the authenticated `TransactionInfo` recorded on-chain (and proven into the transaction accumulator). It validates status, gas used, write-set hash, and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually commit to the state root / position-state root produced by execution. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (hash of the re-executed write set) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but the function ends with an explicit TODO admitting the gap:

```

// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is the sole per-transaction integrity check used by `ChunkExecutorInner::verify_execution`, which re-executes historical transactions with the VM and compares the result to the persisted, accumulator-authenticated `TransactionInfo` list: [3](#0-2) 

This `verify_execution` path backs `TransactionReplayer::enqueue_chunks`, which is driven by:
- `storage/backup/backup-cli`'s transaction restore/replay flow (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`), used when restoring/replaying an archive against local execution, and
- `storage/db-tool/src/replay_on_archive.rs`, the dedicated tool for replaying an archived chain and confirming local execution matches the authenticated history.

Both consumers rely on `ensure_match_transaction_info` as the authority for "does my local execution match the ledger." Because the function never compares the recomputed state-checkpoint root (Sparse Merkle Tree root over the resource state) or the newer hot-state/position-state checkpoint hashes against the corresponding fields carried in the accumulator-proven `TransactionInfo`, a state root divergence — caused by a VM non-determinism bug, an execution/config change, or corrupted/malicious archive data feeding into replay — is silently accepted as "verified" as long as write-set bytes, events, gas, and status happen to match.

### Impact Explanation
This breaks the state-commitment integrity invariant required by the audit gate: "Wrong accumulator root … or state proof accepted as valid" and "hard-fork-only divergence during commit, replay, restore, or proof verification." The whole purpose of `replay_on_archive` / backup replay-verification is to catch exactly this class of divergence (e.g. after a protocol upgrade, to confirm deterministic replay of history, or to detect a hard fork). With the state-checkpoint hash comparison omitted, the tool can report a clean, "verified" replay even though the locally computed Sparse Merkle Tree state root — and therefore the entire resulting global state — differs from the one actually committed and cryptographically bound into the ledger's `TransactionInfo`/accumulator. This is a direct proof/authenticated-response integrity gap: it undermines confidence in the very tool operators and auditors use to confirm mainnet history/replay integrity, and it means state-root corruption (whether from a determinism bug, storage bug, or a compromised archive source) would not be surfaced by verification.

### Likelihood Explanation
The gap is deterministic and always present when replay-verification paths are exercised (`replay_on_archive`, backup-cli replay with verification, `TransactionReplayer::enqueue_chunks`), rather than probabilistic. It requires an actual pre-existing state-divergence trigger to be *masked* (e.g. a real determinism bug or corrupted archive), so it is a "detection gap" rather than a way to directly corrupt consensus-committed state; it does not by itself let an attacker forge a valid state proof to a live full node/API consumer. That keeps likelihood at operational/tooling risk rather than a live consensus-breaking exploit, but the invariant is explicitly and permanently broken in shipped code (confirmed by the developers' own TODO), not a hypothetical.

### Recommendation
In `ensure_match_transaction_info` (`types/src/transaction/mod.rs`), after the existing event-root check, recompute the state checkpoint root (and, when applicable, hot-state/position-state checkpoint roots) from the post-execution state and assert equality against `txn_info.state_checkpoint_hash()` / `txn_info.hot_state_checkpoint_hash()` / `txn_info.position_state_checkpoint_hash()` whenever those fields are `Some` on the expected `TransactionInfo`. Until that is implemented, `replay_on_archive` and backup-replay verification should surface an explicit warning that checkpoint/state-root equivalence is *not* verified, so operators do not treat a "successful replay" as proof that the state root matches.

### Proof of Concept
Not directly exploitable via a single reproducible transaction — the flaw is a missing assertion, provable by code inspection and call-graph tracing:
1. `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) checks status, gas, write-set hash, and event root, then returns `Ok(())` without checking `state_checkpoint_hash`, as documented by the inline TODO at lines 2197-2203.
2. `ChunkExecutorInner::verify_execution` (`execution/executor/src/chunk_executor/mod.rs:684-706`) calls this function as the only per-transaction correctness check when re-executing a chunk during replay verification.
3. This path is reached from `TransactionReplayer::enqueue_chunks`/`commit`, used by `storage/backup/backup-cli`'s transaction restore (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`) and by `storage/db-tool/src/replay_on_archive.rs`.
4. Therefore, feeding a chunk whose re-executed write set/events/gas/status happen to match the persisted `TransactionInfo` but whose resulting state (e.g., due to a state-store bug or altered execution semantics) produces a different Sparse Merkle root will pass `verify_execution` and be reported as a successful, verified replay, even though the actual state root diverges from the one authenticated in the ledger's accumulator-proven `TransactionInfo`.

Note: I could not fully trace every downstream consumer of `TransactionReplayer` (e.g. `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) within the available search budget; those additional call sites likely share the same gap since they call the same `ensure_match_transaction_info` function, but I was unable to inspect their full context to confirm identical usage semantics.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
