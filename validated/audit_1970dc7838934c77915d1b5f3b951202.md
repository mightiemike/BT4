## Finding: Attacker-Controlled `TxType` Downgrades Reorg-Confirmation Depth for Real Value-Moving Inbound Deposits

### Title
Attacker-chosen inbound `TxType` (GAS / GAS_AND_PAYLOAD) forces FAST confirmation depth on fund-moving deposits, weakening reorg protection - (File: universalClient/chains/evm/event_parser.go)

### Summary
`finalizeEvent` in the EVM event parser assigns `store.ConfirmationFast` purely based on the raw `TxType` word decoded from event log data, which is fully attacker-controlled input in the gateway-contract call that emits the event, rather than from the admin-configured per-chain/per-method `ConfirmationType` stored in the on-chain registry (`GatewayMethods.confirmation_type` / `VaultMethods.confirmation_type`). [1](#0-0) [2](#0-1) 

### Finding Description
The `TxType` word is read directly out of raw log data (Word 4 of the `sendFunds`/`executeUniversalTx` event payload), a value the transaction sender fully controls when constructing the call to the gateway contract: [3](#0-2) 

`finalizeEvent` then sets `ConfirmationFast` whenever this attacker-chosen value is `0` or `1` (Solidity-encoded `GAS` / `GAS_AND_PAYLOAD`), and `ConfirmationStandard` otherwise: [4](#0-3) 

This confirmation type is later consumed by `EventConfirmer.getRequiredConfirmations`, which maps `ConfirmationFast` to a materially lower confirmation depth (default 5) versus `ConfirmationStandard` (default 12): [5](#0-4) 

Critically, `GAS` and `GAS_AND_PAYLOAD` are not "no value at risk" transaction types — per the module's own documentation, `GAS` mints native PC to the recipient as a gas top-up and `GAS_AND_PAYLOAD` does the same plus executes a payload, both driven by the attacker-supplied `Amount` field with no smaller cap than `FUNDS`: [6](#0-5) [7](#0-6) 

The only enforced constraint is that `Amount` be non-zero for `GAS`/`FUNDS` (no upper bound), so an attacker can move an arbitrarily large native-token amount labeled as `GAS`: [8](#0-7) 

Thus, by simply choosing `TxType = GAS` (or `GAS_AND_PAYLOAD`) instead of `FUNDS` for an otherwise identical large-value deposit, an unprivileged sender causes the universal client to require only ~5 confirmations instead of ~12 before voting the inbound event as `CONFIRMED`, even though the underlying mint of native PC is economically equivalent to a `FUNDS` deposit and carries the same reorg risk on the source chain.

### Impact Explanation
If the source chain experiences a reorg beyond the FAST threshold but within the STANDARD threshold (a routine occurrence on many EVM chains, especially L2s/testnets with probabilistic finality), a `GAS`/`GAS_AND_PAYLOAD` event that the confirmer already voted `CONFIRMED` — and that Universal Validators then finalize and mint PC for — can be reorganized away on the source chain. The minted native PC (and any payload execution funded by it) is not backed by a real, final source-chain transaction, resulting in unauthorized mint / unbacked value creation on Push Chain reachable purely through ordinary deposit flow (choice of `TxType` in calldata), with no privileged actor required.

### Likelihood Explanation
Exploitation requires only that the attacker send an ordinary gateway transaction with `TxType = 0` or `1` and a large `Amount`, and that the source chain undergo a confirmation-depth-appropriate reorg (attacker can also actively induce this on lower-security or attacker-influenced source chains). No collusion with validators, UVs, TSS signers, or admins is needed — the confirmation-type assignment logic itself is the flaw.

### Recommendation
Do not derive `ConfirmationType` from the attacker-supplied `TxType` field. Use the admin-configured, per-chain/per-method `ConfirmationType` already modeled in the registry (`GatewayMethods.confirmation_type`, `VaultMethods.confirmation_type`, `BlockConfirmation.fast_inbound/standard_inbound`), so confirmation depth reflects actual chain reorg risk and value semantics rather than a value the sender controls.

### Proof of Concept
1. Craft a `sendFunds`/`executeUniversalTx` call to the gateway contract with `txType = 0` (`GAS`) and a large `amount` (e.g., equivalent to a `FUNDS` deposit).
2. `parseUniversalTx` → `finalizeEvent` sets `event.ConfirmationType = store.ConfirmationFast` purely because `TxType == 0`. [9](#0-8) 
3. `EventConfirmer.processPendingEvents` promotes the event to `CONFIRMED` after only `fastConfirmations` (default 5) blocks instead of `standardConfirmations` (default 12). [10](#0-9) 
4. UVs vote and finalize the inbound; `ExecuteInboundGas` mints PC to the recipient based on the attacker-chosen `Amount`. [11](#0-10) 
5. If the source-chain transaction is reorged out between confirmation depth 5 and 12, the minted PC has no backing deposit — demonstrable via a Go unit test asserting `getRequiredConfirmations(store.ConfirmationFast) < standardConfirmations` for a `TxType`/`Amount` combination that triggers real fund minting.

```go
// finalizeEvent marshals the payload and sets confirmation type on the event.
func finalizeEvent(event *store.Event, payload *common.UniversalTx, logger zerolog.Logger) {
	if b, err := json.Marshal(payload); err == nil {
		event.EventData = b
	} else {
		logger.Warn().Err(err).Msg("failed to marshal universal tx payload")
	}

	if payload.TxType == 0 || payload.TxType == 1 {
		event.ConfirmationType = store.ConfirmationFast
	} else {
		event.ConfirmationType = store.ConfirmationStandard
	}
}
```

```go
// getRequiredConfirmations returns the required number of confirmations based on confirmation type
func (ec *EventConfirmer) getRequiredConfirmations(confirmationType string) uint64 {
	switch confirmationType {
	case store.ConfirmationFast:
		if ec.fastConfirmations >= 0 {
			return ec.fastConfirmations
		}
		return 5
	case store.ConfirmationStandard:
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	default:
		// Default to standard if unknown
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	}
```

```go
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {

	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)

		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")

		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
```
