### Title
`sanitizeHost` throws an uncaught native `TypeError` instead of `InvalidHostError` for base64 input that decodes to an invalid URL authority - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
`sanitizeHost` calls `new URL(\`https://${decodeHost(sanitizedHost)}\`)` immediately after confirming the input only matches the base64 character set regex, without validating that the decoded value forms a syntactically valid host/authority. A crafted base64 string that decodes to something like `:::garbage:::` causes the native `URL` constructor to throw a `TypeError` ("Invalid URL") that is never caught, rather than being handled and converted into the library's typed `InvalidHostError` or returning `null`.

### Finding Description
In `sanitizeHost` (`packages/apps/shopify-api/lib/utils/shop-validator.ts`, function starting line 52), the flow is: [1](#0-0) 
1. `host` is checked against `base64regex` — this only verifies the character set (`[0-9a-zA-Z+/]+={0,2}`), not that the decoded content is a valid hostname.
2. If it matches, `decodeHost` (a thin wrapper around `atob`) decodes it, and the result is fed directly into `new URL('https://' + decoded)` with no try/catch.

Since arbitrary printable bytes (e.g., `:::garbage:::`) are valid base64-alphabet input after encoding, an attacker can produce a `host` query-string value that passes the base64 regex but decodes into a string that the WHATWG `URL` parser rejects as an invalid authority (e.g., multiple colons outside IPv6 brackets), causing `URL` to throw a native `TypeError`, not the library's `InvalidHostError`.

This function is invoked directly, without any wrapping try/catch, from several code paths reachable by an unauthenticated client supplying the `host` query parameter, including:
- `buildEmbeddedAppUrl` in `packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts` (`sanitizeHost(config)(host, true)` at line 48), used by `getEmbeddedAppUrl`. [2](#0-1) 
- `redirectToShopifyOrAppRoot` in `packages/apps/shopify-app-express/src/middlewares/redirect-to-shopify-or-app-root.ts`, which calls `api.utils.sanitizeHost(req.query.host as string)!` unguarded. [3](#0-2) 
- `clientSideRedirect`/`redirectToAuth` in `packages/apps/shopify-app-express/src/redirect-to-auth.ts` (line 37), reachable from the OAuth begin flow triggered by unauthenticated GET requests. [4](#0-3) 
- `validateShopAndHostParams` in both `shopify-app-remix` and `shopify-app-react-router` packages, called on every embedded-admin authentication request. [5](#0-4) 

None of these call sites wrap `sanitizeHost` in a try/catch that would convert a native `TypeError` into a controlled HTTP response — they only handle the expected `InvalidHostError`/`null`-return contract, not an arbitrary thrown error from the `URL` constructor. The existing unit tests (`shop-validator.test.ts`) only cover base64 strings that decode to syntactically valid hostnames that merely fail the domain allow-list regex (e.g., `notshopify.com`), so this crash path is untested.

### Impact Explanation
This is a denial-of-service condition in the authentication/embedded-app entry points: an unauthenticated request to any route that calls `sanitizeHost` with attacker-controlled `host` (login redirect, embedded app URL builder, admin authentication middleware in Express/Remix/React Router adapters) can throw an unhandled exception instead of returning a clean 4xx response. Depending on the host framework's global error handling, this can result in an unhandled promise rejection / process crash for some server configurations, or at minimum an uncontrolled 500 response instead of the intended validation-error path — matching the "DoS in an authentication handler" impact class called out in scope.

### Likelihood Explanation
Trivially reachable: the attacker only needs to send an HTTP GET request with a `host` query parameter whose base64 decoding forms an invalid URL authority (e.g., base64 of `":::garbage:::"`). No authentication, secrets, or special configuration are required — every embedded app using the default OAuth begin/callback or embedded-app-url flow is affected. It is fully repeatable and deterministic.

### Recommendation
Wrap the `new URL(...)` call in `sanitizeHost` in a try/catch, and on failure either return `null` or throw `InvalidHostError` (consistent with `throwOnInvalid`), matching the same fail-safe pattern used elsewhere in the validator instead of letting the native `URL` constructor's exception propagate uncaught.

```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost does not throw an unhandled native TypeError for malformed decoded host', () => {
  const shopify = shopifyApi(testConfig());

  const malformedBase64Host = Buffer.from(':::garbage:::').toString('base64');

  // Expected: returns null (or throws typed InvalidHostError when throwOnInvalid=true)
  expect(() => shopify.utils.sanitizeHost(malformedBase64Host)).not.toThrow();
  expect(shopify.utils.sanitizeHost(malformedBase64Host)).toBeNull();
});
```
