PoisonMicroblock accepts a signature-malleable twin of a single genuinely-signed microblock header as "proof" of double-signing, letting an attacker steal a miner's slashing commission - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`check_microblock_header_signer` (in `stackslib/src/chainstate/stacks/db/transactions.rs`, called from `handle_poison_microblock`) recovers a pubkey hash from each of the two supplied `StacksMicroblockHeader`s independently via `check_recover_pubkey`, which itself uses `recover_to_pubkey_without_validating_low_s` [2](#0-1) . Because high-S ("malleable") signatures are accepted, an attacker can take a single microblock header that a miner genuinely signed once, flip `(s, recovery_id)` to the standard ECDSA-malleable complement `(n-s, 1-v)` without knowing the private key, and submit `(header_original, header_malleable_twin)` as a `PoisonMicroblock` transaction. This passes both the codec-level fork-shape check and `check_microblock_header_signer`, causing the chain to treat a miner who never double-signed as if they had, and to pay the attacker the reporter's commission.

### Finding Description
The equality that should hold is: *reward/commission paid to a poison-microblock reporter == proof that the miner produced two distinct microblock headers with the same `sequence`/`prev_block` (an actual equivocation)*.

Trace of the exact path:
1. `StacksMicroblockHeader::sign` computes the signature over `Sha512Trunc256Sum::from_data(serialize(self, empty_sig=true))`, i.e. over `version || sequence || prev_block || tx_merkle_root` with the signature field zeroed [3](#0-2) .
2. `check_recover_pubkey` recomputes that same digest (again zeroing the signature field) and recovers a public key using `StacksPublicKey::recover_to_pubkey_without_validating_low_s`, explicitly *skipping* the low-S canonicalization check [2](#0-1) [4](#0-3) .
3. Standard ECDSA malleability: given any valid signature `(r, s, v)` over a message, `(r, n-s mod n, 1-v)` is *also* a valid signature over the exact same message and recovers to the exact same public key — this requires no knowledge of the private key, only public arithmetic. The repo's own test `test_with_negated_s` demonstrates and asserts this property [5](#0-4) .
4. The wire-level `consensus_deserialize` for `PoisonMicroblock` only requires `h1 != h2` (as full structs, including the `signature` field) and that `sequence`/`prev_block` are consistent with a fork shape [1](#0-0) . It never checks that the headers differ in `tx_merkle_root`/content — differing only in `signature` bytes is sufficient to pass.
5. `check_microblock_header_signer` in `stackslib/src/chainstate/stacks/db/transactions.rs` calls `check_recover_pubkey` on each header independently and only compares the two derived pubkey hashes for equality — it never checks that the headers are semantically distinct microblocks (distinct `tx_merkle_root`) nor that the two signatures are cryptographically independent proofs [6](#0-5) .

Attacker's exact input: take one microblock header `H` that the target miner genuinely signed and broadcast once (a completely normal, honest mining action). Compute `H' = H` with `signature = (r, n-s, 1-v)`. Submit `TransactionPayload::PoisonMicroblock(H, H')`. Since `H.sequence == H'.sequence`, `H.prev_block == H'.prev_block`, and `H != H'` (differ only in signature bytes), the transaction passes deserialization. `check_microblock_header_signer` recovers the same `Hash160` for both (since both signatures are valid over the identical digest and recover to the same public key), so `handle_poison_microblock` proceeds as if it found a genuine equivocation, looks up `get_microblock_pubkey_hash_height` for that (legitimately registered) pubkey hash, and records the attacker as reporter via `insert_microblock_poison`, entitling them to the commission that should only go to someone who caught a real double-signing miner.

Why existing guards fail: the mempool-level check in `blocks.rs` (`mempool_storage`/`will_admit_mempool_tx`) applies the same insufficient checks (`sequence`/`prev_block` match + `check_recover_pubkey` equality) [7](#0-6) , and none of these guards ever verify that the two signatures are *independent* (i.e., that they don't reduce to the same canonical low-S signature via the well-known `(r,s,v) <-> (r, n-s, 1-v)` malleability relation).

### Impact Explanation
This is a block-reward/commission theft: an honest miner who signed exactly one microblock is falsely reported as an equivocator, and their coinbase/commission-affected reward is redirected to an unrelated attacker who never observed a real fork and never needed a minority/majority position — only public knowledge of one already-broadcast signed header. This matches the "reward paid to the wrong party" / reward mis-payment category, and because the false accusation can be manufactured entirely offline and injected by any account able to submit transactions, this is directly reachable by an unprivileged, minority-stake attacker.

### Likelihood Explanation
Preconditions: the attacker needs (a) to observe any one legitimately signed microblock header from a target miner (trivially available — it's broadcast on the P2P network and stored in staging tables), and (b) to be able to submit an ordinary Stacks transaction (the reporter's account only needs to pay the tx fee, no stake, no privileged role, no BTC spend required beyond ordinary tx fees). The exploit is purely a public-key arithmetic operation (negate `s` mod `n`, flip the recovery bit) requiring no cryptographic secrets. It is fully repeatable against any miner who has ever produced a microblock, at negligible cost, by any unprivileged participant.

### Recommendation
- In `check_recover_pubkey` (and everywhere microblock header signatures are recovered for poison-microblock validation), enforce low-S/canonical signature form (use `recover_to_pubkey` instead of `recover_to_pubkey_without_validating_low_s`), so that only one canonical signature per message is ever considered valid.
- Additionally, `check_microblock_header_signer` / the `PoisonMicroblock` codec check should require that the two headers differ in `tx_merkle_root` (i.e., represent genuinely different microblock contents at the same sequence/parent), not merely differ in raw struct equality (which can be satisfied by a malleable signature substitution alone).
