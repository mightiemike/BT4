Based on my investigation, here is the mapped finding, focused on the `app/ante/account_init_decorator.go` and `app/txpolicy/gasless.go` files that implement Push Chain's "gasless first-use account initialization" — a candidate for the "admission and cryptographic path" pivot called out in the scope.

### Title
Free, fee-less on-chain account creation via forged gasless-tx admission enables unbounded state-bloat DoS - (File: app/ante/account_init_decorator.go)

### Summary
`AccountInitDecorator.AnteHandle` [1](#0-0)  lets any brand-new address bypass the entire remainder of the standard `AnteHandler` chain (fee deduction, gas metering, standard `SigVerificationDecorator`) as long as the transaction's message set matches `txpolicy.IsGaslessTx` [2](#0-1) . The decorator only checks a self-signed signature over a hardcoded `AccountNumber: 0, Sequence: 0` [3](#0-2) , then unconditionally creates and persists a new account on chain [4](#0-3) , before returning `ctx, nil` — never calling `next(ctx, tx, simulate)`. This means fee/gas decorators never run for this path.

### Finding Description
`IsGaslessTx` allows several message types — `MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`, `MsgVoteChainMeta`, `MsgMigrateUEA`, `MsgExecutePayload` — to be submitted without gas [5](#0-4) . These message types are intended to be sent by Universal Validators or UEAs, but `IsGaslessTx` performs no sender/authorization check — it only inspects the `TypeUrl` of the wrapped messages. Any unprivileged attacker can generate an arbitrary new keypair (free), self-sign a tx containing one of these message types addressed to itself, and submit it. Since the address `HasAccount(ctx, newAccAddr) == false`, `AccountInitDecorator` verifies only a trivial self-consistent signature (account number/sequence hardcoded to 0, so no real chain state constrains it) and unconditionally persists a new account via `aid.ak.NewAccountWithAddress` / `aid.ak.SetAccount` [6](#0-5) . The inner message itself will later fail in the module's `msg_server` (e.g., `msg_vote_inbound.go`) because the sender is not a registered Universal Validator, but that failure occurs in a later execution stage and does not roll back the account creation that already happened in the ante-handler's committed branch. Because no fee, gas, or minimum balance is required for this path, an attacker can repeat this with unlimited fresh keypairs to persist unlimited new accounts in state at zero cost, without needing any privileged role (validator, admin, TSS key holder, or existing funded account).

### Impact Explanation
This is a state-growth resource-exhaustion vector reachable by any unprivileged external actor with only the ability to generate keypairs and broadcast transactions — no funds, no validator or governance role required. It falls under the explicitly in-scope "denial of service... reachable without privileged control" category, since it does not require a malicious peer/validator/relayer assumption and is not a network-layer DoS but an application-level abuse of a Push-Chain-specific admission control (`AccountInitDecorator` + `IsGaslessTx`). Persisted bloat in the auth module's account store increases long-term state size and iteration/storage costs for all full nodes.

### Likelihood Explanation
High from a mechanical standpoint: constructing such a transaction only requires knowledge of the public message type URLs (which are public in the proto definitions) and a locally generated keypair; no chain-specific secret or privileged credential is needed. The main friction is that each transaction must be individually broadcast and each spam account is single-use for the free path, so throughput is bounded by transaction submission/mempool throughput rather than compute cost.

### Recommendation
`IsGaslessTx`/`AccountInitDecorator` should not treat account initialization as free purely based on message `TypeUrl` allowlisting. Before creating a new account and bypassing fee/gas, the decorator (or an earlier check) should validate that the actual signer is authorized for the specific gasless message — e.g., checking `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration` senders against the current Universal Validator set in `x/uvalidator`, and `MsgExecutePayload`/`MsgMigrateUEA` senders against a legitimate UEA derivation, prior to persisting the new account and skipping fee/gas decorators. Rate-limiting or requiring a minimal bonded stake/registration check for account-initializing gasless senders would also mitigate the spam vector.

### Proof of Concept
1. Generate a new, unfunded secp256k1/ed25519 keypair `K` with derived address `A` (never seen on chain).
2. Construct a transaction whose single message is `MsgVoteInbound` (or any other type from `GaslessMsgTypes`) with `Signer/Creator = A`, using `AccountNumber=0, Sequence=0` for the sign doc.
3. Broadcast the tx. `IsGaslessTx` returns true [7](#0-6) ; `AccountInitDecorator` sees `HasAccount(A)==false`, verifies the trivial self-signature, and calls `NewAccountWithAddress`/`SetAccount`, persisting account `A` on chain with no fee paid [8](#0-7) .
4. The subsequent `MsgVoteInbound` handler execution fails (A is not a Universal Validator), but the account creation from step 3 is already committed.
5. Repeat steps 1–4 with fresh keypairs indefinitely to grow on-chain account state at zero cost.

**Note on confidence**: I was not able to trace the exact baseapp commit semantics (whether ante-handler state changes survive a failing message execution) directly in this repository's `app.go`/baseapp wiring within the available tool budget — this is standard Cosmos SDK `runTx` behavior (ante-handler branch is committed independently of the message-execution branch) but I could not re-verify it against this specific SDK version in the codebase before the iteration limit was reached. If this repo pins a customized baseapp that reverts ante-state on message failure, the persistence-based DoS impact would need re-validation, though the free/authorization-bypass mechanism in `AccountInitDecorator` itself is confirmed directly from source.

func (aid AccountInitDecorator) AnteHandle(ctx sdk.Context, tx sdk.Tx, simulate bool, next sdk.AnteHandler) (sdk.Context, error) {
	if !txpolicy.IsGaslessTx(tx) {
		// Skip account initialization for non-gasless transactions
		ctx.Logger().Debug("account init decorator: non-gasless tx, skipping account init")
		return next(ctx, tx, simulate)
	}

	sigTx, ok := tx.(authsigning.Tx)
	if !ok {
		return ctx, errorsmod.Wrap(sdkerrors.ErrTxDecode, "invalid transaction type")
	}

	signers, err := sigTx.GetSigners()
	if err != nil || len(signers) != 1 {
		ctx.Logger().Debug("account init decorator: could not get unique signer, passing to next handler",
			"num_signers", len(signers),
			"error", err,
		)
		return next(ctx, tx, simulate)
	}

	newAccAddr := signers[0]
	if !aid.ak.HasAccount(ctx, newAccAddr) {
		ctx.Logger().Debug("account init decorator: new account detected on gasless tx, verifying signature",
			"address", sdk.AccAddress(newAccAddr).String(),
			"simulate", simulate,
		)
		// if account does not exist on chain, bypass rest of ante chain (especially gas and signature verification) here.
		// Perform signature verification on account number e and sequence number e instead.
		if err := aid.verifySignatureForNewAccount(ctx, tx, simulate); err != nil {
			ctx.Logger().Debug("account init decorator: signature verification failed for new account",
				"address", sdk.AccAddress(newAccAddr).String(),
				"error", err,
			)
			return ctx, err
		}

		acc := aid.ak.NewAccountWithAddress(ctx, newAccAddr)
		acc.SetSequence(1)
		aid.ak.SetAccount(ctx, acc)
		ctx.Logger().Info("account init decorator: new account created via gasless tx",
			"address", sdk.AccAddress(newAccAddr).String(),
		)
		return ctx, nil
	}

	ctx.Logger().Debug("account init decorator: existing account on gasless tx, passing to next handler",
		"address", sdk.AccAddress(newAccAddr).String(),
	)
	return next(ctx, tx, simulate)

// IsGaslessTx checks if a transaction contains only allowed gasless message types
// Returns true if all messages in the transaction are in the allowed gasless message types
func IsGaslessTx(tx sdk.Tx) bool {
	var (
		// GaslessMsgTypes defines the message types that are allowed in gasless transactions
		GaslessMsgTypes = []string{
			sdk.MsgTypeURL(&uexecutortypes.MsgMigrateUEA{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgExecutePayload{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteInbound{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteOutbound{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteTssKeyProcess{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteFundMigration{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteChainMeta{}),
		}
	)

	msgs := tx.GetMsgs()
	if len(msgs) == 0 {
		return false
	}

	for _, msg := range msgs {
		switch m := msg.(type) {
		case *authz.MsgExec:
			// Only gasless if ALL inner messages are allowed
			for _, innerMsg := range m.Msgs {
				if !slices.Contains(GaslessMsgTypes, innerMsg.TypeUrl) {
					return false
				}
			}
		default:
			if !slices.Contains(GaslessMsgTypes, sdk.MsgTypeURL(msg)) {
				return false
			}
		}
	}
	return true
}
