### Title
`CancelAllUnfreezeV2Actuator`/`CancelAllUnfreezeV2Processor` re-freeze resources and increase TRON Power without settling pending vote rewards - (File: `actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java`)

### Summary
This is analogous to the reported bug class ("skip pending reward before mutating stake state"), but the concrete manifestation in java-tron is different from a simple missed-claim: `CancelAllUnfreezeV2Actuator.execute()` and its TVM counterpart `CancelAllUnfreezeV2Processor.execute()` restore unexpired `unfrozenV2` amounts back into `frozenV2` balances (increasing bandwidth/energy/TRON Power weight) without first calling `mortgageService.withdrawReward()` / `VoteRewardUtil.withdrawReward()`, unlike every other stake-mutating path (`UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `UnfreezeBalanceV2Processor`, `WithdrawRewardProcessor`) which explicitly settle rewards at the start of execution.

### Finding Description
Compare the reward-settlement pattern across actuators that mutate a user's frozen/stake state:

- `UnfreezeBalanceActuator.execute()` calls `mortgageService.withdrawReward(ownerAddress)` as the very first state-mutating step. [1](#0-0) 
- `UnfreezeBalanceV2Actuator.execute()` likewise calls `mortgageService.withdrawReward(ownerAddress)` before mutating unfreeze/vote state. [2](#0-1) 
- `UnfreezeBalanceV2Processor.execute()` (the TVM-native equivalent) calls `VoteRewardUtil.withdrawReward(ownerAddress, repo)` first. [3](#0-2) 
- `WithdrawRewardProcessor.execute()` also settles via `VoteRewardUtil.withdrawReward`. [4](#0-3) 

In contrast, `CancelAllUnfreezeV2Actuator.execute()` never calls `mortgageService.withdrawReward()`. It directly iterates the account's `unfrozenV2List`, moves not-yet-expired entries back into frozen balances via `updateFrozenInfoAndTotalResourceWeight`/`updateAndCalculate`, and adjusts `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight`, then persists the account — all without settling the reward-accrual bookkeeping (`beginCycle`/`endCycle`/`allowance`) maintained by `MortgageService`/`DelegationStore`. [5](#0-4) 

The TVM equivalent, `CancelAllUnfreezeV2Processor.execute()`, has the identical omission — no call to `VoteRewardUtil.withdrawReward(ownerAddress, repo)` anywhere in its execute path, unlike its sibling `UnfreezeBalanceV2Processor`. [6](#0-5) 

The root cause mirrors the external report's bug class: a stake-state-mutating entry point (`instantUnstake`/re-freeze) changes the weight/voting-power basis for reward accrual without first flushing the reward computed against the *old* weight/vote-count into the user's claimable allowance. Because `VoteRewardUtil.withdrawReward`/`MortgageService.withdrawReward` compute rewards proportionally using `beginCycle`→`endCycle` snapshots of the account's vote list at the time of settlement, changing `frozenV2`/TRON Power/vote-power state in between settlement points via `CancelAllUnfreezeV2` — without an intervening reward flush — means the next `withdrawReward` call will apply the post-cancel voting power/weight retroactively across cycles that occurred under the pre-cancel state, corrupting the reward attribution for the affected cycle boundary.

### Impact Explanation
This can cause incorrect reward accounting for accounts that use `CancelAllUnfreezeV2` (either via the `CancelAllUnfreezeV2Contract` transaction type or the `CANCELALLUNFREEZEV2` TVM opcode from a smart contract). The user's vote-driven reward calculation is not "frozen" at the point of the state change, unlike every parallel unfreeze/withdraw path in the codebase, which consistently calls reward settlement first. This is a resource/reward accounting correctness bug rather than a fund-draining exploit; the practical loss is limited to reward-computation inconsistency, and I was not able to fully trace whether `computeReward`'s per-cycle Vi-delta computation is fully insulated from a mid-cycle vote-power change caused solely by `CancelAllUnfreezeV2` (since the account's votes list itself is untouched by this actuator — only the underlying frozen/weight balances change). This limits confidence that the impact is severe.

### Likelihood Explanation
`CancelAllUnfreezeV2Contract` is a normal, permissionless broadcast transaction, and `CANCELALLUNFREEZEV2` is a reachable TVM opcode callable by any smart contract once `AllowCancelAllUnfreezeV2`/`allowTvmFreezeV2` is enabled by committee proposal (both actuator and processor gate on this flag). Any account with a non-empty `unfrozenV2List` (i.e., a very common case for regular stakers) can trigger this path. [7](#0-6) 

### Recommendation
Add a `mortgageService.withdrawReward(ownerAddress)` call at the start of `CancelAllUnfreezeV2Actuator.execute()`, and a corresponding `VoteRewardUtil.withdrawReward(ownerAddress, repo)` call at the start of `CancelAllUnfreezeV2Processor.execute()`, mirroring the pattern already used consistently in `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, and `UnfreezeBalanceV2Processor`, so that pending rewards are settled against the account's state prior to any resource/weight mutation.

### Proof of Concept
Not directly demonstrable from static review alone — I was unable to execute a concrete numeric scenario (e.g., a Devin session running `CancelAllUnfreezeV2ActuatorTest`/`FreezeV2Test` scenarios with an interleaved reward-payment cycle) to confirm the magnitude of reward drift. The structural evidence is:
1. `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor`/`WithdrawRewardProcessor` all call reward-withdrawal as their first action. [1](#0-0) 
2. `CancelAllUnfreezeV2Actuator`/`CancelAllUnfreezeV2Processor` mutate frozen/weight state without doing so. [6](#0-5)

  public Map<String, Long> execute(CancelAllUnfreezeV2Param param, Repository repo) throws ContractExeException {
    Map<String, Long> result = new HashMap<>();
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    long withdrawExpireBalance = 0L;
    for (Protocol.Account.UnFreezeV2 unFreezeV2: ownerCapsule.getUnfrozenV2List()) {
      if (unFreezeV2.getUnfreezeExpireTime() > now) {
        String resourceName = unFreezeV2.getType().name();
        result.put(resourceName, result.getOrDefault(resourceName, 0L) + unFreezeV2.getUnfreezeAmount());

        updateFrozenInfoAndTotalResourceWeight(ownerCapsule, unFreezeV2, repo);
      } else {
        // withdraw
        withdrawExpireBalance += unFreezeV2.getUnfreezeAmount();
      }
    }
    if (withdrawExpireBalance > 0) {
      ownerCapsule.setBalance(ownerCapsule.getBalance() + withdrawExpireBalance);
    }
    ownerCapsule.clearUnfrozenV2();

    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);

    result.put(VMConstant.WITHDRAW_EXPIRE_BALANCE, withdrawExpireBalance);
    return result;
  }
