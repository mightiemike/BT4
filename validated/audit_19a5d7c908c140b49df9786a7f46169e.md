### Title
`handle_poison_microblock` never checks that the two microblock headers actually conflict (same `sequence`/`prev_block`), allowing any two legitimately-published, non-forking microblocks to be reported as a valid poison — ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`StacksChainState::check_microblock_header_signer` and the `handle_poison_microblock` Clarity handler that consumes it only verify that `mblock_header_1` and `mblock_header_2` recover to the *same public key*; they never verify that the two headers actually equivocate (i.e., same `sequence` and `prev_block` but different content/signature). The equivalent conflict check — `microblock_header_1.sequence != microblock_header_2.sequence || ... .prev_block != ...` — exists only in the mempool-admission path (`will_admit_mempool_tx` in `blocks.rs`), which is bypassed when a block containing the `PoisonMicroblock` tx is validated by other nodes via `process_transaction` → `process_transaction_payload` → `handle_poison_microblock`.

### Finding Description
The claimed broken equality is: `consensus-valid PoisonMicroblock tx == mempool-valid PoisonMicroblock tx`. Before the fix these were assumed equivalent; in fact they diverge.

- `check_microblock_header_signer` (`stackslib/src/chainstate/stacks/db/transactions.rs:686-713`) only compares `pkh1 != pkh2` recovered via `check_recover_pubkey()`; it does not compare `sequence`, `prev_block`, or `version`. [1](#0-0) 
- `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs:722-856`) calls only `check_microblock_header_signer`, then unconditionally uses `mblock_header_1.sequence` as the slashing/report sequence — it never cross-checks `mblock_header_2`'s sequence or `prev_block` against `mblock_header_1`. [2](#0-1) [3](#0-2) 
- The actual "do these headers conflict" check — `microblock_header_1.sequence != microblock_header_2.sequence || microblock_header_1.prev_block != microblock_header_2.prev_block || microblock_header_1.version != microblock_header_2.version` — exists only in `will_admit_mempool_tx`, a subjective mempool-relay gate, not a consensus rule enforced during block validation. [4](#0-3) 

Because `will_admit_mempool_tx` is only invoked when a transaction is submitted into a node's own mempool (e.g. via `mem_pool.miner_submit` in `neon_node.rs`'s `load_and_vet_parent_microblocks`), a block producer can construct a block directly containing a `PoisonMicroblock(header_1, header_2)` payload where `header_1` and `header_2` are two *real, legitimately signed, non-conflicting* microblocks from the target miner's single canonical linear stream (e.g., sequence 5 and sequence 6, both correctly signed with the miner's real key, with `prev_block` correctly chaining forward — no fork, no equivocation). When other nodes validate that block, they call `process_transaction` → `process_transaction_payload` → `handle_poison_microblock`, which never runs the mempool's conflict check, and thus accepts the tx as valid poison, slashing the honest miner.

This differs from the question's exact scenario (which requires forging a signature with a "stolen" key, which is not feasible without the private key) — that specific off-chain-fabrication path is not exploitable, since `check_recover_pubkey` cryptographically binds the header to whoever signed it. However, the underlying root cause it points at is real: the consensus-critical acceptance path is missing the conflict/equivocation check that only exists in the mempool gate, which is bypassable by a block producer including the transaction directly.

### Impact Explanation
An attacker holding a single minority miner/sortition slot can construct and get accepted a Nakamoto block containing a `PoisonMicroblock` transaction built from any miner's two real (non-forking, non-equivocating) microblocks. Since `handle_poison_microblock` does not verify actual equivocation, all validating nodes will accept the transaction as legitimate and permanently mark the miner's microblock pubkey hash as poisoned/reported, transferring commission of that miner's coinbase reward to the attacker's reporting address — i.e., block-reward theft from a non-equivocating miner. This matches the Critical impact category (block-reward theft / reward mis-payment), and it is fully repeatable against any miner who has ever produced two or more microblocks in a stream (essentially any microblock-producing miner).

### Likelihood Explanation
Preconditions: the target miner must have published at least two microblocks in some past tenure (extremely common — any non-trivial microblock stream). The attacker needs only to win a single sortition/minor commit slot (minority stake, one miner slot — explicitly an allowed unprivileged attacker profile) so they can construct their own block and directly embed the crafted `PoisonMicroblock` tx, bypassing their own mempool's `will_admit_mempool_tx` gate (which they control anyway, but more importantly, other validating nodes never re-run this gate). No majority stake, no compromised keys, and no P2P/social requirements are needed — the exploit is purely a missing-check-at-the-consensus-layer bug.

### Recommendation
Move the conflict check currently only present in `will_admit_mempool_tx` (`microblock_header_1.sequence != microblock_header_2.sequence || .prev_block != .prev_block || .version != .version`) into `StacksChainState::check_microblock_header_signer` (or directly into `handle_poison_microblock`) so it is enforced as a consensus rule during `process_transaction_payload`, not merely as a mempool-admission heuristic. Additionally require `mblock_header_1 != mblock_header_2` (distinct signatures/content) to rule out trivial self-matches.

### Proof of Concept
Rust integration test plan (in `stackslib/src/chainstate/stacks/db/transactions.rs` test module, alongside `process_poison_microblock_valid` style tests):
1. Generate a real miner key `block_privk` and insert its pubkey hash via `insert_microblock_pubkey_hash`.
2. Build two **genuinely valid, non-conflicting** `StacksMicroblockHeader`s from the same key: `header_5` with `sequence = 5`, `prev_block = hash(mblock_4)`, and `header_6` with `sequence = 6`, `prev_block = hash(mblock_5)` — i.e., a real contiguous, non-forked two-step chain, both signed correctly by `block_privk`.
3. Construct `TransactionPayload::PoisonMicroblock(header_5, header_6)` and directly call `StacksChainState::process_transaction` (bypassing `will_admit_mempool_tx`), simulating how a block producer would embed the tx directly in a block.
4. Assert on both sides of the equality:
   - Equality before: "miner never equivocated" (only one linear stream stored/loaded via `load_descendant_staging_microblock_stream_with_poison`, no `poison_opt` returned).
   - Equality after: assert `process_transaction` returns `Ok(..)` (accepts the tx) and `get_poison_microblock_report` records a slash for the miner's pubkey hash — demonstrating reward/slashing occurred despite no real fork/equivocation ever existing in the canonical microblock stream.
5. Contrast with a call to `StacksChainState::will_admit_mempool_tx` on the same payload, which should return `Err(MemPoolRejection::PoisonMicroblocksDoNotConflict)`, proving the two validation paths diverge.

    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
