### Title
Order matching in `MarketSellAssetActuator` can be permanently blocked by a single griefing maker order, causing a persistent DoS on the exchange order book - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.execute()` catches only a fixed set of checked exceptions (`ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`, `ContractValidateException`) around the whole order-creation-and-matching flow [1](#0-0) . The matching loop `matchOrder`/`matchSingleOrder` walks the resting maker orders in the order book and, for every match, credits the maker's account balance via `addTrxOrToken` → `AccountCapsule.addAssetAmountV2`/`setBalance` [2](#0-1) . This credit uses an overflow-checked `addExact`, which throws `ArithmeticException` on overflow [3](#0-2) . `ArithmeticException` is a `RuntimeException`, not one of the caught checked exceptions in `execute()`, so it propagates uncaught out of the actuator.

### Finding Description
A malicious user can pre-position a maker order such that the credit received by their own account, upon being matched, causes their token or TRX balance to overflow `Long.MAX_VALUE` (e.g. by first accumulating a very large asset balance close to `Long.MAX_VALUE` via legitimate token issuance/transfers/other trades, then placing a resting sell order at an advantageous price). Because `matchOrder` always attempts to match against the best (lowest) price first in `pairPriceToOrderStore`'s ordered price list [4](#0-3) , any subsequent taker (any anonymous account broadcasting a `MarketSellAssetContract`) whose sell order would match against the attacker's poisoned maker order triggers `addTrxOrToken(makerOrderCapsule, ...)`, which calls the overflow-checked balance/asset addition on the *maker's* account [5](#0-4) . Since the maker's balance was engineered to overflow, this throws `ArithmeticException`, which is not caught by `execute()`'s catch clause [1](#0-0) , and the exception propagates out of the actuator uncaught.

Because the poisoned maker order is never removed from `pairPriceToOrderStore` (removal only happens after a *successful* match reduces its remaining quantity to zero, at line `makerOrderCapsule.getSellTokenQuantityRemain() == 0` in the caller) [6](#0-5) , it remains the best/only order at that price level, and every subsequent taker transaction that would match against it repeats the same failure. This is the direct structural analog of the reported bug class: a single unrecoverable "transfer" (asset/balance credit) failure inside a loop over multiple counter-parties permanently blocks the operation (here: order matching) for all future participants, not just the attacker.

### Impact Explanation
This can permanently freeze a price level (or, depending on liquidity, most of the practical trading range) of a token pair in java-tron's on-chain decentralized exchange (Market module) for all other unprivileged users, since every attempt to match against the poisoned maker order throws an uncaught exception and fails the taker's transaction. This is a persistent Denial-of-Service on the exchange/market matching engine, an in-scope, reachable-via-broadcast-transaction vulnerability class (resource/accounting corruption and DoS via protocol implementation).

### Likelihood Explanation
Reaching `Long.MAX_VALUE` balance for a token requires either owning/issuing large token supplies or accumulating balance over many transactions, which raises the bar compared to the original ERC20 bug (which needed only a blacklist/paused token). However, TRC10 token supply is attacker-controlled at issuance time (an attacker can issue a token with `totalSupply = Long.MAX_VALUE` and hold it themselves), making the TRX-independent asset-credit branch of `addTrxOrToken` (`accountCapsule.addAssetAmountV2`) directly attacker-controllable in a single step, without needing prior accumulation. Therefore the likelihood is non-trivial: an attacker fully controls both the poisoned account's balance and the offending maker order's parameters.

### Recommendation
Wrap `matchOrder`/`matchSingleOrder` (and the underlying `addAssetAmountV2`/`addExact` calls) so that `ArithmeticException` (and other unexpected `RuntimeException`s) are caught in `MarketSellAssetActuator.execute()`, converting them into a controlled `ContractExeException`/failed transaction rather than an uncaught propagation. More importantly, cap balances defensively before crediting (reject/skip the match, or cancel/void the offending maker order) instead of letting the failure abort the whole transaction, and consider validating that a maker's resulting balance cannot exceed safe bounds when the maker order is created, so a single bad maker order cannot permanently block the order book for other users.

### Proof of Concept
1. Attacker issues (or otherwise legitimately obtains) a TRC10 token `T` with an extremely large balance approaching `Long.MAX_VALUE` in their own account.
2. Attacker places a `MarketSellAssetContract` selling `T` for TRX (or another token) at an attractive price, creating a resting maker order recorded in `pairPriceToOrderStore`/`pairToPriceStore`.
3. A victim broadcasts a `MarketSellAssetContract` on the opposite side that would match against the attacker's maker order.
4. During `matchOrder` → `matchSingleOrder` → `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)`, the credit to the attacker's account overflows `Long.MAX_VALUE`, and `Maths.addExact` throws `ArithmeticException` [3](#0-2) .
5. `MarketSellAssetActuator.execute()`'s catch block does not list `ArithmeticException`, so the exception propagates uncaught [1](#0-0) , failing the victim's transaction.
6. Because the attacker's maker order remains unconsumed at the best price, step 3–5 repeats for every subsequent taker attempting to match at that price level, permanently denying trading against it.

Note: I was unable to directly trace how an uncaught `ArithmeticException` from inside actuator `execute()` is ultimately handled by the calling `Manager`/`TransactionCapsule` execution wrapper (e.g., whether it is caught generically at a higher layer and merely fails the single transaction, or has broader block-processing consequences) within the indexed portions of the codebase; this affects whether the impact is "single transaction always fails" vs. a more severe processing halt. A Devin session with full repository access would be needed to confirm the exact exception-handling behavior in `TransactionCapsule`/`Manager.processTransaction` for uncaught `RuntimeException`s from actuators.

    List<byte[]> priceKeysList = pairPriceToOrderStore

            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);

        return;

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists

        }

          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);

  public boolean addAssetAmountV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    //key is token name
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAsset(nameKey, addExact(currentAmount, amount, disableJavaLangMath))
          .putAssetV2(tokenID, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenIDStr = ByteArray.toStr(key);

        currentAmount = 0L;
      }
