### Title
Unprivileged `TransferToGasKey` action lets anyone frontrun and permanently block `DeleteKey`/`DeleteAccount` on a victim's gas key - ([File: runtime/runtime/src/actions.rs])

### Summary
`check_actor_permissions` restricts most sensitive actions (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeployGlobalContract`, `UseGlobalContract`, `WithdrawFromGasKey`, `DeleteAccount`) to require `actor_id == account_id`, but `Action::TransferToGasKey` is deliberately left unrestricted, falling into the no-op permission branch alongside `CreateAccount`/`FunctionCall`/`Transfer`. This means **any account (an unprivileged third party, with no access key on the victim account) can top up a victim's existing gas key balance**. `action_delete_key`/`action_delete_account` refuse to delete a gas key (or an account holding one) whenever the gas key's balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR). An attacker can therefore donate funds to a victim's gas key to push it above the 1 NEAR threshold immediately before the victim's `DeleteKey`/`DeleteAccount` transaction executes, causing that transaction to fail with `GasKeyBalanceTooHigh` — the direct analog of the reported bug where an unprivileged donation frontruns and blocks an owner-only cleanup/removal operation gated on a balance-derived check.

### Finding Description
`check_actor_permissions` (`runtime/runtime/src/actions.rs:755-800`) enumerates the actions that require the acting identity to equal the target account: [1](#0-0) 

Note that `Action::TransferToGasKey(_)` is explicitly grouped with permissionless actions (`CreateAccount`, `FunctionCall`, `Transfer`) at line 793-796, while `Action::WithdrawFromGasKey(_)` (the *withdraw* side) is restricted at line 768. This asymmetry means depositing into a gas key is public, but withdrawing from it is owner-only.

`action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257-288`) performs no predecessor/actor check itself — it simply looks up the gas key by `account_id` + `public_key` and adds the deposit to `gas_key_info.balance`: [2](#0-1) 

The victim's public key for their own gas key is visible on-chain (it must be, to be usable), so any attacker can construct a `TransferToGasKeyAction { public_key: <victim gas key>, deposit: ... }` receipt targeting the victim account.

Separately, both single-key deletion and whole-account deletion enforce a hard cap on gas-key balance before allowing removal:

- `delete_gas_key` (called from `action_delete_key`) rejects deletion if `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR): [3](#0-2) 

- `action_delete_account` sums all gas-key balances on the account and rejects the whole `DeleteAccount` if the sum exceeds the same 1 NEAR cap: [4](#0-3) 

Because `TransferToGasKey` is unrestricted, an attacker can watch the mempool/chain for a victim's pending `DeleteKey`/`DeleteAccount` transaction (or simply act preemptively/repeatedly) and submit a `TransferToGasKey` transaction that funds the target gas key just above 1 NEAR. This is the direct analog of the reported issue: a state-changing, owner-restricted cleanup operation (`removeAsset`, checked via `getTVLForAsset() > 0`) is blocked by an externally, permissionlessly-manipulable balance signal (`IERC20.balanceOf`, donatable by anyone). Here the "balanceOf" equivalent is `gas_key_info.balance`, mutable by anyone via `TransferToGasKey`, and the "owner-only cleanup" equivalent is `DeleteKey`/`DeleteAccount`, which is actor-restricted (only the account itself) but is nonetheless blockable by an outsider's deposit.

### Impact Explanation
This lets any unprivileged account permanently deny a victim account the ability to delete a specific gas key, or delete the whole account, by repeatedly (and cheaply, relative to griefing power — each grief just requires depositing >0 NEAR above the current balance up to the 1 NEAR cap) funding the gas key whenever the owner tries to bring the balance back down and delete it. Since `WithdrawFromGasKey` is owner-restricted and takes its own transaction/block, an attacker who front-runs (same block or next block, submitting `TransferToGasKey` right after any `WithdrawFromGasKey`) can indefinitely keep the balance above the burn cap, resulting in a denial-of-service against account/key lifecycle management — an owner can never reliably clean up or fully delete their account. This matches "Medium" severity griefing/DoS class similar to the source report (cheap-cost, repeatable, owner cannot prevent it through his own transactions alone).

### Likelihood Explanation
High reachability: `TransferToGasKey` is a standard user-facing `Action` reachable by any signed transaction/meta-transaction from any account, requiring only knowledge of the victim's public gas key (which is necessarily public/on-chain to be usable) and enough NEAR to fund the deposit (deposit is not lost forever — the attacker's funds land in the victim's gas key balance, recoverable by the victim via `WithdrawFromGasKey`, but the grief is on availability/timing of deletion, not fund theft). No special privileges, validator status, or protocol bugs are needed — only the asymmetric actor-permission list in `check_actor_permissions`.

### Recommendation
Restrict `Action::TransferToGasKey` to require `actor_id == account_id` in `check_actor_permissions`, mirroring the restriction already applied to `WithdrawFromGasKey`, `AddKey`, and `DeleteKey`. Alternatively, decouple the gas-key-balance-too-high deletion block from external donations, e.g. by capping/burning any excess above `MAX_BALANCE_TO_BURN` automatically at deletion time instead of rejecting the whole action, or by allowing deletion regardless of balance and simply burning up to a bounded amount while refunding the account for the rest.

### Proof of Concept
1. Victim account `victim.near` adds a gas key `gk` via `AddKey` with `AccessKey::gas_key_full_access(n)`.
2. Victim funds `gk` lightly (e.g., 0.1 NEAR) via `TransferToGasKey` for normal use, intending to later delete it.
3. Attacker `attacker.near` (no access key on `victim.near`) submits `SignedTransaction` with `Action::TransferToGasKey(TransferToGasKeyAction { public_key: gk, deposit: 1_000_000_000_000_000_000_000_001 })` (~1 NEAR + 1 yocto), signed with the attacker's own key, `signer_id = attacker.near`, `receiver_id = victim.near`.
4. `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257`) executes successfully because `check_actor_permissions` places `TransferToGasKey` in the unrestricted branch; `gk`'s `GasKeyInfo.balance` now exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR).
5. Victim submits `DeleteKey` for `gk` (or `DeleteAccount`); `delete_gas_key`/`action_delete_account` reject it with `GasKeyBalanceTooHigh` (`runtime/runtime/src/access_keys.rs:103-111`, `runtime/runtime/src/actions.rs:370-379`).
6. If the victim withdraws the excess via `WithdrawFromGasKey` and retries deletion, the attacker repeats step 3 in the intervening block, keeping the balance perpetually above the cap and blocking deletion indefinitely.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
