### Title
Attacker-controlled `RevertInstructions.FundRecipient` can force outbound revert re-mint to fail, permanently freezing bridged funds in `ABORTED` state outside the RESCUE_FUNDS recovery path — (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`buildRevertOutbound` and `handleFailedOutbound` use `outbound.RevertInstructions.FundRecipient` — a value that originates from the user's own inbound submission — as the destination for `CallPRC20Deposit` when re-minting bridged tokens on a failed/reverted outbound. If that recipient address is one for which the PRC20 mint call reverts (e.g., not a valid 20-byte hex address, a contract that reverts on token receipt, or a blacklisted/misconfigured address), `handleFailedOutbound` calls `AbortOutbound`, setting `OutboundStatus = ABORTED`. Unlike the `NFT-in-StabilityPool` bug class, there is at least one nominal recovery mechanism in this codebase (`AttachRescueOutboundFromReceipt` / `RESCUE_FUNDS`), but that mechanism explicitly requires the stuck outbound to be in `REVERTED` status — not `ABORTED`. This leaves `ABORTED` outbounds with no protocol-defined path back into the fund-recovery flow, mirroring the reported bug class of "asset moved into a state with no corresponding withdrawal function."

### Finding Description
The revert/refund flow for a failed outbound is:

1. `FinalizeOutbound` → `handleFailedOutbound` (`x/uexecutor/keeper/outbound.go:99-161`) re-mints the bridged PRC20 to a `recipient` chosen from `outbound.RevertInstructions.FundRecipient` if set, else `outbound.Sender`: [1](#0-0) 

2. `outbound.RevertInstructions` (and the analogous `inbound.RevertInstructions`) are populated from `buildRevertOutbound`, which is built directly from the `Inbound` record — a structure whose fields (including `RevertInstructions.FundRecipient`) originate from the raw source-chain payload that any ordinary user can construct when initiating a bridge action: [2](#0-1) 

3. If the `CallPRC20Deposit` mint to that attacker/user-chosen recipient fails (e.g. `common.HexToAddress(recipient)` on a malformed string silently becomes a colliding/zero address, or the recipient is a contract designed to revert on `depositPRC20Token`'s internal transfer), the outbound is immediately marked `ABORTED` "for manual intervention": [3](#0-2) 

4. The only other on-chain recovery mechanism for stuck funds, `AttachRescueOutboundFromReceipt`, is gated on the original UTX having an `INBOUND_REVERT` outbound in `Status_REVERTED` — it explicitly does not accept `Status_ABORTED`: [4](#0-3) 

5. `Status_ABORTED` is documented as "requires manual intervention," and the protocol has no chain-driven message to transition an `ABORTED` outbound back into an eligible state for `RESCUE_FUNDS` or any other flow: [5](#0-4) 

The net effect: the bridged PRC20 value that was supposed to be re-minted to the user during a revert never lands anywhere (the mint call reverted), the UTX's outbound is stuck in `ABORTED`, and the rescue-fund escape hatch (the closest analog to a "withdraw" function) cannot be invoked because it strictly checks for `REVERTED`, not `ABORTED`.

### Impact Explanation
This falls under "permanent freezing of user or protocol-controlled funds" in the allowed-impact list. A normal user, simply by supplying a malformed or adversarial `FundRecipient` in their own bridge payload (or by targeting a chain/token combination where such a recipient is later reachable), can drive their own bridged position into a dead-end `ABORTED` state that the existing `RESCUE_FUNDS` admin flow cannot reach, since it only recognizes `REVERTED` outbounds as rescue-eligible. This is analogous to the reported NFT lock: value enters a state (`ABORTED`) for which the protocol's own "make it whole" mechanism (`RESCUE_FUNDS`) has no eligibility branch.

### Likelihood Explanation
Reaching `ABORTED` requires the re-mint call in `handleFailedOutbound` to fail, which is dependent on EVM/contract-level behavior of `CallPRC20Deposit` against a user-supplied recipient — this is plausible (malformed address parsing, a hostile PRC20/handler interaction, or contract enforcement rejecting the recipient) but not unconditionally guaranteed for every input, and the exact conditions that make `depositPRC20Token` revert live in the EVM contracts (`UniversalCore`), which are outside this repo's Go code and could not be fully verified within the scope of this investigation. This uncertainty lowers confidence relative to a fully proven exploit chain.

### Recommendation
- Extend the `AttachRescueOutboundFromReceipt` eligibility check to also accept outbounds in `Status_ABORTED` (in addition to `Status_REVERTED`) when validating whether a rescue can be attached, so stuck `ABORTED` records are not permanently excluded from the recovery path.
- Alternatively, add an explicit admin/governance message (in the spirit of `RevertStuckInbound`) that can re-drive an `ABORTED` outbound's re-mint with an operator-supplied fallback recipient (e.g., the original `outbound.Sender`) when the user-supplied `FundRecipient` is unusable, and record it as a new PCTx rather than leaving the state as a dead end.
- Validate/sanitize `RevertInstructions.FundRecipient` at inbound-ingestion time (reject or fall back to `Sender` if it is not a well-formed EVM address) to reduce the likelihood of an unrecoverable mint failure in the first place.

### Proof of Concept
Not independently executable within this investigation (no local Foundry/Go test harness was run). The conceptual PoC path, based on the code above, is:

1. A user submits a bridge inbound (e.g. `TxType_FUNDS_AND_PAYLOAD`) whose payload sets `RevertInstructions.FundRecipient` to a value that will make the corresponding `depositPRC20Token` call revert when later invoked (e.g., a value that parses to an address belonging to a contract without a receiver hook that the `UniversalCore` handler requires, or a degenerate/zero address depending on `UniversalCore`'s validation).
2. The inbound executes normally, produces an `OutboundTx` (e.g., from a payload-triggered destination call).
3. UVs vote the outbound as failed (`MsgVoteOutbound` with `success=false`), triggering `FinalizeOutbound` → `handleFailedOutbound`.
4. `CallPRC20Deposit(ctx, prc20, recipient=FundRecipient, amount)` reverts; `handleFailedOutbound` calls `AbortOutbound`, setting `OutboundStatus = ABORTED`.
5. Attempting `AttachRescueOutboundFromReceipt` for this UTX fails with `"no reverted inbound-revert outbound"` because the outbound's status is `ABORTED`, not `REVERTED`, per `create_outbound.go:251-261` and the negative test coverage of this exact check in `test/integration/uexecutor/rescue_funds_test.go`.

This chain could not be validated end-to-end against a running node/contract set in this session; the exact conditions under which `depositPRC20Token` reverts for a given recipient depend on the `UniversalCore` Solidity contract, which is outside the indexed Go codebase and should be verified directly.

### `Status` — per-outbound status

`OutboundTx.outbound_status` uses a separate, narrower enum:

| `Status` | Meaning |
|---|---|
| `PENDING` | Outbound created on Push Chain, waiting for UVs to broadcast and vote |
| `OBSERVED` | UVs voted the outbound was successfully broadcast on the destination chain |
| `REVERTED` | UVs voted the outbound permanently failed; revert path triggered |
| `ABORTED` | Finalization or revert attachment failed and requires manual intervention |
