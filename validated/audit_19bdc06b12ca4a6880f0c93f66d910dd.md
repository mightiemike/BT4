## Analog Confirmed: Unbounded recursion in NEAR's transaction/receipt outcome traversal

### Title
Unbounded recursion in `Chain::get_recursive_transaction_results` allows stack-exhaustion crash of any node serving `tx`/`tx_status` JSON-RPC requests - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` walks the tree of `ExecutionOutcome`s spawned by a transaction by recursively following `outcome.receipt_ids` with **no depth limit and no non-recursive fallback**, unlike the analogous `ReceiptToTx` lookup path which explicitly enforces `MAX_DEPTH=1000`. This function is invoked on every call to the public JSON-RPC `tx` / `tx_status` / `EXPERIMENTAL_tx_status` methods (and by `broadcast_tx_commit`/`send_tx` polling), making it reachable by any unprivileged RPC caller who merely names a transaction hash. [1](#0-0) [2](#0-1) 

### Finding Description
`get_recursive_transaction_results` pushes the outcome for `id`, then loops over `outcome.receipt_ids` and calls itself once per child receipt id, with no bound on recursion depth: [3](#0-2) 

It is used by both `get_final_transaction_result` (blocks until fully resolved) and `get_partial_transaction_result_option` (best-effort, partial outcome): [4](#0-3) [5](#0-4) 

`get_partial_transaction_result_option` is called from `ViewClientActor::get_tx_status`, which is the handler behind the `TxStatus`/`TxStatusRequest` actor messages that back the `tx`, `tx_status`, and `EXPERIMENTAL_tx_status` JSON-RPC methods, as well as the RPC's own transaction-status polling loop (`tx_status_fetch`/`tx_status_fetch_single`): [6](#0-5) [7](#0-6) [8](#0-7) 

The codebase demonstrates explicit awareness that unbounded traversal of receipt-parent chains is dangerous: the newer `GetReceiptToTx` lookup enforces a hard `MAX_DEPTH=1000` and returns a `DepthExceeded` error instead of recursing further, with a dedicated regression test proving the guard: [9](#0-8) [10](#0-9) 

No equivalent guard exists on `get_recursive_transaction_results`, which walks the *forward* (children) direction of the same kind of chain.

The depth of the receipt outcome tree for one transaction is normally bounded by gas (an integration test shows self-recursive cross-contract calls achieve only ~56-221 hops under max prepaid gas): [11](#0-10) 

However, the yield/resume mechanism (`yield_timeout_length_in_blocks: 200`) lets a contract create a `PromiseYield` receipt that only resolves when an external "resume" transaction is later submitted. Because each resume is its own signed transaction with a fresh prepaid-gas budget, an attacker is not limited to the gas of a single transaction: by chaining "yield → resume → yield → resume → …" across many separate transactions (each within the 200-block timeout window relative to its predecessor), the *outcome tree reachable from the original transaction hash* can be grown to depths far beyond what any single transaction's gas allows — with no protocol-level bound on the total chain length over time. Once such a chain exists, any node (including a plain RPC node) that later serves a `tx`/`tx_status` request for the original transaction hash (or for `EXPERIMENTAL_tx_status`) will recurse the full depth of that tree, exhausting the thread stack and crashing the serving process.

### Impact Explanation
A single crafted transaction hash (attacker-controlled, built up over time via many of the attacker's own cheap transactions) can crash any node process that answers a `tx`/`tx_status`/`EXPERIMENTAL_tx_status` JSON-RPC query, or that internally polls transaction status (`send_tx_commit`), for that transaction. This is a transaction/data-triggered denial of service against RPC-serving nodes — validators that also serve RPC, or any RPC gateway used by wallets/dApps, could be forced to crash repeatedly whenever the poisoned transaction hash is queried, effectively meeting the report's bar of a "transaction-triggered halt" of node processes reachable from ordinary un-privileged RPC/transaction activity.

### Likelihood Explanation
Building the chain requires only ordinary permissionless actions available to any account: deploying/using a contract that issues `promise_yield_create`/`promise_yield_resume` in sequence across multiple transactions, each transaction obeying normal gas/fee rules — no validator or node privileges are needed. The only "cost" to the attacker is the standard gas/fee of many small transactions and elapsed block time to stay within each 200-block yield window, which is inexpensive relative to the resulting DoS. The un-guarded recursive function is also symmetrical to a function already known internally to need a depth cap (`GetReceiptToTx`'s `MAX_DEPTH`), indicating the missing guard here is a genuine oversight rather than an intentionally-accepted risk.

### Recommendation
Convert `get_recursive_transaction_results` to an explicit iterative (stack/queue-based) traversal, mirroring the pattern already used elsewhere in the codebase for trie/receipt traversal (e.g., `TrieRecorder::get_subtree_size`'s explicit `VecDeque`-based traversal, or `TrieStorageUpdate::flatten_nodes`'s crumb-stack approach): [12](#0-11) [13](#0-12) 

Additionally, enforce an explicit maximum outcome-tree depth/size (analogous to the `ReceiptToTx` `MAX_DEPTH=1000` / `DepthExceeded` pattern) so that pathological transaction/receipt/yield-resume chains cannot cause unbounded work or unbounded stack usage regardless of traversal style. [9](#0-8) 

### Proof of Concept
Conceptual PoC (exact yield/resume gas accounting was not verified in this pass, see caveat below):
1. Deploy a contract exposing two entry points: `start()` which issues a `promise_yield_create` targeting a `resume()` callback, and `resume()` which, upon being invoked via the yield-resume mechanism, immediately issues another `promise_yield_create`/`resume()` cycle.
2. Submit the initial transaction calling `start()`, recording its transaction hash `TX0`.
3. Repeatedly, within each 200-block yield-timeout window, submit a new transaction that resumes the pending yield, causing `resume()` to fire and schedule the next yield — repeat this thousands of times to build a very deep chain of execution outcomes all reachable, via `receipt_ids`/`SuccessReceiptId`, from `TX0`.
4. Once the chain is sufficiently deep, issue a JSON-RPC `tx` or `tx_status` request (or `EXPERIMENTAL_tx_status`) for `TX0` against any RPC node that tracks the relevant shard(s).
5. The node's `ViewClientActor::get_tx_status` → `Chain::get_partial_transaction_result_option`/`get_final_transaction_result` → `get_recursive_transaction_results` recurses once per outcome in the chain; sufficient chain depth exhausts the serving thread's stack and crashes the node process.

**Caveat / what is unverified**: I was not able to fully trace, within this pass, the exact gas/storage cost accounting for chained yield/resume cycles across independent transactions to confirm there is no additional per-chain-length cost or protocol-enforced total limit that would cap the achievable depth below what is needed to exhaust a typical node's stack (default 8MB, frame size for this function appears small — tens to a few hundred bytes per level). Confirming the concrete number of yield/resume hops needed, and whether any global counter (e.g., total outstanding yields per account, or a maximum chain length induced by `PromiseYield`/`PromiseResume` receipt processing) exists elsewhere in `runtime/runtime/src/lib.rs` would require deeper review than the index could support here. This should be validated with a live/local NEAR devnet before treating the severity as confirmed "High."

    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }
