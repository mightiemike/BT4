## Title
Unbounded per-cycle reward computation loop enables CPU/time exhaustion DoS via `MortgageService.withdrawReward` - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.getOldReward` iterates once per governance cycle between an account's last-withdrawn cycle and the current cycle, with no upper bound on the number of iterations and no check that sufficient "work budget" remains for the call. This is the same bug class as the reported Compound `Comptroller.sol` issue: a `for`/loop-driven computation whose iteration count is attacker/time controlled, with no guard (e.g., a gas/费用/iteration cap check) to bail out before exhausting available resources.

### Finding Description
`MortgageService.withdrawReward` (and its sibling `queryReward`) computes rewards for an account by calling `computeReward(beginCycle, endCycle, accountCapsule)`, which in turn calls `getOldReward(begin, end, votes)` for any portion of the interval that predates `newRewardAlgorithmEffectiveCycle`: [1](#0-0) 

```java
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
  if (dynamicPropertiesStore.allowOldRewardOpt()) {
    return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
  }
  long reward = 0;
  for (long cycle = begin; cycle < end; cycle++) {
    reward += computeReward(cycle, votes);
  }
  return reward;
}
```

The loop bound `end - begin` is `currentCycle - beginCycle`, i.e., the number of maintenance cycles that have elapsed since the account last had its reward settled. This is fully attacker-controlled: a user simply refrains from calling any actuator that triggers `withdrawReward`/settlement (vote, freeze/unfreeze, withdraw balance) for a long period, letting `beginCycle` fall far behind `currentCycle`.

`withdrawReward` is invoked unconditionally from multiple ordinary, unprivileged actuators/native-contract processors whenever an account interacts with voting/freezing: [2](#0-1) [3](#0-2) 

Inside the loop, `computeReward(cycle, votes)` performs a DB lookup per vote per cycle (`delegationStore.getReward`, `delegationStore.getWitnessVote`): [4](#0-3) 

so total work is O((currentCycle - beginCycle) × votesCount), which is unbounded and can grow arbitrarily as time passes without any check to short-circuit or defer the computation. Unlike TVM bytecode execution — which is metered opcode-by-opcode via `Program.spendEnergy`/`checkCPUTimeLimit` in `VM.java` (`actuator/src/main/java/org/tron/core/vm/VM.java`) — this actuator-level Java loop has no equivalent per-iteration cost check, gas accounting, or hard cap tied to the fee paid for the triggering transaction.

### Impact Explanation
A witness voter (or delegator) can accumulate an arbitrarily large `currentCycle - beginCycle` gap simply by not touching their account for a long period (this is entirely normal/permissionless behavior, not an attack requiring special access). When they finally submit any transaction that triggers `withdrawReward` (vote, freeze, unfreeze, or withdraw-balance), block-producing/validating nodes must execute a loop whose length is proportional to elapsed cycles, consuming CPU time disproportionate to the transaction's declared/paid resources. This is an underpriced-public-work / potential block-processing-delay (halt-adjacent) issue: transaction execution cost is not commensurate with the resource fee charged, and if triggered broadly or with a sufficiently stale account, it can slow down block production/validation across the network.

### Likelihood Explanation
This requires only ordinary account activity by any unprivileged user (letting cycles accumulate, then submitting a normal vote/unfreeze/withdraw transaction) — no special privileges, exploits, or code paths reserved for trusted roles are needed. The reachability is confirmed through multiple standard actuators (`VoteWitnessActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `WithdrawBalanceActuator`) and native-contract processors that call `withdrawReward`/`VoteRewardUtil.withdrawReward`. However, this path is only live when `dynamicPropertiesStore.allowOldRewardOpt()` is false (i.e., the "old reward algorithm" optimization has not been activated on the network); once `allowOldRewardOpt` is enabled, the per-cycle loop is replaced by `rewardViCalService.getNewRewardAlgorithmReward`, which is presumably O(1)-ish per vote (not independently verified here due to remaining tool budget). The severity therefore depends on whether `allowOldRewardOpt` is active on the target chain — this could not be conclusively confirmed within the available investigation.

### Recommendation
Add an explicit bound or "checkpoint" mechanism to the cycle-by-cycle reward loop analogous to the recommended Compound fix: instead of unconditionally iterating from `beginCycle` to `endCycle`, cap the number of cycles processed per call (e.g., process at most N cycles per invocation and persist an intermediate `beginCycle` checkpoint so subsequent calls resume rather than reprocessing/blocking on the full backlog), or migrate fully off the O(cycles) `getOldReward` path onto the O(1)-per-vote Vi-delta algorithm (`computeReward(beginCycle, endCycle, accountCapsule)` at lines 199-230, which already exists and is bounded) for all cycles, removing the unbounded per-cycle loop entirely.

### Proof of Concept
1. An account votes for a witness and then does not interact with voting/freeze/withdraw actuators for a long span of maintenance cycles while `allowOldRewardOpt()` remains false on the network (this is the default/legacy path prior to the optimization being enabled).
2. `beginCycle` for the account remains fixed while `dynamicPropertiesStore.getCurrentCycleNumber()` (`currentCycle`) keeps advancing every maintenance cycle.
3. The account (or anyone triggering an actuator that calls `mortgageService.withdrawReward(address)` for that account, e.g., `VoteWitnessActuator`, `UnfreezeBalanceActuator`) submits a single ordinary transaction.
4. `withdrawReward` → `computeReward(beginCycle, endCycle, accountCapsule)` → `getOldReward(begin, oldEndCycle, srAddresses)` executes a `for (long cycle = begin; cycle < end; cycle++)` loop with `end - begin` equal to the full backlog of cycles, each iteration performing DB reads per voted witness, causing CPU/time cost that scales with elapsed time and vote count, unbounded by the transaction's paid resources.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
