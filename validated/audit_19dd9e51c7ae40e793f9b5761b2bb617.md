### Title
Snapshot-restart mid-distribution reward recalculation uses live (attacker-mutable) stake delegations instead of the epoch-boundary-frozen amounts, diverging from replay-only nodes - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`Bank::epoch_reward_status` (containing the frozen `all_stake_rewards` plan computed once at the epoch boundary) is never serialized into `BankFieldsToSerialize`/`SerializableVersionedBank`, so on snapshot restore it is rebuilt by `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards`, which recomputes each staker's reward from the *live* `StakesCache` at the restart slot rather than the delegation amounts that were frozen when the original plan was computed. An attacker who merges/splits their own already-active stake account between the epoch boundary and a snapshot slot taken inside the distribution window can therefore cause a restarted node's recalculated reward for that stake account to differ from the value already baked into `all_stake_rewards` on every non-restarted (pure-replay) node.

### Finding Description
On a normal (non-restarted) path, `all_stake_rewards`/`partition_indices` are computed exactly once at the epoch boundary and then propagated *unchanged* through every subsequent child bank via
`epoch_reward_status: parent.epoch_reward_status.clone()` [1](#0-0)  — later blocks only pay out partitions, they never recompute amounts from current account state.

`BankFieldsToSerialize` and `SerializableVersionedBank` do not include `epoch_reward_status` [2](#0-1) [3](#0-2) , so on `Bank::new_from_fields` restore the field is reset to `EpochRewardStatus::default()` [4](#0-3)  and reconstructed by `initialize_after_snapshot_restore` → `recalculate_partitioned_rewards_if_active` [5](#0-4) [6](#0-5) .

`recalculate_stake_rewards` derives `stake_delegations` from `self.stakes_cache.stakes()` at the *restart slot*, via `get_epoch_params_for_recalculation`, which reads `stakes.stake_delegations_vec()` — the live delegation set at call time, not a snapshot of what existed at the epoch boundary [7](#0-6) [8](#0-7) . The denominator (total delegated stake / `RewardEpochDelegatedStakes`) is explicitly protected from drift by being fetched as a cached, frozen value via `AlpenglowEpochType::get`, but the per-account numerator (`Delegation.stake` for each staker) is not similarly frozen — it is read directly off the live `StakeAccount` in the current `StakesCache`.

For an already fully-active delegation (`activation_epoch <= rewarded_epoch < deactivation_epoch`), `Delegation::stake`/`stake_v2` for a past `rewarded_epoch` returns the raw current `stake` field, not a historically-frozen value. That raw field is directly mutable by the stake owner via ordinary `Merge`/`Split` stake instructions on their own already-delegated stake account — no privileged role, warmup delay, or leader/validator control is required, satisfying the "unprivileged attacker controlling their own accounts" constraint.

Exploit flow:
1. Epoch boundary bank computes and freezes `all_stake_rewards` (includes attacker's stake amount X) — this frozen list is what every non-restarted/replay-only node will pay out unchanged for the rest of the window.
2. Inside the distribution window (before the last partition), the attacker merges another of their own stake accounts into the target stake account (or splits it), changing its raw `Delegation.stake` field to Y ≠ X.
3. A node takes (or already scheduled) a snapshot at slot S inside the window and restarts.
4. `recalculate_stake_rewards` on that node recomputes the reward for the attacker's pubkey using the mutated stake Y instead of the frozen X, producing a different `stake_rewards`/`partition_indices` value than the canonical frozen plan used by non-restarted peers.
5. When `distribute_partitioned_epoch_rewards` later pays out this partition, the restarted node credits a different lamport amount than replay-only peers, changing capitalization and the bank hash for that slot on the restarted node relative to the rest of the cluster.

No existing guard (ancestor/ancestors check, ref-count, ancestor ancestors, ancestors gating) prevents this because the recalculation is explicitly designed to read the *current* `StakesCache`, not a historical snapshot; there is no code path that freezes/serializes the per-account delegation amounts used for the original calculation.

### Impact Explanation
This is a snapshot-vs-replay fidelity break (an honest node that restarts from a snapshot taken mid-distribution can diverge in capitalization/bank hash from honest nodes that never restarted), which matches the "snapshot-fidelity"/bank-hash divergence category explicitly named in the prompt. The scope is limited to nodes that happen to restart from a snapshot inside a reward-distribution window and to stake accounts whose delegation amount was mutated (merge/split) by their owner between the epoch boundary and that snapshot slot — this is a normal, unprivileged, low-cost user action.

### Likelihood Explanation
Feasibility requires: (a) a node restarts from a snapshot taken strictly inside the distribution window — a routine, config-driven event (validators regularly restart from local/incremental snapshots, and cluster-provided snapshots are frequently mid-epoch), and (b) the attacker performs an ordinary `Merge`/`Split` on their own already-delegated stake account timed to land between the epoch boundary and the snapshot slot. Both are attacker-controllable/observable (snapshot intervals are periodic and public via slot/block-height), making repeated attempts straightforward. This is not a one-off; the attacker can retry every distribution window.

### Recommendation
Either (1) serialize `epoch_reward_status` (or at minimum the frozen `all_stake_rewards`/`partition_indices`/`distribution_starting_block_height`) as part of `BankFieldsToSerialize`/`SerializableVersionedBank` and the corresponding deserialize structs so restart reconstructs the exact frozen plan instead of recomputing it; or (2) if recalculation must remain used, freeze the per-account delegation amounts (not just the aggregate denominator) at epoch-boundary time (e.g., in the `EpochRewards` sysvar or an equivalent immutable structure) so `recalculate_stake_rewards` cannot observe post-boundary account mutations.

### Proof of Concept
Rust integration test plan (extending the existing `test_recalculate_partitioned_rewards`/`test_initialize_after_snapshot_restore` harness in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`):
1. Build a reward bank with >=2 partitions (`create_reward_bank_with_specific_stakes`), cross the epoch boundary, and capture `EpochRewardStatus::Active(EpochRewardPhase::Calculation).all_stake_rewards` as the frozen `expected_rewards`.
2. Advance one slot into the distribution window (before the final partition), then have the attacker's own stake account (already included in `expected_rewards`) execute a `Merge` (or manually mutate `Delegation.stake` via `StakesCache::check_and_store` in-test) to change its delegated stake.
3. Call `bank.recalculate_partitioned_rewards_if_active(...)` (simulating snapshot-restore reconstruction) and extract the new `all_stake_rewards`.
4. Assert `recalculated_rewards[attacker_index].inflation.stake_reward != expected_rewards[attacker_index].inflation.stake_reward` for the remaining (not-yet-paid) partitions containing the attacker's stake — demonstrating divergence from the frozen plan that a non-restarted sibling bank (built via plain `Bank::new_from_parent`, which just `.clone()`s `epoch_reward_status`) would have paid.
5. Extend to a differential/property test: fork two bank chains at the epoch boundary — one continuing via `Bank::new_from_parent` only, one that snapshot-serializes/restores at a randomized slot inside the window after the same attacker mutation — and assert their final `capitalization()`/bank hash match at window completion; expect the assertion to fail, confirming the divergence.

    /// Retrieves stake history and delegations for stake reward recalculation
    /// after snapshot restore.
    fn get_epoch_params_for_recalculation<'a>(
        &'a self,
        rewarded_epoch: Epoch,
        stakes: &'a Stakes<StakeAccount<Delegation>>,
    ) -> EpochRewardCalculateParamInfo<'a> {
        // Use `stakes` for stake-related info
        let stake_history = stakes.history().clone();
        let stake_delegations = stakes.stake_delegations_vec();

        // Use the VAT-filtered vote-account snapshot from epoch_stakes.
        // Recalculation should match the vote-account admission policy used for
        // distribution.
        let leader_schedule_epoch = self.epoch_schedule().get_leader_schedule_epoch(self.slot());
        let distribution_epoch_vote_accounts = self
            .epoch_stakes(leader_schedule_epoch)
            .expect("calculation should always run after Bank::update_epoch_stakes()")
            .stakes()
            .vote_accounts();
        let cached_vote_accounts =
            self.get_cached_vote_accounts(rewarded_epoch, distribution_epoch_vote_accounts);

        EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        }
    }

    /// If rewards are still active, recalculates partitioned stake rewards and
    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
        drop(stakes);
        let partition_indices = hash_rewards_into_partitions(
            &stake_rewards,
            &epoch_rewards_sysvar.parent_blockhash,
            epoch_rewards_sysvar.num_partitions as usize,
        );
        (stake_rewards, partition_indices)
    }
