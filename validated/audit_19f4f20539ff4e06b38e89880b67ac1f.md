### Title
`ensure_match_transaction_info` (execution `verify_execution` replay path) skips checkpoint-hash comparison, letting a divergent authenticated position/state root pass replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the integrity check used both by `db-tool`'s replay/verify tooling and by `ChunkExecutorInner::verify_execution` during backup/state-sync replay against previously-committed `TransactionInfo`s [2](#0-1) . It explicitly compares status, gas, write-set hash and event root hash against the given `TransactionInfo`, but a code comment states it deliberately does **not** validate `state_checkpoint_hash` / hot-state / `position_state_checkpoint_hash` [3](#0-2) .

### Finding Description
`ensure_match_transaction_info` verifies exactly four fields between a freshly-computed `TransactionOutput` and a trusted, proof-backed `TransactionInfo`: status, gas used, write-set hash (`state_change_hash`), and event root hash [4](#0-3) . The function's trailing comment acknowledges the gap directly: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [5](#0-4) .

This function is the sole per-transaction correctness gate in the replay path: `ChunkExecutorInner::verify_execution` re-executes transactions locally and calls it to compare the freshly computed output against the `TransactionInfo` that was persisted/synced from a remote peer or backup archive [6](#0-5) . The `TransactionInfo` carries `state_checkpoint_hash()`, which is meant to authenticate the resulting global/position state root at that version (used elsewhere, e.g. accumulator commitment). Because the state/hot-state/position checkpoint hash comparison is skipped here, a locally computed state root that differs from the one embedded in the trusted `TransactionInfo` (and thus from the one committed under the accumulator/ledger-info signature) will not cause `verify_execution` — nor `db-tool`'s replay-verify — to fail, as long as write-set bytes, events, gas, and status happen to match.

### Impact Explanation
This breaks the state-commitment/proof-integrity invariant that "committed state must equal the correct VM result, and the checkpoint hash must correctly and verifiably bind the resulting state". Divergence here is exactly the kind of "hard-fork-only divergence during commit, replay, or proof verification" called out in the state-integrity gate: a corrupted/incorrect state root (e.g. from a JMT/summary bug, a resource-group materialization bug, or a state-sync backup that was tampered with) can be replayed and accepted as verified even though the position/state root it implies is wrong. Any downstream tooling or automated integrity job (`db-tool replay-verify`, `replay_on_archive`) relying on `ensure_match_transaction_info`/`verify_execution` to catch state divergence gives a false "OK" signal, masking silent ledger corruption that would only be caught later (if at all) when state proofs are independently checked against a signed `LedgerInfo`.

### Likelihood Explanation
This is a real, currently-acknowledged gap (the TODO comment is present in shipped code), not a hypothetical. It requires no privileged access to trigger — any divergence introduced by a bug in state computation, or a maliciously/faulty backup archive/replay source supplying transactions+write-sets+events+`TransactionInfo` whose `state_change_hash`/gas/status/events match but whose true resultant state root differs, would sail through `verify_execution`. It is gated behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/checkpoint-hash features per the comment, limiting current blast radius to configurations where that flag matters, but the comment itself flags this as a "must be fixed before enabling" item, i.e., a known-open integrity hole in the verification path.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()`, hot-state checkpoint hash, and `position_state_checkpoint_hash()` (when present in `txn_info`) against those computed for the output/parent state, failing replay/verify when any diverges, consistent with the TODO already recorded in the code.

### Proof of Concept
Conceptual repro (cannot execute the full node/VM here to produce concrete hash bytes):
1. Take a chunk of transactions/write-sets/events/`TransactionInfo`s from a backup/state-sync source where the `state_checkpoint_hash` in the `TransactionInfo` was computed against a *different* (incorrect) resultant state tree than what local re-execution produces, while keeping the write-set bytes, events, gas, and status identical.
2. Feed this into `ChunkExecutorInner::verify_execution` (or `db-tool`'s replay-verify entry point that calls `ensure_match_transaction_info`) [7](#0-6) .
3. Observe that `Ok(())` is returned because only status/gas/write-set-hash/event-root are checked [4](#0-3) , despite the state/position checkpoint root being wrong — confirming replay-verify accepts a divergent authenticated state root as valid.

*Note: full exploitation confidence is limited by the fact that this path is currently only load-bearing when `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/trading-native checkpoint hashes are enabled; I could not fully trace all current on-chain gating flags for that feature within the available index, so likelihood should be validated against the current feature-flag rollout state before treating this as immediately mainnet-exploitable.*

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
