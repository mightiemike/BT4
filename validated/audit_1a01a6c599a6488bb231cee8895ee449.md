### Title
Raw attacker-supplied session token reflected unsanitized in HTTP error response via `InvalidJwtError` message - ([File: packages/apps/shopify-api/lib/session/decode-session-token.ts])

### Summary
`decodeSessionToken` interpolates the raw, attacker-controlled `token` string directly into the `InvalidJwtError` message without sanitization or truncation. This message is later sent verbatim to the client via `res.send(error.message)` in `handleSessionError` in `shopify-app-express/src/middlewares/validate-authenticated-session.ts`, reflecting arbitrary attacker input back in the HTTP response body.

### Finding Description
In `decodeSessionToken` (`packages/apps/shopify-api/lib/session/decode-session-token.ts` lines 28-32), any failure of `jose.jwtVerify` (malformed JWT, bad signature, wrong algorithm, etc.) is caught and re-thrown as:
```
throw new ShopifyErrors.InvalidJwtError(`Failed to parse session token '${token}': ${error.message}`);
``` [1](#0-0) 

The full raw `token` (the entire attacker-supplied Bearer header value, unbounded in length and content) is embedded unsanitized into the error message.

This function is reached through the request path for embedded apps in `getCurrentSessionId` (`packages/apps/shopify-api/lib/session/session-utils.ts` lines 42-56), which extracts the `Bearer` token from the `Authorization` header and calls `decodeSessionToken(config)(matches[1])` directly on attacker input with no prior sanitization or validation of the token's shape. [2](#0-1) 

In `shopify-app-express`, `validateWithAuthCodeFlow` calls `api.session.getCurrentId(...)`, catches any thrown error, and calls `handleSessionError(req, res, error)`:
```
} catch (error) {
  config.logger.error(`Error when loading session from storage: ${error}`);
  handleSessionError(req, res, error);
  return undefined;
}
``` [3](#0-2) 

`handleSessionError` then does, for `InvalidJwtError`:
```
case error instanceof InvalidJwtError:
  res.status(401);
  res.send(error.message);
  break;
``` [4](#0-3) 

`res.send(string)` in Express sets `Content-Type: text/html` by default unless already set, so the raw token content — fully attacker-controlled and never HTML/CRLF-escaped — is reflected back in a `text/html` response body. No JWT signature check occurs before this reflection (the failure happens during/because of signature/format verification), so this is reachable with zero prior authentication, using only a crafted `Authorization: Bearer <token>` header against any route protected by `validateAuthenticatedSession` on a non-token-exchange, embedded app configuration.

### Impact Explanation
This is a reflected-content/log-injection surface, not a secret leak: it does not expose `apiSecretKey`, session tokens, or other internal state — only the attacker's own submitted input is echoed back. Depending on the host app's response handling and any downstream logging/monitoring that captures response bodies, this could enable reflected HTML injection (subject to browser content-type sniffing and app-level CSP) or log-injection if the error is also logged elsewhere with the same unsanitized content (`config.logger.error` also logs the raw error, including the token, into application logs). This matches Shopify's bounty impact class of "reflected content/log injection" at a low-to-moderate severity rather than a confirmed secret disclosure or session forgery.

### Likelihood Explanation
Trivially reproducible by any unauthenticated/anonymous client: send any malformed string as `Authorization: Bearer <crafted-string>` to a route protected by `validateAuthenticatedSession` on an embedded app not using `future.tokenExchange`. No credentials, secrets, or prior session are required — only a network request.

### Recommendation
- Do not interpolate the raw `token` value into `InvalidJwtError` messages in `decode-session-token.ts`; instead log/report a fixed, generic message (e.g., `'Failed to parse session token'`) or only include a truncated/hashed reference for debugging, and log the raw token (if needed) only server-side with proper escaping.
- In `handleSessionError`, avoid sending `error.message` directly to the client for internal errors; return a generic, fixed error message and log full details server-side only.

### Proof of Concept
```ts
// packages/apps/shopify-app-express/src/middlewares/__tests__/validate-authenticated-session.test.ts (illustrative)
import request from 'supertest';

it('reflects raw attacker-controlled token content in 401 response body', async () => {
  const maliciousToken = '<script>alert(1)</script>\r\nX-Injected: true';

  const res = await request(app)
    .get('/protected-route')
    .set('Authorization', `Bearer ${maliciousToken}`);

  expect(res.status).toBe(401);
  // Raw attacker payload reflected unsanitized in the response body
  expect(res.text).toContain(maliciousToken);
});
```
Expected: the malformed token content (including `<script>` or CRLF-adjacent text) appears verbatim in the 401 response body, confirming reflection of unsanitized attacker input via `InvalidJwtError.message`.

function handleSessionError(_req: Request, res: Response, error: Error) {
  switch (true) {
    case error instanceof InvalidJwtError:
      res.status(401);
      res.send(error.message);
      break;
    default:
      res.status(500);
      res.send(error.message);
      break;
  }
}
