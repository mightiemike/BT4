### Title
Wallet Contract hardcodes a single non-network-specific `AddressRegistrar` account, causing the relayer-fee refund to fire even though the underlying transfer permanently fails on any deployment other than the one true registrar chain - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (the EVM-emulation contract deployed on ETH‑implicit accounts, reachable by anyone submitting an RLP-encoded "Ethereum" transaction via `rlp_execute`) hardcodes the `AddressRegistrar` account id into a single build-time constant that is **not** varied per network the way `CHAIN_ID` is. Unlike `CHAIN_ID`, which is deliberately set differently for `wallet_contract_mainnet.wasm`, `wallet_contract_testnet.wasm`, and `wallet_contract_localnet.wasm` in `runtime/near-wallet-contract/build.rs`, the `ADDRESS_REGISTRAR_ACCOUNT_ID` file baked into the contract with `std::include_str!("ADDRESS_REGISTRAR_ACCOUNT_ID")` [1](#0-0)  contains one static value, `address-map.near` [2](#0-1) , that is compiled into every network's wasm artifact identically (the build script only substitutes `CHAIN_ID`, never the registrar id) [3](#0-2) .

### Finding Description
This mirrors the reported bug class exactly: an on-chain code path that unconditionally calls out to a **hardcoded external account/address** which is only guaranteed to exist and behave correctly on one specific deployment (there, the Ethereum-mainnet Chainlink Feed Registry at a fixed address; here, whatever NEAR account happens to be registered as `address-map.near` on the specific network the wasm's build pipeline used).

The reachable path is:
1. Any signer/relayer submits `rlp_execute(target, tx_bytes_b64)` to an ETH-implicit account (a normal transaction, no privilege required) [4](#0-3) .
2. If the decoded transaction is a base-token transfer whose `target` is *another* eth-implicit account, `inner_rlp_execute` defers the nonce increment and schedules a cross-contract call to the hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` to check if that address is a registered named account [5](#0-4) .
3. Critically, **before** that registrar call resolves, if the transaction carries a non-zero relayer `fee`, the contract unconditionally schedules a promise that pays the fee to the relayer (`predecessor_account_id`) [6](#0-5) .
4. The actual value transfer to `target` is only executed inside `address_check_callback`, and only in the `PromiseResult::Successful` branch where the registrar reports `None` (not registered) [7](#0-6) . If the registrar call instead resolves as `PromiseResult::Failed` — which is exactly what happens whenever `address-map.near` does not exist or is not the deployed `AddressRegistrar` contract on the network in question — the callback simply returns an error `ExecuteResponse` and never calls `action_to_promise`, so the user's transfer never executes [8](#0-7) .

Because the fee-refund promise (step 3) and the registrar-lookup promise (step 2) are both fired from `inner_rlp_execute` independently rather than being conditioned on the ultimate success of the transfer, any relayer fee for this class of transaction is paid out even though the registrar dependency is structurally guaranteed to fail on every network deployment except the one the wasm happened to be built against.

### Impact Explanation
On any chain where `address-map.near` is not the actual `AddressRegistrar` contract (any non-mainnet network using the mainnet-built wasm, any testnet/localnet where the account is missing or different, or any future L2/appchain deployment of this same wallet-contract mechanism), every attempted eth-implicit-to-eth-implicit base-token transfer with a relayer fee results in:
- The relayer's fee being paid unconditionally (fee bypass — the relayer is compensated for a service that can never be completed on that chain), and
- The user's actual funds transfer never being executed, permanently, for this entire class of transactions on that deployment.

This is a fee/value-bypass matching the "fee or gas bypass" / "unauthorized value movement" acceptance criteria: value (the relayer fee) is extracted from the user account without the corresponding service being deliverable, deterministically and repeatably, purely because of the hardcoded, non-per-network registrar address.

### Likelihood Explanation
High for any deployment other than the one canonical network where `address-map.near` is the genuine registrar. The build script (`build.rs`) shows the project's own convention for hardcoded, network-dependent constants is to parameterize them per target network (as done for `CHAIN_ID`); the `ADDRESS_REGISTRAR_ACCOUNT_ID` was not given the same treatment, so the bug is triggered automatically and unconditionally by ordinary relayer/user transaction flow — no attacker action beyond normal usage is required.

### Recommendation
Treat `ADDRESS_REGISTRAR_ACCOUNT_ID` the same way `CHAIN_ID` is treated in `build.rs` — parameterize it per network build (mainnet/testnet/localnet, and any future chain) so the compiled wasm always points at a registrar account that actually exists and is the correct contract on that chain. Additionally, decouple the relayer fee-refund promise from unconditional dispatch: it should only be paid out after the transfer promise chain (including the registrar lookup and subsequent transfer) succeeds, not before.

### Proof of Concept
1. Deploy the `wallet_contract_mainnet.wasm` (or any wasm built with the checked-in `ADDRESS_REGISTRAR_ACCOUNT_ID = "address-map.near"`) on a network where `address-map.near` does not exist as the `AddressRegistrar` contract (e.g., a local sandbox, testnet, or any new L2/appchain deployment).
2. Create two ETH-implicit accounts, A and B, each with the Wallet Contract deployed.
3. Have the owner of A sign an Ethereum-style base-token-transfer transaction (via `rlp_execute`) targeting B, with `max_fee_per_gas`/`gas_limit` producing a non-zero relayer `fee`.
4. A relayer submits this via `rlp_execute`. `inner_rlp_execute` schedules (a) the fee-refund promise to the relayer, and (b) the cross-contract `lookup` call to `address-map.near` [9](#0-8) .
5. Because `address-map.near` does not exist/is not the registrar on this chain, the promise resolves as `PromiseResult::Failed`, and `address_check_callback` returns `success: false` without ever transferring funds to B [8](#0-7) .
6. Observe that the relayer nonetheless received the fee refund from step 4(a), while B never received the intended transfer — repeatable for every such transaction on this deployment.
