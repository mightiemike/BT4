## Analog Found

### Title
Cairo0 class cache is never revalidated against declared state, allowing stale/undeclared classes to be treated as declared - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` serves compiled classes from a long-lived, cross-block `ContractClassManager` cache. For Cairo1 classes it re-verifies declaration status against the authoritative state reader on every cache hit, but for Cairo0 (`RunnableCompiledClass::V0`) classes it skips this check entirely and trusts the cache unconditionally.

### Finding Description
The class cache is populated whenever any code path calls `get_compiled_class`, including speculative/concurrent execution, re-execution, and block building for proposals that may later be aborted, rejected, or reverted. The comment in the code explicitly acknowledges this staleness risk: [1](#0-0) 

For the `RunnableCompiledClass::V0(_)` arm, the branch is a no-op (`{}`), so no call to `self.state_reader.is_declared(class_hash)` is made — unlike the sibling branch for Cairo1 classes, which explicitly re-checks declaration and returns `StateError::UndeclaredClassHash` if the state reader disagrees with the cache: [2](#0-1) 

The `FetchCompiledClasses::is_declared` trait itself documents that it only meaningfully tracks Cairo1 declarations ("Cairo 0 classes always return `false`"), which is precisely why the Cairo0 path was left unchecked — but that design assumption breaks the safety property once a Cairo0 class hash has been cached from a state that is later invalidated (e.g., a reverted/aborted proposal, a speculative execution branch that is discarded, or any scenario where the same class hash is redeclared/undeclared across chain reorganizations).

This mirrors the reported bug class: an accounting/caching subsystem (`getTVL()` / Rio's internal withdrawal ledger in the original report; here, the process-wide compiled-class cache) is updated through one canonical path (declare transactions / committed state) but can also be populated or left stale via a different path (speculative execution of transactions referencing a class hash before its declaring transaction is finalized, or execution against a proposal that gets discarded). Because the cache is not re-synchronized with the authoritative state for Cairo0 classes, a divergence window is created where the cached value no longer reflects on-chain truth, and unlike the Cairo1 case, no self-healing check exists to catch it.

### Impact Explanation
If a Cairo0 class hash becomes cached (e.g., during speculative/concurrent execution of a transaction in a proposal that references the class) and that proposal/block is later discarded or reverted, any subsequent transaction from any sender that references the same class hash will be served the stale compiled class from the cache without any re-verification that it is actually declared in the current, canonical state. This allows an unprivileged transaction sender to have contract code executed under a class hash that is not actually declared on-chain, which can lead to execution results inconsistent with what an honest node without the poisoned cache would compute for the same block — a state/execution divergence risk between nodes with warm vs. cold caches, and a way to bypass the "declare before use" invariant enforced elsewhere in the system.

### Likelihood Explanation
Reaching this path only requires submitting ordinary transactions (e.g., an invoke or deploy referencing a Cairo0 class hash) around block-building/re-execution boundaries where speculative execution, aborted proposals, or reverts are already known to occur in this codebase (the Cairo1 branch's comment confirms "it might contain a declared class from a reverted block, for example" is a recognized, expected occurrence). No special privileges, node control, or network position are needed — an unprivileged transaction sender triggering `get_compiled_class` for a Cairo0 class hash under normal execution is sufficient to exercise the vulnerable branch.

### Recommendation
Apply the same re-verification performed for Cairo1 classes to the `RunnableCompiledClass::V0` branch: call `self.state_reader.is_declared(class_hash)` (or an equivalent authoritative declaration check that also covers Cairo0 classes) before trusting a cache hit, or otherwise invalidate/evict cached Cairo0 entries whenever the block/proposal that caused them to be cached does not commit.

### Proof of Concept
Not independently executable from the index alone — the exact trigger requires orchestrating a scenario where a Cairo0 class hash is cached from a discarded/reverted proposal and then queried again from a different (canonical) execution context, which spans the batcher/blockifier re-execution and revert machinery not fully visible in this trace. This should be validated with a Devin session that can build a reproduction combining `ContractClassManager` caching, block-building abort/rewind, and the code paths in `crates/blockifier/src/state/state_reader_and_contract_manager.rs` and `crates/blockifier/src/state/contract_class_manager.rs`.

    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
