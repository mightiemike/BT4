### Title
Caller deposit is permanently lost when intermediate cross-contract calls fail in the Wallet Contract's multi-step promise chain - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract's `rlp_execute` flow uses multi-step promise chains for ERC-20 transfers and address-registrar checks, tracking an external caller's attached deposit (`CallerDeposit`) so it can be refunded if the downstream action fails. However, the refund logic is only implemented in the final callback (`rlp_execute_callback`), not in the intermediate callbacks (`address_check_callback`, `nep_141_storage_balance_callback`) that handle the outcome of the registrar lookup and `storage_balance_of` query. If those intermediate cross-contract calls fail, the caller's deposit is silently dropped with no compensating refund promise, mirroring the reported bug class of asymmetric/incomplete handling of an external callback's success/failure outcomes.

### Finding Description
`CallerDeposit` is explicitly documented as existing "to refund the caller's deposit if the cross-contract call fails": [1](#0-0) 

The only place that actually performs this refund is `rlp_execute_callback`, on `PromiseResult::Failed`: [2](#0-1) 

But for ERC-20 transfers and eth-implicit address-check transfers, the promise chain first calls an external contract (`storage_balance_of` on the token, or `lookup` on the address registrar) before reaching `rlp_execute_callback`. Those results are consumed in `address_check_callback` and `nep_141_storage_balance_callback`, which receive `caller_deposit` as a parameter yet never refund it when the underlying `PromiseResult` is `Failed`:

- `address_check_callback`'s `Failed` arm returns an error `ExecuteResponse` without creating any refund promise, discarding `caller_deposit`: [3](#0-2) 
- `nep_141_storage_balance_callback`'s `Failed` arm has the identical pattern: [4](#0-3) 

In both cases `caller_deposit` is a function parameter that is only forwarded to a *subsequent* success-path promise (`.then(ext.rlp_execute_callback(caller_deposit))`); on the failure branch it is simply dropped and the function returns a plain value `ExecuteResponse`, which cannot itself move funds.

### Impact Explanation
`CallerDeposit::new` captures `attached_deposit` sent by an external (non-self) predecessor to the wallet contract: [5](#0-4) . This deposit is real NEAR held by the wallet contract, intended to reimburse whoever attached it (e.g., a relayer paying storage/registration costs on the user's behalf) if the underlying eth-emulated action does not complete. If the intermediate `storage_balance_of` query (e.g., token contract doesn't implement it, runs out of gas, or the account being queried is malformed) or the address-registrar `lookup` call fails, the wallet contract returns an error response but keeps the attached deposit with no code path ever created to send it back. This is a genuine, transaction-triggered, permanent loss of funds for the account that attached the deposit — funds become frozen inside the wallet contract's balance with no user-callable recovery path (the contract does not expose any manual withdrawal of stray balance for this scenario).

### Likelihood Explanation
Reaching this requires nothing privileged — any relayer or user submitting an eth-emulated `ft_transfer` (ERC20Transfer path) or an EOA base-token transfer to another eth-implicit address (`address_check` path) with a non-zero attached deposit can trigger it whenever the token contract's `storage_balance_of` view call or the address-registrar `lookup` call fails (e.g., malformed/non-standard NEP-141 token, insufficient prepaid gas for the view call, or a temporarily broken registrar). This does not require attacker collusion or a malicious external contract — an ordinary, unremarkable failure of an external view call is sufficient, making it readily reachable in normal operation.

### Recommendation
Mirror the refund logic used in `rlp_execute_callback` inside both `address_check_callback` and `nep_141_storage_balance_callback`'s `PromiseResult::Failed` arms: when the intermediate call fails, create a refund `Promise::new(account_id).transfer(...)` for `caller_deposit` before returning the error `ExecuteResponse`, exactly as already done at the end of the chain. Consider factoring this into a shared helper to avoid the asymmetry recurring as new multi-step flows are added.

### Proof of Concept
1. A relayer calls `rlp_execute` on a user's wallet contract with a non-zero attached deposit, encoding an ERC-20 transfer to an unregistered receiver on a token contract whose `storage_balance_of` implementation is missing, non-standard, or is only provided with insufficient gas (`NEP_141_STORAGE_BALANCE_OF_GAS = 5 Tgas`) causing it to fail.
2. `inner_rlp_execute` builds the promise chain `storage_balance_of(...).then(nep_141_storage_balance_callback(...))`, with `caller_deposit = Some(CallerDeposit { account_id: relayer, yocto_near: N })`: [6](#0-5) 
3. The `storage_balance_of` cross-contract call fails (`PromiseResult::Failed`), so `nep_141_storage_balance_callback` returns `ExecuteResponse { success: false, ... }` without emitting any refund transfer: [7](#0-6) 
4. The relayer's `N` yoctoNEAR remains in the wallet contract's balance permanently; no subsequent call path exists to reclaim it, since the nonce has already been incremented (transaction considered "used") and no compensating action was ever scheduled.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
