### Title
Floating-point proportional usage calculation in `UnDelegateResourceActuator::execute()` causes bandwidth/energy usage mis-accounting across multiple delegators sharing the same receiver - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The reported BendDAO bug is a class of "pooled accounting mismatch" issue: a per-position value (yield) is derived from a pooled/aggregate balance using a ratio computed at execution time, so when multiple positions share the same pool, the order of operations produces inconsistent, non-conservative results for individual positions. `UnDelegateResourceActuator::execute()` reproduces this same pattern for TRON's delegated resource (bandwidth/energy) accounting: it computes `transferUsage` proportionally from the receiver's *aggregate* frozen balance (`receiverCapsule.getAllFrozenBalanceForBandwidth()` / `getAllFrozenBalanceForEnergy()`), which is the sum of delegations from potentially many different owners, rather than from the specific delegation record being un-delegated.

### Finding Description
In `UnDelegateResourceActuator.execute()`, when an owner un-delegates bandwidth or energy previously delegated to a `receiverAddress`, the actuator computes how much of the receiver's currently consumed usage should be "clawed back" to the owner: [1](#0-0) [2](#0-1) 

`transferUsage` is computed as `receiverCapsule.getNetUsage() * (unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth())` using double-precision floating point, then cast to `long`. `getAllFrozenBalanceForBandwidth()` reflects the receiver's *total* frozen-for-bandwidth balance, which is the sum of the receiver's own frozen balance plus all delegations from every owner that has delegated to that receiver — i.e., a shared pool, analogous to the pooled `YieldAccount` ETH balance in the original finding. The ratio used to compute each individual owner's "share" of consumed usage is recalculated fresh at the time of each un-delegation call, using whatever the current aggregate `netUsage`/`getAllFrozenBalanceForBandwidth()` happen to be — it is not tracked per-delegation.

This means that when several distinct owners have each delegated resource to the same receiver and the receiver has consumed part of its bandwidth/energy, the first owner to un-delegate captures usage proportional to the *current* ratio, permanently changing `receiverCapsule.getNetUsage()`/`getEnergyUsage()` for the remaining delegators. Because the actual usage consumed is not tracked per-delegator (there is no equivalent of a "yield source shares" ledger per delegation, only an aggregate `netUsage` counter and aggregate `getAllFrozenBalanceForBandwidth()`), the value attributed to each subsequent un-delegator is skewed by the order in which un-delegations occur — exactly the same "first actor gets disproportionate benefit, later actors get a worse outcome" pattern the external report describes for `YieldStakingBase::stake()`/`getAccountYieldBalance()`.

### Impact Explanation
The impact is resource/reward accounting corruption: `receiverCapsule`'s `netUsage`/`energyUsage` counters can be transferred back to un-delegating owners in proportions that do not correspond to what each owner's specific delegated balance actually consumed, because the "shares" (aggregate frozen balance ratio) used for the calculation floats with concurrent, unrelated delegations/un-delegations from other owners. Depending on execution order, some owners can reclaim more usage credit than they are entitled to (at the expense of the receiver's or other owners' accounting), while others receive less — this is a resource-accounting corruption reachable purely through broadcast `UnDelegateResourceContract` transactions from unprivileged accounts, no special privileges required.

### Likelihood Explanation
This is triggerable by any account: any owner can `FreezeBalanceV2`, then `DelegateResourceContract` to any receiver, and any other owner can independently do the same to the same receiver, then both can `UnDelegateResourceContract` in any order. No privileged role or malicious peer/node is required — the entire flow is a sequence of ordinary broadcast transactions using existing actuators (`FreezeBalanceV2Actuator`, `DelegateResourceActuator`, `UnDelegateResourceActuator`).

### Recommendation
Track consumed usage per delegation record (or per delegator) rather than deriving each un-delegator's "clawback" share from the receiver's shared/aggregate frozen balance and usage counters at the time of the specific un-delegate call. Alternatively, ensure the proportional calculation is invariant to the order of concurrent delegate/un-delegate operations from unrelated owners, e.g., by snapshotting or accounting usage attribution at delegation time rather than recomputing it against a floating aggregate denominator at un-delegation time.

### Proof of Concept
1. Account `R` (receiver) exists.
2. Owner `A` freezes and delegates `X` bandwidth-TRX to `R` via `DelegateResourceContract`.
3. Owner `B` freezes and delegates `Y` bandwidth-TRX to `R` via `DelegateResourceContract`. Now `R.getAllFrozenBalanceForBandwidth() == X + Y`.
4. `R` consumes bandwidth over time, so `R.getNetUsage() > 0`.
5. Owner `A` sends `UnDelegateResourceContract` for `X`. In `UnDelegateResourceActuator.execute()` (lines 80-88), `transferUsage` is computed using `R.getNetUsage() * (X / (X + Y))` at this moment, and `R.getNetUsage()` is decremented by this amount.
6. Owner `B` then sends `UnDelegateResourceContract` for `Y`. The same formula is now applied to the *already-reduced* `R.getNetUsage()` and to `R.getAllFrozenBalanceForBandwidth()` (now just `Y`), so `B`'s clawback is computed against a different/reduced usage baseline than if `B` had un-delegated first.
7. Reversing the order of steps 5 and 6 produces different `transferUsage` outcomes for `A` and `B`, demonstrating that the amount of "usage" credited back to each delegator depends on un-delegation order rather than on each delegator's own actual contribution/consumption — the same class of pooled-accounting mismatch as the original finding.
