### Title
`DelegateAction` (Meta-Transaction) Signature Lacks Chain-ID Binding — Cross-Chain Replay of Signed Delegate Actions - (File: `core/primitives/src/action/delegate.rs`)

---

### Summary

The `DelegateAction` (NEP-366 meta-transaction) signing scheme does not include any chain-specific identifier in the signed payload. The hash that a user signs covers only a fixed protocol discriminant plus the action fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). None of these fields are chain-specific. A valid `DelegateAction` signature produced on NEAR testnet is cryptographically identical to one on mainnet (or any NEAR fork) for the same account, key, and nonce. An attacker who intercepts a signed `DelegateAction` can wrap it in a fresh outer `SignedTransaction` targeting mainnet and execute the inner actions under the victim's identity on mainnet without the victim's consent.

---

### Finding Description

`DelegateAction::get_nep461_hash()` computes the hash that the user signs:

```rust
// core/primitives/src/action/delegate.rs  lines 353-357
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}

`SignableMessage` serialises as `discriminant || msg`:

```rust

The `discriminant` is the compile-time constant `2^30 + 366` (NEP-366), identical on every NEAR network:

```rust

``` [3](#0-2) 

The `DelegateAction` struct itself contains no chain-specific field:

```rust
// core/primitives/src/action/delegate.rs  lines 46-64
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,

    pub public_key: PublicKey,

``` [4](#0-3) 

The runtime verifier `apply_delegate_action` checks the signature, expiry, sender match, and nonce — but never checks which chain the action was intended for:

```rust
// runtime/runtime/src/actions.rs  lines 430-448
if !signed_delegate_action.verify() { ... }
if apply_state.block_height > delegate_action.max_block_height() { ... }
if delegate_action.sender_id().as_str() != sender_id.as_str() { ... }
validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
``` [5](#0-4) 

**Contrast with regular `SignedTransaction`:** every outer transaction carries a `block_hash` field that is chain-specific (a recent block hash from the target chain). The `chain_validate` closure in chunk production rejects transactions whose `block_hash` is not within the validity window of the current chain:

```rust
// chain/chain/src/runtime/mod.rs  line 1058
if !chain_validate(&validated_tx.to_signed_tx()) { ... }
``` [6](#0-5) 

The inner `DelegateAction` has no equivalent binding. The outer transaction's `block_hash` binds the *relayer's* transaction to a chain, but the *user's* inner signature is chain-agnostic.

**Note:** The ETH-implicit wallet contract (`near-wallet-contract`) correctly enforces chain ID for Ethereum-style transactions:

```rust
// runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs  line 328-329
if tx.chain_id != Some(CHAIN_ID) {
    return Err(Error::Relayer(RelayerError::InvalidChainId));
}
``` [7](#0-6) 

This protection is absent from the native `DelegateAction` path.

---

### Impact Explanation

An attacker who obtains a `SignedDelegateAction` intended for testnet (e.g., from a public relayer API, a broadcast, or a leaked payload) can:

1. Wrap it in a new outer `SignedTransaction` addressed to mainnet with a valid mainnet `block_hash`.
2. Submit it to mainnet.
3. If the victim's account exists on mainnet with the same public key and the nonce is valid, the inner actions execute under the victim's `sender_id` on mainnet.

The inner actions can be any `NonDelegateAction`: `Transfer`, `FunctionCall`, `AddKey`, `DeleteKey`, `DeployContract`, etc. This enables unauthorized fund transfers, unauthorized key management, and unauthorized contract calls — all attributed to the victim's account.

---

### Likelihood Explanation

- Many developers and users maintain the same named account on both mainnet and testnet with the same key pair.
- Relayer services often expose public HTTP endpoints that log or broadcast `SignedDelegateAction` payloads.
- The `max_block_height` field provides expiry, but block heights on mainnet and testnet are numerically close (both have been running for years and are within the same order of magnitude), so a recently signed action is valid on both chains simultaneously.
- The nonce is per-access-key; if the victim has used the key more on testnet than mainnet, the testnet nonce is ahead and the mainnet nonce is still valid for replay.
- No special privilege is required: any unprivileged observer of a `SignedDelegateAction` can perform the replay.

---

### Recommendation

Include the chain's genesis ID (chain ID string + genesis block hash, as defined in `GenesisId`) or at minimum the chain ID string in the signed payload of `DelegateAction`. The `DelegateAction` struct should gain a `chain_id: String` field (or the `SignableMessage` wrapper should include it), and `get_nep461_hash()` must incorporate it before hashing. The runtime verifier `apply_delegate_action` must then assert that the chain ID in the action matches `apply_state`'s chain ID. This mirrors the fix applied in the Term Finance report (adding `block.chainid` to the signed hash) and the existing practice in the wallet contract (`CHAIN_ID` constant baked into each per-network build).

---

### Proof of Concept

```
1. Alice has account "alice.near" on both testnet and mainnet,
   same ED25519 key pair, mainnet access-key nonce = 5.

2. Alice signs a DelegateAction on testnet:
     sender_id    = "alice.near"
     receiver_id  = "bob.near"
     actions      = [Transfer { deposit: 10 NEAR }]
     nonce        = 6          // valid on testnet (ak_nonce=5)
     max_block_height = 200_000_000  // far future, valid on both chains
     public_key   = <Alice's key>
   Hash = SHA256( LE32(2^30+366) || borsh(DelegateAction) )
   Signature = Sign(Hash, Alice's private key)

3. Attacker intercepts the SignedDelegateAction from the testnet relayer.

4. Attacker constructs a new outer SignedTransaction on mainnet:
     signer_id    = <attacker's account>
     receiver_id  = "alice.near"
     actions      = [Delegate(SignedDelegateAction from step 2)]
     block_hash   = <recent mainnet block hash>
   Signs with attacker's own key and submits to mainnet.

5. Mainnet runtime calls apply_delegate_action:
   - signed_delegate_action.verify() → TRUE
     (same key, same hash, chain-agnostic)
   - block_height (mainnet) ≤ max_block_height → TRUE
   - sender_id == tx.receiver_id ("alice.near") → TRUE
   - validate_delegate_action_key: ak_nonce=5, delegate_nonce=6 → VALID
   - New receipt: predecessor="alice.near", receiver="bob.near",
     actions=[Transfer 10 NEAR]

6. Bob receives 10 NEAR from Alice on mainnet.
   Alice never authorised this mainnet transfer.
```
