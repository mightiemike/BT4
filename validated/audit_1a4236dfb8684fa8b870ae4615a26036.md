Based on my research, I found the strongest analog to the mempool memory-limit issue within AccountsDB's cache flush architecture.

### Title
Unbounded write-cache memory growth from unrooted slots that are permanently excluded from size-based eviction - (File: accounts-db/src/accounts_db.rs)

### Summary
The accounts write cache (`AccountsCache`) enforces a size limit (`write_cache_limit_bytes` / `WRITE_CACHE_LIMIT_BYTES_DEFAULT`) only against *rooted* slots. Unrooted slots are structurally exempt from this limit and are never flushed or evicted by the size-based mechanism, so their accumulated account data counts against no cap at all.

### Finding Description
`should_aggressively_flush_cache` gates flushing on both the cache exceeding `write_cache_limit_bytes` and the existence of unflushed roots: `self.write_cache_limit_bytes.unwrap_or(WRITE_CACHE_LIMIT_BYTES_DEFAULT) < self.accounts_cache.size() && self.accounts_cache.num_unflushed_roots() > 0` [1](#0-0) . `flush_accounts_cache` explicitly documents that it never purges unrooted slots: "we don't purge unrooted slots here because there may be ongoing scans/references for those slots, let the `Bank::drop()` implementation do cleanup instead on dead banks" [2](#0-1) .

This behavior is directly validated by the test suite, whose comment states plainly: "unrooted slots are never evicted by the flush path, so they will always be in the cache regardless of the total size" [3](#0-2) , and the corresponding assertions confirm every unrooted slot remains cached irrespective of `write_cache_limit_bytes` [4](#0-3) .

The `AccountsCache` itself has no independent per-slot or aggregate size cap for unrooted content — `size()` simply reports `total_size` and `store()` unconditionally inserts into whichever slot cache is being targeted, with no rejection path for unrooted slots exceeding any threshold [5](#0-4) [6](#0-5) . The only eviction path for an unrooted slot is `remove_unrooted_slots`/`purge_slot`, driven externally by replay stage's fork-pruning logic, not by any accounts-db memory-pressure signal [7](#0-6) .

This mirrors the reported mempool bug class precisely: a structure that tracks a size/count limit for one subset of its content (rooted slots / "tracked" pool) but exempts another subset (unrooted slots / analogous to unbounded per-address flooding) from any enforcement, allowing that unbounded subset to grow memory usage without limit.

### Impact Explanation
If unrooted (not-yet-rooted) banks accumulate — e.g., during a period of chain instability, extended forking, or repeated duplicate/discarded blocks before the fork choice rule converges — every account write made while replaying those banks stays resident in the write cache with no size ceiling, since `write_cache_limit_bytes` cannot trigger any eviction for them. Because slot caches are only removed once ReplayStage explicitly calls `remove_unrooted_slots` (bank drop/purge), the write cache can grow proportionally to the amount of transaction/account-write activity across all outstanding unrooted forks. This can drive a node toward OOM, a scenario the accounts-db side of AccountsDb is otherwise designed to guard against for rooted data via `write_cache_limit_bytes`.

### Likelihood Explanation
The condition requiring many concurrent unrooted banks to persist for an extended period is not a purely theoretical concern in Solana's fork-based consensus (e.g., under partition, slow root advancement, or a burst of duplicate blocks), but it does depend on external conditions (fork depth/duration) rather than being trivially triggerable by an ordinary unprivileged transaction sender alone, since bank/slot creation is driven by the leader schedule and consensus, not by end users directly. The likelihood is therefore moderate — it requires abnormal cluster conditions rather than a single crafted transaction, unlike the mempool bug where any user could flood the pool.

### Recommendation
Give the write cache an independent, always-enforced size/entry cap that also applies to unrooted slots — e.g., track memory used by unrooted slot caches separately and, once a configurable ceiling is reached, either reject/backpressure further unrooted writes or force eviction of the oldest/least-referenced unrooted slot caches (subject to the existing scan-safety invariants already respected by `remove_unrooted_slots`). At minimum, `should_aggressively_flush_cache` and `flush_accounts_cache` should be extended so a global cache-size ceiling (covering both rooted and unrooted slots) can still trigger corrective action, rather than being entirely gated on the presence of unflushed roots.

### Proof of Concept
1. Configure `write_cache_limit_bytes` to a small value (as done in the existing regression test `run_test_flush_accounts_cache_if_needed` in `accounts-db/src/accounts_db/tests/impl.rs`).
2. Store many accounts across `num_unrooted` unrooted slots without ever rooting them (simulating multiple long-lived forks under normal replay), then call `flush_accounts_cache(false, None)`.
3. Observe (as the existing test already demonstrates) that `accounts_cache.num_slots()` equals `num_unrooted` regardless of how far `total_slots` exceeds `max_cache_slots()`/`write_cache_limit_bytes` — i.e., cache size for unrooted content is unbounded by design [8](#0-7) .

fn run_test_flush_accounts_cache_if_needed(num_roots: usize, num_unrooted: usize) {
    let mut db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    db.write_cache_limit_bytes = Some(max_cache_slots() as u64);
    let space = 1; // # data bytes per account. write cache counts data len
    let account0 = AccountSharedData::new(1, space, &Pubkey::default());
    let mut keys = vec![];
    let num_slots = 2 * max_cache_slots();
    for i in 0..num_roots + num_unrooted {
        let key = Pubkey::new_unique();
        db.store_for_tests((i as Slot, &[(&key, &account0)][..]));
        keys.push(key);
        db.mark_slot_frozen(i as Slot);
        if i < num_roots {
            db.add_root(i as Slot);
        }
    }

    db.flush_accounts_cache(false, None);

    let total_slots = num_roots + num_unrooted;
    // If there's <= the max size, then nothing will be flushed from the cache
    if total_slots <= max_cache_slots() {
        assert_eq!(db.accounts_cache.num_slots(), total_slots);
    } else {
        // Otherwise, all roots are flushed to storage and all unrooted slots remain
        // in the cache. unrooted slots are never evicted by the flush path, so they will
        // always be in the cache regardless of the total size.
        assert_eq!(db.accounts_cache.num_slots(), num_unrooted);
        for root_slot in 0..num_roots {
            assert!(
                db.accounts_cache.slot_cache(root_slot as Slot).is_none(),
                "root_slot {root_slot} should have been flushed from cache"
            );
        }
        for unrooted_slot in num_roots..total_slots {
            assert!(
                db.accounts_cache
                    .slot_cache(unrooted_slot as Slot)
                    .is_some(),
                "unrooted_slot {unrooted_slot} should remain in cache"
            );
        }
    }

    pub fn store(
        &self,
        slot: Slot,
        pubkey: &Pubkey,
        account: AccountSharedData,
    ) -> Arc<CachedAccount> {
        let slot_cache = self.slot_cache(slot).unwrap_or_else(||
            // DashMap entry.or_insert() returns a RefMut, essentially a write lock,
            // which is dropped after this block ends, minimizing time held by the lock.
            // However, we still want to persist the reference to the `SlotStores` behind
            // the lock, hence we clone it out, (`SlotStores` is an Arc so is cheap to clone).
            self
                .cache
                .entry(slot)
                .or_insert_with(|| self.new_inner())
                .clone());

        let (item, is_new_key) = slot_cache.insert(pubkey, account);
        if is_new_key {
            // Only update the index when the pubkey is new to this slot. Overwrites within the
            // same slot (is_new_key = false) cannot update the index because the ref count was
            // already incremented when the pubkey was first stored in this slot
            self.index.insert(pubkey, slot);
        }
        item
    }
