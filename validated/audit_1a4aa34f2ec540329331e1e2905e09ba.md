This confirms the analog: `performTokenExchange` (in `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`) is reachable per-request from any embedded-app HTTP call carrying a session token, and it calls `config.sessionStorage.storeSession(offlineSession)` (and the online-token variant) any time an existing session is missing/expired, using the deterministic id `offline_<shop>` (or `<shop>_<userId>` for online) from `getOfflineId`/`getJwtSessionId` in `packages/apps/shopify-api/lib/session/session-utils.ts`. The `KVSessionStorage.storeSession` in `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts` then unconditionally appends that same id to the shop's id list via `addShopIds` without checking for an existing entry, exactly mirroring the `addToken` bug class of "no duplicate check before adding to an array."

### Title
Unbounded duplicate session-id accumulation in KV session storage's shop index - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`KVSessionStorage.storeSession` calls the private `addShopIds` helper on every invocation, which reads the shop's id-list key and appends the new id(s) with no check for whether the id is already present, then writes the concatenated array back.

### Finding Description
`storeSession` is:
```ts
public async storeSession(session: Session): Promise<boolean> {
  await this.namespace.put(session.id, JSON.stringify(session.toPropertyArray(true)));
  await this.addShopIds(session.shop, [session.id]);
  return true;
}
```
and
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
}
``` [1](#0-0) [2](#0-1) 

There is no `.includes()` / de-duplication check comparable to the "duplicate token" fix recommended in the referenced yaxis finding. Session ids are deterministic: `getOfflineId` returns `offline_<shop>` and `getJwtSessionId` returns `<shop>_<userId>` [3](#0-2) . The token-exchange middleware, which is invoked on ordinary embedded-app HTTP requests whenever no active session is cached, calls `storeSession` with these deterministic ids every time the cached session is missing/expired:
```ts
const offlineSession = await exchangeToken(...);
await config.sessionStorage.storeSession(offlineSession);
...
if (config.useOnlineTokens) {
  const onlineSession = await exchangeToken(...);
  await config.sessionStorage.storeSession(onlineSession);
}
``` [4](#0-3) 

Because the same deterministic id can legitimately be re-stored many times (session expiry, retries, multiple tabs/users, revoked/reinstalled sessions, or simply repeated 401/expiry cycles), each `storeSession` call appends another copy of the same id string to the shop's `shop:<shop>` index array, which is never de-duplicated by `addShopIds` or by `removeShopIds` (which only filters exact matches when deleting, and leaves any surviving duplicates from earlier calls intact) [5](#0-4) .

### Impact Explanation
The `shop:<shop>` KV value grows without bound as sessions are naturally re-stored over the life of an installation, eventually approaching Cloudflare KV's per-value size limit and causing `put` to fail — a self-inflicted denial of service on the auth/session-refresh path (`storeSession`/`findSessionsByShop`) for that shop. `findSessionsByShop` also returns increasingly many duplicate `Session` objects for the same id [6](#0-5) , which can corrupt any downstream logic (e.g., billing, multi-session enumeration) that assumes one entry per stored session, similar in kind to the double-counting impact described in the referenced report.

### Likelihood Explanation
This requires no privileged action — it is triggered purely by normal, unprivileged use of the app (repeated legitimate token-exchange calls that any installed merchant's browser/app-bridge session naturally performs whenever cached session expires), and accumulates deterministically over the app's lifetime, so likelihood of eventual impact is high for any app using `KVSessionStorage` with token exchange or online-session usage patterns that call `storeSession` more than once per shop/user id.

### Recommendation
In `addShopIds`, check whether each id already exists in `shopIds` before appending (e.g., `const merged = Array.from(new Set([...shopIds, ...ids]))`), so re-storing an existing session id is a no-op for the index, mirroring the deduplication check recommended in the source report for `addToken`.

### Proof of Concept
1. Configure an embedded app using `KVSessionStorage` with `config.useOnlineTokens` (or the offline-only flow) and mount `performTokenExchange` as the auth middleware, as in `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`.
2. As a normal merchant, make a request with a session token whenever no active offline/online session is currently loaded (e.g., after the loaded session's `isActive` check fails due to expiry) [7](#0-6) . This repeats naturally over time without any attacker action.
3. Each time, `storeSession` is called with the same deterministic `offline_<shop>` (or `<shop>_<userId>`) id, and `addShopIds` appends another copy of that id to the `shop:<shop>` KV entry [2](#0-1) .
4. Inspect the `shop:<shop>` KV key after repeated cycles — it contains multiple duplicate copies of the same session id, growing unbounded, and `findSessionsByShop(shop)` returns duplicated `Session` results.
