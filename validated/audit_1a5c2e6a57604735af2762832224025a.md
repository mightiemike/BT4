Found it: `WithdrawBalanceActuator` enforces a 24-hour withdrawal cooldown (`witnessAllowanceFrozenTime`, based on `latestWithdrawTime`), but the equivalent TVM-exposed `withdrawReward()` native path (`WithdrawRewardProcessor`) never checks that cooldown at all.

### Title
Missing withdrawal cooldown check in TVM `withdrawReward()` native contract bypasses the 24-hour reward-withdraw restriction enforced by `WithdrawBalanceActuator` - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java)

### Summary
`WithdrawBalanceActuator.validate()` restricts witness/voter reward withdrawal to once every `witnessAllowanceFrozenTime` (24 hours), comparing `now - latestWithdrawTime` before allowing a withdraw transaction. [1](#0-0)  The same reward-withdraw effect is also reachable from inside the TVM via the `withdrawReward()` opcode, which routes through `WithdrawRewardProcessor` — a sibling "entry point" performing the identical state mutation (clearing `allowance`, crediting `balance`, updating `latestWithdrawTime`) but whose `validate()` only checks the guard-representative restriction and never checks `latestWithdrawTime`/`witnessAllowanceFrozenTime`. [2](#0-1) 

### Finding Description
This mirrors the ERC4626 vault bug class precisely: the base functionality (withdraw reward / clear allowance) is exposed through two parallel code paths that should share the same restriction, but only one path (`WithdrawBalanceActuator`, invoked by the `WithdrawBalanceContract` transaction type) was given the additional business-rule check (24-hour cooldown via `latestWithdrawTime`). The sibling path — `WithdrawRewardProcessor.validate()`, invoked from `Program.withdrawReward()` when a smart contract executes the `withdrawReward()` TVM opcode — omits that check entirely: [2](#0-1)

Compare to the actuator's check, which the native processor lacks: [1](#0-0) 

```java
long latestWithdrawTime = accountCapsule.getLatestWithdrawTime();
long now = dynamicStore.getLatestBlockHeaderTimestamp();
long witnessAllowanceFrozenTime = dynamicStore.getWitnessAllowanceFrozenTime() * FROZEN_PERIOD;

if (now - latestWithdrawTime < witnessAllowanceFrozenTime) {
  throw new ContractValidateException("The last withdraw time is "
      + latestWithdrawTime + ", less than 24 hours");
}
```

`Program.withdrawReward()` builds a `WithdrawRewardParam` from `getContextAddress()` (i.e., the calling contract account, which — like any account — can accrue voting/SR `allowance`) and runs it straight through `WithdrawRewardProcessor.validate()`/`execute()`, with `execute()` unconditionally overwriting `latestWithdrawTime` to the current timestamp but never having gated on it: [3](#0-2) [4](#0-3) 

An account that has accrued voting rewards can therefore withdraw its full `allowance` repeatedly (many times per block/day) via a smart contract calling the `withdrawReward()` opcode, whereas the exact same account trying to do it through the ordinary `WithdrawBalanceContract` transaction type is limited to once per 24 hours.

### Impact Explanation
This is a concrete accounting/rate-limit bypass: the 24-hour throttle on witness/voter reward withdrawal — a deliberate economic/anti-spam control tied to `witnessAllowanceFrozenTime` and `FROZEN_PERIOD` — is completely unenforced on the TVM-callable path. Any account (including a smart-contract-controlled account) that has voting rewards accruing can drain/claim rewards on an arbitrary cadence instead of once daily, defeating the intended reward-payout cadence. While the amount withdrawable in any single call is still bounded by the actually-accrued `allowance`, the ability to withdraw immediately and repeatedly (rather than being throttled) breaks a state/accounting invariant the protocol explicitly enforces elsewhere, and is directly analogous in root cause to the reported vault issue (one entry point restricted, an equivalent sibling entry point left unrestricted).

### Likelihood Explanation
High likelihood of triggering: any account with witness votes/rewards can deploy or use a simple smart contract that repeatedly executes the `withdrawReward()` opcode (gated only by `VMConfig.allowTvmVote`/reward feature flags being enabled, and static-call restrictions which don't block this since it's a state-modifying call), with no privileged role required.

### Recommendation
Add the same `latestWithdrawTime`/`witnessAllowanceFrozenTime` cooldown check to `WithdrawRewardProcessor.validate()` that exists in `WithdrawBalanceActuator.validate()`, so both entry points enforce the identical withdrawal-cadence restriction.

### Proof of Concept
1. Have an account vote for a witness and accrue `allowance` (reward) over multiple maintenance cycles, as in `WithdrawBalanceActuatorTest.testWithdrawBalance` setup. [5](#0-4) 
2. Deploy a contract that repeatedly calls the TVM `withdrawReward()` opcode (as exercised in `FreezeV2Test`/native-contract test patterns) instead of sending a `WithdrawBalanceContract` transaction.
3. Observe that each call succeeds and resets `latestWithdrawTime`, crediting `balance` from `allowance` every time new `allowance` accrues, with no 24-hour wait — unlike calling `WithdrawBalanceActuator`, which throws `"The last withdraw time is ..., less than 24 hours"` if attempted again within the window. [6](#0-5)

  public void validate(WithdrawRewardParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();

    boolean isGP = CommonParameter.getInstance()
        .getGenesisBlock().getWitnesses().stream().anyMatch(witness ->
            Arrays.equals(ownerAddress, witness.getAddress()));
    if (isGP) {
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(ownerAddress)
              + "] is a guard representative and is not allowed to withdraw Balance");
    }
  }

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }

  public long withdrawReward() {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner, 0, null,
        "withdrawReward", nonce, null);

    WithdrawRewardParam param = new WithdrawRewardParam();
    param.setOwnerAddress(owner);
    param.setNowInMs(getTimestamp().longValue() * 1000);
    try {
      WithdrawRewardProcessor processor = new WithdrawRewardProcessor();
      processor.validate(param, repository);
      long allowance = processor.execute(param, repository);
      repository.commit();
      if (internalTx != null) {
        internalTx.setValue(allowance);
      }
      return allowance;
    } catch (ContractValidateException e) {
      logger.warn("TVM WithdrawReward: validate failure. Reason: {}", e.getMessage());
    } catch (ContractExeException e) {
      logger.warn("TVM WithdrawReward: execute failure. Reason: {}", e.getMessage());
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return 0;
  }
