### Title
Fixed static energy cost for WITHDRAWREWARD opcode does not scale with the number of votes iterated, allowing energy-fee underpayment - (File: `actuator/src/main/java/org/tron/core/vm/EnergyCost.java`)

### Summary
The TVM's `WITHDRAWREWARD` opcode charges a fixed, constant energy cost (`WITHDRAW_REWARD = 20000`) via `EnergyCost.getWithdrawRewardCost` regardless of how much computational work is actually performed when the reward is computed. This mirrors the GMX `estimateExecuteWithdrawalGasLimit` bug class: a static/fixed cost model that ignores variable, data-dependent work performed during execution (there: token swaps at the end of withdrawal execution; here: the vote/witness iteration performed while withdrawing rewards).

### Finding Description
`EnergyCost.getWithdrawRewardCost` is registered as the energy-cost function for the `Op.WITHDRAWREWARD` opcode: [1](#0-0) [2](#0-1) 

This constant cost is charged before `Program.withdrawReward()` executes the actual logic, which delegates to `WithdrawRewardProcessor.execute` and ultimately `VoteRewardUtil.withdrawReward`: [3](#0-2) [4](#0-3) 

`VoteRewardUtil.withdrawReward` calls `computeReward`, which loops over the account's entire `getVotesList()` and, for each vote, performs a `DelegationStore` lookup and `BigInteger` arithmetic: [5](#0-4) 

An account can hold up to `MAX_VOTE_NUMBER` votes (enforced by `VoteWitnessActuator.validate`), and a single `VoteWitnessContract` call can vote for up to that many distinct witnesses in one transaction: [6](#0-5) 

Since `getWithdrawRewardCost` always returns the fixed `WITHDRAW_REWARD` value irrespective of `getVotesList()` size, a contract can vote for the maximum number of witnesses and then repeatedly invoke `WITHDRAWREWARD`, triggering an O(votes) loop each time, while only ever being charged a flat 20000 energy — the same amount charged when the account has zero or one vote.

This differs from `VOTEWITNESS` itself, whose cost function (`getVoteWitnessCost`/`getVoteWitnessCost2`/`getVoteWitnessCost3`) does scale with the size of the on-stack witness/amount arrays via memory-expansion cost, showing that the codebase's general design intent is for opcode energy cost to track the actual amount of work/data involved — an intent that `getWithdrawRewardCost` fails to follow. [7](#0-6) 

### Impact Explanation
Because the energy charged for `WITHDRAWREWARD` is decoupled from the actual iteration cost, a malicious contract can cheaply trigger relatively expensive, repeated per-vote computation (DelegationStore reads, BigInteger math) across many calls in a single transaction (bounded by the overall transaction energy/fee limit, but each individual `WITHDRAWREWARD` invocation is undercharged relative to its real cost). This creates a mispriced-computation / potential-DoS vector in TVM execution and energy metering: node computational cost is not proportional to the energy fee actually collected for that specific operation, which can be leveraged to waste node CPU cycles cheaper than intended, and it is precisely the same class of underestimation bug flagged in the source report (static cost not accounting for variable, data-dependent execution).

### Likelihood Explanation
Reaching this path only requires deploying/using a contract that calls `WITHDRAWREWARD` (accessible via any `TriggerSmartContract` transaction, i.e., broadcastable by any anonymous account), after first voting for up to `MAX_VOTE_NUMBER` witnesses with `VOTEWITNESS`. No privileged role, leaked key, or malicious peer/node behavior is required — it is reachable purely through normal, permissionless transaction broadcast.

### Recommendation
Make `getWithdrawRewardCost` scale with the actual amount of work performed, e.g. by charging additional energy proportional to `accountCapsule.getVotesList().size()` (mirroring how `getVoteWitnessCost` scales with witness/amount array size), instead of returning a single fixed constant regardless of the number of votes being processed.

### Proof of Concept
1. Attacker account votes for `MAX_VOTE_NUMBER` distinct witnesses via `VOTEWITNESS` (validated by `VoteWitnessActuator.validate`, `contract.getVotesCount() <= MAX_VOTE_NUMBER`).
2. Wait until reward has accrued for at least one cycle (or repeat over cycles).
3. From a smart contract, repeatedly execute the `WITHDRAWREWARD` opcode (`Program.withdrawReward()` → `WithdrawRewardProcessor.execute` → `VoteRewardUtil.withdrawReward` → `computeReward`), which iterates over all `MAX_VOTE_NUMBER` votes and performs `DelegationStore` lookups and `BigInteger` math per vote.
4. Observe that `EnergyCost.getWithdrawRewardCost` charges the same fixed `20000` energy per call whether the account has 0 votes or `MAX_VOTE_NUMBER` votes — i.e., the energy fee does not scale with the O(votes) work performed, unlike `VOTEWITNESS`'s cost function which does scale with array size.

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
