### Title
Deterministic account IDs commit only to a mutable `AccountId` reference, not to code bytes, enabling cross-chain/cross-network address collision and code-substitution - (File: `core/primitives/src/utils.rs`, `runtime/runtime/src/global_contracts.rs`)

### Summary
NEP-616 deterministic accounts derive their `0s…` account ID purely by hashing the borsh-encoded `DeterministicAccountStateInit` (a `GlobalContractIdentifier` plus a `data` map), with no chain-specific salt (no genesis hash / chain ID in the preimage). When the `GlobalContractIdentifier::AccountId` variant is used, the ID commits only to an account-name string, not to the actual contract bytecode that account currently owns — and that binding (name → code) is resolved live and independently on every chain/shard set that runs the same nearcore software.

### Finding Description
`derive_near_deterministic_account_id` computes `'0s' + keccak256(borsh(state_init))[12:32]` [2](#0-1) . The `state_init.code` field can be `GlobalContractIdentifier::AccountId(AccountId)` [3](#0-2) , a mode explicitly designed so "the owner can update the contract for all its users" [4](#0-3) .

When a `DeterministicStateInitAction` is executed, `deploy_deterministic_account` calls `use_global_contract`, which looks up whatever code is *currently* published under that `AccountId` on the local chain and sets `AccountContract::GlobalByAccount(id)` [5](#0-4) [6](#0-5) . Nothing in the account-ID derivation or in the deploy path pins the actual bytecode; the resolution of `AccountId → code` is entirely local, mutable, and chain-specific.

This is the direct structural analog of the reported bug class: an address/ID that is supposed to represent a specific deployed contract instance is instead computed from data (here, an account-name reference) that does not uniquely and immutably commit to the code that will actually execute at that ID. Just as `CREATE`/`clone()` addresses in the Solidity report are reproducible across chains but can resolve to different, attacker-controlled bytecode when replayed on another chain, the same `DeterministicAccountStateInit` (naming the same global-contract owner account and same `data`) produces the identical `0s…` account ID on every independent nearcore-based network (mainnet, a testnet, or any other chain forked from/running this software), yet each network independently resolves the referenced `AccountId`'s current global contract — which can be owned and freely rewritten by different, non-cooperating parties per network.

### Impact Explanation
A user or protocol that treats the deterministic account ID as chain-portable (a reasonable assumption, since the whole point of NEP-616 is "the account id is derived from a `DeterministicAccountStateInit` instance" and thus is supposed to represent one canonical logical entity) can be led to interact with or fund the identically-addressed account on a second network where the referenced `AccountId` is controlled by an unrelated or malicious party. Because `use_global_contract` swaps in whatever bytecode that account currently owns [7](#0-6) , funds pre-deposited to the deterministic account (permitted before initialization, per the docs: "A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`" [8](#0-7) ) or funds sent to it after initialization can be routed through attacker-controlled logic, resulting in unauthorized value movement/drain once the substituted contract is invoked.

### Likelihood Explanation
This requires only ordinary, unprivileged actions: submitting a `Transfer` to a computed deterministic ID and a `DeterministicStateInitAction`/`DeployGlobalContractAction` referencing an `AccountId`-mode global contract — all standard transaction types reachable by any signer. It is entirely plausible for a project to reuse the same `state_init` (same global-contract owner account name, same data) across a mainnet deployment and a separate nearcore-based test/fork network, and for that account name to be free or attacker-registrable on the second network.

### Recommendation
Bind the deterministic account ID derivation to chain identity when the referenced global contract is the mutable `AccountId` variant (e.g., include `chain_id`/genesis hash in the `DeterministicAccountStateInit` preimage, or restrict deterministic accounts to `GlobalContractIdentifier::CodeHash`, which is immutable and content-addressed, matching the `cloneDeterministic`/salted recommendation in the source report). At minimum, document and enforce that `AccountId`-mode deterministic accounts are not chain-portable and should never be treated as canonical across independent nearcore networks.

### Proof of Concept
1. On chain A, deploy a legitimate global contract under account `trusted.near` via `DeployGlobalContractAction{ deploy_mode: AccountId }` [9](#0-8) .
2. Compute `state_init = DeterministicAccountStateInit::V1{ code: GlobalContractIdentifier::AccountId("trusted.near"), data }` and its derived ID `0s...` via `derive_near_deterministic_account_id` [10](#0-9) . Users send funds/transactions to `0s...` on chain A trusting the resolved code.
3. On chain B (an independent nearcore-based network where `trusted.near` is unregistered or owned by an attacker), the attacker deploys a malicious global contract under the same account name `trusted.near`.
4. Any user who computes the same `state_init` and sends a `Transfer` + `DeterministicStateInitAction` to `0s...` on chain B gets an account with the identical ID, but `use_global_contract` binds it to the attacker's code [1](#0-0) , allowing the attacker to intercept deposits/calls that the user assumed matched the trusted chain-A behavior.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
