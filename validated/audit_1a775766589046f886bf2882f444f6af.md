### Title
Deposit slot permanently reserved in `pending_deposits` on simulation/inclusion divergence, blocking real deposit forever - ([File: crates/sequencer/src/rpc.rs])

### Summary
`send_raw_deposit_transaction` validates a deposit blob only against the *pending* EVM state via `evm.get_call(..., Some(BlockId::pending()), ...)`, then unconditionally reserves the deposit's `calc_tx_id` slot in `DepositDataMempool::pending_deposits` via `add_deposit_tx`. Because `calc_tx_id` is derived only from the `moveTx`'s `version`/`vin`/`vout`/`locktime` and not from the `MerkleProof`, and because the mempool's only release mechanism (`remove_deposits`) is exclusively invoked for deposits that are actually included/succeed, a divergence between simulation-time state and inclusion-time state can leave a deposit permanently stuck occupying the real deposit's txid slot.

### Finding Description
The binding claimed broken: `pending_deposits[txid] == the Bitcoin move-to-vault output identified by moveTx(version, vin, vout, locktime)`, which should be creditable exactly once and only by the real depositor.

Trace:
- `send_raw_deposit_transaction` (crates/sequencer/src/rpc.rs:330-388) builds a call via `make_deposit_tx_from_data` and validates it with `evm.get_call(dep_tx, Some(BlockId::pending()), ...)` — a snapshot check against the sequencer's current pending EVM state, not the state at actual future inclusion. [1](#0-0) 
- On success it calls `deposit_mempool.lock().add_deposit_tx(...)`, which computes `txid = calc_tx_id(&req)` and inserts unconditionally into `pending_deposits: HashSet<Vec<u8>>` before ever verifying inclusion succeeds; only `false` is returned (not an error) if already present. [2](#0-1) 
- `calc_tx_id` hashes only `tx.version`, `tx.vin`, `tx.vout`, `tx.locktime` of the decoded `moveTx` — the `MerkleProof` (or any other field required to prove Bitcoin inclusion) is not part of the identifier. [3](#0-2) 
- The only path that removes an entry from `pending_deposits` is `remove_deposits`, which is driven by the caller (runner) supplying the set of deposits that were included; `fetch_deposits` itself is explicitly non-destructive ("without removing them"). [4](#0-3) 

Because `calc_tx_id` ignores the proof, an attacker who observes a real, still-unconfirmed Clementine `moveTx` in the Bitcoin mempool can submit a deposit blob with the identical `moveTx` fields but a garbage/stale `MerkleProof`, hoping it clears the `eth_call` pending-state check (e.g., if the bridge contract's simulated call path does not fully re-verify proof validity against the light-client-committed header at call time, or the header changes between simulation and inclusion). This reserves the txid slot in `pending_deposits`. If the real, correct deposit is submitted afterward with the same `txid`, `add_deposit_tx` returns `Ok(false)` and the RPC returns "Deposit already pending in mempool", rejecting the legitimate depositor's submission. Meanwhile the attacker's bad entry sits in `accepted_deposit_txs`/`pending_deposits` and — if inclusion consistently fails for that entry (e.g., due to an invalid proof that a genuine bridge/system-tx execution rejects) — is never removed because `remove_deposits` is never invoked for it.

I was not able to fully inspect `crates/sequencer/src/runner.rs`'s exact `apply_l2_block_txs`/`process_sys_txs` revert semantics (i.e., whether a failing deposit tx aborts only that deposit's inclusion and is retried every block, or aborts block production entirely) within the available tool budget, so I cannot state with full certainty the precise recovery/retry behavior on the runner side. However, the `deposit_data_mempool.rs` API design (non-destructive fetch + explicit, success-only removal, txid independent of proof) is sufficient on its own to demonstrate that a mismatched simulation-vs-inclusion outcome leaves the reservation stuck, since there is no code path that removes a `pending_deposits` entry other than `remove_deposits` being called with that specific deposit as "included."

### Impact Explanation
If the described divergence is reachable in practice, the real depositor's Bitcoin-side `moveTx` output can never be credited on L2 because its `calc_tx_id` slot is permanently occupied by a non-removable, always-failing entry — this is a permanent freeze of a Bitcoin-backed deposit, matching the Critical category ("funds permanently frozen"). It is repeatable per targeted deposit and requires only that the attacker observe an unconfirmed Bitcoin move-to-vault transaction and front-run it via `citrea_sendRawDepositTransaction` with a corrupted proof.

### Likelihood Explanation
Preconditions: sequencer regtest/testnet with a public `citrea_sendRawDepositTransaction` endpoint; attacker must be able to observe a real, not-yet-included Clementine deposit's `moveTx` (public via Bitcoin mempool or DA), and must additionally get their crafted blob to pass the pending-state `eth_call` simulation with an invalid proof — this last condition depends on bridge contract logic not fully assessed here (out of scope: Solidity system-contract internals). Attacker cost is minimal (a single JSON-RPC call, no Bitcoin fee required for the attack itself). Full confirmation requires validating the bridge contract's simulation-time vs. inclusion-time proof verification, which is outside the scope of `crates/sequencer/src/rpc.rs`.

### Recommendation
- Make `calc_tx_id` (or an additional dedup key) include the Bitcoin-side proof/output identity used for inclusion, or better, use the true Bitcoin `txid`/`wtxid` of the move transaction as computed independent of attacker-supplied proof bytes, so a rejected/invalid submission cannot occupy the slot of the real one.
- Add a removal/expiry path for deposits that fail during `process_sys_txs`/`apply_l2_block_txs` (a call to `remove_deposits`, or a dedicated "invalidate" method) so failed deposits are purged from `pending_deposits` rather than silently retried forever.
- Re-simulate against the true state at inclusion time (not `BlockId::pending()`) or re-validate the Bitcoin merkle proof against the light client's finalized header before final admission, closing the simulation/inclusion time-of-check-time-of-use gap.

```rust
#[test]
fn test_stale_proof_permanently_blocks_real_deposit_slot() {
    let mut mempool = DepositDataMempool::new();

    // Attacker-crafted deposit: identical moveTx fields (version/vin/vout/locktime)
    // as the real upcoming deposit, but a garbage/stale MerkleProof.
    let attacker_deposit = build_deposit_with_same_movetx_bad_proof();
    // Real deposit: correct proof, same moveTx.
    let real_deposit = build_deposit_with_same_movetx_good_proof();

    assert_eq!(
        DepositDataMempool::calc_tx_id(&attacker_deposit).unwrap(),
        DepositDataMempool::calc_tx_id(&real_deposit).unwrap(),
        "txid binding depends only on moveTx, not proof"
    );

    // Attacker's blob is accepted into the mempool (simulated as passing eth_call).
    assert!(mempool.add_deposit_tx(attacker_deposit.clone()).unwrap());

    // Simulate runner attempting inclusion and failing (no remove_deposits call,
    // since the deposit never succeeds on real inclusion).
    // ... (fetch_deposits does not remove; remove_deposits is never invoked for this txid)

    // Real depositor now tries to submit the correct deposit with same txid.
    let accepted = mempool.add_deposit_tx(real_deposit.clone()).unwrap();
    assert!(!accepted, "real deposit is rejected as duplicate forever");

    // pending_deposits still contains the txid, occupied by the unremovable bad entry.
    assert_eq!(mempool.fetch_deposits(10)[0], attacker_deposit);
}
```

Confirming the full end-to-end exploit additionally requires a sequencer-harness test proving the crafted blob passes `evm.get_call` at `BlockId::pending()` and subsequently fails in `runner::process_sys_txs`, which requires bridge-contract-level details not verified in this pass.

```rust
    pub fn fetch_deposits(&mut self, limit_per_block: usize) -> Vec<Deposit> {
        let number_of_deposits = self.accepted_deposit_txs.len().min(limit_per_block);

            .cloned()
            .collect();

    /// Removes specific deposits from the mempool after they have been successfully included in a block
    ///
    /// # Arguments
    /// * `deposits_to_remove` - The deposits that were successfully included
    ///
    /// # Returns
    /// The number of deposits actually removed
    #[instrument(level = "trace", skip_all, ret)]
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
```

```rust
    pub fn add_deposit_tx(&mut self, req: Deposit) -> anyhow::Result<bool> {
        let txid = Self::calc_tx_id(&req)?;

        debug!("Adding deposit with tx: {}", hex::encode(txid));

        // Check if deposit is already pending
        if !self.pending_deposits.insert(txid.to_vec()) {
            tracing::debug!("Deposit already pending in mempool");
            return Ok(false);
        }

        self.accepted_deposit_txs.push_back(req);
        SM.deposit_data_mempool_txs_inc.increment(1);
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        Ok(true)
    }
```

```rust
    fn calc_tx_id(req: &Deposit) -> anyhow::Result<[u8; 32]> {
        let call = BridgeContract::depositCall::abi_decode_raw(req, true)
            .map_err(|e| anyhow::anyhow!("Could not decode DepositCall ABI: {e:?}"))?;

        let tx = call.moveTx;

        let mut data = Vec::new();

        data.extend_from_slice(&tx.version.0);
        data.extend_from_slice(&tx.vin.0);
        data.extend_from_slice(&tx.vout.0);
        data.extend_from_slice(&tx.locktime.0);

        let hasher = Sha256::hash(&data);

        let second = Sha256::hash(&hasher);

        Ok(second)
    }
```
