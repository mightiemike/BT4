### Title
Front-Runnable Asset-Name Squatting Enables Permanent Denial-of-Service Against Legitimate `AssetIssueContract` Issuers - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator` enforces a global, first-come-first-served uniqueness constraint on token names when `AllowSameTokenName == 0`. Because the uniqueness check is keyed purely on the attacker-controllable `name` field and not bound to the intended issuer, any unprivileged, funded account can observe a pending `AssetIssueContract` broadcast (or simply predict/target a desired name) and front-run it with the identical name, permanently blocking the legitimate account from ever issuing that asset name. This mirrors the reported bug class: an unprivileged actor exploits a "first writer wins" uniqueness check on a resource meant to be reserved for a specific actor, causing denial-of-service for the intended operation.

### Finding Description
In `validate()`, the only check preventing name collision is a global lookup in `assetIssueStore`: [1](#0-0) 

This check does not scope the name to the address that intends to use it, nor does it reserve the name for a particular signer ahead of time — it is purely "whoever's `AssetIssueContract` transaction lands in a block first with this exact `name` wins." Any account can call this actuator (subject only to holding `getAssetIssueFee()` TRX and not having issued an asset before, per): [2](#0-1) 

Since TRON transactions (and the `name` field) are visible in the mempool/broadcast layer before confirmation, an attacker can observe a victim's pending `AssetIssueContract` transaction (or simply anticipate a well-known/branded name a project intends to use) and submit their own `AssetIssueContract` with the identical `name` and a higher fee/priority, or simply broadcast first. Once the attacker's transaction is included, `assetIssueStore.get(name)` becomes non-null, and the legitimate issuer's transaction will permanently fail validation with `"Token exists"` — there is no mechanism to release, dispute, or reclaim the name since asset issuance records are never deleted. This is structurally analogous to the reported `onERC721Received` issue: an unprivileged actor exploits a check on a caller/parameter-derived key (rather than an actor-bound reservation) to grief a specific legitimate operation and cause a permanent denial-of-service for that operation.

### Impact Explanation
This allows any funded, unprivileged account to permanently block a targeted party (including an "admin"/project team account) from ever issuing a token with a chosen name once `AllowSameTokenName == 0` is in effect, since the name is stored forever with no deletion path. This is a direct denial-of-service against legitimate use of the `AssetIssueContract` RPC/broadcast path reachable by anyone, matching the accepted impact category of "DoS via RPC-API or protocol implementation" against a specific, targeted legitimate transaction.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the network to currently have `AllowSameTokenName == 0` (this is a chain-configurable parameter controlled by `DynamicPropertiesStore`, historically the default/legacy mode on TRON before the multi-token-name upgrade), and (b) the attacker to know or predict the target name in advance (e.g., a widely announced brand/token launch) or observe it in the mempool before confirmation. Any account with the modest issuance fee can perform the attack with no privileged access required, and the action is fully deterministic and reproducible — it does not depend on race-condition timing beyond ordinary transaction-ordering/front-running.

### Recommendation
- Deprecate/avoid relying on the legacy global name-uniqueness path (`AllowSameTokenName == 0`) for any security-relevant flows, since it inherently allows name squatting.
- If backward compatibility with `AllowSameTokenName == 0` must be preserved, consider adding a reservation mechanism (e.g., binding a name to a specific `ownerAddress` via a prior on-chain commitment/proposal) before permitting issuance, so an unrelated account cannot claim a name intended for another address.
- At minimum, document this as expected/legacy behavior and ensure the maintained/default code path (`AllowSameTokenName == 1`, keyed by unique token ID rather than name) is the one relied upon for any admin/critical asset issuance.

### Proof of Concept
1. Set `AllowSameTokenName == 0` (legacy mode).
2. Victim ("Admin") broadcasts `AssetIssueContract` with `name = "BRAND"`.
3. Attacker observes the pending transaction (or anticipates the name) and broadcasts their own `AssetIssueContract` with `name = "BRAND"` and sufficient fee, arranging for it to be included first (e.g., via higher fee/energy priority or simple race).
4. Attacker's transaction executes first; `assetIssueStore.put(assetIssueCapsule.createDbKey(), ...)` stores the name. [3](#0-2) 
5. Victim's transaction is then processed by `validate()`, which now finds `assetIssueStore.get("BRAND") != null` and throws `"Token exists"`, permanently preventing the victim from ever issuing that name. [1](#0-0) 

**Note on confidence:** This is a reasoned analog based on the same "unprivileged front-run of a globally unique, non-actor-bound key check" bug class described in the report; I could not verify current mainnet/testnet default value of `AllowSameTokenName` from the index (only `DynamicPropertiesStore.java` getter/setter signatures were found, not the initialization default), so the practical exploitability depends on that runtime configuration.
