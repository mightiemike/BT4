### Title
Stale `AccountIndexStore` entries permanently reserve released account names - (File: actuator/src/main/java/org/tron/core/actuator/UpdateAccountActuator.java)

### Finding Description
`UpdateAccountActuator.execute` renames an account by writing the new name into `AccountStore` and `AccountIndexStore`, but it never removes the old name-to-address mapping from `AccountIndexStore`: [1](#0-0) 

`AccountIndexStore.put` only writes `name -> address`; there is no corresponding delete call anywhere in the actuator, even though `TronStoreWithRevoking`-based stores (and `AccountIndexStore` itself, exercised via `delete()` in the actuator's own unit test file) support key deletion: [2](#0-1) 

`validate()` rejects a name if `AccountIndexStore.has(name)` is true and `AllowUpdateAccountName == 0`: [3](#0-2) 

Because the old mapping is never deleted, once an address has been indexed under `name1`, `AccountIndexStore.has(name1)` remains true forever, even after that address renames away from `name1` to `name2` (which is only possible while `AllowUpdateAccountName == 1`, since a second rename while the flag is `0` is separately blocked at line 89-92). If the flag is later toggled back to `0`, any future account attempting to claim `name1` will be rejected with "This name is existed" indefinitely, despite no live account actually holding that name.

### Impact Explanation
This permanently orphans a name resource in `AccountIndexStore`. Any address that once held `name1` and then changed its name effectively "burns" `name1` for all future accounts as long as `AllowUpdateAccountName == 0`, with no in-repo mechanism to reclaim or clear the stale entry. This is a real invalid-state/resource-lock bug in the actuator's cleanup logic.

### Likelihood Explanation
The bug is deterministic and 100% reproducible given the required flag transition (`AllowUpdateAccountName`: `0 -> 1` to allow the rename-away, then `1 -> 0` again). Toggling `AllowUpdateAccountName` is a chain-wide dynamic property change (via a witness proposal, `ProposalService`), not something the unprivileged attacker directly controls — the attacker's transactions themselves (`AccountUpdateContract`) require no special privilege, but the full failure scenario needs the flag to have been enabled at some point in the chain's history. Given the flag governs a documented feature (allow-multiple-renames), such a transition is realistic over the life of a network, and once it has occurred, the resulting stale index entries are permanent and unrecoverable through any public API.

### Recommendation
In `UpdateAccountActuator.execute`, before writing the new name to `AccountIndexStore`, delete the old name mapping if the account had a non-empty previous name, e.g.:
```java
if (account.getAccountName() != null && account.getAccountName().size() > 0) {
  chainBaseManager.getAccountIndexStore().delete(account.getAccountName().toByteArray());
}
account.setAccountName(accountUpdateContract.getAccountName().toByteArray());
chainBaseManager.getAccountStore().put(ownerAddress, account);
chainBaseManager.getAccountIndexStore().put(account);
```

### Proof of Concept
```java
// Extends UpdateAccountActuatorTest style setup (dbManager, ACCOUNT_NAME, ACCOUNT_NAME_1, OWNER_ADDRESS, OWNER_ADDRESS_1)

@Test
public void staleNameIndexPermanentlyLocksName() throws Exception {
  // Precondition: AllowUpdateAccountName = 0, A has empty name
  dbManager.getDynamicPropertiesStore().saveAllowUpdateAccountName(0);

  // Step 1: A renames to name1 (succeeds)
  UpdateAccount(ACCOUNT_NAME, OWNER_ADDRESS);
  Assert.assertTrue(dbManager.getAccountIndexStore().has(ACCOUNT_NAME.getBytes()));

  // Step 2: enable multi-rename, A renames away to name2
  dbManager.getDynamicPropertiesStore().saveAllowUpdateAccountName(1);
  UpdateAccount(ACCOUNT_NAME_1, OWNER_ADDRESS);

  // BUG: old mapping name1 -> A is never removed
  Assert.assertTrue(dbManager.getAccountIndexStore().has(ACCOUNT_NAME.getBytes())); // still true, orphaned

  // Step 3: disable multi-rename again, B (unnamed) tries to claim name1
  dbManager.getDynamicPropertiesStore().saveAllowUpdateAccountName(0);

  AccountCapsule bAccount = new AccountCapsule(
      ByteString.copyFrom(ByteArray.fromHexString(OWNER_ADDRESS_1)),
      ByteString.EMPTY, AccountType.Normal);
  dbManager.getAccountStore().put(bAccount.getAddress().toByteArray(), bAccount);

  UpdateAccountActuator actuatorB = new UpdateAccountActuator();
  actuatorB.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getContract(ACCOUNT_NAME, OWNER_ADDRESS_1));

  try {
    actuatorB.validate();
    Assert.fail("expected ContractValidateException");
  } catch (ContractValidateException e) {
    // Fails permanently even though A no longer owns ACCOUNT_NAME
    Assert.assertEquals("This name is existed", e.getMessage());
  }
}
```
Expected assertion outcome demonstrates: `AccountIndexStore.has(ACCOUNT_NAME)` remains `true` after A no longer holds `ACCOUNT_NAME`, and account B's `validate()` unconditionally throws "This name is existed", confirming the name is permanently and incorrectly reserved.
