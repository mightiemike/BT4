### Title
Missing Slippage/Minimum-Output Protection in `ExchangeWithdrawActuator` Liquidity Withdrawal - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The `ExchangeWithdrawActuator`, which lets an exchange creator withdraw liquidity from a Bancor-style TRC10 exchange pair, computes the counter-asset amount (`anotherTokenQuant`) purely from the pool's current spot ratio at execution time and provides no user-supplied minimum-received parameter. This mirrors the reported bug class exactly: while the trading path (`ExchangeTransactionContract`) enforces a caller-supplied `expected` minimum, the withdrawal path has no equivalent slippage bound, so a withdrawer can receive an arbitrarily worse ratio than intended if the pool is moved between transaction submission and execution.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum field, unlike `ExchangeTransactionContract` which explicitly defines `expected: expected minimum number of tokens` for trades [1](#0-0) .

In `ExchangeWithdrawActuator.execute`, the amount of the paired token returned to the withdrawer (`anotherTokenQuant`) is derived solely from the exchange's current `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with no comparison against any caller-specified minimum: [2](#0-1) 

`doValidate()` only checks that the derived `anotherTokenQuant` is non-zero, non-negative, that pool balances are sufficient, and that a rounding-precision bound ("Not precise enough") is respected — none of these checks constrain the ratio against manipulation, only against integer-rounding loss: [3](#0-2) 

By contrast, `MarketSellAssetContract`/`ExchangeTransactionContract` designs explicitly bake in a caller-chosen minimum-received amount to guard against exactly this kind of ratio shift, as shown by the `expected` field and by test cases that assert failure when the actual output falls short of `expected` ("token required must greater than expected") [4](#0-3) . The withdraw path has no analogous mechanism.

The pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be moved arbitrarily by any account submitting an `ExchangeTransactionContract` trade against the same `exchange_id` before the withdraw transaction is packed into a block — this is a normal, unprivileged, permissionless action available to any account, not requiring any special role. Only the exchange creator is authorized to withdraw, but this is not a privileged system role — any account can create an exchange and thus become its "creator" [5](#0-4) .

### Impact Explanation
An attacker (or even accidental/opportunistic traders) can front-run a pending `ExchangeWithdrawContract` transaction with a large trade against the same exchange pair, skewing `firstTokenBalance`/`secondTokenBalance`. Because the withdraw computation uses the live ratio with no minimum-output floor, the withdrawer's `anotherTokenQuant` can be pushed to an arbitrarily unfavorable value (bounded only by the "Not precise enough" rounding check, not by market-rate deviation), causing a direct, realized accounting loss to the withdrawing account. This is a genuine underpriced-value/settlement-type impact: the withdrawer loses real token value with no recourse, matching the reported bug class of unbounded slippage in a removeLiquidity-equivalent operation.

### Likelihood Explanation
Exploitation only requires submitting an ordinary `ExchangeTransactionContract` trade shortly before the target's `ExchangeWithdrawContract` is confirmed — both are unprivileged, permissionless actions available to any account on TRON, and transaction ordering within a block is influenced by normal mempool/fee dynamics, making the classic front-running pattern from the report directly applicable. The precision check ("Not precise enough", ~0.01% tolerance) only bounds rounding error, not the price impact from an intervening trade, so it does not mitigate this risk [6](#0-5) .

### Recommendation
Add an `expected`/minimum-received field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce in `ExchangeWithdrawActuator.doValidate()`/`execute()` that the computed `anotherTokenQuant` (and/or `tokenQuant`) is not less than the caller-specified minimum, rejecting the transaction otherwise.

### Proof of Concept
1. Account A creates an exchange pair (TokenX/TokenY) and holds creator rights, intending to withdraw liquidity via `ExchangeWithdrawContract` for a given `tokenQuant` of TokenX, expecting a proportional amount of TokenY back based on the current ratio.
2. Attacker observes A's pending withdraw transaction in the mempool and submits an `ExchangeTransactionContract` that sells a large amount of TokenY into the pool (or buys a large amount of TokenX), which is confirmed first, drastically shifting `firstTokenBalance`/`secondTokenBalance`.
3. A's withdraw transaction executes against the now-skewed ratio: `anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` (or the mirrored branch) yields a far smaller TokenY amount than A intended [7](#0-6) .
4. Because `ExchangeWithdrawContract` has no `expected` minimum field, `doValidate()` cannot reject this unfavorable outcome — it only checks non-zero balances and rounding precision, so the transaction succeeds and A's funds are effectively lost to the price shift.
