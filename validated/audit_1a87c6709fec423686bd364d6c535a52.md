### Title
No slippage control in `ExchangeWithdrawContract` allows sandwich attacks against exchange liquidity withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's TRC10 Bancor-style exchange module allows an exchange creator to withdraw liquidity via `ExchangeWithdrawContract`, but unlike the swap contract (`ExchangeTransactionContract`), the withdraw contract has no `expected`/minimum-amount field. The amount of the paired token received on withdrawal is computed purely from the pool's current spot ratio at execution time, with no way for the caller to bound the acceptable outcome. Any unprivileged account can submit ordinary swap transactions (`ExchangeTransactionContract`, which has no access restriction) immediately before and after the withdrawal transaction to move the pool ratio and extract value from the withdrawer, exactly the sandwich pattern described in the referenced report.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` fields — no minimum-amount-out parameter: [1](#0-0) 

Compare this to `ExchangeTransactionContract`, which explicitly carries an `expected` field ("expected minimum number of tokens") used to protect swappers from slippage: [2](#0-1) 

In `ExchangeTransactionActuator.doValidate()`, the computed `anotherTokenQuant` is checked against the caller-supplied `tokenExpected` and the transaction is rejected if it's not met: [3](#0-2) 

`ExchangeWithdrawActuator`, however, computes `anotherTokenQuant` strictly from the exchange's *current* `firstTokenBalance`/`secondTokenBalance` ratio at the moment of execution, with no equivalent minimum check: [4](#0-3) 

The only "protection" present is a precision-drift check ("Not precise enough") that verifies the computed value is close to a proportional recomputation — this bounds rounding error, not price manipulation, and does not defend against ratio shifts caused by intervening swaps: [5](#0-4) 

Crucially, the token/TRX ratio used by the withdrawal is the exact same pool state (`firstTokenBalance`/`secondTokenBalance`) that `ExchangeTransactionActuator` mutates on every swap, and `ExchangeTransactionContract` has no access-control restriction — any account holding the sell-side asset can invoke it: [6](#0-5) 

This means an unprivileged attacker can, within the same or adjacent blocks, broadcast a large swap transaction that skews `firstTokenBalance`/`secondTokenBalance` in their favor immediately before the victim's withdrawal is processed, let the victim's withdrawal execute at the skewed ratio (receiving an unfavorable `anotherTokenQuant`), then broadcast a reversing swap afterward to restore the ratio and capture the difference — a classic sandwich attack, mirroring the Superposition `decr_position`/`update_position` slippage issue where withdrawal lacks `amount_0_min`/`amount_1_min` protection.

### Impact Explanation
Any account withdrawing liquidity from a TRC10 exchange pool via `ExchangeWithdrawContract` can have the paired-token amount they receive manipulated downward by an attacker sandwiching the withdrawal with ordinary, unprivileged swap transactions against the same exchange. This is direct, quantifiable asset/accounting loss for the withdrawer, extracted by the attacker, without requiring any special privilege, node compromise, or protocol bug beyond missing slippage bounds.

### Likelihood Explanation
Exploitation only requires the attacker to observe a pending `ExchangeWithdrawContract` transaction (via the public P2P network / node mempool) and submit two ordinary `ExchangeTransactionContract` swaps (broadcast transactions, no special permission) bracketing it — this is a standard MEV/sandwich pattern requiring no privileged access, and is directly enabled by the missing `expected`/min-out field on the withdraw contract.

### Recommendation
Add a minimum-acceptable-amount field (e.g., `expected`) to `ExchangeWithdrawContract`, analogous to `ExchangeTransactionContract.expected`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the transaction if the computed `anotherTokenQuant` (and/or `tokenQuant` if applicable) falls below the caller-specified minimum, closing the sandwich window described above.

### Proof of Concept
1. Exchange pool holds `firstTokenBalance` / `secondTokenBalance` at some ratio R.
2. Victim (exchange creator) broadcasts `ExchangeWithdrawContract` to withdraw `tokenQuant` of the first token, expecting to receive `anotherTokenQuant ≈ secondTokenBalance * tokenQuant / firstTokenBalance` computed at ratio R. [7](#0-6) 
3. Attacker, an unprivileged holder of the second token, front-runs with a large `ExchangeTransactionContract` sell of the second token, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for the withdrawer (this call has no restriction — any account can invoke it). [6](#0-5) 
4. Victim's withdrawal executes against the skewed pool, computing a reduced `anotherTokenQuant` with no floor enforced.
5. Attacker back-runs with a reversing swap, restoring the ratio and pocketing the extracted value — because `ExchangeWithdrawContract` never exposes a way for the victim to specify a minimum acceptable `anotherTokenQuant`, unlike `ExchangeTransactionContract`'s `expected` field.
