## Title
`ensure_match_transaction_info` skips `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, allowing replay-verify and chunk-execution to accept an output with a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant-checking function used by both consensus-adjacent chunk execution (`execution/executor/src/chunk_executor/mod.rs::verify_execution`) and offline replay tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger`, `aptos-move/cli`) to confirm that a freshly-executed `TransactionOutput` matches the accumulator-proof-bound `TransactionInfo` for a given version. It only checks `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`. It explicitly does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, as acknowledged in its own TODO comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  compares only four fields between the locally-produced `TransactionOutput` and the (proof-verified, accumulator-committed) `TransactionInfo`:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It never reads or compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against anything computed locally. This is admitted directly in the trailing comment: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is used in two integrity-relevant call sites, not just debugging tools:
1. `execution/executor/src/chunk_executor/mod.rs::verify_execution` at [2](#0-1)  — this is invoked as part of `VerifyExecutionMode` chunk replay (used by e.g. fast-sync/backup-restore verification and state-sync chunk validation flows), where transactions and `TransactionInfo`s arrive from an untrusted peer along with an accumulator proof, and the local node re-executes and must independently confirm the recomputed state agrees with the info bound to the accumulator root.
2. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` at [3](#0-2)  — used to validate that archive-node replay reproduces the exact on-chain ledger state.

Because the sparse-merkle state root (`state_checkpoint_hash`), the hot-state root, and the new "trading-native" position-state root (`position_state_checkpoint_hash`) are excluded from this check, a locally-computed state whose account/resource state diverges from the state committed on-chain (while write-set bytes and events still happen to hash identically, or more realistically while the divergence is confined to fields not captured by the write-set hash, such as position/trading-native state that is tracked outside the ordinary write set) will pass `ensure_match_transaction_info` without error.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... must not be accepted as verified" invariant for any code path relying on `ensure_match_transaction_info` as the correctness gate:
- In chunk replay/verify-execution mode, a state divergence confined to the state-checkpoint/hot-state/position-state roots is silently accepted as "verified," meaning the executor's replay-based sanity check provides no protection against an execution or storage bug that corrupts the account state tree while leaving the write-set hash and event hash unaffected.
- The comment explicitly ties this to the upcoming `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature and to `db-tool`'s `replay_on_archive`, i.e., the exact tooling operators use to authenticate archived ledger history against consensus-certified roots. A successful "replay-verify" result can be reported even though the authenticated state root does not match, undermining audits/investigations that rely on this tool to detect divergence or corruption.

This is a real proof-integrity gap (verification function that should bind full state, but does not), though it is currently gated by the fact that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and the trading-native position-state feature are apparently not yet fully enabled (per the TODO), which somewhat limits present-day severity — but the `state_checkpoint_hash`/`hot_state_checkpoint_hash` gap exists unconditionally today, independent of that feature flag.

### Likelihood Explanation
Likelihood of the state-root divergence itself occurring (e.g., via an executor/storage bug or non-determinism) is not separately demonstrated here; what is proven directly by the code is that the verification function that is supposed to catch such divergence has a structural gap acknowledged by the maintainers. Any bug elsewhere in the state-checkpoint computation (e.g. `do_state_checkpoint.rs`) that produces a wrong state root while leaving write-set bytes/events technically hash-identical to the accumulator-anchored transaction info would go undetected by this specific gate.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against the values produced by local re-execution/state-checkpointing, before any code path (especially `replay_on_archive` and chunk `verify_execution`) reports success. This should be done unconditionally, not deferred until `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, since `state_checkpoint_hash`/`hot_state_checkpoint_hash` already exist in `TransactionInfoV0`/`V1` today.

### Proof of Concept
No exploit PoC is provided because triggering an actual state-checkpoint-hash divergence requires an independent root-cause bug elsewhere (e.g., in state checkpoint computation) that this repo snapshot does not contain; what is verifiable directly from source is the structural gap itself:
- `ensure_match_transaction_info` body checks only `status`, `gas_used`, `state_change_hash`, `event_root_hash`: [4](#0-3) 
- Explicit maintainer acknowledgment that checkpoint hashes are skipped and that `replay_on_archive` can report false success: [5](#0-4) 
- Consuming call sites that treat this function as the correctness oracle: [6](#0-5)  and [7](#0-6) 

**Uncertainty note:** I could not confirm within this session whether `state_checkpoint_hash`/`hot_state_checkpoint_hash` divergence can currently be independently triggered by an existing local bug (which would elevate this from "verification gap" to "demonstrated wrong-root acceptance"), nor could I fully trace whether any other check (outside `ensure_match_transaction_info`) redundantly validates these checkpoint hashes in the `verify_execution`/`replay_on_archive` call paths. Given the index's size limits, a full-repository Devin session would be needed to check `do_state_checkpoint.rs` and any additional guards around these two call sites before treating this as conclusively exploitable versus a currently-latent gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
