### Title
Tokens are permanently burned when `DeleteAccount`'s balance refund is sent to a non-existent `beneficiary_id` - (File: runtime/runtime/src/actions.rs, runtime/runtime/src/lib.rs)

### Summary
The `DeleteAccount` action lets an account owner (or an actor with matching permission) delete their account and route the remaining balance to an arbitrary `beneficiary_id`. There is no validation that `beneficiary_id` actually exists at execution time. The remaining balance is pushed via a system-refund receipt (`Receipt::new_balance_refund`) rather than pulled/verified. Refund receipts can never create an account (implicit creation is explicitly disallowed for refunds), so if `beneficiary_id` does not exist (analogous to "recipient cannot receive the transfer", as in the blacklisted-address report), the refund receipt fails with `AccountDoesNotExist` and, per the documented refund-failure rule, **the entire amount is burnt** instead of being stuck or returned.

### Finding Description
`action_delete_account` computes the account's balance and unconditionally pushes a system balance-refund receipt to `beneficiary_id`: [1](#0-0) 

This uses the "push" pattern flagged in the source report: funds are sent out with no verification that the target can receive them, and no pull/withdraw fallback.

Refund receipts are generated with `predecessor_id = "system"` and are explicitly barred from creating accounts, including so-called "0u"/universal accounts and regular named accounts that were never created: [2](#0-1) 

A dedicated regression test confirms this exact failure mode for a missing account and that the receipt is rejected with `AccountDoesNotExist` rather than silently dropped or auto-created: [3](#0-2) 

When a refund receipt (i.e., `predecessor_id().is_system()`) fails, the runtime does not retry or return the funds to the deleted account (which no longer exists) — it burns the deposit into `other_burnt_amount`: [4](#0-3) 

This burn-on-refund-failure behavior is also documented as the general design for all refunds: [5](#0-4) 

Unlike gas/deposit refunds to the `signer_id` (which are described as "best effort" for allowance but still just burn on failure), the `DeleteAccount` beneficiary is fully attacker/user chosen and not validated for existence anywhere in validation (`docs/RuntimeSpec/Actions.md` only requires `beneficiary_id` to be a syntactically valid `AccountId`): [6](#0-5) 

### Impact Explanation
Any unprivileged transaction signer who submits a `DeleteAccount` action (directly, via a relayer/meta-transaction, or via a contract's `promise_batch_action_delete_account`) with a `beneficiary_id` that does not exist causes their entire remaining account balance to be irrecoverably destroyed (burned) rather than transferred. This is a stronger outcome than the referenced report's "stuck funds" — here funds are permanently removed from circulation with no path to recovery, matching the "permanently frozen funds" / value-destruction impact category. It can also be triggered unintentionally (e.g., a typo'd or since-deleted beneficiary account, or a contract batch computing a beneficiary id incorrectly), turning an ordinary account-cleanup operation into a fund-destroying operation with no warning or revert of the whole receipt.

### Likelihood Explanation
Likelihood is high for accidental triggering (typos, stale beneficiary accounts, contracts that compute beneficiary ids dynamically without verifying account existence) and straightforward for anyone wanting to force a burn deliberately. No special privileges are needed — `DeleteAccount` is available to any account owner and to relayers via meta-transactions (`Action::Delegate`), and to any contract via the Promise API (`promise_batch_action_delete_account`).

### Recommendation
- Before creating the `Receipt::new_balance_refund` in `action_delete_account`, verify that `beneficiary_id` refers to an existing (and initialized) account; if it does not, fail the action (e.g., with an `AccountDoesNotExist`-style validation error) instead of proceeding to delete the account and burn the balance.
- Alternatively, adopt a pull-based/escrow model for `DeleteAccount` payouts: hold the balance in a recoverable state (or require the beneficiary to already exist, checked at validation time) rather than unconditionally emitting an unauthenticated push transfer that burns on failure.
- At minimum, make the failure mode "abort/rollback the whole `DeleteAccount` action" (funds retained on the still-existing account) rather than "delete account first, then burn on refund failure" — i.e., re-order storage checks and existence checks for `beneficiary_id` before `remove_account` is called.

### Proof of Concept
1. Create/fund account `alice.near` with balance `B > 0`.
2. Submit `SignedTransaction` with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "iamnotarealaccount.near".parse().unwrap() })` signed by `alice.near`, where `iamnotarealaccount.near` has never been created.
3. `action_delete_account` runs: `account_balance > 0`, so it emits `Receipt::new_balance_refund(&"iamnotarealaccount.near", B)`, then calls `remove_account` and clears `account_id`'s state (`runtime/runtime/src/actions.rs:380-387,404`).
4. The emitted balance-refund receipt is later processed. In `apply_action`, `check_account_existence` for `Action::Transfer` on a refund receipt with `account.is_none()` returns `ActionErrorKind::AccountDoesNotExist` (per `runtime/runtime/src/actions.rs:842-850` and the confirmed pattern in the existing test at `runtime/runtime/src/tests/apply.rs:6883-6926`, which currently only exercises the "0u" scenario but exercises the identical mechanism for any missing account).
5. Because `receipt.predecessor_id().is_system()` is true and the result is `Err`, the runtime burns the full deposit amount into `other_burnt_amount` (`runtime/runtime/src/lib.rs:1047-1055`) instead of returning it anywhere.
6. Net effect: `alice.near`'s account and its balance `B` are both gone; `B` was neither transferred to `beneficiary_id` nor kept by `alice.near` — it is permanently burned.

Note: I was unable to execute this scenario in a live test-loop harness (no execution tools available in this environment); the conclusion is derived directly from the cited source code paths and the existing analogous unit test that exercises the same `check_account_existence`/refund-burn mechanism for a different missing-account case. A background Devin session with repo access could add and run a concrete `test-loop-tests` case (mirroring `test-loop-tests/src/tests/create_delete_account.rs`) that asserts the burn for a non-`0u`, plain named `beneficiary_id` that was never created, to empirically confirm the exact burnt-amount accounting.

**File:** docs/RuntimeSpec/Refunds.md (L10-13)
```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.

## DeleteAccountAction

```rust
pub struct DeleteAccountAction {
    /// The remaining account balance will be transferred to the AccountId below
    pub beneficiary_id: AccountId,
}
```

**Outcomes**:

- The account, as well as all the data stored under the account, is deleted and the tokens are transferred to `beneficiary_id`.

### Errors

**Validation Error**:

- If `beneficiary_id` is not a valid account id, the following error will be returned

```rust
/// Invalid account ID.
InvalidAccountId { account_id: AccountId },
```

- If this action is not the last action in the action list of a receipt, the following error will be returned

```rust
/// The delete action must be a final action in transaction
DeleteActionMustBeFinal
```

- If the account still has locked balance due to staking, the following error will be returned

```rust
/// Account is staking and can not be deleted
DeleteAccountStaking { account_id: AccountId }
```
