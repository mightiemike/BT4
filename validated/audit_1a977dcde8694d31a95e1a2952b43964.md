## Analog Found

### Title
Unconditional `has_in_flight_tx` Reset at Callback Entry Permanently Freezes ETH-Implicit Wallet Accounts on Any Mid-Callback Panic - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (deployed as a global contract for every ETH-implicit account, per NEP-518) guards sequential execution with a single boolean, `has_in_flight_tx`. Just like the reported `isAcquired` flag in `FundContract`, this flag is meant to gate whether a follow-up operation (`rlp_execute`) is allowed to proceed, and is supposed to be reliably cleared once the in-flight operation completes. However, the clearing of the flag is performed as an ordinary state write at the *top* of each `#[private]` callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), rather than being guaranteed independent of that receipt's success. Because NEAR receipts are atomic (a panicking receipt rolls back **all** state changes it made, including ones made before the panic), any panic occurring later in the same callback execution silently reverts the `has_in_flight_tx = false` write together with everything else, leaving the flag permanently `true`.

### Finding Description
`WalletContract` stores a single `bool` invariant: [1](#0-0) 

`rlp_execute` refuses to start a new transaction while the flag is set: [2](#0-1) 

Every callback that is expected to "complete" an in-flight transaction resets the flag as its very first statement, e.g. `rlp_execute_callback`: [3](#0-2) 

and `address_check_callback` / `nep_141_storage_balance_callback` follow the identical pattern (reset at entry, then conditionally re-arm to `true` if another promise is chained): [4](#0-3) [5](#0-4) 

This mirrors the `_updateUserWithdrawal()` pattern in the external report: a state-guard boolean is written unconditionally inside a function whose successful completion is not itself guaranteed. In the Solidity report, a revert-free but logically-incomplete withdrawal cleared `isAcquired` and locked the user out of ever satisfying `_canCompleteWithdraw()` again. Here, the runtime guarantee that makes the "unconditional write" *usually* safe is receipt atomicity: if the callback function panics for any reason after the flag reset statement executes (host env panics such as `env::panic_str`, a `.unwrap()`/arithmetic panic in serialization, gas exhaustion mid-execution, or any future code path added to these `#[private]` methods), the near runtime rolls back the entire receipt's state changes — undoing the reset of `has_in_flight_tx` along with any other otherwise-successful side effects. `rlp_execute` will then reject all subsequent calls forever with `"transaction already in progress"`, since there is no separate recovery path and this flag can only be written from inside `rlp_execute`/the private callbacks.

This is architecturally significant because ETH-implicit accounts running this contract explicitly cannot recover via any other channel: NEP-518 accounts cannot have a full-access key added, nor be deleted, and the wallet contract is the sole entry point for actions from that account: [6](#0-5) 

### Impact Explanation
If the reset-at-entry callback panics after commit-worthy state changes but the panic itself is deterministic (a bug reachable by crafted RLP transaction bytes, adversarial cross-contract responses causing deserialization edge cases, or particular gas-limit conditions that any relayer can trigger by simply calling `rlp_execute`), then `has_in_flight_tx` becomes permanently stuck at `true`. This is functionally identical to the reported "partial withdrawal permanently fails": the account (holding real user funds, since ETH-implicit accounts are funded on creation) becomes permanently unable to execute *any* transfer, function call, or key management action ever again — a concrete case of permanently frozen funds, which the validation rules explicitly accept as in-scope impact. Because the wallet contract is deployed once as a global contract and used by every ETH-implicit account on the network, a single reachable panic path in any of the four `#[private]` callbacks is a network-wide, per-account denial-of-service with no operator/validator involvement required — reachable purely by submitting a transaction/RPC call, matching the "unprivileged transaction signer" reachability requirement.

### Likelihood Explanation
Likelihood depends on whether an actual panic can be triggered inside one of the callbacks after `has_in_flight_tx = false` executes but before the function returns normally — this requires deeper contract-level fuzzing/audit of `internal::parse_rlp_tx_to_action`, `ethabi_utils`, and the cross-contract response deserialization paths (`serde_json::from_slice`, `StorageBalance` parsing, `env::promise_result` handling) than could be completed in this pass. The structural weakness (an unconditional, non-idempotent boolean reset relied upon for correctness, defeated by receipt-level atomic rollback) is confirmed by direct code inspection; whether a concrete panic-inducing input currently exists in the shipped `internal`/`eth_emulation`/`ethabi_utils` modules was not verified line-by-line due to iteration limits.

### Recommendation
Do not rely on state writes made earlier in a receipt to persist independently of that receipt's success/failure. Instead:
- Wrap the bodies of `address_check_callback`, `nep_141_storage_balance_callback`, and `rlp_execute_callback` so that any internal error path returns a graceful `ExecuteResponse { success: false, .. }` instead of panicking (avoid `.unwrap()`, `env::panic_str`, and unchecked arithmetic in these methods).
- Add a recovery mechanism independent of the normal flow — e.g., a time-boxed / height-boxed "in-flight" timeout so that if a callback never executes (or never executes successfully), the guard automatically expires rather than requiring a `false` write to survive.
- Audit `internal::parse_rlp_tx_to_action`, `ethabi_utils`, and all `serde_json` deserialization paths reachable from callback bodies for panics, and add fuzz/property tests specifically asserting that `has_in_flight_tx` cannot get stuck at `true` under adversarial cross-contract responses or malformed RLP payloads.

### Proof of Concept
Not independently reproduced in this pass — this requires either (a) locating or crafting a concrete panic-inducing input to one of the `#[private]` callbacks (e.g. a cross-contract response that deserializes but subsequently causes an arithmetic/format panic, or a `target`/`action` combination that panics in `action_to_promise`/`ethabi_utils` after `has_in_flight_tx=false` has executed), or (b) exhausting attached gas precisely between the flag-reset statement and the function's natural return so the callback receipt fails with `FunctionCallError` after partial execution. Both require dynamic testing against the compiled `near-wallet-contract` Wasm (e.g., via `cargo test`/`workspaces-rs` sandbox) that was outside the scope of static code reading performed here.

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,

            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
