## Analog Found

### Title
Gas-exhaustion in Wallet Contract callback permanently freezes `has_in_flight_tx`, bricking the account's funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (the global contract deployed for ETH-implicit accounts, see `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`) enforces a single-in-flight-transaction invariant via the `has_in_flight_tx` boolean field. This flag is only ever cleared back to `false` inside one of the promise callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). If any of these callbacks panics (e.g. from a gas-exhaustion) after the flag was set to `true`, NEAR's atomic state-revert-on-panic semantics roll back the callback's state changes together with everything else in that receipt — including the `has_in_flight_tx = false` write — leaving the flag permanently stuck at `true`. From that point on `rlp_execute` (the sole entry point for authorizing any action, including moving `$NEAR` out of the account) always short-circuits with `"transaction already in progress"` before doing anything, and there is no other function to reset the flag. This is directly analogous to the reported bug class ("contract has no way to move funds out because the only intended path is blocked"), except here the missing "withdraw" path is the entire wallet-contract control flow being permanently deadlocked.

### Finding Description
`WalletContract::rlp_execute` in [1](#0-0)  sets `self.has_in_flight_tx = true` before returning any `Promise`, and refuses to process a new transaction while that flag is `true`: [2](#0-1) 

The flag is only cleared as the *first* statement of the corresponding callbacks, e.g. `nep_141_storage_balance_callback`: [3](#0-2) 

For an ERC-20-style transfer, `inner_rlp_execute` schedules a call to `storage_balance_of` on the arbitrary `target`/`token_id` account (fully controlled by whoever the wallet owner's signed Ethereum transaction names as `to`), then chains `nep_141_storage_balance_callback` with a fixed *static* gas budget: [4](#0-3) [5](#0-4) 

Inside `nep_141_storage_balance_callback`, the callback deserializes whatever bytes the (attacker-controlled) `token_id` contract returned from `storage_balance_of`: [6](#0-5) 

Because this deserialization work happens *after* `self.has_in_flight_tx = false;` was already written in the same function invocation, a large/malicious return payload that drives the callback's own WASM execution past its fixed static gas allocation (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`, i.e. `Gas::from_tgas(5)+Gas::from_tgas(5)+Gas::from_tgas(5)` plus whatever gas the user attached to their own downstream call) causes the whole receipt to abort with an out-of-gas panic. NEAR reverts *all* state writes of a panicking function call atomically, so the `has_in_flight_tx = false` write is undone along with the rest, leaving `has_in_flight_tx` permanently `true`. The same class of issue also applies to `address_check_callback`, which similarly clears the flag first and then does further work (though the address registrar there is a fixed protocol account, the token/target contract in the NEP-141 path is fully attacker-controlled, making it the more direct vector).

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, every subsequent call to `rlp_execute` returns immediately at the guard check without creating any promise, and there is no other public method that clears the flag. Since the wallet contract's account normally has no full-access key and `rlp_execute` is the only sanctioned path to move `$NEAR` (or any tokens) out of the account, this permanently and irrecoverably freezes all of the account's funds — a direct match to the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
This is reachable by any unprivileged party: an ETH-implicit account owner (or a relayer acting on their behalf) simply needs to sign/relay an Ethereum-emulated ERC-20 transfer whose `target`/token contract is attacker-controlled (e.g. a scam token, or the attacker interacting with their own wallet contract via a token they deploy), and have that token's `storage_balance_of` return an oversized/expensive-to-deserialize payload. No validator, network, or operator privilege is required — only a standard `FunctionCall` transaction plus a normal contract deployment.

### Recommendation
Clear `has_in_flight_tx` (or otherwise make the in-flight guard resettable) via a mechanism that does not depend on the same receipt that performs unbounded/attacker-influenced work completing successfully — for example, decouple the flag reset from the callback's main logic by performing it in a minimal, gas-cheap wrapper executed with guaranteed gas before any variable-cost deserialization, or bound/validate the size of cross-contract responses before deserializing them, or add a recovery path (e.g., a timeout-based or owner-signed "force reset" action) that can clear a stuck `has_in_flight_tx` flag.

### Proof of Concept
1. Deploy a malicious NEP-141-like contract whose `storage_balance_of` method returns a very large/deeply nested JSON payload.
2. As the eth-implicit account owner, sign (via the standard `rlp_execute` flow used in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/utils/test_context.rs`) an ERC-20 "transfer" Ethereum transaction targeting the malicious contract.
3. Relay the transaction through `rlp_execute`; `inner_rlp_execute` schedules `storage_balance_of` → `nep_141_storage_balance_callback` with static gas `NEP_141_STORAGE_BALANCE_CALLBACK_GAS + action.gas()`.
4. The malicious contract's oversized response causes `nep_141_storage_balance_callback`'s `serde_json::from_slice` to exceed the allotted static gas, panicking and reverting the `has_in_flight_tx = false` write from step 2 (`self.has_in_flight_tx = true` set in `rlp_execute`).
5. All further `rlp_execute` calls on this wallet contract now immediately return `"transaction already in progress"`, permanently blocking any future transfer of the account's `$NEAR` balance.

    #[payable]
    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }
