### Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, allowing replay-verify to certify a diverged world-state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by chunk-executor replay verification, `db-tool`'s `replay_on_archive`, and the Aptos debugger/CLI transaction-replay commands) checks status, gas, write-set hash, and event root hash against a proof-authenticated `TransactionInfo`, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description
`ensure_match_transaction_info` is the function these tools rely on to confirm that a locally re-executed transaction matches the transaction info that is bound (via the transaction accumulator / `TransactionInfoWithProof`) to an authenticated ledger version. [1](#0-0) 

The function verifies:
- execution status [2](#0-1) 
- gas used [3](#0-2) 
- write-set hash (`state_change_hash`) [4](#0-3) 
- event root hash [5](#0-4) 

But it never compares the locally-computed world-state root (`state_checkpoint_hash`), the hot-state root, or the new `position_state_checkpoint_hash` field against the values carried in the authenticated `TransactionInfo`. This gap is explicitly acknowledged in a TODO directly above the `Ok(())` return: [6](#0-5) 

`TransactionInfoV1` and `TransactionInfoV0` both carry these checkpoint hash fields as part of the accumulator leaf that is authenticated by `TransactionAccumulatorProof`/`LedgerInfo`. [7](#0-6) 

This comparator is used by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which re-executes a chunk and calls `ensure_match_transaction_info` per transaction to validate replayed output against archived `TransactionInfo`s. [8](#0-7) 
- `storage/db-tool/src/replay_on_archive.rs`'s replay-verify path, which is the primary mainnet archive-integrity tool.
- `aptos-move/cli/src/commands.rs`'s transaction-replay/debugger commands. [9](#0-8) [10](#0-9) 

Because the write set and events being validated are, by design, the transient per-transaction outputs, and the world state root is only materialized at checkpoint boundaries, a bug anywhere in state-value merklization, hot-state handling, or the new "position state" (trading-native) tree could cause the *locally computed* state root to diverge from the *authenticated* `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` recorded on-chain — while `ensure_match_transaction_info` would still report success, because the write-set hash and event root can match even though the resulting Merkle root over state does not (e.g. mis-ordering of updates, an off-by-one in usage/version binding at checkpoint construction, or a divergent hot-state/position-state root computation).

### Impact Explanation
This breaks the "authenticated response/proof must stay bound to the right ledger version and root" invariant for replay/restore verification tooling: it can allow a real state-commitment divergence (e.g., corrupted or incorrectly computed Merkle/JMT root at a checkpoint, or a bug in the not-yet-enabled "trading native"/position-state tree) to go undetected in the exact tool designed to catch it. This is High severity because it undermines the core auditing mechanism operators and researchers use to confirm mainnet ledger integrity against backups/archives — a corrupted or manipulated state root could pass "replay verify" clean, delaying detection of consensus-breaking divergence, hard-fork bugs, or archive tampering.

### Likelihood Explanation
The comment states this gap exists specifically because `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state checkpoint hashing is not yet fully wired into this comparator, and it is a currently-shipping (not test/mock/example) code path exercised by `verify_execution` and `replay_on_archive`, both used on real ledger data. It requires only a latent divergence in state-root computation (from any bug, not attacker-controlled input) to be silently missed by this check — moderate likelihood in practice since it is a detection gap rather than a directly attacker-triggerable primitive, but it fires automatically whenever such a divergence occurs.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally-computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when available/applicable to the transaction) against the corresponding fields on `txn_info`, failing loudly on mismatch, before any feature flag depending on these checkpoints (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled on mainnet.

### Proof of Concept
Not independently reproducible from static analysis alone: this is a detection-gap finding (missing invariant check), not an attacker-triggerable exploit primitive. Reproduction would require inducing an actual state-root divergence (e.g., a checkpoint-hash-computation bug) and observing that `chunk_executor::verify_execution` / `db-tool replay_on_archive` / CLI replay commands report success despite the world-state root differing from the authenticated `TransactionInfo.state_checkpoint_hash`, which requires environment access beyond static code review.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
