### Title
DKG aggregate-key poisoning via unrestricted `vote-for-aggregate-public-key` cross-cycle key reuse - (File: `stackslib/src/chainstate/stacks/boot/signers-voting.clar`)

### Summary
`signers-voting.clar` records every voted-on aggregate public key in a global `used-aggregate-public-keys` map, keyed only by the key bytes and independent of the reward cycle it is meant for [1](#0-0) . `is-novel-aggregate-public-key` only returns true if the key was never used, or was used for the *same* reward cycle [2](#0-1) . A signer belonging to the currently-established signer set can therefore submit a vote that binds a not-yet-approved future aggregate key to the wrong reward cycle, permanently poisoning that key for its intended cycle — the same "claim the victim's identifier before them" pattern described in the front-running report, just applied to the DKG key identity instead of a `loanId`.

### Finding Description
`vote-for-aggregate-public-key` accepts `(signer-index, key, round, reward-cycle)` from any address, verified only by weight lookup and vote-uniqueness for that `(reward-cycle, round, signer)` tuple [3](#0-2) . Crucially, the private helper `is-in-voting-window`, defined to gate voting to the correct prepare-phase window for the correct cycle [4](#0-3) , is never invoked inside `vote-for-aggregate-public-key`. The only cycle-scoped guard actually enforced is "not yet approved for this cycle" [5](#0-4) , not "we are inside this cycle's voting window."

Because of this missing check, any signer who is a legitimate (weighted) member of *some* already-established reward-cycle's signer set can call the function at any time, supplying any `reward-cycle` value for which they hold weight, and any `key` value of their choosing. If that signer learns (e.g., via signer-to-signer DKG gossip/StackerDB traffic that necessarily precedes the on-chain vote) the aggregate public key that the legitimate signer set intends to finalize for reward cycle `N+1`, the attacker submits a vote using that exact key but tagged to a *different* reward cycle they control, e.g. `N`. Because `used-aggregate-public-keys` is set unconditionally with `map-set` after any accepted vote [6](#0-5) , the key is now bound to cycle `N`. When the honest cycle `N+1` signers later submit their votes for that same key, `is-novel-aggregate-public-key` returns false and `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY` is raised for every vote using that key [7](#0-6) , permanently blocking that key from ever being approved for cycle `N+1`, exactly mirroring the reported bug class: the attacker's front-run claim on a shared identifier causes the legitimate participants' equivalent transaction to revert.

### Impact Explanation
This is minority-triggerable: a single rogue or compromised signer with nonzero weight in any established cycle is sufficient — no majority of signer weight is needed to execute the poisoning transaction itself (only ordinary weight to be considered a legitimate voter, which the honest key-holder needs to have *some* weight, not the majority). The result is that the correct DKG output for a target reward cycle can never be finalized on-chain, forcing signers to burn additional off-chain DKG rounds/keys and delaying `.signers-voting` consensus on the aggregate key — a bounded "poison" of the signer voting state rather than a chain split, matching the High-impact category of a minority-triggerable static-validation/consensus-state divergence.

### Likelihood Explanation
Requires the attacker to (a) already be a weighted member of some signer set (a normal, unprivileged actor role in this system, not an admin/majority) and (b) learn a not-yet-submitted legitimate aggregate key value before it is broadcast, which is plausible since DKG round-key material and coordination happen over signer-to-signer channels/StackerDB ahead of the final on-chain vote transaction, and mempool visibility of the first submitted vote would also reveal the key to any observer in time to front-run subsequent legitimate votes for the correct cycle.

### Recommendation
Enforce `is-in-voting-window` (or an equivalent reward-cycle/round validity check binding the vote strictly to the reward cycle whose signer set was just set) inside `vote-for-aggregate-public-key` before accepting any vote, and consider scoping `used-aggregate-public-keys` uniqueness checks so a key can only be marked "used" once bound to a cycle for which the voting window is currently open, preventing any address from pre-emptively claiming a key for an unrelated cycle.

### Proof of Concept
1. Reward cycle `N`'s signer set is already set via `.signers set-signers`, and attacker `A` is one of its weighted members.
2. Honest signers for cycle `N+1` compute aggregate key `K` off-chain via DKG and prepare to submit `vote-for-aggregate-public-key(idx, K, round=0, reward-cycle=N+1)`.
3. `A` observes `K` (via signer gossip/StackerDB traffic or a pending mempool tx) and immediately calls `vote-for-aggregate-public-key(A-idx, K, round=0, reward-cycle=N)` — this succeeds because `is-in-voting-window` is never checked, and `used-aggregate-public-keys` records `K -> N` [6](#0-5) .
4. When honest signers' votes for `reward-cycle=N+1` using key `K` are processed, `is-novel-aggregate-public-key K N+1` evaluates `(is-eq N N+1)` → `false`, so every such vote reverts with `ERR_DUPLICATE_AGGREGATE_PUBLIC_KEY` [8](#0-7) , permanently preventing cycle `N+1` from ever approving key `K`.
