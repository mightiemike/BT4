### Title
Deleting an account never releases its postponed / pending-input-data receipt state, permanently leaking un-charged global state trie storage - (File: `core/store/src/utils/mod.rs`)

### Summary
`action_delete_account` / `remove_account` remove an account's `Account`, `ContractCode`, `AccessKey`/gas-key-nonce and `ContractData` entries, but never touch the per-account receipt-processing bookkeeping (`PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`) that is keyed by the same `AccountId`. This bookkeeping is also explicitly excluded from `storage_usage` accounting ("we don't charge storage for receipts"), so it is never staked/paid for. If an account accumulates such entries and is then deleted while a data dependency remains unmet, the entries become permanently orphaned in the global state trie: no code path ever visits or removes them again, mirroring the FlashMQ bug where a session's queued QoS messages are never released on session expiration.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:504-575`) is the sole cleanup routine invoked from `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`, call at `:387`). It removes: [1](#0-0) 

only `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/gas-key-nonce entries, and `TrieKey::ContractData`. It does **not** iterate or remove `TrieKey::PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId` — all of which are keyed `{receiver_id: AccountId, ...}` exactly like the columns that *are* cleaned up: [2](#0-1) 

These entries are set via `set_postponed_receipt` / `set` for `PendingDataCount`/`PostponedReceiptId` when an incoming action receipt has unmet `input_data_ids` (`process_action_receipt`, `runtime/runtime/src/lib.rs:1647-1712`): [3](#0-2) 

They are only ever removed when the matching `Data` receipt actually arrives and decrements the pending count to zero (`process_receipt`, `runtime/runtime/src/lib.rs:1421-1528`). There is no other place in the codebase that garbage-collects these keys independent of that specific resolving receipt arriving.

Crucially, this postponed-receipt bookkeeping is explicitly **not counted against the account's `storage_usage`**, per the runtime's own storage-accounting comment: [4](#0-3) 

So none of it is subject to the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` cap checked in `action_delete_account` (which only looks at `account.storage_usage()`), and none of it required storage staking to create.

`PromiseYield`/`PromiseYieldStatus` entries are *not* the practical leak vector here because they are bounded by the timeout queue: `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3113-3209`) fires unconditionally at `expires_at` regardless of whether the owning account still exists, synthesizing a `PromiseResume` that removes the `PromiseYieldReceipt`/`PromiseYieldStatus` entries: [5](#0-4) 

The unbounded, permanently-orphanable case is the plain postponed `Action` receipt / `PendingDataCount` / `PostponedReceiptId` / `ReceivedData` family: these have **no timeout mechanism at all** and are cleaned up only by the arrival of a specific `Data` receipt satisfying `input_data_ids`. If that Data receipt is never produced (e.g., its producing receipt errors out before emitting output data, is dropped, or is simply never sent by a cooperating/malicious predecessor contract), the postponed state can never be resolved. Once the receiver account is subsequently deleted via `DeleteAccount`, there is no remaining reference or process that will ever visit those trie keys again — they are permanently stuck, exactly like FlashMQ's queued QoS messages that survive session expiry because nothing releases them.

### Impact Explanation
Each unresolved postponed-receipt entry set (`PostponedReceiptId` + `PendingDataCount` + `PostponedReceipt`, or `ReceivedData` waiting on a postponed receipt that never completes) permanently inflates the global state trie that every validator/RPC node must store and replicate forever, without the attacker ever paying storage stake for it (the state-applier code explicitly disclaims charging for receipts). This is an unbounded, uncompensated state-growth primitive reachable from an ordinary, unprivileged account: create postponed dependencies, ensure they are never satisfied, then delete the account so no code path can ever reclaim the entries. This bypasses the storage-staking economic model that NEAR relies on specifically to prevent unbounded free state growth, which is the closest concrete-impact category ("fee bypass") available for this bug class under the review's acceptance criteria.

### Likelihood Explanation
The missing-cleanup root cause is directly verified in `remove_account`/`action_delete_account`, requires no privileged role, and is reachable purely via standard `FunctionCall`/`DeleteAccount` transactions from the account owner. The remaining open question — the exact contract-level sequence guaranteed to leave `input_data_ids` permanently unsatisfied (e.g., whether a failed receipt's `new_receipts`, including its `output_data_receivers` `Data` receipt, are always cleared on error, or whether `Data` output is always emitted even on failure to support `PromiseResult::Failed` semantics) — was not fully resolved from the available code excerpts and should be confirmed with a live trace/test by the engineering team before treating this as fully weaponizable at scale. The architectural gap itself (no cleanup, no charge) is proven with certainty regardless.

### Recommendation
- In `remove_account` (`core/store/src/utils/mod.rs`), also iterate and remove `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, and yield-id mapping entries scoped to the deleted `account_id`, mirroring the existing access-key/contract-data iteration.
- Alternatively (or additionally), require `action_delete_account` to reject deletion while any such pending entries exist for the account (similar to the existing storage-usage-based `DeleteAccountWithLargeState` guard), forcing resolution or explicit reclamation before deletion.
- Charge storage stake for postponed-receipt bookkeeping proportional to its lifetime/size, or add a timeout/GC mechanism (analogous to the `PromiseYieldTimeout` queue) for plain postponed action receipts so they cannot remain unresolved indefinitely.

### Proof of Concept
1. Attacker deploys a contract on account `A` (or uses an existing account) and issues a batch of promise actions whose callback receipt on `A` carries `input_data_ids` dependent on a companion cross-contract call, per the standard `promise_then` callback pattern (`runtime/runtime/src/receipt_manager.rs:111`, `create_action_receipt`).
2. Attacker arranges for the dependency's resolving `Data` receipt to never be produced/delivered to `A` (candidate mechanisms requiring engineering verification: forcing the producing receipt into an error path whose `new_receipts` — including the `output_data_receivers` `Data` receipt — are discarded, per `runtime/runtime/src/lib.rs` `set_error` receipt-clearing behavior referenced in `protocol-model/spec/runtime-execution.md:149`).
3. This leaves `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` trie entries under `receiver_id = A` permanently pending (confirmed unremovable absent the missing Data receipt, per `runtime/runtime/src/lib.rs:1421-1528`).
4. Attacker then submits `DeleteAccount` for `A`. `action_delete_account`/`remove_account` (`runtime/runtime/src/actions.rs:330-406`, `core/store/src/utils/mod.rs:504-575`) delete the account but leave the `PostponedReceipt*`/`PendingDataCount` keys intact in the trie, uncharged and now permanently orphaned since no future receipt can ever arrive to resolve them.
5. Repeating steps 1–4 across many disposable accounts accumulates unbounded, free, permanent global-state trie growth.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
