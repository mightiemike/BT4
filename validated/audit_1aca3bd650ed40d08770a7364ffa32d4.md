### Title
Gateway `validate` entry point leaks raw internal blockifier/state-storage error strings to the transaction sender - (File: crates/apollo_gateway/src/stateful_transaction_validator.rs)

### Summary
The Starknet gateway's `add_tx` flow runs stateful validation of a submitted transaction via `StatefulValidator::validate`. When this validation fails for any reason other than the well-known Cairo-level revert path, `run_validate_entry_point` takes the raw `StatefulValidatorError` and puts its `Display` (`e.to_string()`) directly into the `message` field of a `StarknetError` with code `ValidateFailure`, which is returned verbatim to the RPC/HTTP caller.

### Finding Description
`run_validate_entry_point` converts any error from `blockifier_validator.validate(account_tx)` into a user-facing message without sanitization or generalization: [1](#0-0) 

`blockifier_validator.validate` returns `StatefulValidatorResult<()>`, whose error is `StatefulValidatorError`, an enum that transparently wraps several deep internal error types: [2](#0-1) 

One of the wrapped variants is `StateError`, which itself contains: [3](#0-2) 

`StateError::StateReadError(String)` carries an opaque `String` populated by the underlying storage/state-reader implementation (e.g., `apollo_state_reader`, `apollo_rpc_execution`, sync/py state readers - 14+, 7+, 7+ call sites respectively construct this variant from lower-level backend errors). These backend errors can include storage-engine internals (e.g., file/DB errors, RocksDB-style messages, path fragments, or other environment-specific diagnostic text) that were never designed to be shown to an external caller. Because `run_validate_entry_point` calls `.to_string()` on the whole `StatefulValidatorError` chain (via `thiserror`'s `#[error(transparent)]` propagation) and puts it straight into the response `message`, any state-read failure encountered while validating a submitted transaction is relayed unfiltered to the transaction sender.

This is structurally identical to the reported AshAi bug class: a user-facing validation error is built by calling `to_string()`/`inspect()` on a raw internal error term instead of returning a generic, sanitized message and logging the real error server-side. The rest of the gateway code base is otherwise careful about this exact risk — e.g. `StarknetError::internal_with_logging` explicitly logs the real error and returns only `"Internal error"` to the caller: [4](#0-3) 
and the HTTP layer even has a dedicated sanitization step for other error paths: [5](#0-4) 
but `run_validate_entry_point`'s final `.map_err` bypasses both of these safeguards by directly embedding `e.to_string()` as the `ValidateFailure` message, which is not classified as `is_internal()` and therefore is not caught by generic internal-error redaction paths.

### Impact Explanation
An unprivileged transaction sender can trigger this path by simply submitting any transaction to the gateway that reaches `run_validate_entry_point` and causes a state read to fail (e.g., by referencing an address/class in a way that trips the underlying storage backend into an unexpected error, or by racing/triggering backend I/O errors during the concurrent state read used for validation). The resulting `StarknetError{code: ValidateFailure, message: e.to_string()}` is returned directly to the RPC caller as part of the standard add_tx error response, disclosing internal implementation details of the node's storage/state-reader layer (error text is not classified as `is_internal()`/redacted, and is not passed through the HTTP-layer sanitizer that only escapes special characters rather than removing sensitive content). While this does not directly expose credentials the way the AshAi report did (this Starknet sequencer has no third-party embedding-provider API keys in this code path), it is the same bug class — disclosure of raw internal error state to an untrusted caller — and can leak internal storage/backend diagnostic information that aids further attacks or reveals implementation/environment details that should remain private to the node operator.

### Likelihood Explanation
High reachability: this code executes on the hot path of every `add_tx` call for invoke/declare/deploy-account transactions during stateful validation, gated only by normal gateway admission (no special privilege required). Any transaction that causes `StatefulValidator::validate` to return an `Err` (state error, executor error, pre-validation error, or transaction-execution error other than the ones handled by earlier, more specific mappers) results in raw error text propagating to the caller. Triggering the specific `StateReadError` variant requires an underlying backend failure, which is not guaranteed on every request, but the sink itself indiscriminately serializes the `Display` of the entire `StatefulValidatorError` union (including `TransactionExecutionError`/`TransactionExecutorError`/`TransactionPreValidationError` internals), so any latent error text in any of these deep transparent wrapper chains is exposed the same way.

### Recommendation
In `run_validate_entry_point` (crates/apollo_gateway/src/stateful_transaction_validator.rs:351-354), stop returning `e.to_string()` directly as the user-facing message. Instead:
- Log the full `StatefulValidatorError` (and its source chain) server-side via `tracing::error!`/`warn!`.
- Return a generic, fixed message for the `ValidateFailure` code (or, where the error is a legitimate Cairo-level validate revert reason, continue surfacing that specific, already-sanitized string, but exclude `StateError`/`TransactionExecutorError`/other infrastructure-layer variants from being echoed back).
- Mirror the existing pattern used elsewhere in this file/module, e.g. `StarknetError::internal_with_logging`, which logs internally and returns only `"Internal error"` to the caller.

### Proof of Concept
1. Submit any transaction to the gateway `add_tx` endpoint such that `extract_state_nonce_and_run_validations` proceeds to `run_validate_entry_point`.
2. Cause (or wait for) the underlying state reader used by `CachedState`/`StateReaderAndContractManager` to return a `StateError::StateReadError(msg)` during the `__validate__` call (e.g., a backend I/O hiccup, or by constructing a request that exercises an edge case in the state reader implementation, e.g. `apollo_state_reader::apollo_state`).
3. Observe the gateway's response: `StarknetError { code: ValidateFailure, message: <raw internal error string> }`, returned as the HTTP/RPC error body to the client, per crates/apollo_gateway/src/stateful_transaction_validator.rs:345-354.
4. Confirm the message content is the literal `Display` output of the internal `StatefulValidatorError`/`StateError` value rather than a sanitized/generic message — unlike the deliberate redaction pattern used by `StarknetError::internal_with_logging` in crates/apollo_gateway_types/src/deprecated_gateway_error.rs:76-79.

/// Serializes a `StarknetError` into an HTTP response, encode the error message
/// to defend potential Cross-Site risks.
fn serialize_error(error: &StarknetError) -> Response {
    let quote_re = Regex::new(r#"[\"`]"#).unwrap(); // " and ` => ' (single quote)
    let sanitize_re = Regex::new(r#"[^a-zA-Z0-9 :.,\[\]\(\)\{\}'_]"#).unwrap(); // All other non-alphanumeric characters except [:.,[](){}]_ => ' ' (space)

    let mut message = error.message.clone();
    message = quote_re.replace_all(&message, "'").to_string();
    message = sanitize_re.replace_all(&message, " ").to_string();

    let sanitized_error = StarknetError { code: error.code.clone(), message };

    serde_json::to_vec(&sanitized_error)
        .expect("Expecting a serializable StarknetError.")
        .into_response()
}
