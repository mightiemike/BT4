### Title
Unauthenticated JSON-RPC methods `citrea_haltCommitments` / `citrea_resumeCommitments` allow any caller to halt sequencer L1 commitment production - (File: `crates/sequencer/src/rpc.rs`)

### Summary
The sequencer exposes `citrea_haltCommitments` and `citrea_resumeCommitments` as public JSON-RPC methods. Unlike `citrea_testPublishBlock`, which checks `self.context.test_mode` before acting, these two methods perform no authorization or mode check whatsoever, and they are not included in the RPC layer's `PROTECTED_METHODS` allow-list that gates access behind the `api_key`. Any unauthenticated network caller reaching the sequencer's RPC port can therefore halt (or resume) the sequencer's production of `SequencerCommitment`s to the Bitcoin DA layer.

Compare this to `publish_test_block`, the sibling method, which explicitly checks a privileged/mode flag before acting: [3](#0-2) 

The node's RPC authentication middleware only protects three named methods — `backup_create`, `backup_validate`, `backup_info` — via the `api_key` mechanism; every other method, including `citrea_haltCommitments` and `citrea_resumeCommitments`, bypasses authentication entirely: [4](#0-3) 

The halt/resume signal is forwarded from the RPC handler into the sequencer runner's main loop, which relays it to the `CommitmentService`: [5](#0-4) 

`CommitmentService` toggles `is_producing_commitments` based on this signal and skips all commitment creation/submission while halted: [6](#0-5) 

This is confirmed by the project's own integration test, which shows that calling `halt_commitments()` over RPC completely stops new commitments from being sent to the DA layer, and `resume_commitments()` restores them: [7](#0-6) 

### Impact Explanation
Sequencer commitments are the mechanism by which L2 block ranges are anchored and made verifiable on the Bitcoin DA layer — batch provers, full nodes, and the light-client proof pipeline all depend on commitments continuing to be posted at the sequencer's configured cadence. An unauthenticated caller who can reach the sequencer's RPC endpoint can invoke `citrea_haltCommitments` to indefinitely stop commitment submission (silently, since the RPC call itself just returns `Ok(())`), stalling batch proving, finalization progress, and the light-client proof chain for the rollup, without needing any credential, API key, sequencer role, or private key. This is precisely the "unauthenticated JSON-RPC call that mutates node state" class of High-severity issue: a state-mutating admin action reachable without going through the `Auth` middleware that was clearly intended to gate privileged operations (as evidenced by the existing `PROTECTED_METHODS`/`api_key` mechanism protecting the analogous `backup_*` methods).

### Likelihood Explanation
No special access is required — only network reachability to the sequencer's JSON-RPC port, which is exposed by `start_rpc_server` using the standard `RpcConfig` (`bind_host`/`bind_port`) with no per-method authorization aside from the `Auth` middleware's hardcoded 3-method allow-list. Any client capable of forming a JSON-RPC request (`citrea_haltCommitments`) can trigger it immediately and repeatedly.

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and any other sensitive administrative sequencer RPC methods) to the `PROTECTED_METHODS` list in `crates/common/src/rpc/auth.rs` so they require a valid `api_key`, mirroring the protection already applied to `backup_create`/`backup_validate`/`backup_info`. Alternatively, gate these methods behind the same kind of explicit mode/authorization check used by `publish_test_block`.

### Proof of Concept
1. Start a sequencer node with default configuration (no custom RPC auth beyond the built-in `api_key`, which by default protects only backup methods).
2. As an unauthenticated remote client, send:
```json
{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}
```
3. Observe (as shown by the existing test `test_sequencer_halt_resume_commitments`) that the sequencer stops submitting `SequencerCommitment`s to the DA layer even though L2 block production continues.
4. The attacker can leave commitments halted indefinitely (or toggle at will via `citrea_resumeCommitments`), degrading/stalling the rollup's finalization and proving pipeline, purely via unauthenticated RPC access.
