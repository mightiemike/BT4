### Title
Unbounded permanent `FailedVerification` tombstone accumulation in `ProgramCache` from cheap malformed program accounts - (File: program-runtime/src/loaded_programs.rs / program-runtime/src/program_cache_entry.rs / svm/src/program_loader.rs)

### Summary
An unprivileged attacker can create arbitrarily many distinct accounts owned by `bpf_loader`/`bpf_loader_deprecated` with invalid ELF/verifier-failing bytecode, invoke each as a `program_id` in a cheap transaction, and cause a permanent `FailedVerification` tombstone `ProgramCacheEntry` to be inserted into the validator-global `ProgramCache::index` for each distinct pubkey. These tombstones are never evicted by memory-pressure eviction and are never pruned by `ProgramCache::prune`, so cache memory grows without bound relative to attacker cost (one cheap transaction + refundable rent per entry).

### Finding Description
`svm/src/program_loader.rs::load_program_with_pubkey` loads an account, and if ELF parsing/verification fails (`ProgramCacheEntry::new` returns `Err`), it builds a permanent tombstone via `ProgramCacheEntry::new_tombstone(deployment_slot, owner, ProgramCacheEntryType::FailedVerification(env))` at [2](#0-1) . For LoaderV1/V2 (`bpf_loader`/`bpf_loader_deprecated`) accounts, `deployment_slot` is hardcoded to `0` at [3](#0-2) .

This tombstone is then inserted into `ProgramCache::index` (a `HashMap<Pubkey, Vec<Arc<ProgramCacheEntry>>>`) via `assign_program`, keyed by the account's own pubkey [4](#0-3) . Because each malformed account uses a distinct pubkey, each produces its own top-level HashMap entry — there is no cap on distinct keys.

Two independent mechanisms are supposed to bound cache growth, and both fail to reclaim these entries:
1. **Eviction** (`evict_using_random_selection` / `sort_and_unload`) only unloads `Loaded` entries into `Unloaded`; tombstones (`FailedVerification`, `Closed`, `DelayVisibility`) are explicitly excluded from eviction, confirmed by the test comment "Tombstones and unloaded entries are expected to not be evicted" at [5](#0-4)  and the eviction logic itself at [6](#0-5) .
2. **Pruning** (`ProgramCache::prune`) removes entries only for orphaned forks or stale runtime environments [7](#0-6) . For an entry at `deployment_slot == 0`, the check `entry.deployment_slot <= self.latest_root_slot` is always true (since `latest_root_slot` only increases), and it is retained as the "first ancestor" found for that key's `Vec` — every slot-0 tombstone survives every future reroot indefinitely, since there's only one entry per key's `Vec` and it's always treated as the still-relevant first ancestor.

Because the account owner check for program invocation (`svm/src/account_loader.rs::load_transaction_accounts`) only verifies `PROGRAM_OWNERS.contains(owner_id)` [1](#0-0)  without requiring the account to be marked `executable`, an attacker can trivially create such an account (`system_instruction::create_account` with `owner = bpf_loader::id()`, arbitrary garbage data) and reference it as `program_id` in an instruction of a transaction they submit. The transaction fails with `InvalidProgramForExecution` or similar, but the cache entry is inserted as a side effect of `load_program_with_pubkey`/`filter_executable_program_accounts` regardless of the transaction's ultimate success.

Since `ProgramCache` is explicitly documented as "not persisted to disk or a snapshot" [8](#0-7) , this growth is bounded by validator uptime (a restart clears it), but during that uptime the cache HashMap can grow without bound as new distinct malformed pubkeys are used, even after the attacker closes the source accounts and reclaims rent — the tombstone remains regardless of the underlying account's continued existence.

### Impact Explanation
This is a disproportionate-cost resource-exhaustion (memory growth) issue on every validator that processes the attacker's transactions: cache index memory (one `HashMap` entry + `Vec<Arc<ProgramCacheEntry>>` + `FailedVerification(ProgramRuntimeEnvironment)` per malformed pubkey) grows linearly with the number of distinct malformed accounts submitted, while attacker cost is one cheap transaction fee plus refundable rent per account (rent is later reclaimed by closing the account, since the cache entry is decoupled from account existence). This matches an Agave bounty category of disproportionate storage/CPU cost / DoS via cache exhaustion, scoped to `program-runtime`'s `ProgramCache`.

### Likelihood Explanation
Fully reachable by an unprivileged attacker using only standard `system_instruction::create_account` (setting `owner = bpf_loader::id()`) and submitting one transaction per malformed program id referencing that garbage-owned account as an instruction `program_id`. No special permissions, validator/leader control, or account-executable flag are required. It is trivially automatable and repeatable at essentially unbounded scale, limited only by attacker transaction throughput and fee budget.

### Recommendation
Bound the number of persistent `FailedVerification`/other tombstone entries in `ProgramCache`, e.g., by:
- Including tombstones in a capacity-aware LRU/GDSF eviction pool (or a separate bounded pool) rather than excluding them entirely from eviction.
- Enforcing a hard cap on distinct tombstone entries (or total `index` size) with eviction of least-recently-used tombstones once exceeded.
- Alternatively, avoid caching a `FailedVerification` tombstone at all for pubkeys whose account no longer satisfies basic sanity checks (e.g., not `executable`), or expire tombstones for accounts that have since been closed/re-purposed.

    pub fn prune(
        &mut self,
        new_root_slot: Slot,
        new_environment: Option<ProgramRuntimeEnvironment>,
        fork_graph: &FG,
    ) {
        match &mut self.index {
            IndexImplementation::V1 { entries, .. } => {
                for second_level in entries.values_mut() {
                    // Remove entries un/re/deployed on orphan forks
                    let mut first_ancestor_found = false;
                    let mut first_ancestor_env = None;
                    *second_level = second_level
                        .iter()
                        .rev()
                        .filter(|entry| {
                            let relation =
                                fork_graph.relationship(entry.deployment_slot, new_root_slot);
                            if entry.deployment_slot >= new_root_slot {
                                matches!(relation, BlockRelation::Equal | BlockRelation::Descendant)
                            } else if matches!(relation, BlockRelation::Ancestor)
                                || entry.deployment_slot <= self.latest_root_slot
                            {
                                if !first_ancestor_found {
                                    first_ancestor_found = true;
                                    first_ancestor_env = entry.program.get_environment();
                                    return true;
                                }
                                // Do not prune the entry if the runtime environment of the entry is
                                // different than the entry that was previously found (stored in
                                // first_ancestor_env). Different environment indicates that this entry
                                // might belong to an older epoch that had a different environment (e.g.
                                // different feature set). Once the root moves to the new/current epoch,
                                // the entry will get pruned. But, until then the entry might still be
                                // getting used by an older slot.
                                if let Some(entry_env) = entry.program.get_environment()
                                    && let Some(env) = first_ancestor_env
                                    && entry_env != env
                                {
                                    return true;
                                }
                                self.stats.prunes_orphan.fetch_add(1, Ordering::Relaxed);
                                false
                            } else {
                                self.stats.prunes_orphan.fetch_add(1, Ordering::Relaxed);
