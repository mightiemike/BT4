`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash verification, letting replay-verify accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the sole per-transaction correctness gate used by the archive replay-verification tool. It checks status, gas, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code's own TODO documents.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates `status`, `gas_used`, `write_set` (via `state_change_hash`), and `event_root_hash` against the archived `TransactionInfo`, but the closing comment states outright:

"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [2](#0-1) 

This function is consumed directly by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions locally and calls `ensure_match_transaction_info` as the only correctness check per transaction, with no independent verification of `state_checkpoint_hash` anywhere in that file: [3](#0-2) 

Because `state_checkpoint_hash` (the JMT/state-Merkle root committed at checkpoint boundaries) is never re-derived and compared during replay-verify, a divergence between the locally re-executed state tree and the archived, ledger-committed state root at a checkpoint transaction is silently accepted as a passing replay. The write-set hash check only proves the individual transaction's write-set bytes match; it says nothing about whether accumulating those writes into the state tree produces the same root that was actually committed and signed into the `LedgerInfo`.

### Impact Explanation
`replay_on_archive` (and `aptos-debugger`, which shares the same verification primitive) is the tool operators and auditors use to confirm that an archived, already-committed chain history is reproducible by independent re-execution — i.e., to detect a hard fork / non-determinism / storage corruption between what was committed on mainnet and what a clean re-execution produces. Because the state (and hot-state / position-state) checkpoint root is never compared, a state root divergence introduced by a bug in execution, storage commit, or Merkle accumulation would go completely undetected by this tool, even though gas/status/events/write-set hash for the individual transaction still matched. This directly undermines the "wrong accumulator/Merkle root accepted as valid" and "restore/replay path reinterpreting committed data" integrity guarantees: the primary safety net for catching ledger state divergence during replay is a no-op for the state root itself.

### Likelihood Explanation
This isn't a hypothetical edge case — it's an intentional, currently-shipped gap acknowledged in the code, exercised on every checkpoint transaction processed by `replay_on_archive`/`aptos-debugger` (i.e., always, since every block boundary is a checkpoint). Any latent nondeterminism or storage bug affecting state-tree construction (independent from write-set serialization) would pass replay-verify silently today.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash` (and, when the relevant feature flags are enabled, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) between the locally re-executed state summary and `txn_info`, failing verification on mismatch, as the existing TODO already prescribes before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled for the base state root case that is always active regardless of that flag.

### Proof of Concept
Not independently reproducible without a live divergence-inducing bug; the finding is a verification-logic gap (missing invariant check), not a triggerable state corruption by itself. Demonstrating full impact would require pairing it with a separate bug that corrupts the state Merkle tree while leaving write-set bytes/gas/events/status intact — at which point `replay_on_archive`/`aptos-debugger` would report success despite the state root diverging, since [4](#0-3)  is exhaustive of the checks performed and none of them cover the checkpoint hash.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
