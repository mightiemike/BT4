### Title
Self-matching a taker order against your own resting maker order causes the maker-side settlement credit to be silently overwritten (lost) - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
When a taker's `MarketSellAssetContract` matches a resting maker order owned by the **same address**, `matchSingleOrder` credits the maker leg via the 2-arg `addTrxOrToken(MarketOrderCapsule, long)` helper, which reads a fresh `AccountCapsule` from `accountStore`, applies the credit, and immediately `accountStore.put`s it. `execute()` subsequently performs its own unconditional `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` using the taker-side in-memory `AccountCapsule` that was loaded *before* the maker-side write. Because both writes target the same account key in a self-trade, the final `execute()` write clobbers the maker-side credit, permanently erasing that portion of the settlement.

### Finding Description
`execute()` loads the account once up front: [1](#0-0) 

then mutates it in memory for the taker's sell leg and passes it through `matchOrder`: [2](#0-1) 

Inside `matchSingleOrder`, the taker leg is credited on the same in-memory `takerAccountCapsule`, but the maker leg uses the standalone helper that re-reads the account from the store, mutates it, and writes it back right away: [3](#0-2) [4](#0-3) 

Finally, `execute()` unconditionally persists the taker-side `AccountCapsule` snapshot taken before the maker-side write occurred: [5](#0-4) 

When the maker order's owner equals the taker's owner (self-trade — nothing in `validate()` prevents this, it only forbids `sellTokenID == buyTokenID`, not same-owner matching, see lines 202-224), both writes target the same DB key. The 2-arg `addTrxOrToken` writes an updated copy to the store, but that copy is immediately overwritten by `execute()`'s final `accountStore.put` using the stale in-memory `accountCapsule`, which never observed the maker-side delta. This is a classic lost-update race within a single transaction execution.

### Impact Explanation
The maker-side buy-token credit is erased from persisted state. Concretely, in a full self-match, the account ends up net-negative by the exact matched credit amount (asset/TRX permanently lost/burned from the user's balance), because the sell-side deduction from `transferBalanceOrToken` and the maker-side credit that should return value were both computed but the credit was discarded by the overwrite. This is a direct, unauthorized loss of user funds/assets, not merely a display bug, since it's the final on-chain committed state.

### Likelihood Explanation
Fully reachable by any unprivileged account with no special privileges: (1) submit a `MarketSellAssetContract` selling token A for token B, letting it rest as a maker order; (2) submit a second `MarketSellAssetContract` from the same address selling B for A, sized/priced to match the resting order. Both are ordinary public transactions. The only chain-level precondition is that the market feature is enabled (`dynamicStore.supportAllowMarketTransaction()`), which is a general feature flag, not an attacker-controlled privilege. The bug is deterministic and repeatable every time a self-match occurs.

### Recommendation
Avoid the read-modify-write race by not re-fetching the maker's account inside `addTrxOrToken(MarketOrderCapsule, long)` when its owner equals the taker's owner: detect self-trade in `matchSingleOrder`/`matchOrder` and apply the maker-side credit onto the same in-memory `takerAccountCapsule` object used for the taker leg (analogous to the 3-arg `addTrxOrToken` overload), only falling back to the independent read/write path when the maker's address differs from the taker's. Alternatively, refactor so all account mutations for a given key within one `execute()` call operate on a single cached, in-memory `AccountCapsule` instance (keyed by address) that is loaded once and written once at the end, eliminating the possibility of overwriting intermediate writes to the same key.

### Proof of Concept
```java
// Add to MarketSellAssetActuatorTest.java
@Test
public void selfMatchLosesMakerCredit() throws Exception {
  InitAsset();

  byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
  AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
  accountCapsule.addAssetAmountV2(TOKEN_ID_ONE.getBytes(), 1000L,
      dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
  accountCapsule.addAssetAmountV2(TOKEN_ID_TWO.getBytes(), 1000L,
      dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
  dbManager.getAccountStore().put(ownerAddress, accountCapsule);

  // Step 1: owner creates resting maker order: sell 100 of TOKEN_ID_ONE for 100 of TOKEN_ID_TWO
  MarketSellAssetActuator makerActuator = new MarketSellAssetActuator();
  makerActuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
      OWNER_ADDRESS_FIRST, TOKEN_ID_ONE, 100L, TOKEN_ID_TWO, 100L));
  TransactionResultCapsule ret1 = new TransactionResultCapsule();
  makerActuator.validate();
  makerActuator.execute(ret1);

  // sanity: TOKEN_ID_ONE deducted, TOKEN_ID_TWO unchanged
  accountCapsule = dbManager.getAccountStore().get(ownerAddress);
  long tokenOneAfterMaker = accountCapsule.getAssetV2MapForTest().get(TOKEN_ID_ONE); // 900
  long tokenTwoAfterMaker = accountCapsule.getAssetV2MapForTest().get(TOKEN_ID_TWO); // 1000

  // Step 2: same owner creates taker order that fully self-matches: sell 100 of TOKEN_ID_TWO for 100 of TOKEN_ID_ONE
  MarketSellAssetActuator takerActuator = new MarketSellAssetActuator();
  takerActuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
      OWNER_ADDRESS_FIRST, TOKEN_ID_TWO, 100L, TOKEN_ID_ONE, 100L));
  TransactionResultCapsule ret2 = new TransactionResultCapsule();
  takerActuator.validate();
  takerActuator.execute(ret2);

  accountCapsule = dbManager.getAccountStore().get(ownerAddress);
  long tokenOneFinal = accountCapsule.getAssetV2MapForTest().get(TOKEN_ID_ONE);
  long tokenTwoFinal = accountCapsule.getAssetV2MapForTest().get(TOKEN_ID_TWO);

  // Expected (no net change from a full self-trade round trip):
  // tokenOneFinal == 1000 (900 + 100 credited back as taker)
  // tokenTwoFinal == 1000 (1000 - 100 debited as taker, +100 credited as maker)
  Assert.assertEquals(1000L, tokenOneFinal);
  Assert.assertEquals(1000L, tokenTwoFinal); // FAILS: actual is 900 — maker-side 100 TOKEN_ID_TWO credit lost
}
```
Running this test against the current code shows `tokenTwoFinal == 900` instead of the expected `1000`, demonstrating that the maker-side credit written by `addTrxOrToken(MarketOrderCapsule, long)` (`MarketSellAssetActuator.java:550-562`) is overwritten by `execute()`'s final `accountStore.put` (`MarketSellAssetActuator.java:148`), confirming the lost-update / erasure of settlement value.
