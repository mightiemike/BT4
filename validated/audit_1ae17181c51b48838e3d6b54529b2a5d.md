## Title
Unbounded recursive `bytecode_hash_node` compiled-class hashing can stack-overflow the sequencer's class manager / gateway process outside compiler sandboxing - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs` recursively walks a `NestedIntList` bytecode-segment tree (`node.iter_children()`) with no depth bound to compute the compiled-class hash [1](#0-0) . This computation runs in `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs`) via `executable_class.hash(&HashVersion::V2)`, which is invoked in the parent `apollo_class_manager`/`apollo_compile_to_casm` process, i.e. *after* the actual Sierra→CASM compilation has already returned from the CPU/memory/time-limited sandboxed subprocess [2](#0-1) .

### Finding Description
The MySQL CVE describes a DDL operation (schema change) that can crash/hang the server due to an unguarded code path reachable by a privileged client. The closest Starknet analog reachable from an unprivileged sender is a `Declare` transaction, which is Starknet's "DDL"-equivalent (it registers a new class/schema in state).

The declare flow is:
`Gateway::add_tx_inner` → `convert_rpc_tx_to_internal_and_executable_txs` → `ClassManager::add_class` → `SierraCompiler.compile` [3](#0-2) [4](#0-3) .

Inside `SierraCompiler::compile`, the actual Sierra→CASM transformation is delegated to a subprocess with enforced `max_cpu_time`/`max_memory_usage`/`max_bytecode_size` limits, specifically to contain crashes from malicious classes (as demonstrated by `memory_limit_error_message`, which documents the subprocess being "terminated by signal 6" on OOM without taking down the parent) [5](#0-4) [6](#0-5) .

However, immediately after the sandboxed `compile()` call returns, the parent process computes `executable_class.hash(&HashVersion::V2)` directly, unsandboxed [7](#0-6) . This hash computation walks the CASM's `bytecode_segment_lengths` tree (`NestedIntList`) via `bytecode_hash_node`, which recurses once per tree level with **no maximum-depth check** [1](#0-0) . Because `bytecode_segment_lengths` reflects the nesting structure of the compiled Sierra program's control flow (branches/functions), a Sierra program crafted to produce deeply/pathologically nested segments (bounded only by `max_bytecode_size`, which limits total bytecode length but not tree depth) can force a stack depth proportional to the number of nested segments, well beyond default thread stack sizes, causing a Rust stack overflow. Unlike a normal panic, stack overflow aborts the process (SIGABRT/SIGSEGV) and is not recoverable via `Result`/`catch_unwind`, and this occurs in the parent `apollo_class_manager` / `apollo_compile_to_casm` component - not inside the resource-limited compiler subprocess that the codebase explicitly built to contain exactly this class of crash.

The same hashing routine is also exercised again later during declare validation (`check_compile_class_hash_v2_declaration`, `crates/starknet_api/src/executable_transaction.rs:228-244`) and gateway validation, meaning a crash could recur at multiple stages of the declare-processing pipeline for a single malicious class.

### Impact Explanation
A single attacker-submitted `Declare` transaction with a specially crafted Sierra program can crash the `apollo_class_manager`/`apollo_compile_to_casm` component of a sequencer process outside the protection of the existing subprocess sandbox that was specifically designed to isolate such crashes. Repeated submission (each requiring only normal declare fees/resource bounds - not any special privilege) could repeatedly crash/restart this component, denying the sequencer's ability to process new declare transactions and, if this component's failure cascades (e.g., via shared process or restart storms), broader transaction confirmation. This matches "network unable to confirm new transactions" territory, analogous to the CVE's DoS impact on MySQL Server via DDL.

### Likelihood Explanation
Likelihood is Medium: the attacker needs only to submit an ordinary `Declare` transaction (no elevated privilege, unlike the CVE which required "high privileged attacker"), making this trivially reachable by any unprivileged sender who can pay the fee. The main uncertainty is exactly how deep/pathological a `bytecode_segment_lengths` tree the compiler (`cairo_lang_starknet_classes`) can be coerced to emit for a class within the `max_bytecode_size` limit, and the default stack size configured for the `apollo_class_manager`/`apollo_compile_to_casm` component threads (unlike the `blockifier` execution path, which explicitly pre-allocates large stacks for recursion-heavy Cairo-native execution, no equivalent stack-size hardening was found for this hashing path in the class-manager/compiler binaries).

### Recommendation
- Bound the recursion depth of `bytecode_hash_node` (and the equivalent `iter_children` traversal) to a fixed maximum matching whatever structural nesting limit the compiler enforces, rejecting any `bytecode_segment_lengths` tree that exceeds it before hashing.
- Alternatively/additionally, perform the `executable_class.hash(&HashVersion::V2)` computation inside the same resource-limited subprocess/sandbox that performs Sierra→CASM compilation, so a stack overflow there is contained the same way OOM/CPU-limit violations already are.
- Convert the recursive traversal to an explicit iterative (stack-based) algorithm to remove reliance on native call-stack depth entirely.

### Proof of Concept
1. Craft a Sierra program whose compiled CASM bytecode segment structure (`bytecode_segment_lengths`) is deeply nested (e.g., via many nested conditional branches/functions) while keeping total bytecode size under `max_bytecode_size`.
2. Submit this class via a `Declare` transaction through the gateway (`Gateway::add_tx_inner`).
3. Observe that after successful sandboxed compilation, the subsequent `executable_class.hash(&HashVersion::V2)` call in `apollo_compile_to_casm`/`apollo_class_manager` recurses through `bytecode_hash_node` for each segment-tree level and overflows the thread stack, aborting the process - unlike the already-mitigated OOM/CPU-limit case in `compile_test.rs::memory_limit_error_message`, this crash is not contained by any sandbox.

*Note: I could not fully verify the exact maximum achievable segment-tree depth produced by the `cairo_lang_starknet_classes` compiler for a given `max_bytecode_size`, nor the exact stack size configured for the `apollo_class_manager`/`apollo_compile_to_casm` runtime threads, since those details live in dependency crates/deployment configs not fully covered by the indexed codebase. Confirming the precise depth threshold required to trigger an actual stack overflow would require hands-on testing in a full checkout.*

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

            contract_class,
            additional_args,
            resource_limits,

#[test]
fn memory_limit_error_message() {
    let compiler = SierraToCasmCompiler::new(SierraCompilationConfig {
        max_bytecode_size: DEFAULT_MAX_BYTECODE_SIZE,
        max_memory_usage: 8 * 1024 * 1024,
        max_cpu_time: DEFAULT_MAX_CPU_TIME,
        audited_libfuncs_only: false,
    });
    let contract_class = get_test_contract();

    let error_message = match compiler.compile(contract_class) {
        Err(CompilationUtilError::CompilationError(msg)) => msg,
        other => panic!("Expected CompilationError, got: {other:?}"),
    };

    // The exact allocation byte count and presence of the backtrace hint
    // vary between runs depending on the compiler binary's memory layout.
    // Anchoring with ^ and $ also verifies the cleanliness intent: no
    // resource-limit setup noise or stack frames around the OOM message.
    let backtrace_note =
        r"(\nnote: run with `RUST_BACKTRACE=1` environment variable to display a backtrace)?";
    let pattern = Regex::new(&format!(
        r"^memory allocation of \d+ bytes failed{backtrace_note} \(process terminated by signal 6\)$"
    ))
    .unwrap();
    assert!(pattern.is_match(&error_message), "unexpected error message: {error_message:?}");
}
