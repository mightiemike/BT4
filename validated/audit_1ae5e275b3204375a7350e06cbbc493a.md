### Title
Hardcoded `MAX_MATCH_NUM` limit causes legitimate `MarketSellAssetContract` orders to revert mid-execution after state has already been partially mutated in-memory - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.execute()` performs a multi-step atomic operation: it deducts the fee, transfers the sell-side balance/token, creates and persists the taker order, and then matches the taker order against resting maker orders in the order book. If the number of matches required to fill (or partially fill) the taker order exceeds the hardcoded `MAX_MATCH_NUM` (20), the actuator throws a `ContractValidateException` mid-way through `matchOrder`, which is caught in `execute()` and rethrown as `ContractExeException`. This is directly analogous to the ICHI vault report: a single logical operation is decomposed into sequential steps where a hardcoded limit enforced partway through can cause the whole operation to revert, with no way for the caller to split it into multiple transactions to avoid the failure, since matching happens synchronously within one `execute()` call.

### Finding Description
`MarketSellAssetActuator.execute()` runs several steps in sequence: pay fee, `transferBalanceOrToken`, `createAndSaveOrder`, then `matchOrder` (which iterates over resting maker orders and calls `matchSingleOrder` repeatedly), and finally persists the order and account state. [1](#0-0) 

Inside `matchOrder`, each successful match increments `matchOrderCount`, and once it exceeds the hardcoded constant `MAX_MATCH_NUM` (20), a `ContractValidateException` is thrown mid-loop: [2](#0-1) 

`MAX_MATCH_NUM` is a fixed, non-configurable value: [3](#0-2) 

This exception propagates out of `execute()` and is converted into a `ContractExeException`: [4](#0-3) 

Unlike the ICHI vault bug (where a single-call re-deposit exceeding `deposit0Max/1Max` reverts), here the entire sell transaction—including fee payment, balance transfer, and order creation that already happened earlier in the same `execute()` call—reverts, because `Manager.pushTransaction`/`generateBlock` only merge the `ISession` on success; on any exception the session is closed without merging, which triggers `Session.close()`/`revoke()` and rolls back all state mutated during `processTransaction`, including the earlier fee deduction and order creation: [5](#0-4) [6](#0-5) 

Because matching is entirely synchronous within a single actuator execution, there is no way for a user to "break down" a large sell order into multiple transactions to avoid the revert — the number of matches needed against the resting order book at the time of execution is fully determined by market state, not user input. This exposes the exact same bug class as the report: a legitimate multi-step atomic user operation can be forced to revert entirely by a hardcoded per-call limit that the user cannot control or predict, and cannot work around via transaction splitting because the limit is enforced mid-operation, not up front. Additionally, since resting maker orders (from any account, including an adversary) determine the match count, an attacker can grief legitimate large taker sell orders by placing many small maker orders at favorable prices for the pair, deliberately pushing any large opposing taker order over `MAX_MATCH_NUM` and forcing it to always revert (denial of service against otherwise valid market orders) — the taker's `validate()` step cannot detect this in advance because it does not simulate matching against the order book.

### Impact Explanation
Impact is Medium: legitimate market participants attempting to sell an asset that requires matching more than 20 resting maker orders will always have their transaction fail with `ContractExeException` ("Too many matches"), even though their order parameters (price, quantity, balances) are entirely valid per `validate()`. This is a denial-of-service on the TRON internal DEX (Market) feature for legitimate large orders whenever liquidity is fragmented across more than `MAX_MATCH_NUM` price-compatible maker orders, and it can be intentionally triggered/amplified by an adversary who fragments their own maker liquidity to block others' otherwise-valid sell orders from executing (griefing). Unlike the ICHI report's more contained impact (funds simply aren't locked, other withdraw options remain available), java-tron's market DEX has no alternative withdrawal-type route — a taker's `MarketSellAssetContract` transaction simply cannot succeed under these conditions no matter how it's constructed, since matching order count is outside caller control.

### Likelihood Explanation
Likelihood is Medium: it requires the order book for a given token pair to have more than 20 matchable price-compatible maker orders at execution time. This can occur naturally in an active market, and can be trivially and cheaply engineered by any user creating multiple small maker orders (bounded only by `MAX_ACTIVE_ORDER_NUM = 100` per account) to intentionally grief specific counterparties or trade pairs.

### Recommendation
Do not hard-fail the entire transaction when the match count limit is reached. Instead, stop matching gracefully once `MAX_MATCH_NUM` matches have been consumed, persist the partially-filled taker order into the order book (as already done via `saveRemainOrder` for the remaining quantity), and return success — analogous to allowing partial execution rather than reverting the whole operation. Alternatively, expose `MAX_MATCH_NUM` as a per-transaction or dynamic-store-configurable parameter, and/or perform a pre-flight simulation during `validate()` so callers can detect and react to (e.g., reduce order size) an unmatchable order before committing gas/fees, rather than fully reverting deep into `execute()`.

### Proof of Concept
1. An attacker (or natural market activity) creates 21+ small resting `MarketSellAssetContract` orders for pair (B, A) at prices that would match a victim's taker order for pair (A, B), respecting `MAX_ACTIVE_ORDER_NUM = 100`.
2. A victim submits a valid `MarketSellAssetContract` selling asset A for asset B with a quantity large enough that, given the fragmented order book, matching requires more than `MAX_MATCH_NUM = 20` maker orders. [7](#0-6) 
3. `validate()` succeeds since it has no way to know the number of on-chain matches required.
4. `execute()` deducts the fee, transfers the sell balance/token, creates the order, then calls `matchOrder`, which increments `matchOrderCount` on each match; upon the 21st match it throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")`. [8](#0-7) 
5. The exception is caught in `execute()` and rethrown as `ContractExeException`, causing `processTransaction`'s `ISession` to never merge and the entire mutation (fee burn, balance transfer, order creation, and all partial matches already applied to in-memory capsules) is discarded via `revoke()`. The victim's transaction fails unconditionally regardless of how it is resubmitted, as long as the order-book fragmentation persists — confirmed by the existing regression test `exceedMaxMatchNumLimit` in `MarketSellAssetActuatorTest.java`, which reproduces exactly this revert scenario. [9](#0-8)

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
