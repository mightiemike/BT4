### Title
Webhook HMAC only signs the request body, not the `X-Shopify-Shop-Domain`/topic headers, allowing cross-tenant webhook forgery - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
The Solana vault bug allowed an attacker to supply an unverified, attacker-controlled field (`deposit_token` / `token_hash`) that was never cryptographically bound to the value the program actually trusted (`allowed_token`), letting the attacker substitute a worthless token while the protocol still credited USDC. The analogous flaw in `shopify-app-js` is in webhook signature verification: `validateHmacFromRequest` computes and checks the HMAC only over `rawBody`, while the shop-identifying `X-Shopify-Shop-Domain` header (and topic) — which downstream code trusts to select *which merchant's* offline session/access token to load — is never part of the signed data.

### Finding Description
`validateHmacFromRequestFactory` retrieves the HMAC header and validates it against `rawBody` only: [1](#0-0) 

`checkWebhooksHeaders` (and the events variant) then reads the `domain`, `topic`, and other headers purely as required-presence fields — it never verifies they match anything covered by the HMAC: [2](#0-1) 

The webhook authentication flow then uses `check.domain` — an unauthenticated header value — as the shop identity to load (or create) that shop's offline session and access token, and dispatches the parsed body to app webhook handlers under that shop's session context: [3](#0-2) [4](#0-3) 

The same pattern is used in `shopify-app-express`'s `process()` handler, which passes `webhookCheck.domain` straight to the registered callback: [5](#0-4) 

Because the HMAC secret (`config.apiSecretKey`) is the app's single, global client secret — identical for every shop that installs the app — an attacker who installs the app on their own (attacker-controlled) shop can trigger a legitimate webhook (e.g. `products/create`) and capture a valid `(rawBody, hmac)` pair signed by Shopify with that shared secret. The attacker can then POST that exact `rawBody` + `hmac` to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain (and/or a different topic). `validateHmacString` still succeeds because it only compares the HMAC against `rawBody`, which is unchanged; `checkWebhooksHeaders` only requires the domain header to be non-empty. This is a direct structural analog to the Solana bug: a security-critical field (`domain`/shop identity, analogous to `deposit_token`) is disjoint from the field that is actually authenticated (`hmac` over body, analogous to `token_hash`), and downstream logic trusts the unauthenticated field.

### Impact Explanation
A successful forgery causes the app to: (1) load/refresh the victim shop's real offline session and access token via `ensureValidOfflineSession`/`createOrLoadOfflineSession`, and (2) invoke the app's registered webhook handler with attacker-chosen JSON payload, `webhookCheck.topic`, and `webhookId`, but the *victim's* `shop`/session/admin API client. Depending on what the app's webhook handlers do with the payload (e.g. update records keyed by webhook body, trigger side effects such as billing changes, uninstall cleanup, GDPR data actions, or write app data tied to `shop`), this enables cross-tenant data corruption or unauthorized actions performed under a real merchant's authenticated session context, entirely from an anonymous/attacker-installed shop.

### Likelihood Explanation
Any actor can freely install the app on a shop they control (Shopify apps can typically be installed on any dev/production store) and capture at least one valid webhook body+HMAC pair without any special privilege. Forging the domain/topic header on replay requires no cryptographic secret knowledge, only header manipulation, since those fields sit entirely outside the HMAC's signed byte range. This significantly increases likelihood versus other analogs requiring secret leakage or MITM.

### Recommendation
Include the security-relevant headers (`X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-API-Version`) in the HMAC-covered data, or otherwise cryptographically bind the domain to the same proof used for the body (e.g., verify the header values against Shopify's per-shop webhook secret if available, or reject and re-validate the returned `check.domain` against an out-of-band trusted source, such as fetching the shop from the previously established/matching offline session rather than trusting the header verbatim). At minimum, document/require apps to treat `webhookCheck.domain` as untrusted unless corroborated by an independent authenticated channel.

### Proof of Concept
1. Register the target app on an attacker-controlled dev store; trigger any webhook topic (e.g. `products/create`) to capture `rawBody` and the valid `X-Shopify-Hmac-Sha256` header Shopify sends (signed with the app's shared `apiSecretKey`).
2. Replay the exact `rawBody` and `hmac` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.io` (and optionally change `X-Shopify-Topic`).
3. `validateHmacFromRequest` in [6](#0-5)  succeeds because only `rawBody` is checked; `checkWebhooksHeaders` accepts the forged `domain`/`topic` because it only checks for header presence.
4. `authenticate()` in [7](#0-6)  loads the victim shop's offline session and dispatches the attacker's payload to the app's handler under `shop: 'victim-shop.myshopify.io'`.
