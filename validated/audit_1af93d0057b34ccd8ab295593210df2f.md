### Title
DoS via unbounded VotesStore iteration in `getPaginatedNowWitnessList` reachable from anonymous HTTP/gRPC requests - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The `getPaginatedNowWitnessList` API, exposed via `GetPaginatedNowWitnessListServlet` and gRPC `RpcApiService`, is intended to return a *paginated* slice of witnesses. However, before applying the `offset`/`limit` pagination, it unconditionally calls `countVote(votesStore)`, which iterates over **every entry in the entire `VotesStore`** — i.e., every account that has voted in the current epoch — regardless of the requested page size.

### Finding Description
`Wallet.getPaginatedNowWitnessList()` first loads all witnesses, then calls the private helper `countVote(votesStore)`, which walks the full `VotesStore` iterator and aggregates old/new vote deltas for every voter entry in the store: [1](#0-0) [2](#0-1) 

This is analogous to the reported `_calculateMaxVotePossible()`/`getTotalVotingPower()` bug in Ve.sol: an unbounded loop over the full set of stakers/voters is executed to compute an aggregate value, even though only a small paginated slice of the result is ultimately needed. In java-tron, `VotesStore` accumulates one entry per account that casts a vote via `VoteWitnessActuator` in the current maintenance cycle — this can grow to be very large (potentially hundreds of thousands of entries on a live network with high voter participation), since there is no cap on the number of distinct voting accounts, only a cap on the number of candidates a single account can vote for (`MAX_VOTE_NUMBER`), enforced in `VoteWitnessActuator.validate()`: [3](#0-2) 

The endpoint is reachable by any anonymous caller with no privilege requirement, both via HTTP: [4](#0-3) 
and via gRPC through `RpcApiService`, which also calls `wallet.getPaginatedNowWitnessList`.

Unlike the on-chain `Ve.sol` case where the cost is metered in EVM gas, here the cost is CPU time and DB reads on the full node itself. A caller can invoke this endpoint repeatedly (or with a large `limit`/`offset` that still forces the full unpaginated scan) to force the node to repeatedly scan its entire `VotesStore` on every request, tying up node resources (RocksDB iterator overhead, deserialization of every `VotesCapsule`, and Java heap allocation for a full `HashMap` of vote deltas) for O(n) work per request where n is the total number of active voters network-wide.

### Impact Explanation
This does not corrupt consensus state or directly stall block production (unlike the in-protocol `MaintenanceManager.doMaintenance()` which also does a similar full-store scan but only once per maintenance cycle and as part of normal block processing already budgeted for). However, because this API path is exposed to arbitrary, unauthenticated RPC/HTTP clients and performs unbounded work per call, it enables a low-cost, repeatable resource-exhaustion (DoS) attack against a full node's RPC/HTTP service, degrading availability of the node's public API for legitimate users. If deployed widely on public RPC endpoints (as is common for java-tron full nodes), this is a meaningful availability risk at the RPC-API layer.

### Likelihood Explanation
High: no authentication, no permission check, and no rate limiting beyond the generic `RateLimiterServlet` (which limits request rate but not per-request cost) is applied before the expensive scan executes. Any attacker can trigger the full scan with a single request, and the cost scales with the number of active voters, which grows over time as network participation increases.

### Recommendation
Avoid a full `VotesStore` scan on every read-only pagination request. Options:
- Maintain a running aggregate (similar to the recommended `pointHistory`/`totalSupply()` pattern in the original report) so witness vote deltas can be looked up without iterating the entire store, or apply pagination-aware filtering that only touches the relevant subset of `VotesStore` entries.
- Alternatively, cache the result of `countVote()` per block/maintenance cycle instead of recomputing it on every API call, since the underlying `VotesStore` only changes once per epoch during `MaintenanceManager.doMaintenance()`.
- Add a hard cap or circuit breaker on the cost of this endpoint (e.g., reject if `VotesStore` size exceeds a safe threshold, or precompute/cache and serve the cached snapshot).

### Proof of Concept
1. Populate `VotesStore` with a large number of distinct voter entries (achievable over time as normal `VoteWitnessContract` transactions accumulate one entry per unique voting account per epoch — no single-transaction cap prevents this since `MAX_VOTE_NUMBER` only limits candidates per vote, not the number of distinct voters).
2. As an anonymous client, repeatedly send `GET /wallet/getpaginatednowwitnesslist?offset=0&limit=1` (or the gRPC equivalent) to a public full node.
3. Each request forces `Wallet.getPaginatedNowWitnessList` → `countVote(votesStore)` to iterate the entire `VotesStore`, regardless of the tiny requested page size, consuming CPU/DB I/O proportional to the total number of network voters on every call.
4. Repeated concurrent requests degrade the node's RPC/HTTP service responsiveness for all other API consumers.
