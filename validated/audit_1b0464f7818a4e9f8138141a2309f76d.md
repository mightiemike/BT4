### Title
`TransactionOutput::ensure_match_transaction_info` never validates state-checkpoint / hot-state / position-state roots, letting corrupted checkpoint hashes pass chunk-executor and replay verification - ([File: types/src/transaction/mod.rs])

### Summary
`ensure_match_transaction_info` is the function used by the chunk executor (state-sync/replay path) and the debugger/CLI replay-verify tooling to confirm that a re-executed `TransactionOutput` matches a previously persisted/authenticated `TransactionInfo`. It checks status, gas, write-set hash, and event-root hash, but by its own documented admission it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is exactly the kind of "authenticated proof-bearing response bound to the wrong root" gap the state-integrity gate is looking for: replay/verification code can affirmatively report a match while the recomputed world-state (or position-state) Merkle root actually diverges from the one the network committed to.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is defined at: [1](#0-0) 

It validates:
- `status` vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `write_set_hash` (hash of `self.write_set()`) vs. `txn_info.state_change_hash()`
- recomputed `event_root_hash` vs. `txn_info.event_root_hash()`

but the function ends with an explicit acknowledged gap: [2](#0-1) 
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

`TransactionInfo` carries these fields precisely because they are authenticated, accumulator-committed roots of ledger state at checkpoint boundaries: [3](#0-2) [4](#0-3) 

`ensure_match_transaction_info` is invoked from the chunk executor's ledger-update path, i.e., during transaction replay/verification when applying a chunk from a peer or during sync: [5](#0-4) 

It is also used by `aptos-debugger` and the `aptos-move/cli` replay/verification commands, which are the tools operators and auditors use to validate that on-chain history is internally consistent. Because the comparison omits the checkpoint-hash fields, any code path that computes a `TransactionOutput` whose write set matches the persisted `state_change_hash` (i.e. per-transaction resource writes are unchanged) but whose *derived Merkle root* over that state differs — for example a bug in the (in-development) `position_state_checkpoint_hash`/hot-state root computation, a Jellyfish Merkle Tree defect, or a divergent `DoStateCheckpoint` implementation — will still be reported as "matches", i.e., a wrong root is silently accepted as valid by the verification tooling.

### Impact Explanation
This breaks the invariant that authenticated proof/commitment fields (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) inside `TransactionInfo` are actually verified against locally recomputed state whenever a `TransactionOutput` is checked against a `TransactionInfo`. A wrong Merkle/state root can propagate through the chunk-executor commit path and through operator-facing replay-verify tooling without detection, since the function that is supposed to catch such divergence structurally cannot: it never compares those hash fields at all. This falls squarely under "wrong accumulator root, Merkle proof ... accepted as valid" in the gate criteria, because the very code responsible for flagging root mismatches during replay/commit validation is missing the check.

### Likelihood Explanation
The gap is unconditional in the current code — it exists regardless of feature flags today because the comparator simply never inspects the three checkpoint-hash fields, and the TODO itself flags this as a real, understood pre-existing hole that must be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." The state-checkpoint hash and hot-state hash fields are also present and set on `TransactionInfoV0`/`V1` for ordinary, already-live checkpoint logic (per-block state checkpoints, hot-state) — not just for the not-yet-enabled trading/position feature — so the missing validation already applies to the pre-existing `state_checkpoint_hash`/`hot_state_checkpoint_hash` checks used by chunk-executor replay today, not only to the future position-state feature.

### Recommendation
Extend `ensure_match_transaction_info` to compare the caller-supplied/recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when applicable/known) against the corresponding fields on `txn_info`, returning an error on mismatch, mirroring the existing `write_set_hash`/`event_root_hash` checks. This should be resolved before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, but the state/hot-state checkpoint hash validation gap applies to the currently-active checkpoint mechanism as well and should be closed independently.

### Proof of Concept
Not independently reproducible from static analysis alone — the vulnerability is a validation-omission (missing check), not a triggerable exploit path in this codebase snapshot. The proof of the gap is the function body itself: [1](#0-0)  never reads `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` from either `self` or `txn_info`, so any `TransactionOutput`/`TransactionInfo` pair with identical write-set/event hashes but different checkpoint hashes will pass `ensure_match_transaction_info` unconditionally, as confirmed by the author's own TODO comment describing this exact scenario.

Note: I could not verify from the index whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently enabled on mainnet (only its definition and a handful of references were found), which affects how much of the `position_state_checkpoint_hash` portion of this gap is presently reachable versus forward-looking; the `state_checkpoint_hash`/`hot_state_checkpoint_hash` portion, however, applies to already-active checkpoint logic.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    pub fn update_ledger(&self) -> Result<()> {
        let _timer = CHUNK_OTHER_TIMERS.timer_with(&["chunk_update_ledger_total"]);

        let (parent_state_summary, parent_position_state_summary, parent_accumulator, chunk) =
            self.commit_queue.lock().next_chunk_to_update_ledger()?;
        let ChunkToUpdateLedger {
            output,
            chunk_verifier,
        } = chunk;

        let txn_infos = chunk_verifier.transaction_infos();
        let known_state_checkpoints = Some(
            txn_infos
                .iter()
                .map(|t| t.state_checkpoint_hash())
                .collect_vec(),
        );
        let known_hot_state_checkpoints =
            output.execution_output.hot_state_root_in_txn_info.then(|| {
                txn_infos
                    .iter()

                    .collect_vec()
            });
        let compute_trading_native_state_roots =

                .iter()
                .map(|t| t.position_state_checkpoint_hash())
                .collect_vec()
        });
        let position_persisted = compute_trading_native_state_roots
            .then(|| ProvablePositionStateSummary::new_persisted(self.db.reader.as_ref()))
            .transpose()?;
        let state_checkpoint_output = DoStateCheckpoint::run()
            .execution_output(&output.execution_output)

            .persisted_state_summary(&ProvableStateSummary::new_persisted(

            .maybe_known_state_checkpoints(known_state_checkpoints)
            .maybe_known_hot_state_checkpoints(known_hot_state_checkpoints)
            // Parent position summary is chained across chunks by the commit

            // base supplies cold-key proofs. The known-hash check validates the

            .maybe_parent_position_state_summary(parent_position_state_summary.as_ref())

            .build()?;

        let ledger_update_output = DoLedgerUpdate::run(
            &output.execution_output,

            parent_accumulator.clone(),
        )?;

        chunk_verifier.verify_chunk_result(&parent_accumulator, &ledger_update_output)?;
