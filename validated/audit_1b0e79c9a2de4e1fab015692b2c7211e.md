### Title
Backup-restored `write_sets` are never authenticated against the accumulator-committed `state_change_hash`, allowing corrupted write sets to be persisted as if verified - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
The transaction-backup restore path reads `write_sets` directly from the backup file as raw, untrusted bytes and only "verifies" the chunk using `TransactionListWithProof`/`TransactionListWithProofV2`, a type that intentionally does not include write sets. As a result, the write set bytes that get persisted into `LedgerDb`/`WriteSetDb` (and used for the "save before replay" fast path) are never checked against `txn_info.state_change_hash()`, even though that hash is exactly the field the transaction accumulator proof authenticates.

### Finding Description
In `LoadedChunk::load`, the code parses each backup record into `(txn, aux_info, txn_info, events, write_set)` and stores `write_sets` in a `Vec<WriteSet>` separate from the `txn_list_with_proof` object: [3](#0-2) 

The `txn_list_with_proof` built here (`TransactionListWithProofV2::new(TransactionListWithAuxiliaryInfos::new(TransactionListWithProof::new(txns, Some(event_vecs), ..., TransactionInfoListWithProof::new(range_proof, txn_infos))))`) is then verified: [4](#0-3) 

But `TransactionListWithProof` only contains `transactions`, `events`, `first_transaction_version`, and `proof` — no `write_sets` field exists on this struct at all: [1](#0-0) 

Its `verify()` checks (1) transaction-hash match against `txn_info.transaction_hash()`, (2) the accumulator range proof over the `TransactionInfo` hashes, and (3) event root hashes — nothing about write sets: [2](#0-1) 

By contrast, `TransactionOutputListWithProof::verify` (used in the state-sync/output path) explicitly recomputes `CryptoHash::hash(&txn_output.write_set)` and checks it equals `txn_info.state_change_hash()`: [5](#0-4) 

That check is the analog of `Transaction::ensure_match_transaction_info`, which is the canonical invariant binding a write set to its committed `TransactionInfo`: [6](#0-5) 

In the backup/restore flow, after `LoadedChunk::load()` "verifies" the chunk (without ever touching `write_sets`), the unchecked `write_sets` are handed to `restore_handler.save_transactions(...)` / `restore_utils::save_transactions` and written straight into `WriteSetDb` alongside the (verified) `txn_infos`: [7](#0-6) [8](#0-7) 

This is precisely the "save before replay" fast path — i.e., versions restored below `first_to_replay` are persisted without any VM re-execution, and hence without any independent recomputation of the state-change hash. The `range_proof`/accumulator only proves the `TransactionInfo` (which carries `state_change_hash`) is in the ledger; it does not prove that the concurrently-loaded `write_sets` bytes match that hash. A corrupted, truncated, or tampered `write_set` in the backup blob (from a compromised/faulty backup storage backend, e.g. `BackupStorage`) will pass `LoadedChunk::load`'s verification untouched and be committed to `WriteSetDb` as if authenticated, silently diverging the restored state from the value actually captured on-chain and referenced by `state_change_hash`/the accumulator proof.

### Impact Explanation
This breaks the state-commitment/proof-integrity invariant that everything reachable from a `TransactionInfo` proven-in-the-accumulator (the `state_change_hash`) must correspond to the actual write set applied. A node performing a "restore then save-before-replay" recovery from an untrusted or compromised backup source can end up with a divergent ledger (wrong committed resource/account values at restored versions) without any error, since nothing in the restore's verification step ever recomputes or checks `CryptoHash::hash(write_set) == txn_info.state_change_hash()`. This is a durable-storage state-commitment corruption issue, not merely an availability/DoS issue, and it can surface later as consensus/replay divergence when the node's state is used to serve authenticated API responses, generate/validate future state proofs, or continue chain execution from the corrupted state.

### Likelihood Explanation
Likelihood is Medium: it requires an operator to restore from a backup source that supplies mismatched write sets for otherwise-valid `TransactionInfo`/proof pairs (e.g. compromised or buggy `BackupStorage` implementation, corrupted transfer, or malicious storage backend), which is a plausible failure/attack surface distinct from a malicious validator/consensus actor. The affected code path (`save_before_replay_version`, versions below `first_to_replay`) is the default fast path used whenever a restore does not request full replay from genesis-adjacent versions.

### Recommendation
In `LoadedChunk::load` (or immediately after loading, before `save_transactions`), recompute `CryptoHash::hash(&write_set)` for each loaded `write_set` and assert equality with the corresponding `txn_info.state_change_hash()`, mirroring the check already done in `TransactionOutputListWithProof::verify` and `Transaction::ensure_match_transaction_info`. This closes the gap between the accumulator-proven `TransactionInfo` and the actually-persisted write set for the "save before replay" restore fast path.

### Proof of Concept
Conceptual PoC (cannot be executed without a full backup/restore test harness):
1. Produce a valid transaction backup chunk (via normal backup tooling) containing `(txn, aux_info, txn_info, events, write_set)` records and its accompanying `(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)`.
2. Tamper with only the `write_set` bytes of one record in the transaction chunk file (leave `txn_info`, `events`, and the proof untouched), simulating a compromised/corrupted `BackupStorage`.
3. Run `TransactionRestoreController`/`TransactionRestoreBatchController` against this tampered chunk with a `replay_from_version` set beyond this chunk's versions (so it goes through `save_before_replay_version`, not chunk-executor replay).
4. Observe that `LoadedChunk::load` succeeds (`txn_list_with_proof.verify(...)` at `storage/backup/backup-cli/src/backup_types/transaction/restore.rs:167` passes because it never inspects `write_sets`), and the tampered write set is written into `WriteSetDb` via `restore_utils::save_transactions_impl` at `storage/aptosdb/src/backup/restore_utils.rs:258-265`, producing a state at that version inconsistent with the on-chain committed `state_change_hash`.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
