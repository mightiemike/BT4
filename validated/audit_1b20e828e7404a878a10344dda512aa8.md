### Title
Missing Case Normalization in TRC10 Asset Name Uniqueness Check Enables Token Impersonation - (File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java)

### Summary
`AssetIssueActuator.validate()` enforces TRC10 token-name uniqueness by doing a raw, case-sensitive lookup of the asset name in `AssetIssueStore`, and only special-cases the reserved name `"trx"` by lowercasing it for comparison. Any other name is not normalized, so tokens that differ only by letter casing (e.g. `USDT` vs `usdt` vs `Usdt`) are treated as distinct on-chain assets, allowing an attacker to register a look-alike token name that most users/exchanges will treat as the same asset.

### Finding Description
When `dynamicStore.getAllowSameTokenName() == 0`, uniqueness of a new asset's name is enforced with a byte-exact check: [1](#0-0) 
This uses `assetIssueStore.get(assetIssueContract.getName().toByteArray())`, i.e. the raw bytes of the submitted name, as the store key (see `AssetIssueCapsule.createDbKey()`), with no case folding. [2](#0-1) 

The only place case is normalized at all is the reserved-word check that blocks issuing an asset literally named `TRX`/`trx`/etc.: [3](#0-2) 

Name format validation (`TransactionUtil.validAssetName`) only checks length and that each byte is a "readable" ASCII character (`0x21`–`0x7E`); it does not restrict or normalize case: [4](#0-3) 

This is analogous to the reported ZNS domain-spoofing issue: on-chain identifiers that differ only by case are recognized as distinct entities, while off-chain consumers (wallets, exchanges, block explorers, users) commonly treat names case-insensitively or fail to notice subtle case differences, creating impersonation/spoofing risk (e.g., registering `usdt` right after `USDT` exists, or vice versa).

Notably, the codebase already demonstrates that java-tron developers recognize this class of bug and have fixed it for a *different* identifier: `AccountIdIndexStore` (backing `SetAccountIdActuator`) explicitly lowercases keys on `put`/`get`/`has` to enforce case-insensitive uniqueness of account IDs: [5](#0-4) 
and there is dedicated test coverage plus a `MigrateTurkishKeyHelper` locale-normalization migration for this exact concern: [6](#0-5) 
However, this normalization was never applied to TRC10 asset names in `AssetIssueActuator`/`AssetIssueStore`, nor (as far as I could verify) to `AccountName`/`AccountIndexStore` used by `UpdateAccountActuator`, which performs a raw `has(accountName)` check without any case folding: [7](#0-6) 
I was unable to fully confirm the internals of `AccountIndexStore` (used by `UpdateAccountActuator`) since I ran out of tool calls before reading `chainbase/src/main/java/org/tron/core/store/AccountIndexStore.java`; it is possible (but unconfirmed) that it also lacks case normalization, which would extend this same finding to account display names.

### Impact Explanation
An attacker can broadcast an `AssetIssueContract` transaction naming a token with a case-variant of an existing, reputable TRC10 token name (e.g., a stablecoin or exchange token). Because the name uniqueness check is case-sensitive, this registration succeeds even though `getAllowSameTokenName() == 0` is meant to prevent duplicate/confusing token names. Users, wallets, or automated systems that normalize or display names case-insensitively could be misled into interacting with (sending funds to, trusting) the attacker's token instead of the legitimate one — an asset/accounting-integrity and impersonation risk reachable directly by any account via a normal broadcast transaction, at the cost of only the asset issue fee.

### Likelihood Explanation
This requires no special privileges, no leaked keys, and no protocol-level exploit — any account with enough balance to pay the `AssetIssueFee` can submit an `AssetIssueContract` transaction with an attacker-chosen case-variant name via the standard broadcast-transaction path. The bug is a straightforward logic gap in `AssetIssueActuator.validate()`, directly reachable, and requires no timing race beyond registering after the legitimate token exists.

### Recommendation
Normalize the asset name (and ideally the abbreviation) to a canonical case (e.g., lowercase using `Locale.ROOT`, mirroring `AccountIdIndexStore.getLowerCaseAccountId`) before performing the existence check in `AssetIssueActuator.validate()` and before using it as the storage key in `AssetIssueCapsule.createDbKey()`/`AssetIssueStore`, consistent with the approach already used for `AccountIdIndexStore`. Extend the same review to `AccountIndexStore`/`UpdateAccountActuator` for account display names if confirmed to lack normalization.

### Proof of Concept
1. Actor A issues a TRC10 token named `USDT` via `AssetIssueContract` while `AllowSameTokenName == 0`; validation passes and the token is stored under key `"USDT"`.
2. Actor B (attacker) issues a second `AssetIssueContract` with name `usdt`. In `AssetIssueActuator.validate()`, the check `assetIssueStore.get(assetIssueContract.getName().toByteArray()) != null` looks up key `"usdt"`, which does not match the stored key `"USDT"`, so the "Token exists" check is bypassed and the transaction succeeds.
3. Two visually/semantically identical token names now coexist on-chain as distinct assets, one of which is attacker-controlled, satisfying the token-impersonation/spoofing scenario described in the report.

  private static boolean validBytes(byte[] bytes, int maxLength, boolean allowEmpty) {
    if (ArrayUtils.isEmpty(bytes)) {
      return allowEmpty;
    }
    return bytes.length <= maxLength;
  }

  private static boolean validReadableBytes(byte[] bytes, int maxLength) {
    if (ArrayUtils.isEmpty(bytes) || bytes.length > maxLength) {
      return false;
    }
    // b must be readable
    for (byte b : bytes) {
      if (b < 0x21) {
        return false; // 0x21 = '!'
      }
      if (b > 0x7E) {
        return false; // 0x7E = '~'
      }
    }
    return true;
  }

  public void put(AccountCapsule accountCapsule) {

  }

  public byte[] get(ByteString name) {
    BytesCapsule bytesCapsule = get(name.toByteArray());
    if (Objects.nonNull(bytesCapsule)) {
      return bytesCapsule.getData();
    }
    return null;
  }

  @Override
  public BytesCapsule get(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
    if (ArrayUtils.isEmpty(value)) {
      return null;
    }
    return new BytesCapsule(value);
  }

  @Override
  public boolean has(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
