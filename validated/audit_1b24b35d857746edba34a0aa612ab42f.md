## Finding: Missing floor check on global resource weight accounting in TVM native contract path

The reported Solidity bug is about a subtraction (`currentTotalSupply - TARGET_TOTAL_SUPPLY`) that can silently go negative/underflow because no sanity check bounds it before the arithmetic. The equivalent risk pattern exists in java-tron's global staking-weight accounting: one implementation of `addTotalNetWeight`/`addTotalEnergyWeight` bounds the result at zero, but a second implementation used by the TVM native-contract path does not.

`DynamicPropertiesStore.addTotalNetWeight`/`addTotalEnergyWeight` (used by the plain, non-TVM actuators such as `FreezeBalanceActuator`/`UnfreezeBalanceActuator`) explicitly clamps the running total so it can never go below zero when `allowNewReward()` is active: [1](#0-0) 

However, `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight` — used by the TVM native-contract processors (`FreezeBalanceProcessor`, `UnfreezeBalanceProcessor`, `FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, `CancelAllUnfreezeV2Processor`) that are reachable via smart-contract calls to the freeze/unfreeze precompiles — performs the same accumulation with no floor check whatsoever: [2](#0-1) 

This asymmetry is exactly analogous to the reported bug class: one code path enforces "value must not go below zero" before it's used downstream, the other silently allows it, relying only on the (disabled-by-default) `assert` statement in `EnergyProcessor.calculateGlobalEnergyLimit`: [3](#0-2) 

Java `assert` statements are no-ops unless the JVM is started with `-ea`, so in a normal production node this assertion provides no real protection, and `totalEnergyWeight`/`totalNetWeight` can end up ≤ 0 or negative after the TVM path decrements it.

### Title
Global resource-weight (`TotalNetWeight`/`TotalEnergyWeight`) accounting lacks floor protection in TVM native-contract path - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.addTotalNetWeight` and `addTotalEnergyWeight`, used by TVM native contracts (freeze/unfreeze/cancel-unfreeze v1/v2), accumulate deltas into the chain-wide staking weight without ever clamping the result to zero, unlike the equivalent `DynamicPropertiesStore` methods used by the plain (non-TVM) actuators, which clamp with `max(0, ...)` when `allowNewReward()` is enabled.

### Finding Description
`DynamicPropertiesStore.addTotalNetWeight`/`addTotalEnergyWeight` treat the network-wide resource weight as an invariant that must never go negative, and defensively clamp it. `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight` — the sibling implementation invoked from TVM native contracts such as `UnfreezeBalanceProcessor`, `UnfreezeBalanceV2Processor`, and `CancelAllUnfreezeV2Processor` — apply the identical `+=` accumulation but omit the clamp entirely. The only remaining guard, `assert totalEnergyWeight > 0` in `EnergyProcessor.calculateGlobalEnergyLimit`, is compiled but not enforced at runtime because Java assertions are disabled by default. If any accounting discrepancy between per-account frozen-balance tracking and the aggregated global weight arises (e.g., mismatched weight deltas across the V1/V2 freeze/unfreeze/delegate/cancel-unfreeze code paths, all of which mutate this same counter from different entry points), the resulting `TotalNetWeight`/`TotalEnergyWeight` can go to zero or negative and stay there, since nothing corrects it back.

### Impact Explanation
`TotalEnergyWeight`/`TotalNetWeight` is the divisor in `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`, which determines every account's available bandwidth/energy from frozen TRX. A corrupted (zero/negative) value causes division by zero or a negative divisor, producing incorrect (potentially inflated or NaN-derived) energy/bandwidth limits for all accounts network-wide — a consensus-relevant resource-accounting corruption reachable purely through normal contract calls, not requiring any privileged actor.

### Likelihood Explanation
The two accounting entry points (`DynamicPropertiesStore` for plain actuators, `RepositoryImpl` for TVM native contracts) are maintained independently and diverge in this floor-clamp logic, which itself is evidence the two paths are not kept consistent by design. Any transaction that triggers the TVM native freeze/unfreeze/delegate/cancel-unfreeze contracts is unprivileged and broadcastable by any account, and the affected accumulation logic executes on every such call, giving many chances for it to reach an underflowed state.

### Recommendation
Add the same non-negative floor clamp used in `DynamicPropertiesStore.addTotalNetWeight`/`addTotalEnergyWeight` to `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight` (and `addTotalTronPowerWeight`), and replace the runtime-disabled `assert totalEnergyWeight > 0` in `EnergyProcessor`/`RepositoryImpl.calculateGlobalEnergyLimit` with an explicit check that logs/handles the zero-or-negative case safely instead of relying on Java assertions.

### Proof of Concept
Not applicable — reaching the underflow requires reproducing a subtle discrepancy between multiple concurrent freeze/unfreeze/delegate accounting paths across a live node's block history, which cannot be demonstrated from static code review alone. The finding is based on the direct code contrast between the two divergent implementations of the same accounting method shown above.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
