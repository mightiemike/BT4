### Title
Unbounded decimal `from_amount`/`to_amount` strings in shielded TRC-20 parameter creation enable BigInteger-parsing DoS - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.createShieldedContractParameters` and `Wallet.createShieldedContractParametersWithoutAsk` accept the untrusted, string-typed protobuf fields `from_amount` and `to_amount` and pass them straight into `getBigIntegerFromString`, which constructs a `BigInteger` from an attacker-controlled decimal string with no length or canonicalization check before any other validation occurs.

### Finding Description
`getBigIntegerFromString` simply trims the input and calls `new BigInteger(trimmedIn, 10)` with no bound on the string length: [1](#0-0) 

This is invoked unconditionally, before any semantic validation of the amounts, in both shielded TRC-20 parameter builders: [2](#0-1) [3](#0-2) 

`from_amount`/`to_amount` are declared as free-form `string` fields in the protobuf schema, so no protocol-level bound exists on their length: [4](#0-3) 

The HTTP entrypoint that reaches this code path is `CreateShieldedContractParametersServlet`, which is exposed unauthenticated (any caller that can reach the node's HTTP API), only performs a generic `Util.checkBodySize(contract)` on the whole request body and a feature-flag check (`checkAllowShieldedTransactionApi`), neither of which validates or bounds the length of the individual `from_amount`/`to_amount` numeric strings: [5](#0-4) [6](#0-5) 

Since the overall JSON body-size cap only limits total request size (not the size of any single field), an attacker can craft a request whose body is filled almost entirely with digits inside `from_amount`, up to the configured HTTP body size limit. `java.math.BigInteger`'s decimal string constructor performs quadratic-time work as the digit count grows, so a body filled with a very long numeric string forces disproportionate CPU consumption relative to the tiny amount of useful data conveyed, exactly mirroring the reported gnark verifier issue where oversized decimal public inputs cause expensive parsing before any real validation.

### Impact Explanation
This is a verifier/actuator-side availability issue: an unauthenticated or low-privilege caller can repeatedly send requests to `/wallet/createshieldedcontractparameters` (or the "without ask" variant) with an oversized `from_amount`/`to_amount` string, causing the node to spend disproportionate CPU/memory on `BigInteger` construction for every request, before the subsequent `checkBigIntegerRange` bit-length check (which happens only after parsing is already complete) has any chance to reject it. Repeated requests can degrade the node's HTTP API responsiveness, consistent with an underpriced/unbounded verifier-side-work DoS.

### Likelihood Explanation
High reachability: the servlet has no authentication, the feature is intended to be user-facing for shielded TRC-20 transfers (gated only by the node operator's `allowShieldedTransactionApi` flag, which is a feature toggle, not an access control), and the malformed string only needs to fit within the general HTTP body size cap that applies to all endpoints, not any amount-specific limit.

### Recommendation
Enforce a strict maximum digit length on `from_amount` and `to_amount` in `getBigIntegerFromString` (or at the point they are read from the request) before constructing the `BigInteger`, e.g., reject any string longer than the maximum decimal digits needed to represent a 256-bit value (as already implicitly required by `checkBigIntegerRange`'s 256-bit check). Perform this length check prior to calling `new BigInteger(...)` so oversized inputs fail fast without expensive parsing.

### Proof of Concept
1. Enable the shielded transaction API on a target node (`allowShieldedTransactionApi=true`).
2. Send an HTTP POST to `/wallet/createshieldedcontractparameters` with a JSON body where `from_amount` is a decimal string of hundreds of thousands of digits (padded to just under the server's HTTP body-size limit) and other required fields populated with minimally valid placeholder data.
3. Observe that `Wallet.createShieldedContractParameters` calls `getBigIntegerFromString(request.getFromAmount())`, which invokes `new BigInteger(trimmedIn, 10)` on the full oversized string, consuming CPU time proportional to the square of the digit count before the `checkBigIntegerRange` 256-bit check rejects it.
4. Repeating this request concurrently amplifies CPU load, degrading the node's HTTP API responsiveness for other users.

  private BigInteger getBigIntegerFromString(String in) {
    String trimmedIn = in.trim();
    if (trimmedIn.length() == 0) {
      return BigInteger.ZERO;
    }
    return new BigInteger(trimmedIn, 10);
  }
