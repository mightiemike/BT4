### Title
Unhandled `.unwrap()` panic in delayed-receipt shard-filtering during chunk apply causes a permanent, transaction-triggered chain halt - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `.unwrap()` on `Receipt::receiver_shard_id`, which can return `Err(EpochError::ShardingError(...))` for a `GlobalContractDistribution` receipt whose `target_shard` can no longer be resolved to a shard in the current layout (e.g., after multiple resharding events). Because this code runs inside `Runtime::apply` on every validator, an attacker who deploys a global contract shortly before a shard split — and whose resulting `GlobalContractDistribution` receipt is pushed into the delayed-receipt queue and survives across two resharding generations — can cause every honest node applying that chunk to panic when the delayed queue is eventually drained, halting chunk production for the affected shard(s) indefinitely (until manual intervention/rollback).

### Finding Description
- `Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437-466`) for `GlobalContractDistribution` receipts looks up `target_shard` in the current `ShardLayout`; if the shard no longer exists it calls `shard_layout.resolve_to_current_shard(target_shard)`, and if that also fails (no descendant found — e.g., the receipt is stale across more than one resharding generation, or the split-history chain can't map it) it returns `Err(EpochError::ShardingError(...))`.
- `DelayedReceiptQueueWrapper::receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`) calls this function and immediately `.unwrap()`s the result:
```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```
- This filter is invoked from `DelayedReceiptQueueWrapper::pop` (`runtime/runtime/src/congestion_control.rs:880-910`), which is called from `Runtime::process_delayed_receipts`/`process_receipts` (`runtime/runtime/src/lib.rs:2778-2825`) — i.e., on the hot path of every chunk apply (`Runtime::apply`, `runtime/runtime/src/lib.rs:1860`).
- A regression test in this very tree, `test_stale_global_contract_distribution_after_double_resharding` (`test-loop-tests/src/tests/global_contracts_distribution.rs:32-186`), documents exactly this scenario: an unprivileged account deploys a global contract on a shard that is force-split twice; the resulting `GlobalContractDistribution` receipt is kept in the delayed queue (by saturating compute) across both resharding events, and the test explicitly checks that draining the delayed queue afterward does not panic ("If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations").
- Because `Runtime::apply` is deterministic and runs identically on every validator/chunk-producer tracking that shard, a panic here does not just crash a single node — it crashes *every* node that must apply that chunk, which halts consensus/chunk production for the shard (a "transaction-triggered halt" in the terms of the report's Validate criteria).

### Impact Explanation
This is directly analogous to CVE-2024-56946 (Technitium DNS Server DoS): an unhandled exception in a processing loop (there: DNS-over-QUIC listener thread; here: the delayed-receipt draining loop inside chunk apply) permanently disables further processing once triggered. In nearcore's case the effect is worse than the DNS server case because `Runtime::apply` is the deterministic state-transition function run by every validator — a panic here reproduces on all nodes simultaneously and stops the chain (or the affected shard) from making further progress, a scenario the project treats as a critical liveness bug (see the existing dedicated regression test guarding it). This satisfies the report's acceptance criterion of a "transaction-triggered halt."

### Likelihood Explanation
Triggering requires: (1) an unprivileged account deploying a `GlobalContractDistribution`-producing action (`DeployGlobalContract`) whose receipt is delayed at the time of two subsequent resharding events affecting its target shard, and (2) enough compute saturation to keep the receipt in the delayed queue across both resharding boundaries — all of which are achievable by an ordinary account with modest funds using normal transactions/contract calls (no validator or protocol-level privilege needed), as demonstrated by the repository's own reproduction test. The main constraint is that dynamic resharding (multiple splits of the same lineage) must occur while the receipt is delayed, which narrows the window but is entirely attacker-triggerable via transaction timing/spam rather than requiring any network- or validator-level compromise.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (`?`) so that an unresolvable `target_shard` surfaces as a normal `RuntimeError`/`StorageError` (e.g., treated the same way other "inconsistent state" cases are handled elsewhere in this file, such as via `StorageError::StorageInconsistentState`) instead of panicking, and/or ensure `ShardLayout::resolve_to_current_shard` retains enough split-history depth to resolve receipts delayed across more than one resharding generation. Extend the existing `test_stale_global_contract_distribution_after_double_resharding` test to also cover a third resharding generation to confirm the fix generalizes, and audit other call sites of `Receipt::receiver_shard_id` for the same unwrap pattern.

### Proof of Concept
The repository's own test `test_stale_global_contract_distribution_after_double_resharding` (`test-loop-tests/src/tests/global_contracts_distribution.rs:32-186`) is a concrete PoC skeleton:
1. Deploy a test contract and then a global contract from an unprivileged account (`user0`) on a shard that is configured (via dynamic resharding force-split) to be split twice in sequence.
2. Saturate the shard's compute budget every block with ordinary `burn_gas_raw` calls so the `GlobalContractDistribution` receipt is pushed to, and stays in, the delayed-receipt queue through both resharding events.
3. Stop saturating and let the delayed queue drain; if `receiver_shard_id()`/`resolve_to_current_shard` cannot map the stale `target_shard` into the (twice-split) current layout, `receipt_filter_fn`'s `.unwrap()` panics during `Runtime::apply`, which the test detects via the chain head stalling short of the expected height (`head_height >= drain_end` assertion failing).

Note: I could not fully verify from static reading alone whether the current version of `resolve_to_current_shard` (`core/primitives/src/shard_layout/{mod.rs,v3.rs}`) already closes this gap for two resharding generations or only for one — the test's docstring ("after two resharding generations") suggests this is the specific edge the fix targets, but I was not able to inspect the full implementation of `resolve_to_current_shard` before running out of tool budget, so whether the panic is still reachable in this exact tree or has been fully closed by that function should be confirmed by a follow-up review of `core/primitives/src/shard_layout/v3.rs`.
