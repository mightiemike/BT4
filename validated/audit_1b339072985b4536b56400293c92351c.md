### Title
Token-name squatting/front-running DoS in `AssetIssueActuator` blocks legitimate TRC10 issuance — ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator` allows anyone to issue a TRC10 token by broadcasting an `AssetIssueContract` with a user-chosen `name`. When the network parameter `AllowSameTokenName` is disabled (`getAllowSameTokenName() == 0`), the actuator enforces global uniqueness of the token name via a classic check-then-set pattern split across `validate()` and `execute()`, which any unprivileged account can race to claim first.

### Finding Description
In `validate()`, the actuator checks whether the requested name is free: [1](#0-0) 
and only after that check passes does `execute()` write the record into `assetIssueStore`: [2](#0-1) 

Because both the name-existence check and the actual store write happen at transaction-processing time (not at broadcast time), any user can observe a pending `AssetIssueContract` transaction for a desired `name` in the mempool and broadcast their own `AssetIssueContract` with the identical `name` and a higher fee/priority so it gets packed into the block first. The legitimate issuer's transaction then fails validation with `"Token exists"`, exactly mirroring the Folks Finance `accountId`-squatting pattern where a unique user-chosen identifier is checked-then-committed with no reservation/commitment scheme to bind it to the original requester. The unit test `IssueSameTokenNameAssert` in `AssetIssueActuatorTest.java` confirms this exact revert behavior when a name has already been claimed: [3](#0-2) 

This is reachable from any anonymous, unprivileged account via a normal broadcast transaction (`AssetIssueContract`), requires no special role, and the attack can be repeated indefinitely against any desired token name.

### Impact Explanation
An attacker can grief any user attempting to issue a TRC10 token with a specific name by front-running their transaction with an identical name, permanently denying that name to the legitimate issuer (names are enforced unique for the lifetime of the chain when `AllowSameTokenName` is off). Since this is a network-wide parameter historically defaulted to closed on many past/private java-tron deployments (and is exactly the situation the `AllowSameTokenName` fork was introduced to remedy), the griefing surface is real for chains/testnets running with it disabled: unlike the Folks Finance bug, this requires the attacker to also pay `getAssetIssueFee()`, so it is griefing with a bounded cost, not a fully free DoS, and it only blocks a specific chosen name rather than "every account creation."

### Likelihood Explanation
Likelihood is moderate: it requires (1) the target network to have `AllowSameTokenName` disabled, and (2) the attacker to observe the victim's pending transaction and out-race it (mempool front-running / fee bidding), which is a well-understood and easily automated technique. On networks where `AllowSameTokenName` is enabled (the current mainnet default), this specific vector does not apply since the V1 uniqueness check is bypassed and only the V2 auto-incrementing `tokenIdNum` key is used.

### Recommendation
- Where `AllowSameTokenName` is disabled, consider a commit-reveal or reservation mechanism for token names, or bind name uniqueness enforcement to `(ownerAddress, name)` pairing with a pre-registration step, so a front-runner without the legitimate owner's context cannot squat a name.
- More practically, since `AllowSameTokenName` already exists as the sanctioned mitigation for this exact class of issue, ensure documentation/config guidance discourages disabling it, and evaluate deprecating the legacy `assetIssueStore` (V1) code path entirely to remove the racy uniqueness check.

### Proof of Concept
1. Victim broadcasts `AssetIssueContract` with `name = "GOODNAME"` while `AllowSameTokenName == 0`.
2. Attacker observes the pending transaction in the mempool, crafts an `AssetIssueContract` with the same `name = "GOODNAME"` and a higher fee, and broadcasts it.
3. The attacker's transaction gets included first; `execute()` writes `assetIssueCapsule` keyed by `"GOODNAME"` into `assetIssueStore`.
4. When the victim's transaction executes, `validate()`'s check at `AssetIssueActuator.java:210-214` finds the name already exists and reverts with `"Token exists"`, matching the `IssueSameTokenNameAssert` test behavior at `AssetIssueActuatorTest.java:1701-1731`, permanently denying the victim their desired token name.
