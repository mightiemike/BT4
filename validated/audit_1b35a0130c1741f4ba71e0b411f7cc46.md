### Title
Unbounded zk-proof generation loop in `ZenTransactionBuilder.build()` allows RPC-triggered CPU exhaustion before any spend/receive count limits are enforced - (File: framework/src/main/java/org/tron/core/zen/ZenTransactionBuilder.java)

### Summary
`ZenTransactionBuilder.build()` iterates over the `spends` and `receives` lists and invokes native zk-SNARK proof generation (`generateSpendProof`/`generateOutputProof`) for every entry with no upper-bound check before doing so [1](#0-0) . This code is reachable from the unauthenticated `CreateShieldedTransaction` HTTP endpoint via `wallet.createShieldedTransaction(...)` [2](#0-1) , meaning a client-supplied request can trigger arbitrarily many expensive native proof computations before any per-transaction spend/receive count cap is applied.

### Finding Description
The only enforcement of a spend/receive count limit (1 spend max, 2 receives max) lives in `ShieldedTransferActuator.checkSender()`/`checkReceiver()`, which run inside the actuator's `validate()` method [3](#0-2) . That validate/actuator path only executes when a fully-built transaction is later processed/broadcast through consensus/mempool logic — it is not invoked during transaction *construction*.

`ZenTransactionBuilder.build()`, however, is invoked earlier, directly from the client-facing `CreateShieldedTransactionServlet`/`wallet.createShieldedTransaction`, and performs proof generation for every entry in `spends`/`receives` with no size check whatsoever: [4](#0-3) 

Each iteration calls into `JLibrustzcash.librustzcashSaplingSpendProof`/`librustzcashSaplingOutputProof`, which are expensive native zk-SNARK proof-generation routines [5](#0-4) [6](#0-5) . Since this all happens before the transaction is ever submitted to the actuator or the network, none of the consensus-level count checks (`checkSender`, `checkReceiver`) or any fee/energy/bandwidth accounting apply. The `RateLimiterServlet` base class used by `CreateShieldedTransactionServlet` throttles request rate but does not bound the size/complexity of an individual request's payload, so a single request with a very large `spends`/`receives` payload passes any rate limiting and directly triggers the unbounded loop.

I was not able to fully verify the exact wire-format limits of the `PrivateParameters` gRPC/HTTP message consumed by `wallet.createShieldedTransaction` (i.e., whether its repeated note fields are structurally capped) — the relevant `Wallet.java` `createShieldedTransaction` method body was not retrievable in this analysis. This is a gap in verification: if `PrivateParameters` only allows a small fixed number of repeated entries by protobuf/business-logic construction before ever reaching `ZenTransactionBuilder`, the practical exploitability would be limited. However, the `ZenTransactionBuilder.build()` method itself — which is also called from other shielded-transaction builder helper paths — has no defensive cap, and the only cap that exists anywhere in the code is the actuator-level check that runs strictly *after* proof generation. This confirms the core defect: metering/limiting is not faithful (post-hoc, at actuator validate time) rather than being enforced before the expensive unmetered proof-generation work in the builder.

### Impact Explanation
If reachable with attacker-controlled cardinality (which requires confirming the `PrivateParameters` structure allows many repeated spend/output entries), this enables CPU exhaustion DoS on the full node's client-facing HTTP/RPC service — matching the "DoS via RPC-API" bounty class. The proof generation is entirely local/server-side CPU work performed synchronously within the servlet request handler, with no fee, energy, or bandwidth charged, since it occurs before consensus-level transaction execution/accounting.

### Likelihood Explanation
Preconditions: attacker needs no privileged role, funds, or signed transaction — just the ability to send an HTTP POST to `/wallet/createshieldedtransaction`. Cost to attacker is essentially zero (no fee is charged for constructing, only for broadcasting/executing a valid transaction). Feasibility depends on whether the `PrivateParameters` message actually permits an attacker to submit many spend/output note entries in one call; this could not be fully confirmed from the code retrieved. If confirmed, the attack is trivially repeatable and requires no special timing or race conditions.

### Recommendation
Add an explicit upper bound check on `spends.size()` and `receives.size()` at the very start of `ZenTransactionBuilder.build()` (mirroring or stricter than the actuator's `checkSender`/`checkReceiver` limits of 1 spend / 2 receives), rejecting the request before any native proof-generation work begins. Additionally, verify and, if necessary, restrict the `PrivateParameters`/related builder-populating RPC message schemas so they cannot carry an unbounded number of repeated note entries, and consider adding a request-body size/entry-count guard in `CreateShieldedTransactionServlet` and equivalent gRPC handlers.

  public SpendDescriptionCapsule generateSpendProof(SpendDescriptionInfo spend,
      long ctx) throws ZksnarkException {

    byte[] cm = spend.note.cm();

    // check if ak exists
    byte[] ak;
    byte[] nf;
    byte[] nsk;
    if (!ArrayUtils.isEmpty(spend.ak)) {
      ak = spend.ak;
      nf = spend.note.nullifier(ak, JLibrustzcash.librustzcashNskToNk(spend.nsk),
          spend.voucher.position());
      nsk = spend.nsk;
    } else {
      ak = spend.expsk.fullViewingKey().getAk();
      nf = spend.note.nullifier(spend.expsk.fullViewingKey(), spend.voucher.position());
      nsk = spend.expsk.getNsk();
    }

    if (ByteArray.isEmpty(cm) || ByteArray.isEmpty(nf)) {
      throw new ZksnarkException("Spend is invalid");
    }

    byte[] voucherPath = spend.voucher.path().encode();

    byte[] cv = new byte[32];
    byte[] rk = new byte[32];
    byte[] zkproof = new byte[192];
    if (!JLibrustzcash.librustzcashSaplingSpendProof(
        new SpendProofParams(ctx,
            ak,
            nsk,
            spend.note.getD().getData(),
            spend.note.getRcm(),
            spend.alpha,
            spend.note.getValue(),
            spend.anchor,
            voucherPath,
            cv,
            rk,
            zkproof))) {
      throw new ZksnarkException("Spend proof failed");
    }
    SpendDescriptionCapsule spendDescriptionCapsule = new SpendDescriptionCapsule();
    spendDescriptionCapsule.setValueCommitment(cv);
    spendDescriptionCapsule.setRk(rk);
    spendDescriptionCapsule.setZkproof(zkproof);
    spendDescriptionCapsule.setAnchor(spend.anchor);
    spendDescriptionCapsule.setNullifier(nf);
    return spendDescriptionCapsule;
  }

  public ReceiveDescriptionCapsule generateOutputProof(ReceiveDescriptionInfo output, long ctx)
      throws ZksnarkException {
    byte[] cm = output.getNote().cm();
    if (ByteArray.isEmpty(cm)) {
      throw new ZksnarkException("Output is invalid");
    }

    Optional<NotePlaintextEncryptionResult> res = output.getNote()
        .encrypt(output.getNote().getPkD());
    if (!res.isPresent()) {
      throw new ZksnarkException("Failed to encrypt note");
    }

    NotePlaintextEncryptionResult enc = res.get();
    NoteEncryption encryptor = enc.getNoteEncryption();

    byte[] cv = new byte[32];
    byte[] zkProof = new byte[192];
    if (!JLibrustzcash.librustzcashSaplingOutputProof(
        new OutputProofParams(ctx,
            encryptor.getEsk(),
            output.getNote().getD().getData(),
            output.getNote().getPkD(),
            output.getNote().getRcm(),
            output.getNote().getValue(),
            cv,
            zkProof))) {
      throw new ZksnarkException("Output proof failed");
    }

    if (ArrayUtils.isEmpty(output.ovk) || output.ovk.length != 32) {
      throw new ZksnarkException("ovk is null or invalid and ovk should be 32 bytes (256 bit)");
    }

    ReceiveDescriptionCapsule receiveDescriptionCapsule = new ReceiveDescriptionCapsule();
    receiveDescriptionCapsule.setValueCommitment(cv);
    receiveDescriptionCapsule.setNoteCommitment(cm);
    receiveDescriptionCapsule.setEpk(encryptor.getEpk());
    receiveDescriptionCapsule.setCEnc(enc.getEncCiphertext());
    receiveDescriptionCapsule.setZkproof(zkProof);

    OutgoingPlaintext outPlaintext =
        new OutgoingPlaintext(output.getNote().getPkD(), encryptor.getEsk());
    receiveDescriptionCapsule.setCOut(outPlaintext
        .encrypt(output.ovk, receiveDescriptionCapsule.getValueCommitment().toByteArray(),
            receiveDescriptionCapsule.getCm().toByteArray(),
            encryptor).getData());
    return receiveDescriptionCapsule;

  private void checkSender(ShieldedTransferContract shieldedTransferContract)
      throws ContractValidateException {
    if (!shieldedTransferContract.getTransparentFromAddress().isEmpty()
        && shieldedTransferContract.getSpendDescriptionCount() > 0) {
      throw new ContractValidateException("ShieldedTransferContract error, more than 1 senders");
    }
    if (shieldedTransferContract.getTransparentFromAddress().isEmpty()
        && shieldedTransferContract.getSpendDescriptionCount() == 0) {
      throw new ContractValidateException("ShieldedTransferContract error, no sender");
    }
    if (shieldedTransferContract.getSpendDescriptionCount() > 1) {
      throw new ContractValidateException("ShieldedTransferContract error, number of spend notes"
          + " should not be more than 1");
    }
  }

  private void checkReceiver(ShieldedTransferContract shieldedTransferContract)
      throws ContractValidateException {
    if (shieldedTransferContract.getReceiveDescriptionCount() == 0) {
      throw new ContractValidateException("ShieldedTransferContract error, no output cm");
    }
    if (shieldedTransferContract.getReceiveDescriptionCount() > 2) {
      throw new ContractValidateException("ShieldedTransferContract error, number of receivers"
          + " should not be more than 2");
    }
  }
