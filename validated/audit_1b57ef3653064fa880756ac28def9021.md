## Analysis

The reported Stader bug class is: **a shared "next-in-line" pointer/state is mutated unconditionally as a side effect of an attempted operation, even when that operation ultimately fails**, letting a low-cost attacker force the mutation to bias future outcomes in their favor.

An analogous pattern exists in `apollo_mempool`'s capacity-overflow eviction path, reachable from a plain unprivileged transaction submitted via the gateway.

### Title
Mempool eviction of other accounts' transactions is not rolled back when the triggering transaction is ultimately rejected - (File: `crates/apollo_mempool/src/mempool.rs`)

### Summary
When an incoming transaction would exceed mempool capacity, `handle_capacity_overflow` calls `try_make_space`, which evicts transactions from a **randomly chosen** gap account to free space [1](#0-0) . If the freed space is still insufficient to admit the incoming transaction, the function returns `Err(MempoolError::MempoolFull)` — but the eviction that already occurred is **not reverted** [2](#0-1) .

### Finding Description
`try_make_space` accumulates evicted transactions in `evicted_txs`, permanently removes them from `tx_pool`, and removes their references from `tx_queue`, then returns a boolean indicating whether *enough* space was freed [3](#0-2) . `handle_capacity_overflow` only checks this boolean to decide whether to accept the incoming transaction; on failure it simply returns `MempoolError::MempoolFull`, leaving the eviction side effect committed [4](#0-3) .

The victim account is chosen essentially at random from `accounts_with_gap`, not tied to the attacker's own transaction in any protective way [5](#0-4) . This is confirmed as intended (not test-only) behavior by an explicit regression test asserting the eviction persists "regardless of whether large_tx is accepted or rejected" [6](#0-5) .

This mirrors the Stader bug class precisely: the state-advancing action (here, eviction of a legitimate victim's queued transactions) happens unconditionally as a side effect of attempting an operation, independent of whether that top-level operation (here, admitting the attacker's transaction) actually succeeds.

### Impact Explanation
An unprivileged transaction sender can craft a transaction whose size guarantees it will not fit even after eviction (e.g., an oversized signature/calldata, cheap to construct and pay gateway-level fees for), causing `try_make_space` to evict another account's queued, already-validated transactions with zero probability of ever benefiting the attacker's own transaction. Because eviction target selection is essentially random among gap accounts, any account that happens to have a nonce gap is at risk of having its legitimate pending transactions purged from the mempool without recourse, causing delay/loss for honest users and degrading fair transaction admission — an unauthorized removal of another user's queued transaction/state, analogous to "gaming the system" described in the original finding.

### Likelihood Explanation
Triggering this requires only crafting and submitting a single oversized transaction through the standard gateway path once the mempool is near capacity (a state that occurs naturally under load and can also be induced by the same attacker via repeated submissions). No special privileges, node compromise, or multi-party coordination are required, and the flaw is deterministic/repeatable, not a one-off race condition.

### Recommendation
Reserve/simulate the eviction outcome before committing it: only apply the removals from `tx_pool`/`tx_queue` after confirming `total_space_freed >= required_space` (i.e., perform a dry-run selection of candidate accounts/bytes, and only mutate state once success is guaranteed), or otherwise roll back (re-insert) the evicted transactions if the final admission of the incoming transaction fails.

### Proof of Concept
This is directly demonstrated by the existing test `rejects_or_accepts_tx_based_on_freed_space` with `signature_size = 20` (`insufficient_eviction_space` case): the mempool is filled with `tx1`/`tx2` from address `0x1`; an oversized `large_tx` from `0x0` is submitted, is rejected with `MempoolError::MempoolFull`, yet `assert!(!mempool.tx_pool.contains_account(contract_address!("0x1")))` confirms `0x1`'s transactions were evicted anyway [6](#0-5) .

```rust
    pub fn get_evictable_account(&self) -> Option<ContractAddress> {
        let len = self.accounts_with_gap.len();
        if len == 0 {
            return None;
        }
        let random_index = thread_rng().gen_range(0..len);
        self.accounts_with_gap.get_index(random_index).copied()
    }

    // Attempts to make space for a new transaction by evicting existing transactions.
    // Returns true if enough space was freed, false otherwise.
    pub fn try_make_space(&mut self, required_space: u64) -> bool {
        let mut total_space_freed = 0;
        let mut evicted_txs = Vec::new();

        while total_space_freed < required_space {
            let Some(address) = self.get_evictable_account() else {
                break;
            };

            let txs: Vec<_> = self.tx_pool.account_txs_sorted_by_nonce(address).copied().collect();
            for tx_ref in txs.iter().rev() {
                let tx = self
                    .tx_pool
                    .remove(tx_ref.tx_hash)
                    .expect("Transaction must exist in the pool.");
                total_space_freed += tx.total_bytes();
                evicted_txs.push(*tx_ref);
                metric_count_evicted_txs(1);
                self.decrement_stuck_txs_if_gap_account(address, 1);
                if total_space_freed >= required_space {
                    break;
                }
            }

            // Clean up if account is now empty.
            if !self.tx_pool.contains_account(address) {
                self.accounts_with_gap.swap_remove(&address);
            }
        }

        // Keep the queue consistent with the pool: the evicted txs were removed from the pool, so
        // drop their (now-orphaned) queue references too. In fee mode gap accounts are never
        // queued, so this is a no-op there; in Echonet/FIFO mode they are, and skipping this leaves
        // a dangling reference that panics the next `get_txs`.
        self.tx_queue.remove_txs(&evicted_txs);

        total_space_freed >= required_space
    }
```

```rust
    fn handle_capacity_overflow(
        &mut self,
        tx: &InternalRpcTransaction,
        account_nonce: Nonce,
        freed_bytes: u64,
    ) -> Result<(), MempoolError> {
        let address = tx.contract_address();

        let account_has_gap = self.accounts_with_gap.contains(&address);
        let account_has_txs = self.tx_pool.contains_account(address);
        let closing_gap = tx.nonce() == account_nonce;
        let creating_gap = (account_has_gap || !account_has_txs) && !closing_gap;

        // Only the net growth must be evicted: an accompanying replacement removal frees
        // `freed_bytes` (0 when there is no replacement).
        let required_space = tx.total_bytes().saturating_sub(freed_bytes);
        if !creating_gap && self.try_make_space(required_space) {
            return Ok(());
        }

        Err(MempoolError::MempoolFull)
    }
```

```rust
#[rstest]
#[case::insufficient_eviction_space(20, false)]
#[case::sufficient_eviction_space(8, true)]
fn rejects_or_accepts_tx_based_on_freed_space(
    #[case] signature_size: usize,
    #[case] expect_success: bool,
) {
    let tx1 = add_tx_input!(tx_hash: 1, address: "0x1", tx_nonce: 1, account_nonce: 0);
    let tx2 = add_tx_input!(tx_hash: 2, address: "0x1", tx_nonce: 2, account_nonce: 0);

    let large_signature = vec![felt!("0x0"); signature_size];
    let large_tx = AddTransactionArgs {
        tx: internal_invoke_tx(invoke_tx_args!(
            tx_hash: tx_hash!(3),
            signature: TransactionSignature(large_signature.into())
        )),
        account_state: AccountState { address: contract_address!("0x0"), nonce: nonce!(0) },
    };

    let capacity = tx1.tx.total_bytes() + tx2.tx.total_bytes();
    let mut mempool = Mempool::new(
        MempoolConfig {
            static_config: MempoolStaticConfig {
                capacity_in_bytes: capacity,
                ..Default::default()
            },
            ..Default::default()
        },
        Arc::new(FakeClock::default()),
    );

    for tx in [&tx1, &tx2] {
        add_tx(&mut mempool, tx);
    }

    if expect_success {
        add_tx(&mut mempool, &large_tx);
        assert!(mempool.tx_pool.get_by_tx_hash(large_tx.tx.tx_hash()).is_ok());
    } else {
        add_tx_expect_error(&mut mempool, &large_tx, MempoolError::MempoolFull);
    }

    // Transactions tx1 and tx2 are evicted regardless of whether large_tx is accepted or rejected.
    // We do not revert the eviction attempt even if adding large_tx ultimately fails.
    assert!(!mempool.tx_pool.contains_account(contract_address!("0x1")));
}
```
