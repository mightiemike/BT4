### Title
TRC10 Exchange (bancor-like AMM) ignores token `precision` when creating/injecting/withdrawing/trading, causing incorrect exchange rates across tokens with different decimals - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java])

### Summary
The external report describes an oracle that computes USD value using raw amounts without normalizing for each token's decimals, silently assuming all tokens share 1e18 precision. Java-tron's TRC10 Exchange subsystem exhibits the same root-cause bug class: TRC10 tokens can be issued with different `precision` values (0–6, enforced in `AssetIssueActuator.validate()`), but every Exchange actuator (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) and the underlying bancor-formula processors (`ExchangeCapsule.transaction`, `ExchangeProcessor`, `SafeExchangeProcessor`) operate purely on raw `long` token quantities/balances with no reference to `precision` anywhere in that code path.

### Finding Description
`AssetIssueContract` defines a `precision` field (0–6) that determines how many "decimal" places a TRC10 token's raw integer amount represents [1](#0-0) . `AssetIssueActuator.validate()` enforces the precision range but otherwise never affects downstream math [2](#0-1) .

`ExchangeCreateActuator.execute()` creates a pool directly from `firstTokenBalance`/`secondTokenBalance` raw quantities supplied by the creator, with no lookup or use of either token's `precision` [3](#0-2) . A grep across all `Exchange*.java` actuator/capsule files confirms `precision` is referenced only in unrelated test files — it is never read by `ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`, `ExchangeCapsule`, `ExchangeProcessor`, or `SafeExchangeProcessor`.

`ExchangeCapsule.transaction()` runs the bancor-style relay-supply formula purely on raw `long` balances (`firstTokenBalance`, `secondTokenBalance`, `sellTokenQuant`) without any decimal normalization step [4](#0-3) . `ExchangeInjectActuator` and `ExchangeWithdrawActuator` likewise compute the proportional "other side" quantity as a straight ratio of raw balances (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`), again with no decimal adjustment [5](#0-4) [6](#0-5) .

This mirrors the OmoOracle bug: both systems treat heterogeneous-precision token amounts as if they were homogeneous, using raw integer quantities directly in price/ratio math. In java-tron's case, if the two TRC10 tokens paired in an Exchange pool have different `precision` values (e.g., token A precision=0, token B precision=6), the pool's raw-balance ratio does not represent the true economic exchange rate between the tokens — a "1 unit" of token A (raw integer 1) is treated as economically equivalent in the ratio math to "1 unit" of token B (raw integer 1, but representing 0.000001 of a human-readable token B), even though they represent vastly different real quantities.

### Impact Explanation
Any TRC10 exchange pool created between tokens with differing `precision` will price trades, injections, and withdrawals incorrectly relative to the tokens' real decimal-adjusted value. Because TRX itself is fixed at 6-decimal SUN precision but TRC10 tokens can be issued at precision 0 (i.e., "whole units" only) up through 6, an attacker/pool creator pairing a low-precision token against TRX or another asset can create severely mispriced pools, allowing extraction of value via inject/withdraw/exchange operations that don't reflect true worth — a concrete accounting/settlement impact (not merely theoretical), matching the High-impact classification of the original oracle bug.

### Likelihood Explanation
Likelihood is Medium: pool creation and TRC10 issuance (including choice of `precision`) are both unprivileged operations available to any account, and nothing in `ExchangeCreateActuator` or `AssetIssueActuator` prevents or warns against pairing tokens of differing precision. Exploitation requires deliberately issuing/pairing mismatched-precision tokens, which is straightforward for any user, but the resulting mispricing would primarily harm counterparties/liquidity in that specific pool rather than the entire network.

### Recommendation
When creating an Exchange pool (`ExchangeCreateActuator`) and when computing proportional quantities in `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeCapsule.transaction()`, normalize raw balances/quantities by each token's `precision` (looked up via `AssetIssueStore`/`AssetIssueV2Store`) before performing ratio or bancor-formula math, analogous to the recommended fix of scaling `amountToken` by `decimalsUSD/decimalsToken` in the oracle report.

### Proof of Concept
Conceptual scenario (not executed, no test harness access in this mode):
1. Issue TRC10 token A with `precision = 0` and TRC10 token B with `precision = 6` via `AssetIssueActuator`.
2. Call `ExchangeCreateActuator` to create a pool with `firstTokenBalance` = 1000 (token A) and `secondTokenBalance` = 1000 (token B raw units, i.e., 0.001 "real" token B) — the actuator accepts this without any precision check [3](#0-2) .
3. The pool now treats 1 unit of A as economically equal to 1 raw unit of B, though B's raw unit is 1e-6 of its display unit — a 1,000,000x mispricing.
4. Subsequent `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` calls compute swap/injection amounts using this mispriced raw-balance ratio [4](#0-3) , letting a counterparty extract value disproportionate to the tokens' real worth.
