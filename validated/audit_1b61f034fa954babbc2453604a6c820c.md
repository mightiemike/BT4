This is a real, code-acknowledged gap: `ensure_match_transaction_info` in `types/src/transaction/mod.rs` verifies transaction status, gas used, write-set hash (against `state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against locally-recomputed values — a limitation the code's own comment flags.

### Title
Replay-verify's `ensure_match_transaction_info` skips checkpoint-hash validation, allowing a divergent state root to pass verification - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the authenticity gate used by replay/verification tooling (`db-tool`'s `replay_on_archive`, `aptos-debugger`, and CLI commands) to confirm that a locally re-executed `TransactionOutput` matches the trusted, previously-persisted `TransactionInfo`. It checks status, gas used, write-set hash, and event root hash, but the function's own trailing comment states it deliberately skips validating the state/hot-state checkpoint hashes and the `position_state_checkpoint_hash` [2](#0-1) .

### Finding Description
The comparator is meant to be the final integrity check that a re-executed transaction's committed state matches the authenticated on-chain `TransactionInfo`. However, it only asserts equality on:
- `status` vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `write_set_hash` (state_change_hash) vs. `txn_info.state_change_hash()`
- `event_root_hash` vs. `txn_info.event_root_hash()` [3](#0-2) 

It never compares `txn_info.state_checkpoint_hash()`, any hot-state checkpoint hash, or `txn_info.position_state_checkpoint_hash()` against values independently recomputed during replay. This is confirmed by the in-code TODO: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [2](#0-1) .

By contrast, the online executor path (`DoStateCheckpoint::get_state_checkpoint_hashes`) does perform this comparison when `known_state_checkpoints` are supplied, ensuring computed checkpoint roots match expected ones during block execution/chunk-executor sync [4](#0-3) . This means the gap is confined to the standalone replay/verification tooling path (`replay_on_archive`, `aptos-debugger`, `cli/src/commands.rs`) that calls `ensure_match_transaction_info` directly rather than going through the full chunk-executor commit pipeline.

### Impact Explanation
If a JMT root, hot-state root, or the newer native-position state root computed during offline replay diverges from what is actually recorded/committed on-chain (e.g. due to a state-computation bug, storage corruption, or an intentionally crafted malicious archive/backup being replayed), `ensure_match_transaction_info` will still report success as long as the write-set bytes, events, gas, and status match. This defeats the purpose of "replay-verify" as an integrity check for state commitment/proof binding, and could mask a hard-fork-class state divergence bug rather than surfacing it, which matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category.

### Likelihood Explanation
This is not an attacker-triggerable state corruption by itself — the check is a verification-tool gap, not a mainnet consensus bug. Its likelihood of causing real harm depends on it being relied upon as the sole verification for detecting position/hot-state root divergence in ecosystem tooling. Since the code comment itself describes this exact scenario as a live limitation ("can report a successful replay even when the authenticated position state root diverges from local execution"), the code path is real and reachable, but the severity is bounded to whatever operational role `replay_on_archive`/`aptos-debugger` play in real chain-consistency assurance — I was not able to fully verify (within available iterations) whether any other check compensates for this in the actual `replay_on_archive` control flow (e.g. whether it separately calls into the full `DoStateCheckpoint` path that already does validate hashes). This is a factor I could not conclusively rule out or confirm.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality between locally recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` and the corresponding fields on the trusted `txn_info`, at least whenever `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or the hot-state feature) is enabled, so that replay-verify tooling cannot silently pass over an authenticated-root mismatch.

### Proof of Concept
Not independently reproduced as a live exploit — this is a code-review-confirmed logic gap (backed by the author's own TODO), not a demonstrated on-chain state corruption. Conceptually: run offline replay of a version range where the executor's independently-recomputed position/hot-state checkpoint root differs from the persisted `TransactionInfo`'s checkpoint hash (while write-set bytes/events/gas/status still match); `ensure_match_transaction_info` returns `Ok(())` despite the root mismatch.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
