Based on my investigation, I found a strong analog to the LSP0 truncation bug in Chainlink's Vault capability's owner-label derivation.

### Title
Silent truncation/coercion of the `owner` identifier into an Ethereum address label allows secret label/identity mismatch across non-canonical owner strings - ([File: core/capabilities/vault/vaultutils/labels.go])

### Summary
`WorkflowOwnerToLabel` in `core/capabilities/vault/vaultutils/labels.go` builds the 32-byte TDH2 encryption label used to bind a vault secret to its owner by calling `common.HexToAddress(owner)` and copying the resulting 20-byte value into a 32-byte buffer, exactly the "trim bytes32→bytes20 without documenting/enforcing canonical format" pattern described in the LSP0 report. `common.HexToAddress` (go-ethereum) is lenient: it silently right-aligns/pads or truncates any input into a fixed 20-byte address rather than rejecting non-canonical values, and the caller-side `owner` string used for this derivation is not validated to be a canonical 40-hex-character address before being passed through this conversion.

### Finding Description
The label used to cryptographically bind a TDH2-encrypted vault secret to a specific owner is computed as: [1](#0-0) 

and is checked for equality in `EnsureRightLabelOnSecret`: [2](#0-1) 

The `owner` string that reaches this function originates from user-supplied request fields (`SecretIdentifier.Owner`) and, separately, from JWT/allowlist-derived owner strings (see `DeriveJWTAuthorizedVaultWorkflowOwner`): [3](#0-2) 

The request-level validator (`ValidateSecretIdentifier`) only checks the owner string for alphanumeric characters and a length bound — it does **not** require it to be a canonical `0x`-prefixed 20-byte hex address: [4](#0-3) 

Because `common.HexToAddress` silently coerces malformed/non-canonical hex strings (e.g., missing `0x` prefix, wrong length, mixed/odd-length hex) into a fixed 20-byte address instead of erroring, two textually distinct `owner` strings can be silently mapped to the same (or an unexpected) 20-byte address and therefore the same 32-byte label — mirroring the LSP0 issue where the spec never documented that a 32-byte value gets truncated to 20 bytes before being used as a lookup/binding key, causing implementations that don't replicate the exact truncation semantics to disagree on identity.

### Impact Explanation
If two owner-identifier strings that a downstream consumer (e.g., a non-reference client, a different SDK, or a workflow author manually constructing a request) considers distinct are silently coerced by `HexToAddress` to the same 20-byte address/label, secrets encrypted under one owner representation could pass the `EnsureRightLabelOnSecret` check for another representation of "the same" owner, undermining the vault's owner-based isolation guarantee (secret disclosure / cross-tenant data boundary). This is a genuine trust-boundary concern because vault owner labels are the sole cryptographic binding used to prevent one owner's secrets from being usable/decryptable under another owner's authorization context.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: the existing test suite (`validator_test.go`, `plugin_test.go`) shows the label-matching logic is exercised extensively for canonical addresses, and most legitimate owner values observed in the codebase (`0x...40-hex-chars`) are canonical Ethereum addresses generated internally (e.g., via `crypto.PubkeyToAddress` or `GenerateWorkflowOwnerAddress`), reducing the chance that two internally-generated owners collide. However, the request-side `owner` field accepted from JSON-RPC input is only checked with `isValidIDComponent` (alphanumeric) and a length bound, not with a strict address-format check, so a request could pass validation with an owner string that is not a well-formed address, and `HexToAddress`'s lenient parsing means such malformed values do not error out — they are silently reinterpreted, which is the same "undocumented trimming" root cause flagged in the external report.

### Recommendation
- Enforce that `owner` is a canonical `0x`-prefixed, 40-hex-character Ethereum address string in `ValidateSecretIdentifier` (and any other path accepting `owner`), rejecting all non-canonical inputs, rather than relying on `common.HexToAddress`'s lenient/truncating parsing.
- Document explicitly (in code comments and any protocol/API documentation) that `WorkflowOwnerToLabel`/`EncryptSecretWithWorkflowOwner` truncate/right-align input into a 20-byte address before use as a label, so integrators and non-reference client implementers replicate the exact semantics.
- Consider using `common.IsHexAddress` (as already done in gateway validation, e.g. `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`) to strictly validate the owner string prior to calling `HexToAddress` anywhere it is used to derive a security-relevant label.

### Proof of Concept
Not independently executed; the analysis is derived from static code review of:
- `core/capabilities/vault/vaultutils/labels.go` (`WorkflowOwnerToLabel`)
- `core/capabilities/vault/validator.go` (`ValidateSecretIdentifier`, `EnsureRightLabelOnSecret`)

A concrete PoC would need to demonstrate two distinct `owner` input strings that `common.HexToAddress` maps to the same `common.Address` (e.g., an oversized or malformed hex string that truncates to the same 20 bytes as a legitimate address) and show that `ValidateSecretIdentifier` accepts both while `EnsureRightLabelOnSecret` treats them as equivalent — this would require running the Go `go-ethereum` `HexToAddress`/`FromHex` logic directly, which I could not execute in this read-only analysis. This should be verified in a live/dev environment before treating it as confirmed exploitable.

```go
// WorkflowOwnerToLabel converts a workflow owner string to a 32-byte TDH2 ciphertext
// label using the Ethereum address encoding: 12 zero bytes followed by the 20-byte address.
// This matches the label format used when secrets are encrypted for a vault workflow owner,
// including JWT-derived workflow owners.
func WorkflowOwnerToLabel(owner string) [32]byte {
	var label [32]byte
	addr := common.HexToAddress(owner)
	copy(label[12:], addr.Bytes())
	return label
}
```

```go
// EnsureRightLabelOnSecret verifies that the TDH2 ciphertext label matches the workflow
// owner label (Ethereum address, left-padded to 32 bytes). owner must be non-empty;
// when the public key is nil, verification is skipped for the same reasons as
// verifyEncryptedSecret.
func EnsureRightLabelOnSecret(publicKey *tdh2easy.PublicKey, secret string, owner string) error {
	cipherText, err := verifyEncryptedSecret(publicKey, secret)
	if err != nil {
		return err
	}
	if cipherText == nil {
		return nil
	}
	if owner == "" {
		return errors.New("owner must not be empty for secret label verification")
	}

	expected := vaultutils.WorkflowOwnerToLabel(owner)
	secretLabel := cipherText.Label()
	if secretLabel == expected {
		return nil
	}

	return fmt.Errorf("secret label [%s] does not match workflow owner label [%s]",
		hex.EncodeToString(secretLabel[:]), hex.EncodeToString(expected[:]))
}
```

```go
func DeriveJWTAuthorizedVaultWorkflowOwner(orgID string, tenantID uint64, claimedWorkflowOwnerFromJWT string) (string, error) {
	if orgID == "" {
		return "", errors.New("org_id is required for JWT-derived vault workflow owner")
	}
	if tenantID == 0 {
		return "", ErrMissingTenantID
	}
	prefix := strconv.FormatUint(tenantID, 10)
	addr, err := workflows.GenerateWorkflowOwnerAddress(prefix, orgID)
	if err != nil {
		return "", fmt.Errorf("could not derive vault workflow owner address: %w", err)
	}
	derived := common.BytesToAddress(addr).Hex()
	if claimedWorkflowOwnerFromJWT != "" && !strings.EqualFold(strings.TrimSpace(claimedWorkflowOwnerFromJWT), derived) {
		return "", fmt.Errorf("JWT workflow_owner claim %q does not match derived workflow owner %q", claimedWorkflowOwnerFromJWT, derived)
	}
	return derived, nil
}
```
