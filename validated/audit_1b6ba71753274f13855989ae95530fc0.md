### Title
Deterministic accounts have no owner escape-hatch, permanently freezing NEAR deposited to a deterministic account whose bound global contract lacks a withdrawal path - (File: runtime/runtime/src/deterministic_account_id.rs, runtime/runtime/src/actions.rs)

### Summary
NEAR's `DeterministicStateInitAction` creates accounts whose code and initial state are pinned to an immutable `GlobalContractIdentifier` and whose `actor_id` permanently remains the predecessor account rather than the deterministic account itself. As a direct consequence, `AddKey`, `DeployContract`, `DeleteAccount`, and other owner-only actions can never be executed on a deterministic account by anyone, ever. This removes the "escape hatch" that every other NEAR account type has (adding a full-access key to bypass broken/incomplete contract logic and reclaim funds). If the global contract bound to a deterministic account never exposes a method that transfers or refunds its own balance, any NEAR deposited into that account (the amount required to satisfy storage staking, or any amount sent via a prior `Transfer`) is frozen in the account forever, with no possible unstaking/withdrawal path — mirroring the reported smart-contract bug class ("deposit accepted, no withdraw mechanism, funds locked forever"), but at the protocol level and without even the theoretical option of an admin fix, since no key can ever be attached to the account.

### Finding Description
`action_deterministic_state_init` creates the account via `create_deterministic_account`, whose doc comment makes the invariant explicit: [1](#0-0) 

Because `actor_id` is not changed to the deterministic account, `check_actor_permissions` in `runtime/runtime/src/actions.rs` will reject `AddKey`, `DeployContract`, `DeleteKey`, `DeployGlobalContract`, `UseGlobalContract`, `WithdrawFromGasKey`, and `DeleteAccount` for that account forever, since `actor_id != account_id` can never become false for it: [2](#0-1) 

`check_account_existence` further confirms `DeterministicStateInit`/`UniversalStateInit` are the only actions with special-cased existence handling — there is no path that ever grants the deterministic account itself the authority to add a key: [3](#0-2) 

The deposit-settlement logic only refunds the portion of the attached deposit that exceeds the storage-staking requirement; the amount needed to satisfy storage staking is permanently added to the account's balance and is controlled entirely by the bound global contract's WASM logic from then on: [4](#0-3) 

Global contracts referenced by `CodeHash` are explicitly immutable once deployed (per `docs/RuntimeSpec/Actions.md`), so if the deployer never implemented a withdraw/transfer-out method in that WASM, there is no future upgrade path either: [5](#0-4) 

Any unprivileged transaction signer/RPC caller can trigger this end-to-end sequence themselves: submit `DeployGlobalContractAction` with arbitrary WASM lacking any balance-transfer export, then submit `DeterministicStateInitAction` (or a prior `Transfer`) targeting the derived deterministic account id, depositing NEAR that satisfies storage staking.

### Impact Explanation
The frozen amount is exactly the storage-staking-required balance (and any additional NEAR sent to the account via `Transfer` before/after init) — this constitutes concrete, permanently frozen user funds with no possible recovery mechanism (no key can ever be added, no `DeleteAccount` refund path, no contract upgrade for `CodeHash`-mode global contracts). This satisfies the "permanently frozen funds" impact bucket and is reachable purely through normal, permissionless transaction submission by a single account — no validator, network, or operator privilege required.

### Likelihood Explanation
Likelihood is bounded by the fact that this requires either (a) a user to deliberately reference/deploy a global contract without withdrawal logic and then initialize a deterministic account on it, or (b) a user mistakenly sending funds to a deterministic account address whose bound contract has no exit path. Because the protocol permanently forecloses the standard "add a full-access key to bail out a broken contract" recovery available to every other NEAR account type, any contract author error or malicious global-contract deployer turns this into an unrecoverable, protocol-enforced freeze rather than a contract-level oversight that the account owner could patch around.

### Recommendation
Consider whether deterministic accounts should retain some minimal, protocol-level recovery mechanism (e.g., allowing the account itself, once some `data`-defined "owner" is proven, to add a key, or supporting an unstake/withdraw-style system action independent of the bound contract's exports) so that funds sent to a deterministic account are not unconditionally frozen when the underlying global contract omits balance-transfer logic. At minimum, this permanent-lock risk and the removal of the usual "owner can always regain control via a full access key" guarantee should be called out prominently in the NEP-616 / `DeterministicStateInitAction` documentation so wallets and dApps can warn users before transferring funds to such accounts.

### Proof of Concept
1. Submit `DeployGlobalContractAction { code: <wasm with no exported withdraw/transfer method>, deploy_mode: CodeHash }` from any account — this is a normal, unprivileged transaction (see `runtime/runtime/src/global_contracts.rs::action_deploy_global_contract`).
2. Derive the deterministic account id from a `DeterministicAccountStateInit::V1 { code: CodeHash(hash_of_above), data: {...} }`.
3. Submit a `DeterministicStateInitAction` (with `deposit` covering storage staking) targeting the derived account id — `action_deterministic_state_init` creates the account and settles the deposit, refunding only the excess above the storage-staking requirement (`runtime/runtime/src/deterministic_account_id.rs:57-115`).
4. Attempt `AddKey`, `DeployContract`, or `DeleteAccount` on the deterministic account from any signer, including the original depositor: all are rejected by `check_actor_permissions` because `actor_id` (the predecessor) never equals the deterministic `account_id` (`runtime/runtime/src/actions.rs:760-801`).
5. Because the bound global contract exposes no method to move its own balance, the storage-staking-required NEAR balance on the account is permanently unreachable — confirmable by observing the account's `amount` remains static across any subsequent transaction attempts, with every attempted recovery action failing with `ActorNoPermission`.

pub(crate) fn settle_state_init_deposit(
    account: &mut Account,
    deposit: Balance,
    account_id: &AccountId,
    receipt: &Receipt,
    config: &RuntimeConfig,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // Use attached deposit to satisfy storage staking requirements and refund
    // the rest.
    let deposit_refund = match check_storage_stake(account, account.amount(), config) {
        Ok(_) => {
            // no additional storage needed, refunding all
            deposit
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(missing_amount)) => {
            if missing_amount <= deposit {
                // use exactly as much as needed and refund the rest
                let new_balance = safe_add_balance(account.amount(), missing_amount)?;
                account.set_amount(new_balance);
                deposit.checked_sub(missing_amount).expect("just checked missing_amount <= deposit")
            } else {
                result.result = Err(ActionErrorKind::LackBalanceForState {
                    account_id: account_id.clone(),
                    amount: missing_amount,
                }
                .into());
                return Ok(());
            }
        }
        Err(StorageStakingError::StorageError(err)) => {
            return Err(RuntimeError::StorageError(StorageError::StorageInconsistentState(err)));
        }
    };

    if deposit_refund > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund));
    }

    Ok(())
}

pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}
