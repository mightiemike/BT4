### Title
Integer overflow in CALLDATACOPY bounds check bypasses array copy limit - ([File: actuator/src/main/java/org/tron/core/vm/program/invoke/ProgramInvokeImpl.java])

### Summary
The `CALLDATACOPY` opcode handler in java-tron's TVM implementation performs a bounds check using plain 32-bit `int` addition (`offset + length`) that can silently overflow, exactly mirroring the root-cause pattern described in the Vyper `slice()` report (`assert(le(add(start, length), src_len))` performed without overflow protection).

### Finding Description
`callDataCopyAction` in `actuator/src/main/java/org/tron/core/vm/OperationActions.java` pops `memOffset`, `dataOffset`, and `length` from the stack and calls `program.getDataCopy(dataOffsetData, lengthData)`: [1](#0-0) 

This delegates to `ProgramInvokeImpl.getDataCopy`: [2](#0-1) 

Here `offset` and `length` are derived via `DataWord.intValueSafe()`, which clamps any value that doesn't fit cleanly in 4 bytes (or whose top bit is set) to `Integer.MAX_VALUE`: [3](#0-2) 

The bounds check `if (offset + length > msgData.length)` is done with plain `int` arithmetic (no `long` promotion). If `offset` and `length` are both large enough that their sum exceeds `Integer.MAX_VALUE`, the addition wraps to a negative number, which is never `> msgData.length`, bypassing the truncation logic — the exact overflow-bypasses-assert pattern described in the report's root cause (`vyper/builtins/functions.py:348`).

By contrast, the analogous `RETURNDATACOPY` bounds check in `Program.java` was written correctly with an explicit `(long)` cast to avoid this exact class of bug, confirming the CALLDATACOPY path is the outlier: [4](#0-3) 

### Impact Explanation
If the overflow check is bypassed, `System.arraycopy(msgData, offset, data, 0, length)` is invoked with an oversized `length` relative to `msgData`, which would throw an uncaught `ArrayIndexOutOfBoundsException` inside contract execution — a denial-of-service against the node processing the transaction/contract call. In addition, `byte[] data = new byte[length]` is executed unconditionally before the bounds check, and `length` can be attacker-controlled up to `Integer.MAX_VALUE` (~2GB), which is itself a resource-exhaustion risk for the node executing the contract if not fully offset by energy metering.

### Likelihood Explanation
This code path is reachable by any smart-contract call containing the `CALLDATACOPY` (`0x37`) opcode with attacker-controlled stack values for offset/length, i.e., from an ordinary, unprivileged broadcast transaction invoking a contract. However, exploitability is constrained by TVM energy metering: copying/allocating buffers of the size needed to trigger the overflow (`offset` and `length` both close to `Integer.MAX_VALUE`) would incur extremely large memory-expansion energy costs, which in most cases would exceed the transaction's energy limit and cause an `OutOfEnergyException` before the vulnerable code executes. I was unable to fully verify (within available search budget) whether the `CALLDATACOPY` energy cost function bounds this scenario using safe (`BigInteger`) arithmetic in all configurations, so likelihood should be treated as uncertain/medium rather than confirmed-high.

### Recommendation
Change the bounds check in `ProgramInvokeImpl.getDataCopy` (and any other call-data/code-copy helper using the same pattern) to use `long` arithmetic, e.g. `if ((long) offset + (long) length > msgData.length)`, consistent with the fix already applied in `Program.getReturnDataBufferData`. Additionally, validate `length` against a sane upper bound before allocating `new byte[length]` to avoid unconditional large allocations regardless of the overflow outcome.

### Proof of Concept
Not independently verified with a live testnet PoC (would require confirming actual energy-cost bypass), but the code-level trigger is: invoke `CALLDATACOPY` with a `length` stack value crafted (via `intValueSafe()` clamping) to be exactly `Integer.MAX_VALUE`, and a small nonzero `offset` such that `offset + length` overflows `int` to a negative value, causing `getDataCopy` to skip the truncation branch and pass the full (oversized) `length` to `System.arraycopy`, which will throw `ArrayIndexOutOfBoundsException` given `msgData` is far smaller than `length`.

```java
  public byte[] getDataCopy(DataWord offsetData, DataWord lengthData) {

    int offset = offsetData.intValueSafe();
    int length = lengthData.intValueSafe();

    byte[] data = new byte[length];

    if (msgData == null) {
      return data;
    }
    if (offset > msgData.length) {
      return data;
    }
    if (offset + length > msgData.length) {
      length = msgData.length - offset;
    }

    System.arraycopy(msgData, offset, data, 0, length);

    return data;
  }
```

```java
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
```
