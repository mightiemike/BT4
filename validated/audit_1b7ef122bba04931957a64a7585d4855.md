### Title
OIDC pre-authentication endpoints registered via `ExtendRouter` inherit the permissive "Authenticated" rate limiter instead of the strict "Unauthenticated" limiter applied to `/sessions` - ([File: core/web/router.go])

### Summary
`NewRouter` applies the `Authenticated` rate-limit tier (`rl.AuthenticatedPeriod()`, `rl.Authenticated()`) to the top-level `api` group, and `app.AuthenticationProvider().ExtendRouter(api)` is mounted directly on that same `api` group. `sessionRoutes`, by contrast, wraps the unauthenticated `POST /sessions` login endpoint in a dedicated `unauth` sub-group using the stricter `Unauthenticated` rate-limit tier. Because OIDC's `ExtendRouter` implementation registers pre-auth endpoints (`/oidc-login`, `/oidc-exchange`) directly on `api` without its own equivalent rate-limiting group, these endpoints get the more permissive authenticated-tier rate limit rather than the strict unauthenticated-tier limit meant for pre-auth/credential-related endpoints.

### Finding Description
In `core/web/router.go`, the `api` router group is created with the authenticated rate limiter applied globally: [1](#0-0) 

`sessionRoutes` deliberately creates a nested group with the *unauthenticated* (typically stricter/lower) rate limit specifically for `POST /sessions`, the login/credential-check endpoint: [2](#0-1) 

`ExtendRouter` is invoked directly on the top-level `api` group with no additional rate-limit wrapping: [3](#0-2) 

The OIDC provider implementation registers `GET /oidc-enabled`, `GET /oidc-login`, and `POST /oidc-exchange` directly on the `api` group it is handed, with no auth middleware (since these are necessarily pre-authentication endpoints) and no additional rate-limiter group: [4](#0-3) 

Since `/oidc-exchange` is functionally analogous to `/sessions` (it accepts credentials/tokens and issues a session on success), it should logically be protected the same way `POST /sessions` is — via the stricter `Unauthenticated` rate-limit tier — to defend against credential-stuffing/brute-force. Instead it only inherits whatever rate limiter is applied to the general `api` group (the `Authenticated` tier), which is designed for legitimate, already-throttled traffic from authenticated users and is typically configured to allow a much higher request volume. This creates an inconsistency: the invariant that "every route surface exposed by an AuthenticationProvider must inherit equivalent security middleware as native session routes" is violated for the OIDC provider's pre-auth exchange endpoint.

### Impact Explanation
This does not bypass authentication outright — OIDC token exchange still requires a valid OIDC provider token/callback to succeed. The impact is rate-limit amplification: an attacker can send far more requests to `/oidc-exchange` (or the OIDC login initiation flow) per unit time than they could to `/sessions`, because it is rate-limited by the more permissive `Authenticated` tier config instead of the stricter `Unauthenticated` tier config. This matches the described "brute-force amplification bypassing WebServer.RateLimit.Unauthenticated" scoped impact, applicable specifically when the node is configured with `OIDCAuth` (this is a supported/default-available authentication provider, not misconfiguration). Note: this affects only deployments actively using `OIDCAuth`; `LDAPAuth`'s `ExtendRouter` is a no-op and adds no routes, so it is not affected.

### Likelihood Explanation
The precondition is simply that `WebServer.Auth.Type = "oidc"` be configured, which is a documented, supported deployment mode, not an operator misconfiguration. Any unauthenticated network client can send unlimited-appearing requests to `/oidc-exchange` up to the higher authenticated-tier threshold, repeatably, since it is a structural router-wiring issue rather than a one-off state.

### Recommendation
Wrap the routes registered by `AuthenticationProvider.ExtendRouter` (or at minimum the OIDC pre-auth endpoints `/oidc-login` and `/oidc-exchange`) in a router sub-group that applies the same `Unauthenticated` rate-limit tier used for `POST /sessions`, e.g. by passing an `unauth`-style group (with `rateLimiter(rl.UnauthenticatedPeriod(), rl.Unauthenticated())`) into `ExtendRouter` instead of the bare `api` group, or by having each `ExtendRouter` implementation apply its own equivalent rate-limit middleware to pre-auth endpoints.

### Proof of Concept
Integration test analogous to `TestSessions_RateLimited` (`core/web/router_test.go:127`):
1. Configure `WebServer.Auth.Type = "oidc"` with a minimal/mock OIDC config so `oidcAuthenticator.ExtendRouter` registers `/oidc-exchange`.
2. Set `WebServer.RateLimit.Unauthenticated = 5` / `UnauthenticatedPeriod = 20s` and `WebServer.RateLimit.Authenticated` to a much higher value (defaults).
3. Send 6+ unauthenticated `POST /oidc-exchange` requests with invalid/malformed exchange payloads within the 20s window.
4. Assert: unlike `POST /sessions` which returns `429` on the 6th request, `/oidc-exchange` does NOT return `429` until the much higher `Authenticated` threshold is exceeded — demonstrating the inherited rate-limit tier mismatch.

```go
func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
```
