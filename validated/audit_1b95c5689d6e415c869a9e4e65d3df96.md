### Title
Superfluous `attached_deposit` in `WalletContract::rlp_execute` is silently forfeited instead of being validated or refunded - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`WalletContract::rlp_execute` is a `#[payable]` entrypoint callable by any unprivileged caller (owner, relayer, or third party) that accepts an attached NEAR deposit (the "msg.value" analog) together with an RLP-encoded Ethereum transaction describing the actual Near action to perform. [1](#0-0)  The amount of value actually moved by the decoded action is computed exclusively from the `tx.value` field embedded inside the RLP payload (converted via `additional_value`/`yocto_near`), never from the attached NEAR deposit itself. [2](#0-1)  The attached deposit is only tracked opportunistically through `CallerDeposit`, and solely for the purpose of refunding it if the resulting cross-contract promise fails. [3](#0-2)  There is no check analogous to DODO's `require(msg.value == amount)` / `require(msg.value == 0)` guarding against a caller attaching a deposit that the decoded action does not need or use.

### Finding Description
`inner_rlp_execute` builds an `ExecutionContext` directly from `env::attached_deposit()` and immediately wraps it in an optional `CallerDeposit`, which is only populated when the caller is not the wallet's own account and the deposit is non-zero. [4](#0-3)  This `caller_deposit` is threaded through to `rlp_execute_callback`, `address_check_callback`, and `nep_141_storage_balance_callback`. [5](#0-4) 

In `rlp_execute_callback`, the refund logic is only triggered when the spawned promise fails:
```
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        // refund
    }
    ...
}
PromiseResult::Successful(value) => {
    ExecuteResponse { success: true, success_value: Some(value), error: None }
}
``` [6](#0-5) 

On the success path, `caller_deposit` is simply dropped — regardless of whether the decoded action actually needed or consumed any deposit at all. Meanwhile, the value that is actually transferred by the decoded Near action (`Transfer`/`FunctionCall`) is derived purely from the ETH-emulated `tx.value` field and the in-line `yocto_near`, completely independent of the attached NEAR deposit:
```
Action::Transfer { receiver_id: _, yocto_near } => {
    let action = TransferAction {
        deposit: NearToken::from_yoctonear(
            additional_value.saturating_add(yocto_near.into()),
        ),
    };
    ...
}
``` [7](#0-6) 
For `AddKey`/`DeleteKey` actions, `Action::value()` is hard-coded to zero, meaning any deposit is entirely irrelevant to those actions:
```
Action::AddKey { .. } => NearToken::from_yoctonear(0),
Action::DeleteKey { .. } => NearToken::from_yoctonear(0),
``` [8](#0-7) 

This is directly analogous to the DODO `_deposit()` bug: the contract never validates that `attached_deposit` (msg.value) is zero when the action doesn't need it, nor that it matches the value the action is actually going to move. Just as DODORouteProxy silently swallows a mistakenly-attached `msg.value` in the non-ETH branch, `WalletContract::rlp_execute` silently swallows an attached NEAR deposit whenever:
- the decoded action is `AddKey` or `DeleteKey` (value is always zero, so any deposit is pure "misattached" funds), or
- the decoded action succeeds and the caller mistakenly believed the attached deposit would fund the transfer amount (it does not — only the RLP-embedded `tx.value`/`yocto_near` do), or
- the underlying promise is a self-transfer (`SelfBaseTokenTransfer`) or any other action where the deposit plays no functional role in the executed action.

In all of these cases, on success the deposit is retained forever by the wallet contract's account balance with no mechanism for the caller to reclaim it, since `caller_deposit` is discarded unconditionally in the `Successful` branch.

### Impact Explanation
Any unprivileged caller (a relayer or third party calling `rlp_execute` on behalf of, or targeting, someone else's eth-implicit wallet) who attaches a NEAR deposit to a call whose decoded action does not use it (e.g., `AddKey`, `DeleteKey`, or any action where they mistakenly assume the deposit funds the transfer) permanently and irreversibly loses those funds to the target wallet's account. This is a concrete, unauthorized-value-movement / loss-of-funds bug reachable from a single submitted transaction with no privileged role required, matching the accepted impact categories (permanently frozen/lost funds due to unauthorized value transfer away from the depositor without their intended semantics being honored).

### Likelihood Explanation
Likelihood is moderate: it requires a caller (often a relayer, which is explicitly an untrusted, external, unprivileged party in this design per the contract's own documentation about "faulty relayers") to attach a NEAR deposit to a `rlp_execute` call for an action that doesn't consume it. Given relayers are paid via `tx_fee`/refunds computed separately from the attached deposit, and the deposit and RLP-embedded value are two independent, easily-confused quantities, mis-attachment is a realistic operational mistake, not merely a theoretical edge case, and the sanity tests in the repo (`test_caller_refunds`, `test_base_token_transfer_with_relayer_refund`) demonstrate the contract already treats attached deposits as generally forfeitable on success. [9](#0-8) 

### Recommendation
Add an explicit invariant in `inner_rlp_execute`/`rlp_execute_callback` that rejects (or fully refunds) any non-zero `attached_deposit` from an external caller whenever the decoded action's `value()` is zero (i.e., `AddKey`, `DeleteKey`, `SelfBaseTokenTransfer`, or any action that does not itself require the deposit to complete). Concretely:
- Before creating the promise, if `caller_deposit.is_some()` and `action.value().is_zero()`, either `require`-reject the call (mirroring `require(msg.value == 0, ...)` in DODO) or unconditionally schedule a refund transfer back to `predecessor_account_id`.
- In `rlp_execute_callback`, refund `caller_deposit` on both the `Successful` and `Failed` branches whenever the action did not itself require that deposit, instead of only refunding on failure.

### Proof of Concept
1. Relayer (any unprivileged account, not the wallet owner) calls `rlp_execute(target, tx_bytes_b64)` on some user's eth-implicit `WalletContract`, attaching e.g. 5 NEAR as the payable deposit.
2. The RLP-encoded transaction decodes to an `AddKey` (or `DeleteKey`) action — see `parse_tx_data`'s `ADD_KEY_SELECTOR`/`DELETE_KEY_SELECTOR` branches, which are classified `SelfNearNativeAction` and whose `Action::value()` is hard-coded to zero. [10](#0-9) 
3. `inner_rlp_execute` builds `CallerDeposit` from the 5 NEAR attached deposit, dispatches the `AddKey`/`DeleteKey` promise (which uses zero deposit), and on success calls `rlp_execute_callback`. [11](#0-10) 
4. `rlp_execute_callback` receives `PromiseResult::Successful` and returns success without ever inspecting or refunding `caller_deposit`. [6](#0-5) 
5. The 5 NEAR the relayer attached remains permanently in the target wallet's account balance; the relayer has no way to recover it, mirroring the DODO `_deposit()` "useless `msg.value` not checked" loss-of-funds pattern.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
