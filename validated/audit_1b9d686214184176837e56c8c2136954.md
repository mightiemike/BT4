### Title
OAuth Callback HMAC Validation Uses a Different Parameter Parsing (Last-Wins) Than the Token-Exchange/Session Logic (First-Wins), Enabling HTTP Parameter Pollution of `shop`/`code` - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
In the OAuth callback handler, the query string is parsed twice with two different duplicate-key semantics: once via `URLSearchParams.get()` (first occurrence wins) to determine the actual `shop`/`code` used for the token exchange and session creation, and once via `Object.fromEntries(query.entries())` (last occurrence wins) to build the object that is HMAC-validated. An attacker who controls only the very first duplicate occurrence of `shop` or `code` in the query string can make the app use an unverified value for business logic while the HMAC check validates a different, legitimately-signed value — mirroring the zcashd/Zebra bug class where the same encoded input is parsed two different ways in two components, and the security check only sees one interpretation.

### Finding Description
`callback()` in [1](#0-0)  parses the incoming request URL into a `URLSearchParams` object and extracts `shop` via `.get('shop')`, which returns the **first** occurrence of a repeated key per the WHATWG URL spec.

The same `query` object is then converted with `Object.fromEntries(query.entries())` to build `authQuery` [2](#0-1) , which is passed to `validateHmac(config)(query)` for HMAC verification. Because plain-object property assignment overwrites on duplicate keys, `Object.fromEntries` keeps the **last** occurrence of a repeated key — the opposite selection rule from `.get()`.

Inside `validateHmac`, `normalizeQuery` only re-derives duplicate-key semantics when the input is a raw `URLSearchParams` instance or contains array values [3](#0-2) ; because `authQuery` is already a flattened plain object (produced by `Object.fromEntries`), it is passed through unchanged and the HMAC is computed and checked purely against the **last**-duplicate values [4](#0-3) .

Meanwhile, the code that actually performs the security-sensitive action uses the **first**-duplicate values from the raw `URLSearchParams`:
- `cleanShop = sanitizeShop(config)(query.get('shop')!, true)!` — used to build the token-exchange URL and as `session.shop` [5](#0-4) 
- `code: query.get('code')` — sent to Shopify's `/admin/oauth/access_token` endpoint [6](#0-5) 

So a request with duplicated `shop=`/`code=` query parameters is HMAC-validated against the last pair while the app's actual token exchange and resulting `Session` are built from the first pair. This is the same root-cause pattern as the analog report: the byte range that is validated for authenticity is not the same byte range that is subsequently interpreted and acted on.

### Impact Explanation
If exploitable end-to-end, this would let an attacker who has legitimately obtained a Shopify-signed OAuth callback URL for a shop they control (`shop`/`code`/`hmac`/`state` all valid for that shop) repackage it with a duplicated `shop` and/or `code` parameter: keeping the value used by the HMAC check (the last occurrence) equal to their own legitimately-signed value so validation passes, while placing an arbitrary, unverified value as the first occurrence, which is what actually gets used to select the token-exchange endpoint (`cleanShop`) and to populate the stored `session.shop`. This undermines the core integrity guarantee of the HMAC check — that the `shop`/`code` values acted upon are exactly the values Shopify signed. The practical severity of this specific pattern in shopify-app-js depends on whether Shopify's `/admin/oauth/access_token` endpoint independently rejects a code redeemed against a mismatched shop subdomain (which would abort the flow before a session is stored), analogous to how the underlying zcashd/Zebra report itself was rated "Medium" specifically because its practical trigger is narrow.

### Likelihood Explanation
Reaching this code path only requires an unprivileged, single external HTTP request to the app's OAuth callback route; no privileged access or secrets are needed, satisfying the "unpriv actor / single request" constraint. The one gating factor for full exploitation is Shopify's own code/shop-binding enforcement on the token endpoint, which is outside this repository's control and could not be verified here.

### Recommendation
Normalize the query exactly once, using a single, well-defined duplicate-key policy, and use that same normalized object for both HMAC validation and all subsequent business logic (`shop` selection, `code` extraction, session creation). Concretely: in `callback()`, derive `shop` and `code` from the same `authQuery` object (or an explicitly-normalized structure) that is passed into `validateHmac`, rather than re-reading from the raw `URLSearchParams` via `.get()`. Additionally, `validateHmac`/`normalizeQuery` should reject (rather than silently normalize) any occurrence of `shop`, `code`, `state`, or `timestamp` appearing more than once in the OAuth query, mirroring the existing `APP_PROXY_SINGLE_VALUE_PARAMS` duplicate-rejection logic already applied to the app-proxy signator path.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, completing OAuth `begin()` to receive a Shopify-issued callback redirect: `.../auth/callback?code=CODE1&host=H&shop=attacker-shop.myshopify.com&state=S&timestamp=T&hmac=VALIDHMAC`.
2. Attacker crafts: `.../auth/callback?shop=victim-shop.myshopify.com&code=CODE1&host=H&shop=attacker-shop.myshopify.com&state=S&timestamp=T&hmac=VALIDHMAC` (duplicated `shop`, first = victim, last = attacker's original value).
3. `validateHmac` computes/validates against `authQuery` built by `Object.fromEntries`, which retains `shop=attacker-shop.myshopify.com` (last) — HMAC check passes.
4. `cleanShop = sanitizeShop(query.get('shop'))` resolves to `victim-shop.myshopify.com` (first occurrence) and is used for the token-exchange POST and `session.shop`, diverging from the value that was actually HMAC-verified.

export function validateHmac(config: ConfigInterface) {
  return async (
    query: HmacQuery,
    {signator}: {signator: HMACSignator} = {signator: 'admin'},
  ): Promise<boolean> => {
    const normalizedQuery = normalizeQuery(query, signator);

    if (signator === 'admin' && !normalizedQuery.hmac) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain an HMAC value.',
      );
    }

    if (signator === 'appProxy' && !normalizedQuery.signature) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain a signature value.',
      );
    }

    validateHmacTimestamp(normalizedQuery);

    const hmac =
      signator === 'appProxy'
        ? normalizedQuery.signature
        : normalizedQuery.hmac;
    const localHmac = await generateLocalHmac(config)(
      normalizedQuery,
      signator,
    );

    return safeCompare(hmac as string, localHmac);
  };
}

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }
