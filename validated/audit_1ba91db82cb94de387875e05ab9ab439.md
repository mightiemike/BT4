Confirmed: this is a real, precise analog of the ENS bug class — "the code path that's supposed to perform a permission-affecting refresh takes a shortcut that skips the security-critical validation the other path performs."

### Title
Token-exchange re-authentication strategy skips scope-change validation, reusing stale-permission sessions - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts`)

### Summary
`AuthCodeFlowStrategy.authenticate` treats a session as valid only if `session.isActive(config.scopes)` [1](#0-0) , which passes the app's currently configured scopes into `Session.isScopeChanged` so a scope downgrade/change forces re-authorization. `TokenExchangeStrategy.authenticate`, the alternate/"managed installation" code path for the exact same responsibility, instead calls `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` [2](#0-1) , explicitly passing `undefined` for the scopes argument.

### Finding Description
`Session.isActive` computes validity as `!isScopeChanged && hasAccessToken && !isExpired` and `isScopeChanged` short-circuits to `false` (i.e., "no change, still valid") whenever `scopes` is `undefined` [3](#0-2) . This is exactly the "renew via the wrong function" pattern from the ENS report: two code paths exist for the same operation (deciding whether an existing session/permission grant can keep being used, or must be re-issued), one of them performs the authorization-critical check (`auth-code-flow.ts` passes `config.scopes`), the other silently bypasses it (`token-exchange.ts` passes `undefined`). The `shopify-app-react-router` package has the identical bypass in its own `token-exchange.ts` strategy [4](#0-3) .

Because `isScopeChanged` returns `false` whenever the argument is `undefined`, an existing stored session is always considered "still has the right scopes" under this strategy, regardless of what scopes the merchant has actually granted or what scopes the app currently requires. This mirrors the ENS `ETHRegistrarController.renew` bug: the intended permission-refresh logic (`_setData`/fuse update, here: forcing re-exchange when scopes are stale) exists in the codebase but is not reached from this call path.

### Impact Explanation
If a merchant reduces the scopes granted to the app (or the app's required `config.scopes` changes) after a session was stored, the auth-code-flow path will detect the mismatch and force re-authorization to obtain a token with the current scope set. The token-exchange path will not — it keeps using/serving the previously stored session/access token without validating that its scope actually matches what's required, because the scope check is disabled at the call site. This can result in the app continuing to operate as if a wider or different permission grant is still in effect, and — per the app's own logic that assumes `authenticate.admin` enforces scope currency — could allow API calls to proceed with stale entitlements. As in the ENS finding, this is a workaround-able/medium-severity permission-consistency defect (the underlying access token from Shopify's platform still governs actual API authorization), not a full authentication bypass, since Shopify's admin API will independently reject calls outside the token's real granted scope.

### Likelihood Explanation
Reachable by any embedded app installation using the recommended "Shopify managed installation + token exchange" strategy (the one Shopify's own docs recommend for embedded apps [5](#0-4) ), triggered by an ordinary single-merchant scope change — no privileged actor, secret leak, or MITM required. It occurs on every request handled by `authenticate.admin` under this strategy, since the check runs unconditionally at line 56 of `token-exchange.ts`.

### Recommendation
Pass the configured scopes into the `isActive` check in both `TokenExchangeStrategy.authenticate` implementations, matching `AuthCodeFlowStrategy`:
```ts
!session.isActive(config.scopes, WITHIN_MILLISECONDS_OF_EXPIRY)
```
so a scope mismatch forces a fresh token exchange, the same way it forces a fresh OAuth redirect in the auth-code-flow strategy.

### Proof of Concept
1. Configure an embedded app with `future.unstable_newEmbeddedAuthStrategy` (token exchange) enabled and `scopes: ['read_orders']`.
2. Merchant installs the app; an offline session is stored with `scope: 'read_orders'`.
3. App's required scopes are later changed/reduced (e.g., to `scopes: ['read_orders','write_customers']` or the merchant's actual grant changes) so the stored session's `scope` no longer matches `config.scopes`.
4. A subsequent request goes through `TokenExchangeStrategy.authenticate`: `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` returns `true` purely because the token isn't expired — the scope mismatch is never evaluated (`isScopeChanged` short-circuits on `undefined`) [6](#0-5) .
5. Compare with the same scenario under `AuthCodeFlowStrategy.authenticate`, which calls `session.isActive(config.scopes)` and correctly redirects to re-authorize when scopes differ [7](#0-6) , as covered by the existing test `'redirects to auth if the session is no longer valid for non-embedded apps when at the top level'` [8](#0-7)  — no equivalent scope-mismatch-triggers-reauth test exists for the token-exchange strategy.

  public isActive(
    scopes: AuthScopes | string | string[] | undefined,
    withinMillisecondsOfExpiry = 500,
  ): boolean {
    const hasAccessToken = Boolean(this.accessToken);
    const isTokenNotExpired = !this.isExpired(withinMillisecondsOfExpiry);
    const isScopeChanged = this.isScopeChanged(scopes);
    return !isScopeChanged && hasAccessToken && isTokenNotExpired;
  }

  /**
   * Whether the access token includes the given scopes if they are provided.
   */
  public isScopeChanged(
    scopes: AuthScopes | string | string[] | undefined,
  ): boolean {
    if (typeof scopes === 'undefined') {
      return false;
    }

    return !this.isScopeIncluded(scopes);
  }
