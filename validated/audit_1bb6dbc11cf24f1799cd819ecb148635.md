### Title
Unhandled `ReceiptValidationError` on incoming cross-shard receipts causes validator/RPC-node panic (chunk-application halt) - (File: `chain/chain/src/runtime/mod.rs`)

### Summary
`Runtime::process_incoming_receipts` treats any incoming (cross-shard) receipt that fails `validate_receipt` as a hard, unrecoverable `RuntimeError::ReceiptValidationError`, which is then converted to a Rust `panic!` in the chunk-apply error handler. This mirrors the Aedes bug class (CWE-755, improper handling of an exceptional condition while processing an inbound message) but manifests as a full node/chunk-producer panic rather than a benign error return.

### Finding Description
`Runtime::apply` processes three receipt streams: local, delayed, and incoming. For the delayed-receipt queue, a `validate_receipt` failure is deliberately downgraded to a `StorageError::StorageInconsistentState`, which is a recoverable, catchable error type [2](#0-1) . For the incoming-receipt path, however, the same kind of validation failure is mapped straight to `RuntimeError::ReceiptValidationError` and propagated with `?` [1](#0-0) .

At the call site in `chain/chain/src/runtime/mod.rs`, the top-level `apply_result` error handler explicitly converts `RuntimeError::ReceiptValidationError` into a `panic!`, annotated with `// TODO(#2152): process gracefully` — an acknowledged-but-unfixed gap [3](#0-2) . `RuntimeError::UnexpectedIntegerOverflow` is handled the same way immediately above it.

Because incoming receipts originate as outgoing receipts from *another shard's* execution (which can itself be produced by an ordinary, unprivileged `FunctionCall` action creating a promise/receipt), the question is whether an attacker-controlled contract call can produce a receipt that passes the sending shard's `NewReceipt`-mode validation (checked once, at creation time, per `runtime/runtime/src/verifier.rs:687-696` and `runtime/runtime/src/lib.rs:871`) but later fails the destination shard's `ExistingReceipt`-mode re-validation. The protocol's own comments acknowledge such a divergence exists: `ValidateReceiptMode::ExistingReceipt` documentation states it must "tolerate some receipts that wouldn't pass new validation" because "there is a bug which allows creating receipts above the size limit" (referencing near/nearcore#12606) [4](#0-3) . The existing regression test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs` demonstrates precisely this scenario — a receipt that passes creation-time size validation but is oversized once `output_data_receivers` are appended — and the test comment states the runtime "shouldn't die" when this happens [5](#0-4) . That test only currently exercises the local/receiving-shard code path where the oversized receipt is caught during creation-time re-validation inside `apply_action_receipt`, not the direct `process_incoming_receipts` path that hard-panics.

### Impact Explanation
If an attacker-controlled receipt (from a signed transaction or a contract's promise chain) can be shaped so that it passes validation on the sending shard but fails `validate_receipt` when re-checked as an *incoming* receipt on the receiving shard, `RuntimeError::ReceiptValidationError` is returned from `Runtime::apply` and the node panics in `apply_chunk` (`chain/chain/src/runtime/mod.rs:372`). Because chunk application happens identically and deterministically on every validator tracking that shard, this single crafted receipt would crash every honest validator/RPC node processing that chunk simultaneously — a transaction-triggered chain halt, which is one of the explicitly accepted high-severity impacts (chain halt caused by a single submitted transaction/receipt).

### Likelihood Explanation
Likelihood depends on whether a validation-relevant field can actually diverge between `NewReceipt` creation-time checks and `ExistingReceipt` incoming-time checks for cross-shard (not just same-shard) receipts — this is the part not fully confirmed from static review alone. The code's own documentation for `ValidateReceiptMode` explicitly states that such known divergences exist (`ExistingReceipt` must tolerate receipts that fail `NewReceipt` checks, referencing a known unresolved receipt-size bug, near/nearcore#12606) [4](#0-3) , and the panic-on-error `TODO(#2152)` in the chunk-apply handler shows the nearcore team is already aware this path is reachable and unresolved [3](#0-2) . This makes the bug class credible and reachable in principle from an unprivileged contract call producing a cross-shard receipt, though confirming a concrete field/size divergence that only manifests on the *incoming* (not local) path would require deeper tracing of `Receipt::from_action_receipt`/`ReceiptSink::forward_or_buffer_receipt` construction versus `validate_receipt`'s checks, which was not fully exhaustively verified here.

### Recommendation
- Do not `panic!` on `RuntimeError::ReceiptValidationError` in `chain/chain/src/runtime/mod.rs`; instead treat it as a recoverable/inconsistent-state condition analogous to the delayed-receipt path (`StorageError::StorageInconsistentState`) or as an explicit "reject chunk" error that doesn't crash the process.
- Align `process_incoming_receipts`'s error handling with `process_delayed_receipts`: wrap `validate_receipt` failures the same way for both queues so no receipt processing path can trigger a raw `panic!`.
- Close out TODO(#2152) by auditing all receipt-validation invariants so `NewReceipt` and `ExistingReceipt` validation cannot diverge for any field influenced by attacker-supplied contract logic (e.g., receipt/data size growth after creation-time checks, as tracked in near/nearcore#12606).

### Proof of Concept
Not independently reproduced in this review — confirming exploitability requires constructing a contract-driven receipt (e.g., via `promise_return`/output-data-receiver growth, similar to the `test_max_receipt_size_promise_return` test pattern) that is delivered as an *incoming* cross-shard receipt to a different shard than the one that created it, and demonstrating that `validate_receipt(..., ExistingReceipt)` fails only on the receiving side, triggering the panic at `chain/chain/src/runtime/mod.rs:372`. The existing test `test_max_receipt_size_promise_return` (`test-loop-tests/src/tests/max_receipt_size.rs:130-208`) is the closest available fixture and should be adapted to force cross-shard delivery of the oversized receipt rather than same-shard/local delivery.
