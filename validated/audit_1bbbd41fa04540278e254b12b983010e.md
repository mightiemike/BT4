### Title
Gas key balances are permanently burned instead of refunded to the beneficiary on `DeleteAccount` - ([File: runtime/runtime/src/actions.rs])

### Summary
When an account owning one or more gas keys (NEP-536/`GasKeys` protocol feature) is deleted via `DeleteAccountAction`, the account's main `amount` is refunded to the `beneficiary_id`, but any balance held inside the account's gas keys is deliberately burned rather than transferred to the beneficiary or made withdrawable beforehand. This mirrors the report's bug class: value that a user has legitimately funded/earned (here, pre-paid gas-key balance, analogous to accrued lender interest) has no path to be recovered by the user or moved to their designated beneficiary, resulting in permanent loss of funds.

### Finding Description
`action_delete_account` in [1](#0-0)  computes `gas_key_balance_to_burn` via `compute_gas_key_balance_sum(state_update, account_id)` and, after refunding only the plain account `amount` to the beneficiary with `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`, adds the entire gas-key balance sum to `result.tokens_burnt` instead of including it in the beneficiary refund. The account (and its gas keys) is then removed with `remove_account`.

This is confirmed by the design doc, which explicitly documents the behavior: [2](#0-1)  states `DeleteAccount` "Refunds remaining balance to beneficiary, burns gas-key balances, removes the account."

The `WithdrawFromGasKeyAction` mechanism exists specifically to let a signer move funds *out* of a gas key back into the account's spendable `amount` before deletion [3](#0-2) , but nothing in `action_delete_account` requires or enforces that gas keys be drained first — a user (or an application driving a single `DeleteAccount` action, e.g. a batch transaction, or a relayer/gas-key manager acting on the owner's stale state) can trigger deletion while gas keys still hold funded balance, and that balance is unconditionally burned.

Similarly, funds actively in flight to a gas key are also non-recoverable: gas refunds attempt to credit a gas key's balance via `try_refund_gas_key_balance` [4](#0-3) , and `action_transfer_or_implicit_account_creation` routes system gas refunds preferentially into the gas key balance [5](#0-4) . If the account is deleted in the same or a subsequent chunk before the owner withdraws, those refunded tokens are burned along with the rest of the gas key balance, with no possibility of recovery — analogous to the Blueberry report's "earned rewards become permanently locked" scenario, except here it is outright destroyed (burnt) rather than merely stuck.

### Impact Explanation
This causes concrete, transaction-triggered permanent loss of user funds: NEAR tokens that a user deposited into a gas key (via `TransferToGasKeyAction`, itself a normal user-signed transaction action [6](#0-5) ) or that were credited to it as a gas refund are irrecoverably destroyed the moment `DeleteAccount` executes, instead of being returned to the account owner/beneficiary. This is a direct "permanently frozen/destroyed funds" outcome reachable by a single unprivileged transaction signer (the account owner or anyone with `DeleteAccount` permission on the account), matching the class of "invalid state transition acceptance" / "permanently frozen funds" outlined in the validation criteria. Severity is High: it is a straightforward, deterministic loss of principal (not merely APY), triggerable by any account holder who forgets (or is tricked/relayed into) deleting an account while a gas key retains balance, or by a relayer-managed workflow that issues `DeleteAccount` without first draining gas keys.

### Likelihood Explanation
Likelihood is non-trivial but not universal: gas keys (`GasKeys` protocol feature, PV 85) are a newer mechanism primarily used by relayers/meta-transaction flows to pre-fund gas payment separately from the main account balance. Any account using this pattern that is later deleted (e.g., cleanup, migration, or an application-driven "close account" flow) without first calling `WithdrawFromGasKeyAction` to drain the gas key will hit this path. Since `DeleteAccount` does not check for or forbid nonzero gas-key balances (it only rejects if the burn amount exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`, i.e., large balances are blocked but smaller ones are silently burned), this is easy to trigger accidentally and is intentional protocol behavior rather than a rare edge case.

### Recommendation
Modify `action_delete_account` to include the summed gas-key balances in the beneficiary refund (extending `Receipt::new_balance_refund` amount by `gas_key_balance_to_burn`, or requiring gas keys be pre-drained) instead of unconditionally moving them to `tokens_burnt`. If burning is intentional design (e.g., to simplify storage cleanup/accounting), this should be clearly surfaced to users/tooling (e.g., wallets should force `WithdrawFromGasKey` before allowing `DeleteAccount`), and ideally the protocol should reject `DeleteAccount` when nonzero gas-key balance exists, the same way it already limits deletion when storage usage is too large (`DeleteAccountWithLargeState`).

### Proof of Concept
1. Create account `A` with some NEAR balance.
2. `A` adds a gas key via `AddKeyAction` with `AccessKey::gas_key_full_access(...)`.
3. `A` funds the gas key with `TransferToGasKeyAction { public_key, deposit }` for a nontrivial deposit (test setup mirrors `test_gas_key_refund` at [7](#0-6) ).
4. `A` submits a `DeleteAccountAction { beneficiary_id: B }` without first withdrawing from the gas key.
5. Observe: `action_delete_account` computes `gas_key_balance_to_burn` (the funded gas-key deposit) and adds it to `result.tokens_burnt` [1](#0-0) ; only `account.amount()` is sent to `B` via `Receipt::new_balance_refund`. The gas-key deposit is gone forever — not received by `A`, `B`, or any withdrawal action, since `A`'s account (and its access keys) no longer exists after `remove_account`.

**Note on verification limits:** I was not able to inspect `compute_gas_key_balance_sum` or `GasKeyInfo::MAX_BALANCE_TO_BURN`'s exact threshold value within this session, nor the full `remove_account` implementation, due to iteration limits. These would be useful for a background agent to confirm the exact burn threshold and whether any upstream caller (e.g., wallet/relayer tooling in this repo) already guards against this scenario before finalizing a fix.

/// Tries to refund gas to a gas key's balance.
/// Returns true if the key exists and is a gas key (balance was credited).
/// Returns false otherwise (key not found or is not a gas key).
pub(crate) fn try_refund_gas_key_balance(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    public_key: &PublicKey,
    deposit: Balance,
) -> Result<bool, StorageError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, public_key)? else {
        return Ok(false);
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        return Ok(false);
    };
    gas_key_info.balance = gas_key_info.balance.checked_add(deposit).ok_or_else(|| {
        StorageError::StorageInconsistentState("gas key balance integer overflow".to_string())
    })?;
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);
    Ok(true)
}

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
}
