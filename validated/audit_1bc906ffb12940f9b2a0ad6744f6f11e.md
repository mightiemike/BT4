Based on my investigation, I found a valid analog in the bucket map's index vs. data bucket grow paths.

### Title
Data bucket grow path fails to transfer `delete_file_on_drop` restart ownership, unlike the index grow path - (File: `bucket_map/src/bucket.rs`)

### Summary
`Bucket::apply_grow_index` explicitly transfers "delete-on-drop" ownership from the old `BucketStorage` to the new one when a restart file is being tracked, but the parallel `Bucket::apply_grow_data` function — which is invoked from the exact same `handle_delayed_grows` dispatch point — omits this step entirely. This mirrors the reported bug class: one code path (`createMarket`/`apply_grow_index`) performs a required setup step while the sibling path (`setPrincipal`/`apply_grow_data`) that should perform the same class of work does not.

### Finding Description
`BucketStorage<O>` has a `delete_file_on_drop: bool` field, and its `Drop` impl deletes the backing mmap file from disk if that flag is set: [1](#0-0) 

When the index bucket grows, `apply_grow_index` correctly juggles this flag: it marks the *old* index storage for deletion and clears the flag on the *new* index storage (so the new file survives future restarts): [2](#0-1) 

However, `apply_grow_data`, which is the equivalent function for data buckets, does no such thing. It simply overwrites `self.data[ix] = bucket` (or pushes newly created buckets via `add_data_bucket`) without ever inspecting or setting `delete_file_on_drop` on either the old or new `BucketStorage<DataBucket>`: [3](#0-2) 

Both `apply_grow_index` and `apply_grow_data` are dispatched from the same `handle_delayed_grows` function, which is called on every write-lock acquisition after a grow was queued by `grow()`/`grow_data()`/`grow_index()`: [4](#0-3) 

Newly-created `BucketStorage` instances (e.g. via `new_resized`/`new_with_capacity`) default `delete_file_on_drop` to whatever their constructor sets (typically `true`, matching the "delete on drop unless told otherwise" pattern used for index buckets). Since `apply_grow_data` never flips this flag the way `apply_grow_index` does, the old data-bucket file being replaced is dropped in-place with whatever flag value it already had (from its own creation-time default), and the new data-bucket file keeps whatever flag it was constructed with — there is no explicit hand-off of "who owns the on-disk file across a resize" for data buckets, unlike for the index bucket.

### Impact Explanation
This is a structural inconsistency between the two "apply grow" functions that mirrors the reported bug class exactly: a step performed on one path (transferring delete-file-on-drop ownership for restart-file tracking on `apply_grow_index`) is simply missing on the sibling path (`apply_grow_data`). Given that `RestartableBucket`/`Restart` machinery exists specifically so that on-disk bucket files can be reused across validator restarts, an inconsistency here creates a class of correctness risk for the disk-index restart path: a data-bucket file could either (a) be deleted prematurely if its old `BucketStorage` happens to have `delete_file_on_drop = true` and is dropped when replaced during a grow, or (b) never be cleaned up if it should have been deleted. Because data buckets do not currently participate in the `RestartableBucket` file-name/random tracking scheme visible in `restart.rs` (only the index bucket's file is registered via `restartable_bucket.set_file`), the immediate practical exposure is more likely wasted/leaked disk-index data files than silent data corruption on the hot read path — but this is exactly the type of "broken but currently only reachable via internal state management" gap the reported analog describes.

### Likelihood Explanation
Likelihood is low-to-moderate: this only triggers when a data bucket needs to grow (`BucketMapError::DataNoSpace`), which happens routinely as the accounts index disk-backed bucket map fills up, so the code path itself is reachable under normal validator operation. However, since data buckets today are not wired into the persistent restart tracking (`RestartableBucket` only tracks index files per the code inspected), the missing flag transfer may currently be latent/inert rather than actively causing file loss — I was not able to fully confirm within the available context whether `BucketStorage<DataBucket>` construction paths (`new_resized`, `new`) ever set `delete_file_on_drop = false` for data buckets, which would determine whether this gap is presently benign or actively causes premature file deletion during grows.

### Recommendation
Audit `apply_grow_data` and give it symmetric handling to `apply_grow_index`: if data-bucket files are ever intended to persist across restarts (or if `delete_file_on_drop` must be transferred correctly regardless), explicitly set `delete_file_on_drop = true` on the outgoing `BucketStorage<DataBucket>` and `false` on the incoming one before the swap, mirroring the `self.restartable_bucket.restart.is_some()` guard used in `apply_grow_index`. At minimum, add an explicit comment/assertion documenting why data buckets do not need this transfer, so the asymmetry is not accidental drift between the two nearly-identical functions.

### Proof of Concept
Not applicable as a runnable exploit — this is a structural code-review finding based on directly comparing `apply_grow_index` (`bucket_map/src/bucket.rs:749-764`) against `apply_grow_data` (`bucket_map/src/bucket.rs:776-800`), both reachable from `handle_delayed_grows` (`bucket_map/src/bucket.rs:845-859`), showing the latter omits the `delete_file_on_drop` hand-off logic present in the former.

    pub fn apply_grow_index(&mut self, mut index: BucketStorage<IndexBucket<T>>) {
        self.stats
            .index
            .resize_grow(self.index.capacity_bytes(), index.capacity_bytes());

        if self.restartable_bucket.restart.is_some() {
            // we are keeping track of which files we use for restart.
            // And we are resizing.
            // So, delete the old file and set the new file to NOT delete.
            // This way the new file will still be around on startup.
            // We are completely done with the old file.
            self.index.delete_file_on_drop = true;
            index.delete_file_on_drop = false;
        }
        self.index = index;
    }

    pub fn handle_delayed_grows(&mut self) {
        if self.reallocated.get_reallocated() {
            // swap out the bucket that was resized previously with a read lock
            let mut items = std::mem::take(&mut *self.reallocated.items.lock().unwrap());

                // data bucket

                self.apply_grow_data(i as usize, new_bucket);
            }
        }
