### Title
Hardcoded/misconfigurable `ADDRESS_REGISTRAR_ACCOUNT_ID` in Wallet Contract can silence the anti-misrouting relayer check, enabling fund misdirection - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Wallet Contract (used to emulate Ethereum transactions for ETH-implicit NEAR accounts) hardcodes the account ID of a trusted "Address Registrar" contract as a compile-time constant baked into the WASM, exactly like the audited contract hardcoded a fixed (and in that case invalid/zero) oracle address for a security-critical external lookup.

### Finding Description
`ADDRESS_REGISTRAR_ACCOUNT_ID` is loaded at compile time from a plain text file and parsed at runtime with no validation beyond `AccountId` syntax: [1](#0-0) [2](#0-1) 

This registrar lookup is the *only* on-chain safety mechanism protecting against a faulty/malicious relayer who submits an unsigned meta-transaction (`rlp_execute`) on behalf of a wallet owner. When the relayer claims that an Ethereum `to` address is *not* a registered named NEAR account (`TargetKind::EthImplicit`), the contract independently calls the registrar to confirm that claim in `address_check_callback`: [3](#0-2) 

If the address **is** actually registered, the contract detects the relayer's dishonesty, refuses to execute the (mis-)targeted transfer, and revokes the relayer's access key via `create_ban_relayer_promise`. If the registrar contract referenced by `ADDRESS_REGISTRAR_ACCOUNT_ID` is misconfigured — pointing to the wrong account, a contract that was never populated, or one whose `lookup` method always returns `None` (the exact analog of the audited report's oracle being fixed to the zero address so it can never return a meaningful price) — this check becomes a permanent no-op: `lookup` always resolves to `None`, so the contract can never detect a mismatched target, and a faulty/malicious relayer's redirection of a transfer to a raw eth-implicit address is always accepted as legitimate: [4](#0-3) 

### Impact Explanation
A user's intended transfer to a registered named NEAR account can be silently redirected by a malicious relayer to the corresponding hashed eth-implicit account instead, since the on-chain guard that should catch and ban this behavior is permanently disabled by the misconfigured registrar reference. Because eth-implicit accounts are claimable by whoever holds the matching Secp256k1 private key, an attacker in control of (or able to brute-force/target) that address can withdraw the misrouted funds — resulting in unauthorized value movement out of the user's control, with no on-chain remediation since the relayer is never banned and the nonce/replay protections do not prevent the initial misdirection.

### Likelihood Explanation
This requires only a single relayed transaction from an unprivileged relayer/meta-transaction sender through the standard `rlp_execute` entrypoint; no validator, network, or operator privilege is needed. The precondition is that the compiled `ADDRESS_REGISTRAR_ACCOUNT_ID` constant is wrong or points at an unpopulated/broken registrar, which — exactly as in the referenced report where the oracle address was left as a placeholder — is a deployment/configuration class of error with no on-chain enforcement that the referenced contract actually behaves as intended.

### Recommendation
Do not rely on an unauthenticated, hardcoded external account ID as the sole safety oracle for this security check. Validate that the registrar account actually exists and is the canonical, governance-controlled registrar (e.g. pin it via genesis/config with an upgrade path, or add a fallback/fail-closed behavior — treat `PromiseResult::Failed`/malformed responses as "assume registered" rather than "assume unregistered" — so that a broken or misconfigured registrar cannot be interpreted as "no risk of misdirection").

### Proof of Concept
1. Wallet Contract is built with `ADDRESS_REGISTRAR_ACCOUNT_ID` pointing to an account that either does not exist or is a registrar contract with an empty/stale mapping.
2. A malicious relayer receives a user's Ethereum-style transaction whose `to` address is actually registered to `alice.near` in the (correct) registrar, but the relayer submits `rlp_execute` with `target` set to the raw `0x...` eth-implicit account instead of `alice.near`.
3. `parse_rlp_tx_to_action` classifies this as `EOABaseTokenTransfer { address_check: Some(address), .. }` per [5](#0-4) .
4. `inner_rlp_execute` calls the (misconfigured) registrar and proceeds to `address_check_callback` per [6](#0-5) .
5. Because the registrar always returns `None`, `address_check_callback` treats the target as legitimately unregistered and executes the transfer to the raw eth-implicit account instead of `alice.near`, and the relayer is never banned per [7](#0-6) .
6. Funds land in an account the intended recipient does not control.

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
