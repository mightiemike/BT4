### Title
Attached Deposit Is Permanently Misdirected to the Wallet Contract Instead of Being Refunded to the Caller on Invalid-Target Error - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Uniswap `UniV3Swap` bug is a "wrong recipient" class: the code silently sends value to the wrong party (itself) instead of the party that actually deposited/should receive it. The nearcore Wallet Contract (`near-wallet-contract`) has a structurally identical bug: an externally attached deposit (`CallerDeposit`) is tracked so it can be refunded to the caller if the requested action cannot be executed, but in the `address_check_callback` "invalid target" branch the tracked deposit is simply dropped, so the funds stay on the wallet's own balance (`current_account_id`) instead of returning to the caller who sent them — an unintended recipient of value, reachable directly by any RPC caller invoking `rlp_execute`.

### Finding Description
`WalletContract::rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`) is called by any external account/relayer against an ETH-implicit account. Inside `inner_rlp_execute` (`lib.rs:330-410`), a `CallerDeposit` is created via `CallerDeposit::new` (`types.rs:180-191`) whenever the `predecessor_account_id` differs from `current_account_id` and a non-zero deposit was attached — this represents the caller's (relayer's) own funds sent along with the call, intended to eventually be refunded if the requested action fails.

For the `EOABaseTokenTransfer { address_check: Some(address), .. }` case, the contract calls the address registrar and routes to `address_check_callback` (`lib.rs:134-192`), forwarding `caller_deposit`. In that callback:

```rust
let promise = if maybe_account_id.is_some() {
    if env::signer_account_id() == current_account_id {
        create_ban_relayer_promise(current_account_id)
    } else {
        return PromiseOrValue::Value(ExecuteResponse {
            success: false,
            success_value: None,
            error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
        });
    }
} ...
``` [1](#0-0) 

When the target address maps to an existing named account (`maybe_account_id.is_some()`) and the call was not signed with the wallet's own access key (`signer_account_id() != current_account_id`), the function returns an error value directly — without creating any promise to refund `caller_deposit` to the original `account_id` stored in it (`types.rs:172-191`). The parameter `caller_deposit` is received but unused on this code path.

Elsewhere in the contract, this refund pattern is implemented correctly, e.g. in `rlp_execute_callback` on `PromiseResult::Failed`:
```rust
if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
    let refund_promise = env::promise_batch_create(&account_id);
    env::promise_batch_action_transfer(refund_promise, NearToken::from_yoctonear(yocto_near.into()));
}
``` [2](#0-1) 

This confirms the intended invariant: any tracked `CallerDeposit` must be refunded to its `account_id` whenever the requested action does not go through. The `address_check_callback`'s invalid-target branch violates this invariant, leaving the attached deposit permanently on the wallet's own balance (`current_account_id`) — i.e., value moves to an unintended recipient (the contract/account itself) instead of the caller who is entitled to a refund.

### Impact Explanation
Any external account (an unprivileged RPC/transaction caller acting as a relayer) that calls `rlp_execute` with `attached_deposit > 0` and a `target` whose derived Ethereum address happens to correspond to an already-registered named NEAR account will have its attached deposit permanently absorbed into the ETH-implicit wallet account's balance, with no compensating transfer back to the caller. This is unauthorized value movement / loss of funds for the caller — reachable purely through a normal `FunctionCall` transaction to `rlp_execute` (no privileged role, no validator or network assumption needed), matching the "concrete unauthorized value movement" and "permanently frozen funds" bar for validity. Because refunding on failure is the contract's own documented invariant (see `CallerDeposit` doc comment and the other correctly-implemented refund sites), this is a genuine logic bug rather than intended behavior.

### Likelihood Explanation
The path is trivially reachable: an ordinary account calls `rlp_execute` with `target` set to an eth-implicit account address whose corresponding NEAR address happens to already be registered as a named account, and attaches a non-zero deposit while using its own signer key (not the wallet's access key) — exactly the condition guarding the vulnerable `else` branch. No special privileges, validator behavior, or timing races are required; a caller (or malicious relayer targeting itself) can trigger this deterministically on any submitted transaction.

### Recommendation
In the invalid-target branch of `address_check_callback` (`lib.rs:167-173`), before returning the error `ExecuteResponse`, refund the `caller_deposit` (if present) to its `account_id`, mirroring the refund logic already used in `rlp_execute_callback`. Alternatively, factor the refund-on-failure logic into a shared helper and call it from every early-return/error branch that currently discards `caller_deposit`, ensuring the invariant "caller_deposit is refunded whenever the action does not succeed" holds uniformly across all code paths.

### Proof of Concept
1. Deploy an ETH-implicit wallet contract for address `A` (owner-controlled via a Secp256k1 key).
2. Have an external NEAR account `Relayer` (not holding an access key on `A`) call `A.rlp_execute(target, tx_bytes_b64)` with `attached_deposit = D > 0`, where:
   - `tx_bytes_b64` encodes a signed Ethereum transaction representing an `EOABaseTokenTransfer` with `address_check: Some(address)` (i.e., `target` is another eth-implicit account whose real NEAR account may or may not be named, forcing the address-registrar lookup path).
   - The address registrar lookup for that derived address returns `Some(existing_account_id)` (i.e., the address is already claimed by a named account), causing `maybe_account_id.is_some()`.
3. Since `Relayer != A` (`env::signer_account_id() != current_account_id`), `address_check_callback` takes the `else` branch and returns an error response without creating a refund promise.
4. Observe: `Relayer`'s attached deposit `D` is deducted from its balance and added to `A`'s balance permanently; no receipt is generated to send `D` back to `Relayer`, confirmed by inspecting `A`'s and `Relayer`'s balances before/after the call and the absence of any outgoing transfer receipt to `Relayer` in the execution outcome.
