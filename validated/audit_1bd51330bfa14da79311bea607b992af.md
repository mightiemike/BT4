### Title
Stale `candidate_info.ref_count`/`slot_list` snapshot in `do_clean_scan` can cause `checked_sub().expect(...)` panic in `update_candidate_after_reclaims` - ([File: accounts-db/src/accounts_db.rs])

### Summary
`do_clean_scan` reads a pubkey's `(slot_list, ref_count)` snapshot via `accounts_index.scan()` and later, in a *separate* lock acquisition, calls `collect_reclaims` → `clean_rooted_entries` → `purge_older_root_entries`, which recomputes reclaims against the *current* (possibly newer) slot list. If new rooted versions of the same pubkey are appended between these two lock acquisitions, `update_candidate_after_reclaims` subtracts a `reclaims.len()` computed from the newer state from a `ref_count` captured from the older snapshot, which can underflow and panic.

### Finding Description
`do_clean_scan` captures, under one lock, `slot_list` and `ref_count` for a candidate pubkey via `self.accounts_index.scan(...)` [2](#0-1) . When the latest rooted entry is zero-lamport, `candidate_info.slot_list` and `candidate_info.ref_count` are populated from this T1 snapshot; when it is non-zero-lamport or not-found-on-fork, they are left empty (default), which matters below. Separately, `should_collect_reclaims` is set whenever `slot_list.len() > 1` (multiple rooted versions) [3](#0-2) .

After the scan's lock is released, `collect_reclaims` is invoked, which re-acquires the entry lock and calls `clean_rooted_entries`/`purge_older_root_entries` against the *current* (T2) slot list, not the T1 snapshot [4](#0-3) [5](#0-4) . Between T1 and T2 there is no lock held across `do_clean_scan`'s two accesses to the same pubkey, so ordinary account-write/root traffic (attacker rapidly rewriting the same pubkey into new rooted slots) can append additional rooted, zero-lamport entries to the pubkey's slot list in that window.

`update_candidate_after_reclaims` then does:
```
candidate_info.ref_count = candidate_info.ref_count.checked_sub(reclaims.len() as RefCount).expect("candidate ref count covers every reclaimed entry");
``` [6](#0-5) 
Since `candidate_info.ref_count` is the stale T1 value while `reclaims.len()` reflects everything reclaimed from the T2 (larger) slot list, `reclaims.len()` can exceed the stale `ref_count`, causing the `checked_sub` to return `None` and the `.expect(...)` to panic.

This is only reachable when the zero-lamport branch populated a non-empty `candidate_info.slot_list` (the `if candidate_info.slot_list.is_empty() { return; }` guard at the top of `update_candidate_after_reclaims` protects the non-zero-lamport and not-found-on-fork branches, since those never populate `slot_list`/`ref_count` in the scan closure) [7](#0-6) .

Preconditions for the underflow:
1. Attacker pubkey has ≥2 rooted slot-list entries at T1 with the latest being zero-lamport (candidate captured with `ref_count = N`).
2. Before `collect_reclaims` runs for that same pubkey (a window bounded only by scheduling of the parallel `candidates_bin.retain` closure, not any explicit synchronization), the attacker's continued transaction stream causes additional rooted entries to be appended to the same pubkey's slot list (e.g., write non-zero then zero-lamport again, repeated, each committed and rooted).
3. At T2, `purge_older_root_entries` computes `reclaims.len()` based on the enlarged slot list, exceeding the T1 `ref_count`.

No existing slot/ancestor, zero-lamport, or ref-count guard prevents this, because the two index accesses (`scan` and `collect_reclaims`) are not atomic with respect to each other, and `CleaningInfo`'s cached fields are never re-validated against the index before the subtraction.

### Impact Explanation
This is a validator-halting panic (`Node halt / Denial of Service` category per Agave's bounty categories) reachable purely by an unprivileged user submitting normal transactions at high frequency against their own account(s) while background `clean_accounts` runs concurrently — no special privileges, leader/gossip access, or crafted snapshots are required. Because `clean_accounts` runs on every validator's background thread pool, a successfully timed sequence could simultaneously crash multiple/most validators processing the same transaction stream, which is a cluster-wide halt risk.

### Likelihood Explanation
This requires precise timing: the attacker must race normal transaction/root processing against the background `clean_accounts` scan-then-reclaim window for the *same pubkey*, which is a narrow but not synchronization-protected window, and it must occur while the pubkey has multiple rooted entries including a zero-lamport latest entry. Because `clean_accounts` runs periodically and processes many pubkeys per pass, and the attacker fully controls transaction submission rate and pubkey usage pattern (create/spend-to-zero/refund cycles), the required condition (append new rooted zero-lamport version of the same pubkey in between the scan and collect_reclaims sub-steps) is repeatable by flooding rooted-slot creation for one pubkey. Exact reliability depends on scheduler/thread-pool timing between the parallel scan and the reclaim call, so it is probabilistic rather than deterministic per attempt, but repeatable given enough attempts, which fits a fuzzing/stress-test discovery model.

### Recommendation
Make the "read slot_list/ref_count" and "compute+apply reclaims" operations atomic with respect to the same pubkey's index entry: e.g., compute `should_collect_reclaims`, fetch the up-to-date slot list, and call `purge_older_root_entries` all within one lock acquisition per pubkey (or re-fetch a fresh snapshot immediately before calling `update_candidate_after_reclaims`, and clamp/re-validate `candidate_info.ref_count` and `slot_list` against the live entry rather than trusting the T1 snapshot). Alternatively, change `update_candidate_after_reclaims` to tolerate reclaims that reference newer entries than the cached snapshot by intersecting/re-deriving the reclaim set instead of blindly subtracting counts, and replace the panicking `.expect()` with graceful recomputation or discarding stale candidate bookkeeping instead of asserting.

    fn purge_older_root_entries(
        &self,
        slot_list: &mut SlotListWriteGuard<T>,
        reclaims: &mut ReclaimsWithNewestSlot<T>,
        max_clean_root_inclusive: Option<Slot>,
    ) -> bool {
        if slot_list.len() <= 1 {
            self.purge_older_root_entries_one_slot_list
                .fetch_add(1, Ordering::Relaxed);
        }
        // Find the newest slot at or below the clean root, then reclaim every slot older than it.
        let newest_slot = slot_list
            .iter()
            .map(|(slot, _)| *slot)
            .filter(|slot| slot <= &max_clean_root_inclusive.unwrap_or(Slot::MAX))
            .max()
            .unwrap_or_default();

        slot_list.retain_and_count(|(slot, value)| {
            let should_purge = *slot < newest_slot;
            if should_purge {
                reclaims.push(((*slot, *value), newest_slot));
            }
            !should_purge
        }) == 0
    }

    ) -> bool {
