### Title
Market taker orders can be griefed into forced revert via maker order-count DoS in `MarketSellAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The Code4rena WiseLending finding describes how an unprivileged actor can cheaply manipulate shared on-chain state (total borrow shares) so that a hard `revert` is triggered in someone else's transaction instead of the protocol gracefully clamping the operation. The closest reachable analog in java-tron is the `MAX_MATCH_NUM` order-matching cap inside `MarketSellAssetActuator.matchOrder()`, which reverts the entire taker transaction with `ContractValidateException("Too many matches...")` if a taker's order needs to consume more than 20 resting maker orders — a count that any unprivileged account can cheaply inflate ahead of time.

### Finding Description
In `MarketSellAssetActuator.matchOrder()` [1](#0-0) , the taker's incoming sell order is matched against the resting maker order book at the best price. Each individual maker order consumed increments `matchOrderCount`, and once it exceeds the hardcoded `MAX_MATCH_NUM = 20` [2](#0-1)  the actuator throws instead of partially filling and stopping cleanly:

```
matchOrderCount++;
if (matchOrderCount > MAX_MATCH_NUM) {
  throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
}
``` [3](#0-2) 

This exception is thrown from within `execute()`, which has already mutated in-memory state (balance debit, fee burn, order creation) before calling `matchOrder()` [4](#0-3) ; it is caught only by the generic `ContractValidateException` catch clause and rethrown as `ContractExeException`, marking the whole transaction FAILED.

Because the number of maker orders resting at the best price is entirely attacker-controlled — any account can place many tiny `MarketSellAssetContract` orders at the same price point ahead of a victim's larger taker order (analogous to the borrower front-running the liquidator by repaying 1 share) — an attacker can deliberately fragment the order book so that a legitimate, otherwise fully matchable taker order is forced to traverse more than `MAX_MATCH_NUM` maker orders and hard-reverts, exactly like the WiseLending `checkMaxShares()` revert-instead-of-clamp pattern.

### Impact Explanation
This is a DoS vector for the on-chain market/exchange (`WiseSecurity`-style "exchange/market math" surface). A legitimate large taker cannot obtain the best available price/fill because the transaction is forced to revert entirely rather than partially fill up to `MAX_MATCH_NUM` orders and leave the remainder resting or returned, which is what happens in the normal remaining-order path (`saveRemainOrder`) [5](#0-4) . Repeated griefing forces victims to either accept worse prices, split orders manually, or repeatedly pay transaction fees for reverted attempts — a market-liveness degradation rather than a fund-loss bug, similar to the Medium severity assigned to the original finding.

### Likelihood Explanation
Likelihood is moderate: placing many small maker orders at the best price is cheap (bounded by `dynamicStore.getMarketSellFee()` per order and the `MAX_ACTIVE_ORDER_NUM = 100` per-account cap [6](#0-5) ), and no privileged role is required — any address can create `MarketSellAssetContract` orders. The condition triggers whenever a taker order's fill would otherwise need to walk through more than 20 resting orders at the matched price, which is a realistic scenario for thinly-fragmented order books.

### Recommendation
In `matchOrder()`, instead of throwing when `matchOrderCount` exceeds `MAX_MATCH_NUM`, stop matching and treat the unconsumed remainder like any other unmatched quantity (save it back into the order book via the existing `saveRemainOrder` path), returning success with a partial fill rather than reverting the whole transaction.

### Proof of Concept
1. Attacker creates 25+ tiny `MarketSellAssetContract` maker orders for pair (A, TRX) at the best price, each below the quantity that would trigger `takerBuyTokenQuantityRemain == 0` (`quantity too small`) rejection.
2. Victim submits a legitimate `MarketSellAssetContract` sized to be filled by matching the top price level, which now spans more than `MAX_MATCH_NUM` (20) of the attacker's fragmented orders.
3. `matchOrder()` increments `matchOrderCount` past 20 and throws `ContractValidateException("Too many matches...")` [3](#0-2) , which is caught in `execute()` and converted to `ContractExeException`, failing the victim's transaction entirely instead of partially filling it.
