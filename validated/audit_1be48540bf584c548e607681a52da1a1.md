### Title
Unbounded active-ballot scan on every `CreateBallot` call enables DoS of inbound/outbound voting - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
Every call to `CreateBallot` unconditionally invokes `ExpireBallotsBeforeHeight`, which iterates the **entire** `ActiveBallotIDs` collection and performs an individual `Ballots.Get` for each entry before the new ballot is even written. `CreateBallot` runs synchronously inside the gasless `MsgVoteInbound`/`MsgVoteOutbound` message flow whenever a validator casts the *first* vote on a novel cross-chain observation. An unprivileged external attacker can cheaply generate an unbounded number of distinct, legitimate cross-chain events (e.g. many dust deposits from different source chains/tx hashes/log indices), causing honest Universal Validators to create a correspondingly large number of ballots. Because ballots are only cleaned up as a side effect of the *next* `CreateBallot` call, the `ActiveBallotIDs` set can only grow monotonically between cleanups, making each subsequent vote message pay an O(N) full-set scan — directly mirroring the NFTR-10 pattern of a fixed function fanning out into thousands of sub-calls inside a single execution context and risking exceeding gas/consensus-execution limits.

### Finding Description
`CreateBallot` calls `ExpireBallotsBeforeHeight` as its very first step: [1](#0-0) 

`ExpireBallotsBeforeHeight` performs a full, unpaginated walk of `ActiveBallotIDs`, doing a `Ballots.Get` lookup for every ID in the set: [2](#0-1) 

`CreateBallot` is reached from the standard inbound-observation vote path — the ballot is created on the first validator vote for any newly-observed inbound tx: [3](#0-2) 

`MsgVoteInbound`/`MsgVoteOutbound` are both in the gasless allowlist, meaning submitting/triggering these observations costs no chain fee for the submitting party, and the underlying inbound event is derived from ordinary user-initiated cross-chain deposits, which an unprivileged external attacker fully controls (source-chain tx hash, log index, source chain choice): [4](#0-3) 

Because ballot cleanup (`ExpireBallotsBeforeHeight`) only fires as a side effect of creating the *next* ballot, and each of those creation calls itself performs a full-set scan, the cost of `CreateBallot` scales linearly with however many active ballots currently exist. An attacker who continuously originates many distinct, tiny, legitimate cross-chain events (no validator or node compromise required — honest UVs observe and vote on real, attacker-originated deposits) can keep growing `ActiveBallotIDs` faster than single calls can drain it, since each `CreateBallot` invocation only expires ballots whose `BlockHeightExpiry` has already passed — never processing more than what naturally expires — while at the same time appending a new active entry. This produces the same class of issue flagged in NFTR-10: a fixed function whose internal fan-out (number of sub-lookups) is driven by attacker-influenced state size rather than being bounded/batched, which risks exceeding the execution/gas budget of the message that happens to trigger it and stalling further ballot creation (i.e., stalling processing of new inbound/outbound observations) for that message class.

### Impact Explanation
If the active-ballot set grows large enough (attacker keeps originating many distinct low-value cross-chain events faster than they naturally expire), each subsequent `MsgVoteInbound`/`MsgVoteOutbound` that creates a new ballot pays an increasingly expensive linear scan. In the worst case this can push the per-message execution cost toward or past the point where ordinary vote-processing transactions become impractically expensive or begin to threaten block-level resource budgets, denying timely finalization of legitimate inbound/outbound observations — a DoS on the universal-execution voting pipeline reachable purely from unprivileged, honest-validator-observed user activity.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to sustain a volume of distinct cross-chain events large enough to keep `ActiveBallotIDs` populated faster than the passive expiry-on-next-create mechanism drains it (ballots only get pruned as a side effect of someone else creating a ballot, and only those whose expiry height has already elapsed). This is achievable with low-value dust deposits across many source chains/tx hashes, since submitting inbound events costs the attacker only source-chain gas, not Push Chain fees (the vote messages are gasless for the validators, and observation-triggering events come from ordinary user deposits).

### Recommendation
- Decouple ballot expiry from `CreateBallot`: run expiry as a bounded, paginated/batched sweep in `BeginBlocker`/`EndBlocker` (capped at a fixed max number of ballots processed per block) rather than inline inside every `CreateBallot` call.
- Cap the number of items scanned/expired per `CreateBallot` invocation, or use a min-heap/time-indexed index keyed by expiry height so only genuinely-expired entries are visited instead of the full active set.
- Add a hard ceiling on `ActiveBallotIDs` size or an operator-configurable throttling/rate-limit on new inbound-ballot creation per source chain to bound worst-case growth.

### Proof of Concept
1. An attacker performs many small, valid deposits on a supported source chain (or across multiple supported chains), each with a distinct tx hash/log index, so each is treated as a novel inbound event.
2. Honest Universal Validators observe each event and submit `MsgVoteInbound` for each; each first vote invokes `k.CreateBallot`, which invokes `ExpireBallotsBeforeHeight`, scanning the full, ever-growing `ActiveBallotIDs` set (see `x/uvalidator/keeper/ballot.go:36-39` and `:320-364`).
3. As the attacker continues generating new distinct events faster than existing ballots reach their `BlockHeightExpiry`, the active-ballot set size (and thus the per-`CreateBallot` scan cost) grows without an enforced upper bound, increasing the resource cost of every subsequent inbound/outbound vote message.

```go
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
```
