### Title
`verify_signer_signatures` treats attacker-controlled `version` high-bit as proof of full signer quorum, bypassing signature checks - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoBlockHeader::verify_signer_signatures` short-circuits to `get_shadow_signer_weight(reward_set)` whenever `is_shadow_block()` is true, and `is_shadow_block()` is defined purely as a bit (`version & 0x80`) inside the block header that is fully attacker-controlled, with no separate cryptographic binding to a privileged/SIP-only origin. Any block whose creator sets that single bit causes the function to report the *entire* reward-set weight as "signed" without inspecting `signer_signature` at all.

### Finding Description
The broken equality is:

`verify_signer_signatures(block, reward_set) == total_signing_weight(reward_set)` even when `sum(weight of valid recovered signatures in block.signer_signature) == 0`.

Code path:
- `is_shadow_block()` / `is_shadow_block_version()` only inspect the header's `version` byte: `version & 0x80 != 0` [1](#0-0) .
- `verify_signer_signatures` checks this flag before doing any signature recovery/threshold work and returns early: [2](#0-1) .
- `get_shadow_signer_weight` simply sums every signer's weight in the reward set, unconditionally: [3](#0-2) .
- This generic header method is invoked directly, with no origin/privilege check, from at least the unsolicited-block signature gate used for network-pushed blocks: [4](#0-3) , and from the staging/storage acceptance path that ultimately calls `store_block_if_better` with the returned "signing_weight": [5](#0-4) .

Nothing in `verify_signer_signatures` itself ties `is_shadow_block()` to the fact that legitimate shadow blocks are supposed to be produced only through an out-of-band, SIP-triggered insertion mechanism (`NakamotoStagingBlocksConnRef::add_shadow_block`, exercised only via internal test/CLI tooling such as `contrib/stacks-inspect`) rather than via normal P2P relay/push of an arbitrary `NakamotoBlock`. The design intent documented in the code — "It won't be downloaded or broadcasted, but every node will have it" [6](#0-5)  — is not enforced by any check inside `verify_signer_signatures`, and the function is reused verbatim for both the internal shadow-insertion flow and generic block validation/relay call sites.

I was not able to fully confirm, within the scope of this investigation, whether the top-level block-acceptance dispatcher used for network-sourced blocks (upstream of the `mod.rs:2917` snippet, referred to in its comment as `Self::validate_nakamoto_block_burnchain`) contains an additional, separate guard that rejects any externally-received block whose header already carries the shadow bit before `verify_signer_signatures` is reached. `net/relay.rs` itself contains no `is_shadow_block` check, and `check_nakamoto_block_signer_signature` in `net/unsolicited.rs` — a network-reachable gate for unsolicited/pushed blocks — calls `verify_signer_signatures` with no such filtering. This leaves genuine uncertainty about whether an upstream check in `validate_nakamoto_block_burnchain` fully neutralizes the bypass for the authoritative staging/storage path, versus only for the advisory unsolicited-block gate.

### Impact Explanation
If the bypass is reachable through the authoritative acceptance path (`store_block_if_better`), this is Critical: a normal tenure block with zero valid signer signatures would be accepted network-wide as if it had full reward-set signing weight, i.e., an invalid/unsigned block accepted by consensus-critical logic, which can produce chain splits between nodes that do vs. do not have additional out-of-band shadow-block restrictions, or allow acceptance of miner-crafted blocks without signer approval. At minimum, it is confirmed that the network-facing signature-checking gate in `net/unsolicited.rs` can be tricked into reporting a fully-signed block for an unsigned one, which affects relay/propagation decisions for unsolicited blocks.

### Likelihood Explanation
The only precondition is that the attacker can set a single bit (`0x80`) in the `version` field of a `NakamotoBlock` header they construct and submit/relay — a field fully within their control when crafting or forwarding a block. No stake, signer key, or elevated role is required to flip this bit; the requirement is only whether the resulting block can reach a call site of `verify_signer_signatures` (confirmed for `net/unsolicited.rs`, uncertain for the fully-authoritative staging insertion path pending confirmation of any additional upstream dispatch guard).

### Recommendation
`verify_signer_signatures` (and any shadow-specific validation) must not treat the `is_shadow_block()` header bit as trustworthy on its own for any block that arrives through normal P2P download/relay/push paths. The shadow-weight short-circuit should only be reachable for blocks whose shadow status was established through the dedicated internal insertion mechanism (`add_shadow_block`), e.g., by having the caller pass an explicit, non-attacker-controlled `is_shadow` flag/provenance marker into `verify_signer_signatures` rather than deriving it from the block's own header bit, or by adding an explicit rejection of any header with the shadow bit set at every network ingestion point (`net/unsolicited.rs`, download/relay, and the staging acceptance path) before signature/weight verification occurs.

### Proof of Concept
```rust
// stackslib/src/chainstate/nakamoto/tests/mod.rs (new test)
#[test]
fn test_shadow_bit_bypasses_signature_check_on_normal_block() {
    let signers = [
        (Secp256k1PrivateKey::random(), 100),
        (Secp256k1PrivateKey::random(), 100),
        (Secp256k1PrivateKey::random(), 100),
    ];
    let reward_set = make_reward_set(&signers);
    let total_weight = reward_set.total_signing_weight().unwrap();

    let mut header = NakamotoBlockHeader::empty();
    // Attacker sets the shadow bit on an otherwise normal header, no real tenure change.
    header.version |= 0x80;
    header.signer_signature = vec![]; // zero valid signatures

    let signing_weight = header
        .verify_signer_signatures(&reward_set, StacksEpochId::latest())
        .expect("shadow bit causes verify_signer_signatures to succeed with 0 signatures");

    // Broken equality: reported weight equals full reward-set weight
    // even though summed weight of valid signatures is 0.
    assert_eq!(signing_weight, total_weight);
    assert_eq!(header.signer_signature.len(), 0);
}
```
This test demonstrates the equality violation directly at `verify_signer_signatures`. Extending it into a two-node integration harness that pushes such a header through `Peer::check_nakamoto_block_signer_signature` (`net/unsolicited.rs`) and/or the staging `store_block_if_better` path would confirm the reachability and severity for the full network-acceptance flow; that extended reachability through the authoritative storage path was not fully verified in this investigation and should be validated before treating the finding as fully proven at Critical severity end-to-end.
