### Title
Truncating the EIP-1559 base fee to whole `upc` before multiplying by `gasUsed` systematically under-charges gas fees on every derived EVM payload execution - (File: x/uexecutor/keeper/fees.go)

### Summary
`CalculateGasCost` in `x/uexecutor/keeper/fees.go` truncates the fractional part of `baseFee` (a `LegacyDec`, 18-decimal precision) down to a whole `upc` *before* multiplying by `gasUsed`, instead of computing the full-precision product and truncating only the final result. This is structurally identical to the `StakingRewards.notifyRewardAmount` bug: a per-unit rate is rounded down first, and the rounding error is then multiplied by a large quantity (`gasUsed`), which itself is invoked on every single ordinary user transaction, so the loss compounds across the entire tx volume of the chain rather than being a one-off dust amount.

### Finding Description [1](#0-0) 

```go
baseFeeBig := baseFee.BigInt()
// @dev: ... the base fee is always a whole number of upc -- no fractional upc exists.
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
``` [2](#0-1) 

The code assumes `baseFee` (sourced from `k.feemarketKeeper.GetBaseFee(sdkCtx)`) is always an integer number of `upc`. `GetBaseFee` returns a `LegacyDec`, and Cosmos EVM's `feemarket` module dynamically adjusts the base fee every block using an EIP-1559-style multiplicative formula (`baseFee * (1 ± gasUsedDelta/gasTarget/denominator)`), which routinely produces genuinely fractional `Dec` values (e.g. `1234567890.734...`). `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` discards that fractional remainder immediately, then `effectiveGasPrice * gasUsedBig` (line 81) multiplies the already-truncated integer by a potentially large `gasUsed` (tens of thousands to millions for contract execution). The fractional part that was thrown away scales with `gasUsed`, so the systemic undercharge grows with transaction gas consumption instead of staying bounded to a rounding epsilon.

This function is called from `DeductGasFeesFromReceipt` (`x/uexecutor/keeper/fees.go:97-148`), which is invoked for every `UniversalPayload`-carrying inbound execution (`PAYLOAD` / `GAS_AND_PAYLOAD` transaction types) to deduct and burn the user's gas fee via `DeductAndBurnFees`. Because this runs on every ordinary user-submitted universal transaction with a payload, an unprivileged user's normal transaction flow alone triggers the under-collection — no malicious validator, TSS participant, or admin action is required.

### Impact Explanation
Each execution under-collects gas fees from the paying account by up to `(fractional part of baseFee) * gasUsed` upc. Over the lifetime of the chain and across all `PAYLOAD`/`GAS_AND_PAYLOAD` executions, this is a systemic protocol-level fee-accounting corruption: users are burned less than the fee formula intends, meaning the protocol (and validators who ultimately rely on correctly captured gas fees) permanently lose the truncated portion on every transaction. This falls under the explicitly in-scope impact category "corruption of ... gas fee accounting, refund accounting" reachable purely from "ordinary user deposits, payloads, contracts, or default transaction submission paths."

### Likelihood Explanation
Likelihood is high for the *triggering condition* — every payload-carrying transaction hits this path — but the magnitude per transaction depends on how much fractional drift the `feemarket` base-fee adjustment algorithm actually accumulates in a given block (bounded by <1 upc, i.e., <10⁻¹⁸ of a full token, per unit of gas price). Whether the aggregate loss becomes "significant" over time depends on total payload-transaction gas volume and how far `baseFee` drifts from a whole-upc value under sustained congestion; this could not be fully confirmed without inspecting the exact `feemarket` `CalculateBaseFee` implementation vendored into this fork (not found in the indexed code, likely inside the `github.com/cosmos/evm/x/feemarket` dependency, which is out of the scanned repository).

### Recommendation
Do not truncate `baseFee` to a whole `upc` before multiplying by `gasUsed`. Instead, compute `effectiveGasPrice * gasUsed` in full `Dec` precision (or scale `gasUsed` into the 1e18 fixed-point domain before multiplying) and only truncate once, at the very end, when converting the final gas cost to an integer `upc` amount for burning. This mirrors the standard mitigation for the analogous `StakingRewards` finding: round only the final distributed/charged amount, never an intermediate per-unit rate that will be multiplied by a large quantity.

### Proof of Concept
1. Assume `feemarket` computes `baseFee = 1_000_000_000.700000000000000000` (a `LegacyDec` with a `0.7` fractional upc component) after a block of above-target gas usage.
2. A user submits a `MsgVoteInbound`-derived `PAYLOAD` execution whose EVM receipt reports `GasUsed = 500,000`.
3. `CalculateGasCost` truncates `baseFeeBig` to `1_000_000_000` upc (discarding `0.7`), then computes `gasCost = 1_000_000_000 * 500_000 = 500,000,000,000,000 upc`.
4. The mathematically correct fee is `1_000_000_000.7 * 500_000 = 500,000,000,350,000 upc`.
5. The difference, `350,000 upc`, is never collected from the user and never burned — repeated across every payload transaction in the block/epoch, this systematically leaks fee revenue proportional to `gasUsed`, exactly mirroring the `rewardRate` truncation compounding over `rewardsDuration` in the original `StakingRewards` report.
