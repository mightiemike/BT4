## Verdict: Valid — confirmed by the codebase and by its own test suite

The failure mode described in the question is real and is exactly the behavior that the repository's own integration test documents and accepts as-is (`outbound disabled returns error`), with no retry/rollback mechanism implemented in the scoped code.

### Title
Non-atomic outbound attachment after `ExecutePayloadV2` permanently drops successfully executed outbound funds - (`x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
`ExecuteInboundFundsAndPayload` calls `k.ExecutePayloadV2(ctx, ...)` directly against the live `sdk.Context` (not a `CacheContext`), so any EVM state changes made by the payload — including a PRC20 burn performed by `UniversalGatewayPC.withdraw()`/`withdrawAndExecute()` — are committed to the store immediately and irreversibly. [1](#0-0) 

Only *after* that commit does the code attempt to persist the corresponding outbound intent via `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt`. If that call fails, the only handling is to write the error string into `utx.RevertError` — there is no retry, no reversal of the already-committed burn, and no other code path in the repository ever reads `RevertError` to reattempt attachment. [2](#0-1) 

### Finding Description
`BuildOutboundsFromReceipt` fails (returns a non-nil error, discarding all parsed outbounds for that receipt) in two attacker-reachable cases:

1. Destination chain has outbound disabled (`IsChainOutboundEnabled` returns false): [3](#0-2) 

2. The PRC20 token in the event has no registered token config on the destination chain (`GetTokenConfigByPRC20` errors): [4](#0-3) 

Both `chainId` and `token` in the `UniversalTxOutbound` event are attacker-supplied arguments to the `withdraw`/`withdrawAndExecute` call on `UniversalGatewayPC`, invoked from the user's own `UniversalPayload` executed via `ExecutePayloadV2` against their UEA. The repository's own test explicitly demonstrates and expects this exact failure/no-op behavior: [5](#0-4) 

and for the direct inbound-payload path: [6](#0-5) 

Because `ExecutePayloadV2` is invoked on the uncached `sdkCtx` (unlike the `isSmartContract` branch a few lines above, which deliberately wraps its EVM call in `sdkCtx.CacheContext()` specifically to allow atomic rollback on downstream failure): [7](#0-6) 

the gateway-side burn/withdraw effect from the payload persists even when `AttachOutboundsToExistingUniversalTx` subsequently fails. Grepping the whole codebase for `RevertError` shows it is only ever written (in `execute_inbound_funds_and_payload.go`, `execute_inbound_gas_and_payload.go`, `execute_inbound_funds.go`, `execute_inbound_gas.go`, `handle_failed_inbound_validation.go`, `msg_vote_outbound.go`) — no keeper code reads it back to retry attachment. The `UniversalTx` is left with a `PcTx` marked `SUCCESS`, no `OutboundTx` entry, and a `RevertError` string, and nothing in the module (cron, hook, or message handler) ever revisits it.

### Impact Explanation
Funds moved by the gateway contract (burn/lock of PRC20 as part of the outbound intent) are committed on-chain, but the canonical `UniversalTx.OutboundTx` — the only structure the relayer/TSS pipeline watches to actually deliver funds on the destination chain (via `PendingOutbounds`) — never receives the entry. This is a genuine "permanent freezing of user funds" outcome: the value is gone from the sender's balance with no compensating outbound ever queued, and no code path exists to regenerate or retry it. This matches the in-scope impact category for accounting corruption / permanent loss of funds reachable through ordinary payload execution.

### Likelihood Explanation
High. Any user submitting a `FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` inbound whose `UniversalPayload` calls `UniversalGatewayPC.withdraw()`/`withdrawAndExecute()` with a destination `chainId` that is disabled for outbound, or a token address not registered as `TokenConfig` on that chain, deterministically triggers this path — no validator collusion, no privileged role, and no race condition required. This can happen either through attacker intent (griefing their own funds is not required to be "profitable" to still be a fund-freezing bug affecting the depositor) or simply through a chain being disabled by governance after being previously enabled/used in constructed payloads, which is a realistic operational scenario.

### Recommendation
- Wrap `ExecutePayloadV2` in a `CacheContext` (as already done for the `isSmartContract` branch) and only `writeCache()` after `AttachOutboundsToExistingUniversalTx` succeeds, so a failed attach reverts the EVM-side burn together with the payload execution.
- Alternatively/additionally, persist the decoded-but-unattached outbound data (or the raw receipt) in the `UniversalTx` and add a retry/reconciliation path (e.g., a keeper method or begin-blocker) that re-attempts `AttachOutboundsToExistingUniversalTx` for any UTX with a non-empty `RevertError`, so an outbound-disabled or missing-token-config condition can self-heal once configuration is fixed, without losing the funds.
- Validate `chainId`/token registrability for the outbound *before* allowing the gateway call to burn/withdraw funds (i.e., push the same checks currently done in `BuildOutboundsFromReceipt` into the EVM-side `_validateCommon` of `UniversalGatewayPC`, if not already present there), so the burn simply cannot occur for a destination that cannot record the outbound.

### Proof of Concept
1. Register `eip155:A` chain config with `IsOutboundEnabled: true` initially (or leave a token unregistered on a valid chain) and deploy a UEA for an attacker-controlled `UniversalAccountId`.
2. Attacker submits an inbound of `TxType_FUNDS_AND_PAYLOAD` whose `UniversalPayload.Data` calls `UniversalGatewayPC.withdraw(...)` targeting `chainId = "eip155:A"` with a PRC20 `token` address that has no `TokenConfig` (or targeting a chain later disabled for outbound between payload construction and voting finalization).
3. Once quorum is reached, `ExecuteInboundFundsAndPayload` runs `ExecutePayloadV2` on `ctx` directly — the gateway call succeeds, burns/moves the PRC20, and returns a receipt with a `UniversalTxOutbound` log.
4. `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt` returns an error at the `IsChainOutboundEnabled` or `GetTokenConfigByPRC20` check (exactly as reproduced by the existing test `TestPostTxProcessing_WithSyntheticOutboundEvent/outbound disabled returns error`, `test/integration/uexecutor/evm_hooks_and_outbound_test.go:576-627`, and `TestOutbound_ChainEnabled/outbound not created when destination chain outbound is disabled`, `test/integration/uexecutor/chain_enabled_test.go:360-380`).
5. Inspect the resulting `UniversalTx`: `PcTx` entry is `SUCCESS` (payload executed), `OutboundTx` is empty, `RevertError` is set to the attach error, and `PendingOutbounds` has no entry for this UTX — the burned funds are permanently unrecoverable through any code path in the module.

	})
