## Finding

### Title
Sequencer permanently drops failed Bitcoin deposits from its deposit mempool, freezing the corresponding BTC without ever minting cBTC - (File: `crates/sequencer/src/runner.rs`)

### Summary
The sequencer's block-production loop removes **all** deposits it fetched from the `DepositDataMempool` for a given block, regardless of whether each individual deposit's `Bridge.deposit()` system transaction actually succeeded on-chain. Deposits whose system transaction reverts during real block application are discarded from the mempool exactly the same as deposits that succeeded, even though the comment explicitly says only "successfully included" deposits should be removed. Because the deposit mempool is in-memory only and there is no retry/resubmission path back into it, a deposit that reverts during production is permanently lost from the sequencer's perspective: the BTC was locked on Bitcoin (`moveTx` already confirmed), but the corresponding cBTC mint on Citrea never happens and can never happen again through the normal flow.

### Finding Description
`produce_l2_block_inner` fetches a batch of pending deposits from the deposit mempool up-front: [1](#0-0) 

This raw `deposit_data` is fed into `dry_run_transactions`, which internally calls `produce_and_run_system_transactions` → `process_sys_txs`. Inside `process_sys_txs`, when a deposit's system transaction fails with `EvmSystemTransactionNotSuccessful` (e.g. the `Bridge.deposit()` call reverts), the code explicitly reverts the working set, decrements the nonce, and **skips adding that transaction to the block** via `continue`: [2](#0-1) 

So a reverted deposit never makes it into `txs_to_run` / the final `L2Block` — no on-chain effect occurs and no cBTC is minted for it.

However, back in `produce_l2_block_inner`, after the block is saved, the code removes deposits from the mempool using the *original, unfiltered* `deposit_data` list — not the subset that was actually included in the produced block: [3](#0-2) 

`remove_deposits` in `DepositDataMempool` simply deletes whatever transaction IDs are passed to it, with no distinction between "included" and "reverted": [4](#0-3) 

Since the deposit mempool is purely in-memory (`Arc<Mutex<DepositDataMempool>>`, created fresh via `DepositDataMempool::new()`, never persisted to the ledger DB) and the only way to (re-)enter a deposit into it is the `citrea_sendRawDepositTransaction` RPC call, once a deposit is removed here it is gone from the sequencer forever unless some off-chain actor manually notices the failure and resubmits it: [5](#0-4) [6](#0-5) 

This breaks the intended binding: **BTC locked in the `moveTx` on Bitcoin ⇔ cBTC eventually credited to the recipient on Citrea.** After the flawed removal, the left side (BTC locked) remains true forever while the right side (cBTC credited) becomes permanently false for that deposit, with no automatic recovery mechanism — this is the mirror-image of the double-mint concern in the original nonce-analog report: here a legitimate one-time state-mutating action (the deposit) is consumed exactly once from the queue regardless of whether it was actually applied, so a failed application can never be retried through the normal path.

A deposit can validly fail the second, real execution (`process_sys_txs`) even though it passed the earlier `eth_call` simulation performed in `send_raw_deposit_transaction` at admission time, because the two checks run against different state snapshots (`BlockId::pending()` at submission time vs. the actual `prestate` at production time, potentially after `setDepositScript`/`setReplaceScript`/`setFailedDepositVault` owner calls, or after the light client's tracked block info has advanced) — so a real, previously-valid deposit can transition from "would succeed" to "reverts" between the two checks.

### Impact Explanation
This is a Critical-class issue under "funds permanently frozen": a user's real Bitcoin deposit is locked in the Clementine `moveTx` output, but the sequencer silently and irrecoverably drops the corresponding `Bridge.deposit()` call from its processing queue if it fails once at production time, with no automatic re-attempt. The user's cBTC is never minted, and there is no protocol-level mechanism forcing resubmission.

### Likelihood Explanation
Likelihood is Medium: the failure requires the deposit's on-chain execution to diverge between the RPC-time `eth_call` simulation and the later real block-production execution (e.g., a state change to the bridge's deposit script/parameters, or any other transient revert condition), which is not attacker-controlled but can occur naturally as part of normal sequencer operation, especially under load, restarts of dependent state, or operator maintenance actions on the bridge contract in between submission and inclusion.

### Recommendation
Only remove from the deposit mempool the deposits whose system transaction was actually included/successful in the produced block. `process_sys_txs`/`produce_and_run_system_transactions` should return which deposits (by tx id) succeeded so that `remove_deposits` is called with that filtered set instead of the full `deposit_data` fetched at the start of block production. Deposits that fail should remain in the mempool (or be moved to a retry queue) so they are reconsidered in a subsequent block rather than being silently dropped.

### Proof of Concept
1. Submit a valid deposit via `citrea_sendRawDepositTransaction`; it passes the `eth_call` simulation and is added to `DepositDataMempool` ( [7](#0-6) ).
2. Before the sequencer actually produces the block containing this deposit, cause the bridge state relevant to this deposit to change such that `Bridge.deposit()` will now revert for this exact `moveTx` (e.g. `owner` calls `setDepositScript`/`setReplaceScript`, changing `depositPrefix`/`depositSuffix` so the previously-matching script no longer validates).
3. Sequencer runs `produce_l2_block_inner`; `process_sys_txs` hits `EvmSystemTransactionNotSuccessful` for this deposit, reverts and `continue`s, so the deposit transaction is not included in the block ( [2](#0-1) ).
4. After the block is saved, `remove_deposits(&deposit_data)` is still called with the original unfiltered `deposit_data`, which includes this failed deposit, removing it from the mempool permanently ( [8](#0-7) ).
5. The BTC remains locked in the `moveTx` on Bitcoin; the user's cBTC is never minted and the deposit can only be recovered if some external actor notices and manually resubmits via the RPC (or via `replaceDeposit` on-chain, which requires a separate N-of-N signed transaction).

    /// Removes specific deposits from the mempool after they have been successfully included in a block
    ///
    /// # Arguments
    /// * `deposits_to_remove` - The deposits that were successfully included
    ///
    /// # Returns
    /// The number of deposits actually removed
    #[instrument(level = "trace", skip_all, ret)]
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }

    /// eth_sendRawDepositTransaction RPC call implementation
    fn send_raw_deposit_transaction(&self, deposit: Bytes) -> RpcResult<()> {
        debug!("Sequencer: citrea_sendRawDepositTransaction");

        let deposit_tx_size = deposit.len();
        SM.deposit_tx_size.record(deposit_tx_size as f64);

        let evm = Evm::<DefaultContext>::default();
        let mut working_set = WorkingSet::new(self.context.storage.clone());

        let dep_tx = self
            .context
            .deposit_mempool
            .lock()
            .make_deposit_tx_from_data(deposit.clone().into());

        let start = std::time::Instant::now();
        let tx_res = evm.get_call(
            dep_tx,
            Some(BlockId::pending()),
            None,
            None,
            &mut working_set,
            &self.context.ledger,
        );
        let deposit_tx_call_duration = Instant::now()
            .saturating_duration_since(start)
            .as_secs_f64();
        SM.deposit_tx_call_duration.record(deposit_tx_call_duration);

        match tx_res {
            Ok(hex_res) => {
                tracing::debug!("Deposit tx processed successfully {}", hex_res);
                let add_result = self
                    .context
                    .deposit_mempool
                    .lock()
                    .add_deposit_tx(Deposit::from(deposit.to_vec()));

                match add_result {
                    Ok(true) => Ok(()),
                    Ok(false) => Err(jsonrpsee::types::error::ErrorObject::owned(
                        jsonrpsee::types::error::INVALID_PARAMS_CODE,
                        "Deposit already pending in mempool",
                        None::<()>,
                    )),
                    Err(_) => Err(jsonrpsee::types::error::ErrorObject::owned(
                        jsonrpsee::types::error::INVALID_PARAMS_CODE,
                        "Invalid deposit",
                        None::<()>,
                    )),
                }
            }
            Err(e) => {
                error!("Error processing deposit tx: {:?}", e);
                SM.unaccepted_deposit_txs.increment(1);
                Err(e)
            }
        }
    }
