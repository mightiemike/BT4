### Title
`tokenExchange` never verifies that the session token's `dest` claim matches the caller-supplied `shop`, allowing cross-tenant shop/token pairs to reach Shopify and to be baked into the locally created `Session` - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Finding Description
`tokenExchange` decodes the session token only to validate its signature/audience/expiry, and never compares the resulting `payload.dest` to the caller-supplied `shop` parameter: [1](#0-0) 

`decodeSessionToken` similarly only checks the JWT signature (HS256 with `apiSecretKey`), expiry/nbf, and `aud === config.apiKey` — it never validates `dest`: [2](#0-1) 

Because of this, `tokenExchange` will build the POST URL from the **caller-supplied `shop`** (`https://${cleanShop}/admin/oauth/access_token`) while sending the **subject_token** (the session token) whose embedded `dest` may point to a completely different shop, and — critically — it uses that same caller-supplied `shop` (not anything derived from the token or from Shopify's response) to construct the resulting `Session` object: [3](#0-2) 

This means the library performs no local (defense-in-depth) tenant-isolation check before dispatching the request or before minting a `Session` keyed to an arbitrary shop string. Some consumers mitigate this by deriving `shop` directly from `payload.dest` themselves, e.g. `shopify-app-express`'s `performTokenExchange`: [4](#0-3) 

...but `shopify-app-remix` and `shopify-app-react-router`'s `TokenExchangeStrategy`/`createTokenExchangeStrategy` instead pass `shop` from `sessionContext.shop` (derived via `getShopFromRequest(request)`, i.e. request-derived, not token-derived) straight into `tokenExchange` alongside the raw `sessionToken`: [5](#0-4) [6](#0-5) 

So the library provides no protection if a host app (using the remix/react-router packages as designed) is tricked into calling `tokenExchange` with a `shop` value that diverges from the token's `dest`.

However, whether presenting a shop-A-scoped `subject_token` against `victim-shop.myshopify.com/admin/oauth/access_token` actually yields a usable, cross-tenant access token depends entirely on **Shopify's OAuth server**, which is outside this repository. Shopify's token-exchange endpoint is documented to validate that the ID token's `dest` matches the shop domain being targeted, and is expected to reject such mismatched requests with `invalid_subject_token`. This library cannot be shown, from this codebase alone, to defeat that server-side check — I cannot verify the external server behavior with the tools available.

### Impact Explanation
Two distinct effects follow from the missing check, with different confidence levels:
1. **Confirmed (library-only)**: the library will happily send a request pairing an unrelated shop's subject_token with an attacker-chosen target domain, and — if that request somehow succeeded or partially succeeded — would construct a `Session` object stamped with the attacker-supplied `shop` rather than a shop verified from the token or from Shopify's response, risking session-storage corruption/key confusion (`Session{shop: cleanShop, accessToken: <from response>}`).
2. **Unconfirmed (requires external behavior)**: actual cross-tenant token theft (obtaining a usable access token for `victim-shop`) additionally requires Shopify's backend to accept a `dest`/target-domain mismatch, which is not verifiable in this repo and is contrary to Shopify's documented token-exchange contract.

Given rule #1 requires "exact file/function support" for concrete, reproducible impact, and the cross-tenant token-theft portion cannot be reproduced or verified without Shopify's live server (out of scope, no MITM/external assumptions allowed), this should be treated as a **defense-in-depth gap** in the library rather than a demonstrated cross-tenant compromise.

### Likelihood Explanation
Low, as currently understood: the primary safety net is Shopify's server-side validation of `dest` vs. the request URL for the token-exchange grant, not this library. Exploitability against a real merchant would require either (a) Shopify's server not enforcing that binding (unverified/unlikely), or (b) a host app built on `shopify-app-remix`/`shopify-app-react-router` passing a `shop` value into `tokenExchange` that an attacker can desynchronize from the token's `dest` (plausible, since `shop` there comes from `getShopFromRequest`, not from `payload.dest`).

### Recommendation
Add a local cross-check in `tokenExchange` (or in `decodeSessionToken` when called from this path) asserting that `new URL(payload.dest).hostname === sanitizeShop(config)(shop, true)` before constructing the request, and throw `InvalidJwtError`/reject on mismatch. This closes the defense-in-depth gap regardless of Shopify server behavior and prevents any locally-created `Session` from ever being stamped with an unverified shop.

  const tokenForShopA = signJwt({dest: 'https://shop-a.myshopify.com', aud: apiKey});

    shop: 'victim-shop.myshopify.com',
    sessionToken: tokenForShopA,

  // FAILS today: request is sent to victim-shop with shop-A's token, no local rejection

Expected (fixed) behavior: `tokenExchange` should throw before calling `fetchRequestFactory` when `payload.dest` hostname differs from the sanitized `shop` argument.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
