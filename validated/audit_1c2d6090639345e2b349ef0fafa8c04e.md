### Title
`UnDelegateResourceProcessor.execute` clears DelegatedResourceAccountIndex without checking the lock-key capsule, unindexing a still-frozen locked delegation - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Summary
`UnDelegateResourceProcessor.execute` only checks the unlock-key (`lock=false`) `DelegatedResourceCapsule` for zero balance before clearing the `DelegatedResourceAccountIndexStore` entries for an owner/receiver pair. It never checks whether a lock-key (`lock=true`) capsule for the same pair still holds a nonzero frozen balance, unlike `UnDelegateResourceActuator.execute`, which explicitly requires `lockResource == null && unlockResource == null`.

### Finding Description
In `UnDelegateResourceProcessor.execute`, the index-clearing logic reads: [1](#0-0) 
which only inspects `delegatedResourceCapsule` fetched via `createDbKeyV2(ownerAddress, receiverAddress, false)` (the unlock key), as set up earlier at [2](#0-1) 
It never fetches or checks the lock-key capsule (`createDbKeyV2(..., true)`).

By contrast, the standalone `UnDelegateResourceActuator.execute` explicitly fetches both keys and only clears the index when both are absent: [3](#0-2) 

A locked delegation (lock-key capsule) can be created by an unprivileged attacker via a normal `DelegateResourceContract` transaction with `lock=true`, handled by `DelegateResourceActuator.delegateResource`, which writes to `createDbKeyV2(ownerAddress, receiverAddress, true)`: [4](#0-3) 

An unlocked delegation to the same receiver can be added later (either via another `DelegateResourceContract` with `lock=false`, or via the TVM `delegateResource` precompile, which always writes to the unlocked key): [5](#0-4) 

The attacker can then invoke the TVM `unDelegateResource` precompile repeatedly (via `Program.unDelegateResource`, which drives `UnDelegateResourceProcessor.validate`/`execute`) to fully drain the unlocked portion to zero: [6](#0-5) 

Once the unlock-key capsule's `frozenBalanceForBandwidth`/`frozenBalanceForEnergy` both reach 0, the `fromKey`/`toKey` index entries are unconditionally cleared even though the lock-key capsule at the same owner/receiver pair may still hold a nonzero frozen balance. This produces an inconsistent state where `DelegatedResourceAccountIndexStore` no longer references the pair, but `DelegatedResourceStore` still contains the locked capsule with nonzero balance.

### Impact Explanation
This is scoped to the attacker's own state: the attacker's still-locked/frozen delegated resource for the given receiver becomes unindexed and effectively undiscoverable through `DelegatedResourceAccountIndexStore` (used by wallet/API listing of delegated resources), even though the underlying frozen TRX/resource remains locked in `DelegatedResourceStore` until its expiration. This is a state/index consistency bug (invalid divergence between two related stores) rather than fund theft, since the funds are not stolen from a third party — they simply become harder to discover/enumerate via the index until natural expiration unlocks them (`unLockExpireResource` will still process it correctly since it only depends on `DelegatedResourceStore`, not the index).

### Likelihood Explanation
The preconditions are fully within reach of an unprivileged attacker with a normal account: (1) send a `DelegateResourceContract` with `lock=true` to delegate a locked portion to a receiver, (2) delegate an additional unlocked portion to the same receiver (via contract or TVM precompile), (3) call the TVM `unDelegateResource` precompile enough times to bring the unlocked portion to exactly zero. This is deterministic and fully repeatable without any special privileges, race conditions, or unusual network state.

### Recommendation
In `UnDelegateResourceProcessor.execute`, before clearing the `DelegatedResourceAccountIndexStore` entries, also fetch the lock-key capsule (`DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, true)`) and only clear the index when both the unlock-key and lock-key capsules are null/zero-balance, mirroring the check in `UnDelegateResourceActuator.execute` (`lockResource == null && unlockResource == null`).

### Proof of Concept
Java unit/integration test plan (JUnit, mirroring existing `UnDelegateResourceActuatorTest`/TVM precompile test patterns):
1. Set up owner and receiver accounts with sufficient `FrozenV2BalanceForBandwidth`.
2. Issue a `DelegateResourceContract` from owner to receiver with `lock=true`, `balance=X` (creates lock-key `DelegatedResourceCapsule`).
3. Invoke the TVM `delegateResource` precompile (or a second `DelegateResourceContract` with `lock=false`) from owner to receiver with `balance=Y` (creates unlock-key `DelegatedResourceCapsule`).
4. Invoke `Program.unDelegateResource` (i.e., construct `UnDelegateResourceParam` and call `UnDelegateResourceProcessor.validate`/`execute` directly against a `Repository`) with `unDelegateBalance=Y` for the unlocked resource type, driving the unlock-key capsule's balance to exactly 0.
5. Assert:
   - `DelegatedResourceStore.get(createDbKeyV2(owner, receiver, true))` is non-null and its `getFrozenBalanceForBandwidth()` (or Energy) equals `X` (funds still locked).
   - `DelegatedResourceAccountIndexStore` no longer contains the fromKey/toKey entries for (owner, receiver) — e.g., `getV2Index(owner).getToAccountsList()` no longer contains `receiver`.
   - This combination (nonzero balance in store + absent index) demonstrates the store/index consistency violation, contrasting with `UnDelegateResourceActuatorTest.testLockedAndUnlockUnDelegateForBandwidthUsingWindowSizeV2`, which shows the actuator path correctly keeps the lock-key capsule indexed (`Assert.assertNotNull(lockedResourceCapsule1)` at line 424, without asserting index removal because the lock resource still exists).
