Based on the investigation, `DelegationStore.getBrokerage(byte[] address)` always reads the **current/latest** stored value (`cycle = -1`) rather than a value snapshotted per voting cycle [1](#0-0) , and `UpdateBrokerageActuator` lets any witness change this value at any time with no cooldown or "effective next cycle" restriction [2](#0-1) . This is analogous to the Beedle `Lender.setPool` front-running pattern, but the exploitable side here is that a witness (SR) can adjust their commission cut immediately before the block reward for that same cycle is paid out.

#### Title
Witness can front-run/self-serve `UpdateBrokerageContract` to unexpectedly change the reward cut taken from voters before reward distribution - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

#### Summary
`UpdateBrokerageContract`/`UpdateBrokerageActuator` lets a Super Representative (SR/witness) change the `brokerage` percentage (the SR's cut of block/voting rewards) at any time [3](#0-2) . `MortgageService.computeReward`/`payBlockReward` (via `DelegationStore.getBrokerage`) reads the brokerage stored for the "current" bucket (`cycle = -1`, i.e. always the latest value) when calculating the voter/witness split, as demonstrated in `DelegationServiceTest.testPay` where the `rate` used for a cycle's reward split is whatever was most recently set [4](#0-3) . There is no mechanism forcing a brokerage change to only take effect starting from the *next* cycle, so an SR can raise its brokerage right up to the moment rewards for the ongoing cycle are computed/paid.

#### Finding Description
Voters delegate/vote for an SR expecting the SR's currently published brokerage rate. Because `getBrokerage(byte[] address)` always resolves to the "current" (`cycle == -1`) value written by the most recent `UpdateBrokerageContract` [5](#0-4) , and `UpdateBrokerageActuator.execute` applies the update immediately with `delegationStore.setBrokerage(ownerAddress, brokerage)` (no cycle-delay, no cap besides `[0,100]`) [6](#0-5) , an SR can submit a transaction to bump the brokerage to the maximum (100%) immediately before the reward-paying logic in `MortgageService` executes for that cycle. This mirrors the report's root cause: a privileged actor (pool lender / SR) can adjust a rate parameter that materially affects counterparties' (borrower / voter) payout with no floor/ceiling enforced by the counterparty and no delay protecting already-committed positions.

#### Impact Explanation
If exploited, voters who already voted/delegated toward an SR expecting a certain reward split can have their share of block rewards reduced to zero (brokerage=100 means the SR takes the entire reward) for the cycle being finalized, since the change is read live rather than being locked in per-cycle. This is an accounting/economic manipulation impacting the SR-voter reward-sharing invariant relied upon by `MortgageService.computeReward`.

#### Likelihood Explanation
Any existing witness account (an unprivileged-relative-to-voters, but on-chain, permissionless-to-become role) can broadcast `UpdateBrokerageContract` at will [7](#0-6) , and reward computation cycles run periodically (block-by-block and at maintenance), giving the SR many opportunities to raise brokerage just before a payout without any explicit protections in the validate/execute path.

#### Recommendation
Snapshot brokerage per-cycle so that a brokerage change submitted during cycle N only takes effect starting cycle N+1 (i.e., always write with the target cycle number based on `dynamicPropertiesStore.getCurrentCycleNumber() + 1`, and have `getBrokerage` look up the value active for the specific reward-cycle being computed, similar to how `getWitnessVi`/`getReward` are cycle-scoped). This closes the gap between "current effective rate that voters relied on" and "the rate actually applied when rewards are computed."

#### Proof of Concept
This requires a running Devin session with access to the codebase/test harness to write and run a JUnit reproduction (e.g., extending `UpdateBrokerageActuatorTest`/`DelegationServiceTest`) that: (1) has a voter vote for SR at a low brokerage rate, (2) has the SR call `UpdateBrokerageActuator` to set brokerage to 100 immediately before `MortgageService.payStandbyWitness()`/`computeReward` runs for the same cycle, and (3) asserts the voter's reward is reduced to zero for that cycle despite having voted before the change.
