### Title
Missing symmetric limit check on `output_data_receivers` allows oversized/uncapped `ActionReceipt`s past the receipt-size witness limit - (File: `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`validate_action_receipt` enforces a maximum on one half of a bidirectional receipt relationship — `input_data_ids` — via `max_number_input_data_dependencies`, but never validates the mirror-image field, `output_data_receivers`. This is the same bug class as the Sherlock report: `vouchees` is bounds-checked while the paired `vouchers` array is not, letting the unchecked side grow unbounded and break invariants enforced on the checked side.

### Finding Description
`validate_action_receipt` only bounds `input_data_ids`: [1](#0-0) 

There is no equivalent check anywhere in the codebase for `output_data_receivers` (`grep` for `DataReceiverLengthExceeded`/`NumberOfDataReceivers`-style errors returns nothing), even though `output_data_receivers` is structurally the mirror of `input_data_ids` — one side records "who I depend on", the other "who depends on me": [2](#0-1) 

Each call that wires a callback (`promise_then`/`promise_batch_then`) pushes a `DataReceiver` onto the *target* receipt's `output_data_receivers` with no cap: [3](#0-2) 

Worse, `output_data_receivers` is only checked as part of the whole-receipt `max_receipt_size` gate at creation time (`ValidateReceiptMode::NewReceipt`), but the runtime subsequently *extends* `output_data_receivers` onto an already-validated new receipt without re-running that size/limit check: [4](#0-3) [5](#0-4) 

This exact gap is independently acknowledged in the codebase's own tests/comments (referencing nearcore issue #12606), which demonstrate that a receipt can be pushed above `max_receipt_size` via `output_data_receivers` extension after the size check has already passed: [6](#0-5) 

The forwarding path even contains an explicit compensating workaround that clamps the *reported* size to `max_receipt_size` rather than rejecting the oversized receipt outright, confirming the underlying receipt itself remains unbounded: [7](#0-6) 

### Impact Explanation
Because `output_data_receivers` has no dedicated limit (unlike `input_data_ids`) and is not re-validated after being extended post-creation, a contract can construct a promise DAG (via `.then()`/`promise_batch_then`) whose target receipt accumulates a large number of `DataReceiver` entries, producing a receipt that exceeds `max_receipt_size`. This receipt is then propagated through the outgoing-receipt/state-witness pipeline, which is exactly the class of bug the state-witness size limits (`max_receipt_size`, `per_receipt_storage_proof_size_limit`, `outgoing_receipts_*_size_limit`) are meant to bound to keep `ChunkStateWitness` under its ~21MiB target. An oversized receipt that slips past the intended hard limit risks state-witness bloat/rejection inconsistencies between honest nodes, or requires ad-hoc clamping workarounds (as already visible in `try_forward`) rather than being rejected outright — i.e., an invalid-state-transition-acceptance / witness-limit-bypass class issue.

### Likelihood Explanation
Reachable purely from a contract call: any account can deploy a contract that chains many `promise_then` calls targeting the same receipt index within the gas budget (`max_total_prepaid_gas`), directly growing `output_data_receivers` with no dedicated cap, mirroring the reachable, unprivileged trigger in the original report (any member calling `updateTrust`).

### Recommendation
Add a symmetric bound on `output_data_receivers` mirroring the `max_number_input_data_dependencies` check in `validate_action_receipt` (e.g., a new `max_number_output_data_receivers` limit config value with a corresponding `ReceiptValidationError` variant), and enforce it both at initial receipt validation and whenever `output_data_receivers` is subsequently extended (e.g., in the `lib.rs:1152-1190` extension path), not just at the one-time `NewReceipt` size check.

### Proof of Concept
Not independently exploitable-proven with available tooling in this pass; the codebase itself documents the underlying oversized-receipt-via-`output_data_receivers` behavior in `test_max_receipt_size_promise_return` (`test-loop-tests/src/tests/max_receipt_size.rs:130-208`), which is cited above as concrete evidence that extending `output_data_receivers` after creation bypasses `max_receipt_size` validation, corroborating the missing-symmetric-check root cause identified in `validate_action_receipt`.
