### Title
Meta-transaction `DelegateAction` signatures lack any chain/network-specific domain separator, enabling cross-network signature replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
Analogous to the `Forwarder._verifySig` finding — where a caller-supplied, chain-agnostic `domainSeparator` allowed a valid signature to be replayed across chains — NEAR's NEP-366 meta-transaction (`DelegateAction`/`DelegateActionV2`) signing scheme also omits any chain- or network-identifying value from the signed payload, relying only on the account's access-key nonce for replay protection.

### Finding Description
A `SignedDelegateAction` is verified purely by hashing a `SignableMessage` composed of a `MessageDiscriminant` (only encoding the NEP number, e.g. NEP-366/611) and the `DelegateAction`/`DelegateActionV2` body itself: [1](#0-0) [2](#0-1) 

The signed struct contains only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — no genesis hash, chain id, or any other network-specific identifier: [3](#0-2) [4](#0-3) 

Regular `SignedTransaction`s bind to a specific chain fork via `block_hash` (recent block hash), but `DelegateAction` has no equivalent field, and `SignedDelegateAction::verify`/`VersionedSignedDelegateAction::verify` never consult `apply_state`'s chain/genesis identity — validation is limited to nonce ordering and an upper bound, then signature-over-body matching: [5](#0-4) 

Because the signed bytes contain no chain-specific salt, a `SignedDelegateAction` that is valid for a given `sender_id`/`public_key`/nonce on one NEAR-protocol network is equally valid on any other NEAR-protocol network where the same account exists with the same public key and an access key whose current nonce is still below the signed nonce (e.g., a forked/mirrored network, a canary/shadow network seeded from the same genesis/state snapshot, or a re-genesis/restart that preserves account state).

### Impact Explanation
If the same account id and access key (nonce state) exist on two independently operated NEAR networks that share genesis/account state (a realistic operational scenario for testnets mirroring mainnet state, disaster-recovery/backup chains, or shadow chains used for load testing), an attacker who observes a signed `DelegateAction` on chain A can resubmit it verbatim (wrapped by any relayer, since the relayer is untrusted and unauthenticated in the protocol) on chain B, causing the sender's delegated actions (transfers, `AddKey`, contract calls, etc.) to execute on chain B without the sender's consent for that network. This can result in unauthorized value movement or unauthorized privilege changes (e.g., adding a full-access key) on the second network, mirroring the "cross-chain signature replay" impact in the analog report.

### Likelihood Explanation
This requires two NEAR networks with overlapping account/access-key state (matching `sender_id`, `public_key`, and nonce state) — a condition that does not hold between distinct networks with independent genesis (e.g., mainnet vs. testnet as currently operated), but is realistic for forked, mirrored, or reset-and-restored networks, which NEAR operators/relayer ecosystems commonly stand up for testing, migrations, or disaster recovery. The `max_block_height` field limits the replay window per originating chain's height but does not prevent replay on a second chain at an equivalent height. This is a design gap rather than a proven exploited path against a single canonical network today.

### Recommendation
Include a chain-specific and protocol-specific domain separator in the NEP-461/NEP-366 signing scheme — e.g., mix the genesis hash (or a `chain_id`) into `MessageDiscriminant`/`SignableMessage` alongside the existing NEP-number discriminant, similar to how EIP-712's `domainSeparator` incorporates `block.chainid`. Validate this value against the applying chain's genesis/chain id in `apply_delegate_action` (`runtime/runtime/src/actions.rs`) before accepting the signature, so a `SignedDelegateAction` produced for one network can never verify on another.

### Proof of Concept
1. Network A and Network B are both instantiated from the same genesis/state snapshot (e.g., a mirrored testnet or DR replica), so `alice.near` exists on both with the same public key and identical access-key nonce.
2. Alice signs a `DelegateAction` (e.g., `AddKeyAction` granting full access, or a transfer) intended for Network A only, per `SignedDelegateAction::sign` at [6](#0-5) .
3. A relayer/attacker submits the identical `SignedDelegateAction` bytes inside a transaction on Network B.
4. `VersionedSignedDelegateAction::verify`/`SignedDelegateAction::verify` succeeds because the signed hash never encoded which network it was meant for [7](#0-6) , and `apply_delegate_action`'s nonce checks pass because Network B's access-key nonce state matches Network A's pre-execution state [8](#0-7) .
5. The delegated action executes on Network B without Alice's consent for that network.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}
