## Finding [1](#0-0) 

The nearcore analog of the reported `TimeLockPool.withdraw()` missing zero-address check is in `DeleteAccountAction` (the receiver-loses-funds pattern), not a zero address but an unchecked *non-existent* beneficiary account.

### Title
`DeleteAccount` action burns an account's entire remaining balance forever if `beneficiary_id` does not exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`validate_delete_action` only checks that `beneficiary_id` is a syntactically valid `AccountId`; it never checks that the account actually exists on chain, analogous to the missing zero-address check in the reported `TimeLockPool.withdraw()`.

### Finding Description
When a `DeleteAccount` action executes, `action_delete_account` unconditionally builds a system balance-refund `Receipt` addressed to `delete_account.beneficiary_id`, carrying the entire remaining account balance: [2](#0-1) 

No existence check on `beneficiary_id` is performed before this — the only validation is format-level, in `validate_delete_action`: [1](#0-0) 

This balance refund is a `Receipt::new_balance_refund`, whose `predecessor_id` is `"system"`: [3](#0-2) 

When this receipt is later applied, `check_account_existence` runs on the resulting `Transfer` action against the beneficiary account. Because the receipt is a refund (`is_refund = true`), `implicit_creation_allowed` unconditionally returns `false`, so a missing beneficiary account causes the transfer to fail with `AccountDoesNotExist`: [4](#0-3) [5](#0-4) 

Critically, when a system-predecessor (refund) receipt fails, its deposit is not retried, forwarded, or bounced back to anyone — it is burned outright: [6](#0-5) 

A test in the codebase itself documents this exact hazard, explicitly noting the beneficiary "has to exist" or the transfer is lost: [7](#0-6) 

### Impact Explanation
Any unprivileged transaction signer (via `SignedTransaction::delete_account`) or any contract acting on its own account (via `promise_batch_action_delete_account`, reachable from any contract call) can trigger `DeleteAccount` with an attacker/user-supplied `beneficiary_id`. If that `beneficiary_id` is a syntactically valid but non-existent account (e.g., a typo, or a `sub.account.near` name that was never created), the entire remaining NEAR balance of the deleted account is irrecoverably burned rather than transferred — a real, concrete, permanent loss of funds, matching "permanently frozen/lost funds" from the validation criteria.

### Likelihood Explanation
High-likelihood accidental trigger: any user typo in a beneficiary account id (a very common mistake, exactly as described in the original report for `address(0)`) during a normal, unprivileged `DeleteAccount` transaction or a contract-driven self-deletion via `promise_batch_action_delete_account` results in silent, irreversible fund loss with no on-chain revert of the delete itself (the account deletion succeeds; only the money transfer fails and is burned).

### Recommendation
Before creating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or otherwise refuse to delete the account / reject the action) so that user funds are never silently burned due to a non-existent beneficiary. Alternatively, route a failed beneficiary refund back to the original `account_id`'s "system" refund path with retry/forwarding semantics instead of unconditional burn-on-failure for this specific action type.

### Proof of Concept
1. Create account `alice.near` with balance `X`.
2. Submit `SignedTransaction::delete_account(nonce, alice.near, alice.near, "nonexistent.near", signer, block_hash)` where `nonexistent.near` is a syntactically valid, but never-created, account id.
3. `validate_delete_action` passes (format is valid).
4. `action_delete_account` deletes `alice.near` and emits `Receipt::new_balance_refund("nonexistent.near", X)`.
5. When this refund receipt executes, `check_account_existence` returns `AccountDoesNotExist` because `implicit_creation_allowed` forbids creation for refunds.
6. `lib.rs`'s refund-processing path detects `result.result.is_err()` on a system-predecessor receipt and adds `X` to `other_burnt_amount` — `alice.near`'s balance `X` is permanently destroyed, not delivered to any account.

```rust
/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
```
