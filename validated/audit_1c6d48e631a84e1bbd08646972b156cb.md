### Title
Wallet Contract's in-flight-transaction lock has no reset path, permanently freezing an ETH-implicit account when a chained callback fails to run - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The external report describes a proxy contract that can enter a state where its normal flow (`withdraw`) is interrupted, its balance stays unchanged, and — because the contract has no rescue/no-op tolerance for that state — funds become permanently stuck. The nearcore analog is the `WalletContract`'s `has_in_flight_tx` guard: every `rlp_execute` call sets this flag to `true` and relies exclusively on a *subsequent chained callback receipt* (`rlp_execute_callback`, `nep_141_storage_balance_callback`, `address_check_callback`, or `ban_relayer`) to flip it back to `false`. If that chained callback receipt never successfully executes to the point of resetting the flag, the flag remains `true` forever and there is no admin/rescue function anywhere in the contract to clear it.

### Finding Description
`rlp_execute` unconditionally rejects any call while `has_in_flight_tx == true`: [1](#0-0) 

It sets the flag before returning a `Promise` in every branch: [2](#0-1) 

The flag is only ever cleared inside `#[private]` callback methods, each of which resets it at the very top of the function body, e.g. `rlp_execute_callback`: [3](#0-2) 
and `nep_141_storage_balance_callback`: [4](#0-3) 
and `address_check_callback`: [5](#0-4) 

These callback methods are chained via `.then(...)` onto promises whose static gas is computed by adding the callback's fixed static gas to the *inner action's* requested gas (`callback_gas = X_CALLBACK_GAS.saturating_add(action.gas())`), e.g.: [6](#0-5) [7](#0-6) 

On NEAR, a `.then()`-chained callback receipt is guaranteed to be *scheduled*, but its actual gas budget comes entirely from the static gas attached at scheduling time; if that receipt runs out of gas before it can execute the `self.has_in_flight_tx = false` state write and commit, the callback receipt fails and the flag-reset state change is rolled back for that receipt (per the standard NEAR promise/receipt gas-accounting and rollback semantics documented for action-receipt execution: on failure `state_update.rollback()` discards all state changes from the receipt). This is structurally identical to the reported bug class: a legitimate "emergency"/failure path (the inner cross-contract call under-gassing, panicking, or the relayer intentionally attaching insufficient total gas) causes the flag/state that gates future operations to never be reset, and — unlike the P2P proxy recommendation — there is no rescue/reset mechanism (no owner-only `reset_in_flight` or similar) anywhere in `WalletContract`.

Once `has_in_flight_tx` is stuck at `true`, every future `rlp_execute` call on that account is unconditionally rejected at the guard, permanently disabling the ETH-implicit account's only transaction path and freezing any assets ($NEAR or NEP-141 tokens held by the wallet, since transfers out are only possible via `rlp_execute`) that are controlled by it.

### Impact Explanation
This freezes the wallet-contract-controlled account entirely: no further `Transfer`, `FunctionCall`, ERC-20 emulation, or any other action can be relayed through `rlp_execute` because the guard at the top of the function rejects every call while the flag is stuck. Any native $NEAR balance or NEP-141 token balances owned by that eth-implicit account become permanently inaccessible through the wallet mechanism, matching the "permanently frozen funds" acceptance criterion. This is reachable by an ordinary, unprivileged transaction signer/relayer — no validator or node compromise is required — merely by submitting (or causing to be submitted) an `rlp_execute` transaction whose target cross-contract call consumes attached gas up to the boundary where the trailing callback receipt itself cannot complete (e.g., a malicious or misconfigured token contract that burns gas up to its limit, or a relayer that deliberately routes maximum-gas actions), or simply if the inner action panics with the callback still under-provisioned relative to actual chain conditions.

### Likelihood Explanation
Reaching this requires only ordinary permission-less interaction: any relayer or the user themselves (self-relaying) can submit an `rlp_execute` transaction. The invariant documented in the contract itself ("`has_in_flight_tx` must be `true` when a mutable method... returns a promise and `false` otherwise") shows the developers are aware this flag is fragile and depends on the callback always completing — but they only handle the `PromiseResult::Failed` case (a completed-but-unsuccessful cross-call), not the case where the callback receipt itself fails to execute/commit its state change due to gas exhaustion or being executed by a target contract that behaves adversarially with gas consumption. Because gas estimation for the target action (`action.gas()`) is attacker/relayer-influenced input embedded in the signed Ethereum transaction, and the static callback gas is a small fixed constant added on top, an attacker-controlled or buggy interaction can plausibly exhaust the callback's gas budget before the flag reset commits.

### Recommendation
1. Ensure that the state write resetting `has_in_flight_tx = false` happens in a way that is guaranteed to succeed independent of the inner cross-contract call's gas consumption — e.g., reserve gas explicitly and structurally so that flag reset is not dependent on downstream user-influenced gas usage, or perform the reset as the very first operation of the receipt with a hard-reserved minimum gas floor validated at `rlp_execute` time.
2. Add an explicit, permissionless (or timelocked) "unstick" / self-repair mechanism: e.g., allow the wallet's own signer to submit a diagnostic/reset transaction, or add a fallback so that if a scheduled callback is detected as not having executed (via a timeout receipt or yield/resume), `has_in_flight_tx` can be forced back to `false` without requiring the original chain of promises to succeed.
3. Validate/require a minimum reserved gas amount for the callback independent of `action.gas()`, and reject `rlp_execute` calls where total attached gas cannot guarantee the callback's execution regardless of what the inner call does with its portion.

### Proof of Concept
Conceptual sequence (not fully verified against a running test-loop, since sandbox/adversarial reproduction is out of scope for this analysis and outside the tools available here):
1. Attacker/relayer submits `rlp_execute` targeting an ERC-20 emulation transfer to a token contract that is crafted (or coincidentally configured) to consume gas up to the edge of what `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` allocates for the trailing `nep_141_storage_balance_callback`/`rlp_execute_callback` chain.
2. `rlp_execute` sets `has_in_flight_tx = true` and returns the promise chain (`lib.rs:116-127`).
3. The chained callback receipt, starved of gas by upstream consumption, fails before it can commit `self.has_in_flight_tx = false`; the receipt's state changes (including the flag reset) roll back.
4. Every subsequent `rlp_execute` call against this account is now rejected at `lib.rs:97-105` with "transaction already in progress," indefinitely, since no other method exists in the contract to clear `has_in_flight_tx`.
5. All $NEAR/NEP-141 balances controlled by that eth-implicit account are permanently unreachable via the wallet-contract mechanism.

Note: I was not able to fully verify the exact gas-exhaustion mechanics of `.then()`-chained callback receipts against the live runtime gas-scheduling code within the scope of this investigation (this would require deeper tracing through `runtime/runtime/src/function_call.rs` and the gas-purchase/refund pipeline). This should be validated with a concrete test-loop reproduction (e.g., in `test-loop-tests` or the wallet-contract's own sandbox test suite) before treating the exploitability as fully confirmed.
