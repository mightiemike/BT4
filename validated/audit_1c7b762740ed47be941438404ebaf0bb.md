## Title
Wallet Contract permanently retains external caller's attached deposit when a Relayer error triggers the ban-relayer path - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In `inner_rlp_execute`, `CallerDeposit` is captured up-front from the attached deposit of a non-self predecessor so that it can be refunded if the cross-contract call subsequently fails [1](#0-0) . However, on the `Error::Relayer` path — taken when the relayer misbehaves (e.g. sets an incorrect `target`) — the function returns the error directly without ever attaching the previously-created `caller_deposit` to any refund promise [2](#0-1) . In `rlp_execute`, this `Err(Error::Relayer(_))` case is handled by creating a "ban relayer" promise that carries no `caller_deposit` parameter at all [3](#0-2) , and `ban_relayer` itself only returns a failure `ExecuteResponse`, performing no refund [4](#0-3) .

### Finding Description
`CallerDeposit::new` is built solely from `attached_deposit` and the predecessor being different from `current_account_id` [5](#0-4) ; its purpose, per its doc comment, is explicitly "to keep track of the deposit given by an external caller ... so we can refund the caller's deposit if the cross-contract call fails" [6](#0-5) . The refund is only ever wired through the `rlp_execute_callback` failure branch, which reads `caller_deposit` and issues a transfer back to `account_id` [7](#0-6) . But `caller_deposit` is only ever forwarded into that callback along the success/`User`-error parsing branches of `inner_rlp_execute` — never on the `Error::Relayer` branch [8](#0-7) . Since `Error::Relayer` is returned to `rlp_execute`, which for the access-key relayer case only spawns `create_ban_relayer_promise(current_account_id)` — a call that does not accept or reference `caller_deposit` — the deposit that was attached by the external (predecessor) caller is left sitting on the wallet contract's own balance with no code path that ever schedules its return.

This mirrors the reported bug class: a value ("bonus"/refund) that the contract is documented and designed to distribute back to its rightful owner is gated behind a variable/parameter that is silently never populated on a specific control-flow branch, so the intended distribution logic is unreachable on that branch and the funds become stuck in the contract.

### Impact Explanation
An external, unprivileged caller (any account that calls `rlp_execute` on someone else's Wallet Contract instance with an attached deposit, as demonstrated by `test_caller_refunds`) can have their deposit permanently retained by the wallet contract if the transaction triggers a `Error::Relayer` classification (e.g., a target/address-registrar mismatch) while the call is being made via a full-access/whitelisted relayer key equal to `current_account_id`. This is a concrete, transaction-triggered loss of funds for the caller — value that should be refunded is retained by the contract with no code path to recover it, matching "permanently frozen funds" for the caller.

### Likelihood Explanation
The path is reachable purely through the public `rlp_execute` entry point using ordinary account interactions (an external caller attaching a deposit, and a relayer or the account's own access key submitting a malformed/target-mismatched Ethereum-emulation transaction) — no privileged, validator, or network-layer capability is required. The existing test suite (`test_caller_refunds`, `test_relayer_invalid_address_target`) exercises adjacent scenarios (cross-contract call failure, relayer banning) but does not appear to cover the combination of "external caller deposit present" + "Relayer-error → ban-relayer" path, which is consistent with this refund omission going unnoticed.

### Recommendation
Thread `caller_deposit` through the `Error::Relayer` branch of `inner_rlp_execute` and into `create_ban_relayer_promise`/`ban_relayer`, so that whenever a caller's deposit was captured but the call is aborted via the ban-relayer path, a refund transfer to the original caller is scheduled exactly as it is on the `rlp_execute_callback` failure branch.

### Proof of Concept
1. Deploy the Wallet Contract for an eth-implicit account and register a full-access key for that account to itself (the "access-key relayer" pattern used for `rlp_execute`).
2. An external caller (a separate Near account, not the wallet's own account) calls `rlp_execute` with a non-zero attached deposit, wrapping an Ethereum-emulation transaction whose `target` is set incorrectly (as in `test_relayer_invalid_address_target`), causing `parse_rlp_tx_to_action` (via `validate_tx_relayer_data`) to yield `Err(Error::Relayer(_))`.
3. `inner_rlp_execute` returns `Err(Error::Relayer(_))` directly (never referencing the already-constructed `caller_deposit`).
4. Because `env::signer_account_id() == current_account_id` (the access key relayer), `rlp_execute` calls `create_ban_relayer_promise(current_account_id)` and returns `PromiseOrValue::Promise(promise)` without any refund transfer to the external caller.
5. Compare the caller's account balance before and after the call: the attached deposit is not returned, remaining on the wallet contract's balance indefinitely, in contrast to the refund behavior verified for the ordinary cross-contract-call-failure case in `test_caller_refunds`.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
