### Title
Non-standard NEP-141 responses cause permanent loss of externally-attached deposits in the NEAR Wallet Contract - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `near-wallet-contract` (used to emulate Ethereum-style EOAs on NEAR, exposing `rlp_execute` to unprivileged relayers/callers) tracks a `CallerDeposit` explicitly so it can refund an external caller's attached deposit if a cross-contract call fails. However, in two callback paths that interact with NEP-141 token contracts (the NEAR analog of ERC20), a non-standard or malfunctioning token response causes the code to return an error `ExecuteResponse` **without ever issuing the refund promise**, permanently trapping the caller's attached NEAR in the wallet contract.

### Finding Description
`CallerDeposit` is created for every external (non-self) caller of `rlp_execute` that attaches a deposit, specifically to be refunded if the downstream promise fails: [1](#0-0) 

The only place that actually performs this refund is `rlp_execute_callback`, and only in its `PromiseResult::Failed` branch: [2](#0-1) 

But for emulated ERC20 (NEP-141) transfers, execution first goes through `nep_141_storage_balance_callback`, which calls the token's `storage_balance_of` and parses the JSON response as `Option<StorageBalance>`: [3](#0-2) 

If that cross-contract call fails (`PromiseResult::Failed`) or the token returns a response that does not deserialize into the expected `Option<StorageBalance>` shape (a "non-standard" NEP-141 implementation, exactly analogous to the ERC20 report's non-standard `transfer`/`approve` return values), the function returns an `ExecuteResponse{success:false, ...}` directly — it never constructs a refund promise for `caller_deposit`, unlike `rlp_execute_callback`. The same pattern exists in `address_check_callback` for the `EOABaseTokenTransfer` path when the address registrar's response is malformed: [4](#0-3) 

Since `caller_deposit` is only consulted in `rlp_execute_callback`, any early return from `nep_141_storage_balance_callback` or `address_check_callback` silently discards the caller's deposit tracking — the yoctoNEAR remains part of the wallet contract's account balance forever, with no code path to reclaim or refund it to the original caller.

### Impact Explanation
This results in permanently frozen funds for any unprivileged external caller (a relayer or any account invoking `rlp_execute` with an attached deposit intended to compensate gas/fees) whenever the target NEP-141 token contract is non-standard, temporarily misbehaving, or simply returns `storage_balance_of` in a slightly different (but still valid) JSON shape than expected. This matches the report's core impact class ("funds ... locked ... forever") but applies to attacker- or relayer-attached NEAR deposits in the Wallet Contract rather than pool assets. Because `rlp_execute` is payable and reachable directly by any external transaction signer, this is reachable without any privileged role.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an external (non-self) caller attaching a nonzero deposit to `rlp_execute`, and (b) the target NEP-141 token's `storage_balance_of` (or the registrar's `lookup`) call to either fail or return a response NEAR-SDK cannot deserialize into the expected type. This can happen with any non-compliant/buggy token contract, a token contract that is paused/upgraded to a different schema, or an adversarial token contract deliberately returning malformed JSON to grief callers/relayers routing transactions through it — all of which are realistic conditions outside of nearcore's own compliant contracts.

### Recommendation
In `nep_141_storage_balance_callback` and `address_check_callback`, refund the `caller_deposit` in every early-return error branch (failed promise result and JSON deserialization failure), mirroring the refund logic already present in `rlp_execute_callback`. Consider factoring the refund logic into a shared helper to avoid this divergence being reintroduced in future callback additions.

### Proof of Concept
1. Deploy a NEP-141-like contract whose `storage_balance_of` method returns a JSON value that does not match `Option<StorageBalance>` (e.g., returns a bare number or an object missing required fields) instead of failing or returning `null`/a valid `StorageBalance`.
2. As an external, non-self caller, invoke `rlp_execute` on a Wallet Contract instance with an RLP-encoded ERC20 `transfer` calldata targeting that token, attaching a nonzero NEAR deposit (`CallerDeposit` gets created since `predecessor_account_id != current_account_id`).
3. The wallet contract calls `storage_balance_of`, whose response fails to deserialize in `nep_141_storage_balance_callback` (line ~211-219), causing an immediate `ExecuteResponse{success:false}` to be returned without ever creating a `promise_batch_action_transfer` refund to the caller.
4. Observe that the caller's attached deposit remains part of the Wallet Contract account's balance with no way to reclaim it, confirming permanent fund loss for the external caller.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
