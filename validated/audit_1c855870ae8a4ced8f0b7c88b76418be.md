This confirms the strongest analog: `authenticateExtensionFactory` explicitly calls `validateSessionToken(..., {checkAudience: false, ...})`, in both `shopify-app-remix` and `shopify-app-react-router`, meaning session tokens accepted at this handler are **not bound to the app's own `apiKey`/`aud` claim** — the exact same class of bug as the HOPR finding, where a signed artifact's tenant/context-binding field (`chainId` in the domain separator; `aud`/API key here) is computed but not verified at the point of use.

### Title
Extension request authentication accepts session tokens without verifying the `aud` (API key) claim, enabling cross-app token replay - ([File: packages/apps/shopify-app-remix/src/server/authenticate/public/extension/authenticate.ts])

### Summary
`shopify.authenticate.public.*Extension` handlers validate the App Bridge session token JWT but explicitly disable audience checking (`checkAudience: false`). This is analogous to the HOPR `domainSeparator` bug: a cryptographically signed token carries a context-binding field (`aud`, i.e., which app the token is scoped to — comparable to `chainId`/domain separator), but the verifying code intentionally skips validating that binding before trusting the token's `shop`/`sub` claims.

### Finding Description
`decodeSessionToken` in `packages/apps/shopify-api/lib/session/decode-session-token.ts` (lines 15-43) only compares `payload.aud` to `config.apiKey` when `checkAudience` is `true`: [1](#0-0) 

However, `authenticateExtensionFactory` (both in `shopify-app-remix` and `shopify-app-react-router`, identical code) calls `validateSessionToken` with `checkAudience: false`: [2](#0-1) 

Since the JWT is still signed with the shared `apiSecretKey` and only requires a valid `HS256` signature plus `exp`/`nbf` checks, disabling the `aud` check means any session token minted for *any* app that shares/derives from a compromised or reused key — or, more importantly, any session token whose audience was never intended for this app — will still pass validation as long as the signature check succeeds. The `shop`/`dest` claim from that token is then trusted to build a session ID (`getJwtSessionId`/`getOfflineId`) and dispatch to the extension handler, exactly like the domain-separator bug: a value meant to scope the credential to a specific context (chain/app) is generated correctly but not enforced at verification time.

### Impact Explanation
If two or more Shopify apps configured with the codebase inadvertently share the same `apiSecretKey`, or if a session token intended for a different app instance is captured, `checkAudience: false` means the extension endpoint will accept it as valid, resolving to a shop's session and granting access to the extension's authenticated context (session, CORS-approved actions) without confirming the token was actually issued for this app. This weakens tenant/app isolation guarantees the `aud` claim is designed to provide, mirroring the "replay across the wrong context" impact of the original finding.

### Likelihood Explanation
Reachable by any client capable of sending a request to the extension endpoint with a self-supplied `Authorization`/session-token header — i.e., a single merchant or a script running in a storefront/theme-app-extension context, no privileged access needed. Exploitability depends on obtaining a validly-signed-but-wrong-audience token (e.g., from a differently configured app sharing infrastructure/secrets, or a leaked token from another install using the same secret), which somewhat limits practical likelihood but does not require MITM or secret leakage of *this* app's own key — it only requires a token signed with the same HMAC secret but a different intended audience.

### Recommendation
Remove or gate the `checkAudience: false` override in `authenticateExtensionFactory`, or at minimum add an explicit warning/require an alternate binding check (e.g., verify `shop` domain against an expected value, or validate `aud` against a known list of valid API keys for the app) before trusting the decoded payload's `shop`/`sub` claims.

### Proof of Concept
1. Two Shopify app instances (App A, intended; App B, attacker's own installed app) are configured with the same `apiSecretKey` (e.g., via a shared secrets store misconfiguration, or the attacker discovers/derives the same key used for a differently-scoped app instance).
2. Attacker obtains a valid App-Bridge session token issued for App B (`aud = App B's apiKey`), signed with the shared secret.
3. Attacker sends this token as the session-token header to App A's `authenticate.public.checkoutExtension`/`public.customerAccountExtension` endpoint.
4. `validateSessionToken` → `decodeSessionToken(token, {checkAudience: false})` succeeds because signature verification passes and `aud` is never compared to App A's `apiKey`.
5. The extension handler proceeds using the `shop`/`sub` claims from the App-B-scoped token, treating the request as authenticated for App A.

I was unable to fully confirm whether `apiSecretKey` sharing across differently-configured app instances is a realistic deployment scenario in this specific codebase's supported hosting patterns (e.g., multi-app-per-secret setups) — this affects the practical likelihood assessment. I also examined but ruled out the webhook-HMAC/domain-header binding as a weaker analog, since Shopify's webhook HMAC scheme not including the shop-domain header in the signed payload is inherent, documented Shopify platform behavior (not a code defect introduced by this repository), and exploiting cross-tenant replay there would require either knowledge of the shared `apiSecretKey` or MITM/log-capture of a legitimate webhook delivery — both explicitly excluded by the validation rules.
