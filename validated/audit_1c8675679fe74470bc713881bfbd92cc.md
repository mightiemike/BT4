## Title
Backup/restore transaction verification never authenticates `WriteSet` bytes against the accumulator-proven `TransactionInfo.state_change_hash` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionListWithProof::verify` (used by the backup/restore chunk-loading path in `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`) authenticates transaction hashes, event root hashes, and the transaction-accumulator range proof, but it never checks that the `WriteSet` loaded from the backup file hashes to the `state_change_hash` field carried inside the (accumulator-proven) `TransactionInfo`.

### Finding Description
In `LoadedChunk::load` [1](#0-0) , the transaction, `TransactionInfo`, events, and `WriteSet` are all deserialized independently from the same backup record, and the `write_sets` vector is kept aside from the `TransactionListWithProof` used for verification: [2](#0-1) .

The verification call, `txn_list_with_proof.verify(ledger_info.ledger_info(), Some(manifest.first_version))?`, dispatches to `TransactionListWithProof::verify` in `types/src/transaction/mod.rs` [3](#0-2) . That function checks:
- the first-version alignment,
- length equality between transactions and transaction infos,
- `txn.committed_hash() == txn_info.transaction_hash()`,
- the accumulator range proof against `ledger_info.transaction_accumulator_hash()`,
- (if present) event lists against `txn_info.event_root_hash()`.

It never computes `CryptoHash::hash(write_set)` and compares it to `txn_info.state_change_hash()`. Since `write_sets` is not even part of the `TransactionListWithProofV2` struct that gets verified (it's tracked separately in `LoadedChunk`), the write sets loaded from the backup archive are unauthenticated data with respect to the trusted, accumulator-anchored `TransactionInfo`.

By contrast, `TransactionOutput::ensure_match_transaction_info` (used only in the *replay-verify* path, when `VerifyExecutionMode::should_verify()` is true) does check `write_set_hash == txn_info.state_change_hash()` [4](#0-3) , but this path is opt-in and re-executes the VM; it is not exercised by ordinary (non-replay, "load-and-persist") transaction restore, and the same function's own comment documents that even this replay-verification comparator omits checkpoint-hash checks: [5](#0-4) .

The restored write sets are subsequently persisted verbatim as committed ledger data via `save_transactions`/`WriteSetDb::put_write_set` and can even be replayed into state via `calculate_state_and_put_updates` during KV-only restore: [6](#0-5) .

### Impact Explanation
A corrupted or malicious backup source (compromised backup storage, MITM on backup transport, or a buggy backup writer) can supply an arbitrary `WriteSet` for any transaction record while keeping the transaction body/hash and events untouched. `TransactionListWithProof::verify` will accept the chunk because none of its checks touch the write set, and the accumulator range proof only binds `TransactionInfo` hashes (which include `state_change_hash`, but that field is never cross-checked against the actual bytes being restored). The restoring node then durably commits the forged write set into `WriteSetDb` and (in KV-replay mode) folds it into the JellyfishMerkle-derived state store via `calculate_state_and_put_updates`, producing ledger/state data that diverges from what was actually authenticated by consensus/validator signatures over the `LedgerInfo`. This is a direct "committed state differs from the correct VM result / corrupts durable ledger data" impact, and it also breaks the authenticated-API guarantee since API responses (e.g. `WriteSetChange`s served for that version) would reflect the forged data while claiming to be backed by proof-verified transaction info.

### Likelihood Explanation
Exploitation requires control over, or corruption of, the backup archive contents (e.g. a malicious/compromised backup storage backend or transport), which is a real but non-default threat model for node operators restoring from third-party or shared backups (this is explicitly why `epoch_history.verify_ledger_info` and the accumulator range proof exist — to make backups trustlessly verifiable). The bug undermines exactly that trustless-verification guarantee for the write-set component, so likelihood is meaningful for any restore that consumes an untrusted or tampered backup, and unbounded/silent since no error is raised.

### Recommendation
In `TransactionListWithProof::verify` (or in `LoadedChunk::load` immediately after loading), compute `CryptoHash::hash(write_set)` for every `write_set` and assert it equals the corresponding `transaction_infos[i].state_change_hash()` before accepting the chunk, mirroring the check already performed in `TransactionOutput::ensure_match_transaction_info`. This should be enforced unconditionally in the load/verify path used by both `TransactionRestoreController`/`TransactionRestoreBatchController` and `ReplayVerifyCoordinator`, not only under `VerifyExecutionMode`.

### Proof of Concept
Conceptual (index-level) PoC, given repo access is required to run it fully:
1. Take a valid transaction backup chunk (manifest + transaction file + proof file) for some version range.
2. In the transaction file, replace the serialized `WriteSet` bytes for one record with a different, arbitrary write set (leave the `Transaction`, `TransactionInfo`, `PersistedAuxiliaryInfo`, and events untouched so `transaction_hash`/`event_root_hash` still match).
3. Run `TransactionRestoreController`/`TransactionRestoreBatchController::run()` against this tampered chunk with a valid `epoch_history`/`ledger_info`.
4. Observe `LoadedChunk::load` succeeds (`txn_list_with_proof.verify` passes because it never checks write-set hashes), and the tampered write set is persisted via `restore_utils::save_transactions` into `WriteSetDb` (and folded into state during KV replay), producing ledger data inconsistent with the originally committed, validator-signed transaction.

Note: I was not able to fully re-inspect `storage/aptosdb/src/backup/restore_utils.rs` end-to-end in this session (tool errors on the final read attempts) to double-check whether some other call site independently re-verifies write-set hashes before `save_transactions`; based on all code paths found, no such check exists, but this should be confirmed by grepping for any additional `state_change_hash` comparison guarding the restore write path before treating this as fully conclusive.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
}
