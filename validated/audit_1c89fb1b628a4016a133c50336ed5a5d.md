### Title
Exchange bancor-formula `pow()` computation can diverge across platforms, causing consensus state divergence - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`, `platform/src/main/java/{arm,x86}/org/tron/common/math/MathWrapper.java`)

### Summary
The Bancor-relay exchange math in java-tron (`ExchangeProcessor`) computes fractional exponents via `Math.pow()`/`StrictMath.pow()` exactly like PoolTogether's PRBMath `pow()`. Unlike Solidity fixed-point `pow()`, this is a native floating-point call whose result can differ across CPU architectures (the codebase itself ships a hand-maintained table of historically divergent ARM-vs-x86 `Math.pow()` outputs), which is a direct instance of the "pow() returns inconsistent values" bug class from the external report, but manifested as a cross-platform consensus-divergence bug rather than a fixed-point rounding bug.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the Bancor relay-token conversion using `Maths.pow(base, exponent, useStrictMath)`: [1](#0-0) [2](#0-1) 

`Maths.pow` dispatches to either `MathWrapper.pow` (`Math.pow`, JIT/hardware-intrinsic, platform-dependent) or `StrictMathWrapper.pow` (`StrictMath.pow`, deterministic fdlibm implementation), depending on a chain configuration flag: [3](#0-2) 

The ARM build of `MathWrapper` contains a hardcoded lookup table (`powData`) of specific `(base, exponent) -> result` overrides for dozens of real mainnet block heights, explicitly compensating for cases where `Math.pow()` on ARM produced a different bit pattern than on x86 for the exact same inputs used by this exchange formula: [4](#0-3) 

The x86 build simply calls `Math.pow` directly with no such compensation: [5](#0-4) 

This proves the exact bug class from the report already materialized in production: the non-strict `pow()` path is not guaranteed to return the same value across all validating nodes, and only *previously observed* divergent inputs were patched by hardcoding their outputs. Any new attacker-influenced `(base, exponent)` pair not already present in the compensation table can still produce divergent `Math.pow()` results between ARM and x86 (or between different JVM vendors/versions/JIT states) nodes.

The exchange path is reachable by any unprivileged user through `ExchangeTransactionActuator`, which calls `ExchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`, itself calling into `ExchangeProcessor` when the "hardened" calculation path is not active: [6](#0-5) [7](#0-6) 

A user fully controls `sellTokenQuant` (and can create/inject arbitrary exchange balances via `ExchangeCreateActuator`/`ExchangeInjectActuator`), which directly determines the `base` argument (`1.0 + quant/newBalance`) fed into `pow()`. This gives an attacker the ability to search off-chain for input ratios that are known/likely to produce architecture-dependent `Math.pow()` divergence and are not present in the hardcoded compensation table, then submit an `ExchangeTransactionContract` with that ratio.

### Impact Explanation
If different super representative / full nodes (running on different CPU architectures, JVM vendors, or JIT optimization states) compute different `anotherTokenQuant` for the same transaction, they will each apply a different resulting `firstTokenBalance`/`secondTokenBalance` and a different `AccountCapsule` balance/asset delta: [8](#0-7) 
This produces a state-root/consensus divergence (chain fork) or, at minimum, an accounting error in Exchange/account balances — the same class of impact ("invalid-state/divergence") that made the original PoolTogether finding a confirmed, mitigated Medium-severity issue.

### Likelihood Explanation
The likelihood is bounded by the fact that this exact bug class has already occurred in production (evidenced by the extensive hardcoded `powData` remediation table spanning many mainnet block heights), and the mitigation (`StrictMathWrapper`/`SafeExchangeProcessor`, gated by the `allowStrictMath` and `AllowHardenExchangeCalculation` dynamic parameters) is a governance-controlled proposal rather than an unconditional code fix: [9](#0-8) [10](#0-9) 
Until both hardening flags are enabled network-wide, any node still running the legacy non-strict `MathWrapper.pow` path (or any newly-introduced JVM/hardware combination whose `Math.pow` diverges from the values baked into the historical table) is exposed. An unprivileged user can trigger the vulnerable code path with an ordinary `ExchangeTransactionContract`.

### Recommendation
- Ensure `AllowStrictMath` and `AllowHardenExchangeCalculation` are activated on all networks (mainnet, Nile, private chains) so that `ExchangeCapsule.transaction` always routes through `SafeExchangeProcessor`'s deterministic `BigDecimal`/`StrictMathWrapper` computation rather than the legacy `ExchangeProcessor`/`MathWrapper.pow` path.
- Remove/deprecate the platform-specific `MathWrapper` implementations and hardcoded `powData` compensation table entirely once the hardened path is mandatory, since relying on an incomplete manually curated list of "known bad" inputs is not a sound mitigation against unseen divergent inputs.
- Add consensus tests that run the exchange formula across multiple CPU architectures/JVMs to catch any remaining `Math.pow` divergence before it reaches mainnet.

### Proof of Concept
1. An unprivileged user creates or uses an existing `Exchange` pair via `ExchangeCreateActuator`/`ExchangeInjectActuator`, choosing `firstTokenBalance`/`secondTokenBalance` values.
2. The user submits an `ExchangeTransactionContract` with a `tokenQuant` value chosen so that `base = 1.0 + quant/newBalance` is a value for which `Math.pow(base, 0.0005)` (or `2000.0`) is known to differ between hardware/JVM implementations (e.g., via off-chain fuzzing analogous to the entries already recorded in `platform/src/main/java/arm/org/tron/common/math/MathWrapper.java`, but for a combination not yet present in that table).
3. If the network has not activated `AllowStrictMath`/`AllowHardenExchangeCalculation`, nodes running on different CPU architectures compute different `anotherTokenQuant` in `ExchangeProcessor.exchangeFromSupply`, leading to differing account balances and exchange pool balances being persisted, causing a chain state divergence/fork.

**Note:** I could not fully verify the current on-chain/default activation status of `AllowStrictMath`/`AllowHardenExchangeCalculation` (i.e., whether they are enabled by default in `reference.conf`/genesis parameters or require a committee proposal to be activated), since `DynamicPropertiesStore.java`'s relevant getter/default-value code was not returned by the search tool. This detail affects whether the vulnerable code path is currently reachable on live TRON mainnet or only on chains/testnets where the hardening proposal has not yet passed.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
