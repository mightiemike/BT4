### Title
DoS in `ExchangeInjectActuator.execute` via intermediate multiplication overflow before division mismatched with `doValidate`'s safe BigInteger check - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` validates a TRX/token exchange injection using safe `BigInteger` arithmetic in `doValidate()`, but `execute()` independently recomputes the swap amount using raw `long` overflow-checked multiplication (`multiplyExact`/`floorDiv`) on the *pre-division* product. This mirrors the reported Tapioca `Market._isSolvent` bug class: the intermediate product `secondTokenBalance * tokenQuant` can overflow `long` even when the final (correct) quotient is small and within limits, causing a legitimate, already-validated transaction to fail at execution time.

### Finding Description
`doValidate()` computes the counter-token amount safely with `BigInteger`: [1](#0-0) 

But `execute()` recomputes the same value independently using primitive-`long` `multiplyExact`/`floorDiv` on the raw balances and quantity, not reusing the validated `BigInteger` result: [2](#0-1) 

Because `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`) is computed as a raw `long` product *before* dividing by the other balance, this intermediate value can exceed `Long.MAX_VALUE` (~9.22e18) even though the mathematically correct final quotient (`anotherTokenQuant`) is small and well below `dynamicStore.getExchangeBalanceLimit()`. `doValidate()`'s `BigInteger` path does not have this limitation, so a transaction can pass validation and then throw `ArithmeticException` inside `execute()`: [3](#0-2) 

This is structurally identical to the reported bug class: `amount = (share * totalAmount) / totalShares_` overflowing in the multiply-before-divide pattern even when the final result is in-range, causing reverts of otherwise-valid user actions. Notably, `ExchangeWithdrawActuator` avoids this pattern in `execute()` by also using `BigInteger`: [4](#0-3) 
which highlights the asymmetry/inconsistency in `ExchangeInjectActuator`.

### Impact Explanation
Any unprivileged account can trigger `ExchangeInjectContract` (via `TransactionCapsule`/broadcast, processed by `ExchangeInjectActuator`). For exchange pools with sufficiently large token balances (well within `getExchangeBalanceLimit()`, which defaults to a large value permitting balances up to ~1e15), a legitimate, validate-passing inject transaction will throw `ArithmeticException` during `execute()`, get wrapped into `ContractExeException`, and fail on-chain. This is a functional Denial-of-Service on core exchange market functionality: legitimate users' inject transactions are rejected/reverted purely due to an internal computation artifact, not because the operation is actually invalid — consuming bandwidth/fee for a doomed transaction and freezing the ability to interact with that exchange pool once balances grow large enough.

### Likelihood Explanation
The trigger condition (`balance * quant` overflowing 64-bit `long` while the true quotient stays small) is easily reached once token balances and inject quantities scale into the 1e9–1e15 range, which is plausible for popular TRC10/TRX exchange pools approaching `getExchangeBalanceLimit()`. No special privileges are required — only an account holding sufficient balance/asset amount to submit a valid-looking `ExchangeInjectContract`.

### Recommendation
Make `execute()` reuse the same safe computation path as `doValidate()` (i.e., compute `anotherTokenQuant` via `BigInteger` multiply-then-divide, as `ExchangeWithdrawActuator.execute()` already does), rather than recomputing independently with primitive `multiplyExact`/`floorDiv` on the raw pre-division product. This removes the intermediate-overflow window entirely and keeps `validate()`/`execute()` consistent.

### Proof of Concept
1. Create/inject an exchange pool where `firstTokenBalance` and `secondTokenBalance` are large (e.g., both near 1e15, within `getExchangeBalanceLimit()`).
2. Submit `ExchangeInjectContract` with `tokenQuant` also large (e.g., ~1e15), such that the true result `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` remains within `getExchangeBalanceLimit()` (e.g., balances are proportionate so the quotient stays small).
3. `doValidate()` passes because it computes `anotherTokenQuant` via `BigInteger.multiply().divide()` and it is within limits: [5](#0-4) 
4. `execute()` recomputes with `multiplyExact(secondTokenBalance, tokenQuant)` on raw `long`s: [6](#0-5) 
   Since `secondTokenBalance * tokenQuant` alone (before dividing by `firstTokenBalance`) exceeds `Long.MAX_VALUE`, `multiplyExact` throws `ArithmeticException`.
5. This is caught and the transaction fails with `ContractExeException`, even though `doValidate()` deemed it a legitimate, in-limit exchange injection: [7](#0-6)
