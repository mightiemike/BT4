### Title
Deterministic-account receiver spoofing via meta-transactions bypasses receiver validation on pre-v85 protocol versions - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/actions.rs`)

### Summary
Analogous to the Juicebox `borrowFrom` exploit — where a caller-supplied `REVLoanSource` struct (`.terminal`/`.token`) was checked against the wrong context, letting an attacker forge accounting and skip the oracle — nearcore's meta-transaction (`DelegateAction`) validation for `DeterministicStateInitAction` historically validated the **outer transaction's** `receiver_id` against the derived deterministic account id instead of the **inner delegate action's** `receiver_id`. This is the same bug class: a caller-controlled routing/context field is checked against the wrong reference, letting a crafted inner action target an account different from the one that passed validation.

### Finding Description
Deterministic accounts (NEP-616) require that `DeterministicStateInitAction.state_init` derive exactly to the receiver id it is delivered to; this is enforced by `validate_actions`/`InvalidDeterministicStateInitReceiver` in `runtime/runtime/src/action_validation.rs`. When the action is wrapped in a `DelegateAction` (a meta-transaction), the outer `SignedTransaction.receiver_id` is the delegate-action account (e.g. `det_account_b`), while the actual execution target is `delegate_action.receiver_id`, which can be set independently by the meta-transaction sender.

The pre-fix code path validated the *outer* tx receiver against the derived id — which trivially matches, since the relayer/tx sender controls both the outer receiver and the `state_init` payload — while leaving the *inner* `delegate_action.receiver_id` (a separate, attacker-influenced field) unchecked at that stage. This is documented directly in the regression test: [1](#0-0) 

The exploit construction confirms the caller supplies a mismatched pair of accounting-relevant fields (`state_init` for one account, `receiver_id` targeting a different account), directly mirroring the Juicebox pattern of a caller-supplied struct whose fields are inconsistently cross-validated: [2](#0-1) 

The fix is gated behind `ProtocolFeature::FixDelegatedDeterministicStateInit`, activated at protocol version 85: [3](#0-2) 

Protocol-version-gated fixes only apply once the network has upgraded past the activation version. The codebase's `MIN_SUPPORTED_PROTOCOL_VERSION` is 83, meaning this same binary is designed to keep processing chunks at protocol versions 83 and 84 — versions where `FixDelegatedDeterministicStateInit` is *not yet* enabled and the vulnerable receiver-matching logic in `validate_actions`/`apply_delegate_action` is exercised as originally written: [4](#0-3) 

The dispatch/execution path that ultimately spawns the mismatched inner receipt is `apply_delegate_action`, which builds a new receipt from `delegate_action.receiver_id()` and the delegate's own actions after only checking sender-id, signature, and expiry — not that the inner receiver was independently re-validated against the deterministic derivation at initial admission time for that protocol version: [5](#0-4) 

### Impact Explanation
If a shard/validator set is still running protocol version 83 or 84 (both within `MIN_SUPPORTED_PROTOCOL_VERSION..PROTOCOL_VERSION`), an attacker can craft a meta-transaction whose outer receiver matches one deterministic account's derived id (satisfying the buggy initial tx-admission check) while the inner `DelegateAction.receiver_id` targets a *different* deterministic account. Depending on how far execution proceeds before the later `validate_receipt` re-check catches the mismatch, this could let a `DeterministicStateInitAction` write global-contract-code/state associations, or route deposits/fees, against an account the attacker did not correctly derive/own — analogous to Juicebox's forged accounting context that let the attacker borrow against inflated state. This is a state-transition-correctness / access-control issue reachable directly from a single submitted (relayed) meta-transaction.

### Likelihood Explanation
Exploitability depends entirely on network protocol version: on any chain/testnet still at protocol version 83–84 (which this binary explicitly supports per `MIN_SUPPORTED_PROTOCOL_VERSION = 83`), the condition is live and reachable by any unprivileged transaction signer acting as a meta-transaction relayer, with no special privileges needed — matching the required "unprivileged transaction signer/meta-transaction sender" attacker model. Once the network is on v85+, the second-layer `validate_receipt` check (confirmed by the passing post-fix test) prevents actual state corruption, limiting impact to failed/rejected receipts. I could not fully verify from the index which protocol version is actually live on the target network, so likelihood should be treated as conditional on that fact.

### Recommendation
Ensure `FixDelegatedDeterministicStateInit` is unconditionally applied (i.e., remove the protocol-version gate, or raise `MIN_SUPPORTED_PROTOCOL_VERSION` to ≥85) so that inner `DelegateAction.receiver_id` is always validated against the derived deterministic account id at initial transaction/action validation, not only at receipt-unpacking time, regardless of which protocol version the chunk producer nominally negotiates.

### Proof of Concept
The existing regression test in the repository demonstrates the exploit end-to-end pre-fix (deploy `det_account_b`, grant it a full-access key via a nested promise, then submit a `SignedTransaction` whose outer `receiver_id = det_account_b` but whose `DelegateAction.receiver_id = det_account_a`, with `state_init` derived for `det_account_b`): [6](#0-5) [7](#0-6)

fn try_meta_tx_deterministic_receiver_exploit(
    protocol_version: ProtocolVersion,
) -> Result<FinalExecutionOutcomeView, InvalidTxError> {
    let mut env = TestEnv::setup_with_version(Balance::from_near(100), protocol_version);
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let (_state_init_a, det_account_a) = env.new_deterministic_account_with_data(small());
    let (state_init_b, det_account_b) = env.new_deterministic_account_with_data(big());
    assert_ne!(det_account_a, det_account_b);

    // Deploy det_account_b and add a full-access key so it can act as meta_tx_sender.
    let user_signer = create_user_test_signer(&env.user_account());
    let storage_balance = env.balance_for_storage(state_init_b.clone());
    let deploy_tx = SignedTransaction::deterministic_state_init(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        env.get_tx_block_hash(),
        state_init_b.clone(),
        storage_balance,
    );
    env.run_tx(deploy_tx);

    let meta_tx_sender_signer = create_user_test_signer(&det_account_b);
    let pk_base64 = near_primitives_core::serialize::to_base64(
        &borsh::to_vec(&meta_tx_sender_signer.public_key()).unwrap(),
    );
    let add_key_args = serde_json::json!([
        { "batch_create": { "account_id": det_account_b.as_str() }, "id": 0 },
        {
            "action_add_key_with_full_access": {
                "promise_index": 0,
                "public_key": pk_base64,
                "nonce": 0
            },
            "id": 0,
            "return": true
        }
    ]);
    let add_key_tx = SignedTransaction::call(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        Balance::from_near(2),
        "call_promise".to_owned(),
        serde_json::to_vec(&add_key_args).unwrap(),
        Gas::from_teragas(300),
        env.get_tx_block_hash(),
    );
    env.run_tx(add_key_tx);

    // Craft the exploit: outer_tx.receiver = det_account_b = derive(state_init_b).
    // Old check: det_account_b == derive(state_init_b) passes.
    // The delegate action targets det_account_a, which is the wrong account.
    // In no protocol version can this ever be allowed to be executed successfully.
    let relayer = env.independent_account();
    let relayer_signer = create_user_test_signer(&relayer);
    let inner_action = Action::DeterministicStateInit(Box::new(DeterministicStateInitAction {
        state_init: state_init_b,
        deposit: Balance::ZERO,
    }));
    let delegate_nonce = env.next_nonce_for(&det_account_b);
    let delegate_action = DelegateAction {
        sender_id: det_account_b.clone(),
        receiver_id: det_account_a,
        actions: vec![NonDelegateAction::try_from(inner_action).unwrap()],
        nonce: delegate_nonce,
        max_block_height: 1_000_000,
        public_key: meta_tx_sender_signer.public_key(),
    };
    let signed_delegate_action =
        SignedDelegateAction::sign(&meta_tx_sender_signer, delegate_action);
    let tx = SignedTransaction::from_actions(
        env.next_nonce(),
        relayer,
        det_account_b,
        &relayer_signer,
        vec![Action::Delegate(Box::new(signed_delegate_action))],
        env.get_tx_block_hash(),
    );
    env.try_execute_tx(tx)
}
