### Title
`CalculateGasCost` truncates the EIP-1559 effective gas price down, systematically under-charging users and under-burning protocol fees - (File: x/uexecutor/keeper/fees.go)

### Summary
`Keeper.CalculateGasCost` (x/uexecutor/keeper/fees.go) converts the `feemarketKeeper.GetBaseFee` `LegacyDec` value into an integer effective gas price via `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))`, which is an integer floor division rounding *down*. This value is then multiplied by `gasUsed` and the resulting `gasCost` is deducted (and burned) from the UEA/recipient in `DeductGasFeesFromReceipt`. Analogous to the Mellow `ratiosX96Value` bug, where a denominator used to compute user withdrawal was rounded down (favoring the withdrawer over the vault), here the fee/cost owed by the user for consuming protocol-provided gas is rounded down, favoring the payer (attacker-controlled UEA) at the expense of the protocol's fee-burn accounting.

### Finding Description
`CalculateGasCost` at [1](#0-0)  takes `baseFee` (a `sdkmath.LegacyDec`) and does:
```go
baseFeeBig := baseFee.BigInt()
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
```
The code comment asserts that "the base fee is always a whole number of upc -- no fractional upc exists," implying this `Div` is a lossless "unwrap" of the LegacyDec fixed-point encoding [2](#0-1) . That assumption is external to this scoped code: `baseFee` is produced by the `cosmos/evm` feemarket module's `GetBaseFee`, which stores/adjusts the base fee as a general `LegacyDec` (subject to EIP-1559-style multiplicative adjustment by elasticity/denominator constants each block). There is no invariant enforced anywhere in this repository's scope guaranteeing the resulting `LegacyDec` is always an exact multiple of `1e18` — if the feemarket's block-to-block adjustment ever produces a base fee with a nonzero fractional upc component (e.g. `1000000000.4 upc` scaled internally), `Div` silently truncates that fraction toward zero rather than rounding up.

This truncated `effectiveGasPrice` is then multiplied by `gasUsed` to produce `gasCost` [3](#0-2) , and `DeductGasFeesFromReceipt` burns exactly this (under-computed) amount from the UEA/recipient account via `DeductAndBurnFees` [4](#0-3) . Every unit of gas used, the fractional-upc shortfall compounds with `gasUsed`, so the deficit is not a one-wei rounding artifact but scales with gas consumption — the same "denominator/price rounds down, so the amount extracted from the payer is understated" pattern as the Mellow report, except here the "vault" is the protocol's fee-burn/consensus economics instead of an LP vault.

### Impact Explanation
Every `ExecutePayload`/`ExecuteInboundGasAndPayload`/`ExecutePayloadV2` invocation that deducts gas fees from a UEA is affected identically and deterministically by the same rounding rule, since it's driven purely by consensus state (`baseFee`) and is not privileged. This causes systematic under-collection (and thus under-burn) of the fee that the protocol's tokenomics rely on to reflect real gas cost, benefiting every unprivileged, ordinary user (or contract) executing payloads on Push Chain, at the expense of protocol fee accounting invariants. Reproducing the exact `ratiosX96Value` severity (an M-level rounding-direction bug affecting protocol solvency/accounting) requires the underlying feemarket base fee to actually carry a fractional-upc component in practice.

### Likelihood Explanation
Likelihood is *low-to-uncertain* because the fees.go comment claims (without repo-level enforcement) that `baseFee` is always guaranteed to be a whole number of `upc` — this guarantee actually depends entirely on the external `cosmos/evm` feemarket module's base-fee update algorithm, which is out of this repository's scope and was not verifiable from the indexed code. If the feemarket module genuinely always keeps `baseFee` at an exact `1e18` multiple (e.g., because it re-rounds after every adjustment), this `Div` never truncates and there is no exploitable rounding here at all — in which case existing behavior preserves the invariant and this is not a valid finding.

### Recommendation
- Do not assume base fee is always an integer number of `upc`; instead round the effective gas price **up** (ceiling) when converting from `LegacyDec` to the integer `upc` amount charged to the user, mirroring the Mellow fix of switching `mulDiv` to `mulDivRoundingUp` for values that reduce what is collected from the payer.
- Concretely, replace the truncating `Div` with a ceiling division, e.g. compute `gasCost` directly as `baseFee.MulInt64(int64(gasUsed)).Ceil().RoundInt()` (Dec-level ceiling) instead of truncating `baseFee` to an integer before multiplying by `gasUsed`, so any fractional-upc component is never silently dropped in the user's favor.
- Add an explicit invariant check that fails loudly (rather than silently truncating) if `baseFee` is not an exact multiple of `1e18`, so the underlying assumption is verified rather than assumed.

### Proof of Concept
Conceptually (not run against a live node, since this requires driving the feemarket base fee to a non-`1e18`-multiple `LegacyDec` value, which is controlled by the external feemarket module and outside verified reach in this session):
1. Cause `feemarketKeeper.GetBaseFee` to return a `LegacyDec` such as `1_000_000_000.4 * 1e18` internally (i.e., a fractional upc component), via ordinary block-to-block EIP-1559 base fee adjustment.
2. A user submits/triggers `ExecutePayload` for a UEA, consuming `gasUsed = N` gas.
3. `CalculateGasCost` computes `effectiveGasPrice = floor(1_000_000_000.4) = 1_000_000_000`, dropping `0.4` upc per gas unit.
4. `gasCost = 1_000_000_000 * N`, which is `0.4 * N` upc less than the economically "true" cost.
5. `DeductAndBurnFees` burns exactly this understated `gasCost` from the UEA, with the shortfall recurring on every payload execution, permanently under-collecting protocol fees in the user's favor.

**Caveat:** I was unable to inspect the `cosmos/evm` feemarket module's base-fee computation (external dependency, not in this repo's indexed scope) to confirm whether `baseFee` can actually take on a non-`1e18`-multiple value in practice. If a Devin agent with full filesystem/dependency access confirms the feemarket module can produce such fractional base fees, this finding is concretely exploitable; if the feemarket module always keeps base fee at whole-upc granularity, this is not materially exploitable and the comment's assumption holds.

```go
func (k Keeper) CalculateGasCost(
	baseFee sdkmath.LegacyDec,
	maxFeePerGas *big.Int,
	maxPriorityFeePerGas *big.Int,
	gasUsed uint64,
) (*big.Int, error) {
	baseFeeBig := baseFee.BigInt()
	// @dev: LegacyDec stores values with 18-decimal precision internally, so 1 upc = 1e18
	// in the LegacyDec representation. Since 1 upc is the smallest denomination (like wei
	// in Ethereum), the base fee is always a whole number of upc -- no fractional upc exists.
	// This division unwraps the LegacyDec encoding back to the actual upc amount.
	// Note: baseFee.BigInt() returns a reference to the internal big.Int; the in-place Div
	// mutates it, which is safe here since baseFee is a local value-type copy.
	baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
```
