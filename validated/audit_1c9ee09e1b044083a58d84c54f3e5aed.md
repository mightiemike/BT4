The strongest reachable analog is in `DeleteAccount`'s beneficiary payout path, which mirrors the audit report's core defect: value is unconditionally routed to a caller-supplied address with no existence/validity check, and if that address turns out invalid the funds are irrecoverably destroyed rather than the action failing safely.

### Title
Unvalidated `beneficiary_id` in `DeleteAccountAction` causes permanent burn of account balance instead of a safe failure - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` pays out the deleted account's remaining balance to `delete_account.beneficiary_id` by constructing a `Receipt::new_balance_refund` unconditionally, without ever checking that the beneficiary account exists. [1](#0-0) 

### Finding Description
When `DeleteAccount` executes, if the account has a positive balance the runtime directly emits a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` — this is a *refund receipt* (`predecessor_id == "system"`) from the moment it is created, not a normal `Transfer` action. [1](#0-0) 

There is no check anywhere in `action_delete_account` that `beneficiary_id` refers to an existing account. Because the payout receipt is already tagged as a system refund, if `beneficiary_id` does not exist, `check_account_existence`/`implicit_creation_allowed` reject a refund that would create the account ("Refund can never create an account"), so the receipt fails with `AccountDoesNotExist`. [2](#0-1) 

Critically, refund receipts are special-cased so that a failure does not spawn any further refund — the deposit is simply burned:
```
let gas_refund_result = if receipt.predecessor_id().is_system() {
    // If the refund fails tokens are burned.
    if result.result.is_err() {
        stats.balance.other_burnt_amount = safe_add_balance(...)?
    }
    ...
``` [3](#0-2) 

This is confirmed by the project's own regression test, which explicitly notes the account must exist "otherwise the balance transfer the delete sends it would come straight back as a refund" (i.e., burned, since a refund's failure burns rather than re-refunds), and sets up the beneficiary account specifically to avoid triggering this path. [4](#0-3) 

This is the direct structural analog of the reported `SdtBlackHole` issue: value is sent to an address taken from user input with no validation that the address is capable of receiving it, and an invalid destination causes the value to be irretrievably lost rather than the operation failing atomically. Contrast this with an ordinary `Transfer` action to a nonexistent account, which fails as a normal (non-refund) action receipt, so `refund_unspent_gas_and_deposits` correctly generates a *new* deposit refund back to the predecessor (`test_refund_on_send_money_to_non_existent_account`), preserving the funds. [5](#0-4)  `DeleteAccount`'s payout deliberately bypasses that safety net by being constructed as a refund receipt from the start.

### Impact Explanation
Any unprivileged account owner who submits `Action::DeleteAccount(DeleteAccountAction { beneficiary_id })` (directly or via a meta-transaction/delegate action) with a `beneficiary_id` that does not correspond to an existing account — due to typo, race (the beneficiary account being deleted between transaction construction and execution), or naive tooling — causes their entire remaining account balance to be permanently burned with no recovery path. This is a concrete, protocol-enforced loss of funds triggered by a single transaction, matching the "permanently frozen/lost funds" impact class.

### Likelihood Explanation
The path is reachable by any account holder deleting their own account; no privileged role or special conditions are required beyond choosing/consuming a `beneficiary_id` that turns out invalid at execution time (plausible via typo, cross-shard delay, or race with the beneficiary account's own deletion in the same or an adjacent block).

### Recommendation
Before emitting the balance-refund receipt in `action_delete_account`, either verify that `beneficiary_id` maps to an existing account and reject/fail the `DeleteAccount` action if not (returning the account intact rather than proceeding), or route the payout through a normal (non-refund) `Transfer`-style receipt whose failure triggers a proper follow-up refund instead of a burn, consistent with how ordinary `Transfer` actions to nonexistent accounts are handled today.

### Proof of Concept
1. Create account `bob.near` with a nonzero balance and no locked stake.
2. Submit `SignedTransaction::from_actions(..., vec![Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near".parse().unwrap() })], ...)` where `nonexistent.near` has never been created.
3. `action_delete_account` removes `bob.near` and pushes `Receipt::new_balance_refund(&"nonexistent.near", account_balance)`. [6](#0-5) 
4. This refund receipt is processed with `predecessor_id == "system"`; `check_account_existence` rejects creating `nonexistent.near` via a refund (`is_refund` branch returns `false`), producing `AccountDoesNotExist`. [2](#0-1) 
5. Because the failing receipt's predecessor is `system`, no further refund is generated; the balance is added to `other_burnt_amount` and permanently lost. [3](#0-2) 
6. This mirrors `refund_may_not_create_universal_account`, which already demonstrates that a `Receipt::new_balance_refund` targeting a nonexistent account fails with `AccountDoesNotExist` without creating the account — confirming the burn path is real and exercised in the existing test suite. [7](#0-6)
