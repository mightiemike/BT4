### Title
Denial of Service via unvalidated attacker-controlled array size in deprecated Cairo0 syscall array reader - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
`read_felt_array` in the deprecated (Cairo0) syscall hint processor reads an array-length felt directly from Cairo VM memory — a value fully controlled by the executing contract's bytecode/calldata — and passes it, converted to `usize`, straight into `felt_range_from_ptr` with no check that the declared size is consistent with the actual remaining VM memory/segment size. This mirrors the `get-ip-range` bug class: an untrusted "range/length" descriptor is expanded into a full collection before the size is validated against the real bounds of the data, allowing a single crafted input to trigger resource exhaustion. [1](#0-0) 

### Finding Description
`read_felt_array` reads `array_size` as a raw `Felt` from the pointer position in VM memory: [2](#0-1) 

This differs from the safer variant used for the newer (Cairo1) syscall path, `read_felt_array` in `crates/blockifier/src/execution/syscalls/hint_processor.rs`, which computes the array size as the *difference between two VM pointers* (`array_data_end_ptr - array_data_start_ptr`), a value inherently bounded by the segments the VM itself allocated: [3](#0-2) 

In the deprecated Cairo0 path, however, `array_size` is an attacker/contract-supplied felt with no independent corroboration against actual segment length before it is used to drive `felt_range_from_ptr`'s read loop. This function is reachable from any Cairo0 contract call that invokes `library_call`/`__execute__`/`call_contract`-style syscalls, since `read_calldata`, which is used to parse `calldata` for deprecated syscall requests, wraps `read_felt_array` directly: [4](#0-3) 

This is directly analogous to the `get-ip-range` vulnerability (GHSA-6q4w-3wp4-q5wf / CVE-2021-27191): in both cases, an untrusted "size"/"range" value is used to eagerly materialize a collection (an IP list there, a `Vec<Felt>` here) before validating that the size is bounded by the actual available/legitimate data, enabling a cheap malicious input to cause a disproportionately expensive allocation or iteration.

By contrast, the codebase's own Cairo1 retdata deserialization path (`CairoArray::try_from` in `apollo_cairo_utils`) explicitly guards against exactly this pattern, validating the declared length against `iter.len()` (remaining felts) before calling `Vec::with_capacity`, with an inline comment describing the exact same threat model: [5](#0-4) 

The absence of an equivalent guard in the deprecated Cairo0 `read_felt_array` path is the root-cause gap.

### Impact Explanation
An attacker able to deploy/declare or invoke a Cairo0 contract that issues a deprecated syscall (e.g. `call_contract`, `library_call`, `deploy`) with a crafted `calldata_size`/`array_size` field pointing to a very large felt (e.g. close to `usize::MAX` after `to_biguint()`/`try_from`) can force the sequencer to attempt to materialize a felt range of that declared size. Depending on `felt_range_from_ptr`'s exact memory-access loop semantics (not independently confirmed within the scope of this scan), this can translate into an attempted massive allocation or an extremely long-running per-element VM memory lookup loop before eventually failing — consuming CPU and/or memory on the sequencer node processing the transaction. This can degrade the sequencer's ability to process transactions in a timely manner (a network availability impact), consistent with CWE-400 resource exhaustion.

### Likelihood Explanation
Reachable directly from a single submitted transaction: any account can declare/deploy a Cairo0 class (still supported by the deprecated syscall path) and invoke it with adversarial calldata designed to set `array_size` to an extreme value, without requiring any special privileges. No proposer, peer, or operator compromise is needed.

### Recommendation
Add an explicit bound check in `read_felt_array` (deprecated syscalls path) that validates `array_size` against the maximum feasible/expected size (e.g., remaining VM memory segment size, or a hard configured cap) before calling `felt_range_from_ptr`, mirroring the guard already implemented in `apollo_cairo_utils::CairoArray::try_from` — reject the syscall with an error instead of attempting to read/allocate an unvalidated attacker-controlled amount of data.

### Proof of Concept
Not independently executed within this scan; the code path was identified via static analysis of `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:931-950`. Conceptually: submit an `Invoke`/`L1Handler` transaction targeting a Cairo0 contract that issues a `library_call`/`call_contract` deprecated syscall whose calldata segment encodes an `array_size` felt far larger than any legitimately allocated segment (e.g., `2^63`), and observe CPU/memory behavior in `felt_range_from_ptr` during execution. Note: I was unable to inspect the full implementation of `felt_range_from_ptr` (in `crates/blockifier/src/execution/execution_utils.rs`) within this session to confirm exactly how it handles out-of-bounds sizes (whether it fails fast per missing memory cell or attempts bulk allocation first); this should be verified before treating the severity as confirmed-High versus a bounded/cheap-fail case.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
}

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
