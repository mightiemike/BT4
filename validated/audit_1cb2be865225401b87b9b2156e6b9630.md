### Title
`sanitizeHost` throws an unhandled `TypeError` on malformed base64-decoded host input, causing a DoS in the auth/host-validation path - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates that the `host` parameter is base64-encoded via a regex, then immediately calls `new URL('https://' + decodeHost(sanitizedHost))` with no try/catch. Since `decodeHost` simply calls `atob`, an attacker can supply base64 that passes the regex but decodes to a string containing WHATWG "forbidden host code points" (e.g. space, `#`, `?`, `@`, control characters), which makes `new URL(...)` throw a `TypeError` that propagates uncaught out of `sanitizeHost`.

### Finding Description
`sanitizeHost` in [1](#0-0)  only checks that `host` matches a generic base64 character-set regex before decoding and parsing it as a URL:
```
const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
  ...
```
`decodeHost` is a thin wrapper around `atob` [2](#0-1) . `atob` will happily decode base64 into arbitrary byte/character sequences, including characters that are invalid inside a URL host component per the WHATWG URL Standard (space, `#`, `?`, `@`, `\`, control characters, etc.). When such a string is passed into `new URL('https://' + decoded)`, the URL parser throws a `TypeError: Invalid URL` for hosts containing forbidden host code points. There is no `try/catch` anywhere in `sanitizeHost` around this call, so the exception is not converted to a `null` return or an `InvalidHostError` — it propagates directly out of the function.

Downstream, `buildEmbeddedAppUrl`/`getEmbeddedAppUrl` call `sanitizeHost(config)(host, true)` with no surrounding try/catch [3](#0-2) , and `redirectToAuth`'s `clientSideRedirect` in shopify-app-express similarly calls `api.utils.sanitizeHost(req.query.host as string)` without a try/catch [4](#0-3) . Neither of these library entry points catches the `TypeError`, so if the host application itself doesn't wrap the call (which none of the shown integration helpers do), the unhandled exception crashes the request or triggers an unhandled promise rejection/500 depending on the runtime.

The existing test suite for `sanitizeHost` only exercises inputs that are valid ASCII strings before base64 encoding [5](#0-4) ; it does not cover base64 payloads that decode to strings with forbidden host code points, so this edge case is untested and unguarded.

### Impact Explanation
This is a request-level Denial of Service: any unauthenticated caller of an endpoint that resolves the embedded app URL or triggers the client-side auth redirect (both of which read `host` from the query string and pass it straight to `sanitizeHost`) can throw an unhandled exception in the process. Depending on the framework/error middleware wrapping the call, this can manifest as an unhandled exception crashing a worker/process (Node) or an ungraceful 500 with a stack trace, which maps to Shopify's "Denial of Service in authentication flow" impact class. It does not by itself forge sessions, tokens, or bypass HMAC/JWT checks — impact is confined to availability/robustness of the host-validation path.

### Likelihood Explanation
No privileged access or secrets are required — an attacker only needs to control the `host` query parameter, which is standard input to embedded-app URL/auth-redirect endpoints. Constructing a base64 string that decodes to a forbidden host code point (e.g. `Buffer.from(' invalid').toString('base64')`) is trivial and fully repeatable. The only precondition is that the calling code path does not itself wrap `sanitizeHost` in a try/catch, which is true for the `getEmbeddedAppUrl`/`buildEmbeddedAppUrl` and `redirectToAuth` code shown in this repo.

### Recommendation
Wrap the `new URL(...)` call inside `sanitizeHost` in a try/catch, returning `null` (or throwing `InvalidHostError` when `throwOnInvalid` is set) on parse failure, so that malformed base64-decoded input can never produce an unhandled exception:
```ts
let hostname: string;
try {
  ({hostname} = new URL(`https://${decodeHost(sanitizedHost)}`));
} catch {
  sanitizedHost = null;
}
```

### Proof of Concept
```ts
import {shopifyApi} from '@shopify/shopify-api';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost should not throw for base64 decoding to invalid host chars', () => {
  const shopify = shopifyApi(testConfig());

  const malformedHost = Buffer.from(' invalid#host').toString('base64');

  // Currently throws TypeError: Invalid URL instead of returning null
  expect(() => shopify.utils.sanitizeHost(malformedHost)).not.toThrow();
  expect(shopify.utils.sanitizeHost(malformedHost)).toBeNull();
});
```
Expected today: the `new URL` call throws `TypeError: Invalid URL`, which propagates out of `sanitizeHost` and fails the test with an uncaught exception rather than returning `null`.
