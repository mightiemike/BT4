### Title
Duplicate `capabilities.TriggerResponse` sends per single gateway trigger message due to missing loop break in `processTrigger` - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
`triggerConnectorHandler.processTrigger` iterates every entry in `payload.Topics` for each registered trigger and sends a `capabilities.TriggerResponse` to `trigger.ch` for every topic that matches `trigger.allowedTopics`, without deduplicating per-trigger. The `break` statement at line 136 only breaks the `select` block, not the outer `for _, topic := range topics` loop, so a single gateway message with N matching topics produces N sends of a `TriggerResponse` carrying the identical `TriggerEventID` (`body.Sender+payload.TriggerEventId`), violating the code's own "can only be triggered once" invariant.

### Finding Description
In `processTrigger` [1](#0-0) , the code loops `for _, trigger := range h.registeredWorkflows` and, for each trigger, loops `for _, topic := range topics`. For every topic present in `trigger.allowedTopics`, provided the sender is allowed and the rate limiter permits it, it constructs a `capabilities.TriggerResponse` with `ID: TriggerEventID` (deterministic from `body.Sender` and `payload.TriggerEventId`) and sends it on `trigger.ch`. The comment at line 135 states "Sending n topics that match a workflow with n allowedTopics, can only be triggered once," but the `break` immediately following only exits the `select { ... }` statement — it does not `break` or `continue` out of the topic loop for that trigger. As a result, if `payload.Topics` contains multiple entries that all exist in a single trigger's `allowedTopics` map, the handler sends one `TriggerResponse` per matching topic, all with the same `TriggerEventID`, into `trigger.ch`.

The rate limiter (`trigger.rateLimiter.Allow(body.Sender)`) is checked per topic, so it does not prevent multiple sends within a single message as long as the limiter allows that many tokens for the sender in that instant; it only throttles overall request rate, not per-message duplication. There is no deduplication of `topic` values or of triggers already matched within this call.

### Impact Explanation
An attacker who is an allowed sender for at least one registered trigger (a normal precondition of using this capability, not a privilege escalation) can submit a single `MethodWebAPITrigger` gateway message with a `Topics` array containing many entries all present in that trigger's `allowedTopics`. This causes repeated enqueuing of duplicate/identical trigger events into the trigger's channel, resulting in (a) duplicate workflow execution for what should be a single triggering event, and (b) rapid filling of the fixed 1000-slot `defaultSendChannelBufferSize` channel [2](#0-1) , which can block further legitimate trigger delivery to that workflow (denial of trigger functionality) once the channel consumer can't keep up.

### Likelihood Explanation
Feasible and repeatable: the only precondition is being a legitimate allowed sender for some registered trigger with more than one entry in `allowedTopics` (a configuration attacker can target since `AllowedTopics` is typically a broader set than a single value) and crafting `payload.Topics` to include duplicates or many of that trigger's allowed topics in one request. This requires no signature bypass, no privilege escalation, and no assumption of malicious nodes — it is directly reachable via `HandleGatewayMessage` → `processTrigger` from any request an allowed sender can submit.

### Recommendation
After a trigger is successfully matched and a `TriggerResponse` is sent for it, break out of the inner `for _, topic := range topics` loop (or track "already fully matched" per trigger and `continue` to the next trigger) so each trigger is sent at most one `TriggerResponse` per `processTrigger` invocation, restoring the intended "can only be triggered once" invariant.

### Proof of Concept
Unit test in `core/capabilities/webapi/trigger/trigger_test.go` style:
1. Register a trigger via `RegisterTrigger` with `AllowedTopics = []string{"t1","t2","t3"}` and `AllowedSenders` including a test sender address.
2. Call `processTrigger` (or `HandleGatewayMessage`) with `payload.Topics = []string{"t1","t2","t3"}` and `body.Sender` = the allowed sender.
3. Drain the returned channel `ch` and assert `len(received) == 1` (expected per invariant) — the test will show `len(received) == 3`, all with identical `Event.ID`, demonstrating the bug.
4. Extend to N=1000 topics to show the channel fills to capacity (`defaultSendChannelBufferSize`) from a single gateway message, and that a subsequent legitimate message from a different sender blocks/fails to enqueue, proving denial of trigger delivery.
