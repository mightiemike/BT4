## Title
`replay_on_archive`/`aptos-debugger`/`aptos-move-cli` replay verification silently accepts a wrong committed state root because `TransactionOutput::ensure_match_transaction_info()` never checks `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info()` [1](#0-0)  is the function used by the archive-replay tool (`storage/db-tool/src/replay_on_archive.rs`), the Aptos debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`) and the CLI transaction-replay command (`aptos-move/cli/src/commands.rs`) to confirm that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` that is authenticated by the ledger/transaction accumulator. The function compares status, gas, write-set hash and event-root hash, but its own doc comment admits it deliberately skips comparing the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields of `TransactionInfo` against the locally recomputed state roots. This is the exact analog of the reported bug class: a value that is supposed to be validated against a correctly-bound base (the true, freshly computed state root) is instead left unchecked/using the wrong (unvalidated) reference, so a corrupted or forged commitment can pass verification.

### Finding Description
`ensure_match_transaction_info` is meant to be the "trust boundary" that proves a re-executed transaction's output matches the on-chain, accumulator-proven `TransactionInfo`. Its own code comment says: [2](#0-1) 

which states this comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)", so tooling built on it "can report a successful replay even when the authenticated position state root diverges from local execution."

Concretely, the function only asserts:
- `status` matches [3](#0-2) 
- `gas_used` matches [4](#0-3) 
- write-set hash equals `txn_info.state_change_hash()` [5](#0-4) 
- event-root hash equals `txn_info.event_root_hash()` [6](#0-5) 

It never checks `txn_info.state_checkpoint_hash()` (the Sparse/Jellyfish Merkle root that authenticates the *entire post-transaction state*), nor `hot_state_checkpoint_hash()`, nor the newer `position_state_checkpoint_hash()` used for the trading-native state feature.

This gap is exercised at three real call sites that all feed into `ensure_match_transaction_info` with the sole purpose of validating a committed/backed-up ledger against a fresh VM execution:
- `db-tool`'s archive replay-verify tool `execute_and_verify`, which reads `expected_txn_info` from a backup/archive and calls the comparator per-transaction: [7](#0-6) 
- `aptos-debugger`'s mismatch printer, which is explicitly designed to surface state divergence for debugging: [8](#0-7) 
- the Move CLI's transaction-replay command, which calls the same comparator right after converting a fresh VM output: [9](#0-8) 

By contrast, the in-process chunk-executor path (`execution/executor/src/chunk_executor/chunk_result_verifier.rs`) does *not* rely on this weak comparator; it uses `LedgerUpdateOutput::ensure_transaction_infos_match`, which does full `TransactionInfo == TransactionInfo` structural equality (including the checkpoint-hash fields) [10](#0-9) , and `DoStateCheckpoint::get_state_checkpoint_hashes` independently validates the checkpoint hash against `known_state_checkpoints` taken from the accumulator-authenticated `TransactionInfo` [11](#0-10) . So the state-root binding *is* enforced in the block/chunk-executor commit path, but it is explicitly *not* enforced by the standalone `ensure_match_transaction_info` helper used by the offline verification/debugging tools above.

### Impact Explanation
This falls squarely under "Authenticated API or state-view output bound to the wrong version, object, or proof context" and "hard-fork-only divergence during commit, replay, restore, or proof verification." The archive replay-verify tool (`db-tool replay-verify` / `replay-on-archive`) exists specifically to catch state divergence between a backed-up/archived ledger and a freshly re-executed VM result — this is one of the primary integrity checks operators run to detect non-determinism, corrupted backups, or maliciously tampered `TransactionInfo` records injected into a backup/archive. Because the comparator silently ignores the state-root-bearing fields, a `TransactionInfo` (and hence an accumulator leaf) whose `state_checkpoint_hash` does not match the real post-execution state root will pass `replay-verify` and `aptos-debugger`/CLI replay checks without any error, even though write-set/events/gas/status match. This means a corrupted or forged state commitment embedded in an archived backup or a debugging session's "expected" `TransactionInfo` set can be accepted as "verified" even though it does not correspond to the actual committed ledger state — exactly the "committed state differs from correct VM result" and "wrong … state proof accepted as valid" impact classes called out in the state-integrity gate. Given `compute_trading_native_state_roots` and hot-state features are being actively rolled out (per the accompanying TODO), this gap will also silently mask divergence in the new `position_state_checkpoint_hash` root during rollout/replay-verify audits meant to catch exactly that kind of regression.

### Likelihood Explanation
High likelihood of being triggered unintentionally (a genuine execution/consensus/storage bug that corrupts the state root while leaving write-set/events/gas/status unaffected — e.g., an under/over-write of state during checkpointing, a hot-state or position-state root computation bug — would go completely undetected by these tools), and it is trivially reachable by anyone who runs `replay-on-archive`, `aptos-debugger`, or the CLI's txn-replay against any archived data, including data sourced from third-party/backup providers. No privileged access is required to trigger the blind spot; it's a passive verification gap that turns a security check into a false-positive-prone stub for the class of bug it is depended upon to prevent.

### Recommendation
Update `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs` to independently compute (or accept as a parameter, where full re-execution state isn't locally available) and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields on `txn_info`, mirroring what `DoStateCheckpoint::get_state_checkpoint_hashes` and `LedgerUpdateOutput::ensure_transaction_infos_match` already enforce in the in-process executor path. At minimum, callers such as `replay_on_archive.rs` and the debugger/CLI tools should be updated to also assert on these checkpoint hashes (via full `TransactionInfo` equality, or by recomputing the state root from the resulting `LedgerState`) before reporting replay success.

### Proof of Concept
1. Take an archived backup (or a debugging "expected" `TransactionInfo` list) where a single transaction's `state_checkpoint_hash` field has been corrupted/forged (e.g., replaced with an arbitrary `HashValue`), while `transaction_hash`, `state_change_hash` (write-set hash), `event_root_hash`, `gas_used`, and `status` are left correct/matching the real VM output.
2. Run `db-tool replay-on-archive` (or `aptos-debugger`/CLI replay) over that version range: `Verifier::execute_and_verify` re-executes the transaction, obtains the correct `TransactionOutput`, and calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ..)` [12](#0-11) .
3. Because `ensure_match_transaction_info` never inspects `state_checkpoint_hash`, the call returns `Ok(())` and the tool reports the version as successfully verified, even though the corrupted `TransactionInfo`'s state root does not match the real, freshly-computed ledger state at that version. An operator relying on this tool to detect archive corruption/state divergence sees a false "all good" result.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())
        {
            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
    }
