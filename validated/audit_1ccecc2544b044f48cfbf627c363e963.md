This is confirmed and well-documented by nearcore's own tests (`refund_may_not_create_universal_account`, `runtime/runtime/src/lib.rs:1047-1054`): a `DeleteAccount`'s `beneficiary_id` is only checked for well-formed syntax, never for existence, and the balance payout is a "free" system refund, so a bad beneficiary destroys the balance instead of aborting the delete.

### Title
Permanent Loss of Account Balance via `DeleteAccount` to a Non-Existent `beneficiary_id` - (File: runtime/runtime/src/actions.rs)

### Summary
`DeleteAccountAction::beneficiary_id` is validated only for syntactic correctness (a well-formed `AccountId`), never for existence, before `action_delete_account` deletes the signer's account and emits a system-refund receipt carrying the entire remaining balance to that beneficiary. If the beneficiary account does not exist and is not implicitly creatable, the follow-up transfer receipt fails, and because it is a "free" system refund receipt, the failure results in the funds being permanently burned rather than returned to the deleted account or the transaction being rejected atomically.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) reads `account_ref.amount()` and, if positive, unconditionally queues `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` [1](#0-0) , then immediately sets `*account = None`, permanently removing the account and its balance from local state [2](#0-1) . There is no check that `beneficiary_id` refers to an existing account, nor that it is distinct from a name that cannot be created implicitly — validation only guarantees the identifier is well-formed (`validate_receipt`/`validate_action_receipt` re-validate the account-id string format, not existence) [3](#0-2) .

When the generated `new_balance_refund` receipt is later processed as a `Transfer` action, `check_account_existence` treats it as a refund (`predecessor_id == "system"`), and `implicit_creation_allowed` explicitly forbids account creation for refunds: "Refund can never create an account" [4](#0-3) . So if the beneficiary account does not exist (e.g. it was mistyped, or has meanwhile been deleted, or is a plain named account that was never created), the refund fails with `AccountDoesNotExist`, matching the exact behavior pinned by the test `refund_may_not_create_universal_account` [5](#0-4) .

Critically, this failure is not "money-safe" the way an ordinary failed transfer is. Refund receipts are processed by `apply_action_receipt`, which special-cases `predecessor_id().is_system()`: "If the refund fails tokens are burned" — the deposit is added to `stats.balance.other_burnt_amount` rather than returned anywhere [6](#0-5) . This matches the documented refund semantics: "If the execution of a refund fails, the refund amount is burnt" [7](#0-6) .

By contrast, a normal (non-refund) `Transfer` action to a non-existent named account fails the whole enclosing action, and per the balance-checker invariant this simply leaves both accounts' balances unaffected, e.g. `test_refund_on_send_money_to_non_existent_account` shows the sender keeps its funds when a same-tx transfer to a missing account fails [8](#0-7) . `DeleteAccount`, however, is architected so the balance payout happens via a follow-up refund receipt decoupled from the delete itself: by the time the refund is attempted, the source account has already been irreversibly deleted (`*account = None`) and its balance is gone from state, with no rollback path connecting the refund's outcome back to the delete.

### Impact Explanation
Any unprivileged holder of a full-access key on their own account (the only actor permitted to submit `DeleteAccount`, since `check_actor_permissions` requires `actor_id == account_id`) [9](#0-8)  can lose their entire remaining NEAR balance by submitting `DeleteAccount { beneficiary_id }` with a `beneficiary_id` that is syntactically valid but does not exist (typo, previously-deleted account, or a plain named account nobody has created). Because the payout is modeled as a free system refund and refunds "can never create an account," the transfer silently fails and the balance is permanently burned instead of being preserved or the delete being rejected. This is concrete, unauthorized, permanent loss of funds — the same class of impact as the external report's "stuck funds" via a missing zero-address-style validation, except here the destination is destroyed by design rather than merely inaccessible.

### Likelihood Explanation
High reachability: it requires a single ordinary signed transaction from the account's own owner containing one `DeleteAccount` action — no cross-account privilege, no validator/relayer cooperation, and no race condition. A simple typo in the beneficiary account id, or targeting an account the user believes exists but does not (e.g., they never actually created it, or it was deleted between crafting and submitting the transaction), is sufficient to trigger the loss.

### Recommendation
Before deleting the account and emitting the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an account that actually exists (or is safely creatable), or otherwise ensure that a failed beneficiary-transfer refund routes the balance back to the deleting account (or fails the whole `DeleteAccount` action) instead of being unconditionally burned via the system-refund failure path in `runtime/runtime/src/lib.rs`.

### Proof of Concept
1. Alice controls `alice.near` with balance `B > 0` and a full-access key.
2. Alice signs `DeleteAccountAction { beneficiary_id: "typo-nonexistent.near" }` targeting `alice.near` (self-signed, satisfying `check_actor_permissions`).
3. `action_delete_account` runs: `account_balance = B > 0`, pushes `Receipt::new_balance_refund("typo-nonexistent.near", B)`, then sets `alice.near`'s account to `None` — `alice.near` is deleted [10](#0-9) .
4. The refund receipt (`predecessor_id = "system"`) is later processed as a `Transfer` to `"typo-nonexistent.near"`. `check_account_existence` sees `is_refund = true`, so `implicit_creation_allowed` returns `false` unconditionally, and the action fails with `AccountDoesNotExist` — reproduced exactly by the existing test `refund_may_not_create_universal_account` [5](#0-4) .
5. Because the receipt's predecessor is "system", the failure path in `apply_action_receipt` adds the full deposit `B` to `other_burnt_amount` instead of refunding it anywhere [6](#0-5) .
6. Result: `alice.near` is gone, `"typo-nonexistent.near"` was never created, and `B` yoctoNEAR is permanently removed from total supply — Alice's entire balance is lost with no recovery path.
