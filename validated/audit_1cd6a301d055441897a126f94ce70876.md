Based on my research, I found a genuine local code issue that is a structural analog to the external report's "stale/incomplete integrity check leads to using bad state" pattern — but manifesting in Aptos's **replay-verification comparator**, not price oracles.

### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify tooling accept a divergent authenticated state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the function used by replay/verification tooling to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` (the record bound into the transaction accumulator and thus the ledger's Merkle-proof chain). It checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it explicitly does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the exact fields that authenticate the state Merkle root(s) committed at checkpoint boundaries.

### Finding Description [1](#0-0) 

The function's own comment acknowledges the gap: [2](#0-1) 

It states: *"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."*

This is used by `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`, both of which are the canonical tools for confirming that re-executing archived/backed-up transaction history reproduces the exact ledger state that was actually committed (including the newer "trading-native"/position state root machinery gated by `compute_trading_native_state_roots`, visible in `execution/executor-types/src/execution_output.rs` and `execution/executor/src/workflow/do_get_execution_output.rs`). The `TransactionInfo` type itself carries these checkpoint hash fields as first-class, hash-committed data [3](#0-2) , meaning they are part of what the transaction accumulator authenticates — but the comparator used to validate replay correctness silently drops them from the equality check.

### Impact Explanation
Because the comparator omits the checkpoint-hash fields, a non-determinism or logic bug that corrupts state-checkpoint root computation (main state root, hot-state root, or the newer position-native state root) — for example introduced by a change to `DoStateCheckpoint`, the hot-state pipeline, or `compute_trading_native_state_roots` — would not be detected by `replay_on_archive` or the debugger's replay-verify path. This directly matches the in-scope impact class "Hard-fork-only divergence during commit, replay, restore, or proof verification": the authenticated, Merkle-proof-bound state root can diverge from what local re-execution actually produces, and the tooling whose job is to catch exactly that divergence will report success anyway. This undermines confidence in replay-based auditing/upgrade-safety checks across the network and could mask a genuine consensus-breaking state-computation bug until it manifests on live nodes.

### Likelihood Explanation
This is a code-confirmed gap (acknowledged directly in a TODO in the source) rather than a hypothetical; it triggers deterministically whenever `replay_on_archive` or the debugger's `ensure_match_transaction_info` path is used against a transaction whose write-set/event hashes still match but whose checkpoint hash(es) do not — i.e., precisely the scenario an attacker or a build regression involving new state-root machinery (hot-state, position-native roots) would produce. It requires no privileged access to trigger — it's a limitation of the verification logic itself.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/expected) against locally recomputed values before enabling any feature (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that depends on these fields for correctness, and update `replay_on_archive`/`aptos_debugger` call sites accordingly.

### Proof of Concept
I was not able to fully trace the exact call sites in `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` in this session (tool errors prevented reading those files in the final iteration), so the precise conditions under which each tool surfaces (or fails to surface) a checkpoint-hash mismatch to the user are not independently confirmed beyond the acknowledged TODO in `types/src/transaction/mod.rs`. This should be verified by inspecting those two call sites directly, along with `DoStateCheckpoint`'s hot-state/position-root computation, before treating this as fully proven end-to-end.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
