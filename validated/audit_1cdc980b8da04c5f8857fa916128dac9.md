### Title
Unbounded native crypto loop in `ShieldedTRC20ParametersBuilder.build()`/`createSpendAuth` allows CPU-exhaustion DoS via oversized `spends` list - ([File: framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java])

### Summary
`ShieldedTRC20ParametersBuilder.build(boolean withAsk)` iterates over the full `spends` list to generate zk-SNARK spend proofs and, when `withAsk=true`, `createSpendAuth` iterates again to compute `librustzcashSaplingSpendSig` for every entry, with no upper bound enforced before these native-crypto loops execute. The only bound check on the number of spends (`spendCount < 1 || spendCount > 2`) lives in `transferParamsToHexString`, which runs only after the expensive per-spend proof/signature loops have already completed.

### Finding Description
`CreateShieldedContractParametersServlet.doPost` parses attacker-supplied JSON into a `PrivateShieldedTRC20Parameters` protobuf and passes it to `wallet.createShieldedContractParameters(...)`, which ultimately populates a `ShieldedTRC20ParametersBuilder`'s `spends` list and calls `build(withAsk)` [1](#0-0) .

Inside `build()`, for `TRANSFER` type, the code loops `for (SpendDescriptionInfo spend : spends)` calling `generateSpendProof(spend, ctx)`, which invokes the native `librustzcashSaplingSpendProof` for every element with no size check [2](#0-1) . If `withAsk` is true, `createSpendAuth(dataHashToBeSigned)` is then called, which again loops `for (int i = 0; i < spends.size(); i++)` invoking `JLibrustzcash.librustzcashSaplingSpendSig` for each entry, also unbounded [3](#0-2) .

The only place that rejects `spendCount > 2` is `transferParamsToHexString`, executed later when building the trigger contract input [4](#0-3) . Because this check occurs after the expensive proof-generation loop (and, when `withAsk`, after the signature loop as well), an attacker-controlled `spends.size()` directly drives the amount of native CPU work performed before any rejection happens. This request path is a plain HTTP JSON servlet (`RateLimiterServlet` only provides IP-based rate limiting, not payload-size/proof-count limiting), so it sits outside TVM energy/bandwidth metering entirely — there is no fee charged proportional to the CPU cost of the SNARK proof/signature operations performed here.

### Impact Explanation
This is a DoS via RPC-API: an unauthenticated client can send a single HTTP POST to `CreateShieldedContractParametersServlet` with a large repeated `spend_description`/spend list, causing the node to perform expensive elliptic-curve/zk-SNARK proof generation and signing operations proportional to the attacker-chosen list length, consuming CPU with no economic cost. Repeated requests can degrade or stall the full node's HTTP API responsiveness.

### Likelihood Explanation
The attacker needs no privileges — just network access to a full node's HTTP API (default-enabled `CreateShieldedContractParametersServlet`). The cost to the attacker is limited to constructing a JSON body with many spend entries (bounded only by the HTTP body size limiter, if configured, and JSON parse limits), which is significantly cheaper than the native cryptographic work triggered server-side. The attack is trivially repeatable.

### Recommendation
Enforce an explicit maximum spends/receives count (e.g., 2) immediately after deserializing `PrivateShieldedTRC20Parameters` and before populating `spends`/calling `build()`, so the check happens prior to any proof-generation or signing loop, not only inside `transferParamsToHexString`.

### Proof of Concept
```
POST /wallet/createshieldedcontractparameters
Content-Type: application/json

{
  "shielded_TRC20_contract_address": "<hex>",
  "spend_description": [ /* N copies of a syntactically-valid SpendDescription-equivalent input */ ],
  "shielded_TRC20_parameters_type": "transfer",
  ...
}
```
Assertion for a fix: sending a request with `spend list length > 2` should be rejected immediately (HTTP 400/invalid-parameter) before any `librustzcashSaplingSpendProof`/`librustzcashSaplingSpendSig` calls occur; measuring server latency for N = 2, 100, 10000 should show constant (near-zero) processing time after the fix, versus linear scaling before it.

Note: I was unable to retrieve the exact body of `Wallet.java`'s `createShieldedContractParameters`-equivalent method (the index did not return its content), so I cannot confirm with certainty whether an additional validation step exists there before `ShieldedTRC20ParametersBuilder.build()` is invoked; this should be verified directly in the full repository before treating the fix as complete.

  private void createSpendAuth(byte[] dataToBeSigned) throws ZksnarkException {
    for (int i = 0; i < spends.size(); i++) {
      if (spends.get(i).expsk == null) {
        throw new ZksnarkException("missing expanded spending key for spend authorization");
      }
      byte[] result = new byte[64];
      JLibrustzcash.librustzcashSaplingSpendSig(
          new LibrustzcashParam.SpendSigParams(spends.get(i).expsk.getAsk(),
              spends.get(i).alpha,
              dataToBeSigned,
              result));
      builder.getSpendDescriptionBuilder(i)
          .setSpendAuthoritySignature(ByteString.copyFrom(result));
    }
  }
