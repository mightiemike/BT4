### Title
Exchange withdraw/inject reverts on legitimate small-amount operations due to rounding-to-zero of the paired token quantity - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The Bancor-style TRC10 `Exchange` withdraw and inject actuators compute the "paired" token quantity (`anotherTokenQuant`) by multiplying the user-supplied quantity by one pool balance and dividing by the other. When the two token balances in the pool are highly imbalanced (which happens naturally with tokens of very different decimals/precision, or pools skewed toward one side), a legitimate, otherwise valid request can compute `anotherTokenQuant == 0`, causing the whole transaction to revert with an explicit validation error rather than silently proceeding. This mirrors the GFX `claimOrder` bug class: a rounding-to-zero result on a division that is unavoidable given integer arithmetic causes revert of an action a user is legitimately entitled to perform.

### Finding Description
In `ExchangeWithdrawActuator.doValidate()`, the paired token amount is computed as: [1](#0-0) 

and identically for the other branch: [2](#0-1) 

If `bigSecondTokenBalance.multiply(bigTokenQuant)` is smaller than `bigFirstTokenBalance` (or vice versa for the other branch), `divideToIntegralValue` truncates to `0`, and the actuator immediately throws:

```
"withdraw another token quant must greater than zero"
```

This is the *unavoidable* rounding-to-zero condition described in the source report: the user requested a valid, non-zero withdrawal of `tokenID`, but because the pool ratio (driven by pool imbalance or by underlying token decimal differences) makes the entitled paired amount round down to less than 1 unit, the whole transaction reverts rather than proceeding (e.g., by simply not crediting the zero-valued side, as the source report's fix recommends: “only transfer the assets if the amount is more than zero”). The identical pattern exists in `ExchangeInjectActuator.doValidate()`: [3](#0-2) 

By contrast, the TRC10 order-book market actuator (`MarketSellAssetActuator`) already handles the exact same rounding-to-zero edge case gracefully by returning the remaining sell-side tokens to the user and marking the order inactive instead of reverting: [4](#0-3) 

This shows the codebase is aware of, and has a design pattern for, the rounding-to-zero problem elsewhere, but the older bancor-style `Exchange` actuators (Inject/Withdraw) do not apply the same graceful handling and instead hard-revert.

### Impact Explanation
A user who holds a balance of `tokenID` in the exchange pool that is small relative to the pool's balance ratio can be permanently unable to withdraw that balance (or a sub-portion of it) via `ExchangeWithdrawActuator`, because any `tokenQuant` they choose that yields `anotherTokenQuant == 0` will revert. In the worst case, if the user's entire remaining position is below this threshold, they cannot withdraw it at all through this path — an accounting/settlement denial-of-service on funds the user is legitimately entitled to, analogous to the original report's "owner unable to collect fee" impact where a legitimate settlement action is blocked purely due to integer rounding. The severity is bounded by the fact that a user can choose to withdraw in larger quantities to avoid the zero-rounding threshold (unlike the original bug where the amount is fully determined by the batch and depositAmount), which reduces but does not eliminate the DoS in dust-balance/high-imbalance scenarios.

### Likelihood Explanation
This requires a pool with a large imbalance between `firstTokenBalance` and `secondTokenBalance` (readily achievable given TRC10 tokens can have wildly different total supplies/precisions, and pool balances drift over time through injects/withdraws/trades) and a user attempting to withdraw/inject a small `tokenQuant` relative to that imbalance. No privileged role or attacker action is required — any unprivileged exchange participant can hit this condition through normal usage, particularly as their remaining balance shrinks to a small residual (dust) amount.

### Recommendation
Apply the same rounding-safe pattern already used in `MarketSellAssetActuator` to `ExchangeWithdrawActuator` and `ExchangeInjectActuator`: instead of hard-reverting when the computed paired quantity rounds to zero, either (a) allow the transaction to proceed while skipping the zero-valued transfer/balance update on the paired side, or (b) surface a way for users to fully withdraw their entire remaining position without being subject to the ratio-based paired-quantity computation (e.g., a "withdraw all" path that doesn't depend on `divideToIntegralValue` yielding a positive integer for `anotherTokenQuant`).

### Proof of Concept
1. Create an `Exchange` pool with a first token balance and second token balance of vastly different magnitude, e.g. `firstTokenBalance = 100_000_000_000L`, `secondTokenBalance = 1L` (achievable over time via repeated `ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeTransactionActuator` calls that skew the ratio, or directly via test setup as in `ExchangeWithdrawActuatorTest`).
2. A user calls `ExchangeWithdrawActuator` with `tokenID = firstTokenID` and a small `tokenQuant` (e.g. `1`).
3. `anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divideToIntegralValue(bigFirstTokenBalance) = 0`.
4. `doValidate()` throws `ContractValidateException("withdraw another token quant must greater than zero")` at [5](#0-4) , and the withdrawal is rejected even though the user holds a legitimate, non-zero pool share expressed in `tokenID`.
5. The existing test `SameTokenNameCloseNotPreciseEnough2` demonstrates this exact revert path is already triggered by small quantities in the test pool: [6](#0-5) .
