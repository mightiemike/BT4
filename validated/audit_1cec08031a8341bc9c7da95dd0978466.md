### Title
Zero allowance for gas-key `FunctionCall` access keys is silently converted to unlimited allowance - ([File: runtime/near-vm-runner/src/wasmtime_runner/logic.rs])

### Summary
The host function `promise_batch_action_add_gas_key_with_function_call` treats an explicit `allowance = 0` the same way `UniV3OracleImpl._getQuoteAmount` treats `po.fee == 0`: as "unset", silently substituting the maximum-privilege default (`None` = unlimited allowance) instead of honoring the caller's intended value of zero.

### Finding Description
In `promise_batch_action_add_gas_key_with_function_call`, the raw `u128` allowance value read from guest memory is converted to an `Option<Balance>` with sentinel semantics identical in spirit to the reported bug: [1](#0-0) 

```rust
let allowance = Balance::from_yoctonear(get_u128(...)?);
let allowance = if allowance > Balance::ZERO { Some(allowance) } else { None };
```

This is documented behavior, not accidental: `docs/RuntimeSpec/Components/BindingsSpec/PromisesAPI.md` explicitly states "If the `allowance` value (not the pointer) is `0`, the allowance is set to `None` (which means unlimited allowance)." [2](#0-1) 

The `FunctionCallPermission.allowance` field is `Option<Balance>` where `None` means unlimited and `Some(x)` means a hard balance cap that is decremented on every use and enforced at the verifier level (`check_and_compute_new_allowance`): [3](#0-2) [4](#0-3) 

There is therefore no way for a contract to use this host function to create a gas-key `FunctionCall` access key with an intentional, enforced allowance of exactly `0` (e.g. a key meant to be able to invoke methods but never spend any balance on gas/fees). Any value of `0` silently upgrades to `None` (unlimited), which for a gas-key path means the key can draw against the account's/gas-key's prepaid balance without the cap the calling contract intended.

This is directly reachable from an unprivileged actor: any account can submit a `FunctionCall` transaction to a contract that internally calls `promise_batch_action_add_gas_key_with_function_call` with an allowance argument of `0`, and the resulting on-chain access key silently becomes unlimited-allowance instead of zero-allowance.

### Impact Explanation
A contract that intends to grant a "spend nothing, but still allowed to call methods" key (allowance = 0, e.g. for keys used purely for identification/authorization gating, or as a safety default before a follow-up top-up) instead grants an unlimited-allowance key. This is a fee/limit bypass: value that should be capped at zero can instead be spent without bound from whichever balance backs the key's allowance (account balance for legacy `FunctionCallPermission` semantics, or the gas key's prepaid pot in the gas-key model). Any contract relying on `allowance == 0` to mean "no spending permitted" is silently defeated, enabling unauthorized value movement/gas spending beyond what the contract author intended to authorize.

### Likelihood Explanation
High reachability, but impact is gated by contract logic: exploitation requires a contract that (a) calls this host function and (b) passes a caller/user-controlled allowance value expecting `0` to mean "no allowance." Since the semantics are silently different from ordinary caller expectations (0 almost universally means "none/no permission" in other systems, as in the original audit finding), contracts built without awareness of this documented quirk are at risk. The primitive itself is fully reachable by any unprivileged transaction signer through a single contract call using standard promise-batch host functions.

### Recommendation
Do not overload `allowance == 0` as a sentinel for "unlimited." Either:
- Require a distinct sentinel (e.g. `u128::MAX` or a separate boolean flag) to signal "unlimited," leaving `0` to mean a literal zero allowance, or
- Document and audit all call sites/consumers of `promise_batch_action_add_gas_key_with_function_call` (and the analogous `promise_batch_action_add_key_with_function_call` path, which should be checked for the same pattern) to ensure they cannot be driven by attacker-controlled input to `0`, and add a runtime check that rejects/clarifies zero-allowance requests rather than silently upgrading them to unlimited.

### Proof of Concept
1. Deploy a contract that exposes a method taking an `allowance: u128` parameter and forwards it verbatim into `promise_batch_action_add_gas_key_with_function_call` when creating a function-call gas key for a caller-supplied public key.
2. An unprivileged account calls this method with `allowance = 0`, expecting the resulting key to have zero spending power.
3. The runtime host function converts `allowance = 0` into `None` (unlimited allowance) as shown in `runtime/near-vm-runner/src/wasmtime_runner/logic.rs:3717-3722`.
4. Querying the resulting access key (e.g. via `ViewGasKeyNonces`/access-key view, following the pattern in `test-loop-tests/src/tests/gas_keys.rs:809-837`, which explicitly passes `"allowance": "0"` and asserts `allowance.is_none()`) confirms the key was created with unlimited allowance instead of the requested zero. [5](#0-4) 
5. The holder of that public key can subsequently spend gas/fees against the associated balance without the zero-cap the calling contract attempted to enforce.

Note: I was unable to fully confirm within the available context whether the sibling function `promise_batch_action_add_key_with_function_call` (non-gas-key variant) contains the identical `allowance == 0 → None` conversion; the grep results indicate it exists in the same file but I did not get to inspect its body directly before running out of iterations. This should be verified as part of remediation, as it is very likely to share the exact same sentinel-collision pattern.

```rust
fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
```
