### Title
Missing input-size validation before `jose.jwtVerify` allows CPU/memory-exhaustion DoS in session-token auth path - ([File: packages/apps/shopify-api/lib/session/decode-session-token.ts])

### Summary
`decodeSessionToken` passes the raw `Authorization: Bearer` value directly into `jose.jwtVerify` with no upper bound on token length or segment size, and no attacker-supplied secret is required to reach this code path. An attacker can send arbitrarily large, well-formed-looking (`x.y.z`) but invalid JWT strings to any endpoint that calls `getSessionTokenHeader`/`validateSessionToken` (including the App Bridge extension endpoint), forcing the server to base64-decode and JSON-parse attacker-controlled payloads before signature verification fails.

### Finding Description
`getSessionTokenHeader` in `packages/apps/shopify-app-remix/src/server/authenticate/helpers/get-session-token-header.ts` simply strips the `"Bearer "` prefix from the `Authorization` header with no length check: [1](#0-0) 

This value flows unchanged through `authenticateExtension` in `packages/apps/shopify-app-remix/src/server/authenticate/public/extension/authenticate.ts`, which requires no prior authentication and calls `validateSessionToken` for any request that includes the header: [2](#0-1) 

`validateSessionToken` forwards the token as-is to `api.session.decodeSessionToken`: [3](#0-2) 

`decodeSessionToken` calls `jose.jwtVerify(token, ...)` with no prior length/format cap on `token`: [4](#0-3) 

There is no size-limiting check anywhere in this call chain (`getSessionTokenHeader`, `validateSessionToken`, `decodeSessionToken`) — a repo-wide search for length/size guards (`MAX_`, `maxLength`, `byteLength`) found none relevant to session-token parsing. Because HMAC/signature verification happens only after `jose` base64url-decodes the header/payload/signature segments and JSON-parses the header and payload, an attacker who has no valid `apiSecretKey` can still force the server to spend CPU/memory decoding and parsing multi-megabyte segments on every request before the signature check fails.

### Impact Explanation
This maps to a denial-of-service in the authentication handler: an unauthenticated attacker can repeatedly send large `Bearer` values to any route protected by `authenticateExtension` (or other session-token authentication paths built on `decodeSessionToken`), consuming disproportionate CPU/memory per request relative to attacker cost, degrading availability of the auth path for all tenants sharing that app process.

### Likelihood Explanation
Preconditions are minimal: only network access to a public endpoint that authenticates via session token (e.g., the checkout/extension endpoint), no secret or prior authentication needed. The attack is trivially repeatable/scriptable (flood of POST/GET requests with large `Authorization` headers), though actual severity depends on host/reverse-proxy header-size limits (e.g., default Node/Express/Nginx header size caps may already restrict header size before it reaches this code) — the library itself provides no defense-in-depth check.

### Recommendation
Add an early length/format check on the token in `getSessionTokenHeader`/`decodeSessionToken` (e.g., reject tokens exceeding a reasonable JWT size such as a few KB, or validate the three-segment structure and per-segment length before calling `jose.jwtVerify`), independent of any upstream reverse-proxy header limits.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/session/__tests__/decode-session-token-dos.test.ts
import {decodeSessionToken} from '../decode-session-token';
import {testConfig} from '../../__tests__/test-config';

test('large garbage bearer token is not rejected early', async () => {
  const config = testConfig();
  const decode = decodeSessionToken(config);

  const hugeSegment = 'A'.repeat(5 * 1024 * 1024); // 5MB base64url-ish segment
  const fakeJwt = `${hugeSegment}.${hugeSegment}.${hugeSegment}`;

  const start = process.hrtime.bigint();
  await expect(decode(fakeJwt)).rejects.toThrow();
  const elapsedMs = Number(process.hrtime.bigint() - start) / 1e6;

  // No size guard exists today, so large inputs are fully decoded/parsed
  // before failing — asserting an upper bound currently fails.
  expect(elapsedMs).toBeLessThan(50); // demonstrates lack of an early-reject size check
});
```

```
POST /checkout-extension-endpoint HTTP/1.1
Authorization: Bearer <5MB>.<5MB>.<5MB>
```
to a route using `authenticateExtensionFactory` reproduces the same unmetered decode/parse cost server-side.
