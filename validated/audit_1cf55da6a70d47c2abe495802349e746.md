### Title
Unbounded full-store serialization in `RpcApiService.listExchanges`/`Wallet.getExchangeList` enables repeated-call DoS, same root cause as `ListProposalsServlet` - ([File: framework/src/main/java/org/tron/core/services/RpcApiService.java])

### Summary
`RpcApiService.listExchanges` calls `Wallet.getExchangeList()`, which iterates the entire `ExchangeStore` and serializes every entry into an `ExchangeList` response with no pagination, size cap, or cursor. This is structurally identical to the `ListProposalsServlet` full-store dump pattern already flagged as a DoS vector, so an unprivileged gRPC client can repeatedly invoke `listExchanges` to force full-store iteration/serialization work on every call.

### Finding Description
`Wallet.getExchangeList()` reads every record from the exchange store (no offset/limit) and builds an `ExchangeList` protobuf, and `RpcApiService.listExchanges(EmptyMessage, StreamObserver<ExchangeList>)` simply forwards to it and streams the full result back to any caller who can open a gRPC channel. There is no per-request authentication/authorization on this call — any unprivileged client can call it. The only mitigation present is the generic gRPC `RateLimiterInterceptor`, which by default assigns each method a `DefaultBaseQqsAdapter` with `QpsStrategy.DEFAULT_QPS_PARAM` (a flat QPS cap, not scaled to the cost of the underlying work) unless a specific override is configured in `rate.limiter.rpc` config for `listExchanges`. This means the CPU/serialization cost of a full-store dump is not accounted for by the limiter — it merely limits requests-per-second, not requests × store-size, so as the exchange store grows (through ordinary market activity, i.e., unprivileged users creating exchanges/trading), the cost per allowed call grows unboundedly. This is exactly the same code shape and same missing control (no pagination on a full-store list RPC) as the previously identified `ListProposalsServlet`/`listProposals` issue.

### Impact Explanation
Concrete impact: RPC-API DoS via CPU/memory exhaustion from repeated full-store serialization, matching the "DoS via RPC-API" bounty class. Because the interceptor rate-limits by call count and not by response size/cost, a growing exchange store combined with the flat per-endpoint QPS allowance still permits sustained CPU/GC pressure on the node proportional to `QPS_ceiling × store_size`, which can degrade or stall the FullNode for other legitimate RPC/API consumers.

### Likelihood Explanation
Preconditions require only a populated `ExchangeStore` (achievable through ordinary, unprivileged market activity — no special role needed) and network access to the node's gRPC endpoint (default exposed port, no non-default config required). The attacker cost is a handful of gRPC calls, gated only by the default per-endpoint QPS limiter, which does not scale with response payload size, so the attack is fully repeatable up to whatever QPS ceiling is configured and remains effective as long as the store is non-trivially sized.

### Recommendation
Add pagination (offset/limit or cursor-based) to both `listProposals`/`getProposalList` and `listExchanges`/`getExchangeList` in `Wallet.java`/`RpcApiService.java`, and/or introduce a cost-aware rate limiter (e.g., weight per response by number of records serialized) for these full-store list RPC endpoints so the two issues are fixed together as one class of bug rather than separately.
