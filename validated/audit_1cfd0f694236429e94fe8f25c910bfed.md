### Title
Repay-specific pause does not halt interest accrual, enabling forced liquidation during a repay-only pause - (File: mainnet/contracts/vault/v0-vault-stx.clar and equivalent vault contracts)

### Summary
The Zest v2 vault contracts expose a `pause-states` tuple with independently settable flags (`deposit`, `redeem`, `borrow`, `repay`, `accrue`, `flashloan`). Interest accrual is only skipped when the dedicated `accrue` flag is paused; pausing `repay` alone does not stop the index from advancing. A borrower can therefore be locked out of `system-repay` while their debt keeps compounding, reproducing the exact bug class described in the external report but through the vault's granular pause flags rather than a single global pause.

### Finding Description
`accrue()` explicitly passes through without updating `index`/`lindex` only when the `accrue` field of `pause-states` is true: [1](#0-0) 

`set-pause-states()` treats the `accrue` flag specially: it forces an `accrue()` before pausing it and jumps `last-update` forward on unpausing to skip the paused window entirely, so debt does not grow while `accrue` is paused: [2](#0-1) 

However, `repay` is a separate, independent flag in the same tuple. `system-repay()` unconditionally calls `(try! (accrue))` first — which runs the normal (non-paused) accrual path whenever `accrue` itself is not paused — and only afterward checks the `repay`-specific guard: [3](#0-2) 

Consequently, if the DAO (via `check-dao-auth`) pauses only `repay` (e.g., to halt withdrawal/repay flows during an incident) while leaving `accrue` unpaused, every call to `system-repay` still runs `accrue`, growing `index`/`total-debt` for all borrowers, then reverts with `ERR-PAUSED`. Borrowers are unable to repay while their debt (and effective health factor) continues to deteriorate — identical in effect to the reported `VaultController` issue, just triggered via a different flag in the same pause tuple. The same pattern (`system-repay` calling `accrue` unconditionally before the `repay`-guard) appears identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, and `v0-vault-usdh.clar`.

### Impact Explanation
Any borrower with an open position becomes unable to service their debt during a `repay`-only pause window, while accrued interest keeps increasing `total-debt` via the unaffected `accrue` path. Once `repay` is re-enabled (or immediately, if `borrow`/liquidation-adjacent checks use the grown debt figure), positions that were previously healthy can be pushed past the liquidation threshold purely due to accrual during the window the user was blocked from repaying — a temporary freezing of the ability to service debt that can convert into a forced liquidation and permanent loss of the user's collateral, matching the High/Critical impact bands (temporary freezing of funds escalating to loss of user collateral via forced liquidation).

### Likelihood Explanation
This requires a DAO governance action (`check-dao-auth`) to set `pause-states` with `repay: true` while `accrue: false` — a plausible, even likely, operational choice (e.g., pausing repayments during an incident investigation without wanting to also freeze interest bookkeeping/treasury fee accrual). No compromise of DAO keys is required; it is a normal use of the exposed `set-pause-states` API that the current code fails to guard against for the `repay` flag the way it explicitly does for the `accrue` flag.

### Recommendation
Mirror the `accrue`-flag handling for the `repay` flag: either (a) make `accrue()` also pass through without advancing `index`/`lindex` whenever `repay` is paused (and jump `last-update` forward on unpause of `repay`, similar to the existing `accrue` unpause logic), or (b) have `system-repay` check the `repay` pause flag before invoking `accrue`, so that borrowers' debt does not silently grow during a period in which they are contractually prevented from paying it down.

### Proof of Concept
1. Borrower deposits collateral and calls `system-borrow`, opening a debt position tracked via `principal-scaled`/`index` in, e.g., `v0-vault-stx.clar`.
2. DAO calls `set-pause-states` with `{ ... repay: true, accrue: false, ... }` — a legitimate, unprivileged-attacker-independent governance action [4](#0-3) .
3. Time passes (multiple blocks). Any interaction that triggers `accrue()` (e.g., another user's `system-borrow`, `transfer`, or `deposit`) advances `index`/`total-debt` for the paused borrower's loan, since only the `accrue` flag — not `repay` — gates the accrual computation [5](#0-4) .
4. The borrower attempts `system-repay`; `accrue` runs (further compounding debt) and then the call reverts with `ERR-PAUSED` due to the `repay` guard [3](#0-2) , leaving the borrower with no way to reduce their growing debt.
5. Once `repay` is unpaused (or via any liquidation path relying on `total-debt`), the borrower's position may now be underwater purely due to accrual during the window they were blocked from repaying, resulting in liquidation and loss of collateral they otherwise would have protected by timely repayment.
