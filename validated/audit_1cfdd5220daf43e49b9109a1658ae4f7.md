## Title
Excess Attached Deposit Permanently Stuck in `AddressRegistrar::register` With No Withdrawal Path - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar` contract's `#[payable] register` method only computes and validates a *minimum* required deposit for the storage it consumes, but never refunds the difference between the attached deposit and that minimum when registration succeeds. The contract exposes no other method (no `withdraw`, no owner-only rescue function) that can move balance back out, so any excess native token (`$NEAR`) attached by a caller — whether directly or indirectly via the Wallet Contract's `rlp_execute` "value" field — is permanently trapped in the contract's account balance.

### Finding Description
`register()` computes `required_deposit` from the bytes needed to store the address/account mapping and panics if `given_deposit < required_deposit` [1](#0-0) . If the entry is new (`Entry::Vacant`), the mapping is inserted and the full `given_deposit` (which can exceed `required_deposit` by an arbitrary amount) stays on the contract with no refund of the surplus [2](#0-1) . Only the collision path (`Entry::Occupied`) refunds the caller, and even then it refunds the *entire* `given_deposit`, not specifically the surplus in the success case [3](#0-2) . There is no owner, admin, or withdraw method anywhere in the contract (`PanicOnDefault` struct with only `register`, `lookup`, `get_address`) [4](#0-3) , so once excess $NEAR lands on the contract it can never be moved out again.

This is directly reachable by an unprivileged caller in a single transaction: any account can call `register` with a deposit far larger than `required_deposit` and the difference is burned into the contract balance forever. It's also reachable indirectly through the Wallet Contract, which forwards Ethereum "value" (via `Wei` conversion) as the attached deposit of the inner `FunctionCall` action without capping it to what the target contract actually needs [5](#0-4) . The project's own integration test explicitly documents and accepts this behavior: attaching 3 NEAR to a `register` call that only requires a tiny storage deposit results in the full 3 NEAR being consumed with no refund on success [6](#0-5) .

### Impact Explanation
Any user (directly, or via an ETH-implicit account/relayer using the Wallet Contract) who attaches more $NEAR than the minimal required storage deposit when calling `register` permanently loses the surplus — the funds become irrecoverable native tokens locked in a contract account with no owner and no withdrawal mechanism. This is a direct, unauthorized, permanent loss of user funds triggered by a single transaction; it requires no cooperation from validators, no malicious peers, and no special privileges.

### Likelihood Explanation
High. Overpayment is easy to trigger accidentally: a caller (or a wallet/relayer translating an Ethereum transaction's `value` field into a NEAR deposit) has no strong reason to compute the exact `storage_byte_cost * bytes_to_store` value before calling `register`, and any small overestimate results in permanent loss with no recourse. The behavior is already exercised, and effectively normalized, in the project's own test suite.

### Recommendation
In `AddressRegistrar::register`, after successfully inserting a new mapping, refund the difference `given_deposit - required_deposit` back to `env::predecessor_account_id()` (mirroring what is already done on the collision path), rather than only refunding on the `Entry::Occupied` branch. Consider adding a bound (e.g., require `given_deposit == required_deposit` or refund any excess in both branches) so no path allows silent retention of unspent deposit.

### Proof of Concept
1. Deploy `AddressRegistrar` and call `new()`.
2. From any unprivileged account, call `register(account_id)` attaching a deposit far larger than the actual `required_deposit` computed from `storage_byte_cost() * (20 + account_id.len())` (e.g. attach `NearToken::from_near(3)` when only ~0.00032 NEAR is required, as done in the existing test `test_caller_refunds`) [7](#0-6) .
3. The call succeeds (`Entry::Vacant` branch), the mapping is stored, but no refund promise is created [2](#0-1) .
4. The excess balance remains on the `AddressRegistrar` account permanently; there is no method in the contract to move it back out.
