### Title
Receipt size validation does not account for `output_data_receivers` appended after the size check, allowing receipts to exceed `max_receipt_size` - (File: `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/lib.rs`)

### Summary
This nearcore path mirrors the UMA `LongShortPair` bug class: a size-limit check is performed on an object at creation time, but the object later has an additional field appended by the protocol itself, without re-validating the now-larger object against the same limit. In nearcore, a new `ActionReceipt`'s size is checked against `max_receipt_size` via `validate_receipt` with `ValidateReceiptMode::NewReceipt`, but `output_data_receivers` are appended to that receipt afterward in `apply_action_receipt` in `runtime/runtime/src/lib.rs`, with no re-check.

### Finding Description
`validate_receipt` enforces `max_receipt_size` only for `ValidateReceiptMode::NewReceipt`: [1](#0-0) . This mode's own doc comment already acknowledges a known escape ("There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed") referencing `near/nearcore#12606`: [2](#0-1) .

The concrete root cause is in `apply_action_receipt` in `runtime/runtime/src/lib.rs`: after a new action receipt is created and validated at the point of `promise_return`/`promise_then` (a receipt at or under `max_receipt_size`), the caller's `output_data_receivers` are merged into that already-created new receipt via `extend_from_slice`, growing it further with no subsequent size re-validation: [3](#0-2) .

This is structurally identical to the UMA analog: the constructor/validator confirms the size of the *initial* payload is within limits, but the additional field appended by the protocol afterward (`output_data_receivers`, analogous to the appended "early expiration" field) is not accounted for, so the final artifact can silently exceed the declared limit.

### Impact Explanation
A receipt that exceeds `max_receipt_size` is a value the protocol is supposed to reject deterministically. Allowing it to slip past validation means the enforced consensus invariant "no receipt exceeds `max_receipt_size`" is violated by a receipt that is nonetheless accepted into state and forwarded across shards. This is an invalid state transition acceptance: nodes that assume the invariant holds (e.g. for buffer/size accounting in congestion control, state-witness size budgeting, or storage-proof limits) can diverge in behavior from nodes that hit different code paths handling oversized data, and downstream contract logic (e.g. `assert_test_completed`/promise-return chains as demonstrated by the existing regression tests) can behave differently than intended by protocol limits. The nearcore test suite itself demonstrates the receipt is created, accepted, and forwarded despite exceeding the size limit, and only asserts the runtime doesn't crash, not that the state transition is rejected.

### Likelihood Explanation
Reachable from a single unprivileged transaction: any account can deploy a contract and call a method that builds a promise chain (`promise_create` → `promise_then` → `promise_return`) sized so the intermediate receipt lands at `max_receipt_size` before `output_data_receivers` is appended, exactly as already reproduced by the existing (currently-passing-but-flagged) regression test `test_max_receipt_size_promise_return`: [4](#0-3) . No validator, network, or operator privilege is required.

### Recommendation
Re-run `validate_receipt` (or an equivalent size check against `max_receipt_size`) on the new action receipt after `output_data_receivers` are merged in `apply_action_receipt`, and reject/refuse the resulting receipt (or fail the originating action) if the final size exceeds the limit, rather than deferring to the "tolerate gracefully" `ExistingReceipt` fallback path.

### Proof of Concept
Use the existing repository regression test as the PoC, which already demonstrates the bypass end-to-end: deploy `near_test_contracts::rs_contract()`, call a method that creates a promise DAG `[A -then-> B]`, where `A`'s execution creates a third promise `C` sized so the resulting receipt is exactly `max_receipt_size`, then does `promise_return`; the runtime's `extend_from_slice` merge of `output_data_receivers` afterward pushes the receipt above `max_receipt_size` without a size re-check: [5](#0-4) .

// A function call will generate a new receipt. Size of this receipt will be equal to
// `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and
// the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently
// isn't because of a bug (See https://github.com/near/nearcore/issues/12606)
// Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`.
#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
