## Title
`SignedDelegateAction` (NEP-366 meta-transactions) is replayable across chain forks because its signed hash has no chain/ancestry binding, unlike ordinary transactions - (File: `core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`DelegateAction`/`DelegateActionV2` (the payload a user signs to authorize a meta-transaction, per NEP-366/NEP-611) is hashed and signed only over `sender_id, receiver_id, actions, nonce, max_block_height, public_key` plus a NEP discriminant tag. `SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify` check only this signature, and `apply_delegate_action` only checks the access-key nonce and an absolute `max_block_height`. [1](#0-0) [2](#0-1) 

Unlike this, an ordinary `SignedTransaction` carries a `block_hash` that is validated against the actual ancestry of the chain (`validity_period_validate_is_ancestor`), which explicitly detects and rejects transactions replayed "from a different fork": [3](#0-2) [4](#0-3) 

The `DelegateAction` signature contains none of that chain-anchoring data.

### Finding Description
The delegate-action signing scheme (NEP-461/NEP-366) is:
```
SignableMessage { discriminant: NEP-tag, msg: &DelegateAction }
hash = hash(borsh(SignableMessage))
signature = signer.sign(hash)
``` [5](#0-4) 

`DelegateAction`'s fields are `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` - none of which reference a specific block hash, genesis hash, or chain id. Its only replay defenses are:
1. Access-key `nonce`, checked/incremented in `validate_delegate_action_key`.
2. An absolute `max_block_height`, checked as a plain integer comparison against `apply_state.block_height`. [6](#0-5) [7](#0-6) 

Both quantities are purely local, height/nonce-based state that is identical on any two chains that share history up to a fork point. Regular NEAR transactions avoid this exact weakness because their `block_hash` field is checked with `check_transaction_validity_period` → `validity_period_validate_is_ancestor`, which walks the actual chain to confirm the referenced block is really an ancestor of the block including the transaction - this is precisely the mechanism that distinguishes one post-fork branch from the other (`rpc_handler.rs` even logs "expired or from a different fork"). [8](#0-7) 

A `SignedDelegateAction`, however, is only ever wrapped inside a relayer's own `SignedTransaction` when the relayer submits it to the network; the inner delegate signature itself never gets checked against any block hash. Consequently, if a `SignedDelegateAction` produced (or intercepted from a relayer/mempool) before a chain split is not yet consumed (its nonce not yet applied) on one branch, it remains valid to submit — wrapped in a fresh, branch-specific transaction — on that branch even after having already been executed on the other branch, as long as each branch's access-key nonce/`max_block_height` state independently still permits it. Nothing in `DelegateAction`, `SignedDelegateAction::verify`, or `apply_delegate_action` ties the authorization to a specific chain history.

### Impact Explanation
Any account that authorizes a meta-transaction (e.g., "transfer $FT to X", "add a key", "call a contract with a deposit") signs only nonce/height-bound data. On a chain fork/split (e.g., contentious protocol fork producing two independently-live post-fork chains sharing pre-fork state and access-key nonces), a relayer (an unprivileged party — anyone can relay a `SignedDelegateAction`, that is the entire point of NEP-366) can resubmit the same previously observed `SignedDelegateAction` on the sibling branch. Because nonce and `max_block_height` are per-branch local state that started out identical at the fork point, the replayed delegate action is accepted again, causing the sender's single authorized action (fund transfer, key addition, deposit-bearing call, etc.) to execute a second time on an independent ledger without further consent from the sender. This is unauthorized duplicate value movement stemming from a signature scheme lacking chain-domain separation, directly analogous to the reported `constructMsg` issue that lacks `block.chainid`.

### Likelihood Explanation
Requires a chain split event (a fork with independently valid successor chains sharing genesis/pre-fork state) — this is an "eventual chain fork" scenario, matching the report's own threat model, and is entirely reachable through the unprivileged meta-transaction/relayer path (no validator, operator, or network-attacker privilege needed): any address holding a copy of a `SignedDelegateAction` (the delegate-action sender broadcasts it to a relayer off-chain and has no control over how many times/branches it is relayed) can replay it.

### Recommendation
Bind the delegate-action signature to chain identity/ancestry, mirroring the protection already given to ordinary transactions:
- Add a chain-identifying/anchoring field (e.g., a recent `block_hash` validated via `validity_period_validate_is_ancestor`, or a `genesis_hash`/`chain_id`) into `DelegateAction`/`DelegateActionV2` and into the NEP-461 `SignableMessage` payload that gets hashed and signed in `core/primitives/src/signable_message.rs` / `core/primitives/src/action/delegate.rs`.
- Validate that field the same way `apply_delegate_action` in `runtime/runtime/src/actions.rs` already validates nonce and `max_block_height`, rejecting delegate actions whose referenced block is not an ancestor of the current chain.

### Proof of Concept
1. Alice signs `DelegateAction { sender_id: alice, receiver_id: ft_contract, actions: [ft_transfer(bob, 100)], nonce: N, max_block_height: H, public_key: alice_pk }` and hands `SignedDelegateAction` to Relayer via `SignedDelegateAction::sign` (`core/primitives/src/action/delegate.rs:92-95`).
2. Relayer wraps it in a transaction and submits it on chain A; it succeeds — `validate_delegate_action_key` bumps Alice's access-key nonce to `N` on chain A only (`runtime/runtime/src/actions.rs:605-655`).
3. Suppose (or simulate in a test-loop/fork scenario) chain B is a sibling branch sharing state up to a common ancestor before this transaction was included, so Alice's access-key nonce on chain B is still `< N` and current block height on B is `< H`.
4. Relayer (or anyone with the intercepted `SignedDelegateAction` bytes) wraps the same, unmodified `SignedDelegateAction` in a new transaction (own `block_hash`, valid on chain B) and submits it to chain B.
5. `SignedDelegateAction::verify` succeeds (nothing in the signed payload differs per chain), `apply_delegate_action`'s nonce/height checks pass on chain B, and the `ft_transfer(bob, 100)` executes a second time — on an independent ledger — without any new authorization from Alice.

/// For a given transaction, it expires if the block that the chunk points to is more than `validity_period`
/// ahead of the block that has `base_block_hash`.
pub fn check_transaction_validity_period(
    chain_store: &ChainStoreAdapter,
    prev_block_header: &BlockHeader,
    base_block_hash: &CryptoHash,
    transaction_validity_period: BlockHeightDelta,
) -> Result<(), InvalidTxError> {
    let base_header =
        chain_store.get_block_header(base_block_hash).map_err(|_| InvalidTxError::Expired)?;

    metrics::CHAIN_VALIDITY_PERIOD_CHECK_DELAY
        .observe(prev_block_header.height().saturating_sub(base_header.height()) as f64);

    // First check the distance between blocks
    if prev_block_header.height() > base_header.height() + transaction_validity_period {
        return Err(InvalidTxError::Expired);
    }

    // Then check if there is a path between the blocks (`base` is an ancestor of `prev`)
    validity_period_validate_is_ancestor(&base_header, prev_block_header, chain_store)
}

/// Check if base_header is an ancestor of prev_block_header.
/// Used in check_transaction_validity_period.
fn validity_period_validate_is_ancestor(
    base_header: &BlockHeader,
    prev_block_header: &BlockHeader,
    chain_store: &ChainStoreAdapter,
) -> Result<(), InvalidTxError> {
    let base_height = base_header.height();
    let prev_height = prev_block_header.height();
    let base_block_hash = base_header.hash();

    // Base can't be an ancestor of prev if its height is bigger
    if base_height > prev_height {
        return Err(InvalidTxError::InvalidChain);
    }

    // if both are on the canonical chain, comparing height is sufficient
    // we special case this because it is expected that this scenario will happen in most cases.
    if let Ok(base_block_hash_by_height) = chain_store.get_block_hash_by_height(base_height) {
        if &base_block_hash_by_height == base_block_hash {
            if let Ok(prev_hash) = chain_store.get_block_hash_by_height(prev_height) {
                if &prev_hash == prev_block_header.hash() {
                    return Ok(());
                }
            }
        }
    }

    // if the base block height is smaller than `last_final_height` we only need to check
    // whether the base block is the same as the one with that height on the canonical fork.
    // Otherwise we walk back the chain to check whether base block is on the same chain.
    let last_final_height = chain_store
        .get_block_height(prev_block_header.last_final_block())
        .map_err(|_| InvalidTxError::InvalidChain)?;

    if last_final_height >= base_height {
        let base_block_hash_by_height = chain_store
            .get_block_hash_by_height(base_height)
            .map_err(|_| InvalidTxError::InvalidChain)?;
        if &base_block_hash_by_height == base_block_hash {
            Ok(())
        } else {
            Err(InvalidTxError::InvalidChain)
        }
    } else {
        let header =
            get_block_header_on_chain_by_height(chain_store, prev_block_header.hash(), base_height)
                .map_err(|_| InvalidTxError::InvalidChain)?;
        if header.hash() == base_block_hash { Ok(()) } else { Err(InvalidTxError::InvalidChain) }
    }
}

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }
