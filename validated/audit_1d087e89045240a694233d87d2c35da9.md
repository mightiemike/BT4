## Analysis

The LimboDAO "stuck proposal" bug class is fundamentally about **a container operation absorbing/swallowing the failure of a step that already produced real side effects**, so that a partial, inconsistent state persists instead of being fully committed or fully rolled back. Since dao-multisig itself is out of scope, I looked for the same *mechanism* — a fold/map that absorbs failure of an inner mutating step — in the market contract, and found it in `liquidate-multi`.

`liquidate-multi` is implemented as `(ok (map call-liquidate positions))` [1](#0-0) , which is mirrored on mainnet [2](#0-1) . Because the top-level public function always returns `(ok ...)` regardless of whether individual `call-liquidate` → `liquidate` invocations return `(err ...)`, Clarity's whole-transaction atomicity/rollback is never triggered — the *outer* call succeeded, so the VM commits everything that happened during the transaction, even mutations produced by an inner `liquidate()` call that itself "failed."

Inside `liquidate()`, the mutating vault-side step `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` executes *before* the per-user obligation mutations `debt-remove-scaled` / `collateral-remove` on `.market-vault` [3](#0-2)  (same ordering on mainnet [4](#0-3) ). If the later `try!`-wrapped call to `.market-vault debt-remove-scaled` (or `collateral-remove`) fails for any reason, `liquidate()` returns `(err ...)` for that batch element — but `vault-system-repay`'s already-applied vault-level mutation is not selectively undone, and since `liquidate-multi` still returns `(ok (list ...))` at the top level, Clarity persists it.

### Title
Partial-mutation persistence in `liquidate-multi` due to unguarded `map` swallowing inner `liquidate()` failures - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` uses `(ok (map call-liquidate positions))` instead of a reverting fold, so any individual position's failure inside `liquidate()` is captured as an `(err ...)` list element rather than propagated. Because the overall transaction still returns `ok`, Clarity commits all state mutations made up to the point of failure inside that failed `liquidate()` call, including the vault-level debt-repay bookkeeping performed by `vault-system-repay`, even though the corresponding borrower-obligation mutation (`debt-remove-scaled`/`collateral-remove`) never executed.

### Finding Description
`liquidate()` performs its mutations in this order: pause/health/slippage `asserts!` → `(try! (vault-system-repay ...))` (vault-level: pulls repayment and updates vault debt/interest bookkeeping) → `(try! (contract-call? .market-vault debt-remove-scaled ...))` and `collateral-remove` (per-borrower obligation bookkeeping) [5](#0-4) .

If `debt-remove-scaled` or `collateral-remove` fails after `vault-system-repay` has already succeeded, `liquidate()` returns `(err ...)`. When called directly as a standalone transaction, Clarity's whole-transaction atomicity would roll back everything, including the `vault-system-repay` mutation, because the top-level result is `err`.

However, when reached through `liquidate-multi`'s `call-liquidate` wrapper [6](#0-5)  and the batch driver `(ok (map call-liquidate positions))` [1](#0-0) , the `err` from that single position's `liquidate()` call is merely stored as one entry in the returned list — it is never `try!`'d or `asserts!`'d by `liquidate-multi`. The enclosing `liquidate-multi` transaction therefore returns `(ok (list ...))` overall, and Clarity commits the entire transaction's state, including the partial `vault-system-repay` mutation from the "failed" element, while the corresponding borrower obligation was never decremented.

This is the same failure-absorption mechanism as the LimboDAO bug class: a batch/fold-style entry point absorbs an inner step's failure into a wrapped success, letting a partially-mutated, inconsistent state persist instead of triggering a full rollback or a full commit.

### Impact Explanation
This produces a vault/obligation accounting desync: the vault's aggregate debt/interest bookkeeping reflects a repayment (and pulls/consumes the liquidator's repayment funds via `vault-system-repay`) for a position whose borrower-level obligation in `.market-vault` was never reduced. Depending on which side of the mismatch is used for future accounting (aggregate vault liabilities vs. per-user obligations), this can manifest as protocol insolvency (vault believes it holds fewer outstanding claims than borrowers still owe) or as a loss of the liquidator's repayment funds for a liquidation that is reported as failed. Both map to in-scope Critical impact categories (protocol insolvency / theft of funds in motion).

### Likelihood Explanation
Triggering requires only a normal liquidator submitting a `liquidate-multi` batch where at least one element's `debt-remove-scaled`/`collateral-remove` call fails after `vault-system-repay` already succeeded (e.g., a race between two batch entries touching the same borrower/asset within the same block, or any edge-case rejection at the `.market-vault` layer). No DAO compromise, oracle manipulation, or privileged access is needed — it is reachable by any caller of the permissionless `liquidate-multi` entry point using ordinary batch inputs.

### Recommendation
Do not swallow per-element errors with a bare `map`. Either (a) use `try!` on each `call-liquidate` result so any failing element reverts the entire batch (losing the "isolate failures" feature but restoring atomicity), or (b) make `vault-system-repay` and the obligation-mutating calls transactionally coupled inside `liquidate()` such that a later failure cannot leave `vault-system-repay`'s effects uncommitted relative to `debt-remove-scaled`/`collateral-remove` — e.g., perform all validation/computation for both steps before any state-mutating call, so the only mutations that occur are the ones guaranteed to complete together.

### Proof of Concept
1. Liquidator submits `liquidate-multi` with two positions in the same block: position A (borrower `X`, debt asset `D`) and position B (borrower `X`, same debt asset `D`, overlapping/adjacent state).
2. `call-liquidate` on position A executes fully: `vault-system-repay` succeeds (vault-level debt/interest updated, liquidator funds pulled), then `debt-remove-scaled` succeeds, decrementing borrower `X`'s scaled debt for asset `D`.
3. `call-liquidate` on position B executes against the now-updated (lower) scaled debt for borrower `X`/asset `D`: `vault-system-repay` succeeds again (pulling more liquidator funds and updating vault bookkeeping), but the subsequent `debt-remove-scaled` call fails (e.g., `scaled-to-remove` computed against stale `curr-scaled` exceeds the already-reduced value, or another edge condition at the `.market-vault` layer causes rejection).
4. `liquidate()` for position B returns `(err ...)`; `call-liquidate` returns that same `(err ...)` as a list element; `liquidate-multi` still returns `(ok (list (ok ...) (err ...)))` at the top level.
5. Because the overall transaction result is `ok`, Clarity commits everything, including position B's `vault-system-repay` mutation (funds pulled, vault bookkeeping updated) even though borrower `X`'s obligation in `.market-vault` was never reduced for that portion — the vault's aggregate accounting and the per-user obligation registry are now out of sync, and the liquidator's funds for the "failed" position B were consumed without a corresponding recorded liquidation.
