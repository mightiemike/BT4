Confirmed: `ExchangeInjectContract` and `ExchangeWithdrawContract` (unlike `ExchangeTransactionContract`, which carries an `expected` field) have no user-supplied minimum/maximum-output field at all.

### Title
Missing slippage-protection field in `ExchangeInjectContract`/`ExchangeWithdrawContract` allows sandwich/front-running loss of TRX/TRC10 value on Bancor-based Exchange pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`java-tron`'s on-chain Bancor-style token exchange (`ExchangeCreate`/`ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction`) computes the counter-token amount from the pool's live ratio at execution time. `ExchangeTransactionContract` protects the trader with a caller-supplied `expected` minimum-output field, enforced in `ExchangeTransactionActuator`. `ExchangeInjectContract` and `ExchangeWithdrawContract`, however, carry no such field, so the amount of the "another token" the caller will give up (inject) or receive (withdraw) is entirely determined by whatever the pool ratio happens to be at the exact block/order the transaction executes, with no way for the signer to bound the outcome.

### Finding Description
`ExchangeTransactionContract` includes an `expected` field explicitly to bound slippage: [1](#0-0) , enforced in `ExchangeTransactionActuator.doValidate()`: [2](#0-1) .

In contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — no expected/minimum field: [3](#0-2) .

`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` purely from the current pool balances at execution time, with no comparison against a client-declared bound: [4](#0-3) . The `doValidate()` recomputation of `anotherTokenQuant` only rejects a zero/negative result or exceeding the global balance limit — it never checks it against anything the caller specified: [5](#0-4) .

Likewise, `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the live pool ratio with no user-supplied floor, and `doValidate()`'s "Not precise enough" check only guards against integer-rounding drift between validate-time and execute-time math (a ~0.01% tolerance band), not against economically adverse ratio movement caused by an intervening transaction: [6](#0-5) [7](#0-6) .

Both are reachable from any account via ordinary broadcast transactions (`ExchangeInjectContract`/`ExchangeWithdrawContract`), gated only by "must be the pool creator" — any account that itself created the exchange pool via `ExchangeCreateContract`, not a privileged node/operator role: [8](#0-7) .

The underlying pool ratio is a Bancor relay-token curve (`ExchangeCapsule.transaction`, `ExchangeProcessor`/`SafeExchangeProcessor`) whose price moves with every `ExchangeTransactionContract` trade executed in the pool: [9](#0-8) .

### Impact Explanation
Because block producers order transactions and multiple transactions targeting the same exchange pool can be included within one block (or across adjacent blocks before a widely-spaced inject/withdraw is picked up), an attacker who observes a pending `ExchangeInjectContract` or `ExchangeWithdrawContract` in the mempool can insert a large `ExchangeTransactionContract` trade immediately before it to shift the pool ratio unfavorably, let the victim's inject/withdraw execute at the manipulated ratio, then reverse the trade afterward (classic sandwich). Since `ExchangeInjectContract`/`ExchangeWithdrawContract` lack an `expected`-style bound, the victim (who must be the pool's creator to call these) has no on-chain way to cap the resulting counter-token loss — they either receive fewer tokens on withdraw or give up more value on inject than intended, a direct value-corruption/accounting impact without any tool for the caller to protect themselves.

### Likelihood Explanation
Any account that created an exchange pool can be targeted, and the attack only requires observing a pending transaction in the mempool and paying gas for one extra trade before/after it — no special network position or leaked keys are required, only ordinary broadcast transactions and predictable Bancor-curve math (`ExchangeProcessor.exchange`).

### Recommendation
Add a caller-supplied bound analogous to `ExchangeTransactionContract.expected` to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `expected_another_token_quant` for inject as a maximum acceptable counter-token spend, and a minimum acceptable counter-token receipt for withdraw), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` the same way `ExchangeTransactionActuator` enforces `tokenExpected`.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` from the pool creator withdrawing `tokenQuant` of `firstTokenID`, expecting to receive `anotherTokenQuant` of `secondTokenID` based on the current ratio.
2. Attacker submits an `ExchangeTransactionContract` selling a large amount of `secondTokenID` into the same pool just before the victim's transaction, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for the withdrawer.
3. The victim's `ExchangeWithdrawActuator.execute()` recomputes `anotherTokenQuant` from the now-manipulated balances — since there is no `expected` minimum field on `ExchangeWithdrawContract`, the transaction succeeds and the victim receives materially less `secondTokenID` than intended.
4. Attacker reverses their trade afterward, extracting the value difference, while the victim had no on-chain mechanism to prevent the loss.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
