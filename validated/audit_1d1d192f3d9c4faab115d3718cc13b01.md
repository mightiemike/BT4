Based on my research, I found a genuine analog worth reporting: an unhandled-panic-on-malformed-input bug in the L1 message hash computation path, directly analogous to the Confluence plugin's "unexpected request body crashes the plugin" bug class.

### Title
Panic-inducing DoS via empty-calldata L1 handler transaction reaching `l1_handler_message_hash` - (File: `crates/starknet_api/src/hash.rs`)

### Summary
`starknet_api::transaction::L1HandlerTransaction` derives `Deserialize` with no invariant enforcing that `calldata` is non-empty, yet `l1_handler_message_hash` (invoked via `L1HandlerTransaction::calc_msg_hash`) unconditionally calls `calldata.0.split_first().expect(...)`, which panics if `calldata` is empty. This mirrors the reported Confluence-plugin class of bug: an endpoint/code path that accepts attacker-influenced input without validating a structural precondition, and panics/crashes instead of returning a graceful error.

### Finding Description
`l1_handler_message_hash` in [1](#0-0)  does:
```
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
```
This function is called from `L1HandlerTransaction::calc_msg_hash` [2](#0-1) , which is used from the RPC layer (`apollo_rpc/src/v0_8/api/api_impl.rs`) to compute the L1→L2 message hash, e.g. for `estimateMessageFee`-style entry points that accept a `MessageFromL1`/L1Handler-shaped transaction as untrusted input.

Critically, the codebase itself acknowledges the missing invariant: the sibling method `payload_size` on the same struct family was patched to guard against exactly this case with `saturating_sub`, and a regression test explicitly documents it: [3](#0-2)  and [4](#0-3) . The comment states verbatim: *"`Calldata` has no non-empty invariant and `L1HandlerTransaction` derives `Deserialize`, so an empty calldata is constructible."* This confirms the type is expected to be built from externally supplied/deserialized data (RPC parameters, JSON test/RPC-fetched objects, protobuf conversions) without a length check, yet `l1_handler_message_hash` was not given the same fix — it still uses `.expect(...)` on `split_first()`, which panics on an empty slice.

The RPC entry point that constructs an `L1HandlerTransaction` from a client-supplied `MessageFromL1` prepends `from_address` unconditionally [5](#0-4) , so a naive analysis might suggest calldata can never be empty on that particular path. However, `calc_msg_hash`/`l1_handler_message_hash` is a general-purpose API on the `starknet_api` type, called wherever an `L1HandlerTransaction` object is available — including from deserialized/untrusted sources per the codebase's own admission — and is not gated by the same defensive check applied to `payload_size`. Any caller that constructs or receives an `L1HandlerTransaction` with `calldata = []` (via JSON-RPC deserialization, stored/replayed transaction objects, or other conversion paths that don't go through the `MessageFromL1`-based constructor) will panic the calling process when `calc_msg_hash` is invoked.

### Impact Explanation
A panic in a sequencer/RPC node process handling transaction or message data constitutes a crash/DoS of that component — consistent with the "network unable to confirm new transactions" acceptance criterion if triggered on a critical-path service (e.g., the RPC node, or any component that computes L1↔L2 message hashes as part of processing untrusted L1Handler-shaped data). This is a High-severity class exactly analogous to the reported Mattermost Confluence Plugin bug: unexpected/malformed input structure (missing required field) triggers an unhandled panic rather than a validated error response.

### Likelihood Explanation
The precondition (non-empty calldata) is not enforced by the type system (`Calldata` has no non-empty invariant, confirmed by the codebase's own test comments), and `Deserialize` is derived directly on `L1HandlerTransaction`, meaning any JSON/RPC/storage path that builds this struct from external data can produce an empty-calldata instance. The fix applied to `payload_size` (using `saturating_sub`) was not mirrored in `l1_handler_message_hash`, indicating an inconsistent/incomplete fix — a strong signal that this exact function was overlooked.

### Recommendation
Replace the `.expect(...)` panic in `l1_handler_message_hash` with a graceful error return (e.g., return a `Result`/`StarknetApiError` for empty calldata), mirroring the `saturating_sub` fix already applied to `L1HandlerTransaction::payload_size`. Additionally, audit all other call sites that index or destructure `calldata.0` on `L1HandlerTransaction`-family types (e.g., `crates/apollo_batcher/src/cende_client_types.rs:78`, `crates/starknet_os_flow_tests/src/test_manager.rs:691`) for the same unchecked-empty-slice pattern.

### Proof of Concept
1. Construct (or deserialize from JSON/RPC input) an `starknet_api::transaction::L1HandlerTransaction` with `calldata: Calldata(Arc::new(vec![]))` — this is unconstrained since `Calldata` allows empty vectors and the struct derives `Deserialize`.
2. Wrap it into an `executable_transaction::L1HandlerTransaction` (as `payload_size`'s own regression test does) and call `.calc_msg_hash()`.
3. `l1_handler_message_hash` executes `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")`, which panics because the slice is empty, crashing the calling process/thread.

**Note on scope/uncertainty:** I was not able to fully trace every call site that constructs an `L1HandlerTransaction` from fully untrusted external bytes (vs. from the sender-controlled `MessageFromL1` path which always prepends `from_address`) within the tool budget available. The strongest evidence for reachability is the codebase's own acknowledgment (in `payload_size`'s doc comment and regression test) that empty calldata is constructible via deserialization for this exact type family, while the parallel `calc_msg_hash` path was left unpatched. A full audit of all `Deserialize`-reachable construction sites for `L1HandlerTransaction` would be needed to confirm the precise externally-triggerable entry point with certainty.

```rust
pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());

    let payload_length_as_felt =
        Felt::from(u64::try_from(payload.len()).expect("usize should fit in u64"));
    encoded.extend(payload_length_as_felt.to_bytes_be());
```
