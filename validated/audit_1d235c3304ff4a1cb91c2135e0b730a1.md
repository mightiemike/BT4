### Title
Replay/backup verification (`ensure_match_transaction_info`) silently accepts wrong state, hot-state, and position state roots - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative check used by the chunk-replay verification pipeline (`ChunkExecutorInner::verify_execution` in `execution/executor/src/chunk_executor/mod.rs`) and by the standalone `replay_on_archive` tool (`storage/db-tool/src/replay_on_archive.rs`) to confirm that VM re-execution of an archived/backed-up transaction reproduces the exact result recorded in the trusted, Merkle-proven `TransactionInfo`. The function checks status, gas, write-set hash, and event root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the values actually produced by re-execution, so a divergence in any of those roots is never detected by this check.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates `status`, `gas_used`, `write_set_hash` (== `state_change_hash`), and `event_root_hash` against the supplied `TransactionInfo`. It stops there, and the code contains an explicit acknowledgement of the gap: [2](#0-1) 

This comment states plainly that checkpoint hashes (main state, hot state, and the trading-native position state) are ignored, and that "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

This function is not a test helper — it is wired into two real verification code paths that are meant to be state-commitment-integrity gates:

1. `ChunkExecutorInner::verify_execution`, invoked during `TransactionReplayer::enqueue_chunks` when `VerifyExecutionMode::should_verify()` is true. This path re-executes historical transactions with the VM and is supposed to catch divergence before the chunk is queued to be committed to local storage: [3](#0-2) 
This is used from the backup-cli restore/replay flow (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs`) which drives `chunk_replayer.enqueue_chunks(...)` with a configurable `verify_execution_mode` before committing replayed history to a restoring node's DB: [4](#0-3) 

2. `replay_on_archive::execute_and_verify`, the dedicated archive-replay auditing tool: [5](#0-4) 

In both cases, the `TransactionInfo` supplied as the expected value came from a chain-authenticated source (transaction accumulator proof against a `LedgerInfo`), so its `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields are trustworthy — but the local, freshly-computed values from `DoStateCheckpoint`/`DoLedgerUpdate` are never diffed against them here. If any of these values diverge (due to a state-computation bug, non-determinism, feature flag skew such as `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, or a corrupted/malicious backup archive whose write-sets are individually hash-consistent but whose aggregate state root is wrong), `ensure_match_transaction_info` reports success regardless.

### Impact Explanation
This breaks the state-proof integrity invariant that verification tooling must reject any replayed/restored history whose derived state root does not match the chain-committed root. A node performing `replay_on_archive` (used to audit archive nodes/backups for correctness) or a node restoring from backup with execution verification enabled can be told the replay is correct while its Sparse-Merkle-Tree state root, hot-state root, or position (trading-native) state root has silently diverged from the authenticated ledger. This is exactly the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated ... proof context" scenario the state-integrity gate calls out: the corrupted value is the state (or hot-state/position-state) root that the verification step is specifically responsible for authenticating, and no error surfaces to operators relying on this tool for integrity assurance.

### Likelihood Explanation
The gap is deterministic and unconditional — it is not a race or timing bug, it is an unconditional omission in the comparison function, already flagged internally via a `TODO(trading-native)` comment. It will manifest anytime replay produces a different state/hot-state/position-state root than the archived `TransactionInfo` (e.g., a state-computation regression, or a modified/corrupted backup archive with self-consistent per-transaction write-set hashes but altered aggregate state), and the only two callers of this integrity check will not catch it.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on the `TransactionInfo` and when the relevant checkpoint output is available from the replay) against the locally computed values, failing verification on mismatch, exactly as already suggested by the in-code TODO before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
1. In `execution/executor/src/chunk_executor/mod.rs::verify_execution` (or `replay_on_archive::execute_and_verify`), construct a scenario where VM re-execution of a transaction produces write-set/events/gas/status identical to the archived `TransactionInfo` but where the resulting state-checkpoint root differs from `TransactionInfo::state_checkpoint_hash()` (e.g., inject a corrupted `state_checkpoint_hash` field into a fabricated backup, or force divergence in `DoStateCheckpoint` output).
2. Run `enqueue_chunks`/`verify_execution` with `verify_execution_mode.should_verify() == true`.
3. Observe `ensure_match_transaction_info` returns `Ok(())` at [6](#0-5)  despite the state root mismatch, so the chunk is accepted and enqueued for commit / reported as a successful replay.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
