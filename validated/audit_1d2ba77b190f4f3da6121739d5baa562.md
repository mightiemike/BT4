### Title
Unbounded full-store iteration in `getAssetIssueList`/`listExchanges`/`listProposals` RPC & HTTP APIs enables anonymous DoS - (File: `chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java`, `ExchangeStore.java`, `ProposalStore.java`)

### Summary
The `getTickState()` finding is a case of an on-chain "list all inserted items" function with no bound on the number of iterations, letting the item count (attacker-influenceable) dictate gas/compute cost. java-tron has the same anti-pattern in its read-only wallet APIs: `AssetIssueStore.getAllAssetIssues()`, `ExchangeStore.getAllExchanges()`, and `ProposalStore.getAllProposals()` each iterate the *entire* underlying store with no cap, and are reachable unauthenticated via gRPC (`GetAssetIssueList`, `ListExchanges`, `ListProposals`) and HTTP (`/wallet/getassetissuelist`, `/wallet/listexchanges`, `/wallet/listproposals`).

### Finding Description
`AssetIssueStore.getAllAssetIssues()` streams the full `iterator()` of the asset-issue store with no limit: [1](#0-0) 

`ExchangeStore.getAllExchanges()` and `ProposalStore.getAllProposals()` do the same, also sorting the whole in-memory list afterward: [2](#0-1) [3](#0-2) 

These are invoked directly by `Wallet.getAssetIssueList()` and `Wallet.getExchangeList()`, with no offset/limit parameter at all: [4](#0-3) [5](#0-4) 

Both are wired to unauthenticated, anonymous-reachable transports:
- gRPC `WalletSolidityApi`/`WalletApi`: `getAssetIssueList(EmptyMessage)`, `listExchanges(EmptyMessage)`, and `listProposals(EmptyMessage)`, all taking `EmptyMessage` (no bound parameter): [6](#0-5) [7](#0-6) 
- HTTP servlets `GetAssetIssueListServlet`, `ListExchangesServlet`, `ListProposalsServlet` call the identical unbounded APIs with only a generic per-endpoint `RateLimiterServlet` (a request-rate cap, not a per-request cost cap): [8](#0-7) [9](#0-8) [10](#0-9) 

This mirrors the report exactly: the codebase already contains the "correct" fix pattern for the same underlying data (`getAssetIssueList(offset, limit)`, `getPaginatedExchangeList(offset, limit)`, `getPaginatedProposalList(offset, limit)`, which cap `limit` via `ASSET_ISSUE_COUNT_LIMIT_MAX`/`EXCHANGE_COUNT_LIMIT_MAX`/`PROPOSAL_COUNT_LIMIT_MAX`): [11](#0-10) [12](#0-11) 

Yet the un-paginated `EmptyMessage`-based endpoints (`GetAssetIssueList`, `ListExchanges`, `ListProposals`) remain exposed alongside the paginated ones, giving any anonymous caller a way to force the full, unbounded scan regardless of how large the store grows.

### Impact Explanation
As the number of asset issues, exchanges, or proposals grows on-chain, a single anonymous RPC/HTTP call to any of these three endpoints forces the full node to: (1) open a store iterator over the entire dataset, (2) materialize every entry into a `List`, (3) sort it, and (4) serialize the whole thing into a protobuf/JSON response. This is CPU, memory, and I/O cost fully proportional to on-chain state size and not capped by the caller-supplied parameters (there are none). Repeated concurrent calls can degrade node responsiveness or exhaust memory, a denial-of-service vector against publicly reachable Full/Solidity/PBFT node RPC and HTTP APIs — directly analogous to the accepted `getTickState()` "might run out of gas"/unbounded-iteration class, translated to node resource exhaustion instead of EVM gas exhaustion.

### Likelihood Explanation
Reaching this code path requires nothing more than an anonymous gRPC or HTTP call to a public node — no signed transaction, no privileged role, and no special network position. `RateLimiterServlet` throttles request *frequency* but does not bound the *cost* of a single accepted request, so even a rate-limited caller can trigger full-store scans repeatedly, and each scan gets more expensive over time as asset issues/exchanges/proposals accumulate on mainnet. This makes the likelihood moderate-to-high on any long-lived, heavily used chain, consistent with the original report's judged severity (functionality/availability impact).

### Recommendation
- Deprecate/remove (or internally redirect to a bounded default) the un-paginated `GetAssetIssueList`, `ListExchanges`, and `ListProposals` RPCs/HTTP endpoints, or enforce a hard maximum item count analogous to `ASSET_ISSUE_COUNT_LIMIT_MAX`/`EXCHANGE_COUNT_LIMIT_MAX`/`PROPOSAL_COUNT_LIMIT_MAX` even in the "list all" code path.
- Alternatively, have `Wallet.getAssetIssueList()`, `getExchangeList()`, and (indirectly) `listProposals()` internally delegate to their paginated counterparts with a capped default limit rather than calling `getAllAssetIssues()`/`getAllExchanges()`/`getAllProposals()` directly.
- Add per-request cost accounting (e.g., an item-count/time budget) in `RateLimiterServlet`/gRPC interceptors so a single request cannot scan unbounded state regardless of endpoint.

### Proof of Concept
1. Deploy/observe a Full Node with the HTTP API enabled (default config exposes `/wallet/...`).
2. Issue many `AssetIssueContract`/`ExchangeCreateContract` transactions over time (or wait for organic chain growth) so `AssetIssueStore`/`ExchangeStore` contain a large number of entries.
3. As an anonymous client, repeatedly call:
   - `GET/POST http://<node>/wallet/getassetissuelist`
   - `GET/POST http://<node>/wallet/listexchanges`
   - `GET/POST http://<node>/wallet/listproposals`
   or the equivalent gRPC calls `GetAssetIssueList(EmptyMessage)`, `ListExchanges(EmptyMessage)`, `ListProposals(EmptyMessage)`.
4. Each call triggers `AssetIssueStore.getAllAssetIssues()` / `ExchangeStore.getAllExchanges()` / `ProposalStore.getAllProposals()`, which fully iterates and sorts the entire store and serializes it to the response with no size cap, unlike `GetPaginatedAssetIssueList`/`GetPaginatedExchangeList`/`GetPaginatedProposalList`, which cap results via `*_COUNT_LIMIT_MAX`. Sustained/concurrent calls against a large store degrade node performance, demonstrating the DoS.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
