### Title
`ConfigLoader.load` unconditionally writes global `CommonParameter.ENERGY_LIMIT_HARD_FORK` even when `isolate=true`, breaking thread-local isolation for solidity/PBFT constant calls - ([File: actuator/src/main/java/org/tron/core/vm/config/ConfigLoader.java])

### Summary
`ConfigLoader.load` is documented and designed so that `isolate=true` confines all VM config flags read from a possibly-stale (solidity/PBFT) `DynamicPropertiesStore` snapshot to a `ThreadLocal` view, leaving the process-wide `VMConfig.globalSnapshot` untouched. However, the call `VMConfig.initVmHardFork(checkForEnergyLimit(ds))` on line 24 executes unconditionally before the `isolate` check, and `VMConfig.initVmHardFork` writes directly to the static, non-thread-local field `CommonParameter.ENERGY_LIMIT_HARD_FORK` regardless of `isolate`. This means a constant call served against the solidity/PBFT store can overwrite the global hard-fork flag that the concurrent HEAD block-processing thread relies on.

### Finding Description
`ConfigLoader.load` in `actuator/src/main/java/org/tron/core/vm/config/ConfigLoader.java` is called by `VMActuator.validate` [1](#0-0)  both for HEAD block/tx processing (`isolate=false`) and for constant calls (`isolate=true`, driven by `isConstantCall`). The isolate flag is meant to route all snapshot fields either into `VMConfig.setLocalSnapshot` (thread-local) or `VMConfig.setGlobalSnapshot` (process-wide, volatile) [2](#0-1) .

But before that branch, line 24 does:
```java
VMConfig.initVmHardFork(checkForEnergyLimit(ds));
```
executed unconditionally, independent of `isolate` [3](#0-2) . `VMConfig.initVmHardFork` writes straight into the static field `CommonParameter.ENERGY_LIMIT_HARD_FORK`, which has no thread-local counterpart at all [4](#0-3) . `checkForEnergyLimit(ds)` derives its result from `ds.getLatestBlockHeaderNumber()` on whatever `DynamicPropertiesStore` was passed in — for a solidity/PBFT-scoped constant call this is the solidity/PBFT store, not the HEAD store [5](#0-4) .

Reachability: an unprivileged, anonymous client can hit `/walletsolidity/triggerconstantcontract`, handled by `TriggerConstantContractOnSolidityServlet`, which wraps the normal `TriggerConstantContractServlet.doPost` in `walletOnSolidity.futureGet(...)` [6](#0-5) . That in turn calls `wallet.triggerConstantContract(...)` [7](#0-6) , which eventually invokes `VMActuator.validate` with `isConstantCall=true` and a `StoreFactory` bound to the solidity/PBFT `ChainBaseManager`, thereby calling `ConfigLoader.load(solidityStoreFactory, true)`. This can run concurrently on a separate request-handling thread while the block-processing thread calls `ConfigLoader.load(headStoreFactory, false)`.

Because `initVmHardFork` bypasses the isolate/local-vs-global distinction entirely, a race is real: if the solidity/PBFT store is behind HEAD across the `blockNumForEnergyLimit` activation boundary, the constant-call thread can write `false` into `CommonParameter.ENERGY_LIMIT_HARD_FORK` immediately after (or racing with) the HEAD thread writing `true` (or vice versa), leaving the global flag transiently inconsistent with the actual HEAD state that block validation is currently processing. No existing check (`ForkController` gates, `TransactionCapsule.validateSignature`, actuator `validate()`, energy accounting) protects this particular static field, since those all operate on `DynamicPropertiesStore`-derived per-call state rather than this global mutable flag.

### Impact Explanation
This is a transient consensus-relevant flag flip affecting `CommonParameter.ENERGY_LIMIT_HARD_FORK`, used elsewhere (e.g., `StorageUtils.getEnergyLimitHardFork()`) to gate energy-limit-related logic paths [8](#0-7) . If read by the HEAD block-processing path at the exact moment it has been overwritten by a concurrent solidity/PBFT-scoped constant call, this could cause a single node to momentarily apply the wrong energy-limit-hard-fork behavior during block validation — a divergent-state / consensus-determinism risk local to the node experiencing the race (matches the "consensus divergence" bounty impact class), though it is scoped to a narrow flag and a narrow race window rather than a full chain split, since `ForkController` fork-activation logic for most hard forks is otherwise gated by proper per-transaction `DynamicPropertiesStore` reads.

### Likelihood Explanation
The race requires: (1) the node runs the solidity/PBFT HTTP API (default-enabled in many full-node configurations, not a non-default requirement), (2) the solidity/PBFT store genuinely lags HEAD across the `blockNumForEnergyLimit` boundary (happens naturally for a limited window around that block height only), and (3) precise timing overlap between an incoming constant-call request and HEAD block processing. An unprivileged attacker only needs to send ordinary `triggerconstantcontract` requests to `/walletsolidity/...`, at negligible cost, and can send many concurrently to increase the chance of overlap, but the exploitable window is bounded to the fork-activation block range, making it low-probability outside of that transition and not persistently exploitable.

### Recommendation
Guard the `VMConfig.initVmHardFork(checkForEnergyLimit(ds))` call with the same `isolate` branching used for the rest of the snapshot: either move it inside the `if (isolate) {...} else {...}` block and only call it in the `else` (global) branch, or introduce a thread-local-aware equivalent (e.g., store `energyLimitHardFork` inside `VMConfig.Snapshot` and expose it via `VMConfig.current()` instead of mutating the static `CommonParameter.ENERGY_LIMIT_HARD_FORK` field directly).

### Proof of Concept
```java
// JUnit-style race demonstration (conceptual; exact wiring of StoreFactory-backed
// solidity/head DynamicPropertiesStore mocks is implementation detail):
@Test
public void configLoader_isolate_doesNotProtect_energyLimitHardFork() throws InterruptedException {
  DynamicPropertiesStore staleSolidityDs = mock(DynamicPropertiesStore.class);
  when(staleSolidityDs.getLatestBlockHeaderNumber()).thenReturn(0L); // below fork block

  DynamicPropertiesStore headDs = mock(DynamicPropertiesStore.class);
  when(headDs.getLatestBlockHeaderNumber()).thenReturn(Long.MAX_VALUE); // past fork block

  StoreFactory solidityFactory = storeFactoryFor(staleSolidityDs);
  StoreFactory headFactory = storeFactoryFor(headDs);

  AtomicBoolean sawStaleValueOnHeadThread = new AtomicBoolean(false);
  ExecutorService pool = Executors.newFixedThreadPool(2);
  Runnable solidityCaller = () -> {
    for (int i = 0; i < 100000; i++) {
      ConfigLoader.load(solidityFactory, true); // isolate=true, simulating triggerconstantcontract
    }
  };
  Runnable headProcessor = () -> {
    for (int i = 0; i < 100000; i++) {
      ConfigLoader.load(headFactory, false); // isolate=false, block processing
      if (!CommonParameter.ENERGY_LIMIT_HARD_FORK) {
        sawStaleValueOnHeadThread.set(true); // should always be true (post-fork) but can be flipped false
      }
    }
  };
  pool.submit(solidityCaller);
  Future<?> f = pool.submit(headProcessor);
  f.get();
  pool.shutdown();

  // DETERMINISM check: HEAD thread's view of ENERGY_LIMIT_HARD_FORK must never be
  // clobbered by the solidity-derived value.
  Assert.assertFalse(
      "CommonParameter.ENERGY_LIMIT_HARD_FORK was overwritten by stale solidity store",
      sawStaleValueOnHeadThread.get());
}
```
Expected: the assertion fails on the current code, demonstrating that `initVmHardFork` writes bypass the `isolate` guard and can be observed as flipped by the concurrent non-HEAD thread.
