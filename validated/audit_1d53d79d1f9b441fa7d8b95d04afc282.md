### Title
Duplicate-witness gas/state-bloat griefing via unmerged votes in `VoteWitnessActuator` - (File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java)

### Summary
`VoteWitnessActuator`, the actuator that handles the standard, anonymously-broadcastable `VoteWitnessContract` transaction, allows a transaction to list the same witness address multiple times (up to `MAX_VOTE_NUMBER = 30`) without any deduplication check, mirroring the `Allowed*Enforcer` bug class where duplicate entries in attacker-controlled terms are never rejected. The votes are appended as separate `Vote` entries into the persistent `Account.votes` protobuf field, which is walked with an O(n) linear loop by many downstream consumers, on every future transaction/maintenance cycle that touches that account — unlike the classic report's single-transaction gas cost, here the bloat becomes part of persistent chain state.

### Finding Description
`VoteWitnessActuator.validate()` iterates over `contract.getVotesList()` and validates each vote's address/amount/existence, but never checks that witness addresses are distinct: [1](#0-0) 

Compare this to `AccountPermissionUpdateActuator.checkPermission()`, which explicitly deduplicates key addresses via `.stream().distinct()` and rejects the transaction if any duplicates are found: [2](#0-1) 

No equivalent check exists for `VoteWitnessContract`. In `execute()`, `countVoteAccount()` then appends every vote entry from the transaction — including duplicates for the same witness — directly onto the account, without merging: [3](#0-2) 

`AccountCapsule.addVotes()` simply appends a new `Vote` entry to the protobuf-backed list on every call — there is no map/merge logic: [4](#0-3) 

This is functionally identical to the reported bug class: the same address (witness) can be repeated arbitrarily (bounded only by `MAX_VOTE_NUMBER`), inflating a data structure (`votes` list) that is subsequently scanned linearly by many other code paths, e.g.:
- `AccountCapsule.getTronPowerUsage()` sums over the whole list.
- `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator.updateVote()` and the native `VoteWitnessProcessor.updateVote()` iterate the full votes list on every subsequent freeze/unfreeze action.
- TVM precompiles `VoteCount`, `UsedVoteCount` linearly scan `accountCapsule.getVotesList()` for a fixed, size-independent energy charge (500/20), so their real CPU cost scales with list size while the energy fee charged does not. [5](#0-4) 
- Maintenance cycle logic that tallies witness votes across all accounts scans every account's votes list once per maintenance cycle.

Notably, the newer nativecontract path `VoteWitnessProcessor.execute()` (used for TVM-triggered voting) already fixes this exact issue by merging duplicate witness entries into a `HashMap` before writing, proving the project is aware the merge is necessary but the legacy `VoteWitnessActuator` path was never updated to match: [6](#0-5) 

### Impact Explanation
Unlike the original `Allowed*Enforcer` report (where duplicate entries only inflate one transaction's own gas cost), here the duplicate `Vote` entries are written into persistent on-chain `Account` state via `accountStore.put(...)`. Every subsequent transaction or maintenance cycle that reads that account's votes (unfreeze actuators, TVM vote precompiles, DPoS maintenance vote tallying) pays a linear cost proportional to the bloated list, repeatedly, for as long as the account holds those votes. An attacker can repeatedly re-submit `VoteWitnessContract` with up to 30 duplicate entries per transaction (constrained only by owned TRON Power/threshold checks, which duplicate votes to the same witness do not multiply beyond the sum check), causing unbounded growth in state size for that account and increased processing cost for anyone (including block-producing witnesses during block validation and maintenance) who has to read/iterate that account's votes. This is a DoS/gas-griefing vector against node processing and against the account's own future transactions, rather than a direct fund-loss bug — bounded by `MAX_VOTE_NUMBER=30` per transaction but unbounded across repeated transactions since votes are always fully replaced/cleared and re-added each time (`clearVotes()` then re-append), so the list size is capped at 30 per vote operation, but this still triggers repeated O(30) scans on every downstream read where legitimate accounts would have far fewer distinct entries, and can be repeated at negligible cost by any account holding minimal TRON Power.

### Likelihood Explanation
High reachability: `VoteWitnessContract` is a standard, unprivileged transaction type broadcastable by any account with any non-zero TRON Power (frozen balance). No special permissions or precompile access are required. The exploit requires only constructing a transaction with the same witness address repeated in the `votes` field, which the actuator's `validate()` never rejects.

### Recommendation
Add a duplicate-address check in `VoteWitnessActuator.validate()` analogous to the one already present in `AccountPermissionUpdateActuator.checkPermission()` — either reject transactions containing duplicate `vote_address` entries, or merge duplicate entries into a single vote per witness (summing vote counts) before persisting, matching the behavior already implemented in `VoteWitnessProcessor.execute()`. Applying the same `voteMap`-merge pattern used in the native contract path to `countVoteAccount()` would close this gap.

### Proof of Concept
1. Freeze a small balance to obtain non-zero TRON Power for `OWNER_ADDRESS`.
2. Construct a `VoteWitnessContract` with the owner address and 30 `Vote` entries, all pointing to the same valid witness address, with `voteCount` values whose sum does not exceed `tronPower` (e.g., `voteCount = tronPower / 30` each).
3. Broadcast the transaction; `VoteWitnessActuator.validate()` passes (no distinct-address check), and `countVoteAccount()` appends all 30 duplicate `Vote` entries to `AccountCapsule.votes` via repeated `addVotes()` calls (see `framework/src/test/java/org/tron/core/actuator/VoteWitnessActuatorTest.java` `getRepeateContract`/`vote1WitnssOneMoreTiems` test helpers which already demonstrate the actuator accepting a repeated-witness vote list up to `MAX_VOTE_NUMBER`).
4. Observe `accountCapsule.getVotesList().size() == 30` after execution instead of `1`, and that any subsequent call touching this account's votes (e.g., `UnfreezeBalanceActuator`, TVM `VoteCount`/`UsedVoteCount` precompile calls, or the DPoS maintenance witness tally) must iterate all 30 duplicate entries instead of 1, for a constant, size-independent energy/fee charge.

    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }

  public static class VoteCount extends PrecompiledContract {

    @Override
    public long getEnergyForData(byte[] data) {
      return 500;
    }

    @Override
    public Pair<Boolean, byte[]> execute(byte[] data) {
      if (data == null || data.length != 2 * WORD_SIZE) {
        return Pair.of(true, longTo32Bytes(0L));
      }

      DataWord[] words = DataWord.parseArray(data);
      byte[] address = words[0].toTronAddress();
      AccountCapsule accountCapsule = this.getDeposit().getAccount(address);

      long voteCount = 0;
      if (accountCapsule != null && !accountCapsule.getVotesList().isEmpty()) {
        ByteString witness = ByteString.copyFrom(words[1].toTronAddress());
        for (Protocol.Vote vote : accountCapsule.getVotesList()) {
          if (witness.equals(vote.getVoteAddress())) {
            voteCount += vote.getVoteCount();
          }
        }
      }

      return Pair.of(true, longTo32Bytes(voteCount));
    }
  }

  public static class UsedVoteCount extends PrecompiledContract {
