### Title
Public transaction-submission HTTP server has no header/body read timeout, enabling slow-request connection exhaustion DoS - ([File: crates/apollo_http_server/src/http_server.rs])

### Summary
The public-facing `apollo_http_server`, which exposes `/gateway/add_transaction` and `/gateway/add_rpc_transaction` to any unprivileged transaction sender, is served via bare `axum::serve(listener, app)` with no per-connection header-read timeout, body-read timeout, or overall request timeout configured.

### Finding Description
`HttpServer::run` binds a `TcpListener` and hands it directly to `axum::serve` with no timeout middleware or hyper builder configuration: [1](#0-0) 
The router only applies `RequestBodyLimitLayer` (byte-size cap) and `RequestDecompressionLayer`; there is no `tower::timeout::TimeoutLayer`, no hyper `http1_header_read_timeout`, and no idle/keepalive timeout comparable to Node's `server.timeout`/`headersTimeout`/`requestTimeout`: [2](#0-1) 
By contrast, the internal service-to-service `RemoteComponentServer`/`RemoteComponentClient` machinery does implement HTTP/2 keepalive intervals/timeouts and client-side request timeouts (`request_timeout_ms`, `keepalive_interval_ms`, `keepalive_timeout_ms`), confirming the sequencer codebase is otherwise timeout-aware for its internal RPC surface but not for the externally reachable transaction ingress: [3](#0-2) [4](#0-3) 

Because `RequestBodyLimitLayer` only bounds the number of bytes eventually accepted, and does not bound the time taken to deliver them, an attacker can, exactly as in the reported Node.js CVE-2020-8251 pattern, open many TCP connections to the gateway HTTP endpoint and drip-feed headers/body at an arbitrarily slow rate (or stop after headers, before starting the body) without ever hitting an idle timeout, since none exists. Each such connection remains open and consumes a listener/OS socket resource indefinitely.

### Impact Explanation
An unprivileged network attacker (no special credentials, only needs network access to a sequencer node's HTTP ingress) can exhaust the pool of accepted TCP connections/file descriptors on the node's public transaction-submission endpoint by holding open many slow/incomplete requests. This blocks legitimate transaction senders from submitting transactions to that sequencer, i.e., "a network unable to confirm new transactions" through that ingress path, matching the qualifying impact criteria.

### Likelihood Explanation
Likelihood is high: the attack requires only standard TCP/HTTP client tooling, no privileged access, no protocol-level exploit, and is described concretely in the referenced report with a minimal reproduction script. The `/gateway/add_transaction` and `/gateway/add_rpc_transaction` endpoints are, by design, open to arbitrary unauthenticated senders.

### Recommendation
Add explicit timeouts to the public HTTP server: configure a header-read timeout and an overall request/body timeout (e.g., via `tower_http::timeout::TimeoutLayer` and/or hyper/axum connection builder options such as `http1_header_read_timeout`), analogous to Node's `requestTimeout` mitigation from PR nodejs/node#33304, and consider bounding total idle connection lifetime and per-IP concurrent connection counts at the listener/reverse-proxy level.

### Proof of Concept
1. Start the sequencer node with `components.http_server.execution_mode = Enabled`.
2. From an attacker host, open N TCP connections to the gateway's `add_transaction` port, on each: send `POST /gateway/add_transaction HTTP/1.1` request line and headers, including a large `Content-Length`, then send the body one byte at a time with long delays (analogous to the report's sample `net.createConnection` script).
3. Observe that none of the connections are closed by the server due to a header/body timeout (no such timeout exists in `HttpServer::app`/`HttpServer::run`), so connections accumulate.
4. Repeat with enough parallel connections to exhaust the listener's accept queue/OS FD limit, after which legitimate `add_transaction` requests can no longer be served.
