### Title
Duplicate keys in an unverified `KvOnly` state-snapshot restore chunk corrupt the persisted `StateStorageUsage`/item count while silently collapsing to the last write - ([File: storage/aptosdb/src/state_restore/mod.rs])

### Summary
`StateValueRestore::add_chunk` (`storage/aptosdb/src/state_restore/mod.rs:73-112`) accumulates a running `StateStorageUsage` by iterating every `(k, v)` pair in the incoming chunk and calling `usage.add_item(...)` once per pair [1](#0-0) , then separately builds the actual `kv_batch` to persist by `.collect()`-ing the same chunk into a keyed map `((k, self.version), Some(v))` [2](#0-1) . If the chunk contains a duplicate key, the `usage` counter is incremented for **both** occurrences, but the keyed-map collection silently collapses the duplicate to a single (last) entry actually written to storage — exactly the "tracked total vs. actual stored value" divergence in the seed report.

### Finding Description
This divergence is only exploitable because `StateSnapshotRestoreMode::KvOnly` bypasses all ordering/proof checks. In `StateSnapshotRestore::add_chunk`, the `Default` mode calls `tree_restore.verify_chunk(...)` *before* the KV write, which enforces `hashed_key > prev_leaf.account_key()` for every entry (including within a single chunk) and aborts the whole operation on failure [3](#0-2) . But the `KvOnly` branch calls only `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?` and completely ignores the `proof` argument — no merkle-proof verification and no monotonic/duplicate-key check occurs at all [4](#0-3) . This mode is actively used in production restore flows: `RestoreCoordinator::run_impl` invokes `StateSnapshotRestoreMode::KvOnly` to restore the pre-`ledger_history_start_version` KV snapshot, downloaded from a backup manifest [5](#0-4) , and that same restore run uses `VerifyExecutionMode::NoVerify` for subsequent transaction replay [6](#0-5) , so nothing downstream re-checks that the persisted usage matches the real KV/tree contents for that snapshot.

The persisted `usage` is not just internal bookkeeping: it flows into `StateStore::kv_finish` → `ledger_db.metadata_db().put_usage(version, usage)` [7](#0-6) , is read back via `StateStore::get_usage` [8](#0-7) , and is exposed to the Move VM through the `get_state_storage_usage_only_at_epoch_beginning` native [9](#0-8) , which is written into the on-chain `state_storage::StateStorageUsage` resource at every epoch boundary and consumed by `storage_gas` [10](#0-9) .

### Impact Explanation
A node that restores from a crafted or corrupted backup manifest (or hits this bug due to any producer emitting a duplicate key inside a single KvOnly restore chunk) ends up with a `StateStorageUsage`/`VersionData.state_items`/`total_state_bytes` value in its metadata DB that overcounts relative to the actual number of distinct keys physically written, while the underlying KV data for the duplicated key only reflects the last write (dropping the other value entirely, not merely double-counted). This corrupts a durable, consensus-consumed value (`state_storage::StateStorageUsage`) with no independent cross-check, since `KvOnly` restores skip proof verification and the accompanying transaction replay uses `NoVerify`. Downstream, gas cost of storage operations calculated by `storage_gas.move` would diverge for that node/subsequent epoch versus a node that restored honestly, a form of state/computation divergence rooted in unauthenticated durable data.

### Likelihood Explanation
This requires a backup source (self-hosted or third-party manifest) to supply a chunk with a duplicate key for `KvOnly` restores; there is no cryptographic binding checked in that path, so a compromised or buggy backup pipeline is sufficient — no privileged access to a live validator is needed, only control over (or corruption of) backup archive content that an operator chooses to restore from.

### Recommendation
In `StateValueRestore::add_chunk`, deduplicate the incoming chunk by key (keeping the last occurrence) before computing `usage`, or reject the chunk if adjacent/duplicate keys are detected, matching the invariant enforced elsewhere for `Default`-mode/tree restores. Alternatively, enforce the same strictly-increasing-key check independent of the JMT proof when running in `KvOnly` mode.

### Proof of Concept
1. Build a `StateSnapshotRestore` with `StateSnapshotRestoreMode::KvOnly`.
2. Call `add_chunk` with a chunk `vec![(key_a, value_v1), (key_a, value_v2)]` (same key twice, distinct values/sizes), and any dummy proof (ignored in this mode).
3. Observe `usage.add_item` is called twice (once per `key_a` entry) in `storage/aptosdb/src/state_restore/mod.rs:96-99`, inflating `items`/`bytes` by one extra entry's worth.
4. Observe the actual `kv_batch` written to storage contains only one entry for `key_a` (`value_v2`), because `.collect()` into the keyed map at `storage/aptosdb/src/state_restore/mod.rs:101-105` overwrites the first with the second.
5. Call `finish()`; the persisted `StateStorageUsage` (via `kv_finish`) now overcounts relative to the actual number of stored items/bytes, with no proof-verification failure raised anywhere in the `KvOnly` path.

fn native_get_usage(
    context: &mut SafeNativeContext,
    _ty_args: &[Type],
    _args: VecDeque<Value>,

    assert!(_ty_args.is_empty());
    assert!(_args.is_empty());

    context.charge(STATE_STORAGE_GET_USAGE_BASE_COST)?;

    let ctx = context.extensions().get::<NativeStateStorageContext>();
    let usage = ctx.resolver.get_usage().map_err(|err| {
        PartialVMError::new(StatusCode::VM_EXTENSION_ERROR)
            .with_message(format!("Failed to get state storage usage: {}", err))
    })?;

    Ok(smallvec![Value::struct_(Struct::pack(vec![
        Value::u64(usage.items() as u64),
        Value::u64(usage.bytes() as u64),
    ]))])
}
