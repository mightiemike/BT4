### Title
Zero-value liquidity injection due to unguarded floor-division rounding in `ExchangeInjectActuator` - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
The TRC10 Exchange module (java-tron's on-chain AMM for TRC10↔TRX/TRC10↔TRC10 pairs) allows any account to create a pool with an arbitrary, highly skewed token ratio via `ExchangeCreateContract`, and lets any account later inject additional liquidity via `ExchangeInjectContract`. The counter-side amount required for an injection is computed with integer floor division and is never checked to be non-zero before the actuator commits state changes, mirroring the "initial deposit / ratio manipulation" bug class from the external report: a cheaply-created skew in the pool ratio causes a legitimate user's later interaction to receive/contribute effectively "0" on one side while still spending real assets and permanently distorting the pool.

### Finding Description
`ExchangeCreateActuator` lets any account create a pool with essentially any ratio between `first_token_balance` and `second_token_balance`, bounded only by `getExchangeBalanceLimit()`, with no minimum-liquidity or maximum-ratio safeguard: [1](#0-0) 

When a second account later injects liquidity through `ExchangeInjectActuator.execute`, the "other side" amount is derived via `floorDiv`: [2](#0-1) 

If the pool ratio between the injected token and the other token is large enough (e.g. `secondTokenBalance` ≫ `firstTokenBalance`, or vice versa) relative to the injector's `tokenQuant`, `floorDiv(secondTokenBalance * tokenQuant, firstTokenBalance)` (or the symmetric case) truncates to `0`. There is no validation step in the actuator that rejects an injection whose computed `anotherTokenQuant` is `0` — execution proceeds, the injector's real assets (`tokenQuant`) are deducted from their account and added into the pool balance via `exchangeCapsule.setBalance(...)`, while the "other" amount contributed is `0`. This both (a) lets an injector unilaterally shift the pool ratio further without paying the counter-asset, and (b) can be leveraged by an attacker who first creates/skews a pool cheaply (low `first_token_balance`/`second_token_balance` amounts are permitted, see `firstTokenBalance <= 0` check only) so that subsequent normal-sized injections or swaps by other users round to zero on one leg, silently altering the AMM price/reserve accounting (`exchangeCapsule.setBalance`) without a proportionate contribution — the on-chain analog of the reported "0 shares minted for a deposit" griefing pattern, since Exchange balances directly determine AMM pricing (`ExchangeCapsule.transaction`, `ExchangeProcessor`/`SafeExchangeProcessor`) used for all subsequent trades: [3](#0-2) 

### Impact Explanation
Successful exploitation corrupts the on-chain AMM reserve accounting for a TRC10 exchange pool: legitimate users' subsequent injections or swaps use a manipulated ratio, and the pool state (`ExchangeV2Store`) becomes internally inconsistent (one side inflated with zero-cost contribution). This causes asset/accounting corruption within the exchange pool and mispriced swaps for all subsequent traders on that pool — a direct, on-chain accounting impact reachable from an ordinary broadcast transaction, without any privileged role.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the attacker to first establish (or wait for) a sufficiently skewed pool ratio and for a victim to inject/trade an amount small enough relative to that ratio to trigger the floor-to-zero rounding. `ExchangeCreateContract` permits creating pools with very small balances on one side (only `> 0` is enforced) which makes engineering such a skew inexpensive, similar to the low-cost griefing described in the original report.

### Recommendation
In `ExchangeInjectActuator.execute`/`doValidate`, explicitly reject injections where the computed `anotherTokenQuant` (or the primary `tokenQuant`'s proportional contribution) rounds to `0`, and consider enforcing a minimum initial-liquidity / minimum-ratio constraint in `ExchangeCreateActuator.doValidate` (e.g., reject creation or subsequent inject/trade attempts when the resulting balance ratio exceeds a sane bound), analogous to the "minimum initial deposit" mitigation recommended for ERC-4626-style vaults.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` with `first_token_balance = 1` and `second_token_balance = balanceLimit` (or another extreme ratio permitted by `getExchangeBalanceLimit()`), passing the `firstTokenBalance <= 0 || secondTokenBalance <= 0` check in `ExchangeCreateActuator.doValidate`.
2. A victim later calls `ExchangeInjectContract` supplying `tokenId = firstTokenID` with a modest `quant` (e.g. `quant = 1`).
3. In `ExchangeInjectActuator.execute`, `anotherTokenQuant = floorDiv(secondTokenBalance * 1, firstTokenBalance)` — with `firstTokenBalance = 1` this instead inflates, but the symmetric case (injecting the large-balance side with a small quant relative to the other) truncates `anotherTokenQuant` to `0`.
4. `exchangeCapsule.setBalance(...)` commits the pool with the victim's real tokens added on one side and `0` added on the other, and `accountCapsule.reduceAssetAmountV2(anotherTokenID, 0, ...)` is a no-op — the victim has permanently shifted pool reserves/price for zero counter-payment risk to the attacker who set up the skew, corrupting the AMM accounting used by `ExchangeCapsule.transaction` for all future trades.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
