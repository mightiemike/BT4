### Title
Unhandled TypeError from `new URL()` in `sanitizeHost()` on malicious base64 host input - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
`sanitizeHost()` decodes an attacker-supplied base64 `host` value with `atob()` and passes the raw decoded bytes directly into `new URL('https://' + decoded)` with no `try/catch`. Because the base64 format check does not constrain the *decoded* content, an attacker can craft a `host` value that decodes into a string containing forbidden host code points (e.g. `<`, `>`, `@`, `\0`, `^`, `|`), causing the WHATWG URL parser to throw an uncaught `TypeError`, which propagates out of `sanitizeHost()` instead of being represented as `null`/`InvalidHostError`.

### Finding Description
`sanitizeHost()` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` only validates that the *base64 encoding* is well-formed via `base64regex.test(host)`: [1](#0-0) 

It then calls `decodeHost(sanitizedHost)` (a thin wrapper around `atob`) and feeds the result directly into `new URL('https://' + decoded)`: [2](#0-1) 

Nothing constrains the *decoded* bytes — any arbitrary string that happens to be valid base64 will pass the regex, including one that decodes to text containing forbidden host code points (`<`, `>`, `@`, `[`, `]`, `^`, `|`, `\`, or NUL). The WHATWG URL parser throws `TypeError: Invalid URL` for such inputs (note: literal tab/CR/LF characters are stripped by the parser before host parsing and won't trigger this, but other forbidden host code points will). This `new URL()` call is not wrapped in a `try/catch`, so the exception is not converted into the library's typed `InvalidHostError` and instead propagates as an unhandled `TypeError`.

Reachable, unauthenticated call sites include `buildEmbeddedAppUrl`/`getEmbeddedAppUrl` in `packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts`, which reads the `host` query parameter straight from the incoming request and calls `sanitizeHost(config)(host, true)`: [3](#0-2) 

`validateShopAndHostParams` (used in `authenticate.ts` for both shopify-app-remix and shopify-app-react-router) also calls `api.utils.sanitizeHost(url.searchParams.get('host')!)` on the raw request query param before any HMAC/session verification: [4](#0-3) 

Note the question incorrectly cites `packages/apps/shopify-api/lib/auth/oauth/refresh-token.ts` as the location — that file only calls `sanitizeShop`, not `sanitizeHost`, and has no relation to this bug: [5](#0-4) 

### Impact Explanation
This is a DoS in an authentication/request-validation path: any unauthenticated request that includes a crafted `host` query parameter can cause an unhandled `TypeError` inside `sanitizeHost()`, instead of the intended fail-closed `InvalidHostError`/`null` result. Depending on the host app's error handling, this could crash the request handler process or return an unstructured 500 rather than a controlled invalid-host response — a scoped denial-of-service / unhandled-exception bug in the host validation logic, not a full outage of the library itself.

### Likelihood Explanation
The attack requires no privileges: any anonymous client can send an HTTP request to an embedded-app route with an arbitrary `host` query parameter. Constructing a valid base64 string whose decoded content contains a forbidden host code point (e.g. base64 of `"a<b.myshopify.com"`) is trivial and fully attacker-controlled. This is reliably repeatable on every request.

### Recommendation
Wrap the `new URL(...)` call in `sanitizeHost()` in a `try/catch`, treating any parsing failure the same as an invalid host (`sanitizedHost = null`, and throw `InvalidHostError` when `throwOnInvalid` is set), so malformed decoded content never produces an unhandled exception.
