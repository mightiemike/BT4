## Finding

Replay-verify tooling in Aptos (`storage/db-tool`'s `replay-verify` binary and the chunk executor's replay path) authenticates re-executed transactions against archived/backup `TransactionInfo` records using a single comparator, `TransactionOutput::ensure_match_transaction_info`. That comparator never checks the state-checkpoint root hash(es), so a divergence in the committed state tree root between the archived ledger and freshly re-executed state passes replay-verify as a clean match.

### Title
Replay-verify accepts divergent state-checkpoint roots as valid because `ensure_match_transaction_info` never checks `state_checkpoint_hash` - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole authenticity check used by the archive replay-verify tool (`storage/db-tool/src/replay_on_archive.rs`) and by the chunk executor's `verify_execution` path (`execution/executor/src/chunk_executor/mod.rs`) to confirm that locally re-executed transactions match the trusted, backed-up `TransactionInfo` (which is itself bound into the transaction accumulator/ledger proof chain). This comparator checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it deliberately skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the actual global state-tree root commitments produced at checkpoint boundaries.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates status, gas, write-set hash, and event root hash, but the function's own trailing comment documents that it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)" and that this allows "replay-verify tooling (e.g. db-tool's `replay_on_archive`) [to] report a successful replay even when the authenticated position state root diverges from local execution" [2](#0-1) .

The checkpoint hashes that are skipped are exactly the state-tree root commitments assembled per-transaction at checkpoint versions in `DoLedgerUpdate::assemble_transaction_infos`, where `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` are folded into the `TransactionInfo` that ultimately gets hashed into the transaction accumulator leaf [3](#0-2) . These are the fields that authenticate the actual Merkle/Jellyfish state root, distinct from the write-set hash which only proves the shape of the write set applied by one transaction, not the resulting global state root.

This comparator is used in two mainnet-relevant, unprivileged verification paths:
1. `storage/db-tool`'s `replay_on_archive` binary, whose `execute_and_verify` calls `ensure_match_transaction_info` as the only check that re-executed output matches the archived, ledger-info-anchored `TransactionInfo` [4](#0-3) .
2. The chunk executor's `verify_execution`, used during state-sync/backup verification and fast-forward, which calls the same comparator on transactions replayed from a backup chunk [5](#0-4) .

Because neither path independently re-derives and compares the state-checkpoint hash, a stored `TransactionInfo` (or a bug in state-tree assembly/hashing on the executing node) whose `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` diverges from what local re-execution actually produced will not be caught. The tool will report "replay OK" while the underlying committed state root is not proven consistent with re-executed state.

### Impact Explanation
This breaks the core promise of replay-verify: that data pulled from backups/archives and independently re-executed is provably consistent with the locally computed ledger state. A wrong state-checkpoint root — whether from storage corruption, a state-tree computation bug, or a malicious/compromised backup source — can be accepted as "verified" by the replay-verify tooling and by chunk-executor verification during state sync, even though the actual state root differs from what execution produced. This is a proof-integrity failure matching the "wrong accumulator root ... accepted as valid" and "replay path must not reinterpret committed data into a different ledger state" categories: verification infrastructure that operators and auditors rely on to catch exactly this class of divergence silently passes it through.

### Likelihood Explanation
The gap is deterministic and unconditional — it is not behind a feature flag; the state_checkpoint_hash check is simply absent from the comparator for all TransactionInfo variants (V0 and V1), not just the newer trading-native hot-state/position fields. Any node operator or automated system running `replay-verify` against a backup, or a full node validating a downloaded chunk via chunk-executor verification, is affected whenever a state-root mismatch (from any root cause — storage bug, tree-assembly bug, or corrupted backup) exists but the write set/events/status/gas happen to match.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally-computed `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) against the value in `txn_info`, failing verification on mismatch, before this comparator is relied upon as an authoritative check in `replay_on_archive` and chunk-executor `verify_execution`.

### Proof of Concept
No exploit is required beyond code inspection: `ensure_match_transaction_info`'s body [6](#0-5)  only asserts on `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`, and its own comment block confirms the state-checkpoint fields are intentionally excluded and that this is known to let `replay_on_archive` succeed despite a real state-root divergence [2](#0-1) . Both call sites (`storage/db-tool/src/replay_on_archive.rs` execute_and_verify, and `execution/executor/src/chunk_executor/mod.rs` verify_execution) use this function as their sole correctness gate, so any test that feeds an `expected_txn_info` with a tampered `state_checkpoint_hash` alongside a correct write set/events will pass verification unmodified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
