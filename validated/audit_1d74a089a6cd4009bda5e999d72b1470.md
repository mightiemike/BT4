## #VulnerabilityFound

### Title
Mempool TTL eviction (`remove_txs_older_than`) evicts unexpired transactions while never removing truly expired ones - ([File: crates/apollo_mempool/src/transaction_pool.rs])

### Summary
`TimedTransactionMap::remove_txs_older_than` is the exact analog of the reported `split_off_older_than` bug: it uses `BTreeMap::split_off` on a cutoff key but keeps the wrong half as the "removed" set, instead of reassigning the split-off tail back into `self` (as the codebase does correctly in sibling functions such as `prune_fee_proposals_window` and `clear_old_tx_from_consumed_queue`).

### Finding Description
`remove_txs_older_than` computes a cutoff `SubmissionID` at `now - duration` and calls: [1](#0-0) 

```rust
let split_off_value = SubmissionID { submission_time: self.clock.now() - duration, ... };
let old_txs = self.txs_by_submission_time.split_off(&split_off_value);
...
for (submission_id, tx) in old_txs.into_iter() { ... removed_txs.push(tx); }
```

`BTreeMap::split_off(key)` retains in `self` everything with key `< key` and **returns** everything with key `>= key`. Since `SubmissionID` orders primarily by `submission_time`, entries with `submission_time >= now - duration` (i.e., transactions still within the TTL window, not expired) are exactly the ones returned into `old_txs` and then removed from the pool. Conversely, entries with `submission_time < now - duration` (the genuinely expired, "older than TTL" transactions) are the ones that remain in `self.txs_by_submission_time` — never removed.

This is precisely the same class of bug as the report's `split_off_older_than`/`Vec::split_off` mix-up: the developer used the split half that logically should stay, as the half to discard, leaving the truly stale data behind and discarding fresh data instead.

Contrast with the two other, correctly implemented, split_off-based prune helpers in the same codebase, which explicitly swap the retained/returned halves back: [2](#0-1) [3](#0-2) 

`remove_txs_older_than` is reachable from any account submitting a transaction, since it is invoked on every `add_tx` and `get_txs` call: [4](#0-3) [5](#0-4) 

The wrapper in `TransactionPool` calls straight through without correcting the inversion: [6](#0-5) 

### Impact Explanation
Because the wrong half of the split is treated as "the transactions to remove":
1. **Legitimate, still-valid transactions get incorrectly evicted from the mempool** on virtually every `add_tx`/`get_txs` call (any transaction with `submission_time >= now - TTL`, i.e., essentially every non-expired transaction not specifically protected by the `exclude_txs` staged-nonce check), causing unauthorized loss/dropping of a sender's pending transaction without it ever being included in a block.
2. **Genuinely expired transactions are never purged** — they remain permanently in `txs_by_submission_time` (and thus continue to occupy `tx_pool`/`txs_by_account`/queue state), causing unbounded mempool growth over time. Any account can submit transactions and have them linger indefinitely, degrading mempool health/memory and, over time, the node's ability to admit and order new transactions correctly.

This corrupts mempool admission/ordering guarantees reachable from a single unprivileged transaction sender, and can lead to permanent loss of submitted (but not yet included) transactions or state where the mempool never correctly drains stale entries — a functional/DoS-adjacent correctness bug in a core sequencer path (mempool admission and ordering), not requiring any malicious actor.

### Likelihood Explanation
High likelihood of being triggered under completely normal operation: the buggy path executes on every single `add_tx` call (and every `get_txs` call), for every account, with no attacker action required — it is a deterministic logic defect, not a crafted attack.

### Recommendation
Fix `remove_txs_older_than` to keep the correct partition, mirroring the pattern used in `prune_fee_proposals_window`/`clear_old_tx_from_consumed_queue`:
```rust
let split_off_value = SubmissionID { submission_time: self.clock.now() - duration, ... };
// Entries with key >= split_off_value are NOT expired and must be retained.
let still_valid = self.txs_by_submission_time.split_off(&split_off_value);
let old_txs = std::mem::replace(&mut self.txs_by_submission_time, still_valid);
```
Then process `old_txs` (the genuinely expired half) exactly as today (re-insert entries preserved via `exclude_txs`, remove the rest from `hash_to_submission_id`, return `removed_txs`).

### Proof of Concept
1. Set `transaction_ttl = 60s`.
2. At `t=0`, submit `tx1` (address A, unrelated to any staged/excluded nonce).
3. At `t=10s`, submit `tx2` (address B). This call invokes `add_tx -> remove_expired_txs -> remove_txs_older_than(60s, ...)`.
   - `cutoff = t(10) - 60 = -50`. Both `tx1` (submission_time=0) and any subsequent tx have `submission_time >= cutoff`, so `split_off` returns them into `old_txs`, and (absent an `exclude_txs` match) they get removed from the pool — i.e., `tx1`, which is not expired at all, is wrongly evicted immediately.
4. Let a transaction age past TTL (e.g., submitted at `t=0`, checked at `t=1000s`, cutoff `=940`). Its key (`submission_time=0`) is `< cutoff`, so it stays in `self.txs_by_submission_time` — i.e., it is *never* split off/removed, contradicting the intended TTL eviction and leaving it in the pool forever.

    pub fn remove_txs_older_than(
        &mut self,
        duration: Duration,
        exclude_txs: &HashMap<ContractAddress, Nonce>,
    ) -> Vec<TransactionReference> {
        let split_off_value = SubmissionID {
            submission_time: self.clock.now() - duration,
            tx_hash: Default::default(),
            batching_time: None,
        };
        let old_txs = self.txs_by_submission_time.split_off(&split_off_value);

        let mut removed_txs = Vec::new();
        for (submission_id, tx) in old_txs.into_iter() {
            if exclude_txs.get(&tx.address).is_some_and(|nonce| tx.nonce < *nonce) {
                // The transaction should be preserved. Add it back.
                self.txs_by_submission_time.insert(submission_id, tx);
            } else {
                self.hash_to_submission_id.remove(&tx.tx_hash).expect(
                    "Transaction should have a submission ID if it is in the timed transaction \
                     map.",
                );
                removed_txs.push(tx);
            }
        }

        removed_txs
    }
