### Title
Transaction ID cache poisoning via garbage-signature broadcast causes permanent DUP_TRANSACTION_ERROR denial-of-settlement for legitimate transactions - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.broadcastTransaction` inserts the transaction's `txID` into `dbManager.getTransactionIdCache()` before performing signature verification, TaPoS/expiration checks, or actually executing the transaction via `dbManager.pushTransaction`. Since `txID = hash(raw_data)` is independent of the signature, an attacker who knows a victim's not-yet-broadcast `raw_data` can pre-broadcast it with a garbage-but-length-valid signature to poison the cache, causing the victim's later legitimately-signed broadcast of the same `raw_data` to be rejected with `DUP_TRANSACTION_ERROR` before it ever reaches `Manager.pushTransaction`.

### Finding Description
In `Wallet.broadcastTransaction` [1](#0-0) , the only signature check performed before the cache write is `SignUtils.isValidLength(sig.size())`, which only validates the byte length (65 bytes) and not cryptographic correctness. Immediately after, the cache-poisoning-critical block runs: [2](#0-1) 

This unconditionally calls `dbManager.getTransactionIdCache().put(txID, true)` for any `txID` not already present, *before* `trx.checkExpiration(...)` and `dbManager.pushTransaction(trx)` are invoked (where the real signature/TaPoS validation happens). None of the subsequent `catch` blocks (`ValidateSignatureException`, `ContractValidateException`, `TaposException`, etc.) remove the poisoned `txID` from the cache [3](#0-2) . Consequently, once an attacker submits a garbage-signature transaction with the same `raw_data` as a victim's pending (unbroadcast) transaction, the cache entry persists, and the victim's subsequent valid broadcast of identical `raw_data` is short-circuited by the `getIfPresent(txID) != null` check and returns `DUP_TRANSACTION_ERROR`, without ever reaching `Manager.pushTransaction`.

This is reachable via the public, unauthenticated HTTP endpoint `POST /wallet/broadcasttransaction`, which is backed by `BroadcastServlet` calling into `Wallet.broadcastTransaction`.

### Impact Explanation
This is a griefing/denial-of-settlement vector: any attacker who can predict or observe a victim's `raw_data` (e.g., via network sniffing, mempool gossip prior to full broadcast, or a shared/predictable `ref_block` and expiration window) can render that transaction unbroadcastable until its `expiration` field lapses, since the txID cache is keyed purely on `raw_data` hash and is populated by unauthenticated, unauthorized garbage-signature submissions. This can delay or misaccount time-sensitive TRX transfers or delegation actions without requiring the attacker to know any private key.

### Likelihood Explanation
Feasibility requires the attacker to learn the exact `raw_data` (all fields including `ref_block_bytes`, `ref_block_hash`, `expiration`, `contract`) of a transaction before it is broadcast by the legitimate signer, and for the transaction to not already be present in the cache. This is a real precondition dependent on external raw_data leakage (e.g., transaction relaying, shared infra, or predictable transaction construction such as identical wallets generating deterministic ref_block/expiration in a tight window), making exploitation situational but technically straightforward once raw_data is known — the attacker only needs a 65-byte filler signature, no private key or special privilege.

### Recommendation
Move the `trxCacheEnable` duplicate-check/insert logic to occur only after signature validation and `dbManager.pushTransaction` succeeds (or catch-block cleanup should remove the `txID` from `dbManager.getTransactionIdCache()` on any validation failure path), so that only successfully validated and accepted transactions poison the dedupe cache. Alternatively, bind the cache key to a value that also incorporates the actual verified signature/sender rather than purely `raw_data` hash for the pre-validation gate.

### Proof of Concept
```java
// Pseudo-outline for a JUnit test in framework/src/test/java/org/tron/core/WalletMockTest.java style
@Test
public void testTxIdCachePoisoningByGarbageSignature() {
  TransactionCapsule trx = createSampleTransactionCapsule(); // build raw_data only
  Transaction rawDataProto = trx.getInstance();

  // Attacker crafts same raw_data with a garbage 65-byte signature
  Transaction attackerTx = rawDataProto.toBuilder()
      .clearSignature()
      .addSignature(ByteString.copyFrom(new byte[65])) // valid length, garbage bytes
      .build();

  GrpcAPI.Return attackerResult = wallet.broadcastTransaction(attackerTx);
  // Expect it to fail signature/pushTransaction validation (e.g., SIGERROR),
  // but txID cache is now poisoned:
  assertNotEquals(GrpcAPI.Return.response_code.SUCCESS, attackerResult.getCode());

  // Victim now signs the SAME raw_data legitimately
  Transaction victimTx = signWithRealKey(rawDataProto);
  GrpcAPI.Return victimResult = wallet.broadcastTransaction(victimTx);

  // BUG: victim incorrectly gets DUP_TRANSACTION_ERROR though never pushed
  assertEquals(GrpcAPI.Return.response_code.DUP_TRANSACTION_ERROR, victimResult.getCode());
}
```
Expected (buggy) result: the second call returns `DUP_TRANSACTION_ERROR` even though the transaction was never executed via `Manager.pushTransaction`, confirming the cache poisoning at [2](#0-1) .
