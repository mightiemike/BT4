### Title
Unchecked return value of `reduceAssetAmountV2` in `ExchangeCreateActuator` and `ExchangeInjectActuator` can silently corrupt exchange/asset accounting - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`AccountCapsule.reduceAssetAmountV2` returns a `boolean` indicating whether the asset deduction actually succeeded, exactly like the `gwt.burn()`/`gwt.mint()` return values in the referenced report. Several actuators (`TransferAssetActuator`, `ParticipateAssetIssueActuator`, `Commons.adjustAssetBalanceV2`) correctly check this return value and abort with `ContractExeException`/`BalanceInsufficientException` on failure. `ExchangeCreateActuator.execute()` and `ExchangeInjectActuator.execute()` call `reduceAssetAmountV2` but discard the boolean result, then unconditionally proceed to credit the exchange pool (`ExchangeCapsule.setBalance(...)`) and mark the transaction as `SUCESS`.

### Finding Description
In `ExchangeCreateActuator.execute()`, the owner's asset balance is supposed to be deducted before the exchange pool is created: [1](#0-0) 
The return value of `reduceAssetAmountV2` is ignored, and the code unconditionally proceeds to persist the `ExchangeCapsule` with the requested `firstTokenBalance`/`secondTokenBalance`: [2](#0-1) 

The identical pattern exists in `ExchangeInjectActuator.execute()`: [3](#0-2) 

Both actuators rely entirely on their `validate()` step (`assetBalanceEnoughV2`) to guarantee `reduceAssetAmountV2` will succeed at execution time, and never re-check the result at the point of mutation: [4](#0-3) [5](#0-4) 

By contrast, the correct pattern used elsewhere in the codebase explicitly checks the return value and throws on failure: [6](#0-5) [7](#0-6) 

`reduceAssetAmountV2` itself can return `false` silently (without any exception) whenever `currentAmount` is `null` or insufficient for the requested `amount`: [8](#0-7) 

Because `ExchangeCreateActuator`/`ExchangeInjectActuator` don't re-validate this outcome, any code path where the validate-time state and execute-time state of an account's asset map diverge (e.g. via future refactors, additional contracts touching the same account within block/tx processing, or bugs in `assetBalanceEnoughV2` vs. `reduceAssetAmountV2` key-normalization logic for `AllowSameTokenName`) results in the exchange pool being credited with asset value that was never actually deducted from the owner's account — while the transaction result is still marked `SUCESS`.

### Impact Explanation
If the deduction silently fails while the exchange pool bookkeeping still records the deposited amount, the chain state becomes internally inconsistent: TRX/asset units appear to exist in the `ExchangeCapsule` balances without a corresponding decrease in any account's holdings, effectively fabricating value in the exchange market and corrupting resource/asset accounting — one of the explicitly in-scope impact categories (asset or accounting corruption via broadcast transactions).

### Likelihood Explanation
Exploitability at present is limited because `validate()` performs `assetBalanceEnoughV2` immediately before `execute()` runs within the same transaction processing step, so under the current code the check and the mutation should normally agree. The likelihood is therefore moderate/low today, but the missing defensive check removes the safety net that exists everywhere else in the actuator codebase, and it is a genuine bug-class match to the audited `dpnm_sc.sol` issue (unchecked return of a value-mutating call). Any divergence between the two states — introduced by future changes, a different key-normalization behavior between `assetBalanceEnoughV2`/`reduceAssetAmountV2`, or reentrant-like sequencing — would be silently exploitable by any account holder issuing `ExchangeCreateContract`/`ExchangeInjectContract` transactions.

### Recommendation
Check the boolean return value of `reduceAssetAmountV2` (and `addAssetAmountV2` where relevant) in `ExchangeCreateActuator.execute()` and `ExchangeInjectActuator.execute()`, and throw `ContractExeException`/`BalanceInsufficientException` on failure, mirroring the pattern already used in `TransferAssetActuator` and `Commons.adjustAssetBalanceV2`, e.g.:
```java
if (!accountCapsule.reduceAssetAmountV2(firstTokenID, firstTokenBalance, dynamicStore, assetIssueStore)) {
  throw new ContractExeException("reduceAssetAmount failed !");
}
```

### Proof of Concept
Not directly reproducible with the current code (the `validate()` pre-check normally prevents the failure path from being reached), so no concrete exploit transaction can be demonstrated purely from static analysis. The finding is based on the unchecked return value at [1](#0-0)  and [9](#0-8) , which is a defense-in-depth gap identical in class to the reported `gwt.burn`/`gwt.mint` issue rather than a currently demonstrated end-to-end exploit.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
