The default value of `apiNonBlocking` is `false` [1](#0-0) , meaning blocking `acquire()` semantics are the default node behavior rather than requiring non-default configuration.

### Title
DoS via blocking RateLimiter.acquire() on gRPC worker threads exhausts fixed thread pool - (framework/src/main/java/org/tron/core/services/ratelimiter/adapter/QpsRateLimiterAdapter.java)

### Summary
`QpsRateLimiterAdapter.acquire()` delegates to `QpsStrategy.acquire()`, which calls Guava's `RateLimiter.acquire()` and blocks the calling thread until a permit is available [2](#0-1) [3](#0-2) . Because `RateLimiterInterceptor.interceptCall` invokes `rateLimiter.acquirePermit(runtimeData)` synchronously on the gRPC call thread before `next.startCall()` is invoked, this blocking occurs on threads drawn from the gRPC server's fixed executor pool, and since `apiNonBlocking` defaults to `false`, this is the default blocking path.

### Finding Description
`RpcService.initServerBuilder()` configures the gRPC server with a bounded fixed thread pool sized by `rpcThreadNum` [4](#0-3) , and `RateLimiterInterceptor` is registered as a server interceptor [5](#0-4) . In `interceptCall`, the code calls `rateLimiter.acquirePermit(runtimeData)` directly on the calling thread before the actual RPC handler runs [6](#0-5) . `acquirePermit` dispatches to `acquire()` (blocking) when `apiNonBlocking=false`, which is the default value in `RateLimiterConfig` [1](#0-0) . `QpsStrategy.acquire()` blocks on Guava's `RateLimiter.acquire()`, sleeping the thread for however long is needed to obtain a token at the configured qps [3](#0-2) . Since the gRPC executor pool is fixed-size, an attacker who fires more concurrent requests than the qps allows and more concurrent connections than the thread pool size can occupy every worker thread in blocked `acquire()` calls, starving subsequent legitimate calls (including time-sensitive multisig/freeze-unfreeze broadcast calls routed through the same gRPC service) of any available worker thread.

None of the existing checks (`TransactionCapsule.validateSignature`, actuator `validate()`, `ForkController` gates, energy/bandwidth accounting) intervene here because the blocking occurs in the interceptor layer before the request even reaches transaction validation or the actuator — it is purely a transport/rate-limiter-layer resource exhaustion, independent of transaction content or fees.

### Impact Explanation
This is a DoS via RPC-API: an unprivileged, anonymous client with no special access can exhaust the fixed gRPC worker thread pool by issuing more concurrent calls to a rate-limited endpoint than the pool size, causing legitimate concurrent calls (including time-sensitive account operations broadcast through the same gRPC service) to be blocked/delayed. This matches TRON's "DoS via RPC-API" bounty impact class.

### Likelihood Explanation
Preconditions are default (`apiNonBlocking=false` by default) plus any endpoint configured with a `QpsRateLimiterAdapter` and a qps low relative to attacker throughput. Cost to the attacker is minimal — merely opening N concurrent gRPC connections/streams to a rate-limited endpoint (no fees, no signed transactions required if hitting a query endpoint), which is trivial and repeatable. The severity depends on `rpcThreadNum` (pool size) relative to attacker's concurrent connections and `maxConcurrentCallsPerConnection`; a sufficiently determined attacker opening many connections can occupy the whole pool.

### Recommendation
Avoid performing blocking `RateLimiter.acquire()` calls directly on gRPC worker/executor threads. Either always use non-blocking `tryAcquire()` semantics in the gRPC interceptor path (reject over-limit requests immediately with `RESOURCE_EXHAUSTED`) or move blocking waits off the request-handling thread pool (e.g., schedule the delayed continuation via a separate scheduled executor / `ScheduledExecutorService` rather than blocking the pool thread), and cap the maximum blocking wait to bound worst-case thread occupancy.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/services/ratelimiter/adaptor/QpsAdapterDoSTest.java
@Test
public void testAcquireBlocksWorkerThreadUnderLowQps() throws Exception {
  Args.getInstance().setRateLimiterApiNonBlocking(false); // default
  QpsRateLimiterAdapter adapter = new QpsRateLimiterAdapter("qps=1"); // low qps endpoint

  int threadPoolSize = 4; // simulate small rpcThreadNum
  ExecutorService pool = Executors.newFixedThreadPool(threadPoolSize);

  // Attacker floods more concurrent requests than qps and pool size.
  for (int i = 0; i < threadPoolSize; i++) {
    pool.submit(() -> adapter.acquire(null)); // blocks on rateLimiter.acquire()
  }

  long start = System.currentTimeMillis();
  Future<Boolean> legitimateCall = pool.submit(() -> adapter.acquire(null));
  // pool is fully occupied by attacker calls waiting on the limiter;
  // legitimate call cannot even be scheduled until a worker frees up.
  legitimateCall.get(10, TimeUnit.SECONDS);
  long elapsed = System.currentTimeMillis() - start;

  Assert.assertTrue("legitimate call blocked too long due to worker starvation",
      elapsed > 1000); // exceeds acceptable bound for a "legitimate" late call
}
```
Expected: the legitimate call's queued task cannot even start executing until an attacker-occupied thread completes its blocking `acquire()`, demonstrating unbounded/serialized blocking of worker threads from a fixed qps configuration, consistent with the described DoS path through `RateLimiterInterceptor.interceptCall` → `QpsRateLimiterAdapter.acquire` → `QpsStrategy.acquire`.
