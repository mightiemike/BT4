### Title
Uncaught exception in `sanitizeHost` via malformed base64 `host` causes unhandled crash instead of `InvalidHostError` - (`packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
`sanitizeHost` validates the `host` value only with a loose base64-alphabet regex before calling `decodeHost`/`new URL()`, without a `try/catch`. A minimal base64-alphabet string like `"a"` (length 1, mod 4 == 1) passes the regex but is invalid base64 per the WHATWG forgiving-base64 algorithm implemented by Node's global `atob`, so `atob("a")` throws an uncaught `DOMException`. This exception propagates out of `sanitizeHost` instead of being converted to `InvalidHostError`, hitting every caller (`getEmbeddedAppUrl`/`buildEmbeddedAppUrl`, the Remix/React Router `validateShopAndHostParams`, Express `redirect-to-auth`/`redirect-to-shopify-or-app-root`) that does not itself wrap the call in a `try/catch`.

### Finding Description
In `packages/apps/shopify-api/lib/utils/shop-validator.ts`:

```ts
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
  ...
``` [1](#0-0) 

`decodeHost` is a thin wrapper around `atob`: [2](#0-1) 

The pre-filter regex `^[0-9a-zA-Z+/]+={0,2}$` only checks the character alphabet, not that the string length is a valid base64 length. A one-character string such as `"a"` satisfies the regex (one-or-more alnum chars, zero padding) but is not decodable per the WHATWG "forgiving-base64" algorithm Node's `atob` implements (remaining length mod 4 == 1 is always a decode failure), so `atob("a")` throws instead of returning a value. Neither `decodeHost` nor `sanitizeHost` catches this, so the exception is thrown out of `sanitizeHost` itself — before the function ever gets to the `throwOnInvalid`/`InvalidHostError` logic at the bottom of the function.

Every caller passes attacker-controlled query-string `host` values directly into `sanitizeHost`/`buildEmbeddedAppUrl` without a surrounding `try/catch`:
- `buildEmbeddedAppUrl` calls `sanitizeHost(config)(host, true)` directly: [3](#0-2) 
- `validateShopAndHostParams` (Remix) calls `api.utils.sanitizeHost(...)` with no try/catch around it, expecting only a `null`/falsy return: [4](#0-3) 

This breaks the fail-closed design intent (return `null`/throw `InvalidHostError` for bad input) — instead it throws an unrelated, uncaught `DOMException`, which in Express/Remix/React-Router handlers not equipped for it can produce an unhandled promise rejection or 500 crash path in the authentication handler chain.

### Impact Explanation
This is a low-privilege, unauthenticated availability issue in the authentication handler chain: an attacker can trigger an uncaught exception (instead of a controlled `InvalidHostError`) simply by supplying `?host=a` (or any other base64-alphabet string whose length mod 4 == 1) to any admin/auth route that resolves `host` through `sanitizeHost`/`buildEmbeddedAppUrl`. This matches Shopify's "DoS in an authentication handler" impact class — it does not lead to session/token compromise, but it undermines the fail-closed invariant since malformed input escapes as an unhandled runtime error rather than the expected graceful validation error.

### Likelihood Explanation
Trivial to trigger: no authentication, no secrets, and no non-default configuration are required — just an HTTP GET to any embedded-app admin/auth entry point with a crafted `host` query parameter (e.g., `host=a`). It is fully repeatable and requires only knowledge of the base64-alphabet pre-check's weakness.

### Recommendation
Wrap the `decodeHost`/`new URL()` call in `sanitizeHost` in a `try/catch`, treating any decode/parse failure the same as an invalid host (`sanitizedHost = null`, then respect `throwOnInvalid` to raise `InvalidHostError`), e.g.:
```ts
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  try {
    const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
    ...
  } catch {
    sanitizedHost = null;
  }
}
```

### Proof of Concept
```ts
import {sanitizeHost} from '../../lib/utils/shop-validator';
import {testConfig} from '../../lib/__tests__/test-config';

test('sanitizeHost throws uncaught error for malformed base64 host instead of returning null / InvalidHostError', () => {
  const config = testConfig();

  // "a" passes /^[0-9a-zA-Z+/]+={0,2}$/ but is invalid base64 (length % 4 === 1),
  // so atob("a") throws instead of sanitizeHost returning null / InvalidHostError.
  expect(() => sanitizeHost(config)('a')).toThrow(); // throws DOMException, NOT InvalidHostError
  expect(() => sanitizeHost(config)('a', true)).toThrow(); // still not InvalidHostError
});
```
Expected (buggy) behavior: both calls throw a `DOMException`/`TypeError` from `atob`/`new URL`, not `InvalidHostError`, and the first call throws even with `throwOnInvalid = false`, contradicting the function's documented "return null" contract for invalid input.
