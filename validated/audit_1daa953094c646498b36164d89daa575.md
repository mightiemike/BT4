After thorough analysis of the nearcore codebase, I have found a valid analog.### Title
DelegateAction (Meta-Transaction) Signature Missing Chain-ID Binding Enables Cross-Chain Replay — (`core/primitives/src/signable_message.rs`)

---

### Summary

The `SignableMessage` scheme used to sign `DelegateAction` (NEP-366 meta-transactions) and `DelegateActionV2` (NEP-611) does not bind the signature to any chain-specific identifier. Neither the `MessageDiscriminant` nor the `DelegateAction` payload includes a `chain_id` or genesis hash. A signed `DelegateAction` produced for NEAR mainnet is cryptographically valid on NEAR testnet (and any other NEAR-protocol network) whenever the same account and key exist on both chains with a compatible nonce and unexpired `max_block_height`. An unprivileged attacker who observes a relayed meta-transaction on one network can replay it on another, causing unauthorized execution of the inner actions — including token transfers, key management, and contract calls — against the victim's account on the target chain.

---

### Finding Description

**Root cause — `SignableMessage` carries no chain domain**

`DelegateAction::get_nep461_hash()` constructs the signed digest as:

```
SHA-256( Borsh( MessageDiscriminant(NEP_366) || DelegateAction ) )
``` [1](#0-0) 

`MessageDiscriminant` is a single `u32` derived from the NEP number:

```
discriminant = MIN_ON_CHAIN_DISCRIMINANT + 366   // = (1<<30) + 366
``` [2](#0-1) [3](#0-2) 

This discriminant is **identical on every NEAR network** (mainnet, testnet, betanet, any private fork). The `DelegateAction` payload itself contains only:

| Field | Chain-specific? |
|---|---|
| `sender_id` | No — account names are identical across chains |
| `receiver_id` | No |
| `actions` | No |
| `nonce` | No — per-key counter, independent per chain |
| `max_block_height` | No — block heights are not chain-specific |
| `public_key` | No | [4](#0-3) 

**Contrast with regular `SignedTransaction`**

A regular `SignedTransaction` includes a `block_hash` field — a hash of a specific block on the originating chain. The runtime enforces `transaction_validity_period` against that hash, so a mainnet transaction cannot pass the freshness check on testnet (the block hash does not exist there). [5](#0-4) 

`DelegateAction` has no equivalent chain anchor. `max_block_height` is a raw integer height, not a block hash, and block heights are numerically comparable across all NEAR networks.

**Execution path — no chain check in `apply_delegate_action`**

`apply_delegate_action` performs exactly four checks before executing the inner actions:

1. Signature validity (`signed_delegate_action.verify()`) — passes on any chain where the key is registered.
2. `block_height > max_block_height` — passes if the target chain's height is below the ceiling.
3. `sender_id` matches the receipt's `account_id` — passes if the account exists on the target chain.
4. Nonce validity via `validate_delegate_action_key` — passes if the target chain's access-key nonce is lower than the delegate nonce. [6](#0-5) 

None of these checks are chain-specific. There is no `chain_id` or genesis-hash comparison anywhere in the delegate-action execution path.

---

### Impact Explanation

An attacker who observes a valid `SignedDelegateAction` broadcast on mainnet (e.g., via the RPC or a public relayer) can submit the identical bytes to testnet (or any other NEAR network). If the preconditions hold, the runtime on the target chain will:

- Accept the signature as valid (same key, same payload hash).
- Accept the nonce (target chain's access-key nonce is lower).
- Accept `max_block_height` (target chain's height is below the ceiling).
- Execute the inner actions with `predecessor_id = sender_id` (the victim's account).

Inner actions that cause material harm:
- `Transfer` — drains NEAR tokens from the victim's account on the target chain.
- `AddKey` / `DeleteKey` — compromises account access on the target chain.
- `FunctionCall` — executes arbitrary contract logic (e.g., DeFi withdrawals, NFT transfers) on behalf of the victim.

This maps directly to **unauthorized transaction**, **stealing or loss of funds**, and **contract execution flow breakage** in the HackenProof scope.

---

### Likelihood Explanation

The preconditions are routinely satisfied in practice:

1. **Same account on both chains**: NEAR account names are human-readable strings. Users and projects routinely register the same name on mainnet and testnet. Implicit accounts (ETH-style hex addresses) are deterministic and identical across chains.
2. **Same key**: Developers and wallets commonly reuse the same key pair on testnet and mainnet.
3. **Lower nonce on testnet**: Testnet accounts are typically less active; their access-key nonces are lower than mainnet counterparts, making a mainnet-signed nonce valid on testnet.
4. **`max_block_height` not expired**: Relayers typically set `max_block_height = current_height + 100` or more. Both mainnet and testnet have been running for years and have comparable block heights (both in the tens of millions), so a mainnet ceiling is numerically valid on testnet within the same window.
5. **Observability**: `SignedDelegateAction` payloads are visible in transaction receipts via the public JSON-RPC (`EXPERIMENTAL_tx_status`, `chunk`). Any observer can extract and re-submit them.

---

### Recommendation

Bind the `DelegateAction` signature to the chain by including the `chain_id` (from `GenesisConfig`) or the full `GenesisId` (chain_id + genesis hash) in the signed payload. The cleanest approach is to add `chain_id: String` to `DelegateAction` and `DelegateActionV2`, or to include it in `SignableMessage` as a domain-separation field alongside the discriminant:

```rust
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub chain_id: String,   // e.g. "mainnet", "testnet"
    pub msg: &'a T,
}
```

Alternatively, replace `max_block_height` with a `block_hash` (as regular transactions use), which is inherently chain-specific and simultaneously provides freshness and chain binding. Either change requires a protocol version bump and a new `DelegateAction` version.

### Proof of Concept

**Setup:**
- `alice.near` exists on both mainnet and testnet with the same Ed25519 key pair.
- Mainnet access-key nonce for that key: `5_000_000`.
- Testnet access-key nonce for the same key: `100` (less active account).
- Current mainnet block height: `120_000_000`. Current testnet block height: `118_000_000`.

**Step 1 — Alice signs a DelegateAction on mainnet:**
```
DelegateAction {
    sender_id:       "alice.near",
    receiver_id:     "token.near",
    actions:         [FunctionCall { method: "ft_transfer", args: {to:"attacker.near", amount:"1000"}, deposit: 1 }],
    nonce:           5_000_001,
    max_block_height: 120_000_200,
    public_key:      ed25519:AliceKey,
}
```
Alice's relayer submits this to mainnet. The `ft_transfer` executes on mainnet.

**Step 2 — Attacker extracts the `SignedDelegateAction`:**
The attacker queries `EXPERIMENTAL_tx_status` on any mainnet RPC node and extracts the raw `SignedDelegateAction` bytes (signature + payload).

**Step 3 — Attacker submits to testnet:**
The attacker wraps the identical `SignedDelegateAction` in a new outer transaction (signed by the attacker's own testnet key, addressed to `alice.near` on testnet) and submits it to a testnet RPC node.

**Step 4 — Testnet runtime validation:**
- `signed_delegate_action.verify()` → **passes** (same key, same payload, same discriminant `(1<<30)+366`).
- `block_height (118_000_000) > max_block_height (120_000_200)` → **false**, not expired.
- `sender_id ("alice.near") == receipt account_id` → **passes**.
- `nonce (5_000_001) > ak_nonce (100)` → **passes**.

**Result:** `ft_transfer` executes on testnet's `token.near` contract with `predecessor_id = "alice.near"`, transferring 1000 tokens from Alice's testnet balance to the attacker — without Alice's consent or knowledge.

The broken invariant: `apply_delegate_action` at [7](#0-6) 
accepts a signature whose hash [8](#0-7) 
contains no chain identifier, so the same bytes satisfy the verification predicate on every NEAR network simultaneously.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
