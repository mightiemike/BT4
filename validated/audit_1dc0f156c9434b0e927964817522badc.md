### Title
`resolve-callcode`'s ztoken price resolution reads `get-cached-indexes` without guaranteeing the cache was populated for the current block, producing a stale/absent index at the value read - (mainnet/contracts/market/v0-4-market.clar)

### Summary
`v0-4-market.clar`'s `resolve-ztoken` reads the ztoken liquidity index from `get-cached-indexes`, a per-timestamp cache populated only by `accrue-and-cache`/`vault-accrue`. Several public entry points explicitly document the requirement to call `accrue-user-debts`/`accrue-user-collateral` "FIRST" so the cache is "populated" before price resolution runs, implying that if this ordering is not followed (or the cache entry from a different/earlier code path is stale relative to the vault's true state), the value used to price a ztoken collateral/debt asset diverges from the value the vault itself would compute after accrual, mirroring the Notional M-11 pattern of a stateful "before" quantity vs. a state-changing "after" quantity being computed from two different sources of the same underlying interest data.

### Finding Description
`resolve-ztoken` computes a ztoken's USD value using a cached index rather than the vault's live, freshly-accrued index: [1](#0-0) 

That cache is populated by `accrue-and-cache`, which is timestamp-keyed and either returns a cache hit or calls `vault-accrue` fresh: [2](#0-1) 

The `liquidate` entry point contains an explicit code comment acknowledging this ordering dependency — accrual must run before price resolution can safely use the cache: [3](#0-2) 

Meanwhile, the underlying vault's own `accrue` function computes the "true" index (`next-index`), and when the vault is in `pause-states.accrue`, it explicitly passes through the *old*, un-accrued index without reverting and without updating the cache-relevant `last-update` timer: [4](#0-3) 

This reproduces the Notional bug class precisely: the value used to compute a "before" state (cached index at the time `accrue-and-cache` last ran, or the pass-through non-accrued index while `accrue` is paused) can diverge from the value that the vault would produce if accrual is later triggered normally (e.g., once unpausing sets `last-update` to `stacks-block-time`, jumping over the entire paused period, as seen in `set-pause-states`): [5](#0-4) 

Because `resolve-ztoken`'s price is consumed directly in collateral/debt USD valuation (`get-notional-evaluation`, `is-healthy`, liquidation LTV math), any place where the cached index used for pricing does not match the vault's actual, freshly-accrued index produces an inconsistent valuation within the same transaction — the same "before vs after" interest-accrual mismatch that caused Notional's rebalance revert, except here it manifests as mispriced collateral/debt rather than a revert.

### Impact Explanation
A mismatch between the cached ztoken index used for pricing and the vault's true accrued index causes collateral/debt to be valued using a stale (either too low or too high) exchange rate at the moment of a health check, borrow, or liquidation. Depending on the direction of the drift (paused accrual keeps the index artificially low, so ztoken collateral is undervalued and ztoken debt is undervalued too), positions can be assessed as healthier or less healthy than they truly are, or a legitimate liquidation can be blocked/mis-sized because `total-collateral-usd`/`total-debt-usd` do not reflect the interest that would apply if accrual actually ran. This falls under temporary freezing of funds / value (liquidations blocked or health checks passing/failing incorrectly) as opposed to a permanent theft, matching the "temporary freezing of funds" impact class.

### Likelihood Explanation
This requires the `accrue` pause state to be toggled on a vault (a DAO-controlled admin action per `set-pause-states`), or a call path where `accrue-and-cache` is invoked with a stale cache entry relative to the vault's real accrual state within the same block. It is a viable, though not everyday, scenario — analogous to Notional's "interest rate model changed" edge case being unlikely but reachable — and is triggered by ordinary operational pausing rather than adversarial input, so its likelihood is comparable to the original Medium-severity Notional finding.

### Recommendation
Ensure `resolve-ztoken`/`accrue-and-cache` always reflects the vault's actual current accrual state rather than a value that can lag behind due to pausing or caching order dependencies. Either invalidate/refresh the index cache whenever a vault's pause state changes (mirroring the `last-update` jump already done in `set-pause-states`), or have `resolve-ztoken` call the vault's live accrual path directly rather than relying on a separately-populated cache, and add an explicit invariant/assertion that accrual has been performed for the current block before any ztoken price resolution executes.

### Proof of Concept
1. DAO pauses accrual on `v0-vault-usdc` via `set-pause-states` (accrue: true), which internally calls `accrue()` once to capture pending interest, then leaves `index`/`lindex` frozen — this is a legitimate part of the code paths. [6](#0-5) 
2. Time passes while `accrue` remains paused; the vault's `next-index`/`next-liquidity-index` computations correctly report `idx`/`lidx` unchanged (per `get accrue states`), so debt/interest that would have accrued is suppressed. [4](#0-3) 
3. Meanwhile, in `market.clar`, any call that resolves zUSDC-collateral pricing via `resolve-ztoken`/`get-cached-indexes` returns the pre-pause cached `lindex`, which happens to coincide with the frozen vault index — but a comparable call path expecting to compare a "before" snapshot (captured earlier in the same block, e.g., a cached entry from `accrue-and-cache` at a different timestamp within the paused window) against a "post-unpause" recomputation (after DAO flips accrual back on, jumping `last-update` to `stacks-block-time` and thereby skipping accrued interest for the whole paused interval) produces two different views of the same asset's value depending on which code path/timestamp bucket was used. [1](#0-0) 
4. A borrower/liquidator transaction straddling this state transition (unpause + immediate liquidation/borrow in the same or adjacent block) will see collateral/debt valuations computed from an index that does not reflect the interest jump forced by the `last-update` skip, producing an LTV/health assessment inconsistent with the vault's true state — mirroring Notional's `totalUnderlyingValueBefore`/`After` mismatch that caused the rebalance assertion to fail; here it instead causes a liquidation/health-check to pass or fail incorrectly, temporarily freezing legitimate liquidations or distorting borrow capacity.
