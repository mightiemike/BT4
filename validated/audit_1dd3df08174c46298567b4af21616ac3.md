### Title
Panic (index-out-of-bounds) on deserialization of fixed-size hash/address fields when using non-human-readable serde format - (File: crates/starknet_api/src/serde_utils.rs)

### Summary
`BytesAsHex<N, PREFIXED>` (used as the backing representation for `ClassHash`, `ContractAddress`, `StorageKey`, `TransactionHash`-adjacent felt-like fixed-size fields, etc.) implements a custom `Deserialize` that, for non-human-readable formats, uses a `Visitor::visit_seq` implementation which writes into a fixed-size array `res: [u8; N]` using an unchecked, unbounded index counter.

### Finding Description
In `crates/starknet_api/src/serde_utils.rs`: [1](#0-0) 
the `visit_seq` implementation loops `while let Some(value) = seq.next_element()?` and does `res[i] = value; i += 1;` with no check that `i < N`. If a non-human-readable deserializer feeds a sequence with more than `N` elements (e.g., a maliciously crafted binary-encoded payload for a `PrefixedBytesAsHex<N, true>`/`BytesAsHex<N, false>`-backed type such as `ClassHash`, `ContractAddress`, `StorageKey`, or hash fields in `core.rs`/`block.rs`/`transaction/fields.rs`), the array write `res[i] = value` will panic with an "index out of bounds" once `i >= N`, rather than being rejected gracefully via a deserialization error.

This mirrors the CVE-2017-11608 bug class: a crafted/malformed input causes an out-of-bounds memory access due to unchecked length handling during low-level decoding, leading to abnormal process termination (denial of service) rather than clean error handling.

The relevant types (`BytesAsHex`/`PrefixedBytesAsHex`) back core Starknet identifiers used throughout transaction, class, and contract-address handling: [2](#0-1) 

### Impact Explanation
Reachability of this bug depends on whether an attacker-controlled binary/non-human-readable payload feeding a `BytesAsHex`/`PrefixedBytesAsHex`-typed field is deserialized on the sequencer's hot path (e.g., mempool p2p propagation, RPC-transaction binary conversion, or internal component communication) without a prior explicit length check. If reachable from an untrusted transaction, contract deployer, or L1 message payload, a crafted sequence with `len > N` would panic the deserializing task/thread, causing denial of service — potentially disrupting mempool admission, gateway validation, or gossip propagation and thereby the network's ability to confirm new transactions.

However, I could not fully confirm within the available search results that any of the network-facing binary deserialization paths (`apollo_protobuf` conversions, mempool p2p `RpcTransactionBatch`, gateway ingestion) actually route length-unchecked external byte counts into this exact `visit_seq` code path versus using serde's tuple/array deserialization with format-enforced fixed lengths (e.g., protobuf, bincode fixed-size arrays typically encode/decode exactly `N` elements and wouldn't allow `>N` elements to be sent in the first place for a fixed-size tuple). Serde's `deserialize_tuple(N, ...)` call in this code, per serde semantics, generally guarantees the visitor sees at most `N` elements for well-behaved format implementations (many binary formats enforce this by construction), which would make this over-read effectively unreachable in practice for compliant deserializers. I was not able to verify with certainty (within available tool budget) whether every non-human-readable deserializer used on the transaction-ingestion path enforces this invariant, or whether a hostile/malformed byte stream (not honoring the tuple length contract) could still reach `visit_seq` with excess elements.

### Likelihood Explanation
Low-to-uncertain. This requires a non-human-readable deserializer implementation that does not respect the `deserialize_tuple(N, ...)` element-count contract, or a call site that manually constructs a `SeqAccess` with more than `N` elements. I could not confirm such a call site from the code explored.

### Recommendation
Regardless of current reachability, harden `visit_seq` in `crates/starknet_api/src/serde_utils.rs` to defensively bound-check `i < N` before writing into `res[i]`, returning a `serde::de::Error::invalid_length` (or similar) instead of allowing an out-of-bounds panic if a malformed/adversarial deserializer implementation ever supplies more than `N` elements.
