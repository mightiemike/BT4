### Title
Loss of Funds via Unvalidated `refund_to` Redirect Causing Refund Receipts to Fail and Burn Deposits - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEAR's `promise_set_refund_to` host function lets a predecessor contract redirect the balance refund of an outgoing receipt to an arbitrary account, analogous to Arbitrum's `excessFeeRefundAddress`/`callValueRefundAddress` in `createRetryableTicket`. Just like the Arbitrum bug, the target account is never checked for existence before it is used as the refund destination. If the redirected account does not exist, the refund receipt fails and — per protocol design — the deposit is **permanently burned** instead of returned to the original depositor.

### Finding Description
A contract can call `promise_set_refund_to(promise_idx, account_id)` to set the `refund_to` field of an outgoing `ActionReceiptV2`, redirecting balance refunds away from the default receiver (the predecessor) to any syntactically valid `AccountId` [1](#0-0) . This account ID is stored verbatim in `refund_to` [2](#0-1)  and only syntactically re-validated (character/length rules), never checked for existence, per `validate_action_receipt` re-validating the `refund_to` id format [3](#0-2) .

When the receipt this refund_to applies to fails, the runtime creates a `Receipt::new_balance_refund` addressed to `receipt.balance_refund_receiver()`, which resolves to `refund_to` if set, else the predecessor [4](#0-3) , and pushes it as a new receipt [5](#0-4) .

This refund receipt is itself an `ActionReceipt` containing a single `Transfer` action with `predecessor_id == "system"` [6](#0-5) . Critically, `check_account_existence` for a `Transfer` action requires `implicit_creation_allowed`, and that function explicitly forbids account creation when the receipt is a refund: `is_refund => return false // Refund can never create an account` [7](#0-6) . So if the `refund_to` account does not already exist on-chain, the refund `Transfer` fails with `ActionErrorKind::AccountDoesNotExist` [8](#0-7) .

Per the protocol's documented refund semantics: "If the execution of a refund fails, the refund amount is burnt" [9](#0-8) . This is implemented directly in `apply_action_receipt`: for a system-predecessor (refund) receipt whose execution result is an error, the deposit is added to `stats.balance.other_burnt_amount` rather than refunded anywhere [10](#0-9) .

### Impact Explanation
Any contract using `promise_set_refund_to` (or forwarding a user-supplied account as the refund target, e.g. cross-shard bridge/proxy contracts) can cause deposit refunds to be permanently burned rather than returned, if the specified `refund_to` account does not exist. This is a direct structural analog of the reported Arbitrum issue: an unvalidated, attacker/caller-controlled refund address whose non-existence on the destination execution context causes irrecoverable loss of the refunded value. The existing test suite even demonstrates the happy path where `refund_to` targets an *existing* account (`near_3`) [11](#0-10) , but there is no protocol-level guard preventing `refund_to` from pointing at a nonexistent account, and the refund-failure-burns-funds behavior is unconditional.

### Likelihood Explanation
Reachable by any regular transaction/contract call: an attacker-controlled or buggy contract that calls `promise_batch_create` + `promise_set_refund_to` with a target it does not control the existence of (e.g., a not-yet-deployed sub-account, a mistyped account, or a 3rd-party account that may or may not exist) and then triggers a failing downstream receipt (e.g., calling a nonexistent method, as shown in the test) will have its deposit burned. No validator/operator/leaked-key/network-layer conditions are required — a single signed transaction from an ordinary account is sufficient to trigger the loss.

### Recommendation
Before accepting `refund_to` for an outgoing receipt (or before generating the deposit-refund receipt), verify the target account exists in state, or alternatively allow refund receipts to fall back to implicit-account creation semantics for `refund_to` targets the same way ordinary transfers do, rather than unconditionally disallowing account creation for all refund receipts. At minimum, surface/document this footgun clearly to contract developers using `promise_set_refund_to`, since currently a mistaken or malicious `refund_to` silently and irreversibly burns user deposits.

### Proof of Concept
1. Deploy Contract A. Contract A receives a deposit-carrying function call.
2. Contract A creates an outgoing promise to Contract B calling a method that will fail (e.g., a nonexistent method, deposit attached).
3. Contract A calls `promise_set_refund_to(promise_idx, "not-yet-created.contract-a.near")` — an account that does not exist.
4. The call to Contract B fails. The runtime generates `Receipt::new_balance_refund(refund_to, deposit)` targeting the nonexistent account (`core/primitives/src/receipt.rs:496`).
5. `check_account_existence` for the refund's `Transfer` action rejects it via `implicit_creation_allowed` returning `false` for `is_refund=true` (`runtime/runtime/src/actions.rs:928-933`), producing `AccountDoesNotExist`.
6. Per `apply_action_receipt`, this failed refund's deposit is added to `other_burnt_amount` (`runtime/runtime/src/lib.rs:1047-1055`) — the funds are permanently burned instead of being returned to Contract A (the original depositor).

pub fn promise_set_refund_to(
    ctx: &mut Ctx,
    memory: &mut [u8],
    promise_idx: u64,
    account_id_len: u64,
    account_id_ptr: u64,
) -> Result<()> {
    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(HostError::ProhibitedInView {
            method_name: "promise_set_refund_to".to_string(),
        }
        .into());
    }
    let refund_to = read_and_parse_account_id(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        &ctx.config,
        account_id_ptr,
        account_id_len,
    )?;
    let promise = ctx
        .promises
        .get(promise_idx as usize)
        .ok_or(HostError::InvalidPromiseIndex { promise_idx })?;

    let receipt_idx = match &promise {
        Promise::Receipt(receipt_idx) => Ok(*receipt_idx),
        Promise::NotReceipt(_) => Err(HostError::CannotSetRefundToOnJointPromise),
    }?;

    ctx.ext.set_refund_to(receipt_idx, refund_to);
    Ok(())

// redirect the balance refund using `promise_refund_to`
#[test]
fn test_refund_to() {
    let group = RuntimeGroup::new(4, 4, near_test_contracts::rs_contract());

    let signer_sender = group.signers[0].clone();
    let signer_receiver = group.signers[1].clone();
    let deposit = Balance::from_yoctonear(1000);

    let data = serde_json::json!([
        {
            "batch_create": {
                "account_id": "near_2",
            },
            "id": 0
        },
        {
            "action_function_call": {
                "promise_index": 0,
                "method_name": "non_existing_function",
                "arguments": [],
                "amount": deposit,
                "gas": GAS_2,
            },
            "id": 0
        },
        {
            "set_refund_to": {
                "promise_index": 0,
                "beneficiary_id": "near_3"
            }, "id": 0
        }
    ]);

    let signed_transaction = SignedTransaction::from_actions(
        1,
        signer_sender.get_account_id(),
        signer_receiver.get_account_id(),
        &signer_sender,
        vec![Action::FunctionCall(Box::new(FunctionCallAction {
            method_name: "call_promise".to_string(),
            args: serde_json::to_vec(&data).unwrap(),
            gas: GAS_1,
            deposit,
        }))],
        CryptoHash::default(),
    );

    let handles = RuntimeGroup::start_runtimes(group.clone(), vec![signed_transaction.clone()]);
    for h in handles {
        h.join().unwrap();
    }

    println!("{:?}", group.executed_receipts);

    use near_primitives::transaction::*;
    let [r0] = &*assert_receipts!(group, signed_transaction) else {
        panic!("Incorrect number of produced receipts")
    };

    let receipts = &*assert_receipts!(group, "near_0" => r0 @ "near_1",
        ReceiptEnum::Action(ActionReceipt{actions, ..}) | ReceiptEnum::ActionV2(ActionReceiptV2{actions, ..}),
        {},
        actions,
        a0, Action::FunctionCall(function_call_action), {
            assert_eq!(function_call_action.gas, GAS_1);
            assert_eq!(function_call_action.deposit, deposit);
            assert_eq!(function_call_action.method_name, "call_promise");
        }
    );
    let [r1, refunds @ ..] = &receipts else { panic!("Incorrect number of produced receipts") };
    group.assert_gas_refunds(&refunds[..]);

    let receipts = &*assert_receipts!(group, "near_1" => r1 @ "near_2",
        ReceiptEnum::Action(ActionReceipt{actions, ..}) | ReceiptEnum::ActionV2(ActionReceiptV2{actions, ..}),
        {},
        actions,
        a0, Action::FunctionCall(function_call_action), {
            assert_eq!(function_call_action.gas, GAS_2);
            assert_eq!(function_call_action.deposit, deposit);
            assert_eq!(function_call_action.method_name, "non_existing_function");
        }
    );
    // The redirected deposit refund (to `near_3`) is emitted first; any trailing receipt is the
    // gas refund for executing this receipt.
    let [deposit_refund, refunds @ ..] = &receipts else {
        panic!("Incorrect number of produced receipts")
    };
    group.assert_gas_refunds(&refunds[..]);

    // This is the redirected refund
    assert_refund!(group, deposit_refund @ "near_3");
}
