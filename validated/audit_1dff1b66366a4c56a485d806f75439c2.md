### Title
Zero-time value mismatch between oracle-based zToken notional valuation (liquidity index) and the vault's actual `convert-to-assets` share ratio in `collateral-remove-redeem` - (File: `local-testing/contracts/market/market.clar` / `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`collateral-remove-redeem` is a two-step entry point: it first calls `collateral-remove`, which health-checks and prices the withdrawn zToken collateral using the market's own oracle-side valuation of the zToken (`resolve-ztoken`, driven by the cached liquidity index `lindex`), and then immediately calls `vault-redeem`, which converts the exact same zToken amount to underlying using the vault's independent `convert-to-assets-preview` ratio (`total-assets-preview / total-supply-preview`). These two "balance sheet" representations of "how much underlying one zToken is worth" are computed by different formulas and are never reconciled, exactly mirroring the yAxis Vault/Controller inconsistency in the referenced report.

### Finding Description
The market's oracle callcode for zTokens computes a zToken's USD value using only the cached liquidity index: [1](#0-0) 

This `lindex`-based price is what feeds `get-notional-evaluation` / `calculate-asset-notional-value`, and is exactly what is used for the pre- and post-withdrawal health checks inside `collateral-remove`: [2](#0-1) 

`collateral-remove-redeem` chains this health-checked removal directly into a vault redemption of the same `amount`: [3](#0-2) 

However, the vault's actual conversion of zToken shares to underlying tokens is computed completely independently, via `total-assets-preview` and `total-supply-preview`: [4](#0-3) [5](#0-4) 

`total-supply-preview` additionally dilutes the share count with a "treasury LP preview" — shares that will be minted to the protocol fee reserve out of freshly-accrued interest — a factor that has no analog anywhere in the market's `lindex`-based oracle price: [6](#0-5) 

Because the market prices/health-checks the zToken purely off `lindex` while the vault's redeemable value per share is `ta/ts` (which further subtracts the treasury-lp dilution and rounds via `mul-div-down`), the two values are not guaranteed to be equal at any given block. `collateral-remove` treats the withdrawal as safe/healthy based on the `lindex` notional value, then `vault-redeem` pays out strictly less (or more) underlying based on the vault's own `ta/ts` ratio — the exact “decide what the balance sheet stands for and make it consistent” defect called out in the reference report, just replacing Vault.sol/Controller.sol with `vault-*.clar`/`market.clar`.

### Impact Explanation
Every call to `collateral-remove-redeem` prices the withdrawn zToken collateral for health-check purposes using a value that differs from the value the vault actually pays out. This causes users to either receive less underlying than their collateral was valued at (a permanent, uncompensated loss of yield/principal on withdrawal — protocol insolvency risk if the divergence is systematically unfavorable to users) or, in the reverse direction, be able to withdraw more underlying than their oracle-assessed collateral value implied (temporary/permanent freezing or under-collateralization of other users' funds, since the vault's total assets backing all other zToken holders is depleted beyond what the market's accounting assumed). This lands in the in-scope "temporary/permanent freezing of unclaimed yield or funds" impact class.

### Likelihood Explanation
This is not a chance timing race — it is a structural inconsistency that exists in every single-transaction call to `collateral-remove-redeem`, since the two valuations (`lindex`-based oracle notional vs. `ta/ts`-based vault conversion) are computed by unrelated formulas within the same block/transaction. No attacker interleaving or multi-block timing is required; the divergence is present whenever the vault's fee-reserve/treasury-lp accrual (`calc-treasury-lp-preview`) or rounding behavior causes `ta/ts` to diverge from `lindex`, which happens continuously as interest accrues and fee-reserve shares are minted.

### Recommendation
Standardize on a single source of truth for "underlying value of one zToken." Either have the market's oracle `resolve-ztoken` call the vault's own `convert-to-assets` function directly (so both the health check and the actual redemption use the identical exchange rate), or have the vault's `redeem`/`convert-to-assets-preview` use the same `lindex` used by the oracle, removing the independent `total-assets-preview`/`total-supply-preview`/treasury-lp-preview computation as a second, divergent representation of the same value.

### Proof of Concept
1. A user supplies USDC via `supply-collateral-add`, receiving zUSDC collateral, recorded via `collateral-add`.
2. Time passes; interest accrues in `vault-usdc`. The vault's `total-supply-preview` grows by `calc-treasury-lp-preview` (protocol fee-reserve shares) while `total-assets-preview` grows by accrued interest — see: [7](#0-6) 
3. Separately, the market's cached `lindex` for USDC is updated via `accrue-and-cache` and used to price zUSDC in `resolve-ztoken`: [1](#0-0) 
4. The user calls `collateral-remove-redeem`. Step 1 (`collateral-remove`) computes `collateral-value` for the withdrawn zUSDC amount using `lindex`, passes the health check based on that value: [8](#0-7) 
5. Step 2 (`vault-redeem` → vault's `redeem`) converts the same zUSDC `amount` to underlying using `convert-to-assets-preview`, i.e., `mul-div-down amount ta ts`, where `ts` includes the treasury-lp dilution not reflected in `lindex`: [4](#0-3) 
6. Because `ta/ts` ≠ the `lindex`-implied ratio, the underlying amount transferred to the user in Step 2 diverges from the USD value the health check in Step 1 assumed the collateral to represent — reproducing, contract-for-contract, the yAxis "two inconsistent balance sheets" bug from the reference report.

                       (if (is-eq ztoken-id zsBTC) sBTC
                       (if (is-eq ztoken-id zstSTX) stSTX
                       (if (is-eq ztoken-id zUSDC) USDC

    (asserts! (<= underlying-id stSTXbtc) ERR-UNKNOWN-VAULT)
