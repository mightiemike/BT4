### Title
Unbounded TRC10 asset-map iteration in `SUICIDE`/`SUICIDE2` allows underpriced, gas-unbounded DoS - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
The `AddLiquidity`/`GetAllBalances` DoS in Canto's coinswap module has a direct structural analog in java-tron's TVM `SUICIDE` opcode. When a contract self-destructs, `Program.suicide()`/`suicide2()` call `MUtil.transferAllToken`, which iterates over the *entire* TRC10 asset map of the contract account (`AccountCapsule.getAssetMapV2()`) to move every token balance to the beneficiary. An unprivileged attacker can inflate this map to an arbitrary size by sending many distinct TRC10 token types to the target contract address before triggering (or being made to trigger) `SUICIDE`, causing the operation to perform unbounded work while being charged a fixed, size-independent energy cost.

### Finding Description
`Program.suicide()` and `Program.suicide2()` invoke `MUtil.transferAllToken(getContractState(), owner, obtainer)` for every self-destruct when `VMConfig.allowTvmTransferTrc10()` is enabled. [2](#0-1) 

`MUtil.transferAllToken` fetches the *entire* asset map of the sender via `fromAccountCap.getAssetMapV2()` and iterates over every entry with `forEach`, rewriting both the source and destination account protobufs: [3](#0-2) 

`getAssetMapV2()` first calls `importAllAsset()` and returns the account's full `assetV2` map, with no size cap: [4](#0-3) 

Crucially, the energy charged for `SUICIDE`/`SUICIDE2` is a hard-coded constant, unrelated to the number of assets that will be iterated and rewritten: [1](#0-0) 

Sending a TRC10 token to any address (including a contract) is an unprivileged operation available to anyone who owns TRC10 balance (via `TransferAssetContract`/`transferToken`), and TRC10 issuance itself is available to any account meeting the fixed issuance fee, so an attacker can create/acquire many distinct token IDs cheaply and distribute them to the victim contract address. This mirrors the reported bug exactly: an attacker inflates an address's token-balance map, then a subsequent balance-iterating operation (`GetAllBalances` in Canto, `transferAllToken` in java-tron) performs work proportional to the number of distinct tokens, while gas/energy accounting does not scale with that work.

### Impact Explanation
The impact is a resource-exhaustion / underpriced-public-work condition on the TVM executor: a contract holding a very large number of distinct TRC10 balances (attacker-inflated) will, upon self-destruction, force the executing node to iterate and rebuild large protobuf maps for both the dying account and the beneficiary account while consuming only the fixed `SUICIDE`/`SUICIDE_V2` energy. This can slow down or stall transaction/block processing for the node executing/validating that transaction, and because the cost is fixed rather than proportional, the attacker pays far less than the true computational cost — a form of underpriced public work analogous to the Medium-severity Canto finding. It does not directly corrupt consensus state (both nodes execute deterministically the same iteration), but it creates an asymmetric CPU/latency cost that can be used to degrade validator or full-node performance for a low, fixed fee.

### Likelihood Explanation
Likelihood is moderate: it requires (a) TRC10 transfer to TVM enabled (`allowTvmTransferTrc10`), which is an active, long-standing mainnet feature, and (b) the attacker to issue/acquire many TRC10 token IDs and transfer them into the target contract, then trigger `SUICIDE`. TRC10 issuance has an issuance fee per token, so scaling the attack to a very large number of distinct tokens has a real but bounded cost to the attacker, comparable to how Canto's whitelist requirement reduced (but the judges still found IBC-sourced denoms could bypass) similar restrictions. The self-destructing contract must be attacker-controlled or attacker-triggerable, which is trivially satisfiable since the attacker deploys their own contract and calls `SUICIDE` themselves.

### Recommendation
- Charge `SUICIDE`/`SUICIDE2` energy proportional to the number of asset entries being iterated/transferred in `MUtil.transferAllToken`, similar to how `LOG`/`SSTORE` costs scale with data size.
- Alternatively, cap the number of distinct TRC10 assets an account/contract may hold at any time (rejecting further token transfers into an account once the cap is reached), bounding the worst-case iteration size independent of gas metering changes.
- Audit other unbounded per-asset iterations reachable via TVM/actuators (e.g., `AccountCapsule.getAssetMapV2()` consumers) for the same fixed-cost/variable-work mismatch.

### Proof of Concept
1. Attacker issues N distinct TRC10 tokens (paying the standard per-issuance fee), e.g. N = 10,000.
2. Attacker deploys a simple contract with a `SUICIDE`-triggering function (as in `framework/src/test/java/org/tron/common/runtime/vm/TransferTokenTest.java`, which already demonstrates the `suicide(address)` + TRC10 transfer flow at lines 94-165).
3. Attacker sends 1 unit of each of the N tokens to the contract address using `TransferAssetContract`/`transferToken`, inflating the contract's `assetV2` map to N entries — this uses `AccountCapsule.addAssetAmountV2` under the hood, with no upper bound on distinct token count.
4. Attacker calls the contract's `suicide(address)` function, invoking `Program.suicide()` → `MUtil.transferAllToken`, which iterates all N entries and rewrites two account protobufs, while the VM only charges the fixed `SUICIDE`/`SUICIDE_V2` energy constant defined in `EnergyCost.java` lines 57-58 and 281-299, independent of N.   public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
