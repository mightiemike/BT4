### Title
Deleting the protocol treasury account permanently halts the chain at every future epoch boundary - (File: `runtime/runtime/src/lib.rs`)

### Summary
`update_validator_accounts` unconditionally looks up the `protocol_treasury_account_id` at every epoch boundary to credit its reward share and treats a missing account as a fatal, unrecoverable `StorageInconsistentState` error. The protocol treasury account is an ordinary named account (e.g. `near` on mainnet) whose owner controls it with a normal access key, and nothing in the runtime protects it from being deleted via a standard `DeleteAccount` transaction. Once deleted, every subsequent epoch boundary deterministically triggers the fatal error path, which the chunk-application catch-all converts into a `panic!`, crashing every honest node that processes that shard and halting the chain — conceptually identical to "renouncing ownership"/removing a privileged account and bricking protocol-wide operations, except here the blast radius is the entire network rather than a single dApp.

### Finding Description
`ValidatorAccountsUpdate.protocol_treasury_account_id` is populated every epoch boundary from `genesis_config.protocol_treasury_account` in `chain/chain/src/runtime/mod.rs:264-274`, independent of whether that account still exists in state.

In `update_validator_accounts` (`runtime/runtime/src/lib.rs:1661-1687`), when the treasury account did not also serve as a validator, the code does:
```
let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
    StorageError::StorageInconsistentState(format!(
        "Protocol treasury account {} is not found", account_id))
})?;
```
There is no existence check performed anywhere before this — the account is assumed to always exist. `StorageError::StorageInconsistentState` is documented in `core/primitives/src/errors.rs:163-168` as "it's also probably ok to panic in every place that produces this error" — and that is exactly what happens: `chain/chain/src/runtime/mod.rs:1279-1284` catches every `Error::StorageError` other than `FlatStorageBlockNotSupported`/`MissingTrieValue` and calls `panic!("{err}")`.

Nothing in `action_delete_account` (`runtime/runtime/src/actions.rs:299-348`) special-cases the treasury account — the only checks are storage-size (`MAX_ACCOUNT_DELETION_STORAGE_USAGE`) and zero locked/staking balance (`compute_gas_key_balance_sum`/staking check via `check_actor_permissions`). Any account holder, including whoever legitimately controls the treasury account's access key, can submit a normal, self-signed `DeleteAccount` transaction (`predecessor_id == receiver_id == account_id`, per the "Administrative actions ... can be proceed only if sender=receiver" rule in `core/primitives/src/errors.rs:743-748`) and permanently remove the account from state — there is no way to "un-delete" it afterward, since it is a plain named account, not a special protocol-reserved one at the runtime level.

### Impact Explanation
Once the treasury account is deleted, at the very next epoch boundary (which happens roughly every ~12 hours on mainnet-scale epoch lengths, and is unavoidable since epoch transitions are triggered automatically by block height, not by any transaction the attacker needs to keep sending), `update_validator_accounts` will unconditionally hit the missing-account branch and return `StorageInconsistentState`, which every node applying that shard's chunk will `panic!` on. Because this state transition function is deterministic, **every honest validator/RPC node reaches the identical panic**, causing a synchronized, permanent chain halt with no automatic recovery path (the same panic recurs on retry since the account remains deleted). This is a concrete, protocol-level, transaction-triggered halt affecting the entire network, not just the account owner.

### Likelihood Explanation
The precondition is narrow (only the entity controlling the treasury account's private key can trigger it), but it requires no special protocol privilege beyond normal transaction signing rights over one's own account, and the action itself (`DeleteAccount`) is a completely ordinary, always-available action with no safeguard recognizing the account's protocol role. This could occur through operator error (accidentally deleting/renouncing a "no-longer-needed" foundation account) as well as deliberately, mirroring exactly the "renouncing ownership" bug class from the reference report — an unprivileged-reachable action (self-executed by the credential holder) with a disproportionate, protocol-wide consequence and no code-level guard against it.

### Recommendation
Add an explicit guard in `action_delete_account` (or in `check_actor_permissions`) that rejects deletion of the account matching `genesis_config.protocol_treasury_account` (or more generally, any account referenced by protocol-level bookkeeping such as the registrar account), returning a dedicated `ActionErrorKind` instead of allowing the deletion to succeed. Alternatively, make `update_validator_accounts` tolerate a missing treasury account by skipping the reward credit (and logging/metric-emitting the anomaly) rather than returning a fatal `StorageInconsistentState`.

### Proof of Concept
1. On a network whose `genesis_config.protocol_treasury_account` is an ordinary named account (e.g. `near`), sign and submit a transaction from that account to itself: `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: <any_account> })`, exactly as exercised in `meta_tx_delete_account`/`test_delete_account*` (e.g. `integration-tests/src/tests/features/delegate_action.rs:574-620`), targeted at the treasury account instead of a throwaway test account. The account has zero locked stake and storage well under `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, so it passes all existing `action_delete_account` checks and is removed from state via `remove_account` (`core/store/src/utils/mod.rs:487-556`).
2. Wait for the next epoch boundary. `chain/chain/src/runtime/mod.rs:264-274` still populates `protocol_treasury_account_id` from genesis config (unconditionally), and `update_validator_accounts` (`runtime/runtime/src/lib.rs:1664-1669`) calls `get_account(...)?.ok_or_else(...)`, returning `StorageError::StorageInconsistentState("Protocol treasury account ... is not found")`.
3. `apply_chunk` (`chain/chain/src/runtime/mod.rs:1279-1284`) matches this as a generic `StorageError` (not `FlatStorageBlockNotSupported`/`MissingTrieValue`) and executes `panic!("{err}")` — reproducibly, on every node applying the shard, at every future epoch boundary, halting the chain.

    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
