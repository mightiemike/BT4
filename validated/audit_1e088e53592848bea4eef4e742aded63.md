### Title
Panic-as-error-handling in `TransactionBatchProcessor::replenish_program_cache` / `prepare_one_program_for_upcoming_feature_set` can be triggered by an ordinary client transaction that closes a program account, halting the validator - ([File: svm/src/transaction_processor.rs])

### Summary
`TransactionBatchProcessor::replenish_program_cache` and `prepare_one_program_for_upcoming_feature_set` both call `load_program_with_pubkey(...)` and immediately `.expect("called load_program_with_pubkey() with nonexistent account")` on the result, converting a normal `Option::None` (account not found) into a hard panic instead of a `TransactionError`.

### Finding Description
`filter_executable_program_accounts` builds a list of `ProgramToLoad` entries for any account key that resolves (via `callbacks.get_account_shared_data`) to an account owned by a BPF loader: [1](#0-0) 

Both call sites that consume this list then re-fetch the very same accounts a second time and treat "not found" as an unreachable invariant violation rather than an error:

- In the hot transaction-processing path: [2](#0-1) 

- In the epoch-boundary program-cache preparation path: [3](#0-2) 

`load_program_with_pubkey` returns `None` purely and simply when `callbacks.get_account_shared_data(pubkey)` returns `None` at that moment: [4](#0-3) 

For `prepare_one_program_for_upcoming_feature_set`, the `account_loader` parameter is the raw `&CB` (i.e. the `Bank`/callback trait object directly, not a per-batch snapshot `AccountLoader` that caches a consistent view for the duration of one batch), as seen in its signature: [5](#0-4) 

Because there are two independent, non-atomic reads of account state (`filter_executable_program_accounts` then `load_program_with_pubkey`) against a live, mutable `Bank`, any intervening mutation of that specific program account between the two reads — for example, an ordinary client transaction that closes an upgradeable BPF program account (setting its lamports to 0 / removing it, via the standard `bpf_loader_upgradeable` Close instruction) executing concurrently on another banking-stage/replay thread — makes the second lookup return `None` even though the first one succeeded. This turns the documented "cannot happen" assumption behind the `.expect(...)` into a reachable panic driven entirely by unprivileged transaction content (a program-closing instruction any signer of the program's upgrade authority, or any account owner, can submit as an ordinary transaction).

The authors themselves acknowledge the panic is directly reachable given a nonexistent account, evidenced by the existing unit test that documents and expects this exact panic message: [6](#0-5) 

### Impact Explanation
A panic inside `TransactionBatchProcessor`/`replenish_program_cache` occurs while holding the global program cache locks used by every banking/replay thread on the validator. An unhandled panic here unwinds the calling thread (banking stage worker, replay stage, or the epoch-boundary preparation task), and because these are core consensus-critical execution paths, the panic can crash or corrupt the validator process, resulting in a cluster-halting condition if triggered broadly enough or a leader/replay stall for the affected validator. This satisfies the "cluster-halting panic" acceptance bar, since it converts what should be a `TransactionError` (`ProgramAccountNotFound`) into an unrecoverable `panic!`/`unwrap()`-style failure deep in the SVM.

### Likelihood Explanation
Likelihood is Medium: it requires precise timing — a program-closing (or otherwise account-removing) transaction must be committed to the account state between the `filter_executable_program_accounts` scan and the subsequent `load_program_with_pubkey` re-fetch for the same pubkey. For the batch-processing hot path (`load_and_execute_sanitized_transactions`), the two calls use the same per-batch `AccountLoader` snapshot and thus are unlikely to race within a single batch. The higher-risk path is `prepare_one_program_for_upcoming_feature_set`, which reads directly from the live `Bank` (not a frozen per-batch snapshot) via `&CB`, making the TOCTOU window real whenever this preparation runs concurrently with ordinary transaction execution that can close/mutate the exact same program account. An attacker who controls (or colludes with) a program's upgrade/close authority for a widely-used or frequently-invoked program could deliberately time a close instruction to increase the odds of hitting this window, but exact reproduction requires validator-internal concurrency conditions I could not fully verify from static reading (the precise callers/locking of `prepare_one_program_for_upcoming_feature_set` in `runtime/src/bank.rs` were not fully explored before running out of tool budget).

### Recommendation
Replace the `.expect("called load_program_with_pubkey() with nonexistent account")` panics in both `replenish_program_cache` and `prepare_one_program_for_upcoming_feature_set` with graceful handling: treat a `None` result the same as "program account was closed/not found" (analogous to the existing `if missing_programs.is_empty() { return; }` early-return already present for the empty case), and propagate/skip rather than crash. This removes the reliance on an implicit "the account can't disappear between these two reads" invariant that does not hold when account state may be mutated concurrently between the two reads.

### Proof of Concept
Conceptual reproduction (not fully validated against live validator locking, as noted above):
1. Deploy an upgradeable BPF program P via `bpf_loader_upgradeable`.
2. Have many transactions across the cluster reference/invoke P so it is scheduled for program-cache maintenance at an epoch/feature-set boundary via `prepare_one_program_for_upcoming_feature_set`.
3. Concurrently, submit an ordinary transaction from P's upgrade authority (or account owner) that closes P's program/programdata account, zeroing its lamports, timed to land between the `filter_executable_program_accounts` read and the `load_program_with_pubkey` read inside `prepare_one_program_for_upcoming_feature_set`.
4. The second read returns `None`, `.expect(...)` fires, and the panic propagates, corrupting/crashing the affected banking/replay thread. [3](#0-2)

pub fn filter_executable_program_accounts<'a, CB: TransactionProcessingCallback>(
    callbacks: &CB,
    program_cache_for_tx_batch: &ProgramCacheForTxBatch,
    keys: impl Iterator<Item = &'a Pubkey>,
    check_program_deployment_slot: bool,
) -> Vec<ProgramToLoad<'a>> {
    let mut result = Vec::new();
    for account_key in keys {
        if let Some(cache_entry) = program_cache_for_tx_batch.find(account_key) {
            cache_entry.stats.uses.fetch_add(1, Ordering::Relaxed);
        } else if let Some((account, last_modification_slot)) =
            callbacks.get_account_shared_data(account_key)
        {
            let loader = if loader_v4::check_id(account.owner()) {
                ProgramCacheEntryOwner::LoaderV4
            } else if bpf_loader_upgradeable::check_id(account.owner()) {
                ProgramCacheEntryOwner::LoaderV3
            } else if bpf_loader::check_id(account.owner()) {
                ProgramCacheEntryOwner::LoaderV2
            } else if bpf_loader_deprecated::check_id(account.owner()) {
                ProgramCacheEntryOwner::LoaderV1
            } else {
                continue;
            };
            let match_criteria = if check_program_deployment_slot {
                get_program_deployment_slot(callbacks, &account, loader)
                    .map_or(ProgramCacheMatchCriteria::Tombstone, |slot| {
                        ProgramCacheMatchCriteria::DeployedOnOrAfterSlot(slot)
                    })
            } else {
                ProgramCacheMatchCriteria::NoCriteria
            };
            result.push(ProgramToLoad {
                program_id: account_key,
                loader,
                match_criteria,
                last_modification_slot,
            });
        }
