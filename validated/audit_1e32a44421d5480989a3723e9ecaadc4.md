## Title
Unbounded `PendingInbounds.Walk` Scan in `afterInboundBallotTerminal` Turns Attacker-Spammable Inbound Volume into O(n) Validator-Processing Cost per Vote — ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
The external report describes a griefing pattern where an attacker cheaply grows an array (`delegates`) that a victim's unrelated transaction (`transfer`) must later iterate in full, inflating the victim's gas cost by ~100x. The closest reachable analog in Push Chain is the `PendingInbounds` collection and its terminal-vote callback: any unprivileged party can cheaply create many distinct `PendingInboundEntry` records (one per unique `sha256(source_chain:tx_hash:log_index)`), and every single inbound ballot finalization anywhere on the chain then pays an `O(n)` linear scan cost over *all* currently pending entries to locate the one it belongs to.

### Finding Description
`RecordInboundVote` [1](#0-0)  creates a new `PendingInboundEntry` keyed by `utx_key = sha256(source_chain:tx_hash:log_index)` the moment the *first* Universal Validator votes on an observed source-chain event. This key is fully determined by attacker-controllable source-chain transaction content (any distinct `tx_hash`/`log_index` on any registered chain produces a brand-new entry) — no chain-side admission control limits how many concurrent `PendingInboundEntry` records can exist.

When any one of these ballots reaches a terminal state, `BallotHooks.afterInboundBallotTerminal` is invoked and performs a full `Walk` over the *entire* `PendingInbounds` map, with a nested scan over each entry's `Variants` slice, just to find the one entry containing the finalizing `ballotID`: [2](#0-1) 

This is analogous to the `MAX_DELEGATES` griefing pattern: the cost of an operation (`afterInboundBallotTerminal`, fired on *every* inbound vote that reaches quorum, including votes cast for entirely unrelated, honestly-submitted inbounds) scales with the total size of a collection that any unprivileged actor can inflate at will, simply by generating many distinct real (even dust-value) cross-chain deposit events on cheap source chains. The code comment explicitly assumes this can't happen ("the pending set is small and transient"), but nothing enforces that assumption — it is not validated against attacker-driven growth.

`RecordOutboundVote`, by contrast, does a direct O(1) map lookup [3](#0-2)  — the inbound path's design (linear `Walk` instead of an index from `ballotID → utxKey`) is the specific weak point.

### Impact Explanation
Because `MsgVoteInbound` is a gasless message type [4](#0-3) , this does not directly translate into a "100x gas fee" charged to an end user the way the Alchemix report describes. Instead, the impact is a compute-amplification / DoS-class issue: an unprivileged attacker who floods many source chains with distinct low-cost deposit transactions can force every Universal Validator's ballot-finalization hot path (triggered on every single terminal inbound vote, including those cast for legitimate, unrelated users) into `O(n)` work, where `n` is the attacker-inflated size of `PendingInbounds`. Repeated over many concurrently finalizing ballots during a flood, this becomes effectively quadratic processing overhead for honest validators/nodes, degrading throughput for ordinary users' inbound processing — the closest in-scope match to "denial of service ... reachable without privileged control."

### Likelihood Explanation
Moderate-to-low. It requires an attacker to sustain a burst of many distinct, validator-observable source-chain events concurrently (cheap on low-fee L2s, but each such event still costs a source-chain transaction and needs the honest UVs to actually vote before quorum retires the entry). It does not cause fund loss, consensus divergence, or permanent state corruption — it is a resource/availability concern bounded by how large `PendingInbounds` can realistically grow before UVs catch up and finalize outstanding ballots.

### Recommendation
Replace the `PendingInbounds.Walk` scan in `afterInboundBallotTerminal` with a secondary index keyed by `ballotID → utxKey` (mirroring the `PRC20Index` pattern already used in `x/uregistry`, or simply doing a direct lookup analogous to `RecordOutboundVote`'s O(1) `PendingOutbounds.Get`), so ballot-terminal processing cost is independent of the total number of concurrently pending inbound entries.

### Proof of Concept
Not independently exploitable for fund loss; the reasoning path is:
1. Attacker submits N distinct small-value deposit transactions across one or more registered source chains, each with a unique `tx_hash`/`log_index`.
2. Honest UVs observe and begin voting on each — `RecordInboundVote` [5](#0-4)  creates N separate `PendingInboundEntry` records before quorum completes on all of them.
3. As soon as any one ballot (attacker's or an unrelated legitimate user's) reaches quorum, `afterInboundBallotTerminal`'s `PendingInbounds.Walk` [6](#0-5)  must scan all N outstanding entries to locate the matching ballot ID — repeated for every terminal vote received while the flood is outstanding.

func (k Keeper) RecordInboundVote(
	ctx context.Context,
	inbound types.Inbound,
	voter string,
	ballotID string,
) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	height := uint64(sdkCtx.BlockHeight())
	utxKey := types.GetInboundUniversalTxKey(inbound)

	entry, err := k.PendingInbounds.Get(ctx, utxKey)
	if err != nil && !errors.Is(err, collections.ErrNotFound) {
		return err
	}
	if errors.Is(err, collections.ErrNotFound) {
		entry = types.PendingInboundEntry{
			UtxKey:          utxKey,
			CreatedAtHeight: height,
		}
	}

) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
