## Analog Found

Push Chain's isCEA "smart-contract-recipient" execution path reproduces the report's core issue (item 2: an attacker-chosen "enforcer"/recipient can freely consume gas for its own purposes) as an *unbounded, unmetered EVM call into attacker-controlled bytecode*, executed by every validator during consensus-critical, gasless inbound finalization.

### Title
Unbounded gas forwarded to attacker-controlled recipient contract in `CallExecuteUniversalTx` enables free consensus-wide gas griefing - (File: x/uexecutor/keeper/evm.go)

### Summary
For `isCEA` inbounds whose recipient is a plain deployed contract (not a UEA), `ExecuteInboundGasAndPayload` / `ExecuteInboundFundsAndPayload` invoke `k.CallExecuteUniversalTx`, which calls the attacker-chosen recipient's `executeUniversalTx` via `DerivedEVMCall` with `gasLimit = nil`, unlike the sibling user-derived path `CallUEAExecutePayload`, which explicitly parses and enforces `UniversalPayload.GasLimit` as the call's gas cap. Because the recipient contract is fully attacker-controlled (any address the attacker names as `Recipient` on the source-chain deposit) and the call is module-sender/gasless, an attacker can deploy a computationally expensive `executeUniversalTx` implementation and trigger it for free, imposing real CPU/gas cost on every validator each time UV votes reach quorum for that inbound.

### Finding Description
`CallExecuteUniversalTx` passes `nil` as `gasLimit` to `DerivedEVMCall`: [1](#0-0) 

Compare this with the sibling user-derived path, which explicitly derives `gasLimit` from the caller-declared `UniversalPayload.GasLimit` and enforces it on the call: [2](#0-1) 

`CallExecuteUniversalTx` is reached from the `isCEA` "smart contract recipient" branches in both inbound-execution flows, where `ueaAddr`/`recipientAddr` is simply the attacker-supplied `utx.InboundTx.Recipient` from the observed source-chain event — fully attacker-controlled, not the protocol-trusted `UNIVERSAL_CORE` handler used by other module-sender calls (e.g. `CallPRC20Deposit`): [3](#0-2) [4](#0-3) 

The declared `UniversalPayload.GasLimit` is later used only for *fee validation after the fact* — comparing `receipt.GasUsed` against it inside `DeductGasFeesFromReceipt` — never as an actual EVM execution cap for this call site: [5](#0-4) 

Per `DerivedEVMCall`'s documented semantics, `gasLimit=nil` means "use a sensible default," i.e. the call is not bounded by anything the attacker declared: [6](#0-5) 

Because the entire EVM call + fee deduction runs in a `CacheContext` that is discarded whenever fee deduction fails (e.g., the malicious contract holds zero `upc`), the expensive EVM execution still runs and consumes real resources on every voting validator, but no fee is ever collected — this rollback-on-insufficient-balance behavior is confirmed by existing test coverage: [7](#0-6) [8](#0-7) 

`IsCEA`/`Recipient`/`Data` on the `Inbound` are attacker-controlled fields derived from an ordinary source-chain deposit observed and voted on by UVs — no privileged actor is required to trigger this path; only UV vote quorum (an ordinary, expected part of the protocol) is needed to finalize it via `MsgVoteInbound`, which is itself a gasless message: [9](#0-8) 

### Impact Explanation
This is an unprivileged, network-non-local denial-of-service vector: an attacker who controls the destination contract and the source-chain deposit event can force every Push Chain validator to execute an arbitrarily gas-heavy `executeUniversalTx()` implementation on each inbound they trigger, with no monetary cost if the recipient contract is left unfunded (the fee-deduction rollback erases the charge entirely). Repeated cheaply (each unique `source_chain:tx_hash:log_index` produces a new UTX), this degrades block-processing time for the whole validator set — a resource-exhaustion/gas-griefing pattern directly analogous to the report's "enforcer does gas-intensive/griefing work for free" scenario, but here it is baked into a core-protocol execution path rather than a delegation caveat.

### Likelihood Explanation
Likelihood is moderate-to-high: no special privileges, keys, or governance access are required — only a normal source-chain deposit to a self-deployed malicious contract with `IsCEA=true`. The only dependency is reaching UV vote quorum, which is the ordinary, expected lifecycle for any inbound and does not require attacker collusion with validators (honest UVs will vote based on what they observed on the source chain, which the attacker fully controls).

### Recommendation
Enforce `UniversalPayload.GasLimit` (parsed and validated, as already done in `CallUEAExecutePayload`) as the explicit `gasLimit` argument passed to `DerivedEVMCall` inside `CallExecuteUniversalTx`, rather than passing `nil`. This bounds attacker-controlled recipient execution to a caller-declared (and therefore fee-accountable) ceiling, closing the gap between the enforced cap on user-derived calls and the unbounded module-sender call into attacker-owned code.

### Proof of Concept
1. Attacker deploys `MaliciousRecipient` on Push Chain's EVM whose `executeUniversalTx(...)` performs an expensive loop (e.g., large-iteration hashing/storage writes) and leaves the contract's native `upc` balance at zero.
2. Attacker performs a minimal deposit on a configured source chain (e.g., 1 USDC) targeting Push Chain's gateway, setting `isCEA=true`, `recipient=MaliciousRecipient`, and an arbitrary `UniversalPayload` (the declared `GasLimit` field is irrelevant to the actual EVM call cap).
3. UVs observe and vote the inbound via `MsgVoteInbound` (gasless); at quorum, `ExecuteInboundGasAndPayload`/`ExecuteInboundFundsAndPayload` detects the smart-contract-recipient branch and calls `CallExecuteUniversalTx(cacheCtx, MaliciousRecipient, ...)` with `gasLimit=nil`.
4. The expensive contract logic executes fully on every core validator processing the vote transaction, consuming its "sensible default" gas allotment.
5. `DeductGasFeesFromReceipt` fails (zero balance) → the `CacheContext` is discarded → no fee is ever collected, while the deposit (outside the cache) still lands, and the expensive computation already happened on every validator's node.
6. Repeat with new `tx_hash`/`log_index` values to keep forcing free expensive computation.
