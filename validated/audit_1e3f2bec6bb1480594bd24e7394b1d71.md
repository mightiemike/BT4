### Title
Stale resource-usage decay is used to validate delegation limits while the decayed value is discarded before execution - ([File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java])

### Summary
`DelegateResourceContract` lets any account delegate part of its frozen TRX-derived bandwidth/energy to another account. `validate()` computes the "available" balance that can be delegated by first decaying `netUsage`/`energyUsage` via `BandwidthProcessor.updateUsageForDelegated`/`EnergyProcessor.updateUsage`, then subtracting the decayed usage from the frozen balance. `execute()` then performs the delegation using a *freshly re-fetched* `AccountCapsule` from `accountStore`, which never received the decayed usage values computed during `validate()`.

### Finding Description
This mirrors the Sherlock M-11 bug class: an accounting/"claim" step that must be applied before a downstream balance/allocation calculation is either skipped or discarded at the point where the calculation is actually used, producing a mismatch between the value used to authorize an action and the value actually persisted.

In `DelegateResourceActuator.validate()`, `processor.updateUsageForDelegated(ownerCapsule)` (BANDWIDTH) or `processor.updateUsage(ownerCapsule)` (ENERGY) is called to decay stale `netUsage`/`energyUsage` figures forward to "now" before computing the amount available to delegate: [2](#0-1) 

These processor methods only mutate the `AccountCapsule` object instance passed into them; they do not call `accountStore.put(...)` to persist the decayed usage: [1](#0-0) 

`execute()` then obtains a brand-new `AccountCapsule` instance from `accountStore` (not the one mutated in `validate()`), meaning the decay computed for the availability check is thrown away, and the actual state persisted to the account (via `accountStore.put(ownerCapsule.createDbKey(), ownerCapsule)`) still carries the un-decayed `netUsage`/`energyUsage`: [3](#0-2) 

Because the un-decayed (i.e., artificially higher) usage is what remains on-chain, subsequent bandwidth/energy availability calculations (`calculateGlobalNetLimit`, `calculateGlobalEnergyLimit`, and later `DelegateResourceContract`/`UnDelegateResourceContract` calls) that read `getNetUsage()`/`getEnergyUsage()` directly will overstate the account's currently consumed resource relative to what it should be after decay, understating available free resource until a normal transaction happens to trigger `updateUsage` and persist it.

### Impact Explanation
This is a state-divergence/accounting bug reachable by any unprivileged user issuing a `DelegateResourceContract`, an existing, permissionless TRON transaction type used for resource market/staking delegation. The practical effect is transient inaccuracy in on-chain persisted bandwidth/energy usage counters used for resource accounting and further delegation validation, rather than a direct fund-theft primitive — it is closer to the "invalid-state/divergence" class than an "underpriced-public-work" or authentication bypass. It does not, by itself, allow double-delegation because the check inside `validate()` still uses the (correct, decayed) numbers for that one transaction's authorization; the issue is that decayed state is not committed for use by future transactions/queries, which can produce inconsistent-looking usage/available-resource figures.

### Likelihood Explanation
High reachability (any user can call `DelegateResourceContract`), but the concrete consequence is limited to stale usage counters being written back until the next transaction naturally re-decays them, so the likelihood of a serious economic impact is comparatively low. I was not able to fully verify with a live trace/test whether any subsequent logic in the same transaction or block depends on the persisted (undecayed) value in a way that produces a stronger accounting divergence (e.g., double counting available resource in the same block for `UnDelegateResourceContract`); this would require running the actuator test suite (e.g., `framework/src/test/java/org/tron/core/actuator/DelegateResourceActuatorTest.java`) to confirm empirically.

### Recommendation
In `DelegateResourceActuator.execute()`, either reuse the same `AccountCapsule` object (with decayed usage) computed in `validate()`, or re-run `BandwidthProcessor.updateUsageForDelegated`/`EnergyProcessor.updateUsage` on the freshly-fetched `ownerCapsule` before performing the delegation math and persisting it, ensuring the decayed/"claimed" usage state is what gets written to `accountStore`.

### Proof of Concept
Not independently reproduced against a live node in this session; the finding is based on static code-path analysis of `DelegateResourceActuator.validate()`/`execute()` and `BandwidthProcessor`, showing the decayed `AccountCapsule` instance from `validate()` is discarded and a separately-fetched, un-decayed instance is persisted in `execute()`. A concrete PoC would require instrumenting `DelegateResourceActuatorTest` to freeze/delegate resource across a time gap and assert on `getNetUsage()`/`getEnergyUsage()` immediately after `execute()` versus the value computed inside `validate()`.
