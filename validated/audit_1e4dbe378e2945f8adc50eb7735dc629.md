### Title
Permanent freeze of the NEAR Wallet Contract via untrusted external-contract callback panic leaving `has_in_flight_tx` stuck `true` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the Ethereum-transaction-emulation account contract) gates every `rlp_execute` call behind a single boolean flag `has_in_flight_tx`, which is only cleared inside the asynchronous callback that follows a cross-contract call to an arbitrary, attacker-influenced target contract (a NEP-141 token or the address registrar). Because NEAR only persists a receipt's state changes if that receipt's execution does not panic, any panic inside the callback (before it returns) discards the `has_in_flight_tx = false` write and leaves the flag permanently `true`, exactly mirroring the external report's pattern where an uncontrolled external contract's behavior blocks/permanently locks a core user-facing action.

### Finding Description
`rlp_execute` refuses to start a new transaction whenever `self.has_in_flight_tx` is `true`, and unconditionally sets it to `true` before returning any promise: [1](#0-0) 

The flag is only reset back to `false` at the very top of the follow-up callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`): [2](#0-1) [3](#0-2) 

Both of these callbacks are scheduled after a cross-contract call to a `target`/`token_id` account that is fully attacker- or relayer-controlled (any NEP-141 contract address the caller specifies as `target` in the emulated ERC-20 transfer, or the fixed address registrar for base-token transfers). The callback gas budgets are small, fixed constants (`RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_OF_GAS`, `REGISTRAR_LOOKUP_GAS` — each `5 Tgas`), and the callback deserializes the attacker-controlled response with `serde_json::from_slice(&value)`: [4](#0-3) [5](#0-4) 

Per the runtime's receipt-application semantics, if a receipt's execution fails for any reason (including running out of gas while executing the callback function body), the entire state update for that receipt — including the earlier `self.has_in_flight_tx = false` assignment — is rolled back: [6](#0-5) [7](#0-6) 

A malicious or simply misbehaving `target`/`token_id` contract can return an oversized or otherwise expensive-to-deserialize successful response from `storage_balance_of`/`lookup`. Because the static callback gas is a small fixed constant unrelated to the size of the untrusted response, the callback's execution can be made to exhaust its gas budget and panic deterministically. Since the callback never completes, `has_in_flight_tx` is never actually reset to `false` in the committed state, and there is no other function in the contract that clears this flag. Every subsequent `rlp_execute` call from this account then hits the early-return guard and is rejected forever: [8](#0-7) 

### Impact Explanation
This is the same bug class as the master-chef report: reliance on an externally-controlled, untrusted contract's well-behavedness to complete a callback that resets critical internal state. Here the consequence is more severe than the original finding — instead of temporarily blocking one operation, it permanently and irreversibly freezes the entire `WalletContract` account. Once triggered, the account can never again execute any emulated Ethereum transaction (transfers, ERC-20 transfers, function calls, key management) via `rlp_execute`, i.e. all of the account's Ethereum-emulated funds and access become permanently inaccessible through this interface — a concrete "permanently frozen funds" outcome triggered by a single submitted transaction.

### Likelihood Explanation
The `target` account for an ERC-20-style transfer, or any contract that responds to the address-registrar `lookup` call chain, is attacker/relayer-supplied and not vetted by the protocol. Triggering an out-of-gas condition in a tightly gas-budgeted callback by controlling the size/complexity of a successful cross-contract response is a well-understood, reproducible technique requiring no special privilege — only the ability to submit one `rlp_execute` transaction targeting a contract the attacker (or a naturally buggy/upgraded third-party token) controls.

### Recommendation
- Reset `has_in_flight_tx` using a mechanism that survives callback failure, e.g. schedule the flag reset as a separate, minimal, dedicated final callback with generously reserved gas that runs regardless of whether the main callback logic panics, or perform the state mutation before doing any gas-variable work (deserialization of attacker-controlled payloads) inside the callback.
- Bound/validate the size of cross-contract call return values before deserializing them, and/or increase and decouple the gas reserved specifically for safely handling arbitrarily large external responses from the gas used for the rest of the callback logic.
- Add an emergency/administrative recovery path (e.g., time-boxed self-reset) that can clear a stuck `has_in_flight_tx` flag if a scheduled callback never resolves.

### Proof of Concept
1. Owner of the `WalletContract` account submits an `rlp_execute` transaction whose emulated action is an ERC-20 transfer with `target`/`token_id` set to an attacker-deployed "token" contract.
2. `inner_rlp_execute` schedules `storage_balance_of` on that contract followed by `nep_141_storage_balance_callback`, reserving only `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (5 Tgas + downstream) for the callback: [9](#0-8) 
3. The attacker's `storage_balance_of` implementation returns a large/expensive-to-parse successful payload.
4. `nep_141_storage_balance_callback` starts by memory-setting `has_in_flight_tx = false`, then panics (out of gas) while processing `env::promise_result(0)`/`serde_json::from_slice`.
5. Per the runtime's rollback rule, the whole receipt's state changes — including the flag reset — are discarded, so the previously committed `has_in_flight_tx = true` persists.
6. Every future call to `rlp_execute` on this account now short-circuits at the `if self.has_in_flight_tx` guard and returns an error without ever creating a promise, permanently blocking the account.
