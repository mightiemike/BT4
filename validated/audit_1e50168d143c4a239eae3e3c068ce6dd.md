## Title
`TransactionOutput::ensure_match_transaction_info` never validates the native-position state root, letting corrupted/tampered trading-position state pass replay and restore verification - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the function that replay/restore-verification code paths use to check that a locally re-executed (or backup-provided) `TransactionOutput` actually matches the authenticated `TransactionInfo` committed in the ledger's transaction accumulator. It checks status, gas, the write-set hash (`state_change_hash`) and the event root hash, but explicitly skips the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and — most importantly — the `position_state_checkpoint_hash` that commits the native-position (on-chain trading) Sparse-Merkle-Tree root. Combined with the fact that native-position writes are deliberately excluded from the write-set hash itself, this means the only cryptographic commitment to the position state (`position_state_checkpoint_hash`, part of `TransactionInfoV1`, which is accumulator-hashed and therefore validator-signed) is never checked by the local verification routine used during chunk replay and backup verify-execution.

### Finding Description
1. Native-position writes are stored in a `WriteSet` "extension" bucket that is explicitly excluded from serialization/hashing: [1](#0-0) 
The comment states this is "so `TransactionInfo` hashes and the on-disk `WriteSet` format are unaffected" — i.e. these writes do not contribute to `state_change_hash`.

2. The *only* commitment to this state is the periodic, optional `position_state_checkpoint_hash` field added to `TransactionInfoV1`, populated only when the `compute_trading_native_state_roots` feature is active: [2](#0-1) [3](#0-2) 

3. `TransactionOutput::ensure_match_transaction_info` — the function used to validate that a re-executed/backup-provided output matches the committed, accumulator-authenticated `TransactionInfo` — checks status, gas, write-set hash, and event root, but the code itself documents that it *ignores* `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`: [4](#0-3) 

4. This exact function is invoked from the chunk-executor's replay/verify-execution path (used by backup restore's `VerifyExecutionMode` and by `db-tool`'s `replay_on_archive`), which is the mechanism meant to detect if re-executed (or archived) transaction data diverges from what the network actually committed: [5](#0-4) [6](#0-5) 

Because the write-set hash never covers native-position data, and `ensure_match_transaction_info` never independently checks `position_state_checkpoint_hash`, there is no local check anywhere in the replay/verify path that confirms the position-state root a restored/replayed dataset produces actually matches the one signed by validators in `TransactionInfoV1`.

### Impact Explanation
An operator restoring from, or replay-verifying, a backup/archive whose native-position (trading) state data has been corrupted or tampered with (accidentally or maliciously by whoever produced/served the backup) would have that corrupted position Merkle state silently accepted into their database: `write_set`, `events`, `gas_used`, and `status` all still hash-match (since position writes don't affect `state_change_hash`), so `ensure_match_transaction_info` returns `Ok(())` even though the position state root the node computes differs from the one actually committed and signed via `position_state_checkpoint_hash`/`TransactionInfoV1`. This is exactly the "authenticated proof-bearing response bound to the wrong root" class of issue: the accumulator/`TransactionInfo` genuinely authenticates the correct root, but the verification tooling that is supposed to catch divergence from it does not check that field, so committed local state can silently diverge from the correct VM result during restore/replay.

### Likelihood Explanation
The gap is unconditionally present in the code path (not merely theoretical): the comment in `ensure_match_transaction_info` explicitly acknowledges "replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution," confirming the maintainers are aware but have not fixed it. Its real-world severity is currently reduced because `compute_trading_native_state_roots` (the feature gate for `position_state_checkpoint_hash`) is not yet enabled in mainnet per surrounding comments/TODOs; the flaw becomes exploitable in restore/replay-verify workflows only once that feature is turned on, or in any deployment where it already is.

### Recommendation
Extend `ensure_match_transaction_info` (or an accompanying check in the chunk-executor replay/verify path) to compare the locally computed position-state checkpoint root (and the hot-state checkpoint root, also currently skipped) against `txn_info.position_state_checkpoint_hash()` / `hot_state_checkpoint_hash()` whenever those fields are `Some`, before the `compute_trading_native_state_roots` feature is enabled on mainnet.

### Proof of Concept
Local code proof (no live exploit needed since the check is unconditionally absent):
1. `types/src/transaction/mod.rs:2139-2204` — read `ensure_match_transaction_info`; note it checks `status`, `gas_used`, `write_set_hash` vs `state_change_hash`, and `event_root_hash`, but returns `Ok(())` without ever inspecting `txn_info.position_state_checkpoint_hash()`.
2. `types/src/write_set.rs:759-802` — confirm `native_position_iter`/`add_native_positions` live in a `#[serde(skip)]` `extensions` bucket, so `CryptoHash::hash(write_set)` (the value compared as `state_change_hash`) is unaffected by whatever is written to the position tree.
3. `execution/executor/src/chunk_executor/mod.rs:684-707` — confirm `verify_execution` (used for backup verify-execution replay) calls `ensure_match_transaction_info` as its sole cross-check between locally re-executed output and the trusted `TransactionInfo`.
4. Construct (conceptually) an archived transaction list/backup where the write set and events for a transaction are legitimate, but the associated native-position write for that transaction has been altered — `state_change_hash` still matches (extensions aren't hashed), and since `ensure_match_transaction_info` never checks `position_state_checkpoint_hash`, `verify_execution`/`replay_on_archive` would report success even though the restored position Merkle tree diverges from the one actually committed on-chain.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
```
