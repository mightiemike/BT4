This TODO comment flags a real gap worth investigating further — let me confirm how `ensure_match_transaction_info` is used and whether the missing checkpoint-hash validation is a genuine state-integrity issue.## Title
`replay_on_archive`'s `ensure_match_transaction_info` skips checkpoint-hash validation, letting a corrupted state root pass replay-verification — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function used by `db-tool`'s `replay_on_archive` (and `aptos-debugger`/`cli`) to check that a locally re-executed transaction matches the authenticated `TransactionInfo` pulled from an archive/backup — deliberately does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. Only `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash` are checked. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` compares locally computed values (status, gas, write-set hash, event root hash) against the trusted `TransactionInfo` fetched from the archive, but explicitly stops before validating any state-root-derived hash: [2](#0-1) 

The comment in the code itself documents the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```
This function is the sole state-root-adjacent integrity gate used in `replay_on_archive.rs::execute_and_verify`, which drives `cur_txns`/`expected_txn_infos` comparison after block re-execution: [3](#0-2) 

Because none of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` are checked here, a divergence between the locally executed Sparse-Merkle-Tree state root (or the newer hot-state/position-state roots) and the archived, ledger-info-authenticated root at that version will not cause `execute_and_verify` to report an error — as long as the write set, events, gas, and status happen to match. This means the tool can certify "replay succeeded" for a version where the actual committed world-state root differs from what local VM execution produced, silently accepting a wrong/corrupted state commitment as valid.

This is distinct from, and independently verifiable from, the seed report's "missing sub-component in an aggregate correctness check" pattern: just as the Perennial vault's collateral aggregation silently dropped a component (fees) that mattered for a downstream safety decision (liquidation), `ensure_match_transaction_info` silently drops components (checkpoint hashes) that matter for the downstream safety decision of "did replay actually reproduce the correct ledger state."

### Impact Explanation
Replay-verify (`replay_on_archive`, and its wrapper used in the backup-cli `replay_verify` pipeline / CI `testsuite/replay-verify`) is the primary tool operators and Aptos Labs itself use to attest that an archived history, when re-executed, reproduces the exact same ledger state that was actually committed and signed by validators. If the state/hot-state/position-state checkpoint hash is wrong (due to a storage bug, backup corruption, or a bug in state-checkpoint computation itself — several of which are visible nearby, e.g. the hot-state/position-state accumulation logic that was searched above), this tool would not catch it, because it never compares those roots against the trusted, ledger-info-bound `TransactionInfo`. Consumers of "replay succeeded" (auditors, node operators restoring from backup, CI gating releases) would get a false assurance that the durable/authenticated state root is correct, when in fact it is not. This matches the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated API/state-view output bound to the wrong version/root" impact classes.

### Likelihood Explanation
The comment shows this is an intentional-but-documented gap (currently gated behind a not-yet-enabled feature, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), meaning the code path is live today in `replay_on_archive` for every replay run, not just a future feature. Any bug elsewhere in state-checkpoint hash computation (state SMT, hot-state SMT, or the newer "position state" root introduced for `TransactionInfoV1`) would go undetected by this specific verification tool. Triggering it does not require an attacker with special privileges — it only requires that a genuine state-root computation bug exist elsewhere (several new, not-fully-hardened subsystems near this code, e.g. hot-state promotion and position-state checkpointing, are visible in the codebase and are the very features this gap exists to eventually check).

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash()`, `hot_state_checkpoint_hash()` (for V1), and `position_state_checkpoint_hash()` (for V1) against locally computed values whenever those hashes are present in the local execution output, rather than deferring this to a future feature flag. At minimum, `replay_on_archive` and any tool relying on this comparator to gate "replay succeeded" should independently assert on the state checkpoint hash before reporting success.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-tool gap, not an on-chain-triggerable exploit. The proof is the code path itself: `replay_on_archive.rs::execute_and_verify` calls `ensure_match_transaction_info` (line 392) as its only correctness gate after `execute_block`, and that function's own source/comment confirm it does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
