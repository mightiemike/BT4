### Title
Signer state-machine consensus threshold rounds down while block-approval threshold rounds up, letting a sub-quorum signer weight be treated as "agreement" - (File: libsigner/src/v0/signer_state.rs)

### Summary
The intended semantics of `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` (70%) are implemented twice with two different, non-equivalent rounding rules: once as a ceiling in the consensus-critical block-signature check, and once as a floor in the signer network's state-machine agreement check. For the same `total_weight`, these two formulas disagree whenever `total_weight * 7` is not a multiple of 10, breaking the equality that both are supposed to enforce the same 70% threshold.

### Finding Description
`NakamotoBlockHeader::compute_voting_weight_threshold` computes the number of signer-weight units required to approve a Nakamoto block using ceiling division: [1](#0-0) 

```
let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
u32::try_from((total_weight * threshold) / 10 + ceil)
```
i.e. `threshold = ceil(total_weight * 7 / 10)`. This is the value used in `verify_signer_signatures` to decide whether a block's aggregated signer weight is sufficient for it to be accepted as valid: [2](#0-1) 

By contrast, `GlobalStateEvaluator::reached_agreement`, which is the signer software's mechanism for deciding when the signer network as a whole has reached "agreement" on shared state (which miner is active/valid, the current burn view, the tx-replay set, the supported protocol version), uses plain floor integer division on the *same* constant: [3](#0-2) 

```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight) >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
```
i.e. `threshold' = floor(total_weight * 7 / 10)`.

For any `total_weight` where `total_weight * 7 mod 10 != 0`, `threshold' < threshold`. Example: `total_weight = 11` → block-approval threshold = `ceil(77/10) = 8`, but state-machine agreement threshold = `floor(77/10) = 7`. A signer weight of exactly `7` is therefore treated by `GlobalStateEvaluator` as having reached "agreement" on e.g. `current_miner`, `burn_block_view`, or the `tx_replay_set`, even though that same weight (`7 < 8`) would be insufficient to satisfy the canonical, consensus-defining block-approval threshold enforced in `NakamotoBlockHeader::verify_signer_signatures`.

`reached_agreement`/`determine_global_state`/`determine_global_burn_view` feed directly into signer decision-making (e.g. `stacks-signer/src/v0/signer.rs`, `stacks-node/src/nakamoto_node/stackerdb_listener.rs`), which decides which miner/tenure/burn-view the signer treats as canonical and which blocks it will sign. Because the "agreement" bar used to pick a canonical view is lower than the bar actually required to make a block valid on-chain, a bounded set of signers (holding exactly the floor-rounded weight, which is less than the true ceiling-rounded requirement) can cause the signer's local state machine to lock onto a miner/tenure/burn-view state that a stricter, correctly-rounded observer would not yet consider agreed-upon. This is exactly a "signer weight below threshold" divergence: one code path silently accepts a weight that is below the threshold enforced by the other.

### Impact Explanation
This is a High-severity, minority-triggerable divergence between two components that are both supposed to implement the identical 70%-weight quorum rule:
- It can cause signers to disagree amongst themselves (or with the node) about whether a given state (current miner, burn view, replay set) has reached quorum, at boundary weights that are `< 30%` short of true consensus with only rounding as the difference.
- This is bounded, not needing a majority/Sybil attack — it only requires the natural distribution of signer weights to land on a `total_weight` where `total_weight*7 mod 10 != 0` (i.e., most reward cycles, since `total_weight` is rarely a multiple of 10), which is essentially the common case, not an edge case requiring active manipulation.
- The direct consequence is temporary tip/state disagreement among signers about the canonical miner/tenure, matching the "temporary tip disagreement" and "signer weight below threshold" categories called out as valid High-impact findings.

### Likelihood Explanation
High likelihood of occurrence in normal operation: any reward cycle where the total signer weight is not an exact multiple of 10 (the overwhelmingly common case, since weight is derived from stacked STX apportioned across up to hundreds of signers) will have a floor/ceiling threshold mismatch of 1 unit of weight. No attacker action, privileged key, or majority collusion is required — the divergence is purely a rounding defect present in both code paths whenever the natural weight distribution produces a non-exact multiple.

### Recommendation
- Short term: change `GlobalStateEvaluator::reached_agreement` (and `reached_disagreement`) in `libsigner/src/v0/signer_state.rs` to use the exact same ceiling-division formula as `NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs`, or better, factor the threshold computation into a single shared function used by both call sites so the two can never diverge.
- Long term: audit all other places that re-derive a 70%/30% weight threshold from `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` (e.g. `stacks-signer/src/v0/signer.rs`, `stacks-signer/src/chainstate/mod.rs`/`v2.rs`) to confirm they all use the identical rounding rule as the on-chain block-approval check, and add a unit test that asserts equivalence across a range of `total_weight` values.

### Proof of Concept
For `total_weight = 11` (e.g. 11 units of signer weight distributed across the signer set for a reward cycle):
1. `NakamotoBlockHeader::compute_voting_weight_threshold(11)` → `ceil(11*7/10) = ceil(7.7) = 8`. A block needs signer weight `>= 8` of `11` to be considered validly signed per `verify_signer_signatures`.
2. `GlobalStateEvaluator::reached_agreement(7)` with `total_weight = 11` → `7 >= floor(11*7/10) = 7` → `true`. The signer state machine reports "agreement reached" on, e.g., `current_miner`/`burn_block_view` at weight `7`.
3. Signers relying on `reached_agreement` (via `determine_global_state`/`determine_global_burn_view`) will treat the state as canonical and act on it (e.g., decide which miner's tenure to build/sign on) at weight `7`, one unit of weight below the `8` actually required for a block to be accepted by `verify_signer_signatures`. This produces a window in which the signer network's chosen canonical view is not backed by a signer weight sufficient to actually get a block through consensus, causing signer/tip disagreement bounded to this weight gap.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
