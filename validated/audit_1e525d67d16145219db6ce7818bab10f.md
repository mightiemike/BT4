### Title
Unbounded `burnt_gas_reward` fee ratio can panic `checked_sub().unwrap()` in receipt gas-reward accounting, halting chunk application - (File: runtime/runtime/src/lib.rs)

### Summary
Analogous to the reported Astaria bug — where an unchecked/unvalidated `protocolFeeNumerator` could exceed `protocolFeeDenominator` and underflow a fee subtraction — nearcore's `RuntimeFeesConfig::burnt_gas_reward` fraction (mainnet `3/10`) is never bounds-checked at genesis or config-diff ingestion time, yet it is trusted implicitly by an `unwrap()`ed `checked_sub` in `Runtime::apply_action_receipt`.

### Finding Description
In `runtime/runtime/src/lib.rs`, after computing `tx_burnt_amount` for a receipt, the function-call gas reward is computed and then subtracted from `tx_burnt_amount`: [1](#0-0) [2](#0-1) 

`receiver_gas_reward = gas_burnt_for_function_call * burnt_gas_reward.numer() / burnt_gas_reward.denom()`, and `receiver_reward` is priced in tokens at `gas_burn_price`/`gas_purchase_price`. The code then does `tx_burnt_amount = tx_burnt_amount.checked_sub(receiver_reward).unwrap()`. This is only safe as an *invariant*, not something the type system enforces: it holds only because `burnt_gas_reward.numerator/denominator <= 1` in every shipped `RuntimeFeesConfig` (`core/parameters/res/runtime_configs/parameters.yaml` sets `3/10`), and because `gas_burnt >= gas_burnt_for_function_call` for any receipt.

Unlike other rational parameters that are explicitly bounds-checked at genesis validation (`online_max_threshold <= 1`, `gas_price_adjustment_rate < 1`), `burnt_gas_reward` (and other `Rational32` fee parameters such as `pessimistic_gas_price_inflation`, `gas_refund_penalty`) have **no equivalent bounds check** in `core/chain-configs/src/genesis_validate.rs`: [3](#0-2) 

`ParameterTable`/`RuntimeConfigStore` parsing (`core/parameters/src/parameter_table.rs`) also performs no range validation on `Rational { numerator, denominator }` values pulled from YAML config diffs — it only type-converts them into `Rational32`: [4](#0-3) 

If a future protocol-version config diff (via the versioned `RuntimeConfigStore`/`CONFIG_DIFFS` mechanism that every validating node applies deterministically once voted in) ever sets `burnt_gas_reward.numerator > burnt_gas_reward.denominator` (e.g. an off-by-one YAML diff mistake, analogous to the reported "if by error protocolFeeNumerator is set greater than protocolFeeDenominator"), `receiver_gas_reward` could exceed the gas actually burnt for the receipt, and the priced `receiver_reward` could exceed `tx_burnt_amount`. The `checked_sub().unwrap()` at line 1132 would then panic during `apply_action_receipt`, which every honest validating/RPC node executes identically for the same receipt (this is normal `FunctionCall` receipt processing, reachable simply by any account submitting a function call transaction).

### Impact Explanation
A panic inside `Runtime::apply_action_receipt` — reached on the hot path of ordinary `FunctionCall` receipt processing triggered by any user transaction — crashes chunk application deterministically on every node applying that chunk. Because the trigger condition depends only on a network-wide (not per-node) config parameter and a completely ordinary receipt, this is not a Byzantine/malicious-node scenario: it is a transaction-triggered, protocol-wide halt once the bad parameter value is live. This matches the required "transaction-triggered halt" impact category.

### Likelihood Explanation
Likelihood is low under current conditions, since today's shipped `burnt_gas_reward` values (`3/10` on mainnet/testnet, and similarly small fractions in other configs) never approach the unsafe boundary, and no code path lets a transaction sender directly set this value. The exposure is structural, not currently triggered: there is no genesis/config-diff-time guard analogous to the `online_max_threshold <= 1` and `gas_price_adjustment_rate < 1` checks that exist for other rational parameters, so a future protocol-config typo (this exact class of mistake is explicitly what the external report warns about) would not be caught before being voted in and applied. Given `ParameterTable::apply_diff` has no validation for fraction parameters, the safety of this "unchecked" invariant rests entirely on manual review discipline rather than an enforced check.

### Recommendation
Add explicit bounds validation for all `Rational32`-typed fee/reward parameters that runtime code assumes are `<= 1` (`burnt_gas_reward`, `pessimistic_gas_price_inflation` where relevant, `gas_refund_penalty`), either in `ParameterTable`/`RuntimeConfigStore` construction (so a malformed config diff fails to build rather than shipping) or as an explicit genesis/config validation pass mirroring the existing `online_max_threshold`/`gas_price_adjustment_rate` checks in `core/chain-configs/src/genesis_validate.rs`. Additionally, replace the `checked_sub(receiver_reward).unwrap()` at `runtime/runtime/src/lib.rs:1132` with a `checked_sub` that returns a graceful `RuntimeError`/clamps the reward to `tx_burnt_amount`, so that even if the invariant is ever violated the failure mode is a recoverable error rather than a node panic.

### Proof of Concept
Not independently reproducible from the current codebase, since no currently-shipped `RuntimeConfig`/`RuntimeConfigStore` diff sets `burnt_gas_reward.numerator > burnt_gas_reward.denominator`; exploitation requires a future protocol-version config change carrying that mistake. This finding is a defense-in-depth/config-validation gap analogous to the reported Astaria issue, not a currently-exploitable bug with today's parameters — flagged per the instruction to map the *bug class* (unchecked arithmetic reliant on an unvalidated fee ratio) to the strongest analogous reachable nearcore code path, `Runtime::apply_action_receipt`'s function-call gas-reward subtraction.
