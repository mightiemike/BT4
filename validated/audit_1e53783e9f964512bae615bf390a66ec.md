---

### Title
`DelegateAction` Inner Signature Lacks Chain-ID Binding — Cross-Chain Replay of Meta-Transactions — (`core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

---

### Summary

The `SignedDelegateAction` inner signature (NEP-366 meta-transactions) does not commit to any chain identifier. A `SignedDelegateAction` signed for NEAR mainnet is cryptographically valid on NEAR testnet (or any other NEAR-compatible chain) if the same `sender_id` account exists with the same public key and a lower nonce. A malicious relayer — or any party that intercepts the off-chain `SignedDelegateAction` — can replay it on a different chain without the user's consent, causing unauthorized execution of the inner actions on that chain.

---

### Finding Description

In NEAR's meta-transaction design (NEP-366), a user (Alice) creates and signs a `DelegateAction` off-chain. A relayer wraps it in an outer `SignedTransaction` and submits it on-chain. This is structurally identical to the Biconomy pattern: there is an **outer** signed envelope (the relayer's `SignedTransaction`) and an **inner** signed payload (the user's `SignedDelegateAction`).

The outer `SignedTransaction` includes a `block_hash` field that binds it to a specific chain and a specific recency window. The inner `DelegateAction`, however, is signed over a payload that contains **no chain identifier**:

```rust
// core/primitives/src/action/delegate.rs
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,
    pub nonce: Nonce,
    pub max_block_height: BlockHeight,
    pub public_key: PublicKey,
    // ← NO chain_id, NO genesis_hash, NO block_hash
}
``` [1](#0-0) 

The hash that Alice signs is computed in `get_nep461_hash`:

```rust
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
``` [2](#0-1) 

`SignableMessage` prepends only a NEP discriminant (a 4-byte integer derived from NEP number 366 or 611), not any chain-specific value:

```rust
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,  // = NEP_366 constant, same on every chain
    pub msg: &'a T,
}
``` [3](#0-2) 

The discriminant is a fixed constant derived solely from the NEP number:

```rust
SignableMessageType::DelegateAction =>
    MessageDiscriminant::new_on_chain(NEP_366_META_TRANSACTIONS).unwrap()
``` [4](#0-3) 

The runtime's `apply_delegate_action` verifies the inner signature and checks the nonce against on-chain state, but performs no chain-identity check:

```rust
pub(crate) fn apply_delegate_action(...) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() { ... }  // signature check only
    if apply_state.block_height > delegate_action.max_block_height() { ... }  // expiry
    if delegate_action.sender_id().as_str() != sender_id.as_str() { ... }    // account match
    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?; // nonce
    // ← NO check that this chain's genesis_id matches anything in the signed payload
``` [5](#0-4) 

The nonce check in `validate_delegate_action_key` only prevents same-chain replay (it advances the access key nonce on the current chain). It provides no protection against replay on a different chain where the same account/key has a lower nonce: [6](#0-5)

### Impact Explanation

A malicious relayer who receives a `SignedDelegateAction` from Alice can submit it to any NEAR-compatible chain where:
1. `alice.near` exists with the same public key registered.
2. The access key nonce on that chain is lower than the `nonce` in the `DelegateAction`.
3. The current block height is below `max_block_height`.

The inner actions (e.g., `ft_transfer`, `AddKey`, `DeleteAccount`) execute on the target chain without Alice's consent for that chain. This constitutes an **unauthorized transaction** on the target chain. If the inner actions include a `Transfer` with attached deposit (paid by the relayer), the relayer can drain Alice's token balances on the target chain. If the inner actions include `AddKey`, the attacker can gain access to Alice's account on the target chain.

---

### Likelihood Explanation

The attack requires:
- A malicious relayer (or interception of the off-chain `SignedDelegateAction`).
- Alice having the same account ID and public key on multiple NEAR chains (common for mainnet/testnet users).
- A valid nonce window on the target chain.

The relayer is an unprivileged third party — anyone can operate one. The `SignedDelegateAction` is transmitted off-chain to the relayer, making interception possible. The scenario is realistic for any user who has the same named account on mainnet and testnet (a common pattern). The `max_block_height` field limits the replay window but does not eliminate it.

---

### Recommendation

Include the chain's genesis identifier (chain ID + genesis block hash, i.e., `GenesisId`) in the `DelegateAction` signed payload, analogous to how the outer `SignedTransaction` binds to a specific chain via `block_hash`. The `SignableMessage` or `DelegateAction` struct should commit to the chain identity:

```rust
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,
    pub nonce: Nonce,
    pub max_block_height: BlockHeight,
    pub public_key: PublicKey,
    pub chain_id: String,          // e.g., "mainnet", "testnet"
    pub genesis_hash: CryptoHash,  // genesis block hash
}
```

Alternatively, include the chain ID in the `SignableMessage` discriminant or as a prefix in the hash computation. The runtime's `apply_delegate_action` should then verify that the chain ID in the signed payload matches the current chain's genesis ID.

---

### Proof of Concept

1. Alice signs a `DelegateAction` on NEAR mainnet:
   ```
   DelegateAction {
     sender_id: "alice.near",
     receiver_id: "ft.near",
     actions: [FunctionCall { method_name: "ft_transfer", args: {receiver_id: "attacker", amount: "1000"}, ... }],
     nonce: 5,
     max_block_height: 200_000_000,
     public_key: alice_ed25519_pk,
   }
   ```
   Hash = `SHA256(borsh(0x4000016E | DelegateAction{...}))` — identical on mainnet and testnet.

2. Alice sends `SignedDelegateAction` to a relayer off-chain.

3. The relayer submits it to mainnet (legitimate) and also constructs a new outer `SignedTransaction` wrapping the **same** `SignedDelegateAction` and submits it to testnet.

4. On testnet, `apply_delegate_action` calls `signed_delegate_action.verify()` — the signature is valid (same hash, same key). The nonce check passes if Alice's testnet access key nonce < 5. The `ft_transfer` executes on testnet's `ft.near` contract, transferring Alice's testnet FT balance to the attacker.

5. The same attack applies to any NEAR-compatible chain sharing the same account namespace and key infrastructure.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }
