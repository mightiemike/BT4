### Title
Meta-transaction (`Delegate`/`DelegateV2`) inner-action send fees are priced using the outer relayer↔receiver comparison instead of the inner sender↔receiver comparison - ([File: runtime/runtime/src/config.rs])

### Summary
`total_send_fees` in `runtime/runtime/src/config.rs` computes the gas SEND fee for every action using a single boolean, `sender_is_receiver`, that is supplied once by the caller and never re-derived for nested actions. When the action being priced is a `Delegate`/`DelegateV2` (a meta-transaction), the function recurses into the wrapped inner actions but keeps using the *outer* `sender_is_receiver` value (relayer vs. the top-level transaction's `receiver_id`) instead of recomputing it from the delegate action's own `sender_id`/`receiver_id` pair (the "Alice ↔ Bob" hop). This is the same class of bug as the SwapperImpl report: a value (price/fee) is derived from one identity pairing while the actual value transfer/charge that "crosses the wire" pertains to a different pairing, and the mismatch is attacker-controllable.

### Finding Description
`total_send_fees` [1](#0-0)  takes a single `sender_is_receiver: bool` argument that callers compute once (typically `receiver_id == signer_id` for the whole transaction, see `calculate_tx_cost` [2](#0-1) ). For a `Transfer`/`FunctionCall`/etc. this flag correctly reflects whether that particular hop is local (`sir`) or cross-shard (`not_sir`).

For `Delegate` and `DelegateV2` actions, however, the code recurses into the inner actions of the meta-transaction while passing through the *same* outer flag, instead of computing a new flag from the delegate action's own `sender_id`/`receiver_id`: [3](#0-2) 

Per the project's own documentation of the meta-transaction gas model, this is not correct: the inner actions are sent from the meta-transaction's `sender_id` (e.g. "Alice") to its `receiver_id` (e.g. "Bob"), and that second hop's `sir`/`not_sir` fee should be selected by comparing **Alice == Bob**, not by comparing the relayer to Alice: [4](#0-3) 

Because the code instead forwards the relayer↔Alice comparison unchanged into the fee computation for the Alice↔Bob hop, an attacker who controls the outer transaction (any relayer, which is just an unprivileged transaction signer) can decouple the two comparisons: submit a transaction where `signer_id == receiver_id` (so `sender_is_receiver = true`, selecting the cheap `send_sir` fee table) while making the wrapped `DelegateAction.receiver_id` a *different*, cross-shard account (so the real hop is `not_sir`). The gas amount computed and reserved/burned for sending the inner actions therefore uses the cheaper same-shard fee schedule for what is actually a cross-shard send.

### Impact Explanation
This is a fee/gas accounting bypass reachable from a single submitted transaction (any relayer of a meta-transaction, i.e., an ordinary tx signer — no special privilege required). The `sir`/`not_sir` split exists specifically because cross-shard forwarding is more expensive to the network (extra receipt production/transmission work); mispricing it as local both under-burns gas relative to the real work performed and desynchronizes the "pre-charged" (`tx_cost`) balance deduction from the truth of what the actual send should cost. Depending on which side of the recursion actually burns the fee at execution time, this manifests as either a permanent underpayment for cross-shard message routing (fee bypass) or a gas-reservation shortfall that can cause otherwise-valid meta-transactions to run out of prepaid gas partway through execution.

### Likelihood Explanation
High reachability: any account can act as a relayer and submit a `SignedTransaction` containing a `Delegate`/`DelegateV2` action with `signer_id == receiver_id` while setting the inner `DelegateAction.receiver_id` to an unrelated account. No validator collusion, no timing race, and no privileged role is required — this is exactly the mechanic normal meta-transaction relaying already uses, just with the sender/receiver of the outer envelope deliberately made identical.

### Recommendation
In `total_send_fees`, when handling `Delegate`/`DelegateV2`, recompute the `sender_is_receiver` boolean for the recursive call from the delegate action's own `sender_id` and `receiver_id` (i.e. `delegate_action.sender_id == delegate_action.receiver_id`) rather than reusing the outer flag, matching the two-hop `SEND(1)`/`SEND(2)` model described in `docs/architecture/how/meta-tx.md`.

### Proof of Concept
1. Attacker controls account `relayer.near` (any unprivileged account, no stake required) and account `alice.near` — could be the same key/account for both roles, or attacker simply crafts the delegate action's `sender_id` to equal `relayer.near`'s target.
2. Attacker submits `SignedTransaction { signer_id: relayer.near, receiver_id: relayer.near, actions: [DelegateAction{ sender_id: relayer.near, receiver_id: victim_shard_account.near, actions: [Transfer/FunctionCall/...] }] }` — note outer `signer_id == receiver_id`, satisfying `sender_is_receiver = true`.
3. During `verify_and_charge_transaction` → `tx_cost` → `calculate_tx_cost` → `total_send_fees`, the top-level `Delegate` branch is entered with `sender_is_receiver = true` (correct for the relayer→relayer hop) and recurses with the same `true` flag into the inner actions targeting `victim_shard_account.near`, which is on a different shard from `alice.near`/`relayer.near`.
4. The inner actions' SEND fee is computed with the cheap `send_sir` fee table instead of `send_not_sir`, even though the inner actions are genuinely forwarded cross-shard to `victim_shard_account.near`.

Note: I was not able to fully trace, within the available tool budget, the exact call site that burns the corresponding fee at actual `Delegate` receipt-execution time (in `runtime/runtime/src/actions.rs`) to confirm whether that execution path independently recomputes the correct `sender_is_receiver` for the inner hop or also reuses the same value used here. If it independently recomputes correctly, the impact is limited to a gas-reservation/prepaid-gas mismatch (potential execution-time gas exhaustion for legitimately cross-shard delegate actions); if it reuses the same (incorrect) determination, the impact is a genuine, permanent gas/fee underpayment for cross-shard meta-transaction forwarding. This should be verified against `runtime/runtime/src/actions.rs`'s delegate-action handling before remediation.

Ok, now adapt for meta transactions. Let's assume Alice uses a relayer to

   burn the `SEND` fee again. This time based on `Alice == Bob` to figure out
   `sir` or `not_sir`. Let's call this `SEND(2)`.
