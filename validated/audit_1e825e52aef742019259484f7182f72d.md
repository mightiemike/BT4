### Title
Auth middleware only gates `backup_*` RPC methods, leaving privileged node-mutating methods (`batchProver_setCommitments`, `batchProver_submitFakeProof`, `citrea_haltCommitments`/`resumeCommitments`, `txpool_removeTransactionsByHash`/`BySender`) callable by anyone who can reach the RPC port - ([File: crates/common/src/rpc/auth.rs])

### Summary
The external report's bug class is "any caller can invoke privileged functions because there is no whitelist/authorization check." The direct analog in this repository is the `Auth` JSON-RPC middleware, which restricts the API key check to a hard-coded allowlist (`PROTECTED_METHODS`) of only three methods, while every other registered RPC method - including several that mutate critical prover/sequencer state - is dispatched with no authentication at all. [1](#0-0) 

### Finding Description
`Auth::call` only requires (and checks) an API key for methods present in the `PROTECTED_METHODS` constant, which is `["backup_create", "backup_validate", "backup_info"]`. For any other method name, the request is passed straight through to the inner service with no authorization check whatsoever. [2](#0-1) 

This `Auth` layer is the only authorization layer installed on the RPC server (`rpc_middleware` in `start_rpc_server`), so any method not in the allowlist is fully open to any client that can reach the RPC listen address. [3](#0-2) 

Several state-mutating, non-`backup_*` RPC methods are registered on this same server:
- `batchProver::setCommitments` - explicitly documented as overriding existing commitments ("use with caution"). [4](#0-3) 
- `batchProver::submitFakeProof` - triggers the batch prover's own signing key to submit a proof-shaped payload to L1 DA for an arbitrary commitment index range. [5](#0-4) 
- `citrea_haltCommitments` / `citrea_resumeCommitments` on the sequencer, and `txpool_removeTransactionsByHash` / `txpool_removeTransactionsBySender`, which mutate sequencer commitment flow and mempool contents. [6](#0-5) 

Unlike the `backup_*` endpoints, none of these methods carry any additional caller-identity check inside their handler implementations - the RPC dispatch layer is the only place where such a check could be enforced, and it explicitly does not enforce one for these methods.

### Impact Explanation
This matches the report's High-severity bucket directly: "an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`." An attacker who can reach a batch prover's or sequencer's RPC port (which is the same server/middleware stack as the public JSON-RPC endpoint, gated only by the same allowlist) can call `setCommitments` to overwrite sequencer commitments in the prover's ledger, or call `submitFakeProof` to make the batch prover submit a proof-shaped DA transaction signed with the batch prover's own key for a commitment range chosen by the attacker, or halt/resume the sequencer's commitment submission - all without ever presenting the `api_key` that only `backup_*` methods require.

### Likelihood Explanation
No special privilege beyond network access to the RPC endpoint is required; the check that would gate these methods is an explicit name-based allowlist that simply omits them, so the vulnerability is triggered by a normal RPC call structured the way `jsonrpsee`'s `#[rpc]` macro already exposes it - no cryptographic bypass or race condition is needed.

### Recommendation
Change `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs` from an allowlist of methods to protect into a default-deny model (or explicitly add every state-mutating method: `batchProver_setCommitments`, `batchProver_submitFakeProof`, `batchProver_pauseProving`, `citrea_haltCommitments`, `citrea_resumeCommitments`, `txpool_removeTransactionsByHash`, `txpool_removeTransactionsBySender`, etc.) so that any RPC method capable of mutating prover/sequencer/ledger state requires the same API-key check already applied to `backup_*`.

### Proof of Concept
1. Start a batch-prover or sequencer node with its RPC server bound to a reachable address per `start_rpc_server` / `Auth::new` configuration. [7](#0-6) 
2. From an unauthenticated client, send a JSON-RPC request `{"method":"batchProver_setCommitments","params":[[...attacker-chosen commitments...]]}` (or `batchProver_submitFakeProof`, `citrea_haltCommitments`, etc.) with no API key parameter.
3. `Auth::call` checks `PROTECTED_METHODS.contains(&method)`, finds it false for these method names, and forwards the call unmodified to the handler. [8](#0-7) 
4. The handler executes normally, e.g. `set_commitments` overwrites stored sequencer commitments, or `submit_fake_proof` builds and submits a DA transaction using the batch prover's own key for an attacker-specified commitment range. [9](#0-8)

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }

        let Some(api_key) = api_key else {
            return Box::pin(async move {
                MethodResponse::error(
                    req.id().clone(),
                    ErrorObjectOwned::owned(401, "Cannot access protected method", None::<String>),
                )
            });
        };
