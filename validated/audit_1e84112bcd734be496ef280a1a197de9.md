### Title
`collateral-add` permanently credits collateral even when the malicious `<ft-trait>` transfer call returns `(ok false)`, because `try!` only unwinds on `Err`, not on a falsy `Ok` — ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
`collateral-add` writes the increased balance to the `collateral` map (via `add-user-collateral`, bound in the `result` `let`-binding) before it calls the caller-supplied `<ft-trait>` implementation's `transfer` function through `receive-tokens`. `try!` unwraps a `response`, but it only aborts execution on the `Err` variant — a legitimate `(ok false)` response from a malicious token contract is accepted as success, so the map write is never rolled back even though no tokens were actually received.

### Finding Description
Sequence of `collateral-add` (`mainnet/contracts/market/v0-market-vault.clar`, function `collateral-add`):
1. `let`-bindings evaluate strictly in order: `states`, `entry` (`resolve-or-create`), `user-id`, `mask`, `updated-mask`, `updated-entry`, and finally `result`. [1](#0-0) 
2. The `result` binding calls `add-user-collateral`, which performs `map-set collateral key updated-collateral-amount` — this is a real, immediately-applied state write, executed *before* any external call. [2](#0-1) 
3. Only after the `let` completes does the function body run `(try! (check-impl-auth))`, the pause/amount `asserts!`, and then `(try! (receive-tokens ft amount account))`, which performs `(contract-call? asset transfer amount account current-contract none)` on the attacker-controlled `ft` trait implementation. [3](#0-2) [4](#0-3) 
4. Because `map-set` writes are applied to the live execution context immediately, a callback made from within the malicious `transfer` implementation (e.g. a nested `contract-call?` back to `get-collateral`) does observe the incremented value before the transaction finishes — confirming the CHECK_THEN_ACT_INTEGRITY concern raised in the question.
5. However, the critical defect is what happens next: `try!` only short-circuits on the `Err` variant of a `response`. If the malicious `transfer` implementation returns `(ok false)` (a syntactically valid, non-erroring response) instead of actually moving tokens, `try!` simply binds `false` and execution **continues normally** to `(insert updated-entry)` and `(ok result)`. The transaction does **not** unwind, so the `map-set collateral` performed in step 2 is never rolled back. [5](#0-4) 

The root cause is that `receive-tokens`/`collateral-add` never asserts the boolean payload of the transfer response (e.g., `(asserts! (try! (receive-tokens ...)) ERR-...)`); it only guards against Clarity-level `Err`. A crafted `<ft-trait>` implementation that returns `(ok false)` without transferring any tokens defeats this check entirely, and the collateral bookkeeping is left permanently mutated with no assets actually deposited.

### Impact Explanation
This lets an attacker record inflated/phantom `collateral` map entries for an account without ever transferring real tokens into the vault. If that fabricated collateral is later usable to borrow real assets from the market (subject to `asset-id`/`ft` correspondence enforced elsewhere in the market layer, which was not fully verifiable from the code inspected), this constitutes direct theft of user/protocol funds and insolvency — Critical. Even absent a downstream borrow, an accounting map that no longer reflects real backing assets is itself a broken security invariant of a lending market's core ledger.

### Likelihood Explanation
The precondition is that an unprivileged attacker can get their own `<ft-trait>` contract used as the `ft` argument to `collateral-add` (directly reachable if `check-impl-auth`'s required caller — the registered `impl`/market contract — forwards a caller-supplied trait, as the question's rules explicitly allow "deploys its own Clarity contract and passes it as `<ft-trait>`"). Given that, the exploit requires no capital and is fully attacker-chosen and repeatable — the attacker's own malicious contract simply returns `(ok false)`.

### Recommendation
In `collateral-add` (and any other function relying on `receive-tokens`/`send-tokens`), explicitly assert the boolean payload of the transfer response rather than only checking for `Err`, e.g.:
```clarity
(asserts! (try! (receive-tokens ft amount account)) ERR-COLLATERAL-TRANSFER-FAILED)
```
Additionally, perform the collateral map mutation only after the token transfer has been confirmed successful, to preserve check-then-act ordering even for well-behaved tokens.

### Proof of Concept
1. Deploy a mock `<ft-trait>` contract `evil-ft` whose `transfer` function ignores its arguments and returns `(ok false)`.
2. In a Clarinet simnet test, register/authorize `evil-ft` as usable via the market's deposit-collateral path (or call `market-vault.collateral-add` directly if `check-impl-auth` permits, per test harness setup mirroring the deployed `impl`).
3. Call `collateral-add account amount evil-ft asset-id`.
4. Assert the call returns `(ok amount)` (no abort).
5. Call `market-vault.get-collateral id asset-id` and assert it now returns `amount`, despite `evil-ft`'s balance/vault balance showing zero tokens actually moved — demonstrating the collateral map write is not rolled back even though no real transfer occurred.
