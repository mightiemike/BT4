## Title
Native-position writes (`Extension::NativePosition`) are excluded from the `WriteSet` hash bound into `TransactionInfo.state_change_hash`, breaking write-set/proof integrity for durable trading-position state - (File: `types/src/write_set.rs`)

### Summary
`TransactionOutputListWithProof::verify` (and other proof-verification paths) authenticate a transaction's write set by comparing `CryptoHash::hash(&txn_output.write_set)` against `txn_info.state_change_hash()`, which is itself accumulator-proven up to a signed `LedgerInfo`. However, `WriteSetV0` marks its `hotness` and `extensions` fields with `#[serde(skip)]`, and `Extension::NativePosition` (the bucket that carries real, durably-committed "Position" state writes consumed by `NativeStateCommitter`/`PositionDb`) lives inside `extensions`. Because BCS serialization — and therefore the derived `CryptoHash` — skips these fields, two write sets that differ only in their native-position content hash identically and both satisfy the same `state_change_hash` proof.

### Finding Description
`types/src/write_set.rs` defines:
```
pub struct WriteSetV0 {
    value_writes: WriteSetMut,
    #[serde(skip)]
    hotness: BTreeSet<StateKey>,
    #[serde(skip)]
    extensions: Vec<Extension>,
}
``` [1](#0-0) 

The comment explicitly documents the intent: "Skipped from serde so `TransactionInfo` hashes and the on-disk `WriteSet` format are unaffected." [2](#0-1) 

`Extension::NativePosition` carries `NativePositionOp` entries, described as being "consumed by [the] storage commit applier" and feeding `PositionDb`: [3](#0-2) 

These writes are actually applied durably: `NativeStateCommitter::apply` writes each `(state_key, WriteOp)` into `PositionValueSchema`/`StalePositionValueIndexSchema` and produces `MerkleLeafUpdate` entries used to update a position Merkle tree. [4](#0-3) 

Meanwhile, `WriteSet` derives its cryptographic hash straight from `Serialize`:
```
#[derive(BCSCryptoHash, Clone, CryptoHasher, ...)]
pub enum WriteSet { V0(WriteSetV0), V1(WriteSetV1) }
``` [5](#0-4) 

And `TransactionOutputListWithProof::verify` uses exactly this hash to authenticate outputs against the accumulator-proven `TransactionInfo`:
```
let write_set_hash = CryptoHash::hash(&txn_output.write_set);
ensure!(
    txn_info.state_change_hash() == write_set_hash,
    ...
);
``` [6](#0-5) 

Because `hotness`/`extensions` never enter the BCS bytes that get hashed (for `WriteSetV0`, which is the persisted/committed variant — see `WriteSetMut::freeze()` which always builds `WriteSet::V0`) [7](#0-6) , the `state_change_hash` recorded in `TransactionInfo` — and thus covered by the transaction accumulator and ultimately by validator signatures on `LedgerInfo` — carries **no cryptographic commitment to the native-position writes actually persisted to `PositionDb`**.

### Impact Explanation
This breaks the core proof-and-storage invariant required here: "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged" and "Authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object."

Concretely:
- Any consumer that verifies a `TransactionOutputListWithProof`/`TransactionOutputWithProof` (state sync, backup/restore replay, light clients, `TransactionRestoreBatchController`) has no way to detect tampering, corruption, or divergent execution of the `NativePosition` portion of a write set — the exact same `TransactionInfo`/accumulator proof validates arbitrarily different native-position contents.
- Restore and replay paths (`storage/aptosdb/src/db/aptosdb_writer.rs`, `TransactionRestoreBatchController`) apply `wsets` (full `WriteSet`, including whatever `NativePosition` extension a backup/data source supplies) after only checking the (non-covering) `state_change_hash`, so a corrupted or substituted backup/data-service response can silently commit different position/trading state into `PositionDb` on the restoring node, producing durable ledger data that a legitimate proof falsely certifies as correct.
- Because the divergence is invisible to the state-change-hash / accumulator chain, this is a hard-fork-class integrity gap: two full nodes could end up with different `PositionDb` contents for the same, fully-verified transaction history, with no proof-level or accumulator-level signal of disagreement.

This satisfies the "Committed state that differs from the correct VM result" and "authenticated ... proof accepted as valid [when it should not be]" impact categories.

### Likelihood Explanation
No privileged access is required to trigger the divergence: any party supplying transaction/output data over the state-sync or backup/restore paths (a faulty or adversarial full node, storage service, or corrupted backup blob) can substitute different `NativePosition` write content while keeping `value_writes` (and hence the checked hash) identical, and the standard proof-verification code path (`TransactionOutputListWithProof::verify`, restore's `save_transactions`) will accept it. The design is intentional per the `#[serde(skip)]` comment, meaning the gap is systematic rather than a one-off bug, increasing the likelihood this path is reached by any consumer of native-position/trading data through untrusted or semi-trusted state-sync/backup channels.

### Recommendation
Include a commitment to `Extension::NativePosition` (and, if security-relevant, `hotness`) in the value that gets hashed into `TransactionInfo`, e.g., by adding a dedicated hash field to `TransactionInfo` for native/side-channel writes (mirroring how `event_root_hash`/`state_change_hash` are handled), or by removing `#[serde(skip)]` from fields that carry durably-committed state so they participate in `state_change_hash`. Any data that is written to durable storage and later read back as authoritative state must be covered by the transaction's cryptographic commitment chain.

### Proof of Concept
1. Take a `TransactionOutput` whose `WriteSet` (`WriteSetV0`) has some `value_writes` W and native-position bucket `extensions = [Extension::NativePosition(P1)]`, with `TransactionInfo.state_change_hash = H = CryptoHash::hash(WriteSet{ value_writes: W, hotness: {}, extensions: [NativePosition(P1)] })`.
2. Construct a second `WriteSet` with identical `value_writes` W but a different native-position bucket `extensions = [Extension::NativePosition(P2)]` (P2 ≠ P1).
3. Because `hotness`/`extensions` are `#[serde(skip)]` on `WriteSetV0`, `CryptoHash::hash` (BCS-based) of both write sets is identical: `CryptoHash::hash(WriteSet2) == H`. [1](#0-0) 
4. Feed `WriteSet2` (with `P2`) as part of a `TransactionOutputListWithProof` (or via the backup/restore `output_with_proof.transactions_and_outputs`) alongside the original `TransactionInfo`/accumulator proof for H.
5. `TransactionOutputListWithProof::verify` succeeds because `txn_info.state_change_hash() == write_set_hash` holds trivially [6](#0-5) , and the restore/commit path (`restore_utils::save_transactions` → `NativeStateCommitter::apply`) durably commits `P2`'s position writes into `PositionDb` [4](#0-3)  even though the ledger's authenticated proof chain only ever certified `P1`.

I was not able to confirm in the time available whether the position-Merkle-tree root produced by `NativeStateCommitter`/`position_merkle_db.rs` is separately folded into the `LedgerInfo`/consensus data hash (which would provide an independent binding); if it is not, the divergence described above is also invisible at the ledger-info/consensus level, making this a full state-integrity/hard-fork-class gap rather than a merely local one.

```rust
    pub fn apply<P>(
        &self,
        version: Version,
        position_writes: P,
        sharded_kv_batches: &mut PositionShardedKvBatches,
        in_chunk_prior: &mut InChunkPriorVersions,
    ) -> Result<NativeMerkleLeafUpdates>
    where
        P: IntoIterator<Item = (StateKey, WriteOp)>,
    {
        let mut position_merkle: Vec<MerkleLeafUpdate> = Vec::new();
        for (state_key, op) in position_writes {
            match state_key.inner() {
                StateKeyInner::TradingNative(TradingNativeKey::Position { .. }) => (),
                other => {
                    return Err(AptosDbError::Other(format!(
                        "position_write_set contained non-Position StateKey: {other:?}"
                    )));
                },
            };
            let maybe_value = op.as_state_value_opt().cloned();
            let kind_label = if maybe_value.is_some() {
                "upsert"
            } else {
                "delete"
            };
            POSITION_WRITES.with_label_values(&[kind_label]).inc();
            let state_key_hash = state_key.hash();
            let shard = ShardedKvDb::shard_of_state_key(&state_key);
            let pos_batch = sharded_kv_batches[shard].get_or_insert_with(SchemaBatch::new);

            // In-chunk map first (same-chunk earlier writes), then DB.
            let prior_v = match in_chunk_prior.get(&state_key_hash) {
                Some(&v) => Some(v),
                None => self
                    .position_db
                    .find_prior_version(state_key_hash, version)
                    .map_err(|e| AptosDbError::Other(format!("find_prior_version: {e}")))?,
            };
            // Always emit a stale-index row — first writes use
            // `NO_PREV_VERSION` and the pruner skips them via
            // `is_first_write()`. Lets truncation iterate this CF
            // alone to reach every kv row.
            pos_batch
                .put::<StalePositionValueIndexSchema>(
                    &StalePositionValueIndex {
                        stale_since_version: version,
                        version: prior_v.unwrap_or(StalePositionValueIndex::NO_PREV_VERSION),
                        state_key_hash,
                    },
                    &(),
                )
                .map_err(|e| AptosDbError::Other(format!("stale_position_value_index put: {e}")))?;
            pos_batch
                .put::<PositionValueSchema>(&(state_key_hash, version), &maybe_value)
                .map_err(|e| {
                    AptosDbError::Other(format!("position_value batch put failed: {e}"))
                })?;

            in_chunk_prior.insert(state_key_hash, version);

            let value_hash = maybe_value.as_ref().map(StateValue::hash);
            position_merkle.push(MerkleLeafUpdate {
                state_key_hash,
                state_key: state_key.clone(),
                value_hash,
            });
        }

        Ok(NativeMerkleLeafUpdates {
            position: position_merkle,
        })
    }
