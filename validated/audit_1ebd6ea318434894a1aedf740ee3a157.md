### Title
Fee-dependent `valueBalance` divergence between cached SNARK proof verification and pool-value debit - (File: `ShieldedTransferActuator.java`)

### Summary
`calcFee()` is state-dependent (it returns `ShieldedTransactionCreateAccountFee` if the transparent-to account does not yet exist, otherwise the lower `ShieldedTransactionFee`), and `checkProof()`'s cryptographic value-balance validation is skipped on any re-validation once `ZKProofStore` has cached a `true` result for the transaction id. This allows the `valueBalance` bound by the Sapling binding signature (computed with `fee_v` at the time of the first successful `validate()`) to diverge from the `valueBalance` actually applied to `Commons.adjustTotalShieldedPoolValue` in `execute()` (computed with `fee_e` from a fresh `calcFee()` call), since account-creation state for the `toAddress` can change between the two calls without triggering re-verification.

### Finding Description
`checkProof()` computes `valueBalance = addExact(subtractExact(toAmount, fromAmount), fee)` and feeds it to `librustzcashSaplingFinalCheck` [1](#0-0) . Critically, at the very start of `checkProof()`, if the transaction id is already present in `proofStore`, the function short-circuits and returns without recomputing or re-checking `valueBalance` against the current `fee` at all: [2](#0-1) .

`fee` itself is not a transaction field but is recomputed via `calcFee()` on every call to `validate()` and `execute()`, and its value depends purely on mutable chain state — whether an account already exists at `transparentToAddress`: [3](#0-2) .

Exploit flow:
1. Attacker crafts a `ShieldedTransferContract` with a `transparentToAddress` that does **not** yet have an account. `calcFee()` returns the higher `ShieldedTransactionCreateAccountFee` (`fee_v`).
2. Attacker submits/broadcasts the transaction; `validate()` runs, computes `fee_v`, and `checkProof()` verifies the binding signature against `valueBalance_v = toAmount - fromAmount + fee_v`, then records `proofStore.put(txId, true)` [4](#0-3) .
3. Before this transaction is actually included/executed on-chain, the attacker (or anyone) causes an account to be created at the same `transparentToAddress` (e.g., a trivial TRC10/TRX transfer to that address in an earlier transaction/block).
4. When the block processor later re-validates this pending transaction (a normal re-validation path, e.g. re-verification during block assembly/import), `validate()` runs again, `calcFee()` now returns the lower `ShieldedTransactionFee` (`fee_e < fee_v`), but `checkProof()` sees `proofStore.has(txId) == true` and returns immediately — the SNARK/binding-signature check for `valueBalance_e` is never performed.
5. `execute()` then runs using the newly recomputed `fee_e`, and applies `Commons.adjustTotalShieldedPoolValue(addExact(subtractExact(toAmount, fromAmount), fee_e), dynamicStore)` [5](#0-4) , and burns `fee_e` (not `fee_v`) to the blackhole account [6](#0-5) .

The result: the pool-value debit/credit and fee burn actually committed to chain state (`valueBalance_e`) is never the value that was cryptographically attested by the Sapling binding signature (`valueBalance_v`). No guard exists to detect or reject this divergence because the proof-cache skip in `checkProof()` bypasses re-validation entirely.

### Impact Explanation
`totalShieldedPoolValue` (and the transparent blackhole fee burn) is adjusted by an amount that was never proven consistent with the zk-SNARK binding signature. Depending on the direction of fee change, this either under-debits the shielded pool relative to what was cryptographically committed (silently inflating value available in the shielded pool over time) or causes incorrect accounting of collected fees, breaking the core invariant that on-chain state changes for shielded transactions must be provably consistent with the value proven by the binding signature.

### Likelihood Explanation
This requires: (a) a transparent-to address that does not yet have an account at submission time, (b) the transaction being re-validated (not just validated once) before being executed — a normal occurrence when a transaction sits in the pending pool and is revalidated during block packing/import, and (c) an account being created at that same address between the two validations. All three conditions are achievable by an ordinary, unprivileged actor with two ordinary transactions (no special privileges, no local keys, no admin access), making this feasible and repeatable, though it requires precise timing/sequencing across two transactions in the mempool/block-processing window.

### Recommendation
Do not allow `checkProof()`'s cached-result short-circuit to bypass fee/valueBalance consistency checks. Either (1) persist and re-check the exact `fee`/`valueBalance` used at proof-recording time and reject re-validation if the freshly computed `fee` differs, or (2) make `calcFee()` deterministic and independent of mutable account-existence state for the lifetime of a given transaction (e.g., snapshot the fee decision once and store it keyed by transaction id alongside the proof cache), ensuring `execute()` always uses the exact fee that was cryptographically bound during `checkProof()`.

### Proof of Concept
Java integration test plan (`ShieldedTransferActuatorTest`):
1. Build a `ShieldedTransferContract` with `transparentToAddress = addrX` (no existing account), valid spend/receive descriptions and binding signature computed against `fee = ShieldedTransactionCreateAccountFee`.
2. Call `actuator.validate()` — assert it succeeds and `proofStore.has(txId) == true`.
3. Outside the actuator, insert an `AccountCapsule` for `addrX` into `accountStore` (simulating a concurrent account-creation transaction).
4. Call `actuator.validate()` again — assert (bug) that it returns `true` without re-invoking `librustzcashSaplingFinalCheck` (verifiable via a spy/mock on `JLibrustzcash`, or by asserting no exception is thrown despite `calcFee()` now returning a different value).
5. Call `actuator.execute()` and capture the value passed to `Commons.adjustTotalShieldedPoolValue` (via a spy on `Commons` or by asserting the resulting `dynamicStore.getTotalShieldedPoolValue()`).
6. Assert that the `valueBalance` applied in step 5 (`toAmount - fromAmount + ShieldedTransactionFee`) differs from the `valueBalance` originally verified in step 2 (`toAmount - fromAmount + ShieldedTransactionCreateAccountFee`), demonstrating the divergence between the cryptographically-proven value and the actually-applied pool-value adjustment.

  private long calcFee(ShieldedTransferContract shieldedTransferContract) {
    byte[] toAddress = shieldedTransferContract.getTransparentToAddress().toByteArray();
    boolean hasTransparentTo = (toAddress.length > 0);
    if (hasTransparentTo) {
      AccountCapsule toAccount = chainBaseManager.getAccountStore().get(toAddress);
      if (toAccount == null) {
        return chainBaseManager.getDynamicPropertiesStore()
            .getShieldedTransactionCreateAccountFee();
      }
    }
    return chainBaseManager.getDynamicPropertiesStore().getShieldedTransactionFee();
  }
