### Title
Integer-division truncation in `ParticipateAssetIssueActuator` causes buyers to overpay for asset-issue participation, with the rounding dust captured by the issuer - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
`ParticipateAssetIssueActuator.execute()` debits the full TRX `cost` from the participating account but credits it with `exchangeAmount = floorDiv(cost * num, trxNum)` tokens — a value rounded down by integer division. The counterparty (the asset issuer, `toAccount`) receives the entire, un-truncated `cost` in TRX yet only loses the truncated `exchangeAmount` of tokens. This mirrors the reported `AllocationVesting.lockFutureClaimsWithReceiver()` bug class: the caller is charged the exact input amount, but the amount actually credited/locked is rounded down, and the truncated remainder is not returned to the caller — it is effectively transferred to another party instead of being preserved for the payer.

### Finding Description
In `execute()`:
```
long cost = participateAssetIssueContract.getAmount();
...
long balance = subtractExact(ownerAccount.getBalance(), cost);   // full cost debited
...
long exchangeAmount = multiplyExact(cost, assetIssueCapsule.getNum());
exchangeAmount = floorDiv(exchangeAmount, assetIssueCapsule.getTrxNum());  // truncated
ownerAccount.addAssetAmountV2(key, exchangeAmount, ...);          // truncated amount credited
...
toAccount.setBalance(addExact(toAccount.getBalance(), cost));     // issuer gets FULL cost
toAccount.reduceAssetAmountV2(key, exchangeAmount, ...);          // issuer only loses TRUNCATED amount
``` [1](#0-0) 

The same truncation is echoed in validation: [2](#0-1) 

Because `exchangeAmount` is computed with `floorDiv`, whenever `cost * num` is not an exact multiple of `trxNum`, up to `trxNum - 1` "units" of proportional token value are lost by the buyer: the buyer paid for `cost * num / trxNum` (exact) tokens but only receives the floor of that value, while the seller/issuer keeps the full TRX payment and only relinquishes the smaller, truncated token amount. This is functionally identical to the reported bug: an amount is debited in full, but a rounded-down amount is what is actually delivered/locked, and the dust is not refunded to the payer — instead the counterparty benefits.

The existing test suite even documents this behavior as expected, confirming the rounding is real and reproducible: [3](#0-2) 

### Impact Explanation
Any unprivileged account calling `ParticipateAssetIssueContract` (via `ParticipateAssetIssueActuator`) with an `amount` such that `amount * num` is not evenly divisible by `trxNum` overpays in TRX relative to the tokens actually received. The truncated fractional token value is retained by the asset issuer's balance because only the (smaller) truncated `exchangeAmount` is deducted from `toAccount`, while `toAccount` receives the buyer's entire, non-truncated TRX payment. This is an accounting/settlement flaw: value that should belong to the buyer (or at minimum be prevented from being paid) is silently transferred to the issuer on every imprecise participation. Repeated participation using amounts chosen to maximize truncation error lets an issuer (or a colluding buyer/issuer pair) systematically extract dust value across many transactions.

### Likelihood Explanation
This code path is reachable by any account with a positive balance issuing a `ParticipateAssetIssueContract` transaction — no privileged role is required. The condition `cost * num % trxNum != 0` is easy to trigger by choosing an appropriate `amount`, and is common whenever `trxNum`/`num` are not simple round ratios (which asset issuers control at `AssetIssueContract` creation time). The bug is deterministic and requires no race condition or special network state.

### Recommendation
Use exact-division validation (reject amounts that don't divide evenly) or refund the truncated remainder in TRX back to the buyer before finalizing the transfer, e.g.:
```
long exchangeAmount = multiplyExact(cost, num);
long remainder = exchangeAmount % trxNum;
exchangeAmount = exchangeAmount / trxNum;
if (remainder != 0) {
    // either reject the transaction, or refund the TRX equivalent of `remainder`
    // back to the owner instead of transferring it to `toAccount`.
}
```
This ensures the buyer is only ever debited proportionally to what they actually receive, consistent with the recommendation in the original report to truncate the debited amount up front rather than truncate the delivered amount after the debit.

### Proof of Concept
1. Asset issuer creates an `AssetIssueContract` with `trxNum = 3`, `num = 1` (i.e., 3 TRX buys 1 token).
2. Buyer calls `ParticipateAssetIssueContract` with `amount = 1` TRX.
   - `cost = 1`
   - `exchangeAmount = floorDiv(1 * 1, 3) = 0`
   - Validation at [4](#0-3)  throws `"Can not process the exchange!"` for `exchangeAmount <= 0`, so this exact micro-case is blocked.
3. However, for `amount = 4` TRX with `trxNum = 3`, `num = 1`:
   - `exchangeAmount = floorDiv(4, 3) = 1` (not 4/3)
   - Buyer pays 4 TRX in full (debited via `subtractExact(ownerAccount.getBalance(), cost)`), but only receives 1 token, whereas the exact proportional entitlement is 1.33 tokens.
   - `toAccount` receives the full 4 TRX (`addExact(toAccount.getBalance(), cost)`) but only loses 1 token from its asset balance (`reduceAssetAmountV2(key, exchangeAmount, ...)`), retaining the "1/3 token worth" of dust value that the buyer paid for but never received.
   - This matches the pattern validated by the existing test `sameTokenNameCloseExchangeDevisibleTest`, which asserts `owner.getAssetMapForTest() == (999L * NUM) / TRX_NUM` — the floor-divided (truncated) amount — as the expected, unrefunded result. [5](#0-4)
