### Title
Unrestricted "BOOTSTRAP" declare bypasses signature validation and fee enforcement for any transaction sender - ([File: crates/starknet_api/src/executable_transaction.rs])

### Summary
A hardcoded sender address (`'BOOTSTRAP'`) causes the sequencer's declare-transaction execution path — in both the Rust `blockifier` and the Starknet OS Cairo program — to skip `__validate_declare__` signature verification, nonce incrementing, and fee charging entirely. The condition that triggers this bypass is derived purely from transaction *fields* (`sender_address`, `nonce`, `charge_fee`) rather than from any privileged/authenticated context, block-number gate, or node-operator-controlled runtime state. Any unprivileged transaction sender who can craft an RPC declare transaction with `sender_address == bootstrap_address()`, `nonce == 0`, and resource bounds that evaluate to zero possible fee can reach this code path.

### Finding Description
`DeclareTransaction::is_bootstrap_declare` treats a declare transaction as a "bootstrap" transaction purely based on transaction content: [1](#0-0) 

This flag is consumed in `AccountTransaction::execute_raw`, where, if true, the transaction's `__validate_declare__` entry point is never invoked, no fee is charged, and (per the accompanying comment) "no account-related action" — including nonce increment — occurs: [2](#0-1) 

The identical bypass exists independently in the Starknet OS Cairo re-execution path, which is used for proving: it checks `sender_address == 'BOOTSTRAP' and tx_info.nonce == 0 and tx_info.version == 3`, and if `max_possible_fee == 0`, declares the class and returns without running `__validate_declare__` or charging fee: [3](#0-2) 

Reaching this path from the gateway requires only:
1. Setting `sender_address` to the fixed constant `bootstrap_address()` (`0x424f4f545354524150`, ASCII "BOOTSTRAP") — a value any client can compute and is not derived from any signature or account deployment.
2. `check_declare_permissions` in the gateway only rejects declares if `block_declare` is set or if `authorized_declarer_accounts` is configured and excludes the sender; by default (`authorized_declarer_accounts = None`) any address, including the bootstrap address, is permitted: [4](#0-3) 
3. Setting resource bounds so that `max_possible_fee(Tip::ZERO) == Fee(0)`. In production this is normally blocked by `validate_resource_bounds` in `StatelessTransactionValidator::validate_resource_bounds`, but this check is explicitly disabled during "system bootstrap" via a config flag documented as `"It should be set to false during a system bootstrap"`: [5](#0-4) [6](#0-5) 

Once `validate_resource_bounds` is `false` (a config state intended only for the genesis bootstrap phase of a chain, but implemented as a persistent runtime toggle with no automatic re-enable and no block-height gate), **any subsequent user**, not just the genesis operator, can submit a declare transaction from the reserved BOOTSTRAP address to declare arbitrary Sierra classes with:
- No signature verification (`__validate_declare__` never runs),
- No fee payment,
- No nonce consumption (nonce remains `0` forever, so the bypass is repeatable for every new, not-yet-declared class hash).

The only mitigation is a "declare once" `prev_value = 0` check per class hash in the OS/`try_declare`, but this does not limit the number of *distinct* free declarations, nor gate the special address to genesis-only usage.

### Impact Explanation
This mirrors the reported bug class exactly: an unconfirmed/unapproved actor (here, any unprivileged transaction sender impersonating the reserved "BOOTSTRAP" identity) performs a privileged action — bypassing account validation and fee enforcement that gate all other Starknet transactions — because the guard is a pure data-pattern check rather than an actual authorization or lifecycle-state check. If a node operator's `validate_resource_bounds` flag remains `false` after genesis (there is no code path that automatically flips it back to `true` once bootstrapping completes), the sequencer allows:
- Unlimited free class declarations (bypassing Starknet's fee market entirely for the declare transaction type),
- Compiler/CPU resource consumption (Sierra→CASM compilation) with no fee cost, since declares still go through `declare_compilation_semaphore`/compilation before execution,
- A discrepancy between "confirmed, fee-paying, signed" declares and unauthorized zero-cost declares that any anonymous sender can inject, undermining the integrity/authorization model of the declare transaction type.

This satisfies "unauthorized account action" from the validation criteria (an action — contract class declaration and mempool/compiler resource consumption — performed without the authorization checks, i.e. signature validation, that normally gate it).

### Likelihood Explanation
Exploitability is conditional on the node/chain configuration: `validate_resource_bounds` must be `false`. The documentation explicitly frames this as a bootstrap-only setting, implying it is expected to be toggled by the operator, and the codebase provides no automatic protection (e.g., a check restricting `BOOTSTRAP` declares to block 0, or a hard block-height cutoff) once the flag is left enabled. This is analogous to the referenced Mastodon bug, where the vulnerable code path was likewise gated behind an opt-in flag (`EXPERIMENTAL_FEATURES=fasp`) that, if left enabled, permitted unapproved parties to invoke privileged actions. I could not fully verify, within the available context, whether there is a separate mechanism outside the files reviewed (e.g., in `apollo_batcher` or genesis-initialization code) that forcibly re-enables `validate_resource_bounds` after the first block or restricts the BOOTSTRAP declare mechanism to a specific initial block range — this should be confirmed before treating this as unconditionally exploitable in a production deployment.

### Recommendation
- Gate the BOOTSTRAP declare bypass (in both `blockifier` and the Starknet OS Cairo program) on an explicit, non-spoofable "bootstrap phase" indicator (e.g., current block number == 0, or a one-time flag cleared after genesis) rather than solely on transaction field values that any sender can produce.
- Ensure `validate_resource_bounds` (and any equivalent zero-fee acceptance path) cannot remain permanently disabled in production; consider making it block-height-scoped rather than a persistent boolean config, or add a hard-coded check that BOOTSTRAP declares are only accepted for block number 0.
- Add an explicit safeguard in `check_declare_permissions` / stateless validation to reject any declare transaction using the reserved `bootstrap_address()` outside of the genesis block, independent of the `validate_resource_bounds` and `authorized_declarer_accounts` settings.

### Proof of Concept
1. Configure (or leave misconfigured) a running sequencer with `validate_resource_bounds = false` and default `authorized_declarer_accounts = None` (post-genesis).
2. Craft an RPC `DeclareTransaction::V3` with:
   - `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`),
   - `nonce = 0`,
   - resource bounds such that `max_possible_fee(Tip::ZERO) == 0` (e.g., `AllResourceBounds::new_unlimited_gas_no_fee_enforcement()`, as used in `generate_bootstrap_declare()`, `crates/mempool_test_utils/src/starknet_api_test_utils.rs:585-595`),
   - Arbitrary/empty signature (unchecked because validate is skipped),
   - Any not-yet-declared Sierra class and matching `compiled_class_hash`.
3. Submit via `POST /add_transaction`. The gateway's `check_declare_permissions` passes (no allowlist configured), stateless validation passes (`validate_resource_bounds` disabled), and execution reaches `AccountTransaction::execute_raw`, which detects `is_bootstrap_declare == true` and declares the class without running `__validate_declare__` or charging any fee (`crates/blockifier/src/transaction/account_transaction.rs:899-911`).
4. Repeat with different classes indefinitely (nonce stays `0`), each time declaring a new class for free with no valid signature.

    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

        // - After the transaction is executed successfully, the batcher does not notify the mempool

        // - When the next block is produced, the mempool will propose the same transaction again.
