### Title
Nested `WithdrawFromGasKey` inside a `DelegateV2` action bypasses the pending-transaction-queue's gas-key balance accounting - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
The pending transaction queue enforces a "how much has this gas key already committed to spend in this uncertified window" constraint so that multiple in-flight (included-but-not-yet-certified) transactions signed by the same gas key cannot together overdraw its balance. This tracking only scans **top-level** actions of a transaction for `WithdrawFromGasKey`, exactly the kind of "the enforcement check is on the wrong/incomplete surface" bug described in the external report, where a delay/limit mechanism (`initiateWithdrawal` window) could be routed around via an alternate path (transferring to a second account) not covered by the same check.

### Finding Description
`PendingTxSession::check_pending` computes `paid_from_gas_key` by combining a snapshot of already-certified pending gas-key cost with a session-local `session_gas_key_withdrawals` map that is populated only by scanning the *outer* transaction's top-level actions: [1](#0-0) 

The struct-level documentation for `PendingTxSession` explicitly states that gas-key balance overspending is *not* covered by the ephemeral `TrieUpdate` the way ordinary balance/nonce checks are, and must be tracked separately by this session map: [2](#0-1) 

A `WithdrawFromGasKey` action nested inside a `Delegate`/`DelegateV2` meta-transaction is not a top-level action of the outer signed transaction, so `check_pending`'s scan (`for action in tx.transaction.actions()`) never sees it and never adds it to `session_gas_key_withdrawals`. This is confirmed directly by the protocol-version comment describing the very hole this class of nesting creates: [3](#0-2) 

nearcore does contain fixes for parts of this bug class — `RejectDelegateV2` disables `DelegateV2` from gas keys because the inner nonce update is invisible to the queue, and `RejectWithdrawFromGasKeyInDelegate` specifically rejects a `WithdrawFromGasKey` nested inside any delegate action, with a regression test that demonstrates the pre-fix behavior actually drains the gas key balance: [4](#0-3) [5](#0-4) 

This is the direct nearcore analog of the Collateral finding: a spending/withdrawal accounting mechanism that is supposed to bound how much value can move out of a locked balance during an uncertified/pending window can be routed through an alternate action path (nesting inside a delegate/meta-transaction) that the accounting logic does not scan, letting the same balance be spent more than once (double-withdrawal) before the runtime's authoritative check catches up — analogous to using a second account transfer to keep dodging the Collateral withdrawal window check.

### Impact Explanation
If `RejectWithdrawFromGasKeyInDelegate` were not active (e.g., on a node running just before this protocol-version gate, or if any other action nesting path exists that isn't covered by the fix), an attacker could submit several transactions in the same uncertified window, each nesting a `WithdrawFromGasKey` for the same gas key inside a delegate action. Because `check_pending`'s `session_gas_key_withdrawals` accounting never registers these nested withdrawals, the pending-transaction-queue admits all of them as if the gas key still had its full balance, and the runtime applies each `WithdrawFromGasKey` receipt independently (`runtime/runtime/src/access_keys.rs` `action_withdraw_from_gas_key`), each one moving balance from the gas key into the account. This lets a signer over-withdraw beyond the gas key's actual balance-enforcement intent during the uncertified window, i.e., unauthorized/duplicated value movement analogous to the Collateral double-withdrawal.

### Likelihood Explanation
On the current tip of this repo the mitigation (`RejectWithdrawFromGasKeyInDelegate`, alongside `RejectDelegateV2`) appears to already close this specific nested-withdraw path once the corresponding protocol version is active. The regression test in `reject_delegated_gas_key_withdraw.rs` demonstrates the exploit is real pre-upgrade and is closed post-upgrade. I was not able to fully verify within the available context whether `RejectWithdrawFromGasKeyInDelegate`/`RejectDelegateV2` are unconditionally active at the reported `STABLE_PROTOCOL_VERSION` for this build, nor whether any other nested-action surface (besides `Delegate`/`DelegateV2`) still bypasses `session_gas_key_withdrawals`. This residual uncertainty should be verified with a full read of `core/primitives-core/src/version.rs` feature-activation table and `runtime/runtime/src/action_validation.rs`.

### Recommendation
- Confirm `RejectWithdrawFromGasKeyInDelegate` and `RejectDelegateV2` are unconditionally enabled (not nightly-only) at the deployed/stable protocol version, with no fallback path.
- Audit all other ways an action list can be nested or composed (e.g., any future promise/meta-transaction batching, cross-shard receipt construction) to ensure `PendingTxSession::check_pending`'s scan of `tx.transaction.actions()` cannot be circumvented by wrapping a `WithdrawFromGasKey` (or any action whose effects are not otherwise covered by the ephemeral `TrieUpdate`) inside a container action.
- Consider making the pending-queue's session tracking recursive/structural (walking all nested actions of any depth) rather than enumerating only top-level actions, so newly introduced composite actions don't reopen this class of bug.

### Proof of Concept
Demonstrated directly by the existing repo regression test, which shows a nested `WithdrawFromGasKey` inside a delegate action draining the gas key's balance pre-upgrade: [6](#0-5)

/// Per-chunk-production session. Combines pending transaction queue state with session-local tracking
/// for constraints NOT handled by the ephemeral TrieUpdate.
///
/// The ephemeral TrieUpdate handles within-chunk accumulation for balance
/// (deducts cost), gas key balance (deducts gas_key_cost), and nonces
/// (advances after each accepted tx). The session only tracks what the
/// ephemeral state does NOT cover:
/// - P_MAX / deploy exclusivity counts (per account)
/// - WithdrawFromGasKey amounts (action effects not applied by ephemeral state)
///
/// The session holds an `Arc<Mutex<ShardedPendingTransactionQueue>>` and acquires the lock briefly
/// per transaction rather than holding it for the entire chunk production duration. This avoids
/// blocking block processing and RPC handlers.
pub struct PendingTxSession {
    pending_transaction_queue: Arc<Mutex<ShardedPendingTransactionQueue>>,
    shard_uid: ShardUId,
    session_access_key_tx_counts: HashMap<AccountId, usize>,
    session_deploy_tx_counts: HashMap<AccountId, usize>,
    session_gas_key_withdrawals: HashMap<GasKey, Balance>,
}
