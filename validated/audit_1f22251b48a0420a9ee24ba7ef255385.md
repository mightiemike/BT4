### Title
Missing declared-class/Cairo1 validation in Starknet OS `execute_replace_class` diverges from blockifier's `replace_class` check, enabling wrong committed state root - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The `ReplaceClass` syscall handler in the actual execution engine (`blockifier`) enforces that the target class hash is declared and is a Cairo1 class before allowing a contract to replace its own class. The Starknet OS Cairo implementation of the same syscall — used for re-execution/proving of the block — omits both checks (there is an explicit unresolved `TODO` acknowledging the missing declared-class check), and the deprecated Cairo0 syscall path has the identical gap. This creates a divergence between what the sequencer's blockifier actually permits/commits and what the OS will accept and prove.

### Finding Description
In `blockifier`, `replace_class` is gated by explicit validation: [1](#0-0) 

and for the deprecated (Cairo0) syscall path: [2](#0-1) 

Both paths call `get_compiled_class` (or an equivalent), which fails with `StateError::UndeclaredClassHash` if the class hash was never declared, and the Cairo1 path additionally rejects replacement to a Cairo0 (V0) class with `ForbiddenClassReplacement`.

In the Starknet OS Cairo program — which re-executes the block's transactions to produce the state-transition proof — the equivalent syscall implementation performs **no such check**: [3](#0-2) 

The comment at line 902 explicitly flags this gap as unresolved: `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.` The deprecated (Cairo0) OS syscall handler has the same unguarded behavior: [4](#0-3) 

This means the OS blindly writes the requested `class_hash` into `contract_state_changes` regardless of whether that class hash was ever declared or is a valid Cairo1 class — a check that is load-bearing in the actual execution engine used to build and commit the block.

### Impact Explanation
Any unprivileged contract can invoke `replace_class_syscall` with an arbitrary, undeclared (or Cairo0) class hash as part of its own execution. In `blockifier`, such a call causes the transaction to fail/revert (via `StateError::UndeclaredClassHash` or `ForbiddenClassReplacement`), so this state change is never part of the block's committed state root produced by the sequencer. However, because the Starknet OS's re-execution/proving path performs no equivalent validation, if the OS is given the same call to re-execute or to attempt to independently derive the state diff, it will silently accept the invalid class replacement, producing a state transition/root that differs from the one actually computed and committed by the sequencer's blockifier. This is a root-cause for honest-node/verifier divergence and a wrong committed state root, since the component responsible for proving state-transition correctness (the OS) does not enforce the same invariants as the component responsible for actually executing and committing the block (blockifier). Depending on how discrepancies between blockifier's committed diff and OS-recomputed diff are handled downstream (fact validation, re-execution tests, proving), this can manifest as unauthorized/incorrect state (a class hash change that should have been rejected) becoming part of a provable state transition, or a block that blockifier considers valid failing OS verification (or vice versa) — undermining the integrity guarantee between execution and proof.

### Likelihood Explanation
The divergent code paths are unconditionally reachable: any contract can call `replace_class` with attacker-chosen calldata (an arbitrary felt as `class_hash`), requiring no privileged role, no admin key, and no special network position — exactly the "single submitted transaction/contract call" reachability required. The bug is not theoretical: the missing check is explicitly marked with a `TODO` in the OS source, confirming it is a known, unresolved gap rather than a hypothetical omission.

### Recommendation
Add the same validation in the Starknet OS Cairo implementation of `execute_replace_class` (`syscall_impls.cairo`) and its deprecated counterpart (`deprecated_execute_syscalls.cairo`) that blockifier already performs in `syscall_base.rs::replace_class` and `hint_processor.rs::replace_class`: verify the target `class_hash` corresponds to a declared class (and, for the non-deprecated path, that it is a Cairo1 class) before writing the new `StateEntry`, mirroring the `ForbiddenClassReplacement`/`UndeclaredClassHash` semantics so that OS re-execution and blockifier execution stay consistent for every transaction.

### Proof of Concept
1. Deploy a contract exposing the `replace_class_syscall`.
2. Submit an invoke transaction that calls `replace_class_syscall(class_hash)` with a `class_hash` that has never been declared (or, for the Cairo1 path, one of a declared Cairo0 class).
3. In `blockifier`, this fails: `syscall_base.rs::replace_class` (lines 369-378) calls `self.state.get_compiled_class(class_hash)?`, which raises `StateError::UndeclaredClassHash`, causing the transaction to revert and be excluded from the committed state diff.
4. If the same call is fed to the Starknet OS's `execute_replace_class` (`syscall_impls.cairo`, lines 881-920), no equivalent check exists — the class hash is written directly into `contract_state_changes` (lines 906-914) — so the OS accepts and represents a state transition that the sequencer's own execution engine would have rejected, producing divergent state roots between the two components.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
