Confirmed: there is no test in `token-exchange.test.ts` exercising a `shop` value that diverges from `sessionToken`'s `dest` claim, and all official framework callers (`shopify-app-remix`, `shopify-app-react-router`, `shopify-app-express`) derive `shop` from the token's own decoded `dest` before calling `tokenExchange`. That means the divergence can only be introduced by a direct/custom caller of the underlying `@shopify/shopify-api` `shopify.auth.tokenExchange()` API — which is a supported, documented public entry point.

### Title
Token exchange does not bind the verified session token to the `shop` used to request/tag the access token - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
`tokenExchange()` decodes and cryptographically verifies the caller-supplied `sessionToken`, but immediately discards the verified payload and instead uses a caller-supplied, unrelated `shop` string to build the request to Shopify's `/admin/oauth/access_token` endpoint and to tag/create the resulting `Session`. The value that was actually authenticated (the token's `dest`/shop claim) is never cross-checked against the value that is actually used for the security-sensitive operation.

### Finding Description
In `tokenExchange` [1](#0-0) , the flow is:
1. `await decodeSessionToken(config)(sessionToken)` verifies the JWT signature/expiry and returns a `payload` object containing `dest` (the shop the token was actually issued for) — but the return value is discarded (not assigned to anything).
2. `const cleanShop = sanitizeShop(config)(shop, true)!` sanitizes a completely separate, caller-supplied `shop` argument.
3. The exchange request is sent to `https://${cleanShop}/admin/oauth/access_token` with `subject_token: sessionToken`, and the resulting `Session` is created with `shop: cleanShop` [2](#0-1) .

This is structurally the same root cause as the reported bug class: a value that is validated once (payload.dest, analogous to `payoutToken.decimals()` at mint time) is not cached/enforced for the subsequent sensitive use, and a different, attacker/caller-controllable value (`shop`, analogous to the re-fetched `decimals()` at exercise time) is trusted instead for the actual state-changing operation.

The official wrapper packages avoid triggering this because they always derive `shop` from the same decoded token (`new URL(payload.dest).hostname`) before calling `tokenExchange` — see `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts` lines 66-67 and the remix/react-router `getSessionTokenContext`/`validateSessionToken` flow, which extracts `shop` from `payload.dest` after validation [3](#0-2) . But `shopify.auth.tokenExchange` is exported as a standalone, documented public API [4](#0-3) , and nothing inside the library itself enforces that `shop` matches the token's `dest`.

### Impact Explanation
If any app built directly on `@shopify/shopify-api` (bypassing the shopify-app-remix/express/react-router wrappers, or building a custom integration) passes a `shop` value from a source that is independent of the session token (e.g., a query parameter, a different session, or another tenant's stored shop), the library will happily exchange the caller's valid session token against a `shop` domain that does not correspond to the token, and persist a `Session` object keyed to that mismatched shop/token pair. Depending on how the consuming app keys its session storage, this can lead to cross-tenant session/token confusion — a session record for shop B built using an OfflineAccessToken/OnlineAccessToken request whose `subject_token` actually belongs to shop A.

### Likelihood Explanation
Likelihood is limited by the fact that the documented and shipped framework adapters (remix, react-router, express) always derive `shop` from the verified token before calling this function, so a standard shopify-app-js-based app is not exploitable through this path today. The exposure exists specifically for the library's public `tokenExchange` API when used directly by custom consumers who pass `shop` from an untrusted or session-independent source, which is a real but narrower reachable surface than the officially blessed flows.

### Recommendation
Have `tokenExchange` use the shop derived from the verified `sessionToken.dest` claim (as the wrapper packages already do) rather than trusting/accepting a separately supplied `shop` argument, or, if a `shop` parameter must remain part of the public API for backward compatibility, validate that `sanitizeShop(shop)` equals the hostname of the decoded payload's `dest` and throw `InvalidJwtError`/`InvalidOAuthError` on mismatch before making the exchange request.

### Proof of Concept
1. Obtain a valid, unexpired session token for `shop-a.myshopify.com` (e.g., via App Bridge for a merchant using the app).
2. Call `shopify.auth.tokenExchange({ shop: 'shop-b.myshopify.com', sessionToken, requestedTokenType })` directly against the `@shopify/shopify-api` library (bypassing the remix/express/react-router wrappers).
3. Observe that `decodeSessionToken` succeeds (the token is valid), and the library proceeds to POST `subject_token=sessionToken` to `https://shop-b.myshopify.com/admin/oauth/access_token`, then returns/persists a `Session` with `shop: 'shop-b.myshopify.com'` — despite the token never having attested to `shop-b`.
