## Title
Stale TSS-address balance snapshot in fund migration permanently strands native funds sent to the old key after signing - (File: `universalClient/chains/evm/tx_builder.go`)

### Summary
`x/utss`'s fund-migration flow sweeps the *entire native balance* of the old TSS-controlled address to the new TSS address by querying the balance once and hard-coding the resulting transfer amount (`TSSFundMigrationAmount`) into the signing request. `BroadcastFundMigrationTx` explicitly refuses to re-query the balance at broadcast time. This is the same "stale accounting checkpoint" bug class as Sherlock M-9: an on-chain/off-chain component snapshots a balance, uses it to move/settle funds, and any value that arrives at that address after the snapshot but before the sweep is not accounted for and is stranded, since the address is deprecated once migration completes.

### Finding Description
`GetFundMigrationSigningRequest` in `universalClient/chains/evm/tx_builder.go` (lines 477-538) queries `tb.rpcClient.GetBalance(ctx, fromAddr)` for the old TSS address (unless a `claimedAmount` override is supplied) and computes `maxTransfer = balance - gasCost - l1GasFee` via `computeFundMigrationTransfer` [1](#0-0) . This `maxTransfer` is baked into `TSSFundMigrationAmount` and is deliberately **never re-derived**: `BroadcastFundMigrationTx`'s own comment states "Uses `req.TSSFundMigrationAmount` fixed at signing time — do not re-query balance" [2](#0-1) .

The safety argument documented in the code is: "Fund migration only triggers when outbound is disabled and no pending outbounds remain, so the balance at signing time will equal the balance at broadcast time" [3](#0-2) . That reasoning only covers *protocol-driven* outbound flows guarded by `IsChainOutboundEnabled` / `HasPendingOutboundsForChain` in `InitiateFundMigration` [4](#0-3) . It does **not** cover the trivial unprivileged case: the old TSS address is a plain externally-owned account on the external EVM chain, and anyone can send native currency to it directly (e.g., a normal wallet-to-wallet transfer, unrelated to any Push Chain inbound/outbound message). Any such transfer that lands on the old TSS address after the balance is queried for signing, but before/at the sweep broadcast, increases the actual on-chain balance beyond `maxTransfer`. Since `maxTransfer` is fixed and never revisited, that residual amount is left behind at an address that, once migration completes, is no longer part of any tracked "current" TSS key and has no automatic mechanism to be swept again.

This mirrors the `claimFees`/`_accumulateExternalRewards` pattern in the referenced report exactly: a "last known balance" is captured, an external, permissionless deposit arrives in the gap, and the subsequent state-mutating operation (claimFees / broadcast sweep) commits using the stale value, silently leaving the delta unaccounted for.

### Impact Explanation
Funds sent to the deprecated old TSS address after the migration's balance snapshot are not swept to the new TSS key and become inaccessible through the normal fund-migration path. Because the old key is retired from `CurrentTssKey` once migration for that chain finalizes, no future protocol flow automatically revisits that address's balance. Recovery, if possible at all, requires an admin to manually notice the stray balance and call `MsgInitiateFundMigration` again for the same `(old_key_id, chain)` pair (the duplicate check in `InitiateFundMigration` only blocks a currently-*pending* migration, not a completed one) — i.e., the funds are DoS'd/frozen until a privileged operator intervenes, exactly the "medium" impact class accepted in the referenced Sherlock report (not silently lost forever, but locked and requiring manual rescue). This affects protocol/TSS-controlled operational funds (the gas float used to pay for outbound broadcasts on that chain), which if drained to zero due to a mis-swept amount could also degrade the chain's ability to pay for subsequent outbound transactions.

### Likelihood Explanation
Triggering the root cause requires no privilege: any external actor (or even an honest user by accident) can send native currency to a known, publicly-derivable TSS address on the external chain at any time, including in the narrow window between `InitiateFundMigration` being observed off-chain and the sweep transaction being signed/broadcast by the Universal Validators. Because `KEYGEN`-driven fund migrations happen for every connected external chain whenever the TSS key rotates, and the old address remains a valid, funded EOA right up until the sweep confirms, the race window exists on every migration. However, exploiting it for material gain (rather than simply causing a small dust freeze) is limited to the amount an attacker is willing to donate, so this is more of a reliability/dust issue than a high-value drain, which lowers overall likelihood of large-scale exploitation while still constituting a real, reachable invariant violation.

### Recommendation
Re-query the old TSS address's balance immediately before broadcast (or add a follow-up "sweep leftover" step keyed off the *current* balance rather than the *signing-time* balance), and/or keep the `FundMigration` record queryable/re-triggerable indefinitely with an automated or validator-initiated retry for any residual balance detected on the old key's address after the first sweep completes, rather than relying purely on manual admin re-initiation.

### Proof of Concept
1. Admin disables outbound for chain X and calls `MsgInitiateFundMigration` for the old TSS key.
2. Universal Validators build the fund-migration signing request: `GetFundMigrationSigningRequest` reads the old TSS address's current balance `B` and fixes `maxTransfer = B - gasCost` into `TSSFundMigrationAmount`.
3. Before the TSS signature round finishes and the sweep transaction is broadcast, an unprivileged external actor sends `X` additional native tokens directly to the old TSS address on chain X (a plain transfer, unrelated to any Push Chain message).
4. `BroadcastFundMigrationTx` broadcasts the transaction using the pre-fixed `TSSFundMigrationAmount` (comment: "do not re-query balance"), sweeping only `B - gasCost`, leaving `X` tokens behind at the old address.
5. `VoteFundMigration` finalizes the migration as `COMPLETED`; `CurrentTssKey` no longer points to the old key. The `X` tokens sitting at the old TSS address are now stuck with no automatic path back into protocol accounting, requiring a manual admin-initiated re-migration to recover — a class-M denial-of-fund-access consistent with the referenced report's accepted impact.

```go
// BroadcastFundMigrationTx assembles and broadcasts a signed fund migration transaction.
// Uses req.TSSFundMigrationAmount fixed at signing time — do not re-query balance.
func (tb *TxBuilder) BroadcastFundMigrationTx(ctx context.Context, req *common.UnsignedSigningReq, data *common.FundMigrationData, signature []byte) (string, error) {
	if len(signature) != 65 {
		return "", fmt.Errorf("signature must be 65 bytes [r(32)|s(32)|v(1)], got %d", len(signature))
	}

	if data.GasPrice == nil || data.GasPrice.Sign() == 0 {
		return "", fmt.Errorf("gas price must be provided for fund migration")
	}
	if data.GasLimit == 0 {
		return "", fmt.Errorf("gas limit must be provided for fund migration")
	}

	// Use the exact amount fixed at signing time. Re-querying balance here would race
	// with a successful broadcast from another validator (balance goes to 0 post-sweep).
	if req.TSSFundMigrationAmount == nil || req.TSSFundMigrationAmount.Sign() <= 0 {
		return "", fmt.Errorf("req.TSSFundMigrationAmount must be set for fund migration broadcast")
	}
```

```go
// computeFundMigrationTransfer returns the native amount to sweep from the old
// TSS address to the new one: balance - (gasPrice * gasLimit) - l1GasFee.
// The l1GasFee covers OP-stack sequencer data-availability charges (0 for
// non-L2 chains). All validators must compute the same value — any drift
// here breaks the TSS signing hash.
func computeFundMigrationTransfer(balance, gasPrice *big.Int, gasLimit uint64, l1GasFee *big.Int) (*big.Int, error) {
	gasCost := new(big.Int).Mul(gasPrice, new(big.Int).SetUint64(gasLimit))
	totalFee := new(big.Int).Set(gasCost)
	if l1GasFee != nil && l1GasFee.Sign() > 0 {
		totalFee.Add(totalFee, l1GasFee)
	}
	maxTransfer := new(big.Int).Sub(balance, totalFee)
	if maxTransfer.Sign() <= 0 {
		return nil, fmt.Errorf("insufficient balance for gas: balance=%s gasCost=%s l1GasFee=%s",
			balance.String(), gasCost.String(), l1GasFeeString(l1GasFee))
	}
	return maxTransfer, nil
}
```
