## Analysis: Analog Found

The reported bug class—exponential/power-function math in a market pricing curve breaking down under extreme (but reachable) input ratios, causing either reverts or corrupted output—has a concrete analog in java-tron's legacy Bancor-style exchange math.

### Title
Unguarded floating-point power math in `ExchangeProcessor` allows overflow/`Infinity` corruption of exchange balances - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute Bancor-curve trades using raw `double` arithmetic and `Math.pow` with a fixed large exponent (`2000.0`), exactly the same class of "exponential math that breaks past a reachable input range" as the VRGDAC `xToY`/`yToX` bug in the external report. This is the default path used by `ExchangeTransactionActuator` and `ExchangeInjectActuator` unless a governance-gated hardening flag is enabled.

### Finding Description
`ExchangeCapsule.transaction` selects the processor based on `hardenedCalc` (the `allowHarden()` flag), defaulting to the unguarded `ExchangeProcessor` when the corresponding chain parameter/proposal (`AllowHardenExchangeCalculation`) has not been activated: [1](#0-0) 

`ExchangeProcessor` performs the trade using unchecked `double` math: [2](#0-1) 

`exchangeFromSupply` raises `1 + supplyQuant/supply` to the power `2000.0`. As `supplyQuant` (the "relay" minted from the sell side) approaches a large enough fraction of `supply` (1e18 baseline), the base of the power exceeds roughly `1.42`, at which point `Math.pow(base, 2000)` exceeds `Double.MAX_VALUE` and returns `Double.POSITIVE_INFINITY`. The subsequent cast `(long) exchangeBalance` on an `Infinity`-derived value in Java silently truncates to `Long.MAX_VALUE` rather than throwing — unlike the Solidity revert in the original report, this path does not fail safely; it produces a bogus, attacker-favorable result.

This exact defect was independently identified and is exercised by the project's own test suite, which demonstrates that `ExchangeProcessor` (`useStrictMath=true` or `false`) produces different/incorrect results compared to the fixed `SafeExchangeProcessor` (which uses `BigDecimal` with `longValueExact()` to force a hard failure instead of silent corruption): [3](#0-2) 

The safe/hardened replacement exists specifically to close this precision/overflow gap: [4](#0-3) 

### Impact Explanation
Any account can broadcast an `ExchangeTransactionContract` or `ExchangeInjectContract` and reach this code path directly: [5](#0-4) 

When the pow-overflow condition is hit, `buyTokenQuant`/`anotherTokenQuant` can become a corrupted (e.g., `Long.MAX_VALUE`-adjacent) value that is then used to update on-chain pool balances and credit the trader's account balance: [6](#0-5) 

This is an accounting-corruption / asset-drain risk on the unhardened (default) code path, matching the "exchange/market math" category — it is the direct java-tron analog of the external report's exponential-math breakdown, except that instead of a permanent revert it manifests as silently wrong (attacker-favorable) trade output because Java's numeric cast from `Infinity`/`NaN` does not throw.

### Likelihood Explanation
Reaching the vulnerable region requires the relay amount to become a large fraction of the fixed `1_000_000_000_000_000_000L` supply constant in a single trade; this in turn requires a sell quantity that is a large fraction of the pool balance, which is possible for smaller/newer exchange pools or once `getExchangeBalanceLimit()` governance parameter allows sufficiently large pools/trades, and is entirely under attacker control (no privileged access needed, only funds and one transaction). Since hardening (`AllowHardenExchangeCalculation`) is a governance-gated flag rather than the default, the vulnerable path is reachable on any deployment where that proposal hasn't been passed.

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal-based, exact arithmetic with hard failure on overflow) the unconditional implementation for `ExchangeCapsule.transaction`, removing the legacy `ExchangeProcessor` double-math path entirely rather than gating the fix behind an opt-in governance proposal.

### Proof of Concept
Not independently reproduced with a runnable test in this analysis; the reasoning is derived from static review of `ExchangeProcessor.exchangeFromSupply`'s `Math.pow(base, 2000.0)` combined with Java's non-throwing narrowing cast of `Infinity` to `long`, and corroborated by the existing `ExchangeProcessorTest.testStrictMath` divergence test between `ExchangeProcessor` and `SafeExchangeProcessor`.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
