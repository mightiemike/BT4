**Analysis:** The code path in question — `vote_processor::is_vote_authorize_with_bls_enabled` gating `VoteInstruction::Authorize(_, VoteAuthorize::VoterWithBLS(args))` — routes into `vote_state::authorize` [1](#0-0) , which unconditionally calls `verify_bls_proof_of_possession` before installing the new BLS pubkey. That function requires a proof-of-possession signature that cryptographically binds the claimed BLS public key to the specific vote account pubkey (message = `"ALPENGLOW" || vote_account_pubkey`), verified via genuine BLS signature verification: [2](#0-1) .

Since BLS signatures cannot be forged without the corresponding private key, an attacker cannot produce a valid `bls_proof_of_possession` for a BLS pubkey they do not control — this is confirmed by unit tests covering exactly the attacker's described exploit idea: reusing someone else's BLS pubkey/PoP [3](#0-2) , garbage/zero PoP bytes, and PoP bound to a different vote account, all of which are rejected with `InstructionError::InvalidArgument` [4](#0-3) .

The `is_vote_authorize_with_bls_enabled` boolean only gates whether the `VoterWithBLS` instruction variant is accepted at all (feature-gate check), not whether the cryptographic proof-of-possession check is bypassed — that check runs unconditionally whenever the `VoterWithBLS` branch executes [1](#0-0) . Timing the transaction to land in the slot where the feature activates does not change this: the feature bool only toggles between "reject instruction" and "run authorize with mandatory PoP verification" — there is no code path where the PoP check is skipped. Thus the invariant "BLS voter authorization requires proof of the corresponding key" is enforced at the cryptographic level and cannot be broken by transaction crafting alone.
