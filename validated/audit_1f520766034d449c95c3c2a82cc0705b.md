## Finding: Non-atomic cross-lock read yields position/state version skew in `get_pre_committed_ledger_summary`

### Summary
`get_pre_committed_ledger_summary` in `storage/aptosdb/src/db/aptosdb_reader.rs` builds a `LedgerSummary` whose `state`/`state_summary` fields and `position_state_summary` field are read from **two independent mutexes without any coordinating lock or version check**, and the resulting struct is constructed via a raw struct literal that bypasses the version-consistency assertion that `LedgerSummary::new` otherwise enforces.

### Finding Description
`LedgerSummary` is documented/designed so that `state`, `state_summary`, and (implicitly) `position_state_summary` must correspond to the same ledger version. The normal constructor enforces this for `state`/`state_summary`: [1](#0-0) 

However, `get_pre_committed_ledger_summary` never calls this constructor. It instead:
1. Reads `state`/`state_summary` atomically from `self.state_store.current_state_locked()`.
2. Separately reads the native-position tip from a *different* lock: `store.current_state().lock().clone()`.
3. Assembles a `LedgerSummary` with a raw struct literal, skipping `assert_versions_match` entirely. [2](#0-1) 

Because steps 1 and 2 lock and clone two unrelated mutexes with no shared critical section, a commit that advances the main state store and a commit that advances the native-position store (via independent write paths, e.g. `execution/executor/src/chunk_executor/chunk_commit_queue.rs` and `execution/executor/src/workflow/do_state_checkpoint.rs`, which separately update `position_state_summary`) can interleave between the two reads. The resulting `LedgerSummary.position_state_summary` can therefore be bound to a different ledger version than `LedgerSummary.state`/`state_summary`, even though nothing downstream re-validates version alignment before consuming the struct (e.g., to seed the executor's reset root block).

### Impact Explanation
If `position_state_summary` is skewed relative to `state`/`state_summary`, any subsequent execution or proof-construction step that treats `LedgerSummary` as a version-aligned snapshot (as its own constructor's `assert_versions_match` implies it should be) is operating on a torn/incoherent view. Depending on how the consuming code (block-tree reset, chunk commit queue reconciliation) uses this without its own re-validation, this can lead to native-position roots being merged into or compared against the wrong main-state version, corrupting the derived commitment root for that subsystem.

### Likelihood Explanation
I could not fully confirm, within the available iterations, whether the downstream consumers (`execution/executor/src/chunk_executor/chunk_commit_queue.rs`, `execution/executor/src/workflow/do_state_checkpoint.rs`, `execution/executor/src/types/partial_state_compute_result.rs`) perform their own version-consistency check on `position_state_summary` before use, which would determine whether this race is merely latent (caught by an assertion/panic) or silently propagates a mismatched root. I also could not confirm whether the native-position/"trading native" subsystem (gated behind `ENABLE_TRADING_NATIVE` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is active on mainnet or is still an experimental/opt-in feature, which materially affects whether this qualifies under the review's mainnet-impact standard.

### Recommendation
- Construct `LedgerSummary` in `get_pre_committed_ledger_summary` through a path that validates (or explicitly documents an exception for) version alignment between `position_state_summary` and `state`, rather than bypassing `assert_versions_match`.
- Ensure both reads occur under a single atomic snapshot boundary (e.g., a shared epoch/version token, or take both locks and re-check versions before returning) so the returned `LedgerSummary` is a coherent point-in-time view.
- Audit all consumers of `LedgerSummary.position_state_summary` to confirm they either re-validate version alignment or are provably unaffected by transient skew.

### Proof of Concept
Not independently reproduced. The described race requires: (1) a workload that produces near-simultaneous commits to the main state store and the native-position store, and (2) an `AptosDB` built with native-position support enabled, then calling `get_pre_committed_ledger_summary` concurrently with those commits and asserting `position_state_summary`'s internal version equals `state.next_version() - 1`. I was unable to execute this scenario or trace the full downstream consumption to confirm end-to-end impact within the tool-call budget available. [2](#0-1) [3](#0-2)

    fn get_pre_committed_ledger_summary(&self) -> Result<LedgerSummary> {
        gauged_api("get_pre_committed_ledger_summary", || {
            let (state, state_summary) = self
                .state_store
                .current_state_locked()
                .to_state_and_summary();
            let num_txns = state.next_version();

            let frozen_subtrees = self
                .ledger_db
                .transaction_accumulator_db()
                .get_frozen_subtree_hashes(num_txns)?;
            let transaction_accumulator =
                Arc::new(InMemoryAccumulator::new(frozen_subtrees, num_txns)?);
            // Pre-committed position tip, so the executor's reset root block can
            // seed from it (None when position is disabled).
            let position_state_summary = self
                .position
                .as_ref()
                .and_then(|bundle| bundle.state_store.as_ref())
                .map(|store| store.current_state().lock().clone());
            Ok(LedgerSummary {
                state,
                state_summary,
                transaction_accumulator,
                position_state_summary,
            })
        })
    }
