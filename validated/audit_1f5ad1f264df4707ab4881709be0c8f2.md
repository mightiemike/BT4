## Analysis Result

This is a valid analog. The Witch.sol root cause (an unvalidated payout-recipient address that can be set to a value guaranteed to make the payout transaction revert, permanently blocking finalization) maps directly onto `RevertInstructions.FundRecipient` on Push Chain's outbound path.

### Title
Attacker-controlled `RevertInstructions.FundRecipient` with no address validation lets a user permanently strand their own bridged funds in `ABORTED` state - (File: `x/uexecutor/keeper/outbound.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
`event.RevertRecipient` from the on-chain `UniversalGatewayPC` withdraw event is copied verbatim into `OutboundTx.RevertInstructions.FundRecipient` with no address-format or non-zero validation, unlike the mandatory validation applied to `Inbound.Recipient` in `ValidateForExecution`.

### Finding Description
When building an outbound from a user-originated PC transaction, `BuildOutboundsFromReceipt` sets: [1](#0-0) 
directly from `event.RevertRecipient`, an arbitrary string supplied by the caller of the gateway contract (an unprivileged EOA/UEA-driven user transaction). There is no `IsValidAddress` check on this field anywhere in `x/uexecutor/types/inbound.go`'s `ValidateForExecution`, nor in `create_outbound.go` or `outbound.go`.

If the destination-chain outbound later fails (attacker can construct a payload/gas configuration that legitimately fails on the destination chain, or simply observe a natural failure), `handleFailedOutbound` re-mints the bridged PRC20 to this attacker-chosen recipient: [2](#0-1) 
`common.HexToAddress(recipient)` silently converts an empty or malformed string to `0x000...000` rather than erroring. If the PRC20 token's mint/transfer implementation reverts on transfers to the zero address (standard OpenZeppelin ERC20 behavior, as flagged in the original Witch.sol report), `CallPRC20Deposit` will always fail for this outbound, and the code takes the "un-liquidatable" path: [3](#0-2) 
which calls `AbortOutbound`, permanently freezing the outbound in `Status_ABORTED` "for manual intervention": [4](#0-3) 
The same unvalidated-recipient pattern also appears in `applyGasRefund`'s fallback deposit path and in `buildRevertOutbound` / rescue-outbound recipient selection, all of which trust `RevertInstructions.FundRecipient` without validating it is a well-formed, non-zero address: [5](#0-4) [6](#0-5) 

### Impact Explanation
This does not let an attacker steal or freeze *other* users' funds — the invariant it breaks is narrower than the original Witch.sol case: it lets a user (or a contract they craft) attach an unpayable `FundRecipient` to their own bridge transaction so that any later revert/refund path targeting that recipient permanently gets stuck as `ABORTED`, matching the in-scope impact category "permanent freezing... of user or protocol-controlled funds." It also creates operational burden: every `ABORTED` outbound requires manual/governance intervention, and while `ABORTED` funds are not literally lost (the PRC20 mint simply never succeeds), the bridged value is inaccessible through the normal automated flow indefinitely.

### Likelihood Explanation
Reachable via a fully unprivileged, ordinary user transaction: any caller of `UniversalGatewayPC`'s withdraw/outbound function can set the revert-recipient field to `address(0)` or any other address on an ERC20-like PRC20 whose `_mint`/transfer path reverts on the zero address. No validator or admin collusion is required, and the only extra condition is that the *outbound itself* fails on the destination chain (attacker-inducible via a gas limit set too low, or an intentionally-reverting destination-chain call, both of which the attacker fully controls in their own transaction).

### Recommendation
Validate `RevertInstructions.FundRecipient` (and the `Recipient`/`Sender` fallback fields used in refund and revert paths) with the same `utils.IsValidAddress(..., utils.HEX)` check already used for `Inbound.Recipient` in `ValidateForExecution`, rejecting empty/zero/malformed addresses at admission time in `BuildOutboundsFromReceipt`, `buildRevertOutbound`, and `applyGasRefund`, rather than allowing `common.HexToAddress` to silently coerce bad input into the zero address and only surfacing the failure as an unrecoverable `ABORTED` state later.

### Proof of Concept
1. Attacker calls `UniversalGatewayPC`'s withdraw/bridge-out function on Push Chain, setting the gateway event's `revertRecipient` field to `address(0)` (or any address on a token that reverts transfers-to-zero) and a payload/gas configuration on the destination chain that will predictably fail (e.g., insufficient `gasLimit`).
2. `BuildOutboundsFromReceipt` creates an `OutboundTx` with `RevertInstructions.FundRecipient = "0x0000...0000"` unchecked [1](#0-0) .
3. Universal Validators observe and vote the outbound as failed via `MsgVoteOutbound`, driving `FinalizeOutbound` → `handleFailedOutbound`.
4. `CallPRC20Deposit(ctx, prc20, common.HexToAddress(""/"0x0"), amount)` reverts because the token forbids minting/transferring to the zero address.
5. `AbortOutbound` marks the outbound `Status_ABORTED` permanently [3](#0-2) , and it is removed from `PendingOutbounds`, leaving the bridged value stuck with no automated recovery path.

Note: I could not fully confirm within the indexed context whether the specific PRC20 implementation used on Push Chain actually reverts on mint/transfer-to-zero-address (this depends on the Solidity `PRC20`/`UniversalCore` contracts, which were not present in the indexed Go repository content). This assumption is carried over directly from the original Witch.sol report's stated OpenZeppelin default behavior; if Push Chain's PRC20 contracts instead silently accept zero-address transfers, the "un-liquidatable/ABORTED" impact described here would not trigger, though the missing input validation itself remains a code-quality/defense-in-depth gap. I'd recommend confirming the PRC20 contract behavior directly (e.g., via a Devin session with full repo/contract access) before treating this as fully confirmed.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}
