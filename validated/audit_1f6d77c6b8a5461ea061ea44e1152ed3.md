### Title
Relayer fee refund is paid out unconditionally in `inner_rlp_execute`, before the underlying action's success is known - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In `near-wallet-contract`, `inner_rlp_execute` dispatches a `promise_batch_action_transfer` paying the relayer's fee for emulated base-token/ERC-20 transfers *before* the promise carrying out the actual user-requested action has resolved, and never checks that either promise succeeded before/relative to the other. This mirrors the reported bug class ("unchecked return value" causing the caller to be unaware whether a value-moving call actually completed) - here the relayer is paid regardless of whether the emulated transfer the fee was meant to compensate for ultimately succeeds.

### Finding Description
`inner_rlp_execute` parses the RLP-encoded Ethereum-style transaction into a `TransactionKind`. For `EOABaseTokenTransfer`/`ERC20Transfer` with a non-zero `fee`, it immediately fires a fire-and-forget transfer to the relayer: [1](#0-0) 

This refund promise is created and dispatched independently of, and prior to resolution of, the promise chain that actually performs the requested action (`action_to_promise(...).then(ext.rlp_execute_callback(...))`), which is only built afterwards: [2](#0-1) 

Neither promise's result feeds into the other: the fee-transfer promise's success/failure is never observed by the contract (no `.then()` callback attached to it, unlike every other cross-contract call in this file which is routed through `rlp_execute_callback`), and the main action promise's eventual `PromiseResult::Failed` in `rlp_execute_callback` only triggers a refund of the *external caller's attached deposit* (`caller_deposit`), not of the fee already paid to the relayer: [3](#0-2) 

So there is no code path that ties the relayer fee payment to successful completion of the action it is meant to reimburse gas for, and no check (return-value or callback) verifying that the fee-transfer promise itself succeeded.

### Impact Explanation
Because the fee-paying transfer to the relayer is unconditionally submitted and its outcome is never checked against the outcome of the main action:
- A relayer receives payment for gas/service even when the eth-emulated action it relayed subsequently fails (e.g., the target `FunctionCall`/`Transfer` action reverts or the receiving account doesn't exist), so the wallet's balance is drained for a service that was not rendered - a real, repeatable value movement out of the wallet contract that is not reversed/accounted for symmetrically the way the `caller_deposit` refund is.
- Nonce handling in the same function explicitly increments the nonce for these transaction kinds before the fee refund is fired and before the outcome of the main action is known, so this is not a transient/edge state - it is the intended common path for every fee-bearing emulated transfer.

This results in unauthorized value movement from the wallet-contract's balance whenever the paid-for action fails, which the user (the account owner who authorized only a fee for a *successful* relay) did not consent to.

### Likelihood Explanation
Any signer of an RLP-encoded transaction routed through `rlp_execute` with a non-zero relayer `fee` on an `EOABaseTokenTransfer` or `ERC20Transfer` triggers this code path. Causing the underlying action to fail is straightforward and fully attacker/relayer-controllable (e.g., target account doesn't exist, ERC-20 contract rejects the transfer, insufficient balance in a race, or a malicious/careless relayer submitting a transaction destined to fail while still collecting the fee). No privileged access is required - this is reachable from an ordinary transaction/RPC call into the Wallet Contract.

### Recommendation
Chain the relayer fee-refund transfer to the outcome of the main action, e.g., dispatch it only after `rlp_execute_callback` observes `PromiseResult::Successful`, or make the fee-payment promise itself part of the same promise chain (`.then(...)`) so its success can be checked and rolled back/withheld if the primary action fails. At minimum, attach a callback that verifies the fee-transfer succeeded and reconciles fee payment with the transfer/ERC-20 action's actual result, analogous to adding a `require`/`safeTransfer`-style check for the underlying `IWETH.transfer` in the original report.

### Proof of Concept
1. Deploy a Wallet Contract instance for some eth-implicit account with a non-zero NEAR balance.
2. Have the account owner sign (or a relayer submit) an RLP transaction with `EthEmulationKind::EOABaseTokenTransfer { fee: NonZero, .. }` targeting an account/action guaranteed to fail post-fee-dispatch (e.g., target a `FunctionCall` receiver that does not implement the called method, or an `ERC20Transfer` to an unregistered/blocked receiver where `storage_deposit`+`ft_transfer` chain ultimately reverts).
3. Call `wallet_contract.rlp_execute(target, tx_bytes_b64)` from the relayer account.
4. Observe: `inner_rlp_execute` fires the fee transfer to the relayer immediately per [4](#0-3) , then the main action promise fails, and `rlp_execute_callback` returns `success: false` while only refunding the *caller's* `caller_deposit`, not the relayer fee.
5. Compare relayer's balance before/after: it will have increased by `fee` despite `ExecuteResponse.success == false`, confirming the fee was paid for a failed action with no check tying its outcome to the action outcome.
