### Title
`TransactionOutput::ensure_match_transaction_info` skips state-checkpoint hash verification, letting replay-verify accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by the `replay-verify`/`replay_on_archive` tooling to confirm that locally re-executed transactions match the authenticated `TransactionInfo` from an archive/backup, does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. Only `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash` are compared. A divergence in the locally computed world-state root (Sparse Merkle Tree / JMT root, hot-state root, or position-state root) from the archived, authenticated value will pass verification silently.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  is the sole comparator used to validate a freshly executed `TransactionOutput` against a trusted, previously committed `TransactionInfo`. It checks execution status, gas used, the write-set hash against `state_change_hash`, and the event root hash — but the code contains an explicit acknowledgment that the state-checkpoint-related hashes are not verified: [2](#0-1) 

`state_checkpoint_hash` is the periodic Sparse Merkle Tree root summarizing the entire world state (distinct from `state_change_hash`, which is only the hash of the transaction's own write set delta), and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are newer checkpoint roots defined on `TransactionInfoV1` [3](#0-2) . Because the write-set hash can match while the *materialized* state (built by applying that write set on top of prior state, hot-state promotion, or trading-native position state) diverges, a bug in state-application logic, JMT/SMT update code, or the newer hot-state/position-state computation would not be caught by this comparator.

The only current caller of this function is `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` against the archived, ledger-info-authenticated `TransactionInfo`: [4](#0-3) .

### Impact Explanation
This is the primary tool used to detect state-commitment divergence when replaying historical (or hard-forked) chain data against a candidate execution engine/build — precisely the "replay/restore/proof-verification" integrity surface called out in scope. Because the state-checkpoint hash (the actual authenticated world-state root) is never compared, `replay-verify` can report "success" even when the locally computed world state diverges from the real, on-chain committed state. This defeats the purpose of the tool for its main use case: catching state-root divergence introduced by consensus-affecting bugs, hard-fork mismatches, or new-feature rollouts (hot state, "trading-native" position state) before they are trusted. A silent pass here could let a node/build ship with a corrupted state root undetected, since operators rely on this exact check as their correctness gate.

### Likelihood Explanation
The gap is deterministic and always present — it's not conditional on any privileged actor or race: any execution engine change that alters the derived state root without changing the raw write-set bytes (e.g. bugs in hot-state promotion, position-state checkpointing, or how prior state is folded in) will pass `ensure_match_transaction_info` unnoticed. The comment in the code confirms the maintainers are aware but have not wired in the check, and it is explicitly tied to gating the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature — meaning this is an active, not yet closed, gap ahead of a feature rollout.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute the relevant state-checkpoint hash(es) from the resulting state view (when a checkpoint is due) and assert equality with `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, mirroring the existing pattern used for `state_change_hash` and `event_root_hash`. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any feature relying on the new checkpoint fields, so `replay-verify`/`replay_on_archive` actually gates on full state-root correctness.

### Proof of Concept
1. Take a block sequence with a periodic state checkpoint transaction.
2. Introduce (or simulate) a change to state-application logic (e.g., in hot-state promotion or JMT node materialization) that leaves the transaction's own write-set bytes and event list unchanged, but alters the derived Sparse Merkle Tree root used to populate `state_checkpoint_hash`.
3. Run `storage/db-tool/src/replay_on_archive.rs` against archived transactions/infos containing the correct, original `state_checkpoint_hash`.
4. Observe `execute_and_verify` → `ensure_match_transaction_info` returns `Ok(())` despite the mismatched world-state root, because none of the checkpoint-hash fields are compared [5](#0-4) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
