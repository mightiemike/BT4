### Title
Missing per-step uniqueness in `getMessageID` allows response cross-wiring/DoS between concurrent web-api-target steps - (File: core/capabilities/webapi/target/target.go)

### Summary
`getMessageID` derives the gateway `messageID` solely from `WorkflowExecutionID` and the constant `ghcapabilities.MethodWebAPITarget`, omitting `req.Metadata.ReferenceID` (the per-step identifier used elsewhere in the codebase, e.g., `client_request.go`). Any workflow with two or more `web-api-target` steps sharing one `WorkflowExecutionID` (parallel branches, or sequential calls where a stale response arrives late) collide on the same `messageID`, causing deterministic "duplicate message" failures or late/misdelivered gateway responses being routed to the wrong step's channel.

### Finding Description
`Capability.Execute` computes `messageID` via `getMessageID(req)` and passes it to `c.connectorHandler.HandleSingleNodeRequest(ctx, messageID, payload)`. [4](#0-3) 

Internally, `handleSingleNodeRequest` registers a response channel keyed only by this `messageID` via `c.responses.new(messageID)`, and cleans it up with `defer c.responses.cleanup(messageID)`. [5](#0-4) 

The `responses` map's `new`/`get`/`cleanup` operations are keyed purely by string ID with no association to which logical call created it: [6](#0-5) 

When the gateway later calls back via `HandleGatewayMessage`, it looks up the channel solely by `body.MessageId` and forwards the response to whatever channel is currently registered for that ID: [7](#0-6) 

Two failure modes result from `getMessageID`'s lack of a per-call/step discriminator:
1. **Concurrent collision → DoS**: If two `web-api-target` steps execute concurrently in the same `WorkflowExecutionID`, the second call's `c.responses.new(messageID)` fails with `"duplicate message received for ID"` and the step errors out immediately.
2. **Sequential ID reuse → cross-wiring**: If the first call times out (its channel is `cleanup`'d) and a second call in the same execution later reuses the identical `messageID`, a late-arriving gateway response for the *first* (already-abandoned) request can be delivered to the *second* call's channel via the map lookup in `HandleGatewayMessage`, since nothing ties the response to the specific logical request beyond the reused string ID.

This contradicts the intended design pattern already implemented for the executable-capability path, which explicitly appends `ReferenceID` to support parallel step execution: `requestID := types.MethodExecute + ":" + workflowExecutionID + ":" + req.Metadata.ReferenceID`. [1](#0-0) 

No existing check (rate limiter, signature check, or namespace check) in `handleSingleNodeRequest`/`HandleGatewayMessage` validates that a response actually corresponds to the specific step/call that issued it — the only "collision" defense is the mutex-guarded map, which prevents two *simultaneously active* entries but does nothing once one is cleaned up and reused.

### Impact Explanation
Within a single workflow execution, this can cause: (a) legitimate parallel web-api-target steps to fail non-deterministically with duplicate-message errors, breaking workflow execution reliability, and (b) in the rarer timing-dependent case, a step receiving another step's HTTP response body/headers/status code instead of its own — a data-integrity violation that could propagate incorrect data into subsequent on-chain writes or decision logic. This matches "misreporting/data tampering" and "unsafe execution/data integrity" bounty impact categories, though the corruption is confined to steps within the same workflow execution (same owner), not a cross-tenant data leak.

### Likelihood Explanation
The bug requires only a workflow spec design (not privileged access) that issues two `web-api-target` steps sharing the same `WorkflowExecutionID` — for example, parallel branches in a DAG workflow, which is a normal and supported workflow-authoring pattern per the CRE model. The DoS variant (duplicate-message error) is deterministic and easy to trigger. The cross-wiring variant additionally requires a timing window (one request must time out/complete and be cleaned up before the second registers with the same ID, and the stale gateway response must arrive after that point), making it feasible but harder to trigger reliably, especially since gateway response networking introduces natural timing jitter that a patient party can exploit or that occurs incidentally under load/timeouts.

### Recommendation
Include `req.Metadata.ReferenceID` (or another per-step/per-call unique component, e.g., a monotonically incrementing counter or random nonce) in `getMessageID`'s constructed string, mirroring the pattern in `core/capabilities/remote/executable/request/client_request.go`:
```go
messageID := []string{
    req.Metadata.WorkflowExecutionID,
    req.Metadata.ReferenceID,
    ghcapabilities.MethodWebAPITarget,
}
```
Also validate `ReferenceID` is non-empty (similar to the existing `ValidateWorkflowOrExecutionID` checks) to avoid silently degrading to a fixed empty string.

func (r *responses) new(id string) (chan *api.Message, error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	_, ok := r.chs[id]
	if ok {
		return nil, fmt.Errorf("already have response for id: %s", id)
	}

	// Buffered so we don't wait if sending
	ch := make(chan *api.Message, 1)
	r.chs[id] = ch
	return ch, nil
}

func (r *responses) cleanup(id string) {
	r.mu.Lock()
	defer r.mu.Unlock()

	delete(r.chs, id)
}

func (r *responses) get(id string) (chan *api.Message, bool) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	ch, ok := r.chs[id]
	return ch, ok
}
