### Title
Wallet Contract's `has_in_flight_tx` lock can be permanently stuck `true`, freezing the account if a callback ever panics - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The near-wallet-contract (the Ethereum-compatible smart-contract wallet used for eth-implicit accounts) uses a single boolean flag `has_in_flight_tx` to serialize transactions: it is set `true` before creating an outbound promise chain and is only reset to `false` inside the corresponding private callback. There is no other function in the contract that can clear this flag. Because NEAR reverts *all* state writes made during a receipt if that receipt's execution panics, any panic occurring inside one of the reset-callbacks (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`) undoes the `self.has_in_flight_tx = false` write together with everything else in that call, leaving the flag permanently `true`. From that point on, `rlp_execute` always short-circuits with `"transaction already in progress"` [1](#0-0)  and the account can never again submit a transaction through the wallet contract, which is its only means of spending funds/managing keys.

### Finding Description
`WalletContract` stores the lock in its persisted state: [2](#0-1) 

`rlp_execute` checks the flag and rejects any call while a transaction is in flight, otherwise it sets the flag to `true` and returns a promise: [3](#0-2) 

The flag is only ever cleared at the top of the follow-up private callbacks, e.g. `rlp_execute_callback`: [4](#0-3) 

and `nep_141_storage_balance_callback`, which itself re-arms the flag to `true` again before dispatching a further promise chain (`storage_deposit` + transfer) that must, in turn, successfully invoke `rlp_execute_callback` to clear it: [5](#0-4) 

Every one of these callback functions is `#[private]` and runs as its own receipt/action; NEAR's runtime commits or rolls back the *entire* set of state changes performed by a single function invocation atomically — a panic anywhere in the function (out-of-gas, unwrap on unexpected data, deserialization panic on a malicious response, integer overflow panic, etc.) discards every write made in that call, including the `has_in_flight_tx = false` assignment made at the very start of the function. There is no other method in the contract capable of resetting this field (grep for `has_in_flight_tx` shows all 11 occurrences confined to `lib.rs`, with no admin/owner "reset" or "recover" entrypoint). This is structurally identical to the reported Gitcoin issue: a one-way flag (`isReadyForPayout` / `has_in_flight_tx`) that gates the only remaining valid path forward, with no fallback once that path's completion step fails/panics.

### Impact Explanation
Because `rlp_execute` is the sole entrypoint through which the eth-implicit account can perform *any* NEAR action (transfers, function calls, adding/removing access keys, etc. — see the `AddKeyAction`/`Action::Transfer` handling reachable only via `rlp_execute`), a stuck `has_in_flight_tx = true` permanently disables the account. Since key management (`AddKey`/`DeleteKey`) is itself routed through `rlp_execute`, the owner cannot even add a full-access key to escape the contract logic once locked — the funds held by the account become permanently unusable/frozen, matching the "impact" bar (permanently frozen funds) called for by this analog class. This is worse than the original Gitcoin report where funds could eventually be recovered by an operator; here the wallet contract has no privileged recovery path once the flag is stuck.

### Likelihood Explanation
The path is reachable purely from a normal user/relayer submitting an RLP-encoded Ethereum transaction (`rlp_execute`), which any unprivileged relayer or the account owner can call. Triggering the stuck state requires a callback panic, which can plausibly be induced by:
- A target/`token_id` contract (attacker-controlled, since `target`/token contract is chosen by whoever submits the transaction) returning malformed/oversized data to `storage_balance_of`/registrar `lookup` that causes unexpected panics or gas exhaustion while the fixed, hard-coded static gas budgets (`RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`) are consumed before the flag-reset logic executes far enough to complete cleanly.
- Any latent panic bug in the callback logic (e.g. future code changes, edge cases in `action_to_promise`, or unexpected `promise_results_count()`).

I was not able to fully confirm a concrete, deterministic zero-cost trigger (e.g., a guaranteed out-of-gas condition against the fixed gas constants) using only the indexed code; a background Devin session with full repo/test access would be needed to construct and run an end-to-end reproduction (e.g., a malicious NEP-141/registrar contract crafted to panic the callback) to conclusively prove exploitability versus this being only a defense-in-depth/robustness concern.

### Recommendation
- Do not gate the lock reset behind logic that can panic; perform `self.has_in_flight_tx = false` in a way that cannot be rolled back together with the rest of the callback (e.g., split into two receipts, or wrap risky logic in `catch_unwind`-safe helpers / promise-based error handling instead of `unwrap`/panics).
- Add a privileged or time-based recovery mechanism (e.g., allow the flag to be cleared if no callback fires within N blocks, similar to a timeout) so a single panicking callback cannot permanently disable the account.
- Increase callback gas budgets defensively and avoid computationally-unbounded operations (JSON parsing of attacker-influenced payloads) inside the same receipt that must reset the lock.

### Proof of Concept
Conceptual reproduction (not fully executed/validated against a live runtime in this session):
1. Deploy the wallet contract for an eth-implicit account.
2. Deploy a malicious "token" contract implementing NEP-141's `storage_balance_of` that returns a payload engineered to exhaust the remaining gas or panic during `serde_json::from_slice` inside `nep_141_storage_balance_callback` (or `address_check_callback` for the registrar path).
3. Submit an RLP-encoded ERC-20 transfer transaction via `rlp_execute` with `target` set to the malicious token contract. This sets `has_in_flight_tx = true` and schedules the `storage_balance_of` → `nep_141_storage_balance_callback` promise chain.
4. When the malicious contract's response causes `nep_141_storage_balance_callback` to panic, NEAR reverts all state changes from that callback receipt, including the intended `self.has_in_flight_tx = false`.
5. Any subsequent call to `rlp_execute` (even a completely unrelated, legitimate transaction) now fails with `"Error: transaction already in progress, please try again later."` forever, because no code path exists to clear `has_in_flight_tx` outside the now-unreachable callback completion.

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
