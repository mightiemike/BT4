### Title
Unbounded per-request ZK decryption CPU cost in `Wallet.queryNoteByIvk`/`ScanNoteByIvk` bypasses QPS-only rate limiting - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.queryNoteByIvk` allows any unauthenticated gRPC caller to force the node to run `Note.decrypt` (a zk-snark elliptic-curve operation) against every `ReceiveDescription` of every `ShieldedTransferContract` found in up to 1000 blocks, per single call. The only gate is `RateLimiterInterceptor`'s per-endpoint QPS token bucket, which limits *request count*, not *CPU work per request*, so an attacker can drive sustained heavy CPU load with cheap, garbage input and no economic cost.

### Finding Description
The gRPC call chain is: client → `RateLimiterInterceptor.interceptCall` (QPS gate only) [1](#0-0)  → `LiteFnQueryGrpcInterceptor.interceptCall`, which only blocks the call when the node `isLiteNode()` AND `openHistoryQueryWhenLiteFN` is false; on a normal (non-lite) full node or one with that flag enabled, the call passes through untouched [2](#0-1)  → `Wallet.scanNoteByIvk` → `Wallet.queryNoteByIvk`.

`queryNoteByIvk` only bounds the block range (`endNum - startNum <= 1000`), not the amount of shielded transaction data or decrypt operations inside that range [3](#0-2) . For every block in range, every transaction's `ShieldedTransferContract`, and every `ReceiveDescription` within it, the code unconditionally calls `Note.decrypt(...)` with the caller-supplied (and possibly garbage) `ivk` [4](#0-3) . `Note.decrypt` performs asymmetric/EC cryptographic work per call; there is no cache, no per-caller budget, and no cost accounting tied to the number of `ReceiveDescription`s scanned — the QPS limiter in front only throttles call *frequency*, not the amount of work each accepted call triggers.

The rate limiter is configured generically per RPC method with a default QPS strategy applied to all services at startup [5](#0-4) ; this is orthogonal to the actual CPU cost of a `ScanNoteByIvk` call, which scales with the number of shielded transactions present in the chosen 1000-block window (a value the attacker cannot reduce but also isn't charged for). Because the endpoint requires no shielded key ownership or proof of possession — a bogus `ivk` is processed the same as a real one, since `Note.decrypt` simply fails silently (`Optional` empty) after doing the crypto work — an attacker gains no legitimate output but still consumes full CPU cost per call.

Opening N parallel gRPC channels (each independently subject to the per-endpoint QPS limiter, which is typically per-second-based and does not cap concurrent in-flight long-running calls) lets an attacker multiply concurrent CPU-bound decrypt work across worker/handler threads, degrading responsiveness of unrelated RPCs sharing the same gRPC server thread pool.

### Impact Explanation
This is a DoS-via-RPC-API class issue: sustained CPU exhaustion on the full node's gRPC service thread pool degrades or stalls unrelated RPC calls (e.g., `GetNowBlock`, broadcast handling) for legitimate users, without the attacker needing any privileged role, funds, or on-chain transaction (this is a pure gRPC query, not a state-changing transaction, so no energy/bandwidth is charged as would be for on-chain execution). Impact is scoped to nodes that are not lite nodes or that have `openHistoryQueryWhenLiteFN=true` — i.e., default full/witness nodes with shielded API enabled.

### Likelihood Explanation
Feasible with default configuration: no special node setting is required beyond the node not being a strict lite node (the common default deployment for full nodes/witness nodes serving shielded queries). The attacker needs no account, no keys, no fee payment — just network access to the gRPC port and the ability to open concurrent channels, which is trivial and repeatable indefinitely. The main variable affecting real-world severity is how many `ShieldedTransferContract`s/`ReceiveDescription`s actually exist in the chosen 1000-block window; on a chain with meaningful shielded pool usage this is a nontrivial and attacker-selectable amount of decrypt work per call, and it is entirely free to trigger repeatedly.

### Recommendation
- Add a work-based cost/backpressure control for `queryNoteByIvk`/`scanNoteByIvk` (and the OVK/TRC20 variants) independent of QPS, e.g., cap the total number of `ReceiveDescription`s decrypted per call or apply a separate concurrency-limiting semaphore/queue specifically for these CPU-heavy shielded-scan endpoints.
- Consider a dedicated thread pool/executor for shielded scan RPCs so CPU-bound decrypt work cannot starve other RPC handlers sharing the main gRPC dispatch pool.
- Track and enforce a global concurrent-request limit (not just per-connection QPS) for `ScanNoteByIvk`/`ScanNoteByOvk`/`ScanShieldedTRC20NotesBy*` across all channels from all clients.

// Pseudocode PoC: flood ScanNoteByIvk with garbage ivk on many parallel channels
// while measuring latency of GetNowBlock.

ExecutorService pool = Executors.newFixedThreadPool(50);
byte[] garbageIvk = new byte[32]; // all zero / random bytes, no real key needed

for (int i = 0; i < 50; i++) {
  pool.submit(() -> {
    while (true) {
      WalletGrpc.WalletBlockingStub stub = WalletGrpc.newBlockingStub(channel);
      GrpcAPI.DecryptNotesMarked req = GrpcAPI.DecryptNotesMarked.newBuilder()
          .setStartBlockIndex(0)
          .setEndBlockIndex(999)
          .setIvk(ByteString.copyFrom(garbageIvk))
          .build();
      stub.scanNoteByIvk(req); // repeated tight loop, no backoff needed beyond QPS token refill
    }
  });
}

// Assert: P99 latency of GetNowBlock increases significantly / thread pool saturates

Expected result: server-side CPU utilization from `Note.decrypt` calls rises sharply and unrelated RPC latency (`GetNowBlock`) degrades, demonstrating that per-endpoint QPS metering in `RateLimiterInterceptor` does not bound the actual CPU cost consumed by `Wallet.queryNoteByIvk`.

    // that would be rejected by the per-endpoint limiter anyway. acquirePermit()
    // chooses blocking or non-blocking semantics based on rate.limiter.apiNonBlocking.
    boolean perEndpointAcquired = rateLimiter == null || rateLimiter.acquirePermit(runtimeData);
    boolean acquireResource = perEndpointAcquired && GlobalRateLimiter.acquirePermit(runtimeData);

        ((IPreemptibleRateLimiter) rateLimiter).release();
      }
      call.close(Status.fromCode(Code.RESOURCE_EXHAUSTED), new Metadata());
      return listener;
