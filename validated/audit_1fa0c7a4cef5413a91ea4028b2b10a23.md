### Title
App Proxy HMAC canonicalization uses undelimited key/value concatenation, allowing parameter-boundary collision forgery - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
The App Proxy signature verification path builds the string-to-sign by concatenating `key=value` pairs with **no separator** between pairs. This is the same root-cause class as the Seaport Merkle-tree bug: a hash/HMAC is computed over data whose structural boundaries are ambiguous, so two semantically different inputs can produce byte-identical canonical strings (and therefore identical, validly-signed HMACs). An attacker who controls arbitrary custom query-parameter values (which Shopify's App Proxy forwards and signs verbatim) can shift the key/value boundary so that a signature computed for one parameter set also validates a different parsed parameter set, letting security-relevant fields (e.g. `logged_in_customer_id`) end up with attacker-controlled values while the HMAC still checks out.

### Finding Description
`stringifyQueryForAppProxy` builds the canonical string by simple concatenation without any delimiter between entries: [1](#0-0) 

This is used by `generateLocalHmac`/`validateHmac` for the `appProxy` signator: [2](#0-1) 

`normalizeQuery` rebuilds the parameter object from a `URLSearchParams` (the actual production input type, as used by both the Remix and React Router App Proxy authenticators) by iterating decoded `key`/`value` pairs, so a value can legitimately contain a literal `=` character (from a URL-encoded `%3D`) without being treated specially: [3](#0-2) 

Because the canonical string has no delimiter between `key=value` entries, two different parameter sets can collide:
- `{bar: "2", foo: "1"}` → sorted → `"bar=2foo=1"`
- `{bar: "2foo=1"}` (i.e. request sent as `bar=2foo%3D1`) → `"bar=2foo=1"`

Both produce the identical canonical string, hence the identical HMAC for the same secret. The only params that are hardened against this class of ambiguity are the fixed security params in `APP_PROXY_SINGLE_VALUE_PARAMS` (`hmac`, `shop`, `signature`, `timestamp`), which are only checked for *repetition*, not for this boundary-shifting collision with arbitrary custom parameters: [4](#0-3) 

The production entry point passes the raw request's `URLSearchParams` straight into `validateHmac`, with no additional canonicalization or escaping of embedded `=`/parameter-boundary characters: [5](#0-4) [6](#0-5) 

This mirrors the Seaport finding precisely: the "leaf" (a single param's raw value) is not distinguishable from an "intermediate node" (the concatenation of two adjacent params), because there is no domain separation/framing in how the signed payload is constructed — exactly the class of defect the Seaport report attributes to using raw, un-hashed/un-delimited leaves.

### Impact Explanation
Any consumer app that trusts specific query parameters forwarded through the App Proxy for authorization decisions — most notably `logged_in_customer_id`, which Shopify explicitly forwards via App Proxy requests so apps can identify "the currently logged-in storefront customer" — can be misled: an attacker can craft a request whose canonical/signed string collides with a legitimately-signed request, while the actual parsed `URLSearchParams` object differs from what was signed. This is a customer/tenant-boundary integrity issue in a widely-used, unprivileged, anonymous-reachable code path (any storefront visitor can hit the App Proxy endpoint).

### Likelihood Explanation
Exploitability requires: (1) the app to accept and trust one or more custom/extra query parameters through the proxy (a supported, encouraged usage pattern for App Proxy apps), and (2) an attacker able to include a literal `=` inside a parameter value (trivial via URL-encoding, since App Proxy forwards arbitrary storefront query strings). Both conditions are realistic for real-world App Proxy integrations, and the attack requires no secret knowledge and no privileged position — only an anonymous request through the shop's public storefront/App Proxy endpoint.

### Recommendation
Adopt the same fix philosophy as recommended in the referenced report: eliminate boundary ambiguity instead of relying on raw concatenation.
- Build the canonical string with an explicit, escaped delimiter between `key` and `value` and between pairs (e.g., percent-encode `=` and `&` within keys/values before concatenating, or use `&`-joined `key=value` pairs consistently, as is already done for the `admin` signator via `ProcessedQuery`).
- Alternatively, reject/escape any parameter value containing the raw delimiter characters (`=`) before it participates in canonicalization, closing off the possibility that a value can "absorb" a subsequent key/value pair.
- Extend the repeated-parameter hardening (`APP_PROXY_SINGLE_VALUE_PARAMS` check) into a general boundary-collision check that verifies the canonical string can be uniquely decomposed back into the exact same key/value pairs.

### Proof of Concept
1. A legitimate App Proxy request is signed by Shopify for `?shop=shop.myshopify.com&timestamp=T&bar=2&foo=1`. The canonical string (sorted) is `bar=2foo=1`, and `signature = HMAC(bar=2foo=1)`.
2. An attacker crafts a forged request to the app's proxy endpoint: `?shop=shop.myshopify.com&timestamp=T&bar=2foo%3D1&signature=<same signature>` (single param `bar` whose decoded value is `"2foo=1"`).
3. `normalizeQuery` parses this into `{bar: "2foo=1"}`; `stringifyQueryForAppProxy` produces `"bar=2foo=1"` — identical to step 1's canonical string.
4. `validateHmac` computes the same local HMAC and `safeCompare` succeeds, so the forged request is accepted as validly signed, even though the actual `URLSearchParams` no longer contains a `foo` key at all (or contains a different `bar` value) than what any downstream code expects, corresponding to code paths in [1](#0-0)  and [3](#0-2) .

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}

export function validateHmac(config: ConfigInterface) {
  return async (
    query: HmacQuery,
    {signator}: {signator: HMACSignator} = {signator: 'admin'},
  ): Promise<boolean> => {
    const normalizedQuery = normalizeQuery(query, signator);

    if (signator === 'admin' && !normalizedQuery.hmac) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain an HMAC value.',
      );
    }

    if (signator === 'appProxy' && !normalizedQuery.signature) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain a signature value.',
      );
    }

    validateHmacTimestamp(normalizedQuery);

    const hmac =
      signator === 'appProxy'
        ? normalizedQuery.signature
        : normalizedQuery.hmac;
    const localHmac = await generateLocalHmac(config)(
      normalizedQuery,
      signator,
    );

    return safeCompare(hmac as string, localHmac);
  };
}

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
