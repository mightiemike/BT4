### Title
Voter block/tx-fee rewards become permanently unclaimable when a witness's per-cycle vote count drops to zero - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[],Long>> votes)` silently discards an entire cycle's accumulated witness reward whenever the witness's recorded total vote count for that cycle is `0` or `DelegationStore.REMARK`. This is structurally identical to the reported `EscrowedToken` bug: a guard added to avoid a division-by-zero (`totalVote == 0` → skip) causes the numerator value (`totalReward`) to be dropped instead of being redistributed or refunded, so the corresponding reward amount is permanently lost with no mechanism to reclaim it.

### Finding Description
Block rewards and transaction-fee rewards are accrued per witness per cycle via `MortgageService.payReward()`, which calls `delegationStore.addReward(cycle, witnessAddress, value)`: [1](#0-0) 

Later, when a voter withdraws/queries their reward, `computeReward(long cycle, List<Pair<byte[], Long>> votes)` distributes that cycle's `totalReward` proportionally to each voter based on `userVote / totalVote`: [2](#0-1) 

The guard `if (totalVote == DelegationStore.REMARK || totalVote == 0) { continue; }` exists purely to avoid a division by zero, exactly like the `if (totalVesting > 0)` guard in the reported `EscrowedToken` bug. However, `totalReward` for that cycle was already recorded in `DelegationStore` via `addReward` while the witness was actively producing blocks/receiving fees; it is never re-added to any other pool, never tracked in a separate "unclaimable" accumulator, and is never redistributed to any other witness's voters. Once `computeReward` skips it, the value stored under `buildRewardKey(cycle, address)` in `DelegationStore` is orphaned forever — no code path ever reads or recovers it again.

The per-cycle `totalVote` value used for the division is snapshotted once per maintenance cycle in `MaintenanceManager.doMaintenance()`: [3](#0-2) 

An unprivileged actor can drive a witness's `voteCount` for the *next* cycle to `0` (or leave it unset, i.e. `REMARK`) by voting for a witness and then fully unvoting before the maintenance boundary via the standard `VoteWitnessActuator`/`WithdrawBalanceActuator` broadcast-transaction paths, while the witness still accrues block/tx-fee rewards during the cycle from block production and transaction fees. When `computeReward` later runs for that cycle, the previously accrued reward for every voter of that witness in that cycle is dropped.

The same unsafe divide-by-zero-avoidance pattern (skip instead of redistribute/track) is duplicated in `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`, which forward the previous `Vi` value without incorporating `reward` when `voteCount == 0`: [4](#0-3) 

### Impact Explanation
This results in a permanent loss (stuck/unclaimable) of witness reward funds belonging to voters — an accounting corruption of the reward-distribution mechanism. Because it happens deterministically in every node (not a consensus divergence bug), the practical impact is silent, irrecoverable loss of TRX-denominated rewards owed to voters, exactly mirroring the "removedAmount stuck forever" scenario described in the source report. There is no `recoverUnclaimableFunds`-style mechanism, no accounting variable tracking the lost amount, and no way for governance or users to reclaim it.

### Likelihood Explanation
Reachable by any unprivileged account using only standard broadcast transactions (vote for a witness, then withdraw/unvote before the next maintenance cycle boundary) combined with the witness earning block/transaction-fee rewards during that same cycle window — no privileged role, leaked key, or malicious peer is required. The precise timing needed (driving a witness's vote count to exactly zero for a whole cycle while it still has already-recorded rewards from block production/fees) makes this a lower-probability but realistic occurrence, particularly for low-vote-count witnesses near the edge of the standby/active witness list.

### Recommendation
Add an accounting variable (e.g., an `unclaimableReward` counter per cycle/witness or a global sink) that is incremented by `totalReward` whenever `computeReward` encounters `totalVote == REMARK || totalVote == 0`, instead of silently discarding it via `continue`. Provide a well-audited mechanism (or redirect to the community/burn pool that already exists in java-tron, e.g., the black-hole address handling used elsewhere) to account for and dispose of these funds in a way that is transparent and doesn't remain untracked in `DelegationStore` forever. Apply the same fix to the equivalent skip logic in `DelegationStore.accumulateWitnessVi`/`RewardViCalService.accumulateWitnessVi`.

### Proof of Concept
Conceptual reproduction (would need to be validated against a running node/test harness, which is unavailable in this analysis):
1. Vote for witness `W` with a nonzero amount in cycle `N`, so `witness.getVoteCount() > 0`.
2. Ensure `W` produces blocks and/or receives transaction fees during cycle `N`, so `MortgageService.payReward` calls `delegationStore.addReward(N, W, value)` with `value > 0`.
3. Before the maintenance boundary that snapshots vote counts for cycle `N+1`, fully withdraw/unvote all votes for `W`, so `MaintenanceManager.doMaintenance()` calls `delegationStore.setWitnessVote(N+1, W, 0)`.
4. Any voter that had voted for `W` in cycle `N` now calls `withdrawReward`/`queryReward`; `MortgageService.computeReward(N, votes)` reads `totalVote = delegationStore.getWitnessVote(N, W)` (or the relevant boundary cycle) as `0`/`REMARK`, hits the `continue` branch, and the previously recorded `totalReward` for that cycle is never paid to any account — permanently stuck in `DelegationStore` with no code path to recover it.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
```java
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {

    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
```
