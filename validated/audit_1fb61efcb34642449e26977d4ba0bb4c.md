Based on my investigation, I found a strong analog matching the "pause that passes through instead of reverting" mechanism explicitly permitted by the rules.

### Title
`accrue` pause silently returns stale index while `next-index`-based previews keep advancing, causing conversion mismatch on deposit/redeem - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent `v0-vault-*.clar` vaults)

### Summary
The vault's public `accrue` function, when the `accrue` pause flag is set, returns the *current stored* `index`/`lindex` without persisting any update and without reverting [1](#0-0) . However, `deposit`/`redeem` compute the actual conversion rate via `convert-to-shares-preview` / `convert-to-assets-preview`, which internally call `total-assets-preview` → `debt-preview` → `next-index`, a function independent of the `accrue` pause flag and of the value returned by `accrue` [2](#0-1) .

### Finding Description
`deposit` and `redeem` call `(try! (accrue))` first, bind its result to `u` (unused beyond acknowledging success), then separately compute `inkind` via `convert-to-shares-preview`/`convert-to-assets-preview` [3](#0-2) . These preview helpers call `total-assets-preview`, which calls `debt-preview`, which calls `calc-cumulative-debt` using `next-index` — a value computed from elapsed time regardless of whether the `accrue` pause flag is active [4](#0-3) .

When `accrue` is paused, the state-mutating branch (`var-set index`, `var-set lindex`, treasury minting) is skipped, and the function returns the last-persisted `index`/`lindex` unchanged — the "pass-through" bug-class explicitly called out in the report's mechanism list [5](#0-4) . But `next-index` (used by the preview/conversion path that determines actual `inkind` shares/assets moved) is not gated by this same pause flag, so it continues to reflect interest accrued since the last real update. This creates a divergence: the vault's on-chain persisted accounting (`index`) is frozen by the pause, while the value used to price the deposit/redeem in the same transaction is not, producing an inconsistent share/asset conversion relative to the frozen `assets`/`principal-scaled` state that the pause was intended to preserve.

### Impact Explanation
This lands in the **temporary freezing/mispricing of user funds** impact class: when the accrual pause is active (e.g., during a paused/maintenance state), deposits and redeems still execute (since `deposit`/`redeem` pause flags are independent of the `accrue` pause flag) but use a conversion rate computed from a different accrual assumption than the one actually persisted to storage, allowing users to mint/redeem shares at a mismatched rate relative to the frozen ledger state, diluting or over-crediting other depositors' claims on the vault's assets.

### Likelihood Explanation
Likelihood is moderate: it requires the DAO/operator to activate the `accrue` pause flag specifically (distinct from the `deposit`/`redeem` pause flags) while leaving deposit/redeem enabled, and requires time to elapse so `next-index` diverges from the frozen `index`. This is a narrow operational window but is a legitimate protocol-state combination, not requiring any external compromise.

### Recommendation
Make `total-assets-preview`/`debt-preview`/`next-index` respect the same `accrue` pause flag as the public `accrue` function, or have `deposit`/`redeem` short-circuit conversion using the value actually returned/persisted by `accrue` rather than independently recomputing via `next-index`, so paused accrual is consistently reflected across all rate-determining paths within the same transaction.

### Proof of Concept
1. DAO/operator sets the `accrue` pause flag true on `v0-vault-stx` (or any `v0-vault-*`) via `pause-states`, leaving `deposit`/`redeem` flags false.
2. Time elapses such that `next-index` (time-dependent) would differ meaningfully from the frozen `index`.
3. A user calls `deposit`: `(try! (accrue))` returns the stale `{index, lindex}` and skips all `var-set` updates [3](#0-2) .
4. `convert-to-shares-preview` is computed using `total-assets-preview`, which uses `next-index` reflecting the un-paused, time-advanced accrual state [6](#0-5) .
5. Shares are minted at this inconsistent rate while `var-set assets` still updates the persisted ledger under the (frozen) `accrue` assumption, producing a rate mismatch between the paused accounting and the unpaused pricing used for this specific deposit.

I was unable to locate and confirm the exact definition of `next-index` within the tool-call budget (only its call sites were found), so the precise time-dependency formula it uses is not directly verified — this should be confirmed against `mainnet/contracts/vault/v0-vault-stx.clar` (or the analogous shared vault-interest library) before treating this as conclusively exploitable.
