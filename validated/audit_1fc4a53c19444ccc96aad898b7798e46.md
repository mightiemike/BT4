### Title
Hardcoded `paid_fee_on_l1 = Fee(1)` in consensus-path L1Handler conversion nullifies the L1-fee-paid check - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
`TransactionConverter::convert_consensus_l1_handler_to_internal_l1_handler` builds the executable `L1HandlerTransaction` used by validators/executors from a `ConsensusTransaction::L1Handler`, but instead of propagating the real fee that was paid on L1 for the message, it hardcodes `Fee(1)`, with an explicit TODO acknowledging the gap: [1](#0-0) 

This is the same bug class as the LiFi `LIFuelFacet` finding: a mechanism intended to enforce a limit/precondition (here: "an L1 message must have paid a non-zero fee on L1 before its L1Handler is executed") is not actually backed by real, chain-verified data — it degenerates into a fixed placeholder value that the downstream check can never meaningfully evaluate against.

### Finding Description
`L1HandlerTransaction::execute_raw` enforces a resource-bound check and then a fee-sufficiency check that only verifies the "paid fee" field is non-zero: [2](#0-1) 

That `paid_fee_on_l1` value is expected to come from the actual amount paid by the L1 sender when the message was sent to the L2 core contract. The `starknet_api::executable_transaction::L1HandlerTransaction` struct carries this as an explicit field: [3](#0-2) 

However, the raw `transaction::L1HandlerTransaction` type carried inside `ConsensusTransaction::L1Handler` (the wire/consensus representation) does **not** include `paid_fee_on_l1`. When a node needs to convert a consensus-received `L1Handler` transaction back into the executable form (e.g. to re-execute a proposal during validation), `TransactionConverter::convert_consensus_l1_handler_to_internal_l1_handler` fabricates the fee field as `Fee(1)` rather than sourcing it from the original L1 event log: [1](#0-0) 

Because `Fee(1) != Fee(0)`, the only check that exists (`paid_fee == Fee(0)`) is *always* satisfied for every L1Handler transaction that goes through this conversion path, regardless of what was truly paid on L1 (including the legitimate "fee = 0" case that the check exists to reject). This is functionally identical to the LiFi bug pattern described in the report: a safety limit exists on paper (`InsufficientFee` check) but is fed data that can never trigger a rejection, so the limit provides no real protection.

### Impact Explanation
The `InsufficientFee` check is the sequencer's only on-chain safeguard against executing L1Handler transactions for which the L1 sender did not actually pay anything. With this hardcoded value, that guard is a no-op for every node that reconstructs the executable transaction via the consensus path, not just the proposer that originally scraped the L1 event. Since the placeholder is applied deterministically and identically by all nodes, this does not directly cause state-root divergence between honest nodes, but it does mean the fee-enforcement contract for L1Handler execution is broken network-wide: L1 handler transactions consume L2 execution resources (bounded only by the fixed `l1_handler_max_amount_bounds`, analogous to LiFi's "high fixed limits [that] don't check that there is enough liquidity available") while the sequencer's fee-paid sanity check can never reject them for lacking payment. This undermines the intended cost/limit-enforcement design for a transaction type that — like `LIFuelFacet` — is meant to move a bounded, backend-checked amount of value/resources across a trust boundary (L1→L2) without a working final safety check on the L2 side.

### Likelihood Explanation
This code path is reached whenever a consensus-delivered `L1Handler` transaction (`ConsensusTransaction::L1Handler`) is converted to its executable form via `convert_consensus_tx_to_internal_consensus_tx` → `convert_consensus_l1_handler_to_internal_l1_handler`, which is invoked from the proposal-validation flow (`apollo_consensus_orchestrator/src/validate_proposal.rs`). I was not able to fully trace, within the remaining budget, whether this exact function is on the hot path for every validator's block re-execution or only for a subset of flows (e.g., some paths may instead pull the original transaction with its real `paid_fee_on_l1` from local L1-scraper storage). This distinction affects whether the gap is exercised on every L1Handler transaction or only in some code paths — this remains unverified and should be confirmed by a maintainer/engineer with full repo access.

### Recommendation
Do not synthesize `paid_fee_on_l1` in `convert_consensus_l1_handler_to_internal_l1_handler`. Either (a) include the real `paid_fee_on_l1` in the `ConsensusTransaction::L1Handler` wire format so it round-trips correctly, or (b) have the converter look up the true paid fee from the node's own L1 event-scraper store keyed by the transaction's L1 nonce/hash before constructing the executable transaction, and fail conversion if the value cannot be authenticated. The `Fee(1)` placeholder and its TODO should not ship in a path that feeds the `InsufficientFee` enforcement check.

### Proof of Concept
Conceptual trace (not exhaustively confirmed to be reachable in every validator flow given remaining time constraints):
1. An L1 sender calls `sendMessageToL2` on the Starknet core contract with `value = 0` (no fee paid), producing an L1→L2 message event.
2. A node's proposer path (via its own L1 scraper) is expected to construct the `L1HandlerTransaction` with `paid_fee_on_l1 = Fee(0)`, which `execute_raw` would reject via `TransactionFeeError::InsufficientFee`, as covered by the existing regression test: [4](#0-3) 
3. If the same transaction instead arrives at a node through the consensus path as `ConsensusTransaction::L1Handler` (which has no `paid_fee_on_l1` field) and is converted via `convert_consensus_l1_handler_to_internal_l1_handler`, the executable transaction is built with `paid_fee_on_l1 = Fee(1)` unconditionally: [5](#0-4) 
4. `execute_raw`'s check `if paid_fee == Fee(0)` never fires for this reconstructed transaction, so the fee-sufficiency safeguard is silently bypassed for that node's execution/validation of the block.
