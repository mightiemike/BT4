### Title
Stale `ref_count` snapshot in cleaning candidates can cause `checked_sub().expect()` panic in `update_candidate_after_reclaims` - ([File: accounts-db/src/accounts_db.rs])

### Summary
`update_candidate_after_reclaims` assumes `candidate_info.ref_count` (captured earlier when the pubkey was added to the clean candidate set) is always ≥ `reclaims.len()` (computed later, live, by `collect_reclaims`/`clean_rooted_entries`). Because `candidate_info.ref_count` is only refreshed in the zero-lamport branch of the clean scan and never refreshed for the "multiple rooted entries" branch, a pubkey whose rooted-write count grows between candidate construction and reclaim collection can cause the live reclaim count to exceed the stale ref count, underflowing the `checked_sub` and triggering the `.expect("candidate ref count covers every reclaimed entry")` panic.

### Finding Description
`update_candidate_after_reclaims` performs: [1](#0-0) 
which subtracts `reclaims.len()` from `candidate_info.ref_count` and `.expect()`s that this never underflows.

In the cleaning scan loop, when a pubkey is found to have multiple rooted slot-list entries (`slot_list.len() > 1`), `should_collect_reclaims` is set, but `candidate_info.ref_count` is **not** updated with the freshly observed `ref_count` from the scan — that update only happens in the separate zero-lamport branch: [2](#0-1) 

Afterward, the actual reclaim set is computed live against the current index state via `collect_reclaims` → `clean_rooted_entries`, which unrefs the entry by exactly the number of purged (older) slot-list entries found *at that later point in time*: [3](#0-2) [4](#0-3) 

Because `candidate_info.ref_count` was captured earlier (during candidate construction, before the scan loop) and is never refreshed for this code path, if the attacker's pubkey receives additional rooted writes to slots below `max_clean_root_inclusive` between the time the candidate was constructed and the time `collect_reclaims` actually runs against the live index entry, the live entry's slot list will contain more purgeable older entries than the number implied by the stale `ref_count`. `clean_rooted_entries`/`purge_older_root_entries` purges all entries strictly older than the newest entry ≤ `max_clean_root_inclusive`, so a wider live slot list yields more reclaims than `candidate_info.ref_count` (captured earlier) can cover, causing `checked_sub` to return `None` and the `.expect()` to panic.

An unprivileged user fully controls the write frequency and pubkeys of accounts they own, and can repeatedly write to the same account across many slots that subsequently get rooted, inflating the slot-list length/ref_count of that pubkey between the background cleaner's candidate-construction pass and its actual reclaim-collection pass for that same clean cycle.

### Impact Explanation
This causes an unhandled `panic!` (via `.expect()`) inside `AccountsDb::update_candidate_after_reclaims`, which runs from the background accounts-cleaning path. A panic in this codepath crashes/aborts the validator process, i.e. a remotely-triggerable node liveness/availability issue caused purely by normal account write patterns from a fee-paying, unprivileged user. This matches the "node panic / crash caused by unprivileged input" bounty category.

### Likelihood Explanation
Preconditions: attacker needs to make many rooted writes to the same pubkey (fully within their control — pay for and resubmit transactions touching one account across many slots) timed so that additional rooted writes land on that pubkey inside the window between when the cleaner's candidate list captures `ref_count` for that pubkey and when `collect_reclaims` is later executed for that same pubkey in the same `clean_accounts` invocation. This window exists because candidate construction and the parallel `do_clean_scan`/`collect_reclaims` step are not committed atomically against a single point-in-time snapshot of the entry for the non-zero-lamport, multi-rooted-entry branch.

I was not able to fully trace, within the available tool budget, the exact code that performs the *initial* population of `candidate_info.ref_count` before `do_clean_scan` runs (i.e., the `construct_candidates`-style logic) to precisely characterize how wide this window is in practice (single clean-cycle iteration vs. across multiple background loop iterations). This is a genuine gap in my verification — someone should trace that function/the full `clean_accounts` call before treating this as fully confirmed. Given the direct code evidence that (a) the update path leaves `candidate_info.ref_count` unrefreshed for the exact branch that triggers `should_collect_reclaims`, and (b) the actual reclaim count is computed independently and later, this is very likely exploitable but the precise reproduction timing needs the PoC below run against the real `clean_accounts` scheduler to confirm feasibility under real background-cleaning cadence.

### Recommendation
In the "multiple rooted entries" branch of `do_clean_scan` (around `accounts_db.rs:1960-1969`), refresh `candidate_info.ref_count = ref_count` (the value obtained fresh from the same scan) exactly as is already done in the zero-lamport branch, so the ref count used in `update_candidate_after_reclaims` always reflects the same point-in-time snapshot as the `slot_list` used to decide whether to collect reclaims. Alternatively/also, make `update_candidate_after_reclaims` tolerant of `reclaims.len()` exceeding the stale `ref_count` (e.g., saturate to zero or re-fetch the live ref count) rather than `.expect()`-panicking, since it is fed by two temporally-decoupled data sources.

```rust
// accounts-db/src/accounts_db/tests/impl.rs
#[test]
#[should_panic(expected = "candidate ref count covers every reclaimed entry")]
fn test_update_candidate_after_reclaims_stale_ref_count_panics() {
    let accounts = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);

    // Simulate a candidate whose ref_count was captured *before* additional
    // rooted writes to the same pubkey occurred (the stale snapshot).
    let mut candidate_info = CleaningInfo {
        slot_list: vec![(1, AccountInfo::default()), (2, AccountInfo::default())],
        ref_count: 2, // stale value from earlier candidate construction
        ..Default::default()
    };

    // Simulate the *live* reclaim set collected later, after the attacker
    // added more rooted writes to the same pubkey (e.g. slots 1,2,3 purged
    // because a newer rooted write at slot 4 exists in the live index).
    let mut reclaims = ReclaimsWithNewestSlot::new();
    reclaims.push((1, AccountInfo::default()));
    reclaims.push((2, AccountInfo::default()));
    reclaims.push((3, AccountInfo::default())); // extra reclaim beyond stale ref_count

    // This should panic via the `.expect(...)` because reclaims.len() (3)
    // exceeds candidate_info.ref_count (2).
    accounts.update_candidate_after_reclaims(&mut candidate_info, &reclaims);
}
```

```rust
    pub fn clean_rooted_entries(
        &self,
        pubkey: &Pubkey,
        reclaims: &mut ReclaimsWithNewestSlot<T>,
        max_clean_root_inclusive: Option<Slot>,
    ) -> bool {
        let map = self.get_bin(pubkey);
        map.slot_list_mut_with_entry(pubkey, |mut slot_list, entry| {
            let reclaims_start = reclaims.len();
            self.purge_older_root_entries(&mut slot_list, reclaims, max_clean_root_inclusive);
            // Unref each reclaimed entry. This must happen inside the closure so the
            // updated ref count is visible to the write-through check.
            entry.unref_by_count((reclaims.len() - reclaims_start) as RefCount);
        })
        .is_none()
    }
```
