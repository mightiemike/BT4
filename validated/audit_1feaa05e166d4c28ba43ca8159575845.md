### Title
Unmetered memory expansion from precompiled-contract return data when `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` is not enabled - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
In `Program.callToPrecompiledAddress()`, the TVM analog of a low-level `.call()` that copies unbounded return data to memory, the code has two different write paths for a precompiled contract's output depending on a governance feature flag. When `VMConfig.allowTvmSelfdestructRestriction()` is false (the default, per `common/src/main/resources/reference.conf` and `DynamicPropertiesStore.getAllowTvmSelfdestructRestriction()` which default to `0`), the return data of the precompiled contract is written to memory with `this.memorySave(msg.getOutDataOffs().intValue(), out.getRight())`, which unconditionally extends VM memory to the full length of `out.getRight()` regardless of the `outDataSize` the caller specified (and paid gas for) in the `CALL`/`STATICCALL`/`DELEGATECALL` opcode operands.

### Finding Description
The energy cost for memory expansion on a `CALL`-family opcode is computed once, up front, in `EnergyCost.getCalculateCallCost()` / `getCalculateCallCost()` → `calcMemEnergy()`, using only the caller-declared `outDataOffs`/`outDataSize` operands [1](#0-0) . That declared size is what memory expansion is billed for before the call executes.

After the call executes, `Program.callToPrecompiledAddress()` writes the actual precompiled-contract output into memory:
```java
if (VMConfig.allowTvmSelfdestructRestriction()) {
  this.memorySave(msg.getOutDataOffs().intValueSafe(), msg.getOutDataSize().intValueSafe(), out.getRight());
} else {
  this.memorySave(msg.getOutDataOffs().intValue(), out.getRight());
}
``` [2](#0-1) 

The guarded branch (`memorySave(addr, allocSize, value)`) calls `memory.extendAndWrite(addr, allocSize, value)`, which extends memory only to the caller-paid `allocSize` and copies `min(value.length, allocSize)` bytes [3](#0-2) [4](#0-3) . This is the "SafeCall"-style fix, bounding the copy/expansion to what was billed.

The unguarded (default) branch calls `memorySave(int addr, byte[] value)` → `memory.write(addr, value, value.length, false)`, which calls `extend(address, value.length)` unconditionally — i.e., it expands memory to the *actual* length of the precompiled contract's return data, not the length the caller declared and paid for in the `CALL` opcode operands [5](#0-4) [6](#0-5) . This is functionally identical to the reported Solidity bug class: an external call's return data is copied to memory (causing memory-expansion cost) beyond what was priced/limited by the caller.

This is directly analogous to the reported issue: `.call()` in Solidity copies all return data to memory regardless of what's "expected," incurring unbudgeted memory-expansion gas; here, the TVM's precompiled-call return-copy path bypasses the caller's declared/paid `outDataSize` entirely when the mitigating flag is off, so memory can be expanded beyond what `getCalculateCallCost()` charged for.

The corresponding non-precompiled path (`callToAddress`) already always uses the size-limited write (`memorySaveLimited`) regardless of the flag [7](#0-6) , which underscores that the precompiled-contract path is the outlier still gated behind a feature flag that defaults to disabled.

### Impact Explanation
If `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has not been activated (default `0` in config, requires a passed committee proposal at `ForkBlockVersionEnum.VERSION_4_8_1` or later — see `ProposalUtil.java` and `reference.conf`), any TVM contract call to a precompiled-contract address whose output is larger than the caller-declared `outDataSize` will expand VM memory beyond the amount priced into the `CALL` opcode's memory-expansion energy cost. Depending on how large a precompile's return data can be, an attacker-influenced contract could use this to consume node memory/CPU (via `Memory`'s chunk allocation) disproportionate to the energy actually charged, a resource-accounting/DoS-adjacent issue analogous to the reported griefing vector. It does not directly cause fund loss but represents an energy-metering bypass in the TVM's core CALL-handling logic, reachable from any ordinary (non-privileged) smart-contract transaction.

### Likelihood Explanation
Reachability requires only a broadcast smart-contract transaction that issues a `CALL`/`STATICCALL`/`DELEGATECALL` to a precompiled contract address with a small declared `outDataSize`, while the precompiled contract's actual return data is larger. Likelihood on production TRON mainnet is uncertain: this is gated by the on-chain `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` committee proposal — if already active on mainnet (I could not verify current mainnet chain-parameter state from the codebase alone, only that the default config value is `0`), the vulnerable branch is dead code there. It remains reachable, however, on any chain/deployment (private chains, sidechains, or a mainnet snapshot before the proposal passed) where the proposal has not been approved.

### Recommendation
Remove the feature-flag gating and always bound the precompiled-call output write to the caller-declared `outDataOffs`/`outDataSize` (i.e., always use the `memorySave(addr, allocSize, value)` / `memorySaveLimited` behavior), matching what `callToAddress()` already does unconditionally, so return-data copying can never exceed what was charged via `EnergyCost.getCalculateCallCost()`.

### Proof of Concept
Not independently executable from static analysis alone; conceptually:
1. Deploy/target a chain where `getAllowTvmSelfdestructRestriction() == 0` (default).
2. From a smart contract, issue a `STATICCALL`/`CALL` to a precompiled-contract address (e.g., one of the `PrecompiledContracts.PrecompiledContract` implementations) with `outDataSize` set to `0` or a small value, while supplying input that causes the precompile to return output data much larger than `outDataSize`.
3. Observe that `Program.callToPrecompiledAddress()` takes the `else` branch and calls `memorySave(offset, out.getRight())`, expanding VM memory to `out.getRight().length` — a length never accounted for in the pre-call `calcMemEnergy()` charge, decoupling memory expansion from energy cost.

I could not verify from the index whether any specific precompiled contract in this codebase actually returns large/variable-length output (the search for concrete `PrecompiledContract` implementations and their output sizes did not return conclusive results within available iterations), so the magnitude of exploitable memory growth is unconfirmed and would need to be validated with the full source in a Devin session.

  public void write(int address, byte[] data, int dataSize, boolean limited) {

    if (data.length < dataSize) {
      dataSize = data.length;
    }

    if (!limited) {
      extend(address, dataSize);
    }

    int chunkIndex = address / CHUNK_SIZE;
    int chunkOffset = address % CHUNK_SIZE;

    int toCapture = 0;
    if (limited) {
      toCapture = (address + dataSize > softSize) ? softSize - address : dataSize;
    } else {
      toCapture = dataSize;
    }

    int start = 0;
    while (toCapture > 0) {
      int captured = captureMax(chunkIndex, chunkOffset, toCapture, data, start);

      // capture next chunk
      ++chunkIndex;
      chunkOffset = 0;

      // mark remind
      toCapture -= captured;
      start += captured;
    }

    if (programListener != null) {
      programListener.onMemoryWrite(address, data, dataSize);
    }
  }
