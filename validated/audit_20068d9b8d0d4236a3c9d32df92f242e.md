### Title
`replay_on_archive` / `ensure_match_transaction_info` silently skips state-checkpoint hash verification, letting a diverging state root pass as a "successful" replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used by the archive replay-verify tool (`storage/db-tool/src/replay_on_archive.rs`) to check that a freshly re-executed transaction matches the historically committed `TransactionInfo`. It checks status, gas, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually authenticate the JMT/state-summary root produced by `DoStateCheckpoint`. This is the same class of bug as the `LendingTerm` issue: two code paths that are supposed to enforce the same invariant (state consistency) use inconsistent logic, and the weaker one is the one that gates the "did replay succeed" decision, rendering the stronger commit-time check meaningless for this purpose.

### Finding Description
At commit-time, `execution/executor/src/workflow/do_state_checkpoint.rs::get_state_checkpoint_hashes` strictly validates the checkpoint hash: `ensure!(known[idx] == Some(computed_last_checkpoint_hash), ...)`. [1](#0-0) 

However, when the archive replay-verify tool re-executes historic transactions and compares outputs to the already-committed `TransactionInfo`s, it calls `ensure_match_transaction_info`, which checks status, gas, write-set hash and event-root hash — but the state/hot-state/position checkpoint hashes are never compared: [2](#0-1) 

The TODO comment in that exact function documents the gap explicitly: [3](#0-2) 

This comparator is invoked directly by `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which re-executes transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` against `expected_txn_infos` pulled from the backup/archive: [4](#0-3) 

Because the checkpoint-hash fields are skipped, if VM execution logic diverges from the historically-committed state (e.g. a resource-value bug, a native-position/"trading-native" state-root computation bug, or an unintended hard-fork-causing behavior change) but write set operations still happen to hash the same or events/status/gas still match, `replay_on_archive` will report the transaction as a verified match even though the state root it would produce is wrong. The check is precisely the "authenticated" invariant binding a version's committed data to its true root; skipping it means the audit/verification tool cannot catch state-root divergence, which is the primary signal replay-verify tooling is meant to catch.

### Impact Explanation
`replay_on_archive` is the tool used to validate that re-executing an archived transaction history against a candidate VM/runtime build reproduces the exact same committed ledger state — this is the standard mechanism for catching state-breaking bugs before/after a software upgrade (hard-fork-class regressions). Because `ensure_match_transaction_info` never compares `state_checkpoint_hash` (nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`), a state-root-diverging bug in execution or in state-checkpoint construction (JMT, hot-state, or the new position/"trading-native" state summary) can pass replay-verify undetected as long as write-set/event/status/gas values happen to match. This directly matches the required impact "Hard-fork-only divergence during commit, replay, restore, or proof verification" — a wrong state root is accepted as valid by the verification tooling that exists specifically to catch this class of defect.

### Likelihood Explanation
This is not a hypothetical inconsistency: the code contains its own explicit TODO acknowledging the exact scenario ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"), and the only caller of this function in a verification context (`replay_on_archive.rs`) exercises exactly this code path with no additional state-root check elsewhere in that tool. The gap is triggered any time the write set/events/status/gas of a transaction do not change under a state-computation regression — which is plausible for many kinds of state-only bugs (e.g. errors localized to the state-summary/checkpoint construction layer, hot-state tracking, or the newly introduced native "position" state summary, none of which factor into `write_set` hash equality checks used here). This is a real gap in a currently-shipped verification tool, not merely a theoretical analog.

### Recommendation
Extend `ensure_match_transaction_info` (or add an explicit additional check invoked by `replay_on_archive.rs`) to compare `txn_output`'s recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when applicable/available) against the corresponding fields on the expected `TransactionInfo`, mirroring the strict `ensure!` used in `DoStateCheckpoint::get_state_checkpoint_hashes`. Until `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-style checks are unified between the commit path and the replay/verify path, `replay_on_archive` should not be treated as sufficient evidence that state roots match across a build/version boundary.

### Proof of Concept
1. Introduce (or imagine) a state-computation change that alters the resulting state-checkpoint/JMT root for some historical transaction range without altering the transaction's write set serialization, emitted events, gas used, or execution status (e.g., a bug confined to `LedgerStateSummary::update`/`ProvableStateSummary` or the position-state summary path in `do_state_checkpoint.rs`).
2. Run `db-tool replay-on-archive --start-version .. --end-version ..` against an archived history spanning that range.
3. `execute_and_verify` re-executes the transactions and calls `ensure_match_transaction_info` with the archived `expected_txn_infos`. [5](#0-4) 
4. Because `ensure_match_transaction_info` never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, the call returns `Ok(())` and the tool reports the transactions as successfully verified, even though the actual (unverified) state root diverges from the one recorded in the archived `TransactionInfo`.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
