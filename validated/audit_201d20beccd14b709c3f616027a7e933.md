## Title
Unauthenticated Rate Limit Configuration Is Never Applied — All Requests Use the Looser Authenticated Threshold - (File: core/web/router.go)

### Summary
The Chainlink node's `WebServer.RateLimit` configuration defines two distinct throttling policies — a strict one for unauthenticated requests (`Unauthenticated`/`UnauthenticatedPeriod`, default 5 req/20s) and a looser one for authenticated requests (`Authenticated`/`AuthenticatedPeriod`, default 1000 req/min) [1](#0-0) . However, `NewRouter` only ever constructs one rate limiter, wired with the `Authenticated`/`AuthenticatedPeriod` values, and applies it to the entire top-level route group that serves *all* endpoints, including ones reachable without any authentication.

### Finding Description
In `core/web/router.go`, the single `rateLimiter` middleware instance is built from `rl.AuthenticatedPeriod()` / `rl.Authenticated()` and attached to the whole `api` group covering session, v2, loop, health, and debug routes: [2](#0-1) 

The `rateLimiter` helper itself is generic and accepts a period/limit pair, but it is only ever invoked with the `Authenticated` config values here, and separately with hardcoded static-asset limits for the GUI: [3](#0-2) [4](#0-3) 

A `grep` across `core/web/*.go` confirms that `rl.Unauthenticated()` / `rl.UnauthenticatedPeriod()` (defined in `core/services/chainlink/config_web_server.go`) are never referenced anywhere in the router or session/auth handling code — only `AuthenticatedPeriod()`/`Authenticated()` show up, exactly matching the two call sites above. The accessor methods exist and are documented, but the stricter policy is dead code: [5](#0-4) 

This means unprivileged-user-reachable, unauthenticated endpoints — most notably:
- `POST /sessions` (login, brute-force target for credential stuffing) [6](#0-5) 
- `POST /v2/jobs/:ID/runs` and `GET /v2/ping`, reachable via External-Initiator header auth or with no auth at all [7](#0-6) 
- `PATCH /v2/resume/:runID`, an entirely unauthenticated group [8](#0-7) 

are all throttled at the permissive `Authenticated` rate (1000 requests/minute by default) instead of the intended `Unauthenticated` rate (5 requests/20 seconds by default). The documentation and config schema promise a 12,000x stricter limit for exactly these unauthenticated paths, but the code never enforces it.

### Impact Explanation
This directly matches the reported bug class ("lack of resources and rate limiting") with a concrete, reachable root cause: an unprivileged attacker can send credential-stuffing/brute-force requests against `/sessions` or spam unauthenticated webhook-run/resume endpoints at up to 1000 req/min per client instead of the documented 5 req/20s, consuming CPU/DB/network resources and significantly weakening login brute-force protection. It does not grant direct auth bypass by itself, but it removes a documented defense-in-depth control against brute force and resource exhaustion on unauthenticated attack surface.

### Likelihood Explanation
High likelihood: no special access or conditions are required — any unauthenticated client can exploit this over the network, exactly as described in the original report (300 req/min observed). The bug is a straightforward misconfiguration in `NewRouter`, present for the whole life of the router.

### Recommendation
Split the route groups so unauthenticated endpoints (`/sessions`, unauthenticated `/v2` routes, external-initiator routes) are wrapped with a rate limiter built from `rl.Unauthenticated()`/`rl.UnauthenticatedPeriod()`, while authenticated routes keep the current `Authenticated` limiter. Add a regression test asserting that unauthenticated requests are rejected after the configured `Unauthenticated` threshold, not the `Authenticated` one.

### Proof of Concept
Given default config (`Authenticated=1000/1m`, `Unauthenticated=5/20s`), an unauthenticated client can send ~1000 `POST /sessions` login attempts per minute before being throttled, since the middleware installed in `NewRouter` only consumes `rl.Authenticated()`/`rl.AuthenticatedPeriod()` [9](#0-8) , rather than the far stricter `Unauthenticated` values that the config docs claim apply to such requests [10](#0-9) .

```go
func rateLimiter(period time.Duration, limit int64) gin.HandlerFunc {
	store := memory.NewStore()
	rate := limiter.Rate{
		Period: period,
		Limit:  limit,
	}
	return mgin.NewMiddleware(limiter.New(store, rate))
}
```

```go
func TestSessions_RateLimited(t *testing.T) {
	t.Parallel()

	ctx := t.Context()
	app := cltest.NewApplicationEVMDisabled(t)
	require.NoError(t, app.Start(ctx))

	router := web.Router(t, app, nil)
	ts := httptest.NewServer(router)
	defer ts.Close()

	client := clhttptest.NewTestLocalOnlyHTTPClient()
	input := `{"email":"brute@force.com", "password": "wrongpassword"}`

	for range 5 {
		request, err := http.NewRequestWithContext(ctx, "POST", ts.URL+"/sessions", bytes.NewBufferString(input))
		require.NoError(t, err)

		resp, err := client.Do(request)
		require.NoError(t, err)
		assert.Equal(t, http.StatusUnauthorized, resp.StatusCode)
	}

	request, err := http.NewRequestWithContext(ctx, "POST", ts.URL+"/sessions", bytes.NewBufferString(input))
	require.NoError(t, err)

	resp, err := client.Do(request)
	require.NoError(t, err)
	assert.Equal(t, 429, resp.StatusCode)
}
```
