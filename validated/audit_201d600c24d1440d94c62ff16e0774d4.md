### Title
Unauthenticated pre-authorization TDH2 ciphertext/label validation enables CPU-cost DoS amplification and validation-oracle behavior - (File: core/capabilities/vault/gateway_vault_request_processor.go)

### Summary
`processCreateSecretsRequest` and `processUpdateSecretsRequest` call `p.validator.ValidateCreateSecretsRequest` / `ValidateUpdateSecretsRequest` — which perform full TDH2 ciphertext unmarshal/verify and label-matching against `publicKey` — before `p.authorizeAndStamp` ever invokes `p.authorizer.AuthorizeRequest`. This lets any caller reaching the gateway vault JSON-RPC pipeline force elliptic-curve TDH2 verification work and receive a validation-specific error, without holding a valid allowlist entry or JWT for the claimed owner.

### Finding Description
In `core/capabilities/vault/gateway_vault_request_processor.go`, `processCreateSecretsRequest` (lines 88-120) and `processUpdateSecretsRequest` (lines 122-154) unmarshal the request, then immediately call the validator: [1](#0-0) 

Only after this validation succeeds does `authorizeAndStamp` call `p.authorizer.AuthorizeRequest` (line 233). This ordering contradicts the file's own documented "pipeline invariant" comment, which states `ValidateStructureBeforeAuth → AuthorizeRequest`, but the actual validator (`ValidateCreateSecretsRequest`/`ValidateUpdateSecretsRequest`) does far more than structural checks — it decodes and cryptographically verifies each ciphertext via `EnsureRightLabelOnSecret` → `verifyEncryptedSecret` → `tdh2easy.Ciphertext.UnmarshalVerify`, which is a nontrivial pairing/elliptic-curve operation: [2](#0-1) 

and the label comparison: [3](#0-2) 

An attacker who can reach `HandleJSONRPCUserMessage`/`ProcessRequest` can submit a `CreateSecretsRequest`/`UpdateSecretsRequest` batch (up to the configured `MaxRequestBatchSizeLimiter` bound) with crafted hex ciphertexts. Each element triggers `hex.DecodeString` + `tdh2easy.Ciphertext.UnmarshalVerify`, all executed before any authorization/allowlist/JWT check runs. This is CPU cost incurred by an unauthorized caller, and is a real amplification vector since the cost is paid per-batch-item prior to any authentication gate.

Regarding the "oracle" angle: the distinguishable error text ("doesn't have owner as the label" vs. a generic verify failure) does reveal whether the attacker's forged ciphertext's embedded label matches `vaultutils.WorkflowOwnerToLabel(owner)` for the `owner` value the attacker themselves supplied in the request. Because `WorkflowOwnerToLabel` is a deterministic, publicly computable function of the (attacker-supplied) owner string — not a secret derived from the victim's actual encrypted data — this does not disclose any information about a victim's ciphertext content or correlate a candidate ciphertext to a genuine victim secret; it only tells the attacker whether their own local TDH2 encryption matches the expected label format for a public key/owner pair they already control the inputs to. So the meaningful, exploitable impact here is the pre-auth CPU cost, not a secret-disclosure oracle.

### Impact Explanation
Unauthenticated/unauthorized callers can force the gateway/node vault pipeline to perform batched TDH2 `UnmarshalVerify` cryptographic operations before authorization is checked. Because `AuthorizeRequest` (allowlist/JWT check, presumably cheaper) runs strictly after this crypto-heavy validation, an attacker can send large validation-failing batches repeatedly to consume CPU on gateway/vault nodes — a computational resource-exhaustion / DoS amplification vector reachable without any privilege, matching a "Denial of Service" class impact rather than a secret-disclosure class impact.

### Likelihood Explanation
Feasibility is high for the DoS-amplification portion: it requires no valid allowlist entry, JWT, or prior secret knowledge — only the ability to send `SecretsCreate`/`SecretsUpdate` JSON-RPC requests to the gateway with `publicKey` cached (`skipLabelValidation=false`), which is the normal operating state. The request can be repeated and batched up to `MaxRequestBatchSizeLimiter`, making it trivially repeatable. The secret-disclosure/oracle aspect has low real impact since the "leaked" comparison is against attacker-chosen, publicly-derivable data.

### Recommendation
Reorder the pipeline so `authorizer.AuthorizeRequest` (identity/allowlist/JWT check) runs before any cryptographically expensive validation (`EnsureRightLabelOnSecret`/`verifyEncryptedSecret`/`UnmarshalVerify`). Perform only cheap structural/size checks (nil checks, batch-size limits, hex well-formedness) pre-authorization, and defer TDH2 ciphertext verification until after the caller is confirmed authorized for the claimed owner — consistent with the documented pipeline invariant comment at the top of `gateway_vault_request_processor.go`.

### Proof of Concept
Unit test in `core/capabilities/vault` package:
1. Construct a `RequestValidator` with permissive limiters and a valid TDH2 `publicKey`.
2. Construct a `GatewayVaultRequestProcessor` with an `Authorizer` stub that always returns an authorization error (simulating an unauthorized/unauthenticated caller) and records whether `AuthorizeRequest` was invoked.
3. Call `processCreateSecretsRequest` with a `CreateSecretsRequest` containing an `EncryptedSecret` with `Id.Owner = "victim"` and a well-formed-but-mismatched-label TDH2 ciphertext.
4. Assert that:
   - The returned error originates from `ValidateCreateSecretsRequest` (contains "doesn't have owner as the label"), not from the authorizer stub's error.
   - The authorizer stub's `AuthorizeRequest` was never called (proving validation, including `UnmarshalVerify`, executed before authorization).
5. Optionally benchmark repeated calls with a large batch of invalid ciphertexts to demonstrate CPU cost incurred purely by unauthorized requests before rejection.

func EnsureRightLabelOnSecret(publicKey *tdh2easy.PublicKey, secret string, owner string) error {
	cipherText, err := verifyEncryptedSecret(publicKey, secret)
	if err != nil {
		return err
	}
	if cipherText == nil {
		return nil
	}
	if owner == "" {
		return errors.New("owner must not be empty for secret label verification")
	}

	expected := vaultutils.WorkflowOwnerToLabel(owner)
	secretLabel := cipherText.Label()
	if secretLabel == expected {
		return nil
	}

	return fmt.Errorf("secret label [%s] does not match workflow owner label [%s]",
		hex.EncodeToString(secretLabel[:]), hex.EncodeToString(expected[:]))
}
```

func verifyEncryptedSecret(publicKey *tdh2easy.PublicKey, secret string) (*tdh2easy.Ciphertext, error) {
	cipherBytes, err := hex.DecodeString(secret)
	if err != nil {
		return nil, errors.New("failed to decode encrypted value:" + err.Error())
	}
	if publicKey == nil {
		// Public key can be nil if gateway cache isn't populated yet (immediately after gateway reboots).
		// Ok to not validate in such cases, since this validation also runs on Vault Nodes.
		return nil, nil
	}

	cipherText := &tdh2easy.Ciphertext{}
	if err := cipherText.UnmarshalVerify(cipherBytes, publicKey); err != nil {
		return nil, errors.New("failed to verify encrypted value:" + err.Error())
	}
	return cipherText, nil
```
