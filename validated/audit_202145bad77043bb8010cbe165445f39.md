### Title
Unbounded, unprivileged growth of `SecondaryIndex` reverse-index Vec causes O(n) / O(n²) CPU cost on every insert and on essential clean/purge - ([File: accounts-db/src/accounts_index/secondary.rs])

### Summary
`SecondaryIndex::insert` and `SecondaryIndex::remove_by_inner_key_if` are on the hot path of every account store and of `clean_accounts`'s dead-key purge. The reverse index maps an account pubkey (`inner_key`) to a `Vec<Pubkey>` of the secondary keys (mint/owner) it has ever been indexed under, and the code explicitly assumes this fan-out is "rare" so it is a linearly-scanned `Vec` rather than a `HashSet`. [1](#0-0) 

### Finding Description
`SecondaryIndex::insert` deduplicates by doing a linear `outer_keys.contains(key)` scan of the pubkey's reverse-index `Vec` before pushing a new entry, and only skips growth if the exact same outer key was already recorded: [2](#0-1) 

This is reachable by any unprivileged user through `update_secondary_indexes`, which is invoked on every store for accounts owned by the SPL Token program(s) and indexes them by their `mint`/`owner` fields read straight out of account data: [3](#0-2) [4](#0-3) 

Because a user fully controls the lifecycle of their own token accounts (create → initialize with mint A → close → recreate at the same pubkey → initialize with a different mint B → close → ...), they can drive many *distinct* mint/owner values through the same account pubkey before that pubkey is ever rooted and cleaned. Each distinct value is a cache miss in the `outer_keys.contains(key)` check, so it is pushed onto the `Vec`, making the reverse-index entry for that pubkey grow without bound and turning subsequent inserts into O(n) (and the whole sequence into O(n²)) work under the entry's write lock.

This same unbounded `Vec` is later walked during garbage collection: `remove_by_inner_key_if` (called from `clean_accounts`'s dead-key handling path via `handle_dead_keys` → `purge_secondary_indexes_for_dead_keys`) drains the entire `Vec` and, for every element, calls `remove_index_entries`, which itself does an inner-key removal against the corresponding forward-index entry: [5](#0-4) [6](#0-5) 

`clean_accounts` is the essential AccountsDb garbage-collection routine that reclaims dead storages and bounds disk/index growth for the whole validator, not just for the attacker's own accounts. [7](#0-6) 

### Impact Explanation
An attacker who repeatedly recreates a token account with a fresh mint/owner value before it is rooted can inflate a single reverse-index `Vec` arbitrarily. Every subsequent secondary-index insert for that same account pubkey degrades to O(n) (contains-scan) work while holding the reverse-index entry's write lock, and eventually a `clean_accounts` pass must drain and process the entire bloated `Vec` while holding that same lock, imposing disproportionate CPU cost on `clean_accounts` and stalling secondary-index maintenance for that pubkey and any indexed mint/owner keys concurrently trying to insert/remove. Since `clean_accounts` is a shared background maintenance task, this degrades the accounts-db's bookkeeping throughput for the whole node rather than only for the attacker, mirroring the Convex `extraRewards` DoS pattern: cheap, unbounded, attacker-controlled growth of a structure that a subsequent essential maintenance operation is forced to fully traverse.

### Likelihood Explanation
Likelihood is limited by practical constraints: SPL Token account creation/closing/re-initialization requires rent-exempt lamports and transaction fees for each cycle, and secondary indexes (`--account-index`) are opt-in and not enabled by default on most validators/RPC nodes. Where enabled (typically to support `getProgramAccounts` by mint/owner), an attacker with modest funds can automate many create/close/reinit cycles targeting a small number of pubkeys within a short window before roots/clean catch up, since the growth check (`outer_keys.contains`) has no configured cap.

### Recommendation
- Cap the number of distinct outer keys tracked per `inner_key` in `SecondaryIndex::reverse_index`, or switch the reverse-index entry from `Vec<Pubkey>` to a `HashSet<Pubkey>` to make membership checks O(1) instead of O(n), removing the "rare fan-out" assumption.
- Consider evicting/collapsing stale reverse-index entries for unrooted pubkeys more eagerly (e.g., on each store, rather than only at `clean_accounts`), so bloat cannot accumulate across many unrooted mutations of the same account before a root/clean cycle occurs.
- Add a metric/alert on `SecondaryIndex` reverse-index entry length so operators running secondary indexes can detect abuse.

### Proof of Concept
Not directly executable from the indexed context (would require constructing sequential SPL Token `InitializeAccount`/`CloseAccount` instructions repeatedly for the same account pubkey with distinct mints, feeding `AccountsDb::update_secondary_indexes` before any root/clean occurs, and observing `SecondaryIndex::reverse_index.get(&pubkey)`'s `Vec` length grow unbounded along with rising `insert`/`remove_by_inner_key_if` latency). This would need to be validated by an environment capable of running a validator/test harness, which is outside the scope of this read-only code search.

        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));

            outer_keys.push(*key);
