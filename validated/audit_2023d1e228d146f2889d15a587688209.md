## Title
Front-running/premature execution of a `SignedDelegateAction` permanently burns its nonce, permanently DoS'ing the user's intended meta-transaction - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEP-366 meta-transactions are designed so that a `SignedDelegateAction` produced off-chain by a user can be submitted on-chain by **any** relayer, since the payload is fully signed and self-authorizing. Anyone in possession of a broadcasted `SignedDelegateAction` (shared with multiple relayer services, seen via a relayer's public API, or observed before its intended relayer's transaction lands) can wrap it in their own transaction and submit it first. Because the access-key nonce for the delegate action is consumed and permanently persisted the moment `apply_delegate_action`/`validate_delegate_action_key` runs — *before* the inner actions are executed in their own, later, receipt — an unprivileged third party can force premature or unfavorable execution of the delegate action, irreversibly burning its nonce and permanently denying the user's originally intended meta-transaction, exactly mirroring the reported `checkOrder`-style nonce-griefing DoS.

### Finding Description
`apply_delegate_action` verifies the delegate's signature/expiry and then calls `validate_delegate_action_key`, which checks and immediately commits the new nonce via `set_access_key`/`set_gas_key_nonce`: [1](#0-0) 

This nonce commit happens **before** the inner actions are actually executed — those are packaged into a brand-new `Receipt` that is only appended to `result.new_receipts` and processed independently, potentially on a different shard and in a later block: [2](#0-1) [3](#0-2) 

Because these are two separate receipts with separate commit/rollback boundaries, a later failure of the inner-action receipt (wrong timing, stale contract state, expired conditions, etc.) can never roll back the nonce update that already succeeded when the `Delegate`/`DelegateV2` action itself was applied. The nonce check itself is a strict, one-shot monotonic comparison with no notion of "intended relayer": [4](#0-3) 

Since `DelegateAction`/`SignedDelegateAction` carries no restriction on which account may act as the relayer — any account can wrap it in a transaction as the signer (the design intent of meta-transactions, described in the architecture docs) — a malicious actor who obtains a copy of the signed payload can submit it themselves ahead of, or instead of, the user's intended relayer: [5](#0-4) 

Existing tests confirm the nonce update is unconditional and one-shot: replaying (or resubmitting) the same `SignedDelegateAction`/gas-key delegate a second time always fails with `DelegateActionInvalidNonce`, with no path to reuse or reset that nonce: [6](#0-5) [7](#0-6) 

The comment in the code even acknowledges the relayer bears execution risk but not that the sender's nonce is irrevocably spent regardless of the outcome of the inner action: [8](#0-7) 

### Impact Explanation
An unprivileged actor who intercepts a broadcasted/shared `SignedDelegateAction` can wrap and submit it via their own account at an unfavorable moment (e.g. before an intended precondition is met, after intentionally altering receiver-side state, or simply racing the legitimate relayer with a transaction they know will make the inner action fail on the receiver shard). Because the nonce commit and inner-action execution are decoupled into separate receipts, the sender's access key (or gas key) nonce is consumed permanently even though the user's actual intended action never executes successfully. Since the user cannot re-issue the same nonce (a new `DelegateAction` requires a strictly higher nonce that only the original signer's private key can produce, and if the delegate action represented a one-time, time-bounded authorization, e.g., an auction bid, claim, or liquidation-style action, there is no recovery), this results in permanent denial of the user's authorized transaction — a direct meta-transaction DoS analogous to the reported `checkOrder` nonce-griefing bug.

### Likelihood Explanation
Likelihood is realistic given the explicit design of NEP-366: relaying is permissionless by construction, and `SignedDelegateAction` payloads are meant to be passed to relayer services (which may be public, shared, or observable via mempool/gossip before inclusion). No signature or authorization from the sender is required to submit an already-signed delegate action, so any party with access to the bytes can act.

### Recommendation
Consider adding a mechanism that lets the relayer/sender bind the delegate action's on-chain nonce consumption to successful completion of the inner actions (e.g., only commit the nonce update after the inner receipt succeeds, or provide an explicit relayer-authorization/allow-list field), and/or make nonce-burning atomic with the inner action outcome so that failed/mistimed delivery does not permanently forfeit the sender's one-time authorization.

### Proof of Concept
1. Alice signs a `DelegateAction` (nonce N) intended for relayer R to submit only once condition C holds on the receiver contract.
2. Attacker M obtains the `SignedDelegateAction` bytes (e.g., from a public relayer pool or by observing R's transaction before inclusion).
3. M wraps the same bytes in M's own transaction and submits it earlier, while condition C does not hold, so the inner `FunctionCall` in the new receipt created by `apply_delegate_action` (`runtime/runtime/src/actions.rs:499-513`) fails.
4. `validate_delegate_action_key` has already advanced/committed the access key's nonce to N (`runtime/runtime/src/actions.rs:729-746`) as part of M's transaction succeeding at the `Delegate` action level, regardless of the later receipt's failure.
5. When R subsequently submits Alice's original `SignedDelegateAction` (nonce N) once condition C holds, it is rejected with `DelegateActionInvalidNonce` (as demonstrated by `test_validate_delegate_action_key_update_nonce`, `runtime/runtime/src/actions.rs:1605-1621`), permanently denying Alice's intended action.

**File:** docs/architecture/how/meta-tx.md (L40-52)
```markdown
With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.

On chain, the `SignedDelegateAction` inside the transaction is converted to an
action receipt with the same `SignedDelegateAction` on the relayer's shard. The
receipt is forwarded to the account from `Alice`, which will unpacked the
`SignedDelegateAction` and verify that it is signed by Alice with a valid Nonce
etc. If all checks are successful, a new action receipt with the inner actions
as body is sent to `FT`. There, the `ft_transfer` call finally executes.
```
