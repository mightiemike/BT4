## Title
Anyone can permanently claim the `BOOTSTRAP` declare fast-path and declare arbitrary classes without fee, nonce, or `__validate_declare__` checks - (File: `crates/starknet_api/src/executable_transaction.rs`, `crates/blockifier/src/transaction/account_transaction.rs`, `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo`)

## Summary
Both the Rust blockifier and the Starknet OS Cairo code contain a special "bootstrap declare" fast-path: a `Declare` V3 transaction whose `sender_address == bootstrap_address()` (the ASCII literal `'BOOTSTRAP'`, a plain, non-account, non-hash-derived `ContractAddress`), `nonce == 0`, and `charge_fee == false` (equivalently, `max_possible_fee == 0` on the OS side) skips `__validate_declare__`, skips the nonce increment, and skips the fee charge entirely — it only performs the class declaration. This mirrors the reported governance bug pattern: a check ("is this the legitimate bootstrap flow?") is gated on a state condition (`nonce == 0`, no fee enforced) that is trivially satisfiable by *anyone*, not only by the intended one-time genesis process, because `bootstrap_address()` is a fixed, publicly known constant with no signature/ownership binding and no on-chain deployed account guarding it.

## Finding Description
`DeclareTransaction::bootstrap_address()` returns a hardcoded, publicly known constant address (`ContractAddress::from(0x424f4f545354524150_u128)`, i.e., the ASCII bytes for `"BOOTSTRAP"`): [1](#0-0) 

`is_bootstrap_declare` decides whether to take the bypass path purely from transaction-supplied fields — `sender_address == bootstrap_address()`, `nonce == 0`, and the caller-controlled `charge_fee` flag — with no cryptographic signature check, no restriction to a genesis/first-block context, and no check that this flow has not already been used: [2](#0-1) 

In the blockifier execution path, when `is_bootstrap_declare` returns true, the transaction is executed directly via `run_execute`, entirely skipping `perform_pre_validation_stage` (nonce/fee checks) and the account's `__validate_declare__` entry point: [3](#0-2) 

The same logic is duplicated in the Starknet OS Cairo program, which checks `sender_address == 'BOOTSTRAP' and tx_info.nonce == 0 and tx_info.version == 3` together with `max_possible_fee == 0`, and if true, directly writes the class declaration into `contract_class_changes` and returns, bypassing `check_and_increment_nonce`, `__validate_declare__`, and `charge_fee`: [4](#0-3) 

Because `bootstrap_address()` is not an address derived from a deployed account contract (no `__validate_declare__` implementation is ever invoked for it, and no code/state exists there), and because the nonce at this address is always read as `0` from an uninitialized state entry, **any external tx sender** can construct a `Declare` V3 transaction with `sender_address = 0x424f4f545354524150`, `nonce = 0`, and zero/near-zero resource bounds (`charge_fee = false` is derived from `enforce_fee`, which is influenced by resource bounds/version), and the transaction will:
- Skip nonce enforcement (there is no nonce state tied to a real account to prevent replays/collisions across many attacker-chosen class hashes).
- Skip fee charging.
- Skip the account-contract `__validate__` gate entirely.
- Directly write an attacker-chosen `class_hash -> compiled_class_hash` mapping into global contract class state, protected only by the `prev_value == 0` idempotency guard (i.e., it succeeds once per unique class hash and is otherwise a free, ungated "declare" primitive with no signer requirement).

This is analogous to the reported Olympus Governance bug: a designed-for-bootstrap check ("no votes minted yet" / "system not yet has real state at this address") is expressed as a state predicate (`nonce == 0`, "no signature/no fee required") that remains permanently, unconditionally true for this specific address, so the "trusted-only" fast path is actually reachable by an unprivileged party for as long as the network exists — there is nothing that disables the bootstrap branch once the real genesis/bootstrap has completed, and nothing that restricts which class hashes can be declared through it or how many times it can be used (once per never-before-declared class hash).

## Impact Explanation
An attacker can use this path as a permanent, fee-free, unauthenticated class-declaration oracle:
- They can flood declared-class state with arbitrary attacker-controlled classes at zero cost (no fee charged, no resource-bound enforcement via the normal gateway `ZeroResourceBounds` check is guaranteed to apply to a transaction whose `charge_fee` derivation makes `enforce_fee` false), consuming block/bouncer capacity and state growth without paying for it — a resource-exhaustion/free-execution vector.
- More seriously, any code path in the system (mempool, batcher, indexers, or off-chain tooling) that treats "sender is `bootstrap_address()`" as an implicit trust signal that "this is the legitimate system-bootstrap declare" is fooled, since the condition is satisfiable by anyone at any time, not only during the intended one-time genesis bootstrap. Given the explicit code comment "This flow is used for the sequencer to bootstrap a new system," any downstream assumption that this sender/flow only ever occurs once, at genesis, under sequencer control, is false.
- This also breaks the intended "declare once" invariant tied specifically to the trusted bootstrap process: because the guard is on `sender_address == 'BOOTSTRAP' && nonce == 0` and there is no additional binding (no signature check is performed for this address, and it can never be deployed as a real account), an attacker can repeatedly submit differently-classed bootstrap-style declares (each with a fresh, never-declared `class_hash`) forever, since `nonce` never increments for this pseudo-account and is always read as `0`.

Given the described mempool test note — "Bootstrap declare txs are unique: they are sent from a special address and do not increment its nonce. As a result, they are not removed from the mempool upon successful execution" — the mempool/batcher's re-proposal-and-rejection lifecycle for this special sender further indicates the flow was designed assuming a single, sequencer-controlled instance, not an adversarial multi-user scenario. [5](#0-4) 

## Likelihood Explanation
High likelihood of reachability by an unprivileged transaction sender: the sender address, nonce, and resource-bounds/charge-fee fields of a `Declare` V3 transaction are all attacker-controlled inputs to the gateway/mempool/blockifier pipeline. No cryptographic proof of ownership of `bootstrap_address()` is required or possible (there is no private key — it is a fixed constant), and no state-based one-time-use enforcement of the "bootstrap flow" exists beyond the ordinary `prev_value == 0` class-uniqueness guard, which merely limits the payload to fresh class hashes, not to a single legitimate use of the whole bootstrap mechanism.

## Recommendation
- Remove the permanent bootstrap-declare fast path from the steady-state transaction-processing pipeline, or gate it behind an explicit, checked one-time system flag (e.g., a chain-level "bootstrap completed" storage flag checked and set atomically in the same execution, similar to fixing the reported governance bug by requiring a minimum "real" state before trusting the shortcut).
- If the bootstrap flow must remain available in the general transaction path (e.g., for resumable multi-tx bootstrap), bind it to an out-of-band authorization mechanism (e.g., a signature verifiable against a well-known bootstrap public key, or restrict it to block number / genesis-only context) rather than relying solely on a fixed, unauthenticated `sender_address` constant and an always-zero nonce.
- At minimum, ensure the gateway rejects `Declare` transactions targeting `bootstrap_address()` outside of the genesis/bootstrap block(s), and ensure the mempool cannot admit unlimited zero-fee bootstrap-style declares from arbitrary callers.

## Proof of Concept
1. Construct a `DeclareTransaction::V3` with:
   - `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`)
   - `nonce = Nonce(Felt::ZERO)`
   - `resource_bounds` such that `enforce_fee`/`charge_fee` evaluates to `false` (as used by the test helper `generate_bootstrap_declare`, which sets `resource_bounds: ValidResourceBounds::create_for_testing_no_fee_enforcement()`), see: [6](#0-5) 
   - a never-before-declared `class_hash` / `compiled_class_hash` pair chosen entirely by the attacker.
2. Submit this transaction to the gateway/mempool like any ordinary transaction (no signature over a real account is needed/verified for this address).
3. On execution, `AccountTransaction::execute_raw` detects `is_bootstrap_declare == true` and calls `run_execute` directly, bypassing `perform_pre_validation_stage` (fee/nonce checks) and `__validate_declare__`: [7](#0-6) 
4. The class is declared into state at zero cost, with no signature check, and the transaction can be repeated indefinitely with new class hashes since the address never accrues a real, incrementing nonce (existing test `test_bootstrap_declare` at `crates/blockifier/src/transaction/account_transactions_test.rs:905-991` demonstrates the exact mechanics of this successful, cost-free declaration using only the public `bootstrap_address()` constant).     // In this case, no account-related actions should be made besides the declaration.

        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

fn test_bootstrap_declare(
    block_context: BlockContext,
    #[case] declare_tx: DeclareTransaction,
    #[case] hash_version: HashVersion,
) {
    let class_info = calculate_class_info_for_testing(
        FeatureContract::Empty(CairoVersion::Cairo1(RunnableCairo1::Casm)).get_class(),
    );
    let contract_class = class_info.contract_class();
    let mut executable_declare = ApiExecutableDeclareTransaction {
        tx: declare_tx.clone(),
        tx_hash: TransactionHash::default(),
        class_info,
    };

    // Update compiled_class_hash in V3 declare txs to match the contract class with the given hash
    // version.
    if let DeclareTransaction::V3(tx) = &mut executable_declare.tx {
        if let ContractClass::V1((casm, _)) = &contract_class {
            tx.compiled_class_hash = casm.hash(&hash_version);
        }
    }
    let compiled_class_hash = executable_declare.tx.compiled_class_hash();
    let declare_account_tx = AccountTransaction::new_for_sequencing(
        ApiExecutableTransaction::Declare(executable_declare),
    );

    let mut state = CachedState::from(DictStateReader::default());
    let res = declare_account_tx.execute(&mut state, &block_context).unwrap();

    // Check declaration.
    assert_eq!(
        state.get_compiled_class_hash(declare_tx.class_hash()).unwrap(),
        compiled_class_hash
    );

    // Ensure the only change is the class declaration: no fees, nonce bump, etc.
    assert_eq!(res, TransactionExecutionInfo::default());
    assert_eq!(
        state.to_state_diff().unwrap().state_maps,
        StateMaps {
            compiled_class_hashes: HashMap::from([(declare_tx.class_hash(), compiled_class_hash)]),
            declared_contracts: HashMap::from([(declare_tx.class_hash(), true)]),
            ..Default::default()
        }
    );
}
