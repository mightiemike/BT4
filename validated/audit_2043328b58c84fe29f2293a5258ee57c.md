**Analysis:**

The premise conflates two unrelated pieces of code. `set_block` in `crates/evm/src/evm/handler.rs` is a trivial one-line setter that forwards the REVM block environment into the execution context — it has no connection to receipt roots or log blooms: [1](#0-0) 

The symbols cited as "carrying the value" (`TxInfo`, `CitreaChainExt`, `CitreaChain`, `CitreaCallExt`) are part of an unrelated subsystem that tracks per-transaction L1 fee/state-diff-size accounting, not receipt roots or log blooms: [2](#0-1) [3](#0-2) 

The actual construction of `receipts_root` and `logs_bloom` happens in `end_l2_block_hook` in `crates/evm/src/hooks.rs`, where both are computed directly from the same in-memory `receipts` slice that is subsequently persisted to storage in the same function call: [4](#0-3) [5](#0-4) 

Because the header's `receipts_root`/`logs_bloom` and the persisted receipts (`self.receipts.push(receipt, ...)`) are derived from the identical `receipts` vector within a single synchronous function, there is no code path by which the two could diverge — a reverting transaction with large state diffs still produces exactly one receipt entry in that same vector (attacker-controlled bytecode/calldata affects gas usage and diff-size fee accounting via `calc_diff_size`/`TxInfo`, not which receipts get included in the root computation). The equality "header's committed receipt root == root recomputed from executed receipts" holds trivially by construction, both before and after the described attacker action, since both sides are built from the same data in the same call.

No reachable divergence exists through `set_block`, `TxInfo`, `CitreaChainExt`, `CitreaChain`, or `CitreaCallExt` — none of these participate in receipt root or log bloom construction at all.
