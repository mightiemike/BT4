## Title
Blake2F precompile executes attacker-chosen `rounds` bounded only by feeLimit/energy accounting, with no protocol-level ceiling on VM occupancy time - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

## Summary
The `Blake2F.getEnergyForData` charges energy 1:1 with the attacker-supplied 32-bit `rounds` field, and `Blake2bfDigest.compress()` then executes a `for (long j = 0; j < rounds; ++j)` loop with no independent cap on `rounds` itself. No VMConfig flag, EnergyCost table, or Blake2F-specific bound restricts `rounds` beyond what the transaction's `feeLimit`/energy balance can pay for, matching the EIP-152 design intent but leaving CPU time proportional purely to paid energy.

## Finding Description
`Blake2F.getEnergyForData` parses the first 4 bytes of the 213-byte input as `rounds` and returns `rounds.longValue()` directly as the energy cost, with no maximum clamp: [1](#0-0) 

`execute()` then runs `Blake2bfMessageDigest.digest()`, whose `Blake2bfDigest.initialize()` reads the same unsigned 32-bit `rounds` value from the buffer without any bound check: [2](#0-1) 

and `compress()` loops exactly `rounds` times doing constant-time mix work per iteration: [3](#0-2) 

The call path from a public transaction is: `TriggerSmartContract` → VM `CALL`/`STATICCALL` opcode → `OperationActions.exeCall` → `Program.callToPrecompiledAddress`, which computes `requiredEnergy = contract.getEnergyForData(data)` and only checks that it does not exceed the energy the caller has allocated to the call (`msg.getEnergy()`), which is itself bounded by the overall transaction energy limit derived from `feeLimit`/energy price: [4](#0-3) 

This is the *only* gate: there is no `UPPER_BOUND`-style cap like the one present in `ModExp` (`UPPER_BOUND = 1024`) that rejects oversized inputs regardless of fee: [5](#0-4) 

No `VMConfig` flag or `EnergyCost.java` logic was found that clamps `rounds` for Blake2F specifically, and the `MAX_FEE_LIMIT` chain parameter (enforced elsewhere in `Wallet.java`/`DynamicPropertiesStore.java`/`ProposalUtil.java`) only limits the total fee/energy a transaction may spend, not the CPU-time-per-energy-unit ratio of any single opcode. Since `getEnergyForData` charges 1 energy unit per round (i.e., 1:1, the cheapest possible EIP-152-compliant pricing), the number of rounds an attacker can buy scales linearly with `MAX_FEE_LIMIT / energyPrice`, and each round performs a fixed amount of 64-bit ALU work with no other throttling (no periodic time-check/interrupt inside `compress()`'s loop, unlike `ModExp`'s `MUtil.checkCPUTimeForModExp()` call for large exponents).

## Impact Explanation
Because energy cost and CPU work are proportionally coupled by design (Blake2F's per-round pricing mirrors upstream go-ethereum/EIP-152), this is not a case of "underpriced" work relative to Blake2F's own cost model — it charges exactly proportional to work performed. However, unlike `ModExp`, `Blake2F` has no absolute upper bound on `rounds` independent of the fee balance, and no mid-loop CPU-time abort mechanism. If `MAX_FEE_LIMIT / energyPrice` yields a `rounds` value whose single-threaded wall-clock execution time is disproportionate to the network's block interval, a single transaction could occupy VM execution for a duration that degrades block production/propagation, since TVM execution is single-threaded per block.

## Likelihood Explanation
Feasible only if `allowTvmCompatibleEvm` is enabled (Blake2F precompile is TVM-Compatible-EVM-gated) and requires no privileged access — any account can submit a `TriggerSmartContract` with a crafted `rounds` value at the network's current `MAX_FEE_LIMIT` and energy price. The actual severity depends entirely on the concrete numeric values of `MAX_FEE_LIMIT` and the per-round wall-clock cost of `compress()`, which were not empirically measured in this review — whether the resulting worst-case rounds count produces execution time material relative to block interval is not verified in-repo and would require a benchmark/PoC to confirm quantitatively.

## Recommendation
Because whether this is materially exploitable depends on concrete constant values (`MAX_FEE_LIMIT`, current energy price, and measured `compress()` throughput) that were not found in the indexed code, add either: (a) an explicit `UPPER_BOUND`-style cap on `rounds` for Blake2F (as `ModExp` does for its inputs) independent of fee balance, or (b) a periodic CPU-time check inside the round loop (analogous to `MUtil.checkCPUTimeForModExp()`) that aborts/throws once a wall-clock budget is exceeded.
