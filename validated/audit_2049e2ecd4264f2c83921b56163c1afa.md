### Title
Missing range validation for `ENERGY_FEE` / `EXCHANGE_CREATE_FEE` committee proposals allows economic parameters to be set to unbounded/zero values, bricking or underpricing TVM execution - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator()` is the single choke-point that is supposed to bound every chain parameter that can be changed via a committee proposal, mirroring the "reasonable range bounds ... checked in the initialize()/setter functions" recommendation from the external report. Almost every `ProposalType` case in the switch enforces an explicit min/max, but `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` are the exception — they fall straight through to `break` with **no bounds check at all**, even though the enum comment documents an intended range of `[0, 100000000000]`.

### Finding Description
The validator dispatches on `ProposalType` and enforces bounds for virtually all economic parameters (e.g. `CREATE_ACCOUNT_FEE`, `TRANSACTION_FEE`, `ASSET_ISSUE_FEE`, `WITNESS_PAY_PER_BLOCK`, etc. are all capped at `LONG_VALUE = 100_000_000_000_000_000L` and rejected if negative): [1](#0-0) 

However, `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` are grouped into a no-op case that performs no validation whatsoever: [2](#0-1) 

The enum declaration itself documents the intended range that is never enforced: [3](#0-2) 

`ENERGY_FEE` is the price (in SUN) charged per unit of energy consumed by TVM (smart contract) execution — it is read and persisted through `DynamicPropertiesStore`/`getEnergyFee()`, consumed by `VMActuator` for fee calculation, and is exactly the kind of "committee/governance setting" the external report warns about (analogous to Auction `duration`/`timeBuffer` or Governor `quorumThresholdBps` in the Nouns Builder report — a numeric governance parameter with no sanity bound). Because `validator()` is the only gate invoked from `ProposalCreateActuator`/`ProposalApproveActuator` before a proposal's value is accepted and later applied, a proposal can set `ENERGY_FEE` to `0`, to a negative value, or to an astronomically large value with no revert.

### Impact Explanation
- Setting `ENERGY_FEE` to `0` makes TVM execution economically free: any unprivileged account can invoke arbitrary smart contract calls without paying for the energy they consume, i.e. classic **underpriced-public-work** — a vector for spamming full nodes with compute-heavy contract calls at no cost.
- Setting `ENERGY_FEE` to a negative value could corrupt fee/receipt accounting downstream (`ReceiptCapsule`, balance deduction logic), an **accounting/invalid-state** risk.
- Setting `ENERGY_FEE` to an extremely large value effectively halts all smart-contract execution network-wide (no account can afford to call any contract), a **halt/DoS** of TVM functionality analogous to the auction/proposal "bricking" described in the report. Because parameter changes are also only fixable by another committee proposal, and every contract call in the interim is either free or impossible, the impact is systemic and hits ordinary (unprivileged) users' ability to use the chain.
- `EXCHANGE_CREATE_FEE` shares the same unguarded path and affects the (Bancor-style) exchange-creation economics.

### Likelihood Explanation
Likelihood is low, matching the original report's assessment — it requires a super-representative committee proposal to pass, which is a low-frequency, semi-trusted governance action. However, unlike most other parameters in the same file, there is literally zero bounds enforcement for these two cases (not even a `< 0` check that every sibling case has), so a single misconfigured or malicious proposal is sufficient, with no compensating control anywhere else in the validation pipeline.

### Recommendation
Add explicit range validation for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` in `ProposalUtil.validator()`, consistent with the sibling cases and the documented range in the enum comment, e.g.:
```java
case ENERGY_FEE:
case EXCHANGE_CREATE_FEE: {
  if (value < 0 || value > LONG_VALUE) {
    throw new ContractValidateException(LONG_VALUE_ERROR);
  }
  break;
}
```
Additionally consider a stricter, economically sane upper bound (rather than the generic `LONG_VALUE` ceiling) so that `ENERGY_FEE` cannot be raised so high that ordinary users can no longer afford to execute any contract.

### Proof of Concept
1. A committee member/proposal creator submits a `ProposalCreateContract` with parameter code `11` (`ENERGY_FEE`) and value `0`. [3](#0-2) 
2. `ProposalCreateActuator`/`ProposalApproveActuator` call `ProposalUtil.validator(...)`, which reaches the `ENERGY_FEE`/`EXCHANGE_CREATE_FEE` case and simply `break`s without any check. [2](#0-1) 
3. Once approved by quorum, the value `0` (or an arbitrarily large/negative value) is written to `DynamicPropertiesStore` as the effective `ENERGY_FEE`.
4. All subsequent TVM executions are priced using this unvalidated value, either making contract calls free for every unprivileged user (spam/DoS via underpriced execution) or making them unaffordable for anyone (halting TVM usage network-wide) until a further corrective proposal passes.
