### Title
Webhook HMAC does not bind to X-Shopify-Shop-Domain, allowing cross-tenant offline session retrieval via replayed rawBody+HMAC with a spoofed shop header - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
`validateHmacFromRequestFactory` (in `packages/apps/shopify-api/lib/utils/hmac-validator.ts`) verifies the webhook HMAC over `rawBody` alone, never including the `X-Shopify-Shop-Domain` header in the signed data. `validateFactory` in `validate.ts` then independently reads the domain header via `checkWebhooksHeaders`/`checkEventsHeaders` and returns it as `check.domain`, which `authenticateWebhookFactory` passes directly into `ensureValidOfflineSession(params, check.domain)` to look up and return that shop's offline access-token session.

### Finding Description
The verification flow is:
1. `validateFactory` (`packages/apps/shopify-api/lib/webhooks/validate.ts:56-61`) calls `validateHmacFromRequestFactory(config)` which computes `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` — the signed input is *only* `rawBody* (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:189-197`).
2. Once `validHmacResult.valid` is `true`, `validateFactory` calls `checkWebhookHeaders(request.headers, webhookType)` (`validate.ts:73`), which in `checkWebhooksHeaders`/`checkEventsHeaders` (`validate.ts:99-146`, `148-203`) extracts the `domain` field straight from the request's `X-Shopify-Shop-Domain` header — a value that is never part of the HMAC computation.
3. `authenticateWebhookFactory` (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:35-52`) trusts `check.domain` unconditionally and calls `ensureValidOfflineSession(params, check.domain)`, which resolves an offline session ID via `api.session.getOfflineId(shop)` and loads it from session storage (`create-or-load-offline-session.ts:14-15`), then returns an authenticated `admin` API client backed by that shop's stored offline access token (`authenticate.ts:92-102`).

Because the domain header is decoupled from the cryptographic proof, any HTTP request bearing a previously valid `(rawBody, hmac)` pair combined with an attacker-chosen `X-Shopify-Shop-Domain` value will pass HMAC validation and cause the library to fetch and use the offline session of whatever shop is named in that header — not the shop that the payload/signature actually pertains to. Existing checks that fail to stop it:
- `safeCompare`/HMAC check only validates that `rawBody` was signed by the app's shared `apiSecretKey` — it says nothing about which shop that body belongs to.
- There is no cross-check anywhere in `validate.ts`, `hmac-validator.ts`, or `authenticate.ts` that the `domain` header is consistent with the shop the HMAC was originally generated for (e.g., by including domain in the signed payload, or by validating domain against a known active webhook subscription/shop record before session lookup).

### Impact Explanation
An attacker who can obtain one valid `(rawBody, hmac)` webhook pair for any shop on the app can cause the app to authenticate a request as a *different* shop (any other shop installed on the same app), causing `ensureValidOfflineSession` to retrieve and use that other shop's offline access token. This is a cross-tenant session/data access issue: the replayed payload (topic, resource IDs, JSON body from shop A) is processed under shop B's identity/session, and any handler logic keyed off `check.domain`/`session.shop` (e.g., writes, data association, admin API calls using shop B's access token) will act on behalf of shop B in response to attacker-controlled data. This corresponds to a cross-tenant/session-isolation bypass class of impact.

### Likelihood Explanation
Exploitability is fully gated by the stated precondition: the attacker must already possess a valid `rawBody`+`hmac` pair for some shop under the app (not derivable without knowledge of `apiSecretKey`, since the HMAC cannot be forged from scratch). Obtaining such a pair as a genuine unprivileged attacker is non-trivial in the standard Shopify delivery model, since webhooks are delivered directly from Shopify's infrastructure to the app's single registered endpoint URL and are not routed through or exposed to the merchant/shop owner by default; capturing one would typically require either the app echoing/logging webhook contents somewhere attacker-accessible (a host-app issue, out of scope) or some other disclosure channel. Given that precondition holds, however, the replay itself is trivial, fully repeatable, and requires no further secrets — the domain header can be freely set on the crafted POST request.

### Recommendation
Bind the shop identity cryptographically to the HMAC verification instead of trusting the `X-Shopify-Shop-Domain` header independently: e.g., verify that the resolved `domain`/`webhookId` corresponds to an actual, currently-registered webhook subscription (topic+shop+webhookId combination) before doing the session lookup, or otherwise ensure uniqueness/replay protection is enforced per (`shop`, `webhookId`) pair so a captured payload cannot be redirected to another tenant. At minimum, reject webhook deliveries where the `webhookId` has already been processed for a different shop, and do not treat the `domain` header as authoritative purely because the generic HMAC (which is shared across all shops on the app) is valid.

```ts
// packages/apps/shopify-api/lib/webhooks/__tests__/validate-cross-tenant.test.ts
import {createSHA256HMAC} from '../../../runtime/crypto';
import {HashFormat} from '../../../runtime/crypto/types';
import {validateFactory} from '../validate';
import {testConfig} from '../../__tests__/test-config'; // hypothetical shared test config helper

test('HMAC validity is independent of X-Shopify-Shop-Domain header', async () => {
  const config = testConfig({apiSecretKey: 'secret'});
  const rawBody = JSON.stringify({id: 12345, note: 'order for shop A'});
  const hmac = await createSHA256HMAC(config.apiSecretKey, rawBody, HashFormat.Base64);

  const validate = validateFactory(config);

  const result = await validate({
    rawBody,
    rawRequest: new Request('https://app.example.com/webhooks', {
      method: 'POST',
      headers: {
        'X-Shopify-Hmac-Sha256': hmac,
        'X-Shopify-Topic': 'orders/create',
        // attacker swaps the domain from shop-a to shop-b while keeping the same rawBody+hmac
        'X-Shopify-Shop-Domain': 'shop-b.myshopify.com',
        'X-Shopify-API-Version': '2024-01',
        'X-Shopify-Webhook-Id': 'wh_123',
      },
      body: rawBody,
    }),
  });

  expect(result.valid).toBe(true);
  // @ts-expect-error narrowed for test
  expect(result.domain).toBe('shop-b.myshopify.com'); // accepted despite hmac being computed without any shop binding
});
```

```typescript
export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);

        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}
```

```typescript
export async function createOrLoadOfflineSession(
  {api, config, logger}: BasicParams,
  shop: string,
) {
  if (config.distribution === AppDistribution.ShopifyAdmin) {
    logger.debug('Creating custom app session from configured access token', {
      shop,
    });
    return api.session.customAppSession(shop);
  } else {
    logger.debug('Loading offline session from session storage', {shop});
    const offlineSessionId = api.session.getOfflineId(shop);
    const session = await config.sessionStorage!.loadSession(offlineSessionId);

    return session;
  }
```
