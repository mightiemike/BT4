### Title
Unsigned-subtraction underflow in Bitcoin difficulty retarget inverts the clamp direction, letting a miner force the DA light client to a maliciously low difficulty target - (File: crates/bitcoin-da/src/verifier.rs)

### Summary
`calculate_new_difficulty` computes the epoch timespan with a plain unsigned `u32` subtraction, `last_timestamp - epoch_start_time`, without any checked/saturating arithmetic [1](#0-0) . If a miner crafts the final block of a 2016-block epoch so that its timestamp is *lower* than the epoch's start timestamp (only constrained by `verify_timestamp`, which merely requires `block_time > median(prev_11_timestamps)` and is otherwise independent of `epoch_start_time`) [2](#0-1) , the subtraction wraps to a value near `u32::MAX` instead of producing a small/negative timespan.

### Finding Description
The retarget logic is:
```
let mut actual_timespan = last_timestamp - epoch_start_time;
if actual_timespan < expected_epoch_timespan / 4 {
    actual_timespan = expected_epoch_timespan / 4;
} else if actual_timespan > expected_epoch_timespan * 4 {
    actual_timespan = expected_epoch_timespan * 4;
}
``` [3](#0-2) 

The correct Bitcoin semantics clamp a *too-short* epoch (attacker mined the epoch faster than expected, or here, with a manipulated regressive timestamp) to the **lower** bound `expected_epoch_timespan/4`, which *increases* difficulty. Because the subtraction is unsigned and unchecked, a negative real timespan (`last_timestamp < epoch_start_time`) wraps to a huge positive `u32` value, which the code instead clamps to the **upper** bound `expected_epoch_timespan*4` — the opposite branch, producing a *decrease* in difficulty (an easier target) exactly when the correct behavior demands the difficulty increase.

This function is invoked identically from all three difficulty-tracking verification paths — `verify_header_chain_mainnet`, `verify_header_chain_testnet4`, and `verify_header_chain_signet` [4](#0-3) [5](#0-4) [6](#0-5)  — and the resulting `current_target_bits` is persisted into `LatestDaState`, which is exactly the DA-integrity state consumed by the light-client circuit and stored on-disk/RPC as `StoredLatestDaState` / `LatestDaStateRpcResponse` [7](#0-6) [8](#0-7) . The wrong (too easy) `current_target_bits` is then fed as the expected difficulty for the *next* header, which `verify_target_hash` checks against [9](#0-8) .

Binding broken: the DA header chain's `current_target_bits` computed by this native/guest-shared code should equal the difficulty the real Bitcoin network actually enforces for the corresponding height; here it can diverge to a strictly-easier value, i.e. `computed_target(citrea) ≠ target(bitcoin_consensus)`, undermining the proof-of-work assumption the light client relies on for trusting header-chain-derived DA facts (a forged/weakened DA inclusion binding).

### Impact Explanation
Any party able to mine (even a single, low-probability) block at the exact boundary height `epoch_block == BLOCKS_PER_EPOCH - 1` with a timestamp lower than the recorded `epoch_start_time` — while still satisfying the median-of-11 rule — triggers the wraparound and forces the model to clamp to the *maximum easing* factor (`expected_epoch_timespan * 4`) instead of the correct *maximum tightening* factor. This lowers the target the verifier will subsequently accept for the whole next epoch, weakening the effective PoW threshold `verify_header_chain_common` enforces for all following blocks. Because Citrea's Bitcoin light client trusts this locally-computed target (not an independently re-derived Bitcoin consensus value) to gate which headers/blocks are treated as valid DA chain, this can let a low-hashrate miner (particularly practical against low-difficulty networks such as testnet4, whose retarget windows are far more volatile) get an easier-than-real target accepted into `LatestDaState`, silently diverging the light client's notion of DA-chain validity from actual Bitcoin consensus.

### Likelihood Explanation
Exploitation only requires mining ordinary, individually-valid blocks with a chosen timestamp at epoch boundaries — a capability any permissionless miner has (does not require majority hashrate, a sequencer/prover role, or any privileged key). It is a data-driven (attacker-chosen timestamp field) integer-arithmetic bug directly analogous to the `mempool.dat` malformed-time-field overflow class in the report: an externally-supplied time value drives unchecked arithmetic (`last_timestamp - epoch_start_time`) whose result then silently controls consensus-critical state, rather than crashing (which would at least be caught as a DoS, but is out of scope here — the real risk is the *silent wrong value*, not a panic).

### Recommendation
Replace the raw subtraction with a signed/checked computation, e.g. compute `last_timestamp as i64 - epoch_start_time as i64`, clamp on the signed value, and only then cast back to `u32`; or use `last_timestamp.checked_sub(epoch_start_time)` and treat `None` (i.e., `last_timestamp < epoch_start_time`) explicitly as "timespan below the minimum", forcing the `expected_epoch_timespan/4` clamp rather than letting it wrap into the opposite clamp branch.

### Proof of Concept
1. Track a `LatestDaState` where `epoch_start_time = T0` (timestamp of block `epoch_block == 0`).
2. At block height `epoch_block == BLOCKS_PER_EPOCH - 1`, mine (or on testnet4, wait for/produce) a block whose timestamp `T1 < T0`, while still satisfying `T1 > median(prev_11_timestamps)` so `verify_timestamp` passes [2](#0-1) .
3. `calculate_new_difficulty(T0, T1, ...)` computes `actual_timespan = T1 - T0` which underflows `u32`, producing a value ≫ `expected_epoch_timespan * 4` [1](#0-0) .
4. The clamp branch selects `expected_epoch_timespan * 4` (max easing) instead of the correct `expected_epoch_timespan / 4` (max tightening), producing a `current_target_bits` far easier than the real Bitcoin consensus target for that epoch [10](#0-9) .
5. This incorrect target is persisted in `LatestDaState.current_target_bits` and used to validate all subsequent block headers via `verify_target_hash` in `verify_header_chain_common` [9](#0-8) , letting an attacker-controlled, weaker-than-real-consensus header chain continue to pass DA verification.

/// Calculates the new difficulty target for the next epoch.
fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target_bits: u32,
    max_target: U256,
    expected_epoch_timespan: u32,
) -> [u8; 32] {
    // Step 1: Calculate the actual timespan of the epoch
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < expected_epoch_timespan / 4 {
        actual_timespan = expected_epoch_timespan / 4;
    } else if actual_timespan > expected_epoch_timespan * 4 {
        actual_timespan = expected_epoch_timespan * 4;
    }
    // Step 2: Calculate the new target
    let new_target_bytes = bits_to_target(current_target_bits);
    let mut new_target = U256::from_be_bytes(new_target_bytes)
        .wrapping_mul(&U256::from(actual_timespan))
        .wrapping_div(&U256::from(expected_epoch_timespan));
    // Step 3: Clamp the new target to the maximum target
    if new_target > max_target {
        new_target = max_target;
    }

    new_target.to_be_bytes()
