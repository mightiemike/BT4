## Title
Unwrap-Induced Chain Halt on Stale `GlobalContractDistribution` Receipt After Multiple Reshardings - ([File: runtime/runtime/src/congestion_control.rs])

## Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally `.unwrap()`s the result of `Receipt::receiver_shard_id`, which is documented to return an `Err` when a `GlobalContractDistribution` receipt's stale `target_shard` (from an old, retired shard layout) cannot be resolved to a shard in the current layout via `resolve_to_current_shard`. If a `GlobalContractDistribution` receipt sits in the delayed-receipt queue across two or more resharding events, this unwrap can panic during normal chunk application, halting the node that processes it.

## Finding Description
`Receipt::receiver_shard_id` for `ReceiptEnum::GlobalContractDistribution` explicitly handles the case where the receipt's `target_shard` no longer exists in the current shard layout by calling `shard_layout.resolve_to_current_shard(target_shard)`, and returns a structured `Err(EpochError::ShardingError(...))` if that resolution fails: [1](#0-0) 

However, the delayed-receipt queue's shard filter, which is exercised on every dequeue/peek during chunk application (including after resharding, per its own doc comment), does not propagate this `Err` — it unwraps it directly: [2](#0-1) 

The function's own comment acknowledges the resharding-induced staleness scenario it is meant to guard against ("it's possible for a chunk to have delayed receipts that technically belong to the sibling shard before a resharding event"), but the `.unwrap()` converts any resolution failure into a hard panic rather than a handled error. This function is called from both `pop` (used while draining the delayed queue during `apply_chunk`/`process_receipts`) and `peek_iter`.

A regression/exploit-style test in the repository directly targets this code path: it deploys a global contract (creating a `GlobalContractDistribution` receipt with `target_shard` pointing at the shard containing the deploying account), then forces two sequential dynamic-resharding events on that very shard while saturating compute so the receipt is pushed into, and kept in, the delayed-receipt queue across both reshardings. The test's own comments state the expected failure mode plainly: [3](#0-2) 

Whether `resolve_to_current_shard` is able to walk the full split lineage across *two* resharding generations (not just one parent→child hop) determines whether this specific panic is currently reachable in this tree; I was not able to fully confirm the multi-generation lineage-walking behavior of `resolve_to_current_shard` (`core/primitives/src/shard_layout/v3.rs`) before running out of tool calls, so this should be verified by tracing that function's implementation and its use of the shard-split history structures (`get_parent_shard_id`/`get_children_shards_ids`) before treating this as fully proven. Regardless of that open question, the underlying design flaw is clear and independently verifiable from the code shown above: `receipt_filter_fn` treats a documented, reachable `Err` variant of `receiver_shard_id` as infallible.

## Impact Explanation
If reachable, this is a transaction-triggered halt: any account can submit a `DeployGlobalContract` action (an ordinary, unprivileged transaction) to create a `GlobalContractDistribution` receipt. If congestion (attacker-inducible via compute-saturating transactions on the target shard, as the test does with `burn_gas_raw`) keeps that receipt delayed across the shard undergoing resharding twice, every honest validator that eventually dequeues the receipt during normal chunk application will panic and crash, since `receipt_filter_fn` is invoked deterministically as part of consensus-critical state transition logic. Because this would trigger consistently on every node processing the same delayed queue at the same point, it produces a chain-wide halt rather than a localized fork — squarely within the "transaction-triggered halt" impact category.

## Likelihood Explanation
Exploitation requires: (1) deploying a global contract from an account in a shard, (2) that shard undergoing two resharding events while the distribution receipt remains delayed, and (3) an attacker sustaining congestion on that shard to keep the receipt in the delayed queue through both reshardings. Resharding is normally triggered by validator/protocol-level thresholds (e.g., shard memory usage) rather than being directly attacker-controlled, which raises the bar for a real-world attacker versus the test's use of a forced `DynamicReshardingConfig`. This makes exploitation timing-dependent and non-trivial, but not implausible on a live network with dynamic resharding enabled and sustained congestion, especially since global contract deployment and heavy compute transactions are both ordinary, permissionless actions.

## Recommendation
- In `DelayedReceiptQueueWrapper::receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`), propagate the `Result` from `receiver_shard_id` instead of unwrapping it, and have `pop`/`peek_iter` surface a proper `RuntimeError`/`StorageInconsistentState` so a stale receipt fails the chunk gracefully (or is retried/migrated) instead of panicking the process.
- Audit all other call sites of `Receipt::receiver_shard_id` for the same unwrap-on-Err pattern, since the function is explicitly documented to be fallible for `GlobalContractDistribution` receipts after resharding.
- Verify (and, if necessary, fix) that `ShardLayout::resolve_to_current_shard` can walk an arbitrary-depth split lineage, not just a single generation, so genuinely valid stale receipts resolve correctly across multiple reshardings rather than only being "handled" by not crashing.

## Proof of Concept
The existing test in the repository is effectively the PoC for the vulnerable code path; it should be run under the exact protocol version where `resolve_to_current_shard` is confirmed not to walk multi-generation lineage: [4](#0-3) 

Conceptually:
1. Deploy a global contract from account `A` on shard `S_A` (`DeployGlobalContract` action), creating a `GlobalContractDistribution` receipt targeting `S_A`.
2. Flood `S_A` with compute-heavy transactions (e.g., repeated high-gas `FunctionCall`s) every block so the distribution receipt is pushed into, and stays in, the delayed-receipt queue.
3. Force/await two sequential resharding events that split `S_A` (and its child) while the receipt remains delayed.
4. Stop flooding and let the delayed queue drain; when the runtime dequeues the stale receipt, `receipt_filter_fn` calls `receiver_shard_id`, which (if the target shard cannot be resolved through two generations of splits) returns `Err`, and the `.unwrap()` panics, crashing every node that reaches this point in the state transition — halting the chain.

    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
