## Title
Dynamic Energy Factor for smart contracts can be cheaply inflated to its maximum, causing a persistent energy-fee DoS against any contract - (File: `chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java`)

### Summary
java-tron's dynamic energy mechanism (enabled via `ALLOW_DYNAMIC_ENERGY`) increases the effective energy cost of calling a smart contract if that contract's per-cycle energy usage exceeds a governance-set threshold, and decays the multiplier back down when usage stays low. The increase step is applied once per maintenance cycle as a fixed percentage regardless of *how much* the threshold was exceeded, mirroring the structural flaw in the reported `RAACMinter::updateEmissionRate()` bug: a cheap, barely-over-threshold nudge triggers the exact same rate change as genuine heavy load, and this can be repeated every cycle to drive the multiplier to its cap.

### Finding Description
`ContractStateCapsule.catchUpToCycle()` is the core state-transition function for a per-contract "energy factor" that multiplies energy cost for `CALL`-family opcodes and other operations executed against that contract: [1](#0-0) 

The check `getEnergyUsage() > threshold` is a boolean gate — as soon as a contract's accumulated energy usage in a cycle exceeds `DYNAMIC_ENERGY_THRESHOLD`, the factor is bumped by `increasePercent = 1 + increaseFactor/precisionFactor`, capped at `DYNAMIC_ENERGY_MAX_FACTOR`. It does not matter whether usage exceeded the threshold by 1% or 100000%; the increase applied is identical. This is analogous to `RAACMinter.calculateNewEmissionRate()`, where crossing `utilizationTarget` by any margin triggers the same fixed `adjustment = emissionRate * adjustmentFactor / 100` step.

This factor is read and applied on every VM execution against the contract: [2](#0-1) [3](#0-2) 

Governance parameters that control the magnitude/threshold are settable via chain proposals: [4](#0-3) [5](#0-4) 

Any unprivileged account can trigger a target smart contract at will (via an ordinary `TriggerSmartContract` broadcast transaction). By issuing calls whose cumulative energy usage in a maintenance cycle just exceeds `DYNAMIC_ENERGY_THRESHOLD` — a minimal, cheap action compared to what would be required to organically drive real usage that high — an attacker forces the same maximal per-cycle increase in `energyFactor` as legitimate heavy congestion would produce. Repeating this every maintenance cycle (`getCurrentCycleNumber()` increments once per maintenance period) escalates the target contract's `energyFactor` toward `DYNAMIC_ENERGY_MAX_FACTOR`, exactly as the RAAC attacker escalated `emissionRate` toward `maxEmissionRate` over repeated intervals.

### Impact Explanation
Once the factor is inflated, every subsequent legitimate caller of the targeted contract pays a `penalty` energy surcharge computed in `VM.play()`: [6](#0-5) 

This directly raises the real-world cost (in frozen/staked TRX-derived energy or TRX burned as fee) for all users of a targeted dApp/contract, and can push transactions that would otherwise succeed into "out of energy" failures — a griefing/DoS effect against a specific contract achieved by an unprivileged attacker at a cost far lower than the aggregate cost imposed on the victim's user base. This is analogous to the "rewards minting process is manipulated" impact in the original report, translated here to "resource/energy fee accounting is manipulated."

### Likelihood Explanation
This requires `ALLOW_DYNAMIC_ENERGY` to be active (a v4.7+ feature flag set via governance proposal) and requires the attacker to repeat the minimal-nudge call across multiple maintenance cycles, which is unprivileged, cheap, and fully automatable — comparable in effort/likelihood to the original PoC's 16-interval loop.

### Recommendation
Scale the per-cycle `energyFactor` increase (and possibly the decrease) proportionally to the magnitude by which `getEnergyUsage()` exceeds (or falls below) the threshold, rather than applying a fixed step for any crossing, so a marginal, cheaply engineered exceedance cannot produce the same effect as genuine heavy load. Consider also incorporating a magnitude-aware cap on how much the factor may move per cycle, analogous to capping rate changes on "the difference between utilization rates" as recommended in the source report.

### Proof of Concept
Conceptual PoC (would need to be run against a devnet with `ALLOW_DYNAMIC_ENERGY=1`, low `DYNAMIC_ENERGY_THRESHOLD`, and non-trivial `DYNAMIC_ENERGY_INCREASE_FACTOR`):
1. Deploy/target a smart contract `C`.
2. Each maintenance cycle, from any unprivileged account, send just enough `TriggerSmartContract` calls to `C` so that `ContractStateCapsule.getEnergyUsage()` for `C` exceeds `DYNAMIC_ENERGY_THRESHOLD` by a negligible margin.
3. Observe `energyFactor` for `C` (readable via the `ContractState` associated with `C`'s address in the contract-state store) increase by the same `increasePercent` each cycle regardless of the minimal exceedance.
4. Repeat across cycles; observe `energyFactor` converge to `DYNAMIC_ENERGY_MAX_FACTOR`.
5. Any subsequent legitimate call to `C` now incurs the `penalty` surcharge computed in `VM.play()`, raising its effective energy cost for all callers.

```java
  public boolean catchUpToCycle(
      long newCycle, long threshold, long increaseFactor, long maxFactor,
      boolean useStrictMath, boolean disableMath
  ) {
    long lastCycle = getUpdateCycle();

    // Updated within this cycle
    if (lastCycle == newCycle) {
      return false;
    }

    // Guard judge and uninitialized state
    if (lastCycle > newCycle || lastCycle == 0L) {
      reset(newCycle);
      return true;
    }

    final long precisionFactor = DYNAMIC_ENERGY_FACTOR_DECIMAL;

    // Increase the last cycle
    // fix the threshold = 0 caused incompatible
    if (getEnergyUsage() > threshold) {
      lastCycle += 1;
      double increasePercent = 1 + (double) increaseFactor / precisionFactor;
      this.contractState = ContractState.newBuilder()
          .setUpdateCycle(lastCycle)
          .setEnergyFactor(min(
              maxFactor,
              (long) ((getEnergyFactor() + precisionFactor) * increasePercent) - precisionFactor,
              disableMath))
          .build();
    }
```

```java
  public long updateContextContractFactor() {
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());

    if (contractStateCapsule == null) {
      contractStateCapsule = new ContractStateCapsule(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber());
      contractState.updateContractState(getContextAddress(), contractStateCapsule);
    } else {
      if (contractStateCapsule.catchUpToCycle(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber(),
          VMConfig.getDynamicEnergyThreshold(),
          VMConfig.getDynamicEnergyIncreaseFactor(),
          VMConfig.getDynamicEnergyMaxFactor(),
          VMConfig.allowStrictMath(),
          VMConfig.disableJavaLangMath())) {
        contractState.updateContractState(getContextAddress(), contractStateCapsule
        );
      }
    }
    contextContractFactor = contractStateCapsule.getEnergyFactor()
        + Constant.DYNAMIC_ENERGY_FACTOR_DECIMAL;
    return contextContractFactor;
  }
```
