### Title
Exchange pool IDs are assigned via a global sequential counter, making `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` vulnerable to blockchain re-orgs - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java)

### Summary
`ExchangeCreateActuator` assigns a new exchange pool's ID as `getLatestExchangeNum() + 1`, a purely sequential counter unrelated to the pool's contents (token pair, creator, balances). Any account may create an exchange without any privileged role check. Later interactions (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) reference the target exchange solely by this numeric ID. If a chain re-org reorders two `ExchangeCreateContract` transactions from different (unprivileged) accounts, the numeric ID that was previously assigned to "Pool A" (e.g. TRX/TokenX) can become assigned to a different "Pool B" (e.g. TRX/TokenY) after the re-org, causing a pending or subsequently-applied `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` to execute against the wrong token pair.

### Finding Description
In `ExchangeCreateActuator.execute`, the pool ID is derived purely from a global counter, not from the pool's content: [1](#0-0) 

This ID is persisted as the new `LATEST_EXCHANGE_NUM` and used as the storage key for the `ExchangeCapsule`: [2](#0-1) 

`ExchangeCreateActuator.doValidate` places no restriction on who can create an exchange beyond having an existing account and sufficient balance — no witness/owner privilege is required, so any two unrelated, unprivileged users' `ExchangeCreateContract` transactions can be reordered by a re-org: [3](#0-2) 

Downstream actuators identify the target exchange only by this numeric, content-independent ID. `ExchangeTransactionActuator` (a token swap that moves user funds) fetches the pool exclusively via `contract.getExchangeId()`: [4](#0-3) [5](#0-4) 

The same ID-only lookup pattern is used by `ExchangeInjectActuator` and `ExchangeWithdrawActuator` (`getExchangeId`), meaning all fund-moving exchange operations trust that a given numeric ID always refers to the same token pair over time.

### Impact Explanation
Consider: Alice creates Exchange A (TRX/TokenX) which is assigned ID 5. Bob, observing Exchange A, broadcasts an `ExchangeTransactionContract` with `exchangeId = 5` intending to swap into TokenX. Meanwhile Carol independently creates Exchange B (TRX/TokenY) in a competing/soon-to-be-discarded block. If a re-org drops Alice's `ExchangeCreateContract` and replaces it with Carol's (or reorders them), Exchange ID 5 now refers to Carol's TRX/TokenY pool. Bob's transaction — re-applied on the reorganized chain — executes against the wrong pool, swapping funds into an unintended token (TokenY) at Carol's pool's price/ratio instead of the pool Bob evaluated, with no built-in check tying the transaction to pool contents (only `firstTokenId`/`secondTokenId` membership and price expectation checks are performed at validate time based on whatever pool now sits at that ID). This causes real, unintended asset loss/exposure for ordinary (non-privileged) users, matching the report's "loss of funds due to acting on the wrong resource after re-org" impact class.

### Likelihood Explanation
Exchange creation is open to any account (no privileged role required), so many independent, unprivileged users can submit `ExchangeCreateContract` transactions in overlapping time windows, making ID-reassignment scenarios plausible whenever a chain re-org/fork-resolution reorders transaction inclusion — analogous to the original report's scenario where any address with posting rights could reorder publications. The severity depends on how often re-orgs occur in the deployed network and how quickly users act on freshly created exchanges, but the code path itself is fully unprivileged and reachable from ordinary broadcast transactions.

### Recommendation
Do not identify exchange pools (or other user-created, fund-bearing resources) purely by a monotonically increasing counter. Bind the ID to content-derived data (e.g., include a hash of the creator address, token IDs, and creation-time nonce/transaction hash in the pool's identifier or require callers to additionally supply and validate the expected token pair/creator when referencing an exchange by ID in `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`).

### Proof of Concept
1. Attacker/observer sees pending transaction `TX1`: `ExchangeCreateContract` from address A creating pool (TRX/TokenX) — expected to receive ID `N+1` where `N = getLatestExchangeNum()`.
2. A second transaction `TX2`: `ExchangeCreateContract` from address B creating pool (TRX/TokenY) is broadcast around the same time.
3. Victim broadcasts `TX3`: `ExchangeTransactionContract` with `exchangeId = N+1`, intending to trade against A's TRX/TokenX pool.
4. A re-org occurs such that `TX2` is included before `TX1` (or `TX1` is dropped/reordered), so ID `N+1` is now assigned to B's TRX/TokenY pool per `ExchangeCreateActuator.execute` (`long id = addExact(dynamicStore.getLatestExchangeNum(), 1)`).
5. `TX3` is replayed/re-applied on the reorganized chain; `ExchangeTransactionActuator.execute` fetches the exchange via `Commons.getExchangeStoreFinal(...).get(ByteArray.fromLong(exchangeTransactionContract.getExchangeId()))`, which now resolves to B's pool, causing the victim's funds to be swapped against an unintended token pair.
