## Summary

`deserialize_multi_key` in `multi_key.move` does not enforce any of the invariants that `new_multi_key_from_single_keys` enforces (non-empty key set, key-count ceiling, valid threshold). This lets a BCS-encoded `MultiKey` with zero public keys pass through deserialization and reach `to_authentication_key`, producing a syntactically valid 32-byte authentication key that can never be satisfied by any signature, since there are no keys to sign against.

## Finding Description

`new_multi_key_from_single_keys` explicitly asserts:
- `num_keys > 0` (`E_INVALID_MULTI_KEY_NO_KEYS`)
- `num_keys <= MAX_NUMBER_OF_PUBLIC_KEYS` (`E_INVALID_MULTI_KEY_TOO_MANY_KEYS`)
- `signatures_required <= num_keys` (`E_INVALID_MULTI_KEY_SIGNATURES_REQUIRED`) [1](#0-0) 

But `deserialize_multi_key`, the function used whenever a `MultiKey` is parsed from raw bytes (via `new_public_key_from_bytes`), performs none of these checks — it simply reads a vector of `AnyPublicKey`s and a `u8` threshold and constructs the struct directly: [2](#0-1) 

`new_public_key_from_bytes` only checks for trailing/extra bytes, not structural validity of the parsed content: [3](#0-2) 

`to_authentication_key` then unconditionally hashes whatever `MultiKey` struct it is given — including one with an empty `public_keys` vector — into a valid-looking authentication key: [4](#0-3) 

This confirms the deserialization path lacks the `E_INVALID_MULTI_KEY_NO_KEYS`-equivalent guard that the constructor path has, so a zero-key `MultiKey` blob can be deserialized and hashed without rejection.

## Impact Explanation

If this deserialized/hashed value is used as the new authentication key in an account's rotation flow (`account.move` consumes `AnyPublicKey`/`MultiKey` machinery for `rotate_authentication_key`-style operations, per the 28 matches for this construct in that file), an attacker or a buggy caller could commit an authentication key to on-chain account state that corresponds to a MultiKey with zero required/available signers. Such an account would become permanently unauthenticatable by any valid signature scheme, since the underlying `public_keys` vector is empty and no signature can ever satisfy a 0-of-0 (or ill-defined) multi-key policy. This breaks the invariant that every committed authentication key must be backed by at least one verifiable key, and results in a persisted, unsatisfiable authenticator in account state (effectively a permanently locked/bricked account, or a state entry that cannot be proven against by design).

I was not able to fully re-trace, within the remaining tool budget, the exact call path inside `account.move` that consumes `multi_key::new_public_key_from_bytes`/`to_authentication_key` results for the rotation write (i.e., confirm whether the specific rotation entry function forwards raw MultiKey bytes straight into this deserializer before writing `Account.authentication_key`). This should be verified directly in `aptos-move/framework/aptos-framework/sources/account/account.move` before treating the impact as fully proven end-to-end.

## Likelihood Explanation

High for the deserialization gap itself — it's a straightforward code-inspection finding: the constructor path and the deserialization path clearly diverge in validation despite representing the same logical object. Likelihood of a **full state-corruption exploit** depends on whether any privileged entry function accepts arbitrary MultiKey bytes for an authentication-key write without re-validating key count separately (not fully confirmed here).

## Recommendation

Add the same three assertions from `new_multi_key_from_single_keys` (non-empty, max-key-count, threshold-within-bounds) into `deserialize_multi_key`, so that no code path — direct construction or BCS deserialization — can produce a `MultiKey` value violating these invariants.

## Proof of Concept

1. Construct BCS bytes for a `MultiKey` with `public_keys = []` (empty vector, BCS length-prefix `0x00`) and any `signatures_required` byte (e.g., `0x00`).
2. Call `multi_key::new_public_key_from_bytes(bytes)` — this succeeds because `deserialize_multi_key` performs no key-count check, and `has_remaining` is false so the extra-bytes check also passes.
3. Call `to_authentication_key` on the resulting `MultiKey` — it returns a valid-looking 32-byte `sha3_256` hash with `SIGNATURE_SCHEME_ID = 3` appended, with no indication that zero keys back it.
4. If this key is written into account state via a rotation-style entry point, the account resource now stores an authentication key that can never be satisfied by any signature verification, corrupting the “authenticator must be satisfiable” invariant of account state. [5](#0-4)

    /// Parses the input bytes into a MultiKey public key.
    public fun new_public_key_from_bytes(bytes: vector<u8>): MultiKey {
        let stream = bcs_stream::new(bytes);
        let pk = deserialize_multi_key(&mut stream);
        assert!(!bcs_stream::has_remaining(&mut stream), error::invalid_argument(E_INVALID_MULTI_KEY_EXTRA_BYTES));
        pk
    }

    /// Creates a new MultiKey public key from a vector of single key public keys and a number representing the number of signatures required to authenticate a transaction.
    public fun new_multi_key_from_single_keys(single_keys: vector<single_key::AnyPublicKey>, signatures_required: u8): MultiKey {
        let num_keys = single_keys.length();
        assert!(
            num_keys > 0,
            error::invalid_argument(E_INVALID_MULTI_KEY_NO_KEYS)
        );
        assert!(
            num_keys <= MAX_NUMBER_OF_PUBLIC_KEYS,
            error::invalid_argument(E_INVALID_MULTI_KEY_TOO_MANY_KEYS)
        );
        assert!(
            (signatures_required as u64) <= num_keys,
            error::invalid_argument(E_INVALID_MULTI_KEY_SIGNATURES_REQUIRED)
        );
        MultiKey { public_keys: single_keys, signatures_required }
    }

    /// Deserializes a MultiKey public key from a BCS stream.
    public fun deserialize_multi_key(stream: &mut bcs_stream::BCSStream): MultiKey {
        let public_keys = bcs_stream::deserialize_vector(stream, |x| single_key::deserialize_any_public_key(x));
        let signatures_required = bcs_stream::deserialize_u8(stream);
        MultiKey { public_keys, signatures_required }
    }

    /// Returns the authentication key for a MultiKey public key.
    public fun to_authentication_key(self: &MultiKey): vector<u8> {
        let pk_bytes = bcs::to_bytes(self);
        pk_bytes.push_back(SIGNATURE_SCHEME_ID);
        hash::sha3_256(pk_bytes)
    }
