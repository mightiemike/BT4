## Title
Owner of an `AccountId`-mode global contract can silently rug-pull all accounts referencing it (no timelock on code updates) - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
The reported bug class is "the privileged party can instantly repoint a critical dependency (fee/exchange address) to a malicious value and immediately exploit users who already trusted the old value, with no timelock." The direct nearcore analog is `GlobalContractDeployMode::AccountId`: an account can deploy/redeploy WASM code under its own `AccountId` at any time, and every account that already referenced that code (via `UseGlobalContractAction` or a `DeterministicStateInitAction` pointing to it by `AccountId`) will transparently execute whatever code currently sits at that identifier on the next call — with no timelock, no re-consent, and no version pinning.

### Finding Description
`GlobalContractDeployMode::AccountId` deploys are explicitly documented as mutable: "This allows the owner to update the contract for all its users" [1](#0-0) . The deploy handler `action_deploy_global_contract` simply re-runs `initiate_distribution`, which derives the same `GlobalContractIdentifier::AccountId(account_id)` regardless of how many times it's redeployed [2](#0-1) . When the distribution receipt lands on a shard, `apply_distribution_current_shard` unconditionally overwrites the trie key for that identifier with the new code (gated only by a monotonically increasing nonce that prevents stale/duplicate overwrites, not that prevents legitimate newer overwrites) [3](#0-2) .

Any account that already executed `UseGlobalContractAction`/`AccountContract::GlobalByAccount(id)` — or was created via `DeterministicStateInitAction` with `code: GlobalContractIdentifier::AccountId(id)` — is bound only to the *identifier*, not to the actual bytes: `use_global_contract` stores `AccountContract::GlobalByAccount(id)` on the account [4](#0-3) , and the deterministic-account derivation hashes `DeterministicAccountStateInit` (which embeds only the `GlobalContractIdentifier`, not a code hash, when `AccountId` mode is used) [5](#0-4) . Deployment of the deterministic account itself calls `use_global_contract` to fetch "whatever code is live right now" [6](#0-5) .

This is functionally identical to the reported pattern: a party (the global-contract deploying account) controls a pointer (`exchange`/code reference) that downstream users have already committed funds/trust to, and can swap it to malicious logic at will, then trigger execution against victims who believed they were interacting with the previously reviewed/audited code. `test_global_contract_update` and `test_global_contract_nonce_prevents_stale_overwrite` in the test suite confirm this update-in-place semantics is by design and works exactly this way [7](#0-6) .

### Impact Explanation
Any account (including deterministic accounts that already hold a NEAR balance, per `test_contract_transfer_and_state_init_to_deterministic_account`) that references a global contract by `AccountId` is at the mercy of that account's controller. The controller can, after users have deposited funds or granted access expecting known code, redeploy new code that transfers out balances, mis-executes access-key logic, or drains storage — all executed under the *victim's own account* with the victim's balance, causing unauthorized value movement without any transaction from the victim. Because there is no timelock or code-hash pinning option enforced for `AccountId` mode, this can be done atomically in response to observing a victim's deposit/`UseGlobalContractAction` transaction (i.e., frontrun/backrun the moment of trust), mirroring the original report's "owner changes exchange, then calls gulp with 0 slippage" attack.

### Likelihood Explanation
The mechanism requires no protocol bug beyond intended design: any account with a global-contract deploy is trusted to run mutable code forever unless callers explicitly choose `CodeHash` mode instead. Application/wallet/relayer contracts that use `AccountId` mode for upgradability (as demonstrated in the wallet-contract and sharded-contract test helpers) are the ones exposed; users interacting with such contracts have no on-chain way to verify code hasn't changed between their trust decision and their transaction's execution.

### Recommendation
- Prefer `GlobalContractDeployMode::CodeHash` wherever downstream accounts hold value, since it is immutable by construction.
- For `AccountId`-mode contracts, provide a protocol- or convention-level delay/timelock between a `DeployGlobalContractAction` update and when it takes effect for already-bound accounts (e.g., allow currently-bound accounts a grace period to re-pin to a specific hash or opt out before the new code activates), and surface the current code hash so RPC/view calls can let integrators detect swaps before submitting value-bearing transactions.

### Proof of Concept
1. Account `owner` deploys benign global contract code `C1` under `AccountId` mode (`DeployGlobalContractAction{ deploy_mode: AccountId }`), as in `deploy_global_contract` in the test harness.
2. `victim` account issues `UseGlobalContractAction{ contract_identifier: AccountId(owner) }`, binding itself to whatever code lives at `owner`'s global-contract slot, or creates a deterministic account with `code: GlobalContractIdentifier::AccountId(owner)` and deposits funds into it, exactly as in `new_deterministic_account_with_data`/`test_contract_transfer_and_state_init_to_deterministic_account`.
3. `owner` submits a new `DeployGlobalContractAction{ code: C2 (malicious), deploy_mode: AccountId }`. Per `initiate_distribution`/`apply_distribution_current_shard`, this overwrites the trie entry for identifier `AccountId(owner)` on every shard, gated only by nonce freshness, not consent from `victim`.
4. `owner` (or anyone) triggers a call against `victim`'s account (or the deterministic account) which now runs `C2`, letting `owner` drain `victim`'s balance/storage — with no signature or approval from `victim` for the code swap itself.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

            global_contract_data.code().to_vec(),
            code_hash,

fn test_global_contract_update() {
    let mut env = GlobalContractsTestEnv::setup(Balance::from_near(1000));
    let use_accounts = [env.account_shard_0.clone(), env.account_shard_1.clone()];

    env.deploy_trivial_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        env.use_global_contract(
            account,
            GlobalContractIdentifier::AccountId(env.deploy_account.clone()),
        );

        // Currently deployed trivial contract doesn't have any methods,
        // so we expect any function call to fail with MethodNotFound error
        let call_tx = env.call_global_contract_tx(account.clone(), account.clone());
        let call_outcome = env.execute_tx(call_tx);
        assert_matches!(
            call_outcome.status,
            FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
                kind: ActionErrorKind::FunctionCallError(FunctionCallError::MethodResolveError(
                    MethodResolveError::MethodNotFound
                )),
                index: _
            }))
        );
    }

    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        // Function call should be successful after deploying rs contract
        // containing the function we call here
        env.assert_call_global_contract_success(account.clone(), account.clone());
    }
}
