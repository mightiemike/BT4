### Title
Per-token `Enabled` flag is never enforced anywhere in production code, allowing minting/bridging of tokens the admin has toggled off - (File: x/uregistry/keeper/keeper.go, x/uexecutor/keeper/handler.go, x/uexecutor/keeper/create_outbound.go)

### Summary
`uregistry.v1.TokenConfig.enabled` is documented as "Whether this token is enabled for minting/bridging" [1](#0-0) , but no keeper code path anywhere in the repository reads `TokenConfig.Enabled`/`GetEnabled()` to gate any mint, deposit, or outbound-creation logic. The only enable/disable gate actually enforced is the **chain-level** `ChainConfig.Enabled.{IsInboundEnabled,IsOutboundEnabled}` flag, which is a coarser, chain-wide switch, not the per-token one.

### Finding Description
This is the direct Push Chain analog of the external H-01 finding: a "toggle" meant to disable an asset for movement is set on-chain but the enforcement code that should check it is missing (H-01's asymmetry between `manage()` and `replenishTokens()` is here total omission rather than asymmetry).

Concretely:
- `TokenConfig.Enabled` is defined and settable via `MsgAddTokenConfig`/`MsgUpdateTokenConfig` (admin-only) [2](#0-1) [3](#0-2) .
- `GetTokenConfig` and `GetTokenConfigByPRC20`, the two lookup functions used throughout `x/uexecutor`, return the full `TokenConfig` struct (including `Enabled`) but never check the field themselves [4](#0-3) [5](#0-4) .
- Inbound minting (`depositPRC20`) fetches the token config and immediately calls the mint-equivalent `CallPRC20Deposit` with no `Enabled` check at all [6](#0-5) .
- Outbound creation (`BuildOutboundsFromReceipt`) checks `IsChainOutboundEnabled` (chain-level) and then calls `GetTokenConfigByPRC20`, but never inspects `tokenCfg.Enabled` before building the withdrawal `OutboundTx` [7](#0-6) .
- Grepping the entire repo for any use of the getter (`GetEnabled()`/`.Enabled`) on a `TokenConfig` value outside of generated protobuf/reflection code and tests returns zero hits in keeper/module logic — only `ChainConfig.Enabled` (a different type) is checked, in `VoteInbound` and `BuildOutboundsFromReceipt`/EVM hooks [8](#0-7) [9](#0-8) .

The README even documents `TokenConfigs` as "token whitelist by `chain:address`... with native representation, decimals, and liquidity cap" without any mention of the enabled flag being enforced [10](#0-9) , corroborating that the flag is effectively dead/unwired in the current implementation.

### Impact Explanation
If an admin disables a specific `TokenConfig` (e.g., in response to a compromised/exploited external token, a bridge incident, or to freeze a suspicious asset) expecting minting and withdrawal to stop for that asset, the system continues to:
- mint PRC20 representations on unprivileged user inbound votes reaching quorum (`VoteInbound` → `depositPRC20`), and
- create and eventually broadcast outbound withdrawals for that same disabled token (`BuildOutboundsFromReceipt`).

This breaks the accounting/registry invariant that a disabled token cannot be minted or bridged, directly enabling unauthorized mint and unauthorized release of funds for an asset the admin explicitly tried to block, with no privileged-actor assumption required on the attacker side (any unprivileged user submitting inbound/outbound-triggering transactions benefits from the bypass).

### Likelihood Explanation
High, mechanically: the check is simply absent from every reachable code path, so any ordinary inbound funds/payload flow for a "disabled" token config succeeds exactly as if it were enabled. The only friction is that this requires an admin to have actually toggled a token off in the first place (which is an expected, non-privileged-attacker-triggered admin action, and the resulting failure is on the honest-admin/user side, not requiring any adversarial control).

### Recommendation
Add explicit `TokenConfig.Enabled` checks in:
1. `depositPRC20` (`x/uexecutor/keeper/handler.go`) before calling `CallPRC20Deposit`, mirroring the `IsChainInboundEnabled` check already done in `VoteInbound`.
2. `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go`) after `GetTokenConfigByPRC20`, before building the `OutboundTx`, mirroring the `IsChainOutboundEnabled` check already present.
3. Any other mint/burn/transfer path in `x/uexecutor` that resolves a `TokenConfig` (e.g., `ExecutePayload`/CEA funds handling) should perform the same check.

### Proof of Concept
Unable to construct a runnable PoC transcript within the current investigation — this requires running the integration test harness (`test/integration/uexecutor/...`) to add a token config with `Enabled: false` and confirm `VoteInbound`/`BuildOutboundsFromReceipt` still succeed. Based on static analysis, the reasoning is:
1. Admin calls `MsgUpdateTokenConfig` setting `Enabled: false` for a given `chain:address` token [3](#0-2) .
2. A user submits the corresponding source-chain deposit; validators vote via `MsgVoteInbound`; `VoteInbound` only checks `IsChainInboundEnabled(sourceChain)`, not the token's `Enabled` field, so the ballot finalizes and `depositPRC20` mints PRC20 to the recipient regardless [8](#0-7) [6](#0-5) .
3. Symmetrically, a withdrawal of that same disabled-token PRC20 back to the external chain proceeds through `BuildOutboundsFromReceipt`, which only checks chain-level outbound enablement, not `tokenCfg.Enabled` [7](#0-6) .

Given the source index does not include a complete end-to-end test for this exact per-token-disabled scenario (only chain-level enable/disable tests were found, e.g. `test/integration/uexecutor/chain_enabled_test.go`), a Devin session with full repository/test-execution access would be needed to confirm this empirically by writing and running such an integration test.

// AddTokenConfig adds a new token configuration to the uregistry.
func (k Keeper) AddTokenConfig(ctx context.Context, tokenConfig *types.TokenConfig) error {
	// Ensure the chain exists
	if _, err := k.GetChainConfig(ctx, tokenConfig.Chain); err != nil {
		return fmt.Errorf("chain %s is not supported: %w", tokenConfig.Chain, err)
	}

	// More efficient check for existing token config
	storageKey := types.GetTokenConfigsStorageKey(tokenConfig.Chain, tokenConfig.Address)
	has, err := k.TokenConfigs.Has(ctx, storageKey)
	if err != nil {
		return err
	}
	if has {
		return fmt.Errorf("token config for %s on chain %s already exists", tokenConfig.Address, tokenConfig.Chain)
	}

	// Set the new token config
	if err := k.TokenConfigs.Set(ctx, storageKey, *tokenConfig); err != nil {
		return err
	}
	k.Logger().Info("token config added",
		"chain", tokenConfig.Chain,
		"token_address", tokenConfig.Address,
	)
	return nil

	)

// GetTokenConfigByPRC20 looks up a token config by PRC20 address via the
// PRC20Index (O(1)). Returns ErrNotFound if the registered chain doesn't match.
func (k Keeper) GetTokenConfigByPRC20(
	ctx context.Context,
	chain string,
	prc20Addr string,
) (types.TokenConfig, error) {

	if strings.TrimSpace(prc20Addr) == "" {
		return types.TokenConfig{}, fmt.Errorf("prc20 address is empty")
	}
	// Same canonical form as the index function, so any case variant hits the row.
	prc20Addr = canonicalPRC20(prc20Addr)

	// PRC20 addresses are globally unique by construction; MatchExact returns at most one.
	iter, err := k.TokenConfigs.Indexes.PRC20Index.MatchExact(ctx, prc20Addr)
	if err != nil {
		return types.TokenConfig{}, err
	}
	defer iter.Close()

	for ; iter.Valid(); iter.Next() {
		pk, err := iter.PrimaryKey()
		if err != nil {
			return types.TokenConfig{}, err
		}
		cfg, err := k.TokenConfigs.Get(ctx, pk)
		if err != nil {
			return types.TokenConfig{}, err
		}
		if cfg.Chain == chain {
			return cfg, nil
		}
	}

	return types.TokenConfig{}, collections.ErrNotFound
}

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
