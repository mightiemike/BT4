### Title
Incorrect compact-bits ("nBits") re-encoding in `target_to_bits` causes light client to reject legitimate Bitcoin epoch-boundary blocks - (File: crates/bitcoin-da/src/verifier.rs)

### Summary
`target_to_bits` re-implements Bitcoin Core's `arith_uint256::GetCompact()` used to encode a 256-bit target as the 32-bit "bits" field, but omits the sign-bit normalization step that Bitcoin Core performs whenever the mantissa's most significant byte has its high bit set. This produces a `bits` value that diverges from the one the real Bitcoin network actually mines under, for any epoch retarget where the new target's top mantissa byte is `>= 0x80`.

### Finding Description
`calculate_new_difficulty` computes the new 256-bit target following Bitcoin's retarget formula correctly (multiply by actual timespan, divide by expected timespan, clamp) [3](#0-2) . The resulting `[u8; 32]` big-endian target is then compacted back into the 32-bit `bits` header field by `target_to_bits`: [4](#0-3) 

Bitcoin Core's actual `GetCompact` implementation additionally checks whether the extracted 3-byte mantissa has its top bit set (`nCompact & 0x00800000`), because the "bits" encoding treats the mantissa as a sign-and-magnitude value. If the top bit is set, Bitcoin Core shifts the mantissa right by 8 bits and increments the exponent byte by one, to avoid an ambiguous "negative" encoding. Citrea's `target_to_bits` does not perform this check; it always takes the size derived purely from `target_u256.bits()` and copies out `target[size-1..=size+1]` verbatim, without shifting or bumping `size` when the extracted mantissa's high bit is set.

For any retargeted difficulty whose big-endian representation has this "sign-bit" condition, Citrea's re-encoding yields a `bits` value that Bitcoin Core would never produce for that exact 256-bit target — i.e. the native (Bitcoin miner/consensus) encoding and Citrea's guest/verifier encoding of the *same target* diverge, breaking the binding: `expected_bits (computed in verifier) == bits (as encoded by real Bitcoin consensus for the same target)`.

Because `expected_bits` is checked with strict equality against `block_header.bits()` at the first block of every new 2016-block epoch (mainnet), 5.5-hour signet epoch, or testnet4 epoch [5](#0-4) , [2](#0-1) , a legitimate, correctly-mined Bitcoin block that Bitcoin Core itself accepts can be rejected by Citrea's DA verifier as `InvalidBlockBits`, halting light-client-proof progression on an otherwise valid, canonical Bitcoin chain.

### Impact Explanation
This breaks the "honest nodes converging on an unproved root" / DA-header-chain-integrity boundary: the light client circuit's view of `LatestDaState.current_target_bits` can permanently diverge from the real Bitcoin chain at a retarget boundary, meaning the light-client proof chain cannot advance past a legitimate Bitcoin block, or would need a fork/incompatible target that no real Bitcoin block will ever satisfy, effectively halting light-client-proof generation for Citrea's Clementine bridge, which relies on the light-client state root for bridge-operator challenge resolution [6](#0-5) . This is a critical availability/consensus-divergence issue for the DA integrity binding, though it does not directly move funds by itself — its severity depends on whether it can be triggered on real mainnet/testnet4 target sequences.

### Likelihood Explanation
Likelihood is low-to-uncertain: the sign-bit-set condition on the mantissa's top byte occurs only for specific target values (~1/256 chance per retarget purely by mantissa distribution, ignoring drift correlations), and Bitcoin's actual historical difficulty sequence would need to hit this condition for this to manifest on a live network. It is a deterministic bug, not attacker-triggerable on demand (nobody controls Bitcoin's total hashrate to force a specific retarget outcome), so it is a latent consensus-divergence bug that would surface unpredictably as Bitcoin's difficulty evolves, rather than an actively exploitable path today. I was not able to fully confirm from the available index whether any past or near-future real Bitcoin difficulty adjustment hits this exact condition — this would require checking historical `nBits` values for a mantissa `>= 0x800000` prior to compaction, which is not verifiable purely from the code in this repository.

### Recommendation
Update `target_to_bits` to mirror Bitcoin Core's `GetCompact` exactly: after extracting the 3-byte mantissa, check if the highest bit (`0x80`) of the first mantissa byte is set; if so, shift the mantissa right by one byte (effectively re-deriving from `size+1`) and increment the exponent (`compact_target[0]`) by one, before final assembly.

### Proof of Concept
Conceptual (not independently executed given read-only access): choose a target value `T` whose big-endian bytes at the computed `size` boundary yield a mantissa with top bit set (e.g., top byte `0x80..0xFF`). Compute `target_to_bits(T)` via Citrea's implementation and compare against Bitcoin Core's `GetCompact()` for the same `T` (verifiable via `python-bitcoinlib` or Bitcoin Core's `arith_uint256::GetCompact`). The two encodings will differ by one in the exponent byte and by a factor of 256 in the mantissa's byte offset, demonstrating the divergence deterministically for any such target — this can then be forced into `calculate_new_difficulty`'s output by choosing `epoch_start_time`/`last_timestamp` such that the multiply-divide-clamp arithmetic lands on such a target.

/// Converts the big-endian target value to the little-endian `bits` field of a block header.
pub(crate) const fn target_to_bits(target: &[u8; 32]) -> u32 {
    let target_u256 = U256::from_be_slice(target);
    let target_bits = target_u256.bits();
    let size = (263 - target_bits) / 8;
    let mut compact_target = [0u8; 4];
    compact_target[0] = 33 - size as u8;
    compact_target[1] = target[size - 1_usize];
    compact_target[2] = target[size];
    compact_target[3] = target[size + 1_usize];
    u32::from_be_bytes(compact_target)
}

/// Calculates the new difficulty target for the next epoch.
fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target_bits: u32,
    max_target: U256,
    expected_epoch_timespan: u32,
) -> [u8; 32] {
    // Step 1: Calculate the actual timespan of the epoch
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < expected_epoch_timespan / 4 {
        actual_timespan = expected_epoch_timespan / 4;
    } else if actual_timespan > expected_epoch_timespan * 4 {
        actual_timespan = expected_epoch_timespan * 4;
    }
    // Step 2: Calculate the new target
    let new_target_bytes = bits_to_target(current_target_bits);
    let mut new_target = U256::from_be_bytes(new_target_bytes)
        .wrapping_mul(&U256::from(actual_timespan))
        .wrapping_div(&U256::from(expected_epoch_timespan));
    // Step 3: Clamp the new target to the maximum target
    if new_target > max_target {
        new_target = max_target;
    }

    new_target.to_be_bytes()
}

# The Light Client Circuit
This document describes the logic and structure of light client proofs, which allow a verifier to confirm that an L2 state committed to by the sequencer is valid, using information included in a DA (Data Availability) block. Each proof builds on the previous one, forming a verifiable chain of state transitions. Verifying a single proof attests that, for the given Bitcoin chain up to that DA block, the L2 state produced by the circuit is correct, verified, and consistent with the on-chain commitments.
