## Title
Replay-verify state root divergence undetected due to skipped checkpoint hash validation — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-data comparator used by replay/verification tooling to confirm that locally re-executed transaction output matches the transaction info recorded and proven in the archived ledger. The function explicitly skips comparing the state-checkpoint-related hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) between the locally computed `TransactionInfo` and the expected/archived one, as acknowledged by its own TODO comment. This means a state root divergence between local execution and the archived (authenticated) ledger will not be flagged as a mismatch by this check.

### Finding Description
`ensure_match_transaction_info` validates only `status`, `gas_used`, `write_set` (via `state_change_hash`), and `event_root_hash`: [1](#0-0) 

The comment inline states the gap directly: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [2](#0-1) 

This function is the sole verification step used by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes transactions from backup and calls `ensure_match_transaction_info` against the `expected_txn_infos` read from the backup/archive to detect divergence: [3](#0-2) 

Because the state-checkpoint hash comparison (which is the field that authenticates the Sparse-Merkle/Jellyfish state root, hot-state root, and native "position" state root against the transaction accumulator via the associated `TransactionInfo`) is never checked here, a divergence in the *state* produced by local execution versus the state committed/authenticated on-chain (e.g., due to a state-computation bug, a native module change, or corrupted archive/backup data reproduced identically in write-set/events but not in derived Merkle roots) is invisible to this tool.

### Impact Explanation
This breaks the state-proof integrity guarantee that replay/verification tooling is meant to enforce: verifying that a node's local VM execution over historical transactions reproduces the exact, authenticated ledger state. If the state root diverges (a hard-fork-class defect, storage schema bug, or corruption during restore/replay), `replay_on_archive` and any other caller of `ensure_match_transaction_info` (e.g. `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) will report success despite an actual state-root mismatch. This falls squarely under the state-integrity gate's "Wrong ... state proof accepted as valid" and "Hard-fork-only divergence during ... replay ... accepted" categories: consumers of replay-verify tooling (auditors, node operators validating archive integrity, and dev tooling used to validate protocol upgrades) get a false assurance that historical state is correctly reproduced.

### Likelihood Explanation
The gap is unconditional (not behind an unimplemented feature flag check inside the comparator itself — the checkpoint hashes are simply never compared), and it is on the only verification path exercised by the shipped `replay_on_archive` binary. Any real divergence between VM-computed state and the historical authenticated state (a legitimate concern this tool exists to catch) will silently pass. The likelihood of the underlying state divergence occurring is separate from this bug, but given that this is the last line of defense to catch such divergence, the missing check materially raises the risk that undetected state-root regressions ship or go unnoticed until a hard fork occurs in production.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()` (and, where applicable, `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`) between `self`-derived state and `txn_info`, gated appropriately behind the relevant on-chain feature checks (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) so the comparison is correct for both V0 and V1 `TransactionInfo` variants, before enabling/relying on this check for the trading-native rollout as the comment suggests.

### Proof of Concept
1. Take an archived backup where the recorded `TransactionInfo.state_checkpoint_hash` corresponds to a legitimate authenticated ledger state at some version.
2. Run `replay_on_archive` (`storage/db-tool/src/replay_on_archive.rs`) against a target DB using a VM/build that produces identical `write_set`, `events`, `gas_used`, and `status` for the replayed transactions, but a different derived state root (e.g. due to an unrelated state-computation defect not affecting the write set hash itself, such as an issue in Merkle-root aggregation, hot-state computation, or the "position" state subsystem).
3. `execute_and_verify` calls `ensure_match_transaction_info`, which passes because it never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`.
4. The tool reports zero failed transactions, i.e., "replay verified", despite the local ledger state diverging from the authenticated on-chain state.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
