### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant session/request forgery - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
The `shopify-api` webhook validator computes and checks the HMAC over the raw request **body only**, while the shop identity used for all downstream routing (`domain` header) is taken verbatim from an unsigned header and never bound to that HMAC. This is the same class of bug as the "double-entrypoint collateral token": two separate references are treated as one authenticated identity — the cryptographically-verified entity (the HMAC-signed body, keyed by the app's single shared `apiSecretKey`) and the entity actually used for authorization/session-selection (the `X-Shopify-Shop-Domain` header) are not the same value, and the code never checks that they are consistent.

### Finding Description
`validateHmacFromRequestFactory` only hashes `rawBody` against the app's `apiSecretKey` and compares it to the `hmac` header: [1](#0-0) 

`validateFactory` calls this body-only HMAC check, and only after it passes does it extract the `domain` header via `checkWebhookHeaders`/`checkWebhooksHeaders` — with no cryptographic linkage between the two: [2](#0-1) [3](#0-2) 

The `domain` field returned from validation is then used directly, unsanitized, to look up (and act on behalf of) the offline session/access token for that shop: [4](#0-3) [5](#0-4) 

Because Shopify apps use a single `apiSecretKey` shared across **every shop** that installs the app, and the HMAC digest is a function of body+secret only (not shop domain), any two webhook deliveries with identical bodies produce identical valid HMACs regardless of which shop they were originally destined for. A merchant who installs the app on their own store can capture a legitimate webhook delivery (body + valid `X-Shopify-Hmac-Sha256`) sent to their own endpoint, then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different (victim) shop that also has the app installed. The HMAC check still passes (it never inspected the domain), `check.domain` is the attacker-chosen victim shop, and `ensureValidOfflineSession(params, check.domain)` loads the victim's real offline session/access token, which is then handed to the webhook handler/`admin` client together with attacker-controlled body content.

### Impact Explanation
This enables cross-tenant request forgery: an unprivileged single merchant (their own shop) can cause the app to execute webhook-handler business logic against a *different* installed shop's session and access token, using attacker-crafted payload content of a topic they choose (as long as they can obtain one legitimate signed body/HMAC pair for that topic, e.g. from their own store's `app/uninstalled`, `orders/create`, `shop/update`, etc.). Depending on what the app's webhook handlers do (write to DB keyed by domain, call the Admin API using the loaded session, delete data, etc.), this can result in unauthorized cross-tenant data manipulation, forced session deletion for a victim (if replaying an `app/uninstalled`-shaped body), or corrupted per-shop state — all without ever compromising the API secret or performing a MITM.

### Likelihood Explanation
Likelihood is moderate-to-high in any app whose webhook handlers branch or persist data keyed by `shop`/`domain`: the prerequisite is only that the attacker themselves has legitimately installed the app on their own store (single, unprivileged merchant) and can capture one real webhook delivery for the topic they want to abuse — trivial with browser/network tooling or a local proxy, no secret leakage or MITM required. The `domain` header is never sanitized or cross-checked against the HMAC-covered content anywhere in this library.

### Recommendation
- Do not trust the `X-Shopify-Shop-Domain` (or events-equivalent) header as an authorization boundary on its own. Cross-check it against the shop associated with the session/subscription that is expected to receive that webhook (e.g., verify a stored, per-shop webhook `id`/subscription record, or otherwise bind the domain to app-side state established at webhook registration time) before using it to select which shop's session/access token to load.
- Consider including the shop domain (and/or webhook id) as part of the value that is validated, or maintain a server-side allow-list mapping expected webhook ids/topics to the shop that registered them, rejecting any mismatch.
- At minimum, sanitize the `domain` header with `sanitizeShop` and reject/flag replays where the same `webhookId` is delivered with different domains within a short window.

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and on `victim.myshopify.com`.
2. Attacker triggers a webhook topic on their own store (e.g. `products/create`) and captures the raw POST body `B` plus the valid `X-Shopify-Hmac-Sha256: H` header that Shopify sent to the app's public webhook URL (`H = HMAC-SHA256(apiSecretKey, B)`, independent of shop).
3. Attacker POSTs `B` to the same app webhook endpoint, keeping `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id` to arbitrary/desired values.
4. `validateHmacFromRequestFactory` recomputes `HMAC-SHA256(apiSecretKey, B)` and it matches `H` (see `packages/apps/shopify-api/lib/utils/hmac-validator.ts:189-197`), so validation succeeds.
5. `checkWebhooksHeaders` extracts `domain = 'victim.myshopify.com'` unchecked (`packages/apps/shopify-api/lib/webhooks/validate.ts:107,131`).
6. `authenticate()` calls `ensureValidOfflineSession(params, check.domain)` and loads `victim.myshopify.com`'s real offline session/access token, then invokes the registered handler for the attacker-chosen topic with body `B` and the victim's `admin` client (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:35-96`).

Note: I could not find any code path in this repository that binds `X-Shopify-Shop-Domain` to the HMAC digest or otherwise re-validates it against the shop that legitimately owns the webhook subscription, so this gap appears to be present across `shopify-app-remix`, `shopify-app-react-router`, and `shopify-app-express` (`packages/apps/shopify-app-express/src/webhooks/index.ts` also consumes `check.domain` from the same `validate.ts`).

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
