This confirms the analog is a genuine, documented, unpatched design gap: when an inbound's ballot fails to reach quorum (all variants terminate `EXPIRED`/`REJECTED`), the user's already-locked/observed source-chain funds are moved into `ExpiredInbounds` with **no current refund mechanism** — the code and docs explicitly label it as consumed by a "future escape-hatch refund flow" that does not exist yet, and there is no permissionless message to trigger a refund from this state.

### Title
Inbound funds become permanently unrecoverable when all ballot variants expire/reject before quorum, with no user-triggerable refund path - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
When Universal Validators observe a source-chain inbound event, the chain creates a `PendingInboundEntry` and votes are recorded via ballots per `InboundVariant` [1](#0-0) . If none of the variants reach quorum before their ballot expires (i.e., all variants terminate as `EXPIRED`/`REJECTED`), `BallotHooks.afterInboundBallotTerminal` removes the entry from `PendingInbounds` and moves the full per-variant audit trail into `ExpiredInbounds`, explicitly annotated as "Consumed by the future escape-hatch refund flow" [2](#0-1) . No `UniversalTx` is ever created for this event, and no `MsgServer` handler, query-triggered action, or automatic process exists that reads `ExpiredInbounds` and mints/refunds anything back to the user — the only related recovery path, `RevertStuckInbound`, is admin/governance-only and operates on a still-`PENDING`/stuck ballot forced to `EXPIRED` via `MsgRecomputeBallotQuorum`, not on entries already reclassified into `ExpiredInbounds` [3](#0-2) .

### Finding Description
The lifecycle is: an unprivileged user deposits/locks funds on a source chain (the funds are already spent/committed off-chain by the time UVs start voting). UVs then vote `MsgVoteInbound` observations, each producing a ballot per unique variant [4](#0-3) . Ballots have a bounded expiry (`BlockHeightExpiry`), enforced by `ExpireBallotsBeforeHeight`/`MarkBallotExpired` [5](#0-4) . If, purely due to honest-but-imperfect timing (e.g. validator downtime, network partitions causing votes to trickle in slower than the expiry window, or a version/format skew causing each UV to independently produce a different variant so none reaches quorum alone), all variants of a given inbound reach a terminal-failure state before any reaches `PASSED`, the entry is permanently archived to `ExpiredInbounds` with the comment confirming no refund mechanism currently exists for it. From that point, the user's already-committed source-chain funds have no way back onto Push Chain and no way to be refunded on the source chain either — the entry sits in `ExpiredInbounds`, queryable via `AllExpiredInbounds` but not actionable [6](#0-5) . This is directly analogous to the referenced report's pattern: a legitimate, honestly-behaving user is penalized (here, total loss rather than just a fee) purely because a time-boxed intermediate state (ballot voting window / grace period) elapses without the expected outcome, and the protocol provides no dequeue/recovery path for that specific terminal condition.

### Impact Explanation
This is a permanent loss/freezing of user funds reachable purely through the ordinary, honest deposit → vote → ballot-expiry flow, with no admin or malicious-actor involvement required to create the stuck state (though admin intervention via a separate, narrower path (`RevertStuckInbound`) can be exercised for a different sub-case). Given the explicit code/doc comments acknowledging the missing "escape-hatch refund flow" as future work, this matches "permanent loss" / "permanent freezing" of user funds, which is in scope.

### Likelihood Explanation
Likelihood is Medium: it requires the ballot for every observed variant of a specific inbound to expire before reaching quorum — plausible during validator set churn, chain congestion, or format-variance across UV client versions producing diverging `Inbound` variants, none of which alone reach quorum. It does not require an attacker; it can happen from ordinary conditions.

### Recommendation
Implement the referenced "escape-hatch refund flow": add a permissionless (or at least non-privileged, deterministically-triggerable) message/keeper flow that reads `ExpiredInbounds` entries and creates a revert `OutboundTx` (mirroring `RevertStuckInbound`'s pattern) to return the user's funds on the source chain, rather than leaving them permanently archived with no consumer.

### Proof of Concept
1. User submits a deposit event on a source chain that is observed by UVs.
2. Due to honest timing/format variance, UVs split their votes across multiple `InboundVariant`s of the same logical `utx_key`, such that no single variant's ballot reaches quorum before `BlockHeightExpiry`.
3. `ExpireBallotsBeforeHeight` marks each variant's ballot `EXPIRED`; `BallotHooks.afterInboundBallotTerminal` detects all variants terminal-failure and moves the entry into `ExpiredInbounds` [7](#0-6) .
4. No UTX was created; the user's funds are locked/spent on the source chain and are now unreachable via any implemented Push Chain or admin flow (`RevertStuckInbound` only handles a still-pending ballot forced to `EXPIRED`, not an entry already in `ExpiredInbounds`).
5. Querying `AllExpiredInbounds` shows the entry, but there is no message to convert it into a refund.

func (k Keeper) MarkBallotExpired(ctx context.Context, id string) error {
	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as expired",
		"ballot_id", id,
		"expiry_height", ballot.BlockHeightExpiry,
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.ExpiredBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = types.BallotStatus_BALLOT_STATUS_EXPIRED
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, types.BallotStatus_BALLOT_STATUS_EXPIRED)
	return nil
}
