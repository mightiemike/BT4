## Analysis Result

### Title
Native TRX sent via `CALL`/`CALLTOKEN` to read-only precompiled contract addresses is unconditionally transferred and permanently frozen - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
Analogous to the Li.Fi bug where ERC20-only bridging functions failed to reject non-zero `msg.value`, java-tron's `Program.callToPrecompiledAddress` unconditionally transfers whatever native TRX/TRC10 value ("endowment") accompanies a `CALL`/`CALLCODE`/`CALLTOKEN` to a precompiled/native-contract address, without checking that the target precompiled contract is actually able to use, hold, or refund that value. All of TRON's native precompiled contracts (vote, freeze/resource query, reward query, etc.) are read/query or fixed-purpose system functions that never consume or move the transferred endowment, so any TRX/TRC10 mistakenly attached to a call against one of these fixed system addresses becomes permanently stuck.

### Finding Description
When the TVM interpreter executes a `CALL` (or `CALLTOKEN`) opcode whose target address resolves to a precompiled contract via `PrecompiledContracts.getContractForAddress`, the interpreter routes the call to `Program.callToPrecompiledAddress`: [1](#0-0) 

The code computes `endowment` from the call's stack `value` parameter, verifies the sender's balance/token balance is sufficient, and then — *before* invoking the actual precompiled contract logic — unconditionally moves the endowment to the `contextAddress` (the fixed precompiled-contract address, e.g. the vote system address `0x...10001`) via `MUtil.transfer` for TRX or `deposit.addTokenBalance` for TRC10: [2](#0-1) 

Only afterward does it call `contract.execute(data)`: [3](#0-2) 

`PrecompiledContracts.java` defines the fixed system addresses for native functions such as vote counting, reward balance, resource/freeze queries, etc. — all of which are inspection/state-mutation helpers with no `payable`-style semantics and no code path to spend, forward, or refund an attached value: [4](#0-3) 

None of these precompiled contract addresses correspond to an account that any actuator or contract logic can subsequently withdraw from — they are protocol-reserved addresses, not user- or contract-controlled accounts, so TRX/TRC10 tokens sent to them via a non-zero `CALL` value are permanently unrecoverable. There is no check in `callToPrecompiledAddress` (nor in `callAction`/`callTokenAction` in `OperationActions.java`) that rejects a non-zero `value`/`tokenId` amount when the destination is a precompiled address that doesn't declare itself payable: [5](#0-4) 

This mirrors the Li.Fi root cause precisely: a function/target that has no legitimate use for the attached native value fails to revert when non-zero value is supplied, resulting in funds being unconditionally moved and frozen.

### Impact Explanation
Any unprivileged smart-contract caller who mistakenly (or is tricked by a malicious contract into) issuing a `CALL`/`CALLTOKEN` with non-zero `value` to one of the fixed precompiled system addresses (vote, freeze/resource-query, reward-query addresses, etc.) will have that TRX/TRC10 silently transferred to the precompiled address and permanently lost, since no actuator or opcode path exists to move funds back out of these reserved addresses. This is a direct, concrete fund-loss/freezing impact matching the "frozen or lost funds" impact class called out in the report.

### Likelihood Explanation
Likelihood is moderate: it requires a contract author (or a contract whose logic can be manipulated by an attacker, e.g., via a proxy/delegatecall pattern or a bug in fee/value forwarding logic) to issue a low-level `call.value(x)(...)` against one of these fixed system addresses. This is more likely to happen accidentally in complex composed DeFi/wrapper contracts on TRON that dynamically forward `msg.value` to arbitrary target addresses (analogous to the bridging facets in the original report that blindly forwarded `msg.value`), especially since these system addresses look like ordinary addresses at the bytecode level.

### Recommendation
In `Program.callToPrecompiledAddress`, reject (push zero / revert or refund energy without transferring) whenever `msg.getEndowment()` (or token value) is non-zero for any precompiled contract that is not designed to receive value — i.e., add an explicit "is payable" flag/check per precompiled contract, and only perform the endowment transfer at lines 1701-1721 when that flag is set. This mirrors the Li.Fi fix of reverting non-native-target calls that arrive with unexpected non-zero value.

### Proof of Concept
1. Deploy or use an existing contract on java-tron whose code performs a low-level call such as `voteContractAddress.call.value(100)(data)` targeting the vote precompiled contract address `0x...10001` (or any of the other fixed addresses enumerated in `PrecompiledContracts.java`, lines 109-131 / 161-206).
2. Execute the call with a non-zero TRX value attached.
3. Observe in `Program.callToPrecompiledAddress` (lines 1701-1721 of `actuator/src/main/java/org/tron/core/vm/program/Program.java`) that `MUtil.transfer` moves the TRX to the precompiled contract's fixed system address regardless of whether `contract.execute(data)` succeeds, fails, or ignores the value entirely.
4. Confirm via `AccountStore` that the balance credited to the precompiled/system address is never debited again by any subsequent actuator — the funds are permanently stuck.

*Note: I was unable to fully trace whether any special-cased withdrawal path exists elsewhere in the codebase for reclaiming balances credited to these fixed precompiled addresses; my search of `PrecompiledContracts.java` and related actuators found no such mechanism, but a full audit of all `AccountStore` consumers would be needed to rule this out with complete certainty.*

  public static void callAction(Program program) {
    // use adjustedCallEnergy instead of requested
    program.stackPop();
    DataWord codeAddress = program.stackPop();
    DataWord value = program.stackPop();

    if (program.isStaticCall() && !value.isZero()) {
      throw new Program.StaticCallModificationException();
    }
    DataWord adjustedCallEnergy = program.getAdjustedCallEnergy();
    if (!value.isZero()) {
      adjustedCallEnergy.add(new DataWord(EnergyCost.getStipendCallCost()));
    }
    exeCall(program, adjustedCallEnergy, codeAddress, value, DataWord.ZERO(), false);
  }
