### Title
Single corrupted/unreadable account storage entry aborts index generation for the entire AccountsDb, blocking startup/restart even though all other slots are healthy - (File: `accounts-db/src/accounts_db.rs`)

### Summary
This is the closest concrete in-scope analog to the `BalancedVault` "one broken market blocks the whole vault" bug class. In `BalancedVault`, a fatal failure in a single underlying market makes `_maxRedeemAtEpoch` return 0 for that market, which causes the `redeem()` check to revert for *the whole vault*, permanently locking funds in the healthy markets too. The agave analog is `AccountsDb::generate_index_for_slot`, where a single account storage entry's `scan_accounts` failure is treated as an unconditional `.expect()` panic, which propagates out of the worker thread and aborts the *entire* `generate_index()` pass across all storages/slots, not just the one at fault.

### Finding Description
`generate_index()` distributes all account storages across worker threads and calls `generate_index_for_slot` for each one: [1](#0-0) 

Inside `generate_index_for_slot`, the per-storage account scan result is unwrapped unconditionally: [2](#0-1) 

If `storage.scan_accounts(...)` returns an `Err` for even one storage/slot (e.g. due to an unreadable/corrupted append-vec file, a truncated file from a prior unclean shutdown, or a disk I/O error on that one storage), the `.expect("must scan accounts storage")` at line 5786 panics that worker thread. The outer `generate_index` loop treats *any* worker thread panicking as fatal to the whole operation: [3](#0-2) 

`if let Ok(thread_accum) = thread_handle.join() else { ...; panic!("index generation failed"); }` means one bad storage entry (analogous to one "broken market") is sufficient to fail index generation for **every** other healthy slot as well, since there is no per-slot isolation or skip-and-continue path. `generate_index()` is called from `reconstruct_accountsdb_from_fields`, which is on the snapshot-load/startup path: [4](#0-3) 

This means a validator that has a single corrupted account storage file on disk (which can occur for reasons other than a malicious/crafted snapshot — e.g. a partial write from a crash, filesystem bit rot, or a bug elsewhere that leaves an append-vec inconsistent) cannot come back up at all, even though the remaining storages/slots and their accounts are perfectly intact. There is no partial-recovery, quarantine, or "skip this one slot and continue" mechanism, mirroring the Vault's lack of a partial/emergency-withdrawal path when one market is stuck.

### Impact Explanation
A single damaged account storage entry converts a localized, single-slot data problem into a total denial of service for the whole node: the validator cannot rebuild its accounts index and therefore cannot restart or bootstrap from that snapshot/storage set at all, even though the vast majority of accounts/storages are healthy. This is analogous to the Sherlock M-16 finding where a single broken market makes the entire Vault (all markets, not just the broken one) permanently unusable for withdrawal. Unlike a hard fork-triggering exploit, this is closer to an availability/liveness issue for the specific node, but it can affect any validator/RPC node whose local storage suffers this kind of single-entry corruption, with no way to selectively "cut losses" on the bad slot and preserve the good ones.

### Likelihood Explanation
This requires an account storage file to fail `scan_accounts` on a single slot while other slots are fine. This is a plausible non-malicious failure mode (disk-level corruption, unclean shutdown truncation, filesystem error) that is explicitly not "maliciously crafted snapshots," which is the item excluded by SECURITY.md — that carve-out covers deliberately crafted archives to attack the loader/deserializer, not incidental storage corruption discovered during normal local index (re)generation at startup. This makes it a real but relatively rare operational scenario (single-node, single-storage failure) rather than a broadly exploitable network-wide condition.

### Recommendation
Change `generate_index_for_slot`'s handling of a `scan_accounts` failure so it doesn't unconditionally panic the whole index-generation pass:
- Propagate the per-slot scan error up through `IndexGenerationAccumulator`/`IndexGenerationInfo` as a `Result`, and have `generate_index()` decide policy (e.g., fail fast with a clear diagnostic identifying the bad slot/store id, or optionally quarantine/skip that one slot's storage while still building the index for all remaining healthy slots, with an explicit opt-in flag since silently dropping accounts affects capitalization/hash correctness).
- At minimum, ensure the panic message/log clearly attributes the failure to the specific `store_id`/slot so operators can distinguish "one storage is corrupted" from "all storages/hardware are broken," and document that a single damaged append-vec currently blocks the full restart.

### Proof of Concept
Conceptual reproduction (would need to be validated in a background Devin session against the actual `AccountsFile`/`AppendVec` scan implementation):
1. Start a validator, let it persist several rooted slots/account storages to disk.
2. Stop the validator and corrupt/truncate a single append-vec file belonging to one slot (simulating disk bit rot or a partial write), leaving all other storage files intact.
3. Restart the validator so it goes through `reconstruct_accountsdb_from_fields` → `AccountsDb::generate_index()`.
4. Observe that `storage.scan_accounts(...)` for the corrupted slot returns `Err`, hits `.expect("must scan accounts storage")` in `generate_index_for_slot` (accounts-db/src/accounts_db.rs:5786), panics the worker thread, and the outer `generate_index()` panics with "index generation failed" (accounts-db/src/accounts_db.rs:5919), preventing the validator from starting up at all — despite every other slot's storage being fully intact and loadable.
