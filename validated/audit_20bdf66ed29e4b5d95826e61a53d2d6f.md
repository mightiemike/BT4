## Analysis

I found a direct structural analog to the DynamoFinance bug: a place where an integrity check that should validate committed state is explicitly, intentionally left unimplemented with a `TODO` comment, while the surrounding code still returns `Ok(())` as if the check passed.

### Title
`TransactionOutput::ensure_match_transaction_info` silently skips state/hot-state/position checkpoint hash verification, letting replay-verify accept a divergent ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk replay/verification (`ChunkExecutorInner::verify_execution` in `execution/executor/src/chunk_executor/mod.rs`) to prove that a freshly re-executed transaction output matches the persisted, hash-committed `TransactionInfo`. It checks status, gas, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that authenticate the Merkle roots of the account/state tree, hot-state tree, and trading-native position tree at checkpoint boundaries.

### Finding Description [1](#0-0) 

The function's doc-comment enumerates what it verifies (status, gas, write set hash, event root hash, transaction hash) but the checkpoint hashes are conspicuously absent, and the code even contains a `TODO` acknowledging the gap:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
```

This function is invoked in the actual verification hot path: [2](#0-1) 

`verify_execution` re-executes a batch of transactions and calls `txn_out.ensure_match_transaction_info(version, txn_info, ...)` to decide whether locally computed output matches the (untrusted, backup-sourced) `TransactionInfo`/write set being replayed. If this returns `Ok(())`, `remove_and_apply` commits the batch as verified. Because the comparator never checks `state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, a `TransactionInfo` (or accompanying data) whose checkpoint hash differs from what local re-execution actually produces will still pass this "verified" gate as long as status/gas/write-set/event hash happen to match.

By contrast, the true state-checkpoint computation path (`DoStateCheckpoint::run` / `get_state_checkpoint_hashes`) does perform this check when driving fresh execution with `known_state_checkpoints`: [3](#0-2) 
but this path is for online execution/commit, not for the chunk-executor's `verify_execution`/`ensure_match_transaction_info` comparator used by replay/restore tooling.

### Impact Explanation
Replay-verify (`storage/db-tool/src/replay_verify.rs`, `ReplayVerifyCoordinator`) exists specifically to catch cases where re-executing history against backed-up transaction data produces a different ledger state than what was committed/backed up — i.e., to detect state divergence, non-determinism bugs, or corrupted backups. Because the comparator omits checkpoint-hash comparison, replay-verify can report success (`"ReplayVerify coordinator succeeded"`) even when the authenticated state root, hot-state root, or position-state root computed during replay diverges from the root that was actually committed to the accumulator/ledger. This directly undermines a state-commitment integrity guarantee: an authenticated proof artifact (`TransactionInfo.state_checkpoint_hash`) is not actually checked against the locally recomputed value in this path, so a wrong root can be accepted as valid by the tooling meant to detect exactly that class of divergence.

### Likelihood Explanation
This is not a hypothetical: the TODO explicitly documents that this can occur for the trading-native/position state root path once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, and the same comparator has no state/hot-state checkpoint check at all today (independent of that feature flag). The check is on the standard replay/restore code path (`chunk_executor::verify_execution`) exercised by `db-tool replay-verify`, `ReplayVerifyCoordinator`, and general chunk replay — not a rare or privileged path.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s freshly-computed checkpoint root(s) against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` whenever those fields are present on the transaction info (i.e., at checkpoint-boundary transactions), matching the same validation already performed in `DoStateCheckpoint::get_state_checkpoint_hashes` for the online-execution path. This should be done before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production, as the TODO itself states.

### Proof of Concept
Not independently reproducible from static analysis alone — the divergence requires a replayed execution whose write-set/event/gas/status match but whose recomputed Merkle roots (state, hot-state, or position) differ from the persisted `TransactionInfo`, e.g. due to a non-deterministic bug in Merkle root computation for the position tree feature. The code path itself (`ensure_match_transaction_info` lacking the check, called from `verify_execution`) is directly confirmed by inspection.

### Note on confidence
This finding is based on static code review; I could not execute the replay pipeline to empirically trigger a checkpoint-hash mismatch that is masked by this comparator, so the "exact corrupted value" is inferred from the explicit TODO comment in the source rather than a demonstrated PoC run.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
