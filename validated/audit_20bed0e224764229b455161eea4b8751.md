## Title
Registry-declared `LiquidityCap` for PRC20 tokens is never enforced during deposit/minting - (File: `x/uexecutor/keeper/handler.go`)

### Summary
`TokenConfig.LiquidityCap` is documented as the "max supply cap for this token" and is required to be a non-empty value at registration time, but no code path in the deposit/minting flow ever reads or checks it before minting PRC20 tokens. Every inbound `FUNDS`, `FUNDS_AND_PAYLOAD`, and `GAS_AND_PAYLOAD` deposit mints the PRC20 representation for the exact `inbound.Amount` reported by Universal Validators with no upper bound check against the registry-declared cap, so PRC20 supply can grow without limit regardless of the configured cap.

### Finding Description
`x/uregistry/types/token_config.go` `ValidateBasic()` only checks that `LiquidityCap` is a non-empty string at config-add/update time [1](#0-0) . The field is documented in the proto as the max supply cap for the token [2](#0-1) .

The actual mint path, `depositPRC20` in `x/uexecutor/keeper/handler.go`, fetches the token config, resolves the PRC20 contract address, parses the requested amount, and calls `CallPRC20Deposit` — it never reads or compares against `tokenConfig.LiquidityCap`: [3](#0-2) .

`CallPRC20Deposit` (and the auto-swap variant `CallPRC20DepositAutoSwap`) similarly issue the mint via `DerivedEVMCall` with no cap check anywhere in the call chain: [4](#0-3) [5](#0-4) .

A grep across the entire repository confirms `LiquidityCap`/`liquidityCap` is referenced only in protobuf-generated code, config JSON files, and unit tests that check `ValidateBasic()` — it is never read by any keeper logic that performs a deposit, mint, or supply check. `Inbound.ValidateForExecution()` (the gate immediately before execution) also only validates that the amount is a well-formed non-negative `uint256`, with no reference to the token's liquidity cap: [6](#0-5) .

Since inbound execution is driven purely by Universal Validator quorum on an `Inbound.Amount` reported from an external-chain event, and honest validators simply relay whatever amount was observed on the source chain gateway, an unprivileged user can deposit (or repeatedly deposit) arbitrarily large amounts on the external chain gateway, and Push Chain will mint the corresponding PRC20 amount with no ceiling — even though the registry explicitly declares and validates a `LiquidityCap` intended to bound this.

### Impact Explanation
This breaks the PRC20 accounting invariant the registry itself declares: PRC20 total minted supply for a token should never exceed the operator-configured `LiquidityCap`. Because there is no enforcement, an attacker (or just organic large deposits) can mint PRC20 supply far beyond the intended cap, which is explicitly called out as in-scope ("corruption of PRC20 or native asset accounting ... token mapping"). Unbounded minting undermines liquidity/collateral assumptions the cap was meant to protect (e.g., where PRC20 minting is backed by external-chain vault liquidity or DEX-routable liquidity for auto-swap paths), and can also inflate the amounts routed through `depositPRC20WithAutoSwap`'s Uniswap-style swap logic, elevating slippage/price-impact risk analogous in spirit to the GammaSwap DoS scenario in the source report, though here manifesting as accounting/cap corruption rather than a reverting call.

### Likelihood Explanation
Likelihood is high in the sense that no special conditions are needed: any legitimate large deposit, or a sequence of deposits by an unprivileged attacker on the source chain, triggers the unchecked mint. It requires only honest Universal Validators reporting an honestly-observed external event — no malicious validator, relayer, or admin action is needed.

### Recommendation
Enforce `TokenConfig.LiquidityCap` in the deposit path: before calling `CallPRC20Deposit` / `CallPRC20DepositAutoSwap`, query the PRC20 contract's current total supply (or track cumulative minted amount in `x/uexecutor` state) and reject/cap the amount if `currentSupply + amount > LiquidityCap`, producing a failed `PCTx` and revert outbound consistent with other execution-validation failures in `ExecuteInboundFunds` / `ExecuteInboundFundsAndPayload` / `ExecuteInboundGasAndPayload`.

### Proof of Concept
1. Register a token via `MsgAddTokenConfig` with `liquidity_cap = "1000000"` (1 USDC at 6 decimals).
2. Have Universal Validators observe (honestly) a real gateway deposit event for `amount = "1000000000000"` (1,000,000 USDC) on the source chain — or repeat smaller genuine deposits many times.
3. Submit `MsgVoteInbound` from a quorum of bonded UVs with `TxType_FUNDS` and that amount, exactly as done in the existing test flow in `test/integration/uexecutor/inbound_solana_test.go` (`TestSolanaInboundFunds`) which shows unlimited/multiplied accumulation of PRC20 balance across inbounds with no cap check [7](#0-6) .
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints the full amount with no reference to `LiquidityCap`, resulting in PRC20 total supply far exceeding the registry's declared `1000000` cap.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}
