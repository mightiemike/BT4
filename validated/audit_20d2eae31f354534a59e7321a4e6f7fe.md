### Title
Floor-rounded `transferUsage` in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` lets an account grind free bandwidth/energy via repeated small undelegations - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.execute()` (and its TVM-precompile twin `UnDelegateResourceProcessor.execute()`) computes the proportional amount of "used resource" (`transferUsage`) that must move from the receiver back to the owner whenever a delegated bandwidth/energy allocation is partially reclaimed. The computation uses `double` arithmetic followed by a truncating `(long)` cast, which always rounds toward zero (floor). This is the same rounding-direction bug class described in the external report: a proportional, per-partial-operation calculation that always rounds in favor of the party issuing the operation (here, the "owner"/undelegator), at the expense of the other party (the "receiver"), across repeated small operations.

### Finding Description

and the identical logic for `ENERGY`: [2](#0-1) 

`transferUsage` is computed as `receiverUsage * (unDelegateBalance / allFrozenBalance)` using `double` math and then truncated with `(long)`, which floors any fractional result. This value is then:
- subtracted from the receiver's recorded `NetUsage`/`EnergyUsage` (line 90/113), and
- added to the owner's own usage via `ResourceProcessor.unDelegateIncrease` → `unDelegateIncreaseV2`: [3](#0-2) 

Because the division always floors, the amount credited back to the owner's own usage is always ≤ the exact proportional value, and the amount removed from the receiver's usage is likewise always ≤ the exact value. This means the owner (who initiates the `UnDelegateResourceContract` transaction and therefore chooses the chunk size) systematically ends up with an artificially *lower* recorded resource usage than they should have, while the receiver retains an artificially *higher* recorded usage than it should. This is directly analogous to the reported bug: a self-service, permissionless "partial withdraw/transfer" operation whose proportional-share math rounds in favor of the party that triggers it.

Because `UnDelegateResourceContract` is an ordinary broadcastable transaction (also exposed as a TVM native contract via `UnDelegateResourceProcessor`, reachable from any contract call), an attacker who controls both the "owner" and "receiver" addresses (self-delegation between owner and receiver is disallowed only for identical addresses, not for two attacker-controlled addresses) can:
1. Delegate frozen TRX (bandwidth/energy) from address A to address B.
2. Consume resource on B so `receiverCapsule.getNetUsage()`/`getEnergyUsage()` is nonzero.
3. Issue many small `UnDelegateResourceContract` transactions (instead of one large one) to reclaim the delegation back to A.

Each small transaction floors its own `transferUsage`, so the cumulative usage moved back to A across N small chunks is strictly less than doing it in one large chunk (each chunk can lose up to just under 1 unit of usage to rounding). The attacker's own account A therefore ends up under-reporting its true consumed bandwidth/energy usage, effectively "laundering" already-consumed resource usage away through the rounding gap, repeatedly, at no cost beyond transaction fees.

### Impact Explanation
This is a resource-accounting corruption issue: an unprivileged account can permanently and repeatably erase fractions of its own recorded bandwidth/energy usage by chunking `UnDelegateResourceContract` (or the TVM `unDelegateResource` native contract) calls into many small amounts. Over many iterations this lets an account retain more available free bandwidth/energy than it is entitled to relative to its frozen TRX, undermining the fairness of the network's resource model (which underlies transaction fee exemption) without any special privilege — a systemic, if slow, resource/accounting drift exploitable by any account.

### Likelihood Explanation
The path is fully reachable by an anonymous account via a standard signed transaction (`UnDelegateResourceContract`) or via a smart-contract call to the `unDelegateResource` precompiled/native contract, requiring no special permissions — only that the account has previously delegated resource to a receiver it also controls. The gain per chunk is small (bounded by <1 usage unit per call) but is repeatable indefinitely and cheaply (calcFee() for this actuator is 0), so it is a low-cost, high-repeatability drift bug rather than a one-shot high-value exploit.

### Recommendation
Round `transferUsage` (and the analogous `unDelegateMaxUsage`) using a rounding mode that does not systematically favor the initiator, or perform the division with a rounding-neutral/ceiling policy combined with a final consistency check, similar to the hardened `BigInteger`/`divideCeil` paths already used elsewhere in `ResourceProcessor` (e.g., `divideCeilExact`, `calculateGlobalLimitV2`). Ensure that the *sum* of usage moved across arbitrarily many partial undelegations of the same total amount is invariant (or at least bounded independent of chunk count), for instance by tracking a running remainder or by disallowing/discouraging the granular chunking pattern (minimum undelegate amount, or accumulate fractional remainder in persistent state instead of discarding it each call).

### Proof of Concept
1. Freeze TRX for bandwidth on address A; delegate an amount `X` to address B (also attacker-controlled) via `DelegateResourceContract`.
2. Cause B to consume bandwidth/energy so `receiverCapsule.getNetUsage()`/`getEnergyUsage()` > 0.
3. Instead of calling `UnDelegateResourceContract` once with balance `X`, call it `N` times with balance `X/N` each.
4. Compare A's final `NetUsage`/`EnergyUsage` after the N-chunk approach versus the single-call approach: due to the floor `(long)` cast in [4](#0-3) 
the N-chunk approach yields a strictly lower (or equal) cumulative `transferUsage` credited to A, demonstrating the rounding drift that can be repeated indefinitely for further gain.
