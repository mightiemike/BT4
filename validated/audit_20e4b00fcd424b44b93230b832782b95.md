This confirms a concrete, exploitable analog: `ClassManager` uses `ConcurrentLocalComponentServer`, which explicitly clones the component and spawns concurrent tasks per request via a semaphore-bounded pool [1](#0-0) , and `ClassManagerRequest::AddClass` requests are dispatched to `ClassManager::add_class` under this concurrent server [2](#0-1) . Meanwhile `add_class` performs a classic check-then-act (TOCTOU) on the shared class cache: it checks whether the class already exists, and if not, spends time compiling (I/O + CPU bound `self.compiler.compile(...).await`) before finally writing the class via `self.classes.set_class(...)` [3](#0-2) .

### Title
Race condition in `ClassManager::add_class` allows duplicate concurrent Sierra→CASM compilation and wasted resources under concurrent Declare submissions - (File: `crates/apollo_class_manager/src/class_manager.rs`)

### Summary
`ClassManager::add_class` is reachable by any contract declarer through the gateway's declare flow. It performs a non-atomic check-then-act: check if the class hash is already present, and if absent, compile it and then store it. Because the class manager component runs on a `ConcurrentLocalComponentServer` that clones the component and processes requests concurrently (bounded by a semaphore, not a mutex over this critical section), N parallel `Declare` transactions for the *same* new class hash can all pass the "already exists" check before any of them finishes compiling and storing, causing the class to be compiled N times concurrently.

### Finding Description
`add_class` reads `self.classes.get_executable_class_hash_v2(class_hash)`. If not found, it proceeds to call the (potentially expensive) `self.compiler.compile(...)` and only afterward calls `self.classes.set_class(...)` [4](#0-3) . There is no lock guarding this sequence. The gateway independently bounds the number of concurrent *compilations it itself triggers* via `declare_compilation_semaphore` in `apollo_gateway/src/gateway.rs`, but this permit is dropped before stateful validation/mempool submission and is per-gateway-process — it does not coordinate across parallel client requests hitting the class manager directly, nor across multiple gateway replicas, nor across requests that arrive close enough in time to both pass the "not compiling" check [5](#0-4) . Since `ClassManagerRequest::AddClass` is served on `ConcurrentLocalComponentServer` which spawns a task per request up to `max_concurrency` (default 128) with a *cloned* component instance [6](#0-5) , this is genuinely a multi-task race on the same underlying class storage, structurally analogous to the Discourse "add users to group DM" race: a check against shared state followed by a slow operation followed by a write, with no lock covering the whole sequence.

### Impact Explanation
This is a resource-exhaustion/duplication issue rather than a state-inconsistency or fund-loss issue: worst case is redundant CPU/memory consumption performing the same Sierra→CASM compilation multiple times in parallel for the same class hash, submitted by an unprivileged declarer sending many parallel/duplicate declare-class requests. `CachedClassStorage::set_class` is the actual persistence step; if it is idempotent (last-write-wins) there is no consensus/root divergence, only wasted resources. I could not fully verify `CachedClassStorage::set_class`'s internal concurrency semantics (whether it uses a lock or an atomic map) within the available context, so I cannot confirm whether this can also produce inconsistent/duplicate storage entries or only wasted CPU.

### Likelihood Explanation
Reachable by any unprivileged party who submits multiple `Declare` transactions for the same never-before-seen class hash in parallel (directly to the class-manager RPC or through concurrent gateway declare requests before the per-gateway-process semaphore is engaged, or across multiple gateway replicas which each have their own independent semaphore). This requires only ordinary declare transactions, no special privileges.

### Recommendation
Guard the check-then-compile-then-store sequence in `ClassManager::add_class` with a per-class-hash lock/mutex (or a distributed lock if the class manager is horizontally scaled) so that concurrent requests for the same class hash serialize around the "is already declared" check and compilation, mirroring the fix applied upstream in the Discourse advisory (wrapping the vulnerable section in a lock before the check).

### Proof of Concept
1. Submit N (e.g., 10) `Declare` transactions/requests carrying an identical, previously-undeclared Sierra class simultaneously (e.g., via N parallel gateway clients or by calling the class-manager's `AddClass` RPC directly N times in parallel).
2. Because `ConcurrentLocalComponentServer` clones the `ClassManager` component and runs up to `max_concurrency` requests in parallel tasks [7](#0-6) , all N requests can pass the `get_executable_class_hash_v2` check in `add_class` before any completes compilation [8](#0-7) , each triggering a full, redundant Sierra→CASM compilation for the same class.
3. Observe N concurrent compiler invocations for a single class hash instead of one, confirming the race.
