## Finding

### Title
Missing `chain_id` domain separation in `RotationProofChallenge` allows cross-network signature replay of key-rotation authorization - ([File: aptos-move/framework/aptos-framework/sources/account/account.move])

### Summary
`RotationProofChallenge`, the struct signed by both the current and the new key to authorize `rotate_authentication_key`/`rotate_authentication_key_with_rotation_capability`, contains only `sequence_number`, `originator`, `current_auth_key`, and `new_public_key`. It has no `chain_id` (nor genesis/chain-id-equivalent) field. By contrast, `RotationCapabilityOfferProofChallengeV2` was explicitly extended with a `chain_id` field, with the framework's own doc comment stating this addition "prevents replaying the challenge message" [1](#0-0) . `RotationProofChallenge` was never given the same treatment [2](#0-1) .

### Finding Description
`rotate_authentication_key` reconstructs the challenge purely from on-chain state (`account_resource.sequence_number`, the signer's own `addr`, `account_resource.authentication_key`) plus caller-supplied `to_public_key_bytes`, then verifies the caller-supplied `cap_rotate_key`/`cap_update_table` signatures against that reconstructed struct [3](#0-2) . The doc comment for `RotationProofChallenge` claims replay protection comes from the sequence number: "These two signatures cannot be replayed in another context because they include the TXN's unique sequence number" [4](#0-3) .

This reasoning only holds *within a single chain*, because sequence numbers, addresses, and default `current_auth_key` values are independently but deterministically derived the same way on every Aptos network (testnet, devnet, mainnet) for an account that has not yet transacted: address = auth_key = hash of the public key, and `sequence_number == 0`. For such an account, the exact same `RotationProofChallenge` bytes (`sequence_number=0`, `originator=addr`, `current_auth_key=addr`, `new_public_key=<attacker-controlled>`) are valid on every network simultaneously, because nothing in the struct binds the signature to a specific chain.

An attacker can therefore have a victim sign this message in a context that appears to be testnet (e.g. a fake testnet dApp, faucet, or "test key rotation" flow), then take the raw signature bytes (`cap_rotate_key`, `cap_update_key`) and submit them unmodified as arguments to `rotate_authentication_key` in a mainnet transaction. Since `rotate_authentication_key` is a `public entry fun` invokable by anyone who can produce a valid signer for `addr` (the transaction sender is the account itself, but note the account being rotated is the signer `account: &signer`, meaning the *victim's own address* must be the transaction sender — this narrows, but does not eliminate, the exploit surface: the attacker needs the victim's account to submit the tx, or must use `rotate_authentication_key_with_rotation_capability` variant where a delegate signer submits on behalf of the offerer). For the delegate-capability variant, the delegate is a third party and the check is bound to `rotation_cap_offerer_address`'s state, which is likewise unbound to chain id, compounding the risk if a rotation-capability offer was accepted the same way across chains.

### Impact Explanation
If exploited, an attacker can cause a `rotate_authentication_key` transaction — authorized only by signatures the victim believed were scoped to a non-production/testnet context — to commit on mainnet, overwriting the victim's `Account.authentication_key` and the `OriginatingAddress` table entry with attacker-chosen values. This directly corrupts committed mainnet account state (potential account takeover) using signatures never intended for mainnet, which fits the "unprivileged input corrupts committed state" bar.

### Likelihood Explanation
Exploitation requires the victim's account to be in the exact same `(sequence_number, current_auth_key)` state on both networks at the time of signing — realistically true only for freshly-created, never-yet-transacted accounts (default `sequence_number = 0`, `current_auth_key = address`). It also requires the transaction be submitted by the account itself (or via an already-accepted rotation-capability delegate) as `account: &signer` is the true sender/signer for `rotate_authentication_key`; this is a meaningful precondition but does not require any trusted-operator error — a social-engineering/phishing vector inducing the victim to sign an off-chain message and then submit or have submitted an unmodified copy is sufficient, since Move entry function execution enforces no chain-scoping of the signed payload itself.

### Recommendation
Add a `chain_id: u8` field to `RotationProofChallenge` (mirroring `RotationCapabilityOfferProofChallengeV2`) and populate it from `chain_id::get()` when reconstructing the challenge in `rotate_authentication_key` and `rotate_authentication_key_with_rotation_capability`, and update the off-chain `RotationProofChallenge` serialization type in `types/src/account_config/resources/challenge.rs` accordingly [5](#0-4) . This is a breaking, hard-fork-style change to a signed struct's BCS layout and must be versioned/gated carefully.

### Proof of Concept
1. Create a fresh account (never transacted) with public key `pk`; note `addr = auth_key(pk)`.
2. Sign `RotationProofChallenge { sequence_number: 0, originator: addr, current_auth_key: addr, new_public_key: attacker_pk }` with `pk`'s private key and with `attacker_pk`'s private key, in a harness/test-harness instance representing "testnet" context, per the existing e2e test pattern [6](#0-5) .
3. Take the raw `signature_by_curr_privkey`/`signature_by_new_privkey` bytes and submit them as `cap_rotate_key`/`cap_update_table` to `rotate_authentication_key` on a second harness instance simulating mainnet, using the same account address/state.
4. Observe the transaction succeeds and `Account.authentication_key` for `addr` is rotated on the "mainnet" instance, even though the signatures were produced for a different network context — because `rotate_authentication_key`'s reconstructed `challenge` contains no chain-binding field [3](#0-2) .
