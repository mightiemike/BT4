### Title
Unchecked subtraction in `run_revertible` can underflow if execution consumes more steps than allotted, panicking the sequencer during a single transaction's execution - (File: crates/blockifier/src/transaction/account_transaction.rs)

### Summary
`AccountTransaction::run_revertible` computes `execution_steps_consumed` via a plain (non-checked, non-saturating) subtraction of `execution_context.n_remaining_steps()` from `n_allotted_execution_steps`. This mirrors the audit-report pattern (`Program.complete`'s unchecked `programInfo.duration - elapsed`): a resource/duration-style plain subtraction that assumes an invariant (remaining steps can never exceed the allotted steps) which is not enforced by a `checked_sub`/`saturating_sub` at this specific call site, unlike sibling code in the same file (`subtract_steps` explicitly uses `saturating_sub` "since subtracting more steps than remain would underflow").

### Finding Description
In `crates/blockifier/src/transaction/account_transaction.rs`:

```rust
let n_allotted_execution_steps = execution_context.subtract_validation_and_overhead_steps(...);
...
let execution_result = self.run_execute(&mut execution_state, &mut execution_context, remaining_gas);

// Pre-compute cost in case of revert.
let execution_steps_consumed =
    n_allotted_execution_steps - execution_context.n_remaining_steps();
``` [1](#0-0) 

`n_allotted_execution_steps` is the result of `subtract_validation_and_overhead_steps`, which itself calls `subtract_steps`, explicitly implemented with `saturating_sub` "since subtracting more steps than remain would underflow": [2](#0-1) 

This shows the codebase authors are aware that step-count subtractions can underflow and guard against it elsewhere — but the specific subtraction at `account_transaction.rs:749-750` that computes `execution_steps_consumed` for the revert-path receipt has no such guard. It implicitly assumes `execution_context.n_remaining_steps()` (read *after* `run_execute` completes) can never exceed `n_allotted_execution_steps` (captured *before* `run_execute` runs). If any code path inside `run_execute`/nested entry-point execution ever raises `vm_run_resources` back up (e.g., via `set_remaining_steps`/a fresh `RunResources::new(n_steps)` invocation with a larger step count, such as when switching between Cairo0/old-Cairo1 VM-mode calls and Sierra-gas-tracked calls, as suggested by references to `infinite_gas_for_vm_mode`), `n_remaining_steps()` could exceed `n_allotted_execution_steps`, and the plain `-` subtraction would underflow.

### Impact Explanation
`usize` subtraction underflow in a Rust binary panics if overflow-checks are enabled (debug builds, or any release profile with `overflow-checks = true`; no `overflow-checks` setting was found in the repo's Cargo configuration, so the default profile-dependent behavior applies). A panic inside transaction execution triggered by a single submitted transaction would crash/abort the batcher/blockifier task executing that block, which can halt block production for that node — a form of the "network unable to confirm new transactions" impact class. In a release build without overflow checks, the subtraction would instead silently wrap to a huge `usize`, corrupting the reported `n_reverted_steps` in the transaction receipt, which feeds into resource accounting, fee computation, and the state diff / block statistics — potentially causing incorrect fee charges (unauthorized loss of funds) or block-building/consensus divergence between nodes with different overflow-check configurations.

### Likelihood Explanation
I was **not able to conclusively verify** a concrete execution path where `execution_context.n_remaining_steps()` exceeds `n_allotted_execution_steps` after `run_execute` — this would require deeper analysis of how `vm_run_resources`/`RunResources` interacts across nested Cairo0/Cairo1/Sierra-gas calls, and the tools available did not let me trace this exhaustively (e.g., where and how "infinite_gas_for_vm_mode" is actually assigned to `vm_run_resources` mid-execution, and whether that context is the same `EntryPointExecutionContext` used at the top level). The explicit `saturating_sub` in `subtract_steps` for the "same class of value" strongly suggests the underlying invariant is not always trivially true, which is the basis for flagging this as an analog, but I could not confirm reachability from a single unprivileged transaction with certainty.

### Recommendation
Replace the plain subtraction with a saturating or checked variant, consistent with the pattern already used in `subtract_steps`:
```rust
let execution_steps_consumed =
    n_allotted_execution_steps.saturating_sub(execution_context.n_remaining_steps());
```
Additionally, audit all other plain (`-`) arithmetic on step/gas counters that cross entry-point-call boundaries to ensure the "remaining ≤ allotted" invariant is either statically guaranteed or defensively guarded with `checked_sub`/`saturating_sub`, mirroring how `GasAmount`/`BouncerWeights` already do via `checked_sub`.

### Proof of Concept
Not able to construct a concrete PoC transaction with the available tools/context; a full PoC would require tracing the exact conditions under which `vm_run_resources` is re-initialized with a step count larger than `n_allotted_execution_steps` mid-`run_execute` (e.g., constructing a Cairo1 contract that calls into a Cairo0 contract, or vice versa, in a way that resets the run resources), and confirming the Cargo release profile's `overflow-checks` setting (not found in the indexed files) to determine whether this manifests as a panic (DoS) or a silent wraparound (fee/receipt corruption).

```rust
    /// Subtracts the given number of steps from the currently available run resources.
    /// Used for limiting the number of steps available during the execution stage, to leave enough
    /// steps available for the fee transfer stage.
    /// Returns the remaining number of steps.
    pub fn subtract_steps(&mut self, steps_to_subtract: usize) -> usize {
        // Saturating, since subtracting more steps than remain would underflow.
        let new_remaining_steps = self.n_remaining_steps().saturating_sub(steps_to_subtract);
        self.set_remaining_steps(new_remaining_steps)
    }
