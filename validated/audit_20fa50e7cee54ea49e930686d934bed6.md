### Title
Unsound manual `Send`/`Sync` impl on `FileHandler` causes data races between mmap writes and lock-free raw-pointer reads - (File: `crates/apollo_storage/src/mmap_file/mod.rs`)

### Summary
`FileHandler<V, Mode>` manually implements `Send`/`Sync` via `unsafe impl` and stores a raw pointer (`memory_ptr: *const u8`) into a memory-mapped file that is *also* wrapped in an `Arc<Mutex<MMapFile<V>>>`. The `Reader::get` path dereferences `memory_ptr` directly, entirely bypassing the mutex that otherwise protects concurrent mutation of the same backing memory in `Writer::append`. This is the same bug class as CVE-2020-35897 in the `atom` crate: an unsafe, hand-rolled `Send`/`Sync` impl that lets a type be freely shared/cloned across threads without actually guaranteeing the underlying memory access is synchronized, opening the door to data races.

### Finding Description
`FileHandler` is defined with a raw pointer field and an `Arc<Mutex<MMapFile<V>>>`: [1](#0-0) 

The `unsafe impl Send`/`unsafe impl Sync` for `FileHandler` make every clone of this handle freely shareable across threads, including the raw `memory_ptr`, which is never covered by the mutex: [2](#0-1) 

`Writer::append` takes the mutex and mutates the mmap in place through a `&mut [u8]` slice derived from `mmap_file.mmap`: [3](#0-2) 

But `Reader::get` reads the very same underlying bytes through the raw `self.memory_ptr` **without ever acquiring the mutex**: [4](#0-3) 

Both `memory_ptr` and the mutex-guarded `mmap` alias the same OS-level memory mapping (`memory_ptr = mmap.as_ptr()` at creation time), so the mutex provides no actual protection for readers that go through the raw-pointer path. `FileHandlers<RO>`/`FileHandlers<RW>` (thin wrappers cloning multiple `FileHandler`s) are used concurrently across the storage reader/writer split: writers append contract classes, CASM, transactions and state diffs during block building, while readers (RPC, gateway, blockifier state reader) fetch the same data from other threads: [5](#0-4) [6](#0-5) [7](#0-6) 

Because the write path (`&mut mmap_file.mmap[offset..]`) and the read path (`std::slice::from_raw_parts(self.memory_ptr...)`) can execute concurrently on different threads without any synchronizing operation between them (the mutex only guards the write side), this is a textbook Rust data race: unsynchronized concurrent mutable/immutable aliasing of the same memory, which is undefined behavior regardless of whether writes and reads target disjoint append-only offsets, since there is no happens-before relationship enforced between the byte-copy in `append` and the raw read in `get`. This directly parallels the `atom` advisory's root cause — an unsafe `Send`/`Sync` bound that is not actually upheld by the type's internal synchronization.

### Impact Explanation
`append_classes`/`append_casm`/`append_transaction` are invoked on every block containing a `declare` transaction, a compiled CASM, or any transaction body, i.e. directly reachable from ordinary user-submitted transactions during block building. `get_class`/`get_casm` are read concurrently by RPC handlers, the gateway (validating subsequent declare/invoke transactions), and the blockifier state reader during execution of other transactions in the same or adjacent blocks. A data race here can produce torn/inconsistent reads of contract bytecode/CASM/state-diff data on one node while leaving other nodes' copies internally consistent, which can lead to divergent execution results (wrong computed state root or block hash) between otherwise-honest nodes running under different thread-scheduling timing, or to a node crashing/panicking on deserialization of corrupted bytes, potentially halting that node's ability to process new blocks.

### Likelihood Explanation
Triggering requires ordinary concurrent activity intrinsic to node operation — one thread appending new classes/CASM/transactions to storage (on block commit) while another thread concurrently reads previously indexed locations (RPC/gateway/execution), which happens continuously and is entirely reachable by submitting normal declare/invoke/L1-handler transactions; no privileged access or malicious peer/operator behavior is needed. However, in practice the race window is narrow (a location is only exposed to readers after the corresponding DB transaction commits, which itself provides some synchronization via the LMDB/mdbx transaction machinery), so observable corruption depends on scheduling/timing and is not guaranteed on every run, which is why this is assessed as a data race with real but not deterministic exploitability — consistent with a Medium-severity classification, matching the referenced advisory's severity.

### Recommendation
Remove the raw-pointer read path and the manual `unsafe impl Send`/`Sync` for `FileHandler`. Have `Reader::get` acquire the same `Mutex` used by the writer (or switch to a synchronization primitive that allows concurrent readers with a writer that establishes proper happens-before ordering, e.g. `RwLock`/atomic fence around the flushed range, or memory-mapped-file with explicit `Ordering::Release`/`Acquire` synchronization on the offset). At minimum, `memory_ptr`-based reads must not be reachable while another thread might be inside `append`'s critical section without synchronization.

### Proof of Concept
Not directly demonstrable without a runtime harness; the race is structural rather than input-dependent. It can be shown conceptually by running two threads sharing a cloned `FileHandler<V, RW>`/`FileHandler<V, RO>` pair — one repeatedly calling `append` while the other repeatedly calls `get` on a previously returned `LocationInFile` under a ThreadSanitizer / Miri build (`unsafe { std::slice::from_raw_parts(...) }` read racing with `&mut mmap_file.mmap[offset..]` write) — which will report a data race, exactly analogous to how `atom`'s unsound `Send` impl allowed concurrent unsynchronized access to its inner value. impl<V: ValueSerde + Debug> Writer<V> for FileHandler<V, RW> {
    fn append(&mut self, val: &V::Value) -> LocationInFile {
        trace!("Inserting object: {:?}", val);
        let serialized = V::serialize(val).expect("Should be able to serialize");
        let len = serialized.len();
        let offset;
        {
            let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
            offset = mmap_file.offset;
            trace!("Inserting object at offset: {}", offset);
            let mmap_slice = &mut mmap_file.mmap[offset..];
            mmap_slice[..len].copy_from_slice(&serialized);
            mmap_file
                .mmap
                .flush_async_range(offset, len)
                .expect("Failed to asynchronously flush the mmap after inserting");
            mmap_file.offset += len;
            mmap_file.should_flush = true;
        }
        let location = LocationInFile { offset, len };
        self.grow_file_if_needed(location.next_offset());
        location
    }

    /// Returns an object from the file.
    fn get(&self, location: LocationInFile) -> MmapFileResult<Option<V::Value>> {
        trace!("Reading object at location: {:?}", location);
        let mut bytes = unsafe {
            std::slice::from_raw_parts(
                self.memory_ptr.offset(location.offset.try_into()?),
                location.len,
            )
        };
        trace!("Deserializing object: {:?}", bytes);
        Ok(V::deserialize(&mut bytes))
    }
}

fn write_classes<'env>(
    classes: &[(ClassHash, &SierraContractClass)],
    txn: &DbTransaction<'env, RW>,
    declared_classes_table: &'env DeclaredClassesTable<'env>,
    file_handlers: &FileHandlers<RW>,
    file_offset_table: &'env FileOffsetTable<'env>,
) -> StorageResult<()> {
    for (class_hash, contract_class) in classes {
        let location = file_handlers.append_contract_class(contract_class);
        declared_classes_table.insert(txn, class_hash, &location)?;

    }
    Ok(())
}
