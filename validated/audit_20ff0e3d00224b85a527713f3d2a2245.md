### Title
Unbounded Recursion in `get_recursive_transaction_results` Enables RPC-Triggered Stack-Overflow Crash - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` recurses over the receipt DAG of a transaction with no depth limit, no cycle protection, and no bound on total nodes visited before hitting the stack. It is the backing implementation for `Chain::get_final_transaction_result`, which is reachable from any JSON-RPC caller querying the final status of a transaction (`tx`/`EXPERIMENTAL_tx_status`-style status queries handled by the view client). An attacker who controls a contract can grow a transaction's receipt tree deep enough (via chained cross-contract calls, data receipts, and postponed/yield-resume receipts) that a subsequent, ordinary RPC status query for that transaction causes unbounded native-stack recursion and crashes the RPC-serving node process — an unprivileged, transaction/RPC-triggered halt, directly analogous to the ESLint CVE's uncontrolled recursion during object traversal.

### Finding Description [1](#0-0) 
```
fn get_recursive_transaction_results(
    &self,
    outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
    id: &CryptoHash,
    require_all_outcomes: bool,
) -> Result<(), Error> {
    let outcome = match self.get_execution_outcome(id) { ... };
    outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
    let outcome_idx = outcomes.len() - 1;
    for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
        let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
        self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
    }
    Ok(())
}
```
This function walks the produced-receipt-id graph by recursing once per child receipt id with no `MAX_DEPTH` guard, unlike the sibling `GetReceiptToTx` walk which the codebase explicitly bounds with `RECEIPT_TO_TX_MAX_DEPTH` (1000) specifically to guard against exactly this class of unbounded traversal: [2](#0-1) 

`get_final_transaction_result` calls straight into this unbounded recursion: [3](#0-2) 

The recursion depth is controlled entirely by the shape of the receipt graph produced by an attacker-authored contract. The codebase's own evil-contract tests demonstrate that receipt chains of significant depth are achievable in a single transaction — `max_self_recursion_delay`, which self-chains cross-contract calls until gas runs out, already reaches depths of 56–221 per the existing test bound, and `slow_test_self_delay` documents this behavior: [4](#0-3) 

Because promise/yield-resume chains, postponed data receipts, and multi-block execution are not limited to a single 300 Tgas budget the way a single WASM call stack is, an attacker can compose considerably deeper receipt/outcome DAGs than 221 (e.g. by fanning out over many transactions/blocks whose receipts still chain through `receipt_ids`), well past what a native thread stack can absorb via this specific recursive-Rust-function traversal — mirroring the ESLint bug class where attacker-controlled graph structure drives uncontrolled recursive traversal to a stack overflow.

### Impact Explanation
A stack overflow in Rust aborts the process (there is no catchable exception for stack overflow), so any node serving this RPC path (validator or RPC node with `get_final_transaction_result` reachable) crashes when a client queries the status of a transaction whose receipt graph was engineered to be sufficiently deep. This is a transaction/RPC-triggered denial of service against otherwise-honest nodes, satisfying the "transaction-triggered halt" impact class explicitly accepted in scope.

### Likelihood Explanation
Likelihood is elevated because: (1) building deep receipt chains from a single or few transactions is already demonstrated feasible in-repo (self-recursion delay contract, evil-contract tests); (2) the vulnerable function is reachable by any unprivileged JSON-RPC caller simply by querying transaction status for a transaction whose receipt chain the attacker previously created; (3) the codebase's own newer sibling function (`GetReceiptToTx`) was explicitly hardened with a depth limit for this exact failure mode, indicating this is a known and previously-mitigated class of bug that was not back-ported to `get_recursive_transaction_results`.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative (explicit stack/queue-based) traversal, or add an explicit depth/node-count bound (mirroring `RECEIPT_TO_TX_MAX_DEPTH`) that returns an error instead of recursing indefinitely, and add cycle/duplicate detection to bound total work regardless of graph shape.

### Proof of Concept
1. Submit a transaction to a contract that fans out/chains many cross-contract `FunctionCall`/promise actions (e.g. variations of `max_self_recursion_delay`/postponed data receipts) across one or more blocks, engineered so the resulting `receipt_ids` graph reachable from the original transaction hash has recursion depth well beyond a safe native stack size.
2. Once all receipts have executed and outcomes are persisted, call the JSON-RPC transaction-status endpoint that resolves to `Chain::get_final_transaction_result` for the transaction hash.
3. The view/RPC-serving node recurses through `get_recursive_transaction_results` without any depth bound, overflowing the native stack and crashing the process, denying service to that node.

    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }
