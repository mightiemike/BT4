## Finding: Griefing-induced storage bloat via forced `many_refs_old_alive` state blocking ancient append-vec packing - (File: accounts-db/src/ancient_append_vecs.rs)

### Summary
The external report's bug class is: an unprivileged party can use a trivial/dust operation on a resource keyed by another party's identifier to set shared, "sticky" state that a later consistency check must respect, permanently blocking a legitimate operation for the victim (DoS) at negligible attacker cost. The closest concrete analog inside AccountsDB's in-scope surface (accounts hashing/index, clean/shrink/purge, ancient-append-vec packing) is the `ref_count > 1` / "many refs, old alive" classification used by ancient append-vec packing, which any unprivileged transaction sender can cheaply and repeatedly induce against an arbitrary victim pubkey to keep that pubkey's ancient storage un-packable indefinitely.

### Finding Description
When AccountsDB decides which ancient slots can be repacked/combined, it calls `calc_accounts_to_combine`, which classifies each alive account by its accounts-index `ref_count` and whether the current (ancient) slot holds the newest slot-list entry: [1](#0-0) 

If `ref_count != 1` and the slot list contains a *newer* slot for that pubkey, the entry is bucketed into `many_refs_old_alive` rather than `one_ref`/`many_refs_this_is_newest_alive`. In `calc_accounts_to_combine`, any ancient storage that ends up with `many_refs_old_alive` accounts (and no other packable accounts) is entirely excluded from packing for that pass: [2](#0-1) 

The accompanying comment explicitly frames this as a normally transient condition that "clean" is expected to resolve — but nothing in the code prevents an attacker from perpetually re-creating the precondition. Because Solana's System Program `Transfer` instruction lets *any* signer credit lamports to *any* arbitrary, unowned pubkey (the recipient need not sign or pre-exist), an attacker can:

1. Identify a victim pubkey whose account currently lives in an ancient (already-packed) append-vec slot.
2. Periodically send a 1-lamport (or 0-lamport-net) transfer that touches that same pubkey in a newer slot, which is credited into the accounts index with a new slot-list entry — bumping `ref_count` and making the *ancient* slot's entry for that pubkey no longer "the newest."

Until `clean_accounts_older_than_root` reclaims the stale ancient-slot entry, `shrink_ancient_slots`/`combine_ancient_slots_packed` will see `ref_count > 1` with an older/non-newest reference and refuse to pack that whole ancient storage (`remove.push(i); continue;` in `calc_accounts_to_combine`, tracked via the `many_refs_old_alive` / `unpackable_slots_count` stats): [3](#0-2) 

Because ancient-slot combination runs on its own cadence (separate from, and typically less frequent than, per-root `clean`), an attacker who re-touches the target pubkey at a cadence competitive with the ancient-combine pass can keep the storage perpetually classified as unpackable, at the cost of a single cheap system transfer per cycle — regardless of who legitimately owns/uses that pubkey.

### Impact Explanation
This does not corrupt balances or state (all classifications above are for maintenance/packing decisions only), but it lets an unprivileged, unrelated attacker impose disproportionate, sustained storage and CPU overhead on every full node: the targeted ancient append-vec (and any others sharing the storage) is kept from being combined/shrunk, so validators retain more (and larger) uncombined ancient storages than necessary, indefinitely, for a target the attacker does not own. This matches the "disproportionate storage and CPU cost" acceptance criterion, and is the closest analog to the external report's "unrelated attacker uses a dust operation to force a persistent, victim-affecting state that blocks a legitimate follow-up operation."

### Likelihood Explanation
Likelihood is Medium: the primitive (crediting lamports to an arbitrary pubkey) is a normal, always-available operation for any transaction sender, and the classification logic (`ShrinkCollectAliveSeparatedByRefs::add`, `calc_accounts_to_combine`) is deterministic and already known to produce this skip behavior under ordinary conditions (the in-code comments acknowledge it happens from "clean bugs or low memory conditions"). Turning transient occurrences into a sustained, targeted DoS requires the attacker to win a race against `clean_accounts_older_than_root` on a recurring basis, which bounds — but does not eliminate — practical exploitability.

### Recommendation
- Do not let `many_refs_old_alive` accounts unconditionally veto packing of an entire ancient storage; instead pack the unaffected (`ref_count == 1`) accounts in the same storage and only defer the specific multi-ref accounts, rather than `remove.push(i); continue` on the whole slot's `ShrinkCollect`.
- Consider having `combine_ancient_slots_packed`/`shrink_ancient_slots` proactively request an eager `clean_accounts_older_than_root` pass (or an eager unref) for exactly the pubkeys blocking a pack attempt, instead of waiting for the next general clean cycle.
- Add metrics/alerting keyed on repeated `many_refs_old_alive` occurrences for the same pubkey across consecutive ancient-combine passes, which would reveal sustained griefing versus incidental transience.

### Proof of Concept
Conceptual reproduction using existing test scaffolding (`ancient_append_vecs.rs` test helpers such as `add_older_ref`, which already demonstrates injecting an extra older/newer index entry for stored accounts): [4](#0-3) 

1. Store account `V` (the "victim" pubkey, owned by anyone) into an ancient slot `S`; root/flush and let it be ancient-packed once.
2. Have an unrelated "attacker" account send a trivial transfer that touches `V` in a new, later slot `S'` (any system transfer crediting `V` suffices; `V` need not sign).
3. Before `clean_accounts_older_than_root` reclaims `S`'s stale entry, trigger `combine_ancient_slots_packed`/`shrink_ancient_slots` for `S`; observe (as in `calc_accounts_to_combine`) that `V`'s entry is classified `many_refs_old_alive`, and — if `S` has no other packable accounts — `S` is entirely skipped (`unpackable_slots_count` increments, `remove.push(i)`).
4. Repeat step 2 on a cadence competitive with the ancient-combine job's schedule to keep `S` perpetually unpackable, at attacker cost of one cheap transfer per cycle.
