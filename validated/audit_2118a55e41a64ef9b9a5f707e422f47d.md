### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting `replay_on_archive`/`replay-verify` silently accept a corrupted state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `execution/executor/src/chunk_executor/mod.rs`) to check that a freshly-executed `TransactionOutput` matches an already-committed/backed-up `TransactionInfo`. It compares status, gas used, write-set hash, and event-root hash, but explicitly and admittedly (per its own TODO comment) does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed value.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` checks:
- `status`
- `gas_used`
- `write_set_hash == txn_info.state_change_hash()`
- `event_root_hash == txn_info.event_root_hash()`

and then returns `Ok(())` without checking `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()` against anything recomputed locally. The code itself documents the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

The `TransactionInfo` V1 variant carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields, all constructed via `assemble_transaction_infos` in the normal execution path [3](#0-2) , and these are exactly the fields the accumulator/transaction-info hash binds into the ledger's Merkle proof structure (`TransactionInfo::hash()` covers the whole struct including the checkpoint hashes). That hash is what feeds the transaction accumulator root that backs `TransactionInfoWithProof`/state proofs.

The direct consumer, `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, re-executes archived transactions and calls `ensure_match_transaction_info` against the `expected_txn_infos` pulled from backup, treating a return of `Ok(())` as full agreement between re-execution and the backed-up ledger state: [4](#0-3) 

Because the checkpoint-hash fields are excluded from the comparison, if a `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` embedded in a committed/backed-up `TransactionInfo` was ever wrong (due to a bug elsewhere in checkpoint computation, a backup/restore corruption, or a malicious/compromised backup source), `ensure_match_transaction_info` — and therefore `replay_on_archive`'s pass/fail verdict — will not detect the discrepancy. Replay-verify is one of the main integrity backstops used to confirm that an archived/backed-up ledger truly reflects the deterministic VM execution; this gap means that backstop provably does not cover part of the authenticated `TransactionInfo` payload.

Separately, `TransactionOutputListWithProof::verify` (used for verifying output lists served over the API/state-sync) does the same subset of checks (status/gas/write-set/event-root/tx-hash) and likewise never touches `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`: [5](#0-4) . Because the overall proof (`self.proof.verify(...)`) still authenticates the full serialized `TransactionInfo` (accumulator inclusion proof over `TransactionInfo::hash()`), a value corrupted at the source (e.g., a malicious/corrupted backup, or a bug in `DoStateCheckpoint`) will still cryptographically "verify" as long as the bytes match what was signed, but callers relying specifically on `ensure_match_transaction_info`/output-list verification to *independently confirm the checkpoint root against locally recomputed state* get no such assurance for the checkpoint fields.

### Impact Explanation
This is a proof/verification-integrity gap in local code, not a cryptographic break of the accumulator: an accumulator proof that authenticates a `TransactionInfo` whose checkpoint-hash fields do not correspond to the actual state produced by execution would still be accepted by `ensure_match_transaction_info` as "matching," because that specific field is never compared. This directly weakens the replay/backup-verification pipeline's ability to catch a divergence between the authenticated ledger state and the locally recomputed state for the state/hot-state/position checkpoint roots — precisely the "authenticated API/proof output bound to the wrong version/object" and "hard-fork-only divergence undetected during restore/replay" class of impact. Today, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are gated behind features that are (per repo comments) not yet enabled on mainnet, and the primary `state_checkpoint_hash` field is separately protected elsewhere in the normal block-execution path via `DoStateCheckpoint::get_state_checkpoint_hashes`'s `known_state_checkpoints` check. However, `ensure_match_transaction_info`/replay-verify tooling does not go through that path — it is the dedicated cross-check meant to catch exactly this kind of corruption when replaying from backups, and it silently no-ops on it. Should `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or the hot-state-root feature be enabled without fixing this comparator (as the TODO warns), a divergence in the trading-native/position state root would go completely undetected by replay-verify, allowing corrupted or stale position-state to be perpetuated through backups/restores without any automated verification catching it.

### Likelihood Explanation
The bug is not conditioned on attacker-controlled input in the base case — it's a latent gap in an existing, in-repo, currently-shipped verification routine that is explicitly flagged by the code's own author as incomplete and dangerous to leave as-is once the feature guarding these fields is turned on. It requires no privileged access to trigger: any actor supplying a backup/archive with a bad checkpoint hash, or any latent bug that causes checkpoint-hash divergence, will not be caught by the standard replay-verify safety net. The severity is currently bounded by the fact that the guarded features (`hot_state_root_in_txn_info`, `compute_trading_native_state_roots`) are not yet active on mainnet per repository comments, making current-day impact Medium, escalating to High/Critical the moment those features activate.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` (and the corresponding checks in `TransactionOutputListWithProof::verify`) to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values embedded in the supplied `TransactionInfo`, mirroring the validation already performed inside `DoStateCheckpoint::get_state_checkpoint_hashes` for the normal execution path. Do this before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`hot_state_root_in_txn_info` are enabled on mainnet, consistent with the existing TODO.

### Proof of Concept
Conceptual PoC (cannot be executed without the full state-checkpoint machinery, which requires committing a chunk with a deliberately wrong checkpoint hash):
1. Construct (or corrupt) a backup/archive whose `TransactionInfo` for some version has a `state_checkpoint_hash` (or, once enabled, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) that does not match what re-execution would produce, while keeping `write_set`, `events`, `status`, and `gas_used` consistent/correct.
2. Run `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::verify` (or `replay_verify.rs`) against this archive.
3. Observe that `execute_and_verify` → `ensure_match_transaction_info` returns `Ok(())` for that transaction despite the checkpoint-hash mismatch, because the comparator never inspects those fields (lines 2196-2203 of `types/src/transaction/mod.rs`), so `replay_on_archive` reports success even though the authenticated checkpoint root diverges from the locally recomputed state.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
