### Title
Vault authorization replay guard is purely in-memory and reset on node/process restart, allowing replay of previously-authorized JWT/allowlist vault requests - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
The `RequestReplayGuard` used by the Vault capability's `authorizer` to prevent replay of authorized JSON-RPC requests (secret create/update/delete/list) stores its "seen" digests purely in an in-process `map[string]int64` with no persistence to durable storage. [1](#0-0) 
This mirrors the reported ledger bug class: authoritative anti-replay/accounting state (there: balances; here: the set of already-authorized request digests) is not carried across a restart/upgrade boundary, even though the mechanism is relied upon as the sole safeguard against re-processing a privileged, already-executed request.

### Finding Description
`authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt())` immediately after successful JWT-based or allowlist-based authorization, and treats `ErrRequestAlreadySeen` as the mechanism that rejects a duplicate/replayed request: [2](#0-1) 

The guard's state (`seen map[string]int64`) lives solely in process memory: [3](#0-2) 

This is the same bug class as the DFinity ledger report: a component's durable/critical safety state (there, `State::balances`; here, the replay-guard's `seen` digest map) is not serialized/restored across a node restart or version upgrade. Any Chainlink node process restart (crash, deploy, upgrade, pod reschedule in the CRE/DON deployment) wipes the `seen` map. A request digest that was already authorized and executed (e.g., a `CreateSecrets`/`UpdateSecrets`/`DeleteSecrets` call, gated by a JWT or allowlisted signature whose validity window can still be within `authResult.ExpiresAt()`) can be resubmitted by the same unprivileged caller after the restart and will be treated as brand-new, since the map no longer contains that digest. The vault system currently relies on `CheckAndRecord` as the single anti-replay control layered on top of the JWT/allowlist "digest" authorization; JWT tokens or authorized-signature validity windows are typically valid for some time window (`authResult.ExpiresAt()`), and if that window spans a restart, the same authorized message can be re-submitted and re-executed.

### Impact Explanation
An unprivileged caller (any vault client whose request was previously authorized and processed) can resubmit the exact same authorized JSON-RPC request (e.g., a `secrets.create`/`secrets.update`/`secrets.delete` call) after any node restart/upgrade of the DON member handling the request, before the request's signature/JWT window expires. Because the replay guard's memory is wiped, this "already processed" request is re-authorized and re-forwarded to the `SecretsService`, causing an unsafe re-execution of a privileged vault action (duplicate secret write/overwrite, duplicate delete, etc.) — a concrete "unsafe transaction/workflow execution" instance per the accepted impact classes. This is distinct from a mere DoS: it's unauthorized re-execution of a state-changing vault operation that should only ever be permitted once per authorized digest.

### Likelihood Explanation
Node/pod restarts (deploys, rolling upgrades, crashes, OOM kills) are routine operational events in a DON, and JWT/allowlist auth windows commonly span multiple seconds-to-minutes (`ExpiresAt()`), so the race window between "restart" and "signature/token still valid" is realistic, especially under load or during a rolling upgrade of the DON. The exploit requires no privileged access — merely replaying a previously legitimate request that the attacker (or observer, if the request/response is otherwise observable) already possesses, which matches the "unprivileged-user" analog requirement of this report.

### Recommendation
Persist the replay-guard's seen-digest set (or at least enough of it to cover realistic auth-token TTLs) to durable storage (e.g., the node's database) so it survives process restarts, analogous to persisting balances alongside blocks in the original report. At minimum, on restart the guard should be rehydrated from a persisted log of recently-authorized digests with their expiries before the node begins accepting vault requests again, or persisted expiries should be short enough and restart-safe fallback (e.g., a distributed replay cache) should be used so a restart cannot silently reopen a replay window.

### Proof of Concept
1. Client submits a valid vault request (e.g., `secrets.create`) with a JWT/allowlist signature valid for `N` seconds; `authorizer.AuthorizeRequest` succeeds and records its digest in `RequestReplayGuard.seen` via `CheckAndRecord`. [4](#0-3) 
2. The vault-capability-hosting node process restarts (deploy/upgrade/crash) before the JWT/signature expiry `authResult.ExpiresAt()` elapses. The in-memory `seen` map is reinitialized empty by `NewRequestReplayGuard()`. [5](#0-4) 
3. Client resubmits the identical (still-valid) signed request. `authorizeRequest` re-validates the still-unexpired JWT/signature and calls `CheckAndRecord` again; since the digest is no longer in `seen`, no `ErrRequestAlreadySeen` is returned, and the request is treated as new and re-forwarded to `SecretsService` for processing, per the pipeline in `GatewayVaultRequestProcessor.authorizeAndStamp`. [6](#0-5) 

**Caveat**: I was unable to determine within the indexed content whether an additional restart-safe replay-prevention layer exists outside this package (e.g., a database-backed dedupe on the `SecretsService` side, keyed on `RequestId`) that might mitigate this at a different layer. If a persistent/idempotency check exists downstream (analogous to `idempotency_key` columns seen elsewhere in the codebase, e.g., `eth_txes.idempotency_key`), it could reduce or eliminate the practical impact; this should be verified in a live session before treating this as a fully unmitigated vulnerability.

type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID

	if err := stamp(prefixedRequestID); err != nil {
		p.lggr.Errorw("failed to stamp authorized request params", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, fmt.Errorf("failed to stamp authorized request params: %w", err)
	}

	p.lggr.Debugw("authorized gateway vault request", "method", req.Method, "requestID", req.ID, "owner", authorizedOwner, "orgID", authResult.OrgID(), "workflowOwner", authResult.WorkflowOwner())
	return &AuthorizedGatewayVaultRequest{
		Req:        *req,
		AuthResult: authResult,
	}, nil
}
