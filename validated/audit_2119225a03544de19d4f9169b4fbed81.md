## Title
Lack of Slippage Control in `ExchangeWithdrawActuator` Enables Sandwich Attacks on Bancor-style Exchange Withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract` (the TRC10 Bancor-style exchange withdrawal) has no caller-specified minimum-output ("expected") field, unlike its sibling `ExchangeTransactionContract`. This mirrors the reported `PositionManager._swapToVolt()` bug class: a value-converting operation with a price computed at execution time and no slippage floor, reachable through a permissionless, price-moving public action (`ExchangeTransactionContract`).

### Finding Description
`ExchangeWithdrawContract` only carries `exchange_id`, `token_id`, and `quant` — no expected/minimum amount field [1](#0-0) , as also documented in the protocol spec listing `owner_address`, `exchange_id`, `token_id`, `quant` with no expected value, in contrast to `ExchangeTransactionContract` which explicitly documents an `expected` field ("expected minimum number of tokens").

In `ExchangeWithdrawActuator.execute()`, the amount of the counter-token (`anotherTokenQuant`) received by the withdrawer is computed purely from the exchange's current on-chain reserve ratio at execution time: [2](#0-1) 

`doValidate()` re-derives the same ratio-based `anotherTokenQuant` purely to check reserve sufficiency and rounding precision — it never compares against any user-supplied floor because none exists: [3](#0-2) 

By contrast, `ExchangeTransactionActuator` (the swap actuator) explicitly requires and enforces a minimum (`tokenExpected`) before letting the trade go through: [4](#0-3) 

Since `ExchangeTransactionContract` swaps are fully permissionless (anyone with sufficient balance/asset can call it) and directly move `firstTokenBalance`/`secondTokenBalance` of any exchange pair, any unprivileged attacker can observe a pending `ExchangeWithdrawContract` in the mempool and sandwich it:
1. Front-run with an `ExchangeTransactionContract` swap that shifts the pool ratio unfavorably for the pending withdrawal's `tokenID`.
2. Let the victim's withdraw execute, receiving a reduced `anotherTokenQuant` computed from the now-skewed ratio.
3. Back-run with the reverse swap to restore the ratio, pocketing the extracted counter-token value (minus negligible swap rounding/fees).

This is the same root cause as the reported bug: a value-conversion function computed against a manipulable live price/ratio, with no caller-enforced minimum-output guard, reachable via a public, permissionless action.

### Impact Explanation
An attacker can extract real economic value from any account that withdraws liquidity from a TRC10 Bancor exchange, without needing any special privilege — only the ability to submit ordinary, permissionless `ExchangeTransactionContract` transactions around the victim's withdrawal in the same or adjacent blocks. This directly causes underpriced settlement / stolen value in an unprivileged, publicly reachable accounting path, matching the accepted impact classes (accounting/settlement manipulation).

### Likelihood Explanation
Exploitation requires only standard transaction ordering control (block producers or MEV-style bundling within a block, which java-tron's block production model supports since multiple transactions can be included in one block by the packing witness, or the attacker can simply race transactions across adjacent blocks given the withdraw transaction is visible pre-confirmation). No special permission or trusted role is needed — the withdrawer must simply be the exchange's creator (a normal, unprivileged account that created the pool), and the attacker is an ordinary unprivileged user submitting swaps. The precision-check logic in `doValidate()` (0.01% tolerance) only guards against stale/rounding mismatches between the transaction's expected ratio and current ratio — it does not protect against an attacker deliberately moving the ratio within that same block/transaction ordering window.

### Recommendation
Add a caller-specified minimum-output field (e.g., `expected`) to `ExchangeWithdrawContract`, analogous to `ExchangeTransactionContract.expected`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the withdrawal if the computed `anotherTokenQuant` falls below the caller's specified minimum.

### Proof of Concept
1. Exchange pool state: `firstTokenBalance = 1,000,000 A`, `secondTokenBalance = 1,000,000 B` (1:1 ratio).
2. Creator broadcasts `ExchangeWithdrawContract` intending to withdraw `tokenQuant = 100,000 A`, expecting roughly `100,000 B` back based on the current ratio.
3. Attacker observes the pending transaction and front-runs it with an `ExchangeTransactionContract` selling a large amount of `B` for `A`, sharply reducing `secondTokenBalance` relative to `firstTokenBalance`.
4. The creator's withdrawal executes using the manipulated ratio in `execute()` (`anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`), yielding far less than `100,000 B`.
5. Attacker back-runs with the reverse `ExchangeTransactionContract` (selling `A` back for `B`), restoring the ratio and capturing the `B` shortfall extracted from the creator, minus negligible AMM curve fees.
6. Because `ExchangeWithdrawContract` has no `expected`/minimum field, the actuator has no way to reject the unfavorable execution — unlike `ExchangeTransactionActuator`, which would have rejected the trade via its `tokenExpected` check.
