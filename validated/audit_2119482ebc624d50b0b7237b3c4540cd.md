**Analysis:**

The premise that different validators could use different `ReservedAccountKeys` snapshots for the same bank/slot is incorrect. `reserved_account_keys.is_reserved()` (line 346) operates on `self.reserved_account_keys`, which is derived from `ReservedAccountKeys::update_active_set(&feature_set)` [1](#0-0)  — a key moves from `inactive` to `active` only when its corresponding feature is activated in `feature_set`, and feature activation slots are themselves consensus data replicated deterministically by every validator replaying the same chain. Every validator computing the same bank at the same slot will derive an identical `feature_set` and therefore an identical `reserved_account_keys.active` set — there is no validator-local choice of "which snapshot to use."

`ReservedAccountKeys::new` seeds the `active`/`inactive` split from the static `RESERVED_ACCOUNTS` table based on whether a `feature_id` is `None` (already active) or `Some` (pending activation) [2](#0-1) , and `is_reserved` simply checks membership in `active` [3](#0-2) . Which keys exist in this table, and which feature gates them, is fixed protocol code — not something an unprivileged attacker can influence or predict beyond what's publicly known and identical for all validators.

In `Bank::collector_type_checked`, the reserved check at line 346 is evaluated against `self.reserved_account_keys` on the bank object itself [4](#0-3) , which is set/updated consistently as part of deterministic bank processing (feature activation happens at fixed epoch boundaries recorded on-chain), not from an ad-hoc or validator-specific snapshot. So while it's true that a `block_revenue_collector` pointing at a not-yet-reserved key can succeed in one epoch and then fail (and burn) in a later epoch once the key becomes reserved [5](#0-4) , this transition happens identically for every validator at the same slot — it does not "intermittently flip" between validators or cause any accounting divergence across the cluster. This is the intended, deterministic behavior of SIMD-0232's reserved-collector protection, not an exploitable consensus bug.
