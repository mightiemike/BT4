### Title
L1 handler cancellation state is silently overridden by `mark_committed`, allowing cancelled transactions to still be executed - ([File: crates/apollo_l1_events/src/transaction_record.rs])

### Summary
The reported Vader bug is a "cancel flag" pattern flaw: cancelling a proposal only clears one piece of state (`mapPID_votes`) but leaves the finalization-eligibility fields (`mapPID_timeStart`, `mapPID_finalising`) untouched, so the finalize/execute path never actually checks for cancellation and the proposal still executes. The analogous pattern exists in the sequencer's L1→L2 message lifecycle: `TransactionRecord::mark_cancellation_request` sets `state = CancellationStartedOnL2` and records `cancellation_requested_at`, and after a timelock `update_time_based_state` promotes the state to `CancelledOnL2` [1](#0-0) [2](#0-1) . However, `mark_committed`, which is called from `commit_txs` when a transaction is included in a committed block, never inspects the cancellation state at all — it unconditionally forces `state = Committed` and only asserts that the transaction hasn't been double-committed [3](#0-2) [4](#0-3) .

### Finding Description
The cancellation lifecycle relies on `is_validatable()` — which excludes `Committed`, `CancelledOnL2`, and `Consumed` states — to keep a cancellation-requested/cancelled L1 handler transaction out of new proposals and out of validator approval [5](#0-4) . This gate is only enforced in `validate_tx`, at the moment a transaction is being considered for inclusion [6](#0-5) .

The actual commit path, `TransactionManager::commit_txs`, does not consult `is_validatable()`, `is_cancelled()`, or the `cancellation_requested_at` field in any way — for every hash in `committed_txs` it unconditionally calls `mark_committed()`, which itself only guards against double-commit, not against a prior cancellation state (`CancellationStartedOnL2` or `CancelledOnL2`) [4](#0-3) [3](#0-2) . This mirrors the Vader bug exactly: the "cancel" state is a side channel (`cancellation_requested_at` / `CancellationStartedOnL2` / `CancelledOnL2`) that is checked only at one gate (`validate_tx`, analogous to `finaliseProposal`) but is completely bypassed at the actual execution/finalization step (`commit_txs`/`mark_committed`, analogous to the queued-execution step in the report).

Because a node's local `commit_txs` call is driven by the externally-agreed block content (i.e., whatever committed/rejected hash set is supplied by the consensus/commit flow, as documented in the finalization sequence where the batcher calls `mempool`/L1-provider `commit_block` with the finally decided transaction set) [7](#0-6) , any deviation between the locally-tracked cancellation state and the actually-committed set of hashes is written through without a consistency check. If a proposer (potentially with stale local cancellation-request awareness, e.g. before it has scraped a cancellation event, or if a different node's L1-scraping lags) includes and gets quorum for an L1 handler transaction whose cancellation was already requested (or even fully finalized) from this node's perspective, `commit_txs` will still forcibly transition it to `Committed`, overwriting whatever cancellation-related state existed, with no error raised beyond an unrelated double-commit assertion.

### Impact Explanation
An L1 handler transaction whose cancellation was requested (and possibly already timelock-expired to `CancelledOnL2`) can still end up marked `Committed` by an honest node's `TransactionManager::commit_txs`, purely because the state-transition function performs no cancellation check. This creates a divergence between a node's understanding of "this L1 message should never execute again" and reality: the record's terminal/authoritative state can be silently rewritten to `Committed` regardless of prior cancellation bookkeeping. This is directly analogous to the reported finding's "canceled proposals can still be executed" impact — cancellation intent is recorded but not enforced at the actual state-finalizing step, undermining the cancellation guarantee for L1→L2 messages that is otherwise supposed to be gated by `is_validatable()`.

### Likelihood Explanation
The bypass only manifests when a divergence exists between a node's local cancellation bookkeeping and the transaction set that ultimately reaches quorum/commit (e.g., timing/ordering differences in L1-event scraping across nodes, or a proposer race where cancellation is requested after a proposal already has quorum). `validate_tx` is the only enforcement point, and `commit_txs`/`mark_committed` have no defense-in-depth check, so any such race — however it arises — is unconditionally accepted at commit time with no assertion failure or rejection.

### Recommendation
Mirror the report's own recommendation: instead of only gating on `is_validatable()` at proposal/validation time, have `mark_committed` (or `commit_txs`) also assert/check the transaction's cancellation-related fields (`cancellation_requested_at`, `state == CancellationStartedOnL2/CancelledOnL2`) before unconditionally overwriting state to `Committed`. At minimum, log/alert loudly (or treat as a fatal invariant violation) when a transaction being committed was already in a cancellation state, so the divergence is detected rather than silently overwritten [8](#0-7) .

### Proof of Concept
1. Node A processes an L1 event and calls `request_cancellation(tx_hash, t)` on `tx_hash`, transitioning its local record to `CancellationStartedOnL2` [9](#0-8) .
2. Due to L1-scraping timing differences, another node's local `TransactionManager` has not yet observed the cancellation event, so it still treats `tx_hash` as `Pending`/proposable and includes it in a proposal that reaches consensus quorum.
3. When Node A's `commit_txs` is invoked with `tx_hash` in `committed_txs` (following the externally agreed block), it calls `mark_committed()` on the record regardless of its `CancellationStartedOnL2` state [8](#0-7) [3](#0-2) .
4. The record's state is forcibly overwritten to `Committed` with no error, silently erasing the cancellation intent that Node A had already recorded — demonstrating that the cancellation flag is never consulted at the commit/finalization boundary.

Note: I was unable to fully trace the exact upstream code path that supplies `committed_txs` to `commit_txs` for L1 handler transactions (i.e., the precise proposer/batcher call site invoking `TransactionManager::commit_txs`), so the concrete cross-node timing scenario above is inferred from the state-machine code and the documented finalization flow rather than from a directly observed call site; this should be verified against the batcher/L1-provider integration code for full certainty.

    pub fn mark_cancellation_request(
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }

    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();
        }
        for &tx_hash in rejected_txs {
            self.with_record(tx_hash, |r| r.mark_rejected()).expect(
                "Rejected L1 handler tx has no record. Unreachable: all L1 handler txs in a \
                 committed block were validated as known (validation rejects unknown hashes), \
                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",
            );
        }
    }
