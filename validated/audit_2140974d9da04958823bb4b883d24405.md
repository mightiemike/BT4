## Title
Unbounded `PendingInbounds` collection scan on every inbound ballot finalization enables gas-based denial of service — (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
`x/uexecutor`'s `afterInboundBallotTerminal` hook performs a full linear scan (`k.PendingInbounds.Walk(ctx, nil, ...)`) over the entire `PendingInbounds` collection every time *any* inbound ballot reaches a terminal state (`PASSED`, `REJECTED`, or `EXPIRED`). This walk runs synchronously inside the consensus-critical `MsgVoteInbound` message handler for every Universal Validator vote that finalizes a ballot. Because inbound-ballot expiry is effectively disabled (`DefaultExpiryAfterBlocks = 100_000_000`) and any account can trigger the creation of new `PendingInbounds` entries by generating ordinary cross-chain deposit events that Universal Validators must observe and vote on, an unprivileged attacker can inflate `PendingInbounds` to a size that makes this linear scan exceed the gas available to `MsgVoteInbound` transactions, halting inbound finalization system-wide. This mirrors the Squeeth report's core lesson — an attacker crafting a large volume of "valid" work items to blow past the gas budget of an on-chain settlement/finalization operation.

### Finding Description
`RecordInboundVote` (`x/uexecutor/keeper/inbound.go`) appends a new `PendingInboundEntry`/`InboundVariant` to the `PendingInbounds` collection on the first vote for any new inbound observation: [1](#0-0) 

Entries are only removed once **all** variants for a `utx_key` reach a terminal ballot status, via the hook `afterInboundBallotTerminal`: [2](#0-1) 

Two structural facts combine to make this exploitable:

1. **The hook does a full unindexed scan of the entire collection** for every single terminal ballot transition, not just the one it needs — `PendingInbounds.Walk(ctx, nil, ...)` iterates every key until it finds the one containing `ballotID`. Ballot IDs are one-way hashes and there is no secondary index from `ballotID -> utxKey`, so this scan is unavoidable and its cost is `O(N)` where `N` is the current size of `PendingInbounds`.

2. **Entries can persist effectively forever.** Ballot expiry is set to `100_000_000` blocks (comment: "effectively disable expiry"): [3](#0-2) 
Additionally, `VoteOnInboundBallot` always casts `VOTE_RESULT_SUCCESS` — there is no `FAILURE` vote path for inbound ballots — so a ballot can only reach `REJECTED` under conditions that never occur for this ballot type in practice; ballots that don't reach the `2/3` quorum simply sit `PENDING` indefinitely. [4](#0-3) 

Any unprivileged user can trigger creation of new `PendingInbounds` entries simply by sending ordinary, minimal-value cross-chain transfers/deposits from any inbound-enabled external chain — this is the exact same "gateway event" trigger used for legitimate bridging, requiring no elevated permission and no cooperation from a malicious validator. `VoteInbound` only checks that the source chain has inbound enabled before creating state: [5](#0-4) 

By continuously generating a high volume of such events (across one or many inbound-enabled chains, using minimal-value transfers to keep attacker cost low), an attacker inflates `PendingInbounds` well beyond what UV vote processing can drain in a comparable timeframe (each event requires a full confirmation-wait + a separate `MsgVoteInbound` transaction per UV before it can even begin converging toward quorum). As `N` grows, each subsequent `MsgVoteInbound` that finalizes *any* ballot (including completely unrelated, legitimate ones) has to pay the ever-increasing walk cost. Cosmos SDK KV-store gas metering charges per-`Get`/iteration-step gas, and each `PendingInboundEntry` also carries full `Inbound` payloads and voter lists, so the per-entry cost is non-trivial. Once the walk's gas cost for a "typical" position in the collection approaches or exceeds the gas limit UVs use for `MsgVoteInbound` (or even the network's max block gas), those vote transactions begin failing with out-of-gas, which means:

- The failing `MsgVoteInbound` reverts entirely (no state change survives), so the failing ballot never records that vote.
- Because the walk cost is a property of the *global* `PendingInbounds` size, this doesn't just block the attacker's spam ballots — it blocks finalization of **every other pending inbound ballot in the system**, including honest users' legitimate bridging deposits.
- Because entries can't be pruned without reaching a terminal status, and reaching a terminal status requires successfully executing this same expensive hook, the system can enter a self-sustaining lockup: `N` never shrinks once it crosses the threshold where votes start failing.

This is a state-safety / DoS condition reachable purely through ordinary, unprivileged, honest-validator-assumption user action (sending cross-chain deposits), matching "denial of service only when it is not network-level and is reachable without privileged control" and "consensus or state-machine divergence reachable from ordinary user deposits" in the allowed-impact scope.

### Impact Explanation
If the walk cost exceeds available gas, `MsgVoteInbound` transactions system-wide begin reverting whenever they would finalize a ballot. This halts inbound execution (mints, payload execution, gas abstraction) for **all** chains and **all** users, not just the attacker's target — a chain-wide liveness failure of the core cross-chain bridging pipeline (`x/uexecutor`). Because expiry is effectively disabled and stuck ballots cannot make progress once vote execution starts failing, the condition is not self-healing without a chain upgrade / manual state surgery, which is consistent with a persistent, high-severity denial of service against a user-reachable, unprivileged-input flow.

### Likelihood Explanation
The trigger requires no privileged capability, no validator collusion, and no cryptographic break — only the ability to originate cheap, low-value transactions on any inbound-enabled external chain repeatedly enough to outpace validator vote throughput and inflate `PendingInbounds`. Cost to the attacker scales with external-chain gas fees for minimal-value transfers, which is generally low, while the amplification on Push Chain (global O(N) scan per any ballot finalization) is disproportionate. The `DefaultExpiryAfterBlocks = 100_000_000` setting (an explicit, currently-shipped configuration) removes the natural self-cleaning mechanism that would otherwise bound worst-case growth, making sustained accumulation practical over time.

### Recommendation
- Maintain an explicit secondary index from `ballotID -> utxKey` (e.g., a `collections.Map`) so `afterInboundBallotTerminal` can do an O(1) lookup instead of a full-collection scan.
- Reintroduce a bounded, enforced expiry for `PendingInbounds` entries (or add an explicit size/age cap with a real escape-hatch/refund path) so the collection cannot grow unboundedly.
- Consider metering/limiting how many inbound observations from a single source/sender can be simultaneously pending, or requiring a minimum bridged value / rate-limiting per source chain to raise the attacker's cost of generating entries.
- Add gas-usage guardrails around the hook (or move the audit-trail maintenance off the hot vote path into a batched/paginated background process) so a single vote transaction's cost cannot scale with attacker-controlled global state size.

### Proof of Concept
1. Deploy/observe that `DefaultExpiryAfterBlocks` is `100_000_000` and that `VoteOnInboundBallot` only ever casts `VOTE_RESULT_SUCCESS` (no rejection path), confirming entries are not naturally pruned.
2. From an unprivileged account, repeatedly initiate minimal-value transfers on one or more inbound-enabled external chains, generating a steady stream of distinct `Inbound` observations faster than Universal Validators can vote them to quorum.
3. Observe `PendingInbounds` growing without bound over time (query via `x/uexecutor` pending-inbound query endpoints).
4. Once `N` is large enough that `PendingInbounds.Walk` in `afterInboundBallotTerminal` consumes gas approaching a UV's configured `MsgVoteInbound` gas limit (or the chain's max block gas), submit/observe a normal, unrelated `MsgVoteInbound` that would finalize a ballot; show the transaction fails with an out-of-gas error, and that this failure recurs for subsequent legitimate votes, demonstrating a persistent halt of inbound-ballot finalization chain-wide.

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}

func (k Keeper) VoteInbound(ctx context.Context, universalValidator sdk.ValAddress, inbound types.Inbound) error {
	// Canonicalize first so every derived key + the stored inbound use one
	// representation per logical event.
	inbound.Canonicalize()

	k.Logger().Info("vote inbound received",
		"validator", universalValidator.String(),
		"source_chain", inbound.SourceChain,
		"tx_hash", inbound.TxHash,
		"tx_type", inbound.TxType.String(),
		"sender", inbound.Sender,
	)

	// Check inbound enabled before any state changes
	enabled, err := k.uregistryKeeper.IsChainInboundEnabled(ctx, inbound.SourceChain)
	if err != nil {
		return errors.Wrap(err, "failed to check inbound enabled")
	}
	if !enabled {
		k.Logger().Warn("vote inbound rejected: chain inbound disabled", "source_chain", inbound.SourceChain)
		return fmt.Errorf("inbound is disabled for chain %s", inbound.SourceChain)
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Step 1: Derive UTX key from the original inbound data (source_chain:tx_hash:log_index)
	universalTxKey := types.GetInboundUniversalTxKey(inbound)
	found, err := k.HasUniversalTx(ctx, universalTxKey)
	if err != nil {
		return errors.Wrap(err, "failed to check UniversalTx")
	}
	if found {
		k.Logger().Warn("vote inbound rejected: utx already exists", "utx_key", universalTxKey)
		return fmt.Errorf("universal tx with key %s already exists", universalTxKey)
	}
