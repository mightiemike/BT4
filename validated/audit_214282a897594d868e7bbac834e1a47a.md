### Title
Global compiled-class cache skips the "is declared" freshness check for Cairo 0 classes, allowing use of undeclared/reverted class code - (File: `crates/blockifier/src/state/state_reader_and_contract_manager.rs`)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` reads from a process-wide, long-lived cache (`ContractClassManager`/`GlobalContractCache`) before consulting the authoritative state. For Cairo 1 classes it explicitly re-validates a cache hit against `state_reader.is_declared(class_hash)` because, per the code's own comment, "the cache does not guarantee [declaration]... it might contain a declared class from a reverted block." For Cairo 0 (`RunnableCompiledClass::V0`) classes this re-validation is skipped entirely (`RunnableCompiledClass::V0(_) => {}`), so a cache hit is trusted unconditionally regardless of whether the class is actually declared in the state being read. [1](#0-0) 

### Finding Description
This mirrors the Lean 4 bug class exactly: a shared cache entry (analogous to the kernel's type-inference cache) is trusted without re-checking whether it is still valid in the *current* checking context (analogous to local-context membership). Lean checks closure for `def`/`theorem` but omits it for `add_opaque`; here the sequencer checks declaration freshness for Cairo 1/Native classes but omits it for Cairo 0.

Root cause:
- The `ContractClassManager` cache (`GlobalContractCache`) is process-global and outlives any single block/tx execution — it is not rolled back when a transaction, a candidate block, or a speculative execution is discarded. [2](#0-1) 
- `get_compiled_from_class_manager` populates this cache on any cache miss via `set_and_compile`, independent of whether the read ultimately belongs to a transaction/round that is committed. [3](#0-2) 
- On a subsequent cache hit, the declared/non-declared status is re-validated only for the non-V0 branch:
```
match &runnable_class {
    RunnableCompiledClass::V0(_) => {}
    _ => {
        if !self.state_reader.is_declared(class_hash)? {
            return Err(StateError::UndeclaredClassHash(class_hash));
        }
    }
}
``` [4](#0-3) 
- This asymmetry is acknowledged in-code as necessary due to reverted-block staleness, but the fix was applied to only one of the two code paths, leaving Cairo 0 classes exposed to the same staleness the comment warns about.

Downstream consumers rely on `state.get_compiled_class(class_hash)` as the sole existence/declaration check before permitting class use:
- `replace_class` (deprecated Cairo 0 syscall path) trusts `get_compiled_class` alone to confirm the class is declared before rewriting a contract's class hash: "Ensure the class is declared (by reading it)." [5](#0-4) 
- The Cairo 1 `replace_class` syscall base similarly relies on `get_compiled_class` returning `Err(UndeclaredClassHash)` for a truly undeclared class before allowing the state write. [6](#0-5) 
- `deploy` reads `get_compiled_class` transitively during constructor execution and similarly depends on it correctly rejecting undeclared classes (tests assert `UndeclaredClassHash` for undeclared hashes). [7](#0-6) 

If a Cairo 0 class is ever fetched into the global cache from a state/context where it appeared declared (e.g., a speculative or later-discarded/failed transaction execution, a candidate block that is not ultimately committed, or a view-call state at a different block), the entry persists. A subsequent, unrelated transaction on the canonical (undeclared) state can hit the cache and be treated as if the class were declared, since the V0 branch performs no re-check.

### Impact Explanation
If exploitable, this allows an unprivileged transaction sender to make a contract's `class_hash` point to Cairo 0 bytecode that was never actually declared/committed in the canonical state (via `replace_class`) or to deploy a contract at an address running undeclared code (via `deploy`). This produces:
- A state diff (`class_hashes` write) referencing a class hash with no corresponding declaration in the canonically committed/synced state, which other honest nodes reconstructing state independently (with their own, differently-populated caches) would not resolve the same way — a source of honest-node divergence and a wrong committed state root/block hash.
- Execution of Cairo 0 bytecode that bypassed declaration checks, potentially enabling logic that should not be reachable (e.g., a superseded/rolled-back implementation), an unauthorized account/contract action.

This satisfies the "wrong committed root or block hash" / "honest-node divergence" acceptance criteria, warranting Medium/High severity depending on exact reachability of a stale-but-undeclared cache entry in production block-building flow.

### Likelihood Explanation
The vulnerable code path is reachable from ordinary Cairo 0 declare/deploy/replace-class flows, i.e., from a single submitted transaction, without any operator/proposer privilege — satisfying the "unprivileged transaction sender" reachability bar. However, I could not fully confirm from the indexed code alone the precise operational scenario that populates the global cache with a class that is *not* declared in the specific state later queried (e.g., whether speculative/discarded block-building attempts in the batcher share the same long-lived `ContractClassManager` instance across proposal rounds, and whether a failed/reverted Cairo 0 declare still causes a `get_compiled_class` read that populates the cache before the declare is known to fail). The existing test `cairo_1_declared_then_verification_failed_after_reorg` in `state_reader_and_contract_manager_test.rs` demonstrates the developers explicitly modeled and fixed this staleness scenario for Cairo 1 — the absence of an equivalent Cairo 0 test/fix strongly suggests the gap is real but I could not trace an end-to-end proof-of-concept purely via static reading of the indexed files. [8](#0-7) 

### Recommendation
Apply the same declaration-freshness check used for Cairo 1/Native classes to Cairo 0 classes in `get_compiled_from_class_manager`: instead of `RunnableCompiledClass::V0(_) => {}`, call an analogous "is Cairo-0 declared" check against `state_reader` (e.g., extend `FetchCompiledClasses::is_declared` to cover Cairo 0, or add a parallel `is_deprecated_declared` method) before trusting a V0 cache hit. This closes the asymmetry that mirrors the Lean CVE-2026-72711 bug class (trusting a cached inference/compilation result without validating it against the current context).

### Proof of Concept
Not independently reproduced end-to-end against a running sequencer; reasoning is based on static code review:
1. Trigger any code path that calls `StateReaderAndContractManager::get_compiled_class` for a Cairo 0 class hash `H` in a context/state where `H` is (or later becomes) declared — e.g., a declare transaction that is executed speculatively (in a discarded candidate block, a reorg, or a subsequently-failed transaction) — causing `set_and_compile(H, CompiledClasses::V0(...))` to populate the global `ContractClassManager` cache. [9](#0-8) 
2. On the canonical state where `H` was never actually declared, submit a transaction whose Cairo 0 contract calls `replace_class(H)` (deprecated syscall) or `deploy(class_hash=H, ...)`.
3. `get_compiled_class(H)` hits the stale global cache entry; because it is `RunnableCompiledClass::V0`, the `is_declared` re-check is skipped and the class is returned as if declared, matching the test-asserted positive-flow behavior for `replace_class`/`deploy` rather than the expected `StateError::UndeclaredClassHash`. [10](#0-9)

impl<S: FetchCompiledClasses> StateReaderAndContractManager<S> {
    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }

#[derive(Clone, Debug)]
pub struct GlobalContractCache<T: Clone>(pub Arc<Mutex<ContractLRUCache<T>>>);

impl<T: Clone> GlobalContractCache<T> {
    /// Locks the cache for atomic access. Although conceptually shared, writing to this cache is
    /// only possible for one writer at a time.
    pub fn lock(&self) -> LockedClassCache<'_, T> {
        self.0.lock().expect("Global contract cache is poisoned.")
    }

    pub fn get(&self, class_hash: &ClassHash) -> Option<T> {
        self.lock().cache_get(class_hash).cloned()
    }

    pub fn set(&self, class_hash: ClassHash, contract_class: T) {
        self.lock().cache_set(class_hash, contract_class);
    }

    pub fn clear(&mut self) {
        self.lock().cache_clear();
    }

    pub fn new(cache_size: usize) -> Self {
        Self(Arc::new(Mutex::new(ContractLRUCache::<T>::with_size(cache_size))))
    }

fn test_replace_class() {
