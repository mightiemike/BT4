## Title
Market order matching engine allows a resting maker order to be fully consumed and closed while the maker receives zero tokens in return, due to a missing zero-amount guard in the "taker == maker" branch of `matchSingleOrder` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes, via integer division, how many "buy" tokens a resting maker order should receive when it is matched against an incoming taker order. In two of the three branches of this method the code explicitly guards against the computed amount rounding down to `0` and refunds the affected side instead of letting it lose its funds. The third branch — the "taker == maker" (exact match) branch — has no such guard. If the division rounds `makerBuyTokenQuantityReceive` down to `0`, the maker's entire remaining sell-side balance is still consumed and the order is marked `INACTIVE` (removed from the order book), while the maker is credited `0` tokens.

### Finding Description
`matchSingleOrder` is reached from `MarketSellAssetActuator.execute` → `matchOrder` → `matchSingleOrder`, which is invoked whenever an anonymous `MarketSellAssetContract` broadcast transaction matches against existing resting orders in the on-chain order book. [1](#0-0) 

Inside `matchSingleOrder`, three cases are handled depending on how the taker's remaining sell quantity compares to the maker's remaining sell quantity:

1. **taker == maker** (exact match): the maker's payout `makerBuyTokenQuantityReceive` is computed via `multiplyAndDivide`, the maker's remaining sell balance is immediately zeroed, and the order is marked `INACTIVE` — with **no check that `makerBuyTokenQuantityReceive` is non-zero**. [2](#0-1) 

2. **taker < maker**: no payout calculation issue since the taker's full remaining amount is transferred, no rounding to zero possible. [3](#0-2) 

3. **taker > maker**: here the code *does* check `if (makerBuyTokenQuantityReceive == 0)` and, if so, refunds the maker's remaining sell tokens via `returnSellTokenRemain` instead of letting the maker's balance be silently zeroed. [4](#0-3) 

The comment attached to case 3 explains the developers' assumption that a zero payout "would not happen" when `sellQuantity < buyQuantity` for the maker's order — but this assumption does not hold for maker orders where `sellQuantity > buyQuantity` (i.e., an order selling a large quantity of token A for a small quantity of token B). In the "taker == maker" branch, `multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` performs a floor division, and when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`, the result is `0`. [5](#0-4) 

After returning from `matchSingleOrder`, the caller `matchOrder` sees `makerOrderCapsule.getSellTokenQuantityRemain() == 0` and removes the maker's order from the price-level linked list via `orderIdListCapsule.removeOrder(...)`, permanently taking it out of the order book. [6](#0-5) 

Unlike the external report's NFT-auction scenario — where an item is popped from a queue and its `_settleAuction` logic only performs state changes/transfers when `amount > 0`, leaving the asset permanently stuck when `amount == 0` — here the maker's sell-side asset is not "stuck" in a queue, but it is silently and permanently destroyed: it was already debited from the maker's account when the order was created (`transferBalanceOrToken`), the order is deleted from the book, and the maker's compensation (`addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive=0)`) is zero. [7](#0-6) [8](#0-7) 

### Impact Explanation
Any user can lose the entire remaining balance of a resting sell order with no compensation, if a subsequent matching order happens to be small enough (relative to the resting order's original sell/buy ratio) that the rounding of `multiplyAndDivide` yields `0` buy tokens for the maker while still fully "filling" and deleting the maker's order. This is direct, irrecoverable asset loss/accounting corruption in the on-chain DEX (Market) module, triggerable purely by broadcasting normal `MarketSellAssetContract` transactions — no privileged role required.

### Likelihood Explanation
Reaching the "taker == maker" branch requires only that `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`, i.e., the taker's remaining amount exactly matches the maker's remaining sell amount — a normal, common occurrence in order matching (e.g., a taker order sized to exactly consume the last unit of a maker order). Triggering the zero-rounding condition additionally requires the maker order's sell/buy ratio and remaining balance to satisfy `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`, which is achievable by any user simply creating a sell order with a large sell/buy quantity ratio and allowing it to be worn down to a small remainder — entirely within an attacker's or ordinary user's control, making this practically triggerable rather than a purely theoretical edge case.

### Recommendation
Add the same zero-payout guard used in the "taker > maker" branch to the "taker == maker" branch of `matchSingleOrder`: before zeroing the maker's `SellTokenQuantityRemain` and marking the order `INACTIVE`, check whether `makerBuyTokenQuantityReceive == 0`, and if so, call `MarketUtils.returnSellTokenRemain(makerOrderCapsule, ...)` to refund the maker's remaining sell-side tokens instead of silently discarding them.

### Proof of Concept
1. Account A creates a `MarketSellAssetContract` maker order: sell `1000` of token A for `1` of token B (`sellTokenQuantity=1000, buyTokenQuantity=1`), which is placed on the order book via `createAndSaveOrder`. [9](#0-8) 
2. Through prior partial fills (or directly, if created with `sellTokenQuantityRemain=1`), the maker order's `SellTokenQuantityRemain` is reduced to `1` (i.e., `makerSellRemainQuantity = 1`).
3. Account B broadcasts a `MarketSellAssetContract` taker order such that its remaining sell quantity converts, at the maker's price, to exactly `1` unit of token A (`takerBuyTokenQuantityRemain == 1 == makerOrderCapsule.getSellTokenQuantityRemain()`), landing in the "taker == maker" branch.
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 1, 1000) = 0` (floor division). [10](#0-9) 
5. `takerBuyTokenQuantityReceive = 1` (the maker's last unit of token A) is credited to the taker; `makerOrderCapsule.setSellTokenQuantityRemain(0)` and the order is marked `INACTIVE` and removed from the order book; `addTrxOrToken(makerOrderCapsule, 0)` credits the maker with `0` tokens of B for the trade. [11](#0-10) 
6. Result: Account A's remaining `1` unit of token A (already debited from its balance at order creation) is permanently lost — no tokens are returned, and the order no longer exists to reclaim it.

  public static void returnSellTokenRemain(MarketOrderCapsule orderCapsule,
      AccountCapsule accountCapsule,
      DynamicPropertiesStore dynamicStore,
      AssetIssueStore assetIssueStore) {
    byte[] sellTokenId = orderCapsule.getSellTokenId();
    long sellTokenQuantityRemain = orderCapsule.getSellTokenQuantityRemain();
    if (Arrays.equals(sellTokenId, "_".getBytes())) {
      accountCapsule.setBalance(addExact(
          accountCapsule.getBalance(), sellTokenQuantityRemain,
          dynamicStore.disableJavaLangMath()));
    } else {
      accountCapsule
          .addAssetAmountV2(sellTokenId, sellTokenQuantityRemain, dynamicStore, assetIssueStore);
    }
    orderCapsule.setSellTokenQuantityRemain(0L);
  }
