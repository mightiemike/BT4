### Title
Open redirect via protocol-relative/backslash bypass in `sanitizeRedirectUrl`/`isSafe` - ([File: packages/apps/shopify-app-remix & shopify-app-react-router /server/authenticate/admin/helpers/validate-redirect-url.ts])

### Summary
`isSafe()` never validates that the resolved URL's host/origin matches the app's own domain — it only checks for a literal triple-slash (`FILE_URI_MATCH`), whitespace, and double-slash/backslash in `url.pathname` (`INVALID_RELATIVE_URL`) post-parse. Because WHATWG's `URL` parser normalizes backslashes to slashes for special schemes (http/https) and treats any leading `//`, `\\`, `/\`, or `\/` as a protocol-relative authority, an attacker-controlled `redirectTo.url` value such as `/\evil.com` (or even plain `//evil.com`) resolves to an entirely different host while `isSafe` still returns `true`.

### Finding Description
In `validate-redirect-url.ts`: [1](#0-0) 

- `FILE_URI_MATCH = /\/\/\//` only matches three consecutive forward slashes, so it never fires on backslash sequences (`\\`, `/\`, `\/`) or on plain two-slash protocol-relative strings (`//evil.com`).
- `INVALID_RELATIVE_URL = /[/\\][/\\]/` is tested against `url.pathname` **after** `new URL(redirectUrl, domain)` has already parsed the string — not against the raw input and not against `url.host`.
- Per the WHATWG URL Standard, for special schemes (http/https), backslashes are treated as path/authority separators identical to `/`. A string beginning with any two of `{/, \}` (e.g. `\\evil.com`, `/\evil.com`, `\/evil.com`, or plain `//evil.com`) is parsed as a "network-path reference," causing the parser to adopt `evil.com` as the new host while inheriting the base's scheme.
- After parsing, `url.pathname` becomes `/` (or similar), which does **not** match the double-slash/backslash regex, so `INVALID_RELATIVE_URL` passes.
- `isSafe` then only checks `url.protocol` against `['https:', 'http:']` and SSL requirement — both trivially satisfied by `https://evil.com`.
- Critically, `isSafe`/`sanitizeRedirectUrl` **never compares `url.hostname`/`url.origin` to the `domain` argument's host** anywhere in the function. This means the function is not actually a same-origin/domain allowlist at all — any http(s) absolute or protocol-relative/backslash-relative URL passes.

This is consumed by `renderAppBridge`: [2](#0-1) 
which injects `destination.toString()` into a `window.open(...)` script served to the authenticated embedded-admin iframe. If a host app passes an attacker-influenced value (e.g., a `redirect`/`return_to` query parameter) into `redirectTo.url`, the attacker fully controls the destination host despite the intent of `sanitizeRedirectUrl` being to restrict redirects to `config.appUrl`.

### Impact Explanation
This is an open redirect from a document served inside the authenticated Shopify Admin embedded-app context. An attacker can craft a link that, once clicked by a merchant/staff user inside the admin iframe, causes the app to `window.open` an attacker-controlled origin. Combined with the embedded app boundary/token flows (App Bridge, session token exchange), this can be leveraged for phishing, and in flows where bounce/redirect pages carry tokens in the URL, potential token/state leakage to the external origin — matching Shopify's "Open Redirect leading to token/session leakage" bounty class.

### Likelihood Explanation
Preconditions: a host application built on this library must forward an attacker/user-controlled value into `renderAppBridge`'s `redirectTo.url` (e.g. exposing a raw `redirect_uri`/`return_to` query param without additional origin restriction of its own — the library itself provides no such restriction despite `sanitizeRedirectUrl`'s apparent purpose). Given that precondition, exploitation requires no privileges beyond sending a normal HTTP request with a crafted query parameter or link — fully consistent with "unprivileged attacker" scope. The bypass strings (`//evil.com`, `\\evil.com`, `/\evil.com`) are simple and repeatable.

### Recommendation
After constructing `url = new URL(redirectUrl, domain)`, explicitly verify `url.host === new URL(domain).host` (or `url.origin === new URL(domain).origin`) before considering the redirect safe, rather than relying solely on regex checks against the raw string and `pathname`. Additionally, reject any redirect input beginning with `//`, `\\`, `/\`, or `\/` outright, since these are always attempts at protocol-relative/authority overrides regardless of what the WHATWG parser later resolves.

```ts
  // Expected (secure): should throw ShopifyError
  // Actual: returns a URL object
  expect(result.host).not.toBe('evil.com'); // FAILS - result.host === 'evil.com'

it('BUG: plain protocol-relative URL also bypasses isSafe', () => {
  const result = sanitizeRedirectUrl(APP_URL, '//evil.com/path');
```

```typescript
const FILE_URI_MATCH = /\/\/\//;
const INVALID_RELATIVE_URL = /[/\\][/\\]/;
const WHITESPACE_CHARACTER = /\s/;
const VALID_PROTOCOLS = ['https:', 'http:'];

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
```
