## Title
Deleting and re-creating a validator account as an uninitialized universal account can trigger a fatal, chain-halting storage-invariant panic - (File: `runtime/runtime/src/lib.rs`)

### Summary
In `update_validator_accounts`, the runtime assumes that any account referenced by `stake_info`/`validator_rewards`/`last_proposals` from the epoch manager is either an *initialized* account carrying a `locked` balance, or, if uninitialized, has zero stake/reward/proposal recorded against it. This mirrors the `sweepInterest` bug class: the code enforces an invariant about a party's balance/state that a normal, unprivileged action (deleting an account) can invalidate, and when the invariant fails the failure is not a soft error but a `StorageError::StorageInconsistentState`, which is fatal for chunk application.

### Finding Description
`action_delete_account` in `runtime/runtime/src/actions.rs` removes an account and refunds `account.amount()` to a beneficiary, without itself checking `account.locked()`. [1](#0-0) 

Separately, `update_validator_accounts` (`runtime/runtime/src/lib.rs`) is fed a `ValidatorAccountsUpdate` (`stake_info`, `validator_rewards`, `last_proposals`) computed by the epoch manager from up to the **last three epochs'** of stake history. When it looks up the account and finds it *uninitialized*, the code treats this as an edge case that "can only happen when a validator deletes their account and re-creates it in an uninitialized state," and asserts that in that case `max_of_stakes`, `reward`, and `last_proposal` must all be zero — otherwise it returns a fatal `StorageInconsistentState`: [2](#0-1) 

The `locked` value tracked by the epoch manager for stake-invariant purposes is not simply "current locked balance" — it is defined (per `docs/ChainSpec/EpochAndStaking/Staking.md`) as the **maximum of the account's stake over the last three epochs**, recomputed only at epoch boundaries: [3](#0-2) 

This means an account's on-chain `locked` field can already read `0` (e.g., right after an unstake proposal is submitted, since "locked balance can only increase" on-chain until the epoch-boundary recompute) while the epoch manager still carries a nonzero `max_of_stakes` for that account for up to two more epoch boundaries (the 3-epoch lookback). If the account owner deletes the account during this window — which is permitted at the runtime-action level whenever the actor has permission and the account's on-chain `locked` currently reads zero — and a new account is created at the same id as an *uninitialized* universal account (e.g., via a plain `Transfer` receipt, which the runtime explicitly allows to create a `0u`-prefixed uninitialized account, see `action_implicit_account_creation_transfer`/`AccountType::UniversalAccount` handling), then at the next epoch boundary `update_validator_accounts` will find the account `!is_initialized()` while `max_of_stakes` (carried over from the epoch manager's lookback window) is still `> 0`, hitting the fatal branch. [4](#0-3) 

Unlike the `sweepInterest` case where a griefer merely bricks a single sweep call, here the broken invariant is escalated to `RuntimeError` via `StorageError`, which is treated as unrecoverable/fatal chunk-apply state, not a normal transaction failure returned to the user.

### Impact Explanation
A `StorageError::StorageInconsistentState` returned from `update_validator_accounts` propagates as a `RuntimeError` out of `apply()`. This is not a per-transaction `ActionError` that gets reported to the caller and rolled back — it is treated by the node as an unexpected/fatal storage inconsistency, which halts chunk production/application for that shard on every node that reaches this state deterministically (since the trigger is a deterministic sequence of validator actions plus normal epoch-boundary processing). This satisfies the "transaction-triggered halt" acceptance criterion: a validator-controlled account can, by unstaking, deleting its account, and re-creating it as an uninitialized universal account inside the epoch-manager's 3-epoch stake-lookback window, force this fatal path at the following epoch boundary.

### Likelihood Explanation
The precondition set is: (1) be a staked validator/account with a nonzero recent stake history, (2) unstake so the current on-chain `locked` reads zero, (3) delete the account (permitted once `locked == 0` on-chain), and (4) get the same account id re-created as an uninitialized universal account before the epoch manager's 3-epoch-lookback `max_of_stakes` for that id decays to zero. All of these are reachable via ordinary transactions signed by the account owner (an unprivileged transaction signer) with no protocol-level restriction visible in the reviewed code path that specifically forbids re-creating a previously-staked account id as `AccountType::UniversalAccount` while epoch-manager lookback state is still nonzero. The developers' own comment in `update_validator_accounts` acknowledges this exact scenario is reachable ("The only way it could appear in stake_info is when a validator deletes their account and re-creates in an uninitialized state") and treats the zero-value assumption as "defense in depth," implying it is not proven unreachable, only expected to hold under normal conditions.

Uncertainty: I was not able to fully trace, within the tool-call budget, the epoch-manager code that builds `ValidatorAccountsUpdate.stake_info`/`last_proposals` (`chain/epoch-manager/src/lib.rs` re-exports only; the actual builder logic was not located) to confirm precisely how many epochs of lookback data can coexist with an on-chain `locked == 0` state, nor whether some other guard (e.g., disallowing account deletion or re-creation for ids with pending epoch-manager stake history) exists elsewhere that would block this sequence. This should be verified against the epoch-manager's proposal/validator-selection code before treating this as confirmed-exploitable.

### Recommendation
- In `update_validator_accounts`, do not treat a nonzero `max_of_stakes`/`reward`/`last_proposal` against an uninitialized account as a fatal, unrecoverable error. Instead, either (a) settle/burn or refund the outstanding stake safely without panicking, or (b) prevent the unsafe state from ever arising by refusing `DeleteAccount` (or refusing re-creation as an uninitialized account at the same id) while the epoch manager still has non-decayed stake history (`max_of_stakes > 0`) for that account id.
- Add an explicit epoch-manager-side or runtime-side check that surfaces this as a normal `ActionError` (rejected transaction) rather than a `StorageError::StorageInconsistentState` fatal path, consistent with how other invariant violations reachable by user action are handled.

### Proof of Concept
Conceptual sequence (not independently executed, given the uncertainty noted above):
1. Attacker account `A` stakes and becomes part of validator stake history for several epochs.
2. `A` submits a `Stake` action with `stake = 0` to fully unstake, so its on-chain `locked` value is on a path to zero (`action_stake` in `runtime/runtime/src/actions.rs`).
3. Once on-chain `locked() == 0`, `A` submits `DeleteAccount` with itself as beneficiary; `action_delete_account` removes the account without checking epoch-manager-side stake history.
4. Before the epoch-manager's 3-epoch lookback for `A`'s `max_of_stakes` decays to zero, someone sends a plain `Transfer` to a `0u...` universal-account id that maps back to `A`'s account id (or otherwise re-creates `A` as `AccountType::UniversalAccount`), producing an uninitialized account at that id.
5. At the next epoch boundary, `update_validator_accounts` processes `stake_info` for `A`, finds the account uninitialized, and finds `max_of_stakes > 0` (carried from the lookback), returning `StorageError::StorageInconsistentState`, which is fatal for that shard's chunk application. [5](#0-4)

```rust
    fn update_validator_accounts(
        &self,
        state_update: &mut TrieUpdate,
        validator_accounts_update: &ValidatorAccountsUpdate,
    ) -> Result<(), RuntimeError> {
        for (account_id, max_of_stakes) in &validator_accounts_update.stake_info {
            let account = get_account(state_update, account_id)?;
            // An uninitialized account has no `locked` field, so none of this applies
            // and it is skipped. The only way it could appear in stake_info is when a
            // validator deletes their account and re-creates in an uninitialized state.
            // None of the checked values could be positive in such case. The check is
            // defense in depth, so that minted tokens do not leak from the supply if
            // this path ever becomes reachable.
            if account.as_ref().is_some_and(|account| !account.is_initialized()) {
                let rewards = &validator_accounts_update.validator_rewards;
                let reward = *rewards.get(account_id).unwrap_or(&Balance::ZERO);
                let proposals = &validator_accounts_update.last_proposals;
                let last_proposal = *proposals.get(account_id).unwrap_or(&Balance::ZERO);
                if *max_of_stakes > Balance::ZERO
                    || reward > Balance::ZERO
                    || last_proposal > Balance::ZERO
                {
                    return Err(StorageError::StorageInconsistentState(format!(
                        "FATAL: staking invariant does not hold. Uninitialized account \
                         {account_id} can hold no locked balance: max of stakes \
                         {max_of_stakes}, reward {reward}, last proposal {last_proposal}"
                    ))
                    .into());
                }
                continue;
            }
```

```markdown
### Returning stake

`locked` is the number of tokens locked for staking, it's computed the following way:

- initially it's the value in genesis or `0` for new accounts
- on a staking proposal with a value higher than `locked`, it increases to that value
- at the start of each epoch it's recomputed:
    1. consider the most recent 3 epochs
    2. for non-slashed accounts, take the maximum of their stakes in those epochs
    3. if an account made a proposal in the block that starts the epoch, also take the maximum with the proposal value
    4. change `locked` to the resulting value (and update `amount` so that `amount + locked` stays the same)
```
