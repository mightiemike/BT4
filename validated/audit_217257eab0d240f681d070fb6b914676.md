### Title
Precompiled-contract return data is copied to memory beyond the caller-declared `outDataSize`, allowing free/underpriced memory-expansion gas griefing - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The reported bug is about a low-level `.call{}("")` that lets an untrusted receiver return an arbitrarily large payload, which the caller's EVM/TVM implicitly copies into memory at uncontrolled/uncharged cost, griefing whoever pays for the call (a relayer). The same root cause — return data whose size is dictated by the *callee*, copied to the caller's memory without being bounded by what the caller declared and paid gas for — exists in java‑tron's TVM implementation of `CALL`/`CALLCODE`/`DELEGATECALL`/`STATICCALL` to precompiled-contract addresses.

### Finding Description
When a contract executes `CALL` (or `CALLCODE`/`DELEGATECALL`/`STATICCALL`) against a precompiled-contract address, `OperationActions.exeCall` builds a `MessageCall` with the caller-declared `outDataOffs`/`outDataSize` and expands memory only for that declared size before dispatching: [1](#0-0) 

`Program.callToPrecompiledAddress` then executes the precompiled contract and writes its actual output back into memory. Crucially, there are two code paths depending on the `allowTvmSelfdestructRestriction` proposal: [2](#0-1) 

- If the proposal is enabled, `memorySave(offset, outDataSize, out.getRight())` bounds the write/extend to the caller-declared `outDataSize` (safe).
- If the proposal is **not** enabled (i.e., pre-proposal / legacy default behavior), it calls `this.memorySave(msg.getOutDataOffs().intValue(), out.getRight())`, which resolves to `memorySave(int addr, byte[] value)`: [3](#0-2) 

That method calls `Memory.write(addr, data, data.length, false)` with `limited=false`, which internally calls `extend(address, dataSize)` using the **full length of the precompiled contract's actual output**, not the caller-declared `outDataSize`: [4](#0-3) [5](#0-4) 

The energy that was charged for the `CALL` opcode's memory expansion, however, is computed earlier (in `EnergyCost`/`calcMemEnergy`) using the caller's **declared** `outDataOffs`/`outDataSize` from the stack — not the real returned size. Any excess memory that must be allocated because the actual return data is larger than what was declared and paid for is allocated "for free": the extra `Memory.extend` call is not gated by any additional energy charge in this code path.

This exactly mirrors the reported root cause: the amount of data copied into memory is controlled by the callee/precompiled output, not bounded/charged according to what the caller reserved and paid for.

### Impact Explanation
Any contract call performing `CALL`/`STATICCALL`/`CALLCODE`/`DELEGATECALL` to a TVM precompiled-contract address while `allowTvmSelfdestructRestriction` is not active exercises this unbounded-copy path. Whoever's transaction pays the energy for that outer transaction (the transaction sender — frequently a relayer forwarding calls on behalf of end users, exactly the actor called out in the original report) can be forced to pay for a memory allocation whose true cost was never charged at the `CALL` opcode. This is an underpriced/uncharged computational-work issue on a public, unprivileged code path (any user-deployed contract can trigger `CALL` to a precompiled address), and can be used to grief transaction senders/relayers or to inflate per-transaction resource consumption beyond what energy accounting reflects.

### Likelihood Explanation
The vulnerable branch is reached whenever the `allowTvmSelfdestructRestriction` chain proposal has not been activated on a given network (its existence as a guarded/newer branch strongly suggests it is not universally active by default across all java‑tron deployments/test/private networks, and any node running an older parameter set is exposed). Triggering it only requires an ordinary, unprivileged smart-contract call to a precompiled address with a small declared `outDataSize` while the corresponding precompiled contract returns a larger payload than declared — no special privileges are needed.

### Recommendation
Always bound the memory write/extend for precompiled-contract return data to the caller-declared `outDataSize`, independent of the `allowTvmSelfdestructRestriction` proposal state (i.e., make the safe/limited `memorySave(offset, outDataSize, out.getRight())` path the unconditional behavior), and ensure the CALL opcode's charged memory-expansion energy always matches what is actually written/extended. This removes the free-allocation path and enforces that copy costs on external-return data are always paid by the caller, mirroring the officially recommended fix of decoupling data-copy behavior from automatic/unbounded copying.

### Proof of Concept
1. Deploy an attacker contract `A` that:
   - Prepares call data in memory for a precompiled address whose output size scales with a caller-influenced input (e.g., a precompiled contract implementation that echoes/expands data based on input length).
   - Issues `CALL` (or `STATICCALL`) to that precompiled address with a small `outDataSize` (e.g., 32 bytes) declared on the stack, so the `EnergyCost` calculation for the CALL opcode only charges memory-expansion energy for 32 bytes.
2. On a network/config where `allowTvmSelfdestructRestriction` is not enabled, the precompiled contract executes and returns a much larger byte array than the declared `outDataSize`.
3. `Program.callToPrecompiledAddress` takes the `else` branch and calls `memorySave(offset, out.getRight())`, which calls `Memory.extend` to the full actual return size — memory grows far beyond what was declared/charged for the CALL, with no corresponding extra energy debit for that excess allocation.
4. Repeating/parametrizing this call inside a relayed transaction inflates the actual computational/memory cost paid by the transaction submitter (e.g. a relayer) without the energy metering reflecting the true cost, reproducing the griefing effect described in the original report. [6](#0-5)

  public void write(int address, byte[] data, int dataSize, boolean limited) {

    if (data.length < dataSize) {
      dataSize = data.length;
    }

    if (!limited) {
      extend(address, dataSize);
    }

    int chunkIndex = address / CHUNK_SIZE;
    int chunkOffset = address % CHUNK_SIZE;

    int toCapture = 0;
    if (limited) {
      toCapture = (address + dataSize > softSize) ? softSize - address : dataSize;
    } else {
      toCapture = dataSize;
    }

    int start = 0;
    while (toCapture > 0) {
      int captured = captureMax(chunkIndex, chunkOffset, toCapture, data, start);

      // capture next chunk
      ++chunkIndex;
      chunkOffset = 0;

      // mark remind
      toCapture -= captured;
      start += captured;
    }

    if (programListener != null) {
      programListener.onMemoryWrite(address, data, dataSize);
    }
  }

  public void extend(int address, int size) {
    if (size <= 0) {
      return;
    }
    final int newSize = addExact(address, size, VMConfig.disableJavaLangMath());
    int toAllocate = newSize - internalSize();
    if (toAllocate > 0) {
      addChunks((int) ceil((double) toAllocate / CHUNK_SIZE, VMConfig.disableJavaLangMath()));
    }

    toAllocate = newSize - softSize;
    if (toAllocate > 0) {
      toAllocate = (int) ceil((double) toAllocate / WORD_SIZE,
          VMConfig.disableJavaLangMath()) * WORD_SIZE;
      softSize = addExact(softSize, toAllocate, VMConfig.disableJavaLangMath());

      if (programListener != null) {
        programListener.onMemoryExtend(toAllocate);
      }
    }
  }
