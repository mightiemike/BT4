## Analysis

The reported bug class — an unconditional state reset triggered by *any* withdrawal (even a tiny one) that forfeits previously-accrued reward eligibility, disproportionate to the amount withdrawn — has a direct analog in `UnfreezeBalanceActuator` (the legacy freeze/vote mechanism in java-tron).

### Title
Unfreezing a trivial amount of BANDWIDTH/ENERGY unconditionally wipes all accumulated witness votes, forfeiting reward eligibility - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java`)

### Summary
`UnfreezeBalanceActuator.execute()` settles the caller's pending SR voting reward via `mortgageService.withdrawReward(ownerAddress)` and then, for BANDWIDTH/ENERGY unfreezes, unconditionally clears **all** of the account's votes (`accountCapsule.clearVotes()`) regardless of how small the unfrozen amount is relative to the account's total frozen/voting power.

### Finding Description
In `execute()`, after computing `unfreezeBalance` for the requested resource type, the actuator computes `needToClearVote`: [1](#0-0) 

`needToClearVote` defaults to `true` and is only set to `false` when `supportAllowNewResourceModel()` is enabled **and** `accountCapsule.oldTronPowerIsInvalid()` is already true. In the common/legacy path (old resource model, or new model but TronPower not yet invalidated), unfreezing *any* nonzero BANDWIDTH or ENERGY amount — even 1 sun, far below the account's total frozen balance and voting power — triggers `accountCapsule.clearVotes()`, wiping out the entire vote list built up over potentially many cycles.

This mirrors the reported "lost rewards upon withdrawal" pattern exactly: a state variable that gates future reward accrual (`votesList`, consumed by `MortgageService.withdrawReward`/`VoteRewardUtil.withdrawReward` via `beginCycle`/`endCycle` bookkeeping) is reset to empty on any withdrawal, not proportionally to the amount withdrawn or gated on whether the remaining frozen balance can no longer support the votes. [2](#0-1) 

Contrast this with the newer `UnfreezeBalanceV2Processor`/`UnfreezeBalanceActuator` TVM native-contract path, which only clears votes when `accountCapsule.getTronPower() < usedTronPower * TRX_PRECISION` — i.e., proportionally, only when the remaining frozen power can no longer cover the existing votes: [3](#0-2) 

The legacy `UnfreezeBalanceActuator` (v1, non-TVM, directly reachable from a broadcast `UnfreezeBalanceContract` transaction) lacks this proportionality check for the BANDWIDTH/ENERGY case, so any partial unfreeze forces a full vote-clear.

### Impact Explanation
A user who freezes a large balance, votes for SRs to accrue standby-witness rewards, and later unfreezes even a negligible amount of BANDWIDTH or ENERGY (e.g., to test withdrawal, or as part of routine resource management) will have their entire vote list cleared. This:
- Immediately stops future reward accrual for that account until they manually re-vote (`beginCycle` is advanced without votes, per `MortgageService.withdrawReward`).
- Silently and disproportionately destroys governance state (votes) that has no logical dependency on the tiny unfrozen amount.
- Can be triggered unintentionally, causing unexpected loss of ongoing reward eligibility — the same "silent economic harm from an oversized side effect of a small user action" class as the reported deposit-bonus bug.

### Likelihood Explanation
This is trivially reachable by any account holder via a standard `UnfreezeBalanceContract` transaction (broadcastable by anyone controlling frozen BANDWIDTH/ENERGY and existing votes). No privileged role or race condition is required — a user only needs to have frozen balance, cast votes, and then unfreeze any nonzero amount of BANDWIDTH or ENERGY while `oldTronPowerIsInvalid()` is false (the common state for most accounts using the legacy resource model, or new-model accounts before TronPower is invalidated).

### Recommendation
Align the legacy `UnfreezeBalanceActuator.execute()` clear-vote logic with the proportional logic already used in `UnfreezeBalanceProcessor`/`UnfreezeBalanceV2Actuator`: only clear votes when the account's remaining `TronPower` (post-unfreeze) is insufficient to cover its currently used vote count, rather than unconditionally clearing all votes on any nonzero BANDWIDTH/ENERGY unfreeze.

### Proof of Concept
1. Account freezes 10,000 TRX for BANDWIDTH and 10,000 TRX for ENERGY (accruing large TronPower).
2. Account votes for SRs using the full TronPower.
3. Several cycles pass, accruing standby-witness reward via `MortgageService.payReward`.
4. Account submits `UnfreezeBalanceContract` for ENERGY with the smallest possible unfreeze amount (unit balance).
5. `UnfreezeBalanceActuator.execute()` runs; because `oldTronPowerIsInvalid()` is false, `needToClearVote` remains `true`, and `accountCapsule.clearVotes()` is invoked, deleting the entire vote list even though only a negligible fraction of TronPower was released.
6. From the next cycle onward, the account earns zero additional voting reward until it manually re-casts all votes, despite retaining almost all of its original frozen balance and TronPower.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }
