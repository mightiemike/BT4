### Title
Webhook domain header is not covered by HMAC verification, enabling cross-tenant session hijack in webhook authentication - (File: packages/apps/shopify-api/lib/webhooks/validate.ts, packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts, packages/apps/shopify-app-react-router/src/server/authenticate/webhooks/authenticate.ts)

### Summary
This is the closest unprivileged analog to the ThunderNFT bug class ("one code path enforces a binding check, a related code path relies on the same check but omits the missing cross-field validation"). In the smart-contract bug, `place_order` verifies `msg_asset_id()`/`msg_amount()` match the order, but `update_order` skips that binding check, letting an attacker forge asset amounts. In shopify-app-js, `shopify.webhooks.validate`/`process` verifies the HMAC of the **raw body only**, and separately extracts the `X-Shopify-Shop-Domain` header as trusted metadata — but the header is never cryptographically bound to the HMAC-verified payload. The webhook authenticate handlers in `shopify-app-remix` and `shopify-app-react-router` then use that unauthenticated domain value directly as the key to load an offline session (with a real access token) from session storage and hand it to the app's webhook callback.

### Finding Description
`validateHmacFromRequestFactory` computes/compares the HMAC over `rawBody` alone: [1](#0-0) 

`validateFactory` (`shopify.webhooks.validate`) calls this HMAC check, and if it passes, separately reads headers (topic, domain, apiVersion, webhookId) via `checkWebhookHeaders`, which only enforces their *presence*, not their integrity: [3](#0-2) 

The webhook authenticate factories in both `shopify-app-remix` and `shopify-app-react-router` take `check.domain` — sourced purely from the unauthenticated `X-Shopify-Shop-Domain` header — and pass it straight into `ensureValidOfflineSession`, which loads (or creates) the offline session for that shop and attaches an authenticated `admin` API client built from that session to the webhook context handed to the app's callback: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the HMAC secret is a single per-app secret shared across every shop that installed the app (not per-shop), any actor who has installed the app on their own store (a "single merchant" — satisfying the "unprivileged actor" requirement) can capture one legitimate `(rawBody, hmac)` pair from their own store's webhook deliveries. They can then replay that exact body+HMAC to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and, for the events webhook type, `topic`) with a victim shop's domain. `validateHmacFromRequestFactory` will still report the HMAC as valid (it only checks the body), and the handler will resolve `check.domain` to the victim shop, load the victim's real offline session/access token from `sessionStorage`, and invoke the app's webhook business logic as if the (attacker-crafted) payload legitimately originated from the victim shop.

### Impact Explanation
This allows an attacker with no more privilege than "one merchant account that installed the target app" to make the target app process attacker-controlled webhook payloads under the identity/session of a completely different (victim) shop, with the app's real `admin` GraphQL/REST client for that victim shop attached to the context. Depending on what the app's webhook handlers do with the payload (e.g., orders/customers/fulfillment/inventory sync logic that writes back to the shop via the attached `admin` client, or GDPR/compliance topics), this can lead to unauthorized cross-tenant data manipulation, corruption, or disclosure in the victim's store — a cross-tenant/session-confusion vulnerability directly analogous to the "forged input accepted because the validation check doesn't bind all the relevant fields together" root cause of the smart-contract report.

### Likelihood Explanation
Medium-High. The attacker only needs to be able to install the target app on any shop they control (a normal, unprivileged action any merchant can perform) and capture one webhook delivery (trivial — install app, trigger an event, read the POST body/headers from their own endpoint or logs). No secrets, no MITM, and no elevated privileges are required; the webhook endpoint is by definition a public, unauthenticated HTTP endpoint. The main constraint on impact is the specific business logic in each app's registered webhook handler and whether the app performs any independent verification that the attacker-supplied domain "makes sense" for the received payload (which the library itself does not do or encourage).

### Recommendation
Bind the shop/domain identity to the same integrity check as the body: e.g., include the `X-Shopify-Shop-Domain` (and topic/webhookId, for events) header values inside the HMAC-signed material in `validateHmacFromRequestFactory`/`generateLocalHmac` for webhooks (Shopify already signs headers this way for App Proxy `signator: 'appProxy'` requests — the same discipline should be extended to webhook domain/topic headers), or, at minimum, cross-check that the resolved `domain` actually correlates to a session that was created via a legitimate OAuth/token-exchange flow for that specific webhook subscription (e.g., store the expected shop per registered webhook ID and compare on receipt) before attaching a live `admin` client to the webhook context.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-owned store), completing normal OAuth.
2. Attacker configures the app's webhook endpoint to log the raw POST body and headers of an incoming webhook (e.g., `orders/create`), capturing a valid `(rawBody, X-Shopify-Hmac-Sha256)` pair signed with the app's `apiSecretKey`.
3. Attacker sends a new POST to the same public webhook endpoint with:
   - Body = the exact captured `rawBody`
   - `X-Shopify-Hmac-Sha256` = the exact captured HMAC value
   - `X-Shopify-Shop-Domain` = `victim-shop.myshopify.com` (a shop that has an existing session in the app's `sessionStorage`)
   - Same/any valid `X-Shopify-Topic`, `X-Shopify-API-Version`, `X-Shopify-Webhook-Id` headers.
4. `validateHmacFromRequestFactory` accepts the request because only the body is HMAC-verified. [1](#0-0) 
5. `authenticateWebhookFactory` resolves `check.domain === 'victim-shop.myshopify.com'`, loads `victim-shop`'s real offline session via `ensureValidOfflineSession`, and invokes the app's webhook handler with `session`/`admin` bound to the victim shop but `payload` fully attacker-controlled. [7](#0-6) 

### What I could not fully verify
I was not able to inspect Shopify's server-side webhook delivery behavior (outside this repo) to confirm whether Shopify's own infrastructure applies any additional out-of-band protection (e.g., IP allow-listing at the platform level) that might mitigate real-world exploitability of a spoofed `X-Shopify-Shop-Domain` header reaching the app's endpoint directly — that is outside the scope of the shopify-app-js codebase itself, which is what this analysis is restricted to.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

function getRequiredHeader(
  headers: Headers,
  headerName: string,
  missingHeaders: string[],
): string | undefined {
  const value = getHeader(headers, headerName);
  if (!value) {
    missingHeaders.push(headerName);
  }
  return value;
}

function checkWebhookHeaders(
  headers: Headers,
  webhookType: WebhookTypeValue,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  if (webhookType === WebhookType.Webhooks) {
    return checkWebhooksHeaders(headers);
  }
  return checkEventsHeaders(headers);
}

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
