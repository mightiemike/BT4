### Title
`ensure_match_transaction_info` silently skips checkpoint-root verification, allowing corrupted trading-native/hot-state roots to pass replay-verify - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  is the canonical routine used by replay/verification tooling to check a locally-recomputed `TransactionOutput` against the authenticated `TransactionInfo` fetched from storage/backup. It validates status, gas, write-set hash (`state_change_hash`) and event root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents as a TODO.

### Finding Description
`ensure_match_transaction_info` is the single authoritative comparator between VM re-execution results and the transaction info that is bound into the ledger accumulator (and therefore proof-verified against a `LedgerInfoWithSignatures`). It is called from replay/verification utilities such as `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/cli/src/commands.rs`, whose entire purpose is to detect state-commitment divergence between independently computed execution and the already-committed, signature-backed ledger data.

The function checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

But `TransactionInfoV1` (introduced alongside `TRANSACTION_INFO_V1`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`, see [2](#0-1)  and [3](#0-2) ) carries three additional committed roots — `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — none of which are compared. These roots are produced by `DoStateCheckpoint::run`/`compute_position_checkpoint` ( [4](#0-3) ) and are exactly the kind of "committed state must match VM re-execution" invariant this Sherlock-style task is scoped to. The maintainers' own inline comment confirms the break: [5](#0-4) 

This is a direct structural analog to M-10: just as `prepForZeroHeightGenesis` omitted several required state-reset steps (allowing stale/incorrect state to silently carry over into the new genesis), `ensure_match_transaction_info` omits several required state-root comparisons (allowing a wrong/corrupted checkpoint root to silently pass as "verified"). In both cases the *coverage* of an integrity-check routine is incomplete relative to what the protocol now commits to durable/authenticated state, and the gap is not enforced anywhere else in the call chain — the function's own doc-comment says so.

### Impact Explanation
Once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled on-chain (both are marked "permanent" feature flags intended for mainnet use), the `position_state_checkpoint_hash` and `hot_state_checkpoint_hash` become part of what full nodes and validators cryptographically commit to in `TransactionInfoV1`, which is itself accumulator-hashed and signed by validators. If the local `state_summary`/`position_state_summary` computed by a node's storage layer diverges from the already-committed root (e.g. due to a bug in `compute_position_checkpoint`, a schema/replay bug in `state_restore`, or corrupted data feeding the native-position tree), `ensure_match_transaction_info` will report a clean match anyway, since it doesn't check those fields. Replay-verify tooling (`replay_on_archive`, debugger commands) built on top of this function is the primary defense used to catch exactly this class of divergence before it's treated as trusted archival/replay data. A silent pass means an incorrect committed root for the native-position/hot-state subsystem can go undetected by the verification tool, defeating the "proof/commitment integrity" guarantee for that subsystem.

### Likelihood Explanation
This requires the trading-native / hot-state feature flags to actually be enabled (`COMPUTE_TRADING_NATIVE_STATE_ROOTS` requires `TRANSACTION_INFO_V1` and `HOTNESS_IN_EPILOGUE`), so it is not an issue for legacy TransactionInfoV0 chains. But once enabled, the missing check is unconditional and deterministic — no adversarial input is needed to trigger the blind spot, only a genuine state divergence (bug, storage corruption, or non-determinism in the new position/hot-state trees) that the verification tool is specifically meant to catch. The maintainers' own TODO comment indicates they are aware but have not yet closed the gap, and no other call site independently re-verifies these three hashes when doing replay/verification.

### Recommendation
Extend `ensure_match_transaction_info` to also validate, when available on `txn_info`:
- `txn_info.state_checkpoint_hash()`,
- `txn_info.hot_state_checkpoint_hash()`,
- `txn_info.position_state_checkpoint_hash()`,

against the locally recomputed checkpoint/hot-state/position-state roots (threading them in as additional parameters, similar to `expected_write_set`/`expected_events`), before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are relied upon in production replay-verify or debugging workflows.

### Proof of Concept
Not applicable as an executable exploit — the finding is a code-level gap in an integrity-verification routine, confirmed via the routine's own source and its explicit TODO comment: [1](#0-0) . Demonstrating impact would require running a chain with `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` enabled, injecting a divergent position-state root during local re-execution, and observing that `replay_on_archive`/CLI replay-verify tooling reports success despite the mismatch — this requires a running node/test environment beyond static code review, so it is flagged as unverified dynamically but structurally proven by the code and comment above.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
