`UNIVERSAL_BATCH_CALL` exists as a reserved system-contract slot in `x/uregistry`, confirming Push Chain supports multiple gateway calls fanning out from a single payload execution transaction — one execution can emit multiple `UniversalTxOutboundEvent` logs in a single receipt. [1](#0-0) 

### Title
Single disabled/unmapped destination in a batched-outbound receipt permanently drops all outbounds from that transaction - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`BuildOutboundsFromReceipt` loops over every log in a payload-execution receipt and decodes each `UniversalTxOutboundEvent`. If any single decoded event targets a chain with outbound disabled, or references a PRC20 that has no reverse-mapped `TokenConfig`, the function immediately returns `nil, err` for the **entire** receipt — discarding all outbound records already built from prior logs in the same transaction, not just the bad one. Because the underlying EVM state (the `UEA`/gateway `withdraw` calls that lock/burn the PRC20 legs) has already been committed before this function runs, the valid legs' funds are left with no `OutboundTx` record, no TSS signing request, and no revert path. This is the Push Chain analog of the reported HoneyFactory bug: one "bad" entry in a loop blocks/discards processing for all other entries in the same batch.

### Finding Description
`BuildOutboundsFromReceipt` iterates `receipt.Logs` and, for each `UniversalTxOutboundEvent` found, calls `IsChainOutboundEnabled` and `GetTokenConfigByPRC20`. On the first failure it returns immediately: [2](#0-1) 

Note the `outbounds` slice accumulated from earlier iterations is thrown away — the function returns `nil` (not the partial slice) on error: [3](#0-2) 

This function is invoked from `AttachOutboundsToExistingUniversalTx`, which is called after a UEA payload finishes executing (already committed on `ctx`, not a cache context): [4](#0-3) 

When `AttachOutboundsToExistingUniversalTx` returns an error, the code path only records the error string on `UTX.RevertError` and returns `nil` — it does not roll back the EVM execution, does not create any revert/rescue outbound, and does not retry building the surviving valid outbounds: [5](#0-4) 

A user who controls the payload delivered via `MsgExecutePayload`/inbound execution (an ordinary, unprivileged flow — `MsgExecutePayload` is callable by "any" signer per the module docs) can use the `UNIVERSAL_BATCH_CALL` system contract to invoke the gateway's `withdraw`/`withdrawAndExecute` multiple times in one transaction, targeting several different (chain, token) pairs. If any one of those targets happens to have outbound disabled or lacks a `TokenConfig` reverse mapping (a normal, non-malicious registry state — no privileged/admin action required by the attacker), the entire batch of outbound records is silently dropped for that receipt, even though every other leg's funds were already withdrawn/locked on Push Chain. [6](#0-5) 

### Impact Explanation
This corrupts the canonical `UniversalTx` outbound state and causes permanent freezing of user/protocol-controlled funds: the on-chain PRC20 withdraw/lock for every leg of a batched payload already executed and committed, but zero `OutboundTx` entries are created for any of them when one leg is invalid. Without an `OutboundTx` entry, the funds are never queued into `PendingOutbounds` for TSS signing/broadcast, and — unlike normal inbound-validation failures which explicitly build an `INBOUND_REVERT` outbound — this failure path only stores a `RevertError` string with no automated recovery outbound. This falls squarely within the "permanent freezing of user or protocol-controlled funds" and "corruption of ... canonical UniversalTx state" allowed-impact categories.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a payload that fans out into multiple `withdraw` calls in a single EVM transaction (enabled by the existing `UNIVERSAL_BATCH_CALL` system contract) and (2) at least one of the targeted (chain, token) pairs being disabled/unmapped in `uregistry` at execution time — plausible since chain/token enablement changes over time and users don't necessarily know the current registry state when constructing multi-leg payloads. No privileged action or malicious validator/relayer is required; the trigger is purely a user-submitted payload plus ordinary registry configuration drift.

### Recommendation
In `BuildOutboundsFromReceipt`, do not abort the whole loop on a per-event failure. Instead, skip the invalid event (log a warning, optionally record it as an aborted/failed sub-entry) and continue processing the remaining logs, returning the outbounds that were successfully built. Where a leg cannot be safely converted to an outbound, attach a compensating action (e.g., a `RESCUE_FUNDS`-style outbound or explicit `ABORTED` outbound status) so the affected leg's funds are not silently stranded, mirroring the existing revert/rescue pattern used elsewhere in `x/uexecutor` (e.g., `handleFailedOutbound`, `AttachRescueOutboundFromReceipt`).

### Proof of Concept
Conceptual reproduction (exact batch-call payload encoding not fully verified against the live `UNIVERSAL_BATCH_CALL` ABI within this investigation):
1. Admin/registry state: chain A outbound enabled + token mapped; chain B outbound disabled (or its PRC20 has no `TokenConfig` reverse mapping).
2. User submits `MsgExecutePayload` whose payload, via `UNIVERSAL_BATCH_CALL`, calls `UniversalGatewayPC.withdraw()` twice in one EVM transaction: leg 1 → chain A (valid), leg 2 → chain B (outbound disabled).
3. `ExecutePayloadV2` executes and commits both withdraw calls on-chain (PRC20 locked/burned for both legs).
4. `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt` processes leg 1 successfully, appends to `outbounds`, then hits leg 2, calls `IsChainOutboundEnabled` → false, and returns `nil, err`, discarding leg 1's already-built outbound.
5. Result: `UTX.OutboundTx` remains empty; `UTX.RevertError` is set to the chain-B error string; leg 1's funds (for the valid chain A leg) have no `OutboundTx`/`PendingOutbounds` entry and are never signed/broadcast by TSS, nor reverted — permanently stuck.

This trace was constructed from static code reading only; I was not able to execute the integration test suite to confirm runtime behavior with an actual multi-log receipt from `UNIVERSAL_BATCH_CALL`, so the exact batching mechanics and whether any downstream safeguard exists outside the files reviewed should be verified before treating this as fully confirmed.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
