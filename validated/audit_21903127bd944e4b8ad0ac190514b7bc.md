## Title
Meta-transaction (`DelegateAction`/`DelegateActionV2`) signatures lack any chain/genesis domain separator, enabling cross-network replay of relayed transactions - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The NEP-366/NEP-611 meta-transaction signing scheme signs only a `MessageDiscriminant` (a hard-coded NEP number) concatenated with the borsh-serialized `DelegateAction`/`DelegateActionV2` payload. Unlike ordinary `SignedTransaction`s, which include a `block_hash` field anchoring the transaction to a specific chain's recent history, a `SignedDelegateAction`/`VersionedSignedDelegateAction` contains no chain identifier, genesis hash, or any other domain-separating value. This is the exact "signature is replayable across domains" bug class from the external report (missing `domainSeparator` binding signature to chain/contract/deployment identity), applied to NEAR's meta-transaction primitive.

### Finding Description
`SignableMessage::sign`/`verify` hashes only `discriminant || borsh(msg)`: [1](#0-0) 

The `discriminant` is a static constant per NEP (366 or 611), not something tied to a specific network: [2](#0-1) 

`DelegateAction` and `DelegateActionV2` themselves only carry `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` - no `chain_id`, no genesis hash, no network identifier: [3](#0-2) 

Replay protection for a delegate action is enforced only via the per-account, per-key `nonce` compared against on-chain state (`validate_delegate_action_key`) and `max_block_height` compared against the local `apply_state.block_height`: [4](#0-3) 

Both of these checks are evaluated **against locally stored per-chain state** — they do not encode which chain the signature was intended for. By contrast, ordinary `SignedTransaction`s include a `block_hash` referencing a specific recent block, which naturally diverges between two independently-evolving chains after a split, providing an *incidental* (not designed-in) domain binding that delegate actions completely lack.

In GitHub's tests, this is even called out as a known-narrow protection: the test relies on `nonce` reuse, not on any chain identity check, to reject replay: [5](#0-4) 

Whenever two NEAR-protocol-compatible networks share overlapping account/access-key state (e.g., a chain fork/split from a common genesis, a testnet or appchain bootstrapped from a mainnet state snapshot/export, or any deliberate/accidental chain fork where the same `sender_id` + `public_key` + `nonce` state coincide across the two chains), a `SignedDelegateAction` crafted and authorized by a user for execution on chain A can be captured by any relayer/observer and resubmitted verbatim on chain B. Because the signed payload contains no chain-identifying material, `SignedDelegateAction::verify`/`VersionedSignedDelegateAction::verify` will accept it on chain B exactly as it did on chain A, as long as the nonce on chain B's access key state has not yet advanced past the signed value and the local block height is still under `max_block_height`.

### Impact Explanation
A user who authorizes a meta-transaction (e.g., a token transfer, function call, or key/account management action) intending it to run on one network can have that exact authorization replayed by any third party (not just their chosen relayer) on another network sharing overlapping account/key state, causing the sender's intended action to execute a second, unauthorized time against their account on the other chain. This is unauthorized value movement/execution triggered purely by an unprivileged holder of the previously-published `SignedDelegateAction` bytes (relayers commonly gossip or the transaction becomes publicly visible once included in a block), matching "concrete unauthorized value movement" / "invalid state transition acceptance" criteria.

### Likelihood Explanation
Exploitation requires that two chains share coincident account/key/nonce state (a chain fork, a mainnet-genesis-derived testnet/appchain, or similar network duplication scenario), which is a realistic and recurring situation in blockchain ecosystems (chain splits, community forks, snapshot-based test networks). No cryptographic secrets are required — the attacker only needs to observe/capture an already-signed, previously-broadcast `SignedDelegateAction` and resubmit it as the relayer-signed outer action on the other chain.

### Recommendation
Bind the meta-transaction signature to the deploying chain by including a chain-specific value (e.g., genesis hash or a protocol-defined `chain_id`) inside the signed payload — either as an additional field on `DelegateAction`/`DelegateActionV2` or folded into the `MessageDiscriminant`/`SignableMessage` construction in `core/primitives/src/signable_message.rs` — and reject `apply_delegate_action` execution (`runtime/runtime/src/actions.rs`) if it does not match the current chain's identity, analogous to an EIP-712-style `domainSeparator`.

### Proof of Concept
1. On chain A, Alice signs `DelegateAction { sender_id: "alice.near", receiver_id: "bob.near", actions: [Transfer], nonce: N, max_block_height: H, public_key: pk }` via `SignedDelegateAction::sign` (`core/primitives/src/action/delegate.rs:92-95`), producing a signature bound to nothing but `discriminant(366) || borsh(delegate_action)`.
2. A relayer submits this on chain A; it executes normally.
3. Chain B is a network that shares Alice's `alice.near` account state (same public key, same or lower nonce for that key) — e.g., a fork of chain A from before this transaction, or a test/appchain seeded from chain A's exported genesis records.
4. Any party who has observed the `SignedDelegateAction` bytes (e.g., from chain A's public block data) wraps it as the sole action in a new outer `SignedTransaction` (any account can be the outer relayer) addressed to `bob.near` on chain B and submits it via chain B's JSON-RPC.
5. `apply_delegate_action` on chain B calls `signed_delegate_action.verify()` (`runtime/runtime/src/actions.rs:474`), which succeeds because the signature check never involves chain B's identity — only `validate_delegate_action_key`'s nonce/access-key check, which chain B's independent state satisfies if it has not yet consumed nonce `N`.
6. Alice's transfer action executes a second time against her account on chain B without her having authorized any action there.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

pub struct DelegateAction {
    /// Signer of the delegated actions
    pub sender_id: AccountId,
    /// Receiver of the delegated actions.
    pub receiver_id: AccountId,
    /// List of actions to be executed.
    ///
    /// With the meta transactions MVP defined in NEP-366, nested
    /// DelegateActions are not allowed. A separate type is used to enforce it.
    pub actions: Vec<NonDelegateAction>,
    /// Nonce to ensure that the same delegate action is not sent twice by a
    /// relayer and should match for given account's `public_key`.
    /// After this action is processed it will increment.
    pub nonce: Nonce,
    /// The maximal height of the block in the blockchain below which the given DelegateAction is valid.
    pub max_block_height: BlockHeight,
    /// Public key used to sign this delegated action.
    pub public_key: PublicKey,
}

#[derive(
    BorshSerialize,
    BorshDeserialize,
    Serialize,
    Deserialize,
    PartialEq,
    Eq,
    Clone,
    Debug,
    ProtocolSchema,
)]
#[cfg_attr(feature = "schemars", derive(schemars::JsonSchema))]
pub struct SignedDelegateAction {
    pub delegate_action: DelegateAction,
    pub signature: Signature,
}

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}
