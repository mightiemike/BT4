I have enough evidence now to confirm the unit-mismatch analog. `outbound.GasFee` is explicitly documented as "amount of GasToken paid to relayer" — i.e., denominated in units of the `gas_token` PRC20 (which can be any onboarded token, e.g. a 6-decimal stablecoin), set from the `UniversalTxOutboundEvent.GasFee` field [1](#0-0) . Meanwhile `obs.GasFeeUsed`, the value Universal Validators vote in via `MsgVoteOutbound`, is computed client-side purely from the destination chain's native gas asset: `gasUsed * gasPrice` in wei, with no reference to the `gas_token` denomination at all [2](#0-1) .

`applyGasRefund` then subtracts these two heterogeneous values directly as raw big.Int strings with no unit conversion:### Title
Excess gas refund is computed by subtracting a native-gas-denominated value from a gas-token-denominated fee, corrupting the refund amount on every observed outbound - ([File: x/uexecutor/keeper/outbound.go])

### Summary
This is the Push Chain analog of the Hyperdrive "wrong flat fee" bug: the original bug subtracted a base-asset amount from a share-asset amount without converting units first, producing a nonzero value where zero was expected. In `applyGasRefund`, Push Chain subtracts `obs.GasFeeUsed` (denominated in the destination chain's **native gas asset**, e.g. wei) from `outbound.GasFee` (denominated in the **gas_token PRC20** the relayer is actually paid in, e.g. a 6-decimal stablecoin) as if they were the same unit.

### Finding Description
`outbound.GasFee` is populated from the `UniversalTxOutboundEvent.GasFee` field, which is explicitly documented as "amount of `GasToken` paid to relayer" [3](#0-2) , and is written onto the `OutboundTx` record verbatim when the outbound is built from the EVM receipt [4](#0-3) . `gas_token` is a PRC20 address that can represent any onboarded external asset with its own decimals (per `x/uregistry` `TokenConfig.Decimals`, e.g. 6 for USDC/USDT) [5](#0-4) .

`obs.GasFeeUsed`, by contrast, is what Universal Validators compute and vote via `MsgVoteOutbound` — the EVM client helper `GetGasFeeUsed` (and the equivalent enrichment in `event_confirmer.go`) computes it strictly as `gasUsed * gasPrice` in the destination chain's **native wei/lamport-equivalent gas asset**, with no reference at all to the outbound's `gas_token`: [6](#0-5) 

Once the ballot for the vote finalizes, `applyGasRefund` parses both strings as raw big.Ints and subtracts them directly, with no decimal/denomination normalization step: [7](#0-6) 

```go
gasFee := new(big.Int)
gasFee.SetString(outbound.GasFee, 10)      // denominated in gas_token PRC20 units
gasFeeUsed := new(big.Int)
gasFeeUsed.SetString(obs.GasFeeUsed, 10)   // denominated in native gas wei
...
refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
```

This mirrors exactly the Hyperdrive pattern: `_baseAmount.divDown(_sharePrice) - _shareReservesDelta` mixed a base-denominated quantity with a share-denominated quantity in one subtraction, producing a nonzero "flat fee" that should have been zero. Here, a native-gas-wei quantity is subtracted from a gas-token quantity, producing a `refundAmount` that has no coherent real-world meaning whenever the gas token isn't already pegged 1:1 (in raw integer units) to the native asset's wei value.

`refundAmount` is then passed straight into `CallUniversalCoreRefundUnusedGas`, which mints/transfers that many units of the PRC20 `gas_token` to the recipient [8](#0-7) , and the underlying handler mints/moves `amount` of `gasToken` on the EVM side [9](#0-8) .

### Impact Explanation
For gas tokens whose smallest unit doesn't correspond 1:1 to destination-chain wei (essentially any gas token with fewer than 18 decimals, or any decimal-count mismatch versus the native asset), the refund amount is arbitrarily wrong:
- If `outbound.GasFee` (gas_token raw units, e.g. 6-decimal USDC) happens to be numerically larger than `obs.GasFeeUsed` (18-decimal wei), the protocol computes and pays out a hugely inflated "refund" in the PRC20 gas token relative to what was actually overpaid — an unauthorized over-mint/over-transfer of protocol-controlled PRC20 funds to the outbound sender/fund_recipient, satisfying the "unauthorized mint" / "corruption of PRC20 accounting" allowed-impact categories, reachable purely by an ordinary user's outbound completing (no privileged actor needed — the wrong math executes for every successful outbound where `gas_token` isn't the native 18-decimal asset).
- If `obs.GasFeeUsed` is numerically larger (likely, since wei values are usually much bigger magnitude than low-decimal token units), `gasFee.Cmp(gasFeeUsed) <= 0` triggers and the refund is silently skipped even when a real overpayment happened — a permanent, protocol-level loss of user refund entitlement.

Because this computation runs deterministically from consensus-agreed vote data (`obs.GasFeeUsed` is part of the ballot key [10](#0-9) ) all honest nodes converge on the same (wrong) refund amount, so it does not cause a consensus fork — but it does silently corrupt PRC20 accounting and misroute value.

### Likelihood Explanation
This triggers on every `MsgVoteOutbound` finalization for an outbound whose `gas_token` is not the native 18-decimal asset of the destination chain — a completely ordinary, unprivileged flow (any user's cross-chain outbound with a non-native gas token, e.g. USDC-denominated relayer fees). No malicious validator, admin, or attacker action is required; honest UVs report `GasFeeUsed` exactly as designed via `GetGasFeeUsed`/`event_confirmer.go`, and the bug lies purely in the module's mismatched-unit subtraction. The existing test suite (`test/integration/uexecutor/gas_fee_refund_test.go`) exercises `applyGasRefund` only with same-magnitude mock integers ("111", "50", "999") that happen not to expose the units mismatch, so the defect is not caught by current tests.

### Recommendation
Before subtracting, convert `obs.GasFeeUsed` from native-gas-asset units into `outbound.GasToken` units using the same price/decimals conversion the `UniversalCore` contract uses when it originally computed `outbound.GasFee` (i.e., call the equivalent of `getOutboundTxGasAndFees`'s pricing logic, or have validators report `GasFeeUsed` already denominated in `gas_token` units before voting). Only after both operands are in the same denomination should `applyGasRefund` compute `refundAmount = gasFee - gasFeeUsedInGasToken`. Add a unit/integration test using a `gas_token` with non-18 decimals and a native-asset gas price that would expose a unit mismatch (e.g. `gas_token` decimals = 6, native gas wei magnitude vastly different) to lock in correct behavior.

### Proof of Concept
1. Register an external chain and token whose `NativeRepresentation`/gas_token uses 6 decimals (e.g. USDC-style PRC20) as the outbound's `gas_token`, with `UniversalCore.getOutboundTxGasAndFees` returning `gasFee = 5_000_000` (5 USDC, 6 decimals) for this outbound — this becomes `outbound.GasFee`.
2. Let the outbound actually execute on the destination chain consuming `gasUsed = 21000`, `gasPrice = 20_000_000_000` (20 gwei) → native wei cost = `420_000_000_000_000` (0.00042 ETH). Universal Validators report this raw wei value as `obs.GasFeeUsed = "420000000000000"` per `GetGasFeeUsed` [2](#0-1) .
3. Submit `MsgVoteOutbound` with `success=true`, `gas_fee_used="420000000000000"` from 2/3+ Universal Validators to finalize the outbound ballot.
4. `handleSuccessfulOutbound` → `applyGasRefund` runs: `gasFee.Cmp(gasFeeUsed) <= 0` is true (5,000,000 < 420,000,000,000,000), so the "no excess to refund" branch fires and the refund is skipped even though the relayer clearly wasn't paid the full 5 USDC gas fee amount they were quoted, illustrating the unit corruption directly (in the opposite-magnitude case, the refund fires and mints an absurd PRC20 amount instead). Either direction demonstrates the fee/refund math is operating on mismatched units, exactly analogous to the reported Hyperdrive flat-fee bug.

// GetGasFeeUsed returns the gas fee used by a transaction on the EVM chain.
// Fetches the receipt for gasUsed and the transaction for gasPrice, then returns
// gasUsed * gasPrice as a decimal string. Returns "0" if not found.
func (tb *TxBuilder) GetGasFeeUsed(ctx context.Context, txHash string) (string, error) {
	hash := ethcommon.HexToHash(txHash)
	receipt, err := tb.rpcClient.GetTransactionReceipt(ctx, hash)
	if err != nil {
		return "0", nil
	}

	tx, _, err := tb.rpcClient.GetTransactionByHash(ctx, hash)
	if err != nil {
		return "0", nil
	}

	gasUsed := new(big.Int).SetUint64(receipt.GasUsed)
	gasPrice := tx.GasPrice()
	if gasPrice == nil || gasPrice.Sign() == 0 {
		return "0", nil
	}

	gasFeeUsed := new(big.Int).Mul(gasUsed, gasPrice)
	return gasFeeUsed.String(), nil

// applyGasRefund computes the excess gas (gasFee - gasFeeUsed) and, if positive,
// calls UniversalCore refundUnusedGas. The result is recorded in outbound.PcRefundExecution.
// It is called for both successful and failed outbounds — gas is consumed on the
// external chain regardless of execution outcome.
func (k Keeper) applyGasRefund(ctx sdk.Context, outbound *types.OutboundTx, obs *types.OutboundObservation) {
	if obs.GasFeeUsed == "" || outbound.GasFee == "" || outbound.GasToken == "" {
		return
	}

	gasFee := new(big.Int)
	if _, ok := gasFee.SetString(outbound.GasFee, 10); !ok {
		return
	}

	gasFeeUsed := new(big.Int)
	if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok {
		return
	}

	// No excess gas to refund
	if gasFee.Cmp(gasFeeUsed) <= 0 {
		return
	}

	refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
