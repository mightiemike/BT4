### Title
Config-tightening protocol upgrades can permanently brick the delayed-receipt queue via unguarded `max_actions_per_receipt` / `max_total_prepaid_gas` checks - (File: `runtime/runtime/src/action_validation.rs`)

### Summary
`validate_actions_with_mode` enforces `max_actions_per_receipt` and `max_total_prepaid_gas` unconditionally, without gating on `ValidateReceiptMode`, unlike several other limits in the same function that were deliberately made mode-aware to avoid exactly this failure. If a future runtime-config/protocol-version upgrade lowers either limit, a receipt that was valid and got persisted into the FIFO delayed-receipt queue under the old (looser) limit will fail validation when it is later dequeued under `ExistingReceipt` mode, producing a fatal `StorageInconsistentState` error that aborts the entire chunk apply — bricking the delayed queue for that shard, analogous to the reported Y2K `relayerFee` FILO-queue-bricking bug.

### Finding Description
`validate_receipt` is called on every delayed receipt when it is popped from the persistent FIFO queue, using `ValidateReceiptMode::ExistingReceipt`: [1](#0-0) 

If this validation fails, the runtime treats it as a fatal, unrecoverable error rather than skipping/dropping the offending receipt: [1](#0-0) 

`validate_receipt` → `validate_action_receipt` → `validate_actions_with_mode` (`runtime/runtime/src/verifier.rs:742-770`, `runtime/runtime/src/action_validation.rs:86-153`) is the checking function. The developers were clearly aware that tightening limits over time could invalidate already-queued receipts, and deliberately gated some checks by `mode == ValidateReceiptMode::NewReceipt` so they are skipped for `ExistingReceipt`s already in flight: [2](#0-1) 

The accompanying test explicitly documents the rationale — that enforcing a new/tighter limit against `ExistingReceipt`s "would fail the whole chunk": [3](#0-2) 

However, two other checks in the exact same function are **not** gated by `mode` at all and run unconditionally for both `NewReceipt` and `ExistingReceipt`:

- The total-actions-per-receipt limit: [4](#0-3) 

- The total-prepaid-gas limit: [5](#0-4) 

Both `max_actions_per_receipt` and `max_total_prepaid_gas` are ordinary versioned `RuntimeConfig` parameters (analogous to a timelocked `relayerFee`): they can be lowered by a scheduled protocol-version/config upgrade whose activation height is known in advance, exactly as the timelocked `relayerFee` change is known in advance in the Y2K report.

### Impact Explanation
An attacker who observes an upcoming protocol upgrade that lowers `max_actions_per_receipt` or `max_total_prepaid_gas` can, before the upgrade activates:
1. Submit a transaction/receipt whose action count or total prepaid gas is within the *current* (larger) limit but above the *future* (smaller) limit.
2. Force that receipt into the persistent delayed-receipt FIFO queue (e.g. by congesting the target shard so `process_incoming_receipts`/`process_local_receipts` defer it — this is the normal, permissionless congestion-control push path documented at `runtime/runtime/src/lib.rs:2707-2711` and `:2385`).
3. Once the upgrade activates, `process_delayed_receipts` will dequeue this receipt and re-validate it with `ExistingReceipt` mode; because the two limits above are unconditionally enforced, validation fails.
4. The failure is mapped to `StorageError::StorageInconsistentState`, which propagates as a fatal `RuntimeError` out of `Runtime::apply`, aborting chunk application for the shard.

Because the delayed queue is strict FIFO (`TrieQueue`, `core/store/src/trie/receipts_column_helper.rs`), this poisoned receipt sits at the head of the queue forever and every subsequent chunk-apply attempt on that shard hits the same fatal error — the shard can never make forward progress again ("transaction-triggered halt"), matching the accepted impact class (transaction-triggered halt / invalid state transition acceptance path denial).

### Likelihood Explanation
This requires a real network condition (a protocol upgrade that lowers one of these two specific limits) to be scheduled, combined with an attacker deliberately front-running it. Likelihood of the precondition (a limit-lowering upgrade) occurring is protocol-governance-dependent and not something an attacker controls, which lowers overall likelihood versus the Sherlock original (where the timelocked fee change is a routine, frequent admin action). However, the code comments and tests in `action_validation.rs` show the nearcore team is already aware this exact scenario is dangerous and mitigated it for *other* limits (`max_deploy_actions_per_receipt`, `max_state_init_entries`, delegate-related removals) but missed `max_actions_per_receipt` and `max_total_prepaid_gas`, so the mitigation is inconsistent/incomplete rather than absent by design — a single future config change to either parameter (in a direction that lowers it) would immediately create a chain-halting condition.

### Recommendation
Gate the `max_actions_per_receipt` and `max_total_prepaid_gas` checks in `validate_actions_with_mode` (`runtime/runtime/src/action_validation.rs:93-98` and `:143-150`) the same way `max_deploy_actions_per_receipt` and `max_state_init_entries` are already gated: only enforce them under `ValidateReceiptMode::NewReceipt`, and treat `ExistingReceipt`s (whether incoming or dequeued from the delayed queue) leniently, consistent with the documented intent that "a receipt built before it took effect has to keep executing." Alternatively, add an explicit migration step that drains/re-validates the delayed queue before any protocol upgrade that lowers either limit takes effect, or downgrade validation failures on `ExistingReceipt` to a per-receipt error outcome instead of a fatal `RuntimeError`.

### Proof of Concept
Not independently executable from static analysis alone; the vulnerable code path is directly demonstrated by:
1. `runtime/runtime/src/action_validation.rs:93-98` and `:143-150` — unconditional (not `mode`-gated) checks.
2. `runtime/runtime/src/action_validation.rs:117-123` — sibling checks in the same function that *are* `mode`-gated, showing the intended mitigation pattern that was not applied to the two flagged checks.
3. `runtime/runtime/src/action_validation.rs:1809-1823` — test comment explicitly stating that enforcing a tightened limit against `ExistingReceipt`s "would fail the whole chunk."
4. `runtime/runtime/src/lib.rs:2628-2640` — where an `ExistingReceipt` validation failure on a delayed receipt is converted into a fatal `StorageError::StorageInconsistentState`, aborting `Runtime::apply` for the whole chunk.

A concrete reproduction would require: (a) a test harness that lowers `max_actions_per_receipt`/`max_total_prepaid_gas` between two `RuntimeConfig` versions, (b) enqueuing a receipt valid under the old config into the delayed queue (e.g. via `test_apply_delayed_receipts_adjustable_gas_limit`-style congestion), and (c) applying a chunk under the new config to observe the `RuntimeError` — this was not run, so the impact is derived from direct code/documentation inspection rather than a live exploit trace.
