### Title
Double-precision rounding in standby witness reward distribution can zero-out legitimate reward shares - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The reported bug class is: a proportional-share calculation performed with limited numeric precision that can round down to `0` for a legitimate participant, causing that participant to receive none of an entitlement they are otherwise due. The strongest reachable analog of this exact pattern in java-tron is the standby-witness reward split in `MortgageService.payStandbyWitness()`, which computes each witness's share of the fixed per-block "witness-127" allowance using `double` arithmetic and then truncates the result to a `long`, which can silently round a witness's fractional reward down to zero.

### Finding Description
`MortgageService.payStandbyWitness()` computes:
```java
double eachVotePay = (double) totalPay / voteSum;
for (WitnessCapsule w : witnessStandbys) {
  long pay = (long) (w.getVoteCount() * eachVotePay);
  payReward(w.getAddress().toByteArray(), pay);
}
``` [1](#0-0) 

`totalPay` is the fixed `WITNESS_127_PAY_PER_BLOCK` allowance (16,000,000 sun by default) [2](#0-1) , and `voteSum` is the sum of vote counts across up to `WITNESS_STANDBY_LENGTH` (127) standby witnesses. When a witness's `voteCount` is small relative to `voteSum` (e.g. a witness barely qualifying for the standby list while other witnesses hold overwhelmingly larger vote totals), `w.getVoteCount() * eachVotePay` can be less than `0.5`, and the `(long)` cast truncates it to `0`. That witness then receives `0` reward for the block/cycle via `payReward`, even though they are legitimately entitled to a nonzero (if tiny) fractional share of `totalPay`. This directly mirrors the reported bug's root cause: `optionShare = (optionTokenBalance * 1e18) / totalOptionTokenSupply` truncating to `0` when the numerator is small relative to the denominator, causing the entitled party to get nothing.

Unlike other proportional-share computations in this codebase (e.g. `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, which validate the computed cross amount and reject the transaction if it rounds to `<= 0` [3](#0-2) , or `RepositoryImpl`/`BandwidthProcessor`/`EnergyProcessor`, which have been hardened with `BigInteger`-based exact-precision paths gated by `allowHardenResourceCalculation`/`hardenCalculation` flags [4](#0-3) ), the standby witness reward path in `MortgageService.payStandbyWitness()` has no such precision hardening or zero-result guard.

### Impact Explanation
The impact is a reward-accounting correctness defect: a legitimately elected standby witness whose vote share is small relative to the pool of standby witnesses can be paid `0` for a given block/cycle, even though they are entitled to a nonzero fractional reward. Repeated over many blocks, this systematically under-pays low-vote standby witnesses, silently deviating from the intended proportional-reward design (an unrecoverable rounding loss, since the truncated remainder is not carried forward or redistributed).

### Likelihood Explanation
This code path executes automatically on every block once `allowChangeDelegation` is enabled (the current reward regime), as `Manager.payReward()` unconditionally calls `mortgageService.payStandbyWitness()` for each produced block [5](#0-4) . No attacker action or malicious transaction is required; it is triggered purely by normal chain operation whenever the vote distribution among the 127 standby witnesses is sufficiently skewed, which is a realistic and likely condition on a live network with many low-vote standby witnesses.

### Recommendation
Replace the `double`-based proportional calculation in `MortgageService.payStandbyWitness()` with an exact-precision integer computation (e.g. `BigInteger` multiply-then-divide, consistent with the hardened patterns already used elsewhere in this codebase such as `RepositoryImpl.calculateGlobalEnergyLimit` and `ResourceProcessor`), so that a witness's reward share is computed and truncated only once at the very end, minimizing avoidable rounding-to-zero cases, and consider carrying/accumulating fractional remainders across cycles rather than discarding them.

### Proof of Concept
1. Configure a set of standby witnesses such that `voteSum` is large (e.g. 127 witnesses collectively holding a very large aggregate vote count) while one particular standby witness `W` has a comparatively tiny vote count.
2. With `totalPay = WITNESS_127_PAY_PER_BLOCK` (default 16,000,000 sun), compute `eachVotePay = totalPay / voteSum` as a `double`.
3. If `W.getVoteCount() * eachVotePay < 1.0`, the `(long)` cast in `payStandbyWitness()` truncates `pay` to `0`, and `payReward(W.address, 0)` is called — `W` receives no reward for that block despite holding a nonzero, legitimately entitled vote share, reproducing the same class of zero-reward-due-to-truncation described in the external report.

  public void payStandbyWitness() {
    List<WitnessCapsule> witnessStandbys = witnessStore.getWitnessStandby(
        dynamicPropertiesStore.allowWitnessSortOptimization());
    long voteSum = witnessStandbys.stream().mapToLong(WitnessCapsule::getVoteCount).sum();
    if (voteSum < 1) {
      return;
    }
    long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
    double eachVotePay = (double) totalPay / voteSum;
    for (WitnessCapsule w : witnessStandbys) {
      long pay = (long) (w.getVoteCount() * eachVotePay);
      payReward(w.getAddress().toByteArray(), pay);
      logger.debug("Pay {} stand reward {}.", Hex.toHexString(w.getAddress().toByteArray()), pay);
    }
  }
