### Title
Multi-signature weight can be double-counted for a single key in `ValidateMultiSign`, bypassing the account's signature threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract, which TVM smart contracts use to verify that a set of signatures meets an account's `Permission` threshold, contains a duplicate-detection bug that lets the same signing key contribute its weight to the total more than once, as long as the individual signature bytes differ. This is analogous to the reported HSG issue, where signature-counting logic failed to enforce uniqueness/consistency of the signatures being tallied against the threshold, letting a party "sign" more than intended and defeat the multisig guarantee.

### Finding Description
`ValidateMultiSign.execute` accumulates `totalWeight` from `permission.getKeysList()` weights for every provided signature, guarding against duplicates via `executedSignList`: [1](#0-0) 

The dedup check is:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
        continue;
    }
    MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
The intent appears to be: if `recoveredAddr` has already contributed weight, skip it (i.e., `continue`). Instead, the code only `continue`s when the *exact same signature bytes* were already seen; if the recovered address is already in the list but the signature bytes differ, execution simply calls `MUtil.checkCPUTime()` and falls through to add the weight again. Because ECDSA signing is not required to be deterministic here (and even with deterministic nonces an attacker fully controls their own key and can trivially produce two distinct valid `(v,r,s)` signatures over the same hash from the same private key), a single key can supply multiple distinct signatures for the same `hash` and have its weight counted multiple times (bounded only by `MAX_SIZE = 5`).

This contrasts with the correct pattern used elsewhere in the codebase, `TransactionCapsule.checkWeight`, which (post fork `VERSION_4_7_1`) keys its duplicate map by the recovered **address**, guaranteeing one weight contribution per signer regardless of how many distinct signatures that signer submits: [2](#0-1) 

`ValidateMultiSign` lacks this guarantee, so its threshold check can be satisfied by fewer distinct signers than the permission's `Key` set actually requires — the same underlying bug class as the report: signature-counting logic that does not consistently track "one signature per distinct signer" against the threshold, allowing effective weight inflation.

### Impact Explanation
`ValidateMultiSign` is exposed to any TVM contract via the precompile address and is meant to let smart contracts verify TRON account multisig approvals (e.g., escrow/custody contracts gating fund releases on an account's `Permission` threshold). An attacker who controls a single key present in the permission's key list (even with a small weight) can synthesize multiple distinct signatures over the same `hash` from that one key and have the corresponding weight counted multiple times, potentially reaching `permission.getThreshold()` without collecting approvals from the other required signers. This is an unauthorized-account-operation / accounting-corruption class vulnerability: contracts that rely on `ValidateMultiSign` to gate on-chain fund transfers or privileged actions can be tricked into believing sufficient independent approvals exist when they do not.

### Likelihood Explanation
Exploitation only requires: (1) an on-chain contract that calls `ValidateMultiSign`, and (2) the attacker controlling one key listed in the target account's active permission with nonzero weight. Producing multiple valid distinct signatures from one's own private key over the same hash requires no special access — it's just resigning (or using standard ECDSA signature malleability transforms `(r, n-s, v flipped)`). No privileged access, leaked keys, or malicious peers are needed, making this reachable purely through crafting the `signatures` array argument to a broadcast/contract call.

### Recommendation
Change the dedup logic so that once `recoveredAddr` has contributed weight, any further signature recovering to the same address is skipped outright (i.e., always `continue` when `matrixContains(executedSignList, recoveredAddr)` is true), matching the address-based uniqueness enforcement already used in `TransactionCapsule.checkWeight`:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    continue;
}
```
removing the fallthrough path that allows a second, distinct signature from an already-counted address to add weight again.

### Proof of Concept
1. Create an account with an active `Permission` of `threshold = 2`, containing key `K1` (weight 1) and key `K2` (weight 1).
2. Attacker controls only `K1`.
3. Compute `hash` per `ValidateMultiSign`'s combine/Sha256 scheme (address, permissionId, data).
4. Using `K1`, produce two different valid signatures over `hash` — e.g. sign twice (ECDSA `k` need not be identical across calls in the general signing API), yielding `sig1 != sig2` but both recovering to `K1`'s address.
5. Call `ValidateMultiSign(address, permissionId, data, [sig1, sig2])`.
6. In `execute`, the loop processes `sig1`: `recoveredAddr = K1`, not yet in `executedSignList`, weight 1 added, totalWeight = 1.
7. Loop processes `sig2`: `recoveredAddr = K1` is now in `executedSignList`, but `sig2` (exact bytes) is not, so it does **not** `continue`; it proceeds to add weight 1 again, totalWeight = 2.
8. `totalWeight (2) >= threshold (2)` → returns `dataOne()` (success), even though only one distinct signer (`K1`) actually approved. `K2`'s approval was never obtained. [3](#0-2)
