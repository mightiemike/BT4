In the Starknet OS Cairo re-execution path, `execute_replace_class` at [1](#0-0)  takes the `class_hash` from the syscall request and directly writes it into the contract's state entry **without verifying that a class was actually declared with that hash**, marked by an explicit TODO acknowledging the gap. This mirrors the reported bug class exactly: a privileged/critical parameter (here, the class hash used to permanently mutate a contract's code) is accepted and committed without validation in the code path that computes the OS's state changes and, ultimately, the state commitment.

By contrast, the Rust `blockifier` execution engine that actually executes transactions during block building *does* perform this check — `replace_class` in `syscall_base.rs` calls `self.state.get_compiled_class(class_hash)?` before writing the new class hash [2](#0-1) , and the deprecated syscall handler does the same [3](#0-2) . This is confirmed by tests asserting rejection of undeclared class hashes [4](#0-3) .

### Title
Unvalidated class hash in OS `execute_replace_class` allows committing state with an undeclared class - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The Starknet OS Cairo program's `execute_replace_class` function (used during proof generation / OS re-execution to produce `contract_class_changes` and the final state commitment) does not verify that `request.class_hash` corresponds to a class that was actually declared. It merely reads the current state entry and overwrites `class_hash` in the new `StateEntry`, deferring the check with an explicit `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.` comment.

### Finding Description
In `execute_replace_class` [1](#0-0) , the request's `class_hash` is taken as-is:
```
let class_hash = request.class_hash;

// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
local state_entry: StateEntry*;
%{ GetContractAddressStateEntry %}

tempvar new_state_entry = new StateEntry(
    class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
);
```
There is no `assert_not_zero`, no lookup into `contract_class_changes`, and no cross-check against a `finalize_class_hash`/declared-class dictionary before this value is committed to `contract_state_changes`. The equivalent deprecated-syscall implementation in the same file, `execute_replace_class` for the Cairo0 path [5](#0-4) , has the exact same gap — no validation at all.

This is inconsistent with the production `blockifier` execution engine, which is supposed to be semantically equivalent to (and re-verified by) the OS. The Rust `syscall_base::replace_class` explicitly fetches the compiled class (`self.state.get_compiled_class(class_hash)?`) to force an error if it is undeclared, and additionally checks the class is Cairo1 before allowing the replacement [2](#0-1) .

Because the OS's job is to re-execute the block and independently derive `contract_class_changes`/`contract_state_changes` that feed into the state commitment and block hash, if the OS's Cairo implementation of `execute_replace_class` does not perform the same validation as blockifier, a class hash that blockifier would have rejected (undeclared, or not properly linked to a `ContractClassComponentHashes`) could still be accepted and committed by the OS side, producing a state root/commitment that diverges from what an honest client (using blockifier's stricter check) would expect, or allowing state to reference a "class" with no corresponding declared/compiled representation.

### Impact Explanation
An unvalidated class hash written into the committed contract state entry allows an attacker-controlled `replace_class` invocation to set the contract's class hash to an arbitrary felt (including one for which no class was ever declared/compiled). Because this occurs in the OS's Cairo state-transition logic — the code that produces the final `contract_state_changes` dict used to compute the Patricia tree / global state commitment — this can produce a wrong committed state root relative to what should be produced under proper validation, i.e., a state root that does not correspond to a coherent, executable state. Any subsequent call into that contract address would reference a non-existent CASM/Sierra class, and the state commitment would not match blockifier's independently-computed result, causing an honest-node/prover divergence on that block.

### Likelihood Explanation
`replace_class` is a permissionless syscall reachable directly by any deployed account/contract executing an ordinary transaction — no special privileges are required, only that the caller's contract invokes the `replace_class` syscall with an arbitrary `class_hash` felt. Since the missing check is explicitly flagged with a TODO in the source, this is a known, currently-unaddressed gap in this code path.

### Recommendation
Add the equivalent declared-class existence check in the Cairo `execute_replace_class` implementation(s) — mirroring `syscall_base::replace_class` in blockifier — by validating the given `class_hash` against the OS's set of declared/compiled class hashes (e.g., cross-referencing `contract_class_changes` / the declared-classes dictionary populated during declare-transaction processing and `finalize_class_hash`) before writing the new `StateEntry`, for both the Cairo1 syscall path (`syscall_impls.cairo`) and the deprecated Cairo0 path (`deprecated_execute_syscalls.cairo`).

### Proof of Concept
1. Deploy a Cairo1 contract that exposes an entry point calling `replace_class_syscall(class_hash)` with a caller-supplied `class_hash` (e.g., `test_contract.cairo`'s `test_replace_class`, reachable via ordinary `INVOKE` transaction) [6](#0-5) .
2. Submit an `INVOKE` transaction calling this entry point with an arbitrary, never-declared `class_hash` felt (e.g. `0x1234`).
3. blockifier (used for actual sequencing/execution) will reject this with `"is not declared"` per its check [4](#0-3) ; however, if the same transaction/block is re-executed by the Starknet OS Cairo program (used for proving), `execute_replace_class` in `syscall_impls.cairo` performs no such check and would happily commit the arbitrary class hash into `contract_state_changes`, producing a divergent state entry/commitment relative to the blockifier-derived state for the same block.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
