## Analysis

Confirmed from `runtime/runtime/src/deterministic_account_id.rs:117-133` (`create_deterministic_account`): a NEP-616 deterministic account (`0s…` id) is created with `AccountContract::None` and **no access key at all** — "Unlike `CreateAccount`, this account creation does not change `actor_id`... preventing `AddKey`, `DeployContract`, or any other actions that only the account owner is permitted to do." Its contract is set exclusively via `use_global_contract` (`deploy_deterministic_account`, line 151), where `state_init.code()` is a `GlobalContractIdentifier` that can be `AccountId(publisher)` (mutable) rather than `CodeHash` (immutable) — confirmed in `core/primitives-core/src/global_contract.rs:25-38` and documented explicitly in `docs/RuntimeSpec/Actions.md:440-449`: *"Contract is deployed under the owner account id... This allows the owner to update the contract for all its users."*

This exactly mirrors the `AutoCompound`/`Automator` pattern: a third-party ("vault"/"global contract publisher") controls a mutable state variable that downstream depositors implicitly trust, and that state can be changed unilaterally after users have already committed funds, with no fallback path for those users to recover access. Unlike a `Named` account (which always has an owner-controlled full-access key it can use to redeploy/fix its own contract or delete the account), a deterministic account by design has **no key whatsoever**; the *only* way to interact with it is through whatever code is currently addressed by its `GlobalContractIdentifier`. If a user builds/funds a deterministic account whose `code` field is `GlobalContractIdentifier::AccountId(publisher)`, that publisher can later call `DeployGlobalContractByAccountId` with different code (`action_deploy_global_contract` / `runtime/runtime/src/global_contracts.rs:25-63`, `GlobalContractDeployMode::AccountId`) — an ordinary unprivileged transaction — and the runtime resolves the contract for the deterministic account through this same identifier every time (`RuntimeContractIdentifier::resolve`, `runtime/runtime/src/contract_code.rs:36-73`). If the publisher deploys code lacking a transfer/withdraw path (intentionally or by accident), every deterministic account pointing at that `AccountId` identifier permanently loses any means to move its balance out, since there is no full-access key fallback (as there would be for a `Named` account).

I was not able to fully verify within the available searches whether there is any protocol-level safeguard preventing a deterministic account from being created against an `AccountId`-mode identifier specifically (versus requiring `CodeHash` mode), nor whether the `DeleteAccount` path is blocked for deterministic accounts to allow at least fund recovery via `beneficiary_id`. These would materially affect severity and should be checked in the actual codebase before finalizing a report.

### Title
Permanently frozen funds in NEP-616 deterministic accounts via mutable `AccountId`-mode global contract - (`runtime/runtime/src/deterministic_account_id.rs`)

### Summary
Deterministic accounts (`0s…`) are created with `AccountContract::None` and **no access key**, deriving all authority solely from whatever code the account's `GlobalContractIdentifier` currently resolves to. When that identifier is `GlobalContractIdentifier::AccountId(publisher)` (mutable mode), the publisher can redeploy different code at any time via an ordinary `DeployGlobalContractByAccountId` transaction, changing the effective logic for every deterministic account that references it — with no recourse for those accounts, since they have no full-access key to self-remediate.

### Finding Description
`create_deterministic_account` (`runtime/runtime/src/deterministic_account_id.rs:117-133`) explicitly notes the account is created without granting `actor_id`/ownership, "preventing `AddKey`, `DeployContract`, or any other actions that only the account owner is permitted to do." The account's code is set once via `deploy_deterministic_account` → `use_global_contract` (`:142-176`, `runtime/runtime/src/global_contracts.rs:76-109`), storing an `AccountContract::GlobalByAccount(publisher_account_id)` when the `DeterministicAccountStateInitV1.code` field is `GlobalContractIdentifier::AccountId`. Every subsequent function call against this account is resolved through `RuntimeContractIdentifier::resolve` (`runtime/runtime/src/contract_code.rs:36-73`), which always re-derives the current code hash for `AccountId`-mode identifiers rather than pinning it at creation time.

Separately, `action_deploy_global_contract` (`runtime/runtime/src/global_contracts.rs:25-63`) allows the publisher account to redeploy arbitrary new code under `GlobalContractDeployMode::AccountId` at will — this is an unprivileged, single-transaction action with no restriction tied to how many downstream accounts depend on it. `docs/RuntimeSpec/Actions.md:440-449` documents this as intended ("This allows the owner to update the contract for all its users"), but the consequence for deterministic accounts (which have zero alternative authorization mechanism) is structurally identical to the `AutoCompound.setVault(_active=false)` bug: a mutable admin-controlled flag/pointer that legitimate depositors trusted at deposit time can later be changed in a way that denies them access to funds they already committed, and — unlike a named account — there is no fallback key to escape the trap.

### Impact Explanation
Any user/depositor funds sent into a deterministic account whose code identifier is `AccountId`-mode become permanently inaccessible if the publisher (deliberately, or through a buggy upgrade) deploys new code that omits a `Transfer`/withdrawal path, or that fails for any input. Because the account has no access key and `AddKey`/`DeployContract` are structurally blocked for these accounts, there is no possible transaction the depositor can sign to recover the funds — this is a stronger, un-mitigable variant of the reported `AutoCompound` bug (which at least allowed recovery via a different, unaffected code path once the root cause was understood). This satisfies "permanently frozen funds" per the validation criteria.

### Likelihood Explanation
Reaching this requires only: (1) a deterministic account created with `code: GlobalContractIdentifier::AccountId(publisher)` (an ordinary, permitted `DeterministicStateInitAction`), and (2) the publisher later calling `DeployGlobalContractByAccountId` with different/incompatible code — both single, unprivileged transactions available to any signer. No validator, node, or network-level compromise is needed. The likelihood of *accidental* triggering (e.g., a publisher upgrading their shared contract and inadvertently breaking a code path some deterministic accounts depended on) is realistic given this is a documented, intended mutability feature; the likelihood of *deliberate* abuse depends on whether users are expected/warned to only build deterministic accounts against `CodeHash`-mode identifiers, which I could not confirm is enforced in code.

### Recommendation
Consider one or more of: (a) disallowing `GlobalContractIdentifier::AccountId` for deterministic-account state-init `code`, restricting deterministic accounts to immutable `CodeHash`-mode contracts only, so their behavior can never change post-creation; (b) providing a `DeleteAccount`-style fund-recovery fallback for deterministic accounts even without a contract-level withdrawal path (e.g., allowing the original depositor or a designated beneficiary to reclaim balance if the account's resolved contract becomes non-functional); or (c) requiring downstream tooling/wallets to strongly warn users before funding a deterministic account backed by a mutable `AccountId` contract identifier.

### Proof of Concept
1. Publisher account `pub.near` deploys a global contract in `GlobalContractDeployMode::AccountId` mode (`action_deploy_global_contract`), containing a working `transfer`/`withdraw` method.
2. User creates a deterministic account via `DeterministicStateInitAction` with `state_init.code = GlobalContractIdentifier::AccountId("pub.near")`, and funds it with a deposit (covered in `settle_state_init_deposit`, `deterministic_account_id.rs:73-115`).
3. `pub.near` later calls `DeployGlobalContractByAccountId` again with new code that omits the withdrawal method (or panics on all calls).
4. The user's deterministic account — via `RuntimeContractIdentifier::resolve` — now executes the new code for any `FunctionCall`; since the account has no access key (`create_deterministic_account`), no `AddKey`/`DeployContract`/`DeleteAccount` transaction can be authorized to remediate, and the deposited balance is permanently unreachable through any on-chain transaction.
