### Title
Fork-dependent poison-microblock report state causes `assert_eq!` panic in `inner_insert_matured_miner_reward` when maturing a shared ancestor block - (File: stackslib/src/chainstate/stacks/db/accounts.rs)

### Summary
`find_mature_miner_rewards` computes the matured reward for a historical ancestor block by querying `get_poison_microblock_report` against the *currently executing fork's* Clarity state, not the ancestor block's own fixed history. Two sibling forks that share a common ancestor block but diverge before a poison-microblock report is filed can therefore compute two different `MinerReward` values for the *same* `(parent_block_id, child_block_id)` key, which triggers the `assert_eq!` panic in `StacksChainState::inner_insert_matured_miner_reward` at accounts.rs:515.

### Finding Description
The broken equality is: `reward(parent_block_id, child_block_id)` on fork A **==** `reward(parent_block_id, child_block_id)` on fork B, for a `(parent_block_id, child_block_id)` pair that identifies a common ancestor block shared by both forks.

The code assumes this equality always holds — `inner_insert_matured_miner_reward` fetches any previously-stored reward for the same key and asserts it is identical to the newly computed one: [1](#0-0) 

However, the reward is not actually a pure function of `(parent_block_id, child_block_id)`. In `find_mature_miner_rewards`, the poison-microblock recipient used to compute the reward is derived from `get_poison_microblock_report(clarity_tx, reward_height)`, where `clarity_tx` is the Clarity state of the block *currently being processed on the calling fork*, not a value fixed by the ancestor block itself: [2](#0-1) 

Because a poison-microblock report is filed via an ordinary transaction that can be included in any block mined after the equivocating microblock stream is produced, two sibling forks that diverge before such a transaction is confirmed can end up with different answers to "was a poison report filed for `reward_height`, and by whom":
- Fork A includes a poison-microblock transaction naming reporter R1 before maturity.
- Fork B includes no report, or a report naming a different reporter R2, before maturity.

Since `poison_recipient_opt` feeds directly into `calculate_miner_reward`, the two forks compute two distinct `MinerReward` structs for the identical ancestor `(parent_block_id, child_block_id)` key. When each fork's block-processing calls `insert_matured_child_miner_reward` / `insert_matured_parent_miner_reward` (which both funnel into `inner_insert_matured_miner_reward`), the second write for the pair fails the `assert_eq!`, panicking the node process. Existing validation layers (`check_tenure_tx`, VRF/static block validation, MARF hashing) do not guard this path because it is not a consensus-acceptance check — it fires deep inside reward bookkeeping *after* both blocks have already been independently accepted as valid on their respective forks.

### Impact Explanation
The panic is a Rust `assert_eq!` failure, which aborts/crashes the node process. Any node that processes both sibling forks to the point of maturing the shared ancestor's coinbase (which any full node validating both branches during a reorg must do) will crash. This is a Critical, chain-halting condition: it is a bug reachable by an unprivileged single miner/reporter who can arrange for the two forks to include differing poison-report transactions, and it does not require majority stake — only the ability to extend a minority fork with a different poison-report transaction than the canonical fork.

### Likelihood Explanation
This requires: (1) a genuine microblock/tenure fork worth poison-reporting to exist (feasible for any miner producing forked microblocks or being targeted by such), (2) two Stacks forks sharing a common ancestor whose reward matures on both branches, and (3) different (or absent) poison-microblock transactions being included before the maturation height is reached on each branch. This is plausible for a minority miner deliberately engineering divergent transaction inclusion across two competing tenures/forks, without needing majority stake, signers, or admin access. It does, however, require legacy microblock/poison-microblock mechanics to still be reachable in the code paths under test; I was not able to fully confirm within the available tool budget whether poison-microblock reporting is still active for the current (Nakamoto) block-processing pipeline referenced in the question versus only legacy epoch-2.x chainstate, since the question's cited file `stackslib/src/chainstate/burn/atc.rs` does not correspond to any file found in the repository index — the relevant logic is in `stackslib/src/chainstate/stacks/db/accounts.rs` as verified.

### Recommendation
Make matured-reward computation for a given `(parent_block_id, child_block_id)` deterministic and fork-invariant: derive `poison_recipient_opt` from the poisoned block's own confirmed history (e.g., record the poison-report inclusion at the time the poisoned tenure itself is finalized, or key the poison lookup off the ancestor's own state root rather than the currently-processing fork's live Clarity state). Alternatively, replace the `assert_eq!` with fork-aware conflict resolution (e.g., accept the first-seen valid reward for the key and treat subsequent divergent computations as an expected reorg artifact instead of a fatal invariant violation).

### Proof of Concept
1. Build two sibling Nakamoto/epoch-2.x tenures atop a shared parent block `P`, using a chainstate test harness (`stackslib/src/chainstate/stacks/tests/block_construction.rs` patterns).
2. In fork A, include a `TransactionPayload::PoisonMicroblock` transaction reporting reporter `R1` for the equivocating microblock stream produced by `P`'s miner, before the maturity window (`MINER_REWARD_MATURITY`) elapses.
3. In fork B, include no poison-microblock transaction (or one naming reporter `R2`) before the same maturity window elapses.
4. Advance both forks past `MINER_REWARD_MATURITY` blocks so `find_mature_miner_rewards` computes and calls `insert_matured_child_miner_reward(parent_block_id, child_block_id, reward)` for the same `(parent_block_id, child_block_id)` pair on both forks against the same chainstate DB.
5. Assert that processing fork B's maturation call triggers a Rust panic inside `inner_insert_matured_miner_reward` at the `assert_eq!(rw, reward, ...)` line (accounts.rs:515), with `rw.recipient == R1` and `reward.recipient == R2` (or `None`), demonstrating the two computed `MinerReward` values differ for the identical ancestor key.
