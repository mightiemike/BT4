### Title
State-restore `KvOnly` mode writes untrusted state values into the state-KV DB without any hash/proof verification - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
### Finding Description
`StateSnapshotRestore::add_chunk` in `storage/aptosdb/src/state_restore/mod.rs` dispatches on `StateSnapshotRestoreMode`. For `Default` mode, the code explicitly documents and implements "verify proof -> write state_kv_db -> write state_merkle_db" [1](#0-0) , i.e. `self.tree_restore...verify_chunk(chunk.iter().map(|(k,v)| (k, v.hash())).collect(), proof)` recomputes each value's hash from the actually-downloaded blob and checks it against the Merkle range proof before any DB write occurs.

However, for `StateSnapshotRestoreMode::KvOnly`, `add_chunk` calls `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;` directly, with **no call to `verify_chunk`/`verify` and no proof argument used at all** [2](#0-1) . `StateValueRestore::add_chunk` (the underlying KV writer) never hashes or checks the incoming `(K, V)` pairs against any root hash — it just tracks progress and calls `write_kv_batch` [3](#0-2) .

This `KvOnly` mode is actually exercised by the production restore coordinator: `RestoreCoordinator::run_impl` (Phase 1a) calls `StateSnapshotRestoreController` with `restore_mode: StateSnapshotRestoreMode::KvOnly` to restore the state-KV values for the `kv_snapshot`, using blobs and proof files fetched from the (potentially adversarial/compromised) `BackupStorage` [4](#0-3) . The generic restore-controller loop for state snapshots downloads `blobs` and a `proof` per chunk from storage and hands them to `receiver.add_chunk(blobs, proof)` uniformly regardless of mode [5](#0-4)  — the caller has no way to know that the `proof` is silently discarded when `KvOnly` is selected.

Subsequently, Phase 2 restores the tree itself in `TreeOnly` mode against the tree_snapshot's own manifest/proof [6](#0-5) . `TreeOnly`'s `verify_chunk` only checks that the leaf **hashes supplied in the tree manifest's own proof chunk** are internally consistent with the JMT structure and target root hash [7](#0-6) ; it never re-derives those hashes from the actual state-KV values written to disk in Phase 1. Therefore nothing in the restore pipeline ever confirms that the raw state values persisted into `state_kv_db` during the KvOnly phase actually match the hashes committed to by the Aptos consensus-signed root hash.

### Impact Explanation
A backup-storage provider (or a man-in-the-middle able to tamper with backup blob files, which is the exact threat model that all the other restore paths defend against with proof verification) can supply arbitrary/corrupted state values for the `KvOnly` phase. These corrupted values are persisted directly into the durable state-KV database of a restoring/bootstrapping full node or validator, without any cryptographic binding to the real chain state. Because the subsequent `TreeOnly` step never cross-checks KV content against tree hashes, the corruption is never detected. The result is a full node whose queryable/authenticated state (account resources, balances, etc.) is silently wrong relative to the real ledger, while the node's synced version/ledger info still appear valid — a durable ledger-state integrity break reachable purely by a restore operator pointing at attacker-controlled backup storage, no privileged access or consensus fault required. This matches the "Committed state that differs from the correct VM result or corrupts durable ledger data" and "Authenticated API or state-view output bound to the wrong version/object" impact classes in scope.

### Likelihood Explanation
Restoring from `KvOnly` snapshots is a normal, non-exceptional code path used automatically whenever `RestoreCoordinator` resumes/starts and has a state-kv snapshot at an earlier version than the tree snapshot — this is the default two-phase restore behavior, not a rarely-used option. Any operator restoring a node from third-party or self-hosted backup storage (a common practice for bootstrapping fullnodes) is exposed. The only requirement for exploitation is control over, or MITM of, the backup storage's blob responses for state-snapshot chunks, which is precisely the scenario the proof-verification design elsewhere in this file is meant to prevent.

### Recommendation
In `StateSnapshotRestore::add_chunk`'s `KvOnly` branch, verify the downloaded chunk against the supplied `SparseMerkleRangeProof` (as done in `Default`/`TreeOnly`) before calling `kv_restore.add_chunk`, or otherwise reject `KvOnly` requests that don't carry a verifiable proof reconciled against the target root hash. At minimum, ensure the Phase-2 `TreeOnly` verification recomputes leaf hashes from the actual persisted KV values rather than trusting hashes taken from the tree manifest alone, so that a mismatch between Phase-1 KV data and the true root hash is detected before the DB is considered restored.

### Proof of Concept
1. Stand up a `BackupStorage` implementation (or intercept HTTP/GCS responses) that returns a valid-looking manifest but substitutes tampered `StateValue` bytes in the blob chunks for a given `kv_snapshot`, while returning any well-formed (but now-mismatched) `SparseMerkleRangeProof` object matching the original real byte length/shape so deserialization succeeds.
2. Run `RestoreCoordinator::run_impl` against this storage with a `kv_snapshot.version < tree_snapshot.version` scenario (the common resumed-restore path).
3. Phase 1a calls `StateSnapshotRestoreController` with `StateSnapshotRestoreMode::KvOnly`; `add_chunk` writes the tampered values straight to `state_kv_db` — confirm via direct inspection of `write_kv_batch` calls / state_kv_db contents.
4. Continue through Phase 1b/Phase 2 (`TreeOnly` for the tree snapshot) to completion; the restore reports success even though `state_kv_db` now diverges from the real chain state for the tampered keys.
5. Query the restored node's `DbReader` (e.g., `get_state_value_with_proof_by_version`) for the tampered key at the kv-restored version and observe it returns the corrupted value with no error, since the proof-verification step was skipped in Phase 1 and Phase 2 never revisits it.

    pub fn add_chunk(&mut self, mut chunk: Vec<(K, V)>) -> Result<()> {
        // load progress
        let progress_opt = self.db.get_progress(self.version)?;

        // skip overlaps
        if let Some(progress) = progress_opt {
            let idx = chunk
                .iter()
                .position(|(k, _v)| CryptoHash::hash(k) > progress.key_hash)
                .unwrap_or(chunk.len());
            chunk = chunk.split_off(idx);
        }

        // quit if all skipped
        if chunk.is_empty() {
            return Ok(());
        }

        // save
        let mut usage = progress_opt.map_or(StateStorageUsage::zero(), |p| p.usage);
        let (last_key, _last_value) = chunk.last().unwrap();
        let last_key_hash = CryptoHash::hash(last_key);

        // In case of TreeOnly Restore, we only restore the usage of KV without actually writing KV into DB
        for (k, v) in chunk.iter() {
            usage.add_item(k.key_size() + v.value_size());
        }

        // prepare the sharded kv batch
        let kv_batch: StateValueBatch<K, Option<V>> = chunk
            .into_iter()
            .map(|(k, v)| ((k, self.version), Some(v)))
            .collect();

        self.db.write_kv_batch(
            self.version,
            &kv_batch,
            StateSnapshotProgress::new(last_key_hash, usage),
        )
    }
