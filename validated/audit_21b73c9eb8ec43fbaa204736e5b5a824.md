### Title
Panic on real-world Cairo1 declared classes with 3+ level bytecode segmentation depth in `NestedFeltCounts::new_inner` - (File: crates/blockifier/src/execution/contract_class.rs)

### Summary
`NestedFeltCounts::new_inner`, used every time a `CasmContractClass` is converted into a `CompiledClassV1` (i.e. on every declared/executed Cairo1 class), hard-asserts that the compiler-generated `bytecode_segment_lengths` tree never nests deeper than one level. This assumption is not guaranteed by the Sierra→CASM compiler and is not checked/rejected earlier in the declare pipeline, so a legitimately compiled contract whose control-flow produces a deeper segmentation tree causes an unconditional `panic!`, analogous to the CVE-2018-7872 pattern of trusting an internal/attacker-influenced structural invariant without validating it before use, leading to a crash.

### Finding Description
When a `CasmContractClass` (produced by the sequencer's own Sierra→CASM compiler from a user-submitted Sierra program, or read back from state/OS input) is converted into the blockifier's runnable `CompiledClassV1`, the code builds a `NestedFeltCounts` tree mirroring the compiler's `bytecode_segment_lengths` (a `NestedIntList`): [1](#0-0) 

The recursive helper unconditionally asserts:
```
assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");
```
before doing anything else, and this is reached on **every** recursive call, including for `NestedIntList::Node` children of children. This assumption ("segmentation depth at most 1", i.e. a two-level tree: top-level segments that are either leaves or one level of sub-segments) matches only *some* outputs of the Cairo1 bytecode segmentation algorithm. The segmentation algorithm in `cairo-lang-starknet-classes` builds the segment tree based on the program's function/branch nesting; for contracts with more deeply nested branches (nested `if`/match inside nested function calls, etc.), the compiler can legitimately emit a `bytecode_segment_lengths` tree with 3+ levels of nesting. There is no earlier validation step in the declare/compile pipeline (`SierraToCasmCompiler::compile` in `crates/apollo_compile_to_casm/src/compiler.rs`, or the `SierraCompiler::compile` wrapper in `crates/apollo_compile_to_casm/src/lib.rs`) that rejects or flattens such deeper trees before the class is accepted, hashed, and later converted with `TryFrom<VersionedCasm> for CompiledClassV1`: [2](#0-1) 

This `TryFrom` conversion is exercised on the class declaration/validation and execution paths (and again whenever the class is loaded for execution, or re-derived for OS/proving flows), so the panic is reachable purely from processing a declared class whose Sierra compiles down to a deeper segmentation tree — no malformed/forged bytes are even required, just sufficiently nested contract logic.

This mirrors the CVE-2018-7872 bug class: an internal structural assumption about nested/length-encoded data (there, `CONSTANT16` "getName" indexing; here, nested segment-length structure) is trusted without being validated/bounded before being dereferenced/asserted, and a normally-reachable input (not even a corrupted file, just a real program) crashes the process.

### Impact Explanation
A `panic!` inside `blockifier`'s class-conversion code aborts (or at minimum errors out at a place not designed to gracefully propagate a user-triggerable condition) the thread/process handling the transaction. Since this code path is exercised during declare-transaction processing and again during every execution of that class, and also in Starknet OS re-execution when compiled classes are loaded (`crates/starknet_os/src/hints/hint_implementation/compiled_class/implementation.rs`), a single declare transaction for a contract whose CASM bytecode segmentation tree happens to exceed depth 1 can crash the sequencer / re-execution / proving pipeline that processes it — a network-wide DoS if such a transaction is broadcast and processed by all sequencer/validator nodes, since all honest nodes would hit the same panic deterministically (also causing state-transition divergence/inability to progress if some component catches the panic differently than others).

### Likelihood Explanation
The panic requires only a normal contract deployment whose Sierra compiles to a CASM with a bytecode segmentation tree deeper than one level; it does not require crafting raw/corrupted bytes, only sufficiently nested branch/function structure. This makes the likelihood non-trivial: the trigger condition depends on the compiler's actual segmentation behavior for real contracts, which was not independently verified to be exhaustively bounded at depth 1 in all cases (the `assert!` comment itself signals the developers were aware this is an unproven invariant — "Only supported for segmentation depth at most 1"). I was unable to fully verify from the available code whether upstream compiler guarantees (e.g. a hidden depth cap enforced elsewhere in `cairo-lang-starknet-classes`) make this actually unreachable in practice; this should be confirmed against the exact `cairo-lang-starknet-classes` version vendored in this repo before treating this as fully proven.

### Recommendation
- Replace the `assert!(segmentation_depth <= 1, ...)` with either: (a) a graceful fallback that treats an arbitrarily nested segment tree correctly (remove the depth restriction and make `new_inner` fully recursive with no depth cap), or (b) a proper `Result`-returning validation that surfaces as a normal transaction/class-compilation error (e.g. reject the declare with a `CompilationUtilError`/`ProgramError`) instead of panicking, at the compiler wrapper stage (`SierraToCasmCompiler::compile`) before the class is accepted into state.
- Add a fuzz/property test that compiles a range of programs with deep nested branch/function structures and asserts no panic occurs, to confirm/deny actual reachability of depth > 1 trees from the real compiler.
- Ensure the same depth-bound issue does not exist for the mirrored Cairo0-hint / Starknet OS code paths that consume the same `bytecode_segment_lengths` structure (`crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`), since those recurse without any depth assumption today but should be double-checked for consistency with any future fix.

### Proof of Concept
1. Author (or locate/generate) a Cairo1 contract whose compiled Sierra program contains sufficiently deep nested branching/function calls such that `cairo-lang-starknet-classes`'s bytecode segmentation produces a `bytecode_segment_lengths` `NestedIntList` with nesting depth ≥ 2 (i.e. a `Node` containing a `Node` containing another `Node`).
2. Submit this contract as a Declare transaction (Cairo1/Sierra) through the gateway; the sequencer compiles it via `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs`), producing a `CasmContractClass` with the deep `bytecode_segment_lengths`.
3. When this class is subsequently converted to `CompiledClassV1` via `TryFrom<VersionedCasm>` (`crates/blockifier/src/execution/contract_class.rs:626-677`) — which happens during class execution/state loading — `NestedFeltCounts::new` → `new_inner` is invoked and panics on the `assert!(segmentation_depth <= 1, ...)` check once recursion reaches depth 2.
4. Observe the panic crashing the executing component/thread that handles the declare or subsequent invoke transaction referencing this class.

(Note: I was not able to construct and locally compile a concrete Sierra program guaranteed to produce a depth-≥2 segmentation tree within this investigation; this PoC path is derived directly from the code's own explicit assumption and comment, but empirical confirmation with the exact bundled compiler version is recommended before treating this as fully proven exploitable.)

impl NestedFeltCounts {
    /// Builds a nested structure matching `layout`, consuming values from `bytecode`.
    #[allow(unused)]
    pub fn new(bytecode_segment_lengths: &NestedIntList, bytecode: &[BigUintAsHex]) -> Self {
        let (base_node, consumed_felts) = Self::new_inner(bytecode_segment_lengths, bytecode, 0);
        assert_eq!(consumed_felts, bytecode.len());
        base_node
    }

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }

impl TryFrom<VersionedCasm> for CompiledClassV1 {
    type Error = ProgramError;

    fn try_from((class, sierra_version): VersionedCasm) -> Result<Self, Self::Error> {
        let data: Vec<MaybeRelocatable> =
            class.bytecode.iter().map(|x| MaybeRelocatable::from(Felt::from(&x.value))).collect();

        let mut hints: HashMap<usize, Vec<HintParams>> = HashMap::new();
        for (i, hint_list) in class.hints.iter() {
            let hint_params: Result<Vec<HintParams>, ProgramError> =
                hint_list.iter().map(hint_to_hint_params).collect();
            hints.insert(*i, hint_params?);
        }

        // Collect a sting to hint map so that the hint processor can fetch the correct [Hint]
        // for each instruction.
        let mut string_to_hint: HashMap<String, Hint> = HashMap::new();
        for (_, hint_list) in class.hints.iter() {
            for hint in hint_list.iter() {
                string_to_hint.insert(serde_json::to_string(hint)?, hint.clone());
            }
        }

        let builtins = vec![]; // The builtins are initialize later.
        let main = Some(0);
        let reference_manager = ReferenceManager { references: Vec::new() };
        let identifiers = HashMap::new();
        let error_message_attributes = vec![];
        let instruction_locations = None;

        let program = Program::new(
            builtins,
            data,
            main,
            hints,
            reference_manager,
            identifiers,
            error_message_attributes,
            instruction_locations,
        )?;

        let bytecode_segment_felt_sizes =
            NestedFeltCounts::new(&class.get_bytecode_segment_lengths(), &class.bytecode);

        Ok(CompiledClassV1(Arc::new(ContractClassV1Inner {
            program,
            entry_points_by_type: (&class.entry_points_by_type).into(),
            hints: string_to_hint,
            sierra_version,
            bytecode_segment_felt_sizes,
        })))
    }
