### Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` JSON-RPC methods allow any caller to halt sequencer commitment production - (File: crates/sequencer/src/rpc.rs)

### Summary
The sequencer exposes two privileged JSON-RPC methods, `citrea_haltCommitments` and `citrea_resumeCommitments`, that toggle whether the `CommitmentService` publishes sequencer commitments to the DA layer. Unlike the analogous NFTX bug where `assignFees()` lacked an owner check, these methods have **no caller authentication or authorization check** at all, and they are not included in the node's `Auth` middleware protected-method list, so any client with network access to the sequencer's RPC port can halt (and later resume) commitment publication.

### Finding Description
`SequencerRpcServerImpl::halt_commitments` and `resume_commitments` simply forward a signal to the commitment service without validating the caller's identity or credentials: [1](#0-0) 

These methods are registered as regular, unauthenticated RPC methods on the trait: [2](#0-1) 

The node's global RPC `Auth` middleware only guards a hard-coded allowlist of three unrelated backup methods (`backup_create`, `backup_validate`, `backup_info`); every other method, including `citrea_haltCommitments`/`citrea_resumeCommitments`, bypasses the API-key check entirely: [3](#0-2) 

The halt/resume signal is honored unconditionally by the sequencer's main event loop and forwarded to `CommitmentService`, which stops (or resumes) submitting `SequencerCommitment` DA transactions as soon as the signal is received - no further authorization check occurs downstream: [4](#0-3) [5](#0-4) 

This is structurally identical to the NFTX `assignFees()` finding: a state-mutating administrative function is reachable by any unprivileged caller because the intended access-control boundary (only the sequencer operator should be able to halt/resume commitments) was never enforced at the RPC layer.

### Impact Explanation
Sequencer commitments are the DA-layer anchor that the light-client proof circuit and full nodes rely on to advance verified L2 state and ultimately to feed Clementine's bridge proof. An unauthenticated third party who can reach the sequencer's RPC endpoint can call `citrea_haltCommitments` to indefinitely stop new sequencer commitments from being posted to Bitcoin, without ever needing the sequencer's private key or any node-operator role. This is an unauthenticated JSON-RPC call that mutates node state, matching the "High" impact category (unauthenticated call that mutates node state or bypasses `Auth`), since it crosses the authority boundary that should restrict administrative sequencer control to the operator.

### Likelihood Explanation
Likelihood depends entirely on network exposure of the sequencer's RPC endpoint. If the endpoint is reachable (e.g., default bind configuration, or any misconfiguration exposing it beyond a trusted network), exploitation requires only a single unauthenticated JSON-RPC call with no signature, key, or special role - trivial to execute.

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and any other operator-only control methods) to the `PROTECTED_METHODS` list in `crates/common/src/rpc/auth.rs`, or otherwise require the `Auth` API key / operator-only channel for these calls before forwarding `SequencerRpcMessage::HaltCommitments`/`ResumeCommitments`.

### Proof of Concept
1. Locate a running Citrea sequencer node with its RPC port reachable.
2. Send an unauthenticated JSON-RPC request:
```json
{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}
```
3. Observe via `runner.rs`/`commitment/service.rs` that the halt signal is accepted and `CommitmentService` stops publishing new `SequencerCommitment` DA transactions, with no authentication check ever performed, unlike the deliberately gated `backup_*` methods.

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }

        let Some(api_key) = api_key else {
            return Box::pin(async move {
                MethodResponse::error(
                    req.id().clone(),
                    ErrorObjectOwned::owned(401, "Cannot access protected method", None::<String>),
                )
            });
        };
