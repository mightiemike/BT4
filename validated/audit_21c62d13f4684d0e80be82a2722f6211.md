### Title
Wallet Contract's `has_in_flight_tx` lock can become permanently stuck if the relayer-ban action runs out of gas, freezing the ETH-implicit account forever - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `near-wallet-contract` (deployed on every ETH-implicit account, see `docs/DataStructures/Account.md:124`) uses a single boolean flag, `has_in_flight_tx`, to serialize `rlp_execute` calls, exactly mirroring the Symmetry liquidation pattern: a phase-1 action sets a "locked" flag, and an expected phase-2 completion is supposed to clear it. If the completion step (here, the `ban_relayer` self-call) never actually executes — because the relayer starves the receipt of gas — the flag is never reset, and the account is permanently locked out of `rlp_execute`, which is the **only** entry point that can move funds or otherwise act on behalf of an ETH-implicit account.

### Finding Description
`WalletContract::rlp_execute` refuses to run if `has_in_flight_tx` is already `true` [1](#0-0) , and every code path that returns a `Promise` sets `has_in_flight_tx = true` immediately before returning [2](#0-1) . The documented invariant is that the flag must be `true` while a promise is outstanding and `false` otherwise [3](#0-2) .

Every promise chain built through `.then()` (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) is guaranteed by the NEAR runtime to eventually execute and reset the flag to `false` at its very first line, since a receipt's data dependency is always resolved (success or failure) and a `Data`/`PromiseResume` receipt is always produced.

However, the "faulty relayer" ban path does **not** use a `.then()` callback. It builds a single batched promise with two sequential actions on the *same* receiver (the wallet contract's own account): `delete_key(pk)` followed by `function_call_weight("ban_relayer", ...)` [4](#0-3) . `has_in_flight_tx` is only ever reset inside `ban_relayer`'s own body [5](#0-4) . This promise is dispatched from two places: directly from `rlp_execute` on a relayer error [6](#0-5) , and from `address_check_callback` [7](#0-6) .

Action receipts on NEAR are not atomic across the action list: if an earlier action in a batch succeeds and a later action in the same receipt fails to be dispatched (e.g. due to insufficient forwarded gas for the `FunctionCall`), the earlier action's state change (`DeleteKey`) is retained while the later action (`ban_relayer`, the only code path that clears the lock in this branch) never executes. Because the gas forwarded to this new receipt is whatever prepaid gas remains unused from the calling receipt (the relayer's own `rlp_execute` transaction or the `address_check_callback` receipt, whose own static gas budgets are small fixed constants such as `ADDRESS_CHECK_CALLBACK_GAS`/`RLP_EXECUTE_CALLBACK_GAS` = 5–10 Tgas [8](#0-7) ), an unprivileged relayer fully controls how much gas is attached to `rlp_execute`. By attaching just enough gas to reach the "faulty relayer" branch but not enough to cover `DeleteKey`'s base cost plus `ban_relayer`'s required static gas (`Gas::from_tgas(1)`), the relayer can cause `delete_key` to succeed while the `ban_relayer` function call fails to execute at all — leaving `has_in_flight_tx = true` forever, with no other function in the contract able to clear it.

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true`, every future call to `rlp_execute` — from *any* relayer, not just the misbehaving one — immediately returns the "transaction already in progress" error without doing anything [9](#0-8) . Since `rlp_execute` is the sole entry point through which an ETH-implicit account can transfer `$NEAR`, call other contracts, or manage its access keys [10](#0-9) , the account and every asset it holds becomes permanently frozen with no recovery path defined in the contract. This matches the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Triggering this requires only a single unprivileged `FunctionCall` transaction to `rlp_execute` with a deliberately (or accidentally) low attached-gas value combined with a malformed/erroring RLP payload that routes execution into the relayer-ban branch (e.g. `Error::Relayer(_)` from `inner_rlp_execute`, such as sending garbage transaction bytes as in `test_relayer_invalid_tx_data`). Any account that funds and operates an ETH-implicit account is exposed to this if a relayer (which by the contract's own threat model can be dishonest or careless) submits such a transaction; no elevated privileges, validator collusion, or multi-block timing race is needed.

### Recommendation
Do not rely on a bare batched action to clear `has_in_flight_tx`. Either:
- Attach `ban_relayer` via an explicit `.then()` callback so the runtime's guaranteed data-dependency resolution ensures it always executes (mirroring the other callback paths), or
- Reserve enough minimum gas explicitly for the `function_call_weight("ban_relayer", ...)` action and fail the whole `rlp_execute` invocation up front (before any state-mutating action is dispatched) if insufficient gas is attached, so `delete_key` can never succeed without `ban_relayer` also being guaranteed to run.

### Proof of Concept
1. A relayer submits a `FunctionCall` transaction targeting the eth-implicit account's `rlp_execute` method with `tx_bytes_b64` set to invalid/garbage bytes (as in `test_relayer_invalid_tx_data`, which normally results in `Error::Relayer` and a call to `create_ban_relayer_promise`) and `env::signer_account_id() == current_account_id` (i.e. submitted via an access key registered on the wallet contract, as in the "relayer with access key" flow) [11](#0-10) .
2. The relayer attaches gas just above the minimum needed to reach the `Err(Error::Relayer(_))` branch inside `rlp_execute`, but below the amount needed to cover `DeleteKey`'s base cost plus `ban_relayer`'s `Gas::from_tgas(1)` static allocation once forwarded to the new receipt.
3. `rlp_execute` sets `has_in_flight_tx = true` and returns the batched promise [12](#0-11) .
4. In the resulting receipt, `delete_key(pk)` executes and revokes the relayer's key; the subsequent `function_call_weight("ban_relayer", ...)` action fails to dispatch/execute due to insufficient remaining gas, so `ban_relayer`'s body (which resets `has_in_flight_tx`) never runs.
5. Any subsequent call to `rlp_execute` by any relayer immediately short-circuits with `"Error: transaction already in progress"`, permanently freezing the account.

Note: I was unable to execute this scenario end-to-end in an integration test within this session; the conclusion is based on static analysis of the promise/action-batching code and NEAR's documented non-atomic, sequential action-execution semantics within a single receipt (`docs/RuntimeSpec/Actions.md`). Confirming the exact gas thresholds at which `delete_key` succeeds but `function_call_weight` fails to dispatch would benefit from a dedicated sandbox/integration test.

### Wallet Contract

The Wallet Contract (see [NEP-518](https://github.com/near/NEPs/issues/518) for more details) functions as a user account and is designed to receive, validate, and execute Ethereum-compatible transactions on the NEAR blockchain.

Without going into details, an Ethereum-compatible wallet user sends a transaction to an RPC endpoint, which wraps it and passes it to the Wallet Contract (on the target account) as an `rlp_execute(target: AccountId, tx_bytes_b64: Vec<u8>)` contract call.
Then, the contract parses `tx_bytes_b64` and verifies it is signed with the private key matching the target [ETH-implicit account ID](#eth-implicit-account-id) on which the contract is hosted.

Under the hood, the transaction encodes a NEAR-native action. Currently supported actions are:

- Transfer (from ETH-implicit account).
- Function call (call another contract).
- Add `AccessKey` with `FunctionCallPermission`. This allows adding a relayer's public key to an ETH-implicit account, enabling the relayer to pay the gas fee for transactions from this account. Still, each transaction has to be signed by the owner of the account (corresponding Secp256K1 private key).
- Delete `AccessKey`.
