### Title
Unsynchronized concurrent read/write in `FileHandler`'s unconditional `Send`/`Sync` impl allows data races on mmap-backed storage (transactions, state diffs, classes, CASM) - (File: crates/apollo_storage/src/mmap_file/mod.rs)

### Summary
`FileHandler<V, Mode>` in `apollo_storage`'s mmap-file module carries a raw pointer (`memory_ptr: *const u8`) into a shared, growable `MmapMut` alongside `unsafe impl Send`/`unsafe impl Sync` that place no bounds on `V` or synchronization requirements. The reader path dereferences `memory_ptr` directly, completely bypassing the `Mutex<MMapFile<V>>` that guards writer mutation, mirroring the `atomic-option` bug class (CWE-662: unconditional/unsound thread-safety marker leading to a data race) from CVE-2020-36219.

### Finding Description
`FileHandler` is defined as: [1](#0-0) 

The `Writer::append` implementation takes the `Mutex` lock, mutates the shared `mmap` buffer, and updates `offset`/`should_flush` under that lock: [2](#0-1) 

However `Reader::get` reads bytes directly through the raw `memory_ptr`, without ever acquiring `mmap_file`'s `Mutex`: [3](#0-2) 

This is architecturally identical to the `atomic-option` flaw: a type is marked `Sync`/`Send` unconditionally (no bound requiring the underlying data to be safely shareable), and consumers of the type can race a writer thread mutating the backing memory (`mmap_slice[..len].copy_from_slice(...)`, `mmap_file.offset += len`) against reader threads dereferencing the same memory region with no `Mutex`, `Atomic`, or fence establishing a happens-before relationship. The doc comment merely states "the caller must ensure new data is appended at the offset returned by the previous write," which is a soundness contract resting entirely on external, out-of-band synchronization (LMDB commit ordering) that the type itself does nothing to enforce, and does not eliminate the race for concurrent growth (`mmap.flush_async_range`) and concurrent read while the mutex-protected append path is running.

This storage layer directly backs consensus-relevant, transaction-derived data: thin state diffs, Sierra/CASM/deprecated contract classes, and transaction/transaction-output bodies, all reachable from ordinary transaction submission and class declaration flows: [4](#0-3) [5](#0-4) 

A `StorageReader::begin_ro_txn()` (used pervasively for state reads, block building, and OS re-execution) clones `FileHandlers<RO>` and calls `Reader::get` concurrently with any in-flight `FileHandlers<RW>::append_*` call from block commit: [6](#0-5) 

### Impact Explanation
A torn/partial read of `Vec<u8>`-serialized state diffs, contract classes, or transactions (read via raw pointer while a writer thread is mid-`copy_from_slice`) can produce a deserialization result that silently differs across processes/threads observing the same `LocationInFile`, without any error being raised (deserialization simply proceeds against whatever bytes are currently resident, potentially half-old/half-new). Because these mmap files back exactly the class/state-diff data used to (re-)construct state, feed the Starknet OS re-execution path, and answer state-diff/class queries used in block building and commitment, a race-induced corrupted read is capable of producing divergent or incorrect state-diff/class content read back by different components (or on different runs), which can manifest as wrong committed state/root or honest-node divergence in scenarios where the storage-read result feeds directly into state commitment or re-execution without a checksum. This is UB territory (unsynchronized read of memory concurrently written), so the actual behavior is undefined and can range from silent data corruption to a crash (denial of block production availability on the affected node).

### Likelihood Explanation
The race requires ordinary, non-malicious concurrency: any block commit (`append_state_diff`/`append_contract_class`/`append_casm`/`append_transaction`) racing with any concurrent RO read via `StorageReader::begin_ro_txn()` (e.g., RPC serving state, or building/re-executing the next block) is enough to trigger the unsynchronized access — no attacker-crafted payload is needed, only normal read/write concurrency that the node's own architecture creates. The crate's own test suite (`concurrent_reads_single_write`) demonstrates this exact concurrent-read-while-write pattern is an expected usage mode: [7](#0-6) 
Because the underlying data race is UB rather than a deterministic logic bug, actual manifestation (visible corruption vs. silently benign due to fortunate memory ordering on a given platform) is non-deterministic, which is why this is rated as a likelihood-moderate but severity-relevant soundness issue rather than a guaranteed reproducer in every environment.

### Recommendation
- Require readers to acquire the same `Mutex<MMapFile<V>>` (or switch to an `RwLock`, allowing concurrent readers but serializing against writers) before dereferencing mmap-backed memory, instead of bypassing it via a raw pointer captured at `open_file` time.
- Remove the unconditional `unsafe impl Send`/`Sync` and instead derive/require `Send + Sync` only when properly guarded (e.g., wrap `memory_ptr` accesses behind the lock, or use atomic/volatile-safe reads with explicit memory ordering matching the writer's).
- Add loom-based or sanitizer-based (ThreadSanitizer) tests to catch actual data races on this path, since the current tests only assert eventual correctness under a `Barrier`-synchronized happy path, not close races.

### Proof of Concept
Not applicable in the classic "malicious transaction payload" sense — this is a soundness/data-race bug reachable via ordinary node operation: concurrently commit a block that appends a state diff/class/transaction (`FileHandlers<RW>::append_*`) while another thread/task performs `StorageReader::begin_ro_txn()` and reads the corresponding `LocationInFile` via `get_state_diff_from_location`/class getters. Under `cargo test -Z sanitizer=thread` or a `loom` model, this manifests as a detected data race on `mmap` memory accessed both under `Mutex` (writer) and via raw pointer (reader) with no synchronization, analogous to the `AtomicOption<T>: Sync` unconditional-impl race in CVE-2020-36219/GHSA-8gf5-q9p9-wvmc.

impl<V: ValueSerde + Debug> Writer<V> for FileHandler<V, RW> {
    fn append(&mut self, val: &V::Value) -> LocationInFile {
        trace!("Inserting object: {:?}", val);
        let serialized = V::serialize(val).expect("Should be able to serialize");
        let len = serialized.len();
        let offset;
        {
            let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
            offset = mmap_file.offset;
            trace!("Inserting object at offset: {}", offset);
            let mmap_slice = &mut mmap_file.mmap[offset..];
            mmap_slice[..len].copy_from_slice(&serialized);
            mmap_file
                .mmap
                .flush_async_range(offset, len)
                .expect("Failed to asynchronously flush the mmap after inserting");
            mmap_file.offset += len;
            mmap_file.should_flush = true;
        }
        let location = LocationInFile { offset, len };
        self.grow_file_if_needed(location.next_offset());
        location
    }

#[test]
fn concurrent_reads_single_write() {
    let dir = tempdir().unwrap();
    let offset = 0;
    let (mut writer, reader) = open_file::<NoVersionValueWrapper<Vec<u8>>>(
        get_mmap_file_test_config(),
        dir.path().to_path_buf().join("test_concurrent_reads_single_write"),
        offset,
    )
    .unwrap();
    let first_data = vec![1, 2, 3];
    let second_data = vec![3, 2, 1];
    let first_location = writer.append(&first_data);
    writer.flush();
    let second_location =
        LocationInFile { offset: first_location.next_offset(), len: first_location.len };

    let n = 10;
    let barrier = Arc::new(std::sync::Barrier::new(n + 1));
    let mut handles = Vec::with_capacity(n);

    for _ in 0..n {
        let reader = reader.clone();
        let reader_barrier = barrier.clone();
        let first_data = first_data.clone();
        handles.push(std::thread::spawn(move || {
            assert_eq!(reader.get(first_location).unwrap().unwrap(), first_data);
            reader_barrier.wait();
            // readers wait for the writer to write the value.
            reader_barrier.wait();
            reader.get(second_location).unwrap()
        }));
    }
    // Writer waits for all readers to read the first value.
    barrier.wait();
    writer.append(&second_data);
    writer.flush();
    // Allow readers to proceed reading the second value.
    barrier.wait();

    for handle in handles {
        let res = handle.join().unwrap().unwrap();
        assert_eq!(res, second_data);
    }
