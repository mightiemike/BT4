Based on the investigation, I found a genuine state-integrity gap in the backup **transaction restore path** that mirrors the "not all deployment-config conditions are checked" bug-class: a proof-verification routine checks *some* fields (transaction hash, event root hash, status) but skips checking that the loaded **write set actually matches the accumulator-proven `TransactionInfo.state_change_hash`**, unlike the sibling `TransactionOutputListWithProof::verify` which does perform that exact check.

### Title
Restored `write_set`s are persisted without verifying `state_change_hash`, allowing corrupted/mismatched write sets to be committed as authenticated ledger data - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
`LoadedChunk::load` reads `(txn, aux_info, txn_info, events, write_set)` tuples from a backup chunk file, but only wraps `txns`, `event_vecs`, and `txn_infos` into a `TransactionListWithProof` for verification against the ledger-info-anchored accumulator proof; `write_sets` is kept out-of-band and never checked against `txn_info.state_change_hash()`. [1](#0-0) 

### Finding Description
`TransactionInfo` binds a `state_change_hash` (the hash of the write set) into the value that is accumulator-proven against a trusted `LedgerInfoWithSignatures`. The intended invariant is "any write set accepted into storage must hash to the `state_change_hash` recorded in its accumulator-proven `TransactionInfo`" — this is exactly what `TransactionOutputListWithProof::verify` enforces via `CryptoHash::hash(&txn_output.write_set) == txn_info.state_change_hash()`. [2](#0-1) 

However, the transaction-backup format stores `write_set` as a value separate from `TransactionOutput`, and `LoadedChunk::load` never routes it through an equivalent check: it builds `TransactionListWithProof` using only `txns`, `event_vecs`, `first_version`, and `TransactionInfoListWithProof`, and calls `.verify(...)` on that structure — a type that has no `write_set` field and therefore cannot check it. [3](#0-2) 

The unverified `write_sets` are then handed straight to `restore_utils::save_transactions` / `save_transactions_impl`, which persists them into `WriteSetDb` and, when `kv_replay` is enabled, feeds them into `state_store.calculate_state_and_put_updates` to materialize actual JMT state values — with no hash cross-check against the already-verified `txn_info` anywhere in that path. [4](#0-3) 

### Impact Explanation
A corrupted or substituted `write_set` in a backup chunk (whether from storage bit-rot, a compromised/malicious backup storage backend, or a bug in the backup writer) will be silently accepted and committed under a `TransactionInfo` that is legitimately accumulator-proven and ledger-info-signed. This produces committed state that differs from the correct VM result while the associated proof metadata (`txn_info`, accumulator root) still authenticates as valid — a direct violation of the "committed state must match VM result" and "proof context must stay bound to correct data" invariants called out in the state-integrity gate. Since `kv_replay` writes these bogus write sets directly into versioned state, this can corrupt durable ledger data on any node performing restore.

### Likelihood Explanation
This triggers on every restore that goes through `TransactionRestoreController` with `kv_replay` (or any downstream consumer of the persisted `WriteSetDb`), since no code path re-derives or checks `state_change_hash` against the loaded write set before or after `save_transactions`. It requires either backup storage integrity failure or backup write-set corruption, which is within threat models for restore/disaster-recovery tooling that state sync and validators rely on for bootstrapping.

### Recommendation
Add an explicit check in `LoadedChunk::load` (or immediately before `save_transactions`) that computes `CryptoHash::hash(&write_set)` for each transaction and asserts equality with the corresponding `txn_info.state_change_hash()`, mirroring the check already implemented in `TransactionOutputListWithProof::verify`.

### Proof of Concept
1. Craft a backup transaction chunk file where the `(txn, aux_info, txn_info, events, write_set)` record has a `write_set` different from the one used to compute the real `state_change_hash`, but keep `txn_info`, `txn`, and `events` untouched (so `txn_list_with_proof.verify` still passes, since it only checks txn hash, event root hash, and status).
2. Feed the chunk plus the legitimate `(range_proof, ledger_info)` into `TransactionRestoreController::run`.
3. Observe that `LoadedChunk::load` succeeds (verify only inspects txns/events/txn_infos), and `restore_utils::save_transactions_impl` persists the tampered `write_set` into `WriteSetDb`; with `kv_replay` enabled, `calculate_state_and_put_updates` commits the tampered state values into the state DB under a version whose `TransactionInfo`/accumulator proof is still valid.

**Caveat:** I was not able to view the full body of `TransactionListWithProof::verify` in this session (ran out of tool iterations) to give a line-exact citation of its check list; my conclusion that it omits write-set verification is based on (a) the struct definition/construction not including a `write_sets` field at all in `LoadedChunk::load`, and (b) contrasting it with the sibling `TransactionOutputListWithProof::verify`, which explicitly performs this check on a `write_set` field it does carry. If further review shows an equivalent check exists elsewhere in the restore pipeline for `TransactionListWithProof`, this finding does not hold.
