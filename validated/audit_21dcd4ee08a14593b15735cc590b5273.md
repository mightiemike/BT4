### Title
Unvalidated interest-rate curve points allow permanent underflow-revert of `accrue`, blocking deposit/borrow/repay/withdraw - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent vault contracts)

### Summary
The vault contracts (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`) let the DAO configure an 8-point utilization/interest-rate curve via `set-points-util` / `set-points-rate`, which are only checked for a per-value upper bound, never for monotonic ordering between successive points. If the curve is ever submitted with a non-increasing `util` or `rate` sequence, the interpolation routine performs unsigned subtractions that can underflow, causing `interest-rate` (and therefore every state-mutating entry point that calls `accrue`, including deposits, borrows, repayments and withdrawals) to permanently abort.

### Finding Description
`set-points-util` and `set-points-rate` pack the supplied `(list 8 uint)` via `pack-u16`, which validates only that each element is `<= max-val` (`BPS` for utils, `MAX-U16` for rates): [1](#0-0) 

There is no check anywhere that `utils[i+1] > utils[i]` or that the corresponding `rates` are monotonic. The interpolation logic that consumes these arrays assumes ascending order: [2](#0-1) 

and performs the interpolation with unsigned (`uint`) subtractions: [3](#0-2) 

In Clarity, `uint` subtraction where the subtrahend exceeds the minuend causes a runtime arithmetic-underflow abort of the entire transaction (analogous to a Solidity revert from SafeMath/0.8 overflow checks) — this is exactly the mechanism the original Merit Circle report describes for `TimeLockPool.getMultiplier`.

This interpolation is reached from every accrual on every state-changing call:
`interest-rate` → `next-index` / `next-liquidity-index` → invoked from `accrue`, which is called by `set-fee-reserve`, `set-points-util`, `set-points-rate`, and — critically — by the deposit/borrow/repay/withdraw entry points of the vault, e.g.: [4](#0-3) 

If `linear-interpolate` is fed `x1 > x2` or `y1 > y2` for a mis-ordered pair of points (which is exactly what happens once `utils`/`rates` are no longer strictly increasing), the subtraction `(- x2 x1)` or `(- y2 y1)` underflows and aborts.

### Impact Explanation
Once a curve is set out of order, `interest-rate` reverts unconditionally on every call. Since `accrue` (and thus `next-index`/`next-liquidity-index`) is invoked by every state-mutating vault function — deposits, borrows, repayments, withdrawals, and even the setters used to fix the curve (`set-points-util`/`set-points-rate` themselves call `accrue` before applying the new value) — the vault becomes permanently unusable for all users. This freezes all currently supplied/borrowed funds in that vault (temporary freezing of funds, potentially indefinite if the DAO cannot execute a corrective proposal because the setter functions that would fix it also call `accrue` and thus also revert), matching the "temporary freezing of funds" impact class.

### Likelihood Explanation
This does not require any external exploit — a single malformed governance proposal (a typo, wrong sort order, or copy-paste error in either the `util` or `rate` list) is sufficient to trigger the DoS on the very next accrual-touching call, including the call that set the bad values in the same block or any subsequent block. Given there is no validation of ordering anywhere in `pack-u16`, `set-points-util`, or `set-points-rate`, likelihood of an unvalidated, incorrectly-ordered curve slipping through is non-trivial, especially across six near-identical vault deployments each needing separately curated 8-point curves.

### Recommendation
Add an explicit monotonicity check when packing/setting the curve points: assert that for all `i`, `utils[i] < utils[i+1]` and `rates[i] <= rates[i+1]` (or whatever ordering the interpolation algorithm requires) before accepting the new curve in `set-points-util` and `set-points-rate`. Reject the transaction with a clear error rather than allowing a value that will later underflow inside `linear-interpolate`.

### Proof of Concept
1. DAO calls `(contract-call? .vault-usdc set-points-util (list u0 u5000 u2500 u7000 u7500 u8500 u9000 u10000))` — a curve where the third point (`u2500`) is smaller than the second (`u5000`), violating ascending order. `pack-u16` only checks `pos <= BPS`, so this passes. [5](#0-4) 
2. On the next call to any state-changing entry point (e.g. `deposit`), `accrue` is invoked, which calls `next-index`/`next-liquidity-index` → `interest-rate` → `interpolate-rate` → `resolve-and-interpolate`. [6](#0-5) 
3. During the fold over the zipped util/rate pairs, once the target utilization falls between the out-of-order points, `linear-interpolate` is called with `x2 < x1` (since the "next" util value is smaller than the "previous" one due to the mis-ordering), causing `(- x2 x1)` to underflow. [3](#0-2) 
4. The underflow aborts the entire transaction, so `deposit` (and every other function calling `accrue`) reverts. Because the fix requires calling `set-points-util`/`set-points-rate` again, and those setters themselves call `(try! (accrue))` before applying the corrected values, the vault is stuck in a permanently reverting state until a separate mechanism (if any) bypasses `accrue`. [1](#0-0)
