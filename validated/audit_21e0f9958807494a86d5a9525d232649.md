### Title
Duplicate-rescue guard in `AttachRescueOutboundFromReceipt` only excludes `PENDING`/`OBSERVED`, allowing a second `RESCUE_FUNDS` outbound after the first rescue reaches any terminal status other than `REVERTED` - ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
`AttachRescueOutboundFromReceipt` attaches a `TxType_RESCUE_FUNDS` outbound to an existing `UniversalTx` whenever it observes a `RescueFundsOnSourceChain` event from the `UniversalGatewayPC` gateway contract. The only anti-duplication check it performs scans existing outbounds on the UTX and rejects a new rescue **only** if a prior rescue outbound is still `PENDING` or `OBSERVED`. [1](#0-0) 

### Finding Description
The guard's comment states the intended invariant: "reject if an active rescue (PENDING or OBSERVED) already exists. A REVERTED rescue may be retried." This design only accounts for two outcomes of a prior rescue attempt: still-in-flight (`PENDING`/`OBSERVED`) or explicitly failed (`REVERTED`). It does not account for a prior rescue that reached a *different* terminal state — e.g., a successfully executed/finalized rescue outbound (whatever terminal "success" status `FinalizeOutbound`/`VoteOutbound` assigns when `observedTx.Success == true`, as seen in `msg_vote_outbound.go`) or any other non-`REVERTED` terminal status such as an aborted state. [2](#0-1) 

Once an outbound's `OutboundStatus` transitions out of `PENDING`/`OBSERVED` into any terminal value that is not literally `REVERTED`, the loop in `AttachRescueOutboundFromReceipt` no longer sees it as blocking, so a second `RescueFundsOnSourceChain` event for the same `originalUtxId` will pass the guard, and `attachOutboundsToUtx` will append a second `RESCUE_FUNDS` `OutboundTx` with `Status_PENDING` to the same UTX, which then proceeds through normal TSS signing/voting to be broadcast against the same escrowed source-chain funds pool. [3](#0-2) 

The rescue eligibility checks earlier in the function (CEA-deposit-`FAILED` check, or `INBOUND_REVERT` reaching `REVERTED`) are evaluated against the *original inbound/auto-revert* outbound, not against the state of any prior rescue outbound, so they do not prevent re-triggering rescue once a first rescue has already completed successfully. [4](#0-3) 

### Impact Explanation
If a second rescue outbound is created and carried through voting/TSS signing by honest validators (the flow that follows an accepted `OutboundTx` is unchanged and is executed the same way as any other legitimate outbound), the same escrowed/stuck source-chain funds could be released twice — once via the original successful rescue and once via the duplicate — resulting in unauthorized double release of protocol/user-controlled funds. This falls squarely in the "unauthorized release ... of user or protocol-controlled funds" and "corruption of ... refund accounting" impact categories.

### Likelihood Explanation
The exploitability hinges on whether an unprivileged actor can cause the `UniversalGatewayPC` contract to emit a second `RescueFundsOnSourceChain` event for the same `universalTxId` after a first rescue has already completed. That contract's on-chain gating logic lives outside the scoped Go surfaces reviewed here (it is Solidity, not part of `x/`, `universalClient/`, `precompiles/usigverifier/`, or the ante/gasless controls), so it could not be verified directly. However, the presence of an explicit off-chain (module-level) duplicate-guard in `AttachRescueOutboundFromReceipt` — rather than reliance on the contract alone — suggests the module is expected to be the authoritative de-duplication point, since the UTX/outbound status bookkeeping lives only in this module's state, not on the gateway contract. If the contract does not itself track "already rescued" state per UTX (plausible, since that bookkeeping is delegated to this module), then this Go-side gap is directly exploitable by any unprivileged party able to invoke the rescue path a second time.

### Recommendation
Change the guard to reject creation of a new `RESCUE_FUNDS` outbound whenever **any** prior rescue outbound exists on the UTX whose status is not a definitive, retryable failure state (i.e., invert the check to an explicit allow-list of `REVERTED`/failed-terminal statuses rather than a deny-list of `PENDING`/`OBSERVED`). Concretely: reject if a prior rescue outbound's status is anything other than `Status_REVERTED` (or whatever failure-terminal status is used), instead of only rejecting `PENDING`/`OBSERVED`.

### Proof of Concept
1. Create a UTX with `InboundTx.IsCEA = true` and `PcTx[0].Status = "FAILED"` (or a non-CEA UTX with a `REVERTED` `INBOUND_REVERT` outbound).
2. Call `AttachRescueOutboundFromReceipt` with a receipt containing a `RescueFundsOnSourceChain` log for this UTX → a `RESCUE_FUNDS` outbound is attached with `Status_PENDING`.
3. Drive that outbound through `VoteOutbound`/`FinalizeOutbound` with `observedTx.Success = true` so it reaches whatever terminal "success" status is assigned (anything other than `Status_REVERTED`).
4. Call `AttachRescueOutboundFromReceipt` again with a second receipt/log for the same `originalUtxId`.
5. Assert: the loop at `create_outbound.go:271-282` does not reject the call (since the existing rescue outbound's status is neither `PENDING` nor `OBSERVED`), and a second `RESCUE_FUNDS` `OutboundTx` is appended to `originalUtx.OutboundTx`, proving the duplicate-rescue invariant is violated for non-`REVERTED` terminal statuses.

Note: I could not fully confirm the exact name of the "success" terminal `Status_*` enum value assigned by `FinalizeOutbound` within the available inspection budget; the referenced files (`x/uexecutor/keeper/outbound.go`, `x/uexecutor/types/outbound_tx.go`) contain the relevant status-transition logic but weren't read in full. This does not affect the core finding — the guard's logic explicitly only special-cases `PENDING`/`OBSERVED` vs. `REVERTED`, leaving any other terminal status unguarded.
