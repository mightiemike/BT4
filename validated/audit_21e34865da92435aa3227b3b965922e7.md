### Title
Market's timestamp-keyed `index-cache` is not invalidated when bad-debt socialization changes the vault's liquidity index mid-block - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
### Finding Description
`v0-4-market.clar` caches vault liquidity/borrow indexes per `{ timestamp: stacks-block-time, aid: uint }` in `index-cache`, via `accrue-and-cache`: [1](#0-0) 

Once a `(timestamp, aid)` pair is cached, every later read in the same block (`get-cached-indexes`) returns the cached value without re-querying the vault, on the theory that the vault's index cannot change again within the same block: [2](#0-1) 

That assumption is false. `socialize-debt-asset` — the bad-debt write-down helper invoked from `liquidate` — explicitly demonstrates that the vault's `lindex`/`index` *can* change again later in the same block, after a cache entry already exists, because writing down debt in the vault changes `next-liquidity-index()`. The developers patched this one call site by manually re-writing `index-cache` after `vault-accrue`: [3](#0-2) 

This manual patch proves the source value (the vault's index) is mutable mid-block and that stale cache reads are a recognized risk — but it is only applied at this one call site. Any other transaction in the same block that reads `get-cached-indexes`/`accrue-and-cache` for the same `aid` *before* this socialization occurs will populate the cache with the pre-write-down index; any transaction that reads it *after* socialization for the same block will get the corrected value only because of the manual overwrite, not because the caching model itself detects invalidation. The cache-invalidation mechanism is coupled purely to `stacks-block-time`, not to actual mutation of vault state — exactly the "cached value not invalidated when its source moves" pattern.

### Impact Explanation
Because scaled debt and collateral values (and therefore health/LTV checks in `borrow`, `repay`, `collateral-remove`, and `liquidate`) are computed directly from these cached indexes (see `calculate-asset-notional-value`, `convert-to-scaled-debt`, `process-debt-asset`), any operation that reads a stale, un-refreshed cached index within the same block as a bad-debt write-down for the same asset will compute debt/collateral notional values against the wrong index. Depending on ordering, this can let a user's position appear healthier or less healthy than it actually is, leading to under- or over-valuation of debt for borrow/repay/liquidation math within that block — a temporary freezing/incorrect-accounting condition on user funds rather than a lasting insolvency, since the cache resets on the next block.

### Likelihood Explanation
This requires bad-debt socialization to occur (a liquidation that fully wipes out a borrower's collateral for an asset) and another transaction reading/writing the same asset's cached index in the same block, before and after that socialization event. Bad-debt events are not attacker-controlled at will (they depend on real insolvent positions), which limits likelihood, but the underlying cache-invalidation gap is a genuine design flaw independent of any single actor's intent — the protocol itself acknowledges and patches only the one known case.

### Recommendation
Remove reliance on the assumption that vault indexes are immutable within a block. Either (a) invalidate/refresh the specific `(timestamp, aid)` cache entry any time a vault-mutating call (e.g. `vault-socialize-debt`, `vault-accrue` triggered elsewhere) changes `index`/`lindex`, consistently across all call sites, not just `socialize-debt-asset`, or (b) key cache reads to a monotonically increasing "generation" counter per vault that increments on any index-changing write, rather than solely on `stacks-block-time`.

### Proof of Concept
1. Within block N, transaction A (e.g., another user's `borrow`/`repay`/`collateral-remove` for asset X) calls `accrue-and-cache(X)`, which is a cache MISS, so it calls `vault-accrue` and stores `{index, lindex}` in `index-cache` at `{timestamp: N, aid: X}` [1](#0-0) .
2. Later in the same block N, transaction B calls `liquidate` on a borrower whose entire collateral is exhausted for debt asset X, triggering `no-collateral-left` and the `fold socialize-debt-asset` path [4](#0-3) . Inside `socialize-debt-asset`, `vault-socialize-debt` write-down reduces the vault's outstanding debt, changing `next-liquidity-index()`, and the function manually overwrites `index-cache` for `{timestamp: N, aid: X}` [5](#0-4) .
3. Any third transaction C, still in block N, that reads a *different* asset's cache but reuses stale intermediate values computed from transaction A's cached index for asset X before step 2 occurred (e.g., a position evaluation whose `get-notional-evaluation` call was already using the pre-write-down cached index from step 1, cached under the same block timestamp) does not get corrected, because the invalidation performed in step 2 is scoped only to the `socialize-debt-asset` code path and does not retroactively correct any value already derived from the cache by other in-flight computations in the same block.
4. The result: within the same block, different transactions/read paths for the same vault index can observe two different values (pre- and post-write-down) depending on ordering, purely due to the timestamp-only cache key, confirming the cache is not invalidated when its underlying source (the vault index) is mutated by an event other than natural time-based accrual.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
