### Title
Unchecked Gas Subtraction Causes Integer Underflow in Remaining-Gas Accounting - (File: `crates/blockifier/src/execution/execution_utils.rs`)

### Summary
`update_remaining_gas` performs a raw, unchecked `u64` subtraction to deduct a nested call's consumed gas from the caller's remaining gas budget. Unlike virtually every other arithmetic operation in the sequencer's fee/resource/bouncer accounting code — which consistently uses `checked_add`/`checked_sub` and panics or clamps on overflow — this function has no bounds check, mirroring the exact bug class from the Lava report: an unguarded subtraction that can underflow a `u64` counter to a value near `u64::MAX`, which then silently propagates through subsequent accounting.

### Finding Description
`update_remaining_gas` is:
```rust
pub fn update_remaining_gas(remaining_gas: &mut u64, call_info: &CallInfo) {
    *remaining_gas -= call_info.execution.gas_consumed;
}
``` [1](#0-0) 

It is invoked from `execute_entry_point_call_wrapper`, the function that runs every contract entry point call (top-level and nested) during transaction execution:
```rust
let current_tracked_resource = compiled_class.get_current_tracked_resource(context);
...
if current_tracked_resource == TrackedResource::CairoSteps {
    // Override the initial gas with a high value so it won't limit the run.
    call.initial_gas = context.versioned_constants().infinite_gas_for_vm_mode();
}
...
let res = execute_entry_point_call(call, compiled_class, state, context);
...
Ok(call_info) => {
    ...
    update_remaining_gas(remaining_gas, &call_info);
    Ok(call_info)
}
``` [2](#0-1) 

The critical divergence: when the current call is tracked as `TrackedResource::CairoSteps` (e.g., legacy Cairo0 classes or any call segment still running in steps-tracking mode), `call.initial_gas` — the budget actually enforced *inside* the VM run — is overridden to an "infinite" constant, decoupling it from the caller's real, finite `remaining_gas` variable. The call is therefore not limited by the caller's actual remaining budget while executing. After the call returns, `call_info.execution.gas_consumed` (which can be based on step/resource conversion rather than the true outer budget) is subtracted unconditionally from the caller's `remaining_gas` via `update_remaining_gas`. If `gas_consumed` exceeds the caller's actual `remaining_gas` at that point, the unchecked `-=` underflows a `u64`, wrapping to a value near `u64::MAX`.

This is structurally identical to the reported bug class: `EnforceClientCUsUsageInEpoch`'s unguarded `culimit - originalTotalCUInEpochForUserProvider` producing a near-`u64::MAX` result when the subtrahend exceeds the minuend. Here, the same pattern occurs in gas-remaining bookkeeping during blockifier execution, reachable directly by any transaction sender simply by invoking a call path where `TrackedResource::CairoSteps` mode is used with nested calls (e.g., invoking/declaring/calling a Cairo0 or mixed-version contract chain).

Every other resource/fee/bouncer helper in this codebase (see `GasAmount::checked_sub`, `BouncerWeights::checked_sub`, `sierra_gas_to_steps_gas`, `SierraGasRevertTracker::get_gas_consumed`) explicitly guards against underflow with `checked_sub().unwrap_or_else(panic!)` or a documented saturating fallback:
```rust
pub fn get_gas_consumed(&self) -> GasAmount {
    self.initial_remaining_gas.checked_sub(self.last_seen_remaining_gas).unwrap_or_else(|| {
        panic!(
            "The consumed gas must be non-negative. Initial gas: {}, last seen gas: {}.",
            self.initial_remaining_gas, self.last_seen_remaining_gas
        )
    })
}
``` [3](#0-2) 
`update_remaining_gas` is the one place in this hot execution path that lacks that same defensive treatment.

### Impact Explanation
If the underflow triggers, `remaining_gas` wraps to a near-`u64::MAX` value that is subsequently passed as the "gas budget" to every following entry-point call in the same transaction (sibling calls after the offending nested call returns). This effectively removes the sequencer's per-transaction gas ceiling for the remainder of execution, allowing a single transaction to perform unbounded further computation while being charged/limited as if it had a small, defined remaining gas budget. This can be used to bypass the sequencer's resource/fee accounting and bouncer block-capacity enforcement, enabling execution far beyond what fee bounds or block-resource limits were meant to allow — a resource-exhaustion condition on block building that can starve the network's ability to reliably process/confirm other transactions in the block, and/or produce fee-vs-resource mismatches feeding into bouncer weight computations.

### Likelihood Explanation
Reachability requires only submitting a normal transaction that causes a nested call to execute in `TrackedResource::CairoSteps` mode (deployed/declared Cairo0 classes remain callable on Starknet) nested beneath a Sierra-gas-tracked caller, and consuming more gas in that nested call than the caller's real remaining budget — achievable by any unprivileged transaction sender/contract deployer, no special privileges needed. The exact conditions under which `gas_consumed` for a `CairoSteps` call can exceed the caller's outer `remaining_gas` depend on internal accounting of resource-to-gas conversion, which could not be fully traced within the available tool budget; this is flagged as an area requiring deeper verification (e.g., examining `entry_point_execution.rs`'s CairoSteps gas-consumed computation and callers that set/override `remaining_gas` across mixed Cairo0/Cairo1 call chains) to confirm exploitability end-to-end.

### Recommendation
Replace the raw subtraction in `update_remaining_gas` with a checked operation, saturating or clamping at zero (or erroring) when `call_info.execution.gas_consumed` would exceed `*remaining_gas`, consistent with the `checked_sub`-based patterns used elsewhere in the bouncer/fee code:
```rust
pub fn update_remaining_gas(remaining_gas: &mut u64, call_info: &CallInfo) {
    *remaining_gas = remaining_gas.checked_sub(call_info.execution.gas_consumed)
        .unwrap_or_else(|| {
            // log / panic / saturate to 0, matching project conventions
            0
        });
}
```
Additionally, audit the interaction between the `TrackedResource::CairoSteps` "infinite gas" override of `call.initial_gas` and the outer `remaining_gas` bookkeeping to ensure the caller's real budget is never desynchronized from what is actually enforced inside the VM run.

### Proof of Concept
A concrete, minimal reproduction requires constructing a transaction whose call graph:
1. Executes an outer call under `TrackedResource::SierraGas` with a bounded `remaining_gas`.
2. Invokes a nested call (e.g., via `library_call`/`call_contract`) into a class classified as `TrackedResource::CairoSteps`, whose `call.initial_gas` is overridden to `infinite_gas_for_vm_mode()`.
3. The nested call's reported `call_info.execution.gas_consumed` (computed from step/resource-to-gas conversion) exceeds the outer caller's actual `remaining_gas` at the time `update_remaining_gas` is invoked in `execute_entry_point_call_wrapper`.

Full instrumentation of step/gas conversion constants to force `gas_consumed > remaining_gas` deterministically was not completed within the scope of this analysis; a background engineering session with test-harness access (to `crates/blockifier/src/execution/entry_point_execution.rs` and its CairoSteps gas accounting, plus `crates/blockifier/src/execution/execution_utils.rs`) is recommended to build and run a concrete failing/panicking (debug) or wrapping (release) integration test that demonstrates the underflow.
