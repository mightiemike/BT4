### Title
`IndexLimit::Threshold` memory budget is computed only for "regular" (single-slot, ref-count-1) index entries, letting real in-mem index memory usage exceed the configured budget - (File: accounts-db/src/accounts_index/bucket_map_holder.rs)

### Summary
`BucketMapHolder::new()` converts a user-configured byte budget (`IndexLimitThreshold::num_bytes`) into a per-bin entry-count high/low watermark by dividing the byte budget by a single, fixed `bytes_per_entry` constant. That constant is derived from `InMemAccountsIndex::size_of_uninitialized() + size_of_single_entry()`, which by its own doc comment only models a "regular" entry — one with `ref_count == 1` and a single-element slot list. In practice, accounts that have not yet been cleaned/rooted-collapsed can have `ref_count > 1` and slot lists with multiple entries, each of which requires additional heap allocation beyond the "regular" size. The watermark computed from the idealized per-entry size is therefore not representative of worst-case (or even common, pre-clean) memory usage, so the actual memory consumed by the in-mem accounts index bins can exceed the configured `--accounts-index-limit` budget by an unbounded, size-dependent margin — the same class of bug as `minDepositAmount()`, which extrapolated a single calibrated constant (tuned for the 18-decimal case) across all cases without accounting for the dimension (decimals/value) that actually determines correctness.

### Finding Description
In `BucketMapHolder::new()`, when `config.index_limit` is `IndexLimit::Threshold(threshold)`, the code computes:
```
let bytes_per_entry = InMemAccountsIndex::<T, U>::size_of_uninitialized()
    + InMemAccountsIndex::<T, U>::size_of_single_entry();
let limit_entries = (limit_bytes as usize) / bytes_per_entry;
let entries_per_bin = limit_entries / bins;
let target_entries_per_bin = Self::calculate_target_entries_per_bin(entries_per_bin);
``` [4](#0-3) 

`size_of_single_entry()` is explicitly documented as "The size of an index value, with only a single entry in the slot list", i.e., it assumes the account's slot list contains exactly one `(Slot, T)` pair and the entry has `ref_count == 1`: [5](#0-4) 

The corresponding "regular"-only assumption is also called out directly in `try_make_entry_for_flush`'s comment ("'regular' means ref count == 1 and slot list len == 1") and in the background flush/eviction path (`should_evict_based_on_count`, `should_evict_based_on_free_entries`, `max_evictions_for_threshold`), all of which key off of raw entry *counts* per bin using the same fixed-size assumption baked into the watermark computation: [6](#0-5) [7](#0-6) 

The `Stats` reporting code independently acknowledges this gap: it computes a separate `estimate_mem_bytes` datapoint that explicitly adds extra bytes for entries "held in mem due to ref count or slot list length" beyond the regular-entry assumption, noting that `approx_size_of_one_entry()` assumes 'regular' entries — but this richer estimate is only used for telemetry, not for the eviction/threshold decision logic itself: [3](#0-2) 

Because the *decision* of when to start evicting (`should_evict_based_on_count`) is purely a function of raw per-bin entry count compared against a watermark computed from the "regular" per-entry size, any workload with many multi-version (multiple un-cleaned roots) or multi-ref-count accounts will consume substantially more memory per index entry than budgeted, while the eviction logic still believes the bin is under its high-water mark. This is directly analogous to the reported bug class: a single formula tuned for one canonical/base case (18-decimal assets ≙ "regular" entries) is applied uniformly, and the outlier case (non-18-decimal assets ≙ non-regular, multi-slot-list entries) causes the result to diverge wildly from the intended target, in this case turning a memory *budget* into a much larger, unbounded real memory footprint.

### Impact Explanation
This causes disproportionate memory (and, transitively, CPU due to more/larger GC-like eviction passes and background flush work) consumption relative to the operator-configured `--accounts-index-limit`, which is exactly the "disproportionate storage and CPU cost" impact category. On a validator that sized its available RAM based on the configured index-limit assuming the documented behavior, sustained bursts of non-regular (multi-slot-list / high-ref-count) index entries — which occur naturally whenever cleaning falls behind roots being created (e.g., during load spikes) — can push actual in-mem index memory well past the intended ceiling, risking OOM-driven node panics rather than the graceful disk-eviction behavior the threshold mechanism is meant to guarantee.

### Likelihood Explanation
Multi-slot-list, multi-ref-count entries are a normal, expected state for any pubkey that has been written in more than one un-cleaned root (a common condition, not an edge case) — they exist by design until `clean_accounts` catches up. Under load or when clean falls behind (e.g., long-running scans holding roots, slow clean passes, or accounts-index disk backing pressure), this divergence becomes likely to manifest as sustained excess memory rather than a purely theoretical one-off.

### Recommendation
When computing `bytes_per_entry` (and the derived watermarks) in `BucketMapHolder::new()`, either: (1) size the per-entry budget using a distribution-aware or worst-case estimate that accounts for typical ref-count/slot-list-length overhead (similar to how `Stats`'s `estimate_mem_bytes` already does for telemetry), or (2) feed the live `held_in_mem` ref-count/slot-list-length counters back into `should_evict_based_on_count`/`should_evict_based_on_free_entries` so eviction decisions are driven by actual estimated memory rather than a fixed "regular"-entry-sized count threshold.

### Proof of Concept
1. Configure a validator with `--accounts-index-limit <N>GB` (i.e., `IndexLimit::Threshold`), which computes `high_water_mark`/`low_water_mark` per bin via `bytes_per_entry = size_of_uninitialized() + size_of_single_entry()` as shown above.
2. Drive a workload (or replay a busy period) where a large fraction of hot pubkeys are updated across multiple un-cleaned roots faster than `clean_accounts` retires old versions, so many in-mem index entries carry `slot_list.len() > 1` and/or `ref_count > 1` (each extra slot-list element allocates an additional `SlotListItem<T>` beyond the inline "single entry" assumption, per the `stats.rs` comment).
3. Observe that `should_evict_based_on_count` continues to report bins as under threshold (because raw entry count is below `high_water_mark`), while actual heap memory used by the in-mem index bins exceeds `threshold.num_bytes` by a multiple proportional to the average slot-list length/ref-count in the workload — i.e., the configured index memory ceiling is not honored, unlike the documented guarantee in `--accounts-index-limit`'s help text.

    /// Returns true when a bin's HashMap free entries (`capacity - len`) are low
    /// enough that eviction should begin to prevent an imminent capacity doubling.
    /// The threshold is the overhead gap between `target_entries` and `high_water_mark`.
    pub fn should_evict_based_on_free_entries(&self, free_entries: usize) -> bool {
        match &self.threshold_entries_per_bin {
            None => self.is_disk_index_enabled(),
            Some(threshold_entries_per_bin) => {
                let overhead = threshold_entries_per_bin
                    .target_entries
                    .saturating_sub(threshold_entries_per_bin.high_water_mark);
                free_entries < overhead
            }
        }
    }

    /// Calculate maximum evictions to perform for threshold-based flushing
    /// Returns current_entries for Minimal disk index
    /// Returns the max_evictions for Threshold mode to bring count to the low water mark
    pub fn max_evictions_for_threshold(&self, current_entries: usize) -> NonZeroUsize {
        let evictions = match &self.threshold_entries_per_bin {
            None => current_entries,
            Some(threshold_entries_per_bin) => {
                // Low water mark: evict down to specified ratio of the per-bin threshold
                current_entries.saturating_sub(threshold_entries_per_bin.low_water_mark)
            }
        }
        .max(1);
        // SAFETY: evictions is ensured to be non-zero above.
        NonZeroUsize::new(evictions).unwrap()
    }
