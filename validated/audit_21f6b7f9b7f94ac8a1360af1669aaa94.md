## Finding: `verified_state_view_at_version` silently skips proof verification on DB errors, returning unverified state as authenticated

### Title
`DbStateView::get` silently bypasses Merkle proof verification when the proof fetch errors, returning unverified state values labeled as verified - ([File: storage/storage-interface/src/state_store/state_view/db_state_view.rs])

### Summary
`VerifiedStateViewAtVersion::verified_state_view_at_version` constructs a `DbStateView` that is meant to serve state reads bound to a specific, proof-verified `state_root_hash` obtained from a verified `TransactionInfo` [1](#0-0) . The actual read/verify path, however, only checks the proof when the proof fetch happens to succeed, and silently falls through to returning the unverified value otherwise: [2](#0-1) 

### Finding Description
This mirrors the structure of the external bug: a case that should hard-fail (invalid/unavailable proof) instead silently defaults to trusting unverified/attacker-adjacent data. Here, when `self.db.get_state_value_with_proof_by_version(key, version)` returns `Err(..)` (e.g., pruned state, sharding/backend errors, or any transient storage error), the `if let Ok(...)` pattern discards the error entirely — no verification occurs, and no error propagates. Execution proceeds directly to `self.db.get_state_value_with_version_by_version(key, version)`, which fetches the value via the ordinary versioned lookup with **no cryptographic binding to `root_hash`** at all. The caller of `verified_state_view_at_version` has no way to distinguish "value was proof-verified against `state_root_hash`" from "value was fetched with zero verification" — both return `Ok(Some(value))`.

### Impact Explanation
Since `verified_state_view_at_version` is explicitly the "verified" state-view construction path (its comment/API name promises proof-bound reads pinned to a ledger version and root hash), any consumer relying on this API for authenticated state reads (e.g., debugging/replay tools, or any component trusting `VerifiedStateViewAtVersion` for security-sensitive verification) can be silently served state that was never checked against `state_root_hash`. If the underlying storage is corrupted, lagging, or manipulated (e.g., a different/rolled-back state-kv shard, a stale on-disk value, or a bug in a lower storage layer) — while the proof-fetch backend call errors out — the consumer gets an unverified value with no signal that verification was skipped. This breaks the "authenticated response bound to the right ledger version and root" invariant.

### Likelihood Explanation
The likelihood of the *proof fetch specifically failing* while the *unproven lookup succeeds* is not trivially always true, but it is fully plausible: `get_state_value_with_proof_by_version` and `get_state_value_with_version_by_version` are separate calls against potentially different code paths/backends (proof generation touches the Merkle tree layer, whereas the plain versioned lookup touches the KV layer directly). Any divergence between these two layers — pruning boundaries, sharding inconsistency, or a transient error in the Merkle-proof path — silently degrades to unverified reads instead of erroring. Because the failure mode is "silent success with no verification," it would not be caught by callers, is not observable in normal operation, and would only be caught by very targeted testing.

I was not able to fully confirm which production callers (besides `vm_validator.rs`) actually invoke `verified_state_view_at_version` in a security-critical path within the indexed portion of this repo (grep for `DbStateView { }` construction sites returned limited results, and due to index size limits I could not read every caller of `VerifiedStateViewAtVersion` in full to establish end-to-end exploitability against mainnet-facing behavior). Confirming this would require a full-repo grep for `verified_state_view_at_version(` call sites, which I could not complete in the given tool budget.

### Recommendation
Change the `if let Ok(...)` to propagate the error (`?`) so that a failure to fetch/verify the proof causes `get` to return an error rather than silently falling back to an unverified read. This is the same recommendation category as the external report: fail closed instead of silently defaulting to a less-trusted result.

impl VerifiedStateViewAtVersion for Arc<dyn DbReader> {
    fn verified_state_view_at_version(
        &self,
        version: Option<Version>,
        ledger_info: &LedgerInfo,
    ) -> StateViewResult<DbStateView> {
        let db = self.clone();

        if let Some(version) = version {
            let txn_with_proof =
                db.get_transaction_by_version(version, ledger_info.version(), false)?;
            txn_with_proof.verify(ledger_info)?;

            let state_root_hash = txn_with_proof
                .proof
                .transaction_info
                .state_checkpoint_hash()
                .ok_or_else(|| StateViewError::NotFound("state_checkpoint_hash".to_string()))?;

            Ok(DbStateView {
                db,
                version: Some(version),
                maybe_verify_against_state_root_hash: Some(state_root_hash),
            })
        } else {
            Ok(DbStateView {
                db,
                version: None,
                maybe_verify_against_state_root_hash: None,
            })
        }
    }
