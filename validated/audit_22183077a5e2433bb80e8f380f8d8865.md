### Title
Stateless Validator Resolves Shard Layout from Wrong Block (Main-Transition Block Instead of Resharding Boundary Block), Causing Permanent Post-Resharding Halt - (`File: chain/chain/src/stateless_validation/chunk_validation.rs`)

---

### Summary

During stateless chunk validation after a shard split, the validator resolves the parent and child shard layouts using the epoch of the **main-transition block** (the last new chunk of the parent shard). The block producer, however, resolves those layouts from the **resharding boundary block** (the first block of the new epoch). When the parent shard produces no new chunk in the entire last old-layout epoch, the main-transition block falls in an earlier epoch that still carries the old shard layout. The child shard's brand-new `ShardId` does not exist in that old layout, so `get_child_congestion_info` fails with `InvalidShardId`. Every chunk validator deterministically rejects the child's first chunk, and the resharded shards halt permanently — a consensus-level divergence between the block producer and all stateless validators.

---

### Finding Description

The bug class from the external report is: *a flag/variable is computed from source A but used to interpret data from source B, when source B may have a different context*. The nearcore analog is: the **shard layout** is resolved from the main-transition block's epoch (source A = last new chunk of the parent shard) but is used to interpret resharding data that belongs to the boundary block's epoch (source B = the epoch-transition block).

**Block producer path** (`ReshardingManager::process_memtrie_resharding_storage_update`):
- Resolves `parent_shard_layout` and `child_shard_layout` from the **resharding boundary block** — the first block of the new epoch. This block always carries the new post-split layout, so the child shard IDs are present.

**Stateless validator path** (`validate_chunk_state_witness_impl`, `ImplicitTransitionParams::Resharding` arm):
- Before the fix, the validator resolved `parent_shard_layout` and `child_shard_layout` from `block_hash` — the **main-transition block hash**, i.e. the block that contained the last new chunk of the parent shard.
- If the parent shard produced no new chunk in the entire last old-layout epoch E, the main-transition block lies in an epoch *before* E. That epoch's shard layout is the old layout, which does not contain the child shard IDs.
- `ReshardingManager::get_child_congestion_info` then calls `shard_layout.get_shard_index(child_shard_uid)`, which fails with `InvalidShardId` because the child shard does not exist in the old layout.

The fix (present in this codebase) corrects the validator to resolve epochs from `transition.block_hash` (the resharding implicit transition's own block, i.e. the boundary block), not from the main-transition `block_hash`:

```rust
// WRONG (pre-fix): uses main-transition block_hash
let epoch_id = epoch_manager.get_epoch_id(&block_hash)?;  // block_hash = main transition

// CORRECT (post-fix): uses the resharding transition's own block
let epoch_id = epoch_manager.get_epoch_id(&transition.block_hash)?;
``` [1](#0-0) 

The comment in the fixed code explicitly documents the wrong-context hazard:

> "Using the main-transition `block_hash` here is wrong: if the parent shard produced no chunk in the last old-layout epoch, that block lies in an earlier epoch and resolves to the old layout, so the child's new shard id is absent and validation fails with `InvalidShardId`, permanently halting the resharded shard." [2](#0-1) 

---

### Impact Explanation

- **Consensus flaw reachable from ordinary conditions**: A shard that misses all chunks in the last old-layout epoch (a recoverable chunk outage, not an attack) triggers the bug. Every stateless validator independently resolves the wrong layout and rejects the child shard's first chunk with `InvalidShardId`. Since the rejection is deterministic and affects all validators simultaneously, the child shards can never accumulate the >2/3 endorsement stake required for chunk inclusion.
- **Permanent halt of resharded shards**: The child shards never produce an endorsed chunk after the split. All state and funds locked in those shards become permanently inaccessible — a loss-of-funds / contract-execution-flow-breakage impact.
- **No privileged attacker required**: The trigger is a naturally occurring chunk outage (network partition, chunk producer downtime) in the epoch immediately before a resharding boundary. Static (protocol-upgrade-driven) resharding proceeds even when the parent shard is silent, making this reachable without any attacker action. [3](#0-2) 

---

### Likelihood Explanation

- Resharding events are infrequent but scheduled. Static resharding is protocol-version-driven and happens regardless of whether the parent shard is producing chunks.
- A full-epoch chunk outage for a single shard is a recoverable scenario (the chain continues; only that shard's state is stale). Under normal operation this is rare but not impossible (e.g., all assigned chunk producers for a shard go offline simultaneously for one epoch).
- The combination — resharding boundary coinciding with a full-epoch chunk outage on the parent shard — is low-probability in practice but has no protocol-level guard preventing it.
- The bug is present in the unfixed code path; the fix is already applied in this repository.

---

### Recommendation

The fix already present in this codebase is correct: in `validate_chunk_state_witness_impl`, within the `ImplicitTransitionParams::Resharding` arm, resolve the parent and child epoch IDs (and thus shard layouts) from `transition.block_hash` (the resharding implicit transition's own block — the boundary block), not from the outer `block_hash` (the main-transition block).

```rust
// Correct: use the resharding transition's own block hash
let epoch_id = epoch_manager.get_epoch_id(&transition.block_hash)?;
let parent_shard_layout = epoch_manager.get_shard_layout(&epoch_id)?;
let child_epoch_id = epoch_manager.get_next_epoch_id(&transition.block_hash)?;
let child_shard_layout = epoch_manager.get_shard_layout(&child_epoch_id)?;
``` [4](#0-3) 

Additionally, a regression test `slow_test_resharding_parent_missing_full_epoch_before_split` in `test-loop-tests/src/tests/resharding_missing_chunks.rs` verifies that child shards recover normally after the fix. [5](#0-4) 

---

### Proof of Concept

1. Configure a network with a static (protocol-upgrade-driven) resharding scheduled at protocol version N+2.
2. Drop all chunks for the parent shard (the shard to be split) starting from epoch E-1, so the parent produces no new chunk in epoch E (the last old-layout epoch).
3. Allow the protocol upgrade to proceed. The resharding boundary block arrives at the start of epoch E+1.
4. The chunk producer for a child shard produces the child's first chunk and distributes a `ChunkStateWitness`. The witness's main-transition block is in epoch E-1 (the last epoch where the parent produced a chunk).
5. Each stateless validator enters `validate_chunk_state_witness_impl`, reaches the `ImplicitTransitionParams::Resharding` arm, and (on unfixed code) calls `epoch_manager.get_epoch_id(&block_hash)` where `block_hash` is the main-transition block in epoch E-1.
6. `get_shard_layout` for epoch E-1 returns the old layout, which does not contain the child shard IDs.
7. `ReshardingManager::get_child_congestion_info` calls `child_shard_layout.get_shard_index(child_shard_uid)` → `InvalidShardId` error.
8. All validators return `Error::InvalidChunkStateWitness`, refuse to endorse, and the child shards halt permanently.

The regression test `slow_test_resharding_parent_missing_full_epoch_before_split` reproduces this scenario end-to-end and asserts that child shards produce endorsed chunks after the fix. [6](#0-5) [7](#0-6)
