### Title
Sequential `exchangeId` Reused Across Reorgs Allows Trades Against an Unintended Token Pair - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`ExchangeCreateActuator` assigns a new exchange pair's identifier purely from a global sequential counter (`dynamicStore.getLatestExchangeNum() + 1`), exactly analogous to the reported DAO proxy address that is derived only from the factory address + nonce. `ExchangeTransactionActuator` (and the inject/withdraw actuators) later trust this bare numeric `exchangeId` to look up the token pair, without binding the trade to the actual token-pair identity the user intended when the transaction was signed.

### Finding Description
In `ExchangeCreateActuator.execute`, the exchange id is computed as: [1](#0-0) 
This `id` depends solely on how many `ExchangeCreateContract` transactions have already been committed on-chain — i.e., on transaction *ordering*, just like the Polygon factory nonce in the original report.

`Manager.java` implements chain fork switching (`switchFork`), meaning that when a reorg occurs, transactions from the abandoned branch are pulled back into the pending pool and re-executed on the new canonical chain, potentially in a different relative order relative to other pending `ExchangeCreateContract` transactions from other users. Because the id assignment is purely sequential and global, a reorg can cause `LatestExchangeNum` to advance through a different sequence, so the same numeric `exchangeId` a user previously observed (e.g., in a wallet UI, or referenced in an already-signed offline transaction) can end up bound to a **different token pair** after the reorg.

Later, `ExchangeTransactionActuator.doValidate`/`execute` trust the `exchangeId` alone to fetch the pair: [2](#0-1) 
The validation only checks that the user-supplied `tokenID` (the token side they want to sell) matches one of the two tokens in whatever pair is currently stored under that id — it never checks the *other* leg of the pair against what the user intended. A user's pre-broadcast/pre-signed trade (specifying `exchangeId`, `tokenId`, `quant`, and `expected`) can therefore be routed against a completely different counter-token than the user believed, as long as the `tokenExpected` amount threshold happens to be satisfied.

### Impact Explanation
If a reorg reshuffles the order in which competing `ExchangeCreateContract` transactions are committed, a previously-known `exchangeId` can silently now reference an unrelated (or malicious) token pair. A pending or replayed `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` referencing that id will execute against the wrong pair, causing users to receive an unintended (potentially worthless) token instead of the one they intended to acquire — direct asset/accounting corruption for the victim, mirroring the "join the wrong DAO" fund-loss scenario in the report.

### Likelihood Explanation
This requires a live chain reorg (fork switch) coinciding with unconfirmed, competing `ExchangeCreateContract` transactions from different accounts, plus a victim transaction that references the exchange only by numeric id. Reorgs of a few blocks are a known possibility in java-tron's DPoS consensus (handled explicitly by `Manager`'s fork-switch logic), and `ExchangeCreateContract`/`ExchangeTransactionContract` are ordinary unprivileged, broadcastable transactions — so the precondition is realistic though not trivially guaranteed, since it requires transaction-ordering non-determinism across the reorg window, not merely reorg occurrence.

### Recommendation
Bind exchange operations to the pair identity, not just the sequential id: require `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` to also specify (and have validated against) the expected `firstTokenId`/`secondTokenId` (or a hash/commitment of the pair) stored in the `ExchangeCapsule`, rejecting the operation if the on-chain pair does not match what the caller expects — analogous to the report's recommendation to verify `ensName`/`daoCreator` in `joinDAO`.

### Proof of Concept
1. Two accounts, Alice and Mallory, each submit `ExchangeCreateContract` transactions in the same block window (e.g. Alice creates TRX/USDT, Mallory creates TRX/SCAM).
2. Suppose in the initial chain state Alice's pair gets `exchangeId=N` and Mallory's gets `N+1`.
3. Bob observes `exchangeId=N` is the TRX/USDT pool and submits a signed `ExchangeTransactionContract` with `exchangeId=N`, `tokenId=TRX`, `quant`, and a computed `expected` USDT amount based on the pool's current reserves.
4. A short reorg occurs before Bob's transaction is confirmed; in the new canonical ordering, Mallory's `ExchangeCreateContract` is committed first, so her TRX/SCAM pair now receives `exchangeId=N` while Alice's TRX/USDT pair becomes `N+1`.
5. Bob's transaction, still referencing `exchangeId=N`, is validated in `ExchangeTransactionActuator.doValidate` — `tokenID` (TRX) still matches one leg of the pool, and if Mallory sets the SCAM/TRX reserves such that the computed `anotherTokenQuant` still exceeds Bob's `expected` threshold, the trade proceeds via `ExchangeCreateActuator`/`ExchangeCapsule.transaction` logic at [3](#0-2) , and Bob receives worthless SCAM tokens instead of USDT.
