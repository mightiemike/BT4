### Title
Missing zero-address validation on `RevertInstructions.FundRecipient` lets an attacker permanently burn refunded/reverted funds - ([File: x/uexecutor/types/inbound.go], [File: x/uexecutor/keeper/build_revert_outbound.go], [File: x/uexecutor/keeper/outbound.go])

### Summary
`Inbound.RevertInstructions.FundRecipient` is attacker-controlled data that originates from the depositor's call to the external-chain gateway contract, is relayed unmodified by Universal Validators, and is used verbatim as the destination address for refunded/reverted funds — both when re-minting PRC20 on Push Chain and when building the outbound revert transaction back to the source chain. Neither `Inbound.ValidateForExecution()` nor the revert-building code checks that `FundRecipient` is non-zero or otherwise well-formed; only an empty-string check (`!= ""`) gates the fallback-to-sender logic.

### Finding Description
`ValidateForExecution` in [1](#0-0)  validates `Recipient` format for `FUNDS`/`GAS` and isCEA payload flows via `utils.IsValidAddress(p.Recipient, utils.HEX)`, but it never inspects `p.RevertInstructions.FundRecipient` at all — there is no call path that validates this field's format or rejects the zero address.

Both places that consume `FundRecipient` only guard against the empty string, not the zero address: [2](#0-1) [3](#0-2) 

In `handleFailedOutbound`, the resolved `recipient` is passed straight into `CallPRC20Deposit`, which mints/deposits PRC20 tokens on Push Chain to that address with no zero-address guard: [4](#0-3) 

Similarly, `buildRevertOutbound` sets `outbound.Recipient` directly from `FundRecipient` for the `INBOUND_REVERT` outbound that gets TSS-signed and broadcast to the source chain, again with no zero-address check.

`FundRecipient` is populated from raw event data decoded from the external chain's gateway/deposit event (see the SVM/EVM event parsers and `common/event_processor.go` which populate `RevertInstructions`), meaning the value is fully controlled by the depositor who calls the gateway contract — an unprivileged external actor.

### Impact Explanation
If an attacker deposits funds through the gateway with `RevertInstructions.FundRecipient` set to the zero address (`0x000...000`), and the corresponding inbound is later reverted or its execution fails (e.g., malformed payload, missing token config, expired ballot via `RevertStuckInbound`, or execution failure requiring `handleFailedOutbound`), the protocol will mint PRC20 tokens to the zero address on Push Chain and/or construct an outbound revert transaction sending native asset to the zero address on the external chain. Since the zero address is unspendable, this results in a **permanent loss of user/protocol-controlled funds** — squarely within the allowed impact scope ("permanent loss ... of user or protocol-controlled funds").

### Likelihood Explanation
Likelihood is moderate-to-high: it requires no privileged access, no validator collusion, and no cross-linking of ballots — an ordinary depositor can set an arbitrary `fundRecipient` on the source-chain gateway call and then intentionally trigger a revert condition (e.g., malformed `UniversalPayload`, unsupported token, or letting the ballot expire) to force the refund path to fire. Every honest validator will observe and vote on the same malicious `FundRecipient` value, so it reaches consensus and executes exactly as submitted.

### Recommendation
Add an explicit zero-address (and format) check on `RevertInstructions.FundRecipient` wherever it is consumed for refund/revert purposes:
- In `Inbound.ValidateForExecution()`, validate `FundRecipient` (when set) with `utils.IsValidAddress(...)` and reject the zero address, falling back to `Sender` if it fails validation (or rejecting the inbound outright).
- In `buildRevertOutbound` and `handleFailedOutbound`, add a defensive zero-address check before using `FundRecipient` as the mint/refund destination, falling back to `outbound.Sender`/`inbound.Sender` when the configured recipient is the zero address.

### Proof of Concept
1. Attacker calls the external-chain gateway contract's deposit function with a `FUNDS_AND_PAYLOAD` (or `FUNDS`) inbound, setting `RevertInstructions.fundRecipient = 0x0000000000000000000000000000000000000000`, and an intentionally malformed `UniversalPayload` (e.g., invalid selector) or an unsupported/removed token so execution will fail.
2. Universal Validators observe the deposit event and vote `MsgVoteInbound` with the inbound as emitted (including the zero `FundRecipient`), reaching quorum honestly.
3. `VoteInbound` → `ValidateForExecution` fails on the payload/token, calling `handleFailedInboundValidation` → `buildRevertOutbound`, which sets `Recipient = FundRecipient = 0x0` (since it is non-empty) — [2](#0-1) .
4. The resulting `INBOUND_REVERT` outbound is TSS-signed and broadcast to the source chain, sending the refunded asset to the zero address, or (for a failed outbound path) `handleFailedOutbound` mints PRC20 to `common.HexToAddress(recipient)` = zero address — [3](#0-2)  — permanently destroying the refunded value.

// ValidateForExecution checks fields that are required for actual execution of the inbound.
// Called after ballot finalization, before ExecuteInbound. Failures here produce a failed
// PCTx and (for non-isCEA) a revert outbound, rather than dropping the vote.
func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}
