### Title
Global-contract identity keyed only by `AccountId` allows a reclaimed/deleted account name to hijack code trusted by all its existing "users" - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
When `GlobalContractDeployMode::AccountId` is used, a global contract is addressed purely by the deploying `AccountId`, with no binding to a specific "incarnation" of that account. Other accounts opt in once via `UseGlobalContractAction{ AccountId(owner) }`, storing `AccountContract::GlobalByAccount(owner)` on their own record. If the `owner` account is later deleted and the name is recreated by a different party, that new party can redeploy a different global contract under the same `AccountId` identifier, and every account that previously referenced `GlobalByAccount(owner)` will silently start executing the new, attacker-controlled code — analogous to Alice's deleted "handle" being followed because the deleted-profile check only compared handles, not profile identity.

### Finding Description
`UseGlobalContractAction` stores a reference by account identity, not by a specific deployment: [1](#0-0) 

The code that a `FunctionCall` actually executes is resolved at call time straight from this stored `AccountContract::GlobalByAccount(id)` field, by looking up the current `GlobalContractCode` trie entry for `GlobalContractIdentifier::AccountId(id)`: [2](#0-1) [3](#0-2) 

Deployment under `AccountId` mode simply (re)writes the `GlobalContractCode` entry keyed by the deployer's own `AccountId` — there is no check that the deployer is the *same* account that originally deployed under that name, only that the transaction's predecessor is currently that account: [4](#0-3) [5](#0-4) 

Critically, deleting an account (`DeleteAccountAction`/`action_delete_account`/`remove_account`) removes the account record, its access keys, gas keys, and contract data/local code, but does **not** touch the `GlobalContractCode`/`GlobalContractNonce` trie entries keyed by `GlobalContractCodeIdentifier`: [6](#0-5) [7](#0-6) 

So the `GlobalContractCode` entry for `AccountId(owner)` outlives the account itself. Named accounts can be freely recreated by anyone once deleted (subject to the normal account-creation rules), and the new occupant of that name can immediately call `DeployGlobalContract` with `deploy_mode: AccountId`, overwriting the shared code that other, unrelated accounts still point to via `AccountContract::GlobalByAccount(owner)`. Those consumer accounts never re-confirm or re-consent to the new code — the next `FunctionCall` against them silently resolves to whatever the new "owner" deployed, per `RuntimeContractIdentifier::resolve`.

This mirrors the C4 report precisely: the reference used for authorization/identity ("handle" → `AccountId`) is decoupled from the actual underlying entity's lifecycle ("profile" → account incarnation / global-contract deployment), so a fresh entity created with the recycled identifier is transparently substituted wherever the old identifier is still referenced.

### Impact Explanation
Any account that opted into a `GlobalByAccount` contract from a name that is later deleted and re-registered becomes subject to arbitrary code execution chosen by the new occupant of that name, without any new transaction, approval, or `UseGlobalContract` action from the victim account. Because global-contract code runs with full access to the victim account's storage/context during `FunctionCall`, this allows an attacker who can grab a recycled `AccountId` to run malicious logic (e.g., to trigger unintended transfers, promises, or corrupt application state) inside every account still bound to that identifier — a state-transition outcome (arbitrary/unauthorized code execution reached through a legitimate, protocol-defined action) that can lead to unauthorized value movement for any of those dependent accounts.

### Likelihood Explanation
Exploitation requires only ordinary, permissionless actions available to any transaction signer: deleting an account (or waiting for a popular global-contract-owner account to be deleted), recreating an account with the same name, and issuing `DeployGlobalContractAction{ deploy_mode: AccountId }`. No validator, network, or privileged access is needed — every step is reachable from a single unprivileged transaction. The main precondition is that some other account previously executed `UseGlobalContract{ AccountId(owner) }` against a name that later becomes deletable/reclaimable, which is a realistic scenario for popular reusable/shared-library global contracts.

### Recommendation
Bind `AccountContract::GlobalByAccount`/`GlobalContractIdentifier::AccountId` references to a specific deployment "generation" rather than the bare account name — e.g., include a monotonically increasing per-account "contract epoch"/creation-height component (similar to how `AccessKey`/bootstrap nonces are reseeded on account recreation) in the `GlobalContractCode`/`GlobalContractNonce` trie key, or clear/invalidate `GlobalContractCode` entries owned by an account when that account is deleted, so a freshly recreated account cannot silently inherit or hijack the previous incarnation's global-contract identity. Alternatively, disallow account deletion while any `GlobalContractCode` deployed under `AccountId` mode by that account still exists (mirroring how `DeleteAccountStaking`/`DeleteAccountWithLargeState` already block deletion under certain conditions).

### Proof of Concept
1. Account `owner.near` deploys a benign global contract with `DeployGlobalContractAction{ deploy_mode: AccountId }` (`runtime/runtime/src/global_contracts.rs:25-63`).
2. Account `victim.near` runs `UseGlobalContractAction{ contract_identifier: AccountId(owner.near) }`, setting `AccountContract::GlobalByAccount(owner.near)` on its own record (`runtime/runtime/src/global_contracts.rs:76-108`).
3. `owner.near` is deleted via `DeleteAccountAction`; `remove_account` clears the account/keys/local code/data but leaves the `GlobalContractCode`/`GlobalContractNonce` entries for `GlobalContractCodeIdentifier` associated with `owner.near` untouched (`core/store/src/utils/mod.rs:504-553`).
4. Attacker creates a new account named `owner.near` (subject to normal creation rules) and deploys a new, malicious contract with `DeployGlobalContractAction{ deploy_mode: AccountId }`, overwriting the `GlobalContractCode` entry for `AccountId(owner.near)`.
5. Any subsequent `FunctionCall` to `victim.near` resolves its contract via `RuntimeContractIdentifier::resolve` → `GlobalContractIdentifier::AccountId(owner.near)` → the attacker's new code (`runtime/runtime/src/contract_code.rs:36-73`, `91-106`), executing arbitrary attacker logic in `victim.near`'s context — without `victim.near` ever issuing a new `UseGlobalContract` action.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }
