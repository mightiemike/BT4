## Title
`TransactionOutput::ensure_match_transaction_info()` never validates the state-checkpoint / hot-state / position-state roots, letting replay-verification tools accept a corrupted state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the single correctness check used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that locally re-executed transactions match the authenticated `TransactionInfo` pulled from an archive/backup. The function checks `status`, `gas_used`, `write_set` hash, and `event_root_hash`, but explicitly and admittedly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` computes and compares only three fields against the trusted `TransactionInfo`: status, gas used, write-set hash (`state_change_hash`), and event root hash. It never recomputes or compares the authenticated `state_checkpoint_hash` (the JMT/state-tree root committed on-chain), nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`: [2](#0-1) 

The code itself flags this as a known gap via an inline TODO: [3](#0-2) 

This method is the *sole* correctness gate used by the db-tool replay-verification utility that operators run against archived history to detect state divergence/forks: [4](#0-3) 

Because the write-set hash (`state_change_hash`) only proves that the *raw write operations* produced by re-execution are byte-identical to the archived write set, it says nothing about whether applying those writes to the local Merkle/Jellyfish state tree produces the same root that was actually committed and signed by validators. A divergence can arise independent of the write set itself — e.g., an off-by-one/ordering bug in the JMT/SMT batch-update logic, a bug in `LedgerStateWithSummary::update`/`ProvableStateSummary`, a stale/incorrectly-thawed hot-state cache, or (per the same TODO) any bug in the new position-state (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) root computation path — and `ensure_match_transaction_info` would still report success because it never inspects `state_checkpoint_hash` at all, in any code path, regardless of whether trading-native state roots are enabled.

By contrast, the real consensus/chunk-executor commit path *does* verify the checkpoint hash against known values from `TransactionInfo`: [5](#0-4) 

So the state-root integrity check exists and is correctly enforced during normal execution/commit, but is silently missing from the standalone replay/verification tooling that operators and auditors rely on to detect exactly this class of bug (state-tree divergence not reflected in the write set).

### Impact Explanation
This does not corrupt the actual committed ledger (the live commit path still validates checkpoint hashes via `DoStateCheckpoint`/`get_state_checkpoint_hashes`), so it is not a live consensus-fork primitive by itself. However, it directly undermines one of the required integrity pivots: "replay paths ... must not reinterpret committed data into a different ledger state" and "Wrong accumulator root ... or state proof accepted as valid" — here, a wrong/corrupted state root would be *accepted as valid* by the replay-verify tool. This is the exact tool operators/auditors use to detect divergence between a re-executed history and the authenticated archive (i.e., to catch state-root bugs or malicious archive data before they become an operational incident). If the underlying state-tree/root-computation logic has any bug (a real and recurring bug class in JMT/SMT-heavy code, as evidenced by the extensive hot-state/position-state refactor visible in this codebase), this verification gap means the bug would go undetected by the intended safety net, silently propagating incorrect state roots that operators believe have been validated. This is a real, code-provable oversight, but its severity is bounded by the fact that it affects an offline verification/debugging tool rather than the live consensus-critical commit path.

### Likelihood Explanation
The gap is deterministic and always present (not behind a feature flag) — every call to `ensure_match_transaction_info` skips checkpoint-hash comparison. Triggering an actual undetected divergence still requires a separate latent bug in state-root computation (JMT/SMT/hot-state/position-state) to exist and produce a wrong root while write-sets remain hash-identical. I could not fully verify within the available search budget whether any additional/independent check backstops this in `aptos-debugger.rs` or `cli/commands.rs` beyond calling the same method, so the true likelihood of the state-root divergence pre-condition being met is unverified and would need further investigation of the JMT/hot-state code paths themselves.

### Recommendation
Extend `ensure_match_transaction_info` to compute the actual state/hot-state/position-state checkpoint roots from local execution when the corresponding checkpoint exists on the `TransactionInfo`, and compare them against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (when present) and `txn_info.position_state_checkpoint_hash()` (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled), returning an error on mismatch exactly as it already does for status/gas/write-set/event-root. This closes the gap noted in the existing TODO before any reliance is placed on it, especially before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on.

### Proof of Concept
1. Instrument `replay_on_archive` (or `aptos-debugger`) to replay a known transaction range from a backup archive.
2. Force (via a test/hypothetical local bug or fault-injection) a scenario where a re-executed transaction produces a `WriteSet` that is byte-identical to the archived one (same `state_change_hash`), but the local state Merkle/Jellyfish tree accumulates it into a different root than the archived `state_checkpoint_hash` (e.g., simulate a stale hot-state cache entry, or ordering divergence not reflected in the write op values themselves).
3. Run `execute_and_verify` in `replay_on_archive.rs`; observe that `ensure_match_transaction_info` returns `Ok(())` despite the divergent state root, because `state_checkpoint_hash` is never compared. [6](#0-5) [7](#0-6)
