### Title
Panic-based DoS via unchecked bytecode segment length slicing during Declare compilation - ([File: crates/blockifier/src/execution/contract_class.rs])

### Summary
`NestedFeltCounts::new_inner`, invoked during conversion of a compiled CASM class into `CompiledClassV1` for every Cairo1 Declare transaction, slices the class's `bytecode` buffer using lengths taken from the CASM's `bytecode_segment_lengths` field without checking that these lengths are within the bounds of the actual bytecode. If they diverge, the slicing operations panic instead of returning a graceful error.

### Finding Description
`NestedFeltCounts::new` recurses over `bytecode_segment_lengths` and slices `bytecode` accordingly: [1](#0-0) 

For a `Leaf(len)`, the code does `&bytecode[..*len]`; for inner nodes it advances via `&bytecode[total_felt_count..]`. Neither branch validates `*len <= bytecode.len() - total_felt_count` before slicing — Rust panics with an out-of-bounds slice index if the segment length exceeds the remaining bytecode. This is analogous to the CVE-2023-0804 pattern: an out-of-bounds access caused by trusting an attacker/crafted-input-controlled size field without a bounds check before it's used to index into a buffer.

This function is invoked from `TryFrom<VersionedCasm> for CompiledClassV1`, which is on the path used to materialize a declared class into its executable representation: [2](#0-1) 

The `bytecode_segment_lengths` value it's built from is a `NestedIntList` structure that ships with the `CasmContractClass` — it is present on the on-chain-consumed compiled class object (see `get_bytecode_segment_lengths` on `CasmContractClass`) [3](#0-2) , and it is read again whenever a class is fetched/hydrated from storage or from a peer via `SyncStateReader::get_compiled_classes`, which calls `CompiledClassV1::try_from(casm_contract_class)` directly on data obtained from another node/client without first re-validating segment-length/bytecode-length consistency: [4](#0-3) 

In the normal Declare-transaction flow, `bytecode_segment_lengths` is produced by the trusted `SierraToCasmCompiler` subprocess together with the corresponding `bytecode`, so the two are self-consistent for classes compiled locally from Sierra [5](#0-4) . The gateway additionally validates only that the caller-supplied `compiled_class_hash` matches the hash computed from the (already-parsed) CASM class [6](#0-5)  and [7](#0-6) ; the hash-computation path (`bytecode_hash`/`bytecode_hash_node`) has its own internal `assert_eq!` on total consumed length, so a mismatched CASM would already panic there before/around class-hash verification rather than being rejected cleanly: [8](#0-7) 

### Impact Explanation
A panic triggered while processing a submitted Declare transaction (or while another node re-materializes a synced/declared class from storage/peers via `SyncStateReader`) crashes the executing thread/process. Because both the class-hash computation (`assert_eq!`) and `NestedFeltCounts::new` (`&bytecode[..*len]`) are unguarded panics reachable from attacker-influenced CASM contents, this can cause honest sequencer nodes processing the same Declare transaction, or nodes syncing the resulting declared class, to panic — a network-wide halt/DoS on new-transaction confirmation rather than data corruption, matching the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
Exploitability hinges on whether an attacker can get a `CasmContractClass` with `bytecode_segment_lengths` inconsistent with `bytecode` accepted anywhere before this code runs. If the only path to construct such a class is the trusted, deterministic `SierraToCasmCompiler` subprocess (compiling a submitted Sierra program), the two fields should always agree, making this specifically hard to trigger via normal Sierra→CASM compilation flow. The likelihood is materially higher for the `SyncStateReader::get_compiled_classes` path, which re-parses a `CasmContractClass` fetched from another party (peer/central sync) without re-verifying segment/bytecode consistency, so a divergence introduced anywhere upstream (bug, storage corruption, malicious peer serving crafted class data) reaches the unchecked slice directly. I could not fully confirm within the available context whether any intermediate validation (e.g., schema/structural checks in `apollo_storage`/state-sync deserialization) already rejects such malformed segment-length data before reaching `CompiledClassV1::try_from`; this is the main remaining uncertainty.

### Recommendation
- In `NestedFeltCounts::new_inner` (and `NestedFeltCounts::new`), replace unchecked `bytecode[..*len]` / `bytecode[total_felt_count..]` indexing with checked slicing (`get(..*len)` / `get(total_felt_count..)`) and propagate a proper `Result`/error (e.g., a new `ProgramError`/`TransactionExecutionError` variant) instead of panicking.
- Ensure `TryFrom<VersionedCasm> for CompiledClassV1` surfaces this as a recoverable error so callers (gateway compilation, state sync, storage read) can reject the malformed class instead of crashing the process.
- Add the same bounds validation before/at the point `bytecode_hash`/`bytecode_hash_node`'s `assert_eq!` is reached, converting it into a returned error.
- Add regression tests constructing a `CasmContractClass` whose `bytecode_segment_lengths` sums to a value larger than `bytecode.len()` and assert a clean error is returned from every ingestion path (`CompiledClassV1::try_from`, `SyncStateReader::get_compiled_classes`, gateway declare flow).

### Proof of Concept
Conceptual (Rust, `crates/blockifier/src/execution/contract_class.rs`):
```rust
let malicious_lengths = NestedIntList::Leaf(bytecode.len() + 1); // exceeds actual bytecode length
let casm = CasmContractClass { bytecode: /* len = N */, bytecode_segment_lengths: Some(malicious_lengths), .. };
// Reached via SyncStateReader::get_compiled_classes or any direct CompiledClassV1::try_from(casm) call:
let _ = CompiledClassV1::try_from((casm, sierra_version)); // panics: slice index N+1 out of range for bytecode of length N
```
Because I could not conclusively verify (within the tool budget available) that every ingestion path performs a prior structural validation rejecting such a malformed `CasmContractClass`, this should be validated further with a live/staging Devin session that can run the crate's test suite and attempt to feed a crafted `CasmContractClass` through `SyncStateReader::get_compiled_classes` and the gateway Declare path to confirm the panic is actually reachable end-to-end.

impl NestedFeltCounts {
    /// Builds a nested structure matching `layout`, consuming values from `bytecode`.
    #[allow(unused)]
    pub fn new(bytecode_segment_lengths: &NestedIntList, bytecode: &[BigUintAsHex]) -> Self {
        let (base_node, consumed_felts) = Self::new_inner(bytecode_segment_lengths, bytecode, 0);
        assert_eq!(consumed_felts, bytecode.len());
        base_node
    }

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }
}

fn bytecode_hash<H, NL>(bytecode: &[Felt], bytecode_segment_lengths: &NL) -> Felt
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    let mut bytecode_iter = bytecode.iter().copied();
    let (len, bytecode_hash) =
        bytecode_hash_node::<H, NL>(&mut bytecode_iter, bytecode_segment_lengths);
    assert_eq!(len, bytecode.len());
    bytecode_hash
}

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
