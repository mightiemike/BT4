Based on the investigation, I found a concrete analog in java-tron's public HTTP wallet/API layer.

### Title
Missing Input Validation on Public HTTP API Numeric Parameters Leaks Exception Details - (File: `framework/src/main/java/org/tron/core/services/http/`)

### Summary
Multiple unauthenticated HTTP API servlets in java-tron parse user-supplied GET parameters directly into `long` via `Long.parseLong()` without any format, range, or null validation before use. When parsing fails or values are malformed, the exception (including its full class name and message) is returned verbatim to the caller, and in several cases no bound is enforced on numeric ranges before they are handed to store-scanning wallet methods.

### Finding Description
Across the HTTP API surface, handlers such as `GetExchangeByIdServlet.doGet`, `GetProposalByIdServlet.doGet`, `GetPaginatedAssetIssueListServlet.doGet`, `GetPaginatedExchangeListServlet.doGet`, `GetPaginatedProposalListServlet.doGet`, `GetBlockByLatestNumServlet.doGet`, `GetTransactionCountByBlockNumServlet.doGet`, and the shielded-note scan servlets (`ScanNoteByIvkServlet`, `ScanNoteByOvkServlet`, `ScanAndMarkNoteByIvkServlet`, `ScanShieldedTRC20NotesByIvkServlet/OvkServlet`) all take a raw `request.getParameter(...)` string and pass it straight into `Long.parseLong(...)` with no prior validation of format, sign, or magnitude: [1](#0-0) [2](#0-1) [3](#0-2) 

Any thrown exception (`NumberFormatException`, `NullPointerException` if the parameter is absent, etc.) is caught generically and routed to `Util.processError`, which calls `Util.printErrorMsg`. That helper serializes the exception's fully-qualified class name and raw message directly into the JSON response body returned to the caller: [4](#0-3) [5](#0-4) 

This mirrors the reported bug class exactly: unvalidated `int()`/`float()` casts of request parameters (`oid`, `sz`, `px`) that raise unhandled exceptions and leak internals — here it is `Long.parseLong` on `id`, `num`, `offset`, `limit`, `startNum`/`endNum`, `start_block_index`/`end_block_index`, etc., with the resulting exception detail echoed back to an unauthenticated caller.

Some endpoints additionally lack range/consistency checks before the parsed value is used. For example `GetExchangeByIdServlet.doGet` and `GetProposalByIdServlet.doGet` pass an arbitrary attacker-chosen `long` id straight into `wallet.getExchangeById`/`wallet.getProposalById` with no bound, while `GetPaginatedAssetIssueListServlet`, `GetPaginatedExchangeListServlet`, and `GetPaginatedProposalListServlet` accept arbitrary `offset`/`limit` pairs and forward them unchecked to the corresponding `Wallet` pagination methods — I could not fully confirm from the indexed code whether `Wallet.getPaginatedProposalList`/`getAssetIssueList`/`getPaginatedExchangeList` themselves cap the requested limit, so the resource-consumption angle (large limit causing heavy store scans) is plausible but unverified.

### Impact Explanation
The confirmed, concrete impact is **information leakage**: any unauthenticated user hitting these public FullNode HTTP API endpoints with a malformed numeric parameter receives the internal Java exception class name and message in the response, which can reveal implementation details useful for further attack reconnaissance. This is a direct analog of the report's cited impact ("Information leakage via unhandled exceptions"). The unbounded numeric parsing is also a design-level input-validation gap consistent with OWASP A04/API4 cited in the report, though I was unable to confirm within the available index whether the unbounded `offset`/`limit` values actually translate into unbounded DB/CPU work inside `Wallet`'s pagination methods — that would need direct confirmation of `Wallet.java`'s implementation, which the index did not return in full.

### Likelihood Explanation
High: these are unauthenticated, publicly reachable HTTP GET endpoints on the FullNode HTTP API (no privileged role required), and triggering the leak requires nothing more than supplying a non-numeric or malformed string for parameters like `id`, `num`, `offset`, or `limit`.

### Recommendation
- Validate and sanitize all numeric HTTP parameters before parsing (regex/format check, explicit range bounds) instead of relying on `Long.parseLong` to fail loudly.
- Replace `Util.printErrorMsg`'s inclusion of `e.getClass()` and raw `e.getMessage()` with a generic, sanitized error message for client-facing responses; log full exception details server-side only.
- Enforce explicit upper/lower bounds on `offset`/`limit`/id-range parameters at the servlet layer, mirroring the existing `BLOCK_LIMIT_NUM` pattern already used in `GetBlockByLatestNumServlet`/`GetBlockByLimitNextServlet`, and apply it consistently to the pagination and scan servlets that currently lack it.
- Return proper HTTP 400 status codes for malformed input instead of HTTP 200 with an embedded error JSON.

### Proof of Concept
```
GET /wallet/getexchangebyid?id=notanumber HTTP/1.1
Host: <fullnode>:8090
```
Expected observation: response body contains `{"Error":"class java.lang.NumberFormatException : For input string: \"notanumber\""}` (via `Util.printErrorMsg` at `framework/src/main/java/org/tron/core/services/http/Util.java:117-121`, reached from `GetExchangeByIdServlet.doGet` at `framework/src/main/java/org/tron/core/services/http/GetExchangeByIdServlet.java:33-41`), confirming both the missing validation on the `id` parameter and the leakage of internal exception class/message to an unauthenticated caller. The same pattern can be repeated against `getproposalbyid?id=`, `getpaginatedassetissuelist?offset=&limit=`, `scannotebyivk?start_block_index=`, etc.
