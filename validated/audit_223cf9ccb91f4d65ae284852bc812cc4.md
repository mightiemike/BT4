This confirms the mechanism: `socialize-debt` in the vault contracts directly mutates `lindex` (and `principal-scaled`/`total-borrowed`/`assets`) via `var-set`, without going through `accrue-and-cache`, and without updating `market.clar`'s `index-cache` map [1](#0-0) . The market's cache is keyed only by `{ timestamp: stacks-block-time, aid: aid }` [2](#0-1) , so once populated for a given asset within a block, it is treated as authoritative for the rest of the transaction — the doc explicitly states "No manual invalidation needed" and "Eliminates stale data risks," which is precisely the assumption that breaks when a vault-mutating call (`socialize-debt`) occurs mid-transaction after the cache was already primed for that asset.

### Title
Stale `index-cache` in `v0-4-market.clar` after `liquidate-multi` socializes bad debt on a shared debt asset - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` folds/maps over a list of independent liquidation calls in a single transaction [3](#0-2) . Each individual `liquidate` call primes `index-cache` for the debt asset via `accrue-and-cache`, which caches the vault's `index`/`lindex` keyed only by `stacks-block-time` and `aid` [2](#0-1) . When a position has no remaining collateral, `liquidate` triggers bad-debt socialization via `socialize-debt-asset`/`vault-socialize-debt`, which calls the vault's `socialize-debt` function [4](#0-3) . That function directly `var-set`s `lindex`, `principal-scaled`, `total-borrowed`, and `assets` in the vault, bypassing the normal `accrue()` path entirely [1](#0-0) . Because `stacks-block-time` does not change within the same transaction, any subsequent liquidation in the same `liquidate-multi` batch that touches the same debt asset will hit the market's `index-cache` (cache HIT) and reuse the pre-socialization `index`/`lindex`, even though the vault's actual on-chain state has just moved.

### Finding Description
1. `liquidate-multi` maps `call-liquidate` over a list of borrower positions in one atomic transaction [3](#0-2) .
2. For borrower A (position 1) with the same debt asset `aid`, `liquidate` calls `accrue-user-debts`, which calls `accrue-and-cache aid`, populating `index-cache { timestamp: stacks-block-time, aid }` with the vault's current index/lindex [2](#0-1) .
3. If borrower A's position has no collateral left after seizure, the bad-debt path runs `fold socialize-debt-asset` over the remaining debt, which calls `vault-socialize-debt aid`, invoking the vault's `socialize-debt` public function [4](#0-3) .
4. `socialize-debt` mutates `lindex`, `principal-scaled`, `total-borrowed`, and `assets` directly with `var-set`, without calling `accrue()` and without any interaction with market.clar's cache [1](#0-0) . This is the "source" (vault state) moving.
5. For borrower B (position 2, same debt asset, same transaction/block), `liquidate` again calls `accrue-and-cache aid`. Since `stacks-block-time` is unchanged, the lookup key `{ timestamp: stacks-block-time, aid }` already exists in `index-cache` from step 2, so the function returns the cached (pre-socialization) index/lindex — a cache HIT — instead of re-reading the vault's now-updated `lindex` [2](#0-1) .
6. Borrower B's health/LTV, notional valuation, and liquidation-amount math (which consume `get-cached-indexes`) are computed against the stale liquidity index rather than the index that reflects the write-down `socialize-debt` just performed [5](#0-4) .

This is the direct structural analog of the veALCX bug: a value (`index-cache`) is bound/cached under an assumption ("nothing moves within the same timestamp"), an event occurs that invalidates that assumption (`socialize-debt`'s direct `var-set` write-down bypassing the cache), and a later read in the same evaluation context (`get-cached-indexes`/`accrue-and-cache`) is used without being told the source moved.

### Impact Explanation
Because zToken (`zsBTC`, `zSTX`, etc.) collateral valuation and debt valuation in `liquidate` depend on the cached `lindex`/`index` [6](#0-5) , a stale lindex following a same-block `socialize-debt` write-down can cause subsequent liquidations in the same `liquidate-multi` batch to under- or over-value collateral/debt for the affected asset. Depending on directionality this can result in a liquidator seizing more collateral than warranted by the post-write-down state (theft of value from the borrower / temporary mispricing of collateral) or under-collection of debt repayment relative to the seized collateral. This falls under "temporary freezing of funds" / value-manipulation impact class, since the mispriced liquidation settles at an incorrect exchange rate for at least one leg of the batch.

### Likelihood Explanation
This requires: (a) a `liquidate-multi` batch containing at least two positions sharing the same debt asset, (b) the first position's collateral being fully exhausted (triggering `socialize-debt`), and (c) both liquidations occurring in the same block. Any liquidator can construct such a batch deliberately (this is a single-transaction, single-actor exploit — not two independent users colliding), making it feasible to intentionally engineer bad-debt-then-liquidate ordering within one atomic call to profit from the stale cache on the second position.

### Recommendation
`accrue-and-cache`/`index-cache` should be invalidated (or bypassed) whenever a vault-mutating call that is not itself an `accrue()` (e.g., `socialize-debt`, `system-repay`, `system-borrow`) is executed within the same transaction for that `aid`. Concretely, either (1) have `socialize-debt` (and other state-mutating vault entrypoints) explicitly clear/refresh the corresponding `index-cache` entry in `market.clar` via a callback, or (2) remove the cache dependency from cross-position batch operations like `liquidate-multi` by forcing a fresh `vault-accrue`/state read for each position rather than trusting the per-timestamp cache once any bad-debt socialization has occurred in the same transaction.

### Proof of Concept
Conceptual sequence (Clarity, single transaction):
1. Attacker (liquidator) submits `liquidate-multi` with two entries: `{ borrower: A, debt-ft: X, ... }` and `{ borrower: B, debt-ft: X, ... }`, where A and B share debt asset `X` and A's collateral will be fully exhausted by its own liquidation.
2. Position A liquidation runs: `accrue-and-cache X` populates `index-cache {timestamp, aid: X}` with index `I0`/`lindex L0` [2](#0-1) .
3. A's collateral is fully seized; `no-collateral-left` is true, triggering `fold socialize-debt-asset` → vault `socialize-debt` for asset `X`, writing `lindex` down to `L1 < L0` directly via `var-set` [7](#0-6) .
4. Position B liquidation runs in the same transaction: `accrue-and-cache X` finds the existing `index-cache` entry for `{timestamp, aid: X}` (cache HIT) and returns stale `I0`/`L0` instead of the vault's now-current `L1` [2](#0-1) .
5. B's collateral/debt valuation and final liquidation amounts are computed using stale `L0`, producing an incorrect exchange rate for the second liquidation relative to the vault's actual, just-updated state.

Note: this analysis is based on static code review of `v0-4-market.clar` and the vault `socialize-debt`/`accrue` functions; I was not able to execute a Clarinet/forge-equivalent test in this environment to empirically confirm the exact numeric divergence, so the magnitude of the mispricing in a live scenario is not verified end-to-end.
