### Title
Paused `accrue` returns stale index without reverting, allowing debt/liquidity index to silently freeze while dependent operations proceed - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent vault contracts)

### Summary
Every Zest vault contract (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) implements `accrue` with a pause branch that, instead of reverting, returns the cached `index`/`lindex` values unchanged and skips updating `last-update`, `total-borrowed`-derived debt, and the treasury reserve mint.

### Finding Description
`accrue` reads `pause-states` and, when `accrue` is paused, takes the pass-through branch: [1](#0-0) 
returning `{ index: idx, lindex: lidx }` directly without recomputing `next-index`/`next-liquidity-index` or reverting the transaction. Every state-mutating entry point that touches debt or liquidity accounting — `system-borrow`, `system-repay`, deposit/redeem preview paths — calls `(try! (accrue))` first and then reads `(var-get index)`/`total-debt`/`total-assets-preview` as if it reflected up-to-date interest: [2](#0-1) 
Because the pause simply short-circuits the update instead of reverting, `last-update` is not advanced while paused (see the conditional `var-set last-update` guarded by index-change checks): [3](#0-2) 
When the pause is later lifted, `next-index`/`next-liquidity-index` compute `time-delta` as `(- stacks-block-time (var-get last-update))`, which now spans the entire paused interval plus any elapsed time before the pause: [4](#0-3) 
This means the accrual clock is only "advanced on change" (i.e., only updates `last-update` when index actually changes), and while paused, any operation that reads `total-debt`/`total-assets`/`total-supply` before unpausing uses the stale value bound before the pause was invalidated by the passage of time, while operations executed the moment after unpause absorb the entire skipped interest catch-up in a single index jump.

### Impact Explanation
An operation (deposit, borrow, repay) that occurs at the exact block the pause is lifted will trigger a `next-index` calculation covering the full accumulated `time-delta` since `last-update`, which could be an arbitrarily long paused window. Because the reserve-factor treasury mint (`treasury-lp`) is computed from the debt-delta between `old-debt` (last cached index) and `new-debt` (freshly computed index) at that single accrual call, a user interacting in the block right after unpause can be diluted or advantaged based on entirely undocumented, non-time-weighted jump math. Suppliers who were in the vault throughout the pause do not have their share of that catch-up interest protected from mint/redeem operations timed around the unpause event — this is a freezing/distortion of unclaimed yield rather than direct principal theft, landing in the "High - temporary freezing of funds / theft of unclaimed yield" impact class.

### Likelihood Explanation
This requires the `accrue` pause flag to be toggled (an admin/DAO-controlled action), which is a normal operational lever (e.g., for emergency response), not an attacker-triggered condition. The exploitability window depends on operational choices about when to pause and unpause, making it a low-to-moderate likelihood, config-dependent scenario rather than a directly attacker-triggered exploit.

### Recommendation
When `accrue` is paused, either (a) revert state-changing calls that depend on `index`/`lindex` freshness (`system-borrow`, `system-repay`, deposit, redeem) instead of silently passing through stale values, or (b) advance `last-update` to the pause time so that when unpaused, interest only accrues from the pause boundary forward rather than compounding the entire paused duration into a single jump discovered by whoever transacts first after unpause.

**Note on scope:** The original report's actual bug class — proportional yield distribution letting a late whale front-run an early depositor — is a two-user interference pattern explicitly excluded by the task rules ("Reject analogs whose mechanism is two different users interfering with each other"). I did not find that pattern replicated in the Zest vault code in a form that avoids this exclusion (the vaults use continuously-compounding shared indexes, not a periodic `distributeReward`-style batch split), so I substituted the closest genuinely in-scope analog: the pause-passthrough clock-freeze pattern explicitly listed as an allowed analog class.
