### Title
Unprivileged (view-only) authenticated users can read the full effective node configuration, including RPC node URLs/API keys embedded in EVM node configs - ([File: core/web/config_controller.go])

### Summary
The `/v2/config` and `/v2/config/v2` routes are registered with only session/token authentication and no role check, unlike nearly every other route in the router. Any authenticated user, including a low-privilege `UserRoleView` account, can call `ConfigController.Show` and receive the node's full effective TOML configuration, which can include EVM/Solana/etc. node RPC URLs that commonly embed provider API keys (e.g. Infura/Alchemy `https://.../v3/<API_KEY>`).

### Finding Description
In `core/web/router.go` the `authv2` group wraps most routes with a role gate such as `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole`: [1](#0-0) 

but the config route is registered bare:
```go
cc := ConfigController{app}
authv2.GET("/config", cc.Show)
authv2.GET("/config/v2", cc.Show)
``` [2](#0-1) 

The only gate applied to this group is generic authentication (`auth.AuthenticateByToken` / `auth.AuthenticateBySession`), which accepts any authenticated user regardless of role, including `UserRoleView`. [3](#0-2) 

`ConfigController.Show` then returns `cfg.ConfigTOML()`'s effective value (or user-input value if `userOnly=true`) with no field-level redaction: [4](#0-3) 

`ConfigTOML()` returns `g.inputTOML` / `g.effectiveTOML`, which are serializations of the `Config` struct (as distinct from the separately-redacted `Secrets`/`secretsTOML`): [5](#0-4) 

While `Secrets` (DB URL, keystore password, etc.) are intentionally kept out of this response, the `Config` struct includes chain node connection settings (e.g. EVM `Nodes[].WSURL` / `HTTPURL`) which in real deployments frequently embed provider API keys directly in the URL (Infura/Alchemy/QuickNode style URLs). These are not stored under `Secrets` in this codebase, so they pass through unredacted in the effective config TOML returned by this endpoint.

### Impact Explanation
A `UserRoleView` (read-only) authenticated user — someone who should only be able to view non-sensitive operational status — can retrieve the node's complete effective configuration and obtain RPC provider endpoint URLs with embedded API keys for every configured chain. This is an authorization-boundary/information-disclosure issue: the endpoint is missing the same role check applied to nearly every other admin/operational endpoint in the same route group, and it discloses credentials-bearing URLs to a role that should not have access to them. This maps to a secret-disclosure impact under the bounty program's classification (unauthorized secret disclosure from a low-privilege session).

### Likelihood Explanation
Fully reachable by any user who has been granted a `UserRoleView` (or higher) account on the node — no admin privileges, no special config, and no additional attacker capability required. Any organization that grants view-only dashboard access to less-trusted staff/monitoring accounts is exposed. The request is a simple authenticated `GET /v2/config` (or `/v2/config/v2`), trivially repeatable.

### Recommendation
Restrict `/v2/config` and `/v2/config/v2` to `auth.RequiresAdminRole` (or at minimum `auth.RequiresEditRole`), consistent with other sensitive routes in the same file, and/or redact known-sensitive fields (e.g. node URLs) from the TOML before returning it to non-admin roles.

### Proof of Concept
Integration test plan (extending existing `config_controller_test.go`/router auth tests):
1. Configure a node with an EVM chain whose `Nodes[0].WSURL`/`HTTPURL` contains a fake but distinctive "API key" query/path segment (e.g. `wss://example.com/v3/SECRET_TOKEN_1234`).
2. Create a session/API token for a user with `sessions.UserRoleView` (see `core/web/auth/auth.go` role definitions).
3. Issue `GET /v2/config` authenticated as that view-only user.
4. Assert the HTTP status is `200 OK` (not `401`/`403`), and that the returned JSON `config` field (TOML) contains the string `SECRET_TOKEN_1234`.
5. Compare against another admin-only endpoint (e.g. `/v2/keys/eth`) which correctly returns `403` for the same view-role user, to demonstrate the inconsistency in access control on `/v2/config`.

func (cc *ConfigController) Show(c *gin.Context) {
	cfg := cc.App.GetConfig()
	var userOnly bool
	if s, has := c.GetQuery("userOnly"); has {
		var err error
		userOnly, err = strconv.ParseBool(s)
		if err != nil {
			jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("invalid bool for userOnly: %w", err))
			return
		}
	}
	var toml string
	user, effective := cfg.ConfigTOML()
	if userOnly {
		toml = user
	} else {
		toml = effective
	}
	jsonAPIResponse(c, ConfigV2Resource{toml}, "config")
}
```
