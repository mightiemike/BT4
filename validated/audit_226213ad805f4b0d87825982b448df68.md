### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign` precompiled contract (legacy path) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract, reachable by any unprivileged account via a TVM contract call, extracts a signature array using a length value taken directly from attacker-controlled calldata **before any bound check is applied**, when the `allowTvmSelfdestructRestriction` VM feature flag is disabled. This mirrors the reported `fixDeserializedWrappedEVMAccount` bug class: an "array-like"/length field supplied by an untrusted caller is used to allocate memory (`new byte[len][]`) with no upper bound, and the energy metering for the call does not scale with that length.

### Finding Description
`ValidateMultiSign.execute()` computes the signature array using either a guarded path or an unguarded legacy path depending on a hard-fork flag: [1](#0-0) 

When `VMConfig.allowTvmSelfdestructRestriction()` is `true`, the code precomputes `sigArraySize` and rejects the call if it exceeds `MAX_SIZE` (5) before calling `extractSigArray`. However, when the flag is `false`, the code calls `extractBytesArray` with **no size check whatsoever**: [2](#0-1) 

Inside `extractBytesArray`, `len` is read straight from the attacker-supplied word array (`words[offset].intValueSafe()`), which can be any value up to `Integer.MAX_VALUE`, and is immediately used to allocate `new byte[len][]` — an array of up to ~2 billion object references — before any subsequent validation (`signatures.length > MAX_SIZE`) is applied: [3](#0-2) 

Crucially, the energy charged for this precompile call is computed only from the *actual* size of the calldata (`data.length`), not from the attacker-chosen `len` embedded inside a single 32-byte word: [4](#0-3) 

This is the same root-cause pattern as the Shardeum report: a length/size field taken from untrusted input is used to size a memory allocation without validating it against the cost actually charged for the operation, allowing a small calldata payload to trigger a disproportionately large allocation.

### Impact Explanation
If `allowTvmSelfdestructRestriction` is not yet activated on a given network (e.g., during a hard-fork rollout window, on a private/consortium chain, or a network that intentionally has not enabled this proposal), any account can submit a transaction invoking the `ValidateMultiSign` precompile with a crafted calldata word containing a huge integer at the `len` position. This causes the node executing/validating that transaction to attempt to allocate an outsized `byte[][]` array, which can trigger `OutOfMemoryError` or severe GC pressure on the executing node, stalling block production/validation — a localized denial-of-service against nodes processing that transaction. Because block execution (including precompile execution) is performed by every full/validator node that processes the block, this can propagate to a broader liveness impact if not caught, matching the "invalid-state/halt" impact category.

### Likelihood Explanation
Likelihood depends entirely on whether `allowTvmSelfdestructRestriction()` is already enabled by default on the live network at the current chain height, since the guarded branch (`extractSigArray`) explicitly does not have this flaw. I was not able to fully confirm within the available tool budget whether this proposal is already activated on mainnet by default (the flag is backed by `DynamicPropertiesStore`/`ProposalUtil`, suggesting it is a committee-activatable hard fork parameter rather than an always-on constant). If the proposal has already been activated network-wide, this specific code path is effectively dead on mainnet and the exploitability is low; if it has not yet been activated, or is disabled on a given private/test network, the vulnerability is directly and trivially reachable by any unprivileged sender.

### Recommendation
- Remove the unguarded legacy path or apply the same `MAX_SIZE` bound check inside `extractBytesArray` (and `extractBytes32Array`) unconditionally, regardless of `allowTvmSelfdestructRestriction`, so that `len` is always validated against a small upper bound (e.g., `MAX_SIZE`) before allocating `byte[len][]`.
- Ensure `getEnergyForData` charges energy proportional to the actual number of signatures processed (as derived from the length field), not merely the raw `data.length`, so any legitimately large value is economically deterred even if a bound check is bypassed elsewhere.
- Audit all other DataWord-array extraction helpers (`extractBytes32Array`, `extractSigArray`) for callers that don't pre-validate the derived length before allocation.

### Proof of Concept
Craft a contract call to the `ValidateMultiSign` precompile with calldata such that:
1. `words[3]` encodes an offset pointing to a chosen word index `offset`.
2. `words[offset]` contains a large value (e.g., `0x7FFFFFFF`).
3. On a network where `allowTvmSelfdestructRestriction()` is `false`, this reaches `extractBytesArray(words, offset, rawData)` at [5](#0-4)  and attempts `new byte[2147483647][]`, causing an immediate large memory allocation/`OutOfMemoryError` on the executing node while the attacker only pays energy proportional to the small calldata size actually sent.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
