The strongest local integrity gap I found is in the transaction-backup restore path: `write_sets` loaded from a backup manifest are never authenticated by the same proof used to authenticate transactions/events, yet they are later fed directly into state reconstruction during KV-only replay.

### Title
Unverified `write_sets` accepted during backup KV-replay corrupt reconstructed ledger state - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
`LoadedChunk::load` reads `txns`, `persisted_aux_info`, `txn_infos`, `event_vecs`, and `write_sets` from the same backup chunk file, but only wraps `txns`/`txn_infos`/`event_vecs` in a `TransactionListWithProofV2` and calls `.verify()` against the trusted `ledger_info`. `write_sets` is kept completely outside of the verified structure. [1](#0-0) 

`TransactionListWithProofV2::verify` (via the wrapped `TransactionListWithProof::verify`) only checks that transaction hashes match `txn_info.transaction_hash()`, that the accumulator proof authenticates the `txn_infos` against the `ledger_info`, and that event root hashes match — it never checks a write-set hash against `txn_info.state_change_hash()`. [2](#0-1) 

Compare this with `TransactionOutputListWithProofV2::verify`, which explicitly authenticates the write set for each transaction against `txn_info.state_change_hash()` before it is trusted: [3](#0-2) 

Because `LoadedChunk` uses the *transaction* proof type (not the *output* proof type), the loaded `write_sets` never go through this check.

### Finding Description
When `TransactionRestoreOpt::replay_from_version` is set with `kv_only_replay = true`, versions before the replay-from version are saved directly via `RestoreHandler::save_transactions_and_replay_kv`, which calls `restore_utils::save_transactions_impl` with `kv_replay = true`. In that branch, the (unauthenticated) `write_sets` are fed straight into `state_store.calculate_state_and_put_updates` to reconstruct the Jellyfish Merkle state — bypassing VM execution entirely and without any check that the write set matches `txn_info.state_change_hash()`: [4](#0-3) 

Since `verify_chunk`/`add_chunk` machinery, `TransactionInfoListWithProof::verify`, and `LoadedChunk::load`'s `txn_list_with_proof.verify(...)` call never touch `write_sets`, a corrupted or tampered backup archive (e.g., a compromised/misconfigured backup storage backend, or bit-rot/bug during backup file production) can supply a `write_set` whose hash does not match the corresponding `txn_info.state_change_hash()` recorded in the (validly proven) `TransactionInfo`, yet the loader still reports the chunk as verified. [5](#0-4) 

The mismatched write set is then committed into the restored node's state tree, producing a state root that diverges from the value that would result from actually executing the transaction / from the state implied by the authenticated `TransactionInfo.state_change_hash`.

### Impact Explanation
This breaks the "committed state must match the correct/authenticated result" invariant for a node performing a backup-based fast restore with KV-only replay: the resulting Jellyfish Merkle tree and state values are derived from data that was never bound to the accumulator-verified `TransactionInfo`. A node restored this way can end up with a state root/state values that disagree with the rest of the network at the affected version, and any state proofs it later serves for that version would be internally consistent (self-signed) but wrong relative to the honest chain — a durable, silent ledger-state corruption rather than a crash, which is why it rises to high severity.

### Likelihood Explanation
Likelihood is moderate: the KV-only replay/restore path is a deliberate, operator-invoked recovery workflow (`TransactionRestoreOpt::kv_only_replay`), and the trust model of backup storage is nominally "operator controlled," but the proof-verification code exists specifically to protect the restore process against backup corruption/tampering — the write-set field is simply omitted from that guarantee, which is exactly the class of gap the report seeks (data that should be constrained/validated but is treated as fully trusted).

### Recommendation
Before using `write_sets` for KV-only replay (or before any commit that skips VM execution), verify each write set's `CryptoHash::hash(&write_set)` equals the corresponding `txn_info.state_change_hash()`, mirroring the check already performed in `TransactionOutputListWithProofV2::verify`. This should be enforced in `LoadedChunk::load` (or immediately before `save_transactions_and_replay_kv`) so that unauthenticated write sets can never reach `calculate_state_and_put_updates`.

### Proof of Concept
1. Produce a backup transaction chunk file for a range of versions.
2. Tamper with the `write_set` bytes of one record while leaving `txn`, `txn_info`, and `events` untouched (so hash/proof checks against `txn_info.transaction_hash()`/events/accumulator still pass).
3. Run `aptos-debugger`/backup-cli restore with `--replay-transactions-from-version` and `--kv-only-replay=true` targeting a version range that includes the tampered record.
4. Observe `LoadedChunk::load` returns `Ok` (verification passes) and `restore_utils::save_transactions_impl` commits state derived from the tampered write set, producing a state root that would not match the actual network state at that version.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;
