### Title
Proposal approval can be hijacked to a different proposal due to sequential, execution-time proposal IDs - ([File: actuator/src/main/java/org/tron/core/actuator/ProposalCreateActuator.java])

### Summary
java-tron's on-chain governance (`ProposalCreateContract` / `ProposalApproveContract`) assigns proposal IDs sequentially at execution time rather than deriving them from the proposal's content. `ProposalApproveActuator` blindly trusts the numeric `proposal_id` supplied in the transaction and applies the approval to whatever `ProposalCapsule` currently occupies that slot in `ProposalStore`. This is the same bug class described in the external report: an approval meant for one proposal can be silently redirected to a different proposal if the slot's contents change between the time the approver signs/broadcasts their vote and the time it is actually included on-chain.

### Finding Description
`ProposalCreateActuator.execute()` computes the proposal ID purely from a global counter at the moment the creation transaction is executed, not from the proposal's content: [1](#0-0) 

Because the ID (`getLatestProposalNum() + 1`) is only resolved during block execution — and depends on how many `ProposalCreateContract` transactions have been processed before it — the final ID assigned to any given proposal is not deterministic at signing time; it depends on transaction ordering/inclusion, which a block-producing witness controls, and can also shift after a chain reorganization.

`ProposalApproveActuator.execute()` then approves a proposal purely by numeric ID, with no binding to the original proposal's content: [2](#0-1) 

and `validate()` only checks that the ID is within the known range and not expired/canceled — it never verifies the approver actually reviewed the specific parameters currently stored at that ID: [3](#0-2) 

The proto definitions confirm `ProposalApproveContract` references proposals purely by an `int64 proposal_id`, with no content hash or nonce tying the approval to specific proposal parameters: [4](#0-3) 

This exactly mirrors the reported bug class: a witness (analogous to the report's "council member") who signs/broadcasts a `ProposalApproveContract{proposal_id=N}` intending to approve a specific, already-observed proposal, can have that approval misapplied to a completely different proposal if slot `N` ends up holding different content — e.g., due to a chain reorg that drops the original `ProposalCreateContract` transaction, or due to a malicious block-producing witness reordering/substituting a competing `ProposalCreateContract` so that their own proposal claims ID `N` instead.

### Impact Explanation
A malicious witness could get an honest witness's approval vote misapplied to the attacker's own proposal (e.g., one that changes critical chain parameters governed by the proposal mechanism, such as energy/bandwidth pricing parameters, `ALLOW_*` feature switches, etc.). If enough approvals are hijacked this way, the attacker's proposal could reach the approval threshold required to take effect without the genuine consent of the witnesses whose votes were counted, corrupting on-chain governance and potentially causing consensus-relevant parameter changes that diverge from what the actual witness quorum intended.

### Likelihood Explanation
Exploitation requires either (a) a chain reorganization that drops the original proposal-creation transaction while a pending approval transaction referencing its expected ID survives, or (b) a witness with block-production influence deliberately manipulating transaction ordering so a competing proposal claims the ID that another witness's pre-signed approval is targeting. Both conditions require a witness (an elevated but not uncommon role — there are typically 27 active SRs) acting adversarially, and some timing/ordering luck. This is a plausible but not trivially "anyone, anytime" exploit, matching the moderate likelihood assessment of the original report (which explicitly notes large reorgs have been observed on other chains).

### Recommendation
Derive `proposal_id` deterministically from the proposal's content (e.g., a hash of `owner_address`, `parameters` map, and a nonce/creation transaction ID) instead of a purely sequential counter resolved at execution time, as recommended in the original report's mitigation. Alternatively, require `ProposalApproveContract` to carry a content hash/commitment of the proposal being approved, and have `ProposalApproveActuator.validate()` verify that hash against the currently stored `ProposalCapsule` before recording the approval, ensuring an approver's vote can never be silently redirected to a different proposal occupying the same numeric slot.

### Proof of Concept
1. Witness A broadcasts `ProposalCreateContract` (Tx1) intending to create benign proposal P with parameters `{X: v}`.
2. Witness B observes Tx1 get included with `proposal_id = N` (per `ProposalCreateActuator.execute()` logic) and broadcasts `ProposalApproveContract{proposal_id=N, is_add_approval=true}` (Tx2) to approve P.
3. Before Tx2 is confirmed, a malicious block-producing witness either triggers/benefits from a reorg that drops Tx1, or reorders transactions in a block it produces so that its own `ProposalCreateContract` (Tx3, containing malicious parameters) is processed in place of Tx1 and is assigned the same `proposal_id = N` (since `id = getLatestProposalNum() + 1` is resolved at execution time).
4. Tx2 (Witness B's approval for `proposal_id=N`) is subsequently included; `ProposalApproveActuator.execute()` fetches whatever `ProposalCapsule` is stored at key `N` — now the attacker's malicious proposal — and adds Witness B's approval to it.
5. Witness B's vote is now counted toward the attacker's proposal instead of the originally intended proposal P, without B's knowledge, potentially helping the malicious proposal reach the required approval threshold.
