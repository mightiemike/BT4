### Title
Unauthenticated, fee-free "bootstrap declare" bypasses account validation on live networks - ([File: crates/starknet_api/src/executable_transaction.rs])

### Summary
The `is_bootstrap_declare` special-case, mirrored in the blockifier's `execute_raw` and in the Starknet OS Cairo re-execution, skips nonce enforcement, `__validate_declare__` signature/account verification, and fee charging for any V3 Declare transaction whose `sender_address` equals the hardcoded constant `bootstrap_address()` ('BOOTSTRAP'), whose `nonce == 0`, and whose resource bounds are all zero. Nothing in the gateway, mempool, or execution path restricts this special case to genesis / a pristine chain — the default `authorized_declarer_accounts` config is `None` (unrestricted), so on a live, running network any unprivileged transaction sender can submit such a transaction repeatedly to declare arbitrary Sierra/CASM classes for free and without any signature check, entirely bypassing the framework's normal per-tx validation path.

### Finding Description
The declare-specific bootstrap check is defined once and consumed identically by both the blockifier and the Starknet OS: [1](#0-0) 

In `AccountTransaction::execute_raw`, when `is_bootstrap_declare` returns true, the transaction's normal `perform_pre_validation_stage` (nonce/fee checks) and `run_or_revert` (which invokes `__validate_declare__`) are skipped entirely — the class is declared directly and the function returns: [2](#0-1) 

The Starknet OS Cairo re-execution logic (`transaction_impls.cairo`) implements the identical special case — same condition (`sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, and zero max possible fee), same effect (skip `__validate_declare__`, skip nonce increment, skip fee charge, and directly `dict_update` the class hash): [3](#0-2) 

`charge_fee` becomes false (i.e. the bypass condition is met) whenever the transaction's resource bounds yield `max_possible_fee == 0`, which is entirely attacker-controlled: `enforce_fee()` returns `resource_bounds.max_possible_fee(tip) > Fee(0)`, so a transaction with `max_amount = 0` / `max_price_per_unit = 0` for all resources satisfies the bypass unconditionally: [4](#0-3) [5](#0-4) 

Crucially, `bootstrap_address()` is a fixed, publicly-known constant (the felt encoding of `'BOOTSTRAP'`), not a secret or genesis-only value: [6](#0-5) 

No code path checks that this special-case is only reachable at genesis / when no blocks have been produced. The `SyncStateReaderFactory` only falls back to a `GenesisStateReader`/`GenesisFixedBlockStateReader` (which return `Nonce::default()` = 0 and a default `BlockInfo`) when there are literally no blocks yet; once the chain is running, the "BOOTSTRAP" account's real on-chain nonce is read from state and — because that address is never used by legitimate accounts and never has its nonce incremented (see the comment "they are not removed from the mempool... do not increment its nonce" in the bootstrap test) — remains `0` forever, so the tx-nonce-0 condition is trivially satisfiable indefinitely: [7](#0-6) [8](#0-7) 

The only gate that could restrict this in the gateway is `check_declare_permissions`, which checks `block_declare` and `is_authorized_declarer`. By default, `authorized_declarer_accounts` is `None`, and `is_authorized_declarer` returns `true` for every address when the allow-list is unset — meaning by default the bootstrap address is not excluded and any declarer, including the BOOTSTRAP address, is permitted: [9](#0-8) [10](#0-9) 

The stateful validator's own nonce check (`validate_nonce`) does nothing to prevent this either — for a Declare, it only requires `incoming_tx_nonce == account_nonce`, which (since account_nonce for the never-deployed BOOTSTRAP address is always 0) is always satisfiable with `nonce: 0`: [11](#0-10) 

This is structurally analogous to the reported CVE's bug class: the system has two parallel enforcement paths (the normal per-account validate/fee/nonce pipeline vs. a special "bootstrap" fast path built directly into transaction execution), and the fast path bypasses the authentication/authorization/fee enforcement that the normal path enforces — reachable by an unprivileged external sender who simply crafts a transaction matching a few public, well-known field values.

### Impact Explanation
Any unprivileged transaction sender can submit an unsigned, unvalidated, zero-fee Declare transaction (sender = `'BOOTSTRAP'`, nonce = 0, zero resource bounds) at any point after genesis, and have it accepted into the mempool, executed by the sequencer, and re-verified successfully by the Starknet OS (both paths implement the identical bypass, so no divergence between blockifier and OS results). This:
- Completely bypasses account authentication (no `__validate_declare__`/signature check is performed).
- Completely bypasses fee enforcement (no balance debit occurs), causing the operator to perform Sierra→CASM compilation and class storage/state work for free, an unbounded resource-consumption/DoS vector for the gateway's compiler and mempool.
- Represents "unauthorized account action" in the sense defined by the validation rules: a transaction is accepted and its effect committed to state (class declaration) despite deliberately bypassing the very mechanism (validate + fee) that is supposed to gate all account-initiated state changes.

Because the identical logic is duplicated in the blockifier and the Starknet OS Cairo re-execution, this is exploitable on a live network without causing an OS/blockifier consensus divergence, which increases its practical severity (it will not be caught by the OS re-execution as an inconsistency — it simply "works" everywhere).

### Likelihood Explanation
High. The trigger condition requires only public knowledge (source code is open) of: the constant address `'BOOTSTRAP'`, nonce `0`, and zero resource bounds. No signature, no funded account, and no special authorization are required by default (`authorized_declarer_accounts: None`). Any external party capable of submitting an RPC declare transaction can exploit this repeatedly (once per unique class hash, since `dict_update` with `prev_value=0` prevents re-declaring the exact same class hash, but arbitrary new classes can always be crafted).

### Recommendation
Restrict the bootstrap-declare fast path so it can only be exercised during genuine chain bootstrap, e.g.:
- Gate the bypass on an explicit "chain not yet bootstrapped" flag/height (e.g., only allow when `block_number == 0` / no prior blocks exist), rather than relying solely on the sender address, nonce, and fee being attacker-controlled values.
- Alternatively/additionally, restrict the reserved `bootstrap_address()` via the existing `authorized_declarer_accounts` allow-list by default (deny it unless explicitly enabled for a one-time bootstrap), and have `check_declare_permissions` reject the bootstrap address once the chain is live.
- Ensure the OS-side check (`transaction_impls.cairo`) is updated consistently with any additional guard so blockifier and OS re-execution stay in agreement.

### Proof of Concept
1. Deploy/run a sequencer with default `GatewayStaticConfig` (`authorized_declarer_accounts: None`, `block_declare: false`) on a chain that has already produced blocks.
2. Craft a V3 Declare RPC transaction with:
   - `sender_address = starknet_api::executable_transaction::DeclareTransaction::bootstrap_address()` (felt of `'BOOTSTRAP'`)
   - `nonce = 0`
   - `resource_bounds` = all-zero (`l1_gas`, `l2_gas`, `l1_data_gas` each `max_amount = 0`, `max_price_per_unit = 0`) — mirroring `generate_bootstrap_declare()`'s test helper: [12](#0-11) 
   - An empty/arbitrary signature (no valid signature is required).
   - A never-before-declared class (`class_hash`/`compiled_class_hash`).
3. Submit via the gateway's `add_tx`. `check_declare_permissions` passes (no allow-list configured). Stateless validation passes (signature length checks don't require a *valid* signature). Stateful validation reads `account_nonce = 0` for the never-deployed bootstrap address, satisfying the nonce check.
4. During execution, `AccountTransaction::execute_raw` detects `is_bootstrap_declare(charge_fee=false) == true` and skips `perform_pre_validation_stage` and `run_or_revert` (i.e., skips `__validate_declare__`), declaring the class directly with zero cost: [13](#0-12) 
5. Repeat with new class hashes indefinitely to declare arbitrary classes for free without ever needing a valid signature or account balance.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }
