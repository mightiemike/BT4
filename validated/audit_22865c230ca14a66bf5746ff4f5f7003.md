## Analog Found

### Title
Permanent Denial-of-Service of the NEAR Wallet Contract via Stuck `has_in_flight_tx` Lock When the Fixed-Gas Callback Runs Out of Gas Before Resetting It - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (`WalletContract`, used to let Ethereum-style signed transactions control a NEAR account) serializes all of a wallet owner's transactions through a single in-flight-transaction lock, `has_in_flight_tx`. This flag is only reset back to `false` by the first statement of a chain of `#[private]` callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), each of which is invoked with a small, hardcoded gas budget. If any of those callback receipts runs out of gas before its Rust method body executes (which the runtime does when prepaid gas is insufficient to even load/start the contract), the reset statement never runs, and `has_in_flight_tx` stays `true` forever. Because `rlp_execute` rejects all further calls the moment this flag is `true` — without creating any promise or state change that could clear it — the wallet becomes permanently unusable by its owner. This mirrors the UF-2 report's class of bug (a mint pipeline made of several external calls, any one of which can fail and block the whole flow), but here the failure is **not resubmittable**: there is no path in the contract to clear the stuck flag once tripped.

### Finding Description
`WalletContract::rlp_execute` immediately short-circuits and returns an error value (no promise created) whenever `self.has_in_flight_tx` is `true`: [1](#0-0) 

The flag is set to `true` at the end of `rlp_execute`/`address_check_callback`/`nep_141_storage_balance_callback` when they hand off to a further cross-contract promise, and it is only ever reset to `false` as the *first statement* of each of the chained callback functions: [2](#0-1) [3](#0-2) [4](#0-3) 

Each of these callback receipts is scheduled with a small, fixed gas budget (`RLP_EXECUTE_CALLBACK_GAS = 5 TGas`, and the composite `ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` constants derived from it): [5](#0-4) 

The final `rlp_execute_callback` — which is the *only* callback that ultimately fires in the common (single cross-contract call) case — always receives exactly this fixed `RLP_EXECUTE_CALLBACK_GAS`, independent of the size of the compiled `WalletContract` WASM or of the protocol's current contract-loading fee.

The runtime charges a contract-loading fee (`contract_loading_base + contract_loading_bytes * code_len`) before the WASM method body is entered, and if the receipt's prepaid gas cannot cover this pre-execution cost, execution aborts with `GasExceeded`/"Exceeded the prepaid gas" *before* any of the contract's Rust code (including the `has_in_flight_tx = false` reset) ever runs: [6](#0-5) [7](#0-6) [8](#0-7) 

Because `has_in_flight_tx = true` was already committed to state by the *prior* receipt (the one that created the promise chain) — a separate, already-successful state transition — this commit is not rolled back when the later callback fails. The callback's own failure (an aborted `FunctionCallError`, not a panic that would roll back the enclosing receipt) simply produces a `Failure` outcome for that specific receipt while leaving `has_in_flight_tx` stuck at `true` in contract state, since the reset statement was never reached.

Once stuck, `rlp_execute` rejects every subsequent call at the very first `if self.has_in_flight_tx` check, without spawning any promise — there is no code path anywhere in the contract that can clear the flag again. The wallet is permanently frozen.

### Impact Explanation
This is a **transaction-triggered, permanent denial-of-service / frozen-funds** condition for the affected NEAR Wallet Contract instance: the account owner (and any relayer acting on their behalf) permanently loses the ability to execute any Ethereum-emulated transaction through this contract, because `rlp_execute` will forever return "transaction already in progress" without ever creating a promise that could reset the lock. Unlike the original UF-2 finding — where a failed `publicMint` transaction could simply be resubmitted — here a single stuck callback permanently bricks the wallet with no recovery path, since the only method capable of clearing `has_in_flight_tx` is the very callback that failed to run. This can occur through ordinary protocol evolution (e.g. contract-loading fee increases, contract binary growth over successive audits/upgrades of `WalletContract`, or gas-cost parameter changes across a protocol upgrade) narrowing the margin between the hardcoded `RLP_EXECUTE_CALLBACK_GAS` budget and the real loading+dispatch cost, without requiring any malicious relayer action.

### Likelihood Explanation
The gas margin is fixed at compile time (`RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)`) while the actual cost of loading and dispatching the compiled `WalletContract` WASM (which bundles RLP parsing, ETH ABI utilities, and borsh (de)serialization) is a function of the current protocol's gas-cost parameters and the contract's own compiled size — both of which can change over time (as documented for `contract_loading_base`/`contract_loading_bytes`, and separately for base FunctionCall/action fees across protocol versions). Because this is a hardcoded constant rather than a value computed against the live runtime config, the safety margin can erode with entirely benign protocol/config changes or contract growth, with no on-chain signal until an in-flight transaction actually gets stuck.

### Recommendation
Do not gate the wallet's liveness on a single hardcoded gas constant for the terminal callback. Options include: (1) making `has_in_flight_tx` self-healing via a timeout (e.g. storing a block height/timestamp when it was set, and allowing `rlp_execute` to proceed if a sufficiently long time has passed even while the flag is `true`), (2) computing the callback's attached gas defensively with a generous, periodically-reviewed safety margin above `contract_loading_base + contract_loading_bytes * current_code_len`, or (3) providing a privileged/owner-only recovery method to force-clear the flag after some minimum elapsed time, so a stuck lock can be observed and repaired rather than being permanently terminal.

### Proof of Concept
1. Deploy `WalletContract` and call `rlp_execute` with a valid Ethereum-emulated transaction that routes through the "default" `action_to_promise(...).then(ext.rlp_execute_callback(...))` path (the fixed 5 TGas callback branch), setting `has_in_flight_tx = true`.
2. Arrange for the receipt executing `rlp_execute_callback` to receive insufficient prepaid gas to complete contract loading and dispatch — e.g. via a protocol/config change that raises `contract_loading_base`/`contract_loading_bytes`, or by growing the compiled `WalletContract` binary so that `contract_loading_base + contract_loading_bytes * code_len` (plus base FunctionCall/action costs) exceeds `RLP_EXECUTE_CALLBACK_GAS` (5 TGas).
3. Observe that the `rlp_execute_callback` receipt fails with `FunctionCallError` (`GasExceeded`/"Exceeded the prepaid gas"), as reproduced generically by `test_gas_exceed_loading` in `runtime/near-vm-runner/src/tests/runtime_errors.rs:842-853`, meaning the Rust method body (and its `self.has_in_flight_tx = false;` first statement) never executes.
4. Call `rlp_execute` again with any valid transaction: it immediately returns `ExecuteResponse { success: false, error: Some("Error: transaction already in progress...") }` for all future calls, permanently, since `has_in_flight_tx` remains `true` and no code path can reset it.
