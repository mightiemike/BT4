## Finding [1](#0-0) [2](#0-1) 

### Title
Hardcoded, size-independent callback gas stipends in the NEAR Wallet Contract can be exhausted by attacker-controlled cross-contract response data, permanently freezing the wallet via a stuck `has_in_flight_tx` flag - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract hardcodes fixed gas stipends (`NEP_141_STORAGE_DEPOSIT_GAS`, `NEP_141_STORAGE_BALANCE_OF_GAS`, `REGISTRAR_LOOKUP_GAS`, `RLP_EXECUTE_CALLBACK_GAS`, each `5 Tgas`) for cross-contract calls and their callbacks, similar in spirit to Solidity's fixed 2300-gas `.send()`/`.transfer()` stipend that the referenced report flags as fragile. The wallet's callback functions (`nep_141_storage_balance_callback`, `address_check_callback`) deserialize a response value returned by an arbitrary, caller-chosen NEP-141/registrar target contract using only this fixed extra gas budget on top of the user-supplied `action.gas()`. If deserializing or processing that response consumes more gas than statically budgeted, the callback aborts mid-execution before it can commit `self.has_in_flight_tx = false`, and the entire receipt is rolled back per NEAR's atomic-failure semantics.

### Finding Description
The contract enforces a single-in-flight-transaction invariant guarded by `has_in_flight_tx`, explicitly documented as "must be `true` when a mutable method of this contract returns a promise and `false` otherwise." [2](#0-1) 

Every mutating entry point (`rlp_execute`) refuses to run if `has_in_flight_tx` is already `true`: [3](#0-2) 

For a NEP-141 (ERC-20 style) transfer, the flow calls `storage_balance_of` on the attacker/user-selected `target` token contract and chains a fixed-gas callback: [4](#0-3) 

`nep_141_storage_balance_callback` sets `has_in_flight_tx = false` as its very first statement, then deserializes the promise result and, on success, builds the next promise: [5](#0-4) 

The static gas attached to this callback is the small hardcoded constant chain `NEP_141_STORAGE_BALANCE_CALLBACK_GAS = 5+5+5 Tgas`, plus the user's `action.gas()`: [6](#0-5) 

Because `target`/`token_id` is a contract the transaction signer chooses (any NEP-141-shaped contract, honest or malicious), the size/shape of its `storage_balance_of` response is entirely under that contract's control. If the deserialization (`serde_json::from_slice`) plus subsequent logic in the callback exceeds the fixed gas stipend, the callback function fails with `GasExceeded` before its `self.has_in_flight_tx = false` write is committed. Per the runtime's atomicity guarantee — "a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting" — that write is discarded, leaving `has_in_flight_tx` permanently `true`. Every subsequent `rlp_execute` call on that wallet will then be rejected forever, exactly the "vault/owner can never call certain sensitive functions again" outcome flagged in the referenced report, just replacing Solidity's 2300-gas stipend with NEAR's hardcoded `Gas::from_tgas(5)` constants.

### Impact Explanation
A permanently frozen `has_in_flight_tx` flag makes the affected Wallet Contract instance unable to execute any further Ethereum-emulated transactions — the account's entire NEAR balance and any assets controlled through this contract become inaccessible via its intended interface. This matches the "permanently frozen funds" acceptance criterion. The condition is triggered purely by the transaction signer choosing to interact with a token/registrar contract whose response happens to (or is crafted to) exceed the fixed gas budget — no privileged access, validator, or network-level compromise is required.

### Likelihood Explanation
Likelihood is Medium: the fixed budgets (5–15 Tgas) are small relative to NEAR's per-call/per-receipt gas limits (up to 300 Tgas), so ordinary well-behaved NEP-141 tokens are unlikely to trip this. However, a user (or a relayer acting on the user's signed transaction) interacting with an adversarial or unusually complex token contract — or any future upgrade of a legitimate token contract that increases response payload complexity — can trigger the freeze deterministically, since the gas stipend is a static constant rather than scaled to the worst-case response size/complexity.

### Recommendation
Do not hardcode a fixed, worst-case-independent gas stipend for callbacks that process externally-controlled response data. Either (a) reserve `has_in_flight_tx = false` writes so they are committed independently of the rest of the callback logic (e.g., via a cheaper, unconditional "unlock" path with generous gas margin before doing any variable-cost processing of the promise result), or (b) bound/validate the size of `PromiseResult` payloads before deserializing them, or (c) attach a substantially larger, defensively-sized static gas budget to these callbacks so realistic malicious payloads cannot exhaust it, following the same pattern already used for `action.gas()` (i.e., scale the callback's gas with the expected worst-case cost of processing attacker-supplied data, not a flat constant).

### Proof of Concept
1. Deploy a NEP-141-shaped contract whose `storage_balance_of` method returns a JSON payload deliberately crafted to be maximally expensive to deserialize (e.g., deeply nested/large numeric fields) while staying under NEAR's max value-return size limit.
2. Sign an RLP-encoded "ERC20Transfer" Ethereum transaction from the Wallet Contract's owner key targeting this token contract, and submit it via `rlp_execute`.
3. Observe that `nep_141_storage_balance_callback` is invoked with only `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (15 Tgas) + `action.gas()`, and that gas exhaustion occurs during `serde_json::from_slice` before `self.has_in_flight_tx = false` is durably committed for that receipt.
4. Confirm the receipt fails and rolls back, and subsequent `rlp_execute` calls are permanently rejected with "transaction already in progress," as per the check in `rlp_execute`. [3](#0-2)
