### Title
Witness block/transaction-fee rewards become permanently unclaimable when a witness's per-cycle vote count is zero - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
This is a structural analog of the reported `updateGlobalExchangeRate`-with-zero-shares bug class: TRON's DPoS reward accounting increments an aggregate reward accumulator for a witness/cycle independent of whether that witness has any voter "shares" for the cycle, and the distribution logic silently drops (rather than safely handles) rewards whenever the vote-count denominator is zero, permanently orphaning funds.

### Finding Description
Every block, `MortgageService.payBlockReward`/`payTransactionFeeReward` call `payReward`, which unconditionally accumulates value into the reward store keyed by `(cycle, witnessAddress)`: [1](#0-0) 

This call does not check whether the witness has any recorded votes for that cycle. Per-cycle witness vote counts are snapshotted at each maintenance cycle in `MaintenanceManager.doMaintenance`: [2](#0-1) 

`witness.getVoteCount()` can legitimately be zero — a low-vote or unpopular witness can have all voters permissionlessly unvote / unfreeze via ordinary broadcast transactions (`VoteWitnessContract`, `WithdrawBalanceContract`, `UnfreezeBalanceV2Contract`) before the next maintenance recalculates the active set, while the witness continues producing blocks (and earning rewards) for the remainder of the current cycle.

Once a cycle's vote count for a witness is zero, the reward accumulated for that cycle is never converted into a claimable share. In the new reward algorithm, `DelegationStore.accumulateWitnessVi` explicitly skips folding the reward into the per-vote index when `voteCount == 0`, forwarding only the previous index value: [3](#0-2) 

The same guard exists in `RewardViCalService.accumulateWitnessVi`: [4](#0-3) 

In the legacy reward algorithm, `MortgageService.computeReward(cycle, votes)` similarly skips any SR whose recorded total vote for that cycle is zero, `continue`-ing past the reward entirely instead of distributing it: [5](#0-4) 

In all three cases the value already written by `addReward(cycle, witnessAddress, value)` is never read back by any withdrawal path when the corresponding vote count is zero for that cycle — it stays in the `delegation` store forever, unreachable by any account's `withdrawReward`/`queryReward` flow (`MortgageService.withdrawReward`/`queryReward`, `VoteRewardUtil.withdrawReward`/`queryReward`).

### Impact Explanation
Funds (TRX earmarked as block/transaction-fee rewards) become permanently locked/unclaimable whenever a witness produces blocks or collects transaction fees during a cycle where its recorded vote count is zero. This is a genuine value-leak/loss-of-funds condition analogous to the reported Covalent bug, though bounded to the reward portion attributable to zero-vote witnesses in a given cycle — comparable to the Medium severity rating given to the original finding ("Assets not at direct risk...but leak value with a hypothetical attack path... with external requirements").

### Likelihood Explanation
Reaching zero vote count for an active witness requires the coincidence of (a) a witness with very low overall vote weight and (b) all of its voters withdrawing/unfreezing votes in the same maintenance window before the witness is removed from the active set. This is achievable without any privileged role — purely through ordinary, permissionless voting/unfreeze transactions — but requires specific conditions (a low-vote SR and its voters coordinating to unvote), making it a real but situational griefing/self-inflicted-loss scenario rather than trivially exploitable at will against arbitrary victims.

### Recommendation
Do not silently drop rewards when the per-cycle vote-count denominator is zero. Options include: (1) redirecting undistributed rewards for zero-vote cycles to a recoverable pool (e.g., carry-forward to the witness's own withdrawable allowance, or to a protocol treasury) instead of leaving them keyed under an unreachable `(cycle, address)` slot, or (2) preventing `payReward`/`payBlockReward` from crediting a witness for a cycle in which it has zero recorded votes, redirecting that credit elsewhere. Any fix should ensure funds credited via `DelegationStore.addReward` are always eventually reachable through some claim path.

### Proof of Concept
1. Register a witness `W` with a very small number of votes (or 0 self-vote) such that it barely remains in the active/standby set for cycle `N` (vote count for cycle `N` is snapshotted via `MaintenanceManager.doMaintenance` → `delegationStore.setWitnessVote(N, W, voteCountAtMaintenance)`).
2. Have all voters of `W` broadcast unvote/unfreeze transactions (`VoteWitnessContract` with zero votes, or `UnfreezeBalanceV2Contract`) after the vote snapshot for cycle `N` is taken but before witness `W` is dropped from the active set at the next maintenance — driving `W`'s live vote count effectively to zero while it is still an active block producer for the remainder of cycle `N`.
3. Wait for `W` to produce one or more blocks / collect transaction fees during cycle `N`; each triggers `MortgageService.payBlockReward`/`payTransactionFeeReward` → `payReward`, which calls `delegationStore.addReward(N, W, value)`.
4. After maintenance rolls to the next cycle, inspect `accumulateWitnessVi(N, W, voteCount=0)` (or `RewardViCalService`) — the reward stored for `(N, W)` is never folded into `getWitnessVi`, and (for the legacy path) `MortgageService.computeReward` skips SR `W` for cycle `N` since `totalVote == 0`.
5. No account's `withdrawReward`/`queryReward` (`MortgageService`, `VoteRewardUtil`) will ever surface the value added in step 3 — it remains permanently stranded in the `delegation` store.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
