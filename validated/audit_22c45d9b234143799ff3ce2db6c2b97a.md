### Title
`CLEAN_INTERVAL`/`SHRINK_INTERVAL` in `AccountsBackgroundService` assume a fixed (legacy) slot time, causing accounts cleaning/shrinking to fall out of sync with cluster with reduced slot times - (File: `runtime/src/accounts_background_service.rs`)

### Summary
`AccountsBackgroundService`'s main loop paces `clean_accounts`/`flush_accounts_cache` and `shrink_candidate_slots` using wall-clock constants (`CLEAN_INTERVAL = 50s`, `SHRINK_INTERVAL = 1s`) that were explicitly derived assuming a 400ms slot time (the legacy default). The codebase now supports feature-gated slot-time reductions down to 200ms via `slot_params.rs`, but these ABS timers were never re-derived from the active slot time, so the intended cadence relationship to snapshot/slot production breaks down as slot time shrinks — directly analogous to the reported `Goldigovernor` bug where governance timing constants assumed the wrong (15s) block time instead of Berachain's actual 5s block time.

### Finding Description
In `runtime/src/accounts_background_service.rs`, the comment for `CLEAN_INTERVAL` states the intent explicitly: [1](#0-0) 

```
// Set the clean interval duration to be approximately how long before the next incremental
// snapshot request is received, plus some buffer.  The default incremental snapshot interval is
// 100 slots, which ends up being 40 seconds plus buffer.
const CLEAN_INTERVAL: Duration = Duration::from_secs(50);
const SHRINK_INTERVAL: Duration = Duration::from_secs(1);
```

The "40 seconds" figure is derived from `100 slots * 400ms/slot` — i.e., the legacy `ns_per_slot` baseline defined in `runtime/src/slot_params.rs` (`LEGACY_SLOT_PARAMS.ns_per_slot = 400_000_000`). This is the exact same class of bug as the report: a time-based limit hardcoded from an assumed block/slot duration.

However, `slot_params.rs` shows the codebase already supports reducing slot time via feature gates down to 200ms: [2](#0-1) 

Once any of the `reduce_slot_time_to_{350,300,250,200}ms` features activate, 100 slots complete in as little as 20 seconds instead of 40. The ABS loop, however, uses the same fixed `CLEAN_INTERVAL`/`SHRINK_INTERVAL` regardless of active slot time: [3](#0-2) 

This is the code path that gates `flush_accounts_cache`, `clean_accounts`, `shrink_ancient_slots`, and `shrink_candidate_slots` — i.e., the accounts cache flush/shrink/clean/purge subsystem targeted by this scan.

### Impact Explanation
Because `CLEAN_INTERVAL`/`SHRINK_INTERVAL` are not derived from the bank's actual `ns_per_slot` (which is dynamic per `SlotParams`/feature activation), a faster slot time causes:
- Incremental snapshot requests (tied to slot count, not wall time) to arrive more frequently than the clean cadence assumes, so `clean_accounts` runs relatively less often per snapshot/slot cycle than the comment's stated design intent.
- `dirty_stores` and `uncleaned_pubkeys` (see `shrink_all_slots`'s `DIRTY_STORES_CLEANING_THRESHOLD` logic at `accounts_db.rs:3216-3238`) to accumulate faster relative to how often they are drained, increasing storage footprint and the CPU cost of eventual, larger clean/shrink passes — a disproportionate storage and CPU cost condition.
- `shrink_candidate_slots`, gated by the same relative `should_shrink || should_clean` cadence, to likewise fall behind, worsening append-vec bloat.

### Likelihood Explanation
This triggers automatically and deterministically whenever a slot-time-reduction feature (`reduce_slot_time_to_350ms`/`300ms`/`250ms`/`200ms`) is activated cluster-wide — no attacker action is needed. It is a latent, always-reachable timing mismatch, not a theoretical corner case.

### Recommendation
Compute `CLEAN_INTERVAL` and `SHRINK_INTERVAL` (or the effective clean/shrink slot cadence) from the bank's current `ns_per_slot`/`SlotParams` rather than as fixed wall-clock constants, mirroring how `slot_params.rs` already derives other consensus-facing limits (cost limits, shred limits, etc.) per active slot-time regime.

### Proof of Concept
1. Activate `feature_set::reduce_slot_time_to_200ms` (or any of the 350/300/250ms gates) on a cluster.
2. Observe that `SlotParams::ns_per_slot` for new slots becomes 200ms per `SLOT_PARAMS_200MS` (`runtime/src/slot_params.rs:171-181`), so 100 slots elapse in ~20s instead of ~40s.
3. `AccountsBackgroundService`'s loop still only triggers `should_clean`/`should_shrink` based on the unchanged `CLEAN_INTERVAL = 50s` / `SHRINK_INTERVAL = 1s` constants (`runtime/src/accounts_background_service.rs:46-47`, `540-570`), so clean/shrink cadence relative to slot/snapshot production no longer matches the documented design ratio, letting `dirty_stores`/append-vec bloat grow faster than intended between cleans.
