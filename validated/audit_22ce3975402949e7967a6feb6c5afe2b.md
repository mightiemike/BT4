### Title
Griefing DoS via dust maker orders forcing legitimate MarketSellAssetContract trades to revert - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator` allows any unprivileged account to place small ("dust") maker orders in the on-chain order book at the best price for a token pair. When a later taker's `MarketSellAssetContract` transaction matches against that price level, the actuator counts how many maker orders it walks through and only checks the `MAX_MATCH_NUM` limit *after* performing the match and mutating order state, inside `execute()` rather than during `validate()`. An attacker can pre-populate the order book with more than `MAX_MATCH_NUM` (20) tiny orders at the best price so that any victim's matching transaction is forced to iterate through them and then throws, causing the whole transaction to fail. This mirrors the ExtraRewardsDistributor griefing pattern: cheap, dust-value, unprivileged transactions are used to force an otherwise-valid pending transaction into a revert path.

### Finding Description
In `matchOrder`, the inner loop walks the maker order list for the best price and increments `matchOrderCount` for every maker order consumed: [1](#0-0) 

The `MAX_MATCH_NUM` bound (20) is only enforced reactively — the check happens *after* `matchSingleOrder` has already executed and after the maker order may have been removed from the book: [2](#0-1) 

`matchSingleOrder` mutates account balances/assets and order state as it goes: [3](#0-2) 

Because order creation (`createAndSaveOrder`) is essentially free (bounded only by `MAX_ACTIVE_ORDER_NUM = 100` per account and the fixed `MarketSellFee`), an attacker can cheaply place 21+ dust orders at the best price for a pair before a victim's larger sell order arrives: [4](#0-3) 

When the victim's transaction reaches `matchOrder`, it is forced to walk through the attacker's dust orders one by one; once `matchOrderCount` exceeds `MAX_MATCH_NUM`, a `ContractValidateException("Too many matches...")` is thrown inside `execute()` — which is caught and converted into a failed `ContractExeException`, reverting the entire transaction and consuming the victim's fee: [5](#0-4) 

This is analogous to the reported `ExtraRewardsDistributor.addRewardToEpoch()` griefing: a small, cheap, permissionless write to shared/ordered state (here, the maker order book at a specific price) is used to make a legitimate transaction hit a hard-coded limit check and revert, wasting the fee already spent (or in Aura's case, blocking the intended state transition).

### Impact Explanation
This is a denial-of-service on the TRC10 exchange market feature reachable from any broadcast `MarketSellAssetContract` transaction. A griefer can:
1. Place ≥21 minimal orders at the best price for a targeted token pair (cheap, bounded only by the fixed market fee and `MAX_ACTIVE_ORDER_NUM`).
2. Force any subsequent taker transaction that would match at that price to revert with `code.FAILED`, burning the taker's `MarketSellFee` and CPU/energy while providing no trade execution.
3. Repeat indefinitely (recreating dust orders after cancellation) to persistently deny normal trading on a token pair, since order creation and cancellation are inexpensive compared to the wasted fee/energy of victims.

This does not cause direct fund loss beyond fees, but it is a real DoS/griefing of the on-chain exchange/order-matching protocol implementation, reachable by anonymous actors with no privileged role required.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to predict or race a specific price level for a token pair the victim intends to trade, and requires `ALLOW_MARKET_TRANSACTION` to be enabled (`dynamicStore.supportAllowMarketTransaction()`), which is already active per [6](#0-5) . Unlike the original Aura report, no mempool front-running timing is strictly necessary — the attacker can simply pre-seed the order book for a pair/price ahead of time since orders persist until matched/cancelled, making this arguably easier to exploit than the original bug.

### Recommendation
- Enforce the `MAX_MATCH_NUM` bound proactively before mutating any order/account state (e.g., check `orderIdListCapsule` size or a running match counter before calling `matchSingleOrder`, not after), so the limit rejects further matching without requiring a costly revert of already-applied side effects.
- Consider validating up-front (in `validate()`) whether the taker order would require exceeding `MAX_MATCH_NUM` distinct maker orders at the crossing price(s), or process partial fills up to the limit and leave the remainder resting in the book instead of throwing.
- Consider a minimum order size or increasing per-price-level order aggregation to make dust-order spam economically unattractive.

### Proof of Concept
1. Enable market transactions (`ALLOW_MARKET_TRANSACTION`) as done in existing tests, e.g. `MarketSellAssetActuatorTest` setup.
2. As attacker `A`, submit 21 `MarketSellAssetContract` transactions selling token X for token Y at the best price (minimal quantities, e.g. `sellTokenQuantity=1`), each creating a new resting maker order via `createAndSaveOrder`: [7](#0-6) 
3. As victim `B`, submit a `MarketSellAssetContract` transaction selling token Y for token X at a price that crosses A's resting orders, with a large enough quantity to require matching against more than `MAX_MATCH_NUM` (20) of A's dust orders.
4. Observe that `matchOrder` processes A's orders one-by-one, incrementing `matchOrderCount`, and once it exceeds 20 the actuator throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")` inside `execute()`, which is caught and converted to `ContractExeException`, causing `B`'s entire transaction to fail (`code.FAILED`) and consuming B's `MarketSellFee`, while A's dust orders remain (partially) available to repeat the griefing against future takers.

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,
      MarketSellAssetContract contract) {
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(contract.getOwnerAddress().toByteArray());
    if (marketAccountOrderCapsule == null) {
      marketAccountOrderCapsule = new MarketAccountOrderCapsule(contract.getOwnerAddress());
    }

    // note: here use total_count
    byte[] orderId = MarketUtils
        .calculateOrderId(contract.getOwnerAddress(), sellTokenID, buyTokenID,
            marketAccountOrderCapsule.getTotalCount());
    MarketOrderCapsule orderCapsule = new MarketOrderCapsule(orderId, contract);

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    orderCapsule.setCreateTime(now);

    marketAccountOrderCapsule.addOrders(orderCapsule.getID());
    marketAccountOrderCapsule.setCount(marketAccountOrderCapsule.getCount() + 1);
    marketAccountOrderCapsule.setTotalCount(marketAccountOrderCapsule.getTotalCount() + 1);
    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;
  }
