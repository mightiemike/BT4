### Title
Unbounded `ActiveBallotIDs` walk on every gasless ballot creation enables validator-vote-processing DoS - (File: x/uvalidator/keeper/ballot.go)

### Summary
`x/uvalidator`'s generic ballot machine creates a new ballot (and index entry in `ActiveBallotIDs`) the moment the first Universal Validator vote arrives for any distinct crosschain observation (a unique inbound tx hash+log index, outbound observation, or chain-meta report). `CreateBallot` unconditionally calls `ExpireBallotsBeforeHeight`, which performs a full linear walk of the entire `ActiveBallotIDs` keyset (fetching each `Ballot` from `Ballots`) before the new ballot can be stored. Because `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta` are gasless, and the number of distinct observations is driven directly by ordinary, unprivileged, cheap external-chain activity (each new deposit/tx hash triggers honest UVs to vote a brand-new observation), the size of `ActiveBallotIDs` — and therefore the fixed per-vote processing cost — is attacker-influenceable with no economic disincentive, mirroring the code-423n4 TwapOracle finding where an unbounded, non-prunable set had to be fully iterated on every update.

### Finding Description
`CreateBallot` in [1](#0-0)  is invoked lazily on the first vote for a new ballot ID (per `x/uvalidator/README.md`, "A ballot is created lazily on the first vote"). Before storing the new ballot, it calls `ExpireBallotsBeforeHeight(ctx, blockHeight)`.

`ExpireBallotsBeforeHeight` in [2](#0-1)  iterates the *entire* `ActiveBallotIDs` collection, doing a `Ballots.Get` for each entry, to find which ones have expired. This is O(n) in the total number of currently-active (not-yet-finalized, not-yet-expired) ballots, run synchronously inside the message-handling path of every `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta` that happens to be the *first* vote on a new observation.

These vote messages are gasless ( [3](#0-2) , [4](#0-3) ), so there is no gas cost that scales with, or discourages, this O(n) work, and the `DeductFeeDecorator`/`MinGasPriceDecorator` skip fee/gas-price checks entirely for these messages ( [5](#0-4) , [6](#0-5) ).

Ballot IDs are `sha256` hashes of the canonical observation (source chain, tx hash, log index for inbound; outbound ID/observation for outbound). An unprivileged external actor controls this input entirely: by broadcasting many cheap, distinct transactions on any registered external chain (each with a unique tx hash / log index), they force honest, unmodified Universal Validators to submit votes on many distinct new observations in a short window (before any of them can expire), growing `ActiveBallotIDs` without requiring any privileged behavior from validators or admins. As `ActiveBallotIDs` grows, every subsequent *new* ballot creation (i.e., every subsequent first-vote on a fresh observation, which happens continuously as normal cross-chain traffic occurs) pays the full linear cost of walking the whole set.

### Impact Explanation
This is a network-availability / block-processing-cost degradation, not a permanent lock like the original TwapOracle finding (ballots here do eventually self-prune via expiry, unlike TwapOracle pairs which had no removal path at all). However, because the walk happens synchronously and gasless inside consensus-critical vote message handling, sustained cheap external-chain spam can inflate the per-vote CPU/IO cost for every Universal Validator's node processing new observations, slowing consensus-critical vote finalization and increasing block-processing time network-wide — a DoS vector reachable purely through ordinary unprivileged user transaction submission on source chains, with no validator or admin misbehavior required.

### Likelihood Explanation
Moderate-to-low. It requires sustained volume of distinct external-chain transactions within the ballot expiry window to keep `ActiveBallotIDs` large; normal expiry naturally prunes entries once `expiryAfterBlocks` elapses. But because triggering vote messages are gasless and cost the attacker only ordinary (cheap) external-chain gas, and the number of concurrently-active ballots is entirely a function of external-chain transaction volume the attacker controls, sustained low-cost spamming is a realistic way to keep this set large.

### Recommendation
- Bound or rate-limit the number of concurrently active ballots per ballot type/observation source, or
- Replace the eager, full walk in `ExpireBallotsBeforeHeight` with a bounded/paginated sweep per invocation (expire at most N stale ballots per call) so a single `CreateBallot` call has an upper-bounded cost regardless of `ActiveBallotIDs` size, or
- Move ballot expiry sweeping out of the hot vote-processing path entirely (e.g., into `BeginBlocker`/`EndBlocker` with a bounded per-block budget) rather than running it synchronously on every new-ballot creation.

### Proof of Concept
1. An attacker (no special privileges, not a validator) broadcasts a large number of distinct low-value transactions on a registered external chain in a short period, each with a unique tx hash/log index (e.g., many small deposits to different or the same recipient).
2. Honest Universal Validators, following the normal protocol, submit `MsgVoteInbound` for each distinct observation via gasless transactions.
3. Each first vote on a new observation invokes `CreateBallot` → `ExpireBallotsBeforeHeight`, which walks the full `ActiveBallotIDs` set (see [7](#0-6) ).
4. As the attacker keeps submitting new distinct transactions faster than the ballot expiry window, `ActiveBallotIDs` accumulates, and the fixed per-vote cost of processing every subsequent new observation grows linearly, degrading vote-processing throughput/latency chain-wide at zero marginal Cosmos-tx cost to the attacker.

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}

	// Close iterator explicitly before mutation phase to release the IAVL snapshot
	iter.Close()

	if len(toExpire) > 0 {
		k.Logger().Debug("expiring stale ballots", "count", len(toExpire), "current_height", currentHeight)
	}

	// Phase 2: expire collected ballots (safe — iterator is closed)
	for _, id := range toExpire {
		if err := k.MarkBallotExpired(ctx, id); err != nil {
			return err
		}
	}

	return nil
}

func IsGaslessTx(tx sdk.Tx) bool {
	var (
		// GaslessMsgTypes defines the message types that are allowed in gasless transactions
		GaslessMsgTypes = []string{
			sdk.MsgTypeURL(&uexecutortypes.MsgMigrateUEA{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgExecutePayload{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteInbound{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteOutbound{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteTssKeyProcess{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteFundMigration{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteChainMeta{}),
		}
	)

	msgs := tx.GetMsgs()
	if len(msgs) == 0 {
		return false
	}

	for _, msg := range msgs {
		switch m := msg.(type) {
		case *authz.MsgExec:
			// Only gasless if ALL inner messages are allowed
			for _, innerMsg := range m.Msgs {
				if !slices.Contains(GaslessMsgTypes, innerMsg.TypeUrl) {
					return false
				}
			}
		default:
			if !slices.Contains(GaslessMsgTypes, sdk.MsgTypeURL(msg)) {
				return false
			}
		}
	}
	return true
}
