### Title
JWT replay-protection race in WorkflowMetadataHandler allows double-spend of a single trigger JWT - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` checks `jwtCache.isReplay(claims.ID)` and later calls `jwtCache.recordUsage(claims.ID)` as two separate, independently-locked operations rather than one atomic check-and-set. Two concurrent `Authorize` calls carrying the same JWT can both pass the `isReplay` check before either calls `recordUsage`, allowing the same JWT/`jti` to authorize a workflow trigger more than once.

### Finding Description
`Authorize` at [1](#0-0)  verifies the JWT signature, then calls `h.jwtCache.isReplay(claims.ID)` to reject already-used tokens, performs the authorized-key lookup, and only afterwards calls `h.jwtCache.recordUsage(claims.ID)` to mark the `jti` as used.

The cache implementation uses a `sync.RWMutex` but takes and releases the lock separately for each operation: [2](#0-1) 

`isReplay` takes an `RLock`, checks map membership, and releases; `recordUsage` takes a separate `Lock` later. There is no single critical section covering "check-not-present-then-insert." If two goroutines call `Authorize` concurrently with the same valid JWT (e.g., attacker replays the same HTTP trigger request twice in parallel), both can execute `isReplay` and observe `exists == false` before either executes `recordUsage`. Both then pass the authorized-key check and both return a valid `*gateway.AuthorizedKey`, i.e., the token is accepted twice.

Nothing else in the reachable path serializes concurrent `Authorize` invocations for the same `jti` — `h.mu` in `WorkflowMetadataHandler` only guards `authorizedKeys`/`workflowRefToID` maps for `syncMetadata`, not JWT replay state, and is taken via `RLock` in `GetWorkflowID`/`GetWorkflowReference`, unrelated to `Authorize`.

### Impact Explanation
This breaks the stated invariant that a signed trigger JWT must authorize exactly once. An attacker who possesses one valid trigger JWT can, by sending it as two (or N) concurrent requests, get more than one workflow-trigger execution authorized from a token intended for single use. This is a replay-protection bypass in the gateway's workflow trigger authorization path, potentially causing duplicate/unauthorized workflow executions — a workflow-execution integrity issue, though bounded by the number of concurrent requests the attacker can race within the token's validity/cleanup window.

### Likelihood Explanation
The precondition is minimal: the attacker just needs one valid signed trigger JWT (which is already required for legitimate single use) and the ability to fire it concurrently over HTTP to the gateway — no privileged access or key compromise needed. The race window between the `isReplay` read and the `recordUsage` write is small but real for any TOCTOU race, and is fully deterministic to reproduce in a unit test with goroutines synchronized via a barrier, making it a reliably exploitable condition.

### Recommendation
Make the check-and-set atomic under a single lock acquisition, e.g., add a method `checkAndRecord(jti string) bool` on `jwtReplayCache` that takes `cache.mu.Lock()` once, checks `cache.cache[jti]` existence, and if not present, inserts `time.Now()` and returns "not a replay", returning "is a replay" otherwise. Update `Authorize` to call this single atomic method in place of the separate `isReplay`/`recordUsage` calls.

### Proof of Concept
Add a concurrency test in `workflow_metadata_handler_test.go`:
1. Construct a `WorkflowMetadataHandler` with a valid workflow ID registered in `authorizedKeys`, and a valid signed JWT for an authorized signer with a fixed `jti`.
2. Launch N (e.g., 50) goroutines, each calling `h.Authorize(workflowID, token, req)` with the same token, synchronized to start simultaneously via a `sync.WaitGroup`/channel barrier.
3. Count how many calls return `nil` error (success).
4. Assert exactly 1 success and N-1 failures with "JWT token has already been used" error.
5. Run with `go test -race -run TestAuthorize_ConcurrentReplay -count=100` to reliably observe >1 success before the fix, and exactly 1 success after applying the atomic `checkAndRecord` fix.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
