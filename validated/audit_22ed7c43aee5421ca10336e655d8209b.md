### Title
Webhook and Fulfillment-Service authentication trust the unauthenticated `X-Shopify-Shop-Domain` header, allowing cross-tenant session hijacking - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`)

### Summary
Shopify's HMAC validation for webhooks and fulfillment-service requests only signs the raw request body. The `shop`/`X-Shopify-Shop-Domain` header used to select which merchant's offline session gets loaded is never included in the signed data, so it is not bound to the signature — directly analogous to the Astaria report where `StrategyDetailsParam.vault` was accepted unvalidated and used to select a different resource than the one that had actually been authorized.

### Finding Description
`validateHmacFromRequestFactory` computes the HMAC exclusively over `rawBody`: [1](#0-0) 

`checkWebhooksHeaders` then extracts `domain`, `topic`, `apiVersion`, and `webhookId` straight from HTTP headers, entirely outside of the HMAC-protected data: [2](#0-1) 

The webhook authenticate handler then trusts `check.domain` unconditionally, using it to look up (and vend an authenticated `admin` client bound to) the offline session for that shop: [3](#0-2) 

The same pattern exists for the Fulfillment Service handler, which reads the shop straight from the header: [4](#0-3) 

Because the app's webhook HMAC secret (`apiSecretKey`) is the same for every shop that installs the app, any single merchant who has legitimately received one webhook (or fulfillment-service request) from Shopify possesses a valid `(rawBody, hmac)` pair. That merchant can replay the exact body and HMAC to the app's public webhook/fulfillment-service endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. Validation only checks that the HMAC matches the body — it never checks that the domain header corresponds to the shop that actually produced that HMAC — so the forged request passes validation. The handler will then load the victim's offline session/access token and process the attacker's payload as if it originated from the victim shop, exactly as the `StrategyDetailsParam.vault` param in the Astaria report was accepted without checking it matched the vault that authorized the loan.

### Impact Explanation
An authenticated single merchant/customer of the app can force the app's business logic (webhook or fulfillment-service handlers) to run against a different, victim shop's offline session and access token, using attacker-controlled payload data. This is a cross-tenant access vulnerability: it can be used to trigger unwanted admin-API side effects (e.g., app logic that mutates resources, fulfills orders, or issues charges) in a victim's store, using data the attacker fully controls, while impersonating a delivery that Shopify never sent for that victim.

### Likelihood Explanation
The attacker only needs to be an ordinary merchant that has installed the app once (to receive one legitimate webhook/fulfillment-service delivery with a valid HMAC) and the ability to send arbitrary HTTP requests to the app's public, unauthenticated endpoint — both of which are trivially available to any customer of a multi-tenant Shopify app. No secrets need to be leaked and no MITM is required.

### Recommendation
Bind the shop identity to the signed payload rather than trusting the header in isolation: either include the domain/topic/webhook-id headers in the HMAC computation (as Shopify's public webhook signing recommendation suggests verifying the full envelope where possible), or cross-check the header-derived shop against a second authenticated signal (e.g. reject if a stored session's shop doesn't match request origin expectations, or use per-shop webhook secrets where available). At minimum, treat `check.domain`/`X-Shopify-Shop-Domain` as attacker-controllable input and add defense-in-depth checks before using it to select which shop's credentials to expose to handler logic.

### Proof of Concept
1. Install the target Vulnerable app on shop `attacker.myshopify.com`.
2. Trigger any webhook topic subscribed by the app (e.g. `products/create`) so Shopify sends a POST to the app's webhook endpoint with headers including a valid `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's shared `apiSecretKey`, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Capture the exact `rawBody` and `X-Shopify-Hmac-Sha256` value from that request.
4. Re-POST the identical body and HMAC header to the same webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com` (a shop that also has the app installed).
5. `validateHmacFromRequestFactory` verifies the HMAC against `rawBody` only and succeeds; `checkWebhooksHeaders` returns `domain: 'victim.myshopify.com'` unchecked; the webhook handler loads `victim.myshopify.com`'s offline session and executes the app's webhook business logic against the victim's store using the attacker's payload.

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
