## Finding: Meta-transaction (`DelegateAction`) signatures lack any chain/genesis binding, enabling cross-fork replay

### Title
Cross-fork replay of `DelegateAction` meta-transaction signatures due to missing chain/genesis binding in the NEP-461 signed payload - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
NEAR's meta-transaction scheme (NEP-366/NEP-461) has the user sign a `DelegateAction`/`DelegateActionV2` off-chain; a relayer later wraps that signed payload in an outer transaction and submits it on-chain. The bytes that are actually signed by the user (`SignableMessage`) contain only a small `MessageDiscriminant` plus the `DelegateAction` fields themselves (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`) — there is no genesis hash, chain ID, or any other chain-specific/fork-specific value in the signed payload, analogous to an EIP-2612 permit whose `DOMAIN_SEPARATOR` chain ID becomes stale after a hard fork.

### Finding Description
The signed hash for a delegate action is computed purely from the discriminant and the action struct itself: [1](#0-0) 

The `SignableMessage` wrapper that produces this hash carries no chain-binding field at all — just a NEP discriminant and the message: [2](#0-1) 

Contrast this with ordinary `SignedTransaction`s, which include a recent `block_hash` that must resolve to a block within the validity window of the specific chain the node is tracking — this hash is fork-specific and short-lived (as documented by the mirror tool, which must remap keys specifically because `block_hash` "will be rejected" across a forked chain): [3](#0-2) 

`DelegateAction` deliberately avoids this per-block binding and instead uses an absolute `max_block_height` as its only expiry mechanism, checked purely against the local chain's current height with no reference to a specific block hash, genesis hash, or chain identifier: [4](#0-3) [5](#0-4) 

Because `max_block_height` is a plain integer height rather than a hash tied to one specific chain, a fork that shares the pre-fork state (accounts, keys, nonces) and produces blocks at similar or higher heights than the original chain will happily accept the exact same signed bytes. Verification only checks the ed25519/ML-DSA signature over these bytes plus the access-key nonce/expiry on whichever chain state it is applied against: [6](#0-5) 

Nothing in nearcore's core transaction/action primitives has a chain ID concept comparable to EVM's `chainId` — a search of `core/primitives/src/transaction.rs` for `chain_id`/`genesis_hash` returns no results, confirming that the only replay-protection primitive that is chain-fork-aware is the ordinary transaction's recent `block_hash`, which `DelegateAction` intentionally does not use.

### Impact Explanation
If NEAR ever undergoes a state-preserving hard fork or state-forked network (which is a supported/expected operational scenario, evidenced by the existence of the `tools/mirror` fork-and-replay tooling and its explicit warning about `block_hash` rejection), any `SignedDelegateAction` a user produced for the original chain can be resubmitted by any relayer on the forked chain as long as:
1. The sender's access key/nonce on the fork has not yet advanced past `delegate_action.nonce`, and
2. The fork's current block height is still `<= max_block_height`.

Because the relayer pays gas and the action executes with `sender_id` as predecessor, this allows unauthorized execution of the delegated actions (transfers, function calls, key management, etc.) against the sender's account on the forked chain without the sender's fresh consent — i.e., unauthorized value movement analogous to the ERC20Permit replay scenario in the original report.

### Likelihood Explanation
This requires a specific precondition (a chain fork or forked/mirrored network sharing pre-fork account/key/nonce state) plus possession of a previously-issued `SignedDelegateAction` (e.g., one intercepted, leaked by a relayer, or simply reused by a relayer that stored it). It is not exploitable on a single, non-forked chain because nonce/expiry checks still apply there. Likelihood is therefore tied to fork/mirroring events, which are infrequent but explicitly supported operational scenarios in this codebase.

### Recommendation
- **Short term**: Bind the NEP-461 `SignableMessage`/`DelegateAction` payload to a chain-specific value (e.g., include the genesis hash or a `chain_id`-equivalent field) so that signatures produced for one chain cannot be replayed on a forked chain sharing the same account/key state, mirroring EIP-2612's chain ID inclusion in the domain separator.
- **Long term**: Document and mitigate cross-fork replay risk generally for all off-chain-signed, chain-agnostic payloads (not just `DelegateAction`), and ensure any future NEP-461-based signature schemes mandate a chain-binding field by construction.

### Proof of Concept
1. On chain A, Alice signs a `DelegateAction` (`get_nep461_hash`) authorizing a transfer, with `max_block_height = A_height + 100`, and hands the `SignedDelegateAction` to relayer R (or R simply retains a previously-used one).
2. Chain A is forked into chain B, which inherits Alice's account, access key, and nonce state as of the fork point (e.g., via a mirrored/forked deployment as supported by `tools/mirror`).
3. Before Alice's nonce is advanced on chain B and before chain B's height passes `max_block_height`, relayer R wraps the same `SignedDelegateAction` bytes in a new outer transaction addressed to chain B and submits it.
4. `apply_delegate_action` in `runtime/runtime/src/actions.rs` verifies the signature (valid, since nothing chain-specific was signed), checks `max_block_height` against chain B's local height (still valid), and checks/advances the nonce in `validate_delegate_action_key` — all checks pass, and Alice's delegated action executes on chain B without her consent for that chain. pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }
