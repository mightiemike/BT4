## Title
Attacker-controlled outbound gas parameters can permanently stall `PendingOutbounds`, blocking `InitiateFundMigration` and freezing old-key TSS funds - (File: `x/utss/keeper/msg_initiate_fund_migration.go`)

### Summary
`InitiateFundMigration` requires that `HasPendingOutboundsForChain` returns `false` before an old TSS key's funds can be swept to the current key. The `PendingOutbounds` index that backs this check is populated whenever a user-driven payload produces a `UniversalTxOutbound` event, and the outbound's gas parameters (`GasLimit`, `GasPrice`/fee) originate from attacker-supplied `UniversalPayload` execution, not from validator- or protocol-fixed values. If those parameters make the destination-chain broadcast permanently unbroadcastable (e.g. TSS sweep/broadcast fails indefinitely because the encoded gas price/limit can never be included, or the destination-chain tx never finalizes), the corresponding `PendingOutbounds` entry is never cleared by ordinary chain logic — the codebase's own tests document that ballot expiry does **not** remove the entry ("Pending outbounds should still exist ... the outbound persists for operator investigation", `test/integration/uexecutor/pending_outbound_audit_trail_test.go:232-236`) and that clearing stuck entries requires a dedicated software **upgrade handler** (`app/upgrades/purge-expired-outbounds/upgrade.go`), not routine on-chain logic reachable by anyone. This mirrors the GMX `PirexGmx.initiateMigration` bug class: an attacker plants an un-clearable precondition-blocking object (there: vester tokens; here: a stuck `PendingOutboundEntry`) that permanently prevents a migration guard from ever passing.

### Finding Description
`InitiateFundMigration` (`x/utss/keeper/msg_initiate_fund_migration.go:40-47`) enforces:
```go
hasPending, err := k.uexecutorKeeper.HasPendingOutboundsForChain(ctx, chain)
...
if hasPending {
    return 0, fmt.Errorf("chain %s still has pending outbounds; wait for them to drain before migration", chain)
}
```
`PendingOutbounds` entries are created in `attachOutboundsToUtx` (`x/uexecutor/keeper/create_outbound.go:339-407`) for every outbound built from a `UniversalTxOutbound` log emitted by `UniversalGatewayPC`, which is triggered by ordinary, unprivileged `MsgExecutePayload` calls. The outbound's `GasFee`, `GasLimit`, and `GasPrice` come directly from the decoded event (`event.GasFee`, `event.GasLimit`, `event.GasPrice` — `create_outbound.go:77-80`), which is derived from the payload the (attacker-controlled) UEA/CEA execution submits — not from a protocol-enforced floor.

Removal from `PendingOutbounds` only happens on quorum-reaching validator votes (`RecordOutboundVote` → finalize path) or via the dedicated chain-upgrade purge tool. Ballot expiry alone does **not** remove the entry, as explicitly verified by `TestMultiBallotExpiry_DoesNotRemovePendingOutbound` (`test/integration/uexecutor/pending_outbound_audit_trail_test.go:200-236`) — the audit-trail comment states the entry is kept "for operator investigation," i.e., by design it requires manual/governance intervention (the `purge-expired-outbounds` upgrade) rather than being self-healing.

If an outbound's TSS-broadcast can never succeed (e.g., attacker sets gas parameters that leave the sweep transaction perpetually unbroadcastable/unconfirmable on the destination chain, or crafts a payload/target combination that the destination chain will never execute), honest Universal Validators can neither vote it to a terminal success nor have the automatic pipeline clear it — the event simply stays in a non-terminal state (`SIGNED`/pending broadcast) indefinitely on the client side, while the on-chain `PendingOutbounds` entry for that chain never disappears.

### Impact Explanation
As long as one such stuck entry exists for a given destination chain, `k.PendingMigrations`-gated `InitiateFundMigration` can never be admin-initiated for that chain (`x/utss/keeper/msg_initiate_fund_migration.go:40-47`), which means the *old* TSS key's escrowed/locked funds on that external chain can never be swept to the new key after a `KEYGEN` rotation. Since `TssKeyHistory` funds under a rotated-away key have no other migration path in the scoped code, this is a **permanent freezing of protocol-controlled funds** reachable purely from an ordinary user's `MsgExecutePayload`/outbound-creating transaction — no privileged actor, malicious validator, or malicious relayer is required to plant the blocking entry.

### Likelihood Explanation
Medium. Triggering it requires an unprivileged user to submit a payload whose resulting outbound event carries gas parameters or targeting that guarantee non-finalization on the destination chain — a condition fully within an attacker's control at submission time (the event's `GasFee`/`GasLimit`/`GasPrice` are read straight from the emitted log the attacker's transaction produced). The remaining variable is whether honest TSS/UV logic has any independent, non-privileged path to abandon and clean up such a stuck pending outbound; based on the reviewed code paths (client-side retry loop with no unconditional give-up on EVM, and the explicit "entry persists" test/audit-trail semantics on-chain), no such automatic cleanup was found. This assessment is based on the code paths inspected; I was not able to fully trace the EVM-side `txresolver`/deadline-expiry logic (`universalClient/tss/txresolver/evm.go`) within the available iterations, so it is possible there is an additional automatic REVERT/terminal path for stuck EVM outbounds that would mitigate this — this should be verified before treating the finding as confirmed exploitable end-to-end.

### Recommendation
- Add a chain-native (non-upgrade-handler) escape hatch that lets `PendingOutbounds` entries reach a terminal state (e.g., forced REVERT/ABORT) once `SigningDeadline` has passed, independent of validator votes, so a single stuck outbound cannot indefinitely block per-chain invariants like `HasPendingOutboundsForChain`.
- Do not let `InitiateFundMigration`'s pending-outbound guard be blockable by a single unresolved entry indefinitely; consider allowing admin-forced skip/abort of expired outbounds (with appropriate on-chain event/audit trail) rather than requiring a full software upgrade to purge them.
- Validate/clamp attacker-supplied `GasLimit`/`GasPrice`/`GasFee` for outbound-producing payloads against protocol-known minimums so a user cannot construct an outbound that the TSS pipeline can never successfully broadcast or resolve.

### Proof of Concept
1. Attacker submits `MsgExecutePayload` whose payload triggers a call into `UniversalGatewayPC` producing a `UniversalTxOutbound` event to a target chain `X`, with `GasFee`/`GasLimit`/`GasPrice` values chosen so the resulting sweep/broadcast transaction can never be included/finalized on chain `X` (e.g., price too low relative to `X`'s prevailing fee market, or a payload target guaranteed to revert without freeing the nonce).
2. `BuildOutboundsFromReceipt`/`attachOutboundsToUtx` creates a `PendingOutboundEntry` for chain `X` (`x/uexecutor/keeper/create_outbound.go:339-407`).
3. Honest Universal Validators attempt TSS signing/broadcast; the destination tx never finalizes, so no `MsgVoteOutbound` quorum is ever reached; per `TestMultiBallotExpiry_DoesNotRemovePendingOutbound`, even ballot expiry leaves the `PendingOutbounds` entry intact.
4. Admin later needs to rotate the TSS key (`KEYGEN`) and calls `MsgInitiateFundMigration` for chain `X`; `k.uexecutorKeeper.HasPendingOutboundsForChain(ctx, "X")` returns `true` because of the attacker's stuck entry, and `InitiateFundMigration` permanently rejects with `"chain %s still has pending outbounds"` (`x/utss/keeper/msg_initiate_fund_migration.go:45-47`), freezing the old key's funds on chain `X` indefinitely absent a manual chain-software upgrade. func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}

// deleteExpiredOutboundBallots iterates all pending outbounds, finds their expired
// ballots, and deletes them. This allows validators to re-vote on the outbounds,
// creating fresh ballots with the current validator set and large expiry.
func deleteExpiredOutboundBallots(ctx sdk.Context, ak *upgrades.AppKeepers) (deleted, skipped, errCount int) {
	logger := ctx.Logger()

	if ak == nil || ak.UExecutorKeeper == nil || ak.UValidatorKeeper == nil {
		logger.Error("purge-expired-outbounds: keeper is nil, skipping")
		return 0, 0, 1
	}

	ek := ak.UExecutorKeeper
	vk := ak.UValidatorKeeper

	// Phase 1: collect all pending outbound entries (avoid mutating during iteration)
	type pendingItem struct {
		outboundId    string
		universalTxId string
	}
	var items []pendingItem

	err := ek.PendingOutbounds.Walk(ctx, nil, func(key string, entry types.PendingOutboundEntry) (bool, error) {
		items = append(items, pendingItem{
			outboundId:    entry.OutboundId,
			universalTxId: entry.UniversalTxId,
		})
		return false, nil
	})
	if err != nil {
		logger.Error("purge-expired-outbounds: failed to walk pending outbounds", "error", err)
		return 0, 0, 1
	}

	logger.Info("purge-expired-outbounds: found pending outbounds", "count", len(items))
