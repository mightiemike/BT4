### Title
Unbounded growth of L1 handler transaction records for Rejected transactions leads to host memory exhaustion - (File: crates/apollo_l1_events/src/transaction_manager.rs)

### Summary
`TransactionManager` keeps every L1→L2 message it has ever scraped in the `records: Records` map (an `IndexMap<TransactionHash, TransactionRecord>`) until it is explicitly removed. Only two removal paths exist: `finalize_cancellation` [1](#0-0)  and the lazy consumed-queue sweep in `clear_old_tx_from_consumed_queue` [2](#0-1) . There is no removal path for transactions that reach the `Rejected` state via `mark_rejected` [3](#0-2) , and no state transition ever moves a record out of `Rejected` back to a state that would later be consumed or cancelled [4](#0-3) . This mirrors the Xen CVE-2018-5244 pattern: a per-entity tracking structure is allocated on creation but has no corresponding free operation on one of its terminal lifecycle paths.

### Finding Description
`commit_txs` is called at block-commit time with the list of transaction hashes that were rejected during proposal/validation, and unconditionally calls `mark_rejected` on their records: [5](#0-4) 

`mark_rejected` sets `state = TransactionState::Rejected` and `rejected = true`, with no accompanying eviction from `self.records`: [3](#0-2) 

`maintain_indices` (called from `with_record` after every mutation) only manages the `proposable_index` and `consumed_queue`; since `is_proposable()` is `false` for `Rejected`, the entry is dropped from `proposable_index`, but the underlying `TransactionRecord` in `records` is never removed: [6](#0-5) 

Compare this with the two states that do get cleaned: `CancellationFinalizedOnL1` triggers `self.records.remove(&tx_hash)` in `finalize_cancellation` [7](#0-6) , and `Consumed` records are pushed into `consumed_queue` and later swept by `clear_old_tx_from_consumed_queue` once the configured timelock elapses [8](#0-7) . No equivalent queue or sweep exists for `Rejected`. `TransactionState::Rejected` is a dead end in the state machine: nothing in `transaction_record.rs` transitions a record out of `Rejected`, so once marked, the record is permanently retained in memory.

An L1 message sender is an unprivileged actor (anyone can invoke the StarknetCore contract's L1→L2 messaging entry point on L1). By repeatedly sending L1→L2 messages that are designed to fail execution during proposal (e.g., invalid selector, contract that reverts, insufficient resource bounds), the attacker can force `commit_txs` to mark an ever-growing number of transaction hashes as `Rejected`, each permanently retaining a `TransactionRecord` (which, for a scraped message, holds the full `L1HandlerTransaction` payload — calldata, addresses, nonce, etc., not just the hash) in the sequencer's `records` map.

### Impact Explanation
Every rejected L1 handler transaction permanently consumes host memory proportional to the payload size of the original L1 message, and this list has no cap or eviction visible in `TransactionManagerConfig`/`transaction_manager.rs`. Sustained abuse leads to unbounded host OS memory growth on every node running the L1 events/message provider component, eventually causing OOM crashes of the sequencer process — a network unable to confirm new transactions once enough nodes are affected. This matches the impact class of the reference CVE (host memory exhaustion via un-freed per-entity tracking structure).

### Likelihood Explanation
Triggering this requires only the ability to send L1→L2 messages that fail during L2 execution, which is achievable by any L1 account willing to pay L1 gas per message, and does not require compromising the sequencer, controlling the mempool, or being a validator/proposer. The bug is deterministic (100% of designed-to-fail messages become `Rejected` records and are never reclaimed), so likelihood is high modulo the cost of sending many small L1 messages — which is an economic (not protocol) barrier, and this crate-owning `records` structure has no size cap to fall back on.

### Recommendation
Add a cleanup/eviction path for `Rejected` records analogous to the `consumed_queue`/timelock mechanism already used for `Consumed` transactions: e.g., track rejection timestamps in a queue and lazily (or via a periodic sweep) remove `Rejected` records past a retention timelock in `clear_old_tx_from_consumed_queue`-style logic, or fold rejected records into the existing `consumed_queue` eviction pass. Additionally, enforce a hard cap on `records.len()` (or reject/evict oldest terminal-state records) as defense in depth.

### Proof of Concept
1. An attacker calls the L1 `StarknetCore` messaging entrypoint (`sendMessageToL2`/equivalent) many times, each with a payload crafted to fail during L2 execution (e.g., calling a nonexistent entry point / an entry point that reverts, or unreachable calldata).
2. The `apollo_l1_events` scraper picks up each message and calls `TransactionManager::add_tx`, creating a `TransactionRecord` per message [9](#0-8) .
3. During block proposal/validation, each of these transactions fails execution and is included in `rejected_txs` passed into `commit_txs`, which calls `mark_rejected` on each [5](#0-4) .
4. Repeating steps 1–3 indefinitely causes `self.records` to grow without bound, since no code path ever calls `self.records.remove(&tx_hash)` for `Rejected` transactions, unlike `Consumed` (`clear_old_tx_from_consumed_queue`) and `CancellationFinalizedOnL1` (`finalize_cancellation`).

**Uncertainty note**: I could not find, within the indexed portion of the codebase, any external capacity limit configured for `TransactionManagerConfig`/`records` that would bound this growth (only `l1_handler_proposal_cooldown_seconds`, `l1_handler_cancellation_timelock_seconds`, and `l1_handler_consumption_timelock_seconds` fields were located via search). If such a cap exists elsewhere and is not indexed, it would mitigate this finding; I recommend verifying `apollo_l1_events_config/src/config.rs` in full via a Devin session with complete file access to confirm no size-bound field was missed.

    pub fn add_tx(
        &mut self,
        tx: L1HandlerTransaction,
        block_timestamp: BlockTimestamp,
        scrape_timestamp: UnixTimestamp,
    ) {
        let tx_hash = tx.tx_hash;
        // If exists, return false and do nothing. If not, create the record as a HashOnly payload.
        let is_new_record = self.create_record_if_not_exist(tx_hash);
        // Replace a HashOnly payload with a Full payload. Do not update a Full payload.
        // A hash only payload can come from catching up from state sync, and then updated by
        // add_events from the scraper. However, if we get the same full tx twice (from the scraper)
        // it could indicate a double-scrape, and may cause the tx to be re-added to the proposable
        // index.
        self.with_record(tx_hash, move |record| match &record.tx {
            TransactionPayload::HashOnly(_) => {
                if !is_new_record {
                    info!(
                        "Transaction {tx_hash} already exists as a HashOnly payload. It was \
                         probably gotten via state sync component, and is now updated with a Full \
                         payload."
                    );
                }
                record.tx.set(tx, block_timestamp, scrape_timestamp);
                // Counts the HashOnly -> Full transition, regardless of whether the HashOnly
                // was just created here or pre-existed from state sync.
                L1_MESSAGE_SCRAPER_L1_HANDLER_TX_COUNT.increment(1);
            }
            TransactionPayload::Full { tx: _, created_at_block_timestamp: _, scrape_timestamp } => {
                warn!(
                    "Transaction {tx_hash} already exists as a Full payload, scraped at \
                     {scrape_timestamp}. This could indicate a double scrape. Ignoring the new \
                     transaction."
                );
            }
        });
    }

    pub fn finalize_cancellation(&mut self, tx_hash: TransactionHash) {
        let Some(record) = self.records.get(&tx_hash) else {
            info!(
                "Attempted to finalize cancellation for non-existent transaction: {tx_hash}. This \
                 can happen if the transaction was too old to be scraped (e.g. it was created \
                 before we started scraping)."
            );
            return;
        };

        // Regardless of the state of the tx in the record, if we get the cancellation event from
        // the L1 contract, we delete this tx from the records and from the proposable index, even
        // if it was Pending and ready to be proposed (which is not supposed to happen, hence the
        // warning).
        if record.state != TransactionState::CancellationStartedOnL2 {
            warn!(
                "Attempted to finalize cancellation for transaction {tx_hash} that is not in the \
                 cancellation started on L2 state, but in the {:?} state.",
                record.state
            );
        }
        // This will also call maintain_indices to remove the tx from the proposable index.
        self.with_record(tx_hash, |r| r.mark_cancellation_finalized_on_l1());
        self.records.remove(&tx_hash);
    }

    fn maintain_indices(&mut self, hash: TransactionHash) {
        if let Some(record) = self.records.get(&hash) {
            let TransactionPayload::Full { scrape_timestamp, .. } = record.tx else {
                // We haven't scraped this tx yet, so it isn't indexed.
                return;
            };

            let tx_hash = hash;

            if record.is_proposable() {
                // Assumption: txs will only be added to the index once, on arrival, so this
                // preserves arrival order.
                let tx_hashes = self.proposable_index.entry(scrape_timestamp).or_default();
                if !tx_hashes.contains(&tx_hash) {
                    tx_hashes.push(tx_hash);
                }

                // This tx needs to be removed from the proposable index if it was on it.
                // Remove from the vec for this timestamp, and drop the entry if it becomes empty.

                            tx_hashes.remove(index_in_vec);
                            if tx_hashes.is_empty() {
                                entry.remove();
                            }
                        }
                    }

                }
