## Analog Found: Duplicate signature-weight counting in `ValidateMultiSign` precompile

### Title
Single-signer weight is double-counted via ECDSA signature malleability in `ValidateMultiSign` precompiled contract - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The external report's bug class is "a signature can be reused to repeat a privileged effect (claiming a reward) more times than intended, because the check for prior use is not robust." The reachable analog in java-tron is the `ValidateMultiSign` precompiled contract, callable by any smart contract (and therefore by any anonymous broadcast transaction that triggers such a contract). Its de-duplication logic checks whether the *exact byte encoding* of a signature has been seen before, rather than whether the *signing key* has already contributed its weight. Because ECDSA signatures are malleable, a single private key can produce two byte-distinct, both-valid signatures over the same hash, letting the same key's weight be added to `totalWeight` twice (or more).

### Finding Description
`ValidateMultiSign.execute()` builds a hash from `(address, permissionId, data)` and iterates supplied signatures: [1](#0-0) 

For each signature it recovers the signer address, then checks for prior use:
```
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
``` [2](#0-1) 

The "already used" check is keyed on the exact bytes of `sign` merged with `recoveredAddr`, not solely on `recoveredAddr`. If `recoveredAddr` is already present but the byte-identical `sign` is not (i.e., a *different* valid signature that recovers to the same address), the loop does **not** `continue` — it falls through and adds `weight` to `totalWeight` again. ECDSA signatures are malleable: for any valid `(r, s, v)` there exists a second valid `(r, n-s, v')` that recovers to the same address (`recoverAddrBySign` at [3](#0-2)  uses `Rsv.fromSignature`/`SignUtils.fromComponents` and only calls `signature.validateComponents()` before recovery). Unless that component check enforces the canonical low-`s` form (not confirmed from the code paths inspected), an attacker holding one key can submit two syntactically different signatures over the identical hash and have the precompile count that single key's weight twice, three times, etc. (bounded only by `MAX_SIZE = 5`).

This mirrors the report's root cause exactly: the code de-duplicates on the wrong granularity (exact blob) instead of the semantically relevant identity (the recovered signer), letting one signature-worth of authorization be "reused" to accumulate more privilege than it should.

### Impact Explanation
`ValidateMultiSign` is used by smart contracts to implement on-chain M-of-N authorization gates (e.g., custody/multisig wallets, DAOs, treasury releases) built on top of TRON account permissions. A contract that trusts this precompile's boolean result to gate a privileged action (fund transfer, permission change, reward release) can be tricked into believing a threshold of *distinct* co-signers was met when in fact only one signer supplied malleable variants of their own signature. This is a genuine authorization-bypass / unauthorized-account-operation primitive reachable from ordinary contract calls triggered by anonymous transactions, matching the "unauthorized account operation / accounting corruption" impact bar.

### Likelihood Explanation
Exploitation requires only: (1) an account with a multi-key permission whose threshold is intended to require ≥2 distinct signers, and (2) any calling contract that uses `ValidateMultiSign` to gate value-moving or privilege-granting logic. Generating a malleable ECDSA signature pair from a single private key is a standard, well-known operation (flip `s` to `n-s`, adjust recovery id), requiring no special access — any holder of one key in the permission set can attempt this. The only mitigating factor is that it depends on downstream contract logic actually relying on `ValidateMultiSign`'s weight-threshold semantics for genuinely privileged effects, and on whether `validateComponents()`/`SignUtils.fromComponents` truly omits a canonical-`s` (low-s) restriction — this exact check was not directly located in the indexed code and should be verified against `ECKey.ECDSASignature`/`SM2.SM2Signature` before treating this as fully confirmed.

### Recommendation
- Change the de-duplication key in `ValidateMultiSign.execute()` to be solely `recoveredAddr` (one weight contribution per unique signer address), not the concatenation of address+raw signature bytes.
- Additionally/alternatively, enforce canonical (low-`s`) signature normalization in the signature-recovery path (`recoverAddrBySign` / `SignUtils.fromComponents` / `ECDSASignature.validateComponents`) so that malleable signature variants are rejected outright, consistent with EIP-2/BIP-62 style canonicalization.
- Apply the same audit to `BatchValidateSign` and any other precompile/actuator path that aggregates or counts per-signer contributions from raw signature bytes.

### Proof of Concept
1. Create an account with an `Active` permission containing keys `K1` (weight 1) and `K2` (weight 1), threshold 2 — intended to require both `K1` and `K2` to authorize.
2. As the holder of `K1` only, sign the target hash to get `sig1 = (r, s, v)`.
3. Derive the malleable counterpart `sig1' = (r, n-s, v')`, which recovers to the same address as `K1`.
4. Call the `ValidateMultiSign` precompile (address as exposed via TVM) with `signatures = [sig1, sig1']`.
5. In the loop: for `sig1`, `recoveredAddr = K1`, not yet in `executedSignList` → weight 1 added. For `sig1'`, `recoveredAddr = K1` again, `matrixContains(executedSignList, K1)` is true, but `matrixContains(executedSignList, merge(K1, sig1'))` is false (different bytes) → falls through, adds weight 1 again.
6. `totalWeight = 2 >= threshold(2)` → precompile returns "valid", even though only `K1` ever authorized the action, bypassing the intended 2-of-2 requirement. [2](#0-1)

    byte[] out = null;

    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);

          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {

            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
