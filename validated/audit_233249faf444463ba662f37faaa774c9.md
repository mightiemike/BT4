## Title
Non-monotonic aggregator-count key derivation lets same-transaction create/destroy sequences alias two distinct AggregatorV1 objects to the same `StateKey` - (File: `aptos-move/framework/natives/src/aggregator_natives/aggregator_factory.rs`)

### Summary
`native_new_aggregator` derives each new aggregator's storage key by hashing the session hash together with `aggregator_data.num_aggregators() as u32` [1](#0-0) . `num_aggregators()` is *not* a monotonically increasing "creations so far" counter — it returns the current size of the live `values`/`ids` maps, which shrinks whenever a create-then-destroy pair is elided in the same transaction [2](#0-1) . This lets a sequence of create/destroy/create calls within one transaction reuse the same derived `key`, and thus the same `AggregatorID`/`StateKey` (built from a fixed table `handle` plus that `key`) [3](#0-2) , for two objects the Move layer believes are distinct.

### Finding Description
The comment in the native explicitly states the intended design: "taking hash of transaction and number of aggregator instances created so far" [4](#0-3) . But the actual counter, `AggregatorData::num_aggregators`, is defined as `self.values.len() + self.ids.len()` [5](#0-4) , and `remove_aggregator` deletes the entry from `values`/`ids` and, when the aggregator was created earlier in the same transaction, elides it entirely (removes it from `new_aggregators` too) [6](#0-5) . The unit test `create_then_destroy_within_txn_is_elided` confirms this elision semantic [7](#0-6) .

Concretely, within one transaction:
1. create A → `num_aggregators()==0` → key₀; `values={A}`.
2. create B → `num_aggregators()==1` → key₁; `values={A,B}`.
3. destroy A (created this txn) → elided → `values={B}`, so `num_aggregators()` drops back to `1`.
4. create C → `num_aggregators()==1` → **key₁ again**, identical to B's key.

Because `AggregatorID::new(handle, key)` builds the state key purely from `(handle, key)` [8](#0-7) , and all V1 aggregators created through `aggregator_factory::create_aggregator_internal` share the same singleton `AggregatorFactory` table handle [9](#0-8) , B and C collide on the exact same `StateKey`. `aggregator_data.set_value(id, 0)` for C simply overwrites the map entry already used for B (same `BTreeMap` key), so from that point the two Move-level `Aggregator` objects (B and C), which the calling module treats as independent, are backed by the identical underlying table item.

### Impact Explanation
Two logically distinct aggregator objects created in the same transaction can be silently unified into a single state key. Any subsequent `add`/`sub`/`read` on one object transparently mutates the other, and the final write set will contain only one entry for what should be two independent table items — a genuine state-corruption/aliasing bug reachable from any Move code path that creates and destroys aggregators inside a single transaction. Because the derivation is deterministic and consensus-relevant (it directly determines the write-set key), any two nodes executing the same transaction would derive the same aliasing, so it does not desync consensus, but it does corrupt the intended state model (an unprivileged caller triggering the framework's own aggregator bookkeeping to merge two independent counters is a real integrity violation of state commitment, not merely a presentation issue).

### Likelihood Explanation
Exploitability is constrained by privilege on `aggregator_factory::create_aggregator_internal`, which is `public(friend)` and restricted to `aptos_framework::genesis` and `aptos_framework::optional_aggregator` [10](#0-9) . `optional_aggregator::new`/`destroy`/`switch` are themselves `friend`-scoped to specific framework modules (e.g., coin supply tracking) [11](#0-10) , so an ordinary user transaction cannot directly call `create_new_aggregator`/`remove_aggregator` at will with attacker-chosen ordering — this must be reached indirectly through a framework module that internally performs multiple aggregator create/destroy cycles inside one transaction (e.g., repeated `switch` calls or repeated coin-initialization/removal flows). I was not able to confirm, within the available code, an existing framework entry point that lets an unprivileged caller trigger multiple `optional_aggregator` create+destroy+create cycles inside a single transaction — this would require further tracing of every friend caller of `optional_aggregator::new`/`switch`/`destroy` (e.g., `coin.move`, `fungible_asset.move`) to see whether any exposes a user-triggerable code path invoking it multiple times per transaction. Given this gap, likelihood is currently unconfirmed/low rather than demonstrated.

### Recommendation
Change the key-derivation counter to a strictly monotonic "aggregators created in this transaction" counter (e.g., track a running `created_count: u32` that only increments in `create_new_aggregator` and is never decremented in `remove_aggregator`), rather than deriving it from the live `values.len() + ids.len()`. This restores the intended semantics described in the code comment and eliminates the possibility of key reuse within a transaction regardless of create/destroy ordering.

### Proof of Concept
Extend the existing `num_aggregators_counts_touched` test in `aggregator_v1_extension.rs` [12](#0-11)  to reproduce the collision at the `AggregatorData` level:

```rust
let mut data = AggregatorData::default();
let a = aggregator_v1_id_for_test(1);
let b = aggregator_v1_id_for_test(2);
let c = aggregator_v1_id_for_test(3);

data.create_new_aggregator(a.clone());
data.set_value(a.clone(), 0);                 // num_aggregators() was 0 for A

data.create_new_aggregator(b.clone());
data.set_value(b.clone(), 0);                 // num_aggregators() was 1 for B

data.remove_aggregator(a.clone());            // create+destroy elided -> values now {B}
assert_eq!(data.num_aggregators(), 1);        // <-- counter went BACKWARDS

// Simulating native_new_aggregator's derivation, C would now hash with count=1,
// the same count B used, producing the same derived `key` (and thus the same
// AggregatorID, since handle is shared) despite B and C being distinct objects.
```

This demonstrates that `num_aggregators()` is not stable/monotonic across a create→destroy→create sequence, which is the root cause of the key-collision path described above. Full end-to-end reproduction (proving a truly unprivileged Move entry function can trigger the sequence, and that two distinct on-chain `Aggregator` values end up backed by the same `StateKey` in the produced write set) requires an e2e-move-tests harness exercising a friend module that performs the create/destroy/create pattern within one transaction — this was not located/confirmed in the reviewed code.

    /// Returns the number of aggregators touched in this transaction. Used
    /// for deterministic key derivation, so it counts every touched aggregator
    /// regardless of the optimization (only one of the two value maps is
    /// populated at a time).
    pub fn num_aggregators(&self) -> u128 {
        debug_assert!(self.values.is_empty() || self.ids.is_empty());
        (self.values.len() + self.ids.len()) as u128
    }

    /// Destroys an aggregator. If it was created in this transaction, the create and destroy cancel
    /// out and nothing is written; otherwise it is marked for deletion from storage.
    pub fn remove_aggregator(&mut self, id: AggregatorID) {
        self.values.remove(&id);
        self.ids.remove(&id);
        self.read_aggregators.remove(&id);

        // If the aggregator was created in this transaction, the create and destroy cancel out;
        // otherwise it has to be deleted from storage.
        if !self.new_aggregators.remove(&id) {
            self.destroyed_aggregators.insert(id);
        }
    }
