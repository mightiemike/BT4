### Title
`ensure_match_transaction_info()` skips checkpoint-hash comparison, letting replay-verify tooling report a false "match" despite a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` in `types/src/transaction/mod.rs` is the comparator used by db-tool's replay-verify path (`storage/db-tool/src/replay_on_archive.rs`) and other replay/debugger tooling to check that a freshly re-executed `TransactionOutput` matches an already proof-authenticated `TransactionInfo` pulled from archive/backup. The function checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is explicitly acknowledged in a `TODO(trading-native)` comment in the code itself.

### Finding Description
`ensure_match_transaction_info()` [1](#0-0)  compares four fields between the locally re-executed `TransactionOutput` and the trusted `TransactionInfo`: status, gas_used, write_set hash vs. `state_change_hash`, and event_root_hash. It never touches `txn_info.state_checkpoint_hash()`, the hot-state checkpoint hash, or `position_state_checkpoint_hash`, as the trailing comment makes explicit: [2](#0-1) .

This comparator is the sole per-transaction correctness check used by `replay_on_archive.rs`'s `execute_and_verify`, which re-executes historical transactions with the current VM and compares the result against the archived, ledger-proof-verified `TransactionInfo` list: [3](#0-2) . The archived `expected_txn_infos` were only previously bound to a ledger accumulator proof (i.e., that the *bytes* of the `TransactionInfo` were included in the chain), not re-verified against a freshly computed state root during this tool's execution path. Since `state_change_hash` (per-txn write-set hash) is different from `state_checkpoint_hash` (accumulated Sparse-Merkle-Tree root at a checkpoint boundary, which depends on the entire prior state, not just this transaction's write set), a bug in state-tree update logic, hot-state materialization, or the new "trading-native"/position state root logic could produce an incorrect accumulated state root while every individual write-set hash still matches. `ensure_match_transaction_info()` would return `Ok(())` in that case, silently missing the divergence.

Contrast this with the `ChunkResultVerifier` used in normal (non-debugging) chunk-executor replay flows, `ReplayChunkVerifier::verify_chunk_result()`, which calls `ledger_update_output.ensure_transaction_infos_match(...)` [4](#0-3)  — that path compares full `TransactionInfo` objects (which include the checkpoint hash fields) rather than the field-limited comparator in `types/src/transaction/mod.rs`. This means the field-omission is specific to the debugger/replay-on-archive tooling path, not the production commit path.

### Impact Explanation
This maps to the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated API ... output bound to the wrong version, object, or proof context" categories in the state-integrity gate. If the underlying state-tree/checkpoint-hash computation ever diverges from the historical, ledger-committed root (e.g., due to a bug introduced in state-merkle-tree logic, hot-state handling, or newly added "trading-native" position-state roots), `replay_on_archive`/db-tool verification — which is explicitly relied on as a safety net to catch consensus-breaking VM changes before they reach mainnet — would report success instead of flagging the divergence. This directly undermines an authenticated, proof-bound state-root check, and a silent divergence of this kind is exactly the pre-condition for an undetected hard fork.

### Likelihood Explanation
The exposure requires an underlying bug that changes the accumulated state root while leaving individual write-set hashes, event hashes, gas usage, and status unaffected — this is a real and plausible failure mode because `state_checkpoint_hash` depends on tree-construction logic (SMT/JMT updates, hot-state materialization, and the new position-state root path) that is separate from write-set serialization. The comment in the code itself flags this as a known, currently-live gap, gated only on the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature but affecting the comparator unconditionally today. Likelihood of the underlying divergence trigger is moderate (requires a separate root-cause bug), but the detection gap itself is unconditionally present in the current code.

### Recommendation
In `ensure_match_transaction_info()`, when `expected` state/hot-state/position checkpoint hashes are present (i.e., when this transaction is a checkpoint boundary), recompute the corresponding hash(es) from the locally executed state and assert equality against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, mirroring what `ensure_transaction_infos_match` already validates in the standard chunk-executor replay path.

### Proof of Concept
Conceptual/code-level (no live network needed — this is a static code-completeness gap, not an exploit against a running network):
1. In `replay_on_archive.rs`, run `execute_and_verify` against a chunk of historical transactions whose archived `TransactionInfo` values are trusted (previously proof-verified).
2. Suppose the current VM/tree logic, due to a hypothetical bug, computes the *same* per-transaction write set, gas usage, status, and events as history, but a *different* final Sparse-Merkle-Tree/JMT root (state_checkpoint_hash) at the checkpoint boundary — e.g., a bug in stale-node pruning, hot-state carry-over, or position-state root aggregation.
3. `ensure_match_transaction_info()` at [5](#0-4)  only checks status/gas/write_set_hash/event_root_hash, so it returns `Ok(())`.
4. `execute_and_verify` records no error for that transaction/chunk, and the db-tool replay-verify job reports success despite the state root having silently diverged from the authenticated ledger state.

Note: I was not able to trace whether other callers of `ensure_match_transaction_info` (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) have supplementary checks that would independently catch this gap; a full assessment would require reviewing those call sites as well, which I could not fully inspect within the available iterations.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
