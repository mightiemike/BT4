## Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verification tooling accept a `TransactionOutput` whose state/hot-state/position state roots diverge from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed to the ledger accumulator. The function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the corresponding fields computed during re-execution. [1](#0-0) 

### Finding Description
The relevant code: [2](#0-1) 

The function verifies `status`, `gas_used`, `write_set_hash` vs `txn_info.state_change_hash()`, and `event_root_hash` vs `txn_info.event_root_hash()`. It ends with a `TODO(trading-native)` comment that is itself an admission of the gap: *"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution. Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`."* [3](#0-2) 

This differs from the normal block/chunk-execution commit path, which does validate state-checkpoint hashes: `DoStateCheckpoint` compares `known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints` (sourced from committed `TransactionInfo`s) against locally computed checkpoint hashes and errors on mismatch. [4](#0-3) [5](#0-4) 

However, the replay/debugger tooling path that uses `ensure_match_transaction_info` does not go through `DoStateCheckpoint`; it only compares the four fields listed above. This means a re-executed transaction whose Move-VM/state-checkpoint output silently diverges from the committed ledger state (e.g., due to a state-merkle-root computation bug, a hot-state or position-state feature interacting incorrectly with the JMT/state-summary layer, or non-determinism introduced by a future protocol change) would still pass `ensure_match_transaction_info` and be reported as a successful replay, because the write-set hash and event-root hash can match while the state-checkpoint/hot-state/position-state roots do not.

### Impact Explanation
This breaks the "authenticated response/proof output must stay bound to the right ledger version, root, and object" invariant for replay and verification tooling: `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` are used to independently verify that historical execution matches what was committed on-chain (used for auditing hard forks, chain-state divergence investigations, and confirming VM upgrades don't silently change behavior). If the checkpoint-hash mismatch is exactly the kind of divergence these tools are meant to catch (a corrupted or incorrectly computed state root that does not affect the write-set/event content but does affect the state-tree root), the tooling will falsely report "replay success," masking a real state-commitment divergence. This is a state-integrity/proof-verification gap: a wrong state-checkpoint root can be accepted as "matching" even though it is not the correct VM result, undermining downstream trust in replay-verification for detecting silent consensus/state divergence.

Because `position_state_checkpoint_hash` and `hot_state_checkpoint_hash` are gated by not-yet-fully-enabled features (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, hot state), the position/hot-state-specific part of this gap is not yet triggerable on current mainnet blocks that don't use those features. But `state_checkpoint_hash` (the classic state-checkpoint hash present on every checkpoint transaction) is always populated on mainnet, and it is also excluded from this comparison — so the gap applies today for standard state-checkpoint transactions, not only future trading-native functionality.

### Likelihood Explanation
Likelihood of the underlying divergence (a state-checkpoint-root bug distinct from write-set/event divergence) occurring is not high by itself, but the point of replay-verification tooling is precisely to catch such rare, hard-to-detect bugs. Because the comparator silently ignores exactly the field designed to catch that class of bug, the tool's detection coverage for state-tree corruption is weaker than intended. The bug is fully reachable today (no privilege needed — anyone running `replay-verify`/db-tool/aptos-debugger against archived data) since `ensure_match_transaction_info` is called unconditionally, and the missing check is unconditional as well (not just conditional on the trading-native feature).

### Recommendation
In `ensure_match_transaction_info` (`types/src/transaction/mod.rs`), add explicit comparisons of `self`'s recomputed `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` (or the checkpoint-hash values produced by the execution pipeline for this transaction) against the corresponding fields on `txn_info`, returning an error on mismatch, matching the pattern already used in `DoStateCheckpoint::get_state_checkpoint_hashes`. This should be done before any code path that could produce a non-`None` `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` becomes reachable (i.e., before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` broadly), and ideally immediately, since `state_checkpoint_hash` validation is missing even for standard, already-enabled checkpointing.

### Proof of Concept
Not applicable as an exploit script (this is a missing-check finding). Conceptual demonstration: construct a `TransactionOutput`/`TransactionInfo` pair where `write_set`, `events`, `gas_used`, and `status` are identical, but the two `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) values differ. Call `TransactionOutput::ensure_match_transaction_info` — it returns `Ok(())` despite the state-checkpoint mismatch, whereas the equivalent path through `DoStateCheckpoint::get_state_checkpoint_hashes` (used in normal block/chunk execution) would `ensure!`-fail on the same mismatch, confirming the two paths have inconsistent integrity guarantees.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
