## Analysis Summary

The C4 finding is about a single-step, irreversible admin-address change (`changeUberOwner`) that only validates the new address isn't the zero address, but never verifies the target is actually usable — so a typo permanently bricks the system with no recovery path.

The strongest reachable analog in `nearcore--024` is the `DeleteAccount` action's `beneficiary_id` field. Any unprivileged account holder can submit a `DeleteAccountAction` (directly or via meta-transaction) specifying an arbitrary `beneficiary_id` as the destination for their entire remaining balance. Validation of that field is exactly as shallow as `changeUberOwner`'s zero-address check: it only confirms the string is a *syntactically valid* account ID, never that the account exists or is reachable. Execution then unconditionally emits a system refund receipt carrying the whole balance to that ID in one irreversible step, and this repo's own tests confirm that when the target account does not exist, the refund receipt fails and (per the documented "failed refund" invariant) the balance is burned rather than restored to anyone.

### Title
Single-step, unvalidated `beneficiary_id` in `DeleteAccountAction` permanently burns the deleted account's entire balance on a typo/non-existent destination - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccount` moves an account's entire balance to `beneficiary_id` in a single, irreversible step. The only check performed on `beneficiary_id` — both at validation time and at execution time — is that it is a syntactically well-formed account ID string; there is no check that the account exists, is controlled by anyone, or is even the same account type intended by the caller. If a user (or a relayer executing a meta-transaction on the user's behalf) submits a `DeleteAccount` action with a mistyped or nonexistent `beneficiary_id`, the account is deleted and its full balance is sent as a system balance-refund receipt to that address; since refund receipts are never allowed to create new accounts, the transfer fails and the funds are burned with no way to recover them — structurally identical to the reported "wrong-address, single-step, unrecoverable" `uberOwner` bug class, just applied to a fund-destination address instead of an authority address.

### Finding Description
Validation of the action only calls `validate_action_account_id`, which enforces the `AccountId` grammar and nothing else: [1](#0-0) 

Execution (`action_delete_account`) computes the account's current balance and unconditionally queues a `Receipt::new_balance_refund` to `beneficiary_id`, then immediately removes the account from state — there is no second confirmation step, no existence check on the destination, and no way to reverse the deletion once it commits: [2](#0-1) 

The documentation for this action explicitly states the only pre-execution error is a malformed account ID string — never a check that the beneficiary account actually exists: [3](#0-2) 

Balance-refund receipts (the mechanism used to pay the beneficiary) are categorically barred from creating a new account, and a repo test explicitly asserts that a refund to a nonexistent target fails with `AccountDoesNotExist` while leaving the target account absent from state: [4](#0-3) 

A separate test's own comment on the "happy path" independently confirms the danger: it notes that the beneficiary "has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" — i.e., the developers were aware of, but did not add protocol-level protection against, this exact scenario: [5](#0-4) 

Finally, the spec for this component documents the systemic consequence of a failed refund: rather than being restored to the (now-deleted) sender, the burnt deposit goes to `other_burnt_amount`, i.e. it is destroyed, not recovered: [6](#0-5) 

This is directly analogous to the `changeUberOwner()` bug class: a single-step, irreversible state transition driven by a user-supplied address, gated only by a superficial format check, where an incorrect (but well-formed) address causes unrecoverable loss — in this case of the caller's entire NEAR balance rather than of contract-owner control.

### Impact Explanation
Any unprivileged NEAR account holder who submits `DeleteAccount { beneficiary_id }` with a mistyped, nonexistent, or otherwise incorrect (but grammatically valid) `beneficiary_id` permanently and unrecoverably burns their account's entire remaining balance. There is no correction mechanism: the account no longer exists by the time the beneficiary-refund receipt fails, so the funds cannot be reclaimed by anyone. This is a concrete, protocol-level "permanently frozen/burned funds" outcome triggered entirely by a normal transaction from a single unprivileged signer — no attacker or validator collusion required.

### Likelihood Explanation
Low-to-moderate likelihood, high impact — matching the judge's own characterization of the analogous C4 finding as Medium risk. `DeleteAccount` is a rarely-exercised but fully user-reachable action (also reachable via NEP-366 meta-transactions/relayers), and a mistyped or stale `beneficiary_id` (e.g., referencing a sub-account that was itself deleted, or a fat-fingered account name) is a plausible real-world user error with no safety net in the protocol.

### Recommendation
Introduce protocol-level protection analogous to the two-step ownership-change pattern recommended in the original report — e.g., have `DeleteAccount` (or a wrapping client/wallet flow) require confirming that `beneficiary_id` corresponds to an existing, funded account (or the signer's own account) before the delete is accepted, or make the balance-refund receipt failure roll back the whole delete instead of unconditionally removing the account first. At minimum, wallets/clients issuing this action should be required to pre-verify beneficiary existence off-chain, but a protocol-level existence check at `validate_delete_action`/`action_delete_account` would remove the unrecoverable-burn class entirely.

### Proof of Concept
1. Alice owns `alice.near` with balance `B > 0`.
2. Alice submits a transaction with a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "aliceen.near" })` (a typo of a nonexistent account) signed with her own full-access key.
3. `validate_delete_action` passes because `"aliceen.near"` is a syntactically valid `AccountId`.
4. `action_delete_account` removes `alice.near` from state and queues `Receipt::new_balance_refund("aliceen.near", B)`.
5. When that refund receipt is processed, `check_account_existence`/`implicit_creation_allowed` reject account creation for refunds (`is_refund: true` always returns `false`), so the receipt fails with `AccountDoesNotExist`.
6. `alice.near` no longer exists (already removed in step 4), so the failed refund's deposit is burned into `other_burnt_amount` rather than returned to anyone — `B` is permanently lost, exactly as in the `changeUberOwner` scenario where an unrecoverable address error bricks/destroys value with no remediation path.

## Invariants & failure modes

- **Gas ordering**: `merge` asserts `gas_burnt_for_function_call <= gas_burnt <= gas_used` per action (`runtime/runtime/src/lib.rs:440`).
- **Failed receipt atomicity**: a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting (`runtime/runtime/src/lib.rs:967`). `set_error` additionally clears queued receipts, proposals, and burnt/subsidized amounts (`runtime/runtime/src/lib.rs:487`).
- **Staking invariant**: `update_validator_accounts` returns a fatal `StorageInconsistentState` if `locked < max_of_stakes` (`runtime/runtime/src/lib.rs:1617`).
- **Invalid txs make progress, not failure**: a chunk with invalid transactions is not rejected; the offending txs are skipped during conversion, polluting the chain with junk but keeping the shard live (`runtime/runtime/src/lib.rs:1706` doc; skip sites at `:1994`, `:2199`).
- **Refund receipts are free**: system-predecessor receipts burn zero gas; a failed refund burns its deposit into `other_burnt_amount` rather than refunding (`runtime/runtime/src/lib.rs:929`, `:972`).
- **Delayed receipts must stay valid**: a delayed receipt that fails `validate_receipt` on dequeue is treated as `StorageInconsistentState` (`runtime/runtime/src/lib.rs:2500`).
