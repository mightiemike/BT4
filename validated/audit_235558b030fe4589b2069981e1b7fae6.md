### Title
Unbounded per-account `slot_list` growth causes full O(n) linear scans on every read/clean pass - (File: accounts-db/src/accounts_index.rs)

### Summary
`AccountsIndex::latest_slot()` and `purge_older_root_entries()` both perform a full linear iteration over a pubkey's entire `slot_list` — the per-account analog of the reported `stakerTierHistory` unbounded-array pattern — on every single account read, upsert-reclaim resolution, and clean pass. If cleaning is delayed or blocked (e.g., by a held `ScanGuard`/ongoing scan pinning `min_ongoing_scan_root`, per `max_clean_root()`), this list can grow with every root produced while the affected pubkey is repeatedly written, and every subsequent access to that pubkey pays the full linear cost.

### Finding Description
`AccountMapEntry::slot_list` is a `Vec`-backed list of every `(Slot, T)` version of an account still known to the index [1](#0-0) . Every read of a pubkey (`get_account_info_with_and_then` → `latest_slot`) does a full linear scan of this list, without any short-circuit besides sequential iteration: [2](#0-1) 

This is invoked on essentially every account load through `get_account_info_with_and_then` [3](#0-2) , and by clean's per-candidate scan [4](#0-3) .

Clean is the only mechanism that trims `slot_list` back down, via `purge_older_root_entries`, which also does a full linear scan/filter of the list each time it runs [5](#0-4) . Critically, `max_clean_root()` bounds cleaning to `min_ongoing_scan_root()` whenever a scan is active [6](#0-5) , and `ScanGuard` pins a `max_root` in `ongoing_scan_roots` for the scan's lifetime, explicitly stating this can prevent clean from progressing past that root while active [7](#0-6) [8](#0-7) . Comments on `flush_rooted_accounts_cache_with_clean` explicitly acknowledge that a long-running scan can prevent cleaning of updates from newer slots [9](#0-8) .

This mirrors the `stakerTierHistory` bug class precisely: an unbounded per-key history list is fully re-scanned on every access, its length is driven by ordinary system activity (root production / account writes) rather than by the account owner's own actions, and the linear-scan cost scales with however many roots accumulate before clean can run.

### Impact Explanation
While `slot_list` length is normally kept small (1–2 entries typical) because clean runs continuously, any condition that suppresses cleaning for an account that is written on every new root (a validator identity/vote-adjacent system account, a frequently-written program-owned PDA, etc.) causes `slot_list` to grow by one entry per root. Every subsequent `latest_slot()` call for that pubkey — i.e., every transaction load/store touching it — becomes O(n) in the number of accumulated roots, and the clean scan itself (`purge_older_root_entries`) becomes correspondingly more expensive per pass, disproportionately increasing CPU cost for both normal transaction processing and the AccountsDB clean/shrink pipeline for that specific account.

### Likelihood Explanation
The precondition (an active scan holding back `max_clean_root`) is a legitimate, reachable code path (`ScanGuard`, used for `getProgramAccounts`-style RPC scans and other index scans), not a contrived or purely theoretical state — the codebase's own comments describe this exact scenario as a known consequence of long-running scans. However, per SECURITY.md scope limits, RPC-triggered growth requiring sustained/abnormal client behavior beyond a single call within `CLUSTER_SLOT_TIME_TARGET / 2` is explicitly out of scope, which weakens confidence that this is independently exploitable by an unprivileged actor without such an RPC precondition. I could not confirm within the available index whether any other non-RPC, purely internal path (e.g., normal validator operation without a scan) can indefinitely delay clean for a specific hot pubkey; this is the main open uncertainty.

### Recommendation
- Bound how far `min_ongoing_scan_root` can lag behind the current root before clean is allowed to proceed regardless (there is already a `max_distance_to_min_scan_slot` stat tracked in `ScanGuard::try_new`, suggesting the team is aware of this drift but does not currently cap it).
- Consider incremental/resumable cleaning of a single pubkey's `slot_list` so a single clean pass does not need to reprocess entries already known to be below the newest safe root.
- Emit metrics/alerts when an individual `slot_list` length exceeds a sane threshold so operators can detect pathological accumulation before it becomes a CPU cost problem.

### Proof of Concept
Not independently verified with a runnable reproduction; the analysis is based on static code-path tracing:
1. Start an index scan (e.g., via an RPC-exposed scan) that pins `ongoing_scan_roots` at slot `R` (`ScanGuard::try_new`) [10](#0-9) .
2. While the scan is held open, repeatedly write to the same pubkey across many subsequent roots > `R`.
3. `max_clean_root()` restricts clean's `max_clean_root_inclusive` to `R` [6](#0-5) , so `purge_older_root_entries` cannot reclaim any of the newer entries, and the pubkey's `slot_list` grows by one entry per subsequent root.
4. Every load of that pubkey (`latest_slot`) and every clean pass touching it now costs O(number of roots since `R`), disproportionately increasing CPU time for that specific account relative to normal indexed accounts.

    // Given a SlotList `L`, a list of ancestors and a maximum slot, find the latest element
    // in `L`, where the slot `S` is an ancestor or root, and if `S` is a root, then `S <= max_root`
    pub(crate) fn latest_slot(
        &self,
        ancestors: Option<&Ancestors>,
        slot_list: &[SlotListItem<T>],
        max_root_inclusive: Option<Slot>,
    ) -> Option<usize> {
        let mut current_max = 0;
        let mut rv = None;
        if let Some(ancestors) = ancestors
            && !ancestors.is_empty()
        {
            for (i, (slot, _t)) in slot_list.iter().rev().enumerate() {
                if (rv.is_none() || *slot > current_max) && ancestors.contains_key(slot) {
                    rv = Some(i);
                    current_max = *slot;
                }
            }
        }

        // If we found an ancestor, then we can return early without checking the roots
        // If there is a root that is newer than the newest ancestor but not an ancestor
        // then the root is from a different fork and should not be returned
        if let Some(rv) = rv {
            return Some(slot_list.len() - 1 - rv);
        }

        let max_root_inclusive = max_root_inclusive.unwrap_or(Slot::MAX);

        slot_list
            .iter()
            .enumerate()
            .filter(|(_, (slot, _t))| *slot <= max_root_inclusive)
            .max_by_key(|(_, (slot, _t))| *slot)
            .map(|(index, _)| index)
    }

    pub(crate) fn try_new(
        scan_tracker: &'a ScanTracker,
        scan_bank_id: BankId,
        max_root_inclusive_fn: impl FnOnce() -> Slot,
    ) -> Option<Self> {
        {
            let locked_removed_bank_ids = scan_tracker.removed_bank_ids.lock().unwrap();
            if locked_removed_bank_ids.contains(&scan_bank_id) {
                return None;
            }
        }

        let max_root_inclusive = {
            let mut w_ongoing_scan_roots = scan_tracker
                // This lock is also grabbed by clean_accounts(), so clean
                // has at most cleaned up to the current `max_root` (since
                // clean only happens *after* BankForks::set_root() which sets
                // the `max_root`)
                .ongoing_scan_roots
                .write()
                .unwrap();
            // `max_root()` grabs a lock while
            // the `ongoing_scan_roots` lock is held,
            // make sure inverse doesn't happen to avoid
            // deadlock
            let max_root_inclusive = max_root_inclusive_fn();
            if let Some(min_ongoing_scan_root) =
                ScanTracker::min_ongoing_scan_root_from_btree(&w_ongoing_scan_roots)
                && min_ongoing_scan_root < max_root_inclusive
            {
                let current = max_root_inclusive - min_ongoing_scan_root;
                scan_tracker
                    .max_distance_to_min_scan_slot
                    .fetch_max(current, Ordering::Relaxed);
            }
            *w_ongoing_scan_roots.entry(max_root_inclusive).or_default() += 1;
            max_root_inclusive
        };

        scan_tracker.active_scans.fetch_add(1, Ordering::Relaxed);
        Some(Self {
            scan_tracker,
            max_root: max_root_inclusive,
            scan_bank_id,
        })
