Based on the investigation, the strongest reachable analog in java-tron is in `ParticipateAssetIssueActuator`, which implements TRC10 token-sale participation (an ICO-style "buy tokens with TRX" flow with a fixed, time-bounded token supply held by the issuer) — the same bug class as the Set Protocol Dutch-auction frontrunning DoS: a transaction that computes a fixed required output quantity and reverts (rather than capping) if that exact amount is no longer available due to a preceding transaction consuming part of the supply.

### Title
Full-supply/last-lot `ParticipateAssetIssue` purchases can be DOS'd via frontrunning small participations - (File: actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java)

### Summary
`ParticipateAssetIssueActuator` lets any account buy TRC10 tokens from an ongoing asset issuance by sending TRX; the actuator computes a fixed `exchangeAmount` from the sent `amount` and requires the issuer's (`toAddress`) remaining asset balance to be at least that amount, both at validation time and during execution via a strict subtraction. Because this check is an exact `>=` bound rather than a "buy up to what's available" cap, any unprivileged account can front-run a legitimate buyer who is trying to acquire the last/most of the remaining token allocation, causing the legitimate transaction to revert with "Asset balance is not enough!" — exactly analogous to the `AuctionRebalanceModuleV1` full-inventory DOS in the external report.

### Finding Description
In `doValidate()`, the exchange amount is computed deterministically from the caller-supplied `amount` and the fixed issuance ratio, then checked against the issuer's remaining token balance: [1](#0-0) 

In `execute()`, the same `exchangeAmount` is subtracted from the issuer's (`toAccount`) asset balance, and if it is insufficient the whole transaction reverts: [2](#0-1) 

There is no mechanism to cap the purchase to "whatever remains" — the caller must specify an exact TRX `amount`, which deterministically maps to an exact token `exchangeAmount` via `multiplyExact`/`floorDiv` on `assetIssueCapsule.getNum()`/`getTrxNum()`: [3](#0-2) 

Because a `ParticipateAssetIssueContract` is a normal, unprivileged transaction (any account can call it, and multiple accounts can compete for the same fixed-size token issuance), a malicious actor can observe a pending large/last-lot participation transaction in the mempool and front-run it with a tiny participation transaction targeting the same asset. This reduces `toAccount`'s remaining asset balance just enough that the victim's precomputed `exchangeAmount` now exceeds what remains, causing `assetBalanceEnoughV2` to fail and the victim's whole transaction (which already paid gas/bandwidth) to revert with "Asset balance is not enough !".

This mirrors the root cause in the Sherlock report precisely: `require(_componentQuantity <= bidInfo.auctionQuantity, ...)` reverts instead of clamping, letting any user front-run and shrink `auctionQuantity` below what a victim specified.

### Impact Explanation
Any unprivileged account can repeatedly and cheaply grief legitimate participants who are trying to purchase the entire/most of the remaining supply of a limited, time-bound TRC10 issuance (a common pattern for time-limited/fixed-supply token sales). This:
- Wastes the victim's bandwidth/energy fee on a reverted transaction.
- Can be used to intentionally stall a buyer from acquiring the full remaining allocation before the issuance's `endTime`, causing the buyer to receive less than they intended or nothing at all if the window closes.
- Is easily and cheaply repeatable, since the attacker only needs to submit a minimal-amount participation each time the target broadcasts a transaction, and gains no funds themselves but can deny others.

This matches the accepted Sherlock precedent (settled as Medium) where "DOS of a valid bid ... is considered damage to how the auction/sale functions", even though there is no direct loss of principal to the attacker or protocol beyond griefing and reduced acquisition by the legitimate buyer.

### Likelihood Explanation
`ParticipateAssetIssueContract` is a standard, unprivileged, fee-paying transaction type available to any account holding TRX, requiring no special permissions. Asset issuances with fixed `startTime`/`endTime` and limited remaining supply are a normal use pattern for TRC10 tokens, so scenarios where a buyer wants the full/last remaining allocation are plausible and economically motivated (e.g., near `endTime`, or when supply is nearly exhausted). Front-running via mempool observation and fee/priority manipulation is a well-established capability on TRON.

### Recommendation
Allow victims to express "buy as much as remains" intent instead of requiring an exact match:
- Add an optional flag/sentinel (e.g., `amount == -1` or a dedicated field) that caps `exchangeAmount`/`cost` to the issuer's actual remaining asset balance at execution time, rather than reverting when the precomputed exact amount exceeds what remains.
- Alternatively, clamp `exchangeAmount` to `min(computedExchangeAmount, toAccount.getAssetBalance(assetName))` and refund/return the unused proportional TRX `cost`, so a legitimate buyer's transaction always succeeds for whatever amount is actually still available instead of reverting entirely.

### Proof of Concept
1. Asset `X` has a limited remaining participation-eligible balance of `R` tokens held by issuer `toAddress`, with `endTime` approaching.
2. Victim `V` broadcasts `ParticipateAssetIssueContract` with `amount = A` such that the computed `exchangeAmount = floor(A * num / trxNum) == R` (i.e., V is trying to buy exactly all that remains).
3. Attacker `M` observes V's pending transaction and broadcasts a `ParticipateAssetIssueContract` with a tiny `amount` (e.g., `amount = 1`) for the same asset with higher fee/priority, which executes first via `toAccount.reduceAssetAmountV2(...)`, reducing `toAccount`'s remaining balance to `R - ε`. [2](#0-1) 
4. V's transaction then executes `doValidate()`/`execute()` with the same precomputed `exchangeAmount == R`, but `toAccount.assetBalanceEnoughV2(assetName, R, dynamicStore)` now fails because only `R - ε` remains, so V's transaction reverts with "Asset balance is not enough !", even though V would gladly have accepted `R - ε` tokens. [4](#0-3) 
5. `M` can repeat this cheaply for every retry V makes until `endTime` passes, denying V the ability to acquire the remaining supply.
