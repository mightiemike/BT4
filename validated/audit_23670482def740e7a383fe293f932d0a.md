### Title
Unvalidated bytes32→address truncation in `ContractEventParser`/`ContractEventParserAbi` lets a malicious contract spoof the `address` field in event-subscription output - ([File: framework/src/main/java/org/tron/common/logsfilter/ContractEventParser.java])

### Summary
The reported ENS bug is a general "bytes32→address" truncation-without-validation pattern: a 32-byte word is reduced to a 20-byte address by taking the last 20 bytes, without checking that the discarded upper 12 bytes are zero. In java-tron's event-subscription log decoder, `ContractEventParser.parseDataBytes`/`parseTopic` (and its ABI-decoding counterpart) perform the exact same unchecked truncation when decoding a Solidity `address`-typed event field or topic emitted from any (attacker-controlled) smart contract.

### Finding Description
When decoding an emitted log for the `address` ABI type, the code does:
```java
} else if (type == Type.ADDRESS) {
  byte[] last20Bytes = Arrays.copyOfRange(startBytes, 12, startBytes.length);
  return StringUtil.encode58Check(TransactionTrace.convertToTronAddress(last20Bytes));
}
``` [1](#0-0) 
and identically in `parseTopic`: [2](#0-1) 

The 32-byte `startBytes`/`bytes` value comes straight from raw log/topic data that any deployed smart contract can freely emit (`LOG0..LOG4`), e.g. `emit MyEvent(address indexed a, ...)` where the contract writes an arbitrary, fully attacker-controlled 32-byte word for that slot. Solidity/TVM would normally zero-extend a legitimate address to 32 bytes, but nothing prevents a contract (via inline assembly or raw `LOG` opcodes) from placing non-zero garbage in the upper 12 bytes while making the lower 20 bytes equal to a victim address of interest. `ContractEventParser` never checks that the upper 12 bytes are zero before slicing them off — it silently truncates and reports a legitimate-looking Base58 TRON address, exactly the `hexToAddress`/ENS bug pattern (truncate 256→160 bits without validating the discarded bits are zero).

This decoded, Base58-encoded "address" is what actually reaches external consumers: it is put into the JSON payload delivered through `EventPluginLoader`/`IPluginEventListener` (native message queue or gRPC/plugin event stream) that exchanges, wallets, and other downstream services rely on for on-chain monitoring: [3](#0-2) [4](#0-3) 

### Impact Explanation
Downstream services (exchange deposit/withdraw trackers, custodial wallets, indexers) commonly key their internal accounting off the decoded `address` field of TRC20/TRC721 `Transfer`-style events. Because the parser accepts any 32-byte word whose low 20 bytes match a target address — regardless of whether the high 12 bytes are actually zero (i.e., regardless of whether the value is a "real" address at all) — a malicious contract can emit forged events that masquerade as transfers to/from a victim address that were never validated as canonical addresses at the TVM/ABI level. This can lead to accounting corruption in systems that trust the event-subscription feed (e.g., crediting/debiting the wrong account, false deposit notifications), which is a direct analog of "asset or accounting corruption" caused by accepting an invalid/truncated address as valid.

### Likelihood Explanation
Reachable by any unprivileged actor: deploying and calling a contract that emits a log with a crafted (non-zero-padded) 32-byte value is a normal, permissionless operation, no special privileges or peer/dependency compromise needed. The only precondition is that the node operator has `event.subscribe.enable = true` with `contractevent`/`contractlog` triggers enabled, which is a common production configuration for exchanges and monitoring infrastructure.

### Recommendation
In `ContractEventParser.parseDataBytes`/`parseTopic` (and the equivalent `ContractEventParserAbi`/`ContractEventParserJson` paths), when decoding `Type.ADDRESS`, verify the upper 12 bytes are all zero before truncating; if not, either throw/reject the field (mirroring `UnsupportedOperationException`/`OutputLengthException` already used elsewhere in this file) or flag the trigger payload as containing an invalid address rather than silently emitting a Base58-encoded address.

### Proof of Concept
1. Deploy a contract that emits a raw log via inline assembly, e.g.:
```solidity
function fakeTransfer(address victim) external {
    assembly {
        // topic0 = keccak256("Transfer(address,address,uint256)")
        // put victim in low 20 bytes but set upper 12 bytes to non-zero garbage
        let word := or(shl(160, 0xdeadbeefdeadbeefdeadbeefdeadbeef), victim)
        mstore(0x00, word)
        log1(0x00, 0x20, 0x1234...)
    }
}
```
2. With `event.subscribe` enabled and `contractevent`/`contractlog` triggers on, `ContractEventParser`/`ContractEventParserAbi` decodes the topic/data field typed `address` by taking `Arrays.copyOfRange(startBytes, 12, 32)`, ignoring that the upper 12 bytes are non-zero, and emits a valid-looking Base58 address for `victim` in the pushed trigger JSON.
3. A downstream consumer subscribed to this feed sees what looks like a legitimate transfer event referencing `victim`'s address, even though the raw on-chain word was never a canonical (zero-padded) address.
