### Title
Quadratic-complexity storage-write revert-tracking causes disproportionate CPU cost per transaction - (File: crates/blockifier/src/execution/syscalls/syscall_base.rs)

### Summary
`SyscallHandlerBase::storage_write` (and its Cairo0 counterpart `DeprecatedSyscallHintProcessor::set_contract_storage_at`) re-scans the entire, ever-growing `EntryPointExecutionContext::revert_infos` vector on every *first* write to a previously-unseen storage key within a call's lifetime. Because this vector is never trimmed on success (only drained on revert), a single transaction can be crafted so that this scan cost grows linearly with each iteration of a loop, producing O(N²) total CPU work for O(N) chargeable syscalls — the same "quadratic blow-up from repeated re-scanning of accumulated state" bug class as the referenced Suricata SMTP/MIME URL-extraction CVE.

### Finding Description
`context.revert_infos.0` (`ExecutionRevertInfo`, defined in `crates/blockifier/src/execution/entry_point.rs:97-101`) accumulates one `EntryPointRevertInfo` entry per contract call made during a transaction's execution (validate + execute). Entries are only removed via `EntryPointExecutionContext::revert` when a call actually reverts (`crates/blockifier/src/execution/entry_point.rs:554-570`); on the success path the vector keeps growing for the whole transaction. [1](#0-0) 

Each `SyscallHandlerBase` (one per active call frame) records `revert_info_idx = context.revert_infos.0.len() - 1` at creation time: [2](#0-1) 

`storage_write` then does, for the *first* write to any given key within that frame: [3](#0-2) 

The `.skip(self.revert_info_idx + 1)` walk scans every `EntryPointRevertInfo` pushed *since this frame started* — i.e., every nested/child call made so far in this frame's own execution. If a contract, within a single call, repeatedly interleaves (a) a `call_contract` syscall (which pushes one new `EntryPointRevertInfo`) and (b) a `storage_write` to a fresh key, the i-th write scans i entries. Summed over N iterations this is O(N²), while the transaction is only billed for N syscalls (O(N) gas/steps). The identical pattern exists for Cairo 0 contracts: [4](#0-3) 

The revert-info accounting itself is explicitly noted as a source of quadratic risk in a related design decision ("We don't merge infos related [to the] same contract as doing it on every nesting level would result in O(N^2) complexity"), showing the surrounding code is aware of, but does not fully close, this class of cost: [5](#0-4) 

### Impact Explanation
Any account/contract deployer can submit a single `INVOKE` transaction whose contract logic issues a loop of `call_contract` + `storage_write(new_key)` syscalls. The Starknet fee/step model charges these as O(N) operations, but the sequencer's (and every full node's) blockifier execution engine performs O(N²) work internally. An attacker can therefore pay for N linear-cost syscalls while forcing the block-building/re-execution machinery to spend quadratically more wall-clock CPU time than budgeted. At scale (e.g., a few thousand iterations, still well within per-tx step limits), this can materially slow down block production and re-execution across all nodes that execute the same transaction (sequencer, full nodes, and re-execution paths in RPC/trace endpoints), creating a availability/performance-DoS condition consistent with "a network unable to confirm new transactions" if block-building consistently exceeds its time budget.

### Likelihood Explanation
High likelihood: this is reachable via a completely ordinary INVOKE transaction to any deployed/declared Cairo0 or Cairo1 contract that performs `call_contract` and `storage_write` syscalls in a loop — no special permissions, no contract deployer trust, and no reliance on a malicious operator/prover/node. It only requires standard `DECLARE` + `DEPLOY`/constructor + `INVOKE` capability available to any user.

### Recommendation
Bound or amortize the revert-info original-value lookup:
- Replace the linear scan in `storage_write`/`set_contract_storage_at` with an indexed structure (e.g., a `HashMap<(ContractAddress, StorageKey), Felt>` populated incrementally as new frames are pushed, or per-contract per-key "already captured" markers) so the cost of finding an already-captured original value is O(1) amortized instead of O(current depth/breadth).
- Alternatively, charge additional gas/steps proportional to the size of `revert_infos.0` scanned per write so cost billing matches actual computational cost, closing the fee/CPU-time mismatch.
- Add a regression/benchmark test measuring wall-clock time for a transaction that alternates many `call_contract` + fresh `storage_write` syscalls to confirm the fix removes the quadratic blow-up.

### Proof of Concept
Deploy a Cairo1 contract with an external entry point that, given a loop count `N`, does for `i in 0..N`:
1. `call_contract(any_trivial_contract_address, some_selector, [])` — pushes a new `EntryPointRevertInfo` into `context.revert_infos.0`.
2. `storage_write(key = i, value = 1)` — a first-time write to a brand-new key in the calling frame, which triggers `storage_write`'s scan over `context.revert_infos.0[revert_info_idx+1..]`, now of length `i`.

Invoke this entry point via a normal `INVOKE` transaction with `N` chosen near the maximum allowed by per-transaction step/gas limits. Measure blockifier execution wall-clock time versus `N`; it should grow superlinearly (quadratically) relative to the linear growth of `N`, unlike the linear growth exhibited when `storage_write` calls are not interleaved with new `call_contract` invocations (i.e., when the scanned suffix stays empty).

Note: I was not able to directly execute or benchmark this PoC (no execution environment available in this session) — the finding is based on static code-path analysis of `crates/blockifier/src/execution/syscalls/syscall_base.rs` and `crates/blockifier/src/execution/entry_point.rs`; empirical confirmation of the wall-clock blow-up should be performed by running the described transaction against the blockifier test harness.

    pub fn storage_write(&mut self, key: StorageKey, value: Felt) -> SyscallResult<()> {
        let contract_address = self.call.storage_address;

        match self.original_values.entry(key) {
            hash_map::Entry::Vacant(entry) => {
                // Check if any inner call (entries created after this handler's entry) already
                // captured an original value for this key. If so, use that value instead of the
                // current state, because the inner call captured the true original before any
                // writes in this execution scope.
                let original_value = self
                    .context
                    .revert_infos
                    .0
                    .iter()
                    .skip(self.revert_info_idx + 1)
                    .find_map(|info| {
                        if info.contract_address == contract_address {
                            info.original_values.get(&key).copied()
                        } else {
                            None
                        }
                    })
                    .map_or_else(|| self.state.get_storage_at(contract_address, key), Ok)?;
                entry.insert(original_value);
            }
            hash_map::Entry::Occupied(_) => {}
        }

        self.storage_access_tracker.accessed_storage_keys.insert(key);
        self.state.set_storage_at(contract_address, key, value)?;

        Ok(())
    }
