### Title
`AccountCostIncrease`'s `create_account_charge` fee can be bypassed by creating and deleting an account within the same receipt - (File: `runtime/runtime/src/lib.rs`)

### Summary
Perennial's M-10 root cause was that an expensive protocol operation (an oracle price request) had its compensating fee assessed only at **settlement time**, so a user who opened and closed a position atomically before settlement never incurred the fee, even though the expensive resource (an oracle request/keeper incentive) had already been consumed. `nearcore` has a structurally identical pattern: the `AccountCostIncrease` protocol feature charges an extra `create_account_charge` for creating a new account, but this charge is only levied if the account **still exists at the end of the receipt**. Bundling `CreateAccount` and `DeleteAccount` into a single action receipt lets the expensive resource (a new account/state entry) be created and then removed before the fee-assessment check runs, so the charge is skipped entirely, exactly mirroring the "deposit-then-immediately-withdraw" bypass in the audit.

### Finding Description
When applying an action receipt, the runtime snapshots whether the account existed *before* running the receipt's actions: [1](#0-0) 

After all actions in the receipt have executed (in order, including any `DeleteAccount`), the runtime decides whether a new account was "created" purely by looking at the **post-execution** local `account` variable: [2](#0-1) 

`created_new_account = account_did_not_exist && account.is_some() && result.result.is_ok()`. If the same receipt contains `CreateAccount` (or an implicit-account-creating `Transfer`) followed later by `DeleteAccount`, `action_delete_account` clears the local `account` to `None` before this check runs, so `account.is_some()` is `false` — `created_new_account` evaluates to `false` even though a brand-new account was, in fact, created and destroyed during this receipt.

That flag feeds directly into the refund/fee logic in `refund_unspent_gas_and_deposits`, where the extra `create_account_charge` (capped at `account_creation_charge`, mainnet `0.007 N`) is only subtracted from the gas refund `if a new account was created`: [3](#0-2) 

Because `created_new_account` is `false` for the create+delete-in-one-receipt case, this subtraction step is skipped and the `account_creation_charge` is never burnt, even though the account creation (and its associated state/witness overhead that this NEP-536/`AccountCostIncrease` charge exists to compensate for) genuinely occurred.

This is directly analogous to the Sherlock M-10 bug: there, the fee (oracle/keeper incentive) is meant to compensate for an expensive resource request, but it is only debited at settlement, so opening and closing a position atomically (before settlement) bypasses it. Here, the `create_account_charge` is meant to compensate for account-creation overhead, but it is only debited if the account still exists when the post-action check runs, so creating and deleting the account atomically (within the same receipt) bypasses it.

The reachability of "create and delete an account within a single receipt" is already demonstrated in the existing test suite (via a self-signed `call_promise` batch action, and via `bootstrap_tx` state-init flows), confirming this is a normal, unprivileged, single-receipt code path, not a contrived edge case: [4](#0-3) [5](#0-4) 

### Impact Explanation
The `create_account_charge` under `AccountCostIncrease` (PV 85) was introduced specifically to raise the effective cost of account creation to account for real, on-chain overhead (state growth / storage-proof cost) that account creation imposes on validators. Bypassing it lets an attacker (an ordinary transaction signer, or a self-signed batch/`call_promise` sender, or even a relayer-funded meta-transaction flow) repeatedly create and delete accounts within single receipts, paying only the base `create_account_cost`/`delete_account_cost` action fees while avoiding the surcharge meant to price in the account-creation overhead. This is a fee/gas-bypass of a specific protocol-level anti-abuse charge — the same bug class Sherlock rated Medium in Perennial (fee bypass via atomic open+close), and it maps to the "gas metering ... fee or gas bypass" category explicitly called out in this scan's acceptance criteria. It does not directly mint tokens or corrupt the state root, but it is a concrete, protocol-defined fee that a normal transaction signer can systematically avoid paying, undermining the anti-spam/cost-recovery purpose of `AccountCostIncrease` for a repeatable operation.

### Likelihood Explanation
High reachability, low complexity: any signer can submit a single action receipt (a self-signed function call using `call_promise`/promise batch actions, or a signed transaction with actions `[CreateAccount, ..., DeleteAccount]`, subject to `DeleteActionMustBeFinal` requiring `DeleteAccount` be the last action) that creates then deletes the account before the runtime's post-execution `account.is_some()` check runs. This requires no validator collusion, no cross-shard timing tricks, and works within a single chunk. It is gated purely behind protocol version 85 (`AccountCostIncrease`) being active; on releases where that feature is enabled, the bypass is always available to a normal caller.

### Recommendation
Compute `created_new_account` from the fact that a `CreateAccount` (or account-creating `Transfer`/implicit account creation) action successfully executed during the receipt — e.g., track this as a result flag set at the point of creation in `apply_action`/`ActionResult`, independent of whether a later action in the same receipt subsequently deletes the account — rather than inferring it from the account's existence at the end of the receipt. This ensures `create_account_charge` is charged whenever account creation actually occurred, regardless of whether the account is deleted later in the same receipt.

### Proof of Concept
1. Enable/target a protocol version where `AccountCostIncrease` (PV 85) is active (mainnet-equivalent behavior).
2. Submit a single action receipt whose actions are, in order: `CreateAccount` (or an implicit-account-creating `Transfer`) followed by other setup actions and a final `DeleteAccount` (satisfying `DeleteActionMustBeFinal`) — this is exactly the pattern already exercised by the existing `delete_after_init_removes_account` and `test_instant_delete_account` tests, which show create+delete succeeding within one receipt: [5](#0-4) [4](#0-3) 
3. After `apply_action_receipt` finishes, inspect the emitted gas-refund receipt / burnt tokens. Because `account.is_some()` is `false` at the check on `lib.rs:1057`, `created_new_account` is `false`, so `refund_unspent_gas_and_deposits`'s `create_account_charge` subtraction (`lib.rs:1243`, described in `protocol-model/spec/economics.md:65`) is never applied — the gas refund to the signer is larger by exactly `account_creation_charge` (mainnet `0.007 N`) compared to the case where the account is created and left to persist.
4. Repeating this pattern lets a signer create and destroy accounts indefinitely while never paying the `create_account_charge` surcharge that `AccountCostIncrease` was designed to impose on account creation.

Note: I was not able to fully trace the `apply_action` / `action_delete_account` implementation (in `runtime/runtime/src/actions.rs`) within the indexed context to confirm the exact point at which the local `account` variable is set to `None` on deletion; this is inferred from the documented behavior of `DeleteAccount` ("removes the account") and the test evidence that create+delete-in-one-receipt succeeds. A background agent with full repository access should verify this by instrumenting/adding a unit test asserting the refund amount with and without a trailing `DeleteAccount`, under `AccountCostIncrease`.

1. **Gas burn price** — with `AccountCostIncrease` enabled, gas is burnt at `min(gas_purchase_price, apply_state.gas_price)`; before it, at `apply_state.gas_price` (`lib.rs:920`).
2. **Refunds** — `refund_unspent_gas_and_deposits` (`lib.rs:1166`) refunds unspent gas and, on failure, the full deposit. `gross_gas_refund` = prepaid gas + prepaid exec gas − gas actually used/burnt (`lib.rs:1186`). It then:
   - Computes the NEP-536 penalty `gas_penalty_for_gas_refund(gross)` = `min(gross, max(gross * gas_refund_penalty, min_gas_refund_penalty))` (`core/parameters/src/cost.rs:683`) at `gas_burn_price` (post-`AccountCostIncrease`) or `gas_purchase_price` (before) (`lib.rs:1201`). The unused-gas refund is issued at `gas_purchase_price` minus this penalty (`lib.rs:1210`).
   - Records `price_deficit` if the burn price rose above purchase price, else `price_surplus` (`lib.rs:1220`). With `AccountCostIncrease`, the surplus is refunded to the signer (`burned_gas_refund`, `lib.rs:1235`); before, it was retained as burnt.
   - If a new account was created (post-`AccountCostIncrease`), an extra `create_account_charge` = `min(desired = account_creation_charge − already-burned, burned_gas_refund)` is subtracted from the refund (`lib.rs:1243`).
3. **tx_burnt_amount** — burnt tokens for the receipt = `gas_burn_price * gas_burnt − price_deficit` (`lib.rs:975`), plus `refund_penalty`, `create_account_charge`, and `result.tokens_burnt`; pre-`AccountCostIncrease` also plus `price_surplus` (`lib.rs:978`). System/refund receipts burn 0 gas (`lib.rs:972`).
4. **Contract reward** — of the gas burnt *for function calls*, a `burnt_gas_reward` fraction (mainnet `3/10`) is paid to the receiver account and *subtracted* from `tx_burnt_amount` (`lib.rs:990`). Reward is priced at `gas_burn_price` post-`AccountCostIncrease`, else `gas_purchase_price` (`lib.rs:998`). If the receiver account no longer exists, the whole amount stays burnt (goes to validators via §3). The remaining `tx_burnt_amount` accumulates into `stats.balance.tx_burnt_amount` (`lib.rs:1023`) and ultimately reduces total supply as `balance_burnt`.

    #[test]
    fn delete_after_init_removes_account() {
        init_test_logger();
        let signer = signer_for("bootstrap-then-delete");
        let state_init = state_init_for(&[signer.public_key()]);
        let account_id = derive_universal_account_id(&state_init.to_raw());
        let balance = Balance::from_near(10);
        let (runtime, tries, root, apply_state, epoch) = setup(&account_id, balance);

        // The beneficiary has to exist, otherwise the balance transfer the delete
        // sends it would come straight back as a refund.
        let beneficiary: AccountId = "beneficiary.near".parse().unwrap();
        let mut state = tries.new_trie_update(ShardUId::single_shard(), root);
        set_account(
            &mut state,
            beneficiary.clone(),
            &Account::new(Balance::from_near(1), Balance::ZERO, AccountContract::None, 100),
        );
        state.commit(StateChangeCause::InitialState);
        let trie_changes = state.finalize().unwrap().trie_changes;
        let mut store_update = tries.store_update();
        let root = tries.apply_all(&trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        let delete = Action::DeleteAccount(DeleteAccountAction { beneficiary_id: beneficiary });
        let tx = bootstrap_tx(&signer, &state_init, &account_id, expected_nonce(), vec![delete]);
        let (root, outcomes) = apply_txs(&runtime, &tries, root, &apply_state, &epoch, vec![tx]);

        assert_matches!(outcomes[0].outcome.status, ExecutionStatus::SuccessReceiptId(_));
        let receipt_outcome = outcomes
            .iter()
            .find(|outcome| !matches!(outcome.outcome.status, ExecutionStatus::SuccessReceiptId(_)))
            .expect("the state init receipt must have an outcome");
        assert_matches!(
            &receipt_outcome.outcome.status,
            ExecutionStatus::SuccessValue(_),
            "initializing and then deleting in one receipt must succeed"
        );

        let state = tries.new_trie_update(ShardUId::single_shard(), root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "the account must be gone once the delete has run"
        );
    }
