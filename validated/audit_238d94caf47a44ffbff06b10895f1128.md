### Title
Unbounded attacker-controlled `gasLimit`/payload in `UniversalPayload` lets honest UV finalization votes panic-rollback, permanently blocking inbound finalization - (File: `x/uexecutor/types/universal_payload.go`, `x/uexecutor/keeper/msg_vote_inbound.go`)

### Summary
`UniversalPayload.GasLimit` and `.Data` are decoded straight from attacker-controlled source-chain event bytes (`DecodeUniversalPayloadEVM`/`DecodeUniversalPayloadSolana`) and are never bounded before being handed to `DerivedEVMCall` during synchronous inbound finalization. This is the same bug class as the TOKI bridge finding: an attacker-sized gas/payload value that consumes (or exceeds) the resources available in the finalizing operation, causing that operation to fail destructively and block forward progress — here, the finalizing `MsgVoteInbound` transaction itself, rather than an IBC channel.

### Finding Description
`UniversalPayload.ValidateBasic` (`x/uexecutor/types/universal_payload.go:24-64`) only checks that `GasLimit`/`Value`/etc. parse as non-negative integers — there is no upper bound. [1](#0-0) 
`Inbound.ValidateForExecution` (`x/uexecutor/types/inbound.go:126-175`) likewise never caps `UniversalPayload.GasLimit` or `Data` length before execution. [2](#0-1) 
For non-CEA payload inbounds, the actual `UniversalPayload` that gets executed is decoded straight from `RawPayload` — bytes emitted verbatim by the source-chain gateway event, fully attacker-controlled — via `DecodeUniversalPayloadEVM`/`DecodeUniversalPayloadSolana`, again with no cap on `gasLimit` or `data` length. [3](#0-2) [4](#0-3) 

Honest UVs observe and faithfully report this event via `MsgVoteInbound` (this is the intended "dumb relay" design, confirmed by tests: `TestInbound_VoteInboundValidationPipeline` explicitly documents "UV is a dumb relay"). When quorum is reached, `VoteInbound` (`x/uexecutor/keeper/msg_vote_inbound.go`) records the vote, commits the ballot tally via a `CacheContext.commit()`, then — in the SAME message-handler invocation, on the outer (uncached) `ctx` — creates the `UniversalTx` and calls `k.ExecuteInbound(ctx, utx)` synchronously. [5](#0-4) 
That dispatches to `ExecutePayloadV2` → `CallUEAExecutePayload`, which parses the attacker-controlled `GasLimit` string directly into the `*big.Int` gas limit passed to `k.evmKeeper.DerivedEVMCall`, with no min/max sanity check. [6](#0-5) [7](#0-6) 

Because `ExecuteInbound` runs directly on the message-handler-scoped `ctx` (not a further cache-context that's swallowed on error), any panic during this EVM execution (e.g., the SDK gas meter for the enclosing `MsgVoteInbound` tx running out because the attacker-chosen `gasLimit` demands more computation than the tx's declared gas, or an uncaught runtime panic inside the derived-call path) is caught by `baseapp`'s top-level recover and discards **all** state changes made during this message execution — including the `RecordInboundVote`/ballot-tally `commit()` that happened earlier in the same handler. The net effect: the validator's vote that would have pushed the ballot over quorum is wiped as if it never happened.

### Impact Explanation
Because the payload bytes are attacker-controlled and reproduced identically by every honest UV, every subsequent attempt to cast the quorum-crossing vote for this specific inbound hits the exact same panic and rollback. The malicious inbound event can never reach `BALLOT_STATUS_PASSED`, so no `UniversalTx` is ever durably created for it. Since the user's underlying deposit already happened on the source chain (out of Push Chain's control), this constitutes a permanent, unprivileged, unrecoverable freeze of that user's cross-chain funds/inbound state — directly analogous to the TOKI report's "blocked channel," except the blast radius here is scoped to the specific malicious inbound (and repeatedly wastes UV/node computation on every finalization attempt) rather than the entire bridge, which is still in-scope per the "permanent freezing of user funds" and "denial of service…reachable without privileged control" allowed-impact categories.

### Likelihood Explanation
High. No privileged actor is required: any user can trigger a source-chain gateway event with an attacker-chosen `UniversalPayload.gasLimit`/`data`, and honest, unmodified Universal Validators are required by design ("dumb relay") to report it verbatim. No code path in `ValidateBasic`, `ValidateForExecution`, or the decode functions rejects an oversized `gasLimit` or `data` before it reaches `DerivedEVMCall`.

### Recommendation
- Add explicit upper bounds on `UniversalPayload.GasLimit` (e.g., a module param comparable to the Solidity bridge's `MAX_OUTER_GAS`) and on `UniversalPayload.Data` length, enforced in `Inbound.ValidateForExecution` / `UniversalPayload.ValidateBasic` before the inbound is ever voted into a ballot.
- Ensure `ExecuteInbound`'s payload-execution step is wrapped in its own `CacheContext` with a `recover()` boundary so that an EVM-side gas exhaustion/panic cannot roll back the already-tallied ballot vote — a failed execution should still let the vote/ballot state and `UniversalTx` (marked failed, eligible for revert) persist, exactly as the "always create UTX" comment in `VoteInbound` intends.
- Reject/normalize `gasLimit` values that exceed whatever gas the finalizing `MsgVoteInbound` transaction is guaranteed to have, rather than relying on the submitting client to happen to pick a sufficient `--gas` value.

### Proof of Concept
Conceptual (cannot be executed without a running devnet + source-chain gateway):
1. Attacker sends a source-chain deposit/gateway transaction whose emitted event ABI-encodes a `UniversalPayload` with `gasLimit` set far beyond what any UV's submitted `MsgVoteInbound` transaction gas will cover (or targeting a `to` contract that burns gas without reverting cheaply).
2. Honest UVs observe the event and submit `MsgVoteInbound` reporting it verbatim (per the "dumb relay" design confirmed in `x/uexecutor/types/inbound_test.go`).
3. On the quorum-crossing vote, `VoteInbound` → `ExecuteInbound` → `ExecutePayloadV2` → `CallUEAExecutePayload` → `DerivedEVMCall` attempts to run the EVM call with the attacker's oversized `gasLimit`.
4. The resulting gas exhaustion/panic is caught by `baseapp`, rolling back the entire `MsgVoteInbound` tx, including the ballot-tally `commit()` from earlier in the same handler.
5. Repeat step 2–4 indefinitely: the ballot for this inbound never finalizes, and the corresponding `UniversalTx`/funds handling never occurs.

I was not able to inspect the internal gas-accounting implementation of `DerivedEVMCall` itself (defined in the external forked `github.com/pushchain/evm` dependency, outside this repository's indexed scope), so the precise mechanism by which an oversized `gasLimit` translates into an SDK-level panic (vs. a contained EVM-level revert) could not be fully confirmed from source in this repo — this is stated as an open assumption based on the documented behavior in `DERIVED_TRANSACTIONS.md` and the complete absence of any gasLimit/data-length cap in the validation pipeline.
