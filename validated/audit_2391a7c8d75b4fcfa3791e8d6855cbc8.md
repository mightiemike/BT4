## Finding: Inconsistent `GetCanDelegatedMaxSize` View Calculation vs. Actual `DelegateResourceContract` Enforcement

### Title
Divergent bandwidth-usage estimation between `GetCanDelegatedMaxSize` view RPC and actual `DelegateResourceContract` enforcement leads to inaccurate max-delegable-size results - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The bug class in the report — a view/estimator function that computes a "max amount" without accounting for all constraints enforced by the real state-changing operation, causing misleading results and failed transactions — has a concrete analog in java-tron's resource delegation subsystem. The `getCanDelegatedMaxSize` RPC (backed by `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize`) computes bandwidth usage differently from the actual enforcement logic in `DelegateResourceActuator.validate()` and the TVM-native `DelegateResourceProcessor.validate()`, producing three different answers for "how much can I delegate" depending on the code path.

### Finding Description
`Wallet.calcCanDelegatedBandWidthMaxSize` (the implementation behind the public `GetCanDelegatedMaxSize` gRPC/HTTP API, used by wallets/dApps to determine the safe amount to delegate) unconditionally inflates `accountNetUsage` by `TransactionUtil.estimateConsumeBandWidthSize(dynamicStore, ownerCapsule.getFrozenV2BalanceForBandwidth())`: [1](#0-0) 

In contrast, `DelegateResourceActuator.validate()` — the code that actually enforces the limit when a `DelegateResourceContract` is executed — only applies this same bandwidth estimate conditionally, when `this.getTx() != null && this.getTx().isTransactionCreate()`: [2](#0-1) 

Furthermore, the TVM native-contract path `DelegateResourceProcessor.validate()` (used when `DelegateResource` is invoked from a smart contract) omits this estimate entirely, computing `netUsage` purely from `ownerCapsule.getNetUsage()`: [3](#0-2) 

This means the same underlying "available FreezeBandwidthV2 balance" check — `frozenV2BalanceForBandwidth - v2NetUsage >= delegateBalance` — is computed three different ways depending on whether the caller is: (1) querying the read-only RPC, (2) submitting a normal `DelegateResourceContract` transaction, or (3) invoking the TVM `delegateResource` precompile from a contract. This is structurally identical to the sUSX issue: a view function meant to tell users the maximum safe amount does not reflect the actual limits enforced at execution time.

### Impact Explanation
A wallet or dApp that queries `GetCanDelegatedMaxSize` to determine a safe delegation amount and then submits a `DelegateResourceContract` with that exact value can have the transaction revert with `"delegateBalance must be less than or equal to available FreezeBandwidthV2 balance"` if the actuator's conditional bandwidth estimate applies but the view function's calculation diverges from it, or conversely under-report the true delegable amount, needlessly restricting legitimate resource delegation. This causes failed transactions and user confusion consistent with the report's medium-severity classification (state divergence between an advisory view and enforced accounting logic).

### Likelihood Explanation
This is reachable by any unprivileged account holder using the standard `GetCanDelegatedMaxSize` API before calling `DelegateResourceContract`, or by any smart contract using the `delegateResource` TVM precompile, both of which are common, unprivileged, everyday operations (resource delegation is a core java-tron feature). No special permissions are required to trigger the divergence.

### Recommendation
Unify the bandwidth/energy usage estimation logic used by `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize`, `DelegateResourceActuator.validate()`, and `DelegateResourceProcessor.validate()` into a single shared helper so that the "max delegable size" view function always exactly matches what will be enforced during actual execution, regardless of whether the delegation is triggered via a normal transaction or the TVM native contract path.

### Proof of Concept
Compare the three code paths for the same account state:
1. `getCanDelegatedMaxSize` (regular tx query) → `Wallet.calcCanDelegatedBandWidthMaxSize` always subtracts `estimateConsumeBandWidthSize(frozenV2BalanceForBandwidth)` from available balance. [4](#0-3) 
2. Submitting `DelegateResourceContract` via normal flow → `DelegateResourceActuator.validate()` only subtracts that estimate `if (this.getTx().isTransactionCreate())`. [5](#0-4) 
3. Invoking `delegateResource` from a smart contract (TVM) → `DelegateResourceProcessor.validate()` never subtracts the estimate. [3](#0-2) 

An account with `frozenV2BalanceForBandwidth = X` and zero net usage will get three different "max delegable" results depending on which path is queried/executed, demonstrating the accounting divergence. (Note: full semantics of `TransactionCapsule.isTransactionCreate()` — which determines when the actuator's stricter branch is taken — were not fully traced within the available index; a Devin session with full repo access is recommended to confirm the exact conditions under which the actuator and view function diverge in production transaction flows.)
