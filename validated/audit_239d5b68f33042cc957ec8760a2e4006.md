## Analysis

The in3-server report is fundamentally a **resource-only DDoS/amplification bug** (no state impact, purely uncompensated compute cost). Per the scan rules, such findings are excluded unless they map to a concrete transaction-triggered impact (fee/gas bypass, state-root divergence, invalid state transition, etc.). I found a genuine analog in nearcore that maps the same underlying bug class — **signature-verification compute costs are attributed to a shard that never performs the verification, letting the real compute cost escape that shard's budget** — but this one is proven as a live gas/compute-metering bypass reachable from a single transaction, not just resource exhaustion.

### Title
Inner delegate-action (meta-transaction) ML-DSA-65 signature verification compute escapes the receiver shard's `compute_limit` before `FixMlDsaCostCharging` (v87) - ([File: runtime/runtime/src/actions.rs])

### Summary
`apply_delegate_action` performs the *actual* cryptographic verification of a `Delegate`/`DelegateV2` action's inner signature on the **receiver shard**, but before protocol feature `FixMlDsaCostCharging` (activated at protocol version 87) the compute cost of that verification is instead charged at transaction-conversion time on the **signer's shard**, which never runs the verify. [1](#0-0) 

### Finding Description
`signature_verification_cost()` computes the extra gas/compute for the signer's own signature plus each `Delegate` action's inner signer, keyed by `SignatureKind` (only `MlDsa65` is non-zero). This total, including the inner-delegate **compute**, is charged on the signer's shard at conversion time when `meter_inner_verify_on_receiver` (the `FixMlDsaCostCharging` gate) is not set: [2](#0-1) 

The actual work — `signed_delegate_action.verify()` — is executed later on the **receiver shard** inside `apply_delegate_action`. Only when `fix_ml_dsa_cost_charging` is true does the receiver shard add `delegate_signature_verification_compute(...)` to `result.compute_usage` before verifying; otherwise the receiver shard's `compute_usage`/`total.compute` never reflects this real cost: [3](#0-2) 

`result.compute_usage` feeds directly into `processing_state.total.compute`, which is compared against the chunk's `compute_limit` to decide whether receipts should be delayed instead of executed in `process_receipts`: [4](#0-3) 

Because the true ML-DSA-65 verification cost (documented at mean ≈ 80 µs, tail up to ~1.3 ms per verify) is not counted against the receiver shard's `compute_limit` when the fix is disabled, the throttling mechanism that is supposed to bound wall-clock work per chunk on that shard is bypassed for this cost component: [5](#0-4) 

The `fix_ml_dsa_cost_charging` config flag and its purpose are explicitly documented as fixing exactly this mis-charging: [6](#0-5) 

Crucially, `FixMlDsaCostCharging` is gated to protocol version **87**, while the stable protocol version reflected in this tree is **86** (`EnforcePerReceiptStorageProofLimit => 86`): [7](#0-6) 

This means at the currently shipped stable protocol version, the mis-charging (compute escapes the receiver shard's budget) is the live, active behavior — not a hypothetical pre-fix state. A dedicated unit test confirms the compute delta between fixed/unfixed behavior is exactly the verification cost, proving the receiver shard receives zero compute charge for this work when the fix is off: [8](#0-7) 

### Impact Explanation
Any account (an ordinary meta-transaction relayer/signer, fully unprivileged) can submit standard transactions containing `Delegate`/`DelegateV2` actions whose inner signer uses an ML-DSA-65 key, directing them at a chosen receiver shard. Each such delegate action forces the **receiver shard** to perform a real ML-DSA-65 verification (materially more expensive than ed25519/secp256k1) whose compute cost is not counted against that shard's `compute_limit`. This is a **gas/compute metering bypass**: the accounting model assumes `compute_usage` tracks real wall-clock cost per shard so `process_receipts` can throttle work to fit the chunk's time budget, but for this cost component that invariant is broken. An attacker can therefore cause a target shard to perform materially more real verification work per chunk than its `compute_limit` was designed to allow, without that shard's throttling logic ever triggering delayed-receipt fallback for the offending cost. This is analogous to the in3-server bug class: expensive signature-verification work is pushed onto a party (here, a shard/its validators) whose accounting does not reflect or bound the true cost, enabling amplified, under-priced work against a target.

### Likelihood Explanation
Requires the `PostQuantumSignatures` feature (ML-DSA-65 keys) to be usable, which is present in this codebase and reachable by any account holder adding/using an ML-DSA-65 key as a delegate-action inner signer — no special privilege, validator status, or network position needed; only crafting standard meta-transactions. The vulnerable code path is default (unfixed) behavior at the stable protocol version documented in this tree, prior to the `FixMlDsaCostCharging` activation at v87.

### Recommendation
Backport/expedite activation of `FixMlDsaCostCharging` (or an equivalent gate) so the inner delegate signature verification compute is always charged to the shard that actually performs the verification (`apply_delegate_action`'s receiver shard), consistent with the model already implemented and gated behind the flag in `runtime/runtime/src/config.rs` and `runtime/runtime/src/actions.rs`. Until fully rolled out, consider bounding the number of ML-DSA-65 inner delegate signatures processable per chunk on any shard, mirroring the recommendation in the source report to cap expensive-signature counts per request.

### Proof of Concept
1. Create an ML-DSA-65 access key and use it as `sender_id`/`public_key` for a `DelegateAction` inner signer (per `PostQuantumSignatures` support).
2. Submit ordinary `SignedTransaction`s from any relayer account containing `Action::Delegate`/`DelegateV2` with that inner ML-DSA-65 signer, targeting receivers all mapped to one victim shard.
3. At conversion time, the signer's shard burns `ml_dsa_65_verification_cost` gas (no receiver-shard compute charged) per `signature_verification_cost` in `runtime/runtime/src/config.rs`.
4. On the receiver shard, `apply_delegate_action` performs the real `signed_delegate_action.verify()` cost but — pre-`FixMlDsaCostCharging` — does not add `delegate_signature_verification_compute(...)` to `result.compute_usage`, so `processing_state.total.compute` in `process_receipts` undercounts real work done, as directly demonstrated by `test_delegate_action_meters_inner_verify_compute` (`runtime/runtime/src/actions.rs:1443-1482`), which shows the compute delta between fixed/unfixed runs equals exactly the (uncharged) verification cost.
5. Repeating this at volume forces the receiver shard to perform verification work unaccounted for by its own `compute_limit` throttle.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }

fn signature_verification_cost(
    fees: &RuntimeFeesConfig,
    signer_public_key: &PublicKey,
    actions: &[Action],
    meter_inner_verify_on_receiver: bool,
) -> Result<ParameterCost, IntegerOverflowError> {
    let costs = &fees.signature_verification_costs;
    let mut total = costs[signature_kind(signer_public_key.key_type())];
    for action in actions {
        if let Some(delegate_action) = delegate_inner_action(action) {
            let kind = signature_kind(delegate_action.public_key().key_type());
            let mut cost = costs[kind];
            if meter_inner_verify_on_receiver {
                cost = ParameterCost { compute: 0, ..cost };
            }
            total = total.checked_add_result(cost)?;
        }
    }
    Ok(total)
}

### 6. Variable-time verify

ML-DSA verify is variable-time (rejection sampling on signature generation
sets up patterns that show as small variance on verify). For the initial
integration:

- Concrete verify-time distribution from benches at
  `core/crypto/benches/{signatures.rs, verify_distribution.rs,
  ml_dsa_worst_case.rs}`: mean ≈ 80 µs (vs ~32 µs ed25519); the tail
  (p99.9 ≈ 170 µs, p99.99+ up to ~1.3 ms) is OS scheduling noise, not
  signature content - **verified by benchmark**: verify time is flat across
  all signature hint-weights (and a single fixed signature reproduces the
  whole distribution), so no maliciously-crafted signature can blow up
  verification time. Measured single-core on an Intel Core Ultra 9 185H.
- Pricing: charged as **gas at transaction conversion** via the
  `ml_dsa_65_verification_cost` runtime parameter (100 Ggas - the extra
  verification cost of ML-DSA-65 over the classical schemes: ~2x the measured
  ~50 µs mean difference at the 1 Tgas/s calibration target, leaving tail
  headroom). The charge is added to the transaction's *burnt* gas (per
  signature, including each `Delegate` action's inner signer), so it raises
  what the signer pays to buy the transaction but never the gas available to
  the resulting receipts; in-contract cross-contract calls are unaffected. See
  the verification-pricing note under "Resolved during integration" for the
  full mechanism.
