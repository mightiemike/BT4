## Title
Attacker can front-run `DeleteKey`/`DeleteAccount` by funding a victim's gas key above the burn threshold to block key/account deletion - (File: `runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/actions.rs`)

## Summary
`TransferToGasKeyAction` lets anyone deposit NEAR into any account's existing gas key by targeting that account as the receiver of a receipt [1](#0-0) . If the funded balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR), both `DeleteKey` on that gas key and `DeleteAccount` on the whole account are rejected with `GasKeyBalanceTooHigh`, exactly mirroring the DYAD "front-run deposit blocks removal" pattern.

## Finding Description
`action_delete_key` dispatches gas-key deletion to `delete_gas_key`, which unconditionally rejects the deletion if the key's accumulated balance is too large to be burned: [2](#0-1) 

The same threshold is aggregated and enforced again when the whole account is deleted, in `action_delete_account`: [3](#0-2) 

Funding a gas key is performed via the `TransferToGasKey` action, which is applied against `account_id` — the *receiver* of the action receipt, not necessarily the signer who paid the deposit: [1](#0-0) 

The deposited amount is deducted from the caller's own balance at the point the action is appended to a promise (e.g. from the WASM host function), and the promise's receiver account can be set to any `account_id`, just like a plain `Transfer` action: [4](#0-3) 

Because the public key of an existing gas key is publicly queryable via RPC (`view_access_key`), an attacker who observes (in the mempool) that a victim is about to issue `DeleteKey`/`DeleteAccount` can pre-emptively send a `TransferToGasKey` receipt to the victim's account, topping the target gas key's balance above 1 NEAR. This is the direct nearcore analog of the DYAD bug: an unprivileged party deposits value into a target's position to make a "must be empty/below-threshold" removal check fail.

## Impact Explanation
This blocks the account owner's ability to remove a compromised or unwanted gas key, or to delete their account, at low, repeatable cost to the attacker (the attacker only needs to push the balance a small amount above the 1 NEAR threshold; e.g. after the victim withdraws down via `WithdrawFromGasKey`, the attacker can top it back up). This is a state-transition-blocking griefing vector reachable by any unprivileged transaction sender against any account whose gas-key public key is known, forcing the owner into a permanent race they cannot reliably win, denying them a legitimate protocol action (key rotation/removal or full account deletion).

## Likelihood Explanation
Likelihood is high: the gas key's public key is not secret (queryable via standard RPC calls such as `view_access_key`), the `TransferToGasKey` action has no authorization check tying it to the account owner, and mempool visibility of the victim's pending `DeleteKey`/`DeleteAccount` transaction gives the attacker the timing needed to front-run cheaply.

## Recommendation
Do not hard-fail deletion when the gas key balance exceeds the burn threshold; instead allow the owner to force-delete (burning only up to `MAX_BALANCE_TO_BURN` and refunding/rejecting the excess back to the depositor or the beneficiary), or restrict `TransferToGasKey`/`WithdrawFromGasKey` funding so that only the account owner (self-receipts, i.e. `predecessor_id == receiver_id`) can increase a gas key's balance, closing the third-party deposit vector entirely.

## Proof of Concept
1. Victim account `A` has a gas key `pk` with balance `b < 1 NEAR`, and `A` submits a `DeleteKey(pk)` (or `DeleteAccount`) transaction.
2. Attacker `B`, observing the pending transaction, submits a receipt with `receiver_id = A`, `Action::TransferToGasKey { public_key: pk, deposit: 1 NEAR - b + 1 yoctoNEAR }` before `A`'s transaction is applied — analogous to the PoC `vaultManager.deposit(id, vault, 1)` front-run in the referenced report.
3. `A`'s `DeleteKey`/`DeleteAccount` now fails with `GasKeyBalanceTooHigh` per `delete_gas_key` / `action_delete_account`'s aggregate check [5](#0-4) [3](#0-2) .
4. `B` can repeat this indefinitely each time `A` tries to withdraw the excess and retry deletion, permanently denying `A` the ability to remove the key/account.

**Note on confidence:** I was unable to conclusively confirm in the available code whether any additional runtime/verifier-level restriction forces `TransferToGasKey`'s receiver to equal its signer (i.e., a strict self-only constraint) — all test usages I found were self-transactions, but I found no explicit enforcement code for such a restriction, and the host-function path (`promise_batch_action_transfer_to_gas_key`) clearly allows targeting an arbitrary `receiver_id` via `batch_create(account_id)`. If such a restriction exists elsewhere and was not surfaced by my searches, this analog would not hold; confirming this would require a Devin session with full-codebase access to trace `verify_and_charge_tx_ephemeral`/`validate_action_receipt` for `TransferToGasKey`.

fn delete_gas_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
) -> Result<(), RuntimeError> {
    if gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: Some(Box::new(public_key.clone())),
            balance: gas_key_info.balance,
        }
        .into());
        return Ok(());
    }

pub fn promise_batch_action_transfer_to_gas_key(
    ctx: &mut Ctx,
    memory: &mut [u8],
    promise_idx: u64,
    public_key_len: u64,
    public_key_ptr: u64,
    amount_ptr: u64,
) -> Result<()> {
    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(HostError::ProhibitedInView {
            method_name: "promise_batch_action_transfer_to_gas_key".to_string(),
        }
        .into());
    }
    let public_key_buf = get_public_key(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        public_key_ptr,
        public_key_len,
        ctx.ext.post_quantum_keys_enabled(),
    )?;
    let public_key_res = public_key_buf.decode();
    let pk_len = public_key_res.as_ref().map_or(0, |pk| pk.len());
    let amount =
        Balance::from_yoctonear(get_u128(&mut ctx.result_state.gas_counter, memory, amount_ptr)?);
    let (receipt_idx, sir) = promise_idx_to_receipt_idx_with_sir(ctx, promise_idx)?;
    let receiver_id = ctx.ext.get_receipt_receiver(receipt_idx);
    let send = gas_key_transfer_send_fee(&ctx.fees_config, sir, pk_len);
    let exec_pk_len = gas_key_exec_pk_len(&public_key_res, &ctx.config, pk_len);
    let exec = gas_key_transfer_exec_fee(&ctx.fees_config, receiver_id.len(), exec_pk_len);
    let burn_base = send.base;
    let use_base = burn_base.gas.checked_add(exec.base.gas).ok_or(HostError::IntegerOverflow)?;
    ctx.result_state.gas_counter.pay_action_accumulated(
        burn_base,
        use_base,
        ActionCosts::gas_key_transfer_base,
    )?;
    let burn_byte = send.per_byte;
    let use_byte =
        burn_byte.gas.checked_add(exec.per_byte.gas).ok_or(HostError::IntegerOverflow)?;
    ctx.result_state.gas_counter.pay_action_accumulated(
        burn_byte,
        use_byte,
        ActionCosts::gas_key_byte,
    )?;
    ctx.result_state.deduct_balance(amount)?;
    ctx.ext.append_action_transfer_to_gas_key(receipt_idx, public_key_res?, amount);
