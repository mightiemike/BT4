### Title
Inconsistent version-1 smart contract transfer restriction between `TransferActuator` and `TransferAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`TransferActuator.validate()` enforces two protections before allowing value to reach a smart-contract account: the `ForbidTransferToContract` check and, when `AllowTvmCompatibleEvm` is enabled, an additional block on sending TRX to any contract whose `getContractVersion() == 1`. `TransferAssetActuator.validate()`, which performs the analogous operation for TRC10 asset transfers, only implements the first check and completely omits the `AllowTvmCompatibleEvm`/contract-version-1 restriction, exactly mirroring the reported bug class where one function (`safeTransferFrom`) enforces a restriction on both sides while a companion function (`safeBatchTransferFrom`) only partially enforces it.

### Finding Description
In `TransferActuator.validate()`, after the `ForbidTransferToContract` check, there is a second gate specifically for contracts whose version is `1` (legacy, pre-EVM-compatible contracts), guarded by `dynamicStore.getAllowTvmCompatibleEvm() == 1`: [1](#0-0) 

This logic does not exist anywhere in `TransferAssetActuator.validate()`, which only performs the `ForbidTransferToContract` check: [2](#0-1) 

The `AllowTvmCompatibleEvm` flag is a chain-wide committee proposal parameter (a `VMConfig.Snapshot` field also used by TVM opcode behavior), confirming that the version-1-contract restriction is intended to be an unconditional, chain-level safety rule once the proposal is active, not specific to native TRX transfers: [3](#0-2)  This is the same class of bug as the report: a security invariant ("no value transfer into a version-1 contract once `AllowTvmCompatibleEvm` is on") is checked in one transfer actuator but skipped in the sibling actuator that performs a functionally equivalent value-moving operation.

### Impact Explanation
An attacker (or any ordinary account) can broadcast a `TransferAssetContract` (TRC10 asset transfer) to a version-1 smart contract even when `AllowTvmCompatibleEvm` is enabled, bypassing the protection that `TransferContract` (TRX transfer) enforces. If version-1 contracts have known incompatibilities under the EVM-compatible execution mode (which is presumably why the restriction exists for TRX), TRC10 assets sent this way could trigger the same unsafe contract behavior the TRX-side check was designed to prevent, leading to stuck/lost assets or contract state inconsistency. Impact is medium: it is a bypass of an existing on-chain safety control, not a full node compromise.

### Likelihood Explanation
Likelihood is medium: the divergent behavior only manifests once the `AllowTvmCompatibleEvm` committee proposal has been enabled and only affects value sent through `TransferAssetContract` targeting a version-1 contract, but no special privilege or malicious node is required — any account can broadcast such a transaction.

### Recommendation
Add the same `AllowTvmCompatibleEvm` / contract-version-1 guard used in `TransferActuator.validate()` to `TransferAssetActuator.validate()`, mirroring the `ContractCapsule` lookup and `getContractVersion() == 1` check so both actuators enforce identical restrictions on transferring value into legacy version-1 contracts.

### Proof of Concept
1. Committee enables `AllowTvmCompatibleEvm` via proposal.
2. Deploy/identify a contract with `contractVersion == 1`.
3. Attempt `TransferContract` (TRX) to that contract → rejected with "Cannot transfer TRX to a smartContract which version is one."
4. Send a `TransferAssetContract` (TRC10 asset) with the same `toAddress` → `validate()` in `TransferAssetActuator` only checks `ForbidTransferToContract`, not `AllowTvmCompatibleEvm`, so the transfer succeeds despite the equivalent restriction being active for TRX.
