## Title
ShieldedTransferContract bypasses bandwidth metering while forcing expensive zk-proof verification (CPU-cost/bandwidth mismatch) - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java, actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

## Summary
`BandwidthProcessor.consume` explicitly skips all bandwidth accounting for `ShieldedTransferContract` transactions via a `continue` on `contract.getType() == ShieldedTransferContract`, while `ShieldedTransferActuator.validate()` unconditionally performs up to one `librustzcashSaplingCheckSpend` and up to two `librustzcashSaplingCheckOutput` calls plus a `librustzcashSaplingFinalCheck`, all of which are computationally expensive zk-SNARK verifications. [1](#0-0) [2](#0-1)  This creates an asymmetry where the fixed `getShieldedTransactionFee()` fee does not scale with the actual CPU work incurred by validators/nodes.

## Finding Description
`BandwidthProcessor.consume` iterates over all contracts in a transaction and normally deducts bandwidth (`useAccountNet`) or applies a bandwidth fee based on transaction byte size. For `ShieldedTransferContract`, it explicitly `continue`s, meaning no bandwidth deduction/throttling is applied at all for these transactions. [3](#0-2) 

Meanwhile, `ShieldedTransferActuator.validate()` — invoked during transaction validation before/at execution — calls `checkProof()`, which for each `SpendDescription` calls `JLibrustzcash.librustzcashSaplingCheckSpend` (native zk-SNARK Groth16 verification), for each `ReceiveDescription` calls `librustzcashSaplingCheckOutput`, and finally `librustzcashSaplingFinalCheck`. [4](#0-3)  A `ShieldedTransferContract` supports up to 1 spend and up to 2 receive descriptions, so each transaction can trigger up to 3 zk-proof checks per transaction. [5](#0-4) 

There is a mitigating mechanism: `ZKProofStore` caches proof verification results keyed by transaction ID, so if the same transaction's proof has already been checked, `checkProof` short-circuits and returns immediately without re-running the native calls. [6](#0-5)  However, this cache only prevents *re-verification of the identical transaction* (e.g., during re-validation when the tx moves from mempool to block); it does nothing to prevent an attacker from crafting many *distinct* transactions, each incurring a fresh, uncached zk-proof verification, all while paying only the fee returned by `calcFee()` (a fixed `getShieldedTransactionFee()` or `getShieldedTransactionCreateAccountFee()`) and consuming zero bandwidth. [7](#0-6) 

An unprivileged attacker with a funded account (to pay the fixed shielded-transfer fee) and a valid Sapling spend/output proof (which can be generated client-side using standard sapling proving keys, requiring no privileged role) can broadcast many `ShieldedTransferContract` transactions. Each transaction forces the full node to run up to 3 native zk-SNARK verification calls during `validate()`, at a fixed, cheap fee, and without bandwidth throttling normally used to rate-limit resource-intensive activity.

## Impact Explanation
This matches a DoS-via-TRON-protocol-implementation impact class: an attacker can amplify CPU cost per unit of paid resource compared to a normal `TransferContract`, since ordinary transfers are bandwidth-metered (deducting from the sender's free/staked bandwidth or requiring TRX burn for extra bandwidth) proportional to their processing cost, whereas shielded transfers impose disproportionately higher CPU cost (native zk-proof verification) for a flat, potentially low fee and zero bandwidth consumption. At scale, this could degrade block-processing throughput or increase mempool/validation latency for the whole node, though the fee (paid on-chain) and network propagation still limit the raw rate of the attack to what the attacker can afford and broadcast.

## Likelihood Explanation
- Precondition `dynamicStore.supportShieldedTransaction()==true` must hold — this is a network-wide flag gated by `ALLOW_SAME_TOKEN_NAME` and shielded-transaction support flags controlled by committee proposals, not attacker-controlled, but assumed true per the question. [8](#0-7) 
- The attacker needs a funded account to pay the fixed shielded fee (`fromAmount <= fee` is rejected). [9](#0-8) 
- No special privilege beyond an ordinary funded account and knowledge of the (public) sapling proving procedure is required — an unprivileged attacker role fits the threat model.
- The attack is repeatable at the rate the attacker can afford transaction fees and the network accepts broadcasts, bounded by normal chain transaction throughput (TPS) limits and P2P propagation, not by bandwidth-based rate limiting (since bandwidth is explicitly skipped).

## Recommendation
Charge bandwidth/resource cost proportional to actual zk-verification work for `ShieldedTransferContract`, e.g., remove or narrow the `continue` bypass in `BandwidthProcessor.consume` for `ShieldedTransferContract`, or introduce an energy-like cost model specifically for the number of `SpendDescription`/`ReceiveDescription` entries that scales with the number of native zk-proof verification calls, rather than relying solely on a flat fee unrelated to CPU cost. Additionally, ensure `getShieldedTransactionFee()`/`getShieldedTransactionCreateAccountFee()` values are periodically reviewed by governance to reflect the real cost of Sapling proof verification.
