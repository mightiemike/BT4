The bug class described in the report is a storage-key case-mismatch: a CosmWasm contract writes state using an address string exactly as supplied by the caller (`on_behalf_of`/`recipient_address`), but reads it back using `info.sender`, which the chain always lowercases — so an uppercase deposit key never matches the lowercase lookup key.

I looked for an analogous "write with one casing, read with a different casing" pattern in java-tron's account/address handling:

- TRON account/contract state is keyed by raw 21-byte address arrays (`AccountStore`, `RepositoryImpl.getStorage`, `Repository.getStorageValue`, etc.), not by a Base58/case-sensitive string representation, so there's no equivalent "same logical address, two different key encodings" ambiguity for normal account or contract storage lookups. [1](#0-0) 
- The only place in the codebase that does deliberately case-fold a key is `AccountIdIndexStore`, which lowercases the key on **both** `put` and `get`/`has`, so writes and reads are always consistent — this is the opposite of the reported bug pattern (which lowercases only on read). [2](#0-1) 
- A locale-dependent case-folding bug (Turkish dotless-ı) was already identified and fixed via `MigrateTurkishKeyHelper`, confirming the team already hardened this specific class of case-normalization mismatch for `AccountIdIndexStore`. [3](#0-2) 
- Base58Check address encoding/decoding (`Commons.decodeFromBase58Check`, `Base58.decode`) is inherently case-sensitive per RFC alphabet, and any wrong-case input simply fails decode/checksum validation rather than silently mapping to a different storage key. [4](#0-3) 

No reachable path from an anonymous RPC/broadcast transaction/contract call was found where an address or identifier is stored with one casing and later looked up with a different (normalized) casing, causing state to become inaccessible or misattributed.
