### Title
Fee-only transaction prioritization allows congestion-based starvation of consensus-critical `VoteWitnessContract` transactions - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.generateBlock` selects transactions for a block purely by a fee-based `order` field (or plain FIFO if sorting is disabled) with no awareness of transaction *type*. There is no mechanism analogous to a prioritized `CheckTx`/mandatory-transaction class that guarantees inclusion of consensus-critical messages such as `VoteWitnessContract`, which feed directly into the DPoS maintenance cycle that elects/re-elects the active Super Representative (SR) set. This mirrors the Umee oracle-vote starvation bug class: system-critical governance messages compete on equal (or worse) footing with ordinary value-transfer transactions and can be crowded out during congestion, corrupting or delaying consensus-affecting state (the SR election result) rather than merely delaying a price feed.

### Finding Description
Block packing iterates `pendingTransactions`/`rePushTransactions` and orders them with `downComparator`, which sorts strictly by `TransactionCapsule.getOrder()`—set to the transaction fee only *after* it has already been executed once (`trxCap.setOrder(transactionInfo.getFee())`, `Manager.java:1611`). When `Args.getInstance().isOpenTransactionSort()` is `false` (the non-priority path), the queues are plain `LinkedBlockingQueue`s and transactions are packed strictly FIFO with zero prioritization (`Manager.java:505-511`, `Manager.java:1665-1688`).

In either mode, `generateBlock` has no logic that recognizes or favors `VoteWitnessContract` (or any other consensus-relevant contract type) over ordinary transactions: [1](#0-0) 

The only special-casing present in the packing loop concerns shielded transaction counts, multi-sign accounts, block-size limits, and (post-fork) rejection of `ExchangeTransactionContract`—none of which give priority to governance-critical votes: [2](#0-1) 

`VoteWitnessContract` transactions accumulate `Votes` in the `VotesStore` via `VoteWitnessActuator.countVoteAccount`, and these accumulated votes are only consumed and applied to the active SR set once per maintenance cycle in `MaintenanceManager.doMaintenance`, gated by `applyBlock`'s check of `consensusDelegate.getNextMaintenanceTime() <= blockTime`: [3](#0-2) [4](#0-3) 

If a `VoteWitnessContract` transaction is not packed into a block before the maintenance boundary because the mempool is flooded with higher-fee (or simply earlier-submitted, in FIFO mode) unrelated transactions, that vote is entirely excluded from the vote tally for the current cycle (`countVote` in `MaintenanceManager.java:165-194` only counts votes that made it into `VotesStore` before `doMaintenance()` runs). This is structurally identical to the Umee finding: a message whose timely, guaranteed inclusion is required for correct system-wide state transition (SR election here; exchange-rate update there) has no priority path and can be starved by ordinary transaction volume.

### Impact Explanation
An attacker who congests the network (e.g., floods it with many small, valid, fee-bearing transactions) around a maintenance-time boundary can prevent legitimate `VoteWitnessContract` transactions from validators/voters from being packed in time. This can bias or delay SR set changes, effectively let an attacker manipulate which witnesses become/remain active for a cycle by selectively starving the votes of others, or cause repeated cycles where votes are dropped and never re-counted (since the FIFO/fee packing gives no guarantee of eventual inclusion within a specific window). This affects consensus-level state (governance and reward eligibility of SRs), which is a systemic integrity issue, not merely a UX inconvenience.

### Likelihood Explanation
Likelihood is bounded by the cost and reliability of congesting the network precisely around the maintenance boundary (default 6-hour cycle) and by the fact that vote transactions themselves pay bandwidth/energy costs so they aren't inherently "free" to include. However, no special engineering effort is required to exploit the current packing algorithm — an attacker only needs to submit a volume of higher-priority-by-fee (or earlier, in FIFO mode) transactions during the target window; the deficiency is a design gap in `generateBlock`'s scheduling logic rather than a rare edge case.

### Recommendation
- Short term: Extend `generateBlock`'s transaction-selection logic in `Manager.java` to grant an explicit priority class to consensus/governance-critical contract types (e.g., `VoteWitnessContract`, `WitnessUpdateContract`, `WitnessCreateContract`) similar to how `isShieldedTransaction`/`isMultiSignTransaction` are special-cased, ensuring they are packed ahead of ordinary transfers when present in the pool, especially as blocks approach `nextMaintenanceTime`.
- Long term: Decouple SR-election-affecting vote accounting from raw block-inclusion order — e.g., allow a grace/carry-over mechanism so that valid votes broadcast before the maintenance boundary but not yet included are still counted for that cycle, removing the hard dependency on precise block-packing order for consensus-affecting outcomes.

### Proof of Concept
Conceptual reachable path (no privileged access required):
1. Attacker broadcasts a large number of ordinary, fee-bearing (or simply well-timed if `isOpenTransactionSort=false`) transactions to full nodes shortly before the next maintenance boundary (`consensusDelegate.getNextMaintenanceTime()`), filling `pendingTransactions`/block-size budget as processed in `generateBlock` (`Manager.java:1667-1714`).
2. A legitimate voter's `VoteWitnessContract` transaction, submitted via normal broadcast RPC, sits in the same queue without any type-based priority and is postponed (`postponedTrxCount++`, `Manager.java:1712`) past the block(s) preceding `nextMaintenanceTime`.
3. When `MaintenanceManager.applyBlock` detects `nextMaintenanceTime <= blockTime`, it calls `doMaintenance()`, which tallies only votes already present in `VotesStore` (`countVote`, `MaintenanceManager.java:165-194`); the starved vote is excluded from this cycle's SR count, permanently for that cycle since the vote's effect is time-boxed to the maintenance window.

I was not able to fully verify the exact default value/initialization of `TransactionCapsule.order` or the default value of `isOpenTransactionSort` due to index truncation on those specific fields; a Devin session with full repository access would be needed to confirm these defaults precisely, though the packing-loop behavior itself (lines 1667–1714 of `Manager.java`) and the maintenance-boundary vote-counting logic are confirmed directly from source.

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }

  public void applyBlock(BlockCapsule blockCapsule) {
    long blockNum = blockCapsule.getNum();
    long blockTime = blockCapsule.getTimeStamp();
    long nextMaintenanceTime = consensusDelegate.getNextMaintenanceTime();
    boolean flag = consensusDelegate.getNextMaintenanceTime() <= blockTime;
    if (flag) {
      if (blockNum != 1) {
        updateWitnessValue(beforeWitness);
        beforeMaintenanceTime = nextMaintenanceTime;
        doMaintenance();
        updateWitnessValue(currentWitness);
      }
      consensusDelegate.updateNextMaintenanceTime(blockTime);
      if (blockNum != 1) {
        //pbft sr msg
        pbftManager.srPrePrepare(blockCapsule, currentWitness,
            consensusDelegate.getNextMaintenanceTime());
      }
    }
    consensusDelegate.saveStateFlag(flag ? 1 : 0);
    //pbft block msg
    if (blockNum == 1) {
      nextMaintenanceTime = consensusDelegate.getNextMaintenanceTime();
    }
    pbftManager.blockPrePrepare(blockCapsule, nextMaintenanceTime);
  }
