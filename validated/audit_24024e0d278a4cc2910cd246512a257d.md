### Title
Non-hardened `ExchangeWithdrawActuator` accepts imprecise withdrawal amounts due to floating-point ratio approximation - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The report's bug class is: a function that approximates a conversion/exchange rate (EIP-4626 `convertToAssets`) is used to authorize a state-changing operation, and the approximation can return "too much," breaking the invariant that the operation should be exact/conservative. The java-tron analog is the `bancor`-style AMM exchange pool's proportional withdraw/inject logic, which computes the exact result with `BigInteger`/`BigDecimal` but then re-validates precision using **double-precision floating point** arithmetic when the `allowHardenExchangeCalculation` chain parameter is disabled (the legacy/default code path).

### Finding Description
`ExchangeWithdrawActuator.doValidate()` computes the exact "another token" quantity to release using integer division: `bigSecondTokenBalance.multiply(bigTokenQuant).divideToIntegralValue(bigFirstTokenBalance).longValueExact()` [1](#0-0) .

It then attempts to bound how imprecise this floor-division result may be compared to the "true" ratio. When `allowHarden()` is true, this check uses `BigDecimal` with explicit `RoundingMode.HALF_UP` and a `BigDecimal` comparison [2](#0-1) . But when hardened calculation is **not** enabled, the same check instead converts to a Java `double` and computes the remainder ratio with plain floating-point division/subtraction: `bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance, 4, BigDecimal.ROUND_HALF_UP).doubleValue() - anotherTokenQuant` followed by `remainder / anotherTokenQuant > 0.0001` [3](#0-2) . The symmetric branch for the other token has the identical double-based check [4](#0-3) .

This mirrors the root cause pattern in the external report: an approximate/rounded conversion computation (double-precision `doubleValue()` arithmetic, which is not exact for large `BigDecimal`/`BigInteger` pool balances) is used as the sole gate deciding whether a withdrawal ratio is "precise enough" to be accepted, instead of using exact integer/BigDecimal arithmetic throughout. Because `double` has only ~15-17 significant decimal digits of precision, for sufficiently large pool balances (`firstTokenBalance`/`secondTokenBalance`, which are bounded by `getExchangeBalanceLimit()` but can still be very large, e.g. up to `10^18`-scale token quantities used elsewhere in the same file, see `1_000_000_000_000_000_000L` in `ExchangeProcessor`/`SafeExchangeProcessor` [5](#0-4) ), the `doubleValue()` conversion of the `BigDecimal` product/quotient silently loses precision, allowing the imprecision check to pass even though the actual floor-divided `anotherTokenQuant` deviates from the true proportional value by more than the intended `0.0001` tolerance.

The existence of a parallel, more rigorous `BigDecimal`-only "hardened" code path (guarded by the `allowHardenExchangeCalculation` dynamic property, exposed via `AbstractExchangeActuator.allowHarden()` and `DynamicPropertiesStore`) confirms that the java-tron team itself recognized this precision-loss risk in the legacy double-based check and added a fix analogous to the report's `previewRedeem` mitigation - but only for chains that have activated the corresponding hard fork/parameter [6](#0-5) .

### Impact Explanation
On chains/networks where `allowHardenExchangeCalculation` has not been activated (legacy behavior, still reachable as it's a runtime-configurable proposal, not a hard requirement), an exchange creator broadcasting `ExchangeWithdrawContract` (and symmetrically `ExchangeInjectContract`, which has no precision-tolerance check at all) can craft `tokenQuant` values such that the floating-point precision check under-detects deviation from the true proportional ratio, letting them extract or inject a slightly-off, but exchange-invariant-breaking, quantity of the paired token repeated over many transactions. This corrupts the constant-ratio invariant of the pool (`firstTokenBalance`/`secondTokenBalance`), degrading pricing accuracy for the AMM-style Bancor exchange used by `ExchangeTransactionActuator` for all other traders, i.e., asset/accounting corruption within the exchange subsystem.

### Likelihood Explanation
The withdraw path is only usable by the exchange's own creator (`accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` [7](#0-6) ), which is a normal, unprivileged on-chain account (anyone can create an exchange), reachable via a standard broadcast transaction — not a privileged/admin operation. Exploitability additionally depends on whether `allowHardenExchangeCalculation` is disabled on the target network and requires carefully chosen inputs to exploit the double-precision rounding gap repeatedly, which lowers but does not eliminate practical likelihood.

### Recommendation
Remove the double-based precision-tolerance branch entirely and always perform the imprecision check with `BigDecimal`/`BigInteger` exact arithmetic (as already done in the hardened path), regardless of the `allowHardenExchangeCalculation` flag, mirroring the report's recommendation to always use the exact/conservative computation rather than an approximate one.

### Proof of Concept
Not independently reproduced in this analysis; the vulnerable arithmetic path is demonstrated by the non-hardened `remainder`/`anotherTokenQuant` `double` computation at [3](#0-2) , contrasted with the exact `BigDecimal` hardened check at [2](#0-1) . Confirming actual exploitability with concrete numeric inputs that trigger double-precision rounding beyond the `0.0001` tolerance would require running the actuator with large `firstTokenBalance`/`secondTokenBalance` values, which is out of scope for static analysis alone.
