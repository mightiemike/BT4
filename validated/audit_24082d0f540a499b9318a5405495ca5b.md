### Title
Internal transaction hash omits `tokenInfo` and `sendAddress`, allowing hash collisions between TRC10 token transfers and TRX transfers - ([File: chainbase/src/main/java/org/tron/common/runtime/InternalTransaction.java])

### Summary
`InternalTransaction#getEncoded()` serializes only `parentHash`, `receiveAddress`, `data`, and `value`, and `getHash()` combines that with only the `nonce`. Because `sendAddress`, `note`, and `tokenInfo` are excluded from the hash input, two internal transactions that differ only in which asset was moved (TRX vs. a specific TRC10 `tokenId`) or in who the actual sender was can produce identical `getHash()` output.

### Finding Description
`getEncoded()` builds the raw byte buffer strictly from `parentHash`, `receiveAddress`, `data`, and `value`: [1](#0-0) 

`getHash()` then only appends the `nonce` bytes to that encoding before hashing with `Hash.sha3`: [2](#0-1) 

The constructor comment explicitly acknowledges that the single `value` field is overloaded to represent either a TRX call value or a TRC10 token amount, with the actual token identity carried out-of-band in `tokenInfo`: [3](#0-2) 

Since `tokenInfo` (and `sendAddress`, `note`) are stored on the object but never fed into `getEncoded()`/`getHash()`, two `InternalTransaction` instances built by `ProgramResult.addInternalTransaction(...)` (invoked from `Program#addInternalTx`) with the same `parentHash`, `receiveAddress`, `data`, `value`, and `nonce` but different `tokenInfo` maps (e.g., one from a `CALLTOKEN` moving TRC10 tokenId `"123"` and one from a plain `CALL` moving TRX) will yield identical hashes: [4](#0-3) [5](#0-4) 

`TransactionUtil.buildInternalTransaction` (used to build the externally-exported `Protocol.InternalTransaction`) uses `it.getHash()` as the identifying `hash` field while separately serializing the (excluded-from-hash) `tokenInfo` map into `CallValueInfo` entries: [6](#0-5) 

The event-log pipeline (`TransactionLogTriggerCapsule.getInternalTransactionList`) similarly emits `hash` and `tokenInfo` as separate, independently-derived fields: [7](#0-6) 

No validation logic anywhere ties `hash` uniqueness to `tokenInfo`/`sendAddress` content, so nothing prevents this collision from occurring when the other fields (`parentHash`, `receiveAddress`, `data`, `value`, `nonce`) coincide.

### Impact Explanation
Any downstream consumer (bridge, exchange, indexer) that keys settlement or crediting decisions off the internal-transaction `hash` exported via `buildInternalTransaction` or the event trigger pojo cannot distinguish a TRC10 transfer of a given `tokenId`/amount from a TRX transfer of the numerically identical `value`, if the other encoded fields match. This is a genuine accounting-ambiguity flaw: the hash is supposed to uniquely identify a specific value-transfer event, but its preimage does not include the asset identity (`tokenInfo`) or the true sender (`sendAddress`), breaking the deterministic/unambiguous accounting invariant for the exported trace format.

### Likelihood Explanation
Reaching this requires only that an attacker's own contract triggers two internal calls (one `CALLTOKEN`, one plain `CALL`, or two `CALLTOKEN`s with different `tokenId`) that happen to share `parentHash` (same immediate caller), `receiveAddress` (same callee), `data`, `value`, and `nonce`. This is fully within reach of an unprivileged contract author, since `data`, `value`, and target address are attacker-chosen in both call types; the main open question — not fully verifiable from the reviewed code — is how `nonce` is assigned per internal call by `Program.java`. If `nonce` is a deterministic per-call-frame counter (as opposed to something incorporating the token id or send address), two independently-issued internal calls in different branches of execution, or across two separate transactions replaying the same call pattern, can realistically collide on all encoded fields, making the collision structurally reproducible rather than probabilistic.

### Recommendation
Include `sendAddress`, `note`, and a canonical serialization of `tokenInfo` (sorted by `tokenId`) in the byte buffer built by `getEncoded()` before hashing, so that `getHash()` is a true, collision-resistant identifier of the exact value-transfer semantics (asset type, sender, amount, receiver, and call data).

```java
import static org.junit.Assert.assertNotEquals;
import java.util.HashMap;
import java.util.Map;
import org.junit.Test;
import org.tron.common.runtime.InternalTransaction;

public class InternalTransactionHashCollisionTest {

  @Test
  public void tokenTransferAndTrxTransferShouldNotCollide() {
    byte[] parentHash = new byte[]{1, 2, 3};
    byte[] sendAddressA = new byte[]{0x41};
    byte[] sendAddressB = new byte[]{0x42}; // different sender
    byte[] receiveAddress = new byte[]{9, 9};
    byte[] data = new byte[]{7, 7, 7};
    long value = 100L;
    long nonce = 0L;

    Map<String, Long> trc10TokenInfo = new HashMap<>();
    trc10TokenInfo.put("1000123", 100L); // TRC10 transfer of tokenId 1000123

    Map<String, Long> trxTokenInfo = new HashMap<>(); // empty -> plain TRX transfer

    InternalTransaction tokenTx = new InternalTransaction(
        parentHash, 1, 0, sendAddressA, receiveAddress, value, data, "call", nonce, trc10TokenInfo);
    InternalTransaction trxTx = new InternalTransaction(
        parentHash, 1, 0, sendAddressB, receiveAddress, value, data, "call", nonce, trxTokenInfo);

    // Expected (per accounting invariant): hashes must differ because these
    // represent transfers of different assets from different senders.
    // Actual: hashes are identical because getEncoded()/getHash() ignore
    // sendAddress and tokenInfo.
    assertNotEquals(
        "Internal tx hash must not collide across different assets/senders",
        org.bouncycastle.util.encoders.Hex.toHexString(tokenTx.getHash()),
        org.bouncycastle.util.encoders.Hex.toHexString(trxTx.getHash()));
  }
}
```
Expected result on current code: the assertion fails, proving `getHash()` produces identical output for a TRC10 token transfer and a TRX transfer that differ only in `sendAddress`/`tokenInfo`. As a differential check, also assert that `TransactionUtil.buildInternalTransaction(tokenTx).getHash()` equals `TransactionUtil.buildInternalTransaction(trxTx).getHash()` while their `CallValueInfo` lists differ, confirming the exported trace exhibits the same ambiguity.

```java
  public final byte[] getHash() {
    if (!isEmpty(hash)) {
      return Arrays.copyOf(hash, hash.length);
    }

    byte[] plainMsg = this.getEncoded();
    byte[] nonceByte;
    nonceByte = Longs.toByteArray(nonce);
    byte[] forHash = new byte[plainMsg.length + nonceByte.length];
    System.arraycopy(plainMsg, 0, forHash, 0, plainMsg.length);
    System.arraycopy(nonceByte, 0, forHash, plainMsg.length, nonceByte.length);
    this.hash = Hash.sha3(forHash);
    return Arrays.copyOf(hash, hash.length);
  }
```

```java
  public byte[] getEncoded() {
    if (protoEncoded != null) {
      return protoEncoded.clone();
    }
    byte[] parentHashArray = parentHash.clone();

    if (parentHashArray == null) {
      parentHashArray = EMPTY_BYTE_ARRAY;
    }
    byte[] valueByte = Longs.toByteArray(this.value);
    byte[] raw = new byte[parentHashArray.length + this.receiveAddress.length + this.data.length
        + valueByte.length];
    System.arraycopy(parentHashArray, 0, raw, 0, parentHashArray.length);
    System
        .arraycopy(this.receiveAddress, 0, raw, parentHashArray.length, this.receiveAddress.length);
    System.arraycopy(this.data, 0, raw, parentHashArray.length + this.receiveAddress.length,
        this.data.length);
    System.arraycopy(valueByte, 0, raw,
        parentHashArray.length + this.receiveAddress.length + this.data.length,
        valueByte.length);
    this.protoEncoded = raw;
    return protoEncoded.clone();
  }
```
