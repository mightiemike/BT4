### Title
Exchange (Bancor-style TRC10 AMM) liquidity provision/withdrawal uses manipulable on-chain spot reserve ratio, enabling value extraction from other liquidity providers - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
java-tron's built-in Exchange module (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) implements an on-chain Bancor-style AMM for TRC10 tokens/TRX. `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counterpart token amount for a liquidity add/remove strictly from the exchange's *current* reserve ratio (`firstTokenBalance`/`secondTokenBalance`) at the moment of execution, with no protection against the ratio having been just moved by a swap. This is structurally the same bug class as the reported Uniswap issue: a "spot price" read from a pool whose reserves can be shifted by an attacker-controlled trade immediately beforehand, then used to price a critical operation (here, liquidity withdrawal/injection) to the attacker's benefit and other LPs' loss.

### Finding Description
`ExchangeCapsule.transaction()` implements the Bancor relay-token swap math and mutates `firstTokenBalance`/`secondTokenBalance` in place [1](#0-0) , using `ExchangeProcessor`/`SafeExchangeProcessor` to compute swap output purely from current pool reserves [2](#0-1) .

`ExchangeWithdrawActuator.execute()` (and its `doValidate()`) determines `anotherTokenQuant` — the amount of the paired token an LP receives when withdrawing `tokenQuant` of one side — by directly multiplying the withdrawn quantity by the *current* `secondTokenBalance/firstTokenBalance` (or inverse) ratio read from the store at execution time: [3](#0-2) 

Similarly, `ExchangeInjectActuator.execute()` computes the required counterpart deposit the same way, from the live pool ratio at execution time: [4](#0-3) 

Neither actuator checks whether the pool ratio has deviated from some external/expected reference price, nor does it apply any time-weighting, slippage bound versus a prior state, or minimum-liquidity/price-impact guard beyond a raw balance cap (`getExchangeBalanceLimit`). The ratio used is exactly the kind of instantaneously-computed AMM spot price the external report warns about — the same mechanism the report calls "the result of a simulated swap, given the current state of the pools," which "can be easily manipulated."

An attacker can:
1. Submit an `ExchangeTransactionContract` swap that heavily skews `firstTokenBalance`/`secondTokenBalance` in the target exchange (using `ExchangeTransactionActuator`, which calls `ExchangeCapsule.transaction()` with no protection against the caller being the only party moving the whole pool) [5](#0-4) .
2. Immediately submit an `ExchangeWithdrawContract` for a small amount of the now-cheap side, and because `anotherTokenQuant` is computed from the freshly skewed ratio, receive a disproportionately large amount of the now-scarce/expensive side [6](#0-5) .
3. Reverse the initial swap (or let it settle) to restore the pool and pocket the extracted value, at the expense of the pool/other LPs' remaining balances.

Because these are separate transactions rather than a single atomic call, the attack does not require flash-loan-style atomicity within one tx — it only requires the attacker to control transaction ordering within the same block or accept normal block-interval risk, which is a materially different (and in some ways easier/harder, but still concretely exploitable) threat model than the Uniswap PoC. I was not able to fully confirm within the available tooling whether java-tron supports multiple contracts inside one atomic transaction (which would make the attack fully atomic like the Uniswap PoC); the `TransactionCapsule`/`Tron.proto` do define `contract` as a repeated field, but I could not verify from the indexed content whether the executor processes multiple contracts from unrelated actuators atomically as a single unit or whether same-block reordering/mining control is the realistic threat vector. This should be verified against the full source before finalizing severity.

### Impact Explanation
If reserve-ratio manipulation followed by inject/withdraw is confirmed exploitable within a single block (or by a block-producing witness who can order/insert transactions), an attacker can drain value from other liquidity providers in any TRC10/TRX Exchange pair, directly analogous to the reported impact (attacker profit, victims left with degraded position value). This affects real on-chain value (TRX and TRC10 token balances held in `AccountStore`), which is core accounting state, not a theoretical or mocked-only path.

### Likelihood Explanation
The `Exchange` feature is a long-standing, low-liquidity legacy AMM in java-tron (largely superseded by the `Market`/order-book contracts for new TRC10 trading), so real-world pools may have limited depth, which actually *increases* practical manipulability (thin pools are cheaper to move). However, exploitation requires either favorable transaction ordering within a block or being the block-producing witness, and is not a pure single-transaction atomic exploit like the Uniswap flash-loan PoC — I could not confirm from available context whether java-tron's transaction/contract model allows bundling swap + inject/withdraw + reverse-swap atomically in one transaction, which materially affects likelihood.

### Recommendation
- Do not price liquidity injection/withdrawal purely off the instantaneous `firstTokenBalance`/`secondTokenBalance` ratio; require the caller to specify a minimum/maximum acceptable counterpart amount (slippage bound) as already partially done via `tokenExpected` in `ExchangeTransactionActuator`, and extend equivalent bounds checks to `ExchangeInjectActuator`/`ExchangeWithdrawActuator`.
- Consider using a time-weighted average of the reserve ratio over multiple blocks rather than the instantaneous value for any calculation that determines value transferred to/from a caller.
- Audit whether same-block transaction ordering (especially witness-controlled ordering) can chain `ExchangeTransactionContract` + `ExchangeWithdrawContract`/`ExchangeInjectContract` to extract value, and add per-block or per-transaction price-impact caps on the Exchange if so.

### Proof of Concept
Conceptual (not verified end-to-end due to inability to confirm atomic multi-contract transaction support):
1. Attacker calls `ExchangeTransactionContract` selling a large amount of tokenA into the pool, skewing `firstTokenBalance`/`secondTokenBalance` heavily (via `ExchangeTransactionActuator` → `ExchangeCapsule.transaction()`).
2. In the same block (or immediately after, if ordering can be controlled), attacker calls `ExchangeWithdrawContract` for a small `tokenQuant` of tokenB; `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the now-skewed ratio [3](#0-2) , yielding an inflated amount of tokenA.
3. Attacker reverses the initial swap, restoring the pool ratio and realizing profit at the expense of remaining LPs' pool share value.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
