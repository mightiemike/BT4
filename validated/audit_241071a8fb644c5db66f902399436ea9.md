## Title
Protocol-treasury reward silently dropped when the treasury account is also an active validator - (File: `chain/epoch-manager/src/reward_calculator.rs`)

### Summary
`RewardCalculator::calculate_reward` computes a `HashMap<AccountId, Balance>` of "who gets how much" for an epoch. It first inserts the protocol-treasury's share, then iterates all validators and inserts their share under the *same* map, keyed by `account_id`. If the protocol treasury account happens to also be an active validator (i.e., it appears in `validator_block_chunk_stats`), the second `insert` silently **overwrites** the treasury entry with only the validator reward, discarding the treasury reward from the map — while the treasury reward is still counted in the returned total (`epoch_actual_reward`, i.e. `minted_amount`). Downstream, `update_validator_accounts` trusts this map to actually credit the account and explicitly skips a second credit "because the reward was already distributed above." The net effect: tokens are minted into total supply that are never credited to any account balance.

### Finding Description
In `chain/epoch-manager/src/reward_calculator.rs`:
```

...
for (account_id, stats) in validator_block_chunk_stats {
    ...
    res.insert(account_id, reward);
    epoch_actual_reward = epoch_actual_reward.checked_add(reward).unwrap();
}
``` [1](#0-0) [2](#0-1) 

`res` is a plain `HashMap<AccountId, Balance>`. The treasury entry is inserted at line 84. Then, for every validator (including the treasury account itself, if it is staking and thus present in `validator_block_chunk_stats`), line 142 does `res.insert(account_id, reward)` — this **replaces** rather than **adds to** the existing treasury entry when `account_id == protocol_treasury_account`. The treasury's `epoch_protocol_treasury` balance is silently lost from the map, even though `epoch_actual_reward` (the function's second return value, used as `minted_amount`) still correctly sums `epoch_protocol_treasury + Σ(validator rewards)` because that accumulation uses the local `reward` variable, not the map.

`minted_amount` feeds directly into `new_total_supply = prev.total_supply + minted_amount − balance_burnt` [3](#0-2) , so total supply is inflated by the full treasury amount. However, actual balance crediting relies on the corrupted map (`validator_rewards`) in `update_validator_accounts`:

```
if let Some(account_id) = &validator_accounts_update.protocol_treasury_account_id {
    // If protocol treasury stakes, then the rewards was already distributed above.
    if !validator_accounts_update.stake_info.contains_key(account_id) {
        ...
        let treasury_reward = *validator_accounts_update.validator_rewards.get(account_id)...;
        account.set_amount(account.amount().checked_add(treasury_reward)...);
        ...
    }
}
``` [4](#0-3) 

When `protocol_treasury_account_id` is present in `stake_info` (i.e., the treasury account is a currently-staked validator with a locked balance being tracked), the code assumes "the reward was already distributed above" via the earlier per-validator loop at [5](#0-4) . That earlier loop credits `locked` using `validator_accounts_update.validator_rewards.get(account_id)` — but that value is exactly the corrupted map entry from `calculate_reward`, i.e. only the *validator* reward, with the *treasury* reward silently dropped. So the treasury account's `locked` balance is increased only by its validator reward, never by its treasury share, while total supply was incremented by both.

### Impact Explanation
This breaks the fundamental protocol invariant that `total_supply == sum(all account balances)` and that `minted_amount` at every epoch boundary is fully and correctly credited somewhere (see the accounting invariant description at [6](#0-5) , which explicitly assumes minted tokens land as validator/treasury rewards). The `epoch_protocol_treasury` portion is permanently uncredited to any account — effectively lost/frozen funds from the treasury's perspective, while the chain's `total_supply` header field is inflated as if it had been distributed. This is a supply-accounting divergence rather than validator-balance theft, but it is a concrete, protocol-level invalid state transition: minted tokens vanish from the credited-balance ledger while still counted in `total_supply`.

### Likelihood Explanation
The condition requires only that `protocol_treasury_account` be one of the epoch's active/staked validators (present in both `validator_block_chunk_stats` and `stake_info`), which is a configuration/staking condition rather than a privileged code path — any chain (mainnet, testnet, or custom deployment) whose treasury account also participates as a validator hits this on every epoch boundary where that holds, deterministically and silently (no error, no panic, both honest nodes compute the same wrong-but-consistent result, so it would not be caught by state-root divergence detection between honest nodes — it is a systematic accounting bug baked into consensus).

### Recommendation
In `calculate_reward`, use `entry(...).and_modify(|r| *r = r.checked_add(reward).unwrap()).or_insert(reward)` (or equivalent) instead of a bare `insert` when adding each validator's reward, so that if `account_id == protocol_treasury_account`, the treasury and validator rewards are summed rather than one overwriting the other. Correspondingly, `update_validator_accounts` should not need to special-case "already distributed above" once the map is fixed to correctly aggregate both components under one key. Add a regression test with a validator account_id equal to `protocol_treasury_account` verifying the credited balance equals `epoch_protocol_treasury + validator_reward` and that it matches `minted_amount`.

### Proof of Concept
1. Configure/deploy a chain (e.g. via `setup_epoch_manager` test helper, as used in [7](#0-6) ) where `protocol_treasury_account` (e.g. `"near"`) is also one of the staked validators, with nonzero stake and normal block/chunk production.
2. Run one epoch to completion so `finalize_epoch` → `RewardCalculator::calculate_reward` executes [8](#0-7) .
3. Inspect the returned `HashMap`: the entry for `"near"` equals only the per-stake validator reward, not `epoch_protocol_treasury + validator_reward`.
4. Apply the resulting `ValidatorAccountsUpdate` via `update_validator_accounts` [9](#0-8)  and confirm the treasury/validator account's on-chain `locked`/`amount` increase is short by exactly `epoch_protocol_treasury`, while `minted_amount`/`total_supply` for the block still includes the full `epoch_protocol_treasury + validator_reward` sum (per `new_total_supply` computation at `core/primitives/src/block.rs:193`, cited in [3](#0-2) ).

    pub fn calculate_reward(
        &self,
        validator_block_chunk_stats: HashMap<AccountId, BlockChunkValidatorStats>,
        validator_stake: &HashMap<AccountId, Balance>,
        total_supply: Balance,
        _protocol_version: ProtocolVersion,
        epoch_duration: u64,
        online_thresholds: ValidatorOnlineThresholds,
        max_inflation_rate: Rational32,
    ) -> (HashMap<AccountId, Balance>, Balance) {
        let mut res = HashMap::new();
        let num_validators = validator_block_chunk_stats.len();
        let use_hardcoded_value = self.genesis_protocol_version == PROD_GENESIS_PROTOCOL_VERSION;
        let protocol_reward_rate = if use_hardcoded_value {
            Rational32::new_raw(1, 10)
        } else {
            self.protocol_reward_rate
        };
        let epoch_total_reward = Balance::from_yoctonear(
            (U256::from(*max_inflation_rate.numer() as u64)
                * U256::from(total_supply.as_yoctonear())
                * U256::from(epoch_duration)
                / (U256::from(self.num_seconds_per_year)
                    * U256::from(*max_inflation_rate.denom() as u64)
                    * U256::from(NUM_NS_IN_SECOND)))
            .as_u128(),
        );
        let epoch_protocol_treasury = Balance::from_yoctonear(
            (U256::from(epoch_total_reward.as_yoctonear())
                * U256::from(*protocol_reward_rate.numer() as u64)
                / U256::from(*protocol_reward_rate.denom() as u64))
            .as_u128(),
        );
        res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury);
        if num_validators == 0 {
            return (res, Balance::ZERO);
        }
        let epoch_validator_reward =
            epoch_total_reward.checked_sub(epoch_protocol_treasury).unwrap();
        let mut epoch_actual_reward = epoch_protocol_treasury;

### 3. Total-supply change per block
`new_total_supply = prev.total_supply + minted_amount − balance_burnt` (`core/primitives/src/block.rs:193`). `minted_amount` is `Some` only on the first block of an epoch, taken from the epoch info populated by `calculate_reward` (`chain/chain/src/chain.rs:2519`). `balance_burnt` is the sum of each included chunk's `prev_balance_burnt()` (`block.rs:152`). Thus inflation *adds* to supply once per epoch, and burnt fees *subtract* every block; the difference is net issuance.

## Invariants & failure modes
- **Non-negative supply arithmetic.** `new_total_supply` uses checked add/sub and panics on overflow/underflow (`block.rs:193`); a block whose `balance_burnt` exceeds `prev + minted` is impossible by construction.
- **Minted ≤ cap.** `epoch_actual_reward` ≤ `epoch_total_reward` because per-validator rewards are fractions of the pool and below-threshold validators earn 0 (`reward_calculator.rs:109`). Verified by `test_adjust_max_inflation` (`reward_calculator.rs:590`).
- **Burn price ≤ purchase price (post-`AccountCostIncrease`).** `min(purchase, block)` guarantees the receiver reward and refunds never mint new tokens or underflow (comment at `lib.rs:922`).
- **Refund penalty ≤ refund.** `gas_penalty_for_gas_refund` clamps to `min(penalty, gas_refund)` (`cost.rs:692`).
- **Gas-price bounds.** Always clamped to `[min_gas_price, max_gas_price]` and unchanged on skipped blocks (`block.rs:449`, `block.rs:471`).
- **Storage staking.** An account failing `check_storage_stake` and not zero-balance cannot transact / receive deposits that push it under the threshold: `LackBalanceForState` (`verifier.rs:347`, `verifier.rs:520`).
- **Contract reward requires a live account.** If the receiver account is gone at the end of execution, its reward is not credited and remains burnt (goes to validators) (`lib.rs:1008`).

    fn update_validator_accounts(
        &self,
        state_update: &mut TrieUpdate,
        validator_accounts_update: &ValidatorAccountsUpdate,
    ) -> Result<(), RuntimeError> {
        for (account_id, max_of_stakes) in &validator_accounts_update.stake_info {
            let account = get_account(state_update, account_id)?;
            // An uninitialized account has no `locked` field, so none of this applies
            // and it is skipped. The only way it could appear in stake_info is when a
            // validator deletes their account and re-creates in an uninitialized state.
            // None of the checked values could be positive in such case. The check is
            // defense in depth, so that minted tokens do not leak from the supply if
            // this path ever becomes reachable.
            if account.as_ref().is_some_and(|account| !account.is_initialized()) {
                let rewards = &validator_accounts_update.validator_rewards;
                let reward = *rewards.get(account_id).unwrap_or(&Balance::ZERO);
                let proposals = &validator_accounts_update.last_proposals;
                let last_proposal = *proposals.get(account_id).unwrap_or(&Balance::ZERO);
                if *max_of_stakes > Balance::ZERO
                    || reward > Balance::ZERO
                    || last_proposal > Balance::ZERO
                {
                    return Err(StorageError::StorageInconsistentState(format!(
                        "FATAL: staking invariant does not hold. Uninitialized account \
                         {account_id} can hold no locked balance: max of stakes \
                         {max_of_stakes}, reward {reward}, last proposal {last_proposal}"
                    ))
                    .into());
                }
                continue;
            }
            if let Some(mut account) = account {
                if let Some(reward) = validator_accounts_update.validator_rewards.get(account_id) {
                    tracing::debug!(target: "runtime", %account_id, %reward, locked = %account.locked(), "account adding reward to stake");
                    let locked = account.locked().checked_add(*reward).ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow("update_validator_accounts".into())
                    })?;
                    account.set_locked(locked).or_inconsistent_state(account_id)?;
                }

                tracing::debug!(target: "runtime",
                       %account_id, locked = %account.locked(), %max_of_stakes,
                       "account stake and max of stakes"
                );
                if account.locked() < *max_of_stakes {
                    return Err(StorageError::StorageInconsistentState(format!(
                        "FATAL: staking invariant does not hold. \
                         Account stake {} is less than maximum of stakes {} in the past three epochs",
                        account.locked(),
                        max_of_stakes)).into());
                }
                let last_proposal = *validator_accounts_update
                    .last_proposals
                    .get(account_id)
                    .unwrap_or(&Balance::ZERO);
                let return_stake = account
                    .locked()
                    .checked_sub(max(*max_of_stakes, last_proposal))
                    .ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - return stake".into(),
                        )
                    })?;
                tracing::debug!(target: "runtime", %account_id, %return_stake, "account return stake");
                let locked = account.locked().checked_sub(return_stake).ok_or_else(|| {
                    RuntimeError::UnexpectedIntegerOverflow(
                        "update_validator_accounts - set_locked".into(),
                    )
                })?;
                account.set_locked(locked).or_inconsistent_state(account_id)?;
                account.set_amount(account.amount().checked_add(return_stake).ok_or_else(
                    || {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - set_amount".into(),
                        )
                    },
                )?);

                set_account(state_update, account_id.clone(), &account);
            } else if *max_of_stakes > Balance::ZERO {
                // if max_of_stakes > 0, it means that the account must have locked balance
                // and therefore must exist
                return Err(StorageError::StorageInconsistentState(format!(
                    "Account {} with max of stakes {} is not found",
                    account_id, max_of_stakes
                ))
                .into());
            }
        }

        if let Some(account_id) = &validator_accounts_update.protocol_treasury_account_id {
            // If protocol treasury stakes, then the rewards was already distributed above.
            if !validator_accounts_update.stake_info.contains_key(account_id) {
                let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
                    StorageError::StorageInconsistentState(format!(
                        "Protocol treasury account {} is not found",
                        account_id
                    ))
                })?;
                let treasury_reward = *validator_accounts_update

                    .get(account_id)
                    .ok_or_else(|| {
                        StorageError::StorageInconsistentState(format!(
                            "Validator reward for the protocol treasury account {} is not found",
                            account_id
                        ))
