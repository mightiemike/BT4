### Title
Merchant Custom App admin authentication builds the Admin session from an unauthenticated `shop` query parameter - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts])

### Summary
For apps using `AppDistribution.ShopifyAdmin` (merchant custom apps) with `isEmbeddedApp: false`, `getSessionTokenContext` takes the `shop` value directly from the request's unauthenticated `shop` URL query parameter and passes it straight to `MerchantCustomAuth.authenticate`, which builds an `Admin` session with `api.session.customAppSession(shop)` and the app's single statically configured `adminApiAccessToken`. This is structurally the same bug class as the reported `depositFor` issue: a privileged/identity-bearing operation is driven by a caller-supplied value instead of a value derived from a verified credential (session token / OAuth cookie), rather than always operating on the authenticated identity.

### Finding Description
In the token-context resolution for the admin auth strategy: [1](#0-0) 

when `config.isEmbeddedApp` is `false` (the case for merchant custom apps), the code reads `shop` directly from `url.searchParams.get('shop')` with no signature, HMAC, or session-token verification tying that value to the caller. This `shop` is then passed unmodified into the strategy: [2](#0-1) 

The `MerchantCustomAuth` strategy takes this attacker-influenced `shop` and constructs a full `Session`/`Admin` API context using the app's single, statically configured `adminApiAccessToken`, without any check that this `shop` matches the shop the token was actually issued for: [3](#0-2) 

The only shop/host validation path, `validateShopAndHostParams`, is gated entirely on `config.isEmbeddedApp`, so it is skipped for merchant custom apps: [4](#0-3) 

The only sanitation that does occur happens inside `customAppSession`, which calls `sanitizeShop` to ensure a syntactically valid myshopify-style domain, but does not verify that this domain is the one the configured token belongs to: [5](#0-4) 

This mirrors the report's root cause: using a caller-controlled identity/target parameter (`_for` in the Solidity report, `shop` here) for a privileged operation (transferring funds / issuing an authenticated Admin API session and outbound request) instead of deriving that identity from the verified caller (`msg.sender` / a validated session token or OAuth-issued cookie).

### Impact Explanation
An anonymous caller can hit the app's admin loader/action with an arbitrary `?shop=<other-shop>.myshopify.com` value. The app will build an `Admin` API client and issue outbound Admin API requests to that shop's domain, carrying the app's real `adminApiAccessToken` in the request. Because Shopify's servers ultimately validate that the access token belongs to the specified shop, this cannot be leveraged to read another merchant's data (Shopify will reject the mismatched token/shop pair), which limits real-world impact — consistent with the original report's own note that impact is limited (inconvenience/functional confusion rather than data exposure). However, it still represents an authentication-context bug: shop-scoped logic (logging, billing, redirect helpers, per-shop context) throughout `authenticateAdmin` is driven off of unauthenticated input rather than a value cryptographically tied to the caller for the merchant-custom-app path.

### Likelihood Explanation
Trivial to trigger — merchant custom apps are non-embedded, so this code path is reached directly by any anonymous HTTP request to the app with a `shop` query parameter, no OAuth flow, no session token, and no HMAC needed.

### Recommendation
For the `AppDistribution.ShopifyAdmin` (merchant custom app) path, do not trust `url.searchParams.get('shop')` as the effective shop identity for building the `Admin` session. Instead, bind the accepted `shop` value to the shop configured for the app's `adminApiAccessToken` (e.g., validate it against a configured/expected shop, or derive it from a verified source such as a signed cookie/session established by the app's own login flow) before calling `customAppSession`, mirroring how the embedded path derives `shop` only after `validateSessionToken` succeeds.

### Proof of Concept
1. Deploy a merchant custom app (`distribution: AppDistribution.ShopifyAdmin`, `isEmbeddedApp: false`, configured with `adminApiAccessToken` for `real-shop.myshopify.com`).
2. As an anonymous user, send `GET https://app.example.com/app?shop=other-shop.myshopify.com`.
3. Observe that `getSessionTokenContext` returns `shop = "other-shop.myshopify.com"` with no signature/session-token check, and `MerchantCustomAuth.authenticate` builds a session/`Admin` context for `other-shop.myshopify.com` using the app's real access token, causing the app to issue an Admin API request to `other-shop.myshopify.com/admin/...` carrying the token (Shopify rejects it server-side, but the app's shop-scoped logic executed on unauthenticated attacker input).

  request: Request,

    const url = new URL(request.url);

export function customAppSession(config: ConfigInterface) {
  return (shop: string): Session => {
    return new Session({
      id: '',
      shop: `${sanitizeShop(config)(shop, true)}`,
      state: '',
      isOnline: false,
    });
  };
