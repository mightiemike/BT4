Comment on line 90 explicitly says: `// Step 4: Deduct gas fees regardless of success/failure. If deduction fails, return error so the entire Cosmos tx rolls back (including EVM state).` This is the code's own stated assumption — that returning an error from the message handler rolls back the `CallUEAExecutePayload` EVM state written in Step 3. `ExecutePayloadV2` (`x/uexecutor/keeper/execute_payload.go`) explicitly does **not** rely on that assumption — it wraps the EVM call and the fee deduction in a manual `sdkCtx.CacheContext()` / `writeCache()` pair, with a comment stating this "closes the free-execution gap when the UEA has no native UPC to cover gas." That defensive pattern only makes sense if committed EVM state (via `DerivedEVMCall(commit=true, ...)`) is **not** guaranteed to be rolled back by an ordinary Go `error` return from the Cosmos message handler — EVM state commits and the Cosmos SDK's branched multistore are two different commit mechanisms in the cosmos-evm fork, and `DerivedEVMCall` may finalize EVM-side state independently of whether the surrounding SDK message ultimately errors.

The message actually routed by `MsgServer.ExecutePayload` (`x/uexecutor/keeper/msg_server.go:43-55` → `x/uexecutor/keeper/msg_execute_payload.go:16`) is the **unguarded** `ExecutePayload`, not `ExecutePayloadV2`. If the underlying commit semantics don't roll back on error (which is exactly what V2's cache-wrap is defending against), an attacker can call `MsgExecutePayload` against a UEA holding just enough native `upc` to look non-zero (satisfying the auto-deploy gate at line 61) but insufficient to cover gas, causing `DeductGasFeesFromReceipt` to fail at `DeductAndBurnFees` (insufficient balance) while `CallUEAExecutePayload`'s value transfer / contract call already committed for free.

I could not fully verify whether `DerivedEVMCall`'s EVM-side commit is truly independent of the SDK's per-message rollback (that requires reading the forked `cosmos/evm` `DerivedEVMCall` implementation, which is outside this indexed repo), so I cannot assert with certainty that state actually survives the error return in `ExecutePayload`. Given this uncertainty and that `x/uexecutor` itself treats the same pattern as a known "free-execution gap" worth explicitly guarding against in one sibling function but not the other, I'm flagging this as the most concrete, reachable analog to the M-10 pattern (an alternate/duplicate code path lacking a solvency-style invariant that a sibling path enforces), while being explicit about the verification gap.

### Title
Unguarded `ExecutePayload` message-handler path skips the fee/EVM-state atomicity guard present in `ExecutePayloadV2` - (File: x/uexecutor/keeper/msg_execute_payload.go)

### Summary
`x/uexecutor` has two implementations of UEA payload execution: `ExecutePayload` (`msg_execute_payload.go`, wired to the live `MsgExecutePayload` gasless message) and `ExecutePayloadV2` (`execute_payload.go`, apparently unused by any message handler in this codebase). `ExecutePayloadV2` explicitly wraps `CallUEAExecutePayload` + `DeductGasFeesFromReceipt` in a `CacheContext`/`writeCache()` pair specifically "to close the free-execution gap when the UEA has no native UPC to cover gas." `ExecutePayload` — the path actually reachable by any unprivileged user via `MsgExecutePayload` — instead calls `CallUEAExecutePayload` directly on `sdkCtx` and merely returns an error from `DeductGasFeesFromReceipt` failures, relying on an unverified assumption (stated in its own comment) that this error causes a full rollback of prior EVM state changes.

### Finding Description
- `CallUEAExecutePayload` (`x/uexecutor/keeper/evm.go:156-193`) invokes `evmKeeper.DerivedEVMCall(..., commit=true, ...)`, which per `DERIVED_TRANSACTIONS.md` produces a real EVM transaction with a real receipt — i.e., genuine EVM-side commit semantics distinct from the Cosmos SDK KVStore branch.
- `ExecutePayload` (`msg_execute_payload.go:87-97`) calls this directly against `sdkCtx`, then calls `DeductGasFeesFromReceipt` (`fees.go:97-148`), which fails with "insufficient gas" if the UEA's native `upc` balance is below the computed gas cost (`DeductAndBurnFees` → `SendCoinsFromAccountToModule`).
- `ExecutePayloadV2` (`execute_payload.go:35-56`) explicitly avoids trusting that a returned error rolls back the EVM call by running both steps inside a local `cacheCtx`/`writeCache()` block, only committing if both the EVM call and fee deduction succeed.
- The pre-check at `msg_execute_payload.go:57-67` only requires the UEA to hold a *non-zero* balance to permit auto-deploy/execution — it does not verify the balance is sufficient to cover the payload's gas cost before executing.

### Impact Explanation
If EVM state committed via `DerivedEVMCall(commit=true)` is not automatically discarded by the surrounding Cosmos message handler returning a Go `error` (which is exactly the scenario `ExecutePayloadV2`'s cache-wrap defends against), an unprivileged attacker can execute arbitrary UEA-authorized payloads (fund transfers, contract calls, state changes reachable through the UEA) while paying zero gas fee, since the `DeductGasFeesFromReceipt` failure only errors the Cosmos message without a corresponding EVM rollback. This is unauthorized module-originated EVM execution / broken gas-fee accounting reachable by any unprivileged user submitting a gasless `MsgExecutePayload`.

### Likelihood Explanation
Reachability requires only: (1) a UEA holding a non-zero but gas-insufficient native balance (attacker controls this, e.g., by funding just above zero or draining it down after a prior payload), and (2) submitting `MsgExecutePayload` (gasless, permissionless per `app/txpolicy/gasless.go`). No privileged role, TSS, or validator collusion is needed. The only uncertainty is whether the underlying `cosmos/evm` fork's `DerivedEVMCall` commit is genuinely independent of the SDK's per-message atomic rollback — this cannot be confirmed from the indexed repository content alone (the fork's implementation lives in a separate `replace`d module), which is why `ExecutePayloadV2`'s defensive comment is the strongest available evidence that this is a known, real risk class the team explicitly engineered around in one path but left unguarded in the other.

### Recommendation
Route `MsgExecutePayload` through the same cache-context pattern as `ExecutePayloadV2` (or make `ExecutePayload` call `ExecutePayloadV2` internally) so that `CallUEAExecutePayload`'s EVM state changes and `DeductGasFeesFromReceipt` commit atomically together, never independently. Additionally, verify the UEA's balance is sufficient to cover the payload's declared `MaxFeePerGas * GasLimit` before executing, not merely non-zero.

### Proof of Concept
1. Attacker creates/derives a UEA and funds it with a small non-zero `upc` balance (e.g., 1 unit) — sufficient to pass the `balance.Amount.Sign() == 0` check at `msg_execute_payload.go:61` (or the UEA already exists and its balance has been drawn down below gas cost from a prior execution).
2. Attacker submits `MsgExecutePayload` with a `UniversalPayload` calling an arbitrary function on a target contract through the UEA, with a valid `VerificationData` signature.
3. `ExecutePayload` calls `CallUEAExecutePayload` directly on `sdkCtx`; the EVM call executes and (per the theorized commit semantics) finalizes state.
4. `DeductGasFeesFromReceipt` fails with "insufficient gas" because the UEA balance can't cover `gasCost`.
5. `ExecutePayload` returns an error, but if `DerivedEVMCall`'s commit already persisted independently of the SDK message rollback, the payload's EVM effects (e.g., a token transfer or state mutation) survive while no gas fee was ever collected — a free, unauthorized EVM execution.
