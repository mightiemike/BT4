### Title
Missing domain separation (no chain ID / verifying-contract binding) in the `validatemultisign` precompile enables cross-chain and cross-contract signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (TVM address `0x0a`, exposed to Solidity as `validatemultisign(address, uint256, bytes32, bytes[])`) computes the message hash purely from `account address + permissionId + caller-supplied data`, with no chain identifier and no binding to the calling contract's address. This is the same root-cause pattern as the reported `Forwarder._verifySig` bug: the "domain" of the signature is left entirely to caller-supplied input instead of being enforced by the verifying code, which permits the same signature to be accepted for unrelated verification contexts (different chains or different consuming contracts) as long as the account, permission id, and `data` happen to match.

### Finding Description
`ValidateMultiSign.execute` builds the digest as: [1](#0-0) 

```
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(..., combine);
```

The recovered signer addresses are then weighted against the target account's on-chain `Permission` and compared to its threshold: [2](#0-1) 

Nothing in this hash construction includes:
- A chain identifier (TRON has no native `chainid`, but the genesis block hash / `ethChainId()` derivation shows the concept exists and is normally used to distinguish mainnet from Nile/Shasta/private chains — see `TronJsonRpcImpl.ethChainId`, which derives chain identity from the genesis block hash, something never mixed into this precompile's hash) [3](#0-2) .
- The address of the calling/verifying contract (`msg.sender`/`address(this)`), so the same signature is valid for *any* contract that constructs an identical `combine` value.
- Any nonce or deadline field enforced by the precompile itself — expiry/anti-replay is left entirely to whatever the calling contract chooses to embed in the opaque `data` parameter.

This is structurally identical to the reported issue: `Forwarder._verifySig` accepted `domainSeparator` as caller-supplied input rather than deriving it on-chain from `block.chainid`/verifying contract address, enabling replay across chains that share the same account/nonce state. Here, the TVM precompile provides *no* domain-separation primitive at all — the entire "salt and `block.chainid`" responsibility that the original report's sponsors explicitly called "imperative" is pushed onto every downstream Solidity author using `validatemultisign` to implement custom authorization/relay logic (gasless transfers, multisig wallets, etc.), with no protocol-level safety net or even a required convention.

By contrast, TRON's native transaction signature path (`TransactionCapsule.checkWeight` / `Wallet.getTransactionApprovedList`) signs over the full `raw_data`, which contains `ref_block_hash`/`ref_block_bytes`/`expiration`, and is checked against Tapos (`Manager.validateTapos`), giving it natural chain- and time-binding [4](#0-3) . The `validatemultisign` precompile has none of these protections, making it the strongest reachable analog to the reported bug class.

### Impact Explanation
Any unprivileged actor can deploy a TVM contract that calls `validatemultisign` to gate authorization/fund-moving logic (this is exactly how the precompile is advertised for use — building custom permission-based flows). If:
- the same account address/permission structure exists across two TRON networks (mainnet, Nile, Shasta, or a private fork) — which is guaranteed since TRON addresses are derived purely from the EC keypair and are identical across all TRON-compatible chains, or
- two different deployed contracts happen to accept the same `data` encoding for the same account/permissionId (a realistic outcome if developers follow common conventions, e.g. `abi.encode(to, amount)`),

then a signature obtained for use on one chain/contract is accepted verbatim on the other, since the precompile hash carries no domain-separating information. This can lead to unauthorized execution of privileged multisig-gated actions (e.g., approvals/transfers) on the second chain/contract — an authorization-bypass/replay impact consistent with the "unauthorized fund transfers" impact described in the original report, especially given TRON's real deployments across mainnet and multiple public testnets with identical account addressing.

### Likelihood Explanation
The precompile is reachable by any unprivileged party who can deploy or interact with a smart contract on TVM — no privileged role is required. Exploitation additionally requires a specific but common downstream pattern: a Solidity contract using `validatemultisign` for authorization without independently mixing in `block.chainid`/`address(this)`/a nonce into `data`. Since the precompile does not enforce or even encourage this via its interface, and TRON explicitly targets multi-network deployments (mainnet + Nile + Shasta, and permissioned private chains), this is a realistic, non-theoretical risk for the ecosystem of contracts built on this primitive.

### Recommendation
Harden the precompile itself rather than relying entirely on caller discipline:
1. Mix a chain-specific identifier (e.g., genesis block hash, as already used for `ethChainId()`) into the `combine` hash computed in `ValidateMultiSign.execute`.
2. Include the calling/verifying contract's address (`msg.sender` within the TVM context) in the hash so a signature is only valid for the specific contract it was intended for.
3. Document/require that consumers add explicit nonce and deadline fields inside `data`, and consider exposing a companion precompile or convention that already binds `data` to `(chainid, verifyingContract, nonce, deadline)` similar to EIP-712, to remove this footgun from application developers.

### Proof of Concept
1. Deploy the same private key-controlled account with an `Active` permission (threshold 1, single key `K`) on TRON Mainnet and on Nile Testnet (addresses are identical across networks by construction).
2. Deploy a contract `C` on both networks with identical bytecode that calls:
   `validatemultisign(accountAddr, permissionId, dataHash, [sig])` to gate a `transfer`.
3. Off-chain, sign `dataHash` once with key `K` — this produces a signature `sig` valid for `Sha256Hash(accountAddr || permissionId || dataHash)`, per [1](#0-0) .
4. Submit `sig` to contract `C` on Mainnet: the multisig check passes and the gated action executes.
5. Submit the identical `sig` to contract `C` on Nile Testnet (or to any other unrelated contract `C'` that reuses the same `dataHash`/`accountAddr`/`permissionId` convention): the multisig check passes again because the precompile hash never incorporated a chain or contract identifier, allowing the signature to be replayed outside its intended context — mirroring the cross-chain replay exploit path described in the original `Forwarder` report.
