### Title
Witness keystore password accepted via `--password` CLI argument, exposing it to shell history and `ps` - (File: `framework/src/main/java/org/tron/core/config/args/CLIParameter.java`)

### Summary
java-tron's `FullNode` startup accepts a `--password` command-line flag that is used to decrypt a witness's local keystore file. Like the eth2deposit-cli issue described in the report, this allows the password protecting the witness's BLS/ECDSA signing key to be captured in shell history, process listings (`ps`), and other OS-level command logging.

### Finding Description
`CLIParameter` defines a plaintext `--password` option intended to unlock a witness keystore file at node startup: [1](#0-0) 

This value flows into `WitnessInitializer.initFromKeystore`, which decrypts the witness keystore using the supplied password (or, only if empty, falls back to an interactive/masked prompt via `WalletUtils.inputPassword()`): [2](#0-1) 

When an operator launches the witness node with `java -jar FullNode.jar --witness -p <privkey> --password=<pwd> ...` (or via keystore mode), the plaintext password is passed as a normal argv entry. On POSIX systems this is recorded in the invoking user's shell history file, and for the duration of the process it is visible to any local user able to run `ps -ef`/`/proc/<pid>/cmdline`, exactly mirroring the eth2deposit-cli finding (TOB-EF-DEP, Figure 6.1/6.2). Note that the project's separate `Toolkit.jar keystore` subcommands (`KeystoreNew`, `KeystoreImport`, `KeystoreUpdate`) were hardened to require `--password-file` or an interactive TTY prompt instead of a raw CLI argument: [3](#0-2) 
but this hardening was not applied to the `CLIParameter.password` flag used at `FullNode` witness startup.

### Impact Explanation
A local attacker (or any process able to enumerate command lines / read shell history on the same host, e.g., a co-tenant, another OS user, or a compromised low-privilege process) can recover the plaintext password protecting the witness's signing keystore. Combined with read access to the keystore JSON file, this yields the witness's private key, enabling unauthorized block signing, impersonation, or theft of any funds/permissions tied to that key — a concrete authentication/key-compromise impact analogous to the original report's "Eve gains access to the sensitive keys."

### Likelihood Explanation
Requires local access to the machine running the witness node (shell history file, `/proc`, or `ps` visibility) — this is not remotely exploitable, but is a realistic operational risk for shared/cloud hosts, CI logs, or process managers that record startup commands (systemd journal, docker inspect, bash_history, etc.), which is a common real-world deployment pattern for witness/SR nodes.

### Recommendation
Deprecate/remove the ability to pass `--password` as a plaintext CLI argument for witness keystore unlocking in `CLIParameter`/`WitnessInitializer`. Replace it with the same pattern already used by the `Toolkit.jar keystore` commands: read from a `--password-file` (regular file, not a symlink, with restrictive permissions) or prompt interactively via `Console.readPassword`, as implemented in `KeystoreCliUtils.readPassword`. Long term, avoid ever accepting secrets as raw argv and document that operators should use file-based or environment-scoped secret injection instead.

### Proof of Concept
```bash
# Password appears in argv and is logged to shell history / visible via ps
java -jar FullNode.jar --witness --keystore-factory=false \
  --password="mySecretWitnessPassword" -c config.conf

# On another local session/user:
history | grep password
ps -ef | grep FullNode.jar
# Both reveal "mySecretWitnessPassword" in plaintext
```
This mirrors the exact class of vulnerability from the external report, ported to `CLIParameter.password` → `WitnessInitializer.initFromKeystore` in java-tron. [4](#0-3)

  static String readPassword(File passwordFile, PrintWriter err) throws IOException {
    if (passwordFile != null) {
      byte[] bytes = readRegularFile(passwordFile, MAX_FILE_SIZE, "Password file", err);
      if (bytes == null) {
        return null;
      }
      try {
        String password = WalletUtils.stripPasswordLine(
            new String(bytes, StandardCharsets.UTF_8));
        // Reject multi-line password files. stripPasswordLine only trims
        // trailing terminators; any remaining \n/\r means the file had
        // interior line breaks. A common mistake is passing a two-line
        // `keystore update` password file to `keystore new` / `import` —
        // without this guard the literal "old\nnew" would silently become
        // the password, and neither visible line alone would unlock the
        // keystore later.
        if (password.indexOf('\n') >= 0 || password.indexOf('\r') >= 0) {
          err.println("Password file contains multiple lines; provide a "
              + "single-line password (the `keystore update` two-line "
              + "format is not accepted here).");
          return null;
        }
        if (!WalletUtils.passwordValid(password)) {
          err.println("Invalid password: must be at least 6 characters.");
          return null;
        }
        return password;
      } finally {
        Arrays.fill(bytes, (byte) 0);
      }
    }

    Console console = System.console();
    if (console == null) {
      err.println("No interactive terminal available. "
          + "Use --password-file to provide password.");
      return null;
