### Title
Unbounded Memory Allocation in RPC Declare-v1 Program Decompression Leads to Node DoS - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
`decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs` base64-decodes and gzip-decompresses an attacker-supplied string with `GzDecoder::read_to_end()` and **no size limit**, unlike the sibling helper `decompress_with_size_limit` in `crates/starknet_api/src/compression_utils.rs`, which explicitly bounds decompression via `.take(max_size + 1)`. This is the same bug class as the reported Gophish CVE-2026-39904: attacker-controlled compressed content is fully decompressed into memory with no cap, enabling a classic zip-bomb DoS (CWE-770).

### Finding Description
`decompress_program` reads:

``` [1](#0-0) 

This function is used (per `execution_test.rs` imports and the `get_decompressed_program` unit test) as part of processing a `BroadcastedDeclareV1Transaction`'s `DeprecatedContractClass.program` field, which is submitted as a base64+gzip-encoded string by an unauthenticated JSON-RPC caller when invoking read-execution endpoints such as `starknet_estimateFee` / `starknet_simulateTransactions` [2](#0-1) , whereas `BroadcastedDeclareV1Transaction` is a public, unsigned-fee-checked, unauthenticated input type [3](#0-2) .

By contrast, every other decompression path in the same codebase enforces a bound:
- `decompress_with_size_limit` in `starknet_api::compression_utils` explicitly caps decompressed output and returns `CompressionError::SizeLimitExceeded` [4](#0-3) .
- The gateway's own `DeprecatedGatewaySierraContractClass::convert_to_sierra_contract_class` uses `decode_and_decompress_with_size_limit` with a max size [5](#0-4) .
- The HTTP server layer separately caps decompressed request bytes via `RequestBodyLimitLayer`/`http_body_util::Limited` as a defense specifically against zip bombs [6](#0-5) .

`decompress_program` is the one outlier that still performs unbounded `read_to_end()`, matching the exact root cause pattern from the Gophish advisory (`ioutil.ReadAll()` on decompressed content without a size cap).

### Impact Explanation
A crafted gzip bomb (a small compressed payload expanding to gigabytes) submitted as the `program` field of a `BroadcastedDeclareV1Transaction` via `estimateFee` or `simulateTransactions` causes the RPC/execution process to attempt allocating unbounded memory, exhausting server memory and causing the process to be killed by the OS (OOM) or otherwise become unresponsive. This is a resource-exhaustion DoS reachable by any external, unauthenticated caller with a single RPC request — no funds, signature validity, or prior state are required since this occurs during stateless-ish transaction conversion prior to full validation.

### Likelihood Explanation
High likelihood: the RPC endpoints `starknet_estimateFee` and `starknet_simulateTransactions` are public-facing and unauthenticated; constructing a gzip bomb is trivial and well-documented; no rate limiting or authentication is described as gating this specific decompression path, and the code contains an explicit acknowledging `TODO(dan): add time and size limits.` comment confirming the gap was known but unaddressed.

### Recommendation
Replace the unbounded `GzDecoder::read_to_end` call in `decompress_program` with the same bounded decompression pattern already used elsewhere in the codebase — e.g., reuse `starknet_api::compression_utils::decompress_with_size_limit`/`decode_and_decompress_with_size_limit`, enforcing a configured maximum decompressed program size (consistent with `max_contract_bytecode_size`/`max_contract_class_object_size` limits already enforced in the gateway) and rejecting oversized output before or during decompression.

### Proof of Concept
1. Craft a small gzip payload that decompresses to several GB of data (a classic "zip bomb", e.g., gzip of a highly repetitive large buffer).
2. Base64-encode the compressed bytes and place them into the `program` field of a `DeprecatedContractClass` within a `BroadcastedDeclareV1Transaction`.
3. Submit this as part of a `starknet_estimateFee` or `starknet_simulateTransactions` JSON-RPC call to the node.
4. `decompress_program` will call `decoder.read_to_end(&mut decompressed)` with no size bound, causing the process to allocate the full decompressed size in memory and be killed by the OS or exhaust node memory, denying service to other RPC clients. [7](#0-6)

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
