### Title
Unbounded attacker-controlled array-length parameter in deprecated (Cairo0) syscalls causes unvalidated memory allocation / DoS - (File: `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`)

### Summary
Cairo0 contract syscalls that read variable-length arrays from VM memory (`EmitEvent`, `SendMessageToL1`) trust an attacker/contract-controlled length felt and pass it directly into an allocation routine before any bound is enforced, mirroring the iperf3 flaw where an unvalidated peer-controlled numeric parameter (`len`/`parallel`) drove unbounded buffer/thread allocation.

### Finding Description
The deprecated syscall array reader reads a raw `array_size` felt from VM memory — a value fully controlled by the executing Cairo0 contract's code/calldata — and converts it to `usize` without any upper bound check, then immediately uses it to size a memory read: [1](#0-0) 

This is invoked directly while parsing the `EmitEvent` request (`keys`/`data` arrays) and the `SendMessageToL1` request (`payload` array) before any of the sequencer's configured resource limits (e.g. `max_keys_length`, `max_data_length` in `tx_event_limits`) are checked: [2](#0-1) [3](#0-2) 

The size is then handed to `felt_range_from_ptr`, which calls into the VM's integer-range read with the attacker-supplied `size` with no sanity cap: [4](#0-3) 

Contrast this with the non-deprecated (Cairo1) syscall array reader, where the "size" is derived from the difference between two `Relocatable` pointers that must correspond to actually-allocated VM segments — bounding the value structurally: [5](#0-4) 

The deprecated path has no such structural bound: `array_size` is an arbitrary felt, not tied to any real segment size, so a value like `2^32` or `2^63` can be supplied, causing the read/allocation attempt to run before the sequencer's declared per-event data/key length limits (`max_data_length: 300`, `max_keys_length: 50`, see `crates/blockifier/resources/blockifier_versioned_constants_0_13_1.json:1-6`) are ever consulted, since those checks occur in higher-level event validation logic that only runs after the request struct (and its already-allocated `Vec<Felt>`) has been constructed.

### Impact Explanation
Any account can declare and invoke a Cairo0 (deprecated) contract that calls `emit_event` or `send_message_to_l1` with a crafted, oversized `keys_len`/`data_len`/`payload_size` argument. Every sequencer/full node that executes or re-executes this transaction (including Starknet OS re-execution by other nodes validating the block) will attempt the same oversized allocation deterministically, causing memory exhaustion / process crash across all honest nodes that must process the transaction — a network-wide resource-exhaustion DoS reachable from a single unprivileged transaction, satisfying the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
High: the attack requires only deploying/declaring a trivial Cairo0 contract and sending one `Invoke` transaction that calls `emit_event`/`send_message_to_l1` with a large size felt — no privileged role, no race condition, and no special network conditions are needed. Any full node/sequencer that executes the transaction is affected identically.

### Recommendation
Validate `array_size` against a strict upper bound (e.g., the configured `max_keys_length`/`max_data_length`/reasonable calldata-derived bound) immediately after reading it in the deprecated `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`), before calling `felt_range_from_ptr`/`vm.get_integer_range`, mirroring the length validation already present in the gateway's stateless transaction validator (`crates/apollo_gateway/src/stateless_transaction_validator.rs`). Reject requests exceeding the bound with a syscall execution error instead of attempting the allocation.

### Proof of Concept
1. Declare and deploy a Cairo0 contract whose entry point invokes the `EmitEvent` (or `SendMessageToL1`) syscall, writing an attacker-chosen large value (e.g. `2^40`) as `keys_len`/`data_len`/`payload_size` into the syscall's memory segment instead of the real number of following felts.
2. Submit a single `Invoke` transaction calling that entry point.
3. During execution, `EmitEventRequest::read` (or `SendMessageToL1Request::read`) calls `read_felt_array`, which converts the attacker-controlled size to `usize` and calls `felt_range_from_ptr(vm, ptr, size)` → `vm.get_integer_range(ptr, size)`, attempting to materialize a `Vec<Felt>` of that length before any of the sequencer's event-size limits are enforced, exhausting node memory/CPU on every node that executes or re-executes the block.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
