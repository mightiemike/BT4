Confirmed: for webhook HMAC validation, `validateHmacFromRequest` (in `packages/apps/shopify-api/lib/utils/hmac-validator.ts`, lines 168-201) computes the HMAC only over `rawBody` using `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` [1](#0-0) . The `domain` and `topic` headers are never included as HMAC input — they are only parsed and returned separately by `checkWebhooksHeaders`/`checkEventsHeaders` in `validate.ts`, after HMAC has already passed [2](#0-1) . This means a legitimate signed request (with a valid HMAC over its body, obtainable from the attacker's own shop's real webhook deliveries) can have its `X-Shopify-Shop-Domain` (or `X-Shopify-Hmac-Sha256`-adjacent domain field for Events) header swapped to point at a different shop, and the HMAC check will still pass because the signature only covers `rawBody`.

However, tracing this further into `authenticateWebhookFactory`, after `check.valid` is true, the code calls `ensureValidOfflineSession(params, check.domain)` [3](#0-2) , which looks up a session keyed by the (forged) domain from the app's own session storage. Since the attacker doesn't control what's stored in the victim shop's session storage, they cannot inject arbitrary data there — only cause the app's own `admin` client to be built with the real session credentials of shop B if one is found, while the webhook body content (topic/payload) actually belongs to shop A. In `process.ts` (`shopify-app-express`/plain shopify-api usage), `callWebhookHandlers` similarly dispatches strictly `if (webhookCheck.valid)` before any handler invocation [4](#0-3) , and the handler receives `webhookCheck.domain` (the attacker-forged domain) as an argument passed straight to the app's callback [5](#0-4) .

This is a legitimate design gap (HMAC not binding the domain/topic headers) but exploiting it requires the attacker to already possess a **validly-signed webhook body+HMAC pair**, i.e., a real webhook delivery that Shopify sent them for their own shop. They cannot forge a new HMAC without the app's `apiSecretKey`. Under the rules of this audit ("Attacker controls: a webhook topic/domain header pointing at another shop" but "No app-developer role, no leaked secret"), the only way to get a valid `(rawBody, hmac)` pair is to be a legitimate merchant of the app receiving their own real webhooks and then replaying that captured payload with a modified `domain` header — this is within an unprivileged merchant's capability (no MITM needed; they simply capture their own webhook via a controlled endpoint or logs, then resend it with a different domain header from their own machine).

The consequence, though, is that the payload content itself still belongs to shop A (the attacker's own shop) — only the `shop`/`domain` field and thus which session is looked up changes. The app-side session lookup (`ensureValidOfflineSession`) will retrieve shop B's real offline access token if the app has one, and the handler code (registered by the app developer) will process shop A's webhook payload as if it were shop B's, and any admin API calls it makes use shop B's real token. This is a genuine cross-tenant data-confusion primitive: an app's own webhook handler could act on shop B's admin session using attacker-controlled body content nominally validated under shop A's HMAC.

### Title
Webhook domain/topic headers are not covered by HMAC, enabling cross-tenant webhook replay - (File: packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts, packages/apps/shopify-api/lib/utils/hmac-validator.ts, packages/apps/shopify-api/lib/webhooks/process.ts)

### Summary
Shopify webhook HMAC validation in this library signs only the raw request body (`validateHmacString(config, rawBody, hmac, ...)`), never the `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers. A merchant who legitimately receives a real, validly-signed webhook for their own shop can resend that same body+HMAC pair with the domain header changed to a victim shop, and `authenticateWebhookFactory`/`process()` will accept it as valid and dispatch to handlers with the forged `shop`/`domain` value, which is then used to fetch the victim shop's real offline session.

### Finding Description
`validateHmacFromRequestFactory` computes and compares HMAC strictly against `rawBody` [1](#0-0) . `checkWebhooksHeaders`/`checkEventsHeaders` extract `domain` and `topic` purely from headers, independent of the HMAC computation, and return them as `valid: true` fields once HMAC passes [6](#0-5) . `authenticateWebhookFactory` then trusts `check.domain` to fetch a session via `ensureValidOfflineSession(params, check.domain)` and builds an `admin` client with it [7](#0-6) . Because the domain is unauthenticated data despite `check.valid === true`, dispatch is not fully "post-verification" with respect to the shop identity — only the body integrity/secret possession is verified, not the domain binding.

### Impact Explanation
Impact is limited: attacker cannot forge a fresh HMAC without the app secret, so they can only replay a body+HMAC pair they legitimately received for their own shop. The result is that the app's registered webhook handler is invoked believing the event is for a different (victim) shop, with a real admin session/token for that victim shop attached, while the payload content is actually the attacker's own shop's data. This is a data/identity-confusion bug within scope ("forged authenticated request causing state change/data access") but its severity depends entirely on how a given host app's handler logic uses the `shop`/`domain` and payload fields together — the library itself does not perform any state change, it only supplies the mismatched context to app code.

### Likelihood Explanation
Requires only that the attacker be a real merchant on the app (unprivileged relative to other tenants), able to receive one legitimate webhook for their own shop and resend it with a modified `Domain` header to the app's public webhook endpoint. No MITM, no secret, no special role needed — moderately feasible and repeatable for any topic the app subscribes to.

### Recommendation
Bind the shop domain (and ideally the topic) into the authenticated payload, e.g., include `X-Shopify-Shop-Domain` in the HMAC input, or independently verify that the domain header matches the shop associated with a per-shop webhook secret when available, before using `check.domain` to look up sessions or invoke handlers.
