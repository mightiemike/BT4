## Analysis

The report describes an unvalidated, config-derived denominator flowing into an unchecked division, triggered by an ordinary user action. The nearcore analog is the `burnt_gas_reward` ratio used while burning gas for function calls in `Runtime::apply_action_receipt`. [1](#0-0) 

```rust
let receiver_gas_reward = result
    .gas_burnt_for_function_call
    .checked_mul(*apply_state.config.fees.burnt_gas_reward.numer() as u64)
    .unwrap()
    .checked_div(*apply_state.config.fees.burnt_gas_reward.denom() as u64)
    .unwrap();
```

`checked_div` returns `None` exactly when the divisor is `0`, and the `.unwrap()` will panic in that case, as also documented for `Gas::checked_div`. [2](#0-1) 

`burnt_gas_reward` is a `Rational32` field of `RuntimeFeesConfig`, materialized from the versioned `RuntimeConfigStore` (parsed from YAML parameter files/diffs), and it can also be entirely overridden by a chain-specific `genesis_runtime_config`: [3](#0-2) [4](#0-3) 

Critically, `validate_genesis`/`GenesisValidator::validate_processed_records` — the only semantic-validation pass over genesis — checks `GenesisConfig` fields (`online_min/max_threshold` bounds, `gas_price_adjustment_rate < 1`, `epoch_length > 0`), but never validates `RuntimeFeesConfig.burnt_gas_reward` (or the other `Rational32` fee ratios such as `pessimistic_gas_price_inflation_ratio`) for a non-zero denominator: [5](#0-4) 

If a chain's runtime-config parameters (via `genesis_runtime_config`, a custom parameter YAML/diff, or a misconfigured chain-id override in `RuntimeConfigStore::for_chain_id`) ever specify `burnt_gas_reward = { numerator: N, denominator: 0 }`, no validation catches it before the config is loaded into `ApplyState`. Once loaded, this code path is unconditionally reachable by **any unprivileged account submitting an ordinary `FunctionCall` action**: whenever `result.gas_burnt_for_function_call > 0` (i.e., any successful or failed function call that burns function-call gas), the runtime computes `receiver_gas_reward` and panics on the zero-denominator division, aborting `apply_action_receipt` for the whole chunk.

### Title
Unchecked division by `burnt_gas_reward` denominator causes transaction-triggered node panic - (File: `runtime/runtime/src/lib.rs`)

### Summary
`Runtime::apply_action_receipt` computes the contract's share of burnt function-call gas via `gas_burnt_for_function_call.checked_mul(numer).unwrap().checked_div(denom).unwrap()`, where `numer`/`denom` come from the runtime config's `burnt_gas_reward: Rational32` (`RuntimeFeesConfig`). Neither the runtime-config assembly (`RuntimeConfigStore`/`ParameterTable`) nor genesis validation (`genesis_validate.rs`) enforces that this denominator is non-zero. If it is ever misconfigured to zero (e.g., via a custom `genesis_runtime_config` or parameter diff), the `.unwrap()` on `checked_div` panics on every function-call receipt with non-zero burnt gas — reachable by any ordinary user submitting a `FunctionCall` action.

### Finding Description
`receiver_gas_reward` is computed unconditionally for every receipt that burns function-call gas: [1](#0-0) 

`Gas::checked_div` explicitly returns `None` on a zero divisor: [2](#0-1) 

`burnt_gas_reward` originates from `RuntimeFeesConfig`, itself built from the versioned parameter table and optionally overridden wholesale per chain via `genesis_runtime_config`: [3](#0-2) [4](#0-3) 

Genesis/config semantic validation only checks a handful of `GenesisConfig`-level ratios and thresholds; it never inspects `RuntimeFeesConfig.burnt_gas_reward` (or sibling ratios like `pessimistic_gas_price_inflation_ratio`) for a non-zero denominator: [5](#0-4) 

This is structurally identical to the reported bug class: a group/global configuration value that feeds a division and is never checked for zero, later triggered during normal, unprivileged use (claiming vested tokens / here, executing an ordinary function call).

### Impact Explanation
A zero `burnt_gas_reward` denominator causes an unconditional Rust panic inside `apply_action_receipt`, which runs during ordinary chunk application. Any single `FunctionCall` action from any signer that burns non-zero function-call gas triggers the panic, crashing the node process applying that chunk. Since this runs identically on every validator applying the same chunk (deterministic `ApplyState.config`), it results in a **transaction-triggered halt** of chunk production/validation across the network for that shard — matching the accepted impact class of a transaction-triggered halt.

### Likelihood Explanation
Exploitability depends on the misconfiguration actually occurring (a chain operator, or a config-generation tool, setting `burnt_gas_reward.denominator = 0`), which the report's own template treats as a plausible operational mistake ("not set correctly or mistakenly set to zero") rather than requiring adversarial network/validator access. Given there is no validation gate anywhere in the genesis/config-loading pipeline preventing this specific misconfiguration, likelihood is non-trivial for any deployment that customizes runtime-config fee parameters (private/enterprise chains, testnets, or future parameter additions), and the trigger itself (a `FunctionCall` transaction) requires no privilege at all.

### Recommendation
1. Add a genesis/config validation check (in `GenesisValidator::validate_processed_records` or an equivalent `RuntimeConfig`/`RuntimeFeesConfig` sanity check invoked by `RuntimeConfigStore::new`) that rejects any `Rational32` fee/reward ratio (`burnt_gas_reward`, `pessimistic_gas_price_inflation_ratio`, `gas_refund_penalty`, etc.) whose denominator is zero.
2. Replace the `.unwrap()` chain at `runtime/runtime/src/lib.rs:1108-1113` with a safe fallback (e.g., treat a zero-denominator ratio as "no reward" and log/return a `RuntimeError`) instead of panicking, consistent with the codebase's general preference for `checked_*` + explicit error propagation over `.unwrap()` on config-derived values.

### Proof of Concept
1. Construct (or load) a `RuntimeConfig` whose `fees.burnt_gas_reward = Rational32::new_raw(3, 0)` (denominator 0) — e.g., via a custom `genesis_runtime_config` passed to `RuntimeConfigStore::new`, which is accepted without validation.
2. Start a chain with this config and submit an ordinary `SignedTransaction` containing a `FunctionCall` action to any deployed contract, with enough attached gas that `gas_burnt_for_function_call > 0`.
3. During chunk application, `Runtime::apply_action_receipt` reaches `runtime/runtime/src/lib.rs:1112`'s `checked_div(0).unwrap()`, panicking and aborting the apply step for every validator applying that chunk, halting the shard.
