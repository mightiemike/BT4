### Title
Unbounded HashMap allocation in `Chainbase.prefixQuery` reachable via public `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` API - ([File: chainbase/src/main/java/org/tron/core/db2/core/Chainbase.java])

### Summary
`Chainbase.prefixQuery` (called through `TronStoreWithRevoking.prefixQuery`) has no result-size limit, unlike the store's other prefix-scan methods (`getKeysNext`, `getValuesNext`) which take an explicit `limit`. The only production caller of `TronStoreWithRevoking.prefixQuery` is `DelegatedResourceAccountIndexStore.getWithPrefix`, which is reachable from the public, unauthenticated `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` wallet API. An attacker can broadcast many cheap `DelegateResourceContract` transactions from one address to many distinct receiver addresses, then query the index for that address, causing the node to build unbounded in-memory `HashMap`s proportional to attacker-created entries. Note: the market-order example cited in the question (`MarketPairPriceToOrderStore`) does not actually call `prefixQuery` — it uses the limit-bounded `getKeysNext` — so that specific vector is invalid, but the underlying `prefixQuery` primitive is exploitable through the delegated-resource index path.

### Finding Description
`Chainbase.prefixQuery(byte[] key)` [1](#0-0)  calls `prefixQueryRoot` (unbounded DB-level prefix scan into a `HashMap`) and `prefixQuerySnapshot` (unbounded in-memory snapshot collection via `SnapshotImpl.collect(all, key)`) and merges them with `result.putAll(snapshot)` — none of these paths take or enforce a `limit`, in contrast to `getKeysNext`/`getValuesNext`/`getNext` in the same class which explicitly cap output size [2](#0-1) .

`TronStoreWithRevoking.prefixQuery` wraps this and additionally deserializes every matched value into a capsule object via `Collectors.toMap`, multiplying the memory/CPU cost per entry [3](#0-2) .

The only production store invoking this unbounded method is `DelegatedResourceAccountIndexStore.getWithPrefix`, called by `getIndex`/`getV2Index`, which builds `tmpToList`/`tmpFromList` from `this.prefixQuery(key).values()` with no cap on returned entries [4](#0-3) . These are invoked from `Wallet.java` (confirmed via grep matches on `DelegatedResourceAccountIndexStore` in `framework/src/main/java/org/tron/core/Wallet.java`), which backs the public gRPC/HTTP APIs `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2`. These are read-only, unauthenticated query endpoints with no pagination or result-size cap.

An unprivileged attacker can:
1. Send many `DelegateResourceContract` transactions from a single address to many distinct receiver addresses (each transaction is a normal, cheap fee-paying operation, no special privilege required), each creating a new `V2_FROM_PREFIX/from/to` and `V2_TO_PREFIX/to/from` key entry in `DelegatedResourceAccountIndexStore`.
2. Call the public `GetDelegatedResourceAccountIndexV2` API for that address.
3. This triggers `getV2Index` → `getWithPrefix` → `prefixQuery(key)` twice, each scanning and materializing every matching key/value pair (both from the underlying LevelDB/RocksDB store and any in-memory snapshot layer) into unbounded `HashMap`s, then deserializing every value into a `DelegatedResourceAccountIndexCapsule`.

No fee, rate limit, or cap is applied to this read path — the cost of the query is entirely proportional to attacker-controlled prior on-chain state, while the query itself costs the caller nothing beyond a single RPC call.

### Impact Explanation
Repeated calls to `getDelegatedResourceAccountIndex(V2)` against an address with a large number of delegate targets can force the full node to allocate memory and CPU proportional to the attacker's chosen entry count on every query, with no upper bound. This enables a memory/CPU exhaustion DoS against full nodes/API nodes serving public wallet RPCs, since the cost scales with data the attacker fully controls and can grow indefinitely at low cost (transaction fees for `DelegateResourceContract`, no minimum bandwidth cost floor beyond typical fee schedule).

### Likelihood Explanation
Feasible and repeatable by any account with enough TRX to pay for a large number of `DelegateResourceContract` transactions (fees are typically modest, and resource delegation can be delegated in small increments to many addresses). The read API is public and unauthenticated, and can be invoked repeatedly at will to sustain load once the underlying store is populated.

### Recommendation
Add a mandatory `limit` parameter (and ideally pagination/cursor support) to `Chainbase.prefixQuery`/`prefixQueryRoot`/`prefixQuerySnapshot` and to `TronStoreWithRevoking.prefixQuery`, mirroring the bounded design already used by `getKeysNext`/`getValuesNext`/`getNext`. Update `DelegatedResourceAccountIndexStore.getWithPrefix` and the corresponding `Wallet`/RPC handlers to enforce a maximum number of returned delegate/undelegate index entries per query, with pagination for callers that need the full set.

```java
@Test
public void testUnboundedPrefixQueryDoS() {
  byte[] from = randomAddress();
  int N = 200_000; // attacker-controlled entry count
  for (int i = 0; i < N; i++) {

    delegatedResourceAccountIndexStore.delegateV2(from, to, i + 1L);
  }

  long before = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory();
  long start = System.nanoTime();

  DelegatedResourceAccountIndexCapsule result =
      delegatedResourceAccountIndexStore.getV2Index(from); // calls prefixQuery internally

  long elapsed = System.nanoTime() - start;
  long after = Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory();

  // Expected (bug confirmed) assertions:
  assertEquals(N, result.getAllToAccountsCount());
  // Repeat with N doubled and assert (after-before) and elapsed scale ~linearly with N
  // with no configurable cap — demonstrating unbounded per-request cost.
}
```
Fuzz/invariant variant: parametrize `N` across increasing magnitudes and assert both heap delta and RPC latency for `getDelegatedResourceAccountIndexV2` grow unbounded/linearly with `N` for a fixed single request, with no server-side limit rejecting or truncating the result.

```java
  private Map<WrappedByteArray, byte[]> prefixQueryRoot(byte[] key) {
    Map<WrappedByteArray, byte[]> result = new HashMap<>();
    if (((SnapshotRoot) head.getRoot()).db.getClass() == LevelDB.class) {
      result = ((LevelDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    } else if (((SnapshotRoot) head.getRoot()).db.getClass() == RocksDB.class) {
      result = ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
    }
    return result;
  }

  private Map<WrappedByteArray, byte[]> prefixQuerySnapshot(byte[] key) {
    Map<WrappedByteArray, byte[]> result = new HashMap<>();
    Snapshot snapshot = head();
    if (!snapshot.equals(head.getRoot())) {
      Map<WrappedByteArray, WrappedByteArray> all = new HashMap<>();
      ((SnapshotImpl) snapshot).collect(all, key);
      all.forEach((k, v) -> result.put(k, v.getBytes()));
    }
    return result;
  }
```

```java
  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
```
