### Title
Backup restore accepts write-sets that are never hash-bound to the merkle-proven `TransactionInfo`, allowing wrong state to be committed during restore/replay - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
During transaction backup restore, `LoadedChunk::load` reads `write_sets` directly from the backup chunk file and only runs the accumulator/proof verification (`txn_list_with_proof.verify(...)`) over `(transactions, events, transaction_infos)`. The `write_set` for each transaction is never hashed and compared against the corresponding `TransactionInfo::state_change_hash()`, even though `state_change_hash` is defined as `CryptoHash::hash(write_set)` at execution time. A corrupted or substituted write-set in the backup artifact will pass verification and be durably written to the ledger DB as if it were the VM's real output.

### Finding Description
When a validator/full node restores from a backup, `LoadedChunk::load` parses each record into `(txn, aux_info, txn_info, events, write_set)`: [1](#0-0) 

It then builds a `TransactionListWithProofV2` for verification, but the struct passed to `verify()` only contains `txns`, `event_vecs`, and `txn_infos` (via `TransactionInfoListWithProof::new(range_proof, txn_infos)`); `write_sets` is a separate `Vec<WriteSet>` on `LoadedChunk` that is populated straight from disk and carried alongside, untouched by verification: [2](#0-1) 

Compare this to how `TransactionInfo.state_change_hash` is actually derived during real execution — it is the hash of the transaction's write set, and this hash is what gets accumulated into the merkle-proven `TransactionInfo` and ultimately the ledger's accumulator root: [3](#0-2) 

Because `verify()` is never given the `write_set`s, it cannot check `CryptoHash::hash(write_set) == txn_info.state_change_hash()`. The loaded (unverified) `write_sets` are subsequently persisted straight into the DB via `restore_handler.save_transactions(...)` → `save_transactions_impl` → `write_set_db.rs::put_write_set`, which does a raw `batch.put::<WriteSetSchema>(&version, write_set)` with no hash check at all: [4](#0-3) [5](#0-4) 

The `TransactionInfo`s themselves are proof-verified against the accumulator/ledger-info root (so an attacker cannot forge a `TransactionInfo`), but the `write_set` bytes bound to that `TransactionInfo` by hash are never independently re-derived and compared. This breaks the "VM outputs / write sets ... must survive executor-to-storage handoff unchanged" invariant specifically for the restore path: a backup artifact (corrupted, tampered, or produced by a buggy/malicious backup-generation tool) can carry a `write_set` that does not match the `state_change_hash` recorded in the legitimately-signed `TransactionInfo`, and the restoring node will accept and durably commit that wrong write-set as the canonical state for that version.

### Impact Explanation
This corrupts durable ledger state on any node that restores from the tampered/corrupted backup: the committed state values at that version will not match what was actually executed/committed by the validators (as attested by the real `TransactionInfo.state_change_hash`), yet the node's local accumulator/ledger-info checks will still pass because those checks never touch the `write_set` at all. This is a direct "committed state that differs from the correct VM result" scenario and can propagate to state sync/other consumers of that node, corrupting API responses (e.g., `get_state_value_by_version`) bound to that (wrong) version while claiming validity.

### Likelihood Explanation
Likelihood depends on backup file integrity: this requires the backup manifest/chunk file's `write_set` bytes to diverge from what was really executed while `txn_info` stays correct (e.g., a compromised/misconfigured backup storage backend, a bug in backup generation, or a MITM against backup storage that specifically only tampers with the write_set bytes but leaves everything else, including transaction bytes, events, and proof, intact). It does not require any privileged access to consensus or execution, only to the backup storage/transport that any operator restoring from backup trusts implicitly.

### Recommendation
In `LoadedChunk::load`, after determining `txn_infos` from the verified `TransactionListWithProofV2`, additionally recompute `CryptoHash::hash(&write_set)` for each transaction and assert it equals `txn_info.state_change_hash()` before returning the `LoadedChunk` (or before `save_transactions`/replay uses it). This closes the gap by binding the untrusted write_set bytes to the merkle-proven commitment the same way `assemble_transaction_infos` does at original execution time.

### Proof of Concept
1. Take a legitimate backup transaction chunk file (format V0/V1) containing `(txn, txn_info, events, write_set)` records and a valid `(range_proof, ledger_info)` sidecar.
2. Replace the `write_set` bytes for one record with a different, attacker-chosen `WriteSet` (leave `txn`, `txn_info`, `events` untouched, so `txn_info.state_change_hash()` no longer matches the replaced `write_set`).
3. Point a restoring node's `TransactionRestoreController`/`TransactionRestoreBatchController` at this modified backup.
4. `LoadedChunk::load` calls `txn_list_with_proof.verify(ledger_info.ledger_info(), ...)`, which succeeds because it only checks `txns`/`events`/`txn_infos` against the accumulator proof — the tampered `write_set` is never part of that check.
5. `save_transactions`/`save_transactions_impl`/`put_write_set` persist the tampered write set at that version with no hash validation, so the restored node ends up with ledger state at that version that differs from the real committed VM output, while its accumulator root and transaction-info proofs remain "valid."
