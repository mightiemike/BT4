### Title
`handle_poison_microblock` slashes a miner using two non-conflicting, sequentially-different microblocks because the only signer check performed is pubkey-hash equality, not sequence/prev_block equality - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
`handle_poison_microblock` relies solely on `check_microblock_header_signer` to validate a `PoisonMicroblock` transaction, which only verifies that both headers recover to the same signing pubkey hash and never checks that `mblock_header_1.sequence == mblock_header_2.sequence` (or that `prev_block` matches). The equivalent equality check does exist, but only inside the RPC/mempool admission gate (`will_admit_mempool_tx`), which is not re-applied on the consensus block-processing path (`process_transaction` → `handle_poison_microblock`).

### Finding Description
The equality that must hold for legitimate poison evidence is `seq(headerA) == seq(headerB)` (and `prev_block(headerA) == prev_block(headerB)`) under the same miner key — i.e., both headers must occupy the same slot in the microblock stream to prove equivocation. `check_microblock_header_signer` at [1](#0-0)  only recovers and compares the two signing pubkey hashes (`pkh1 != pkh2`); it never inspects `sequence` or `prev_block`.

`handle_poison_microblock` calls only this function as its validity gate before proceeding to slash the miner's key: [2](#0-1) 

It then treats `mblock_header_1.sequence` as the fork point and records/updates a poison report for the miner's key at that height, without ever confirming `mblock_header_2.sequence` equals it: [3](#0-2) 

By contrast, the sequence/prev_block/version equality invariant IS enforced — but only in the mempool admission path (`will_admit_mempool_tx`), not in the consensus transaction-processing path: [4](#0-3) 

Since a block's transactions are applied via `process_transaction` → `run_poison_microblock` → `handle_poison_microblock` during block validation/acceptance (not through `will_admit_mempool_tx`), the sequence-equality guard is not part of the consensus rule set: [5](#0-4) 

**Exploit flow:** An attacker (who can be a single miner with any minority stake, or any unprivileged user who can get a miner to include their transaction, or a malicious miner including their own transaction directly in a block they mine) takes two microblocks that the target miner honestly and sequentially produced (e.g., seq=3 and seq=4, `prev_block` chained correctly, no equivocation at all) and packages them as `TransactionPayload::PoisonMicroblock(header_seq3, header_seq4)`. This tx is included directly in a mined block (bypassing the mempool RPC gate entirely, since a miner can place arbitrary payload bytes into its own block without going through `will_admit_mempool_tx`). When honest nodes process this block via `process_transaction`, `handle_poison_microblock` only checks that both headers were signed by the same key (true, since they are both genuinely from the target miner) and that the key/height maturity checks pass — it never rejects on the mismatched sequence numbers. The transaction succeeds, records a poison report against the honest miner's key, and the corresponding slashing/reward-redirection logic (miner reward maturation checks against `get_microblock_poison_report`) triggers, illegitimately diverting/forfeiting that miner's coinbase reward.

### Impact Explanation
This is block-reward theft against an honest miner who never equivocated: the miner's coinbase reward is forfeited/redirected to the reporter based on fabricated "poison" evidence that does not actually demonstrate a fork (different, non-conflicting sequence numbers). Because every honest node applies the same deterministic (but incorrect) consensus rule, all nodes agree on the wrongful slashing — it does not cause disagreement between honest nodes/a chain split, but it does directly cause reward theft/loss, matching the Critical category "block-reward theft/double-payment/loss."

### Likelihood Explanation
No special stake or privilege is required beyond being able to mine (or otherwise get) a block containing the crafted transaction — a minority miner slot is already listed as within the unprivileged attacker's capabilities in the rules. The attacker needs only two already-public, validly signed microblocks from the target miner at different, non-conflicting sequence numbers, which are broadcast in the normal course of operation and thus trivially obtainable. The attack is repeatable against any miner whose microblock public key hash has not yet matured (`MINER_REWARD_MATURITY` window), i.e. within a bounded number of blocks after each of that miner's tenures.

### Recommendation
In `handle_poison_microblock` (or in `check_microblock_header_signer`), enforce that `mblock_header_1.sequence == mblock_header_2.sequence` and `mblock_header_1.prev_block == mblock_header_2.prev_block` (and that the two headers are not identical) before accepting the transaction as valid poison evidence — mirroring the check already present in `will_admit_mempool_tx` at `blocks.rs:6844-6850`, but applied on the consensus path so it cannot be bypassed by direct block inclusion.

### Proof of Concept
Rust integration test plan (added near `process_poison_microblock_multiple_same_block` in `stackslib/src/chainstate/stacks/db/transactions.rs`):
1. Insert a miner's microblock pubkey hash at height 1 via `insert_microblock_pubkey_hash`.
2. Construct `mblock_1` at `sequence = 3` and `mblock_2` at `sequence = 4`, both validly signed by the same `block_privk`, with `mblock_2.prev_block` correctly linking to `mblock_1`'s hash (i.e., a genuine, non-conflicting sequential pair, not a fork).
3. Build a `TransactionPayload::PoisonMicroblock(mblock_1.header, mblock_2.header)`, sign it, and call `StacksChainState::process_transaction`.
4. Assert on both sides of the claimed equality:
   - `mblock_1.header.sequence != mblock_2.header.sequence` (proving these are NOT the same slot / not real equivocation), and separately
   - Assert that `process_transaction` returns `Err` (i.e., the transaction should be rejected) — and observe that, contrary to expectation, it currently returns `Ok`, inserting a poison report via `get_poison_microblock_report` for the honest miner's key/height, demonstrating the wrongful slashing state change.

    /// Given two microblock headers, were they signed by the same key?
    /// Return the pubkey hash if so; return Err otherwise
    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
