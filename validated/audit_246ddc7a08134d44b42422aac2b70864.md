### Title
Paused `accrue` skips the real interest index update while `redeem`/`deposit` still price shares off `next-index()`, letting depositors extract phantom yield from the vault's real reserves — (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and sibling vaults)

### Summary
Every ZEST vault contract (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) implements `accrue` so that when the `accrue` pause flag is set, it **passes through without reverting**, returning the stale `index`/`lindex` and leaving `last-update` untouched. This is intentional so callers such as `deposit`/`redeem` (which call `(try! (accrue))` first) never revert while paused. However, the share-pricing helpers used by `deposit`/`redeem` — `convert-to-assets-preview`/`convert-to-shares-preview` → `total-assets-preview` → `debt-preview` → `next-index()` — compute interest strictly from elapsed wall-clock time relative to `last-update`, with **no awareness of the pause flag at all**. While `accrue` is paused, real time keeps advancing but the persisted `index`/`last-update` are frozen; the preview path nonetheless keeps inflating `total-assets-preview` as if interest were still accruing, and this inflated value is what is actually paid out on `redeem`.

### Finding Description
`accrue()` in the vault contracts:
```
(define-public (accrue)
  (let ((states (var-get pause-states)) (idx (var-get index)) (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic ... (updates index/lindex/last-update)
          ...)))
``` [1](#0-0) 

When paused, this returns the old, frozen `index`/`lindex` and **does not** update `last-update` — that is expected, since the admin explicitly wants the recorded index to stop growing.

`set-pause-states` performs a single "sync" `accrue` right before flipping the pause flag on, and jumps `last-update` forward when unpausing to skip the paused window for future accrual: [2](#0-1) 

The problem is that `deposit`/`redeem` do **not** use the persisted, pause-aware `index`. They price shares via `convert-to-assets-preview`/`convert-to-shares-preview`, which call `total-assets-preview`, which calls `debt-preview`, which calls `next-index()` — a function that computes "what the index would be right now" purely from elapsed time since `last-update`, with no reference to `pause-states` whatsoever: [3](#0-2) 

So even though `accrue()` correctly refuses to persist new interest while paused, the preview functions used by `redeem`/`deposit` to compute the exchange rate keep growing `total-assets-preview` for the entire duration accrual is paused, because they measure "time since `last-update`" unconditionally rather than "time the vault was actually un-paused."

`redeem` uses exactly this preview value to compute the amount of real underlying paid out (`inkind`), which is deducted straight from `assets` (the real underlying reserve), not from any freshly-accrued (and thus real) debt interest: [4](#0-3) 

### Impact Explanation
While the DAO has `accrue` paused (a legitimate, intended admin action — no DAO compromise required), any user calling `redeem` receives underlying priced using `next-index()`'s phantom, unpaused-equivalent interest that was never actually recorded into `index`/`total-borrowed`/`debt`. That phantom value is paid out of the vault's real `assets` balance. Because the persisted debt-side accounting never grew (interest wasn't accrued into `principal-scaled`/`total-borrowed`), the vault has no matching increase in receivable value to back this payout — the extra underlying is siphoned directly from the shares of all other depositors. Repeated or large redemptions during a paused window can drain the vault's real underlying reserve below what's needed to honor remaining depositors' shares, which is a permanent-freezing-of-funds / protocol-insolvency-class impact (other users' deposits become partially or fully unredeemable).

### Likelihood Explanation
This requires no privileged access beyond the DAO's ordinary, documented pause action (pausing `accrue` is a standard emergency lever, not a compromise). Once `accrue` is paused, any user (attacker or legitimate holder) can simply call `redeem` — a normal, permissionless, single-transaction call — and the mismatch triggers automatically as time passes during the pause window. No cross-user race or MEV timing is needed; the longer the pause lasts, the larger the phantom interest becomes, making the exploit strictly worse the longer the intended safety pause is in effect.

### Recommendation
Make `next-index()`/`next-liquidity-index()` (and therefore `total-assets-preview`/`debt-preview`) aware of `pause-states`: when `accrue` is paused, these preview functions should return the currently persisted `index`/`lindex` unchanged (mirroring what `accrue()` itself does), rather than computing a value based on elapsed time since `last-update`. Alternatively, compute elapsed time relative to the timestamp at which the pause was engaged instead of `last-update`, so that no interest is ever previewed during a paused window.

### Proof of Concept
1. DAO calls `set-pause-states` to pause `accrue` on `v0-vault-usdc`. This runs one final real `accrue()` (syncing `index`/`lindex`/`last-update` to "now"), then sets `pause-states.accrue = true`.
2. Time passes (many blocks) while `accrue` remains paused. `index`/`lindex`/`last-update` remain frozen because `accrue()` now pass-throughs.
3. Attacker (or any holder) calls `redeem(amount, min-out, recipient)`:
   - `redeem` calls `(try! (accrue))`, which pass-throughs and returns the old, frozen `index`/`lindex` — no state mutated.
   - `redeem` then computes `inkind` via `convert-to-assets-preview`, which calls `total-assets-preview` → `debt-preview` → `next-index()`. `next-index()` computes interest for the *entire elapsed real time* since the frozen `last-update`, inflating `total-assets-preview` even though the pause was meant to freeze this exact value.
   - `redeem` pays out `inkind` (the inflated value) from `var-get assets`, burning only `amount` shares.
4. Because `principal-scaled`/`total-borrowed`/`index` were never updated to reflect this "interest" (the pause correctly prevented that), the vault's real reserve (`assets`) is now short by the phantom amount, at the expense of remaining shareholders — a real, verifiable value leak using nothing but the documented pause feature and a standard `redeem` call.
