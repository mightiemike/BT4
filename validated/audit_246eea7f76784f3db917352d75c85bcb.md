### Title
`ensure_match_transaction_info` omits state/hot-state/position checkpoint hash checks, allowing replay-verify to silently accept a corrupted state-commitment root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by every offline "replay and compare against the authenticated `TransactionInfo`" tool (`db-tool replay-verify` / `replay-on-archive`, `aptos move replay`/CLI debugger). It checks status, gas, write-set hash, and event-root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` carried in `TransactionInfoV1`. This is exactly the "forgot to override/verify a sibling entry point" bug class from the external report: the function is supposed to fully bind a locally-recomputed output to the authenticated, accumulator-committed `TransactionInfo`, but a subset of the commitment fields is left unchecked.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  validates only 4 of the fields that make up a `TransactionInfoV1`: status, gas_used, write-set hash (`state_change_hash`), and event root hash. The function's own comment admits the gap: [2](#0-1) 

The state/hot-state/position checkpoint hashes are exactly the fields that bind a transaction's output to the Sparse-Merkle/Jellyfish-Merkle state root recorded in the accumulator-committed `TransactionInfoV1` (see the field definitions and their accessors at [3](#0-2)  and [4](#0-3) ). Nowhere else in the local-replay path is this gap closed:

- `db-tool`'s archive replayer calls exactly this comparator as its sole correctness gate after re-executing transactions, with no additional checkpoint-hash check: [5](#0-4) .
- The `aptos move` CLI debugger/replay path uses the same comparator with the same limitation: [6](#0-5) , [7](#0-6) .

By contrast, the *online* chunk-executor/consensus commit path (`DoLedgerUpdate`/`DoStateCheckpoint`) does correctly thread and validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally computed values before they enter the committed `TransactionInfo`/accumulator (see [8](#0-7)  and [9](#0-8) ). So on-chain state-checkpoint integrity for full sync/chunk-apply is enforced. The gap is isolated to the standalone, single-`ensure_match_transaction_info`-based replay/verify tools that do not go through `DoStateCheckpoint`/accumulator verification at all — for them, this comparator is the *only* place that ever compares locally recomputed output to the authenticated ledger commitment.

### Impact Explanation
If `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (native-position state) or `HOT_STATE_ROOT_IN_TXN_INFO` is enabled and a divergence exists between locally-replayed state/hot-state/position roots and the historically committed `TransactionInfoV1` checkpoint hashes (e.g. due to a state-computation bug, a storage corruption, or a malicious archive/backup source feeding altered checkpoint hashes alongside a matching write-set/event-root), `db-tool replay-on-archive` and `replay-verify` will report success even though the authenticated state-commitment root diverges from the correct VM result. This directly matches the required "committed state that differs from the correct VM result... accepted as valid" impact class, since these tools are the primary mechanism operators and auditors use to attest that an archived/backed-up ledger state is correct.

### Likelihood Explanation
The comment is explicit that this gap exists and is currently gated behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS` not yet being enabled in production (per the feature-flag gating logic in [10](#0-9) ), and hot-state root inclusion is also stated as "currently `None` in testnet and mainnet" ( [11](#0-10) ). This means **today**, on mainnet, this particular comparator's blind spot is not actively exploitable because the checkpoint-hash fields it fails to check are still always `None`. The bug is real (a genuinely missing invariant check with an explicit developer TODO acknowledging it), but its live impact is currently latent/theoretical pending activation of these features — it is a pre-existing landmine rather than an active, currently-triggerable mainnet gap, which caps the present-day likelihood.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when the local recomputation produces them) against the corresponding fields of `txn_info`, matching how `write_set_hash`/`event_root_hash` are already validated. Land this fix and add a regression test before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or `HOT_STATE_ROOT_IN_TXN_INFO` in any environment where `replay_on_archive`/`replay_verify` is relied upon as a correctness oracle.

### Proof of Concept
Not applicable as a live mainnet exploit today (the relevant checkpoint-hash fields are always `None` under current mainnet feature flags), so no on-chain PoC is provided. The code-level PoC is the comparator itself: construct a `TransactionInfoV1` with a `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` that does not match a locally-recomputed `LedgerStateSummary`, keep `write_set`/events/gas/status identical, and observe that `TransactionOutput::ensure_match_transaction_info` ( [1](#0-0) ) returns `Ok(())`, causing `replay_on_archive::Verifier::execute_and_verify` ( [12](#0-11) ) to report a clean replay despite the divergent state root.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
