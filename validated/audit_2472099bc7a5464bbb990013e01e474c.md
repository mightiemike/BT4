### Title
Truncating (round-toward-zero) integer division of a negative `unfreezeBalance` in `UnfreezeBalanceProcessor.execute()` under-decrements global resource weight - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java])

### Summary
`UnfreezeBalanceProcessor.execute()` adjusts the network-wide `totalNetWeight`/`totalEnergyWeight` counters by dividing a *negative* value (`-unfreezeBalance`) by `TRX_PRECISION` using plain Java `long` division. [1](#0-0) 
Java `long`/`long` division truncates toward zero, not toward negative infinity. When the dividend is negative and not an exact multiple of `TRX_PRECISION` (1,000,000 sun), this produces a smaller-magnitude (less negative) result than the mathematically correct floor, mirroring exactly the rounding flaw described in the Notional `convertFromStorage()` report: a division on a negative accounting value that should round away from zero (to preserve the full magnitude of a decrease/debt) instead rounds toward zero.

### Finding Description
`totalNetWeight` / `totalEnergyWeight` (stored in `DynamicPropertiesStore`) are the *denominators* used everywhere resource limits are computed proportionally to frozen balance, e.g. `calculateGlobalEnergyLimit`/`calculateGlobalLimitV1`/`calculateGlobalLimitV2`. [2](#0-1) [3](#0-2) 

When a user unfreezes (via `UnfreezeBalanceV2Contract`, executed through the native-contract path `UnfreezeBalanceProcessor.execute()`), the code computes:
```
repo.addTotalNetWeight(-unfreezeBalance / TRX_PRECISION);
repo.addTotalEnergyWeight(-unfreezeBalance / TRX_PRECISION);
``` [4](#0-3) 

`unfreezeBalance` is a positive sun amount that is not required to be an exact multiple of `TRX_PRECISION` (unlike the delegated-resource path in `UnfreezeBalanceActuator`, which computes the weight delta as `newWeight - oldWeight` from two *floor* divisions of positive numbers and is therefore consistent). Here the negative dividend is divided directly: e.g. for `unfreezeBalance = 1,999,999` sun, `-1,999,999 / 1,000,000 == -1` in Java (truncation toward zero), whereas the mathematically-correct decrease is `-2`. The total weight tracked in `DynamicPropertiesStore` is therefore left larger than it should be after every such unfreeze whose sun amount is not an exact multiple of one TRX.

The comment left in the code itself, `// adjust total resource, used to be a bug here`, indicates this exact area has already been a source of prior accounting bugs. [5](#0-4) 

### Impact Explanation
`totalNetWeight`/`totalEnergyWeight` are global, network-wide state used as divisors when computing every account's proportional bandwidth/energy limit. A systematic under-decrement (i.e., value stays too large) dilutes the denominator less than it should, meaning the network's computed per-TRX weight is fractionally lower than the "true" value after unfreezes accumulate. Because this is triggered on every `UnfreezeBalanceV2Contract` execution by any unprivileged account holder, and the error is one-directional (always rounds the decrease toward zero, never overshoots), the drift compounds monotonically over the life of the chain, corrupting global consensus-relevant accounting state (`totalNetWeight`/`totalEnergyWeight` in `DynamicPropertiesStore`) that affects every account's resource-limit computation. This is analogous to the reported "protocol losing dust that can be accumulative" impact in the referenced report, except here the corrupted value is shared network state rather than a per-user debt balance.

### Likelihood Explanation
High likelihood of occurrence: any account can unfreeze any non-multiple-of-1,000,000-sun frozen balance via a normal, unprivileged broadcast transaction (`UnfreezeBalanceV2Contract`), and this code path executes unconditionally on every such unfreeze. No special preconditions, privileges, or race conditions are required. The magnitude of each individual drift is small (at most 1 unit of weight per call), so exploitation as a large, single-transaction theft is not feasible, but cumulative/adversarial repeated triggering (freeze/unfreeze in small non-multiple-of-TRX_PRECISION amounts) is straightforward for any attacker to force sustained state drift.

### Recommendation
Use floor-consistent division for the negative decrement, matching the pattern used elsewhere in the codebase (e.g., compute the change from two floor-divided non-negative quantities, as `UnfreezeBalanceActuator` does with `oldWeight`/`newWeight`), or explicitly floor-divide:
```java
long decrease = -Math.floorDiv(unfreezeBalance, TRX_PRECISION);
repo.addTotalNetWeight(decrease);
```
alternatively compute the weight delta the same way `UnfreezeBalanceActuator` does (`oldWeight - newWeight` from two floor divisions of the pre/post frozen balances) instead of directly dividing a negated value.

### Proof of Concept
1. Freeze `1,999,999` sun (just under 2 TRX) for BANDWIDTH via `FreezeBalanceV2Contract`. `totalNetWeight` increases correctly by `floor(1_999_999/1_000_000) = 1`.
2. After the unfreeze period elapses, submit `UnfreezeBalanceV2Contract` to unfreeze this exact amount.
3. `UnfreezeBalanceProcessor.execute()` computes `-1_999_999 / 1_000_000`, which in Java evaluates to `-1` (truncation toward zero) instead of the correct `-2` (floor). [6](#0-5) 
4. `totalNetWeight` is left with a net `+0` from this freeze/unfreeze cycle even though the actual frozen balance backing that weight is now zero — the global weight has drifted upward by 1 unit relative to real backing collateral. Repeating this freeze/unfreeze cycle with non-multiple-of-`TRX_PRECISION` amounts accumulates unbounded drift in `totalNetWeight`/`totalEnergyWeight`, corrupting the shared resource-limit denominator used by `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` for the entire network.

  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
