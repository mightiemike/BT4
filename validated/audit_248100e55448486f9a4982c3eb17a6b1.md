### Title
Missing validation that `UniversalStateInit` carries at least one access key (or contract code) permanently locks any funds sent to the derived account - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/universal_account_id.rs`)

### Summary
The reported Pickle Finance bug class is "no check of parameter values when executing a constructor" — specifically missing `require(x != 0)` guards on inputs consumed during contract initialization, which can leave the contract permanently unusable/inaccessible. The reachable nearcore analog is in the `UniversalStateInit` action, which "constructs" a brand-new `0u`-style universal account from attacker/user-supplied bytes. `validate_universal_state_init` checks an upper bound on the number of access keys but never enforces a lower bound (or requires contract code), so a `UniversalStateInitAction` with zero access keys and no code is accepted and permanently installed as an "Initialized" account with no way to ever be controlled.

### Finding Description
`validate_universal_state_init` in `runtime/runtime/src/action_validation.rs` validates the derived receiver id, decodes the state init, validates any embedded global-contract identifier, and enforces a maximum on `access_keys().len()` and the byte lengths of storage entries: [1](#0-0) 

There is no analogous check that `access_keys()` is non-empty, nor any requirement that `code()` be `Some(..)` when there are no keys. Both `code` and `access_keys` are independently optional/emptyable fields of `UniversalStateInit`.

The execution path, `action_universal_state_init` in `runtime/runtime/src/universal_account_id.rs`, unconditionally marks the account `Initialized` before installing whatever the (unchecked) state init contains: [2](#0-1) 

`install_universal_account` then writes contract code only `if let Some(code) = state_init.code()` and access keys only by iterating `state_init.access_keys()` — both are simply skipped when empty, with no failure path: [3](#0-2) 

If `code` is `None` and `access_keys` is empty, the account still transitions from `Uninitialized`/nonexistent to fully `Initialized` (`account.initialize()` on line 68), but with **no access key that could ever sign a transaction for it and no contract that could ever process an incoming receipt on its behalf**. Because `!account.is_initialized()` gates the entire install branch, this action can only run once per account — after it runs with empty parameters, the account can never be repaired via a second `UniversalStateInit`, and no `AddKey`/`DeployContract` action can reach an account with no access key (those require `actor_id == account_id`, which requires the sender to already control the account).

This exactly parallels the reported bug class: essential "constructor" parameters (the equivalent of `_governance`, `_controller`, etc. in the Pickle Finance report) are accepted without a `!= 0`/non-empty check, silently producing a permanently broken, unusable contract/account instead of reverting.

### Impact Explanation
Any NEAR subsequently transferred to this derived account id (via a plain `Transfer`, which is always allowed to fund a nonexistent/uninitialized universal account) becomes permanently frozen: there is no key to sign a withdrawal and no contract logic to move the funds out. This is a direct "permanently frozen funds" outcome reachable purely by an unprivileged transaction sender constructing and submitting a single transaction — no validator, relayer, or node compromise required.

### Likelihood Explanation
High reachability, low complexity: any RPC caller/transaction signer can submit a `UniversalStateInitAction` with `access_keys: {}` and `code: None` in the state-init payload; validation in `validate_universal_state_init` and `validate_deterministic_state_init`'s sibling `validate_global_contract_identifier` never rejects this shape. It requires no special privileges, no protocol feature outside the already-active `UniversalAccounts` feature gate, and no race condition — a single transaction reliably reproduces the state, either by the sender's own error or as a griefing vector against anyone who is later told to send funds to a particular universal account id.

### Recommendation
Add a validation rule in `validate_universal_state_init` (mirroring the existing `max_universal_state_init_keys` check) rejecting a state init when `state_init.access_keys().is_empty() && state_init.code().is_none()`, returning a new `ActionsValidationError` variant (e.g. `UniversalStateInitEmpty`). This preserves the "constructor parameter must not be the empty/zero equivalent" invariant analogous to `require(variableAddress != address(0))`.

### Proof of Concept
1. Construct `UniversalStateInit::V1(UniversalStateInitV1 { code: None, data: BTreeMap::new(), access_keys: BTreeSet::new() })`.
2. Derive `account_id = state_init.derive_account_id()`.
3. Send a `Transfer` to `account_id` to fund it (allowed for uninitialized universal accounts, as shown by the pattern in the existing test): [4](#0-3) 
4. Submit a transaction with `Action::UniversalStateInit(UniversalStateInitAction { state_init: state_init.to_raw(), deposit: Balance::ZERO })` targeting `account_id`. This passes `validate_universal_state_init` (no lower-bound check) and `action_universal_state_init` marks the account `Initialized` with zero access keys and no contract.
5. Observe: `env.view_account(&account_id).state == AccountState::Initialized`, no access key exists for any key, and no contract is deployed — the previously transferred balance is now permanently unreachable.
