**Analysis:**

The `UnsyncCodeStorage<M>` struct always constructs `script_cache` and `module_storage` together as a pair, and both fields are private with no setter methods to swap one independently of the other. [1](#0-0)  The only constructor, `UnsyncCodeStorage::new`, is a private (non-`pub`) function, and the only way to build an instance is through the `AsUnsyncCodeStorage` trait, which always creates a fresh empty `script_cache` alongside a freshly derived `module_storage` from the same underlying context (state view + environment) in a single atomic call. [2](#0-1) 

`module_storage()` and `into_module_storage()` are pure read accessors — the former returns a reference without touching `script_cache`, and the latter consumes `self` (and therefore drops `script_cache` along with it), so there is no code path where a live `script_cache` can survive being paired with a swapped-out or newly reconstructed `module_storage`. [3](#0-2) 

Searching the production call sites confirms this: the only non-test production consumer is `AptosCodeStorageAdapter` in `state_view_adapter.rs`, which builds a brand-new `UnsyncCodeStorage` via `into_unsync_code_storage()` fresh for every `as_aptos_code_storage()` call, tied 1:1 to a single state view — used for standalone transaction simulation/debugger flows, not the consensus block-execution path. [4](#0-3)  The actual consensus block-executor sequential-execution path does not use `UnsyncCodeStorage` at all; it uses `UnsyncMap`, which similarly bundles `module_cache` and `script_cache` together and is always freshly created per block via `UnsyncMap::new()`. [5](#0-4) [6](#0-5) 

Since there is no API surface allowing an attacker (or even a caller) to combine a previously-populated `script_cache` with a `module_storage` built from a different state view, the described exploit path does not exist in this codebase.
