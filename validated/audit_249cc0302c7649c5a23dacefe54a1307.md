## Title
Missing slippage/minimum-output protection in `ExchangeInjectContract` and `ExchangeWithdrawContract` allows exchange-pool ratio front-running to cause fund loss — (`File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron's Bancor-style token-pair Exchange feature lets any account create a liquidity pool (`ExchangeCreateContract`) and then inject or withdraw liquidity as the pool creator. Unlike the trade-execution contract (`ExchangeTransactionContract`), which explicitly carries a user-supplied `expected` minimum-output field, the liquidity `Inject`/`Withdraw` contracts only carry a `quant` for one side of the pair — the counter-token amount (`anotherTokenQuant`) is computed from the pool's *current* balance ratio at execution time, with no user-specified bound. This is the same bug class as the reported ERC4626 issue: a value-conversion operation (deposit/withdraw against a pooled exchange rate) is executed without any slippage tolerance, so the ratio can move between transaction submission and inclusion (e.g., due to an intervening `ExchangeTransactionContract` trade), causing the liquidity provider to receive less, or contribute disproportionately more, than intended.

### Finding Description
`ExchangeCreateActuator` allows any unprivileged account to create a token-pair pool by locking `firstTokenBalance`/`secondTokenBalance` [1](#0-0) . Once created, only the pool creator can call `ExchangeInjectContract`/`ExchangeWithdrawContract`, but "creator" here is just the ordinary account that created the pool — not a privileged/system role.

For `ExchangeWithdrawActuator.execute`, `anotherTokenQuant` is derived purely from the pool's live balances at execution time: [2](#0-1) 

The `doValidate()` method only checks that this computed ratio is "precise enough" (a rounding-tolerance check), not that it meets any user-desired minimum: [3](#0-2) 

Similarly, `ExchangeInjectActuator.execute` computes the counterpart deposit amount from the live ratio with no user-supplied cap: [4](#0-3) 

By contrast, the protocol *does* define slippage protection for the trade-execution flow: `ExchangeTransactionContract` includes an explicit `expected` field, and `ExchangeTransactionActuator.doValidate` enforces "token required must greater than expected" [5](#0-4) . No equivalent `expected`/minimum-bound field exists on `ExchangeInjectContract` or `ExchangeWithdrawContract` (both only carry `owner_address`, `exchange_id`, `token_id`, `quant`) [6](#0-5) .

The pool ratio (`firstTokenBalance`/`secondTokenBalance`) is mutated by every `ExchangeTransactionContract` trade via `ExchangeCapsule.transaction`, using a bonding-curve formula in `ExchangeProcessor` [7](#0-6) [8](#0-7) . Because block producers order transactions and multiple pending trades can be included ahead of a pending Inject/Withdraw, the ratio the creator observed when signing their Inject/Withdraw transaction can differ materially from the ratio applied at execution — exactly the "exchange rate can change while the transaction is pending" scenario described in the ERC4626 report.

### Impact Explanation
A pool creator withdrawing liquidity can receive a smaller amount of the counter-token than expected if the ratio shifts unfavorably before inclusion (loss of expected value on withdrawal), and a creator injecting liquidity can be forced to commit a larger counter-token amount than intended for the same target ratio, effectively overpaying due to unfavorable pool movement — both are direct, unmitigated value-loss outcomes for an unprivileged (non-system) account, analogous to the ERC4626 deposit/redeem slippage issue. This falls under the accounting/settlement impact category since it directly affects the value users receive/spend in an on-chain state-mutating operation with no way to bound the outcome.

### Likelihood Explanation
Exchange creation, trading, injection, and withdrawal are all open to any account with sufficient balance, so this can be triggered by any user with a live pool and any actor able to submit an `ExchangeTransactionContract` trade in the same or a preceding block. Given how frequently pools may be traded (arbitrage bots reacting to any imbalance) and the lack of a mempool with strict ordering guarantees, an Inject/Withdraw transaction sitting pending is realistically exposed to ratio movement before inclusion, making the scenario plausible rather than purely theoretical, mirroring the sponsor/judge's medium-severity treatment of the analogous ERC4626 report.

### Recommendation
Add an optional minimum/maximum bound parameter to `ExchangeInjectContract` and `ExchangeWithdrawContract` (analogous to the existing `expected` field on `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator.doValidate()` so the transaction fails if the computed `anotherTokenQuant` falls outside the caller's specified tolerance.

### Proof of Concept
1. Account A creates a pool via `ExchangeCreateContract` with tokens X/Y at a 1:1 ratio and later becomes the sole authorized caller for Inject/Withdraw operations on this pool.
2. A submits `ExchangeWithdrawContract` to withdraw `quant` of X, expecting to receive `anotherTokenQuant` of Y based on the current 1:1 ratio, per `ExchangeWithdrawActuator.execute` [9](#0-8) .
3. Before A's transaction is packed into a block, another account submits an `ExchangeTransactionContract` trade that shifts the pool ratio unfavorably for Y (e.g., sells a large amount of Y into the pool), executed via `ExchangeCapsule.transaction`/`ExchangeProcessor.exchange` [10](#0-9) .
4. When A's `ExchangeWithdrawContract` is finally executed, `anotherTokenQuant` is recomputed from the now-shifted balances, giving A materially less Y than anticipated when the transaction was signed — with no `expected`/minimum-output check to abort the transaction, unlike the protection that exists for `ExchangeTransactionContract`.
