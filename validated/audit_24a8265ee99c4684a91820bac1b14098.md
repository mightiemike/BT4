### Title
Order-book pre-positioning DoS in `MarketSellAssetActuator` causes fee loss and blocks legitimate matching - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
The `LamboWin` `rebalance()` bug lets a malicious actor front-run/pre-position state so that a beneficial transaction's post-condition check reverts, causing the honest caller to lose gas/fees and the protocol to fail to reach its target state. `MarketSellAssetActuator.matchOrder()` in java-tron's on-chain TRC10 market has an analogous, reachable pattern: an unprivileged attacker can pre-populate an order book with many small maker orders at the best price so that any subsequent large taker order is forced through `MAX_MATCH_NUM` iterations and reverts with `ContractExeException`, after the taker's fee has already been deducted and burned/transferred.

### Finding Description
`execute()` first deducts and burns/transfers the sell fee and transfers the sell-token balance out of the taker's account, and only afterwards calls `matchOrder()`: [1](#0-0) 

Inside `matchOrder()`, the taker's order is matched sequentially against maker orders at the best price; if the number of orders touched exceeds `MAX_MATCH_NUM` (20), the method throws `ContractValidateException("Too many matches...")`: [2](#0-1) 

This exception propagates out of `execute()`'s try block and is converted into a `ContractExeException`, but only after the fee-deduction and token-transfer side effects have already been applied within the same `execute()` call: [3](#0-2) 

An attacker (any unprivileged account, no special permission required) can place 21+ tiny maker sell orders at the best available price for a given token pair via ordinary `MarketSellAssetContract` broadcasts. When a legitimate large taker order arrives to match against that price level, `matchOrder()`'s inner loop is forced to iterate through more than `MAX_MATCH_NUM` maker orders, and the whole actuator execution throws — exactly mirroring the external report's pattern where a malicious counterparty manipulates on-chain state before the victim's transaction executes, causing the victim's beneficial action to revert despite fees/resources already having been irrevocably consumed for the deduction/transfer steps performed earlier in `execute()`.

### Impact Explanation
This is a DoS vector against the exchange/market-math actuator: attackers can grief legitimate large taker orders, forcing repeated failed transactions and burned/consumed `MarketSellFee` (TRX) for victims, and can be used to block a specific token pair's matching entirely by keeping ≥`MAX_MATCH_NUM` micro-orders resident at the best price. This causes accounting/resource loss for victims (analogous to "loss of funds for protocol and its users" in the source report) and denial of market rebalancing/liquidity clearing for a token pair.

### Likelihood Explanation
Likelihood is moderate: placing many small orders costs the attacker the per-order `MarketSellFee` for each maker order (a cost), and `MAX_MATCH_NUM` is a fixed constant (20) that could be reached at reasonably low cost. Any account can create market orders without special privileges, making this reachable by any anonymous broadcaster of the `MarketSellAssetContract` transaction type. This is unlike the original DeFi report (which relies on flashloans/mempool front-running with no persistent cost); here the attack requires sustained order placement fees, somewhat reducing incentive/likelihood versus the original report.

### Recommendation
- Perform the `MAX_MATCH_NUM` check (and any other state that can cause `matchOrder` to fail) in `validate()` before any balance/fee mutation occurs in `execute()`, or ensure the entire actuator's state changes (including fee burn/transfer) are only committed after `matchOrder()` completes successfully, so a matching failure never leaves the taker's fee/token already spent.
- Consider making `MAX_MATCH_NUM` dynamic/configurable and enforcing a limit on the number of maker orders resident at a single best price level per account/pair to reduce the attacker's ability to cheaply saturate the match queue.
- Add a "not enough remaining resources to complete match" pre-check that reverts before mutating account balances.

### Proof of Concept
1. Attacker account (unprivileged) broadcasts 25 `MarketSellAssetContract` transactions selling token A for token B, each with the exact same effective price (e.g. sell 1 A for 2 B repeated 25 times), all resting at the best price for the pair `A->B`.
2. Victim broadcasts a large `MarketSellAssetContract` selling token B for token A intended to sweep the order book at that price.
3. `execute()` in `MarketSellAssetActuator` first deducts the victim's `MarketSellFee` (burned/transferred) and transfers the sell-token balance out of the victim's account (`transferBalanceOrToken`) — see [1](#0-0) .
4. `matchOrder()` iterates the 25 resting orders, exceeds `MAX_MATCH_NUM = 20`, and throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")` as seen in [4](#0-3) .
5. The transaction fails with `code.FAILED` yet the victim's already-deducted fee (and possibly partially-transferred token balance state, depending on DB-session rollback semantics) represents wasted resources, and the victim's intended trade never completes — a repeatable DoS against that pair's matching.
