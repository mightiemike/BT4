## Title
`replay-verify`'s transaction-output equivalence check never validates the state (Sparse Merkle Tree) checkpoint root, allowing silent state-root divergence to pass as "verified" — (File: `types/src/transaction/mod.rs`)

### Summary
The `TransactionOutput::ensure_match_transaction_info` function is the sole cross-check used by `storage/db-tool/src/replay_on_archive.rs` (the `replay-verify` tool) to confirm that a freshly re-executed transaction output matches the transaction info that was actually committed and authenticated on-chain (fetched from the local archive DB, which is populated from state-sync/backup with accumulator-proof-verified data). This function checks transaction status, gas used, the write-set hash, and the event root hash, but never compares `state_checkpoint_hash` — the Jellyfish/Sparse Merkle Tree root summarizing the full world state at a checkpoint — against the value actually present in the authenticated `TransactionInfo`.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only:
- `status()` vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed event root vs `txn_info.event_root_hash()`

It never reads or compares `txn_info.state_checkpoint_hash()` (the world-state Merkle root at checkpoint boundaries) at all. The function even contains an explicit acknowledgement of a closely related gap: [2](#0-1) 
which only calls out that hot-state and position-state checkpoint hashes are skipped — but the comment is misleading because the base `state_checkpoint_hash` (the one field always populated for every real checkpoint transaction, independent of the "trading-native" feature) is *also* never checked anywhere in this function.

This function is the actual correctness oracle used by `execute_and_verify` in the `replay-verify` tool: it replays historical transactions with a fresh VM against `self.arc_db`'s state view and compares the freshly computed `TransactionOutput` to the `expected_txn_infos` pulled from the already-persisted, accumulator-authenticated ledger data: [3](#0-2) 

Matching the write-set hash only proves the *delta* produced by a transaction matches; it says nothing about whether applying that delta to the prior JMT/SMT actually reproduces the same overall state root that was committed to the ledger and referenced by `state_checkpoint_hash`. A state-tree bug (e.g., in JMT construction, key hashing, restore/replay reconciliation, or a storage-schema reinterpretation) that corrupts the checkpoint root while leaving individual per-transaction write sets, gas, status, and events unchanged would go completely undetected by `replay-verify`.

### Impact Explanation
`replay-verify` exists specifically to catch state-commitment divergence between local re-execution and the authenticated ledger — this is the audit tool operators and the Foundation rely on to catch determinism/state-corruption bugs, including ones that would otherwise require a hard fork to fix. Because the state checkpoint root is never compared, a real divergence in the committed world-state root (the most safety-critical invariant of the whole system) is invisible to this tool: it will report a clean "verified" result even though the actual account/resource state at that version diverges from mainnet. This directly matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong ... state proof accepted as valid" impact categories, since checkpoint hashes are exactly what downstream proof verification (`TransactionInfoWithProof`, state proofs) binds to.

### Likelihood Explanation
This isn't a probabilistic external-attacker exploit; it's a structural gap in an existing, always-invoked verification path — any state-root-corrupting bug anywhere in the executor/storage stack (independent root cause) will always slip past `replay-verify` undetected, silently, on every affected version. The comment at lines 2197-2203 shows the team is aware of the adjacent hot-state/position-state gap but the same code path shows the base `state_checkpoint_hash` field is unconditionally skipped too.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`'s locally reconstructed `state_checkpoint_hash` (when present on the checkpoint transaction) against `txn_info.state_checkpoint_hash()`, and add equivalent validation for hot-state and position-state checkpoint hashes before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, consistent with the existing TODO in the code.

### Proof of Concept
1. In `replay_on_archive.rs`, run `replay-verify` over a version range containing a checkpoint transaction.
2. Introduce (or trigger) any state-tree/state-store bug that changes the final SMT/JMT root at that checkpoint while leaving the individual transaction's write set, gas, status, and events byte-identical to what's expected (e.g. a bug in how prior versions' state is folded into the tree, not in the transaction's own write set).
3. `ensure_match_transaction_info` at [4](#0-3)  passes all four checks it performs.
4. `execute_and_verify` reports no error for this chunk: [5](#0-4) , even though the actual committed world-state root has diverged from the value replay computed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
