### Title
Stale unbounded `cycle-total-weight` cache in `signers-voting.clar` lets a re-registered signer set forge aggregate-key approval below the true 70% threshold - ([File: stackslib/src/chainstate/stacks/boot/signers-voting.clar])

### Summary
`signers-voting.clar` caches the total signing weight for a reward cycle the first time `get-and-cache-total-weight` is called, and never invalidates or refreshes that cache for the rest of the cycle:

```
(define-private (get-and-cache-total-weight (reward-cycle uint))
    (match (map-get? cycle-total-weight reward-cycle)
        total (ok total)
        (let ((signers (unwrap! (contract-call? .signers get-signers reward-cycle) (err ERR_FAILED_TO_RETRIEVE_SIGNERS)))
                (total (fold sum-weights signers u0)))
            (map-set cycle-total-weight reward-cycle total)
            (ok total))))
``` [1](#0-0) 

Meanwhile, `get-signer-weight` (used per-vote) always reads the *live* signer entry via `.signers get-signer-by-index`, which the `.signers` contract permits to be overwritten for the same `reward-cycle` as long as `last-set-cycle` still equals that cycle:

```
(define-private (set-signers (reward-cycle uint) (signers (list 4000 { signer: principal, weight: uint })))
     (begin
      (asserts! (is-eq (var-get last-set-cycle) reward-cycle) (err ERR_CYCLE_NOT_SET))
      (ok (map-set cycle-signer-set reward-cycle signers))))
``` [2](#0-1) 

This is the direct structural analog of the reported bug: a value ("price"/weight) is cached without any timestamp or invalidation, while a second code path consumes the fresh, potentially different, underlying data — creating a window where a validation check (the 70% consensus threshold) is evaluated against stale denominator data.

### Finding Description
The vote-tallying threshold in `vote-for-aggregate-public-key` is computed as:
```
(cached-weight (try! (get-and-cache-total-weight reward-cycle)))
(threshold-weight (get-threshold-weight reward-cycle))
...
(if (>= new-total threshold-weight) ... )
``` [3](#0-2) 
and
```
(define-read-only (get-threshold-weight (reward-cycle uint))
    (let  ((total-weight (default-to u0 (map-get? cycle-total-weight reward-cycle))))
        (/ (+ (* total-weight threshold-consensus) u99) u100)))
``` [4](#0-3) 

Both `threshold-weight` and `cached-weight` are read from the SAME cached map `cycle-total-weight`, set only once per reward cycle via `get-and-cache-total-weight` on the first vote of that cycle. There is no timestamp, height check, or re-derivation trigger tied to `cycle-signer-set` mutations. If the node calls `set-signers` a second time for the same `reward-cycle` (permitted by the on-chain assertion, which only checks `last-set-cycle == reward-cycle`, not "has-not-been-set-yet") — for example due to a reward-cycle boundary being reprocessed after a burnchain fork/reorg causing a different anchor-block/reward-set computation for the same cycle number — the `.signers` map (`cycle-signer-set`) is updated to a new signer list/weights, but `cycle-total-weight` for that cycle keeps the OLD total from the first computation forever, exactly mirroring `_lastPriceOnUpkeepBTC`/`_lastPriceOnUpkeepETH` staying stale after `performUpkeep` stops running.

After such a re-registration, `get-signer-weight` (which reads live per-signer weight from `.signers get-signer-by-index`) will report weights consistent with the NEW, larger signer set/weight distribution, while `threshold-weight`/`cached-weight` still reflect the OLD (smaller) total. Consequently, a coalition of signers whose weight is smaller than 70% of the true, current total signer weight can still push `new-total >= threshold-weight`, because `threshold-weight` was computed off the stale (smaller) denominator — breaking the intended equality "≥70% of the current total signer weight approved the aggregate public key."

### Impact Explanation
This is a minority-triggerable divergence between the stated/expected voting-weight threshold (based on the current, canonical signer set) and the actual weight required to pass, analogous to a "signer weight below threshold" bypass called out in-scope. It can let an aggregate public key be approved (`map-insert aggregate-public-keys reward-cycle key`) without genuine 70% support from the current reward-cycle's signer set, which downstream affects consensus over Nakamoto block signing/threshold verification (`compute_voting_weight_threshold` / `verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs`) since the wrong aggregate key or a weight-threshold rooted in stale data feeds into node-level agreement — a High-severity condition (bounded, minority-triggerable validation divergence), not requiring an admin/majority.

### Likelihood Explanation
Requires the (rare, but permitted by contract logic) re-invocation of `set-signers` for the same `reward-cycle` — the on-chain assertion (`is-eq (var-get last-set-cycle) reward-cycle)`) does not forbid overwriting an already-set cycle's signer list, only requires that the "current" pointer still targets that cycle. Whether stacks-core's reward-set computation logic can re-derive and re-write a different signer list for the same cycle number (e.g. across a burnchain reorg before the cycle boundary finalizes) could not be fully confirmed from the code paths inspected in this session (the exact call site invoking `update_signers`/`set-signers` per reward-cycle transition was not located before the iteration budget ran out), so likelihood is assessed as plausible-but-unconfirmed rather than proven.

### Recommendation
- Short term: invalidate/recompute `cycle-total-weight` whenever `cycle-signer-set` is (re)written for a reward cycle (e.g., clear the cache entry inside `set-signers`, or fold weight computation directly into `set-signers` and store it there instead of lazily caching in the voting contract).
- Long term: remove the separate caching map entirely and have `get-threshold-weight`/`get-and-cache-total-weight` always derive the total weight directly from the live `cycle-signer-set` for the reward cycle, eliminating any window where threshold and per-signer weight lookups can read from different generations of the reward set.

### Proof of Concept
1. Reward cycle `R` begins; `.signers` is populated via `set-signers(R, listA)` with `total_weight(listA) = 100`.
2. A signer casts the first vote of cycle `R`; `get-and-cache-total-weight(R)` computes and caches `cycle-total-weight[R] = 100`; `threshold-weight = ceil(100*70/100) = 70`.
3. Before voting concludes, the node (through whatever path can legitimately call `set-signers` again for the same `reward-cycle`, gated only by `last-set-cycle == R`) re-registers a different signer set `listB` with `total_weight(listB) = 200` (e.g. reflecting a corrected/re-derived reward set for the same cycle).
4. `get-signer-weight` now returns weights sourced from `listB` for subsequent voters, but `cycle-total-weight[R]` and thus `threshold-weight` remain frozen at the stale value derived from `listA` (70, out of a true total of 200).
5. A coalition of signers holding, say, 80 weight-units out of the true 200 (40% — below the intended 70% consensus) can push `new-total` to 80 ≥ 70 (the stale threshold), causing `map-insert aggregate-public-keys reward-cycle key` to succeed and the "approved-aggregate-public-key" event to fire — a bypass of the intended 70%-of-current-total-weight consensus rule.
