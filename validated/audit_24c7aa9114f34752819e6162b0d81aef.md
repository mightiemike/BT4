### Title
Front-runnable AMM liquidity operations without slippage protection in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron implements an on-chain Bancor-style AMM ("Exchange") with three broadcastable contract types: `ExchangeTransactionContract` (swap), `ExchangeInjectContract` (add liquidity), and `ExchangeWithdrawContract` (remove liquidity). Only `ExchangeTransactionContract` carries a caller-supplied `expected` (minimum-received) field that is validated against the freshly computed swap output [1](#0-0) . `ExchangeInjectContract` and `ExchangeWithdrawContract` have no equivalent bound: the counter-token amount is derived purely from the pool's *current* ratio at execution time, with no user-supplied min/max to reject an unfavorable price [2](#0-1) [3](#0-2) . This is the same bug class described in the external report: swap/liquidity operations execute at whatever price is on-chain at the moment of execution, with the specific parameter that would let the caller bound their exposure to price movement (analogous to `minimum-amount-out`) hardcoded absent for these two operations, while it exists for the third.

### Finding Description
`ExchangeInjectContract`/`ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/slippage bound field, per the protocol documentation [4](#0-3) . In `ExchangeInjectActuator.execute`, the amount of the paired token the caller must additionally contribute (`anotherTokenQuant`) is computed strictly from the exchange's `firstTokenBalance`/`secondTokenBalance` at execution time [5](#0-4) . In `ExchangeWithdrawActuator.execute`, the amount of the paired token returned to the caller is likewise derived from the live pool ratio [6](#0-5) .

Because these are ordinary broadcast transactions visible in the mempool before block inclusion, an attacker can submit an `ExchangeTransactionContract` swap immediately before the victim's inject/withdraw transaction to shift `firstTokenBalance`/`secondTokenBalance`, and (optionally) a second swap immediately after to restore the price — a classic sandwich. Unlike `ExchangeTransactionActuator`, whose `validate()` re-checks `anotherTokenQuant` against the caller's `expected` value and reverts the transaction if the price moved unfavorably [1](#0-0) , neither `ExchangeInjectActuator.doValidate` nor `ExchangeWithdrawActuator.doValidate` bounds `anotherTokenQuant` against any caller-supplied expectation — they only check that it is positive and within the configured balance limit [7](#0-6) [8](#0-7) .

### Impact Explanation
A victim performing `ExchangeInject` can be forced, by a front-run swap, to contribute an inflated amount of the paired asset for the same declared `quant`, or a victim performing `ExchangeWithdraw` can be made to receive a deflated amount of the paired asset — in both cases at a price manipulated away from the pre-transaction market rate, resulting in a direct economic loss transferred to the sandwiching attacker. This is an accounting/asset-corruption impact on the exchange's liquidity provider (only `exchangeCapsule.getCreatorAddress()` may call inject/withdraw per [9](#0-8)  and [10](#0-9) ), but the attack itself is executed entirely by an unprivileged, anonymous mempool participant via ordinary broadcast transactions.

### Likelihood Explanation
Exploitation requires only observing a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction in the mempool and submitting bracketing `ExchangeTransactionContract` swaps with sufficient fee/bandwidth to be ordered before (and after) it — no special network position, validator collusion, or private relay is required, unlike the Gelato-only swaps discussed in the source report. The likelihood is moderated only by the restriction that the caller of inject/withdraw must be the exchange's creator, which limits how often such transactions occur, but does not reduce the attacker's capability once one is broadcast.

### Recommendation
Add a caller-specified bound (e.g., a `max_another_token` or `min_another_token` field) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the freshly computed `anotherTokenQuant` against it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, mirroring the `expected` check already present in `ExchangeTransactionActuator` [1](#0-0) , so the transaction reverts if the pool ratio has moved unfavorably between broadcast and execution.

### Proof of Concept
1. Eve monitors the mempool for a broadcast `ExchangeInjectContract` (or `ExchangeWithdrawContract`) from the exchange creator specifying `token_id`/`quant`.
2. Eve broadcasts an `ExchangeTransactionContract` swap with a higher fee/priority to execute immediately before the victim's transaction, shifting `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule` via `ExchangeCapsule.transaction` [11](#0-10) .
3. When the victim's `ExchangeInjectActuator.execute`/`ExchangeWithdrawActuator.execute` runs, `anotherTokenQuant` is computed against the now-skewed pool balances [2](#0-1) , causing the victim to deposit more / withdraw less of the paired token than intended, with no on-chain check to reject this.
4. Eve optionally submits a reverse swap afterward to restore the pool price and realize the extracted value, completing the sandwich.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
