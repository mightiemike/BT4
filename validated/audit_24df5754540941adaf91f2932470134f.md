### Title
Standby-witness reward dilution from vote-count update ordering in `IncentiveManager.reward()` - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
`MaintenanceManager.doMaintenance()` updates each witness's `voteCount` with the votes newly cast during the just-finished cycle, and only afterwards calls `incentiveManager.reward(newWitnessAddressList)` to pay standby-witness allowances proportional to `voteCount`. This mirrors the Burve H-4 pattern: the denominator used to split a pre-accrued reward pool is updated with new stake *before* the reward is distributed, diluting the share owed to voters who held their stake throughout the period being rewarded.

### Finding Description
In `doMaintenance()`, votes accumulated in `VotesStore` during the cycle are tallied via `countVote()` and merged into each witness's `voteCount` immediately: [1](#0-0) 

Right after this update, `incentiveManager.reward(newWitnessAddressList)` is invoked: [2](#0-1) 

`IncentiveManager.reward()` computes `voteSum` from the *current* (just-updated) `voteCount` of each standby witness and divides a fixed `totalPay` (`witnessStandbyAllowance`) proportionally: [3](#0-2) 

Because `voteCount` was already inflated with brand-new votes cast during the cycle that just ended (via `countVote`/`witnessCapsule.setVoteCount(...)`), those new voters — who did not hold their stake for the period the `totalPay` reward corresponds to — dilute the share owed to existing voters, exactly matching the root cause described in the Burve report (`valueStaked`/`self.bgtValueStaked` updated before `addEarnings()`/reward-per-share computation).

By contrast, the newer reward path correctly avoids this: `MaintenanceManager` calls `delegationStore.accumulateWitnessVi(curCycle, ..., witness.getVoteCount())` *before* the vote-count update for the same cycle, and `setWitnessVote(nextCycle, ...)` is only recorded for the following cycle's snapshot: [4](#0-3) [5](#0-4) 

`IncentiveManager.reward()` itself only guards against running when `allowChangeDelegation()` is enabled — i.e., it is the active reward path for standby witnesses under the *old* (pre-new-reward-algorithm) delegation model: [6](#0-5) 

### Impact Explanation
On any network state where `allowChangeDelegation` is not yet enabled (the legacy reward mechanism), every maintenance cycle with new votes cast for standby witnesses will systematically under-pay long-term voters and over-pay/dilute-favor freshly cast votes, resulting in unfair, non-deterministic-by-design reward misallocation. This is an accounting/fee-distribution correctness bug affecting on-chain reward payouts, analogous to the Sherlock H-4 finding, though its blast radius is limited to the legacy path guarded by `allowChangeDelegation`.

### Likelihood Explanation
This triggers naturally and unconditionally whenever votes change for a standby witness in a cycle under the legacy algorithm — no attacker action or special preconditions are required, matching the "happens naturally" characterization of the original report.

### Recommendation
Snapshot `voteCount` (or the pre-update `voteSum`) prior to updating witness vote counts with the current cycle's new votes, and use that snapshot as the denominator in `IncentiveManager.reward()`, consistent with how `accumulateWitnessVi` in the new algorithm captures `witness.getVoteCount()` before applying `countWitness` updates.

### Proof of Concept
Conceptual trace based on code order in `doMaintenance()`:
1. Witness W has `voteCount = 1000` at start of cycle, all held by Alice for the entire cycle duration (this is the stake that "earned" the standby allowance for this cycle).
2. During the cycle, Bob votes 9000 for W (recorded in `VotesStore`, not yet merged into `voteCount`).
3. At maintenance: `countVote()` computes `+9000` for W; `witnessCapsule.setVoteCount(1000 + 9000) = 10000` is saved immediately.
4. `incentiveManager.reward(newWitnessAddressList)` runs next, computing `voteSum` including Bob's 9000, so Alice — who alone earned the standby reward for the elapsed cycle — receives only `1000/10000` of `totalPay` instead of the full amount, while Bob (who just voted and contributed nothing to that cycle) is credited a share he did not earn.   public void reward(List<ByteString> witnesses) {
    if (consensusDelegate.allowChangeDelegation()) {
      return;
    }
    if (witnesses.size() > WITNESS_STANDBY_LENGTH) {
      witnesses = witnesses.subList(0, WITNESS_STANDBY_LENGTH);
    }
    long voteSum = 0;
    for (ByteString witness : witnesses) {
      voteSum += consensusDelegate.getWitness(witness.toByteArray()).getVoteCount();
    }
    if (voteSum <= 0) {
      return;
    }
    long totalPay = consensusDelegate.getWitnessStandbyAllowance();
    for (ByteString witness : witnesses) {
      byte[] address = witness.toByteArray();
      long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay
          / voteSum));
      AccountCapsule accountCapsule = consensusDelegate.getAccount(address);
      accountCapsule.setAllowance(accountCapsule.getAllowance() + pay);
      consensusDelegate.saveAccount(accountCapsule);
    }
  }
