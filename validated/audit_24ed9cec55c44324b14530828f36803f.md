## Finding

### Title
Cross-Context HMAC Signature Replay Between Webhook, Flow, and Fulfillment-Service Validation - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`shopify.webhooks.validate`, `shopify.flow.validate`, and `shopify.fulfillmentService.validate` all funnel through the same `validateHmacFromRequestFactory`, which authenticates a request purely by computing `HMAC-SHA256(apiSecretKey, rawBody)` (base64) and comparing it to the `X-Shopify-Hmac-Sha256` header. None of these three "policy instances" mix any context-specific data (endpoint type, topic, destination) into the signed message, so an HMAC that Shopify legitimately generated for one surface (e.g. a webhook delivery) is byte-for-byte indistinguishable from — and therefore acceptable as — a valid signature for a completely different surface (a Flow action call or a Fulfillment Service callback) whenever the raw body happens to match.

### Finding Description
`validateHmacFromRequestFactory` is shared across `HmacValidationType.Webhook`, `HmacValidationType.Flow`, and `HmacValidationType.FulfillmentService`: [1](#0-0) 

For the non-Events webhook type and for Flow/Fulfillment (`webhookType` is `undefined`), the header used is the same constant, `ShopifyHeader.Hmac`, and the "message" that gets signed is only the `rawBody` — nothing identifies which policy/endpoint the signature was meant for: [2](#0-1) 

`packages/apps/shopify-api/lib/flow/validate.ts` and `packages/apps/shopify-api/lib/fulfillment-service/validate.ts` both call this exact same factory with no additional binding data: [3](#0-2) 

This is structurally identical to the `ApprovedCallsPolicy` bug: several distinct "policy instances" (here, three distinct verification entry points — Webhook, Flow, Fulfillment Service) share the same signing secret (`apiSecretKey`, the on-chain analog of `SIGNER_ROLE`) and construct an identical message hash with no domain separator (the on-chain analog of "include the verifying address in the signature"). The library has already recognized and partially fixed this exact bug class for cookies — a changelog entry shows that OAuth state/session cookie signatures used to be directly reusable as webhook HMACs, and the fix was to derive a cookie-specific key via HKDF (`COOKIE_SIGNING_INFO`) rather than signing with the raw secret: [4](#0-3) [5](#0-4) 

That fix, however, was scoped only to the `Cookies` signing path. It was never extended to `validateHmacFromRequestFactory`, so Webhook/Flow/Fulfillment-Service verification still signs with the raw `apiSecretKey` and no domain separator, leaving the exact reuse vector that the cookie fix was designed to close open between these three verification surfaces.

### Impact Explanation
Any app that implements more than one of these validators (a very common pattern — e.g. an app that both receives regular webhooks and also acts as a Flow action provider or a Fulfillment Service) is exposed to cross-surface signature replay: a valid `(rawBody, X-Shopify-Hmac-Sha256)` pair genuinely issued by Shopify for one context (e.g., a webhook delivery containing attacker-influenced content, such as an order note or product field set by a merchant who installed the app in their own store) can be replayed verbatim against a different validation endpoint of the same app (Flow action handler or Fulfillment Service callback) and will pass authentication, because the signed message and secret are identical across all three surfaces. This allows a forged/accepted "Shopify request" at an endpoint it was never intended for, potentially triggering unintended app logic (e.g., invoking a Flow action or fulfillment callback) using attacker-controlled body content.

### Likelihood Explanation
Exploitation requires: (1) the target app to expose at least two of {webhook, Flow, fulfillment-service} validation endpoints, and (2) the attacker to obtain a genuine `(rawBody, hmac)` pair — achievable by any user who can install the app on their own development/test store and trigger a webhook, Flow, or fulfillment call with content they control, then replay that captured pair against the other endpoint. No secret material needs to be leaked and no privileged role is required beyond installing the app on an attacker-controlled shop, which is standard for any Shopify app. This is a moderate-likelihood issue since it depends on the specific app combining multiple validators, but the shopify-app-js library itself provides no domain separation to prevent it, unlike the cookie-signing surface, which was already hardened for this exact bug class.

### Recommendation
Extend the domain-separation fix already applied to `Cookies.setAndSign`/`isSignedCookieValid` (HKDF-derived, purpose-specific key via `deriveSHA256HMACKey`) to `validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts`. Derive a distinct signing key per `HmacValidationType` (Webhook vs Flow vs FulfillmentService), e.g. `deriveSHA256HMACKey(apiSecretKey, 'shopify-app-js/webhook-hmac/v1')`, `.../flow-hmac/v1`, `.../fulfillment-service-hmac/v1`, mirroring `COOKIE_SIGNING_INFO`. This prevents a signature generated for one verification surface from ever validating against another, closing the same replay class that was already fixed for cookies.

### Proof of Concept
1. Attacker installs the target app on a shop they control and configures a webhook (or Flow trigger, or fulfillment-service order) whose payload body they can influence (e.g., set a custom field/note to arbitrary text `B`).
2. Shopify delivers the request to the app's webhook endpoint with `rawBody = B` and header `X-Shopify-Hmac-Sha256 = HMAC-SHA256(apiSecretKey, B)` (base64) — the attacker captures this `(B, hmac)` pair (they control the traffic to their own store's app installation, or can proxy/log the request).
3. Attacker sends `B` and the same `hmac` header to the app's Flow-action or Fulfillment-Service endpoint (which independently call `shopify.flow.validate()` / `shopify.fulfillmentService.validate()`), targeting a different shop's tenant if the app's routing allows shop selection from the body/query rather than a value bound into the HMAC.
4. Because `validateHmacFromRequestFactory` verifies only `HMAC-SHA256(apiSecretKey, rawBody)` with no type/context binding, the forged request passes validation at the second endpoint, demonstrating cross-context signature replay.

```typescript
export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
```
