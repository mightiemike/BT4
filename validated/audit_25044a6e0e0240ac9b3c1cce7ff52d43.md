### Title
Single-flight guard on the Wallet Contract's `rlp_execute` is set only on the happy path, allowing a second transaction to be admitted while the first is still in flight - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
This is the closest reachable analog in nearcore to the Sherlock finding: a state-mutating entry point that dispatches a cross-contract callback without robust "reentrancy" protection. The NEAR Wallet Contract (`near-wallet-contract`) implements Ethereum-transaction emulation and explicitly tries to prevent overlapping in-flight transactions with a boolean flag `has_in_flight_tx`, exactly analogous to a `nonReentrant` guard, because `rlp_execute` creates promises with callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) that mutate contract state (`nonce`) after external cross-contract calls complete.

### Finding Description
`WalletContract::rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`) checks `self.has_in_flight_tx` at entry, and only sets it to `true` when a `Promise` is produced by `inner_rlp_execute`, or when a `Error::Relayer` short-circuit path builds a ban-relayer promise: [1](#0-0) 

The single-flight invariant is documented explicitly on the struct field: [2](#0-1) 

The flag is reset to `false` at the start of every "leaf" callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) before those callbacks decide whether to schedule a further promise and set the flag `true` again: [3](#0-2) [4](#0-3) 

Because NEAR's actor-model receipt execution serializes calls to a given contract account (there is no synchronous EVM-style callback re-entry within a single WASM execution), the direct Solidity-style reentrancy described in the report does not map 1:1. The relevant analog is whether an *intervening* transaction targeting the same Wallet Contract account could be admitted and executed while a previous multi-hop promise chain (which increments `nonce` only in a callback, per `inner_rlp_execute`, lines 347-410) is still unresolved — i.e., a window where `has_in_flight_tx` is `false` even though a promise chain from a prior call is logically still "in flight" as far as its nonce bookkeping/refund side effects go, because the flag toggles false→true across two separate contract executions (main call and callback), and any receipt targeting the same account executed in between (e.g. from a different, concurrently-submitted relayer transaction) would observe `has_in_flight_tx == false` and be admitted.

### Impact Explanation
If the flag window can be raced by a malicious/faulty relayer submitting a second `rlp_execute` transaction using the same access key at the moment the flag is momentarily `false` (before the promise created in `inner_rlp_execute` is returned and the field is persisted, or is momentarily false again between the "callback resetting it to false" and "callback setting it back to true"), then a user's nonce/action ordering guarantees could be violated, leading to reordering or double-processing of the same nonce's action, unauthorized replay, or unexpected fund movement (fees, refunds, or NEP-141 transfers) tied to the eth-emulation logic. However, I could not conclusively verify within the indexed code whether such an intervening receipt is actually schedulable in the same or an overlapping block (this depends on receipt ordering guarantees enforced elsewhere in the runtime, e.g. per-account receipt queues, which I was not able to fully trace with the available tools).

### Likelihood Explanation
Low-to-uncertain. NEAR's runtime generally processes receipts to a given account sequentially and function-call state changes are committed atomically per receipt, which is a much stronger isolation guarantee than EVM's single-transaction call stack that the original Sherlock finding depends on. Exploiting this would require a relayer to control/submit a second transaction referencing the same access key while the flag is toggled between calls (across block boundaries, since each promise hop is its own receipt/block step), which is a narrower, harder-to-trigger race than the original Solidity reentrancy bug. I was unable to fully confirm from the indexed files whether nearcore's scheduling could actually produce the described race window.

### Recommendation
- Audit the exact receipt/callback boundaries in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` to confirm no receipt destined for the same Wallet Contract account can be scheduled/executed between the point `inner_rlp_execute` returns a promise and the point `has_in_flight_tx` is persisted as `true` (lines 116-127), and between each callback's `self.has_in_flight_tx = false` reset and its own re-arming of the flag (lines 140, 190-191, 202, 271-272, 280, 321).
- Consider setting `has_in_flight_tx = true` deterministically before any promise-creating side effects are computed (fail-closed), rather than only on the `Ok`/ban-relayer branches, and re-verify invariants with a state-machine style test that submits two `rlp_execute` calls back-to-back across the callback boundary to ensure the second is always rejected until the full multi-hop chain, including all callbacks, has resolved.

### Proof of Concept
Not constructible with the tools available — this would require running the NEAR test-loop/runtime harness (e.g., patterns similar to `test-loop-tests/src/tests/yield_resume.rs`) to submit two `rlp_execute` transactions from the same relayer/access key in adjacent blocks and observe whether the second is admitted while `has_in_flight_tx` briefly reads `false` between hops of the first transaction's promise chain. This is flagged as unverified and would need dynamic testing to confirm exploitability.

    #[payable]
    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
