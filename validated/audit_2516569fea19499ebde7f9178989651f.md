## Finding

### Title
Meta-transaction (`DelegateAction`) sender can redirect the relayer's prepaid deposit to themselves on inner-action failure - (File: `runtime/runtime/src/actions.rs`)

### Summary
In NEAR's meta-transaction (NEP-366) flow, the relayer purchases and attaches the deposit for the inner actions on behalf of the delegate-action sender ("Alice"). If the inner action fails, the protocol's uniform deposit-refund rule sends the refund to the `predecessor_id` of the failing receipt — which for a delegate action's inner receipt is Alice, not the relayer who actually paid for the deposit. Alice, as an unprivileged account who merely signs the inner `DelegateAction`, can craft an inner action that is guaranteed (or highly likely) to fail after the relayer has funded it, causing the relayer's tokens to be refunded to Alice instead of back to the relayer. This mirrors the reported `mintWithReferralFor()` bug class: two logically linked concepts (who pays vs. who is authorized to reclaim the payment) are supplied/controlled independently, letting the unprivileged party redirect value that should return to the payer to themselves.

### Finding Description
`apply_delegate_action` in [1](#0-0)  constructs the inner receipt with `predecessor_id: sender_id.clone()` (Alice) while the relayer is only the `signer_id`/gas payer. The comment in the code explicitly flags this: [2](#0-1) 

This is confirmed by the general refund rule documented in [3](#0-2) : deposit refunds always go to `predecessor_id`, "because only the predecessor can attach deposits" — an assumption that does not hold for meta-transactions, where the relayer (not the predecessor) actually funds the deposit.

The project's own architecture docs describe the exact exploit condition: [4](#0-3)  — "there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard."

Gas refunds are correctly routed to the relayer (`signer_id`) as shown in [5](#0-4) , but the balance/deposit refund logic in `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs`) and `Receipt::new_balance_refund` ( [6](#0-5) ) uses `receipt.balance_refund_receiver()`, which resolves to the failing receipt's predecessor — Alice — not the relayer.

### Impact Explanation
A relayer that funds meta-transactions can have its prepaid deposit siphoned to the delegate-action sender whenever the sender crafts (or can influence) an inner action to fail after the deposit has been attached. This is concrete unauthorized value movement from the relayer's balance to an unprivileged third party (the meta-tx sender), triggered purely by a single submitted meta-transaction/delegate action. Relayer services (widely used for gasless UX, e.g., wallets, dApp backends) that don't strictly pre-simulate and bound every possible failure path are exposed to direct fund loss.

### Likelihood Explanation
This requires only that (a) a relayer service accepts and forwards `DelegateAction`s from arbitrary/untrusted senders and attaches nontrivial deposits on their behalf, and (b) the sender can craft an inner action likely to fail (e.g., calling a nonexistent method, targeting a contract state that will reject the call, or exploiting execution-order/race conditions) after the deposit was already committed. Because relayer designs vary and the docs explicitly warn implementers about this, it is a realistic, moderate-likelihood risk for any relayer that funds meta-transaction deposits without safeguards, and it's already been implicitly acknowledged in the docs rather than mitigated at the protocol level.

### Recommendation
Decouple deposit-refund routing from `predecessor_id` for delegate-action-spawned receipts: track and refund deposit failures for inner actions of a `Delegate`/`DelegateV2` action back to the actual relayer (the original transaction `signer_id`) rather than the DelegateAction's `sender_id`, or require relayers to explicitly opt into per-delegate-action refund routing (analogous to `promise_set_refund_to`) before submitting, with protocol-level enforcement rather than relying solely on relayer-side vetting/simulation of every inner action.

### Proof of Concept
1. Relayer receives a `SignedDelegateAction` from Alice whose inner action is a `FunctionCall` to `bob.near::nonexistent_method` (or any call engineered to fail) with a large `deposit` attached and minimal `gas`.
2. Relayer wraps it in a transaction (`Action::Delegate`), signs it as `signer_id`, and submits it on-chain, per the flow in `apply_delegate_action` ( [7](#0-6) ): the new receipt has `predecessor_id: sender_id` (Alice), funded from relayer's prepaid balance.
3. On Bob's shard, the `FunctionCall` fails (method not found). `refund_unspent_gas_and_deposits` generates a deposit-refund receipt via `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)` targeting the failing receipt's predecessor, i.e., Alice — not the relayer who funded the deposit.
4. Result: Alice receives the deposit tokens that the relayer paid for; the relayer only gets its unused gas refunded (per the correct signer-based gas-refund path), suffering a net token loss to an unprivileged counterparty it merely relayed a transaction for. [8](#0-7)  demonstrates the general mechanics of deposit-refund redirection to a chosen `predecessor`/beneficiary on receipt failure, which is the same underlying primitive exploited here for meta-transactions.

```markdown
## Gas refunds in meta transactions

Gas refund receipts work exactly like for normal transaction. At every step, the
difference between the pessimistic gas price and the actual gas price at that
height is computed and refunded. At the end of the last step, additionally all
remaining gas is also refunded at the original purchasing price. The gas refunds
go to the signer of the original transaction, in this case the relayer. This is
only fair, since the relayer also paid for it.
```

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```

```rust
// redirect the balance refund using `promise_refund_to`
#[test]
fn test_refund_to() {
    let group = RuntimeGroup::new(4, 4, near_test_contracts::rs_contract());

    let signer_sender = group.signers[0].clone();
    let signer_receiver = group.signers[1].clone();
    let deposit = Balance::from_yoctonear(1000);

    let data = serde_json::json!([
        {
            "batch_create": {
                "account_id": "near_2",
            },
            "id": 0
        },
        {
            "action_function_call": {
                "promise_index": 0,
                "method_name": "non_existing_function",
                "arguments": [],
                "amount": deposit,
                "gas": GAS_2,
            },
            "id": 0
        },
        {
            "set_refund_to": {
                "promise_index": 0,
                "beneficiary_id": "near_3"
            }, "id": 0
        }
    ]);

    let signed_transaction = SignedTransaction::from_actions(
        1,
        signer_sender.get_account_id(),
        signer_receiver.get_account_id(),
        &signer_sender,
        vec![Action::FunctionCall(Box::new(FunctionCallAction {
            method_name: "call_promise".to_string(),
            args: serde_json::to_vec(&data).unwrap(),
            gas: GAS_1,
            deposit,
        }))],
        CryptoHash::default(),
    );

    let handles = RuntimeGroup::start_runtimes(group.clone(), vec![signed_transaction.clone()]);
    for h in handles {
        h.join().unwrap();
    }

    println!("{:?}", group.executed_receipts);

    use near_primitives::transaction::*;
    let [r0] = &*assert_receipts!(group, signed_transaction) else {
        panic!("Incorrect number of produced receipts")
    };

    let receipts = &*assert_receipts!(group, "near_0" => r0 @ "near_1",
        ReceiptEnum::Action(ActionReceipt{actions, ..}) | ReceiptEnum::ActionV2(ActionReceiptV2{actions, ..}),
        {},
        actions,
        a0, Action::FunctionCall(function_call_action), {
            assert_eq!(function_call_action.gas, GAS_1);
            assert_eq!(function_call_action.deposit, deposit);
            assert_eq!(function_call_action.method_name, "call_promise");
        }
    );
    let [r1, refunds @ ..] = &receipts else { panic!("Incorrect number of produced receipts") };
    group.assert_gas_refunds(&refunds[..]);

    let receipts = &*assert_receipts!(group, "near_1" => r1 @ "near_2",
        ReceiptEnum::Action(ActionReceipt{actions, ..}) | ReceiptEnum::ActionV2(ActionReceiptV2{actions, ..}),
        {},
        actions,
        a0, Action::FunctionCall(function_call_action), {
            assert_eq!(function_call_action.gas, GAS_2);
            assert_eq!(function_call_action.deposit, deposit);
            assert_eq!(function_call_action.method_name, "non_existing_function");
        }
    );
    // The redirected deposit refund (to `near_3`) is emitted first; any trailing receipt is the
    // gas refund for executing this receipt.
    let [deposit_refund, refunds @ ..] = &receipts else {
        panic!("Incorrect number of produced receipts")
    };
    group.assert_gas_refunds(&refunds[..]);

    // This is the redirected refund
    assert_refund!(group, deposit_refund @ "near_3");
}
```
