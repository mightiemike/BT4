Confirmed: nowhere in the restore path (`restore_utils.rs`, `restore_handler.rs`) is a transaction's `write_set` cryptographically bound to its `TransactionInfo.state_change_hash()` before it is written to durable storage.

### Title
Transaction backup restore commits `WriteSet`s to storage without verifying them against `TransactionInfo.state_change_hash` - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
When restoring from a transaction backup, `LoadedChunk::load` reconstructs `txns`, `txn_infos`, `event_vecs`, and `write_sets` from the backup file, but only wraps `txns`/`events`/`txn_infos` in a `TransactionListWithProof` for proof verification. `write_sets` are kept in a separate `Vec<WriteSet>` that never participates in `.verify()`. They are later passed straight into `restore_utils::save_transactions_impl`, which writes them to `WriteSetDb` and (in `kv_replay` mode) applies them to state, with no check that `CryptoHash::hash(write_set) == txn_info.state_change_hash()`.

### Finding Description
`LoadedChunk::load` (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs:99-186`) parses each backup record into `(txn, aux_info, txn_info, events, write_set)` and pushes `write_set` into a plain `Vec<WriteSet>` [1](#0-0) . It then builds a `TransactionListWithProofV2` using only `txns`, `event_vecs`, and `TransactionInfoListWithProof::new(range_proof, txn_infos)`, and calls `.verify(...)` [2](#0-1) . The `TransactionListWithProof` type has no `write_set` field at all, and its `verify()` implementation (`types/src/transaction/mod.rs:2693-2752`) only checks transaction hashes, transaction-info accumulator proof, and event root hashes [3](#0-2) . By contrast, `TransactionOutputListWithProof::verify` (`types/src/transaction/mod.rs:2941-3023`) explicitly checks `write_set_hash == txn_info.state_change_hash()` — this is the invariant that's supposed to bind a write set to its authenticated transaction info [4](#0-3) .

The restore code path never uses `TransactionOutputListWithProof`; it discards `write_sets` from proof verification entirely and passes it around as a bare, unauthenticated vector (`unpack()` returns it separately from the proof-checked `txn_list_with_proof`) [5](#0-4) . It is fed to `restore_handler.save_transactions(...)` / `save_transactions_and_replay_kv(...)` [6](#0-5) , which forwards to `restore_utils::save_transactions_impl` [7](#0-6) . That function writes `write_sets` into `WriteSetDb::put_write_set` and, when `kv_replay` is set, applies them via `state_store.calculate_state_and_put_updates` to compute the persisted ledger state — all without ever comparing the write set's hash to `txn_info.state_change_hash()` [8](#0-7) . A grep across `storage/aptosdb` confirms `state_change_hash` is referenced only in test files, never in any restore/commit code path [9](#0-8) .

### Impact Explanation
Since restore relies purely on trusted, offline backup storage (`BackupStorage`) for `write_sets` bytes, and that channel is not part of the accumulator-proof-checked payload, any corruption or substitution of the write-set bytes for a given version — from a compromised/faulty backup blob, storage bit-rot, or a malicious/buggy backup provider — will be silently accepted and committed to the restored node's ledger DB and, in `kv_replay` mode, applied to derive the restored state tree. Because the write set is what actually mutates persisted state and (via `StateUpdateRefs::index_write_sets`) contributes to the state root, an operator restoring from a tampered or corrupted backup ends up with a durable ledger whose transaction outputs (and possibly its state root, if kv_replay path recomputes state) diverge from the originally executed VM result, while a `verify`-mode restore would still misreport "verified" success because it only checks txn/txn_info/event fields, not write sets. This is exactly the "committed state differs from correct VM result / corrupts durable ledger data" and "restore paths must preserve deterministic proof binding" invariant called out in the prompt.

### Likelihood Explanation
This requires an attacker (or corruption event) able to control/tamper the transaction backup blob content read by `storage.open_for_read(&manifest.transactions)` while the accompanying `TransactionAccumulatorRangeProof`/`LedgerInfoWithSignatures` remain the legitimate ones for txns/events (the proof only covers those, not write sets), so the swap is undetected by `.verify()`. This is a real gap in defense-in-depth for the restore/backup trust model (which is explicitly a target area per the prompt's "restore flows" pivot), though it depends on backup-storage integrity being weaker than assumed, which is a plausible but non-default operational scenario, so I rate confidence in exploitability as high for the code-path bug itself, though real-world triggering depends on backup provider compromise.

### Recommendation
Bind `write_sets` to the accumulator proof: either use `TransactionOutputListWithProof`/an equivalent verifier that checks `CryptoHash::hash(write_set) == txn_info.state_change_hash()` for every loaded record before returning from `LoadedChunk::load`, or add an explicit assertion in `restore_utils::save_transactions_impl` (and its `kv_replay` branch) comparing the write set hash against `txn_infos[idx].state_change_hash()` prior to writing to `WriteSetDb` / feeding `StateUpdateRefs`.

### Proof of Concept
1. Take a legitimate transaction backup chunk file and its `TransactionAccumulatorRangeProof` + `LedgerInfoWithSignatures`.
2. Modify only the serialized `write_set` bytes of one record inside the transactions blob (leave `txn`, `txn_info`, `events` untouched so `committed_hash()`/event-root checks still pass).
3. Run `TransactionRestoreController`/`TransactionRestoreBatchController::run_impl` against this tampered chunk (in `Restore` or `kv_replay` mode).
4. `LoadedChunk::load`'s `txn_list_with_proof.verify(...)` succeeds (it never inspects `write_sets`).
5. `restore_utils::save_transactions_impl` persists the tampered `write_set` into `WriteSetDb` (and, with `kv_replay=true`, applies it to derive `ledger_state`), producing a restored DB whose write set/state for that version differs from what was actually executed on-chain, with no error raised anywhere in the pipeline.

    ledger_db: Arc<LedgerDb>,
    first_version: Version,
    txns: &[Transaction],
    persisted_aux_info: &[PersistedAuxiliaryInfo],
    txn_infos: &[TransactionInfo],
    events: &[Vec<ContractEvent>],
    write_sets: &[WriteSet],
    ledger_db_batch: &mut LedgerDbSchemaBatches,
    state_kv_batches: &mut ShardedStateKvSchemaBatch,
    kv_replay: bool,
) -> Result<()> {
    for (idx, txn) in txns.iter().enumerate() {
        ledger_db.transaction_db().put_transaction(
            first_version + idx as Version,
            txn,
            /*skip_index=*/ false,
            &mut ledger_db_batch.transaction_db_batches,
        )?;
    }

    for (idx, aux_info) in persisted_aux_info.iter().enumerate() {
        PersistedAuxiliaryInfoDb::put_persisted_auxiliary_info(
            first_version + idx as Version,
            aux_info,
            &mut ledger_db_batch.persisted_auxiliary_info_db_batches,
        )?;
    }

    for (idx, txn_info) in txn_infos.iter().enumerate() {
        TransactionInfoDb::put_transaction_info(
            first_version + idx as Version,
            txn_info,
            &mut ledger_db_batch.transaction_info_db_batches,
        )?;
    }
