### Title
Stale `last-update` timestamp causes zero-rate idle periods to be retroactively billed at a later nonzero rate - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
`last-update` is only advanced inside `accrue` when `index` or `lindex` actually changes (`v0-vault-stx.clar:860-862`). When `interest-rate()` returns `u0` (e.g. zero utilization, or a DAO-configured 0% tier), `next-index`/`next-liquidity-index` return the unchanged `idx`/`lidx` exactly, so `last-update` is frozen. Once utilization/rate later becomes nonzero, the very next `accrue` computes `time-delta` spanning the entire frozen gap plus the new period, and applies the *current* nonzero rate to that whole span, retroactively charging interest for a period whose true rate was zero.

### Finding Description
1. `points-ir` defaults to `{util: u0, rate: u0}` (all-zero packed curve) at deploy (`v0-vault-stx.clar:94-96`), and the DAO can legitimately configure a 0% rate at low/zero utilization via `set-points-rate`/`set-points-util` (`v0-vault-stx.clar:666-702`) — zero rate is a normal, reachable state, not a contrived edge case.
2. `interest-rate` (`v0-vault-stx.clar:371-377`) reads `utilization` and interpolates; when utilization is `u0` (no debt) or maps to a 0% segment, it returns `u0`.
3. `next-index` (`v0-vault-stx.clar:379-390`) binds `rate (interest-rate)` and `time-delta (- stacks-block-time (var-get last-update))`, then `multiplier (calc-multiplier-delta rate time-delta true)`. With `rate = u0`, `mul-div-up` of `0 * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS` is exactly `u0`, so `multiplier = INDEX-PRECISION` regardless of `time-delta`, and `calc-index-next idx multiplier` returns `idx` unchanged. The same holds for `next-liquidity-index` (`v0-vault-stx.clar:392-404`) since `calc-liquidity-rate` also yields `u0`.
4. In `accrue` (`v0-vault-stx.clar:835-863`), `next` equals `idx` and `nliq` equals `lidx` in this state, so the guard at line 860, `(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)`, evaluates false — `last-update` is **not** advanced, even though real chain time has elapsed and every intervening `accrue` call (from any deposit/redeem/borrow/repay) confirms the same zero-rate outcome.
5. This can persist across an arbitrary number of blocks with no state change to `last-update`.
6. When a state-changing call increases utilization (e.g. `system-borrow`, `v0-vault-stx.clar:865-900`), note the `u (try! (accrue))` binding is evaluated **before** `principal-scaled`/`total-borrowed` are updated, so that particular `accrue` call still sees pre-borrow (zero) utilization and still does not advance `last-update`.
7. On the *next* call to `accrue` (by any caller, at any later block), `interest-rate()` now reflects the new nonzero utilization. `next-index`/`next-liquidity-index` compute `time-delta` as the *entire* stale span (idle zero-rate period + new active period) and apply the *current* nonzero rate to all of it via `calc-multiplier-delta`. The resulting `index`/`lindex` jump is written permanently via `var-set index next` / `var-set lindex nliq` / `var-set last-update stacks-block-time` (`v0-vault-stx.clar:851-862`).
8. No later check (slippage checks in `deposit`/`redeem` bound only the caller's own conversion, not the correctness of the index growth itself) recovers this — the inflated `index`/`lindex` and the `treasury-lp` mint to `.dao-treasury` (`v0-vault-stx.clar:849-850,857-858`) are permanent.

Root cause: advancing `last-update` conditionally on whether the index *changed* rather than unconditionally on every `accrue` invocation. The correct invariant is that elapsed real time must be "consumed" (i.e., `last-update` advanced) on every accrual attempt regardless of whether the multiplier was `1` (zero rate) — because a zero-rate window is a *resolved* (correctly zero-interest) fact, not a pending balance to be later repriced.

### Impact Explanation
Borrowers are overcharged interest for the entire idle zero-rate window, computed at a rate that never actually applied during that window; this overcharge is compounded via `calc-index-next` (multiplicative) into `index`, permanently increasing `total-debt`. The excess is split between `dao-treasury` (via `treasury-lp` mint) and existing LPs (via the increase in `total-assets`/`lindex`), i.e., value transferred out of borrowers' accounts to other parties without their debt ever having accrued at that rate. This is a direct, permanent misallocation of funds between protocol participants — Critical.

### Likelihood Explanation
Precondition is simply a period of zero utilization or a DAO-configured 0% rate tier followed by resumed borrowing activity — an ordinary, unprivileged, commonly-occurring sequence requiring no special capital or attacker coordination; any user's normal borrow/repay/deposit/redeem timing triggers it. It is fully repeatable every time the vault experiences an idle (zero-rate) interval followed by nonzero utilization, and the "attack" is really incidental to protocol usage rather than requiring adversarial ordering within a single block.

### Recommendation
Always advance `last-update` to `stacks-block-time` unconditionally at the end of every non-paused `accrue` call (removing the `is-eq idx next`/`is-eq lidx nliq` gating), so that each already-resolved (even zero-interest) interval is properly closed out and cannot later be repriced at a different rate.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy and `initialize` `v0-vault-stx`; via DAO, `set-points-util`/`set-points-rate` with a curve whose first point is `{util: 0, rate: 0}`.
2. Deposit liquidity so utilization is `0` and `interest-rate()` returns `u0`.
3. Advance the simnet chain by N blocks/time (e.g. several hours) with no state-changing vault calls (or with calls that keep utilization at 0). Query `get-last-update` — assert it is unchanged from step 2.
4. Trigger `system-borrow` (via authorized market mock) to move utilization to a nonzero tier with a nonzero rate. Query `get-last-update` right after — assert it is still unchanged (since the `accrue` inside `system-borrow` ran on pre-borrow state).
5. Advance a few more blocks, then call `accrue` (or any state-changing function that triggers it). Read `get-index`/`get-debt` and compare to the value that would result if `time-delta` had been `0` for the idle window (i.e., only charging the post-borrow duration at the new rate). Assert the observed `index`/debt reflects the full stale N-block span billed at the new nonzero rate, proving the retroactive overcharge.
