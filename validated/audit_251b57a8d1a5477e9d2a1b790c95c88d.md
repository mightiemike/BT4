## Title
Batch liquidation silently absorbs a failed bad-debt socialization, leaving already-executed collateral seizure, debt removal, and repayment permanently committed - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi()` executes each requested liquidation via a bare (non-`contract-call?`) invocation of `liquidate()` and wraps the whole batch as `(ok (map call-liquidate positions))`, explicitly designed so a failing liquidation does not abort the whole batch. However, `liquidate()` performs its state-mutating `contract-call?`s (`vault-system-repay`, `debt-remove-scaled`, `collateral-remove`) *before* it reaches the bad-debt socialization step, which can itself fail via `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)`. Because the earlier calls are separate, already-successful `contract-call?`s, and the overall enclosing `liquidate-multi` call still returns `(ok ...)`, those earlier mutations are never rolled back even though the logical liquidation "failed."

### Finding Description
`liquidate()` in [1](#0-0)  executes the token repayment, scaled-debt removal, and collateral removal as independent `contract-call?`s to `.v0-market-vault` and the vault contracts. Only afterward, if `no-collateral-left` is true, does it attempt bad-debt socialization via a `fold` over `socialize-debt-asset`: [2](#0-1) 

`socialize-debt-asset` itself performs `unwrap!` on `vault-socialize-debt` and `debt-remove-scaled`, and on failure returns `{ success: false }` (an "absorb failure" fold) [3](#0-2) . If that fold reports failure, `liquidate()` hits `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` at line 1548, and returns an `err` response.

When `liquidate()` is invoked directly by a transaction, this `asserts!` failure aborts the entire top-level transaction, rolling back everything — safe. But `liquidate-multi()` calls `liquidate` through `call-liquidate`, a **bare function call**, not `contract-call?`: [4](#0-3) [5](#0-4) 

Because `liquidate-multi` unconditionally wraps the mapped results in `(ok ...)`, the top-level transaction always commits. Clarity only automatically reverts state at a `contract-call?` boundary (or the top-level transaction boundary) when that call returns `err`; a bare function invocation of `liquidate` inside `map` provides no such boundary of its own. Consequently, all of the `contract-call?`s already executed earlier inside that particular (logically-failed) `liquidate()` invocation — `vault-system-repay` (moving repayment funds), `debt-remove-scaled` (wiping the borrower's scaled debt for the repaid asset), and `collateral-remove` (transferring seized collateral to the liquidator) — remain committed even though the function's own final `asserts!` reported failure and the socialization of the position's remaining bad debt never happened.

This is the "fold that absorbs failure" analog described in the prompt: mutation is applied before the guard (`asserts! ... ERR-BAD-DEBT-SOCIALIZATION-FAILED`) is evaluated, and the enclosing batch entry point (`liquidate-multi`) swallows the failure rather than propagating it to a revert.

### Impact Explanation
The borrower's debt for the seized asset is wiped and their collateral is seized/transferred to the liquidator, and repayment tokens move, but the remaining bad debt on other assets that should have been socialized (written off / distributed to LPs) is left dangling, unaccounted, and now under-collateralized. This produces protocol insolvency: liabilities recorded in the vaults (`total-borrowed`) no longer correspond to any recoverable collateral, and this state cannot be corrected after the fact since the borrower's collateral is already gone. This lands in the Critical impact category (protocol insolvency / permanent freezing of funds via orphaned, unbacked debt).

### Likelihood Explanation
This requires only that `liquidate-multi` be used with a position whose bad-debt socialization step can independently fail (e.g., an underlying vault's `socialize-debt-asset` reverting via `unwrap!` on `vault-socialize-debt` for one of several remaining debt assets while the first/targeted asset's repay-and-seize already succeeded). Since `liquidate-multi` is a normal permissionless public entry point intended for liquidators, and the socialization step depends on other contracts (`.v0-market-vault`, per-asset vaults) whose failure modes are not fully controlled by the liquidator, this is reachable under realistic conditions without requiring privileged access or DAO compromise.

### Recommendation
Wrap the invocation of `liquidate` inside `call-liquidate`/`liquidate-multi` with an explicit `contract-call?` (e.g., `(contract-call? .v0-4-market liquidate ...)`) so that a failure anywhere inside a single liquidation is atomically rolled back for that entry, or restructure `liquidate` so the bad-debt-socialization fold runs and is validated *before* any of the vault-mutating `contract-call?`s (repay, debt-remove-scaled, collateral-remove) are executed, ensuring the guard precedes the mutation rather than following it.

### Proof of Concept
1. Liquidator calls `liquidate-multi` with one position `{ borrower: B, collateral-ft: C, debt-ft: D, debt-amount: X, min-collateral-expected: 0 }` where borrower `B` holds debt in asset `D` and asset `E`, with collateral only in asset `C`.
2. Inside `call-liquidate` → `liquidate` (bare call, no `contract-call?` boundary): asserts pass, `vault-system-repay`, `debt-remove-scaled` (for `D`), and `collateral-remove` (for `C`, seizing all of it) execute and commit as independent successful `contract-call?`s [1](#0-0) .
3. `no-collateral-left` evaluates true (all `C` collateral seized), triggering bad-debt socialization over the remaining debt list including asset `E` [6](#0-5) .
4. The `socialize-debt-asset` fold's call to `vault-socialize-debt` for asset `E` fails (e.g., vault-specific condition), so `socialization-result` has `success: false`; `(asserts! ... ERR-BAD-DEBT-SOCIALIZATION-FAILED)` triggers, and `liquidate` returns `(err ...)`.
5. `call-liquidate` returns this err value untouched; `map` collects it into the results list; `liquidate-multi` returns `(ok (list (err ...)))` — the top-level transaction commits.
6. Result: borrower `B`'s collateral in `C` is gone and debt in `D` is cleared, but debt in `E` was never socialized nor repaid — it remains as unbacked, unrecoverable protocol debt, permanently corrupting vault accounting.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }

                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)

        ))
