## Finding

Based on my review, I found a valid analog to the reported bug class in nearcore's Chain Signatures-style Ethereum Wallet Contract (`runtime/near-wallet-contract`). The core mechanic mirrors the Wenwin bug: a state flag that is *supposed to be reset unconditionally by a callback* can instead be permanently stuck because the callback's gas budget is fixed/attacker-influenceable and insufficient, causing the callback to abort before its state-resetting write is committed — and NEAR rolls back **all** state writes of a failed/aborted receipt, not just the failing part.

### Title
Fixed-gas callback in the Wallet Contract can be starved of gas by a large promise result, permanently stalling `has_in_flight_tx` and halting the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` enforces a strict one-in-flight-transaction invariant via `has_in_flight_tx`, documented as: "must be `true` when a mutable method... returns a promise and `false` otherwise" [1](#0-0) . Every promise-returning path resets the flag to `false` as the **first statement** of its designated callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) [2](#0-1) [3](#0-2) . This design assumes the callback will always run to completion, exactly the assumption that broke in the Wenwin report where a `try{}/catch{}`-wrapped external call left `lastRequestFulfilled` stuck at `false`.

### Finding Description
The final callback in the chain, `rlp_execute_callback`, is dispatched with a **fixed** static gas reservation, `RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, that does not scale with the size of the promise result it must process [4](#0-3) . Inside the callback, `env::promise_result(0)` copies the callee's returned value into a register, which is charged per-byte gas (`write_register_byte`) that is not accounted for by the fixed reservation [5](#0-4) . If the target contract that the emulated Ethereum transaction calls returns a sufficiently large value (bounded only by the protocol's `max_length_returned_data`/return-value limit), the per-byte register-write cost inside `rlp_execute_callback` alone can exceed the fixed 5 Tgas budget, causing the callback's WASM execution to abort with `GasExceeded`.

Crucially, NEAR's runtime treats a receipt/function-call abort as fully atomic: "When a receipt fails, its state changes are rolled back using `TrieUpdate`" [6](#0-5) , and near-sdk only persists the contract's mutated state back to storage if the exported method returns without panicking. Since `self.has_in_flight_tx = false;` is a normal in-memory mutation executed at the top of the callback, an abort anywhere later in that same function call discards that write along with everything else — leaving `has_in_flight_tx` at whatever value the *previous* receipt set it to (`true`), exactly the same "reset never lands because the surrounding execution unwound" pattern as the Solidity `try{}/catch{}` bug, just triggered by the WASM gas metering path (`gas_counter.rs`/`process_gas_limit`) instead of Solidity's 1/64-gas-retention quirk.

The check that enforces the invariant is unconditional and has no timeout, retry, or admin override: `rlp_execute` always short-circuits with `"transaction already in progress"` whenever `has_in_flight_tx == true` [7](#0-6) , and there is no other code path in the contract that clears the flag.

### Impact Explanation
Once the flag is stuck at `true`, the Wallet Contract account can never process another Ethereum-emulated transaction: every future `rlp_execute` call from the legitimate owner or any relayer is rejected at the top with the "already in progress" error, forever. Because this contract is the sole mechanism through which the Ethereum-style account signs/moves value on NEAR, this is a transaction-triggered, permanent halt of that account and effectively **permanently frozen funds** for the affected account (assets held by that eth-implicit account become inaccessible through the wallet's transaction path) — squarely inside the accepted impact categories (transaction-triggered halt / permanently frozen funds).

### Likelihood Explanation
The trigger does not require any privileged role — any unprivileged transaction signer (the wallet's own owner acting through a normal relayer-submitted RLP transaction, or a griefing target contract chosen by an attacker who convinces/tricks a relayer into routing a call there) can cause the target of the emulated call to return a value large enough to exceed 5 Tgas of register-write cost in the callback. Since the reservation is a hardcoded constant independent of the target's behavior, this is reliably reproducible, not merely theoretical, and requires only one transaction to trigger, matching "a single submitted transaction" reachability required by the rules.

### Recommendation
Scale `RLP_EXECUTE_CALLBACK_GAS` (and any other terminal-callback gas reservation) to account for the worst-case size of the promise result it may need to read (or cap/charge for large results deterministically before entering the callback), and/or restructure the callback so the state-resetting write is guaranteed to be the *only* effect that must succeed, decoupled from the potentially-unbounded-cost processing of the promise result (e.g., write `has_in_flight_tx = false` and persist it before doing any per-byte-costed work, or split the reset into its own minimal, cheaply-priced call).

### Proof of Concept
1. Register a relayer key for a Wallet Contract account as shown in the test harness [8](#0-7) .
2. Craft/sign an Ethereum transaction (via `rlp_execute`) whose `to`/`target` points at a contract method that returns a value close to the platform's maximum return-data size (comfortably achievable, e.g. via a generic large-value-returning method as used in existing test contracts, `return_large_value`, which is used elsewhere in the repo precisely to construct oversized promise results [9](#0-8) ).
3. Submit `rlp_execute` with enough total attached gas to run the target call successfully but relying on the wallet contract's own fixed `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) for `rlp_execute_callback`.
4. Observe that `rlp_execute_callback` aborts with `GasExceeded` while reading the oversized `promise_result(0)` into a register; per NEAR's all-or-nothing receipt semantics, the earlier `self.has_in_flight_tx = false;` write in that same call is rolled back.
5. Observe that all subsequent `rlp_execute` calls from any relayer/owner are rejected with `"transaction already in progress, please try again later."` [10](#0-9)  indefinitely, with no recovery path in the contract.
