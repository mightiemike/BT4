Based on the wallet-contract code, I found a directly analogous "pay-before-verifying-success" pattern.### Title
Wallet Contract pays relayer fee unconditionally before confirming the underlying action succeeds - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`inner_rlp_execute` dispatches an unconditional `Transfer` of the relayer `fee` to `predecessor_account_id` as soon as an `EOABaseTokenTransfer`/`ERC20Transfer` is parsed, before the actual emulated action's promise is created, chained, or resolved. Just like the Ajna flashloan bug where tokens are force-pulled from the receiver without checking whether repayment already happened, here the wallet irrevocably pays the caller regardless of whether the paired transfer action later fails.

### Finding Description
In `inner_rlp_execute`, once the transaction is parsed as an `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the code eagerly creates an independent outgoing receipt transferring `fee` to `predecessor_account_id` — completely decoupled from the main action's promise chain: [1](#0-0) 

This happens *before* the code below constructs and dispatches the actual base-token-transfer / ERC-20-transfer promise (`address_check`, `ft_transfer`/`storage_deposit`, etc.), and before that promise's `.then(ext.rlp_execute_callback(...))` resolves: [2](#0-1) 

If the main action subsequently fails — e.g. the address-registrar check rejects the target (`address_check_callback` returning failure), the `ft_transfer` call panics (insufficient token balance, malicious/rejecting token contract, `storage_deposit` batch partially failing), or any cross-contract call in the chain fails — `rlp_execute_callback` only refunds the `caller_deposit` (the attached NEAR value of the transaction) on failure; it has no mechanism to claw back or account for the `fee` that was already sent to the predecessor: [3](#0-2) 

Because `rlp_execute` is a public `#[payable]` method callable by **any** account (the only requirement is `predecessor_account_id != current_account_id`, which is what defines someone as a "relayer" in this contract) and can be invoked with any validly ECDSA-signed Ethereum-style transaction the user has broadcast, an unprivileged caller can submit (or race-submit) a transaction they know or suspect will fail the underlying action, collect the `fee`, and leave the wallet owner's intended transfer unexecuted — exactly analogous to the flashloan pattern of moving value based on an assumption of success rather than a verified post-condition.

### Impact Explanation
This causes concrete unauthorized value movement: the wallet owner's NEAR balance is drained to pay a `fee` to a caller/relayer even when the corresponding action (NEAR transfer to another wallet, or NEP-141/ERC-20 transfer) never completes. There is no atomicity or rollback linking the fee payment to the success of the serviced action, so funds can be extracted without delivering the paid-for service, at the cost of the wallet-owner account (Medium: financial loss reachable purely via a public, unprivileged contract call, no special access key required to trigger — only the ability to be the `predecessor_id`, i.e. any account submitting the transaction).

### Likelihood Explanation
Reachable directly from a signed, submitted NEAR transaction calling the public `rlp_execute` method — no validator, network, or privileged access is needed. Any account (not necessarily a benevolent, well-behaved relayer) can act as the "predecessor" and receive the fee. The only condition is that the wrapped Ethereum-style transaction encodes a non-zero fee and the underlying action fails after the fee-transfer receipt has already been dispatched (address-registrar mismatch, receiver not registered/insufficient token balance on `ft_transfer`, cross-contract failure, etc.), all of which are realistic, attacker-triggerable failure modes.

### Recommendation
Do not dispatch the relayer fee transfer eagerly and independently of the main action. Instead, chain the fee-payment as a dependent step executed only after `rlp_execute_callback` confirms the main action succeeded (e.g., pay the fee from within `rlp_execute_callback`'s `PromiseResult::Successful` branch), or attach the fee to the same batched promise/receipt as the serviced action so both share the same success/failure fate.

### Proof of Concept
1. A user signs an Ethereum-style `EOABaseTokenTransfer` (or ERC-20 `transfer`) transaction with a non-zero `fee` intended for a relayer.
2. An unprivileged account submits this transaction via `rlp_execute`/`rlp_execute_from` as `predecessor_account_id`.
3. `inner_rlp_execute` immediately dispatches a `Transfer` of `fee` to that caller via `env::promise_batch_create`/`env::promise_batch_action_transfer` (lines 382-384), independent from the main action's promise.
4. The main action subsequently fails (e.g., target fails the address-registrar check, or the NEP-141 `ft_transfer` panics due to insufficient balance) and `rlp_execute_callback`'s `PromiseResult::Failed` branch only refunds `caller_deposit`, never the already-sent `fee`.
5. Net effect: the caller keeps the `fee` extracted from the wallet owner's balance while the user's intended transfer never executed — the wallet paid without receiving the intended service, matching the "double paying"/unconditional-transfer root cause described in the source report.

        TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
            address_check: Some(address),
            ..
        }) => {

            let ext = WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let address_registrar = {
                let account_id = ADDRESS_REGISTRAR_ACCOUNT_ID
                    .trim()
                    .parse()
                    .unwrap_or_else(|_| env::panic_str("Invalid address registrar"));
                ext_registrar::ext(account_id).with_static_gas(REGISTRAR_LOOKUP_GAS)
            };
            let address = format!("0x{}", hex::encode(address));
            address_registrar.lookup(address).then(ext.address_check_callback(
                target,
                action,
                caller_deposit,
            ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
        }
        _ => {
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))
