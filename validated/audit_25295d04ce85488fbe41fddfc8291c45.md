### Title
Unbounded resource-delegation fan-out enables RPC-triggered DoS via `DelegatedResourceAccountIndexStore` prefix scan/sort - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegateResourceActuator` allows any account to delegate as little as 1 TRX of frozen resource to an arbitrary number of distinct receiver addresses, with no cap on the number of distinct delegatees an owner may accumulate. Each delegation writes a new key-value pair into `DelegatedResourceAccountIndexStore`. The anonymous, publicly reachable `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` RPC/HTTP endpoints then perform an unbounded `prefixQuery` scan and sort over all entries for the requested address, mirroring the reported bug class of loops that scale with attacker-controlled/user-state size and can be driven to consume excessive resources.

### Finding Description
`DelegateResourceActuator.validate()` only checks that `delegateBalance >= TRX_PRECISION` (i.e., ≥ 1 TRX) and that the owner has enough available frozen balance; it does not limit how many distinct receiver addresses an owner can delegate to over time [1](#0-0) . Each successful delegation calls `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, ...)`, which persists an index entry keyed by `V2_FROM_PREFIX + owner + receiver` (and the mirrored `V2_TO_PREFIX` entry) [2](#0-1) .

When any client later queries an account's delegation index (`GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2`, exposed over gRPC and HTTP, including on Solidity/PBFT nodes), the store performs a full prefix range scan and sorts the results by timestamp: [3](#0-2) 
This is analogous to `getIndex()`/`getWithPrefix()` used by the legacy (non-V2) index as well. The number of loop iterations (and comparator invocations during `sort`) is proportional to the number of distinct delegation relationships the target account has accumulated — a value fully controlled by any attacker who can freeze and delegate 1 TRX at a time to a large number of distinct, cheaply generated receiver addresses.

This mirrors the reported bug class: a loop whose iteration count scales with user-controlled state size (`portfolio.length` in the original report vs. delegation fan-out count here), reachable from a public entry point (anonymous RPC/HTTP `GetDelegatedResourceAccountIndex*` vs. `liquidate`), with no limit imposed by the actuator that creates the state.

### Impact Explanation
An attacker can cheaply inflate the size of their own (or, since delegation indices are stored per-account and address generation is free, freely-created sacrificial) account's delegation index by issuing many `DelegateResourceContract` transactions with minimal (1 TRX) balances to many distinct freshly generated receiver addresses (each receiver account must merely exist — a `CreateAccount`/first transfer is enough to instantiate it). Once the fan-out list is large, every subsequent `GetDelegatedResourceAccountIndex`/`V2` RPC or HTTP call against that address forces the serving full node (or SolidityNode/PBFT node) to scan and sort potentially large collections in `prefixQuery` + `Comparator.comparing(...timestamp)`, consuming CPU and memory on the node processing an anonymous, unauthenticated query. Because this endpoint is available on public full nodes (per `api.proto`), an attacker can trigger CPU/memory exhaustion by repeatedly re-querying it, or by inflating the index and letting normal API consumers unintentionally trigger the expensive scan. This is a resource/DoS-class issue in the RPC-API surface rather than any accounting/consensus corruption.

### Likelihood Explanation
Likelihood is moderate. Executing many `DelegateResourceContract` transactions and creating receiver accounts each costs real TRX (transaction bandwidth/energy fee and 1 TRX minimum delegate amount per receiver, plus account creation fees), which raises the cost floor for an attacker compared to a pure on-chain smart-contract loop DoS, but is still bounded and finite — an attacker with a modest budget can create thousands of delegation relationships. There is no protocol-level cap (`MAX_VOTE_NUMBER`-style limit) on distinct delegatees analogous to the vote-count limit enforced elsewhere (e.g., `VoteWitnessActuator`/`VoteWitnessProcessor` cap total votes at `MAX_VOTE_NUMBER`) [4](#0-3) , so nothing currently prevents unbounded fan-out growth for delegated-resource indices.

### Recommendation
- Impose a maximum number of distinct `toAccounts`/`fromAccounts` entries per address in `DelegateResourceActuator.validate()`/`DelegateResourceProcessor.validate()`, similar to the `MAX_VOTE_NUMBER` cap used for voting.
- Add pagination to `GetDelegatedResourceAccountIndex`/`V2` (mirroring the pattern already used in `getPaginatedNowWitnessList`) so the RPC handler cannot be forced to materialize/sort an unbounded result set in one call.
- Consider indexing/prefix-scanning with a bounded/streamed iterator plus a server-side hard cap on returned/scanned entries, rejecting or truncating requests beyond a safe threshold, and monitor/alert on abnormally large delegation index sizes.

### Proof of Concept
1. Attacker account A freezes resources (`FreezeBalanceV2Contract`) to obtain freezable BANDWIDTH/ENERGY balance.
2. Attacker repeatedly (N = large, e.g., tens of thousands) creates a fresh keypair `Ri`, funds it minimally so the account exists, and submits `DelegateResourceContract{owner=A, receiver=Ri, balance=1_000_000 (1 TRX)}` — each call passes `DelegateResourceActuator.validate()` (only checks ≥1 TRX and available balance) and appends a `V2_FROM_PREFIX+A+Ri` / `V2_TO_PREFIX+Ri+A` pair via `delegateV2` [5](#0-4) .
3. Any client calls `GetDelegatedResourceAccountIndexV2(A)` over the public gRPC/HTTP API. The full node executes `getWithPrefix`, performing a `prefixQuery` scan of all N entries and sorting by timestamp [3](#0-2) , consuming CPU/memory proportional to N on the responding node for every such request.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
