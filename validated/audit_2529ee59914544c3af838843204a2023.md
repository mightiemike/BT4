## Title
`WalletContract::rlp_execute_callback` early-return for emulated self-transfers permanently swallows a relayer's attached NEAR deposit - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (`WalletContract::rlp_execute`), reachable by any unprivileged relayer/transaction signer calling a `#[payable]` method, mirrors the Alchemix `RewardsDistributor.claim()` bug class: an early-return branch exists that returns a "success" result without checking or refunding `msg.value`/attached deposit that a caller supplied.

### Finding Description
`rlp_execute` is `#[payable]` [1](#0-0) , so any relayer account can attach an arbitrary NEAR deposit when calling it. `inner_rlp_execute` builds a `CallerDeposit` from the attached deposit whenever the caller (`predecessor_account_id`) differs from the wallet's own account (`current_account_id`) [2](#0-1) . This `CallerDeposit` is threaded through to `rlp_execute_callback`, whose stated purpose is "to refund the caller's deposit if the cross-contract call fails" [3](#0-2) .

When the parsed Ethereum transaction is classified as `EthEmulationKind::SelfBaseTokenTransfer` (an emulated Ethereum self-transfer, i.e. the `to` address resolves to the wallet's own address) [4](#0-3) , `inner_rlp_execute` calls `rlp_execute_callback` *directly*, not as a promise callback: [5](#0-4) 

Because there is no antecedent promise, `env::promise_results_count()` is `0` when this scheduled call executes, and `rlp_execute_callback` takes the early-return branch: [6](#0-5) 

This branch returns `success: true` and **never inspects `caller_deposit`, never refunds it, and never uses it for anything**. The condition that gates whether `caller_deposit` is `Some` (`current_account_id == predecessor_account_id`, i.e. self-call) is a *different* notion of "self" than `SelfBaseTokenTransfer` (which is about the parsed Ethereum tx's `to` address equaling the wallet's own Ethereum address). A relayer account (`predecessor_account_id != current_account_id`) can attach a NEAR deposit to `rlp_execute` while submitting an Ethereum transaction whose `to` field is the wallet's own address — this is entirely legal input the relayer controls — producing `caller_deposit = Some(...)` while landing in the `n == 0` early-return path that silently drops it.

Since attached deposits on a NEAR function call are credited to the receiving account's balance before contract execution runs (per the Economics API: "the balance that was attached to the call that will be immediately deposited before the contract execution starts" [7](#0-6) ), the relayer's tokens are irreversibly absorbed into the wallet contract's own account balance, with no promise ever created to move them back to the relayer. This is functionally identical to the reported Alchemix bug: an early-return path in a value-accepting entry point that bypasses the refund/consumption logic for attached value.

### Impact Explanation
Any relayer that attaches NEAR to `rlp_execute` while relaying an Ethereum-emulated self-transfer transaction permanently loses that deposit; it is credited to the wallet-contract account without the relayer's consent and without any corresponding compensation or refund path. This is an unauthorized, permanent transfer/freezing of relayer funds triggered purely by a crafted (but protocol-valid) transaction — no malicious validator, network, or privileged actor is required, only a normal relayer/caller who attaches a deposit and a self-transfer-shaped Ethereum payload.

### Likelihood Explanation
Medium: it requires a caller to (a) be a different account than the wallet contract (typical for relayers), (b) attach a non-zero NEAR deposit to `rlp_execute`, and (c) submit/relay an Ethereum transaction that resolves to `EthEmulationKind::SelfBaseTokenTransfer`. Relayer implementations that speculatively attach deposits (e.g., to cover a possible fee/value payment) for arbitrary user-signed transactions, without special-casing self-transfers, would trigger this unintentionally; a malicious/careless relayer could also trigger it on their own accidentally-resent transactions, similar to the "user resubmits" scenario in the original report.

### Recommendation
In `rlp_execute_callback`, the `n == 0` branch should check `caller_deposit` before returning, refunding it via a transfer promise to `caller_deposit.account_id` exactly as done in the `PromiseResult::Failed` branch, e.g.:
```rust
if n == 0 {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(refund_promise, NearToken::from_yoctonear(yocto_near.into()));
    }
    return ExecuteResponse { success: true, success_value: None, error: None };
}
```
Alternatively, disallow/ignore attached deposits for the `SelfBaseTokenTransfer` code path at parse time so `CallerDeposit` can never be `Some` when this early return is reached.

### Proof of Concept
Conceptual reproduction (cannot execute against this read-only index, but the code path is unambiguous from source):
1. Deploy `WalletContract` at an eth-implicit account `0xAAA...` (its own address).
2. From a distinct relayer account `relayer.near`, call `rlp_execute(target = 0xAAA..., tx_bytes_b64 = <RLP of a signed tx from 0xAAA... to 0xAAA... with empty/unparsable data>)` attaching e.g. `1 NEAR` deposit.
3. `parse_rlp_tx_to_action` resolves `target_kind = TargetKind::CurrentAccount` with unparsable data, yielding `TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer)` [4](#0-3) .
4. `CallerDeposit::new` returns `Some(CallerDeposit { account_id: relayer.near, yocto_near: 1 NEAR })` because `predecessor_account_id (relayer.near) != current_account_id (0xAAA...)` [2](#0-1) .
5. `inner_rlp_execute` schedules `rlp_execute_callback(Some(caller_deposit))` directly (no antecedent promise) [5](#0-4) .
6. When executed, `env::promise_results_count() == 0`, so the callback returns `success: true` without ever touching `caller_deposit` [6](#0-5) .
7. Result: `relayer.near`'s 1 NEAR deposit is now part of `0xAAA...`'s account balance permanently, with no refund receipt ever created.

Note: I was unable to run an actual integration test against this repository (no execution environment available), so this PoC is a source-level trace rather than an executed test; the existing unit test suite in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests` (not fully reviewed here due to index limits) may already contain fixtures for `SelfBaseTokenTransfer` that could be adapted to assert the missing refund.
