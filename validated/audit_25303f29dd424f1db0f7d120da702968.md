### Title
`remove_account` does not clean up `PromiseYieldReceipt`/`PromiseYieldStatus`/postponed-receipt state on `DeleteAccount`, allowing stale receipts to execute against a recreated account - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:505-575`), invoked by `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) when a `DeleteAccount` action executes, only removes the `Account`, `ContractCode`, access/gas keys, and `ContractData` entries for the account. It never removes the account's `PromiseYieldReceipt`, `PromiseYieldStatus`, `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, or `ReceivedData` trie entries, nor the corresponding `PromiseYieldTimeout` queue entry. This mirrors the reported analog: `transferERC721` moves the NFT out but never runs `delete timelockERC721s[key]`, leaving stale bookkeeping that can later be matched against new activity.

### Finding Description
`remove_account` is the single cleanup routine used by `DeleteAccountAction`: [1](#0-0) 
It removes the account row, code, access/gas keys, and contract data, but never touches `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceiptId`, `TrieKey::ReceivedData`, or the account's outstanding `PromiseYieldTimeout` queue entries (all of which are keyed by `receiver_id`/`account_id` per `core/primitives/src/trie_key.rs:203-247`).

`action_delete_account` calls this helper directly and then nulls out the in-memory `Account`: [2](#0-1) 

Meanwhile, a contract on the account can create a `PromiseYield` receipt (via `yield_create`), which is stored keyed by `(receiver_id, data_id)` and gets a `PromiseYieldTimeout` queue entry for future resolution: [3](#0-2) [4](#0-3) 

If the account is deleted (e.g., by its own owner, or automatically as part of an account lifecycle flow) while such a yield is outstanding, the `PromiseYieldReceipt`/`PromiseYieldStatus`/timeout-queue entries survive under the now-defunct `account_id`. NEAR permits recreating an account with the same `AccountId` after deletion (verified by the existing test suite covering delete/recreate-in-same-chunk semantics, `runtime/runtime/src/tests/apply.rs:4978-5055`, and nonce-bootstrap-on-recreation handling at `runtime/runtime/src/tests/apply.rs:6094-6159`). Once the account is recreated (possibly by a different owner/contract), `resolve_promise_yield_timeouts` will still find the orphaned `PromiseYieldTimeout` entry when it comes due, check `contains_key` on the still-present `PromiseYieldReceipt` key, and unconditionally synthesize and execute a `PromiseResume` receipt against the *new* incarnation of the account: [5](#0-4) 
That resume causes `apply_action_receipt` to execute the *stale* yielded `ActionReceipt` (the original `FunctionCall`/callback action, with predecessor `system`/original caller and payload from before deletion) against the newly created account's current code and storage: [6](#0-5) 

The same class of issue applies to `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`/`ReceivedData`: if the account had a postponed action receipt awaiting a `DataReceipt` when it was deleted, those entries also survive `remove_account` and can be matched by a later, unrelated `DataReceipt` arriving for the recreated account, triggering execution of the stale postponed action (`runtime/runtime/src/lib.rs:1450-1509`).

### Impact Explanation
This is a concrete invalid-state-transition path: a receipt created under one account "incarnation" (tied to one contract deployment/owner) is executed against a semantically different, later incarnation of the same `AccountId` — the runtime has no way to distinguish "this account" from "the account that used to have this name." Because the resumed/postponed action receipt can contain arbitrary attacker-chosen actions (e.g., `FunctionCall`, `Transfer`) recorded before deletion, its unexpected re-execution against the new account can move balance or invoke methods the new owner never intended to be called with that payload — i.e., unauthorized value movement / invalid state transition acceptance, triggered purely by ordinary transactions (`DeleteAccount` + `CreateAccount` + normal receipt processing), reachable by any unprivileged account owner.

### Likelihood Explanation
Requires an account to have an outstanding `PromiseYield` (or a postponed action receipt with unmet input data) at the moment its `DeleteAccountAction` executes, followed by recreation of the same `AccountId` before the yield's timeout fires (or before the missing `DataReceipt` arrives). This is a normal, deterministic sequence reachable by a single account owner controlling their own deletion/recreation timing and is not dependent on any adversarial network/validator behavior, so it is realistically triggerable, though it requires a specific sequence of self-directed transactions/contract calls rather than a single call.

### Recommendation
Extend `remove_account` (or `action_delete_account`) to also purge, for the account being deleted: all `PromiseYieldReceipt`/`PromiseYieldStatus` entries and their `YieldIdToDataId`/`DataIdToYieldId` mappings, all `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`/`ReceivedData` entries for that `receiver_id`, and any outstanding `PromiseYieldTimeout` queue entries referencing the account (or make `resolve_promise_yield_timeouts`/the resume path validate that the account incarnation matches before executing). At minimum, gate account recreation so it cannot happen while such pending state exists for the account.

### Proof of Concept
1. Deploy a contract at `child.near` that calls `yield_create` in a `FunctionCall`, producing a `PromiseYield` receipt with `data_id = D` and a `PromiseYieldTimeout` queue entry with a future `expires_at`.
2. Before `expires_at`, submit a `DeleteAccount` receipt for `child.near` (via `action_delete_account` → `remove_account`); confirm via storage inspection that `TrieKey::PromiseYieldReceipt{child.near, D}`, `TrieKey::PromiseYieldStatus{child.near, D}`, and the `PromiseYieldTimeout` queue entry are still present after deletion (as in `runtime/runtime/src/tests/apply.rs:4978` style delete/recreate tests, but checking yield-related keys instead of contract code).
3. Recreate `child.near` with a different contract/state via `CreateAccount` + `DeployContract` in a later or the same chunk.
4. Advance blocks to `expires_at`; observe `resolve_promise_yield_timeouts` synthesizing and executing a `PromiseResume` for `data_id = D` against the recreated `child.near`, causing the old yielded action receipt to run against the new account's code/state.
