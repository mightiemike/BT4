### Title
Permanent loss of funds when a `0u` Universal Account id is derived from non‑canonical `RawStateInit` bytes - (File: `core/primitives/src/utils.rs`)

### Summary
NEAR's Universal Accounts (`0u...`, NEP‑616‑adjacent feature) compute the account id as `SHA3‑256(RawStateInit bytes)`, hashing the *exact wire bytes* rather than any canonicalized/decoded form. Anyone (contract, relayer, wallet SDK) can independently produce a `UniversalStateInit`, get its `RawStateInit`, and either (a) hash it directly to get the correct account id, or (b) decode it and re‑serialize the typed value to compute an id. Because borsh only canonicalizes on encode, not on decode, these two derivations can diverge for logically identical state. A party who funds the id obtained from the re‑encoded (non‑canonical) path — instead of the id derived from the original raw bytes they intend to install later — creates an account that can never be initialized, permanently locking the transferred funds, functionally identical to the reported bridge bug where a hash-based identity computed in one context diverges from the identity checked in another, with no recovery path.

### Finding Description
The account id for a `0u` Universal Account is defined as: [1](#0-0) 

which explicitly documents: *"Re-serializing could yield a different ID, if `state_init` contained non-canonical borsh representation."* The `RawStateInit` wire type reinforces this: *"Two encodings of the same logical value are two different accounts, which is deliberate ... canonical encoding cannot be enforced end to end anyway."* [2](#0-1) 

The runtime enforces a strict equality between the receiver id of a `UniversalStateInit` action and `derive_universal_account_id(raw_bytes)`: [3](#0-2) 

Separately, a plain `Transfer` to *any* well-formed `0u`-typed account id (regardless of whether a matching state init has ever existed) unconditionally creates an `Uninitialized` account and accepts the deposit: [4](#0-3) 
This is confirmed by test coverage showing a lone transfer to an all‑zero‑hash `0u` id ("with no known state init, so the account can never leave the uninitialized state") still succeeds and holds the funds: [5](#0-4) 

The vulnerability class from the report maps directly here: the depositor (transaction signer) and the party later trying to "claim"/initialize the account (via `UniversalStateInitAction`) must agree on exactly the same bytes-derived identity. If a wallet, SDK, or contract computes the account id by decoding `RawStateInit` into the typed `UniversalStateInit` and re‑serializing it (a natural implementation pattern, especially across different language/SDK borsh implementations, or when passing state through any code path that decodes and re-encodes), it can get an id that differs from the one the protocol will actually accept for that same logical state, as proven by the repo's own tests: [6](#0-5) [7](#0-6) 

If a user/relayer sends a `Transfer` to the id obtained via the re‑encoded (non‑canonical) path, the receiving account is created as `Uninitialized` and holds the deposit. But the *only* way to ever initialize it is a `UniversalStateInitAction` whose receiver id matches `derive_universal_account_id` of the *exact bytes hashed for that id* — bytes that the depositor, having only ever produced the canonical re‑encoding, can never reproduce (the canonical encoder never emits the non‑canonical bytes that hashed to the address they funded). An uninitialized account with no matching state init is permanently inert: it rejects every action except its own state init and further transfers. [8](#0-7) 
There is no way to `DeleteAccount` (the beneficiary-refund path) or recover the deposit, because `DeleteAccount` also requires the account to be initialized as it needs an access key/actor to authorize it, and the account has none.

### Impact Explanation
This is a "permanently frozen funds" scenario: NEAR tokens sent to a Universal Account address computed via a non‑canonical (but still borsh‑valid) re‑serialization of an otherwise correct `UniversalStateInit` become unrecoverable, since no future transaction can ever supply the exact byte string that hashes to that specific address (the encoder only ever emits canonical bytes). This can occur any time a wallet, relayer, or dApp integration accepts a Universal Account's typed state description, decodes it (e.g. from RPC, from a stored template, or from a different serialization library), and re-derives the address from the decoded/re-encoded form instead of retaining and hashing the original raw bytes — exactly mirroring the bridge bug's root cause (identity is computed once at "deposit" time and must be reproduced bit‑for‑bit at "claim"/init time, but two logically-equivalent representations of the same value produce different addresses).

### Likelihood Explanation
Likelihood is realistic but not trivial: it requires a client-side implementation bug or cross‑implementation inconsistency (e.g., a borsh encoder that doesn't sort `BTreeMap`/`BTreeSet` containers, or code that decodes a `RawStateInit` and later re-serializes the typed value to derive an id instead of hashing the original bytes) — the repository's own tests demonstrate this is an easy mistake to make, going as far as constructing a hand-built "non-canonical but valid" fixture to pin the correct (bytes-based) behavior. Because the "wrong" derivation still parses as a valid `0u` account id and a `Transfer` to it silently succeeds and creates a normal-looking `Uninitialized` account, there is no on-chain signal that the funds are unrecoverable until an initialization attempt against that id inevitably fails with `InvalidUniversalStateInitReceiver`.

### Recommendation
- Document unambiguously (in NEP text, `docs/DataStructures/Account.md`, and SDK guidance) that `derive_universal_account_id` MUST be computed over the exact `RawStateInit` bytes that will later be submitted in the `UniversalStateInitAction`, and that clients must **never** decode-then-re-encode a state init to (re)derive its address.
- Provide and mandate a canonical, cross-language reference encoder (or a host function, already present for contracts via `universal_state_init_to_account_id`) so wallets/relayers never hand-roll borsh serialization of `UniversalStateInit`.
- Consider adding a client-facing warning/validation step (in RPC helpers or SDKs) that re-derives the id from re-encoded bytes and warns if it disagrees with the id used to fund the account, before a `Transfer`-only creation is allowed to proceed.
- Evaluate whether a bounded recovery mechanism (e.g., allowing the original depositor, provable via some other means, to reclaim balance from a `0u` account that has remained uninitialized past some very long timeout) is feasible without breaking the "id commits to bytes" invariant.

### Proof of Concept
1. Construct a valid `UniversalStateInit::V1` (e.g., one full-access key, no code, empty data).
2. Obtain its canonical `RawStateInit` via `to_raw()`; separately, hand-construct (or obtain from a differently-ordered/less strict borsh encoder) a **non-canonical** but still well-formed borsh encoding of the same logical value (e.g., `data` entries written out of canonical `BTreeMap` order, as shown in the repo's own `non_canonical_state_init` helper): [9](#0-8) 
3. Compute `id_a = derive_universal_account_id(&canonical_raw)` and `id_b = derive_universal_account_id(&non_canonical_raw)`; the repo's tests confirm `id_a != id_b` even though both decode to the identical logical `UniversalStateInit`: [10](#0-9) 
4. Send a `Transfer` action to `id_b` (the id obtained via the decode+re-encode path) with a nontrivial deposit. The account is created as `Uninitialized` and holds the funds (per `action_universal_state_init`'s "may already exist without its state" transfer path and confirmed by `test_dump_state_with_uninitialized_universal_account`).
5. Attempt to submit `UniversalStateInitAction { state_init: canonical_raw, .. }` addressed at `id_b`: it is rejected at validation with `InvalidUniversalStateInitReceiver { receiver_id: id_b, derived_id: id_a }` because `id_a != id_b`: [3](#0-2) 
6. There is no bytes the depositor's canonical encoder can ever produce that hash to `id_b` (a canonical encoder never emits `non_canonical_raw`), so `id_b`'s account remains permanently `Uninitialized`, and only `AccountNotInitialized`-rejected actions or further deposits are possible against it, as confirmed by `uninitialized_account_rejects_actions_needing_state`: [8](#0-7) 
The deposited balance is unrecoverable.

/// Returns the `0u` universal account ID defined by `state_init`: SHA3-256
/// (FIPS-202) over exactly those bytes, encoded with the UAID address codec.
///
/// **Note:** This function deliberately does not take `UniversalStateInit`, but
/// `RawStateInit`, because account ID is committed to the exact user-supplied bytes.
/// Re-serializing could yield a different ID, if `state_init` contained non-canonical
/// borsh representation.
pub fn derive_universal_account_id(state_init: &RawStateInit) -> AccountId {
    use sha3::Digest;
    let hash = sha3::Sha3_256::digest(&state_init.0).into();
    encode_universal_account_id(&hash)
}

        // Borsh accepts it and re-sorts on decode, so the typed form's own encoding
        // differs from this one.

            bytes.extend_from_slice(&1u32.to_le_bytes());
            bytes.push(key);
            bytes.extend_from_slice(&0u32.to_le_bytes());

/// A state init whose borsh is valid but is not what the typed form would write:
/// the storage entries are in descending key order, which borsh accepts and
/// re-sorts on decode. Hand-assembled, since the typed API cannot express it.
fn non_canonical_state_init(public_key: &PublicKey) -> RawStateInit {
    let mut bytes = vec![
        0, // V1
        0, // code: None
    ];
    bytes.extend_from_slice(&2u32.to_le_bytes()); // data: 2 entries, descending
    for (key, value) in [(b"b", b"2"), (b"a", b"1")] {
        bytes.extend_from_slice(&1u32.to_le_bytes());
        bytes.extend_from_slice(key);
        bytes.extend_from_slice(&1u32.to_le_bytes());
        bytes.extend_from_slice(value);
    }
    bytes.extend_from_slice(&1u32.to_le_bytes()); // access_keys: 1
    let handle = PublicKeyHandle::from(public_key.clone());
    bytes.extend_from_slice(&borsh::to_vec(&handle).expect("borsh must not fail"));
    RawStateInit(bytes)
}

/// The account created is the one derived from the bytes the sender serialized,
/// not from re-encoding the struct they decode to. Two encodings of the same
/// logical state init are two different accounts, which is what lets a producer
/// whose serializer does not sort `BTree*` containers still address its account.
#[test]
fn test_universal_state_init_derives_from_supplied_bytes() {
    init_test_logger();
    let mut env = Env::setup();

    let public_key = SecretKey::from_seed(KeyType::ED25519, "uaid-non-canonical").public_key();
    let raw = non_canonical_state_init(&public_key);

    // Without this the test proves nothing: it has to be an encoding the typed
    // form would not have written.
    let decoded = UniversalStateInit::from_raw(&raw).expect("fixture must be valid borsh");
    assert_ne!(decoded.to_raw().0, raw.0, "fixture must be non-canonical");

    let from_supplied = derive_universal_account_id(&raw);
    let from_re_encoding = decoded.derive_account_id();
    assert_ne!(from_supplied, from_re_encoding, "the two encodings must derive different ids");

    env.create_universal_account(raw, &from_supplied, Balance::from_near(1));

    // The account exists at the id derived from the bytes that were sent...
    let view = env.view_account(&from_supplied);
    assert!(view.storage_usage > 0, "the supplied bytes should have created the account");
    let access_key = env.env.rpc_node().view_access_key_query(&from_supplied, &public_key).unwrap();
    assert!(
        matches!(access_key.permission, AccessKeyPermissionView::FullAccess),
        "installed key must be full access, got {:?}",
        access_key.permission
    );

    // ...and nothing exists at the id their re-encoding would have derived.
    assert!(
        env.try_view_account(&from_re_encoding).is_err(),
        "re-encoding the decoded state init must not be what the id follows"
    );
}
