### Title
Inconsistent signer-weight threshold rounding between `GlobalStateEvaluator::reached_agreement` and `NakamotoBlockHeader::compute_voting_weight_threshold` - (File: libsigner/src/v0/signer_state.rs)

### Summary
The external report's root cause is a rounding-direction bug: a division performed before a multiplication (or, more generally, a threshold computed without correct ceiling) silently shifts an economic/consensus boundary. The Stacks codebase contains the same *rounding-inconsistency* bug class in the signer-weight approval threshold: two different formulas are used to compute the "70% of total signer weight" consensus boundary, and only one of them rounds up (ceils). This creates two different numeric thresholds for what should be the exact same quantity.

### Finding Description
The consensus-critical threshold for accepting a Nakamoto block is computed with an explicit ceiling: [1](#0-0) 

```
let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
u32::try_from((total_weight * threshold) / 10 + ceil)...
```

This is used by `verify_signer_signatures` to decide whether a block has enough signer weight to be valid [2](#0-1) , and matches the round-up unit test (e.g. `total_weight=511` → threshold `358`, not `357`) [3](#0-2) .

However, the `GlobalStateEvaluator` in `libsigner`, which signers use to determine the network's agreed-upon current miner, burn view, protocol version, and transaction-replay set, computes the *same nominal 70% threshold* using plain floor division with no ceiling adjustment: [4](#0-3) 

```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
```

For `total_weight = 511`, `compute_voting_weight_threshold` yields `358`, but `reached_agreement`'s inline computation yields `floor(511*7/10) = 357`. `reached_agreement` gates `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, and `determine_global_state` (current-miner state machine and tx-replay-set agreement) [5](#0-4) , which in turn feeds signer decisions about which miner/tenure to treat as canonical and which transaction-replay set to honor.

The equality broken: "signer weight considered sufficient for global-state agreement" should equal "signer weight required for block/consensus approval" (`compute_voting_weight_threshold`), but the two formulas diverge by exactly one weight unit whenever `total_weight * 7` is not a multiple of 10 (the majority of possible `total_weight` values, since `reward_slots` and thus total weight is not always a multiple of 10).

### Impact Explanation
This is a threshold/validation divergence within the signer set (matching the allowed class "signer weight below threshold or from the wrong set"). Because `GlobalStateEvaluator::reached_agreement` can register "global agreement" on a current-miner/tenure view or tx-replay set at a lower weight than the network's real approval threshold, individual signer nodes can conclude the network has agreed on a given miner/tenure or replay set while that same aggregate weight would fail the stricter `compute_voting_weight_threshold` check used for actual block signature acceptance elsewhere in the protocol. This can produce a temporary tip/state disagreement among signers about the canonical miner/tenure, which is a High-impact class per the given rubric ("minority-triggerable... temporary tip disagreement"), bounded to signer coordination rather than causing a deep chain split by itself.

### Likelihood Explanation
This divergence is not attacker-exclusive; it occurs deterministically whenever `total_weight * NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` is not an exact multiple of 10 (the common case) and votes land exactly on the boundary between the floor and ceil values. No majority collusion is required — any distribution of votes producing a sum in that one-unit gap will do, making it reachable under ordinary signer-set compositions rather than requiring an adversarial majority.

### Recommendation
Replace the inline floor-division threshold math in `reached_agreement`/`reached_disagreement` (`libsigner/src/v0/signer_state.rs`) with a call to (or the same ceiling logic as) `NakamotoBlockHeader::compute_voting_weight_threshold`, ensuring both consensus paths use one canonical, consistently-rounded threshold function.

### Proof of Concept
1. Configure a reward set with `total_weight = 511`.
2. `NakamotoBlockHeader::compute_voting_weight_threshold(511)` returns `358` (verified by the existing unit test) [3](#0-2) .
3. Construct a `GlobalStateEvaluator` with `total_weight = 511` and submit signer state updates summing to exactly `357` weight units supporting a particular `current_miner`/burn view.
4. `reached_agreement(357)` evaluates `511 * 7 / 10 = 357` (floor, no ceil) and returns `true`, causing `determine_global_state()` to report consensus on that miner/tenure view [6](#0-5) , even though `358` weight units would be required for the equivalent block-approval threshold used by `verify_signer_signatures`, demonstrating the two threshold computations diverge by one unit at this boundary.

Note: I was unable to trace every downstream consumer of `determine_global_state()`/`reached_agreement()` in `stacks-signer/src/v0/signer.rs` and `signer_state.rs` within the available search budget, so the exact operational consequence (e.g., whether it can cause a signer to sign a block for the "wrong" miner) should be confirmed by a deeper read of those files before treating this as fully proven end-to-end.

    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }
