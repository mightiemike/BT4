### Title
Owner role lockout via unrecoverable `DeleteKey` action on ETH-implicit Wallet Contract accounts - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (NEP-518) lets an ETH-implicit account owner submit an RLP-signed `DeleteKey` action that is converted, in one irreversible step, into `Promise::new(target).delete_key(action.public_key)` with no check that at least one usable access key remains on the account. Because `AddKey` with `FullAccess` permission is explicitly rejected for this contract (`UnsupportedAction::AddFullAccessKey`) and ETH-implicit accounts can never receive a full access key nor be deleted, deleting the last remaining `FunctionCall` relayer key permanently removes every possible way to submit a future transaction to that account, mirroring the "one-step ownership/permission change with no recovery path" bug class from the report.

### Finding Description
`action_to_promise` in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:475-501` translates a decoded RLP action into a NEAR promise:
```
near_action::Action::DeleteKey(action) => {
    Ok(Promise::new(target).delete_key(action.public_key))
}
```
There is no validation of how many access keys remain on `target` before the delete is scheduled, and no two-step/staged recovery mechanism analogous to the report's recommendation. Meanwhile `AddKey` for `FullAccess` is unconditionally rejected:
```
near_action::AccessKeyPermission::FullAccess => {
    Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
}
``` [1](#0-0) 

Documentation confirms the account can never regain a full access key nor be deleted once created:
"An ETH-implicit account can only be used by calling the methods of the Wallet Contract. It cannot be deleted, nor can a full access key be added." [2](#0-1) 

The only access keys an ETH-implicit account can ever hold are `FunctionCall`-permission relayer keys added via `add_access_key_allowance_with_nonce` in the same `action_to_promise` function: [3](#0-2) 

If the owner (via a valid RLP-signed transaction, which is exactly the "unprivileged transaction signer" reachable path) issues `DeleteKey` targeting the last remaining relayer key on their own eth-implicit account — whether by mistake, by a relayer coercing a specific signed payload, or simply because no replacement key was queued in the same batch — there is no subsequent way to submit any further transaction to that account: no full access key can ever be added, and `rlp_execute` itself can only be invoked by an account that already possesses an access key on the target.

### Impact Explanation
This permanently freezes any NEAR/NEP-141 balances held by the affected ETH-implicit account, matching the accepted "permanently frozen funds" impact category. Unlike the generic NEAR account model (where a compromised full-access-key situation can sometimes be mitigated by other keys, and where account owners intentionally manage their own keys with full understanding of the risk), the Wallet Contract path structurally forbids the standard recovery route (`AddKey` FullAccess) that exists for every other account type, making the lockout unconditional and irreversible once the last relayer key is gone.

### Likelihood Explanation
The action is reachable purely from a single signed Ethereum-style transaction routed through `rlp_execute` — no validator or node collusion needed. It can happen from ordinary usage (e.g., a wallet UI rotating relayer keys and issuing `DeleteKey` before the corresponding `AddKey` succeeds, or a relayer submitting only the delete half of a rotation), which is a realistic and low-effort trigger, consistent with the Medium severity rated in the original report for the analogous single-step ownership change.

### Recommendation
Before executing a `DeleteKey` action inside `action_to_promise`, verify (via a state read/callback) that the target account will retain at least one active `FunctionCall` access key with sufficient permission to invoke `rlp_execute` after the deletion completes, or require any relayer-key rotation to be expressed as an atomic `AddKey` + `DeleteKey` pair executed as a single all-or-nothing promise batch, so the account is never left with zero usable relayer keys.

### Proof of Concept
1. Create an ETH-implicit account and, via the address's Wallet Contract, add exactly one relayer `FunctionCall` access key `K1` using the `AddKey` RLP action path (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:488-495`).
2. Sign and submit (via any relayer) an RLP transaction whose decoded action is `DeleteKey(K1)` targeting the same eth-implicit account, executed through `rlp_execute` → `inner_rlp_execute` → `action_to_promise` (`lib.rs:330-501`).
3. Observe the `DeleteKey` promise executes successfully and removes `K1`, leaving the account with zero access keys.
4. Attempt to submit any further `rlp_execute` call (or any other transaction) to the account: it fails because there is no access key on the account to authorize the call, and no `AddKey(FullAccess)` path exists (`UnsupportedAction::AddFullAccessKey`, `lib.rs:485-487`), and the account cannot be deleted per the documented invariant.
5. Any NEAR/NEP-141 balance held by the account is now permanently unreachable.

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
```
