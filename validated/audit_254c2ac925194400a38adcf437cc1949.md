### Title
Shielded TRC20 Mint/Burn Trusts Declared Amount Instead of Actual Token Balance Delta, Enabling Note/Reserve Desync with Non-Standard TRC20 Tokens - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`Wallet.createShieldedContractParameters`/`createShieldedContractParametersWithoutAsk` build shielded MINT and BURN note-values by trusting `fromAmount`/`toAmount` supplied in the RPC request (scaled only by the token's `scalingFactor()`), and assert these values match the notes' commitments. Neither the wallet layer nor the `ShieldedTRC20ParametersBuilder`/shielded pool interaction verifies that the number of TRC20 tokens actually moved into or out of the shielded pool contract matches this declared amount. This is the same root-cause pattern as the reported RoyaltyVault/Splitter bug: accounting is derived from a nominal transfer amount rather than an observed balance delta.

### Finding Description
For MINT, the caller declares `fromAmount`; `checkPublicAmount` scales it by `scalingFactor()` and the resulting `scaledFromAmount` is required to equal the value of the shielded receive note being created. [2](#0-1)  For BURN, `scaledToAmount` (derived the same way) must equal the spent note's value, and this amount is later used by `ShieldedTRC20ParametersBuilder.build` to encrypt the burn message and to encode `transparentToAmount`/`value`, which is used as the on-chain transfer amount to the recipient. [3](#0-2) 

None of this logic queries `balanceOf()` before/after invoking the shielded pool's TRC20 `transferFrom`/`transfer` to determine how many tokens were actually received or sent by the pool contract — it only relies on the declared amount and `scalingFactor()`. If the underlying TRC20 token backing a shielded pool is a fee-on-transfer or rebasing token (or has any other non-standard transfer semantics), the number of shielded notes minted can exceed the tokens actually deposited into the pool (mint side), or the pool can promise to pay out (burn side) more tokens than it actually holds relative to outstanding shielded value, corrupting the pool's internal transparent/shielded balance invariant — this mirrors exactly the FoT/rebasing accounting mismatch described in the report, just for the shielded TRC20 bridge instead of `RoyaltyVault`/`Splitter`.

### Impact Explanation
If a shielded pool is deployed for a non-standard TRC20 (fee-on-transfer or rebasing), an attacker or ordinary user can:
- Mint shielded notes whose total declared value exceeds the tokens actually deposited (deflationary/FoT token), inflating claimable shielded value beyond the pool's real token reserve.
- Over time this creates a shortfall such that the last legitimate burn/withdraw fails because the pool no longer holds enough tokens, denying service and effectively stealing funds from other legitimate note holders — an accounting/asset corruption analogous to the referenced report's DoS/fund-loss scenario.

This is a protocol-level, TRC20-integration issue reachable via ordinary RPC calls (`createShieldedContractParameters`, then broadcasting the built transaction), not requiring any privileged role.

### Likelihood Explanation
Exploitability strictly depends on which TRC20 token is bound to a given shielded pool contract. Standard-compliant, non-fee/non-rebasing TRC20s (as officially supported, e.g. USDT/USDD on TRON) are unaffected. However, since java-tron itself does not restrict or document which tokens are shielded-pool eligible at this validation layer, and does not perform balance-delta checks, the risk depends entirely on external deployment/token choice — same "requires exotic token" caveat noted in the original report and its confirmed status.

### Recommendation
Before finalizing MINT parameters (and prior to broadcasting BURN), query the shielded pool contract's TRC20 `balanceOf()` before and after the transfer/mint operation, and require the declared `fromAmount`/`toAmount` to equal the actual observed balance delta rather than trusting the client-supplied value scaled only by `scalingFactor()`. At minimum, document that only standard, non-fee-on-transfer, non-rebasing TRC20 tokens are supported for shielded pools, consistent with the original report's suggested mitigation.

### Proof of Concept
Conceptual PoC (cannot be executed without deploying a live FoT TRC20 and shielded pool contract, which is outside index scope):
1. Deploy a shielded TRC20 pool bound to a TRC20 token that charges e.g. a 5% fee on `transfer`.
2. Call `createShieldedContractParameters` with `from_amount = 1000` (scaled), producing a MINT note of value 1000 shielded units, per [2](#0-1) .
3. Broadcast the resulting trigger transaction; due to the 5% fee, the pool contract actually receives only 950 tokens, while 1000 units of shielded value now exist as claimable notes.
4. Repeat until, upon burn/withdrawal by legitimate note holders, the pool's actual TRC20 balance is insufficient to satisfy all outstanding shielded note values, causing the last burn transactions to revert — reproducing the "last user cannot withdraw" scenario from the referenced report.

   * trigger contract to get the scalingFactor, and check the public amount,

  private long[] checkPublicAmount(byte[] address, BigInteger fromAmount, BigInteger toAmount)
      throws ContractExeException, ContractValidateException {
    checkBigIntegerRange(fromAmount);
    checkBigIntegerRange(toAmount);

    BigInteger scalingFactor;
    try {
      byte[] scalingFactorBytes = getShieldedContractScalingFactor(address);
      scalingFactor = ByteUtil.bytesToBigInteger(scalingFactorBytes);
    } catch (ContractExeException e) {
      throw new ContractExeException("Get shielded contract scalingFactor failed");
    }
    if (scalingFactor.compareTo(BigInteger.ZERO) <= 0) {
      throw new ContractValidateException("scalingFactor must be positive");
    }

    // fromAmount and toAmount must be a multiple of scalingFactor
    if (!(fromAmount.mod(scalingFactor).equals(BigInteger.ZERO)
        && toAmount.mod(scalingFactor).equals(BigInteger.ZERO))) {
      throw new ContractValidateException("fromAmount or toAmount invalid");
    }

    long[] ret = new long[2];
    try {
      ret[0] = fromAmount.divide(scalingFactor).longValueExact();
      ret[1] = toAmount.divide(scalingFactor).longValueExact();
    } catch (ArithmeticException e) {
      throw new ContractValidateException("fromAmount or toAmount invalid");
    }

    return ret;
  }
