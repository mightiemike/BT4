### Title
Webhook HMAC does not bind the shop domain, allowing cross-tenant webhook forgery - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`)

### Summary
`shopify.webhooks.validate` authenticates an incoming webhook solely by recomputing an HMAC over `rawBody` with the app's shared `apiSecretKey`, exactly as `BufferRouter.resolveQueuedTrades` authenticated only the signed `price` while trusting the caller-supplied `asset`/`queueId` linkage without cross-checking it. Here, the `X-Shopify-Shop-Domain` header (`domain`) that identifies *which* installed shop the webhook is for is never included in the HMAC computation, so it is accepted unauthenticated and then used to select the tenant whose session/data the app acts upon.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC purely from `rawBody` and compares it against the `hmac` header: [4](#0-3) . The `domain`, `topic`, `apiVersion`, and `webhookId` headers are only checked for *presence*, never bound to the signature, in `checkWebhooksHeaders`: [5](#0-4) .

Because Shopify signs webhooks with the app's single, app-wide client secret (the same key regardless of which shop triggered the event), any merchant who has installed the app can capture a legitimately-signed `(rawBody, hmac)` pair from a webhook fired on their *own* store (e.g. by triggering `products/create` or any subscribed topic), and then replay that exact body+HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `validate()` will report `valid: true` with `domain` equal to the attacker-chosen victim domain, because the domain was never part of the authenticated content — this mirrors the BufferRouter flaw where `_openQueuedTrade` trusted `queuedTrade.targetContract`/asset linkage without validating it against the signed price's actual asset.

This forged, "valid" webhook is then used across all consuming packages to select the tenant context:
- `packages/apps/shopify-api/lib/webhooks/process.ts` passes `webhookCheck.domain` straight into the registered handler callback, which for `shopify-app-express` includes the built-in `APP_UNINSTALLED` handler that deletes **all sessions for that shop** via `AppInstallations.delete(shopDomain)` [2](#0-1) .
- `shopify-app-remix`/`shopify-app-react-router`'s `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` to load the victim shop's stored offline session and attach an authenticated Admin API client to the webhook context [6](#0-5) .

### Impact Explanation
An attacker (a single merchant who has installed the app — no privileged access required) can forge webhook deliveries attributed to any other shop that uses the same app, using only their own legitimately-signed webhook material. Depending on which handlers the app developer has registered, consequences include:
- Denial of service against victim shops: replaying a forged `APP_UNINSTALLED` webhook wipes the victim's stored sessions via the built-in Express handler, forcing re-authentication/breaking the app for that shop.
- Injection of attacker-controlled data into victim-shop business logic: any custom webhook handler (e.g. `orders/create`, `products/update`, GDPR `customers/redact`, `shop/redact`) executes with the attacker's payload but with `shop`/`session` bound to the victim, and (in the remix/react-router adapters) an authenticated `admin` client for the victim shop is handed to the handler, i.e. the handler runs with the victim's real Admin API credentials while trusting the attacker's forged event data.
- Cross-tenant confusion of any app state keyed by webhook `domain` (analytics, audit logs, per-shop counters, billing triggers, etc.).

### Likelihood Explanation
Reachable from an anonymous HTTP request to the app's webhook endpoint. The only prerequisite is that the attacker possesses at least one valid `(rawBody, hmac)` pair, which any merchant automatically obtains the moment any webhook fires for their own installed instance (no secret leakage or privileged access needed — this is normal, expected webhook traffic to their own shop). The victim only needs to be another shop with the same app installed. This is a single unprivileged actor exploiting a design gap, matching the "accepted forged Shopify request" / "cross-tenant access" acceptance criteria.

### Recommendation
Do not trust `X-Shopify-Shop-Domain` (or any other header) as authenticated once the HMAC check passes. Either:
- Require callers to independently confirm that the resolved session's `shop` matches an expected/allow-listed value before performing destructive or state-mutating actions (e.g., session deletion, admin API calls), or
- Cross-check the `domain` header against Shopify's known registered shop for this app installation (e.g., via the session lookup) before trusting it, rejecting webhooks where the claimed shop has no legitimate session or has never installed the app, and
- Consider rate limiting / anomaly detection on webhook domains that don't match a currently active install, and clearly document in `packages/apps/shopify-api/lib/webhooks/validate.ts` / `process.ts` that `domain` is not cryptographically bound to the payload so downstream consumers add their own tenant verification before acting on it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers/observes any subscribed webhook (e.g. `app/uninstalled` or any custom HTTP topic), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — both are valid per `validateHmacFromRequestFactory` since they were genuinely computed with the app's `apiSecretKey`.
2. Attacker resends the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic` to the desired topic (unchanged from step 1 to keep the HMAC valid, or crafted to match a body/topic pair the attacker controls).
3. `shopify.webhooks.validate` returns `{valid: true, domain: 'victim-shop.myshopify.com', ...}` because HMAC validation only checked `rawBody` (see `packages/apps/shopify-api/lib/utils/hmac-validator.ts` lines 168-200) and header presence (see `packages/apps/shopify-api/lib/webhooks/validate.ts` lines 99-134), never binding `domain` to the signature.
4. Downstream code (`process.ts`, or `authenticateWebhookFactory` in `shopify-app-remix`/`shopify-app-react-router`) treats the request as an authentic event for `victim-shop.myshopify.com`, loading its stored offline session/admin client or invoking the `APP_UNINSTALLED` deletion handler against it — exactly analogous to BufferRouter accepting a price signed for asset A while executing the trade against the queued order for asset B, since the "which tenant/asset" component of the request was never bound to what was actually signed.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
