I have enough context to give a definitive answer. `MAX_MATCH_NUM` (fixed at 20) in `MarketSellAssetActuator` is a hardcoded, non-governance-adjustable constant that limits the number of maker orders a single `MarketSellAssetContract` can match against. If a taker's order requires more matches than this limit (which is fully determined by the state of the public order book, not attacker-controlled state), `matchOrder` throws a `ContractValidateException`, permanently failing the transaction and reverting all its state changes.

### Title
Hardcoded MAX_MATCH_NUM in MarketSellAssetActuator can permanently block legitimate sell/buy orders (DoS) - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator` enforces a fixed cap of 20 order matches (`MAX_MATCH_NUM`) per `MarketSellAssetContract` execution. This constant has no getter/setter exposed to committee governance (unlike `MAX_ACTIVE_ORDER_NUM`, which at least has a `@Setter`), and there is no on-chain mechanism (proposal type) to raise it. If matching a taker's order against the resting order book at the best price requires more than 20 fills, the transaction throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM)` and fails deterministically, exactly mirroring the reported bug class: an unchangeable threshold parameter that can render otherwise-valid operations permanently stuck.

### Finding Description
In `matchOrder`, the actuator pulls up to `MAX_MATCH_NUM + 1` maker orders at the best price and iterates through them, incrementing `matchOrderCount` for every single maker order consumed [1](#0-0) . If more than `MAX_MATCH_NUM` (20) maker orders must be consumed to satisfy the taker's price/quantity, it throws a `ContractValidateException`, which propagates up through `execute()` and is converted into a `ContractExeException`, aborting the whole transaction (fee is not persisted because `accountStore.put` never runs) [2](#0-1) .

`MAX_MATCH_NUM` is declared as a private static field with only a `@Getter`, no setter, no proposal type, and no dynamic-store-backed configuration path [3](#0-2) . Unlike `MAX_ACTIVE_ORDER_NUM`, which is annotated `@Setter` (even though this is only exercised from unit tests), there is no path — administrative or otherwise — to adjust `MAX_MATCH_NUM` at runtime.

Because the number of matches required is a function of the public order book (an unprivileged, anonymous actor can post arbitrarily many small maker orders at the best price for a token pair via `MarketSellAssetContract`), any account/observer can engineer a book state where a legitimate taker order (for a size that would normally be perfectly fillable) always requires more than 20 fills at the best price, causing every attempt by that taker to fail with the same deterministic error, regardless of retries, as long as the offending resting orders remain.

### Impact Explanation
This is a protocol-level Denial-of-Service against the TRC10 exchange/market matching engine (`MarketSellAssetActuator`), reachable from any anonymous broadcast transaction containing a `MarketSellAssetContract`. A taker who wants to fill a large sell order at the best resting price can be permanently blocked from doing so if the book at that price level is fragmented into more than 20 orders — a condition trivially created by any other unprivileged account posting many small maker orders. There is no governance parameter, admin override, or retry strategy (other than manually splitting into smaller orders or waiting for the book to change) that can resolve this, matching the "stuck due to unchangeable constant" bug class from the external report, except here the "harvest" analog is an on-chain order-matching operation directly reachable by ordinary users rather than a strategy contract admin.

### Likelihood Explanation
Likelihood is moderate to high in any actively used TRC10 exchange market: fragmenting the best price level into >20 small orders is inexpensive (bounded only by `MarketSellAssetContract`'s `MarketSellFee` and `MAX_ACTIVE_ORDER_NUM`=100 orders per account) [3](#0-2) , and does not require any privileged role. The condition can occur unintentionally too (many independent market participants placing small orders at the same best price), making this a systemic availability issue, not merely a griefing vector.

### Recommendation
Convert `MAX_MATCH_NUM` into a dynamic, committee-governed parameter (mirroring how other exchange/market limits such as `MARKET_SELL_FEE`/`MARKET_CANCEL_FEE` are managed via `ProposalUtil`/`DynamicPropertiesStore`), so it can be raised without a hard fork if order-book fragmentation makes the current cap impractical. Alternatively (or additionally), allow partial fills to be persisted as a partially-matched resting order instead of reverting the whole transaction when the match limit is hit, so a taker's order is not entirely blocked — it simply gets less filled per transaction and the remainder stays queued or can be resubmitted.

### Proof of Concept
1. Deploy/enable market transactions (`ALLOW_MARKET_TRANSACTION`).
2. From account B (unprivileged), submit 21+ `MarketSellAssetContract` maker orders for pair (tokenA, tokenB) all at the identical best price (e.g., sell 100 tokenA for 200 tokenB, repeated 21 times) — see the existing test pattern for constructing this exact scenario [4](#0-3) .
3. From account A (taker), submit a `MarketSellAssetContract` sized to require matching against all 21+ maker orders at that price.
4. Observe the transaction fails with `ContractValidateException`/`ContractExeException`: "Too many matches. MAX_MATCH_NUM = 20", and this failure is deterministic and unresolvable by account A alone as long as the order book at that price remains fragmented in >20 pieces.

            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book
