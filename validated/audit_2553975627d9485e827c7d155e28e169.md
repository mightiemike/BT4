## Analysis Result

Based on the investigation, there's a valid analog: an uncaught-error panic (`.unwrap()` on a `Result` that can be `Err` from attacker-influenced routing data) reachable purely through ordinary transactions, capable of halting chunk production on a shard.

### Title
Chunk-apply panic via `.unwrap()` on `receiver_shard_id()` for stale `GlobalContractDistribution` receipts crossing unresolvable shard-layout history - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally `.unwrap()`s the result of `Receipt::receiver_shard_id(&shard_layout)` when popping a receipt from the persistent delayed-receipt queue. For `GlobalContractDistribution` receipts, `receiver_shard_id` returns `Err(EpochError::ShardingError(...))` whenever the receipt's recorded `target_shard` can no longer be resolved to a shard in the current layout (i.e. `ShardLayout::resolve_to_current_shard` fails to find a descendant). Any unprivileged account can trigger a `DeployGlobalContract` action, whose resulting `GlobalContractDistribution` receipt records a `target_shard`; if that receipt is kept in the delayed queue across the chunk's compute-limit backpressure while shard layout changes occur (resharding), the shard-tracking metadata attached to the receipt can become unresolvable, and the `.unwrap()` will panic during ordinary chunk application.

### Finding Description
- `receiver_shard_id` (`core/primitives/src/receipt.rs:437-466`) explicitly documents the failure mode for `GlobalContractDistribution`: `target_shard` may be from "an arbitrarily old layout" if "the receipt could have been delayed across multiple resharding events," and returns `Err(EpochError::ShardingError(...))` when `shard_layout.resolve_to_current_shard(target_shard)` cannot find a matching shard. [1](#0-0) 
- The only caller that consumes this path during ordinary delayed-receipt draining is `DelayedReceiptQueueWrapper::receipt_filter_fn`, which calls `.unwrap()` on that exact `Result` while popping receipts belonging to a shard that underwent a resharding split: [2](#0-1) 
- `pop()` invokes `receipt_filter_fn` on every delayed receipt while draining the persistent trie-backed delayed queue during normal chunk application (`runtime/runtime/src/congestion_control.rs:880-910`), which is on the hot path of `Runtime::apply` (called for every new chunk, `runtime/runtime/src/lib.rs:1717` region). [3](#0-2) 
- Nearcore's own regression test acknowledges this exact panic class exists and is only partially mitigated: it explicitly exercises **two** sequential resharding generations and asserts the chain keeps making progress, with the comment: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations."* [4](#0-3) 
The mitigation (`resolve_to_current_shard`, tracking split history) only covers the *split-history* case that the fix explicitly targeted. The `.unwrap()` panic point itself was not removed — it remains live in `receipt_filter_fn`, so any scenario outside what `resolve_to_current_shard`'s split-history bookkeeping covers (e.g., additional resharding generations beyond what was tested, shard-history pruning/GC, or any other case where the old `target_shard` cannot be mapped forward) will still panic the runtime's `apply()` call, i.e., every validator/node applying that shard's chunk crashes simultaneously.

### Impact Explanation
A panic inside `Runtime::apply` during ordinary chunk processing is not a recoverable, per-transaction failure — it aborts the node process. Because all honest validators/chunk producers tracking the affected shard execute the identical deterministic state transition, they all hit the same `.unwrap()` and panic simultaneously, producing a **transaction-triggered halt** of that shard (and, transitively, of chain progress depending on cross-shard dependencies). This matches the "Uncaught Exception" bug class in the reference advisory (permanent crash triggered by processing a single attacker-supplied artifact) but with materially higher severity here, since it can stop an entire shard rather than a single web app instance.

### Likelihood Explanation
Exploitation requires only standard permissionless capabilities: any account can submit a `DeployGlobalContract` transaction (creating a `GlobalContractDistribution` receipt with an attacker-influenced `target_shard`) and can submit gas-heavy transactions to keep a shard's compute budget saturated so the receipt is pushed into, and lingers in, the delayed queue while resharding proceeds. The recently added regression test demonstrates NEAR engineers themselves consider this reachable and worth guarding against for the 2-generation case; the underlying `.unwrap()` remains for any case exceeding that coverage, so likelihood is non-trivial though it requires orchestrating congestion across multiple resharding epochs (making it a targeted rather than trivial one-shot exploit).

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (and its `shard_layout(...).unwrap()` sibling) with graceful error handling: if `receiver_shard_id` cannot resolve a `GlobalContractDistribution` receipt's `target_shard` to any shard in the current layout, treat the receipt as belonging to a "catch-all"/allowed shard (or drop/re-forward it with a warning) instead of panicking the whole runtime. More robustly, ensure `resolve_to_current_shard`'s split-history bookkeeping is retained/extended to cover an unbounded number of resharding generations (or persist a canonical mapping keyed by receipt rather than relying on shard-layout history depth), so `receiver_shard_id` never returns `Err` for a receipt that was validly created under a prior layout.

### Proof of Concept
1. As any account, deploy a global contract (`DeployGlobalContract`, `GlobalContractDeployMode::CodeHash`) from an account located in a shard slated for a dynamic-resharding split — this creates a `GlobalContractDistribution` receipt whose `target_shard` is the pre-split shard id.
2. Continuously submit gas-heavy `FunctionCall` transactions (e.g. burning ~half the gas limit each, several per block) to the same shard so its compute budget is saturated every block, forcing the incoming `GlobalContractDistribution` receipt into the persistent delayed-receipt queue instead of executing immediately.
3. Allow/force enough additional dynamic-resharding split events to occur while the receipt sits in the delayed queue such that `ShardLayout::resolve_to_current_shard` can no longer map the original `target_shard` forward (the nearcore team's own test only validates up to two generations — go beyond that boundary, or exploit any layout-history pruning/GC path).
4. Stop saturating compute so the runtime drains the delayed queue; `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` calls `receiver_shard_id(&shard_layout).unwrap()` on the stale receipt, which returns `Err(EpochError::ShardingError)`, panicking `Runtime::apply` on every node applying that shard's chunk and halting chunk production. [5](#0-4)

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }

fn test_stale_global_contract_distribution_after_double_resharding() {

        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
