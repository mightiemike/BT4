### Title
Unbounded/negative index derived from attacker-controlled `Contract.type` in `checkPermissionOperations` causes uncaught `IndexOutOfBoundsException` (DoS) - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
`WalletUtil.checkPermissionOperations` only validates that `permission.getOperations()` is exactly 32 bytes, but never validates that the contract's type value is within the expected `0..255` range before using it to index into that 32-byte bitmap. Because `contract.getTypeValue()` returns the raw underlying `int32` of a protobuf enum field (which in proto3 accepts arbitrary/unrecognized values, including negative ones via wire-level encoding), an attacker can supply a transaction whose `Contract.type` field decodes to a negative or very large integer, causing `ByteString.byteAt()` to be called with an out-of-range index and throw an uncaught `IndexOutOfBoundsException`.

### Finding Description
The method is: [1](#0-0) 

It checks only `operations.size() != 32`, but computes `contractType = contract.getTypeValue()` and directly uses `contractType / 8` and `contractType % 8` as an index into the fixed 32-byte `operations` bitmap without validating that `contractType` falls in `[0, 255]`. `Contract.getTypeValue()` returns the raw `int32` backing an enum field; in proto3, enum wire values are not restricted to declared enum constants — a crafted/raw transaction can encode any `int32` value (including negative numbers via varint sign-extension, or very large positive values) into that field, and `getTypeValue()` will happily return it as `UNRECOGNIZED`'s underlying value. When `contractType` is negative, Java's `/` and `%` operators produce a negative index (e.g., `-8/8 = -1`), causing `operations.byteAt(-1)` to throw. When `contractType` is very large (e.g., `Integer.MAX_VALUE`), `contractType/8` exceeds 31, again throwing an out-of-bounds exception. This is exactly the sign-extension/negative-index class of bug described: lengths/indices are trusted as validated without bounding, when in fact they are attacker-controlled raw wire values.

The size check on `operations` (`!= 32`) gives a false sense of safety — it bounds the array itself but not the index used against it.

### Impact Explanation
An uncaught `IndexOutOfBoundsException` thrown from a permission-checking routine invoked during transaction/permission validation can propagate as an unexpected runtime exception in the transaction processing path. Depending on the caller's exception handling, this can cause request-level failures, inconsistent validation behavior, or destabilize a node processing loop, matching a "DoS via protocol implementation" impact class rather than fund loss or key leakage.

### Likelihood Explanation
Constructing such a transaction requires only the ability to submit a transaction with a `Contract.type` field encoded with an out-of-range enum value and an accompanying `Permission` with a 32-byte `operations` field — accessible to any unprivileged party able to broadcast raw transaction bytes or otherwise reach permission validation. No special key, role, or node access is needed; cost is limited to whatever fee/broadcast requirement normally applies to a transaction. The exact reachability from `TransactionCapsule`/actuator validation paths (confirmed call sites exist in `TransactionCapsule.java`, `TransactionUtil.java`, and `Wallet.java`) was not fully traced end-to-end within available iterations, so the precise handling of the thrown exception at each call site (whether it is caught and converted into a normal validation failure, or propagates uncaught) could not be conclusively verified.

### Recommendation
Before indexing, validate `contractType` is within `[0, operations.size() * 8)` (i.e., `0 <= contractType < 256` for a 32-byte bitmap) and throw a `PermissionException` (not an unchecked exception) otherwise:
```java
int contractType = contract.getTypeValue();
if (contractType < 0 || contractType / 8 >= operations.size()) {
  throw new PermissionException("contract type out of range: " + contractType);
}
```

```java
  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
```
