## Finding

### Title
Off-by-one leaf count passed to `confirm_or_save_frozen_subtrees` corrupts the transaction accumulator during fast-sync state-snapshot finalization - (File: `storage/aptosdb/src/db/aptosdb_writer.rs`)

### Summary
`AptosDB::finalize_state_snapshot` (used during fast-sync / state-snapshot restore) calls `restore_utils::confirm_or_save_frozen_subtrees` with the raw `version` as the `num_leaves` argument, instead of `version + 1` (the number of leaves that exist up to and including `version`). Every other call site in the codebase that derives `num_leaves`/`num_transactions` from a `Version` consistently uses `version + 1`, confirming this is the correct convention and that the call in `finalize_state_snapshot` is inconsistent with it.

### Finding Description
`confirm_or_save_frozen_subtrees` uses its `num_leaves: LeafCount` parameter to compute the accumulator's frozen-subtree `Position`s via `FrozenSubTreeIterator::new(num_leaves)`, then zips those positions with the caller-supplied `frozen_subtrees` hash list (taken from the sync proof's `left_siblings()`) and writes each `(position, hash)` pair into `TransactionAccumulatorSchema`: [1](#0-0) [2](#0-1) 

The codebase's established convention is that `num_leaves` (or `num_transactions`) equals `version + 1`, since accumulator leaf indices are 0-based and a ledger at `version` V contains V+1 transactions/leaves. This is demonstrated by every other accumulator-position-computing call site: [3](#0-2) 

However, in `AptosDB::finalize_state_snapshot`, the raw `version` (not `version + 1`) is passed directly as `num_leaves`: [4](#0-3) 

Since `FrozenSubTreeIterator` derives the tree's frozen-subtree decomposition from the binary representation of `num_leaves`, an off-by-one input does not merely shift results — it can produce an entirely different set/count of subtree `Position`s than the one that was actually used to build the `left_siblings()` proof data supplied by the peer. The function does compare `positions.len() == frozen_subtrees.len()` as a sanity check, but for the versions where the leaf-count binary representations happen to coincide in position count, the `(position, hash)` pairing will silently be **wrong**, writing correct-looking hashes into the wrong `TransactionAccumulatorSchema` keys inside the local ledger's accumulator database, corrupting durable ledger data used to serve/verify future accumulator and transaction proofs.

### Impact Explanation
`TransactionAccumulatorSchema` entries written here back the frozen-subtree cache the accumulator relies on for `get_frozen_subtree_hashes`, `get_transaction_proof`, `get_transaction_range_proof`, and `get_consistency_proof`: [5](#0-4) 

If this data is committed at the wrong `Position`, a node that fast-synced through `finalize_state_snapshot` will have a locally corrupted accumulator structure that no longer matches the canonical ledger. Any subsequent transaction/accumulator proof served by that node (or generated for its own restore continuation) would be built on the wrong leaf hashes at the wrong tree positions — i.e., a wrong accumulator/Merkle proof that could still verify internally against a locally-derived (but wrong) root, or fail entirely and halt sync. This falls squarely within the "wrong accumulator root, Merkle proof… accepted as valid" and "restore paths… must preserve deterministic proof binding" impact categories.

### Likelihood Explanation
This code path executes automatically and unprivileged whenever a node performs a fast-sync/state-snapshot restore (a normal, non-privileged operational flow, not requiring any special permission) — every full node or validator that fast-syncs invokes `finalize_state_snapshot`. The bug is deterministic given the version being finalized; it doesn't require any attacker action, just a call with a version whose `+1`/`-1` leaf-count binary decomposition length coincidentally matches (this depends on version value, but is not a rare edge case since it recurs for infinitely many version values based on binary structure of leaf counts).

### Recommendation
Change the call in `finalize_state_snapshot` to pass `version + 1` (matching the convention of `get_transaction_proof`/`get_frozen_subtree_hashes`), i.e.:
```rust
restore_utils::confirm_or_save_frozen_subtrees(
    self.ledger_db.transaction_accumulator_db_raw(),
    version + 1,
    frozen_subtrees,
    None,
)?;
```
Additionally, consider strengthening `confirm_or_save_frozen_subtrees_impl`'s existing length-only `ensure!` check to also validate that the computed `Position`s are structurally consistent with the supplied proof (e.g., cross-check against the proof's own claimed leaf count) so a silent, coincidental length match cannot mask a leaf-count mismatch.

### Proof of Concept
Not independently exploitable via external input in the classic sense (no attacker-controlled malicious peer is required per the scope), but reproducible locally:
1. Drive a node through `finalize_state_snapshot` at a chosen `version` where `FrozenSubTreeIterator::new(version)` and `FrozenSubTreeIterator::new(version + 1)` produce position lists of equal length (occurs for various binary patterns of leaf counts).
2. Observe that `confirm_or_save_frozen_subtrees` writes the proof's `left_siblings()` hashes to the `Position`s computed from `version` instead of `version + 1`.
3. Query `get_transaction_proof`/`get_frozen_subtree_hashes` afterward at/above that version and observe a proof/root that no longer matches the canonical ledger accumulator, since `get_frozen_subtree_hashes` and `get_transaction_proof` both compute positions using `ledger_version + 1`: [6](#0-5) 

Note: I could not fully verify within available iterations whether `restore_handler.rs`'s separate `confirm_or_save_frozen_subtrees` wrapper (used by the backup-cli `transaction/restore.rs` path) applies a `+1` correction before delegating to `restore_utils::confirm_or_save_frozen_subtrees` — that call site passes `first_chunk.manifest.first_version` directly and could not be inspected further in this session. The `aptosdb_writer.rs` call site analyzed above, however, is unambiguous and directly citable.

```rust
/// A helper function that confirms or saves the frozen subtrees to the given change set
fn confirm_or_save_frozen_subtrees_impl(
    transaction_accumulator_db: &DB,
    frozen_subtrees: &[HashValue],
    positions: Vec<Position>,
    batch: &mut SchemaBatch,
) -> Result<()> {
    positions
        .iter()
        .zip(frozen_subtrees.iter().rev())
        .map(|(p, h)| {
            if let Some(_h) = transaction_accumulator_db.get::<TransactionAccumulatorSchema>(p)? {
                ensure!(
                        h == &_h,
                        "Frozen subtree root does not match that already in DB. Provided: {}, in db: {}.",
                        h,
                        _h,
                    );
            } else {
                batch.put::<TransactionAccumulatorSchema>(p, h)?;
            }
            Ok(())
        })
        .collect::<Result<Vec<_>>>()?;
```

```rust
        ledger_version: Version,

    }
```
