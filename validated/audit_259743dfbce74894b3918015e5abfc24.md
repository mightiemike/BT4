Based on my investigation, the closest native analog to the `wLP` blacklist finding is in `x/uexecutor`'s outbound-creation path, where an admin-curated registry flag (`ChainConfig.Enabled.IsOutboundEnabled`) or token removal (`RemoveTokenConfig`) can strand funds that a user has already irreversibly committed on Push Chain via `UniversalGatewayPC`.

### Title
Withdrawal (outbound) events are silently dropped when destination-chain outbound or the token is disabled *after* the user's PRC20 has already been burned/withdrawn on Push Chain — ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
`x/uregistry` lets the admin toggle `ChainConfig.Enabled.IsOutboundEnabled` and remove/disable `TokenConfig` entries at any time via `MsgUpdateChainConfig` / `MsgRemoveTokenConfig` [1](#0-0) . These flags are re-checked, at outbound-creation time, against a user's already-submitted EVM transaction that called `UniversalGatewayPC` to withdraw/burn a PRC20, exactly mirroring the InitCapital pattern where a collateral-affecting flag is flipped after the user has already committed state.

### Finding Description
`BuildOutboundsFromReceipt` is invoked from the EVM post-tx-processing path once a user's transaction has already emitted a `UniversalTxOutboundEvent` from `UNIVERSAL_GATEWAY_PC` (i.e., the PRC20 burn / gateway call already executed on the EVM side) [2](#0-1) . It then re-validates the destination chain and token against the *current* registry state:

```
outboundEnabled, err := k.uregistryKeeper.IsChainOutboundEnabled(ctx, event.ChainId)
...
if !outboundEnabled {
    return nil, fmt.Errorf("outbound is disabled for chain %s", event.ChainId)
}
tokenCfg, err := k.uregistryKeeper.GetTokenConfigByPRC20(ctx, event.ChainId, event.Token)
if err != nil {
    return nil, err
}
``` [3](#0-2) 

If the admin disabled outbound for that chain, or removed the token config, between the time the user's transaction was submitted and the time this hook runs, `BuildOutboundsFromReceipt` errors out and no `OutboundTx`/`PendingOutbounds` entry is ever created for that withdrawal — confirmed directly by the integration test that expects `err.Error()` to contain `"outbound is disabled"` [4](#0-3) .

This is the direct structural analog of the reported wLP issue: a user already deposited/committed collateral (here: already burned PRC20 / triggered the gateway withdrawal event), and a subsequent config change (blacklist / disable) by the admin prevents completion of the corresponding withdrawal, with no code path shown that guarantees the underlying EVM burn is atomically rolled back together with the outbound-creation failure.

The project's own documentation independently acknowledges this exact risk class for the `PendingOutbounds` lifecycle, stating resolution is deliberately left to governance ("Auto-refund risks double-pay... resolution is governance-driven, not chain-driven") [5](#0-4) , and provides an admin-only `RESCUE_FUNDS` / rescue-outbound escape hatch (`AttachRescueOutboundFromReceipt`) [6](#0-5)  for stuck funds — evidence the team is aware of this bug class and has partially mitigated it, similar to the sponsor's "we will use unwhitelisting with care" response in the original report.

### Impact Explanation
If the underlying EVM transaction (the PRC20 burn/withdrawal call to `UniversalGatewayPC`) is not atomically reverted when `BuildOutboundsFromReceipt` returns an error, an honest user's withdrawal is silently dropped: their PRC20 is burned but no corresponding outbound is ever created, resulting in permanent loss of funds with no automated recovery — matching the "permanent loss of user-controlled funds" allowed-impact category. Even if the burn is atomically reverted (which I could not confirm — see below), the user still cannot withdraw until an admin manually intervenes via the `RESCUE_FUNDS` path, an availability/DoS-style impact on withdrawals for legitimately owned funds.

### Likelihood Explanation
Medium. This requires an admin config change (disabling outbound / removing a token) to race against an in-flight user withdrawal — the same "acknowledged, will use with care" scenario as the original report. It is not attacker-triggerable, but it is reachable purely through ordinary admin registry maintenance combined with an ordinary user transaction, with no attacker privilege required to be the victim.

### Recommendation
1. Verify (and if missing, enforce) that a failure inside `BuildOutboundsFromReceipt` / `CreateUniversalTxFromReceiptIfOutbound` fully reverts the originating EVM message's state changes (the PRC20 burn), so the two failure modes are: (a) burn + outbound both succeed, or (b) neither happens — never a burn without an outbound.
2. If atomic revert is not achievable (e.g., because the burn already landed in a separate, already-committed EVM transaction), automatically attach a `RESCUE_FUNDS`/refund outbound instead of just returning a hard error when `IsChainOutboundEnabled` or `GetTokenConfigByPRC20` fails, mirroring the `INBOUND_REVERT` pattern already used for failed inbound flows.
3. Document and, if possible, enforce a drain/decommission workflow for `MsgUpdateChainConfig`/`MsgRemoveTokenConfig` analogous to `x/utss`'s `InitiateFundMigration`, which already blocks disabling actions while `HasPendingOutboundsForChain` is true [7](#0-6)  — but note this guard does not exist for `uregistry`'s own `MsgUpdateChainConfig`/`MsgRemoveTokenConfig` handlers themselves.

### Proof of Concept
1. Admin registers chain X with `IsOutboundEnabled=true` and token T.
2. User submits an EVM transaction calling `UniversalGatewayPC` to withdraw PRC20(T) to chain X, emitting `UniversalTxOutboundEvent`.
3. In the same or an adjacent block, admin submits `MsgUpdateChainConfig` disabling outbound for chain X (or `MsgRemoveTokenConfig` for T) — a normal, legitimate admin action, not requiring any exploit.
4. The post-tx-processing hook runs `BuildOutboundsFromReceipt`, which now sees `IsChainOutboundEnabled(X) == false` (or `GetTokenConfigByPRC20` failing) and returns an error — reproduced verbatim in `TestPostTxProcessing_WithSyntheticOutboundEvent/outbound_disabled_returns_error` [8](#0-7) .
5. No `OutboundTx`/`PendingOutbounds` entry is created for the user's withdrawal.

**Note on incomplete verification:** I was not able to locate, within the available search iterations, the exact `x/evm`/`ante` wiring that determines whether an error returned from this post-tx-processing hook rolls back the already-executed EVM message (the PRC20 burn) or merely fails to record the outbound while the burn stands committed. This distinguishes "temporary stuck funds requiring rescue" from "permanent unrecoverable loss," and is the critical fact needed to finalize severity. I recommend a Devin session with full repository access to trace `evm_hooks.go`'s registration point in the Cosmos EVM message pipeline to confirm this behavior before treating this as a confirmed high-severity finding.

	ctx context.Context,
	utxId string,
	receipt *evmtypes.MsgEthereumTxResponse,

	outbounds := []*types.OutboundTx{}

	k.Logger().Debug("building outbounds from receipt", "utx_id", utxId, "tx_hash", receipt.Hash, "log_count", len(receipt.Logs))

	for _, lg := range receipt.Logs {
