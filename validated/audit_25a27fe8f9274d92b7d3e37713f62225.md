### Title
Shared (non-deep-copied) `Storage` object between parent/child `Repository` lets reverted nested calls' storage writes leak into committed state pre-hard-fork - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
In `RepositoryImpl.getStorage()`, when `StorageUtils.getEnergyLimitHardFork()` returns `false`, a child `Repository`'s `Storage` object for an address is set to the exact same object reference as the parent's (`storage = parentStorage;`) instead of a deep copy. Because `Storage.put()` mutates the shared `rowCache` map in place, any SSTORE performed inside a nested call permanently mutates the parent's (and root's) storage state immediately, independent of whether the child `Repository`'s cache is ever `commit()`ed — so a REVERTed inner call still leaves its storage writes visible.

### Finding Description
`RepositoryImpl.getStorage(byte[] address)` implements the following logic: [1](#0-0) 

When the hard fork flag is off, `storage = parentStorage` — the child does not get its own `Storage` instance, it gets a reference to the parent's. `Storage.put()` writes directly into `rowCache`, a mutable `HashMap` field of the `Storage` object itself: [2](#0-1) 

Crucially, this mutation happens synchronously at SSTORE-execution time (`RepositoryImpl.putStorageValue` → `getStorageInternal` → `storage.put`), not deferred until `Repository.commit()`: [3](#0-2) 

Normally, TVM isolation relies on each nested-call `Repository` (`deposit = getContractState().newRepositoryChild()` in `Program.callToAddress`) buffering its writes in its own caches, and only propagating them to the parent via `commit()` if the call succeeds; if the call reverts, the child `Repository` object is simply discarded without calling `commit()`, and the parent state should remain untouched. This works correctly for `accountCache`, `codeCache`, `contractCache`, etc., which are per-`Repository` `HashMap`s populated with copied `Value` wrappers. However, for `Storage`, when the hard-fork flag is disabled, the "cache" object handed to the child *is the parent's live `Storage` instance*, not a copy. Any `put()` call therefore corrupts the parent's in-memory storage state directly and irreversibly — discarding the child `Repository` afterward (on revert) does nothing to undo the mutation, because the mutation already happened on the shared object, not on the child's local cache.

The `getEnergyLimitHardFork` gate confirms the intended fix (deep copy) already exists but is fork-gated: [4](#0-3) [5](#0-4) 

Existing project tests explicitly document both behaviors: `testParentChild` (hard fork on) shows correct isolation via `new Storage(parentStorage)` deep copy, while `testParentChildOldVersion` (hard fork off) explicitly asserts `rootRepository.getStorageValue(...)` equals the child's written value **immediately, before `commit()` is called** — i.e., the parent is mutated by the child's un-committed writes: [6](#0-5) 

This is precisely the aliasing bug the question describes: a nested CALL that SSTOREs and then REVERTs will have already mutated the shared `rowCache`, so the outer contract's subsequent SLOAD sees the fabricated value, since the child's `Storage` object was never a separate isolated copy in the first place.

### Impact Explanation
This corresponds to state/accounting corruption (VALUE_CONSERVATION / rollback-atomicity violation): a reverted nested call can still cause persistent, incorrect contract storage state. An attacker-controlled contract could implement a pattern such as calling into itself or another attacker-controlled contract, writing a forged balance/allowance/flag via SSTORE, and then reverting — yet the outer transaction's storage read (SLOAD) or the eventual commit path could observe/propagate the forged value, since the shared `Storage` object was mutated regardless of the revert. This falls into the "asset/accounting corruption" / "unauthorized state change" bounty impact class, since it can be leveraged to fabricate token balances, allowances, or ownership flags in a smart-contract system running on the pre-fork path.

### Likelihood Explanation
This requires only unprivileged capabilities: deploying/calling smart contracts and paying normal transaction fees/energy for a CALL that reverts. The exploit is entirely deterministic and repeatable, requiring no race conditions or privileged roles. The sole precondition is that the chain (or a fork of the chain, since this is an open-source client) is running with `ENERGY_LIMIT_HARD_FORK` (`getEnergyLimitHardFork()`) disabled — i.e., pre-activation of that particular hard fork proposal. On the current mainnet, this hard fork is long activated, so the aliasing path is dead code on production TRON mainnet; however, on any deployment (private chain, testnet, or fork of this repo) where the corresponding hard-fork proposal has not yet been activated, this is fully exploitable by any funded account, at a low fixed cost equal to the energy/bandwidth of two contract calls.

### Recommendation
Remove the fork gate for the `Storage` deep-copy in `RepositoryImpl.getStorage()`, always constructing `storage = new Storage(parentStorage)` for child repositories regardless of `StorageUtils.getEnergyLimitHardFork()`, matching the semantics of all other per-repository caches (`accountCache`, `codeCache`, etc.) which already copy-on-write rather than alias. If backward-compatible replay of pre-fork blocks is required, isolate the legacy behavior to historical block re-execution only, never to new transaction processing.

### Proof of Concept
The existing repository test `StorageTest.testParentChildOldVersion` already demonstrates the aliasing (it is effectively the PoC requested): [7](#0-6) 

A minimal targeted JUnit reproduction:
```java
// Pre-fork state
CommonParameter.setENERGY_LIMIT_HARD_FORK(false);

Repository root = RepositoryImpl.createRoot(StoreFactory.getInstance());
byte[] address = Hex.decode(OWNER_ADDRESS);
DataWord slot = new DataWord("balanceSlot".getBytes());
DataWord originalValue = new DataWord("real_balance".getBytes());
root.putStorageValue(address, slot, originalValue);

// simulate nested CALL that will revert
Repository child = root.newRepositoryChild();
DataWord fakeValue = new DataWord("fake_balance".getBytes());
child.putStorageValue(address, slot, fakeValue); // SSTORE inside inner call

// simulate REVERT: child is discarded, commit() is never invoked
// child = null;

// Outer contract's subsequent SLOAD, expecting the pre-call value
Assert.assertEquals(originalValue, root.getStorageValue(address, slot)); 
// FAILS pre-fork: root now reads fakeValue because Storage object was aliased,
// not deep-copied, so the "reverted" child's write already mutated root's state.
```
With `CommonParameter.setENERGY_LIMIT_HARD_FORK(true)` set instead, the same test passes because `RepositoryImpl.getStorage()` performs `new Storage(parentStorage)`, isolating the child's writes until an explicit `commit()`.

  private Storage getStorageInternal(byte[] address) {
    address = TransactionTrace.convertToTronAddress(address);
    if (getAccount(address) == null) {
      return null;
    }
    Key addressKey = Key.create(address);
    Storage storage;
    if (storageCache.containsKey(addressKey)) {
      storage = storageCache.get(addressKey);
    } else {
      storage = getStorage(address);
      storageCache.put(addressKey, storage);
    }
    return storage;
  }

  public Storage getStorage(byte[] address) {
    Key key = Key.create(address);
    if (storageCache.containsKey(key)) {
      return storageCache.get(key);
    }
    Storage storage;
    if (this.parent != null) {
      Storage parentStorage = parent.getStorage(address);
      if (StorageUtils.getEnergyLimitHardFork()) {
        // deep copy
        storage = new Storage(parentStorage);
      } else {
        storage = parentStorage;
      }
    } else {
      storage = new Storage(address, getStorageRowStore());
    }
