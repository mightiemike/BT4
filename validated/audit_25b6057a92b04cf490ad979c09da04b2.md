Based on my investigation, I found a genuine, self-documented integrity gap in the state/proof verification path, distinct from the mainline consensus-critical `TransactionOutputListWithProofV2::verify` (which does check `state_change_hash`, gas, status, and event roots correctly per `types/src/transaction/mod.rs:2941-3023`).

### Title
`TransactionOutput::ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, allowing divergent state roots to pass replay-verify as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  validates status, gas used, write-set hash (`state_change_hash`), and event root hash against a committed `TransactionInfo`, but explicitly and knowingly omits validation of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually authenticate the Sparse-Merkle/Jellyfish state root at checkpoints.

### Finding Description
The function's own comment documents the gap: [2](#0-1) 
This means that a caller relying on `ensure_match_transaction_info` to confirm that a locally-recomputed `TransactionOutput` matches the authenticated, accumulator-committed `TransactionInfo` at a version will get a green light even if the state-checkpoint root (the field that binds the transaction to the correct global state tree) is wrong. Only `state_change_hash` (the write-set hash) is checked, not `state_checkpoint_hash` (the periodic SMT/JMT root). This function is used by `aptos-move/cli`'s replay tooling (`aptos-move/cli/src/commands.rs:2810-2812`) to gate whether a locally-replayed execution "matches" the archived, authenticated transaction info.

### Impact Explanation
This falls inside the state-integrity gate's category of "authenticated API or state-view output bound to the wrong version, object, or proof context" and "hard-fork-only divergence during commit, replay, restore, or proof verification." If a node's local state-checkpoint computation diverges from the canonically committed one (e.g., due to a JMT/hot-state computation bug, a schema/versioning bug in state checkpoint hashing, or a bug in `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state logic), replay-verify and CLI-based auditing tools built on `ensure_match_transaction_info` would silently report success even though the actual state root differs from the authoritative one. This defeats the very purpose of the checker as a corruption/divergence detector for archival replay and forensic verification of ledger integrity.

### Likelihood Explanation
This is a real, currently-shipped gap (not speculative): the TODO comment itself confirms the checkpoint hash fields are intentionally left unchecked pending the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature. Its likelihood of causing user-visible harm depends on there being a state-root computation bug elsewhere that this checker was supposed to catch — I could not confirm such a co-occurring root-cause bug within the scope of this investigation. Note the mainline consensus commit path (`TransactionOutputListWithProofV2::verify` in `types/src/transaction/mod.rs:2941-3023`, used for real synced/restored data) does not have this specific gap since it doesn't check checkpoint hashes either — checkpoint hashes are only produced periodically and are validated elsewhere in the executor pipeline (`DoStateCheckpoint::run` in `execution/executor/src/chunk_executor/mod.rs:398-413`, which does check `known_state_checkpoints`/`known_position_state_checkpoints` against computed values). So the primary blast radius of this specific gap is the CLI/replay-verify tooling relying on `ensure_match_transaction_info`, which is diagnostic rather than a live consensus/commit gate.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when known) against locally recomputed values before returning `Ok(())`, consistent with the comment's own stated intent, so that replay-verify/CLI tooling cannot report a false-positive match when the authenticated state root has actually diverged.

### Proof of Concept
Not independently demonstrable purely from this snippet — the checker's gap is a code-level fact (see cited lines), but exploiting it requires an actual state-checkpoint-hash computation bug elsewhere that this checker fails to catch, which I could not locate/confirm within the given scope. I flag this with reduced confidence: the direct analog to the external report (a return-value/verification helper that gives false assurance about the "actual" committed value) is textually confirmed, but the full end-to-end "wrong state committed to mainnet" chain requires a second, unconfirmed root-cause bug in the checkpoint-hash generation itself.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
