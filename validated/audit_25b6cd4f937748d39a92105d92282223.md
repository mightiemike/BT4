### Title
Unbounded PRC20 Minting — `LiquidityCap` Is Never Enforced During Inbound Deposits (File: `x/uexecutor/keeper/handler.go`)

### Summary
`TokenConfig.LiquidityCap` is documented as "max supply cap for this token" and required to be set by the admin at registration time, but no code path in `x/uexecutor` ever reads or compares this value against cumulative minted supply before calling `CallPRC20Deposit`. Any unprivileged external user who triggers a valid, honestly-voted inbound (via the normal source-chain deposit flow) can mint PRC20 tokens without any bound, exactly mirroring the external report's root cause of an accounting field existing in the model but never being maintained/enforced in the mint code path.

### Finding Description
`depositPRC20` in `x/uexecutor/keeper/handler.go` fetches the `TokenConfig` via `uregistryKeeper.GetTokenConfig` purely to resolve the PRC20 contract address (`tokenConfig.NativeRepresentation.ContractAddress`) and then calls `k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)` unconditionally. Neither this function nor `CallPRC20Deposit` (`x/uexecutor/keeper/evm.go`) reads `tokenConfig.LiquidityCap`, tracks a running total minted for that token, or rejects a deposit that would push cumulative supply above the configured cap. Every inbound execution path that mints PRC20 (`ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGas*`) funnels through this same `depositPRC20`/`CallPRC20Deposit` helper, so the omission is systemic across all mint-producing inbound flows, not a single call site.

This is structurally identical to the external report: a value meant to bound/track state (`saleSupplyMinted` there, `LiquidityCap` here) is present in the schema and validated as required input, but the mutating operation (minting) never consults or updates any counter that would let the cap be enforced.

### Impact Explanation
Since honest Universal Validators simply relay whatever amount an external-chain gateway event carries, an unprivileged user can deposit funds on the source chain in amounts (or repeated inbounds) that, in aggregate, exceed the `LiquidityCap` the admin configured for that token. Because there is no accounting of cumulative minted PRC20 supply anywhere in `x/uexecutor`, the PRC20 representation of an external asset can be minted without limit, defeating the purpose of the liquidity cap (this exists specifically to bound protocol exposure/backing risk per token). This corrupts PRC20 supply accounting relative to the intended cap invariant and can result in unbacked/over-minted PRC20 tokens circulating on Push Chain — an accounting/asset-representation invariant violation reachable purely through ordinary, honestly-voted user deposits.

### Likelihood Explanation
High. No privileged action or malicious validator/relayer is required — any user who can generate valid deposit events on a supported external chain (the intended, everyday usage of the bridge) can trigger unbounded minting. The only precondition is a `TokenConfig` with a `LiquidityCap` set (which is mandatory for every token per `ValidateBasic`), so this affects all currently configured tokens uniformly.

### Recommendation
Track cumulative minted supply per PRC20/token config (e.g., a `MintedSupply` collection in `x/uexecutor` or `x/uregistry`, keyed by `chain:address`), and check `MintedSupply + amount <= LiquidityCap` before calling `CallPRC20Deposit` in `depositPRC20`. Reject or fail the PCTx (recording `FAILED` status, consistent with other validation failures in this module) when the cap would be exceeded, and increment the counter atomically alongside every successful deposit across all inbound execution paths (`ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGas`, `ExecuteInboundGasAndPayload`).

### Proof of Concept
1. Admin registers a `TokenConfig` for `USDC` on `eip155:11155111` with `liquidity_cap = "1000000000000000000000000"` (1,000,000 tokens at 6 decimals scaled).
2. An external user deposits an amount into the source-chain gateway that is far larger than the configured cap (or issues many smaller deposits that sum above the cap) — this is normal, permissionless bridge usage.
3. Universal Validators honestly observe and vote `MsgVoteInbound` for each deposit; quorum is reached exactly as in the existing test flows (see `test/integration/uexecutor/inbound_synthetic_bridge_test.go`, "multiple inbounds accumulate balances").
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints the full amount to the recipient's UEA every time, with no comparison against `LiquidityCap` at any point.
5. Cumulative minted PRC20 supply for that token now exceeds `LiquidityCap`, with no on-chain record or rejection — confirmable by querying the `TokenConfig.LiquidityCap` value via `x/uregistry` and comparing it against the PRC20 contract's `totalSupply()`, which will exceed the configured cap.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
