### Title
Unbounded per-vote ballot/pending-inbound sweeps cause quadratic gas blowup in inbound voting - (File: `x/uvalidator/keeper/ballot.go`, `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
Every time a universal validator (UV) casts the first vote on a new observation, `CreateBallot` unconditionally performs a full sweep of `ExpireBallotsBeforeHeight` over the entire active-ballot set, and any ballot that expires in that sweep fires a terminal hook that, for inbound ballots, does a second unbounded linear scan over the entire `PendingInbounds` collection to find the matching audit-trail entry. This is the same "pull, nested, unbounded loop on every user-facing transaction" pattern as Renzo's `calculateTVLs`: an attacker who cheaply floods low-value inbound observations on a supported source chain grows both collections, and the per-tx cost of every subsequent `MsgVoteInbound` (and any other first-time ballot vote: outbound, chain-meta, TSS, migration) scales with the size of the attacker-grown backlog rather than being O(1).

### Finding Description
`CreateBallot` calls `k.ExpireBallotsBeforeHeight(ctx, blockHeight)` on every new ballot, i.e. on every first vote for any new observation: [1](#0-0) 

`ExpireBallotsBeforeHeight` has no bound tied to the caller and, per its test coverage, walks/evaluates the active-ballot set to find and expire those past their `BlockHeightExpiry` — this is invoked synchronously inside the hot vote path shared by inbound, outbound, chain-meta, TSS, and migration ballots: [2](#0-1) 

For each ballot that transitions to a terminal state (`MarkBallotExpired`/`MarkBallotFinalized`), a `BallotHooks.AfterBallotTerminal` callback fires: [3](#0-2) [4](#0-3) 

For `INBOUND_TX` ballots, this hook does a full, unbounded `PendingInbounds.Walk` over every currently-tracked pending inbound entry to locate the one variant matching the terminated ballot ID — explicitly because "ballot IDs are one-way canonical digests (not reversible)": [5](#0-4) 

So the effective cost per new vote is: `O(activeBallots)` (expiry sweep) plus, for every ballot expired in that sweep that happens to be an inbound ballot, an additional `O(pendingInbounds)` walk. Both `ActiveBallotIDs` and `PendingInbounds` are populated purely from unprivileged, cheap, externally-observable events: any attacker can submit many trivial deposits/gas-abstraction transactions on a supported EVM/other source chain (e.g. hitting the configured `GatewayMethods` such as `addFunds`), which UVs are obligated to observe and vote on via `VoteInbound`/`VoteOnBallot`: [6](#0-5) 

This mirrors the Renzo `calculateTVLs` bug class exactly: a data structure that grows with unprivileged user activity is fully iterated inside a function invoked on essentially every user-facing transaction, turning a nominally O(1) operation into O(n) (and, across the block, effectively O(n²) as the backlog compounds), with no caching/"push" accounting.

### Impact Explanation
As the attacker grows the number of active ballots and pending inbound entries (by generating many cheap source-chain events observed by UVs), the gas/CPU cost of processing every subsequent `MsgVoteInbound` (or any other first-vote ballot transaction across `x/uexecutor`/`x/utss`) grows proportionally to the size of that backlog. This can degrade validator vote-processing throughput for all users, delay or effectively deny normal deposit/withdrawal finalization (since ballots must reach quorum through this exact codepath), and in the worst case push per-transaction execution costs high enough to exceed practical gas limits for ordinary inbound votes — a denial-of-service condition triggered purely by unprivileged, low-cost source-chain activity, with no validator, admin, or governance action required to create the load (only honest UVs auto-observing and voting as designed).

### Likelihood Explanation
Likelihood is high: creating spam inbound events only requires access to the source chain the way any ordinary depositor would use it (e.g., cheap EVM-chain transactions to the gateway contract), and no threshold/monotonic-growth cap or pagination limits `ExpireBallotsBeforeHeight`'s ballot sweep or `afterInboundBallotTerminal`'s `PendingInbounds.Walk`. Both collections accumulate as fast as UVs can observe and vote, and the sweep/walk run unconditionally on the hot path for every new ballot.

### Recommendation
Replace the two unbounded scans with index-based or amortized approaches:
- Track ballot expiry using a height-indexed collection (e.g., keyed/prefixed by `BlockHeightExpiry`) so `ExpireBallotsBeforeHeight` can bound its work to ballots actually due for expiry rather than scanning the full active set, or move expiry processing to `EndBlock` with a capped batch size instead of doing it synchronously inside every `CreateBallot` call.
- Avoid the reverse lookup of ballot ID → `PendingInbounds` entry via full `Walk`. Store the mapping directly (e.g., key `PendingInbounds` by ballot ID, or maintain an auxiliary `ballotID -> utxKey` index) so `afterInboundBallotTerminal` can do an O(1) lookup instead of an O(n) scan.
- Add explicit caps/rate limits on the number of concurrently active ballots / pending inbound entries per source chain, or require staking/bonding of a minimal value per pending inbound observation to make spam economically costly.

### Proof of Concept
1. An attacker repeatedly triggers cheap deposit/gas-abstraction events on a configured source chain (e.g., calling the `addFunds` gateway method for dust amounts) so that honest UVs create a large number of distinct `INBOUND_TX` ballots via `VoteOnBallot`/`CreateBallot`, each adding an entry to `ActiveBallotIDs` and `PendingInbounds`.
2. As this backlog grows to N ballots/entries, every subsequent `MsgVoteInbound` from a legitimate user's deposit triggers `CreateBallot` → `ExpireBallotsBeforeHeight`, an O(N) scan over `ActiveBallotIDs`.
3. Any ballots found expired in that scan invoke `MarkBallotExpired` → `fireBallotTerminalHook` → `afterInboundBallotTerminal`, each doing a further O(M) `PendingInbounds.Walk` (M = size of `PendingInbounds`).
4. With N and M growing purely from unprivileged attacker-driven source-chain spam, the per-vote gas/CPU cost for ordinary users' deposits grows unbounded, analogous to the Renzo `calculateTVLs` nested-loop DoS.

func (k Keeper) MarkBallotExpired(ctx context.Context, id string) error {
	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as expired",
		"ballot_id", id,
		"expiry_height", ballot.BlockHeightExpiry,
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.ExpiredBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = types.BallotStatus_BALLOT_STATUS_EXPIRED
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, types.BallotStatus_BALLOT_STATUS_EXPIRED)
	return nil
}

// fireBallotTerminalHook invokes the registered BallotHooks (if any) and
// log-swallows any error. Terminal transitions must never be blocked by
// secondary-index side-effect failure.
func (k Keeper) fireBallotTerminalHook(
	ctx context.Context,
	ballotID string,
	ballotType types.BallotObservationType,
	status types.BallotStatus,
) {
	if k.ballotHooks == nil {
		return
	}
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	if err := k.ballotHooks.AfterBallotTerminal(sdkCtx, ballotID, ballotType, status); err != nil {
		k.Logger().Warn("ballot terminal hook returned error",
			"ballot_id", ballotID,
			"ballot_type", ballotType.String(),
			"status", status.String(),
			"err", err.Error(),
		)
	}
}

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
