### Title
Panic while holding the `Scheduler::commit_index` mutex during concurrent commit poisons the lock, permanently blocking block building - (File: `crates/blockifier/src/concurrency/scheduler.rs`, `crates/blockifier/src/concurrency/worker_logic.rs`)

### Summary
`WorkerExecutor::commit_while_possible` acquires the `Scheduler::commit_index` mutex via `try_enter_commit_phase()` and holds the returned `TransactionCommitter` guard across the whole commit loop, including calls into `commit_tx`, which itself can `panic!` (bouncer failure) or hits `unwrap_or_else(|_| panic!(...))`. A panic while this guard is alive poisons the `commit_index` `Mutex`, and other code paths on the same mutex (`get_n_committed_txs`, `try_enter_commit_phase`) then panic unconditionally on every subsequent access, similar in effect to the "lock never released after failure" deadlock class described in the report. [1](#0-0) 

### Finding Description
`Scheduler::try_enter_commit_phase` takes `commit_index.try_lock()` and returns a `TransactionCommitter` holding the `MutexGuard` for the duration of the commit loop: [2](#0-1) 

`commit_while_possible` keeps this guard alive while repeatedly calling `self.commit_tx(tx_index)`: [1](#0-0) 

Inside `commit_tx`, several paths can panic while the commit-index lock is still held by the caller:
- `self.bouncer.lock().expect("Bouncer lock failed.")` panics if the bouncer mutex is itself poisoned from an earlier panic.
- an explicit `panic!("Bouncer update failed. {error:?}: {error}")` for any `TransactionExecutorError` other than `BlockFull`. [3](#0-2) 

A panic occurring anywhere in this call chain unwinds through `commit_while_possible` while the `commit_index` `MutexGuard` is on the stack. Rust drops the guard during unwinding but marks the underlying `std::sync::Mutex` as poisoned. Every later caller of that same mutex then fails:
- `Scheduler::try_enter_commit_phase` explicitly `panic!`s on `TryLockError::Poisoned`.
- `Scheduler::get_n_committed_txs` calls `.lock().unwrap()`, which panics on a poisoned mutex. [4](#0-3) 

`get_n_committed_txs` is polled in a tight loop by `Scheduler::wait_for_completion`, which is invoked by every call to `WorkerPool::run_and_wait` for concurrent block building: [5](#0-4) [6](#0-5) 

The worker pool does catch per-thread panics and marks `a_thread_panicked`, halting the scheduler and re-panicking on the caller (`check_panic`), so the immediate effect is a controlled abort of the current block's concurrent execution rather than a silent hang. However, because the poisoned `commit_index` `Mutex` is embedded in the `Scheduler`, which lives inside the `WorkerExecutor` for the current chunk/block, this is functionally the same "lock stuck due to unhandled failure path" defect as the report: once poisoned, all subsequent lock acquisitions on `commit_index` for that chunk unconditionally fail, and there is no code path that clears/resets the poison or extracts the state safely before the whole worker set aborts. [7](#0-6) 

### Impact Explanation
If reached, this converts what should be a recoverable per-transaction execution/bouncer error into an unrecoverable panic that propagates through `WorkerPool::run_and_wait`/`check_panic`, aborting concurrent execution of the entire block/chunk being built. Since `WorkerExecutor`/`Scheduler` instances are per block-building call (not globally shared across blocks), the poisoning is scoped to that invocation, but it still causes the sequencer's block builder to fail closing out the affected block, which is a liveness/DoS impact on block production for that attempt.

### Likelihood Explanation
Reaching the panic requires either (a) a non-`BlockFull` `TransactionExecutorError` surfacing from `Bouncer::try_update`, or (b) the bouncer mutex already being poisoned by a prior panic. I was not able to fully confirm, within the available tool budget, whether an unprivileged transaction sender can deterministically trigger the non-`BlockFull` branch of `Bouncer::try_update` (the exact error variants and their trigger conditions in `crates/blockifier/src/bouncer.rs` were not fully inspected before the iteration limit). Without that confirmation, the likelihood that a single unprivileged transaction can reliably reach this panic path is uncertain.

### Recommendation
- Avoid holding the `commit_index` guard across code that can panic on attacker-influenced input; convert panics in `commit_tx`'s bouncer-error handling into propagated `Result`s instead of `panic!`.
- Consider using `parking_lot::Mutex` (non-poisoning) for `commit_index`/`bouncer`, or explicitly recover from `PoisonError` (`err.into_inner()`) instead of `panic!`/`unwrap()` on every access path.
- Ensure `WorkerPool`'s panic recovery path fully tears down and reconstructs the `Scheduler`/`WorkerExecutor` state rather than relying on poisoning propagation for correctness.

### Proof of Concept
Could not be fully constructed within the current investigation: it would require confirming a concrete `TransactionExecutorError` (other than `BlockFull`) reachable from `Bouncer::try_update` via an unprivileged transaction's resource usage, which triggers the `panic!("Bouncer update failed...")` while `commit_while_possible` holds `try_enter_commit_phase()`'s guard, and then observing subsequent `get_n_committed_txs`/`try_enter_commit_phase` calls panic on `PoisonError`. This last step is directly supported by the cited code, but the initial trigger condition needs further verification against `crates/blockifier/src/bouncer.rs`, which was not fully reviewed due to the iteration limit.

    /// Tries to takes the lock on the commit index. Returns a `TransactionCommitter` if successful,
    /// or None if the lock is already taken.
    pub fn try_enter_commit_phase(&self) -> Option<TransactionCommitter<'_>> {
        match self.commit_index.try_lock() {
            Ok(guard) => Some(TransactionCommitter::new(self, guard)),
            Err(TryLockError::WouldBlock) => None,
            Err(TryLockError::Poisoned(error)) => {
                panic!("Commit index is poisoned. Data: {:?}.", *error.get_ref())
            }
        }
    }

    pub fn get_n_committed_txs(&self) -> usize {
        *self.commit_index.lock().unwrap()
    }

    /// Sleeps until the scheduler is done or the requested number of committed transactions is
    /// reached.
    pub fn wait_for_completion(&self, target_n_txs: usize) {
        // TODO(lior): Consider splitting n_committed_txs from the commit lock, so that the
        //   following line will not wait for the commit lock and vice versa.
        //   Note that such a change requires updating n_committed_txs only after the tx is
        //   finalized (currently it's updated before the tx is really committed).
        while !(self.done() || self.get_n_committed_txs() >= target_n_txs) {
            std::thread::sleep(std::time::Duration::from_micros(1));
        }

        // Lock and release the commit index to ensure that no commit phase is in progress.
        // Future calls to `try_commit` (which is under the same lock) will exit immediately since
        // the done marker is set.
        drop(self.commit_index.lock());
    }
