## Title
Floating-point truncation in `UnDelegateResourceActuator` resource-usage transfer allows accounting drift that benefits users at the network's expense - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The Umee report describes a class of bug where a fixed-precision/floating computation that is truncated to an integer produces small, systematic rounding errors that favor the caller over the protocol, and where those errors can be repeatedly harvested through ordinary user transactions. In java-tron, `UnDelegateResourceActuator.execute()` reproduces the same bug class: it computes how much "usage" (already-consumed bandwidth/energy) must be transferred from the receiver back to the delegating owner when a delegation is revoked, using `double` arithmetic and a final narrowing cast to `long`, which truncates towards zero on every un-delegate call.

### Finding Description
In `execute()`, the amount of resource *usage* to move from receiver to owner is computed with double-precision floating point and cast to `long`: [1](#0-0) 

and similarly for ENERGY: [2](#0-1) 

`transferUsage` is derived from `receiverCapsule.getNetUsage() * (unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth())`, a proportional (pro-rata) split identical in shape to the Umee `AdjustedBorrow * InterestScalar` computation flagged in the report — a ratio multiplied against an integer amount, truncated via `(long)` cast rather than routed through an exact/ceiling integer division. The truncation direction (`(long)` cast = floor/truncate-toward-zero for positive values) is not chosen to consistently favor the protocol; it simply drops the fractional remainder of `transferUsage`.

This mirrors the reported pattern precisely: the receiver's `netUsage`/`energyUsage` is reduced by the (possibly under-counted) `transferUsage` value while the corresponding, larger amount conceptually "owed" is not reconciled anywhere else — the fractional remainder silently vanishes from both the receiver's and owner's usage ledgers. Because `NetUsage`/`EnergyUsage` values directly gate how much free bandwidth/energy an account can additionally consume before paying TRX, a systematic under-transfer here reduces the receiver's recorded consumption more precisely than it should have, an effect analogous to the "user repays slightly less than borrowed" effect from the Umee report, except the asset here is metered network resource rather than a fungible token.

Reachability: `UnDelegateResourceActuator` is invoked directly from an ordinary, unprivileged `UnDelegateResourceContract` broadcast transaction — no special permission is required beyond owning a delegation relationship, matching the "broadcast transaction" reachability criterion.

### Impact Explanation
Any account that repeatedly delegates and un-delegates resources to itself/associates (a normal, permissionless workflow) can accumulate small discrepancies in tracked `NetUsage`/`EnergyUsage` on both sides of the delegation. Because usage values feed directly into how much bandwidth/energy an account may consume for free (a directly monetizable resource on TRON, since consuming it in excess triggers TRX burn), repeated exploitation across many delegate/undelegate cycles could let an attacker accumulate free resource capacity beyond what the network's economic model intends — an analog to the Umee "borrow/repay in the same transaction, repeat" drain scenario, but manifesting as resource-accounting drift rather than direct token loss. At scale (Exploit Scenario 2 in the report), the aggregate effect across many users/transactions is a slow corruption of the network's resource-weight/usage accounting used for global bandwidth/energy limit calculation elsewhere in `ResourceProcessor`.

### Likelihood Explanation
Likelihood is moderate-to-low: exploiting this requires precise control over `unDelegateBalance`, `netUsage`/`energyUsage`, and `AllFrozenBalance` ratios to consistently produce non-zero truncation remainders, and the code base elsewhere (`ResourceProcessor`, `RepositoryImpl`) has already been extensively hardened with `BigInteger`-based ceiling-division helpers (`hardenCalculation()`/`hardenResourceCalculation()`) guarded by chain parameters — showing the project is aware of and has fixed similar patterns elsewhere, but `UnDelegateResourceActuator`'s `transferUsage`/`unDelegateMaxUsage` computation was not migrated to that hardened path.

### Recommendation
- Replace the `double`-based `transferUsage`/`unDelegateMaxUsage` computations in `UnDelegateResourceActuator.execute()` with exact integer arithmetic (e.g., `BigInteger` multiply-then-divide, as already done via `hardenCalculation()` in `ResourceProcessor`/`RepositoryImpl`), and choose the rounding direction that favors the network/receiver's recorded usage rather than the initiating owner.
- Add invariant/regression tests asserting that repeated delegate/un-delegate cycles do not change total tracked `NetUsage + EnergyUsage` across owner and receiver beyond the expected value.
- Apply the same hardened, `BigInteger`-based computation path used by `calculateGlobalLimitV2`/`getUsage`/`divideCeilExact` uniformly across all resource-transfer code paths, closing any remaining `double`-cast usage-transfer calculations.

### Proof of Concept
A concrete PoC requires running a local java-tron node and issuing a sequence of `DelegateResourceContract`/`UnDelegateResourceContract` transactions with carefully chosen `balance` values (non-exact multiples of `receiver.getAllFrozenBalanceForBandwidth()`) to force `(double) unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth()` to produce a non-terminating fraction, then asserting via `getAccountResource` that `owner.NetUsage + receiver.NetUsage` after repeated cycles is not conserved relative to the pre-cycle total, analogous to the `TestTruncationBug` test shown in the report for Umee's `RepayAsset`/`BorrowAsset`. This would need to be executed in a full node/test harness (see `framework/src/test/java/org/tron/core/actuator/UnDelegateResourceActuatorTest.java` for existing test scaffolding to extend) rather than purely via static analysis.
