### Title
Unbounded `prefixQuery` in `DelegatedResourceAccountIndexStore.getWithPrefix` allows attacker-controlled O(n) disk scan per free HTTP GET request - (`framework/src/main/java/org/tron/core/services/http/GetDelegatedResourceAccountIndexServlet.java`)

### Finding Description
`GetDelegatedResourceAccountIndexServlet.fillResponse` (and its V2 counterpart, `GetDelegatedResourceAccountIndexV2Servlet`) call `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2`, which invoke `DelegatedResourceAccountIndexStore.getIndex`/`getV2Index`. [1](#0-0)  These delegate to the private helper `getWithPrefix`, which runs `this.prefixQuery(key).values()` twice (once for the FROM/V2_FROM prefix, once for the TO/V2_TO prefix) with no limit, offset, or pagination, then sorts and materializes the full result list into memory. [2](#0-1) 

The number of entries scanned by `prefixQuery(FROM_PREFIX/TO_PREFIX + address)` (or the V2 equivalents) is exactly the number of distinct delegation relationships (`from -> to` and `to -> from` pairs) ever recorded for that address, each of which is written by `DelegateResourceActuator.delegateResource`/`DelegateResourceProcessor` via `delegatedResourceAccountIndexStore.delegateV2(...)`. [3](#0-2)  `DelegateResourceActuator.validate()` imposes no cap on the number of distinct receiver addresses an owner can delegate to — it only checks minimum balance (`>= 1 TRX`), receiver account existence, and receiver not being a contract. [4](#0-3)  An attacker can therefore grow the index for their own address to arbitrary size N by issuing N cheap `DelegateResourceContract` transactions to N distinct (pre-activated) receiver addresses, each only costing the minimum 1 TRX delegation plus normal transaction bandwidth/energy — there is no per-entry or per-query fee tied to index size.

Once N is large, any unprivileged caller can hit the public HTTP endpoint `/wallet/getdelegatedresourceaccountindex` (or V2 variant) with that address, and each call triggers an O(N) full key-prefix disk scan and in-memory sort inside `getWithPrefix`. The only protection is `RateLimiterServlet`, which enforces a QPS-based rate limit per endpoint/IP, not a cost- or result-size-based limit. [5](#0-4)  Thus the per-call cost is unbounded and not reflected in any fee — QPS throttling caps request *frequency* but not the *cost per allowed request*, so a small number of allowed requests against a large N can still consume disproportionate CPU/disk I/O on the node.

### Impact Explanation
Repeated queries against an attacker-inflated address index cause disproportionate CPU and disk I/O consumption per HTTP GET on full/solidity/PBFT nodes exposing this API (`FullNodeHttpApiService`, `SolidityNodeHttpApiService`, `HttpApiOnPBFTService` all wire up `GetDelegatedResourceAccountIndexServlet`/V2). This is a resource-exhaustion / degraded-availability concern for the node's public HTTP API rather than a fund-theft or consensus-divergence issue — it does not corrupt state, bypass authorization, or enable double-settlement.

### Likelihood Explanation
Feasible but requires nontrivial attacker investment: the attacker must fund and activate N distinct receiver accounts and issue N `DelegateResourceContract` transactions (each requiring >= 1 TRX frozen balance available for delegation), so growing N to a scale that meaningfully slows disk I/O requires real, repeatable but non-negligible on-chain resource expenditure by the attacker. It is not "free" in the sense of costing nothing, but the read-side cost is not fee-metered at all, so cost asymmetry exists between one-time index inflation and unlimited subsequent free reads by any party (not just the attacker) against that address.

### Recommendation
Bound `getWithPrefix` results (e.g., cap max returned/scanned entries, or require a paginated/limit+offset API), and/or track and expose an index-size counter that lets validate() in `DelegateResourceActuator` reject delegation once an owner's distinct-receiver count exceeds a configurable maximum, similar to protections already used elsewhere (e.g., `GetCanDelegatedMaxSizeServlet` for balance-related limits). Also consider adding a cost/latency-aware rate limiter for this endpoint instead of pure QPS throttling.

```java
// framework/src/test/java/org/tron/core/db/DelegatedResourceAccountIndexStoreTest.java
@Test
public void testGetWithPrefixScalesLinearly() {
  byte[] owner = "benchOwner".getBytes();
  int[] sizes = {100, 1000, 10000};
  long[] elapsed = new long[sizes.length];
  int prev = 0;
  for (int s = 0; s < sizes.length; s++) {
    for (int i = prev; i < sizes[s]; i++) {
      byte[] receiver = ("receiver" + i).getBytes();
      delegatedResourceAccountIndexStore.delegateV2(owner, receiver, i + 1L);
    }
    prev = sizes[s];
    long start = System.nanoTime();
    delegatedResourceAccountIndexStore.getV2Index(owner);
    elapsed[s] = System.nanoTime() - start;
  }
  // Expectation for a bounded/paginated implementation: latency growth should be
  // sub-linear or capped. Currently this assertion FAILS because getWithPrefix
  // performs an unbounded prefixQuery whose cost scales ~linearly with N.
  Assert.assertTrue("Latency should not scale linearly with index size",
      elapsed[2] < elapsed[0] * 20); // expect much less than 100x growth for 100x data
}
```
Run this alongside repeated HTTP calls to `GetDelegatedResourceAccountIndexV2Servlet` against the same `owner` address to observe per-request latency/CPU growth as N increases, confirming the query cost is unbounded and not fee-metered.

```java
  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
```
