### Title
`ensure_match_transaction_info` silently skips state-checkpoint hash verification, allowing replay/verify tooling to accept a wrong state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative check that a (possibly externally-supplied) `TransactionOutput` matches the accumulator-proven `TransactionInfo` for a given version. It validates status, gas, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents as unresolved.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks `status`, `gas_used`, the write-set hash, and the event-root hash against the `TransactionInfo`, but its own trailing comment admits the checkpoint hashes are never compared: [2](#0-1) 

`TransactionInfo` carries `state_checkpoint_hash`, and for V1, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` [3](#0-2) . These fields represent Jellyfish-Merkle / hot-state / position-state roots that are supposed to be authenticated by the accumulator (via `TransactionInfo::hash()` feeding the `TransactionAccumulator`). Yet the one function whose entire purpose is to confirm a `TransactionOutput` (the actual computed execution result) matches its accompanying, proof-verified `TransactionInfo` does not check these root hashes at all.

This function is used by exactly the surfaces named in scope — replay and restore/verification tooling — including `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. Because these are the tools relied upon to detect execution/state divergence before a hard fork or to validate synced/replayed data, a mismatch in the state-checkpoint hash (JMT root, hot-state root, or the newer "position state" root referenced by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) between the locally re-executed output and the ledger-committed `TransactionInfo` will go completely undetected as long as the write-set bytes, events, gas, and status happen to match.

This is structurally the same bug class as the seed report: an incomplete/omitted term in an equality check meant to bind a derived value to an authoritative reference (there, sqrtPrice scaling ignoring decimal delta; here, transaction-output/transaction-info matching ignoring checkpoint-hash fields), leading to an authenticated value (the state-checkpoint root) being accepted without actually being checked against the proof-bound reference.

### Impact Explanation
`ensure_match_transaction_info` is the last-line sanity gate used by chunk-based replay/verification and debugging paths that ingest `TransactionOutput`s (either self-computed or from external chunks) alongside proof-verified `TransactionInfo`s. Because it omits verification of `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, these tools can report "match"/success even when the state root actually produced by execution or application diverges from the state root committed to the accumulator. This directly undermines a proof-and-storage-pivot invariant required by the gate: "VM outputs, transaction infos, events, and write sets must survive executor-to-storage handoff unchanged" and "Authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object." A silent divergence here is precisely a hard-fork-relevant integrity failure: replay-verify (`replay_on_archive`) and debugger flows exist specifically to catch state-root divergence, and this gap defeats that purpose for state/hot-state/position-state roots.

### Likelihood Explanation
Medium. The bug does not require an attacker; it requires only that write-set bytes/events/gas/status compute identically while the derived state checkpoint root differs — which is realistic wherever state-root computation is more complex/newer than write-set serialization, e.g. the hot-state root or "trading native" position-state root paths gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in `types/src/on_chain_config/aptos_features.rs`. The comment in the source itself flags this as an open, acknowledged risk ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), indicating the gap is real and currently latent rather than purely theoretical.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally computed state-checkpoint hash(es) (state root, hot-state root, and position-state root when applicable) against the corresponding fields on `txn_info`, erroring out on any mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any hot-state feature is enabled on mainnet. At minimum, gate replay-verify tooling (`db-tool replay_on_archive`, `aptos-debugger`) on this stricter check so a state-root divergence is never silently reported as a successful replay.

### Proof of Concept
Conceptual repro (cannot fully execute without a live node/build):
1. Construct a `TransactionOutput` whose `write_set`, `events`, `gas_used`, and `status` exactly match a given `TransactionInfo`, but whose actual post-execution state (fed separately into state-checkpoint hash computation, e.g. hot-state or position-state Merkle root) differs from `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`.
2. Call `TransactionOutput::ensure_match_transaction_info(version, &txn_info, None, None)` as done in `execution/executor/src/chunk_executor/mod.rs` or `storage/db-tool/src/replay_on_archive.rs`.
3. Observe the call returns `Ok(())` despite the state-checkpoint hash mismatch, because the function body (lines 2139-2203) never reads or compares `txn_info.state_checkpoint_hash()` (or the V1 hot/position variants) against any independently computed root.

Given the limits of static analysis, I was not able to fully trace every call site to confirm whether a *separate* comparison of the computed state root against `txn_info.state_checkpoint_hash()` exists elsewhere in the chunk-executor commit path (which could partially mitigate this for state sync specifically, though not for the debugger/db-tool replay paths). This should be verified with a live build/test run before treating the impact as unconditionally exploitable end-to-end in the committing path, though the gap in the dedicated matching function itself is confirmed by direct code reading.
