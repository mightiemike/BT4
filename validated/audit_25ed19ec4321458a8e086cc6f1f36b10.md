## Title
Replay-verify integrity check silently ignores state-checkpoint root hashes, allowing state divergence to go undetected - (`types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay/verification tooling to confirm that a freshly re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain (analogous in spirit to the report's "not all payload fields are covered" bug: a validation routine that is supposed to bind an artifact to a signed/committed record omits some of the fields that make up that record). It checks status, gas used, write-set hash (`state_change_hash`) and event root hash, but never checks `state_checkpoint_hash` (the Sparse-Merkle-Tree state root) nor the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` validates only a subset of the fields that constitute the authenticated `TransactionInfo`: [2](#0-1) 

It explicitly acknowledges the gap in a `TODO` comment: [3](#0-2) 

`TransactionInfoV0`/`V1` carry a `state_checkpoint_hash` (and V1 also `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) that is the Merkle root of world state at the end of the transaction: [4](#0-3) [5](#0-4) 

None of these state-root fields are compared to the recomputed value from replaying the transaction against the state, unlike the write-set hash and event-root hash which are checked. This function is the actual correctness gate used by two integrity-critical tools:

1. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` — the primary "replay-verify" tool that re-executes historical transactions with the current VM against an archived DB and is meant to catch execution non-determinism, framework-upgrade regressions, or state-application bugs before/around a network upgrade. [6](#0-5) 

2. `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches` — used by `aptos move` CLI debugging commands to detect execution result mismatches against on-chain committed info. [7](#0-6) 

Because the comparator never checks the state-checkpoint (state-root) hash, a transaction whose write set and events happen to match but whose *effect on the state tree* diverges from what is committed on-chain (e.g., due to a subtle VM/state-application bug, a hot-state or position-state divergence, or any nondeterminism that still produces byte-identical write-set/events yet a different resulting SMT root due to prior-state ordering issues) will be reported by these tools as a successful, matching replay.

### Impact Explanation
This breaks the "authenticated state-root/proof-binding must be preserved" invariant during the replay/verification path: the tool that operators and the Aptos team rely on to certify that re-execution matches the authenticated ledger silently accepts a divergent state root as if it matched. This is precisely the class of "hard-fork-only divergence during commit, replay, restore, or proof verification" impact called out as in-scope, since `replay_on_archive` is the tool used to validate correctness of execution across upgrades/hard-forks, and a false "PASS" here can mask a genuine state-root divergence bug until it manifests as an actual mainnet consensus/state-sync failure.

### Likelihood Explanation
The gap is deterministic and always present (not a race or edge case): the check simply never touches `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so any real state divergence bug whose write-set/events serialize identically but whose end-state SMT differs will always slip past this verification silently. The code's own inline comment confirms the authors are aware this exact scenario ("replay-verify tooling... can report a successful replay even when the authenticated position state root diverges from local execution") is currently possible.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally recomputed state-checkpoint hash(es) (`state_checkpoint_hash`, and, when `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state is enabled, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against the corresponding fields on `txn_info`, returning an error on mismatch just as is already done for `state_change_hash` and `event_root_hash`. Until this is done, `replay_on_archive`/`print_mismatches` should not be treated as a complete state-integrity check.

### Proof of Concept
Not applicable in the traditional PoC sense (this is a verification-completeness gap in tooling logic rather than an exploitable transaction). The gap can be demonstrated by constructing a `TransactionOutput` whose `write_set`/`events` hash to the same values as an `expected_txn_info`, but whose true post-execution state root differs (e.g., by feeding a `TransactionInfo` with an arbitrary/incorrect `state_checkpoint_hash`) and observing that `ensure_match_transaction_info` at [1](#0-0)  returns `Ok(())` despite the state-root mismatch, which `replay_on_archive.rs`'s `execute_and_verify` would then treat as a passing replay.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
