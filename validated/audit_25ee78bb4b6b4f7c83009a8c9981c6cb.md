### Title
Unbounded `VotesStore` full-table scan reachable via unauthenticated `getPaginatedNowWitnessList` API leads to node resource-exhaustion DoS - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
The C4 finding describes an `EnumerableMap` of curator share balances that is never pruned of zero-balance entries, causing full enumeration in a rewards-distribution function to eventually exceed the block gas limit and permanently block reward payouts. The closest reachable analog in java-tron is `Wallet.getPaginatedNowWitnessList`, which performs a **full, unbounded iteration of the entire `VotesStore`** on every call to compute real-time vote deltas, and `VotesStore` entries are only pruned once per maintenance cycle. Since any account can cast a vote (creating/overwriting a `VotesCapsule` entry keyed by voter address) and this API is exposed via gRPC/HTTP to anonymous callers, an attacker can cheaply grow the number of distinct voter entries within an epoch and then repeatedly invoke this read API to force expensive full-store scans on every full node, degrading node performance/availability — a DoS analogous to the unbounded-enumeration root cause in the original report.

### Finding Description
`Wallet.getPaginatedNowWitnessList` builds the "real-time" witness ranking by first fetching the full witness list and then calling a private helper that iterates the **entire** `VotesStore` to compute per-witness vote deltas for the current, unfinished epoch: [1](#0-0) 

```java
VotesStore votesStore = chainBaseManager.getVotesStore();
// Count the vote changes for each witness in the current epoch, it is maybe negative.
Map<ByteString, Long> countWitness = countVote(votesStore);
```

The `countVote` helper walks every key/value pair in `VotesStore` with no pagination, limit, or early exit: [2](#0-1) 

This is structurally the same anti-pattern as the reported bug: a mapping/store that is expected to be "small" in practice is fully enumerated inside a function reachable by unprivileged actors, and the store's size is driven by user-controlled write activity (here, `VoteWitnessContract` transactions) that is not deleted until the next `doMaintenance()` cycle: [3](#0-2) 

Note that `votesStore.delete(next.getKey())` only happens once per maintenance epoch (roughly every 6 hours by default), meaning `VotesStore` can accumulate one entry per distinct voter address that cast a vote during the epoch, and this size is fully attacker-controllable because voting is cheap (bandwidth/energy cost only, and any number of fresh accounts can vote, exactly as the PoC in the original report used thousands of throwaway addresses to bloat a similarly-unbounded structure).

The `getPaginatedNowWitnessList` endpoint is exposed to anonymous clients through multiple unauthenticated interfaces (gRPC `RpcApiService`, HTTP servlet `GetPaginatedNowWitnessListServlet`, and their solidity-node equivalents): [4](#0-3) [5](#0-4) 

Each invocation of this API triggers a fresh `O(N)` scan of `VotesStore` where `N` is the number of distinct voters in the current epoch — there is no caching of `countVote` results across calls.

### Impact Explanation
Unlike the original Solidity bug (which permanently blocks reward distribution once the map is bloated), this analog's primary impact is availability/performance degradation of full nodes and solidity nodes: attacker-inflated `VotesStore` size combined with repeated calls to `getPaginatedNowWitnessList` forces the node to repeatedly execute large iterations and comparisons (`countWitness.getOrDefault`, `Maps.newHashMap()` allocation, `WitnessStore.sortWitnesses`) on every request, consuming CPU/memory and potentially starving other RPC/API consumers or slowing block processing threads that share the same JVM. Because the endpoint is unauthenticated and rate-limiting is not enforced at the application layer, this can be leveraged as a low-cost, repeatable DoS vector against public RPC endpoints. It does not corrupt consensus state or funds, so severity is lower than the original High-severity fund-freezing bug, but it is a legitimate RPC-API DoS analog.

### Likelihood Explanation
Likelihood is moderate-to-high: casting a vote via `VoteWitnessContract` is a normal, low-cost, unprivileged operation available to any funded account, and creating many low-balance accounts to vote (as demonstrated in the original report's PoC methodology) is cheap on TRON. The `getPaginatedNowWitnessList` API requires no authentication and no rate limiting is visible in the reviewed request path, so an attacker can trivially script repeated calls once `VotesStore` has been inflated.

### Recommendation
- Cap the amount of work `getPaginatedNowWitnessList`/`countVote` can perform per call, e.g., by maintaining an incrementally-updated vote-delta cache (updated only when a new vote transaction is processed) instead of scanning the full `VotesStore` on every read request.
- Add rate limiting / pagination cost accounting to the HTTP and gRPC `getPaginatedNowWitnessList` handlers.
- Consider bounding `VotesStore` growth per epoch (e.g., only counting the top-N active voters, or requiring minimum stake to count) so the underlying scan cost cannot be inflated by many low-value voter accounts.

### Proof of Concept
1. Using many freshly funded low-balance accounts, submit `VoteWitnessContract` transactions across the network so that `VotesStore` accumulates a very large number of distinct voter entries within a single maintenance epoch (mirrors the original report's technique of using ~4000 throwaway addresses).
2. Before the next maintenance cycle clears `VotesStore` (`MaintenanceManager.doMaintenance()` → `countVote()` → `votesStore.delete(...)`), repeatedly call the public `getPaginatedNowWitnessList` gRPC/HTTP endpoint.
3. Observe that each call performs a full iteration over the inflated `VotesStore` (`Wallet.countVote`), and measure increasing latency/CPU usage on the target full node as the store size grows, demonstrating a repeatable, low-cost DoS against the read path.

*Note:* I was unable to directly inspect the full contents of `VoteWitnessActuator.java`, `GetPaginatedNowWitnessListServlet.java`, and `VotesStore.java` in this session due to a tool error on the final iteration, so the exact vote-key structure and any existing size/rate limits in those files could not be fully verified. The conclusion above is based on the `Wallet.java` and `MaintenanceManager.java` code that was successfully retrieved; a full Devin session with file access would be needed to confirm whether any undocumented safeguards already exist in those unread files.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
