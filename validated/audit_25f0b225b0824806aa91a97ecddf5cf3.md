I found a concrete analog in the Starknet OS Cairo implementation of the `replace_class` syscall, where the OS is missing a declared-class check that the equivalent blockifier (Rust) implementation enforces.

### Title
Missing declared-class validation in Starknet OS `execute_replace_class` allows state divergence from Blockifier - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
Any contract invoked by an unprivileged transaction sender can call the `replace_class` syscall with an arbitrary, undeclared `class_hash`. In the Starknet OS's Cairo re-execution path, this call is accepted unconditionally — the code contains an explicit `TODO` marking the missing check — whereas the Rust blockifier used for live block building/execution rejects the same call with an `UndeclaredClassHash`/"is not declared" error.

### Finding Description
The OS's `execute_replace_class` function reads the requested `class_hash` from the syscall request and immediately writes it into `contract_state_changes` without verifying that a contract class with that hash has ever been declared: [1](#0-0) 

The comment on line 902 explicitly documents the gap: "TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash." [2](#0-1) 

By contrast, the blockifier's `replace_class` syscall handler (used for gateway validation, mempool admission checks, and actual block execution) explicitly reads the compiled class first, causing the call to fail if the class hash is undeclared: [3](#0-2) 

This is confirmed by the blockifier's own syscall test suite, which asserts that `replace_class` with an undeclared class hash fails with an "is not declared" error: [4](#0-3) [5](#0-4) 

`replace_class` is a standard, unprivileged syscall reachable from any contract's `__execute__` entry point via ordinary `INVOKE` transactions — no special caller permission is required at the protocol level: [6](#0-5) 

### Impact Explanation
The Starknet OS (SNOS) re-executes each block to prove the correctness of the state transition that the sequencer/blockifier already committed. If a block ever contains an execution path that depends on `replace_class` behaving consistently between the blockifier and the OS (e.g., a transaction whose validity/output depends on whether `replace_class` reverts for an undeclared class hash), the missing check causes the OS's computed contract-state changes/state diff and block output to diverge from what the blockifier produced and committed. This is a correctness/soundness bug in the state-transition function used for proof generation: it can lead to the OS accepting or computing a different resulting state (e.g., setting a contract's class hash in the trace to a value that was never validated as declared) than what the sequencer actually committed, i.e., honest-node/prover divergence and a wrong proved state transition for that class of transaction.

### Likelihood Explanation
The `replace_class` syscall is reachable by any unprivileged account issuing a standard `INVOKE` transaction against any contract exposing a replace-class code path (a very common contract pattern, e.g., proxy/upgradeable contracts). No special privileges, keys, or ordering assumptions are required — the caller only needs to submit a syscall request with an arbitrary `class_hash` value.

### Recommendation
Add a declared-class-hash existence check to `execute_replace_class` in `syscall_impls.cairo` (and the corresponding `deprecated_execute_syscalls.cairo` variant, which has the same pattern for older Cairo0-only contracts) equivalent to the blockifier's `get_compiled_class` lookup, so the OS's `replace_class` behavior matches the blockifier's and reverts on an undeclared class hash.

### Proof of Concept
1. Deploy a Cairo1 contract exposing `test_replace_class(class_hash)` which calls `replace_class_syscall(class_hash)`, as in `cairo_steps_test_contract.cairo`. [6](#0-5) 
2. Submit an `INVOKE` transaction calling `test_replace_class` with an arbitrary, never-declared `class_hash`.
3. In the blockifier (used for gateway validation and block building), this call reverts with an `UndeclaredClassHash`/"is not declared" error, as verified in `undeclared_class_hash` test: [4](#0-3) 
4. When the Starknet OS Cairo program re-executes the same transaction trace for proving, `execute_replace_class` performs no such check and unconditionally updates `contract_state_changes` with the undeclared class hash, per lines 900-920 of `syscall_impls.cairo` — a behavioral mismatch from the blockifier that a background engineer should confirm end-to-end by running an SNOS flow test with an undeclared `replace_class` call and comparing state diffs.

Note: I was unable to execute the SNOS flow test harness to empirically confirm the divergence at runtime (this requires running the Cairo VM); the finding is based on direct code inspection of both the OS and blockifier implementations plus the explicit `TODO` comment marking the gap as a known, unresolved discrepancy.
