### Title
`ensure_match_transaction_info` skips state-checkpoint hash comparison, allowing `replay-verify` to accept a divergent state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  is the sole per-transaction correctness comparator used by the `replay-verify` tooling (`storage/db-tool/src/replay_on_archive.rs`) to check that a locally re-executed transaction matches the authenticated `TransactionInfo` recorded in the backup/ledger. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check the `state_checkpoint_hash` (nor hot-state/`position_state_checkpoint_hash`) field, as noted by its own inline TODO. This means a local replay whose resulting state root (JMT root) diverges from the authenticated on-chain state root can still pass `ensure_match_transaction_info` and be reported as a successful, verified replay.

### Finding Description
`replay_on_archive.rs::execute_and_verify` re-executes backed-up transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` as the only pass/fail gate per transaction: [2](#0-1) 

The comparator itself verifies:
- `status` vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `write_set_hash` vs. `txn_info.state_change_hash()`
- `event_root_hash` vs. `txn_info.event_root_hash()` [3](#0-2) 

It then returns `Ok(())` without ever comparing the transaction's (or checkpoint's) `state_checkpoint_hash` / hot-state checkpoint hash / `position_state_checkpoint_hash` against the value computed from local re-execution, with the code's own comment acknowledging the gap: [4](#0-3) 

The state-checkpoint hash is the authenticated Merkle root binding a `TransactionInfo`/ledger version to the actual post-execution state tree (used elsewhere for proof verification, e.g. `TransactionInfo::ensure_state_checkpoint_hash` consumed by the backup/restore path in `storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs` at line 130). Skipping it in the replay comparator breaks the invariant that "committed state that differs from the correct VM result" must be detected during replay/verify: a bug in execution, storage layout, or write-set application that silently produces a wrong state tree (but coincidentally produces the same write-set hash/event hash, or where the divergence only manifests in the aggregated state root rather than in any single write) would not be flagged by `replay-verify`.

### Impact Explanation
This directly matches the "Proof and Storage Pivots" invariant: replay/verify paths must independently re-derive and check the authenticated state root, not merely trust write-set/event hashes. If the state root diverges from correct VM execution (e.g. from a storage-schema bug, hot-state or JMT-related divergence, or any bug that corrupts committed state without changing per-write hashes as recorded), the tool used specifically to catch such state divergence (`replay-verify`) will report success. This is a hard-fork-detection blind spot: `replay-verify` is one of the primary tools operators/auditors rely on to catch consensus-breaking, state-corrupting bugs before/after they occur on mainnet, so a false "verified" result can mask real ledger corruption.

### Likelihood Explanation
The likelihood of triggering this specific comparator gap requires: (1) an underlying (separate) execution/storage bug that changes the computed state root without changing the write-set bytes/hash recorded per-transaction or the event root, and (2) the operator relying on `replay-verify`'s pass/fail result. This is a "second line of defense" gap rather than a bug that spontaneously corrupts state — it does not itself write bad data, but weakens the detection mechanism meant to catch other state-integrity bugs when they occur. Likelihood of the underlying trigger is inherently low/conditional, but the impact if it occurs (silently endorsing a diverged mainnet ledger state) is high, which is consistent with a Medium/High-severity gap in state-integrity tooling.

### Recommendation
In `ensure_match_transaction_info`, compute the state-checkpoint hash (and hot-state checkpoint hash, when applicable) from local re-execution/checkpoint output and compare it against `txn_info.state_checkpoint_hash()` (and other checkpoint-hash fields) whenever the field is `Some` in `txn_info`, failing the check (returning an error) on mismatch, consistent with how it already validates `state_change_hash` and `event_root_hash`. Until this is implemented, `replay-verify` output should not be treated as proof that the state root matches the authenticated ledger.

### Proof of Concept
Not applicable as an exploit PoC (this is a detection-gap in tooling, not a state-mutation bug). Code-level proof of the gap:
1. `storage/db-tool/src/replay_on_archive.rs:392-405` uses `ensure_match_transaction_info` as the only correctness gate for replayed transactions.
2. `types/src/transaction/mod.rs:2139-2204` shows the comparator checks status/gas/write-set-hash/event-root-hash only, with an explicit TODO acknowledging the omission of checkpoint-hash comparison at lines 2197-2202.
3. Consequently, any hypothetical bug that alters the state root without altering the recorded write-set hash or event root (e.g., an unrelated hot-state/JMT commit bug, or a bug in how the checkpoint hash itself is computed/stored) would be invisible to `replay-verify`, which would report a clean pass despite a state-root divergence from the authenticated ledger.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
