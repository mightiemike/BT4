### Title
Shielded transactions bypass bandwidth/fee metering, enabling free spam via expensive zk-SNARK proof verification - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java)

### Summary
`BandwidthProcessor.consume()`, the code path responsible for charging every transaction bandwidth points or a TRX fee before it is accepted, explicitly skips this accounting for `ShieldedTransferContract` transactions. This is analogous to the SORA report's "zero-weight extrinsics": a transaction type is exempted from the resource-metering mechanism that is supposed to make spam economically/computationally costly, while the transaction still forces the node to perform expensive work (zk-SNARK proof verification).

### Finding Description
`BandwidthProcessor.consume()` iterates over all contracts in a transaction and calls `useAccountNet`/`useFreeNet`/`useTransactionFee` to charge bandwidth points or TRX for every contract type — except when the contract type is `ShieldedTransferContract`, which is unconditionally skipped: [1](#0-0) 

This means `ShieldedTransferContract` transactions never consume `netUsage`, `freeNetUsage`, or pay the standard per-byte transaction fee that every other TRON transaction type is subject to. This is confirmed by an existing regression test that explicitly asserts `netUsage` and `freeNetUsage` are unchanged after a shielded transfer: [2](#0-1) 

Instead, `ShieldedTransferActuator` charges only a separate, fixed shielded-pool fee denominated in the "Zen" TRC10 token (`getShieldedTransactionFee()` / `getShieldedTransactionCreateAccountFee()`), which is unrelated to and disconnected from the chain's bandwidth/resource model: [3](#0-2) 

Despite this exemption from bandwidth accounting, processing a `ShieldedTransferContract` forces the node to perform computationally expensive zk-SNARK spend/output/binding-signature verification (`librustzcashSaplingCheckSpend`, `librustzcashSaplingCheckOutput`, `librustzcashSaplingFinalCheck`), invoked from `ShieldedTransferActuator.checkProof()`: [4](#0-3) 

The `PrecompiledContracts` shielded-proof verification tasks (`SaplingCheckSpendTask`, `SaplingCheckOutputTask`, `SaplingCheckBingdingSig`) further show this is treated as CPU-heavy, worker-pool-dispatched work elsewhere in the codebase: [5](#0-4) 

An attacker who controls a funded transparent account can repeatedly submit `ShieldedTransferContract` transactions (transparent-from → shielded pool, or transparent-from → transparent-to via the shielded contract path) that force full zk-SNARK proof verification on every full node, without ever depleting their own bandwidth quota, since the resource accounting for this contract type is a no-op in `BandwidthProcessor`.

### Impact Explanation
This allows an adversary to force disproportionate CPU work (zk-SNARK verification, one of the most expensive operations in the codebase) onto every validating/full node while paying none of the network's normal anti-spam bandwidth cost, and only a small, fixed protocol fee in a TRC10 asset unrelated to bandwidth economics. Because bandwidth points normally rate-limit how many transactions an account can push per time window, and this path is entirely exempted, an account can submit far more of these expensive transactions per unit time than the resource model intends, degrading node performance/availability — a DoS vector reachable purely via ordinary broadcast transactions.

### Likelihood Explanation
Likelihood is high in terms of reachability — this is triggered by any unprivileged account broadcasting a normal `ShieldedTransferContract` transaction, requiring only that shielded transactions are enabled (`supportShieldedTransaction()`/`AllowSameTokenName`) and that the attacker holds sufficient TRX/Zen balance to satisfy `fromAmount > fee`. No privileged role, leaked key, or malicious peer is required. The bar to generate a valid output/spend proof is the normal cost of using the shielded-transfer feature, well within reach of any user of the wallet/SDK.

### Recommendation
Short term: remove the blanket exemption of `ShieldedTransferContract` from `BandwidthProcessor.consume()`, or replace it with an explicit, benchmarked bandwidth/energy cost that reflects the CPU cost of zk-SNARK proof verification (`checkProof`), so that submitting many shielded transactions consumes the account's `netUsage`/`freeNetUsage` (or a dedicated resource) proportional to the verification cost, just as other expensive operations (e.g., smart contract execution) are metered via energy. Benchmark `librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` execution time and assign weights accordingly.

### Proof of Concept
1. Fund an account with TRX and confirm shielded transactions are enabled (`AllowSameTokenName == 1`, `supportShieldedTransaction() == true`).
2. Repeatedly construct and broadcast `ShieldedTransferContract` transactions with a transparent "from" address and valid (or minimally valid) receive descriptions, as done in `getPublicToShieldedTransaction()` used by `ShieldedTransferActuatorTest.publicAddressToShieldedAddressNotConsumeBandwidth`.
3. Observe (as the existing test already demonstrates) that after each transaction the account's `netUsage` and `freeNetUsage` are unchanged, i.e. no bandwidth is consumed, while the node still performed full zk-SNARK proof verification for each transaction — allowing unlimited repetition without triggering the account's bandwidth-based rate limit.
