### Title
Negative exchange reserve guard is skipped when `hardenedCalc=false`, allowing accounting corruption / consensus divergence - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction(byte[], long, boolean, boolean)` only rejects a resulting negative pool balance when the `hardenedCalc` flag is `true`; when it is `false` the check is entirely skipped due to the `if (hardenedCalc && ...)` gate, and the negative balances are written straight into the `Exchange` capsule and persisted by the caller. Because `hardenedCalc` is derived from the chain parameter `allowHardenExchangeCalculation` (via `AbstractExchangeActuator.allowHarden()`), any node/network where this proposal has not been activated (default `0`/false) will accept and persist transactions producing negative exchange reserves, while a node where it is activated will reject the identical transaction — a hard state divergence between the two configurations.

### Finding Description
In `ExchangeCapsule.java`: [1](#0-0) 

The guard is:
```java
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
```
This means whenever `hardenedCalc` is `false`, `newFirstTokenBalance`/`newSecondTokenBalance` can be negative and are written unconditionally into `this.exchange` via `setFirstTokenBalance`/`setSecondTokenBalance`.

The caller, `ExchangeTransactionActuator`, passes `allowHarden()` as `hardenedCalc` in both `validate()` and `execute()`: [2](#0-1) [3](#0-2) 

`validate()` invokes `exchangeCapsule.transaction(...)` only to check `anotherTokenQuant < tokenExpected`; it performs no separate non-negative-balance check of its own. `execute()` then calls `transaction(...)` again on the (persisted) `ExchangeCapsule` and persists the result via `Commons.putExchangeCapsule(...)`: [4](#0-3) 

So when `allowHardenExchangeCalculation == 0` (i.e., `allowHarden()` returns `false`), an attacker who can craft a `sellTokenQuant` (and satisfying `tokenExpected`) such that the AMM math on the plain-`ExchangeProcessor` path (non-`SafeExchangeProcessor`, using plain `+`/`-` instead of `StrictMathWrapper.addExact/subtractExact`) yields `buyTokenQuant` larger than the opposing reserve — whether via extreme inputs/overflow or edge-case math in the non-strict processor — results in the negative-balance state being written to `ExchangeCapsule`/`ExchangeV2Store` and committed to the chain state without any exception, while an identically-configured node with the proposal active (`hardenedCalc=true`) would throw `ContractValidateException` and reject the same transaction in `validate()`.

No other check in `ExchangeTransactionActuator.doValidate()` enforces non-negativity of the resulting reserves post-transaction — the only balance-related checks are the pre-transaction `firstTokenBalance == 0 || secondTokenBalance == 0` closed-exchange check and the `balanceLimit` upper-bound check on the *sold* token side, none of which protect the *bought* token side from going negative.

### Impact Explanation
This corresponds to TRON bounty "accounting/asset corruption" and "consensus divergence" impact classes: a node with `allowHardenExchangeCalculation=0` will accept and persist a transaction that produces a negative reserve in an on-chain `Exchange`/`ExchangeV2` object, corrupting global exchange-pool accounting invariants (non-negative reserves, value conservation). If part of the network has the hardening proposal active and another part does not (a legitimate transitional/precondition state that the proposal mechanism itself is designed to gate), the two node populations diverge in whether they accept the block containing this transaction, producing a chain fork.

### Likelihood Explanation
Preconditions are exactly as stated: `allowHardenExchangeCalculation=false` (the pre-upgrade/default state that the maintainers themselves gate behind a chain parameter, implying it is a real, previously-not-yet-universally-active condition). The attacker only needs to be an ordinary funded account able to broadcast a signed `ExchangeTransactionContract` with a crafted `quant`/`expected` targeting an existing exchange pool — no privileged role is required. Cost to the attacker is limited to the tokens/TRX sold in the transaction and zero fee (`calcFee()` returns `0` for this actuator) plus bandwidth/energy for a normal transaction. The exact numeric inputs needed to force `buyTokenQuant` past the opposite reserve depend on the internal `ExchangeProcessor` (non-strict) math, which was not available to fully inspect in this session, so the concrete overflow/edge-case parameters that trigger it are not independently verified here — but the structural bypass of the guard itself is unambiguous and directly supported by the code.

### Recommendation
Remove the `hardenedCalc &&` gate so the non-negative-balance invariant (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) is always enforced regardless of the `allowHardenExchangeCalculation` proposal state, since this check is a basic economic invariant and not merely an overflow-safety hardening; the overflow-safe arithmetic (`StrictMathWrapper.addExact/subtractExact`) can remain conditionally gated, but the resulting-balance sign check should not be.

```java
// JUnit-style PoC targeting ExchangeCapsule.transaction directly
ExchangeCapsule exchangeCapsule = new ExchangeCapsule(
    ByteString.copyFrom("owner".getBytes()), 1, System.currentTimeMillis(),
    "firstTokenID".getBytes(), "secondTokenID".getBytes());
exchangeCapsule.setBalance(smallFirstBalance, smallSecondBalance); // small reserves

// craft sellTokenQuant so that computed buyTokenQuant > secondTokenBalance
long buyTokenQuant = exchangeCapsule.transaction(
    "firstTokenID".getBytes(), craftedSellTokenQuant,
    /*useStrictMath=*/false, /*hardenedCalc=*/false);

// Expected (vulnerable) behavior: no ContractValidateException thrown
assertTrue(exchangeCapsule.getSecondTokenBalance() < 0);

// Contrast: same call with hardenedCalc = true
assertThrows(ContractValidateException.class, () ->
    exchangeCapsule.transaction("firstTokenID".getBytes(), craftedSellTokenQuant,
        false, /*hardenedCalc=*/true));
```
At the request level: submit a signed `ExchangeTransactionContract` (`exchange_id`, `token_id`, `quant=craftedSellTokenQuant`, `expected` satisfied) against a chain configured with `allowHardenExchangeCalculation=0`; observe the transaction succeeds (`code.SUCESS`) and the resulting `Exchange`/`ExchangeV2` object has a negative `first_token_balance` or `second_token_balance`, whereas the identical request against a chain with the proposal active is rejected in `validate()` with `ContractValidateException("Exchange balance must be >=0 after transaction")`.

```java
  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
```
