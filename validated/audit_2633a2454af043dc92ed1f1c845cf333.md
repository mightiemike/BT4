### Title
Unbounded Recursion Over Attacker-Controlled JSON in Cairo0 Class Hinted-Hash Computation Causes Stack Overflow DoS - (File: crates/starknet_os/src/hints/class_hash/hinted_class_hash.rs)

### Summary
The Starknet sequencer's Cairo0 (deprecated) contract-class hinted-hash computation deserializes the attacker-supplied `abi` field of a declared contract class as an unconstrained `serde_json::Value`, then recursively walks the resulting tree with `sort_json_value` — a plain, unbounded recursive function with no depth limit. This is the same bug class as CVE-2020-24345 (stack consumption via deeply nested/self-referential structures processed by a recursive-descent routine): a single unprivileged Declare (V0/V1) transaction whose `contract_class.abi` contains a deeply nested JSON array/object can drive native call-stack recursion deep enough to overflow the stack.

### Finding Description
`CairoContractDefinition` deserializes the class's `abi` as a raw `serde_json::Value` with no structural constraints: [1](#0-0) 

`compute_cairo_hinted_class_hash` re-serializes the whole `ContractClass` to a `serde_json::Value`, then calls the purely recursive `sort_json_value` helper on it before re-parsing into `CairoContractDefinition` and hashing: [2](#0-1) 

`sort_json_value` recurses once per nesting level of the JSON `abi` value with no depth check whatsoever: [3](#0-2) 

This routine is exercised by `compute_deprecated_class_hash`, invoked whenever a Cairo0 class hash must be computed/verified — including from the Starknet OS re-execution path (`starknet_os/src/hints/hint_implementation/deprecated_compiled_class/class_hash.rs`) that every Declare V0/V1 transaction goes through, as exercised in tests such as: [4](#0-3) 

Because the class's `abi` field is attacker-controlled free-form JSON, and neither the deserialization of `serde_json::Value` nor `sort_json_value`'s traversal impose any recursion-depth bound, a contract class with an `abi` value containing thousands of nested arrays (e.g. `[[[[...]]]]`) forces thousands of native stack frames during hashing. Unlike a Rust panic, native stack overflow is undefined behavior (typically SIGSEGV), which is not recoverable via `Result`/`catch_unwind`, and terminates the process that computed it (gateway validator process and/or an OS/prover re-execution worker), regardless of any Cairo VM step or gas limits — those limits only bound the emulated Cairo VM stack, not this native Rust-side JSON class-hash preprocessing.

### Impact Explanation
A crash of the process performing class-hash validation is a denial-of-service: if triggered in the gateway/validation path it can halt admission of new declare (and by extension all subsequent) transactions on the affected node; if triggered during Starknet OS re-execution/proving it can prevent block proving/verification, i.e., "a network unable to confirm new transactions" per the scope's accepted impact categories. This qualifies as High severity given the low cost (a single, tiny declare transaction payload) versus the potential to repeatedly crash sequencer/prover processes.

### Likelihood Explanation
Likelihood is high: the `abi` field is not size- or depth-restricted beyond the overall transaction/class size cap, and only a few kilobytes of deeply nested JSON (e.g. tens of thousands of `[` characters) are needed to reach typical default thread stack sizes when combined with the multiple recursive passes (JSON parse into `Value`, `sort_json_value`, re-parse into `CairoContractDefinition`). No signature bypass, special privileges, or race conditions are required — any account able to submit a Declare V0/V1 transaction can attempt this.

### Recommendation
- Enforce an explicit maximum JSON nesting depth when parsing/deserializing the `abi` (and generally any attacker-supplied `serde_json::Value`) field of a declared contract class, rejecting classes whose ABI JSON exceeds a safe depth (e.g. using a depth-limited deserializer/visitor or a pre-validation pass with an explicit stack instead of native recursion).
- Rewrite `sort_json_value` to use an explicit work-list/stack (iterative traversal) instead of native function recursion, or add a depth counter that errors out beyond a fixed bound (e.g. 64–128 levels).
- Apply the same depth-limiting treatment to any other unconstrained `serde_json::Value` fields reachable from transaction/class inputs before they are passed to hashing or serialization routines.

### Proof of Concept
1. Craft a Declare V0 or V1 transaction whose `contract_class.abi` field is set to a deeply nested JSON array, e.g. `"[".repeat(50000) + "]".repeat(50000)` (valid JSON, ~100KB, well under typical size limits).
2. Submit the transaction to the gateway (or include it in a batch subject to Starknet OS re-execution).
3. When `compute_cairo_hinted_class_hash` is invoked (via `compute_deprecated_class_hash`) to validate/compute the class hash, `sort_json_value` recurses once per array nesting level (50,000 levels), exhausting the native stack and crashing the process with SIGSEGV before any Cairo-VM step/gas accounting is reached.

/// Recursively sorts all JSON objects by their keys.
/// This ensures deterministic serialization regardless of the `preserve_order` feature in
/// serde_json.
fn sort_json_value(value: serde_json::Value) -> serde_json::Value {
    match value {
        serde_json::Value::Object(map) => {
            let sorted: BTreeMap<String, serde_json::Value> =
                map.into_iter().map(|(k, v)| (k, sort_json_value(v))).collect();
            serde_json::Value::Object(sorted.into_iter().collect())
        }
        serde_json::Value::Array(arr) => {
            serde_json::Value::Array(arr.into_iter().map(sort_json_value).collect())
        }
        other => other,
    }
}
