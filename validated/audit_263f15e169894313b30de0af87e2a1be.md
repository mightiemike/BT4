### Title
Missing declared-class-hash validation in Starknet OS `replace_class` syscall causes blockifier/OS state divergence - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The Starknet OS Cairo implementation of the `replace_class` syscall (`execute_replace_class`) writes an attacker-supplied `class_hash` directly into a contract's `StateEntry` without verifying that the class hash corresponds to a previously declared class. The equivalent Rust blockifier implementation performs this check (`syscall_handler.state.get_compiled_class(request.class_hash)?` before writing), so the two execution engines diverge on the same transaction.

### Finding Description
`execute_replace_class` in `syscall_impls.cairo` (lines 881-920) and the deprecated variant in `deprecated_execute_syscalls.cairo` (lines 307-329) both read `class_hash` from the syscall request and unconditionally build a new `StateEntry` with that class hash, updating `contract_state_changes` for the calling contract's address. The comment at line 902, `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.`, documents that this validation is known to be missing.

By contrast, `blockifier`'s Rust syscall handler for the same operation explicitly ensures the class is declared before mutating state: [3](#0-2) 
and this behavior is asserted by unit tests expecting an `"is not declared"` error for undeclared class hashes, both for the deprecated and current syscall variants: `crates/blockifier/src/execution/deprecated_syscalls/deprecated_syscalls_test.rs:376-391` and `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:17-29`.

Since blockifier is what actually executes transactions and produces the state diff that gets committed on-chain (fee charged, resources bounced, state diff written), while the Starknet OS re-executes the same transaction trace off-chain to produce the proof that the block was executed correctly, this creates a case where blockifier will reject a `replace_class` call with an undeclared class hash (transaction reverts with "is not declared"), but if such a call were ever accepted by blockifier through some other path, or if the OS's independent re-execution trace is trusted for the state commitment, the OS would silently accept setting a contract's class hash to an undeclared/arbitrary value. This produces divergent results between the two independently-maintained execution paths that are required to agree bit-for-bit for the STARK proof of block execution to validate the sequencer's claimed state root.

### Impact Explanation
A discrepancy between blockifier and the Starknet OS on `replace_class` validation is a correctness-critical bug: any contract can trigger `replace_class` in a transaction (it requires no special privilege — this is a syscall any deployed contract's Cairo code can invoke). If the OS's leniency is ever exercised (e.g., due to a different consistency check being bypassed upstream, or future code paths that skip blockifier's check), the OS will compute a different `new_class_hash` state diff than blockifier, causing wrong committed state — either producing an unprovable block (halting block production/proof generation) or, in the worst case, allowing a contract's class hash in the proved state to be set to a class that was never declared, undermining the guarantee that all executed code is registered/audited via declaration. This falls under "wrong committed root" / "honest-node divergence" impact categories.

### Likelihood Explanation
Reaching `execute_replace_class` requires only a normal contract calling `replace_class` in its Cairo code — no special deployer or operator privilege, matching the "unprivileged transaction sender" reachability requirement. The missing check is unconditional (present on every invocation of the syscall in the OS), and the divergence from blockifier's behavior is already explicitly flagged by the maintainers' own TODO comment, indicating it is a known, currently-unaddressed gap rather than a theoretical one.

### Recommendation
Add an explicit assertion in `execute_replace_class` (both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo`) that the given `class_hash` is present in the OS's declared-classes registry before constructing the new `StateEntry`, mirroring the `get_compiled_class` / `is_declared` check performed in blockifier's `syscall_base.rs` and `hint_processor.rs`. This should be enforced identically on both the current and deprecated syscall paths, and covered by an OS-level Cairo test analogous to `blockifier`'s `undeclared_class_hash` test.

### Proof of Concept
1. Deploy a contract exposing the `replace_class` syscall (e.g. `test_replace_class` in the feature-contract test fixtures) with no other special requirements.
2. Send a transaction that invokes `replace_class` with an arbitrary `class_hash` value that was never declared (e.g. `felt!(1234)` as used in `blockifier`'s own `undeclared_class_hash` test at `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:17-29`).
3. Observe that blockifier rejects the call with `"is not declared"`.
4. If this same transaction trace is fed to the Starknet OS re-execution (`execute_replace_class`), it accepts the undeclared class hash unconditionally and writes it into `contract_state_changes`, producing a `StateEntry` with a class hash that blockifier would have rejected — a concrete divergence between the two supposedly equivalent execution engines.
