### Title
Missing upper-bound validation on `origin_energy_limit` allows unbounded energy-fee-split accounting values - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateEnergyLimitContractActuator.java])

### Summary
`UpdateEnergyLimitContractActuator` only rejects `origin_energy_limit <= 0`, with no upper bound, unlike its sibling `UpdateSettingContractActuator` which properly bounds `consume_user_resource_percent` to `[0, 100]`. This mirrors the reported `FliquidatorFTM.setFlashCloseFee` bug class: a numeric accounting factor supplied by an unprivileged caller (any smart-contract owner) is stored without a sane range check and then flows directly into the resource/fee-split accounting math used for every subsequent contract call.

### Finding Description
`UpdateEnergyLimitContractActuator.validate()` checks only the lower bound of the value: [1](#0-0) 

There is no comparison against any chain-level maximum (e.g. `TOTAL_ENERGY_LIMIT`, `dynamicStore.getTotalEnergyCurrentLimit()`, or `Long.MAX_VALUE / X` guard), so a contract owner can set `origin_energy_limit` to an arbitrarily large `int64` value (up to `Long.MAX_VALUE`). This contrasts with the analogous `UpdateSettingContractActuator`, which enforces `newPercent > ActuatorConstant.ONE_HUNDRED || newPercent < 0` before persisting `consume_user_resource_percent`: [2](#0-1) 

The unvalidated value is later consumed by `VMActuator.getTotalEnergyLimitWithFixRatio`, which splits total energy limit between the calling account and the contract's creator (origin) using `consumeUserResourcePercent` together with `originEnergyLimit`: [3](#0-2) 

Here `originEnergyLimit` is combined via `min(...)`, `BigInteger` multiply/divide with `longValueExact()`, and later `addExact(callerEnergyLimit, creatorEnergyLimit, ...)`. Because `origin_energy_limit` has no realistic upper bound, this value directly affects the internal energy-accounting math (creator vs. caller split, and downstream `EnergyProcessor.increase`/usage bookkeeping) that determines how much energy is charged to the contract's creator versus the caller, i.e., internal resource-fee accounting analogous to the flash-close fee factor's effect on internal balance accounting in the reported bug.

### Impact Explanation
Setting an unrealistically large `origin_energy_limit` distorts the fee-split accounting between the contract creator and callers: with `consumeUserResourcePercent` low, `creatorEnergyLimit` can be pushed toward the (unbounded) `originEnergyLimit` value rather than a chain-sane limit, effectively letting the contract creator claim disproportionate creator-side energy allowances relative to intended protocol design, and risking `ArithmeticException`s from `longValueExact()`/`addExact()` on extreme values, which would cause transaction execution to fail (localized DoS for calls to that contract) rather than a global consensus break. This is an accounting-integrity issue in the resource/energy metering path rather than a fund-theft primitive, so impact is moderate.

### Likelihood Explanation
Likelihood is high for the trigger conditions: setting `UpdateEnergyLimitContract` is reachable by any account that is the origin/owner of a deployed contract, via a normal broadcast transaction (`wallet/updateenergylimit` HTTP/RPC endpoint), with no committee or witness privilege required — this matches the "unprivileged actor / broadcast transaction" reachability required by the analog criteria. The only gate is `ReceiptCapsule.checkForEnergyLimit` (a fork-activation check), not a bound on the value itself.

### Recommendation
Add an explicit upper-bound check in `UpdateEnergyLimitContractActuator.validate()`, e.g. requiring `newOriginEnergyLimit` to be within `[1, dynamicStore.getTotalEnergyLimit()]` or another well-defined chain-level ceiling, mirroring the `[0, 100]` bound already enforced in `UpdateSettingContractActuator` for `consume_user_resource_percent`. This prevents unbounded values from propagating into the energy-limit split arithmetic in `VMActuator.getTotalEnergyLimitWithFixRatio`.

### Proof of Concept
1. Deploy a smart contract as account `A` (becomes `originAddress` of the contract).
2. Broadcast an `UpdateEnergyLimitContract` transaction from `A` with `origin_energy_limit = Long.MAX_VALUE` (or any value far exceeding the network's total energy limit) via `wallet/updateenergylimit`.
3. `UpdateEnergyLimitContractActuator.validate()` only checks `newOriginEnergyLimit <= 0` and accepts the value: [1](#0-0) 
4. The value is persisted to `ContractCapsule.setOriginEnergyLimit`.
5. On subsequent `TriggerSmartContract` calls to this contract by other accounts, `VMActuator.getTotalEnergyLimitWithFixRatio` uses this inflated `originEnergyLimit` in `min(...)`/`BigInteger` arithmetic, producing skewed `creatorEnergyLimit` values or throwing `ArithmeticException` on overflow at `longValueExact()`/`addExact()`, corrupting the intended energy-fee split or reverting calls to the contract.

Note: I was not able to fully verify whether any additional upstream guard (e.g., a maximum enforced elsewhere in `ContractCapsule` or a dynamic-property clamp) exists beyond what `grep_search` for `getOriginEnergyLimit` surfaced; the listed call sites (`VMActuator.java`, `ContractCapsule.java`, `TransactionTrace.java`, `TronJsonRpcImpl.java`) did not show any additional bound-clamping logic in the snippets reviewed, but a full read of `ContractCapsule.java`'s `getOriginEnergyLimit` getter could not be completed within the available tool budget.
