### Title
`finalize_cancellation` deletes an L1 handler transaction record unconditionally, even if it was already `Committed`/`Consumed`, discarding bookkeeping needed to prevent re-execution - (File: `crates/apollo_l1_events/src/transaction_manager.rs`)

### Summary
`TransactionManager::finalize_cancellation`, invoked when the `MessageToL2Canceled` L1 event arrives, deletes the transaction's record from `self.records` regardless of what state that record was actually in, including `Committed` or `Consumed`. The function only logs a `warn!` if the state isn't `CancellationStartedOnL2`, but still proceeds to remove the record either way.

### Finding Description
`finalize_cancellation` reads the record, and if its state isn't `CancellationStartedOnL2` it just warns: [1](#0-0) 

The comment inside the function is explicit about the hazard: *"Regardless of the state of the tx in the record, if we get the cancellation event from the L1 contract, we delete this tx from the records and from the proposable index, even if it was Pending and ready to be proposed (which is not supposed to happen, hence the warning)."*

This is the same bug class as the DCA report: an operation that discards/finalizes state (`_cleanup_order` / here, record removal) proceeds without validating that the precondition (transaction not yet committed/consumed) actually holds — only a warning is logged, no invariant is enforced.

While `mark_cancellation_request` does protect against *marking* a `Committed` tx as `CancellationStartedOnL2`: [2](#0-1) 

there is no equivalent guard in `finalize_cancellation`/`mark_cancellation_finalized_on_l1`: [3](#0-2) 

Because the L1 cancellation timelock (`startL1ToL2MessageCancellation` -> wait -> `cancelL1ToL2Message`) is long, a race window exists where: the tx transitions `Pending -> CancellationStartedOnL2` (cancellation requested before commit), then gets `Committed` on L2 via normal consensus (`commit_txs`, which does not check for `CancellationStartedOnL2` state before marking `Committed`): [4](#0-3) 

and only afterward does the `MessageToL2Canceled` event get scraped and delivered to `finalize_cancellation`, which unconditionally removes the (now `Committed`) record from `self.records`. This is reachable purely from an L1 message flow — sending an L1-to-L2 message, requesting its cancellation, and finalizing that cancellation on L1 — all standard, unprivileged actions by any L1 message sender.

### Impact Explanation
Once the record for an already-`Committed` L1 handler transaction is deleted, the transaction manager loses all memory that this L1 message hash was ever included in L2. `validate_tx` returns `NotFound` (allowing revalidation) instead of `AlreadyIncludedOnL2` for a hash no longer in `records`, and any later re-add of the same L1 message hash (e.g. via `add_tx` on a rescrape, resync, or catch-up path) would be treated as a brand-new `Pending` transaction, eligible for proposal/validation again. This opens the door to double inclusion / double execution of an L1-to-L2 message that already minted/transferred funds on L2 — a concrete double-spend / loss-of-funds scenario, matching the "operation proceeds despite incomplete/inconsistent underlying state" root cause in the reference report.

### Likelihood Explanation
The precondition requires a specific but realistic ordering: cancellation requested on L1 before the L1 handler tx is committed on L2, followed by the L2 commit landing before the L1 cancellation finalization event is scraped and processed (well within the intended real-world cancellation timelock window, which is designed to be long enough for exactly this kind of race to normally be prevented — but here the "already committed" check is not enforced, only logged). The code's own comment acknowledges this exact scenario is possible ("even if it was Pending and ready to be proposed... which is not supposed to happen, hence the warning"), indicating the developers were aware of a gap but did not add an enforcing guard for the `Committed`/`Consumed` cases.

### Recommendation
In `finalize_cancellation` (and `mark_cancellation_finalized_on_l1`), do not unconditionally delete the record. If `record.state` is `Committed` or `Consumed`, the cancellation event should be ignored (log and return) rather than removing the record, preserving the invariant that a committed/consumed L1 handler transaction's hash remains known to the transaction manager so it can never be re-validated or re-proposed as `Pending`.

### Proof of Concept
1. An L1 sender sends an L1-to-L2 message (`add_tx` creates a `Pending` record).
2. Before the corresponding L1 handler tx is committed on L2, the sender calls `startL1ToL2MessageCancellation` on L1 → `request_cancellation` sets state to `CancellationStartedOnL2`.
3. Before the sender can finalize the cancellation, a proposer includes and commits the tx on L2 (`commit_txs` → `mark_committed`, no check against `CancellationStartedOnL2`), so the L2 side effects (mint/transfer) execute.
4. The sender then finalizes the cancellation on L1 (`cancelL1ToL2Message`), which is scraped and dispatched to `finalize_cancellation`. The function only warns about the mismatched state and unconditionally removes the (already `Committed`) record from `self.records`.
5. Any subsequent resync/rescrape/catch-up path that reprocesses the original `LogMessageToL2` event (via `add_tx`) treats the L1 handler as a new `Pending` transaction, since no record exists to flag it as `AlreadyIncludedOnL2`, enabling potential re-validation/re-proposal of a message that already executed on L2.

    pub fn finalize_cancellation(&mut self, tx_hash: TransactionHash) {
        let Some(record) = self.records.get(&tx_hash) else {
            info!(
                "Attempted to finalize cancellation for non-existent transaction: {tx_hash}. This \
                 can happen if the transaction was too old to be scraped (e.g. it was created \
                 before we started scraping)."
            );
            return;
        };

        // Regardless of the state of the tx in the record, if we get the cancellation event from
        // the L1 contract, we delete this tx from the records and from the proposable index, even
        // if it was Pending and ready to be proposed (which is not supposed to happen, hence the
        // warning).
        if record.state != TransactionState::CancellationStartedOnL2 {
            warn!(
                "Attempted to finalize cancellation for transaction {tx_hash} that is not in the \
                 cancellation started on L2 state, but in the {:?} state.",
                record.state
            );
        }
        // This will also call maintain_indices to remove the tx from the proposable index.
        self.with_record(tx_hash, |r| r.mark_cancellation_finalized_on_l1());
        self.records.remove(&tx_hash);
    }

    pub fn mark_cancellation_request(
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }
