### Title
Disabled TokenConfig does not block PRC20 minting on inbound execution - (File: x/uexecutor/keeper/handler.go)

### Summary
`uregistry.TokenConfig.Enabled` is documented as controlling "whether this token is enabled for minting/bridging" [1](#0-0) , but no code path in `x/uexecutor` ever reads this field before minting PRC20. This is the direct analog of the ERC-4626 `maxDeposit` bug: a flag that is supposed to gate a deposit-equivalent operation ("even if temporarily disabled it MUST return 0 / block the action") is silently ignored, so the disabled state has no real effect on the mint path.

### Finding Description
`depositPRC20` fetches the `TokenConfig` purely to resolve the PRC20 contract address and never inspects `Enabled`: [2](#0-1) 

This function is invoked from every inbound funds path — `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGasAndPayload` — which are reached from `VoteInbound` after ballot finalization by ordinary user-triggered inbound events on the source chain [3](#0-2) [4](#0-3) . By contrast, the chain-level enable/disable flags (`ChainConfig.Enabled.IsInboundEnabled` / `IsOutboundEnabled`) *are* consistently checked at every relevant gate — `VoteInbound`, `ExecutePayload`, `BuildOutboundsFromReceipt`, TSS signing, and the universal-client broadcaster all enforce them [5](#0-4) [6](#0-5) [7](#0-6) . The `TokenConfig.Enabled` flag has no equivalent enforcement anywhere in `x/uexecutor`, `x/uregistry`, or the derived EVM call layer (`GetTokenConfig`, `GetTokenConfigByPRC20`, `CallPRC20Deposit`, `CallPRC20DepositAutoSwap` all pass through unconditionally).

### Impact Explanation
Per the module's own admin model, disabling a token is the intended mechanism to halt bridging/minting for it (e.g., in response to a depeg, an exploited source-chain token contract, or a liquidity-cap breach that the admin wants to freeze immediately). Because `Enabled` is never enforced on the mint path, an unprivileged user can continue submitting/observing inbound gateway events for a token the admin has explicitly disabled, and validators will continue to vote it through to `ExecuteInbound`, resulting in PRC20 tokens still being minted via `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`. This is an unauthorized-mint condition reachable purely by ordinary inbound submission with honest validators — the admin's disable action provides no actual protection, undermining the registry's stated security control and potentially allowing continued minting against a compromised/misbehaving external token even after the protocol has flagged it unsafe.

### Likelihood Explanation
Medium-to-high: the trigger requires only that an admin has disabled a `TokenConfig` (a realistic incident-response action) while the associated `ChainConfig` remains inbound-enabled (the normal case, since chain-level and token-level enablement are independent knobs). Any subsequent inbound event on that (chain, token) pair from an ordinary user is sufficient — no privileged action or validator collusion is required.

### Recommendation
Add an explicit check of `tokenConfig.Enabled` in `depositPRC20` (and any other PRC20-mint entry points, e.g., the GAS/auto-swap deposit path) immediately after resolving the `TokenConfig`. If disabled, fail the deposit the same way `NativeRepresentation == nil` is currently handled, and route through the existing failed-PCTx/revert-outbound logic so the inbound audit trail is preserved without minting.

### Proof of Concept
1. Admin registers `TokenConfig{Chain: "eip155:11155111", Address: usdcAddr, Enabled: true, ...}` and its `ChainConfig` with `IsInboundEnabled: true`.
2. Admin later calls `MsgUpdateTokenConfig` to set `Enabled: false` for this token (e.g., incident response), leaving the chain's `IsInboundEnabled` unchanged.
3. An ordinary user still deposits the (now-disabled) token into the source-chain gateway and validators observe/vote the inbound via `MsgVoteInbound` — this succeeds because `VoteInbound` only checks `IsChainInboundEnabled`, not the token's `Enabled` flag [5](#0-4) .
4. Ballot finalizes, `ExecuteInbound`/`ExecuteInboundFunds` runs and calls `depositPRC20`, which looks up the disabled `TokenConfig` and mints PRC20 to the recipient regardless [8](#0-7) .
5. Result: PRC20 continues to be minted for a token the admin explicitly disabled — no revert, no block, `Enabled=false` has zero effect.

**Uncertainty note:** I was unable to fully verify within the available index whether `MsgUpdateTokenConfig`/`MsgRemoveTokenConfig` in `x/uregistry/keeper` perform any side-effect (e.g., forcing `ChainConfig.Enabled=false` or clearing `NativeRepresentation`) that might indirectly neutralize a disabled token — the query tools did not surface that handler's body. If such a side-effect exists it could mitigate this finding; confirming this would require inspecting `x/uregistry/keeper/msg_update_token_config.go` and `msg_remove_token_config.go` directly, which is worth doing before treating this as fully confirmed.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
