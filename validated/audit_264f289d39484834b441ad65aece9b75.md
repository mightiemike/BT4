### Title
Replay-verify path (`ensure_match_transaction_info`) never checks `state_checkpoint_hash`, allowing a diverged state root to be silently accepted as a successful replay — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by the chunk executor's `verify_execution` during backup restore / replay-verify) checks status, gas, write-set hash, and event root against the trusted `TransactionInfo`, but explicitly skips the `state_checkpoint_hash` (and hot-state / position-state checkpoint hashes). This is the sole state-divergence check available during transaction replay, so a locally-computed state root that differs from the one actually certified in the historical `TransactionInfo`/`LedgerInfo` is never flagged.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates:
- execution status,
- gas used,
- `write_set` hash vs `txn_info.state_change_hash()`,
- event root hash,

but the function's own trailing comment admits: *"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."* [2](#0-1) 

This function is the exclusive correctness gate used by the chunk executor's replay-verify flow in `ChunkExecutorInner::verify_execution`, which re-executes the transactions through the VM and calls `txn_out.ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))` for each transaction, treating a return of `Ok(())` as proof the replay matches the trusted `TransactionInfo`: [3](#0-2) 

Crucially, after `verify_execution` passes, the executor does **not** commit the freshly re-executed VM output. Instead, `remove_and_apply` re-packages the *original* backup-provided `write_sets`/`transaction_infos` (not the VM's freshly computed state) into a `ChunkToApply` and enqueues it for the ledger-update/commit pipeline: [4](#0-3) 

Because the applied write set is taken as-is from input rather than recomputed and cross-checked at the state-root level, the only place where a genuine "does replayed state match the authenticated state root" check could occur is `ensure_match_transaction_info` — and that check omits `state_checkpoint_hash` entirely. No other call site was found that separately validates the recomputed Jellyfish Merkle root against the trusted `TransactionInfo.state_checkpoint_hash` in this replay path.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result or corrupts durable ledger data" and "hard-fork-only divergence during commit, replay ... must not go undetected" invariants. If VM execution during replay (e.g., a build with a state-computation discrepancy, an execution-environment difference, or a subtly corrupted/malicious backup archive whose write sets still hash-match `state_change_hash` but represent state that merklizes to a different root) produces a state root different from what validators actually certified, `verify_execution`/`ensure_match_transaction_info` will still report success. The resulting local database can then diverge from the authenticated chain state without any error being raised by the replay-verify tooling, which is precisely the safety property this tooling exists to guarantee (db-tool `replay_on_archive`, backup restore replay-verify). This is a state-commitment integrity gap, not merely a cosmetic one.

### Likelihood Explanation
This is a real, already-acknowledged gap in the shipped code (evidenced by the developer's own TODO), reachable through the standard replay-verify / backup-restore-replay code path with no privileged actor required — any state or backup data that reaches this path is "verified" by a function that skips the very check (state root) that verification is meant to catch. It is gated behind normal replay/verify usage, not consensus-time hot path, so its likelihood of affecting live consensus is lower, but it directly undermines a security-critical verification tool, and the flag `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-related comment shows the authors know this must be fixed before enabling that feature — the base `state_checkpoint_hash` case (unrelated to any feature flag) is unconditionally unchecked today.

### Recommendation
In `ensure_match_transaction_info`, add a comparison of the locally computed state checkpoint hash(es) — recomputed after the VM re-execution and any relevant state checkpoint step — against `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` when those roots are checkpointed), returning an error on mismatch instead of silently passing. Ensure the chunk executor's `verify_execution` path computes and threads through the state root produced from the re-executed write sets before calling this validation, so a genuine root divergence causes verification failure rather than a false "replay OK" signal.

### Proof of Concept
Not independently runnable within this analysis (would require constructing a backup archive / replay input where the write-set hash equals the trusted `state_change_hash` but where the resulting Jellyfish Merkle Tree root computed from re-execution differs from `state_checkpoint_hash`, then running `db-tool replay-on-archive` or `TransactionReplayer::enqueue_chunks` with `verify_execution_mode.should_verify() == true`). The core evidence is the code-level proof: `ensure_match_transaction_info` at [1](#0-0)  never reads or compares `state_checkpoint_hash`, and it is the only check invoked in `verify_execution` at [5](#0-4)  before the original (unverified-at-root-level) write sets are committed via `remove_and_apply` at [6](#0-5) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())

    /// Consume `end_version - begin_version` txns from the mutable input arguments
    /// It's guaranteed that there's no known broken versions or epoch endings in the range.
    fn remove_and_apply(
        &self,
        transactions: &mut Vec<Transaction>,
        persisted_aux_info: &mut Vec<PersistedAuxiliaryInfo>,
        transaction_infos: &mut Vec<TransactionInfo>,
        write_sets: &mut Vec<WriteSet>,
        event_vecs: &mut Vec<Vec<ContractEvent>>,
        begin_version: Version,
        end_version: Version,
    ) -> Result<()> {
        let num_txns = (end_version - begin_version) as usize;
        let txn_infos: Vec<_> = transaction_infos.drain(..num_txns).collect();
        let (transactions, persisted_aux_info, transaction_outputs) = multizip((
            transactions.drain(..num_txns),
            persisted_aux_info.drain(..num_txns),
            txn_infos.iter(),
            write_sets.drain(..num_txns),
            event_vecs.drain(..num_txns),
        ))
        .map(|(txn, persisted_aux_info, txn_info, write_set, events)| {
            (
                txn,
                persisted_aux_info,
                TransactionOutput::new(
                    write_set,
                    events,
                    txn_info.gas_used(),
                    TransactionStatus::Keep(txn_info.status().clone()),
                    TransactionAuxiliaryData::default(), // No auxiliary data if transaction is not executed through VM
                ),
            )
        })
        .multiunzip();

        let chunk = ChunkToApply {
            transactions,
            transaction_outputs,
            persisted_aux_info,
            first_version: begin_version,
        };
        let chunk_verifier = Arc::new(ReplayChunkVerifier {
            transaction_infos: txn_infos,
        });
        self.enqueue_chunk(chunk, chunk_verifier, "replay")?;

        Ok(())
