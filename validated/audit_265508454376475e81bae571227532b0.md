### Title
Unguarded division by `totalEnergyWeight`/`totalEnergyLimit` can throw uncaught `ArithmeticException` during TVM energy accounting - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()` and `RepositoryImpl.usageToBalance()` divide by `totalEnergyWeight` and `totalLimit`/`totalEnergyLimit` with no runtime zero-check, relying only on a Java `assert` statement that is compiled out and disabled by default (JVMs run with `-da` unless `-ea` is explicitly set). This mirrors the reported "Division by Zero" bug class: a denominator that can reach zero causes an unhandled arithmetic exception instead of a guarded/validated code path.

### Finding Description
In `RepositoryImpl.calculateGlobalEnergyLimit`, the denominator check is only an `assert`: [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

Contrast this with the sibling, actuator-layer implementation in `EnergyProcessor.calculateGlobalEnergyLimit`, which contains an actual runtime guard before the same division: [2](#0-1) 

```java
long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
}
```

`RepositoryImpl` (in the `actuator/.../vm/repository` package used by the TVM `Repository`/`ContractState` layer that backs contract execution, resource-related opcodes, and native contracts such as delegate/undelegate resource processors) has no such guard — only a compiled-out `assert`. The same pattern recurs in `usageToBalance`: [3](#0-2) 

```java
private long usageToBalance(long usage, long totalWeight, long totalLimit) {
    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(usage)
          .multiply(BigInteger.valueOf(totalWeight))
          .multiply(BigInteger.valueOf(TRX_PRECISION))
          .divide(BigInteger.valueOf(totalLimit))
          .longValueExact();
    }
    return (long) ((double) usage * totalWeight / totalLimit * TRX_PRECISION);
}
```

which is reachable from `getAccountEnergyUsageBalanceAndRestoreSeconds`/`getAccountNetUsageBalanceAndRestoreSeconds` and divides by `totalEnergyLimit`/`totalNetLimit` (a chain-configurable dynamic property) with no zero check at all, in either the BigInteger ("hardened") or double path.

`ContractState` (the per-call TVM repository wrapper that is exercised on every contract invocation) simply forwards `calculateGlobalEnergyLimit` to the underlying `RepositoryImpl`: [4](#0-3) 

So this code path is reachable from ordinary contract-call transactions (any `TriggerSmartContract`/create-contract broadcast that consumes energy), not just privileged administration.

### Impact Explanation
If `totalEnergyWeight` (accumulated from all frozen-for-energy balances chain-wide) is ever zero or negative — e.g., in edge/degenerate network states, right after genesis, or following mass unfreeze — any subsequent contract execution that triggers `calculateGlobalEnergyLimit` (used to determine an account's available energy before executing TVM code, called from `useEnergy`/`getEnergyLimit` style flows) will throw an uncaught `java.lang.ArithmeticException` (division by zero, or in double math produce `Infinity`/`NaN` corrupting the derived energy limit for that account). An uncaught arithmetic exception surfacing from deep inside VM resource accounting during transaction processing is a denial-of-service risk to block/transaction processing for any account attempting a contract call at that moment, and the `assert` is a no-op in default node deployments (`-da`) so it provides no actual protection in production.

### Likelihood Explanation
`totalEnergyWeight`/`totalNetWeight`/`totalEnergyLimit` are protocol-wide accumulated values maintained through freeze/unfreeze and governance-adjustable proposals; they are not attacker-directly-settable, so triggering the exact zero condition requires a specific network state (e.g., very early chain state, or all energy-frozen balances withdrawn network-wide) rather than a single malicious transaction. This bounds likelihood to "requires an unusual, but reachable, chain state" rather than a trivially attacker-triggerable per-transaction bug — lower likelihood than the original Solidity report (where a single call's parameters directly zero the denominator), but the code pattern (relying on a disabled `assert` instead of a real guard, while a parallel implementation in `EnergyProcessor` explicitly guards the same computation) indicates an inconsistent/incomplete fix.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check (mirroring `EnergyProcessor.calculateGlobalEnergyLimit`'s `if (totalEnergyWeight <= 0) return 0;`), and add equivalent runtime guards for `totalLimit`/`totalWeight` in `usageToBalance` before performing either the BigInteger or double division, returning a safe default (e.g., `0`) instead of allowing an unguarded division.

### Proof of Concept
Not independently reproducible from the report alone — I could not verify from the indexed code whether `totalEnergyWeight` can, under current mainnet/testnet governance parameters, actually reach exactly `0` at a point where a contract call would invoke this path (this would require deeper runtime/state analysis, e.g., via a Devin session with full repo/test access, to confirm feasibility and construct an exact reproduction scenario). The code-level defect (division guarded only by a disabled `assert`, inconsistent with the equivalent `EnergyProcessor` guard) is confirmed by direct citation above.
