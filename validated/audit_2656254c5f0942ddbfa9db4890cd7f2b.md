### Title
Stale DON authorization: in-flight `ServerRequest`s retain execution rights for a workflowDON after it is removed via `SetConfig` - ([File: core/capabilities/remote/executable/server.go])

### Summary
`server.Receive` validates `msg.CallerDonId` against `cfg.workflowDONs` only when a `ServerRequest` is first created for a given `requestID`; once created, the `ServerRequest.callingDon` binding is fixed and every subsequent message routed to that `requestID` skips the DON-membership check entirely. A `SetConfig` call that removes a DON (rotation/revocation) therefore has no effect on requests already in flight for that DON, allowing members of a de-registered DON to keep contributing quorum messages and trigger `executeRequest`/`capability.Execute` after their DON has been revoked.

### Finding Description
In `server.Receive` [1](#0-0) , the DON-membership check `callingDon, ok := cfg.workflowDONs[msg.CallerDonId]` is only executed inside the `if _, ok := r.requestIDToRequest[requestID]; !ok` branch, i.e. only the first time a given `requestID` is seen. Once a `request.ServerRequest` is created via `request.NewServerRequest(... callingDon ...)`, the `callingDon` value is copied into the `ServerRequest` struct [2](#0-1)  and is never re-checked against the live `cfg`.

For every subsequent message with the same `requestID`, `Receive` simply looks up the already-created `reqAndMsgID` and calls `reqAndMsgID.request.OnMessage(ctx, msg)` [3](#0-2) . `OnMessage` -> `addRequester` only checks membership against the captured `e.callingDon.Members` [4](#0-3) , and once `F+1` requesters from that same (now possibly revoked) DON are collected, `executeRequest` runs the underlying capability using the stale `callingDon.ID` [5](#0-4) .

`SetConfig` performs an atomic `r.cfg.Store(...)` that swaps in a new `dynamicServerConfig` (including a new `workflowDONs` map) [6](#0-5) , but it never touches `r.requestIDToRequest`, so any `ServerRequest` created under the old config keeps running with the old `callingDon` binding until it times out (`Expired`/`Evictable`, bounded by `RequestTimeout`) or reaches quorum — whichever happens first. There is no re-validation path that aborts or re-authorizes in-flight requests when the owning DON is removed.

### Impact Explanation
A workflow DON that is removed from `cfg.workflowDONs` (e.g., during a legitimate rotation or in response to a suspected compromise of that DON) does not immediately lose the ability to have its already-in-flight `Execute` requests fulfilled. Any remaining honest-looking traffic from members of the revoked DON that arrives for a `requestID` created before the swap will still be aggregated and, once quorum is reached, will invoke `capability.Execute` on the node's underlying capability. This is unauthorized/stale-authorization capability execution: the node executes on behalf of a DON that the operator has explicitly de-registered, undermining the intended access-control invariant that DON removal immediately revokes execution rights.

### Likelihood Explanation
Exploitability requires: (1) at least one message for a given `requestID` reaching the server before the DON is removed (so a `ServerRequest` object is created and cached), and (2) enough additional messages from members of the now-removed DON (up to `F+1` total) arriving afterward, within the `RequestTimeout` window, to reach quorum. Since DON members retain valid p2p identities/keys until fully decommissioned at the transport layer, and the request stays cached until `Expired`/`Evictable`, this is realistically reproducible during any DON rotation window, not a rare race — it is a deterministic property of the code (no re-check exists), only bounded by timing relative to `RequestTimeout`.

### Recommendation
Re-validate DON membership on every message, not just at `ServerRequest` creation: in `server.Receive`, check `cfg.workflowDONs[msg.CallerDonId]` (reloading `cfg` fresh) even for existing `requestID`s, and/or have `SetConfig` proactively cancel/evict any cached `requestIDToRequest` entries whose `callingDon.ID` is no longer present in the new `workflowDONs` map before storing the new config.

### Proof of Concept
Integration test in `core/capabilities/remote/executable`:
1. Call `SetConfig` with `workflowDONs = {X: donX}` where `donX.F = 1` (needs 2 members for quorum).
2. Send one `Execute` message from `donX` member A via `server.Receive` — this creates a `ServerRequest` cached under `requestID`.
3. Call `SetConfig` again with a `workflowDONs` map that no longer contains DON `X`.
4. Send a second `Execute` message with the same `requestID`/message hash from `donX` member B via `server.Receive`.
5. Assert that `capability.Execute` (mock) IS invoked and a success response is dispatched to members A and B — demonstrating that quorum was reached and the request executed using the DON binding captured before revocation, despite `X` no longer being present in the current `cfg.workflowDONs`.
6. Expected secure behavior (currently failing): the second message should be rejected or the request should be aborted with `types.Error_UNAUTHORIZED`/similar once DON `X` is no longer registered.

func NewServerRequest(capability capabilities.ExecutableCapability, method string, capabilityID string, capabilityDonID uint32,

	dispatcher types.Dispatcher, requestTimeout time.Duration, capMethodName string,
	workflowDONBindingGate limits.GateLimiter, lggr logger.Logger) (*ServerRequest, error) {

		workflowDONBindingGate:  workflowDONBindingGate,

func (e *ServerRequest) executeRequest(ctx context.Context, msg *types.MessageBody, method executeFn) {
	ctxWithTimeout, cancel := context.WithTimeout(ctx, e.requestTimeout)
	defer cancel()

	success := false
	start := time.Now()
	responsePayload, err := method(ctxWithTimeout, e.lggr, e.capability, msg.Payload, e.callingDon.ID, e.workflowDONBindingGate)
	if err != nil {
		e.setError(types.Error_INTERNAL_ERROR, err.Error())
	} else {
		success = true
		e.setResult(responsePayload)
	}

	e.metrics.countExecution(ctx, success)
	e.metrics.recordExecutionDuration(ctx, time.Since(start), success)
}

func (e *ServerRequest) addRequester(from p2ptypes.PeerID) error {
	fromPeerInCallingDon := slices.Contains(e.callingDon.Members, from)

	if !fromPeerInCallingDon {
		return fmt.Errorf("request received from peer %s not in calling don", from)
	}

	if e.requesters[from] {
		return fmt.Errorf("request already received from peer %s", from)
	}

	e.requesters[from] = true

	return nil
}
