### Title
Reserve fee (protocol yield cut) is silently skipped when `accrue` is paused, letting deposits/redeems/repayments pass through at a stale index instead of reverting - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vault contracts)

### Summary
Every Zest vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` counterparts) charges a protocol reserve fee on every interest accrual by minting `treasury-lp` vault shares to `.dao-treasury` inside `accrue`. However, when the vault's `accrue` pause flag is active, `accrue` takes a "pass-through" branch that returns the old, frozen `index`/`lindex` and skips the entire fee-minting logic instead of reverting. Every state-changing entrypoint (`deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan`) calls `accrue` first and then proceeds using the (possibly stale) index regardless of whether the fee was actually minted. This mirrors the M-04 pattern of "one code path deducts the protocol fee, the structurally identical path does not" — except here the two paths are the unpaused-accrue branch (fee charged) and the paused-accrue branch (fee free-pass) of the same function.

### Finding Description
`accrue` in the vault contracts is defined as: [1](#0-0) 

```clarity
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                ...
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            ...
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            ...
            (ok { index: next, lindex: nliq })))))
```

- On the **unpaused** path, every unit of interest accrued (`debt-delta`) is split between suppliers and the DAO treasury via `reserve-inc` → `treasury-lp` → `ft-mint? zft treasury-lp .dao-treasury`.
- On the **paused** path, the function returns immediately with the *old* `index`/`lindex` — `last-update` is not advanced, `index`/`lindex` are not advanced, and, critically, no `treasury-lp` is ever minted for that call.

Every economically meaningful entrypoint invokes `accrue` unconditionally as its first step and then continues to operate using whatever `index`/`lindex` value `accrue` returned, e.g.: [2](#0-1) 

```clarity
(define-public (system-repay (amount uint))
  (let (
        (states (var-get pause-states))
        (u (try! (accrue)))
        (scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        ...
```

`deposit`/`redeem` similarly call `(u (try! (accrue)))` and then use `convert-to-shares-preview`/`convert-to-assets-preview`, which are themselves built on `total-assets-preview`, itself dependent on the (possibly stale) `index`: [3](#0-2) 

Because the "PAUSED" branch is a **pass-through instead of a revert**, none of `deposit`, `redeem`, `system-repay`, or `system-borrow` are blocked while `accrue` is paused — they simply keep running against the frozen index, and the reserve-fee mint for that call is unconditionally skipped rather than deferred to a later, correctly-accounted call. This is the direct analog of the Putty bug: the "withdraw" (call) path deducts the fee, the "exercise" (put) path does not, even though both move the same kind of value — here, the "unpaused-accrue" path mints the fee, the "paused-accrue" path does not, even though both are reached by identical calls to the same public function from the same set of callers.

### Impact Explanation
This lands on the in-scope **temporary freezing of unclaimed yield/royalties** impact class (and, depending on how much of `principal-scaled`/`total-supply` shifts during the paused window via `deposit`/`redeem`/`system-repay` executed at the stale index, potentially a **permanent** loss of a slice of the DAO's `fee-reserve` cut): any interest that accrues, and is then extracted or diluted by users transacting during the paused window, is a real economic value transfer for which the protocol's designed reserve-fee cut (`fee-reserve` / `treasury-lp` mint to `.dao-treasury`) is never captured for that specific slice of interest, because `treasury-lp` is calculated as a function of `total-supply` and `total-assets-preview` *at the moment `accrue` successfully runs* — any supply/asset changes that happen via calls serviced by the pass-through branch are not retroactively taxed once accrual resumes.

### Likelihood Explanation
The trigger condition (`accrue` pause flag set) is a legitimate, admin-controlled protocol state (e.g., used during an emergency or maintenance window), not something an external attacker can set unilaterally. However, once that window exists, ANY user can trigger the fee-skipping path with an ordinary, permissionless call to `deposit`, `redeem`, or (if authorized as market) `system-repay`/`system-borrow` — no DAO compromise or privileged access is needed to exploit the window itself, only to observe that `pause-states.accrue` is true. Given pauses of this kind are a normal operational tool (not a rare edge case), and the "pass-through instead of revert" design is applied uniformly across every vault, the exposure window recurs each time accrual is paused for any operational reason.

### Recommendation
When `accrue`'s pause flag is active, either:
1. **Revert** state-changing calls that depend on an up-to-date index (`deposit`, `redeem`, `system-borrow`, `system-repay`) instead of allowing them to pass through with a stale index and a skipped fee, or
2. Persist the "owed" reserve fee amount (or the timestamp/`debt-delta` baseline) across the pause so that the very next successful `accrue()` call retroactively captures the reserve-fee cut for the entire elapsed interval, not just the interval since the pause was lifted.

### Proof of Concept
1. DAO/admin sets `pause-states` with `accrue: true` on `vault-stx` (or any vault) via the pause-setting entrypoint (legitimate operational action, not a compromise).
2. Time passes; interest accrues economically (per the interest-rate curve) but the vault's on-chain `index`/`lindex`/`last-update` remain frozen because every `accrue()` call now hits: [4](#0-3) 
3. A user calls `redeem` (or, if permitted, `system-repay`) on the vault. `redeem` calls `(u (try! (accrue)))`, which returns the stale `{index, lindex}` without minting `treasury-lp` to `.dao-treasury`, then proceeds to burn shares / transfer underlying using `convert-to-assets-preview`, which is computed from `total-assets-preview` built on the frozen `index`. [5](#0-4) 
4. Because the reserve-fee mint never ran for this call, the DAO treasury did not receive its `fee-reserve` cut of whatever interest effectively "existed" for the shares that were just redeemed/repaid.
5. When the pause is lifted and `accrue()` runs normally again, `treasury-lp` is calculated only from the `debt-delta` observed going forward, against the (now-changed) `total-supply`/`total-assets-preview` — the fee corresponding to the value moved during the paused window is never retroactively captured.

Note: I was unable to fully verify, due to running out of tool-call iterations, whether `next-index`/`next-liquidity-index` (which I could not open in the final pass) use `last-update` in a way that fully "catches up" all interest after unpausing or whether some of it is unrecoverable — this affects whether the impact is a temporary delay or a permanent loss of the specific fee slice. I recommend a Devin session or manual review of `next-index`/`next-liquidity-index`/`last-update` usage in `v0-vault-stx.clar` to confirm the exact permanence of the fee loss before finalizing severity.

        (states (var-get pause-states))
        (u (try! (accrue)))

        (idx (var-get index))
        (debt (total-debt))
        (total-borrowed-amount (var-get total-borrowed))
        (capped-amount (if (> amount debt) debt amount))
        (principal-reduction (calc-principal-ratio-reduction capped-amount scaled-principal debt))
        (capped-reduction (if (> principal-reduction scaled-principal) scaled-principal principal-reduction))
        (updated-scaled-principal (- scaled-principal capped-reduction))
        (principal-repaid (mul-div-down capped-amount total-borrowed-amount debt))
        (interest-paid (- capped-amount principal-repaid))
        (total-borrowed-new (if (> total-borrowed-amount principal-repaid) (- total-borrowed-amount principal-repaid) u0)))

    (try! (check-caller-auth))
    (asserts! (not (get repay states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-underlying capped-amount tx-sender))
    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed total-borrowed-new)
