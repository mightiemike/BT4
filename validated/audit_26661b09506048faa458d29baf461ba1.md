There is no `MsgRetryOutbound` / un-abort path in the codebase — once `AbortOutbound` sets `Status_ABORTED`, that outbound has no on-chain recovery mechanism at all. Given that, and the analysis of the refund/re-mint path, here is my assessment.

### Title
Push-based PRC20 re-mint on failed outbound revert has no on-chain recovery path, causing permanent freeze of bridged funds - (File: x/uexecutor/keeper/outbound.go)

### Summary
`handleFailedOutbound` re-mints bridged PRC20 tokens back to a revert recipient by calling `CallPRC20Deposit` [1](#0-0) . If that EVM call fails for any reason, the outbound is irreversibly marked `Status_ABORTED` "for manual intervention" [2](#0-1) , and there is no `Msg` or code path anywhere in the module to retry, resubmit, or otherwise recover an `ABORTED` outbound.

### Finding Description
This is the same push-based-refund bug class as the KIM report: a synchronous, best-effort token transfer is used to return funds, and any revert of that transfer (blacklist, cap, malicious/reverting recipient contract, or any other on-chain condition) is treated as terminal failure with no escape hatch.

- `recipient`/`refundRecipient` in both `handleFailedOutbound` and `applyGasRefund` is taken from `outbound.RevertInstructions.FundRecipient`, which is populated directly from the `Inbound.RevertInstructions.FundRecipient` field supplied by the source-chain event/user [3](#0-2) . This value is attacker/user controlled.
- `CallPRC20Deposit` calls `depositPRC20Token` on the `UNIVERSAL_CORE` handler contract with that recipient [4](#0-3) .
- If the mint reverts (e.g., PRC20 supply/liquidity cap exceeded, a malicious/blacklisting PRC20 implementation, or a recipient that reverts via a token hook), `handleFailedOutbound` calls `AbortOutbound`, which sets `Status_ABORTED` and removes the entry from `PendingOutbounds` [5](#0-4) .
- Per the module's own status documentation, `ABORTED` means "Finalization or revert attachment failed and requires manual intervention" [6](#0-5) .
- Grepping the whole module for any abort-recovery message (`MsgRetryOutbound`, un-abort, reprocess) returns nothing — the `ABORTED` state is a dead end in the `UniversalTx` append-only model.

Compared to the identical pattern in the rescue-funds flow, where a `REVERTED` rescue outbound can be retried via a fresh `AttachRescueOutboundFromReceipt` call [7](#0-6) , `ABORTED` outbounds created inside `handleFailedOutbound` have no equivalent retry path.

### Impact Explanation
Once an outbound hits `ABORTED`, the bridged PRC20 amount is effectively frozen — no automated or user-initiated on-chain mechanism exists to complete the mint or reroute the funds. However, the recipient of this re-mint is the very inbound's own `RevertInstructions.FundRecipient`/`Sender` (i.e., the original depositor's chosen address), so the party best positioned to trigger the abort condition (by choosing/deploying a reverting recipient or being blacklisted on the PRC20) is generally freezing only their own funds, not another user's or the protocol's funds. This limits the blast radius versus the original KIM report, where the attacker's bid froze the *seller's* NFT. I could not confirm within the available index whether the PRC20 contract implementation (Solidity source not indexed) contains any blacklist/pausable/cap logic that a third party could weaponize against someone else's revert recipient, which would elevate this to affecting another party's funds.

### Likelihood Explanation
Low-to-moderate. This requires either (a) a PRC20 token config that enforces a supply/liquidity cap that the re-mint would exceed, (b) a recipient contract designed to revert on receiving tokens, or (c) some blacklist-style restriction implemented at the PRC20/handler level — none of which I could confirm exist in the currently indexed PRC20/handler Solidity source. The Go-side control flow itself is real and reachable by an ordinary, unprivileged inbound sender who sets their own `RevertInstructions.FundRecipient`.

### Recommendation
Add an on-chain recovery message (analogous to the rescue-funds retry flow) that allows re-attempting the PRC20 mint for `ABORTED` outbounds with a fresh/alternate recipient, instead of leaving `ABORTED` as a permanent terminal state requiring off-chain admin action. Consider also validating `RevertInstructions.FundRecipient` at inbound-validation time (basic bytecode/EOA sanity check) to reduce the likelihood of a doomed re-mint at revert time.

### Proof of Concept
Not fully constructible from the indexed code alone: the trigger depends on the PRC20/UniversalCore contract's Solidity logic (cap enforcement, blacklist, or hook behavior), which is not present in this repository's indexed contents (it lives in `push-chain-core-contracts`). I could not verify a concrete on-chain condition that makes `depositPRC20Token` revert for an attacker-chosen `target`, so I cannot provide a complete, verified PoC from this repo alone. Due to index size limits, some contract source files may not be available — a full Devin session with access to the linked `push-chain-core-contracts` repo would be needed to confirm whether such a revertible mint condition exists.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
