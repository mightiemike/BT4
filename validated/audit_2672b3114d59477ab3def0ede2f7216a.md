### Title
Per-endpoint permit held during unbounded global RateLimiter.acquire() wait enables starvation DoS of GlobalPreemptibleAdapter-protected endpoints - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/RateLimiterInterceptor.java])

### Summary
`interceptCall` acquires the per-endpoint permit (e.g. a `GlobalPreemptibleAdapter` semaphore, often `permit=1`) before calling `GlobalRateLimiter.acquirePermit(runtimeData)`, and only releases that permit after the global call returns. In blocking mode the global call can block for an unbounded, queue-dependent time, so the scarce per-endpoint semaphore slot is held the entire time, starving all other legitimate callers of that same endpoint even though the endpoint itself is not overloaded.

### Finding Description
In `RateLimiterInterceptor.interceptCall`, the order is:
```
boolean perEndpointAcquired = rateLimiter == null || rateLimiter.acquirePermit(runtimeData);
boolean acquireResource = perEndpointAcquired && GlobalRateLimiter.acquirePermit(runtimeData);
``` [1](#0-0) 

For a `GlobalPreemptibleAdapter`-backed endpoint, `rateLimiter.acquirePermit()` in blocking mode calls `GlobalPreemptibleStrategy.acquire()`, which does `sp.tryAcquire(DEFAULT_ACQUIRE_TIMEOUT, TimeUnit.SECONDS)` — bounded to 2 seconds — to obtain the semaphore permit itself. [2](#0-1) 

Once that permit is acquired, the same call thread then invokes `GlobalRateLimiter.acquirePermit(runtimeData)`, which in blocking mode calls `acquire()`, which in turn calls the per-IP Guava `RateLimiter.acquire()` and then the node-wide `RateLimiter.acquire()`. [3](#0-2) 

Guava's `RateLimiter.acquire()` has **no timeout** — it blocks (uninterruptibly) until a token is available, and under sustained oversubscription its wait time grows with queue depth without bound. The per-endpoint semaphore permit obtained earlier is only released later — either in the rejection branch (if the global check fails) or in `onComplete`/`onCancel`/the exception handler once the RPC completes. [4](#0-3) 

Because the semaphore is acquired *before* the potentially-unbounded global wait and not released until after it, the endpoint's own configured concurrency (e.g. `permit=1`) is effectively throttled to whatever rate the global limiter's queueing delay allows, independent of the endpoint's actual configured capacity. Meanwhile, other legitimate callers to the same endpoint will time out on the semaphore after only 2 seconds (`DEFAULT_ACQUIRE_TIMEOUT`) and get `RESOURCE_EXHAUSTED`, even though the true bottleneck is unrelated global QPS congestion, not the endpoint itself. The identical pattern also exists in `RateLimiterServlet.service()` for HTTP-facing endpoints. [5](#0-4) 

No auth, accounting, or cost guard mitigates this: any unprivileged caller of a gRPC/HTTP API can trigger it purely with public traffic volume.

### Impact Explanation
An attacker who can saturate the node-wide global QPS limiter (via any combination of public API/gRPC/JSON-RPC calls, which requires no privilege) can, with a small additional burst of calls to a `GlobalPreemptibleAdapter`-protected endpoint (commonly configured with `permit=1`), cause that endpoint's sole/limited semaphore slot(s) to be held for the full duration of the global queueing delay. This starves all subsequent legitimate callers to that specific endpoint, denying them service (`RESOURCE_EXHAUSTED`) even though the endpoint's own per-endpoint limiter was never actually the constraint. This is a resource-ordering-induced availability/DoS issue scoped to specific rate-limited RPC/HTTP methods, not a value-theft or consensus issue.

### Likelihood Explanation
Requires: (1) `rate.limiter.apiNonBlocking = false` (the default), (2) at least one RPC/HTTP method configured with `GlobalPreemptibleAdapter` (default is empty in `config.conf`, so this only applies to operator-enabled deployments that use this strategy), and (3) the ability to saturate node-wide global QPS (default 50000, or lower if operator-tuned) via legitimate unauthenticated traffic. Given these preconditions, the starvation is deterministic and repeatable — it is a structural property of the acquire ordering, not a race that depends on timing luck.

### Recommendation
Invert or bound the acquisition order so the potentially-unbounded wait never occurs while holding the scarce local resource: e.g. attempt the global permit first (or with a bounded timeout), and only then attempt the per-endpoint permit; or make `GlobalRateLimiter.acquire()` timeout-bounded (mirroring `GlobalPreemptibleStrategy`'s 2-second bound) so the per-endpoint permit cannot be held indefinitely waiting on global capacity.

### Proof of Concept
```java
// Sketch integration test (framework/src/test/java/org/tron/core/services/ratelimiter/)
@Test
public void perEndpointPermitHoldTimeScalesWithGlobalDelay() throws Exception {
  // 1. Configure endpoint with GlobalPreemptibleAdapter, permit=1.
  IPreemptibleRateLimiter perEndpoint = new GlobalPreemptibleAdapter("permit=1");
  container.add(KEY_RPC, METHOD_NAME, perEndpoint);

  // 2. Mock GlobalRateLimiter.acquirePermit to simulate a long queueing delay
  //    (representative of global QPS saturation by unrelated traffic).
  try (MockedStatic<GlobalRateLimiter> globalMock = mockStatic(GlobalRateLimiter.class)) {
    globalMock.when(() -> GlobalRateLimiter.acquirePermit(any())).thenAnswer(inv -> {
      Thread.sleep(5000); // simulate global congestion delay
      return true;
    });

    // Thread A: first caller grabs the sole per-endpoint permit, then blocks 5s on global.
    Thread holder = new Thread(() -> interceptor.interceptCall(call, headers, next));
    holder.start();
    Thread.sleep(200); // ensure holder has acquired the semaphore permit

    // Thread B: legitimate second caller to the SAME endpoint.
    long start = System.currentTimeMillis();
    interceptor.interceptCall(call2, headers, next2); // should fail after ~2s (DEFAULT_ACQUIRE_TIMEOUT)
    long elapsed = System.currentTimeMillis() - start;

    // Assert: caller B is rejected (RESOURCE_EXHAUSTED) despite the endpoint's own
    // rate never being exceeded, and elapsed time is bounded by the semaphore
    // timeout (~2s), not by the endpoint's true capacity — demonstrating the
    // per-endpoint permit was unavailable purely because of unrelated global delay.
    verify(call2).close(argThat(s -> s.getCode() == Status.Code.RESOURCE_EXHAUSTED), any());
    assertTrue(elapsed < 3000); // rejected well before holder's 5s global wait completes
    holder.join();
  }
}
```
Expected result: caller B is starved/rejected purely due to global congestion despite never exceeding the endpoint's own configured limit, confirming the per-endpoint permit-holding time is governed by global queueing delay rather than the endpoint's own capacity.

  public boolean acquire() {
    try {
      return sp.tryAcquire(DEFAULT_ACQUIRE_TIMEOUT, TimeUnit.SECONDS);
    } catch (InterruptedException e) {
      // Restore the interrupt flag and reject — caller must not release a permit
      // it never acquired.
      logger.error("acquire permit with error: {}", e.getMessage());
      Thread.currentThread().interrupt();
      return false;
    }
  }
