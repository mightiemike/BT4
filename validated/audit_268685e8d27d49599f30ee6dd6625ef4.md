### Title
Hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` compiled into the ETH Wallet Contract causes silent transfer failure while the relayer fee is already paid - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract (NEP-518, used by ETH-implicit accounts) hardcodes the account ID of the "Address Registrar" contract at compile time via `include_str!` and calls it unconditionally whenever an emulated base-token transfer targets another eth-implicit account with `address_check: Some(address)`. If this baked-in account ID is wrong, stale, or does not correspond to a deployed registrar on the chain the WASM is shipped to, every such transfer's registrar lookup will fail, aborting the intended action — but the relayer fee, which is scheduled independently and unconditionally earlier in the same call, is still paid.

### Finding Description
`ADDRESS_REGISTRAR_ACCOUNT_ID` is baked into the contract binary at build time: [1](#0-0) 

It is parsed and used, with a hard panic if invalid, to build a cross-contract call to the registrar's `lookup` method whenever the transaction is an `EOABaseTokenTransfer` with `address_check: Some(address)`: [2](#0-1) 

Separately from that address-check promise, `inner_rlp_execute` unconditionally schedules a **relayer fee refund** the moment the transaction is parsed, independent of whether the address-check promise (and thus the underlying transfer) will ultimately succeed: [3](#0-2) 

If the registrar call fails (e.g., because the hardcoded account does not exist, was never deployed on that network, or points to an incorrect/legacy value baked into the WASM for a given chain — mirroring the external report's "hardcoded oracle address does not exist on the deployment chain" bug class), `address_check_callback` simply returns a failure response without reverting the already-issued fee transfer: [4](#0-3) 

Separate WASM artifacts are built per-chain (mainnet/testnet/localnet) by `build.rs`, each embedding whatever `ADDRESS_REGISTRAR_ACCOUNT_ID` file value happened to be present at build time: [5](#0-4) 
And the runtime loads these precompiled per-chain WASM blobs directly as the code for ETH-implicit accounts: [6](#0-5) 

Because the registrar account ID is a compile-time constant baked into an already-deployed, non-upgradable contract binary (there is no admin setter, matching the original report's recommendation gap), any mismatch between the embedded value and the actually-deployed registrar for that chain will make the lookup call permanently fail for that WASM version.

### Impact Explanation
Every fee-bearing `EOABaseTokenTransfer` targeting another eth-implicit account goes through this registrar check. If the hardcoded registrar account is wrong for the deployment chain (build artifact mismatch, chain-specific misconfiguration, or the registrar account is later migrated/redeployed at a different ID without updating already-shipped WASM), users signing such transactions will have their fee paid to the relayer via the unconditional refund promise while the base-token transfer itself always fails at the `address_check_callback` step. This is a concrete unauthorized value movement: the relayer/protocol extracts a fee for a transaction that never executes its intended effect, and repeated relayer submissions can extract fees from the same user for a permanently-failing eth-to-eth transfer path, effectively freezing that transaction type for all ETH-implicit users on the affected deployment.

### Likelihood Explanation
Likelihood depends entirely on whether the hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` value embedded in the shipped `wallet_contract_mainnet.wasm` / `wallet_contract_testnet.wasm` / `wallet_contract_localnet.wasm` binaries matches the actually deployed registrar contract on that chain at the time the Wallet Contract global code was activated. Because the value is copied into per-chain resource files during the build process (`build.rs`) and there is no on-chain mechanism to update it once the global contract hash is fixed and adopted by ETH-implicit accounts, any registrar redeployment, migration, or build/config error before finalizing the mainnet build makes this reachable by any relayer/user simply by submitting an eth-emulated base-token transfer to another eth-implicit account with a non-zero fee — a fully unprivileged, routine action.

### Recommendation
- Verify at release time that the compiled `ADDRESS_REGISTRAR_ACCOUNT_ID` for each chain-specific WASM artifact (mainnet/testnet/localnet) matches the actually deployed Address Registrar account on that chain.
- Avoid unconditionally paying the relayer fee before the address-check/registrar lookup succeeds; either chain the fee-refund promise after a successful address check, or make the refund conditional/reversible on failure of the lookup, so relayers cannot collect fees for permanently-failing transfers.
- Consider making the registrar account configurable via a controlled upgrade path (e.g., new global contract hash rollout with migration) rather than solely relying on a compile-time constant with no update mechanism, consistent with the original report's recommendation to add an admin-settable oracle/registrar address.

### Proof of Concept
1. Deploy (or have deployed) the Wallet Contract global code on a chain where the embedded `ADDRESS_REGISTRAR_ACCOUNT_ID` account does not exist or is not the running Address Registrar (e.g., due to a stale build artifact).
2. An eth-implicit account owner signs an `EOABaseTokenTransfer` Ethereum transaction targeting another eth-implicit account, with `address_check: Some(address)` set (as constructed by `internal::parse_rlp_tx_to_action`) and a non-zero relayer fee.
3. A relayer submits `rlp_execute` with this transaction. `inner_rlp_execute` immediately schedules the fee-refund promise to the relayer's account: [7](#0-6) 
4. The address-registrar lookup promise (built from the hardcoded, non-existent account) fails; `address_check_callback` receives `PromiseResult::Failed` and returns an error response without the intended transfer occurring: [4](#0-3) 
5. Net effect: the relayer receives the fee, the user's base-token transfer never happens, and this repeats for every such transaction on that deployment until the WASM is redeployed with a corrected registrar ID.
