### Title
Zero-cost zk-SNARK verification DoS via unbounded shielded transaction spam - ([File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java])

### Summary
`ShieldedTransferActuator.checkProof` runs the full `librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` verification pipeline during `validate()`, memoizing the result in `ZKProofStore` keyed by transaction id [1](#0-0) . Because `BandwidthProcessor.consume` explicitly skips fee/bandwidth accounting for `ShieldedTransferContract`, and the actuator's own shielded fee is only deducted inside `execute()` (which never runs if `validate()` throws), an attacker can force this expensive cryptographic verification to run repeatedly at essentially zero cost by submitting many syntactically valid but doomed-to-fail shielded transactions with distinct transaction ids.

### Finding Description
`checkProof` is invoked from `validate()` [2](#0-1) . It first checks `ZKProofStore.has(tx.getTransactionId())`, but for a fresh/unique txid this always misses, so the full check runs: `librustzcashSaplingCheckSpend` per spend, `librustzcashSaplingCheckOutput` per receive, and `librustzcashSaplingFinalCheck` [3](#0-2) . Any failure throws `ZkProofValidateException`, which is caught in `validate()` and recorded as a negative cache entry keyed by that (now-useless, never-to-be-resubmitted) txid [4](#0-3) . Since txid is derived from the full transaction content (including expiration/ref_block fields), an attacker trivially generates unlimited distinct txids, so the cache never protects against fresh submissions.

Critically, before `validate()`/`execute()` even run, `Manager.processTransaction` calls `consumeBandwidth` to charge the standard bandwidth/net fee [5](#0-4) . But `BandwidthProcessor.consume` explicitly skips this fee for `ShieldedTransferContract`:
```java
for (Contract contract : contracts) {
  if (contract.getType() == ShieldedTransferContract) {
    continue;
  }
  ...
``` [6](#0-5) 
This means no bandwidth-based net fee is ever collected for shielded transactions at this stage. The only fee shielded transactions pay is the `ShieldedTransactionFee`/`ShieldedTransactionCreateAccountFee`, which is deducted inside `ShieldedTransferActuator.execute()` via `Commons.adjustAssetBalanceV2(accountStore.getBlackhole(), ...)` [7](#0-6) . `execute()` is only invoked after `validate()` succeeds; if `checkProof` throws (as it always will for a bogus-but-well-formed spend/receive description), `execute()` never runs and no fee whatsoever is charged.

The result: an attacker pays zero bandwidth fee and zero shielded transaction fee for a transaction that forces a full set of Sapling zk-SNARK verification calls (`CheckSpend`, `CheckOutput`, `FinalCheck`) on every node that processes it in mempool/`pushTransaction`.

### Impact Explanation
This enables a CPU-exhaustion DoS at the mempool level: for the cost of just constructing structurally valid (correct byte-length) but cryptographically bogus spend/receive descriptions, an attacker can force every full node to execute the computationally expensive Groth16 verification circuit repeatedly, with no fee collected and no accounting cost incurred, unlike a transparent transaction rejection which at minimum runs signature verification/basic checks priced by bandwidth. Repeated at scale (many distinct txids per batch, e.g. varying `expiration`/`ref_block_bytes`/nonce-like fields), this can degrade validation throughput and delay legitimate transaction processing/block production for the whole network.

### Likelihood Explanation
Preconditions are minimal and match an unprivileged attacker: ability to broadcast a syntactically valid `ShieldedTransferContract` (spend/receive counts within the actuator's limits, correct `ZC_ENCCIPHERTEXT_SIZE`/`ZC_OUTCIPHERTEXT_SIZE`), which does not require real spendable notes — the checks that would need genuine funds (nullifier double-spend, merkle root existence) are separate from the zk-proof correctness check, and constructing a random/garbage but well-formed `zkproof`/`spendAuthoritySignature`/`bindingSignature` byte array is trivial. The transaction is guaranteed to fail at `CheckSpend`/`CheckOutput`/`FinalCheck`, is rejected, never occupies chain state, and costs the attacker nothing due to the bandwidth-fee bypass for shielded contracts. This is fully repeatable and scriptable, requiring only network bandwidth to broadcast many such transactions.

### Recommendation
Charge a minimum bandwidth/net fee (or a dedicated pre-verification fee) for `ShieldedTransferContract` transactions before running `checkProof`, removing or restricting the blanket `continue` bypass in `BandwidthProcessor.consume` for shielded contracts. Additionally, consider performing cheaper, fail-fast structural/format checks before invoking the full librustzcash verification pipeline, and/or rate-limit the number of shielded transactions with unverified proofs a single sender/address can have in flight in the mempool (independent of `shieldedTransInPendingMaxCounts`, which is a global cap, not a per-account anti-spam mechanism) [8](#0-7) .

### Proof of Concept
Java integration test plan (to be run against `Manager`/`ShieldedTransferActuator` similar to existing `framework/src/test/java/org/tron/core/db/ManagerTest.java`):
1. Enable shielded transactions in `DynamicPropertiesStore` (`AllowSameTokenName=1`, `supportShieldedTransaction=true`).
2. Build N `ShieldedTransferContract` transactions, each with one `SpendDescription` (valid anchor via `merkleContainer.merkleRootExist`, valid-size but random `zkproof`/`rk`/`spendAuthoritySignature`/`nullifier`) and one `ReceiveDescription` (correctly sized `cEnc`/`cOut`, random `zkproof`), each with a distinct `expiration` timestamp so txid differs.
3. For each transaction, call `dbManager.pushTransaction(trx)` and assert it throws `ContractValidateException` originating from `librustzcashSaplingCheckSpend error` (confirming full verification ran).
4. Instrument/measure: before pushing, record `AccountCapsule` balances (attacker has none/zero balance) and confirm no balance deduction and `dynamicPropertiesStore.getTotalTransactionCost()` unchanged after each rejected shielded tx — contrast with an equivalent rejected `TransferContract` where `BandwidthProcessor.consume` still charges bandwidth/fee.
5. Wrap the loop with a wall-clock/CPU timer around `JLibrustzcash.librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` invocations (e.g. via a spy/wrapper) to show non-trivial, repeated CPU cost per rejected transaction, while asserting zero SUN was charged, establishing the fee-to-cost ratio described in the finding.
