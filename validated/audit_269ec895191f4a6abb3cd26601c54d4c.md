### Title
TRC10 asset-name creation via `AssetIssueActuator` can be front-run to hijack ownership of an intended asset name - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
`AssetIssueActuator` lets any account broadcast a `CreateAssetIssueContract` transaction that claims a globally unique asset `name` on a strict first-come-first-served basis, with no whitelist, reservation, or commit-reveal scheme. Because the uniqueness check and the ownership assignment happen in two separate, publicly-observable steps (mempool broadcast, then block inclusion), an attacker who sees a pending `createassetissue` transaction for a given name can submit their own transaction for the same name and have it mined first, permanently becoming the recorded "issuer" of that asset. This mirrors the `CoreFactory.createProject` bug: an unpermissioned, identifier-based "create ownership" action that can be front-run to steal ownership of a resource that other users/participants will later transact against.

### Finding Description
`AssetIssueActuator.validate()` only checks that no asset with the given name already exists in `AssetIssueStore` before allowing creation: [1](#0-0) 

`AssetIssueActuator.execute()` then unconditionally assigns issuer ownership of that name to whichever `ownerAddress` transaction wins the race, writing it into both the V1 and V2 stores and into the creator's `AccountCapsule`: [2](#0-1) [3](#0-2) 

Because Tron transactions are broadcast to the P2P network and sit in nodes' pending-transaction pools before being packed into a block by a witness, any anonymous observer of the network can see a pending `createassetissue` transaction (its `name` field is not hidden) and race it with their own transaction for the identical name, exactly the "check name unused → then create" TOCTOU pattern described in the source finding for `createProject`.

Once the attacker's transaction is included first, they become the permanent, canonical "owner" of that asset name — analogous to the CoreFactory attacker becoming "owner of a collection." Downstream, `ParticipateAssetIssueActuator.validate()` requires that a buyer's `toAddress` equal the asset's recorded `ownerAddress`: [4](#0-3) 

and `execute()` then moves the buyer's TRX balance directly to that `toAddress`: [5](#0-4) 

If any party (exchange, wallet, or user) resolves "the issuer of asset X" from on-chain state after the race rather than verifying the specific address out-of-band beforehand, funds sent via `ParticipateAssetIssueContract` for that name are paid to the attacker rather than to the legitimate creator — the same economic outcome (attacker becomes the payee/owner of a named resource that funds are later routed to) as the original `createProject`/`isForSale` scenario.

### Impact Explanation
An attacker can permanently seize a desired/expected TRC10 asset name before its intended creator's transaction confirms, becoming the on-chain "issuer of record." Any subsequent `ParticipateAssetIssueContract` transactions that resolve the target address from that asset name (rather than a pre-verified address) will transfer TRX to the attacker instead of the intended party — unauthorized diversion of funds tied to a specific named resource, matching the "unauthorized account operation / asset accounting corruption" impact class.

### Likelihood Explanation
Likelihood is moderate: the attack requires (a) observing a pending, not-yet-confirmed `createassetissue` transaction for a specific desired name in the mempool, and (b) successfully getting a competing transaction mined first (e.g., via higher energy/fee prioritization or favorable timing). This is fully reachable by any anonymous network participant broadcasting ordinary transactions — no privileged role, leaked key, or malicious node/peer is required — consistent with the required unprivileged-actor, RPC/broadcast-reachable analog.

### Recommendation
- Require a reservation/commit-reveal step for asset name claims (e.g., commit a hash of the name+salt first, then reveal after a delay) so the actual name is not exposed in cleartext in the mempool before ownership is finalized.
- Alternatively, bind asset creation to a signed, address-specific commitment (similar to the ECDSA-signature mitigation cited in the source report) so that only the party who pre-committed to a name can successfully issue it.
- Require consumers of `ParticipateAssetIssueContract` (wallets/exchanges) to hard-verify the intended issuer address out-of-band rather than trusting the on-chain name→owner mapping resolved after asset creation.

### Proof of Concept
1. Victim signs and broadcasts a `CreateAssetIssueContract` transaction with `name = "GOODCOIN"` and their own `ownerAddress`.
2. Attacker observes this transaction in the P2P/mempool layer before it is packed into a block (name field is plaintext, per `AssetIssueContract`).
3. Attacker crafts and broadcasts their own `CreateAssetIssueContract` with the identical `name = "GOODCOIN"` and their own `ownerAddress`, using a fee/priority that gets it included first.
4. `AssetIssueActuator.validate()` (lines 210–214) sees no existing "GOODCOIN" entry (attacker's tx processed first) and passes; `execute()` (lines 68–122) records the attacker as `ownerAddress`/issuer of "GOODCOIN".
5. Victim's original transaction now fails validation ("Token exists") when processed.
6. Any buyer who later sends a `ParticipateAssetIssueContract` for asset name "GOODCOIN" expecting to pay the victim, but resolving `toAddress` from the on-chain issuer record, instead has their TRX transferred to the attacker's account per `ParticipateAssetIssueActuator.execute()` (lines 59–92).
