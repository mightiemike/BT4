### Title
Transaction-backup restore commits attacker-controlled `WriteSet`s without verifying them against `TransactionInfo::state_change_hash` - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
When restoring transactions from a backup, `LoadedChunk::load` reads `(Transaction, PersistedAuxiliaryInfo, TransactionInfo, Vec<ContractEvent>, WriteSet)` tuples from the backup's `transactions` file and calls `txn_list_with_proof.verify(...)`, but the `WriteSet`s are never included in that struct nor in the verification, so a corrupted or maliciously substituted `WriteSet` in the backup file is committed straight to the restored ledger.

### Finding Description
`LoadedChunk::load` deserializes records containing a `WriteSet` for every transaction ( [3](#0-2) ), then builds a `TransactionListWithProof` purely from `txns`, `event_vecs`, and `txn_infos` — deliberately excluding `write_sets` — and calls `.verify()` on it ( [4](#0-3) ). `TransactionListWithProof` ( [1](#0-0) ) has no `write_set` field, and its `verify()` only checks transaction-hash-vs-`TransactionInfo.transaction_hash` and event-root-hash-vs-`TransactionInfo.event_root_hash` ( [5](#0-4) ). It never checks `CryptoHash::hash(&write_set) == txn_info.state_change_hash()`, unlike the sibling type `TransactionOutputListWithProof::verify`, which does perform that exact check ( [2](#0-1) ).

The unverified `write_sets` are then passed straight through to `restore_handler.save_transactions(...)` ( [6](#0-5) ) → `RestoreHandler::save_transactions` ( [7](#0-6) ) → `restore_utils::save_transactions_impl`, which writes them into `WriteSetDb` ( [8](#0-7) ) and, when `kv_replay` is true, feeds them directly into `calculate_state_and_put_updates` to compute and persist the resulting state ( [9](#0-8) ) — with no re-execution or hash check against the cryptographically-committed `state_change_hash` in `TransactionInfo`.

Because `TransactionInfo.state_change_hash` (the write-set commitment) is exactly the field the accumulator proof authenticates transitively via `TransactionInfo::hash()`, but the actual `WriteSet` bytes used to compute state never get hash-checked against that field during restore, this breaks the "VM outputs / write sets must survive executor-to-storage handoff unchanged" and "restore helpers must not reinterpret committed data into a different ledger state" invariants called out in the prompt.

### Impact Explanation
Anyone who can tamper with (or serves a corrupted copy of) the backup blob storage used for `db-restore` — a compromised/malicious backup mirror, a MITM'd unauthenticated transport, or storage-layer bit corruption — can substitute an arbitrary `WriteSet` for any transaction in the segment that is saved directly (versions before `replay_from_version`, i.e., not VM-replayed), while keeping `Transaction`/`TransactionInfo`/events untouched so the ledger-info/accumulator-based `verify()` still passes. The restoring node then persists state that diverges from the true, consensus-committed ledger state at that version, with `get_state_value_by_version` and other API reads at that node silently returning the wrong values bound to a version/root that no longer matches consensus. This is committed-state corruption / a hard-fork-only divergence for any node performing this restore path (a common flow for state-sync bootstrap, disaster recovery, and fast-sync mirrors).

### Likelihood Explanation
Requires an unprivileged/compromised backup storage or MITM'd transport (both realistic given operators frequently restore from public/community-hosted or replicated backup buckets); it doesn't require validator keys or consensus compromise. It only affects the "save directly, no replay" segment of restore (versions before `replay_from_version`), so operators who always request full replay (`kv_only_replay`/`replay_from_version = 0`) are not exposed — but default and partial-replay restores are.

### Recommendation
In `LoadedChunk::load`, before returning, verify `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every `(write_set, txn_info)` pair — mirroring the check already present in `TransactionOutputListWithProof::verify` — and fail the chunk load if any mismatch is found. Alternatively, extend `TransactionListWithProof`/its verify routine to optionally carry and check write sets so this invariant is enforced centrally rather than ad hoc in the backup-restore code path.

### Proof of Concept
1. Take any valid transaction backup chunk (a `TransactionChunk` with its `transactions` file and `proof` file).
2. In the `transactions` file, replace the `WriteSet` bytes of one record with an attacker-chosen `WriteSet` (leaving `Transaction`, `PersistedAuxiliaryInfo`, `TransactionInfo`, and events byte-for-byte identical).
3. Run `aptos-db-tool backup restore transaction ...` (or the equivalent `TransactionRestoreController`) pointing at this tampered manifest/chunk with `replay_from_version` set beyond this chunk's versions (so it's saved directly, not replayed).
4. Observe: `LoadedChunk::load`'s call to `txn_list_with_proof.verify(...)` succeeds (transaction hash and event root hash unaffected), and `restore_handler.save_transactions` persists the attacker's `WriteSet` as the state at that version — `db.get_state_value_by_version` for the affected keys now returns attacker-chosen values instead of the consensus-committed ones, with no error raised anywhere in the restore pipeline.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
