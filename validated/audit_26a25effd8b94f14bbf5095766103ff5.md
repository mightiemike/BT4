### Title
Unbounded, unbounded-growth shop session-id array in `KVSessionStorage.addShopIds` allows repeated re-authentication to permanently blow up `findSessionsByShop` / session lookup (DoS) - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession` records every stored session id into a per-shop index array via `addShopIds`, but that method never checks whether the id is already present before appending it [1](#0-0) . Every time a session for the same shop/user is re-stored — which happens routinely whenever a token-exchange or offline/online session refresh occurs, e.g. on expiry or invalidation — the same session id is pushed into the array again, causing it to grow without bound and without ever being fully cleaned up until every duplicate copy is explicitly deleted.

### Finding Description
`storeSession` writes the session blob under its own key and then calls `addShopIds(session.shop, [session.id])` to append the id to the shop's index list [2](#0-1) . `addShopIds` reads the current array and writes `[...shopIds, ...ids]` back with no `includes()`/dedup check [1](#0-0) . This is the same root-cause pattern as the analog bug (H-03): an array meant to represent one entry per logical actor is instead allowed to accumulate duplicate/stale entries via repeated legitimate operations, and that array is later iterated in full by a critical function — here, `findSessionsByShop`, which does `Promise.all(sessionIds.map(id => loadSession(id)))` over the entire (potentially huge) id list [3](#0-2) .

The Redis adapter that ships alongside it demonstrates the correct pattern was known and intentionally applied there but not in the KV adapter: `addKeyToShopList` explicitly guards with `if (!idKeysArray.includes(idKey))` before pushing [4](#0-3) .

The trigger path requires no privilege beyond a single merchant/customer using the app normally: token-exchange authentication re-stores the offline (and optionally online) session on every request where the current session is missing/expired [5](#0-4) , and the equivalent Express middleware does the same [6](#0-5) . Because the session id used (`offline_{shop}` or `{shop}_{userId}`) is deterministic and stable, each of these re-stores pushes a *duplicate* of an id already in the array — nothing ever removes it except a full `deleteSession`/`deleteSessions` call, which most authentication code paths do not perform on a mere refresh.

### Impact Explanation
`findSessionsByShop` is used by `AppInstallations.includes`/`AppInstallations.delete` in `shopify-app-express` to decide whether a shop is installed and to clean up sessions on uninstall [7](#0-6) . If the per-shop id array has been inflated to a very large size by repeated re-authentication (offline/online token refresh cycles happen routinely, e.g. once per expired session, once per new device/user for online tokens), then `findSessionsByShop` must fetch every duplicated id individually from the KV namespace, causing severe latency, KV rate/limit exhaustion, or effectively permanent failure of session lookup, install-detection, and uninstall cleanup for that shop — a genuine denial-of-service of an authentication/session-storage handler, directly analogous to the OOG DoS described in the original report.

### Likelihood Explanation
High for any app using `@shopify/shopify-app-session-storage-kv` together with the token-exchange authentication strategy (`shopify-app-remix`, `shopify-app-react-router`, or `shopify-app-express`). No malicious intent is even required — routine offline-token expiry/refresh or online per-user session issuance for active users organically grows the array over time; a moderately active or long-lived install could accumulate very large duplicate lists purely through normal usage, and a user who intentionally forces repeated re-authentication (e.g., by repeatedly invalidating/expiring the session token cycle) can accelerate this deliberately.

### Recommendation
In `addShopIds`, deduplicate before writing back (mirror the Redis adapter's `includes()` check), e.g.:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```
Additionally consider bounding/paginating `findSessionsByShop`'s reads (similar to the Prisma adapter's `take: 25` limit [8](#0-7) ) as defense in depth against any residual growth.

### Proof of Concept
1. Configure an embedded app with `future.tokenExchange` enabled and `KVSessionStorage` as the session storage.
2. As a single installed merchant, repeatedly cause the offline (or online) session to be treated as expired/invalid before each request (e.g. wait past `WITHIN_MILLISECONDS_OF_EXPIRY`, or force an authentication error causing `invalidateAccessToken`) and re-issue the session-token request. Each cycle triggers `authenticate()` → `config.sessionStorage!.storeSession(offlineSession)` with the same deterministic id (`offline_{shop}`) [9](#0-8) .
3. After N repetitions, inspect the KV key `shop:{shop}` — it will contain N duplicate copies of the same session id, since `addShopIds` never dedupes [1](#0-0) .
4. Call `findSessionsByShop(shop)` (directly, or indirectly via `AppInstallations.includes`/`delete`) and observe it performs N KV `get` calls for the same session id, with latency/cost scaling linearly with N — demonstrating the DoS vector on session lookup/installation-check logic [3](#0-2) .

    if (idKeysArrayString) {
