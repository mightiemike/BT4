### Title
Missing Slippage Protection in `ExchangeWithdrawActuator` Enables Sandwich Attacks on Liquidity Withdrawal - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeWithdrawContract`, used to withdraw a token pair's liquidity from java-tron's on-chain Bancor-style exchange, has no field allowing the withdrawer to specify a minimum acceptable amount for the counter-token received. `anotherTokenQuant` is computed purely from the exchange pool's current on-chain balances at the moment the transaction executes [1](#0-0) , with zero user-controlled slippage bound — the exact bug class described in the report (minimums fixed with no real protection), except here it is not merely `1`, it is entirely absent from the protocol message.

### Finding Description
The `ExchangeWithdrawContract` protobuf message only carries `owner_address`, `exchange_id`, `token_id`, and `quant` [2](#0-1) . There is no `expected`/minimum-out field, in contrast to the sibling `ExchangeTransactionContract`, which explicitly carries an `expected` field and enforces it during validation:
`anotherTokenQuant < tokenExpected` throws `ContractValidateException("token required must greater than expected")` [3](#0-2) .

`ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` strictly from the current `firstTokenBalance`/`secondTokenBalance` ratio and only checks internal consistency (balance sufficiency, non-zero, and rounding precision) — never a user-supplied floor [4](#0-3) . `execute()` then mutates account balances/assets and the pool balances using this unprotected value [5](#0-4) .

Because `ExchangeTransactionContract` (buy/sell against the same pool) is a fully unprivileged, anonymously broadcastable transaction type, any address can shift `firstTokenBalance`/`secondTokenBalance` immediately before a pending `ExchangeWithdrawContract` is packed into a block, then reverse the trade afterward (sandwich attack) — extracting value from the withdrawer with no on-chain defense available to them, since the protocol provides no way to bound the acceptable withdrawal ratio.

The only access restriction on `ExchangeWithdrawContract` is that the caller must be the exchange's creator [6](#0-5) ; this is ordinary object-ownership, not a privileged chain role, so the attack surface remains: any unprivileged attacker can front-run any ordinary creator's withdrawal via the public `ExchangeWithdrawServlet`/broadcast path [7](#0-6) .

### Impact Explanation
A withdrawing account can be forced to receive a significantly worse ratio of the counter token than the pool state showed when they signed/broadcast the transaction, because there is no `amountAMin`/`amountBMin`-equivalent to reject an unfavorable execution. This is direct asset/accounting corruption for the withdrawer: the actual protocol state after execution (`exchangeCapsule.setBalance`, `accountCapsule.addAssetAmountV2`) reflects the attacker-manipulated price rather than the fair pool ratio at submission time [8](#0-7) .

### Likelihood Explanation
Exploitation only requires an attacker to observe a pending `ExchangeWithdrawContract` in the mempool and submit a higher-fee `ExchangeTransactionContract` trade beforehand — both are standard, fully unprivileged, anonymously broadcastable transaction types with no additional access control beyond normal balance/fee checks [9](#0-8) . No special permissions, keys, or node compromise are needed.

### Recommendation
Add a user-supplied minimum-received parameter (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the transaction if the computed `anotherTokenQuant` (and/or `tokenQuant` in same-token scenarios) falls below the caller's specified floor.

### Proof of Concept
1. Account `A` (exchange creator) broadcasts `ExchangeWithdrawContract{exchange_id=X, token_id=firstToken, quant=Q}` intending to withdraw liquidity based on the current pool ratio `firstTokenBalance:secondTokenBalance`.
2. Attacker `M`, monitoring the mempool, broadcasts an `ExchangeTransactionContract` with a higher energy fee that sells a large amount of `secondToken` into the pool, shifting the ratio unfavorably for `A`'s pending withdrawal, and gets it included first.
3. `A`'s `ExchangeWithdrawContract` executes next; `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the now-manipulated `firstTokenBalance`/`secondTokenBalance` [10](#0-9) , with no floor to reject the bad rate.
4. `M` then submits a reverse `ExchangeTransactionContract` to restore the pool ratio and pocket the value extracted from `A`'s withdrawal — a classic sandwich, made possible solely because `ExchangeWithdrawContract` lacks any slippage-bound field.
