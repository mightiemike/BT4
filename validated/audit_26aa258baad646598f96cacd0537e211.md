### Title
Non-atomic shop→session-id index updates in `KVSessionStorage` allow stale/ghost session references after deletion, enabling a DoS of the app-installation auth handler - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
The Renzo report describes a class of bug where a resource is "removed" from a system's primary bookkeeping (the `collateralTokens` array) while stale references to it (pending withdrawals) still exist elsewhere, causing the system's aggregate accounting (`totalTVL`) to silently diverge from reality. The analogous pattern in `shopify-app-js` is `KVSessionStorage`'s secondary index (`shop -> [sessionId, ...]`), which is maintained via non-atomic read-modify-write operations that race against concurrent `storeSession`/`deleteSession` calls, allowing the index to retain an ID for a session that was already deleted from primary storage — a "ghost" reference that is never accounted for by callers that trust the index.

### Finding Description
`KVSessionStorage.storeSession` and `deleteSession` each call helper methods that maintain a secondary index mapping a shop domain to an array of session IDs: [1](#0-0) 

Both `addShopIds` and `removeShopIds` perform a classic read-then-write without any locking or compare-and-swap: [2](#0-1) 

If a `deleteSession(id)` and a `storeSession(...)` for the same shop execute concurrently (e.g., a legitimate OAuth callback creating/renewing a session for a shop while an `app/uninstalled` webhook is being processed for the same shop, or two concurrent webhook deliveries), the two read-modify-write sequences can interleave such that the write from `addShopIds` (based on a stale read) overwrites the write from `removeShopIds`, re-introducing the just-deleted session ID into the shop index — even though `this.namespace.delete(id)` has already removed the underlying session data. This is exactly the "removed collateral still counted/still referenced" bug class: the primary object is gone, but a secondary structure that should have been kept in sync still references it.

The consequence surfaces in `findSessionsByShop`, which blindly loads every ID in the index and force-unwraps the result: [3](#0-2) 

Since `loadSession` returns `undefined` for the now-nonexistent session, `sessionIds.map(async (id) => (await this.loadSession(id))!)` returns an array containing `undefined`, mistyped as `Session`.

This directly reaches an authentication code path: `AppInstallations.includes()` and `AppInstallations.delete()` (used by `ensureInstalledOnShop` and the `app/uninstalled` webhook handler) call `findSessionsByShop` and then dereference each returned "session": [4](#0-3) 

`session.accessToken` on an `undefined` entry throws a `TypeError`, which is unhandled by the caller.

### Impact Explanation
`AppInstallations.includes()`/`delete()` are invoked from `ensureInstalledOnShop`, an authentication/installation-check middleware that runs on every embedded-app page load for a shop, and from the `app/uninstalled` webhook handler: [5](#0-4) 

Once the shop index contains a ghost ID, every subsequent request that triggers `findSessionsByShop` for that shop throws an uncaught `TypeError`, breaking the auth/installation-check handler for that shop (denial of service) until the index is manually repaired. This qualifies as a DoS of an auth handler reachable via ordinary webhook delivery and normal OAuth/session-storage traffic — no privileged actor or leaked secret is required, only a race between two otherwise-legitimate storage operations for the same shop.

### Likelihood Explanation
`shopify-app-session-storage-kv` is a shipped, documented session-storage adapter (Cloudflare KV backend) intended for production use. Concurrent writes for the same shop are a realistic occurrence: a merchant reinstalling in quick succession, overlapping OAuth/token-exchange retries, or webhook redelivery (Shopify redelivers webhooks on timeout/5xx) can all trigger overlapping `storeSession`/`deleteSession` calls for the same shop key, and KV's eventual-consistency/network-latency characteristics make the read-modify-write race window non-trivial to avoid without explicit synchronization.

### Recommendation
Make the shop→session-id index update atomic (or convergent) instead of a bare read-modify-write:
- Use a KV mechanism that supports optimistic concurrency (e.g., conditional put with a version/ETag check and retry-on-conflict), or
- Store per-session-per-shop keys (e.g., `shop:{shop}:{sessionId}`) and use KV `list()` to enumerate them instead of maintaining a single mutable array, eliminating the read-modify-write race entirely.
Additionally, harden `findSessionsByShop` to filter out `undefined` results from `loadSession` instead of force-unwrapping them, so a stale index entry degrades gracefully rather than crashing callers like `AppInstallations.includes()`/`delete()`.

### Proof of Concept
1. Two requests for the same shop `X` arrive concurrently: request A calls `storeSession(sessionA)` (e.g., OAuth callback), request B calls `deleteSession(sessionB)` for a previously stored session of the same shop (e.g., triggered by `app/uninstalled` webhook via `AppInstallations.delete`).
2. Both `addShopIds`/`removeShopIds` read the same pre-update array `[sessionB.id]` from `namespace.get(shopKey)`.
3. `removeShopIds` writes `[]` (removing `sessionB.id`); shortly after, `addShopIds` (having read the same stale `[sessionB.id]`) writes `[sessionB.id, sessionA.id]` — reintroducing `sessionB.id` even though `namespace.delete(sessionB.id)` already ran.
4. A subsequent request to `ensureInstalledOnShop` for shop `X` calls `findSessionsByShop`, which tries to load `sessionB.id`, gets `undefined`, and `AppInstallations.includes()`'s `session.accessToken` access throws, returning a 500 and blocking the installed-shop check for shop `X`.

  public async loadSession(id: string): Promise<Session | undefined> {
    const sessionData = await this.namespace.get<[string, string | number][]>(
      id,
      'json',
    );
    return sessionData
      ? Session.fromPropertyArray(sessionData, true)
      : undefined;
  }

  public async deleteSession(id: string): Promise<boolean> {
    const session = await this.loadSession(id);
    if (!session) {
      return true;
    }

    await this.namespace.delete(id);
    await this.removeShopIds(session.shop, [session.id]);
    return true;
  }

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async removeShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(
      key,
      JSON.stringify(shopIds.filter((id) => !ids.includes(id))),
    );
  }
