### Title
Unbounded full-table scan of `VotesStore` on every `getPaginatedNowWitnessList` request enables RPC-API denial-of-service - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.getPaginatedNowWitnessList()`, the handler backing the public gRPC method `GetPaginatedNowWitnessList` and the HTTP endpoint `/wallet/getpaginatednowwitnesslist`, calls a private `countVote(VotesStore)` helper that performs a full, unbounded iteration over **every entry** in `VotesStore` on **every single invocation**, regardless of the caller-supplied `offset`/`limit` pagination parameters.

### Finding Description
`getPaginatedNowWitnessList` is intended to be a cheap, paginated read API (limit capped at `WITNESS_COUNT_LIMIT_MAX`), but before applying any pagination it must recompute "real-time" vote counts by calling: [1](#0-0)

This `countVote` walks the *entire* `VotesStore` via `votesStore.iterator()` with no bound, no offset, and no early exit — unlike the analogous `getAllExchanges`/`getAllProposals`/paginated variants which at least page over a bounded range of keys (`chainbase/src/main/java/org/tron/core/store/ProposalStore.java`, `framework/src/main/java/org/tron/core/Wallet.java:3307-3339`). Every entry in `VotesStore` is keyed by voter address and is created/updated whenever *any* account broadcasts a `VoteWitnessContract` (see `VoteWitnessActuator.countVoteAccount`, `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java:152-191`, and the TVM-callable equivalent `VoteWitnessProcessor.execute`). Entries persist and accumulate for the entire epoch and are only cleared in bulk during `MaintenanceManager.doMaintenance()`'s own separate `countVote` (`consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java:165-195`), which runs once per maintenance cycle, not per request.

Because creating a TRON account and casting a vote transaction is cheap (any funded account with any positive frozen/tron-power can vote, and votes can be split across many distinct low-value transactions from many distinct addresses), an attacker can inflate `VotesStore` with a large number of distinct voter entries within a single epoch. Each subsequent call to the public, unauthenticated `getPaginatedNowWitnessList` RPC/HTTP endpoint then forces the full node to re-scan the entire bloated store synchronously inside the request handler — for every request, not just once per epoch.

### Impact Explanation
This is directly analogous to the reported PoolTemplate.sol bug class: an unbounded loop whose iteration count is attacker-influenced and grows over time, driving up resource consumption (here, wall-clock/CPU/disk-IO on the full node) until legitimate calls to this API become slow or effectively unavailable — a denial-of-service against a public RPC-API/HTTP JSON-RPC surface. Because the endpoint is reachable pre-authentication by any client (it is a plain read query, no signature required), and because the underlying work scales with attacker-controllable state (number of distinct voting accounts/transactions in the current epoch) rather than with the caller's requested `limit`, repeated invocation of this endpoint while `VotesStore` is inflated can degrade or stall the node's API-serving thread pool, affecting availability of this and potentially other RPC calls sharing the same gRPC/HTTP thread pools.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to fund a modest number of accounts and issue a moderate number of `VoteWitnessContract` transactions to inflate `VotesStore` within a single epoch (comments in `MaintenanceManager.doMaintenance` and the store clearing behavior show votes accumulate for the whole epoch before being cleared), then repeatedly call the public pagination endpoint. No privileged role or leaked key is required — only ordinary account creation and vote transactions plus unauthenticated read calls.

### Recommendation
- Cache/precompute the epoch's aggregated vote-count deltas once (e.g., update an incremental counter structure as votes are cast, similar to how `WitnessCapsule.voteCount` is already maintained) instead of recomputing via a full store scan on every read request.
- Alternatively, bound the cost of `countVote` per request, e.g., by short-circuiting once a reasonable safety limit of scanned entries is reached, or by moving the aggregation into an incrementally maintained store keyed for O(1)/O(log n) lookup.
- Consider rate-limiting or otherwise protecting this specific RPC/HTTP endpoint given its cost is decoupled from the caller-specified `limit`.

### Proof of Concept
1. Fund N distinct accounts, each with minimal TRX/frozen balance sufficient to cast one vote (`VoteWitnessContract`), and submit N `VoteWitnessContract` transactions from N distinct addresses within a single maintenance epoch, so that `VotesStore` accumulates N entries (`VoteWitnessActuator.countVoteAccount`, `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java:171-190`).
2. Before the next maintenance cycle clears `VotesStore`, repeatedly call the public `GetPaginatedNowWitnessList` gRPC method (`framework/src/main/java/org/tron/core/services/RpcApiService.java`) or the HTTP endpoint served by `GetPaginatedNowWitnessListServlet` (`framework/src/main/java/org/tron/core/services/http/GetPaginatedNowWitnessListServlet.java`).
3. Observe that each call triggers a full O(N) scan of `VotesStore` inside `Wallet.countVote` (`framework/src/main/java/org/tron/core/Wallet.java:842-872`) regardless of the small `limit` requested, and that response latency/resource usage scales with N rather than with `limit`, demonstrating the unbounded-iteration DoS vector.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }
