### Title
Nested `WithdrawFromGasKey` inside a `Delegate` action bypasses SPICE pending-transaction-queue gas-key accounting - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
The McDex report describes a class of bug where a balance-mutating action (`appliedBalance` for withdrawals) is not tracked by the mechanism meant to guard against nullifying already-submitted, not-yet-final trades, because the guard only inspects a narrow, top-level view of the state. The nearcore analog is the SPICE `PendingTransactionQueue`'s gas-key balance accounting: it only scans a transaction's *top-level* actions for `WithdrawFromGasKey`, so a `WithdrawFromGasKey` nested inside a `Delegate`/meta-transaction action drains a gas key's balance without being counted, invalidating the balance guarantee that other pending (already-admitted-but-not-yet-certified) gas-key transactions relied on when they were accepted into a chunk.

### Finding Description
SPICE production speculatively admits transactions into uncertified chunks before the referenced state is finalized. To keep this safe, `PendingTxSession::check_pending` tracks, per signer/gas-key, how much balance has already been committed by pending transactions so that a later transaction in the same window cannot spend funds twice. For gas keys this includes explicit tracking of `WithdrawFromGasKey` amounts: [1](#0-0) 

This loop iterates `tx.transaction.actions()` directly — i.e. only the outer, top-level actions of the transaction. It does not recurse into the inner action list of a `Delegate`/`DelegateV2` action. A `WithdrawFromGasKey` action can be placed *inside* a `DelegateAction`'s inner actions (a meta-transaction whose signer authorizes draining their own gas key), and until the fix landed, `validate_delegate_action` did not forbid this: [2](#0-1) 

The protocol-feature comment for `RejectWithdrawFromGasKeyInDelegate` states the root cause explicitly: [3](#0-2) 

and the companion comment on `RejectDelegateV2` confirms the queue's blind spot is structural, not incidental: [4](#0-3) 

The pending constraint built from this (incomplete) accounting, `paid_from_gas_key`, is what `verify_and_charge_gas_key_tx_ephemeral` uses to decide whether a gas-key transaction is admissible against the funded balance: [5](#0-4) 

Because a nested `WithdrawFromGasKey` inside a `Delegate` action drains the real balance without being reflected in `paid_from_gas_key`/`session_gas_key_withdrawals`, the pending-queue's view of "funded" balance becomes stale — this is the direct analog of the McDex bug where `appliedBalance` could be inflated and used immediately because the available-margin calculation didn't respect the lock that was supposed to protect concurrently-pending trades.

A regression/behavioral test confirms the pre-fix admission and drain: [6](#0-5) 

### Impact Explanation
Gas-key transactions admitted into earlier uncertified chunks under the (stale) assumption that the gas key still holds sufficient balance can be invalidated or fail once the nested withdrawal is actually applied, since the real balance was drained out-of-band from the queue's perspective. This breaks the core safety property the pending transaction queue exists to guarantee (no double-counting/double-spending of a signer's or gas key's funds across concurrently pending, uncertified chunks), producing incorrect admission decisions during SPICE chunk production — i.e., acceptance of a transaction set that is not actually consistent with the true funded balance, which is the same "nullify an already-submitted operation via an unlocked balance path" bug class as the reference finding.

### Likelihood Explanation
This is reachable by any unprivileged meta-transaction sender: an account signs a `DelegateAction` whose inner actions include `WithdrawFromGasKey` targeting its own gas key, and has a relayer submit it. No validator, operator, or SPICE-validator privilege is required — only that SPICE's pending transaction queue feature is active in the deployed protocol version. The codebase itself confirms exploitability existed by having introduced the dedicated protocol feature `RejectWithdrawFromGasKeyInDelegate` to close it, gated at a protocol version; on any currently-supported protocol version older than that gate, the hole remains open.

### Recommendation
Have `PendingTxSession::check_pending`'s `WithdrawFromGasKey` scan (and any equivalent top-level-only action scans feeding `PendingConstraints`) recurse into the inner actions of `Delegate`/`DelegateV2` actions, not just the outer transaction's actions, so nested withdrawals are counted against `paid_from_gas_key`. Alternatively/complementarily, keep the existing `RejectWithdrawFromGasKeyInDelegate` validation rule (rejecting `WithdrawFromGasKey` nested in a delegate action) enabled as the primary mitigation, and ensure it is active before/at the point the SPICE pending transaction queue is enabled in any deployed protocol version, rather than being a separately-timed gate.

### Proof of Concept [7](#0-6) 

1. Sender adds a gas key and funds it via `TransferToGasKey`.
2. Sender builds a `DelegateAction` whose only inner action is `WithdrawFromGasKey` on that gas key, signed with the sender's plain access key, and has a relayer submit it as the outer transaction — this is exactly `delegated_withdraw_tx` in the test.
3. Prior to `RejectWithdrawFromGasKeyInDelegate` being active, the transaction is admitted and drains the gas key balance (asserted at lines 119-137), while `PendingTxSession::check_pending`'s `session_gas_key_withdrawals` tracking (`pending_transaction_queue.rs:576-585`) never observes it because it only iterates top-level actions — so any other pending gas-key transaction admitted in the same window against the same key is validated against a `paid_from_gas_key` value that does not reflect this drain.
