### Title
`TransactionOutput::ensure_match_transaction_info` omits checkpoint-hash validation, letting corrupted state/hot-state/position roots pass replay verification - (File: types/src/transaction/mod.rs)

### Summary
`ensure_match_transaction_info` is the function used by chunk-replay/verification paths to confirm that a locally re-executed `TransactionOutput` matches the `TransactionInfo` fetched from a peer or backup before it is accepted and committed. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Finding Description
`TransactionInfo` carries four independent, mainnet-relevant commitments to the post-execution ledger state:
- `state_change_hash` — hash of the write set,
- `event_root_hash` — accumulator root over events,
- `state_checkpoint_hash` — Sparse Merkle Tree root of the world state (recorded periodically),
- (in `TransactionInfoV1`) `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` — additional state roots for the hot-state and native-position subsystems. [1](#0-0) 

`ensure_match_transaction_info` validates only `status`, `gas_used`, `state_change_hash`, and `event_root_hash`: [2](#0-1) 

The function's own comment explicitly documents the gap: [3](#0-2) 

This comparator is used by chunk replay/verification call sites (`execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) as the acceptance gate that a locally recomputed `TransactionOutput` matches an externally supplied `TransactionInfo` before treating a chunk as validated. When `compute_trading_native_state_roots` (gated by `BlockExecutorConfigFromOnchain`) is on, `TransactionInfoV1.position_state_checkpoint_hash` (and, more generally, `state_checkpoint_hash`/`hot_state_checkpoint_hash`) become authenticated, security-relevant commitments — yet none of them are cross-checked here. [4](#0-3) 

### Impact Explanation
Any tooling that relies on `ensure_match_transaction_info` as its sole state-equivalence check (e.g. `db-tool`'s `replay_on_archive`/replay-verify, or CLI/debugger simulation-vs-network comparisons) can report a "successful" replay even though the locally computed state root, hot-state root, or native-position root diverges from the version bound to the (proof-verified) `TransactionInfo`. This is exactly the class of bug the state-integrity gate calls out: an authenticated proof/commitment field (a state-checkpoint hash bound to a specific ledger version) is silently ignored by a downstream consumer that is supposed to detect divergence between the correct VM/storage result and the actual one. In a hard-fork or non-deterministic-execution scenario, a corrupted or forked state root would go undetected by this check, undermining the guarantee that "committed state differs from correct VM result" is caught by verification tooling.

### Likelihood Explanation
The gap is triggered purely by normal use of the replay-verification code path (no privileged access required) whenever `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` matter — i.e., whenever a chunk contains a checkpoint transaction or the trading-native-state-roots feature is enabled. It requires no attacker interaction beyond supplying (or having on-chain) a transaction stream whose non-write-set/event state diverges; the check will not flag it. The comment in the source confirms the aptos engineers are aware this is currently a real, unaddressed gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS").

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on either side) against the locally computed equivalents before accepting a chunk as verified, mirroring the existing `write_set_hash`/`event_root_hash` checks, and gate `compute_trading_native_state_roots` enablement on this validation being in place as the code comment itself recommends.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
