### Title
Nested `WithdrawFromGasKey` inside a `Delegate`/`DelegateV2` meta-transaction bypasses the pending-transaction-queue's gas-key balance accounting - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
The `PendingTransactionQueue` used under SPICE to admit not-yet-certified transactions tracks gas-key balance commitments by scanning only the **top-level** actions of a submitted transaction for `Action::WithdrawFromGasKey`. A `WithdrawFromGasKey` action nested inside a `Delegate`/`DelegateV2` meta-transaction is invisible to this scan, so the queue continues to treat the gas key's on-chain balance as fully available even though a withdrawal receipt is already in flight that will drain it. This is directly analogous to the `UniswapV4Wrapper` bug where `tokensOwed` was not decremented after a withdrawal, letting stale accounting be reused to move funds that had already been (or were about to be) spent elsewhere.

### Finding Description
`PendingTransactionQueue::add_chunk_transactions` builds gas-key cost commitments by iterating `tx.actions()` and matching `Action::WithdrawFromGasKey` directly on the outer transaction: [1](#0-0) 

This per-tx aggregate (`pending_gas_key_costs`) is what `verify_and_charge_gas_key_tx_ephemeral` later checks against the gas key's real on-trie balance before admitting a *new* gas-key transaction into a chunk: [2](#0-1) 

The scan operates on `tx.actions()`, i.e. the outer transaction's action list, and never descends into a `DelegateAction`'s inner `actions` field. So if a user submits a `Delegate`/`DelegateV2` meta-transaction whose *inner* action is `WithdrawFromGasKey`, the queue's `chunk_data.gas_key_costs` entry for that gas key is never incremented, even though the delegate receipt — once executed — calls `action_withdraw_from_gas_key`, which unconditionally decreases `gas_key_info.balance` and credits `account.amount()`: [3](#0-2) 

The protocol authors themselves documented this exact bug and shipped a fix gated behind the `RejectWithdrawFromGasKeyInDelegate` protocol feature: [4](#0-3) 

The enforcement point is `validate_delegate_action`, which — only when the feature is enabled and only for `ValidateReceiptMode::NewReceipt` — rejects any `Delegate`/`DelegateV2` whose inner actions contain `WithdrawFromGasKey`: [5](#0-4) 

Before this protocol feature activates (i.e., on any protocol version below its gate, and structurally for any receipt created prior to the upgrade, which is explicitly allowed to keep executing per the `mode == NewReceipt` guard), the nested withdrawal is admitted. The end-to-end effect was confirmed by the project's own regression test, which submits a delegated `WithdrawFromGasKey` pre-upgrade and observes it succeeds and drains the gas key balance that the pending-transaction-queue still counted as funded: [6](#0-5) 

The bug-class parallel to the Solidity report is precise: in both cases, an internal "amount already spoken for" accounting structure (`tokensOwed` in the Solidity wrapper vs. `pending_gas_key_costs`/`PendingConstraints::paid_from_gas_key` in nearcore) is derived only from a narrow, structurally-incomplete view of the mutating action (top-level unwrap calls vs. top-level `WithdrawFromGasKey` actions), letting a semantically equivalent action reachable through an alternate path (partial-unwrap-then-rewrap vs. nested Delegate action) go unaccounted-for, and letting the same underlying balance be spent/counted twice.

### Impact Explanation
While the pending transaction queue's constraints are enforced only for the SPICE (`protocol_feature_spice`) execution model and not on baseline mainnet nearcore, the mechanism is a consensus-adjacent admission-control component: it determines whether a signer-submitted transaction is admitted into a chunk before earlier withdrawals against the same gas key are certified. A gap here allows a signer to withdraw more from a gas key than the key's balance safely supports as tracked by the admission layer, i.e. the account can submit and have admitted (and eventually executed) gas-key transactions whose true available balance the runtime believed was reserved by an in-flight withdrawal. This does not directly forge new tokens (the runtime-level `action_withdraw_from_gas_key` still checks the real on-trie balance via `checked_sub`), but it defeats an intended safety/ordering guarantee of the pending-transaction admission layer for the multi-transaction gas-key balance invariant, and (per the authors' own comment) is a genuine "hole this rule closes." Given this is validator/chunk-producer admission logic reachable by any signer submitting an ordinary meta-transaction, and the protocol authors classified it as consensus-relevant enough to require a protocol-version-gated fix, this rises to at least Medium severity as an accounting/admission-bypass bug in the reachable-by-unprivileged-signer category.

### Likelihood Explanation
Likelihood is high given the fix already exists and is protocol-version-gated (implying the bug was live on some prior/pre-upgrade protocol version), and the authors' own inline comment and dedicated regression test (`test_reject_delegated_gas_key_withdraw_protocol_upgrade`) confirm the exploit path executes successfully pre-upgrade with no special privileges — only a signed `Delegate` action wrapping `WithdrawFromGasKey`, reachable from any account holding a gas key.

### Recommendation
Ensure `PendingTransactionQueue::add_chunk_transactions`'s scan for `WithdrawFromGasKey` recursively inspects nested `Delegate`/`DelegateV2` action lists rather than only the top-level `tx.actions()`, OR retain/backstop the current mitigation (`RejectWithdrawFromGasKeyInDelegate`, rejecting any `WithdrawFromGasKey` nested in a delegate action at `validate_delegate_action`) permanently as the canonical fix rather than a transitional gate, and audit for any other action-scanning accounting structure (e.g. similar per-tx scans feeding `PendingConstraints`) that inspects only top-level actions while a corresponding runtime action handler also accepts the same effect via `Delegate`/`DelegateV2` nesting.

/// Build a meta transaction whose inner action withdraws from the sender's own

/// gas key cannot sign a V1 delegate action.
fn delegated_withdraw_tx(
    env: &TestLoopEnv,
    sender: &AccountId,
    relayer: &AccountId,
    gas_key: &Signer,
) -> SignedTransaction {
    let sender_signer = create_user_test_signer(sender);
    let delegate_action = DelegateAction {
        sender_id: sender.clone(),
        receiver_id: sender.clone(),
        actions: vec![
            Action::WithdrawFromGasKey(Box::new(WithdrawFromGasKeyAction {
                public_key: gas_key.public_key(),
                amount: WITHDRAW_AMOUNT,
            }))
            .try_into()
            .unwrap(),
        ],
        nonce: env.rpc_node().get_next_nonce(sender),
        max_block_height: 1_000_000,
        public_key: sender_signer.public_key(),
    };
    let signed_delegate = SignedDelegateAction::sign(&sender_signer, delegate_action);
    env.rpc_node().tx_from_actions(
        relayer,
        sender,
        vec![Action::Delegate(Box::new(signed_delegate))],
    )

#[test]
fn test_reject_delegated_gas_key_withdraw_protocol_upgrade() {
    init_test_logger();

    if !ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(PROTOCOL_VERSION) {
        return;
    }

    let new_protocol = ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.protocol_version();
    let old_protocol = new_protocol - 1;
    assert!(
        old_protocol >= MIN_SUPPORTED_PROTOCOL_VERSION,
        "no supported protocol version still admits a delegated WithdrawFromGasKey, so there is \
         nothing left to test here - remove this test"
    );

    let sender = create_account_id("alice");
    let relayer = create_account_id("relayer");
    let epoch_length = 10;

    // Boundary "mm": "alice" lands on the first shard, "relayer" on the second,
    // so the delegate receipt crosses a shard on its way to the sender.
    let shard_layout = ShardLayout::multi_shard_custom(vec![create_account_id("mm")], 1);

    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .protocol_version(old_protocol)
        .protocol_upgrade_schedule(ProtocolUpgradeVotingSchedule::new_immediate(new_protocol))
        .epoch_length(epoch_length)
        .shard_layout(shard_layout)
        .add_user_account(&sender, Balance::from_near(1_000))
        .add_user_account(&relayer, Balance::from_near(1_000))
        .build();

    let gas_key: Signer =
        InMemorySigner::from_seed(sender.clone(), KeyType::ED25519, "gas_key").into();
    let add_key_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::AddKey(Box::new(AddKeyAction {
            public_key: gas_key.public_key(),
            access_key: AccessKey::gas_key_full_access(1),
        }))],
    );
    env.rpc_runner().run_tx(add_key_tx, Duration::seconds(10));

    let fund_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::TransferToGasKey(Box::new(TransferToGasKeyAction {
            public_key: gas_key.public_key(),
            deposit: Balance::from_near(10),
        }))],
    );
    env.rpc_runner().run_tx(fund_tx, Duration::seconds(10));

    // Before the upgrade the nested withdrawal is admitted and moves balance out
    // of the gas key, which is the hole this rule closes.
    assert_eq!(
        env.rpc_node().protocol_version_at_head(),
        old_protocol,
        "expected to start pre-upgrade"
    );
    let (_, balance_before) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    let tx = delegated_withdraw_tx(&env, &sender, &relayer, &gas_key);
    let outcome = env
        .rpc_runner()
        .execute_tx(tx, Duration::seconds(10))
        .expect("delegated withdrawal admitted pre-upgrade");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::SuccessValue(_),
        "pre-upgrade delegated withdrawal should execute",
    );
    let (_, balance_after) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    assert_eq!(
        balance_after,
        balance_before.checked_sub(WITHDRAW_AMOUNT).unwrap(),
        "the nested withdrawal should have drained the gas key",
    );
