### Title
Wallet Contract loses caller's attached deposit when an intermediate cross-contract call fails during ETH-emulated transfers - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (`near-wallet-contract`) that backs ETH-implicit accounts forwards a caller's attached NEAR deposit (`CallerDeposit`) through multi-step promise chains for emulated ERC-20 transfers and address-checked base-token transfers. Two of the three callbacks that carry this `caller_deposit` forward — `address_check_callback` and `nep_141_storage_balance_callback` — silently drop it and never refund it when the preceding cross-contract call fails, while the third callback (`rlp_execute_callback`) does correctly refund it on failure. This asymmetry causes the caller's deposit to be permanently retained by the Wallet Contract account instead of being returned.

### Finding Description
`inner_rlp_execute` computes a `caller_deposit` (`let caller_deposit = CallerDeposit::new(&context);`) representing the value the transaction's predecessor is entitled to have refunded if execution fails, and threads it through the promise chain for both the address-check flow and the NEP-141 (ERC-20 emulation) flow: [1](#0-0) 

For an `EOABaseTokenTransfer` with `address_check`, the promise chain calls the address registrar and resolves to `address_check_callback`, passing `caller_deposit` along: [2](#0-1) 

Inside `address_check_callback`, when the registrar lookup fails (`PromiseResult::Failed`), the function returns an error response but never inspects or refunds `caller_deposit`: [3](#0-2) 

The same pattern occurs for the ERC-20 emulation path. `nep_141_storage_balance_callback` receives `caller_deposit` when checking `storage_balance_of` on the token contract: [4](#0-3) 

But if that `storage_balance_of` call fails, the callback again returns an error response without refunding `caller_deposit`: [5](#0-4) 

By contrast, the terminal callback `rlp_execute_callback`, which handles failures of the final action promise, does correctly refund `caller_deposit` on failure: [6](#0-5) 

This shows the refund logic exists and is understood to be required by the contract's own design, but it was only implemented for one of the three failure points in the promise DAG. Any deposit attached by the predecessor (e.g. a relayer forwarding the user's fee/value via `#[payable] rlp_execute`) that is consumed as `caller_deposit` and reaches either of the two unguarded `Failed` branches is left inside the Wallet Contract's account balance with no code path that ever returns it to the rightful owner.

### Impact Explanation
This is a fund-loss (permanently frozen funds) bug reachable by any unprivileged caller of `rlp_execute` (the Wallet Contract's only mutating entry point, invocable by any relayer holding a `FunctionCall` access key or by the account owner itself) whenever:
- the transaction is an `EOABaseTokenTransfer` with an `address_check` (targeting a would-be named account), and the address-registrar `lookup` call fails or times out on gas, or
- the transaction is an emulated `ERC20Transfer`, and the token contract's `storage_balance_of` call fails (e.g., the target is not a valid NEP-141 contract, is paused, or runs out of gas).

In both cases the NEAR value attached to the `rlp_execute` call (`caller_deposit`) is retained by the Wallet Contract account balance without ever being credited back to the caller, and there is no other method on the contract that can move it out again to the original depositor. This satisfies the "permanently frozen funds" impact category.

### Likelihood Explanation
Likelihood is moderate to high: any relayer or automated ETH-transaction submitter routinely constructs `rlp_execute` calls for ERC-20 transfers (the most common wallet operation) and can trivially trigger a failed `storage_balance_of` call (e.g. by targeting a non-existent/misconfigured token contract, or by an honest relayer under-provisioning callback gas so the downstream call fails). No malicious validator, network, or privileged actor is required — a single transaction signer/relayer using the documented, unprivileged `rlp_execute` entry point can reach this path.

### Recommendation
Add the same refund logic used in `rlp_execute_callback` to both `address_check_callback` and `nep_141_storage_balance_callback` on their respective `PromiseResult::Failed` branches, so that any non-`None` `caller_deposit` is transferred back to its owning account before returning the failure `ExecuteResponse`.

### Proof of Concept
1. Create an ETH-implicit account and deploy the Wallet Contract to it, as done in `test_wallet_contract_interaction`. [7](#0-6) 
2. Have a relayer submit `rlp_execute` with a signed Ethereum tx encoding an ERC20 `transfer` where `target` is a NEP-141-like account ID that does not actually implement `storage_balance_of` (or is deleted / lacks the method), and attach a non-zero deposit as the `caller_deposit`-triggering fee/value.
3. `inner_rlp_execute` schedules `storage_balance_of` then `.then(ext.nep_141_storage_balance_callback(...))` per lines 433-458 of `lib.rs`.
4. Because the target does not implement the method, the promise resolves as `PromiseResult::Failed`; `nep_141_storage_balance_callback`'s `Failed` branch (lines 203-210) returns the error response and drops `caller_deposit` without refund.
5. Query the Wallet Contract account balance: the attached deposit remains in the account and is never returned to the relayer/user, demonstrating permanent fund loss.
