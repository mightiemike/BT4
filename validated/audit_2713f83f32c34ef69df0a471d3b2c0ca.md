## Title
Replay-verify's `ensure_match_transaction_info` skips checkpoint-hash validation, letting a diverged state/position root be accepted as a valid replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs`, around lines 2139-2204) is the function used by replay/backup-verification tooling to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` recorded on-chain. It checks status, gas used, write-set hash, and event-root hash, but a comment directly above the final `Ok(())` states it deliberately skips validating the state/hot-state checkpoint hash and the `position_state_checkpoint_hash`.

### Finding Description
The function is called from `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` (line ~392), which is the core loop of the `replay_on_archive`/`replay_verify` tools used to independently re-execute historical transactions and confirm the resulting state matches the authenticated ledger. [1](#0-0) 

`ensure_match_transaction_info` validates status, gas, write-set hash (`state_change_hash`) and event root hash against the `TransactionInfo`, but explicitly does **not** validate the state checkpoint hash (JMT/state root) or the newer `position_state_checkpoint_hash` (native-position/trading-native root): [2](#0-1) 

The code comment itself documents the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```
This means that if a chunk's write set is byte-for-byte identical (so `state_change_hash` matches) but the *checkpoint*/state root computed after applying the state (i.e., the JMT root, hot-state root, or native-position root) diverges from the authenticated `TransactionInfo.state_checkpoint_hash` / `position_state_checkpoint_hash`, replay-verify will still report success. This is precisely the "hard-fork-only divergence during commit/replay/proof verification" and "authenticated ... output bound to the wrong ... root" class of bug: the tool that is meant to be the last line of defense for catching a divergent state-computation (e.g. a subtle JMT/state-view bug, an incorrectly-applied write set ordering, or a bug in the new "native position"/trading-native root computation) is blind to exactly that class of divergence.

### Impact Explanation
`replay_on_archive`/`replay_verify` is the tool operators and the Aptos Labs team use to confirm that historical execution/replay reproduces the exact same ledger state as what was originally committed and authenticated by validator signatures. If the state checkpoint hash comparison is skipped, a state-root divergence (e.g., caused by a bug in state-tree construction, hot-state handling, or the newly-introduced native-position/trading-native checkpoint) would go undetected by this verification tool even though the underlying state committed to storage is wrong. This directly undermines the "state that differs from the correct VM result... accepted as valid" and "hard-fork-only divergence during ... replay ... accepted as valid" impact categories, because the very oracle meant to catch such corruption silently passes.

### Likelihood Explanation
The gap is unconditional and applies to every call of `ensure_match_transaction_info`, not just an edge case — the checkpoint-hash checks are absent from the function entirely, not merely disabled behind a feature-guard that is off during normal use (the accompanying TODO says checks should be added "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`", implying they are not yet gated and are simply missing now). Any bug in state-checkpoint computation (JMT root, hot-state, or the new native-position checkpoint hash) will silently pass replay-verify today. However, actually *triggering* a real state-root divergence still requires an underlying execution/storage bug elsewhere; this finding by itself only removes the detection safety-net, it does not itself directly corrupt consensus-committed data (the accumulator/consistency-proof paths I inspected — `AccumulatorRangeProof::verify`, `TransactionInfoWithProof::verify`, `ChunkResultVerifier` — correctly validate root hashes end-to-end).

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`'s computed state checkpoint hash (and, once available, the position/hot-state checkpoint hash) against `txn_info.state_checkpoint_hash()` (and the corresponding new field), so that `replay_on_archive`/`replay_verify` cannot report success when the checkpoint root diverges from the authenticated `TransactionInfo`.

### Proof of Concept
Not directly exploitable as a standalone PoC without an independent state-root-diverging bug; the concrete demonstration is code-level: any test that feeds `execute_and_verify` a `TransactionOutput` whose write set/events/status/gas match the expected `TransactionInfo` but whose *state checkpoint hash* (if it were computed and compared) would differ, currently passes `ensure_match_transaction_info` unconditionally, since that comparison branch does not exist in the function body. [3](#0-2) 

**Confidence caveat:** I could not fully verify whether checkpoint-hash comparison is performed anywhere else in the replay/verify pipeline (e.g., in `do_state_checkpoint.rs` or `ChunkResultVerifier`) as a redundant safety net, which would reduce the severity of this specific gap. The `ChunkResultVerifier`/`StateSyncChunkVerifier` path I reviewed only verifies `transaction_infos` match and accumulator extension, not a separate state-checkpoint comparison against re-executed output, but I did not have iterations left to trace `do_state_checkpoint.rs` in full to confirm whether an equivalent check exists in the online (non-tool) commit path.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
