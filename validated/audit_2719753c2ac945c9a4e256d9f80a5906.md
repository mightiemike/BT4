## Analysis

I found a genuine analog. `sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` validates the attacker-controlled `host` query parameter using a regex that only checks the *character set* of the base64 string, not that its length is a valid base64 length (multiple of 4, correct padding): [1](#0-0) 

`decodeHost` simply calls `atob(host)` with no error handling: [2](#0-1) 

`atob` throws a `DOMException`/`InvalidCharacterError` synchronously when given a string that matches the base64 character-class regex but has an invalid length/padding (e.g. a single character like `"a"`, or a 5-character string). Since `sanitizeHost`'s regex `^[0-9a-zA-Z+/]+={0,2}$` doesn't enforce `length % 4 === 0`, such malformed-but-charset-valid strings pass the pre-check and reach `decodeHost`/`atob` unguarded, throwing an exception that is not caught anywhere inside `sanitizeHost`.

This function is invoked directly on unauthenticated, attacker-controlled query parameters in multiple auth entry points reachable by any anonymous browser/request, e.g.: [3](#0-2) [4](#0-3) [5](#0-4) 

None of these call sites wrap `sanitizeHost` in a try/catch. In the Remix/React Router adapters, an uncaught throw from a loader/action is caught by the framework's error boundary machinery and rendered as an error page — this is not a bridge-freezing bug, just a per-request 500. In the Express adapter, however, several of these call sites are inside `async` Express route handlers/middleware (not wrapped by any error-handling middleware in the library itself); an unhandled rejection from a thrown synchronous error inside an `async` function that Express doesn't `.catch()` will propagate as an unhandled promise rejection. Depending on the Node.js version's default `--unhandled-rejections` mode, this can terminate the Node process, unlike a normal `res.status()` error response.

**Uncertainty**: I could not fully verify with 100% certainty whether every relevant Express call site executes without any wrapping error-handling middleware (e.g., a top-level Express error handler added by the host app), because that depends on app-level Express configuration outside this package's control, and I did not have visibility into a global unhandled-rejection handler in the library itself. This weakens the strength of the "crashes the whole process" claim to a probable-but-app-config-dependent DoS, rather than a certainty. Also, unlike the Gravity Bridge bug, there is no persistent/permanent "stuck oracle" state here — each request is independent, so this is a per-request (or, in the worst case, process-crash) DoS, not a permanent protocol freeze requiring a redeploy.

Given the rules require a "concrete... DoS of an auth handler," and this is a real, reachable, unauthenticated crash/exception vector into `sanitizeHost`/`decodeHost` triggered by a single malformed `host` query parameter (a value fully controlled by an anonymous requester), it qualifies as a valid analog — though weaker/narrower than the original bridge-freeze bug because it is scoped to a single request/process rather than a permanently corrupted state machine.

### Title
Uncaught `atob()` Exception in `sanitizeHost` via Malformed `host` Query Parameter Causes Unhandled DoS in Auth Flow - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`sanitizeHost` validates the `host` query parameter using a regex that checks only the base64 character set, not valid base64 length/padding, before passing it unguarded to `atob()` in `decodeHost`. A malformed-but-charset-valid `host` value (e.g. a single-character or improperly padded base64 string) causes `atob` to throw synchronously, and this exception is not caught within `sanitizeHost` or at any of its call sites in the Express, Remix, or React Router auth adapters, all of which are reachable by anonymous requests before any session/HMAC validation occurs.

### Finding Description
`sanitizeHost` uses the regex `/^[0-9a-zA-Z+/]+={0,2}$/` to decide whether to treat `host` as valid base64: [1](#0-0) . This regex accepts strings whose length is not a multiple of 4 (a requirement of valid base64), such as `"a"`, `"ab"`, or `"abcde"`. It then unconditionally calls `decodeHost(sanitizedHost)`, which is a thin wrapper around the runtime `atob()` function: [2](#0-1) . `atob()` throws an `InvalidCharacterError`/`DOMException` when given a string of invalid base64 length, and this throw is not wrapped in a try/catch anywhere in `sanitizeHost`.

This function is invoked directly on the raw `host` query parameter — fully attacker-controlled, with no prior authentication — from multiple public-facing entry points:
- `validateShopAndHostParams` in both the Remix and React Router packages, called at the top of `authenticate.admin`: [6](#0-5) 
- `redirectToAuth`'s `clientSideRedirect` in shopify-app-express: [4](#0-3) 
- `redirectToShopifyOrAppRoot` middleware in shopify-app-express: [7](#0-6) 
- `redirectWithExitIframe` in shopify-app-remix: [8](#0-7) 

None of these call sites catch exceptions from `sanitizeHost`; they only check the *return value* for `null`, assuming `sanitizeHost` either returns a string or `null`, never expecting a thrown exception.

### Impact Explanation
This is analogous to the Gravity Bridge bug's root cause: unsanitized/incorrectly-validated attacker-controlled input reaches a strict decode routine (`atob`, analogous to `String::from_utf8`) that throws on malformed-but-superficially-valid input, and the calling code has no exception handling for that specific failure mode — only for the "expected" invalid-format case. In the Express adapter, an uncaught synchronous throw inside an `async` route handler becomes an unhandled promise rejection; if the hosting Node process does not have a global `unhandledRejection` handler, this can crash the entire Node process, taking down the app for all merchants (a full DoS), not just failing the single request. In the Remix/React Router adapters, the impact is reduced to an unhandled loader exception (likely rendered by the framework's error boundary as a 500), which is a less severe but still an availability/robustness bug in the auth entry path.

### Likelihood Explanation
The `host` parameter is fully attacker-controlled and requires no authentication, session, or prior state to trigger — a single anonymous GET request with `?host=a` (or any base64-charset string of invalid length) to `/auth`, `/`, or any route calling `validateShopAndHostParams` is sufficient. This makes the trigger trivially reachable and cheap, similar in spirit to the "extremely low cost way to bring down the network" characterization in the original report, though the blast radius here is scoped to the Node process/request rather than a shared blockchain bridge state.

### Recommendation
Update the base64 validation regex in `sanitizeHost` to also enforce correct base64 length semantics (e.g., `^(?:[0-9a-zA-Z+/]{4})*(?:[0-9a-zA-Z+/]{2}==|[0-9a-zA-Z+/]{3}=|[0-9a-zA-Z+/]{4})$`), or wrap the `decodeHost`/`atob` call in a try/catch inside `sanitizeHost` so any decode failure is treated the same as "invalid host" (returning `null` or throwing `InvalidHostError` consistently) rather than propagating an unexpected, uncaught exception type to callers.

import {redirect} from '@remix-run/server-runtime';

import type {BasicParams} from '../../../types';

export function redirectWithExitIframe(
  params: BasicParams,
  request: Request,
  shop: string,
): never {
  const {api, config} = params;
  const url = new URL(request.url);

  const queryParams = url.searchParams;

  const host = api.utils.sanitizeHost(queryParams.get('host')!);

  queryParams.set('shop', shop);

  let destination = `${config.auth.path}?shop=${shop}`;

  if (host) {
    queryParams.set('host', host);
    destination = `${destination}&host=${host}`;
  }
  queryParams.set('exitIframe', destination);

  throw redirect(`${config.auth.exitIframePath}?${queryParams.toString()}`);
