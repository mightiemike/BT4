### Title
Signer signature threshold silently drops to zero for a degenerate PoX-4 reward set, letting an unsigned Nakamoto block pass `verify_signer_signatures` - (File: stackslib/src/chainstate/nakamoto/mod.rs)

### Summary
`NakamotoBlockHeader::verify_signer_signatures` treats a *present-but-empty* signer list (`RewardSet::signers() == Some(&vec![])`) as a valid reward set rather than rejecting it the way it rejects `signers() == None`. In that state `total_signing_weight()` returns `Ok(0)`, `compute_voting_weight_threshold(0)` returns `0`, and the check `total_weight_signed < threshold` (`0 < 0`) is false — so a block with **zero signer signatures** is accepted as validly signed. This is structurally the same bug class as the fast-jwt report: an "empty" input (empty signer set / empty secret) is fed into the same code path used for legitimate values and satisfies the equality check trivially instead of being rejected up front.

### Finding Description
`StacksChainState::make_signer_set` (stackslib/src/chainstate/stacks/boot/mod.rs:1020-1072), used by the PoX-4 signer-set computation path (`pox_4_compute_and_update_signers`, stackslib/src/chainstate/nakamoto/signer_set.rs:703-738), builds the signer set with a naive floor scheme: [1](#0-0) 

Each entry's `weight = stacked_amt / threshold` is floored, and entries with `weight == 0` are filtered out — but the function *unconditionally* returns `Some(signer_set)` even when the resulting `signer_set` is empty (this only returns `None` when the raw `entries` slice itself was empty, before filtering). If a reward cycle's PoX-4 threshold is computed such that every individual stacker's `amount_stacked / threshold` floors to `0` (e.g., many small, evenly split stackers relative to the computed threshold), `make_signer_set` yields `Some(vec![])`. That gets stored as `RewardSetV0.signers = Some(vec![])`.

Contrast this with the newer PoX-5 path, `pox_5_compute_and_update_signers`, which explicitly guards against this exact degenerate case: [2](#0-1) 

No equivalent guard exists for the PoX-4/`make_signer_set` path.

Downstream, `verify_signer_signatures` only rejects a `None` signer list, not an empty-but-`Some` one: [3](#0-2) 

`RewardSet::total_signing_weight` folds over the (empty) signer vector and returns `Ok(0)` rather than an error: [4](#0-3) 

`compute_voting_weight_threshold` then computes `threshold = ceil(0 * 7 / 10) = 0`: [5](#0-4) 

Finally, the acceptance check compares the empty signature loop's accumulated `total_weight_signed = 0` against `threshold = 0`: [6](#0-5) 

`0 < 0` is `false`, so the function returns `Ok(0)` — full validation success — for a block carrying **no signer signatures at all**.

**Equality broken:** the required invariant is "signer weight (signed) ≥ threshold weight, where threshold is derived from a non-degenerate registered signer set." Here, both sides of the inequality collapse to `0` because the signer-set-construction step silently produced an empty-but-`Some` set instead of erroring, so the check that should gate block acceptance on signer weight becomes vacuously true — directly analogous to the fast-jwt bug where an empty HMAC key made `verifySignature` trivially true.

### Impact Explanation
Every node evaluating the same on-chain PoX-4 signer-set state for that reward cycle would independently compute the same degenerate `RewardSet` and would deterministically accept an unsigned Nakamoto block as validly signed. This is not a minority-divergence issue — because the check is derived deterministically from on-chain state, all honest nodes would agree to accept the fraudulent, signature-less block, meaning the block-producing miner (an otherwise unprivileged participant who is not required to obtain any stacker signatures) could unilaterally advance the Nakamoto chain tip without stacker consensus. This maps to "an invalid block accepted... network-wide" (Critical) in the given impact taxonomy, since the entire signer-threshold security model is bypassed for that reward cycle.

### Likelihood Explanation
The trigger condition requires a reward cycle where the PoX-4 threshold computation produces `stacked_amt / threshold == 0` for every individual stacker in `make_signer_set`'s input (e.g., a low-participation/high-threshold or highly-fragmented-stacking scenario during the PoX-4 window, which is still the active reward-set mechanism prior to PoX-5 activation). This requires no privileged access — any set of stackers (even unwitting ones, or ones deliberately structured by an attacker who controls many small stacking positions) can shape participation to hit this degenerate case, and the PoX-5 code explicitly documents this exact failure mode as one it was designed to avoid, confirming its plausibility. I was not able to fully verify from the available context whether `get_reward_threshold_and_participation` (which computes the PoX-4 threshold) contains its own independent guard preventing an all-zero-weight outcome; this uncertainty should be resolved by a deeper look at `stackslib/src/chainstate/stacks/boot/mod.rs::get_reward_threshold_and_participation` before treating this as fully confirmed exploitable in production configurations.

### Recommendation
In `make_signer_set` (or immediately after calling it in `pox_4_compute_and_update_signers`), treat a filtered-to-empty signer set the same way `pox_5_compute_and_update_signers` does: return an explicit error (e.g., `ChainstateError::PoxNoRewardCycle` / `NoRegisteredSigners`) instead of `Some(vec![])`. Additionally, harden `RewardSet::total_signing_weight` and `NakamotoBlockHeader::verify_signer_signatures` to explicitly reject a `Some(&vec![])` (empty-but-present) signer list rather than only guarding against `None`, so the zero-threshold degenerate state can never be reached even if a future signer-set-construction path reintroduces it.

### Proof of Concept
1. Construct PoX-4 stacking entries for a reward cycle such that every entry's `amount_stacked` is strictly less than the computed `threshold` (e.g., many stackers each stacking slightly less than `total_liquid_ustx / reward_slots`).
2. `pox_4_compute_and_update_signers` calls `StacksChainState::make_signer_set(threshold, entries)`; every entry's `weight = amount_stacked / threshold == 0` and is filtered out, yielding `signer_set = Some(vec![])` (non-`None`, but empty).
3. This `RewardSet::V0` (with `signers: Some(vec![])`) becomes the active reward set for the corresponding Nakamoto reward cycle.
4. The miner (or anyone able to produce a block for that tenure) constructs a `NakamotoBlock` with `signer_signature = vec![]` (no signatures at all).
5. Any node calls `header.verify_signer_signatures(&reward_set, epoch_id)`:
   - `reward_set.signers()` returns `Some(&vec![])`, so the `None`-guard does not fire.
   - `total_weight = reward_set.total_signing_weight().unwrap() == 0`.
   - The `for signature in self.signer_signature.iter()` loop does not execute (`signer_signature` is empty), so `total_weight_signed = 0`.
   - `threshold = compute_voting_weight_threshold(0) == 0`.
   - `total_weight_signed < threshold` → `0 < 0` → `false`.
   - Function returns `Ok(0)` — the completely unsigned block is accepted as validly signed by every node evaluating this reward set.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
