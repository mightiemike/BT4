### Title
Stale market-side `index-cache` used to compute scaled debt after `vault-system-borrow` mutates the vault's index in the same transaction - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar` (and its mainnet counterpart `v0-4-market.clar`) maintains a per-block, per-asset `index-cache` map to avoid repeated cross-contract calls to vaults [1](#0-0) . `borrow()` populates this cache once via `accrue-and-cache asset-id` before doing the health check [2](#0-1) , then executes `vault-system-borrow`, and only afterwards reads `get-cached-indexes` again to compute `scaled-debt-added` [3](#0-2) . Because `get-cached-indexes` is a pure map lookup keyed by `{timestamp: stacks-block-time, aid}` [4](#0-3) , it returns the value cached at Step 3, not a value reflecting any mutation performed by `vault-system-borrow` in between.

### Finding Description
The vault's own `accrue()` (called internally at the top of `system-borrow`) can mutate the vault's `index`/`lindex` state variables and mint treasury shares when the vault's tracked interest changes [5](#0-4) . `market.clar`'s `index-cache` is a snapshot of the vault index taken once per block-timestamp and is never invalidated mid-transaction when the underlying vault's index is subsequently changed by a same-transaction, same-block cross-contract call such as `vault-system-borrow` [3](#0-2) . The `borrow-index` used to convert `amount` to `scaled-debt-added` is therefore read from the pre-borrow cached snapshot rather than the post-`system-borrow` index, so the scaled-debt bookkeeping in `v0-market-vault.debt-add-scaled` is computed against a value that may no longer match the vault's live `index` for the remainder of the transaction and for any function within the same block that trusts `get-cached-indexes` without a fresh vault call.

This is analogous to the reported bug class: a cached value ("the vault index snapshot") is bound before a state-mutating call ("`vault-system-borrow`" mutating the vault's own index) and is used afterward without being invalidated/refreshed, exactly mirroring "a cached value not invalidated when its source moves."

### Impact Explanation
If the vault's index actually changes as a side effect of `vault-system-borrow`'s internal `accrue()` call (i.e., `next-index` differs from the value cached moments earlier because interest accrual crossed a threshold within the same evaluation), the scaled-debt recorded for the user in `v0-market-vault` is computed with a mismatched index relative to the vault's live index. Over many operations this produces a persistent discrepancy between the sum of user-scaled-debt × current index and the vault's own `total-debt()`, i.e., debt accounting drift between `market-vault` and the vaults. This can lead to under- or over-scaled debt being recorded, which is a form of protocol insolvency risk (vault assets vs. recorded obligations diverge) — landing in the Critical impact category (protocol insolvency) if compounded over time, or temporary freezing/mispricing of funds for affected borrow operations.

### Likelihood Explanation
This requires the cached index and the freshly-accrued vault index to actually differ within the same block/transaction, which depends on `next-index()`'s calculation being time/rate-sensitive rather than purely `stacks-block-time`-gated. Given the cache key already includes `stacks-block-time` and normal accrual is designed to be idempotent within the same timestamp, this divergence path is narrow and I could not fully confirm from the available context whether `next-index()` can produce a different value from a second call within the identical `stacks-block-time` (this would need direct inspection of the vault's `next-index`/`next-liquidity-index` private functions, which I did not have available in this pass). This uncertainty limits my confidence in exploitability.

### Recommendation
Re-fetch (`accrue-and-cache`) or explicitly invalidate/refresh the market's `index-cache` entry for `asset-id` immediately after any cross-contract call that can mutate the underlying vault's index within the same function (e.g., after `vault-system-borrow`, `vault-system-repay`, `vault-deposit`, `vault-redeem`), before using `get-cached-indexes` to derive scaled amounts, mirroring the explicit refresh pattern already used in `socialize-debt-asset` [6](#0-5) .

### Proof of Concept
1. Within a single `borrow()` call, `accrue-and-cache asset-id` caches `{index: I0, lindex: L0}` for `{timestamp: T, aid: asset-id}` [7](#0-6) .
2. `vault-system-borrow` is called, which internally invokes the vault's `accrue()`, potentially updating the vault's own `index`/`lindex` vars to `I1`/`L1` if `next-index()`/`next-liquidity-index()` differ from `I0`/`L0` [5](#0-4) .
3. `borrow()` then re-reads `get-cached-indexes asset-id`, which still returns the map entry set in step 1 (`I0`), not `I1`, since nothing re-populated `index-cache` for `{timestamp: T, aid: asset-id}` [3](#0-2) .
4. `scaled-debt-added` is computed against `I0` and stored via `debt-add-scaled`, producing a mismatch relative to the vault's now-live `I1`.

I was not able to fully verify whether `next-index()` is guaranteed identical across two calls at the same `stacks-block-time` (which would neutralize this analog); this should be confirmed by inspecting the vault's private index-calculation functions before treating this as conclusively exploitable.
