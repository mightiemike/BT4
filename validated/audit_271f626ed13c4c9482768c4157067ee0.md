## Title
Domain-unbound signature authorization in `ValidateMultiSign`/`BatchValidateSign` TVM precompiles enables cross-deployment/cross-chain signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
java-tron exposes two TVM precompiled contracts, `ValidateMultiSign` and `BatchValidateSign`, that let a smart contract verify an off-chain-produced ECDSA signature against an on-chain account's multi-sig `Permission`. Both compute (or accept) a signed hash that contains **no chain/network identifier and no calling-contract address** — exactly the missing binding that caused the H-01 finding in the external report. Any dApp built on top of these primitives that authorizes value-affecting actions (claims, withdrawals, approvals) purely from the precompile's boolean result inherits the same cross-chain/cross-deployment signature-replay exposure described in the report.

### Finding Description
`ValidateMultiSign.execute` builds the message hash entirely from caller-controlled fields with no chain-specific salt: [1](#0-0) 

```
DataWord[] words = DataWord.parseArray(rawData);
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter.getInstance().isECKeyCryptoEngine(), combine);
```

The signed hash is `sha256(address || permissionId || data)` — `address` and `permissionId` merely identify *which* account/permission is being checked; `data` is an arbitrary payload chosen entirely by the calling dApp. There is no chain id, genesis hash, or contract address baked into this hash by the precompile itself.

`BatchValidateSign.doExecute` is even more permissive — it takes the hash to be signed directly from calldata with zero binding at all: [2](#0-1) 

Address recovery itself (`recoverAddrBySign`) is a raw ECDSA recovery with no domain separation: [3](#0-2) 

This mirrors the external report's root cause precisely: `PhiFactory::signatureClaim` recovers a signer from `encodeData_` that *contains* a `chainId` field but the factory never checks it against `block.chainid`, so a signature minted for chain B validates on chain A. Here, java-tron's precompile goes a step further — the hash format it defines has *no room at all* for a chain identifier; it is entirely up to the calling contract's `data` argument (an arbitrary, developer-chosen byte string) to embed any domain-separation value such as a chain id or the verifying contract's address. If a dApp author omits this (exactly the class of mistake the external report demonstrates), the same signature, permission, and account address can validate identically:
- on a different java-tron-based network (e.g. Mainnet vs. Nile/Shasta testnets, or any private/consortium chain forked from the same codebase) where an identically-addressed account and an identically-deployed dApp contract exist, or
- against multiple independently-deployed instances of the same dApp contract on the same chain (since the contract's own address is also not part of the hash).

Unlike core TRON transactions — whose `validateSignature`/`addSign` hash the full `TransactionCapsule` `rawData`, which includes `ref_block_hash`/`ref_block_num`/`expiration` and is therefore implicitly bound to a specific chain's block history — the `ValidateMultiSign`/`BatchValidateSign` precompiles provide no such implicit binding: [4](#0-3) 

### Impact Explanation
Any TVM contract that uses `ValidateMultiSign`/`BatchValidateSign` as its sole authorization check for a value-moving action (claim/mint/withdraw/approve — the exact pattern in the report) is exposed to unauthorized replay of a previously-valid signature on a different chain instance or a different, identically-shaped contract deployment, because the account address whose permission is checked and its threshold/keys can be identical across java-tron networks while the value or entitlement referenced by the same `data`/`permissionId` combination differs. This is a direct authorization-bypass / replay class impact, matching the "unauthorized claiming"/loss-of-funds pattern of the external report, and it is baked into the precompile's own hash construction rather than being purely a caller mistake that could be trivially avoided, since the precompile's documented interface offers no reserved field for chain/contract binding.

### Likelihood Explanation
Exploitability depends entirely on downstream dApp design (whether the dApp includes a chain id / contract address inside the `data` argument). Any dApp author reproducing the natural, minimal usage pattern shown in java-tron's own test suite (signing over an opaque payload with no domain separation) is vulnerable, exactly as PhiFactory's authors were. Because `ValidateMultiSign`/`BatchValidateSign` are core, documented, publicly reachable TVM primitives (unprivileged — any contract can call them, and any externally-owned account can supply signatures), the likelihood of at least one popular dApp misusing them this way is comparable to the likelihood that motivated the original H-01 report.

### Recommendation
Update the precompile's hash construction (or at minimum strongly document it) so that the signed payload mandatorily includes: chain-specific data (e.g. `block.chainid`-equivalent / genesis block id) and the calling contract's address, similar to how `Claimable::signatureClaim` re-injects `block.chainid` before verifying, so dApps relying on `ValidateMultiSign`/`BatchValidateSign` cannot omit domain separation by mistake. Alternatively, treat this purely as an application-layer responsibility and add explicit warnings to the TIP/precompile documentation instructing dApp developers to always embed a chain id and verifying-contract address in the `data` field, analogous to EIP-712 domain separators.

### Proof of Concept
1. Deploy the same dApp contract bytecode (which authorizes an action solely via a passing call to `ValidateMultiSign`) on two java-tron networks that share account-address derivation (e.g. Mainnet and a private/consortium fork, or two independently bootstrapped testnets), and create an account with identical address and identical multi-sig `Permission` (same keys/threshold) on both.
2. On network B, have the permission holders sign `toSign = sha256(address || permissionId || data)` where `data` encodes some low-value action (e.g. `artId=1`).
3. Reuse the exact same `(address, permissionId, data, signatures[])` tuple in a call to the dApp on network A, where `artId=1` corresponds to a high-value entitlement.
4. `ValidateMultiSign.execute` recomputes the identical hash (per `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1062-1064`) and returns `true` because address, permissionId, and signatures all match — the dApp on chain A executes the high-value action using a signature that was only ever intended for chain B.

            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
