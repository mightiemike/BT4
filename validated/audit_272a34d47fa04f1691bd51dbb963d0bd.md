## Finding: `write_set` bytes are never hash-checked against `TransactionInfo.state_change_hash` during backup restore

### Title
Backup transaction restore commits `WriteSet` bytes without verifying `state_change_hash`, allowing corrupted/tampered write sets to be accepted as authentic - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
Aptos's `TransactionInfo` binds a transaction to its `write_set` via `state_change_hash = CryptoHash::hash(write_set)`, and this binding is enforced whenever a `TransactionOutputListWithProof` is verified against a ledger info [1](#0-0) . However, the backup/restore code path that loads transaction backup chunks (`TransactionChunkFormat::V0`/`V1`) reads `(Transaction, PersistedAuxiliaryInfo, TransactionInfo, Vec<ContractEvent>, WriteSet)` tuples from the backup file, but only wraps the `Transaction`/`TransactionInfo`/events into a `TransactionListWithProof` for verification — the `write_set` is excluded from that verification object entirely.

### Finding Description
In `LoadedChunk::load`, the raw backup record is deserialized into `txn`, `aux_info`, `txn_info`, `events`, `write_set` [2](#0-1) . The verification object built afterward is a `TransactionListWithProofV2` wrapping `TransactionListWithProof::new(txns, Some(event_vecs), Some(manifest.first_version), TransactionInfoListWithProof::new(range_proof, txn_infos))`, and `write_sets` is kept as a separate, unverified `Vec<WriteSet>` [3](#0-2) .

`TransactionListWithProof::verify()` only checks: (1) transaction hash matches `txn_info.transaction_hash()`, (2) the `TransactionInfoListWithProof` is proven against the ledger info's accumulator root, and (3) event root hashes match if events are present [4](#0-3) . It never touches `write_set` or `state_change_hash`. This is different from `TransactionOutputListWithProof::verify()`, used elsewhere (e.g. state-sync output application), which explicitly re-hashes the write set and compares it to `txn_info.state_change_hash()` [1](#0-0) .

After loading, the unverified `write_sets` are carried through `save_before_replay_version` and handed to `restore_handler.save_transactions(...)` [5](#0-4) , which persists them via `save_transactions_impl` → `WriteSetDb::put_write_set` and, when `kv_replay` is set, directly feeds them into `state_store.calculate_state_and_put_updates` to compute and commit the new JMT state root [6](#0-5) . Nowhere in this path is `CryptoHash::hash(&write_set)` compared against the accepted `txn_info.state_change_hash()`, even though `txn_info` itself has just been cryptographically proven against the ledger info's accumulator root.

Because the accumulator/ledger-info proof only binds the opaque `TransactionInfo` (via its own hash, which includes `state_change_hash` as a field), and the restore code never re-derives and compares `state_change_hash` from the actual `write_set` bytes it is about to commit, a backup archive (or any other component that supplies the `(txn_infos, write_sets)` pair to this restore path) could smuggle in a `write_set` whose content does not match the hash committed on-chain, while every other check (transaction hash, event root, accumulator proof) still passes. The result is a `WriteSetDb` and JMT state store populated with state values that are inconsistent with the authenticated `TransactionInfo.state_change_hash`, i.e., committed state diverging from the correct/verified result.

### Impact Explanation
If exploited (e.g., via a compromised/tampered backup source, or a bug elsewhere that pairs mismatched write sets with genuine `TransactionInfo`s), a node restoring from this backup would silently persist state values that do not correspond to the cryptographically-proven transaction outcome. During `kv_replay`, this directly corrupts the durable state tree used to answer state proofs and API queries, and any subsequent proof serving from this data would be internally consistent (JMT built from bad values) but semantically wrong relative to the real, network-agreed ledger state — a mainnet state-integrity violation matching the "committed state differs from correct VM result / corrupts durable ledger data" and "authenticated API output bound to wrong ... proof context" impact classes.

### Likelihood Explanation
This requires control over, or corruption of, the backup file contents supplied to the restore tool (the restore operator trusts the backup source and the `LedgerInfoWithSignatures`/accumulator proof to authenticate `txn_infos`, but not the write sets riding alongside them in the same record). This is a real gap in defense-in-depth for the restore path specifically, but it is bounded by needing a malicious/corrupted backup artifact and an operator using `kv_replay`/direct restore rather than full replay-from-genesis (full VM replay would independently recompute the write set and likely reveal any inconsistency); this narrows exploitability compared to a fully unprivileged on-chain path.

### Recommendation
In `LoadedChunk::load` (or immediately before persisting write sets in `save_transactions`), verify `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every transaction, mirroring the check already performed in `TransactionOutputListWithProof::verify()`, and reject the chunk if the hashes disagree.

### Proof of Concept
Not independently reproducible without a live restore harness in this session; the flow above is derived from static tracing of `LoadedChunk::load`, `TransactionListWithProof::verify`, and `restore_utils::save_transactions_impl`. I was not able to fully verify whether any downstream check (e.g., in `RestoreHandler::save_transactions` or `state_store::calculate_state_and_put_updates`) independently re-validates `state_change_hash` against the write set before commit — the `restore_handler.rs`/`restore_utils.rs` code I inspected does not perform such a check, but a full audit of all callers of `save_transactions` was not completed within the available tool budget. I recommend a Devin session with full file access to confirm no other guard exists before treating this as conclusively unmitigated.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
