## Finding: State-checkpoint (state-root) hash is never verified in `TransactionOutput::ensure_match_transaction_info`, silently masking state divergence during replay/backup verification

### Title
Replay/backup verification accepts transaction outputs with a divergent state-checkpoint root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator that decides whether a locally-computed `TransactionOutput` matches a version's authenticated `TransactionInfo` (the leaf that is proven into the accumulator/`LedgerInfo`, and hence signature-authenticated). It checks status, gas, write-set hash, and event-root hash, but it explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that bind a version to the actual Sparse-Merkle/Jellyfish-Merkle state root. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` validates transaction status, gas used, the write-set hash against `txn_info.state_change_hash()`, and the event-root hash against `txn_info.event_root_hash()`. [2](#0-1) 

It then stops, with a comment openly acknowledging the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

`state_checkpoint_hash`/`hot_state_checkpoint_hash` are per-version (or per-checkpoint) commitments of the actual world-state tree, distinct from the write-set hash — they capture the *materialized, cumulative* state, not just the delta applied by one transaction. Because `TransactionInfo` is hashed as a whole and that hash is the accumulator leaf proven under the validator-signed `LedgerInfo`, `state_checkpoint_hash` is an authenticated value. Yet no code path re-derives the local state root after replay and compares it to this authenticated field at the point where outputs are validated against `TransactionInfo`.

This comparator is used by every consumer that needs to establish "my locally re-executed transaction produced the state recorded on-chain":
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, used by chunk-executor "verify" mode during replay/execution verification. [4](#0-3) 
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the tool whose entire purpose is to replay an archived chain and assert local computation matches the archived, authenticated data. [5](#0-4) 
- `aptos-move/cli/src/commands.rs`, used when simulating/replaying a mainnet transaction via the CLI. [6](#0-5) 

By contrast, the normal state-sync commit path (`StateSyncChunkVerifier::verify_chunk_result`) validates full `TransactionInfo` equality (`ensure_transaction_infos_match`), which does bind the checkpoint hash because it compares the whole re-assembled `TransactionInfo` object (including checkpoint hashes) rather than going through `ensure_match_transaction_info`. [7](#0-6) 

So the gap is specifically in the standalone replay/verify tools (`replay_on_archive`, `chunk_executor::verify_execution`, CLI transaction replay), not the live consensus commit path.

### Impact Explanation
Storage/backup restore workflows and `replay_on_archive`/`replay-verify` are the mechanisms operators, auditors, and node operators use to assert that a restored/backup-derived ledger (or an archived history) truly reflects the authenticated on-chain state, including its Merkle state roots. Because `ensure_match_transaction_info` never compares the recomputed state root to `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, these tools can report a "successful" verified replay even when the resulting state tree (and thus every account balance/resource reachable through state proofs from that checkpoint) diverges from the authenticated ledger. This corrupts the meaning of "verified" for any downstream trust decision (e.g., accepting a restored DB as canonical, or trusting `replay-verify` output as proof that archived history is intact), satisfying the "restore paths must not reinterpret committed data into a different ledger state" and "replay ... divergence" integrity gates.

### Likelihood Explanation
This requires no privileged access or malicious peer collusion to trigger: any bug in state-tree computation (JMT/SMT logic, KV restore ordering, hot-state handling, or a data-corruption bug elsewhere in storage) that produces a wrong state root but a still-correct write-set/event hash for the affected transaction(s) would go undetected by these tools. The comment in the code confirms the maintainers are aware this exact scenario ("the authenticated position state root diverges from local execution") is currently unguarded, i.e., it is a known, reachable, self-acknowledged gap rather than a theoretical one.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` (or provide it the recomputed checkpoint hash(es) at the call sites in `chunk_executor::verify_execution` and `replay_on_archive::execute_and_verify`) to assert equality between the locally-derived `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` and the corresponding fields on `txn_info`, failing verification (matching the existing `ensure!` pattern used for write-set/event-root/gas/status) whenever they diverge, before any feature that further relies on this comparator (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled.

### Proof of Concept
Not applicable as a runnable exploit — the finding is a structural/logical proof: `ensure_match_transaction_info`'s implementation (lines 2139-2204 of `types/src/transaction/mod.rs`) demonstrably never reads or compares `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, while its own inline TODO comment documents the exact consequence for `replay_on_archive`. Any replayed transaction whose write-set hash and events match, but whose materialized state root differs from the archived, ledger-info-authenticated `state_checkpoint_hash`, will pass this function's checks with `Ok(())`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
