### Title
Governance toggle of `UNFREEZE_DELAY_DAYS` permanently strands already-pending `UnfreezeBalanceV2` balances - ([File: actuator/src/main/java/org/tron/core/actuator/WithdrawExpireUnfreezeActuator.java])

### Summary
The bug class in the report is: a two-phase flow (request → delay → finalize) where an eligibility/config check performed only at "request" time can be invalidated before "finalize" time, permanently stranding the user's funds for at least the delay duration (and potentially forever, since the finalize path itself re-checks the now-invalidated condition). The java-tron analog is the `UnfreezeBalanceV2` → `WithdrawExpireUnfreezeContract` flow gated by the dynamic parameter `UNFREEZE_DELAY_DAYS` / `supportUnfreezeDelay()`.

### Finding Description
`UnfreezeBalanceV2Actuator.execute()` moves a user's frozen balance into the `unfrozenV2` list with an expiry computed from `dynamicStore.getUnfreezeDelayDays()`: [1](#0-0) 

Every actuator in this delayed-unfreeze family — `FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`, and `WithdrawExpireUnfreezeActuator` — gates on the same live dynamic-store flag `supportUnfreezeDelay()` at `validate()` time, not at the time the user's `unfrozenV2` entry was created: [2](#0-1) [3](#0-2) 

`supportUnfreezeDelay()` is simply `getUnfreezeDelayDays() > 0`: [4](#0-3) 

`UNFREEZE_DELAY_DAYS` is a committee/governance proposal parameter that is written unconditionally on every approved proposal (unlike some other "sticky" flags such as `ALLOW_CANCEL_ALL_UNFREEZE_V2`, which explicitly checks `if (getAllowCancelAllUnfreezeV2() == 0)` before writing so it can only be turned on once): [5](#0-4) [6](#0-5) 

Because `UNFREEZE_DELAY_DAYS` can be re-proposed and set back to `0`, and `supportUnfreezeDelay()` re-derives its answer from the *current* value of that store entry rather than from a value snapshotted when the user's `unfrozenV2` entry was created, a user who already has funds sitting in the `unfrozenV2` list (added via `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor`, whose `unfreezeExpire()` logic only releases entries whose `unfreezeExpireTime() <= now`) can end up unable to invoke `WithdrawExpireUnfreezeContract` once the parameter is set back to `0`, because `WithdrawExpireUnfreezeActuator.validate()` unconditionally throws before even checking the expiry list: [7](#0-6) 

This is structurally identical to the `Staking.finalizeStake()` bug class: an eligibility condition checked at the "start" of a delayed two-phase operation can silently change during the delay, and the "finalize" step re-checks the now-different condition instead of honoring the state at request time, locking the user's funds for at least the delay period (and here, indefinitely, since the only way to unlock them is if the committee separately restores `UNFREEZE_DELAY_DAYS > 0` — and even then, the automatic release path (`unfreezeExpire()`) is only invoked as a side effect of calling one of the very actuators that are themselves gated behind `supportUnfreezeDelay()`).

### Impact Explanation
Impact is Medium: user TRX balance that has already passed through `UnfreezeBalanceV2` becomes inaccessible via any of the delayed-unfreeze actuators (`WithdrawExpireUnfreezeContract`, further `UnfreezeBalanceV2Contract`, `CancelAllUnfreezeV2Contract`, `FreezeBalanceV2Contract`) as soon as `UNFREEZE_DELAY_DAYS` is proposed back to `0`, because all of them share the identical `supportUnfreezeDelay()` precondition. Funds are not lost/stolen, but are locked out of the user's control for an indeterminate period tied to governance action, mirroring the reported bug's "locked for extended period" impact.

### Likelihood Explanation
Likelihood is Medium: it requires a committee proposal to change `UNFREEZE_DELAY_DAYS` while users have pending `unfrozenV2` entries — a legitimate governance action, not an attack, exactly as in the original report where token delisting is a normal admin action rather than malicious behavior. The `ProposalService` code shows no guard preventing `UNFREEZE_DELAY_DAYS` from being lowered/zeroed after being enabled (contrast with `ALLOW_CANCEL_ALL_UNFREEZE_V2`, which is explicitly protected against being changed twice), so this reachable path exists in the current implementation.

### Recommendation
Snapshot the eligibility/config state relevant to a delayed operation at the time the delayed entry is created (e.g., store enough information in the `UnFreezeV2` record, or decouple `WithdrawExpireUnfreezeActuator`'s gating check from the live `supportUnfreezeDelay()` flag so that already-pending entries can always be withdrawn once their `unfreezeExpireTime` has passed, regardless of the current value of `UNFREEZE_DELAY_DAYS`). Alternatively, make `UNFREEZE_DELAY_DAYS`, like `ALLOW_CANCEL_ALL_UNFREEZE_V2`, a one-way/write-once proposal parameter so it cannot be lowered back to 0 once enabled while users may have pending balances.

### Proof of Concept
1. Committee approves `UNFREEZE_DELAY_DAYS = N` (N>0), enabling `FreezeBalanceV2Contract`/`UnfreezeBalanceV2Contract`/`WithdrawExpireUnfreezeContract` (see `ProposalService.process`, case `UNFREEZE_DELAY_DAYS`).
2. A user calls `FreezeBalanceV2Contract` then `UnfreezeBalanceV2Contract`; their balance moves into `unfrozenV2` with `unfreezeExpireTime = now + N * FROZEN_PERIOD` (`UnfreezeBalanceV2Actuator.calcUnfreezeExpireTime`).
3. Before that expiry time is reached and processed, the committee approves a new `UNFREEZE_DELAY_DAYS = 0` proposal; `ProposalService.process` unconditionally calls `dynamicStore.saveUnfreezeDelayDays(0)`.
4. Once the entry's `unfreezeExpireTime` passes, the user calls `WithdrawExpireUnfreezeContract` to claim it; `WithdrawExpireUnfreezeActuator.validate()` now throws `"Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee"` because `dynamicStore.supportUnfreezeDelay()` is false, permanently blocking withdrawal of the already-expired, already-pending balance until/unless the committee re-enables the parameter.

            .map(ByteArray::toLong)
