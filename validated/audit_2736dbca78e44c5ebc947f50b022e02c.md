### Title
Replay-verify comparator omits state root checks, letting corrupted committed state pass authenticated verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by the chunk-replayer's `verify_execution` path (backing `db-tool replay-verify` and CLI transaction replay) to confirm that locally re-executed output matches the trusted, ledger-info-proven `TransactionInfo`, never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is explicitly acknowledged by an in-code TODO but is a live, unmitigated gap today.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  checks transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against the authenticated `TransactionInfo`, but explicitly skips the state/hot-state/position checkpoint hashes, as documented by its own comment: [2](#0-1) 

This function is the sole correctness oracle used by `ChunkExecutorInner::verify_execution`, which is invoked from `remove_and_replay_epoch` whenever `verify_execution_mode.should_verify()` is true — i.e., during `db-tool replay-verify` (`storage/db-tool/src/replay_verify.rs`) and `TransactionReplayer::enqueue_chunks`: [3](#0-2) 

Because write-set hash equality does not imply state-checkpoint (Sparse Merkle Tree) root equality — a bug in state merklization, hot-state tracking, sharded JMT commit, or position-state trees could apply the identical key/value writes yet compute a divergent root hash — this verification path is blind to state-root corruption. The write set matching is necessary but not sufficient to prove the committed SMT root is correct.

### Impact Explanation
`replay-verify` exists specifically to detect exactly this class of bug: "committed state that differs from the correct VM result." If a bug elsewhere in the merklization/commit pipeline (JMT batch computation, sharded state cache, hot-state promotion, or the newer native-position tree) corrupts the state root while leaving the write set values themselves correct, `replay-verify` will report success even though the previously-committed `state_checkpoint_hash` (and, when enabled, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) is wrong. This directly matches the "Wrong accumulator root/Merkle proof/state proof accepted as valid" and "authenticated ... output bound to the wrong ... proof context" state-integrity categories: an authenticated proof-bearing verification path silently accepts state divergent from the true VM output.

### Likelihood Explanation
This is not a hypothetical: it is a code-documented gap (the TODO explicitly says the comparator "ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"). Triggering it does not require an attacker — it requires only that some other latent bug (in JMT/hot-state/position-state computation) corrupt a checkpoint root while preserving the write set, at which point the safety net (replay-verify) fails silently. Given `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are newly introduced, not-yet-hardened features, and state-root computation is inherently more complex/bug-prone than write-set hashing, the likelihood of an undetected divergence is non-trivial before these checks are added.

### Recommendation
Extend `ensure_match_transaction_info` (or a caller in the chunk-replayer verification path) to recompute the state checkpoint hash(es) from the resulting `LedgerStateSummary`/`PositionStateWithSummary` after each checkpoint transaction and assert equality against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` whenever these are `Some` in the trusted `TransactionInfo`. This should be done before (or gated identically to) enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on mainnet, as the code comment itself recommends.

### Proof of Concept
Not applicable as a live exploit — this is a verification-tooling gap, not a directly triggerable state-corruption bug. Demonstration path: 1) construct (via test-only hooks) a `TransactionOutput` whose write set matches a target `TransactionInfo`'s `state_change_hash` but whose actual resulting SMT root would differ from `state_checkpoint_hash` (e.g., by feeding an execution path that produces identical writes through a diverging merklization function); 2) run it through `ChunkExecutorInner::verify_execution`/`ensure_match_transaction_info`; 3) observe it returns `Ok(())` despite the state-root mismatch, confirming the checkpoint-hash blind spot as shown at [4](#0-3) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
