### Title
Cross-network replay of security-council-signed `BatchProofMethodId` bodies between `Nightly` and `TestNetworkWithForks` — ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the identical `chain_id` value `5665`, and the shipped default security-council public keys for both networks (`NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` / `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS`) are configured via the same environment-variable names with the same hardcoded fallback values. This means a byte-identical `BatchProofMethodId` blob (body + 3-of-5 signatures) that is valid on one of these two networks is also valid on the other, defeating the chain-id check's documented purpose of preventing cross-network replay.

### Finding Description
The binding claimed by the code's own doc comment is:
`chain_id(network A) == chain_id(network B) ⇒ A == B` (chain id uniquely identifies the network for anti-replay purposes).

In practice, at `crates/light-client-prover/src/circuit/mod.rs` lines 763-770:
```
sov_rollup_interface::Network::Nightly => 5665,
sov_rollup_interface::Network::TestNetworkWithForks => 5665,
``` [1](#0-0) 

so the binding fails: `chain_id(Nightly) == chain_id(TestNetworkWithForks)` while `Nightly != TestNetworkWithForks`.

In `run_l1_block`'s `DataOnDa::BatchProofMethodId` arm, the only anti-replay checks are (1) `activation_l2_height > last_activation_height`, (2) `circuit_chain_id == batch_proof_method_id.body.chain_id`, and (3) `verify_method_id_security_council`: [2](#0-1) 

Notably, unlike the `Complete`, `Aggregate`, and `SequencerCommitment` arms, this arm performs no `blob.sender()` check, so any unprivileged party who can inscribe a Bitcoin reveal transaction on the target network's DA source can submit this blob.

Because `verify_method_id_security_council` verifies signatures over `body.serialize()` (which includes `chain_id`), and because both `chain_id` and — by default — the security-council pubkeys are identical for `Nightly` and `TestNetworkWithForks` (see `crates/light-client-prover/src/circuit/initial_values.rs` lines 500-646, both reading the same `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1..5` env vars with the same fallback constants): [3](#0-2) 

a signed body originally authorized by the security council for `TestNetworkWithForks` will pass all three checks when replayed verbatim into a `Nightly`-configured light client prover (or vice versa), as long as the target network's own last-activation-height ordering condition permits it. `BatchProofMethodIdAccessor::insert` then commits the unintended method id upgrade to that network's JMT state.

### Impact Explanation
If exploited, `BatchProofMethodIdAccessor::insert` records a batch-proof method id upgrade on a network the security council never authorized for that specific network, matching the explicitly listed Critical category "a sequencer commitment or method-id upgrade accepted that was never authorised." Future `Complete`/`Aggregate` proofs on the victim network would then be verified against this unintended method id via `Z::verify` in `process_complete_proof`, potentially accepting proofs the security council never sanctioned for that chain. The attack is repeatable per captured blob and requires only the ability to inscribe a Bitcoin reveal transaction — no sender/authorization check gates the `BatchProofMethodId` arm.

However, `TestNetworkWithForks` is explicitly documented as "used for testing purposes only" (`crates/sovereign-sdk/rollup-interface/src/network.rs` line 16), and `Nightly` is a development/CI network (mock-DA restricted to Nightly, per `initial_values.rs` lines 671-698). Neither variant is `Mainnet`, `Testnet`, or `Devnet` — the networks intended to hold real bridged BTC. The blast radius of this specific chain-id collision is therefore confined to non-production test/nightly environments, not real bridge value.

### Likelihood Explanation
Preconditions: (1) the two colliding networks (`Nightly`, `TestNetworkWithForks`) must both be reachable/operated with a public DA source the attacker can inscribe transactions into; (2) the operator must not have overridden the `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1..5` env vars differently per network (defaults are identical). Given these networks are internal test/nightly deployments, operators may plausibly run them with default/shared key material, making this feasible with minimal Bitcoin inscription fees. This is a genuine code defect in `citrea_network_to_chain_id` but its real-world severity is bounded by the non-production nature of both affected network variants.

### Recommendation
Assign a unique, non-colliding `chain_id` to `Network::TestNetworkWithForks` (distinct from `Nightly`'s `5665`) in `citrea_network_to_chain_id`, and ensure the security-council public keys and any other network-scoped secrets are never defaulted identically across distinct `Network` enum variants.
