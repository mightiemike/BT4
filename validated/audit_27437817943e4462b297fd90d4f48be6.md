### Title
`ensure_match_transaction_info` skips checkpoint-root validation, letting replay-verify accept a diverged position/state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  is the sole comparator used by chunk-executor replay verification to check that a locally re-executed transaction matches the committed/authenticated `TransactionInfo`. It validates status, gas used, write-set hash, and event root, but explicitly skips the state checkpoint hash, hot-state checkpoint hash, and `position_state_checkpoint_hash` fields carried by `TransactionInfo::V1`, per the code's own TODO comment.

### Finding Description
The function is called from `ChunkExecutorInner::verify_execution` in [2](#0-1)  — the exact code path used for replay-verify (e.g., `db-tool replay-on-archive`, `TransactionReplayer::remove_and_replay_epoch`) to check that transactions replayed from a backup/archive produce results matching the transaction infos already committed and anchored to a signed `LedgerInfo`. `TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (see the `builder_v1` constructor at [3](#0-2) ), all of which are folded into the `TransactionInfo` hash that ultimately becomes an accumulator leaf under the ledger's signed root. Despite this, `ensure_match_transaction_info` never recomputes or compares these checkpoint hashes against the locally computed state summary — it only checks `state_change_hash` (write-set hash) and `event_root_hash`. The comment in the code makes the gap explicit: "this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

### Impact Explanation
If a node's local state-checkpoint computation (state Merkle root, hot-state root, or the new "position" native state root gated by `compute_trading_native_state_roots`, referenced throughout `execution/executor/src/workflow/do_state_checkpoint.rs`) diverges from what is embedded in the committed, signature-verified `TransactionInfo`, replay-verify will still report success because the divergent field is simply never checked. This defeats the core security property of replay verification/backup restore auditing: that re-executing transactions and comparing to committed `TransactionInfo`s (which are bound into the accumulator root under a validator-signed `LedgerInfo`) detects any committed-state corruption or divergent execution. An operator restoring from backup, or auditing archived history, could be silently told the ledger state is consistent while the actual state-checkpoint root differs — masking a corrupted or forked state tree that would otherwise be caught by proof/verification tooling before it's trusted or served to clients.

### Likelihood Explanation
This is a latent gap rather than an actively-exploited path today: `TransactionInfo::V1`/checkpoint-hash fields and the `compute_trading_native_state_roots` feature are newer additions (as referenced by `execution/executor/src/workflow/do_state_checkpoint.rs` and the feature flag in `types/src/on_chain_config/aptos_features.rs`), and the comment indicates this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." I could not verify from the available index whether this feature is currently enabled on mainnet — if it is not yet enabled, the checkpoint-root divergence has no live effect (state/hot-state checkpoint hash checks were presumably already covered elsewhere, or the field is not populated). If/when the feature is turned on, or when hot-state checkpoint hashing becomes mainnet-live, the gap becomes directly exploitable for silently passing replay-verify despite state divergence.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values produced by local `DoStateCheckpoint` output before returning `Ok(())`, and require callers (chunk-executor replay path, debugger/db-tool paths) to supply the locally computed checkpoint hashes. This should be done prior to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or exposing hot-state checkpoint hashes to production replay/verify flows.

### Proof of Concept
Not directly exploitable as a standalone PoC without controlling the local state-checkpoint computation; the gap is demonstrated in code review: [4](#0-3)  explicitly documents that the comparator omits checkpoint-hash validation, and its only caller in the replay-verify path, `verify_execution` in [5](#0-4) , never independently checks these fields elsewhere in the loop.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
