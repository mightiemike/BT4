## Finding: Replay-verify integrity check silently ignores state/hot-state/position checkpoint root hashes

### Title
Replay/verify path accepts divergent authenticated state-checkpoint roots as valid transactions - (`File: types/src/transaction/mod.rs`)

### Summary
The generic ERC20 report reduces to one invariant: *a critical state-mutating operation must be validated against its authoritative source before being treated as successful, otherwise stale/incorrect state gets committed silently.* The Aptos-native analog is `TransactionOutput::ensure_match_transaction_info`, the function used by all chunk-replay/verify tooling to confirm that a locally re-executed transaction output matches the persisted `TransactionInfo` for that version. It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or the newer `position_state_checkpoint_hash` fields, as the code itself documents.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator between a re-executed `TransactionOutput` and the `TransactionInfo` stored/authenticated in the ledger (via the transaction accumulator and ledger-info signatures). It validates: [1](#0-0) 

But it deliberately skips the checkpoint-hash fields, with the code's own TODO acknowledging the gap: [2](#0-1) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class committed/authenticated fields alongside `state_change_hash` and `event_root_hash`: [3](#0-2) 

These checkpoint hashes are produced by `DoStateCheckpoint`, which computes both the ordinary Jellyfish-Merkle/SMT state-checkpoint root and, when `compute_trading_native_state_roots` is enabled, a separate "position state" root derived from a distinct SMT keyed on position writes: [4](#0-3) 

`ensure_match_transaction_info` is the correctness gate used by every non-consensus replay/verify entry point: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

Because the comparator never re-derives and compares the checkpoint-hash fields against the `TransactionInfo` that was accumulator-proven and signed by validators, any divergence confined to those fields (write-set/events/status/gas all matching, but the state-checkpoint/hot-state/position-state root differing) passes silently as `Ok(())`.

### Impact Explanation
This breaks the state-commitment integrity invariant required by the gate: "Committed state that differs from the correct VM result... accepted as valid" and "replay... must preserve deterministic proof binding." Concretely: `db-tool replay-on-archive`, the Aptos debugger's replay-verify command, and CLI replay-verify commands are the tools operators and auditors use to confirm that an archived/synced ledger's committed state actually matches VM execution. If a bug (in execution, in the trading-native/position-state feature, in the hot-state feature, or in a corrupted/malicious backup/archive) causes the recomputed state-checkpoint or position-state root to diverge from what was actually accumulator-proven and signed, this comparator will not detect it — it will report a successful replay-verify while the authenticated position/hot state root has silently diverged from local execution. This is a hard-fork-class integrity gap: the very tool meant to catch state divergence during replay/restore cannot see divergence localized to the checkpoint-hash fields, undermining confidence in restore/backup verification and any downstream reliance on `compute_trading_native_state_roots`.

### Likelihood Explanation
Low-to-moderate likelihood of triggering in practice today, since `compute_trading_native_state_roots` / hot-state gating are newer, feature-flagged paths, but the gap is unconditional in the comparator itself (it doesn't check `state_checkpoint_hash` even in the always-on V0 case) and is explicitly flagged by the developers' own TODO, indicating it's a known, currently-unaddressed hole rather than a hypothetical one.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present) against the values carried in the passed-in `TransactionInfo`, mirroring the existing `write_set_hash`/`event_root_hash` checks, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and more generally for all replay/verify callers.

### Proof of Concept
Not applicable as an exploitable transaction sequence — this is a verification-logic gap. Conceptual repro: construct/replay a chunk where the write set, events, gas, and status match `TransactionInfo` exactly, but the persisted `state_checkpoint_hash` (or `position_state_checkpoint_hash`) differs from what the local SMT/position-SMT would compute (e.g., via a bug in `DoStateCheckpoint::extend` or a corrupted backup blob for that field only). `TransactionOutput::ensure_match_transaction_info` at [9](#0-8)  will return `Ok(())`, and `replay_on_archive`/CLI replay-verify will report success despite the authenticated checkpoint root diverging from local execution.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
