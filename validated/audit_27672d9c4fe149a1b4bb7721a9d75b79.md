### Title
`ensure_match_transaction_info()` skips checkpoint-hash validation, letting corrupted authenticated state roots pass replay verification - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the function that authenticated replay/verification tooling uses to confirm a locally re-executed `TransactionOutput` matches the trusted, proof-carrying `TransactionInfo` for a version. It checks status, gas, write-set hash, and event-root hash, but the code contains an explicit acknowledgment that it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the state/hot-state/position Merkle roots.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- write-set hash vs `txn_info.state_change_hash()`
- event-root hash vs `txn_info.event_root_hash()`

It never compares any of the checkpoint-hash fields carried by `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), which are exactly the fields introduced to bind trading-native position state and hot-state roots into the accumulator-proven `TransactionInfo` [2](#0-1) . The code itself flags this gap in a TODO: [3](#0-2) 

This mirrors the report's bug class: a downstream consumer (`validateBalances`) trusts a flag/summary set earlier without re-verifying the full underlying state, allowing a divergence to slip through unnoticed. Here, `ensure_match_transaction_info` is the trust boundary between VM-computed state and the value bound into the accumulator-proven `TransactionInfo`, and it silently omits comparison of the checkpoint hash fields that bind the position/hot-state Merkle roots.

The impacted commit path is real: `assemble_transaction_infos()` in the executor already computes and threads `hot_state_checkpoint_hashes` and `position_state_checkpoint_hashes` into `TransactionInfoV1` when `transaction_info_v1` and `compute_trading_native_state_roots` are enabled [4](#0-3) , and `BlockExecutorConfigFromOnchain::with_features` gates this on-chain feature combination [5](#0-4) .

### Impact Explanation
If `compute_trading_native_state_roots` (or `hot_state_root_in_txn_info`) is enabled on-chain, but a node's local re-execution produces a different position/hot-state root than what is stored in the authenticated `TransactionInfo` (e.g., due to a storage/restore bug, a non-deterministic native computation, or a targeted divergence), `ensure_match_transaction_info` will report success anyway, since it never inspects the position/hot-state checkpoint hash. Any replay-verification or backup-restore tooling relying on this function (e.g., `aptos-move/cli/src/commands.rs`, which calls it twice) would falsely certify a replayed chain segment as matching, even though the authenticated position/hot state root has silently diverged from local execution — a hard-fork-class integrity failure that would go undetected by exactly the mechanism meant to catch it.

### Likelihood Explanation
This requires the on-chain features `transaction_info_v1`, `hotness_in_epilogue`, and `compute_trading_native_state_roots` to all be enabled, which is not yet standard mainnet configuration based on the surrounding comments describing this as a still-evolving "trading-native" feature. The vulnerability is real and confirmed by the code's own TODO comment, but I could not fully verify from the indexed code whether `compute_trading_native_state_roots` is presently active on mainnet, nor trace every downstream caller of `ensure_match_transaction_info` (only two call sites in `aptos-move/cli/src/commands.rs` were found by grep, and their exact usage context — e.g., whether it's part of a security-critical replay-verify path or an offline debugging CLI — was not fully explored due to the iteration limit).

### Recommendation
Extend `ensure_match_transaction_info` to also compare the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields of `self` (as recomputed by the caller) against those in `txn_info`, before returning `Ok(())`. This should be enabled unconditionally, or at minimum required whenever `compute_trading_native_state_roots`/`hot_state_root_in_txn_info` is active, and any replay-verify tool (`db-tool`, `aptos-move/cli`) must fail (not silently pass) on mismatch.

### Proof of Concept
Not independently reproducible from indexed code alone — the concrete PoC would require constructing a `TransactionOutput`/`TransactionInfo` pair where the write-set/events/gas/status match but the position or hot-state checkpoint hash differs, and showing `ensure_match_transaction_info(...)` returns `Ok(())`. The logical proof is the function body itself, which never reads `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` before returning `Ok(())` [1](#0-0) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
