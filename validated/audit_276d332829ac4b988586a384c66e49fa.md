### Title
Broadcast transaction path blocks on a busy-wait polling loop under a shared lock, enabling DoS via request flooding - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
The reported bug describes `ProposeAndWait` in `consortium-node`, which blocks the calling thread in a polling loop (`time.Tick(100ms)` up to 5 minutes) while waiting for an asynchronous operation to complete, making the service vulnerable to thread/resource exhaustion if flooded with requests. The analogous pattern in java-tron is `Manager.pushTransaction`, which is reachable from the unauthenticated `broadcastTransaction` RPC/HTTP entrypoint and spins on a `sleep`-based polling loop while holding a shared lock before doing the actual transaction processing.

### Finding Description
`Wallet.broadcastTransaction` is the entrypoint for any external actor submitting a transaction over gRPC/HTTP/JSON-RPC gateways [1](#0-0) . After a few cheap checks (signature length, pending-queue size, cache) it calls `dbManager.pushTransaction(trx)` [2](#0-1) .

Inside `Manager.pushTransaction`, the transaction is added to `pushTransactionQueue`, its signature is validated, and then the thread enters `synchronized (transactionLock)` and busy-waits with `TimeUnit.MILLISECONDS.sleep(SLEEP_FOR_WAIT_LOCK)` in a `while(true)` loop as long as `isBlockWaitingLock()` returns true, before acquiring the monitor and performing `processTransaction` / adding to `pendingTransactions`: [3](#0-2) 

This is structurally the same anti-pattern as `ProposeAndWait`: a single caller-facing entrypoint that, per invocation, ties up a thread in a sleep-and-recheck loop gated on a shared/global condition (`isBlockWaitingLock()`), and does so inside a `synchronized` block on a shared `transactionLock` object [4](#0-3) , meaning every concurrently broadcast transaction serializes on this same lock and each one can independently spin-wait for the block-production window to close.

### Impact Explanation
Because every `broadcastTransaction` call (accessible without authentication via HTTP `/wallet/broadcasttransaction`, gRPC, and JSON-RPC gateways) funnels into this same `synchronized (transactionLock)` busy-wait, a flood of concurrently submitted transactions can cause many request-handling threads to pile up waiting on the same lock/condition simultaneously. Unlike the queue-depth check (`isTooManyPending`) which is evaluated once before entering the lock [5](#0-4) , the busy-wait loop itself has no bound on the number of threads that can be parked in it at once, so under load this can exhaust request-handler thread pools, degrading or denying transaction processing for the node (a resource-exhaustion / availability issue), matching the "DoS via RPC-API" class called out in the report.

### Likelihood Explanation
The path is reachable by any anonymous network peer through the standard broadcast APIs, requiring no privileged role, no malicious peer collusion, and no dependency changes — only the ability to send transactions rapidly, which is the same "flood the endpoint" precondition as the original report. Exploitability depends on how often/long `isBlockWaitingLock()` returns true (i.e., how frequently block generation windows overlap with pending broadcast calls) and on thread-pool sizing for the RPC/HTTP layer, which I could not fully verify (the definition of `isBlockWaitingLock()` and `SLEEP_FOR_WAIT_LOCK` value were not retrieved within available tool calls).

### Recommendation
Avoid busy-wait sleep loops inside code paths triggered directly by unauthenticated network requests. Prefer an asynchronous/event-driven mechanism (e.g., a bounded queue with worker threads, or condition variables instead of polling sleeps) to signal when the block-waiting condition clears, and add explicit bounds on the number of threads/requests that can be queued or parked awaiting `transactionLock`, similar to the recommendation to rewrite `ProposeAndWait` to be asynchronous or to cap its blocking behavior.

### Proof of Concept
Not independently verified in this pass — I was unable to retrieve the concrete definitions of `isBlockWaitingLock()` and `SLEEP_FOR_WAIT_LOCK` (or confirm the thread-pool model for gRPC/HTTP broadcast handling) before running out of tool-call budget. A background Devin session with full repository access could confirm: (1) the exact conditions under which `isBlockWaitingLock()` stays true and for how long, and (2) whether the gRPC/HTTP servers use a bounded or unbounded thread pool for handling `broadcastTransaction`, to determine precisely how many concurrent flood requests are needed to exhaust the pool.
