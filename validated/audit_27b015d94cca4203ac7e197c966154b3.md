### Title
Stale index-cache read during liquidation lets a debt write-down (`socialize-debt-asset`) be priced against a pre-write-down index, mis-sizing collateral seized in the same transaction - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches each vault's liquidity/borrow index per `{timestamp, aid}` in `index-cache` and reuses the cached value for the rest of the transaction (`accrue-and-cache`, lines 245-257; `get-cached-indexes`, lines 944-945). Ztoken collateral pricing (`resolve-ztoken`, lines 343-347) and liquidation sizing (`scale-debt-for-liquidation`, lines 858-877) both read this cache directly instead of re-accruing. The code explicitly acknowledges that a debt write-down (`vault-socialize-debt`) moves a vault's `lindex` downward and therefore manually refreshes the cache afterward in `socialize-debt-asset` (lines 892-895, with the comment "Refresh cache with new indexes post-write-down (lindex decreased)"). Any earlier value computed within the same transaction from the pre-write-down cache entry - e.g. the size of collateral to seize - is not recomputed once the refresh happens.

### Finding Description
The position data model stores independent collateral and debt lists per account (`{ collateral: (list 64 {aid, amount}), debt: (list 64 {aid, scaled}) }`, lines 516-524), so a single position can simultaneously hold a ztoken (e.g. `zSTX`) as collateral and the underlying asset (`STX`) as debt.

During liquidation of such a position:
1. `get-notional-evaluation`/`calculate-asset-notional-value` (lines 514-574) values the `STX` debt via `accrue-and-cache(STX)` (lines 245-257, 565), populating `index-cache` for `{timestamp: stacks-block-time, aid: STX}` with the current index `L1`.
2. The same fold values `zSTX` collateral via the price oracle callcode path `resolve-ztoken` (lines 343-347), which reads `get-cached-indexes(STX)` - a plain `map-get?` with no accrual - and gets back the same `L1` lindex just cached in step 1.
3. Liquidation math (`process-collateral-asset`, `calc-final-liquidation-amounts`, `scale-debt-for-liquidation`, lines 789-877) sizes the collateral token amount to transfer to the liquidator using prices/indexes derived from `L1`.
4. If the position's debt cannot be fully covered from seized collateral, `socialize-debt-asset` (lines 879-903) is invoked for the `STX` debt: it calls `vault-socialize-debt` (which write-downs the vault's `lindex`, dropping it to `L2 < L1`) and then explicitly overwrites `index-cache` for `STX` with the fresh, lower `L2` value (lines 892-895).
5. The collateral token amount already computed in step 3 - sized against the stale, higher `L1` valuation - is used for the actual token transfer/redemption to the liquidator. It is never recomputed against `L2`.

This is a textbook "cached value not invalidated when its source moves" bug: the bound value is the `index-cache` entry for `{timestamp, aid: STX}`; the invalidating event is the `lindex` write-down performed inside `vault-socialize-debt`/refreshed in `socialize-debt-asset`; the later use is the collateral-sizing computation performed earlier in the same call using the now-stale `L1`. The interleaving is guaranteed by Clarity's sequential, single-threaded evaluation within one transaction: the collateral amount is computed before the debt-socialization branch executes, and Clarity provides no automatic re-evaluation of already-computed `let`-bound values after a later map mutation.

### Impact Explanation
Because the collateral amount transferred to the liquidator is fixed using the pre-write-down (inflated) index while the vault's real backing asset value has just been marked down, the liquidator extracts more collateral value than the post-write-down state actually supports. The shortfall is absorbed by the remaining ztoken holders of that vault, i.e. value is extracted from the pooled vault rather than being purely borne by the liquidated borrower as intended. This is a form of protocol insolvency / freezing of remaining depositors' funds, since the vault's real backing no longer matches the ztoken supply after the mis-sized transfer.

### Likelihood Explanation
Likelihood is Medium: it requires a single position that simultaneously carries `STX`-type debt and the corresponding `zSTX` ztoken as collateral, and that this specific liquidation produces bad debt requiring `socialize-debt-asset` to run for that same asset within the same call. This is a legitimate, code-permitted position configuration (mixed collateral/debt lists) and a bad-debt liquidation path the contract itself implements and documents, not a contrived edge case.

### Recommendation
Recompute (or re-price) any collateral amount that was derived from a cached index for asset `aid` immediately after `socialize-debt-asset` refreshes `index-cache` for that `aid`, or restructure liquidation so that the debt-socialization branch runs and refreshes indexes before collateral-sizing math executes, ensuring collateral transferred always reflects the post-write-down index rather than a value computed against a since-invalidated cache entry.

### Proof of Concept
1. Borrower position: debt = `{aid: STX, scaled: X}`, collateral includes `{aid: zSTX, amount: Y}` (position holds `STX` debt and `zSTX` collateral simultaneously).
2. Liquidator calls `liquidate` on this borrower when the position is unhealthy enough that liquidation results in bad debt on the `STX` leg.
3. `get-notional-evaluation` caches `STX` index as `L1` via `accrue-and-cache` (`v0-4-market.clar:245-257,565`) and prices `zSTX` collateral off the same `L1` via `resolve-ztoken`/`get-cached-indexes` (`v0-4-market.clar:343-347,944-945`).
4. Collateral-seizure amount for `zSTX` is computed from `L1` (`v0-4-market.clar:789-877`).
5. `socialize-debt-asset` runs for the `STX` debt shortfall, writing down the vault's true `lindex` to `L2 < L1` and refreshing `index-cache[STX]` to `L2` (`v0-4-market.clar:879-903`).
6. The already-computed `zSTX` amount from step 4 (sized against `L1`) is transferred to the liquidator, overpaying relative to the vault's now-lower true backing (`L2`), draining value from remaining `zSTX` holders. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

(define-private (scale-debt-for-liquidation
  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))
        ;; If debt was capped, scale collateral proportionally
        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))
    {
      scaled-to-remove: scaled-to-remove,
      debt-to-repay: debt-to-repay,
      coll-final: coll-final
    }))

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
