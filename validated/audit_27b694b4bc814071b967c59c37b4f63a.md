### Title
Reverted L1-Handler Transactions Are Marked as Permanently Consumed, Causing Loss of Bridged L1→L2 Funds - (File: crates/apollo_batcher/src/block_builder.rs, crates/apollo_batcher/src/batcher.rs)

### Summary
When an L1-to-L2 message (`L1HandlerTransaction`) executes but its entry point call reverts (analogous to ZetaChain's `onRevert()` failing after the tokens were already burned), the sequencer still treats the L1 message as **finally consumed**, exactly like a successful execution. Because the message is never distinguished from a rejected one in this path, the L1 sender has no way to reclaim or resubmit the message, and any value the message was meant to credit on L2 (e.g. a bridge deposit) is permanently lost if the L1-handler logic rolls back the crediting.

### Finding Description
An L1 message sender submits a message to L1 which becomes an `L1HandlerTransaction` on Starknet. In `blockifier`, `L1HandlerTransaction::execute_raw` executes the handler; if the inner `run_execute` call fails (a panic/assert in the target contract) or the post-execution gas-bound check fails, the transaction is not treated as an executor error — it is returned as `Ok(...)` with `revert_error: Some(...)`, i.e. a "reverted but accepted" transaction: [1](#0-0) 

In the batcher's `collect_execution_results_and_stream_txs`, every `L1Handler` input transaction unconditionally gets its hash inserted into `consumed_l1_handler_tx_hashes` **before** the result is even matched, and a reverted-but-`Ok` result is simply logged and added to `execution_infos_and_signatures` — it is never added to `rejected_tx_hashes`: [2](#0-1) 

Only transactions whose *executor* returned an outright `Err` (a distinct failure mode, e.g. state errors) are added to `rejected_tx_hashes`: [3](#0-2) 

At block commit time, `commit_proposal_and_block` computes `rejected_l1_handler_tx_hashes` as the intersection of `rejected_tx_hashes` and `consumed_l1_handler_tx_hashes`, and forwards `(consumed, rejected_l1_handler)` to the L1 events provider: [4](#0-3) 

Because a *reverted* (but accepted) L1-handler hash is present only in `consumed_l1_handler_tx_hashes` and never in `rejected_tx_hashes`, it is excluded from this intersection. The L1 events provider's `apply_commit_block` then partitions the consumed set using exactly that rejected-intersection, so the reverted transaction falls into `committed_txs`, not `rejected_and_consumed`: [5](#0-4) 

Per the documented flow, "committed" txs move from Pending to a final `Committed` state, whereas only the outright-rejected ones are unstaged and kept `Pending` (i.e., retriable): [6](#0-5) 

This means a reverted L1-handler transaction is treated identically to a successfully executed one with respect to L1 message consumption — the message can never be resubmitted or reprocessed, even though its state effects (e.g. crediting an L2 recipient with bridged tokens) were rolled back.

### Impact Explanation
This is structurally identical to the ZetaChain root cause: a value-bearing cross-domain message is irrevocably "spent" (burned/consumed) independent of whether the corresponding mint/credit on the destination side actually succeeds. Any L1→L2 bridging or messaging contract whose `@l1_handler` function can revert under some conditions (insufficient computed L2 gas within `l1_handler_max_amount_bounds`, a legitimate business-logic `assert` failing, a reentrancy/nonce guard, or any other panic) will have its associated funds permanently locked/lost, since:
- The message is marked `Committed` on L2 (no L1 resend is possible).
- No L2 state change occurred to credit the intended recipient (execution was aborted/rolled back).

This is a direct, unauthorized-loss-of-funds bug reachable by any L1 message sender without any operator/prover/validator privilege.

### Likelihood Explanation
High. An L1 message sender only needs their message's target `@l1_handler` to revert under any plausible condition (a common, expected occurrence for defensive bridge/contract logic, or simply an out-of-gas condition versus the L2-gas bound configured for L1 handlers). No cooperation from block producers or other privileged parties is required — this occurs automatically as part of normal block building whenever an admitted L1-handler transaction happens to revert during execution.

### Recommendation
Distinguish "reverted-but-executed" L1-handler transactions from "successfully executed" ones when deciding L1 message finality:
- Treat any `L1HandlerTransaction` whose `TransactionExecutionInfo.revert_error` is `Some(..)` the same way as a rejected transaction for the purpose of L1 message consumption/commit (i.e., add its hash to `rejected_tx_hashes`, or otherwise exclude it from `consumed_l1_handler_tx_hashes` being treated as final), so the corresponding L1 message stays `Pending` and can be retried/reprocessed (or provide an explicit compensating/refund mechanism on the contract side that's guaranteed to run).
- Add an integration test mirroring `reverted_l1_handler_tx_flow_test.rs` that specifically asserts the L1 message remains resubmittable (not `Committed`) after a reverted L1-handler execution.

### Proof of Concept
1. An L1 sender sends a bridging message to L2 (an `L1HandlerTransaction`) whose target `@l1_handler` credits tokens to a recipient, but includes a safety check (e.g. a supply cap, pause flag, or nonce check) that can legitimately fail.
2. The sequencer includes this transaction in a block. `run_execute` panics/reverts inside the handler; `L1HandlerTransaction::execute_raw` returns `Ok(TransactionExecutionInfo{ revert_error: Some(..), .. })` per [7](#0-6) .
3. `collect_execution_results_and_stream_txs` inserts the tx hash into `consumed_l1_handler_tx_hashes` and accepts it into `execution_infos_and_signatures` (not `rejected_tx_hashes`) as shown above.
4. `commit_proposal_and_block` computes `rejected_l1_handler_tx_hashes` (empty for this tx) and calls `l1_events_provider_client.commit_block(consumed, rejected_l1_handler, height)`.
5. `apply_commit_block` places the tx hash in `committed_txs` (final state), permanently marking the L1 message as consumed even though no tokens were credited on L2 — the funds encoded in the L1 message are unrecoverable.
