### Title
`liquidate-multi` strands liquidator-transferred collateral and unrepaid debt when bad-debt socialization fails mid-batch - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` iterates over a batch of positions via `(map call-liquidate positions)`, where `call-liquidate` invokes the public function `liquidate` directly (a same-contract function application, not a `contract-call?`) [1](#0-0) . Because `liquidate` is called as a plain in-contract function rather than through `contract-call?`, it does not get its own atomic rollback checkpoint; only the nested `contract-call?`s it makes to `.v0-market-vault` get individually checkpointed and merged into the enclosing (top-level `liquidate-multi`) transaction context as soon as they return `ok`. If `liquidate` subsequently fails later in its own body and returns `(err ...)`, `call-liquidate` returns that same `(err ...)` as one list element, but `map`/`liquidate-multi` swallow it — the batch as a whole still returns `(ok (list ...))`. The already-committed sub-effects from the failed `liquidate` invocation (collateral removed and sent to the receiver, and debt-remove-scaled applied) are therefore persisted even though the final bad-debt socialization step failed and the position's remaining debt was never written off.

### Finding Description
Inside `liquidate`, after debt/collateral processing and the primary repay:
1. `debt-remove-scaled` and `collateral-remove` are executed via `contract-call?` and, on success, their state changes are merged into the current transaction context [2](#0-1) .
2. If `no-collateral-left` is true, the function computes `fresh-debt-list` from the pre-fetched `pos-full` snapshot and calls `(fold socialize-debt-asset fresh-debt-list ...)`, then asserts the fold's success: `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [3](#0-2) .
3. `socialize-debt-asset` itself is a fold that "absorbs" failures of individual debt-asset write-offs (`unwrap!` to `failed-status`, then subsequent iterations are simply skipped via the early `(if (not (get success acc)) acc ...)` guard) [4](#0-3) . If any one of the remaining debt assets (other than the one being liquidated) fails to socialize — e.g., its `vault-socialize-debt`/`vault-accrue`/`debt-remove-scaled` call errors for that asset — the whole fold returns `success: false`, and the outer `asserts!` fires, making `liquidate` itself return `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`.

When `liquidate` is invoked directly (not via `contract-call?`) from within the same contract — as `call-liquidate` does — this `(err ...)` return does not trigger any automatic rollback of the collateral/debt-remove effects that were already committed via the preceding `contract-call?`s in step 1, because Clarity's automatic state-rollback-on-error is scoped to `contract-call?` boundaries and the top-level transaction, not to arbitrary same-contract function applications. In a solo call to `liquidate` (a signed transaction directly invoking it), the top-level transaction itself would still roll back everything on this final error, so the bug is invisible there. But when `liquidate` is called through `call-liquidate`/`map` inside `liquidate-multi`, the `(err ...)` value is merely collected into the output list; `liquidate-multi` still returns `(ok (list ...))` overall, so the whole batch transaction succeeds and the intermediate committed writes from the failed sub-call (collateral already transferred out to the receiver, some debt already zeroed via `debt-remove-scaled`) are permanently persisted on-chain, while the remaining "bad debt" for that borrower is never socialized/written off.

This is the closing-value analog of the referenced report's root cause: a multi-step operation performs value-moving side effects (collateral transfer, debt decrement) and only afterward runs a guard (`ERR-BAD-DEBT-SOCIALIZATION-FAILED`) whose failure is expected to undo everything — but the caller's own comment/design ("Failed liquidations return error codes but don't revert entire batch" [5](#0-4) ) explicitly relies on an isolation guarantee that Clarity does not actually provide for same-contract calls, stranding value/leaving inconsistent debt bookkeeping on abort of one leg of the batch.

### Impact Explanation
The position's collateral has already been transferred to the liquidator (or specified receiver) and part of its scaled debt already zeroed, but the socialization (write-off) of the position's *remaining* debt across other assets never completes and is never retried, because the position's `no-collateral-left` bookkeeping and the fresh debt list were computed against the pre-liquidation snapshot and the failure is silently absorbed by the batch. The result is orphaned debt with no matching collateral backing it in the vault's accounting — i.e., real assets left the protocol (to the liquidator) while the corresponding liability was not reduced/written off, corrupting protocol solvency accounting and/or leaving irrecoverable bad debt permanently unaddressed. This lands on the in-scope "protocol insolvency" / "permanent freezing of funds" impact classes.

### Likelihood Explanation
This requires no DAO compromise, oracle manipulation, or flashloan — it only requires: (a) a caller using the `liquidate-multi` batch entry point (an ordinary user-facing feature), and (b) one position in the batch having multiple simultaneous debt assets such that, once its primary collateral is exhausted, the socialization fold hits a failure for one of its other debt-asset write-offs (e.g., a transient vault-level condition on that specific asset's accrue/socialize call). Given `liquidate-multi` is explicitly designed and documented to support partial-failure semantics, and multi-asset debt positions with exhausted collateral are a normal state reachable during real liquidations, the trigger conditions are realistically reachable in production use, not a contrived edge case.

### Recommendation
Do not rely on same-contract direct function calls for isolation inside `liquidate-multi`/`call-liquidate`. Either:
- Wrap `liquidate` invocation via `as-contract (contract-call? .v0-4-market liquidate ...)` so each position genuinely gets its own atomic checkpoint that rolls back on error, or
- Restructure `liquidate` so the bad-debt-socialization guard is checked and applied *before* any collateral is transferred out / debt is decremented for the position, or
- Have `liquidate-multi` `try!`-propagate a failed sub-liquidation's error, causing the entire batch (and thus all its checkpointed writes) to revert, if partial-batch success cannot be safely supported given Clarity's atomicity model.

### Proof of Concept
1. Borrower has two debt assets (e.g., USDC and USDH) and one collateral asset that becomes fully liquidatable (`no-collateral-left` becomes true after this liquidation call).
2. Liquidator calls `liquidate-multi` with a list containing this borrower's position (and optionally others).
3. Inside `liquidate` (invoked via `call-liquidate`), the primary debt/collateral for the position are processed: `debt-remove-scaled` and `collateral-remove` succeed via `contract-call?`, sending collateral to the liquidator — these writes merge into the enclosing `liquidate-multi` transaction context [2](#0-1) .
4. `no-collateral-left` is true, so `fresh-debt-list` includes the borrower's second debt asset (USDH); the `fold socialize-debt-asset` runs and its `unwrap!` on `vault-socialize-debt`/`vault-accrue`/`debt-remove-scaled` for the USDH asset fails (e.g., due to a transient condition on that vault) [3](#0-2) .
5. `liquidate` returns `(err ERR-BAD-DEBT-SOCIALIZATION-FAILED)`; `call-liquidate` returns the same value into the `map` result list.
6. `liquidate-multi` still returns `(ok (list ... (err u...) ...))` overall [6](#0-5) , so the batch transaction commits. The liquidator's collateral receipt and the primary debt decrement from step 3 persist on-chain, while the borrower's USDH debt is never socialized/written off — an inconsistency between removed collateral and outstanding recorded debt.

Note: I was unable to execute this scenario in a live Clarity VM/test harness to empirically confirm the exact rollback granularity (same-contract call vs. `contract-call?` boundary) claimed here; this determination is based on Clarity's documented atomicity semantics rather than a directly observed test run in this index. If a Devin session with tooling access is available, running a Clarinet/`local-testing` simulation of this exact sequence would conclusively confirm or refute the persistence behavior described.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)

                                      debt-remove-scaled
