### Title
Cross-tenant session hijack via unauthenticated `X-Shopify-Shop-Domain` header trust in fulfillment-service authentication - ([File: packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts])

### Summary
`fulfillment-service/validate.ts` (and `flow/validate.ts`) only verify an HMAC over `rawBody`; unlike `webhooks/validate.ts`, neither performs a `checkWebhookHeaders`-style check that requires or binds a shop-domain header. For Flow this is safe because the shop identity (`shopify_domain`) is read from the HMAC-signed `rawBody` itself. For fulfillment-service, however, the consuming `authenticate.ts` in `shopify-app-remix`/`shopify-app-react-router` derives the shop strictly from the **unsigned** `X-Shopify-Shop-Domain` header, which is not covered by the HMAC and not validated by the library at all.

### Finding Description
`validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` computes the HMAC over `rawBody` only [1](#0-0) . Neither `flow/validate.ts` nor `fulfillment-service/validate.ts` call anything analogous to `checkWebhookHeaders` [2](#0-1) [3](#0-2) , so no header is required to be present or bound to the signed body.

For **Flow**, this gap is inert: `authenticateFlowFactory` extracts the shop identity from `payload.shopify_domain`, which is part of the HMAC-signed `rawBody` itself [4](#0-3) . An attacker cannot change the shop binding without invalidating the signature (which requires `apiSecretKey`, excluded per rules).

For **fulfillment-service**, the design differs: `authenticateFulfillmentServiceFactory` reads the shop from `request.headers.get(ShopifyHeader.Domain)` directly, independent of the signed body [5](#0-4) , then loads that shop's offline session via `ensureValidOfflineSession(params, shop)` and hands back an authenticated `admin` client scoped to that shop.

Exploit flow: an unprivileged attacker who is a legitimate merchant using the shared app on their own store will receive genuine fulfillment-service callbacks from Shopify (valid `rawBody` + valid HMAC, computed with the app's shared `apiSecretKey` which the attacker never needs to know or possess). Because the `X-Shopify-Shop-Domain` header is not part of the signed payload and is never checked for consistency with the body or required by `validate()`, the attacker can replay that exact `(rawBody, hmac)` pair to the app's fulfillment-service endpoint while substituting the `X-Shopify-Shop-Domain` header with a different (victim) shop's domain that also installed the app. `fulfillmentService.validate()` still returns `valid: true` (HMAC checks only the body), and `authenticate.ts` then resolves and returns the **victim's** offline session/admin client to the attacker.

### Impact Explanation
This is a cross-tenant session/data access issue: an app user for shop A can obtain an authenticated Admin API context (offline access token) for shop B merely by replaying a legitimately-received callback with a swapped header, without ever needing the app's secret. This maps to Shopify's "cross-tenant data/state access" bounty impact class, since it lets one merchant's traffic be laundered into another merchant's authenticated session on a multi-tenant app built with this library.

### Likelihood Explanation
Preconditions are met by an ordinary, unprivileged actor: they only need to be a merchant/user of the shared app (to receive one legitimate signed callback) and knowledge/guess of another target shop's `myshopify.com` domain that also uses the same app (often discoverable or guessable). No `apiSecretKey`, no MITM, and no host-app misconfiguration are required — the default `authenticate.fulfillmentService` implementation in `shopify-app-remix`/`shopify-app-react-router` is what trusts the unauthenticated header. This is fully repeatable with a captured request and a simple header substitution.

### Recommendation
- Do not derive the shop identity for fulfillment-service requests solely from the unsigned `X-Shopify-Shop-Domain` header. Either require that shop identity be embedded in and derived from the HMAC-signed `rawBody` (as Flow already does via `payload.shopify_domain`), or extend `validateHmacFromRequestFactory`/`fulfillment-service/validate.ts` to require the domain header and cryptographically bind it (e.g., include it in the signed material or cross-check it against a shop reference inside the signed payload).
- At minimum, add a `checkFulfillmentServiceHeaders`-equivalent to `fulfillment-service/validate.ts` mirroring `checkWebhookHeaders`, and have `authenticate.ts` reject when that check fails rather than trusting `request.headers.get(ShopifyHeader.Domain)` unconditionally.

```ts
// packages/apps/shopify-api/lib/fulfillment-service/__tests__/fulfillment-service.test.ts (illustrative addition)
it('accepts a replayed body/hmac with a swapped shop-domain header', async () => {
  const shopify = shopifyApi(testConfig());
  const payload = {kind: 'FULFILLMENT_REQUEST', order_id: 123}; // no shop-binding field
  const rawBody = JSON.stringify(payload);
  const hmac = await createSHA256HMAC(shopify.config.apiSecretKey, rawBody, HashFormat.Base64);

  // Attacker (merchant of shop-a.myshopify.com) captured this legitimate (rawBody, hmac)
  // pair from their own store's callback, then replays it against a different shop header.
  const spoofedReq: NormalizedRequest = {
    method: 'POST',
    url: 'https://my-app.my-domain.io/fulfillment_order_notification',
    headers: {
      [ShopifyHeader.Hmac]: hmac,
      [ShopifyHeader.Domain]: 'victim-shop.myshopify.com', // not covered by HMAC, unchecked
    },
  };

  const result = await shopify.fulfillmentService.validate({
    rawBody,
    rawRequest: spoofedReq,
  });

  // Library returns valid:true even though shop-domain header is forged/unbound
  expect(result).toMatchObject({valid: true});
});
```
Combined with `authenticateFulfillmentServiceFactory`, this replay causes `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')` to be invoked and a session/admin client for the victim shop to be returned to the attacker's request handler. [5](#0-4)

```typescript
export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}
```

```typescript
function getRequiredHeader(
  headers: Headers,
  headerName: string,
  missingHeaders: string[],
): string | undefined {
  const value = getHeader(headers, headerName);
  if (!value) {
    missingHeaders.push(headerName);
  }
  return value;

function checkWebhookHeaders(
```
