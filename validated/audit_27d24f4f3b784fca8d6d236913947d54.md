### Title
Unbounded `GetValidatorInfo{Latest}` RPC requests trigger expensive epoch aggregation with no rate limiting, enabling non-network-level DoS of the view client and read-lock starvation of block processing — (`chain/client/src/view_client_actor.rs`, `chain/epoch-manager/src/lib.rs`)

### Summary
An unauthenticated attacker can flood the public `validators` JSON-RPC endpoint with `{"epoch_reference": null}` (i.e., `EpochReference::Latest`) requests. Each request acquires a read lock on the shared `EpochManagerHandle` and calls `get_epoch_info_aggregator_upto_last`, which the codebase itself documents as "very expensive." There is no rate limiting, concurrency cap, or caching on this path. The result is saturation of all view client threads and potential write-lock starvation of the block-processing path.

### Finding Description
The `validators` RPC method (`chain/jsonrpc/src/lib.rs:2504`) dispatches `GetValidatorInfo` to the `ViewClientActor` with no throttle. The handler for `EpochReference::Latest` resolves to `ValidatorInfoIdentifier::BlockHash(header_head)` and calls `epoch_manager.get_validator_info(BlockHash(...))`. The adapter implementation (`chain/epoch-manager/src/adapter.rs:1180-1186`) takes a read lock on the `EpochManagerHandle` and calls `EpochManager::get_validator_info`, which unconditionally calls `get_epoch_info_aggregator_upto_last`. Even in the best case (aggregator is current), this clones the full `EpochInfoAggregator` struct — containing per-validator, per-shard HashMaps — under the read lock. In the worst case (aggregator is behind the header head), it traverses every block in the epoch in a loop (`aggregate_epoch_info_upto`, lines 1948–2030), reading `BlockInfo` from storage for each block.

The `ViewClientActor` pool has 4 threads by default. Flooding with concurrent requests saturates all threads. Because the read lock is held for the duration of each call, a pending write lock (needed by `add_validator_proposals` during block processing) is blocked until all concurrent readers finish, potentially delaying epoch transitions and block recording.

### Impact Explanation
- **View client DoS**: All 4 view client threads are consumed by `GetValidatorInfo` requests; all other RPC queries (block queries, tx status, etc.) queue indefinitely.
- **Block processing delay**: `add_validator_proposals` requires a write lock on `EpochManagerHandle`. Under write-preferring `parking_lot::RwLock`, a flood of concurrent readers can delay the write lock acquisition, stalling block info recording and epoch transitions.
- Impact is non-network-level (RPC layer) and fixable without a hardfork (add rate limiting or a response cache at the RPC or view client layer).

### Likelihood Explanation
The `validators` endpoint is publicly documented and requires no credentials. The attack requires only an HTTP client capable of sending concurrent JSON-RPC requests. No privileged access, validator role, or key compromise is needed.

### Recommendation
1. Add a per-IP or global rate limit on the `validators` RPC method, consistent with how `state_request_throttle_period` limits state requests.
2. Cache the `EpochValidatorInfo` result for the current epoch head with a short TTL (e.g., one block time ~1 s), so repeated `Latest` requests return the cached value without re-acquiring the read lock.
3. Consider making `get_epoch_info_aggregator_upto_last` return a reference-counted snapshot rather than a full clone.

    /// Returns epoch info aggregate with state up to `last_block_hash`.
    ///
    /// The block hash passed as argument should be the latest block belonging
    /// to current epoch.  Calling this method on any other block is likely to
    /// result in performance issues since handling something which is not past
    /// the final block will force it to traverse the entire epoch from scratch.
    ///
    /// This method does not change `self.epoch_info_aggregator`.
    pub fn get_epoch_info_aggregator_upto_last(
        &self,
        last_block_hash: &CryptoHash,
    ) -> Result<EpochInfoAggregator, EpochError> {
        if let Some((mut aggregator, replace)) = self.aggregate_epoch_info_upto(last_block_hash)? {
            if !replace {
                aggregator.merge_prefix(&self.epoch_info_aggregator);
            }
            Ok(aggregator)
        } else {
            Ok(self.epoch_info_aggregator.clone())
        }
    }
