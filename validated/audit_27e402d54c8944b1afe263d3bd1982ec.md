### Title
Meta-transaction (`DelegateAction`) balance refunds are misdirected to the inner sender instead of the paying relayer, letting the sender extract relayer-funded deposits by forcing execution failure - ([File: runtime/runtime/src/actions.rs])

### Summary
In NEAR's meta-transaction (NEP-366) flow, the relayer pays all attached deposits for the inner actions of a `DelegateAction`, but if those inner actions fail on the receiver's shard, the protocol refunds the deposit to the `predecessor_id` of the failed receipt — which is the delegate action's `sender_id` (Alice), not the relayer who actually funded the deposit. Alice fully controls whether the inner action fails (e.g., by crafting an action that is guaranteed to fail on the receiver shard, or manipulating her own account/contract state so the receiver-side check fails), so she can unilaterally divert the relayer's funds to herself, mirroring the "lender refuses repayment to force liquidation" pattern: the counterparty who does not bear the cost controls the failure path and captures the refund meant for the paying party.

### Finding Description
`apply_delegate_action` in [1](#0-0)  constructs the inner receipt with `predecessor_id: sender_id.clone()` (Alice) while the relayer is only the `signer_id`/gas payer. The code comment explicitly documents the consequence: "If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction... Relayer should verify DelegateAction before submitting it because it spends the attached deposit."

The refund mechanics themselves are generic and system-wide: `refund_unspent_gas_and_deposits` in [2](#0-1)  always builds the deposit refund receipt addressed to `receipt.balance_refund_receiver()` (the failed receipt's predecessor), and `total_deposit` in [3](#0-2)  confirms that for delegate actions "Relayer pays the deposit but if actions fail, the deposit is refunded to Sender of DelegateAction."

The project's own architecture documentation confirms this is an acknowledged fund-diversion vector, not merely an edge case: [4](#0-3)  states: "what if the transaction fails execution on Bob's shard? At this point, the predecessor is Alice and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard."

This is directly analogous to the Cooler bug: the party who does not fund the payment (Alice/the lender-analog) has unilateral control over whether the payment "succeeds," and failure redirects value to her rather than to the party who paid (the relayer/borrower-analog), rather than simply returning it to the payer.

### Impact Explanation
Any unprivileged account can act as `sender_id` in a `DelegateAction` and coax a relayer into paying for an inner action engineered to fail on the receiver's shard (e.g., targeting a receiver account/contract state the sender knows will reject the call, or a receiver that doesn't exist / lacks storage balance / a function that reliably errors). The relayer's attached deposit is then refunded to the sender rather than returned to the relayer — an unauthorized transfer of value from the relayer to the sender with no compensating action performed. For relayer services that batch high-value deposits (a common meta-tx use case for gasless dApp UX), this allows systematic value extraction from relayers.

### Likelihood Explanation
Likelihood is high for any relayer that accepts arbitrary/unverified `DelegateAction`s from users and does not itself simulate/verify the inner actions will succeed before signing/submitting — exactly the trust assumption the docs call out. No special privileges are needed; only crafting a `SignedDelegateAction` with a deposit-bearing inner action that fails on the receiver shard.

### Recommendation
Route deposit refunds for actions originating inside a `DelegateAction` back to the outer transaction's `signer_id` (the relayer who funded the deposit) rather than to `delegate_action.sender_id`, or require relayers to structure this cost via a compensating mechanism enforced by the protocol rather than relying on off-chain trust. At minimum, this should be surfaced as an explicit protocol-level warning/limit (e.g., capping attached deposits in delegate actions, or a "deposit escrow" scheme) since the current design allows the non-paying party to control the failure outcome and capture the refund.

### Proof of Concept
1. Relayer `R` accepts a `SignedDelegateAction` from sender `Alice` targeting receiver `Bob`, with an inner `FunctionCallAction` carrying a large `deposit` and a `method_name`/args that Alice knows will make the call fail on `Bob`'s shard (e.g., a nonexistent method, or a receiver Alice controls to reject the call based on `predecessor_id == Alice`).
2. `R` signs and submits the outer transaction, paying gas and the deposit as described in [5](#0-4) .
3. The inner receipt is created with `predecessor_id = Alice` per [6](#0-5) .
4. Execution fails on Bob's shard; `refund_unspent_gas_and_deposits` issues `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)` addressed to Alice per [2](#0-1) .
5. Alice receives the full deposit that `R` paid for, while `Bob` never received value and `R` is out the deposit amount — matching the test harness pattern in `generate_delegate_actions` at [7](#0-6) , which sets up exactly this relayer/sender/non-existent-receiver configuration to exercise the failing-inner-action path.

## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
