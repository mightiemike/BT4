### Title
Missing bound on `ENERGY_FEE` chain parameter enables silent overflow in energy-fee billing - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator` bounds nearly every governance-settable numeric parameter (e.g. `TRANSACTION_FEE`, `ASSET_ISSUE_FEE`, `MARKET_SELL_FEE`, `MULTI_SIGN_FEE`, `MEMO_FEE`, etc.) to a sane range such as `[0, LONG_VALUE]` or `[0, MAX_SUPPLY]`. `ENERGY_FEE` (and `EXCHANGE_CREATE_FEE`) is the outlier — its case falls straight through to `break` with **no validation whatsoever**, meaning it can be set to any `long`, including negative values or values close to `Long.MAX_VALUE`. [1](#0-0) 

That unbounded value is later consumed in `ReceiptCapsule.payEnergyBill` using plain (non-exact) multiplication instead of the overflow-checked `multiplyExact` used elsewhere in the very same class: [2](#0-1) 

### Finding Description
`ENERGY_FEE` is a witness-governed dynamic parameter that determines the "sun per energy" price charged to accounts when their frozen energy is exhausted during contract execution. In `ReceiptCapsule.payEnergyBill`:

```java
long sunPerEnergy = Constant.SUN_PER_ENERGY;
long dynamicEnergyFee = dynamicPropertiesStore.getEnergyFee();
if (dynamicEnergyFee > 0) {
  sunPerEnergy = dynamicEnergyFee;
}
long energyFee = (usage - accountEnergyLeft) * sunPerEnergy;
``` [3](#0-2) 

Elsewhere in the same file, the developers deliberately use `multiplyExact` to guard against silent overflow, e.g. in `payEnergyBill`'s origin/caller split: [4](#0-3) 

Because `getEnergyFee()` is fetched from a parameter that `ProposalUtil.validator` never bounds, a proposal that pushes `ENERGY_FEE` to a very large value (up to `Long.MAX_VALUE`, since no `LONG_VALUE`/`MAX_SUPPLY` check exists as it does for every comparable fee) causes `(usage - accountEnergyLeft) * sunPerEnergy` to silently wrap around in Java's default `long` multiplication instead of throwing. This can produce a wildly incorrect or even negative `energyFee`. That corrupted value is then compared against `account.getBalance()` and subtracted:
```java
if (balance < energyFee) { throw new BalanceInsufficientException(...); }
account.setBalance(balance - energyFee);
``` [5](#0-4) 

A negative/overflowed `energyFee` breaks the accounting invariant here in one of two directions: it can make `balance < energyFee` always false (bypassing the insufficient-balance check and crediting the account via `balance - energyFee` becoming an addition), or it can produce an absurd positive fee that always fails the check and permanently blocks any account whose energy is exhausted mid-execution from completing contract calls — a denial-of-service on TVM invocation for every unprivileged user, directly mirroring the external report's `handleFees()` underflow "bricking the contract and preventing users from minting/burning."

### Impact Explanation
This is reachable by every unprivileged user who calls a smart contract once their frozen energy is exhausted (a normal, everyday code path, not a privileged action) — the vulnerability is only latent until a single corrupted `ENERGY_FEE` proposal passes. Once set, it can (a) silently mint/erase account balance due to overflow/underflow in the fee computation, an accounting-integrity break, or (b) render the energy-billing path unusable network-wide, a protocol-availability/DoS condition. This matches the "invalid-state" and "compromised protocol availability" impact class the original report was judged Medium on.

### Likelihood Explanation
Setting `ENERGY_FEE` still requires a passed witness/committee proposal (a governance action), same as the original `LicenseFee` scenario which was likewise gated by a timelock yet still flagged because "there is validity in reducing how the fee can be modified." Unlike every sibling fee parameter in `ProposalUtil`, `ENERGY_FEE` has zero bound checking, so a single miskeyed or malicious proposal value (not even requiring an adversarial supermajority — a typo is sufficient) immediately corrupts a hot path exercised by all ordinary users on every subsequent contract call that exhausts energy.

### Recommendation
Add an explicit bound to the `ENERGY_FEE` (and `EXCHANGE_CREATE_FEE`) case in `ProposalUtil.validator`, consistent with the other fee parameters (e.g. `[0, LONG_VALUE]`), and replace the raw multiplication in `ReceiptCapsule.payEnergyBill` (`(usage - accountEnergyLeft) * sunPerEnergy`) with `multiplyExact` so any residual out-of-range value fails safely with an exception instead of silently wrapping.

### Proof of Concept
1. A proposal sets `ENERGY_FEE` (`code = 11`) to a very large value, e.g. `Long.MAX_VALUE / 2`; `ProposalUtil.validator`'s `ENERGY_FEE` case performs no check and accepts it.
2. `ProposalService.process` stores it via `saveEnergyFee` with no clamping. [6](#0-5) 
3. Any user submits a contract call whose energy usage exceeds their frozen/available energy (`usage - accountEnergyLeft > 0`), triggering `payEnergyBill`.
4. `energyFee = (usage - accountEnergyLeft) * sunPerEnergy` overflows `long`, producing an arbitrary (potentially negative) value.
5. The subsequent `balance < energyFee` / `balance - energyFee` accounting is corrupted, either silently crediting the caller's balance or permanently blocking their transactions with `BalanceInsufficientException`.
