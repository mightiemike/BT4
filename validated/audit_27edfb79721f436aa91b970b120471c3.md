### Title
Webhook shop-domain/topic headers are excluded from HMAC signature, enabling cross-tenant webhook spoofing - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
`validateHmacFromRequestFactory` validates a webhook's authenticity by HMAC-ing only the raw request body against `config.apiSecretKey`. The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers used later to route the webhook and resolve which shop's offline session/access token to use are never included in the signed data — `checkWebhooksHeaders` only confirms these headers are *present*, not that they are authentic or bound to the signed body.

### Finding Description
`validateHmacFromRequest` ( [1](#0-0) ) computes `createSHA256HMAC(config.apiSecretKey, rawBody, HashFormat.Base64)` and compares it against the `X-Shopify-Hmac-Sha256` header. The shop domain, topic, webhook id, and API version headers are never mixed into this HMAC computation. `validateFactory` ( [2](#0-1) ) calls `validateHmacFromRequestFactory` and, if the body-only HMAC passes, calls `checkWebhookHeaders`, which merely verifies the listed headers exist ( [3](#0-2) ) — it does not verify any cryptographic binding between those header values and the signed body.

The resulting `domain`/`topic`/`webhookId` fields are trusted by all downstream consumers: `callWebhookHandlers` passes `webhookCheck.domain` directly to app-supplied callbacks ( [4](#0-3) ), and the framework adapters resolve the offline session/access token for that shop using the unsigned domain header, e.g. `ensureValidOfflineSession(params, check.domain)` ( [5](#0-4) ).

Because a single shared `apiSecretKey` is used to validate all webhooks for the app across every installed shop, and because Shopify's HMAC secret and body-signing scheme are identical regardless of which shop or topic triggered the delivery, an attacker who controls (or has previously observed) a legitimately Shopify-signed webhook payload/HMAC pair for one shop or topic (e.g. by installing the app themselves and receiving a real webhook) can replay that exact `(rawBody, hmac)` pair while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers, since neither is covered by the signature. If the replayed body's content is topic/shop-agnostic — or if the attacker only needs the app to associate an attacker-controlled/otherwise-arbitrary payload with a *different* shop's offline session (e.g. to trigger reprocessing, deletion, or resource actions keyed off `shop`/`topic` for a victim's session) — this allows cross-tenant confusion between mutually distrusting installed shops.

### Impact Explanation
This affects the shared, foundational webhook-validation logic used by every app built on `shopify-api`/`shopify-app-remix`/`shopify-app-react-router`/`shopify-app-express`. If exploitable, it lets an attacker (any merchant who can install the app, i.e. an unprivileged actor relative to other installs) forge webhook headers—shop domain, topic, webhook id—for requests bearing a valid HMAC, causing the app to run a legitimate handler against the wrong shop's offline session/access token, or trigger topic-specific logic (e.g. `APP_UNINSTALLED` cleanup, GDPR data deletion) for a shop that never sent that webhook.

### Likelihood Explanation
Medium-low. Exploitation requires the attacker to obtain at least one valid `(rawBody, hmac)` pair (trivial for topics whose payload is generic/attacker-controllable, e.g. by installing the app themselves) and requires that the victim app's handler logic branches meaningfully based on the unsigned `domain`/`topic` values rather than re-validating shop identity independently. Many apps do exactly this, since the library's documented pattern is to trust `check.domain`/`webhookCheck.domain` directly to resolve `getOfflineId(domain)`.

### Recommendation
Bind the routing-critical headers (`X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-API-Version`) into the HMAC computation itself (e.g. `HMAC(secret, canonicalized_headers || rawBody)`), or otherwise cryptographically bind them to the signed payload, so a valid signature can only be replayed with header values it was actually generated for. At minimum, per-shop webhook secrets/session lookups should independently corroborate that the claimed `domain` matches a shop that could plausibly have produced the given signed payload.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook topic whose body content doesn't embed identifying shop information (or is otherwise attacker-influenced), capturing the resulting `(rawBody, X-Shopify-Hmac-Sha256)` pair from a real Shopify delivery.
2. Attacker (or a MITM-free replay from attacker's own infrastructure, since they legitimately received the webhook) re-sends a POST to the app's `/webhooks` endpoint with the same `rawBody` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and/or a different `X-Shopify-Topic`.
3. `validateHmacFromRequestFactory` (`hmac-validator.ts` lines 189–194) validates successfully because it only checks `rawBody` against the HMAC.
4. `checkWebhooksHeaders` (`validate.ts` lines 99–134) accepts the forged `domain`/`topic` since it only checks header presence.
5. The app's webhook handler / `ensureValidOfflineSession(params, check.domain)` resolves and acts on `victim.myshopify.com`'s offline session using attacker-controlled payload semantics tied to the forged topic.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
