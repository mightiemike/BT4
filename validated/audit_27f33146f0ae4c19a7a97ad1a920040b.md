Based on my investigation, I found a solid analog. The Push Chain SVM outbound path enforces a hard `u64` boundary on withdrawal `amount` for Solana-destined outbounds, while PRC20 balances on Push Chain (EVM side) are `uint256` and routinely 18-decimals. This exactly mirrors the coded-estate `u64` cap bug class, but here the consequence is a permanently stuck/frozen outbound (funds already debited/burned on Push Chain) rather than merely a listing-price limitation.

### Title
Outbound Withdrawals to Solana Permanently Fail (Funds Frozen) When PRC20 Amount Exceeds u64 Max - (File: `universalClient/chains/svm/tx_builder.go`)

### Summary
`GetOutboundSigningRequest`, `BuildOutboundTransaction`, and `BuildRefRouteTransactions` in the Solana `TxBuilder` all hard-reject any outbound `amount` that does not fit into a `u64` (Solana's native token-amount width), via `amount.IsUint64()` checks that return `"amount exceeds u64 max"`.

### Finding Description
When a `UniversalTx` withdraws PRC20 balance to a Solana destination, `BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go`) records `Amount: event.Amount.String()` straight from the `uint256` `UniversalTxWithdraw` EVM event, with no clamping or decimal-aware validation against the destination chain's native width. This `OutboundTx` is committed to `PendingOutbounds` state on Push Chain — meaning the corresponding PRC20 tokens have already been burned/debited from the user on the EVM side before any Solana-side signing is attempted.

Once the universal validators later call `GetOutboundSigningRequest` to build the TSS-signing request for that outbound, the parsed `amount` is checked with: [1](#0-0) 
and any amount above `18446744073709551615` (`u64::MAX`) is rejected outright, with the same check repeated in `BuildOutboundTransaction` and `BuildRefRouteTransactions`: [2](#0-1) [3](#0-2) 

Because PRC20 tokens are typically 18-decimal (e.g., the ERC20-style PRC20 wrapper contract, per `x/uexecutor/types/abi.go`), any withdrawal amount above ~18.44 tokens (`> 18.44 * 10^18` base units) can never be turned into a valid TSS-signing request — every universal validator will independently fail to build the signing request for that outbound, so no TSS signature is ever produced.

### Impact Explanation
The outbound has already been created (`OutboundStatus: types.Status_PENDING`) and the corresponding PRC20 balance was already deducted/burned from the user before this point, per the design described in `x/uexecutor/README.md`: `PendingOutbounds` is "Removed ONLY when validators reach consensus" and "Ballot expiry does NOT remove the entry" because the funds are already in flight and auto-refund/auto-retry are unsafe. Since `GetOutboundSigningRequest` will deterministically and permanently fail for this amount (it's not a transient RPC/network error — it's a hard-coded `u64` boundary check on validated, correctly-formatted numeric input), no validator can ever produce a valid signature, and the outbound can never finalize on Solana. This meets the "permanent freezing of user or protocol-controlled funds" allowed-impact bucket — the user's tokens are burned on Push Chain with no way to ever land on the destination Solana chain, and the only path forward is manual governance/operator intervention (per the README, resolution is "governance-driven, not chain-driven").

### Likelihood Explanation
This requires no privileged access — it is reachable by any ordinary user withdrawing a large PRC20 balance (e.g., an 18-decimal wrapped stablecoin or wrapped asset bridged from another chain) to a Solana destination through the normal withdraw/outbound flow. It does not depend on malicious validators, TSS compromise, or network-level conditions — only on the ordinary numeric size of a legitimate withdrawal amount that a user is otherwise entitled to hold and move.

### Recommendation
- Reject (at outbound-creation time, in `BuildOutboundsFromReceipt` / earlier in the EVM `UniversalGatewayPC.withdraw` validation) any withdrawal whose PRC20 amount, once converted to the destination chain's native decimal representation, would exceed `u64::MAX`, *before* burning/debiting the user's PRC20 balance.
- Alternatively/additionally, perform decimals-aware scaling from the PRC20's 18-decimal representation down to the destination SPL token's actual decimals (per `TokenConfig.Decimals`) before emitting the outbound, so that only truly excessive real-world amounts (rather than an artifact of 18-decimal PRC20 accounting) trigger the u64 boundary.
- If rejection must happen post-facto, ensure a governed, funds-safe recovery path exists (e.g., an explicit "outbound amount infeasible" status with an admin-triggered refund-to-source flow) so debited/burned funds are not left permanently unrecoverable.

### Proof of Concept
1. User bridges/mints a PRC20 balance representing more than ~18.44 tokens at 18 decimals (e.g., `20e18` units) via any inbound/mint path where the source-chain token has 18 decimals.
2. User calls the Universal Gateway `withdraw`/`withdrawAndExecute` targeting a Solana chain with `amount = 20000000000000000000` (`2e19`, i.e., `> u64::MAX`).
3. `BuildOutboundsFromReceipt` records the `OutboundTx` with `Amount = "20000000000000000000"` and status `PENDING`; PRC20 tokens are already burned/debited from the user.
4. When a universal validator's coordinator calls `builder.GetOutboundSigningRequest(ctx, data, nonce)` (`universalClient/chains/svm/tx_builder.go:205-214`), `amount.IsUint64()` returns `false`, and the function returns `"amount exceeds u64 max"` for every validator, every retry.
5. No valid TSS signing session can ever be established for this outbound; it remains permanently `PENDING`, and per `x/uexecutor/README.md` the entry is never auto-cleaned, leaving the user's already-debited funds stuck with no on-chain resolution path.
