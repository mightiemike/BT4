### Title
Backup restore commits `write_set` bytes to durable storage without verifying them against the proof-authenticated `TransactionInfo.state_change_hash` - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
In the transaction-backup restore path, `LoadedChunk::load` verifies transactions and events against the accumulator-proven `TransactionInfo` list, but the `write_set` for each transaction is read from the backup file and carried through to `restore_handler.save_transactions` / `save_transactions_impl` completely outside of that verification, with no check that `CryptoHash::hash(write_set) == txn_info.state_change_hash()`.

### Finding Description
`LoadedChunk::load` reads `(txn, aux_info, txn_info, events, write_set)` tuples from the backup file, then builds a `TransactionListWithProofV2`/`TransactionListWithProof` containing only `txns`, `event_vecs`, and `txn_infos`, and calls `txn_list_with_proof.verify(...)`: [1](#0-0) 

`TransactionListWithProof::verify` checks that transaction hashes match `txn_info.transaction_hash()`, that the `TransactionInfo` list is proven by the accumulator proof against the ledger info, and (only if events are supplied) that the event root hash matches `txn_info.event_root_hash()` — it never touches `write_sets` at all: [2](#0-1) 

Compare this to `TransactionOutputListWithProofV2::verify`, used by the output-based sync/replay path, which explicitly recomputes `CryptoHash::hash(&txn_output.write_set)` and checks it equals `txn_info.state_change_hash()` before accepting the output: [3](#0-2) 

No equivalent check exists anywhere in the transaction-backup restore path: `write_sets` is loaded straight from the untrusted file bytes (`bcs::from_bytes(&record_bytes)`) at [4](#0-3) , kept out of the `TransactionListWithProof` struct that is verified, and later passed unmodified into `restore_handler.save_transactions` at [5](#0-4) , which is committed by `save_transactions_impl` directly to the `WriteSetDb` and used to derive state updates via `state_store.calculate_state_and_put_updates` when `kv_replay` is set: [6](#0-5) 

A repository-wide search confirms `state_change_hash` is never referenced anywhere under `storage/backup/`, so the write-set-to-`TransactionInfo` binding invariant is never enforced on this path, unlike the output-list path.

### Impact Explanation
The `TransactionInfo.state_change_hash` field exists specifically so that a `write_set`’s integrity can be authenticated against the accumulator-proven, ledger-info-signed `TransactionInfo`. By skipping this check in the transaction-backup restore flow, a corrupted or maliciously altered backup archive (e.g. from a compromised or MITM'd backup storage backend) can supply an arbitrary `WriteSet` for a given version while keeping the `Transaction` and `TransactionInfo` (and thus the accumulator proof and ledger-info signatures) valid. The node restoring from this backup will persist the forged write set as though it were the VM-computed result for that transaction, corrupting durable state values (`WriteSetDb`) and any `kv_replay` state derived from it — a direct committed-state-vs-correct-VM-result divergence, matching the "State-Integrity Gate" criteria (wrong committed state that differs from the correct VM result / corrupts durable ledger data).

### Likelihood Explanation
This requires control over, or tampering with, backup archive contents (the transaction manifest file), which is a plausible threat model for restore/disaster-recovery scenarios (compromised backup storage, supply-chain tampering of a backup snapshot, or an operator restoring from an unauthenticated/unverified source). It does not require any validator/consensus privilege, and the missing check is a straightforward, provable code-level gap when contrasted with the sibling output-list verification path that does perform the equivalent check.

### Recommendation
Add a hash check in the transaction-backup restore path analogous to `TransactionOutputListWithProofV2::verify`: after (or as part of) `TransactionListWithProof::verify`/`LoadedChunk::load`, assert `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every `(write_set, txn_info)` pair before the chunk is accepted and before `save_transactions`/`save_transactions_impl` persists it. Consider extending `TransactionListWithProof` (or a wrapper used specifically for restore) to carry `write_sets` and enforce this invariant centrally so all restore/replay call sites benefit.

### Proof of Concept
1. Take a valid transaction-backup chunk file (format V0/V1) as produced by `TransactionChunk`.
2. Keep `Transaction`, `TransactionInfo`, and `events` bytes unchanged for a target record, but overwrite the serialized `WriteSet` bytes for that record with an attacker-chosen write set (e.g., crediting an arbitrary account balance) — record boundaries are simply `len(record) + record`, so this is a direct byte-level edit that still parses via `bcs::from_bytes`.
3. Run `TransactionRestoreController`/`TransactionRestoreBatchController::run_impl`, which calls `LoadedChunk::load` → `txn_list_with_proof.verify(...)` (only checks tx hash, accumulator proof, event root) → `save_before_replay_version` → `restore_handler.save_transactions(...)` → `save_transactions_impl`, all of which succeed because none of them recompute or check `CryptoHash::hash(write_set)` against `txn_info.state_change_hash()`.
4. The forged write set is committed to `WriteSetDb` (and reflected in derived state if `kv_replay` is used), while the transaction/proof verification reported success — demonstrating the write set is not bound to its authenticated `TransactionInfo`.

(Note: I was not able to execute this restore flow in a live environment to observe the final DB state; the analysis is based on tracing the verification and commit code paths and confirming the absence of the `state_change_hash` check via search across `storage/backup/`.)

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
