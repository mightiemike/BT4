**Analysis:** `make_next_sortition_id` in `stackslib/src/chainstate/burn/db/sortdb.rs` is purely a deterministic ID-derivation function: it computes `next_pox = make_next_pox_id(parent_pox, next_pox_info)` and returns `SortitionId::new(this_block_hash, &next_pox)`, with no relation to poison-microblock reward accounting. [1](#0-0) 

Poison-microblock reward bookkeeping lives entirely in `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs`) and `find_mature_miner_rewards` (`stackslib/src/chainstate/stacks/db/accounts.rs`), which are unrelated code paths from `make_next_sortition_id`. There, `insert_microblock_poison`/`get_microblock_poison_report` store exactly one `(reporter, sequence)` tuple per microblock-pubkey-hash height, and a resubmission only overwrites the record if the new `sequence` is strictly lower (i.e., a genuinely better fork proof), otherwise it is dropped. [2](#0-1) 

At maturation time, `find_mature_miner_rewards` reads the report exactly once per `reward_height` via `get_poison_microblock_report`, and `calculate_miner_reward` is invoked exactly once per matured block, so the reward is paid exactly once per offense. [3](#0-2) 

The question's exploit narrative ("replay a report for one double-sign" via `make_next_sortition_id`) has no code-level connection: `make_next_sortition_id` does not read or write any poison-report state, burn distribution, or reward schedule — it only derives a `SortitionId` hash from `(this_block_hash, next_pox)`. There is no reachable path from a Bitcoin block-commit, leader-key, Nakamoto block/microblock, or poison report through `make_next_sortition_id` that affects poison-reward accounting, and the actual poison-reward mechanism already enforces single-payment via its single-slot report storage and one-time maturation read. The claimed equality break is unsupported by the code.
