### Title
Silent proof-verification bypass in `DbStateView::get` on proof-fetch error - (`storage/storage-interface/src/state_store/state_view/db_state_view.rs`)

### Summary
`DbStateView::get` is supposed to guarantee that, whenever the view is constructed with `maybe_verify_against_state_root_hash: Some(root_hash)`, every returned `StateValue` has been checked against a Merkle proof for `root_hash`. The current implementation only performs verification inside an `if let Ok(...)` block and silently does nothing when the proof-fetch call errors, then unconditionally falls through to a second, proof-less lookup call and returns its result.

### Finding Description
```rust
fn get(&self, key: &StateKey) -> StateViewResult<Option<(Version, StateValue)>> {
    if let Some(version) = self.version {
        if let Some(root_hash) = self.maybe_verify_against_state_root_hash {
            if let Ok((value, proof)) =
                self.db.get_state_value_with_proof_by_version(key, version)
            {
                proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
            }
        }
        Ok(self
            .db
            .get_state_value_with_version_by_version(key, version)?)
    } else {
        Ok(None)
    }
}
``` [1](#0-0) 

The bug: `if let Ok((value, proof)) = self.db.get_state_value_with_proof_by_version(key, version)` treats an `Err` from the proof-fetch call as "nothing to verify" rather than propagating the error. If `get_state_value_with_proof_by_version` errors for a given `(key, version)` — for example due to state-merkle-tree pruning having already removed the JMT nodes needed to build a proof for that historical version, while the separate state-KV store (queried by `get_state_value_with_version_by_version`) still retains the raw value for that version because it is pruned on an independent schedule/lag — the verification branch is skipped entirely, and the function falls through to return the unverified value from the second call. Tests referencing `get_state_value_with_proof_by_version` failure/error behavior around pruning boundaries exist in `storage/aptosdb/src/pruner/state_merkle_pruner/test.rs`, consistent with this divergence being reachable in normal operation, not just theoretically.

This breaks the documented invariant in the surrounding module ("DB doesn't support returning proofs for buffered state, so only optionally verify proof") — the intent was clearly to *skip verification only when proofs are structurally unavailable (buffered state)*, not to silently swallow arbitrary DB errors including proof-fetch failures for committed, prunable state.

### Impact Explanation
Any caller that constructs a `DbStateView` with `maybe_verify_against_state_root_hash` set and reads an old, pruning-eligible version can receive a `StateValue` that was never checked against the claimed root hash, even though the API contract implies it was. This is a defense-in-depth failure of the state-view proof-verification invariant: any storage inconsistency, replication bug, or state-merkle corruption for a given version that would normally be caught by `proof.verify(...)` failing loudly is instead masked, and the caller silently receives unverified data as if it were authenticated. This falls under the "Authenticated API or state-view output bound to the wrong version, object, or proof context" impact category, since the returned value is presented as root_hash-bound but is not actually checked.

### Likelihood Explanation
The divergence condition (proof-fetch erroring while the raw KV lookup succeeds) is realistically reachable at version boundaries near the state-merkle pruner's window, since the state-merkle pruner and state-KV pruner run independently. It does not require a specially crafted `StateKey` in the sense of malicious byte content — any existing key at an old-enough version within the pruning skew window is sufficient — so it is reachable from any unprivileged caller of a public read API that surfaces `DbStateView` with proof verification enabled. I was not able to fully trace every `DbReader` implementation's exact error conditions for `get_state_value_with_proof_by_version` (e.g., `AptosDbReader`) in this session, so the precise set of triggering conditions (pruning-only vs. other error paths) is not fully confirmed.

### Recommendation
Change the code to propagate errors from `get_state_value_with_proof_by_version` instead of silently ignoring them via `if let Ok`, e.g.:
```rust
if let Some(root_hash) = self.maybe_verify_against_state_root_hash {
    let (value, proof) = self.db.get_state_value_with_proof_by_version(key, version)?;
    proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
}
```
If a specific error variant is expected/benign for buffered state, match on it explicitly and propagate all other errors, rather than using a blanket `if let Ok`.

### Proof of Concept
Construct a mock `DbReader` where, for a fixed `(key, version)`:
- `get_state_value_with_proof_by_version(key, version)` returns `Err(...)` (simulating pruned merkle nodes), and
- `get_state_value_with_version_by_version(key, version)` returns `Ok(Some((version, value)))` (simulating still-present raw KV data).

Build a `DbStateView` with `maybe_verify_against_state_root_hash: Some(root_hash)` and call `get_state_slot`/`get`. The call returns `Ok(Some(value))` with no verification error, despite `root_hash` never having been checked against `value`, confirming the invariant break at [2](#0-1) .
