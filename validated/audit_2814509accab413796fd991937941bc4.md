### Title
Unmetered/underpriced iteration over attacker-inflated TRC10 asset map in `SUICIDE`/`SUICIDE2` opcode enables gas-underpriced DoS - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The `SUICIDE` opcode charges a fixed energy cost regardless of how many distinct TRC10 token balances the self-destructing contract holds, yet its execution path (`MUtil.transferAllToken`) iterates over the contract's entire `AssetMapV2`, a map an attacker can cheaply inflate to unbounded size by sending many distinct TRC10 tokens to the contract address before it self-destructs.

### Finding Description
When a smart contract executes `SELFDESTRUCT`, `Program.suicide()` / `Program.suicide2()` call `MUtil.transferAllToken(getContractState(), owner, obtainer)`: [1](#0-0) 

`MUtil.transferAllToken` iterates over every entry in the contract's `AssetMapV2` (the full set of TRC10 token balances the account holds) and rewrites both the source and destination account's asset maps entry by entry: [2](#0-1) 

The size of `AssetMapV2` is entirely attacker-controlled: any account (privileged or not) can send arbitrary amounts of any number of distinct TRC10 token IDs to the target contract address via ordinary `TransferAssetContract` transactions (or a TVM `transferToken` call), each a cheap, fixed-fee operation unrelated to the eventual cost this imposes. Once the map has thousands of entries, a single `SUICIDE` invocation forces the node to iterate the entire map, rebuild the account's asset-v2 protobuf maps, and persist the updated `AccountCapsule` to both `owner` and `obtainer` — all charged at the fixed `SUICIDE` energy price. This mirrors the reported pattern exactly: an unprivileged party inflates a balance/asset collection tied to an address, then a downstream state-transition routine (`GetAllBalances`-style iteration in the report; `transferAllToken`'s `getAssetMapV2().forEach` here) performs unmetered/underpriced work proportional to that attacker-controlled collection size.

Unlike the Cosmos `BeginBlock` case, this path does run inside a metered EVM/TVM execution context, so it does not directly cause a chain halt the way an unmetered `BeginBlock` loop would. However, because the `SUICIDE` opcode's energy price is fixed and does not scale with the number of tokens transferred, the actual CPU/storage work done during block validation can be made arbitrarily large for a bounded, cheap energy payment — a classic underpriced-public-work condition that can be used to slow down transaction/block processing across the network at low cost to the attacker.

### Impact Explanation
An attacker can, at low cost, inflate a contract account's TRC10 asset map to a very large size and then trigger `SUICIDE` for a fixed energy fee, forcing every validating node to perform O(n) map iteration, protobuf rebuilding, and RocksDB writes for both `owner` and `obtainer` addresses. Because this cost is not reflected in the energy price, it can be used to degrade block processing time relative to the resources spent by the attacker, which is the same underpriced-iteration root cause described in the report (there, unbounded balance iteration in reward termination; here, unbounded asset-map iteration in self-destruct), even though the practical severity here is "block processing slowdown" rather than an outright deterministic chain halt.

### Likelihood Explanation
Reaching this path requires only unprivileged actions available to any account: (1) deploying or targeting a contract address, (2) sending many distinct TRC10 token transfers to that address (each a normal, cheap transaction with a fixed bandwidth/energy fee independent of the number of distinct denoms already held), and (3) calling a contract function that executes `SELFDESTRUCT`. No special permissions, governance, or validator access are needed, matching the "permissionless" nature of the original report.

### Recommendation
Either (a) charge `SUICIDE`/`SUICIDE2` energy proportional to the number of distinct TRC10 assets held by the self-destructing account (mirroring how `EnergyCost` already scales other opcodes by data size), or (b) cap the number of distinct TRC10 asset IDs an account may hold, or (c) require dynamic gas metering inside `MUtil.transferAllToken`'s loop so that iterating a large `AssetMapV2` cannot be performed for a fixed, attacker-cheap price.

### Proof of Concept
1. Deploy a contract `C` with a `selfdestruct(address)` function.
2. From many different unprivileged accounts (or the same account issuing many `TransferAssetContract`/TVM `transferToken` calls), transfer thousands of distinct TRC10 token IDs (1 unit each) to `C`'s address — each transfer is a cheap, fixed-fee transaction unrelated to the growing size of `C`'s `AssetMapV2`, analogous to the report's `SendCoins` spam loop populating the rewards pool address.
3. Call `C.selfdestruct(inheritor)`, which is metered at the fixed `SUICIDE` energy cost regardless of `AssetMapV2` size, as seen in `Program.suicide()` calling `MUtil.transferAllToken`.
4. Observe that transaction/block processing time for this single fixed-fee transaction scales with the number of distinct TRC10 assets previously deposited, reproducing the "cheap attacker deposit -> expensive unmetered/underpriced iteration during a state transition" pattern from the original report.   public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
