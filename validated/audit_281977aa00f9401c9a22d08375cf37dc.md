Confirmed: `action_delete_account` in `runtime/runtime/src/actions.rs` never checks whether `delete_account.beneficiary_id` equals the account being deleted (or otherwise refers to an account that will not exist post-deletion). This is the direct nearcore analog of the ExperiPie bug class — an address/id parameter that is accepted without validation and, when set to a "self/void" value, causes the funds/logic path it feeds into to be permanently lost.

### Title
Unvalidated `beneficiary_id` in `DeleteAccountAction` permits permanent burning of the deleted account's balance - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_delete_account` pays out the deleted account's remaining balance by emitting a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` and then immediately removes the account, without ever checking that `beneficiary_id` refers to a still-existing (or even distinct) account [1](#0-0) . The only validation performed on `beneficiary_id` anywhere in the pipeline is a generic account-id format check in `validate_delete_action` — it never checks identity against the account being deleted [2](#0-1) .

### Finding Description
A `DeleteAccountAction` can freely set `beneficiary_id` equal to `account_id` itself (self-beneficiary), which is exactly the "unvalidated parameter used in an access/target modifier" pattern from the reference report (there, a zero/invalid address parameter is accepted and used to configure a critical mapping). Test helpers in the codebase even construct this exact self-beneficiary shape by default: `delete_account` sets `beneficiary_id = signer_id` [3](#0-2) , and `test-loop-tests` also builds delete transactions with `beneficiary_id == account_id` [4](#0-3) .

When a self-beneficiary delete executes: `remove_account` deletes the account and `account = None` before the balance-refund receipt is ever processed [5](#0-4) . The refund receipt (a `Transfer` action with `predecessor_id = "system"`) is then delivered to an account that no longer exists. A `Transfer`/refund receipt cannot implicitly (re-)create an account — the code comment and test explicitly confirm "refunds are free, so they must not create an account" and "a refund to a missing id must fail with `AccountDoesNotExist`" [6](#0-5) . Per the documented refund semantics: "If the execution of a refund fails, the refund amount is burnt" [7](#0-6) , and this is implemented at the receipt-processing site: for a system-predecessor (refund) receipt whose result is an error, the deposit is added to `stats.balance.other_burnt_amount` rather than refunded anywhere [8](#0-7) .

The result: an ordinary, unprivileged account owner who submits a single `DeleteAccountAction` with `beneficiary_id` set to their own (about-to-be-deleted) account id — the same shape produced by the test-harness helper functions above, i.e. an entirely reachable and even "natural" transaction shape — causes their entire remaining NEAR balance to be irrecoverably burnt instead of paid out, with no validation error and a `SuccessValue` outcome on the deleting transaction itself (the failure surfaces only in the internal follow-up refund receipt, not visible as a top-level transaction failure).

### Impact Explanation
This is a transaction-triggered, deterministic loss of value: any submitted `DeleteAccountAction` with `beneficiary_id == account_id` (or any other account guaranteed not to exist after this receipt, e.g. a sibling account being deleted in the same chunk) burns the full account balance permanently, with the outer transaction reporting success. This is a "permanently frozen/burned funds" outcome directly reachable from a single unprivileged transaction, matching the accepted impact classes (concrete unauthorized value loss / permanently frozen funds) even though no separate attacker is needed — the missing validation is exactly the class of bug cited in the report (accepting an unchecked identity/address parameter that feeds directly into a fund-disbursement/access path).

### Likelihood Explanation
High likelihood of accidental triggering: wallets, SDKs, or naive integrations that default `beneficiary_id` to the signer/account itself (as this very codebase's own `NodeUser::delete_account` and `TestLoopNode::tx_delete_account` helpers do) will hit this path on every self-delete, silently burning the account's balance instead of returning it to the owner. No special privileges, races, or malicious peers are required — a single signed transaction from the account owner is sufficient.

### Recommendation
Add an explicit check in `action_delete_account` (or in `validate_delete_action`) rejecting `beneficiary_id == account_id`, returning a descriptive `ActionErrorKind` (e.g. `DeleteAccountBeneficiaryIsSelf`) instead of silently emitting a refund receipt that is guaranteed to bounce and be burnt. More generally, before emitting the balance-refund receipt, the runtime could check account existence (or reachability) of `beneficiary_id` and fail the delete action up front rather than only failing the downstream refund receipt.

### Proof of Concept
1. Create/own an account `A` with a non-zero balance and no locked stake.
2. Submit a transaction from `A` (as its own last/only action) containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: A })` — precisely the shape produced by `NodeUser::delete_account(A, A)` [3](#0-2)  or `tx_delete_account(A, A)` [4](#0-3) .
3. `action_delete_account` runs: it reads `account_balance = account_ref.amount()`, pushes `Receipt::new_balance_refund(&A, account_balance)`, then calls `remove_account(state_update, A)` and sets `account = None` — the account is gone before the refund receipt executes [9](#0-8) .
4. The outer `DeleteAccount` transaction/receipt reports success (`SuccessValue`/`SuccessReceiptId`), as seen in the passing `test_delete_account_ok` test which uses this exact self-beneficiary pattern and never asserts on final balance conservation [10](#0-9) .
5. The generated balance-refund receipt is delivered to account `A`, which no longer exists; because refund receipts cannot implicitly create accounts, it fails with `AccountDoesNotExist` (confirmed by the analogous `refund_may_not_create_universal_account` test) [6](#0-5) .
6. Because the failing receipt's predecessor is `"system"`, its deposit is added to `other_burnt_amount` instead of being refunded anywhere [8](#0-7) , permanently destroying the account's balance.
