### Title
Unbounded recursion in `bytecode_hash_node` during compiled-class-hash computation can crash the sequencer via a crafted `bytecode_segment_lengths` structure - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
`bytecode_hash_node` (compiled_class_hash.rs:111-132) recurses once per nesting level of a `NestedIntList` (`HashableNestedIntList`) with no maximum-depth check. This structure — `CasmContractClass::bytecode_segment_lengths` — is produced by the Sierra→CASM compiler subprocess from an attacker-declared Sierra program and is later fed straight back into `hash()`/`hash_inner()`/`bytecode_hash()` to compute the compiled class hash, both in the gateway/class-manager declare flow (`crates/blockifier/src/execution/contract_class.rs` `CasmContractClass::hash`) and in Starknet OS re-execution paths that recompute class hashes from stored CASM.

### Finding Description
`bytecode_hash_node` walks `NestedIntList::Node(children)` recursively: [1](#0-0) 
Unlike the blockifier's own experimental `NestedFeltCounts::new_inner`, which asserts `segmentation_depth <= 1` [2](#0-1) , this production hashing path has **no depth assertion or iteration limit at all**. The recursion depth is bounded only by how deeply nested the `NestedIntList` returned by the external `cairo-lang` Sierra-to-CASM compiler binary happens to be — a value this code does not itself validate before recursing.

This is invoked from `CasmContractClass::hash()` → `hash_inner()` → `bytecode_hash()` → `bytecode_hash_node()` [3](#0-2) , which is called immediately after Sierra→CASM compilation in the SierraCompiler component on every declare transaction: [4](#0-3) 

### Impact Explanation
If a maliciously/degenerately generated `bytecode_segment_lengths` tree (however that comes to be, e.g. via compiler-produced segmentation for pathological but bytecode-size-limited Sierra programs, or via any code path that deserializes `CasmContractClass` from external/stored data such as declared-class caches, class-sync, or OS re-execution) contains many nesting levels, `bytecode_hash_node` recurses once per level with a real Rust stack frame. Given enough nesting, this causes a `StackOverflowError`-equivalent abort (Rust process abort on stack overflow), crashing the sequencer/gateway/class-manager or the Starknet OS re-execution process — a denial-of-service, matching the bug class in the reported CVE (unbounded type nesting → stack overflow).

### Likelihood Explanation
The only currently-known producer of `bytecode_segment_lengths`, the bundled `cairo-lang` compiler, appears to cap segmentation nesting to a small depth in practice, and `max_bytecode_size`/`DEFAULT_MAX_BYTECODE_SIZE` bounds total bytecode length — this constrains, but does not prove, that nesting depth is bounded, since I could not confirm any explicit maximum-depth guarantee from the compiler binary itself (it's an external Cairo/Rust toolchain component outside this index). The lack of a defensive depth check in `bytecode_hash_node` itself means safety currently rests entirely on an implicit, unverified assumption about a subprocess's output shape rather than on an enforced invariant in the hashing code.

### Recommendation
Add an explicit maximum nesting-depth check (mirroring the `segmentation_depth <= 1` assertion already used in `NestedFeltCounts::new_inner`) inside `bytecode_hash_node`, returning an error instead of recursing past a small bound, and/or convert the recursive walk to an explicit iterative stack-based traversal so recursion depth is decoupled from the untrusted/derived data's nesting.

### Proof of Concept
Not able to construct a concrete PoC from static analysis alone: doing so requires confirming, in the actual `cairo-lang` Sierra-to-CASM compiler binary, whether/how `bytecode_segment_lengths` nesting depth can be driven arbitrarily high by a crafted (but bytecode-size-limited) Sierra program — that compiler is an external binary not present in this index. I flag this as the primary uncertainty: the code path itself is provably unbounded, but I could not verify from this repository alone whether an attacker-controlled input can actually force deep nesting in practice.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
