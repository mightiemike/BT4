### Title
`FreezeBalanceProcessor` (TVM native `freezeBalance` contract call) increases `TotalNetWeight`/`TotalEnergyWeight` by the raw frozen amount instead of the account's actual weight delta, causing global resource weight to drift from the sum of per-account weights - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
The `_finalize` fee-accounting bug in the external report is a case where a global aggregate (`totalVotingPower`) is bumped by a raw contribution amount while each individual's actual share (voting power) was computed from a fee-adjusted amount, causing the aggregate to permanently diverge from the sum of individual shares. The same structural pattern (global weight total incremented inconsistently with how the corresponding per-account value is actually changed) exists in java-tron's `FreezeBalanceProcessor`, which is the native/precompiled TVM handler for the legacy `freezeBalanceContract` resource-freeze call reachable from smart contracts.

### Finding Description
When freezing TRX for resources directly via a contract-initiated `FreezeBalanceParam` (the legacy, non-delegating path), `FreezeBalanceProcessor.execute` updates the account's frozen balance using the combined total: [1](#0-0) 

but then updates the chain-wide totals using the *raw newly-frozen amount* divided by `TRX_PRECISION`, not the actual delta between the old and new truncated weight: [2](#0-1) 

Compare this with the sibling `FreezeBalanceActuator` (the normal transaction path for the same operation), which explicitly computes `oldNetWeight`/`newNetWeight` from the account's frozen balance before and after the update and adds only the *increment* to the global total: [3](#0-2) 

Because `TRX_PRECISION` (1 TRX = 1,000,000 sun) truncates fractional weight, an account that already holds a frozen balance with a sub-1-TRX remainder (e.g. 1,500,000 sun → weight 1) and then freezes an additional 1,500,000 sun via this TVM path will end up with a combined frozen balance of 3,000,000 sun (weight 3), but `TotalNetWeight`/`TotalEnergyWeight` is only incremented by `frozenBalance / TRX_PRECISION = 1`, i.e. the correct answer should be +2 to reconcile the account's true weight jump from 1 to 3. This under-counts (or, depending on truncation direction, could also over-count relative to what is later reconciled by `Unfreeze`) the aggregate weight versus the true sum of per-account weights, exactly mirroring the report's root cause: an aggregate counter is advanced using a formula inconsistent with how the corresponding per-entity value is actually derived.

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight` are the denominators used by `BandwidthProcessor`/`EnergyProcessor` to compute each account's proportional share of the network-wide free bandwidth/energy pool. If the aggregate is systematically driven out of sync with the true sum of account weights, resource allocation across the network becomes incorrect — either under-allocating available resources to legitimate stakers, or (if the divergence goes the other direction on `Unfreeze`) allowing accounts to claim more resource share than their actual stake entitles them to. This is a resource-accounting corruption bug reachable from any contract that invokes the freeze-resource native call, which is unprivileged and network-wide in effect.

### Likelihood Explanation
Reachable by any contract/account performing repeated partial freezes via the TVM native `freezeBalance` call where the running total isn't an exact multiple of `TRX_PRECISION` between calls — a routine usage pattern, not requiring any special privilege. The divergence accumulates over time with repeated freeze operations by the same account, making the drift between `TotalNetWeight`/`TotalEnergyWeight` and the true sum of weights increasingly significant on an active chain.

### Recommendation
Make `FreezeBalanceProcessor.execute` consistent with `FreezeBalanceActuator`: capture the account's old weight (`getFrozenBalance()/TRX_PRECISION` or `getEnergyFrozenBalance()/TRX_PRECISION`) before updating, compute the new weight after `setFrozenForBandwidth`/`setFrozenForEnergy`, and add only the delta (`newWeight - oldWeight`) to `TotalNetWeight`/`TotalEnergyWeight`, instead of adding `frozenBalance / TRX_PRECISION` directly.

### Proof of Concept
1. Deploy/trigger a contract path that invokes the native freeze-resource call handled by `FreezeBalanceProcessor` for `BANDWIDTH`, freezing 1,500,000 sun for an account with no prior frozen balance. Weight recorded: `frozenBalance/TRX_PRECISION = 1`; account true weight = 1. Consistent so far.
2. Freeze an additional 1,500,000 sun for the same account via the same path. Account's `frozenBalance` becomes 3,000,000 sun → true weight = 3, but `repo.addTotalNetWeight(frozenBalance / TRX_PRECISION)` only adds `1,500,000/1,000,000 = 1`, bringing recorded total contribution for this account to `1 + 1 = 2` instead of the correct `3`.
3. Compare against the `FreezeBalanceActuator` path (see `oldNetWeight`/`newNetWeight`/`increment` logic) for the same sequence of amounts on a different account — it correctly captures the delta as `3 - 1 = 2` after the second freeze, then `1` on the first, totaling `3`, matching the account's real weight. The two independent code paths that mutate the same global counters use inconsistent formulas, so `TotalNetWeight` no longer equals the sum of true per-account weights whenever the TVM native freeze path is exercised with sub-precision fragmentation.
