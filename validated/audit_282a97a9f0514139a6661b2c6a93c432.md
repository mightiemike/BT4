## Finding Confirmed

### Title
BlockEpiloguePayload::V1 transaction hash does not bind `to_make_hot` hot-state promotion set - [File: types/src/transaction/block_epilogue.rs]

### Summary
`BlockEpiloguePayload::V1` embeds hot-state promotion data (`to_make_hot`) inside a `BlockEndInfoExt` wrapper, but that wrapper's custom `Serialize` implementation silently drops the `to_make_hot` field before BCS-serializing. Since `Transaction`'s `CryptoHash` is computed over its BCS bytes, this means the committed transaction hash for a `V1` block epilogue is identical regardless of which state keys are promoted to hot state, breaking the hash-to-effect binding relied on by `TransactionWithProof`/`TransactionInfo` verification.

### Finding Description
`BlockEpiloguePayload::V1` is defined as: [1](#0-0) 

The `block_end_info` field is a `BlockEndInfoExt` (alias for `TBlockEndInfoExt<StateKey>`), which internally stores both the persistent `BlockEndInfo` and the `to_make_hot: BTreeSet<StateKey>` set: [2](#0-1) 

Critically, the type's `Serialize` implementation only serializes the `inner` field and completely ignores `to_make_hot`: [3](#0-2) 

Correspondingly, `Deserialize` always reconstructs an *empty* `to_make_hot` set, confirming the field is not part of the wire/hash representation at all: [4](#0-3) 

`Transaction::hash()` (via the `CryptoHash`/`CryptoHasher` derive used throughout `types/src/transaction/mod.rs`) computes the transaction hash by BCS-serializing the enum and hashing those bytes. Because `BlockEndInfoExt::serialize` drops `to_make_hot`, two `Transaction::BlockEpilogue(BlockEpiloguePayload::V1 { block_id, block_end_info, fee_distribution })` values that differ *only* in the `to_make_hot` set of `block_end_info` will produce byte-identical BCS encodings, and therefore byte-identical `CryptoHash` outputs.

### Impact Explanation
The transaction hash is the anchor used by `TransactionInfo`/`TransactionWithProof` to bind a leaf in the transaction accumulator to the actual transaction content that was executed and committed. If the hash cannot distinguish between two different `to_make_hot` promotion sets, then a light client or auditor verifying a `TransactionWithProof` for a `V1` block epilogue transaction cannot detect that the hot-state promotion set recorded/replayed differs from what was originally executed. Since `to_make_hot` directly drives hot-state promotion in the state store (`types/src/state_store/hot_state.rs` and `try_get_keys_to_make_hot` in `block_epilogue.rs`), this can allow a mis-recomputed or substituted promotion set during replay/restore to pass hash verification unnoticed, corrupting the effective hot-state layout while the accumulator/proof chain looks unchanged.

### Likelihood Explanation
This is a deterministic serialization bug, not a probabilistic or adversarial-timing issue: any `V1` block epilogue transaction's hash is *always* independent of `to_make_hot`. It reliably triggers on any chain history/replay path that constructs `BlockEpiloguePayload::V1` values (this variant is present in the codebase's block epilogue handling in `aptos-move/aptos-vm/src/aptos_vm.rs`), making the divergence reproducible with a simple unit test rather than requiring any special conditions.

### Recommendation
Include `to_make_hot` in the serialized/hashed representation of `BlockEndInfoExt` (or otherwise fold it into `BlockEpiloguePayload::V1`'s hashed bytes) once the hot-state representation is finalized, so the transaction hash uniquely binds the promotion set. Until then, treat `V1` as unsuitable for any use where `to_make_hot` affects committed ledger state relied upon by hash-based proof verification (this appears to already be flagged by the `TODO(HotState)` comment near the `Arbitrary` impl), and audit all code paths that trust `V1` transaction hashes to also validate the promotion set out-of-band.

### Proof of Concept
```rust
use aptos_crypto::hash::CryptoHash;
use aptos_crypto::HashValue;
use aptos_types::state_store::state_key::StateKey;
use aptos_types::transaction::{Transaction};
use aptos_types::transaction::block_epilogue::{
    BlockEpiloguePayload, BlockEndInfo, BlockEndInfoExt, FeeDistribution,
};
use std::collections::{BTreeMap, BTreeSet};

let block_id = HashValue::zero();
let inner = BlockEndInfo::new_empty();
let fee_distribution = FeeDistribution::new(BTreeMap::new());

let key_a = StateKey::raw(b"a");
let key_b = StateKey::raw(b"b");

let ext1 = BlockEndInfoExt::new(inner.clone(), BTreeSet::from([key_a]));
let ext2 = BlockEndInfoExt::new(inner, BTreeSet::from([key_b]));

let tx1 = Transaction::BlockEpilogue(BlockEpiloguePayload::V1 {
    block_id,
    block_end_info: ext1,
    fee_distribution: fee_distribution.clone(),
});
let tx2 = Transaction::BlockEpilogue(BlockEpiloguePayload::V1 {
    block_id,
    block_end_info: ext2,
    fee_distribution,
});

let bytes1 = bcs::to_bytes(&tx1).unwrap();
let bytes2 = bcs::to_bytes(&tx2).unwrap();
assert_eq!(bytes1, bytes2); // to_make_hot dropped by custom Serialize impl

assert_eq!(tx1.hash(), tx2.hash()); // hashes collide despite different to_make_hot
``` [5](#0-4)
