### Title
Order-matching DoS via `MAX_MATCH_NUM` revert deep inside `execute()` in `MarketSellAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The external report's bug class is: a shared, automatic covering/processing loop that iterates over externally-influenced state (other users' investment strategies) can hit a case that forces the whole user operation to revert, permanently blocking that legitimate user action. The closest reachable analog in java-tron is `MarketSellAssetActuator.matchOrder()`, which walks the on-chain order book (state that unprivileged third parties freely populate) and throws a `ContractValidateException` — converted to `ContractExeException` — once more than `MAX_MATCH_NUM` (20) maker orders must be matched, aborting a transaction that already mutated account/asset state.

### Finding Description
`execute()` performs balance/asset debits and order creation before calling `matchOrder()`: [1](#0-0) 

Inside `matchOrder()`, the loop increments `matchOrderCount` for every maker order consumed and throws once the counter exceeds the fixed constant `MAX_MATCH_NUM`: [2](#0-1) 

`MAX_MATCH_NUM` is a fixed constant (20): [3](#0-2) 

The exception is only caught in `execute()`, not in `validate()`, so it surfaces after the fee has already been debited, tokens/TRX already transferred via `transferBalanceOrToken`, and the taker order already created via `createAndSaveOrder`: [4](#0-3) 

This mirrors the reported bug class: a legitimate, unprivileged user action (a market sell) depends on iterating a data structure (`priceKeysList` / `orderIdListCapsule`, the maker order book) whose shape is controlled by other unprivileged users. If the number of maker orders needed to fill the taker's price/quantity combination exceeds the fixed cap, the transaction is forced to fail via `ContractValidateException`/`ContractExeException`, exactly as the Sushiswap `withdrawInvestment()` interface mismatch forced a revert deep inside a shared, automatic processing path. There is an existing test explicitly demonstrating this failure mode: [5](#0-4) 

### Impact Explanation
Any unprivileged account can create many small maker orders at closely-spaced prices on a token pair (bounded only by `MAX_ACTIVE_ORDER_NUM` = 100 orders per account, and multiple accounts can combine), fragmenting the order book so that a legitimate taker's `MarketSellAssetContract` must match more than `MAX_MATCH_NUM` (20) orders to fill even a modest quantity. Any taker attempting to sell into that price level will have their transaction revert, repeatedly, regardless of retries with the same market conditions, denying them the ability to execute the trade at that price — a DoS against the TRC10 exchange/market feature reachable from an ordinary broadcast transaction. Because the check occurs deep inside `execute()` rather than `validate()`, the transaction fee has already been computed and intended for deduction and the actuator has already mutated in-memory account/asset/order state before failing, which is wasteful and error-prone compared to a pre-flight validation check.

### Likelihood Explanation
High likelihood of being triggered unintentionally (thin order books with many small price-adjacent orders are common), and it is trivially triggerable deliberately by any unprivileged account placing multiple small maker orders — no special privileges, keys, or node compromise required, only ordinary `MarketSellAssetContract`/`MarketCancelOrderContract` broadcast transactions.

### Recommendation
- Move the `MAX_MATCH_NUM` check earlier (or design the matching loop to gracefully partial-fill and stop rather than throw), so a taker transaction that would exceed the match limit either partially executes up to the limit and returns the remainder to the order book, or is rejected in `validate()` before any balance/asset mutation and fee application occurs.
- Ensure the transaction-processing layer that wraps `execute()` fully rolls back all capsule mutations (balance debit, asset transfer, order persistence) when `ContractExeException` is thrown, so a reverted match does not leave the account or order book in a partially-mutated state.
- Consider making `MAX_MATCH_NUM` a governance/committee-configurable dynamic parameter (similar to other `dynamicStore` limits) so it can be tuned without a hard-coded cap that structurally blocks legitimate trades under normal market fragmentation.

### Proof of Concept
1. Attacker (or naturally fragmented market) creates `MAX_MATCH_NUM + 1` (21) small maker sell orders for token pair (A, B) at slightly different, matchable prices, each below `MAX_ACTIVE_ORDER_NUM`.
2. A legitimate user submits a `MarketSellAssetContract` (sell B for A) whose quantity/price is compatible with all 21 resting maker orders and requires consuming more than 20 of them to be filled.
3. `execute()` debits the fee and transfers the sell-side asset via `transferBalanceOrToken`, creates the taker order via `createAndSaveOrder`, then calls `matchOrder()`.
4. `matchOrder()` matches orders one by one; once `matchOrderCount` exceeds `MAX_MATCH_NUM`, it throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")`, which `execute()` converts to `ContractExeException`, failing the transaction as shown by the existing `exceedMaxMatchNumLimit` test: [6](#0-5) 
5. The user cannot successfully execute this legitimate market sell at this price/quantity combination as long as the order book fragmentation persists, reproducing the "withdrawal/operation permanently blocked by shared, automatically-iterated state" pattern described in the external report.

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
