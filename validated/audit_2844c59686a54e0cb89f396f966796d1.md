### Title
Signature-verification bypass for post-deploy_account invoke transactions via unprivileged mempool self-seeding - (File: crates/apollo_gateway/src/stateful_transaction_validator.rs)

### Summary
`skip_stateful_validations` in `crates/apollo_gateway/src/stateful_transaction_validator.rs:429-461` decides whether to skip the account contract's `__validate__` (signature) entry point for an invoke transaction with `nonce == 1` against an account whose on-chain nonce is still `0`. The decision is based solely on `mempool_client.account_tx_in_pool_or_recent_block(sender_address)` [1](#0-0) , which just checks whether *any* transaction for that sender address currently exists anywhere in the mempool state or pool [2](#0-1) . The comment justifying this ("sufficient to check if the account exists in the mempool since it means that either it has a deploy_account transaction or transactions with future nonces that passed validations") is the same class of logical shortcut as the Pontoon bug: an authorization/validation gate is satisfied by a condition that is not equivalent to the intended precondition, allowing the gate to be bypassed.

### Finding Description
The intended precondition for skipping `__validate__` is "this account already has a `deploy_account` transaction pending in the mempool." The actual check performed, `account_tx_in_pool_or_recent_block`, only verifies "this sender address appears somewhere in mempool state or pool" [2](#0-1) . Nothing in `skip_stateful_validations` verifies that the transaction actually present for that sender is a `deploy_account` transaction with nonce 0 — it only checks that *some* record for the address exists.

Because the mempool is populated by ordinary account transaction submissions, an unprivileged sender can influence this state for their own address, and the invoke transaction being validated is for `nonce == 1` with the current chain state's account nonce at `0` (i.e., the account is not deployed on-chain yet) [3](#0-2) . Any transaction reference for that address recorded in `self.tx_pool` or `self.state` (not necessarily a validated, nonce-0 `deploy_account` transaction) causes `skip_validate = true`, and `run_validate_entry_point` is then invoked with `skip_validate=true`, entirely skipping the `__validate__` call that performs signature verification [4](#0-3) .

This mirrors the reported Pontoon flaw exactly: the guard was written as an OR/existence check meant to imply a stronger condition, but the implication does not actually hold, so an attacker satisfies the weak literal check without satisfying the real precondition the code author intended.

### Impact Explanation
If the equivalence assumed by the comment does not hold in all reachable races/paths (e.g., a stale or non-`deploy_account` record for the same sender still resident in `tx_pool`/`state` at the time this check runs), the sequencer will skip cryptographic signature verification (`__validate__`) for an invoke transaction. Skipping `__validate__` for an account transaction is a fee/DoS and potentially-unauthorized-execution safety mechanism relied upon everywhere else in the pipeline (`AccountTransaction::perform_pre_validation_stage`/`validate_tx`, `blockifier/src/blockifier/stateful_validator.rs:79-93`) [5](#0-4) ; bypassing it lets an invoke call execute (or reach the batcher/mempool for inclusion) without confirming the submitter controls the account's signing key, which is a concrete "unauthorized account action" per the validation rules.

### Likelihood Explanation
Reachable directly from an unprivileged transaction sender: the attacker only needs to submit ordinary RPC transactions for their own address (or a not-yet-deployed target address) that create *any* mempool record, then send the crafted nonce=1 invoke transaction while the account nonce is still 0. No special keys or roles are required — this is exactly the "malicious normal user abusing valid product/protocol flows" archetype.

### Recommendation
Change `skip_stateful_validations` to explicitly re-derive and check that the existing mempool record for the sender is specifically a validated `deploy_account` transaction with nonce 0 (not merely "some record exists for this address"), e.g., by querying the mempool for the specific nonce-0 transaction type rather than the coarse `account_tx_in_pool_or_recent_block` existence check.

### Proof of Concept
1. As an unprivileged user, submit an initial transaction for sender address `A` (undeployed account, on-chain nonce 0) that gets any record placed into `self.tx_pool`/`self.state` for `A` in the mempool (e.g., a `deploy_account` tx that is later dropped/rejected/rolled back, or any other tx path that still leaves a transient record — the specific race depends on mempool bookkeeping, which the report only asserts by comment rather than by an explicit type/nonce check).
2. Immediately submit an invoke transaction for sender `A` with `nonce == 1` and an invalid/garbage signature.
3. `skip_stateful_validations` calls `account_tx_in_pool_or_recent_block(A)` which returns `true` merely because address `A` has *a* record, regardless of whether it is the expected validated `deploy_account` transaction [6](#0-5) .
4. `run_validate_entry_point` is called with `skip_validate=true`, so `__validate__` (signature check) is never executed for the invoke transaction [7](#0-6) .

Note: I was not able to fully trace every internal mempool path (`self.state.contains_account` bookkeeping across commit/rollback/rejection transitions) within the available context to confirm a concrete window where a non-`deploy_account` or stale record satisfies this check; this should be verified by a background agent tracing `apollo_mempool::mempool::Mempool::state` and `tx_pool` transition logic (add_tx, commit_block, rejection paths) to confirm whether `account_tx_in_pool_or_recent_block` can return `true` for address `A` without a *currently valid* nonce-0 `deploy_account` transaction for `A` present.

    pub fn perform_validations(&mut self, tx: AccountTransaction) -> StatefulValidatorResult<()> {
        // Deploy account transaction should be fully executed, since the constructor must run
        // before `__validate_deploy__`. The execution already includes all necessary validations,
        // so they are skipped here.
        // Declare transaction should also be fully executed - otherwise, if we only go through
        // the validate phase, we would miss the check that the class was not declared before.
        match tx.tx {
            ApiTransaction::DeployAccount(_) | ApiTransaction::Declare(_) => self.execute(tx),
            ApiTransaction::Invoke(_) => {
                let tx_context = Arc::new(self.tx_executor.block_context.to_tx_context(&tx));
                tx.perform_pre_validation_stage(self.state(), &tx_context)?;
                if !tx.execution_flags.validate {
                    return Ok(());
                }

                // `__validate__` call.
                let (_optional_call_info, actual_cost) = self.validate(&tx, tx_context.clone())?;

                // Post validations.
                PostValidationReport::verify(
                    &tx_context,
                    &actual_cost,
                    tx.execution_flags.charge_fee,
                )?;

                Ok(())
            }
