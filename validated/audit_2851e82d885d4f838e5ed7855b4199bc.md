Confirmed root cause. In `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`, `tokenExchange()` receives both a `shop` string and a `sessionToken` (JWT) as independent parameters. It calls `decodeSessionToken(config)(sessionToken)` purely to validate the signature/expiry of the token, discards the returned payload, and then builds the token-exchange request to `https://${sanitizeShop(config)(shop,true)}/admin/oauth/access_token` using the separately supplied `shop` — never checking that `shop` corresponds to the `dest` claim embedded in the validated `sessionToken`. This is structurally identical to the reported bug class: one field is cryptographically validated (`sessionToken` ~ pair_id) while a second, unrelated field is trusted and used to drive a privileged action (`shop` ~ token_id) without cross-checking correspondence. [1](#0-0) 

The two in-repo callers happen to derive `shop` from the token's own `dest` claim before calling `tokenExchange`, so the mismatch isn't reachable through the shipped `shopify-app-express`/`shopify-app-remix` flows: [2](#0-1) [3](#0-2) 

However, `shopify.auth.tokenExchange` is a public, exported API (`RequestedTokenType`/`tokenExchange` from `@shopify/shopify-api`) that any app author can call directly with an independently sourced `shop` value (e.g., from a query string, header, or other unauthenticated user input) alongside a session token obtained from a *different, legitimately-authenticated* request/shop. Because the library itself performs no binding check between the two, a single merchant/customer who can influence the `shop` argument passed by the app's own (mis-)implementation could get the library to exchange their own valid session token against a victim shop's `/admin/oauth/access_token` endpoint. Whether that succeeds ultimately still depends on Shopify's own OAuth server rejecting a `subject_token` whose `dest` doesn't match the `shop` in the URL — I could not verify Shopify's server-side behavior from this codebase, so I can't confirm end-to-end exploitability, only that the shipped library-level validation gap exists.

### Title
Missing shop/sessionToken binding check in `tokenExchange()` - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`tokenExchange()` validates the `sessionToken` JWT's signature/expiry via `decodeSessionToken`, but never verifies that the token's `dest` (shop) claim matches the separately supplied `shop` parameter used to construct the outbound `/admin/oauth/access_token` request.

### Finding Description
The function destructures `shop` and `sessionToken` as independent caller-supplied inputs. `decodeSessionToken(config)(sessionToken)` is awaited only for its validation side effect (throwing on bad signature/expiry) — its return value (the payload, including `dest`) is discarded. The `shop` value used to build the request URL comes entirely from the caller, with only cosmetic sanitization via `sanitizeShop`, and is never cross-checked against the token's embedded shop. [4](#0-3) 
This mirrors the reported `PixelswapStreamPool` flaw exactly: a validated identifier (`sessionToken`/pair_id) is checked for authenticity in isolation, while a second, unchecked identifier (`shop`/token_id) is used to select the resource/account that the privileged operation acts on.

### Impact Explanation
If any consumer of this library API (a Shopify app built with `@shopify/shopify-app-express`, `@shopify/shopify-app-remix`, etc., or a custom integration using `shopify-api` directly) passes a `shop` value that is not derived from and verified against the session token's own `dest` claim, an attacker holding a valid session token for their own shop could attempt to exchange it for an access token scoped to an arbitrary target shop string, potentially leading to cross-tenant token issuance/confusion if Shopify's OAuth server does not itself reject the mismatch.

### Likelihood Explanation
Low-to-moderate: the bundled `shopify-app-express` and `shopify-app-remix` packages in this repo already derive `shop` safely from the token payload, so the two "in-the-box" call sites are not exploitable. Exploitability depends entirely on (a) an app author calling `shopify.auth.tokenExchange` with an unvalidated/externally-controlled `shop` value, and (b) Shopify's remote OAuth token endpoint not independently rejecting a `subject_token`/`shop` mismatch — the latter could not be verified from this codebase.

### Recommendation
Decode the `sessionToken` payload once, extract its `dest` shop domain, and either use that value exclusively when building the outbound request, or explicitly assert `sanitizeShop(config)(shop, true) === sanitizeShop(config)(new URL(payload.dest).hostname, true)` before proceeding, throwing an `InvalidJwtError`/`InvalidShopError` on mismatch. This closes the gap regardless of how downstream apps call the API.

### Proof of Concept
Not independently reproducible from this repository alone: constructing an end-to-end exploit requires confirming whether Shopify's live `/admin/oauth/access_token` endpoint accepts a `subject_token` (session token) whose `dest` differs from the shop domain in the request URL. Within the library itself, the gap is demonstrable by unit-testing `tokenExchange({shop: 'victim-shop.myshopify.com', sessionToken: signedTokenForOtherShop, requestedTokenType: RequestedTokenType.OfflineAccessToken})` and observing that no error is thrown prior to the outbound HTTP call, despite the shop/token mismatch.
