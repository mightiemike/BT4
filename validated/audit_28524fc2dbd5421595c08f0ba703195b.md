## Title
Witness/voting rewards accrued in a cycle with zero recorded vote-count become permanently unclaimable, mirroring the "epoch with no depositors" reward-loss pattern - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
java-tron distributes block/standby/transaction-fee rewards to a witness for the *current cycle* via `MortgageService.payReward`, which stores the amount keyed by `(cycle, witnessAddress)` in `DelegationStore`. [1](#0-0)  Distribution of that per-cycle bucket to voters depends entirely on the vote-count snapshot recorded for that witness in that same cycle. If that snapshot is zero, the reward is silently skipped from every voter's payout calculation and there is no mechanism to redistribute or reclaim it later — the funds remain permanently stuck in the reward bucket, exactly analogous to `tokenRewardsPerEpoch[token][epochStart]` being lost when a `BribeVotingReward` epoch has no depositors.

### Finding Description
Two reward algorithms exhibit the same root cause:

**Old algorithm** — `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` divides a witness's per-cycle reward pool by the per-cycle recorded vote total, but explicitly skips the cycle entirely (`continue`) when that total is zero: [2](#0-1) 
The per-cycle vote total used here (`delegationStore.getWitnessVote(cycle, srAddress)`) is written once per maintenance cycle from the witness's live vote count: [3](#0-2) 

**New VI algorithm** — `DelegationStore.accumulateWitnessVi` (and its duplicate in `RewardViCalService.accumulateWitnessVi`) folds a witness's per-cycle reward into the running voter-index (`Vi`) only if the *voteCount* passed in is nonzero. If `voteCount == 0` (even though `reward != 0`), the function just forwards the previous `Vi` unchanged, meaning that cycle's reward is dropped from the index forever: [4](#0-3) [5](#0-4) 
This is invoked every maintenance cycle for *all* witnesses using the vote count recorded before the current cycle's votes are tallied: [6](#0-5) 

Because reward crediting (`addReward`) and vote-count snapshotting are decoupled in time, a witness can accrue block/standby/tx-fee reward in a cycle where its snapshotted vote count is (or drops to) zero — e.g., all delegators withdraw/clear their votes mid-cycle while the witness, still classified active from the prior cycle, keeps producing blocks and accruing rewards. On the next maintenance run, that cycle's reward is permanently excluded from voter payouts by both algorithms, with no function anywhere in the codebase (unlike the reporter's suggested `renotifyRewardAmount`) to redistribute or recover it.

### Impact Explanation
High — the reward value (TRX allowance) that was legitimately paid out of the block/standby/transaction-fee pools becomes permanently irrecoverable by any voter, and remains as dead-weight state in `DelegationStore` forever. This is a real accounting/economic loss of protocol-distributed funds, not merely a theoretical edge case, since vote withdrawal/clearing (`clearVote`, unfreeze) mid-cycle is a normal unprivileged user action.

### Likelihood Explanation
Low/medium, mirroring the original report: it requires a witness's cycle-recorded vote total to be zero at the moment `doMaintenance` processes that cycle's rewards (e.g., due to mass vote withdrawal or a newly registered witness receiving block rewards before ever being voted for), which is a plausible but not routine sequence of events.

### Recommendation
Add an explicit fallback path: when `voteCount == 0` but `reward != 0` in `DelegationStore.accumulateWitnessVi`/`RewardViCalService.accumulateWitnessVi`, either (a) carry the unused reward forward and merge it into the next cycle that has a nonzero vote count for that witness, or (b) route it to a recoverable pool (e.g., burn back to `TransactionFeePool` or brokerage) instead of silently discarding it from the `Vi` computation. The equivalent skip in `MortgageService.computeReward` (old algorithm, `totalVote == 0` branch) should receive the same treatment.

### Proof of Concept
1. Witness `W` is an active SR with vote count `V > 0` at start of cycle `C`.
2. All voters call vote-clearing/unfreeze during cycle `C`, driving `W`'s live `voteCount` to `0` (recorded via `WitnessCapsule.setVoteCount`), while `W` remains active (status only updates at next maintenance) and produces blocks, accruing reward via `MortgageService.payReward` → `delegationStore.addReward(C, W, value)`.
3. At the next `MaintenanceManager.doMaintenance()` call for cycle `C`, `accumulateWitnessVi(C, W, 0)` is invoked with `voteCount = 0`; since `reward != 0` but `voteCount == 0`, the branch simply forwards `preVi` unchanged.
4. Any subsequent voter for `W` computes rewards via `deltaVi = endVi - beginVi` across cycles; because `Vi` for cycle `C` never incorporated `W`'s reward, that reward amount is excluded from every future `computeReward`/`getNewRewardAlgorithmReward` result and is never paid to `withdrawReward`/`WithdrawRewardProcessor`. No function exists to reclaim it. [7](#0-6)

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
