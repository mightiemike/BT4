## Finding: Replay-verify skips checkpoint/state-root fields when validating re-executed output against archived `TransactionInfo`

### Title
Replay-verify tooling accepts a divergent state/hot-state/position state root because `ensure_match_transaction_info` never compares checkpoint hashes - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness check used by `storage/db-tool`'s `replay_on_archive` "Verifier" to confirm that re-executing archived transactions reproduces the historical, consensus-committed ledger state. The function compares status, gas, the write-set hash, and the event-root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the archived `TransactionInfo`. As a result, replay-verify can report success even though the locally-derived authenticated state root (the actual Merkle/JMT commitment of world state) diverges from the one that was signed by validators and stored on-chain.

### Finding Description
`ensure_match_transaction_info` explicitly checks only:
- transaction status vs. `txn_info.status()`
- `gas_used()` vs. `txn_info.gas_used()`
- `write_set_hash` (hash of this txn's write set) vs. `txn_info.state_change_hash()`
- `event_root_hash` vs. `txn_info.event_root_hash()` [1](#0-0) 

The in-code TODO acknowledges the gap directly: *"this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."* [2](#0-1) 

This is not a theoretical caller: `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify` is exactly the "replay verify" tool referenced in the TODO — it re-executes archived transactions with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` as the *only* correctness gate before declaring a chunk verified. [3](#0-2) 

The write-set hash check only proves that the VM produced the same *logical* set of key/value writes for that one transaction. It does **not** prove that those writes, once folded into the persistent Jellyfish Merkle Tree / hot-state / position-state trees at a checkpoint boundary, produce the same root hash that was actually committed and signed in the historical ledger (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash` on `TransactionInfoV0`/`V1`). [4](#0-3) [5](#0-4) 

Any divergence introduced downstream of write-set generation — e.g. a bug in checkpoint aggregation, state-tree merklization, hot-state root computation, or the newly-introduced native-position state root (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) — would silently pass replay-verify because the field that would expose the divergence is simply never inspected. [6](#0-5) 

### Impact Explanation
Replay-verify (`db-tool replay-on-archive`, and the CLI/debugger paths in `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` that call the same comparator) is the tool operators and auditors rely on to certify that a backup/archive's history is internally consistent and matches what the chain actually committed. Because checkpoint/state-root fields are excluded from the comparison, a corrupted or buggy state-root commitment (whether from a storage bug, a merklization defect, or a maliciously crafted archive whose write sets are correct but whose recorded checkpoint hash is wrong) is not caught, giving a false assurance of ledger integrity. This directly matches the "Wrong ... state proof accepted as valid" and "authenticated API ... output bound to the wrong ... proof context" categories, since the state checkpoint hash is exactly the authenticated proof-context binding for the state.

### Likelihood Explanation
This requires no attacker privilege to trigger a false-positive verification result — it is a code-path gap in the verifier itself. Any historical or future divergence between the write set and the actual persisted state root (a class of bug distinct from write-set mismatches) will pass unnoticed by design. The gap is broadened further as trading-native/hot-state features (`TRANSACTION_INFO_V1`, `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) are rolled out, since these add new checkpoint-hash fields that are also excluded from the comparator.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the expected `TransactionInfo`) against the corresponding checkpoint hashes recomputed from the replayed execution/storage state, before considering replay-verify successful.

### Proof of Concept
1. Take an archived backup range containing at least one checkpoint transaction with a `state_checkpoint_hash` (or, once enabled, `position_state_checkpoint_hash`).
2. Run `replay_on_archive` (`storage/db-tool/src/replay_on_archive.rs`) with a locally modified execution/storage layer that produces the correct write set/events for each transaction but computes an incorrect state/position checkpoint root at the checkpoint boundary (simulating a merklization or checkpoint-aggregation bug).
3. Observe that `Verifier::execute_and_verify` calls `TransactionOutput::ensure_match_transaction_info` [7](#0-6)  and returns `Ok(None)` (no failure) despite the checkpoint hash being wrong, because the function body never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` [8](#0-7) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
