## Analysis

The Trail of Bits `withdraw` finding is about a contract accepting an attacker/user-supplied recipient address with no restriction, letting funds be sent to an address (the contract itself) from which they can never move again. The closest native analog in this repo is the `RevertInstructions.FundRecipient` field that flows through `x/uexecutor`'s inbound-revert and gas-refund paths.

`FundRecipient` is fully attacker-controlled: it is part of the `Inbound.RevertInstructions` the relayer/UV forwards from the source-chain event, and it is never checked against `IsValidAddress` anywhere. [1](#0-0) [2](#0-1) 

`Canonicalize()` only *lenient*-canonicalizes `FundRecipient` (falls back to the trimmed raw string if it doesn't parse — it never rejects), and `ValidateForExecution()` validates `Recipient` for FUNDS/GAS/isCEA paths but never validates `RevertInstructions.FundRecipient` at all. [3](#0-2) 

Both `buildRevertOutbound` (inbound-revert path) and `applyGasRefund` (outbound gas-refund path) take `FundRecipient` verbatim and hand it to `common.HexToAddress(...)` before minting real PRC20 value to it: [4](#0-3) [5](#0-4) [6](#0-5) 

`common.HexToAddress` on a malformed or non-hex string silently truncates/zero-pads to a 20-byte value rather than erroring, so a bad `FundRecipient` does not fail the mint — it mints to whatever byte pattern the malformed string resolves to (which can collapse to the zero address or to an address nobody controls), so bridged funds/gas refunds land at an address for which no private key or contract logic exists.

### Title
Unvalidated `RevertInstructions.FundRecipient` can permanently strand bridged funds and gas refunds - (File: x/uexecutor/types/inbound.go, x/uexecutor/keeper/build_revert_outbound.go, x/uexecutor/keeper/outbound.go)

### Summary
`Inbound.RevertInstructions.FundRecipient` is a fully user/relayer-supplied field that is used verbatim as the mint destination for (a) inbound-revert PRC20 re-minting and (b) excess-gas refunds, with no address-format validation anywhere in the pipeline. This mirrors the reported `PrimitiveEngine.withdraw` bug class — an unchecked recipient parameter lets value be sent to a dead/unintended destination.

### Finding Description
`Canonicalize()` calls `LenientCanonicalizeAddress`, which by design never rejects a bad value — on parse failure it just returns the trimmed original string [7](#0-6) . `ValidateForExecution()`, which is the sole gate that produces a failed PCTx for bad addresses, checks `Recipient` for `FUNDS`/`GAS`/isCEA but has no case for `RevertInstructions.FundRecipient` [8](#0-7) .

Downstream, `buildRevertOutbound` sets `outbound.Recipient = inbound.RevertInstructions.FundRecipient` directly [4](#0-3) , and when the revert/refund is actually executed, `handleFailedOutbound`/`applyGasRefund` do `common.HexToAddress(recipient)` and call `CallPRC20Deposit` / `CallUniversalCoreRefundUnusedGas` with that address as `to`/`recipient` [9](#0-8) [10](#0-9) . `common.HexToAddress` does not error on malformed input — it deterministically produces some 20-byte address (often the zero address for empty/garbage strings), so the mint always "succeeds" from the protocol's point of view, but the resulting PRC20 balance is credited to an address that is provably uncontrollable (e.g. `0x000...000`).

### Impact Explanation
Any inbound that carries a malformed `RevertInstructions.FundRecipient` (e.g., empty string, non-hex garbage, or a value that happens to canonicalize to the zero address) causes the automatic revert-mint and/or excess-gas-refund step to permanently mint the bridged PRC20 or refunded gas token to an unusable address instead of returning it to the depositor. This is an unauthorized/irrecoverable loss of user funds through the ordinary honest-validator inbound → revert/refund pipeline, satisfying the in-scope "permanent freezing/loss of user or protocol-controlled funds" impact category, without requiring any privileged actor — the attacker is simply the original inbound submitter (or malformed data reaching the source-chain event that a UV faithfully relays).

### Likelihood Explanation
`FundRecipient` originates from source-chain event data that ordinary users control when initiating a bridge deposit, and it passes through the vote/finalization pipeline with no execution-time validation before being used as a fund destination in both `handleFailedOutbound` (INBOUND_REVERT path, triggered whenever the primary outbound execution or ballot fails) and `applyGasRefund` (triggered on essentially every completed outbound with excess gas). Because these are default flows reached by any user whose bridge transaction reverts or overpays gas — not a rare edge case — the likelihood of an inbound with a bad `FundRecipient` reaching mint code is high, and it requires zero validator/relayer misbehavior.

### Recommendation
- **Short term:** Add `RevertInstructions.FundRecipient` validation to `Inbound.ValidateForExecution()` (reject empty or non-hex values, mirroring the existing `Recipient` checks for `FUNDS`/`GAS`), and fail the outbound/refund construction (marking it `ABORTED` for manual intervention) instead of silently minting to `common.HexToAddress`'s fallback value when the field is invalid or resolves to the zero address.
- **Long term:** Add invariant/fuzz tests (analogous to the Echidna property in the seed report) asserting that revert and gas-refund recipients are always non-zero, valid 20-byte addresses before any `CallPRC20Deposit` / `CallUniversalCoreRefundUnusedGas` call is issued.

### Proof of Concept
1. A user submits a source-chain bridge deposit whose gateway event encodes `RevertInstructions.FundRecipient = ""` (or any non-hex string) alongside a payload/amount designed to fail execution (e.g., an invalid function selector, as already used elsewhere in the test suite to force `ExecutionFailed`) — see `vote_inbound_validation_test.go` lines 123-182 for how execution failures are already forced.
2. UVs reach quorum on `MsgVoteInbound`; `ValidateForExecution()` passes because it never checks `RevertInstructions.FundRecipient`.
3. `handleFailedInboundValidation` / `handleFailedOutbound` builds the INBOUND_REVERT outbound via `buildRevertOutbound`, copying the malformed `FundRecipient` into `outbound.Recipient`.
4. On outbound observation, `handleFailedOutbound` calls `CallPRC20Deposit(ctx, prc20, common.HexToAddress(malformedRecipient), amount)`, minting the full bridged amount to the zero/garbage address rather than back to the user, permanently freezing the funds.

Note: I could not execute this end-to-end in a live node to directly observe the resulting balance (index-based static analysis only); the trace above is based on tracing the exact code paths cited. A Devin session with repo access could confirm the exact `common.HexToAddress` fallback behavior for the specific malformed strings a source-chain relayer could realistically produce.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")

			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")

			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)

			return errors.Wrap(err, "invalid payload")

// LenientCanonicalizeAddress canonicalizes addr for chain, falling back to
// the trimmed input when it does not parse.
func LenientCanonicalizeAddress(chain, addr string) string {
	canon, err := CanonicalizeAddressByNamespace(chain, addr)
	if err != nil {
		return strings.TrimSpace(addr)
	}
	return canon
}
