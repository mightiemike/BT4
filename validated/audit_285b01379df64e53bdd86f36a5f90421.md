### Title
`ensure_match_transaction_info` skips state-checkpoint root validation, letting replay-verify tooling silently accept a divergent state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  is the comparison routine used by offline/operational verification tools (`db-tool`'s `replay_on_archive`, `aptos-debugger`, and the `aptos-cli` transaction simulate/replay path) to confirm that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` recorded on an archived/backed-up ledger. It checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash, but it never compares `state_checkpoint_hash` (the SMT/JMT root of the whole account/resource state at a checkpoint), nor `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`. This gap is called out by the code's own TODO comment.

### Finding Description
The function body ends with: [2](#0-1) 
which explicitly documents that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

`state_checkpoint_hash` is the root hash of the global Move state tree at that version — the single most important integrity value a replay tool should reproduce and confirm, since a divergence there means the locally recomputed state (used for all future execution/queries) is not the same object the network committed to. The write-set hash check alone is insufficient: it only proves the transaction's own delta was reproduced identically, not that applying that delta produced the correct resulting global root (a bug in checkpoint/Merkle assembly, batching, or a prior undetected divergence carried forward would still pass).

`replay_on_archive::Verifier::execute_and_verify` calls exactly this weakened check and nothing else: [3](#0-2) 
There is no accompanying comparison of the recomputed state root against `expected_txn_infos[idx].state_checkpoint_hash()` anywhere else in that file's verification loop.

By contrast, the actual online/consensus-facing commit path (`execution/executor/src/workflow/do_state_checkpoint.rs`) does strictly enforce state-checkpoint-hash agreement when known hashes are supplied: [4](#0-3) 
So the live block-execution/commit pipeline is protected, but the archival replay-verification tool (whose entire purpose is to independently re-derive the ledger from a backup and flag any divergence before it becomes an operational or consensus problem) is not.

### Impact Explanation
`replay_on_archive` and the related `aptos-debugger`/CLI paths are the operational safety net used to detect non-determinism or state-divergence bugs in historical or backup data outside of the live consensus/execution pipeline (e.g., during audits, incident investigation, or before promoting a backup as the ground truth). Because the comparator never checks `state_checkpoint_hash`, a scenario where re-execution reproduces the correct write set/events/gas for every individual transaction but accumulates into a different global state root (e.g., due to a state-checkpoint assembly bug, a JMT batching bug, or any bug that affects only the aggregated root and not per-transaction deltas) would be reported as a **successful, matching replay**, masking a real state-commitment integrity issue. This falls squarely in the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong ... state proof accepted as valid" categories, since the tool is meant to catch exactly this class of divergence and currently cannot.

### Likelihood Explanation
This is not a hypothetical edge case — it is a documented, currently-existing gap in production code (not test/mocks), reachable through `replay_on_archive`, a real operator/debugging tool shipped in the `db-tool` binary. It does not require any special privilege to trigger; any state-checkpoint divergence bug elsewhere in the codebase would automatically go undetected by this comparator. That said, the comment frames the missing check as intentional prep work for an unreleased/disabled feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`), suggesting the aptos-core team is already aware of at least the position/hot-state part of the gap; I could not find evidence they are also tracking that the **main** `state_checkpoint_hash` (not just the newer hot-state/position-state hashes) is likewise unchecked, which is the part I consider most exploitable/important since it applies to every checkpointing transaction on mainnet today, not just an unreleased feature.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally recomputed state-checkpoint hash (and, once enabled, hot-state/position-state checkpoint hashes) against `txn_info.state_checkpoint_hash()` whenever the transaction is a checkpoint boundary, mirroring the strict check already present in `do_state_checkpoint.rs`. Until that is done, replay-verify tooling should not be relied upon to certify agreement on state roots, only on write-set/event/gas/status equivalence.

### Proof of Concept
1. Take an archived (backup) ledger with a `TransactionInfo::state_checkpoint_hash` for some checkpoint version `V`.
2. Introduce (or exploit an existing) bug that affects only aggregate state-checkpoint root computation without changing any individual transaction's write set or events (e.g., a defect in JMT batch application ordering, or a stale/incorrectly-reused summary in `do_state_checkpoint.rs`'s in-memory extension path).
3. Run `db-tool replay-on-archive` against the affected range: `Verifier::execute_and_verify` at [3](#0-2)  re-executes the transactions and calls `ensure_match_transaction_info`, which checks status/gas/write-set-hash/event-root-hash only.
4. Because `state_checkpoint_hash` is never compared, the tool reports the chunk as matching/successful even though the locally computed state root at version `V` differs from the one recorded in the backup — the divergence is silently swallowed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
