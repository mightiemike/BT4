### Title
Off-by-One in `DelegateAction` Expiry Check Allows Execution at Intended Expiry Block — (`runtime/runtime/src/actions.rs`)

### Summary

`apply_delegate_action` uses a strict `>` comparison to check whether a `DelegateAction` has expired, but the protocol spec and the field's own doc-comment both state the action should be invalid when `block_height >= max_block_height`. This off-by-one allows a relayer to execute a meta-transaction at the exact block the user intended as the expiry boundary, enabling unauthorized fund transfers or contract calls one block beyond the user's intended deadline.

### Finding Description

In `apply_delegate_action` the expiry guard is:

```rust
// runtime/runtime/src/actions.rs line 435
if apply_state.block_height > delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
```

The operator is `>` (strict greater-than), so the action is accepted whenever `block_height <= max_block_height`. This contradicts two authoritative sources in the same repository:

1. **Field doc-comment** (`core/primitives/src/action/delegate.rs` line 60):
   > "The maximal height of the block in the blockchain **below which** the given DelegateAction is valid."
   "Below which" means valid only for `block_height < max_block_height`; at `block_height == max_block_height` the action should already be expired.

2. **Runtime spec** (`docs/RuntimeSpec/Actions.md` line 402):
   > "If the current block is **equal or greater than** `max_block_height`" → `DelegateActionExpired`
   This explicitly requires `>=`, not `>`.

The existing unit test (`test_delegate_action_max_height`) only verifies that `max_block_height + 1` is rejected; it never asserts that `max_block_height` itself is rejected, so the off-by-one is untested and undetected. The "happy-path" test (`test_delegate_action`) passes `block_height == max_block_height` and expects success, which is the wrong expected outcome per the spec. ### Impact Explanation

`DelegateAction` (NEP-366 meta-transactions) lets a user pre-sign a bundle of actions and hand it to a relayer. `max_block_height` is the user's only on-chain time-bound: once that height is reached the signed payload should be dead. Because the check is `>` instead of `>=`, the relayer retains one extra block of validity.

Concrete harm:

- **Unauthorized fund transfer.** A user signs a `Transfer` or `FunctionCall` DelegateAction with `max_block_height = N`, then at block `N` considers the action expired and takes a follow-up action (e.g., revokes the access key, or signs a replacement transaction). If the relayer races to include the old DelegateAction in block `N` before the revocation lands, the transfer executes against the user's intent.
- **Contract execution flow breakage.** A DelegateAction calling a contract method (e.g., a DEX swap or NFT mint) executes at block `N` when the user believed it was already dead, potentially at a price or state the user no longer accepts.

The impact maps directly to the HackenProof scope items: *unauthorized transaction*, *loss of funds*, and *contract execution flow breakage*, all reachable by an ordinary unprivileged relayer submitting a user-signed payload.

### Likelihood Explanation

The `DelegateAction` feature is live on mainnet. Any relayer that holds a signed DelegateAction can trivially exploit the off-by-one by waiting until `block_height == max_block_height` to submit. No special privilege, key compromise, or network-level access is required — only the ability to submit a transaction, which is available to any unprivileged user. The user's only defense is to set `max_block_height = N - 1` instead of `N`, but the spec and field description give no hint that this workaround is necessary.

### Recommendation

Change the comparison from strict `>` to `>=` in `apply_delegate_action`:

```rust
// runtime/runtime/src/actions.rs
if apply_state.block_height >= delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
```

Also update `test_delegate_action_max_height` to assert that `block_height == max_block_height` is rejected (not just `max_block_height + 1`), and update `test_delegate_action` to use `max_block_height - 1` as the current block height so the happy path remains valid.

The error variant's doc-comment (`"max_block_height` is less than actual block height"`) should also be corrected to `"max_block_height` is less than or equal to actual block height"` to match the fixed semantics. [1](#0-0) [5](#0-4) 

### Proof of Concept

The existing test suite already demonstrates the bug without any modification:

```rust
// runtime/runtime/src/actions.rs — test_delegate_action (line 1282)
// apply_state.block_height == max_block_height → action SUCCEEDS (wrong per spec)
let apply_state = create_apply_state(signed_delegate_action.delegate_action.max_block_height);
apply_delegate_action(...).expect("Expect ok");
assert!(result.result.is_ok(), ...);  // passes — but spec says this should be DelegateActionExpired
```

A relayer exploit in production:

1. User signs `DelegateAction { actions: [Transfer { deposit: 10 NEAR }], max_block_height: N, ... }` and hands it to a relayer.
2. At block `N - 1` the user considers the action about to expire and submits a key-revocation transaction targeting block `N`.
3. The relayer, knowing the off-by-one, submits the DelegateAction in block `N` (same block as the revocation). If the DelegateAction receipt is processed before the revocation receipt within block `N`, the transfer executes.
4. The user loses 10 NEAR despite believing the DelegateAction was expired. [5](#0-4) [6](#0-5)
