## Title
Unauthenticated write-sets accepted during transaction-chunk backup restore (`kv_only_replay`) — `TransactionListWithProof::verify` never checks `state_change_hash` — (File: `types/src/transaction/mod.rs`, `storage/aptosdb/src/backup/restore_utils.rs`, `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
The external report's bug class is "attacker-controlled unbounded/unchecked data is trusted and propagated into consensus-critical logic without validation." The Aptos-native analog I found is structural, not size-related: in the transaction-chunk restore path, the `WriteSet` loaded from a backup file is never checked against the accumulator-authenticated `state_change_hash` carried in the corresponding `TransactionInfo`, unlike the sibling output-list verifier which does perform this check. When `kv_only_replay` restore is used, this unverified write set is fed directly into the state Merkle tree / state KV DB as ground truth.

### Finding Description
`TransactionOutputListWithProof::verify` explicitly authenticates the write set against the proof: [1](#0-0) 

`TransactionOutput::ensure_match_transaction_info` similarly compares `CryptoHash::hash(self.write_set())` against `txn_info.state_change_hash()`: [2](#0-1) 

However, `TransactionListWithProof::verify` — the verifier used for the *transaction* (not output) list variant — only checks the transaction hash, the proof-to-ledger-info binding, and (optionally) event root hashes. It has no `WriteSet` field at all and therefore performs no write-set/`state_change_hash` check: [3](#0-2) 

The backup-restore code for transaction chunks (`LoadedChunk::load`) deserializes `(txn, aux_info, txn_info, events, write_set)` tuples straight from the backup blob. It builds a `TransactionListWithProofV2` for verification purposes, but that structure is only populated with `txns`, `event_vecs`, and `txn_infos` — the independently-loaded `write_sets` vector is kept outside the verified structure entirely: [4](#0-3) 

After `txn_list_with_proof.verify(...)` succeeds (which, per the above, never touched `write_sets`), the same unverified `write_sets` are carried forward and eventually passed to `restore_utils::save_transactions`, where, when `kv_replay` is enabled, they are indexed directly into the state store as the ground truth to compute the new ledger state — with no re-execution and no hash check against `state_change_hash`: [5](#0-4) 

In other words: for every other write-set consumption path in the codebase (`TransactionOutput::ensure_match_transaction_info`, `TransactionOutputListWithProof::verify`), the code enforces `CryptoHash::hash(write_set) == txn_info.state_change_hash()`. The transaction-chunk backup/restore path is the one place that carries a `WriteSet` end-to-end from an untrusted backup file into durable committed state without ever performing that check.

### Impact Explanation
This breaks the "proof and storage pivot" invariant that write sets must survive the executor-to-storage handoff unchanged and bound to the ledger-info-authenticated `state_change_hash`. A corrupted or tampered backup blob (e.g., supply-chain compromise of a shared/public backup bucket, a buggy backup-export tool, or bit-level corruption not caught by any other check) can carry a `TransactionInfo`/transaction/events triplet that is legitimately signed/anchored by the accumulator, paired with an arbitrary, non-matching `WriteSet`. `verify()` will report success, and — when the operator uses `kv_only_replay` restore (a supported, non-privileged restore mode meant to speed up recovery) — the bogus write set is committed straight into the target node's Jellyfish Merkle Tree / state KV store as the authoritative post-transaction state, silently diverging the restored node's state root from the correct, consensus-agreed value. This is a durable, silent state-corruption bug on the restore path, not a mere availability issue, and it can also poison the values later served in that node's authenticated API responses (proofs would still verify at the transaction-info/accumulator level while backing state values are wrong).

### Likelihood Explanation
Likelihood is bounded by the requirement that the attacker (or corruption source) control or tamper with the specific backup blob content consumed during a `kv_only_replay`-style restore, and that this particular restore mode/flow is exercised (it is a supported, documented restore optimization, not an obscure test-only code path — it's referenced from `storage/backup/backup-cli/src/coordinators/restore.rs` and `storage/db-tool`). No consensus/validator signing key compromise or privileged access is required — this is purely a verification gap in code that already treats backup files as adversarial input requiring cryptographic verification (that's the entire purpose of `verify()`), and the well-tested code path uses a `WriteSet` field that is simply omitted from the verified structure and shape of the data.

### Recommendation
Add a write-set/state-change-hash consistency check to the transaction-chunk restore path, mirroring `TransactionOutput::ensure_match_transaction_info`: after loading each `(txn, txn_info, events, write_set)` record, assert `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` before accepting the chunk, and reject/abort restoration (rather than silently continuing) if the check fails. Consider extending `TransactionListWithProof`/`TransactionListWithProofV2::verify` itself to optionally validate an accompanying write-set vector, so any future caller inherits the check by construction instead of relying on call-site diligence.

### Proof of Concept
Conceptual PoC (I was not able to run this in the ask-only sandbox, so this is a structural trace, not an executed exploit):
1. Take a valid transaction backup chunk file (BCS-encoded records of `(Transaction, TransactionInfo, Vec<ContractEvent>, WriteSet)`), leave the manifest, transaction, transaction-info, and events bytes untouched, and only replace the `WriteSet` bytes of one record with an attacker-chosen `WriteSet` (still valid BCS, arbitrary key/value writes).
2. Run the transaction restore controller (`TransactionRestoreController`) with `kv_only_replay` restore mode enabled, pointing at this tampered backup.
3. `LoadedChunk::load` deserializes the tampered `write_sets` vector separately and constructs `TransactionListWithProofV2` without it (`storage/backup/backup-cli/src/backup_types/transaction/restore.rs:105-167`), then calls `.verify(...)`, which returns `Ok(())` because it never inspects `write_sets`.
4. `restore_utils::save_transactions` → `save_transactions_impl` runs `state_store.calculate_state_and_put_updates(&StateUpdateRefs::index_write_sets(first_version, write_sets, ...))` using the tampered write set (`storage/aptosdb/src/backup/restore_utils.rs:258-275`), committing the attacker's chosen state directly into the state Merkle tree/state KV DB.
5. The resulting node's state root at that version diverges from the correct on-chain value even though every `TransactionInfo`/accumulator-based verification along the way reported success.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;
