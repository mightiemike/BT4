### Title
Stale `last-update` timestamp when interest rate is zero causes retroactive interest accrual once utilization becomes non-zero - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The vault's `accrue` function only advances `last-update` when the computed index actually changes. When the vault has zero utilization (no outstanding debt) the interpolated `interest-rate` is `u0`, so `next-index`/`next-liquidity-index` return the unchanged index and `last-update` is left frozen. Once debt is later added and the rate becomes positive, the next `accrue()` call computes `time-delta` against the stale `last-update`, applying the new positive rate over the entire dormant period — inflating debt as if interest had been accruing the whole time, even though no debt existed.

### Finding Description
`accrue` conditionally advances the clock: [1](#0-0) 

`next-index` computes the new index from `rate` (from `interest-rate`) and `time-delta = stacks-block-time - last-update`: [2](#0-1) 

`interest-rate` is derived from `utilization`, which is `calc-utilization(available-liquidity, total-debt)`, returning `u0` when there is no debt: [3](#0-2) 

With `rate = u0`, `calc-multiplier-delta` returns exactly `INDEX-PRECISION` (no growth), so `calc-index-next` returns the same index unchanged: [4](#0-3) 

Because `idx` (and `lindex`) do not change, the guard `(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)` in `accrue` never fires, so `last-update` stays pinned at the old block time — this is the "clock advanced only on change" pattern.

Sequence:
1. Vault has zero debt (`total-debt = 0`), so `utilization = 0` and `interest-rate = 0`. `accrue` is called repeatedly (e.g. via `set-points-util`/`set-points-rate`/DAO calls, or idle deposits/redeems), `idx`/`lindex` never change, `last-update` stays frozen at `T0`.
2. `system-borrow` is called: it first calls `accrue()` (still using pre-borrow, zero-debt utilization ⇒ rate = 0 ⇒ index unchanged ⇒ `last-update` still not advanced), then increases `principal-scaled`/`total-borrowed` — see `system-borrow`: [5](#0-4) 
3. Time passes (`T1`). Utilization is now positive from the new borrow, so `interest-rate` returns a positive rate.
4. Any subsequent call that triggers `accrue()` (deposit, redeem, repay, another borrow, or a DAO parameter update) computes `time-delta = T1 - last-update`, where `last-update` is still `T0` from before the debt even existed. `next-index` thus applies the current positive rate over the *entire* elapsed period, including the time when there was no debt outstanding at all, inflating `index` far beyond what actually accrued.
5. This inflated `index` is used everywhere debt is scaled (`total-debt`, `calc-cumulative-debt`, `debt-preview`), permanently overcharging every borrower's debt with phantom interest that never should have accrued, and correspondingly minting excess treasury LP (`treasury-lp`) and inflating `lindex` for depositors — mispricing shares.

### Impact Explanation
This causes an incorrect, non-reversible over-accrual of interest across all outstanding borrower debt (and a corresponding distortion of `total-assets`/`lindex`/share pricing), which can freeze/misallocate funds and cause protocol insolvency risk since debt figures no longer reflect real economic obligations. This maps to the in-scope Critical impact class: protocol insolvency / permanent freezing of funds, since the miscalculated `index` value permanently corrupts the accounting used for all future debt and asset calculations.

### Likelihood Explanation
Zero-utilization periods (no debt outstanding) are a normal state for a freshly deployed or lightly used vault, and DAO calls like `set-points-util`/`set-points-rate` explicitly invoke `accrue()` — see: [6](#0-5) 
No special privilege or attacker action is required beyond ordinary vault usage timing (an idle vault followed by the first borrow after a period of zero debt), making this readily reachable in normal operation.

### Recommendation
Advance `last-update` in `accrue` unconditionally (on every non-paused invocation), regardless of whether `index`/`lindex` actually changed, mirroring the fix pattern described in the external report (update the timestamp regardless of the computed delta value) so that a zero-rate/zero-utilization period is never later billed at a subsequently-set positive rate.

### Proof of Concept
1. Deploy vault with zero debt; `utilization()` = 0, `interest-rate()` = 0, `last-update = T0`.
2. Call `set-points-rate`/`set-points-util` (or any accrue-triggering entry point) at `T0 + Δ1`: `accrue()` runs, `next-index` returns unchanged `idx` (rate=0), so `last-update` remains `T0`.
3. Call `system-borrow` at `T0 + Δ2`: `accrue()` runs again with pre-borrow zero utilization ⇒ index unchanged ⇒ `last-update` still `T0`; then `principal-scaled`/`total-borrowed` increase.
4. Wait until `T0 + Δ3` (large elapsed time). Call `accrue()` again (e.g., via deposit/redeem/repay): `utilization()` is now positive (from step 3's borrow) ⇒ `interest-rate()` > 0; `time-delta = (T0+Δ3) - T0` (full period since `T0`, not since the borrow); `next-index` applies the positive rate over the whole `Δ3` span, inflating `index` far above the correct value that should only reflect interest accrued since the borrow occurred.
5. `total-debt()`/`debt-preview()` for all borrowers now reflect this inflated `index`, overcharging debt with interest that accrued during a period when no debt existed.

  (let (
      (states (var-get pause-states))
      (u (try! (accrue)))

      (available-assets (get-available-assets))
      (scaled-principal (var-get principal-scaled))
      (idx (var-get index))
      (debt (total-debt))
      (scaled-amount (mul-div-up amount INDEX-PRECISION idx))
      (updated-scaled-principal (+ scaled-principal scaled-amount)))

    (try! (check-caller-auth))
    (asserts! (not (get borrow states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (<= amount available-assets) ERR-INSUFFICIENT-VAULT-LIQUIDITY)
    (asserts! (<= (+ debt amount) CAP-DEBT) ERR-DEBT-CAP-EXCEEDED)

    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed (+ (var-get total-borrowed) amount))
    (try! (send-underlying amount receiver))
