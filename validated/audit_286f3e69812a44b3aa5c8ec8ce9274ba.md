## Finding: Reward recalculation after partial distribution can re-derive feature-gated parameters from the *current* bank instead of the parameters frozen at the original epoch-reward calculation

### Title
Partitioned-epoch-reward recalculation re-snapshots feature flags from the live bank, letting mid-distribution feature activation retroactively change unpaid stake rewards for the same reward epoch - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
Agave computes partitioned epoch rewards once at the epoch boundary in `calculate_rewards_for_partitioning`/`calculate_stake_rewards_and_commissions`, then distributes them incrementally over many blocks. If a restart, warp, or fork causes the reward status to be recomputed mid-distribution, `recalculate_stake_rewards` re-derives the reward parameters (including feature-gated behavior) from the *current* bank's `feature_set` rather than the parameters that were frozen when the original calculation happened, so already-distributed stake accounts can end up paid under one rule set while the remaining, not-yet-distributed accounts for the very same reward epoch get recalculated under a different rule set.

### Finding Description
`calculate_stake_rewards_and_commissions` reads several feature-gated knobs directly from `self.feature_set.snapshot()` at the moment it runs: [1](#0-0) 

This function is called twice for the same reward epoch:
1. At the epoch boundary, via `calculate_rewards_for_partitioning`, to build the original `all_stake_rewards` set that is committed into `Bank::epoch_reward_status` and begins to be paid out block by block. [2](#0-1) 
2. Later, via `recalculate_stake_rewards`, whenever `recalculate_partitioned_rewards_if_active` decides the in-flight distribution needs to be rebuilt (e.g. after `initialize_after_snapshot_restore`, or any other path that rebuilds `epoch_reward_status` from a live bank instead of a serialized snapshot). [3](#0-2) 

The second call re-derives `feature_snapshot` from `self.feature_set` at recalculation time, not from a value pinned at the original calculation: [4](#0-3) 

If any of the flags consumed here (`delay_commission_updates`, `commission_rate_in_basis_points`, `relax_post_exec_min_balance_check`/`adjust_delegations_for_rent`, `custom_commission_collector`, `block_revenue_sharing`, `upgrade_bpf_stake_program_to_v5_1`) become active between the initial calculation and the recalculation, the recomputed `stake_rewards` for the remaining, undistributed stake accounts will differ from what would have been paid under the original rule set - while the accounts already paid out under the earlier calculation keep their old-rule-set amounts. This is structurally the same defect as the reported `voteRewardsCoefficient` issue: a parameter that feeds a per-recipient reward formula for one logical "distribution event" is not frozen at the time the event is created, so different recipients of the same distribution receive amounts computed under different rule versions depending purely on the timing of when their portion was (re)computed.

The codebase is aware this class of divergence is dangerous - a companion safeguard exists for the Alpenglow reward denominator specifically, verified by `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`, which asserts recalculation "must use the same AG delegated stake denominator as the original epoch-boundary calculation": [5](#0-4) 

However that fix only pins the AG delegated-stake denominator; it does not pin the feature-set snapshot consumed by `calculate_stake_rewards_and_commissions` when it is invoked from `recalculate_stake_rewards`.

### Impact Explanation
This produces a silent, per-account balance divergence: stake accounts distributed before a feature activation window receive rewards computed with the old rules, while stake accounts still pending distribution for the identical reward epoch get recalculated and paid with the new rules. Because this only manifests when the epoch-reward distribution is interrupted and rebuilt mid-flight from a live bank (e.g. across a validator restart during active partitioned distribution), it can also cause honest nodes that restarted at different points in the distribution window to compute different `all_stake_rewards`/`epoch_rewards` sums for the same epoch, risking a capitalization/hash mismatch against nodes that never restarted mid-distribution.

### Likelihood Explanation
Requires: (a) an epoch-reward distribution actively in progress (a window that already spans many blocks by design), and (b) a feature activation (or any other bank-state-dependent input to `calculate_stake_rewards_and_commissions`) taking effect during that same window, followed by a path that calls `recalculate_partitioned_rewards_if_active`/`initialize_after_snapshot_restore` on a live (non-frozen-at-original-calc) bank. This is a plausible, non-adversarial sequence of validator restarts and feature-gate rollouts rather than a contrived edge case.

### Recommendation
Freeze the feature-gated reward-calculation inputs (the values captured into `feature_snapshot` inside `calculate_stake_rewards_and_commissions`, plus any other bank-state derived rule inputs) at the time `calculate_rewards_for_partitioning` originally runs, and thread that pinned snapshot through to `recalculate_stake_rewards` instead of re-reading `self.feature_set` from the (possibly different) bank state at recalculation time - mirroring the fix already applied for the AG delegated-stake denominator.

### Proof of Concept
N/A - conceptual analog derived from static analysis of `recalculate_stake_rewards` vs. `calculate_rewards_for_partitioning` and the existing regression test `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`, which demonstrates the codebase already had to specifically patch one instance of this exact class of bug (stale/inconsistent recalculation parameters) but does not cover the feature-set snapshot path.

    /// If rewards are still active, recalculates partitioned stake rewards and
    /// updates Bank::epoch_reward_status. This method assumes that reward
    /// commissions have already been calculated and delivered, and *only*
    /// recalculates stake rewards
    pub(in crate::bank) fn recalculate_partitioned_rewards_if_active<F, TP>(
        &mut self,
        thread_pool_builder: F,
    ) where
        F: FnOnce() -> TP,
        TP: std::borrow::Borrow<ThreadPool>,
    {
        let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
        if epoch_rewards_sysvar.active {
            let thread_pool = thread_pool_builder();
            let (stake_rewards, partition_indices) =
                self.recalculate_stake_rewards(&epoch_rewards_sysvar, thread_pool.borrow());
            self.set_epoch_reward_status_distribution(
                epoch_rewards_sysvar.distribution_starting_block_height,
                stake_rewards,
                partition_indices,
            );
        }
    }
