## Title
Webhook HMAC only signs the raw body, leaving `X-Shopify-Shop-Domain`/`X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers unauthenticated, enabling forged cross-tenant webhook delivery - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
The Pico `read_write` chip bug is a case where a lookup/constraint checks only a subset of the fields that determine an operation's semantics (`opcode`, `a`, `b`, `c`) while leaving other fields that control behavior (`op_a_0`, `is_lb`, `is_sw`, etc.) completely unconstrained, letting an attacker freely manipulate the unchecked fields to change the effective operation while still passing verification. The same class of bug exists in shopify-app-js's webhook authentication: `validateHmacFromRequestFactory` computes and verifies the HMAC over the raw request body only, but the fields that determine *which tenant and event* the message is attributed to (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`, `shopify-event-id`) are read directly from unauthenticated HTTP headers and are never included in the signed content.

### Finding Description
`validateHmacFromRequestFactory` in [1](#0-0)  extracts the `hmac` header, and calls `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` — the digest is computed **only over `rawBody`**. It never mixes in the domain, topic, or webhook id.

`validateFactory` in [2](#0-1)  calls this body-only HMAC check, and only *after* it passes does it call `checkWebhookHeaders`, which reads `topic`, `domain`, `apiVersion`, `webhookId` (and `eventId` for events) straight from the request headers with no cryptographic binding to the signed body: [3](#0-2) .

Downstream, `authenticateWebhookFactory` trusts `check.domain` completely to determine the shop context for the webhook, loading/creating the offline session and admin client for that shop and dispatching to the app's registered handler with `check.topic` and the parsed body: [4](#0-3) . Nothing in this path re-validates that the `domain`/`topic`/`webhookId` combination is the one Shopify actually intended for the signed body — exactly analogous to the unconstrained `op_a_0`/`is_lb`/`is_sw` flags in the Pico `read_write` chip that let a prover redirect the semantic effect of an otherwise-"verified" instruction.

Because the HMAC secret (`config.apiSecretKey`) is the app's single shared secret (not a per-shop secret), *any* legitimately signed `(rawBody, hmac)` pair the app has ever produced/received — for example the fixed sample payload Shopify sends via "Send test notification" in the Partner Dashboard, which any merchant/collaborator with access to the app's webhook subscription can trigger for their own shop — remains a valid, verifiable signature no matter which `domain`/`topic`/`webhookId` header accompanies it on replay. An attacker who can capture (or is handed, e.g. via a test-notification feature) one valid signed body can freely swap the domain/topic headers when POSTing to the app's public webhook endpoint, and `validate()` will still report `valid: true` while attributing the event to an arbitrary victim shop and arbitrary topic.

### Impact Explanation
This breaks the tenant isolation the webhook system is supposed to provide: the app's webhook handler (and anything it does with `session`, `admin` client, and `payload`) is invoked believing it is acting for a shop (`check.domain`) that the signed content was never actually generated for. Depending on what the app does in its webhook handlers (write to the shop's stored data, trigger admin API mutations, delete data on `shop/redact`, etc.), this enables cross-tenant data injection/corruption using only a single captured valid signature, without needing the app secret, a MITM position, or leaked credentials.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one genuine `(rawBody, hmac)` pair not tied cryptographically to headers — achievable by any store owner/collaborator who has access to the app's webhook subscriptions (e.g., via the "send test notification" tooling, which produces a fixed, replayable sample payload signed with the real secret) or by observing any webhook delivery to a shop they control. From there, forging the header values for another shop is a simple unauthenticated HTTP request to the app's public webhook endpoint. No privileged access to Shopify or the app server is required.

### Recommendation
Bind the tenant/event-identifying headers into the signed material, or otherwise cryptographically tie them to the payload before trusting them:
- Verify that `domain` corresponds to a shop with an active, known session/installation before processing (defense-in-depth, already partially done via `ensureValidOfflineSession`, but this alone doesn't stop cross-tenant misattribution using a valid signature for a *different* shop's payload).
- Prefer including `topic`, `domain`, and `webhookId`/`eventId` in the HMAC-signed string (mirroring how `read_write` in the referenced report was fixed by looking up the *whole* instruction, including its selector flags, instead of a partial subset), or reject replays by tracking `webhookId`/`eventId` (nonce) usage so a given signed payload cannot be reprocessed with different header claims.
- At minimum, treat the "send test notification" fixed payload as non-reusable/non-authoritative for production processing paths (e.g., short-circuit test payloads distinctly rather than running them through the same trust path as production events).

### Proof of Concept
1. As a merchant/collaborator with access to the target app's webhook subscription (e.g. via Partner Dashboard "Send test notification" for `products/create`), trigger a test webhook to the app's callback URL. Capture the request: fixed sample `rawBody` plus the real `X-Shopify-Hmac-Sha256` header (valid because it is computed with the actual `apiSecretKey`), along with `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Replay this exact `rawBody` and `X-Shopify-Hmac-Sha256` value in a new POST to the same webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `validateHmacFromRequestFactory` verifies the HMAC against `rawBody` only [5](#0-4)  — succeeds regardless of the swapped headers.
4. `checkWebhookHeaders`/`checkWebhooksHeaders` extracts the attacker-controlled `domain`/`topic`/`webhookId` values as trusted fields [6](#0-5) , and `authenticateWebhookFactory` loads `victim-shop`'s session/admin client and invokes the app's handler for the forged topic [7](#0-6) , causing the app to process a forged event on behalf of a shop that never sent it.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };
