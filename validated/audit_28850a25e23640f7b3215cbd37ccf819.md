### Title
Missing slippage protection in TRON's Bancor-style Exchange withdrawal (`ExchangeWithdrawContract`) allows front-run losses on liquidity removal - (File: `protocol/src/main/protos/core/contract/exchange_contract.proto`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron implements an on-chain Bancor-formula AMM ("TRC10 Exchange") with `ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract`. The swap operation (`ExchangeTransactionContract`) includes an `expected` field to protect against slippage, but the liquidity-removal operation (`ExchangeWithdrawContract`) has no equivalent minimum-amount-out protection. This is the same bug class described in the external report: a liquidity provider withdrawing from a pool cannot bound the amount of the paired token they are willing to accept, and can be front-run into an unfavorable ratio.

### Finding Description
The `ExchangeWithdrawContract` protobuf message only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum field, unlike its sibling `ExchangeTransactionContract`, which explicitly has `expected` for this purpose: [1](#0-0) 

In `ExchangeWithdrawActuator.execute`, the "other token" amount returned to the withdrawing account (`anotherTokenQuant`) is computed purely from the *current* pool balances (Bancor ratio) at execution time, with no user-supplied floor to enforce: [2](#0-1) 

The corresponding validation in `doValidate()` similarly only checks that `anotherTokenQuant` is `> 0` and that the exchange has enough balance and precision — it never compares against a user-specified minimum: [3](#0-2) 

Because any account can submit `ExchangeTransactionContract` trades against the same exchange pool (this is a public, permissionless AMM, not a trusted-role operation), an attacker observing a pending `ExchangeWithdrawContract` transaction in the mempool can front-run it with a trade that skews `firstTokenBalance`/`secondTokenBalance` just before the withdrawal executes. Since `anotherTokenQuant` is recomputed from the post-attack ratio, the victim's withdrawal can be executed at a drastically worse ratio than intended, exactly mirroring the Uniswap `MultiRangeHook`/`FullRangeHook` PoC where a swap shifts price before the liquidity removal executes, causing the victim to receive far less of one token than expected.

### Impact Explanation
This directly causes economic loss to liquidity providers withdrawing from the on-chain Exchange: they receive a token ratio dictated by an attacker-manipulated pool state, with no on-chain mechanism to reject the transaction if the payout falls below their expectation. This is a concrete, unprivileged-user-reachable accounting/settlement impact — any account holding an Exchange-created position and calling withdraw is exposed, and any account can act as the front-runner via ordinary swap transactions.

### Likelihood Explanation
Likelihood is high in practice: front-running via transaction ordering/fee bumping is a well-known and low-cost attack on any public blockchain, and the Exchange feature is fully permissionless — any account can issue `ExchangeTransactionContract` swaps to move the pool ratio immediately before a pending `ExchangeWithdrawContract` is included. No special privileges, insider access, or unusual preconditions are required, only an incentive (larger pools/imbalanced ratios make the attack more profitable).

### Recommendation
Add a minimum-amount-out field to `ExchangeWithdrawContract` (e.g., `expected` similar to `ExchangeTransactionContract`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the withdrawal if the computed `anotherTokenQuant` (or `tokenQuant`, depending on withdrawal direction) is less than the caller-specified minimum, analogous to the `token0Min`/`token1Min` checks recommended in the Uniswap report.

### Proof of Concept
1. LP account A holds an Exchange position and submits `ExchangeWithdrawContract` for `exchange_id=X`, `token_id=firstTokenId`, `quant=Q`, expecting to receive `anotherTokenQuant` of the second token computed from the current pool ratio, per [4](#0-3) .
2. Attacker B observes A's pending transaction and submits an `ExchangeTransactionContract` swap against the same `exchange_id`, shifting `firstTokenBalance`/`secondTokenBalance` sharply (processed by `ExchangeTransactionActuator`, which updates the same exchange balances used by withdraw).
3. B's swap is ordered before A's withdrawal (e.g., via higher priority/fee).
4. A's `ExchangeWithdrawContract` executes against the now-skewed pool, and `anotherTokenQuant` is computed from the manipulated ratio, per [3](#0-2) ; there is no field in the contract or check in the actuator preventing A from receiving far less of the second token than intended — the analogous scenario to the report's `test_MissingSlippageProtection` PoC, where the victim ends up receiving `0` of one token instead of the expected balanced amount.
