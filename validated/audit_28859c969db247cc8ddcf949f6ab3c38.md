This confirms the architecture: `is_first_time_committing_address` calls `Evm::account_exists`, which is a plain `StateMap::get` read [1](#0-0) . This read goes through the same `WorkingSet` abstraction used for every other state access, and reads/writes are captured via `ReadWriteLog`/`Witness` through `StateCheckpoint::freeze` regardless of native or ZK execution [2](#0-1) .

Both native block building and the batch-prover/circuit replay call the exact same shared function `execute_multiple_tx` (`crates/evm/src/evm/executor.rs`), which processes transactions strictly in the sequencer-supplied order, calling `evm.transact(tx)` then `evm.commit(result_and_state.state)` before moving to the next transaction [3](#0-2) . `EvmDb::commit` (`crates/evm/src/evm/db_commit.rs`) writes into the same shared `WorkingSet` that `is_first_time_committing_address` reads from for the *next* transaction, so tx2's read of `account_exists(A)` is guaranteed to see tx1's just-committed `account_idxs` write, deterministically, in both native and ZK execution, because it is the same code, not two independent implementations.

### Title
No vulnerability found - divergence claim is unsupported by the shared execution path

### Summary
The scenario alleges that native fee calculation and ZK circuit replay could diverge on `is_first_time_committing_address` across two transactions in one block touching the same address. Tracing the code shows this is factually incorrect: native block building and the batch circuit's guest replay execute the *identical* `execute_multiple_tx` function, `EvmDb::commit`, and `AccountExistsProvider::is_first_time_committing_address` implementations against the same `WorkingSet`/`ReadWriteLog` abstraction, so there is no separate "native path" vs. "circuit path" that could disagree.

### Finding Description
The claimed binding is: `TxInfo::l1_diff_size` computed natively for tx2 == `TxInfo::l1_diff_size` computed for tx2 inside the guest replay of the same L2 block.

Tracing the code: `calc_diff_size` (`crates/evm/src/evm/handler.rs:622-786`) calls `context.db().is_first_time_committing_address(&addr)` for each touched address [4](#0-3) . This delegates to `EvmDb::is_first_time_committing_address`, which calls `Evm::account_exists`, i.e. `self.account_idxs.get(address, working_set).is_some()` [1](#0-0) . This is an ordinary `StateMap` read that goes through the `WorkingSet`/`StateCheckpoint` cache-log machinery identically whether the storage backend is `ProverStorage` (native) or `ZkStorage` (guest), as documented in the sov-state README [5](#0-4) .

Crucially, transactions within a block are executed one-by-one through `execute_multiple_tx`, which calls `evm.transact(tx)` (running the handler, including `calc_diff_size`) and then `evm.commit(result_and_state.state)` before processing the next transaction [3](#0-2) . `EvmDb::commit` writes new accounts into `account_idxs` via `self.evm.account_set(...)` [6](#0-5) , mutating the shared `WorkingSet` in place. Since tx2's `calc_diff_size` call reads from that same, now-mutated `WorkingSet`, it correctly sees address A as already existing (`is_first_time_committing_address(A) == false`) — this happens deterministically because it is a straight-line sequential read/write dependency, not a race.

This exact function (`execute_multiple_tx`) is invoked from `apply_l2_block_txs`, which is called by `StfBlueprint::apply_l2_block` both when the sequencer/full node builds/replays a block natively and when the batch-prover's guest circuit replays it via `apply_l2_blocks_from_sequencer_commitments` (`crates/sovereign-sdk/module-system/sov-modules-stf-blueprint/src/lib.rs:409-460`, `:464-697`) [7](#0-6) . There is no alternate/duplicated implementation of `calc_diff_size` or `is_first_time_committing_address` for the ZK path — it is the same shared crate code compiled for both native and zkvm targets. The witness (`Witness`/`ReadWriteLog`) generated during native execution simply records the ordered sequence of reads and writes exactly as they occurred during that single deterministic run, including the intermediate tx1-commit-then-tx2-read boundary, and the guest replays the same code against that recorded log with JMT proof verification [8](#0-7) . There is no place where the "boundary" could be lost, because it is inherent to the sequential nature of the shared function, not an out-of-band signal that needs to be separately pinned.

The premise that the witness "does not pin the intermediate per-tx committed state boundary" is factually wrong: the ordered reads/writes list in `ReadWriteLog` inherently encodes this ordering, and it is this same list that is both recorded and replayed.

```markdown
### `Native` & `Zkp` execution:

During `Native` execution, the data is stored in a `key-value` store, which is accessed through the `WorkingSet`. It's worth mentioning that the actual storage mechanism, such as `RocksDB`, is only accessible during this phase when the full node executes the transaction and updates the state.
```

```markdown
### Witness Structure
A witness contains storage key-value pairs and their corresponding JellyFish Merkle Tree (JMT) proofs. On the native side, the system reads from storage (RocksDB) and generates JMT proofs for key-value pairs, collecting them into the witness. In the ZK environment, this witness serves as the storage layer.

In addition to key-value proofs, **JMT update proofs** are used to compute the new JMT root after each state transition. These update proofs show that the set of reads and writes performed during block execution result in the claimed new root, ensuring the integrity of the state transition.

### Cache Optimization
The circuit maintains cumulative state and offchain logs to optimize witness usage:
* If a storage key is accessed in a previous block within the same circuit run, the system reuses the existing proof
* Changes to storage keys are tracked in the cache to avoid regenerating merkle proofs
* Cache pruning occurs at predetermined heights to prevent memory issues

### Witness Verification
In the ZK environment, whenever a storage key-value is read from the witness:
* The corresponding JMT proof is also read and verified
* JMT update proofs are used to verify that the state transition's initial root matches the final JMT state root
```
