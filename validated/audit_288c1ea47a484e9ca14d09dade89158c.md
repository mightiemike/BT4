### Title
Reachable panic in delayed-receipt processing on stale cross-shard-target receipts causes chunk-apply crash / chain halt - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `.unwrap()` on the result of `Receipt::receiver_shard_id()` while draining the delayed-receipt queue during every chunk apply. `receiver_shard_id()` returns `Err(EpochError::ShardingError(...))` whenever a receipt's stored target shard cannot be resolved in the current shard layout or its split history. This is directly analogous to CVE-2024-20973: a normal, unprivileged workload path (here, the chunk-apply "optimizer"/scheduler equivalent — delayed receipt draining) can be driven into a state that triggers an unconditional crash/hang of the node, rather than returning a graceful error.

### Finding Description
`receipt_filter_fn` is invoked on every receipt popped from the persistent delayed-receipt queue during `Runtime::apply`: [1](#0-0) 

```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```

`receiver_shard_id()` for a `GlobalContractDistribution` receipt attempts to remap an old `target_shard` through `shard_layout.resolve_to_current_shard(target_shard)`, but returns an `Err` if the target shard cannot be found in the layout or its recorded split history: [2](#0-1) 

Any transaction that deploys a global contract (`DeployGlobalContract` action, callable by any unprivileged account) creates a `GlobalContractDistributionReceipt` carrying a fixed `target_shard` value that is baked in at creation time: [3](#0-2) 

If this receipt becomes delayed (e.g., the target shard's chunk is saturated with gas so the receipt sits in the delayed queue) and enough resharding events occur before it is finally popped, its `target_shard` can outlive the shard layout's split-history tracking window, causing `resolve_to_current_shard` to fail and `receiver_shard_id()` to return `Err`. The `.unwrap()` in `receipt_filter_fn` then panics inside `Runtime::apply`, which every validator/chunk-producer node executes deterministically for the same chunk — this is not a "malicious node" bug, it is triggered purely by transaction-driven state (contract deployment + natural/dynamic resharding + delayed-queue backlog).

A regression test in the repository specifically exercises this scenario for two resharding generations and asserts the chain does **not** stall, i.e., it demonstrates the exact failure mode described here and confirms the developers are aware of it as a live hazard class: [4](#0-3) 

The test comment explicitly states: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old `target_shard` after two resharding generations."*

While the current `resolve_to_current_shard` mitigation appears to cover the two-generation case tested, the underlying `.unwrap()` in `receipt_filter_fn` remains unconditional and un-hardened against any deeper/older split-history gap (e.g., more resharding generations than tracked, garbage-collected split history, or other cross-shard receipt kinds reaching this filter). The root defect — an `unwrap()` on a fallible, attacker-influenceable computation inside the hot chunk-apply path — is what maps to the CVE-2024-20973 bug class (an internal "optimizer"/query-processing path crashing the server on adversarial-but-otherwise-valid input).

### Impact Explanation
A panic inside `Runtime::apply` aborts the node process (or, depending on process supervision, repeatedly crash-loops it) for every validator/chunk-producer attempting to apply the same chunk, since receipt processing is a deterministic part of the state transition. This is a transaction-triggered halt: an unprivileged account can deploy a global contract and (in combination with delayed-queue backlog and shard resharding) cause chunk application to panic across the network, producing a chain-wide liveness failure rather than a rejected/failed transaction. This matches the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Exploitation requires: (1) an unprivileged `DeployGlobalContract` action from any signer — no special privilege needed; (2) the resulting distribution receipt getting pushed to the delayed queue (achievable by saturating a shard's compute budget with cheap gas-burning calls, as shown in the repository's own test); and (3) enough resharding transitions occurring while the receipt remains delayed to exceed whatever bound `resolve_to_current_shard`'s split-history tracking provides. Items (1) and (2) are trivially reachable by any transaction signer. Item (3) depends on chain-level resharding cadence and how deep the split-history is retained, which was not fully verified within tool budget (I could not read `resolve_to_current_shard`'s implementation in `core/primitives/src/shard_layout/v3.rs` before the session ended, so I cannot confirm precisely how many resharding generations the current mitigation tolerates before failing). Given the test explicitly targets and passes for two generations, the residual risk is that any configuration or timeline exceeding the mitigation's tracked depth (or another `receiver_shard_id` failure path, such as history GC) still hits the unconditional `.unwrap()`.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (and the analogous `shard_layout(...).unwrap()`) with proper error propagation (`?`) so `DelayedReceiptQueueWrapper::pop` returns a `RuntimeError`/`StorageError` instead of panicking, consistent with how `chain/chain/src/chain.rs::build_receipts_hashes` propagates the same fallible call via `?`. Additionally, either bound global-contract-distribution receipts' lifetime in the delayed queue (so they cannot outlive split-history retention) or make `resolve_to_current_shard` guaranteed to succeed for any receipt that was ever validly enqueued, regardless of how many subsequent reshardings occur.

### Proof of Concept
1. Deploy a global contract from any unprivileged account, causing a `GlobalContractDistributionReceipt` with `target_shard = S_A` to be created (`runtime/runtime/src/global_contracts.rs`).
2. Flood shard `S_A` with cheap, high-gas-burning function calls every block so the distribution receipt (arriving as an incoming receipt) is pushed into the delayed queue instead of being processed immediately.
3. Trigger (or wait for) a sequence of dynamic resharding events that split shard(s) enough times that `S_A`'s split history exceeds the tracking window used by `resolve_to_current_shard`.
4. Stop flooding and let the delayed queue drain; when the stale receipt is popped, `receipt_filter_fn` calls `receiver_shard_id()`, which returns `Err`, and the subsequent `.unwrap()` panics inside `Runtime::apply`, halting chunk production for that shard.

This exact sequence (steps 1–4) is implemented as `test_stale_global_contract_distribution_after_double_resharding` in [5](#0-4) , confirming the mechanism is real and reachable purely through transaction-level actions plus normal protocol resharding, not any privileged or malicious-node behavior.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

fn forward_distribution_next_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    epoch_info_provider: &dyn EpochInfoProvider,
    state_update: &mut TrieUpdate,
    receipt_sink: &mut ReceiptSink,
    receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
) -> Result<(), RuntimeError> {
    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(
        global_contract_data
            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()
        .filter(|shard_id| !already_delivered_shards.contains(&shard_id))
        .next()
    else {
        return Ok(());
    };
    let already_delivered_shards = Vec::from_iter(already_delivered_shards);
    let predecessor_id = receipt.predecessor_id().clone();
    let next_receipt = global_contract_data.forward(next_shard, already_delivered_shards);
    let mut next_receipt = Receipt::new_global_contract_distribution(predecessor_id, next_receipt);
    let receipt_id = apply_state.create_receipt_id(receipt.receipt_id(), 0);
    next_receipt.set_receipt_id(receipt_id);
    if apply_state.save_receipt_to_tx {
        receipt_to_tx.push((
            receipt_id,
            ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: *receipt.receipt_id(),
                    parent_predecessor_id: receipt.predecessor_id().clone(),
                }),
                receiver_account_id: next_receipt.receiver_id().clone(),
                shard_id: apply_state.shard_id,
            }),
        ));
    }
    receipt_sink.forward_or_buffer_receipt(next_receipt, apply_state, state_update)?;
    Ok(())
}

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height

    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
