### Title
Exchange liquidity operations (`ExchangeInjectContract` / `ExchangeWithdrawContract`) lack slippage/minimum-received protection, unlike `ExchangeTransactionContract` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The Bancor-style AMM exchange pool implementation in java-tron protects trades (`ExchangeTransactionContract`) with a user-supplied `expected` minimum-output field, but the pool's own liquidity add/remove operations — `ExchangeInjectContract` and `ExchangeWithdrawContract` — carry no equivalent min/max bound on the counter-token amount computed at execution time. This is the exact bug class from the external report: an AMM-style operation whose settlement ratio is determined by pool state at inclusion time, with no slippage control to guard against pool-state changes between submission and execution.

### Finding Description
`ExchangeTransactionContract` includes an `expected` field that the actuator enforces (`anotherTokenQuant < tokenExpected` reverts): [1](#0-0) 

In contrast, `ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant` — no expected/min-output field: [2](#0-1) 

and `ExchangeWithdrawContract` is identical in this respect: [3](#0-2) 

`ExchangeInjectActuator.doValidate` computes the counter-token amount (`anotherTokenQuant`) purely from the exchange's current on-chain balances at validation/execution time, with no comparison against any caller-supplied bound: [4](#0-3) 

The same pattern repeats in `ExchangeInjectActuator.execute`, where `anotherTokenQuant` is derived from `firstTokenBalance`/`secondTokenBalance` at execution time and directly debited/credited without any check against caller expectations: [5](#0-4) 

`ExchangeWithdrawActuator` behaves the same way: it derives `anotherTokenQuant` from current pool balances and only performs a rounding/"precision" sanity check (`"Not precise enough"`), not a user-specified minimum-received guard: [6](#0-5) 

Because `ExchangeTransactionContract` (a trade) is callable by any account and directly mutates `firstTokenBalance`/`secondTokenBalance` of the same pool via `exchangeCapsule.transaction(...)`: [7](#0-6) 

any unprivileged account can shift the pool ratio between the moment the exchange creator constructs/signs an `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction and the moment it is actually included/executed in a block, since java-tron transactions sit in the pending pool for some time before packing. The creator's inject/withdraw settles at whatever ratio exists at inclusion time, with no client-side lower/upper bound enforced on-chain.

### Impact Explanation
An attacker can front-run a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction with one or more `ExchangeTransactionContract` trades to skew `firstTokenBalance`/`secondTokenBalance`, causing:
- On inject: the creator deposits token A at a manipulated ratio and receives an unfavorable amount of LP-equivalent state (token balances), effectively donating value to the attacker who can trade back afterward (classic sandwich).
- On withdraw: the creator receives less of the counter token than expected for the amount they withdraw.

This causes direct accounting/value loss for the exchange creator without any code path to abort the transaction based on their own risk tolerance, unlike the trade path which already has this protection.

### Likelihood Explanation
Any account can broadcast `ExchangeTransactionContract` transactions (no privilege required) and observe pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions in the mempool to time a sandwich. The only actor constraint is that inject/withdraw must be sent by the exchange's creator account, but the attacker triggering the front-run/back-run trades needs no special privilege — this fits the "broadcast transaction" unprivileged threat model.

### Recommendation
Add an `expected`/min-max field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and enforce it in `ExchangeInjectActuator.doValidate`/`ExchangeWithdrawActuator.doValidate` by rejecting the transaction if the computed `anotherTokenQuant` falls below (inject) or above (withdraw) the caller-specified bound.

### Proof of Concept
1. Exchange creator constructs an `ExchangeInjectContract` to inject `tokenQuant` of `firstTokenID`, expecting to also lock in `anotherTokenQuant` of `secondTokenID` computed from the pool ratio observed at construction time (e.g. balances 100:200).
2. Before this transaction is packed into a block, an attacker broadcasts an `ExchangeTransactionContract` trade that shifts the pool ratio significantly (e.g., large sell of `secondTokenID` into the pool).
3. When the creator's `ExchangeInjectContract` is finally executed, `ExchangeInjectActuator.execute` recomputes `anotherTokenQuant` from the new, attacker-skewed balances and debits the creator that new (unfavorable) amount — with no on-chain check comparing it to what the creator originally expected.
4. The attacker then reverses their trade, extracting the value the creator lost due to the ratio shift, analogous to a Uniswap V2 sandwich attack on `addLiquidity`/`removeLiquidity` without `amountAMin`/`amountBMin`.
