### Title
`TransactionOutput::ensure_match_transaction_info` skips state/hot-state/position checkpoint hash comparison, letting replay-verify accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function `db-tool`'s `replay-verify` (`storage/db-tool/src/replay_on_archive.rs`) uses to confirm that locally re-executed transactions match the authenticated `TransactionInfo` recorded in a trusted backup/ledger. It only compares status, gas used, write-set hash, and event root hash — it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, which are exactly the fields that bind a committed transaction to the correct Jellyfish-Merkle/state root. This is called out by the function's own comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates a re-executed `TransactionOutput` against a `TransactionInfo` pulled from storage/backup by checking:
- `status` [2](#0-1) 
- `gas_used` [3](#0-2) 
- `write_set_hash` vs `txn_info.state_change_hash()` [4](#0-3) 
- `event_root_hash` vs `txn_info.event_root_hash()` [5](#0-4) 

It explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, and the code says so directly: [6](#0-5) 

These checkpoint hashes are the roots of the Jellyfish Merkle Tree / hot-state tree / position tree that summarize the *entire world state* at that version — they are what light clients, state-sync, and downstream proof verification ultimately trust as "the state." Verifying only the write-set hash and event root is not sufficient to prove the resulting global state tree is correct: the write-set hash is a hash of *this transaction's own write ops*, not of the resulting merged/committed state, and it says nothing about whether the state tree constructed from many such write-sets (including the effect of state slot metadata, resource-group packing, aggregator/delayed-field resolution, hot-state promotion, or the newer "position" state tree) ends up with the same root as the authenticated ledger.

This function is directly used, with `expected_write_set`/`expected_events` non-`None`, by the `replay-verify` tool's core verification loop: [7](#0-6) 

`replay-verify` is exactly the tool operators and auditors run to detect whether a full re-execution over history reproduces the authenticated on-chain ledger (used, e.g., before/after protocol changes, or to validate a new client/VM against mainnet history). Because it silently omits checkpoint-hash comparison, a class of divergence — where the write-set contents and events match but the resulting state tree root (state, hot-state, or position tree) does not — passes verification undetected.

The gap is also present anywhere else `ensure_match_transaction_info` is used for confidence checks, e.g. the CLI's txn replay/inspection commands [8](#0-7) .

### Impact Explanation
This breaks the "authenticated response/replay must stay bound to the correct state root" invariant called out in the scope: replay/verify tooling can report a clean replay while the locally-computed state root (state checkpoint hash, hot-state checkpoint hash, or the newer position-state checkpoint hash) silently diverges from the value actually committed and signed into the chain's `TransactionInfo`/accumulator. This is a genuine state-commitment integrity gap in the verification tool itself: a bug in JMT construction, resource-group size accounting, aggregator/delayed-field materialization, hot-state promotion policy, or the position-state feature (all of which affect the state root but not necessarily the write-set hash of an individual transaction, since divergence can also come from *aggregation* across many write-sets or from `add_hotness`-style state that isn't part of the write set) would not be flagged by `replay-verify`, giving false confidence that historical replay reproduces the authenticated ledger. This directly matches the in-scope impact "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Wrong accumulator root... accepted as valid," since the state-checkpoint hash is exactly the field bound into `TransactionInfo` and hashed into the transaction accumulator that ledger infos ultimately certify.

### Likelihood Explanation
The comment in the code confirms the maintainers are aware of this gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating it is a known, currently-live limitation rather than a hypothetical. It requires no privileged access or malicious peer behavior to trigger — it's a property of the verification tool's logic itself and applies to any unprivileged operator running `replay-verify` against any range of transactions where a state-root-affecting bug exists upstream. Because it is baked into the shared `TransactionOutput` API in `types/src/transaction/mod.rs`, every caller (`db-tool replay-verify`, `aptos-debugger`, CLI commands) inherits the same blind spot.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally re-computed `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the corresponding fields on `txn_info`, using the same checkpoint-hash computation used in `execution/executor/src/workflow/do_ledger_update.rs::assemble_transaction_infos` [9](#0-8) . Since `TransactionOutput` alone doesn't carry the checkpoint hash (it's computed post-hoc, batched across a chunk, from the resulting state tree), the caller (`replay_on_archive.rs`) needs to be updated to also drive a full state-tree build across the replayed chunk and compare its checkpoint hash(es) to `expected_txn_infos`, not just an isolated per-transaction write-set/event check. This should be resolved (or the flag `COMPUTE_TRADING_NATIVE_STATE_ROOTS` gated appropriately) before treating replay-verify as authoritative proof of state-root parity.

### Proof of Concept
1. Introduce (or have) a bug that affects state-tree construction across a batch of write sets without changing any individual transaction's write-set bytes/hash — e.g., an issue in resource-group serialization ordering feeding the JMT, in hot-state promotion selection, or in the position-state tree (`Position` feature) that changes which keys are written to the tree vs. left in a side-channel.
2. Run `db-tool replay-verify` (`storage/db-tool/src/replay_on_archive.rs`) over a version range covering the affected transactions.
3. Observe that `execute_and_verify` calls `ensure_match_transaction_info` with `Some(&expected_writesets[idx])`/`Some(&expected_events[idx])` [10](#0-9) , which only checks status/gas/write-set-hash/event-root, and returns `Ok(())` even though `state_checkpoint_hash` (or hot-state/position checkpoint hash) on `expected_txn_infos[idx]` would not match the state root actually produced by local replay — because that comparison is never performed [11](#0-10) .
4. `replay-verify` reports success despite the local state root diverging from the authenticated chain state — a false-positive state-commitment integrity check.

**Note on limitations:** I was not able to fully trace how/where checkpoint hashes would need to be reconstructed on the `db-tool` side to add the missing comparison (this requires visibility into how `replay_on_archive.rs` would need to build a state tree across chunks, which is not present in the current tool and would be new functionality), nor could I find a concrete historical bug that actually produces such a divergence today — this finding documents a **verification-gap** (proof/authenticated-response binding weakness) that is explicitly acknowledged in the source rather than a demonstrated live state divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn assemble_transaction_infos(
        to_commit: &TransactionsWithOutput,
        transaction_info_v1: bool,
        state_checkpoint_hashes: &[Option<HashValue>],
        hot_state_checkpoint_hashes: Option<&[Option<HashValue>]>,
        position_state_checkpoint_hashes: Option<&[Option<HashValue>]>,
    ) -> (Vec<TransactionInfo>, Vec<HashValue>) {
        let _timer = OTHER_TIMERS.timer_with(&["assemble_transaction_infos"]);

        (0..to_commit.len())
            .into_par_iter()
            .with_min_len(optimal_min_len(to_commit.len(), 64))
            .map(|i| {
                let txn = &to_commit.transactions[i];
                let txn_output = &to_commit.transaction_outputs[i];
                let persisted_auxiliary_info = &to_commit.persisted_auxiliary_infos[i];
                // Use the auxiliary info hash directly from the persisted info
                let auxiliary_info_hash = match persisted_auxiliary_info {
                    PersistedAuxiliaryInfo::None => None,
                    PersistedAuxiliaryInfo::V1 { .. } => {
                        Some(CryptoHash::hash(persisted_auxiliary_info))
                    },
                    PersistedAuxiliaryInfo::TimestampNotYetAssignedV1 { .. } => None,
                };
                let state_checkpoint_hash = state_checkpoint_hashes[i];
                let event_hashes = txn_output
                    .events()
                    .iter()
                    .map(CryptoHash::hash)
                    .collect::<Vec<_>>();
                let event_root_hash =
                    InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash();
                let write_set_hash = CryptoHash::hash(txn_output.write_set());
                let status = txn_output
                    .status()
                    .as_kept_status()
                    .expect("Already sorted.");
                let txn_info = if transaction_info_v1 {
                    TransactionInfo::builder_v1()
                        .transaction_hash(txn.committed_hash())
                        .state_change_hash(write_set_hash)
                        .event_root_hash(event_root_hash)
                        .maybe_state_checkpoint_hash(state_checkpoint_hash)
                        .maybe_hot_state_checkpoint_hash(
                            hot_state_checkpoint_hashes.and_then(|hot| hot[i]),
                        )
                        .gas_used(txn_output.gas_used())
                        .status(status)
                        .maybe_auxiliary_info_hash(auxiliary_info_hash)
                        .maybe_position_state_checkpoint_hash(
                            position_state_checkpoint_hashes.and_then(|p| p[i]),
                        )
                        .build()
                } else {
                    TransactionInfo::builder_v0()
                        .transaction_hash(txn.committed_hash())
                        .state_change_hash(write_set_hash)
                        .event_root_hash(event_root_hash)
                        .maybe_state_checkpoint_hash(state_checkpoint_hash)
                        .gas_used(txn_output.gas_used())
                        .status(status)
                        .maybe_auxiliary_info_hash(auxiliary_info_hash)
                        .build()
                };
                let txn_info_hash = txn_info.hash();
                (txn_info, txn_info_hash)
            })
            .unzip()
    }
