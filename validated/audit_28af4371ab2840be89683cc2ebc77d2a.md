### Title
Unbounded reward index (`Vi`) accumulation with unchecked `BigInteger.longValue()` narrowing causes silent overflow / permanent corruption of vote reward accounting - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`, `chainbase/src/main/java/org/tron/core/service/RewardViCalService.java`, `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
The external report describes an Aave-style reward index that can hit `type(uint104).max` when the accrual denominator (asset total supply) is dust, permanently blocking further reward updates (revert-based DoS). java-tron's DPoS vote-reward mechanism uses an analogous per-witness "value index" (`Vi`), scaled by `DECIMAL_OF_VI_REWARD = 10^18`, that is incremented every cycle as `reward * 10^18 / voteCount`. Unlike the Solidity index, `Vi` is stored as an unbounded `BigInteger` byte array, so the *index itself* cannot overflow a fixed-width field like `uint104`. However, every consumer of `Vi` (`MortgageService.computeReward`, `VoteRewardUtil.computeReward`, `RewardViCalService.getNewRewardAlgorithmReward`) narrows the final `BigInteger` result back to `long` via the unchecked `.longValue()` call, with no `longValueExact()`/overflow guard — in contrast to the hardened `longValueExact()` overflow checks the codebase already added for energy/bandwidth global-limit math (`EnergyProcessor`, `RepositoryImpl`, `ResourceProcessor`). If any witness accumulates a `Vi` growth rate that is large relative to its vote count (i.e., "dust" `voteCount` denominator relative to reward numerator, exactly the same imbalance the report calls out), the accumulated per-vote reward eventually exceeds `Long.MAX_VALUE` when multiplied back by a voter's `userVote` and this silently wraps instead of reverting.

### Finding Description
The reward index is computed and stored per witness per cycle: [1](#0-0) [2](#0-1) 

The same accrual logic exists in the standalone service used for historical Vi backfill: [3](#0-2) 

`preVi` and the stored `Vi` values are `BigInteger`s serialized via `value.toByteArray()` — an unbounded-width byte array, so unlike the Solidity `uint104` there is no fixed-width overflow at the storage layer: [4](#0-3) 

The vulnerability surfaces when this unbounded `Vi` is consumed to compute a *user's* claimable reward. All three consumers narrow the multiplied/divided `BigInteger` result to `long` using the non-throwing `longValue()`: [5](#0-4) [6](#0-5) [7](#0-6) 

`BigInteger.longValue()` performs a narrowing conversion that silently returns the low-order 64 bits (potentially producing a wrapped, arbitrary, or negative result) rather than throwing, when the underlying `BigInteger` exceeds the `long` range — this is exactly the class of "index-can-grow-unboundedly-and-eventually-breaks-a-fixed-width-consumer" bug described in the report, except manifesting as silent numeric corruption in java-tron instead of an explicit `revert`.

The root-cause condition mirrors the report precisely: `Vi` accrual per cycle is `reward * 10^18 / voteCount` — if `voteCount` (the denominator, analogous to `totalBalance`/`totalSupply` in the report) is small relative to the flat per-block `reward` a witness receives (`payBlockReward`/`payTransactionFeeReward` pay a fixed amount per produced block, independent of vote count, unlike the standby-witness path which is vote-proportional): [8](#0-7) 

then each cycle's `deltaVi` increment is disproportionately large, and after many cycles the accumulated `Vi` for that witness grows without the bound the codebase's own hardening work assumes elsewhere. Notably, the project already recognized this exact overflow class and added explicit `longValueExact()`/`ArithmeticException` hardening to the resource (energy/bandwidth) global-limit math paths, but the vote-reward `Vi` consumers were not similarly hardened: [9](#0-8) 

### Impact Explanation
If a witness's `Vi` growth becomes disproportionate to its vote weight (small `voteCount` denominator vs. large flat block-reward numerator, over enough cycles), any voter's reward query/withdrawal for that witness (`MortgageService.queryReward`/`withdrawReward`, `VoteRewardUtil.queryReward`/`withdrawReward` used by TVM `vote`-precompile contracts, and `RewardViCalService.getNewRewardAlgorithmReward` used during the one-time historical Vi backfill) computes `deltaVi.multiply(userVote).divide(DECIMAL_OF_VI_REWARD).longValue()`. Once the intermediate `BigInteger` exceeds `Long.MAX_VALUE`, this silently wraps to an incorrect (potentially negative) value that is then added to the account's on-chain `allowance` balance via `adjustAllowance`. This is on-chain asset/accounting corruption: a user's claimable TRX allowance can be corrupted (inflated or driven negative/wrong) for every voter of the affected witness, and because the corrupted `Vi` is persisted permanently in `DelegationStore`/`RewardViStore`, the corruption is not a one-off but poisons every future reward computation for that witness — functionally the same "cannot recover, breaks indefinitely" outcome the report describes for the aToken index, just realized as silent accounting drift/DoS of correct reward accounting rather than a revert.

### Likelihood Explanation
Reaching this condition requires a witness with disproportionately high flat block-reward income relative to its vote weight sustained over many cycles — the same kind of edge-case precondition the original report itself concedes ("may need some stars to align"). It is most plausible on low-stake test/private networks or in a scenario where a marginal top-27 witness has just enough votes to be elected while producing many blocks over an extended period, or via long-running accumulation during the historical `RewardViCalService` backfill computation. It is not trivially triggerable by an anonymous single transaction, but it is reachable purely through normal DPoS operation (no privileged actor, no key leak, no P2P/node compromise needed) and the lack of any exact-overflow check (unlike the parallel resource-accounting code that was hardened) means the codebase has no defense-in-depth against it once triggered.

### Recommendation
- Replace `.longValue()` with `.longValueExact()` (or an explicit range check with a fallback/clamping strategy) in `MortgageService.computeReward`, `VoteRewardUtil.computeReward`, and `RewardViCalService.getNewRewardAlgorithmReward`, mirroring the hardening already applied in `EnergyProcessor`/`RepositoryImpl`/`ResourceProcessor` for energy/bandwidth global-limit math.
- Consider bounding/monitoring `Vi` growth rate per cycle so that witnesses with disproportionate reward-to-vote ratios cannot silently produce unbounded index growth, and add alerting/rejection rather than silent truncation if an overflow condition is detected during reward computation or the one-time Vi backfill in `RewardViCalService`.

### Proof of Concept
Deterministic PoC is not fully constructable from the indexed codebase alone (the exact vote-election thresholds and multi-cycle accumulation required to force `Vi * userVote / 10^18` past `Long.MAX_VALUE` need live chain parameters and many cycles of block production). Conceptually:
1. Get a witness elected into the top-27 (or long-lived standby set) with the minimum vote count needed to retain that slot.
2. Let it produce blocks/collect transaction fees over many maintenance cycles via `MortgageService.payBlockReward`/`payTransactionFeeReward`, which credit `delegationStore.addReward` independent of vote count.
3. Each cycle, `DelegationStore.accumulateWitnessVi`/`RewardViCalService.accumulateWitnessVi` computes `deltaVi = reward * 10^18 / voteCount`, growing `Vi` proportionally faster than vote weight would normally imply.
4. After sufficient cycles, any voter (including via the TVM vote precompile, `VoteRewardUtil.computeReward`) calling `queryReward`/`withdrawReward` triggers `deltaVi.multiply(userVote).divide(10^18).longValue()`, and once the multiplied `BigInteger` exceeds `Long.MAX_VALUE`, the returned `long` silently wraps, corrupting the resulting `allowance` credited to the account.

    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record

      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
