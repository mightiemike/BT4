### Title
Exchange liquidity actuators (`ExchangeInjectActuator` / `ExchangeWithdrawActuator`) compute settlement ratio with no slippage/minimum-output protection - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — unlike `ExchangeTransactionContract`, which additionally carries an `expected` field used as a minimum-output slippage guard [1](#0-0) . When an exchange creator submits `ExchangeInjectContract`/`ExchangeWithdrawContract`, the counter-token amount (`anotherTokenQuant`) is derived from the pool's *current* on-chain balances at validate/execute time, which can be moved by any unprivileged trader's intervening `ExchangeTransactionContract` before the inject/withdraw transaction lands. There is no way for the caller to bound the resulting `anotherTokenQuant`, exactly the missing-slippage-control pattern described in the Ajna M-1 report for `addQuoteToken()`.

### Finding Description
`ExchangeTransactionActuator` (the trade/swap path) is properly protected: the caller supplies `expected`, and `doValidate()` reverts if the computed output is below it: [2](#0-1) 

By contrast, `ExchangeInjectActuator.doValidate()` and `execute()` compute `anotherTokenQuant` purely from the live `firstTokenBalance`/`secondTokenBalance` stored in `ExchangeCapsule` at the moment each phase runs, with no caller-supplied bound: [3](#0-2) 
The only checks are that the ratio-derived amount is positive and the account has sufficient balance: [4](#0-3) 

Similarly, `ExchangeWithdrawActuator.doValidate()` recomputes `anotherTokenQuant` from the current pool ratio and only performs an internal rounding-precision sanity check ("Not precise enough") against its own recomputation — not against any user-specified minimum/maximum: [5](#0-4) 

Both `execute()` methods re-read the `ExchangeCapsule` from the store and recompute `anotherTokenQuant` again from balances at execution time: [6](#0-5) [7](#0-6) 

Any account can call `ExchangeTransactionActuator` (unprivileged trade) against the same `exchange_id`, and that trade directly mutates `firstTokenBalance`/`secondTokenBalance` via `Commons.putExchangeCapsule(...)` inside `ExchangeTransactionActuator.execute()` [8](#0-7) . If one or more such trades are packed into blocks before the creator's pending `ExchangeInjectContract`/`ExchangeWithdrawContract` executes (whether due to normal mempool ordering, block producer reordering, or deliberate front-running), the pool ratio the creator actually settles at can differ materially from the ratio observed when they built/signed the transaction — with no field available to cap that deviation, exactly mirroring the Ajna `addQuoteToken()` root cause (deposit fee/LUP determined by storage state at execution time, not submission time, with no slippage bound).

### Impact Explanation
This affects exchange-pool creators (an ordinary, unprivileged role obtained simply by calling `ExchangeCreateActuator` — anyone can create a pool) rather than any chain-privileged actor. A creator injecting liquidity can be forced to deposit a counter-token amount far outside their intended ratio; a creator withdrawing liquidity can receive far less counter-token than expected, or be forced to give up more of the paired token than intended, if the ratio shifts (e.g., due to a large intervening trade) between transaction construction and on-chain execution. Because the pool balances directly determine the settlement amount and there is no bound field in either contract, the accounting result is a real, unbounded (bounded only by pool size limits and account balance) financial loss to the creator — an accounting/settlement impact analogous to the accepted Sherlock medium-severity Ajna finding.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an active exchange pool with liquidity, and (b) a trade transaction (`ExchangeTransactionContract`, callable by any account) landing between the time the creator signs an inject/withdraw transaction and the time it executes. Given java-tron's public mempool and block-producer transaction ordering, this is achievable without any special privilege — a bot can simply watch for pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions and front-run them with a trade that shifts the ratio unfavorably for the creator, or ordinary market activity can incidentally move the ratio. No abnormal chain state or trusted role is required.

### Recommendation
Add a caller-specified bound to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring the `expected` field already used in `ExchangeTransactionContract`), e.g., a minimum/maximum acceptable `anotherTokenQuant`, and revert in `doValidate()`/`execute()` when the pool-state-derived value falls outside that bound — the same style of fix applied upstream for Ajna's `addQuoteToken()`/`moveQuoteToken()`.

### Proof of Concept
1. Account A creates an exchange pool for TokenX/TRX via `ExchangeCreateActuator` and becomes its `creatorAddress`.
2. Account A constructs and signs an `ExchangeInjectContract` intending to inject `tokenQuant` of TokenX at the current ratio (expecting `anotherTokenQuant` TRX to be pulled proportionally), per `ExchangeInjectActuator.execute()`/`doValidate()` logic [9](#0-8) .
3. Before A's transaction is included, attacker B submits an `ExchangeTransactionContract` trade against the same `exchange_id` that shifts `firstTokenBalance`/`secondTokenBalance` significantly, using `ExchangeTransactionActuator.execute()` [10](#0-9) .
4. B's trade lands first in the block; A's `ExchangeInjectContract` then executes against the new, shifted balances, recomputing `anotherTokenQuant` from the post-trade ratio [11](#0-10) .
5. Because `ExchangeInjectContract` has no `expected`/bound field, A's transaction succeeds and pulls a counter-token amount that diverges from what A intended when signing, with no on-chain mechanism to reject the unfavorable outcome (contrast with `ExchangeTransactionActuator`'s `anotherTokenQuant < tokenExpected` revert path [2](#0-1) ). The same scenario applies symmetrically to `ExchangeWithdrawActuator`.
