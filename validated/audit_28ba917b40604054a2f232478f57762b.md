### Title
Denial of Service via Panicking `HashMap` Index on Missing `EntryPointType` Key in Deprecated (Cairo 0) Entry Point Resolution - (File: `crates/blockifier/src/execution/deprecated_entry_point_execution.rs`)

### Summary
The Handlebars advisory describes a crash caused by looking up an unregistered decorator, getting `undefined`, and then unconditionally invoking it, causing an unhandled exception that kills the process. The `blockifier` crate has a structurally identical pattern: `resolve_entry_point_pc` performs an *unchecked* `HashMap` index lookup keyed by `EntryPointType`, which panics if the key is absent, instead of returning a `Result` as every other lookup in the surrounding code does.

### Finding Description
In `resolve_entry_point_pc`:
```rust
let entry_points_of_same_type = &compiled_class.entry_points_by_type[&call.entry_point_type];
``` [1](#0-0) 

`entry_points_by_type` is a plain `HashMap<EntryPointType, Vec<EntryPointV0>>` on `CompiledClassV0Inner`: [2](#0-1) 

This map is populated directly from the deprecated (Cairo 0) contract-class JSON supplied by the class declarer, with no guarantee that all three `EntryPointType` variants (`Constructor`, `External`, `L1Handler`) are present as keys — an omitted key (as opposed to an empty array) is a legal JSON shape: [3](#0-2) [4](#0-3) 

Unlike Rust's `HashMap::get`, indexing via `map[&key]` calls the `Index` trait implementation, which panics with `"no entry found for key"` if the key is missing — this is the direct analog of Handlebars calling `undefined` as a function: an unregistered/missing lookup key is dereferenced/used without a presence check. Contrast this with every other lookup in the same file and in the Cairo-1 path, all of which return `Result` and produce a clean error instead of panicking, e.g. `resolve_entry_point_pc`'s own fallback logic for missing selectors: [5](#0-4) 
and the Cairo-1 equivalent `EntryPointsByType::get_entry_point`, which safely returns `PreExecutionError::EntryPointNotFound` instead of indexing unchecked: [6](#0-5) 

If a Cairo 0 class is declared whose JSON entirely omits, say, the `L1_HANDLER` key (rather than providing `"L1_HANDLER": []`), then any subsequent attempt to execute that class with `entry_point_type == EntryPointType::L1Handler` (e.g. via an L1 handler message, or via `library_call`/`call_contract` targeting that type) reaches line 130 and panics instead of returning `PreExecutionError`.

### Impact Explanation
A panic inside `resolve_entry_point_pc`, invoked from `initialize_execution_context` during entry-point execution, is not a caught `Result` error — it is an unwinding panic. Depending on how the executing thread/task is supervised, this can crash or poison the sequencer's block-building/execution worker, which is directly reachable from a single submitted transaction or L1 message, potentially halting block production (a network unable to confirm new transactions), matching the "Medium/High" DoS class of the analog.

### Likelihood Explanation
Reaching this requires only declaring an ordinary Cairo 0 (deprecated) class with a malformed `entry_points_by_type` map (a key entirely omitted rather than empty), which is a purely syntactic malformation of otherwise-valid class JSON — no privileged access is needed, matching the "single-request" simplicity of the Handlebars bug. However, I could not fully verify within the available context whether declare-time validation (e.g. in `apollo_gateway::stateless_transaction_validator`) already rejects contract classes lacking one of the three required entry-point-type keys before they reach execution; if such validation exists and enforces all three keys unconditionally, the panic path becomes unreachable in production. This uncertainty should be resolved by inspecting `crates/apollo_gateway/src/stateless_transaction_validator.rs` and the declare-transaction JSON-schema validation before treating this as confirmed-exploitable.

### Recommendation
Replace the unchecked index with a safe lookup, e.g. `compiled_class.entry_points_by_type.get(&call.entry_point_type).unwrap_or(&Vec::new())`, and propagate `PreExecutionError::NoEntryPointOfTypeFound` (already defined and used elsewhere in the same function) for a missing key, mirroring the safe pattern already used in `EntryPointsByType::get_entry_point` for Cairo 1 classes. Additionally, verify/add declare-time validation that a submitted deprecated contract class's `entry_points_by_type` always contains all three `EntryPointType` keys (even if empty).

### Proof of Concept
Conceptual reproduction (pending confirmation that gateway validation does not already reject it):
1. Craft a Cairo 0 `ContractClass` JSON whose `entry_points_by_type` object omits the `"L1_HANDLER"` key entirely (only `"CONSTRUCTOR"` and `"EXTERNAL"` present).
2. Declare and deploy this class.
3. Send an L1 handler message (or otherwise trigger execution with `entry_point_type = EntryPointType::L1Handler`) targeting the deployed contract.
4. Execution reaches `resolve_entry_point_pc`, indexing `compiled_class.entry_points_by_type[&EntryPointType::L1Handler]` on a map lacking that key, causing an unhandled panic: [7](#0-6)

impl<EP: Clone + HasSelector> EntryPointsByType<EP> {
    pub fn get_entry_point(
        &self,
        entry_point: &EntryPointTypeAndSelector,
    ) -> Result<EP, PreExecutionError> {
        entry_point.verify_constructor()?;

        let entry_points_of_same_type = &self[entry_point.entry_point_type];
        let filtered_entry_points: Vec<_> = entry_points_of_same_type
            .iter()
            .filter(|ep| *ep.selector() == entry_point.entry_point_selector)
            .collect();

        match filtered_entry_points[..] {
            [] => Err(PreExecutionError::EntryPointNotFound(entry_point.entry_point_selector)),

            _ => Err(PreExecutionError::DuplicatedEntryPointSelector {
                selector: entry_point.entry_point_selector,
