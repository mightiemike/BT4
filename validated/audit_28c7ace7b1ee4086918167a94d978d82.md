### Title
Validator reward silently dropped (minted-but-undelivered tokens) when a validator account is deleted before its deferred reward is applied - (File: runtime/runtime/src/lib.rs)

### Summary
`RewardCalculator::calculate_reward` tallies every validator's per-epoch reward into `epoch_actual_reward`, which becomes `minted_amount` and unconditionally inflates `total_supply` two epochs later. The actual crediting of that reward happens in `Runtime::update_validator_accounts`, but that function only credits the reward if the validator's account still exists, and its "account missing" fallback check only validates `max_of_stakes`, not `reward` or `last_proposal`. A staker who fully unstakes and then deletes their account can cause their earned reward to be counted toward `total_supply` inflation while never being credited to any account — an accounting divergence directly analogous to the Caviar royalty bug (fee/amount tallied into a total, but the actual transfer to the recipient is conditioned on something that isn't guaranteed to hold).

### Finding Description
`RewardCalculator::calculate_reward` computes a `reward` for each validator and unconditionally folds it into `epoch_actual_reward`: [1](#0-0) 

`epoch_actual_reward` is returned as `minted_amount`, which is applied to `total_supply` at the start of the corresponding epoch (`new_total_supply = prev.total_supply + minted_amount − balance_burnt`), regardless of whether the reward is ever actually delivered to an account.

The actual delivery happens in `Runtime::update_validator_accounts`: [2](#0-1) 

Here, the code explicitly guards against the case where the account is *uninitialized* (still present in the trie but never received a real balance) — but that guard only fires when `account.is_some()` and `!is_initialized()`. It raises a `StorageInconsistentState` error if any of `max_of_stakes`, `reward`, or `last_proposal` is non-zero for such an account, per the comment "defense in depth, so that minted tokens do not leak from the supply if this path ever becomes reachable" (lines 1724-1729).

However, when the account has been **fully deleted** (`get_account` returns `None`), the code falls into:
```rust
} else if *max_of_stakes > Balance::ZERO {
    return Err(...)
}
```
This only checks `max_of_stakes`. It does **not** check `reward` or `last_proposal`. If a validator has already been fully unstaked (`max_of_stakes == 0`, because `return_stake` previously zeroed `locked`) and then deletes its account, but is still owed a non-zero `reward` for having validated during a prior epoch (rewards for epoch `T` are applied at the start of epoch `T+2` per the T+2 rule), the `else if` condition is `false`, no error is raised, and the reward is silently dropped — never credited to any account, with no compensating burn adjustment to `total_supply`.

Deleting an account with zero locked stake is a normal, unprivileged operation available once a validator's stake has been fully returned (`account_delete_account`, gated only by the "zero locked stake" requirement, not by pending, already-computed rewards).

### Impact Explanation
This produces a state-transition invariant violation identical in class to the reported Caviar issue: an amount (`reward`) is counted into a cumulative total (`epoch_actual_reward` → `minted_amount` → `total_supply`) but the corresponding value transfer to the intended recipient is conditioned on a fact (account still existing) that is not linked back to the total. The result is:
- `total_supply` is inflated by tokens that are never credited to any account — a genuine supply-accounting divergence (the sum of all account balances will be permanently less than the recorded `total_supply` by the dropped reward amount).
- The dropped reward is not burned, refunded, or redirected to the protocol treasury; it simply vanishes from the ledger's accounting while still being reflected in the recorded inflation figure.

This matches the accepted "supply inflation" / accounting-divergence impact category in scope for this analog search.

### Likelihood Explanation
Reachable via a fully unprivileged sequence of ordinary actions by any staker, requiring no malicious validator/node/operator behavior:
1. Submit a `Stake` action to become a validator for some epoch `T`.
2. Submit a `Stake(0)`/unstake action so `last_proposal`/`max_of_stakes` become `0`; wait for `return_stake` processing to zero out `locked` (`update_validator_accounts`, lines 1772-1793).
3. Once `locked == 0`, submit `DeleteAccount` (permitted since there is no locked stake remaining).
4. Because validator rewards for epoch `T` are computed and applied 2 epochs later (the T+2 rule), the `validator_rewards` map presented to `update_validator_accounts` at that later point still contains a non-zero `reward` entry for the now-deleted account with `max_of_stakes == 0`, triggering the silent-drop path.

No race with block producers, no network-level manipulation, and no special permissions are needed — only ordinary transaction sequencing timed against the two-epoch reward-application delay.

### Recommendation
In `update_validator_accounts` (runtime/runtime/src/lib.rs), extend the "account missing" branch to check `reward` and `last_proposal` in addition to `max_of_stakes`, mirroring the existing uninitialized-account guard:
```rust
} else {
    let reward = *validator_accounts_update.validator_rewards.get(account_id).unwrap_or(&Balance::ZERO);
    let last_proposal = *validator_accounts_update.last_proposals.get(account_id).unwrap_or(&Balance::ZERO);
    if *max_of_stakes > Balance::ZERO || reward > Balance::ZERO || last_proposal > Balance::ZERO {
        return Err(StorageError::StorageInconsistentState(format!(
            "FATAL: staking invariant does not hold. Missing account {} owed stake {}, reward {}, or proposal {}",
            account_id, max_of_stakes, reward, last_proposal
        )).into());
    }
}
```
This converts the silent token loss into a detectable, chunk-failing invariant violation, consistent with how the uninitialized-account case is already handled, and prompts a proper protocol-level fix (e.g., redirect undeliverable rewards to the protocol treasury or burn them with a matching supply adjustment) rather than allowing an undetected `total_supply` divergence.

### Proof of Concept
1. Account `A` stakes and becomes a validator during epoch `T`, earning uptime that yields `reward_A > 0` per `RewardCalculator::calculate_reward` (`chain/epoch-manager/src/reward_calculator.rs:94-144`).
2. `A` submits an unstake action; in the next epoch's `update_validator_accounts` call, `return_stake` drives `A.locked()` to `0` (`runtime/runtime/src/lib.rs:1772-1793`).
3. With `locked == 0`, `A` submits `DeleteAccount`, removing the account from state entirely.
4. Two epochs after `T` (the T+2 rule), the chunk applies `ValidatorAccountsUpdate` containing `stake_info[A] = 0` and `validator_rewards[A] = reward_A > 0` (populated via `chain/chain/src/runtime/mod.rs:243-267`).
5. In `update_validator_accounts`, `get_account(state_update, A)` returns `None`; the uninitialized-account branch is skipped (account is `None`, not `Some(uninitialized)`); execution falls to `else if *max_of_stakes > Balance::ZERO` which is `false` since `max_of_stakes == 0` — no error, no credit (`runtime/runtime/src/lib.rs:1796-1804`).
6. Meanwhile `reward_A` was already included in `epoch_actual_reward`/`minted_amount` for that epoch and applied to `total_supply` via `new_total_supply = prev.total_supply + minted_amount - balance_burnt` (per `core/primitives/src/block.rs:193`, referenced in `protocol-model/spec/economics.md:41`).
7. Net effect: `total_supply` increased by `reward_A`, but no account balance increased by that amount — the reward is permanently unaccounted for, a state-transition/accounting divergence directly analogous to the Caviar royalty-fee-collected-but-undelivered bug.

    fn update_validator_accounts(
        &self,
        state_update: &mut TrieUpdate,
        validator_accounts_update: &ValidatorAccountsUpdate,
    ) -> Result<(), RuntimeError> {
        for (account_id, max_of_stakes) in &validator_accounts_update.stake_info {
            let account = get_account(state_update, account_id)?;
            // An uninitialized account has no `locked` field, so none of this applies
            // and it is skipped. The only way it could appear in stake_info is when a
            // validator deletes their account and re-creates in an uninitialized state.
            // None of the checked values could be positive in such case. The check is
            // defense in depth, so that minted tokens do not leak from the supply if
            // this path ever becomes reachable.
            if account.as_ref().is_some_and(|account| !account.is_initialized()) {
                let rewards = &validator_accounts_update.validator_rewards;
                let reward = *rewards.get(account_id).unwrap_or(&Balance::ZERO);
                let proposals = &validator_accounts_update.last_proposals;
                let last_proposal = *proposals.get(account_id).unwrap_or(&Balance::ZERO);
                if *max_of_stakes > Balance::ZERO
                    || reward > Balance::ZERO
                    || last_proposal > Balance::ZERO
                {
                    return Err(StorageError::StorageInconsistentState(format!(
                        "FATAL: staking invariant does not hold. Uninitialized account \
                         {account_id} can hold no locked balance: max of stakes \
                         {max_of_stakes}, reward {reward}, last proposal {last_proposal}"
                    ))
                    .into());
                }
                continue;
            }
            if let Some(mut account) = account {
                if let Some(reward) = validator_accounts_update.validator_rewards.get(account_id) {
                    tracing::debug!(target: "runtime", %account_id, %reward, locked = %account.locked(), "account adding reward to stake");
                    let locked = account.locked().checked_add(*reward).ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow("update_validator_accounts".into())
                    })?;
                    account.set_locked(locked).or_inconsistent_state(account_id)?;
                }

                tracing::debug!(target: "runtime",
                       %account_id, locked = %account.locked(), %max_of_stakes,
                       "account stake and max of stakes"
                );
                if account.locked() < *max_of_stakes {
                    return Err(StorageError::StorageInconsistentState(format!(
                        "FATAL: staking invariant does not hold. \
                         Account stake {} is less than maximum of stakes {} in the past three epochs",
                        account.locked(),
                        max_of_stakes)).into());
                }
                let last_proposal = *validator_accounts_update
                    .last_proposals
                    .get(account_id)
                    .unwrap_or(&Balance::ZERO);
                let return_stake = account
                    .locked()
                    .checked_sub(max(*max_of_stakes, last_proposal))
                    .ok_or_else(|| {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - return stake".into(),
                        )
                    })?;
                tracing::debug!(target: "runtime", %account_id, %return_stake, "account return stake");
                let locked = account.locked().checked_sub(return_stake).ok_or_else(|| {
                    RuntimeError::UnexpectedIntegerOverflow(
                        "update_validator_accounts - set_locked".into(),
                    )
                })?;
                account.set_locked(locked).or_inconsistent_state(account_id)?;
                account.set_amount(account.amount().checked_add(return_stake).ok_or_else(
                    || {
                        RuntimeError::UnexpectedIntegerOverflow(
                            "update_validator_accounts - set_amount".into(),
                        )
                    },
                )?);

                set_account(state_update, account_id.clone(), &account);
            } else if *max_of_stakes > Balance::ZERO {
                // if max_of_stakes > 0, it means that the account must have locked balance
                // and therefore must exist
                return Err(StorageError::StorageInconsistentState(format!(
                    "Account {} with max of stakes {} is not found",
                    account_id, max_of_stakes
                ))
                .into());
            }
        }
