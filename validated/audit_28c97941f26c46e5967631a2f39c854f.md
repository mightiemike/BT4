Found a directly analogous pattern. NEAR's meta-transaction (`DelegateAction`, NEP-366) design has the exact same trust/race gap as the boostDelegate fee bug: a first-party check on a value can be satisfied while the *actual* resource the value depends on gets drained by another party between signing and execution, causing the paying party to lose funds for nothing.

### Title
Meta-transaction relayer can be starved of compensation because `apply_delegate_action` provides no atomicity or balance-check between the payment action and the delegated action - ([File: runtime/runtime/src/actions.rs])

### Summary
The NEP-366 meta-transaction design documented in `docs/architecture/how/meta-tx.md` explicitly describes a payment pattern analogous to the `boostDelegate` fee model in the report: the signer (Alice) bundles a payment action to the relayer together with the action the relayer actually wants executed, and the relayer decides to front the gas based on an expectation that both will succeed atomically. `apply_delegate_action` in [1](#0-0)  converts the `DelegateAction`'s inner action list into a *single* new receipt without any check that a "payment" action inside it is backed by sufficient balance, and without any global cap/slippage check analogous to `maxFeePct`.

### Finding Description
`apply_delegate_action` only validates the delegate signature, `max_block_height`, `sender_id` match, and the sender's access key/nonce via `validate_delegate_action_key` [2](#0-1) . It does not re-verify at execution time that the balance-dependent state the inner actions rely on (e.g. the sender's token balance meant to compensate the relayer) is still what it was when the relayer decided to front the gas. The docs themselves flag this exact race: [3](#0-2)  — "the payment to the relayer is still not guaranteed... The relayer could waste NEAR gas without compensation if Alice somehow reduces her balance in just the right moment."

This mirrors the report's root cause precisely: a fee/compensation check (`maxFeePct` in Bima, "check the \$FT balance first" for NEAR relayers) is satisfied at decision time, but the actual resource backing that compensation (boost weight in Bima; token balance in NEAR) is a shared, mutable value that a party controlling ordering (the boostDelegate front-running in Bima; the sender_id, or any third party altering Alice's `$FT` balance before the relayer's tx lands, in NEAR) can drain between the check and the execution — with no on-chain re-validation or slippage protection at execution time.

### Impact Explanation
This is a documented, protocol-level limitation of the current `DelegateAction`/meta-transaction implementation, not a hidden bug: relayers can be economically drained of gas fees they fronted with zero on-chain compensation, because the protocol offers no atomic guarantee or balance-at-execution check between the compensating action and the delegated action, and no per-delegate-action fee/slippage bound comparable to `maxFeePct`. Any user (sender_id) or third party who can move the sender's balance between signing and inclusion can cause this, and it requires no validator or network-level privilege — an ordinary transaction signer is sufficient. However, unlike the Bima report, the *loss falls on the relayer* (who opted in to trust the sender) rather than on an unsuspecting counterparty, and NEAR explicitly documents this as a known trust assumption rather than treating it as a security boundary to enforce on-chain.

### Likelihood Explanation
Likelihood is low-to-moderate in practice: exploiting it requires a relayer that does not perform its own pre-flight balance check (which the docs explicitly instruct relayers to do), and the loss is bounded by gas cost, not unbounded value theft from an innocent third party as in the original report. This is fundamentally a design trade-off (documented) rather than an implementation defect.

### Recommendation
This is inherent to the current NEP-366 MVP design and is already documented as a relayer trust assumption; no code defect requires fixing under this specific analog. If tightened guarantees are desired, the protocol would need either (a) an atomic "payment-then-delegated-action" receipt semantics with rollback, or (b) a relayer-specified minimum-compensation/slippage bound checked at execution time inside `apply_delegate_action`, analogous to `maxFeePct` in the Bima report.

### Proof of Concept
Not applicable as a code-level exploit against nearcore itself — the same trust gap is acknowledged in `docs/architecture/how/meta-tx.md` [3](#0-2) : a relayer submits a meta-tx expecting compensation from Alice's `$FT` balance; if Alice's balance drops before/at execution (by any means she or another party controls), `apply_delegate_action` still creates and sends the receipt with the inner actions (including the now-underfunded payment action) with no execution-time re-check protecting the relayer's expected compensation ratio, exactly paralleling how `_transferAllocated`'s `maxFeePct` check passes while the underlying `boostedAmount` has already been drained.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

    // Generate a new receipt from DelegateAction.
    let new_receipt = Receipt::V0(ReceiptV0 {
        predecessor_id: sender_id.clone(),
        receiver_id: delegate_action.receiver_id().clone(),
        receipt_id: CryptoHash::default(),

        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: action_receipt.signer_id().clone(),
            signer_public_key: action_receipt.signer_public_key().clone(),
            gas_price: action_receipt.gas_price(),
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: delegate_action.get_actions(),
        }),
    });
