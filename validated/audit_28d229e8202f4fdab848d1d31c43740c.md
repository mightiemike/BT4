## Analysis

Confirmed root cause: in the Rust `blockifier` execution engine, the `replace_class` syscall handler in `crates/blockifier/src/execution/syscalls/syscall_base.rs:369-378` explicitly reads the target class before installing it (`self.state.get_compiled_class(class_hash)?`), guaranteeing the class is declared, and rejects Cairo0 targets. The deprecated syscall path in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:795-807` similarly guards with `syscall_handler.state.get_compiled_class(request.class_hash)?` before calling `set_class_hash_at`.

However, the Starknet OS (Cairo) re-execution implementation of the same syscall, `execute_replace_class` in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo:881-920`, contains no such check — it directly performs `dict_update{dict_ptr=contract_state_changes}` with the caller-supplied `class_hash` and even has an explicit unresolved TODO documenting the gap:
```
// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
``` [1](#0-0) 

This mirrors the reported bug class exactly: a validation flag/check ("is class declared") is enforced in one code path (the sequencer's Rust blockifier — `try_declare`/`get_compiled_class` gate) but missing in the parallel path that is supposed to reproduce the same state transition (the Cairo OS syscall handler used for proof generation / re-execution), letting the "phase" (declared-class invariant) be silently bypassed.

### Title
Missing declared-class validation in OS `execute_replace_class` diverges from blockifier, enabling wrong committed state root - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The Starknet OS Cairo implementation of the `replace_class` syscall does not verify that the target `class_hash` corresponds to a declared class before writing it into `contract_state_changes`, unlike the Rust `blockifier` implementation (`syscall_base.rs::replace_class`, `deprecated_syscalls/hint_processor.rs::replace_class`), which both call `get_compiled_class`/`get_compiled_class` to enforce declaration (and, in the non-deprecated path, also enforce Cairo1-only replacement).

### Finding Description
`crates/blockifier/src/execution/syscalls/syscall_base.rs:369-378` enforces:
```rust
pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
    let compiled_class = self.state.get_compiled_class(class_hash)?;
    if !is_cairo1(&compiled_class) {
        return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
    }
    self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
    Ok(())
}
``` [2](#0-1) 

and the deprecated path similarly:
```rust
fn replace_class(...) {
    syscall_handler.state.get_compiled_class(request.class_hash)?;
    syscall_handler.state.set_class_hash_at(syscall_handler.storage_address, request.class_hash)?;
}
``` [3](#0-2) 

The corresponding Cairo OS routine that re-executes the syscall for proving purposes performs the state write unconditionally:
```
func execute_replace_class{...}(contract_address: felt) {
    ...
    let class_hash = request.class_hash;
    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}
    tempvar new_state_entry = new StateEntry(class_hash=class_hash, ...);
    dict_update{dict_ptr=contract_state_changes}(key=contract_address, prev_value=..., new_value=cast(new_state_entry, felt));
    ...
}
``` [4](#0-3) 

There is also a second, older/duplicate variant (`deprecated_execute_syscalls.cairo`) with the same unguarded pattern, confirming the check is absent across the OS's syscall implementations: [5](#0-4) 

The blockifier's own regression tests explicitly assert this divergent behavior is required to reject undeclared/Cairo0 class hashes (`undeclared_class_hash`, `cairo0_class_hash` test cases), confirming the Rust engine treats this as a hard invariant that the OS path fails to reproduce: [6](#0-5) 

An attacker (any contract deployer whose contract calls `replace_class`) can submit an ordinary transaction that invokes `replace_class` with an undeclared or arbitrary `class_hash` felt. The blockifier (the sequencer's execution engine used for block building) will reject this with `StateError::UndeclaredClassHash` (transaction reverts/fails), but the Starknet OS re-execution/proving path — which is supposed to independently re-derive the same state transition for proof generation and state-root computation — will accept it and write the arbitrary value into `contract_state_changes` as the contract's new class hash.

### Impact Explanation
This is a state-transition-validation asymmetry between the block-building execution engine and the OS that re-executes transactions to produce the committed state root/proof. If a transaction that the blockifier would reject (or execute differently, since the Rust path also blocks non-Cairo1 replacement) is instead accepted by the OS with a raw felt as the new class hash, the OS-computed state diff/commitment for that contract's class hash slot will disagree with what the sequencer/blockifier actually committed on-chain. This is exactly the "wrong committed root" / "honest-node divergence" category: either the OS-produced state root diverges from the sequencer's blockifier-computed root (breaking provability of otherwise-valid blocks), or, if the OS path is authoritative for proving, a contract's class hash storage slot can be set to a completely undeclared/fabricated value, corrupting that contract's class hash permanently (a form of unauthorized account action / freezing, since an undeclared/garbage class hash makes the account uncallable / stuck) at that address.

### Likelihood Explanation
The `replace_class` syscall is directly callable by any deployed contract, including one deployed by an unprivileged sender in an ordinary `INVOKE`/account transaction. No special privileges are required — only that the calling contract's code includes/exposes a `replace_class` syscall invocation with an attacker-controlled `class_hash` argument (as the blockifier's own `test_replace_class` test contract demonstrates is a normal, testable contract feature). The gap is also explicitly and currently acknowledged by an open `TODO` in the code, confirming it is a known, unresolved condition rather than dead/legacy code.

### Recommendation
Add the same declared-class (and, to match the non-deprecated Rust path, Cairo1-only) validation to `execute_replace_class` in both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo`, mirroring `syscall_base.rs::replace_class`: before performing `dict_update` on `contract_state_changes`, assert that `class_hash` is present in `contract_class_changes` (i.e., has been declared) and, where applicable, verify it is a Cairo1 (Sierra) class, erroring out otherwise so that the OS's accepted/rejected transaction set and resulting state diff exactly match the blockifier's.

### Proof of Concept
1. Declare and deploy an account/contract `C` whose entry point calls the `replace_class` syscall with a caller-supplied felt argument (the exact pattern used in the existing `test_replace_class` test contract referenced by `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs`).
2. Submit an `INVOKE` transaction calling that entry point with `class_hash = <undeclared arbitrary felt>` (as in the `undeclared_class_hash` test) or with a valid but Cairo0 class hash (as in `cairo0_class_hash`).
3. Observe: the sequencer's blockifier execution rejects/reverts the transaction (`StateError::UndeclaredClassHash` / `ForbiddenClassReplacement`), per `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs:17-53`.
4. Feed the identical transaction/calldata into the Starknet OS re-execution path exercising `execute_replace_class` in `syscall_impls.cairo`; because no declared-class check exists there, the OS accepts the syscall and writes `class_hash` into `contract_state_changes` for `contract_address`, producing a state diff/commitment inconsistent with the blockifier's actual (rejecting) behavior.

    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();

    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.

    %{ GetContractAddressStateEntry %}
