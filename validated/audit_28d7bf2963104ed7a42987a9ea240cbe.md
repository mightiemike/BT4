### Title
Unhandled `.unwrap()` on `receiver_shard_id()` panics chunk producers on a stale/unresolvable `GlobalContractDistribution` receipt shard ID - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueue::receipt_filter_fn()` blindly `.unwrap()`s the `Result` returned by `Receipt::receiver_shard_id()`. For `GlobalContractDistribution` receipts, that function can legitimately return `Err(EpochError::ShardingError(..))` when the receipt's `target_shard` cannot be mapped to any shard in the current layout or its recorded split history. A crash here happens while draining the delayed-receipts queue during ordinary chunk application — a code path directly reachable from an unprivileged, un-gated action (`DeployGlobalContract`).

### Finding Description
`Receipt::receiver_shard_id()` resolves the shard for a `GlobalContractDistribution` receipt via `ShardLayout::resolve_to_current_shard`, returning an error if the target shard is absent from both the current layout and its tracked split history: [1](#0-0) 

`resolve_to_current_shard` walks `shards_split_map`, which is built by `build_shard_split_map`. Crucially, this builder stops accumulating history the moment it encounters the transition window between a pre-V3 (`version() < 3`) layout and the first V3 layout, discarding exactly the split that occurred at that transition: [2](#0-1) [3](#0-2) 

As a result, if a `GlobalContractDistribution` receipt is created with a `target_shard` from the layout in place immediately before the network's V1/V2→V3 shard-layout migration, and that receipt is still sitting in the delayed-receipt queue when it is later popped (post-migration, or after subsequent V3 splits push it further away), `resolve_to_current_shard` returns `None`, and `receiver_shard_id()` returns `Err`.

That `Err` is not handled — it is unconditionally unwrapped inside the hot congestion-control filtering path used by every chunk application: [4](#0-3) 

This mirrors the CVE-2021-46019 bug class: a value derived from external/queued input (the pointer/shard reference) is dereferenced (`.unwrap()`ed) without validating that it is still valid, leading to a crash. The project's own test suite documents an almost identical scenario for double-resharding-within-V3 and explicitly frames the failure mode as "processing the stale receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard": [5](#0-4) [6](#0-5) 

That test only exercises two same-version (V3→V3) splits and passes because `resolve_to_current_shard` handles pure V3 history correctly. It does **not** cover the legacy-to-V3 migration boundary, where `build_shard_split_map` deliberately `break`s and permanently loses the split mapping, leaving the class of bug open for any receipt whose `target_shard` predates that migration.

### Impact Explanation
Any account can trigger creation of a `GlobalContractDistribution` receipt simply by deploying a global contract (`DeployGlobalContract` action, no special privilege required). If that receipt is congested/delayed across the shard layout's version migration boundary (attacker can amplify likelihood by saturating the target shard's compute budget, as demonstrated by the existing test harness), the eventual `.unwrap()` panic crashes every chunk producer/validator processing that shard when it drains the delayed queue — a transaction-triggered halt affecting chain liveness. This satisfies the "transaction-triggered halt" impact category.

### Likelihood Explanation
Exploitability requires the shard layout to still carry a legacy (V1/V2) → V3 migration in its recorded history and a receipt to remain queued across that boundary — this is a narrower window than the already-patched V3→V3 case, so the likelihood depends on whether such a legacy migration boundary is still reachable in current/future epoch configurations (e.g., new networks bootstrapped directly on V3 would not be affected, but networks that migrated through V1/V2 could still have the un-tracked split in their historical layout chain, and dynamic resharding continues to grow `shards_split_map` from that already-incomplete base). I could not fully verify from the indexed code whether any currently-configured production shard layout still contains this legacy boundary within `layout_history`, so this should be validated against the live epoch-config history before treating it as certain-to-trigger.

### Recommendation
- Replace the `.unwrap()` in `receipt_filter_fn()` (`runtime/runtime/src/congestion_control.rs:876`) with proper error propagation (return a `RuntimeError`/skip-and-log) instead of panicking on unresolved shard IDs.
- Fix `build_shard_split_map` in `core/primitives/src/shard_layout/v3.rs` to record the split at the legacy→V3 transition boundary instead of `break`-ing before capturing it, so `resolve_to_current_shard` can resolve receipts whose `target_shard` predates the V3 migration.
- Audit all other call sites of `receiver_shard_id()` for the same unwrap-on-`Result` pattern.

### Proof of Concept
1. Bootstrap (or use an existing) network whose shard-layout history contains a transition from a V1/V2 layout to the first V3 layout (this is the un-tracked boundary in `build_shard_split_map`).
2. As any unprivileged account, submit a `DeployGlobalContract` transaction on the shard whose ID exists only in the pre-V3 layout, generating a `GlobalContractDistribution` receipt with `target_shard` equal to that legacy shard ID.
3. Saturate the target shard's compute budget every block (as done in `test_stale_global_contract_distribution_after_double_resharding`, `test-loop-tests/src/tests/global_contracts_distribution.rs:100-162`) so the receipt is pushed into the delayed-receipt queue and remains there through the V1/V2→V3 shard-layout migration.
4. Stop saturating and let the delayed queue drain; when the queue pops the stale receipt, `receipt_filter_fn()` calls `receiver_shard_id()` → `resolve_to_current_shard()` returns `None` (the split at the legacy boundary was never recorded) → `Err(EpochError::ShardingError)` → `.unwrap()` panics, crashing the chunk producer for that shard.

pub fn build_shard_split_map(layout_history: &[ShardLayout]) -> ShardsSplitMapV3 {
    let mut split_history = ShardsSplitMapV3::new();

    for window in layout_history.windows(2) {
        let current_layout = &window[0];
        let prev_layout = &window[1];

        if current_layout.version() < VERSION || prev_layout.version() < VERSION {
            break;
        }

        debug_assert_ne!(current_layout, prev_layout);

        for shard_id in current_layout.shard_ids() {
            match current_layout.try_get_parent_shard_id(shard_id).expect("invalid shard_id") {
                Some(parent_id) if parent_id != shard_id => {
                    split_history.entry(parent_id).or_default().push(shard_id);
                }
                _ => continue,
            }
        }
    }

    split_history
}

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }
