### Title
Internal error messages leaked to unauthenticated OAuth callback/session-validation requests - ([File: packages/apps/shopify-app-express/src/auth/auth-callback.ts])

### Summary
The `shopify-app-express` OAuth callback handler and the session-validation middleware both send raw `error.message` values from caught exceptions directly to the HTTP client. Since the `/auth/callback` endpoint and session-validation code paths are reachable by anonymous/unauthenticated requests (any browser hitting the callback URL, or any request carrying an `Authorization` header/session cookie), an attacker can trigger unexpected internal errors (malformed query strings, storage failures, decoding failures) and receive backend implementation details in the response body — the same bug class as the reported "Application Error Leaks Information About Technology Used" finding (stack/technology disclosure via error message reflected to the client).

### Finding Description
In `handleCallbackError` inside `packages/apps/shopify-app-express/src/auth/auth-callback.ts`, any error that isn't one of the explicitly-typed OAuth errors falls into the `default` branch, which does: [1](#0-0) 
```
default:
  res.status(500);
  res.send(error.message);
  break;
```
This is confirmed by the test `'borks on unknown errors'`, which shows an arbitrary `Error('Unknown error')` thrown from the OAuth callback is reflected verbatim to the HTTP response body with a 500 status: [2](#0-1) 

The same pattern exists in `packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts`, where `handleSessionError` (invoked from the `Authorization: Bearer` code-flow session-validation path, reachable by any request carrying a session token) also reflects `error.message` for any non-`InvalidJwtError` exception, and the session-loading catch block does the same: [3](#0-2) [4](#0-3) 

Both handlers sit directly in request-authentication flows (`/auth/callback` OAuth handler and the authenticated-session middleware), and both are triggerable pre-authentication — an OAuth callback request needs no prior session, and session validation is the first gate hit by any incoming request. Any exception thrown by `config.sessionStorage.loadSession`/`storeSession` (e.g. a database driver error containing connection strings, file paths, or query text), or any unexpected error surfaced from `api.auth.callback` (network/HTTP client failures, JSON parsing errors, host/nonce parsing errors), is passed through unmodified via `error.message` into the HTTP response — this is directly analogous to the reported bug where a body-parser JSON error including absolute filesystem paths (`/home/centos/wallet-backend/node_modules/...`) and Node internals was returned to the caller.

### Impact Explanation
An attacker probing the public OAuth callback endpoint or authenticated routes with malformed input can force underlying dependencies (session storage backends, HTTP clients, JWT/JSON parsers) to throw, and the resulting `error.message` — which may contain internal file paths, database connection details, hostnames, or library/version information — is returned directly in the HTTP response. This is an information-disclosure vulnerability that helps an attacker fingerprint the technology stack and internal infrastructure, aiding further targeted attacks (matching Impact/Likelihood ~3 in the original report).

### Likelihood Explanation
These code paths are reachable by any anonymous HTTP request to `/auth/callback` (no authentication required) or to any route protected by `validateAuthenticatedSession` middleware by simply supplying a malformed or expired `Authorization` bearer token or triggering a session-storage failure. No privileged access or prior session is required to reach the vulnerable `catch` blocks, making exploitation straightforward for any external caller who can cause an exception in the underlying storage/auth calls.

### Recommendation
- In `handleCallbackError` (`auth-callback.ts`) and `handleSessionError` (`validate-authenticated-session.ts`), stop sending raw `error.message` to the client for generic/unexpected errors. Log the full error server-side (`config.logger.error`) and return a generic message (e.g. `"Internal Server Error"`) to the client for the `default` case, mirroring what is already done in `perform-token-exchange.ts`'s `catch` block (`res.status(500).send('Internal Server Error')`).
- Audit all other `res.send(error.message)` / `res.send(error)` occurrences across `shopify-app-express` request-authentication handlers for the same pattern and normalize them to sanitized, generic error responses.

### Proof of Concept
1. Send a request to `GET /auth/callback?shop=<valid>&host=<valid>` with a `code`/`hmac` combination that is technically valid enough to pass initial validation but causes `config.sessionStorage.storeSession` (or another downstream call) to throw an unexpected error (e.g. a database connectivity error).
2. Observe the response: `handleCallbackError`'s `default` branch returns HTTP 500 with the raw `error.message` in the body, as demonstrated by the existing test: [2](#0-1) 
3. Similarly, send an authenticated-route request with a token that causes `config.sessionStorage.loadSession` to throw; observe the raw `error.message` reflected via: [5](#0-4) 

**Note on limitations:** I was unable to inspect `packages/apps/shopify-api/lib/error.ts` and `packages/apps/shopify-api/lib/auth/oauth/oauth.ts` in full due to a tool error on the final iteration, so I cannot enumerate every specific error subclass/message format that could reach these `default`/generic branches (e.g., exact contents of underlying HTTP client errors). The core vulnerable sink pattern (`res.send(error.message)` in an unauthenticated, request-authentication-related handler) is confirmed via grep and the existing unit test.
