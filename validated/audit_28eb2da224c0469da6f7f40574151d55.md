### Title
Reward accumulated for a Super Representative whose recorded cycle vote count is `0` is permanently locked in `DelegationStore` - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService` and `DelegationStore` implement a reward-per-cycle accrual scheme that mirrors the vulnerable pattern in the referenced report: rewards for a witness are accumulated into a per-cycle bucket, but distribution to voters divides by that witness's per-cycle vote-count "denominator". If the denominator recorded for that cycle is `0`, the reward is silently skipped rather than redistributed or carried forward, so it becomes permanently stuck with no recovery mechanism, exactly as described in the report ("if totalSupply()==0 for some period... reward stuck in contract forever").

### Finding Description
Block/standby/transaction-fee rewards for a witness are accumulated per cycle via: [1](#0-0) 

`payReward` is invoked unconditionally by `payBlockReward`/`payTransactionFeeReward` for any witness that produces a block, and by `payStandbyWitness` for any standby witness, regardless of that specific witness's per-cycle vote count: [2](#0-1) 

The per-cycle vote count "denominator" for every witness (not just active ones) is snapshotted once per maintenance interval from the witness's *current* vote count: [3](#0-2) 

The active/standby witness set itself, however, is only re-sorted at maintenance boundaries and is otherwise fixed for the whole cycle: [4](#0-3) 

Consequently, a witness can remain part of the current block-producing/standby set for an entire cycle (continuing to earn `payBlockReward`/`payTransactionFeeReward`/`payStandbyWitness` payouts) while its own vote count for that cycle has already dropped to `0` (e.g. all voters withdrew/un-froze their stake, or `VoteWitnessActuator`/`UnfreezeBalanceV2Actuator` zeroed the witness's votes) before the next maintenance re-selection takes effect. When any voter later tries to claim the accumulated reward for that cycle, both reward paths explicitly skip it because the recorded `totalVote` denominator is `0`:

Old algorithm path: [5](#0-4) 

New "Vi" algorithm path (used by `DelegationStore.accumulateWitnessVi` and mirrored in `RewardViCalService`/`VoteRewardUtil`), which forwards the previous accumulator unchanged instead of distributing the reward when `voteCount == 0`: [6](#0-5) 

In both cases `delegationStore.getReward(cycle, srAddress)`/`addReward` has already stored the paid-out reward amount for that witness/cycle key, but there is no code path anywhere in `MortgageService`, `DelegationStore`, `RewardViCalService`, or `VoteRewardUtil` that ever redistributes, refunds, or reclaims a reward whose cycle vote count is `0`. The value is left in the `delegation` store forever, unreachable by any account, exactly mirroring the `rewardPerTokenStored` staleness in the referenced Solidity report.

### Impact Explanation
Rewards paid to a witness for blocks it produced or for transaction fees/standby duty during a cycle in which its recorded vote total is `0` are permanently lost from the delegation/reward accounting system — no account, including the witness's own voters, can ever claim them. This is an accounting/asset-loss defect in the core DPoS reward-distribution mechanism (`consensus`/`chainbase` reward accounting), not contingent on any privileged actor, malicious peer, or off-chain compromise — it occurs through ordinary user actions (mass unfreeze/vote withdrawal) combined with normal maintenance-cycle timing. Given java-tron mainnet's real economic value tied to SR rewards, this results in real, permanent loss of protocol-distributed reward funds.

### Likelihood Explanation
Likelihood is contingent (Medium), matching the judge's characterization of the analogous C4 finding: it requires that a witness's aggregate vote count reaches `0` for at least one full reward cycle while it is still part of the active/standby set (e.g., all delegators withdraw votes right after the witness was selected, before the next maintenance recalculation removes it from block production). This is a naturally reachable network condition, especially for smaller/edge witnesses or private/test-net deployments with few SR candidates, and requires no attacker capability beyond ordinary vote/unfreeze transactions.

### Recommendation
Add a mechanism in `MortgageService.payReward`/`DelegationStore.accumulateWitnessVi` (and the mirrored `RewardViCalService`/`VoteRewardUtil` logic) to detect when a witness's per-cycle vote total is `0` and either: (a) prevent reward accrual for that witness/cycle in the first place (skip `addReward` when the witness has no recorded voters), or (b) roll the un-distributable reward forward into the next cycle's pool for that witness (or into a general treasury/committee-controlled recovery fund) instead of silently discarding it when `totalVote == 0`.

### Proof of Concept
1. Configure a small witness/testnet where an SR `W` is elected into the active set with vote count `V > 0`.
2. Have all voters call `VoteWitnessActuator`/`UnfreezeBalanceV2Actuator` to withdraw their votes for `W`, driving `W`'s vote count to `0`, before the next `MaintenanceManager.doMaintenance()` boundary.
3. During the remainder of the cycle, `W` continues producing blocks and calls `MortgageService.payBlockReward`/`payTransactionFeeReward`, which call `delegationStore.addReward(cycle, W, value)` — funds accumulate under `cycle-W-reward`.
4. At the next maintenance boundary, `delegationStore.setWitnessVote(cycle, W, 0)` is recorded (per `MaintenanceManager.doMaintenance`, line 160) since `W.getVoteCount()` is now `0`.
5. Any voter who previously voted for `W` in that cycle calls `withdrawReward`/`queryReward`; `computeReward` (`MortgageService.java` lines 171-188) hits `totalVote == 0` and `continue`s, permanently discarding the reward recorded in step 3 with no code path to reclaim it.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
