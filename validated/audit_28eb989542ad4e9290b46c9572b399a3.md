### Title
Precision loss in `double`-based global energy/bandwidth limit calculation causes incorrect resource quota accounting - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
The reported Cairo bug is a classic "divide-before-multiply" precision-loss pattern: `(asset_amt * total_yang) / total_assets` is computed via `Wad` arithmetic that internally divides by `1e18` twice, truncating the intermediate result and under-crediting the depositor. The same class of bug is reproduced in java-tron's resource-accounting code, where the default (non-hardened) path computes a user's global energy/bandwidth limit using `double` division of two ratios and then multiplies them, instead of doing a single exact integer computation.

### Finding Description
In `EnergyProcessor.calculateGlobalEnergyLimitV2`, the default path is: [1](#0-0) 

```java
double energyWeight = (double) frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```

Both `frozeBalance / TRX_PRECISION` and `totalEnergyLimit / totalEnergyWeight` are evaluated as separate floating-point divisions before being multiplied together and truncated to `long`. `double` has only 53 bits of mantissa precision, so once `frozeBalance`, `totalEnergyLimit`, or `totalEnergyWeight` exceed that range (which happens for large frozen balances or large aggregate network weights — both realistic on a live chain), the two independent roundings compound and the final truncated result diverges from the mathematically exact value.

The codebase itself contains an explicit "hardened" replacement, `calculateGlobalLimitV2`, that performs the equivalent computation with a single `BigInteger` multiply-then-divide to avoid this exact defect: [2](#0-1) 

and a dedicated regression test proves the two paths diverge for realistic inputs: [3](#0-2) 

The hardened path is gated behind `hardenCalculation()` / `allowHardenResourceCalculation`, which is a chain-parameter proposal switch; unless/until that proposal is activated on the network, the vulnerable `double`-based legacy formula is the one actually executed: [4](#0-3) [5](#0-4) 

### Impact Explanation
`calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` is the core accounting function that converts an account's frozen TRX (or delegated resource weight) into its usable energy quota, invoked on every `useEnergy` check for TVM contract execution: [6](#0-5) 

Because of the double rounding, an unprivileged user who freezes TRX for energy (a completely normal, permissionless action) can receive a computed energy limit that is off from the exact value — either denying them energy they paid for (loss of resource entitlement) or, in the opposite rounding direction, granting more energy than the network weight formula intends (dilution of the shared "totalEnergyCurrentLimit" pool at the expense of other stakers). This is directly analogous to the original finding's "user loses a portion of their funds" impact, translated to the resource/quota accounting domain, which is a first-class economic resource in java-tron (frozen TRX is bought/staked to obtain it).

### Likelihood Explanation
The vulnerable computation runs unconditionally for every account on every energy consumption/limit check whenever the hardening proposal is not enabled, which is the default/legacy behavior path still shipped in the codebase. No privileged role is required — any account that freezes TRX for energy and later triggers a contract call exercises this code. The magnitude of the discrepancy grows with `frozeBalance`/`totalEnergyWeight`, both of which naturally increase over time on a live network, making the divergence increasingly likely to manifest as amounts grow.

### Recommendation
Make the `BigInteger`-based exact calculation (`calculateGlobalLimitV2`) the default and unconditional implementation rather than gating it behind the `allowHardenResourceCalculation` proposal switch, or equivalently replace the `double` computation with a single integer multiply-then-divide: `frozeBalance * totalEnergyLimit / (TRX_PRECISION * totalEnergyWeight)` using `BigInteger`/`Math.multiplyHigh` to avoid overflow, matching the pattern already implemented in `calculateGlobalLimitV2`.

### Proof of Concept
The repository's own test demonstrates the divergence between the legacy `double` path and the exact `BigInteger` path for realistic values: [3](#0-2) 

With `totalEnergyLimit = 50_000_000_000`, `totalEnergyWeight = 1_234_567`, `frozeBalance = 9_876_543_210_000_000`, the exact `BigInteger` computation and the legacy `double` computation (as used by default in `calculateGlobalEnergyLimitV2`) produce different `long` results, confirming the truncation/precision-loss defect described in the original report is reproducible on the default execution path.

```java
  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
```

```java
  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
```

```java
  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
```
