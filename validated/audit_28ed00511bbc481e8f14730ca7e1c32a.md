### Title
Attacker-set `RevertInstructions.FundRecipient` can permanently brick honest outbound-failure recovery via `AbortOutbound` - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
The external report is a "permissionless settlement can be griefed by an unfriendly recipient address, causing the mandatory token transfer to revert and permanently blocking the invariant" bug class. The Push Chain analog is `handleFailedOutbound` in `x/uexecutor/keeper/outbound.go`, which is invoked from the fully permissionless, honest-validator-driven `FinalizeOutbound` path once `MsgVoteOutbound` reaches quorum. It re-mints (`CallPRC20Deposit`) bridged funds to a recipient address that is **entirely attacker-controlled** (`outbound.RevertInstructions.FundRecipient`, set by the original inbound sender). If that mint call errors for any reason, the code path unconditionally calls `k.AbortOutbound`, which flips the outbound into a terminal `Status_ABORTED` state with no on-chain remediation path in this module — matching the report's "no way to bypass and force-settle" problem.

### Finding Description
The lifecycle is:
1. A user submits an inbound with `RevertInstructions.FundRecipient` fully attacker-controlled (there is no validation restricting it to a "safe" address — it is just carried through `Canonicalize`/`ValidateBasic` as an opaque string, see `x/uexecutor/keeper/build_revert_outbound.go:11-14` and `x/uexecutor/keeper/outbound.go:107-112`, both of which use `RevertInstructions.FundRecipient` verbatim as the recipient of a PRC20 mint).
2. Honest Universal Validators vote (`MsgVoteOutbound`) that the destination-chain execution failed. This is a fully permissionless, honest-validator flow — no privileged actor is involved.
3. `FinalizeOutbound` → `handleFailedOutbound` (`x/uexecutor/keeper/outbound.go:71-161`) computes the revert `recipient` from `outbound.RevertInstructions.FundRecipient` and calls: [1](#0-0) 
4. If `CallPRC20Deposit` (a `DerivedEVMCall` to the PRC20 handler's `depositPRC20Token`, see `x/uexecutor/keeper/evm.go:262-303`) reverts — e.g. because the attacker deliberately chose `FundRecipient = 0x000...000` (many ERC20 mint implementations revert on mint-to-zero-address), or any other address/state that deterministically makes the mint revert — the code does not retry with a safe fallback recipient. It instead calls: [2](#0-1) 
5. `AbortOutbound` (`x/uexecutor/keeper/outbound.go:45-69`) sets `Status_ABORTED` permanently and removes the outbound from `PendingOutbounds`. There is no code path elsewhere in the scanned `x/uexecutor` module that re-attempts, force-settles, or admin-overrides an `ABORTED` outbound with a different (safe) recipient — the bridged funds represented by the outbound are stuck in this terminal state.

This exactly mirrors the Notional pattern: a mandatory, permissionless "settlement" step performs a token transfer to a user-chosen address, and if that transfer is rejected, the whole finalization is permanently blocked with no automatic recovery, and (per the report's own recommendation) would require an admin bypass that does not exist here.

### Impact Explanation
An unprivileged attacker can force their own bridged inbound's failure-outbound into a permanently `ABORTED` state by choosing a `RevertInstructions.FundRecipient` that guarantees `depositPRC20Token` reverts (e.g., the zero address, or any other address/config causing a deterministic mint failure). Because `AbortOutbound` is terminal and no automated or user-driven retry/re-target exists in the module, this results in **permanent freezing of protocol/user-controlled funds** (the bridged amount that should have been re-minted back to the user is now stuck, unreachable through any permissionless path) and it also generically demonstrates that the honest-validator finalization path can be driven into an unrecoverable state by attacker-supplied input alone — undermining the invariant that outbound finalization always resolves the UTX to `OBSERVED`/`REVERTED` recoverable states.

### Likelihood Explanation
High. `FundRecipient` is set at inbound-creation time entirely by the (attacker-controlled) submitting party and is never validated to be a "receivable" address before being used as a mint destination on the failure path. Triggering an outbound failure only requires the destination-chain call to fail (attacker fully controls this, e.g. by making the destination call revert), which is a normal, expected part of the outbound lifecycle (see the existing `handleFailedOutbound`/`applyGasRefund` machinery built specifically to handle "outbound failed" cases). No validator collusion, governance action, or privileged access is required.

### Recommendation
- Validate `RevertInstructions.FundRecipient` at inbound acceptance time (e.g., reject the zero address and any other addresses known to make PRC20 mint calls revert).
- In `handleFailedOutbound`, do not let a single failed mint attempt terminate to `ABORTED` forever without a safe fallback: retry the mint to `outbound.Sender` (a value derived from validated on-chain source data rather than fully attacker-supplied) if the `FundRecipient`-directed mint fails, or provide a permissionless/administrative "redirect and retry" message for `ABORTED` outbounds so re-minting can complete without requiring an unbounded manual/off-chain fix.
- Ensure `AbortOutbound` is paired with a defined on-chain recovery mechanism (analogous to the report's recommendation to let an admin "bypass the withdrawal and force settle").

### Proof of Concept
1. Attacker submits a `FUNDS_AND_PAYLOAD` (or `FUNDS`) inbound whose payload is designed to fail on the destination chain, and sets `Inbound.RevertInstructions.FundRecipient = "0x0000000000000000000000000000000000000000"`.
2. The inbound reaches quorum; an `OutboundTx` is created carrying the same `RevertInstructions` (per `buildRevertOutbound`, `x/uexecutor/keeper/build_revert_outbound.go:11-14`, and the general outbound-creation path in `x/uexecutor/keeper/create_outbound.go`).
3. Honest UVs observe the destination-chain execution fail and submit `MsgVoteOutbound` with `success=false`, reaching quorum honestly.
4. `FinalizeOutbound` → `handleFailedOutbound` computes `recipient = "0x000...000"` and calls `CallPRC20Deposit`, which reverts (mint to zero address).
5. `AbortOutbound` is called, setting the outbound to `Status_ABORTED` permanently; the bridged funds are never re-minted to any address and remain unrecoverable via any exposed message in the scanned module.

*Note: exact PRC20 mint-implementation behavior (whether mint-to-zero-address definitively reverts, or whether other deterministic-revert recipient values exist) could not be fully confirmed from the indexed contract source within this scan — the PRC20/UniversalCore Solidity implementation is outside the indexed Go repository content. This should be verified directly against the PRC20 `depositPRC20Token`/mint implementation before treating severity as fully confirmed.*
