### Title
Asset creation can be permanently blocked by front-running the user-chosen token `name` - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator` lets any account choose an arbitrary `name` for a new token. When same-token-name is disallowed (`AllowSameTokenName == 0`), the name is used as the sole uniqueness key in `AssetIssueStore`, and issuance fails permanently for any later transaction using an already-taken name. This mirrors the reported bug class: a user-supplied identifier is validated for uniqueness against on-chain state before the state is written, so a griefer who observes a pending transaction (e.g. in the broadcast/mempool of a node, or simply races the same name) can consume that name first and permanently deny the intended party the ability to ever issue a token with their desired name.

### Finding Description
`AssetIssueActuator.validate()` checks `assetIssueStore.get(assetIssueContract.getName().toByteArray()) != null` and throws `"Token exists"` if the name is already registered, but only enforces this when `dynamicStore.getAllowSameTokenName() == 0`: [1](#0-0) 

The name itself is fully attacker/user chosen with only cosmetic constraints (`validAssetName`, not equal to `"trx"`): [2](#0-1) 

Execution then persists the asset under a DB key derived from that name (`assetIssueCapsule.createDbKey()`), and once written, no other account can ever issue an asset with that same name while `AllowSameTokenName == 0`: [3](#0-2) 

This is functionally identical to the reported vulnerability pattern: the state-changing operation's success depends entirely on an attacker-observable, user-chosen identifier that is checked for prior existence and rejected if taken — enabling a classic front-running/griefing attack on any chain with a visible/broadcast transaction pool. The existing unit test `IssueSameTokenNameAssert` explicitly demonstrates that a second issuance with the same name reverts with `"Token exists"` while `AllowSameTokenName == 0`: [4](#0-3) 

Unlike `CreateAccountActuator` (where the "identifier" is the caller's own address, so it inherently cannot be squatted by a third party) or `WitnessCreateActuator` (also keyed by the caller's own address), the asset `name` here is an independent, freely chosen string decoupled from the caller's identity, making it directly analogous to the `accountId`-collision griefing bug described in the report.

### Impact Explanation
An attacker monitoring the transaction pool (or simply racing with better fee/priority) can permanently deny a specific desired token name to any issuer while `AllowSameTokenName == 0`. Because the name-uniqueness constraint is a permanent on-chain registration (no expiry, no ownership tied to the front-runner beyond squatting the name), this is a lasting griefing/DoS against the "issue asset by desired name" functionality — the victim can never obtain that name for a real, branded asset. This matches the "Griefing" impact category from the reference report (no profit motive required for the attacker beyond obstruction).

### Likelihood Explanation
Exploitability depends entirely on `getAllowSameTokenName() == 0` being the active state. Historically java-tron shipped with this flag defaulting to `0` and only switched to `1` via a chain parameter/proposal (`ALLOW_SAME_TOKEN_NAME`) once network governance activated it; I could not fully confirm from the index whether the flag is currently forced to `1` (irreversibly) on this particular fork/version, since the `DynamicPropertiesStore.java` default-value logic for this property was not retrievable in the last search iteration. If the deployed network still allows `AllowSameTokenName == 0` (e.g. on genesis or a chain where the governance proposal to enable same-token-name has not been passed), the vulnerability is fully live and requires no privileged access — any account able to broadcast a transaction can exploit it. If the flag is hardcoded to `1` on all supported networks, this specific path is dead code and the same-token-name uniqueness check never triggers.

### Recommendation
- Do not use a user-chosen, front-runnable string/ID as the sole and permanent uniqueness key for a state-changing creation operation.
- If human-readable names remain desired, decouple them from the primary unique key: keep the internal `id` (already generated via `dynamicStore.getTokenIdNum()`, see lines 72-76) as the sole identity, and treat `name` as non-unique metadata, or require a bonded/reserved-name commit-reveal scheme so front-runners cannot squat names without cost.
- Alternatively, confirm and, if not already done, permanently retire the `AllowSameTokenName == 0` code path network-wide so the vulnerable branch in `AssetIssueActuator.validate()`/`execute()` can never be reached again.

### Proof of Concept
1. On a network state where `DynamicPropertiesStore.getAllowSameTokenName() == 0` (default/initial state), Bob broadcasts an `AssetIssueContract` with `name = "BOB_TOKEN"`.
2. Alice observes Bob's pending transaction (via the P2P/broadcast layer or transaction pool) and immediately broadcasts her own `AssetIssueContract` with the identical `name = "BOB_TOKEN"`, paying a higher/equal energy price to be included first.
3. Alice's transaction executes; `AssetIssueStore.put(assetIssueCapsule.createDbKey(), ...)` registers `"BOB_TOKEN"` as taken, per [3](#0-2) .
4. Bob's transaction is subsequently processed; `validate()` finds `assetIssueStore.get("BOB_TOKEN") != null` and throws `ContractValidateException("Token exists")`, per [1](#0-0) , exactly as reproduced by the existing test `IssueSameTokenNameAssert` at [4](#0-3) .
5. Bob can never issue an asset called `"BOB_TOKEN"` again while `AllowSameTokenName == 0` remains set.
