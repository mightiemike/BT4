### Title
Trusting Unverified `shop` Query Parameter for Session Lookup in `AppDistribution.ShopifyAdmin` Flow - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`, `packages/apps/shopify-app-react-router/src/server/authenticate/admin/authenticate.ts`)

### Summary
In the `AuctionEscapeHatch` finding, the root cause was relying on an attacker-influenceable data source (AMM spot price) instead of a verified, tamper-resistant source (a TWAP oracle) for a security-critical calculation. The analogous pattern in shopify-app-js is in `getSessionTokenContext`: for embedded apps distributed via the Shopify Admin (`AppDistribution.ShopifyAdmin`), the `shop` value used to key the session lookup is taken directly from the unauthenticated `shop` URL query parameter rather than from the cryptographically verified JWT session token `dest` claim — the trusted source used in the non-`ShopifyAdmin` branch just a few lines above.

### Finding Description
`getSessionTokenContext` has two branches:
- For non-`ShopifyAdmin` distributions, the code validates the session token via `validateSessionToken`, and derives `shop` from the verified `payload.dest` (a value cryptographically signed by Shopify): [1](#0-0) 
- For `ShopifyAdmin` distribution, the code instead reads `shop` straight from `url.searchParams.get('shop')` — an untrusted, attacker-controllable request parameter with no HMAC or JWT verification applied to it in this function — and uses it as the returned `shop`, which downstream is used together with `api.session.getCurrentId` to resolve the session: [2](#0-1) 

This mirrors the "spot price vs. TWAP oracle" bug class: a verified, tamper-resistant signal (`payload.dest` from a signed session token) exists and is used elsewhere in the very same function, but the `ShopifyAdmin` code path substitutes an easily-spoofed value (raw query string) for the security-relevant decision (which shop's session record to resolve/return). The `getShopFromRequest` helper used elsewhere for logging purposes also just reads the query param with no validation: [3](#0-2) 

The identical pattern exists in the React Router package: [4](#0-3) 

### Impact Explanation
I was unable to fully verify, within the available tool budget, whether `api.session.getCurrentId` cross-checks the returned session's `shop` field against this untrusted `shop` variable before it is used by downstream request handlers, or whether callers of `authenticate.admin` rely on the returned `shop` value as authoritative for tenant-scoped operations. If the returned `shop` (attacker-supplied) is used downstream to scope API calls, webhooks, or billing checks without being reconciled against the actual session/cookie-derived shop, this could enable a cross-tenant confusion issue analogous to using an unreliable oracle: the "critical value" (which shop this session belongs to) is decided from a spoofable input rather than a verified one. This needs to be confirmed by inspecting `api.session.getCurrentId` and all downstream consumers of `SessionTokenContext.shop` in the `ShopifyAdmin` branch, which I could not complete due to running out of iterations.

### Likelihood Explanation
Likelihood is moderate-to-uncertain. The `ShopifyAdmin` distribution path is specifically meant for apps embedded only in Shopify Admin (not directly reachable by arbitrary web traffic without going through Shopify's iframe flow), which reduces but does not eliminate exposure. Since `getCurrentId` internally reads cookies/session storage that are presumably scoped independently, the impact hinges entirely on whether the raw `shop` query param is trusted for anything beyond logging — a detail I could not confirm.

### Recommendation
Verify whether `api.session.getCurrentId`'s returned session is reconciled against the requested `shop`; if the `shop` value from `authenticate.ts`'s `ShopifyAdmin` branch is used for any security decision (e.g., returned to callers as the authenticated shop, used to scope subsequent API calls), it should be validated against `api.utils.sanitizeShop()` and cross-checked against the session actually resolved by `getCurrentId`, rather than trusted as-is from the query string.

### Proof of Concept
Not established — a concrete PoC would require confirming that `api.session.getCurrentId()` does not internally validate/override the untrusted `shop` and that some downstream consumer treats the returned `shop` as authoritative for a security decision. This could not be completed within the available investigation; flagging as an analog worth further review rather than a confirmed exploit.
