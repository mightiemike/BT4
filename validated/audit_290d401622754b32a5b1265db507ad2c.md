## Analog Found: Hardcoded `MAX_MATCH_NUM` in `MarketSellAssetActuator` Can Cause Guaranteed Order-Matching Failures

### Title
Unchangeable `MAX_MATCH_NUM` constant can force legitimate `MarketSellAsset` transactions to permanently revert - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The reported bug class is a hardcoded numeric limit (`MAX_SLIPPAGE`) that, once exceeded by market conditions, causes an operation to unconditionally revert with no way for anyone to adjust the limit on-chain. The java-tron TRC10 order-book Market module (`MarketSellAssetActuator`) contains the same class of issue: the number of maker orders a single taker transaction is allowed to match against is capped by a hardcoded, non-configurable constant `MAX_MATCH_NUM = 20`. If the match count exceeds this limit, the transaction throws and fails, and there is no on-chain mechanism (unlike a chain parameter/proposal) to raise this value.

### Finding Description
`MarketSellAssetActuator` declares: [1](#0-0) 

`MAX_ACTIVE_ORDER_NUM` has a `@Setter`, but `MAX_MATCH_NUM` does not — it is a fixed, compiled-in constant with no chain-governance path (no `ProposalUtil`/`DynamicPropertiesStore` entry) to change it at runtime, unlike other market parameters such as `getMarketSellFee()` which are proposal-adjustable.

During order matching, `matchOrder()` increments a counter for every maker order consumed and throws once the threshold is crossed: [2](#0-1) 

This exception is a `ContractValidateException`, which propagates out of `matchOrder()`, is not swallowed inside `matchOrder`, and unwinds through `execute()`'s outer try/catch, which marks the transaction `FAILED` and rethrows as `ContractExeException`: [3](#0-2) 

Critically, order creation is persisted to `orderStore`/`marketAccountStore` *before* matching is attempted: [4](#0-3) 

while the taker's balance/token debit (`accountStore.put`, line 148) and successful order persistence only happen *after* `matchOrder()` returns without throwing: [5](#0-4) 

This is directly analogous to the external report: a fixed threshold (there: max acceptable slippage; here: max maker orders matched per taker tx) that market activity can push past, causing an unconditional revert of an otherwise valid, unprivileged, ordinary user operation, with no admin/governance lever to raise the limit — java-tron's version is actually more rigid than the audited contract even after mitigation, since the audited contract at least got an admin-adjustable `maxSlippage`.

### Impact Explanation
Because the price level with the best rate on any TRC10/TRX trading pair is a shared, attacker-writable resource (anyone can place a sell order at that price for a trivial quantity), an attacker can populate a single price level with more than `MAX_MATCH_NUM` (20) tiny maker orders. Any subsequent taker who tries to sell into that price level with a quantity that would need to walk through more than 20 of those orders will have `matchOrderCount > MAX_MATCH_NUM`, causing their transaction to fail every time they resubmit against that price level, as long as the attacker keeps ≥21 tiny orders resident there. This is a low-cost, unprivileged griefing/DoS vector against the TRC10 exchange market feature for a given trading pair/price, and it cannot be remedied without a code change/hard fork since the value is not proposal-configurable, mirroring the "harvesting can get stuck" scenario in the source report but for on-chain trading rather than DeFi yield harvesting.

### Likelihood Explanation
Reachable by any unprivileged account: placing many small sell orders via `MarketSellAssetContract` is a normal, permissionless operation, and the fee for doing so (`getMarketSellFee()`) is comparatively low relative to potentially disrupting the matching of a targeted taker's larger order. No special privileges, and no unusual market conditions (only ordinary order placement) are required to trigger the constant's failure path.

### Recommendation
Make `MAX_MATCH_NUM` a chain parameter adjustable through the existing witness-proposal mechanism (as is done for `getMarketSellFee()` in `ProposalUtil.java`/`DynamicPropertiesStore`), or change the matching logic so that once the cap is hit, the taker order is partially filled and the remainder is placed back on the book (as already happens for other partial-fill code paths) rather than aborting the whole transaction with an exception.

### Proof of Concept
1. Attacker creates 21 `MarketSellAssetContract` orders selling token A for token B at the best available price, each for a minimal non-zero quantity, so they sit consecutively at the head of the price-ordered order list for that pair (`pairPriceToOrderStore`).
2. Victim submits a `MarketSellAssetContract` selling token B for token A with a quantity large enough that filling it fully would require consuming all 21+ of the attacker's orders at that price.
3. `MarketSellAssetActuator.matchOrder()` walks the maker order list, and once `matchOrderCount` exceeds `MAX_MATCH_NUM` (20), it throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")` as shown at [6](#0-5) .
4. The victim's transaction fails every time it is resubmitted against that price level while the attacker maintains ≥21 tiny orders there, and there is no configuration knob to raise the 20-order cap without a network-wide code upgrade.
