## Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting replay/chunk-executor verification accept a corrupted state/hot-state/position-state root — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check that binds a freshly computed `TransactionOutput` (write set, events, gas, status) to the authenticated `TransactionInfo` pulled from backup/ledger storage. It validates `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash`, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that carry the state-tree/hot-state/position-state Merkle roots. This is acknowledged in the code itself with a `TODO(trading-native)` comment stating that "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution." This is the direct structural analog of the external report's root cause: a value that is supposed to be an authoritative, already-final commitment (there, `calc_token_amount`; here, `TransactionInfo`'s checkpoint hashes) is bypassed by a check that validates something else instead of the actual invariant that matters.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  is called from two production-integrity-critical call sites:
1. `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and compares the result against the expected `TransactionInfo` read from backup storage: [2](#0-1) .
2. `execution/executor/src/chunk_executor/mod.rs`, used during chunk-execution verification when applying transaction chunks from state sync / backup restore.

The function's body performs these checks: status match, gas match, write-set hash vs `state_change_hash`, and event-root hash vs `event_root_hash`: [3](#0-2) 

But right before returning `Ok(())`, the code contains this explicit acknowledgment that the checkpoint hashes are never compared: [4](#0-3) 

Meanwhile, `TransactionInfoV1` and the position-state pipeline (`DoStateCheckpoint`, `do_ledger_update.rs`) treat `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class, cryptographically bound commitments that are folded into the `TransactionInfo` hash and therefore into the transaction accumulator root: [5](#0-4) , [6](#0-5) . The `DoStateCheckpoint` workflow computes these roots from execution and cross-checks them against externally supplied "known" hashes when provided [7](#0-6) , showing the checkpoint hash is meant to be a strictly verified, non-optional binding — the same strict binding that `ensure_match_transaction_info` fails to enforce when comparing re-executed output against a previously-persisted `TransactionInfo`.

Because `ensure_match_transaction_info` only checks 4 of the ~7 fields in `TransactionInfoV1`, any code path that relies on this function as its sole cross-check between locally computed execution results and an untrusted/archived `TransactionInfo` will silently accept a transaction whose state-checkpoint root, hot-state root, or (once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) position-state root differs from what local execution actually produced.

### Impact Explanation
This falls squarely within the "Proof And Storage Pivots" scope: VM outputs and transaction infos must survive the executor-to-storage/replay handoff unchanged, and authenticated proof-bearing data (the `TransactionInfo` fetched from backup/archive storage, itself normally authenticated by a `TransactionInfoWithProof`/`LedgerInfo` chain) must be fully validated against locally recomputed values before being trusted. Because the checkpoint-hash fields are silently skipped:
- `replay_on_archive` (used to validate historical mainnet archives / replay-verify CI and audits) can report "verification passed" for a chunk whose state root, hot-state root, or position-state root has diverged from correct VM execution — masking a state-divergence bug or an archive/backup corruption that would otherwise be a hard-fork-class discrepancy.
- Any chunk-executor code path that uses this function to gate acceptance of externally supplied transaction outputs against expected `TransactionInfo` (e.g., during state-sync chunk application/replay) inherits the same blind spot for the checkpoint hash fields, which are exactly the fields that bind a transaction to the committed world-state root.

This is a real gap in proof-integrity checking, self-acknowledged in the code as a known deficiency gating the safe rollout of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. It is High severity because it defeats a designed verification invariant for state-commitment correctness in the exact tooling ("replay-verify") whose job is to catch state divergence.

### Likelihood Explanation
The bug is deterministic and always present — every call to `ensure_match_transaction_info` skips these fields, not just under adversarial conditions. The severity is currently bounded because: (a) the main `state_checkpoint_hash`/`hot_state_checkpoint_hash` divergence would typically also produce a write-set/root-hash divergence detectable elsewhere in most normal flows (though not guaranteed if a bug affects checkpoint computation specifically without touching per-txn write sets), and (b) `position_state_checkpoint_hash`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is explicitly not-yet-enabled per the code comment, meaning the position-root gap is a forward-looking landmine that would become critical the moment that feature is turned on without this fix landing first. I could not fully confirm from the available index whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is already active on mainnet or still gated off; this should be verified directly in a live session since the flag's on-chain status determines whether the position-root gap is already live or still latent.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed values (which must be threaded into `TransactionOutput` or passed as additional parameters, similar to `expected_write_set`/`expected_events`) and `txn_info`'s corresponding fields whenever those hashes are `Some` in the transaction info being verified against. This should be validated and enabled before turning on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the code's own TODO comment specifies.

### Proof of Concept
Conceptual PoC (cannot be executed without a full node/archive environment):
1. Construct or corrupt an archived `TransactionInfo` (or a backup blob feeding `replay_on_archive`) so that `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) is wrong while `state_change_hash`, `event_root_hash`, `gas_used`, and `status` remain correct (e.g., corrupt just the last transaction of a block, which is the one carrying the checkpoint hash, while leaving its write set/events/gas/status untouched).
2. Run `replay_on_archive`'s `execute_and_verify` (or the chunk-executor path calling `ensure_match_transaction_info`) against this data: [8](#0-7) .
3. Observe that `ensure_match_transaction_info` returns `Ok(())` (no error raised) despite the checkpoint hash mismatch, because the function never compares `txn_info.state_checkpoint_hash()` (or the hot/position variants) against a recomputed value — confirmed directly by the code and its own TODO comment at [4](#0-3) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
