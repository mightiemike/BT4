### Title
Replay-verify and chunk-executor consistency check silently ignores state/hot-state/position checkpoint root hashes - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single integrity gate used by chunk replay, replay-verify tooling, and the debugger to confirm that a locally re-executed `TransactionOutput` matches an authenticated/committed `TransactionInfo` (e.g. one fetched from an archive, backup, or another node during state-sync/replay-verify). The function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents via a `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` [1](#0-0)  validates 4 fields (status, gas, write-set hash, event root hash) between a locally computed `TransactionOutput` and an authenticated `TransactionInfo`, but the trailing comment makes clear the comparator deliberately skips the checkpoint hashes: [2](#0-1) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as committed, hash-chained fields [3](#0-2) , and accessor methods exist for all three [4](#0-3) . These fields represent the Merkle/JMT state root produced at a checkpoint boundary and are part of the value that is accumulator-hashed and signed by validators as part of consensus/ledger info. `ensure_match_transaction_info` is called from:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, used during chunk replay / state-sync verification [5](#0-4) 
- `storage/db-tool/src/replay_on_archive.rs` (the `replay-verify` tool that re-executes archived history and confirms it matches ground truth)
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`

Because the checkpoint hashes are skipped, none of these code paths can detect a divergence in the computed state root (the JMT root, hot-state root, or the newer "position" state root used by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) as long as the write-set bytes and events hash the same. A bug in `DoStateCheckpoint`/state-summary computation (e.g., an incorrect JMT update, wrong hot-state root, or wrong position-state root — separate but related code the comment references, at `execution/executor/src/workflow/do_state_checkpoint.rs`) would go completely unnoticed by replay-verify and debugger tooling, even though the on-chain `TransactionInfo`/accumulator root is the authenticated source of truth for what is committed.

This is directly analogous to the seed bug: a validation/consistency check ("max amount" restriction) that exists conceptually as part of the invariant but is missing from one of the code paths that should enforce it (`ensure_match_transaction_info` omits 3 of the 6+ relevant fields defined on `TransactionInfo`), so the bypass silently allows a divergent/incorrect state to be treated as verified.

### Impact Explanation
This breaks the "proof and storage pivot" invariant that "Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding." A node running `replay-verify` (used to confirm a replayed/re-executed ledger history matches the authenticated on-chain record) or the chunk-executor's `verify_execution` (used during fast/state-sync from a chunk with `TransactionInfo`s already fixed by consensus) would report success even when the locally computed state checkpoint root (regular, hot-state, or position state) differs from the authenticated committed root. This is exactly the class of gap the "State-Integrity Gate" calls out: "Wrong accumulator root, Merkle proof, transaction proof, event proof, or state proof accepted as valid," and "Hard-fork-only divergence during commit, replay, restore, or proof verification." A node relying on this check to trust that its replayed state matches mainnet history could silently diverge and continue operating on a corrupted state tree, undetected until some other consumer (e.g. a state proof or query) surfaces the divergence — at which point ledger integrity is already compromised for that node.

### Likelihood Explanation
The gap requires a separate root-cause bug in state-checkpoint computation (JMT root, hot-state root, or position-state root) to actually produce a divergent root; `ensure_match_transaction_info` itself is not exploitable by an unprivileged attacker in isolation — it is a missing defense-in-depth check. The severity is limited to detection failure (silent acceptance) rather than an independently attacker-triggerable state corruption, and the code explicitly flags this as a known, intentional gap pending the position-state-root feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) being enabled. Because of this self-documented status, likelihood of it being unknown to the team is low, but the residual risk (that checkpoint-hash divergence goes unverified in production replay tooling and chunk-executor verification) remains real and unresolved in current code.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when `hot_state_root_in_txn_info` is enabled), and `position_state_checkpoint_hash` (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) between the locally computed checkpoint output and the authenticated `TransactionInfo`, mirroring the enforcement already done for write-set and event root hashes, before any feature that depends on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet.

### Proof of Concept
Not directly exploitable as a standalone PoC without a companion bug producing a divergent checkpoint root; the concrete demonstration is code-level: `ensure_match_transaction_info` at [6](#0-5)  never calls `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`, so any test constructing a `TransactionOutput`/checkpoint whose locally computed root differs from the `txn_info`'s checkpoint hash (but with identical write-set/events/gas/status) will pass this check with `Ok(())`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
