### Title
Deposit Refund Misdirection in `DelegateAction` (Meta Transaction) Execution Causes Relayer Fund Loss — (`File: runtime/runtime/src/actions.rs`)

---

### Summary

When a `DelegateAction` inner action fails on the receiver's shard, the attached deposit is refunded to the **sender** (`sender_id` / Alice), not to the **relayer** who actually paid it. An unprivileged user can craft a `DelegateAction` with a large deposit attached to a function call that is designed to fail, causing the relayer to permanently lose the deposit to the user. The root cause is in nearcore's runtime code: `apply_delegate_action` sets the inner receipt's `predecessor_id` to `sender_id`, which is the account that receives deposit refunds on failure.

---

### Finding Description

In `apply_delegate_action` (`runtime/runtime/src/actions.rs`), the inner receipt spawned from the `DelegateAction` is constructed with `predecessor_id: sender_id.clone()` (Alice): [1](#0-0) 

The code comment immediately below this construction explicitly acknowledges the problem: [2](#0-1) 

When the inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` in `runtime/runtime/src/lib.rs` issues a deposit refund to `receipt.balance_refund_receiver()`: [3](#0-2) 

`balance_refund_receiver()` resolves to the receipt's `predecessor_id`, which is `sender_id` (Alice). However, the deposit was paid by the **relayer** (the signer of the outer transaction), because the relayer's balance is charged for all costs including attached deposits when the outer transaction is converted to a receipt.

The gas refund correctly goes to the relayer (the signer): [4](#0-3) 

But the deposit refund goes to Alice — the wrong party.

The protocol documentation explicitly acknowledges this asymmetry: [5](#0-4) 

---

### Impact Explanation

**Broken invariant:** The party that pays a deposit should receive the refund if the action fails. In meta transactions, the relayer pays the deposit but Alice receives the refund.

**Exact corrupted values:**
- Relayer's balance is permanently reduced by `deposit` amount (paid at transaction processing time, never refunded).
- Alice's balance is permanently increased by `deposit` amount (receives the refund receipt).

This is a direct, protocol-enforced fund transfer from the relayer to Alice on every deliberately-failed meta transaction with an attached deposit.

**Impact category:** Stealing / loss of funds; balance manipulation.

---

### Likelihood Explanation

The attack requires no special privileges:

1. Alice creates a `DelegateAction` with a `FunctionCall` action that has a large `deposit` and is designed to fail (e.g., calls a non-existent method, or a contract that panics).
2. Alice submits this `SignedDelegateAction` to any relayer off-chain.
3. The relayer wraps it in a transaction and submits it on-chain, paying the deposit from their balance.
4. `apply_delegate_action` passes all on-chain validation (valid signature, valid nonce, valid key) and creates the inner receipt with `predecessor_id = Alice`.
5. The inner receipt is routed to the receiver's shard and fails.
6. The deposit refund receipt is issued to Alice.

There is no on-chain guard that prevents Alice from attaching an arbitrarily large deposit to a function call inside a `DelegateAction`. The relayer's only defense is off-chain inspection of the `DelegateAction` content before submission — but even that is insufficient if Alice can drain her contract state between the relayer's check and the on-chain execution (a race condition analogous to the external report).

---

### Recommendation

The protocol should route deposit refunds for inner receipts spawned by `DelegateAction` to the **relayer** (the signer of the outer transaction), not to `sender_id`. Concretely, in `apply_delegate_action`, the inner receipt should carry the relayer's account ID as the balance refund receiver, overriding the default predecessor-based routing. This would require either:

- A new receipt field (e.g., `balance_refund_override`) that explicitly names the refund recipient, or
- Setting `predecessor_id` of the inner receipt to the relayer's account ID (though this changes the `predecessor_id` visible to the contract, which has other implications).

Additionally, the protocol should consider enforcing a maximum deposit limit on `DelegateAction` inner actions, or requiring the relayer to explicitly acknowledge the deposit amount before it is charged.

---

### Proof of Concept

**Setup:**
- Relayer account: `relayer.near` (balance: 1000 NEAR)
- Alice account: `alice.near` (balance: 0 NEAR)
- Receiver: `contract.near` (any contract with a method that panics or does not exist)

**Steps:**

1. Alice constructs and signs a `DelegateAction`:
   ```
   DelegateAction {
     sender_id: "alice.near",
     receiver_id: "contract.near",
     actions: [FunctionCall { method: "nonexistent_method", deposit: 500 NEAR, gas: 100 TGas }],
     nonce: <valid>,
     max_block_height: <valid>,
     public_key: <alice's key>,
   }
   ```

2. Alice sends the `SignedDelegateAction` to the relayer off-chain.

3. Relayer wraps it in a transaction (signer = `relayer.near`) and submits it. The relayer's balance is charged 500 NEAR for the deposit plus gas costs.

4. On Alice's shard, `apply_delegate_action` validates the action (signature ✓, nonce ✓, key ✓) and creates an inner receipt:
   ```
   Receipt {
     predecessor_id: "alice.near",   // ← Alice, not the relayer
     receiver_id: "contract.near",
     actions: [FunctionCall { deposit: 500 NEAR, ... }],
     signer_id: "relayer.near",
   }
   ```

5. The inner receipt is routed to `contract.near`'s shard. The function call fails (`nonexistent_method` does not exist).

6. `refund_unspent_gas_and_deposits` issues:
   - Gas refund → `relayer.near` (signer) ✓
   - Deposit refund (500 NEAR) → `alice.near` (predecessor = `balance_refund_receiver()`) ✗

**Result:**
- `relayer.near` balance: ~500 NEAR (lost 500 NEAR deposit, received gas refund)
- `alice.near` balance: 500 NEAR (gained 500 NEAR from deposit refund)

The relayer has been drained of 500 NEAR with no recourse. Alice can repeat this attack indefinitely with different nonces until the relayer's balance is exhausted. [6](#0-5) [7](#0-6) [8](#0-7)

```rust
pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

    // Generate a new receipt from DelegateAction.
    let new_receipt = Receipt::V0(ReceiptV0 {
        predecessor_id: sender_id.clone(),
        receiver_id: delegate_action.receiver_id().clone(),
        receipt_id: CryptoHash::default(),

        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: action_receipt.signer_id().clone(),
            signer_public_key: action_receipt.signer_public_key().clone(),
            gas_price: action_receipt.gas_price(),
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: delegate_action.get_actions(),
        }),
    });

    // Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas.
    // If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction.
    // Gas is refunded to the signer, this is Relayer.
    // Some contracts refund the deposit. Usually they refund the deposit to the predecessor and this is sender_id/Sender from DelegateAction.
    // Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit.

    let prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, action_receipt.actions())?;
    let required_cost = receipt_required_cost(apply_state, &new_receipt)?;
    // This gas will be burnt by the receiver of the created receipt.
    // Compute costs of that are not relevant at this point, the "used" gas is
    // only reserved for execution later, potentially on a different shard.
    result.gas_used = result.gas_used.checked_add_result(required_cost.gas)?;
    // This gas was prepaid on Relayer shard. Need to burn it because the receipt is going to be sent.
    // gas_used is incremented because otherwise the gas will be refunded. Refund function checks only gas_used.
    result.gas_used = result.gas_used.checked_add_result(prepaid_send_fees.gas)?;
    result.gas_burnt = result.gas_burnt.checked_add_result(prepaid_send_fees.gas)?;
    result.compute_usage = safe_add_compute(result.compute_usage, prepaid_send_fees.compute)?;
    result.new_receipts.push(new_receipt);

    Ok(())
}
```

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
