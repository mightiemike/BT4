### Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` RPC methods allow any caller to halt sequencer commitment submission - (File: `crates/sequencer/src/rpc.rs`)

### Summary
The sequencer's public JSON-RPC server exposes `citrea_haltCommitments` and `citrea_resumeCommitments`, which toggle whether the sequencer submits `SequencerCommitment`s to the DA layer. Unlike the sibling method `publish_test_block`, which explicitly checks `self.context.test_mode` before acting, these two methods perform **no authorization, no role check, and no protected-method gating** before forwarding the halt/resume signal to the sequencer runner.

### Finding Description
`SequencerRpc` is registered as a plain, unauthenticated method set merged into the node's RPC module [1](#0-0) . The trait declares `halt_commitments` / `resume_commitments` next to normal, permissionless methods like `eth_sendRawTransaction` [2](#0-1) .

The implementation of these two handlers does nothing but forward a message to the runner: [3](#0-2) 

Contrast this with `publish_test_block`, in the very same `impl` block, which is guarded by a `test_mode` check before it is allowed to run: [4](#0-3) 

The only access-control layer present anywhere in the RPC stack is the `Auth` middleware, and it protects an explicit allow-list of three unrelated backup methods (`backup_create`, `backup_validate`, `backup_info`); every other method, including `citrea_haltCommitments`/`citrea_resumeCommitments`, passes straight through untouched: [5](#0-4) 

This is the direct analog of the reported bug class: a sensitive, state-mutating action (`halt`/`resume` sequencer commitments) that should require an authorization check (equivalent to "KYC approved" in the original report, here "is this an authorized operator call") but instead is reachable by any unauthenticated caller who can reach the sequencer's RPC port, exactly as `/api/v1/otp` and friends were reachable without a KYC check in the original finding.

### Impact Explanation
Calling `citrea_haltCommitments` breaks the equality that the sequencer should keep submitting the sequence of `SequencerCommitment`s that anchor L2 state to the DA layer at a bounded cadence. Halting commitments stalls the entire proving pipeline (batch prover has nothing new to prove, light client prover has nothing new to verify), effectively freezing the rollup's finality progress without any Bitcoin-side, sequencer-authorized, or governance action behind it. This matches the "High" impact bucket: an unauthenticated JSON-RPC call that mutates node state and bypasses `Auth`.

### Likelihood Explanation
Likelihood depends entirely on network exposure of the sequencer's RPC endpoint. If the endpoint is bound to a public interface (as is common for JSON-RPC endpoints meant to accept `eth_sendRawTransaction`), the call requires no credentials, no signature, and no special role — any client that can reach the port can send it. I could not fully verify from the indexed files what the default bind address is in every deployed configuration (`rollup_config.toml` files are excluded from analysis scope per the rules, and I was unable to confirm the exact default `bind_host` value used by production/mainnet configs before running out of iterations), so the exposure surface in a specific deployment is not fully confirmed — but the code itself contains no compensating check, so exploitability is bound only by network reachability, not by any application-layer control.

### Recommendation
Add an authorization check to `halt_commitments` and `resume_commitments` (e.g., require the `Auth` API-key middleware to protect these methods, or add them to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`), mirroring the `test_mode` gate already used for `publish_test_block`. At minimum, these methods should not be reachable without some form of authenticated/privileged access.

### Proof of Concept
1. Start a Citrea sequencer node with its RPC server exposed (default configuration merges `SequencerRpc` methods into the public `rpc_module`, see `crates/sequencer/src/lib.rs:172`).
2. As an unauthenticated network client, send:
```json
{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}
```
3. Observe the RPC call succeeds with `Ok(())` and the sequencer runner receives `SequencerRpcMessage::HaltCommitments` (`crates/sequencer/src/rpc.rs:408-414`), halting further commitment submission with no credentials presented.
4. Later, resume with `citrea_resumeCommitments`, again with no credentials — demonstrating full unauthenticated control over the sequencer's commitment-submission state machine.

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }
