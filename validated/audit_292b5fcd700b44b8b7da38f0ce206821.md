### Title
Council-signed `BatchProofMethodId` (H1) permanently unprovable if a lower-activation-height body is inscribed after a higher one due to unsorted-append `.last()` check - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`run_l1_block` in `crates/light-client-prover/src/circuit/mod.rs` derives `last_activation_height` from `BatchProofMethodIdAccessor::get(...).last().0` [1](#0-0) , and `BatchProofMethodIdAccessor::insert` is a strict append-only `Vec::push` with no sort-on-insert [2](#0-1) . `DataOnDa::BatchProofMethodId` processing does not check `blob.sender()` at all (unlike `Complete`/`Aggregate`/`SequencerCommitment` variants which check `batch_prover_da_public_key`/`sequencer_da_public_key`), so validity is gated purely by the 3-of-5 council signature check, not by who inscribes the transaction. Because the light-client circuit consumes blobs strictly in the order `da_verifier.verify_transactions` returns them (DA block/tx order), an unprivileged party who has obtained two genuinely council-signed bodies (H1<H2) can cause H2's blob to be mined/processed before H1's, permanently poisoning the monotonic `last_activation_height` gate and dropping H1 forever.

### Finding Description
**Broken binding:** For every genuinely council-signed `(activation_l2_height, method_id)` pair the council authorized, that pair should end up present in `BatchProofMethodIdAccessor::get(working_set)`. I.e. `∀ signed body b: b ∈ authorized ⇒ (b.activation_l2_height, b.method_id) ∈ accessor_vec`.

**Trace:**
1. In `run_l1_block`'s blob loop, on `DataOnDa::BatchProofMethodId(batch_proof_method_id)`:
   - `last_activation_height = BatchProofMethodIdAccessor::get(...).last().0` [3](#0-2) .
   - If `batch_proof_method_id.body.activation_l2_height <= last_activation_height`, the blob is skipped with `continue` — no error is raised, no reordering/queueing is attempted [4](#0-3) .
   - Only after passing this check are chain-id and the council signatures (`verify_method_id_security_council`) checked, and only then is `BatchProofMethodIdAccessor::insert` called, which simply does `method_ids.push((activation_l2_height, method_id))` [2](#0-1) .
   - Note that this variant, unlike `Complete`/`Aggregate` (checked against `batch_prover_da_public_key`) and `SequencerCommitment` (checked against `sequencer_da_public_key`), has **no sender check** [5](#0-4) [6](#0-5) . Any Bitcoin transaction inscribing valid council-signed bytes is accepted regardless of inscriber, which is what lets an unprivileged attacker (who merely possesses the signed body+signature bytes, e.g. from mempool observation or leaked pre-publication) submit it themselves with a competitive fee.
2. Because `last_activation_height` monotonically only grows and the vector is appended without sorting, once H2 is inserted first, any subsequently-arriving genuinely-signed H1 body (H1 < H2) fails `activation_l2_height <= last_activation_height` and is dropped permanently — there is no re-ordering, retry, or insert-sorted recovery path anywhere in `BatchProofMethodIdAccessor` or `run_l1_block`.
3. Downstream, `process_complete_proof` selects the method id for a given L2 height via `binary_search_by_key` over this same vector [7](#0-6) , which assumes the vector is sorted ascending by activation height (a property normally guaranteed by the monotonic `last()` check, but which here causes H1 to simply vanish rather than be inserted in the correct sorted position). Consequently, any genuine batch proof generated by the batch prover for L2 heights in `[H1, H2)` using the H1 method id will be verified in the light client circuit against the **wrong** (pre-H1) method id and rejected by `Z::verify` [8](#0-7) , making a truly council-authorized state transition permanently unprovable.

No existing guard intervenes: there is no sender check for this DataOnDa variant, no timestamp/height-based reordering, and no way to "correct" the vector once a higher height has been recorded — `last_activation_height` never decreases.

### Impact Explanation
This breaks PROOF_SOUNDNESS in the "true state transition made unprovable" sense: batch proofs correctly produced by the batch prover under the H1 method id for L2 heights `[H1, H2)` will be permanently rejected by every honest light-client prover, since the accessor's ordered vector never contains H1. This stalls light-client progress for that L2 height range and can require a full governance-level recovery (re-signing at a new, still-higher height) to unstick, which itself risks further races. The attack costs only one Bitcoin inscription+fee and is repeatable for any future council method-id rotation the attacker can observe in advance, giving it a Critical blast radius across all honest light-client-prover nodes for the affected activation window.

### Likelihood Explanation
The exploit is gated entirely on the attacker being able to observe a validly-signed higher-activation body (H2) *before* the lower one (H1) is mined, and on paying differential BTC fees to get it mined first. Because the `BatchProofMethodId` DataOnDa variant has no sender restriction (unlike the other variants), any party possessing the valid signed bytes can inscribe them — this only requires normal Bitcoin fee payment, no privileged key. The precondition ("attacker has observed two genuine council-signed bodies with H1<H2") is stipulated by the audit question; whether council operational practice ever exposes both signed bodies to the public before sequential inscription is a real-world/process question outside this repo, but nothing in the code prevents the described sequence once that precondition holds.

### Recommendation
- Insert into `BatchProofMethodIdAccessor` in **sorted position** (or reject/queue out-of-order lower heights instead of silently dropping and losing them), and/or track "highest height seen" separately from "insert only if committee-approved height is truly new," while still admitting lower activation heights that arrive later, as long as they don't overlap with an already-activated range.
- Add a sender or nonce/monotonic-sequence-number check to the `BatchProofMethodId` DataOnDa path, or require inscriptions to reference the previous method-id entry so height ordering can't be forged by mere fee-based reordering.
- Alternatively, have the council sign a strictly ordered batch (all pending upgrades together) rather than independent per-height bodies, removing the reordering degree of freedom.

    pub fn insert(activation_l2_height: u64, method_id: [u32; 8], working_set: &mut WorkingSet<S>) {
        let key = Self::key();
        let mut method_ids = Self::get(working_set).unwrap_or_default();

        let value: StorageValue = borsh::to_vec(&method_ids)
