Based on my analysis, I found a concrete, code-acknowledged integrity gap in transaction-info verification used by Aptos's replay-verify and execution-verification tooling.

### Title
`TransactionOutput::ensure_match_transaction_info` skips verifying state/hot-state/position checkpoint hashes, letting replay-verify tooling accept a corrupted or diverging state root as valid - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by every "verify local execution against the authenticated, accumulator-committed `TransactionInfo`" code path in the codebase (chunk-executor's `verify_execution`, `db-tool`'s `replay_on_archive`, `aptos-debugger`, and the CLI). It checks status, gas used, write-set hash, and event-root hash, but — as the code itself documents — it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the locally recomputed values.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and validates status, gas, write-set hash and event-root hash, but ends with an explicit TODO instead of a check: [2](#0-1) 

This is the sole comparison invoked by:
- `ChunkExecutorInner::verify_execution`, the dedicated "verify-execution" replay path: [3](#0-2) 
- `db-tool`'s archive replay-verify tool `execute_and_verify`: [4](#0-3) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` (same call site pattern).

The `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields on `TransactionInfo`/`TransactionInfoV1` are the authenticated commitments to the Sparse-Merkle/JMT world-state root (and now the native-position state root gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), bound into the ledger via the transaction accumulator (`TransactionInfoV1` fields shown at [5](#0-4) , feature flags at [6](#0-5) ). These hashes are exactly the values that state-proof and restore correctness depend on. Because `ensure_match_transaction_info` never recomputes and compares them, any of these verification tools can locally re-execute a transaction, produce a write set/events that hash-match, yet have a state root (via a corrupted JMT update, a buggy hot-state or position-state computation) that diverges from the trusted, consensus-signed `TransactionInfo`, and still report "verified"/"replay succeeded".

### Impact Explanation
This breaks the "Committed state that differs from the correct VM result or corrupts durable ledger data" and "Authenticated API or state-view output bound to the wrong version, object, or proof context" invariants for any operator relying on `verify_execution`/`replay_on_archive`/`aptos-debugger` to attest that a restored or replayed database's state matches the authenticated chain history. A node operator (or auditor) using these tools to validate a backup/restore or a hard-fork replay would get a false "match" even though the actual Merkle state root (or the new native-position root once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` ships) silently diverged — undermining the entire purpose of these verification tools and potentially masking state corruption introduced by bugs elsewhere in checkpoint/restore code.

### Likelihood Explanation
This is not a hypothetical: the gap is explicitly flagged by an in-repo TODO comment acknowledging it must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [7](#0-6) , confirming the code owners are aware the check is currently absent for all checkpoint hashes (not just the new position one), and it is on the code path used today by the shipped verify/replay tooling.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when present), and `position_state_checkpoint_hash` (when present) against the values carried in `txn_info`, failing verification on mismatch, consistent with how write-set and event-root hashes are already checked.

### Proof of Concept
Not applicable as an exploit PoC (this is a verification-omission bug, not an executable exploit): the proof is the direct code inspection above — `ensure_match_transaction_info`'s body only compares `status`, `gas_used`, `write_set` hash, and `event_root_hash`, with the trailing comment confirming no checkpoint-hash checks exist, while its only callers use it as the complete/only correctness check for their respective verify-replay flows.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );
