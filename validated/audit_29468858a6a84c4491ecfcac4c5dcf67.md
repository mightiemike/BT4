### Title
Light client circuit accepts a fabricated "genesis" light-client proof for any block by omitting `previous_light_client_proof`, forging a false light-client state - ([File: crates/bitcoin-da/src/verifier.rs], [File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`BitcoinVerifier::verify_header_chain` uses `INITIAL_MAINNET_STATE`/`INITIAL_TESTNET4_STATE`/`INITIAL_SIGNET_STATE` as the fallback "genesis" DA checkpoint whenever `latest_da_state` is `None` [1](#0-0) . `latest_da_state` is `None` precisely when the caller supplies `previous_light_client_proof: None` in `LightClientCircuitInput` [2](#0-1) . Nothing in the guest circuit checks that the block height in `da_block_header` actually matches the network's configured `initial_da_height`; that check only exists on the native/host side when building input, not inside the ZK-proved circuit [3](#0-2) . This mirrors the `setAddress`/`_updateImpl` class of bug: a "no previous state" sentinel is trusted to mean "this really is the very first entry," and an unprivileged party can supply that sentinel out of context to make the state machine re-initialize from scratch, discarding/ignoring the real accumulated state.

### Finding Description
`LightClientProofCircuit::run_circuit` treats `input.previous_light_client_proof == None` as authoritative proof that this is the first-ever light client proof for the chain, and:
- Passes `None` as `latest_da_state` to `verify_header_chain`, which then anchors the chain-of-work/header validation to the network's constant initial state rather than to the true, currently-accumulated chain state [4](#0-3) .
- Calls `run_l1_block` with `previous_light_client_proof_output = None`, which resets `(last_l2_state_root, last_l2_height, last_sequencer_commitment_index)` to `(l2_genesis_root, 0, 0)` and re-`initialize`s `BatchProofMethodIdAccessor` [5](#0-4) .
- Only requires that the JMT storage passed in is fresh — enforced by `assert_eq!(lcp_state_root_transition.init_root, LCP_JMT_GENESIS_ROOT)` [6](#0-5) .

Because the ZK circuit is permissionless to run (anyone with the risc0 guest binary and the correct `light_client_proof_method_id` can generate a proof — there is no signature or role check on who invokes `run_circuit`), an attacker can:
1. Provide `previous_light_client_proof_output = None`.
2. Provide a `da_block_header` at height `INITIAL_MAINNET_STATE.block_height + N` (or the corresponding testnet/signet checkpoint) for any `N`, together with a valid, real chain-of-work-consistent header chain from that fixed checkpoint (this is just public Bitcoin header data, requiring no special role or key).
3. Supply a fresh JMT storage (`ZkStorage::new()`), satisfying `lcp_state_root_transition.init_root == LCP_JMT_GENESIS_ROOT`.

The circuit will happily accept this and emit a `LightClientCircuitOutput` claiming `(l2_state_root, last_l2_height, last_sequencer_commitment_index) = (l2_genesis_root, 0, 0)` for a DA block that is **not** actually the network's true starting point, and re-initialize `BatchProofMethodIdAccessor` with the compiled-in initial method IDs — silently discarding whatever sequencer commitments, batch proofs, and method-id upgrades were legitimately anchored on the real chain up to that point. This produces a second, divergent, but individually "valid" (ZK-verifiable) light-client proof chain for the same network/method-id, i.e., two honest verifiers relying on different "first" proofs would diverge — the equality that should hold, `journal_A(L1_height) == journal_B(L1_height)` for the unique correct light-client proof chain, is broken.

### Impact Explanation
This breaks the "honest nodes converging on an unproved root" / "a light client proof split across honest provers" invariant explicitly called out in scope. The light client proof's core purpose is to feed the proven L2 state root to Citrea's Bitcoin Bridge (Clementine), which is verified inside Clementine's bridge proof during a challenge [7](#0-6) . A forged/rebased LCP chain that starts state fresh at an attacker-chosen later DA height, backed by a legitimately-ZK-verifiable proof, is exactly the "false state transition proved" scenario in scope, since it produces a proof that a downstream verifier (which only checks the method-id and that the proof verifies) cannot distinguish from the canonical chain without external knowledge of which L1 height is the "true" `initial_da_height`.

### Likelihood Explanation
Generating the proof requires only public Bitcoin data (a valid PoW header chain segment from the hardcoded checkpoint) and access to the risc0 guest — no sequencer, prover, security council, or Clementine role/keys are needed, since anyone can run the permissionless guest binary. This satisfies the "unprivileged attacker" requirement of the rules. The main practical constraint is producing a valid Bitcoin header chain segment with correct proof-of-work from the fixed genesis checkpoint to the target height, which is feasible on lower-difficulty networks (regtest/signet/devnet, where the code explicitly notes "it can start from anywhere" [8](#0-7) ) and is a public-data replay on mainnet/testnet (no new hashpower needed, since the headers already exist on the real chain).

### Recommendation
The guest circuit itself (not just the native/host input builder) must bind the "no previous proof" case to the network's compiled-in `initial_da_height`/checkpoint height, rejecting any `da_block_header` whose height doesn't match the expected genesis height when `previous_light_client_proof` is `None`. Equivalently, do not let `None` universally mean "trust this as the genesis state" — require the checkpoint height to be a circuit-level constant checked against `da_block_header.height()`.

### Proof of Concept
1. Take the compiled-in `INITIAL_MAINNET_STATE` (or testnet4/signet) checkpoint used in `crates/bitcoin-da/src/verifier.rs`.
2. Fetch the real Bitcoin header chain from that checkpoint height up to an arbitrary later height `H` (public data, e.g. via any Bitcoin node/API).
3. Build a `LightClientCircuitInput` with `previous_light_client_proof: None`, `da_block_header` = the header at height `H`, and a `completeness_proof`/`inclusion_proof` for that block (can be empty/trivial if the block has no relevant reveal transactions).
4. Run the guest (`LightClientProofCircuit::run_circuit`) with a fresh `ZkStorage::new()`.
5. Observe a valid, ZK-verifiable `LightClientCircuitOutput` with `last_l2_height = 0`, `l2_state_root = l2_genesis_root`, and freshly re-initialized `BatchProofMethodIdAccessor`, anchored at DA height `H` instead of the true initial height — demonstrated functionally by the existing test `test_light_client_circuit_valid_da_valid_data`, which already shows `previous_light_client_proof: None` being accepted together with an arbitrary `MockBlockHeader::from_height(1)` with no height/checkpoint validation in-circuit [9](#0-8) .

# The Light Client Circuit
This document describes the logic and structure of light client proofs, which allow a verifier to confirm that an L2 state committed to by the sequencer is valid, using information included in a DA (Data Availability) block. Each proof builds on the previous one, forming a verifiable chain of state transitions. Verifying a single proof attests that, for the given Bitcoin chain up to that DA block, the L2 state produced by the circuit is correct, verified, and consistent with the on-chain commitments. 

The light client proof's main use case is to provide the L2 state root to Citrea's Bitcoin Bridge, [Clementine](https://citrea.xyz/clementine_whitepaper.pdf). The light client proof is verified inside Clementine's Bridge Proof in case of a challenge to one of the bridge operators.
