### Title
Cross-shard receipt validation failure causes a transaction-triggered node panic instead of a graceful rejection - (File: chain/chain/src/runtime/mod.rs)

### Summary
`Runtime::apply` validates every **incoming** (cross-shard) receipt with `validate_receipt(..., ExistingReceipt)` before executing it, and any validation failure is mapped straight into `RuntimeError::ReceiptValidationError` and propagated out of `apply` [1](#0-0) . The chunk-apply call site in `chain/chain/src/runtime/mod.rs` treats this `RuntimeError` variant as an unrecoverable condition and calls `panic!("{}", e)`, explicitly marked with `// TODO(#2152): process gracefully`, i.e., the developers already know this is not handled safely [4](#0-3) .

### Finding Description
This mirrors the structure of CVE-2018-12893: a defensive "safety check" (added to catch an invalid/inconsistent condition) can, due to an oversight, actually be triggered by an unprivileged, guest-controlled input, and the response to that check firing is to crash the whole component rather than fail gracefully.

In nearcore, `ReceiptValidationError` is explicitly documented as reachable through malicious behavior: the comment on the enum states "The incoming receipt didn't pass the validation, it's likely a malicious behavior" [5](#0-4) . Receipts that a shard receives as "incoming" are outgoing receipts generated by actions on *other* shards during the previous chunk's apply — i.e., they are the direct downstream product of a single submitted transaction's actions (e.g., a `FunctionCall` action that creates a cross-contract promise/receipt, per `action_function_call` in `runtime/runtime/src/function_call.rs:31`, or a `Transfer`/`DeleteAccount` refund receipt). New receipts generated within a chunk are indeed checked at creation time via `validate_receipt(..., NewReceipt)` inside `apply_action_receipt`, but on failure that check is caught and converted into a normal `ActionErrorKind::NewReceiptValidationError`, a graceful per-action failure [6](#0-5) . However, the `ExistingReceipt` check performed later in `process_incoming_receipts`/`process_delayed_receipts` when the receipt is actually consumed on the receiving shard is *not* caught gracefully at the `apply()` boundary for incoming receipts — it is returned as a hard `RuntimeError` that the caller `panic!()`s on [1](#0-0) , [2](#0-1) .

The `ValidateReceiptMode::ExistingReceipt` doc comment itself notes: "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed" (referencing `near/nearcore#12606`) [7](#0-6) , confirming that receipts violating `NewReceipt`-time limits can still slip through to become "incoming" on another shard, and the `ExistingReceipt` validation path is intentionally looser specifically to tolerate that. Any input path where the loosened `ExistingReceipt` checks are *still* violated (any of `InvalidPredecessorId`, `InvalidReceiverId`, `InvalidSignerId`, `InvalidDataReceiverId`, `ReturnedValueLengthExceeded`, `NumberInputDataDependenciesExceeded`, `ActionsValidation`, `ReceiptSizeExceeded`, `InvalidRefundTo` per `ReceiptValidationError` [8](#0-7) ) turns a single-shard, single-transaction-derived defect into a hard panic on every validator that must apply that receiving shard's chunk — i.e., a chunk-apply crash reachable indirectly from a transaction submitted by an ordinary, unprivileged signer.

### Impact Explanation
If a crafted transaction (or the interaction of `NewReceipt`-time validation gaps with looser `ExistingReceipt` validation) manages to produce an outgoing receipt that passes creation-time validation on the sending shard but fails `ExistingReceipt` validation on the receiving shard, every validator/node applying that receiving shard's chunk hits the same `panic!("{}", e)` at `chain/chain/src/runtime/mod.rs:372`. Because this is deterministic state-transition code executed identically by all honest nodes, this is a **transaction-triggered halt**: the affected shard (and potentially the chain, depending on shard-tracking topology) stops making progress until the panic path is patched and nodes are rolled/forked past it — squarely inside the accepted "transaction-triggered halt" impact category.

### Likelihood Explanation
Exploitability is **not proven** here — I found the explicit code path and the TODO acknowledging it is unsafe, and the codebase's own comments confirm that receipt-validation-limit bugs allowing malformed receipts to reach the `ExistingReceipt` stage have existed in the past (`near/nearcore#12606`, referenced directly in `verifier.rs`) [7](#0-6) . I could not, within this investigation, construct a concrete transaction/action sequence in this snapshot that currently produces a receipt passing `NewReceipt` validation but failing `ExistingReceipt` validation — that would require deeper analysis of every action-receipt construction path (e.g., delegate actions, refunds, promise chaining) to find a currently-unpatched discrepancy between the two validation modes. The vulnerability class (a documented "should never happen, but if it does, we panic" gap that historically *has* been triggered by real receipt-limit bugs) is real and reachable in principle from ordinary transactions; whether a *currently* exploitable input exists is unverified.

### Recommendation
Treat `RuntimeError::ReceiptValidationError` (and `RuntimeError::UnexpectedIntegerOverflow`) returned from `Runtime::apply` for incoming/delayed receipts as a recoverable, per-receipt failure (e.g., skip/refund the offending receipt and record a failed outcome) instead of `panic!()`ing at the call site in `chain/chain/src/runtime/mod.rs`, closing out the existing `TODO(#2152)`. Additionally, audit all receipt-construction paths to ensure `NewReceipt`-time validation is strictly at least as strong as `ExistingReceipt`-time validation, so no currently valid transaction can produce a receipt that fails validation only after being handed to another shard.

### Proof of Concept
Not constructed — reaching this panic requires identifying a live receipt-construction path (e.g., via delegate/refund/promise chaining) where an action passes `ValidateReceiptMode::NewReceipt` checks in `apply_action_receipt` but the resulting receipt fails `ValidateReceiptMode::ExistingReceipt` checks in `process_incoming_receipts` on the receiving shard. This would need targeted fuzzing/differential testing of `validate_action_receipt`/`validate_actions_with_mode` between the two modes, which was out of scope for this static review.
