## Title
L1 handler proposable-index ordering lets a well-funded L1 sender flood the sequencer with cheap L1→L2 messages, starving genuine bridge messages behind the fixed per-block cap - ([File: crates/apollo_l1_events/src/transaction_manager.rs])

## Summary
Every block, the batcher pulls L1Handler transactions from the `TransactionManager`'s `proposable_index`, capped at `max_l1_handler_txs_per_block` [1](#0-0) . The index is a global, protocol-wide FIFO structure ordered by scrape timestamp (arrival order) [2](#0-1) , and `get_txs` always drains it from the oldest entry forward, subject only to a cooldown filter [3](#0-2) . This is functionally the same "shared, protocol-wide budget" pattern flagged in the Linea report: a single quota (`max_l1_handler_txs_per_block`) is exhausted every block by whichever L1 messages happen to be oldest/earliest in the queue, with no per-sender fairness or prioritization.

## Finding Description
Any L1 account can call `sendMessageToL2` on the Starknet core contract at minimal cost (gas + `MAX_L1_MSG_FEE`-bounded message fee) to enqueue an `L1HandlerTransaction`. On L2, these events are recorded into `TransactionManager::records` and indexed by scrape timestamp in `proposable_index` [2](#0-1) . The batcher's `ProposeTransactionProvider` requests up to `max_l1_handler_txs_per_block` such transactions per block before switching to mempool transactions [1](#0-0) , and this is a fixed, statically configured cap shared by every L1 message regardless of origin, value, or urgency .

Because `get_txs` walks the `proposable_index` strictly in arrival order (oldest-cooldown-passed first) and only skips already-staged entries [3](#0-2) , an attacker who continuously sends a stream of cheap `sendMessageToL2` calls (e.g., targeting a no-op/self-contract entry point with minimal payload) can keep the queue permanently backlogged with attacker-controlled transactions. Every block, the fixed quota is consumed entirely by the attacker's earlier-queued spam messages before any transaction submitted later by a genuine user (e.g., a bridge deposit `L1HandlerTransaction` created by a real ETH/token deposit) gets a chance to be pulled, exactly mirroring the Linea rate-limiter DoS: a shared, capped, FIFO-style resource can be monopolized by a well-funded attacker to indefinitely delay legitimate use of the same channel.

Unlike a normal mempool (which has fee-escalation/eviction and per-account fairness logic, see `apollo_mempool/src/mempool.rs`), the L1 handler channel has no fee market, no eviction, and no priority scheme — the cap (`max_l1_handler_txs_per_block`) plus strict FIFO ordering is the entire admission-control mechanism, making it structurally analogous to Linea's rate limiter that could be exhausted every period by a well-funded attacker.

## Impact Explanation
While each individual L1→L2 message eventually gets processed (there's no permanent loss like a hard rate-limit rejection), sustained flooding can indefinitely delay processing of genuine bridge/deposit messages, which is the same "network unable to confirm new transactions [of that class]" outcome called out as an acceptable impact category. Users' L1→L2 messages (e.g., deposits, cross-layer calls) remain unconfirmed on L2 for as long as the attacker keeps the queue backlogged, which can be sustained indefinitely at a bounded but nontrivial L1 gas+fee cost — a lower bar than exhausting Linea's ETH-denominated rate limit, since the attacker only needs cheap calldata-sized L1 transactions, not locked capital.

## Likelihood Explanation
Likelihood is *bounded by cost*: the attacker must continuously pay L1 gas plus the required `MAX_L1_MSG_FEE`-scoped fee for every spam message, every block, indefinitely, to keep genuine messages starved (a "well-funded attacker," matching the report's own threat model). This is a lower bar than the Linea report's requirement to lock/round-trip full rate-limit-sized ETH amounts, but it is still an ongoing operational cost, not a one-shot exploit. No special privileges are needed — this is reachable by any unprivileged L1 message sender.

## Recommendation
- Consider adding fairness/anti-spam controls to `proposable_index`/`TransactionManager::get_txs` (e.g., per-sender rate limiting, higher fee-based prioritization, or round-robin across senders) rather than strict global FIFO order gated only by a fixed `max_l1_handler_txs_per_block`.
- Alternatively, decouple `max_l1_handler_txs_per_block` sizing/monitoring from a fixed constant and add alerting/backpressure so operators can detect and respond to sustained L1-handler-queue backlogs (mirroring Linea's own "monitoring for abuse" mitigation).
- Any change should be validated end-to-end against consensus (both `ProposeTransactionProvider` and `ValidateTransactionProvider` must stay consistent, see `crates/apollo_l1_events/src/l1_events_provider.rs`).

## Proof of Concept
1. Attacker repeatedly calls `sendMessageToL2` on L1 with minimal calldata/fee, submitting far more messages per unit time than `max_l1_handler_txs_per_block` allows the sequencer to drain per block.
2. Each message is scraped and inserted into `TransactionManager::proposable_index` keyed by scrape timestamp [2](#0-1) .
3. Every block, `ProposeTransactionProvider` calls `get_l1_handler_txs` which is capped at `max_l1_handler_txs_per_block` and always drains the oldest un-staged entries first [4](#0-3) , [3](#0-2) .
4. As long as the attacker keeps producing more messages per block than the cap, and their messages remain queued earlier (or at comparable rate) to a genuine user's deposit message, the genuine message is pushed indefinitely behind the backlog and never reaches the front of the FIFO queue within any given block, confirmed by the existing test `get_txs_happy_flow`/`get_txs_timestamp_cutoff_*` showing strict oldest-first draining semantics [5](#0-4) .

Note: I could not fully verify from the index whether there is any additional per-sender or fee-based deprioritization elsewhere in the batcher/consensus pipeline that might mitigate this (e.g., in `apollo_batcher_config` sizing logic or a not-indexed part of `transaction_manager.rs`); a Devin session with full repository access would be needed to confirm there is no such safeguard before treating this as conclusively unmitigated.

    pub fn get_txs(&mut self, n_txs: usize, now: u64) -> Vec<L1HandlerTransaction> {
        // Oldest        Now.sub(timelock)     Newest       Now
        //  |<---  passed  --->|                 |           |
        //  |<--- cooldown --->|                 |           |
        // t-------------------------------------------------->
        let cutoff = now.saturating_sub(self.config.l1_handler_proposal_cooldown_seconds.as_secs());
        let past_cooldown_txs = self.proposable_index.range(..cutoff);

        // Linear scan, but we expect this to be a small number of transactions (< 10 roughly).
        let unstaged_tx_hashes: Vec<_> = past_cooldown_txs
            .flat_map(|(_timestamp, tx_hashes)| tx_hashes.iter())
            .skip_while(|&&tx_hash| self.is_staged(tx_hash))
            .take(n_txs)
            .copied()
            .collect();

        for &tx_hash in unstaged_tx_hashes.iter() {
            let record = self.records.get(&tx_hash).expect("transaction should exist");
            assert_eq!(
                record.state,
                TransactionState::Pending,
                "Transaction {tx_hash} has state {:?}. Only Pending transactions should be in the \
                 proposable index.",
                record.state
            );
        }
