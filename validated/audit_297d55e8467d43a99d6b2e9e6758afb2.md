Based on the investigation, I found a genuine analog worth reporting: the deprecated gateway's function-index conversion panics on malformed input reachable by an unprivileged declare-transaction sender.

### Title
Unauthenticated DoS via panicking `usize::try_from(...).expect(...)` in Sierra entry-point conversion during Declare transaction processing - (File: `crates/starknet_api/src/state.rs`)

### Summary
When converting a `SierraEntryPoint` (attacker-controlled, part of a user-submitted Sierra contract class in a Declare transaction) into the internal `EntryPoint` representation, the code calls `usize::try_from(entry_point.function_idx).expect("Function index should fit in a usize")`. Because `function_idx` is a `Felt` fully controlled by the transaction sender/class declarer, supplying a value that does not fit into a `usize` triggers an unhandled `panic!`, crashing the processing thread/task rather than returning a validation error. This is directly analogous to CVE-2019-20396 (segfault/crash in `libyang`'s `yyparse` due to malformed grammar input): a malformed, attacker-supplied structural field crashes the parser/converter instead of being rejected gracefully.

### Finding Description
`SierraContractClass` is deserialized directly from the JSON body of an unprivileged Declare transaction (`RpcDeclareTransaction`/`DeprecatedGatewayDeclareTransaction`) at the gateway, with `entry_points_by_type` containing `SierraEntryPoint { function_idx: Felt, selector: Felt }` [1](#0-0) . The conversion `From<SierraEntryPoint> for EntryPoint` performs an unchecked `.expect()` on the `usize` conversion of `function_idx`: [2](#0-1) 

This conversion is exercised well before any Sierra-to-CASM compilation subprocess isolation kicks in — it happens during deserialization/normalization of the class object itself (e.g., via `SierraContractClass` construction paths used by the gateway, transaction converter, and class manager, such as `SierraContractClass::try_from` in `apollo_compile_to_casm_types::RawClass` conversions and `apollo_class_manager`'s `add_class`) [3](#0-2) . Unlike the Sierra→CASM compilation step, which the codebase explicitly documents as running in a "resource-limited subprocess" specifically because it must tolerate malformed/attacker-controlled Sierra programs [4](#0-3) , this `EntryPoint` conversion runs in-process, in the same task/thread handling the gateway request (or class-manager/compiler-client component), with no panic isolation.

The stateless gateway validator does check Sierra version length and entry point sort/uniqueness [5](#0-4) , but it never validates that each `function_idx` value fits within `usize` bounds before the `EntryPoint::from` conversion is invoked on the class data (which occurs elsewhere in the class-processing pipeline, e.g. when `SierraContractClass` values are round-tripped/converted for storage or hashing).

### Impact Explanation
A successful trigger causes an unhandled Rust panic. Depending on which component performs the conversion (gateway process, class-manager process, or compiler-client), this can crash or poison the async task/thread handling declare-transaction submissions, potentially causing the affected sequencer component to stop processing further declare transactions until restarted — a "network unable to confirm new transactions" condition for declare-transaction admission if the panic occurs in a shared, non-isolated worker (e.g., mutex poisoning in `tokio` tasks or panics that abort the whole process depending on panic=abort build profiles). This matches the CVE class of unauthenticated crash-on-malformed-input.

### Likelihood Explanation
Any unprivileged account can submit a Declare transaction with a crafted Sierra program containing an entry point whose `function_idx` exceeds `usize::MAX` (e.g., a felt like `0x10000000000000000` used elsewhere in this codebase's own tests to demonstrate "does not fit into a usize" conditions, see `apollo_gateway/src/stateless_transaction_validator_test.rs` case `invalid_character_in_sierra_version`) [6](#0-5) . This shows the codebase is aware such out-of-range values are reachable via user input, but that awareness/handling was only applied to the Sierra *version* felts, not to `function_idx` in `SierraEntryPoint::from`.

### Recommendation
Replace the `.expect(...)` in `From<SierraEntryPoint> for EntryPoint` with a fallible conversion (`TryFrom`) that propagates a `StarknetApiError`/validation error up through the Declare transaction validation path, and ensure the stateless/stateful gateway validator explicitly checks `function_idx` bounds for every entry point before class data is normalized or persisted.

### Proof of Concept
1. Submit a Declare transaction (RPC v3) with a `contract_class.entry_points_by_type` containing an entry (e.g., under `external`) with `function_idx` set to a felt value exceeding `usize::MAX` (e.g., `0x10000000000000000`), and a `selector` value.
2. As this class object is converted from `SierraEntryPoint` to `EntryPoint` (e.g., in code paths that construct `starknet_api::state::EntryPoint` from Sierra entry points during class processing), `usize::try_from(entry_point.function_idx)` fails and `.expect("Function index should fit in a usize")` panics.
