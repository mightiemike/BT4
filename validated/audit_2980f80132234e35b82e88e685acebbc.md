## Title
Unsafe narrowing type-cast in `DataWord.intValue()`/`longValue()` silently truncates values instead of throwing as documented, risking corrupted memory offsets in TVM execution - (File: `common/src/main/java/org/tron/common/runtime/vm/DataWord.java`)

### Summary
`DataWord.intValue()` and `DataWord.longValue()` are documented as "checking for lost information" and throwing `ArithmeticException` if the 256-bit word doesn't fit into the target type, but the actual implementation performs no such check — it silently truncates/wraps the value. [1](#0-0) [2](#0-1) 

A safe variant (`intValueSafe()`/`longValueSafe()`) exists that clamps to `Integer.MAX_VALUE`/`Long.MAX_VALUE` on overflow, but the unsafe `intValue()`/`longValue()` are still called directly from several places in `Program.java`, including memory-address-related helpers such as `memorySave(DataWord, DataWord)`, `memoryExpand(DataWord, DataWord)`, and `memoryLoad(DataWord)`. [3](#0-2) 

### Finding Description
Both `intValue()` and `longValue()` compute the result by iterating over the raw 32-byte word and left-shifting into an `int`/`long` accumulator:
```java
public int intValue() {
  int intVal = 0;
  for (byte aData : data) {
    intVal = (intVal << 8) + (aData & 0xff);
  }
  return intVal;
}
```
This silently wraps around for any 256-bit value whose lower 32 (or 64) bits, when reduced, produce a value outside the intended semantic range — there is no bounds check, contrary to the Javadoc contract ("checking for lost information... `@throws ArithmeticException`"). The safe counterparts (`intValueSafe()`, `longValueSafe()`) were clearly added later specifically to guard against this, and they are used correctly in energy-cost computation and several opcode actions (`EnergyCost.java`, `OperationActions.java`). [4](#0-3) [5](#0-4) 

However, `Program.java` still calls the unsafe `intValue()` for memory-address handling:
```java
public void memorySave(DataWord addrB, DataWord value) {
  memory.write(addrB.intValue(), value.getData(), value.getData().length, false);
}
...
public void memoryExpand(DataWord outDataOffs, DataWord outDataSize) {
  if (!outDataSize.isZero()) {
    memory.extend(outDataOffs.intValue(), outDataSize.intValue());
  }
}

public DataWord memoryLoad(DataWord addr) {
  return memory.readWord(addr.intValue());
}
``` [6](#0-5) 

For values in the exact overflow boundary (e.g., a 256-bit word whose truncated lower-32-bit slice happens to be small/negative while the true magnitude is astronomically large), these calls can produce a memory offset/size that is inconsistent with the value that was validated by the corresponding energy-cost function (which typically operates on `DataWord.value()` — the full `BigInteger` — via `memNeeded(...)` in `EnergyCost.java`). If any call path invokes `memorySave(DataWord, DataWord)`, `memoryExpand(DataWord, DataWord)`, or `memoryLoad(DataWord)` without a preceding energy-cost/`checkMemorySize` gate that uses the full BigInteger value, a contract could supply a stack word engineered so the BigInteger-based gate accepts it (or is bypassed) while the truncated `int` used for the actual memory operation diverges from the semantically intended offset/size.

### Impact Explanation
If reachable without a prior full-precision (`BigInteger`) bounds check, this class of bug can cause: incorrect memory read/write offsets inside the TVM memory model, potential memory corruption/undefined interpreter state during contract execution, or non-deterministic behavior across nodes if different call paths compute differing truncated results — which would be a consensus-divergence risk in a blockchain interpreter. At minimum it violates the documented safety contract of the API, making it a latent correctness/DoS risk that could be triggered via a crafted smart-contract call executed through a broadcast transaction (anyone can deploy/call a contract that manipulates stack values reaching these methods).

### Likelihood Explanation
Medium-low confidence on exploitability without full call-graph verification: most opcode actions in `OperationActions.java` already use the "safe" (`intValueSafe`) accessor, and energy-cost calculation (`EnergyCost.calcMemEnergy`/`checkMemorySize`) is generally performed *before* opcode execution using the full `BigInteger` value, which likely prevents an attacker from reaching `Program.memorySave(DataWord,...)`/`memoryExpand`/`memoryLoad(DataWord)` with an out-of-range word in the common opcode-driven paths. I could not fully trace every caller of these three `Program.java` methods (16 total `intValue()` call sites) to confirm whether any caller skips the BigInteger-based guard, so the exact reachability from an anonymous/broadcast transaction remains unverified within the scope of this analysis.

### Recommendation
Either fix `DataWord.intValue()`/`longValue()` to actually enforce the documented `ArithmeticException` behavior (matching their Javadoc), or replace all remaining unsafe call sites in `Program.java` (`memorySave(DataWord, DataWord)`, `memoryExpand`, `memoryLoad(DataWord)`) with the existing safe variants (`intValueSafe()`), consistent with how `OperationActions.java` and `EnergyCost.java` already do it. Audit all 16 `intValue()`/`longValue()` call sites in `Program.java` to confirm each is preceded by an equivalent full-precision bounds check before the truncating cast is used for actual memory addressing.

### Proof of Concept
Not independently constructed/verified — a full PoC would require tracing the exact opcode dispatch path(s) that invoke `Program.memorySave(DataWord, DataWord)`, `memoryExpand(DataWord, DataWord)`, or `memoryLoad(DataWord)` to confirm one exists that lacks a preceding `BigInteger`-based `checkMemorySize`/`memNeeded` gate, and then crafting a stack word whose full value exceeds `Integer.MAX_VALUE`/passes that gate (if any) while its truncated `intValue()` differs from the intended offset. This verification could not be completed within the current investigation; a background engineering session with full repository/build access would be needed to trace the call graph exhaustively and build a working PoC transaction.

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
