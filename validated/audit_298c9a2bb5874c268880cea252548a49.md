## Analysis

The reported Badger-Finance issue is a "check-scope mismatch": a `require` needed only for one specific execution branch is hoisted to the top of the function, so it fires unconditionally and blocks unrelated call paths whenever the guarded condition happens to be true. The scoped Push Chain analog of this pattern is in `x/uexecutor/keeper/msg_execute_payload.go`.

### Title
Overly broad `IsInboundEnabled` gate in `ExecutePayload` freezes unrelated UEA fund access - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
`Keeper.ExecutePayload` — the handler behind `MsgExecutePayload`, which lets any Cosmos signer deliver an owner's pre-authorized payload to their own already-deployed Universal Executor Account (UEA) — unconditionally rejects execution when the owner's origin-chain `ChainConfig.Enabled.IsInboundEnabled` is `false`. `IsInboundEnabled` is semantically about whether new bridge deposits/inbound events from that external chain are accepted; it has no logical relationship to whether a user can already operate an existing UEA on Push Chain (transfer PRC20/native balances it already holds, call arbitrary contracts, or migrate itself).

`IsInboundEnabled`/`IsOutboundEnabled` are chain-level toggles designed to pause the cross-chain bridging pipeline for a given external chain — used elsewhere to gate `VoteInbound` (rejecting *new* inbound deposit votes, as confirmed by the integration test) and to gate outbound creation. Both are legitimate, narrowly-scoped uses of the flag: they stop *new inbound/outbound crosschain traffic*.

`MsgExecutePayload`, however, is not an inbound-crosschain operation at all: it is the mechanism by which a UEA owner (or a relayer delivering the owner's pre-signed payload) operates their **already-deployed, already-funded** Push Chain account — moving PRC20/native balances that already sit in the UEA, calling arbitrary EVM contracts, or migrating the UEA implementation (per `x/uexecutor/README.md`, UEA migration is now performed through this same path). None of that requires new inbound events from the origin chain to be accepted.

By checking `IsInboundEnabled` unconditionally at the top of `ExecutePayload`, the code ties an unrelated, already-settled Push Chain fund-access flow to the bridge's deposit-availability flag. This mirrors the Badger finding precisely: a check relevant only to one specific branch (accepting *new* inbound crosschain funds) is applied as a blanket precondition for a function whose primary paths (spending/using already-settled funds) never touch that branch.

`MigrateUEA` in `x/uexecutor/keeper/msg_migrate_uea.go` uses the same `IsInboundEnabled` gate for the same class of unrelated operation.

### Impact Explanation
Whenever `IsInboundEnabled` is `false` for a chain (e.g., operators pause deposits from that chain after detecting an issue with its gateway/bridge, or simply during a chain onboarding/maintenance window), **every** user whose UEA origin is that chain is prevented from executing any payload against their own UEA — even payloads that only move or spend funds the UEA already holds on Push Chain, with zero interaction with the paused inbound pipeline. This is an unauthorized denial of legitimate access to user-controlled, already-bridged funds: balances are not stolen, but become inaccessible for the duration the flag is off, for a reason (deposit pause) that has nothing to do with the operation being attempted. This matches the "permanent/temporary freezing of user-controlled funds" and "corruption of ... revert destination ... or canonical UniversalTx state reachable from ordinary ... default transaction submission paths" impact categories, since the freeze is triggered purely by ordinary `MsgExecutePayload` submission colliding with a normal (non-malicious) chain-config state, with no privileged or malicious actor required to trigger the specific unprivileged user's failed transaction.

### Likelihood Explanation
High under normal operational conditions: `IsInboundEnabled=false` is an expected, non-malicious operational state (used during onboarding, incident response, or chain deprecation) rather than an edge case. Any user attempting `MsgExecutePayload` during such a window is unconditionally blocked regardless of what their payload does, making the unrelated failure highly likely to occur in practice, as already demonstrated by the existing repository test `TestExecutePayload_ChainEnabled` that documents (but does not question) this exact behavior.

### Recommendation
Scope the `IsInboundEnabled` check to only the code paths that actually depend on accepting *new* inbound crosschain funds (e.g., the auto-deploy-from-pre-funded-balance path could arguably still need it, if that path is considered inbound-adjacent), or remove the check from `ExecutePayload`/`MigrateUEA` entirely and rely on a distinct, purpose-built flag (e.g., a per-chain "UEA execution paused" toggle) if pausing user-initiated execution is actually desired. At minimum, do not let the deposit-pipeline pause flag block a user's ability to spend or migrate funds already resident in their UEA on Push Chain.

### Proof of Concept
1. Governance/operator sets `ChainConfig{Chain: "eip155:11155111", Enabled: {IsInboundEnabled: false, IsOutboundEnabled: true}}` for chain `eip155:11155111` (e.g., pausing deposits after detecting a gateway issue on that chain).
2. A user whose UEA (origin `eip155:11155111`) already holds PRC20/native balance from a prior, already-settled deposit submits `MsgExecutePayload` with a valid `VerificationData` intending only to transfer that balance to another Push Chain address.
3. `Keeper.ExecutePayload` reaches `if !chainConfig.Enabled.IsInboundEnabled { ... return fmt.Errorf("inbound is disabled for chain %s", ...) }` before ever reaching `CallUEAExecutePayload`, and the transaction reverts — as directly confirmed by `TestExecutePayload_ChainEnabled` in `test/integration/uexecutor/chain_enabled_test.go` (lines 192-246), which asserts this exact rejection occurs "before any EVM calls."
4. The user cannot access or move their own already-bridged funds until `IsInboundEnabled` is re-enabled, despite the operation having no relation to new inbound deposits.
