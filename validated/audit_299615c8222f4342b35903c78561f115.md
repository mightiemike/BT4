Based on my investigation, I found a concrete analog: a `.expect()` panic on empty/attacker-controlled data in the L1 message-hash computation path, directly parallel to the Pidgin MXIT bug (crash triggered by a crafted packet whose first element is missing/NULL).

### Title
Panic via `.expect()` on empty calldata in `l1_handler_message_hash` - (File: crates/starknet_api/src/hash.rs)

### Summary
`l1_handler_message_hash` computes the L1→L2 message hash by splitting the first element off the transaction's `calldata` and treating it as the `from_address`. It uses `.expect(...)` instead of returning a `Result`, so an empty `calldata` triggers an unrecoverable panic rather than a graceful error.

### Finding Description
The function unconditionally unwraps the first calldata element: [1](#0-0) 

`Calldata` has no non-empty invariant enforced at the type level — it derives `Deserialize` directly and can be constructed empty, as explicitly confirmed by a regression test guarding a related (but different) empty-calldata bug in the same struct family: [2](#0-1) 

Because `Calldata(Arc::new(vec![]))` is a legal value that survives deserialization and construction, any code path that calls `calc_msg_hash()` / `l1_handler_message_hash()` on an `L1HandlerTransaction` built from attacker- or externally-supplied data (rather than data that has already had `from_address` guaranteed non-empty by the L1 scraper) will panic with `"Invalid calldata, expected at least from_address"` via `split_first().expect(...)`.

The call site exists in the RPC layer: [3](#0-2) 
(grep confirmed two references to `calc_msg_hash` in this file, but I was unable to fully view the surrounding function body due to index/tool limitations — see caveat below.)

### Impact Explanation
If reachable from an externally-triggerable RPC call or from L1-event ingestion with an unchecked/attacker-influenced calldata field, this causes an unhandled Rust panic. Depending on whether the panic is caught at a task boundary, this can crash the process thread handling the request or, in the worst case, the whole node — i.e., a network unable to confirm/serve requests reliably (DoS), matching the CVE's own root cause (NULL/empty-data dereference during message parsing causing service disruption).

### Likelihood Explanation
Likelihood is only partially confirmed: the panic is trivially reachable for any code that constructs `L1HandlerTransaction` from deserialized/external input (confirmed via the `executable_transaction_test.rs` test, which explicitly notes "`Calldata` has no non-empty invariant... so an empty calldata is constructible"). I could not fully verify from the tools available whether the two `calc_msg_hash` call sites in `apollo_rpc/src/v0_8/api/api_impl.rs` operate on RPC-supplied (attacker-controlled) transaction data versus already-validated/sanitized internal data (where the L1 scraper always prepends `from_address`, making calldata non-empty by construction in the normal L1-ingestion flow).

### Recommendation
- Change `l1_handler_message_hash` to return a `Result`/typed error instead of using `.expect()` on `split_first()`.
- Enforce a non-empty invariant on `L1HandlerTransaction.calldata` (or on the `from_address` slot specifically) at construction/deserialization time, so malformed transactions are rejected early with a typed error rather than reaching hash computation.
- Audit all call sites of `calc_msg_hash`/`l1_handler_message_hash` (RPC `api_impl.rs`, `l1_events_provider.rs`, `l1_scraper.rs`) to confirm whether any accept externally-supplied calldata without prior validation, and add explicit length checks there as defense in depth.
