### Title
DoS of `getPaginatedNowWitnessList` via unbounded `VotesStore` full-scan despite pagination - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getPaginatedNowWitnessList()` was written specifically to paginate the witness list and avoid the "return everything" DoS pattern described in the Symbiotic report. However, internally it still performs a full, unbounded iteration over the entire `VotesStore` on every single call via `countVote()`, regardless of the requested `offset`/`limit`. Because voting is free (`VoteWitnessActuator.calcFee()` returns 0) and any account can create a `VotesStore` entry, an attacker can grow `VotesStore` without bound and force every paginated-witness-list request to do O(n) work, reproducing the exact "permissionless growth + unbounded iteration in a view function" bug class from the external report.

### Finding Description
`getPaginatedNowWitnessList(offset, limit)` clamps `limit` to `WITNESS_COUNT_LIMIT_MAX` and validates `offset`/`limit`, giving the appearance of safe pagination: [1](#0-0) 

But before applying the pagination `skip`/`limit`, it calls `countVote(votesStore)`, which iterates the **entire** `VotesStore` via a raw DB iterator, independent of the pagination parameters: [2](#0-1) [3](#0-2) 

`VotesStore` gains one entry per distinct account that has ever voted (keyed by the voter's address), and each entry is written by `VoteWitnessActuator.countVoteAccount()`: [4](#0-3) 

Critically, `VoteWitnessActuator.calcFee()` returns `0`, i.e. voting itself is free (only the ordinary transaction bandwidth/energy cost applies): [5](#0-4) 

The only economic gate is that the sum of votes cast must not exceed the caller's `tronPower` (frozen/staked balance), but this can be satisfied with a minimal, arbitrarily small stake (even fractions of a TRX in `sum <= tronPower` after `TRX_PRECISION` scaling still requires `sum>0`, so a minimal non-zero vote count is enough): [6](#0-5) 

Combined with the fact that new accounts can be auto-created essentially for free as a side effect of a transfer to a non-existent address (`TransferActuator`/`CreateAccountActuator` pattern), an attacker can mass-create wallets, freeze a trivial amount of TRX in each, and cast one vote from each — producing an unbounded number of `VotesStore` entries at negligible cost per entry. Every subsequent call to `getPaginatedNowWitnessList` (reachable anonymously via gRPC `getPaginatedNowWitnessList`, HTTP `GetPaginatedNowWitnessListServlet`, and the Solidity-node equivalents) then re-scans the full store on every invocation: [7](#0-6) 

This is precisely the bug class in the external report: a permissionless, low-/no-cost action inflates an unbounded on-chain data structure, and a "key" view function (here, the very function meant to fix the analogous witness-list DoS) still performs unbounded work per request because pagination was applied only to the output slice, not to the underlying aggregation step.

### Impact Explanation
Each call to `getPaginatedNowWitnessList` (and its Solidity-node/OnSolidity counterparts) requires a full iteration and deserialization of every `VotesCapsule` in `VotesStore`, plus construction of a `HashMap` sized to the number of unique voters. As `VotesStore` grows (attacker-controlled, unbounded), CPU time and memory usage per RPC call grow linearly, degrading or DoS-ing this RPC/HTTP endpoint for all callers (full nodes and solidity nodes), and consuming node resources on every maintenance-period request cycle. This directly matches the report's "Key view functions... will be DoSed on chain due to gas limit and off chain due to rpc timeout" impact, applied to java-tron's witness/vote query path.

### Likelihood Explanation
Likelihood is moderate-to-high: voting is a completely permissionless, zero-fee actuator reachable via any broadcast transaction, and the only friction is that each voting account needs a tiny non-zero frozen balance and to exist (both cheap to obtain in bulk). No privileged role, leaked key, or malicious peer is required — this is purely an unprivileged, protocol-level operation combined with a public RPC/HTTP query path.

### Recommendation
Refactor `getPaginatedNowWitnessList`/`countVote` so that vote-count adjustments are computed only for the witnesses actually being returned in the requested page (e.g., by looking up per-witness vote deltas from an index keyed by witness address, or by capping/paginating the `VotesStore` scan), rather than always scanning and materializing every entry in `VotesStore` regardless of `offset`/`limit`. Alternatively, maintain and update aggregate per-witness vote-delta counters incrementally at vote time instead of recomputing them from a full store scan on every read.

### Proof of Concept
No executable PoC was produced (matching the external report, which likewise had no PoC due to no response from the audited team); the finding is derived from static analysis of the reachable call path: `VoteWitnessActuator.execute()` (free, unbounded `VotesStore` growth) → `Wallet.getPaginatedNowWitnessList()` → `countVote()` full-store iteration → exposed via `RpcApiService.getPaginatedNowWitnessList` and `GetPaginatedNowWitnessListServlet`.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }

      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
