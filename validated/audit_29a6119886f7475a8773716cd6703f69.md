### Title
Missing CASM hash-version check for V2 Declare transactions when `block_casm_hash_v1_declares` is enabled - ([File: crates/blockifier/src/transaction/transactions.rs])

### Summary
The Olympus report's second finding is a missing validation check that should be applied whenever a feature flag is enabled, but is only applied to a subset of the cases it should cover, allowing bypass via an alternate code path. The closest reachable analog in this sequencer is `DeclareTransaction::run_execute` in [1](#0-0) , where the CASM hash-version check `check_compile_class_hash_v2_declaration` is gated by `self.version() >= TransactionVersion::THREE`, meaning `Declare` V2 transactions are never subjected to this check even though they carry a `compiled_class_hash` field validated the same way as V3.

### Finding Description
In `run_execute`, both `DeclareTransactionV2` and `DeclareTransactionV3` share the same match arm and both destructure a `compiled_class_hash`: [2](#0-1) 

But the guard restricting when `check_compile_class_hash_v2_declaration()` is invoked is `self.version() >= TransactionVersion::THREE`, which excludes V2 declare transactions entirely: [3](#0-2) 

`check_compile_class_hash_v2_declaration` itself, defined in `starknet_api`, verifies that the supplied `compiled_class_hash` equals `casm.hash(&HashVersion::V2)` and rejects mismatches with `DeclareTransactionCasmHashMissMatch`: [4](#0-3) . This is the mechanism intended to block declarations using the deprecated Poseidon (V1) compiled-class-hash scheme once `block_casm_hash_v1_declares` is turned on for a given Starknet version.

### Impact Explanation
If `block_casm_hash_v1_declares` is meant to enforce that all declared classes' `compiled_class_hash` uses the V2 (post-0.13.x) hash algorithm — presumably because the Starknet OS/committer/compiler pipeline downstream assumes V2 hashes for class commitment and CASM compilation — then a V2 `Declare` transaction (still a valid, in-scope submission from any unprivileged sender) could bypass this and register a class under a V1-derived `compiled_class_hash`. This is analogous to the Olympus bug: a flag intended to enforce a required invariant for a class of operations doesn't cover all code paths that should be gated by it, potentially producing a state where the class-hash-to-CASM mapping used by different components disagrees, or where a class hash slips past a validation upgrade unnoticed.

### Likelihood Explanation
Uncertain — I could not verify in the time available whether Declare V2 transactions are still accepted on the versions where `block_casm_hash_v1_declares` is set (it's possible V2 declares are already rejected earlier in the gateway/stateless validator for post-0.13 versions, which would make this dead code rather than an exploitable gap). I also did not get to inspect `blockifier_versioned_constants.rs` to confirm the exact semantics/version at which this flag activates, nor `try_declare` to see if it performs its own independent hash validation that would make this redundant.

### Recommendation
Verify whether `Declare` V2 transactions can still reach `run_execute` on any chain/version where `block_casm_hash_v1_declares` is true. If so, extend the guard in `crates/blockifier/src/transaction/transactions.rs` to also invoke `check_compile_class_hash_v2_declaration()` for V2 declares, not just `self.version() >= TransactionVersion::THREE`, or explicitly document/confirm (with a test) that V2 declares are unreachable once this flag is active.

### Proof of Concept
Not conclusively demonstrated. A concrete PoC would require constructing a `DeclareTransactionV2` with a `compiled_class_hash` computed via `HashVersion::V1` on a block context where `versioned_constants.block_casm_hash_v1_declares == true`, and confirming it executes successfully via `try_declare` without hitting `DeclareTransactionCasmHashMissMatch` — this was not verified against the actual `blockifier_versioned_constants.rs` gating logic due to tool-call exhaustion.

Given the significant unverified assumptions here (whether V2 declares are even reachable under the relevant versioned constants, and whether `try_declare` has independent protections), I want to flag directly: **this analog is speculative and not confirmed as a real, exploitable vulnerability** — treat it as a lead requiring further investigation (ideally by a Devin session with full repo access) rather than a validated finding.

impl<S: State> Executable<S> for DeclareTransaction {
    fn run_execute(
        &self,
        state: &mut S,
        context: &mut EntryPointExecutionContext,
        _remaining_gas: &mut u64,
    ) -> TransactionExecutionResult<Option<CallInfo>> {
        let class_hash = self.class_hash();
        match &self.tx {
            starknet_api::transaction::DeclareTransaction::V0(_)
            | starknet_api::transaction::DeclareTransaction::V1(_) => {
                if context.tx_context.block_context.versioned_constants.disable_cairo0_redeclaration
                {
                    try_declare(self, state, class_hash, None)?
                } else {
                    // We allow redeclaration of the class for backward compatibility.
                    // In the past, we allowed redeclaration of Cairo 0 contracts since there was
                    // no class commitment (so no need to check if the class is already declared).
                    state.set_contract_class(class_hash, self.contract_class().try_into()?)?;
                }
            }
            starknet_api::transaction::DeclareTransaction::V2(DeclareTransactionV2 {
                compiled_class_hash,
                ..
            })
            | starknet_api::transaction::DeclareTransaction::V3(DeclareTransactionV3 {
                compiled_class_hash,
                ..
            }) => {
                if context.tx_context.block_context.versioned_constants.block_casm_hash_v1_declares
                    && self.version() >= TransactionVersion::THREE
                {
                    self.check_compile_class_hash_v2_declaration()?
                }
                try_declare(self, state, class_hash, Some(*compiled_class_hash))?
            }
        }
        Ok(None)
    }

    /// Verifies that the compiled class hash field in the declare tx,
    /// is compiled_class_hash_v2 of the compiled contract.
    pub fn check_compile_class_hash_v2_declaration(&self) -> Result<(), StarknetApiError> {
        let compiled_class = &self.class_info.contract_class;
        let compiled_class_hash_v2 = match &compiled_class {
            ContractClass::V0(_) => return Ok(()),
            ContractClass::V1((casm, _)) => casm.hash(&HashVersion::V2),
        };
        let compiled_class_hash = self.compiled_class_hash();
        if compiled_class_hash_v2 != compiled_class_hash {
            let err_var = CasmHashMismatch {
                hash: self.class_hash(),
                actual: compiled_class_hash,
                expected: compiled_class_hash_v2,
            };
            return Err(StarknetApiError::DeclareTransactionCasmHashMissMatch(Box::new(err_var)));
        }
        Ok(())
    }
