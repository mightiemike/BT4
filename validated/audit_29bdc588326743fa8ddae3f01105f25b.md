Based on my research, I found a solid analog. The Hybra Finance bug is fundamentally about: a value is computed/recorded as "owed to a party," a terminal/irreversible state transition occurs, and if the compensating transfer fails at that exact point, the value becomes permanently stranded with no retry path. Push Chain's `x/uexecutor` gas-refund path exhibits the same defect.

### Title
Excess outbound gas refund can be permanently stranded with no retry path once terminal status is set - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`applyGasRefund` computes the excess gas (`gasFee - gasFeeUsed`) owed back to the outbound's sender/fund recipient and attempts to deliver it via `CallUniversalCoreRefundUnusedGas`, first with a DEX swap, then falling back to a direct PRC20 deposit. Both `handleSuccessfulOutbound` and `handleFailedOutbound` call `applyGasRefund` and then unconditionally persist the outbound in a terminal status (`OBSERVED`/`REVERTED`) via `UpdateOutbound`, regardless of whether the refund actually succeeded. If both the swap and no-swap refund legs fail, the excess-gas PRC20 value is permanently orphaned: the outbound record is finalized (so it will never be revisited by the finalization/voting flow), `PcRefundExecution.Status` is simply marked `"FAILED"`, and there is no queue, retry mechanism, or admin-facing recovery path for stranded refunds anywhere in the module.

### Finding Description [1](#0-0) 
`handleSuccessfulOutbound` calls `applyGasRefund` and then immediately calls `k.UpdateOutbound(ctx, utxId, outbound)`, committing the outbound as `OBSERVED` no matter the refund outcome. [2](#0-1) 
`handleFailedOutbound` does the same for the `REVERTED` terminal path — funds revert is handled, then `applyGasRefund` runs, then the outbound is committed regardless of refund success. [3](#0-2) 
Inside `applyGasRefund`, step 1 (swap refund) and step 2 (no-swap fallback refund) are tried in sequence. If step 2's `CallUniversalCoreRefundUnusedGas` also fails, the code sets `refundPcTx.Status = "FAILED"` and `refundPcTx.ErrorMsg`, attaches this to `outbound.PcRefundExecution`, records `outbound.RefundSwapError`, and **returns normally (no error)**. The caller (`handleSuccessfulOutbound`/`handleFailedOutbound`) has no way to distinguish "refund succeeded" from "refund permanently failed" — both paths converge on the same `UpdateOutbound` call that finalizes the record.

This mirrors the Hybra Finance defect precisely: a lazily-computed "owed" value (`earned()` in Hybra; `refundAmount = gasFee - gasFeeUsed` here) is attached to a state transition (`emergencyWithdraw` zeroing balance in Hybra; the outbound reaching a terminal `OBSERVED`/`REVERTED` status here) that the protocol treats as final, with no mechanism to later reconcile or re-attempt delivery of the value that was already computed as due. Per the `x/uexecutor/README.md`, `PendingOutbounds` is only ever revisited while a ballot is un-finalized — once `OBSERVED`/`REVERTED`/`ABORTED` is reached, the entry is out of the active flow permanently: [4](#0-3) 

### Impact Explanation
The excess gas fee paid by the user (module-held PRC20 value) becomes permanently unrecoverable once both refund legs fail at finalization time — no code path in the repository re-queues, retries, or exposes a governance/admin instruction to reclaim or re-deliver a `RefundSwapError`'d amount (confirmed via search: `RefundSwapError`/`PcRefundExecution` are only ever set, tested, or read — never consumed by a retry handler). This is a permanent freezing of protocol/user-controlled PRC20 value, matching the "permanent freezing... of user or protocol-controlled funds" and "gas fee accounting, refund accounting" impact categories in scope. The condition is reachable by unprivileged users: the refund recipient is derived from `outbound.RevertInstructions.FundRecipient` (attacker-controllable at inbound-submission time) or falls back to `outbound.Sender`; a user can supply a `FundRecipient` address whose PRC20-hostile contract or blacklisted status causes both the swap-deposit and no-swap-deposit legs to revert, guaranteeing the excess-gas refund is stranded on every finalized outbound tied to that inbound.

### Likelihood Explanation
Moderate. Requires only a normal user-submitted inbound with `RevertInstructions.FundRecipient` set to a contract that reliably reverts on receiving the PRC20 gas token (e.g., a contract with no fallback/receive-compatible token hook, or one that is blacklisted by the specific PRC20 gas token's transfer logic), combined with any excess gas scenario (`gasFee > gasFeeUsed`, which is the common case since `gasFee` is an upfront estimate). No privileged access, honest-validator collusion, or race condition is needed — it is a direct consequence of `applyGasRefund`'s error-swallowing design.

### Recommendation
Do not treat outbound finalization as unconditionally complete when the gas refund fails. Options:
1. Introduce a distinct non-terminal status (or a separate `PendingRefunds` collection, analogous to `PendingOutbounds`) for outbounds whose `PcRefundExecution.Status == "FAILED"`, and expose a retry/admin message (similar to `MsgRevertStuckInbound`) that can re-attempt or manually settle the stranded refund.
2. At minimum, emit a dedicated `refund_stranded` event with enough context (recipient, amount, gas token) for off-chain automation/operators to reconcile, and document the fund-recovery procedure, rather than silently absorbing the failure into `RefundSwapError`/`PcRefundExecution.Status` fields with no consumer.

### Proof of Concept
1. A user submits (or an inbound causes creation of) an outbound with `RevertInstructions.FundRecipient` set to a contract `Hostile` deployed by the attacker that reverts on any PRC20 `transfer`/`transferFrom` call (e.g., always `revert()` in its fallback or a custom PRC20 hook check).
2. UVs vote the outbound as broadcast (`MsgVoteOutbound`, success=true) with `gasFeeUsed < gasFee` (the common case), reaching quorum and calling `handleSuccessfulOutbound`.
3. `applyGasRefund` computes `refundAmount = gasFee - gasFeeUsed > 0`, attempts swap-refund to `Hostile` → reverts; falls back to no-swap refund to `Hostile` → also reverts.
4. `refundPcTx.Status = "FAILED"`, `outbound.RefundSwapError` set; `handleSuccessfulOutbound` still calls `k.UpdateOutbound(ctx, utxId, outbound)`, which is confirmed by `test/integration/uexecutor/gas_fee_refund_test.go:155-197` ("swap fallback reason stored when swap refund fails") to leave `outbound.OutboundStatus == Status_OBSERVED` — a terminal state.
5. No further code path ever re-attempts the refund; the `refundAmount` worth of gas-token PRC20 remains permanently held by the module/`UniversalCore` contract with no recovery mechanism, for as many outbounds as the attacker repeats this against.

```markdown
### `PendingOutbounds`

- **Created** by chain code at outbound creation in `create_outbound.go` —
  BEFORE any validator vote. The chain knows the outbound exists because it
  generated the destination-chain transaction itself; validators are tasked
  with observing whether/how it landed.
- **Keyed** by deterministic chain-derived `outbound_id`.
- **Variant-aware:** validator votes append `OutboundObservationVariant`s as
  they arrive (`RecordOutboundVote` inside `VoteOutbound`). Multiple variants
  per outbound indicate validator divergence on the destination-chain
  observation (different `success`/`tx_hash`/`error_msg`/`gas_fee_used`).
- **Removed ONLY when validators reach consensus** (existing inline
  `PendingOutbounds.Remove` in `msg_vote_outbound.go` on `PASSED`).
- **Ballot expiry does NOT remove the entry** — this is intentional. The
  destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
  driven, not chain-driven.
```
