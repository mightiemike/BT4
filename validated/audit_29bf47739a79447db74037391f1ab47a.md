Based on my research, GAS and GAS_AND_PAYLOAD inbound processing takes the arbitrary `amount` field, deposits into the PRC20 for the token identified by `AssetAddr`, then auto-swaps the *full* deposited value into PC via `CallPRC20DepositAutoSwap`/`gasAndPayloadDepositAutoSwap` [1](#0-0) . There is no amount cap distinguishing "gas top-up" from a full-value asset transfer — the swap uses the entire `amount` regardless of size [2](#0-1) .

### Title
Confirmation depth hardcoded by attacker-controlled TxType instead of registry policy - (File: `universalClient/chains/evm/event_parser.go`)

### Summary
The universal client's event parser assigns block-confirmation depth for an observed inbound purely from the on-chain-emitted `TxType` word of the gateway event, hardcoding `TxType 0` (`GAS`) and `1` (`GAS_AND_PAYLOAD`) to `FAST` confirmation and everything else to `STANDARD`, instead of deriving it from the uregistry `GatewayMethods.ConfirmationType` / `BlockConfirmation` policy meant to reflect value-at-risk. Since `TxType` and `amount` are both attacker-controlled fields inside the same source-chain gateway call, an attacker can submit a high-value inbound tagged as `GAS`/`GAS_AND_PAYLOAD` to force it through the shallow ("fast") confirmation threshold instead of the deeper "standard" threshold intended for asset-moving transfers.

### Finding Description
`finalizeEvent` (EVM) and the equivalent SVM `parseUniversalTxEvent` decide `event.ConfirmationType` solely from the numeric `TxType` word decoded out of the raw log data: [3](#0-2) [4](#0-3) 

This TxType word is read directly from event data supplied by whoever calls the gateway contract on the source chain (`sendFunds`/`addFunds`), i.e. fully attacker-controlled, alongside the `amount` field [5](#0-4) . The confirmation depth used before an event is marked `CONFIRMED` and eligible for `MsgVoteInbound` is later resolved via `getRequiredConfirmations`, which maps `ConfirmationFast`/`ConfirmationStandard` to the registry's `fast_inbound`/`standard_inbound` values (e.g. `fast_inbound: 0, standard_inbound: 1` in the sample chain configs) [6](#0-5) . The registry's `GatewayMethods` already carries a per-method `ConfirmationType` intended to encode this policy (`addFunds` → `CONFIRMATION_TYPE_FAST`(2) vs `sendFunds` → `CONFIRMATION_TYPE_STANDARD`(1) in the sample configs) [7](#0-6) , but the parser never consults it — it hardcodes the mapping from the raw `TxType` value instead, mirroring the Conic Finance bug class where a hardcoded "version"/type assumption diverges from what the artifact (pool/tx) actually is.

On the execution side, `ExecuteInboundGas`/`ExecuteInboundGasAndPayload` place no cap on `Amount` relative to "gas" semantics: the full attacker-chosen `amount` of whatever `AssetAddr` token is configured is deposited and auto-swapped into PC [1](#0-0) , so `TxType_GAS`/`TxType_GAS_AND_PAYLOAD` is not restricted to small "top-up" values in the way the confirmation-depth design implicitly assumes.

### Impact Explanation
An attacker can craft a source-chain gateway call carrying a large `amount` of a whitelisted token but with `TxType = 0` or `1`, causing the universal client to require only `fast_inbound` (potentially 0–2) confirmations instead of `standard_inbound` (potentially much higher, e.g. 12) before the event is `CONFIRMED` and voted on-chain via `MsgVoteInbound`. If the source-chain transaction is later reorged out after honest UVs have already voted/finalized the ballot and PC has minted/auto-swapped the deposited value, the mint is irreversible on Push Chain while the underlying source-chain transfer never finalized — a fund-creation-from-nothing scenario driven entirely by attacker-chosen fields with no privileged assumptions. This falls squarely within the "Registry and accounting path" and "Honest-validator finalization path" allowed impact (forged/cross-linked inbound state accepted through user-reachable flows with honest validators).

### Likelihood Explanation
Both `TxType` and `Amount` are ABI-encoded, sender-controlled fields inside the same gateway call/event a normal user would make; no privileged relayer or validator collusion is required to set them. The only constraint is that the attacker must be able to trigger a chain reorg of the required depth on the source chain within the shortened confirmation window, which is more feasible against `fast_inbound` depths (frequently 0–5 blocks) than `standard_inbound` depths (12+), making this a realistic griefing/reorg-abuse vector on any chain where the two thresholds differ meaningfully.

### Recommendation
Derive `ConfirmationType` for an observed event from the uregistry `GatewayMethods`/`VaultMethods` configuration for the specific event/method identifier that produced it (already present and populated per-chain), rather than from the attacker-supplied `TxType` word. If per-`TxType` differentiation is still desired for UX reasons, at minimum bound `GAS`/`GAS_AND_PAYLOAD` amounts to a small governance-configured ceiling so "fast" confirmation is only ever applied to genuinely low-value gas top-ups, and treat any `GAS`/`GAS_AND_PAYLOAD` inbound whose value exceeds that ceiling as requiring `standard_inbound` confirmations regardless of the declared `TxType`.

### Proof of Concept
1. Attacker calls the source-chain gateway's `sendFunds`/`addFunds` with a large `amount` of a registered token and `txType = 0` (`GAS`) in the ABI-encoded event payload.
2. `universalClient/chains/evm/event_parser.go`'s `finalizeEvent` decodes `TxType == 0` and sets `event.ConfirmationType = store.ConfirmationFast` [8](#0-7) , regardless of amount or the registry's method-specific `ConfirmationType`.
3. The event confirmer requires only `fast_inbound` confirmations (e.g. 0–2 blocks per sample configs) before flipping to `CONFIRMED`, at which point UVs submit `MsgVoteInbound` and, upon quorum, `ExecuteInboundGas` deposits and auto-swaps the full `amount` into PC [9](#0-8) .
4. If the source-chain block(s) backing the observed event are reorged out after this shallow threshold but the Push Chain mint has already occurred, the attacker retains the minted PC-side value while the source-chain deposit is invalidated.

Note: I was unable to fully verify from the indexed code whether there is an additional amount-based safeguard elsewhere (e.g. a governance-set max GAS top-up cap) that might mitigate step 3/4; a Devin session with full repository access should confirm whether such a cap exists before treating this as fully unmitigated.

// finalizeEvent marshals the payload and sets confirmation type on the event.
func finalizeEvent(event *store.Event, payload *common.UniversalTx, logger zerolog.Logger) {
	if b, err := json.Marshal(payload); err == nil {
		event.EventData = b
	} else {
		logger.Warn().Err(err).Msg("failed to marshal universal tx payload")
	}

	if payload.TxType == 0 || payload.TxType == 1 {
		event.ConfirmationType = store.ConfirmationFast
	} else {
		event.ConfirmationType = store.ConfirmationStandard
	}

func parseUniversalTx(event *store.Event, log *types.Log, dataOffset uint64, payload *common.UniversalTx, logger zerolog.Logger) {
	data := log.Data

	decodePayload(data, dataOffset, payload, logger)

	// revertRecipient (plain address at Word 3)
	if w := readWord(data, 3); w != nil {
		payload.RevertFundRecipient = ethcommon.BytesToAddress(w[12:32]).Hex()
	}

	// txType (Word 4)
	if w := readWord(data, 4); w != nil {
		payload.TxType = uint(new(big.Int).SetBytes(w).Uint64())
	}

	// signatureData (Word 5 offset)
	if w := readWord(data, 5); w != nil {
		payload.VerificationData = decodeSignatureData(data, w, uint64(32*7))
	}

	// fromCEA (Word 6)
	if w := readWord(data, 6); w != nil {
		payload.FromCEA = new(big.Int).SetBytes(w).Uint64() != 0
	}

	finalizeEvent(event, payload, logger)
