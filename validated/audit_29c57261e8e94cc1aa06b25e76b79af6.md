### Title
Wallet Contract pays the relayer fee before validating the emulated base-token/ERC-20 transfer succeeds, enabling unlimited fee drain via a non-incrementing "faulty relayer" replay - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`inner_rlp_execute` unconditionally fires a $NEAR transfer to the transaction's `predecessor_account_id` (the relayer) to reimburse the emulated Ethereum gas fee *before* the actual action (an `EOABaseTokenTransfer` or `ERC20Transfer`) has been verified to succeed. This is the direct analog of the reported "use of unsafe ERC20" bug class: value is moved/credited on the assumption an operation will complete, without checking the actual outcome first. Combined with a code path that intentionally does **not** advance the account nonce when the relayer-supplied `target` is later found invalid, an attacker acting as the relayer can replay the exact same signed transaction indefinitely, collecting the fee refund every time without ever completing the underlying action.

### Finding Description
`rlp_execute` accepts a `target: AccountId` parameter that the caller (relayer) is fully free to choose [1](#0-0) . In `inner_rlp_execute`, once the RLP transaction is parsed, if the transaction kind is `EOABaseTokenTransfer` (or `ERC20Transfer`) with a non-zero fee, a transfer promise paying `fee` to `predecessor_account_id` is scheduled immediately and unconditionally: [2](#0-1) 

This fee-payment promise fires *before* the actual action promise (the real transfer, or in the `address_check: Some(address)` case, the registrar lookup) is even created, let alone resolved. The relevant flow for `EOABaseTokenTransfer{address_check: Some(address), ..}` schedules a lookup to the address registrar and defers to `address_check_callback`: [3](#0-2) 

In `address_check_callback`, if the target address is found to already be registered to a named account (`maybe_account_id.is_some()`), and the relayer's signer is *not* the wallet's own key, the call is rejected as a "faulty relayer" **without incrementing the nonce**: [4](#0-3) 

The comment at lines 162-164 explicitly documents that the nonce is intentionally left unchanged in this branch ("An honest relayer may still be able to successfully send the user's intended transaction"), which is reasonable for benign relayer mistakes, but it also means the exact same `(target, tx_bytes_b64)` pair remains valid for resubmission (nonce check in `validate_tx_relayer_data` will still pass) [5](#0-4) .

Because the fee-refund transfer at lines 374-385 already executed unconditionally in `inner_rlp_execute` on every call — prior to and independent of whether `address_check_callback` ultimately rejects the action — any account that can be chosen as `target` with an address already registered in the registrar allows a malicious predecessor to repeatedly call `rlp_execute` with the same signed transaction, collect the `fee` payment each time, and never deliver the user's intended transfer, since the nonce never advances to invalidate the replay.

### Impact Explanation
Any unprivileged account acting as a relayer for a wallet contract (which by design accepts transactions from arbitrary relayers, not just the wallet owner) can drain the wallet's $NEAR balance in repeated increments equal to the user-specified `tx_fee`, without ever completing the user's intended action. This is a concrete unauthorized value movement / fund-drain vulnerability directly reachable from a standard NEAR transaction (`FunctionCall` to `rlp_execute`), matching the "unsafe transfer without checking success" bug class from the source report.

### Likelihood Explanation
The wallet contract's entire design purpose is to let arbitrary relayers submit user-signed Ethereum-style transactions [6](#0-5) , so the "malicious relayer" role here is simply an unprivileged transaction sender, not an insider. The `target` parameter used to trigger the vulnerable `address_check: Some(...)` path is entirely attacker-supplied at call time [1](#0-0) , and the non-incrementing nonce behavior on this specific rejection path is explicit, intentional code [7](#0-6) , making the replay condition reliably reproducible as long as an attacker can get (or is) a registered account whose derived address can serve as `target`.

### Recommendation
Only send the relayer fee-refund promise after the underlying action promise has resolved successfully (e.g., chain it through `rlp_execute_callback`/`address_check_callback` gated on `PromiseResult::Successful`), or alternatively always increment the nonce once a fee-bearing transaction has been accepted for processing (i.e., once `tx_fee` is computed and about to be paid) so that a given signed transaction cannot be resubmitted after the fee has already been collected.

### Proof of Concept
1. Attacker registers (or otherwise obtains) an eth-implicit `AccountId` whose derived address is present in the address registrar (`maybe_account_id.is_some()` will be `true` for it).
2. Attacker obtains (or is) the signer of a valid Ethereum-emulated base-token-transfer transaction for a wallet contract with `tx_fee > 0` (fee is part of the signed payload, computed from `max_fee_per_gas * gas_limit`, see `internal.rs` lines 54-64).
3. Attacker calls `rlp_execute(target = <the registered eth-implicit account>, tx_bytes_b64 = <the signed tx>)` from their own account (not the wallet's signer key).
4. `inner_rlp_execute` immediately schedules and sends `fee` to the attacker (`predecessor_account_id`) — lines 374-385.
5. The registrar lookup resolves, `address_check_callback` finds `maybe_account_id.is_some()` and `env::signer_account_id() != current_account_id`, so it returns `ExecuteResponse{success:false, ...}` without incrementing the nonce — lines 165-173.
6. Because the nonce did not change, step 3 can be repeated indefinitely with the identical arguments, each time paying the attacker `fee` from the wallet's balance until it is exhausted.
