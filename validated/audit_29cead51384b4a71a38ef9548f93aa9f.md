### Title
Unrecovered panic in `ParallelExecutor.ExecuteTask` task goroutine can crash the entire node process - ([File: core/capabilities/remote/parallel_executor.go])

### Summary
`ParallelExecutor.ExecuteTask` runs the caller-supplied `fn` inside a `t.wg.Go(...)` goroutine with a `defer` that releases `t.taskSemaphore` and cancels the context, but there is no `recover()` around the call to `fn(ctxWithStop)`. Because Go's standard library `sync.WaitGroup.Go` does not recover panics, an unrecovered panic from `fn` (e.g. a panic thrown deep inside `cfg.underlying.Execute` while processing a malformed CCIP/OCR payload) will propagate past the executor's cleanup defer and crash the whole node process.

### Finding Description
In `core/capabilities/remote/parallel_executor.go`, `ExecuteTask` spawns a goroutine via `t.wg.Go`: [1](#0-0) 
The deferred `<-t.taskSemaphore` release is registered before `fn(ctxWithStop)` is invoked, so on a panic, Go's defer-unwind semantics *do* still run this deferred cleanup — the semaphore slot is released and `cancel()` is called. This means the semaphore-leak/`Close()`-hang scenario specifically hypothesized in the question does **not** occur; `t.wg`'s internal accounting is also correctly decremented because `sync.WaitGroup.Go`'s own bookkeping is likewise defer-based and executes during panic unwind.

However, since nothing calls `recover()` anywhere in this call stack, the panic continues propagating after the deferred cleanup completes. An unrecovered panic in any goroutine terminates the entire Go process, per Go runtime semantics. This is a materially worse outcome than the executor "starving" — it takes down the whole Chainlink node.

This code path is reachable from the network: `core/capabilities/remote/executable/server.go`'s `Receive` method calls `r.parallelExecutor.ExecuteTask(ctx, func(ctx context.Context) { err = reqAndMsgID.request.OnMessage(ctx, msg) ... })` for every incoming remote-capability request message: [2](#0-1) 
`request.OnMessage` eventually invokes the underlying capability's `Execute` (`cfg.underlying.Execute`), which handles attacker-supplied payload content (e.g. CCIP/OCR request payloads). If that handler panics on malformed input, the panic is not recovered anywhere in this path.

By contrast, the dispatcher's own per-receiver goroutine explicitly wraps message handling with `recover()`: [3](#0-2) 
demonstrating that the codebase's established pattern for defending against panics from capability/message handling is a `recover()` wrapper — which is missing in `ParallelExecutor.ExecuteTask`.

### Impact Explanation
An attacker who can send a message that reaches a registered executable-capability server (`server.Receive` → `ExecuteTask` → underlying capability `Execute`) and trigger a panic in that capability's handler (e.g., via malformed/adversarial payload causing a nil dereference, out-of-bounds access, or type assertion panic) can crash the entire Chainlink node process. This is a full node-availability DoS, not merely resource starvation within the executor, and matches a "denial of service against node process" bounty impact category. The semaphore/`Close()` deadlock scenario specifically posited in the question is not correct — semaphore release and `Close()` termination are unaffected by the panic because the defer still executes — but the actual consequence (process crash) is more severe.

### Likelihood Explanation
Feasibility depends entirely on whether some registered `commoncap.ExecutableCapability.Execute` implementation can be made to panic on attacker-controlled network input, rather than returning an error. The `ParallelExecutor`/`server.go` layer itself does not validate or sanitize the payload beyond message-ID/hash validation; any panic-causing bug in any registered capability implementation (CCIP, OCR, or other capability handler) is fully unguarded at this layer. Whether such a panic-inducing bug currently exists in a shipped capability handler could not be confirmed from this file set alone — that would require an existing panic bug in a specific capability's `Execute` implementation, which is outside the scope of `parallel_executor.go`/`server.go`. The structural weakness (missing `recover()`) is confirmed and reproducible.

### Recommendation
Wrap the `fn(ctxWithStop)` invocation inside `ParallelExecutor.ExecuteTask`'s goroutine with a `recover()` block, following the same pattern used in `dispatcher.go`'s `setReceiver`, logging the panic and treating it as a task failure rather than letting it escape and crash the process.

### Proof of Concept
Unit test in `core/capabilities/remote/parallel_executor_test.go`:
1. Create a `ParallelExecutor` with `maxParallelTasks = 1`.
2. Call `ExecuteTask(ctx, func(ctx context.Context) { panic("malformed payload") })`.
3. Assert:
   - `Close()` completes within a bounded timeout (e.g. via `require.Eventually`) — expected to pass today because the defer still runs.
   - `occupiedSlots()` returns to `0` after the panicking task — expected to pass today.
   - Additionally, run the test with `-run` under a subprocess harness (e.g. `exec.Command` re-invoking the test binary) to confirm that the *test process itself terminates* due to the unrecovered panic (nonzero exit / panic output), demonstrating that although the semaphore correctly drains, the panic is never contained and would crash a real node process outside of a test harness that isolates it.
