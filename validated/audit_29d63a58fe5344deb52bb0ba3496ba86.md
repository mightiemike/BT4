### Title
`StateSnapshotRestoreMode::KvOnly` writes raw state values to `state_kv_db` without any proof/hash verification, letting corrupted backup data become permanently bound to an incorrect Merkle leaf - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
`StateSnapshotRestore::add_chunk` in `storage/aptosdb/src/state_restore/mod.rs` handles three restore modes differently. In `StateSnapshotRestoreMode::Default`, each chunk's values are hashed and verified against the `SparseMerkleRangeProof`/`expected_root_hash` via `JellyfishMerkleRestore::verify_chunk` *before* being persisted to `state_kv_db`. In `StateSnapshotRestoreMode::TreeOnly`, the tree nodes are similarly proof-verified. But in `StateSnapshotRestoreMode::KvOnly`, the raw `(K, V)` chunk is written straight to `state_kv_db` with **no hash or proof check at all**: [1](#0-0) 

This mode is exercised in production by the backup-restore coordinator's "phase 1.a", which restores a KV-only snapshot from backup storage before replaying transactions: [2](#0-1) 

### Finding Description
The manifest-level check performed in `StateSnapshotRestoreController::run_impl` only verifies that the *overall* `manifest.root_hash` for the snapshot version is authenticated by a `TransactionInfoWithProof`/`LedgerInfoWithSignatures`: [3](#0-2) 

That check authenticates the *root* of the snapshot, but the actual per-key binding between a raw value byte string and its position/hash in the Jellyfish Merkle Tree is normally enforced chunk-by-chunk inside `add_chunk`/`verify_chunk`, which hashes each value and folds it into the `SparseMerkleRangeProof` verification against `expected_root_hash`: [4](#0-3) 

For `KvOnly` mode this per-chunk cryptographic binding is entirely skipped — the code calls `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?` directly, with the `proof` parameter simply discarded. Nothing hashes the incoming values or checks them against the version's Merkle root before they are durably written into `state_kv_db`.

`KvOnly` is used precisely in the scenario where the backup source (`BackupStorage`, e.g., an S3 bucket or other external store) supplies the chunk data, and the coordinator explicitly treats a KV-only snapshot as a bootstrap for a version that has no corresponding tree restore of its own (only a later, different-version `tree_snapshot` gets `TreeOnly`-verified). If the backup storage returns tampered or corrupted raw values for the `KvOnly` snapshot version (bit rot, MITM, malicious/compromised storage backend, or a bug in the backup pipeline), those bytes are accepted and committed to `state_kv_db` unconditionally. Any state key untouched by subsequent replayed transactions between the KV-snapshot version and the later `tree_snapshot` version will remain in `state_kv_db` with content that does not correspond to the JMT leaf hash committed at that key — even though the later `TreeOnly` restore for `tree_snapshot.version` will independently "verify" and pass, because tree verification only checks the internal hash-chain consistency of the tree, not that the persisted raw `state_kv_db` bytes hash to the leaves it commits.

The end result is a durably corrupted, internally inconsistent local ledger state: the node's own `state_kv_db` entry for that key no longer matches the value implied by its own (successfully-verified) Merkle root for that version, and this divergence is silent — no error is raised anywhere in the restore pipeline.

### Impact Explanation
This breaks the state-commitment integrity invariant that "committed state must survive the executor/restore-to-storage handoff unchanged" and that "storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state." A node that completes a `KvOnly`-based restore with tampered/corrupted backup input for a stale key will:
- Serve reads for that key that are permanently wrong for the affected version(s), never matching what the network actually committed.
- Be unable to produce a valid state proof (hash(value) vs. leaf hash) for that key, which is a durable, undetected data-integrity fault in the local database that only becomes evident when a client cross-checks the proof — until then, application logic on the restoring node has silently ingested corrupted data.

Because this is a restore-time integrity bypass rather than an execution-time bug, it does not by itself let an attacker forge a proof that other honest nodes independently accept; the direct damage is confined to nodes that use `KvOnly` restore against an untrusted/corruptible backup source. This still qualifies as a high-severity local-storage-integrity break: state that differs from the correct historical result is durably persisted with no verification, in direct violation of the "authenticated response and proof-bearing values must stay bound to the right ledger version/root" requirement.

### Likelihood Explanation
`KvOnly` mode is not a test-only or dead code path — it is invoked automatically by `RestoreCoordinator::run_impl`'s "phase 1.a" whenever a partial-history restore begins from an in-progress or newly selected KV snapshot (`storage/backup/backup-cli/src/coordinators/restore.rs:242-260`). Any operator restoring a node from an external/self-hosted backup store (the normal, documented restore path) is exposed if that store is compromised, corrupted, or subject to a supply-chain/MITM attack on the specific snapshot file used for the KV-only phase. No privileged access or consensus-level compromise is required — only control over (or corruption of) the backup blob storage that the node reads from during restore.

### Recommendation
Even in `KvOnly` mode, hash each incoming value and verify it (and the chunk order) against the `SparseMerkleRangeProof`/`expected_root_hash`, the same way `Default`/`TreeOnly` do, before writing to `state_kv_db`. If the intent is to defer tree-node writes to a later phase, verification can still be performed without writing tree nodes (i.e., call `verify_chunk`-equivalent logic for hash-checking only, without materializing JMT nodes), so that corrupted or tampered raw values are rejected before being persisted to `state_kv_db`.

### Proof of Concept
1. Start a `RestoreCoordinator` restore that requires phase 1 (i.e., `ledger_history_start_version` set so that a `kv_snapshot` distinct from the final `tree_snapshot` is selected).
2. Control (or corrupt) the backup storage's response for the chunk file(s) referenced in the `kv_snapshot` manifest so that one entry's value bytes differ from what was actually committed on-chain for that key/version, while leaving the manifest's `root_hash` field for the *unrelated* tree_snapshot untouched.
3. Run the restore: `StateSnapshotRestoreController` is invoked with `StateSnapshotRestoreMode::KvOnly` (`storage/backup/backup-cli/src/coordinators/restore.rs:247-259`), calling `add_chunk` (`storage/aptosdb/src/state_restore/mod.rs:213-218`), which persists the tampered value with no hash/proof check.
4. If no later transaction rewrites that key before `tree_snapshot.version`, `tree_snapshot`'s `TreeOnly` restore verification still succeeds (it never inspects `state_kv_db` contents), and the node now durably stores a state value inconsistent with its own verified Merkle root for that key — confirmable by comparing `hash(state_kv_db_value)` against the JMT leaf hash at that key/version.

    fn add_chunk(&mut self, chunk: Vec<(K, V)>, proof: SparseMerkleRangeProof) -> Result<()> {
        match self.restore_mode {
            StateSnapshotRestoreMode::KvOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
            },
            StateSnapshotRestoreMode::TreeOnly => {
                let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_add_chunk"]);
                self.tree_restore
                    .lock()
                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks
                // from min(kv_progress, tree_progress)) would land bytes in (kv_progress,
                // tree_progress] that the tree side skips and therefore does not re-verify.
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_verify_chunk"]);
                    self.tree_restore
                        .lock()
                        .as_mut()
                        .unwrap()
                        .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;
                }
            },
        }

        Ok(())

    /// Restores a chunk of states. This function will verify that the given chunk is correct
    /// using the proof and root hash, then write things to storage. If the chunk is invalid, an
    /// error will be returned and nothing will be written to storage.
    pub fn add_chunk_impl(
        &mut self,
        chunk: Vec<(&K, HashValue)>,
        proof: SparseMerkleRangeProof,
    ) -> Result<()> {
        self.verify_chunk(chunk, proof)?;
        self.commit_chunk()
    }

    /// Verifies a chunk and stages frozen nodes in memory; call [`Self::commit_chunk`] to
    /// flush. On error, in-memory state is partially updated — abort the restore rather
    /// than calling again.
    pub fn verify_chunk(
        &mut self,
        mut chunk: Vec<(&K, HashValue)>,
        proof: SparseMerkleRangeProof,
    ) -> Result<()> {
        if self.finished {
            info!("State snapshot restore already finished, ignoring entire chunk.");
            return Ok(());
        }

        if let Some(prev_leaf) = &self.previous_leaf {
            let skip_until = chunk
                .iter()
                .find_position(|(key, _hash)| key.hash() > *prev_leaf.account_key());
            chunk = match skip_until {
                None => {
                    info!("Skipping entire chunk.");
                    return Ok(());
                },
                Some((0, _)) => chunk,
                Some((num_to_skip, next_leaf)) => {
                    info!(
                        num_to_skip = num_to_skip,
                        next_leaf = next_leaf,
                        "Skipping leaves."
                    );
                    chunk.split_off(num_to_skip)
                },
            }
        };
        if chunk.is_empty() {
            return Ok(());
        }

        for (key, value_hash) in chunk {
            let hashed_key = key.hash();
            if let Some(ref prev_leaf) = self.previous_leaf {
                ensure!(
                    &hashed_key > prev_leaf.account_key(),
                    "State keys must come in increasing order.",
                )
            }
            self.previous_leaf.replace(LeafNode::new(
                hashed_key,
                value_hash,
                (key.clone(), self.version),
            ));
            self.add_one(key, value_hash);
            self.num_keys_received += 1;
        }

        // Verify what we have added so far is all correct.
        self.verify(proof)?;
        Ok(())
