### Title
Unchecked `storeSession()` return value in token-exchange and token-invalidation flows can leave auth state inconsistent - (File: `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`)

### Summary
The `SessionStorage.storeSession()` contract explicitly returns `Promise<boolean>` to signal whether a session write succeeded or failed [1](#0-0) , and the implementation guide documents `false` as a valid, expected outcome on write failure [2](#0-1) . Several security-critical call sites in the token-exchange and token-invalidation auth flows call `storeSession()` and unconditionally treat the operation as successful, exactly mirroring the `VaultV3` pattern of mutating state (`custodied = true`, "session now valid/invalid") without verifying that the underlying transfer/write actually succeeded.

### Finding Description
In the Express token-exchange middleware, after successfully exchanging a session token for offline/online access tokens, the code persists the new session and immediately proceeds to authorize the request without checking the boolean result: [3](#0-2) 

The same unchecked pattern exists in the React Router and Remix token-exchange strategies: [4](#0-3) 

Conversely, `invalidateAccessToken` — invoked from every framework's `handleClientError`/401-handling path when Shopify reports the current access token is stale/revoked — nulls the token and persists it, again without checking the write result: [5](#0-4) [6](#0-5) 

This is used by the token-exchange strategy's `handleClientError`, which is the auth handler's recovery path for a 401 from the Admin API: [7](#0-6) 

Because the boolean success/failure of `storeSession()` is never inspected in any of these call sites, a transient storage failure (DB timeout, throttling, connection loss — the same class of "temporarily unavailable" condition cited as the root cause in the original report) causes the code to proceed as if the state mutation succeeded, exactly as `custodyFunds()`/`returnFunds()` proceeded despite an unchecked ERC20 transfer.

### Impact Explanation
- If `storeSession(offlineSession)`/`storeSession(onlineSession)` silently fails during token exchange, the current request is authorized using a session object that was never actually persisted. The in-memory `newSession` is attached to the request and used to call the Admin API, but subsequent requests will not find this session in storage, forcing the token-exchange path to run again on every request for that shop — a self-inflicted repeated-exchange loop against Shopify's OAuth token endpoint.
- If `storeSession()` fails inside `invalidateAccessToken()` after a 401 from Shopify, the stale/revoked access token is never actually cleared from the session store. `Session.isActive()` does not check `accessToken` presence, only scope/expiry, so the session will continue to be treated as "active" by subsequent requests, each of which will call the Admin API with the same revoked token, get another 401, attempt invalidation again, and fail again — a persistent flapping/DoS condition for that merchant's authenticated routes that self-heals only when the offline token naturally expires or an operator manually intervenes, mirroring the "need for manual governance intervention" impact called out in the original report.
- This does not itself grant an attacker elevated or cross-tenant access; the impact is state inconsistency and denial-of-service of the authentication/token-exchange handler for the affected shop, not a forged-session or cross-tenant bypass.

### Likelihood Explanation
Triggering this requires a genuine storage backend hiccup or an app's custom `SessionStorage` implementation returning `false` on failure (which is the documented, expected behavior) — this can happen under database load, network issues, or throttling, and does not require a malicious actor; it is reachable through the ordinary token-exchange/authenticated-request path used by any single merchant's embedded app session. I was not able to verify how often production `SessionStorage` implementations actually return `false` versus throwing (some reference implementations return `true` unconditionally, e.g. Postgres/SQLite adapters shown in search results), so the practical trigger rate is uncertain and depends on the app's chosen storage backend.

### Recommendation
Check the boolean result of every `storeSession()` call in the token-exchange and token-invalidation flows (`perform-token-exchange.ts`, both `token-exchange.ts` strategies, and `invalidate-access-token.ts` in all three framework packages). On `false`, log an error, avoid treating the request as authorized/invalidated, and return a 5xx or trigger re-authentication rather than silently continuing — analogous to using `SafeERC20`/checking the transfer return value before mutating `custodied` state in the original report.

### Proof of Concept
Not independently verified end-to-end (would require instrumenting a `SessionStorage` implementation to return `false` from `storeSession()` and observing the described flapping/inconsistent-session behavior in a running app); this is inferred from the documented `SessionStorage` contract and the unchecked call sites cited above.

import {Session} from '@shopify/shopify-api';

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}

import type {BasicParams} from '../../types';

export async function invalidateAccessToken(
  params: BasicParams,
  session: Session,
): Promise<void> {
  const {logger, config} = params;

  logger.debug(`Invalidating access token for session - ${session.id}`, {
    shop: session.shop,
  });

  session.accessToken = undefined;
