### Title
Off-chain accounts-lt-hash duplicate-account invariant is unenforced in release builds - ([File: runtime/src/bank/accounts_lt_hash.rs])

### Summary
`Bank::enqueue_off_chain_accounts_lt_hash_updates` requires that its caller never pass the same pubkey twice in a single batch, but this invariant is checked only when `cfg!(debug_assertions)` is true. In release builds, a caller that (even accidentally) submits a duplicate pubkey in the same call will silently corrupt the incremental accounts lattice hash and capitalization accounting instead of panicking, exactly the class of bug the external report warns about: code paths that assume "no duplicate identical operations in the same batch" must enforce that assumption, not merely document it.

### Finding Description
`enqueue_off_chain_accounts_lt_hash_updates` is documented as: "Does not deduplicate accounts, requiring the caller to ensure there are no duplicates." [1](#0-0) 

The actual duplicate detection is gated behind `cfg!(debug_assertions)`: [2](#0-1) 

If `debug_assertions` are off (a normal release/production build of the validator), no duplicate check runs at all, and the function proceeds to load the pre-batch version of each account and enqueue an lt-hash update per index: [3](#0-2) 

For each duplicate pubkey entry, `load_with_fixed_root_do_not_populate_read_cache` returns the *same* pre-batch (`prev_account`) value (since none of the batch's writes have landed in storage yet), while `curr_account` differs per entry. Each duplicate index is separately mixed into the lt hash as `(prev_account, curr_account_i)`. But only the *last* entry for a given pubkey actually survives into the write cache/storage — `write_accounts_to_cache` explicitly keeps only the last version of a pubkey when multiple entries for the same pubkey are present in one batch, discarding the earlier ones as duplicates: [4](#0-3) 

This is precisely analogous to the bug report's Timelock scenario: the code assumes each "action" (here, a per-pubkey account update in a lt-hash-enqueue batch) occurs at most once, and the invariant is enforced by an assertion, but that assertion is only compiled in for debug builds — in release builds the "no duplicate actions" rule silently is not checked, and the resulting effective on-disk state (last-write-wins) diverges from what was mixed into the lt hash (every duplicate write mixed in against the same stale `prev_account`). The result is an accounts-lt-hash value that no longer matches the capitalization/state actually committed to `AccountsDb`.

`store_accounts_without_stakes_cache`, which calls this enqueue function, explicitly documents the same unenforced caller contract: "Callers must ensure there are no duplicates in `accounts`." [5](#0-4) 

There are several off-chain callers of this path (multiple-account batch stores used by core-BPF-loader-migration code in `runtime/src/bank/builtins/core_bpf_migration/source_buffer.rs`, `target_bpf_v2.rs`, and `target_core_bpf.rs`), each of which stores more than one account (buffer/program/programdata accounts) in a single batch. Any of these call sites that construct their batch dynamically (e.g., from configuration or malformed/edge-case account state where the "buffer" and "target" happen to resolve to the same pubkey) would trigger this silent divergence in production, whereas the exact same input in a debug build would deterministically panic (as shown by the existing test `test_enqueue_off_chain_accounts_lt_hash_updates_catches_duplicates`, which only asserts the debug-mode panic and does not test/guard the release-mode behavior). [6](#0-5) 

### Impact Explanation
If the "no duplicates" invariant is ever violated on a live/production (release) validator, the accounts lattice hash computed by `Bank` will silently diverge from the state actually written to `AccountsDb`, without any panic or error. Because the accounts lt hash feeds into bank-hash computation and is compared across snapshot generation/rebuild and honest-node replay, this can produce an honest-node snapshot-vs-replay mismatch or a hash/capitalization divergence — one of the explicitly accepted impact categories.

### Likelihood Explanation
This is not remotely triggerable by an unprivileged transaction; it requires a specific off-chain, node-internal call path (core-BPF-loader migration or any future off-chain multi-account store) to violate its own "no duplicates" contract. The safety net for that contract exists only in debug builds, so any edge case not covered by existing tests (e.g., a migration configuration where the buffer account and program account coincide) would go undetected until it silently corrupts a production node's lt hash — likelihood is low but the defense-in-depth is completely absent in release builds, unlike the equivalent code path for cache-batch stores (`write_accounts_to_cache`) which actively enforces last-write-wins semantics and unlike the on-chain equivalent path.

### Recommendation
Make the duplicate-pubkey check in `enqueue_off_chain_accounts_lt_hash_updates` unconditional (not gated by `cfg!(debug_assertions)`), or better, have it explicitly deduplicate (keep only the last occurrence per pubkey, mirroring `write_accounts_to_cache`'s behavior) so the enqueued lt-hash updates always match what is actually persisted. At minimum, add a `debug_assert!`-independent runtime check on the production build's critical path (or route this call through the same dedup mechanism as `write_accounts_to_cache`) so that a future off-chain caller with duplicate pubkeys cannot silently corrupt the accounts lattice hash in production.

### Proof of Concept
1. Build the validator without `debug_assertions` (release profile).
2. Reach any code path that calls `store_accounts_without_stakes_cache` / `enqueue_off_chain_accounts_lt_hash_updates` with a batch containing two entries for the same pubkey with different lamports/data (e.g., an internal call from a core-BPF-loader migration path where buffer and target accounts alias, or by adding a synthetic call as in `test_enqueue_off_chain_accounts_lt_hash_updates_catches_duplicates` but built in release mode).
3. Observe that, unlike the debug build (which panics with "duplicate accounts were enqueued for hashing"), the release build proceeds silently: both duplicate entries are mixed into `accounts_lt_hash_async_progress`, while `write_accounts_to_cache`/`AccountsDb` storage retains only the last entry per pubkey.
4. Compare `bank.accounts_lt_hash` against the value obtained from an independent recomputation off the persisted storage (e.g., after snapshot regeneration or `calculate_accounts_lt_hash_at_startup`) — the two will diverge because the lt-hash accumulation reflects a stale `prev_account` value applied redundantly to a discarded intermediate account state.

    /// Enqueues the accounts lt hash updates for `accounts` to the accounts hasher thread pool.
    ///
    /// This fn is meant to be called by off-chain events, meaning we know/control `accounts`.
    /// Contrasting with `enqueue_on_chain_accounts_lt_hash_updates()`, this fn:
    /// - Does not deduplicate accounts, requiring the caller to ensure there are no duplicates.
    /// - Does not assume loading the previous version of accounts is fast,
    ///   e.g. when storing stake accounts as part of partitioned epoch rewards.
    ///
    /// If Some, `thread_pool_for_hashing_accounts` will be used
    /// to load the previous version of accounts in parallel.
    pub fn enqueue_off_chain_accounts_lt_hash_updates<'a>(
        &self,
        accounts: &impl StorableAccounts<'a>,
        thread_pool_for_loading_accounts: Option<&ThreadPool>,
    ) {
        if cfg!(debug_assertions) {
            // if debug assertions are on, we will check for duplicates
            use ahash::HashSetExt as _;
            let mut seen_accounts = ahash::HashSet::with_capacity(accounts.len());
            let mut duplicate_pubkeys = ahash::HashSet::with_capacity(0); // assume no duplicates
            for index in 0..accounts.len() {
                let pubkey = accounts.pubkey(index);
                if !seen_accounts.insert(pubkey) {
                    // we've already seen this account, so add it to the duplicates list
                    duplicate_pubkeys.insert(pubkey);
                }
            }
            if !duplicate_pubkeys.is_empty() {
                let mut duplicate_accounts = ahash::HashMap::<_, Vec<_>>::default();
                for duplicate_pubkey in duplicate_pubkeys {
                    for index in 0..accounts.len() {
                        let pubkey = accounts.pubkey(index);
                        if pubkey == duplicate_pubkey {
                            duplicate_accounts
                                .entry(pubkey)
                                .or_default()
                                .push(accounts.account(index, |account| account.take_account()));
                        }
                    }
                }
                panic!("duplicate accounts were enqueued for hashing: {duplicate_accounts:?}");
            }
        }

    // Stores accounts in the write cache. If an account is zero-lamport and not present in the
    // cache or index, there is no need to store it in the write cache as it will not affect the
    // accounts hash. The function returns a BitVec indicating whether each account was stored in
    // the cache. Ordering of accounts is important as duplicate pubkeys are possible. The last
    // account in accounts_and_meta_to_store for each pubkey is stored in the write cache.
    fn write_accounts_to_cache<'a, 'b>(
        &self,
        slot: Slot,
        accounts_and_meta_to_store: &impl StorableAccounts<'b>,
        ancestors: &Ancestors,
    ) -> (BitVec, WriteAccountsToCacheStats) {
        let len = accounts_and_meta_to_store.len();
        let mut pubkey_set = HashSet::with_capacity_and_hasher(len, PubkeyHasherBuilder::default());
        let mut stats = WriteAccountsToCacheStats {
            num_initial_accounts_to_store: len as u64,
            ..Default::default()
        };
        let mut store_account = BitVec::new_fill(false, len as u64);

        (0..len).rev().for_each(|index| {
            accounts_and_meta_to_store.account_default_if_zero_lamport(index, |account| {
                let pubkey = account.pubkey();
                let is_duplicate_account = !pubkey_set.insert(*pubkey);
                if is_duplicate_account {
                    // If the same account is written multiple times in the same batch,
                    // only store the latest version
                    stats.num_duplicate_accounts_skipped += 1;
                    return;
                }
                if account.is_zero_lamport() {
                    match self.is_ancestor_zero_lamport(pubkey, ancestors) {
                        None => {
                            stats.num_ephemeral_accounts_skipped += 1;
                            return;
                        }
                        Some(true) => {
                            stats.num_ancestors_zero_lamport_skipped += 1;
                            return;
                        }
                        Some(false) => {}
                    }
                }

                let account_shared_data = account.take_account();
                let account_data_len = account_shared_data.data().len();
                self.accounts_cache.store(slot, pubkey, account_shared_data);
                store_account.set(index as u64, true);
                stats.num_accounts_stored += 1;
                stats.account_data_bytes_stored += account_data_len as u64;
            })
        });

        (store_account, stats)
    }
