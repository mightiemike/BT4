**Rationale:**

`DecKeyMetadata` (epoch, round) derives `Hash`/`Eq` at [1](#0-0)  and is embedded in `BlockTxnDecryptionKey` alongside the actual key bytes at [2](#0-1) , and wrapped again in `DecryptionPayload` at [3](#0-2) . I searched the full repo for every usage of `DecKeyMetadata`, `BlockTxnDecryptionKey`, and `DecryptionPayload` and found no `HashMap`/`HashSet`/dedup cache keyed by `DecKeyMetadata` anywhere in the consensus pipeline or storage/execution path — the decryption pipeline (`consensus/src/pipeline/decryption_pipeline_builder.rs`) passes the metadata+key pair through directly as a value carried with the block's decryption outcome (`DecryptionOutcome::RoundTracked`), not as a lookup key into any cache used to reuse a previously-committed write set. [4](#0-3) 

Additionally, `(epoch, round)` is not an attacker-controllable or arbitrarily-repeatable pair for two distinct decryption contexts: within a given epoch, block round is monotonically increasing and BFT-safety-enforced by consensus (the same epoch/round pair is only ever finalized with one committed block/`BlockInfo`), so the premise that "two distinct on-chain states produce the same `(epoch, round)` but different actual decryption context" would require a consensus safety violation (fork/equivocation), which is explicitly excluded from scope (this falls under trusted/consensus-safety assumptions, not an unprivileged-input state-corruption path). No cache keyed purely by `DecKeyMetadata` exists in the reviewed code that would allow reuse of a stale `PerBlockDecryptionKeyV2` write-set entry across distinct committed states.
