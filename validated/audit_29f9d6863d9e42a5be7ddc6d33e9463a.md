### Title
Shrink candidate selection can be starved by a single dense storage dominating the aggregate alive-ratio - (File: accounts-db/src/accounts_db.rs)

### Summary
The external report describes an oracle that computes a weighted TVL across pools and can be manipulated so one pool's inflated reserves dominate the aggregate, making all other pools "contribute negligibly" to the final result — silently disabling the resilience the aggregation was meant to provide. The closest concrete analog in Agave is `AccountsDb::select_candidates_by_total_usage`, which decides whether to shrink a batch of storages based on a single global ratio (`total_alive_bytes / total_bytes`) computed by summing over *all* shrink candidates at once, rather than per-storage. A storage with a very high alive-byte count (attacker-controlled, e.g. many accounts written and only a single one closed to qualify it as a "dirty"/shrink candidate) can dominate this sum, making the aggregate ratio look healthy immediately, which causes genuinely sparse/garbage-heavy storages to be pushed to `shrink_slots_next_batch` instead of being shrunk in the current pass.

### Finding Description
`select_candidates_by_total_usage` first computes `total_alive_bytes` and `total_bytes` by iterating over **every** slot in the input `shrink_slots` set and summing `alive_bytes_after_shrink` and `written_bytes` [1](#0-0) . It then sorts stores ascending by their own `alive_ratio` (sparsest first) and walks the list, recomputing a *global* `alive_ratio = total_alive_bytes / total_bytes` at each step to decide whether the shrink goal has been reached [2](#0-1) .

Because `total_alive_bytes` and `total_bytes` are aggregated across all candidates rather than being local to each store, a single storage with a very large `written_bytes`/`alive_bytes_after_shrink` and a high individual alive ratio (i.e., almost fully populated) can dominate the sum. If an unprivileged user creates a storage with a very large number of live accounts and only enough deletions to make the slot a "dirty"/shrink candidate (the minimum requirement for a slot to enter `shrink_candidate_slots`), that storage contributes a huge, near-100%-alive byte count to `total_alive_bytes` and `total_bytes` at the very start of the loop. This pushes the computed global `alive_ratio` above `shrink_ratio` (default `0.80`, see `DEFAULT_ACCOUNTS_SHRINK_RATIO` [3](#0-2) ) even before the algorithm processes the truly sparse (garbage-heavy) stores at the front of the sorted list. When that happens, the loop immediately breaks out via the `alive_ratio > shrink_ratio` branch, and any sparse store still below its own `shrink_ratio` is deferred to `shrink_slots_next_batch` instead of being shrunk in the current cycle [4](#0-3) .

This mirrors the oracle bug class exactly: a single attacker-influenced "reserve" (here, one dense storage) can dominate a supposedly system-wide aggregate metric, causing the other (legitimate, sparse) entries to "contribute negligibly," defeating the purpose of the aggregate check. The unit tests (`test_select_candidates_by_total_usage_3_way_split_condition`, etc.) confirm the mechanics of how the global ratio governs which stores get shrunk vs. deferred based on the mix of alive ratios across all candidates [5](#0-4) .

### Impact Explanation
This does not corrupt account data, capitalization, or hashes; the effect is purely on the shrink scheduling heuristic. However, because shrink is the primary mechanism for reclaiming dead space from AppendVec storages, an attacker who can repeatedly create such "dense" candidate storages can suppress shrinking of other, legitimately sparse storages for extended periods, causing storages to accumulate garbage and disk usage to grow disproportionately relative to live account state. This falls under the accepted "disproportionate storage and CPU cost" impact category. It is not privileged/validator-only — any account owner able to create and delete accounts can influence which slots become shrink candidates and how dense/sparse they are, since ordinary write-cache flushes create the storages iterated by this function.

### Likelihood Explanation
Exploitability requires an attacker to control the relative "mass" of alive bytes vs. total candidates in a given `shrink_candidate_slots` batch. Since shrink candidates are accumulated from clean/dirty-store bookkeeping across many storages/slots over time (not solely from the attacker's own transactions), and slot storages are shared among many accounts/owners in practice, exact control over the mix and timing is nontrivial, but not implausible for a well-resourced adversary who can flood the validator's storage pipeline with large numbers of self-owned accounts, deleting only a minimal fraction to qualify a storage as a shrink candidate. This is a heuristic/DoS-adjacent issue rather than a safety-critical correctness bug, so likelihood is assessed as moderate.

### Recommendation
Avoid basing the shrink-or-defer decision on a single global ratio computed by summing byte counts across all candidates in a batch. Instead:
- Weight/limit the influence any single storage can have on the aggregate (e.g., cap per-storage contribution, or normalize by storage count rather than raw bytes).
- Evaluate the "is this storage worth shrinking" decision independently per storage (as `AccountShrinkThreshold::IndividualStore` already does; see `is_candidate_for_shrink` [6](#0-5) ) rather than only via the `TotalSpace` aggregate mode, or ensure the `TotalSpace` mode cannot be starved by one outsized storage.
- Consider bounding how much total_bytes/total_alive_bytes a single storage may contribute when the `TotalSpace` shrink threshold strategy is in effect.

### Proof of Concept
Conceptual (not executed): 
1. Attacker writes N accounts (e.g., N = 1,000,000) into a slot, producing one large `AccountStorageEntry`.
2. Attacker deletes/closes a single account from that storage in a later slot, which is sufficient to mark the storage's original slot as dirty/a shrink candidate (via the normal `dirty_stores`/candidate bookkeeping).
3. This storage now has alive_ratio ≈ 0.9999999 and dominates `total_alive_bytes`/`total_bytes` when mixed into `select_candidates_by_total_usage` alongside genuinely sparse, low-alive-ratio storages from other slots.
4. The computed aggregate `alive_ratio` at the very start of the sorted loop already exceeds `DEFAULT_ACCOUNTS_SHRINK_RATIO` (0.80), so the sparsest legitimate candidates are pushed into `shrink_slots_next_batch` instead of being shrunk, repeating each cycle as long as the attacker maintains such dense storages among the candidate set [7](#0-6) .

Note: I was not able to fully trace, within the indexed portion of the codebase, the exact conditions under which arbitrary user-created storages get added to `shrink_candidate_slots` (the insertion call sites in `accounts_db.rs` were found via grep but their surrounding logic was not retrievable in this session due to index size limits). If precise confirmation of attacker-reachability of the candidate list is needed, a Devin session with full file access should verify the `shrink_candidate_slots.lock()` insertion sites in `accounts-db/src/accounts_db.rs`.

    fn select_candidates_by_total_usage(
        &self,
        shrink_slots: &ShrinkCandidates,
        shrink_ratio: f64,
    ) -> (IntMap<Slot, Arc<AccountStorageEntry>>, ShrinkCandidates) {
        struct StoreUsageInfo {
            slot: Slot,
            alive_ratio: f64,
            alive_bytes_after_shrink: u64,
            store: Arc<AccountStorageEntry>,
        }
        let mut store_usages = Vec::with_capacity(shrink_slots.len());
        let mut total_alive_bytes: u64 = 0;
        let mut total_bytes: u64 = 0;
        for slot in shrink_slots {
            let Some(store) = self.storage.get_slot_storage_entry(*slot) else {
                continue;
            };
            let alive_bytes_after_shrink = self.alive_bytes_after_shrink(&store) as u64;
            total_alive_bytes += alive_bytes_after_shrink;
            let written_bytes = store.written_bytes();
            total_bytes += written_bytes;
            debug_assert!(
                written_bytes > 0,
                "shrink candidate has zero written bytes! slot: {slot} id: {}",
                store.id(),
            );
            let alive_ratio = alive_bytes_after_shrink as f64 / written_bytes as f64;
            store_usages.push(StoreUsageInfo {
                slot: *slot,
                alive_ratio,
                alive_bytes_after_shrink,
                store: store.clone(),
            });
        }
        store_usages.sort_by(|a, b| {
            a.alive_ratio
                .partial_cmp(&b.alive_ratio)
                .unwrap_or(std::cmp::Ordering::Equal)
        });

        // Working from the beginning of store_usage which are the most sparse and see when we can stop
        // shrinking while still achieving the overall goals.
        let mut shrink_slots = IntMap::default();
        let mut shrink_slots_next_batch = ShrinkCandidates::default();
        for store_usage in &store_usages {
            let store = &store_usage.store;
            let alive_ratio = (total_alive_bytes as f64) / (total_bytes as f64);
            debug!(
                "alive_ratio: {:?} store_id: {:?}, store_ratio: {:?} requirement: {:?}, \
                 total_bytes: {:?} total_alive_bytes: {:?}",
                alive_ratio,
                store_usage.store.id(),
                store_usage.alive_ratio,
                shrink_ratio,
                total_bytes,
                total_alive_bytes
            );
            if alive_ratio > shrink_ratio {
                // we have reached our goal, stop
                debug!(
                    "Shrinking goal can be achieved at slot {:?}, total_alive_bytes: {:?} \
                     total_bytes: {:?}, alive_ratio: {:}, shrink_ratio: {:?}",
                    store_usage.slot, total_alive_bytes, total_bytes, alive_ratio, shrink_ratio
                );
                if store_usage.alive_ratio < shrink_ratio {
                    shrink_slots_next_batch.insert(store_usage.slot);
                } else {
                    break;
                }
            } else {
                let current_store_size = store.written_bytes();
                let after_shrink_size = store_usage.alive_bytes_after_shrink;
                let bytes_saved = current_store_size.saturating_sub(after_shrink_size);
                total_bytes -= bytes_saved;
                shrink_slots.insert(store_usage.slot, Arc::clone(store));
            }
        }
        (shrink_slots, shrink_slots_next_batch)
    }

    pub(crate) fn is_candidate_for_shrink(&self, store: &AccountStorageEntry) -> bool {
        let total_bytes = store.written_bytes();
        let alive_bytes = self.alive_bytes_after_shrink(store) as u64;
        match self.shrink_ratio {
            AccountShrinkThreshold::TotalSpace { shrink_ratio: _ } => alive_bytes < total_bytes,
            AccountShrinkThreshold::IndividualStore { shrink_ratio } => {
                (alive_bytes as f64 / total_bytes as f64) < shrink_ratio
            }
        }
    }

#[test]
fn test_select_candidates_by_total_usage_3_way_split_condition() {
    // three candidates, one selected for shrink, one is put back to the candidate list and one is ignored
    let mut candidates = ShrinkCandidates::default();
    let db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);

    let (_temp_dirs, common_store_path) = get_temp_accounts_paths(1).unwrap();
    let account_size = 100;
    let store_file_size = account_size + 10_000;
    let account = AccountSharedData::new(1, account_size as usize, &Pubkey::default());

    let store1_slot = 11;
    let store1 = Arc::new(AccountStorageEntry::new(
        &common_store_path[0],
        store1_slot,
        store1_slot as AccountsFileId,
        store_file_size,
        db.accounts_file_provider,
    ));
    store1
        .accounts
        .write_accounts(&(store1_slot, [(&Pubkey::new_unique(), &account)].as_slice()));
    db.storage.insert(Arc::clone(&store1));
    store1.num_alive_bytes.store(0, Ordering::Release);
    candidates.insert(store1_slot);

    let store2_slot = 22;
    let store2 = Arc::new(AccountStorageEntry::new(
        &common_store_path[0],
        store2_slot,
        store2_slot as AccountsFileId,
        store_file_size,
        db.accounts_file_provider,
    ));
    store2
        .accounts
        .write_accounts(&(store2_slot, [(&Pubkey::new_unique(), &account)].as_slice()));
    db.storage.insert(Arc::clone(&store2));
    store2
        .num_alive_bytes
        .store(store2.written_bytes() as usize / 2, Ordering::Release);
    candidates.insert(store2_slot);

    let store3_slot = 33;
    let store3 = Arc::new(AccountStorageEntry::new(
        &common_store_path[0],
        store3_slot,
        store3_slot as AccountsFileId,
        store_file_size,
        db.accounts_file_provider,
    ));
    store3
        .accounts
        .write_accounts(&(store3_slot, [(&Pubkey::new_unique(), &account)].as_slice()));
    db.storage.insert(Arc::clone(&store3));
    store3
        .num_alive_bytes
        .store(store3.written_bytes() as usize, Ordering::Release);
    candidates.insert(store3_slot);

    // Set the target alive ratio to 0.6 so that we can just get rid of store1, the remaining two stores
    // alive ratio can be > the target ratio: the actual ratio is 0.75 because of 150 alive bytes / 200 total bytes.
    // The target ratio is also set to larger than store2's alive ratio: 0.5 so that it would be added
    // to the candidates list for next round.
    let target_alive_ratio = 0.6;
    let (selected_candidates, next_candidates) =
        db.select_candidates_by_total_usage(&candidates, target_alive_ratio);
    assert_eq!(1, selected_candidates.len());
    assert!(selected_candidates.contains(&store1_slot));
    assert_eq!(1, next_candidates.len());
    assert!(next_candidates.contains(&store2_slot));
}
