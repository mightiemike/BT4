### Title
`AccountTransaction::assert_actual_fee_in_bounds` panics instead of returning an error when a validated tx's computed fee exceeds its resource bounds - (File: crates/blockifier/src/transaction/account_transaction.rs)

### Summary
The external report's bug class is: an unconditional/incorrectly-assumed invariant on a fee-related code path causes the entire fee-handling flow to unconditionally fail/abort in a reachable, non-malicious configuration, blocking otherwise-legitimate transaction processing. The closest reachable analog in this sequencer is that `handle_fee` calls `assert_actual_fee_in_bounds`, which `panic!()`s the executing thread/process rather than returning a `TransactionExecutionResult` error, whenever `actual_fee > max_possible_fee` is observed post-execution — a condition that is only supposed to have been ruled out by the preceding `PostExecutionReport`/`FeeCheckReport` bounds check.

### Finding Description
`handle_fee` (called from `execute_raw` for every account transaction) unconditionally calls `Self::assert_actual_fee_in_bounds(&tx_context, actual_fee)` before performing the fee transfer: [1](#0-0) 

`assert_actual_fee_in_bounds` does not return a `Result`; on violation it calls `panic!`, which (in a synchronous, non-catch_unwind execution context) aborts the batcher/execution worker's thread when processing that transaction: [2](#0-1) 

The invariant `actual_fee <= max_possible_fee` is supposed to be enforced earlier by `PostExecutionReport`/`FeeCheckReport::check_actual_cost_within_bounds`, which is meant to catch and gracefully revert any transaction whose actual resource usage/fee exceeds the sender's bounds: [3](#0-2) 

However, `max_possible_fee` (used by the panic-check) and the `fee` computed in `TransactionReceipt::from_params` (the value later compared as `actual_fee`) are computed through two independent code paths:
- `max_possible_fee` in `TransactionContext::max_possible_fee` uses `ValidResourceBounds::max_possible_fee(tip)` with `saturating_mul`/`saturating_add` arithmetic and `effective_tip()`. [4](#0-3) [5](#0-4) 
- The actual charged `fee` is computed independently via `tx_context.tx_info.get_fee_by_gas_vector(...)` from the *actual* gas vector and `effective_tip()`, in `TransactionReceipt::from_params`. [6](#0-5) 

Because these are two separately-implemented arithmetic computations (one operating on bound "max amounts", one on measured/reverted resource amounts, going through different gas-to-fee conversion utility `get_fee_by_gas_vector`), any latent discrepancy between them (e.g., rounding/truncation differences, a resource type omitted from one computation, an edge case in `GasVectorComputationMode` handling, or a future regression introduced by either function) causes the `panic!` path to be the *only* thing standing in front of an inconsistency, rather than a recoverable error. The project itself acknowledges the fragility of this invariant: the existing test suite explicitly uses `#[should_panic]` to assert this code panics in negative cases, confirming the panic is intentional but also confirming that any violation of the tightly-coupled bound/fee computations, from any single submitted transaction, converts into a process-level panic rather than a transaction-level rejection: [7](#0-6) 

### Impact Explanation
If any single legitimately-submitted transaction (constructed by an ordinary, unprivileged sender) can drive `actual_fee` computed in `TransactionReceipt::from_params` to exceed `max_possible_fee` computed in `TransactionContext::max_possible_fee` — due to a discrepancy between the two independent fee-computation code paths — then processing that one transaction causes the batcher/execution thread to panic instead of gracefully rejecting the transaction. In a sequencer, an execution-path panic on a single transaction is far more severe than a smart-contract-level revert: it can crash the executing worker/thread, halting proposal or validation of the block containing that transaction, and, if triggered deterministically by an attacker-crafted transaction, be replayed across every node in the network — resulting in a sequencer that is unable to confirm new transactions (a network liveness/availability failure), matching the "network unable to confirm new transactions" acceptance criterion.

### Likelihood Explanation
This is only a Medium-strength analog, not a proven bug: the report is a Solidity/DeFi ETH-vs-ERC20 bug class ("condition can never be satisfied given specific configuration, causing the whole flow to unconditionally fail"), and the closest sequencer analog is this fee-bound assertion panic guarded by an earlier, but *independently implemented*, bound check. I was not able to fully trace every code path of `GasVector::cost`, `get_fee_by_gas_vector`, and `ValidResourceBounds::max_possible_fee` for a concrete arithmetic scenario where the two diverge (e.g. a specific `GasVectorComputationMode::NoL2Gas` vs `AllResources` edge case, or a tip/rounding discrepancy) within the given tool budget. Confirming exploitability requires deeper analysis of `GasVector::cost` and `get_fee_by_gas_vector` (in `crates/starknet_api/src/execution_resources.rs` and `crates/blockifier/src/fee/fee_utils.rs`) to determine whether they can diverge from `ValidResourceBounds::max_possible_fee`'s saturating computation for any valid resource-bounds/gas-vector combination reachable by an ordinary transaction.

### Recommendation
- Replace the `panic!` calls in `AccountTransaction::assert_actual_fee_in_bounds` with a recoverable `TransactionExecutionError`/`TransactionFeeError` variant returned up through `handle_fee`'s `Result`, so that any latent discrepancy between the two fee-computation paths causes the offending transaction to be rejected/reverted rather than crashing the execution worker.
- Unify the fee-bound computation and the actual-fee computation to use the same underlying gas-vector-to-fee conversion function and the same tip/saturation semantics, eliminating the possibility of divergence between `ValidResourceBounds::max_possible_fee` and `TransactionReceipt::from_params`'s fee computation.
- Add property-based/fuzz tests comparing `max_possible_fee` against `get_fee_by_gas_vector`-derived fees across the full space of `GasVectorComputationMode`, tip values, and resource bounds to proactively catch any divergence before it reaches production.

### Proof of Concept
Not independently reproduced. The report's PoC pattern (single unprivileged actor triggers an internally-inconsistent required-condition, causing the fee-handling flow to unconditionally fail) maps to: any invoke/declare/deploy_account transaction whose execution causes `TransactionReceipt::from_params`'s `fee` computation to slightly exceed `TransactionContext::max_possible_fee()`'s output despite passing `FeeCheckReport::check_actual_cost_within_bounds`, would hit the `panic!` in `assert_actual_fee_in_bounds` during `handle_fee`, invoked from every `execute_raw` call: [8](#0-7) 
Reproducing this concretely requires constructing resource bounds/gas-vector values where `GasVector::cost` (used to compute the receipt fee) and `ValidResourceBounds::max_possible_fee` (used for the bound check) diverge — which I could not confirm within the current investigation.

    fn check_actual_cost_within_bounds(
        tx_context: &TransactionContext,
        tx_receipt: &TransactionReceipt,
    ) -> TransactionExecutionResult<()> {
        let TransactionReceipt { fee, gas, .. } = tx_receipt;
        let TransactionContext { tx_info, .. } = tx_context;

        // First, compare the actual resources used against the upper bound(s) defined by the
        // sender.
        match tx_info {
            TransactionInfo::Current(context) => Ok(FeeCheckReport::check_resources_within_bounds(
                &context.resource_bounds,
                gas,
                tx_context,
            )?),
            TransactionInfo::Deprecated(context) => {
                // Check max fee.
                let max_fee = context.max_fee;
                if fee > &max_fee {
                    return Err(TransactionExecutionError::FeeCheckError(
                        FeeCheckError::MaxFeeExceeded { max_fee, actual_fee: *fee },
                    ));
                }
                Ok(())
            }
        }
    }

    /// Returns the maximum possible fee that can be charged for the transaction.
    /// The computation is saturating, meaning that if the result is larger than the maximum
    /// possible fee, the maximum possible fee is returned.
    pub fn max_possible_fee(&self, tip: Tip) -> Fee {
        match self {
            ValidResourceBounds::L1Gas(l1_bounds) => {
                l1_bounds.max_amount.saturating_mul(l1_bounds.max_price_per_unit)
            }
            ValidResourceBounds::AllResources(AllResourceBounds {
                l1_gas,
                l2_gas,
                l1_data_gas,
            }) => l1_gas
                .max_amount
                .saturating_mul(l1_gas.max_price_per_unit)
                .saturating_add(
                    l2_gas
                        .max_amount
                        .saturating_mul(l2_gas.max_price_per_unit.saturating_add(tip.into())),
                )
                .saturating_add(
                    l1_data_gas.max_amount.saturating_mul(l1_data_gas.max_price_per_unit),
                ),
        }
    }

#[rstest]
#[case::positive_case_deprecated_tx(true, true)]
#[case::positive_case_new_tx(true, false)]
#[should_panic(expected = "exceeded bounds; max fee is")]
#[case::negative_case_deprecated_tx(false, true)]
#[should_panic(expected = "exceeded bounds; max possible fee is")]
#[case::negative_case_new_tx(false, false)]
fn test_assert_actual_fee_in_bounds(
    block_context: BlockContext,
    #[case] positive_flow: bool,
    #[case] deprecated_tx: bool,
) {
    let actual_fee_offset = Fee(if positive_flow { 0 } else { 1 });
    if deprecated_tx {
        let max_fee = Fee(100);
        let tx = invoke_tx_with_default_flags(
            invoke_tx_args! { max_fee, version: TransactionVersion::ONE },
        );
        let context = Arc::new(block_context.to_tx_context(&tx));
        AccountTransaction::assert_actual_fee_in_bounds(&context, max_fee + actual_fee_offset);
    } else {
        // All resources.
        let l1_gas = ResourceBounds { max_amount: GasAmount(2), max_price_per_unit: GasPrice(3) };
        let l2_gas = ResourceBounds { max_amount: GasAmount(4), max_price_per_unit: GasPrice(5) };
        let l1_data_gas =
            ResourceBounds { max_amount: GasAmount(6), max_price_per_unit: GasPrice(7) };
        let all_resource_bounds =
            ValidResourceBounds::AllResources(AllResourceBounds { l1_gas, l2_gas, l1_data_gas });
        let all_resource_fee = l1_gas.max_amount.checked_mul(l1_gas.max_price_per_unit).unwrap()
            + l2_gas.max_amount.checked_mul(l2_gas.max_price_per_unit).unwrap()
            + l1_data_gas.max_amount.checked_mul(l1_data_gas.max_price_per_unit).unwrap()
            + actual_fee_offset;

        // L1 resources.
        let l1_resource_bounds = ValidResourceBounds::L1Gas(l1_gas);
        let l1_resource_fee =
            l1_gas.max_amount.checked_mul(l1_gas.max_price_per_unit).unwrap() + actual_fee_offset;

        for (bounds, actual_fee) in
            [(all_resource_bounds, all_resource_fee), (l1_resource_bounds, l1_resource_fee)]
        {
            let tx = invoke_tx_with_default_flags(invoke_tx_args! {
                resource_bounds: bounds,
                version: TransactionVersion::THREE,
            });
            let context = Arc::new(block_context.to_tx_context(&tx));
            AccountTransaction::assert_actual_fee_in_bounds(&context, actual_fee);
        }
    }
}
