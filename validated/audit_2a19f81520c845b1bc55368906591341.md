### Title
Accounts-index disk bucket map capacity is monotonically grown by ordinary account churn and never shrinks - ([File: bucket_map/src/bucket.rs])

### Summary
The `Bucket::grow_index` and `Bucket::grow_data` functions in `bucket_map/src/bucket.rs` only ever allocate larger index/data files when a write fails due to insufficient capacity; there is no corresponding shrink path when accounts are later deleted. Any unprivileged user can force one or more bucket-map index bins (or data buckets) to grow permanently simply by creating and closing a large number of accounts, and that allocation is never released for the lifetime of the validator process.

### Finding Description
When validators run with a disk-backed accounts index (`IndexLimit::Minimal` or `IndexLimit::Threshold`), `Bucket::insert`/`Bucket::try_write` call `Bucket::grow` on `BucketMapError::IndexNoSpace`/`DataNoSpace`, which invokes `grow_index` or `grow_data` [1](#0-0) . `grow_index` allocates a brand-new, strictly larger `BucketStorage` (`current_capacity * 110 / 100`, or more if `anticipated_size` demands it) and copies every live entry into it [2](#0-1) . `grow_data` similarly doubles the data-bucket's power-of-two capacity [3](#0-2) . Neither path is ever invoked in reverse: `delete_key` simply calls `self.index.free(elem_ix)` and marks `at_least_one_entry_deleted`, but the underlying mmap'd storage capacity is untouched [4](#0-3) . There is no `shrink_index`/`shrink_data` counterpart anywhere in `bucket_map`, unlike the in-memory hashmap path, which explicitly rebuilds smaller allocations via `reallocate_to_clear_tombstones` when eviction empties bins [5](#0-4) . Because pubkeys are hashed into bins with `ahash::RandomState` seeded per-bucket-map-instance [6](#0-5) , a burst of many accounts touching the same bin(s) causes that bin's on-disk index (and/or data) file to grow to accommodate the peak, and it stays at that size permanently, even after every account in the burst is subsequently closed and its slot cleaned/purged from the index.

This is directly analogous to the reported Fantom bug: excess resource commitment made during a transient condition (excess `msg.value`, here excess index/data-bucket capacity) is never returned/reclaimed once no longer needed, and there is no mechanism to recover it.

### Impact Explanation
Every validator running with a non-`InMemOnly` accounts-index configuration commits disk (mmap file) space and virtual memory proportional to the historical peak occupancy of each bucket-map bin/data-bucket, not its current occupancy. An unprivileged user can drive this peak arbitrarily higher by submitting transactions that create many short-lived accounts (e.g. rent-exempt system accounts, token accounts) in a way that lands in the same bin(s), then closing them. The disk/mmap footprint from that burst is retained indefinitely, causing disproportionate and unrecoverable storage growth relative to the actual number of live accounts, degrading validator resource usage over time with no operator-facing remedy short of a full index rebuild/restart.

### Likelihood Explanation
This requires no privileged access and no consensus-breaking behavior — only ordinary transactions that create and close accounts, which any user can send at will. Because bin assignment depends on pubkey hashing, achieving concentrated growth of a specific bin needs some grinding, but overall index/data-bucket bloat from repeated create/close churn across the whole account set accumulates naturally over time in normal cluster operation, making the resource-growth effect highly likely to occur even without deliberate targeting.

### Recommendation
Add a shrink/compaction path for both index and data buckets in `bucket_map/src/bucket.rs`, analogous to the in-memory `reallocate_to_clear_tombstones` rebuild, triggered when occupancy drops well below current capacity (e.g., during idle/background maintenance or as part of `AccountsDb` clean/shrink cycles). At minimum, track high-water vs. current occupancy per bin and periodically reallocate to a smaller `BucketStorage` sized to current live-entry count with headroom, freeing the old mmap file.

### Proof of Concept
1. Run a validator (or accounts-db test) configured with `IndexLimit::Threshold`/`Minimal` so the disk `BucketMap` is active.
2. Submit a burst of transactions creating N short-lived accounts that land in a common bucket-map bin, forcing `grow_index`/`grow_data` to allocate larger backing files (observable via `BucketStats.total_file_size`/`max_size` in `bucket_map/src/bucket_stats.rs`) [7](#0-6) .
3. Close/delete all N accounts (`delete_key` is invoked, freeing index slots only) [4](#0-3) .
4. Observe that `total_file_size`/`capacity()` for the affected bucket never decreases, confirming the allocated disk/mmap space is permanently retained despite zero live entries.

    pub fn grow_index(&self, mut current_capacity: u64) {
        if self.index.contents.capacity() == current_capacity {
            // make sure to grow to at least % more than the anticipated size
            // The indexing algorithm expects to require some over-allocation.
            let anticipated_size = self.anticipated_size * 140 / 100;
            let mut m = Measure::start("grow_index");
            //debug!("GROW_INDEX: {}", current_capacity_pow2);
            let mut count = 0;
            loop {
                count += 1;
                // grow relative to the current capacity
                let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
                let (mut index, file_name) = BucketStorage::new_with_capacity(
                    Arc::clone(&self.drives),
                    1,
                    std::mem::size_of::<IndexEntry<T>>() as u64,
                    Capacity::Actual(new_capacity),
                    self.index.max_search,
                    Arc::clone(&self.stats.index),
                    Arc::clone(&self.index.count),
                );
                // index may have allocated something larger than we asked for,
                // so, in case we fail to reindex into this larger size, grow from this size next iteration.
                current_capacity = index.capacity();
                let mut valid = true;
                for ix in 0..self.index.capacity() {
                    if !self.index.is_free(ix) {
                        let elem: &IndexEntry<T> = self.index.get(ix);
                        let new_ix =
                            Self::bucket_create_key(&mut index, &elem.key, self.random, true);
                        if new_ix.is_err() {
                            valid = false;
                            break;
                        }
                        let new_ix = new_ix.unwrap();
                        let new_elem: &mut IndexEntry<T> = index.get_mut(new_ix);
                        *new_elem = *elem;
                        index.copying_entry(new_ix, &self.index, ix);
                    }
                }
                if valid {
                    self.stats.index.update_max_size(index.capacity());
                    let mut items = self.reallocated.items.lock().unwrap();
                    items.index = Some(index);
                    self.reallocated.add_reallocation();
                    self.restartable_bucket.set_file(file_name, self.random);
                    break;
                }

            &self.drives,
            self.index.max_search,
            self.data.get(data_index as usize),
            Capacity::Pow2(std::cmp::max(
                current_capacity_pow2 + 1,
                DEFAULT_CAPACITY_POW2,
            )),
            1 << data_index,
            Self::elem_size(),
            &self.stats.data,
        );
        self.reallocated.add_reallocation();
        let mut items = self.reallocated.items.lock().unwrap();
        items.data = Some((data_index, new_bucket));
    }

    /// Rebuild the bin's HashMap into a fresh allocation to clear tombstones left
    /// behind by evictions. hashbrown counts tombstones against `capacity`, so
    /// without this the bin's effective capacity drifts down over time and triggers
    /// the hashmap to double in capacity.
    ///
    /// Only called in Threshold mode, where `capacity >= target_entries` is guaranteed
    /// by the time eviction runs (`check_flush_trigger` gates on `high_water_mark`).
    fn reallocate_to_clear_tombstones(&self) {
        let stats = self.stats();
        let m = Measure::start("reallocate_hashmap");

        let target_entries = self
            .storage
            .threshold_entries_per_bin
            .as_ref()
            .expect("reallocate_to_clear_tombstones only runs in Threshold mode")
            .target_entries;

        let mut map = self.map_internal.write().unwrap();
        let capacity_pre = map.capacity();

        // Drain the old map into a fresh allocation sized to `target_entries` so the
        // backing storage stays stable across eviction cycles. Building a brand-new
        // map (rather than `shrink_to_fit`) guarantees a full rehash, which is what
        // actually clears the tombstones.
        let mut new_map = HashMap::with_capacity_and_hasher(target_entries, map.hasher().clone());
        new_map.extend(map.drain());
        *map = new_map;
        let capacity_post = map.capacity();
        drop(map);

        stats.update_in_mem_capacity(capacity_pre, capacity_post);
        Self::update_stat(&stats.num_hashmap_reallocates, 1);
        Self::update_time_stat(&stats.hashmap_reallocate_us, m);
    }

#[derive(Debug, Default)]
pub struct BucketStats {
    pub resizes: AtomicU64,
    pub failed_resizes: AtomicU64,
    pub max_size: AtomicU64,
    pub resize_us: AtomicU64,
    pub new_file_us: AtomicU64,
    pub mmap_us: AtomicU64,
    pub find_index_entry_mut_us: AtomicU64,
    pub file_count: AtomicU64,
    pub total_file_size: AtomicU64,
    pub startup: StartupBucketStats,
    pub index_uses_uncommon_slot_list_len_or_refcount: AtomicBool,
}

impl BucketStats {
    pub fn update_max_size(&self, size: u64) {
        self.max_size.fetch_max(size, Ordering::Relaxed);
    }

    pub fn resize_grow(&self, old_size: u64, new_size: u64) {
        let size_change = new_size.saturating_sub(old_size);
        self.total_file_size
            .fetch_add(size_change, Ordering::Relaxed);
    }
}
