### Title
Unbounded `PendingInbounds` linear scan in inbound ballot finalization allows attacker-driven DoS of universal inbound execution - ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
`VoteInbound` creates a `PendingInboundEntry` in the `PendingInbounds` map on the *first* validator vote for any distinct source-chain event [1](#0-0) , and this map is only pruned once all ballot variants for that entry reach a terminal state, via a full linear `Walk` over the entire `PendingInbounds` collection to find the matching ballot ID [2](#0-1) . There is no upper bound on how many entries can exist concurrently in `PendingInbounds`, and no per-source-chain or global rate limit / minimum-value gate on inbound observation creation was found in the code.

### Finding Description
Each unique `(source_chain, tx_hash, log_index)` inbound event tracked by Universal Validators creates its own `PendingInboundEntry`, keyed by `utx_key = sha256(source_chain:tx_hash:log_index)` [3](#0-2) . This entry stays in `PendingInbounds` until every ballot variant attached to it reaches a terminal status (`PASSED`, `REJECTED`, or `EXPIRED`) [4](#0-3) .

The cleanup/finalization path, `afterInboundBallotTerminal`, is invoked by the generic ballot machine in `x/uvalidator` every time *any* inbound ballot reaches a terminal state. Because ballot IDs are one-way digests that cannot be reversed back to their owning `utx_key`, the hook must scan the *entire* `PendingInbounds` collection with `k.PendingInbounds.Walk(ctx, nil, ...)`, iterating every entry's `Variants` slice looking for a matching `BallotId`:

```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [5](#0-4) 

An attacker fully controls how many distinct inbound observations exist concurrently: by submitting many cheap/dust transactions through the gateway on a supported external chain (no minimum-deposit or per-source rate limiting was found in `VoteInbound`, `RecordInboundVote`, or `uregistry`'s chain-inbound-enabled check [6](#0-5) ), each event is independently observed by honest Universal Validators and produces a new distinct `PendingInboundEntry` the moment the first UV votes. Because entries are only removed on ballot *finalization*, and finalization of every unrelated entry triggers a full O(n) scan of the whole map, an attacker can inflate `n` (the number of concurrently in-flight, unresolved inbound observations) by generating many events faster than the block-by-block finalization drains the backlog. Every subsequent `MsgVoteInbound` that finalizes any ballot (including votes on entirely unrelated, legitimate user deposits) then pays the cost of scanning the whole backlog, so the finalization work is effectively O(n²) to drain a backlog of size n. This directly threatens the throughput/availability of `x/uexecutor`'s inbound-execution hot path — the same path that mints PRC20s and runs user payloads for every legitimate crosschain deposit — creating a state where honest users experience degraded or blocked inbound processing purely from an unprivileged attacker spamming cheap external-chain transactions, with no admin or validator misbehavior required.

This is the direct analog of the reported bug class: an ever-referenced, unbounded collection (`pool[]` in the original report, `PendingInbounds` here) is walked in full on a critical accounting/execution path (`claimCalculation`/`getCurrentShareRaw` there, ballot finalization here) with no cap on how many entries an unprivileged actor can cause to exist.

### Impact Explanation
If exploited at scale, this degrades or halts a core universal-execution function (inbound ballot finalization / UTX creation), which gates minting PRC20s and executing user payloads for all inbound crosschain transactions on Push Chain. This can manifest as slow/failed inbound processing for legitimate users during the attack window, i.e., a reachable, non-network-level denial of service triggered purely by unprivileged external-chain activity, matching the "denial of service only when it is not network-level and is reachable without privileged control" in-scope category. It does not itself corrupt funds or state, so the direct impact is medium rather than a fund-loss/critical finding; severity should be judged against how quickly `n` can be inflated relative to per-block gas/CPU budgets in production (unverified in this scan — the analysis is based on code structure, not measured gas costs).

### Likelihood Explanation
Low-to-medium. The attacker needs external-chain gas to generate enough distinct gateway events fast enough to outpace validator finalization throughput, and validators can eventually drain the backlog given time (unlike the original report's permanently-growing, never-shrinking `pool[]`). The window of degraded service is bounded by how quickly `PendingInbounds` entries get finalized, but as long as inbound generation rate > finalization rate, the backlog (and per-scan cost) keeps growing.

### Recommendation
Avoid the full-collection scan in `afterInboundBallotTerminal`. Maintain a secondary index mapping `ballotID -> utxKey` (set alongside `RecordInboundVote`/ballot creation) so the hook can do an O(1) lookup instead of walking all of `PendingInbounds`. Additionally, consider bounding the number of concurrently pending inbound entries per source chain (e.g., a cap or minimum-value threshold for triggering ballot creation) to limit attacker-driven backlog growth.

### Proof of Concept
Conceptual (not executed against a live node):
1. Deploy/observe a supported external chain with `inbound_enabled = true` and no minimum-deposit gate.
2. Submit N distinct dust-value gateway transactions in rapid succession (N large, e.g., several thousand), each with a unique `tx_hash`/`log_index`.
3. Honest Universal Validators observe and cast the first vote for each, causing N `PendingInboundEntry` records to be created via `RecordInboundVote` before any of them finalizes [1](#0-0) .
4. As votes continue to arrive and ballots begin finalizing, every single finalization triggers `afterInboundBallotTerminal`'s `PendingInbounds.Walk`, which is O(N) per call [5](#0-4) .
5. Total work to drain the backlog approaches O(N²), which for a sufficiently large N can materially slow down or (depending on gas/time budgets per block) stall inbound finalization for all users, including legitimate depositors whose unrelated ballots also finalize during this period and thus also pay the O(N) scan cost.

// RecordInboundVote idempotently records a validator's vote on an inbound by
// appending to the per-utx PendingInbounds entry. Creates the entry on the
// first vote for a given utx_key, creates a new variant on the first vote
// of a given (inbound payload bytes / ballotID), and appends the voter to
// an existing variant on subsequent votes for the same payload (deduped).
//
// utx_key = sha256(source_chain:tx_hash:log_index) — see GetInboundUniversalTxKey.
// ballotID = hex(marshal(Inbound)) — see GetInboundBallotKey.
//
// Multiple variants exist for the same utx_key when validators marshal
// slightly different Inbound bytes for the same logical event (different
// decoded fields, formatting, etc.). Each variant tracks which validators
// voted for that exact byte sequence so operators can investigate divergence.
func (k Keeper) RecordInboundVote(
	ctx context.Context,
	inbound types.Inbound,
	voter string,
	ballotID string,
) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	height := uint64(sdkCtx.BlockHeight())
	utxKey := types.GetInboundUniversalTxKey(inbound)

	entry, err := k.PendingInbounds.Get(ctx, utxKey)
	if err != nil && !errors.Is(err, collections.ErrNotFound) {
		return err
	}
	if errors.Is(err, collections.ErrNotFound) {
		entry = types.PendingInboundEntry{
			UtxKey:          utxKey,
			CreatedAtHeight: height,
		}
	}

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}

### `PendingInbounds`

- **Created** by the FIRST validator vote on a given inbound (`RecordInboundVote`
  inside `VoteInbound`). The chain learns about the source-chain event from
  validator observations.
- **Keyed** by `utx_key = sha256(source_chain:tx_hash:log_index)`.
- **Variant-aware:** when validators marshal slightly different `Inbound` bytes
  for the same logical event (different decoded fields, formatting, etc.), each
  unique payload becomes its own `InboundVariant` inside the entry, with its
  own `ballot_id`, `voters[]`, and `terminal_status`.
- **Removed** when ALL related ballot variants reach a terminal state. If any
  variant ended `PASSED`, the existing post-finalization path in `VoteInbound`
  produced a `UniversalTx`. If ALL variants ended `EXPIRED`/`REJECTED`, the
  full per-variant audit trail is moved to `ExpiredInbounds` for the future
  escape-hatch refund flow.
- The cleanup-on-terminal logic lives in `keeper/ballot_hooks.go` (the
  `BallotHooks` impl wired into `x/uvalidator`).
```

func (k Keeper) VoteInbound(ctx context.Context, universalValidator sdk.ValAddress, inbound types.Inbound) error {
	// Canonicalize first so every derived key + the stored inbound use one
	// representation per logical event.
	inbound.Canonicalize()

	k.Logger().Info("vote inbound received",
		"validator", universalValidator.String(),
		"source_chain", inbound.SourceChain,
		"tx_hash", inbound.TxHash,
		"tx_type", inbound.TxType.String(),
		"sender", inbound.Sender,
	)

	// Check inbound enabled before any state changes
	enabled, err := k.uregistryKeeper.IsChainInboundEnabled(ctx, inbound.SourceChain)
	if err != nil {
		return errors.Wrap(err, "failed to check inbound enabled")
	}
	if !enabled {
		k.Logger().Warn("vote inbound rejected: chain inbound disabled", "source_chain", inbound.SourceChain)
		return fmt.Errorf("inbound is disabled for chain %s", inbound.SourceChain)
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Step 1: Derive UTX key from the original inbound data (source_chain:tx_hash:log_index)
	universalTxKey := types.GetInboundUniversalTxKey(inbound)
	found, err := k.HasUniversalTx(ctx, universalTxKey)
	if err != nil {
		return errors.Wrap(err, "failed to check UniversalTx")
	}
	if found {
		k.Logger().Warn("vote inbound rejected: utx already exists", "utx_key", universalTxKey)
		return fmt.Errorf("universal tx with key %s already exists", universalTxKey)
	}
