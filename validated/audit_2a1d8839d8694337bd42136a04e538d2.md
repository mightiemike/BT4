### Title
L1-to-L2 messages are permanently marked "consumed" even when the corresponding L1 handler transaction execution reverts, causing permanent loss/freezing of bridged assets - (File: `crates/blockifier/src/transaction/l1_handler_transaction.rs`, `crates/apollo_batcher/src/block_builder.rs`)

### Summary
When an L1-to-L2 message is delivered as an `L1HandlerTransaction`, the sequencer unconditionally records the transaction hash as "consumed" regardless of whether the destination entry-point call actually succeeds. Any revert (out-of-gas against the fixed protocol-wide gas cap, a bug in the target contract, or any other execution failure) results in the L1 message being irrevocably marked as processed, with no path to retry it, mirroring the Connext `Executor.sol` bug class where an arbitrary call failure still consumes the transferId/message.

### Finding Description
`L1HandlerTransaction::execute_raw` bounds the L2 gas available to the call to a fixed, protocol-wide constant (`l1_handler_max_amount_bounds.l2_gas`), independent of what the L1 sender actually needs or paid for on L1: [1](#0-0) 

If the call's execution fails (either exceeding the fixed L2-gas bound, hitting the post-execution `FeeCheckReport::check_all_gas_amounts_within_bounds` check, or any other execution error), the state changes are rolled back (`execution_state.abort()`) and a "reverted" `TransactionExecutionInfo` is returned as `Ok(...)` — the transaction is *not* treated as failed at the executor level: [2](#0-1) 

Downstream, in the batcher's block builder, every `InternalConsensusTransaction::L1Handler` is unconditionally inserted into `consumed_l1_handler_tx_hashes` *before* the match on the execution `result`, i.e., regardless of whether the transaction executed successfully, reverted, or even failed at the executor level with a hard `TransactionExecutorError`: [3](#0-2) [4](#0-3) 

This is explicitly confirmed by the test `failed_l1_handler_transaction_consumed`, which shows that even an executor-level `StateError` still results in the tx hash being included in `consumed_l1_handler_tx_hashes`: [5](#0-4) 

Once a block is committed, this "consumed" list is sent to the L1 provider, which transitions the message state from `Pending` to `Committed`, permanently removing it from the set of resendable/retryable L1 messages: [6](#0-5) 

The Starknet OS re-execution mirrors this: `consume_l1_to_l2_message` is called unconditionally before invoking the entry point, and it is only skipped for transactions the OS was told in advance are reverted (i.e., consumption still occurs for any transaction that reverts during/at entry-point execution once the message-consumption step has already run): [7](#0-6) 

Because on the L1 side the corresponding message was already consumed by the Starknet core contract when the L1 sender's transaction was mined, and the sequencer additionally marks it "consumed" on L2 upon any outcome (success or revert), there is no mechanism to resend or replay the message. Any L2-side logic that was supposed to run as part of processing that message (e.g., unlocking/minting a bridged NFT, crediting funds in a custom bridge contract) is permanently skipped if it reverted — the assets associated with the L1 deposit become unrecoverable, exactly matching the reported bug class ("arbitrary call execute failure handler ... may break some use case for example NFT bridge").

### Impact Explanation
Any L1-to-L2 message whose target entry point exceeds the fixed `l1_handler_max_amount_bounds.l2_gas` cap, or otherwise reverts (bug in target contract, unexpected state, reentrancy guard, etc.), causes:
- The message to be permanently marked consumed (unretriable) on L2.
- The corresponding L1 message already consumed on L1 (no resend possible).
- Any assets/state changes the L1 handler was supposed to produce (e.g., NFT mint/unlock, token credit in a custom bridge) never occur.

This results in a permanent freezing/loss of user funds for any protocol built on top of L1-handler-based bridging whose destination logic can revert or exceed the gas bound, with no built-in recovery path in the sequencer.

### Likelihood Explanation
This is not an edge case requiring a malicious actor: any legitimate L1 sender whose calldata triggers L2 logic that reverts (due to complex contract state, insufficient fixed L2-gas allowance, or a bug in the destination contract) will trigger this behavior deterministically. Since `l1_handler_max_amount_bounds` is a fixed, protocol-wide constant unrelated to the L1 sender's own resource provisioning, any sufficiently complex or state-dependent L1 handler call is at risk.

### Recommendation
Do not treat an L1 handler transaction as "consumed" purely because a block was produced containing it if its execution reverted. Consider one or more of:
- Distinguish between "processed" (finalized in a block, whether reverted or not) and irreversible asset-affecting side effects; require destination contracts to implement idempotent/retry-safe patterns explicitly, and clearly document that reverted L1 handler calls will not be retried by the sequencer.
- Provide a protocol-level mechanism (e.g., a queryable/callable "failed L1 handler" registry) enabling users/integrators to detect and handle reverted L1-to-L2 messages before or as part of L1 consumption, decoupling the L1 core-contract consumption step from irreversible commitment on L2.
- Reassess whether the fixed `l1_handler_max_amount_bounds.l2_gas` cap is sufficiently high, or make it configurable/related to the fee paid on L1, to reduce the likelihood of legitimate calls reverting due to gas exhaustion.

### Proof of Concept
1. A bridge contract on L2 sends an L1-to-L2 message via `send_message_to_l2` from L1, where the L2 handler performs a complex/state-dependent action (e.g., minting/unlocking an NFT) that either (a) requires more L2 gas than the fixed `l1_handler_max_amount_bounds.l2_gas`, or (b) reverts due to a legitimate state condition (e.g., front-run resource already claimed).
2. The sequencer executes the L1Handler transaction; `run_execute` fails, `execution_state.abort()` rolls back state changes, and `Ok(l1_handler_tx_execution_info(None, receipt, Some(error)))` is returned as shown in `crates/blockifier/src/transaction/l1_handler_transaction.rs:117-141`.
3. In `collect_execution_results_and_stream_txs`, the transaction hash is unconditionally added to `consumed_l1_handler_tx_hashes` (`crates/apollo_batcher/src/block_builder.rs:644-649`), irrespective of the revert.
4. The block is committed; the L1 Provider transitions the message from `Pending` to `Committed` per `docs/diagrams/06-l1-handler-flow.md:163-180`.
5. The NFT/asset that the L1 sender locked/deposited on L1 is never unlocked/minted on L2 (the handler reverted), and the message can never be resent or retried — the asset is permanently lost, matching the exact scenario described in the referenced Connext report.
