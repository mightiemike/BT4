### Title
Missing verification that both microblock headers share the same sequence/fork position allows an attacker-crafted, non-conflicting header pair to hijack a `PoisonMicroblock` report - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`StacksChainState::check_microblock_header_signer` (called from `handle_poison_microblock`) only verifies that `mblock_header_1` and `mblock_header_2` were signed by the same public key hash; it never verifies that the two headers actually occupy the same sequence position (i.e., that they genuinely constitute a fork/equivocation at the reported sequence). `handle_poison_microblock` then blindly trusts `mblock_header_1.sequence` as "the point of equivocation" when deciding whether to overwrite a stored report.

### Finding Description
The claimed equality is: `stored (reporter, sequence)` should equal `(reporter, the earliest sequence at which mblock_header_1 and mblock_header_2 both validly exist and conflict)`.

Tracing the path:
- `check_microblock_header_signer` recovers `pkh1`/`pkh2` from the two headers via `check_recover_pubkey` and only rejects if `pkh1 != pkh2` [1](#0-0) . It does not check `mblock_header_1.sequence == mblock_header_2.sequence`, nor that the two headers actually differ in content while sharing a common parent/position (the real definition of a fork proof).
- `handle_poison_microblock` then uses whichever report has a strictly lower `mblock_header_1.sequence` to overwrite the stored `(reporter, seq)` pair, using only `mblock_header_1.sequence` — never `min(seq1, seq2)` and never confirming that `seq1` is where an actual conflict with `seq2` occurs [2](#0-1) .

For a *genuine* single equivocation event, the two conflicting microblocks necessarily share the same sequence number (that is what makes them a fork at that position), so merely re-ordering which header is passed as "header 1" vs "header 2" for a real matched conflicting pair has no effect — both orderings yield the same sequence value. The exploit as literally described ("swap header_1/header_2 order relative to an honest report") therefore does not change the stored value for a genuine matched pair, and this specific mechanism does not break the equality.

The actual latent gap is broader than reordering: because there is no check that `mblock_header_1` and `mblock_header_2` share a sequence number or genuinely conflict, an attacker could in principle mix an unrelated, non-conflicting, validly-signed header (e.g., an early legitimate microblock from the same miner) as `mblock_header_1` with a genuinely-conflicting header as `mblock_header_2`, claiming an artificially low sequence. I could not verify from the available files whether any additional validation exists elsewhere (e.g., during transaction admission, mempool checks, or the payload's static validity checks) that enforces `seq1 == seq2` or requires the headers to attach to a common ancestor. No such check was found in `handle_poison_microblock` or `check_microblock_header_signer` — an index-limits caveat is not applicable here since the full function bodies were read, but earlier-stage validation code outside these two functions was not located within the tool budget.

### Impact Explanation
If the missing check is confirmed absent everywhere in the transaction-acceptance path, an attacker could register a `(reporter, sequence)` record with a sequence lower than the true equivocation point, causing the miner-reward commission to be paid to the attacker instead of the honest reporter. This is a reward mis-payment bounded to the commission fraction of a single miner's coinbase, not a chain split or double global-reward payment, matching the **High** category ("poison or reward mis-payment bounded to fees").

However, as literally described (order-swap of an honest reporter's own submitted, genuinely-matched header pair), the exploit does not work, because both headers of a real equivocation share the same sequence value, and the stored value is unaffected by argument order.

### Likelihood Explanation
The specific "swap order" mechanism as posed in the question requires no such precondition to succeed — it is a no-op against a genuinely matched header pair. Exploiting the broader "mismatched header" gap requires the attacker to have access to at least one legitimately-signed, non-conflicting microblock header from the target miner in addition to a real conflicting pair, which is plausible for any unprivileged observer of the network, but I could not confirm that no other validation stage blocks this within this repository given the tool budget used.

### Recommendation
In `check_microblock_header_signer` (or immediately after it in `handle_poison_microblock`), additionally require `mblock_header_1.sequence == mblock_header_2.sequence` and that the two headers are distinct (different hashes/signatures) before treating them as proof of equivocation; use that shared sequence (not an unchecked `mblock_header_1.sequence`) as the reported/stored value.

### Proof of Concept
Not applicable as a valid finding for the specific "order-swap" mechanism described — a Rust integration test constructing a genuine equivocation pair (`seq1 == seq2`, differing content, same signer) and submitting it in both header orders would show the stored `(reporter, sequence)` tuple is identical in both orders, confirming the equality is not broken by mere reordering.

    /// Given two microblock headers, were they signed by the same key?
    /// Return the pubkey hash if so; return Err otherwise
    fn check_microblock_header_signer(
        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
