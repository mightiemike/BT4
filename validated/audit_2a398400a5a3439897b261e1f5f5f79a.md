### Title
Webhook HMAC validation does not bind the `X-Shopify-Shop-Domain` header to the signed body, enabling cross-tenant session hijacking via webhook replay - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
`shopify.webhooks.validate`/`process` (and the `authenticate.webhooks` helpers built on top of it) verify webhook authenticity solely by recomputing an HMAC over the **raw request body**. The `domain` (shop), `topic`, `webhookId`, and `apiVersion` values that determine *which shop's session gets loaded and handed to the handler* are read directly from HTTP headers **after** the HMAC check succeeds, and those header values are never included in the signed payload. This mirrors the audited bug class: a security check is performed on one value (the HMAC over the body), while a different, unauthenticated value (`domain` header) is used to select the "share"/tenant that the rest of the code operates on.

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` first calls `validateHmacFromRequestFactory` which validates the request by comparing the `X-Shopify-Hmac-Sha256` header against an HMAC computed over `rawBody` only: [1](#0-0) 

Once that body-only HMAC check passes, `checkWebhooksHeaders`/`checkEventsHeaders` pull the `domain`, `topic`, `apiVersion`, and `webhookId` straight out of the (unsigned) headers and return them as trusted fields: [2](#0-1) 

Nowhere in `stringifyQueryForAdmin`/`stringifyQueryForAppProxy`/`generateLocalHmac` (used for OAuth/app-proxy) or in the webhook body-HMAC path are these headers folded into the signed material — for webhooks, `createSHA256HMAC(config.apiSecretKey, rawBody, ...)` only ever covers the JSON body.

Downstream, `authenticateWebhookFactory` (react-router/remix) takes `check.domain` — the unauthenticated header value — and uses it directly to look up and load the shop's offline session, then attaches an authenticated Admin API client for that session to the webhook context handed to the app's callback: [3](#0-2) 

Because `domain` is never part of the signed content, any party who can obtain **one** validly-signed `(rawBody, X-Shopify-Hmac-Sha256)` pair for their own shop (trivial — they just need an app installed on any shop they control, which will legitimately receive webhooks) can replay that exact body+HMAC pair directly to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value for a victim shop. The HMAC check still passes (it only validates the body), `check.domain` resolves to the attacker-chosen victim shop, and `ensureValidOfflineSession(params, check.domain)` loads *the victim's* offline session and access token, which is then exposed to the app's webhook handler as `session`/`admin` — exactly the cross-tenant "steal another party's resources by controlling a value that a check ignores" pattern from the H-05 report (there, the unauthenticated `share` computation bypassed the `allowedBorrow` check that was evaluated on the pre-computed value; here, the unauthenticated `domain` header bypasses the tenant binding that the HMAC check was supposed to enforce).

### Impact Explanation
An attacker with legitimate access to only their own shop (a single "merchant" actor, not privileged) can trigger a webhook delivery to their own app install, capture the valid `(rawBody, hmac)` pair, and replay it against the same app's public webhook route with a forged `X-Shopify-Shop-Domain` header pointing at any other shop that uses the same app. Because the webhook handler loads and exposes the target shop's offline session/access token via `ensureValidOfflineSession(params, check.domain)`, this results in cross-tenant session/access-token disclosure and unauthorized use of another merchant's Admin API access token inside the app's webhook processing logic — comparable in class (though not necessarily in blast radius) to the original "increase share for a different actor than the one that was checked" vulnerability.

### Likelihood Explanation
Exploitability requires only: (1) an app installed on an attacker-controlled shop (trivial to obtain for public apps), (2) the ability to trigger any subscribed webhook topic on that shop (routine merchant action), and (3) direct HTTP access to the app's public webhook endpoint (always internet-reachable, since Shopify delivers webhooks over plain HTTPS with no client-certificate binding enforced by this library). No secrets need to be leaked and no MITM is required — this is a pure "check applies to body, decision applies to header" design gap.

### Recommendation
Bind the `domain` (and ideally `topic`/`webhookId`) values to the cryptographic check instead of trusting them as bare headers after the body HMAC succeeds:
- Include the `X-Shopify-Shop-Domain` (and other decision-relevant headers) in the HMAC-covered payload, or
- After computing/trusting `check.domain`, cross-validate it against an independently-verified source (e.g., an expected shop associated with the webhook subscription/registration, or a lookup keyed by a value that is part of the signed payload), and reject the webhook if they don't match, rather than blindly using the header value in `checkWebhooksHeaders`/`checkEventsHeaders` (`packages/apps/shopify-api/lib/webhooks/validate.ts:99-203`) to select which shop's session to load in `ensureValidOfflineSession`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; ensure the app subscribes to at least one webhook topic (e.g., `PRODUCTS_CREATE`).
2. Trigger that webhook event on `attacker.myshopify.com` (e.g., create a product) and capture the resulting webhook request: the raw JSON body and the `X-Shopify-Hmac-Sha256` header value that Shopify computed and sent.
3. Craft a new HTTP POST to the app's public webhook endpoint (e.g., `/webhooks`) using the exact captured body and `X-Shopify-Hmac-Sha256` header, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com` (a different shop that also has the app installed).
4. `validateHmacFromRequestFactory` recomputes the HMAC over the (unchanged) body and it matches, so `webhookCheck.valid === true`, with `webhookCheck.domain === 'victim.myshopify.com'` taken straight from the forged header — see `checkWebhooksHeaders` at `packages/apps/shopify-api/lib/webhooks/validate.ts:99-134`.
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` with `check.domain = 'victim.myshopify.com'`, loading and exposing the victim's offline session/access token to the app's webhook handler — see `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:33-96`.

Note: I was unable to fully inspect `ensureValidOfflineSession`'s implementation in this session (only its call sites and usage were found via search); a Devin session with full file access should confirm the exact session-loading/token-exposure mechanics in `packages/apps/shopify-app-{express,remix,react-router}/src/(helpers|server/helpers)/ensure-valid-offline-session.ts` to fully validate the end-to-end token exposure before treating this as confirmed.

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);

    missingHeaders,
  );

    headers,
    headerNames.webhookId,
    missingHeaders,
  );

      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
