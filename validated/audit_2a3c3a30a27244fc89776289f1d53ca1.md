### Title
Unvalidated `beneficiary_id` in `DeleteAccountAction` permanently burns the deleted account's balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction::beneficiary_id` is only checked for syntactic validity, never for whether the account exists or can be created. Because the balance transfer to the beneficiary is generated as a "system" refund receipt, and refund receipts are never allowed to implicitly create an account, specifying a beneficiary that does not (yet) exist on-chain causes the entire remaining account balance to be permanently burnt instead of delivered — the exact "unchecked beneficiary → loss of funds" bug class from the reference report.

### Finding Description
`validate_delete_action` in `runtime/runtime/src/action_validation.rs` only runs `validate_action_account_id`, which is a pure format check via `AccountId::validate`: [1](#0-0) [2](#0-1) 

There is no check that `beneficiary_id` refers to an existing account, nor that it is an account that could be implicitly created by a transfer.

When the action executes, `action_delete_account` transfers the account's full balance to the beneficiary via a system-generated refund receipt: [3](#0-2) 

`Receipt::new_balance_refund` explicitly builds this as a transfer "from system": [4](#0-3) 

When this receipt is later applied, `apply_action` determines `is_refund` purely from `predecessor_id().is_system()`, which is true for this receipt: [5](#0-4) 

`check_account_existence`/`implicit_creation_allowed` unconditionally forbid account creation for refund receipts, regardless of account type (named, near-implicit, eth-implicit, deterministic, or universal): [6](#0-5) [7](#0-6) 

If the beneficiary account does not exist (e.g. a valid-looking named account that was never created, or an implicit account id that has never received a transfer), the Transfer action inside the refund receipt fails with `AccountDoesNotExist`. Per NEAR's documented refund semantics, a failing refund receipt's funds are burnt rather than returned anywhere: [8](#0-7) 

This exact "refund fails → funds burnt, no re-delivery" behavior is confirmed by the test `refund_may_not_create_universal_account`, which asserts that a refund to a missing account fails with `AccountDoesNotExist` and never brings the account into existence: [9](#0-8) 

This action is reachable directly from a single signed transaction (`Action::DeleteAccount`) or via a contract calling `promise_batch_action_delete_account` from WASM with an attacker/user-controlled `beneficiary_id`: [10](#0-9) 

### Impact Explanation
Unlike a simple "transfer to nonexistent account" (which the transaction sender initiates and could in principle re-check before committing), `DeleteAccountAction` is irreversible: the account and its state are unconditionally removed in the same receipt (`remove_account` at `runtime/runtime/src/actions.rs:387`) regardless of whether the beneficiary transfer later succeeds. Because the follow-up transfer is a refund receipt that cannot create the target account, any mistake or unawareness of this asymmetric restriction (e.g., beneficiary is a syntactically valid but not-yet-existing named account, or an implicit account whose public key has never been funded) results in the account's entire NEAR balance being permanently burnt with no path to recovery — matching the report's "Fees/funds could not be sent to beneficiary" impact, but total-supply-reducing here rather than merely fee-related.

### Likelihood Explanation
Any account holder issuing a normal `DeleteAccount` transaction, or any contract routing a promise batch through `promise_batch_action_delete_account` with a user/attacker-supplied `beneficiary_id`, can trigger this. No special privileges are required — it is a single, unprivileged transaction. The only requirement is that the beneficiary account does not already exist and is not created earlier in the same receipt (which validation forbids since `DeleteAccount` must be the final action).

### Recommendation
Validate at `validate_delete_action` (or in `action_delete_account`) that `beneficiary_id` corresponds to an account that either already exists or can legitimately be created by the resulting transfer (i.e., don't route the payout as a "system" refund when the target does not exist), or reject the `DeleteAccount` action outright if the beneficiary account is confirmed not to exist at validation time, giving the caller an explicit, actionable error instead of silently burning the balance.

### Proof of Concept
1. Attacker/user account `alice.near` holds `N` NEAR.
2. `alice.near` submits `SignedTransaction` with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "ghost.near" })` where `ghost.near` is a syntactically valid, never-created account (passes `AccountId::validate`).
3. `action_delete_account` immediately removes `alice.near` and enqueues `Receipt::new_balance_refund("ghost.near", N)` (`runtime/runtime/src/actions.rs:380-387`).
4. When this refund receipt is applied, `apply_action` sets `is_refund = true` (predecessor is `"system"`); `check_account_existence` for the inner `Transfer` sees `account.is_none()` and `implicit_creation_allowed` returns `false` for a refund, producing `ActionErrorKind::AccountDoesNotExist`.
5. Per `docs/RuntimeSpec/Refunds.md:10-13`, the failed refund's deposit is burnt rather than returned to `alice.near` or created at `ghost.near`.
6. Net effect: `N` NEAR is permanently removed from total supply; neither `alice.near` (deleted) nor `ghost.near` (never created) ever receives it.

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.
