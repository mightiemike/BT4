### Title
Interest-index clock (`last-update`) only advances when the index rounds to a non-zero delta, allowing a rate change to be mis-applied retroactively across the "invisible" time window — ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` counterparts) accrues interest via `accrue`, which only updates the `last-update` timestamp variable when at least one of the borrow index (`index`) or liquidity index (`lindex`) actually changes value: [1](#0-0) 

This mirrors the "clock advanced only on change" analog class: the reported Moonwell bug was about an unguarded time parameter (`_endTime`) corrupting downstream index math; here the vault's `last-update` clock (the anchor for all future `next-index`/`next-liquidity-index` math) is silently left stale whenever `interest-rate()` evaluates to `u0` for the current utilization, because `next-index` short-circuits: `(if (get accrue states) idx (... calc-multiplier-delta ...))` and `calc-multiplier-delta` with `rate = u0` returns `INDEX-PRECISION` exactly, so `next == idx` and `nliq == lidx`, and the `(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)` guard never fires. [2](#0-1) 

### Finding Description
`next-index` and `next-liquidity-index` compute `time-delta = stacks-block-time - (var-get last-update)` and apply the current `interest-rate()` (derived from current `utilization()`, itself dependent only on the vault's live `assets`/`total-debt` state) over that whole delta: [3](#0-2) 

`last-update` is the single "clock" both index calculations rely on to know how much elapsed time to compound. It is only ever advanced from inside `accrue`, and only conditionally — when the computed indices differ from the stored ones: [4](#0-3) 

If the vault sits at `utilization() = u0` (no outstanding debt) for a period, and the interest-rate curve's rate at 0% utilization is `u0` (a plausible/likely IR-curve configuration point, since a base rate of 0 at 0% utilization is common for kink models), then every `accrue` call during that period computes `next == idx` and `nliq == lidx` exactly, and `last-update` is never advanced — even though real block time (`stacks-block-time`) is moving forward and multiple deposits/borrows/repayments may occur in between. `last-update` remains frozen at its old value.

When utilization/rate later becomes non-zero (e.g., a borrow occurs) and interest resumes accruing, the very first non-trivial `accrue` call computes `time-delta` against the *stale* `last-update`, spanning the entire "invisible" 0%-utilization window plus the new active period, and applies the **current** rate (computed from the state prevailing at the moment `accrue` finally runs) uniformly across that whole stale span — not the (correctly zero) rate that actually applied during the dormant window. Because the guard is an OR over two independently-rounded index deltas (`index` uses round-up, `lindex` uses round-down), the two can diverge in whether they detect "no-op", but the shared clock (`last-update`) is only reset when *both* directions register a change, so partial/rounding-driven no-ops on one side while the other stays flat can also extend the stale window unnecessarily.

This is structurally identical to the external report's root cause class: a critical timing value (there, `_endTime`; here, `last-update`) is not defensively validated/advanced independent of the value it is meant to gate, so the index-calculation math downstream silently uses a wrong elapsed-time base, corrupting the market/borrow/liquidity index.

### Impact Explanation
Both `index` (debt) and `lindex` (liquidity/supply) drive: 1) how much debt a borrower actually owes (`total-debt`, `debt-preview`, liquidation LTV math in `market.clar`'s `liquidate`), and 2) how much the `zft` supply-share token is worth (`convert-to-assets-preview`, redemption value). A frozen `last-update` clock that later "catches up" by applying the current rate to an inflated stale `time-delta` causes the index to jump by more (or less) than the interest actually owed for that period, silently mispricing debt owed by borrowers and the redemption value of liquidity providers' shares. This falls under temporary/permanent freezing or misallocation of unclaimed yield — funds are not directly drained in one atomic step, but future accrual math for all users of that vault becomes systematically wrong, which can freeze or misallocate unclaimed supply yield across the vault.

### Likelihood Explanation
Requires the vault to pass through a period of exactly-zero effective interest rate (zero utilization with a zero base rate point on the IR curve) long enough for `stacks-block-time` to move meaningfully, followed by a state change that reactivates non-zero utilization. This is a normal operational sequence (all debt repaid, then a new borrow later) rather than an attacker-crafted edge case, making it plausible in ordinary vault lifecycle, though it depends on the deployed IR-curve configuration having a literal `u0` rate at `u0` utilization — this specific parameter value could not be confirmed from the available index and would need to be verified against the deployed `points-ir` configuration.

### Recommendation
Decouple the `last-update` timestamp advance from whether the computed index actually changed. Always set `last-update` to `stacks-block-time` whenever `accrue`'s non-paused branch executes (regardless of whether `next`/`nliq` differ from stored `index`/`lindex`), so the clock never silently stalls independent of the index math it is meant to anchor.

### Proof of Concept
Conceptual sequence (cannot be executed without access to the deployed `points-ir` values, which were not available in the indexed contract source):
1. Vault `v0-vault-stx.clar` reaches `total-debt = u0` (all borrowers repaid), so `utilization() = u0`.
2. If the IR curve's rate at 0% utilization is `u0`, every subsequent `accrue()` call (triggered by deposits/redeems) computes `next == (var-get index)` and `nliq == (var-get lindex)`, so the `var-set last-update` branch in `accrue` never executes: [5](#0-4) .
3. Time passes (multiple blocks), `last-update` remains stuck at the pre-dormancy timestamp.
4. A new borrow occurs, `utilization()` becomes non-zero, `interest-rate()` returns the current non-zero rate.
5. The next `accrue()` call computes `time-delta = stacks-block-time - last-update` spanning the *entire* dormant + active window, and applies the *current* rate over that whole span via `calc-multiplier-delta`, over- or under-crediting interest relative to what should have accrued (zero during dormancy, current rate only during the active portion): [6](#0-5) .

This cannot be treated as fully confirmed without checking the actual deployed `points-ir` word values (base-rate-at-zero-utilization), which the current index does not surface.
