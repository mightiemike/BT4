### Title
`replay-verify` silently ignores state-checkpoint root divergence in `TransactionOutput::ensure_match_transaction_info` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the sole per-transaction integrity check used by the chunk-executor replay-verification path (`verify_execution` in `execution/executor/src/chunk_executor/mod.rs`), only validates transaction status, gas used, write-set hash, event root hash, and transaction hash against the archived `TransactionInfo`. It explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the actual state (JMT) root.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  checks:
- execution status
- gas used
- `write_set_hash == txn_info.state_change_hash()`
- event root hash
- (implicitly, transaction hash is checked by the caller elsewhere)

but explicitly skips state root checks, with a self-documenting TODO: [2](#0-1) 

This function is the only per-transaction correctness check performed by `ChunkExecutorInner::verify_execution`, which re-executes historical transactions with the VM and compares the result to archived `TransactionInfo`s, used by replayer/replay-verify tooling (`db-tool`'s `replay_on_archive`/verify-execution mode): [3](#0-2) 

Unlike normal block/chunk execution — where `DoStateCheckpoint` independently computes the state summary and cross-checks it against `known_state_checkpoints`/`known_hot_state_checkpoints` derived from the committed `TransactionInfo`s (see `execution/executor/src/chunk_executor/mod.rs:373-413` and `execution/executor/src/workflow/do_state_checkpoint.rs:98-190`) — the `verify_execution` replay path calls `DoGetExecutionOutput::by_transaction_execution` directly and never runs `DoStateCheckpoint`, so no other code path independently recomputes and compares the JMT state root during this verification.

### Impact Explanation
The `write_set_hash`/`state_change_hash` comparison only proves the *raw write set* (key/value pairs written by this transaction) matches; it does not prove that applying that write set to the correct prior state produces the correct new state root. If the underlying state-merklization logic (JMT batch update, sharding, hot/cold state split, or the newer position-state tree) has a determinism bug, VM upgrade regression, or hard-fork-only divergence that corrupts the computed state root while leaving individual write sets/events/gas/status unchanged, `replay-verify` would report success even though the state root diverges from the authenticated chain history. This directly matches the stated in-scope impact "Hard-fork-only divergence during commit, replay, ... accepted as valid" and "committed state that differs from the correct VM result... accepted as valid," since this tooling exists specifically to catch such divergences before/after upgrades, and it is blind to state-root regressions by design (confirmed by the code's own TODO comment).

### Likelihood Explanation
This is not exploitable by an external attacker to corrupt consensus-committed state directly — it does not itself write bad state into a live node's storage. Its risk is that it provides false assurance during replay-verification (used to validate execution-determinism/hard-fork safety), so a genuine state-root-diverging bug elsewhere could go undetected by this specific safety net. Likelihood of the gap being hit depends on there being an actual separate state-root bug for it to fail to catch; as a standalone code quality/coverage issue it is deterministic and always present (the check is unconditionally skipped), not probabilistic.

### Recommendation
Extend `ensure_match_transaction_info` (or add a companion check in `verify_execution`) to also validate `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` by running the same `DoStateCheckpoint` computation used in `update_ledger`, so replay-verification actually authenticates the full state root, not just the write set. This should be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any state-checkpoint dependent feature) is enabled, as the existing TODO already notes.

### Proof of Concept
Not applicable as a live exploit — this is a verification-coverage gap, not a directly triggerable state-corruption bug. Demonstration would require: (1) a hypothetical/injected bug in JMT state-root computation that changes the resulting `state_checkpoint_hash` while leaving write set bytes/events/gas/status identical, then (2) showing `db-tool replay-verify` against an archive with the corrected `TransactionInfo` still reports success, because `ensure_match_transaction_info` never inspects `state_checkpoint_hash()`.

**Caveat:** I could not fully trace whether any other independent guard exists specifically in the `db-tool`/aptos-debugger replay entry points (I found references in `storage/db-tool/src/lib.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` but did not have remaining iterations to read their full bodies), so it's possible a redundant check exists elsewhere in the CLI wrapper that partially mitigates this. Given the explicit TODO comment in the type itself acknowledging the gap, I'm confident the core comparator function is missing this check, but cannot fully rule out an external mitigation.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
