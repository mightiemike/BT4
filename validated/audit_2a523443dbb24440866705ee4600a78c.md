### Title
`TokenConfig.Enabled` flag is never enforced in inbound execution — disabled tokens still mint/deposit funds - (File: x/uregistry/keeper/keeper.go, x/uexecutor/keeper/execute_inbound_gas.go, x/uexecutor/keeper/execute_inbound_funds_and_payload.go)

### Summary
The `TokenConfig.Enabled` field is documented as the mechanism to disable a token "for minting/bridging" [1](#0-0) , analogous to setting an adapter's ratio to 0 to block it in the AdapterVault report. However, `GetTokenConfig` — the lookup used by every inbound-execution code path — returns the config unconditionally without checking `Enabled` [2](#0-1) , and none of the consumers (`ExecuteInboundGas`, `ExecuteInboundFundsAndPayload`) gate on it before minting/depositing PRC20 funds [3](#0-2) [4](#0-3) .

### Finding Description
`x/uregistry` exposes `TokenConfig.Enabled` as a per-token kill switch, intended to be the equivalent of the AdapterVault's "set ratio to 0 to stop the adapter from receiving funds" mechanism, but for a specific external token/chain pairing (e.g., after a compromised or misbehaving token bridge, oracle desync, or discovered accounting bug on that token) [5](#0-4) .

`Keeper.GetTokenConfig` simply does a KV lookup and returns whatever is stored, with zero reference to the `Enabled` field [2](#0-1) . This is unlike `IsChainInboundEnabled`/`IsChainOutboundEnabled`, which are explicit boolean gates that `x/uexecutor` checks before processing inbound/outbound flows (confirmed by `chain_enabled_test.go` and the upgrade note in `app/upgrades/chain-meta/upgrade.go`) [6](#0-5) [7](#0-6) . No parallel `IsTokenEnabled`-style function exists or is invoked anywhere in `x/uexecutor`.

Tracing the actual fund-moving paths:
- `ExecuteInboundGas` calls `GetTokenConfig` purely to resolve the PRC20 contract address and then proceeds to swap/deposit — it never checks `tokenConfig.Enabled` [8](#0-7) .
- `ExecuteInboundFundsAndPayload` similarly calls `depositPRC20` for the resolved asset without checking `Enabled` [4](#0-3) .
- `execute_inbound_gas_and_payload.go` follows the same `GetTokenConfig` → deposit pattern.

Because a token's `Enabled` field is never consulted by the actual fund-crediting logic, an admin/governance action that flips `Enabled=false` on a token (e.g., after discovering the token's bridge/oracle is compromised or the token's accounting model is broken) does not actually stop deposits for that token — exactly mirroring the "ratio=0 does not stop the neutral adapter" bug: the intended kill switch exists in the data model but the enforcement point checks a different/no condition, so the "disabled" resource keeps receiving/minting funds.

### Impact Explanation
If a token is marked disabled because of a known issue (compromised bridge, price-oracle mismatch, broken liquidity cap enforcement, discovered double-mint bug on that specific token, etc.), inbound votes referencing that token's `AssetAddr`/`SourceChain` pair will still pass `GetTokenConfig`, resolve a valid PRC20 address, and execute `depositPRC20`/mint flows normally. This allows continued unauthorized minting of a PRC20 asset that the protocol has explicitly tried to shut off, potentially compounding losses from whatever originally triggered disabling the token (unauthorized mint, incorrect accounting, liquidity-cap bypass). This falls squarely within the allowed impact ("unauthorized mint... of user or protocol-controlled funds" and "corruption of PRC20 or native asset accounting... token mapping").

### Likelihood Explanation
High reachability: any ordinary user submitting/observing a standard inbound (`MsgVoteInbound`) for a token whose `TokenConfig.Enabled` has been set to `false` triggers this path with no special privilege required, and honest validators will vote/finalize it normally since nothing in the voting or execution pipeline consults `Enabled`. The only requirement is that a token was previously disabled by an admin — a state entirely plausible in production incident-response scenarios, which is precisely when this gap matters most.

### Recommendation
Add an explicit `IsTokenEnabled`/equivalent check in `x/uregistry/keeper` and enforce it in every inbound execution entry point (`ExecuteInboundGas`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`, and any related deposit/mint call), similar to how `IsChainInboundEnabled` gates `VoteInbound`/`ExecutePayload`. When `Enabled == false`, the inbound should fail pre-execution validation and route to the standard `INBOUND_REVERT` flow, mirroring the chain-level enable/disable enforcement that already exists.

### Proof of Concept
1. Admin registers `TokenConfig{Chain: "eip155:11155111", Address: <tokenAddr>, Enabled: true, NativeRepresentation: {ContractAddress: <prc20Addr>}}`.
2. Incident occurs (e.g., token bridge compromised); admin calls `MsgUpdateTokenConfig` to set `Enabled=false` for that token, intending to stop further deposits.
3. Attacker/user submits a new source-chain deposit event for that same `(chain, tokenAddr)` pair; validators vote via `MsgVoteInbound` and reach quorum (nothing in `VoteInbound`/`ExecuteInboundGas`/`ExecuteInboundFundsAndPayload` checks `TokenConfig.Enabled`).
4. `GetTokenConfig` returns the config (still present, `Enabled=false` ignored) and `depositPRC20`/swap executes as if the token were still active, minting/crediting PRC20 to the recipient.
5. Repeat step 3 indefinitely — the "disabled" token continues to accept and mint funds exactly like the neutral adapter in the original report continued to receive vault deposits despite being nominally blocked.

// IsChainInboundEnabled checks if inbound is enabled for a given chain
func (k Keeper) IsChainInboundEnabled(ctx context.Context, chain string) (bool, error) {
	config, err := k.GetChainConfig(ctx, chain)
	if err != nil {
		if errors.Is(err, collections.ErrNotFound) {
			// chain not found
			return false, nil
		}
		return false, err
	}
	if config.Enabled == nil {
		return false, nil
	}
	return config.Enabled.IsInboundEnabled, nil
}

func (k Keeper) GetTokenConfig(ctx context.Context, chain, address string) (types.TokenConfig, error) {
	storageKey := types.GetTokenConfigsStorageKey(chain, address)
	config, err := k.TokenConfigs.Get(ctx, storageKey)
	if err != nil {
		return types.TokenConfig{}, err
	}
	return config, nil
}
