## Analog Found

### Title
Sandwichable 5% slippage tolerance on inbound gas-abstraction autoswap enables value extraction from user PRC20→native conversions - (File: `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/evm.go`)

### Summary
The external report describes price manipulation of a newly created AMM pool via front-running, which lets an attacker extract value from a victim's deposit due to insufficient price protection. Push Chain's `x/uexecutor` module performs an analogous on-chain AMM swap — converting a user's bridged PRC20 token into native `WPC`/gas token during `GAS`/`GAS_AND_PAYLOAD` inbound execution — using a hardcoded 5% slippage tolerance computed from a spot quote fetched immediately before the swap executes. An unprivileged attacker who observes the pending `MsgVoteInbound` (the quorum-finalizing vote) in the mempool can sandwich the swap to extract value from the user's conversion, since the tolerance band is wide enough to absorb meaningful price manipulation and the quote/swap are not resistant to same-block manipulation.

### Finding Description
When Push Chain processes a `GAS` or `GAS_AND_PAYLOAD` inbound (fee abstraction: converting a bridged token into native gas for the user's UEA), it computes a swap quote and immediately executes the swap in the same keeper call: [1](#0-0) 

The quote is obtained via a `QuoterV2.quoteExactInputSingle` simulation call: [2](#0-1) 

and then a fixed, hardcoded 5% slippage buffer is applied before dispatching the real swap: [3](#0-2) 

Both the quote and the subsequent swap execution occur within the state transition triggered by the validator (`Universal Validator`) `MsgVoteInbound` transaction that finalizes the inbound ballot and dispatches `ExecuteInbound` → `ExecuteInboundGas` → `CallPRC20DepositAutoSwap`. This whole sequence is reachable by an ordinary, honest quorum of validators voting on a legitimate user deposit — no privileged or malicious validator behavior is required for the swap itself to occur.

Because Push Chain's execution layer is EVM-compatible and blocks are proposed by validators from a public mempool, an attacker can:
1. Observe the pending `MsgVoteInbound` transaction that will trigger the quorum-finalizing execution of a large `GAS`/`GAS_AND_PAYLOAD` inbound.
2. Submit (with higher gas/priority, or via other transaction-ordering influence available to any user) a large swap against the same `WPC`↔`PRC20` pool immediately before it, moving the pool price unfavorably for the victim's swap.
3. Let the victim's autoswap execute against the manipulated price — the 5% tolerance is wide enough that this manipulation is not rejected (`minPCOut = quote * 95 / 100`).
4. Reverse the price move with a back-run trade, capturing the difference as profit extracted from the victim's converted funds.

This mirrors the root cause of the external finding: reliance on an on-chain quote fetched at execution time, combined with an insufficiently tight slippage bound, permitting a party who can influence transaction ordering to extract value from another party's deposit-driven conversion.

### Impact Explanation
This falls within the "corruption of ... gas fee accounting ... token mapping" and "unauthorized ... loss of user or protocol-controlled funds" allowed impact categories: an ordinary user's bridged deposit is converted into less native gas token than it should receive, with the difference captured by an unprivileged attacker via a purely mempool-visible manipulation — no compromise of validators, TSS, or governance is required. The loss is real and quantifiable (up to ~5% of the converted amount per attack, and potentially more if pool liquidity is thin, since 5% is a fixed percentage rather than an amount bounded by pool depth).

### Likelihood Explanation
Likelihood is moderate: it requires (a) a `GAS`/`GAS_AND_PAYLOAD` inbound of meaningful size relative to the target pool's liquidity, and (b) the attacker being able to land trades immediately before/after the finalizing vote transaction in the same or adjacent block — feasible on most permissionless block-production designs, and especially so when pools (e.g., new or thin `WPC`/token pools set up per the `e2e-tests` bootstrap flow) have shallow liquidity, making a 5% band economically exploitable with modest capital.

### Recommendation
- Tighten the slippage bound and/or make it liquidity- and amount-aware rather than a fixed 5%, or allow governance/registry-configured per-pool bounds.
- Consider using a TWAP-based or otherwise manipulation-resistant price reference for `minPCOut` instead of a single spot `quoteExactInputSingle` call taken immediately before the swap.
- Where possible, cap the price impact permitted per single inbound conversion (e.g., reject/queue rather than force-execute if computed price impact exceeds a safe threshold), and/or split large conversions to reduce single-block price impact.

### Proof of Concept
1. A `TokenConfig` with a small-liquidity `WPC`/`PRC20` pool is registered (as in the e2e bootstrap flow, `step_create_all_wpc_pools`).
2. A user submits a large `GAS` inbound deposit that, once quorum is reached via `MsgVoteInbound`, will trigger `ExecuteInboundGas` → `GetSwapQuote` → `CallPRC20DepositAutoSwap` with `minPCOut = quote*95/100`.
3. An attacker, observing this pending vote transaction, submits a large swap against the same pool ahead of it (front-run), shifting price against the pending conversion.
4. The victim's autoswap executes and still satisfies the 5% `minPCOut` floor despite the worse effective price.
5. The attacker submits a reversing trade (back-run), recapturing the pool price and pocketing the spread extracted from the victim's conversion. [3](#0-2) [2](#0-1)

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
