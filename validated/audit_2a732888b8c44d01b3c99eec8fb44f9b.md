### Title
Unmetered EVM gas consumption via `MsgMigrateUEA` bypassing `DeductGasFeesFromReceipt` - (File: `x/uexecutor/keeper/msg_migrate_uea.go`)

### Summary
`Keeper.ExecutePayload` [1](#0-0)  always calls `k.DeductGasFeesFromReceipt` after the EVM call, charging the UEA for the gas actually consumed. The sibling function `Keeper.MigrateUEA` [2](#0-1)  performs an equivalent EVM call (`CallUEAMigrateUEA`, which invokes `migrateUEA` on the UEA contract via `DerivedEVMCall`) but never calls `DeductGasFeesFromReceipt` or any other fee-accounting function, even though `MsgMigrateUEA` is dispatched through the exact same gasless, unmetered Cosmos-tx code path as `MsgExecutePayload`.

### Finding Description
`MigrateUEA` is registered as a normal `MsgServer` method [3](#0-2)  and its Cosmos transaction is not fee-metered by the ante chain in the conventional sense — the module's own accounting (`DeductGasFeesFromReceipt`/`DeductAndBurnFees`) is supposed to be the mechanism that bills the UEA for gas used by the derived EVM call, exactly as documented for `ExecutePayload`: "The actual EVM execution gas is deducted from this UEA's balance (`DeductGasFeesFromReceipt`)" [4](#0-3) .

`CallUEAMigrateUEA` builds and commits a real `DerivedEVMCall` (`commit=true`) against the UEA contract [5](#0-4) , producing gas usage exactly like `CallUEAExecutePayload` does for `ExecutePayload`. However `Keeper.MigrateUEA` discards the returned receipt after only logging `GasUsed` — it never routes it through `DeductGasFeesFromReceipt` [2](#0-1) . Since `MsgMigrateUEA` bears no Cosmos-level fee obligation comparable to a normal fee-paying message (the module's own gas billing is the intended charge mechanism, mirroring `ExecutePayload`'s design), any account can repeatedly submit `MsgMigrateUEA` and force the chain to execute EVM calls into the UEA contract, all originating from module-driven `DerivedEVMCall`s, without the UEA (or anyone) ever being billed for the consumed gas — a direct parallel to `collectFees` skipping `applyJITPenalties` while `removeMaker`/`adjustMaker` apply it.

### Impact Explanation
This breaks the gas-accounting invariant that every module-originated `DerivedEVMCall` triggered by an unprivileged user message must be billed to the correct account, corrupting the gas fee accounting/refund invariant referenced in scope ("corruption of ... gas fee accounting, refund accounting"). It allows an unprivileged caller to force real EVM state execution (`migrateUEA`) at zero on-chain cost repeatedly, which is a resource-drain / uncompensated-execution vector distinct from the sibling `ExecutePayload` path that correctly meters this cost. Whether the migration call itself always reverts safely without gas cost is not verifiable from the available code excerpts — the UEA contract's `migrateUEA` implementation lives outside this repository, so the exact magnitude of consumable gas per call could not be confirmed here.

### Likelihood Explanation
`MsgMigrateUEA` is a top-level `Msg` type reachable by any signer with a valid `UniversalAccountId`/deployed UEA and syntactically valid (not necessarily cryptographically-authorized) migration payload/signature — no bonded-validator or admin gate is required based on the code reviewed. `MigrateUEA` only requires that the target UEA `isDeployed` [6](#0-5) , which is broadly true for many active UEAs, and the caller does not need to own it (authorization is deferred entirely to on-chain signature verification inside the UEA contract, as documented for the analogous `ExecutePayload` flow). This makes the missing fee-deduction call trivially and repeatedly triggerable.

### Recommendation
Add the same `DeductGasFeesFromReceipt` (or an equivalent gas-billing step) call in `Keeper.MigrateUEA` immediately after `CallUEAMigrateUEA` returns its receipt, mirroring the pattern in `Keeper.ExecutePayload`, and roll back the EVM state (via cache-context, as `ExecutePayloadV2` does) if fee deduction fails.

### Proof of Concept
Not independently reproduced against a live devnet in this session (no execution tooling available); the analysis is based on static comparison of the two keeper functions, which is confirmed by direct code citation above: `msg_execute_payload.go` lines 86-93 show the deduction call present, `msg_migrate_uea.go` lines 70-83 show it absent for an equivalent EVM call. A concrete PoC would consist of: (1) deploy/discover a UEA, (2) submit repeated `MsgMigrateUEA` transactions (with payloads that will predictably revert or succeed cheaply at the contract level) from an unfunded or minimally-funded account, and (3) observe that `DeductAndBurnFees`/`SendCoinsFromAccountToModule` is never invoked and no balance is debited despite `GasUsed` being non-zero in the receipt log.

func (ms msgServer) MigrateUEA(ctx context.Context, msg *types.MsgMigrateUEA) (*types.MsgMigrateUEAResponse, error) {
	_, evmFromAddress, err := utils.GetAddressPair(msg.Signer)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to parse signer address")
	}

	err = ms.k.MigrateUEA(ctx, evmFromAddress, msg.UniversalAccountId, msg.MigrationPayload, msg.Signature)
	if err != nil {
		return nil, err
	}

	return &types.MsgMigrateUEAResponse{}, nil
}

// CallUEAMigrateUEA migrates UEA through existing UEA
func (k Keeper) CallUEAMigrateUEA(
	ctx sdk.Context,
	from, ueaAddr common.Address,
	migration_payload *types.MigrationPayload,
	signature []byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	abi, err := types.ParseUeaABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UEA ABI")
	}

	abiMigrationPayload, err := types.NewAbiMigrationPayload(migration_payload)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal payload")
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,
		ueaAddr,
		big.NewInt(0),
		nil,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"migrateUEA",
		abiMigrationPayload,
		signature,
	)
}
