### Title
Unprivileged accounts can be griefed into cheap, long-lived storage/index lockups via zero-lamport tombstones gated on the next full snapshot - (File: `accounts-db/src/accounts_db.rs`)

### Summary
Any unprivileged user can cheaply create a zero-lamport, single-ref account (fund it, then drain it to zero lamports in a slot newer than the current `latest_full_snapshot_slot`). This is the AccountsDB analog of the Hyperdrive bug: a cheap trader action (paying only the fixed-rate delta) locks up a disproportionate amount of a shared resource (LP capital) until a slow, externally-gated event unlocks it. Here, the "cheap action" is creating/zeroing an account (cost: transaction fee only), and the "locked shared resource" is AccountsDB storage bytes, the accounts index entry, and an unbounded in-memory tracking set — all of which cannot be reclaimed until the validator's *next full snapshot* slot advances past the account's slot, which is a coarse-grained, infrequent, and attacker-uncontrollable event.

### Finding Description
AccountsDB defers cleanup of zero-lamport accounts until a full snapshot has advanced past the slot in which they went to zero, to preserve incremental-snapshot correctness: [1](#0-0) 

The gating check is centralized in `can_purge_zero_lamport_single_ref_after_shrink`: [2](#0-1) 

Until that gate opens, three things stay "locked":

1. **A storage tombstone byte-record** is retained rather than dropped during shrink, per `load_accounts_index_for_shrink`: [3](#0-2) 

2. **An unbounded in-memory tracking set** grows with every gated zero-lamport pubkey/slot pair: [4](#0-3) 
and is only drained on `clean` after the full snapshot slot advances: [5](#0-4) 

3. **Repeated CPU cost in `clean`/`shrink`**: any storage containing only such tombstones cannot be purged by the normal reclaim path and is specially checked on every `construct_candidate_clean_keys` pass: [6](#0-5) 

Because creating and then zeroing an account costs only the transaction fee (the rent-exempt reserve is fully returned to the payer when the balance is drained to zero), an attacker can cheaply mint many such pubkeys across many slots, each of which:
- occupies an index entry (bucket-map/in-mem index slot, see `accounts-db/src/accounts_index/bucket_map_holder.rs` and `bucket_map/src/bucket.rs`) that cannot be evicted until purge,
- occupies storage bytes as a tombstone that must be carried forward through every subsequent shrink of that slot (`test_shrink_collect_carries_forward_existing_tombstones`, `accounts-db/src/accounts_db/tests/impl.rs:1539-1626`),
- adds an entry to the unbounded `zero_lamport_accounts_to_purge_after_full_snapshot: DashSet`, and
- forces `clean`'s `dirty_stores` scan to repeatedly re-check `has_only_tombstones`/`can_purge_zero_lamport_single_ref_after_shrink` on every pass until the gate opens.

This directly mirrors the Hyperdrive report's structure: a disproportionately cheap unprivileged action (opening a short at a low rate / zeroing an account) locks up a shared resource (LP capital / AccountsDB storage+index+in-mem tracking) that can only be released through a slow, external mechanism (LP withdrawal-share conversion / the next full snapshot), and the ratio of attacker cost to locked resource is worst exactly when the triggering condition is "cheap" (low fixed rate / near-zero rent cost).

### Impact Explanation
- Sustained storage bloat: tombstones for zero-lamport single-ref accounts must be preserved and rewritten on every shrink pass of their slot until the next full snapshot advances past it, inflating on-disk AppendVec/TieredStorage usage disproportionately to the cost paid by the attacker.
- Unbounded in-memory growth: `zero_lamport_accounts_to_purge_after_full_snapshot` is a `DashSet` with no capacity bound tied to attacker cost; heavy spam between full snapshots can grow it substantially, consuming validator memory that only a full snapshot cycle relieves.
- Disproportionate CPU cost: `clean`'s `construct_candidate_clean_keys` and shrink's `load_accounts_index_for_shrink` must repeatedly re-evaluate every gated tombstone/dirty store each clean cycle, scaling clean/shrink cost with the number of griefed accounts rather than with attacker cost.
- This matches the report's "disproportionate storage and CPU cost" acceptance criterion, and is triggerable by any unprivileged account owner — no validator/operator role is required.

### Likelihood Explanation
Full snapshots are taken on a fixed, coarse-grained interval (configured via `--full-snapshot-interval-slots`, default tens of thousands of slots), meaning the "unlock" window can span a significant span of wall-clock time. During that entire window, an attacker can continuously and cheaply produce new zero-lamport, single-ref accounts (each costs only a fee-payer's transaction fee, since the rent reserve is returned on zeroing), each adding to the locked set. Because the gating condition (`latest_full_snapshot_slot`) is a protocol-wide, infrequently-advancing checkpoint rather than a per-account cost, the attack's cost-to-effect ratio is favorable to the attacker, especially when snapshot intervals are large or delayed (e.g., under load). This is a naturally reachable path through ordinary `system_program` transfers with no privileged operations, matching the report's "can also happen naturally" caveat as well as deliberate griefing.

### Recommendation
- Bound the size/lifetime cost of `zero_lamport_accounts_to_purge_after_full_snapshot` (e.g., cap growth, or fold entries into per-slot dirty-store bookkeeping instead of an unbounded global set) so a burst of cheap zero-lamport churn cannot cause unbounded memory growth between full snapshots.
- Consider decoupling the incremental-snapshot correctness requirement from a single global full-snapshot gate, e.g., by tracking per-account/per-slot eligibility more granularly, or by triggering opportunistic full-snapshot-independent purges when tombstone volume crosses a threshold, rather than only at (possibly rare) full snapshot boundaries.
- Add metrics/backpressure so that abnormal growth in gated zero-lamport tombstones (relative to normal cluster activity) is observable and can inform snapshot-interval tuning or rate limiting at the transaction level.

### Proof of Concept
Conceptual reproduction path, consistent with existing test coverage in the codebase (no privileged access required):
1. Set/observe `latest_full_snapshot_slot = S0` (as in `test_clean_purges_zero_lamport_single_ref_at_reclaim`, `accounts-db/src/accounts_db/tests/impl.rs:4861-4917`).
2. In slots `> S0`, repeatedly: fund a fresh pubkey with lamports (single transaction), then transfer/drain it to zero lamports in a later rooted slot — this is ordinary `system_program::transfer` activity costing only the transaction fee.
3. Each such pubkey becomes a zero-lamport single-ref account whose purge is blocked by `filter_zero_lamport_clean_for_incremental_snapshots` (`accounts_db.rs:2292-2373`) and is inserted into `zero_lamport_accounts_to_purge_after_full_snapshot` (`accounts_db.rs:943-948`), while its storage tombstone is carried forward on every shrink of its slot (`accounts_db.rs:2428-2444`, and demonstrated by `test_shrink_collect_carries_forward_existing_tombstones`).
4. Repeat across many pubkeys/slots before the next full snapshot is taken; each iteration adds fixed, cheap attacker cost but a proportionally larger amount of retained storage bytes, index entries, and DashSet memory, plus repeated clean/shrink CPU work — all of which is only released once `latest_full_snapshot_slot` advances past the relevant slots, exactly as shown by `test_clean_accounts_with_latest_full_snapshot_slot` (`accounts_db.rs/tests/impl.rs:5667-5713`).

I was not able to fully verify the exact default value of the full-snapshot interval or quantify precise memory/storage-per-account overhead from the index (`code exists but was not read in full`, e.g. `runtime/src/snapshot_bank_utils.rs`, `snapshots/src/snapshot_config.rs`); a Devin session with full repository access could pull the exact default interval constants and produce a numeric cost/impact estimate if needed.
