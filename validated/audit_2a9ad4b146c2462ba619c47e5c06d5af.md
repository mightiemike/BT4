### Title
`PoisonMicroblock` accepted with byte-identical duplicate headers (no distinct double-sign required) - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`check_microblock_header_signer` only verifies that the signatures on `mblock_header_1` and `mblock_header_2` recover to the same public-key hash; it never checks that the two headers are actually distinct. An attacker can take any single, legitimately-broadcast, signed microblock header and submit it twice as both halves of a `PoisonMicroblock` transaction, triggering the poison-microblock reward/slashing path even though the referenced miner never double-signed.

### Finding Description
The equality the poison-microblock mechanism is supposed to enforce is:

`poison_reward_paid == true` **iff** `mblock_header_1 != mblock_header_2` AND both are signed by the same key AND they conflict at the same sequence (a genuine fork/double-sign).

`check_microblock_header_signer` (stackslib/src/chainstate/stacks/db/transactions.rs:686-713) only implements the "same key" half of this: [1](#0-0) 
It recovers `pkh1` from `mblock_hdr_1.check_recover_pubkey()` and `pkh2` from `mblock_hdr_2.check_recover_pubkey()` and only fails if `pkh1 != pkh2`. If the two headers passed in are the literal same object (byte-identical, same signature), `pkh1 == pkh2` trivially and the check returns `Ok(pkh1)` — there is no check anywhere in this function, nor downstream in `handle_poison_microblock`, that `mblock_header_1 != mblock_header_2`: [2](#0-1) 

The only place an equality/conflict check on the two headers exists in the reviewed code is the mempool admission path in `mempool_storage_check`-style logic in `stackslib/src/chainstate/stacks/db/blocks.rs`: [3](#0-2) 
This only rejects the transaction if `sequence`, `prev_block`, or `version` **differ** between the two headers — i.e., it enforces that the headers *could* represent a valid fork proof (same sequence/prev_block/version, different content) — but it never rejects the case where the two headers are wholesale identical. Two identical headers trivially satisfy "same sequence, same prev_block, same version" and "same recovered pubkey hash," so this guard does not close the gap either.

Attacker's exact input: obtain any real, previously-broadcast, validly-signed `StacksMicroblockHeader` `h` (already public, since microblocks are broadcast and their signer's pubkey hash is registered on-chain via `insert_microblock_pubkey_hash`), then submit `TransactionPayload::PoisonMicroblock(h.clone(), h.clone())` signed by an arbitrary reporter key. Since `h` was really signed by the honest miner, `check_microblock_header_signer` succeeds, `get_microblock_pubkey_hash_height` finds a valid, unmatured entry, and `handle_poison_microblock` proceeds to record a poison report / trigger the miner-reward slashing and commission payout to the reporter — despite the miner never having produced two conflicting microblocks at that sequence.

### Impact Explanation
This lets any unprivileged party fabricate a "proof" of double-signing against an honest miner using only a single, legitimately-produced microblock header they observed on the network, causing miner block-reward slashing and diversion of a poison-microblock commission to the attacker's own account without any actual fork/double-sign having occurred. This is reward theft/misappropriation targeting an honest miner's future coinbase, not bounded merely to a fee, since it is designed to interact with the miner reward maturation and commission-payout logic (`poison_microblock_commission`), matching the Critical "block-reward theft/double-payment" category.

### Likelihood Explanation
Preconditions are trivial and always available in normal chain operation: any chain height with a `microblock_pubkey_hash_height` entry that has not yet matured (within `MINER_REWARD_MATURITY` blocks) suffices, and every miner that ever produces a microblock stream creates such an entry. The attacker needs no stake, no BTC spend beyond an ordinary transaction fee, and no special role — merely the ability to observe one broadcast microblock header and submit a standard `PoisonMicroblock` transaction. The attack is repeatable against every miner/tenure that has produced at least one microblock.

### Recommendation
Add an explicit equality/distinctness check in `check_microblock_header_signer` (or immediately before it is called in `handle_poison_microblock`) that rejects the transaction if `mblock_header_1 == mblock_header_2` (or, more precisely, if their block hashes/signatures are identical), so that a genuine fork proof requires two cryptographically distinct signed headers at the same sequence and `prev_block`. Apply the same distinctness check in the mempool admission path in `blocks.rs` alongside the existing sequence/prev_block/version equality checks.

### Proof of Concept
Rust integration test (modeled on existing tests in `stackslib/src/chainstate/stacks/db/transactions.rs`, e.g. `process_poison_microblock_valid_transaction`):
1. Set up a `TestChainstateBuilder` chain, insert a valid `microblock_pubkey_hash` for a real miner key at height 1 via `StacksChainState::insert_microblock_pubkey_hash`.
2. Construct a single legitimately-signed `StacksMicroblockHeader` `h` using `make_signed_microblock(&block_privk, &privk, ..., seq)`.
3. Build `TransactionPayload::PoisonMicroblock(h.clone(), h.clone())`, sign it with an arbitrary reporter key, and call `StacksChainState::process_transaction`.
4. Assert on both sides of the equality:
   - Expected (per intended invariant): `process_transaction` returns `Err` (rejected, no distinct double-sign) — i.e. `report_opt` from `get_poison_microblock_report` stays `None`.
   - Actual (bug): `process_transaction` returns `Ok`, and `get_poison_microblock_report` returns `Some((reporter_addr, seq))`, showing an unearned poison report/reward was accepted for a miner who never double-signed.
