### Title
Permissionless `accrue` truncates the liquidity index while the debt index still advances, permanently losing depositor yield - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
`accrue()` in each vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) is a public, permissionless function with no caller check. Anyone can call it at will. Each call recomputes `next-index` (borrow/debt index) and `next-liquidity-index` (depositor-facing index) from the elapsed time since `last-update`, and — critically — advances `last-update` to the current block time whenever **either** index changed: [1](#0-0) 

### Finding Description
The two index deltas are computed with different rounding and different rates: [2](#0-1) 

`calc-multiplier-delta` for the debt index uses `mul-div-up` (round up) with the raw borrow `rate`, so any non-zero `time-delta` produces at least a 1-unit increase — the debt index essentially never fails to advance: [3](#0-2) 

The liquidity index, however, is derived from `liquidity-rate`, which is the borrow rate scaled down by both utilization and `(1 - reserve-factor)`: [4](#0-3) 

and it uses `mul-div-down` (truncating), so for short enough time deltas `liquidity-rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS` truncates to `0` while the debt-index calculation (using the larger, un-scaled rate and round-up) still yields a non-zero increment.

Because `last-update` is reset via an `or` over *both* index changes:
```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
```
an attacker can repeatedly call the permissionless `accrue()` at intervals just short enough that the debt index still increments (forcing `last-update` to reset to the current block time) but the liquidity index computation truncates to zero. Each such call permanently discards the fractional liquidity accrual for that interval — it is not carried forward, since the next call's `time-delta` is measured from the new `last-update`. Meanwhile borrowers keep paying (and the debt/treasury-fee side keeps growing, since `mul-div-up` never truncates), so interest is collected from borrowers but never credited to the liquidity index that depositors' share value is intended to track (`get-liquidity-index` / `lindex`, exposed via `get-liquidity-index`): [5](#0-4) 

This is the same class of bug as the reported issue: an externally-callable function that updates a "last observed" timestamp/state even when the reward/interest computation truncated to zero, permanently erasing the un-materialized fractional accrual instead of retaining it for the next call.

### Impact Explanation
Depositors permanently lose the yield fraction that should have accrued to the liquidity index during the truncated intervals, while borrowers still pay full interest (that interest is absorbed into `debt`/`total-borrowed` growth and partly minted to `dao-treasury` via the reserve factor, not returned to depositors' `lindex`). This is a permanent loss of unclaimed yield for LP/depositor share holders, repeatable indefinitely by anyone calling the permissionless `accrue()` at the right cadence, exactly analogous to the referenced `getRewardFor` truncation griefing bug.

### Likelihood Explanation
`accrue()` has no `check-caller-auth` / access restriction, so it is callable by any address at any time. The attacker only needs to compute the interval at which `liquidity-rate * Δt` truncates below `SECONDS-PER-YEAR-BPS / INDEX-PRECISION` (analogous to the `X < 10,006` calculation in the report) and repeat calls at or below that interval, which can be as short as one block for large `totalSupply`/small liquidity rate scenarios. This requires no special capital and is executable by a single actor with no cooperation from other users.

### Recommendation
Do not gate `last-update` on the debt index alone; only advance `last-update` when the liquidity-index computation actually produced a non-zero delta (or track/accumulate the un-applied time separately so it isn't lost), or accumulate fractional remainder across calls (as commonly done via a `remainder`/`carry` variable) so repeated truncation cannot indefinitely erase liquidity accrual. Alternatively, restrict `accrue()` so it cannot be called at sub-threshold intervals, or use a rounding scheme that guarantees the liquidity index advances whenever any other index that shares the same `last-update` clock advances.

### Proof of Concept
1. Attacker observes a vault's `fee-reserve`, `utilization`, and interest-rate curve to derive `liquidity-rate < interest-rate` (see `calc-liquidity-rate`).
2. Attacker computes the max `time-delta` for which `mul-div-down(liquidity-rate, time-delta*INDEX-PRECISION, SECONDS-PER-YEAR-BPS)` truncates to `0`, while `mul-div-up(interest-rate, time-delta*INDEX-PRECISION, SECONDS-PER-YEAR-BPS)` is `>0` (trivially true for round-up on any positive input).
3. Attacker repeatedly calls the public `accrue()` at or below that interval.
4. Each call: `idx` advances (forces `last-update` to reset to `stacks-block-time`), `lindex` stays flat (truncated), so the depositor-facing liquidity accrual for that window is discarded permanently, while borrower debt keeps compounding and any reserve fee minted to `dao-treasury` still reflects the debt-side growth.
5. Repeated indefinitely, depositors' `lindex`-tracked yield never catches up to the true interest paid by borrowers, resulting in permanent loss of unclaimed yield to LPs.

(define-private (calc-multiplier-delta (rate uint) (time-delta uint) (round-up bool))
  (+ INDEX-PRECISION
    (if round-up
      (mul-div-up rate
                  (* time-delta INDEX-PRECISION)
                  SECONDS-PER-YEAR-BPS)
      (mul-div-down rate
                  (* time-delta INDEX-PRECISION)
                  SECONDS-PER-YEAR-BPS))))
