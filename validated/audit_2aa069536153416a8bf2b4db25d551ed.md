## No vulnerability found for this question.

The claimed equality break does not hold. The sortition-processing pipeline already deduplicates and cross-checks leader-key consumption within the same sortition. `get_consumed_leader_keys` fetches, for each accepted candidate, the leader key at `(candidate.key_block_ptr, candidate.key_vtxindex)` via `get_leader_key_at` [1](#0-0) , and `BurnSamplePoint::make_min_median_distribution` builds the burn distribution over the windowed commits before winner selection [2](#0-1) . Critically, after the burn distribution is computed, only commits present in `burn_dist` (one per distinguishable candidate, keyed effectively by the linked UTXO/key chain) are accepted into `accepted_ops`, and any block-commit txid that isn't picked up is explicly rejected with the log "Committed to an already-consumed VRF key" [3](#0-2) . This shows the system already treats two commits pointing at the same `(key_block_ptr, key_vtxindex)` as mutually exclusive — only one can be linked/scored and carried forward.

Furthermore, sortition winner selection (`select_winning_block`) picks exactly one winning candidate from `burn_dist` via `sample_burn_distribution`, which returns a single index into the distribution [4](#0-3) . The resulting `BlockSnapshot` records exactly one `winning_block_txid`/`winning_stacks_block_hash`, and the miner's signing key is derived by re-fetching the leader key at the **winning** commit's `key_block_ptr`/`key_vtxindex` from the sortition DB — not from any other pretender [5](#0-4) . There is no mechanism by which a second (losing) commit referencing the same key pointer could be separately linked to an accepted Stacks block, because Stacks block acceptance for a given sortition is gated on matching the single `winning_block_txid`/`winning_stacks_block_hash` recorded in the `BlockSnapshot` for that sortition, not merely on referencing a valid leader key.

The question's premise — that `check_common`'s per-op validity check alone governs which commit's block becomes canonical — ignores this later distribution/winner-selection stage that already enforces single-key/single-winner exclusivity per sortition. I did not find a `check_common` function under that exact name in `leader_block_commit.rs` in this index (the per-op checks may be named differently or split across functions), so I cannot cite its exact rejection paths for duplicate key pointers, but this is immaterial: even if two commits with identical key pointers both pass individual field validation, the burn-distribution/sortition-winner mechanism shown above only permits one to be linked as the tenure's leader key and only one txid becomes `winning_block_txid` for that sortition, so no chain split or dual-block-acceptance path exists here.

        // pick the next winner
        let win_idx_opt =
            BlockSnapshot::sample_burn_distribution(burn_dist, &vrf_seed, sortition_hash);
        match win_idx_opt {
            None => {
                // no winner
                Ok(None)

        }
