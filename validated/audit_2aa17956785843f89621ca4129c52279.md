## Title
Missing full-history shard resolution on `GlobalContractDistributionReceipt.target_shard` causes a `.unwrap()` panic during chunk apply, halting the chain on static (V0/V1/V2) resharding layouts - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`Receipt::receiver_shard_id` resolves a `GlobalContractDistributionReceipt`'s stale `target_shard` field to a current shard via `ShardLayout::resolve_to_current_shard`, but that resolution only walks the *complete* split history for `ShardLayoutV3` (dynamic resharding). For the still-supported `V0`/`V1`/`V2` static-resharding layouts, `resolve_to_current_shard` falls back to `get_children_shards_ids`, which is explicitly documented as "single generation only." [1](#0-0)  If a `target_shard` is more than one resharding generation stale, resolution returns `None`, `receiver_shard_id` returns `Err(EpochError::ShardingError(...))` [2](#0-1) , and that `Err` is unconditionally `.unwrap()`'d inside `receipt_filter_fn`, called from the delayed-receipt `pop()` path used during every chunk apply. [3](#0-2) 

### Finding Description
This is analogous to the F2FS CVE's root cause: a data-carrying flag/field embedded in a persisted object (the inode's `F2FS_INLINE_DATA` flag / here, a receipt's `target_shard` field) is trusted and acted upon by a background/maintenance operation (GC / delayed-receipt draining) without a bounded, complete sanity check, leading to an unrecoverable crash (`BUG_ON` / Rust `panic!` via `unwrap()`).

Concretely:
- Any unprivileged account can submit `DeployGlobalContract`, which produces a `ReceiptEnum::GlobalContractDistribution` receipt carrying a `target_shard` snapshot of the shard layout at receipt-creation time. [4](#0-3) 
- If this receipt is buffered/delayed (e.g., because its target shard is congested — attacker can trivially self-induce this by saturating compute on that shard, as shown in the repo's own regression test) across **two or more** resharding events while the network is still on `V0`/`V1`/`V2` static shard layouts, `target_shard` becomes unresolvable by `get_children_shards_ids` (single-generation only).
- When the delayed queue is eventually drained, `DelayedReceiptQueueWrapper::pop()` calls `receipt_filter_fn`, which does `receiver_shard_id(&shard_layout).unwrap()` — an unconditional panic on `Err`. [5](#0-4) 
- This panic occurs inside `Runtime::apply`'s receipt-processing phase (`process_delayed_receipts` → `pop`), i.e. inside chunk application on every validator/node applying that chunk. [6](#0-5) 

The repository's own test explicitly documents this exact failure mode for the V3/dynamic-resharding case and states the fix (`resolve_to_current_shard`'s full split-history walk) "only works with V3 shard layouts... With static resharding, the shard layout doesn't maintain a full split history," confirming the V0/V1/V2 path remains exposed to the same class of bug. [7](#0-6) [8](#0-7) 

### Impact Explanation
A successful trigger causes every node applying the affected chunk (containing the drained delayed receipt) to panic inside `Runtime::apply`, which is the core state-transition function invoked by all validators/nodes tracking that shard. This is a transaction-triggered halt: a state-transition function that is supposed to reject or gracefully handle invalid/stale input instead crashes the process, taking down chunk production/validation for the affected shard(s) network-wide — matching the accepted "transaction-triggered halt" impact category.

### Likelihood Explanation
Reaching this requires: (1) submitting an ordinary `DeployGlobalContract` transaction (fully unprivileged), (2) causing the resulting distribution receipt to be delayed via congestion (self-inducible by burning gas on the target shard, as demonstrated in the codebase's own PoC test for the V3 case), and (3) two static resharding events occurring while the receipt is delayed. Condition (3) is dependent on the network's resharding cadence and is not attacker-controlled on networks that have already migrated to `V3`/dynamic resharding; it is realistic on any deployment still using static (protocol-version-driven) resharding with more than one scheduled shard split, or in test/custom networks. Likelihood is therefore moderate and environment-dependent rather than universally and immediately exploitable.

### Recommendation
Extend `ShardLayout::resolve_to_current_shard` for `V0`/`V1`/`V2` to walk the full multi-generation split history (mirroring the `V3` fix), or reject/gracefully delayed-forward receipts whose `target_shard` cannot be resolved instead of propagating the error into an `.unwrap()`. At minimum, `receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs` should not `unwrap()` a fallible shard resolution inside the hot chunk-apply path; it should propagate a `RuntimeError`/`StorageInconsistentState` so the failure can be handled without crashing the process, consistent with how other resharding-related failures return `Err` instead of panicking elsewhere in this module.

### Proof of Concept
The repository already contains an end-to-end regression scenario demonstrating the mechanism (for the now-fixed V3 case), which can be adapted to a static-resharding (V0/V1/V2) network with two scheduled splits:
1. Deploy contract on account `user0`, then submit `DeployGlobalContract` from `user0`, producing a `GlobalContractDistributionReceipt` with `target_shard` = `user0`'s current shard. [9](#0-8) 
2. Saturate compute on that shard every block (e.g. repeated `burn_gas_raw` calls) so the distribution receipt is pushed into, and stays in, the delayed queue while two resharding events happen. [10](#0-9) 
3. Stop saturating and let the delayed queue drain; on a static (V0/V1/V2) layout, `receipt_filter_fn`'s `.unwrap()` on `receiver_shard_id` panics because `resolve_to_current_shard`'s single-generation fallback cannot resolve a twice-stale `target_shard`, halting chunk production on that shard. [11](#0-10)

    // The function follows the guidelines of standard iterator filter function

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }
