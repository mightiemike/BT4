### Title
Reorg-permission window (`first_proposal_burn_block_timing`) is evaluated against per-signer local wall-clock timestamps, letting honest signers disagree on whether a tenure reorg is permitted - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
The Morph report describes a class of bug where a time-bounded safety window (the challenge window) is not uniformly and consistently enforced for all state committed while the window is open, letting a batch bypass the challenge entirely depending on *when* it was created relative to the window. The Stacks analog is `SortitionData::check_parent_tenure_choice`, which decides whether an incoming miner is allowed to reorg an established tenure by comparing a duration (`proposal_to_sortition`) against the configured `first_proposal_burn_block_timing` window - but that duration is computed from two purely local, per-signer wall-clock timestamps rather than from a canonical/consensus-derived value, so different honest signers evaluating the *same* reorg attempt can land on opposite sides of the threshold and reach different verdicts.

### Finding Description
`check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-295`) is the mechanism that decides whether a new tenure is allowed to reorg a previously-established one that already mined a block. The rule is: a reorg is permitted only if the reorged tenure's first (and only) block was proposed "poorly timed", i.e. close enough to the next sortition: [1](#0-0) 

The two inputs feeding `proposal_to_sortition`:
- `sortition_state_received_time` comes from `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` - the local time *this* signer's own node recorded the burn block arriving.
- `approved_at` comes from `local_block_info.approved_time` - the local time *this* signer approved the reorged tenure's first block.

Both are local, non-consensus timestamps recorded independently by each signer as messages/events reach it over the network, exactly the same category of value the Morph bug relied on (`block.timestamp`, a similarly non-synchronized/attacker-influenced value used for a security-relevant window comparison). Unlike the Morph batch-commit timestamp (which is on-chain and globally identical for all observers), the values compared here are **not shared state**: `get_burn_block_receive_time` and `approved_time` are stamped independently on each signer's machine when it locally observes the relevant events, subject to normal network propagation jitter and to a miner's/attacker's ability to selectively delay message delivery to a subset of signers (e.g., via unequal p2p/StackerDB propagation, slow links, or targeted request throttling - no elevated privilege required, just normal network position).

Because `first_proposal_burn_block_timing` is a fixed boundary (default 60s) applied to these locally-measured durations, a scenario engineered so that the true elapsed time between "block N approved" and "sortition N+1 received" sits close to the boundary will cause some signers (who processed the burn block quickly / approved N slowly) to compute a duration `< first_proposal_burn_block_timing` (permitting the reorg, marking the old tenure `superseded`) while others (who approved N quickly / received the new burn block with extra latency) compute a duration `>= first_proposal_burn_block_timing` (refusing the reorg, continuing to sign for the old tenure). This is the same “bypass depending on which side of a window you land on” pattern as the Morph bug, except here the divergence is between individual validators (signers) computing an inconsistent verdict for the identical real-world event, rather than a batch bypassing challenge outright.

This directly breaks the equality that the finding rules require: "a validation verdict two nodes disagree on." The same reorg attempt should be uniformly accepted or uniformly rejected by the entire signer set (this is exactly what the mitigation code around it - `record_superseded_tenure`, `reorg_permit_stands`, and the wider conflict-tracking machinery documented in `docs/signer-flows.md` - exists to manage), but the actual comparison is driven by non-canonical, signer-local data.

### Impact Explanation
This maps to the "High" bucket allowed by the rules: a minority-triggerable, unprivileged, temporary tip disagreement caused by a static-validation divergence. A single miner (the current tenure's block producer, or any third party controlling propagation timing near the tenure boundary) does not need majority signer collusion; they only need to influence delivery timing of the reorged tenure's block or the new sortition/burn-block notification to a subset of signers. The practical consequences are:
- A subset of signers accepts and signs the reorging block (marking the prior tenure `superseded`), while another subset continues to defend the prior tenure and rejects the reorging block, splitting signature weight between two competing tenures.
- Depending on how the split falls relative to the 70% signing-weight threshold, this can stall block production (neither tenure reaches consensus, a livelock/tip-disagreement until the timeout window in `is_timed_out`/`block_proposal_timeout` resolves it) or, in a more adversarial timing/network-partition scenario, let two different quorum subsets each independently believe they have sanctioned a different, mutually exclusive tenure history - the "temporary tip disagreement" case explicitly named as an acceptable High-severity outcome.

It does not reach Critical because reaching an actual persistent chain split still requires the honest majority to be split in a way that is bounded and self-correcting (the code's own conflict/permit-void logic re-derives liveness from the node on each evaluation), but the underlying equality violation - non-deterministic, non-consensus data feeding a security-critical binary decision that must be identical across all validators - is real and directly analogous to the reported bug class.

### Likelihood Explanation
No special privilege is required: any current tenure's miner, or any network-adjacent party that can affect relative message arrival order/timing to different signers near a sortition boundary, can attempt to engineer the race. The window (`first_proposal_burn_block_timing`, default 60s) is wide enough that ordinary network jitter across a geographically distributed signer set could plausibly straddle it on its own, without even requiring deliberate manipulation, making this more of a "when triggered" than "if triggered" concern under adverse network conditions. That said, precisely engineering the split to cause a persistent, exploitable fork (rather than a self-healing stall) requires careful timing control, which lowers likelihood of the most severe outcome while leaving the temporary-disagreement outcome plausible.

### Recommendation
Replace the locally-recorded wall-clock comparison with a value that is either (a) derived from consensus/chain data that all signers can reproduce identically (e.g., the Bitcoin block header timestamp of the new sortition versus the burn-view timestamp recorded in the reorged tenure's own tenure-change/consensus data, rather than each signer's local receipt time), or (b) made robust to per-signer skew by adding an explicit, generously-sized tolerance/buffer that is provably larger than realistic network propagation variance across the signer set, and by requiring the decision to be re-confirmed against the node's canonical view (as `reorg_permit_stands` already does for permit validity) rather than trusting a single local timestamp pairing. At minimum, document and bound the maximum tolerable clock/propagation skew across the signer set for this specific comparison, analogous to how `tenure_idle_timeout_buffer_secs` already exists to compensate for skew in the tenure-extend path.

### Proof of Concept
1. Miner A wins a sortition and is the sole tenure producer; it proposes and gets its single block `N` signed by some fraction of the signer set, with `approved_time` timestamps varying slightly across signers due to normal StackerDB message propagation.
2. Near the natural tenure length, arrange (via normal network conditions or by controlling relay to specific signer endpoints) for the delivery of `N`'s approval events and the delivery of the next Bitcoin block/sortition notification to be skewed across the signer population so that:
   - Signers `S1..Sk` compute `proposal_to_sortition < first_proposal_burn_block_timing` (default 60s).
   - Signers `Sk+1..Sn` compute `proposal_to_sortition >= first_proposal_burn_block_timing`.
3. Miner B wins the next sortition and proposes block `N'`, whose tenure-change payload does not build on tenure A (a reorg attempt), invoking `check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170`) on every signer.
4. `S1..Sk` compute the reorg as "poorly timed" and permit it (`superseded_tenures.push(tenure)`, `record_superseded_tenure`), signing `N'`. `Sk+1..Sn` refuse it (`return Ok(false)`), continuing to consider `N`/tenure A canonical and rejecting `N'` as `RejectReason::ReorgNotAllowed`.
5. Result: the signer set is split on which tenure is canonical for the same real-world reorg event, producing a signature-weight split across two mutually exclusive tenures/tips - the observable "validation verdict two nodes disagree on" condition.

I was not able to execute this scenario in a live multi-signer testbed (only static code/doc review was available via the indexed repository), so the precise magnitude of achievable propagation skew and whether it can be reliably engineered past the default 60s window in production network conditions is unverified and should be confirmed with an integration test (the existing `stacks-signer/src/chainstate/tests/v1.rs::reorg_timing_testing` and `stacks-node/src/tests/signer/v0/reorg.rs` harnesses look directly reusable for constructing such a test, feeding deliberately skewed `sortition_state_received_time`/`approved_time` values to different simulated signers).
