Based on my investigation, I found a genuine analog: `VoteOutbound` in `x/uexecutor/keeper/msg_vote_outbound.go` does not check `IsChainOutboundEnabled` before processing an observation vote, whereas the sibling function `VoteInbound` explicitly gates on `IsChainInboundEnabled` before any state changes.

### Title
`VoteOutbound` does not re-check `IsChainOutboundEnabled` before finalizing an outbound observation, unlike `VoteInbound`'s consistent enabled-gate — ([File: x/uexecutor/keeper/msg_vote_outbound.go])

### Summary
`VoteInbound` ( [1](#0-0) ) explicitly checks `uregistryKeeper.IsChainInboundEnabled` and rejects the vote before any state mutation when the chain's inbound flag is off, and this is confirmed by dedicated tests (`TestVoteInbound_ChainEnabled`) asserting "no UTX should be created even after quorum-worth of disabled attempts" [2](#0-1) . By contrast, `VoteOutbound` ( [3](#0-2) ) contains no equivalent `IsChainOutboundEnabled` check at vote time — the outbound-enabled flag is only consulted once, at outbound *creation* time in `create_outbound.go` [4](#0-3) , gating whether an outbound leg is attached to the UTX at all.

### Finding Description
This is structurally the same inconsistency class as the `cooldown()` report: a state-transitioning function that is missing a "system flag" gate that a sibling function of the same family enforces. Here, `x/uregistry.ChainConfig.Enabled` exposes independent `IsInboundEnabled`/`IsOutboundEnabled` toggles used by the admin to disable crosschain traffic on a chain [5](#0-4) . `VoteInbound` treats this as a hard precondition, checked first, before any ballot state is touched [1](#0-0) . `VoteOutbound`, however, once an outbound already exists in `PENDING` status (created while outbound was enabled, or created before it was disabled), continues to accept UV votes, run ballot finalization, mark the outbound `OBSERVED`, and drive `FinalizeOutbound` (refund/re-mint on failure) with **no re-check of `IsChainOutboundEnabled`** at vote time [6](#0-5) .

Because the outbound-enabled flag can be toggled by the admin after an outbound is already pending (e.g., to halt processing on a chain suspected of an incident), `VoteOutbound` will still fully process and finalize votes on that "frozen" chain's outbound, including refund/re-mint accounting via `FinalizeOutbound`. This mirrors the `cooldown()` bug class exactly: the accompanying "pause"-style guard exists on one function of a pair but not the other, letting normal (non-privileged) user/validator flows produce state transitions the operator intended to block.

### Impact Explanation
If the admin disables outbound on a chain expecting all outbound processing to halt (analogous to intent behind pausing withdrawals), pending outbound ballots can still finalize, causing `FinalizeOutbound` accounting (refund/re-mint of PRC20/native amounts) to execute on a chain the operator believed was frozen. This is within the allowed-impact scope ("corruption of ... refund accounting ... revert destination ... token mapping" and "unauthorized state transitions in universal execution flows") since UV votes are an unprivileged, user-external-event-driven path, not a privileged action, and this diverges from operator-intended halted state without any code change on the attacker's part — only requiring that an outbound is already pending when outbound is disabled.

### Likelihood Explanation
Moderate. It requires (a) an outbound already `PENDING` at the moment the admin flips `IsOutboundEnabled` to false, and (b) UVs continuing to submit `MsgVoteOutbound` (a gasless message type, so no cost barrier — [7](#0-6) ). Since disabling a chain is exactly the kind of emergency-style admin action taken in response to an issue on that chain, in-flight outbounds racing the disable are a realistic and likely-relevant scenario, not a contrived edge case.

### Recommendation
Add an `IsChainOutboundEnabled` check at the top of `VoteOutbound`, mirroring `VoteInbound`'s pattern — reject the vote before any ballot state mutation if outbound is disabled for `outbound.DestinationChain`, e.g.:
```go
enabled, err := k.uregistryKeeper.IsChainOutboundEnabled(ctx, outbound.DestinationChain)
if err != nil {
    return errors.Wrap(err, "failed to check outbound enabled")
}
if !enabled {
    return fmt.Errorf("outbound is disabled for chain %s", outbound.DestinationChain)
}
```
placed after the outbound is looked up (so the destination chain is known) but before ballot voting/finalization proceeds.

### Proof of Concept
1. UV observes and creates an outbound on chain X while `IsOutboundEnabled=true`; outbound status is `PENDING` in `UniversalTx.OutboundTx`.
2. Admin submits `MsgUpdateChainConfig` disabling outbound for chain X (e.g., due to an incident on X).
3. UVs continue submitting `MsgVoteOutbound` for the still-pending outbound; `VoteOutbound` has no gate on `IsChainOutboundEnabled`, so votes are recorded, the ballot can reach quorum, `UpdateOutbound`/`FinalizeOutbound` run, and refund/re-mint accounting executes — even though the admin believed outbound processing on chain X was halted.

I was unable to fully confirm whether any downstream check elsewhere (e.g., inside `VoteOnOutboundBallot` or `FinalizeOutbound`) independently re-validates the enabled flag; the searched code paths in `msg_vote_outbound.go` and the outbound-enabled test file (`chain_enabled_test.go`) only exercise the enabled check at outbound *creation*, not at vote/finalization time, so this should be verified against the full `FinalizeOutbound` implementation before treating this as fully confirmed.

func (k Keeper) VoteOutbound(
	ctx context.Context,
	universalValidator sdk.ValAddress,
	utxId string,
	outboundId string,
	observedTx types.OutboundObservation,
) error {
	k.Logger().Info("vote outbound received",
		"validator", universalValidator.String(),
		"utx_id", utxId,
		"outbound_id", outboundId,
		"obs_success", observedTx.Success,
	)

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Step 1: Fetch UniversalTx
	utx, found, err := k.GetUniversalTx(ctx, utxId)
	if err != nil {
		return err
	}
	if !found {
		return fmt.Errorf("UniversalTx not found: %s", utxId)
	}
	if utx.OutboundTx == nil {
		return fmt.Errorf("no outbound tx found in UniversalTx %s", utxId)
	}

	// Step 2: Find outbound by id
	var outbound types.OutboundTx
	found = false
	for _, ob := range utx.OutboundTx {
		if ob.Id == outboundId {
			outbound = *ob
			found = true
			break
		}
	}
	if !found {
		return fmt.Errorf("outbound %s not found in UniversalTx %s", outboundId, utxId)
	}

	// Canonicalize the observed tx hash for the destination chain so encoding
	// variants of the same observation land on one ballot.
	observedTx.TxHash = utils.LenientCanonicalizeTxHash(outbound.DestinationChain, observedTx.TxHash)
	observedTx.GasFeeUsed = strings.TrimSpace(observedTx.GasFeeUsed)
	observedTx.ErrorMsg = strings.TrimSpace(observedTx.ErrorMsg)

	// Prevent double-finalization
	if outbound.OutboundStatus != types.Status_PENDING {
		k.Logger().Warn("vote outbound rejected: outbound already finalized",
			"outbound_id", outboundId,
			"status", outbound.OutboundStatus.String(),
		)
		return fmt.Errorf("outbound with key %s is already finalized", outboundId)
	}

	// Use temp context to prevent partial writes
	tmpCtx, commit := sdkCtx.CacheContext()

	// Step 3: Vote on outbound ballot
	isFinalized, _, err := k.VoteOnOutboundBallot(
		tmpCtx,
		universalValidator,
		utxId,
		outboundId,
		observedTx,
	)
	if err != nil {
		return err
	}

	// Step 3b: Record this validator's vote in the per-outbound PendingOutbounds
	// entry (variant-aware audit trail). Each unique ObservedTx payload becomes
	// its own variant; multiple variants per outbound_id indicate validator
	// divergence on the destination-chain observation.
	ballotKey, err := types.GetOutboundBallotKey(utxId, outboundId, observedTx)
	if err != nil {
		return fmt.Errorf("failed to derive outbound ballot key: %w", err)
	}
	if err := k.RecordOutboundVote(tmpCtx, outboundId, observedTx, universalValidator.String(), ballotKey); err != nil {
		return err
	}

	commit()

	// Step 4: Exit if not finalized yet
	if !isFinalized {
		k.Logger().Debug("vote outbound recorded, ballot not yet finalized",
			"validator", universalValidator.String(),
			"utx_id", utxId,
			"outbound_id", outboundId,
		)
		return nil
	}

	// Step 5: Update outbound state to OBSERVED
	outbound.OutboundStatus = types.Status_OBSERVED
	outbound.ObservedTx = &observedTx

	k.Logger().Info("outbound observed",
		"utx_id", utxId,
		"outbound_id", outboundId,
		"success", observedTx.Success,
		"dest_chain", outbound.DestinationChain,
	)

	// Persist the state inside UniversalTx
	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Remove from pending outbounds index now that status is OBSERVED
	if err := k.PendingOutbounds.Remove(ctx, outboundId); err != nil {
		return fmt.Errorf("failed to remove pending outbound index for %s: %w", outboundId, err)
	}

	// Step 6: Finalize outbound (refund if failed).
	// If re-mint fails, handleFailedOutbound marks it ABORTED internally and returns nil.
	// Business logic errors are stored in RevertError on the UTX; only infra errors are returned.
	if err := k.FinalizeOutbound(ctx, utxId, outbound); err != nil {
		k.Logger().Error("outbound finalization error stored on utx",
			"utx_id", utxId,
			"outbound_id", outboundId,
			"error", err.Error(),
		)
		if storeErr := k.UpdateUniversalTx(ctx, utxId, func(u *types.UniversalTx) error {
			u.RevertError = err.Error()
			return nil
		}); storeErr != nil {
			return storeErr
		}
	}

// IsChainOutboundEnabled checks if outbound is enabled for a given chain
func (k Keeper) IsChainOutboundEnabled(ctx context.Context, chain string) (bool, error) {
	config, err := k.GetChainConfig(ctx, chain)
	if err != nil {
		if errors.Is(err, collections.ErrNotFound) {
			// chain not found
			return false, nil
		}
		return false, err
	}
	if config.Enabled == nil {
		return false, nil
	}
	return config.Enabled.IsOutboundEnabled, nil
}
