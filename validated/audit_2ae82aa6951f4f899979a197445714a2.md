### Title
Market order matching rounds down the filled quantity without refunding the shortfall, letting the counterparty capture the "dust" value — ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the amount of tokens a taker/maker receives from a trade using integer (floor) division via `MarketUtils.multiplyAndDivide`. When one side's order is the smaller of the two and gets fully consumed, that side's *entire remaining sell quantity* is transferred to the counterparty, while the *converted buy quantity it receives back is floor-divided*. The rounding remainder is never refunded — it is effectively kept by the counterparty, producing a systemic, unrefunded value loss for the side whose order is exhausted, exactly matching the reported "successful bidder loses value to division rounding" bug class.

### Finding Description
In `matchSingleOrder` [1](#0-0) , the taker's hypothetical buy amount is computed as:

```java
long takerBuyTokenQuantityRemain = MarketUtils
    .multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity,
        this.disableJavaLangMath());
```

`MarketUtils.multiplyAndDivide` performs `floorDiv(a*b, c)` [2](#0-1) , so any fractional remainder of `a*b/c` is truncated.

When the taker's computed demand is smaller than the maker's remaining supply ("taker < maker" branch), the code does:

```java
takerBuyTokenQuantityReceive = takerBuyTokenQuantityRemain;         // floor-divided amount
makerBuyTokenQuantityReceive = takerOrderCapsule.getSellTokenQuantityRemain(); // FULL amount
takerOrderCapsule.setSellTokenQuantityRemain(0);                    // fully consumed, no refund
``` [3](#0-2) 

The taker gives up **all** of its remaining sell tokens (`makerBuyTokenQuantityReceive`), but only receives the **floor-divided** conversion (`takerBuyTokenQuantityReceive`). The fractional remainder that should have gone to the taker (or been refunded) instead becomes extra profit for the maker, since the maker's balance is credited with the taker's full payment while only giving up the correctly-reduced amount of its own inventory.

The symmetric case ("taker > maker") shows the same defect in reverse — the maker's order is fully consumed while it only receives the floor-divided `makerBuyTokenQuantityReceive` [4](#0-3) , so whichever side's order is the smaller (fully filled) one loses the rounding remainder to the other side.

This is distinct from the "amount too small" guard, which does correctly refund the taker when `takerBuyTokenQuantityRemain == 0` via `returnSellTokenRemain` [5](#0-4)  — that path only protects against zero-fill dust, not the non-zero rounding remainder in the normal fill path.

Notably, the project's own tests acknowledge this as an "Accuracy problem" in a code comment [6](#0-5) , confirming the rounding behavior is a recognized but unaddressed characteristic of the matching engine.

### Impact Explanation
Every order match where the fully-consumed side's proportional conversion has a non-zero remainder results in that side paying its full sell amount but receiving a rounded-down buy amount, with the difference transferred to the counterparty with no refund. This is a direct, unrefunded loss of user funds in TRON's on-chain decentralized exchange (`MarketSellAssetActuator`), reachable by any unprivileged account placing a market order. While per-trade losses are bounded by the token's price ratio granularity, they are systemic (occur in the common "unequal remaining size" case) and can be amplified by adversarial makers who intentionally set unfavorable sell/buy ratios to reliably skim the rounding remainder from every matching taker order.

### Likelihood Explanation
High. This code path executes on essentially every partial fill where the taker and maker's remaining quantities are not exactly equal (the common case), which is a normal, unprivileged, frequently-triggered flow (`MarketSellAssetContract` / `MarketSellAssetActuator.execute` → `matchOrder` → `matchSingleOrder`) [7](#0-6) .

### Recommendation
Refund the rounding remainder to the side whose order is fully consumed instead of letting the counterparty capture it. Concretely, in the "taker < maker" branch, reduce `makerBuyTokenQuantityReceive` to the amount actually required to purchase `takerBuyTokenQuantityReceive` (e.g., `ceil` or exact conversion) and refund the leftover sell-token difference back to the taker (similarly for the symmetric "taker > maker" branch and the maker). Alternatively, always recompute the exact "cost" of the floor-divided receive amount and credit any leftover back to the party whose order was consumed, mirroring the existing `returnSellTokenRemain` mechanism already used for the zero-fill case.

### Proof of Concept
Consider a maker order selling 3 units of token A for 7 TRX (`makerSellQuantity=3`, `makerBuyQuantity=7`) with a large remaining supply, and a taker selling 10 TRX for token A (`takerSellRemainQuantity=10`):

1. `takerBuyTokenQuantityRemain = floor(10*3/7) = floor(4.285) = 4` [2](#0-1) 
2. Since `4 < makerSellRemainQuantity`, the "taker < maker" branch runs: `takerBuyTokenQuantityReceive = 4`, `makerBuyTokenQuantityReceive = 10` (all of the taker's TRX) [8](#0-7) .
3. Fair cost for 4 units of A at the maker's price (7/3 TRX per unit) is `4 * 7/3 ≈ 9.33` TRX, but the taker pays the full `10` TRX with no refund of the `~0.67` TRX difference — that value is captured entirely by the maker.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
