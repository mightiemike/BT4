### Title
Sandwichable `ExchangeInjectActuator`/`ExchangeWithdrawActuator` liquidity ratio manipulation - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the paired-token amount to move using the exchange pool's *current* `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with no slippage/expected-output guard analogous to `ExchangeTransactionActuator`'s `tokenExpected` check. Because block transaction ordering is attacker-influenceable (same trust model as the mempool front-running described in the external report), an unprivileged user can sandwich another user's inject/withdraw call by trading against the pool via `ExchangeTransactionActuator` immediately before and after it, extracting value exactly as User1 does to User2 in the referenced report.

### Finding Description
`ExchangeInjectActuator.execute()` reads `firstTokenBalance`/`secondTokenBalance` from the `ExchangeCapsule`, derives `anotherTokenQuant` proportionally, and calls `exchangeCapsule.setBalance(...)` directly from these freshly-read values without any bound on how much the ratio may have moved since the caller decided on `tokenQuant`: [1](#0-0) 

The validate path only checks `anotherTokenQuant > 0`, unlike `ExchangeWithdrawActuator.doValidate()`, which at least applies a 0.0001 precision tolerance check, and unlike `ExchangeTransactionActuator.doValidate()`, which enforces `anotherTokenQuant >= tokenExpected` from the caller: [2](#0-1) [3](#0-2) 

`ExchangeWithdrawActuator` has the same structural exposure: `anotherTokenQuant` and the new pool balances are computed from the live ratio just before `setBalance()`, with no protection against that ratio having been moved by an intervening trade in the same block: [4](#0-3) 

Any account can freely trade against the pool via `ExchangeTransactionActuator`, which mutates the pool ratio through `ExchangeCapsule.transaction()`: [5](#0-4) 

This lets any unprivileged attacker construct the exact analog of the reported attack:
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) broadcast by the exchange creator.
2. Attacker front-runs with an `ExchangeTransactionContract` that skews `firstTokenBalance`/`secondTokenBalance` in their favor.
3. The creator's inject/withdraw executes and computes `anotherTokenQuant`/new balances off the skewed ratio, moving assets in/out of the pool at an unfavorable rate for the pool (and for other liquidity/token holders).
4. Attacker back-runs with a reverse `ExchangeTransactionContract`, extracting the ratio distortion as profit, at the expense of the pool and its token holders.

### Impact Explanation
Successful exploitation lets an attacker extract value from the AMM-style `Exchange`/`ExchangeV2` pool at the cost of the creator (during inject) or other pool participants/token holders (during withdraw), i.e., asset/accounting corruption reachable purely through broadcast transactions — no privileged role or off-chain access needed by the attacker.

### Likelihood Explanation
Any account can call `ExchangeTransactionActuator` against an existing exchange pool at will, and transaction ordering within a block/mempool is not guaranteed to protect against front/back-running, so the precondition (a pending inject/withdraw transaction to sandwich) is the only limiting factor, making this feasible whenever exchange creators perform inject/withdraw operations.

### Recommendation
Add an explicit slippage/expected-output parameter (mirroring `tokenExpected` in `ExchangeTransactionContract`) to `ExchangeInjectContract`/`ExchangeWithdrawContract`, and validate the computed `anotherTokenQuant` against it in both actuators' `doValidate()`/`execute()`, rejecting the operation if the pool ratio has moved beyond the caller's tolerance since the transaction was constructed.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeInjectContract{exchangeId, tokenId=firstToken, quant=Q}` intending to inject at the pool's current ratio.
2. Attacker submits `ExchangeTransactionContract` selling a large amount of `firstToken` into the pool, shifting `firstTokenBalance`/`secondTokenBalance` so `anotherTokenQuant` computed in `ExchangeInjectActuator.execute()` (lines 60-83 above) becomes favorable to the attacker's subsequent trade.
3. The creator's inject executes with the skewed ratio, and `Commons.putExchangeCapsule` persists the new (distorted) balances.
4. Attacker submits a second `ExchangeTransactionContract` reversing their initial trade, capturing the ratio distortion introduced by the inject as profit — mirroring steps 4-7 of the external report's PoC against `YuzuILP.updatePool()`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
