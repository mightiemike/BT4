### Title
`rlp_execute` silently drops attached native `NEAR` deposit for AddKey/DeleteKey actions instead of reverting on non-zero value - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/types.rs`)

### Summary
The NEAR wallet contract's `rlp_execute` entry point is `#[payable]`, so a caller (or relayer forwarding an Ethereum-signed transaction) can attach an arbitrary NEAR deposit to any Ethereum-emulated transaction. That deposit is forwarded to `Action::try_into_near_action` as `additional_value` and merged into the resulting Near action's deposit — but only for `FunctionCall` and `Transfer` actions. For `AddKey` and `DeleteKey` actions the `additional_value` parameter is never referenced, so any attached deposit is silently discarded instead of being attached to the resulting promise or rejected up front.

### Finding Description
`Action::try_into_near_action` takes an `additional_value: u128` parameter derived from the caller's attached deposit (via `ExecutionContext::attached_deposit` / `CallerDeposit`), and merges it into `deposit` for `FunctionCall` and `Transfer`: [1](#0-0) 

But the `AddKey` and `DeleteKey` match arms never consume `additional_value` at all — it is completely ignored: [2](#0-1) 

The resulting Near action is passed to `action_to_promise`, which for `AddKey`/`DeleteKey` creates a promise with **zero** attached `NearToken` — the caller's deposit is not forwarded anywhere: [3](#0-2) 

The contract does track the caller's deposit via `CallerDeposit`, but it is only refunded when the downstream promise **fails** — never on success: [4](#0-3) [5](#0-4) 

There is no validation anywhere in `inner_rlp_execute` or `ExecutionContext::new` that rejects a non-zero attached deposit when the parsed action is `AddKey` or `DeleteKey` (both of which have `Action::value() == 0` by definition): [6](#0-5) [7](#0-6) 

This is the same bug class as the Li.Fi finding: functions whose purpose has no legitimate use for the attached native value fail to check/reject a non-zero value, so it is silently absorbed by the contract rather than reverting or being forwarded/refunded.

### Impact Explanation
If a caller (any unprivileged account or a relayer acting on the user's behalf) attaches a NEAR deposit while submitting an Ethereum-emulated `AddKey` or `DeleteKey` transaction through `rlp_execute`, and the underlying promise succeeds, the attached deposit is neither used by the action nor refunded to the caller. The funds remain stuck in the wallet contract account's balance with no code path to reclaim them for the caller who sent them — this is a permanently frozen/misappropriated funds condition reachable by any single transaction signer or RPC caller, matching the "permanently frozen funds" impact category from the report.

### Likelihood Explanation
This is trivially reachable: any account can call the `#[payable]` `rlp_execute` method with a nonzero deposit and an RLP-encoded Ethereum transaction whose ABI-decoded action is `addKey`/`deleteKey` (selectors `ADD_KEY_SELECTOR` / `DELETE_KEY_SELECTOR`). No special privileges, relayer access keys, or malicious validators are required — only a mistake or a malicious relayer/UI that attaches deposit unexpectedly (analogous to the original bug's "mistakenly sent native funds").

### Recommendation
In `inner_rlp_execute` / `ExecutionContext::new`, explicitly reject (return an `Error::User`) any transaction whose parsed action is `AddKey` or `DeleteKey` (or more generally, whose `additional_value`/attached deposit is not consumed by the resulting action) when `attached_deposit` is non-zero, mirroring the check already used for function-call access keys' `DepositWithFunctionCall`. Alternatively, always refund the full `CallerDeposit` back to the caller when the deposit is not attached to the outgoing promise, regardless of success/failure of that promise.

### Proof of Concept
1. Caller/relayer attaches `N` yoctoNEAR (`N > 0`) as `env::attached_deposit()` in a call to `rlp_execute(target, tx_bytes_b64)`.
2. `tx_bytes_b64` encodes an Ethereum transaction whose calldata selector is `ADD_KEY_SELECTOR` (or `DELETE_KEY_SELECTOR`), producing `near_action::Action::AddKey`.
3. `inner_rlp_execute` builds the action via `Action::try_into_near_action(additional_value)`; for `AddKey`, `additional_value` is dropped (`types.rs:262-289`).
4. `action_to_promise` creates an `add_access_key_allowance_with_nonce` promise with no attached tokens (`lib.rs:488-495`).
5. If the promise succeeds, `rlp_execute_callback`'s `PromiseResult::Successful` branch returns success without any refund logic (`lib.rs:313-315`), so the attached `N` yoctoNEAR remains stuck in the wallet contract's own account balance, unreachable by the caller.
