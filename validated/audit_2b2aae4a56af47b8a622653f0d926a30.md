### Title
Cross-tenant offline session hijack via unauthenticated bearer token replay in `getCurrentId`/`validateWithAuthCodeFlow` - (File: `packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts`)

### Summary
`validateWithAuthCodeFlow` calls `api.session.getCurrentId` which, for embedded apps using offline tokens, derives the session-storage lookup key purely from the `dest` claim of any signed session-token JWT presented in the `Authorization: Bearer` header, with no binding to the specific installation/session that minted it. Any correctly-signed JWT with `aud === apiKey` and `dest === <target shop>` — including tokens minted for a different surface/session such as a checkout or customer-account extension token for that shop — will cause the middleware to load and hand over that shop's real offline access-token session to the requester.

### Finding Description
`validateWithAuthCodeFlow` (`packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts:80-91`) starts by calling `api.session.getCurrentId({...})`, which is `getCurrentSessionId` in `packages/apps/shopify-api/lib/session/session-utils.ts:28-84`. For embedded apps, it pulls the `Authorization: Bearer` token from the raw request and decodes it with `decodeSessionToken` [1](#0-0) . `decodeSessionToken` (`packages/apps/shopify-api/lib/session/decode-session-token.ts:15-43`) verifies the HS256 signature against `config.apiSecretKey` and, by default, checks `aud === config.apiKey` [2](#0-1) . It performs **no check that the token was minted for the admin/App-Bridge session context** (there is no `iss`/audience-scope distinction between an admin session token and a checkout/customer-account UI-extension session token — both are HS256-signed with the same app client secret and the same `aud` = app API key, per Shopify's session-token design).

Once decoded, if the app is using offline tokens (the default: `config.useOnlineTokens` false), the session id is computed purely from the `dest` claim:
```
const shop = jwtPayload.dest.replace(/^https:\/\//, '');
...
return getOfflineId(config)(shop);
``` [3](#0-2) 

This offline session id is **independent of `sub`/`sid`** — i.e., independent of which specific session or user context minted the token. Back in `validateWithAuthCodeFlow`, this id is used to `loadSession` from storage [4](#0-3) . Because no `shop` query param is required to match (the mismatch check at line 122 only compares against `req.query.shop`, which the attacker can simply omit), the loaded session for the target shop then passes `session.isActive(...)` and `hasValidAccessToken` checks and is placed into `res.locals.shopify.session`, followed by `next()` [5](#0-4) . From that point, the downstream route handler operates with the target shop's real offline session (including its real access token) attached to the request, on behalf of whoever presented the bearer token.

The exploit path: an unprivileged attacker (e.g., an anonymous customer interacting with a Checkout UI extension or Customer Account UI extension of the same app, installed on shop B) legitimately obtains a valid session token scoped to shop B for a completely different surface/session than the admin embedded app. Because that token is signed with the same app secret and carries the same `aud`, it passes `decodeSessionToken`'s verification unchanged. Replaying it as the `Authorization: Bearer` header against any route protected by `validateAuthenticatedSession` (auth-code-flow branch) causes the middleware to resolve and attach shop B's real offline session — cross-tenant access to another merchant's authenticated session/access token, without ever completing OAuth for that shop.

### Impact Explanation
This breaks the invariant that only material verified for the *current* session/surface should determine which shop's tenant data/access token is exposed to a request. The concrete impact is cross-tenant session hijack: an attacker who never installed or was authorized for shop B can obtain a request context carrying shop B's live offline access token via `res.locals.shopify.session`, letting the app's protected route act against shop B's store data. This matches Shopify's "cross-tenant access" bounty impact class.

### Likelihood Explanation
Preconditions: the app must be embedded, use default offline tokens (`config.useOnlineTokens` false, the common default), and issue session tokens on other surfaces (Checkout/Customer Account UI extensions) that share the app's client secret/API key — which is the normal Shopify session-token architecture, not a misconfiguration. The attacker needs only unprivileged interaction with any Shopify surface of the target app (e.g., visiting checkout as a customer on shop B) to obtain a validly-signed token for shop B, then replay it as a bearer header to any endpoint protected by this middleware. No secret, MITM, or privileged role is required, making this readily reproducible.

### Recommendation
Bind the session lookup to the token's intended context: reject or ignore tokens whose `iss`/audience/claims indicate they were minted for a non-admin surface (checkout/customer-account/POS) when resolving the admin offline-session id, or add an explicit claim (e.g., a `dest`-plus-context binding, or requiring `sid` to match a stored nonce tied to the admin OAuth/session-token issuance flow) so that only tokens minted for the App-Bridge admin session can resolve to `getOfflineId`. At minimum, `getCurrentSessionId`/`decodeSessionToken` should distinguish session-token origin/surface before trusting `dest` for offline-session resolution.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
