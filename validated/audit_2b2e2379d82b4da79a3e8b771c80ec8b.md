### Title
`AccountsDb::shrink_ratio` bypasses the CLI's `[0.0, 1.0]` bounds check when set via `AccountsDbConfig`, corrupting shrink-candidate selection - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountShrinkThreshold`'s `shrink_ratio: f64` is only range-validated on one code path: the validator CLI parser in `validator/src/commands/run/execute.rs`. Any other caller that constructs `AccountsDbConfig { shrink_ratio, .. }` directly (e.g. `ledger-tool`, `test-validator`, `admin_rpc_service`, tests, or any future integrator embedding `accounts-db`) can set `shrink_ratio` to an out-of-range value (negative, or greater than `1.0`), because `AccountsDb::new_with_config` and `AccountShrinkThreshold` perform no bounds check themselves. This mirrors the Saddle Finance bug class: validation exists on the "update" path (CLI) but is skipped on the "initialization" path (direct struct construction).

### Finding Description
`AccountShrinkThreshold` is defined with no invariants enforced in its constructors: [1](#0-0) 

The only place that validates the ratio is the CLI argument-parsing code, which explicitly checks the value is in `0.0..=1.0` before building the enum: [2](#0-1) 

`AccountsDb::new_with_config` takes `AccountsDbConfig` (which carries `shrink_ratio: AccountShrinkThreshold`) and stores it into `self.shrink_ratio` with no re-validation: [3](#0-2) [4](#0-3) 

That unvalidated value is then used directly in fee/ratio-style arithmetic in the shrink decision logic: [5](#0-4) [6](#0-5) 

This is structurally the same defect as the Saddle report: a parameter (`shrink_ratio`, analogous to `swapFee`/`adminFee`) is clamped on one entry point (`setAdminFee`/the CLI validator arg parser) but set directly, without any clamp, on another entry point (`Swap.initialize`/`AccountsDbConfig` struct construction used by `new_with_config`).

### Impact Explanation
If `shrink_ratio` is out of `[0.0, 1.0]`:
- With `AccountShrinkThreshold::IndividualStore { shrink_ratio > 1.0 }`, `is_candidate_for_shrink` computes `(alive_bytes / total_bytes) < shrink_ratio`, which is always true since the alive ratio can never exceed `1.0`. Every storage — including ones that are 100% alive — becomes a perpetual shrink candidate, causing continuous, unnecessary rewriting of account storages (disproportionate CPU and I/O cost).
- With `AccountShrinkThreshold::TotalSpace { shrink_ratio > 1.0 }`, in `select_candidates_by_total_usage`, the loop condition `alive_ratio > shrink_ratio` can never be satisfied, so the "stop shrinking" exit is never reached and essentially all shrink candidates (even fully-alive ones) get shrunk on every pass.
- With a negative `shrink_ratio`, the opposite happens: the "goal already achieved" branch triggers immediately, effectively disabling shrink entirely, letting dead/sparse storages accumulate indefinitely (disproportionate storage growth, unbounded disk usage over time).

This does not require a malicious peer or crafted snapshot — it is purely a config/parameter-validation gap reachable by any code path (including test/ops tooling) that builds `AccountsDbConfig` outside the validator CLI.

### Likelihood Explanation
Moderate-to-low likelihood in the mainline validator binary, since the CLI path (`validator/src/commands/run/execute.rs`) does validate the range before constructing `AccountShrinkThreshold`. However, `AccountsDbConfig`/`AccountShrinkThreshold` are public API surfaces used from multiple call sites (`ledger-tool/src/args.rs`, `test-validator/src/lib.rs`, `validator/src/admin_rpc_service.rs`, `runtime/src/bank/tests.rs`, etc.), and `AccountsDb::new_with_config` itself performs zero defensive validation, so any of those paths (or a future one) can silently introduce the bad value. The bug is inert until such a path passes an out-of-range value, similar to the original Saddle finding requiring `initialize` to be called with unclamped parameters.

### Recommendation
Add validation in `AccountsDb::new_with_config` (or in an `AccountShrinkThreshold` constructor) that clamps or rejects `shrink_ratio` values outside `[0.0, 1.0]`, so that the same invariant enforced today only in the CLI argument parser is enforced at the actual point of use — mirroring the fix applied to Saddle's `Swap.initialize`, which was updated to apply the same limits as the runtime setters.

### Proof of Concept
1. Construct `AccountsDbConfig { shrink_ratio: AccountShrinkThreshold::TotalSpace { shrink_ratio: 1.5 }, .. }` directly (bypassing `validator/src/commands/run/execute.rs`'s `0.0..=1.0` check), e.g. from a test harness or an alternate binary that builds `AccountsDbConfig` itself.
2. Call `AccountsDb::new_with_config(paths, config, None, exit)`; this succeeds with no error because `accounts_db.rs` never re-validates `shrink_ratio`.
3. Populate storages with a mix of highly-alive and mostly-dead slots, then invoke `shrink_candidate_slots`, which calls `select_candidates_by_total_usage(&shrink_candidates_slots, 1.5)`.
4. Observe that the loop's stop condition `alive_ratio > shrink_ratio` (line 3050 in `accounts_db.rs`) is unreachable for `shrink_ratio = 1.5`, so all candidate slots—including fully alive ones—are selected for shrink, demonstrating the unvalidated parameter driving disproportionate/unnecessary shrink work.

    /// Determines whether a given AccountStorageEntry instance is a
    /// candidate for shrinking.
    pub(crate) fn is_candidate_for_shrink(&self, store: &AccountStorageEntry) -> bool {
        let total_bytes = store.written_bytes();
        let alive_bytes = self.alive_bytes_after_shrink(store) as u64;
        match self.shrink_ratio {
            AccountShrinkThreshold::TotalSpace { shrink_ratio: _ } => alive_bytes < total_bytes,
            AccountShrinkThreshold::IndividualStore { shrink_ratio } => {
                (alive_bytes as f64 / total_bytes as f64) < shrink_ratio
            }
        }
    }
