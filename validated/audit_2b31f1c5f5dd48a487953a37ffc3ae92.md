### Title
Wallet Contract's shared hardcoded EVM `CHAIN_ID` for all non-mainnet/testnet networks allows cross-chain signature replay - (File: `runtime/near-wallet-contract/src/lib.rs`, `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The `near-wallet-contract` (the global contract that gives ETH-implicit accounts EVM transaction emulation) checks an EIP-2930/1559 RLP transaction's `chain_id` field against a value baked into the WASM at build time. This value is only distinct for the two officially-recognized NEAR networks; every other NEAR chain (any custom `chain_id` string that is not exactly `"mainnet"` or `"testnet"`) is bucketed into the same `LOCALNET` contract build with the identical hardcoded EVM chain id `399`. Because the signed Ethereum-style transaction bytes carry only this static, non-network-specific chain id, and the account address itself is derived deterministically and chain-agnostically from the signer's secp256k1 public key, a signature produced for a wallet on one independently-operated "localnet-bucketed" NEAR chain is byte-for-byte valid and replayable on any other NEAR-protocol chain that falls into the same bucket.

### Finding Description
`wallet_contract_magic_bytes` and `eth_wallet_global_contract_hash` in `runtime/near-wallet-contract/src/lib.rs` special-case only `chains::MAINNET` and `chains::TESTNET`; every other `chain_id` string falls through to the shared `LOCALNET` contract: [1](#0-0) 

The `LOCALNET` WASM is built once with a fixed EVM chain id of `399`, defined in `build.rs`: [2](#0-1) 

Inside the deployed contract, this compile-time constant is the sole chain-binding check performed on an inbound RLP-encoded Ethereum transaction before it is converted into a NEAR action and executed: [3](#0-2) [4](#0-3) 

There is no dependency on the actual NEAR genesis hash, epoch, or any other network-unique identifier — only this static `CHAIN_ID=399` value, which is identical across every NEAR-protocol-based network that isn't literally named `mainnet`/`testnet` (forknets, mocknets other than the exact `"mocknet"` string, private/custom-named chains, sandboxes deployed with a different `chain_id`, etc., all fall to `LOCALNET`). This is structurally the same root cause as the reported DODO GSP issue: a chain identifier that is fixed independently of the actual live network state and is not included as a network-unique value in the signed payload, enabling signatures to be replayed on a different chain instance that shares the same identifier.

Anyone possessing a valid `SignedTransaction` calling `rlp_execute` (reachable by any account as relayer, per `inner_rlp_execute`/`validate_tx_relayer_data`) can resubmit the identical RLP bytes to the wallet contract instance deployed on any other chain using the `LOCALNET` bucket, because the wallet's own per-network nonce state is independent per chain and does not protect across chains: [5](#0-4) [6](#0-5) 

### Impact Explanation
Because the eth-implicit account id/address is derived purely and deterministically from the signer's public key (chain-agnostic), the same account exists at the same address on every chain that shares the `LOCALNET` wallet-contract build. A single signed Ethereum-style transaction (e.g. a base-token transfer, ERC-20 transfer/approve emulation, or add/delete-key action) captured off one such chain can be resubmitted verbatim as `rlp_execute` on any other chain in the same bucket where the same public key controls funds, moving value or mutating access keys without a fresh authorization on that chain — an unauthorized value movement / access-key-manipulation primitive triggered purely by resubmitting a previously observed transaction.

### Likelihood Explanation
Any account can call `rlp_execute` with an RLP blob copied from a public transaction/receipt on another chain; the only requirement is that the target chain's wallet contract be the shared `LOCALNET` build (true for essentially all non-official NEAR networks, including forknets/mocknets/private deployments used in production-adjacent contexts) and that the victim account holds funds/keys reachable in the same way on that chain. No cooperation from the victim or special privileges are required beyond observing a previously broadcast transaction.

### Recommendation
Bind the wallet contract's chain check to a value that is unique per live network deployment rather than a value shared by every non-mainnet/testnet chain. Concretely, derive/embed the EVM `chain_id` from the actual NEAR `chain_id` string (or genesis hash) at global-contract deployment time instead of collapsing all "other" networks into one shared `LOCALNET` constant, and reject `rlp_execute` calls whose embedded chain id does not correspond to a value cryptographically tied to the specific network's genesis/config.

### Proof of Concept
1. Deploy the (unmodified) `near-wallet-contract` global contract on two independently operated NEAR chains, `chain_id = "forknet-A"` and `chain_id = "forknet-B"`; both resolve to the shared `LOCALNET` wallet contract build with baked EVM `CHAIN_ID = 399` (`eth_wallet_global_contract_hash`/`wallet_contract_magic_bytes` in `runtime/near-wallet-contract/src/lib.rs`).
2. A user creates an ETH-implicit account from public key `P` on `forknet-A`, funds it, and signs an EIP-2930 transaction (`chain_id: 399`) transferring funds to some target, then submits it via `rlp_execute` on `forknet-A`.
3. The same public key `P` also controls an ETH-implicit account on `forknet-B` (same deterministic address derivation) that likewise holds funds (e.g., both chains were seeded from a shared snapshot/faucet).
4. An observer copies the RLP transaction bytes from step 2 and calls `rlp_execute` with them against the wallet contract instance on `forknet-B`. Since `forknet-B`'s wallet contract also has `CHAIN_ID = 399` baked in and its own independent nonce counter starts fresh/unaffected by `forknet-A`'s nonce, the same signed bytes are accepted (`validate_tx_relayer_data` in `internal.rs` only checks `tx.chain_id != Some(CHAIN_ID)`, sender/target/nonce local to `forknet-B`), executing the transfer a second time on `forknet-B` without any new authorization from the key holder.
