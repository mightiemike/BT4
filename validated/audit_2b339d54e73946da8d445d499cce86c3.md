### Title
Unsafe `BigInteger.longValue()` Truncation in Voter Reward Computation Can Produce Distorted/Negative Reward and Allowance Values - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java], [File: actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java], [File: chainbase/src/main/java/org/tron/core/service/RewardViCalService.java])

### Summary
Three reward-accounting code paths in java-tron convert a `BigInteger` reward computation to a `long` using the *unsafe* `BigInteger.longValue()` method instead of the safe, range-checked `longValueExact()` that is used everywhere else in the same files for TRX/asset accounting. `longValue()` silently discards high-order bits and returns wrapped/truncated (and potentially negative) results when the underlying `BigInteger` exceeds `Long.MAX_VALUE`/`Long.MIN_VALUE`, exactly the unsafe-cast bug class described in the Blex report where PnL/fee casts could silently produce distorted values instead of reverting.

### Finding Description
The vote-reward system accumulates a per-witness reward index (`Vi`) as an unbounded `BigInteger` in `DelegationStore`/`RewardViCalService`: [1](#0-0) 

That index is later converted back into a voter's spendable `reward` (a `long`) by multiplying the delta-Vi by the voter's `userVote` count and dividing by `DECIMAL_OF_VI_REWARD`, then calling `.longValue()`: [2](#0-1) [3](#0-2) [4](#0-3) 

Every other conversion of an accounting-relevant `BigInteger` to `long` in this codebase (e.g. `Wallet.checkPublicAmount`, `ResourceProcessor.calculateGlobalLimitV2`, `JsonRpcApiUtil.parseBlockNumber`) deliberately uses `longValueExact()` so an out-of-range result throws `ArithmeticException` rather than silently wrapping: [5](#0-4) 

The three reward-computation call sites above are the exception: they use `longValue()`, which per the JDK contract "if this BigInteger is too big to fit in a long, only the low-order 64 bits are returned," i.e. a silent, unchecked narrowing cast — the same bug class flagged in the external report for `PositionBook`/`FundFee`/`FeeRouter`.

`deltaVi * userVote / DECIMAL_OF_VI_REWARD` is not intrinsically bounded to `long` range: `Vi` is a cumulative index that only grows (it is never reset, only forwarded or incremented) over the lifetime of a witness, and is multiplied by the caller-controlled `userVote` (an unprivileged user's frozen-TRX vote weight) before being divided down. Because both the reward computation and the query path are reachable by ordinary users, an unexpectedly large intermediate product (e.g. from a witness accumulating a very large index over enough cycles combined with a large voter vote count) truncates instead of reverting, and can wrap to an arbitrary — including negative — 64-bit value.

### Impact Explanation
This reward value directly feeds account accounting:
- `MortgageService.adjustAllowance` / `VoteRewardUtil.adjustAllowance` add the (potentially wrapped) reward to `AccountCapsule.setAllowance(...)`, permanently persisting a corrupted balance-like value to state: [6](#0-5) 
- The result is also exposed unprivileged and read-only via the TVM `RewardBalance` precompiled contract, which any smart contract/EOA can call to read `VoteRewardUtil.queryReward`: [7](#0-6) 
- It is written to chain state via the `WithdrawReward`/`WithdrawBalance` actuators/native-contract processors that any account can trigger.

A truncated/wrapped reward could distort a voter's on-chain allowance (state-accounting divergence), and because the arithmetic silently "succeeds" instead of throwing, there is no fail-safe like the `longValueExact()` guard used elsewhere in the same subsystem.

### Likelihood Explanation
Likelihood is low-to-moderate in practice: reaching an intermediate product that exceeds `Long.MAX_VALUE` (~9.22×10^18) requires a witness's cumulative Vi delta times a voter's `userVote` to exceed that bound after dividing by `DECIMAL_OF_VI_REWARD`. This is plausible over long chain lifetimes with witnesses that have very low vote counts (Vi grows as `reward*DECIMAL/voteCount`, so low-vote witnesses accumulate large Vi quickly) combined with large voter positions, but is not trivially triggerable in a single transaction the way the Solidity `PositionBook`/`FeeRouter` bug was. It is nonetheless a genuine unprivileged-reachable divergence between the intended safe-cast pattern used elsewhere in the same modules and the unsafe pattern used in this reward path.

### Recommendation
Replace `.longValue()` with `.longValueExact()` (and handle the resulting `ArithmeticException` defensively, e.g. capping/rejecting the update) in:
- `MortgageService.computeReward` [8](#0-7) 
- `VoteRewardUtil.computeReward` [9](#0-8) 
- `RewardViCalService.getNewRewardAlgorithmReward` [10](#0-9) 

This aligns the reward-accounting path with the safe-cast conventions already used throughout the rest of the same files (`ResourceProcessor`, `Wallet`, `JsonRpcApiUtil`).

### Proof of Concept
A concrete numeric trigger could not be fully validated within the available tooling because the exact value of `DECIMAL_OF_VI_REWARD` and the achievable cumulative `Vi` magnitude over realistic chain lifetimes could not be retrieved before the tool budget was exhausted; this would need to be confirmed with a running/replayed chain (e.g. simulate many cycles for a witness with minimal votes and a large voter position, then call `withdrawReward`/`queryReward` and check whether the returned `long` is negative or wrapped relative to the expected `BigInteger` result). Conceptually: repeatedly call `VoteWitnessActuator` to vote for a witness with `voteCount` kept near 1 while that witness continues to earn block/standby rewards over many cycles (inflating `Vi` per cycle via `reward*DECIMAL_OF_VI_REWARD/voteCount`), then have a large-stake voter call `WithdrawBalanceActuator`/`WithdrawRewardProcessor` (or query via the `RewardBalance` precompile) once `deltaVi*userVote/DECIMAL_OF_VI_REWARD` exceeds `Long.MAX_VALUE`.

    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
