### Title
Missing empty-calldata check in L1 message hash computation causes panic - (File: `crates/starknet_api/src/hash.rs`)

### Summary
`l1_handler_message_hash` (used by `L1HandlerTransaction::calc_msg_hash`) unwraps `calldata.0.split_first()` with an `.expect(...)`, assuming at least one element (the `from_address`) is always present. If this function is ever invoked with an `L1HandlerTransaction` whose `calldata` is empty, the process panics, analogous to the Wireshark BT-ATT dissector crash caused by dereferencing a lookup result without checking it exists first.

### Finding Description [1](#0-0) 

`calc_msg_hash` on `L1HandlerTransaction` calls `l1_handler_message_hash`, which does:
```rust
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
```
There is no prior check that `calldata.0` is non-empty; the code simply assumes the invariant (calldata always starts with `from_address`) holds. This mirrors the CVE-2018-16056 bug class: a lookup/decompose operation is performed on attacker/externally-influenced data without first verifying an "existence" precondition, and the missing check turns into a crash instead of a graceful error.

This routine is reachable from `apollo_rpc`'s JSON-RPC handlers (`crates/apollo_rpc/src/v0_8/api/api_impl.rs`, which references `calc_msg_hash`/`message_hash` in the message-status/handling logic) and from `apollo_rpc/src/v0_8/transaction.rs`. Because I could not fully trace every call path within the remaining iteration budget, I was not able to conclusively confirm whether the gateway/mempool path enforces `calldata` non-emptiness for every `L1HandlerTransaction` before this function can be reached with attacker-influenced data (e.g., through RPC endpoints that accept a transaction hash and recompute the message hash from stored/decoded transaction data, or through test/conversion utilities that construct `L1HandlerTransaction` values). `crates/apollo_gateway/src/stateless_transaction_validator.rs` contains calldata-length-related validation, but I did not verify it specifically enforces a non-empty calldata requirement for L1-handler transactions on every code path that eventually calls `calc_msg_hash`.

### Impact Explanation
If reachable with an empty-calldata `L1HandlerTransaction` (e.g., via a JSON-RPC call that recomputes the message hash from transaction data before/without the same validation the gateway applies to submitted transactions), this would panic the RPC/sequencer node process — a denial-of-service condition preventing the node from confirming/serving new transactions or messages, matching the "network unable to confirm new transactions" impact criterion.

### Likelihood Explanation
The likelihood hinges entirely on whether any reachable path constructs or accepts an `L1HandlerTransaction` with `calldata.0.is_empty()` before calling `calc_msg_hash`. If the gateway's stateless validator unconditionally rejects L1Handler transactions with empty calldata before any such transaction can reach storage or RPC serialization, this is not exploitable by an external actor, only reachable via internal/legitimate L1 event flow (which always includes `from_address`, making it not attacker-controlled in practice). I was unable to confirm this with certainty in the time available.

### Recommendation
Replace the `.expect()` in `l1_handler_message_hash` with a proper `Result`-based check (returning a descriptive error, e.g., `StarknetApiError::InvalidCalldata` or similar) instead of panicking, regardless of whether the current call graph is provably reachable by an attacker — per the project's own coding rule ("Never panic on data reachable from requests"). Additionally, verify and, if necessary, enforce that all paths constructing `L1HandlerTransaction` (RPC, storage deserialization, conversion utilities) guarantee non-empty calldata before this function can be invoked.

/// Calculating the message hash of L1 -> L2 message.
/// For more info: <https://docs.starknet.io/documentation/architecture_and_concepts/Network_Architecture/messaging-mechanism/#structure_and_hashing_l1-l2>
pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());

    let payload_length_as_felt =
        Felt::from(u64::try_from(payload.len()).expect("usize should fit in u64"));
    encoded.extend(payload_length_as_felt.to_bytes_be());

    for felt in payload {
        encoded.extend(felt.to_bytes_be());
    }

    let mut keccak = Keccak256::default();
    keccak.update(&encoded);
    L1L2MsgHash(keccak.finalize().into())
}
