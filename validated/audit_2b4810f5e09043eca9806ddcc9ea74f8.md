## Analysis: Panic-inducing `unwrap()` on unresolved GlobalContractDistribution shard mapping across double resharding

The CVE report describes GPAC's `gf_list_last()` dereferencing invalid memory when a list is empty/inconsistent, causing DoS. The nearcore analog is a state-transition function that calls `.unwrap()` on a `Result` that can legitimately be `Err` in production, panicking the runtime apply loop and halting all nodes applying that chunk.

### Root cause

`Receipt::receiver_shard_id` for a `GlobalContractDistribution` receipt falls back to `ShardLayout::resolve_to_current_shard` when its `target_shard` is no longer in the current layout, returning `Err(EpochError::ShardingError(..))` if the shard cannot be resolved: [1](#0-0) 

`resolve_to_current_shard` dispatches by layout version. For V3 layouts it walks the *full* cumulative split history, but for the older `V0`/`V1`/`V2` layouts (used by static/protocol-version-driven resharding — what real, non-dynamic-resharding networks use) it explicitly only resolves a **single generation**: [2](#0-1) 

The consumer of this in the delayed-receipt queue drain path, `receipt_filter_fn`, unwraps both the shard-layout lookup and the `receiver_shard_id` result unconditionally: [3](#0-2) 

So if a `GlobalContractDistribution` receipt (created by any account calling `DeployGlobalContract` — a normal, unprivileged transaction) sits in the delayed-receipt queue long enough to span **two** static (V0/V1/V2) resharding transitions, `resolve_to_current_shard` returns `None` on the second hop, `receiver_shard_id` returns `Err`, and `receipt_filter_fn`'s `.unwrap()` panics inside `Runtime::apply`/`process_delayed_receipts`, which every node applying that shard's chunk will execute deterministically — a transaction-triggered chain halt, not just a single-node crash.

The receipt itself is created here, seeded with `target_shard = current_shard_id` at deploy time: [4](#0-3) 

Notably, the project's own test suite already recognizes this exact bug class for the *dynamic* (V3) resharding path and specifically tests that the double-resharding case does **not** panic there: [5](#0-4) 

The V3 fix (full cumulative `shards_split_map`, walking arbitrarily many generations) was added, but `resolve_to_current_shard`'s V0/V1/V2 branch retains the original single-generation limitation, and `receipt_filter_fn` still unconditionally unwraps the `Result`.

### Title
Panic-inducing unwrap on unresolvable GlobalContractDistribution shard mapping across two static reshardings halts chunk application - (File: runtime/runtime/src/congestion_control.rs)

### Summary
`receipt_filter_fn` in the delayed-receipt-queue drain path unwraps `Receipt::receiver_shard_id`, which returns `Err` for a `GlobalContractDistribution` receipt whose `target_shard` cannot be resolved by `ShardLayout::resolve_to_current_shard`. For `V0`/`V1`/`V2` shard layouts, that resolver only walks a single resharding generation, so a distribution receipt delayed across two consecutive static reshardings causes the unwrap to panic during normal chunk application.

### Finding Description
`Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437-466`) is designed to gracefully return `Err(EpochError::ShardingError(..))` when a `GlobalContractDistribution` receipt's `target_shard` cannot be mapped to the current shard layout (e.g., after resharding). However, `resolve_to_current_shard` (`core/primitives/src/shard_layout/mod.rs:230-237`) only performs a full multi-generation walk for `ShardLayout::V3`; for `V0`/`V1`/`V2` it falls back to `get_children_shards_ids`, which resolves only one resharding hop. `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`), used while popping receipts from the persistent delayed queue during `Runtime::apply`, calls `.unwrap()` directly on this fallible result instead of handling the `Err` gracefully (e.g., treating it as `StorageInconsistentState` like other similar cases in the runtime, e.g. `runtime/runtime/src/lib.rs:1469-1491`). Any account can trigger creation of a `GlobalContractDistribution` receipt via a normal `DeployGlobalContract` action (`runtime/runtime/src/global_contracts.rs:143-170`); if that receipt is pushed to the delayed queue (e.g., due to shard congestion) and remains there across two consecutive static resharding transitions, the shard it was targeting no longer exists and cannot be resolved by the single-generation fallback, causing the unwrap to panic.

### Impact Explanation
The panic occurs inside `Runtime::apply`'s receipt-processing loop, which is the deterministic state-transition function executed identically by every validator/node tracking the affected shard. Because the trigger (a delayed `GlobalContractDistribution` receipt plus two reshardings) is part of the canonical chain state, all honest nodes applying that chunk hit the same panic — this is a transaction-triggered halt of chunk application for the affected shard, not merely a single misbehaving node crashing.

### Likelihood Explanation
Reaching this requires: (1) a `DeployGlobalContract` transaction — freely available to any signer, (2) the resulting distribution receipt getting stuck in the delayed queue long enough to span two resharding events, and (3) the network being on `V0`/`V1`/`V2` static shard layouts rather than `V3` dynamic resharding (which nearcore's test suite shows was already hardened for this exact bug class). Static resharding events are infrequent and typically coupled to protocol upgrades, and sustaining shard congestion across two of them requires specific timing, so the likelihood is not trivially exploitable on demand, but the underlying panic condition is a genuine unhandled-`Err` state-consistency gap in the runtime that any global-contract deployer can seed.

### Recommendation
- In `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`), replace the `.unwrap()` calls with proper error propagation (e.g., surfacing `RuntimeError::StorageError(StorageError::StorageInconsistentState(..))` or `RuntimeError::ReceiptValidationError`), matching the graceful-error pattern already used elsewhere in the runtime for postponed/delayed receipts.
- Extend `ShardLayout::resolve_to_current_shard`'s `V0`/`V1`/`V2` branch (or the `get_children_shards_ids` chain it relies on) to walk multiple resharding generations rather than only one, consistent with the `V3` full-history behavior, so legacy layouts are not asymmetrically vulnerable.

### Proof of Concept
1. Deploy on a network still using `ShardLayout::V1`/`V2` (static resharding).
2. From an unprivileged account, submit a `DeployGlobalContract` action; this creates a `GlobalContractDistributionReceipt` with `target_shard` = the deployer's current shard (`runtime/runtime/src/global_contracts.rs:143-170`).
3. Saturate the target shard's compute/gas so the receipt is pushed into the persistent delayed-receipt queue instead of being processed immediately.
4. Trigger (or wait for) two consecutive static resharding transitions (protocol upgrades that change the shard layout) while the receipt remains delayed.
5. Stop saturating and let the delayed queue drain; when the stale receipt is popped, `receipt_filter_fn` calls `receiver_shard_id(&shard_layout).unwrap()`, which now returns `Err` because `resolve_to_current_shard` on the `V1`/`V2` path cannot walk back two generations, causing a panic inside `Runtime::apply` on every node applying that chunk.

    /// Resolve any historical shard ID to a current descendant shard ID.
    /// For V3 layouts this uses the complete `shards_split_map`.
    /// For older layouts it falls back to `get_children_shards_ids` (single generation only).
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        match self {
            Self::V0(_) | Self::V1(_) | Self::V2(_) => {
                self.get_children_shards_ids(shard_id).map(|c| c[0])
            }
            Self::V3(v3) => v3.resolve_to_current_shard(shard_id),
        }
    }
