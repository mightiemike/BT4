### Title
Missing "class must be declared" check in Starknet OS `execute_replace_class` allows honest-node state divergence via `replace_class` syscall - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The `replace_class` syscall lets any contract change its own class hash. Blockifier (the Rust execution engine that builds/validates blocks) enforces that the target `class_hash` must correspond to an already-declared class before applying the state update. The Starknet OS (the Cairo re-execution/proving engine that must independently reproduce the same state transition for proof generation) does **not** perform this check at all — it unconditionally writes the new (possibly undeclared) class hash into `contract_state_changes`. This mirrors the referenced bug class exactly: a restriction ("class must be declared") is enforced on one state-mutation path (blockifier tx execution) but is bypassable through another path that mutates the exact same piece of state (OS re-execution) without re-checking the invariant — just like `MAX_MINT_PER_ADDRESS` being checked at `mint` but not at `transferFrom`.

### Finding Description
In `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`, `execute_replace_class` explicitly skips the declared-class check with a `TODO`: [1](#0-0) 

The deprecated (Cairo0) OS syscall path has the identical gap: [2](#0-1) 

In contrast, Blockifier's Rust implementation of the same syscall enforces the check by reading the compiled class, which fails with a `StateError` ("... is not declared") if the class was never declared, for both the deprecated (Cairo0) and current syscall handlers: [3](#0-2) 

This is confirmed by Blockifier's own test suite, which explicitly asserts that replacing with an undeclared class hash is rejected ("is not declared") and that replacing with a valid declared class succeeds: [4](#0-3) [5](#0-4) 

Any unprivileged account can trigger this divergence with a single ordinary transaction: a contract simply calls the `replace_class` syscall with a `class_hash` value that has never been declared.
- Under honest Blockifier execution (which builds/validates the block), this syscall raises a state error, the call/transaction fails/reverts, and the target contract's class hash is left unchanged in the committed block (only fee/nonce state changes are applied, per V3 revert semantics).
- Under the Starknet OS re-execution of the very same transaction (used to reconstruct/prove the block's state transition for L1), the identical `replace_class(class_hash)` call succeeds unconditionally and the OS writes the undeclared `class_hash` into `contract_state_changes` for that contract, producing a genuinely different final state than what Blockifier computed.

Because the OS is the component responsible for independently re-deriving the state root/commitment used for proving and settlement, this creates a case where the OS's re-executed state diverges from the state produced by the honest sequencer/blockifier for the exact same transaction — an honest-node/committed-state divergence, not dependent on any malicious operator, prover, or peer.

### Impact Explanation
This breaks a core soundness invariant of the OS: every state mutation it applies during re-execution must match what an honest sequencer (Blockifier) would have produced, since the OS's re-execution is the basis of the correctness proof submitted for the block. Because the class-declared check is silently missing in the Cairo implementation while being enforced in Blockifier, a normal user transaction calling `replace_class` with an undeclared class hash causes the OS to compute a wrong committed class hash / wrong state root for that contract relative to the Blockifier-computed (canonical) state — i.e., "wrong committed root" and "honest-node divergence," which the validation criteria explicitly treat as concrete, in-scope impact. Since a contract's class hash directly determines what code the network subsequently executes for that address, an undetected mismatch here can propagate into incorrect execution of subsequent calls to that contract in the OS's view, further compounding state corruption.

### Likelihood Explanation
The trigger requires nothing more than an ordinary account submitting an `__execute__` call that invokes `replace_class` with a `class_hash` that has not been declared — no elevated privileges, no colluding sequencer/prover/peer, and no unusual transaction shape. This is directly reachable from the standard invoke-transaction execution path that every user transaction goes through, making the likelihood high for anyone aware of the missing check (which is also flagged by an explicit `TODO` comment in the source, making it easy to notice).

### Recommendation
Add the same "class must be declared" check to the OS's `execute_replace_class` (both the current Cairo1 path in `syscall_impls.cairo` and the deprecated Cairo0 path in `deprecated_execute_syscalls.cairo`) that Blockifier performs in `hint_processor.rs`/`syscall_base.rs`, i.e., verify the `class_hash` exists in the OS's declared-class mapping (mirroring `state.get_compiled_class`) before writing the new `StateEntry`, and cause the syscall/transaction to fail exactly as Blockifier does when the class is undeclared. This must be resolved (the `TODO(Yoni, 1/1/2026)` comment indicates it is a known, unresolved gap) before any block containing `replace_class` calls can be safely proven.

### Proof of Concept
1. An unprivileged user deploys/uses any account/contract that supports calling arbitrary syscalls (or a contract with an external entrypoint that calls `replace_class`).
2. The user submits an ordinary `invoke` transaction whose execution calls the `replace_class` syscall with a `class_hash` value that has never been declared on-chain.
3. Under Blockifier (the node building the block): `syscall_base.rs`/`hint_processor.rs`'s `replace_class` calls `state.get_compiled_class(request.class_hash)`, which fails since the class hash is undeclared, producing a `StateError`/`SyscallExecutionError` and reverting the effect (contract's class hash unchanged in the committed state).
4. When the Starknet OS re-executes the same transaction for proving, `execute_replace_class` in `syscall_impls.cairo` (or `deprecated_execute_syscalls.cairo` for Cairo0) performs no declared-class validation and unconditionally updates `contract_state_changes` with the new (undeclared) `class_hash`.
5. Comparing the two state transitions for the same block/transaction shows the contract's class hash differs between the Blockifier-committed state and the OS re-executed state — a concrete, reproducible honest-node divergence triggerable by a single unprivileged transaction.
