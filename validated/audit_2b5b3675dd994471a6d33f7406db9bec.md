### Title
Sequencer's fee-transfer execution does not verify the ERC20 `transfer` boolean return value, allowing a non-reverting failed fee payment to be treated as successful - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo])

### Summary
Both the Starknet OS (Cairo) `charge_fee` function and the blockifier's `execute_fee_transfer` invoke the fee token's `transfer` entry point but only check that the call did not revert. Neither checks the entry point's returned `success` felt (the boolean return value that the ERC20 `transfer` convention specifies), which is the exact bug class described in the reference report (unchecked ERC20 `transfer` return value can silently fail).

### Finding Description
In the Starknet OS, `charge_fee` builds a `TransferCallData` and executes the fee token's `transfer` entry point via `non_reverting_select_execute_entry_point_func`, then returns immediately without inspecting `retdata`: [1](#0-0) 

Compare this to `run_validate`, in the same file's helper module, which explicitly checks the `retdata` for the expected value (`VALIDATED`) after calling the same non-reverting helper: [2](#0-1) 

The helper `non_reverting_select_execute_entry_point_func` only asserts that the call did not revert (`is_reverted = 0`); it returns `retdata` to the caller for the caller to validate, but `charge_fee` discards this value entirely: [3](#0-2) 

The same pattern exists in the Rust blockifier: `execute_fee_transfer` executes the `transfer` entry point and returns `Ok(CallInfo)` as soon as `.execute(...)` does not return an `Err`, without inspecting `call_info.execution.retdata` for the ERC20 boolean success flag: [4](#0-3) 

The ERC20 convention used by Starknet's own fee-token reference implementation returns a `(success: felt)` value rather than reverting on failure (e.g. insufficient balance triggers an `assert_not_zero` on `enough_balance`, which *does* revert for the reference implementation, but the interface contract explicitly returns a boolean and nothing in the OS/blockifier fee-charging code enforces that a class implementing a different, non-reverting failure convention must return `TRUE`): [5](#0-4) 

Because the network's fee token address is a governance/admin-controlled parameter (`starknet_os_config.fee_token_address` in the OS, `chain_info.fee_token_address` in blockifier) rather than a hardcoded, audited single implementation, any class deployed at that address that implements a "soft-fail" transfer (returns `success=FALSE` without reverting) would let every transaction that uses it pass fee charging while the balance is not actually deducted, since neither `charge_fee` (OS) nor `execute_fee_transfer` (blockifier) checks the return value.

### Impact Explanation
If the fee token's `transfer` implementation returns `FALSE` on failure instead of reverting (a legal ERC20-style implementation choice), the sequencer will:
- Record `fee_transfer_call_info` as if the fee was successfully charged.
- Commit a state diff and block in which the sender's balance was not actually decremented by the fee.
- Diverge from any honest node that independently re-executes the transaction with an ERC20 return-value check (or with a different token version), producing a state/commitment mismatch, or systematically allow fee-free transactions to be included, draining sequencer revenue and permanently misrepresenting the committed state (loss of funds for the network / incorrect state root).

This matches the class of unauthorized state mutation from an unchecked ERC20 return value described in the reference report, reachable purely through normal transaction execution paths (`charge_fee` runs for every fee-charging transaction).

### Likelihood Explanation
The `fee_token_address` is a configurable, chain-level parameter, not an immutable protocol constant enforced by code; the vulnerability triggers automatically on every transaction whenever the configured fee token deviates from the "always-revert-on-failure" convention assumed implicitly by this code. Since the check is entirely missing rather than being an edge case, likelihood is high once such a token is in use, though it is contingent on the specific ERC20 implementation deployed as the fee token (the reference implementation reverts, so exploitation requires a different/future fee-token class).

### Recommendation
- In `charge_fee` (Cairo OS), after calling `non_reverting_select_execute_entry_point_func` for the transfer, assert the returned `retdata` equals `1` (i.e., `felt(true)` / `FELT_TRUE`), mirroring the pattern already used in `run_validate` for the `VALIDATED` return value.
- In blockifier's `execute_fee_transfer` (and `concurrency_execute_fee_transfer`), after `fee_transfer_call.execute(...)` succeeds, inspect `call_info.execution.retdata` and reject/panic if it does not equal `[FELT_TRUE]`, ensuring consistent behavior between the OS and blockifier re-execution paths.

### Proof of Concept
Not applicable in the traditional sense (no external Solidity contract to exploit); the vulnerable code path is exercised on every fee-charging transaction:
1. Deploy/configure a fee-token class at `fee_token_address` whose `transfer` function returns `success = 0` (FALSE) when the sender's balance is insufficient, instead of reverting via `assert_not_zero`.
2. Submit any account transaction with `charge_fee = true` and a sender balance lower than the fee.
3. `charge_fee` (OS) / `execute_fee_transfer` (blockifier) invokes `transfer`, which returns without reverting and with `retdata = [0]`.
4. Because neither code path inspects `retdata`, the transaction is accepted as if the fee was paid, and the account's balance is not actually deducted, while the block is committed as valid — producing a state divergence from any node/verifier that enforces the ERC20 return-value check.

    fn execute_fee_transfer(
        state: &mut dyn State,
        tx_context: Arc<TransactionContext>,
        actual_fee: Fee,
    ) -> TransactionExecutionResult<CallInfo> {
        // The least significant 128 bits of the amount transferred.
        let lsb_amount = Felt::from(actual_fee.0);
        // The most significant 128 bits of the amount transferred.
        let msb_amount = Felt::ZERO;

        let TransactionContext { block_context, tx_info } = tx_context.as_ref();
        let storage_address = tx_context.fee_token_address();
        // The fee contains the cost of running this transfer, and the token contract is
        // well known to the sequencer, so there is no need to limit its run.
        let mut remaining_gas_for_fee_transfer =
            block_context.versioned_constants.os_constants.gas_costs.base.default_initial_gas_cost;
        let fee_transfer_call = CallEntryPoint {
            class_hash: None,
            code_address: None,
            entry_point_type: EntryPointType::External,
            entry_point_selector: selector_from_name(constants::TRANSFER_ENTRY_POINT_NAME),
            calldata: calldata![
                *block_context.block_info.sequencer_address.0.key(), // Recipient.
                lsb_amount,
                msb_amount
            ],
            storage_address,
            caller_address: tx_info.sender_address(),
            call_type: CallType::Call,

            initial_gas: remaining_gas_for_fee_transfer,
        };
        let mut context = EntryPointExecutionContext::new_invoke(
            tx_context,
            true,
            SierraGasRevertTracker::new(GasAmount(remaining_gas_for_fee_transfer)),
        );

        Ok(fee_transfer_call
            .execute(state, &mut context, &mut remaining_gas_for_fee_transfer)
            .map_err(|error| Box::new(TransactionFeeError::ExecuteFeeTransferError(error)))?)
    }

func ERC20_transfer{syscall_ptr: felt*, pedersen_ptr: HashBuiltin*, range_check_ptr}(
    sender: felt, recipient: felt, amount: Uint256
) {
    alloc_locals;
    assert_not_zero(sender);
    assert_not_zero(recipient);
    uint256_check(amount);  // Almost surely not needed, might remove after confirmation.

    let (local sender_balance: Uint256) = ERC20_balances.read(account=sender);

    // Validates amount <= sender_balance and returns 1 if true.
    let (enough_balance) = uint256_le(amount, sender_balance);
    assert_not_zero(enough_balance);

    // Subtract from sender.
    let (new_sender_balance: Uint256) = uint256_sub(sender_balance, amount);
    ERC20_balances.write(sender, new_sender_balance);

    // Add to recipient's balance.
    let (recipient_balance: Uint256) = ERC20_balances.read(account=recipient);
    // Overflow is not possible because sum is guaranteed by mint to be less than total supply.
    let (new_recipient_balance, _: Uint256) = uint256_add(recipient_balance, amount);
    ERC20_balances.write(recipient, new_recipient_balance);
    Transfer.emit(sender, recipient, amount);
    return ();
}
