### Title
Pre-fork `checkWeight` dedups by raw ECDSA signature encoding, allowing one signer's malleated duplicate signature to be double-counted toward multi-sig weight - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Finding Description
`TransactionCapsule.checkWeight` deduplicates signatures using a `HashMap addMap` whose key is computed from the raw signature bytes, not from the recovered signer address, unless the chain has passed the `VERSION_4_7_1` fork: [1](#0-0) 

Specifically, for each signature the code computes `base64 = TransactionCapsule.getBase64FromByteString(sig)`, which reconstructs `(r, s, v)` from the raw signature bytes and re-encodes it, without any canonicalization of `s`: [2](#0-1) 

Only if `ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)` is true does the code switch the dedup key to `encode58Check(address)` (the recovered signer address): [3](#0-2) 

ECDSA signatures are malleable: for any valid `(r, s, v)` there exists a second valid signature `(r, N-s, v')` (with `N` the curve order and `v'` flipped) that recovers to the *same* address/public key. Because `getBase64FromByteString` encodes the raw `(r, s, v)` triplet without normalizing `s` to the low-S canonical form, the two malleated variants produce different base64 strings and therefore different `addMap` keys pre-fork. Both variants pass the address/weight lookup (`SignUtils.signatureToAddress`) and are accepted as if they came from two different signers, each contributing the same key's `weight` to `currentWeight`. The `signatureToAddress` call successfully recovers the same address for both variants, but nothing in the pre-fork path checks that address for duplication - only in the post-fork path.

This lets a single private key satisfy a permission that nominally requires signatures from `N ≥ 2` distinct keys, because the attacker submits their own signature twice in malleated form, inflating `currentWeight` beyond what the true set of distinct signers supports.

### Impact Explanation
On any chain/test harness where `VERSION_4_7_1` has not yet passed (e.g., private/consortium chains, sidechains, freshly bootstrapped test networks, or the transitional window before the fork activates), an attacker holding only one key of a multi-sig permission (`Permission` on an account, used by `TransferContract`, TRC10 asset transfers, TRC20/smart-contract triggers via `TriggerSmartContract`, exchange operations, etc.) can submit a transaction with two malleated copies of their own signature and have `checkWeight` (called from `validateSignature`/`validatePubSignature`) count them as two independent signers. This bypasses the intended multi-signature threshold, allowing unauthorized execution/movement of value that should have required cooperation of multiple key holders.

### Likelihood Explanation
Feasibility is high but conditional: it requires the specific fork `VERSION_4_7_1` to not have passed on the target chain. The vulnerable code path is fully reachable via a standard, unprivileged transaction submission (`TransactionCapsule.sign` + manual signature-list manipulation, matching the exact attacker capability assumed by the audit scope), with no special privileges beyond controlling one signing key within the permission's key list. The exploit is deterministic and repeatable — ECDSA malleation is a well-known, mechanically simple transformation of `(r, s, v)`.

### Recommendation
Always canonicalize the recovered signer to an address-based dedup key regardless of fork status, or equivalently, canonicalize `s` to low-S form before deriving the `base64` key, so that malleated signature pairs collapse to the same map key pre-fork as well. The safest fix is to remove the fork-gated behavior and always key `addMap` by `encode58Check(address)`.

### Proof of Concept
```java
// Illustrative differential test (pseudo-Java) comparing pre- vs post-fork behavior
@Test
public void testMalleatedSignatureDoubleCounted() throws Exception {
  // permission with threshold requiring weight from at least 2 distinct signers
  Permission permission = buildTwoOfTwoPermission(keyA, keyB);
  TransactionCapsule tx = buildSampleTransferTransaction();
  tx.sign(keyA.getPrivateKeyBytes());

  ByteString originalSig = tx.getInstance().getSignature(0);
  ByteString malleatedSig = malleate(originalSig); // (r, N-s, v') derived from same key A

  List<ByteString> sigs = new ArrayList<>();
  sigs.add(originalSig);
  sigs.add(malleatedSig);

  byte[] hash = tx.getTransactionId().getBytes();

  // Simulate fork NOT passed
  ForkUtils.disable(Parameter.ForkBlockVersionEnum.VERSION_4_7_1);
  long weightPreFork = TransactionCapsule.checkWeight(permission, sigs, hash, null);
  // BUG: weightPreFork == weight(A) + weight(A) >= threshold, even though B never signed
  assertTrue(weightPreFork >= permission.getThreshold());

  // Simulate fork passed
  ForkUtils.enable(Parameter.ForkBlockVersionEnum.VERSION_4_7_1);
  PermissionException ex = assertThrows(PermissionException.class,
      () -> TransactionCapsule.checkWeight(permission, sigs, hash, null));
  assertTrue(ex.getMessage().contains("has signed twice"));
}
```
Expected result: pre-fork run allows `currentWeight` to exceed the sum of genuinely distinct signer weights (single key counted twice), while post-fork run correctly throws `PermissionException` for the duplicate signer — confirming the dedup-by-raw-signature flaw is fork-gated and exploitable whenever `VERSION_4_7_1` has not activated.
