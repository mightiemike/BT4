## Title
Alias-Contract Key-Space Collision Between Contract Addresses and Storage Keys Causes State-Diff Corruption in Stateful Compression - ([File: crates/blockifier/src/state/stateful_compression.rs])

### Summary
The Passport advisory root cause is that a single `sub` claim value is used to look up two logically distinct entity types (OAuth clients and users) that share the same integer ID space, so a value legitimately belonging to one entity type resolves to the other. The sequencer's stateful-compression ("state aliasing") feature has the same class of bug: contract addresses and per-contract storage keys are aliased through **one shared key space** in the alias contract's storage, keyed only by a raw felt (`AliasKey = StorageKey`), with no tag distinguishing "this felt is a contract address" from "this felt is a storage key of some contract." An attacker who fully controls the storage keys they write in their own contract can pick a storage key equal to an already-aliased contract address, causing the two logically distinct identifiers to collide and share a single alias entry.

### Finding Description
`allocate_aliases_in_storage` (crates/blockifier/src/state/stateful_compression.rs) iterates over `contract_addresses` and `storage_keys` extracted from the state diff and inserts an alias for each felt key into one common map keyed only by `AliasKey`: [1](#0-0) 

Both contract addresses and storage keys are collapsed to the same `AliasKey`/`StorageKey` type with no discriminator of origin: [2](#0-1) [3](#0-2) 

`insert_alias` checks whether an alias already exists for a given felt key and, if so, silently reuses it rather than allocating a fresh alias: [4](#0-3) 

Because a contract's storage key is a value the contract (hence, indirectly, the transaction sender/deployer) can pick arbitrarily (e.g. via a `Store` in Cairo pointing at any felt), an attacker can choose a storage key equal to the numeric value of an existing/target contract address that has already been (or will be) allocated an alias in the same or an earlier block. When `compress`/`AliasCompressor` later replaces the storage key and the contract address with "their" aliases, both the address and the unrelated storage key are represented by the *same* alias value: [5](#0-4) 

On decompression, `AliasDecompressorUtil` builds a single `reversed_alias_mapping: HashMap<Alias, AliasKey>` from the alias value back to whichever original key (address- or storage-key- typed) was last inserted for that alias, then uses this same map indiscriminately to reconstruct both contract addresses (`decompress_address`) and storage keys (`decompress_storage_key`): [6](#0-5) 

Since the mapping is keyed only by the alias value and not by the semantic type of the original key, a collision (attacker-chosen storage key == existing contract address) causes `restore_alias_key` to return the wrong original identifier for one of the two contexts, corrupting the decompressed state diff: a `nonce`/`class_hash` update meant for contract A can be reconstructed as though it targets a completely different address (the colliding storage-key value from contract B), or vice versa.

### Impact Explanation
This is a state/root-integrity bug, not merely a resource issue: the alias-based compression scheme is used by the Starknet OS as part of computing/verifying the committed state diff on L1 (data-availability). A collision between the contract-address alias namespace and the storage-key alias namespace can cause the reconstructed (decompressed) state diff to attribute a nonce/class-hash change to the wrong contract address, or a storage write to the wrong (contract, key) pair. This can lead to:
- Wrong committed state diff / state root being derived from stateful compression, or
- Divergence between the value written on-chain by the compressed representation and the value the OS/verifier reconstructs, undermining the integrity of the DA/committed data for the affected contracts.

This matches the "wrong committed root" / state-corruption category called out as an acceptable impact class.

### Likelihood Explanation
Exploitability requires:
1. Attacker deploys or controls a contract and writes to an arbitrary storage slot of their choosing (`sstore`), which is entirely permitted — storage keys are attacker-chosen felts.
2. The chosen storage-key felt equals the felt value of some existing contract address on-chain (addresses of well-known contracts are public knowledge, e.g. token contracts, the account's own address, or an address the attacker will also touch in the same state diff/block so it gets an alias in the same commitment window).
3. Both keys must be present in the modified-keys set that gets compressed within the same alias contract state (no cryptographic pre-image work is needed — the attacker simply reuses a known public felt value as their own storage key).

This does not require a hash collision or heavy computation; only knowledge of the target address's felt value, which is public. This is reachable purely from a single unprivileged transaction sender picking calldata/storage writes, satisfying the "single submitted transaction" reachability requirement. Because of this, likelihood is Medium-to-High given the modest prerequisites (only requires the compression feature to be active/enabled with an alias contract for those addresses ≥ `MIN_VALUE_FOR_ALIAS_ALLOC`).

### Recommendation
Separate the alias key spaces for contract addresses and storage keys (e.g. tag the `AliasKey` with its origin, or use disjoint storage regions/prefixes in the alias contract for "address aliases" vs "storage-key aliases" per contract), so a numeric collision between an address and an unrelated storage key can never cause alias reuse across the two domains. Additionally, harden `AliasDecompressorUtil`'s `reversed_alias_mapping` to detect and reject ambiguous alias reuse (i.e., the same alias value mapping to two different `AliasKey`s of different semantic types) rather than silently overwriting.

### Proof of Concept
1. Deploy contract `T` at some address that will be included in a state diff (e.g., `T` performs a self-write, guaranteeing its address gets an alias allocated once its address value passes `MIN_VALUE_FOR_ALIAS_ALLOC`, i.e., `>= 0x80`).
2. In the same or a later block, from contract `T` (or any attacker-controlled contract), issue a storage write via `Store` where the storage key felt equals the numeric felt value of `T`'s (or another target contract's) address.
3. Trigger `allocate_aliases_in_storage`/`compress` over a state diff containing both: (a) `T`'s address-keyed nonce/class-hash update, and (b) the attacker's storage write whose key equals `T`'s address.
4. Because `insert_alias` treats identical felt values as "already aliased," both are assigned the same alias entry in the alias contract storage.
5. Run `decompress` (as in `crates/blockifier/src/state/stateful_compression_test_utils.rs`) and observe that `AliasDecompressorUtil::restore_alias_key` returns an incorrect original key for one of the two entries (address vs storage key), reconstructing state changes against the wrong logical target — demonstrating cross-domain identifier confusion analogous to the Passport `sub`-claim collision.

Note: I was not able to execute this scenario end-to-end (no test harness run), so this analysis is based on static code review of `stateful_compression.rs`/`stateful_compression_test_utils.rs`; a Devin session with repo access would be needed to build and run a concrete reproduction test to confirm the exact failure mode (silent misattribution vs. a panic/`unwrap` on ambiguous mapping).

pub fn allocate_aliases_in_storage<S: StateReader>(
    state: &mut CachedState<S>,
    alias_contract_address: ContractAddress,
) -> StateResult<()> {
    let state_diff = state.to_state_diff()?.state_maps;

    // Collect the contract addresses and the storage keys that need aliases.
    let contract_addresses: BTreeSet<ContractAddress> =
        state_diff.get_contract_addresses().into_iter().collect();
    let mut contract_address_to_sorted_storage_keys = HashMap::new();
    for (contract_address, storage_key) in state_diff.storage.keys() {
        if contract_address > &MAX_NON_COMPRESSED_CONTRACT_ADDRESS {
            contract_address_to_sorted_storage_keys
                .entry(contract_address)
                .or_insert_with(BTreeSet::new)
                .insert(storage_key);
        }
    }

    // Iterate over the addresses and the storage keys and update the aliases.
    let mut alias_updater = AliasUpdater::new(state, alias_contract_address)?;
    for contract_address in contract_addresses {
        if let Some(storage_keys) = contract_address_to_sorted_storage_keys.get(&contract_address) {
            for key in storage_keys {
                alias_updater.insert_alias(key)?;
            }
        }
        alias_updater.insert_alias(&StorageKey(contract_address.0))?;
    }

    alias_updater.finalize_updates()
}

impl<S: StateReader> AliasCompressor<'_, S> {
    fn compress_address(
        &self,
        contract_address: &ContractAddress,
    ) -> CompressionResult<ContractAddress> {
        if should_compress_address(contract_address) {
            Ok(self.get_alias(StorageKey(contract_address.0))?.try_into()?)
        } else {
            Ok(*contract_address)
        }
    }

    fn compress_storage_key(
        &self,
        storage_key: &StorageKey,
        contract_address: &ContractAddress,
    ) -> CompressionResult<StorageKey> {
        if should_compress_storage_key(storage_key, contract_address) {
            Ok(self.get_alias(*storage_key)?.try_into()?)
        } else {
            Ok(*storage_key)
        }
    }

    fn get_alias(&self, alias_key: AliasKey) -> CompressionResult<Alias> {
        let alias = self.state.get_storage_at(self.alias_contract_address, alias_key)?;
        if alias == Felt::ZERO { Err(CompressionError::MissedAlias(alias_key)) } else { Ok(alias) }
    }
}

/// Replaces aliases with the original contact addresses and storage keys.
pub(crate) struct AliasDecompressorUtil {
    reversed_alias_mapping: HashMap<Alias, AliasKey>,
}

impl AliasDecompressorUtil {
    fn new<S: StateReader>(
        state: &S,
        alias_contract_address: ContractAddress,
        alias_keys: HashSet<AliasKey>,
    ) -> Self {
        let mut reversed_alias_mapping = HashMap::new();
        for alias_key in alias_keys.into_iter() {
            reversed_alias_mapping.insert(
                state.get_storage_at(alias_contract_address, alias_key).unwrap(),
                alias_key,
            );
        }
        Self { reversed_alias_mapping }
    }

    fn decompress_address(&self, contract_address_alias: &ContractAddress) -> ContractAddress {
        if contract_address_alias.0 >= MIN_VALUE_FOR_ALIAS_ALLOC {
            ContractAddress::try_from(
                *self.restore_alias_key(Felt::from(*contract_address_alias)).key(),
            )
            .unwrap()
        } else {
            *contract_address_alias
        }
    }

    fn decompress_storage_key(
        &self,
        storage_key_alias: &StorageKey,
        contact_address: &ContractAddress,
    ) -> StorageKey {
        if storage_key_alias.0 >= MIN_VALUE_FOR_ALIAS_ALLOC
            && contact_address > &MAX_NON_COMPRESSED_CONTRACT_ADDRESS
        {
            self.restore_alias_key(*storage_key_alias.0)
        } else {
            *storage_key_alias
        }
    }

    fn restore_alias_key(&self, alias: Alias) -> AliasKey {
        *self.reversed_alias_mapping.get(&alias).unwrap()
    }
