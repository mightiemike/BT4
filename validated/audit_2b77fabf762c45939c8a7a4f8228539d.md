### Title
Exchange liquidity injection lacks minimum/maximum bound checks, exposing users to unbounded slippage from ratio front-running - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` lets a user add liquidity to a TRC10 bancor-style exchange pair by specifying only one token and its amount (`token_id`, `quant`). The actuator then computes the counterpart token amount (`anotherTokenQuant`) required from the current on-chain pool ratio at execution time, and unconditionally deducts it from the user's balance. There is no user-supplied bound (min/max) on `anotherTokenQuant`, so if the pool ratio changes between transaction signing and execution, the user can be forced to pay a very different (larger) amount of the second token than they intended — the exact bug class described in the LPIssuer.deposit report (deposit amount computed against a "balanced ratio" that can be shifted by another actor before inclusion).

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant`: [1](#0-0)  — actually see the message definition in the protocol doc: [2](#0-1) 

Unlike `ExchangeTransactionContract`, which has an explicit `expected` field used to bound the received amount (`token required must greater than expected`): [3](#0-2) 

`ExchangeInjectContract` has no analogous field to bound `anotherTokenQuant`. In `doValidate()`, the counterpart amount is derived purely from the exchange's current on-chain balances at validation/execution time: [4](#0-3) 

and then unconditionally charged to the user in `execute()`: [5](#0-4) 

Because `firstTokenBalance`/`secondTokenBalance` (the pool ratio) can be changed by any other broadcast transaction that executes first in the same block window — an `ExchangeTransactionContract` (a trade), another `ExchangeInjectContract`, or an `ExchangeWithdrawContract` — a user's signed `ExchangeInjectContract` with a fixed `quant` for one token will be re-priced against the new ratio at execution time. This mirrors the reported `LPIssuer.deposit` issue: the user assumes a certain "balanced" price ratio when signing, but a frontrunning/interleaved transaction shifts the ratio, and the contract has no parameter to reject execution if the recomputed `anotherTokenQuant` deviates from what the user expected.

### Impact Explanation
A user submitting `ExchangeInjectContract` can have significantly more or less of the second token consumed than they expected, purely as a function of transaction ordering within the mempool/block. This can be exploited (accidentally by concurrent activity, or deliberately by an attacker submitting an interleaving trade/inject/withdraw) to force a victim's injection to consume an unintended and unbounded amount of their second token balance, or to leave them with a materially worse liquidity position than they signed up for. This is an accounting/economic-correctness issue reachable directly from a normal broadcast transaction — no privileged role is required to trigger it.

### Likelihood Explanation
Ordinary transaction ordering nondeterminism (or a deliberate front-running trade against the same exchange pair) is sufficient to trigger the mispricing; no special access is needed. The `ExchangeTransactionActuator` was clearly designed with this risk in mind (it has an `expected` slippage-bound field), but the same protection was not extended to `ExchangeInjectActuator` (or `ExchangeWithdrawActuator`), making this a straightforward, reachable, unprivileged path.

### Recommendation
Add an optional `expected`/bound field to `ExchangeInjectContract` (analogous to `ExchangeTransactionContract.expected`), and in `ExchangeInjectActuator.doValidate()`/`execute()` reject the transaction if the recomputed `anotherTokenQuant` exceeds the user-specified maximum (or falls outside an acceptable range), rather than always deducting whatever amount is currently implied by the pool ratio. The same slippage-bound protection should be reviewed for `ExchangeWithdrawActuator`.

### Proof of Concept
1. Exchange pool has balances `firstToken=1000`, `secondToken=1000` (1:1 ratio).
2. User signs `ExchangeInjectContract{token_id=first, quant=100}` expecting to also pay ~100 of `secondToken` (per `anotherTokenQuant = secondBalance*quant/firstBalance`, computed in `ExchangeInjectActuator.doValidate()` at lines 215-227 [6](#0-5) ).
3. Before the user's transaction executes, another transaction (e.g., an `ExchangeTransactionContract` trade) shifts the pool to `firstToken=1000`, `secondToken=4000`.
4. The user's `ExchangeInjectContract` now executes and computes `anotherTokenQuant = 4000*100/1000 = 400`, silently deducting 400 `secondToken` from the user instead of the ~100 they expected, with no check to prevent or bound this — matching the "balanced amounts" mispricing described in the original report.
