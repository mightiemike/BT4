### Title
Deposit mempool unconditionally purges deposits after block production regardless of on-chain execution success, letting an eth_call-time-vs-execution-time state divergence silently and permanently drop a valid Bitcoin deposit's cBTC credit - (File: crates/sequencer/src/runner.rs)

### Summary
`DepositDataMempool::make_deposit_tx_from_data` builds the exact same `from: SYSTEM_SIGNER` / `to: BridgeWrapper::address()` / `input: BridgeWrapper::deposit(...)` call that `signed_system_transaction`/`system_event_to_transaction` later construct for `SystemEvent::BridgeDeposit`, but the admission `eth_call` is evaluated at `BlockId::pending()`, i.e. against the state committed as of RPC-submission time, while the actual system transaction executes only later, whenever the deposit is dequeued FIFO from the mempool. State can and does diverge in that window through ordinary L2 transactions. When the real execution reverts (`EvmSystemTransactionNotSuccessful`), `CitreaSequencer::process_sys_txs` correctly skips it inside the block, but `produce_block` in `crates/sequencer/src/runner.rs` still calls `remove_deposits(&deposit_data)` with the full pre-fetch list rather than only the deposits that were actually included, permanently purging the reverted deposit from `pending_deposits`/`accepted_deposit_txs` with no automatic retry.

### Finding Description
Binding: cBTC credited by a SYSTEM_SIGNER Bridge deposit == exactly one Bitcoin move-to-vault output Clementine actually presigned, counted once.

- `DepositDataMempool::make_deposit_tx_from_data` builds `TransactionRequest{ from: Some(SYSTEM_SIGNER), to: BridgeWrapper::address(), input: BridgeWrapper::deposit(deposit_tx_data), gas: SYSTEM_TX_GAS_LIMIT }`. [1](#0-0) 
- `system_event_to_transaction`/`signed_system_transaction` build the functionally equivalent real transaction for `SystemEvent::BridgeDeposit`: same `to`, same `input`, `value: ZERO`, `gas_limit: SYSTEM_TX_GAS_LIMIT`, signed as `SYSTEM_SIGNER`. [2](#0-1) 
- The admission gate `send_raw_deposit_transaction` executes the request via `evm.get_call(dep_tx, Some(BlockId::pending()), ...)`. [3](#0-2) 
- `get_call_inner`'s `BlockId::pending()` path resolves to `get_pending_block_env`, which reads from the working set built on `self.context.storage.clone()` — i.e. the state committed as of the *last finalized* L2 block at RPC time, not the state that will exist when the deposit is actually dequeued and processed. [4](#0-3) [5](#0-4) 
- Deposits sit in a FIFO queue (`fetch_deposits` does not remove) until dequeued by the block builder, so many L2 blocks (and arbitrary attacker transactions) can execute between admission-time simulation and real inclusion. [6](#0-5) 
- At real inclusion, `process_sys_txs` executes the deposit as a genuine SYSTEM_SIGNER tx; on `EvmSystemTransactionNotSuccessful` it reverts the checkpoint and `continue`s, silently omitting it from `all_txs` (the actually-included system transactions) without surfacing a per-deposit failure list to the caller. [7](#0-6) 
- Critically, the caller in `produce_block` fetches `deposit_data` once, up front, and later calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using that *same original full list*, not `all_txs`/only the subset that was actually applied successfully. [8](#0-7) [9](#0-8) 
- `remove_deposits` deletes the entry from both `pending_deposits` and `accepted_deposit_txs`, so a reverted deposit is gone from the mempool with no automatic re-queue. [10](#0-9) 

Exploit flow: an attacker deploys a helper contract L on L2 whose storage/existence gates the recipient-contract logic invoked by `Bridge.deposit`'s `recipient.call{value:...}("")`. They submit a real (Clementine-presigned) deposit blob for their own BTC deposit whose recipient depends on L's current state such that the call succeeds. They call `citrea_sendRawDepositTransaction`; the sequencer's `eth_call` at `BlockId::pending()` succeeds against the state committed at that instant, so the deposit is admitted to `accepted_deposit_txs`. Before the deposit is dequeued (it can sit behind other deposits/blocks due to FIFO ordering and `deposit_mempool_fetch_limit`), the attacker sends an ordinary L2 transaction that flips L's state (e.g. self-destructs L or toggles a storage slot). When the sequencer eventually dequeues and executes the deposit as a real `SYSTEM_SIGNER` transaction, the same call now reverts, `process_sys_txs` drops it from `all_txs`, and `produce_block` still purges it from the deposit mempool via the unfiltered `deposit_data` list. The Bitcoin-side move-to-vault output (already presigned/executed by Clementine, off-chain and irreversible) now has no corresponding cBTC credit, and the mempool no longer tracks the deposit for retry.

### Impact Explanation
The affected deposit's cBTC is never minted even though the corresponding Bitcoin move-to-vault output was already presigned/spent by Clementine, breaking the 1:1 binding and effectively freezing that BTC value on L2 until someone manually resubmits the identical deposit blob via `citrea_sendRawDepositTransaction` (which itself is again subject to the same simulate/execute divergence if the underlying state dependency persists). This is repeatable per-deposit and does not require sequencer, Clementine, or any privileged key — only the ability to deploy a contract and send ordinary transactions. Blast radius is limited to deposits whose recipient logic is state-dependent (most directly, deposits where the attacker is depositor and controls the recipient contract, i.e. primarily self-inflicted unless a victim uses a shared/state-dependent recipient contract).

### Likelihood Explanation
No privileged access is required: any unprivileged actor can call `citrea_sendRawDepositTransaction`, deploy an L2 contract, and send ordinary transactions, and needs only Bitcoin fees to fund the underlying deposit (or none if they simply grief their own already-presigned deposit to prove the divergence). The condition is deterministic and fully attacker-controlled (self-destruct or storage flip timed against block production interval), so it is reliably reproducible in a `cargo test`/local devnet setting without requiring mainnet or a live Clementine instance.

### Recommendation
Track per-deposit success/failure explicitly in `process_sys_txs`/`produce_and_run_system_transactions` and return only the successfully-included deposits to `produce_block`; call `remove_deposits` with that successful subset only, leaving reverted deposits in the mempool for automatic retry (with a bound retry count/backoff to avoid unbounded head-of-line blocking). Additionally, consider re-validating deposits against the actual prestate immediately before inclusion (or invalidating/expiring deposits whose `eth_call` simulation result becomes stale) rather than relying solely on the admission-time simulation.

Plan:
1. Deploy a helper contract `Toggle` with a public bool flag, and a recipient contract `Vault` whose `receive()`/fallback reverts iff `Toggle.flag() == false` (or succeeds only while `Toggle` has code, reverting after `selfdestruct`).
2. Set `Toggle.flag = true`; construct a Clementine-shaped deposit blob (`BridgeContract::depositCall`) whose recipient is `Vault`.
3. Call `citrea_sendRawDepositTransaction` and assert it returns `Ok(())`, confirming `evm.get_call(..., BlockId::pending())` succeeded (simulate-time result: success) — assert via direct call to `DepositDataMempool::make_deposit_tx_from_data` + `Evm::get_call_inner` at `BlockId::pending()`.
4. Before the sequencer dequeues the deposit (hold it behind other deposits or delay block production), send an ordinary tx that sets `Toggle.flag = false` (or self-destructs `Toggle`).
5. Let the sequencer build the L2 block containing the deposit; assert the `process_sys_txs` path returns/logs `EvmSystemTransactionNotSuccessful` for the `BridgeDeposit` event (execute-time result: revert).
6. Assert `DepositDataMempool` no longer contains the deposit (`pending_deposits`/`accepted_deposit_txs` both empty for that txid) after block production, proving simulate-time result (`Ok`) != execute-time result (`Err`) and that the deposit was dropped from consideration without being credited.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
