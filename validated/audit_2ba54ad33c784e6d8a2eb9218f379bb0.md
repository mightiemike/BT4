### Title
Account resources returned in JSON via `GET /accounts/{address}/resources` are decoded using the **latest** on-chain type layout instead of the layout at the requested historical `ledger_version` - ([File: api/src/accounts.rs])

### Summary
The `resources()` handler for the account-resources API fetches raw resource bytes at the caller-specified historical `ledger_version`, but when serializing them to JSON it builds its BCS-to-JSON converter from the **latest** state view rather than the state view at that same version.

### Finding Description
In `Account::resources` [1](#0-0) , the raw resource bytes are fetched with `self.ledger_version` via `get_resources_by_pagination`, but for the JSON path the converter used to decode them is built from `self.context.latest_state_view_poem(&self.latest_ledger_info)`, i.e. the current/latest ledger state, not `self.ledger_version`. This is visible directly in the code:
```
let (resources, next_state_key) = self.context.get_resources_by_pagination(
    self.address.into(), self.start.as_ref(), self.ledger_version, ...
)?;
...
AcceptType::Json => {
    let state_view = self.context.latest_state_view_poem(&self.latest_ledger_info)?;
    let converter = state_view.as_converter(...);
    let converted_resources = converter.try_into_resources(...)?;
```
Compare this with the single-resource path `Account::find_resource`, which correctly reuses the *same* versioned `state_view` obtained via `self.context.state_view(Some(self.ledger_version))` for both fetch and conversion [2](#0-1) . This asymmetry is the root cause: `resources()` decodes historical-version bytes with the type layout resolver bound to the current/latest version, not the requested one.

This is the exact scenario the code elsewhere explicitly warns about — a TODO in the transaction-info converter states plainly: "the resource value is interpreted by the type definition at the version of the converter, not the version of the tx: must be fixed before we allow module updates" [3](#0-2) . `Account::resources()` hits this same class of bug directly on a production, non-experimental, widely-used endpoint.

### Impact Explanation
If a Move module governing a resource's struct layout is upgraded on-chain (field added/removed/reordered, or type changed) between the requested historical `ledger_version` and the current chain tip, `GET /accounts/{address}/resources?ledger_version=<old>` will decode the old, on-disk BCS bytes using the new layout. This is exactly the "Authenticated API or state-view output bound to the wrong version, object, or proof context" impact called out in the task: the response is served under `ledger_info`/`X-APTOS-LEDGER-VERSION` headers claiming version `V`, but the resource contents are actually decoded with the schema live at the head of the chain, not `V`. Depending on the layout diff, this manifests as garbled field values, silently wrong values (fields shifted to the wrong name/type), or a decode failure returned as an internal error for what should be a valid historical query. Any indexer, wallet, or auditor relying on this endpoint for historical/point-in-time resource state gets state bound to the wrong version — i.e., authenticated data that does not correspond to the version it is labeled with.

### Likelihood Explanation
Every time a resource's struct layout changes on mainnet (a routine, expected occurrence for account/framework and app-level structs) and a client queries `resources()` for a historical `ledger_version` before that change, this bug is triggered deterministically with no privileged access needed — any unauthenticated API caller supplying a `ledger_version` query parameter can hit it.

### Recommendation
In `Account::resources()`, build the converter for the JSON branch from the same versioned state view used to fetch the resources (i.e. `self.context.state_view(Some(self.ledger_version))` / the `state_view` at `self.ledger_version`), matching the pattern already used correctly in `Account::find_resource` and `StateApi::resource`, rather than calling `latest_state_view_poem`.

### Proof of Concept
1. At version `V1`, resource `0x1::foo::Bar` has layout `{a: u64}`.
2. Upgrade the module so at version `V2` (`V2 > V1`) `Bar` becomes `{a: u64, b: u64}` (or a field type change), and let the chain progress past `V2`.
3. Call `GET /accounts/{addr}/resources?ledger_version=V1` with `Accept: application/json`.
4. `get_resources_by_pagination` returns the raw BCS bytes for `Bar` as they existed at `V1` (`{a: u64}`), but `try_into_resources` is invoked against `latest_state_view_poem`, which resolves `Bar`'s type layout as `{a: u64, b: u64}` (the current one). The BCS bytes are the wrong length/shape for the layout being used to decode them, producing either a decode error (masking a query that should have succeeded) or, in cases where sizes coincidentally align, misinterpreted field values — while the API response still reports `ledger_version: V1` in its headers/body.

**Note on certainty:** I was unable to fully trace `get_resources_by_pagination` in `api/src/context.rs` (its body wasn't returned before tool access ended) to double-check the exact key set it reads at `self.ledger_version`, and I could not confirm the `Account::new`/struct-field wiring of `latest_ledger_info` vs `ledger_version`. The core asymmetry (fetch-at-version vs. convert-at-latest) is directly visible in the cited code and is the same bug class already flagged as a known limitation elsewhere in the codebase, but a background agent should re-verify `get_resources_by_pagination`'s version handling before treating this as fully confirmed.
