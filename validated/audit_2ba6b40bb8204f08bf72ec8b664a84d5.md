### Title
CRLF/control-character injection bypasses `sanitizeHost` domain allow-list because it validates a URL-normalized value while `decodeHost`/`buildEmbeddedAppUrl` use the raw, unstripped decoded string - (File: `packages/apps/shopify-api/lib/auth/decode-host.ts`, `packages/apps/shopify-api/lib/utils/shop-validator.ts`, `packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts`)

### Summary
`decodeHost` performs no validation at all - it is a one-line `atob(host)` passthrough. All validation is delegated to `sanitizeHost`, but that function checks the `hostname` produced by `new URL('https://' + decodeHost(host))`, which per the WHATWG URL spec silently strips embedded ASCII tab/CR/LF characters before parsing. `buildEmbeddedAppUrl` then calls `decodeHost(host)` again independently and concatenates the **raw, unstripped** decoded string directly into the redirect URL via template literal, so the value that was validated and the value that is actually used diverge.

### Finding Description
- `decodeHost` in `packages/apps/shopify-api/lib/auth/decode-host.ts` is: `return atob(host);` - no character filtering, no host-format checking. [1](#0-0) 
- `sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` only enforces that the *encoded* `host` string matches a base64-character regex (`^[0-9a-zA-Z+/]+={0,2}$`), which restricts the wire-format characters but not the decoded bytes; base64 can decode to arbitrary bytes, including `\r`, `\n`, and other control characters. [2](#0-1) 
- The allow-list check itself operates on `new URL('https://' + decodeHost(sanitizedHost)).hostname`, then tests `hostRegex = /\.(myshopify\.com|...)$/` against that hostname. [3](#0-2) 
- Because the WHATWG URL parser strips embedded ASCII tab/CR/LF from the input string during parsing, an attacker can craft a decoded payload containing `\r\n` such that after stripping, the resulting hostname legitimately ends in `.myshopify.com` (satisfying `hostRegex`), while the **raw** decoded string (with `\r\n` intact) still contains the literal control bytes.
- `buildEmbeddedAppUrl` in `packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts` calls `sanitizeHost(config)(host, true)` for validation, then **separately** calls `decodeHost(host)` again and builds the final URL by string concatenation: `` `https://${decodedHost}/apps/${config.apiKey}` ``, without ever re-running it through `URL` normalization. [4](#0-3) 
- This means the string returned to callers (used by consumers such as `redirect-to-shopify-or-app-root` middlewares across `shopify-app-express`/`shopify-app-remix`/`shopify-app-react-router`) can contain raw, unescaped `\r\n` bytes even though it passed the "only `*.myshopify.com`" invariant check.

### Impact Explanation
The validation-vs-usage mismatch is a genuine bug: the check that is supposed to enforce "the destination host must be `*.myshopify.com`" is performed on a normalized/stripped copy of the value, not on the value that is actually returned and used to build a redirect URL. If a downstream consumer places this URL into a `Location` header or otherwise treats it as a trusted, pre-vetted string without its own CRLF filtering, this enables HTTP response splitting / header injection in an authentication-adjacent code path (`buildEmbeddedAppUrl`/`getEmbeddedAppUrl`, used by embedded-app redirect helpers), which can be leveraged for injected headers/cookies or reflected content in the response, aiding phishing of session tokens as described in the question.

However, the concrete "attacker redirects to an arbitrary non-myshopify domain" version of the classic open-redirect is **not** achieved here, because the `hostRegex` suffix check still requires a literal `.myshopify.com` (or other allow-listed domain) substring to survive stripping - the attacker cannot make the check pass while pointing the eventual hostname at a fully attacker-controlled domain. The realistic, demonstrable impact is limited to injecting raw CR/LF bytes into the returned URL string despite the domain suffix check passing, i.e. a validate/use mismatch and potential header-splitting primitive, not an unrestricted open redirect to attacker infrastructure. Modern Node.js `http` (`setHeader`/`res.redirect`) additionally rejects header values containing `\r`/`\n` at the runtime level (`ERR_INVALID_CHAR`), which would block the response-splitting outcome in many deployments - I could not find a sink in this repo (e.g. the actual `res.redirect`/`Location` header write in `shopify-app-express`'s `redirect-to-shopify-or-app-root.ts`) that was directly inspected to confirm whether it re-validates the string before writing it as a header, so the end-to-end exploitability to a real header-splitting/XSS outcome in a specific adapter is not fully confirmed from the code paths I was able to review.

### Likelihood Explanation
Fully reachable by an unprivileged, unauthenticated attacker: `host` is an attacker-supplied query parameter with no signature or secret involved, and both `sanitizeHost` and `buildEmbeddedAppUrl`/`getEmbeddedAppUrl` are directly reachable via `shopify.auth.getEmbeddedAppUrl` and equivalent middleware in the app packages. Crafting a base64 string that decodes to bytes containing `\r`/`\n` while its URL-stripped form still ends in `.myshopify.com` is a straightforward, repeatable base64-encoding exercise (fast validation via a Jest test).

### Recommendation
- Make `sanitizeHost`/`decodeHost` reject decoded strings containing any control characters (`\r`, `\n`, `\t`, NUL, etc.) before any further use, rather than relying on `new URL()` for validation.
- Validate the *same* string that will actually be used downstream - i.e., have `buildEmbeddedAppUrl` reuse the exact validated/normalized host value from `sanitizeHost` rather than independently calling `decodeHost` again and using the raw un-normalized result.
- Encode/normalize the final URL using the `URL` API (`new URL(...)`) end-to-end (including when building `buildEmbeddedAppUrl`'s return value), instead of manual template-string concatenation, so any residual control characters are stripped consistently in both the check and the used value.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.crlf.test.ts
import {testConfig} from '../../__tests__/test-config';
import {sanitizeHost} from '../shop-validator';
import {decodeHost} from '../../auth/decode-host';

test('sanitizeHost passes while decodeHost still contains raw CRLF', () => {
  const config = testConfig();

  // Craft a decoded payload with embedded CR LF that, once stripped by
  // the WHATWG URL parser, still ends in an allow-listed suffix.
  const rawDecoded = 'evil-injected\r\nX-Injected-Header: pwn\r\n.myshopify.com/admin';
  const base64Host = Buffer.from(rawDecoded, 'utf-8').toString('base64');

  // Passes the base64 charset AND the .myshopify.com suffix check.
  const sanitized = sanitizeHost(config)(base64Host, false);
  expect(sanitized).not.toBeNull();

  // But the raw value that would actually be used to build the redirect
  // URL (via buildEmbeddedAppUrl) still contains raw CR/LF bytes.
  const decoded = decodeHost(sanitized as string);
  expect(decoded).toContain('\r\n');
});
```
Expected result: `sanitized` is non-null (i.e., `sanitizeHost` reports the host as valid/allow-listed), yet `decoded` still contains literal `\r\n` bytes - demonstrating that the "only `*.myshopify.com`" invariant, as enforced today, does not guarantee the absence of CRLF/control characters in the value that `buildEmbeddedAppUrl` subsequently uses to construct the redirect URL.

  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;

    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);

        'myshopify\\.com',
        'shopify\\.com',
        'myshopify\\.io',
        'spin\\.dev',
        'shop\\.dev',
      ];

        const hostTransformationDomains = config.domainTransformations
          .filter((t) => t.includeHost !== false)

              domainTransformations: [t],
            }),
          );

export function buildEmbeddedAppUrl(
  config: ConfigInterface,
): BuildEmbeddedAppUrl {
  return (host: string): string => {
    sanitizeHost(config)(host, true);
    const decodedHost = decodeHost(host);

    return `https://${decodedHost}/apps/${config.apiKey}`;
  };
