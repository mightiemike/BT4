### Title
Unbounded active-ballot scan on every `CreateBallot` call enables a growth-based gas/DoS analog to the collateral-array unbounded-loop bug - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
The Sherlock report describes a class of bug where an attacker-controllable, unbounded collection is iterated in a loop on a critical user-facing path, eventually causing transactions that touch that loop to fail once the collection grows large enough to exceed the gas/processing budget. The candidate Push Chain analog is `CreateBallot`, which unconditionally calls `ExpireBallotsBeforeHeight` on every invocation, and that function iterates the *entire* `ActiveBallotIDs` collection shared across all ballot types (inbound, outbound, TSS, migration) before creating the new ballot. [1](#0-0) [2](#0-1) 

### Finding Description
`CreateBallot` runs `ExpireBallotsBeforeHeight(ctx, blockHeight)` before storing any new ballot, and that function does a full `Iterate` over `ActiveBallotIDs`, fetching each ballot from the `Ballots` collection to check its expiry height. This is O(N) in the number of currently-active ballots, on every single new ballot creation.

Ballots are created whenever a new, uniquely-keyed observation appears — e.g. a new `Inbound`/`Outbound` ballot key derived from `source_chain:tx_hash:log_index` or the outbound observation hash. Per the module README, `PendingInbounds`/ballots are variant-aware and created per unique observed event; the wiki/README documentation confirms zero-amount and low-cost inbound events are accepted paths (see the "zero amount FUNDS_AND_PAYLOAD" test), suggesting an attacker can cheaply generate many distinct source-chain events that validators will observe and vote on, each spawning its own ballot.

If an attacker floods many distinct low-cost/zero-amount external-chain events within a single ballot-expiry window, the `ActiveBallotIDs` set can grow large before any of those ballots expire. Because `ExpireBallotsBeforeHeight` is re-run in full on every subsequent `CreateBallot`, the cost of processing every new vote message (`MsgVoteInbound`/`MsgVoteOutbound`) that creates a ballot grows linearly with the size of this shared active-ballot set, mirroring the unbounded-collateral-array pattern in the original report, where an attacker-influenced collection size degrades a shared iteration path used by every other participant.

### Impact Explanation
This does not directly move funds, but it degrades a path that gates finalization of legitimate inbound/outbound observations for **all** users, not just a single loan/bid as in the original (which is actually why the Sherlock judges capped severity at Medium rather than High). If sufficient active ballots accumulate, subsequent `MsgVoteInbound`/`MsgVoteOutbound` transactions become more expensive to process, and in the worst case (many thousands of concurrently-active ballots from a flood of cheap external events) could threaten to blow through gas/time budgets for otherwise-honest validator vote transactions, delaying finalization of unrelated deposits/withdrawals platform-wide.

### Likelihood Explanation
I could **not fully confirm** several critical preconditions within my tool budget:
- Whether ballot expiry windows (`expiryAfterBlocks`) are short enough in production config to keep `ActiveBallotIDs` naturally small.
- Whether there is any independent limit on the number of distinct pending inbound/outbound observations that can be outstanding at once.
- The actual gas/complexity cost of `Ballots.Get` lookups at scale (KV-store iteration cost profile).
- Whether `MsgVoteInbound`/`MsgVoteOutbound` are gasless (per the README they are), which would mean the cost of this growing loop is not paid by the attacker or even by the validator in Cosmos gas terms, but instead consumes real block-production CPU time — a different (and less clearly in-scope, more "network-level") DoS shape than a hard revert-on-gas-limit.

Given these open questions, I do not have a concrete, minimal PoC demonstrating actual transaction failure or validator halt, only a structural resemblance to the reported bug class (unbounded loop growth from attacker-reachable input, executed on a shared/critical path).

### Recommendation
This is not a confirmed, fully-reasoned exploit chain — it should be treated as a lead for further investigation, not a validated finding. To validate:
1. Determine the maximum realistic size of `ActiveBallotIDs` under expected production load and confirm whether `expiryAfterBlocks` bounds it tightly.
2. Check whether `ExpireBallotsBeforeHeight`'s cost is paid in Cosmos gas (and thus subject to a block gas limit revert) or is unmetered node-side work outside the ante gas-metering path (since votes are gasless), which would reclassify this as a validator-resource DoS rather than a user-transaction-revert DoS.
3. If confirmed exploitable, consider bounding `ExpireBallotsBeforeHeight` per call (e.g., process at most K expirable ballots per invocation) rather than a full scan, or move expiry sweeping to a dedicated `EndBlocker` pass instead of running it inline in the hot `CreateBallot` path.

### Proof of Concept
Not constructed — I was unable to verify within the available tool calls whether an unprivileged actor can, in practice, drive `ActiveBallotIDs` to a size where `ExpireBallotsBeforeHeight`'s iteration meaningfully degrades vote-transaction processing (as opposed to being naturally bounded by short expiry windows or ordinary validator vote cadence). A concrete PoC would require simulating a burst of many distinct low-cost inbound observations within one expiry window and measuring processing cost of subsequent `MsgVoteInbound` calls, which requires runtime/benchmarking access beyond static code search.

```go
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
```
