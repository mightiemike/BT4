## Analysis

The comment on `RescueFundsOnSourceChainEvent` confirms this event is "emitted by UniversalGatewayPC when a **user** initiates a rescue on the source chain" [1](#0-0) , and `event.PRC20` is decoded directly from an indexed topic supplied by the caller's contract invocation, with no relationship enforced to the original locked asset [2](#0-1) . This means an unprivileged user who owns/triggers a stuck `UniversalTx` can call the `rescueFunds`/`rescueFundsOnSourceChain` gateway function with an arbitrary `prc20` argument.

On the keeper side, `AttachRescueOutboundFromReceipt` takes `event.PRC20` and resolves it against the registry for `originalUtx.InboundTx.SourceChain` via `GetTokenConfigByPRC20`, with no check that this PRC20 corresponds to the actual asset that was originally locked/deposited in `originalUtx.InboundTx` [3](#0-2) . The resulting `OutboundTx` sets `ExternalAssetAddr: tokenCfg.Address` and `Prc20AssetAddr: event.PRC20` (derived from the attacker-chosen token) while `Amount: originalUtx.InboundTx.Amount` is copied unchanged from the original inbound (denominated in the *original* asset's units) [4](#0-3) . There is no field in `InboundTx` referenced anywhere in this function that ties the rescue back to the originally-locked asset address — only `SourceChain` and `Amount` are used, and `SourceChain` alone doesn't disambiguate between multiple tokens registered on the same chain.

This confirms the described exploit is technically valid at the keeper level: an attacker can select `event.PRC20 = Y` (registered, unrelated token) while the stuck UTX's inbound was for asset `X`, producing a rescue `OutboundTx` that pairs `Y`'s address with `X`'s numeric `Amount`. Because `attachOutboundsToUtx` blindly appends this outbound to `PendingOutbounds` and it proceeds to the `MsgVoteOutbound`/TSS signing flow through honest-validator observation of the *source-chain* execution (not re-validation of the asset/amount pairing against the inbound) [5](#0-4) , this corrupted `ExternalAssetAddr`/`Amount` pair reaches TSS-signing eligibility without further binding checks in this file.

However, I could not verify within the scoped repo whether:
1. The actual Solidity `rescueFundsOnSourceChain`/`rescueFunds` function (not present in this Go repo, likely in a separate contracts repo) restricts which PRC20 can be passed relative to the UTX's original locked token (e.g., requiring `prc20` match the UTX's stored asset on-chain before emitting the event) — the test-only gateway stub confirms tests bypass such validation, but production contract logic is out of scope/not indexed here.
2. Universal Validators or the TSS relayer's outbound broadcasting logic (`universalClient/chains/evm/tx_builder.go`) perform an independent sanity check cross-referencing `Prc20AssetAddr`/`ExternalAssetAddr` against the original inbound before constructing/signing the on-chain rescue call.

Given the keeper code in `create_outbound.go` alone has no validation binding `event.PRC20` to the original locked asset, and the event is explicitly documented as user-initiated, this is a credible finding assuming the on-chain contract does not itself enforce the binding (which would need confirmation from the Solidity source, unavailable in this indexed codebase).

### Title
Unvalidated `event.PRC20` in Rescue Outbound Allows Asset/Amount Mismatch - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`AttachRescueOutboundFromReceipt` resolves the rescue outbound's `ExternalAssetAddr`/`Prc20AssetAddr` from the attacker/user-supplied `event.PRC20` without validating it matches the asset actually locked in `originalUtx.InboundTx`, while copying the original `Amount` unchanged, producing a mismatched asset/amount pair.

### Finding Description
`event.PRC20` is decoded from an indexed topic of a user-triggered `RescueFundsOnSourceChain` log [2](#0-1) . The keeper resolves it only against `originalUtx.InboundTx.SourceChain` via the registry, with no comparison to the original inbound's asset [3](#0-2) , then builds the outbound using this unrelated token's config alongside the untouched original `Amount` [4](#0-3) .

### Impact Explanation
If unmitigated by the (out-of-scope) Solidity contract, this could cause TSS to sign an outbound instructing release of token Y at an amount denominated for token X, potentially mis-crediting recipients or over/under-releasing escrowed reserves — an accounting corruption of PRC20/native asset semantics.

### Likelihood Explanation
Depends entirely on whether the production `UniversalGatewayPC.rescueFundsOnSourceChain` Solidity function validates `prc20` against the UTX's originally locked asset before emitting the event. This contract source is not present/indexed in the reviewed Go repository, so likelihood cannot be conclusively assessed from scoped code alone.

### Recommendation
In `AttachRescueOutboundFromReceipt`, cross-validate `event.PRC20` against the original locked asset recorded on `originalUtx.InboundTx` (e.g., its `AssetAddr`/PRC20 field) before accepting the rescue event, rejecting mismatches.

### Proof of Concept
Not fully constructible within scoped code alone — requires confirming whether the Solidity `rescueFunds` function permits arbitrary `prc20` input for a stuck UTX locked in a different asset. The Go-level integration test `TestRescueFunds` in `test/integration/uexecutor/rescue_funds_test.go` demonstrates the harness (`buildRescueFundsLog`) can freely set `prc20Addr` independent of the original inbound asset, and `AttachRescueOutboundFromReceipt` accepts it without cross-check [6](#0-5) , but this only proves the keeper-side gap, not full exploitability, since the actual gating happens on-chain in the (unavailable) Solidity contract.

func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}
