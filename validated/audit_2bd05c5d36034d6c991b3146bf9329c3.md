### Title
Missing zero-value guard for `totalEnergyWeight` causes division-by-zero / silent-NaN divergence in `RepositoryImpl.calculateGlobalEnergyLimit()` - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()`, the resource-accounting function invoked from the TVM execution path to compute an account's global energy limit, divides by `totalEnergyWeight` while relying only on a Java `assert` statement to prevent a zero value from reaching the division. Java assertions are disabled by default in production JVMs (no `-ea` flag), so this check is a no-op at runtime — exactly the "check that doesn't actually check" pattern described in the `guardianDiffBips()` report, where a value used as a divisor is not properly validated before division.

### Finding Description
`calculateGlobalEnergyLimit()` in `RepositoryImpl` computes: [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

The only safeguard against `totalEnergyWeight == 0` is `assert totalEnergyWeight > 0;`, which is stripped out at runtime unless the JVM is started with `-ea` (not the default for production `FullNode`/`SolidityNode` deployments). Consequently:
- When `hardenResourceCalculation()` is enabled, `BigInteger.divide(BigInteger.ZERO)` throws an uncaught `ArithmeticException` inside the TVM/actuator hot path.
- When it is disabled, `(double) totalEnergyLimit / 0` silently yields `Infinity`/`NaN`, which is then cast to `long`, producing an incorrect (and platform/architecture-dependent for edge cases) energy limit rather than failing loudly.

Notably, the sibling implementation of the same logic in `EnergyProcessor` explicitly hardens this exact scenario, proving the zero-weight state is a recognized, real condition that must be guarded against: [2](#0-1) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  ...
  long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
  if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
    return 0;
  } else {
    assert totalEnergyWeight > 0;
  }
  ...
}
```

`RepositoryImpl.calculateGlobalEnergyLimit()` has no equivalent explicit `<= 0` early return — it dropped the real guard and kept only the non-functional `assert`, which is the direct analog of the reported bug class: a divisor is assumed non-zero via an ineffective/missing check rather than an explicit runtime validation.

### Impact Explanation
This code path is reachable from ordinary (unprivileged) smart-contract execution: `RepositoryImpl.calculateGlobalEnergyLimit()` is exposed through the `Repository` interface and delegated to via `ContractState.calculateGlobalEnergyLimit()` used inside TVM program execution (`VMActuator`) and `Wallet` RPCs. [3](#0-2) 

If `totalEnergyWeight` is ever zero (e.g. network state with no frozen-for-energy balance, or a transient window during freeze/unfreeze/reward-mechanism changes — the exact scenario `EnergyProcessor` was patched for via `allowNewReward()`), the hardened path throws an uncaught `ArithmeticException` during transaction/contract execution. Since this occurs deterministically for every full node processing the same block, it manifests as a consensus-wide processing failure (an availability/halt-class impact) rather than a benign per-node exception, matching the "invalid-state/divergence/halt" impact category. In the non-hardened path, the silent `NaN`/`Infinity` cast to `long` corrupts the calculated energy limit, an accounting-divergence risk between the two parallel implementations (`EnergyProcessor` vs `RepositoryImpl`) of the same business rule.

### Likelihood Explanation
Likelihood is constrained by how often `totalEnergyWeight` can actually be zero in a live network with existing frozen balances, which I could not fully verify given available tooling (this would require tracing all freeze/unfreeze/reward-activation state transitions). However, the codebase itself documents this as a real, previously-encountered zero-value condition (the `allowNewReward()` guard and the surrounding "fix the threshold = 0 caused incompatible" comment in `EnergyProcessor`/`ContractStateCapsule`), and that fix was not mirrored into `RepositoryImpl`. This makes the analog concrete rather than purely theoretical, though the exact trigger conditions on mainnet remain unconfirmed.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit()` with an explicit runtime check mirroring `EnergyProcessor`'s guard (e.g. `if (totalEnergyWeight <= 0) { return 0; }`) before performing either the `BigInteger` or `double` division, so both implementations of this business rule are consistent and safe against a zero divisor regardless of JVM assertion settings.

### Proof of Concept
1. Drive `DynamicPropertiesStore.getTotalEnergyWeight()` to return `0` (the same state class already anticipated by `EnergyProcessor`'s `allowNewReward() && totalEnergyWeight <= 0` branch).
2. Trigger any TVM contract call that causes `RepositoryImpl.calculateGlobalEnergyLimit(accountCapsule)` to be invoked with `hardenResourceCalculation()` enabled (default in current chain parameters, per test suite `RepositoryImplHardenTest`).
3. Because the JVM runs without `-ea` in production, `assert totalEnergyWeight > 0;` is skipped, and execution reaches `BigInteger.valueOf(energyWeight).multiply(...).divide(BigInteger.valueOf(0))`, which throws `ArithmeticException: / by zero`, propagating out of the TVM execution path for every node processing that block.
