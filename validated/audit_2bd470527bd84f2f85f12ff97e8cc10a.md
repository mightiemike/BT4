## Analysis Result

### Title
Excess outbound gas fee is permanently stranded when both refund legs of `applyGasRefund` fail - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
The C4 report's bug class is: an operation collects/holds more of an asset than it ultimately needs, and the excess is supposed to be returned to the payer, but a failure in the "return leftover" step causes the excess to be permanently lost instead of refunded. Push Chain's outbound gas-fee-refund path (`x/uexecutor/keeper/outbound.go`) exhibits the same class of bug: excess gas fee already collected from the user during outbound creation is refunded via a best-effort on-chain call, and when that call fails, the excess is simply recorded as `"FAILED"` with no retry or reconciliation path, leaving user funds permanently stuck.

### Finding Description
Every outbound's `GasFee` is fixed at outbound-creation time based on the destination-chain gas price snapshot taken from the `UniversalGatewayPC` event [1](#0-0) . This `GasFee` amount of `GasToken` (a PRC20) is deducted from the user up-front and is meant to cover the relayer's actual destination-chain gas cost.

Once Universal Validators vote the real outbound result via `MsgVoteOutbound`, `handleSuccessfulOutbound` / `handleFailedOutbound` call `applyGasRefund`, which computes `refundAmount = gasFee - gasFeeUsed` and attempts to return the unused portion to the user [2](#0-1) .

The refund is attempted in two stages:
1. **Swap-refund**: fetch a fee tier and swap quote, then call `CallUniversalCoreRefundUnusedGas(..., withSwap=true, ...)` [3](#0-2) .
2. **Fallback no-swap refund**: if step 1 fails for any reason, call `CallUniversalCoreRefundUnusedGas(..., withSwap=false, ...)` directly [4](#0-3) .

If the second (fallback) call also returns an error, the code path is:
```go
resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, false, big.NewInt(0), big.NewInt(0))
if err != nil {
    refundPcTx.Status = "FAILED"
    refundPcTx.ErrorMsg = err.Error()
} else {
    ...
}
outbound.PcRefundExecution = refundPcTx
outbound.RefundSwapError = swapFallbackReason
``` [5](#0-4) 

There is no retry loop, no re-queueing mechanism, and no alternate path (e.g. direct bank credit) that runs when this final `CallUniversalCoreRefundUnusedGas` call fails. `outbound.PcRefundExecution.Status` is simply persisted as `"FAILED"` and the outbound proceeds to `OBSERVED`/`REVERTED` regardless [6](#0-5) . The excess `GasToken` amount that was already deducted from the user remains wherever it was held prior to the refund attempt (inside the `UniversalCore`/gateway system contract's accounting) with no code path left to move it to the user. This is functionally identical to the C4 finding: value that should be returned to the payer after an operation under-consumes it is simply abandoned when the return-transfer step itself fails.

The integration test suite explicitly documents this as accepted behavior rather than a bug requiring remediation: *"In the test environment the UniversalCore stub may or may not implement refundUnusedGas... The important invariant is that the execution record is stored regardless of EVM success/failure"* and *"the outbound status stays OBSERVED (refund failure does not revert the outbound)"* [7](#0-6) .

### Impact Explanation
Any ordinary, unprivileged user whose outbound results in `gasFee > gasFeeUsed` (the common case, since `gasFee` is a conservative up-front estimate) is exposed. If the on-chain `refundUnusedGas` call fails for both the swap and no-swap legs — e.g. due to quote/slippage failure combined with the no-swap deposit call reverting (misconfigured/paused PRC20, insufficient liquidity in the UniversalCore contract's accounting, or any transient EVM-level revert) — the excess `GasToken` amount is permanently unrecoverable through any exposed message or automated retry. This is a direct, unauthorized-style permanent loss of protocol/user-controlled funds reachable purely through the standard inbound → outbound → vote lifecycle, without any privileged or malicious actor involved.

### Likelihood Explanation
This does not require a malicious validator, relayer, or admin — it only requires the ordinary condition `gasFeeUsed < gasFee` (expected on essentially every successful/failed outbound, since `GasFee` is a conservative estimate) combined with any transient failure of the second-stage `refundUnusedGas` EVM call (e.g. quote staleness, slippage guard, temporary token pause, insufficient balance in the escrow contract). No attacker action is needed to trigger the loss; it can occur as a natural consequence of market conditions or contract-level guards on `UniversalCore`.

### Recommendation
When both refund legs in `applyGasRefund` fail, do not treat the excess as settled. Options: (1) persist the failed refund in a retryable queue (similar to `PendingOutbounds`) so a subsequent block/keeper pass can retry `CallUniversalCoreRefundUnusedGas`; (2) expose a permissionless message that lets the affected user (or anyone) re-trigger the refund attempt for outbounds whose `PcRefundExecution.Status == "FAILED"`; or (3) fall back to a guaranteed-to-succeed native bank credit path that cannot revert, instead of relying solely on an EVM call that can fail for token- or liquidity-specific reasons.

### Proof of Concept
1. A user submits a `FUNDS_AND_PAYLOAD` inbound that triggers an outbound with `GasFee = 1000` (estimated).
2. UVs vote `MsgVoteOutbound` with `gasFeeUsed = 200`, producing `refundAmount = 800` in `applyGasRefund`.
3. The swap-refund attempt fails (e.g., `getSwapQuoteForRefund` returns a stale/invalid quote causing `minPCOut` slippage revert inside `UniversalCore.refundUnusedGas`).
4. The fallback no-swap `CallUniversalCoreRefundUnusedGas(..., withSwap=false, ...)` also fails (e.g., recipient's PRC20 deposit hook reverts, or the escrow balance backing the gas token accounting is momentarily inconsistent).
5. `refundPcTx.Status = "FAILED"` is recorded, `outbound.PcRefundExecution` is persisted, and the outbound flow completes as `OBSERVED`/`REVERTED` [5](#0-4) .
6. No further logic exists anywhere in `x/uexecutor` to retry or otherwise settle this `refundAmount`; the 800 units of `GasToken` are permanently unaccounted-for from the user's perspective.

// applyGasRefund computes the excess gas (gasFee - gasFeeUsed) and, if positive,
// calls UniversalCore refundUnusedGas. The result is recorded in outbound.PcRefundExecution.
// It is called for both successful and failed outbounds — gas is consumed on the
// external chain regardless of execution outcome.
func (k Keeper) applyGasRefund(ctx sdk.Context, outbound *types.OutboundTx, obs *types.OutboundObservation) {
	if obs.GasFeeUsed == "" || outbound.GasFee == "" || outbound.GasToken == "" {
		return
	}

	gasFee := new(big.Int)
	if _, ok := gasFee.SetString(outbound.GasFee, 10); !ok {
		return
	}

	gasFeeUsed := new(big.Int)
	if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok {
		return
	}

	// No excess gas to refund
	if gasFee.Cmp(gasFeeUsed) <= 0 {
		return
	}

	refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
