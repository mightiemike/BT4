## Analog Found

### Title
Meta-transaction nonce front-running enables permanent griefing of relayer-submitted `DelegateAction`/`DelegateActionV2` - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEP-366 meta transactions let a user ("sender") sign a `SignedDelegateAction`/`VersionedSignedDelegateAction` off-chain and hand the signed bytes to a relayer, who wraps it in a transaction and pays gas on the sender's behalf [1](#0-0) . This mirrors the reported ERC-20 `permit` pattern: a self-contained, bearer, off-chain-signed credential that consumes a nonce the first time it is presented on-chain. Just as an attacker can front-run a `permit()` call to burn the victim's ERC-20 nonce and cause `pool.repayWithPermit`/`pool.supplyWithPermit` to revert, an attacker who observes a `SignedDelegateAction` (e.g. via the public mempool, gossip, or by being handed it as an alternate/backup relayer) can wrap it in their own transaction and submit it first.

### Finding Description
The delegate-action nonce check lives in `validate_delegate_action_key` in `runtime/runtime/src/actions.rs`. It reads the sender's access-key (or gas-key) current nonce and requires the delegate action's nonce to be strictly greater: [2](#0-1) 

Because the check only depends on the `sender_id`/`public_key`/`nonce` fields inside the already-signed `DelegateAction`, and the signature itself does not bind to a specific relayer or submitting transaction, *anyone* who has a copy of the fully-signed `SignedDelegateAction` bytes can wrap them in their own outer transaction (any account can be the relayer/outer signer, per `SignedTransaction::from_actions` usage) and submit it to the network first. The `test_gas_key_delegate_v2_meta_transaction` test explicitly demonstrates that replaying/resubmitting the same signed delegate action after the nonce has advanced fails deterministically with `ActionErrorKind::DelegateActionInvalidNonce`: [3](#0-2) 

This is precisely the mechanics described in the report: the legitimate relayer's transaction is guaranteed to revert (the `DelegateAction` action fails with `DelegateActionInvalidNonce`) once someone else has front-run the nonce, and because a `DelegateAction` may not be paired with unrelated non-delegate actions in the same receipt (`DelegateActionMustBeOnlyOne`, see `docs/RuntimeSpec/Actions.md:372-377`), the entire relayer-sponsored receipt is wasted: the relayer has already burned the `SEND` gas cost for the outer transaction (`docs/architecture/how/meta-tx.md:175-183`), and the intended action never executes.

### Impact Explanation
This griefs the sender/relayer flow that meta-transactions were introduced (NEP-366) specifically to make trustless-ish and convenient: a malicious third party who is not a validator, not privileged, and needs no special access can permanently deny a specific relayer submission from succeeding by racing it with the observed signed payload, burning relayer gas and denying the user's intended state change (e.g., adding a key, transferring tokens via relayer). This matches the "Griefing" impact class of the original report — no profit motive required, but it reliably denies legitimate use of `Action::Delegate`/`Action::DelegateV2`.

### Likelihood Explanation
Any unprivileged party who can see a signed `SignedDelegateAction`/`VersionedSignedDelegateAction` (which by design must be handed to a relayer, transmitted over a network, or otherwise made public before submission) can copy it into their own outer transaction and submit it via the ordinary transaction-submission/RPC path with no elevated privileges, gas advantage, or validator status needed — only that their copy lands in an earlier block than the intended relayer's. This is a one-shot, reliably reproducible transaction-level race, not a chance/timing-window edge case.

### Recommendation
Bind the outer transaction/relayer identity into the signed payload (e.g., include an authorized-relayer field or an outer-transaction-hash commitment inside the data that `DelegateAction::get_nep461_hash` signs), or require the relayer to be a specific pre-committed account so that arbitrary third parties cannot lift and resubmit a `SignedDelegateAction` ahead of its intended submitter. Alternatively, document this as an inherent trust assumption between sender and relayer (as `docs/architecture/how/meta-tx.md` already partially does for the account-initialization griefing case) and encourage relayers to keep signed delegate actions confidential until submission.

### Proof of Concept
1. Sender signs a `DelegateAction` (nonce `N+1`, `receiver_id`, `actions`) intended for relayer `R`, producing `SignedDelegateAction` `S`, as in `test_meta_tx`: [4](#0-3) .
2. Attacker `A` (any account, no special privilege) observes `S` (e.g., via the mempool/gossip before `R`'s transaction is included, or because `S` was transmitted to `R` over an insecure/observable channel) and immediately wraps the same `S` in `A`'s own transaction, submitting it to the network.
3. If `A`'s transaction lands in an earlier block, `validate_delegate_action_key` advances the sender's nonce to `N+1` [5](#0-4) .
4. `R`'s original transaction, containing the same `S`, now fails validation with `ActionErrorKind::DelegateActionInvalidNonce` exactly as shown in the replay test [6](#0-5) , wasting `R`'s prepaid gas and denying the sender's intended action from executing through their chosen relayer.

## Limitation: Accounts must be initialized

Any transaction, including meta transactions, must use NONCEs to avoid replay
attacks. The NONCE must be chosen by Alice and compared to a NONCE stored on
chain. This NONCE is stored on the access key information that gets initialized
when creating an account.

Implicit accounts don't need to be initialized in order to receive NEAR tokens,
or even $FT. This means users could own $FT but no NONCE is stored on chain for
them. This is problematic because we want to enable this exact use case with
meta transactions, but we have no NONCE to create a meta transaction.

For the MVP, the proposed solution, or work-around, is that the relayer will
have to initialize the account of Alice once if it does not exist. Note that
this cannot be done as part of the meta transaction. Instead, it will be a
separate transaction that executes first. Only then can Alice even create a
`SignedDelegateAction` with a valid NONCE.

                    InvalidAccessKeyError::DelegateActionRequiresGasKey,
                )
                .into());
                return Ok(());
            };
            if nonce_index >= gas_key_info.num_nonces {

                    nonce_index,

                return Ok(());
            }
            // The index is range-checked above and gas keys initialize every

                        ))

            (current_nonce, DelegateNonceUpdate::GasKey { nonce_index })
