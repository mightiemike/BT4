### Title
Deposit path lacks the zero-shares-minted guard present in redeem, allowing silent loss of deposited principal - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vaults)

### Summary
All six tokenized vaults (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) compute `inkind` (shares to mint) via `convert-to-shares-preview` in `deposit`, but never assert that `inkind` is non-zero before minting. The symmetric `redeem` function does enforce this with `ERR-OUTPUT-ZERO`, showing the check was intentionally added on one side of the vault but omitted on the other.

### Finding Description
In `deposit`, the guards are: [1](#0-0) 

```clarity
(asserts! (not (get deposit states)) ERR-PAUSED)
(asserts! (var-get initialized) ERR-INIT)
(asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
(asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
(var-set assets (+ current-assets amount))
```

There is no `(asserts! (> inkind u0) ...)`. Compare this to `redeem`, which explicitly guards against a zero-value conversion result: [2](#0-1) 

```clarity
(asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
(asserts! (not (get redeem states)) ERR-PAUSED)
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
```

`ERR-OUTPUT-ZERO` is a defined error code in the vaults, proving the protocol authors recognized that a rounding-derived conversion can legitimately be zero and must be explicitly rejected — they applied this defense only to `redeem`, not `deposit`. The only guard that could catch a zero-share deposit on the deposit path is `(asserts! (>= inkind min-out) ERR-SLIPPAGE)`, but this is a no-op protection whenever the caller supplies `min-out = u0` (the default/naive usage pattern, and the value used across the protocol's own test suite for non-slippage-sensitive calls, e.g. `vaultUsdc.deposit(0n, 0n, alice)` pattern seen in tests): [3](#0-2) 

When `amount` is small enough (nonzero) relative to `convert-to-shares-preview`'s share-price rounding that the computed `inkind` rounds down to `u0`, and `min-out` is `u0`:
1. `amount > u0` passes (`ERR-AMOUNT-ZERO`).
2. `inkind >= min-out` passes trivially since `u0 >= u0`.
3. `receive-underlying` transfers the user's underlying asset into the vault.
4. `ft-mint? zft u0 recipient` mints zero zTokens — this call succeeds (Clarity's `ft-mint?` does not revert on a zero amount, it simply performs a no-op mint), so the transaction as a whole returns `(ok u0)` instead of reverting.
5. `assets` is incremented by `amount`, permanently absorbing the user's underlying into vault accounting without issuing any claim (zToken) to the depositor.

The transaction never reverts — the mutation (`ft-mint?` with 0 shares) is evaluated without any guard rejecting the zero-value outcome, unlike the symmetric guard that exists on `redeem`.

### Impact Explanation
The depositor's underlying asset is transferred into the vault contract and irrecoverably credited to protocol-wide `assets` accounting, but the depositor receives zero zTokens (no shares), so they have no mechanism to redeem or reclaim the deposited principal. This is a permanent loss of the user's principal — a direct theft/permanent freezing of user funds at rest, matching the in-scope Critical impact class.

### Likelihood Explanation
Triggering this requires only a single transaction with a deposit `amount` small enough (relative to the vault's current share price after `accrue`) that `convert-to-shares-preview` rounds down to zero, combined with the common case of `min-out = u0` (no slippage protection specified). This is most easily reachable early in a vault's life or right after a large accrual event skews the share price upward, and is straightforward for any user (accidentally or intentionally) to trigger since it requires no interaction with other users' positions — a pure single-transaction rounding condition.

### Recommendation
Add the same zero-output guard to `deposit` that already exists in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed before `receive-underlying`/`ft-mint?` in all six vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`), ensuring deposits that would mint zero shares revert instead of silently consuming the user's underlying asset.

### Proof of Concept
1. Deploy/observe a vault where share price (`assets`/total shares) has grown such that some small `amount` A satisfies `convert-to-shares-preview(A) == u0` (e.g., after significant interest accrual increases the exchange rate).
2. Call `deposit(A, u0, recipient)` where `min-out = u0`.
3. Execution proceeds: `(> amount u0)` passes since A > 0; `(>= inkind min-out)` passes since `u0 >= u0`; `receive-underlying` pulls A units of underlying from the caller; `ft-mint? zft u0 recipient` succeeds as a no-op; `(var-set assets (+ current-assets amount))` credits A into the vault's assets.
4. The transaction returns `(ok u0)` — no revert — while the depositor's zToken balance is unchanged (`u0` shares minted) and their underlying asset A is now vault property with no corresponding claim, resulting in an unrecoverable loss of A for that user. [4](#0-3) [5](#0-4)
