## Finding: Chunk-executor `verify_execution` accepts a divergent execution result because `ensure_match_transaction_info` skips checkpoint-hash comparison

### Title
Replay/chunk-verification path silently accepts execution divergence in state/hot-state/position checkpoint roots - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole per-transaction integrity check used by both the chunk executor's state-sync verification path (`execution/executor/src/chunk_executor/mod.rs::verify_execution`) and the archive replay tool (`storage/db-tool/src/replay_on_archive.rs::execute_and_verify`). It compares status, gas, write-set hash, and event-root hash, but explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` carried in `TransactionInfoV1`, as documented by its own trailing comment. [1](#0-0) 

### Finding Description
`TransactionInfoV1` carries three checkpoint-commitment fields that are meant to bind execution results to consensus: `state_checkpoint_hash`, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` [2](#0-1) . These are produced at commit time in `DoLedgerUpdate::assemble_transaction_infos` and folded into the transaction-info hash that is appended to the transaction accumulator [3](#0-2) , so any divergence in these roots is a real ledger-integrity break.

However, `ensure_match_transaction_info` — the function used to verify that a *locally re-executed* `TransactionOutput` matches an already-committed/backed-up `TransactionInfo` — checks only `status`, `gas_used`, the write-set hash (`state_change_hash`), and `event_root_hash`: [4](#0-3) 

It never re-derives or compares the state/hot-state/position checkpoint hashes, and the code explicitly acknowledges this gap: [5](#0-4) 

This function is the actual "verify" call in two authenticated-data-consuming call sites:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which re-executes a chunk of transactions during backup replay/verification and calls `ensure_match_transaction_info` per transaction to decide whether the chunk's outputs match the (verified) `TransactionInfo`s before continuing [6](#0-5) .
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the standalone `replay-verify` tool used to validate archived transaction history against re-execution [7](#0-6) .

Because state-checkpoint hashes (and, for the newer native-trading feature, the position-state root) are never checked here, a bug in the state-checkpoint/Merkle-root computation path — for example in `DoStateCheckpoint`'s hot-state or position-state root derivation feeding `TransactionInfoV1` — would go completely undetected by both of these verification tools. They would report "replay successful" even though the locally computed state root diverges from the one committed by consensus.

### Impact Explanation
This breaks the "authenticated replay/verification must be bound to the correct state root" invariant described in the task's proof/storage pivots. A validator, full node operator, or auditor relying on `replay_on_archive` or the chunk-executor's `verify_execution` step to detect state-computation bugs (e.g., a subtly wrong JMT/hot-state root, or — once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` ships — a wrong position-state root) would get a false "match" result, masking a real divergence between locally recomputed state and the state actually committed to the ledger. This is exactly the class of hard-fork-only/consensus-divergence detection failure the task calls out as in-scope, because it defeats the tooling meant to catch committed-state corruption before/during restore and replay.

### Likelihood Explanation
The gap is triggered any time these tools are used to verify a chunk whose transactions include a `TransactionInfoV1` with checkpoint hashes (i.e., once `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled, which the repo's own smoke tests show is an active feature path being rolled out). No malicious input is required — a purely internal computation bug in the state/hot-state/position root logic is sufficient to be silently missed. The `COMPUTE_TRADING_NATIVE_STATE_ROOTS` position-root aspect is explicitly gated as "before enabling," so today's most concrete exposure is the state/hot-state checkpoint hash blind spot, which is already reachable via the enabled `TRANSACTION_INFO_V1`/`HOT_STATE_ROOT_IN_TXN_INFO` flags.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (when applicable) `position_state_checkpoint_hash` against the values carried in the provided `TransactionInfo`, for both `TransactionInfoV0` (state checkpoint only) and `TransactionInfoV1` variants, before this comparator is relied upon by any verification/replay tooling — and definitely before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet as the code comment itself warns.

### Proof of Concept
Not independently reproducible as an exploit against consensus itself (this is a verification-tool blind spot, not a consensus state-commit bug): the code's own comment at [5](#0-4)  confirms the exact gap — `ensure_match_transaction_info` ignores checkpoint hashes — and both call sites (`chunk_executor::verify_execution` and `replay_on_archive::execute_and_verify`) use exactly this function as their pass/fail oracle, so any hypothetical bug in state/hot-state root computation would pass both tools' checks undetected.

**Caveat**: This is a verification-tooling gap, not a direct on-chain state corruption by itself; it requires a *separate* root-cause bug in checkpoint-hash computation to have real-world impact. I could not identify such a root-cause computation bug within the available indexed code (state-checkpoint hash computation itself, e.g. in `DoStateCheckpoint`, was not covered in the retrieved snippets), so I cannot claim a demonstrated wrong-value chain all the way to a corrupted committed root — only that the safety net designed to catch such divergence is itself broken by design (acknowledged via the in-code TODO).

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
