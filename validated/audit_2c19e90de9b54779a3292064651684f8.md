## Finding

The `WalletContract::rlp_execute` entry point is `#[payable]` and unconditionally captures `env::attached_deposit()` into `ExecutionContext`, but several early, synchronous error paths return an `ExecuteResponse` without ever creating a refund promise for that deposit — permanently trapping the caller's NEAR in the contract. [1](#0-0) 

### Title
Attached deposit is permanently lost on synchronous validation failures in `WalletContract::rlp_execute` - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`rlp_execute` is marked `#[payable]`, so any external caller (a relayer or third party, not just the wallet owner) may attach a NEAR deposit when invoking it. `inner_rlp_execute` builds an `ExecutionContext` from `env::attached_deposit()` and derives a `CallerDeposit` intended to protect that value, but this protection is only wired into the asynchronous promise-callback path (`rlp_execute_callback`), not into the synchronous error branches that return immediately with `Err`.

### Finding Description
`inner_rlp_execute` computes `caller_deposit` right after constructing `ExecutionContext` [2](#0-1) , then calls `parse_rlp_tx_to_action`. On any parsing failure — `Err(err @ Error::User(_))` or any other `Err(err)` (`AccountNonceExhausted`, `AccountId`, `Relayer` errors, etc.) — the function immediately `return`s the error without ever touching `caller_deposit` [3](#0-2) .

That `Err` propagates to `rlp_execute`, which converts it directly into a value response without creating any promise:
```
Err(e) => PromiseOrValue::Value(e.into()),
``` [4](#0-3) 

Because the function returns normally (does not panic), the NEAR protocol treats the receipt execution as **successful**, so the attached deposit is *not* auto-refunded by the runtime. Per the protocol's economics model, `attached_deposit` is deposited into the receiving account's balance before execution begins, and is only auto-refunded to the predecessor if the receipt execution actually fails (panics) [5](#0-4) . The only place in this contract that explicitly refunds `CallerDeposit` is inside `rlp_execute_callback`, guarded by `PromiseResult::Failed`, which is reachable only when a cross-contract promise was actually created and later failed [6](#0-5) . The synchronous validation-error branches never reach that code path, so `caller_deposit` there is simply dropped.

The contract's own error-module documentation acknowledges only that external callers pay gas for their own mistakes, but says nothing about attached deposits being retained — indicating this was an unconsidered gap rather than an intentional design choice: [7](#0-6) 

This mirrors the reported bug class: a payable/value-accepting entry point whose failure paths do not correctly return or otherwise account for attached value, resulting in funds becoming stuck in the contract.

### Impact Explanation
Any account (not just a relayer, since `rlp_execute` is a normal payable public method callable by anyone) that attaches a NEAR deposit to `rlp_execute` and triggers a synchronous validation error — e.g., malformed RLP, wrong nonce, `ExcessYoctoNear`, `UnknownFunctionSelector`, `InvalidAbiEncodedData`, `AccountNonceExhausted`, or any `RelayerError`/`UserError` surfaced before a promise is scheduled — permanently loses that attached deposit. The NEAR is not burned or sent to another party maliciously by an attacker, but it becomes value that is credited to the ETH-implicit wallet account balance with no code path returning it to the sender, i.e., silently absorbed/frozen from the caller's perspective. This is a genuine, protocol-visible loss-of-funds bug in a bridge-adjacent, protocol-level contract (the NEAR Wallet Contract used for ETH-implicit accounts).

### Likelihood Explanation
This requires only a single unprivileged transaction: any caller invoking `rlp_execute` with `deposit > 0` and an RLP payload/target/nonce combination that fails validation before a cross-contract promise is created. Given the number of validation checks that occur before any promise scheduling (nonce check, address extraction, RLP/ABI parsing, action-type checks, target/signature checks), this is easily triggered accidentally by a buggy relayer/front-end, or deliberately by any user probing the contract, with no special privileges needed.

### Recommendation
In every synchronous error branch of `inner_rlp_execute` (and in `rlp_execute`'s `Err(e) => PromiseOrValue::Value(...)` branch), if `attached_deposit` is non-zero, issue a `Promise::new(predecessor_account_id).transfer(attached_deposit)` (or equivalent) before returning the failure value, mirroring the refund logic already implemented in `rlp_execute_callback`. Alternatively, centralize deposit handling so that `CallerDeposit` is refunded consistently across both synchronous and asynchronous failure paths.

### Proof of Concept
1. Deploy/target a NEAR Wallet Contract instance on an ETH-implicit account, as in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`.
2. As any external account, call `rlp_execute(target, tx_bytes_b64)` attaching a non-zero NEAR deposit (`.deposit(NearToken::from_near(N))`), where `tx_bytes_b64` is crafted to trigger a synchronous validation error, e.g. an ABI-encoded `Transfer` action with `yocto_near >= MAX_YOCTO_NEAR` (triggers `UserError::ExcessYoctoNear`, as exercised — without a deposit — in `test_excess_yocto` [8](#0-7) ), or any malformed nonce/RLP payload.
3. Observe: `ExecuteResponse.success == false`, but the caller's account balance decreases by the full attached deposit (minus gas), and the wallet contract's balance increases by that deposit permanently, with no subsequent refund receipt generated (contrast with `test_caller_refunds`, which only exercises the promise-failure refund path [9](#0-8) ).

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
