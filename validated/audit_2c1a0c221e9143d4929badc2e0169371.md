### Title
Unauthenticated `batchProver_setCommitments` RPC call overrides the local sequencer-commitment ledger, an admin-only operation lacking access control - (File: `crates/batch-prover/src/rpc.rs`)

### Summary
The batch prover's JSON-RPC interface exposes `setCommitments` (and related mutating methods `prove`, `submitFakeProof`, `pauseProving`, `retryProvingJob`) with no access-control gate. The rollup's RPC `Auth` middleware only protects three hard-coded method names (`backup_create`, `backup_validate`, `backup_info`); every other method, including these state-mutating batch-prover admin calls, is reachable by any unauthenticated JSON-RPC caller.

### Finding Description
`Auth::call` in `crates/common/src/rpc/auth.rs:11,36` checks the requested method name against a fixed allow-list, `PROTECTED_METHODS`, and lets any method not in that list pass straight through to the underlying service without an API key: [1](#0-0) [2](#0-1) 

`crates/batch-prover/src/rpc.rs` defines `setCommitments`, explicitly documented as an override-with-caution admin utility: [3](#0-2) 

and its implementation directly overwrites the ledger DB's commitment-by-index, commitment-index-by-L1, and pending-commitment tables with attacker-supplied values, with no sender/caller check whatsoever: [4](#0-3) 

The RPC server that serves these methods is the same server that applies the `Auth` middleware layer (`layer_fn(move |s| super::auth::Auth::new(s, rpc_config.api_key.clone()))`), so unless `setCommitments`/`prove`/`submitFakeProof`/`pauseProving`/`retryProvingJob` are added to `PROTECTED_METHODS`, any network caller reaching this RPC port can invoke them: [5](#0-4) 

This mirrors the reported bug class exactly: an operation that should require an authorized/admin caller (`resetGame`/`onlyOwner` in the external report) has no restriction because the access-control allow-list was never updated to include it (`ResetSystem` was omitted from `openAccess: false` in `mud.config.ts`; here, `setCommitments` etc. are omitted from `PROTECTED_METHODS`).

### Impact Explanation
`setCommitments` lets an unprivileged caller overwrite the batch prover's local view of sequencer commitments — the data structure the prover subsequently uses to build circuit inputs and drive proving (`create_circuit_input`, `submit_fake_proof`, `prove`). By injecting bogus commitment entries (arbitrary `merkle_root`/`l2_end_block_number` pairs) an attacker can corrupt the prover's internal bookkeeping, cause it to attempt proving over fabricated commitment ranges, desynchronize its pending-commitment queue, and disrupt subsequent legitimate proving requests — an unauthenticated JSON-RPC call mutating node state, which is explicitly listed as a valid High-impact class in scope. (Whether a corrupted local commitment can ultimately produce a false on-chain state transition depends on downstream verification against DA-signed commitments in the light-client circuit, which was not fully traced in this pass — see Uncertainty below.)

### Likelihood Explanation
High: exploitation requires only a single unauthenticated JSON-RPC call to the batch-prover's RPC endpoint if it is network-reachable; the `Auth` middleware performs no default-deny, only a hard-coded allow-list of three unrelated backup methods, so no credentials or special role are needed to reach `setCommitments`.

### Recommendation
Add `setCommitments`, `submitFakeProof`, `prove`, `pauseProving`, and `retryProvingJob` (all state-mutating batch-prover admin methods) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, or otherwise require the RPC API key / an explicit authorization check before executing these handlers in `crates/batch-prover/src/rpc.rs`, consistent with the pattern already used for the backup RPC methods.

### Proof of Concept
1. Start a batch-prover node with its JSON-RPC server bound and reachable, without supplying (or with) an `api_key`, since `setCommitments` is not in `PROTECTED_METHODS`.
2. From any unauthenticated client, call:
```json
{"jsonrpc":"2.0","id":1,"method":"batchProver_setCommitments","params":[[{"merkleRoot":"0x00...","index":"0x1","l2EndBlockNumber":"0x1","l1Height":"0x1"}]]}
```
3. Observe the call succeeds (per `crates/batch-prover/src/rpc.rs:345-381`) and overwrites `ledger_db` commitment tables, with no API key or signature required, even though the method mutates prover state (analogous to calling `resetGame()` in the reference report with no `onlyOwner` modifier).

**Uncertainty:** I could not fully trace, within the available tool budget, whether corrupted local commitment entries injected via `setCommitments` can propagate into a proof that is ultimately accepted at the light-client stage (which independently verifies sequencer-commitment blobs against the sequencer's DA public key in `crates/light-client-prover/src/circuit/mod.rs`), or whether the impact is confined to local prover-node bookkeeping/DoS of the proving pipeline. This affects whether the impact should be classified as Critical (false state transition path) versus the High classification given above (unauthenticated RPC mutating node state).

```rust
    async fn set_commitments(
        &self,
        commitments: Vec<SequencerCommitmentRpcParam>,
    ) -> RpcResult<()> {
        for commitment in commitments {
            let l1_height = commitment.l1_height.to::<u64>();
            let commitment = SequencerCommitment {
                merkle_root: commitment.merkle_root,
                index: commitment.index.to::<u32>(),
                l2_end_block_number: commitment.l2_end_block_number.to::<u64>(),
            };

            info!(
                "Overriding sequencer commitment, index={} merkle_root={} l2_end_height={} l1_height={}",
                commitment.index,
                hex::encode(commitment.merkle_root),
                commitment.l2_end_block_number,
                l1_height,
            );

            self.context
                .ledger_db
                .put_commitment_by_index(&commitment)
                .map_err(internal_rpc_error)?;
            // This might cause some duplicate commitment indices appear in l1 -> index table which is ok
            self.context
                .ledger_db
                .put_commitment_index_by_l1(SlotNumber(l1_height), commitment.index)
                .map_err(internal_rpc_error)?;
            self.context
                .ledger_db
                .put_prover_pending_commitment(commitment.index)
                .map_err(internal_rpc_error)?;
        }

        Ok(())
    }
```
