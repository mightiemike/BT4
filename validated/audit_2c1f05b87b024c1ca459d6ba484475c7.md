### Title
Griefing self-DoS on liquidation via repeated same-block micro-borrows resetting `last-borrow-block` - (File: `mainnet/contracts/market/v0-market-vault.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`debt-add-scaled` unconditionally overwrites `last-borrow-block` with the current `stacks-block-height` on every call, and `liquidate()` unconditionally rejects any liquidation attempt when `last-borrow-block == stacks-block-height`. A borrower (or anyone able to trigger a debt-add on the position) can keep the position permanently "borrowed this block" from a liquidator's perspective by re-issuing a trivial borrow in the same block a liquidator tries to act, analogous to the mVeNFT report where an unrelated state-mutating call (`_poke`) stamps a timestamp that then blocks the legitimate follow-up action (`vote`).

### Finding Description
`debt-add-scaled` in `market-vault.clar`/`v0-market-vault.clar` does: [1](#0-0) 
which sets `last-borrow-block: stacks-block-height` on **every** call to `debt-add-scaled`, regardless of amount, with only `(asserts! (> scaled-amount u0) ...)` as a floor — any nonzero scaled-debt addition qualifies.

`liquidate()` in `v0-4-market.clar` reads this stamped value and hard-fails if it equals the current block height: [2](#0-1) 

The check is a strict equality on `stacks-block-height`, not a decaying/expiring timelock keyed to the liquidator's context — it is purely "was any debt added to this account in the current block." Because `borrow()` calls `debt-add-scaled` for any `amount > u0` (there is no minimum borrow floor beyond `> u0`), and Stacks transaction fees are comparatively cheap, a borrower can issue a minimal borrow transaction that re-stamps `last-borrow-block` in the same block as an incoming liquidation, permanently deferring an otherwise-legitimate liquidation to "next block," and can repeat this pattern every block a liquidator attempts to act.

### Impact Explanation
This causes temporary freezing of the liquidator's ability to seize/repay bad debt exactly when the position is unhealthy — a governance/liquidation-availability DoS that, if sustained block after block by a motivated underwater borrower, keeps insolvent debt on the books (temporary freezing of protocol/lender funds represented by the impaired collateral/debt), matching the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
Reachable with a single unprivileged account issuing a minimal `borrow()` call; no DAO or oracle compromise needed. It requires the attacker to observe/predict when a liquidation transaction targeting them will land in the same block, which is feasible via mempool monitoring, and the cost is only that of a minimal borrow transaction repeated per block — an economically cheap griefing vector, though it only delays rather than eliminates liquidation (liquidator can retry next block), which bounds severity to Medium/temporary freezing rather than permanent loss.

### Recommendation
Do not let arbitrary/incidental debt-add operations reset the same-block liquidation-protection stamp. Only set `last-borrow-block` when a *new* borrow first opens/increases risk beyond what was already flagged this block, or better, use a monotonic "position already flagged unhealthy-eligible" check independent of the most recent stamp, or require the anti-flash-loan check to compare against the block in which collateral/price was last read rather than any debt-add event on the account.

### Proof of Concept
1. Attacker/borrower position becomes liquidatable (price drop or interest accrual). [3](#0-2) 
2. A liquidator submits `liquidate(borrower, ...)` in block N.
3. Borrower (or any actor able to act on the account, e.g. via a bot) submits `borrow(ft, 1, ...)` in the same block N; `borrow()` calls `vault-system-borrow` then `debt-add-scaled`, which sets `last-borrow-block = stacks-block-height (N)`. [4](#0-3) [5](#0-4) 
4. Depending on transaction ordering within block N, `liquidate()`'s `same-block-check` sees `last-borrow-block == stacks-block-height` and reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK`. [2](#0-1) 
5. Borrower repeats step 3 every subsequent block that a liquidator attempts to act, indefinitely deferring liquidation of the unhealthy position.

Note: this analysis relies on the indexed contents of `market-vault.clar`/`v0-market-vault.clar` and `v0-4-market.clar`/`market.clar`; I could not fully verify whether transaction ordering within a Stacks block is deterministic/attacker-controllable enough to guarantee the borrower's `borrow()` lands before the liquidator's `liquidate()` in the same block, which affects the practical reliability of this griefing vector — a full Devin session with repo/test access would be needed to confirm block-ordering assumptions and any additional guards (e.g., minimum borrow amounts, per-account rate limits) that may exist elsewhere in the codebase but were not surfaced by the search.
