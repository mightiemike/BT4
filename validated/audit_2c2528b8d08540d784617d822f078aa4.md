### Title
Webhook HMAC validation does not bind the signed hash to the destination shop domain, enabling cross-tenant webhook spoofing - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
Shopify webhook requests are authenticated purely by computing `HMAC(apiSecretKey, rawBody)` and comparing it to the `X-Shopify-Hmac-Sha256` header. The `X-Shopify-Shop-Domain` header, which is later trusted to look up and attach the target shop's offline session/access token, is never included in the HMAC-signed material. Because the same `apiSecretKey` is shared across every shop that installs the app, a valid `(body, hmac)` pair legitimately produced for one shop can be replayed against the same public webhook endpoint while claiming to be from a different shop, exactly analogous to the reported "hash reused across games" bug class, where a signed value is valid in one context but is not bound to that context's identity.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC solely from `rawBody` and the shared `config.apiSecretKey`, then compares it to the incoming `hmac` header: [1](#0-0) 

The shop identity (`X-Shopify-Shop-Domain`) is parsed from headers only as metadata and is never mixed into the signed payload used for `validateHmacString`: [2](#0-1) 

Because `apiSecretKey` is a single app-wide secret (not per-shop), any merchant who installs the app can trigger a real webhook on their own store (e.g. `PRODUCTS_CREATE` with an attacker-chosen product title), capture the genuine `(rawBody, hmac)` pair that Shopify sends, and then POST that exact pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value for a *different, victim* shop. `validateFactory` only checks the HMAC and presence of required headers, so this forged request is accepted as valid: [3](#0-2) 

Downstream, both `shopify-app-remix` and `shopify-app-react-router` trust `check.domain` unconditionally to load the real offline session (and access token) for the named shop and attach an authenticated admin client to the webhook context passed to the developer's handler: [4](#0-3) 

### Impact Explanation
An attacker who is any single merchant able to install the target app on their own store can forge webhook deliveries "from" any other shop that has the app installed. This causes the app's webhook pipeline to load and attach the victim's real offline session and Admin API client to a handler invocation whose topic/body content is attacker-controlled (crafted via fields on their own store, such as product titles/descriptions), and whose `shop_domain` is claimed to be the victim. Depending on what the developer's webhook handler does with the authenticated `admin` client and payload, this enables cross-tenant business-logic abuse using a genuine victim access token (e.g. writes/mutations, data corruption, triggering side effects) — impact is High because it defeats the core assumption that a validated webhook accurately identifies its origin shop.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the attacker to be an app merchant (unprivileged relative to other tenants) capable of installing the app and generating at least one webhook on their own store, and to know/guess a target shop's `.myshopify.com` domain (often discoverable). No secret material needs to be leaked — the attack only exploits the fact that the shop domain is not part of the signed content, which is a design-level omission rather than a leaked-key scenario.

### Recommendation
Bind the destination shop identity to the value being verified, mirroring the report's suggestion to encode the caller's identity into the verified hash:
- After a webhook is HMAC-validated, cross-check `check.domain` against a shop that is actually known to have installed the app (e.g. verify a session exists via `sessionStorage`/`findSessionsByShop` before trusting `check.domain`) rather than blindly calling `ensureValidOfflineSession(params, check.domain)` with an unauthenticated header value.
- Where feasible, additionally validate that the raw webhook body's own shop-scoped identifiers (e.g. resource GIDs, `admin_graphql_api_id`) are consistent with the claimed `X-Shopify-Shop-Domain`, since that header itself is not covered by the HMAC.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `PRODUCTS_CREATE`).
2. Attacker creates a product with an attacker-chosen title/body on their own store, triggering Shopify to POST a legitimately signed webhook: `rawBody = B`, `X-Shopify-Hmac-Sha256 = H = HMAC(apiSecretKey, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and replays it directly to the app's public webhook endpoint, replacing only the domain header: `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, keeping body `B` and hmac `H` unchanged.
4. `validateHmacFromRequestFactory` recomputes `HMAC(apiSecretKey, B) == H` and passes; `checkWebhookHeaders` finds all required headers present, so `webhooks.validate` returns `valid: true` with `domain: 'victim-shop.myshopify.com'`.
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading victim's real offline session/access token, and invokes the developer's webhook handler with attacker-controlled payload `B` and an authenticated `admin` client scoped to the victim shop.
