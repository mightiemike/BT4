### Title
Missing `supportUnfreezeDelay` governance-flag check in `WithdrawExpireUnfreezeProcessor` allows the unfreeze-delay feature to be used via TVM before it is enabled by the committee - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java)

### Summary
The Vader `LinearVesting.claimConverted()` bug is that a state-gating modifier (`hasStarted`) is checked in some code paths but omitted in the vulnerable function, letting users act before the feature was actually enabled. Java-tron has a structurally identical pattern for the `WithdrawExpireUnfreeze` feature: the standard transaction actuator enforces a "has this feature been turned on by governance" check, but the equivalent TVM-native-contract code path used by smart contracts omits it.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` explicitly requires the committee-controlled `supportUnfreezeDelay()` flag before allowing the withdrawal of expired-unfreeze balances: [1](#0-0) 

This check exists specifically because the unfreeze-delay mechanism (v2 freeze/unfreeze with a waiting period before funds can be withdrawn) is a feature gated by the committee, distinct from the general "allow TVM FreezeV2" flag.

However, the equivalent logic reachable from smart contracts, `WithdrawExpireUnfreezeProcessor.validate()`/`execute()` (invoked by `Program.withdrawExpireUnfreeze()` for the `WITHDRAWEXPIREUNFREEZE` TVM opcode), never calls `supportUnfreezeDelay()`: [2](#0-1) [3](#0-2) 

The `WITHDRAWEXPIREUNFREEZE` opcode itself is only gated by the separate `allowTvmFreezeV2` proposal, not by `supportUnfreezeDelay`: [4](#0-3) 

These are two independent committee-controlled proposal flags (`allowTvmFreezeV2` for enabling FreezeV2-family opcodes, and `UnfreezeDelayDays`/`supportUnfreezeDelay` for enabling the unfreeze-delay withdrawal feature), evidenced by `supportUnfreezeDelay` being referenced separately in `DynamicPropertiesStore`, `FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`, and `WithdrawExpireUnfreezeActuator`, while `allowTvmFreezeV2` is referenced separately in `VMConfig`, `FreezeV2Util`, `PrecompiledContracts`, and `OperationRegistry`. This mirrors the Vader bug class: a state/feature-enablement check ("has the feature been started/opened by the owner/committee") is present in one code path (the direct-transaction actuator) but missing in a functionally equivalent, unprivileged-user-reachable path (the TVM native contract processor).

### Impact Explanation
If the committee enables `allowTvmFreezeV2` (needed for the FreezeV2 opcode family generally) before separately enabling `supportUnfreezeDelay` (i.e., before `UnfreezeDelayDays` governance proposal passes), any smart contract can call the `WITHDRAWEXPIREUNFREEZE` opcode to withdraw expired-unfreeze balances even though this specific sub-feature was never "started" by governance. This creates a state divergence between the two entry points for the same contract type (`WithdrawExpireUnfreezeContract`): one enforces the governance gate, the other does not, allowing unprivileged users to trigger functionality that the committee has not yet turned on.

### Likelihood Explanation
Reaching this requires (a) the network operating in a window where `allowTvmFreezeV2` is active but `supportUnfreezeDelay` is not, and (b) an account already having `UnFreezeV2` entries with `unfreezeExpireTime` values populated (created via `UnfreezeBalanceV2` actuator/processor). Since these are governance-configuration-dependent conditions specific to proposal rollout ordering, likelihood is low but concrete — it is a real code-path divergence, not a theoretical one, since the two implementations objectively differ in the checks performed.

### Recommendation
Add a `dynamicStore.supportUnfreezeDelay()` check (mirroring `WithdrawExpireUnfreezeActuator.validate()`) to `WithdrawExpireUnfreezeProcessor.validate()`, throwing a `ContractValidateException` if the feature is not yet enabled by the committee, so both entry points enforce identical governance gating.

### Proof of Concept
1. Committee enables `allowTvmFreezeV2` (activating `FREEZEBALANCEV2`/`UNFREEZEBALANCEV2`/`WITHDRAWEXPIREUNFREEZE` opcodes) but has not yet enabled `supportUnfreezeDelay` (e.g., `UnfreezeDelayDays` proposal not passed).
2. A contract account accumulates `UnFreezeV2` entries via `UNFREEZEBALANCEV2` with expired `unfreezeExpireTime`.
3. The contract calls `WITHDRAWEXPIREUNFREEZE`, which routes to `Program.withdrawExpireUnfreeze()` → `WithdrawExpireUnfreezeProcessor.validate()`/`execute()`; no `supportUnfreezeDelay()` check blocks it, so the balance is withdrawn — whereas the same account calling the plain `WithdrawExpireUnfreezeContract` transaction via `WithdrawExpireUnfreezeActuator` would be rejected with "Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee".   public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
  }

  public long withdrawExpireUnfreeze() {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner, 0, null,
        "withdrawExpireUnfreeze", nonce, null);

    try {
      WithdrawExpireUnfreezeParam param = new WithdrawExpireUnfreezeParam();
      param.setOwnerAddress(owner);

      WithdrawExpireUnfreezeProcessor processor = new WithdrawExpireUnfreezeProcessor();
      processor.validate(param, repository);
      long expireUnfreezeBalance = processor.execute(param, repository);
      repository.commit();
      if (internalTx != null) {
        internalTx.setValue(expireUnfreezeBalance);
      }
      return expireUnfreezeBalance;
    } catch (ContractValidateException e) {
      logger.warn("TVM WithdrawExpireUnfreeze: validate failure. Reason: {}", e.getMessage());
    } catch (ContractExeException e) {
      logger.warn("TVM WithdrawExpireUnfreeze: execute failure. Reason: {}", e.getMessage());
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return 0;
  }
