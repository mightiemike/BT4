### Title
Multi-sig weight duplication via ECDSA signature malleability bypasses pre-fork "signed twice" dedup in `checkWeight` - (File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java)

### Summary
Before the `VERSION_4_7_1` hard fork, `TransactionCapsule.checkWeight` deduplicates signatures by the base64 encoding of the raw signature bytes instead of the recovered signer address. Because ECDSA signatures are malleable (a signature `(r, s)` and `(r, n-s)` both recover to the same public key/address), an attacker can submit two distinct-byte signatures from a single private key that both validate and both contribute weight, defeating the "has signed twice" check and reaching a multi-sig threshold with fewer real signers than the permission policy requires.

### Finding Description
`checkWeight` builds a `HashMap addMap` keyed initially on `base64` (the raw bytes of each submitted signature), and only re-keys on the recovered `address` (via `encode58Check(address)`) when `ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)` is true: [1](#0-0) 

For every signature in `sigs`, the code:
1. Requires only `sig.size() >= 65` (no canonical-form / low-S enforcement) — `SignUtils.isValidLength` (the stricter length check) is explicitly documented as NOT used here. [2](#0-1) 
2. Recovers `address` via `SignUtils.signatureToAddress(hash, base64, ...)`, which for the default ECKey engine calls `ECKey.signatureToAddress`. [3](#0-2) 
3. Looks up the key's weight via `getWeight(permission, address)`.
4. **Pre-fork**, dedups on the raw signature `base64` string, not on the resolved `address`. Since a malleated signature `(r, n-s, v')` produces different raw bytes/base64 than the original `(r, s, v)` while recovering to the identical address, `addMap.containsKey(base64)` is `false` for the second entry, so the "has signed twice" `PermissionException` is never thrown, and `currentWeight` is incremented a second time for the same underlying key.

This directly violates the intended invariant that a permission requiring N distinct approving keys cannot be satisfied by fewer real signers, allowing a single private key holder to forge a second, differently-encoded valid signature over the same `hash` and double their weight.

### Impact Explanation
Any multi-sig `Permission` (active/owner/witness permission with `threshold > 1` and multiple keys, but reachable with as few as one real key plus one malleated re-signature) can have its threshold satisfied by a single colluding/compromised key instead of the required number of independent approvers. This can authorize fund transfers, resource delegation, withdrawals, or any privileged actuator gated by that permission — i.e., the "signed twice" invariant that underlies multi-sig security is broken pre-fork, allowing unauthorized execution of transactions that should require multiple independent signers.

### Likelihood Explanation
Exploitability requires only: (1) the network/context to be pre-`VERSION_4_7_1` fork (a genuinely reachable historical condition, and any fork-disabled/test/private network still running old logic remains exposed), and (2) one private key under attacker control participating in a multi-sig permission. Generating the malleated signature `(r, n-s)` from `(r, s)` is a standard, deterministic, cheap EC operation requiring no additional secret knowledge — fully reproducible and repeatable for every transaction the attacker wants to push through.

### Recommendation
Always dedup by the recovered `address` (as done in the `VERSION_4_7_1` path) unconditionally, rather than gating this fix behind a fork check, and additionally enforce canonical (low-S) signature form for all signatures accepted in `checkWeight`, rejecting `s > HALF_CURVE_ORDER` before recovery so semantically-duplicate signatures cannot be constructed at all.

### Proof of Concept
Java unit test plan (added to a test class like `TransactionCapsuleTest`):
```java
@Test
public void testCheckWeightMalleableSignatureBypassesDedup() throws Exception {
  ECKey key = new ECKey();
  byte[] hash = Sha256Hash.hash(true, "test-tx-hash".getBytes());

  // Build a 2-of-N (or N-of-N) permission containing only `key`'s address once,
  // but with enough total keys/threshold that a single real signer should not suffice.
  Permission permission = Permission.newBuilder()
      .setThreshold(2)
      .addKeys(Key.newBuilder().setAddress(ByteString.copyFrom(key.getAddress())).setWeight(1))
      .addKeys(Key.newBuilder().setAddress(ByteString.copyFrom(new ECKey().getAddress())).setWeight(1))
      .build();

  ECKey.ECDSASignature original = key.sign(hash);
  byte[] sig1 = ECDSASignatureToBytes(original); // canonical (r, s, v)

  // Malleate: s' = N - s, flip recovery id accordingly
  BigInteger sPrime = ECKey.CURVE.getN().subtract(original.s);
  ECKey.ECDSASignature malleated = new ECKey.ECDSASignature(original.r, sPrime);
  malleated.v = (byte) (original.v ^ 1); // adjust recovery id to still recover same address
  byte[] sig2 = ECDSASignatureToBytes(malleated);

  List<ByteString> sigs = Arrays.asList(ByteString.copyFrom(sig1), ByteString.copyFrom(sig2));

  long weight = TransactionCapsule.checkWeight(permission, sigs, hash, null);

  // Pre-fork (ForkController VERSION_4_7_1 not active): expect this to WRONGLY succeed
  // with weight == 2 using a single controlling key, instead of throwing
  // PermissionException("... has signed twice!").
  Assert.assertEquals(2L, weight); // demonstrates the flaw pre-fork
}
```
Expected correct behavior (post-fix): the second call should throw `PermissionException` with message containing `"has signed twice!"` regardless of fork status, and `weight` should never reach `2` from a single real key.
