This is a real, confirmed griefing/drain vector: `DeductGasFeesFromReceipt` in `x/uexecutor/keeper/fees.go` charges gas from the target UEA's balance based purely on `receipt.GasUsed`, without checking whether the EVM call reverted. Combined with `MsgExecutePayload`'s explicit design that any signer can submit a payload targeting any victim's `UniversalAccountId` (documented as intentionally `Signer != Owner`), an attacker can force the victim's UEA to pay real gas costs for calls the attacker fully controls and that never need to succeed.

### Title
Unauthenticated `MsgExecutePayload` submissions can drain a victim UEA's native balance via gas-fee deduction regardless of execution success - (File: `x/uexecutor/keeper/msg_execute_payload.go`, `x/uexecutor/keeper/fees.go`)

### Summary
`ExecutePayload` lets *any* Cosmos signer submit a payload against *any* `UniversalAccountId` (owner), and it is a gasless message so the attacker pays nothing. After calling `CallUEAExecutePayload`, the keeper unconditionally calls `DeductGasFeesFromReceipt`, which deducts `upc` from the **victim UEA's** balance based only on `receipt.GasUsed` — it never checks `receipt.VmError`/success. Because the attacker fully controls `UniversalPayload.GasLimit`, `MaxFeePerGas`, and `To`/`Data` (the only thing they cannot forge is `VerificationData`), they can repeatedly submit payloads that consume gas inside the UEA's EVM call (e.g., large `Data`, expensive `To` targets, or gas-heavy reverts) and have that gas billed to the victim, for free to themselves, at zero cost, in an unbounded loop. [1](#0-0)  confirms the intentional design that `Signer != Owner` for `MsgExecutePayload`, and that authorization/anti-forgery is expected to live entirely inside signature verification. The README's own safety argument explicitly claims "No EVM gas is charged to the victim UEA... the deduction is rolled back with the rest of the transaction" on a failed signature check [2](#0-1) . This claim depends entirely on `CallUEAExecutePayload`'s EVM call reverting with **zero gas used** on signature failure — but Solidity `require`/`revert` after non-trivial computation still consumes gas up to the point of revert, and the surrounding Cosmos SDK message handler does **not** roll back the fee deduction on signature failure, since fee deduction happens as its own step regardless of `execErr`.

### Finding Description
- `msgServer.ExecutePayload` → `Keeper.ExecutePayload` (`x/uexecutor/keeper/msg_execute_payload.go`) resolves the victim's UEA address from the attacker-supplied `UniversalAccountId`, calls `CallUEAExecutePayload`, then in Step 4 calls `DeductGasFeesFromReceipt` unconditionally, "regardless of success/failure": [3](#0-2) 
- `DeductGasFeesFromReceipt` deducts and burns real `upc` from the target UEA's own balance purely as a function of `receipt.GasUsed` and the attacker-chosen `MaxFeePerGas`/`GasLimit` fields inside the payload — there is no check of `receipt.VmError` or of the EVM call's actual success: [4](#0-3) 
- The keeper only returns `execErr` (i.e., propagates the Cosmos tx failure) **after** the fee has already been deducted: [5](#0-4) 
- `MsgExecutePayload` is explicitly gasless for the attacker (`app/txpolicy/gasless.go`), and the module's own README states the authorization model deliberately allows `Signer != Owner`, relying solely on `verificationData` signature-check inside the UEA contract to prevent abuse: [6](#0-5) 

This is the direct analog of the CollateralManager bug: a state-mutating function (`commitCollateral`/`DeductGasFeesFromReceipt`) is reachable and mutates an entity's (loan's/UEA's) balance/state without verifying the caller is authorized *for that specific mutation to occur at all* — here, an unprivileged attacker forces value extraction from a victim account merely by submitting a message referencing that victim's `UniversalAccountId`, exactly the same "public function callable on someone else's active state" root cause.

### Impact Explanation
An attacker can repeatedly submit `MsgExecutePayload` messages (free of Cosmos gas cost, since the message type is gasless) targeting any known/discoverable victim UEA, each one intentionally causing `CallUEAExecutePayload`'s underlying EVM call to consume nontrivial gas (e.g., a `Data` payload that triggers expensive computation in the `To` contract or in the UEA's revert path before failing the signature check) while never needing `VerificationData` to be valid. Each submission burns real `upc` from the victim's balance via `DeductAndBurnFees`, permanently and irrecoverably (funds are burned, not merely transferred). Because the attacker fully controls `GasLimit`/`MaxFeePerGas` within the payload (bounded only by validation, but attacker can maximize within limits) and pays zero cost themselves, this is an unauthorized, permanent drain of victim-controlled funds — squarely in scope ("stealing, draining, permanent loss ... of user or protocol-controlled funds").

### Likelihood Explanation
High, if the underlying claim in the README ("no gas charged on signature failure") does not hold in practice for non-trivial reverts. The attack requires no privileged role, no validator collusion, and no race condition — merely knowledge of a victim's `UniversalAccountId` (deterministically derivable) and submission of a single message type that any account can send for free. This is a "default transaction submission path" fully reachable by any external unprivileged user, matching the required threat model exactly.

### Recommendation
- Check `receipt.VmError` (or equivalent revert indicator) in `DeductGasFeesFromReceipt` and skip/limit fee deduction when the underlying EVM call reverted due to signature/authorization failure specifically, mirroring the CollateralManager fix's approach of tightening the guard rather than relying on downstream contract behavior.
- Alternatively/additionally, require the Cosmos-level `ExecutePayload` message handler to only deduct gas fees from the payload owner's UEA when `CallUEAExecutePayload` succeeds; failed authorization should either charge the `Signer` (who submitted the bogus payload) a nominal cost, or be free but capped at a minimal always-cheap pre-check (e.g., cheap `ecrecover`-based check before touching `Data` execution) so failed submissions cannot be made expensive.
- Verify empirically (not just by comment/README claim) that `CallUEAExecutePayload`'s failure path in `UEA_EVM.sol`/`UEA_SVM.sol` always reverts at `receipt.GasUsed == 0`, or add gas metering caps at the Cosmos layer that reject/refund large `GasUsed` values attributable to signature-check failures.

### Proof of Concept
1. Attacker identifies (or brute-forces via the deterministic factory) a funded victim `UniversalAccountId`/UEA address (owner unknown/uncooperative to attacker).
2. Attacker crafts a `UniversalPayload` with `To` set to a contract (or the UEA itself) whose call path performs meaningful computation (e.g., a large loop, expensive storage write attempt, or long `Data` blob) before any signature check inside `executeUniversalTx` can short-circuit it — or simply relies on the EVM gas consumed up to the `require(signatureValid)` revert point.
3. Attacker sets `MaxFeePerGas`/`GasLimit` to reasonable but non-trivial values, and submits `MsgExecutePayload` with a garbage/self-signed `VerificationData` that will fail the UEA's signature check.
4. `msgServer.ExecutePayload` executes: `CallUEAExecutePayload` returns a receipt with `GasUsed > 0` and `execErr != nil` (signature check reverted): `x/uexecutor/keeper/msg_execute_payload.go` lines 86-97.
5. `DeductGasFeesFromReceipt` is invoked with the non-nil receipt regardless, and burns `gasCost` upc from the victim UEA's balance via `DeductAndBurnFees`, before `execErr` is finally returned to fail the overall message.
6. Attacker repeats step 3–5 in a loop (message is gasless, so no cost to the attacker) until the victim's UEA balance is fully drained/burned.

**Note on uncertainty**: I was not able to inspect the Solidity source of `UEA_EVM.sol`/`UEA_SVM.sol` (they live in the separate `push-chain-core-contracts` repo, referenced only via external GitHub links in the README, not part of this indexed repository) to confirm whether `receipt.GasUsed` is actually non-zero on signature-check failure. The vulnerability's materiality hinges on this fact, which the module's own documentation asserts is "zero" but which is not verifiable from the code available in this repository. If `GasUsed` is provably always `0` on signature failure (e.g., the check happens before any state access with an early `require`), this specific PoC would not be exploitable and the finding would reduce to a lower-severity concern about `DeductGasFeesFromReceipt`'s missing `VmError` check as defense-in-depth rather than a confirmed live drain.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.

#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
```

// DeductGasFeesFromReceipt calculates and deducts gas fees from a recipient address
// based on the EVM receipt and universal payload parameters.
// Returns nil if receipt is nil (Go-level error, no EVM tx was created).
// Returns error with gas details if deduction fails (insufficient balance, etc).
func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}
```
