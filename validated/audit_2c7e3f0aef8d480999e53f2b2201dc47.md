### Title
Griefing Fund Migration by sending native tokens to the old TSS address causes signing-hash mismatch and repeated migration failure - ([File: universalClient/tss/sessionmanager/sessionmanager.go], [File: universalClient/chains/evm/tx_builder.go])

### Summary
The fund-migration flow computes the amount to sweep from a retiring TSS address as `balance - gasCost - l1GasFee`, where `balance` is queried live from the external chain independently by the coordinator and by each verifying Universal Validator (UV). Because the "swept amount" (and therefore the TSS signing hash) is derived from a live, attacker-influenceable on-chain balance rather than a value fixed once at migration-initiation time, an unprivileged attacker can send a trivial amount of native gas token directly to the (publicly known) old TSS address between the coordinator's balance snapshot and a verifier's independent balance snapshot, causing the two computed hashes to diverge and the signing request to be rejected.

### Finding Description
When a `KEYGEN` rotation occurs, `x/utss` emits a `FundMigrationInitiatedEventData` (old/current TSS pubkeys, chain, `GasPrice`, `GasLimit`, `L1GasFee`) but deliberately does **not** fix the balance/amount to sweep at initiation time [1](#0-0) .

The coordinator later builds the signing request by querying the *live* balance of the old TSS address: [2](#0-1) 

Each UV that must co-sign independently rebuilds and verifies this same hash by calling `GetFundMigrationSigningRequest` with `Balance` unset, forcing a **fresh** `GetBalance` RPC call: [3](#0-2) 

`GetFundMigrationSigningRequest` computes `maxTransfer = balance - gasCost - l1GasFee` from whatever the live balance happens to be at query time: [4](#0-3) [5](#0-4) 

The comment in the code explicitly (and incorrectly, from a security standpoint) assumes this is safe: *"Fund migration only triggers when outbound is disabled and no pending outbounds remain, so the balance at signing time will equal the balance at broadcast time."* This assumption only accounts for the protocol's own outbound flow — it does not account for an external, unprivileged actor sending native tokens directly to the (public, well-known) old TSS address on the external chain at any time between the coordinator's query and a UV's independent verification query.

Because the resulting `maxTransfer` feeds directly into the EIP-155 transaction that is hashed and signed, any balance drift between the coordinator's snapshot and a UV's snapshot produces a different `SigningHash`, and the strict-equality check rejects the request: [6](#0-5) 

This is the direct analog of the UniswapHelper report: instead of comparing an on-chain balance (`localSCXBalance`) against a caller-supplied `rectangleOfFairness` with `==`, this code implicitly requires strict equality between two independently-observed live balances (via a hash-equality check) to accept the migration signing round. An attacker who sends dust native token to the old TSS address at any point during the multi-round TSS ceremony can perpetually desynchronize the balance views of the coordinator vs. the verifying UVs, since the TSS address is a plain, publicly observable EOA on the external chain that anyone can send funds to — no privileged access is required.

### Impact Explanation
This is a denial-of-service on the TSS key-rotation fund-migration process: an attacker can repeatedly and cheaply (cost of a dust transfer's gas fee on the external chain) prevent honest UVs from converging on a valid `SigningHash`/`TSSFundMigrationAmount`, blocking the sweep of retiring-key funds from the old TSS address to the new one. Since `KEYGEN` migrations are meant as periodic security rotations (limiting exposure of a potentially-compromised key), indefinitely stalling them undermines the protocol's key-security assumptions and its stated invariant that "any drift [in the computed value] breaks the TSS hash." Funds are not stolen and normal outbound/inbound flows for other chains are unaffected, but this materially disrupts the honest-validator TSS finalization path called out in scope ("wrong TSS event... migration outcome").

### Likelihood Explanation
Likelihood is limited by timing: the coordinator's balance query and the UVs' independent verification queries happen close together during one DKLS signing round, so the attacker must send the griefing transfer inside that narrow window (repeated attempts are cheap and can be automated/scripted against the known old-TSS address, and the process can be retried on every new signing round, giving the attacker many chances). Because retries with a fresh nonce/balance snapshot occur on failure, the exact reliability of "permanent" blocking versus "probabilistic, retried" blocking could not be fully confirmed from the available code (the retry/backoff scheduling logic outside the reviewed files was not inspected), so likelihood should be treated as moderate rather than certain.

### Recommendation
Fix the old-key TSS address's balance and computed sweep amount once, at `InitiateFundMigration` time (or at the first successful coordinator query), and persist it on the `FundMigration` record so all subsequent verifications by UVs compare against that persisted value instead of re-querying a potentially-changed live balance. Alternatively, require the sweep amount to be `>=` a minimum expected amount computed at initiation rather than requiring bit-for-bit equality of two independently observed balances, so that additional attacker-sent dust does not break consensus (mirroring the audit's own recommended `==` → `>=` mitigation). This preserves the "sweep the current balance" design while removing the strict-equality race that an unprivileged party can trigger by sending funds to a public address.

### Proof of Concept
1. Observe (or derive) the public old-TSS EOA address for the chain undergoing `KEYGEN` migration via `x/utss` events (`FundMigrationInitiatedEventData.OldTssPubkey` is emitted on-chain, from which the address is trivially derived, per `DeriveEVMAddressFromPubkey`) [7](#0-6) .
2. Wait for a `SIGN_FUND_MIGRATE` coordination round to begin (coordinator builds and broadcasts the setup message with its own freshly-queried balance) [8](#0-7) .
3. During the ceremony (before UVs finish verifying), send any nonzero amount of the external chain's native gas token directly to the old TSS EOA.
4. Each UV independently re-queries `GetBalance` for the old TSS address when running `verifyFundMigrationSigningRequest`, obtaining a balance that now includes the attacker's transfer, and computes a different `maxTransfer`/`SigningHash` than the coordinator's [9](#0-8) .
5. `verifyFundMigrationSigningRequest` rejects the coordinator's signing request due to hash mismatch, and the migration signing round fails; repeat step 3 on each subsequent retry to keep blocking the migration.

	var migrationData utsstypes.FundMigrationInitiatedEventData
	if err := json.Unmarshal(eventData, &migrationData); err != nil {
		return nil, nil, fmt.Errorf("failed to unmarshal fund migration event data: %w", err)
	}

	// Load old keyshare as a sanity check; keyID bytes are derived from the string.
	if _, err := c.keyshareManager.Get(migrationData.OldKeyID); err != nil {
		return nil, nil, fmt.Errorf("failed to load keyshare for old keyId %s: %w", migrationData.OldKeyID, err)
	}
	keyIDBytes := deriveKeyIDBytes(migrationData.OldKeyID)

	signingReq, err := c.buildFundMigrationTransaction(ctx, eventData, assignedNonce, nil /* query chain for balance */)
	if err != nil {
		return nil, nil, fmt.Errorf("failed to build fund migration transaction: %w", err)
	}

	participantIDs := make([]byte, 0, len(partyIDs)*10)
	for i, partyID := range partyIDs {
		if i > 0 {
			participantIDs = append(participantIDs, 0)
		}
		participantIDs = append(participantIDs, []byte(partyID)...)
	}

	setupData, err := session.DklsSignSetupMsgNew(keyIDBytes, nil, signingReq.SigningHash, participantIDs)
	if err != nil {
		return nil, nil, fmt.Errorf("failed to create fund migration sign setup: %w", err)
	}

	return setupData, signingReq, nil
}

// buildFundMigrationTransaction parses event data and returns the signing
// request for sweeping old-TSS funds to the current TSS. If claimedAmount is
// non-nil, the balance is reconstructed as amount + gas + L1 instead of
// queried from chain — used by the ACK verify path to rebuild the hash
// deterministically without racing a successful sweep.
func (c *Coordinator) buildFundMigrationTransaction(ctx context.Context, eventData []byte, assignedNonce *uint64, claimedAmount *big.Int) (*common.UnsignedSigningReq, error) {
	if assignedNonce == nil {
		return nil, fmt.Errorf("assigned nonce is required for fund migration transaction")
	}
	var migrationData utsstypes.FundMigrationInitiatedEventData
	if err := json.Unmarshal(eventData, &migrationData); err != nil {
		return nil, fmt.Errorf("unmarshal fund migration event data: %w", err)
	}
	oldTSSAddr, err := DeriveEVMAddressFromPubkey(migrationData.OldTssPubkey)
	if err != nil {
		return nil, fmt.Errorf("derive old TSS address: %w", err)
	}
	currentTSSAddr, err := DeriveEVMAddressFromPubkey(migrationData.CurrentTssPubkey)
	if err != nil {
		return nil, fmt.Errorf("derive current TSS address: %w", err)
	}
	if c.chains == nil {
		return nil, fmt.Errorf("chains manager not configured")
	}
	client, err := c.chains.GetClient(migrationData.Chain)
	if err != nil {
		return nil, fmt.Errorf("get client for chain %s: %w", migrationData.Chain, err)
	}
	builder, err := client.GetTxBuilder()
	if err != nil {
		return nil, fmt.Errorf("get tx builder for chain %s: %w", migrationData.Chain, err)
	}

	gasPrice := new(big.Int)
	gasPrice.SetString(migrationData.GasPrice, 10)
	l1GasFee := new(big.Int)
	l1GasFee.SetString(migrationData.L1GasFee, 10)

	var balance *big.Int
	if claimedAmount != nil {
		// balance = amount + gas + L1; inverse of computeFundMigrationTransfer
		balance = new(big.Int).Set(claimedAmount)
		balance.Add(balance, new(big.Int).Mul(gasPrice, new(big.Int).SetUint64(migrationData.GasLimit)))
		if l1GasFee.Sign() > 0 {
			balance.Add(balance, l1GasFee)
		}
	}

	return builder.GetFundMigrationSigningRequest(ctx, &common.FundMigrationData{
		From:     oldTSSAddr,
		To:       currentTSSAddr,
		GasPrice: gasPrice,
		GasLimit: migrationData.GasLimit,
		L1GasFee: l1GasFee,
		Balance:  balance,
	}, *assignedNonce)

func computeFundMigrationTransfer(balance, gasPrice *big.Int, gasLimit uint64, l1GasFee *big.Int) (*big.Int, error) {
	gasCost := new(big.Int).Mul(gasPrice, new(big.Int).SetUint64(gasLimit))
	totalFee := new(big.Int).Set(gasCost)
	if l1GasFee != nil && l1GasFee.Sign() > 0 {
		totalFee.Add(totalFee, l1GasFee)
	}
	maxTransfer := new(big.Int).Sub(balance, totalFee)
	if maxTransfer.Sign() <= 0 {
		return nil, fmt.Errorf("insufficient balance for gas: balance=%s gasCost=%s l1GasFee=%s",
			balance.String(), gasCost.String(), l1GasFeeString(l1GasFee))
	}
	return maxTransfer, nil
}
