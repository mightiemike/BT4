### Title
Unprivileged account can permanently freeze another account's gas key (and block account deletion) by inflating its balance above the burn cap - (File: runtime/runtime/src/access_keys.rs)

### Summary
`TransferToGasKeyAction` lets *any* account send NEAR into another account's gas key with no check that the caller controls the target account. An attacker can use this to push a victim's gas key balance above `GasKeyInfo::MAX_BALANCE_TO_BURN`, which permanently blocks that key from ever being deleted and can also permanently block deletion of the whole account, freezing the owner's ability to reclaim their balance via account deletion.

### Finding Description
`action_transfer_to_gas_key` only checks that the target `account_id`/`public_key` pair identifies an existing gas key; it never checks that the predecessor of the receipt (the caller) is the account owner or holds any permission over `account_id`: [1](#0-0) 

The corresponding action-validation function performs no sender/receiver relationship check either — it only gates the protocol feature: [2](#0-1) 

Gas key public keys are discoverable on-chain (access keys are listed via `view_access_key`/`view_access_key_list`), so an attacker only needs to know the victim's account id and the public key of one of its gas keys — both are public information.

Once the balance is inflated past the cap, two independent recovery paths for the victim are permanently blocked:

1. Deleting the specific gas key via `DeleteKey`: [3](#0-2) 

2. Deleting the whole account (which sums *all* gas-key balances on the account against the same cap): [4](#0-3) 

This is the same bug class as the referenced report: an unprivileged party can perform a cheap, permissionless state-mutating call against a *victim's* account (here, `TransferToGasKeyAction`, analogous to the 0-value `transfer` that resets `lastInteractedTimestamp`) which flips a gating condition (`balance > MAX_BALANCE_TO_BURN`, analogous to `lastInteractedTimestamp + 1 days < now`) used later to authorize the victim's withdrawal/removal action, and this can be repeated indefinitely since the mutation is always attacker-reachable and cheaper than the fix.

### Impact Explanation
Once a gas key's balance is pushed above the burn threshold:
- The specific gas key can never be deleted (`DeleteKey` permanently fails with `GasKeyBalanceTooHigh`), permanently occupying its storage slot and access-key nonce entries — the owner can never reclaim the storage stake tied to that key or rotate it away.
- If the inflated key is the account's only gas key (or the sum of gas-key balances on the account exceeds the cap), `DeleteAccount` permanently fails as well, meaning the owner can never delete the account and never trigger the balance refund to a beneficiary (`Receipt::new_balance_refund`) that normally happens on deletion.

This is a concrete, transaction-triggered, permanently frozen-funds condition reachable by any unprivileged account with minimal cost (the attacker just needs to fund the deposit once, above the cap, which by design is meant to be small so it can be safely burned — meaning the griefing cost is intentionally low).

### Likelihood Explanation
High. The attack requires only:
1. Public knowledge of the victim account id and one of its gas key public keys (obtainable via standard RPC view calls).
2. A single `TransferToGasKeyAction` transaction with a deposit above `MAX_BALANCE_TO_BURN`.

No access key, staking, or validator privilege is needed, and the action is available to any signer that can submit a transaction to the target account.

### Recommendation
Restrict `TransferToGasKeyAction` so that only the account owner (i.e., predecessor_id == account_id, or a signer already holding an access key on that account) can top up a gas key, similar to how `WithdrawFromGasKey` is expected to be self-authorizing. Alternatively, decouple the deletion/burn-cap check from externally-fundable balance by tracking "self-funded" vs "externally-funded" balance, or by allowing deletion to always succeed and simply forfeit/burn any balance regardless of size (removing the `MAX_BALANCE_TO_BURN` upper bound as a blocking condition rather than a hard failure).

### Proof of Concept
1. Victim account `victim.near` adds a gas key `pk_gas` via `AddKeyAction` with `GasKeyFullAccess` and a small `num_nonces` (see `add_gas_key`, `runtime/runtime/src/access_keys.rs:194-228`).
2. Attacker (any funded account, no relationship to `victim.near`) queries `view_access_key(victim.near, pk_gas)` via JSON-RPC to learn `pk_gas` is a gas key.
3. Attacker submits a transaction to `victim.near` containing `Action::TransferToGasKey(TransferToGasKeyAction { public_key: pk_gas, deposit: D })` where `D > GasKeyInfo::MAX_BALANCE_TO_BURN`. This succeeds unconditionally per `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257-288`), since there is no ownership check.
4. Victim later attempts `DeleteKey(pk_gas)` — `action_delete_key` → `delete_gas_key` returns `ActionErrorKind::GasKeyBalanceTooHigh` and the key is never removed (`runtime/runtime/src/access_keys.rs:93-111`).
5. If `pk_gas` is the only/aggregate-exceeding gas key on the account, victim's `DeleteAccount(beneficiary)` also fails with `GasKeyBalanceTooHigh` (`runtime/runtime/src/actions.rs:370-379`), permanently preventing the account from being deleted and its balance refunded to any beneficiary.

Note: I was unable to open `core/primitives-core/src/account.rs` directly (path not indexed under `core/primitives/src/account.rs`) to confirm the exact numeric value of `GasKeyInfo::MAX_BALANCE_TO_BURN`; its existence and blocking role are confirmed by the call sites cited above and by the repository's own documentation reference to it as a small (≤1 NEAR) burn cap.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
