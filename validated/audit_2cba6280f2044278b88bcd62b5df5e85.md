### Title
Webhook DoS via unauthenticated shop-domain forgery — HMAC does not bind `X-Shopify-Shop-Domain`/topic headers to the signed payload, allowing cross-tenant session deletion - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
This is a valid analog to the reported griefing pattern: a low-cost, unprivileged action lets an attacker impose an unwanted, state-changing effect (session invalidation) on a victim tenant, exactly like the original report where cheap unauthenticated `mint()` calls let an attacker impose `restrictActionUntil` on arbitrary victim addresses. Here, the equivalent "restriction" is deleting/losing the victim shop's offline access-token session by forging the identity fields of an otherwise HMAC-valid webhook request.

### Finding Description
`validateFactory` in [1](#0-0)  computes the webhook's authenticity solely from `validateHmacFromRequestFactory`, which HMACs only the **raw body** of the request with the app's shared secret: [2](#0-1) . The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers are only checked for **presence**, never for **integrity** — `checkWebhooksHeaders` merely calls `getRequiredHeader`, it never folds these header values into the HMAC computation: [3](#0-2) .

Because the app's `apiSecretKey` is shared across every shop that installs the app (it is not per-tenant), any merchant who legitimately installs the app can capture a genuinely-signed `(rawBody, hmac)` pair from a real webhook delivered to their own shop (e.g. by uninstalling the app to trigger `APP_UNINSTALLED`, whose body is typically `{}`). That attacker can then replay the exact same `rawBody` + valid `hmac` to the app's webhook endpoint while freely rewriting the unauthenticated `domain`, `topic`, and `webhookId` headers to name a victim shop and any topic they choose — the signature will still validate since it never covered those headers.

The forged `domain` field then propagates unauthenticated into the processing pipeline: `webhookCheck.domain` is passed straight to the handler callback in `callWebhookHandlers` [4](#0-3) , and into `ensureValidOfflineSession(params, check.domain)` in the framework adapters [5](#0-4) . In `shopify-app-express`, the built-in `APP_UNINSTALLED` handler is wired to `AppInstallations.delete(shopDomain)` [6](#0-5) , which looks up and deletes **all** sessions for the attacker-supplied `shopDomain` via `findSessionsByShop`/`deleteSessions` [7](#0-6)  — with no verification that the request actually originated from that shop.

### Impact Explanation
This is a functional analog to the original "griefing via arbitrary minting" report: a cheap, repeatable, unprivileged call that forces an unwanted state transition onto an arbitrary victim tenant. Here, an attacker (any merchant who has installed the app once) can forge an `APP_UNINSTALLED` webhook naming a completely different victim shop, causing:
- Deletion of the victim's offline access-token session, silently breaking the merchant's app functionality (background jobs, webhooks requiring an offline session, scheduled tasks) until they manually reinstall/re-authorize.
- Repeated, low-cost re-forging of this request re-triggers the DoS indefinitely, similarly to the report's "front-run every operation with `mint(1)`" pattern.
- Because `deliveryMethod` and `callback` execution rely purely on `topic` + unauthenticated `domain`, other custom app handlers keyed to shop-scoped side effects (e.g., disabling features, sending emails, revoking data) are similarly exposed to cross-tenant spoofing.

### Likelihood Explanation
Any actor who can install the app on at least one shop (a very low bar — free trial, dev store, etc.) can obtain a valid `(rawBody, hmac)` pair for a chosen webhook topic (particularly `APP_UNINSTALLED`, whose payload is fixed/empty and thus trivially reproducible). No secret needs to be leaked, no privileged access needed, and the forged request can be replayed against the shared public webhook endpoint at will. This satisfies the "accepted forged Shopify request" / cross-tenant analog criteria.

### Recommendation
- Bind the shop domain (and other identity-critical headers such as topic/webhook id) into the HMAC-signed material, or independently verify `domain` against a value the app already possesses/trusts for that delivery (Shopify's actual webhook signing does cover the domain implicitly via body+shared secret per topic in real deployments, but this library's `checkWebhooksHeaders` should not treat these headers as trusted just because the body's HMAC is valid).
- Before performing destructive actions (e.g., deleting sessions) in response to `APP_UNINSTALLED`, cross-check that the request's `domain` header matches an active session/install record independently verified through the Admin API or another authenticated channel, not solely webhook headers.
- Consider adding replay protection (nonce/webhook id de-duplication window) so a captured legitimate payload cannot be resent with different headers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Attacker uninstalls the app, causing Shopify to deliver a genuine `APP_UNINSTALLED` webhook with body `{}` and header `X-Shopify-Hmac-Sha256: <validHmac>` to the app's webhook endpoint (captured via own logs/proxy).
3. Attacker resends the identical body + `X-Shopify-Hmac-Sha256` header to the same endpoint, but changes `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic: app/uninstalled`.
4. `validateFactory` accepts the request because `validateHmacFromRequestFactory` only checks `(rawBody, hmac)`, ignoring the `domain`/`topic` header [8](#0-7) .
5. The `APP_UNINSTALLED` handler executes `AppInstallations.delete('victim-shop.myshopify.com')`, deleting the victim's stored session(s) [7](#0-6) , without the victim ever having uninstalled the app.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
