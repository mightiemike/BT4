### Title
Attacker-triggered `prune_by_deployment_slot` forces O(total cache keys) work per failed-deploy transaction - (File: program-runtime/src/loaded_programs.rs)

### Finding Description
`ProgramCache::prune_by_deployment_slot` is implemented as an unconditional scan of the entire second-level entries map (`for second_level in entries.values_mut() { second_level.slot_versions.retain(...) }`) followed by a full-map cleanup pass in `remove_programs_with_no_entries`, rather than looking up and pruning only the specific program key associated with the deployment being rolled back. This function is invoked from `runtime/src/bank.rs` whenever a transaction that speculatively inserted a program cache entry (e.g., an upgradeable-loader deploy/upgrade) fails and is rolled back on a given slot, so that the speculative entry for that slot is removed from the global cache. Because the routine iterates `entries.values_mut()` — the map of every distinct program key known to the validator-wide `ProgramCache`, not just the key touched by the failing transaction — its cost scales with the total number of distinct program entries `M` present in the cache at the time, regardless of which single key the attacker's transaction actually touched. An attacker only needs to repeatedly submit a normal, permissionless (upgradeable-loader) deploy transaction that they cause to fail/roll back on the same slot; each such transaction, which the attacker pays a fixed fee for, drives one full O(M) sweep of the shared cache populated by all other users' programs.

### Impact Explanation
This is a disproportionate CPU-cost issue: transaction fees are fixed/local to the attacker's own transaction, but the cost imposed by `prune_by_deployment_slot` scales with the size of the entire validator-global program cache (`M`), which is populated by unrelated users. This decouples cost from fees paid and falls into the "disproportionate CPU cost" bounty category rather than requiring any privileged access — the attacker only needs the ability to submit program-deploy transactions that fail/roll back on a chosen slot, which is within normal unprivileged user capability.

### Likelihood Explanation
The precondition — causing a program deployment transaction to fail and roll back on a specific slot — is achievable by an ordinary user (e.g., structuring the deploy so a later instruction in the same transaction fails, or triggering an error path in the upgradeable loader after the speculative cache entry has been created). This can be repeated across many slots to repeatedly trigger the full-cache scan, and the cost grows as the shared program cache grows from ordinary cluster activity, making the attack cheap and repeatable relative to its impact.

### Recommendation
Change `prune_by_deployment_slot` (and its caller in `bank.rs`) to take the specific program key that was speculatively inserted and prune only that key's second-level entry via a direct map lookup/removal, instead of iterating `entries.values_mut()` for the whole cache. If a full-cache sweep is still needed for other invariants, decouple it from the per-transaction rollback path (e.g., batch/periodic pruning) so a single attacker-paid transaction cannot force an O(M) global scan.

### Proof of Concept
Rust benchmark/integration test plan in `program-runtime/src/loaded_programs.rs` tests module:
1. Construct a `ProgramCache` and insert `M` synthetic entries under `M` distinct "other user" program keys (varying `M`, e.g., 100, 10_000, 100_000).
2. Insert one additional entry under an "attacker" key with `deployment_slot = S`.
3. Measure wall-clock/instruction count of calling `prune_by_deployment_slot(S)` (simulating the rollback of the attacker's single failed deploy transaction).
4. Assert that the measured cost scales linearly with `M` (i.e., grows well beyond a constant/O(1) bound tied only to the attacker's own key), demonstrating that a single attacker transaction's rollback cost is proportional to the entire cache size rather than to the attacker's own footprint or fee paid.
