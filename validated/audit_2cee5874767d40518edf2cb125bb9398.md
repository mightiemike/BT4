### Title
Unhandled exception in `sanitizeHost` via malformed base64 `host` param crashes unauthenticated OAuth/embedded-bootstrap paths - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`sanitizeHost` validates only the character set of the `host` parameter with `base64regex` before calling `decodeHost` (`atob`) and `new URL('https://' + decoded)`, with no `try/catch` around either call. [1](#0-0)  An attacker-controlled `host` query parameter that passes the loose regex but decodes to an invalid-length base64 payload or to a hostname string that the WHATWG URL parser rejects (invalid IDNA/forbidden host code points) will cause `atob` or `new URL` to throw synchronously, and this exception propagates out of `sanitizeHost` uncaught.

### Finding Description
`sanitizeHost`'s `base64regex = /^[0-9a-zA-Z+/]+={0,2}$/` only checks the character alphabet and optional padding — it does **not** enforce that the base64 string length is a multiple of 4, nor that the padding is well-formed. [2](#0-1)  This means strings such as a single character (`"a"`) satisfy the regex but are invalid base64, and `decodeHost` (`atob(host)`) can throw a `DOMException`/`InvalidCharacterError` for such input. [3](#0-2)  Separately, even when `atob` succeeds, the decoded string is fed directly into `new URL('https://' + decodeHost(sanitizedHost))` with no `try/catch`; the WHATWG URL parser throws a `TypeError` ("Invalid URL") for hostnames with forbidden host code points or invalid IDNA/punycode sequences. [4](#0-3)  Neither path is wrapped in a `try/catch`, so both cases throw out of `sanitizeHost` instead of returning `null`.

This function is reachable from multiple unauthenticated entry points that take `host` straight from the query string of the request:
- `redirectToAuth` → `clientSideRedirect` in shopify-app-express calls `api.utils.sanitizeHost(req.query.host as string)` directly off an unauthenticated `/auth` (or embedded bootstrap `embedded=1`) request. [5](#0-4) 
- `validateShopAndHostParams` in shopify-app-remix calls `api.utils.sanitizeHost(url.searchParams.get('host')!)` on every embedded-app authenticate call before any session/HMAC validation. [6](#0-5) 
- `buildEmbeddedAppUrl`/`getEmbeddedAppUrl` call `sanitizeHost(config)(host, true)` on the `host` query parameter taken from the raw request before any authentication. [7](#0-6) 

None of these callers wrap the `sanitizeHost` call in a `try/catch`; they only check the return value for `null`/falsy, expecting a graceful failure, not an exception. The existing unit tests (`shop-validator.test.ts`) only cover regex-charset mismatches (e.g., `'plain-string-is-not-base64'` containing a hyphen) and never exercise a string that is regex-valid but decodes to a malformed/invalid host, so this gap is not caught by existing tests. [8](#0-7) 

### Impact Explanation
An unauthenticated attacker can send a single crafted request to an app's `/auth` route (or any embedded-bootstrap/authenticate route) with a `host` query parameter chosen to trigger an uncaught exception inside `sanitizeHost`. Depending on the framework's error handling for synchronous throws inside request handlers, this results in an unhandled exception per request at minimum (a 500 rather than a clean redirect/`null` handling), and in frameworks/deployments where such a throw escapes the framework's own error boundary (e.g., inside an `async` handler where the rejection is not caught upstream), it can crash the Node process — a denial-of-service against the authentication entry point. This matches the "DoS in an authentication handler" impact class called out in scope.

### Likelihood Explanation
This requires no privileges: default configuration, an anonymous HTTP GET to the standard `/auth` or embedded-bootstrap route with a crafted `host` parameter is sufficient. The `base64regex` gap (missing length/padding validation) and the missing `try/catch` around `new URL` are both present unconditionally in `sanitizeHost`, so the issue is trivially repeatable and does not depend on any secret or non-default setting.

### Recommendation
Wrap the `decodeHost`/`new URL` logic inside `sanitizeHost` in a `try/catch`, returning `null` (or throwing `InvalidHostError` only when `throwOnInvalid` is set) on any decode/parse failure. Additionally, tighten `base64regex` to require proper base64 length (multiple of 4) so `atob` cannot be reached with a structurally invalid payload.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts
test('does not throw for malformed base64 host', () => {
  const shopify = shopifyApi(testConfig());

  // "a" satisfies base64regex but is invalid base64 length -> atob throws
  expect(() => shopify.utils.sanitizeHost('a')).not.toThrow();
  expect(shopify.utils.sanitizeHost('a')).toBeNull();
});

test('does not throw for host decoding to invalid hostname', () => {
  const shopify = shopifyApi(testConfig());

  // Bytes that decode to control chars / invalid host code points,
  // making `new URL('https://' + decoded)` throw a TypeError.
  const malformed = Buffer.from([0x00, 0x01, 0xff, 0xfe]).toString('base64');

  expect(() => shopify.utils.sanitizeHost(malformed)).not.toThrow();
  expect(shopify.utils.sanitizeHost(malformed)).toBeNull();
});
```
Both assertions currently fail (the calls throw instead of returning `null`), confirming the uncaught-exception path in `sanitizeHost`.
