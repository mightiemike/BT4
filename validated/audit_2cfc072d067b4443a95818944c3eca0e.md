### Title
`DeleteAccountAction.beneficiary_id` is never validated for existence, permanently burning the account's balance when the refund fails - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_delete_account` unconditionally deletes the account and unconditionally emits a `Receipt::new_balance_refund` to `delete_account.beneficiary_id`, with no check that the beneficiary account exists or can accept the transfer. If the beneficiary does not exist, the resulting refund receipt fails, and per the documented refund semantics a failed refund is burnt rather than returned to anyone. This mirrors the IMA finding's root cause: an irreversible value-moving action is dispatched to an unvalidated destination, and when that destination cannot process the resulting message, the value is permanently lost instead of failing atomically up-front.

### Finding Description
`action_delete_account` computes the account's balance and pushes an unconditional balance-refund receipt to the caller-supplied `beneficiary_id`, then deletes the account and clears it, all before the refund receipt is even attempted: [1](#0-0) 

There is no existence check on `beneficiary_id` in either `check_actor_permissions` or in `action_delete_account` itself — permission checks only verify the actor and staking lock, not whether `beneficiary_id` is even a real account: [2](#0-1) 

The public spec confirms the only validation performed on `beneficiary_id` is format validation (`InvalidAccountId`), never existence: [3](#0-2) 

Balance-refund receipts are refund receipts (`predecessor_id == "system"`), and refunds are explicitly barred from creating any account — including implicit ones — so a refund to a nonexistent `beneficiary_id` cannot fall back to implicit account creation: [4](#0-3) 
This is directly exercised by a test showing a refund to a missing `0u` (universal/implicit) account fails with `AccountDoesNotExist` rather than creating the account or bouncing the funds anywhere: [5](#0-4) 

Per the documented refund semantics, when execution of a refund receipt fails, the refund amount is burnt, not retried or returned to the deleted account (which no longer exists) or to anyone else: [6](#0-5) 

An integration test explicitly acknowledges this hazard in a comment, confirming the beneficiary must pre-exist or the transferred balance is lost: [7](#0-6) 

This is structurally the same bug class as the reported IMA issue: `_exit()` unconditionally debits/burns the sender-side token and dispatches to an unvalidated destination (`MAINNET_HASH`) whose receiver contract cannot process the resulting message type, permanently losing the value. Here, `action_delete_account` unconditionally destroys the account and dispatches an irreversible transfer to a caller-supplied, unvalidated `beneficiary_id`; if the destination cannot receive it (does not exist, and is barred from implicit creation via refund), the value is burnt with no possibility of recovery.

### Impact Explanation
A user who submits a single `DeleteAccountAction` with a mistyped, unregistered, or not-yet-created `beneficiary_id` irreversibly loses their account's entire remaining NEAR balance: the account is deleted first, and the refund to the invalid beneficiary is burnt rather than bounced back. Unlike ordinary failed actions (which roll back and refund the caller), this specific action commits the deletion unconditionally and only then discovers the beneficiary is unreachable, at which point there is no account left to refund and the funds are destroyed. This is "permanently frozen/lost funds" as called out by the acceptance criteria, triggered by a single unprivileged signed transaction.

### Likelihood Explanation
Reachable directly by any transaction signer via a single `DeleteAccount` action in a transaction they sign, with the beneficiary field entirely attacker/user-controlled and unchecked ahead of time. No special privileges, node cooperation, or multi-step setup are required — only a typo or reference to a not-yet-created (e.g., not-yet-funded implicit) account is sufficient to trigger permanent loss.

### Recommendation
Before deleting the account and burning its balance, validate that `beneficiary_id` refers to an existing account (or an implicit account type that a normal transfer could create), and reject the `DeleteAccount` action with an explicit error (e.g., `BeneficiaryDoesNotExist`) if it does not, mirroring the recommended fix in the IMA report of rejecting transfers to destinations known to be unable to process them, rather than silently burning value after an irreversible state change.

### Proof of Concept
1. Create account `victim.near` with a non-zero balance.
2. Sign and submit a transaction from `victim.near` containing a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "does-not-exist.near" })` (or an implicit-account-id string that has never been funded).
3. `action_delete_account` runs: it reads `victim.near`'s balance, pushes `Receipt::new_balance_refund("does-not-exist.near", balance)`, deletes `victim.near` from state (`remove_account`), and returns success for the `DeleteAccount` action itself — [8](#0-7) .
4. In a subsequent receipt application, the refund receipt executes against `does-not-exist.near`; because refunds cannot trigger implicit account creation ( [4](#0-3) ), the `Transfer` action fails with `AccountDoesNotExist`.
5. Per the documented refund-failure rule, the balance is burnt rather than refunded anywhere ( [6](#0-5) ): `victim.near` no longer exists, `does-not-exist.near` never received the funds, and the tokens are permanently gone from circulation with no recipient — an unrecoverable, self-inflicted loss triggered entirely by one signed transaction with no upfront validation of the destination.

```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```
