### Title
Permanent lock of NEAR transferred to a deterministic (`0s…`) account backed by a global contract without a withdrawal path - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
Deterministic accounts (NEP-616, `0s…` ids) are, by protocol design, accounts that never receive an access key: their only authority is whatever `GlobalContractIdentifier` code is committed to by their `DeterministicAccountStateInit`. Any unprivileged signer can send a plain `Transfer` action to such an id, which — exactly like Solidity's implicit `receive()` — silently credits the account's balance with no logic attached. If the global contract code referenced by that deterministic account never issues a `Transfer`/`FunctionCall` promise to move funds elsewhere (mirroring BathBuddy's `receive()` with no corresponding withdrawal method), the deposited NEAR is permanently unrecoverable: there is no access key to sign a withdrawal transaction, and the protocol provides no other way to move balance out of an account other than through the account's own signed transactions or contract-issued promises.

### Finding Description
A `Transfer` action addressed to an as-yet-nonexistent deterministic account id is permitted to create the account on its own (`implicit_creation_allowed`), before any `DeterministicStateInitAction` ever runs: [1](#0-0) 

When the account is later (or already) initialized, `action_deterministic_state_init` only ever installs the referenced global-contract code and the state's key/value `data`; there is no field for, and no code path that installs, an access key: [2](#0-1) 

This matches the documented data model: `DeterministicAccountStateInitV1` carries only `code: GlobalContractIdentifier` and `data: BTreeMap<Vec<u8>, Vec<u8>>` — no key material at all: [3](#0-2) 

The protocol explicitly forbids ever adding a key to such an account through a batched transaction, closing off any recovery path: [4](#0-3) 

Consequently, the *only* way NEAR held by a deterministic account can ever leave it is via a `Promise`/`Transfer` issued by the deployed global contract's own code. If that contract (which anyone can reference via `GlobalContractIdentifier::AccountId`/`CodeHash` when deriving a new deterministic account address) exposes no such withdrawal logic — e.g. a contract like `near-test-contracts/sharded-contract`, whose only exported method (`spread`) creates further sub-accounts and never transfers funds back out — [5](#0-4) 
then any `Transfer` (implicit-creation transfer, post-init top-up transfer, or excess deposit beyond storage-staking that isn't automatically refunded) sent to that account's derived id is permanently locked. This is the direct protocol-level analog of BathBuddy's `receive()`: value can flow in through an ordinary, unprivileged action, but there is no protocol- or contract-level mechanism guaranteed to let it flow back out.

### Impact Explanation
This is a permanent, unrecoverable loss-of-funds condition (frozen funds) triggerable by any regular transaction signer with nothing more than a standard `Transfer` action targeting a publicly-derivable `0s…` account id. Because the account can never receive an access key, and the contract logic backing it is chosen by whoever authored the referenced global contract (which may be widely reused across many deterministic accounts, as encouraged by NEP-616's "shared code, many accounts" design), a single such contract missing a withdrawal path can trap NEAR sent to *every* account instantiated from it, indefinitely.

### Likelihood Explanation
High reachability: constructing a deterministic-account id only requires knowing (or choosing) a `DeterministicAccountStateInit` (code identifier + data), which is fully public/derivable off-chain, and then sending an ordinary signed `Transfer` transaction — no special privileges, relayer cooperation, or validator involvement needed. Because global contracts referenced by `GlobalContractIdentifier::AccountId` can also be silently redeployed/changed by their owner (per `GlobalContractDeployMode::AccountId` semantics) after users have already funded derived deterministic accounts expecting different code, the risk of ending up with a contract lacking withdrawal logic is not purely hypothetical misuse — it can also arise from a legitimate contract being redeployed without a withdrawal method, or from any of the many minimal/example global contracts used for NEP-616 testing being reused in production.

### Recommendation
- Require (or strongly enforce at the protocol/tooling level) that any global contract intended to back deterministic or universal accounts expose a canonical withdrawal/transfer-out entry point, or
- Provide a protocol-level escape hatch allowing an account's balance to be recovered when no access key exists and the contract exposes no relevant callable method (e.g., a documented "sweep" mechanism gated by proof of the original `DeterministicAccountStateInit` data), and
- Emit clear warnings/documentation for wallets and tooling constructing `Transfer`s to `0s…`/`0u…` ids without a known, audited withdrawal path in the target contract.

### Proof of Concept
1. Deploy (or reference) a global contract that exposes no method capable of issuing an outbound `Transfer`/payment promise, e.g. the `spread`-only contract at `runtime/near-test-contracts/sharded-contract/src/lib.rs`.
2. Derive a deterministic account id from a `DeterministicAccountStateInitV1 { code: <that contract>, data: <anything> }` (publicly computable, per `docs/DataStructures/Account.md:167-172`).
3. As any unprivileged account, send a `Transfer` action with a nonzero deposit to that derived id — this creates the account per `action_implicit_account_creation_transfer`/`implicit_creation_allowed` in `runtime/runtime/src/actions.rs`.
4. Optionally run `DeterministicStateInitAction` to fully initialize it (`runtime/runtime/src/deterministic_account_id.rs:15-52`) — no access key is ever installed.
5. Observe: the transferred balance can only be moved by a promise issued from the contract's own code; since no such promise exists, the funds remain in the account permanently, with no signer able to construct a valid outbound `Transfer` transaction (no access key exists) and no contract call available to trigger one.

        Some(account) => account,
