### Title
Unauthenticated JSON-RPC stack-overflow abort via deeply nested `serde_json::Value` in the `params`/`id` fields of a `Message` request - ([File: chain/jsonrpc-primitives/src/message.rs])

### Summary
The `nearcore` JSON-RPC endpoint (`/`, port 3030 by default) deserializes every inbound POST body into the `Message` enum before any method routing, authentication, or per-method validation occurs. The `Request.params` (and `id`) fields are typed as raw `serde_json::Value`, whose `Deserialize` implementation is an unbounded recursive-descent parser with no depth limit. A single small POST body containing a few thousand nested JSON arrays (e.g. `[[[[[...]]]]]`) drives this deserialization past the worker thread's stack guard page, and Rust's runtime responds with `std::process::abort()`, killing the entire node process — exactly the same bug class as the reported `scim_proto`/`kanidm_proto` PEG-parser stack exhaustion (CWE-248/400/674), reachable pre-auth over the network.

### Finding Description
`chain/jsonrpc-primitives/src/message.rs` defines:
```rust
pub struct Request {
    jsonrpc: Version,
    pub method: String,
    #[serde(default, skip_serializing_if = "Value::is_null")]
    pub params: Value,
    pub id: Value,
}
``` [1](#0-0) 

`Message::from_slice`/`from_str` parses the raw request bytes directly into this `Message` enum using `serde_json::de::from_slice`, i.e. deserialization of attacker-controlled bytes happens unconditionally before `JsonRpcHandler::process()` even inspects the `method` name: [2](#0-1) 

Per the architecture documentation, the JSON-RPC POST pipeline is:
1. `rpc_handler()` deserializes the body into a `Message`.
2. `process()` validates it's a `Request` and dispatches by `method`. [3](#0-2) 

Because `params`/`id` are generic `serde_json::Value`, the `Value` deserializer recurses once per nested array/object level with no depth counter — it is architecturally identical to the unbounded `peg::parser!` recursion described in the external advisory (`"(" e:parse() ")" { e }`), just implemented inside `serde_json`'s recursive-descent `Value` visitor instead of a hand-written PEG grammar.

The only documented mitigation on this endpoint is a request body size limit, not a nesting-depth limit:
> Middleware: CORS (configurable via `cors_allowed_origins`) and request body size limit (default 10MB). [4](#0-3) 

A payload of a few thousand nested brackets is only a few KB — well under the 10 MB limit — so the size guard does not prevent the attack, mirroring the report's observation that reverse-proxy header/body limits do not stop the crash either.

Critically, the JSON-RPC `/` endpoint requires **no authentication token, signed transaction, or access key** — any network caller can POST to it, matching the "single unauthenticated GET/POST" reachability requirement from the external report. This is distinct from the `DelegateAction`/meta-transaction recursion, which nearcore explicitly guards against via the `NonDelegateAction` wrapper type that rejects nested `Delegate`/`DelegateV2` variants at the Borsh level and caps `actions.len()` before validation recursion: [5](#0-4) [6](#0-5) 
That path is bounded to a single level of recursion and is not vulnerable. The JSON-RPC message-parsing path, however, has no equivalent depth check.

### Impact Explanation
A successful stack exhaustion during `Value` deserialization causes Rust's stack-overflow guard-page handler to invoke `std::process::abort()` (SIGABRT), which — unlike a panic — cannot be caught by `catch_unwind`/task isolation. This terminates the entire `neard`/RPC process, dropping all in-flight JSON-RPC queries, transaction submissions, and any client relying on that node for chain access. If the affected node is a validator's RPC-facing process or a widely used public RPC endpoint, this is a transaction/RPC-triggered denial of service against a production node with no privileges required, satisfying the "transaction-triggered halt" / availability-impact criteria.

### Likelihood Explanation
High likelihood of reachability: the JSON-RPC endpoint is enabled by default, requires no authentication, and accepts arbitrary POST bodies up to 10 MB, far more than the few KB needed to reach a few-thousand-deep nesting level. No feature flag or special configuration is needed to expose the vulnerable code path.

### Recommendation
- Enforce an explicit nesting-depth limit before/while parsing the JSON-RPC body — e.g., pre-scan bracket/brace nesting depth in `chain/jsonrpc-primitives/src/message.rs::from_slice`/`from_str`, or use a bounded/iterative JSON value type (or `serde_json`'s depth-limiting deserializer options) instead of the default recursive `Value`.
- Consider running request body deserialization inside a `spawn_blocking`/`catch_unwind`-protected context with a guarded, generously sized stack, and add a fuzz/regression test asserting that deeply nested JSON payloads are rejected with a normal parse error rather than aborting the process.

### Proof of Concept
```sh
python3 -c "
import json
body = '{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"status\",\"params\":' + '['*5000 + ']'*5000 + '}'
print(body)
" > payload.json

curl -sk -X POST http://127.0.0.1:3030/ \
  -H 'Content-Type: application/json' \
  --data-binary @payload.json
# Expected on vulnerable build: connection reset / empty reply,
# node process log shows "thread ... has overflowed its stack, fatal runtime error: stack overflow" and the neard process aborts (SIGABRT).
```
This targets the parsing pipeline described in `chain/jsonrpc/RPC_ARCHITECTURE.md` (`rpc_handler()` → `Message::from_slice` → `serde_json::Value` deserialization) before the `method`/`status` handler is ever invoked.
