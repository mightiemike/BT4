### Title
`VoteWitnessActuator` fails to deduplicate/merge witness votes, allowing repeated vote entries for the same witness - (File: `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

### Summary
The legacy (non-TVM) `VoteWitnessActuator.countVoteAccount()` iterates over the raw `VoteWitnessContract` vote list and appends each vote entry directly to the account's votes and the `VotesCapsule`'s new-votes list, without checking whether a witness address has already been added in the same list. This mirrors the reported NFTX bug class: failure to check for an existing entry (`_receiver`/witness) before adding it again, resulting in duplicated bookkeeping entries.

### Finding Description
In `countVoteAccount()`:
```java
voteContract.getVotesList().forEach(vote -> {
  votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
  accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
});
``` [1](#0-0) 

Each entry in the contract's vote list is appended as a new vote record for the owner account — there is no aggregation/merge keyed on `vote.getVoteAddress()`. This is confirmed by contrast with the newer TVM-native equivalent, `VoteWitnessProcessor.execute()`, which explicitly merges duplicate witness addresses into a `voteMap` before applying votes:
```java
voteMap.put(vote.getVoteAddress(),
    LongMath.checkedAdd(voteMap.getOrDefault(vote.getVoteAddress(), 0L), voteCount));
...
for (Map.Entry<ByteString, Long> entry : voteMap.entrySet()) {
  accountCapsule.addVotes(entry.getKey(), entry.getValue());
  votesCapsule.addNewVotes(entry.getKey(), entry.getValue());
}
``` [2](#0-1) 

The `validate()` method of `VoteWitnessActuator` also does not reject duplicate witness addresses within a single `VoteWitnessContract`; it only checks address validity, per-vote positive count, account/witness existence, and that the summed vote count does not exceed `tronPower`: [3](#0-2) 

Because the sum-vs-`tronPower` check sums every vote entry (duplicates included), an attacker cannot exceed their real TronPower in total, but they *can* split their existing TronPower across many repeated entries for the *same* witness. This is confirmed permitted behavior — the actuator's own test suite explicitly exercises "vote to the same witness multiple times" as a *supported* path (`vote1WitnssOneMoreTiems`, using `getRepeateContract` which adds the same witness address multiple times): [4](#0-3) 

### Impact Explanation
Unlike the original NFTX report (a permissioned function), this java-tron path is reachable by any unprivileged account via a `VoteWitnessContract` broadcast transaction. Repeated per-witness entries bloat the on-chain `AccountCapsule` votes list and `VotesCapsule` new-votes list stored for that account without any real gain by the caller (since total is capped by TronPower and, per the test, entries for the same witness end up counted cumulatively when the witness's vote total is computed at maintenance time). The primary consequence is state bloat / inconsistent list structure (many duplicate `Vote` entries for one witness address stored in the account and votes capsule) rather than an accounting overflow that benefits the attacker, since the final witness vote tally in `vote1WitnssOneMoreTiems` sums correctly to 10+30. This differs from the original NFTX finding where duplication caused a receiver to be paid twice; here, duplication causes redundant, unbounded-size vote-list state rather than a clear fund/accounting exploit, since the same TronPower budget still bounds the total.

### Likelihood Explanation
High reachability: any account holding frozen TRX (TronPower) can submit a `VoteWitnessContract` with up to `MAX_VOTE_NUMBER` (30) vote entries repeating the same witness address, and the actuator will accept and store all of them without complaint, as demonstrated by the actuator's own regression test.

### Recommendation
In `VoteWitnessActuator.validate()`, reject vote lists that contain duplicate `vote.getVoteAddress()` entries (as is effectively done via the `voteMap` merge in `VoteWitnessProcessor`), or merge duplicate witness votes during `countVoteAccount()` the same way `VoteWitnessProcessor.execute()` does, to keep the legacy and native contract-invocation paths consistent and avoid unbounded duplicate vote-list growth.

### Proof of Concept
1. Freeze balance to obtain TronPower for `OWNER_ADDRESS` (as in `voteCountsTest`/`vote1WitnssOneMoreTiems`).
2. Build a `VoteWitnessContract` with the same `WITNESS_ADDRESS` repeated N times (≤30), each with a small `vote_count`, via `getRepeateContract` pattern.
3. Call `VoteWitnessActuator.validate()` then `execute()` — both succeed, and `AccountCapsule.getVotesList()` / `VotesCapsule` end up storing N separate `Vote` entries for the same witness instead of one merged entry, as shown by the existing `vote1WitnssOneMoreTiems` test that passes with 30 duplicate entries for `WITNESS_ADDRESS`.
