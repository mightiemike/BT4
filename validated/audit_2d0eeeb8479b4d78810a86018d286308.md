### Title
Webhook `X-Shopify-Shop-Domain` Header Is Not Covered by HMAC Validation, Allowing Cross-Tenant Session Use via Replay - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`)

### Summary
Shopify webhook authentication in this library verifies only that the raw request body's HMAC matches (computed with the app's shared secret), but the `domain`/shop identity used afterward to select which merchant's session/access token gets attached to the request is read from an **unauthenticated header** that is never checked against the signed content, mirroring the reported bug class where an "order account" was never verified against the account actually used to execute the update.

### Finding Description
`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` computes the HMAC only over `rawBody` and the app secret via `validateHmacFromRequestFactory` [1](#0-0) , and only *after* the HMAC succeeds does it read the `X-Shopify-Shop-Domain` header via `checkWebhookHeaders`/`checkWebhooksHeaders`, which simply extracts the header value with no cryptographic binding to the signed payload [2](#0-1) . The underlying `validateHmacFromRequestFactory`/`validateHmacString` confirms the HMAC is computed strictly from `rawBody` and the secret, with no header data mixed in [3](#0-2) .

Downstream, `authenticateWebhookFactory` (both `shopify-app-remix` and `shopify-app-react-router`) takes `check.domain` — the very unauthenticated header value — and passes it directly to `ensureValidOfflineSession(params, check.domain)` to look up and attach that shop's offline session/access token to the webhook context [4](#0-3) . `ensureValidOfflineSession` loads or creates a session purely keyed off this `shop` string [5](#0-4) .

Because the HMAC only binds the body — not the domain — an attacker who is a legitimate (unprivileged) merchant of the same app can capture one of their own genuine webhook deliveries (valid `rawBody` + valid `hmac` for their own store, generated by Shopify using the shared app secret) and replay that exact `(rawBody, hmac)` pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to point at a different (victim) shop that also uses the app. The HMAC check still succeeds (it never inspects the domain), `checkWebhookHeaders` accepts the forged domain, and `ensureValidOfflineSession` loads the **victim's** offline session/access token, which is then exposed to the app's webhook handler as `session`/`admin` in the resulting `WebhookContext` [6](#0-5) . This is structurally identical to the reported analog: the "authenticated" identity (HMAC signer, i.e. shop that legitimately produced the body) is never checked against the identity ("domain" header) actually used to select the account/session acted upon.

### Impact Explanation
If an app's webhook handler acts on the payload data (attacker-controlled, since it's the attacker's own webhook body) using the `admin` GraphQL/REST client bound to the victim shop's session (attacker-selected via the forged domain header), the attacker can cause reads or writes against a victim merchant's store using the victim's access token — a cross-tenant access/session-confusion vulnerability reachable from an unprivileged, unauthenticated HTTP request (no admin/keeper privilege required, unlike the Blex report where the analogous execution was at least gated to keepers).

### Likelihood Explanation
Exploitability requires: (1) attacker's own store to be a legitimate install of the target app (trivial, self-signup), (2) the ability to trigger a real webhook to their own store and capture the raw body + HMAC, and (3) the ability to POST that raw body/HMAC pair to the app's public webhook endpoint with a modified domain header. All three are within reach of a single unprivileged merchant with basic HTTP tooling; no secrets need to be leaked and no MITM is required.

### Recommendation
Verify that the shop asserted by the `X-Shopify-Shop-Domain` header corresponds to a shop that is actually entitled to have generated the signed body — e.g., include the domain (and ideally webhook id/topic/timestamp) as part of the HMAC-covered data, or independently confirm (via a nonce/webhook-id uniqueness check plus a lookup that the topic/webhook subscription was registered for that specific domain) before using `domain` to select which session is attached to the webhook context. At minimum, reject requests where the resolved session's shop cannot be cryptographically tied to the specific webhook delivery.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Attacker performs a benign action on their own store that emits a subscribed webhook (e.g. `products/update`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value sent to the app's webhook endpoint.
3. Attacker resends an HTTP POST to the same webhook endpoint with the identical body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `validateFactory` (`packages/apps/shopify-api/lib/webhooks/validate.ts`) validates the HMAC successfully (body unchanged) and returns `domain: 'victim-shop.myshopify.com'` from the forged header.
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's offline session/access token into the webhook context passed to the app's handler. [7](#0-6) [4](#0-3)

  };

  config: ConfigInterface,
  data: string,

export function getCurrentTimeInSec() {

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
