The strongest analog to this Gravity Bridge bug in java-tron is the **incomplete PBFT equivocation-penalty logic** in `PbftMessageHandle.java`.

### Title
Double-signing (equivocation) by SR/witness nodes in PBFT consensus is detected but never penalized - (File: `consensus/src/main/java/org/tron/consensus/pbft/PbftMessageHandle.java`)

### Summary
Just as Gravity Bridge defined a `MsgSubmitBadSignatureEvidence` message intended to punish validators for signing conflicting/bad data but never wired it into the handler (making the anti-collusion mechanism a dead letter), java-tron's PBFT layer detects when a Super Representative (SR/witness) signs two different `PbftMessage` payloads for the same height/view (i.e., equivocation) but explicitly leaves the punishment logic unimplemented, marked only by a `// todo` comment.

### Finding Description
In `PbftMessageHandle.onPrepare()` and `PbftMessageHandle.onCommit()`, when a second vote is received for a key that's already been voted, the code compares the previously stored message's data against the new message's data. If they differ — meaning the same SR signed two different values for the same height/view, which is a classic Byzantine equivocation — the code contains only a comment stating the intent to penalize the behavior, with no actual implementation: [1](#0-0) [2](#0-1) 

Both branches simply `return` after the empty `//todo:Penalize multiple signatures at the same height` comment block, so the malicious SR suffers no consequence: no slashing, no evidence recording, no blacklist, nothing observable to the rest of the system. This mirrors the Gravity finding precisely: a security mechanism against Byzantine/malicious validator behavior is designed into the protocol's comments/intent but never actually implemented/wired up, so the disincentive against misbehavior does not exist in the shipped code.

The PBFT layer in java-tron is used to reach finality-like agreement on blocks (`DataType.BLOCK`) and on the SR list (`DataType.SRL`), with votes forwarded and processed by `PbftMsgHandler.processMessage()` [3](#0-2)  and results committed via `PbftMessageAction.action()` [4](#0-3) .

### Impact Explanation
Because equivocating SRs are not penalized, a malicious or colluding subset of SRs can double-sign conflicting PREPARE/COMMIT messages for the same view/height without cost. Since PBFT signatures are persisted and relied upon for block-finality attestation (`putBlockSignData`) and SR-list attestation (`putSrSignData`), an unpunished equivocating SR undermines the integrity guarantees the PBFT layer is meant to provide — the same "no disincentive to collude" concern flagged in the original Gravity finding, here applied to java-tron's PBFT-based finality/SRL agreement rather than to bridge withdrawals.

### Likelihood Explanation
The vulnerable code path is reached automatically any time a validator (SR) sends conflicting votes at the same height/view — no special privilege beyond being an SR is required to trigger the missing-penalty condition, and the detection logic that should trigger punishment is unconditionally reached; it just does nothing once triggered.

### Recommendation
Implement the intended penalty for equivocating SRs in `PbftMessageHandle.onPrepare()` and `onCommit()` — e.g., recording verifiable evidence of the conflicting signed messages and applying an on-chain slashing/exclusion mechanism analogous to what Gravity's `MsgSubmitBadSignatureEvidence` was meant to provide, rather than leaving the branch as a no-op with only a TODO comment.

### Proof of Concept
1. Have an SR (witness) sign and broadcast a `PbftMessage` (PREPARE or COMMIT) for view/height `X` with data `A`.
2. Have the same SR sign and broadcast a second `PbftMessage` for the same view/height `X` with different data `B`.
3. Trace execution: `pareVoteMap.containsKey(key)` (or `commitVoteMap.containsKey(key)`) is true, the stored data differs from the new data, entering the `//todo:Penalize multiple signatures at the same height` block, which does nothing before returning. [1](#0-0)  No slashing, evidence record, or any punitive action is ever taken against the offending SR.

  public void action(PbftMessage message, List<ByteString> dataSignList) {
    switch (message.getDataType()) {
      case BLOCK: {
        long blockNum = message.getNumber();
        chainBaseManager.getCommonDataBase().saveLatestPbftBlockNum(blockNum);
        Raw raw = message.getPbftMessage().getRawData();
        chainBaseManager.getPbftSignDataStore()
            .putBlockSignData(blockNum, new PbftSignCapsule(raw.toByteString(), dataSignList));
        logger.info("commit msg block num is:{}", blockNum);
      }
      break;
      case SRL: {
        try {
          Raw raw = message.getPbftMessage().getRawData();
          chainBaseManager.getPbftSignDataStore().putSrSignData(message.getEpoch(),
              new PbftSignCapsule(raw.toByteString(), dataSignList));
          logger.info("sr commit msg :{}, epoch:{}", message.getNumber(), message.getEpoch());
        } catch (Exception e) {
          logger.error("process the sr list error!", e);
        }
      }
      break;
      default:
        break;
    }
  }
