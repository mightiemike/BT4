## Validated Finding

**Binding claimed broken:** `deposits_removed_by_remove_deposits == deposits_actually_included_in_committed_block(succeeded_in_apply_l2_block_txs)`

Tracing the code confirms this binding **is broken**.

`produce_l2_block_inner` fetches a batch of pending deposits unconditionally: [1](#0-0) 

That exact, unfiltered `deposit_data` slice is later passed to `remove_deposits` after block commit, with no per-deposit success tracking: [2](#0-1) 

Meanwhile, inside `process_sys_txs` (called transitively from `dry_run_transactions` → `produce_and_run_system_transactions`), any deposit whose `apply_l2_block_txs` call fails with `EvmSystemTransactionNotSuccessful` is explicitly caught, the working set is reverted, and the loop `continue`s **without** pushing the deposit's system transaction into `all_txs`: [3](#0-2) 

This means `all_txs`/`txs_to_run` (the transactions that are actually re-applied and committed to chain state at lines 573–580) can be a **strict subset** of the original `deposit_data` batch — yet `remove_deposits` at line 638 operates on the full, unfiltered `deposit_data`, not on the subset that succeeded. There is no analogous `deposit_failed_txs` list (unlike `l1_fee_failed_txs` for user EVM transactions) that would let the caller exclude failed deposits before removal.

`remove_deposits` does clear the `pending_deposits` entry for the removed txid, so the exact permanence mechanism described in the question ("calc_tx_id would again collide") is not accurate — a manual resubmission via `citrea_sendRawDepositTransaction` is not blocked by a duplicate check. However, if the on-chain revert condition is deterministic (e.g., the deposit's Bitcoin SPV proof was valid against a Bridge/light-client state that has since been permanently superseded within the same block by a `BitcoinLightClientSetBlockInfo` system event, which is processed *before* deposit events in `produce_and_run_system_transactions`), any resubmission's `eth_call` simulation would fail identically, so the deposit could never be re-added to the mempool and its cBTC would never be minted — a real, demonstrable loss. [4](#0-3) 

### Title
Sequencer removes entire fetched deposit batch from mempool regardless of per-deposit on-chain success - (File: `crates/sequencer/src/runner.rs`)

### Summary
`produce_l2_block_inner` calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the raw, unfiltered batch returned by `fetch_deposits`, while `process_sys_txs` silently drops any deposit that reverts during `apply_l2_block_txs` from the actually-committed transaction list. There is no mechanism analogous to `l1_fee_failed_txs` to track and exclude failed deposits before calling `remove_deposits`, so a deposit that reverts on-chain during block building is still permanently removed from the sequencer's FIFO deposit queue without ever minting cBTC.

### Finding Description
The broken binding is: `removed_deposits (deposit_data, full batch) != minted_deposits (subset in txs_to_run that succeeded in process_sys_txs)`. The sequencer fetches deposits at `crates/sequencer/src/runner.rs:517-520`, passes them through `dry_run_transactions`, and inside `process_sys_txs` (`crates/sequencer/src/runner.rs:1678-1702`) any deposit failing with `EvmSystemTransactionNotSuccessful` is reverted and skipped from `all_txs` — meaning it is never included in the committed block and never credits cBTC. Despite this, `produce_l2_block_inner` (`crates/sequencer/src/runner.rs:636-643`) unconditionally calls `remove_deposits(&deposit_data)` on the entire original batch, deleting the failed deposit's entry from both `accepted_deposit_txs` and `pending_deposits` (`crates/sequencer/src/deposit_data_mempool.rs:79-109`). No existing guard (`BitcoinVerifier`, `Auth`, fork rules) touches this purely sequencer-local bookkeeping path, since it operates entirely off-chain in the sequencer's in-memory mempool.

### Impact Explanation
A legitimate depositor whose deposit passes the initial `eth_call` simulation in `send_raw_deposit_transaction` (`crates/sequencer/src/rpc.rs:329-388`) but reverts later during actual block-building (e.g., due to a state change between simulation time and inclusion time within `produce_and_run_system_transactions`, such as a `BitcoinLightClientSetBlockInfo` event processed just before the deposit event in the same block) has their deposit data dropped from the queue without cBTC ever being minted. Since `remove_deposits` also clears the `pending_deposits` de-duplication entry, the same deposit bytes can technically be resubmitted, but if the revert condition is deterministic the resubmission's `eth_call` will fail identically forever, making it impossible to get the deposit re-accepted into the mempool — resulting in a Bitcoin-side deposit that can never be minted on L2. This affects one deposit per occurrence and is not attacker-repeatable at will, but it is a real, silent asset-loss bug in the sequencer's own bookkeeping.

### Likelihood Explanation
Requires no attacker privilege — only a normal deposit submission via `citrea_sendRawDepositTransaction` combined with a state transition (e.g., another system event or deposit processed in the same block) that changes the outcome between simulation and inclusion. This is a naturally-occurring race in normal sequencer operation rather than something requiring adversarial resources; no BTC/cBTC cost is needed beyond a normal deposit.

### Recommendation
Track per-deposit success explicitly (mirroring `l1_fee_failed_txs`) during `process_sys_txs`/`produce_and_run_system_transactions`, and propagate only the successfully-applied deposits back to `produce_l2_block_inner` so that `remove_deposits` is called only with the subset of `deposit_data` that was actually included and executed successfully in the committed block. Deposits that fail should remain in `accepted_deposit_txs`/`pending_deposits` (or be re-queued) for retry in a subsequent block rather than being dropped.

### Proof of Concept
`cargo test` in `crates/sequencer` (or an integration test in `bin/citrea/tests`) that:
1. Submits a deposit via `send_raw_deposit_transaction` whose `eth_call` simulation succeeds.
2. Before the deposit is included in a block, injects a second system event/state change (e.g., a `BitcoinLightClientSetBlockInfo` for the same L1 block range) that causes the deposit's `Bridge.deposit` call to revert inside `apply_l2_block_txs` during actual block production.
3. Asserts that after `produce_l2_block_inner` completes: (a) `deposit_mempool.lock()` no longer contains the deposit (i.e., `remove_deposits` removed it) — checking both `pending_deposits` and `accepted_deposit_txs` are empty for that entry, and (b) the intended recipient's cBTC balance via `Evm::account_info` remains zero, confirming the binding `removed_deposits == minted_deposits` is violated.
