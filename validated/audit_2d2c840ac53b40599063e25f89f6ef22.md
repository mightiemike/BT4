## Analysis

The reported EthBridge.sol bug is a missing zero-address check on a user-supplied recipient parameter in a deposit function, leading to tokens being minted/locked at an address nobody can access. The equivalent invariant on Push Chain is: **inbound deposit/gas-topup execution must not mint value to an unusable/zero recipient**.

I traced the inbound validation and execution pipeline in `x/uexecutor`:

- `Inbound.ValidateForExecution` in [1](#0-0)  only checks that `Recipient` is non-empty and passes `utils.IsValidAddress(p.Recipient, utils.HEX)` for `TxType_FUNDS` / `TxType_GAS`.
- `IsValidAddress(..., HEX)` delegates to `common.IsHexAddress`, which only validates hex-string format/length — it does **not** reject the zero address [2](#0-1) .
- `ExecuteInboundFunds` then calls `common.HexToAddress(inbound.Recipient)` directly and mints PRC20 to that address via `depositPRC20` → `CallPRC20Deposit` with no additional zero-address guard [3](#0-2) .
- The same pattern exists for `TxType_GAS` (gas top-up deposit+autoswap) in `ExecuteInboundGas`, and for the isCEA branches of `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload`, where the only recipient check is a `"0x"` prefix check, not a zero-address check [4](#0-3) .

Because `Recipient` is sourced from the external-chain deposit event (attacker-controlled — the attacker chooses the recipient when calling the source-chain bridge/gateway contract), an attacker can submit a deposit specifying recipient `0x000...000`. Honest Universal Validators will observe and vote this real event data through the normal quorum path, and the node will accept it and mint PRC20 (or gas-swap proceeds) directly to the zero address — an unrecoverable address on Push Chain's EVM, causing permanent loss of the bridged value with no revert/rescue path triggered (since the deposit call itself does not error).

### Title
Missing zero-address check on inbound `Recipient` causes permanent loss of bridged funds/gas top-up - (File: x/uexecutor/types/inbound.go, x/uexecutor/keeper/execute_inbound_funds.go, x/uexecutor/keeper/execute_inbound_gas.go)

### Summary
`Inbound.ValidateForExecution` and the downstream `ExecuteInboundFunds`/`ExecuteInboundGas`/isCEA payload execution paths validate that `Recipient` is a well-formed hex address but never reject the zero address (`0x000...000`). An external, unprivileged attacker who initiates a cross-chain deposit specifying the zero address as recipient on the source chain will have that inbound accepted by honest validators through the normal quorum/voting flow, after which Push Chain mints PRC20 tokens (FUNDS/CEA paths) or performs the gas-swap deposit (GAS path) directly to `0x0000000000000000000000000000000000000000`, permanently and irrecoverably burning the bridged value.

### Finding Description
`ValidateForExecution` performs recipient checks per `TxType`:
```go
case TxType_FUNDS, TxType_GAS:
    if strings.TrimSpace(p.Recipient) == "" { ... }
    if !utils.IsValidAddress(p.Recipient, utils.HEX) { ... }
``` [1](#0-0) 

`utils.IsValidAddress(addr, HEX)` is a thin wrapper over `common.IsHexAddress`, which only checks that the string is 40 hex characters (optionally 0x-prefixed) — the zero address passes this check [2](#0-1) .

For `TxType_FUNDS`, `ExecuteInboundFunds` converts the recipient directly and deposits PRC20 without any additional guard:
```go
receipt, err := k.depositPRC20(
    sdkCtx,
    inbound.SourceChain,
    inbound.AssetAddr,
    common.HexToAddress(inbound.Recipient),
    inbound.Amount,
)
``` [3](#0-2) 

For `TxType_GAS`, `ExecuteInboundGas` resolves/derives the UEA but for the plain (non-CEA) gas top-up path or edge cases where recipient resolution isn't strictly the deployed UEA, the eventual `CallPRC20DepositAutoSwap` target is still taken from resolved addresses without zero-checking the original recipient input feeding the flow [5](#0-4) .

For the isCEA branches of `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload`, the only recipient check is a `0x`-prefix string check before treating the value as the deposit target:
```go
if !strings.HasPrefix(strings.ToLower(utx.InboundTx.Recipient), "0x") {
    execErr = fmt.Errorf("recipient must be a valid hex address when isCEA is true")
} else {
    ueaAddr = common.HexToAddress(utx.InboundTx.Recipient)
    ...
    // EOA/non-UEA path still deposits when amount > 0
``` [6](#0-5)  — zero address is not a UEA and has no code, so it falls into the "EOA: just deposit" branch, minting funds to `0x0`.

Since `Recipient` originates from attacker-controlled calldata on the source chain (the deposit/lock call to the source-chain bridge contract), and honest validators simply relay what actually happened on-chain, this is fully reachable by an ordinary unprivileged user without any validator, relayer, or admin misbehavior.

### Impact Explanation
Funds (PRC20 minted representation of bridged assets) or the entire gas top-up amount are permanently and irrecoverably lost — minted to an address with no known private key and no rescue path is auto-triggered (the deposit call succeeds, so no `INBOUND_REVERT` outbound is created; for isCEA paths, failures don't even generate a revert outbound by design). This matches the "permanent freezing"/"unauthorized burn" of user or protocol-controlled funds impact category.

### Likelihood Explanation
Trivial and fully attacker-controlled: any user can initiate a deposit specifying the zero address as recipient in the deposit calldata on the source chain. No special privileges, timing, or validator collusion required — honest UVs will observe and report the event exactly as it happened, and the node will process it as designed.

### Recommendation
Add an explicit zero-address rejection for `Recipient` (and any other resolved deposit target such as `ueaAddr`) in `Inbound.ValidateForExecution` (`x/uexecutor/types/inbound.go`) for `TxType_FUNDS`, `TxType_GAS`, and the isCEA branches of `TxType_FUNDS_AND_PAYLOAD`/`TxType_GAS_AND_PAYLOAD`, e.g.:
```go
if strings.EqualFold(p.Recipient, EvmZeroAddress) {
    return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be the zero address")
}
```
This should fail validation the same way an empty/malformed recipient does today (producing a FAILED PCTx with revert outbound for non-isCEA types), preventing funds from ever being minted to an unrecoverable address.

### Proof of Concept
1. Attacker calls the source-chain bridge/lock contract's deposit function specifying `recipient = 0x0000000000000000000000000000000000000000` and a nonzero `amount`.
2. Honest Universal Validators observe this real on-chain event and submit `MsgVoteInbound` with `Inbound.Recipient = "0x0000000000000000000000000000000000000000"`.
3. Quorum is reached; `Inbound.ValidateForExecution` passes because the zero address is a syntactically valid hex address and non-empty.
4. `ExecuteInboundFunds` (or the GAS / isCEA payload equivalents) calls `common.HexToAddress("0x0...0")` and mints PRC20 (or performs the gas-swap deposit) to the zero address.
5. The PCTx records `"SUCCESS"`; no revert outbound is created (for FUNDS/GAS the deposit itself did not error; for isCEA paths, reverts are never generated by design). The bridged value is permanently lost.
