### Title
Missing non-negative/uint256 validation on `ObservedTx.GasFeeUsed` allows inflated gas-refund computation - (File: `x/uexecutor/types/msg_vote_outbound.go`)

### Summary
`MsgVoteOutbound.ValidateBasic` only checks that `ObservedTx.GasFeeUsed` is a non-empty string; it never checks that the value is a valid, non-negative `uint256` decimal string. [1](#0-0)  Downstream, `applyGasRefund` parses this attacker/observer-supplied string directly with `big.Int.SetString` and computes `refundAmount := gasFee - gasFeeUsed` after only checking `gasFee.Cmp(gasFeeUsed) <= 0`. [2](#0-1)  A negative `gasFeeUsed` value is never rejected, mirroring the reported 1inch class of bug where a signed value is used as if guaranteed non-negative before an unsigned arithmetic operation, inflating the computed amount.

### Finding Description
`ValidateBasic` for `MsgVoteOutbound` performs only an empty-string check on `observed_tx.gas_fee_used`: [1](#0-0) 

There is no `big.Int.SetString` + `Sign() < 0` guard analogous to what `Inbound.ValidateForExecution` correctly does for `Amount`. [3](#0-2) 

The value then flows into `applyGasRefund`:
```go
gasFeeUsed := new(big.Int)
if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok {
    return
}
if gasFee.Cmp(gasFeeUsed) <= 0 {
    return
}
refundAmount := new(big.Int).Sub(gasFee, gasFeeUsed)
``` [2](#0-1) 

`big.Int.SetString` happily parses negative decimal strings (e.g. `"-100"`), so `gasFeeUsed` can be negative. Since `gasFee` (a positive, protocol-computed quote) is always greater than any negative `gasFeeUsed`, the `Cmp` guard never blocks the negative-value path, and `refundAmount = gasFee - gasFeeUsed` becomes `gasFee + |gasFeeUsed|` — larger than the actual quoted `gasFee`. This value is then handed to `CallUniversalCoreRefundUnusedGas`, which performs a real PRC20/native-asset refund/mint through `DerivedEVMCall`. [4](#0-3) 

This is the direct structural analog of the reported bug: a value that should be constrained to a non-negative range (`int256`-like signed decimal string) is consumed by unsigned/positive-only arithmetic (`uint256`-style subtraction) without a sign check, producing an inflated result.

### Impact Explanation
If this value can ever be attacker-influenced (e.g., a bug or compromised client producing a malformed/negative `GasFeeUsed` string that a quorum of universal validators independently derive and vote on, or any future code path that forwards attacker-controlled data into `GasFeeUsed` without sanitization), the resulting refund amount can exceed the legitimately quoted `gasFee`, causing unauthorized over-minting/over-refunding of PRC20 or native gas-token funds. This corrupts refund accounting, one of the explicitly in-scope invariants ("corruption of ... gas fee accounting, refund accounting").

### Likelihood Explanation
Under the current, honest-universal-validator client implementation, `GasFeeUsed` is derived from `gasUsed * gasPrice` on EVM chains (both non-negative by construction) [5](#0-4) , and defaults to `"0"` for SVM/outbound observation building if empty. [6](#0-5)  I could not find, within the scope explored, a concrete unprivileged path where an ordinary external-chain user directly controls the string that ends up in `GasFeeUsed` such that it becomes negative — the honest-validator software always computes it from unsigned quantities. Therefore likelihood is **low/uncertain**: the missing validation is a genuine defense-in-depth gap (the message-level `ValidateBasic` should reject non-numeric/negative strings exactly as `Inbound.ValidateForExecution` does for `Amount`), but I could not confirm a concrete unprivileged attacker-reachable trigger that forces a negative `GasFeeUsed` through the current client code paths. This should be treated as a hardening gap rather than a confirmed exploitable vulnerability without further investigation into all producers of `OutboundObservation.GasFeeUsed` (including any custom/relayer-supplied paths not covered by my search).

### Recommendation
In `MsgVoteOutbound.ValidateBasic` (and/or `OutboundObservation` validation), parse `GasFeeUsed` with `big.Int.SetString` and reject if parsing fails or if `Sign() < 0`, matching the pattern already used in `Inbound.ValidateForExecution` for `Amount`. Additionally, add a defensive `Sign() < 0` check on `gasFeeUsed` inside `applyGasRefund` in `x/uexecutor/keeper/outbound.go` before computing `refundAmount`, so that even if an invalid value slips through message validation, the refund calculation cannot be inflated.

### Proof of Concept
1. Construct/observe a `MsgVoteOutbound` with `ObservedTx.GasFeeUsed = "-1000000000000000000"` (any negative decimal string) and `ObservedTx.Success = true` (satisfying the only other `ValidateBasic` requirements: non-empty `TxId`/`UtxId`, non-empty `TxHash`, `BlockHeight > 0`).
2. `ValidateBasic` passes because it only checks the string is non-empty. [1](#0-0) 
3. Once quorum is reached, `applyGasRefund` runs: `gasFeeUsed.SetString("-1000000000000000000", 10)` succeeds; `gasFee.Cmp(gasFeeUsed) <= 0` is false (gasFee positive > negative gasFeeUsed), so execution proceeds to `refundAmount := gasFee.Sub(gasFee, gasFeeUsed)`, yielding `gasFee + 1e18` instead of the correct (near-zero or negative-clamped) refund. [2](#0-1) 
4. `CallUniversalCoreRefundUnusedGas` is invoked with the inflated `refundAmount`, causing an over-refund/over-mint of the gas token to the recipient. [4](#0-3) 

Note: step 1's precondition — how a negative string would actually reach the vote message in production given the honest-validator client always computes `GasFeeUsed` from non-negative arithmetic — is not fully confirmed; this PoC demonstrates the code-level exploitability of the missing validation but not a confirmed unprivileged, end-to-end trigger path from ordinary user action alone.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}

// GetGasFeeUsed returns the gas fee used by a transaction on the EVM chain.
// Fetches the receipt for gasUsed and the transaction for gasPrice, then returns
// gasUsed * gasPrice as a decimal string. Returns "0" if not found.
func (tb *TxBuilder) GetGasFeeUsed(ctx context.Context, txHash string) (string, error) {
	hash := ethcommon.HexToHash(txHash)
	receipt, err := tb.rpcClient.GetTransactionReceipt(ctx, hash)
	if err != nil {
		return "0", nil
	}

	tx, _, err := tb.rpcClient.GetTransactionByHash(ctx, hash)
	if err != nil {
		return "0", nil
	}

	gasUsed := new(big.Int).SetUint64(receipt.GasUsed)
	gasPrice := tx.GasPrice()
	if gasPrice == nil || gasPrice.Sign() == 0 {
		return "0", nil
	}

	gasFeeUsed := new(big.Int).Mul(gasUsed, gasPrice)
	return gasFeeUsed.String(), nil
}
