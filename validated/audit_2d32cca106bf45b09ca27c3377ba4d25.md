### Title
Token-exchange auth strategy skips scope validation, letting legacy under-scoped offline/online sessions remain "active" - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts`)

### Summary
`Session.isActive()` optionally validates that the session's granted OAuth scopes still match the app's currently configured scopes, via the `scopes` parameter [1](#0-0) . This mirrors `MarketLib.assertMaxLeverage()` in the reference bug — a bound that's supposed to be enforced against the *current* admin-controlled configuration. But in the token-exchange strategy used by `shopify-app-remix` and `shopify-app-react-router`, the scope check is passed `undefined`, which unconditionally disables it.

### Finding Description
`Session.isScopeChanged(scopes)` explicitly short-circuits to `false` (i.e., "no change detected", scopes considered fine) whenever `scopes === undefined`: [2](#0-1) 

`Session.isActive()` uses that result to decide whether the token is usable: [3](#0-2) 

`TokenExchangeStrategy.authenticate()` (both in `shopify-app-remix` and `shopify-app-react-router`) calls this with `undefined` for the scopes argument: [4](#0-3) 

Contrast this with `AuthCodeFlowStrategy.authenticate()`, which correctly passes `config.scopes` so a scope mismatch forces re-auth: [5](#0-4) 

The root cause is structurally identical to the reported bug class: a security-relevant limit/check (`maxOpenLeverage` / required `scopes`) is enforced on one control path (`setPositionLeverage` / `AuthCodeFlowStrategy`) but silently bypassed on another path that reuses previously-issued/legacy state (`getPositionLeverage` from a stored position / `session.isActive(undefined, …)` on a stored session) instead of validating it against the current admin-configured value. When an app developer changes `scopes` in the app config (e.g., to remove an overly-broad legacy scope for security reasons, or the merchant's granted scopes on Shopify's side are reduced/out of sync), a merchant's existing offline/online session obtained via token-exchange is still treated as "active" and reused for admin API calls without ever checking that its `scope` string matches the app's newly configured scopes. Only expiry and access-token presence gate reuse; scope drift is invisible to this path.

### Impact Explanation
Apps using the token-exchange auth strategy (`shopify-app-remix`'s `authorization: 'token_exchange'` or `shopify-app-react-router` equivalents) will keep serving Admin API calls with a session whose granted scope set no longer matches (and may be broader or narrower than) what the developer currently expects/requires in `scopes` config. Because the developer-facing `scopes` API/`ensureInstalledOnShop`/redirect-to-reauth flow is bypassed, an app cannot rely on `authenticate.admin()` to guarantee scope freshness when using token exchange — this can let stale/broader-than-intended permissions be used against the Admin API for the lifetime of the offline token, silently defeating scope reductions performed for security hardening.

### Likelihood Explanation
This triggers automatically, with no attacker action needed, any time: (1) an app is configured to use token exchange (the modern default recommended strategy for embedded apps), and (2) the developer reduces `scopes` in `shopify.server.ts`/config after merchants have already installed with broader scopes. Since token-exchange sessions are typically long-lived (persisted `offlineSession`/`onlineSession` without forced expiry tied to scope config), this is a persistent state, not a one-off race.

### Recommendation
Pass the configured `config.scopes` into `session.isActive()` in `TokenExchangeStrategy.authenticate()` (mirroring `AuthCodeFlowStrategy`), so that a scope mismatch triggers a fresh `exchangeToken` call (and thus picks up the current scope set / forces re-consent) rather than silently reusing the stored session:
```ts
if (!session || !session.isActive(config.scopes, WITHIN_MILLISECONDS_OF_EXPIRY)) {
```

### Proof of Concept
1. Configure a `shopify-app-remix` app with `authorization: 'token_exchange'` and `scopes: ['read_products', 'read_orders']`.
2. Merchant installs; token exchange stores an offline session with `scope = 'read_products,read_orders'`.
3. Developer later tightens security and redeploys with `scopes: ['read_products']` only (removing `read_orders`), expecting `authenticate.admin()` to force a fresh authorization/token exchange reflecting the reduced scope.
4. A subsequent embedded-app request from the same merchant hits `authenticateAdmin()` → `getSessionTokenContext` → loads `existingSession` from storage → calls `strategy.authenticate(request, {session: existingSession, ...})`.
5. In `TokenExchangeStrategy.authenticate()`, `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` returns `true` (token not expired, has access token, scope check skipped) even though the session's `scope` no longer matches the app's current `config.scopes`.
6. The stale, over-scoped session is returned and used unchanged for Admin API calls — no re-exchange, no scope validation ever occurs, exactly analogous to a legacy leverage value being reused without validation against the new `maxOpenLeverage` limit.

  /**
   * Whether the session is active. Active sessions have an access token that is not expired, and has has the given
   * scopes if scopes is equal to a truthy value.
   */
  public isActive(
    scopes: AuthScopes | string | string[] | undefined,
    withinMillisecondsOfExpiry = 500,
  ): boolean {
    const hasAccessToken = Boolean(this.accessToken);
    const isTokenNotExpired = !this.isExpired(withinMillisecondsOfExpiry);
    const isScopeChanged = this.isScopeChanged(scopes);
    return !isScopeChanged && hasAccessToken && isTokenNotExpired;
  }

    scopes: AuthScopes | string | string[] | undefined,
  ): boolean {

      return false;
