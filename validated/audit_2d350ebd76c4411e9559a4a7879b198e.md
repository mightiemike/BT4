### Title
Signer vote for aggregate public key never enforces the prepare-phase voting window, allowing a stale/late vote to set a different aggregate key for an already-active reward cycle - (File: stackslib/src/chainstate/stacks/boot/signers-voting.clar)

### Summary
The `.signers-voting` contract defines `is-in-voting-window` to restrict `vote-for-aggregate-public-key` to the reward cycle currently being set up by the node (`last-set-cycle`) during its prepare phase, but this helper is **never called** by `vote-for-aggregate-public-key`. This is structurally the same root cause as the Ammplify `M-13` bug: a state value that should have been checked/consumed at the point of a state-changing action is instead left unchecked, so the operation proceeds using a state condition that is stale relative to what the check was designed to enforce.

### Finding Description
`.signers` tracks `last-set-cycle` — the most recently *prepared* reward cycle — and separately persists `cycle-signer-set` indefinitely, keyed by cycle number: [1](#0-0) 

`.signers-voting` defines the intended guard: [2](#0-1) 

`is-in-voting-window` checks that `reward-cycle` equals `last-cycle` (the cycle the node most recently set up) **and** that the current burn height is in the prepare phase. This is exactly the check needed to ensure a vote can only affect the *upcoming* cycle's aggregate key, during the correct window.

However, `vote-for-aggregate-public-key` never calls it: [3](#0-2) 

The only gating conditions present are:
- `(is-none (map-get? aggregate-public-keys reward-cycle))` — the key for that cycle hasn't been finalized yet.
- `(is-novel-aggregate-public-key key reward-cycle)` — the key buffer hasn't been used before.
- `get-signer-weight`, which only requires that `.signers get-signer-by-index reward-cycle signer-index` succeed and match `tx-sender` — i.e., that `cycle-signer-set` for that `reward-cycle` was set at some point in the past.

Since `cycle-signer-set` is never deleted, `get-signer-weight` (and thus a full vote) succeeds for **any historical reward-cycle number** whose signer set was ever computed, not just the one currently being prepared (`last-set-cycle`). Combined with the missing `is-in-voting-window` call, a signer subset that meets the 70% `threshold-consensus` for that historical/target cycle's weight can call `vote-for-aggregate-public-key` for a `reward-cycle` that has already started (or even one long past, as long as its `aggregate-public-keys` entry was never set), well outside the prepare-phase window the mechanism was designed to enforce.

This mirrors the Ammplify pattern precisely: a state field (`last-set-cycle` / `asset.timestamp`) is updated by one code path (`stackerdb-set-signer-slots` / `collectFees`) and a *different*, already-mutated or independently-persisted piece of state (`cycle-signer-set` weight table / already-reset `asset.timestamp`) is consumed by a second code path (`vote-for-aggregate-public-key` / `removeMaker`) without re-validating the temporal precondition (`is-in-voting-window` / pre-update duration) that the design intends to enforce.

### Impact Explanation
Any signer subset holding ≥70% of a *previously computed* reward cycle's weight can set (or attempt to set) `aggregate-public-keys` for that cycle at a time later than the intended prepare-phase window — including after the cycle has already begun using a different (or no) aggregate key. Because different nodes/signers may observe this state transition at different points relative to their own tenure/cycle processing, this is a minority-triggerable divergence in a piece of state (`get-approved-aggregate-key`) consumed elsewhere in the PoX signer-set/consensus flow, and can produce disagreement between signers about which aggregate key is authoritative for a cycle — a "committed state two nodes disagree on" style High-severity issue, bounded to the signer/aggregate-key subsystem rather than a full chain split.

### Likelihood Explanation
Reaching this requires only unprivileged signer transactions (no admin/majority needed): any coalition controlling 70% of a stale/target cycle's already-recorded weight can trigger `vote-for-aggregate-public-key` for that cycle at any later block, since neither `is-in-voting-window` nor any burn-height/-cycle freshness check is enforced in the public entry point. The precondition ("that cycle's signer set was computed and its key not yet finalized") is easy to satisfy because `cycle-signer-set` and unfinalized `aggregate-public-keys` entries persist indefinitely.

### Recommendation
Call `is-in-voting-window` (or an equivalent freshness check against `last-set-cycle` and the current prepare-phase burn height) as an `asserts!` inside `vote-for-aggregate-public-key`, exactly as its doc-comment states voting "must happen after the list of signers has been set... which occurs in the first block of the prepare phase" — i.e., restrict votes to `reward-cycle == (contract-call? .signers get-last-set-cycle)` during the prepare phase for that cycle.

### Proof of Concept
Conceptual (Clarity-level) sequence, since this repo section is boot-contract Clarity, not directly instrumentable via the indexed sources here:
1. Reward cycle `N`'s signer set is computed and stored in `.signers` `cycle-signer-set` at the appropriate prepare phase; `last-set-cycle` advances to `N`, then `N+1`, etc., as subsequent cycles are prepared.
2. No aggregate key was ever finalized for cycle `N` (`aggregate-public-keys` has no entry for `N`), e.g., voting stalled below threshold during `N`'s actual window.
3. Cycles pass; `last-set-cycle` is now far ahead of `N`, and mining/signing for cycle `N` has already occurred (using whatever fallback key logic exists for "no key").
4. Because `vote-for-aggregate-public-key` never checks `is-in-voting-window`, a signer coalition that held ≥70% weight in cycle `N`'s (still-persisted) `cycle-signer-set` can call `vote-for-aggregate-public-key` with `reward-cycle = N` at the current (much later) block height and successfully set `aggregate-public-keys[N]`, since the only checks (`is-none`, `is-novel-aggregate-public-key`, per-signer weight lookup) all still pass.
5. Any downstream consumer of `get-approved-aggregate-key` for cycle `N` that had already assumed "no key was set for N" now observes a late-arriving key, creating disagreement between components/nodes that read this state at different times.

(define-private (is-in-voting-window (height uint) (reward-cycle uint))
    (let ((last-cycle (unwrap-panic (contract-call? .signers get-last-set-cycle))))
        (and (is-eq last-cycle reward-cycle)
            (is-in-prepare-phase height))))
