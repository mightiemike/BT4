### Title
Per-scan obsolete-account list rebuild scales with total historical deletions, not live dead accounts - (File: accounts-db/src/account_storage_entry.rs, accounts-db/src/obsolete_accounts.rs)

### Summary
`AccountStorageEntry::obsolete_accounts` is a monotonically-growing `Vec<ObsoleteAccountItem>` (`ObsoleteAccounts::accounts`). Every time an account in the storage is superseded by a newer write (which can happen repeatedly for the same storage while it is still "alive enough" to avoid shrink), a new entry is *appended* to this vector; entries are never removed or compacted — only the file backing the whole storage is ever dropped in bulk. This mirrors the reported Solidity bug class: logical "deletion" that leaves the array populated with stale/inert entries, forcing every later scan to pay for the full historical size of the array instead of its live size.

### Finding Description
`ObsoleteAccounts::mark_accounts_obsolete` only pushes into `self.accounts`, never removes stale items: [1](#0-0) 

`AccountStorageEntry::excluded_offsets`, which is recomputed on **every** call to `scan_accounts`/`scan_accounts_without_data`, iterates the *entire* `obsolete_accounts` vector (`filter_obsolete_accounts(None)`) plus the tombstone set and rebuilds an `IntSet` from scratch each time: [2](#0-1) 

`filter_obsolete_accounts` itself is a linear scan with no bound on the underlying `Vec`'s length: [3](#0-2) 

`scan_accounts`/`scan_accounts_without_data` are invoked repeatedly and independently for the *same* storage over its lifetime by numerous hot paths — `construct_candidate_clean_keys` (clean), `get_unique_accounts_from_storage_for_shrink` (shrink evaluation), `exhaustively_verify_refcounts`, and snapshot/index generation: [4](#0-3) [5](#0-4) 

Crucially, whether a storage is eligible for shrink (which is the only mechanism that eventually discards the storage — and with it the `obsolete_accounts` list) is governed purely by the alive-byte ratio, not by the length of `obsolete_accounts`: [6](#0-5) 

This means a storage that stays just above the shrink ratio threshold (default `IndividualStore`/`TotalSpace` ratios) while individual accounts inside it keep getting superseded (each superseding event appends one more `ObsoleteAccountItem`, see `remove_dead_accounts`) can accumulate an arbitrarily large `obsolete_accounts` list over its lifetime, entirely decoupled from how many accounts are *currently* dead in it: [7](#0-6) 

Every subsequent `scan_accounts` call against that storage (clean passes, shrink evaluation, ancestor verification, snapshot writers) then pays the full O(n) cost of scanning the ever-growing obsolete list, exactly analogous to the reported Solidity pattern where "delete" only zeroes an element instead of shrinking/compacting the array, causing unbounded iteration cost to accumulate over the lifetime of the structure.

### Impact Explanation
This causes disproportionate, unbounded CPU cost on every account-storage scan for long-lived storages with churny accounts (repeated clean passes, shrink candidate evaluation, refcount verification, and snapshot writing all rescan the full obsolete list each time), without a corresponding decrease in memory/iteration footprint. In adversarial or heavy-churn conditions this degrades validator CPU efficiency for account scans/clean/shrink/snapshot generation, which are on the critical path for keeping up with the cluster — a "disproportionate storage and CPU cost" issue per the accepted impact categories.

### Likelihood Explanation
This triggers under ordinary operation whenever a storage's alive-byte ratio stays above the shrink threshold while individual accounts within it are repeatedly superseded (a common real-world pattern for storages holding a mix of hot and cold accounts). No malicious input is required, only sustained account churn concentrated in storages that don't yet qualify for shrink.

### Recommendation
Bound the growth of `ObsoleteAccounts::accounts`, e.g., by periodically compacting/removing entries whose stale bytes have already been accounted for, or by caching/incrementally maintaining the `excluded_offsets` `IntSet` on the `AccountStorageEntry` (updated on insert instead of rebuilt on every scan) so per-scan cost tracks live dead-entry count rather than the storage's full historical obsolete-account count. Alternatively, factor obsolete-list length (not just byte ratio) into shrink-candidacy so pathologically long-lived, high-churn storages are shrunk proactively.

### Proof of Concept
1. Create a storage at slot `S` containing many accounts (e.g. via `AccountsDb::store_for_tests`).
2. Repeatedly, over many subsequent rooted slots, overwrite one or two of the accounts originally in `S` (keeping the overall alive-byte ratio of `S` above the shrink threshold, e.g. by never touching the majority of accounts in `S`), and run `clean_accounts` after each root so each supersede event calls `remove_dead_accounts` → `mark_accounts_obsolete`, appending to `S`'s `obsolete_accounts` list.
3. Observe (e.g. via `AccountStorageEntry::obsolete_accounts()` in tests, as exercised by `test_calculate_storage_count_and_alive_bytes_obsolete_account` in `accounts-db/src/accounts_db/tests/impl.rs`) that the obsolete list length grows unboundedly with the number of supersede events while `S` never becomes a shrink candidate.
4. Measure `scan_accounts`/`scan_accounts_without_data` time on `S` (invoked e.g. via `clean_accounts_for_tests`, `exhaustively_verify_refcounts`, or snapshot generation) growing linearly with the number of historical supersede events rather than with `S`'s current live account count.

    /// Collect the offsets that should be excluded from scans
    fn excluded_offsets(&self) -> IntSet<Offset> {
        let mut offsets: IntSet<_> = self
            .obsolete_accounts_read_lock()
            .filter_obsolete_accounts(None)
            .map(|(offset, _)| offset)
            .collect();
        offsets.extend(self.tombstone_offsets_read_lock().iter().copied());
        offsets
    }

    /// Iterate over the alive accounts in this storage, excluding obsolete accounts and tombstones.
    /// The return value is the number of values excluded from the scan.
    pub(crate) fn scan_accounts<'a>(
        &'a self,
        reader: &mut impl RequiredLenBufFileRead<'a>,
        mut callback: impl for<'local> FnMut(Offset, StoredAccountInfo<'local>),
    ) -> Result<u64, AccountsFileError> {
        let excluded_offsets = self.excluded_offsets();
        let mut num_excluded = 0;
        self.accounts.scan_accounts(reader, |offset, account| {
            if excluded_offsets.contains(&offset) {
                num_excluded += 1;
                return;
            }
            callback(offset, account);
        })?;
        Ok(num_excluded)
    }

    pub(crate) fn is_candidate_for_shrink(&self, store: &AccountStorageEntry) -> bool {
        let total_bytes = store.written_bytes();
        let alive_bytes = self.alive_bytes_after_shrink(store) as u64;
        match self.shrink_ratio {
            AccountShrinkThreshold::TotalSpace { shrink_ratio: _ } => alive_bytes < total_bytes,
            AccountShrinkThreshold::IndividualStore { shrink_ratio } => {
                (alive_bytes as f64 / total_bytes as f64) < shrink_ratio
            }
        }
    }
