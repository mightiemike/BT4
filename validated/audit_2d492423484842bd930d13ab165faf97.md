### Title
Wallet Contract pays relayer fee unconditionally before the underlying user action's success is known - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`WalletContract::rlp_execute` (the NEAR wallet contract's Ethereum-transaction-emulation entry point) dispatches the relayer's compensation `fee` as an independent, unconditional `Transfer` receipt to the relayer *before* the outcome of the actual user-intended action (base-token transfer or ERC-20 `ft_transfer`) is known. If that main action later fails, only the `caller_deposit` is refunded; the relayer fee is never returned, and the nonce has already been consumed so the transaction can never be retried.

### Finding Description
In `inner_rlp_execute`, for `EOABaseTokenTransfer` and `ERC20Transfer` transaction kinds, the code increments the nonce and then unconditionally creates a separate promise/receipt paying the relayer's `fee`: [2](#0-1) 

This fee-paying receipt (`env::promise_batch_create(&context.predecessor_account_id)` + `promise_batch_action_transfer`) is fired independently of, and *before*, the promise chain that actually performs the user's requested action (`action_to_promise(...).then(...rlp_execute_callback...)`), constructed later in the same function: [3](#0-2) 

The only failure-handling/refund path that exists is in `rlp_execute_callback`, and it only refunds `caller_deposit` (the attached deposit passed to the target contract), never the relayer `fee`: [1](#0-0) 

This is structurally the same bug class as the referenced report: a value-affecting operation (paying the relayer) is treated as final/successful without checking or waiting on the "error code" (success/failure) of the dependent operation it is supposed to be compensating for. Because NEAR receipts dispatched from the same function call are independent unless explicitly chained with `.then()`/`.and()`, the fee-payment receipt to the relayer executes and settles completely independently of whether the main action receipt (the transfer/`ft_transfer`) ultimately succeeds or fails.

Additionally, the nonce is incremented in the same code path before the outcome is known (`nonce.saturating_add(1)` at line 364), which is by design to prevent replay — but it also means there is no way for the same signed transaction to be retried to recover the failed action, compounding the fee loss with a permanently lost/failed transfer.

### Impact Explanation
Any relayer (an unprivileged meta-transaction sender relaying a user's signed Ethereum-style transaction) can submit a transaction whose underlying action is guaranteed or likely to fail at execution time for reasons outside the user's knowledge at signing time (e.g., the NEP-141 token contract has since paused, the receiver rejects the transfer, `storage_deposit`/`ft_transfer` batched actions fail, gas is insufficient for the target contract's logic, etc.). The relayer still collects the `fee` NEAR tokens the user committed to pay for successful relaying, while the user's actual intended value transfer never happens and cannot be resubmitted (nonce already consumed). This is a concrete, unauthorized value movement out of the user's wallet contract with no corresponding service rendered — direct loss of user funds.

### Likelihood Explanation
Reachable by any account that can call `rlp_execute` on a deployed Wallet Contract with a validly signed (from the wallet owner's perspective) but execution-fragile Ethereum transaction — no special privilege, validator status, or protocol-level access is required. A dishonest or even just poorly-timed relayer (e.g., racing a token pause/registry change) can trigger this every time an underlying action fails after the fee-payment receipt has already been dispatched.

### Recommendation
Do not dispatch the relayer fee transfer as an independent up-front receipt. Instead, chain it into (or make it conditional on) the success path of the main action's promise — e.g., only send the fee transfer from within `rlp_execute_callback` after observing `PromiseResult::Successful`, mirroring how `caller_deposit` is already refunded only on `PromiseResult::Failed`. This mirrors the `CompoundPrizePool` fix pattern of not treating an operation as complete/final until the dependent call's actual result/error status has been checked.

### Proof of Concept
1. A user signs an Ethereum-style ERC-20 transfer transaction (`ft_transfer`) via the wallet contract with a non-zero relayer `fee`, targeting a NEP-141 token contract.
2. A relayer submits it via `rlp_execute`. `inner_rlp_execute` increments the nonce and immediately fires a `Transfer` receipt of `fee` to the relayer's account (lines 381-384).
3. Separately, the code builds the `storage_balance_of` → (`storage_deposit` + `ft_transfer`) → `rlp_execute_callback` promise chain for the actual transfer.
4. If the token contract subsequently fails the `ft_transfer` action (e.g., the token contract is paused, or the receiver account was deleted, or gas runs out), `rlp_execute_callback` observes `PromiseResult::Failed` and refunds only `caller_deposit` — the `fee` receipt to the relayer has already independently succeeded and is not reverted or clawed back.
5. Net effect: the relayer is paid `fee`, the user's nonce is consumed, and the user's ERC-20 transfer never took place — permanent loss of the fee amount for a transaction that produced no value for the user.
