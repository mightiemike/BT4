### Title
`DelegateResourceActuator`/`UnDelegateResourceActuator` do not sync the vote/reward checkpoint that `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`/`VoteWitnessActuator` always apply - ([File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java])

### Summary
The reported Popcorn bug is a class of "inconsistent checkpoint sync": one state-mutating entry point (`withdraw`) refreshes an accounting checkpoint (`highWaterMark`) before/after mutating balances, while a sibling entry point (`redeem`) mutates the same balances but skips the sync, leaving a stale checkpoint that corrupts a later fee/reward calculation. In java-tron, the equivalent checkpoint is the reward/vote accounting maintained by `MortgageService.withdrawReward()` (and its TVM twin `VoteRewardUtil.withdrawReward()`), which snapshots an account's vote list before its resource/tron-power composition changes and settles the account's accrued voting reward up to the current cycle.

### Finding Description
Every actuator that can change an account's effective TronPower in a way that could leave existing votes “over-collateralized” consistently calls the reward/vote checkpoint first:
- `WithdrawBalanceActuator.execute()` calls `mortgageService.withdrawReward(...)` [1](#0-0) 
- `UnfreezeBalanceV2Actuator.execute()` calls `mortgageService.withdrawReward(ownerAddress)` before adjusting frozen balance and then calls `updateVote(...)` to shrink existing votes if TronPower becomes insufficient [2](#0-1) 
- `VoteWitnessActuator.countVoteAccount()` calls `mortgageService.withdrawReward(ownerAddress)` before recording new votes [3](#0-2) 
- The TVM-native equivalents (`UnfreezeBalanceProcessor`, `UnfreezeBalanceV2Processor`, `VoteWitnessProcessor`, `WithdrawRewardProcessor`, `Program.withdrawRewardAndCancelVote`) all call `VoteRewardUtil.withdrawReward(ownerAddress, repo)` first, and `UnfreezeBalanceV2Processor.updateVote()` proportionally shrinks votes when `ownedTronPower < totalVote * TRX_PRECISION` [4](#0-3) 

In contrast, `DelegateResourceActuator.execute()` moves an owner's non-delegated frozen V2 balance into `DelegatedFrozenV2Balance` (i.e., resource/TronPower backing is handed to a receiver) but never calls `mortgageService.withdrawReward()` and never re-checks or shrinks the owner's existing votes against the now-reduced TronPower [5](#0-4) . The same absence exists in `UnDelegateResourceActuator.execute()` and in their TVM counterparts `DelegateResourceProcessor.execute()` / `UnDelegateResourceProcessor.execute()` [6](#0-5) [7](#0-6) .

This mirrors the Popcorn bug exactly: a class of mutating actions (unfreeze/withdraw/vote) always reconciles the checkpoint (reward settlement + vote-shrink), while a sibling mutating action (delegate/undelegate resource) that also reduces the account's backing TronPower skips it.

### Impact Explanation
`MortgageService.withdrawReward` / `VoteRewardUtil.withdrawReward` compute voting rewards purely from the account's stored `votesList` (via `computeReward`, `Vi` deltas) [8](#0-7) , without re-validating that the account still holds enough TronPower to back those votes. Because `DelegateResourceActuator`/`UnDelegateResourceActuator` never invoke the checkpoint or the `updateVote` shrink logic that the unfreeze path uses, an account can vote for witnesses, then delegate away the frozen balance that backed those votes (receiving resources to another account) while its `votesList` (and thus its stream of voting rewards) remains unchanged. This causes reward/vote accounting corruption: the account continues to receive full voting rewards for TronPower it no longer effectively holds/uses for its own resource needs, and the total "backed" vote weight across the network can drift from actual staked TronPower. This is a concrete asset/accounting-corruption bug reachable from an ordinary broadcast `DelegateResourceContract`/`UnDelegateResourceContract` transaction or the corresponding TVM opcodes, requiring no privileged role.

### Likelihood Explanation
High reachability: `DelegateResourceContract` and `UnDelegateResourceContract` are ordinary, unprivileged transaction types available to any account (gated only by `dynamicStore.supportDR()`/`supportUnfreezeDelay()` feature flags, not by role) [9](#0-8) , and the TVM opcodes `delegateResource`/`unDelegateResource` are callable from any smart contract [10](#0-9) . Any account that has previously voted and then delegates its frozen resource can trigger the drift with a single transaction; no race condition or special timing is required.

### Recommendation
Update `DelegateResourceActuator.execute()`, `UnDelegateResourceActuator.execute()`, `DelegateResourceProcessor.execute()`, and `UnDelegateResourceProcessor.execute()` to call the same reward/vote checkpoint used by the unfreeze path: invoke `mortgageService.withdrawReward(ownerAddress)` (resp. `VoteRewardUtil.withdrawReward(ownerAddress, repo)`) before mutating the frozen/delegated balances, and then run the same `updateVote`-style proportional vote-shrink logic used in `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor` whenever the owner's remaining TronPower falls below the sum of its existing votes.

### Proof of Concept
1. Account A freezes balance (`FreezeBalanceV2Contract`, BANDWIDTH) and gains TronPower.
2. Account A votes for witness W with its full TronPower (`VoteWitnessContract`), which calls `mortgageService.withdrawReward()` and stores A's `votesList`.
3. Account A calls `DelegateResourceContract` to delegate that same frozen BANDWIDTH balance to account B. `DelegateResourceActuator.execute()` moves the balance into `DelegatedFrozenV2BalanceForBandwidth` and never calls `mortgageService.withdrawReward()` nor adjusts/shrinks A's `votesList`, unlike the equivalent unfreeze path.
4. At the next maintenance cycle, A's unchanged `votesList` still earns full voting reward via `computeReward()`/`withdrawReward()`, even though the TronPower backing those votes has been handed to B — producing reward/vote accounting divergent from actual staked TronPower.

Note: I was not able to fully verify, within the available iterations, the exact formula in `AccountCapsule.getTronPower()`/`getAllTronPower()` that determines whether delegated-away balance is excluded from the voter's own TronPower count in every code path (pre- vs post- `supportAllowNewResourceModel`). This detail should be confirmed by a developer with full file access, as it affects whether the vote-count over-collateralization is exactly as described or only manifests under specific `supportAllowNewResourceModel`/`supportDR` flag combinations.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  public boolean delegateResource(
      DataWord receiverAddress, DataWord delegateBalance, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver,
        delegateBalance.longValue(), null,
        "delegateResourceOf" + convertResourceToString(resourceType), nonce, null);

    try {
      DelegateResourceParam param = new DelegateResourceParam();
      param.setOwnerAddress(owner);
      param.setReceiverAddress(receiver);
      param.setDelegateBalance(delegateBalance.sValue().longValueExact());
      param.setResourceType(parseResourceCodeV2(resourceType));

      DelegateResourceProcessor processor = new DelegateResourceProcessor();
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM DelegateResource: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM DelegateResource: balance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
  }
