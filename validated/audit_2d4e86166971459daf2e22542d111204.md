### Title
Relayer Fee Paid Unconditionally Before Confirming the Corresponding Action Succeeds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In the Wallet Contract's `inner_rlp_execute`, the relayer refund/fee transfer for an emulated base-token or ERC-20 transfer is scheduled immediately after parsing the transaction, before the actual action promise (the transfer/`ft_transfer` the user signed) is known to succeed. This mirrors the reported Sense `_fillQuote()` bug class: value (the "fee spend") leaves the contract without any binding/precondition tying it to the successful completion of the operation it is supposed to compensate.

### Finding Description
`inner_rlp_execute` parses the signed Ethereum-style transaction into a Near `Action` and a `TransactionKind`. When the kind is `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the code immediately creates and dispatches a promise batch transferring the fee to the relayer (`predecessor_account_id`): [1](#0-0) 

This transfer is fired independently of the `promise` variable that later chains the actual action (`Transfer`/`ft_transfer`) via `.then(...)`: [2](#0-1) 

The only failure-handling path that exists is `rlp_execute_callback`, which refunds the *caller's attached deposit* if the chained action promise fails — but it does **not** claw back or condition the relayer fee that was already dispatched as a separate, independent promise batch: [3](#0-2) 

Just as `Periphery._fillQuote()` performed a privileged operation (the 0x swap call) without first establishing the precondition (`approve`) needed for it to succeed, the Wallet Contract performs a privileged token movement (fee payment to relayer) without establishing the precondition that the corresponding user-intended action will actually succeed. The fee-transfer batch and the action-execution promise are two independent, uncoupled promise batches within the same receipt; Near's async execution model does not roll back an already-dispatched sibling promise batch if a later `.then()`-chained promise fails.

### Impact Explanation
A relayer (an unprivileged, unauthorized entity relative to the wallet owner's funds — any account can act as relayer per `register_relayer`/open relaying design) can submit a signed transaction whose main action is guaranteed or likely to fail (e.g., a `ft_transfer` that will fail due to insufficient token balance, an unregistered/invalid receiver combined with a crafted failure, or racing nonce/in-flight-tx state) while the non-zero `fee` field is still honored and paid out unconditionally. This results in unauthorized value movement out of the wallet contract's NEAR balance to the relayer without the user's intended action (the thing the fee was meant to compensate) ever completing successfully.

### Likelihood Explanation
Reachable directly from a single submitted transaction/RPC call: any account can act as the relayer that calls `rlp_execute` with an `EOABaseTokenTransfer`/`ERC20Transfer`-shaped payload and a non-zero `fee`, since the fee dispatch happens in the synchronous portion of `inner_rlp_execute` before any promise outcome is known. No privileged access or special network conditions are required, only crafting a payload whose downstream action fails after the fee is already dispatched.

### Recommendation
Do not dispatch the relayer fee transfer independently of the action outcome. Either (a) chain the fee-payment promise after `rlp_execute_callback` confirms the primary action succeeded, or (b) merge the fee transfer into the same promise batch as the action so that a batch failure (where supported) prevents the fee payment, and add explicit clawback/refund logic for the fee when the primary action fails.

### Proof of Concept
1. Wallet contract holds NEP-141 token balance and NEAR balance; a relayer account (no special privilege) calls `rlp_execute` with a signed Ethereum-style transaction encoding an `ERC20Transfer` with a non-zero `fee` and a `value`/args crafted so the subsequent `ft_transfer` call will fail (e.g., transfer amount exceeding wallet's actual token balance, discovered only at execution time).
2. In `inner_rlp_execute`, the code path at lines 374–385 in `lib.rs` unconditionally creates and dispatches the fee-transfer promise batch to `predecessor_account_id` (the relayer) as soon as `fee` is non-zero.
3. The action promise (chained via `.then(ext.rlp_execute_callback(...))`) subsequently fails when the `ft_transfer` reverts.
4. `rlp_execute_callback` only refunds `caller_deposit` (the attached NEAR deposit of the call, if any) — it has no code path referencing or reversing the already-committed fee transfer.
5. Net effect: the relayer receives the fee, but the wallet's intended action never executed — an unauthorized value transfer decoupled from the operation it was meant to fund.

            };

            address_registrar.lookup(address).then(ext.address_check_callback(

                caller_deposit,

        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
