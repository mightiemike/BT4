### Title
`TransactionOutput::ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, allowing a wrong state root to pass replay/backup-restore validation - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single-transaction integrity check used to confirm that a locally re-executed `TransactionOutput` matches the corresponding authenticated `TransactionInfo` (the leaf committed into the transaction accumulator) during chunk execution and replay/backup-verification flows. [1](#0-0)  It checks status, gas used, write-set hash (`state_change_hash`) and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. [2](#0-1) 

### Finding Description
The comment embedded in the code confirms the gap in the developers' own words: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [3](#0-2) 

`ensure_match_transaction_info` is invoked in the chunk executor's apply path (`execution/executor/src/chunk_executor/mod.rs`) as well as in `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`, all of which are supposed to authenticate that locally computed transaction outputs are consistent with the trusted, proof-carrying `TransactionInfo` obtained from a peer, backup archive, or state-sync response before the data is accepted/committed. Because the function silently skips the `state_checkpoint_hash` (main JMT root at a checkpoint), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields, any divergence between the locally computed state root (or the newer "trading-native" position-state root) and what is embedded in the transaction info is never detected by this check. `TransactionInfoV1` explicitly carries all three of these fields as part of the authenticated leaf. [4](#0-3) 

### Impact Explanation
This breaks the proof-binding invariant that a transaction output accepted from an external/replayed source must match every hashed field of the authenticated `TransactionInfo` before being trusted. Where this check is relied on as the sole cross-check (e.g., chunk-executor apply of `TransactionOutputListWithProofV2` during state sync/backup restore, and `replay-verify`/backup tooling that re-executes historical transactions against an accumulator-backed transaction-info list), a corrupted or non-deterministic state root (main state checkpoint, hot-state checkpoint, or the new position/"trading-native" state root) can be silently accepted as correct. This means replay-verify — the tool operators run specifically to certify that backups/archives reproduce the correct ledger state — can report success even though the committed state root diverges from what local execution actually produced, i.e., a wrong state/position proof root is accepted as valid.

### Likelihood Explanation
This is not attacker-triggered in the classic sense; it requires an underlying non-determinism, bug, or corrupted transaction-info/write-set combination to already exist somewhere in the position-state or hot-state root computation path (the newer "trading-native" state roots feature is explicitly called out as under development in the same comment). However, once such a divergence exists — from any cause: implementation bug, hardware/consensus issue, or corrupted archive — this verification gap means it goes undetected specifically in the flows meant to catch it (replay-verify, backup restore verification), turning what should be a hard verification failure into a silent pass. The severity depends on whether `compute_trading_native_state_roots`/hot-state features are enabled on the network being verified; I could not fully trace all call sites' feature-flag gating within the remaining investigation budget, so likelihood should be treated as feature-gated and not universally exploitable on all deployments today.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally computed output/state summary and the `txn_info` when the corresponding value is present in `txn_info` (i.e., at checkpoint boundaries), returning an error on mismatch exactly as done for `state_change_hash` and `event_root_hash`. This should be enforced before enabling any feature (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that relies on these fields for state-proof integrity, per the TODO already present in the code.

### Proof of Concept
Conceptual PoC (cannot be executed without a live devnet/testnet):
1. Enable `compute_trading_native_state_roots` (or hot-state) on a test network so `TransactionInfoV1` carries non-trivial `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` values.
2. Produce a `TransactionOutput` whose write set matches `state_change_hash`/`event_root_hash` but whose derived position/hot state root would differ from the `txn_info`'s recorded `position_state_checkpoint_hash` (e.g., by injecting a bug or corrupted intermediate root in the position-state summary computation used by `do_state_checkpoint.rs`, or by feeding a backup archive where only the checkpoint-hash field was tampered/corrupted while `write_set`/`events` remain valid).
3. Run this through `ensure_match_transaction_info` (as invoked by the chunk executor / `replay-verify` / debugger tooling) and observe it returns `Ok(())` because the function never reads or compares `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` from `txn_info`, confirming the gap is exactly as flagged in the source comment. [5](#0-4)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
