### Title
Missing server-side upper bound on `Wallet.getBlocksByLimitNext` allows unbounded-range block queries via gRPC `GetBlockByLimitNext`, bypassing the HTTP servlet's 100-block clamp - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getBlocksByLimitNext(long number, long limit)` only rejects `limit <= 0`; it enforces no upper bound on `limit` before delegating to `BlockStore.getLimitNumber`, which performs a range read from RocksDB/LevelDB and then an `O(n log n)` sort in `BlockStore.pack`. The `BLOCK_LIMIT_NUM = 100` cap that prevents abuse exists only in the HTTP servlet layer (`GetBlockByLimitNextServlet`), not in `Wallet.java` itself, so a client calling the gRPC `getBlockByLimitNext` RPC directly with a `BlockLimit` message can request an arbitrarily large range and skip that clamp entirely.

### Finding Description
`GetBlockByLimitNextServlet.fillResponse` enforces `endNum - startNum <= BLOCK_LIMIT_NUM` (100) before calling `wallet.getBlocksByLimitNext(startNum, endNum - startNum)`: [1](#0-0) 

However, the underlying method that actually performs the work, `Wallet.getBlocksByLimitNext`, has no such bound — it only checks `limit <= 0`: [2](#0-1) 

That method calls `BlockStore.getLimitNumber(number, limit)`, which fetches up to `limit` values from the revoking DB and then sorts them: [3](#0-2) 

The analogous `BlockIndexStore.pack`/`getLimitNumber` has the identical unbounded-sort pattern: [4](#0-3) 

Because the size check lives only in the HTTP servlet and not in `Wallet.java`, any client that reaches the gRPC service directly (e.g., via the `WalletGrpc` stub's `getBlockByLimitNext(BlockLimit)` call, which protobuf-encodes `startNum`/`endNum` and is wired to `wallet.getBlocksByLimitNext` in `RpcApiService`) bypasses the 100-block cap. I was not able to fully retrieve the body of `RpcApiService.java`'s `getBlockByLimitNext` handler in this session to confirm with certainty that no independent clamp exists there, but based on the grep results and the consistent pattern in this codebase (validation is centralized in the HTTP `Util`/servlet layer, not in `Wallet.java`), this gRPC entry point relies solely on `Wallet.getBlocksByLimitNext`'s lack of validation.

### Impact Explanation
This is a DoS-via-RPC-API class issue: an anonymous gRPC client can request a range covering the entire chain history (or any very large `limit`), forcing the node to perform a large range scan of the block DB, construct a large in-memory list, sort it, and fully serialize/return it — with no per-call cost to the attacker other than a single RPC message. Repeated/concurrent such calls across RPC threads amplify CPU, memory, and I/O load on the node, potentially causing request-handling stalls or resource exhaustion for legitimate operations. This matches the "DoS via RPC-API" impact class, but note the underlying complexity is `O(n log n)` (sort) plus `O(n)` I/O/serialization per call, not literally quadratic — the "quadratic-like" characterization in the question is an overstatement, though the unbounded-resource-consumption issue itself is real and reproducible.

### Likelihood Explanation
- Preconditions: the node's gRPC endpoint (default port, e.g. 50051) is reachable — this is default configuration for most full nodes exposing the P2P/API gRPC service, not a non-default hardening bypass.
- Cost to attacker: essentially free — a single unauthenticated gRPC call with a large `endNum - startNum` (or `BlockIndexStore`-backed calls with large `limit`), repeatable indefinitely and in parallel across many connections.
- Feasibility: high, since the flaw is a straightforward missing bounds check in `Wallet.java` rather than requiring any privileged role, signed transaction, or contract execution.

### Recommendation
Move the range/limit validation from `GetBlockByLimitNextServlet` (and the Solidity/PBFT HTTP equivalents) into `Wallet.getBlocksByLimitNext` itself (and analogously into any `BlockIndexStore`/`BlockStore` `getLimitNumber` callers), enforcing a fixed maximum `limit` (e.g., 100) regardless of which transport (HTTP, gRPC, JSON-RPC) invokes it. This ensures faithful metering across all entry points rather than only the HTTP servlet.

### Proof of Concept
```java
// Illustrates the gap: Wallet.getBlocksByLimitNext has no upper bound,
// while GetBlockByLimitNextServlet enforces BLOCK_LIMIT_NUM = 100.

@Test
public void testUnboundedLimitBypassesHttpClamp() {
  long startNum = 0;
  long hugeLimit = 5_000_000L; // far beyond BLOCK_LIMIT_NUM=100 enforced in servlet

  // Direct call as would happen via gRPC WalletGrpc.getBlockByLimitNext(BlockLimit),
  // which is wired straight to Wallet.getBlocksByLimitNext without servlet-side clamp.
  BlockList result = wallet.getBlocksByLimitNext(startNum, hugeLimit);

  // Expected (per HTTP servlet policy): request should be rejected/clamped.
  // Actual: succeeds and processes up to hugeLimit blocks, doing a full DB range
  // scan + O(n log n) sort in BlockStore.pack with no limit enforcement.
  assertNotNull(result); // demonstrates missing bound in Wallet.java
}
```
Request-level reproduction: send a `BlockLimit{startNum:0, endNum:5000000}` message to the gRPC `getBlockByLimitNext` RPC (bypassing the HTTP servlet entirely) and observe it is processed (subject only to actual chain height and revokingDB constraints), whereas the equivalent HTTP `POST /wallet/getblockbylimitnext` request with `endNum-startNum > 100` is rejected by `GetBlockByLimitNextServlet.fillResponse` and returns `{}`.
