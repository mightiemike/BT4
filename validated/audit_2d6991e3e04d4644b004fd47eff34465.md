### Title
Integer overflow in `frozenDuration * FROZEN_PERIOD` can produce an already-expired `expireTime`, bypassing the freeze lock invariant - (File: `FreezeBalanceActuator.java`)

### Finding Description
`FreezeBalanceActuator.execute()` computes the lock expiration with unchecked `long` arithmetic: [1](#0-0) 

`freezeBalanceContract.getFrozenDuration()` is an attacker-controlled `int64` field taken directly from the broadcast `FreezeBalanceContract`, and `FROZEN_PERIOD` is a fixed millisecond-per-day constant. There is no `Math.multiplyExact` or range clamp on this multiplication, so a sufficiently large `frozenDuration` (approximately `Long.MAX_VALUE / FROZEN_PERIOD + 1` and above) wraps the `long` product to a negative value, making `duration` negative and therefore `expireTime = now + duration` less than `now` — i.e., the frozen balance is recorded as already expired at the moment it is frozen.

The only guard against an out-of-range `frozenDuration` is the bounds check in `validate()`, which is explicitly gated behind the `needCheckFrozeTime` flag: [2](#0-1) 

This flag is read from `CommonParameter.getInstance().getCheckFrozenTime()` and is annotated `//for test`, indicating it is intended for test-harness use rather than as the primary safety mechanism; when it is `0` (as in the exploit precondition described in the question), the `minFrozenTime`/`maxFrozenTime` range check is skipped entirely, and `frozenDuration` is unconstrained except by protobuf's `int64` range. No other bound on `frozenDuration` exists anywhere else in `validate()` or `execute()`.

Because `frozenBalance` is still deducted from the owner's balance and locked into `setFrozenForBandwidth`/`setFrozenForEnergy`/`setFrozenForTronPower` (or delegated via `delegateResource`) using this bogus, already-past `expireTime`, the funds/resource are recorded as unlockable immediately, defeating the intended minimum-lock-period invariant that freeze operations are supposed to enforce.

### Impact Explanation
An attacker can freeze TRX to gain BANDWIDTH/ENERGY/TRON_POWER weight (or delegate resources) and have the position marked as already expired, allowing immediate `UnfreezeBalance` in the very next transaction/block instead of waiting out the minimum freeze period. This breaks the anti-spam/stability invariant that freeze-derived voting/resource weight must be time-locked, and could be abused to rapidly cycle freeze/unfreeze to manipulate `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` or governance voting power windows without incurring the intended lock cost.

### Likelihood Explanation
Exploitability strictly depends on the precondition stated in the question: `CommonParameter.getCheckFrozenTime()` must be disabled (its comment `//for test` suggests it is not intended to be the production enforcement mechanism, though I could not fully verify its compiled default value in `Args.java`/`reference.conf` within available tooling). If disabled, the attack is trivial and fully reachable by any unprivileged account: broadcast one `FreezeBalanceContract` with `frozenDuration ≈ Long.MAX_VALUE / FROZEN_PERIOD + 1` (or larger) — no special privileges, only a valid account and `frozenBalance >= 1 TRX`, are required. If `checkFrozenTime` is enabled and `maxFrozenTime` is small (e.g., a few days), `validate()` will reject the oversized `frozenDuration` before it ever reaches `execute()`, fully mitigating this issue.

### Recommendation
- Perform the min/max `frozenDuration` bound check in `validate()` unconditionally (remove/limit the `needCheckFrozeTime` bypass, or apply an absolute hard cap on `frozenDuration` regardless of the flag).
- Use `Math.multiplyExact(freezeBalanceContract.getFrozenDuration(), FROZEN_PERIOD)` in `execute()` (and any other analogous computation) to fail fast on overflow instead of silently wrapping.
- Assert `expireTime > now` before persisting frozen balances in `execute()`, throwing/aborting the actuator if not.

### Proof of Concept
```java
// FreezeBalanceActuatorOverflowTest.java (framework/src/test/java/org/tron/core/actuator/)
@Test
public void testFrozenDurationOverflowBypassesLock() throws Exception {
  // Ensure checkFrozenTime is disabled (production-representative default)
  dbManager.getDynamicPropertiesStore().saveCheckFrozenTime(0);

  long now = dbManager.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
  long overflowDuration = Long.MAX_VALUE / FROZEN_PERIOD + 1; // triggers wraparound

  FreezeBalanceContract contract = FreezeBalanceContract.newBuilder()
      .setOwnerAddress(ByteString.copyFrom(ownerAddress))
      .setFrozenBalance(1_000_000L) // 1 TRX
      .setFrozenDuration(overflowDuration)
      .setResource(ResourceCode.BANDWIDTH)
      .build();

  FreezeBalanceActuator actuator = new FreezeBalanceActuator();
  actuator.setChainBaseManager(chainBaseManager)
      .setAny(Any.pack(contract));

  actuator.validate(); // passes because needCheckFrozeTime == false
  TransactionResultCapsule ret = new TransactionResultCapsule();
  actuator.execute(ret);

  AccountCapsule account = accountStore.get(ownerAddress);
  long expireTime = account.getFrozenList().get(0).getExpireTime();

  // Invariant that SHOULD hold but is violated:
  Assert.assertTrue("expireTime must be in the future", expireTime > now);
  Assert.assertTrue("expireTime must respect minFrozenTime",
      expireTime >= now + dbManager.getDynamicPropertiesStore().getMinFrozenTime() * FROZEN_PERIOD);
  // Observed: expireTime is negative/less than `now` due to long overflow,
  // demonstrating the frozen balance is immediately "unfreezable".
}
```
Fuzz extension: iterate `frozenDuration` over `{Long.MAX_VALUE/FROZEN_PERIOD, Long.MAX_VALUE/FROZEN_PERIOD+1, Long.MAX_VALUE}` and assert `expireTime > now` never fails after the fix is applied.
