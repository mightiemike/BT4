### Title
Zero-weight/empty reward-set edge case lets a Nakamoto block bypass signer-signature verification entirely - (File: stackslib/src/chainstate/nakamoto/mod.rs)

### Summary
`NakamotoBlockHeader::verify_signer_signatures` accepts a block whenever `total_weight_signed >= threshold`. Both of these are `u32` values computed from the reward set and the block's `signer_signature` vector. If the reward set for a cycle has zero total signing weight (e.g., an empty-but-`Some` signer list, or a set of signers whose apportioned weights are all zero), `compute_voting_weight_threshold` legitimately returns `0`, and an *empty* `signer_signature` vector produces `total_weight_signed == 0`. The comparison `0 < 0` is `false`, so the function returns `Ok(0)` — i.e., a block with **no signatures at all** is treated as validly signed. This mirrors the Ambire bug class: a degenerate/default value (`address(0)` there, `0`-weight/empty-signature here) trivially satisfies an equality/threshold check that was meant to require real authorization.

### Finding Description
`verify_signer_signatures` only rejects up front when `reward_set.signers()` is `None`: [1](#0-0) 
It does not reject when the signer list is present but empty. It then computes `total_weight` from `reward_set.total_signing_weight()` and iterates `self.signer_signature`, accumulating `total_weight_signed`: [2](#0-1) 
Finally, the block is accepted unless the accumulated weight is strictly less than the threshold: [3](#0-2) 
`compute_voting_weight_threshold` computes `ceil(total_weight * 7 / 10)`, which is exactly `0` when `total_weight == 0`: [4](#0-3) 

So for any reward set whose signers collectively have `total_weight == 0` (or an empty-but-non-`None` signer list), both sides of the `<` comparison degrade to `0`, and the check that is supposed to enforce "at least 70% of signer weight approved this block" is trivially satisfied by a block carrying **zero** entries in `signer_signature`. This function is the sole gate used by peer validation (`check_nakamoto_block_signer_signature` in `stackslib/src/net/unsolicited.rs`) and by chainstate block acceptance, so any node reaching this code path with a degenerate reward set would accept an unsigned block as canonical.

Note: I was not able to fully trace every code path that produces the `RewardSet`/`total_signing_weight` to definitively rule out that the "no registered signers" case is always caught earlier via `NoRegisteredSigners`/`ChainstateError` checks elsewhere in the pipeline (e.g. reward-set construction, PoX-5 apportionment `pox_5_make_signer_set`, which explicitly guards against all-zero-weight signer sets via a largest-remainder allocation: [5](#0-4) 
This mitigation appears intentionally designed to prevent the "entire signer set could be dropped" degenerate mode, which suggests the code authors were aware of this class of bug for the *weight-apportionment* path specifically. However, `verify_signer_signatures` itself contains no defensive check against `total_weight == 0` or an empty (but `Some`) `signers()` list, so the guarantee that this state is unreachable depends entirely on upstream reward-set construction always producing a nonzero-weight set — an invariant that is not enforced at the point of verification.

### Impact Explanation
If reachable, this breaks the core equality that Nakamoto block validation is designed to enforce: "at least 70% of signer weight must have signed the block." An attacker (a single miner, no privileged access needed) could produce and broadcast a block with an empty `signer_signature` field that is nonetheless treated as fully signed, letting an unsigned/invalid block be accepted network-wide — a Critical-severity invariant violation (invalid block accepted network-wide) if the degenerate reward-set state is ever reached.

### Likelihood Explanation
Low-to-uncertain. Reaching this state requires a reward set with `total_signing_weight() == 0` while `reward_set.signers()` is `Some(_)` rather than `None`. Existing weight-apportionment code (`pox_5_make_signer_set`) appears to have been hardened specifically to avoid degenerate all-zero-weight signer sets, which reduces the practical likelihood on the PoX-5 path. I could not fully verify all other reward-set construction paths (e.g. bootstrapping/empty-stacker scenarios, or non-PoX-5 legacy reward-set paths) within the available search budget, so likelihood should be treated as unconfirmed/edge-case rather than definitively proven exploitable today.

### Recommendation
In `verify_signer_signatures`, explicitly reject when `signers.is_empty()` or when `total_weight == 0`, rather than relying on the `<` comparison degrading to a trivially-true pass. E.g., add `if signers.is_empty() || total_weight == 0 { return Err(ChainstateError::NoRegisteredSigners(0)); }` immediately after resolving `signers`/`total_weight`, so an empty or zero-weight reward set can never validate a block regardless of how many (zero) signatures are present.

### Proof of Concept
1. Construct (or force, in a test harness) a `RewardSet` whose `signers()` returns `Some(vec![])` or a non-empty vector whose entries all have `weight == 0`.
2. Build a `NakamotoBlockHeader` with `signer_signature = vec![]` (no signatures).
3. Call `header.verify_signer_signatures(&reward_set, epoch_id)`.
4. Observe: `total_weight = 0`, `threshold = compute_voting_weight_threshold(0) = 0`, `total_weight_signed = 0`; the check `total_weight_signed < threshold` (`0 < 0`) is `false`, so the function returns `Ok(0)` instead of an error — an unsigned block is accepted as validly signed.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
