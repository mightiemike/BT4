### Title
Unbounded full-store scan in `GetAssetIssueListServlet` allows attacker-amplified DoS via unauthenticated GET requests - ([File: framework/src/main/java/org/tron/core/services/http/GetAssetIssueListServlet.java])

### Summary
`GetAssetIssueListServlet.doGet` calls `Wallet.getAssetIssueList()`, which invokes `AssetIssueStore.getAllAssetIssues()` — an unbounded full iteration over the entire `asset-issue` RocksDB column via `RockStoreIterator`/`RocksDbDataSourceImpl.iterator()`. Unlike its sibling `GetPaginatedAssetIssueListServlet`, which bounds the scan window with `ASSET_ISSUE_COUNT_LIMIT_MAX`, this endpoint performs O(store-size) native iteration on every unauthenticated request, gated only by `RateLimiterServlet`'s per-endpoint QPS count, not by scan cost.

### Finding Description
`GetAssetIssueListServlet.doGet` (unauthenticated, no fee) calls `wallet.getAssetIssueList()`: [1](#0-0) 

which in `Wallet.getAssetIssueList()` calls `AssetIssueStore.getAllAssetIssues()` with no offset/limit and iterates the full store, applying `BandwidthProcessor.updateUsage` to every capsule: [2](#0-1) 

`getAllAssetIssues()` streams the *entire* RocksDB iterator with no bound: [3](#0-2) 

By contrast, the paginated sibling clamps the result size to `ASSET_ISSUE_COUNT_LIMIT_MAX` after still fully materializing `getAllAssetIssues()` internally, meaning even the paginated endpoint pays the full scan cost, but caps only the JSON response size: [4](#0-3) 

The underlying iterator is a native RocksDB cursor (`RockStoreIterator` wrapping `RocksIterator`) that must walk every key in the column family: [5](#0-4) [6](#0-5) 

The only guard on this HTTP path is `RateLimiterServlet.service()`, which throttles by request/QPS count via a configurable adapter (default `DefaultBaseQqsAdapter`), and a global IP/QPS limiter — neither of which accounts for the cost of the underlying DB scan: [7](#0-6) 

Because `AssetIssueContract` creation is a normal, fee-paying, unprivileged transaction type (handled by `AssetIssueActuator`), an attacker can grow the `asset-issue` store size linearly by broadcasting many such transactions, then repeatedly hit the unauthenticated `/wallet/getassetissuelist` endpoint (and its PBFT/Solidity mirrors, `GetAssetIssueListOnPBFTServlet`/`GetAssetIssueListOnSolidityServlet`) to force O(N) native scans per request. No signature/permission check, actuator validation, or fork gate applies to *read* endpoints — those checks only govern the *write* path that grows the store, and they don't limit how large the store may legitimately become.

### Impact Explanation
Each request triggers an O(store-size) native RocksDB iteration plus full protobuf serialization of every asset issue in the store, consumed on a full node's finite HTTP thread pool. As the store grows (attacker-controlled, paid in TRX fees per asset creation but otherwise unbounded), the per-request cost grows linearly while the rate limiter still only counts requests, not cost — enabling a low-cost requester to consume disproportionate CPU/memory/native-iterator resources per unit of paid cost, degrading availability for all clients of that full node (DoS via RPC-API class).

### Likelihood Explanation
Preconditions: attacker needs (1) ability to broadcast fee-paying `AssetIssueContract`-creating transactions to inflate `AssetIssueStore`, and (2) unauthenticated network access to `GetAssetIssueListServlet` (default-enabled HTTP API, no non-default config required). Both are ordinary, unprivileged capabilities. The main mitigating cost factor is the TRX fee/burn required per asset-issue creation transaction, which I was not able to fully confirm in this pass (I located references to an asset-issue fee constant in `DynamicPropertiesStore`/`Commons.java`/`AssetIssueActuator` but did not read the exact fee amount or verify whether an account can create only one asset per name/lifetime). This fee is the primary economic brake on how large N can practically grow; without knowing its exact value, I cannot precisely bound attacker cost-to-impact ratio, but the code path itself confirms the scan is genuinely unbounded and uncompensated by request-based rate limiting.

### Recommendation
- Enforce a hard cap on `getAllAssetIssues()`/`GetAssetIssueListServlet` result size (analogous to `ASSET_ISSUE_COUNT_LIMIT_MAX`), or deprecate the unpaginated endpoint in favor of `GetPaginatedAssetIssueListServlet` only.
- Have `AssetIssueStore.getAssetIssuesPaginated` iterate with `seek`/limit rather than materializing the entire store before slicing, so the paginated endpoint's cost is also bounded by `limit`, not store size.
- Add a scan-cost-aware or adaptive rate limiter (e.g., cost-weighted token bucket keyed on estimated result size) for full-scan endpoints, distinct from simple request-count QPS limiting in `RateLimiterServlet`.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
