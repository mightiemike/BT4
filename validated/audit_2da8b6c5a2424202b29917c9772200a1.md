Based on my investigation, I found a state-integrity analog in the Aptos replay/backup-verification path that mirrors the bug class from the report: an accounting/verification function that silently omits checking a value it's supposed to authenticate, letting an incorrect result be accepted as valid.

### Title
Replay/backup verification (`ensure_match_transaction_info`) never checks the state-checkpoint (JMT root) hash, letting a corrupted replayed state pass authentication - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by chunk-executor replay verification and backup/replay tooling (`db-tool`'s `replay_on_archive`, the Move debugger/CLI replay commands) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain. The function checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` at all — the code itself documents this gap with an explicit `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates:
- `status()` vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

It never calls `txn_info.state_checkpoint_hash()` and the code contains its own admission of the gap: [2](#0-1) . The `state_checkpoint_hash` is a Jellyfish Merkle Tree root computed separately by the state-checkpoint pipeline in [3](#0-2)  from the *cumulative* state (all resources merklized to that version), not merely the current transaction's write set. The write-set hash and event root hash are derived directly from the `TransactionOutput` itself, so they can match even if the write set was merklized incorrectly into the wrong resulting state root (e.g., a JMT bug, an incorrect base-state supplied to `parent_state_summary.update`, or hot-state/position-state root divergence).

This comparator is the actual authentication check exercised by:
- Chunk-executor replay verification: `verify_execution` in [4](#0-3) 
- Backup archive replay-verify tool: [5](#0-4)  (in `commands.rs` for the debugger flow) and the equivalent call site in `replay_on_archive.rs`.
- CLI/debugger transaction replay: [6](#0-5) 

Because none of these call sites separately re-derive and compare the JMT state-checkpoint root against the backed-up/authenticated `TransactionInfo.state_checkpoint_hash`, a replay whose resulting state tree diverges from the authenticated ledger state (while producing an identical write set and events) is reported as a **successful, verified replay**.

### Impact Explanation
This breaks the proof/commitment invariant that "committed state must match the authenticated ledger root," specifically in the restore/replay verification pivot. An operator restoring from backup, or running `replay-verify`/`replay_on_archive` to validate archived history, can be told the replay is byte-for-byte correct even though the actual Merkle state root (and consequently all downstream Merkle proofs served from that restored database) diverges from the value authenticated by the validator-signed `LedgerInfo`. This can mask a state-divergence bug (hard-fork-class) or a corrupted/malicious backup dataset, and downstream nodes bootstrapped from such a "verified" backup would serve state proofs bound to the wrong root.

### Likelihood Explanation
This requires a pre-existing state-checkpoint-root divergence bug (e.g., in JMT computation, `LedgerStateSummary::update`, or hot/position state merklization) to actually manifest; the comparator itself doesn't create a divergence, it fails to detect one. However, given that `state_checkpoint_hash` is exactly the value these tools exist to protect, and there is no other check anywhere in the cited call paths (`verify_execution`, `replay_on_archive`, CLI replay) that independently authenticates the resulting state root, any future or latent state-checkpoint bug becomes silently undetectable through these verification paths.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `txn_info.state_checkpoint_hash()` (and, when applicable, `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`) against the locally computed checkpoint root for the version being verified, and thread the locally-computed state-checkpoint hash into the callers (`verify_execution`, `replay_on_archive`, CLI replay) so the comparison can actually be performed rather than passing `None`.

### Proof of Concept
Conceptual PoC (cannot be executed without a full node/backup environment):
1. Take a backup chunk where the write set and events for version `V` are unchanged, but simulate/introduce a state-checkpoint root divergence (e.g., feed a different `parent_state_summary` into `DoStateCheckpoint::run`, or a JMT node corruption) such that `last_checkpoint.root_hash()` differs from the authenticated `TransactionInfo.state_checkpoint_hash()` for that version.
2. Run `db-tool replay-on-archive` (or the CLI debugger's transaction replay) over this chunk.
3. Observe `ensure_match_transaction_info` returns `Ok(())` because it only compares `write_set_hash`/`event_root_hash`, even though `state_checkpoint_hash` mismatches — confirming the verification tool reports success despite state divergence, exactly as flagged by the in-code `TODO(trading-native)` comment at [2](#0-1) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
