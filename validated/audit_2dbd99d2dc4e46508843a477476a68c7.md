### Title
Panic on empty L1-handler calldata during `calc_msg_hash` - (File: `crates/starknet_api/src/hash.rs`)

### Summary
`l1_handler_message_hash` (called via `L1HandlerTransaction::calc_msg_hash`) unwraps the calldata's first element with `.expect("Invalid calldata, expected at least from_address")`. This is analogous to the ATS prefetch-plugin crash: a function that processes attacker-influenced data crashes via an unhandled panic path instead of returning an error, when a required precondition (non-empty calldata) is not enforced upstream. [1](#0-0) 

### Finding Description
`l1_handler_message_hash` assumes the transaction's `calldata` always has at least one element (the `from_address`), and unwraps this assumption instead of validating it:
```rust
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
``` [2](#0-1) 

This is invoked from `L1HandlerTransaction::calc_msg_hash` and from RPC/gateway paths that compute the L1-L2 message hash (`apollo_rpc/src/v0_8/api/api_impl.rs`, `apollo_l1_events/src/l1_events_provider.rs::get_txs`) which is exercised on every proposal cycle: [3](#0-2) 

The `from_address`/payload split assumes `calldata` was constructed with an `from_address` prepended by the L1 event scraper. **I was not able to fully verify, within the available tool budget, whether every code path that constructs an `L1HandlerTransaction` (including any RPC-exposed or gateway-facing deserialization path for L1 handler transactions, e.g. `apollo_rpc/src/v0_8/transaction.rs`, `starknet_api/src/executable_transaction.rs`, and `apollo_protobuf/src/converters/transaction.rs`) enforces non-empty calldata before this function is reached.** If any reachable construction path (e.g., a JSON-RPC estimate/simulate call built from an `L1HandlerTransaction` payload with empty `calldata`, or a malformed L1 log payload from an attacker-controlled L1 contract producing a zero-length calldata array) can supply an empty `Calldata`, this `.expect()` will panic the process, matching the "crash on attacker-influenced input" bug class from the ATS report.

### Impact Explanation
If reachable with attacker-controlled empty calldata, this causes a process panic (denial of service) in whatever service invokes `calc_msg_hash` — the L1 events provider (used during block proposal/`get_txs`), or an RPC node servicing `starknet_getMessagesStatus`/related endpoints. A panic during `get_txs` in the sequencer's block-building path could halt block production for that node, which is a network-availability concern (network unable to confirm new transactions) if it affects the active proposer.

### Likelihood Explanation
Likelihood is **unconfirmed** without further verification of all `L1HandlerTransaction` construction sites. The L1 event scraper itself always prepends `from_address`, which would make this path unreachable in the "normal" L1-scraping flow. The main open question is whether any RPC-facing or gateway-facing conversion (not sourced from the trusted L1 scraper) can build an `L1HandlerTransaction`/`Calldata` with zero elements and then call `calc_msg_hash` on it.

### Recommendation
- Replace the `.expect(...)` in `l1_handler_message_hash` with a proper `Result`-returning check (e.g., return a dedicated error variant when `calldata` is empty), per the repo's own stated rule that "Code reachable from HTTP handlers or external input must never use `.unwrap()`, `.expect()`, or unchecked indexing on values derived from that input" [4](#0-3) .
- Audit and enumerate every construction path of `L1HandlerTransaction`/`Calldata` reachable from RPC, gateway, or L1-scraper-untrusted inputs to confirm whether empty calldata can reach `calc_msg_hash`.

### Proof of Concept
Not constructed — reachability from an attacker-controlled, unprivileged entry point (RPC call or malicious L1 message) to a zero-length `Calldata` passed into `calc_msg_hash` was not confirmed within the available investigation. A concrete PoC would require tracing every `L1HandlerTransaction` constructor for a path that permits empty `calldata` before calling `.calc_msg_hash()`.

/// Calculating the message hash of L1 -> L2 message.
/// For more info: <https://docs.starknet.io/documentation/architecture_and_concepts/Network_Architecture/messaging-mechanism/#structure_and_hashing_l1-l2>
pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());

    let payload_length_as_felt =
        Felt::from(u64::try_from(payload.len()).expect("usize should fit in u64"));
    encoded.extend(payload_length_as_felt.to_bytes_be());
```

### Never panic on data reachable from requests
- Code reachable from HTTP handlers or external input must never use `.unwrap()`, `.expect()`, or unchecked indexing on values derived from that input
- Reserve panics for compile-time invariants where failure is a programmer bug, not a runtime possibility
- Return `Result` with a descriptive error variant, or use saturating/capping alternatives
