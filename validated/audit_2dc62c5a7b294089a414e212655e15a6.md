### Title
Unbounded gzip decompression in RPC `decompress_program` allows memory/CPU exhaustion DoS via a decompression-bomb "program" field - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The `decompress_program` helper decompresses a user-supplied, base64-encoded gzip `program` blob without any size or time limit, unlike the sibling `starknet_api::compression_utils::decode_and_decompress_with_size_limit` used elsewhere in the codebase for the same purpose. This is directly analogous to the reported PHP phar/gzip "quine" DoS: an attacker-controlled compressed payload causes the decompressor to expand unboundedly, exhausting node memory/CPU.

### Finding Description
`decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs` decodes base64 and streams the bytes through `GzDecoder::read_to_end` with no cap: [1](#0-0) 

The `// TODO(dan): add time and size limits.` comment on this function confirms the missing bound. Compare this to the properly-bounded equivalent used for the same purpose elsewhere in the codebase (`decompress_with_size_limit` / `decode_and_decompress_with_size_limit`), which caps decompressed output via `.take(max_size + 1)` and errors on overflow: [2](#0-1) 

`decompress_program` is reached from `user_deprecated_contract_class_to_sn_api`, which is invoked when converting a user-submitted `BroadcastedDeclareTransaction::V1` into an `ExecutableTransactionInput` for execution/simulation: [3](#0-2) 

This conversion path is reachable from JSON-RPC methods (e.g. `estimate_fee`/`simulate_transactions`/trace endpoints) that accept a `BroadcastedTransaction` from an unauthenticated RPC caller and execute/simulate it against node state before any fee is charged, i.e., no mempool admission fee/resource-bound gating applies at this decompression step — the bomb triggers on parse/convert, before signature/fee validation completes for these read/simulate RPCs.

### Impact Explanation
An attacker can submit a small (kilobyte-scale) crafted gzip "program" payload whose decompressed size is many orders of magnitude larger (a classic gzip/zip bomb), which `decompress_program` will attempt to fully materialize into memory with no size limit and no read timeout. Repeated calls can exhaust RPC-node memory or pin CPU, degrading or crashing the node process that serves `estimate_fee`/`simulate_transactions`, i.e., a network-availability DoS on nodes serving these RPC methods for the affected code path. This does not directly corrupt committed state, but it can render an RPC/sequencer-facing node unable to serve fee estimation/simulation requests, impacting the network's ability to process new transactions through that node.

### Likelihood Explanation
The path is reachable by any single unprivileged caller submitting a `BroadcastedDeclareV1Transaction` with a malicious `program` field over the public JSON-RPC endpoint — no special privileges, staking, or prior on-chain state are required. Constructing a gzip bomb is straightforward and well documented (as in the original CVE). The only mitigating factor is that this specific path only affects Declare V1 (legacy Cairo0) via `estimate_fee`/`simulate_transactions`, since V2/V3 declare conversions here are unimplemented (`Err(internal_server_error(...))`), but V1 remains actively supported and reachable.

### Recommendation
Apply the same size-bounded decompression used elsewhere (`decompress_with_size_limit`/`decode_and_decompress_with_size_limit` from `starknet_api::compression_utils`) inside `decompress_program`, capping decompressed output to the same `MAX_CAIRO0_PROGRAM_SIZE`/`DEFAULT_MAX_SIERRA_PROGRAM_SIZE`-style limits already enforced in `crates/apollo_protobuf/src/converters/class.rs` and `crates/apollo_http_server/src/deprecated_gateway_transaction.rs`. Additionally, add a decompression time budget to guard against slow-expansion payloads that stay under the size cap but consume excessive CPU.

### Proof of Concept
1. Craft a small `program.json.gz` gzip bomb (e.g., nested/repeated zero-byte gzip streams or a highly compressible large all-zero JSON array) that decompresses to gigabytes from a few KB of input.
2. Base64-encode it and place it as the `program` field of a `BroadcastedDeclareV1Transaction`.
3. Submit it via the RPC `estimate_fee` or `simulate_transactions` method.
4. Observe `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) calling `decoder.read_to_end(&mut decompressed)` with no bound, causing unbounded memory allocation and denial of service on the serving node, before any resource/fee validation can reject the request.

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.

    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
