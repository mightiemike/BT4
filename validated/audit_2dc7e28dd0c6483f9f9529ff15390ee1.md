### Title
Malformed-length `signer-key` in pox-4 silently collapses distinct stackers onto an all-zero signer entry, corrupting the reward-set signing-weight equality - (File: `stackslib/src/chainstate/nakamoto/signer_set.rs`)

### Summary
`RawRewardSetEntry::from_pox_4_tuple` reads the `signer` field returned by the pox-4 contract's `get-reward-set-pox-address` and expects it to be a 33-byte compressed secp256k1 public key. Because the Clarity type `(buff 33)` only enforces a *maximum* length, not a minimum, a stacker can submit a `signer-key` shorter than 33 bytes when calling `stack-stx`/`stack-extend` in pox-4.clar. The Rust-side parser detects the length mismatch but, instead of rejecting the entry, silently substitutes an all-zero 33-byte key: [1](#0-0) 

### Finding Description
`from_pox_4_tuple` pulls `signer` out of the tuple as `buff(SIGNERS_PK_LEN)` and, if the actual length differs, falls back to `[0; SIGNERS_PK_LEN]` (the all-zero key) rather than returning an error: [2](#0-1) 

This zero key is then fed into `StacksChainState::make_signer_set` (via `make_reward_set`), which aggregates all entries sharing the same `signing_key` by summing their `stacked_amt` and computing `weight = stacked_amt / threshold`: [3](#0-2) [4](#0-3) 

Any number of *distinct, unprivileged* stackers can each independently submit a `signer-key` argument that is shorter than 33 bytes (a value they fully control in their own `stack-stx` transaction). Every one of these entries collapses onto the same all-zero `signing_key` and their stacked amounts are merged into a single `NakamotoSignerEntry` with a weight proportional to the *combined* stake, even though the underlying stackers have no shared private key and no one controls the zero key.

This breaks the intended equality that the reward-set/consensus code relies on: *one signing key ⇔ one controllable signer whose weight is exercised only by that key's holder*. Here, weight that the protocol believes is attributable to one identity is actually an unreachable pool contributed by multiple unrelated, uncoordinated (minority) stackers, and it can never be exercised by anyone, since nobody holds the zero private key.

`verify_signer_signatures` and the pox-4 `.signers-voting` contract both compute a `total_weight`/`threshold-weight` from the reward set (`total_signing_weight`, `get-and-cache-total-weight`) and require that a supermajority of *signed* weight reach that threshold: [5](#0-4) [6](#0-5) 

Because the zero-key entry's weight is permanently unsignable, it inflates `total_weight`/`cycle-total-weight` without ever being able to contribute to `total_weight_signed`/`votes-weight`. Depending on how much stake a minority of stackers route into this bucket, this can push the *reachable* threshold unattainable by the honest, key-holding signers for that cycle, or (if the amount is small) merely waste a portion of consensus weight non-deterministically depending on how many distinct stackers happen to submit truncated keys - a condition every node computing the reward set will see identically (since it derives from on-chain data), but which was never intended by the protocol's 1-key-1-signer model.

### Impact Explanation
This is not a case of one honest signer's weight being lost to itself — it is multiple *unprivileged, minority* stackers, none of whom need to collude with a majority, corrupting the mapping from stacked BTC/STX to controllable signing weight. Because the resulting inflated "phantom signer" weight can never be signed for, it can push the effective/reachable weight below the consensus threshold for that reward cycle, i.e., a High-severity minority-triggerable divergence between the recorded consensus threshold and the actually reachable signed weight, bounded to a single reward cycle's signer set (not fee/reward theft, but a threshold/weight equality break consistent with the "signer weight below threshold or from the wrong set" category).

### Likelihood Explanation
Low cost, no majority or coordination required: any single stacker can call `stack-stx` with a `signer-key` buffer shorter than 33 bytes (the Clarity type only bounds the maximum length), and this parsing path (`from_pox_4_tuple`) is exercised deterministically by every node computing the reward set at `pox_4_compute_and_update_signers`/`get_reward_set_epoch2`. Multiple independent (not colluding) stackers doing this by accident or intentionally is a plausible minority-level trigger.

### Recommendation
In `RawRewardSetEntry::from_pox_4_tuple`, treat a `signer` buffer whose length does not equal `SIGNERS_PK_LEN` as a hard error (or drop/replace with a sentinel that is guaranteed unique per malformed entry, e.g. derived from the stacker principal) instead of silently coercing it to the all-zero key, so that unrelated stackers can never be merged into a single fictitious signer identity.

### Proof of Concept
1. Two unrelated stackers, Alice and Bob, each independently call pox-4's `stack-stx` (or `stack-extend`) supplying a `signer-key` buffer of length < 33 bytes (Clarity's `(buff 33)` type only checks the max length, so this is accepted on-chain).
2. When the reward-set/signer-set is computed for the following cycle, `NakamotoSigners::pox_4_compute_and_update_signers` walks the pox-4 reward addresses and calls `RawRewardSetEntry::from_pox_4_tuple` for each entry.
3. Both Alice's and Bob's malformed `signer` fields fail the length check and are coerced to `[0; SIGNERS_PK_LEN]` at `stackslib/src/chainstate/nakamoto/signer_set.rs:311-317`.
4. `StacksChainState::make_signer_set` (`stackslib/src/chainstate/stacks/boot/mod.rs:1039-1065`) merges Alice's and Bob's `stacked_amt` under the single all-zero `signing_key`, producing one `NakamotoSignerEntry` with combined weight, even though neither Alice nor Bob (nor anyone) holds the corresponding private key.
5. This entry's weight is counted in `total_signing_weight`/`cycle-total-weight` used by `verify_signer_signatures` and `.signers-voting`'s `get-threshold-weight`, but can never be signed for, permanently reducing the reachable signed weight relative to the recorded threshold for that reward cycle.
