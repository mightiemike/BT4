### Title
Unbounded `PendingInbounds.Walk` in inbound ballot-terminal hook enables gas-exhaustion DoS on inbound finalization - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
`x/uexecutor`'s `BallotHooks.afterInboundBallotTerminal` performs a full linear scan over the entire `PendingInbounds` collection every time *any* inbound ballot reaches a terminal state (PASSED/REJECTED/EXPIRED). `PendingInbounds` entries are created for every distinct source-chain deposit event observed by validators via `RecordInboundVote`, and their count is effectively driven by ordinary user activity (deposits on the source chain), not by anything privileged or capped on Push Chain. This mirrors the 1inch `ERC20Farmable` bug class: an attacker-influenceable array/collection is iterated in full inside a hot state-transition path, and once its size grows large enough the iteration's gas cost can exceed the block gas limit, causing the enclosing transaction (`MsgVoteInbound`) to fail deterministically for every validator, permanently blocking finalization.

### Finding Description
`x/uexecutor/keeper/inbound.go` `RecordInboundVote` [1](#0-0)  creates a new `PendingInboundEntry` keyed by `utx_key = sha256(source_chain:tx_hash:log_index)` on the first validator vote for any inbound observation. Because `tx_hash`/`log_index` are derived from real source-chain transactions, an unprivileged user can trigger arbitrarily many distinct entries simply by submitting many (even dust-value) deposits on a supported source chain; honest Universal Validators will observe and vote on each one via `MsgVoteInbound`, calling `VoteInbound` [2](#0-1) , which unconditionally calls `RecordInboundVote` for every new inbound before ballot finalization.

When any one of these ballots reaches a terminal state, `CheckIfFinalizingVote` → `MarkBallotFinalized` fires the registered `BallotHooks.AfterBallotTerminal`, which for `INBOUND_TX` ballots calls `afterInboundBallotTerminal`: [3](#0-2) 

This function walks the **entire** `PendingInbounds` map with `h.k.PendingInbounds.Walk(ctx, nil, ...)` looking for the variant matching the just-finalized `ballotID`, only stopping early once found. In the worst case (the matching entry is near the end, or absent) this is a full O(N) iteration over every currently pending inbound entry, each involving a KV-store read and protobuf deserialization, all gas-metered under `storetypes.KVGasConfig()`.

Because `N` (the size of `PendingInbounds`) is driven by ordinary, unprivileged cross-chain deposit activity and has no cap, an attacker can inflate it to a size where this single hook invocation alone exceeds the block's gas limit. Since this hook runs synchronously inside `VoteInbound`, which runs inside the `MsgVoteInbound` message handler used by every honest Universal Validator, this would cause the finalizing `MsgVoteInbound` transaction to run out of gas and fail/revert for every UV attempting to finalize *any* inbound ballot — not just the flooded one — because the hook fires on every terminal transition regardless of which inbound is involved.

### Impact Explanation
This directly threatens the "State safety path" invariant: "only ask consensus or DoS questions when ordinary unprivileged user actions alone can make honest nodes diverge, halt material execution, or persist invalid canonical state." If `PendingInbounds` grows large enough, honest UVs can no longer successfully finalize inbound ballots at all (every finalizing vote transaction fails on gas), which halts the entire inbound processing pipeline for Push Chain — no new `UniversalTx` can be created from inbound deposits, and no PRC20 minting/execution can proceed. This is a chain-wide, unprivileged-triggerable denial of service on a core universal-execution flow (inbound admission), not a network-level DoS, and is reachable purely through default cross-chain deposit submission by any user.

### Likelihood Explanation
The attack requires no privileged role — an ordinary user can generate many low-value/dust deposits on any enabled source chain to inflate `PendingInbounds`. There is no cap, rate-limit, or pruning mechanism observed on `PendingInbounds` growth other than removal upon full ballot resolution, and resolution itself is gated by validator voting throughput, so an attacker can outpace cleanup by submitting deposits faster than validators can finalize them. The precise gas threshold at which this becomes a practical block-gas-limit breach was not independently measured in this review (it depends on the deployed block gas limit and per-entry KV read cost), so exploitability at scale is plausible but unconfirmed without live/benchmarked gas measurements.

### Recommendation
Avoid a full-collection scan on every terminal ballot transition. Options:
- Maintain a direct index from `ballotID` → `utxKey` (e.g., a secondary `collections.Map[string, string]`) so `afterInboundBallotTerminal` can do an O(1) lookup instead of walking all of `PendingInbounds`.
- Alternatively, bound `PendingInbounds` size (e.g., cap total pending entries or per-chain pending entries, with a minimum-deposit-amount threshold to raise the cost of dust spam) and enforce backpressure/rejection of new inbound votes once the cap is hit.
- Add an explicit gas-cost ceiling check before performing the walk and short-circuit/log rather than allowing the hook to consume unbounded gas within a single message execution.

### Proof of Concept
1. Attacker performs a very large number of low-value deposits on an enabled source chain, each producing a unique `(source_chain, tx_hash, log_index)` inbound event.
2. Honest Universal Validators observe and submit `MsgVoteInbound` for each event, causing `RecordInboundVote` to create a corresponding `PendingInboundEntry` for each — `PendingInbounds` grows to size `N` with no cap enforced.
3. Once quorum is reached on any single inbound ballot (attacker's own dust deposits, or any legitimate deposit), `CheckIfFinalizingVote` finalizes it and `BallotHooks.afterInboundBallotTerminal` executes `PendingInbounds.Walk` over all `N` entries in the same transaction.
4. As `N` grows, the gas consumed by this single walk approaches and eventually exceeds the block gas limit, causing the finalizing `MsgVoteInbound` transaction to fail with an out-of-gas error for any validator attempting to finalize an inbound ballot, effectively halting inbound finalization chain-wide until `PendingInbounds` is manually reduced (which itself requires successful finalizations — a self-reinforcing deadlock).

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
