Based on the java-tron `Market` (TRC10 order book) actuator, I found a reachable, unprivileged analog of the described rounding-exploit bug class.

### Title
Market order-matching lets a taker receive a maker's full residual quantity while paying a floor-rounded (under-priced) cost, enabling repeatable value extraction from resting orders - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the amount a taker must pay to consume a maker's remaining order using floor division, but then credits the taker with the maker's *entire, unrounded* remaining sell quantity instead of recomputing the receive amount from the rounded payment. This mirrors the reported staking bug: one side of a share/amount conversion is rounded down for the payer's benefit while the counter-value handed out is not recomputed from that rounded figure, letting the taker systematically underpay for what they receive.

### Finding Description
In the "taker > maker" branch of `matchSingleOrder`: [1](#0-0) 

- `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` — the taker is credited the maker's **exact, full** remaining sell quantity.
- `makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` — this is the price the taker pays, computed with `floorDiv`: [2](#0-1) 

The taker's own remaining sell balance is only decremented by the rounded-down `makerBuyTokenQuantityReceive`: [3](#0-2) 

So the taker pays `floor(makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity)` but receives the *unrounded* `makerSellRemainQuantity` in full — the counter-value is never recomputed from the rounded payment, exactly the flaw the external report calls out ("always recompute `withdraw_amount` with the new rounded `withdraw_share`"). By contrast, in the symmetric "taker < maker" branch the roles are reversed and the maker (not the attacker-controlled taker) receives the full, unrounded amount, so that branch is not exploitable the same way: [4](#0-3) 

The comment at lines 466-474 shows the developers only reasoned about the `makerBuyTokenQuantityReceive == 0` edge case, not the general rounding bias in the taker's favor: [5](#0-4) 

### Impact Explanation
`MarketSellAssetContract` is a fully unprivileged, publicly broadcastable transaction — any account can place sell/buy orders via `MarketSellAssetActuator.validate/execute`: [6](#0-5) 

A taker who is matched against a maker's small leftover order (the "taker > maker" case) is credited that maker's full residual asset amount while only being debited a floor-rounded (smaller) cost. The matching loop repeats up to `MAX_MATCH_NUM` (20) times per transaction: [7](#0-6) [8](#0-7) 

An attacker can construct/target maker orders (their own resting orders, or naturally-occurring small remainders left by other users) with a sell/buy ratio chosen so the floor division loses a meaningful fraction of a unit each match, and repeat this across many matches/transactions to extract asset value from maker-side counterparties at below the maker's intended price — an accounting/asset-value corruption in the exchange's order-matching engine.

### Likelihood Explanation
The rounding bias is deterministic and always present whenever `makerSellRemainQuantity * makerBuyQuantity` is not evenly divisible by `makerSellQuantity` in the "taker > maker" branch — this is the common case for arbitrary integer order sizes, and an attacker fully controls both the maker order (their own resting order, `sellTokenQuantity`/`buyTokenQuantity` up to `getMarketQuantityLimit()`) and the taker order used to sweep it, making the exploit trivially reproducible without needing any privileged role, leaked keys, or malicious peers — only broadcasting ordinary `MarketSellAssetContract` transactions.

### Recommendation
- Always recompute `takerBuyTokenQuantityReceive` from the rounded `makerBuyTokenQuantityReceive` (i.e., derive the amount given out from the amount actually paid), rather than assigning it the maker's full unrounded remaining quantity.
- Alternatively, round `makerBuyTokenQuantityReceive` (the cost charged to the taker) up rather than down in `MarketUtils.multiplyAndDivide` when used for this direction, so the taker never pays less than the fair proportional price for what they receive.
- Add invariant checks ensuring `takerBuyTokenQuantityReceive / makerBuyTokenQuantityReceive` never exceeds `makerSellQuantity / makerBuyQuantity` by more than the intended rounding tolerance.

### Proof of Concept
1. Attacker account A places a maker sell order with `sellTokenId = X`, `sellTokenQuantity = S`, `buyTokenId = Y`, `buyTokenQuantity = B`, chosen so that a later partial fill leaves `makerSellRemainQuantity` where `makerSellRemainQuantity * B` is not exactly divisible by `S` (any generic sizes work; larger `S/B` skew maximizes the rounding loss per match).
2. This order partially fills (or is placed pre-filled to a small remainder) via normal matching, leaving `makerOrderCapsule.getSellTokenQuantityRemain()` small relative to `S`.
3. Attacker account B (or A itself with a second key) submits a `MarketSellAssetContract` selling `Y` for `X` with a large `sellTokenQuantity`, causing the "taker > maker" branch in `matchSingleOrder` to execute:
   - Taker B is credited `takerBuyTokenQuantityReceive = makerSellRemainQuantity` (full).
   - Taker B is only debited `makerBuyTokenQuantityReceive = floor(makerSellRemainQuantity * B / S)`.
4. The difference between the fair proportional cost and the floor-rounded cost is pure loss for maker A / gain for taker B, repeatable across up to 20 matches per transaction and across unlimited transactions/orders.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
