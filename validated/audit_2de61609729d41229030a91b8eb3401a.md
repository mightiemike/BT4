### Title
Unvalidated `GasToken` in outbound gas-refund path lets a user mint arbitrary PRC20 out of thin air - ([File: x/uexecutor/keeper/create_outbound.go])

### Summary
`BuildOutboundsFromReceipt` copies `event.GasToken` straight from the user-triggered `UniversalTxOutbound` EVM log into `OutboundTx.GasToken` with **no registry lookup**, unlike `event.Token` (the bridged asset), which is checked against `uregistryKeeper.GetTokenConfigByPRC20` before being trusted. That unchecked `GasToken` later flows into `applyGasRefund`, which computes `refundAmount = GasFee - GasFeeUsed` and calls `CallUniversalCoreRefundUnusedGas(gasToken, refundAmount, recipient, ...)`, which in turn issues a `DerivedEVMCall` to `UniversalCore.refundUnusedGas(gasToken, amount, recipient, ...)` as the module account.

### Finding Description
This is the closest structural analog to the reported "facilitator borrows and never repays" bug: a value-bearing field (`GasFee`/`GasToken`) that the protocol treats as a promise of already-collected/locked value is trusted from an attacker-controlled input and later used to *release* value (here: a PRC20 "refund"), with no invariant tying the released amount/token back to something actually deposited or registered.

Trace:
1. A user calls the `UniversalGatewayPC` gateway contract to create a withdraw/outbound. The contract emits `UniversalTxOutbound(..., gasToken, gasFee, ...)`. `gasToken` and `gasFee` are attacker-supplied event fields decoded verbatim by `DecodeUniversalTxOutboundFromLog`.
2. `BuildOutboundsFromReceipt` looks up and validates `event.Token` (the bridged asset) via `uregistryKeeper.GetTokenConfigByPRC20`, but assigns `event.GasToken` directly to `outbound.GasToken` with **no equivalent validation** that this address is a registered/whitelisted PRC20 or the canonical gas token for the destination chain (`gasTokenPRC20ByChainNamespace` exists on `UniversalCore` per the ABI but is never queried from `x/uexecutor` Go code to cross-check `outbound.GasToken`).
3. Honest Universal Validators later vote the destination-chain observation, including `gas_fee_used` (the real gas spent on the destination chain). This part is honestly reported.
4. `applyGasRefund` computes `refundAmount = GasFee - GasFeeUsed` using the **unvalidated `GasFee`/`GasToken` from step 1** and calls `CallUniversalCoreRefundUnusedGas`, which performs a module-signed `DerivedEVMCall` to `refundUnusedGas` on the `gasToken` address supplied by the attacker.
5. Because `GasFee` was never checked against anything actually locked/paid by the user (no on-chain confirmation in Go code that this amount of `GasToken` was pulled into a vault, unlike the bridged `Amount`/`Token` which are tied to the actual mint amount from the inbound flow), the "excess" `GasFee - GasFeeUsed` refunded to the user is not backed by any real prior deposit of that token — the module simply instructs `UniversalCore` to mint/deposit `refundAmount` of an attacker-chosen `gasToken` PRC20 to the attacker's own `refundRecipient`.

This mirrors the reported bug precisely: like the Facilitator that borrows vault assets via `_processFacilitatorInteraction` with no repayment check, here the "borrowed" value is the inflated `GasFee` figure declared by the user themselves, and the "repayment" (an actual corresponding deposit/lock of that PRC20 amount) is never verified anywhere in the `x/uexecutor` Go code before the refund mint executes.

### Impact Explanation
If `UniversalCore.refundUnusedGas` performs an unconditional mint/deposit of PRC20 to the recipient (as its sibling `depositPRC20Token` does for inbound deposits), an attacker can:
- Trigger an outbound with a wildly inflated `gasFee` and an arbitrary `gasToken` address of their choosing (e.g., a high-value registered PRC20 they don't actually control the supply of, or even one of their own crafted tokens),
- Have honest validators report a low real `gasFeeUsed`,
- Receive a large "refund" of `gasToken` PRC20 minted to their `refundRecipient` that was never backed by any deposit — i.e., unauthorized PRC20 minting / protocol-fund draining, matching the "unauthorized mint" and "PRC20 accounting corruption" impact classes explicitly in scope.

### Likelihood Explanation
Reachable by any unprivileged user who can call the `UniversalGatewayPC` contract to create an outbound event (a normal, unprivileged user action) and requires no validator or admin collusion — validators only vote the honest destination-chain observation (`gas_fee_used`), which the exploit does not depend on being manipulated. The missing validation is a straightforward gap: every other token/asset field on the outbound path (`event.Token` → `GetTokenConfigByPRC20`) is checked, but `event.GasToken`/`event.GasFee` are not.

### Recommendation
- Validate `event.GasToken` against `uregistryKeeper`'s known/whitelisted PRC20 set (or against the chain's canonical gas token, e.g. via `UniversalCore.gasTokenPRC20ByChainNamespace`) before storing it on `OutboundTx.GasToken`, mirroring the existing `GetTokenConfigByPRC20` check done for `event.Token`.
- Ensure `event.GasFee` corresponds to value actually pulled into `VaultPC`/burned from the user at outbound-creation time (this must be enforced and confirmed either by the gateway contract's on-chain accounting being read back, or by re-deriving `GasFee` from `UniversalCore.getOutboundTxGasAndFees` the same way `buildRevertOutbound` does for revert outbounds, instead of trusting the raw user-emitted event field for the "external" outbound path).
- Add an integration test asserting that `applyGasRefund` cannot mint/refund `GasToken` value that was not previously accounted for/locked, and that an attacker-supplied `GasToken` not matching the registered/canonical gas token for the destination chain is rejected or ignored.

### Proof of Concept
1. Attacker calls `UniversalGatewayPC.withdraw(...)` (or crafts an inbound/outbound event equivalent), passing `gasToken = <any registered high-value PRC20>` and `gasFee = <inflated amount, e.g. 1,000,000>`.
2. `BuildOutboundsFromReceipt` decodes the log and stores `outbound.GasToken`/`outbound.GasFee` verbatim, with no registry validation, per .
3. Honest UVs broadcast/observe the destination-chain tx and vote back a small real `gas_fee_used` (e.g., 50) via `MsgVoteOutbound`.
4. `applyGasRefund` computes `refundAmount = 1,000,000 - 50 = 999,950` and calls `CallUniversalCoreRefundUnusedGas(gasToken, 999950, attackerRecipient, ...)`, per , minting/depositing that amount of the attacker-chosen PRC20 to the attacker with no prior corresponding deposit ever validated in the Go keeper.

Note: I was unable to confirm from this repository whether `UniversalCore.refundUnusedGas`'s Solidity implementation performs an unconditional PRC20 mint/deposit or instead checks a real vault balance before releasing funds — that contract's source is not present in this codebase's indexed scope (it lives in the `pushchain/evm`/core-contracts repo referenced only via ABI here). This is the key uncertainty: if `refundUnusedGas` internally re-derives/validates `gasFee` against its own state rather than trusting the passed-in amount, the impact described above would be mitigated at the Solidity layer, outside what I can verify from the indexed Go code.
