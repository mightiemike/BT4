### Title
TRC10 Exchange liquidity provision/removal (`ExchangeInjectContract`/`ExchangeWithdrawContract`) lack slippage protection and are sandwichable, unlike the swap path - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
Java-tron's built-in TRC10 token-pair AMM ("Exchange") correctly implements the exact mitigation the external report recommends for the swap path: `ExchangeTransactionContract` carries an off-chain-computed `expected` (minimum-received) field that is enforced on-chain in `ExchangeTransactionActuator.doValidate()`. However, the two liquidity operations on the same pool, `ExchangeInjectContract` (add liquidity) and `ExchangeWithdrawContract` (remove liquidity), compute the counter-asset amount purely from the *current* on-chain pool ratio at execution time, with no caller-supplied bound at all. This is precisely the "on-chain same-transaction calculation used for pricing" pattern the report flags as sandwichable in Curve's `add_liquidity`/`remove_liquidity_one_coin`.

### Finding Description
In `ExchangeInjectActuator.execute()`/`doValidate()`, the amount of the counter-token that the exchange creator must supply (or the amount debited) is derived directly from the live pool ratio: [1](#0-0) 

Similarly in `ExchangeWithdrawActuator.execute()`, the counter-token amount returned to the creator is computed from the live ratio with no user-specified minimum: [2](#0-1) 

Compare this to `ExchangeTransactionActuator`, which requires and enforces an `expected` minimum-received value supplied by the caller (calculated off-chain, matching the report's recommendation), rejecting the transaction if the actual output falls short: [3](#0-2) 

No equivalent `expected`/minimum bound exists in either `ExchangeInjectContract` or `ExchangeWithdrawContract` protobuf definitions: [4](#0-3) 

Because `ExchangeTransactionContract` (the swap) is callable by any unprivileged account against the same pool, an attacker can:
1. Front-run the creator's pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction with a large `ExchangeTransactionContract` trade that skews `firstTokenBalance`/`secondTokenBalance` away from the fair ratio.
2. Let the creator's inject/withdraw execute at the skewed ratio (no check prevents this — only a fixed-precision rounding check "Not precise enough" exists in withdraw, which is unrelated to price-fairness): [5](#0-4) 
3. Back-run with an opposite trade to restore the pool price, extracting the value the creator overpaid (on inject) or under-received (on withdraw).

### Impact Explanation
The exchange creator's assets (TRX and/or TRC10 tokens held in the pool) can be siphoned via classic sandwich MEV during liquidity provision/removal, since neither operation validates the resulting exchange rate against any caller-specified tolerance. This is a direct, on-chain accounting loss of protocol/user assets analogous to the reported Curve issue, and it is reachable by any unprivileged account since `ExchangeTransactionContract` (the front/back-run leg) requires no special permission.

### Likelihood Explanation
Likelihood is high: exchange creation, injection, and withdrawal transactions are visible in the mempool before confirmation, and any account can submit the sandwiching `ExchangeTransactionContract` trades against the same `exchange_id`. No privileged role or race condition beyond standard MEV/front-running is required.

### Recommendation
Add a caller-supplied minimum/maximum bound (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator.doValidate()` by rejecting the transaction if the computed counter-token amount falls outside the caller's off-chain-computed tolerance, mirroring the existing `tokenExpected` check in `ExchangeTransactionActuator`.

### Proof of Concept
1. Creator broadcasts `ExchangeWithdrawContract` for exchange `exchange_id`, withdrawing `tokenQuant` of `firstTokenID`, expecting a fair-ratio amount of `secondTokenID`.
2. Attacker sees this pending transaction and front-runs with an `ExchangeTransactionContract` that sells a large amount of `secondTokenID` into the pool, inflating `firstTokenBalance` relative to `secondTokenBalance` (executed via `ExchangeCapsule.transaction`, enforced only by attacker's own `expected` — which attacker sets favorably to themselves).
3. Creator's withdraw executes using the skewed ratio in `ExchangeWithdrawActuator.execute()` lines 74-89, receiving less `secondTokenID` than fair value; no check blocks this since only "Not precise enough" (rounding) is validated, not fairness.
4. Attacker back-runs with the opposite `ExchangeTransactionContract` trade, restoring the ratio and realizing profit equal to the creator's loss.
