This confirms the analog mechanism: an account referencing a global contract via `AccountContract::GlobalByAccount(id)` resolves its code dynamically at call time from `TrieKey::GlobalContractCode { identifier: AccountId(id) }` [1](#0-0) , and that code can be overwritten at any time by the deploying owner simply re-submitting `DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` — there is no timelock, no versioning check tied to a specific caller's pending transaction, and the update is accepted as soon as its nonce is "fresh" (`>=` stored nonce) [2](#0-1) . This is precisely the same class of issue as the OpenQ report: a privileged "owner" account can update shared logic/state that other accounts (callers) depend on, at any time and without any restriction tied to in-flight calls, allowing the owner to frontrun a pending user transaction and change the outcome of that transaction after it was signed/submitted.

### Title
Global contract owner can frontrun in-flight `FunctionCall`s on `GlobalByAccount` contracts by redeploying code with no timelock - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
Contracts deployed with `GlobalContractDeployMode::AccountId` are referenced by many "user" accounts via `UseGlobalContractAction`, which stores `AccountContract::GlobalByAccount(owner_id)` on the user's account [1](#0-0) . The code resolved for every call to such a user account is whatever is currently stored under `TrieKey::GlobalContractCode { identifier: AccountId(owner_id) }`, and the owner can overwrite that code unilaterally and immediately by submitting another `DeployGlobalContractAction`, which simply increments a nonce and republishes new code with no cooldown, quorum, or dependency on any specific pending call [3](#0-2) . Distribution acceptance only requires the incoming nonce be `>=` the currently stored nonce [2](#0-1) , so the owner can redeploy as often as desired, including in direct response to observing a pending user transaction in the mempool/chunk-production window that is about to call a `GlobalByAccount`-referenced contract.

### Finding Description
Any account can become the "owner" of shared logic simply by deploying a contract in `AccountId` mode; other accounts that adopt it via `UseGlobalContractAction` have no say over, and no visibility guarantee into, when the owner changes the code, because there is no versioning pin, allow-list, or delay enforced at the protocol level [4](#0-3) . A user (Alice) who has an existing named account using `GlobalByAccount(owner)`, or who is about to submit `UseGlobalContractAction` followed by a call, can be front-run: the owner observes Alice's transaction (e.g., a withdrawal/claim call) in the transaction pool or an earlier block and submits a competing `DeployGlobalContractAction` under the same `AccountId` identifier. Because chunk producers can include the owner's redeploy transaction ahead of or in the same chunk as Alice's call, and the new code is committed to state (and to same-chunk lookahead via `record_global_contract_deploy`) as soon as its distribution receipt applies on Alice's shard [5](#0-4) , Alice's already-signed transaction can execute against materially different logic than what she intended when she signed it — for example, code that redirects a payout to the owner, removes/disables a withdrawal method, or otherwise resets state the way the OpenQ bounty-owner exploit reset `payoutSchedule`/`tierWinners` to frontrun a claimer.

### Impact Explanation
This enables the deploying/"owner" account of a `GlobalByAccount` contract to unilaterally and atomically change the semantics of every downstream account's calls with no on-chain restriction, which can result in unauthorized value movement (funds routed differently than the signer intended) or permanently frozen functionality (a claim/withdraw method silently removed) for any user relying on that shared contract. Because this is reachable purely via ordinary `DeployGlobalContractAction`/`UseGlobalContractAction` transactions available to any signer, it fits the class of privileged-update frontrunning described in the source report, mapped onto NEAR's global-contract-by-account feature.

### Likelihood Explanation
Likelihood depends on adoption of `GlobalContractDeployMode::AccountId` for financially meaningful shared contracts (e.g., shared vault/claim logic) and on an owner willing to abuse the built-in update mechanism; there is no cryptographic or protocol restriction preventing it, only social/reputational trust in the deploying account, exactly mirroring the "no time lock or restriction" root cause in the OpenQ report.

### Recommendation
Consider adding protocol-level safeguards for `AccountId`-mode global contracts analogous to the OpenQ remediation: e.g., a mandatory delay between deploy and activation of new code (so pending transactions signed against the old code cannot be silently redirected), or a mechanism for callers to pin/lock the code version their `UseGlobalContractAction` depends on so an owner cannot alter behavior underneath an in-flight transaction.

### Proof of Concept
1. Owner account `O` deploys a contract via `DeployGlobalContractAction { deploy_mode: AccountId }` implementing a `claim()` method that pays out to `predecessor_id` [6](#0-5) .
2. User `A` submits `UseGlobalContractAction { contract_identifier: AccountId(O) }` on her own account, then later signs and broadcasts a `FunctionCall("claim")` transaction to herself.
3. `O` observes `A`'s pending `claim()` transaction and submits a new `DeployGlobalContractAction` under the same `AccountId` identifier with code that guts/redirects the `claim()` logic (e.g., makes it a no-op or pays `O` instead).
4. Because nonce freshness only requires `>=` (not tied to any specific caller/transaction), and the new code is committed as soon as its `GlobalContractDistributionReceipt` reaches `A`'s shard [7](#0-6) , `A`'s already-signed `claim()` transaction executes against the new, owner-controlled logic instead of the logic she intended when she signed her transaction.

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

// Checks if the incoming nonce is fresh and updates the stored nonce. Returns
// true if the nonce is fresh, false if it's stale. The nonce is set
// immediately and the freshness check allows the same nonce (>=).
fn check_and_update_nonce(
    global_contract_data: &GlobalContractDistributionReceipt,
    identifier: &GlobalContractCodeIdentifier,
    state_update: &mut TrieUpdate,
) -> Result<bool, RuntimeError> {
    let nonce_key = TrieKey::GlobalContractNonce { identifier: identifier.clone() };
    let stored_nonce = get_nonce(state_update, &nonce_key)?;
    let incoming_nonce = global_contract_data.nonce();

    // Allow the same nonce since the nonce is updated immediately when
    // initiating distribution to prevent multiple distributions with the same
    // nonce from being initiated.
    if incoming_nonce < stored_nonce {
        return Ok(false);
    }

    set_nonce(state_update, nonce_key, incoming_nonce);
    Ok(true)
}
