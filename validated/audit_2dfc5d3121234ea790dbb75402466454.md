### Title
`liquidity_cap` in `TokenConfig` is validated but never enforced before minting PRC20 tokens on inbound deposit - (File: x/uexecutor/keeper/handler.go)

### Summary
`TokenConfig.LiquidityCap` is documented as the "max supply cap for this token" [1](#0-0) , and `ValidateBasic` requires it to be a non-empty value when a token is registered [2](#0-1) . However, the actual PRC20 minting path (`depositPRC20` → `CallPRC20Deposit`) never reads or checks this field before minting — it only reads `NativeRepresentation.ContractAddress` and forwards the raw inbound amount straight into the EVM mint call. This is the same class of bug as the ERC-4626 `maxDeposit()` report: a declared, on-chain-visible limit exists in the schema but is not enforced in the state-mutating path that it is supposed to gate.

### Finding Description
`depositPRC20` in `x/uexecutor/keeper/handler.go` fetches the token config, extracts the PRC20 contract address, parses the inbound `amountStr`, and immediately calls `CallPRC20Deposit` with that raw amount — no comparison against `tokenConfig.LiquidityCap` or the token's current total supply occurs anywhere in this path: [3](#0-2) 

`CallPRC20Deposit` then issues a `depositPRC20Token` derived EVM call as the module account, with `amount` passed through unchanged: [4](#0-3) 

This is invoked from the inbound execution flows (`ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`) which are driven by honest-validator-finalized inbound observations of user-controlled source-chain deposits — an ordinary unprivileged user can deposit any amount on the source chain gateway, and once validators observe/vote it, Push Chain mints the corresponding PRC20 amount on Push Chain with no cap check: [5](#0-4) [6](#0-5) 

A repo-wide search for `LiquidityCap` shows it appearing only in protobuf/type definitions and tests — it is never referenced by any keeper logic in `x/uexecutor` that performs the mint/deposit call. I could not find a Solidity-side cap check either (no `.sol` file in this repo scope references liquidity/maxSupply), but the PRC20 contract source lives in a separate repository (`push-chain-core-contracts`) not indexed here, so I cannot fully confirm or rule out a supply cap enforced purely inside the Solidity `PRC20.sol` contract itself. Within the scope of this repository (`x/`, `universalClient/`, `precompiles/usigverifier`), no enforcement exists.

### Impact Explanation
If `LiquidityCap` is intended as the sole cap-enforcement mechanism (as its field comment states) and is not additionally enforced by the PRC20 contract itself, an unprivileged external attacker can deposit funds on any registered source chain in amounts exceeding the configured liquidity cap, causing unauthorized/uncapped PRC20 minting on Push Chain. This directly corrupts PRC20 accounting and token-mapping invariants and falls within the "unauthorized mint" and "corruption of PRC20 accounting" allowed-impact categories, since it requires no privileged actor — only an honest set of validators relaying a real, unprivileged user's inbound deposit.

### Likelihood Explanation
Likelihood is uncertain without visibility into the `PRC20.sol` implementation. If the Solidity contract itself enforces a max-supply/liquidity check (mirroring how Solmate's ERC4626 enforces limits in `afterDeposit` while `maxDeposit()` misreports them), then this Go-side gap is "only" a reporting/consistency defect analogous to the original report, not an exploitable mint bypass. If the contract has no such check (relying on the registry's `liquidity_cap` being enforced off-chain/on the Go side, which it is not), then any user depositing more than the intended liquidity cap on a source chain, with no chain-side action required beyond a normal deposit, will have their full uncapped amount minted — making this trivially and repeatedly triggerable via ordinary deposit flows.

### Recommendation
Enforce `tokenConfig.LiquidityCap` in `depositPRC20` (x/uexecutor/keeper/handler.go) before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` — query the PRC20's current total supply via a view call, and reject (or clamp with a revert/refund path) any deposit that would push total minted supply above the configured cap, consistent with how the ERC-4626 fix would require `maxDeposit()` to reflect the true enforceable ceiling.

### Proof of Concept
Not independently reproducible from this repository alone: exploitability hinges on whether `PRC20.sol` (in the separate `push-chain-core-contracts` repo) enforces any supply/liquidity limit internally. Within the indexed Go code, the trace is: attacker deposits arbitrary amount on source-chain gateway → honest validators vote and finalize the inbound ballot → `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload` call `depositPRC20` → `CallPRC20Deposit` mints the full raw `inbound.Amount` with zero reference to `tokenConfig.LiquidityCap` at any point in the call chain shown above.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
