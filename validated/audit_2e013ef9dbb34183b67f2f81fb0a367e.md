This confirms a clear, well-documented design pattern in nearcore that structurally mirrors the PoolTogether `swapYieldSource` bug class: `GlobalContractDeployMode::AccountId` lets a contract "owner" account silently redeploy the code that other accounts have opted into referencing, at any point, without any consent, notice, or timelock from those relying accounts.

### Title
Instant, unauthorized code takeover of accounts referencing a `GlobalByAccount` global contract via redeploy of `DeployGlobalContract` (`AccountId` mode) - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
When an account calls `UseGlobalContract` with a `GlobalContractIdentifier::AccountId(owner)`, its code pointer is set to `AccountContract::GlobalByAccount(owner)` [1](#0-0) . The `owner` account can, at any later time and with a single self-signed `DeployGlobalContract` transaction using `GlobalContractDeployMode::AccountId`, overwrite the code stored under that identifier [2](#0-1) , and that new code is what every referencing account will run on its very next `FunctionCall`. There is no timelock, no opt-in re-confirmation by the relying accounts, and no way for those accounts to pin a specific version once they choose `AccountId` mode — this is the exact structural analog of `swapYieldSource`: a trusted party can swap the logic that controls other parties' funds/behavior at will.

### Finding Description
- `GlobalContractDeployMode::AccountId` is explicitly documented: "This allows the owner to update the contract for all its users" [3](#0-2) .
- `action_deploy_global_contract` lets the owner redeploy under the same `AccountId` identifier at will, with no restriction other than paying storage cost [4](#0-3) .
- `initiate_distribution` computes the identifier as `GlobalContractIdentifier::AccountId(account_id)` for `AccountId` mode and bumps a nonce, then propagates the new code to all shards — this is a full code swap under the identifier that other accounts already reference [5](#0-4) .
- Any account that consumed `UseGlobalContract(AccountId(owner))` stores only `AccountContract::GlobalByAccount(owner)` — a live pointer, not a pinned snapshot — so it will execute whatever code currently sits at that identifier the next time it is called [6](#0-5) .
- The test suite explicitly demonstrates this "code swap" behavior as intended functionality: deploying a trivial contract, then redeploying real code under the same `AccountId`, changes what all referencing accounts run without those accounts taking any further action [7](#0-6) .

The relying account (analogous to "old yield source depositors" in the original report) has no cryptographic or protocol guarantee that the code it is running today is the same code it consented to when it called `UseGlobalContract`. The "owner" (analogous to `onlyOwnerOrAssetManager`) is just a single account with a single access key — no multisig, no governance, no timelock is enforced by the protocol.

### Impact Explanation
Any account using `GlobalByAccount` referencing can have its entire behavior rewritten by the referenced owner at any time. If that account holds a balance and has any automation (e.g., relayer patterns, `FunctionCall` access keys with allowance, scheduled yield/resume flows, or Zero-Balance-Account patterns as shown in `setup_zba_global_contract`), the owner can push malicious code that, on next invocation, transfers away the account's NEAR balance or otherwise abuses its identity/permissions [8](#0-7) . Because global contract distribution is shard-wide and every account referencing that `AccountId` picks up the new code, this is a systemic, one-to-many rug: a single malicious redeploy transaction compromises every account across all shards that opted into that global contract by account id.

### Likelihood Explanation
This requires no privileged network role — it is reachable purely through two ordinary, unprivileged transaction types: `DeployGlobalContract` (by the code owner) and `UseGlobalContract` (by any account that chooses to reference that owner's code). Both are documented, first-class, publicly available actions with no additional gating [9](#0-8) . Any account/dApp/wallet that references a third-party global contract by `AccountId` (rather than by immutable `CodeHash`) is exposed; the owner needs only a normal signed transaction to execute the swap.

### Recommendation
- Strongly recommend `CodeHash` mode for any account holding meaningful funds; treat `AccountId` mode as inherently mutable/untrusted, and surface this prominently in wallet/RPC tooling (e.g., a warning on `UseGlobalContractByAccountId`).
- Consider adding an optional pinning mechanism so a consuming account can pin to a specific `nonce`/version of an `AccountId`-mode global contract, and require an explicit re-`UseGlobalContract` action to move to a newer version rather than an implicit live pointer.
- Consider a protocol-level cool-down/timelock on redeploys of `AccountId`-mode global contracts that already have downstream consumers, mirroring the "TimeLock" mitigation recommended in the original finding.

### Proof of Concept
1. Account `owner.near` deploys a benign contract as a global contract with `GlobalContractDeployMode::AccountId` [10](#0-9) .
2. Victim accounts call `UseGlobalContract(GlobalContractIdentifier::AccountId(owner.near))`, setting `AccountContract::GlobalByAccount(owner.near)` on their accounts [11](#0-10) .
3. At any later time, `owner.near` submits a new `DeployGlobalContract` transaction (still `AccountId` mode) containing malicious WASM that, e.g., on any invocation issues a `Transfer` action draining the caller account's balance to an attacker-controlled account.
4. The distribution receipt overwrites the code stored under `GlobalContractCodeIdentifier::AccountId(owner.near)` shard-by-shard [12](#0-11) .
5. The next `FunctionCall` receipt sent to any victim account resolves to the new malicious code (per `test_global_contract_update`'s demonstrated mechanics [13](#0-12) ), executing the drain with no additional consent from the victim.

pub enum GlobalContractDeployMode {
    /// Contract is deployed under its code hash.
    /// Users will be able reference it by that hash.
    /// This effectively makes the contract immutable.
    CodeHash,
    /// Contract is deployed under the owner account id.

    AccountId,
}

**Outcome**:

- First, the provided code is made available as global contract on the current shard.
- The same code propagates globally, shard by shard.
- Eventually, all accounts on all shards can reference the submitted code by the corresponding global contract identifier.

### Errors

**Validation Error**:

- `ContractSizeExceeded` if the provided WebAssembly code is larger than `max_contract_size` (4MiB).

**Execution Error**:

- `LackBalanceForState` if the account does not hold enough NEAR to cover the added storage.
