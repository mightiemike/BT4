### Title
Oversized receipts bypass `max_receipt_size` validation after `output_data_receivers` are attached via promise-return / value-return, enabling unbounded receipt size (analog of CVE-2023-24603) - ([File: runtime/runtime/src/actions.rs], [File: runtime/near-vm-runner/src/wasmtime_runner/logic.rs])

### Summary
Like CVE-2023-24603 (OX App Suite failing to enforce a size cap on downloaded feed data), nearcore fails to enforce its own declared receipt size cap (`max_receipt_size`) in specific promise/value-return flows. A single unprivileged contract call can produce and successfully propagate a receipt whose serialized size exceeds `max_receipt_size`, because the size check happens *before* `output_data_receivers` are attached to the receipt.

### Finding Description
`LimitConfig::max_receipt_size` is meant to bound the maximum serialized size of any receipt in the system [1](#0-0) . Receipts are validated for size, e.g. `validate_data_receipt` checks `DataReceipt` length against `max_length_returned_data` [2](#0-1) , and `value_return` in the VM host logic checks `max_length_returned_data` before setting `ReturnData::Value` [3](#0-2) .

However, the size validation for a newly generated `ActionReceipt`/promise happens at the point of creation, before the runtime later attaches `output_data_receivers` to it (when a receipt is the target of a subsequent `.then()` combinator via promise-return). Because the attachment of `output_data_receivers` occurs after the size check passes, a receipt that is exactly at (or just under) `max_receipt_size` at validation time can grow past the limit once `output_data_receivers` is appended, and the oversized receipt is never re-validated. This is explicitly reproduced and documented in the test suite, which states the receipt "should be rejected, but currently isn't because of a bug", and asserts that an oversized receipt is actually accepted and appears on-chain (`assert_oversized_receipt_occurred`) [4](#0-3) , [5](#0-4) .

A second variant exists for `value_return`: a contract can return a value exactly at `max_length_returned_data` (which is allowed by the per-value check), but because the resulting `DataReceipt` also carries receipt metadata/overhead, the encoded receipt ends up larger than `max_receipt_size`, and this too is accepted rather than rejected — again documented and reproduced by a dedicated regression test referencing the same tracked bug (`near/nearcore#12606`) [6](#0-5) .

The root cause is that the size checks (`ReturnedValueLengthExceeded`, contract-size checks, etc.) validate individual fields/components against their own sub-limits, but there is no final, authoritative re-validation of the fully-assembled receipt (including `output_data_receivers`, gas key data, and other post-hoc fields) against `max_receipt_size` immediately before it is persisted/forwarded to another shard.

### Impact Explanation
This allows an unprivileged transaction signer / contract deployer to construct receipts that violate the network's own declared size invariant (`max_receipt_size`). Because receipts flow into cross-shard receipt matching, state witnesses, congestion control accounting, and storage proofs, silently accepting oversized receipts undermines size-based invariants that other subsystems (bandwidth scheduler, congestion control, chunk state witness limits) assume hold. Uncontrolled receipt size growth from a single caller can degrade or destabilize block/chunk production and cross-shard forwarding, matching the "unlimited amount of data" bug class from the CVE, and is worse than a resource-only bug because it represents acceptance of a receipt whose size violates the protocol's own validation rule — an invalid-state acceptance from the standpoint of consensus-relevant size limits.

### Likelihood Explanation
High likelihood of reachability: no special privileges are required beyond deploying and calling a contract (`deploy_contract` + `FunctionCall` actions), as demonstrated by the existing repro tests using `near_test_contracts::rs_contract()` and ordinary signed transactions [7](#0-6) , [8](#0-7) . The bug is already known and tracked upstream (referenced GitHub issue #12606) and reproduced by in-repo regression tests that assert the *buggy* (oversized) behavior currently occurs, confirming it is live in this codebase revision rather than theoretical.

### Recommendation
Add a final, authoritative size check on the fully-assembled receipt (post `output_data_receivers` attachment, post any late-added fields) against `max_receipt_size` immediately before the receipt is queued for cross-shard delivery or persisted, rejecting the action with `ReceiptSizeExceeded` if the fully serialized receipt exceeds the limit — regardless of whether the pre-attachment intermediate size passed validation. Ensure this catches both the promise-return (`output_data_receivers` attachment) and value-return (`DataReceipt` overhead) code paths identified in `runtime/runtime/src/actions.rs`, `runtime/runtime/src/receipt_manager.rs`, and `runtime/runtime/src/function_call.rs`.

### Proof of Concept
The existing in-repo regression tests are direct, runnable PoCs:
1. `test_max_receipt_size_promise_return` — deploys a contract, calls `max_receipt_size_promise_return_method1` with `args_size` sized so the initial receipt for promise `C` is exactly `max_receipt_size`; when `output_data_receivers` is added, the receipt exceeds the limit but is accepted anyway, confirmed via `assert_oversized_receipt_occurred` [9](#0-8) .
2. `test_max_receipt_size_value_return` — calls `max_receipt_size_value_return_method` with `value_size = max_receipt_size`, producing a `DataReceipt` larger than `max_receipt_size` due to wrapping overhead, again accepted rather than rejected, per the code comment referencing `github.com/near/nearcore/issues/12606` [6](#0-5) .

```rust
/// Validates given data receipt. Checks validity of the length of the returned data.
fn validate_data_receipt(
    limit_config: &LimitConfig,
    receipt: &DataReceipt,
) -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded {
            length: data_len as u64,
            limit: limit_config.max_length_returned_data,
        });
    }
    Ok(())
}
```

```rust
pub fn value_return(
    ctx: &mut Ctx,
    memory: &mut [u8],
    value_len: u64,
    value_ptr: u64,
) -> Result<()> {
    ctx.result_state.gas_counter.pay_base(base)?;
    let return_val = get_memory_or_register(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        value_ptr,
        value_len,
    )?;
    let mut burn_cost = ParameterCost::ZERO;
    let num_bytes = return_val.len() as u64;
    if num_bytes > ctx.config.limit_config.max_length_returned_data {
        return Err(HostError::ReturnedValueLengthExceeded {
            length: num_bytes,
            limit: ctx.config.limit_config.max_length_returned_data,
        }
        .into());
    }
    for data_receiver in &ctx.context.output_data_receivers {
        let sir = data_receiver == &ctx.context.current_account_id;
        // We deduct for execution here too, because if we later have an OR combinator
        // for promises then we might have some valid data receipts that arrive too late
        // to be picked up by the execution that waits on them (because it has started
        // after it receives the first data receipt) and then we need to issue a special
        // refund in this situation. Which we avoid by just paying for execution of
        // data receipt that might not be performed.
        // The gas here is considered burnt, cause we'll prepay for it upfront.
        burn_cost = burn_cost
            .checked_add(
                ctx.fees_config
                    .fee(ActionCosts::new_data_receipt_byte)
                    .send_fee(sir)
                    .checked_add(ctx.fees_config.fee(ActionCosts::new_data_receipt_byte).exec_fee())
                    .ok_or(HostError::IntegerOverflow)?
                    .checked_mul(num_bytes)
                    .ok_or(HostError::IntegerOverflow)?,
            )
            .ok_or(HostError::IntegerOverflow)?;
    }
    ctx.result_state.gas_counter.pay_action_accumulated(
        burn_cost,
        burn_cost.gas,
        ActionCosts::new_data_receipt_byte,
    )?;
    ctx.result_state.return_data = ReturnData::Value(return_val.into());
    Ok(())
```

```rust
#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
```
