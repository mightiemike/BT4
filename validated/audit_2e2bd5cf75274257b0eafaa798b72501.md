### Title
Hardened resource-accounting overflow checks throw uncaught `ArithmeticException` in execution-path code that must always be executable (`ResourceProcessor.increaseV2`, `RepositoryImpl.usageToBalance`) - ([File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java])

### Summary
java-tron introduced a "hardened" resource-accounting mode (`VMConfig.allowHardenResourceCalculation()` / `DynamicPropertiesStore.saveAllowHardenResourceCalculation`) that replaces legacy `long`/`double` bandwidth and energy math with `BigInteger` arithmetic plus `longValueExact()`/`divideCeilExact()` calls. This mirrors exactly the Cache.sol pattern in the report: normal-path arithmetic that used to silently wrap or lose precision now throws on overflow. Some call sites gracefully surface this as a validated failure, but several sit inside the *execute*/state-mutation path of core resource-liveness operations (bandwidth/energy consumption, delegate/undelegate, unfreeze) where a thrown `ArithmeticException` is not caught and propagates as an unexpected `RuntimeException` through the actuator pipeline.

### Finding Description
The hardening code paths are in `ResourceProcessor.increase()` / `increaseV2()` / `unDelegateIncreaseV2()` (`chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java:86-260`) and in `RepositoryImpl.usageToBalance()` / `getUsage()` / `calculateGlobalEnergyLimit()` (`actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java:256-288, 940-986`). When `hardenCalculation()`/`hardenResourceCalculation()` is true, these methods do: [1](#0-0) [2](#0-1) 

`longValueExact()`/`divideCeilExact()` throw an unchecked `ArithmeticException` whenever the `BigInteger` result exceeds `Long` range — this is confirmed directly by the project's own tests (`testGlobalEnergyLimitOverflowDetectedWithHardening`, `testUsageToBalanceOverflowDetectedWithHardening`, `testIncreaseV2OverflowDetected`, `testIncreaseOverflowDetectedWithHardening`) which explicitly assert `ArithmeticException` is thrown: [3](#0-2) [4](#0-3) 

These methods are invoked directly from the *execution* (not just validation) phase of consensus-critical, "should always succeed" operations:
- `EnergyProcessor.useEnergy()` calls `increase(...)` while mutating account energy usage as part of every smart-contract transaction: [5](#0-4) 
- `BandwidthProcessor.useAccountNet()`/`consume()` calls `increase(...)` for every transaction's bandwidth billing: [6](#0-5) 
- `UnDelegateResourceProcessor.execute()` and `WithdrawExpireUnfreezeProcessor.execute()` (TVM native-contract equivalents of `withdraw`/`redeem` in the Euler report) call `processor.unDelegateIncrease(...)` / mutate balances directly with no `try/catch` around the arithmetic: [7](#0-6) [8](#0-7) 

Crucially, unlike `TransferActuator.execute()`, which explicitly catches `ArithmeticException` and converts it into a `ContractExeException` (a controlled failure): [9](#0-8) 

...the resource-processor execute paths above have **no such catch**. The generic actuator dispatch loop in `RuntimeImpl.execute()` also does not catch `ArithmeticException`/`RuntimeException` around `act.execute(...)`: [10](#0-9) 

This is the same "some parts handle overflows properly, other parts still revert" pattern described in the report: `validate()` methods (e.g. `WithdrawExpireUnfreezeActuator.validate()`, `WithdrawBalanceActuator.validate()`) use `LongMath.checkedAdd` wrapped in try/catch to reject cleanly at validation time, but the *execute* phase of resource accounting (bandwidth/energy usage, delegate/undelegate) has no equivalent guard once the hardened arithmetic path is active.

### Impact Explanation
If a value passed into the hardened `BigInteger` arithmetic (account usage, window size, frozen balance, total weight, etc.) is large enough to overflow `Long` after the internal multiplication (e.g. `usage * remainWindowSize`, `frozeBalance * totalLimit`), `longValueExact()`/`divideCeilExact()` throws `ArithmeticException` inside the execute-time mutation of an actuator or resource processor, rather than inside `validate()`. Because this occurs during block-applying transaction execution (`EnergyProcessor.useEnergy`, `BandwidthProcessor.consume`, `UnDelegateResourceProcessor.execute`, `WithdrawExpireUnfreezeProcessor.execute`) and is not caught, it surfaces as an uncaught `RuntimeException` in the actuator execution pipeline. This breaks the liveness guarantee that once a transaction is validated it should be able to execute deterministically — a transaction that should succeed (unfreeze/withdraw/undelegate/normal bandwidth or energy consumption) can instead abort abnormally, and depending on how the surrounding block-application code in `Manager`/`TransactionTrace` handles unexpected `RuntimeException` (not explicitly `ContractExeException`), this can propagate further than intended, risking inconsistent transaction processing or a processing halt for that transaction/block — the same "liveness break" class identified in the Euler report for `withdraw`/`redeem`/`liquidate`.

### Likelihood Explanation
This is gated behind the `allowHardenResourceCalculation` dynamic parameter (a governance-controlled flag), so it is only live once that feature is enabled on the chain. Given the accumulating nature of usage/window-size fields (long-lived accounts with large frozen balances, long window sizes, or values manipulated indirectly via repeated freeze/delegate/undelegate operations), it is plausible for unprivileged users interacting normally (freezing large balances, delegating/undelegating resources repeatedly, or triggering many transactions) to eventually push these intermediate products past `Long.MAX_VALUE`, especially in `unDelegateIncreaseV2`'s `remainUsage * remainWindowSize + usage * windowSize * WINDOW_SIZE_PRECISION` computation, which multiplies several already-large fields together. I could not fully verify (due to running out of tool calls) whether the top-level block-processing code in `Manager`/`TransactionTrace` catches generic `RuntimeException` around `trace.exec()`/actuator execution, which would determine whether this degrades to "transaction fails inside block" versus "block processing throws and halts" — this is the main remaining uncertainty.

### Recommendation
- Wrap all hardened-arithmetic calls that occur inside actuator/processor `execute()` paths (`EnergyProcessor.useEnergy`, `BandwidthProcessor.consume`/`useAccountNet`, `ResourceProcessor.increase/increaseV2/unDelegateIncreaseV2`, `UnDelegateResourceProcessor.execute`, `WithdrawExpireUnfreezeProcessor.execute`, `RepositoryImpl.usageToBalance/getUsage/calculateGlobalEnergyLimit`) in explicit `try { } catch (ArithmeticException e) { throw new ContractExeException(...); }`, consistent with how `TransferActuator.execute()` and the `validate()` methods already do.
- Alternatively, ensure `validate()` for every actuator that reaches hardened arithmetic performs the same overflow check pre-emptively (as `WithdrawExpireUnfreezeActuator.validate()` does for balance addition) so overflow is rejected before mutation begins, guaranteeing `execute()` cannot throw.
- Add integration-level tests that exercise the hardened arithmetic paths through the full actuator/`TransactionTrace`/`Manager` block-application pipeline (not just unit tests of the processor methods in isolation) to confirm an overflow is converted into a normal transaction failure rather than an unhandled exception during block processing.

### Proof of Concept
Not independently executed against a running node (no filesystem/terminal access in this session); the concrete unit-level trigger is demonstrated by the project's own tests, e.g.: [4](#0-3) 
which sets `lastUsage = Long.MAX_VALUE / 10` with hardening enabled and shows `processor.increaseV2(...)` throws `ArithmeticException`. To reproduce the liveness-break scenario end-to-end, a background agent with repo access should drive an account through repeated freeze/delegate/undelegate cycles (or directly construct account state with large `usage`/`windowSizeV2` values) with `allowHardenResourceCalculation=1`, then invoke `UnDelegateResourceActuator`/`WithdrawExpireUnfreezeActuator`/a normal `TriggerSmartContract` transaction through the full `Manager`/`TransactionTrace`/`RuntimeImpl` pipeline to confirm whether the resulting `ArithmeticException` is caught as a graceful transaction failure or escapes as an unhandled `RuntimeException` during block application.

    long energyUsage = accountCapsule.getEnergyUsage();
    long latestConsumeTime = accountCapsule.getAccountResource().getLatestConsumeTimeForEnergy();
    long energyLimit = calculateGlobalEnergyLimit(accountCapsule);
    long newEnergyUsage;
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newEnergyUsage = increase(energyUsage, 0, latestConsumeTime, now);
    } else {
      // only participate in the calculation as a temporary variable, without disk flushing
      newEnergyUsage = recovery(accountCapsule, ENERGY, energyUsage,
          latestConsumeTime, now);
    }

    if (energy > (energyLimit - newEnergyUsage)
        && dynamicPropertiesStore.getAllowTvmFreeze() == 0
        && !dynamicPropertiesStore.supportUnfreezeDelay()) {
      return false;
    }

    long latestOperationTime = dynamicPropertiesStore.getLatestBlockHeaderTimestamp();
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newEnergyUsage = increase(newEnergyUsage, energy, now, now);
    } else {
      // Participate in calculation and flush disk persistence
      newEnergyUsage = increase(accountCapsule, ENERGY, energyUsage, energy,
          latestConsumeTime, now);
    }

    accountCapsule.setEnergyUsage(newEnergyUsage);
    accountCapsule.setLatestOperationTime(latestOperationTime);
    accountCapsule.setLatestConsumeTimeForEnergy(now);

  public long execute(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = ownerCapsule.getInstance().getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze <= 0) {
      return 0;
    }
    ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
        .setBalance(ownerCapsule.getBalance() + totalWithdrawUnfreeze)
        .build());
    List<Protocol.Account.UnFreezeV2> newUnFreezeList = getRemainWithdrawList(unfrozenV2List, now);
    ownerCapsule.clearUnfrozenV2();
    ownerCapsule.addAllUnfrozenV2(newUnFreezeList);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    return totalWithdrawUnfreeze;
  }
