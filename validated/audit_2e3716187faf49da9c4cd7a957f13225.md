### Title
Bad-debt socialization requires success across all remaining debt assets, permanently blocking liquidation of an unhealthy position - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate()` bundles the seizure of a borrower's last collateral with a mandatory "socialize all remaining debt" step across every other debt asset the borrower holds. That step is implemented as a `fold` over `socialize-debt-asset` that silently absorbs a per-asset failure into an accumulator, but the calling function then hard-reverts the *entire* liquidation if that accumulator ever reports failure for a single asset. This mirrors the `PermissionlessBasicPoolFactory.withdraw` bug class: a primary, otherwise-successful user operation (here, liquidation of a genuinely unhealthy position) is made conditional on the success of an unrelated, secondary per-asset step, and one failing item can permanently strand the whole operation.

### Finding Description
`liquidate()` in `mainnet/contracts/market/v0-4-market.clar` performs, within one atomic call:
1. `vault-system-repay` (debt token pulled from liquidator),
2. `debt-remove-scaled` / `collateral-remove` on `.v0-market-vault`,
3. If `no-collateral-left` is true, a mandatory bad-debt socialization pass over every *other* debt asset the borrower still owes, via:

```
(socialization-result (fold socialize-debt-asset fresh-debt-list { borrower: borrower, success: true }))
(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)
``` [1](#0-0) 

`socialize-debt-asset` is written to *absorb* a failure for a given asset into `{ success: false }` and short-circuit the remaining fold items rather than raising an exception at that point:
```
(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  (if (not (get success acc))
      acc
      (let (...)
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            (map-set index-cache ... (unwrap! (vault-accrue asset-id) failed-status))
            (unwrap! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-debt asset-id) failed-status)
          acc)))
``` [2](#0-1) 

The absorbed failure is then converted right back into a hard `asserts!` revert at the `liquidate` call site (line 1548 above). Because Clarity contract calls execute atomically, that final `asserts!` failing rolls back everything already performed in the same call — the debt repayment pulled from the liquidator, the `debt-remove-scaled`, and the `collateral-remove` that seized the borrower's last collateral. In effect, liquidation of an unhealthy position that has no collateral left is entirely gated on every *other* outstanding debt asset for that borrower successfully going through `vault-socialize-debt` → `vault-accrue` → `debt-remove-scaled`. If any single one of those calls returns an error for any reason (e.g., an inconsistency between the cached `pos-full` debt list and live vault state, an unexpected error from `debt-remove-scaled`'s `legal?` check, or any future/edge-case failure in a per-vault socialization path), the position can never be liquidated through this path — the liquidator's transaction reverts every time, and the borrower's under-collateralized, now-fully-seized-of-collateral position remains stuck accruing bad debt indefinitely. There is no `emergency`/best-effort fallback that lets liquidation succeed while marking the failed asset's debt write-down as pending.

### Impact Explanation
If any single debt-asset entry in the borrower's remaining debt list cannot be socialized, the entire liquidation reverts every time it is attempted, since the outer `asserts!` unconditionally requires all fold items to succeed. This permanently blocks recovery of the position's collateral and leaves the corresponding bad debt unrecognized/unwritten on the vault ledger, risking protocol insolvency as the position's uncollected bad debt persists and continues to be counted as (unpayable) outstanding debt. This lands in the in-scope impact class of **permanent freezing of funds / protocol insolvency**, distinct from a deliberate liquidation-pause safety decision — it is an unconditional dependency between an otherwise-valid liquidation and unrelated per-asset bookkeeping calls that can fail independently of the liquidator's or borrower's intent.

### Likelihood Explanation
This path is only reached when a position has multiple debt assets and its last unit of collateral is being seized in a single liquidation call (`no-collateral-left` true) while debt remains outstanding on other assets — a realistic scenario for multi-asset borrowers approaching full liquidation. The likelihood of an individual `vault-socialize-debt`/`debt-remove-scaled` call actually failing depends on vault-specific edge cases not fully enumerable from this review (the exact revert triggers inside per-asset `vault-socialize-debt` could not be confirmed within the available context), but the architectural flaw — collapsing an intentionally fault-tolerant fold back into an all-or-nothing revert — is unconditionally present in the code and requires no attacker action beyond having (or causing) a multi-debt-asset position reach this state.

### Recommendation
Do not require all fold items to succeed before allowing the liquidation's collateral seizure and primary debt repayment to finalize. Either (a) make bad-debt socialization best-effort and non-blocking — record which assets failed to socialize and allow retry via a separate follow-up call, or (b) decouple the socialization step from `liquidate()` into a separate transaction so a failure there cannot roll back an already-valid liquidation of the target debt/collateral pair.

### Proof of Concept
1. Borrower has two debt assets, `aid A` (being liquidated) and `aid B` (remaining), and their only collateral is fully seized by liquidating `A` (`no-collateral-left` becomes true).
2. `liquidate()` executes `vault-system-repay` for `A` and `collateral-remove`, then builds `fresh-debt-list` containing `B`.
3. The `fold socialize-debt-asset` runs over `fresh-debt-list`; assume `vault-socialize-debt` or `debt-remove-scaled` for `B`'s vault returns an error for some vault-specific reason (e.g. an edge-case underflow/legality check on the socialized amount) — `socialize-debt-asset` absorbs it into `{ success: false }` per its `unwrap!`/`failed-status` design. [3](#0-2) 
4. Back in `liquidate()`, `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` fails, reverting the entire transaction — including the already-computed repay and collateral-remove. [1](#0-0) 
5. Every subsequent liquidation attempt on this borrower (any liquidator, any debt asset) hits the same fold over `B` and reverts identically, since the borrower's `B` debt entry and vault state causing the failure do not change — the position becomes permanently unliquidatable while bad debt accrues.
