### Title
Auto-swap deposit paths use a self-quoted, attacker-manipulable AMM price as the only "minimum return" check, with no user-supplied slippage bound - ([File: x/uexecutor/keeper/execute_inbound_gas_and_payload.go], [File: x/uexecutor/keeper/execute_inbound_gas.go], [File: x/uexecutor/keeper/evm.go])

### Summary
For `GAS_AND_PAYLOAD` (and CEA-gas) inbounds, the `uexecutor` module auto-swaps the user's deposited native/gas-token PRC20 into WPC via an on-chain Uniswap-V3-style pool. The "minimum acceptable output" (`minPCOut`) is not something the depositor ever specifies — it is derived entirely inside the module from a live `QuoterV2.quoteExactInputSingle` call taken immediately before the swap, with a hardcoded 5% slippage tolerance. This is the same missing-invariant class as the external `LPIssuer.deposit` report: the amount a user ultimately receives is computed from mutable, attacker-reachable state at execution time rather than from a value the user committed to when they intended the deposit, allowing a classic sandwich around the module-triggered swap.

### Finding Description
`gasAndPayloadDepositAutoSwap` fetches a live quote and computes `minPCOut = quote * 95 / 100` right before performing the swap: [1](#0-0) 

The identical pattern is duplicated in the plain `GAS` inbound path: [2](#0-1) 

and in the gas-refund path used for outbound gas refunds: [3](#0-2) 

The quote itself comes from `GetSwapQuote`, a direct call into a Uniswap V3 `QuoterV2` contract against the same pool that `CallPRC20DepositAutoSwap`/`depositPRC20WithAutoSwap` will trade against: [4](#0-3) 

The `Inbound` message that a user's cross-chain deposit produces carries no minimum-output, expected-amount, or slippage-tolerance field anywhere in `proto/uexecutor/v1/types.proto` — the 5%/95% figure is the *only* protection, and it is computed by the protocol itself from the pool's current spot price rather than supplied/committed to by the depositor. Because the pool (WPC ⇄ PRC20, Uniswap V3 style, deployed by `uregistry` as part of `UNIVERSAL_CORE`'s system contracts) is a normal public AMM, any unprivileged account can submit ordinary swap transactions against it. An attacker who can place a large swap immediately before the block that executes a pending `GAS_AND_PAYLOAD` inbound's autoswap (finalized deterministically the moment the inbound ballot reaches quorum, i.e., a predictable event once 2 of 3 relayers/validators have already voted) depresses the pool price; the module's own `GetSwapQuote` call then returns a quote based on that depressed price, `minPCOut` is set to 95% of that already-bad price, and `CallPRC20DepositAutoSwap` executes at the manipulated rate. The attacker reverses their position afterward in the same or next block, capturing the difference at the depositor's expense.

This is functionally identical to the reported bug class: there is a value (`minPCOut`) that determines how much of the user's converted funds they actually receive, and it is derived from state that can be moved by an unprivileged third party between when the user's intent was formed (submitting the cross-chain deposit on the source chain) and when the module executes the conversion — with no way for the user to bound their own acceptable outcome.

### Impact Explanation
Depositors using the gas-auto-swap flow (`GAS`, `GAS_AND_PAYLOAD`, `CEA` variants of these, and outbound gas refunds with `withSwap=true`) can receive a materially smaller amount of PRC20/WPC than the pool's undisturbed price would produce, with the difference extracted by the attacker who manipulated the pool immediately before the module-triggered swap. This is a direct loss of protocol-mediated user funds via an unprivileged, purely on-chain action against Push Chain's own AMM — no relayer, validator, or admin collusion required, only ordinary transaction submission and block-level ordering (standard sandwich MEV).

### Likelihood Explanation
The precondition (attacker submits an ordinary swap against a public Uniswap V3 pool immediately before/after the module's autoswap executes) requires no privileged access and is a well-understood, commonly-exploited MEV pattern. The main constraint is timing: the attacker must land their manipulation and reversal txs around the exact block in which quorum is reached and the deposit executes. Since inbound execution runs synchronously inside the vote-finalizing `MsgVoteInbound` transaction, an attacker monitoring the mempool/relayer votes can reliably target this block, making the attack practically executable rather than theoretical, though it depends on pool liquidity depth on the specific PRC20↔WPC pair being thin enough to move profitably.

### Recommendation
Do not derive `minPCOut` solely from a quote fetched by the module at execution time. Instead, plumb a user (or origin-chain-event)-supplied minimum output / max-slippage value through the `Inbound` (and refund) flow so the depositor's own expectation, captured at deposit time on the source chain, bounds the acceptable output — analogous to standard AMM router `amountOutMinimum` semantics. At minimum, tighten the tolerance and/or add TWAP-based quoting resistant to single-block manipulation, and consider capping per-block swap size or requiring commit-reveal/deadline-bound quotes fetched from a separate block than the swap itself.

### Proof of Concept
1. A relayer observes 2/3 of universal validators have already voted on a pending `GAS_AND_PAYLOAD` inbound for victim V, leaving the ballot one vote from quorum.
2. Attacker A submits a large `exactInputSingle` swap against the WPC↔PRC20(gas-token) Uniswap V3 pool used by `UniversalCore`, depressing the PRC20→WPC price.
3. In the same or next block, the finalizing `MsgVoteInbound` lands, triggering `ExecuteInboundGasAndPayload` → `gasAndPayloadDepositAutoSwap`, which calls `GetSwapQuote` against the now-depressed pool and computes `minPCOut` as 95% of that depressed quote (`x/uexecutor/keeper/execute_inbound_gas_and_payload.go:369-378`).
4. `CallPRC20DepositAutoSwap` executes V's deposit-swap at the manipulated price, crediting V's UEA with a WPC amount well below the fair-price expectation.
5. Attacker A reverses their initial swap, restoring the pool price and net profiting from the price impact absorbed by V's forced swap — all without any privileged role, purely via public transactions against the PRC20/WPC pool.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
