### Title
Unauthenticated `shop` query parameter used to construct admin/storefront API requests for merchant custom apps, allowing access-token exfiltration to an attacker-controlled domain - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/merchant-custom-app.ts`)

### Summary
For non-embedded apps, `getSessionTokenContext` in `authenticate.ts` takes the `shop` value directly from the unauthenticated `shop` URL query parameter (`url.searchParams.get('shop')`), with no HMAC/JWT verification, and threads it into the authentication strategy as `sessionContext.shop`. [1](#0-0) 

When the `MerchantCustomAuth` strategy is used (custom/merchant-installed apps), `authenticate()` builds a live `Session` purely from this unverified `shop` string via `api.session.customAppSession(shop)`, with no cross-check against a configured/allow-listed shop domain: [2](#0-1) 

`customAppSession` merely sanitizes and echoes back the caller-supplied `shop` into the `Session.shop` field — it does not verify the shop belongs to the app’s configured tenant: [3](#0-2) 

This mirrors the reported bug class: a privileged/identity-bearing parameter ("caller"/shop) that should be derived from a verified source (a signed session token's `dest` claim, as is correctly done for embedded apps a few lines above) is instead accepted as unauthenticated user input and used directly to build downstream authenticated behavior. [4](#0-3) 

### Finding Description
In the embedded-app code path, `shop` is safely derived only after `validateSessionToken` verifies the caller's Shopify-issued JWT and extracts `dest` from the *verified* payload: [4](#0-3) 

However, the non-embedded branch used by `MerchantCustomAuth` (custom/merchant "Admin-created app" distribution) reads `shop` straight from the query string with zero verification, then passes it unchanged to `strategy.authenticate()`: [5](#0-4) 

`MerchantCustomAuth.authenticate` accepts this attacker-controlled `shop` and constructs a `Session` object for it without any allow-list or comparison to the app’s installed/configured shop: [2](#0-1) 

This `Session` (whose `shop` field is fully attacker-controlled) is then used by `createContext`/`createAdminApiContext` to build the Admin GraphQL/REST clients for the request: [6](#0-5) 

Merchant custom apps are designed to hold a single, long-lived, statically-configured Admin API access token for one specific shop (the `Session` returned by `customAppSession` has no per-request `accessToken`, implying the client layer supplies the app's static configured token). Because the outbound request's target hostname is derived from `session.shop`, and `session.shop` is populated straight from the unauthenticated `shop` query parameter, an attacker who controls the value of `shop` can redirect the app's outbound Admin API request (carrying the app's real, static access token in the `Authorization`/`X-Shopify-Access-Token` header) to an arbitrary attacker-controlled `*.myshopify.com`-like hostname.

### Impact Explanation
This is a direct analog of the report's root cause: a function that should derive an identity/target from an authenticated, verified source (here, the shop bound to a JWT session token or OAuth-established session, exactly as done in the embedded branch) instead accepts it as unauthenticated caller input and uses it to construct privileged, credentialed outbound requests. The concrete impact is exfiltration of the app's static Admin API access token to a domain fully controlled by an unauthenticated remote attacker — a secret-disclosure / SSRF-class vulnerability with high severity, since a leaked static Admin API token grants full API access to the real shop's data until rotated.

### Likelihood Explanation
The vulnerable code path is reachable by any single unauthenticated HTTP GET request to a non-embedded custom-app route (no cookies, no valid session token, no HMAC required) — the attacker only needs to append `?shop=attacker-controlled-host` to a request handled by `shopify.authenticate.admin`. No privileged access, secret knowledge, or MITM position is required, matching the "unprivileged actor from a single HTTP request" bar required by the validation rules.

### Recommendation
For the `MerchantCustomAuth` (and equivalent non-embedded/custom-app) strategy, do not trust the `shop` query parameter for constructing the session or outbound API target. Instead:
- Always derive `shop` from the app's own configuration (the single shop domain the merchant custom app was installed for), ignoring/rejecting any `shop` value supplied via the request that doesn't match the configured shop.
- If a `shop` query parameter must be accepted for routing/logging, validate it strictly against the configured/allow-listed shop domain before it is allowed to influence `Session.shop` or client construction, mirroring the verified-JWT `dest` derivation used in the embedded-app branch.

### Proof of Concept
1. Deploy/host a `shopify-app-remix` app configured with `distribution: AppDistribution.ShopifyAdmin` / `MerchantCustomAuth` (a merchant custom/admin-created app) with a static Admin API access token configured.
2. As an unauthenticated attacker, send: `GET https://victim-app.example.com/app/some-authenticated-route?shop=attacker.myshopify.io` (no valid session cookie/JWT required, since this route is served by the non-embedded branch).
3. `getSessionTokenContext` returns `{shop: "attacker.myshopify.io", ...}` unauthenticated. [5](#0-4) 
4. `MerchantCustomAuth.authenticate` builds `Session` with `shop = "attacker.myshopify.io"` via `customAppSession`. [2](#0-1) 
5. The Admin API client is created using this session and issues its GraphQL/REST call to `https://attacker.myshopify.io/admin/api/...`, carrying the app's real static Admin API access token in the request headers, which the attacker (controlling that DNS/host) can capture.

**Note on completeness:** I was unable to inspect `createAdminApiContext`/`adminClientFactory` internals (specifically how the Admin API access token is attached for `MerchantCustomAuth` sessions with no `accessToken` field) before the tool budget was exhausted, so the exact header/token-attachment mechanism is inferred from the design of `customAppSession` (which omits `accessToken` on the `Session`, implying a config-level static token is applied by the client layer) rather than directly confirmed by reading the client factory code.
