### Title
Sortition parent-commit reference resolved by burnchain height, not by identity, allows a Bitcoin reorg to silently rebind a miner's `LeaderBlockCommitOp` to an unintended parent, burning the fee to a different fork - (File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs / stackslib/src/chainstate/burn/db/sortdb.rs)

### Summary
The Sherlock report describes `move()` accepting only a `parentIndex` (a positional pointer) instead of a content-bound identifier, so a re-org between broadcast and inclusion silently rebinds the move to a different, unintended target, causing bond loss. The Stacks analog is `LeaderBlockCommitOp.parent_block_ptr`/`parent_vtxindex`, which likewise identify the intended parent tenure purely by **burnchain block height + vtxindex** rather than by a content hash. Resolution of this pointer walks whatever burnchain fork is canonical *at validation time* [1](#0-0) , so a Bitcoin reorg occurring between the time a miner crafts/broadcasts a block-commit and the time it is actually mined can cause the commit to be validated against a completely different sortition/tenure than the miner intended, at the same height.

### Finding Description
`LeaderBlockCommitOp::insert_block_commit` derives the parent's `SortitionId` purely from `parent_block_ptr` via `get_block_snapshot_by_height`, which internally calls `get_ancestor_snapshot(self, height, chain_tip)` — i.e., "whatever sortition occupies this height on the *current* canonical fork" [2](#0-1) . The same height-indexed lookup is used at consensus-check/validation time via `get_ancestor_snapshot`/`get_ancestor_sort_id` [1](#0-0)  and `get_block_commit_parent` [3](#0-2) .

Crucially, nothing in the commit's on-chain data binds the pointer to the specific burn-block *hash* or specific sortition winner the miner intended. A miner constructs a `LeaderBlockCommitOp` referencing `parent_block_ptr = H` because, at construction time, they believe the winning tenure at burnchain height `H` is tenure `X`. If a Bitcoin reorg replaces the block at height `H` before the commit transaction is mined (a very plausible race, since miners must act quickly within the mining-commitment window to avoid missing their target modulus — see the tight `BURN_BLOCK_MINED_AT_MODULUS` timing check in `LeaderBlockCommitOp::check` [4](#0-3) ), then at validation time height `H` on the now-canonical fork may resolve to a *different* sortition winner `Y` (or no sortition at all). The commit is then processed as chaining off `Y`, not `X`, without any error — the equality "the parent the miner intended to build on == the parent the protocol resolves" is broken silently, exactly analogous to the `move()` bug where `parentIndex` could resolve to a different claim after a re-org.

This mirrors the sortition-winner-selection machinery in `BlockSnapshot::select_winning_block`/`make_snapshot_in_epoch`, which likewise resolves the previous winner strictly by walking `sort_tx.get_last_snapshot_with_sortition(height-1)` on the current tip fork [5](#0-4)  and `select_winning_block` [6](#0-5) , so the "target" for VRF-seed chaining and reward continuity is likewise purely height-derived, not content-bound.

### Impact Explanation
If the reorg swaps in an invalid or unintended parent, the miner's large burn-fee commitment (their "bond", analogous to the challenger's bond in the report) is spent building on a tenure they never intended to extend. Depending on which tenure ends up at that height:
- The commit may become invalid (e.g., failing `check_pox`/reward-address checks intended for a different parent tenure), causing the miner's burn to be wasted with no chance of winning sortition — a direct, uncompensated loss of the committed burn amount, i.e. the "bond".
- Or the commit may validate successfully against an attacker-controlled parent tenure the miner never intended to build on, letting an attacker effectively hijack an honest miner's burn expenditure to extend the attacker's chosen fork, analogous to "scooping up" the defenders' bonds in the report.

This does not require a majority of hashpower — a routine natural Bitcoin reorg (1-2 blocks, which occurs regularly on mainnet, as the original report also emphasizes) occurring in the narrow window between a miner submitting a block-commit and it confirming is sufficient. This is unprivileged and minority-triggerable (any party causing/benefiting from an ordinary short reorg, or simply the natural occurrence of one), matching a High-severity class: a minority-triggerable divergence that leads to bounded (fee-scoped) loss and temporary tip disagreement about which tenure a commit binds to.

### Likelihood Explanation
Short Bitcoin reorgs (1-2 blocks) are a documented, non-adversarial occurrence on mainnet, and the block-commit protocol already has a narrow per-modulus timing window in which the miner must act (`check` rejects commits landing at the wrong height modulus, forcing miners to commit promptly rather than wait for deep confirmation) [4](#0-3) . This structurally forces miners to submit commits without waiting for finality, making the race condition realistic rather than purely theoretical.

### Recommendation
Bind the parent reference to more than a positional height/vtxindex pair — e.g., require the commit to additionally include (and have validation check) the parent burn-block header hash or parent sortition ID/winning txid, so that if the burnchain reorgs and a different sortition occupies that height, the commit is provably invalid (or explicitly re-targetable) instead of being silently reinterpreted against a different, unintended tenure.

### Proof of Concept
1. Miner observes tenure `X` win sortition at burn height `H` on the current canonical Bitcoin fork.
2. Miner crafts and broadcasts `LeaderBlockCommitOp` with `parent_block_ptr = H`, `parent_vtxindex = X.vtxindex`, committing a large burn fee, intending to build on `X`.
3. Before this commit transaction confirms, a natural 1-block Bitcoin reorg replaces the block at height `H`; a different block-commit `Y` (possibly attacker-supplied) is now the sortition winner recorded at height `H` on the new canonical fork (or no sortition occurs there at all).
4. The miner's commit transaction subsequently confirms in a later burn block. During processing, `insert_block_commit`/`get_block_commit_parent` resolve `parent_block_ptr = H` against the *now-canonical* fork via `get_ancestor_snapshot`, binding the commit to `Y` (or failing) instead of `X` [2](#0-1) .
5. The miner's burn fee is spent/consumed under a parent binding they never intended and never approved on-chain, resulting in loss of the committed bond or in unintentionally extending an attacker-favored fork — with no way for the miner to detect or prevent this from the on-chain data alone.

Note: I was unable to view the full body of `check_common` (only located it, not its contents) within the remaining tool budget, so I cannot state with certainty whether any additional cross-check (e.g., a required match against `key_block_ptr`'s VRF proof) narrows this window in practice; this should be verified against `LeaderBlockCommitOp::check_common` in `stackslib/src/chainstate/burn/operations/leader_block_commit.rs` before treating the root-cause characterization as fully exhaustive.

    fn get_last_vrf_seed(
        sort_tx: &mut SortitionHandleTx,
        block_header: &BurnchainBlockHeader,
    ) -> Result<VRFSeed, db_error> {
        let burn_block_height = block_header.block_height;

        // get the last winner's VRF seed in this block's fork
        let last_sortition_snapshot =
            sort_tx.get_last_snapshot_with_sortition(burn_block_height - 1)?;

        let vrf_seed = if last_sortition_snapshot.is_initial() {
            // this is the sentinal "first-sortition" block
            VRFSeed::initial()
        } else {
            // there may have been a prior winning block commit.  Use its VRF seed if possible
            sort_tx
                .get_block_commit(
                    &last_sortition_snapshot.winning_block_txid,
                    &last_sortition_snapshot.sortition_id,
                )?
                .expect("FATAL ERROR: no winning block commits in database (indicates corruption)")
                .new_seed
        };
        Ok(vrf_seed)
    }
