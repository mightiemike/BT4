### Title
Unauthenticated, sender-independent global `accountId` namespace allows front-running/squatting DoS - (File: actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java)

### Summary
`SetAccountIdActuator` lets any account permanently claim an arbitrary, globally-unique `accountId` string, indexed independently of any sender-derived key. Because the index key is purely user-supplied data (not `hash(accountId, senderAddress)` or similar), and the assignment is a one-time, non-reversible operation, an attacker who observes a pending `SetAccountIdContract` transaction in the mempool can front-run it with the same `accountId`, permanently denying the legitimate account owner that identifier — mirroring the `AlignedLayerServiceManager.createNewTask()` front-running bug class where a content-derived (not sender-derived) key lets anyone preempt a legitimate submission.

### Finding Description
`SetAccountIdActuator.validate()` checks two conditions before allowing the ID to be set:
- The calling account must not already have an `accountId` set: `account.getAccountId() != null && !account.getAccountId().isEmpty()` → `"This account id already set"` [1](#0-0) 
- The `accountId` string must not already exist globally: `accountIdIndexStore.has(accountId)` → `"This id has existed"` [2](#0-1) 

In `execute()`, the account's `accountId` field is set and the account is indexed in `accountIdIndexStore` keyed purely by the raw `accountId` bytes, with no relation to `msg.sender`/`ownerAddress`: [3](#0-2) 

This is structurally identical to the reported bug: a public, unauthenticated, unpermissioned function creates a permanent global-namespace entry keyed by attacker-controllable, user-supplied data rather than a sender-scoped key (e.g. `keccak256(id, sender)` as used in the AlignedLayerServiceManager fix). Any party watching the mempool for a `SetAccountIdContract` transaction can copy the `accountId` value into their own transaction, pay a (negligible, since `calcFee()` returns 0) fee, and get it mined first: [4](#0-3) 

Because setting the `accountId` is enforced as a one-time operation per account (`"This account id already set"`) and there is no delete/reassign path exposed by this actuator, the victim's account permanently loses the ability to ever claim that identifier once front-run — this is a stronger, irreversible variant of the reported DoS (the aligned_layer bug allowed re-creation with a different key after the fix; here there is no recovery path at all for that specific ID).

### Impact Explanation
- **Denial of Service / permanent griefing:** A legitimate user's attempt to claim a human-meaningful `accountId` (used for lookups via `GetAccountByIdServlet`/`getAccountById` RPCs, referenced in [5](#0-4) ) can be permanently blocked by any unprivileged attacker who front-runs the transaction, since the id-to-account binding is irrevocable.
- **Extortion potential:** As in the reported pattern, an attacker could squat desirable IDs ahead of known/predictable claims (e.g. exchange or protocol accounts publishing their address and an intended ID) and extort the victim, though there is no on-chain "release" mechanism, making this pure griefing rather than value extraction from the contract itself.
- This does not cause direct fund loss or consensus divergence, so impact is bounded to griefing/service disruption of the `accountId` naming feature, similar in class (not degree) to the original finding.

### Likelihood Explanation
Front-running is straightforward on any public mempool-based chain: the attacker only needs to observe an unconfirmed `SetAccountIdContract` transaction, extract the `accountId` value, and submit their own transaction with higher energy/priority. `calcFee()` for this actuator is 0, so there is no meaningful economic disincentive: [4](#0-3) . Any account (no special privilege required) can call this, and the validation logic that enables the race is exercised directly in `SetAccountIdActuatorTest.nameAlreadyUsed`, confirming the "This id has existed" collision behavior is live, reachable code: [6](#0-5) .

### Recommendation
- Do not index `accountId` uniqueness purely by the raw user-supplied string; if a global uniqueness constraint is required for a "first come" ID system, consider incorporating additional protections (e.g., commit-reveal for ID registration, or minimum-fee/rate-limiting per ID claim) to blunt front-running.
- Alternatively, allow an account to reclaim/reassign a squatted ID under specific dispute conditions, or make ID squatting economically costly (non-zero, meaningful fee) to discourage low-cost griefing.
- Consider whether the "one-time-set, globally-unique, zero-fee" design for `accountId` is still an intended, necessary feature; if it has limited utility, deprecating or fee-gating it removes the exposure entirely.

### Proof of Concept
1. Victim broadcasts a `SetAccountIdContract` transaction: `ownerAddress = Victim`, `accountId = "coolname"`.
2. Attacker observes this pending transaction in the mempool and immediately broadcasts their own `SetAccountIdContract`: `ownerAddress = Attacker`, `accountId = "coolname"`, with equal or higher energy/priority so it is processed first.
3. Attacker's transaction succeeds: `accountIdIndexStore.put(account)` binds `"coolname"` to Attacker's account (see `execute()` at [3](#0-2) ).
4. Victim's transaction then fails validation with `"This id has existed"` (see check at [2](#0-1) ), and because `accountId` assignment is one-time per account, Victim can never claim `"coolname"` on any account thereafter.

Note: I was unable to find any admin/governance function to reset or release an `accountId` binding in this repository via search; if such a mechanism exists elsewhere in the codebase (e.g. an internal migration tool), it was not surfaced by the available indexing, and a full-repository review (e.g. via a Devin session) would be needed to confirm there is truly no recovery path.

    } catch (ContractValidateException e) {
      logger.info(e.getMessage());

      Assert.assertFalse(e instanceof ContractExeException);
