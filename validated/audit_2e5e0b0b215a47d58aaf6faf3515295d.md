## Analog Found

### Title
Inbound PRC20 minting never enforces the registered `LiquidityCap`, allowing aggregate deposits to exceed the configured token limit - ([File: x/uexecutor/keeper/handler.go])

### Summary
`x/uregistry`'s `TokenConfig` carries a `LiquidityCap` field intended to bound how much of an external asset's PRC20 representation may exist on Push Chain [1](#0-0) . However, the inbound deposit path that mints PRC20 (`depositPRC20` → `CallPRC20Deposit`) never reads or checks this cap before minting — it only resolves the `NativeRepresentation.ContractAddress` and mints the full requested `amount` unconditionally [2](#0-1) . This is the same class of bug as the external report: an amount value (here, aggregate deposited/minted PRC20) is never validated against a registered ceiling (here, `LiquidityCap`) before the protocol commits value-bearing state, so the invariant the parameter is meant to enforce can silently be exceeded.

### Finding Description
`TokenConfig.LiquidityCap` exists as a first-class, admin-set parameter on every registered token [3](#0-2) , but a repository-wide search shows it is only referenced in protobuf-generated types and unit tests validating message construction — never in any keeper code path that actually mints or deposits PRC20. Concretely:

- `depositPRC20` (called from every inbound execution path — `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, CEA/gas-and-payload variants) looks up `TokenConfig`, extracts `NativeRepresentation.ContractAddress`, parses the string amount, and calls `CallPRC20Deposit` directly, with no comparison against `tokenConfig.LiquidityCap` or against current PRC20 total supply [2](#0-1) .
- `CallPRC20Deposit` itself is a bare `DerivedEVMCall` to `depositPRC20Token` on the `UNIVERSAL_CORE` handler with the module account as a synthetic sender — it performs no bound-checking either [4](#0-3) .
- `ExecuteInboundFunds` / `ExecuteInboundFundsAndPayload` pass `inbound.Amount` straight through to `depositPRC20` once the inbound ballot passes, with only `ValidateForExecution` enforcing that the amount is a well-formed non-negative uint256 — never a check against any registry-side cap [5](#0-4) [6](#0-5) .

Each individual inbound is a legitimate, honestly-voted observation (an ordinary unprivileged user depositing real funds on the source chain, exactly as required by the in-scope threat model). Nothing malicious or privileged is needed — the attacker only needs to be one of many ordinary users making genuine deposits. Because no code path aggregates minted PRC20 supply against `LiquidityCap` before or after minting, the sum of many honestly-observed deposits for a given token can exceed the cap the admin configured, with no code anywhere enforcing or even reading that value at mint time.

### Impact Explanation
This falls under the explicitly in-scope "corruption of PRC20 or native asset accounting" and "unauthorized mint... of user or protocol-controlled funds" categories. `LiquidityCap` exists specifically to bound the protocol's exposure to a given external asset/bridge (e.g., limiting how much of a risky or low-liquidity token can be represented as PRC20 on Push Chain). If it is never enforced, the PRC20 supply for that asset can grow past the intended risk ceiling purely through normal, honest user activity, defeating the parameter's purpose and potentially leaving PRC20 balances that exceed what the registry configuration was designed to safely support — directly mirroring the referenced report's core defect ("amount... less or equal to the current balance... otherwise some users would be expecting [funds/guarantees] that are not even available").

### Likelihood Explanation
High. No privileged action, malicious validator, or malicious node is required — any set of ordinary users bridging funds for the same token can collectively exceed the cap, since the check simply does not exist in the mint path. The only way to trigger this is via completely ordinary inbound deposits.

### Recommendation
Enforce `TokenConfig.LiquidityCap` inside `depositPRC20` (or in `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload` before calling it) by tracking cumulative minted PRC20 supply per token and rejecting (or reverting to the failed-PCTx/revert-outbound path already used elsewhere) inbound deposits that would push the total past the configured cap.

### Proof of Concept
1. Admin registers a token via `MsgAddTokenConfig` with `LiquidityCap = X`.
2. Multiple distinct unprivileged users deposit real funds via the Gateway on the source chain, each individually within normal limits, summing to > X across N honestly-voted inbounds.
3. Each inbound ballot passes with honest validators (in-scope assumption), and `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints the full amount every time, with no aggregate check against `LiquidityCap` anywhere in `x/uexecutor/keeper/handler.go` or `evm.go`.
4. Total PRC20 supply for that token now exceeds the configured `LiquidityCap`, with no code path having ever consulted the field.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}
