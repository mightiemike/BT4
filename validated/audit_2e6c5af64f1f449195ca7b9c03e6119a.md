### Title
Floating-point precision loss in Bancor-style exchange math corrupts TRC10/TRX exchange pool accounting - (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator`, reachable by any account via a broadcast `ExchangeTransactionContract`, delegates token-swap math to `ExchangeCapsule.transaction()`, which by default uses the legacy `ExchangeProcessor` implementing the Bancor-formula bonding curve with `double`/`Math.pow` arithmetic [1](#0-0) . This mirrors the external report's core theme — that vault/exchange accounting functions (`totalVaultFunds()`, `positionInWantToken()`) can drift from real economic value when intermediate math/state isn't precise or properly hardened before being used to mint/burn shares — except here the "share minting" analog is the on-chain bonding-curve balance update of `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule`.

### Finding Description
The default (non-hardened) `ExchangeProcessor.exchange()` computes the AMM/bonding-curve trade using IEEE-754 `double` precision math: [2](#0-1) 

Unlike the hardened `SafeExchangeProcessor`, which uses `BigDecimal` with explicit scale/rounding and overflow-checked arithmetic (`StrictMathWrapper.addExact`/`subtractExact`) plus a post-condition check that balances stay `>= 0` [3](#0-2) , the legacy path performs no such safety checks: [4](#0-3) 

Whether the hardened path is even used is itself gated by an off-chain-controlled/governance flag, `allowHardenExchangeCalculation`, checked via `Manager.isExchangeTransaction()` and `dynamicStore.allowStrictMath()`/`allowHarden()` before `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)` [5](#0-4) . If this proposal value is `0` (the default state, as exercised by the unit test `isExchangeTransactionBypassedWhenHardenedEnabled` which explicitly toggles `saveAllowHardenExchangeCalculation`), the vulnerable float-based `ExchangeProcessor` is used for every `ExchangeTransactionContract`, `ExchangeInjectActuator`, and `ExchangeCreateActuator` operation that touches this bonding curve [6](#0-5) . The project's own test suite (`ExchangeProcessorTest.testStrictMath`) asserts, across dozens of real-world-scale inputs, that the plain double-based result (`anotherTokenQuant`) *never* equals the hardened/strict result (`safeResult`) — i.e., the legacy math is provably imprecise by design, not just theoretically: [7](#0-6) 

This is directly analogous to the report's "order of operations / stale or imprecise valuation used for share/fund accounting" bug class: the exchange pool's on-chain reserve balances (`firstTokenBalance`, `secondTokenBalance`), which are the sole source of truth for pricing all subsequent trades against the pool (just like `totalVaultFunds()` for share minting), are updated using a computation that is not guaranteed to be conservative or overflow-safe, and no invariant check (e.g., constant product/bonding-curve invariant preservation, or non-negative balance) is enforced on the legacy path.

### Impact Explanation
Any anonymous account can create or use an on-chain TRC10↔TRX or TRC10↔TRC10 exchange pool via `ExchangeCreateContract`/`ExchangeTransactionContract`, both of which are reachable via ordinary broadcast transactions with no privileged role required. Because the float-based `exchangeToSupply`/`exchangeFromSupply` computation truncates to `long` via `(long) issuedSupply` without any check against the invariant, repeated or crafted small trades can accumulate rounding bias, allowing an attacker to extract more of the paired token than the bonding curve should yield, silently corrupting the exchange pool's recorded reserves (`Exchange.firstTokenBalance`/`secondTokenBalance` persisted via `ExchangeStore`/`ExchangeV2Store`). This is an on-chain accounting/asset corruption in the exchange market-math subsystem, not merely an off-chain keeper documentation gap.

### Likelihood Explanation
Exploitability depends on whether `allowHardenExchangeCalculation` is enabled on the running network. Since the hardening (`SafeExchangeProcessor`) was clearly added later as a defense (evidenced by the dedicated bypass check `isExchangeTransaction`/`allowHarden()` and the explicit test proving divergence from the old math), any deployment or period where this proposal remains at its default/disabled value is exposed. The precondition (creating or using an existing exchange pair) requires no special privilege and is available to any TRX/TRC10 holder, making likelihood moderate-to-high wherever hardening isn't yet activated network-wide.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal, overflow-checked, invariant-checked) the unconditional default for all exchange math, removing the `allowHardenExchangeCalculation`/`allowHarden()` bypass path entirely rather than gating it behind a governance proposal.
- Add an explicit bonding-curve invariant check (post-trade product/relay-supply consistency) after every `transaction()` call regardless of hardened mode, mirroring the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard already present in the hardened path.
- Document, and ideally enforce on-chain, that any code path deriving economic value from computed (rather than directly observed) balances must use exact/checked arithmetic before being used to update persisted reserve state.

### Proof of Concept
1. Deploy/observe a network where `DynamicPropertiesStore.getAllowHardenExchangeCalculation() == 0` (default), verified via `ManagerTest.isExchangeTransactionBypassedWhenHardenedEnabled` behavior [8](#0-7) .
2. Create an exchange pair via `ExchangeCreateContract` with attacker-chosen initial reserves.
3. Submit a sequence of `ExchangeTransactionContract` broadcasts with quantities chosen to maximize float rounding bias in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (confirmed non-equal to the exact `BigDecimal` result for realistic inputs, per `ExchangeProcessorTest.testStrictMath`) [9](#0-8) .
4. Observe the persisted `ExchangeCapsule` reserve balances diverge from the economically correct (invariant-preserving) values, resulting in extractable value beyond what the bonding curve should allow.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public void isExchangeTransactionBypassedWhenHardenedEnabled() throws Exception {
    Transaction exchange = Transaction.newBuilder().setRawData(
        Transaction.raw.newBuilder().addContract(
            Transaction.Contract.newBuilder()
                .setType(ContractType.ExchangeTransactionContract)
                .setParameter(Any.pack(ExchangeTransactionContract.newBuilder()
                    .setExchangeId(1L).setQuant(1L).setExpected(1L).build()))
                .build())).build();

    java.lang.reflect.Method m = Manager.class.getDeclaredMethod(
        "isExchangeTransaction", Transaction.class);
    m.setAccessible(true);

    // Default: hardened disabled (==0) -> contract is treated as exchange
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
    Assert.assertTrue("Exchange tx must be detected when hardened disabled",
        (boolean) m.invoke(dbManager, exchange));

    // Hardened enabled -> bypass returns false
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
    Assert.assertFalse("Exchange tx must be bypassed when hardened enabled",
        (boolean) m.invoke(dbManager, exchange));

    // Reset
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
  }
