### Title
Function-call access-key allowance limit is completely bypassed when routed through a meta-transaction (`DelegateAction`) instead of a direct transaction - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
A `FunctionCallPermission.allowance` is meant to cap how much of an account's balance a restricted access key can spend. This cap is only enforced on the direct-transaction path (`verify_and_charge_tx_ephemeral` / `check_and_compute_new_allowance`). The delegate-action (meta-transaction) validation path, `validate_delegate_action_key`, checks receiver match, method-name match, and deposit-with-function-call, but never reads or decrements `allowance` at all. As documented in `docs/architecture/how/meta-tx.md`, this is a known, acknowledged gap: "for allowance, however, there is no check... even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work" [2](#0-1) .

### Finding Description
- Direct-transaction path: `check_and_compute_new_allowance` reads `fc.allowance` and returns `NotEnoughAllowance` if the transaction's total cost exceeds the remaining allowance [3](#0-2) . This is invoked inside `verify_and_charge_tx_ephemeral` before returning success [4](#0-3) .
- Delegate-action path: `validate_delegate_action_key` performs nonce checks, then, for a `FunctionCall`-permissioned key, checks action count, deposit, receiver mismatch, and method-name mismatch — but at no point reads `function_call_permission.allowance` [5](#0-4) .
- Because the relayer pays for the inner actions (the relayer purchases gas and covers deposits for the wrapped actions), the signer's own account balance/allowance is never charged, so there is no other backstop that would indirectly enforce the cap.
- This mirrors the GMX pattern exactly: a spend-limiting check (`allowance` / virtual-inventory price impact) is enforced on one code path but is entirely skipped on an alternate path (`DelegateAction` / a market missing one side's virtual inventory), letting an attacker deliberately choose the path where the check is absent to bypass the limit.

### Impact Explanation
An account owner (or anyone who compromises/obtains a restricted `FunctionCall` access key with a low `allowance` — a security control specifically meant to bound worst-case loss from that key) can use any relayer to fully bypass the allowance cap and invoke the permitted method an unbounded number of times, with the relayer footing the gas/deposit bill. This defeats the entire purpose of `allowance` as a blast-radius limiter for a leaked or intentionally-restricted key: dApps and wallets that rely on allowance to bound how much a given function-call key can authorize (e.g., session keys, dApp-specific keys) lose that guarantee whenever a meta-transaction relayer is available, without any error being raised.

### Likelihood Explanation
Confirmed directly by an existing test, `meta_tx_fn_call_access_key_insufficient_allowance`, which sets a 1-yoctoNEAR allowance (insufficient even for 1 unit of gas) and asserts the call still succeeds via a relayer [6](#0-5) . No special privileges are needed beyond signing a `DelegateAction` with the restricted key and having a relayer submit it — both are ordinary, permissionless flows (`SignedDelegateAction` submitted as a normal transaction). The behavior is also explicitly called out as expected/known in the architecture docs, meaning it's not accidental but was never routed through a fix.

### Recommendation
Enforce `allowance` on the delegate-action key-validation path the same way it is enforced for direct transactions: compute the total cost of the inner actions (or a suitable proxy, since the relayer pays gas) and decrement/check `function_call_permission.allowance` inside `validate_delegate_action_key`, returning a `DelegateActionAccessKeyError` (e.g. a new `NotEnoughAllowance` variant) when insufficient, and persist the decremented allowance on the sender's access key. Alternatively, explicitly document and gate this as intentional and disallow issuing/relying on `allowance`-restricted keys for delegate-action authorization if the cap cannot be meaningfully enforced under the relayer-pays model.

### Proof of Concept
1. Create `sender` with a `FunctionCallPermission` access key restricted to `receiver`, method `TEST_METHOD`, with `allowance = 1 yoctoNEAR` (less than the cost of a single gas unit) — as in `setup_with_access_key` in the test file.
2. Directly sign and submit a normal `SignedTransaction` calling `TEST_METHOD` with this key → fails with `NotEnoughAllowance` (per `check_and_compute_new_allowance`).
3. Instead, wrap the same `FunctionCall` action in a `DelegateAction`/`SignedDelegateAction` signed by `sender`'s restricted key, and have any `relayer` account submit it as a normal transaction (the relayer pays gas/deposit).
4. Observe the call succeeds and is executed as many times as desired (bounded only by nonce/relayer willingness), exactly as shown by `meta_tx_fn_call_access_key_insufficient_allowance` [6](#0-5) , demonstrating the `allowance` cap is never applied on this path.

fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
