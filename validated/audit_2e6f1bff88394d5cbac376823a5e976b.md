Based on the codebase evidence, there is a valid analog to the reported "single-step ownership transfer" bug class in nearcore's access-key model.

### Title
Unconditional single-step `DeleteKey` action permanently bricks accounts with no safety check for last remaining full-access key - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
The `OwnableUpgradeable` single-step ownership transfer bug class maps directly onto NEAR's access-key removal mechanism: `action_delete_key` performs an unconditional, single-step, irreversible removal of an account's access key with no "pending"/two-step confirmation and no protection against removing the account's last remaining `FullAccess` key.

### Finding Description
In NEAR's account model, an access key is the on-chain equivalent of "ownership" — it is what authorizes a signer to issue any action on an account, including `Transfer`, `DeployContract`, `Stake`, and `DeleteAccount`. [1](#0-0)  The `DeleteKeyAction` handler, `action_delete_key`, looks up the key and deletes it directly via `delete_regular_key`/`delete_gas_key` with no check for whether it is the account's last full-access key: [2](#0-1) 

This is a single-step, irreversible transfer-of-control analog to `Ownable`'s single-step `transferOwnership`: once the last full-access key is removed (analogous to transferring ownership to an unreachable/invalid address), there is no "pending owner" state and no way to recover control. The documentation explicitly acknowledges the resulting state: "If account has no access keys attached it means that it has no owner who can run transactions from its behalf." [3](#0-2)  Unlike `Ownable2Step`, there is no mechanism requiring a new key to be added and confirmed before the old one is revoked.

The runtime's own test suite documents this as a known, reachable, single-transaction condition (`test_delete_key_last`), including a `TODO` acknowledging inconsistent/incorrect error handling on retries once the key is gone: [4](#0-3)  A separate protocol-level test also treats "an account with no access key" as an established, reachable end state resulting from `DeleteKey` of the last committed key. [5](#0-4) 

`check_actor_permissions` confirms `DeleteKey` is actor-gated only to require `actor_id == account_id` (i.e., the account itself, via one of its own keys) — there is no additional guard preventing a self-signed transaction from removing the sole remaining key: [6](#0-5) 

### Impact Explanation
Once the last `FullAccess` key of a plain (non-contract) account is deleted, the account's remaining `amount`/`locked` balance becomes permanently unreachable — no future transaction can ever be signed on the account's behalf, and the account cannot be deleted (which also requires the actor to be the account itself and a valid signature). This matches the "permanently frozen funds" impact category: the balance is stranded on-chain forever, with no path to move it, analogous to bricking `onlyOwner`-gated protocol functionality after an ownership-transfer mistake.

### Likelihood Explanation
Low: it requires signer error — a user or key-rotation tool (e.g., a `swap_key`-style flow shown in `integration-tests/src/user/mod.rs`) mistakenly issuing a bare `DeleteKey` for the last key instead of an atomic delete-then-add, or deleting the key before verifying the replacement key was successfully added in a prior transaction. This mirrors the report's stated likelihood ("Low, because it requires an error on the admin/owner side") while the impact is high (irrecoverable loss of account control and frozen funds).

### Recommendation
Introduce a protocol-level (or client/wallet-level) safeguard analogous to `Ownable2Step`: reject a `DeleteKey` action that would remove an account's last remaining `FullAccess` key in the same way `check_actor_permissions`/`action_delete_key` already validate other invariants (e.g., disallow `DeleteAccount` while `locked` is non-zero, see `runtime/runtime/src/actions.rs:777-792`). Alternatively, require that key rotation be expressed as an atomic "replace" primitive (add-then-delete ordering enforced within the same receipt) rather than allowing an unconditional standalone `DeleteKey` of the sole remaining key, mirroring a two-step confirm-before-revoke pattern.

### Proof of Concept
1. Create/fund an account with a single `FullAccess` access key (standard implicit or named account).
2. As that account, sign and submit a single-action transaction: `Action::DeleteKey(DeleteKeyAction { public_key: <own_only_key> })`, targeting itself (`signer_id == receiver_id`), matching the pattern in `test_delete_key_last`. [4](#0-3) 
3. `action_delete_key` executes unconditionally and succeeds, removing the only access key. [2](#0-1) 
4. The account still holds its `amount`/`locked` balance in state, but no further transaction can ever be signed on its behalf, and `DeleteAccount` also requires a valid signer key — the funds are permanently frozen.

pub(crate) fn action_delete_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_key: &DeleteKeyAction,
) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {
        if let Some(gas_key_info) = access_key.gas_key_info() {
            delete_gas_key(
                config,
                state_update,
                account,
                result,
                account_id,
                &delete_key.public_key,
                &access_key,
                gas_key_info,
            )?;
        } else {
            delete_regular_key(
                &config.fees,
                state_update,
                account,
                account_id,
                &delete_key.public_key,
                &access_key,
            );
        }
    } else {
        result.result = Err(ActionErrorKind::DeleteKeyDoesNotExist {
            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),
        }
        .into());
    }
    Ok(())
}

pub fn test_delete_key_last(node: impl Node) {
    let account_id = &node.account_id().unwrap();
    let node_user = node.user();
    let root = node_user.get_state_root();

    assert!(node_user.get_access_key(account_id, &node.signer().public_key()).is_ok());
    let transaction_result = node_user.delete_key(account_id.clone(), node.signer().public_key());

    match transaction_result {
        Ok(transaction_result) => {
            assert_eq!(transaction_result.status, FinalExecutionStatus::SuccessValue(Vec::new()));
            assert_eq!(transaction_result.receipts_outcome.len(), 1 + extra_refund_outcomes());
        }
        Err(err) => {
            // TODO(#6724): This is a wrong error, the transaction actually
            // succeeds. We get an error here when we retry the tx and the second
            // time around it fails. Normally, retries are handled by nonces, but we
            // forget the nonce when we delete a key!
            assert_eq!(
                err,
                CommitError::Server(ServerError::TxExecutionError(
                    TxExecutionError::InvalidTxError(InvalidTxError::InvalidAccessKeyError(
                        InvalidAccessKeyError::AccessKeyNotFound {
                            account_id: account_id.clone(),
                            public_key: node.signer().public_key().into(),
                        },
                    ))
                ))
            )
        }
    }

    let new_root = node_user.get_state_root();
    assert_ne!(new_root, root);

    assert!(node_user.get_access_key(account_id, &node.signer().public_key()).is_err());
}
