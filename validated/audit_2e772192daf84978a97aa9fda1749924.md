### Title
Reverted L1-Handler transactions are recorded as "consumed" by the Batcher even though the Starknet OS never consumes their L1→L2 message, permanently dropping the message from retry — ([File: crates/apollo_batcher/src/block_builder.rs])

### Summary
An L1→L2 message reachable by anyone able to trigger a revert in the target L1-handler entry point (e.g. a business-logic check, reentrancy guard, or any condition in the target contract) is treated by the batcher's off-chain bookkeeping as permanently "consumed," even though the on-chain (OS-committed) execution explicitly skips consumption for reverted L1-handler transactions. This is the same bug-class as the Timelock report: an operation whose Tx does not achieve its intended effect nonetheless causes the "queued" item (here, the pending L1→L2 message) to be dropped forever.

### Finding Description
When the batcher collects execution results for a block, it unconditionally inserts every `L1Handler` transaction's hash into `consumed_l1_handler_tx_hashes`, *before* even looking at whether the transaction execution reverted: [1](#0-0) 

Note that a reverted-but-not-erroring L1-handler execution is returned as `Ok((tx_execution_info, ...))` with `revert_error: Some(...)` set (blockifier explicitly models this as "reverted", not "rejected"): [2](#0-1) 

Only genuine `Err` results from the executor (e.g. a `StateError`) are placed into `rejected_tx_hashes`; a Cairo-level revert of the L1-handler entry point is *not* placed there, only logged as a warning ("is reverted during execution while still accepted"). Consequently, the tx_hash is retained in `consumed_l1_handler_tx_hashes` and is passed downstream to `commit_proposal_and_block`, which forwards it, minus only the `rejected_tx_hashes`-filtered set, to the L1 events provider as "consumed": [3](#0-2) 

This directly contradicts the actual committed/proven behavior in the Starknet OS: for a reverted L1-handler transaction, the OS explicitly skips message consumption entirely — `consume_l1_to_l2_message` is only reached in the non-reverted branch, and the OS returns before ever calling it when `is_reverted != FALSE`: [4](#0-3) 

The `TransactionManager`'s notion of "consumed" is meant to permanently retire a message so it is never re-proposed: [5](#0-4) [6](#0-5) 

Because the batcher's `commit_block` call to the L1 events provider marks the message as consumed regardless of whether the L1-handler entry point reverted, the off-chain message-tracking state diverges from the actual on-chain/OS-committed state: the OS never applied the message (state changes were rolled back and consumption was skipped), yet the sequencer's `TransactionManager` will never surface this L1→L2 message again for inclusion in a future block. There is a test (`failed_l1_handler_transaction_consumed`) that explicitly documents/asserts this behavior for the `Err`-from-executor path, but nothing in the codebase distinguishes the "reverted via revert_error" (Ok) path from a genuinely-processed L1-handler for the purpose of `consumed_l1_handler_tx_hashes`: [7](#0-6) 

An integration test confirms reverted L1-handler transactions are a first-class, expected scenario the pipeline must handle (`reverted_l1_handler_tx_flow`), but it does not verify that the message stays retryable at the L1-events-provider layer: [8](#0-7) 

### Impact Explanation
Any L1→L2 message whose target entry point reverts on L2 (attacker-triggerable simply by crafting calldata/state that causes the target contract's `l1_handler` to revert, or by a legitimate business condition) is permanently removed from the sequencer's retry queue after being included once in a block — regardless of the fact that on the actually-committed/proven L2 state, the message was never processed and no state change occurred. Since Starknet's message-consumption bookkeeping for retryability lives in this off-chain `TransactionManager`/L1-events-provider, and not solely in on-chain state, this divergence causes a genuine, permanent loss: the message can never be resubmitted/retried by the protocol, even though nothing on L2 ever applied its effect (e.g. minting funds, unlocking a deposit). This maps to "concrete loss or permanent freezing of funds" for users relying on the L1→L2 message eventually being applied, and to state/bookkeeping divergence between the sequencer's L1-provider view and the OS-committed state — both are impacts explicitly in-scope (state reads/aliasing, mempool/L1-provider admission and retry logic, Starknet OS re-execution consistency).

### Likelihood Explanation
High likelihood: reverting the target entry point of an L1-handler is trivial and fully controlled by whoever can influence the calldata/state read by that entry point (a condition explicitly exercised by the repo's own `l1_handler_set_value_and_revert` and `reverted_l1_handler_tx_flow` tests), so this is reachable on every block containing a reverted L1-handler, with no special privileges required.

### Recommendation
In `collect_execution_results_and_stream_txs` (crates/apollo_batcher/src/block_builder.rs), only insert an `L1Handler` transaction hash into `consumed_l1_handler_tx_hashes` when `tx_execution_info.revert_error.is_none()` (i.e., mirror the OS's `is_reverted` semantics), and treat reverted L1-handler transactions the same way as `rejected_tx_hashes`/non-consumed for the purposes of the L1 events provider's `commit_block` call, so the off-chain `TransactionManager` retains and can re-propose the message.

### Proof of Concept
1. Deploy an L2 contract with an `l1_handler` entry point that reverts under an attacker-controllable condition (e.g. `l1_handler_set_value_and_revert`, already present in the test suite as used in `crates/starknet_os_flow_tests/src/tests.rs::test_reverted_l1_handler_tx`).
2. Send an L1→L2 message targeting that entry point with calldata that triggers the revert.
3. Observe: `L1HandlerTransaction::execute_raw` returns `Ok(TransactionExecutionInfo{ revert_error: Some(...), .. })` (crates/blockifier/src/transaction/l1_handler_transaction.rs:132-141); the batcher's `collect_execution_results_and_stream_txs` nonetheless inserts the tx hash into `consumed_l1_handler_tx_hashes` unconditionally (crates/apollo_batcher/src/block_builder.rs:644-649) and does **not** add it to `rejected_tx_hashes`.
4. `commit_proposal_and_block` forwards this hash as "consumed" to the L1 events provider (crates/apollo_batcher/src/batcher.rs:1181-1191), which calls `TransactionManager::consume_tx`, permanently marking/removing the record (crates/apollo_l1_events/src/transaction_manager.rs:247-271, crates/apollo_l1_events/src/transaction_record.rs:111-140).
5. Meanwhile, at the OS level, because `is_reverted != FALSE`, `consume_l1_to_l2_message` is never invoked and the message is never actually consumed on the committed state (crates/apollo_starknet_os_program/.../transaction_impls.cairo:383-390, 443-444).
6. Result: the message is unrecoverable — never resubmittable by the sequencer's L1 events pipeline — despite never having been applied on the committed/proven L2 state.

        &mut self,
        tx_hash: TransactionHash,
        consumed_at: BlockTimestamp,
        unix_now: u64,
    ) -> Result<(), BlockTimestamp> {
        self.clear_old_tx_from_consumed_queue(unix_now);

        let Some(record) = self.records.get(&tx_hash) else {
            debug!(
                "Attempted to consume an unknown transaction: {tx_hash}. This can happen if the \
                 transaction was too old to be scraped (e.g. it was created before we started \
                 scraping)."
            );
            return Ok(());
        };

        // Double consumption is a bug.
        if let Some(previously_consumed_at) = record.get_consumed_at_timestamp() {
            return Err(previously_consumed_at);
        }

        // Mark the transaction as consumed.
        self.with_record(tx_hash, |record| record.mark_consumed(consumed_at));
        Ok(())
