Based on my investigation, I found a strong analog to the shelter bug in the `near-wallet-contract`.

### Title
Caller Deposit Lost When `ban_relayer` Path Is Taken After a `CallerDeposit` Was Recorded - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In the C4 report, `Shelter.sol` tracks donated/deposited tokens with a counter (`amountInShelter`/`savedTokens`) that is decoupled from the actual token balance; when the shelter is deactivated the code blindly transfers everything back to the parent contract and resets the counter to `0`, silently stranding any donated funds that were not part of the tracked amount. The `near-wallet-contract` has an analogous pattern: an external caller's attached deposit is tracked out-of-band in a `CallerDeposit` struct [1](#0-0)  that is threaded through several promise callbacks so it can be refunded if the downstream cross-contract call fails. The refund is only actually issued from one specific code path, `rlp_execute_callback`, when the callback is invoked with a failed promise result [2](#0-1) .

### Finding Description
The wallet contract's `inner_rlp_execute` decides, per relayer/user error class, whether to increment the nonce and whether to route through `create_ban_relayer_promise` (which deletes the relayer's key and calls `ban_relayer`) instead of the normal execution/callback path [3](#0-2) . `CallerDeposit` is created before this branching decision is made [4](#0-3) , meaning by the time an external (non-self) caller's deposit is tracked, the flow can still be diverted to `create_ban_relayer_promise`/`ban_relayer` — a code path that has **no knowledge of `caller_deposit` at all** and therefore never issues a refund:
- `create_ban_relayer_promise` builds a promise chain of `delete_key` + `ban_relayer` with no `caller_deposit` argument [5](#0-4) .
- `ban_relayer` itself simply clears `has_in_flight_tx` and returns a failure response — it does not transfer any attached balance back to the caller [6](#0-5) .

This mirrors the shelter bug's root cause exactly: a value (donated LP tokens / an external caller's attached NEAR) is tracked by a side-channel accounting structure (`savedTokens` / `CallerDeposit`), but a specific state-transition path (`exitShelter` / `ban_relayer`) bypasses that accounting and irreversibly disposes of/retains the funds without consulting or refunding based on it. The same "banned relayer" path is also reachable from `address_check_callback` when the signer is the contract itself, which forwards `caller_deposit` in the *non*-ban branch but drops it entirely when constructing the ban-relayer promise in the ban branch [7](#0-6) .

### Impact Explanation
If an external (non-self) caller attaches a deposit to `rlp_execute` for a transaction that is later classified as a `Relayer` error where the signer equals the wallet's own account (a faulty relayer using an access key on this wallet), the flow is diverted through `create_ban_relayer_promise`/`ban_relayer`. The `CallerDeposit` computed at the top of `inner_rlp_execute` is discarded — it is never passed to `ban_relayer`, so the attached NEAR is never refunded to `caller_deposit.account_id`. Because `rlp_execute` is `#[payable]` [8](#0-7) , the deposit is already credited to the wallet contract's balance at the protocol level; the only way it returns to the caller is via an explicit transfer promise, which this path never creates. The result is permanently stranded/frozen funds belonging to the external caller, matching the "permanently frozen funds" impact class for this analog scan.

### Likelihood Explanation
This path is reachable by any account that calls `rlp_execute` as an external, non-self predecessor with a non-zero attached deposit while using an access key registered on the target wallet contract with a relayer-classified parsing error (`Error::Relayer`) — no special privileges are required beyond having (or obtaining) a function-call access key on the wallet, which is the wallet's intended usage model for relayers. The `Error::Relayer` cases are explicitly documented in the code as arising from relayer misbehavior/faulty parsing rather than exotic conditions, making it a realistic, non-adversarial-network trigger.

### Recommendation
Thread `caller_deposit` through `create_ban_relayer_promise`/`ban_relayer` (or explicitly refund it before banning the relayer) so that any tracked external deposit is refunded whenever the in-flight transaction is terminated via the ban-relayer path, mirroring the refund-on-failure behavior already implemented in `rlp_execute_callback`.

### Proof of Concept
1. Deploy the wallet contract and add a function-call access key for a "relayer" account.
2. Have an external account `caller` (distinct from the wallet's `current_account_id`) call `rlp_execute(target, tx_bytes_b64)` with a non-zero attached deposit, where `tx_bytes_b64` is crafted so that `internal::parse_rlp_tx_to_action` returns `Err(Error::Relayer(_))`, and where the transaction is signed with the relayer's access key such that `env::signer_account_id() == current_account_id`.
3. `inner_rlp_execute` returns `Err(Error::Relayer(_))` before ever building the normal callback promise; `rlp_execute` catches this and calls `create_ban_relayer_promise(current_account_id)` [9](#0-8) , which never references `caller_deposit`.
4. `ban_relayer` executes, deletes the relayer's key, and returns a failure `ExecuteResponse` without any transfer action [6](#0-5) .
5. The caller's attached deposit remains in the wallet contract's balance permanently, with no code path left to reclaim it (unlike the failure path in `rlp_execute_callback`, which does issue a refund transfer).

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

fn create_ban_relayer_promise(current_account_id: AccountId) -> Promise {
    let pk = env::signer_account_pk();
