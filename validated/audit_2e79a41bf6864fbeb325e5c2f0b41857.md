### Title
Flow HMAC validation lacks replay protection, allowing unlimited replay of captured webhook requests - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`validateHmacFromRequestFactory` (used for `HmacValidationType.Flow` and other body-based HMAC validations) only checks that `hmac === HMAC-SHA256(apiSecretKey, rawBody)` via `safeCompare`, with no timestamp, nonce, or expiry check, unlike the query-string HMAC path which enforces `validateHmacTimestamp`. Any party who once observes a legitimate Flow request's `rawBody` and `X-Shopify-Hmac-Sha256` header (e.g., via a compromised proxy/log, browser extension, or any logging middleware in the request path) can replay the exact same request indefinitely to re-trigger `authenticateFlowFactory`.

The function reads the `hmac` header and compares it against `HMAC-SHA256(apiSecretKey, rawBody)` using `safeCompare`, then returns `succeed`/`fail` with no additional freshness check. This contrasts with `validateHmac` (used for query-string/OAuth-style HMAC, e.g., app proxy) at lines 84-116, which calls `validateHmacTimestamp` (lines 203-232) to reject requests whose `timestamp` param is more than 90 seconds (`HMAC_TIMESTAMP_PERMITTED_CLOCK_TOLERANCE_SEC`) from the current server time.

`authenticateFlowFactory` in `packages/apps/shopify-app-remix/src/server/authenticate/flow/authenticate.ts` (and the equivalent React Router version) calls `api.flow.validate({rawBody, rawRequest: request})`, which internally calls `validateHmacFromRequest` with `type: HmacValidationType.Flow`. If `result.valid` is true, the flow proceeds to look up the offline session for `payload.shopify_domain` and returns an authenticated `admin` client, enabling the caller to run Admin API mutations as that shop.

Because the HMAC is computed purely over the static `rawBody` with no timestamp/nonce bound into the signed payload (Shopify Flow's actual outbound webhook payload does not include a timestamp field checked by this library), an identical `(rawBody, hmac)` pair remains valid forever — there is no server-side replay cache, nonce tracking, or expiry check anywhere in this validation path.

However, note the precondition: the attacker must already possess a valid captured `(rawBody, hmac)` pair from a real Shopify Flow trigger addressed to the legitimate shop. The prompt's own threat model (a compromised proxy log, or XSS in an unrelated surface the attacker controls) implies the attacker has some privileged vantage point into the request/response path — this is not "no privileged access" in the strict sense of an anonymous internet attacker with zero capture capability. The library's job is to verify authenticity of the sender via HMAC; it does not by design defend against verbatim replay of an intercepted, legitimately-signed byte stream, since Shopify's own webhook/Flow signing scheme does not include a timestamp/nonce in the signed body for this endpoint type (unlike OAuth/app-proxy query params which do carry a `timestamp`).

### Impact Explanation
If exploitable, a captured Flow request could be replayed to repeatedly trigger the app's Flow action handler (e.g., re-invoking an Admin API mutation such as adding a discount, tagging an order, or sending a notification) against the legitimate shop, causing unauthorized repeated state changes. This matches Shopify's "replay of a legitimate signed request leading to unauthorized repeated action" impact class, but its practical severity is capped by the fact that it requires an existing capture capability (e.g., MITM/proxy compromise or log access) that is explicitly excluded from the attacker model in this audit's rules ("No MITM, local-network... assumptions").

### Likelihood Explanation
Low under the stated attacker model. The rules explicitly disallow MITM/proxy-compromise and privileged-access preconditions, and the described attack requires exactly that: capture of a legitimate, correctly-signed webhook body plus its valid HMAC from a channel the attacker does not otherwise control (Shopify servers → app server, over TLS). An "unprivileged" attacker (anonymous internet party, or a merchant/customer without such access) cannot forge or independently obtain a valid `(rawBody, hmac)` pair without the `apiSecretKey`, and `safeCompare` correctly prevents timing-based secret recovery. Absent an actual capture vector within scope, this is a design gap (missing defense-in-depth freshness check) rather than a directly exploitable vulnerability under the given constraints.

### Recommendation
As defense-in-depth, add a replay-protection mechanism for body-based HMAC validation paths (Flow, webhooks, fulfillment-service) similar to Shopify's guidance: track recently-seen `(hmac, shop)` or webhook `X-Shopify-Webhook-Id` values in a short-lived cache/store and reject duplicates within a bounded window, or leverage `X-Shopify-Triggered-At`/similar headers if available, mirroring the `validateHmacTimestamp` tolerance-window approach already used for query-string HMAC in the same file.

### Proof of Concept
Not reproducible within the stated attacker constraints — an unprivileged attacker (no MITM/proxy access, no secret) cannot obtain a valid `(rawBody, hmac)` pair to replay in the first place, so no Jest test demonstrating exploitation from that starting point is possible without violating the rules' exclusions.
