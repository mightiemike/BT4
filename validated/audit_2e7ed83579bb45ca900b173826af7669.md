### Title
Wallet Contract `has_in_flight_tx` lock can become permanently stuck, freezing the ETH-implicit account with no rescue path - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (used to emulate Ethereum-style accounts for ETH-implicit accounts) enforces a single-in-flight-transaction invariant via the `has_in_flight_tx` boolean field. This flag is set to `true` before every promise-returning call and is only reset to `false` as the *first* statement inside each `#[private]` callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). There is no external, admin, or self-recovery function anywhere in the contract or the wider codebase that can reset this flag if a callback receipt fails outright (e.g., due to insufficient prepaid gas or any panic before the reset statement commits). This mirrors the reported Solidity bug class: a "rescue"/recovery capability (resetting stuck state) exists conceptually as an invariant guarantee but is unreachable once broken, permanently freezing the account's functionality. [1](#0-0) 

### Finding Description
`rlp_execute` checks `self.has_in_flight_tx` and rejects any new call while `true`: [2](#0-1) 

It then sets `has_in_flight_tx = true` and returns a `Promise` chained to one of several `#[private]` callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`). Each of these callbacks resets the flag to `false` as their very first statement: [3](#0-2) [4](#0-3) [5](#0-4) 

The static gas budgets chained to these callbacks are fixed, small constants (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`), only padded by `action.gas()` taken from user/relayer-controlled Ethereum-emulated transaction data: [6](#0-5) 

Because a NEAR function-call receipt that runs out of allocated gas reverts *all* state writes made during that receipt's execution (the reset-to-`false` write included), any callback receipt that fails to execute at all or fails before reaching its first line (e.g., due to gas exhaustion, deserialization panics not otherwise wrapped in `match`, or any other host-level failure that aborts the function) leaves `has_in_flight_tx` permanently `true`. There is no code path anywhere in the repository that clears this flag except inside these same callbacks — confirmed by a repo-wide search showing `has_in_flight_tx` is referenced only within this one file, with no reset/rescue/admin function: [7](#0-6) 

Once stuck, every subsequent `rlp_execute` call — for any target, from any relayer — is rejected outright with "transaction already in progress", regardless of caller: [8](#0-7) 

This is directly analogous to the referenced Solidity bug: a designed recovery/consistency mechanism (the invariant "flag always reset in the callback") is unreachable in a specific failure mode, and unlike a Solidity contract there is no `onlyAdmin`/owner-level escape hatch to force a reset, so funds and control held by the ETH-implicit account become permanently unusable through the wallet contract.

### Impact Explanation
This is a transaction-triggered halt of a specific account's usability: the ETH-implicit account (and any $NEAR / NEP-141 tokens routed through it) becomes permanently unable to execute any further Ethereum-emulated action via `rlp_execute`, since the account never regains the ability to distinguish "stuck" from "genuinely in-flight." Because ETH-implicit accounts rely entirely on this single entry point to move funds or manage keys, this results in funds effectively frozen at that account with no recovery, satisfying the "permanently frozen funds" / "transaction-triggered halt" criteria.

### Likelihood Explanation
The trigger requires a promise chain whose scheduled callback receipt cannot execute far enough to write the reset (e.g., under-provisioned gas on the relayer-submitted transaction relative to the actions requested, or any other host-level failure of that specific receipt). Because prepaid gas and the requested `action.gas()` inside the encoded Ethereum transaction are attacker/relayer-influenced inputs feeding directly into the gas math for the chained callback, a relayer (malicious or merely misconfigured) submitting a transaction whose overall prepaid gas is exhausted right around the callback receipt boundary can trigger this deterministically. This is reachable by any relayer or the account owner themselves without requiring any privileged, validator, or network-level position — it is a pure transaction-crafting attack against a specific account.

### Recommendation
Add a bounded automatic-unlock mechanism (e.g., store the block height/timestamp when `has_in_flight_tx` was set and allow `rlp_execute` to proceed if a sufficiently large number of blocks have elapsed without resolution), or provide a dedicated, safely-gated "unstick" entry point that can be called by the account owner (verified via the account's own access key) to force-reset `has_in_flight_tx` after some timeout, ensuring the account can never be permanently locked out of using its own wallet contract due to a single failed/under-gassed callback receipt.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without a live gas-metered WASM runtime, but the code path is deterministic):
1. Deploy the Wallet Contract to an ETH-implicit account as in `test_wallet_contract_interaction` [9](#0-8) .
2. As the relayer, craft an RLP-encoded Ethereum transaction whose emulated action requests a large `gas` value in the ABI-encoded `FunctionCall`/`ERC20Transfer` payload such that, combined with the fixed callback static gas constants, the total gas attached to the transaction is insufficient for the scheduled callback receipt (`address_check_callback`, `nep_141_storage_balance_callback`, or `rlp_execute_callback`) to begin execution.
3. Submit this transaction via `rlp_execute`; `has_in_flight_tx` is set to `true` and a promise is returned [10](#0-9) .
4. The chained callback receipt fails due to insufficient gas before executing `self.has_in_flight_tx = false;`, so this write is reverted; the contract's persisted state retains `has_in_flight_tx = true`.
5. Any subsequent call to `rlp_execute` (from the legitimate owner or any relayer) is rejected with "transaction already in progress" indefinitely, since no code path exists to reset the flag [8](#0-7) .

Note: I was not able to find or execute an integration test that exercises this exact gas-exhaustion-of-callback scenario in the indexed test suite (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/`), so the precise gas thresholds needed to trigger callback-receipt failure are not verified numerically here — a Devin session with full repo/runtime access would be needed to construct and run a concrete gas-boundary test against the sandboxed wallet contract to confirm exact conditions.
