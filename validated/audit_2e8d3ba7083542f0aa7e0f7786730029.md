## Analog Vulnerability Found

### Title
Missing slippage protection in `ExchangeWithdrawActuator` and `ExchangeInjectActuator` allows front-run/sandwich losses - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The TRON TRC10 bancor-style `Exchange` (AMM pool) feature implements slippage protection only for `ExchangeTransactionContract` (trades), via an `expected` minimum-output field. The equivalent `ExchangeInjectContract` and `ExchangeWithdrawContract` operations, which also convert one pooled asset into another at a pool-derived ratio, have **no minimum/maximum bound field at all**, so the counter-asset amount actually delivered can differ arbitrarily from what the caller expected if the pool ratio shifts between broadcast and execution — the exact bug class described in the external report (no way to bound output/received amount before execution).

### Finding Description
`ExchangeTransactionContract` was designed with slippage protection: it carries an `expected` field, and `ExchangeTransactionActuator.doValidate()` reverts if the computed output is below it: [1](#0-0) [2](#0-1) [3](#0-2) 

By contrast, `ExchangeWithdrawContract` and `ExchangeInjectContract` only carry `quant` (the amount of one side to withdraw/inject) — there is no `expected`/minimum field for the counter-asset amount: [4](#0-3) 

In `ExchangeWithdrawActuator.execute()`, the counter-asset amount `anotherTokenQuant` is computed purely from the *current* pool ratio at execution time, with no comparison against any caller-supplied bound: [5](#0-4) 

The same pattern (no bound check) appears in `ExchangeInjectActuator.execute()`: [6](#0-5) 

Both `doValidate()` methods (`ExchangeWithdrawActuator` L132-231, `ExchangeInjectActuator` L126+) only check pool-balance limits, non-zero balances, and precision rounding — never a "received amount is not less than X" check, unlike `ExchangeTransactionActuator`.

Critically, calling `ExchangeInject`/`ExchangeWithdraw` is **not restricted to a privileged system role**: the TRC10 `Exchange` pool feature is permissionless — any account can create its own exchange pair via `ExchangeCreateContract` and thereby become the pool's "creator," which is the only authorization check enforced (`account is not creator`): [7](#0-6) 

Since `ExchangeTransactionContract` (a trade) is a public, permissionless operation that any other user can broadcast, an attacker can observe a pending `ExchangeInject`/`ExchangeWithdraw` transaction in the mempool, submit an `ExchangeTransactionContract` trade immediately before it to skew the pool ratio, let the victim's inject/withdraw execute against the skewed ratio (receiving/paying an amount worse than intended), and then optionally trade back afterward — a classic sandwich attack enabled purely by the absence of a bound check, mirroring the reported `LeverageStrategy.deposit()` flaw where leverage/borrow calculations execute without any minimum-output guarantee.

### Impact Explanation
A pool creator/LP-equivalent user performing `ExchangeWithdraw` or `ExchangeInject` can be economically harmed (receive fewer counter-tokens on withdrawal, or be forced to supply/receive a worse ratio on injection) by an attacker who manipulates the pool ratio between transaction broadcast and packing, with no on-chain mechanism to prevent or revert the unfavorable execution. This is a direct, unprivileged-user-reachable accounting/settlement impact within the exchange module, not a theoretical or admin-only issue.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to observe a pending inject/withdraw transaction and race a trade transaction ahead of it within the same or an adjacent block — feasible given TRON's public transaction broadcast/mempool model, similar to sandwich attacks on other AMMs. The `Exchange` feature is a legacy but still-present, permissionless, on-chain component, so the attack surface exists for any account operating an exchange pool.

### Recommendation
Add a caller-specified bound field (e.g., `expected`/minimum for withdraw, and `expected`/maximum-cost for inject) to `ExchangeWithdrawContract` and `ExchangeInjectContract`, analogous to the `expected` field already present in `ExchangeTransactionContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()` / `ExchangeInjectActuator.doValidate()` by reverting when the computed `anotherTokenQuant` falls outside the caller's specified bound.

### Proof of Concept
1. Attacker monitors the mempool/node for a pending `ExchangeWithdrawContract` (or `ExchangeInjectContract`) transaction from a victim pool creator.
2. Attacker submits and gets an `ExchangeTransactionContract` trade included first, shifting `firstTokenBalance`/`secondTokenBalance` of the target `exchangeCapsule` unfavorably relative to what the victim expected.
3. Victim's `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the now-skewed ratio at lines 77-89 with no minimum check, delivering fewer tokens than the victim would have accepted had a bound existed.
4. Attacker optionally reverses their trade afterward to restore the pool and realize a profit from the victim's suboptimal withdrawal/injection — with no revert path available to the victim, exactly mirroring the reported `LeverageStrategy.deposit()` missing-slippage-check scenario.
