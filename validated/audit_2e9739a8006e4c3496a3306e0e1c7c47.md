### Title

### Summary
The question misattributes the function `incremental_recheck` to `program-runtime/src/serialization.rs`; it actually lives in `core/src/banking_stage/transaction_scheduler/scheduler_controller.rs`. Regardless of that discrepancy, the described double-execution scenario is not exploitable because `incremental_recheck` is a best-effort background hygiene sweep, not the transaction's actual replay-protection gate — that gate is enforced independently and unconditionally at execution/commit time via the bank's status cache.

### Finding Description
`incremental_recheck` in [1](#0-0)  walks `recheck_cursor` through the container's priority queue in `CHECK_CHUNK`-sized batches via `container.recheck_iter`, calling `bank.check_transactions` only on that chunk and removing (`container.remove_by_id`) entries that fail (e.g. `AlreadyProcessed`, `BlockhashNotFound`). Because the cursor only advances a bounded chunk per pass, a transaction placed just past the cursor could indeed remain in the container un-rechecked for one or more passes, exactly as the question describes.

However, this in-buffer staleness has no bearing on double-execution safety. When a transaction is actually scheduled and executed, the bank performs its own duplicate/status check at commit time using the `status_cache`, e.g. `check_transactions_with_processed_slots` used both by `check_status_checks` in `consume_worker.rs` [2](#0-1)  and by the core commit path via `Bank::check_transactions` / `check_transaction_age_and_status_cache` (implemented in `runtime/src/bank/check_transactions.rs`) [3](#0-2) . Any transaction whose signature is already present in the status cache is rejected with `TransactionError::AlreadyProcessed` at that final check, regardless of whether it sat unswept in the scheduler's priority queue. This is directly demonstrated by existing tests such as `test_check_transaction_without_status_cache_allows_already_processed` [4](#0-3) , `test_process_entry_duplicate_transaction` [5](#0-4) , and `test_check_noop_cost_units_and_replay` [6](#0-5) , all of which confirm that a second attempt to execute an already-landed transaction is rejected with `AlreadyProcessed` at commit time and produces no state change (no double-spend).

`incremental_recheck` is purely an optimization to proactively evict garbage from the buffer to save memory/CPU; it is not the sole or authoritative replay-protection mechanism. Removing it entirely would not create a double-execution vulnerability, since the bank's own commit-time status-cache check is what actually prevents replay, independent of scheduler buffer hygiene timing.

### Impact Explanation
No concrete impact: no double-spend, no fund loss, no consensus divergence, and no liveness halt occurs. The described "double-execute" cannot occur because a duplicate signature is always rejected with `TransactionError::AlreadyProcessed` at the mandatory final bank check prior to commit, independent of `incremental_recheck` timing.

    /// Incrementally recheck queued transactions for validity. A cursor walks the
    /// priority queue from highest to lowest priority. When the cursor reaches the end it
    /// wraps back to the top, continuously sweeping the queue.
    fn incremental_recheck(&mut self) {
        let bank = self.sharable_banks.working();

        // Walk the cursor to collect up to one chunk of valid IDs.
        self.recheck_chunk.clear();
        let mut last_seen = None;
        for id in self.container.recheck_iter(self.recheck_cursor.as_ref()) {
            last_seen = Some(*id);

            self.recheck_chunk.push(*id);
            if self.recheck_chunk.len() >= CHECK_CHUNK {
                break;
            }
        }

        // Update cursor: if we hit the chunk limit, continue from last seen;
        // otherwise we exhausted the range, so wrap back to start.
        self.recheck_cursor = if self.recheck_chunk.len() >= CHECK_CHUNK {
            last_seen
        } else {
            None
        };

        // Bail if no work to do (should only happen if container is empty).
        if self.recheck_chunk.is_empty() {
            return;
        }
