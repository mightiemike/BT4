### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay/verify tooling accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to authenticate a locally re-executed transaction output against the `TransactionInfo` fetched from an authenticated source (a backup, an archive node, or a synced peer). It checks the status, gas, write-set hash, and event-root hash, but it deliberately does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` on the `TransactionInfoV1` variant, which carry the Sparse-Merkle state root(s) for the version. This is exactly the class of bug the external report describes in spirit (a value that should gate correctness is silently dropped from a check), but here the dropped check is a state-root/proof binding rather than a fee transfer.

### Finding Description
`ensure_match_transaction_info` explicitly ignores the checkpoint hashes: [1](#0-0) [2](#0-1) 

The comment on lines 2197-2203 is a self-acknowledged gap in the code itself: "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." This is the exact function used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` to compare freshly re-executed `TransactionOutput`s against `expected_txn_infos` pulled from the target/backup database: [3](#0-2) 

`position_state_checkpoint_hash`/`hot_state_checkpoint_hash` are real fields on `TransactionInfoV1` that are supposed to bind the authenticated ledger version to a specific Jellyfish-Merkle/"trading-native" state root, produced alongside `state_checkpoint_hash` during `DoLedgerUpdate::assemble_transaction_infos`: [4](#0-3) 
and defined as accessors on `TransactionInfo`: [5](#0-4) 

Because `ensure_match_transaction_info` never calls these accessors, any divergence between the checkpoint/position state root actually computed by a node's local VM execution and the one embedded in the (already accumulator-verified) `TransactionInfo` from the archive/backup source will not be detected by this comparator. The write-set hash and event-root hash are checked, but the SMT/hot-state root that authenticates the full state view at that version is not.

### Impact Explanation
This breaks the "committed state must match VM result" and "authenticated API/proof output must stay bound to the correct version/root" invariants called out in the task. If a bug in checkpoint/hot-state root construction (e.g., in `DoStateCheckpoint`, the JMT update path, or the `compute_trading_native_state_roots` path) ever produces a wrong state root at the point of commit, `replay_on_archive` — the tool used to verify replay/consistency of a synced or restored database against the accumulator-verified backup — would report success anyway, masking a genuine state-root corruption. This is precisely a "hard-fork-only divergence during commit/replay/restore" that is silently accepted as valid, satisfying the state-integrity gate for proof/commit correctness. The severity is high because it defeats the primary safety net (`replay-verify`) that is meant to catch exactly this class of non-determinism/corruption before or after it reaches mainnet.

### Likelihood Explanation
The gap is not hypothetical: it is documented by the maintainers as a live, unresolved TODO in the code, explicitly naming `db-tool`'s `replay_on_archive` as the affected caller. It requires no privileged access or malicious actor — it silently degrades verification whenever the position/hot-state checkpoint hash path is used (e.g., once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` features are enabled) and any upstream bug causes a state-root mismatch that isn't also reflected in the write-set or event hashes.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` between the locally recomputed value (from `DoStateCheckpoint`/state-checkpoint output) and the `txn_info` being verified, failing the check on any mismatch, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production/replay-verify pipelines.

### Proof of Concept
Not independently exploitable as an attacker-triggerable transaction since it is a verification-tool gap rather than a consensus-path bug; the concrete "PoC" is the code path itself: `replay_on_archive::execute_and_verify` calls `ensure_match_transaction_info` at [6](#0-5) 
which, per the implementation at [7](#0-6) 
returns `Ok(())` even when `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` differ from the locally computed roots, so a synthetic `TransactionOutput` with a corrupted state root but a correct write-set/event hash passes verification undetected. I was not able to fully trace whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are currently enabled on mainnet (index does not show their default/activation status), which affects the immediate exploitability versus latent-risk classification of this finding.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
