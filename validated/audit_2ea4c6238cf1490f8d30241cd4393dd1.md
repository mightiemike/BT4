## Confirmed local candidate: `ensure_match_transaction_info` verification gap

### Title
Chunk-execution replay verification silently skips position/hot-state checkpoint-hash validation - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` (used during backfilled-chunk execution verification, e.g. `execution/executor/src/chunk_executor/mod.rs::verify_execution` and `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`) checks status, gas, write-set hash, and event root hash against a supplied `TransactionInfo`, but never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is exactly the class of bug the seed report describes: a value used to gate downstream committed state (the underlying price scaling) silently diverges from the value actually used to accept/reject the transaction, and the code path that is supposed to catch mismatches lets them through.

### Finding Description
`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as consensus-committed roots [1](#0-0) . These roots are produced during `DoStateCheckpoint::run` from local re-execution of a chunk (`execution/executor/src/workflow/do_state_checkpoint.rs`), including the native-position tree root gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS` [2](#0-1) .

When a chunk is replayed for verification (chunk executor's `verify_execution`, or the offline `replay_on_archive` tool), the code calls `ensure_match_transaction_info` to confirm the locally re-executed `TransactionOutput` matches the externally supplied, already-committed `TransactionInfo` [3](#0-2) [4](#0-3) . That function explicitly checks status, gas, write-set hash, and event root hash [5](#0-4) , but the code contains an explicit, unresolved acknowledgment that it omits the checkpoint-hash fields:

```rust
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [6](#0-5) 

Note that `verify_execution`'s call passes an already-executed `TransactionOutput` that, in the chunk-executor path, has already had its checkpoint hash validated inside the normal `DoStateCheckpoint`/`DoLedgerUpdate` pipeline via the `maybe_known_*_checkpoints` parameters (`execution/executor/src/chunk_executor/mod.rs:373-413`). So the gap is concretely exploitable in the **offline replay/verification tools** (`replay_on_archive`, `aptos-debugger`, `aptos-move/cli` commands that call `ensure_match_transaction_info`), which do not go through `DoStateCheckpoint`'s known-hash check and rely solely on `ensure_match_transaction_info` to detect state divergence.

### Impact Explanation
If a node's local re-execution produces a different `position_state_checkpoint_hash` (or `state_checkpoint_hash`/`hot_state_checkpoint_hash`) than the one embedded in an already-committed `TransactionInfo` — e.g., due to a non-determinism bug in the new native-position state tree, a bug in `compute_position_checkpoint`, or a storage corruption on the machine being verified — the audit/replay tooling (`replay_on_archive`, debugger-based verification, `aptos-move/cli` replay commands) will report the replay as **successful** even though the durable ledger state (position tree, hot state, or state tree) has silently diverged from what consensus actually committed. This defeats the entire purpose of replay-verification: it is the tool operators and node runners use to detect ledger corruption or non-deterministic execution bugs before they compound. Given `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are new, actively-developed features (evidenced by the TODO itself), this is a realistic proof-integrity gap rather than a theoretical one.

### Likelihood Explanation
The bug is a certainty in the sense that the check is provably absent from the code (confirmed via direct reading of `ensure_match_transaction_info`), and it is unconditionally reachable any time `ensure_match_transaction_info` is invoked with a `TransactionInfoV1` carrying non-`None` checkpoint hashes (i.e., whenever `TRANSACTION_INFO_V1` plus `HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled — features already wired into `BlockExecutorConfigFromOnchain::with_features`) [7](#0-6) . No attacker action or malicious peer is required — it's a false-negative in a defense-in-depth integrity check.

### Recommendation
Extend `ensure_match_transaction_info` to also validate, when present in `txn_info` and computable from local execution:
- `state_checkpoint_hash` (currently entirely unchecked even in `replay_on_archive`/CLI paths — only checked via a separate `known_state_checkpoints` mechanism inside `DoStateCheckpoint`, which offline tools bypass),
- `hot_state_checkpoint_hash`,
- `position_state_checkpoint_hash`.

Since these are checkpoint-only values (only set for the last transaction of a checkpoint boundary), the comparison should be conditioned on whether the checkpoint hash is expected at that transaction, mirroring the logic already present in `DoStateCheckpoint::get_state_checkpoint_hashes`. This closes the gap before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet, as the existing TODO recommends.

### Proof of Concept
Not independently reproducible via a public interface (this is a code-review-confirmed gap in an internal verification routine used by offline tools), but the root cause is directly demonstrable by inspection: run `db-tool replay-on-archive` or the `aptos-move/cli` replay command against an archive where `TRANSACTION_INFO_V1` + `HOT_STATE_ROOT_IN_TXN_INFO`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled and inject a deliberate mismatch in the locally computed `hot_state_checkpoint_hash` or `position_state_checkpoint_hash` (e.g., by feeding a `TransactionOutput` whose `HotStateUpdates`/position writes differ from what produced the committed `TransactionInfo`) — `ensure_match_transaction_info` will return `Ok(())` despite the divergence, because none of its `ensure!` checks reference these fields [8](#0-7) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
