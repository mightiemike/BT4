### Title
Truncated per-witness reward division leaves unallocated `TRX` in standby-witness/witness-127 payout distribution - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, `consensus/src/main/java/org/tron/consensus/dpos/IncentiveManager.java`)

### Summary
The reported bug class — proportional distribution of a fixed reward pool across multiple recipients using integer/floating-point division inside a loop, which truncates and leaves a remainder undistributed — has a direct analog in java-tron's per-maintenance-cycle reward payout logic for standby witnesses (`MortgageService.payStandbyWitness()`) and the 127-witness incentive payout (`IncentiveManager.reward()`).

### Finding Description
`MortgageService.payStandbyWitness()` computes a fixed total pool `totalPay` and divides it across all standby witnesses proportional to `voteCount`, using a `double` intermediate that is then truncated to `long` per witness: [1](#0-0) 

Each witness's share is `(long) (w.getVoteCount() * eachVotePay)`. Because `eachVotePay` is `totalPay / voteSum` as a `double`, and each per-witness payment is independently truncated, the sum of all `pay` values across witnesses is generically less than `totalPay`. The undistributed remainder (analogous to the `2`-unit leftover in the report's `2000/3` example) is simply lost — it is never credited to any account nor carried forward.

The same pattern exists in `IncentiveManager.reward()`, which distributes `totalPay = consensusDelegate.getWitnessStandbyAllowance()` proportionally to `voteCount` for up to `WITNESS_STANDBY_LENGTH` witnesses: [2](#0-1) 

Both functions are invoked from `MaintenanceManager.doMaintenance()` every maintenance cycle, which runs deterministically on every full node as part of consensus/block processing (not gated by any privileged actor), making this reachable purely from normal chain progression: [3](#0-2) 

This mirrors the report's root cause precisely: `share_i = amount * weight_i / totalWeight` computed independently per recipient in a loop, with no remainder handling, causing systematic truncation loss.

### Impact Explanation
Each maintenance cycle, the truncation causes a small amount of intended witness/standby-witness reward to go unallocated to any account — it is neither paid to a witness nor retained in a tracked pool. Over many cycles this is a persistent, deterministic under-payment of the reward pool (resource/reward accounting leakage), reducing actual witness incentive payouts below the intended `totalPay`/`getWitnessStandbyAllowance()` amount. This is a real accounting inefficiency in a production reward path, though the amount per cycle is small (bounded by `voteSum` cardinality, at most a few units of truncation per witness).

### Likelihood Explanation
This occurs on essentially every maintenance cycle where `voteSum > 0` and votes aren't evenly divisible, i.e., very frequently in normal chain operation — no attacker action or special conditions are required, only ordinary block/cycle progression.

### Recommendation
Track the amount actually distributed within the loop (`totalDistributed`) and allocate the remainder (`totalPay - totalDistributed`, or `witnessStandbyAllowance - totalDistributed`) to the last recipient processed in the loop, similar to the report's suggested fix, in both `MortgageService.payStandbyWitness()` and `IncentiveManager.reward()`. Alternatively, switch to a proven remainder-distribution algorithm (e.g., largest-remainder method) to avoid persistent under-payment.

### Proof of Concept
Given 3 standby witnesses with vote counts `100, 100, 100` (`voteSum = 300`) and `totalPay = 2000`:
- `eachVotePay = 2000 / 300 = 6.666...`
- Each witness's `pay = (long)(100 * 6.666...) = 666`
- Total distributed = `666 * 3 = 1998`
- `2` units of `totalPay` are never credited to any account, reproducing the exact truncation pattern described in the report, in `MortgageService.payStandbyWitness()` at [4](#0-3)  and analogously in `IncentiveManager.reward()` at [5](#0-4) .

  public void reward(List<ByteString> witnesses) {
    if (consensusDelegate.allowChangeDelegation()) {
      return;
    }
    if (witnesses.size() > WITNESS_STANDBY_LENGTH) {
      witnesses = witnesses.subList(0, WITNESS_STANDBY_LENGTH);
    }
    long voteSum = 0;
    for (ByteString witness : witnesses) {
      voteSum += consensusDelegate.getWitness(witness.toByteArray()).getVoteCount();
    }
    if (voteSum <= 0) {
      return;
    }
    long totalPay = consensusDelegate.getWitnessStandbyAllowance();
    for (ByteString witness : witnesses) {
      byte[] address = witness.toByteArray();
      long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay
          / voteSum));
      AccountCapsule accountCapsule = consensusDelegate.getAccount(address);
      accountCapsule.setAllowance(accountCapsule.getAllowance() + pay);
      consensusDelegate.saveAccount(accountCapsule);
    }
  }
