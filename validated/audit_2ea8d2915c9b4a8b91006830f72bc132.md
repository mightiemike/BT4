### Title
Deterministic contract-address front-running enables permanent Denial-of-Service on `CREATE` (contract deployment) transactions - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
The top-level contract-deployment path (`VMActuator.create()`) hard-fails a `CreateSmartContract` transaction whenever any account object — even a plain, non-contract EOA — already exists at the deterministically-derived contract address. An attacker who can compute or observe that address ahead of confirmation can pre-create the account (e.g. by transferring a trivial amount of TRX to it) and permanently deny the intended contract deployment, exactly mirroring the Phoenix "account creation primitives error if the account already has lamports" bug class.

### Finding Description
`VMActuator.create()` computes the contract address deterministically from the transaction and unconditionally rejects deployment if any account record already exists there: [1](#0-0) 

This check uses `rootRepository.getAccount(contractAddress) != null` as the sole existence test — it does not distinguish between "a real smart contract already deployed there" and "a plain EOA that merely received TRX/TRC10 there." Any account presence throws `ContractValidateException`, aborting the deployment.

`WalletUtil.generateContractAddress` derives the address from data available in the raw (signed but not-yet-confirmed) transaction, meaning any node relaying or observing the transaction in the mempool can compute the future contract address before it lands on-chain. An attacker can then broadcast a trivial TRX transfer to that computed address; because Tron auto-creates an `AccountCapsule` for any address that receives a transfer (`CreateAccountActuator`/implicit account creation in transfer actuators, e.g. `TransferAssetActuatorTest.SameTokenNameOpenNoExitToAccount`), the target address becomes "occupied" before the legitimate `CreateSmartContract` transaction is packed into a block, permanently blocking that specific deployment with no way to remedy since the address is fixed once the transaction is signed.

Notably, this codebase already demonstrates the *correct* remediation elsewhere: the inner `CREATE2` path in `Program.createContractImpl` gracefully absorbs a pre-existing, non-contract account instead of failing — it upgrades the account's type in place and clears delegated resources rather than aborting: [2](#0-1) 

The top-level `create()` validation in `VMActuator.java` never received this same graceful-handling fix, leaving the asymmetry that enables the DoS.

### Impact Explanation
Any anonymous actor observing a pending contract-deployment transaction (via mempool/gossip, requiring no privileged access or leaked keys) can compute the resulting deterministic contract address and pre-fund/pre-create it with an ordinary TRX transfer. This causes the intended deployment transaction to fail validation with "Trying to create a contract with existing contract address," permanently denying deployment of that specific contract. This is a concrete unauthorized-DoS impact on the TVM contract-creation actuator reachable purely via broadcast transactions.

### Likelihood Explanation
Moderate-to-high: it requires only observing the target's pending transaction (public once broadcast to the mempool) and racing a cheap TRX transfer ahead of block inclusion — no special privileges, keys, or node access are needed, only normal transaction broadcast capability that any user of the network already has.

### Recommendation
Change `VMActuator.create()`'s pre-creation existence check to match the graceful handling already used in the CREATE2 path: instead of unconditionally rejecting when `getAccount(contractAddress) != null`, only reject when the account is already a genuine contract (has code/`SmartContract` entry in the `ContractStore`). If the address merely holds an EOA balance from a pre-funding transfer, upgrade its type to `Contract` in place (as done in `Program.createContractImpl` at lines 836-843) and proceed with deployment, preserving any pre-existing balance rather than treating it as a fatal collision.

### Proof of Concept
1. Attacker monitors the mempool/gossip network for a pending `CreateSmartContract` transaction from a target user.
2. Attacker computes `contractAddress = WalletUtil.generateContractAddress(trx)` using the same logic as `VMActuator.create()` (deterministic from `trx`).
3. Attacker broadcasts and gets confirmed (before the target's transaction) a trivial `TransferContract` sending 1 sun to `contractAddress`, causing implicit account creation.
4. When the target's `CreateSmartContract` transaction executes, `VMActuator.create()` at [3](#0-2)  finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException`, permanently failing the deployment for that specific transaction/address.
