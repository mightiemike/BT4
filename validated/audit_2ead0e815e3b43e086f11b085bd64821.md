This is a real equality-breaking bug that maps directly to the report's bug class: an operation whose failure is silently swallowed while a downstream verdict proceeds as if it had succeeded, breaking the equality between the value reth computes and the value actually recomputed via the spec path.

### Title
Silent receipt-root task failure falls back to `None`, skipping receipts-root/logs-bloom verification instead of failing block validation - ([File: crates/engine/tree/src/tree/payload_processor/receipt_root_task.rs])

### Summary
`ReceiptRootTaskHandle::run` returns early *without sending anything* on the oneshot channel whenever it detects incomplete or gapped receipts [1](#0-0) . The caller in `BasicEngineValidator` treats a failed/aborted receive as `None` rather than as a fatal error, and passes that `None` straight into post-execution consensus validation [2](#0-1) .

### Finding Description
`validate_block_post_execution_with_bal_hashes` treats `receipt_root_bloom: None` not as "verification failed" but as "recompute the receipts root/bloom from `result.receipts` right now and compare it" — i.e. `None` is the *normal* synchronous fallback path, not an error signal [3](#0-2) . This is fine when the background task never ran or the caller never wired it up. But here, the background task *did* run, *did* receive a channel of receipts, and *decided* something was wrong (index count mismatch or a gap in the middle) — yet instead of surfacing that as an error, it just drops the sender and returns [4](#0-3) .

On the consumer side, `blocking_recv()` failing due to the dropped sender is caught, logged at `error!`, and converted to `None` via `.ok()` [5](#0-4) . Because `None` is indistinguishable from "task was never used," `validate_block_post_execution_with_bal_hashes` falls through to `verify_receipts(...)` which recomputes the root from `result.receipts` synchronously and *does* still catch a mismatch against the header [6](#0-5) .

This is the exact structural analog to the M-23 report: a subordinate operation (the streaming receipt-root computation) can fail/abort ("transfer fails") while the surrounding accounting path (post-execution validation) proceeds as though everything is fine ("`_calcRewardIntegral` updates accounting regardless"), relying on it being caught by a *different* code path (the synchronous recompute) rather than the task's own result being checked. If `result.receipts` itself is incomplete/reordered in a way that also produces a *correct*-looking root via the synchronous path (e.g. because the streaming task's gap-detection triggers on a race/ordering artifact that doesn't actually reflect corrupted `result.receipts`, only a corrupted internal `pending` map), the block would be accepted using the fallback root that happens to match the header even though the intended incremental computation had already signaled it could not trust its own inputs. More importantly, the silent `return` masks a real defect class: any bug in the receipt-streaming pipeline (e.g. duplicate index sent, wrong count from `receipts_len`) degrades to "log an `error!` and continue," not "fail the block," which is a systemic verification-bypass pattern rather than a hard failure.

### Impact Explanation
If the streaming receipt-root task's error path is reachable under legitimate conditions (e.g. a transiently misordered/duplicated `IndexedReceipt` due to the retry/segment logic elsewhere in the pipeline, or future code changes to `execute_transactions` that resend an index), the result is a `None` fed into consensus validation. This degrades a strict "recomputed value must equal header value" guarantee into "recompute it yourself and hope it's right," silently disabling the fast/streaming verification path without failing the block outright. This does not always produce a wrong final verdict since `verify_receipts` still recomputes from `result.receipts` — the severity is capped by that fallback. However, it is a correctness/observability regression: a real bug that should deterministically invalidate a block (streaming task detects inconsistent receipt stream) is downgraded to a swallowed `error!` log with execution proceeding as if the fast path had simply been skipped, rather than treated as fatal. This matches Medium severity given the original report was also downgraded to Medium because the actual damage is contingent on additional preconditions (a legitimately broken stream that still recomputes "correctly" via the fallback, or a future regression that removes/weakens the synchronous fallback).

### Likelihood Explanation
The error branches (`receipts_len` mismatch, non-empty `pending`) require an actual bug in the incremental streaming pipeline (duplicate/missing/out-of-order `IndexedReceipt::index` values relative to `receipts_len`) to trigger under production conditions; this is not attacker-triggerable via a malicious block or peer, but is silently reachable via legitimate internal races or future refactors to `execute_transactions`/BAL execution paths that stream receipts. Likelihood is low-to-moderate: no external trigger exists today, but the code pattern removes the "fail loudly" guarantee that would otherwise catch such regressions immediately.

### Recommendation
Do not silently drop the oneshot sender on the incomplete/gapped-receipts paths in `ReceiptRootTaskHandle::run`. Instead, send an explicit error variant (e.g. change the oneshot payload to `Result<(B256, Bloom), ReceiptRootTaskError>`) so the consumer in `BasicEngineValidator::validate_block_with_state` can distinguish "receipt-root task never ran" (safe to fall back to synchronous recompute) from "receipt-root task detected internal corruption" (must fail the block/insertion outright rather than silently falling back). This closes the gap between the task signaling a fault and the caller treating that fault identically to "no precomputation available."

### Proof of Concept
1. Instrument `execute_transactions` in `crates/engine/tree/src/tree/payload_validator.rs` (or a BAL execution path) to resend a receipt with an already-seen index, or to skip sending one — this can be simulated in a unit test directly against `ReceiptRootTaskHandle::run`.
2. Call `ReceiptRootTaskHandle::run(receipts_len)` with a receiver that gets `receipts_len - 1` distinct indices (simulating a dropped receipt) as shown in the existing test harness pattern [7](#0-6) .
3. Observe that `run` hits the `receipts_len.is_some_and(|len| len != next)` branch, logs `tracing::error!`, and returns without sending on `result_tx` [4](#0-3) .
4. On the consumer side, `receipt_root_rx.blocking_recv()` returns an error (sender dropped), which is caught, logged, and converted to `None` rather than propagated as a validation failure [5](#0-4) .
5. `validate_post_execution` proceeds using `None`, meaning `validate_block_post_execution_with_bal_hashes` falls back to `verify_receipts(result.receipts)` instead of failing due to the detected stream corruption [8](#0-7) , silently masking the earlier detected inconsistency.
