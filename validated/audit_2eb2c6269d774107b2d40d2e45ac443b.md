### Title
Unmetered ELF verification/JIT cost in `DeployWithMaxDataLen` combined with fixed 3,000 CU default builtin allocation enables CPU-exhaustion DoS - ([File: compute-budget-instruction/src/compute_budget_instruction_details.rs], [File: program-runtime/src/deploy.rs])

### Summary
`ComputeBudgetInstructionDetails::try_from` uses `BuiltinProgramsFilter::check_program_kind` to classify `bpf_loader_upgradeable::id()` as `ProgramKind::Builtin`, and when no `SetComputeUnitLimit` instruction is present, `calculate_default_compute_unit_limit` grants it a flat `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (3,000 CU). The actual work performed for a `DeployWithMaxDataLen` instruction — `Executable::load`, `verify::<RequisiteVerifier>()`, and JIT compilation in `program_runtime::deploy::deploy_program` — is executed entirely outside any compute-meter accounting call, so its real, ELF-size-scaling CPU cost is neither bounded by the 3,000 CU allocation nor reflected by the `CostModel`'s fixed per-instruction cost constant (`UPGRADEABLE_LOADER_COMPUTE_UNITS`).

### Finding Description
An attacker submits a transaction whose only top-level instruction targets `bpf_loader_upgradeable::id()` with `UpgradeableLoaderInstruction::DeployWithMaxDataLen`, referencing a buffer account previously filled (via `Write`) with a near-max-size ELF, and omits any `SetComputeUnitLimit` compute-budget instruction.

- `ComputeBudgetInstructionDetails::try_from` iterates instructions; since `bpf_loader_upgradeable` is a real, statically known builtin loader (present in `MAYBE_BUILTIN_KEY` / not gated by a migration feature), `BuiltinProgramsFilter::check_program_kind` correctly returns `ProgramKind::Builtin` [1](#0-0) .
- Because no `SetComputeUnitLimit` is requested, `sanitize_and_convert_to_compute_budget_limits` falls back to `calculate_default_compute_unit_limit`, which multiplies the count of non-migratable builtin instructions by `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (3,000 CU) [2](#0-1) .
- On the execution side, `process_loader_upgradeable_instruction` handles `DeployWithMaxDataLen` by invoking the `deploy_program!` macro [3](#0-2) , which calls `program_runtime::deploy::deploy_program`. That function performs `Executable::<InvokeContext>::load(...)`, `executable.verify::<RequisiteVerifier>()`, and `ProgramCacheEntry::reload` (ELF parsing, verification, and JIT compilation) — none of these calls interact with the SBPF compute meter (`consume_compute_meter`) at all [4](#0-3) . This work scales with the size of the submitted ELF (up to `MAX_PERMITTED_DATA_LENGTH`, ~10 MiB) but its cost is completely disconnected from both the transaction's assigned CU budget and the `CostModel`'s block-packing estimate.
- The `CostModel`/scheduler test suite confirms this fixed-cost accounting model: for a `DeployWithMaxDataLen` instruction with no CU-limit set, the declared/cost-model-estimated cost for the loader instruction is the constant `solana_bpf_loader_program::UPGRADEABLE_LOADER_COMPUTE_UNITS`, independent of the size of the ELF being verified, and the transaction is granted the flat 3,000 CU default [5](#0-4) .
- No existing check (signer/writable checks, `sanitize_and_convert_to_compute_budget_limits`, or the SBPF compute meter) bounds or charges for the actual ELF-size-dependent verification/JIT work; the transaction either succeeds cheaply (small ELF) or fails cheaply from the metering's perspective (its CU accounting is unaffected, since this work is unmetered), while the leader/validator still performs the full, size-scaling CPU work of parsing/verifying/JIT-compiling the ELF for every such transaction included in the block.

### Impact Explanation
This is a compute/CPU metering-totality violation: real per-transaction leader/replay CPU cost is decoupled from both the CU budget charged to the transaction and the `CostModel` cost used for block cost-tracking and packing decisions. An attacker can pack many `DeployWithMaxDataLen` transactions carrying large (near-`MAX_PERMITTED_DATA_LENGTH`) ELF buffers into a single block cheaply (paying only base fees plus the 3,000 CU nominal allocation and rent for buffer/program accounts), causing the leader/replaying validators to spend CPU time on ELF parsing/verification/JIT far beyond what the cost model believes the block "costs." This can degrade block production/replay throughput cluster-wide — a liveness/availability impact (falls under Solana's Denial-of-Service / resource-exhaustion category), distinct from funds theft or consensus divergence.

### Likelihood Explanation
Fully unprivileged and repeatable: the attacker needs only to fund a buffer account (rent) and a program account (rent), write ELF bytes via `Write` instructions, and submit `DeployWithMaxDataLen` without a `SetComputeUnitLimit` instruction. No special permissions, validator access, or leaked keys are required — any ordinary RPC/TPU client can construct and submit these transactions repeatedly, and the ELF need not even be a valid, useful program; it only needs to pass through `Executable::load`/`verify` far enough to consume CPU time (or even fail late in verification after most of the parsing work is done).

### Recommendation
Meter the ELF loading, verification, and JIT-compilation work performed in `program_runtime::deploy::deploy_program` against the instruction's compute budget (e.g., charge CU proportional to ELF length before/while parsing, or reject early via a strict pre-check tied to `programdata.len()`), and/or make the `CostModel`'s per-instruction cost for `bpf_loader_upgradeable` deploy/upgrade instructions scale with the size of the program being deployed rather than using a fixed constant, so that both the actual CU accounting and the block-packing cost estimate reflect the true, size-dependent cost of ELF verification.

### Proof of Concept
Bank/SVM integration test plan:
1. Build N `SanitizedTransaction`s, each containing only a `DeployWithMaxDataLen` instruction (no `SetComputeUnitLimit`) referencing a distinct buffer account pre-filled with a near-`MAX_PERMITTED_DATA_LENGTH` valid-enough ELF (following the pattern in `core/tests/scheduler_cost_adjustment.rs::deploy_with_max_data_len_ix`).
2. Compute `CostModel::calculate_cost` for each transaction and sum the reported costs (expected to be dominated by the fixed `UPGRADEABLE_LOADER_COMPUTE_UNITS`/3,000 CU allocation, not ELF size).
3. Replay/process all N transactions through `Bank::process_transactions` (or `program-runtime`'s `deploy_program` directly) and measure wall-clock CPU time.
4. Assert that measured wall-clock time grows roughly linearly with total ELF bytes processed and significantly exceeds what the summed `CostModel` cost would predict/allow for that block, demonstrating the metering-totality gap.

    fn calculate_default_compute_unit_limit(&self, feature_set: &FeatureSet) -> u32 {
        // evaluate if any builtin has migrated with feature_set
        let (num_migrated, num_not_migrated) = self
            .migrating_builtin_feature_counters
            .migrating_builtin
            .iter()
            .enumerate()
            .fold((0, 0), |(migrated, not_migrated), (index, count)| {
                if count.0 > 0 && feature_set.is_active(get_migration_feature_id(index)) {
                    (migrated + count.0, not_migrated)
                } else {
                    (migrated, not_migrated + count.0)
                }
            });

        u32::from(self.num_non_migratable_builtin_instructions.0)
            .saturating_add(u32::from(num_not_migrated))
            .saturating_mul(MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT)
            .saturating_add(
                u32::from(self.num_non_builtin_instructions.0)
                    .saturating_add(u32::from(num_migrated))
                    .saturating_mul(DEFAULT_INSTRUCTION_COMPUTE_UNIT_LIMIT),
            )
    }
