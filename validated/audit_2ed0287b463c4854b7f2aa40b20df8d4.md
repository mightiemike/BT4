### Title
Unchecked integer arithmetic in `ExchangeCapsule.transaction`'s default (non-hardened) path allows silent overflow/underflow of Bancor-style exchange pool balances - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()`, the core swap-settlement routine used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, computes new pool balances with plain Java `+`/`-` operators unless a `hardenedCalc` flag (`allowHardenExchangeCalculation` dynamic parameter, gated by `allowHarden()`) is enabled. This mirrors exactly the reported Rust/Solidity bug class: unchecked arithmetic that silently wraps instead of reverting, versus a "SafeMath"-equivalent checked path that is only conditionally used.

### Finding Description
`ExchangeCapsule.transaction` selects between two code paths based on `hardenedCalc`: [1](#0-0) 

When `hardenedCalc` is `false` (the default unless the `allowHardenExchangeCalculation` dynamic parameter is turned on via a maintenance-period proposal), the new pool balances are computed with unchecked `firstTokenBalance + sellTokenQuant` / `secondTokenBalance - buyTokenQuant` style plain arithmetic rather than `StrictMathWrapper.addExact`/`subtractExact`. Only the `hardenedCalc == true` branch uses the checked wrapper and only that branch validates `newFirstTokenBalance < 0 || newSecondTokenBalance < 0`: [2](#0-1) 

This is structurally identical to the reported issue: Uniswap's Solidity code uses `SafeMath` (`.sub()`/`.add()`) for `state.amountCalculated`, while Rust's Seawater code used unchecked `-=`/`+=`. Here, java-tron's own "hardened" (SafeMath-equivalent) path exists — `AbstractExchangeActuator.subtractExact`/`addExact` — but the underlying `ExchangeCapsule.transaction` internal balance update still bypasses it in the default, non-hardened branch, exactly the same "unmatching logic" problem: a safe path exists but an unsafe path is reachable/is the default.

`ExchangeTransactionActuator.execute()` calls this method directly from an unprivileged, anonymous-broadcastable `ExchangeTransactionContract`: [3](#0-2) 

`ExchangeCapsule` balances are `long` (Java primitives), so Java `+`/`-` on `long` do not throw on overflow — they wrap silently (analogous to Rust release-mode wrapping behavior described in the report).

### Impact Explanation
If pool balances (`firstTokenBalance`/`secondTokenBalance`, both attacker-influenced over repeated `ExchangeInjectContract`/`ExchangeTransactionContract` calls) combined with `sellTokenQuant`/`buyTokenQuant` can be driven close to `Long.MAX_VALUE`/`Long.MIN_VALUE` boundaries, the unchecked addition/subtraction in the default path can wrap around, corrupting the on-chain `Exchange` pool state (`firstTokenBalance`, `secondTokenBalance`). This can lead to incorrect asset accounting for the Bancor-relay exchange (TRC10/TRX swap pools), potentially allowing a party to withdraw or trade against a corrupted balance, producing asset/accounting corruption — matching the "accept" criteria of asset or accounting corruption via a broadcast transaction.

### Likelihood Explanation
Likelihood is constrained: `sellTokenQuant`/pool balances are `long`, and `AssetIssueStore`/`AccountCapsule` balance validations (`assetBalanceEnoughV2`, `exchangeBalanceLimit` checks in `doValidate()`) bound most inputs to realistic economic values, and existing validation in the actuators (e.g., `ExchangeInjectActuator.doValidate` checking `newTokenBalance > balanceLimit`) applies only to the inject path, not to the core `transaction()` swap path in the non-hardened branch. Reaching actual 63-bit overflow requires balances/quantities near `Long.MAX_VALUE` (~9.2×10^18), which is difficult but not proven impossible given `exchangeBalanceLimit` is a configurable dynamic parameter and repeated small legitimate injects could accumulate over time. Without a concrete PoC demonstrating a feasible sequence of transactions reaching overflow thresholds under production configuration, this should be treated similarly to the original finding — plausible root cause, but severity should be downgraded absent PoC.

### Recommendation
Make the checked-arithmetic (`StrictMathWrapper.addExact`/`subtractExact`) balance update in `ExchangeCapsule.transaction()` unconditional (not gated by `hardenedCalc`/`allowHardenExchangeCalculation`), and always validate that resulting balances are non-negative, matching the intent of the "hardened" path. This removes the "unmatching logic" between the safe and unsafe branches, analogous to the recommended `checked_add`/`checked_sub` fix in the report.

### Proof of Concept
No concrete transaction sequence was constructed to reach actual `long` overflow in production-realistic exchange pool balances; a PoC would need to (1) create/inject an exchange pool to accumulate balances near `Long.MAX_VALUE` via repeated `ExchangeInjectContract`/`ExchangeTransactionContract` calls while `allowHardenExchangeCalculation` remains disabled (default), and (2) trigger a swap causing `firstTokenBalance + sellTokenQuant` or `secondTokenBalance - buyTokenQuant` to wrap, then observe corrupted `ExchangeCapsule` balances persisted via `Commons.putExchangeCapsule`. This is flagged as unverified/theoretical due to the practical difficulty of reaching 63-bit boundary values under existing `exchangeBalanceLimit` and asset-supply constraints.
