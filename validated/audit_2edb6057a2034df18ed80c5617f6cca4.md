### Title
Unauthenticated `batchProver_setCommitments` RPC mutates ledger_db state without matching DA validation - ([File: crates/batch-prover/src/rpc.rs])

### Summary
The `batchProver_setCommitments` and `batchProver_createCircuitInput` JSON-RPC methods are not present in the RPC `Auth` middleware's `PROTECTED_METHODS` allowlist, so any network caller who can reach the batch prover's RPC port can insert arbitrary `SequencerCommitment` records into `ledger_db` with no signature or DA cross-check, and can pull a generated circuit input back out. However, the "false state transition made provable" claim in the question does not hold end-to-end, because a hard `assert_eq!` inside `get_batch_proof_circuit_input_from_commitments` recomputes the merkle root from the node's own honestly-synced L2 blocks and rejects any commitment whose `merkle_root`/`l2_end_block_number` don't match real local chain data.

### Finding Description
The binding claimed to be broken is: `commitment.merkle_root` (as stored via `set_commitments` and read back by `create_circuit_input`) == `merkle_root` inside a `DataOnDa::SequencerCommitment` signed by `sequencer_da_public_key`. Before tracing code, this equality is NOT actually required for `create_circuit_input` to succeed against arbitrary attacker-supplied data — a different, local equality is enforced instead:

`merkle_root` supplied in `SequencerCommitment` == `MerkleTree::from_leaves(hashes of ledger_db L2 blocks in [start_l2, end_l2])`, enforced at [1](#0-0) 

`set_commitments` is exposed with no authentication check because `PROTECTED_METHODS` in the `Auth` RPC middleware only lists `backup_create`, `backup_validate`, `backup_info`: [2](#0-1) [3](#0-2) 

`set_commitments` blindly writes attacker-supplied `merkle_root`/`index`/`l2_end_block_number` into ledger_db with no signature or DA check: [4](#0-3) 

`create_circuit_input` then reads back commitments by index range and forwards them unchanged via `ProverRequest::CreateInput`: [5](#0-4) 

However, when the prover actually builds the input, `get_batch_proof_circuit_input_from_commitments` independently recomputes the merkle root from the node's own already-synced L2 block hashes for the claimed range and asserts equality with the attacker-supplied `merkle_root`: [1](#0-0) 

Because this local L2 block data originates from the honestly-synced sequencer chain (not attacker-controlled), an attacker cannot forge a `merkle_root`/`l2_end_block_number` pair that both (a) passes this assertion and (b) does not correspond to a real span of the actual L2 chain. If the attacker supplies a mismatching pair, the assertion panics inside the `Prover`'s async task, which is a denial-of-service outcome (explicitly out of scope), not a false-input generation. If the attacker instead reuses a genuinely real span of L2 blocks (recomputing the correct merkle root), the produced circuit input describes a real state transition, not a false one — it just may carry an attacker-chosen `index`/`l1_height` label that does not correspond to any real DA inscription. This mislabeling has no further effect within `create_circuit_input` itself, since the RPC only returns bytes to the caller and does not submit anything to DA. Any actual submission to DA (via `submit_fake_proof` or the operator-triggered `prove` -> real proving -> DA submission path) is a separate, privileged/operator action outside this attacker's capability under the stated threat model, and downstream light-client verification (`verify_batch_proof_seq_comm_relation` in `crates/light-client-prover/src/circuit/mod.rs`) is designed to check the batch proof's sequencer commitments against ones actually observed and signed on DA, which would reject any commitment index/height/l1_height that the sequencer never posted.

The real, demonstrable bug is narrower than claimed: `set_commitments` is an **unauthenticated JSON-RPC call that mutates node state** (writes into `ledger_db`'s commitment index tables and the prover's pending-commitment queue), which can corrupt the batch prover's own bookkeeping (`get_prover_pending_commitments`, `get_commitment_by_index`, `get_commitment_indices_by_l1`) used by its autonomous proving loop (`try_proving`), and can trigger the local merkle-root assertion panic described above (a crash/DoS vector on the batch-prover process), but it does not produce a forged, DA-inconsistent proof that would be accepted by honest verifiers.

### Impact Explanation
This matches the "High" bucket: an unauthenticated JSON-RPC call mutates node state (`ledger_db` commitment tables and prover pending-commitment queue) without any `Auth`/API-key check. Repeated calls let any network caller corrupt a specific batch prover's local commitment bookkeeping and potentially crash its `Prover` background task via the merkle-root assertion, affecting only that operator's node (blast radius limited to whichever batch prover node has its RPC reachable by the attacker). It does not, by itself, mint or move cBTC, does not forge a DA-accepted proof, and does not cause honest nodes to diverge, because the merkle-root assertion and the light-client's DA cross-checks (`verify_batch_proof_seq_comm_relation`) prevent a falsified state transition from ever being accepted.

### Likelihood Explanation
Trivially reachable: any actor with network access to the batch prover's JSON-RPC port can call `batchProver_setCommitments` and `batchProver_createCircuitInput` with zero cost (no BTC/cBTC required, no signature required) because these methods are absent from `PROTECTED_METHODS`. The precondition is that the batch prover's RPC endpoint is network-reachable by the attacker (operational/deployment-dependent); if the operator restricts the port to `localhost` or a private network, likelihood drops to none.

### Recommendation
Add `batchProver_setCommitments` (and ideally other state-mutating batch-prover RPCs such as `pauseProving`, `retryProvingJob`) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs` so they require the configured `api_key`, or gate them behind a separate admin-only RPC listener that is not exposed publicly. Additionally, convert the `assert_eq!` in `get_batch_proof_circuit_input_from_commitments` (crates/batch-prover/src/prover.rs) into a graceful `anyhow::bail!`/`Result` error rather than a panic, so malformed/attacker-inserted commitments cannot crash the prover task.

    async fn set_commitments(
        &self,
        commitments: Vec<SequencerCommitmentRpcParam>,
    ) -> RpcResult<()> {
        for commitment in commitments {
            let l1_height = commitment.l1_height.to::<u64>();
            let commitment = SequencerCommitment {
                merkle_root: commitment.merkle_root,
                index: commitment.index.to::<u32>(),
                l2_end_block_number: commitment.l2_end_block_number.to::<u64>(),
            };

            info!(
                "Overriding sequencer commitment, index={} merkle_root={} l2_end_height={} l1_height={}",
                commitment.index,
                hex::encode(commitment.merkle_root),
                commitment.l2_end_block_number,
                l1_height,
            );

            self.context
                .ledger_db
                .put_commitment_by_index(&commitment)
                .map_err(internal_rpc_error)?;
            // This might cause some duplicate commitment indices appear in l1 -> index table which is ok
            self.context
                .ledger_db
                .put_commitment_index_by_l1(SlotNumber(l1_height), commitment.index)
                .map_err(internal_rpc_error)?;
            self.context
                .ledger_db
                .put_prover_pending_commitment(commitment.index)
                .map_err(internal_rpc_error)?;
        }

        Ok(())
    }

    async fn create_circuit_input(
        &self,
        index_start: u32,
        index_end: u32,
        mode: PartitionMode,
    ) -> RpcResult<Vec<String>> {
        let commitments = self
            .context
            .ledger_db
            .get_commitment_by_range(index_start..=index_end)
            .map_err(internal_rpc_error)?;

        if commitments.is_empty() {
            return Err(internal_rpc_error(
                "No commitments found for the specified range",
            ));
        }

        let (result_tx, result_rx) = oneshot::channel();

        if self
            .context
            .request_tx
            .send(ProverRequest::CreateInput(mode, commitments, result_tx))
            .await
            .is_err()
        {
            return Err(internal_rpc_error("Proving request channel is closed"));
        }

        let Ok(raw_inputs) = result_rx.await else {
            return Err(internal_rpc_error(
                "Proving request failed for some reason, check logs for details",
            ));
        };
