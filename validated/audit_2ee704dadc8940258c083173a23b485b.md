## Title
Floor division in `BuiltinInstanceLimits::induced_gas_costs` can yield a zero per-instance proving-gas cost, letting a transaction consume a Cairo builtin "for free" in bouncer resource accounting - (File: `crates/blockifier/src/bouncer.rs`)

### Summary
`BuiltinInstanceLimits::induced_gas_costs` derives the per-instance proving-gas cost of each Cairo builtin/opcode from the block-wide `proving_gas` budget using plain integer floor division: `cost = proving_gas.0 / limit.get()`. If `limit` (a per-block instance cap, configurable, `NonZeroU64`) is larger than `proving_gas.0`, the resulting per-instance cost is `0`. This mirrors the reported bug class: floor division producing `0` even though a strictly-positive fee/cost is expected, which is then propagated unchecked through the rest of the resource-accounting pipeline.

### Finding Description
`induced_gas_costs` is defined as: [1](#0-0) 

The derive closure performs `proving_gas.0 / limit.get()` with no check that the quotient is non-zero, analogous to the reported Solidity `_interest = _totalDebt * _borrowRate * _timeDelta / (365 days * 1e18)` pattern where division rounds down to zero for legitimate parameter combinations.

This per-builtin cost table (`BuiltinGasCosts`) is used as `proving_builtin_gas_costs` to price every Cairo primitive (builtin) instance a transaction uses when computing the transaction's `proving_gas` weight, which the bouncer uses to enforce per-block capacity: [2](#0-1) 

The value comes from `BouncerConfig::builtin_gas_costs`, which is itself just a thin wrapper around the vulnerable function: [3](#0-2) 

Unlike the fee-computation code paths in the same crate (e.g. `VersionedConstants::convert_l1_to_l2_gas_price_round_up`, `sierra_gas_to_l1_gas_amount_round_up`, `Fee::checked_div_ceil`) which explicitly perform ceiling division to avoid the exact rounding-to-zero problem: [4](#0-3) [5](#0-4) 

`induced_gas_costs` uses unprotected floor division. If an operator/network configures (or the default configuration ever ships with) a `BuiltinInstanceLimits` value for a given builtin that is larger than the configured block `proving_gas` budget (`BouncerWeights::proving_gas` used as `block_max_capacity.proving_gas`), then `derive()` returns `0` for that builtin. Every subsequent instance of that builtin used by any transaction is then priced at `0` proving-gas, i.e. it contributes nothing to the tracked `TxWeights::bouncer_weights.proving_gas` / accumulated block weight.

### Impact Explanation
The bouncer's proving-gas weight is the mechanism that keeps a block's Cairo-primitive proving cost within the provable capacity of the block (`BouncerConfig::within_max_capacity_or_err`, `Bouncer::try_update`). If a builtin's induced cost silently becomes `0`, transactions using that builtin are effectively invisible to this specific resource dimension: the sequencer/bouncer will admit far more instances of that builtin into a block than the true proving budget supports, without ever hitting `BlockFull`. This is a resource/DoS-class impact reaching "a network unable to confirm new transactions" (blocks that cannot actually be proven / block-building capacity violated) once real proving is attempted on an over-packed block — i.e., a state where blocks accepted by the sequencer exceed the provable resource envelope, causing block-production/proving failures downstream. It also creates a free (unmetered) execution avenue that a single unprivileged transaction sender can exploit repeatedly by targeting whichever builtin has an under-priced/zero induced cost, degrading bouncer-based DoS protection.

### Likelihood Explanation
This requires a specific relationship between the configured `block_max_capacity.proving_gas` and per-builtin `BuiltinInstanceLimits`. With the shipped defaults (e.g. `keccak: nz(10_000)`, default proving_gas budget in the multi-billion range as seen in tests: `induced_gas_costs(GasAmount(6_000_000_000))` yields non-zero costs for all defaults, per the test snapshot `test_induced_builtin_gas_costs_from_default_limits`), the bug is not triggered today. However, the function itself has no defensive check (`assert!(cost > 0)` or similar), so any future/alternate configuration (chain config change, test/staging config, or a limit raised without a corresponding proving_gas increase) that makes `limit > proving_gas` for any builtin silently reintroduces this exact zero-fee condition — a config-driven, not code-audited, invariant. Given the lack of any explicit non-zero enforcement, likelihood should be rated Medium: exploitable only under specific (but plausible and unvalidated) parameter combinations, exactly matching the "same combination-of-parameters" caveat in the source report.

### Recommendation
Add an explicit invariant in `induced_gas_costs` (or at `BouncerConfig` construction/deserialization time) that `proving_gas.0 >= limit.get()` for every builtin, or clamp/round the derived cost up to at least `1` when `proving_gas.0 > 0`, mirroring the `checked_div_ceil`/`.ceil()` patterns already used elsewhere in this codebase for fee-critical divisions:
```rust
let derive = |limit: NonZeroU64| -> u64 {
    let cost = proving_gas.0 / limit.get();
    assert!(cost > 0 || proving_gas.0 == 0, "Builtin instance limit exceeds proving-gas budget, inducing a zero cost");
    cost
};
```
Alternatively, validate this relationship in `BouncerConfig`'s config-loading/deny-unknown-fields validation path so that an operator cannot deploy a configuration where any builtin's induced cost floors to zero.

### Proof of Concept
1. Configure (or imagine a future/alternate) `BouncerConfig.block_max_capacity.proving_gas` = e.g. `1_000` and leave `BuiltinInstanceLimits::keccak` at its documented default `10_000` (i.e., `limit > proving_gas`).
2. `BouncerConfig::builtin_gas_costs()` calls `induced_gas_costs(GasAmount(1_000))`, and for `keccak`: `derive(NonZeroU64::new(10_000)) = 1_000 / 10_000 = 0`. [6](#0-5) 
3. Submit transactions that heavily use the `keccak` builtin. `get_tx_weights` computes `proving_gas` via `compute_proving_gas` using `proving_builtin_gas_costs` (= the above table), so every keccak instance contributes `0` to `total_proving_gas`. [2](#0-1) 
4. `Bouncer::try_update`/`BouncerConfig::within_max_capacity_or_err` never sees the true keccak proving cost and keeps admitting transactions, allowing the block's real (keccak-driven) proving-gas usage to exceed `block_max_capacity.proving_gas` while the bouncer still reports the block as having capacity — a resource-accounting failure with no code-level safeguard against it.

impl BuiltinInstanceLimits {
    /// Induces the per-instance proving-gas cost of each Cairo primitive from its per-block
    /// instance limit: `cost = floor(proving_gas / limit)`.
    pub fn induced_gas_costs(&self, proving_gas: GasAmount) -> BuiltinGasCosts {
        let derive = |limit: NonZeroU64| -> u64 { proving_gas.0 / limit.get() };
        BuiltinGasCosts {
            pedersen: derive(self.pedersen),
            range_check: derive(self.range_check),
            range_check96: derive(self.range_check96),
            poseidon: derive(self.poseidon),
            ecdsa: derive(self.ecdsa),
            ecop: derive(self.ecop),
            bitwise: derive(self.bitwise),
            keccak: derive(self.keccak),
            add_mod: derive(self.add_mod),
            mul_mod: derive(self.mul_mod),
            blake: derive(self.blake),
        }
    }
}
