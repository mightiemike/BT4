### Title
Deploy-exclusivity / P_MAX admission race in `PendingTxSession::check_pending` allows the NEP-611 mutual-exclusion invariant to be bypassed - (File: chain/client/src/pending_transaction_queue.rs)

### Summary
The flatcoin bug is a boolean "lock" that is checked and cleared by two independent, uncoordinated writers, so a resource can be treated as unlocked while a competing pending intent for that same resource is still outstanding. The nearcore analog is `PendingTxSession::check_pending` in `chain/client/src/pending_transaction_queue.rs`, which enforces the NEP-611 invariant "an account with a pending deploy-like transaction may not have any other pending access-key transaction, and vice-versa" using a check-then-optimistically-update pattern against shared, mutex-protected aggregate counters (`access_key_tx_count`, `deploy_tx_count`) that are only reconciled with ground truth when a chunk is later certified or rejected.

### Finding Description
`PendingTransactionQueue` maintains per-account aggregates (`PendingAccount.access_key_tx_count`, `PendingAccount.deploy_tx_count`) across all chunks that have been included in blocks but not yet certified/executed [1](#0-0) . `PendingTxSession::check_pending` is the gate that enforces "deploy exclusivity": a deploy-like transaction cannot coexist with any other pending access-key transaction for the same account [2](#0-1)  and also enforces the P_MAX cap for contract accounts [3](#0-2) .

The check is performed by taking a short-lived lock on the shared `Arc<Mutex<ShardedPendingTransactionQueue>>`, snapshotting the *already-certified-pending* state, releasing the lock, and then combining that snapshot with the session's own **local, unshared** counters (`session_access_key_tx_counts`, `session_deploy_tx_counts`) to decide admission [4](#0-3) . After the decision, the session-local counters are updated "optimistically" — i.e. speculative writes to a lock-like gate that is never synchronized back to the shared queue except when the chunk that produced them is ultimately included in a block and merged via `add_chunk_transactions` [5](#0-4) .

This is structurally identical to the `LimitOrder`/`DelayedOrder` `isLocked` race: two independent code paths (here, two independent `PendingTxSession` instances / chunk-production attempts) each hold their own private view of the "lock" (deploy-exclusivity counters), consult a shared but stale source of truth, and only reconcile with the shared state asynchronously and unidirectionally (via `add_chunk_transactions`/`remove_certified_chunk_by_block_hash`) rather than atomically across all writers at decision time. The developers' own comment acknowledges the non-atomicity explicitly: "If the runtime subsequently rejects the tx ... these counts are not rolled back and the tx is discarded ... this reduces throughput under high contention," but the comment only reasons about the throughput-reduction direction of the race (over-restriction) and dismisses it as low risk because "only transactions with valid signatures can reach this point" [6](#0-5) . It does not consider the opposite direction: multiple concurrent sessions (e.g. concurrent chunk-production attempts for different candidate blocks/heights on the same shard, as created via `PendingTxSession::new` in `chunk_producer.rs`) each read the *same* stale snapshot from the shared queue before either session's selections are merged back with `add_chunk_transactions`, so each session can independently conclude "no deploy pending, admit this deploy" or "no other access-key tx pending, admit this transfer" for the same account. If both candidate chunks are subsequently included in blocks (e.g. across a fork, or across the window between chunk production and certification), the shared aggregate state can end up reflecting both a deploy-like transaction and a conflicting non-deploy access-key transaction pending simultaneously for the same account — exactly mirroring the flatcoin PoC where the `isLocked` flag was cleared by one order's cancellation while a second, independent order for the same NFT was still outstanding.

### Impact Explanation
NEP-611 deploy exclusivity exists to prevent a contract deploy from racing with another access-key transaction against the same account's state within the same uncertified window (avoiding non-deterministic or unsafe interleavings of a code change with a concurrently-authorized action). A bypass allows two mutually-exclusive per-account transaction classes to be pending at once, which is precisely the invariant violation the mechanism was built to prevent — the same "protocol invariant undermined" characterization used in the source report for `isLocked`. Because this gate is advisory input to the runtime rather than that runtime's final authority (the runtime still performs its own balance/nonce checks), the direct blast radius is bounded, but the finding shows the admission-control invariant itself is not race-free under concurrent chunk-production sessions for the same shard, which is a state-machine soundness defect in transaction admission and chunk transaction selection — one of the explicitly in-scope subsystems.

### Likelihood Explanation
Reachable purely by an unprivileged signer submitting normally signed transactions; no validator or network-layer misbehavior is required to trigger the race — only the coincidence of two chunk-production sessions for the same shard evaluating overlapping account state before merging results back into `PendingTransactionQueue`. Whether nearcore's current chunk-production scheduling ever actually creates two concurrent `PendingTxSession` instances for the same shard before either's transactions are merged (e.g., due to block-production races, forks, or retries) could not be fully confirmed from the available slices of `chunk_producer.rs`; this is the primary source of uncertainty in this analysis and would need to be verified by reading `chain/client/src/chunk_producer.rs` (and the call sites for `PendingTxSession::new`) in full, which was not retrievable within the remaining tool budget.

### Recommendation
1. Make the deploy-exclusivity/P_MAX check-and-reserve atomic under the same lock as the read: perform `query_pending_state` and the session-local speculative increment together as a single critical section guarded by a shared, cross-session structure (not per-`PendingTxSession` private maps), so two concurrent sessions cannot both observe "no conflict" for the same account.
2. Alternatively, use a per-account reservation token acquired under the shared mutex at admission time and released/committed only when the chunk is finalized, ensuring any concurrent session sees the reservation immediately rather than after `add_chunk_transactions` runs.
3. Add integration/test-loop coverage that constructs two `PendingTxSession`s over the same `ShardedPendingTransactionQueue` and interleaves `check_pending` calls for a deploy tx and a conflicting access-key tx from the same account, asserting that at most one is ever admitted before the other's chunk is merged.

### Proof of Concept
Conceptual reproduction (mirrors the Foundry PoC's cancel-then-transfer pattern, adapted to this subsystem):
1. Create `sharded = Arc::new(Mutex::new(ShardedPendingTransactionQueue::new()))` and two independent `PendingTxSession`s, `session_a` and `session_b`, both bound to the same `shard_uid`, simulating two concurrent chunk-production attempts before either's selections are merged via `add_chunk_transactions` (as would occur in `PendingTxSession::new` call sites in `chain/client/src/chunk_producer.rs`).
2. `session_a.check_pending(&deploy_tx_for_alice, HasContract::No)` → `Admit` (queue is empty, session_a's local `session_deploy_tx_counts["alice"] = 1`, but this is never written into the shared `ShardedPendingTransactionQueue`).
3. Before `session_a`'s chunk is included in a block (i.e., before `add_chunk_transactions` runs), `session_b.check_pending(&transfer_tx_for_alice, HasContract::No)` is evaluated: `query_pending_state` still reports `deploy_tx_count == 0` and `access_key_tx_count == 0` for alice (session_a's reservation is invisible to session_b), so `session_b` also returns `Admit`.
4. Both chunks are subsequently included in blocks and merged into the shared queue via `add_chunk_transactions`, at which point `pending_accounts["alice"]` now has both `deploy_tx_count == 1` and `access_key_tx_count == 1` simultaneously — violating the invariant enforced at lines 537-546 of `chain/client/src/pending_transaction_queue.rs` that a deploy and any other access-key transaction must never coexist as pending for the same account.

This mirrors the Solidity PoC's core mechanic: a check performed against a stale/partial view of a shared "lock", followed by an unsynchronized write, allows a second concurrent actor to be admitted despite a still-outstanding conflicting operation.

            let guard = self.pending_transaction_queue.lock();
            match guard.get(&self.shard_uid) {
