### Title
Attached NEAR deposit is permanently lost when `WalletContract::rlp_execute` fails synchronously without spawning a refund promise - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is marked `#[payable]`, so any predecessor can attach a NEAR deposit to the call. NEAR credits an attached deposit to the receiving contract's account balance unconditionally as soon as the receipt executes, independent of what the contract logic does with it. Several code paths inside `rlp_execute`/`inner_rlp_execute` return early with a plain `ExecuteResponse` (no promise), and on those paths the already-computed `CallerDeposit` is never used to schedule a refund transfer. The deposit therefore stays on the wallet contract's balance forever, exactly analogous to the reported `receiveFunds()` issue where `msg.value` is accepted on code paths that don't use/refund it.

### Finding Description
`rlp_execute` immediately short-circuits before doing any refund bookkeeping when a transaction is already in flight: [1](#0-0) 

For all other cases it calls `inner_rlp_execute`, and any `Err` returned from it is turned directly into a value response with no promise created: [2](#0-1) 

Inside `inner_rlp_execute`, the attached deposit is read via `env::attached_deposit()` when building `ExecutionContext`, and `CallerDeposit::new(&context)` is computed to *later* support refunding an external caller if a spawned cross-contract call fails: [3](#0-2) 

However, on every synchronous error branch (`Error::User(_)`, or any other error from `parse_rlp_tx_to_action`, or `AccountNonceExhausted` before `context`/`caller_deposit` even exist), the function returns `Err(err)` immediately — `caller_deposit` is simply dropped, no refund promise is created: [4](#0-3) 

The `CallerDeposit` mechanism is only ever consumed inside the promise-callback chain (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) to refund the caller when the *spawned* cross-contract call fails asynchronously: [5](#0-4) 

The dedicated test `test_caller_refunds` only exercises the asynchronous-failure refund path (cross-contract call fails after a promise is created), not the synchronous-failure path where `inner_rlp_execute` itself returns `Err` before any promise is scheduled: [6](#0-5) 

Because NEAR's runtime deposits `attached_deposit` into the receiver account's balance unconditionally as part of executing the `FunctionCall` action (before/regardless of the WASM logic's outcome, per the Economics API and refund semantics), any deposit attached to a call that hits one of these synchronous error branches, or the `has_in_flight_tx` early-return, is absorbed into the wallet contract balance with no code path ever issuing a transfer back to the caller.

### Impact Explanation
Any unprivileged external account (e.g., a malicious or buggy relayer, or simply a caller who mis-attaches a deposit while calling `rlp_execute` with an invalid/expired/malformed RLP transaction, wrong nonce, unsupported action, or while a transaction is already in flight) permanently loses that deposit into the wallet contract's balance with no recovery mechanism. This is a permanent, transaction-triggered loss of funds for the caller — a concrete "permanently frozen funds" outcome reachable from a single contract call, matching the report's bug class of `payable`-like functions that silently swallow value on non-consuming code paths.

### Likelihood Explanation
High reachability: `rlp_execute` is a public, payable method callable by any account (not access-key restricted for a general external caller; the `#[payable]` attribute explicitly permits deposits), and triggering a parse/validation error (bad nonce, bad signature/decoding, unsupported action, or a concurrent in-flight transaction) is trivial and fully within an unprivileged caller's control or an accidental relayer mistake.

### Recommendation
On every synchronous error/early-return path in `rlp_execute`/`inner_rlp_execute` (the `has_in_flight_tx` check, `AccountNonceExhausted`, and all `Err` branches from `ExecutionContext::new`/`parse_rlp_tx_to_action`), check whether an attached deposit exists (e.g., using the same `CallerDeposit` logic, computed before any early return) and, if so, schedule a transfer back to the predecessor before returning the error response — mirroring what `rlp_execute_callback` already does for asynchronous failures.

### Proof of Concept
1. Deploy the wallet contract for an eth-implicit account as in `test_wallet_contract_interaction` (`integration-tests/src/tests/features/wallet_contract.rs`).
2. As an external caller (not the wallet account itself), call `rlp_execute(target, tx_bytes_b64)` attaching a non-zero NEAR deposit, where `tx_bytes_b64` is crafted to fail parsing (e.g., a garbled/invalid RLP transaction, or one that decodes but hits `Error::User(_)`, such as an unsupported action or a chain-id mismatch — see `internal::parse_rlp_tx_to_action` error paths, exercised in `tests/user_error.rs`).
3. Observe that `inner_rlp_execute` returns `Err(...)` and `rlp_execute` returns `PromiseOrValue::Value(e.into())` with no promise created.
4. Query the caller's balance before/after: it decreases by the attached deposit, and query the wallet contract's balance: it increases by the same amount, with no subsequent transfer ever returning it — the deposit is permanently stuck in the wallet contract's account.

fn inner_rlp_execute(
    current_account_id: AccountId,
    predecessor_account_id: AccountId,
    target: AccountId,
    tx_bytes_b64: String,
    nonce: &mut u64,
) -> Result<Promise, Error> {
    if *nonce == u64::MAX {
        return Err(Error::AccountNonceExhausted);
    }
    let context = ExecutionContext::new(
        current_account_id.clone(),
        predecessor_account_id,
        env::attached_deposit(),
    )?;
    let caller_deposit = CallerDeposit::new(&context);

    let parsing_result = internal::parse_rlp_tx_to_action(&tx_bytes_b64, &target, &context, *nonce);
    let (action, transaction_kind) = match parsing_result {
        Ok((action, transaction_kind)) => {
            // Increment nonce for all cases where the registrar contract is not needed
            // to prevent replay of those transactions. For transactions that go through
            // the registrar we still do not know if the transaction has a relayer error
            // or not, therefore we must delay incrementing the nonce.
            //
            // Note: relayers with access keys cannot use this delay to needlessly spend
            // the users tokens because only one transaction is allowed to be in-flight
            // at a time.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                address_check: Some(_),
                ..
            }) = &transaction_kind
            {
            } else {
                *nonce = nonce.saturating_add(1);
            }

            // If the action is an emulated base token or ERC-20 transfer with a non-zero fee then
            // create a promise to send the refund to the relayer. This allows any relayer
            // to safely serve base token transfers from any wallet without additional
            // on-boarding because the relayer will receive some compensation for sending
            // the transaction. Users should always verify the fee before signing a base token
            // transfer. Relayers should also verify the fee before sending to make sure the
            // user's signed transaction will refund enough to cover the relayer's gas costs.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                fee,
                ..
            })
            | TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
                &transaction_kind
            {
                if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
                    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
                    env::promise_batch_action_transfer(refund_promise, *fee);
                }
            }

            (action, transaction_kind)
        }
        Err(err @ Error::User(_)) => {
            // Increment nonce on all user errors to prevent replay.
            *nonce = nonce.saturating_add(1);
            return Err(err);
        }
        Err(err) => {
            // Do not increment nonce on Relayer or AccountId errors.
            // The latter error is an issue in the deployment (so the nonce is meaningless).
            // The former arises from the relayer itself doing something wrong and thus the
            // user's transaction could still be valid and potentially submitted properly by
            // another relayer. To allow this we do not increment the nonce.
            //
            // Note: if a relayer is using an access key for this wallet then that key will
            // still be revoked (in the main logic of `rlp_execute`). This fact together with
            // the condition that there only be one in-flight transaction at a time implies
            // that a relayer cannot maliciously burn a large portion of the user's tokens.
            // If the relayer is not using an access key then they are spending their own
            // resources on the gas and therefore we do not care if the relayer submits
            // the same faulty transaction multiple times.
            return Err(err);
        }

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
