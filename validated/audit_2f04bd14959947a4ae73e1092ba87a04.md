Confirmed: the `TokenConfig.Enabled` field exists specifically to gate "whether this token is enabled for minting/bridging" [1](#0-0)  and can be flipped off post-hoc by governance/admin via `MsgUpdateTokenConfig`/`MsgRemoveTokenConfig`, but every inbound-execution code path that fetches the token config (`ExecuteInboundGas`, `ExecuteInboundFunds`→`depositPRC20`, `ExecuteInboundGasAndPayload`) only checks for lookup errors — never the `Enabled` flag itself.

### Title
Missing token-enabled check in inbound execution allows minting a token marked disabled by admin - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
`x/uregistry`'s `TokenConfig.Enabled` field is documented as controlling "whether this token is enabled for minting/bridging" [2](#0-1) , and is admin-only to flip via `MsgUpdateTokenConfig`/`MsgRemoveTokenConfig` [3](#0-2) . However, `x/uexecutor`'s inbound execution paths call `k.uregistryKeeper.GetTokenConfig(...)` and only handle the not-found/lookup-error case; they never read or enforce `tokenConfig.Enabled` before minting the PRC20 representation.

### Finding Description
`depositPRC20` in `handler.go` fetches the token config and immediately proceeds to call `CallPRC20Deposit` without checking `tokenConfig.Enabled`: [4](#0-3) 

The same pattern repeats in the gas-abstraction path: `ExecuteInboundGas` fetches `tokenConfig` and proceeds straight to the swap/deposit flow with no `Enabled` check [5](#0-4) , and in `ExecuteInboundGasAndPayload`, which also fetches `tokenConfig` and deposits without checking `Enabled` [6](#0-5) .

By contrast, `x/uregistry`'s own `IsChainInboundEnabled`/`IsChainOutboundEnabled` helpers exist and are correctly checked at the `MsgVoteInbound`/`MsgExecutePayload` entry points [7](#0-6) [8](#0-7) , but no analogous `IsTokenEnabled` helper exists in `x/uregistry/keeper/keeper.go`, and no caller anywhere in `x/uexecutor` reads `TokenConfig.Enabled`.

This mirrors the SecondSwap bug class exactly: a per-entity "allowed" boolean flag is checked in one lifecycle step (listing/voting) but omitted at the actual value-transfer step (completePurchase/deposit-mint), so once the UTX/ballot has already progressed into the execution pipeline, the disabled flag has no effect on the mint.

### Impact Explanation
If admin disables a compromised, depegged, or exploited token via `MsgUpdateTokenConfig` (setting `Enabled=false`) while leaving the `NativeRepresentation`/PRC20 contract mapping intact (a plausible admin action — disabling further use of a token without immediately unmapping it), inbound votes that are already past the `IsChainInboundEnabled` gate (chain-level, not token-level) will still successfully mint the corresponding PRC20 to the recipient's UEA. This is an unauthorized-mint condition: PRC20 supply is created for a token the admin explicitly intended to stop, undermining the registry's token-level circuit breaker and any accounting/liquidity-cap assumptions built on `Enabled` semantics.

### Likelihood Explanation
Reaching this requires only an ordinary unprivileged user submitting/observing a normal cross-chain deposit for a token whose config still resolves (chain enabled, token config present with `Enabled=false`). No malicious validator or privileged actor action is needed on the attacker's side — the only privileged action involved is the legitimate admin disabling the token, which is an expected governance operation the system is supposed to honor. Since `Enabled` is silently ignored by every inbound-execution code path (three separate paths: `ExecuteInboundFunds`, `ExecuteInboundGas`, `ExecuteInboundGasAndPayload`), a triggering UV vote after the admin disables the token proceeds to a successful ballot-finalized mint. This is a reachable, unprivileged-trigger bug given honest validators simply voting normally.

### Recommendation
Add a token-enabled check in all inbound execution paths that fetch `TokenConfig`, analogous to the existing chain-level `IsChainInboundEnabled` check:
- Add an `IsTokenEnabled(ctx, chain, address)` helper to `x/uregistry/keeper/keeper.go` (mirroring `IsChainInboundEnabled`).
- Call it in `depositPRC20` (`x/uexecutor/keeper/handler.go`), `ExecuteInboundGas`, and `ExecuteInboundGasAndPayload` immediately after `GetTokenConfig` succeeds, treating a disabled token the same as a `GetTokenConfig` failure (fail the PCTx and, for non-CEA inbounds, schedule an `INBOUND_REVERT`).

### Proof of Concept
1. Admin registers `TokenConfig{Chain: "eip155:11155111", Address: usdc, Enabled: true, NativeRepresentation: {ContractAddress: prc20}}`.
2. A user's cross-chain deposit for that token is observed by UVs; they call `MsgVoteInbound` but quorum has not yet been reached.
3. Admin calls `MsgUpdateTokenConfig` to set `Enabled=false` for that token (e.g., due to a discovered issue with the token) while chain-level `IsInboundEnabled` remains `true`.
4. The remaining UV votes are cast; `k.uregistryKeeper.IsChainInboundEnabled` still returns `true` (checked at `VoteInbound`, chain-level only), so the ballot finalizes and `ExecuteInboundFunds`/`ExecuteInboundGas`/`ExecuteInboundGasAndPayload` run.
5. `depositPRC20` (or the gas-swap equivalent) calls `GetTokenConfig`, succeeds, and mints/deposits the PRC20 to the recipient — despite `Enabled` now being `false` — because no path checks `tokenConfig.Enabled`.

*Note: I was unable to fully verify whether an outbound (PRC20 → external token withdraw) path independently re-checks `TokenConfig.Enabled`, as that code was not directly inspected; the analysis above is scoped to the confirmed inbound mint paths.*

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
