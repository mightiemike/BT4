### Title
`remove_deposits` purges deposits from mempool regardless of on-chain execution success - ([File: crates/sequencer/src/runner.rs])

### Summary
`produce_l2_block_inner` calls `DepositDataMempool::remove_deposits(&deposit_data)` using the full, unfiltered list returned by `fetch_deposits()`, not the subset of deposits whose `BridgeDeposit` system transaction actually executed successfully. `process_sys_txs` silently discards (via `continue`, without adding to `all_txs`) any deposit whose Bridge `deposit()` call reverted, but this failure information never reaches the removal call, so the deposit is dropped from the mempool exactly as if it had succeeded.

### Finding Description
The binding that must hold is: `deposits_removed_from_mempool == deposits_whose_BridgeDeposit_system_tx_executed_successfully`.

Trace:
1. `citrea_sendRawDepositTransaction` (`crates/sequencer/src/rpc.rs:330-388`) only performs a speculative `evm.get_call(dep_tx, BlockId::pending(), ...)` simulation, then unconditionally calls `add_deposit_tx` on success [1](#0-0) .
2. On block production, `produce_l2_block_inner` fetches the pending deposits with `fetch_deposits` into `deposit_data`, and this exact slice is used both for simulation via `dry_run_transactions`/`produce_and_run_system_transactions` and later re-used verbatim to call `remove_deposits` [2](#0-1) [3](#0-2) .
3. `process_sys_txs` builds one `BridgeDeposit` system event per entry of `deposit_data` and applies each as a real signed system transaction. If the deposit call reverts (`EvmSystemTransactionNotSuccessful`), the working set is reverted and the loop simply `continue`s without adding the tx to `all_txs` — the failure is swallowed and not surfaced to any caller [4](#0-3) .
4. Because `deposit_data` (the input to `remove_deposits`) is never filtered down to only the deposits that succeeded, `remove_deposits` at line 636-643 removes every deposit that was *fetched*, including ones whose Bridge deposit call actually reverted during real execution [3](#0-2) .
5. `DepositDataMempool::remove_deposits` itself has no concept of success/failure — it only matches by `calc_tx_id` against whatever list it's given [5](#0-4) .

Root cause: the removal call is keyed on "was attempted / fetched for this block" rather than "was successfully applied and credited cBTC." No guard (`BitcoinVerifier`, `Auth`, fork rule, etc.) checks this relationship because it is purely a sequencer-local mempool bookkeeping bug, not a consensus-verified invariant — `verifyInclusion`/Bridge.sol correctly reverts the state changes on failure, but the *mempool* incorrectly still discards the deposit request.

This can be triggered without any privileged role: an attacker (or even benign network conditions) causes multiple L1 blocks to be folded between the time `send_raw_deposit_transaction`'s `eth_call` succeeds (against `BlockId::pending()`) and the time the deposit is actually processed as a system transaction in a subsequent L2 block, during which a competing `setBlockInfo` event changes the light client's stored info for the height referenced by the deposit's inclusion proof, causing the real `deposit()` call to revert while the earlier simulation had succeeded.

### Impact Explanation
When this triggers, a valid Bitcoin move-to-vault deposit (real BTC already locked with Clementine signers) is silently dropped from the sequencer's deposit mempool without any cBTC being credited on L2, violating the stated 1:1 binding between Bitcoin move-to-vault outputs and Bridge-contract credited cBTC (in this direction: 0 cBTC credited despite 1 real deposit). The user/operator receives no explicit failure signal from the original RPC call (which already returned success), and the deposit silently vanishes from `accepted_deposit_txs`/`pending_deposits`. Recovery is only possible if the depositor's off-chain component notices the missing credit and re-submits `citrea_sendRawDepositTransaction` (which is allowed again after removal, per `add_deposit_tx`'s pending-set check). This is repeatable for every deposit unlucky enough to straddle a light-client `setBlockInfo` transition between simulation and inclusion, and it affects only the sequencer's local mempool state (no incorrect consensus root or double-mint), so it does not directly rise to "cBTC minted without a matching deposit" but rather "deposit silently and irrecoverably dropped from queue without automatic retry," pending manual resubmission.

### Likelihood Explanation
Preconditions: multiple L1 blocks must be folded into L2 blocks between the RPC simulation and the block that actually runs the deposit system transaction, with a light-client `setBlockInfo` update at the relevant height happening in between. This is plausible during normal sequencer catch-up (multiple missed DA blocks, `process_missed_da_blocks`) or during any period of latency between deposit submission and mempool draining, and requires no attacker privileges or BTC cost beyond the cost of a legitimate deposit — it can happen incidentally, or be induced by anyone submitting a deposit blob that references a not-yet-finalized/soon-to-be-overwritten light client height and then waiting for natural L1 block cadence to advance.

### Recommendation
Track which deposits actually succeeded during `process_sys_txs`/`produce_and_run_system_transactions` (e.g., return the list of deposit-data entries whose `BridgeDeposit` event was included in `all_txs`) and pass only that successful subset to `remove_deposits`, instead of the full `deposit_data` fetched at the top of `produce_l2_block_inner`. Failed deposits should remain in the mempool (or be explicitly re-queued/logged) so they are retried automatically on a subsequent block once the light client state stabilizes.

```rust
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
```
