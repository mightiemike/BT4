## Analysis

The external report's bug class is: an unprivileged function accepts a value it did not independently verify, letting inconsistent/incorrect state pass as authorized. The strongest Aptos-native analog I found is a genuine, developer-acknowledged integrity gap in the transaction-output-to-`TransactionInfo` comparator used by replay/execution-verification tooling.

### Title
`ensure_match_transaction_info` omits checkpoint-hash comparison, allowing replay/execution verification to accept a divergent position (and state/hot-state) root as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by `db-tool`'s `replay_on_archive`/`replay_verify`, `aptos-debugger`, the CLI replay command, and the chunk executor's `verify_execution` path to confirm that locally re-executed output matches the `TransactionInfo` committed on-chain. The function checks status, gas, write-set hash (`state_change_hash`), and event root hash, but explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The function compares:
- execution status vs `txn_info.status()`
- `gas_used()`
- `write_set` hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

but never touches `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`. The comment at the end of the function is explicit about this gap:

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution. Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`."

This is used as the sole per-transaction correctness gate in multiple consumers:
- `execution/executor/src/chunk_executor/mod.rs` `verify_execution` — the state-sync chunk-executor path that validates locally re-executed output against the target `TransactionInfo` before accepting a backup/state-sync chunk. [2](#0-1) 
- `storage/db-tool/src/replay_on_archive.rs` `execute_and_verify` — mainnet replay-verify tooling. [3](#0-2) 
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` replay commands. [4](#0-3) [5](#0-4) 

Meanwhile, `TransactionInfoV1.position_state_checkpoint_hash` is a real, hashed, consensus-committed field once `TRANSACTION_INFO_V1` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled — it becomes part of the leaf hashed into the transaction accumulator. [6](#0-5)  The on-chain feature flag comment confirms this root is meant to be consensus-verified: "execution computes the trading-native state roots and commits them to `TransactionInfoV1`, so they are consensus-verified." [7](#0-6) 

### Impact Explanation
Once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on (a stated future step per the feature-flag comment), a node whose local native-position Jellyfish Merkle tree state diverges from the authenticated on-chain root (due to a local storage bug, a bug in `position_summary_at_commit`/`merklize_position`, non-determinism in the native-position write path, or a chain fork specific to that subsystem) would **not be detected** by any of the tooling that relies on `ensure_match_transaction_info`:
- `replay_on_archive`/`replay_verify` (mainnet integrity auditing tooling) would report a clean replay despite a wrong position-state root.
- The chunk executor's `verify_execution` (used during fast/intelligent sync verification of downloaded chunks) would accept output whose position root differs from the authenticated `TransactionInfo`.

This breaks the "authenticated API / proof-bearing responses must stay bound to the right ledger version, root, and object" invariant for the native-position subsystem: a diverging, unauthenticated local root can be silently treated as verified-correct.

### Likelihood Explanation
This is currently latent rather than immediately exploitable on mainnet: `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `TRANSACTION_INFO_V1` are gated behind on-chain feature flags [8](#0-7) , and the developers left an explicit TODO acknowledging the exact gap and stating it must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [9](#0-8) . However, the comparator is live code, already used in production replay/verification paths today, and the checkpoint hashes it silently ignores also include the ordinary `state_checkpoint_hash` (main state) and `hot_state_checkpoint_hash` — meaning the gap is not solely a future native-position risk, but a general omission in the correctness gate that a divergence in the (already-live) main state checkpoint hash could similarly slip past this specific check, though that hash is separately checked elsewhere in the pipeline (e.g. `state_snapshot restore` in `storage/backup/backup-cli`). The clearest, self-contained, currently-latent root cause is the explicitly acknowledged omission in this one function.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally-computed equivalents (accepting `None` only where a `None` is also expected, per the feature-flag gating), before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on for any network. All callers (`replay_on_archive`, `chunk_executor::verify_execution`, `aptos-debugger`, CLI replay) should be re-audited to ensure they pass or compute the expected checkpoint hashes for this new check.

### Proof of Concept
Not independently reproducible without enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and injecting a native-position storage divergence, which requires a live/test network with the feature enabled — I was unable to execute this. The finding is based on static code inspection of `ensure_match_transaction_info` and its call sites, corroborated by the maintainers' own inline comment documenting the exact same gap and prerequisite fix.

**Note on confidence**: This finding is anchored to an explicit developer TODO in the code rather than a demonstrated exploit against currently-enabled mainnet behavior; whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is scheduled for near-term activation could not be determined from the indexed code alone.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
