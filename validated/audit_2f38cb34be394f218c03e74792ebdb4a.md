### Title
Unchecked `long` addition/overflow in TRC10 Exchange balance-limit checks and pool balance updates when hardened arithmetic is disabled - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
java-tron's TRC10 "Exchange" (Bancor-style AMM) contract computes pool balances and their bounds using plain `long` arithmetic (`x + y`, `x - y`) whenever the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter is inactive, which is the default state until explicitly activated by governance proposal. This mirrors the reported class of bug (arithmetic overflow in AMM price/reserve math that should have used a safe-math library), except here the overflow is a `long` addition wraparound rather than a `uint256` multiplication overflow.

### Finding Description
`AbstractExchangeActuator.addExact`/`subtractExact` only perform overflow-checked arithmetic when `allowHarden()` is true; otherwise they fall back to raw Java `+`/`-`, which silently wraps on overflow instead of throwing: [1](#0-0) 

`allowHarden()` is gated by `DynamicPropertiesStore.allowHardenExchangeCalculation()`, which is controlled by the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal, only valid after fork `VERSION_4_8_2` and defaulting to `0` (disabled) as shown by the test asserting "has been set to 0, no need to propose again": [2](#0-1) 

This same unguarded `addExact` is used by `ExchangeTransactionActuator.doValidate()` for the very check meant to bound pool balances (`tokenBalance must less than balanceLimit`): [3](#0-2) 

If `tokenBalance + tokenQuant` overflows `Long.MAX_VALUE`, the raw `+` wraps to a large negative number. `tokenBalance > balanceLimit` is then `false` (a negative value is never greater than a positive limit), so the intended overflow-prevention check is bypassed.

The actual balance mutation, in `ExchangeCapsule.transaction()`, performs the same unchecked pattern when `hardenedCalc` is `false` (the default), storing the wrapped-around (possibly negative) balance directly with no post-condition check: [4](#0-3) 

Only the hardened path (`hardenedCalc == true`) guards against negative resulting balances: [5](#0-4) 

The same pattern (`addExact` from `AbstractExchangeActuator`, non-strict by default) is also used in `ExchangeInjectActuator`'s balance-limit checks: [6](#0-5) 

By contrast, the order-book "Market" (TRC10-to-TRC10 limit order) subsystem and `MarketComparator` already apply the report's recommended mitigation pattern — attempt exact `long` multiplication/addition, and fall back to `BigInteger` on `ArithmeticException` — showing the codebase is aware of and has fixed this bug class elsewhere: [7](#0-6) [8](#0-7) 

But the older `Exchange` (Bancor AMM) contract type retains the unsafe default behavior, only remediated behind an opt-in governance switch that is off by default.

### Impact Explanation
An unprivileged user (a TRC10 asset issuer) can drive an `Exchange` pool's stored reserve past `Long.MAX_VALUE`, causing it to wrap to a negative value. This:
- Bypasses the `balanceLimit` safety check that is supposed to cap pool size (`ExchangeTransactionActuator.doValidate`, line 203).
- Persists a corrupted (negative) reserve into the on-chain `Exchange`/`ExchangeV2` store via `ExchangeCapsule.transaction()`.
- Feeds the corrupted reserve into subsequent Bancor-formula trades (`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`), which can produce nonsensical or exploitable trade outputs, effectively breaking the AMM's accounting invariants and potentially enabling further extraction of value from the pool's other-side reserve. This is an invalid-state/accounting-corruption impact directly tied to unsafe arithmetic in the exchange's price/balance calculation, the same bug class as the external report.

### Likelihood Explanation
Exploitability depends on the chain's live configuration: it requires `AllowHardenExchangeCalculation` to remain disabled, which is the pre-activation default enforced by `ProposalUtil`/`ProposalService` and only flips on via a witness governance vote after fork `VERSION_4_8_2`: [9](#0-8) 

An attacker only needs to (a) issue a TRC10 asset with a very large `int64` total supply (permissionless), and (b) hold/accumulate enough of that asset to construct a `tokenQuant` that, added to the pool's current balance, overflows `Long.MAX_VALUE`. No privileged role is required; the entire attack is composed of standard `AssetIssueContract`, `ExchangeCreateContract`/`ExchangeInjectContract`, and `ExchangeTransactionContract` calls available to any account.

### Recommendation
Make the overflow-checked (`StrictMathWrapper.addExact`/`subtractExact`) arithmetic in `AbstractExchangeActuator`, `ExchangeCapsule.transaction()`, and the `ExchangeProcessor`/`SafeExchangeProcessor` path unconditional (not gated behind `AllowHardenExchangeCalculation`), or apply the same "try `long` math, fall back to `BigInteger`" pattern already used in `MarketUtils.multiplyAndDivide` and `MarketComparator.comparePrice` to all `Exchange`-actuator balance arithmetic regardless of the hardening flag.

### Proof of Concept
1. Issue a TRC10 asset `X` with an attacker-chosen `totalSupply` close to `Long.MAX_VALUE` (e.g., `9223372036854775800`), and acquire the full supply.
2. Create (or use an existing) `Exchange` pool pairing `X` with TRX/another token, with `firstTokenBalance` near the network's `getExchangeBalanceLimit()`.
3. On a network where `AllowHardenExchangeCalculation == 0` (default), submit an `ExchangeTransactionContract` selling `X` with `tokenQuant` chosen so `firstTokenBalance + tokenQuant` exceeds `Long.MAX_VALUE`.
4. `ExchangeTransactionActuator.doValidate()`'s `tokenBalance = addExact(tokenBalance, tokenQuant)` (raw `+` since hardening is off) wraps to a negative number, so `tokenBalance > balanceLimit` is `false` and validation passes despite exceeding the intended limit.
5. `execute()` calls `exchangeCapsule.transaction(..., allowHarden()=false)`, which stores the wrapped/negative `newFirstTokenBalance` via `ExchangeCapsule.setBalance` with no negative-balance check (guard at line 160 only applies when `hardenedCalc` is true), corrupting the persisted pool state for all future trades against that `Exchange`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
