This is a solid finding — a real, self-documented integrity gap in the transaction-info/output equivalence check used by state-sync chunk verification and replay-verify tooling.### Title
`ensure_match_transaction_info` silently skips the position/hot-state checkpoint-hash fields, letting `db-tool`'s `replay_on_archive` and state-sync chunk-verification accept a replayed transaction whose authenticated state root diverges from local execution - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used to decide whether a locally re-executed transaction "matches" the archived/committed `TransactionInfo` during archive replay-verify (`storage/db-tool/src/replay_on_archive.rs`) and chunk-executor verification (`execution/executor/src/chunk_executor/mod.rs::verify_execution`). It checks status, gas, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` carried in `TransactionInfoV1`. This is the exact "nested/embedded field that can silently diverge from the parent commitment" pattern the seed report describes, translated to Aptos's `TransactionInfo` commitment object.

### Finding Description
`TransactionInfo::V1` (`types/src/transaction/mod.rs:2440-2461`) embeds several checkpoint hash fields, including `position_state_checkpoint_hash`, which is populated only when the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature is enabled (`types/src/on_chain_config/aptos_features.rs:203-209`, `types/src/block_executor/config.rs:180-189`). This hash is meant to bind the native-position Merkle root into the consensus-verified transaction-info leaf that feeds the transaction accumulator.

The comparator that is supposed to detect execution/storage divergence, `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`), verifies only:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

The function ends with a self-documented gap: [1](#0-0) 
which states the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This comparator is the sole correctness gate in two integrity-critical call sites:
- `storage/db-tool/src/replay_on_archive.rs:392-397` (`execute_and_verify`) - used to certify that archived mainnet history replays correctly. [2](#0-1) 
- `execution/executor/src/chunk_executor/mod.rs:692-705` (`verify_execution`) - used during state-sync/chunk verification to check that a locally re-executed chunk matches the transaction infos delivered from a peer/archive. [3](#0-2) 

Because `position_state_checkpoint_hash` (and the state/hot-state checkpoint hashes) are excluded from the comparison, a `TransactionInfo` whose `position_state_checkpoint_hash` does not match the locally computed native-position state root will still pass verification. Concretely: if the native-position JMT root computed by `DoStateCheckpoint`/`ProvablePositionStateSummary` diverges from what is embedded in a delivered/archived `TransactionInfo` (due to a bug in position-state computation, an inconsistent restore, or a corrupted archive), neither the replay-verify tool nor the chunk-executor's verification path will flag it.

### Impact Explanation
This breaks the state-commitment integrity invariant that "committed state that differs from the correct VM result... must be detected" and the "wrong ... proof accepted as valid" gate. Specifically, once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on (it currently requires `TRANSACTION_INFO_V1` and `HOTNESS_IN_EPILOGUE`, per `types/src/block_executor/config.rs:180-189`), a divergence in the native-position state root would:
- Not be caught by `db-tool`'s archive replay-verify, which is Aptos's tool for auditing historical mainnet correctness (`storage/db-tool/src/replay_on_archive.rs`).
- Not be caught by chunk-executor's `verify_execution` used in state-sync verify-execution mode (`execution/executor/src/chunk_executor/mod.rs`).

This means a corrupted/incorrect `position_state_checkpoint_hash` could propagate through restore/replay tooling undetected, defeating the very purpose of the checkpoint hash as a consensus-verified commitment.

### Likelihood Explanation
The gap is currently latent because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is off by default and gated behind multiple feature flags (`is_compute_trading_native_state_roots_enabled() && is_transaction_info_v1_enabled() && is_hotness_in_epilogue_enabled()`, `types/src/block_executor/config.rs:184-187`), so under the current mainnet configuration this cannot yet manifest — mirroring the seed report's "future upgrade" nature: no impact today, but a hard-coded correctness gap that will silently activate the moment the feature is enabled, with no code change needed to trigger it. The gap is also explicitly acknowledged by the maintainers' own TODO comment, confirming it is a known, unresolved local invariant break rather than speculation.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against the locally computed equivalents, and thread the locally computed checkpoint hashes into both `replay_on_archive::execute_and_verify` and `chunk_executor::verify_execution` before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in any environment where replay-verify or chunk-verify-execution is relied upon for integrity assurance.

### Proof of Concept
Not independently reproducible today because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is disabled by default in the current codebase, so `position_state_checkpoint_hash` is always `None` on both sides and the comparison trivially "passes." The vulnerability is a static code-inspection finding: given the call graph `replay_on_archive::execute_and_verify` → `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`), any mismatch in `position_state_checkpoint_hash` between the archived/expected `TransactionInfo` and the locally executed result will not raise an error, as proven by the exhaustive list of checked fields in that function body (lines 2148-2195) and the maintainers' own acknowledgement in the trailing comment (lines 2197-2203).
