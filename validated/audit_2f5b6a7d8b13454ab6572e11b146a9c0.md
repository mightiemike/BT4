### Title
Non-deterministic event decoding between live and replayed streams due to ABI/creator resolution keyed on current AbiStore/ContractStore state rather than historical block state - ([File: framework/src/main/java/org/tron/core/services/event/BlockEventGet.java])

### Finding Description
`LogInfoTriggerParser.parseLogInfos` (live path, invoked from `VMActuator` during block execution) and `BlockEventGet.parseLogs`/`processTrigger` (backfill/replay path) both independently look up ABI and creator address by calling `getAbiStore().get(contractAddress)` and `getContract(contractAddress)` at the *time the method executes*, not at the historical block height of the log being decoded. [1](#0-0) [2](#0-1) 

`ClearABIContractActuator.execute` allows a contract owner to overwrite the `AbiStore` entry for their own contract with `ABI.getDefaultInstance()` at any point after deployment, which is a legitimate, unprivileged (owner-only, not admin/governance) transaction available on the public API. [3](#0-2) 

Since neither `ContractTriggerCapsule.processTrigger` (used by the synchronous/live `RealtimeEventService` path) nor `BlockEventGet.processTrigger` (used for historical block replay/backfill) snapshot the ABI at the block height of the log, decoding the same historical `LogInfo` at two different times (before vs. after a `ClearABIContract` transaction) yields different results: the live decode uses the ABI that existed when the log was originally emitted, producing a full `topicMap`/`dataMap`, while a later replay after `ClearABIContract` resolves an empty ABI and falls back to a `ContractLogTrigger` (raw, undecoded log) instead of a `ContractEventTrigger`. This breaks decode determinism for the identical on-chain log across live vs. replayed streams.

### Impact Explanation
Downstream consumers reconciling live event-plugin output against historical replay/backfill (via `BlockEventGet`) for the same block can observe different trigger types (`ContractEventTrigger` vs `ContractLogTrigger`) or different `creatorAddress`/decoded topic and data maps for the identical `LogInfo`, since `creatorAddr` is also recomputed from the live `ContractStore` at call time. This is a data-integrity/consistency issue for off-chain indexers/auditors relying on `EventPluginLoader` output, not a consensus-breaking or fund-theft issue — the underlying blockchain state and on-chain log bytes are unaffected; only the plugin-emitted trigger representation diverges.

### Likelihood Explanation
Feasible and fully attacker-controlled: any contract owner can deploy a contract, emit an event, then submit a `ClearABIContract` transaction (already exposed via public transaction/API, gated only by contract ownership) before an operator later replays/backfills that historical block through `BlockEventGet`. This requires no special privilege beyond owning the contract that emitted the log, and is trivially repeatable.

### Recommendation
Persist/snapshot the ABI (and any other block-height-dependent metadata like origin/creator address at deployment time) alongside the emitted log or in a versioned/historical ABI store keyed by block height, rather than resolving from the current `AbiStore`/`ContractStore` singleton state at decode time. Both `LogInfoTriggerParser.parseLogInfos` and `BlockEventGet.parseLogs` should read from this same historical source so that decoding is a pure function of the historical `LogInfo` plus its associated snapshot, guaranteeing identical output at any replay time.

    long fee = calcFee();
    AbiStore abiStore = chainBaseManager.getAbiStore();

      ClearABIContract usContract = any.unpack(ClearABIContract.class);

      byte[] contractAddress = usContract.getContractAddress().toByteArray();
      abiStore.put(contractAddress, new AbiCapsule(ABI.getDefaultInstance()));

      ret.setStatus(fee, code.SUCESS);

      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
  }
