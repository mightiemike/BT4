### Title
Waterfall PoX-commit check compares `PoxAddress` values with raw struct equality instead of canonical `to_burnchain_repr()`, letting a legitimately-paying block-commit be rejected as "bad outputs" - (File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs)

### Summary
`LeaderBlockCommitOp::check_pox_waterfall` validates a miner's block-commit output against the expected sBTC reward recipient using direct Rust `PartialEq` on `PoxAddress` [1](#0-0) , whereas the classic (pre-waterfall) path deliberately avoids raw equality and instead normalizes both sides through `to_burnchain_repr()` before comparing [2](#0-1) . `PoxAddress::Standard` carries an `Option<AddressHashMode>` that the type's own documentation says cannot always be determined ("the address hash mode is optional because if we decode a legacy bitcoin address, we won't be able to determine the hash mode since we can't distinguish segwit-p2sh from p2sh") [3](#0-2) . Because the derived `PartialEq`/`Eq` for `PoxAddress` compares this field too, two `PoxAddress` values that are the *same burnchain output* (same version/hashbytes) but were constructed along different decode paths with a differing `Option<AddressHashMode>` will fail `==` even though `to_burnchain_repr()` would show they are identical.

### Finding Description
This mirrors the reported bug class: an equality check meant to recognize "the same underlying asset/address" instead performs a strict structural comparison that can diverge for two representations of the same value (there: `ETH_ADDRESS` vs `WETH`; here: `PoxAddress::Standard(addr, Some(mode))` vs `PoxAddress::Standard(addr, None)` for the identical `addr`).

- `check_pox_waterfall` is reached once the waterfall/sBTC PoX regime is active for a block-commit's height [4](#0-3) .
- It requires `self.commit_outs.len() == 1` and then checks `self.commit_outs.get(0) != Some(&wf_info.sbtc_address)`, rejecting with `BlockCommitBadOutputs` on any mismatch [1](#0-0) .
- `wf_info.sbtc_address` is the expected recipient sourced from the on-chain reward set / pox-contract path via `RewardSetInfo::Waterfall` [5](#0-4) , while `self.commit_outs` is decoded from the raw burnchain (Bitcoin) transaction outputs of the miner's actual commit. These two `PoxAddress` values are produced by two different decode/construction code paths (contract-derived tuple vs. raw Bitcoin scriptPubKey decode), which is exactly the scenario the type's own doc-comment warns about: the `AddressHashMode` annotation may be unrecoverable/ambiguous from a legacy Bitcoin address, so it is `Option`-typed and can legitimately end up `None` on one side and `Some(_)` on the other for what is the same address.
- The classic PoX-commit path was already patched around this exact hazard: instead of a raw `==`, it explicitly calls `.to_burnchain_repr()` on both sides before comparing, with a comment describing the check as deliberately preceding costlier logic specifically because commit outputs must be validated correctly [6](#0-5) . The waterfall path was not given the same treatment, so it retains the raw-equality hazard.

### Impact Explanation
`check()` calls `check_pox`, which dispatches to `check_pox_waterfall` for waterfall-era commits, and a `BlockCommitBadOutputs` error causes the entire block-commit to be treated as invalid for that miner's sortition attempt [7](#0-6) . Every full node runs the identical, deterministic check, so a miner whose commit legitimately pays the correct sBTC address — but whose on-chain output happens to decode into a `PoxAddress::Standard` with a different `Option<AddressHashMode>` annotation than the contract-derived `wf_info.sbtc_address` — will have that commit uniformly rejected network-wide as "bad outputs," even though it is semantically a correct, fully-paid commit. This is a network-wide wrongful rejection of an otherwise-valid block-commit (and hence of that miner's otherwise-legitimate sortition attempt), matching the "valid block rejected network-wide" bucket, and it is triggerable by any single, unprivileged miner whose commit's Bitcoin-address encoding differs in hash-mode ambiguity from the reward-set's derived value — no majority or admin/privileged role is required.

### Likelihood Explanation
Likelihood is bounded by how often a real block-commit output's `PoxAddress` decode ends up with a different `Option<AddressHashMode>` than the contract-derived `sbtc_address` for the same underlying bytes; the code's own comment establishes that this ambiguity is a real, not merely theoretical, property of Bitcoin address decoding (segwit-p2sh vs. p2sh cannot always be distinguished), and the classic-path code was already changed to defend against it via canonicalized comparison, implying the ambiguity was previously observed as an issue for `PoxAddress` equality checks.

### Recommendation
In `check_pox_waterfall`, replace the direct `PoxAddress` equality check with a canonicalized comparison, mirroring the pre-waterfall path:
```rust
let commit_repr = self.commit_outs.get(0).map(|a| a.to_burnchain_repr());
if commit_repr != Some(wf_info.sbtc_address.to_burnchain_repr()) {
    warn!("Invalid waterfall block commit: unexpected output"; "expected" => %wf_info.sbtc_address, "found" => ?self.commit_outs.get(0));
    return Err(op_error::BlockCommitBadOutputs);
}
```
This makes the waterfall check consistent with the classic-path treatment and eliminates the spurious rejection stemming from the `Option<AddressHashMode>` ambiguity.

### Proof of Concept
1. A miner's block-commit pays exactly to the sBTC reward address expected for the cycle (same version + hashbytes as `wf_info.sbtc_address`), but the raw Bitcoin output's scriptPubKey is of a type for which the hash mode cannot be unambiguously recovered during decode (per the `PoxAddress` doc-comment), so it decodes as `PoxAddress::Standard(addr, None)`.
2. The contract-tracked `wf_info.sbtc_address` for that reward cycle was recorded/derived with `Some(AddressHashMode::...)` for the same `addr`.
3. `check_pox_waterfall` computes `self.commit_outs.get(0) != Some(&wf_info.sbtc_address)`; since derived `PartialEq` on `PoxAddress::Standard` compares the `Option<AddressHashMode>` field too, `Standard(addr, None) != Standard(addr, Some(mode))` even though both represent the same on-chain output [3](#0-2) .
4. The commit is rejected with `op_error::BlockCommitBadOutputs` [8](#0-7) , uniformly on every node, even though the miner correctly paid the reward recipient — reproducing, in the Stacks burnchain-consensus layer, the same "equality check misses a valid alternate representation of the same value" defect described in the ETH/WETH report.
