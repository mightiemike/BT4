### Title
DoS of unauthenticated OAuth/redirect handlers via uncaught `atob()` exception in `decodeHost` — ([File: packages/apps/shopify-api/lib/auth/decode-host.ts])

### Summary
`sanitizeHost` performs a superficial format check on the base64 `host` query parameter but decodes it with `atob()` without validating that the decoded value is actually well-formed base64 or produces a URL-safe string, and without catching decode failures. This mirrors the Bunni bug class: an input passes an initial "shape" check but a value re-derived from it (`decodeHost`/`new URL`) is not re-validated against the constraints the initial check was supposed to guarantee, causing an unhandled revert/exception at the point of use.

### Finding Description
`sanitizeHost` first tests the raw `host` string against a loose base64 alphabet regex, then immediately decodes it and constructs a `URL`: [1](#0-0) 

The regex `^[0-9a-zA-Z+/]+={0,2}$` only checks the character set/padding characters used, not that the string length is a multiple of 4 or that padding is correctly placed — both of which are required for valid base64. `decodeHost` simply calls `atob(host)`: [2](#0-1) 

In Node.js/browsers, `atob()` throws `DOMException [InvalidCharacterError]` when given a string whose length is not a multiple of 4 or with misplaced padding (e.g. `"AAAAA"`, `"A"`, `"AB"`), even though such strings pass the regex used in `sanitizeShop`/`sanitizeHost`. This throw is not wrapped in a `try/catch` anywhere in `sanitizeHost`, so it propagates as an unhandled exception out of `sanitizeHost` itself — a function whose entire contract (per its docs) is "returns `host` if valid, otherwise `null`, unless `throwOnInvalid` is set" — i.e., it is documented to never throw an *unexpected* error type, only `InvalidHostError`.

This function is called directly, without try/catch, from multiple unauthenticated entry points in the OAuth/embedded-app flow that read `host` straight from the request query string:
- `redirectToAuth`/`clientSideRedirect` (Express) reads `req.query.host` and calls `api.utils.sanitizeHost(...)`: [3](#0-2) 
- `redirectToShopifyOrAppRoot` (Express) calls `api.utils.sanitizeHost(req.query.host as string)!`: [4](#0-3) 
- `validateShopAndHostParams` (Remix/React Router) calls `api.utils.sanitizeHost(url.searchParams.get('host')!)`: [5](#0-4) 
- `redirectWithExitIframe` and `buildEmbeddedAppUrl`/`getEmbeddedAppUrl` also call `sanitizeHost`/`decodeHost` directly on attacker-controlled query data: [6](#0-5) [7](#0-6) 

None of these call sites catch generic exceptions from `sanitizeHost`/`decodeHost` — they only handle the documented `InvalidHostError`/falsy-return case (`if (!host) { ... }`). Since `sanitizeHost` is invoked in the App Bridge / login / OAuth-begin code path that is reached before any session or authentication check, any anonymous request to these routes with a malformed-but-regex-passing `host` value will throw an uncaught error instead of returning `null`/`false` as the API contract implies.

### Impact Explanation
This is a Denial-of-Service of the pre-authentication OAuth/App-Bridge redirect handlers reachable by any anonymous HTTP request (no session or shop installation required). Depending on the framework's error handling for uncaught synchronous/async errors in these specific code paths, the request fails with an unhandled error rather than the intended graceful `400/401` style response, and in frameworks without a global error boundary around these specific helper calls, this can manifest as an unhandled promise rejection rather than a clean HTTP error response. The blast radius is per-request (not a persistent stuck state as in the Bunni pool case), so severity is lower than the original report, but it still breaks the intended "always return null/throw a well-typed error" contract of a security-input-sanitization utility that gates the OAuth entry point.

### Likelihood Explanation
Trivial to trigger: any base64-alphabet string whose length is not a multiple of 4 (e.g., `host=AAAAA`) satisfies the `base64regex` check in `sanitizeHost` but fails `atob()`. No authentication, secret knowledge, or special conditions are required — only an anonymous GET request with a crafted `host` query parameter to any of the listed entry points.

### Recommendation
- Wrap the `atob(sanitizedHost)` / `new URL(...)` call in `sanitizeHost` in a `try/catch`, treating decode failures the same as "invalid host" (return `null` or throw `InvalidHostError` per `throwOnInvalid`), consistent with the documented contract.
- Apply the same defensive handling to `decodeHost` callers (`get-embedded-app-url.ts`, `redirect-with-exitiframe.ts`) that decode `host` a second time after `sanitizeHost` has already run, since they currently assume the value is always well-formed once it has passed `sanitizeHost`.

### Proof of Concept
```
GET /redirect-to-auth?shop=my-shop.myshopify.io&embedded=1&host=AAAAA HTTP/1.1
Host: app.example.com
```
`"AAAAA"` matches `/^[0-9a-zA-Z+/]+={0,2}$/` (passes `sanitizeHost`'s initial regex check) but has length 5 (not a multiple of 4), so `atob('AAAAA')` throws `DOMException: The string to be decoded is not correctly encoded.` inside `sanitizeHost`, which is not caught by `clientSideRedirect`/`redirectToAuth`, resulting in an unhandled exception instead of the expected `500 "No host provided"` graceful response path shown in the existing test suite: [8](#0-7)
