### Title
Unrecoverable loss of bridged funds when a `TxType_GAS` outbound fails on the destination chain - (File: `x/uexecutor/keeper/outbound.go`)

### Summary
`handleFailedOutbound` only re-mints (refunds) the bridged PRC20 amount back to the user when `outbound.TxType` is `FUNDS`, `GAS_AND_PAYLOAD`, or `FUNDS_AND_PAYLOAD`. A pure `TxType_GAS` outbound (an unused-gas refund back to a source chain) is excluded from that re-mint branch, exactly like the Sherlock report's split if-condition that skipped incrementing `liquidationBonus` for funds that had already left the vault-equivalent accounting.

### Finding Description
`FinalizeOutbound` routes to `handleFailedOutbound` when Universal Validators vote `success=false` for an outbound [1](#0-0) . Inside `handleFailedOutbound`, the re-mint of `outbound.Amount` back into the Push-Chain PRC20 supply is gated by a `TxType` check that lists only `FUNDS`, `GAS_AND_PAYLOAD`, and `FUNDS_AND_PAYLOAD` [2](#0-1) . If the `TxType` is `GAS` (per the table in the module README, "Refund of unused gas back to a source chain" [3](#0-2) ), the function skips straight to marking the outbound `REVERTED` and only runs `applyGasRefund`, which computes the *relayer gas* excess (`gasFee - gasFeeUsed`) — a completely separate, smaller value — not the underlying `outbound.Amount` that was already deducted/burned on Push Chain to fund this GAS outbound [4](#0-3) .

This mirrors the Sherlock M-8 pattern precisely: two conditions that look related (`collateralBalance > 0` vs. the fee threshold check) were folded into a single branch such that the "return funds to the user" step could be silently skipped while a different, unrelated bookkeeping step still executed. Here, the `TxType` switch that decides "should we re-mint the underlying amount" is disjoint from — and narrower than — the full set of value-carrying outbound types, and the fallback path (`applyGasRefund`) only ever touches gas fee excess, never the principal amount.

### Impact Explanation
If an outbound of `TxType_GAS` fails on the destination chain (broadcast failure, revert, or "not found after retries" per the universalClient outbound flow docs [5](#0-4) ), the user's `outbound.Amount` (the PC-side value that funded this gas top-up) is never re-minted back to them. The outbound is simply marked `REVERTED` with no corresponding fund recovery for the principal, and there is no other automatic path shown in `handleFailedOutbound`/`applyGasRefund` that restores it. This is a permanent loss/freezing of user-controlled funds triggered purely by an honest-validator-observed destination-chain failure — no privileged or malicious actor required.

### Likelihood Explanation
Any transient destination-chain condition that causes a legitimate `GAS`-type outbound to fail (congestion, insufficient gas limit set by `buildRevertOutbound`/`GetGasFeeInfoForRevertOutbound`, RPC issues causing "not found after retries") will trigger this path under entirely honest validator/relayer behavior, since `FinalizeOutbound` is reached whenever UVs vote `success=false`. This does not require an attacker at all — it is a systemic gap for one whole `TxType` class.

### Recommendation
Include `TxType_GAS` in the re-mint branch of `handleFailedOutbound` (or add a dedicated re-mint/refund path specific to gas-type outbounds) so that the underlying PRC20/native amount, not just the excess relayer gas fee, is credited back to the user whenever a `GAS` outbound fails, mirroring the treatment already given to `FUNDS`, `GAS_AND_PAYLOAD`, and `FUNDS_AND_PAYLOAD`.

### Proof of Concept
Not independently executed against the running chain — inferred from code review of `handleFailedOutbound`/`applyGasRefund` in `x/uexecutor/keeper/outbound.go`. I was unable to fully confirm within available context whether the EVM/gateway contract logic that emits `TxType_GAS` outbound events performs an unconditional burn of `outbound.Amount` prior to this keeper-side finalize step (the Solidity gateway/UniversalCore contracts were out of the indexed scope I could inspect), so the exact accounting flow that removes the tokens from circulation before `FinalizeOutbound` runs should be verified by a Devin session with full repository/contract access before treating this as fully confirmed.

```go
func (k Keeper) FinalizeOutbound(ctx context.Context, utxId string, outbound types.OutboundTx) error {
	// If not observed yet, do nothing
	if outbound.OutboundStatus != types.Status_OBSERVED {
		return nil
	}

	obs := outbound.ObservedTx
	if obs == nil {
		return nil
	}

	sdkCtx := sdk.UnwrapSDKContext(ctx)

	k.Logger().Info("finalizing outbound",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"success", obs.Success,
		"dest_chain", outbound.DestinationChain,
		"tx_type", outbound.TxType.String(),
	)

	if !obs.Success {
		return k.handleFailedOutbound(sdkCtx, utxId, outbound, obs)
	}

	return k.handleSuccessfulOutbound(sdkCtx, utxId, outbound, obs)
}
```

```go
func (k Keeper) handleSuccessfulOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	k.Logger().Info("outbound completed successfully",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"dest_chain", outbound.DestinationChain,
	)
	k.applyGasRefund(ctx, &outbound, obs)
```

```markdown
### `TxType` — what flavour of crosschain action

The same enum is used on both `Inbound` and `OutboundTx` to describe what the message is for.

| `TxType` | Inbound semantics | Outbound semantics |
|---|---|---|
| `GAS` | User pre-paid gas on the source chain. Mints PC to the recipient as a gas top-up. | Refund of unused gas back to a source chain. |
| `GAS_AND_PAYLOAD` | Gas top-up + executes a payload through the recipient's UEA in the same Push Chain tx. | Same combo on the destination side. |
| `FUNDS` | Pure synthetic transfer — mints PRC20 representation of an external token. | Pure transfer of a PRC20 back out of Push Chain. |
| `FUNDS_AND_PAYLOAD` | Mints funds + runs a payload (e.g. deposit + DEX swap atomically). | Funds delivery with a destination-side call. |
| `PAYLOAD` | Pure payload execution, no value movement. | Pure call on the destination chain. |
| `INBOUND_REVERT` | Reverts a previously-executed inbound (returns funds to the source-chain sender). | — |
| `RESCUE_FUNDS` | Admin-driven rescue path for stuck funds. | Outbound that delivers the rescue. |
```

```markdown
1. The Push Chain listener picks up the pending outbound
2. A rotating coordinator assigns a nonce, selects a threshold subset of participants, and creates a DKLS signing session

4. Every participating validator broadcasts the identical signed transaction; the first to land wins, the rest are idempotent (same nonce, same signature, same tx hash)
```
