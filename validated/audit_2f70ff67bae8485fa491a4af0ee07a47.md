### Title
Vault gateway request-ID collision allows griefing of another user's in-flight JSON-RPC request - (File: core/services/gateway/handlers/vault/handler.go)

### Summary
The Chainlink Gateway's Vault handler (`core/services/gateway/handlers/vault/handler.go`) tracks in-flight vault requests (e.g. `CreateSecret`, `GetSecret`, `UpdateSecret`, `DeleteSecret`) in a single, gateway-wide `activeRequests` map keyed only by the JSON-RPC `req.ID` string, which is chosen by the calling client and is not scoped to a caller/owner. Any unprivileged user of the gateway can submit a request using the same `req.ID` as another user's in-flight request and cause that user's genuine request to be rejected, exactly the "user-chosen identifier squatting" griefing class described in the external report (where a user-supplied `accountId` could be front-run by another party to block the legitimate owner).

### Finding Description
`activeRequest` objects are created and inserted via `newActiveRequest`: [1](#0-0) 

The function performs a simple existence check on the *global* `h.activeRequests` map keyed purely by `req.ID` (a client-supplied JSON-RPC identifier), and rejects the request entirely if any request — from any caller — already used that ID:
```go
if h.activeRequests[req.ID] != nil {
    h.lggr.Errorw("request id already exists", "requestID", req.ID)
    return nil, errors.New("request ID already exists: " + req.ID)
}
```
There is no association between `req.ID` and the authenticated caller/owner, and no per-owner namespacing of the ID space. `HandleJSONRPCUserMessage` — the entry point for user (workflow-owner) submitted vault JSON-RPC calls — invokes this path with the caller-supplied request directly: [2](#0-1) 

Because the JSON-RPC `id` field is fully attacker-controlled and the collision check operates on a shared namespace, this mirrors the reported bug class exactly: a value that should identify *one user's* operation is globally unique and first-write-wins, so an unprivileged attacker who can predict or observe another user's intended request ID (e.g., deterministic IDs, or IDs seen via any shared/observable channel prior to submission) can pre-register that ID first. The victim's subsequent legitimate request is then rejected with `"request ID already exists"`, denying them use of the vault capability for that operation until they choose a different, unclaimed ID.

### Impact Explanation
This is a griefing/DoS vector against the Vault capability's request-handling path in the Gateway: a malicious, unprivileged actor can cause a specific vault operation from a targeted user to fail deterministically, without any profit motive, by squatting the shared request-ID namespace. This does not compromise secret confidentiality or the DON's aggregation/quorum logic, but it can disrupt availability of the create/read/update/delete-secret RPC flow for specific victims, analogous in class and root cause to the reported account-creation griefing (global, unscoped, user-chosen identifier used as a first-come-first-served uniqueness key).

### Likelihood Explanation
Exploitability depends on the attacker's ability to learn or predict a target's `req.ID` before it is submitted to the gateway (e.g., IDs generated deterministically by client SDKs, or observable in transit/logs before reaching the gateway). Given `req.ID` is not cryptographically secret and JSON-RPC IDs are often simple counters/UUIDs generated by client tooling, collision or prediction is plausible in some client implementations, making this a realistic though environment-dependent griefing vector.

### Recommendation
Scope `activeRequests` (and the corresponding uniqueness/collision check in `newActiveRequest`) by authenticated caller/owner identity in addition to `req.ID`, e.g., key the map by `(ownerID, req.ID)` rather than `req.ID` alone. This prevents one user from being able to collide with, and thereby block, another user's request purely by choosing the same client-supplied identifier.

### Proof of Concept
Conceptual PoC (no live test harness available in this analysis):
1. Attacker observes or predicts the JSON-RPC `id` value a victim's client will use for an upcoming `CreateSecret`/`GetSecret` call to the Gateway's Vault handler.
2. Attacker submits their own JSON-RPC request to the same Gateway Vault handler using that identical `id` value, ahead of the victim.
3. `newActiveRequest` inserts the attacker's entry into `h.activeRequests[id]`.
4. When the victim's legitimate request with the same `id` arrives, `newActiveRequest` finds `h.activeRequests[id] != nil` and returns `"request ID already exists: <id>"`, causing the victim's operation to fail via `HandleJSONRPCUserMessage`. [3](#0-2)

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
