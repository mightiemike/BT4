### Title
Truncating `u16` cast in in-memory trie extension-node header causes undersized allocation / length-mismatch on long trie keys - (File: `core/store/src/trie/mem/flexible_data/extension.rs`)

### Summary
`EncodedExtensionHeader::from_input` truncates the extension (shared-nibble-path) byte length to `u16` when computing the size used to allocate the MemTrie arena slot for a trie `Leaf`/`Extension` node, then unconditionally copies the *original, untruncated* extension bytes into that undersized slot via `copy_from_slice`. This mirrors the GRUB `jfs` bug class: an attacker-influenced length is used to size an allocation, and a subsequent write uses the real (larger) length instead of the (possibly overflowed/truncated) size that was used for allocation.

### Finding Description
- `EncodedExtensionHeader` stores the flexible extension length as `u16` (`extension.rs:9-11`), and `from_input` sets it via `extension.len() as u16` with no check that `extension.len() <= u16::MAX` (`extension.rs:20-22`).
- `MemTrieNodeId::new_impl` uses `extension_header.flexible_data_length()` (i.e. the truncated `u16` value) to size the arena allocation for `Leaf`/`Extension` nodes: `RawEncoder::new(arena, LeafHeader::SERIALIZED_SIZE + extension_header.flexible_data_length() + value_header.flexible_data_length())` (`node/encoding.rs:153-158`, `170-173`).
- It then calls `data.encode_flexible(&extension_header, extension)` passing the **original, full-length** `extension` slice (`node/encoding.rs:164`, `181`), which in turn calls `header.encode_flexible_data(data, &mut self.data.subslice_mut(self.pos, length))` where `length` is the truncated `flexible_data_length()` (`encoding.rs:53-57`).
- `EncodedExtensionHeader::encode_flexible_data` performs `target.raw_slice_mut().copy_from_slice(&extension)` (`extension.rs:28-34`) — `target` is sized to the truncated `u16` length, but `extension` retains its true (possibly >65535-byte) length.

If the extension bytes exceed `u16::MAX` (65535), the allocated arena buffer is undersized relative to the data actually being written. `Vec`/slice `copy_from_slice` requires matching lengths, so in the common Rust case this manifests as a hard panic (length mismatch) rather than silent heap corruption — but it is nonetheless an integer-truncation bug at the exact point (buffer-size derivation from an unchecked, attacker-influenced length before a raw memory write) that the CVE-2025-0685 report describes, and any future refactor of `encode_flexible_data`/`RawEncoder` that uses `raw_slice_mut()[..]` indexing instead of `copy_from_slice` (or that reuses `flexible_data_length()` to bound the write) would turn this into an actual out-of-bounds heap write inside the custom arena allocator (`core/store/src/trie/mem/arena/alloc.rs`), which manages raw byte buffers manually with no bounds checking beyond what call sites provide.

### Impact Explanation
- The MemTrie extension path length is bounded by the trie key length for a `Leaf`, and by the shared-prefix length for internal `Extension` nodes, which is itself bounded by the account's storage key. Runtime limit config's `max_length_storage_key` in this tree is `4_194_304` (4 MiB) by default in `parameters_testnet.yaml` (`core/parameters/res/runtime_configs/parameters_testnet.yaml:308`), i.e. far in excess of `u16::MAX` (65535). A single unprivileged transaction signer calling `storage_write` (`runtime/near-vm-runner/src/wasmtime_runner/logic.rs:4857-4938`) with a key near this limit is sufficient to construct a trie leaf whose extension nibble-path exceeds 65535 bytes, hitting the truncating cast on any node that maintains MemTries (all validators once `MemTrie`/`FlatStorage` config is enabled, which is unconditional in current protocol versions per the congestion-control spec notes).
- With today's implementation this triggers an `unwrap`/length-mismatch panic in the trie-construction path used on every validator applying the chunk, which is a chunk-application crash reachable from a single crafted transaction — a transaction-triggered halt, consistent with the accepted impact class in this scan's rules.
- Because mainnet-focused config snapshots in this tree cap `max_length_storage_key` at `2048` (well under 65535) in several protocol-version snapshots (e.g. `core/parameters/src/snapshots/...testnet_129.json.snap:253`), current mainnet-effective limits may not be reachable; exploitability therefore depends on the exact live `max_length_storage_key` value for the deployed network/protocol version, which could not be fully confirmed for the "production" mainnet config from the indexed files.

### Likelihood Explanation
Medium: the code path is reachable by any transaction signer via a normal `storage_write` host call with a large key, no special privileges required. Likelihood is gated entirely on whether the currently active `RuntimeConfig.wasm_config.limit_config.max_length_storage_key` for the target network/protocol version exceeds `65535` bytes — this varies across the snapshots examined (`4_194_304` in `parameters_testnet.yaml` vs. `2048` in several protocol-version JSON snapshots), so likelihood is network/version-dependent and not confirmed uniformly exploitable on current mainnet.

### Recommendation
- Add an explicit bounds check in `EncodedExtensionHeader::from_input` (and any other `FlexibleDataHeader` impls using narrow integer headers, e.g. `EncodedChildrenHeader`/`EncodedValueHeader`) that rejects or errors on `extension.len() > u16::MAX` rather than silently truncating via `as u16`.
- Alternatively, widen the header field to `u32` (consistent with `max_length_storage_key`'s value range) or assert `extension.len() <= u16::MAX` at construction time with a descriptive panic/error before allocation, so the size used for allocation and the size used for the write are always provably identical.
- Add a defensive assertion in `RawEncoder::encode_flexible`/`FlexibleDataHeader::encode_flexible_data` implementations that `data.len() == target-buffer length` before calling `copy_from_slice`, and add a fuzz/unit test constructing trie leaves/extensions with keys near and above `65535` bytes to catch regressions.

### Proof of Concept
1. Deploy or use any contract exposing a generic `storage_write(key, value)` host call passthrough.
2. Submit a `FunctionCall` transaction from an ordinary account that invokes `storage_write` with a `key` whose byte length is greater than `65535` and less than or equal to the network's configured `max_length_storage_key` (verified to be `4_194_304` in `parameters_testnet.yaml`).
3. When the shard's `MemTries` are updated for this chunk, `MemTrieNodeId::new_impl` constructs a `Leaf`/`Extension` node whose extension byte length exceeds `u16::MAX`; `EncodedExtensionHeader::from_input` truncates it, producing an arena allocation of the truncated length, while `encode_flexible_data` attempts to write the full extension length into it via `copy_from_slice`, causing a slice-length-mismatch panic on every node applying that chunk.
4. Because all honest validators independently apply the same chunk against MemTrie, this crashes the network's block/chunk-application pipeline uniformly — a transaction-triggered halt condition.
