### Title
Validator panic via unbounded slot cache-flush AppendVec size in `do_flush_slot_cache` - ([File: accounts-db/src/accounts_db.rs])

### Finding Description
`AccountsDb::do_flush_slot_cache` ( [1](#0-0) ) sums `AppendVec::calculate_stored_size(account.data().len())` for every account selected to be flushed for a slot into `flush_stats.num_bytes_stored`, with **no upper bound check**. This total is then passed straight to `self.create_store(slot, flush_stats.num_bytes_stored.0)` ( [2](#0-1) ), which calls `AppendVec::new`:

```rust
pub fn new(file: impl Into<PathBuf>, size: usize) -> Self {
    ...
    AppendVec::sanitize_len_and_size(initial_len, size).unwrap();
``` [3](#0-2) 

`sanitize_len_and_size` returns `Err(AppendVecError::FileSizeTooLarge(file_size))` whenever `file_size > MAXIMUM_APPEND_VEC_FILE_SIZE` (16 GiB) ( [4](#0-3) ), and the `.unwrap()` turns that `Err` directly into a panic.

All accounts that are re-stored in a given slot's cache — and thus flushed together into the single `AppendVec` created by `do_flush_slot_cache` — are accounts marked "touched" during transaction execution, not merely write-locked. `update_accounts_for_successful_tx`/`collect_accounts_to_store` explicitly "skip write-locked accounts the transaction left unmodified" ( [5](#0-4) [6](#0-5) ), but a plain lamport transfer to a pre-existing large account still marks it touched and forces its **entire current data length** to be written back to the write cache and later summed in `flush_stats.num_bytes_stored`, even though the account's size never changed in that slot.

The other on-chain size gates do not bound this:
- `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100,000,000 bytes) and the `CostTracker`'s `allocated_data_size` check ( [7](#0-6) [8](#0-7) ) only limits the *increase* in account sizes (`accounts_resize_delta`) within a block; it does not limit the sum of already-existing account sizes touched in that block.
- Per-account cost limits (`MAX_WRITABLE_ACCOUNT_UNITS`) and block CU limits (`MAX_BLOCK_UNITS`, 60M–100M CU) bound the number of write-locking transactions per slot, but a cheap lamport transfer costs only a few thousand CU, so tens of thousands of distinct large accounts can still be touched within a single slot's CU budget.

Consequently, an attacker who (1) creates/funds many accounts each sized near `MAX_ACCOUNT_DATA_LEN` (10 MiB, enforced in `programs/system/src/system_processor.rs` and `transaction-context/src/lib.rs`) over enough prior slots (bounded by the 100 MB/slot growth cap, so no single-slot violation is needed to build the accounts), and then (2) within one subsequent (not-yet-rooted) slot sends a large number of cheap lamport-transfer transactions each touching one of those distinct large accounts, can make the sum of stored sizes for that slot exceed `MAXIMUM_APPEND_VEC_FILE_SIZE` (16 GiB — e.g. ~1,650 accounts of 10 MiB each). When that slot is later flushed via `force_flush_accounts_cache` → `flush_rooted_accounts_cache` → `do_flush_slot_cache` → `create_store` → `AppendVec::new`, the `.unwrap()` on `sanitize_len_and_size` panics, aborting the process. `SnapshotPackagerService`/`AccountsBackgroundService` block on this same flush path before producing snapshot packages, so this crash halts snapshotting and, since every replaying node executes the identical flush, halts every node that replays this slot.

### Impact Explanation
This is a validator/node panic reachable purely through normal, unprivileged transaction submission (funding accounts and sending transfers), matching the "Scope: High — node crash / halt via panic in AccountsDB" bounty category. Because every honest node must flush the same slot the same way, the crash is not limited to a single validator — it can halt all nodes that replay or root the offending slot, which is a cluster-wide liveness failure rather than a localized crash.

### Likelihood Explanation
The attack requires no special privileges — only enough capital to pre-fund a large number of near-max-size accounts (rent-exemption cost scales with total bytes, roughly tens of thousands of SOL for ~16 GiB of account data) and the ability to get a large batch of cheap transfer transactions processed within a single slot (well within existing CU/entry-byte budgets, since each transfer is a few hundred CU). Building the accounts is spread over many slots (bounded by the 100 MB/slot `accounts_resize_delta` cap, not a single-slot bottleneck), and the final trigger step (touching all of them in one slot) is a normal high-throughput batch of transfers. The economic cost is high but not prohibitive for a well-resourced adversary, and the underlying code contains no defensive bound, making this a reproducible design gap rather than a probabilistic race.

### Recommendation
- In `do_flush_slot_cache` (accounts-db/src/accounts_db.rs), check the accumulated `flush_stats.num_bytes_stored` against `MAXIMUM_APPEND_VEC_FILE_SIZE` before calling `create_store`, and handle the overflow case gracefully (e.g., split the slot's accounts across multiple `AppendVec` stores, or fail cleanly instead of panicking).
- Change `AppendVec::new` (and `create_store`) to return a `Result` instead of `.unwrap()`-ing `sanitize_len_and_size`, propagating the error up so callers can decide how to recover instead of aborting the process.
- Consider adding a per-slot bound on the total bytes that can be "touched" (not just newly allocated) and included in a single cache flush, independent of the existing `accounts_resize_delta` growth cap.

fn test_do_flush_slot_cache_total_size_exceeds_appendvec_cap() {
    use crate::append_vec::MAXIMUM_APPEND_VEC_FILE_SIZE;

    let db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    let slot: Slot = 1;
    let ancestors = Ancestors::from(vec![slot]);

    // Simulate many distinct pre-existing "large" accounts all touched (e.g. lamport bump)
    // within the same slot, sized so the sum exceeds MAXIMUM_APPEND_VEC_FILE_SIZE.
    const ACCOUNT_DATA_LEN: usize = 10 * 1024 * 1024; // near MAX_ACCOUNT_DATA_LEN
    let num_accounts = (MAXIMUM_APPEND_VEC_FILE_SIZE as usize / ACCOUNT_DATA_LEN) + 100;

    let accounts: Vec<(Pubkey, AccountSharedData)> = (0..num_accounts)
        .map(|_| {
            let pubkey = Pubkey::new_unique();
            let account = AccountSharedData::new(1, ACCOUNT_DATA_LEN, &Pubkey::default());
            (pubkey, account)
        })
        .collect();
    let refs: Vec<(&Pubkey, &AccountSharedData)> =
        accounts.iter().map(|(k, v)| (k, v)).collect();

    db.store_accounts_unfrozen(
        (slot, refs.as_slice()),
        UpdateIndexThreadSelection::Inline,
        &ancestors,
    );

    // This should not panic; today it panics via AppendVec::new's
    // `sanitize_len_and_size(...).unwrap()` because the summed size
    // exceeds MAXIMUM_APPEND_VEC_FILE_SIZE.
    db.add_root_and_flush_write_cache(slot);
}

    fn do_flush_slot_cache(
        &self,
        slot: Slot,
        slot_cache: &SlotCache,
        pubkeys_to_store: &PubkeysToStore,
    ) -> FlushStats {
        debug_assert!(self.accounts_cache.contains_unflushed_root(slot));
        let mut flush_stats = FlushStats::default();
        let mut skipped_zero_lamport_pubkeys = Vec::new();
        let iter_items: Vec<_> = slot_cache.iter().collect();

        let accounts: Vec<(&Pubkey, &AccountSharedData)> = iter_items
            .iter()
            .filter_map(|iter_item| {
                let key = iter_item.key();
                let account = &iter_item.value().account;
                let mut should_store = match pubkeys_to_store {
                    PubkeysToStore::All => true,
                    PubkeysToStore::Only(store_keys) => store_keys.contains(key),
                };
                // `true` keeps a disk-loaded entry in-mem for the index upsert below
                if should_store
                    && account.is_zero_lamport()
                    && !self
                        .accounts_index
                        .get_and_then(key, |entry| (true, entry.is_some()))
                {
                    // A zero-lamport account with no index entry has no older rooted version
                    // in storage to shadow, so it can just be skipped
                    flush_stats.num_zero_lamport_accounts_skipped += 1;
                    if !self.account_indexes.is_empty() {
                        skipped_zero_lamport_pubkeys.push(*key);
                    }
                    should_store = false;
                }
                if should_store {
                    flush_stats.num_bytes_stored +=
                        AppendVec::calculate_stored_size(account.data().len()) as u64;
                    flush_stats.num_accounts_stored += 1;
                    Some((key, account))
                } else {
                    // Skip writing this account. Either superseded or zero lamport
                    flush_stats.num_bytes_skipped +=
                        AppendVec::calculate_stored_size(account.data().len()) as u64;
                    flush_stats.num_accounts_skipped += 1;
                    None
                }
            })
            .collect();

    fn sanitize_len_and_size(current_len: usize, file_size: usize) -> Result<()> {
        if file_size == 0 {
            Err(AppendVecError::FileSizeTooSmall(file_size))
        } else if usize::try_from(MAXIMUM_APPEND_VEC_FILE_SIZE)
            .map(|max| file_size > max)
            .unwrap_or(true)
        {
            Err(AppendVecError::FileSizeTooLarge(file_size))
        } else if current_len > file_size {
            Err(AppendVecError::OffsetOutOfBounds(current_len, file_size))
        } else {
            Ok(())
        }
    }
