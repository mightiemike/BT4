The node-side `processTrigger` actually does enforce per-topic `allowedSenders` and `rateLimiter` checks before dispatching a trigger event, so the deepest layer of defense exists. However, the Gateway-side entry point that fans this request out to *all* DON nodes has no equivalent check.

### Title
Missing Access Control on Legacy WebAPI Trigger Ingestion in Gateway Capabilities Handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` in the Gateway's capabilities handler accepts `web_api_trigger` messages from any external caller and forwards them to every node in the DON, with only signature-format, payload-decoding, and staleness checks performed — no allowlist or rate-limiting is applied at the Gateway layer, despite an explicit `// TODO: apply allowlist and rate-limiting here` comment in the code [1](#0-0) .

### Finding Description
The Gateway's `ProcessRequest` routes legacy (DON-ID-based) messages to the appropriate handler after only generic structural validation (`msg.Validate()`, which merely checks signature format/length and recovers the sender address from the signature — it does not check the sender against any allowlist) [2](#0-1) [3](#0-2) .

For the `capabilities` (WebAPIHandler) handler, `HandleLegacyUserMessage` decodes the trigger payload, checks that `Timestamp` is non-zero and not stale, then immediately serializes and forwards the message to **every** member of the DON via `don.SendToNode`, with no allowlist or rate-limit check on the sender [4](#0-3) . The developers themselves flagged this gap with the comment `// TODO: apply allowlist and rate-limiting here` [5](#0-4) .

This contrasts with sibling Gateway handlers that implement the same "external user → gateway → DON" trust boundary correctly:
- The Functions handler enforces an allowlist and rate limiter before forwarding requests to nodes [6](#0-5) .
- The Vault handler requires full authorization (allowlist- or JWT-based) via `requestProcessor.ProcessRequest` before dispatching to nodes [7](#0-6) .

Any caller only needs to generate an ECDSA keypair, sign a well-formed message (`msg.Validate()` only checks signature format, not sender identity against any list), and submit it as a legacy DON-ID request to have it dispatched to all DON member nodes. The last line of defense is entirely inside the node's own `triggerConnectorHandler.processTrigger`, which does check `allowedSenders`/`allowedTopics`/rate limiting per registered workflow trigger [8](#0-7) . This means the Gateway itself performs no filtering, so unauthorized/unallowlisted traffic is unnecessarily fanned out to every DON node for every registered workflow, relying solely on the node-side per-workflow check to reject it.

### Impact Explanation
Because the Gateway forwards every syntactically-valid legacy `web_api_trigger` message to all DON nodes without any allowlist or rate limiting, this is a reachable resource-exhaustion / DoS vector against the DON and Gateway (unauthenticated traffic amplification: 1 external request → N node deliveries), and it also increases the attack surface for enumerating/guessing valid topics/sender combinations against every node in the DON, since the Gateway does no early rejection. It does not, by itself, allow a message to actually fire a trigger against a workflow it isn't allowlisted for (that check still occurs node-side), so the confidentiality/integrity impact is bounded to DoS/log-flooding/resource abuse rather than outright trigger spoofing.

### Likelihood Explanation
High likelihood of reachability: the Gateway HTTP endpoint is externally facing by design (`ProcessRequest` is the entry point called by the HTTP server) [9](#0-8) , and any party can produce a validly-formatted, self-signed message satisfying `Message.Validate()` without needing to be a known/allowlisted sender.

### Recommendation
Implement the allowlist and rate-limiting check called out in the existing TODO in `HandleLegacyUserMessage` before forwarding to `don.SendToNode`, mirroring the pattern already used in `functions.functionsHandler.HandleLegacyUserMessage` (per-sender allowlist + rate limiter checked at the Gateway before fan-out) [6](#0-5)  and the Vault handler's `requestProcessor.ProcessRequest` authorization gate [7](#0-6) .

### Proof of Concept
1. Generate an arbitrary ECDSA keypair (no registration/allowlisting required).
2. Craft an `api.Message` with `Body.Method = "web_api_trigger"`, a valid `Body.DonId` matching a real DON, and a `TriggerRequestPayload` with a non-zero, recent `Timestamp` and arbitrary `Topics`.
3. Sign the message with the arbitrary key (`msg.Sign(key)`), satisfying `Message.Validate()` since it only checks signature format/length and recovers the signer — no allowlist check occurs [3](#0-2) .
4. Submit the message to the Gateway's HTTP endpoint; `ProcessRequest` → `HandleLegacyUserMessage` will decode, validate timestamp/format, and forward the message to every member node of the DON via `don.SendToNode`, without any allowlist/rate-limit rejection at the Gateway [10](#0-9) .
5. Repeating this at volume (spoofing message IDs/keys) causes the Gateway to fan requests out to all DON nodes unfiltered, consuming node-side processing/rate-limiter budget per registered workflow trigger.

	}
	var isLegacyRequest = false
	var h handlers.Handler

			handlerKey = serviceName
		} else if donID, ok := g.serviceNameToDonID[serviceName]; ok {

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
