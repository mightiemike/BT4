### Title
Duplicate `data_id` entries in an `ActionReceipt.input_data_ids` list inflate `PendingDataCount`, permanently stalling the postponed receipt - ([File: runtime/runtime/src/lib.rs])

### Summary
The Sherlock report describes a class of bug where an ID is pushed into an accounting list without checking for duplicates, so a later "sum/iterate over the list" step is inflated relative to the real number of distinct entries. The nearcore analog is `Runtime::process_action_receipt`, which iterates `action_receipt.input_data_ids()` and increments an in-memory `pending_data_count` once per entry — with no deduplication — before persisting that count as `TrieKey::PendingDataCount`. If the same `data_id` appears more than once in `input_data_ids`, the persisted count is inflated relative to the number of distinct `DataReceipt`s that will ever actually arrive, and the corresponding action receipt can never reach `pending_data_count == 0`.

### Finding Description
`process_action_receipt` builds the pending-data bookkeeping for a postponed receipt: [1](#0-0) 

For every `data_id` in `input_data_ids()` that has not yet been received, it (a) increments the local counter `pending_data_count`, and (b) writes a `TrieKey::PostponedReceiptId { receiver_id, data_id }` entry pointing at this receipt. There is no check that `data_id` is unique within the list. If the list contains the same `data_id` twice, the loop still increments `pending_data_count` twice, even though the second `set(...)` call for `PostponedReceiptId` just overwrites the same key with the same value (so only one distinct index entry actually exists on the trie).

The persisted count is then used as the single source of truth for whether the postponed receipt is ready to execute: [2](#0-1) 

When the (single) matching `DataReceipt` for that `data_id` finally arrives, `process_receipt` looks up `PostponedReceiptId`, removes it, and decrements `PendingDataCount` by exactly one: [3](#0-2) 

Because only one `DataReceipt` will ever be produced for that `data_id`, the stored count can only be decremented once, and if it was inflated (e.g. `2` instead of `1`), it never reaches `1 → 0`, so the receipt is never fetched via `get_postponed_receipt`/`remove_postponed_receipt` and executed — it remains a `POSTPONED_RECEIPT` in the trie forever, and any waiting logic (and its attached deposit/gas) is permanently stuck.

This directly parallels the `stNXM` bug: `tokenIdToTranches.push(_trancheId)` had no existence check, so a duplicated ID inflated a downstream counter (`stakedNxm`/`assets`) used to decide execution/settlement; here `input_data_ids` has no uniqueness check, so a duplicated `data_id` inflates `PendingDataCount`, the counter used to decide whether the receipt executes.

### Impact Explanation
A receipt that is permanently postponed:
- Never executes its actions (including any `Transfer`, `FunctionCall`, or `AddKey`/`DeleteKey`/`Stake` action it carries), so any deposit attached to it is neither delivered nor refunded — this is a "permanently frozen funds" outcome, one of the explicitly accepted impact categories.
- Leaves orphaned state (`POSTPONED_RECEIPT`, `PENDING_DATA_COUNT`, stale `POSTPONED_RECEIPT_ID`/`RECEIVED_DATA` entries) that accumulates indefinitely, since the cleanup path (`remove_postponed_receipt`) is only reached when the count hits zero.
- Is deterministic and reproducible by any account submitting a transaction that triggers this receipt shape (a `FunctionCall` whose promise construction yields a receipt with a duplicated `data_id` dependency), so it is reachable by an ordinary contract call/transaction, matching the required threat model (unprivileged transaction signer / contract call).

### Likelihood Explanation
The trigger requires only that a contract-generated action receipt end up with the same `data_id` listed twice in `input_data_ids`. NEAR's promise API allows constructing a receipt that depends on more than one prior promise result (e.g. via the promise-joining host function that builds a combined dependency list). If that API does not itself deduplicate the promise/data indices supplied by the caller (I was not able to fully verify the exact host-function code path for this within available tool calls — the relevant logic lives in `runtime/near-vm-runner/src/logic/logic.rs` and `receipt_manager.rs`, which I could not inspect in full detail before running out of iterations), then any contract can pass the same promise index twice, which the runtime should still be checked against. Given the low complexity of the input construction (a single FunctionCall from any account) if this path is confirmed unguarded, likelihood is Medium-to-High; however, I could not conclusively confirm the absence of an upstream dedup check on `input_data_ids`/promise indices, so this should be verified before treating it as certain.

### Recommendation
- In `process_action_receipt` (`runtime/runtime/src/lib.rs:1663`), deduplicate `data_id`s before counting/incrementing `pending_data_count`, e.g. collect unique `data_id`s (a `HashSet`) and derive the count and the number of `PostponedReceiptId` writes from that set, or reject/normalize receipts whose `input_data_ids` contain duplicates at receipt-validation time.
- Alternatively (or additionally), enforce uniqueness of promise/data indices at the point where a contract combines promises into a new action receipt, so `input_data_ids` can never contain duplicates by construction.
- Add a fuzz/unit test that submits a receipt with duplicate `input_data_ids` and asserts the postponed receipt still executes exactly once when the single corresponding `DataReceipt` arrives.

### Proof of Concept
1. From a contract account, construct (via the promise-joining host call, or by directly crafting a receipt for a test harness) an `ActionReceipt` whose `input_data_ids` is `[X, X]` (the same `data_id` twice) rather than `[X]`.
2. Submit the transaction that creates this receipt; `process_action_receipt` runs the loop at `runtime/runtime/src/lib.rs:1663-1677`, setting `pending_data_count = 2` and persisting `TrieKey::PendingDataCount = 2`.
3. Let the single `DataReceipt` for `data_id = X` arrive and be processed by `process_receipt` (`runtime/runtime/src/lib.rs:1452-1526`). `PendingDataCount` is decremented from `2` to `1`; since it is not `1` at the time of the check (it starts at `2`), the branch that executes the receipt (`pending_data_count == 1`) is never taken.
4. The action receipt remains stored as `POSTPONED_RECEIPT` in state indefinitely; its actions (and any attached deposit) are never executed or refunded, and the associated `PendingDataCount`/`PostponedReceiptId` entries persist as orphaned state forever.
