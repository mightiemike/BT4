**Analysis:** `AbstractActuator.subtractExact` at [1](#0-0)  delegates to `Maths.subtractExact`, which in turn calls either `StrictMathWrapper.subtractExact` or `MathWrapper.subtractExact` (the latter simply wraps `Math.subtractExact`) as shown in [2](#0-1)  and [3](#0-2) . `Math.subtractExact`/`Math.addExact` are JDK checked-arithmetic operations that throw `ArithmeticException` on overflow rather than silently wrapping — this is the opposite of an underflow/overflow vulnerability; it's a defensive guard.

Additionally, the actual balance-adjustment logic in `Commons.adjustBalance` explicitly validates sufficiency before performing any subtraction: it checks `if (amount < 0 && balance < -amount) throw new BalanceInsufficientException(...)` before calling `addExact`, as seen at [4](#0-3) . This means an attacker cannot drive a balance below zero through this path — any attempt to subtract more than the account's balance throws `BalanceInsufficientException`, which actuators propagate as a failed transaction (no state change, fee still charged per normal flow).

Similarly, `Commons.adjustTotalShieldedPoolValue` checks the result is non-negative before persisting it: [5](#0-4) .

There is no reachable path where an attacker-controlled amount causes a silent underflow/overflow that bypasses these checks — the checked-arithmetic wrappers throw exceptions on overflow, and the balance-sufficiency check happens prior to the arithmetic in the only call sites (`Commons.adjustBalance`, `AbstractActuator.adjustBalance`). This does not constitute an exploitable accounting-corruption bug.
