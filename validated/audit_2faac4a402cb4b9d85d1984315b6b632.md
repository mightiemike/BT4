**Analysis:**

`process_dkg_result_inner` in `dkg.rs` fetches `dkg_state` fresh from the `resolver` at the start of the function via `OnChainConfig::fetch_config(resolver)`, which reflects the exact state-view snapshot bound to the transaction being executed — not a cached or "stale" value from a prior session [1](#0-0) . The `pub_params` used for verification are derived directly from `in_progress_session_state.metadata`, i.e., the metadata of whatever session is currently recorded in that same resolver snapshot [2](#0-1) . There is no code path where a "different" `in_progress_session_state.metadata` could be substituted while still using the resolver's current state — both the metadata and the transcript-verification step are read from the identical state view within one deterministic function call.

Even hypothetically, `RealDKG::verify_transcript` cryptographically binds verification to the session-specific `DKGSessionMetadata`: it derives `spks` (dealer public keys) and `aux` (epoch + address tuples) from `params.verifier` and `params.pvss_config`, which differ per session/epoch/validator-set [3](#0-2) . A transcript generated against one session's `DKGSessionMetadata` (different dealer/target validator sets, different PVSS public parameters and encryption keys, different epoch used as associated data) will fail `trx.main.verify(...)` against a different session's `pub_params`, because the PVSS scheme's `aux`/epoch binding and encryption keys won't match. This is precisely the cross-session rejection the exploit question asks to disprove — it is enforced by construction, not merely by convention.

Additionally, an explicit epoch guard rejects mismatched-epoch transcripts before verification is even attempted: `if dkg_node.metadata.epoch != config_resource.epoch() { return Err(Expected(EpochNotCurrent)); }` [4](#0-3) .

Since `dkg_state`/`in_progress_session_state` is always read fresh and atomically from the same resolver as the rest of the check, and `verify_transcript` cryptographically ties acceptance to that exact session's public parameters, there is no path by which a transcript from a different session's metadata can pass verification and reach `FINISH_WITH_DKG_RESULT` with mismatched metadata.
