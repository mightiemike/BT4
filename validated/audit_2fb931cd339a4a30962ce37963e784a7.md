### Title
Speculative claim invalid: intra-batch duplicate-message-hash filtering already prevents double-spend - ([File: svm/src/transaction_processor.rs])

### Summary
The premise that duplicate transactions within the same batch/entry could both execute because `status_cache` insertion happens post-batch is incorrect. Duplicate-message-hash rejection is enforced *before* execution, at both the entry-validation layer and the account-locking layer, independent of `status_cache` timing.

### Finding Description
The attack path assumes `check_status_cache` (in `runtime/src/bank/check_transactions.rs`) is the only defense against intra-batch duplicates, and that since it only reads the persisted `status_cache` (populated by `update_transaction_statuses`/`commit_transactions` after the whole batch executes, per `runtime/src/bank.rs:3515-3543`), two identical transactions in one batch would both pass. This ignores two independent, mandatory checks that reject duplicate message hashes *within a batch/entry before execution*:

1. `ledger/src/blockstore_processor.rs:validate_entry_transactions` (lines 253-272) explicitly rejects any entry containing two transactions with the same `message_hash()`, returning `TransactionError::AlreadyProcessed`, before scheduling transactions for execution. Its doc comment states: "Post-SIMD-83 the duplicate-message-hash check is what rejects an entry that replays the same transaction twice (it no longer conflicts on locks)."
2. `runtime/src/bank.rs:try_lock_accounts_with_results` (lines 3688-3721) independently maintains a `batch_message_hashes: AHashSet` and fails any transaction in the batch whose `message_hash()` was already seen earlier in the same batch, again with `TransactionError::AlreadyProcessed`, before entering `load_and_execute_sanitized_transactions`.

This means by the time `load_and_execute_sanitized_transactions` (`svm/src/transaction_processor.rs:402-472`) is called, the `check_results` passed in already mark the second identical transaction as `Err(TransactionError::AlreadyProcessed)`, so it is skipped in the execution loop (line 471-472 branches on `check_result`). The existing repo test `ledger/src/blockstore_processor.rs:test_process_entry_duplicate_transaction` (lines 3728-3781) directly demonstrates this: submitting one entry with two identical transfer transactions results in `Err(TransactionError::AlreadyProcessed)` and balances unchanged (`[5, 5]`), proving no double-spend occurs.

### Impact Explanation
None — the described exploit path does not exist. The claimed impact (intra-batch double-spend via `status_cache` insertion timing) is prevented by pre-execution, entry/batch-level duplicate-message-hash rejection that is mandatory and always active (not feature-gated or optional).

### Likelihood Explanation
Not applicable; the precondition ("neither is yet in `status_cache`... both execute") is false because rejection occurs earlier in the pipeline (`validate_entry_transactions` and `try_lock_accounts_with_results`), not at the `status_cache` check.

### Recommendation
No fix needed. If auditing further, confirm these checks are exercised for all transaction ingestion paths (leader packet processing/scheduling), which they already are per `runtime/src/bank.rs:3688-3721`.

### Proof of Concept
Existing test `ledger/src/blockstore_processor.rs:test_process_entry_duplicate_transaction` (lines 3728-3781) already serves as the PoC: an entry with two byte-identical transfer transactions from `keypair1` to `keypair2` results in `TransactionError::AlreadyProcessed` and balances `[5, 5]` (unchanged), confirming only one (in fact, zero net) transfer takes effect and no double-spend occurs. /// Validate an entry's transactions before scheduling: each transaction's account
/// locks (count and duplicates), and rejection of duplicate message hashes within
/// the entry. Does not take account locks - the unified scheduler orders conflicts.
/// Post-SIMD-83 the duplicate-message-hash check is what rejects an entry that
/// replays the same transaction twice (it no longer conflicts on locks).
fn validate_entry_transactions(
    transactions: &[RuntimeTransaction<SanitizedTransaction>],
    tx_account_lock_limit: usize,
) -> Result<()> {
    let mut batch_message_hashes = AHashSet::with_capacity(transactions.len());

    for transaction in transactions {
        validate_account_locks(transaction.account_keys(), tx_account_lock_limit)?;
        if !batch_message_hashes.insert(transaction.message_hash()) {
            return Err(TransactionError::AlreadyProcessed);
        }
    }

    Ok(())
}

    fn check_status_cache<Tx: TransactionWithMeta>(
        &self,
        sanitized_txs: &[impl core::borrow::Borrow<Tx>],
        mut lock_results: Vec<TransactionCheckResult>,
        collect_processed_slots: bool,
        error_counters: &mut TransactionErrorMetrics,
    ) -> (Vec<TransactionCheckResult>, Option<Vec<Option<Slot>>>) {
        // Do allocation before acquiring the lock on the status cache.
        let mut processed_slots = if collect_processed_slots {
            Some(Vec::with_capacity(sanitized_txs.len()))
        } else {
            None
        };
        let rcache = self.status_cache.read().unwrap();

        for (sanitized_tx_ref, lock_result) in sanitized_txs.iter().zip(lock_results.iter_mut()) {
            let processed_slot = if lock_result.is_ok() {
                self.get_processed_slot(sanitized_tx_ref.borrow(), &rcache)
            } else {
                None
            };

            if processed_slot.is_some() {
                error_counters.already_processed += 1;
                *lock_result = Err(TransactionError::AlreadyProcessed);
            }

            if let Some(processed_slots) = processed_slots.as_mut() {
                processed_slots.push(processed_slot)
            }
        }

        (lock_results, processed_slots)
    }
