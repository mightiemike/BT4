### Title
Rescue outbound amount is hardcoded from the original inbound record instead of the actually rescued amount emitted by the source-chain gateway - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`AttachRescueOutboundFromReceipt` builds the `RESCUE_FUNDS` `OutboundTx` using `originalUtx.InboundTx.Amount` (the amount recorded when the original inbound was first voted in) rather than the amount actually reported in the `RescueFundsOnSourceChain` event that triggered the rescue. This is the same false-assumption pattern as the C4 finding: a refund/withdrawal path assumes the originally recorded contribution/amount is still exactly what is available to be paid out, instead of using the value that was actually recovered.

### Finding Description
When a CEA deposit fails (unregistered asset, contract error, etc.) or a non-CEA inbound's `INBOUND_REVERT` outbound is voted `REVERTED`, funds are considered "stuck" and a rescue path exists: someone calls `RescueFundsOnSourceChain` on the gateway, which emits an event decoded by `types.DecodeRescueFundsOnSourceChainFromLog` into `event`. [1](#0-0) 

`AttachRescueOutboundFromReceipt` then constructs the rescue `OutboundTx`: [2](#0-1) 

Note that `event.PRC20`, `event.Sender`, `event.GasFee`, `event.GasPrice`, and `event.GasLimit` are all pulled from the observed on-chain event, but `Amount` is set to `originalUtx.InboundTx.Amount` — the value stored when the *original* inbound was first recorded, not `event.Amount` (whatever the gateway actually rescued/reported). This mirrors `Migration.withdrawContribution` in the C4 report: it pays out based on a stored "original" figure instead of what was actually recovered by the underlying mechanism (there, `Buyout`; here, the source-chain gateway's rescue call).

The keeper's own `TestRescueFunds` integration tests reinforce that other fields are always taken from the event (see `buildRescueFundsLog(... amount, gasFee, gasPrice ...)` and assertions like `require.Equal(t, "111", rescueObs.GasFee)`), while `Amount` is never checked against the event's amount value — it is silently backfilled from the stale inbound record. [3](#0-2) 

### Impact Explanation
This corrupts `UniversalTx` outbound state and misroutes value in the universal-execution / registry accounting path (in-scope: "corruption of ... refund accounting ... revert destination ... canonical UniversalTx state"). If the amount actually recoverable on the source chain via the rescue call is not exactly equal to the original inbound amount (e.g., partial recovery, a fee-on-transfer asset, or any gateway-side accounting difference for that specific stuck transaction), the `RESCUE_FUNDS` outbound instructs UVs to sign and broadcast a TSS transaction promising to deliver `InboundTx.Amount` — a value that may not correspond to what the gateway actually holds/rescued for that transaction. This can result in an outbound that either cannot be honored (draining more than was rescued, harming the escrow/vault) or that silently pays out a stale, wrong amount unrelated to the real rescue event, independent of any validator or relayer misbehavior — honest UVs simply observe the real event and vote it in, and the bug lies in the keeper's amount-selection logic itself.

### Likelihood Explanation
The rescue path is reachable by any unprivileged user: the CEA-deposit-failure precondition can be triggered by submitting an inbound referencing an unregistered/invalid asset address (as demonstrated by `setupRescueFundsTest`), and the non-CEA precondition is reachable whenever an `INBOUND_REVERT` outbound gets voted `REVERTED` in the normal flow. Once stuck, any account can call the gateway's rescue function; the keeper's `AttachRescueOutboundFromReceipt` unconditionally uses the stale inbound amount for every rescue it processes, so the mismatch is a systematic code defect, not a rare edge case, though it only manifests as a loss/insolvency when the source-chain gateway's actual rescuable amount for a given stuck transaction differs from the originally recorded inbound amount.

### Recommendation
Use `event.Amount` (the amount reported by the `RescueFundsOnSourceChain` event) to populate `OutboundTx.Amount` instead of `originalUtx.InboundTx.Amount`, consistent with how `GasFee`, `GasPrice`, and `GasLimit` are already sourced from the event. If `event.Amount` is intentionally absent from the ABI/event, add it, and validate it does not exceed `InboundTx.Amount` before creating the outbound.

### Proof of Concept
1. Trigger a stuck CEA inbound as in `setupRescueFundsTest` (`x/uexecutor` `rescue_funds_test.go` lines 74-140): submit an inbound with amount `1000000` and an unregistered asset address so the deposit PCTx fails.
2. Have the source-chain gateway rescue only a partial amount (or an amount tokenized differently due to fees) for that stuck transaction, emitting `RescueFundsOnSourceChain` with `event.Amount` != `1000000` (e.g., `900000`).
3. `AttachRescueOutboundFromReceipt` is invoked with the receipt containing this event; the resulting `OutboundTx.Amount` is hardcoded to `"1000000"` from `originalUtx.InboundTx.Amount`, ignoring the actual rescued `900000`.
4. UVs subsequently sign/broadcast a TSS outbound instructing that `1000000` be delivered on the source chain, even though only `900000` was actually rescued into the escrow/vault backing this outbound — an unbacked or mismatched refund instruction reaches the honest-validator finalization/TSS-signing flow.
