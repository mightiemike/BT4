### Title
Inbound ballots that finalize as REJECTED move funds into `ExpiredInbounds` with no implemented refund path — ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
When a source-chain inbound's ballot finalizes as `BALLOT_STATUS_REJECTED` (or all variants end `EXPIRED`/`REJECTED`), `x/uexecutor`'s `BallotHooks.afterInboundBallotTerminal` routes the audit trail into the `ExpiredInbounds` collection instead of creating a `UniversalTx`. No `UniversalTx` is ever created for these entries. The only existing recovery mechanism, `RevertStuckInbound`/`admin_revert.go`, strictly requires the underlying ballot to be in `BALLOT_STATUS_EXPIRED` and explicitly rejects any other status (including `REJECTED`). The rescue path, `AttachRescueOutboundFromReceipt`, requires an existing `UniversalTx` to attach to, which does not exist for `ExpiredInbounds` entries. The result: user funds already bridged/locked into the source-chain gateway for a REJECTED inbound have zero implemented on-chain refund path, exactly mirroring the H-02 pattern where an offer is created via an intermediary and no cancellation function exists to reclaim it.

### Finding Description
The generic ballot machine in `x/uvalidator/types/ballot.go` finalizes a ballot as `BALLOT_STATUS_REJECTED` whenever `ShouldReject()`/`IsFinalizingVote()` determine that NO votes make reaching `VotingThreshold` mathematically impossible: [1](#0-0) [2](#0-1) 

This is a normal, honest-validator outcome (e.g. a majority of validators independently deciding an observed inbound is invalid, or disagreement across `InboundVariant`s), not evidence of malicious behavior.

When this happens for an inbound ballot, `x/uexecutor`'s `BallotHooks.afterInboundBallotTerminal` handles the terminal transition: [3](#0-2) 

Crucially, if all variants end in a non-`PASSED` terminal state, the entry is moved to `ExpiredInbounds` and **no `UniversalTx` is ever created** for the inbound — the user's bridged funds are never accounted for on Push Chain via the normal UTX flow.

The only escape hatch, `RevertStuckInbound`, strictly gates on the underlying ballot's status being `EXPIRED`: [4](#0-3) 

A `REJECTED` ballot status causes this function to return an error (`"ballot status is REJECTED; admin revert requires EXPIRED"`), so it cannot be used to build a compensating `INBOUND_REVERT` outbound for REJECTED-terminal inbounds.

The other candidate recovery mechanism, `AttachRescueOutboundFromReceipt`, requires fetching a pre-existing `UniversalTx`: [5](#0-4) 

Since `ExpiredInbounds` entries never had a `UniversalTx` created, `GetUniversalTx` returns not-found and this path errors out unconditionally for these cases.

The proto/code comments explicitly acknowledge this gap is unimplemented: [6](#0-5) [7](#0-6) 

This is the direct structural analog of the H-02 report: funds move into an intermediary-owned state (here, `ExpiredInbounds`/off-chain gateway custody rather than a router contract) with no implemented cancel/refund function reachable by the user or even by the admin's existing tooling.

### Impact Explanation
Funds that a user legitimately deposited/locked on the source-chain gateway for an inbound whose ballot is finalized `REJECTED` (or whose variants all terminate non-`PASSED`) become **permanently unaccounted for and unrecoverable** through any currently implemented on-chain flow — matching the in-scope impact "permanent freezing... of user or protocol-controlled funds." Unlike `EXPIRED` ballots (which have the admin `RevertStuckInbound` path, however privileged), `REJECTED` ballots have no path at all, not even a privileged one, since `admin_revert.go` explicitly refuses non-`EXPIRED` statuses.

### Likelihood Explanation
Reaching a `REJECTED` terminal ballot does not require any malicious or privileged actor — it is a documented, tested outcome of the honest ballot machine (`TestIntegration_CheckIfFinalizingVote`/"rejected ballot when NO votes make threshold impossible") that can occur from ordinary validator disagreement on a legitimately-submitted inbound (e.g. ambiguous source-chain data, differing confirmations, or a majority determination that the observation is invalid). Since inbound creation is entirely user/attacker-driven (any external-chain deposit triggers UV observation and voting), an unprivileged user can end up in this state without any validator misbehavior. [8](#0-7) 

### Recommendation
Extend `RevertStuckInbound` (or add an equivalent flow) to also accept ballots in `BALLOT_STATUS_REJECTED`, and/or add a dedicated escape-hatch message that consumes `ExpiredInbounds` entries (both `EXPIRED` and `REJECTED` terminal variants) to create a `UniversalTx` + `INBOUND_REVERT`/refund `OutboundTx`, so that REJECTED-terminal inbounds have the same recoverability guarantee as EXPIRED ones. Until implemented, this is a genuine gap referenced by the code's own "future escape-hatch refund flow" comments.

### Proof of Concept
1. An external-chain user submits a valid deposit event on a registered chain/gateway; Universal Validators begin voting `MsgVoteInbound`.
2. A supermajority of honest UVs vote `VOTE_RESULT_FAILURE` on the observation (e.g. legitimate disagreement/invalidity determination), driving `ShouldReject()` true and finalizing the ballot as `BALLOT_STATUS_REJECTED` (see `x/uvalidator/types/ballot.go:86-91,152-160`, exercised by `TestIntegration_CheckIfFinalizingVote`/"rejected ballot" and `TestBallotHook_SingleVariantRejectedRoutesToExpiredInbounds`).
3. `BallotHooks.afterInboundBallotTerminal` routes the entry to `ExpiredInbounds`; no `UniversalTx` is created (`x/uexecutor/keeper/ballot_hooks.go:120-142`).
4. Attempting `MsgRevertStuckInbound`/`RevertStuckInbound` on this inbound fails because `ballot.Status != BALLOT_STATUS_EXPIRED` (`x/uexecutor/keeper/admin_revert.go:47-51`).
5. Attempting the rescue-funds path via `AttachRescueOutboundFromReceipt` fails because no `UniversalTx` exists for this `utxId` (`x/uexecutor/keeper/create_outbound.go:228-234`).
6. The user's source-chain funds remain locked in the external gateway with no on-chain mechanism (privileged or unprivileged) to trigger a refund.

func (k Keeper) RevertStuckInbound(ctx context.Context, inbound types.Inbound) (utxId, outboundId string, err error) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Same canonical form as the vote path, so the admin-supplied payload
	// derives the same ballot key / UTX key the votes did.
	inbound.Canonicalize()

	if vErr := inbound.ValidateBasic(); vErr != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, vErr.Error())
	}

	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest, fmt.Sprintf("failed to derive ballot key: %s", err))
	}

	ballot, err := k.uvalidatorKeeper.GetBallot(ctx, ballotKey)
	if err != nil {
		return "", "", errors.Wrap(sdkErrors.ErrNotFound, fmt.Sprintf("ballot for inbound not found (key=%s): %s", ballotKey, err))
	}

	if ballot.Status != uvalidatortypes.BallotStatus_BALLOT_STATUS_EXPIRED {
		return "", "", errors.Wrap(sdkErrors.ErrInvalidRequest,
			fmt.Sprintf("ballot %s status is %s; admin revert requires EXPIRED (use MsgRecomputeBallotQuorum to drive a stuck pending ballot to EXPIRED)",
				ballotKey, ballot.Status.String()))
	}
