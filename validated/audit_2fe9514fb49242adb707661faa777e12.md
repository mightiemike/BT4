### Title
Unbounded duplicate accumulation in `KVSessionStorage.addShopIds()` causes session-storage index growth / DoS - ([File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts])

### Summary
`KVSessionStorage.storeSession()` unconditionally appends the stored session's `id` to a per-shop index list via `addShopIds()`, without checking whether that id is already present in the list. Because `storeSession()` is called repeatedly for the *same* session id whenever a merchant's offline/online session is refreshed or re-exchanged (a normal, unprivileged/merchant-triggered code path), the per-shop id array grows without bound.

### Finding Description
`addShopIds` reads the existing id array and blindly concatenates the new id(s) onto it, with no de-duplication check: [1](#0-0) 

This is invoked from `storeSession` on every call: [2](#0-1) 

By contrast, the equivalent Redis implementation explicitly guards against duplicates with an `includes()` check before pushing: [3](#0-2) 

`storeSession` is called repeatedly for the same session id in normal, unprivileged flows — e.g. token-exchange re-authentication (`offline_<shop>` id reused) whenever the offline session is missing/expired/invalid, and offline token refresh: [4](#0-3) [5](#0-4) 

Each of these paths is reachable via ordinary app usage by a single merchant/customer session — no elevated privileges are required, and repeated visits or repeated invalid/expiring sessions will each append another duplicate id to `shop:<shop>` in KV storage.

### Impact Explanation
Because the `shop:<shop>` KV value keeps growing with duplicate ids indefinitely, this is an availability issue for the session-storage/auth subsystem:
- `findSessionsByShop` (used during authentication flows) iterates the entire (growing) id list and performs a KV `get` per id, so this operation's cost keeps degrading over time.
- Cloudflare KV values have hard size limits; a sufficiently large duplicate-laden array could eventually cause `put`/`get` failures, breaking `storeSession`/`findSessionsByShop` for that shop entirely (denial of service of the session-storage/auth handler).
- This is caused purely by legitimate/expected traffic (repeated token exchange / refresh calls), not an attacker payload, making it a reliable, low-effort DoS vector against any app using `@shopify/shopify-app-session-storage-kv`.

### Likelihood Explanation
High. Any deployment using `KVSessionStorage` combined with the token-exchange auth strategy or offline-token-refresh feature will trigger `storeSession` for the same shop's offline (and/or online) session id repeatedly during normal operation (e.g., session token near/at expiry, invalidated access token after a 401, or expiring-offline-token refresh), guaranteeing duplicate accumulation over the app's lifetime without any attacker action needed.

### Recommendation
In `KVSessionStorage.addShopIds` (and symmetrically in `removeShopIds`), de-duplicate before persisting, mirroring the Redis implementation's `includes()` guard:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Configure a Shopify app to use `KVSessionStorage` with the token-exchange auth strategy.
2. As a normal merchant, repeatedly load the embedded app after the offline session's access token has been invalidated (e.g., after a 401 from the Admin API) or right at/after the `WITHIN_MILLISECONDS_OF_EXPIRY` window, so `TokenExchangeStrategy.authenticate` re-exchanges and calls `config.sessionStorage.storeSession(offlineSession)` with the same `offline_<shop>` id each time.
3. Inspect the KV value at key `shop:<shop>`: observe the id array growing by one duplicate entry per re-exchange, with no bound, eventually degrading `findSessionsByShop` performance and risking KV value-size limits.
