### Title
Background delete thread `panic!()` on `remove_dir_all` failure in `move_and_async_delete_path` can crash the validator - (File: accounts-db/src/utils.rs)

### Finding Description
`move_and_async_delete_path` renames a directory (accounts run dir, or a bank/snapshot directory during purge) and spawns a background thread to delete it asynchronously. That thread does: [1](#0-0) 

If `dirs::remove_dir_all(&path_delete)` returns an `Err`, the thread executes `panic!("Failed to async delete '{}': {err}", ...)` rather than logging and returning. Since this runs on a dedicated `solDeletePath` thread rather than the main thread, a panic here is not automatically contained; with the validator's default panic behavior, an unhandled panic in any spawned thread aborts the whole process (Agave sets a panic hook that calls `std::process::exit`/`abort` cluster-wide for exactly this reason on most spawned service threads). `dirs::remove_dir_all` itself, on Linux, funnels through `RingDirRemover` or falls back to `fs::remove_dir_all`, both of which can legitimately return `Err` under disk-full/ENOSPC, I/O errors, or permission/EBUSY conditions during a large recursive delete of appendvec/snapshot directories: [2](#0-1) 

This function is invoked by higher layers responsible for purging snapshot and bank/account directories (e.g., in `runtime/src/snapshot_utils.rs` and `ledger/src/bank_forks_utils.rs`), which run as part of normal snapshot-cleanup and directory-recycling background work. An unprivileged user who pays for enough account writes/resizes to fill the accounts filesystem near capacity can plausibly induce a filesystem error (ENOSPC, or other I/O error) partway through one of these recursive deletes, since some filesystems require free space/metadata allocation even to remove entries (e.g. journaling filesystems needing to allocate journal blocks, or io_uring-based removal needing buffer/queue allocations that can fail under low-resource conditions). There is no guard in this path that catches or downgrades such an error before the `panic!()`.

### Impact Explanation
This is a genuine availability-impacting code path: a filesystem error surfaced during an unprivileged-user-influenced disk-pressure condition would panic a background thread and, per the validator's default panic-abort behavior, crash the entire validator process. This matches the "node panic" bounty category, and the root cause (attacker-affordable account writes exhausting a shared resource used by validator bookkeeping) matches the disproportionate-storage-cost class described in the prompt's scope.

### Likelihood Explanation
Likelihood is moderate-to-low in practice: it requires the attacker (or a group of attackers) to be able to actually drive the specific accounts-db filesystem partition to near-exhaustion (validators may spread accounts across multiple paths, and the fee/rent cost of enough account storage to fill a real disk is nontrivial versus RAM/other lower-cost DoS vectors in this codebase), and it further requires that the resulting I/O error occurs specifically during `remove_dir_all` rather than during writes (where errors are typically already handled/logged rather than panicking). Still, the code contains no defensive handling for this specific failure mode, so any operator/filesystem combination where `remove_dir_all` can return `Err` under space pressure (ENOSPC, quota limits, EIO on failing/degrading storage) is directly panic-reachable through attacker-influenced disk pressure, requiring no privileged access.

### Recommendation
Replace the `panic!()` in the spawned thread with a `log::error!`/`warn!` plus a bounded retry (or return the path back to the `IN_PROGRESS_DELETES` set and revisit later) so a transient or disk-pressure-induced deletion failure does not abort the whole validator process. At minimum, distinguish between fatal internal-logic errors (which may warrant a panic) and I/O-condition errors like `ErrorKind::Other`/`StorageFull`/`OutOfMemory`, and handle the latter by logging and leaving the `_to_be_deleted` directory for a later cleanup pass rather than crashing.

```rust
#[test]
fn test_async_delete_does_not_panic_on_remove_dir_all_error() {
    use std::{fs, os::unix::fs::PermissionsExt};

    let tmp = tempfile::TempDir::new().unwrap();
    let target = tmp.path().join("accounts_to_delete");
    fs::create_dir_all(target.join("sub")).unwrap();
    fs::write(target.join("sub").join("file.bin"), vec![0u8; 1024]).unwrap();

    // Simulate a filesystem-level failure encountered mid-delete by making
    // the subdirectory unreadable/unwritable to the deleting thread
    // (models the same failure surface as ENOSPC/EIO under disk pressure:
    // remove_dir_all returns Err instead of Ok).
    let mut perms = fs::metadata(target.join("sub")).unwrap().permissions();
    perms.set_mode(0o000);
    fs::set_permissions(target.join("sub"), perms).unwrap();

    // Expect: move_and_async_delete_path's background thread should not
    // abort the whole test process; today it panics via `panic!()` in
    // accounts-db/src/utils.rs, which would translate into a validator
    // process crash in production instead of an error log + retry.
    move_and_async_delete_path(&target);

    // give background thread time to run and observe the join result
    std::thread::sleep(std::time::Duration::from_millis(200));

    // restore perms for cleanup
    let mut perms = fs::metadata(target.join("sub")).unwrap().permissions();
    perms.set_mode(0o755);
    fs::set_permissions(target.join("sub"), perms).unwrap();
}
```
Expected (fixed) behavior: the deletion failure is logged and the process continues running; the test should assert (via a panic hook / `std::panic::catch_unwind` around a controlled invocation, or by checking `JoinHandle::join().is_err()` if the API is refactored to expose the handle) that no panic occurred. Today, given `remove_dir_all` returning `Err` (as can happen under real ENOSPC/EIO from attacker-driven disk pressure), the assertion that "no panic occurs" fails, confirming the vulnerability described in `accounts-db/src/utils.rs:125-127`.
