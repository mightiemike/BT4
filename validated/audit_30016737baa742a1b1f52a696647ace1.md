### Title
ValidateMultiSign double-counts multisig weight for malleable signature duplicates of the same signer - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`ValidateMultiSign.execute` deduplicates signatures by comparing full merged `recoveredAddr + sign` byte arrays instead of deduplicating strictly by `recoveredAddr`. An attacker who controls (or is given) two distinct byte-level ECDSA signatures that recover to the same address (e.g. via signature malleability `(r, n-s, 1-v)`) can have that single signer's weight counted twice, allowing the precompile to report `totalWeight >= permission.getThreshold()` using fewer distinct real signers than the threshold requires.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute` [1](#0-0) , the loop iterates over supplied signatures, recovers an address per signature, and attempts to skip duplicates:

```
byte[] recoveredAddr = recoverAddrBySign(sign, hash);
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```

`ByteArray.matrixContains` performs raw `Arrays.equals` byte comparisons [2](#0-1) . The intended dedup semantic ("same signer already counted, skip") is only triggered when the *exact byte encoding* of the signature repeats (`matrixContains(executedSignList, sign)`). If `recoveredAddr` was already seen, but the signature bytes differ from any previously stored one (`sign` mismatch), the code does **not** `continue`; it merely calls `MUtil.checkCPUTime()` as a CPU-abuse guard and then falls through to compute and add `weight` for `recoveredAddr` **again**, appending duplicate entries to `executedSignList`.

Standard secp256k1 ECDSA is malleable: given a valid signature `(r, s, v)` for a message hash, `(r, n-s, 1-v)` is also a valid, independently-verifiable signature recovering to the identical address, and it can be derived by anyone from the original signature without the private key. `recoverAddrBySign` in this precompile behaves like Ethereum's `ecrecover` precompile (no evidence in this file of a canonical-low-S rejection prior to recovery), so both encodings will recover to the same `recoveredAddr` but are byte-distinct, thus bypassing the `matrixContains(executedSignList, sign)` check while still matching `matrixContains(executedSignList, recoveredAddr)`.

An attacker controlling only one legitimate signer key (with weight `w` under a `Permission`) can:
1. Sign the multisig hash once to get `(r, s, v)`.
2. Derive the malleated counterpart `(r, n-s, 1-v)` for the same hash — no private key needed.
3. Submit both signatures in the `bytes[]` signature array parameter of `validatemultisign(address,uint256,bytes32,bytes[])`.
4. The loop counts `weight` for iteration 1, then, on iteration 2, sees `recoveredAddr` already present but `sign` (merged bytes) different, so it does not skip and adds `weight` a second time.
5. `totalWeight` becomes `2*w`, which may reach/exceed `permission.getThreshold()` even though only one real distinct signer participated, violating the invariant that the threshold reflects distinct authorized signer weight.

This precompile is reachable by any unprivileged smart contract or externally-owned account via a normal `CALL` to the `validatemultisign` precompiled address — no special privilege required. This differs from `BatchValidateSign`, which checks each provided address against each signature individually rather than accumulating weight with an address-based dedup list, so it is not affected the same way.

### Impact Explanation
A contract relying on `ValidateMultiSign` (TRC-style multisig-gated contracts, e.g. escrow/vault/bridge logic checking on-chain account permission thresholds) can be tricked into believing a multisig threshold has been met with fewer real independent signers than required. This allows a forged multisig approval — e.g., authorizing a transfer or privileged call — using only a subset of the real key holders (as few as `threshold/max-weight-per-key` real signers instead of the intended number), a direct authorization/access-control bypass.

### Likelihood Explanation
- The `MAX_SIZE` cap (5) does not prevent this; only 2 signatures are needed (one legit + one malleated).
- No canonical-S enforcement is visible in the precompile before calling `recoverAddrBySign`; ECDSA malleability computation is trivial (flip `s -> n - s`, `v -> 1 - v`) and requires no private key access, only the original valid signature bytes.
- The `matrixContains` dedup design explicitly is byte-exact rather than address-exact, so this is a straightforward logic gap, not a deep cryptographic attack.
- Reachable from ordinary transaction/contract execution — fully unprivileged.

### Recommendation
Deduplicate strictly by `recoveredAddr` rather than by the merged `sign+recoveredAddr` bytes: once a `recoveredAddr` has been seen, always `continue` (skip weight accumulation) regardless of whether the raw signature bytes differ. Remove/replace the `matrixContains(executedSignList, sign)` exact-byte check, since it allows a second, malleated encoding of the same signer's signature to bypass dedup. Optionally also normalize/reject non-canonical (high-S) signatures during recovery to reduce this style of malleability generally.

### Proof of Concept
Add a unit test alongside the existing `ValidateMultiSignContractTest` (`framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java`) that:

1. Creates an account with an `Active` permission with `threshold = 2` and a single key `key1` with `weight = 1`.
2. Signs the multisig hash once with `key1` to get `ECDSASignature sig = key1.sign(toSign)`.
3. Constructs the malleated signature `(r, CURVE.getN().subtract(sig.s), flip recId)` re-serialized to the same 65-byte `r||s||v` layout `ValidateMultiSign` expects.
4. Submits `signs = [sig.toByteArray(), malleatedSig.toByteArray()]` (two distinct byte arrays) via `validateMultiSign(...)`.
5. Asserts that the result is `DATA_FALSE` (i.e., `totalWeight` must remain `1`, below threshold `2`), proving the fix. Before a fix, the vulnerable code returns `DATA_ONE`, demonstrating the weight was double-counted from a single real signer. [3](#0-2)
