### Title
Front-runnable relayer fee in `rlp_execute` allows MEV-style theft of funds intended for the legitimate relayer - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The dYdX report describes a case where value that was meant to move to a specific, protected destination (the user's own funds during a white-hat rescue) was instead intercepted and captured by an unrelated MEV actor who copied/front-ran the pending operation. In the NEAR Wallet Contract's `rlp_execute` flow, the relayer-fee refund for emulated base-token/ERC-20 transfers is paid to whichever account happens to be the `predecessor_account_id` of the successful call, not to any account cryptographically tied to the user's signed intent. Because `rlp_execute(target, tx_bytes_b64)` is a fully public method and its arguments are just the raw signed Ethereum transaction bytes, anyone who observes a pending `rlp_execute` transaction (in the mempool/chunk before inclusion) can resubmit the identical call as their own transaction, take the `predecessor_account_id` slot, and collect the fee intended for the honest relayer.

### Finding Description
`inner_rlp_execute` computes a `caller_deposit`/fee refund keyed only on `context.predecessor_account_id`: [1](#0-0) 

This is by design meant to let "any relayer safely serve base token transfers from any wallet without additional on-boarding" — the comment explicitly states the fee compensation model is untied to a specific relayer identity: [2](#0-1) 

The signed payload (`tx_bytes_b64`) is user data passed as plain function-call arguments to a public method, not a private/committed value — any account can read a pending `rlp_execute` transaction from the transaction pool, extract `target` and `tx_bytes_b64` verbatim, and submit its own `rlp_execute` call with the same arguments before the original relayer's transaction is included. Because the wallet's nonce-increment/replay-protection is keyed to the signed Ethereum tx's nonce (not to a specific relayer account), the copied call executes successfully exactly as the original would have, and the refund/fee goes to the copier's account instead of the intended relayer: [3](#0-2) 

The contract's own test suite confirms an external caller is compensated purely based on being the successful caller of the contract, with no requirement that the caller be a specific pre-registered relayer: [4](#0-3) 

This is the direct analog of the dYdX incident: a value-bearing operation intended for a specific party (the rescuing team / a specific relayer) is instead capturable by any third party who races to be the one whose transaction lands first — an MEV-style value-extraction opportunity, reachable purely by an unprivileged RPC caller submitting a transaction that mimics a pending one.

### Impact Explanation
Any relayer who does legitimate work brokering an ETH-emulated transfer (paying gas, building/broadcasting the `rlp_execute` transaction) can have their compensation fee stolen by a third party who merely copies the observed pending transaction and gets it included first. This is concrete unauthorized value movement: the fee `NearToken` amount that should go to the honest relayer's account is instead transferred to an attacker's account via `promise_batch_action_transfer`, with the user's/wallet's balance debited exactly as intended but the beneficiary of the fee hijacked. Given `Balance loss ~ fee amount per transaction`, and that this can be repeated systematically against every relayer-fee-bearing `rlp_execute` call network-wide, the aggregate impact is Medium: it constitutes a reliable, repeatable value-diversion primitive against a core Wallet Contract mechanism, directly parallel to the $211K MEV extraction in the dYdX report.

### Likelihood Explanation
Likelihood is high in principle for any attacker running mempool-monitoring tooling similar to standard NEAR MEV/front-running bots: the attack requires only observing a public pending transaction and copying its `target`/`tx_bytes_b64` arguments into a new transaction from the attacker's own account, then getting it included before the original. No special permissions, keys, or validator access are needed — only the ability to submit an unprivileged transaction, which matches the allowed threat model (transaction/contract-call reachable by any signer).

### Recommendation
Bind the relayer-fee refund to an identity committed to by the user's signature rather than to the raw `predecessor_account_id` of whichever account happens to execute the call — e.g., require the signed Ethereum transaction to explicitly designate the intended relayer/fee-recipient account (or a commit-reveal / relayer-registration scheme as already used for the FunctionCall-access-key relayer flow) so that copying the call data does not let an arbitrary third party redirect the fee to itself.

### Proof of Concept
1. Honest relayer `R` observes a user-signed Ethereum transaction (a base-token or ERC-20 transfer with non-zero `fee`) and submits a NEAR transaction calling `wallet.rlp_execute(target, tx_bytes_b64)`, expecting the wallet's fee-refund logic at [5](#0-4)  to pay `fee` to `R`.
2. Attacker `A` observes `R`'s pending transaction in the transaction pool, copies `target` and `tx_bytes_b64` unchanged, and submits `wallet.rlp_execute(target, tx_bytes_b64)` from `A`'s own account with higher priority (e.g., resubmitted earlier/with more favorable gas ordering).
3. `A`'s transaction is admitted first; `inner_rlp_execute` increments the wallet's nonce and executes successfully with `context.predecessor_account_id == A`, so the refund promise sends `fee` to `A` instead of `R`.
4. `R`'s now-duplicate transaction fails (nonce already consumed / transaction replay), and `R` receives no fee despite having originated and broadcast the transfer, while `A` collects it — reproducing the "MEV bot intercepts value meant for the legitimate operation" pattern from the dYdX incident, entirely from an unprivileged transaction submitter's perspective.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
