### Title
Webhook validation trusts the unsigned `X-Shopify-Shop-Domain` header, allowing a captured HMAC-valid webhook to be replayed against a different shop - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts](packages/apps/shopify-api/lib/webhooks/validate.ts))

### Summary
The `isContract()`-style bug class is "a security check is relied upon to guarantee a property, but the property can be forged/decoupled from what was actually verified." The `shopify-app-js` webhook validation pipeline has the same shape of flaw: it validates only the HMAC over the raw body, then unconditionally trusts the `domain` value taken from request headers as the authoritative shop identity, even though that header is not covered by the HMAC.

### Finding Description
`validateFactory` in [1](#0-0)  computes HMAC validity via `validateHmacFromRequestFactory`, which calls `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` — i.e. the HMAC is computed **only over `rawBody`**, per [2](#0-1) . Headers such as `X-Shopify-Shop-Domain`, topic, webhook id, and API version are never part of the signed material.

Once the HMAC check passes, `checkWebhookHeaders`/`checkWebhooksHeaders`/`checkEventsHeaders` simply pull the `domain` header verbatim out of the request and return it as a "valid" field with no cross-check against the signed body or any allow-list, as seen in [3](#0-2)  and [4](#0-3) .

Consumers such as the React Router/Remix webhook authenticate handlers treat this `domain` as trusted shop identity and use it to load the offline session/access token for that shop: [5](#0-4) 
`ensureValidOfflineSession(params, check.domain)` loads/creates a session keyed purely by the unsigned `domain` field: [6](#0-5) 

Because the domain is not bound cryptographically to the body/HMAC, any attacker who can obtain one genuine `{rawBody, hmac}` pair (e.g., by installing the app on their own store/dev shop and capturing a real webhook delivery, since the same `apiSecretKey` is used for all shops of the app) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. The HMAC still validates (it only covers the body), and the app then loads the victim's offline session/access token and invokes the registered webhook handler as if the event legitimately came from the victim shop, with attacker-chosen topic/payload content.

### Impact Explanation
This breaks the tenant isolation the HMAC check is meant to provide: it allows accepted forged Shopify webhook requests where the shop identity is spoofed independent of the signature. Downstream, the app's webhook handler is called with the victim's authenticated `admin` session/access token but attacker-controlled payload and (constrained) topic, enabling cross-tenant confusion — e.g. triggering the app's business logic for one merchant using another (victim) merchant's admin API session, or writing attacker data into the victim's app-side state that is keyed by shop.

### Likelihood Explanation
Exploitability requires only capturing one genuine webhook delivery for a shop the attacker controls (trivial: install the app on a free/dev store and subscribe to any topic) and sending a raw HTTP POST directly to the app's public webhook URL with a modified header — no privileged access, no leaked secrets, no MITM required. This is reachable from an anonymous HTTP request to a public app endpoint.

### Recommendation
Bind the shop/domain claim to the signed data rather than trusting the header value in isolation:
- Cross-validate the `domain` header against the shop associated with the `apiSecretKey`/session actually loaded, or better, use per-shop secrets/session tokens where feasible.
- Alternatively, incorporate the domain (and other identifying headers such as topic/webhook id) into the HMAC computation/verification, or verify webhook `domain` against a previously established/authorized shop-session mapping before granting access to that shop's admin session.
- Add anti-replay protection (e.g., dedupe by `webhookId`/`eventId`, as partially supported by existing fields) to prevent reuse of a captured valid webhook body+HMAC pair altogether.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify delivers a real webhook to the app's endpoint; attacker captures the exact `rawBody` and the `X-Shopify-Hmac-Sha256` value from that request (this is not secret info they need to break — they simply observe their own webhook traffic).
3. Attacker sends a new POST request directly to the app's public webhook endpoint with the identical `rawBody` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `validateFactory` → `validateHmacFromRequestFactory` validates the HMAC successfully (it only checks `rawBody` against `hmac`), per [7](#0-6) .
5. `checkWebhookHeaders` returns `domain: 'victim-shop.myshopify.com'` unchecked, per [8](#0-7) .
6. The webhook authenticate handler calls `ensureValidOfflineSession(params, check.domain)`, loading the victim shop's offline session/access token and invoking the app's webhook callback with that context, per [9](#0-8) .

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

export async function validateHmacString(
  config: ConfigInterface,
  data: string,
  hmac: string,
  format: HashFormat,
) {
  const localHmac = await createSHA256HMAC(config.apiSecretKey, data, format);

  return safeCompare(hmac, localHmac);
}

export function getCurrentTimeInSec() {
  return Math.trunc(Date.now() / 1000);
}

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
