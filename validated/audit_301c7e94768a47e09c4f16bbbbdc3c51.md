### Title
Stale Per-Block Index Cache Not Invalidated by `socialize-debt`, Leading to Mispriced Debt in `liquidate-multi` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` maintains a per-transaction/per-block cache (`index-cache`) of vault borrow/liquidity indexes keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . This cache is populated once via `accrue-and-cache` and re-used for the remainder of the transaction without ever being refreshed [2](#0-1) . However, the underlying vault's index/liquidity-index can be mutated directly and non-time-based by `socialize-debt`, called from within `liquidate`'s bad-debt-socialization path [3](#0-2) . In `liquidate-multi`, which sequentially processes multiple positions in one call via `map call-liquidate` [4](#0-3) , a socialize-debt event triggered by an earlier position leaves the market's cached index for that asset stale for all subsequent positions processed later in the same call, because the cache key does not change (same block timestamp) and nothing forces a re-read.

### Finding Description
The value bound: `index-cache { timestamp: stacks-block-time, aid }` → `{ index, lindex }`, read via `get-cached-indexes`/`accrue-and-cache` and consumed throughout `borrow`, `repay`, `collateral-remove`, and `liquidate` to compute debt valuations (`get-notional-evaluation`, `other-debt-repayable`, `convert-to-scaled-debt`) [5](#0-4) .

The event that invalidates it: a vault's `socialize-debt` function mutates `index`/`lindex`/`principal-scaled`/`total-borrowed` directly, independent of elapsed time, whenever bad debt is written off [6](#0-5) . This is invoked from `v0-4-market.clar`'s liquidation path when a borrower's collateral is exhausted, via `fold socialize-debt-asset` → `vault-socialize-debt` [3](#0-2) . Nowhere does this call path update or invalidate `index-cache` in the market contract.

The later use: `liquidate-multi` sequentially maps `call-liquidate` over a batch of positions within one atomic transaction [4](#0-3) . If an earlier position in the batch shares a debt-asset with a later position and triggers `socialize-debt` (bad-debt write-off), the vault's real index/lindex changes, but the market's `index-cache` for that `{ stacks-block-time, aid }` key still holds the pre-socialization value. All subsequent computations in the batch that call `get-cached-indexes`/`accrue-and-cache` for that asset — e.g. `other-debt-repayable`, `find-and-resolve-asset-value` for debt notional, `convert-to-scaled-debt` — will use the stale index, producing incorrect USD debt valuations for later positions in the same batch call.

### Impact Explanation
Mispriced debt during liquidation batch processing can cause the protocol to seize incorrect collateral amounts or under/over-repay debt relative to actual on-chain state, directly affecting user funds at rest during liquidation (temporary freezing/incorrect settlement of position value, and potential theft of collateral beyond what is owed) — this lands in the High/Critical impact category (temporary freezing of funds / theft of funds via a bug in this code's pricing logic), not an oracle-supplied inaccuracy since the source of staleness is Zest's own caching mechanism.

### Likelihood Explanation
This requires: (1) at least two positions in a single `liquidate-multi` call sharing the same debt asset, (2) the first position to trigger bad-debt socialization (`no-collateral-left` = true) which mutates vault index/lindex directly, and (3) all within the same block/transaction so the `{ stacks-block-time, aid }` cache key is unchanged. Bad-debt socialization is a normal, expected event during liquidations of undercollateralized positions, and any liquidator (or MEV bot) constructing a `liquidate-multi` batch touching multiple borrowers with the same debt asset can trigger this ordering naturally or deliberately. This is plausible but requires specific batch composition, so likelihood is moderate.

### Recommendation
Invalidate or refresh the market's `index-cache` entry for an asset whenever a vault mutates its index/lindex outside of the standard time-based `accrue` path (e.g., after `vault-socialize-debt` returns, call `map-delete`/`map-set` on `index-cache` for that `{ stacks-block-time, aid }` key with freshly-read vault state), or have `socialize-debt-asset`/`vault-socialize-debt` explicitly re-prime the cache via `accrue-and-cache` immediately after mutating vault state, before any later `get-cached-indexes` reads in the same transaction.

### Proof of Concept
Conceptual sequence within one `liquidate-multi` transaction:
1. Position A (borrower Alice, debt asset USDC) and Position B (borrower Bob, debt asset USDC) are both included in a `liquidate-multi` batch [4](#0-3) .
2. `call-liquidate` processes Alice first: her collateral is fully seized and debt fully written off, triggering `no-collateral-left` → `fold socialize-debt-asset` → `vault-socialize-debt` on the USDC vault, which directly `var-set`s `index`/`lindex`/`principal-scaled`/`total-borrowed` [6](#0-5) . The market's `index-cache` map for `{ stacks-block-time, USDC-aid }` is not touched.
3. `call-liquidate` processes Bob next in the same transaction: it calls `get-cached-indexes`/`accrue-and-cache` for the USDC asset id, hitting the now-stale cache entry from before Alice's socialization [2](#0-1) .
4. Bob's `other-debt-repayable`, debt notional value, and `convert-to-scaled-debt` calculations are computed against the stale index rather than the true post-socialization vault index, causing incorrect collateral-to-debt settlement for Bob's liquidation.

Note: full confirmation that `socialize-debt-asset`/`vault-socialize-debt` never re-primes the cache could not be completely traced in this pass due to truncated tool access on the final iteration; the causal chain is established from the cited `index-cache` design and the `socialize-debt` mutation code, but a live trace/test run is recommended to confirm the exact numeric impact.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
