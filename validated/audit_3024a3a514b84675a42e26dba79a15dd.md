### Title
Untested custom cross-platform math wrapper (`Maths`/`StrictMathWrapper`/`MathWrapper`) underlies reward, exchange, and resource accounting with no dedicated unit tests - ([File: common/src/main/java/org/tron/common/math/Maths.java])

### Summary
java-tron ships several hand-rolled, custom arithmetic utility classes—`Maths`, `StrictMathWrapper`, and the platform-specific `MathWrapper` (separate `arm`/`x86` implementations)—that reimplement `java.lang.Math` semantics (`addExact`, `multiplyExact`, `subtractExact`, `pow`, `floorDiv`, `round`, etc.) for "cross-platform consistency." These are consumed directly by consensus-critical accounting code such as `MortgageService.computeReward`/`getOldReward` (witness/voter reward payout) and exchange balance math (`ExchangeCapsule`, `SafeExchangeProcessor`), yet none of these math utility classes have a dedicated unit test file, mirroring the exact bug class described in the external report (untested custom SafeMath-style library backing financial logic).

### Finding Description
`Maths` is a dispatcher that routes to either `StrictMathWrapper` or the platform-dependent `MathWrapper` based on a `useStrictMath`/`disableJavaLangMath` flag: [1](#0-0) [2](#0-1) 

There are two independent `MathWrapper` implementations, one for `arm` and one for `x86` platforms, each hand-reimplementing the same `addExact`/`multiplyExact`/`subtractExact`/`floorDiv`/`min`/`max` logic: [3](#0-2) 

I found no test files matching `MathsTest`, `MathWrapperTest`, or `StrictMathWrapperTest` in the repository, meaning these dispatch/platform classes—despite backing overflow-sensitive financial math—are not directly unit tested; only downstream consumers like `SafeExchangeProcessor`/`ExchangeProcessor` have dedicated tests (`ExchangeProcessorTest`, `ExchangeCapsuleTest`), while `Maths`/`MathWrapper` themselves and `MortgageService`'s reward computation have none.

`MortgageService.computeReward` (old reward algorithm path) performs floating-point reward distribution using raw Java `double` arithmetic (not even routed through the wrapper), which is untested and lossy by construction: [4](#0-3) 

This same class calls into `Maths.min` for old/new reward algorithm cutover selection, and `getOldReward` recurses per-cycle using the untested double-based `computeReward(cycle, votes)`: [5](#0-4) [6](#0-5) 

There is no `MortgageServiceTest` in the repo either (grep found zero matches), so the reward payout math that runs on every maintenance-cycle reward withdrawal (`withdrawReward`/`queryReward`, reachable from any account's `WithdrawBalanceContract`/TVM `withdrawReward` native call) has no dedicated regression coverage tied to the underlying math primitives it depends on.

### Impact Explanation
If `Maths`, `StrictMathWrapper`, or either platform `MathWrapper` is modified (e.g., during a refactor, a build-flag change, or a future contribution) and a subtle bug is introduced (e.g., a wrong overflow check, an off-by-one in `floorDiv`, or arm/x86 `pow` divergence), it would silently corrupt witness/voter reward payouts or exchange balances across all nodes without any test catching it—since no isolated unit test exercises these primitives directly. Because rewards and exchange balances are consensus state, an arm vs. x86 divergence in these wrappers (the entire reason `StrictMathWrapper` was introduced) could also produce different results on different node architectures, risking consensus divergence. This is accounting corruption / potential consensus divergence, not merely a style nit.

### Likelihood Explanation
Likelihood is moderate: the code paths (`MortgageService.withdrawReward`, `ExchangeCapsule.transaction`) are triggered on every ordinary reward withdrawal and exchange transaction, i.e., extremely frequently, by any account via broadcast transactions or TVM calls. The risk materializes only when the untested math utilities are modified or run under different platform builds, not from a single malicious transaction. There is currently no automated regression test that would catch a break introduced in `Maths`/`MathWrapper`/`StrictMathWrapper` directly, which is the essence of the reported bug class.

### Recommendation
Add dedicated unit tests directly for `Maths`, `StrictMathWrapper`, and both `arm`/`x86` `MathWrapper` implementations covering overflow boundaries (`Long.MAX_VALUE`/`MIN_VALUE`), `pow`/`floorDiv` edge cases, and cross-implementation parity between `StrictMathWrapper` and `MathWrapper`. Additionally add a `MortgageServiceTest` covering `computeReward`/`getOldReward` boundary conditions (zero vote, max reward, cycle boundaries) so future changes to the underlying math primitives or reward logic are caught by CI rather than relying solely on higher-level actuator tests.

### Proof of Concept
Not applicable as a live exploit—this finding is about a test-coverage gap, not an directly triggerable vulnerability. The reachable path for illustration: any account calling `withdrawReward`/`WithdrawBalanceContract` invokes `MortgageService.withdrawReward` → `computeReward(beginCycle, endCycle, accountCapsule)` → `getOldReward` → `computeReward(cycle, votes)` using raw double math [7](#0-6) , and any exchange transaction invokes `ExchangeCapsule.transaction` → `SafeExchangeProcessor`/`ExchangeProcessor` using `StrictMathWrapper` [8](#0-7) ; a regression in the untested shared math primitives would silently corrupt outcomes for all such calls with no unit test to detect it.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
