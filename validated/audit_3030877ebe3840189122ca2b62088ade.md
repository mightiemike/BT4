### Title
Witness can set brokerage (reward-share fee) to 100% via `UpdateBrokerageContract`, rugging all future delegation rewards from voters - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
`UpdateBrokerageActuator` lets any witness account change its `brokerage` (the percentage of a witness's block/vote reward that is diverted to the witness before the remainder is split among voters) up to `100` at any time, with no check against a caller-expected prior value and no rate limit beyond the natural maintenance-cycle boundary. This mirrors the `DropEngineV2.setPrimarySaleFeeBps` bug class: an owner/operator role (here, a witness account, which any funded account can freely acquire by creating a witness) can unilaterally raise a "fee" to its maximum (100%) and have it silently applied to value that other unprivileged users (voters/delegators) are counting on receiving.

### Finding Description
`UpdateBrokerageActuator.execute()` calls `delegationStore.setBrokerage(ownerAddress, brokerage)`, which stores the new brokerage at a special "pending" cycle key (`cycle = -1`): [1](#0-0) 

Validation only bounds `brokerage` between 0 and `ActuatorConstant.ONE_HUNDRED` (100) — there is no comparison to what the caller (or any dependent voter) expected the current/previous value to be: [2](#0-1) 

At each maintenance cycle rollover, `MaintenanceManager.doMaintenance()` reads this pending value and commits it verbatim as the brokerage for the *next* cycle, for every witness, without any additional sanity check: [3](#0-2) 

That committed per-cycle brokerage is then used by `MortgageService.payReward()` to skim `brokerageRate * value` off the top of every reward before crediting the remainder to voters: [4](#0-3) 

Because the write path is a single unprivileged transaction (`UpdateBrokerageContract`, reachable via `Wallet.createTransactionCapsule` / gRPC `UpdateBrokerage` / `UpdateBrokerageServlet`) and the read/commit path blindly trusts whatever value is currently pending at the moment `doMaintenance()` executes, a witness can submit a brokerage-to-100 transaction shortly before a maintenance interval elapses. Voters have no on-chain signal distinguishing "brokerage about to spike" from routine operation, and their existing votes for that witness are already locked into the reward-accrual mechanics for the next cycle unless they proactively re-vote in time.

### Impact Explanation
Setting brokerage to 100% causes the witness to capture the *entire* reward for a full cycle that would otherwise be distributed to voters/delegators — direct fund diversion analogous to `revenueRecipient` being rugged in the original report. Because reward accounting (`addReward`/`accumulateWitnessVi` in `DelegationStore`) and payout math in `MortgageService` unconditionally trust the committed brokerage, this is a real, on-chain accounting corruption of voter rewards, not merely a griefing/DoS issue.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires an account to be an active/registered witness (attainable by anyone paying the witness-creation fee, so not a truly "privileged" admin role), and requires timing the `UpdateBrokerageContract` transaction shortly before a maintenance boundary so voters have insufficient time to react by moving their votes elsewhere.

### Recommendation
- Add an explicit, bounded step/cool-down for brokerage changes (e.g., cap the maximum delta per update, or require multiple maintenance cycles before a large increase takes effect), so voters have a guaranteed reaction window.
- Consider lowering the practical upper bound well below 100% (as recommended in the original report for `primarySaleFeeBps`) or emitting an explicit, queryable "pending brokerage change" event/field so wallets/voters can be warned before the change is committed in `MaintenanceManager.doMaintenance()`.
- Optionally let `UpdateBrokerageContract` carry an "expected current brokerage" field and reject the update if it no longer matches, mirroring the report's suggested fix for `configureSequence`.

### Proof of Concept
1. Attacker funds an account and issues `CreateWitnessContract` to become a witness with default brokerage 20 (`DelegationStore.DEFAULT_BROKERAGE`), attracting votes. [5](#0-4) 
2. Shortly before the next maintenance interval elapses, attacker broadcasts `UpdateBrokerageContract{ownerAddress: attacker, brokerage: 100}` via the `UpdateBrokerage` RPC/HTTP endpoint. [6](#0-5) 
3. `UpdateBrokerageActuator.execute()` writes brokerage=100 to the pending (`cycle=-1`) key, passing validation because 100 ≤ `ActuatorConstant.ONE_HUNDRED`. [7](#0-6) 
4. At the next `doMaintenance()` call, this pending value is committed as the brokerage for `nextCycle` for the attacker's witness. [8](#0-7) 
5. For the entirety of that cycle, `MortgageService.payReward()` now diverts 100% of the witness's reward to the attacker, and voters who had already cast/held votes for that cycle receive 0. [4](#0-3)

    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
