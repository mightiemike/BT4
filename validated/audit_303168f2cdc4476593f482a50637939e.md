Based on the code, this is **not exploitable** — the OR-merge logic does not bypass the privilege escalation check; in fact it is specifically designed to prevent this exact attack.

Looking at `prepare_next_cpi_instruction` in `program-runtime/src/invoke_context.rs`, the function processes duplicated `AccountMeta` entries in two passes:

**Pass 1 (building `instruction_accounts`)**: When an account is seen for the first time, an `InstructionAccount` is created at some position (the "canonical" slot recorded in `transaction_callee_map`). When the *same* account appears again later with different flags, the code doesn't just push a fresh copy — it mutates the **canonical** entry in place via `instruction_account.set_is_signer(... || account_meta.is_signer)` / `set_is_writable(...)`, then clones that already-merged value for the duplicate slot. [1](#0-0) 

This means that regardless of which duplicate entry carries the elevated `is_signer`/`is_writable` flags, the canonical entry ends up holding the OR (worst-case/highest) of all the flags across every duplicate of that pubkey in the instruction.

**Pass 2 (privilege check)**: The loop only performs the escalation check for the canonical index (`current_index == index_in_callee`), but by this point that canonical entry already carries the merged (worst-case) flags from pass 1: [2](#0-1) 

Specifically:
```
if instruction_account.is_writable() && !caller_instruction_account.is_writable() {
    return Err(InstructionError::PrivilegeEscalation);
}
if instruction_account.is_signer() && !(caller_instruction_account.is_signer() || signers.contains(account_key)) {
    return Err(InstructionError::PrivilegeEscalation);
}
```
Since `instruction_account` here is the canonical, already-merged entry, this check is evaluated against the *union* of all duplicate metas' flags — not just the first occurrence's flags. In the attacker's scenario (X passed as `(signer:false,writable:false)` then `(signer:true,writable:true)`), the canonical entry for X ends up with `is_writable=true`/`is_signer=true` regardless of ordering, and since the caller (top-level transaction) declared X as `is_writable=false`, the check at line 447 fires and returns `InstructionError::PrivilegeEscalation` — the CPI is rejected before it can execute.

For non-canonical duplicate slots (`current_index != index_in_callee`), the code explicitly skips the check ("This account is repeated, so there is no need to check for permissions") because those slots can never carry higher privilege than the canonical slot that was already checked — they were populated via the same OR-merge. [3](#0-2) 

This exact duplicate-account scenario is covered by the existing `test_duplicated_accounts` unit test, which builds an instruction with repeated `AccountMeta`s and verifies the deduplication/index mapping behavior. [4](#0-3)
