### Title
Free asset extraction via rounding-to-zero in exact-match maker/taker branch of `matchSingleOrder` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the token amount a maker receives (`makerBuyTokenQuantityReceive`) via an integer division (`MarketUtils.multiplyAndDivide`) that rounds down. In two of the three branches of this method, the code explicitly checks for a zero result and aborts the match to avoid giving one side tokens for free. The third branch — the "taker == maker" exact-match case — omits this check, allowing a taker to receive a maker's entire remaining sell-token balance while the taker's own debit (`makerBuyTokenQuantityReceive`) rounds down to zero, i.e., the taker pays nothing.

### Finding Description
In `matchSingleOrder`, three branches handle order matching depending on how `takerBuyTokenQuantityRemain` compares to `makerOrderCapsule.getSellTokenQuantityRemain()`:

- taker < maker (lines 440-452): no zero-quantity risk for maker's receive value here (`makerBuyTokenQuantityReceive` is directly assigned from taker's remain, not computed via a rounding division).
- taker > maker (lines 453-483): `makerBuyTokenQuantityReceive` is computed via `MarketUtils.multiplyAndDivide` and explicitly checked: [1](#0-0) 
  If it rounds to zero, the function returns early and returns the maker's remaining sell tokens back to the maker without ever crediting the taker — preventing a free transfer.
- taker == maker (lines 418-439): the *exact same* rounding computation is used for `makerBuyTokenQuantityReceive`, but with **no zero check**: [2](#0-1) 
  Here `takerBuyTokenQuantityReceive` is unconditionally set to the maker's *full* remaining sell quantity, while `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive`. If `makerBuyTokenQuantityReceive` rounds down to `0` (which happens whenever `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`, per `MarketUtils.multiplyAndDivide`'s floor division), the taker's sell-token remainder is left unchanged (nothing is deducted), yet the taker still receives the maker's entire remaining sell-token balance via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` at line 489.

The rounding division used is: [3](#0-2) 

This is structurally the same bug class as the reported "denormalize" rounding issue: a division that truncates toward zero is used to compute the amount the protocol should debit from the attacker, while the amount credited to the attacker is computed independently (or fixed to a larger value) and is not tied to the (zero-rounded) debit. Repeated exploitation lets an attacker drain a targeted maker order's escrowed tokens without paying the required consideration.

### Impact Explanation
An attacker who controls both a taker order (crafted via `MarketSellAssetContract`, broadcast as a normal transaction) and, or targeting any existing maker order with a favorable price ratio and small remaining quantity, can trigger the taker==maker branch such that `makerBuyTokenQuantityReceive` rounds to zero. This lets the attacker receive the full remaining sell-token quantity of the maker's order for free while their own order's remaining sell quantity is not reduced, allowing repeated exploitation against other orders and pool draining — an asset/accounting corruption reachable purely through broadcast transactions (`MarketSellAssetActuator`), matching the "asset or accounting corruption" acceptance criteria.

### Likelihood Explanation
The exploit only requires crafting/selecting maker and taker orders whose sell/buy ratios satisfy `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity` while `takerBuyTokenQuantityRemain` exactly equals `makerSellRemainQuantity` (the taker==maker branch condition at line 418). Both quantities are attacker-controlled via `MarketSellAssetContract` parameters (`sellTokenQuantity`, `buyTokenQuantity`), and market orders with arbitrary small remainders are achievable through partial fills, making this reachable by any account with no special privileges.

### Recommendation
Add the same zero-check guard used in the taker>maker branch to the taker==maker branch: if `makerBuyTokenQuantityReceive` computed via `MarketUtils.multiplyAndDivide` is `0`, do not credit the taker with the maker's full remaining sell quantity — either round up (ceiling division) so the maker never yields tokens for a zero debit, or abort/return the maker's remaining sell tokens as done in the other rounding-to-zero paths.

### Proof of Concept
1. Create a maker sell order (`sellTokenQuantity = S`, `buyTokenQuantity = B`) and partially fill it so that `makerSellRemainQuantity = R` remains, chosen such that `R * B < S` (so `multiplyAndDivide(R, B, S)` floors to 0).
2. Submit a taker `MarketSellAssetContract` whose sell/buy ratio makes `takerBuyTokenQuantityRemain` (computed via `MarketUtils.multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity)`) exactly equal to `R`, hitting the `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` branch at [4](#0-3) .
3. Observe: `makerBuyTokenQuantityReceive == 0` (per the floor-division), yet `takerBuyTokenQuantityReceive = R` is credited to the taker at line 489, while `takerSellTokenLeft` stays unchanged (since 0 was subtracted), so the taker's own order is not consumed and can be reused to repeat the attack against other maker orders.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
