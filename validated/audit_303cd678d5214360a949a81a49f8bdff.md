### Title
Wallet Contract pays relayer fee for emulated base-token/ERC-20 transfers unconditionally, before the underlying action is known to succeed - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Chainlink upkeep bug describes a pattern where a service fee (upkeep fee) is charged to an account for a triggered action regardless of whether the triggered action actually succeeds, because the fee-charging decision is made before/independently of the actual execution outcome. The `near-wallet-contract` (NEAR's Ethereum-emulation wallet) contains an analogous pattern in `inner_rlp_execute`: a relayer-compensation transfer is dispatched based only on the *parsed* transaction fee field, unconditionally, before the underlying emulated action (the actual base-token or ERC-20 transfer) has executed and is known to succeed.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , once an Ethereum transaction is parsed as an `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the contract immediately creates a `promise_batch_create`/`promise_batch_action_transfer` to pay the relayer (`predecessor_account_id`) that fee — this happens as soon as parsing succeeds, in the `Ok((action, transaction_kind))` branch, *before* the actual transfer/ERC-20 action (`action_to_promise(target, action)`) is dispatched or resolved [2](#0-1) . The refund promise to the relayer is a separate, independently-scheduled promise from the main action promise, rather than being conditioned on the main action's success via the `rlp_execute_callback`. That callback only handles refunding the *caller's deposit* on failure [3](#0-2)  — it does not claw back the relayer fee already paid.

This mirrors the audit finding's root cause: a fee payment that is triggered by the *presence of a fee-bearing signal* (checkUpkeep returning true / a parsed fee > 0) rather than by *confirmed successful completion* of the underlying operation, allowing fee extraction on every attempt regardless of outcome.

### Impact Explanation
Because the relayer fee transfer is dispatched independently of whether the main emulated action succeeds, a relayer (or any actor who can get a transaction with this shape processed, e.g., replaying/resubmitting a transaction that is designed to eventually fail on the receiver's shard) can repeatedly extract the fee from the wallet contract's balance even when the intended base-token/ERC-20 transfer never completes. This is a fee/value-extraction bug: NEAR tokens move out of the user's wallet contract account to the relayer without the corresponding service (a successful transfer) being rendered, which is a concrete unauthorized value movement out of the wallet-contract account.

### Likelihood Explanation
Reachable directly by any account (acting as "relayer") calling `rlp_execute` with a base64 RLP-encoded Ethereum transaction targeting the wallet contract — this is an unprivileged, permissionless entry point reachable from a single transaction/RPC call, matching the constraint that only a signer/RPC caller reachable path counts. The nonce-increment logic complicates naive repeated replay of the exact same transaction (nonce advances on success paths), but distinct fee-bearing transactions that are crafted to fail downstream (e.g., targeting a receiver that will reject the transfer, insufficient storage deposit on an ERC-20 receiver, etc.) can still trigger fee payment before the failure is observed, each with a fresh nonce.

### Recommendation
Move the relayer fee-refund promise to be part of the success branch of `rlp_execute_callback` (or chain it after the main action promise resolves successfully) instead of dispatching it unconditionally in `inner_rlp_execute` before the main action is known to succeed. The fee should only be paid to the relayer once the emulated transfer/ERC-20 call has been confirmed successful via `PromiseResult::Successful`.

### Proof of Concept
Not independently executable from the available indexed context — a full PoC would require constructing a signed Ethereum-emulation transaction (`EOABaseTokenTransfer`/`ERC20Transfer`) with a non-zero `fee` field, targeting a receiver crafted to fail (e.g., a nonexistent account or a contract call that reverts), and observing via `rlp_execute` that the relayer receives the `fee` transfer while `rlp_execute_callback`'s `PromiseResult::Failed` branch fires for the main action, confirming the fee is paid despite failure. This should be validated in a background session with access to run the `near-wallet-contract` integration test harness (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs`) to confirm the exact promise ordering and outcome; I was not able to fully trace the remainder of `inner_rlp_execute` (lines 411+) and `action_to_promise` due to tool/context limits in this session, so the precise promise-chaining guarantees should be re-verified.

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }
