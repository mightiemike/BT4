### Title
ValidateMultiSign precompile allows duplicate weight accumulation for a single signer via ECDSA-malleated signatures of the same recoveredAddr - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` decodes the `signatures` array and, for each entry, recovers the signer address, then attempts to prevent double-counting weight for repeated signatures via: [1](#0-0) 

The dedup check is:
```
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
The `continue` (skip) only fires when the **exact byte-for-byte merged value** (`recoveredAddr || rawSignatureBytes`) has already been seen — i.e., an exact duplicate signature. If `recoveredAddr` has already appeared but the *raw signature bytes differ* (same signer, different signature encoding), the loop does **not** skip; it falls through and adds `weight` for that `recoveredAddr` again. `ByteArray.matrixContains` performs plain `Arrays.equals` comparison, confirmed at `common/src/main/java/org/tron/common/utils/ByteArray.java:189-196`, and does not deduplicate by address alone.

Because ECDSA over secp256k1 is malleable, a single private key can produce two distinct valid signatures for the same message hash `(r, s, v)` and `(r, n-s, v')` that both recover to the identical `recoveredAddr`. An attacker controlling one key with weight `W` in a `Permission` can submit both malleated signatures in the `signatures` array. The exact-byte dedup check will not match (different `s`/`v`), `TransactionCapsule.getWeight` returns `W` both times, and `totalWeight` accumulates `2*W` (or more with additional malleated variants, bounded by `MAX_SIZE`), potentially crossing `permission.getThreshold()` with only one real distinct signer.

The attacker entrypoint is a real, unprivileged smart contract call: `TriggerSmartContract -> Program.callToPrecompiledAddress -> ValidateMultiSign.execute`, with attacker-controlled `signatures` bytes array content, requiring no special privilege beyond deploying/calling a contract that invokes the `validatemultisign` precompile address.

### Impact Explanation
If exploitable, this breaks the core invariant that `ValidateMultiSign` should only return "true" (authorization granted) when the accumulated weight of **distinct** signers meets the account's permission threshold. An attacker holding a single key (with sub-threshold weight) could forge on-chain authorization for actions gated by TVM-level multisig checks (e.g. contract logic that relies on `validatemultisign`/`ValidateMultiSign` to gate value transfers or privileged operations), without collecting the required number of distinct co-signers.

### Likelihood Explanation
Exploitability hinges entirely on whether `recoverAddrBySign` (used inside `ValidateMultiSign.execute`) accepts non-canonical/malleated `s` values (i.e., does not enforce low-`s`/canonical signature form before ECDSA public-key recovery). I was not able to confirm the implementation of `recoverAddrBySign` and the underlying `ECKey` signature-to-address recovery path within the available tool budget, so I cannot conclusively verify that malleated signatures are accepted rather than rejected upstream. If canonical-form (`low-s`) enforcement exists elsewhere in the signature-recovery pipeline, the specific ECDSA-malleability vector would be blocked, though the dedup logic itself (exact-byte match instead of address match) remains structurally unsound and could still be triggered by any other means of producing two byte-distinct signatures recovering to the same address that the code doesn't validate against.

### Recommendation
Change the dedup logic in `ValidateMultiSign.execute` to skip weight accumulation whenever `recoveredAddr` has already been counted, regardless of the exact signature bytes — i.e., `continue` immediately once `ByteArray.matrixContains(executedSignList, recoveredAddr)` is true, rather than only when the full merged byte sequence matches. Track weight per unique `recoveredAddr`, not per unique signature encoding.

          .setWeight(1).build())
      .build();
  toAccount.updatePermissions(toAccount.getPermissionById(0), null,
      Collections.singletonList(activePermission));
  dbManager.getAccountStore().put(key.getAddress(), toAccount);

  byte[] data = Sha256Hash.hash(CommonParameter.getInstance().isECKeyCryptoEngine(), longData);
  byte[] merged = ByteUtil.merge(key.getAddress(), ByteArray.fromInt(2), data);
  byte[] toSign = Sha256Hash.hash(CommonParameter.getInstance().isECKeyCryptoEngine(), merged);

  ECKey.ECDSASignature sig = key1.sign(toSign);
  ECKey.ECDSASignature malleated = new ECKey.ECDSASignature(
      sig.r, ECKey.CURVE.getN().subtract(sig.s)).toCanonicalised(); // flips s
  // recompute recovery id 'v' for malleated signature so it still recovers to key1's address

  List<Object> signs = new ArrayList<>();
  signs.add(Hex.toHexString(sig.toByteArray()));
  signs.add(Hex.toHexString(malleated.toByteArray()));

  // Assert: with only ONE distinct signer (key1, weight 1) but threshold 2,
  // the vulnerable dedup logic would still return DataWord.ONE() (bypass),
  // whereas the invariant requires DataWord.ZERO() (insufficient distinct weight).
  Assert.assertArrayEquals(
      validateMultiSign(StringUtil.encode58Check(key.getAddress()), 2, data, signs).getValue(),
      DataWord.ZERO().getData()); // this assertion should FAIL if the bug is present
}

Expected result if vulnerable: the assertion fails because `totalWeight` reaches 2 (threshold met) from a single distinct signer, confirming the bypass. Note: constructing a valid malleated signature requires recomputing the correct recovery `v` bit for `(r, n-s)`; this is standard secp256k1 malleability math and should be validated against whichever `recoverAddrBySign`/`ECKey` recovery routine is actually invoked, which I could not fully inspect in this session.
