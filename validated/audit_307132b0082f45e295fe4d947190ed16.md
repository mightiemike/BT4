### Title
Merchant custom app admin authentication trusts an unauthenticated `shop` query parameter to select the target store for the app's static Admin API access token - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts])

### Summary
For "merchant custom apps" (`AppDistribution.ShopifyAdmin`, non-embedded, no session tokens), `getSessionTokenContext` reads `shop` directly from the request's URL query string with no signature or identity check, and this value flows straight into `MerchantCustomAuth.authenticate`, which builds a `Session` for that shop and pairs it with the app's single statically-configured `adminApiAccessToken`. This mirrors the reported `Hypervisor.deposit` bug class: a security-sensitive parameter (`from`/`to` in the original report, `shop` here) is taken from caller-supplied input instead of being derived from a verified/authenticated identity.

### Finding Description
When `config.isEmbeddedApp` is `false` and there is no session-token header, `getSessionTokenContext` falls back to:
```ts
const url = new URL(request.url);
const shop = url.searchParams.get('shop')!;
...
return {shop, sessionId, payload: undefined, sessionToken};
``` [1](#0-0) 

This `shop` is passed unchanged into the authentication strategy. For merchant custom apps, `validateShopAndHostParams` — the only gate applied before this — merely checks the `shop` string is a syntactically valid `*.myshopify.com` domain (`api.utils.sanitizeShop`); it never compares it to any expected/pre-configured shop: [2](#0-1) 
Moreover, `validateShopAndHostParams` only runs its checks when `config.isEmbeddedApp` is true, and merchant custom apps are explicitly configured with `isEmbeddedApp: false`, so for this distribution the `shop` param isn't even format-validated at this step.

The strategy `MerchantCustomAuth.authenticate` then builds the session solely from this caller-controlled `shop`:
```ts
const {shop} = sessionContext;
const session = this.api.session.customAppSession(shop);
return session;
``` [3](#0-2) 

`customAppSession` only re-validates the domain shape, not ownership: [4](#0-3) 

This session (with `session.shop` set to the attacker-chosen value) is then used to build the Admin GraphQL client, which authenticates using the app's single configured `adminApiAccessToken` (a static secret set once in `shopifyApp({..., adminApiAccessToken, distribution: AppDistribution.ShopifyAdmin})`) and issues requests to `https://{session.shop}/admin/api/.../graphql.json`: [5](#0-4) [6](#0-5) 

There is no check anywhere in this path that the `shop` parameter matches the one shop the app was actually installed/configured for — exactly analogous to `Hypervisor.deposit` never checking that `from == msg.sender`.

### Impact Explanation
An anonymous requester can hit the app's admin route with an arbitrary `?shop=<any-myshopify-domain>` value. The app will then send an authenticated Admin API request (carrying its real, secret `adminApiAccessToken`) to a store the caller chose, not the store the token was intended for. At minimum this is a confused-deputy issue that leaks the existence/validity of the app's access token to attacker-chosen target requests and can be used to probe/fingerprint or trigger side effects against arbitrary shops using the app's credentials, without any actor-level authorization check. It also breaks the core security invariant of merchant custom apps (single-tenant, access-token bound to one specific store) since the tenant is now caller-selectable.

### Likelihood Explanation
Any unauthenticated actor who can send an HTTP request to the app's `authenticate.admin` route (which is the app's normal entry point, reachable by simply visiting the app URL with a `shop` query param) can trigger this — no privileged access, secrets, or MITM position required. The `distribution: AppDistribution.ShopifyAdmin` / merchant-custom-app pathway is exactly the code path exercised, and there is no HMAC, session token, or host-comparison check gating the `shop` value in this branch, as confirmed by `validateShopAndHostParams` only running for `isEmbeddedApp: true`.

### Recommendation
For the `AppDistribution.ShopifyAdmin` (merchant custom app) strategy, do not derive the session `shop` from an unauthenticated request parameter. Instead, bind the session to a single shop determined by trusted configuration (e.g. a `shop`/`hostName` value fixed in `shopifyApp()` config, or validated against it), and reject/redirect any request whose `shop` query parameter doesn't match that configured value, mirroring how `sanitizeShop`/HMAC/session-token checks gate the `shop` value on the other (embedded/OAuth) code paths.

### Proof of Concept
1. Deploy a merchant custom app with `distribution: AppDistribution.ShopifyAdmin`, `isEmbeddedApp: false`, and `adminApiAccessToken: 'shpat_<real-secret-for-shop-A>'`.
2. As an anonymous user, request `GET https://app.example.com/app?shop=shop-b.myshopify.com` (any syntactically valid `*.myshopify.com` value).
3. Observe `getSessionTokenContext` returns `{shop: 'shop-b.myshopify.com', ...}` [1](#0-0) , `MerchantCustomAuth.authenticate` builds `customAppSession('shop-b.myshopify.com')` [3](#0-2) , and any subsequent `admin.graphql(...)` call sends the app's static `X-Shopify-Access-Token` (belonging to shop A) to `https://shop-b.myshopify.com/admin/api/.../graphql.json` — a request the operator of shop A's app never intended and that is fully controlled by the requester's `shop` parameter.

export function customAppSession(config: ConfigInterface) {

      state: '',
