### Title
Hardcoded, non-adaptive `CLEAN_INTERVAL`/`SHRINK_INTERVAL` in `AccountsBackgroundService` ignores configurable snapshot cadence and slot timing - (File: `runtime/src/accounts_background_service.rs`)

### Summary
`AccountsBackgroundService`'s main loop decides when to clean and shrink the accounts store using two hardcoded, wall-clock `Duration` constants, `CLEAN_INTERVAL` (50s) and `SHRINK_INTERVAL` (1s), which are baked in with an assumption of a fixed slot time and a fixed default incremental-snapshot cadence. [1](#0-0)  This mirrors the TWAP oracle finding: a single fixed "update period" constant is applied uniformly regardless of the actual, configurable cadence of the system it is meant to track, so it silently becomes wrong when that external cadence differs from the assumption baked into the constant.

### Finding Description
The comment directly next to `CLEAN_INTERVAL` states the intent: *"Set the clean interval duration to be approximately how long before the next incremental snapshot request is received, plus some buffer. The default incremental snapshot interval is 100 slots, which ends up being 40 seconds plus buffer."* [2](#0-1)  This derivation assumes both a fixed ~400ms slot time and the *default* incremental snapshot interval of 100 slots. However, the incremental (and full) snapshot interval is operator-configurable via CLI flags and `SnapshotConfig`, independent of this hardcoded constant. [3](#0-2) 

In the main loop, `should_clean` is computed purely from elapsed wall-clock time versus this fixed constant, not from the actual configured snapshot interval or from slot-processing rate:
```
let duration_since_previous_clean = previous_clean_time.elapsed();
let should_clean = duration_since_previous_clean > CLEAN_INTERVAL;
``` [4](#0-3)  The same time-only gating is used for shrink via `SHRINK_INTERVAL`: [5](#0-4) 

Because `CLEAN_INTERVAL`/`SHRINK_INTERVAL` cannot be changed to match the operator's actual snapshot interval or actual observed slot-processing speed, the same problem class as the TWAP report applies: the "update period" (here, the clean/shrink cadence) does not adapt to the differing "volatility"/pace of the system component it interacts with (snapshot cadence and slot production rate). When an operator configures a much larger incremental-snapshot interval (or the cluster is running with different slot timing, e.g., during catch-up where many slots are replayed much faster than 400ms/slot in wall-clock terms), the fixed 50s window no longer bears the intended relationship to "the time before the next incremental snapshot." In fast-slot-processing regimes, many more roots and much more dirty-store data can accumulate within a single fixed 50s window than the constant was designed for, since accumulation is a function of slot count, not wall-clock time.

The `flush_accounts_cache`/`clean_accounts` calls gated by `should_clean` are exactly the "cache flush/clean/purge" surface named in scope, and `shrink_candidate_slots`/`shrink_ancient_slots` gated by `should_shrink` are the "shrink" surface. [6](#0-5) 

### Impact Explanation
Because cleaning and shrinking only run based on a fixed wall-clock timer instead of scaling with the actual snapshot cadence or replay/slot-processing rate, the accounts write cache and account storages (`dirty_stores`) can grow disproportionately between clean/shrink passes whenever slots are processed much faster than the ~400ms assumption baked into `CLEAN_INTERVAL` (e.g., during replay/catch-up bursts, or with a differently-configured incremental snapshot interval). This produces disproportionate storage growth and larger, spikier CPU/I/O cost when the delayed clean/shrink eventually executes, since it must now process a much larger backlog of dirty stores and cached roots than the constant was designed to bound. This falls within the "disproportionate storage and CPU cost" acceptance category for this analog, as an unprivileged-user-triggerable (via ordinary transaction load driving fast slot/account churn) accounts-db cache/clean/shrink cadence defect, not a validator/operator role issue.

### Likelihood Explanation
This is triggerable purely by variance in ordinary chain operation, not any privileged action: catch-up/replay bursts (temporarily processing many slots much faster than real time) and using non-default `--incremental-snapshot-interval-slots`/`--full-snapshot-interval-slots` values are both normal, unprivileged, non-malicious operating conditions. `AccountsBackgroundService` runs continuously on every validator, so the mismatch between the fixed constant and actual cadence occurs whenever these conditions diverge from the 400ms/100-slot assumption baked into the 50-second constant.

### Recommendation
Derive `CLEAN_INTERVAL` (and `SHRINK_INTERVAL`) dynamically from the actually configured snapshot interval(s) (`SnapshotConfig`) rather than from a hardcoded wall-clock duration, and/or gate cleaning/shrinking additionally on slot-count or dirty-store-size thresholds (as is already done elsewhere, e.g. `DIRTY_STORES_CLEANING_THRESHOLD` in `shrink_all_slots`) so the cadence tracks actual account churn instead of assumed wall-clock slot timing. [7](#0-6) 

### Proof of Concept
1. Configure a validator with a non-default, larger `--incremental-snapshot-interval-slots` (or observe a period where slot processing is much faster than 400ms/slot, e.g. ledger replay/catch-up).
2. `AccountsBackgroundService`'s loop still gates `should_clean`/`should_shrink` solely on `CLEAN_INTERVAL` (50s) / `SHRINK_INTERVAL` (1s) wall-clock elapsed time, per [8](#0-7) .
3. During this period, many more slots/roots are added to `accounts_cache` and `dirty_stores` than the constant assumed (100 slots per 50s), because accumulation is driven by slot count/account churn, not by wall-clock time.
4. When the fixed timer finally fires, `clean_accounts`/`shrink_candidate_slots` must process a backlog much larger than intended, producing disproportionate CPU/I/O spikes and elevated storage retention versus the case where the interval tracked the real snapshot/slot cadence.
