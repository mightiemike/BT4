### Title
Wallet Contract permanently traps a caller's attached deposit on early/failure return paths that bypass the `caller_deposit` refund logic - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point optionally tracks an external caller's attached deposit via `CallerDeposit`, intending to refund it if the underlying cross-contract action ultimately fails. However, several failure/return paths never consult or forward this refund, permanently trapping the caller's NEAR on the Wallet Contract's own balance — the same bug class as the Sherlock report: an optional "did the swap/side-effect happen" branch is missing its complementary "return funds to caller" branch.

### Finding Description
`CallerDeposit::new` records the caller's deposit whenever the predecessor differs from the wallet contract itself and a nonzero deposit is attached: [1](#0-0) 

The refund is only actually issued inside `rlp_execute_callback`, and only in its `PromiseResult::Failed` arm: [2](#0-1) 

But `caller_deposit` is threaded as a parameter through two other intermediate callbacks, `address_check_callback` and `nep_141_storage_balance_callback`, whose *own* early failure branches return an `ExecuteResponse` directly without ever forwarding to `rlp_execute_callback` or issuing a refund transfer:

- In `address_check_callback`, if the address-registrar lookup itself fails, returns malformed data, or the target turns out to be an existing named account, the function returns early and `caller_deposit` is simply dropped: [3](#0-2) 

- In `nep_141_storage_balance_callback`, the same pattern occurs when the NEP-141 `storage_balance_of` call fails or returns unparsable data: [4](#0-3) 

- Even earlier, in `inner_rlp_execute`, `caller_deposit` is computed from the already-attached deposit at line 345, but every early `Err` return from RLP parsing (user errors, relayer errors, account-id errors) propagates straight back to `rlp_execute`'s `Err(e) => PromiseOrValue::Value(e.into())` branch, again without ever creating a refund promise for the already-received deposit: [5](#0-4) [6](#0-5) 

Just like the Swivel `Lender.lend()` case — where the "swap to PT" flag being unset leaves the resulting underlying balance stuck on the `Lender` contract with no code path returning it to the caller — here the "did this specific promise chain fail" check is only implemented for the final resolution step. Any failure occurring earlier in the promise chain (registrar failure, NEP-141 storage check failure) or synchronously before any promise is even created (RLP parse failure) causes the attached deposit to remain on the Wallet Contract account permanently, since the Wallet Contract has no owner/admin and no `withdraw()`-style rescue mechanism at all — making the loss strictly worse than in the original report.

### Impact Explanation
Any relayer or external caller that attaches a NEAR deposit to `rlp_execute` (e.g., to fund a value-bearing emulated Ethereum transfer or a NEP-141 transfer with storage registration) loses that deposit outright whenever the transaction happens to hit one of these unrefunded failure branches — e.g., the address registrar being briefly unreachable/erroring, or the target token responding unexpectedly to `storage_balance_of`, or a malformed/invalid RLP-encoded transaction being submitted. Because the Wallet Contract is a global, unowned contract instance deployed per eth-implicit account with no admin recovery function, these funds are permanently unrecoverable, constituting concrete, transaction-triggered fund freeze/loss.

### Likelihood Explanation
This is reachable by any single external account (typically a relayer) calling the public, payable `rlp_execute` method with a non-zero attached deposit — no special privileges are required. The failing conditions (registrar call failure, unexpected/malformed cross-contract response, or invalid RLP transaction encoding) are ordinary operational occurrences, not adversarial edge cases, so the fund loss occurs as part of normal usage, not solely under attacker-controlled conditions.

### Recommendation
Ensure `caller_deposit` is honored on every failure/early-return path that follows deposit intake, not only inside `rlp_execute_callback`'s `Failed` arm:
- In `address_check_callback`, issue the caller-deposit refund transfer before returning `ExecuteResponse { success: false, .. }` in the "registrar call failed", "unexpected response", and "invalid target" branches.
- In `nep_141_storage_balance_callback`, do the same for its "call failed" and "unexpected response" branches.
- In `inner_rlp_execute` / `rlp_execute`, when an `Err` is returned before any promise has been scheduled, issue a `Promise::new(predecessor_account_id).transfer(deposit)` for the already-attached deposit before returning the error `ExecuteResponse`.

Centralizing the refund logic (e.g., a single helper `refund_caller_deposit(caller_deposit)` called from every failure exit point) would prevent this class of gaps from recurring.

### Proof of Concept
1. A relayer calls `WalletContract::rlp_execute(target, tx_bytes_b64)` attaching `N` yoctoNEAR, where the decoded transaction is an `EOABaseTokenTransfer` with `address_check: Some(address)` (i.e., the target's derived address needs registrar confirmation), per `inner_rlp_execute`: [7](#0-6) 
2. `CallerDeposit::new` records `{ account_id: relayer, yocto_near: N }` since `predecessor_account_id != current_account_id`.
3. The scheduled cross-contract call to the `AddressRegistrar` contract fails (e.g., registrar down, out of gas, or any transient error) — `address_check_callback` is invoked with `PromiseResult::Failed`.
4. `address_check_callback`'s `PromiseResult::Failed` arm returns `ExecuteResponse { success: false, ... }` immediately, at [8](#0-7)  without ever transferring the `N` yoctoNEAR back to the relayer.
5. The `N` yoctoNEAR permanently remains on the Wallet Contract's account balance; there is no admin/owner function anywhere in the contract to recover it, unlike the analogous administrative `withdraw()` present in the original report's Swivel `Lender` contract.

fn inner_rlp_execute(
    current_account_id: AccountId,
    predecessor_account_id: AccountId,
    target: AccountId,
    tx_bytes_b64: String,
    nonce: &mut u64,
) -> Result<Promise, Error> {
    if *nonce == u64::MAX {
        return Err(Error::AccountNonceExhausted);
    }
    let context = ExecutionContext::new(
        current_account_id.clone(),
        predecessor_account_id,
        env::attached_deposit(),
    )?;
    let caller_deposit = CallerDeposit::new(&context);

    let parsing_result = internal::parse_rlp_tx_to_action(&tx_bytes_b64, &target, &context, *nonce);
    let (action, transaction_kind) = match parsing_result {
        Ok((action, transaction_kind)) => {
            // Increment nonce for all cases where the registrar contract is not needed
            // to prevent replay of those transactions. For transactions that go through
            // the registrar we still do not know if the transaction has a relayer error
            // or not, therefore we must delay incrementing the nonce.
            //
            // Note: relayers with access keys cannot use this delay to needlessly spend
            // the users tokens because only one transaction is allowed to be in-flight
            // at a time.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                address_check: Some(_),
                ..
            }) = &transaction_kind
            {
            } else {
                *nonce = nonce.saturating_add(1);
            }

            // If the action is an emulated base token or ERC-20 transfer with a non-zero fee then
            // create a promise to send the refund to the relayer. This allows any relayer
            // to safely serve base token transfers from any wallet without additional
            // on-boarding because the relayer will receive some compensation for sending
            // the transaction. Users should always verify the fee before signing a base token
            // transfer. Relayers should also verify the fee before sending to make sure the
            // user's signed transaction will refund enough to cover the relayer's gas costs.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                fee,
                ..
            })
            | TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
                &transaction_kind
            {
                if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
                    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
                    env::promise_batch_action_transfer(refund_promise, *fee);
                }
            }

            (action, transaction_kind)
        }
        Err(err @ Error::User(_)) => {
            // Increment nonce on all user errors to prevent replay.
            *nonce = nonce.saturating_add(1);
            return Err(err);
        }
        Err(err) => {
            // Do not increment nonce on Relayer or AccountId errors.
            // The latter error is an issue in the deployment (so the nonce is meaningless).
            // The former arises from the relayer itself doing something wrong and thus the
            // user's transaction could still be valid and potentially submitted properly by
            // another relayer. To allow this we do not increment the nonce.
            //
            // Note: if a relayer is using an access key for this wallet then that key will
            // still be revoked (in the main logic of `rlp_execute`). This fact together with
            // the condition that there only be one in-flight transaction at a time implies
            // that a relayer cannot maliciously burn a large portion of the user's tokens.
            // If the relayer is not using an access key then they are spending their own
            // resources on the gas and therefore we do not care if the relayer submits
            // the same faulty transaction multiple times.
            return Err(err);
        }
    };
