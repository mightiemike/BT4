### Title
Unconditional "bootstrap declare" bypass via reserved sender address, gated only by external config, not chain state - ([File: crates/blockifier/src/transaction/account_transaction.rs])

### Summary
The F2FS bug treats a synthetic sentinel inode number (`F2FS_COMPRESS_INO`) as unconditionally "special" in `is_meta_ino()`, without checking whether the feature that creates that inode (`compress_cache`) is actually enabled — letting a crafted value that matches the sentinel bypass normal validation. The sequencer has an analogous pattern: `AccountTransaction::execute_raw` special-cases any `Declare` transaction whose `sender_address` equals a hard-coded, publicly-known sentinel address (`'BOOTSTRAP'`), skipping `__validate_declare__`, fee payment, and nonce checks — with no check on the actual chain state (e.g. block number / "is genesis" flag) confirming the network is actually in its bootstrap phase.

### Finding Description
`DeclareTransaction::bootstrap_address()` returns a fixed, public constant — the felt encoding of the ASCII string `'BOOTSTRAP'`: [1](#0-0) 

`is_bootstrap_declare` treats any Declare tx as a “bootstrap declare” purely based on tx-supplied/tx-derived fields — `sender_address == bootstrap_address()`, `nonce == 0`, and `!charge_fee`: [2](#0-1) 

In `AccountTransaction::execute_raw`, if this predicate holds, the sequencer skips `perform_pre_validation_stage` (nonce/fee checks) and `run_or_revert` (which normally invokes `__validate_declare__`), and directly writes the class hash into `contract_class_changes` with no signature verification, no fee charge, and no resource-bound based gas metering: [3](#0-2) 

The identical unconditional pattern exists in the Starknet OS Cairo re-execution path, gated the same way (`sender_address == 'BOOTSTRAP' and nonce == 0 and version == 3` and `max_possible_fee == 0`): [4](#0-3) 

Critically, `charge_fee` (the third condition) is derived from the transaction's own resource bounds having zero `max_possible_fee`, i.e. it is attacker-controlled, not a sequencer/state-derived flag: [5](#0-4) 

The only defense preventing this from being exploitable **after genesis** is the gateway-level `StatelessTransactionValidator::validate_resource_bounds`, which rejects zero-resource-bound transactions — but only `if self.config.validate_resource_bounds` is `true`, and the config's own documentation states it is meant to be turned off specifically during bootstrap: [6](#0-5) [7](#0-6) 

This mirrors the F2FS root cause exactly: the "is this a special/privileged case" check (`is_meta_ino` / `is_bootstrap_declare`) is defined purely in terms of a sentinel value match, with **no code-level assertion that the associated feature/state (compress_cache mount option / actual bootstrap phase, e.g. block height 0) is currently active**. The gate that is supposed to make the sentinel meaningful lives entirely in a separate, independently-toggleable configuration knob (`validate_resource_bounds`) rather than in the state itself (e.g., `block_number == 0`).

### Impact Explanation
If `validate_resource_bounds` is disabled at any point post-genesis (operational necessity, mis-toggled config, or any code path that submits transactions to the batcher bypassing `StatelessTransactionValidator` — e.g. internal re-submission/virtual-block execution paths), any external declarer can submit a `Declare` transaction with `sender_address = bootstrap_address()`, `nonce = 0`, and zero resource bounds to declare **any class** for free, with **no signature validation whatsoever** (`__validate_declare__` is entirely skipped) and without contributing to bouncer/fee accounting. This is an unauthorized account action (state mutation attributed to a "reserved" address with no authentication) and can also be leveraged for unbounded free compute (Sierra→CASM compilation cost bypassing fee enforcement), a resource-exhaustion vector affecting the network's ability to process legitimate transactions.

### Likelihood Explanation
Exploitation requires the `validate_resource_bounds` gateway config to be `false` (or the tx to reach execution bypassing that specific stateless check) at a point in the chain's life after genesis. The condition check itself (`sender_address`, `nonce`, `charge_fee`) has zero secrecy — the "BOOTSTRAP" address is a hardcoded ASCII-derived constant discoverable by reading the open-source code, and reconstructing a matching transaction requires no privileged information. The residual likelihood therefore hinges entirely on operational/config discipline rather than an in-protocol invariant, which is exactly the kind of "should be gated on state, but isn't" gap the report highlights.

### Recommendation
Gate the bootstrap-declare fast path on the actual chain state rather than solely on tx-supplied/config-toggled fields — e.g., require `block_context.block_info.block_number == BlockNumber(0)` (or an explicit "chain not yet bootstrapped" state flag checked in `is_bootstrap_declare`/`execute_raw`) in addition to the sentinel address, nonce, and fee checks. This closes the gap analogous to `F2FS_COMPRESS_INO` requiring `COMPRESS_CACHE` to actually be enabled before treating the sentinel ino as meta.

### Proof of Concept
1. Wait for (or induce) a configuration state where `gateway_config.static_config.validate_resource_bounds == false` (its documented purpose is exactly this, during "system bootstrap" — see `crates/apollo_node/resources/config_schema.json:4152-4156`), or find any submission path that does not invoke `StatelessTransactionValidator::validate`.
2. Craft a `DeclareTransaction::V3` with:
   - `sender_address = DeclareTransaction::bootstrap_address()` (`crates/starknet_api/src/executable_transaction.rs:260-263`)
   - `nonce = Nonce::ZERO`
   - `resource_bounds` set to zero (`ValidResourceBounds::create_for_testing_no_fee_enforcement()` pattern, see `crates/mempool_test_utils/src/starknet_api_test_utils.rs:585-595`)
   - Any attacker-chosen `class_hash`/`compiled_class_hash`, no valid signature required.
3. Submit the transaction. In `AccountTransaction::execute_raw`, `tx.is_bootstrap_declare(charge_fee)` evaluates true, and the class is declared directly via `run_execute`, skipping `__validate_declare__`, nonce bump, and fee charge (`crates/blockifier/src/transaction/account_transaction.rs:899-911`).

        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {

    fn validate_resource_bounds(
        &self,
        tx: &RpcTransaction,
    ) -> StatelessTransactionValidatorResult<()> {
        if !self.config.validate_resource_bounds {
            return Ok(());
        }

        let resource_bounds = *tx.resource_bounds();
        // The resource bounds should be positive even without the tip.
        if ValidResourceBounds::AllResources(resource_bounds).max_possible_fee(Tip::ZERO) == Fee(0)
        {
            return Err(StatelessTransactionValidatorError::ZeroResourceBounds { resource_bounds });
        }

        if resource_bounds.l2_gas.max_price_per_unit.0 < self.config.min_gas_price {
            return Err(StatelessTransactionValidatorError::MaxGasPriceTooLow {
                gas_price: resource_bounds.l2_gas.max_price_per_unit,
                min_gas_price: self.config.min_gas_price,
            });
        }

        // TODO(Arni): Consider adding a validation for max_l2_gas_amount for declare.

        } else if resource_bounds.l2_gas.max_amount.0 > self.config.max_l2_gas_amount {
            return Err(StatelessTransactionValidatorError::MaxGasAmountTooHigh {
                gas_amount: resource_bounds.l2_gas.max_amount,
                max_gas_amount: self.config.max_l2_gas_amount,
