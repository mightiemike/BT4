## Analysis

**EventID collision is not exploitable.** `parseSendFundsEvent` derives `EventID` deterministically as `TxHash:LogIndex` [1](#0-0) , and `InsertEventIfNotExists` enforces a DB unique index on `EventID`, treating unique-constraint violations as harmless duplicates [2](#0-1) , backed by `gorm:"uniqueIndex;not null"` on the model [3](#0-2) . Since `TxHash:LogIndex` is fixed by the chain itself, an attacker cannot manipulate log ordering across blocks to fabricate two distinct local rows for the same canonical log; every observed log maps to exactly one `EventID`/`EventData` row regardless of ordering or replay.

**The real gap is in confirmation-policy selection, not record duplication.** `finalizeEvent` sets `event.ConfirmationType` purely from `payload.TxType`:

```go
if payload.TxType == 0 || payload.TxType == 1 {
    event.ConfirmationType = store.ConfirmationFast
} else {
    event.ConfirmationType = store.ConfirmationStandard
}
``` [4](#0-3) 

`TxType` is Word 4 of the raw ABI-encoded `sendFunds` log data [5](#0-4)  — fully attacker-controlled calldata for a public, unprivileged gateway call. Yet the chain registry's own `GatewayMethods.confirmation_type` explicitly classifies `sendFunds` as `CONFIRMATION_TYPE_STANDARD` (`confirmation_type: 1`) at the config level [6](#0-5) . `parseUniversalTx`/`finalizeEvent` never consults that per-method registry value; it derives `ConfirmationType` solely from the attacker-supplied `TxType` field embedded in the event itself, silently overriding the intended per-method policy.

The confirmer then uses whatever `ConfirmationType` was assigned to pick `requiredConfirmations` (`fastConfirmations` vs `standardConfirmations`) [7](#0-6) , and some configured chains set `fast_inbound: 0` [8](#0-7) . With `requiredConfirmations = 0`, an event can be promoted `PENDING → CONFIRMED` on the very first poll after inclusion (`confirmations := latestBlock - receipt.BlockNumber + 1 >= 0`) [9](#0-8) .

Additionally, there is **no active reorg-detection path** in the confirmer: it only checks receipt existence and `receipt.Status` [10](#0-9) ; `StatusReorged` is defined in the model and referenced only by the cleanup/test code, never assigned by any production confirmation/listener logic. So once an event is marked `CONFIRMED` under an attacker-chosen `FAST` classification, nothing subsequently re-verifies that the originating block is still canonical before the event proceeds to voting/finalization.

**Net effect:** an unprivileged attacker submitting `sendFunds` can set `TxType = 0` or `1` regardless of the actual value/payload being sent, forcing the universal client to apply a shallower confirmation depth than the chain registry mandates for that method. Combined with the absence of any reorg re-validation after promotion to `CONFIRMED`, this narrows (or eliminates) the reorg-safety window the operator configured, increasing the feasibility of a shallow-reorg-based double record/finality mismatch that could lead to unauthorized mint/execution on Push Chain if the source-chain deposit is later reorged out.

I could not verify within available context whether downstream vote/finalization logic in `x/uexecutor` cross-checks `TxType` consistency against payload presence/value or independently re-derives confirmation policy from the registry before minting — that check happens outside `event_parser.go`/`event_confirmer.go` and I was unable to trace it in the remaining budget. This materially affects the actual exploitability/likelihood and should be verified before final severity assignment.

### Title
Attacker-controlled `TxType` field lets `sendFunds` bypass the chain-registry confirmation policy, weakening reorg protection - (File: universalClient/chains/evm/event_parser.go)

### Summary
`parseUniversalTx`/`finalizeEvent` assigns `ConfirmationType` (FAST vs STANDARD) based solely on the attacker-controlled `TxType` word inside the `sendFunds` event payload, ignoring the per-method `confirmation_type` configured in the chain registry. This lets an unprivileged sender force a shallower (even zero-block) confirmation depth for value-bearing/payload-carrying inbound transactions than the operator intended.

### Finding Description
`finalizeEvent` sets confirmation policy from `payload.TxType` [4](#0-3) , and `TxType` is decoded straight from attacker-supplied log data with no cross-validation against payload presence, amount, or the registry's configured `GatewayMethods.confirmation_type` for `sendFunds` [6](#0-5) . The confirmer trusts this per-event classification to select `requiredConfirmations` [7](#0-6) , and no code path re-validates canonical-chain membership once an event is marked CONFIRMED (`StatusReorged` is never assigned in production code).

### Impact Explanation
If exploitable end-to-end (unverified beyond the scoped files), an attacker could get a value/payload-bearing deposit finalized under a shallow or zero-confirmation policy, then have the source-chain transaction removed via a shallow reorg, potentially causing Push Chain to mint/execute against a deposit that no longer exists on the source chain.

### Likelihood Explanation
Requires the target EVM chain to have short reorg windows and a misconfigured/low `fast_inbound` value, plus (unverified) that downstream voting/minting logic does not independently re-check confirmation depth or payload/TxType consistency. Likelihood is moderate to low pending verification of the `x/uexecutor` voting path.

### Recommendation
Derive `ConfirmationType` from the chain registry's per-method `confirmation_type` (or from validated, non-attacker-controlled criteria such as whether a payload/high-value transfer is present) rather than from the raw, attacker-supplied `TxType` word in the event data. Add explicit reorg re-validation (e.g., re-fetch block hash / log inclusion) before finalizing votes on CONFIRMED events.

### Proof of Concept
1. Submit `sendFunds` on an in-scope EVM gateway with a non-trivial `payload`/`amount`, but set the `txType` word to `0`.
2. Observe `finalizeEvent` classify the event as `ConfirmationFast` [4](#0-3)  despite the registry configuring `sendFunds` as STANDARD.
3. On a chain configured with `fast_inbound: 0`, observe the event promoted to CONFIRMED on the first confirmer poll [9](#0-8) .
4. Trigger/await a shallow reorg removing the source block; verify no code transitions the already-CONFIRMED event to REORGED.

func (cs *ChainStore) InsertEventIfNotExists(event *store.Event) (bool, error) {
	if cs.database == nil {
		return false, fmt.Errorf("database is nil")
	}

	// Check for existing event
	var existing store.Event
	err := cs.database.Client().Where("event_id = ?", event.EventID).First(&existing).Error
	if err == nil {
		// Event already exists
		return false, nil
	}
	if err != gorm.ErrRecordNotFound {
		return false, fmt.Errorf("failed to check existing event: %w", err)
	}

	// Store new event
	if err := cs.database.Client().Create(event).Error; err != nil {
		// UNIQUE constraint violation means another goroutine or poll cycle already
		// inserted this event between our check and insert — treat as duplicate.
		if strings.Contains(err.Error(), "UNIQUE constraint failed") {
			return false, nil
		}
		return false, fmt.Errorf("failed to create event: %w", err)
	}

// getRequiredConfirmations returns the required number of confirmations based on confirmation type
func (ec *EventConfirmer) getRequiredConfirmations(confirmationType string) uint64 {
	switch confirmationType {
	case store.ConfirmationFast:
		if ec.fastConfirmations >= 0 {
			return ec.fastConfirmations
		}
		return 5
	case store.ConfirmationStandard:
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	default:
		// Default to standard if unknown
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	}
