## Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify/debugger tooling certify a diverged ledger state as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-equality check used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed `TransactionOutput` matches the `TransactionInfo` fetched from an archive/backup/network source. The function validates status, gas used, `state_change_hash` (write-set hash) and `event_root_hash`, but deliberately omits comparison of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually commit to the resulting state (Sparse-Merkle / Jellyfish-Merkle) root.

### Finding Description [1](#0-0) 

The comparator ends with:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```
This is a self-documented gap acknowledged in the code itself: `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (all present on `TransactionInfo`/`TransactionInfoV1`, see [2](#0-1) ) are never compared inside `ensure_match_transaction_info`, even though they are exactly the fields that bind a `TransactionInfo` to the actual post-execution state root (state Merkle root / hot-state root / native "position" state root used by the trading-native feature).

This function is directly wired into mainnet-relevant integrity tooling:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` calls `executed_outputs[idx].ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)` and only surfaces an error when this call fails [3](#0-2) . This is the tool operators use to validate that a downloaded backup/archive of the chain reproduces exactly the state committed by validators.
- `aptos-move/aptos-debugger/src/aptos_debugger.rs::print_mismatches` uses the same call to detect divergence when replaying committed transactions fetched from a REST endpoint or local DB [4](#0-3) .

Because the state-checkpoint hashes are skipped, any of the following can happen and go undetected by this check:
1. A backup/archive source (or REST endpoint) that supplies a `TransactionInfo` whose `state_change_hash`/`event_root_hash` are correct (i.e., the write set and events applied by the transaction are unmodified) but whose `state_checkpoint_hash` (the periodic full state-root checkpoint) does not match the root that would actually result from applying that write set on top of the correct prior state — for example due to a prior undetected state divergence, a storage bug, or corrupted/withheld state that was never rolled into this write set.
2. The newer `position_state_checkpoint_hash`/`hot_state_checkpoint_hash` fields (part of the still-rolling-out "trading-native"/hot-state features, analogous to the "newly added token/field defaulting to an unvalidated value" pattern in the external report) can silently diverge between the replayed output and the archived `TransactionInfo` without the tooling raising an error.

### Impact Explanation
The exploitable window is directly analogous to the external report's "new field defaults to an unchecked/zero value until it is properly wired into validation" pattern: `TransactionInfoV1`'s checkpoint-hash fields exist and are populated at commit time (`assemble_transaction_infos` in `execution/executor/src/workflow/do_ledger_update.rs` correctly computes and sets `maybe_state_checkpoint_hash`/`maybe_hot_state_checkpoint_hash`/`maybe_position_state_checkpoint_hash` [5](#0-4) ), but the downstream authenticity check that is supposed to *use* those fields to catch divergence deliberately ignores them. This means:
- `db-tool replay-on-archive`, which is the tool operators/auditors use to confirm that archived/backed-up ledger data is a faithful, non-corrupted representation of what validators actually committed, can report "successful replay" even though the actual state root diverges from the correct one.
- This directly matches the required-impact category "Authenticated API or state-view output bound to the wrong version, object, or proof context" and "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" — the replay path here can accept committed data that represents a different (wrong) ledger state as if it matched.

The severity is bounded by the fact that this is a verification/tooling gap, not a consensus-commit or live-execution defect: it does not let an attacker corrupt live mainnet state or forge an accepted BCS/ledger-info signature, since `ensure_match_transaction_info` is not part of the state-sync or consensus commit path (that path uses full `TransactionAccumulatorRangeProof`/`TransactionInfoListWithProof::verify` cryptographic checks, which do hash the full `TransactionInfo`, checkpoint hashes included — see [6](#0-5) ). However, it does undermine the primary tool relied on to *detect* state divergence during archive verification/replay and post-mortem debugging, which is exactly the kind of check meant to catch a hard-fork-only divergence or storage corruption before it's trusted. Given the explicit developer acknowledgment that "the authenticated position state root diverges from local execution" can go unnoticed, and that `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state rollout is ongoing (see feature flag references in `types/src/on_chain_config/aptos_features.rs`, `storage/aptosdb/src/db/aptosdb_reader.rs`/`aptosdb_writer.rs`), this is a live, unmitigated gap in mainnet-relevant verification tooling.

### Likelihood Explanation
High likelihood in the "should have caught it" sense: any historical backup, replayed archive, or REST-served transaction whose full-write-set/event hashes are correct but whose checkpoint-state root has diverged (from a bug in state-checkpoint computation, buffered-state corruption, or an inconsistent DB restore) will pass `ensure_match_transaction_info` silently. The code comment itself confirms the authors are aware this is a live, not hypothetical, gap that must be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`."

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` against the locally computed equivalents (when the local checkpoint hash is present/derivable, e.g., in `db-tool replay_on_archive` where per-transaction checkpoint hashes are computable), returning an error on mismatch just as is done for `state_change_hash`/`event_root_hash`. This should be done prior to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any feature that relies on `position_state_checkpoint_hash` being trustworthy in tooling.

### Proof of Concept
Not independently reproducible as a live-network exploit since the affected function is not on the consensus/state-sync commit path — the flaw is a logic gap in the local comparator, confirmed via code inspection:
1. `execution/executor/src/workflow/do_ledger_update.rs::assemble_transaction_infos` computes and sets `state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash` on committed `TransactionInfo`s.
2. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` re-executes transactions and calls `TransactionOutput::ensure_match_transaction_info(version, &expected_txn_info, ...)` to assert equivalence with the archived `TransactionInfo`.
3. `types/src/transaction/mod.rs::ensure_match_transaction_info` (lines 2139–2204) checks only `status`, `gas_used`, `state_change_hash`, `event_root_hash` and explicitly returns `Ok(())` without checking any checkpoint hash, as documented in its own trailing `TODO(trading-native)` comment.
4. Consequently, feeding `execute_and_verify` a crafted/corrupted `expected_txn_infos[idx]` (or an archive) with a correct write-set/event hash but a mismatched `state_checkpoint_hash`/`position_state_checkpoint_hash` will not trigger the error path, and the replay tool will report a clean pass despite the ledger state actually diverging.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
