I found a genuine analog. In `add-staker-to-signer-for-cycle` (`stackslib/src/chainstate/stacks/boot/pox-5.clar`), the per-staker share accumulator `staker-shares-staked-for-cycle` is overwritten with the bare `stake-amount` instead of being added to the previously fetched `prev-staker-shares`, even though the sibling signer-level accumulators in the same function (`signer-shares-staked-for-cycle`, `signer-pending-staked-ustx-per-cycle`) correctly do `(+ prev-staked stake-amount)`.

### Title
Staker share accumulator overwritten instead of accumulated in `add-staker-to-signer-for-cycle` - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`add-staker-to-signer-for-cycle` is the per-cycle folding step used by both direct STX staking (`add-staker-to-signer-cycles`) and pool/bond delegation paths to register a staker's contribution to a given `(staker, cycle, signer)` slot. It reads the staker's existing accumulated stake via `get-staker-shares-staked-for-cycle` into `prev-staker-shares` [1](#0-0) , uses that value only to decide whether to call `settle-staker-rewards` [2](#0-1) , but then writes the new `staker-shares-staked-for-cycle` entry using only `stake-amount`, discarding `prev-staker-shares` entirely: [3](#0-2) . This mirrors the reported bug class exactly: a "pending"/accumulated value keyed by a user identity is captured, used for one purpose (settlement gating), and then overwritten instead of increment-updated when persisted.

### Finding Description
Compare the two accumulators updated in the same function for the same event:
- Signer-level: `(map-set signer-pending-staked-ustx-per-cycle ... (+ prev-staked stake-amount))` — correctly additive. [4](#0-3) 
- Staker-level: `(map-set staker-shares-staked-for-cycle ... stake-amount)` — **not additive**, overwrites whatever was previously recorded for this `(staker, cycle, signer)` key. [3](#0-2) 

If a staker/delegator's contribution is registered against the same `(staker, reward-cycle, bond-index: none, signer)` key more than once before it is settled/claimed (e.g., additional stack/delegate calls targeting the same signer and cycle, or a delegator adding STX-only stake incrementally across multiple transactions that land in the same reward cycle before rewards are claimed), the second call's `map-set` replaces the first contribution instead of adding to it. The staker's on-chain recorded share (`get-staker-shares-staked-for-cycle`) then equals only the most recent increment, not the cumulative amount actually staked.

This value directly feeds reward computation: `compute-earned-rewards` computes `earned = shares * (rpt - rptPaid) + pending`, using `get-staker-shares-staked-for-cycle`/`get-signer-shares-staked-for-cycle` as the `shares` input [5](#0-4) . Since `shares` is silently truncated to the latest increment, the staker's earned-reward calculation understates their true stake, while the signer-level and total-shares accumulators (which are correctly additive) keep the true cumulative total. This produces a divergent, non-reproducible reward accounting: two honest nodes reading the same on-chain map state will compute the same (wrong) value deterministically, but the value itself no longer represents the actual economic contribution, meaning rewards distributed to the affected staker will not match the amount other stakers/signers expect based on the (correct) aggregate totals — a mismatch between individually-reported and globally-summed stake.

### Impact Explanation
This is bounded to sBTC/STX reward mis-payment within the pox-5 signer/staker reward-splitting logic: an affected staker's `claim-rewards`/`claim-staker-rewards-for-signer` payout, computed via `compute-earned-rewards`, will be calculated from an undercounted `shares` value, while the signer/global totals used to derive the per-token reward rate remain correct. This causes reward funds proportionally owed to the staker to be misallocated (retained in the reserve/other stakers' share) rather than paid to the rightful staker — a reward mis-payment bounded to the sBTC reward pool for that cycle, not a chain-consensus-breaking state-root divergence, since the (buggy) computation is itself deterministic across nodes.

### Likelihood Explanation
Triggerable by any single unprivileged staker/delegator who is added to the same `(staker, cycle, signer)` slot more than once within the same, still-unsettled reward cycle (e.g. via repeated `delegate-stack-stx`/increase calls or pool-driven multiple `add-staker-to-signer-for-cycle` invocations before `claim-rewards` is called) — no majority or privileged actor is required.

### Recommendation
Change the `staker-shares-staked-for-cycle` update at line 1761-1768 to add to the previously fetched `prev-staker-shares`, consistent with the signer-level accumulators in the same function:
```clarity
(map-set staker-shares-staked-for-cycle {
    staker: staker,
    reward-cycle: cycle,
    bond-index: none,
    signer: signer,
}
    (+ prev-staker-shares stake-amount)
)
```

### Proof of Concept
1. A staker/delegator is registered via `add-staker-to-signer-for-cycle` for `(staker=S, signer=SG, cycle=C)` with `stake-amount = A1`; `staker-shares-staked-for-cycle` is set to `A1`, and `signer-pending-staked-ustx-per-cycle`/`total-shares-staked-for-cycle` correctly include `A1`.
2. Before cycle `C` is settled/claimed, the same staker is registered again for the same key with `stake-amount = A2` (e.g., a second `delegate-stack-stx`-style call that lands in the same cycle).
3. `prev-staker-shares = A1` is read at line 1691 but unused for the write; `staker-shares-staked-for-cycle` is overwritten with `A2` instead of `A1 + A2` (line 1761-1768), while `signer-pending-staked-ustx-per-cycle` correctly becomes `A1 + A2` (line 1753-1759).
4. When `get-earned`/`claim-rewards` later computes the staker's reward using `get-staker-shares-staked-for-cycle` = `A2`, it undercounts the staker's true contribution `A1 + A2`, causing the staker to receive fewer rewards than their proportional share of the pool while the pool-level totals used to compute the reward rate remain based on the full `A1 + A2`.
