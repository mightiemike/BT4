### Title
Free/Unauthenticated Class Declaration via Hardcoded `BOOTSTRAP` Sender Address Bypasses Fee and Validation - (File: crates/starknet_api/src/executable_transaction.rs, crates/blockifier/src/transaction/account_transaction.rs)

### Summary
The same bug class as the reported RuyuiShop issue — a state-mutating operation being performed without verifying a mandatory prerequisite, letting a caller bypass a required fee — has a direct structural analog in the sequencer's declare-transaction handling. A `Declare` transaction whose `sender_address` equals a hardcoded constant (`'BOOTSTRAP'`), with `nonce == 0` and `charge_fee == false`, skips all normal account validation, nonce checks, and fee enforcement, and directly writes the class hash into `contract_class_changes`. This "bootstrap declare" flow is documented as intended only for genesis/chain-bootstrapping, but nothing in the reachable code path restricts it to block 0 — it is gated purely on transaction-controlled fields.

### Finding Description
`DeclareTransaction::is_bootstrap_declare` treats a transaction as a "bootstrap declare" purely based on attacker/user-controlled transaction fields: [1](#0-0) 

Unlike a `DeployAccount` transaction (where the sender address is cryptographically derived from a salt/class hash/constructor args), a `Declare` transaction's `sender_address` is simply a plain field supplied by the caller — it is not derived from any signature or commitment. This means any submitter can set `sender_address = bootstrap_address()` (`0x424f4f545354524150`, i.e. felt('BOOTSTRAP')) and `nonce = 0` on a V3 declare transaction they construct themselves.

In `AccountTransaction::execute_raw`, when `is_bootstrap_declare` returns true, the transaction entirely bypasses `perform_pre_validation_stage` (which normally performs the nonce check and fee-bound checks) and bypasses running `__validate_declare__`, going straight to `run_execute`, which declares the class and returns: [2](#0-1) 

The equivalent path exists in the Starknet OS Cairo re-execution logic, which similarly special-cases `sender_address == 'BOOTSTRAP'` to skip validate/account-related actions and unconditionally record the class declaration via `dict_update` with `prev_value=0`: [3](#0-2) 

The only remaining precondition is `charge_fee == false`, which is derived from the transaction's own resource bounds via `enforce_fee(executable_tx, only_query)` in the gateway's stateful validator — i.e., a caller who sets zero/no-fee resource bounds on their declare transaction (as done throughout the test suite via `ValidResourceBounds::create_for_testing_no_fee_enforcement()`) can make `charge_fee` false for their own transaction.

Nothing in the reachable gateway or blockifier code inspected restricts this "bootstrap" special-case to genesis / block number 0 — the check is a pure function of `(sender_address, nonce, charge_fee)`, all of which are attacker-supplied transaction fields. This directly parallels the RuyuiShop bug: a state-changing operation (declaring a class / purchasing) is performed without checking a real prerequisite (that the sender is an actual signed-up account with a genuine identity), allowing the caller to bypass the fee (signup fee / declare fee) that the protocol otherwise mandates.

### Impact Explanation
If reachable outside of the intended genesis-only usage, this allows any unprivileged transaction sender to:
- Declare a Sierra class for free, without paying the declare fee that every other transaction sender must pay (direct loss of protocol/sequencer fee revenue), and
- Have that declaration recorded in state (`contract_class_changes`) without ever running `__validate_declare__`, i.e., without any account-level authorization check, since `'BOOTSTRAP'` is not a real deployed account.

This is a fee-bypass / unauthorized state-mutation class issue, matching the "Avoids signup fee" / "Incorrect state update" impact categories from the reference report, mapped onto the sequencer's declare/fee-accounting pipeline.

### Likelihood Explanation
The `sender_address` field of a `Declare` transaction is not cryptographically bound to a real account (unlike `DeployAccount`), so crafting a transaction with `sender_address = bootstrap_address()` requires no special privilege — any transaction submitter can construct such a transaction. The remaining conditions (`nonce == 0`, `charge_fee == false`) are also transaction-field-controlled. The main uncertainty is whether upstream gateway validation (e.g., `validate_state_preconditions`, or block-height-based restrictions not fully located in this investigation) additionally rejects such transactions outside of genesis; this could not be fully confirmed within the available search budget, since the exact implementation of `enforce_fee` and `validate_state_preconditions` was not retrieved. This should be verified directly in `crates/blockifier/src/transaction/transactions.rs::enforce_fee` and `crates/apollo_gateway/src/stateful_transaction_validator.rs::validate_state_preconditions` before treating this as fully confirmed.

### Recommendation
Restrict the "bootstrap declare" fast path so it can only be exercised at the genesis block (e.g., require `block_context.block_info.block_number == BlockNumber(0)` in both the blockifier's `execute_raw` check and the Starknet OS Cairo equivalent), in addition to the existing `sender_address`/`nonce`/`charge_fee` checks, so that no post-genesis transaction can ever take this fee-free, validation-free path.

### Proof of Concept
Conceptual PoC (pending confirmation of `enforce_fee`/gateway preconditions):
1. Construct a `DeclareTransaction::V3` with `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`), `nonce = Nonce(0)`, and resource bounds set such that `enforce_fee` evaluates to `false` (e.g., zero resource bounds, mirroring `ValidResourceBounds::create_for_testing_no_fee_enforcement()` used throughout the test suite, e.g. `crates/mempool_test_utils/src/starknet_api_test_utils.rs:585-595`).
2. Submit this transaction through the gateway after the chain is already running (well past genesis).
3. Observe that `AccountTransaction::execute_raw` matches `is_bootstrap_declare` and executes `run_execute` directly, bypassing nonce/fee checks and `__validate_declare__`, declaring the class for free: [4](#0-3) 
4. Compare against the existing test `test_bootstrap_declare` in `crates/blockifier/src/transaction/account_transactions_test.rs:905-991`, which exercises exactly this flow (using `ApiExecutableDeclareTransaction::bootstrap_address()`) and asserts the resulting state diff contains only `compiled_class_hashes`/`declared_contracts` entries with no fee or nonce change — confirming the mechanism itself is real and unguarded by block height in the code paths examined.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }
