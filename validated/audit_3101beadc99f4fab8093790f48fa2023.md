### Title
OAuth "Login CSRF" via shared, non-shop-scoped `shopify_app_state`/`shopify_app_session` cookies allows an attacker to bind a victim's browser session to an attacker-controlled shop - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
The Optimism report describes how a re-org can swap which on-chain object (`P`/`Q`) an honest party's follow-up move actually lands on, because the protocol relies on a non-unique/shared identifier (the `create`-derived proxy address) rather than binding each move cryptographically to the specific game/context it was intended for. The direct analog in `shopify-app-js` is the OAuth `begin`/`callback` flow: the anti-CSRF `state` value is stored in a cookie (`shopify_app_state`) whose scope is only the fixed `callbackPath`, not the shop being authenticated, and the resulting session cookie (`shopify_app_session`) defaults to being scoped at `path: '/'` for every shop unless the app developer opts in to a shop-specific `cookiePath`. Because these cookies are not bound to the specific shop/tenant a flow was started for, a second, attacker-triggered `begin` call (a simple unauthenticated GET request) silently overwrites the victim's pending state/session cookie, letting the attacker's own shop's OAuth flow complete "inside" the victim's browser.

### Finding Description
`begin()` unconditionally writes a fresh signed `state` nonce into the `shopify_app_state` cookie scoped only by `callbackPath`: [1](#0-0) 

`callbackPath` is normally a single, fixed route in the app (e.g. `/auth/callback`) shared by *all* shops - it is not derived from the `shop` parameter. This means the cookie set here is not scoped to a particular tenant; any request to `/auth?shop=...` for *any* shop overwrites the same cookie in the requester's browser.

`callback()` completes the flow purely by comparing the query `state` to whatever value currently sits in that shared cookie, and then, for non-embedded apps, writes the resulting session id into `shopify_app_session`: [2](#0-1) 

The session cookie path defaults to `'/'` for every shop unless the developer explicitly supplies a shop-aware `cookiePath` function - a mitigation added later (per the changelog) specifically because "all shops shared a single `shopify_app_session` cookie at `path=/`... so authenticating a new shop would silently overwrite the previous shop's session": [3](#0-2) 

Because `cookiePath` is opt-in (defaults to `/`), and because the `STATE_COOKIE_NAME` cookie has no equivalent shop-scoping mechanism at all, an attacker can force a victim's browser to begin (and, since the attacker owns the target shop, complete) an OAuth flow for a shop the attacker controls, simply by getting the victim to issue a GET request to the app's `/auth?shop=<attacker-shop>` endpoint (e.g. via `<img>`/`<iframe>`/link - no token or prior authentication is required to hit `begin()`).

### Impact Explanation
This is a classic OAuth/login CSRF: the attacker forces the association of their own Shopify store with the victim's browser session. If the victim continues to interact with the app in that browser afterward (or if the app trusts the shop bound to the session cookie for any per-request routing/authorization decisions), data or actions intended for the victim's own store can instead be read from or written to the attacker's store context, and the victim's legitimate concurrent OAuth flow (if any) is disrupted/hijacked. This is a concrete cross-tenant session-binding issue reachable by a single anonymous HTTP GET request against an unauthenticated endpoint (`/auth`), matching the accepted "cross-tenant access"/"OAuth CSRF" categories.

### Likelihood Explanation
Likelihood is moderate-to-high for non-embedded apps that have not opted into the `cookiePath` function: `begin()` performs no origin/referer/CSRF checks and accepts any `shop` value, so triggering it cross-site via a simple GET is trivial. The main precondition is that the target app is non-embedded (embedded apps skip setting `SESSION_COOKIE_NAME` entirely) and has not configured a shop-specific `cookiePath`, which per the changelog was only recently made possible and remains opt-in rather than the default.

### Recommendation
- Scope the `shopify_app_state` cookie itself by shop (e.g., include a shop-derived path or embed/verify the target shop as part of the signed state value) so that a `begin()` call for shop A cannot clobber or be satisfied by a flow intended for shop B.
- Make the shop-aware `cookiePath` behavior the default for `SESSION_COOKIE_NAME` instead of requiring explicit opt-in, or refuse to overwrite an existing valid state/session cookie for a different shop without additional confirmation.
- Consider requiring an existing authenticated app session (or at least a same-site check) before allowing `begin()` to overwrite an in-flight OAuth cookie.

### Proof of Concept
1. Victim opens a tab and starts installing the app for `victim-shop.myshopify.com` (`GET /auth?shop=victim-shop.myshopify.com`), receiving a `shopify_app_state` cookie scoped to `callbackPath` (shared across all shops).
2. Before the victim's flow completes, attacker lures the victim (e.g., hidden `<img src="https://app.example.com/auth?shop=attacker-shop.myshopify.com">`) into issuing `GET /auth?shop=attacker-shop.myshopify.com` in the same browser.
3. This second call to `begin()` (`packages/apps/shopify-api/lib/auth/oauth/oauth.ts` lines 93-100) overwrites the shared `shopify_app_state` cookie with a new nonce tied to the attacker's shop, and redirects the victim's browser to Shopify's `/admin/oauth/authorize` for `attacker-shop.myshopify.com`.
4. Because the attacker owns `attacker-shop`, they can pre-authorize the app (or the redirect completes automatically for a dev-store the attacker controls), and Shopify redirects back to `/auth/callback` with a valid `hmac`/`state`/`code` for the attacker's shop.
5. `callback()` validates successfully (state matches the cookie that was just overwritten, HMAC is genuinely signed by Shopify) and sets `shopify_app_session` in the victim's browser to the attacker's shop session id, scoped at the default `path: '/'` (`packages/apps/shopify-api/lib/auth/oauth/oauth.ts` lines 219-230) — binding the victim's browser to the attacker's store.

```markdown
### Minor Changes

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
```
