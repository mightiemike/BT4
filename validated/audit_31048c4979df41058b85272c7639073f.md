## Analog Found

### Title
Stale Cairo0 class definitions in the process-wide `GlobalContractCache` bypass the "is declared" re-check performed for Cairo1 classes, enabling execution of undeclared/reverted contract code and honest-node state divergence - (File: `crates/blockifier/src/state/state_reader_and_contract_manager.rs`)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` explicitly re-validates that a cached class is still declared in canonical state before returning it — but only for Cairo1 (`RunnableCompiledClass::V0(_) => {}` skips the check, non-V0 variants perform `self.state_reader.is_declared(class_hash)?`). The code comment itself acknowledges the reason for this check: the cache can hold "a declared class from a reverted block." Because the check is asymmetric, a Cairo0 (deprecated) class hash can be served from the shared, cross-block `ContractClassManager`/`GlobalContractCache` even after the corresponding declaration has been reverted from canonical state, so execution silently uses code that per current committed state should not exist.

### Finding Description
`get_compiled_from_class_manager` first attempts to serve a class from the `ContractClassManager`'s `GlobalContractCache`, which is a long-lived, LRU cache shared by the whole sequencer process across many blocks (not scoped to a single block execution) [1](#0-0) . When a cache hit occurs, the code branches on the runnable class type: [2](#0-1) 

For any non-`V0` (i.e. Cairo1) class it re-validates against the canonical state reader via `is_declared`, precisely because a state revert can leave the class in the cache while the state no longer considers it declared. For `V0` (Cairo0/deprecated) classes, no such re-validation is performed — the cached compiled class is returned unconditionally.

`FetchCompiledClasses::is_declared` is explicitly documented to only track Cairo1 classes ("Cairo 0 classes always return `false`") [3](#0-2) , so this is not a simple oversight fixable by calling the same function — the asymmetry is structural: there is no declared-check path for Cairo0 classes at all once they are warm in the global cache.

Block/state reverts are a real, non-malicious path in this codebase: `apollo_storage` implements `revert_state_diff`, which deletes deprecated (Cairo0) class declarations recorded via `deprecated_declared_classes` when the block that introduced them is reverted [4](#0-3) , and tests confirm that after a revert, `is_declared`/definition lookups correctly report the class as no longer declared, while re-declaration is expected to work again cleanly [5](#0-4) . The revert path is driven by node configuration (`revert_config.should_revert` / `revert_up_to_and_including`) [6](#0-5) , i.e. a normal operational/reorg-handling mechanism, not an attacker action.

### Impact Explanation
Once a Cairo0 class hash has been warmed into a sequencer process's `GlobalContractCache` (e.g., by an earlier declare+deploy that is later reverted, while the *contract instance* deployed at that class hash persists in canonical state), subsequent user-submitted transactions invoking that contract will:
- On a node with a warm cache entry for that class hash: successfully execute using the stale Cairo0 bytecode, even though canonical state no longer considers the class declared.
- On a node without that cache entry (freshly started, cold cache, or one that evicted the entry): correctly fail with `StateError::UndeclaredClassHash` via the normal `state_reader.get_compiled_classes` path.

This produces divergent execution results for the same transaction across otherwise-honest sequencer/validator nodes, which can lead to different computed state roots/block hashes for the same block — a consensus-breaking divergence, not merely a resource or availability issue.

### Likelihood Explanation
Reachable purely through: (1) a `declare`+`deploy` transaction sequence at a given class hash, (2) a legitimate state revert of the declaring block (an operational reorg/rollback flow supported natively by `apollo_storage::revert_state_diff`, not requiring any malicious operator), and (3) a subsequent ordinary `invoke` transaction targeting the still-deployed contract address. No special privileges are needed by the transaction sender; the divergence trigger (block revert) is a supported system behavior, and the asymmetric cache-validation logic is unconditional production code on the hot path of every `get_compiled_class` call for Cairo0 classes.

### Recommendation
Apply the same "still declared" verification to Cairo0/deprecated classes retrieved from the `GlobalContractCache` as is already done for Cairo1 classes in `get_compiled_from_class_manager`, e.g. by extending `FetchCompiledClasses::is_declared` (or adding an analogous check) to cover deprecated class hashes, and invoking it in the `RunnableCompiledClass::V0(_)` branch before returning the cached class.

### Proof of Concept
1. Submit `declare` (Cairo0 class `C`) + `deploy` of contract `A` with class hash `C` in block `N`; the sequencer's `ContractClassManager` caches the compiled class for `C` via `set_and_compile` on first execution/access (see cache-miss path) [7](#0-6) .
2. Trigger a revert of block `N`'s state diff (supported operational flow): `deprecated_declared_classes` entry for `C` is deleted from storage, so `is_declared`/class-definition lookups for `C` now report "not declared" [4](#0-3) . Assume the deployment of contract `A` (or an equivalent contract still pointing at class hash `C`) persists in canonical state despite the declare being reverted.
3. Submit an `invoke` transaction calling contract `A`. Execution calls `get_class_hash_at(A)` → `C`, then `get_compiled_class(C)` → `get_compiled_from_class_manager(C)`. Because `C`'s compiled class is `RunnableCompiledClass::V0`, the code takes the `V0(_) => {}` branch and returns the cached class without calling `is_declared`, so the transaction executes successfully using code for a class that canonical state no longer declares.
4. A peer node without a warm cache entry for `C` executing the same transaction instead hits `state_reader.get_compiled_classes(C)` and fails with `UndeclaredClassHash`, diverging from step 3's node in transaction outcome and resulting state root.

fn delete_deprecated_declared_classes_block<'env>(
    txn: &'env DbTransaction<'env, RW>,
    block_number: BlockNumber,
    thin_state_diff: &ThinStateDiff,
    deprecated_declared_classes_block_table: &'env DeprecatedDeclaredClassesBlockTable<'env>,
) -> StorageResult<Vec<ClassHash>> {
    let mut deleted_data = Vec::new();
    for class_hash in thin_state_diff.deprecated_declared_classes.iter() {
        let declared_block_number = deprecated_declared_classes_block_table
            .get(txn, class_hash)?
            .ok_or_else(|| StorageError::DBInconsistency {
            msg: format!(
                "Attempting to revert declaration of class {class_hash} but it doesn't exist in \
                 the DB"
            ),
        })?;

        if block_number < declared_block_number {
            return Err(StorageError::DBInconsistency {
                msg: format!(
                    "Attempting to revert class {class_hash} at block {block_number} but DB shows \
                     it was first declared at later block {declared_block_number}"
                ),
            });
        }

        // Delete the class from the table only if it was first declared in this block.
        if block_number == declared_block_number {
            deprecated_declared_classes_block_table.delete(txn, class_hash)?;
            deleted_data.push(*class_hash);
        }
    }
    Ok(deleted_data)
