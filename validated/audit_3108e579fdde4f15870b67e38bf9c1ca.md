### Title
Inconsistent tenure-change duplicate-block validation between signer chainstate V1 and V2 causes signer signature-set divergence - (File: stacks-signer/src/chainstate/v1.rs, stacks-signer/src/chainstate/v2.rs)

### Summary
`validate_tenure_change_payload`, the check that rejects a tenure-change block proposal as `DuplicateBlockFound` when a competing block has already been accepted in the same tenure, uses two different strictness levels depending on which signer protocol version is active. The V1 implementation only looks at **globally accepted** blocks via `SignerDb::get_last_globally_accepted_block`, while the V2 implementation checks **locally or globally accepted** blocks via `SignerDb::get_last_signed_block`. Because both code paths remain reachable (protocol versions 0/1 negotiate to `SortitionStateVersion::V1`, version ≥ `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (2) negotiates to `V2`), the same duplicate tenure-change proposal can be rejected by V2 signers and accepted/signed by V1 signers, producing a validation verdict that different signers disagree on for the identical input.

### Finding Description
`stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` and only rejects with `RejectReason::DuplicateBlockFound` if a globally-accepted competing block already exists in that tenure: [1](#0-0) 

`stacks-signer/src/chainstate/v2.rs::validate_tenure_change_payload` instead calls `signer_db.get_last_signed_block(&block.header.consensus_hash)`, which additionally returns blocks in the `LocallyAccepted` state (per `SignerDb::get_last_signed_block`'s query on `state IN (GloballyAccepted, LocallyAccepted)`): [2](#0-1) [3](#0-2) 

This divergence is explicitly documented as intentional/known in the repo's own architecture notes, along with a regression test that only fixes the V2 path: [4](#0-3) [5](#0-4) 

Both code paths remain live: `SortitionStateVersion::from_protocol_version` maps any protocol version below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (= 2) to `V1`, and equal/above to `V2`: [6](#0-5) [7](#0-6) 

A test explicitly exercises a fleet running mixed versions 0, 1, and 2 concurrently, confirming V1 semantics are still reachable in production: [8](#0-7) 

**Equality broken:** all signers evaluating the same tenure-change block proposal against the same local SignerDb state should reach the same accept/reject verdict for "is this tenure-change block a duplicate of one we already accepted in this tenure?" Because V1 signers ignore `LocallyAccepted` competing blocks while V2 signers do not, this equality is broken purely as a function of which protocol version each signer negotiated to — no majority collusion or privileged access is required.

### Impact Explanation
A miner (or ordinary network race, since `LocallyAccepted` state is reached well before `GloballyAccepted`) can propose a second, competing tenure-change block for a tenure that already has a `LocallyAccepted` (but not yet `GloballyAccepted`) block. V2 signers will reject the second proposal outright (`DuplicateBlockFound`); V1 signers will not see any existing globally-accepted block yet and will proceed to validate and potentially sign it. This lets an adversarial or merely fast miner obtain V1-signer signatures on a competing tenure-change block that V2 signers have already vetoed, causing the two signer sub-populations to sign conflicting blocks for the same tenure height — a temporary tip disagreement among the signer set, and a path toward the kind of split-signature/duplicate-tenure-change conditions the `DuplicateBlockFound` check exists specifically to prevent.

### Likelihood Explanation
Triggering only requires: (1) at least one signer still negotiating to protocol version < 2 (a supported, tested configuration per `multiversioned_signer_protocol_version_calculation`), and (2) a miner proposing two competing tenure-change blocks for the same tenure within the window between local and global acceptance of the first — an ordinary racing condition rather than a rare or majority-requiring event. No signer or node private key, admin action, or majority coordination is needed; a single adversarial miner is sufficient.

### Recommendation
Make `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` use the same strict check as V2 (`get_last_signed_block`, or a shared helper) so that both protocol versions agree on the definition of "already accepted in this tenure" for the duplicate-block-found check, rather than gating the stricter semantics behind `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`.

### Proof of Concept
1. Configure a signer set where some signers negotiate to protocol version 0/1 (`SortitionStateVersion::V1`) and others to version ≥2 (`V2`), as exercised in `multiversioned_signer_protocol_version_calculation`.
2. Miner proposes tenure-change block `A` for tenure `T`; signers sign it and it reaches `LocallyAccepted` for both V1 and V2 signer subsets, but has not yet reached `GloballyAccepted` (e.g., due to network delay).
3. Miner immediately proposes a second, competing tenure-change block `B` for the same tenure `T`.
4. V2 signers call `validate_tenure_change_payload` → `get_last_signed_block(T)` → finds `A` in `LocallyAccepted` state → rejects `B` with `DuplicateBlockFound`.
5. V1 signers call `validate_tenure_change_payload` → `get_last_globally_accepted_block(T)` → finds nothing (since `A` is not yet `GloballyAccepted`) → does not reject on this basis, and proceeds to validate/sign `B`.
6. Result: V1-subset signers may produce valid signatures over `B` while V2-subset signers refuse it, splitting signer endorsement for tenure `T` between two competing blocks.

    /// Return the last signed block in a tenure (identified by its consensus hash).
    /// A block is considered signed if it is locally or globally accepted. Blocks that
    /// have only been pre-committed are excluded, because a pre-commit does not put a
    /// signature over the block and may be safely superseded by a competing proposal.
    ///
    /// This answers "what is the tenure's signed tip?", a different question from
    /// [`SignerDb::has_signed_block_in_tenure`]'s "does a signature bind us to this tenure?",
    /// which is why the predicates deliberately differ on rejected blocks (see there).
    pub fn get_last_signed_block(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<Option<BlockInfo>, DBError> {
        let query = "SELECT block_info FROM blocks WHERE consensus_hash = ?1 AND state IN (?2, ?3) ORDER BY stacks_height DESC LIMIT 1";
        let args = params![
            tenure,
            &BlockState::GloballyAccepted.to_string(),
            &BlockState::LocallyAccepted.to_string(),
        ];
        let result: Option<String> = query_row(&self.db, query, args)?;

        try_deserialize(result)
    }

            // We don't want the miner of the "inactive" sortition before the flash block

        },

            node_config.miner.block_commit_delay = Duration::from_secs(1);
