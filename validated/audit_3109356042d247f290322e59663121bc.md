I've confirmed the vulnerability in the NEAR Wallet Contract's `address_check_callback` and `nep_141_storage_balance_callback` functions. Both accept a `caller_deposit: Option<CallerDeposit>` parameter specifically designed to refund external callers' deposits on failure, but both silently drop this parameter on their intermediate `PromiseResult::Failed` branches — only the final `rlp_execute_callback` actually performs the refund.

### Title
Failure to refund external caller's attached deposit on intermediate promise failure in `WalletContract::address_check_callback` / `nep_141_storage_balance_callback` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (eth-implicit account emulation) tracks an external caller's attached deposit via `CallerDeposit` so it can be refunded if the emulated Ethereum transaction ultimately fails. However, this refund is only implemented in the terminal callback `rlp_execute_callback`. Two intermediate callbacks in the multi-step promise chains — `address_check_callback` (used for address-registrar lookups) and `nep_141_storage_balance_callback` (used for ERC-20 emulated transfers) — discard the `caller_deposit` parameter entirely when their own cross-contract call fails (`PromiseResult::Failed`), returning an error response without issuing any refund.

### Finding Description
`CallerDeposit::new` [1](#0-0)  creates a record of an external (non-self) caller's attached deposit specifically "to refund the caller's deposit if the cross-contract call fails" [2](#0-1) .

This `caller_deposit` is threaded through the multi-step promise chains for `EOABaseTokenTransfer` with address-check (`address_check_callback`) and `ERC20Transfer` (`nep_141_storage_balance_callback`) [3](#0-2) .

In `address_check_callback`, when the address-registrar lookup promise fails, the function returns immediately without ever using `caller_deposit`: [4](#0-3) 

Likewise in `nep_141_storage_balance_callback`, when the `storage_balance_of` lookup fails, the function returns immediately, again dropping `caller_deposit` without refunding: [5](#0-4) 

By contrast, the only place a refund is actually issued is in `rlp_execute_callback`, on the *final* promise's failure: [6](#0-5) 

Since the attached deposit was already transferred into the wallet contract's account balance as part of the `#[payable]` `rlp_execute` call [7](#0-6) , failing to emit the refund receipt on these intermediate failure paths leaves the caller's yoctoNEAR permanently inside the wallet contract's balance, with no code path left to reclaim it (the test suite even documents the intended refund-on-failure behavior at `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:170-189`, but only exercises the path through `rlp_execute_callback`, not `address_check_callback` or `nep_141_storage_balance_callback`).

### Impact Explanation
Any relayer or unprivileged caller can invoke `rlp_execute` on someone else's eth-implicit wallet contract, attaching a deposit, targeting either (a) an `EOABaseTokenTransfer` whose target requires an address-registrar lookup, or (b) an `ERC20Transfer` whose receiver's registration status must be checked via `storage_balance_of`. If the registrar or NEP-141 contract's promise fails (e.g., registrar/token account doesn't exist, is paused, or panics), the caller's attached deposit is silently absorbed into the target wallet's balance instead of being refunded — permanently frozen from the caller's perspective and an unearned balance increase for the wallet's owner. This is a concrete, transaction-triggered loss of funds for an unprivileged caller, matching "permanently frozen funds" / unauthorized value movement.

### Likelihood Explanation
This is trivially reachable: any account can call `rlp_execute` with a deposit and pick a `target` engineered to hit the address-registrar or NEP-141 storage-balance sub-call paths, and cause that sub-call to fail (e.g. calling `storage_balance_of` on a nonexistent/misconfigured token account, or a registrar lookup that panics/isn't deployed). No special privileges are required — an ordinary relayer or direct caller submitting a single transaction can trigger it every time these lookups fail.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, on the `PromiseResult::Failed` branch, issue the same caller-deposit refund logic currently only present in `rlp_execute_callback` (spawn a `promise_batch_create`/`promise_batch_action_transfer` to `caller_deposit.account_id` for `caller_deposit.yocto_near`) before returning the error `ExecuteResponse`.

### Proof of Concept
1. Deploy a `WalletContract` at an eth-implicit account `W`.
2. An external caller `C` (not `W` itself) calls `W.rlp_execute(target, tx_bytes_b64)` attaching a deposit `D`, where `tx_bytes_b64` encodes an emulated `EOABaseTokenTransfer` whose `to` address requires an address-registrar lookup (i.e., `target` is another eth-implicit-style address needing `address_check`), or an `ERC20Transfer` to an unregistered receiver on a token contract `T`.
3. `inner_rlp_execute` creates `CallerDeposit { account_id: C, yocto_near: D }` and schedules `address_registrar.lookup(...).then(W.address_check_callback(target, action, Some(caller_deposit)))` (or the NEP-141 storage-balance equivalent) [3](#0-2) .
4. Cause the registrar lookup / `storage_balance_of` call to fail (e.g., point `ADDRESS_REGISTRAR_ACCOUNT_ID` lookup at a non-existent contract, or make `token_id` a nonexistent/incompatible account).
5. `address_check_callback`/`nep_141_storage_balance_callback` observes `PromiseResult::Failed` and returns an error `ExecuteResponse` without refunding `caller_deposit` [8](#0-7) .
6. Observe: `C`'s balance decreased by `D` and `W`'s balance increased by `D` (net of gas), with `D` permanently unrecoverable by `C`, in contrast to the documented/tested behavior where failures at the final step do refund `C` (`test_caller_refunds`).
