### Title
Unbounded gzip decompression in `decompress_program` allows memory-exhaustion DoS via `starknet_estimateFee`/`starknet_simulateTransactions` (Declare v1) - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The JSON-RPC handler for legacy (Cairo0) declared contract classes decompresses the attacker-supplied `compressed_program` field with no size or ratio limit, unlike every other decompression path in the codebase (which all use `decode_and_decompress_with_size_limit` / bounded `.take()` readers). An unauthenticated RPC caller can submit a `starknet_estimateFee` or `starknet_simulateTransactions` request containing a `BroadcastedDeclareTransaction::V1` with a small, highly-compressed "gzip bomb" as `compressed_program`; the server will attempt to decompress it fully into memory before doing anything else, matching the CWE-770 memory-exhaustion pattern of GHSA-6p62-6cg9-f5f5 / CVE-2023-6337.

### Finding Description
`decompress_program` reads the base64-decoded bytes into a `GzDecoder` and calls `read_to_end` with an explicit `TODO` acknowledging the missing limit: [1](#0-0) 

This function is invoked when converting a deprecated (Cairo0) declare transaction's contract class from the wire format to the internal `starknet_api` type: [2](#0-1) 

That conversion runs on the `BroadcastedDeclareTransaction::V1 → ExecutableTransactionInput::DeclareV1` path used by the `starknet_estimateFee` and `starknet_simulateTransactions` RPC methods (both callable by any RPC client with a single, unsigned/unauthenticated call, as exercised by `broadcasted_to_executable_declare_v1` and `call_estimate_message_fee`/`call_simulate` tests) [3](#0-2) .

Every other decompression path in this codebase enforces an explicit size cap before or during decompression:
- `decode_and_decompress_with_size_limit` truncates the decompressor with `.take(max_size + 1)` and errors if the output exceeds the configured limit [4](#0-3) , and is used for the Sierra program on the actual gateway declare path (`DeprecatedGatewaySierraContractClass::convert_to_sierra_contract_class`) [5](#0-4) .
- The HTTP gateway additionally wraps the whole request body in a hard `RequestBodyLimitLayer`/`DefaultBodyLimit` to stop zip-bomb expansion at the transport layer [6](#0-5) .

`decompress_program`, by contrast, has neither a decompressed-size cap nor is it protected by an equivalent bound in the RPC server body-limit path (the RPC transport limit only bounds the compressed request bytes, not the decompression ratio inside `decompress_program`). A crafted, small `compressed_program` payload (a classic gzip bomb, e.g. compressing gigabytes of repeated zero bytes) will be expanded fully into a `Vec<u8>` in the node's memory before any size check occurs.

### Impact Explanation
Any RPC/full node exposing `starknet_estimateFee` or `starknet_simulateTransactions` can have its memory exhausted by a single crafted request, potentially causing the process to crash or the host to OOM. If the affected node is also serving other sequencer duties (e.g., co-located with the gateway/mempool component), a crash can disrupt transaction confirmation for the network segment served by that node — matching the "network unable to confirm new transactions" impact criterion. This is a concrete, low-cost, single-request denial-of-service, directly analogous in mechanism and severity to CVE-2023-6337.

### Likelihood Explanation
Likelihood is high: the RPC methods are unauthenticated and take arbitrary user-controlled `BroadcastedTransaction` objects; constructing a gzip bomb is trivial and well documented; no additional privileges, timing, or race conditions are required. The `TODO(dan): add time and size limits` comment already present in the code confirms this is a known, un-remediated gap.

### Recommendation
Bound the decompression in `decompress_program` the same way `decompress_with_size_limit` does elsewhere in the codebase: wrap the `GzDecoder` in a `.take(max_size)` reader (or reuse `decode_and_decompress_with_size_limit`) and reject the request with an RPC error if the decompressed size exceeds a configured maximum (e.g., matching `max_sierra_program_size`/`max_contract_class_object_size`). Apply this consistently to any other unbounded `GzDecoder`/`flate2` usage reachable from RPC input.

### Proof of Concept
1. Construct a `BroadcastedDeclareTransaction::V1` JSON body whose `contract_class.compressed_program` field is a base64-encoded gzip stream that decompresses to several GB (e.g., gzip of a few-hundred-KB payload compresses trivially to a very high ratio, or a "quine"-style repeated-zero gzip bomb achieving >1000x expansion).
2. Send it as a `starknet_estimateFee` or `starknet_simulateTransactions` JSON-RPC request to a node exposing the v0.8 RPC API.
3. `user_deprecated_contract_class_to_sn_api` → `decompress_program` calls `GzDecoder::read_to_end` with no cap, allocating the fully expanded payload in memory [7](#0-6) .
4. Repeated/parallel requests exhaust host memory, crashing the RPC node (or the OS OOM-killer terminates the process), consistent with the CVE-2023-6337 bug class.

**Note on confidence**: I was unable to fully trace how `SERVER_MAX_BODY_SIZE` (used elsewhere for RPC body limits, referenced in `crates/apollo_rpc/src/lib.rs` and `middleware.rs`) interacts with this specific code path — i.e., whether it is large enough that a single request could already exceed it before reaching `decompress_program`, or whether it only bounds the *compressed* wire body while decompression remains unbounded. Given typical gzip compression ratios (easily >100x, and bomb-crafted payloads far higher), even a body within a several-MB limit can still expand to gigabytes, so the vulnerability is very likely to remain exploitable regardless of the exact `SERVER_MAX_BODY_SIZE` value, but confirming the exact configured constant would strengthen the PoC.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
