### Title
Premature unlock of delegated resources via overwritten expire time in `addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` - (File: `FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource` calls `DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`, which unconditionally overwrites the stored `expireTimeForBandwidth`/`expireTimeForEnergy` with the newly computed `expireTime`, while additively summing the frozen balance. A second `FreezeBalanceContract` call with a shorter `frozenDuration` to the same `(ownerAddress, receiverAddress)` pair therefore shortens the lock time for the combined (larger) balance, and `UnfreezeBalanceActuator` will accept an early unfreeze of the entire combined amount once that shorter expire time passes.

### Finding Description
In `FreezeBalanceActuator.execute` (BANDWIDTH branch), when `receiverAddress` is set and `dynamicStore.supportDR()` is true, the code calls `delegateResource(ownerAddress, receiverAddress, true, frozenBalance, expireTime)` for every freeze transaction: [1](#0-0) 

That method fetches (or creates) the `DelegatedResourceCapsule` for the key and, on an existing entry, calls `addFrozenBalanceForBandwidth(balance, expireTime)`: [2](#0-1) 

`DelegatedResourceCapsule.addFrozenBalanceForBandwidth` sums the balance but sets `expireTimeForBandwidth` to whatever `expireTime` was passed in this call, with no comparison to the previously stored value: [3](#0-2) 

Because `expireTime = now + frozenDuration * FROZEN_PERIOD` is computed independently per call, a call with a smaller `frozenDuration` produces a smaller `expireTime`, which overwrites a previously-set larger `expireTime` even though the combined `frozenBalanceForBandwidth` now includes the amount from the earlier, longer-duration freeze. `FreezeBalanceActuator.validate` does not compare durations or reject shorter subsequent durations; it only requires `dynamicStore.supportDR()` and valid addresses. `UnfreezeBalanceActuator.validate` gates unfreezing solely on `delegatedResourceCapsule.getExpireTimeForBandwidth() > now`, so once the shorter expire time elapses, the full combined balance (both freezes) becomes eligible for unfreeze via `UnfreezeBalanceActuator.execute`, which unfreezes `delegatedResourceCapsule.getFrozenBalanceForBandwidth()` in its entirety: [4](#0-3) [5](#0-4) 

The identical overwrite pattern exists in `FreezeBalanceProcessor.delegateResource` (TVM native contract path) and for the ENERGY resource/`addFrozenBalanceForEnergy`. [6](#0-5) 

### Impact Explanation
Any account acting as the delegation owner can unilaterally shorten the effective lock period on an already-delegated (larger) balance by issuing a second `FreezeBalanceContract` with a smaller `frozenDuration` to the same receiver. This breaks the invariant that a locked/delegated balance remains locked for its committed duration, allowing the owner to reclaim the full combined delegated principal earlier than the receiver (or any external system relying on the original commitment) expects — undermining resource-delegation guarantees and any economic agreement predicated on the original freeze duration.

### Likelihood Explanation
Fully feasible with two ordinary, unprivileged transactions from the same owner account to the same receiver: preconditions are only `dynamicStore.supportDR() == true` (delegate-resource feature enabled) and no cap/limit on repeated freezes to the same `(owner, receiver)` pair — both of which hold in the current code, since `validate()` never checks the previous `expireTimeForBandwidth`/`expireTimeForEnergy` against the new one. It is fully repeatable and deterministic.

### Recommendation
In `DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`, set the new expire time to `Math.max(existingExpireTime, expireTime)` instead of unconditionally overwriting it, so that combining balances never shortens the lock period. Apply the same fix to the TVM path in `FreezeBalanceProcessor.delegateResource`.

### Proof of Concept
```java
// Extends FreezeBalanceActuatorTest, using supportDR()=true (dynamicStore.saveAllowDelegateResource(1))
@Test
public void testShortenDelegatedExpireTimeViaSecondFreeze() throws Exception {
  dbManager.getDynamicPropertiesStore().saveAllowDelegateResource(1);
  dbManager.getDynamicPropertiesStore().saveLatestBlockHeaderTimestamp(1_000_000L);

  long balance1 = 1_000_000_000L;
  long longDuration = 30;   // e.g. 30 days -> expireTime1 = now + 30*FROZEN_PERIOD
  FreezeBalanceActuator actuator1 = new FreezeBalanceActuator();
  actuator1.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getDelegatedContractForBandwidth(OWNER_ADDRESS, RECEIVER_ADDRESS, balance1, longDuration));
  TransactionResultCapsule ret1 = new TransactionResultCapsule();
  actuator1.validate();
  actuator1.execute(ret1);

  DelegatedResourceCapsule cap1 = dbManager.getDelegatedResourceStore().get(
      DelegatedResourceCapsule.createDbKey(
          ByteArray.fromHexString(OWNER_ADDRESS), ByteArray.fromHexString(RECEIVER_ADDRESS)));
  long expire1 = cap1.getExpireTimeForBandwidth();

  long balance2 = 1_000_000_000L;
  long shortDuration = 3; // shorter -> expireTime2 < expire1
  FreezeBalanceActuator actuator2 = new FreezeBalanceActuator();
  actuator2.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getDelegatedContractForBandwidth(OWNER_ADDRESS, RECEIVER_ADDRESS, balance2, shortDuration));
  TransactionResultCapsule ret2 = new TransactionResultCapsule();
  actuator2.validate();
  actuator2.execute(ret2);

  DelegatedResourceCapsule cap2 = dbManager.getDelegatedResourceStore().get(
      DelegatedResourceCapsule.createDbKey(
          ByteArray.fromHexString(OWNER_ADDRESS), ByteArray.fromHexString(RECEIVER_ADDRESS)));

  // Bug: expire time is overwritten to the shorter value instead of max(expire1, expire2)
  Assert.assertTrue(cap2.getExpireTimeForBandwidth() < expire1);
  Assert.assertEquals(balance1 + balance2, cap2.getFrozenBalanceForBandwidth());

  // Advance clock to just past the SHORT expire time (still well before the original long-duration commitment)
  dbManager.getDynamicPropertiesStore()
      .saveLatestBlockHeaderTimestamp(cap2.getExpireTimeForBandwidth() + 1);

  UnfreezeBalanceActuator unfreeze = new UnfreezeBalanceActuator();
  unfreeze.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getDelegatedUnfreezeContractForBandwidth(OWNER_ADDRESS, RECEIVER_ADDRESS));
  // Should not throw "It's not time to unfreeze." despite balance1's original long commitment not elapsed
  unfreeze.validate();
  TransactionResultCapsule unfreezeRet = new TransactionResultCapsule();
  unfreeze.execute(unfreezeRet);

  Assert.assertEquals(balance1 + balance2, unfreezeRet.getInstance().getUnfreezeAmount());
}
```
Expected result confirms the vulnerability: `cap2.getExpireTimeForBandwidth()` equals the shorter (second-call) expire time rather than `max(expire1, expire2)`, and `UnfreezeBalanceActuator` allows unfreezing the full combined balance (`balance1 + balance2`) before the originally committed long duration has elapsed.
