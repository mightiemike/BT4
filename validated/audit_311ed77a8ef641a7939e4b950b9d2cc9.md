## Title
TRX sent alongside a `CALL` to a precompiled contract address becomes permanently stuck - (`File: actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress()` unconditionally transfers any attached `endowment` (call value / TRX) to the target precompiled-contract address before invoking the precompiled logic, but none of the precompiled contracts (`RewardBalance`, `IsSrCandidate`, `VoteCount`, `GetChainParameter`, etc.) ever spend, forward, or refund that TRX. Because these are fixed system addresses (e.g. `0x1`–`0xa`, `0x100000...05`, etc.) with no associated private key, actuator, or withdrawal path, any TRX value attached to such a call is permanently locked — analogous to refunded ETH being stuck in `StaticAttester` because it lacks a withdrawal mechanism.

### Finding Description
In `callToPrecompiledAddress`, the endowment transfer is performed independent of whether the invoked precompiled contract actually uses value: [1](#0-0) 

The transfer itself is done via `MUtil.transfer`, which simply credits the target address's balance in the account store, with no check that the destination is a "real"/controllable account: [2](#0-1) 

Unlike the ordinary contract call path (`callToAddress`), which calls `createAccountIfNotExist` and treats the endowment as part of a real account balance that the target contract can subsequently use/withdraw, the precompiled-call path sends value to addresses like `rewardBalanceAddr`, `isSrCandidateAddr`, `voteCountAddr`, `getChainParameterAddr`, etc.: [3](#0-2) 

These precompiled contract implementations (e.g. `RewardBalance.execute`, `IsSrCandidate.execute`) only perform read/query logic and never move or refund the balance credited to their fixed address: [4](#0-3) 

There is no actuator, native-contract processor, or admin-only withdrawal function anywhere in the codebase that can move balance out of these precompiled addresses (they are not real accounts controlled by a private key and are excluded from normal transfer/withdraw actuators), so any TRX sent with such a call is permanently unspendable, similar to ETH being refunded to `StaticAttester` with no way to reclaim it.

### Impact Explanation
Any unprivileged user (EOA or smart contract) can execute a low-level `CALL` with nonzero `value` targeting a precompiled address (directly, or unintentionally through a Solidity `.call{value: x}()` on a system address, or a poorly validated external call target). The TRX is deducted from the sender and credited to a fixed, keyless system address, with no code path in java-tron to recover it. This constitutes a real accounting/state defect — TRX becomes permanently and irrecoverably locked (a subset of the network's circulating TRX becomes inaccessible), which is a genuine "stuck funds" impact analogous to the reported analog. It does not create a fund-theft or consensus-halt scenario, but it is a concrete, reachable loss-of-funds bug.

### Likelihood Explanation
Likely low-to-medium: it requires the caller to explicitly attach TRX value to a call at a precompiled address, which is not the common interaction pattern (most legitimate ABI calls to precompiles like `rewardBalance()` don't send value). However, it can happen accidentally (e.g., generic proxy/relayer contracts that forward `msg.value` to arbitrary target addresses, or fuzzing/mistake by a contract developer), and is trivially reproducible on demand by anyone.

### Recommendation
In `Program.callToPrecompiledAddress`, reject (or refund) any nonzero `endowment`/call value directed at a precompiled contract address before performing the transfer — i.e., enforce that `value` must be zero for the precompiled-address code path, mirroring the report's second recommended fix ("enforce that the value sent with these methods is always zero"), rather than silently crediting balance to an address that can never spend or return it.

### Proof of Concept
Conceptual PoC (not executed, based on code reading):
1. Deploy a simple Solidity contract with a function that does:
   `address(0x0000000000000000000000000000000000000000000000000000000001000005).call{value: 1_000_000}("")` (targeting `rewardBalanceAddr`, TRX precompile for `rewardBalance()`).
2. This reaches `Program.callToAddress`/`callToPrecompiledAddress` in the TVM with `msg.getEndowment().value() = 1_000_000` and `contract = rewardBalance`.
3. `MUtil.transfer` credits `1_000_000` sun to the fixed address `0x...1000005`, and `RewardBalance.execute(data)` is called, which only returns the caller's reward balance — it never touches or forwards the just-credited value.
4. Querying the balance of `0x...1000005` afterward shows the `1_000_000` sun sitting there permanently, with no actuator/native-contract/withdraw path in the codebase capable of moving it out (confirmed via search — no `createAccountIfNotExist`/withdraw hook exists for precompiled addresses, and `MUtil.transfer` performs an unconditional balance credit).

Note: Due to index size limits, exhaustive confirmation that literally zero code paths anywhere in the client can ever debit these fixed precompiled addresses could not be fully verified from the indexed subset; a full repository scan (e.g., via a Devin session) is recommended to confirm there is no hidden reclaim mechanism before treating this as fully confirmed.

    @Override

      long rewardBalance = VoteRewardUtil.queryReward(
          TransactionTrace.convertToTronAddress(getCallerAddress()), getDeposit());
      return Pair.of(true, longTo32Bytes(rewardBalance));
    }
  }

  public static class IsSrCandidate extends PrecompiledContract {

    @Override
    public long getEnergyForData(byte[] data) {
      return 20;
    }

    @Override
    public Pair<Boolean, byte[]> execute(byte[] data) {
      if (data == null || data.length != WORD_SIZE) {
        return Pair.of(true, dataBoolean(false));
      }

      byte[] address = new DataWord(data).toTronAddress();
      WitnessCapsule witnessCapsule = this.getDeposit().getWitness(address);
      if (witnessCapsule != null) {
        return Pair.of(true, dataBoolean(true));
      } else {
        return Pair.of(true, dataBoolean(false));
      }
    }
  }
