### Title
Potential divergence between Blockifier's strict duplicate-selector rejection and the Starknet OS's non-uniqueness-checking entry-point binary search - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/execute_entry_point.cairo)

### Summary
This is the closest reachable analog to the "one controller for two addresses" signature-collision bug class. In this codebase, entry-point selector resolution is performed independently in two components that must agree bit-for-bit: the Rust `blockifier` (used for live block building/execution) and the Cairo `starknet_os` program (used for STARK proving / re-execution). The blockifier explicitly detects and **rejects** duplicate selectors within an entry-point-type array (`PreExecutionError::DuplicatedEntryPointSelector`), while the OS's `get_entry_point`/`get_entry_point_offset` functions rely on `search_sorted_optimistic`, a binary search that assumes the array is strictly sorted/unique and does **not** independently verify uniqueness at lookup time.

### Finding Description
`EntryPointsByType::get_entry_point` and `resolve_entry_point_pc` in the blockifier filter all entry points of the requested type matching the selector and return `PreExecutionError::DuplicatedEntryPointSelector` if more than one match is found: [1](#0-0) [2](#0-1) 

The Starknet OS, however, resolves the same lookup using `search_sorted_optimistic`, a binary-search-style helper, without an equivalent post-search uniqueness check — it simply returns success on the first match found via binary search: [3](#0-2) [4](#0-3) 

Uniqueness/sortedness of entry points is enforced as a *pre-condition* in two other separate places: (1) the OS's own `validate_entry_points`/`deprecated_validate_entry_points` guards, which assert strictly-increasing selectors, invoked separately from the lookup path, and (2) the gateway's stateless declare-transaction validation (`validate_entry_points_sorted_and_unique`) for Sierra/Cairo1 declares only: [5](#0-4) [6](#0-5) 

Because entry-point uniqueness enforcement is split across three independently-maintained code paths (gateway stateless validation, OS-side `validate_entry_points`, and blockifier's `get_entry_point`), any gap in coverage (e.g., for deprecated Cairo0 declares, or a discrepancy in when/whether the OS's `validate_entry_points` check actually gets invoked before `get_entry_point`'s binary search) would let the blockifier and the OS disagree on whether a given transaction succeeds and what state it produces, exactly analogous to the original report's core risk: independent selector-based dispatch tables that are not jointly guaranteed to be collision-free by a single compiler/validator.

### Impact Explanation
If a compiled class could be declared/persisted whose entry points are not unique for a given `EntryPointType` and this state escapes the enforcement points, the sequencer's blockifier would deterministically reject calls to the colliding selector (transaction reverts / declare fails), while the OS re-execution (used to build the proof and verify block correctness) could silently resolve to one of the duplicate entries and successfully execute different code. This produces a state/root divergence between what the sequencer commits and what the OS proves, which maps to "wrong committed root" / inability to produce a valid proof for the block, i.e., a network unable to confirm/finalize the affected block.

### Likelihood Explanation
Low-to-uncertain. The gateway's `validate_entry_points_sorted_and_unique` closes this gap for Sierra/Cairo1 declares, and the OS's own `validate_entry_points`/`deprecated_validate_entry_points` are meant to independently enforce sortedness before the entry-point table is trusted. I could not confirm within the available index whether the equivalent stateful uniqueness check exists for legacy Cairo0 (`DeclareTransaction` V0/V1) classes in the blockifier's execution path (only the OS-side Cairo `deprecated_validate_entry_points` was found), nor could I confirm the exact call ordering guaranteeing `validate_entry_points` always runs before `get_entry_point`'s `search_sorted_optimistic` on every code path (including cached/re-used compiled class facts). This uncertainty means the finding should be treated as informational/needs-verification rather than a confirmed exploitable bug, consistent with how the original Sherlock report was ultimately downgraded to informational after review.

### Recommendation
Consolidate entry-point uniqueness/sortedness enforcement into a single authoritative check applied uniformly to both Cairo0 and Cairo1/Sierra classes, at declare time, and have both the blockifier's `EntryPointsByType::get_entry_point`/`resolve_entry_point_pc` and the OS's `get_entry_point`/`get_entry_point_offset` rely on that single guarantee rather than maintaining independent partial checks (compiler-adjacent gateway validation vs. Rust runtime duplicate-detection vs. Cairo OS strictly-increasing assertion). Add an explicit test asserting that `validate_entry_points`/`deprecated_validate_entry_points` is unconditionally invoked on every compiled-class fact before any `search_sorted_optimistic` lookup, for all class versions.

### Proof of Concept
Not constructible from the indexed code alone — exploitability hinges on confirming a legacy Cairo0 (or any) declare path that bypasses `validate_entry_points_sorted_and_unique` / `deprecated_validate_entry_points` before a compiled class's entry points are trusted by `get_entry_point`. This would require full repository access (e.g., a Devin session) to trace the complete `DeclareTransaction` validation call graph for all transaction versions and confirm whether such a gap exists in practice.

    compiled_class: CompiledClass*, execution_context: ExecutionContext*

    alloc_locals;
    // Get the entry points corresponding to the transaction's type.
    local entry_points: CompiledClassEntryPoint*;
    local n_entry_points: felt;

    tempvar entry_point_type = execution_context.entry_point_type;
    if (entry_point_type == ENTRY_POINT_TYPE_L1_HANDLER) {
        entry_points = compiled_class.l1_handlers;
        n_entry_points = compiled_class.n_l1_handlers;
    } else {
        if (entry_point_type == ENTRY_POINT_TYPE_EXTERNAL) {
            entry_points = compiled_class.external_functions;
            n_entry_points = compiled_class.n_external_functions;
        } else {
            assert entry_point_type = ENTRY_POINT_TYPE_CONSTRUCTOR;
            entry_points = compiled_class.constructors;
            n_entry_points = compiled_class.n_constructors;

            if (n_entry_points == 0) {
                return (success=1, entry_point=cast(0, CompiledClassEntryPoint*));
            }
        }
    }

    // The key must be at offset 0.
    static_assert CompiledClassEntryPoint.selector == 0;
    // TODO(Yoni, 1/1/2026): make sure the cost of searching missing keys is covered
    //   once reverted entrypoints are supported in the OS (should be fine).
    let (entry_point_desc: CompiledClassEntryPoint*, success) = search_sorted_optimistic(
        array_ptr=cast(entry_points, felt*),
        elm_size=CompiledClassEntryPoint.SIZE,
        n_elms=n_entry_points,
        key=execution_context.execution_info.selector,
    );
    if (success != FALSE) {
        return (success=1, entry_point=entry_point_desc);
    }

    return (success=0, entry_point=cast(0, CompiledClassEntryPoint*));
