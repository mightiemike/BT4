### Title
Function-call access key `allowance` limit is not enforced for actions executed via meta-transactions (`DelegateAction`) - (File: `runtime/runtime/src/actions.rs`)

### Summary
The `yield` bug in the reference report shows a "protective" value (the `sellBasePreview` amount) being consumed without ever being validated, so the intended check has no real effect. The nearcore analog is the `allowance` field of a `FunctionCallPermission` access key: this field is designed as a spending cap enforced by `verify_and_charge_tx_ephemeral`/`verify_access_key_permission` when a key is used to sign a normal transaction, but when the same restricted key is instead used to sign the inner `DelegateAction` of a meta-transaction, the allowance limit is silently skipped in `apply_delegate_action` (`runtime/runtime/src/actions.rs:460-535`). The cap that account owners rely on to bound the maximum funds a function-call key can spend is therefore ineffective whenever a relayer is used, exactly mirroring the "check is equivalent to setting `returned = 0`" pattern from the reference report.

### Finding Description
`FunctionCallPermission.allowance` is documented as "a balance limit to use by this access key to pay for function call gas and transaction fees" [1](#0-0) . For ordinary transactions this limit is checked and decremented during transaction verification (`NotEnoughAllowance` error path) [2](#0-1) .

However, when the very same key is used to sign a `DelegateAction` (the inner payload of a NEP-366 meta-transaction), the delegate action is processed by `apply_delegate_action`, which validates the signature, expiry, and sender match, and then calls `validate_delegate_action_key`, but never checks or decrements the signer's `allowance` before spawning the new receipt: [3](#0-2) . The relayer has already prepaid all fees, gas, and any attached deposit for the inner actions, and the comment in the code even acknowledges this fee model explicitly: [4](#0-3) .

This exact bypass is confirmed in nearcore's own architecture documentation: *"For allowance, however, there is no check. All costs have been covered by the relayer. Hence, even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work... if someone were to limit a function access key to one trivial action by setting a very small allowance, that is circumventable by going through a relayer."* [5](#0-4) 

This is structurally identical to the reference bug class: a value meant to gate/limit an operation (`sellBasePreview` in the reference, `allowance` here) is read/relied upon by the wallet/account model, but the enforcement code path that is supposed to validate it (`verify_and_charge_tx_ephemeral`'s allowance check) is not on the path actually taken when a relayer submits the action, making the "check" a no-op for that path.

### Impact Explanation
An account owner who issues a `FunctionCallPermission` access key with a deliberately small `allowance` — the intended security boundary limiting how much value/gas that specific key can ever spend (e.g. handing the key to a dApp, session, or automated agent, trusting that a compromised or malicious key can drain at most `allowance`) — gets no such protection once any relayer routes a `DelegateAction` signed by that key through a meta-transaction. Because deposits/gas are "prepaid" by the relayer and the delegate action still authorizes arbitrary permitted actions (`FunctionCall`, deposits within receiver/method restrictions) on the signer's account without decrementing or checking `allowance`, the value-limiting guarantee of the key is unauthorized/bypassed value movement relative to what the key owner configured and expects. This is a transaction-triggered logic flaw reachable by any unprivileged relayer/meta-transaction sender using a signature they obtained from (or is otherwise authorized by) the key holder for a supposedly bounded key.

### Likelihood Explanation
This requires no privileged access: any account can create a low-allowance `FunctionCallPermission` key and any relayer (an ordinary transaction submitter) can wrap a `DelegateAction` signed with that key. The path is exercised by ordinary meta-transaction usage (NEP-366), which is a first-class, actively used nearcore feature, and the bypass is deterministic and always present, not exploit-condition-dependent — the same code path runs on every delegate action regardless of relayer identity. The behavior is explicitly acknowledged in nearcore's own docs, confirming it is a known, real bypass in the current implementation rather than a hypothetical.

### Recommendation
Enforce (or explicitly, permanently deny) the `allowance` check for the signer's access key when processing `DelegateAction`/`DelegateV2` in `apply_delegate_action`, mirroring the same accounting used in `verify_and_charge_tx_ephemeral`. At minimum, decrement `allowance` by the equivalent cost the relayer prepays on the signer's behalf (or reject signing with allowance-limited function-call keys for meta-transactions), and update `validate_delegate_action_key` to surface an `InvalidAccessKeyError::NotEnoughAllowance`-style error consistent with the direct-transaction path so that the value-limiting semantics of `allowance` hold uniformly across both transaction and meta-transaction execution paths.

### Proof of Concept
1. Alice creates account `alice.near` and adds a `FunctionCallPermission` access key with `allowance = 1 NEAR`, `receiver_id = "app.near"`, restricted to method `"do_thing"`, intending that this key can never cost more than 1 NEAR in aggregate gas/fees even if leaked or misused.
2. A relayer receives (or obtains) a `SignedDelegateAction` signed by this key, calling `do_thing` with `gas` far exceeding what `1 NEAR` of allowance would cover.
3. The relayer wraps it into a `Transaction` with a `Delegate` action, signs with its own (unrelated, full-access) key, and submits it.
4. In `apply_delegate_action` (`runtime/runtime/src/actions.rs:460`), the code validates signature/expiry/sender but never inspects or decrements Alice's key allowance before spawning the inner receipt [6](#0-5) ; the action executes fully, consuming gas well beyond the 1 NEAR allowance ceiling that Alice believed capped this key's usage, exactly as nearcore's own docs describe: *"even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work"* [7](#0-6) .

## Function access keys in meta transactions

Assume alice sends a meta transaction and signs with a function access key.
How exactly are permissions applied in this case?

Function access keys can limit the allowance, the receiving contract, and the
contract methods. The allowance limitation acts slightly strange with meta
transactions.

But first, both the methods and the receiver will be checked as expected. That
is, when the delegate action is unwrapped on Alice's shard, the access key is
loaded from the DB and compared to the function call. If the receiver or method
is not allowed, the function call action fails.

For allowance, however, there is no check. All costs have been covered by the
relayer. Hence, even if the allowance of the key is insufficient to make the call
directly, indirectly through meta transaction it will still work.

This behavior is in the spirit of allowance limiting how much financial
resources the user can use from a given account. But if someone were to limit a
function access key to one trivial action by setting a very small allowance,
that is circumventable by going through a relayer. An interesting twist that
comes with the addition of meta transactions.
