### Title
Vote-reward index accumulation truncates to zero for small per-cycle rewards, causing voters to permanently lose their share of that cycle's reward - (File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java)

### Summary
The reported bug pattern is: a transferred/allocated amount is divided by a large denominator to compute a per-share accumulator (`accRewardPerGns`), and when the amount is small relative to the denominator, integer division truncates the increment to zero — silently discarding the reward even though the underlying value was actually moved into the pool. The same structural pattern exists in java-tron's SR voting-reward accumulator (`Vi`, "value per vote"), used to distribute per-cycle block/fee rewards to voters proportionally to their vote weight.

### Finding Description
When a block is produced, `Manager.payReward` calls `MortgageService.payBlockReward`/`payTransactionFeeReward`, which invoke `payReward`, adding the (post-brokerage) reward for that cycle to the witness's total via `delegationStore.addReward(cycle, witnessAddress, value)`: [1](#0-0) 

Later (in `RewardViCalService`/`DelegationStore`), this per-cycle reward is converted into a delta of the accumulator `Vi` that voters use to compute their share: [2](#0-1) [3](#0-2) 

```
BigInteger deltaVi = BigInteger.valueOf(reward)
    .multiply(DECIMAL_OF_VI_REWARD)
    .divide(BigInteger.valueOf(voteCount));
setWitnessVi(cycle, address, preVi.add(deltaVi));
```

This is structurally identical to the reported bug: `rewardState.accRewardPerGns += (amountToken * precisionDelta * 1e18) / gnsBalance`. If `reward * DECIMAL_OF_VI_REWARD` is smaller than `voteCount`, `deltaVi` truncates to `BigInteger.ZERO`. Since `preVi` is unchanged, that entire cycle's reward becomes permanently unrecoverable by any voter — the reward was already recorded/allocated for the witness's cycle (`delegationStore.addReward`) and is treated as fully distributed once `Vi` is updated for that cycle, yet no voter's `computeReward` (`VoteRewardUtil.computeReward` / `MortgageService.computeReward`) will reflect it because the delta between the `Vi` snapshots at `beginCycle` and `endCycle` is zero: [4](#0-3) [5](#0-4) 

Whether `DECIMAL_OF_VI_REWARD`'s magnitude is large enough in all realistic conditions (small transaction-fee-pool rewards divided among a witness with a very large total vote count) is something I could not fully verify — the index search did not return its declared constant value, and I could not load `DelegationStore.java` in full to confirm the exact scaling factor or any additional minimum-reward guard. This is an important open question: if the constant is not large enough relative to realistic `voteCount` magnitudes (which can be very large, since votes are TRX-power-based and can total in the billions), the truncation-to-zero condition described in the report is reachable in production without any privileged actor involved — it is triggered purely by normal block production and normal voting, i.e., reachable from ordinary transactions (`FreezeBalanceContract`/`VoteWitnessContract`) and the block reward/fee-pool distribution path.

### Impact Explanation
If triggered, this causes silent reward accounting loss: a cycle's reward is treated as "distributed" (Vi is updated, even if the delta is zero) so voters who query/withdraw rewards via `GetRewardServlet`, `WithdrawRewardProcessor` (TVM `withdrawreward`), or `MortgageService.withdrawReward` never receive the value for that cycle, while the reward already left the transaction-fee pool / block reward budget. This is an accounting-corruption class issue (permanent value leakage from the reward system), matching the "Medium" impact of the original finding since funds aren't stolen but rewards are silently zeroed and lost.

### Likelihood Explanation
This requires no privileged actor and is reachable via ordinary node operation (block production, fee pool distribution, and votes with sufficiently large `voteCount` relative to the resulting reward), which fits the "unprivileged analog" requirement. However, I was unable to confirm the exact value of `DECIMAL_OF_VI_REWARD` or whether other safeguards (e.g., minimum reward-per-vote enforcement, or that `TRANSACTION_FEE_POOL_PERIOD` division keeps per-cycle rewards large enough) prevent this in practice. Given the inability to fully verify the scaling constant and boundary conditions, I can't assert this is definitely exploitable at current network parameters — it is a plausible structural analog but unconfirmed as an active vulnerability.

### Recommendation
Confirm the value and precision headroom of `DECIMAL_OF_VI_REWARD` against realistic `voteCount` ranges; if truncation to zero is reachable, either increase its scaling factor, accumulate remainder/dust across cycles instead of discarding it, or defer/aggregate small rewards until they exceed a safe minimum before applying the division, mirroring the fix suggested in the original report (raise the effective "minimum trade size" so the resulting derived value can't round to zero).

### Proof of Concept
Not able to construct a concrete on-chain PoC without confirming `DECIMAL_OF_VI_REWARD`'s value and the achievable range of `voteCount`/per-cycle `reward`; this would require running the node with a witness having an extremely large total vote count and a very small transaction-fee-pool reward for a cycle, then verifying `getWitnessVi(cycle, srAddress)` stays unchanged (`deltaVi == 0`) while `delegationStore.getReward(cycle, srAddress) > 0`, and that voters' `queryReward` doesn't reflect the difference.

    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);

    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
