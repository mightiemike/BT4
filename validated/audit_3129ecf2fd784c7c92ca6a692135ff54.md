### Title
Replay/audit verification silently ignores state-checkpoint and position-state root divergence, allowing corrupted committed state to pass authenticated replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the integrity check used by replay/audit tooling to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` stored in the ledger accumulator. The function checks status, gas, write-set hash, and event-root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that authenticate the Sparse Merkle / Jellyfish Merkle roots for main state, hot state, and the new native-position (trading) state. This mirrors the EigenLayer bug class: a state-commitment quantity (there, "queued slashable shares"; here, "checkpoint root hashes") is excluded from the tracking/verification path that is supposed to bind committed data to what was actually produced, silently under-verifying the ledger state.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is defined at: [1](#0-0) 

It validates:
- execution status vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- write-set hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

But right before returning `Ok(())`, the code contains an explicit acknowledgment that it does **not** validate the checkpoint hashes: [2](#0-1) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
```

This means `state_checkpoint_hash` (SMT root of world state, `TransactionInfoV0`/`V1`), `hot_state_checkpoint_hash` (JMT root of hot state, gated by `HOT_STATE_ROOT_IN_TXN_INFO`), and `position_state_checkpoint_hash` (JMT root of the native-position/trading state, gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) are all committed into `TransactionInfoV1` at execution time: [3](#0-2) 

and are populated during ledger update via `assemble_transaction_infos`: [4](#0-3) 

and computed during state checkpointing via `DoStateCheckpoint::run`, including the position-state root path gated by `compute_trading_native_state_roots`: [5](#0-4) 

These roots are hashed into `TransactionInfo`, which is the leaf hashed into the transaction accumulator — i.e., they are part of the authenticated, consensus-committed ledger state. `ensure_match_transaction_info` is the function `db-tool`'s `replay_on_archive` (and `aptos-move/cli`) use to confirm a locally re-executed transaction actually matches the authenticated on-chain record: [6](#0-5) 

Because the checkpoint-hash comparisons are omitted, if a bug in `DoStateCheckpoint::compute_position_checkpoint` (or the hot-state root computation) produces a wrong root — e.g. from the `native_position_iter()` write collapsing logic, or a discrepancy in how `parent`/`persisted` position summaries are seeded across restarts — `ensure_match_transaction_info` will still return `Ok(())` as long as the write-set bytes, events, gas, and status match. Replay-verification and other tooling built on this comparator can therefore certify "successful replay" even though the authenticated position/hot/state root diverges from what local execution actually produced.

### Impact Explanation
This breaks the state-commitment/proof-integrity invariant that "authenticated API or state-view output stay bound to the right ledger version, root, and object." A silent state-checkpoint-hash mismatch means:
- A corrupted or incorrectly computed state/hot-state/position-state root can be replayed and "verified" as correct by db-tool's replay-verify pipeline, masking a genuine divergence in committed ledger state.
- This is exactly the kind of gap the original report criticizes: a specific state-commitment quantity is excluded from the tracking/verification path, undermining trust in derived guarantees (there, burnable shares; here, root-hash equivalence used to detect forks/corruption during replay).
- Given `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` are relatively new features being staged for mainnet, an unnoticed divergence in these roots would not be caught by the standard audit/replay tooling, delaying detection of a hard-fork-causing bug.

### Likelihood Explanation
The gap is explicit and acknowledged in-code via the TODO, confirming it is a known, currently-present limitation rather than speculation. It only manifests once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (feature flag 122) and/or `HOT_STATE_ROOT_IN_TXN_INFO` (feature flag 123) are enabled on-chain, which the code marks as gated but not yet safe to enable per the TODO's own instruction ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"). This indicates the feature is still being staged, but the comparator gap exists in the codebase now and would need to be fixed before those flags are safely turned on in production.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the locally recomputed values whenever they are present (`Some`) in `txn_info`, mirroring the existing `write_set_hash`/`event_root_hash` checks, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or `HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet.

### Proof of Concept
Not applicable as a runnable exploit — this is a verification-logic gap rather than an externally triggerable state corruption. The proof is the code path itself: `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) omits equality assertions on the three checkpoint-hash fields that are populated by `assemble_transaction_infos` (execution/executor/src/workflow/do_ledger_update.rs:95-121) from roots computed in `DoStateCheckpoint::run`/`compute_position_checkpoint` (execution/executor/src/workflow/do_state_checkpoint.rs:36-190), and is invoked by `replay_on_archive` (storage/db-tool/src/replay_on_archive.rs) as the sole match-check between re-executed output and the authenticated ledger record.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
