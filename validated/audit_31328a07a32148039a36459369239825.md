## Title
Maker's fill quantity rounded down in TRC10 DEX order matching, systematically underpaying makers - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
Java-tron's on-chain TRC10 exchange (`MarketSellAssetActuator`) matches a taker order against resting maker orders and, whenever the maker's entire remaining sell quantity is consumed, computes the amount of `buyToken` the maker receives via `MarketUtils.multiplyAndDivide`, which always rounds the result **down**. This is the same rounding-direction bug class as the Bond `_currentMarketPrice` issue: the counter-value owed to the party giving up its asset (here, the maker) is computed with floor division instead of being rounded in the maker's favor, so the maker is paid strictly less than the exact contractual ratio dictates.

### Finding Description
`MarketUtils.multiplyAndDivide(a, b, c, disableMath)` computes `floor(a*b/c)`: [1](#0-0) 

In `MarketSellAssetActuator.matchSingleOrder`, when the taker's remaining sell quantity exactly matches the maker's remaining sell quantity, or when the taker's demand exceeds the maker's remaining supply, the amount the maker receives (`makerBuyTokenQuantityReceive`) is derived from this same floor-rounded helper: [2](#0-1) [3](#0-2) 

In both cases, `makerBuyTokenQuantityReceive = makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity`, rounded down. Since the maker is giving up its entire `makerSellRemainQuantity` of the sell token (which is deducted from the maker's order in full — see `makerOrderCapsule.setSellTokenQuantityRemain(0)`), the fair-value amount owed to the maker for that exact quantity should be rounded up (or at least not down) to avoid shortchanging the party that is fully consumed. Instead, `floorDiv` guarantees the maker receives `≤` the exact ratio value, with the truncated remainder simply lost (not credited to anyone), directly analogous to how Bond's `_currentMarketPrice` rounded the maker's selling price down instead of up.

By contrast, the taker's own remaining amount is never subjected to this same lossy floor calculation in the "taker < maker" case — the taker's exact remaining sell quantity is transferred to the maker without loss — showing the asymmetry falls specifically on the maker in the other two branches.

### Impact Explanation
Every matched maker order whose full remaining quantity is filled (the common "taker==maker" and "taker>maker" cases) loses the fractional remainder of `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity` due to floor division. This is a systemic, per-trade underpayment of resting limit-order makers on the TRC10 exchange, silently destroying value on every trade that fully consumes a maker order — an accounting/settlement correctness defect affecting ordinary DEX users (makers), not a privileged role.

### Likelihood Explanation
This code path executes on every `MarketSellAssetContract` transaction that matches against and fully consumes an existing resting order — i.e., on essentially every trade in the built-in TRC10 exchange, since exact-match and over-fill scenarios are extremely common. No special privileges or preconditions are required; any user submitting a `MarketSellAssetContract` transaction can trigger the underpayment against any maker whose order is present in the order book.

### Recommendation
Round the maker's fill amount up (ceiling division) instead of down when the maker's remaining quantity is fully consumed, e.g., change `multiplyAndDivide` usage for `makerBuyTokenQuantityReceive` to a ceiling-rounding variant (`ceilDiv(a*b, c)`), consistent with protecting the party whose order is being fully closed out, mirroring the Bond Protocol fix of switching `mulDiv` to `mulDivUp` in `_currentMarketPrice()`.

### Proof of Concept
Given a maker order with `makerSellQuantity = 3`, `makerBuyQuantity = 2` (sells 3 unit A for 2 unit TRX), and a taker whose remaining sell (TRX) exactly matches the maker's remaining sell quantity of A (`makerSellRemainQuantity = 1`, e.g. due to a prior partial fill):
- `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 2, 3) = floor(2/3) = 0`
- The maker's remaining sell quantity is set to `0` (fully consumed) per [4](#0-3) 
but the maker is credited `0` buyToken, i.e., the maker gave away its last unit of `A` for free — the fractional `2/3` TRX is simply lost rather than rounded in the maker's favor.
