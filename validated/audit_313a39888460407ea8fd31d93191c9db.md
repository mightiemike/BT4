Based on my investigation, I found a legitimate, code-documented integrity gap in the transaction-output-to-transaction-info verification path.

### Title
`ensure_match_transaction_info` skips state/position checkpoint hash verification, allowing a diverging authenticated state root to pass chunk-executor replay verification - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant used to confirm that a locally re-executed `TransactionOutput` matches an already-authenticated `TransactionInfo` (the leaf committed into the transaction accumulator and covered by the ledger-info signature). It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or the newer `position_state_checkpoint_hash` field, as flagged by its own TODO comment. [1](#0-0) 

### Finding Description
`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and a repurposed `position_state_checkpoint_hash` field, all of which are part of the hashed, ledger-info-signed commitment for a transaction/checkpoint. [2](#0-1) 

However, `ensure_match_transaction_info` — the function responsible for proving that a locally computed `TransactionOutput` is consistent with the trusted `TransactionInfo` — never re-derives or compares these checkpoint hashes against the locally computed state. This function is not confined to a debug tool: it is invoked from `ChunkExecutorInner::verify_execution` in the chunk executor, which is part of the state-sync "execute and verify" path used when a node backfills/verifies a range of transactions against already-authenticated `TransactionInfo`s. [3](#0-2) 

Because only `write_set` (state_change_hash) and `event_root_hash` are checked, the function proves that the *incremental* change produced by a transaction is correct, but it does not prove that applying that change to the previous (already-verified) state actually produces the correct new checkpoint root — i.e., a bug anywhere in the Sparse-Merkle/Jellyfish state-computation or in the newer "trading-native" position-state computation (guarded by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature) would go completely undetected by this check, even though the corresponding checkpoint hash field exists precisely to catch such divergence.

### Impact Explanation
If the state or position checkpoint root ever diverges from the correct VM/state result (e.g., due to a bug in state-tree construction, hot-state computation, or the position/order-book state root introduced for `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), a node performing state-sync/backfill verification through `ChunkExecutorInner::verify_execution` would accept and commit the divergent state as valid, since the only fields validated are gas/status/write-set-hash/event-root-hash, not the state checkpoint commitments. This matches the "hard-fork-only divergence during commit, replay, restore, or proof verification" and "committed state that differs from the correct VM result" impact classes: the on-disk ledger state a syncing node ends up with could silently diverge from the authenticated commitment while all currently enforced invariants in `ensure_match_transaction_info` still report success.

### Likelihood Explanation
The gap is structural, not a hypothetical edge case — the code deliberately omits verification of `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, and the surrounding TODO comment acknowledges this exact risk ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"). The trigger condition is any bug (present or future) in the state-checkpoint/position-state computation path becoming active once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, at which point this verification gap becomes the only thing standing between a computation bug and silent state divergence on any node using the chunk-executor verify path.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against the actual post-apply state roots before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the existing TODO already recommends, so that `ChunkExecutorInner::verify_execution` and `replay_on_archive` cannot report success on a divergent state root.

### Proof of Concept
Not directly exploitable today because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` gates the position-state root computation, but the code path is already wired into the production `verify_execution` flow, so any future computation bug in that gated feature (or in `hot_state_checkpoint_hash` computation, which is not feature-gated) will not be caught by `ensure_match_transaction_info`, as demonstrated by the check omission at [4](#0-3) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
