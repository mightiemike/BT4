### Title
Unbounded duplicate growth in `KVSessionStorage`'s shop session-id index via repeated `storeSession` calls (token exchange) causes DoS of `findSessionsByShop` / auth handlers - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession` unconditionally appends the session id to the shop's tracked id list every time it's called, without checking whether that id already exists in the list, unlike the equivalent `RedisSessionStorage` implementation, which explicitly dedupes.

### Finding Description
`storeSession` calls `addShopIds(session.shop, [session.id])` on every invocation: [1](#0-0) 

`addShopIds` reads the existing array for the shop key and blindly concatenates the new id(s) onto it with no `includes`/dedup check: [2](#0-1) 

This is the KV-storage analog of the Bribe.sol "deposit without matching accounting on repeated calls" bug class: an accumulator (`shopIds` list, analogous to `totalVoting`) grows every time the "deposit" function (`storeSession`) runs, but nothing ever checks for or collapses duplicate entries for the same underlying id — only `removeShopIds` (analogous to `withdraw`) does bulk filtering, and only fires on explicit deletion.

Critically, `storeSession` for the *same* session id (`offline_<shop>`) is called repeatedly in normal, unprivileged flows — every token-exchange authentication request where the cached offline/online session is missing or close to expiry re-stores the session: [4](#0-3) [5](#0-4) 

Each such call appends another copy of the same session id into `shop:<shop>`'s KV array. In contrast, `RedisSessionStorage.addKeyToShopList` — implementing the identical `SessionStorage` interface for the same purpose — guards against this exact scenario: [3](#0-2) 

The absence of the equivalent check in the KV adapter is the root cause.

### Impact Explanation
Because a single merchant's app simply re-triggering token exchange (e.g. through repeated App Bridge session-token refreshes near expiry, or through automated retries after 401s) causes unbounded, ever-growing duplication in the `shop:<shop>` KV entry, this can:
- Cause `findSessionsByShop` to perform increasingly many redundant `loadSession` KV reads per call, degrading/failing auth-dependent code paths that rely on it (app-installation checks, multi-session listing).
- Eventually cause the `shop:<shop>` KV value to exceed platform size limits (e.g. Cloudflare KV's 25 MB per-value cap) so `namespace.put` in `addShopIds` fails, breaking `storeSession` for that shop going forward and thus bricking the OAuth/token-exchange auth handler for that shop.

This matches "Griefing" (no attacker profit motive, but degraded/broken behavior for the shop) and potentially "DoS of an auth handler," since `storeSession`/`findSessionsByShop` sit directly in the token-exchange authentication path.

### Likelihood Explanation
Requires no privilege beyond being the shop/app itself — this can occur through entirely legitimate, unprivileged usage patterns (repeated token exchanges due to near-expiry sessions, client retries, or a malicious/compromised frontend intentionally hammering the token-exchange endpoint with a valid session token to force store/reload cycles). Only apps that opt into `KVSessionStorage` (e.g. on Cloudflare Workers) are affected.

### Recommendation
Mirror the Redis adapter's approach in `KVSessionStorage.addShopIds`: check for existing membership before appending, e.g.:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Configure an embedded app with `KVSessionStorage` and token exchange enabled.
2. Repeatedly call the token-exchange authenticated endpoint with a session token whose corresponding offline session is expired/near-expiry (or force expiry each time in a test), so `performTokenExchange`/the remix `authenticate` strategy re-runs `config.sessionStorage.storeSession(offlineSession)` with the same `offline_<shop>` id on every call.
3. After N repeated calls, inspect the KV entry at key `shop:<shop>` and observe the id list contains N duplicate entries of `offline_<shop>` instead of one.
4. Call `findSessionsByShop(shop)` and observe it performs N redundant `loadSession` calls; continuing to grow N (e.g., via automated retries) will eventually make the `shop:<shop>` value exceed the KV value size limit, causing `addShopIds`'s `namespace.put` to throw and `storeSession` to fail for that shop.
