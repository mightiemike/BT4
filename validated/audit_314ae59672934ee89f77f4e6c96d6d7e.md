### Title
Inconsistent Token Precision Between V1 and V2 Asset Stores Causes Misinterpreted Token Amounts - (File: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
When a TRC10 token is issued while `AllowSameTokenName` is disabled, `AssetIssueActuator.execute()` persists two different `precision` values for the *same* token: the value the issuer actually requested (0–6, validated in `validate()`) into the legacy `AssetIssueStore`, and a hardcoded `0` into `AssetIssueV2Store`. Any client, wallet, or exchange reading the token metadata through the V2 store (or through APIs backed by it) will treat the token as having 0 decimals, while clients reading the V1 store will treat it as having the issuer-configured precision (up to 6). This is the same class of bug as the ckrBTC finding: the same asset is represented with two inconsistent decimal precisions depending on which store/API is queried, causing under/over-valuation and transaction amount confusion.

### Finding Description
`AssetIssueActuator.execute()` handles asset creation: [1](#0-0) 

When `dynamicStore.getAllowSameTokenName() == 0`, the code explicitly overwrites the V2 capsule's precision to `0` via `assetIssueCapsuleV2.setPrecision(0)` before storing it, while `assetIssueCapsule` (written to `AssetIssueStore`, the V1 store) keeps the precision value taken directly from the submitted `AssetIssueContract`, which `validate()` allows to be between 0 and `ActuatorConstant.PRECISION_DECIMAL` (6): [2](#0-1) [3](#0-2) 

This is not test-only behavior — the actuator's own test suite documents and asserts this exact inconsistency: for the same asset the V1 capsule ends up with `precision == 6` while the V2 capsule ends up with `precision == 0`: [4](#0-3) 

The same forced-zero behavior also appears in the migration helper `AssetUpdateHelper.updateAsset()`, and in test setup code, confirming it is a deliberate, systemic pattern rather than an isolated bug: [5](#0-4) 

The `AssetIssueContract` protobuf message (`precision` field 7) is broadcast by an anonymous user via a standard transaction and is the canonical, on-chain source of the token's decimal metadata: [6](#0-5) 

### Impact Explanation
Any downstream consumer (wallet, exchange, DEX, block explorer, smart-contract tooling) that reads token metadata via the V2-store-backed query path will believe the token has 0 decimals, while consumers reading the legacy V1-store path will use the issuer's actual precision (up to 6). Because token balances/amounts (e.g., in `TransferAssetContract.amount`, `ParticipateAssetIssueContract.amount`) are raw integer "drops" with no embedded decimal marker, a mismatch in the assumed `precision` directly causes a display/interpretation error of up to 10^6x, leading to users misjudging balances, mispricing trades, or entering transaction amounts that are off by orders of magnitude — the same "medium" impact category the original ckrBTC finding was rated at (asset overvaluation/undervaluation confusion, not fund loss by itself, but real potential for user error and mispriced integrations).

### Likelihood Explanation
This triggers deterministically for every TRC10 asset issued while `AllowSameTokenName == 0` and a non-zero precision is requested — no privileged access, malicious peer, or special conditions are required; it is a straightforward consequence of processing a standard, permissionless `AssetIssueContract` transaction. Given `AllowSameTokenName` is a legacy/historical proposal-controlled flag, this primarily affects assets issued during that window, but those tokens remain live and queryable indefinitely afterward via both storage paths.

### Recommendation
Persist the same, issuer-specified `precision` value consistently in both `AssetIssueStore` and `AssetIssueV2Store` (or clearly document/enforce that V1-store precision is deprecated to 0 and require all downstream tooling to exclusively read from V2). At minimum, add a migration/consistency check so that any TRC10 token exposed through wallet/gRPC/HTTP APIs reports a single canonical `precision`, eliminating the divergence between `assetIssueCapsule` and `assetIssueCapsuleV2` in `AssetIssueActuator.execute()`.

### Proof of Concept
1. Ensure `AllowSameTokenName` dynamic property is `0`.
2. Broadcast an `AssetIssueContract` with `precision = 6`.
3. Observe `AssetIssueActuator.execute()` stores `precision = 6` in `AssetIssueStore` (V1) but forcibly stores `precision = 0` in `AssetIssueV2Store` (V2), as reproduced by the existing unit test: [4](#0-3) 
4. Query the same token via any API/tool that reads from the V2 store vs. one that reads the V1 store — the reported decimal precision differs (0 vs 6), causing the same amount of raw token units to be interpreted as vastly different human-readable quantities.
