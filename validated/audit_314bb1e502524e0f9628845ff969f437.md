### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash comparison, letting replay-verify accept a diverged authenticated state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the check used by replay/verification tooling (e.g. `db-tool`'s `replay_on_archive`, `aptos-debugger`) to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` recorded on-chain/in a backup. The function validates status, gas, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that carry the authenticated Sparse-Merkle / native-position state roots.

### Finding Description [1](#0-0) 

The function checks `status`, `gas_used`, `write_set_hash` against `txn_info.state_change_hash()`, and `event_root_hash`, but the comment block explicitly states:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is directly wired into `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes archived transactions with the VM and calls `ensure_match_transaction_info` per transaction to decide pass/fail: [3](#0-2) 

The three unchecked fields (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) are precisely the Merkle roots that `TransactionInfoV1`/`TransactionInfoV0` carry as the authenticated "root hash of the Sparse Merkle Tree describing the world state" and its hot/position extensions: [4](#0-3) 

Because these are never compared to the locally recomputed checkpoint hashes (which are computed elsewhere, in `DoStateCheckpoint::run` / `compute_position_checkpoint`, and folded into `TransactionInfo` via `assemble_transaction_infos`), any divergence between the locally executed world-state root and the authenticated on-chain root for a given transaction is silently ignored by this verification path: [5](#0-4) [6](#0-5) 

This feature gate (`compute_trading_native_state_roots`) is derived from on-chain `Features`, meaning once the corresponding feature flags are enabled on-chain, `TransactionInfoV1.position_state_checkpoint_hash` becomes an authenticated field that this replay tool is supposed to validate but does not: [7](#0-6) 

### Impact Explanation
`ensure_match_transaction_info` is a proof/commitment-integrity check: it is the mechanism that binds a locally re-executed result to the authenticated `TransactionInfo` from the ledger/backup. By omitting the checkpoint-hash comparisons, the replay-verify tool can report a "verified" / consistent result even though the locally computed world-state root (main state, hot state, or native-position state) diverges from the authenticated on-chain root for that transaction. This is a hard-fork-only-type divergence during replay/verification: a state root corruption or non-determinism bug in state-checkpoint or position-checkpoint computation would go undetected by exactly the tool meant to catch such divergences, undermining confidence in replayed/restored ledger data and any auditing built on top of it (e.g. security incident response, chain consistency audits, disaster recovery validation).

### Likelihood Explanation
The gap is unconditional (it exists in all invocations of `ensure_match_transaction_info`, not just when `compute_trading_native_state_roots` is set), but its dangerous case — a divergence that would otherwise be caught by the missing checks — is contingent on: (1) transaction_info_v1 being active (so state/hot-state checkpoint hashes are actually populated), and (2) an underlying nondeterminism/bug or corrupted replay producing a different world-state root while still reproducing the same write-set/events/status/gas. This is a narrower trigger condition than a straightforward bug, and the code's own TODO shows this is a known, not-yet-addressed gap gated behind enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, which appears to still be work-in-progress/not fully enabled on mainnet.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`-derived (or caller-supplied) `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields on `txn_info`, following the same pattern used for `state_change_hash`/`event_root_hash`, before any code path that depends on `compute_trading_native_state_roots` or `hot_state_root_in_txn_info` is enabled in production. This requires plumbing the locally computed checkpoint hashes (from `DoStateCheckpoint`) into the call sites in `replay_on_archive.rs` and `aptos-debugger`/CLI so the comparison has values to check against.

### Proof of Concept
Not independently reproducible as a live exploit without a genuine state-root-divergence bug to trigger it; the finding is the code's own acknowledged, unaddressed check gap in the verification function itself, demonstrated by direct inspection of `ensure_match_transaction_info` (lines 2139–2204) and its sole production call site in `replay_on_archive.rs` (lines 392–405), where no checkpoint-hash fields are ever compared.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    pub fn with_features(mut self, features: &Features) -> Self {
        self.hotness_in_epilogue = features.is_hotness_in_epilogue_enabled();
        self.transaction_info_v1 = features.is_transaction_info_v1_enabled();
        // Requires transaction_info_v1: the hot state root rides in

        self.hot_state_root_in_txn_info = features.is_hot_state_root_in_txn_info_enabled()
            && features.is_transaction_info_v1_enabled();
        // Requires transaction_info_v1 (the root rides in TransactionInfoV1) and
        // hotness_in_epilogue (only the V1 write-set format it enables serializes
        // the native-position extensions; V0 drops them, so output-replay would
        // diverge). Degrades to off if either is missing.
        self.compute_trading_native_state_roots = features
            .is_compute_trading_native_state_roots_enabled()
            && features.is_transaction_info_v1_enabled()
            && features.is_hotness_in_epilogue_enabled();

    }
