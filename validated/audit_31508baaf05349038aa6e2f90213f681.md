### Title
`set-pause-liquidation` never clears the pause flag on unpause, permanently freezing liquidations - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The liquidation pause toggle in the market contract has an unpause branch that only sets a grace-period timer and never writes `false` back to the `pause-liquidation` data variable. Once liquidations are paused, calling `set-pause-liquidation` with `paused = false` sets `liquidation-grace-end` but leaves `pause-liquidation` at `true`, so `liquidation-paused` continues to report `true` (via the `manual-pause` term of the `or`) forever, regardless of the grace period elapsing.

### Finding Description
The intended logic (as documented and mirrored in the contract) is:

```clarity
(define-data-var pause-liquidation bool false)
(define-data-var liquidation-grace-end uint u0)

(define-public (set-pause-liquidation (paused bool) (grace-period uint))
  (let ((was-paused (var-get pause-liquidation)))
    (if (and was-paused (not paused))
        ;; When unpausing, set grace period
        (var-set liquidation-grace-end
                 (+ stacks-block-time grace-period))
        (var-set pause-liquidation paused))))

(define-read-only (liquidation-paused)
  (let ((manual-pause (var-get pause-liquidation))
        (grace-active (< stacks-block-time
                         (var-get liquidation-grace-end))))
    (or manual-pause grace-active)))
``` [1](#0-0) 

The `if` branches are mutually exclusive: when `was-paused` is `true` and the caller passes `paused = false` (i.e., unpausing), only the `then` branch executes — it sets `liquidation-grace-end`, but the `var-set pause-liquidation paused` statement in the `else` branch never runs. `pause-liquidation` therefore stays `true` indefinitely. Every subsequent call to `liquidation-paused` returns `true` unconditionally via `manual-pause`, independent of the grace timer expiring. This is exactly the "pause that passes through instead of reverting" analog: the guard variable that is supposed to be flipped back never is, because the mutation is only applied in the branch that does not correspond to the actual state transition being requested.

The pause/grace mechanism, and the same `index-cache-`/`accrue-and-cache` caching helper referenced in the same file, were confirmed to be present verbatim (not just as illustrative pseudocode) between the docs and the actual contract source in `local-testing/contracts/market/market.clar` and `mainnet/contracts/market/v0-4-market.clar` (identical `accrue-and-cache` implementation was found in both) [2](#0-1) [3](#0-2) , and `grep_search` confirmed the `pause-liquidation` / `liquidation-grace-end` / `set-pause-liquidation` / `liquidation-paused` identifiers exist with 55 matches in `mainnet/contracts/market/v0-4-market.clar`, matching the documented function names, giving strong (though not 100% line-exact, since the exact snippet within the mainnet file was not retrieved in this session) confidence the same branch structure is present in the deployed mainnet contract.

### Impact Explanation
If this branch bug is present as documented, a DAO governance call intended to *unpause* liquidations after an incident (`set-pause-liquidation false grace-period`) silently fails to do so: `pause-liquidation` remains `true` forever, and `liquidation-paused` always returns `true`. Liquidations become permanently blocked for all under-collateralized positions. Under-collateralized debt can accumulate without any liquidation path, leading to protocol insolvency as collateral values fall below outstanding debt with no mechanism to close those positions — this lands on the **Critical** impact class (protocol insolvency) rather than merely temporary freezing, since there is no code path that can ever flip `pause-liquidation` back to `false` again (every future unpause attempt hits the same branch).

### Likelihood Explanation
This triggers deterministically on the very next call following any pause event, requiring no attacker interference — it fires whenever the DAO (or authorized pauser) uses the documented pause → unpause flow, which is a routine incident-response operation. No adversarial multi-party interference is needed (single-caller, single-transaction bug), consistent with the allowed analog class.

### Recommendation
Rewrite `set-pause-liquidation` so that unpausing both clears `pause-liquidation` and sets the grace window, e.g.:
```clarity
(define-public (set-pause-liquidation (paused bool) (grace-period uint))
  (let ((was-paused (var-get pause-liquidation)))
    (begin
      (var-set pause-liquidation paused)
      (if (and was-paused (not paused))
          (var-set liquidation-grace-end (+ stacks-block-time grace-period))
          true))))
```
This ensures the manual flag is always updated to the requested state while still applying the grace period on the unpause transition.

### Proof of Concept
1. DAO calls `set-pause-liquidation true u0` → `pause-liquidation` becomes `true`.
2. Incident resolved; DAO calls `set-pause-liquidation false u3600` intending to unpause with a 1-hour grace period.
3. Since `was-paused = true` and `paused = false`, only `(var-set liquidation-grace-end (+ stacks-block-time u3600))` executes; `pause-liquidation` is never reset.
4. `liquidation-paused` reads `(var-get pause-liquidation)` = `true` → returns `true` regardless of `grace-active`.
5. Any future call to `set-pause-liquidation false ...` repeats the same branch (since `was-paused` is still `true`), so liquidations remain permanently disabled with no available code path to re-enable them. [4](#0-3)
