## Analysis Result

The external report concerns value loss caused by price movement between request time and fulfillment time for a volatile asset, with the client's own admitted partial mitigation being a "swap fee"/slippage tolerance. Push Chain has a directly analogous mechanism — a fixed 5% slippage tolerance around live on-chain swap quotes used to auto-convert volatile PRC20 gas tokens into native PC, both on the inbound gas-funding path and on the outbound gas-refund path. Unlike the report's underlying issue (price staleness from off-chain fulfillment delay), Push Chain's version is unprivileged-attacker-exploitable *within a single block*, because the "live" quote and the swap execution are not protected against spot-price manipulation.

### Title
Sandwichable spot-price swap quotes with fixed 5% slippage tolerance allow value extraction from protocol/user-controlled autoswap and gas-refund flows - (File: x/uexecutor/keeper/execute_inbound_gas_and_payload.go, x/uexecutor/keeper/execute_inbound_gas.go, x/uexecutor/keeper/outbound.go, x/uexecutor/keeper/evm.go)

### Summary
Every module-driven swap in `x/uexecutor` (inbound `GAS`/`GAS_AND_PAYLOAD` autoswap, and outbound gas-fee-refund autoswap) fetches a live spot quote from `QuoterV2.quoteExactInputSingle` via `Keeper.GetSwapQuote` [1](#0-0)  and then executes the actual swap with only a fixed 5% slippage bound (`minPCOut = quote * 95 / 100`) computed from that same just-fetched quote [2](#0-1) [3](#0-2) . Since the quote and the swap both read the live Uniswap V3 pool state and there is no TWAP oracle, no min/max age check, and no protection against reordering within the block, an unprivileged attacker who can also interact with the underlying Uniswap V3 pool can manipulate the pool's spot price immediately before the module's swap executes and restore it immediately after (classic sandwich), extracting value up to the 5% tolerance from every triggered autoswap/refund — i.e. from user or protocol-controlled PRC20/PC funds.

### Finding Description
Three code paths compute a quote and then immediately execute a swap using that quote with a hardcoded 5% slippage tolerance:

1. Inbound `GAS` autoswap: `k.GetSwapQuote` then `CallPRC20DepositAutoSwap` with `minPCOut = quote*95/100` [4](#0-3) .
2. Inbound `GAS_AND_PAYLOAD` autoswap: same pattern in `gasAndPayloadDepositAutoSwap` [2](#0-1) .
3. Outbound excess-gas refund: `applyGasRefund` fetches `getSwapQuoteForRefund` then calls `CallUniversalCoreRefundUnusedGas` with `withSwap=true` and the same `95/100` slippage math [3](#0-2) .

`GetSwapQuote` performs a `CallEVM` (a simulated/static call, `commit=false`) to `QuoterV2.quoteExactInputSingle` against the live pool [1](#0-0) . This is a spot price read with no time-weighting or staleness protection. The module then commits the real swap (`commit=true`) via `DerivedEVMCall` in the very same keeper invocation [5](#0-4) , so both the quote and the swap occur in the same Push Chain block/transaction execution — there is no cross-block delay that would make classic price-staleness (the bug report's literal scenario) the primary risk. Instead the risk is that Push Chain's own upgrade notes confirm this 5% tolerance was added specifically "to mitigate slippage and volatility" [6](#0-5) , i.e. exactly the client's admitted-incomplete fix referenced in the external report. A 5% band is wide enough that an attacker who can move the pool price by manipulating liquidity/large trades against the same Uniswap V3 pool right before the module's swap executes (and reversing after) can capture most or all of that 5% as MEV, at the direct expense of the depositor's PRC20-to-PC conversion (inbound `GAS`/`GAS_AND_PAYLOAD`) or of the refund recipient's returned gas value (outbound refund).

### Impact Explanation
This corrupts PRC20/native accounting and refund accounting: users depositing gas-abstraction funds receive less native PC than they should have (funds are effectively skimmed by the sandwiching attacker rather than by the protocol), and outbound gas-refund recipients receive a reduced refund. Because the swap executes atomically inside module-originated `DerivedEVMCall`s with real value movement, this is an unauthorized-value-extraction / partial-fund-loss issue reachable by any unprivileged user submitting ordinary GAS/GAS_AND_PAYLOAD inbound transactions or by any relayer/validator quorum finalizing an outbound observation — both are default, non-privileged flows.

### Likelihood Explanation
Likelihood depends on the liquidity depth and typical trade size of the specific PRC20/WPC pool used for a given gas token, and on the attacker's ability to get transactions ordered around the module's swap within the same block (feasible for a block proposer or via MEV-style bundling in a permissionless mempool). Because the module swap size can be predicted in advance (it corresponds to known deposit or refund amounts derivable from mempool-visible inbound/outbound messages awaiting quorum), a motivated attacker can target specific large transactions.

### Recommendation
Do not use a live `QuoterV2.quoteExactInputSingle` spot read from the same block as the source of the slippage bound. Instead, derive `minPCOut` from a TWAP/oracle price with a materially tighter, configurable slippage tolerance, or execute quote and swap across separate blocks so users/relayers can react to abnormal deviations, and consider capping single-swap size or adding a maximum allowed deviation from a recent moving-average price.

### Proof of Concept
1. Attacker observes (via mempool or predictable inbound/outbound flow) that a `GAS_AND_PAYLOAD` inbound (or outbound gas refund) for token X is about to be finalized and will trigger `k.GetSwapQuote` + `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` swapping X→WPC on the QuoterV2/Uniswap V3 pool referenced in `GetUniversalCoreQuoterAddress`.
2. Before the module's swap executes in the same block, attacker submits a large trade against the same pool to move the spot price against the module's expected direction.
3. The module calls `GetSwapQuote`, computes `minPCOut = quote*95/100` off the now-manipulated price, and executes the swap via `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas`, receiving PC/WPC output diminished by up to the full 5% tolerance.
4. Attacker reverses their trade in the same block (or shortly after), pocketing the difference at the expense of the depositor's minted PC amount or the refund recipient's returned value.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
