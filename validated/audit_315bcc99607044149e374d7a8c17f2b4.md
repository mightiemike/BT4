### Title
Attacker-controlled `Inbound.Recipient` for isCEA inbounds is only format-validated, not identity-validated, allowing PRC20 funds to be minted to Push Chain's own system contracts and permanently locked - ([File: x/uexecutor/types/inbound.go], [File: x/uexecutor/keeper/execute_inbound_gas_and_payload.go])

### Summary
The Cally finding is a class of bug where an untrusted "target/self" parameter is accepted without checking it isn't the protocol's own address, causing funds to be routed into a place the protocol cannot withdraw from. The candidate analog in Push Chain is the `Recipient` field of an `Inbound` when `IsCEA=true`: it is attacker-controlled (comes from a source-chain gateway event a user triggers themselves) and is validated only for hex-string format via `utils.IsValidAddress`, never checked against Push Chain's own reserved/system contract addresses (`UNIVERSAL_GATEWAY_PC`, `UNIVERSAL_CORE`, the UEA factory, PRC20 contract addresses, or the `uexecutor` module's own EVM address).

### Finding Description
`Inbound.ValidateForExecution` ( [1](#0-0) ) only checks that `Recipient` is non-empty and passes `utils.IsValidAddress(p.Recipient, utils.HEX)` for `FUNDS`/`GAS` types, and for `IsCEA` payload types it likewise only checks non-empty + hex-format ( [2](#0-1) ). There is no check anywhere in this validation path that rejects `Recipient` values equal to Push Chain's own reserved system contracts.

When `IsCEA=true`, `ExecuteInboundGasAndPayload` uses the raw `Recipient` directly as the deposit destination (`ueaAddr = common.HexToAddress(utx.InboundTx.Recipient)`), first checking whether it resolves to a real UEA via the factory, and if not, falling through to a branch that checks only whether the address has contract bytecode versus being an EOA, before still depositing PRC20 to it ( [3](#0-2) ). Nowhere in this branch is there a check that `Recipient` isn't `UNIVERSAL_GATEWAY_PC`, `UNIVERSAL_CORE`, the UEA factory, or a PRC20 contract's own address — the same missing-self-check pattern as Cally's missing `token != address(this)` guard. Test coverage confirms the only rejected shapes are non-hex or empty strings ( [4](#0-3) ), and that an arbitrary explicit recipient (even one unrelated to the sender) is accepted and funded as long as it's a valid-looking address or a deployed UEA ( [5](#0-4) ) — demonstrating the recipient field is trusted at face value.

Since `IsCEA`/`Recipient` values originate from a gateway event on the source chain that any unprivileged user can trigger by calling the gateway contract themselves with a self-chosen recipient parameter, an attacker fully controls this field before Universal Validators simply relay it via `MsgVoteInbound` — this is the "user-reachable flow with honest validators" scenario the scope calls out.

### Impact Explanation
If an attacker sets `Recipient` to a system contract address (e.g. the PRC20 contract's own address, or `UNIVERSAL_GATEWAY_PC`) that is neither a deployed UEA nor has an `executeUniversalTx` entry point compatible with the deposited asset, the PRC20 deposit still executes (`gasAndPayloadDepositAutoSwap` → `CallPRC20DepositAutoSwap`), minting the bridged value to that address. Unlike a normal EOA/UEA recipient, these system contracts have no user-facing withdrawal path for tokens minted into their own balance — mirroring the Cally scenario where ETH becomes permanently unreachable because the vault-owner (Cally itself) has no code path to release it. This is a permanent freezing of user/protocol-controlled funds, which is explicitly in scope.

### Likelihood Explanation
Medium. The trigger requires only an ordinary, unprivileged bridge deposit from any external chain, with the attacker choosing an unusual `recipient`/CEA target on their own gateway call — no validator, TSS, or admin cooperation is needed, and honest Universal Validators will faithfully relay whatever they observed on-chain. The main uncertainty is whether the PRC20/UniversalCore/UEA factory Solidity contracts (outside this repo, in `push-chain-core-contracts`) have some internal `require(to != address(this))`-style guard on their own mint/deposit entry points, which this repo's Go code does not enforce and which I could not verify from the indexed contents available.

### Recommendation
Add an explicit `recipient not in {UNIVERSAL_GATEWAY_PC, UNIVERSAL_CORE, UEA_FACTORY, ue module EVM address, PRC20 contract addresses}` check inside `Inbound.ValidateForExecution` (or immediately before the deposit call in `ExecuteInboundGasAndPayload`/`ExecuteInboundFundsAndPayload`), rejecting the inbound (producing a FAILED PCTx, consistent with existing validation failure handling) whenever the resolved recipient matches any of Push Chain's own system/reserved contract addresses.

### Proof of Concept
1. Attacker calls the gateway contract on an external chain (e.g. Sepolia) with `TxType=FUNDS_AND_PAYLOAD`, `IsCEA=true`, and `Recipient` set to the PRC20 contract's own on-chain address (obtained from the public `uregistry` token config).
2. Universal Validators observe this legitimate on-chain event and honestly relay it via `MsgVoteInbound` — no malicious validator behavior needed.
3. Once quorum is reached, `ExecuteInboundGasAndPayload` resolves `Recipient` as neither a deployed UEA nor treats it specially, and calls `gasAndPayloadDepositAutoSwap`/`CallPRC20Deposit` minting the bridged amount to the PRC20 contract's own address ( [6](#0-5) ).
4. The PCTx records SUCCESS; the bridged value is now minted into the PRC20 contract's own balance with no recipient-side redemption path, permanently locking it — analogous to funds trapped in a Cally vault owned by Cally itself.
