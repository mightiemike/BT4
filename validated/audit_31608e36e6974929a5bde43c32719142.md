Based on the investigation, there is a valid analog in this codebase: a transaction accepted at the gateway can permanently exceed the bouncer's per-block capacity limit, causing `TransactionExecutorError::TransactionTooLarge` on every execution attempt, which — because of Starknet's strict per-account nonce ordering — permanently blocks that account's nonce and denies it (and anyone behind it in the same account's nonce sequence) service, with no automated recovery path.

### Title
Gateway-accepted transaction can permanently exceed bouncer block capacity, causing irrecoverable per-account transaction DoS - (File: crates/blockifier/src/bouncer.rs)

### Summary
The gateway's `StatelessTransactionValidator::validate_resource_bounds` only checks a transaction's declared `max_l2_gas_amount` against a configured gateway-side ceiling (`max_l2_gas_amount`) [1](#0-0) , and the mempool only enforces mempool byte-capacity and fee-escalation rules [2](#0-1) . Neither of these ingestion-time checks is coupled to the batcher's `BouncerConfig.block_max_capacity`, which independently caps sierra_gas, proving_gas, n_events, state_diff_size, etc. per block [3](#0-2) . When a transaction's actual execution weight (which can differ substantially from its declared resource bounds, e.g. due to event emission, state-diff writes, or executed-class accounting) exceeds `block_max_capacity` on its own — even against an otherwise-empty block — `within_max_capacity_or_err` returns `TransactionExecutionError::TransactionTooLarge` [4](#0-3) . This is confirmed as a distinct, non-recoverable-by-retry case in tests, separate from an ordinary `BlockFull` (which just waits for the next block) [5](#0-4) .

### Finding Description
This mirrors the Lido bug class exactly: step 1 (gateway/mempool admission) validates and accepts a value using one set of limits, while step 2 (a later, mandatory processing stage — block building via the bouncer) enforces a different, unrelated limit that the accepted value can permanently fail. Just as a Lido withdrawal amount that is valid at deposit time can be permanently unclaimable at the Lido-imposed withdrawal step, a Starknet transaction that is valid at gateway/mempool admission time can be permanently un-executable at the bouncer step, because:

1. The gateway's resource-bound checks (`max_l2_gas_amount`, `max_calldata_length`, etc.) are configured independently of the batcher's `bouncer_config.block_max_capacity` [6](#0-5) .
2. Actual weights used against the bouncer (`sierra_gas`, `proving_gas`, `n_events`, `state_diff_size`, `receipt_l2_gas`, etc.) are derived from execution, not solely from declared resource bounds [7](#0-6) .
3. Because Starknet enforces strict per-account nonce ordering in both the mempool and block building (`get_txs_and_assert_expected` tests show only in-order nonces are ever proposed) [8](#0-7) , once a transaction at the account's next required nonce is un-executable due to `TransactionTooLarge`, that account can make no further progress: the block-building attempt for that transaction never succeeds, so it is never "rejected" through the normal commit path that would remove it from the mempool and unblock later nonces (`remove_rejected_txs` only fires for transactions actually rejected as part of a committed block) [9](#0-8) .

### Impact Explanation
A stuck account can never advance its nonce again through normal operation: every future block-building attempt for that account's leading nonce fails with `TransactionTooLarge`, and (per the tests) this differs from `BlockFull` because it is not resolved by simply waiting for the next block — the transaction is intrinsically too large for any block under the given bouncer config. Since Starknet requires strict per-nonce ordering, this permanently denies the affected account the ability to confirm any subsequent transaction, a concrete denial-of-service against a network participant with no automated recovery path (only manual intervention/config changes, or the underlying config-consistency bug being fixed, could resolve it).

### Likelihood Explanation
This requires the sequencer operator's gateway/mempool resource-bound configuration to be inconsistent with the batcher's bouncer capacity configuration (e.g., `max_l2_gas_amount`, `max_calldata_length`, or declare-transaction size limits set looser than what the bouncer's `sierra_gas`/`proving_gas`/`state_diff_size`/`n_events` caps can actually accommodate for a single transaction). This is a configuration-coupling gap rather than a pure code bug reachable by a completely unprivileged attacker independent of node configuration, which lowers confidence that it is exploitable in a correctly configured deployment; I could not verify from the available code whether there is an invariant elsewhere in the codebase (e.g., in config validation/deployment tooling) that guarantees gateway/mempool bounds are always conservative enough to fit the batcher's bouncer capacity.

### Recommendation
Enforce a config-time or gateway-side check (analogous to how `validate_resource_bounds` already checks other bounds) that a transaction's maximum possible resource usage (calldata, signature length, declared gas bounds, and any other bouncer-tracked dimensions) can never exceed `BouncerConfig.block_max_capacity`, and add a validation step in deployment tooling that rejects any config where `gateway/mempool` limits could produce a bouncer-side `TransactionTooLarge`. Additionally, consider having the batcher treat `TransactionTooLarge` (as opposed to `BlockFull`) as a rejection reason during block building so the mempool removes the stuck transaction via `remove_rejected_txs`, unblocking the account's subsequent nonces instead of leaving it deadlocked.

### Proof of Concept
Not independently reproducible from the indexed code alone — the existing unit test `test_transaction_too_large_sierra_gas_based` demonstrates the underlying mechanism (a single transaction's `sierra_gas` weight exceeding `block_max_capacity.sierra_gas` deterministically yields `TransactionTooLarge` against an empty block) [5](#0-4) , but confirming end-to-end reachability from gateway ingestion through to a permanently stuck mempool account would require tracing the exact numeric relationship between `StatelessTransactionValidatorConfig`/`MempoolConfig` defaults and `BouncerConfig` defaults in a live deployment, which is beyond what the indexed code snippets can confirm with certainty.

        &self,
        tx: &RpcTransaction,
    ) -> StatelessTransactionValidatorResult<()> {
        if !self.config.validate_resource_bounds {
            return Ok(());
        }

        let resource_bounds = *tx.resource_bounds();

                gas_price: resource_bounds.l2_gas.max_price_per_unit,
                min_gas_price: self.config.min_gas_price,
            });
        }

        // TODO(Arni): Consider adding a validation for max_l2_gas_amount for declare.
        if let RpcTransaction::Declare(_) = tx {
        } else if resource_bounds.l2_gas.max_amount.0 > self.config.max_l2_gas_amount {
            return Err(StatelessTransactionValidatorError::MaxGasAmountTooHigh {
                gas_amount: resource_bounds.l2_gas.max_amount,
                max_gas_amount: self.config.max_l2_gas_amount,
            });
        }

        Ok(())

    fn add_tx_validations(
        &mut self,
        tx_reference: TransactionReference,
        tx: &InternalRpcTransaction,
        account_nonce: Nonce,
    ) -> MempoolResult<()> {
        self.validate_incoming_tx(tx_reference, account_nonce)?;
        let replaced_tx_reference = self.validate_fee_escalation(tx_reference)?;

        // The replaced transaction is still pooled, so its bytes still count toward
        // `size_in_bytes()`. Credit what its removal will free: a same-size bump nets to zero (no
        // overflow handling), and a larger replacement only needs room for the delta, consistent
        // with how a fresh next-nonce transaction is treated. The removal happens only after
        // capacity is confirmed below, so a rejected incoming transaction never strands the
        // account.
        let freed_bytes = replaced_tx_reference.map_or(0, |reference| {
            self.tx_pool
                .get_by_tx_hash(reference.tx_hash)
                .expect("Replacement target from pool must exist.")
                .total_bytes()
        });

        if self.exceeds_capacity(tx, freed_bytes) {
            self.handle_capacity_overflow(tx, account_nonce, freed_bytes)?;
        }

        // Capacity is confirmed: this is the final, infallible mutation before the incoming
        // transaction is inserted by the caller.
        if let Some(existing_tx_reference) = replaced_tx_reference {
            self.remove_replaced_tx(existing_tx_reference);
        }

        Ok(())
    }

    fn remove_rejected_txs(
        &mut self,
        rejected_tx_hashes: IndexSet<TransactionHash>,
        rewound_tx_hashes: &IndexSet<TransactionHash>,
    ) -> AddressToNonce {
        if !rejected_tx_hashes.is_empty() {
            debug!("Removed rejected transactions from mempool: {:?}", rejected_tx_hashes);
        }
        let mut rejected_txs_counter = 0;
        let mut account_nonce_updates = AddressToNonce::new();

        for tx_hash in rejected_tx_hashes {
            // In FIFO mode, if a rejected transaction was rewound, skip removal (keep in pool and
            // queue). Otherwise, remove it from both pool and queue.
            if rewound_tx_hashes.contains(&tx_hash) {
                continue;
            }

            if let Ok(tx) = self.tx_pool.remove(tx_hash) {
                self.tx_queue.remove_by_address(tx.contract_address());
                rejected_txs_counter += 1;
                self.decrement_stuck_txs_if_gap_account(tx.contract_address(), 1);
                account_nonce_updates
                    .entry(tx.contract_address())
                    .and_modify(|nonce| *nonce = (*nonce).min(tx.nonce()))
                    .or_insert(tx.nonce());
            } else {
                continue; // Transaction hash unknown to mempool, from a different node.
            }

            // TODO(clean_accounts): remove address with no transactions left after a block cycle /
            // TTL.
        }
        metric_count_rejected_txs(rejected_txs_counter);
        account_nonce_updates
    }

#[rstest]
fn test_transaction_too_large_sierra_gas_based(block_context: BlockContext) {
    let mut state = test_state(&block_context.chain_info, Fee(0), &[]);
    let mut transactional_state = TransactionalState::create_transactional(&mut state);
    let block_max_capacity = BouncerWeights { sierra_gas: GasAmount(20), ..Default::default() };
    let bouncer_config = BouncerConfig { block_max_capacity, ..Default::default() };

    // Use gas amount > block_max_capacity's.
    let exceeding_gas = GasAmount(30);
    let execution_summary = ExecutionSummary::default();
    let builtin_counters = CairoPrimitiveCounterMap::default();
    let tx_resources = TransactionResources {
        computation: ComputationResources { sierra_gas: exceeding_gas, ..Default::default() },
        ..Default::default()
    };
    let tx_state_changes_keys = transactional_state.to_state_diff().unwrap().state_maps.keys();

    let result = verify_tx_weights_within_max_capacity(
        &transactional_state,
        &execution_summary,
        &builtin_counters,
        &tx_resources,
        &tx_state_changes_keys,
        &bouncer_config,
        &block_context.versioned_constants,
        GasAmount::ZERO,
    )
    .map_err(TransactionExecutorError::TransactionExecutionError);

    let expected_weights = BouncerWeights {
        sierra_gas: exceeding_gas,
        n_txs: 1,
        proving_gas: exceeding_gas,
        ..BouncerWeights::empty()
    };

    assert_matches!(result, Err(
        TransactionExecutorError::TransactionExecutionError(
            TransactionExecutionError::TransactionTooLarge { max_capacity, tx_size }
        )
    )  if *max_capacity == bouncer_config.block_max_capacity && *tx_size == expected_weights);
}
