**Rationale:**

The `to_make_hot: BTreeSet<StateKey>` produced by `get_keys_to_make_hot` in `hot_state_op_accumulator.rs` is computed once at original block execution and embedded directly as a field of the persisted `BlockEpiloguePayload::V2` transaction [1](#0-0) . During replay/state-sync re-execution, the code does not recompute this set from scratch via the accumulator — it reads the already-committed set out of the historical transaction via `try_get_keys_to_make_hot()` [2](#0-1) .

The theoretical failure mode described — `StateKey::Ord` changing incompatibly between code versions and corrupting reconstructed ordering/write sets on replay — would indeed be a determinism hazard, and the file's own comments acknowledge the sensitivity of `Ord` vs `Hash`/`Eq` for `StateKey` and why the deterministic order is imposed exactly once [3](#0-2) . However, this hazard:

1. Requires an actual, incompatible change to `StateKey`'s core `Ord` implementation shipped by protocol developers — not something reachable from any unprivileged transaction, package, API, view, or bytecode input. There is no attacker-controlled data path that can alter `Ord` semantics at runtime.
2. Would equally affect every other `BTreeMap`/`BTreeSet` keyed by `StateKey` throughout the codebase (e.g., the write set itself), so it is a generic hard-fork/versioning-discipline concern for the whole state-key type, not a defect specific to `get_keys_to_make_hot`.
3. Falls squarely under the excluded category of issues that "depend on trusted operator/developer mistakes alone" per the review's decision standard, since it requires a core-code regression rather than an exploit path from unprivileged input.

Since no unprivileged-input-triggerable path exists to cause this divergence, and the described risk is a general engineering-discipline invariant (already implicitly documented in the code) rather than a state-integrity bug reachable by attacker input, this does not meet the acceptance criteria.
