Committee proposal quorum check uses truncating integer division, silently lowering the required 70% witness-approval threshold - (File: `chainbase/src/main/java/org/tron/core/capsule/ProposalCapsule.java`)

### Summary
`ProposalCapsule.hasMostApprovals(List<ByteString> activeWitnesses)` decides whether a governance proposal (which mutates chain-wide dynamic parameters such as fees, energy pricing, resource limits, etc.) has received "most approvals" (intended to mean at least 70% of active witnesses). The check is implemented as `count >= activeWitnesses.size() * 7 / 10`, which performs integer division and truncates toward zero. This is the same class of bug as the reported `requiredImprovementRate` issue: an intended percentage-based threshold is weakened by integer-division precision loss, letting the check pass with fewer approvals than the design intends. [1](#0-0) 

### Finding Description
The intended quorum is 70% of `activeWitnesses.size()`. Because `activeWitnesses.size() * 7 / 10` truncates any fractional remainder, for witness counts that are not exact multiples of 10, the effective threshold is rounded down rather than up. For the standard witness count of 27 (`MAX_ACTIVE_WITNESS_NUM`), `27 * 7 / 10 = 189 / 10 = 18` (truncated from `18.9`), so only 18 approvals (≈66.7%) are required instead of the intended 19 approvals that would correspond to ≥70% (18.9 rounded up). [2](#0-1) 

This value directly gates `ProposalController.processProposal`, which is invoked automatically during network maintenance (`processProposals`) for every pending, non-expired proposal and, if `hasMostApprovals` returns true, calls `setDynamicParameters(proposalCapsule)` and marks the proposal `APPROVED`. [3](#0-2) 

Proposals themselves are created and approved via ordinary broadcast transactions handled by `ProposalCreateActuator` / `ProposalApproveActuator`, so any witness can add or remove their approval by submitting a transaction; the actual APPROVED/DISAPPROVED decision is later computed purely from the truncated integer-division threshold in `hasMostApprovals`. [4](#0-3) 

The bug is systemic across any witness-count value that is not a multiple of 10 — it always rounds the quorum requirement down, never up, biasing the network toward approving proposals more easily than the documented "≥70%" rule.

### Impact Explanation
`setDynamicParameters` applies witness-approved changes to chain-wide `DynamicPropertiesStore` values (transaction fees, account-creation fees, energy/bandwidth pricing, resource limits, protocol feature switches, etc.). A truncated quorum means proposals can be approved and dynamic parameters changed network-wide with less witness consensus than intended (e.g., 18/27 ≈ 66.7% instead of the intended ≥70%). This weakens the governance security assumption that changes to consensus-critical economic and protocol parameters require a supermajority of witnesses, allowing a smaller-than-designed witness coalition to alter global chain parameters — an accounting/consensus-parameter integrity issue rather than a fully isolated cosmetic bug.

### Likelihood Explanation
The flawed comparison executes automatically on every maintenance cycle for every pending proposal (`ProposalController.processProposals` → `processProposal` → `hasMostApprovals`), with no special privilege required beyond the witnesses' normal, expected ability to submit `ProposalApproveContract` transactions. Because `MAX_ACTIVE_WITNESS_NUM` (27) is not a multiple of 10, the rounding-down behavior is not an edge case — it triggers on the network's real, everyday witness count, making the discrepancy from the intended ≥70% threshold continuously present rather than a rare corner case.

### Recommendation
Replace the truncating division with a ceiling-division (or equivalent rational comparison) to correctly enforce "≥70%":
```java
return count * 10 >= activeWitnesses.size() * 7;
```
or, using ceiling division akin to the referenced `Math.ceilDiv` recommendation:
```java
long required = (activeWitnesses.size() * 7 + 9) / 10; // ceil(size * 0.7)
return count >= required;
```
Both avoid any floating/truncating precision loss and enforce the intended semantic threshold for every possible witness-count value, not just multiples of 10.

### Proof of Concept
1. Network has 27 active witnesses (`MAX_ACTIVE_WITNESS_NUM`), the current mainnet/testnet configuration.
2. A proposal is created via `ProposalCreateActuator`.
3. Exactly 18 witnesses call `ProposalApproveActuator` to approve it (66.7% of 27, below the intended 70%).
4. During the next maintenance cycle, `ProposalController.processProposal` calls `proposalCapsule.hasMostApprovals(activeWitnesses)`.
5. `count = 18`, `activeWitnesses.size() * 7 / 10 = 189 / 10 = 18` (integer truncation) — the check `18 >= 18` passes.
6. The proposal is marked `APPROVED` and `setDynamicParameters` is applied, even though only 66.7% (not the intended ≥70%) of witnesses approved it. [1](#0-0)

  public boolean hasMostApprovals(List<ByteString> activeWitnesses) {
    long count = this.proposal.getApprovalsList().stream()
        .filter(witness -> activeWitnesses.contains(witness)).count();
    if (count != this.proposal.getApprovalsCount()) {
      List<ByteString> InvalidApprovalList = this.proposal.getApprovalsList().stream()
          .filter(witness -> !activeWitnesses.contains(witness)).collect(Collectors.toList());
      logger.info("InvalidApprovalList:" + getAddressStringList(InvalidApprovalList));
    }
    if (activeWitnesses.size() != MAX_ACTIVE_WITNESS_NUM) {
      logger.info("activeWitnesses size = {}", activeWitnesses.size());
    }
    return count >= activeWitnesses.size() * 7 / 10;
  }
