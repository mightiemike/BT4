### Title
Non-deterministic floating-point AMM (Bancor) swap-amount calculation in TRON's on-chain Exchange actuators - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
TRON's built-in TRC10 Exchange (Bancor-style AMM, reachable via `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`) computes swap output amounts using non-strict, platform-dependent `java.lang.Math.pow` floating-point arithmetic by default. This is the closest reachable analog to the ReLP bug class: an "inaccurate swap amount calculation" in an automated market maker that can silently misprice swaps/deposits, truncate value via `(long)` casts, and — because the code path is not guaranteed bit-reproducible — potentially diverge between validate/execute or between nodes running different JVMs/platforms.

### Finding Description
`ExchangeCapsule.transaction()` selects between two swap-amount calculators depending on the `allowHardenExchangeCalculation` dynamic property: [1](#0-0) 

When the hardened flag is off (its default unless enabled by a committee proposal, per `ProposalUtil`/`DynamicPropertiesStore`), swap output is computed by `ExchangeProcessor`, which performs the Bancor bonding-curve math (`exchangeToSupply`/`exchangeFromSupply`) entirely in `double` precision using `Maths.pow(...)`, then truncates the result to `long` via a raw `(long)` cast (rounding toward zero, i.e., always in favor of the pool): [2](#0-1) 

`Maths.pow` itself explicitly documents the risk: it dispatches to either `java.lang.Math` (via a wrapper) or `StrictMath`, and its own class Javadoc calls the non-strict path "deprecated" specifically because ordinary `Math.pow` is *not* guaranteed to produce identical results across platforms/JVMs, whereas `StrictMathWrapper.pow` (backed by `StrictMath`) is: [3](#0-2) [4](#0-3) 

The hardened, deterministic path (`SafeExchangeProcessor`, using `BigDecimal` and `StrictMathWrapper`) exists in the codebase but is opt-in via the `allowHardenExchangeCalculation` dynamic property, gated through `AbstractExchangeActuator.allowHarden()`: [5](#0-4) [6](#0-5) 

`ExchangeTransactionActuator.execute()` calls this swap function directly on user-broadcast transactions and applies its output to real account/asset balances without any additional sanity/consistency check against the theoretical AMM formula: [7](#0-6) 

By contrast, `ExchangeInjectActuator`/`ExchangeWithdrawActuator` use plain integer/BigInteger ratio math (not floating point) for proportional deposits/withdrawals, and `ExchangeWithdrawActuator` even adds an explicit "Not precise enough" precision check comparing computed vs. expected amounts — an acknowledgment elsewhere in the codebase that rounding/precision drift in exchange math is a recognized risk that needs bounding: [8](#0-7) 

No equivalent bound exists for the core `ExchangeTransactionActuator` swap path when running in non-hardened (default) mode.

### Impact Explanation
- **Value loss / mispricing:** the `(long)` truncation in `exchangeToSupply`/`exchangeFromSupply` always rounds toward zero, meaning every default-mode swap that goes through `ExchangeProcessor` slightly underpays the counterparty relative to the exact Bancor formula — analogous in kind (though smaller in per-swap magnitude) to the ReLP dust/loss issue, i.e., systematic value leakage baked into an AMM-style balance-update path that is reachable by any account via a plain broadcast transaction.
- **Potential non-determinism / consensus risk:** because the default path relies on `Math.pow` (not `StrictMath.pow`), and the class's own documentation flags this as a cross-platform consistency hazard, any behavioral difference between JVM implementations/versions used by different super representatives when executing the same `ExchangeTransactionContract` could, in principle, produce divergent `Exchange` balances between nodes — a consensus-divergence class of impact. This is speculative without a concrete cross-platform reproduction, but it is the exact risk the codebase's own comments and the "hardened" opt-in flag exist to mitigate.

### Likelihood Explanation
- The path is reachable directly from an anonymous broadcast transaction (`ExchangeTransactionContract`) with no privileged role required — matching the "unprivileged" requirement.
- The non-hardened `ExchangeProcessor` is the default calculation engine unless the `allowHardenExchangeCalculation` proposal has been activated by the committee, so exposure is contingent on current network configuration (which this repo snapshot does not let me confirm definitively).
- The rounding-loss effect is deterministic per swap and small in relative magnitude compared to the ReLP PoC's ~0.67 WETH dust, so likelihood of a materially impactful single-transaction exploit is lower; the more severe, but harder-to-trigger, risk is the theoretical cross-platform non-determinism of `Math.pow`.

### Recommendation
- Make the hardened (`SafeExchangeProcessor`, `BigDecimal`/`StrictMath`-based) calculation path the mandatory default for `ExchangeTransactionActuator`, rather than an opt-in dynamic property, removing the legacy `ExchangeProcessor`/`Maths.pow` double-precision path from consensus-critical execution entirely.
- Add an explicit precision/consistency bound in `ExchangeTransactionActuator` (mirroring the "Not precise enough" check already present in `ExchangeWithdrawActuator`) so that swap outputs are validated against a tolerance of the theoretical formula before mutating balances.
- Audit all remaining consumers of `Maths.pow`/`MathWrapper` in consensus-relevant code paths and migrate them to `StrictMathWrapper` to eliminate cross-platform floating-point risk.

### Proof of Concept
No standalone PoC was constructed against this fork; concretely reproducing the ReLP-style "large stuck dust" scenario or a genuine `Math.pow` cross-platform divergence would require executing the same `ExchangeTransactionContract` on differing JVM/OS/CPU combinations to compare emitted `first_token_balance`/`second_token_balance`, or statistically sampling truncation loss across many swaps via `ExchangeCapsuleTest`-style harnesses (e.g., `chainbase/.../ExchangeCapsule.transaction`) with `useStrictMath=false`, as illustrated by the existing test: [9](#0-8) 

**Caveat:** This is a bug-class analog inferred from the report ("inaccurate swap amount calculation" leading to stuck/lost value in an AMM), not a proven, currently-exploitable incident in this repo. I could not confirm the mainnet-current default value of `allowHardenExchangeCalculation`, nor could I locate `MathWrapper.java` in the indexed codebase to fully confirm it calls `java.lang.Math.pow` verbatim (index size limits may have excluded that file) — a Devin session with full repo access would be needed to verify the exact non-strict math implementation and the live default of the hardening flag.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
