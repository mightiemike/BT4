### Title
Authentication error responses leak account existence via distinct error text ("Invalid email" vs "Invalid password" vs "MFA Error") - (core/sessions/localauth/orm.go)

### Summary
`orm.CreateSession` returns human-readable, semantically distinct error messages for nonexistent email, wrong password, and MFA failure cases, and `SessionsController.Create` passes these errors verbatim into the JSON response body via `jsonAPIError`. This allows an unprivileged attacker to enumerate valid Chainlink node operator/admin account emails by observing which error string is returned for a given login attempt.

### Finding Description
The `POST /sessions` endpoint is handled by `SessionsController.Create`, which calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and on any error immediately calls `jsonAPIError(c, http.StatusUnauthorized, err)` [2](#0-1) . `jsonAPIError` serializes `err.Error()` directly into the response body [1](#0-0) .

Inside `CreateSession`:
- If `FindUser` fails (email not found) or the constant-time email compare mismatches, it returns `pkgerrors.New("Invalid email")` [3](#0-2) .
- If the email is valid but the password is wrong, it returns `pkgerrors.New("Invalid password")` [4](#0-3) .
- If MFA lookup/verification fails, it returns `pkgerrors.New("MFA Error")` [5](#0-4) .

Although a constant-time comparison is used for the email string itself (to avoid timing side-channels on that comparison) [6](#0-5) , this only protects against timing attacks on the email string comparison — it does nothing to prevent the distinguishable error text ("Invalid email" vs "Invalid password") from being returned, which is a far more direct oracle. All three response paths share the same HTTP status code (401), so the only observable signal is the response body content, not the status code — but the body content alone is sufficient for enumeration. There is no rate limiting or account lockout referenced in this code path (consistent with the question's stated precondition), so an attacker can send high-volume `POST /sessions` requests with varying candidate emails and directly determine which emails correspond to real accounts (`"Invalid password"` or `"MFA Error"` responses) versus nonexistent ones (`"Invalid email"`).

### Impact Explanation
This is a username/account enumeration vulnerability. For a system whose admin/operator accounts can move funds or control chain operations, being able to enumerate valid account emails significantly narrows and accelerates follow-on credential-stuffing or targeted password-guessing attacks against those specific accounts, increasing the likelihood of a successful account takeover of privileged, fund-moving admin sessions. This does not by itself grant access, but it materially reduces attacker effort/precondition for a subsequent credential attack.

### Likelihood Explanation
Highly feasible and repeatable: the endpoint is a standard unauthenticated `POST /sessions` HTTP API reachable by any unprivileged attacker; no authorization, signature, or special preconditions are required beyond network access to the API. The question's stated precondition (no lockout/rate-limiting) matches what is visible in this code, so an attacker can automate probing many candidate emails to build a list of valid accounts.

### Recommendation
Return a single generic, identical error message (e.g., "Invalid email or password") and identical HTTP status code for all pre-MFA-challenge authentication failures (nonexistent email, wrong password), removing the distinction between `AuthLoginFailedEmail` and `AuthLoginFailedPassword` from the client-facing response body while still keeping the differentiated audit log events server-side for internal monitoring. The MFA-required response (`sessions.BeginWebAuthnLogin` challenge, or "MFA Error" once already known to have valid credentials) is only reachable after a valid email+password match, so it does not leak account existence by itself, but should be reviewed to ensure it isn't triggered before password validation timing-wise in a way that reveals MFA enrollment.

### Proof of Concept
Integration test in `core/web/sessions_controller_test.go`:
1. Seed one user, e.g. `real@example.com` / `correctpassword`.
2. `POST /sessions` with `{"email": "nonexistent@example.com", "password": "anything"}` — record status code and response body.
3. `POST /sessions` with `{"email": "real@example.com", "password": "wrongpassword"}` — record status code and response body.
4. Assert: currently, both return `401`, but body #2 contains `"Invalid email"` and body #3 contains `"Invalid password"` — i.e. bodies differ, proving the oracle exists (test should assert they currently differ, then after fix assert `require.Equal(t, body2, body3)` to confirm remediation).

const constantTimeEmailLength = 256

func constantTimeEmailCompare(left, right string) bool {
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
