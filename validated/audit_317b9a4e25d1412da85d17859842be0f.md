### Title
Spot-price gas-refund swap uses no slippage/TWAP buffer beyond a fixed 5% band, letting an unprivileged attacker sandwich `applyGasRefund` and drain protocol-held refund value - (File: x/uexecutor/keeper/outbound.go)

### Summary
The external report's core lesson is that a *narrow, static tolerance band* between a "safe" reference value and the value actually used to trigger an on-chain action creates a monitorable, front-runnable extraction window. Push Chain has a structural analog in the gas-refund swap path: the module computes a spot quote and then executes the real swap with only a fixed 5% slippage cushion, using a manipulable single-block price source, on every outbound gas refund.

### Finding Description
When an outbound finishes (success or failure), `Keeper.applyGasRefund` computes the excess gas fee and swaps it back to PC for the user via `CallUniversalCoreRefundUnusedGas` [1](#0-0) . To bound slippage it fetches a spot quote and derives `minPCOut` as a flat 95% of that quote: [2](#0-1) 

The quote itself, `GetSwapQuote`, is a single, uncached call to Uniswap V3's `QuoterV2.quoteExactInputSingle`, which reflects the pool's *current* spot price with no TWAP or multi-block averaging: [3](#0-2) 

Because the quote is fetched and the swap is executed back-to-back inside the same `MsgVoteOutbound` handling (no cross-block delay for the swap itself, but the *pool price* is entirely attacker-influenceable in prior transactions/blocks), an unprivileged actor watching the mempool for a pending `MsgVoteOutbound` that will trigger a refund swap can:
1. Push the PRC20/WPC pool price against the module (e.g., a large swap that moves `TokenIn/TokenOut` spot price) in a transaction that lands before the outbound-finalizing vote.
2. Let the module's refund swap execute at the manipulated spot price — bounded only by the flat 5% `minPCOut` floor, which is wide enough to still permit meaningful value transfer to the attacker on any refund with material size.
3. Reverse the price move afterward, pocketing the difference extracted from the module (i.e., from protocol/user gas-refund value), each time an outbound's excess gas is refunded via the swap path.

This is the same class of bug as the LTV/liquidation-threshold report: a fixed, insufficiently adaptive buffer between a "trigger" value and a "protected" value, combined with a price source the attacker can move in the same block window, turns a routine protocol operation (refunding excess gas) into a repeatable value-extraction primitive against honest users/protocol funds — no malicious validator, TSS participant, or admin is required; UV votes on the outbound observation are entirely honest and simply drive the refund logic that then swaps at attacker-manipulated pricing.

### Impact Explanation
Every outbound with a non-trivial excess-gas swap-refund is exposed. Since refunds happen automatically on both successful and failed outbounds [4](#0-3) , and the swap always uses this single spot-quote/95%-floor pattern, an attacker can repeatedly extract value on a per-outbound basis, draining refund value that should go to end users/the protocol — directly mirroring the report's "drain the vault by monitoring price and profiting from the change" attack shape.

### Likelihood Explanation
Likelihood depends on the liquidity depth of the specific PRC20/WPC pool and the frequency/size of gas-refund swaps; for a thin pool this is trivially and repeatedly exploitable by any funded, unprivileged actor with mempool visibility (no special access needed). For deep pools the extractable margin shrinks, but the underlying design flaw — spot-only pricing plus a fixed percentage floor with no TWAP, no dynamic-slippage cap by volatility, and no cool-off/other MEV mitigation — remains present regardless of pool depth.

### Recommendation
- Replace the single-block spot quote with a TWAP (or otherwise manipulation-resistant) price source for computing `minPCOut`.
- Make the slippage tolerance configurable/governed and scaled to observed volatility of the specific PRC20 pair, rather than a single hardcoded 5% for every token, echoing the "wider gap for volatile assets, narrower for stable ones" principle from the report.
- Consider splitting/limiting large refund swaps, or routing through a protected execution (e.g., commit-reveal or same-block-only quote-then-swap with a maximum allowed pool-price deviation check against a recent moving average) to remove the front-run/back-run window entirely.

### Proof of Concept
Conceptual PoC (cannot be executed without a live chain/pool):
1. Attacker monitors the mempool for a `MsgVoteOutbound` transaction that will finalize an outbound whose `gasFee - gasFeeUsed` (excess) is large enough to matter.
2. Attacker submits a swap on the underlying PRC20/WPC Uniswap V3 pool that shifts the spot price used by `GetSwapQuote`, ensuring it lands in a block/position before the vote's finalizing transaction.
3. The `MsgVoteOutbound` finalizes, triggering `applyGasRefund` → `GetDefaultFeeTierForToken` + `GetSwapQuote` (reads the now-manipulated spot price) → `minPCOut` computed as 95% of that skewed quote → `CallUniversalCoreRefundUnusedGas(..., withSwap=true, fee, minPCOut)` executes the swap at the bad rate, only guaranteed not to fall below the (already-skewed) 95% floor [5](#0-4) .
4. Attacker reverses their pool-price-moving trade in a subsequent transaction, capturing the spread that was effectively transferred out of the protocol's refund swap.

Note: I was not able to locate the underlying Solidity `UniversalCore.refundUnusedGas` / `depositPRC20WithAutoSwap` and pool contract source in the indexed portion of this repo (they live in `push-chain-core-contracts`, referenced only by ABI/address here), so the exact on-chain slippage-check semantics inside the contract itself are unverified from this repo alone; the Go-side call chain shown above is what is directly reachable and auditable here.

// applyGasRefund computes the excess gas (gasFee - gasFeeUsed) and, if positive,
// calls UniversalCore refundUnusedGas. The result is recorded in outbound.PcRefundExecution.
// It is called for both successful and failed outbounds — gas is consumed on the
// external chain regardless of execution outcome.
func (k Keeper) applyGasRefund(ctx sdk.Context, outbound *types.OutboundTx, obs *types.OutboundObservation) {
	if obs.GasFeeUsed == "" || outbound.GasFee == "" || outbound.GasToken == "" {
		return
	}

	gasFee := new(big.Int)
	if _, ok := gasFee.SetString(outbound.GasFee, 10); !ok {
		return
	}

	gasFeeUsed := new(big.Int)
	if _, ok := gasFeeUsed.SetString(obs.GasFeeUsed, 10); !ok {
		return
	}

	// No excess gas to refund
	if gasFee.Cmp(gasFeeUsed) <= 0 {
		return
	}

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}
