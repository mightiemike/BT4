## Title
Replay-verify skips state/hot-state/position checkpoint hash comparison, allowing corrupted state roots to pass as valid replays - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the function used by replay/verification tooling to confirm that a locally re-executed transaction output matches the persisted, authenticated `TransactionInfo` for that version. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed values, per its own TODO comment.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates a `TransactionOutput` against a persisted `TransactionInfo` by comparing status, gas, write-set hash, and event root hash. The function's own comment documents the gap explicitly: [2](#0-1) 

This comparator is called from consumers whose entire purpose is proof-of-correctness for replayed/synced history: `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, `execution/executor/src/chunk_executor/mod.rs`, and — most importantly — `storage/db-tool/src/replay_on_archive.rs`, which is the tool operators use to independently re-execute archived history and confirm it matches the authenticated chain state.

Because the state checkpoint hash (and, when `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state checkpointing is enabled, the hot-state and position-state checkpoint hashes) are never compared here, a divergence between the locally computed state Merkle root and the one committed/signed in the authenticated `TransactionInfo` will not be caught by this check. The write-set hash check only proves the write set itself matches, not that applying it produces the correct resulting state root — the state checkpoint hash is the only proof binding that ties the write set to the actual JMT root committed on-chain.

### Impact Explanation
If any bug elsewhere in the state-checkpoint computation path (e.g. `DoStateCheckpoint`, hot-state/position-state root construction in `execution/executor/src/workflow/do_state_checkpoint.rs`) produces a state root that differs from what was actually persisted/signed, `replay_on_archive` and other verification tooling built on `ensure_match_transaction_info` will report a **successful** replay even though the state root is wrong. This directly undermines the state-integrity guarantee that replay-verify tooling and full-node bootstrap/backup-verification flows are supposed to provide: an authenticated proof artifact (the signed `TransactionInfo.state_checkpoint_hash`) is not actually being checked against independently recomputed state, defeating the purpose of proof verification for state commitments. This is a high-severity gap because it is the exact safety net meant to catch exactly this class of state-divergence bug, and the comment confirms the developers are aware the gap exists specifically because `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state work has not yet wired in the missing checks.

### Likelihood Explanation
This is a real, already-acknowledged code gap (explicit TODO), not a hypothetical. It is a certainty that as long as the trading-native/position-state feature or any other component depending on `state_checkpoint_hash` correctness is active, no code path exercises this comparator to check checkpoint hash correctness during replay. The only mitigating factor is that this specific comparator is used for replay/debug/verification tooling rather than for consensus-time commit itself, so it does not directly corrupt the ledger — it only fails to detect that a corruption/divergence already occurred elsewhere. This still qualifies as a proof-integrity impact per the "Wrong ... state proof accepted as valid" and "Authenticated API ... output bound to the wrong version" scan criteria, since `replay_on_archive`'s job is exactly to validate that the archived, authenticated `TransactionInfo` state-checkpoint proof matches reality.

### Recommendation
Extend `ensure_match_transaction_info` to accept and compare the recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` whenever those fields are present/expected, failing the `ensure!` if they differ, before any feature that materializes those roots (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled on mainnet.

### Proof of Concept
Not independently exploitable/observable purely from this snippet without also finding a concrete bug in the state-checkpoint root computation itself; the PoC would be: (1) introduce/trigger any divergence in the computed state/hot-state/position-state root vs. the persisted `TransactionInfo` root (e.g. via a bug in `do_state_checkpoint.rs`), then (2) run `replay_on_archive` or `aptos-debugger` against that version — `ensure_match_transaction_info` will return `Ok(())` despite the state root mismatch, because it never compares those fields. I was not able to trace a concrete first-order root-cause bug that produces such a divergence in this session, so this finding should be read as: the safety-net check is provably absent (confirmed by reading the function and its TODO), but exploitation depends on a separate as-yet-unidentified root-state-computation bug to actually corrupt the checkpoint hash undetected.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
```
