## Title
Division-before-multiplication in standby witness reward distribution causes silent loss of TRX rewards - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payStandbyWitness()`, executed on every block via `Manager.payReward()`, computes each standby witness's share of the block reward pool by first dividing `totalPay` by `voteSum` and only then multiplying by the individual witness's vote count. This is the same "division before multiplication" pattern flagged in the referenced Sherlock finding, and it causes the per-witness payout to silently round to zero when a witness's vote share of the total is small, permanently losing that witness's reward every single block instead of merely deferring it.

### Finding Description
`payStandbyWitness()` computes: [1](#0-0) 

```java
long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
double eachVotePay = (double) totalPay / voteSum;
for (WitnessCapsule w : witnessStandbys) {
  long pay = (long) (w.getVoteCount() * eachVotePay);
  payReward(w.getAddress().toByteArray(), pay);
}
```

`totalPay` is first divided by `voteSum` (the sum of votes across up to 127 standby witnesses) and only then multiplied by an individual witness's `voteCount`. Because `pay` is cast to `long` (truncating toward zero), any witness whose vote count is small relative to `voteSum` gets `eachVotePay * voteCount` truncated to `0`, and `payReward` is a no-op for that witness that block: [2](#0-1) 

This function is invoked unconditionally on every produced block through `Manager.payReward(BlockCapsule)`: [3](#0-2) 

The exact same division-before-multiplication pattern (dividing a small numerator by a large denominator, then multiplying) also appears in `IncentiveManager.reward()` (the pre-`allowChangeDelegation` legacy path) and in the "old reward algorithm" `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)`: [4](#0-3) [5](#0-4) 

In each case, computing `numerator/denominator` first as a `double` and multiplying second (instead of `numerator*x/denominator`) can make the intermediate ratio round to a value so small that the subsequent multiplication and truncating cast to `long` produces `0`, exactly mirroring the root cause described in the referenced report: "division before multiplication result in loss of token reward if the reward update time elapse is small" (here, the "elapse" analog is the small vote-share/small-payout-pool ratio recomputed every block).

Notably, the codebase later introduced a correct fix pattern for the *new* reward algorithm — using `BigInteger` and multiplying before dividing (`deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)`), as seen in `RewardViCalService`/`VoteRewardUtil`/`MortgageService.computeReward(long,long,AccountCapsule)`. However, `payStandbyWitness()` and the legacy `IncentiveManager.reward()` path were not updated to this pattern and remain vulnerable.

### Impact Explanation
Standby (non-top-27) witnesses with a small share of total standby votes lose their entire block reward on every block where their computed share truncates to zero. Because this recomputation happens every ~3 seconds (each block), the loss is not a one-time rounding error but a systematic, recurring denial of expected reward, effectively zeroing out payouts for a subset of standby witnesses over the long run. This is an accounting/reward-distribution correctness issue affecting on-chain token allowance state (`AccountCapsule.allowance`), reachable purely through normal block production — no privileged actor or malicious input required.

### Likelihood Explanation
This code path executes unconditionally on every block as part of `Manager.processBlock -> payReward -> mortgageService.payStandbyWitness()`. Any standby witness whose `voteCount / voteSum` ratio is small enough that `totalPay * voteCount / voteSum < 1` will experience this truncation deterministically every block, so likelihood of impact is high for lower-ranked standby witnesses, and requires no attacker action to trigger — it is a systemic computational flaw in normal operation.

### Recommendation
Avoid dividing before multiplying. Compute `pay` using integer/`BigInteger` arithmetic with multiplication first, division last, e.g.:
```java
long pay = BigInteger.valueOf(w.getVoteCount())
    .multiply(BigInteger.valueOf(totalPay))
    .divide(BigInteger.valueOf(voteSum))
    .longValueExact();
```
Apply the same fix to `IncentiveManager.reward()` and to the legacy `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` old-algorithm path to be consistent with the multiply-then-divide `BigInteger` pattern already used by the newer VI-based reward algorithm.

### Proof of Concept
1. Configure a scenario with 127 standby witnesses where `voteSum` is large (e.g., billions of total votes) and `totalPay` (i.e., `WITNESS_127_PAY_PER_BLOCK`) is a fixed small value (historically 16 TRX = 16,000,000 sun per block).
2. Give one standby witness a low vote count relative to `voteSum`, such that `totalPay * voteCount / voteSum < 1` (e.g., `voteCount = 100`, `voteSum = 5*10^11` → `eachVotePay ≈ 0.000032`, `pay = (long)(100 * 0.000032) = 0`).
3. Call `mortgageService.payStandbyWitness()` (as invoked every block by `Manager.payReward`) and observe via `delegationStore.getReward(cycle, witnessAddress)` that no reward is credited for that witness that block, despite `voteCount > 0`.
4. Repeat over many blocks/cycles: the witness never accumulates any reward because the truncation to zero recurs every block, unlike a correct multiply-first implementation which would accumulate fractional pay correctly (or at worst lose reward only in a bounded, non-repeating rounding step per payout, not systematically every block).

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
