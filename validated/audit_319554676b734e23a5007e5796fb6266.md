This confirms the mechanism: `find_mature_miner_rewards` pays the entire commission to whichever principal is recorded as the reporter in `get_poison_microblock_report`, whoever wins the `mblock_header_1.sequence < seq` comparison in `handle_poison_microblock`, at whatever height. [1](#0-0)  The comparison is strictly `<`, so equal sequences are dropped as "someone else beat the sender". [2](#0-1) 

Now let's trace the exact equality and sequence of report ordering.

**Broken equality claim:** `reward_paid_to == earliest_valid_reporter_of_evidence`. Let's verify: with R1(seq=10) submitted first (creates record (R1,10)), then attacker (seq=3, copying R2's evidence) submitted before R2's own tx (seq=3): attacker's tx sees existing seq=10, and `3 < 10` is true, so attacker overwrites to `(attacker, 3)`. Then R2's tx sees existing seq=3, and `3 < 3` is false, so R2's report is dropped, keeping `(attacker, 3)`. Final state: reporter=attacker, seq=3 — same result that would occur if R2 had never contended, confirmed by the test at [3](#0-2)  which shows the "second/lower-sequence" submitter always wins regardless of "who discovered the fork".

This means the equality is indeed broken: the reward is paid to whichever transaction happens to be ordered first among all txs presenting the *same, lowest* sequence value for a given `pubkey_hash`/height — not to whoever first *discovered* that fork evidence. Because `PoisonMicroblock` transactions carry the full microblock headers in their payload (public information, visible in the mempool before confirmation), any third party can copy an honest reporter's exact evidence from the mempool and resubmit it with a higher fee to get sequenced earlier in the same block, thereby stealing the commission. Nothing in `check_microblock_header_signer`, the maturity check, or `handle_poison_microblock` distinguishes "first discoverer" from "first orderer/definitely-included-first" — the code has no notion of discovery time, only in-block execution order and reported sequence number.

This requires no special privilege — it is a classic mempool front-running/MEV scenario reachable by an ordinary unprivileged participant who can observe the mempool and pay a higher fee (or otherwise get block placement priority), which fits the allowed attacker model. The impact is bounded to the poison-microblock commission (a fraction of one coinbase, `POISON_MICROBLOCK_COMMISSION_FRACTION = 5%`) [4](#0-3) , i.e., fee/commission-bounded reward mis-payment — matching the "High" impact category, not a chain split or double coinbase payment (the total coinbase disposition is unaffected; only *which* principal receives the reporter's cut changes).

### Title
PoisonMicroblock commission can be front-run by copying an honest reporter's evidence and out-ordering their transaction - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
`handle_poison_microblock` awards the poison-microblock commission to whichever transaction is processed first among all transactions reporting the same lowest `sequence` for a given microblock public key hash, using a strict `<` comparison that treats ties as "already reported; drop". Since the two conflicting microblock headers proving a fork are fully public payload data of a `PoisonMicroblock` transaction (visible in the mempool prior to confirmation), any unprivileged party can copy an honest reporter's exact evidence and resubmit it with a higher fee/priority to be ordered earlier in the same block, stealing that reporter's commission without discovering the fork independently.

### Finding Description
The claimed equality — `reward recipient == earliest discoverer of the fork evidence` — does not hold. Instead, the actual invariant enforced by the code is `reward recipient == transaction processed first among all txs presenting the lowest sequence` [5](#0-4) .

Root cause: the comparison at line 821, `if mblock_header_1.sequence < seq`, only overwrites the stored report when the new sequence is strictly lower than the current champion's; equal sequences are treated as "someone else beat the sender to this report" and dropped [2](#0-1) . There is no tie-break based on discovery time, transaction hash, or timestamp — only in-block execution order matters. Because the `PoisonMicroblock` payload (`mblock_header_1`, `mblock_header_2`) is broadcast in cleartext as part of the pending transaction, an attacker monitoring the mempool can extract a valid reporter's headers and resubmit them verbatim under their own signature/principal with a higher fee, causing miners to order the attacker's copy earlier in the block. Since `check_microblock_header_signer` only validates that both headers are signed by the same microblock key [6](#0-5) , it does not check reporter originality or first-discovery, so the copy is accepted as an equally valid report at the identical sequence.

`find_mature_miner_rewards` later pays the commission to whichever principal is on record in `get_poison_microblock_report` at maturity height, with no re-validation of discovery order [1](#0-0) .

### Impact Explanation
The attacker redirects the `POISON_MICROBLOCK_COMMISSION_FRACTION` (5%) of the miner's coinbase reward from the legitimate first-discovering reporter to themselves [4](#0-3) . This is a reward mis-payment bounded strictly to the commission amount (not the full block reward, and not a chain split or invalid-block acceptance), matching the "High" severity category for "a poison or reward mis-payment bounded to fees." It is repeatable for every microblock fork any honest party detects and broadcasts before confirmation.

### Likelihood Explanation
Preconditions: an honest reporter must have submitted a valid `PoisonMicroblock` transaction to the mempool that has not yet been confirmed. The attacker needs no stake, no signer/miner privilege, and no BTC spend beyond a normal STX transaction fee bump to get miner priority. This is a standard mempool front-running pattern and is fully feasible for any network participant with mempool visibility, and repeatable each time a fork report appears in the mempool before confirmation.

### Recommendation
Change the tie-break/priority rule so it does not purely reward in-block transaction ordering for identical evidence. Options: (1) once a report at a given sequence exists, reject/ignore subsequent reports at the same sequence for the same pubkey hash+height regardless of order (i.e., use `<=` instead of `<` is wrong direction; instead keep first-seen permanently once inserted at that seq, e.g. use mempool-arrival ordering with a nonce/timestamp anchor rather than in-block position), or (2) require the reporting transaction to include a commitment tied to the original discoverer (e.g., a preceding commit-reveal scheme) so that copied evidence cannot be trivially resubmitted by a third party.

### Proof of Concept

1. Set up a chainstate and insert one microblock pubkey hash at height 1, as in `test_process_poison_microblock` test at [7](#0-6) .

5. Optionally extend to `find_mature_miner_rewards`/`calculate_miner_reward` to show the STX commission balance credited to `attacker_addr` instead of `r2_addr` at maturity, confirming the fee-bounded reward mis-payment.
