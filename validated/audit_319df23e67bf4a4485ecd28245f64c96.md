### Title
Permanent Loss of L1→L2 Bridged Funds When an L1Handler Transaction Fails/Reverts on L2 but Its Message Is Still Marked Consumed - (File: crates/apollo_batcher/src/block_builder.rs, crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo)

### Summary
The bug-class in the external report is: an irreversible action (burning the veALCX NFT) is performed before the associated unclaimed value (bribes) is settled, and once the action is taken, ownership can no longer be re-established to claim the reward — resulting in permanent loss. The Apollo sequencer has a structurally analogous flow for L1→L2 messages processed by `L1Handler` transactions: the sequencer's block-building/commit path treats a transaction whose execution failed or was rejected as "consumed" for the purposes of the L1 provider bookkeeping, while the Starknet OS explicitly skips delivering the corresponding state change (the L2 side-effect of the message, e.g. a bridge mint) for reverted L1 handler transactions. Once a message is marked consumed and that fact is committed, there is no mechanism to retry or reclaim it, so the value the L1 sender expected to receive on L2 is permanently unclaimable.

### Finding Description
1. In the Starknet OS, `execute_l1_handler_transaction` decides up front (via the `IsReverted` hint) whether to skip execution: [1](#0-0) 
If the transaction is reverted, the OS returns immediately without ever calling `consume_l1_to_l2_message` and without applying the entry point's state changes; a comment even records that "currently, the contract state is not fetched for reverted L1 handlers": [2](#0-1) 

2. On the sequencer/batcher side, however, the block-building pipeline still records the transaction hash of a failed L1Handler transaction in `consumed_l1_handler_tx_hashes`, which is what gets reported back to the L1 provider and ultimately committed to L1 as "consumed." This is demonstrated directly by the batcher's own test: [3](#0-2) 
Here, an L1Handler transaction execution result is `Err(TransactionExecutorError::StateError(...))`, yet the test explicitly asserts "all L1 handler transaction's are included in the consumed l1 transactions."

3. This "consumed" set is fed into `commit_block`, which the L1 provider's transaction manager uses to permanently transition the message state from "Pending" to "Committed" (i.e., consumed on L1, no further retries): [4](#0-3) 

The net effect: a message whose corresponding L2 execution failed/reverted (and therefore never applied the state change that was supposed to deliver value to the recipient, e.g., minting bridged tokens) can still be marked as permanently consumed at the L1-provider/commitment layer. Just as in the veALCX report — where burning the token (an irreversible operation) removes the only path (`isApprovedOrOwner`) to claim already-accrued value — here, marking the L1→L2 message as consumed (an irreversible bookkeeping operation, mirrored on L1) removes the only path to ever have that message re-delivered or reprocessed, even though the OS guarantees no state change (no value) was produced for a reverted L1 handler execution.

### Impact Explanation
If a legitimate `L1HandlerTransaction` (e.g., a bridge deposit message) reaches the sequencer and its execution reverts or otherwise fails during block building (for reasons unrelated to the correctness of the original L1 message, e.g. gas exhaustion, a transient state error, or a bug in the target contract), the value that the L1 sender is entitled to (the minted/credited funds on L2) is never applied to state, yet the message hash is included in the consumed set and committed to L1 as processed. Since Starknet's L1→L2 messaging model provides no general retry mechanism once a message is marked consumed, this results in a **permanent freezing/loss of the bridged funds** for the affected user — a concrete, fund-impacting analog of the reported "loss of unclaimed bribes after burning veALCX," with the "burn" being the irreversible consumption bookkeeping and the "unclaimed reward" being the L2 state change (funds) that was never delivered.

### Likelihood Explanation
This path is reachable purely from a single L1 message / its corresponding `L1HandlerTransaction`, requiring no privileged operator, malicious proposer, or network-level manipulation — any L1 sender who triggers a message to L2 that later fails/reverts during batcher execution (for any of the many possible revert/error reasons in `run_execute`/`non_reverting_select_execute_entry_point_func`) can trigger this divergence. The batcher's own unit test (`failed_l1_handler_transaction_consumed`) shows this is the *intended, tested* behavior rather than a rare edge case, indicating the likelihood of the underlying condition (transaction fails but is still marked consumed) is not merely theoretical.

### Recommendation
- Distinguish between "L1 message hash observed/attempted in a proposed block" and "L1 message successfully processed with side effects applied" when populating `consumed_l1_handler_tx_hashes`.
- For genuinely reverted/failed L1Handler transactions (as opposed to ones that executed successfully but produced a revert error the OS still charges fee for), ensure the transaction manager either retries the message or exposes an explicit, safe path (e.g., a cancellation/re-issuance flow already partially present via `MessageToL2Canceled`) rather than silently and permanently marking it consumed.
- Add an invariant/test asserting that any L1 message whose corresponding execution did not apply the entry point's state changes (i.e., the OS's "skip execution" branch for reverted L1 handlers) is never included in the L1-committed "consumed" set, closing the gap between the OS state-transition semantics and the batcher/L1-provider bookkeeping semantics.

### Proof of Concept
Direct reproduction of the sequencer-side inconsistency is already codified in the existing test suite and demonstrates the divergence between OS-level state effects and provider-level "consumed" bookkeeping: [3](#0-2) 
This test constructs two L1Handler transactions, forces the first to fail during execution (`StateError::OutOfRangeContractAddress`), and asserts that `result_block_artifacts.execution_data.consumed_l1_handler_tx_hashes` still contains **both** transaction hashes, including the failed one — confirming that a failed L1Handler transaction's corresponding L1 message is treated as consumed at the batcher/provider level even though, per the OS logic at `execute_l1_handler_transaction`, no corresponding state change/value delivery occurs for a transaction that does not execute successfully.

*Note: due to indexing/tool-call limits I was not able to fully trace the exact code path in `crates/apollo_batcher/src/block_builder.rs` that populates `consumed_l1_handler_tx_hashes` from execution results, nor the precise handling in `crates/apollo_l1_events/src/transaction_manager.rs` that finalizes "Committed" status upon `commit_block`. The test result cited is strong behavioral evidence of the described divergence, but a full source-level trace of the exact write path (and whether any downstream mitigation exists, e.g. a later "rejected" reclassification) should be verified with direct file access (e.g., via a Devin session) before treating this as fully confirmed.*

#[tokio::test]
async fn failed_l1_handler_transaction_consumed() {
    let l1_handler_txs = test_l1_handler_txs(0..2);
    let mock_tx_provider = mock_tx_provider_small_stream(l1_handler_txs.clone());

    let mut helper = ExpectationHelper::new();
    helper.expect_successful_get_new_results(0);
    helper.expect_is_done(false);
    helper.expect_add_txs_to_block(&l1_handler_txs);
    helper.expect_get_new_results_with_results(vec![
        Err(TransactionExecutorError::StateError(StateError::OutOfRangeContractAddress)),
        Ok((execution_info(), StateMaps::default())),
    ]);
    helper.expect_is_done(true);
    helper.expect_successful_get_new_results(0);

    helper.mock_transaction_executor.expect_close_block().times(1).return_once(|_| {
        Ok(BlockExecutionSummary {
            state_diff: Default::default(),
            compressed_state_diff: None,
            bouncer_weights: BouncerWeights::empty(),
            casm_hash_computation_data_sierra_gas: CasmHashComputationData::default(),
            casm_hash_computation_data_proving_gas: CasmHashComputationData::default(),
            compiled_class_hashes_for_migration: vec![],
            block_info: BlockInfo::create_for_testing(),
        })
    });

    let (_abort_sender, abort_receiver) = tokio::sync::oneshot::channel();
    let result_block_artifacts = run_build_block(
        helper.mock_transaction_executor,
        mock_tx_provider,
        None,
        false,
        abort_receiver,
        BLOCK_GENERATION_DEADLINE_SECS,
        DEFAULT_IDLE_TIMEOUT_MS,
    )
    .await
    .unwrap();

    // Verify that all L1 handler transaction's are included in the consumed l1 transactions.
    assert_eq!(
        result_block_artifacts.execution_data.consumed_l1_handler_tx_hashes,
        l1_handler_txs.iter().map(|tx| tx.tx_hash()).collect::<IndexSet<_>>()
    );
}
