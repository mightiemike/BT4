## What I found (confirmed)

The `DataWord` class — the TVM's 32-byte word representation — has the exact aliasing pattern described in the external report: when constructed from a 32-byte array, it stores the array **by reference** instead of copying it, and `getData()` returns that same internal reference: [1](#0-0) [2](#0-1) 

Several arithmetic/bitwise opcodes then mutate that backing array **in place** rather than allocating a new one (e.g. `xor` at [3](#0-2) ), and opcode handlers in `OperationActions` explicitly poke individual bytes of the returned array (`word1.getData()[31] = 1`), e.g. in `ltAction`/`gtAction`/`eqAction`/`isZeroAction`/`byteAction`: [4](#0-3) 

`Storage.getValue`/`Storage.put` also work directly with `key.getData()`/`value.getData()` — the raw, unlocked internal arrays — rather than defensive copies: [5](#0-4) 

Notably, `Program.storageSave` (used for `SSTORE`) is defensive — it explicitly calls `.clone()` on both the key and value before persisting: [6](#0-5) 

This asymmetry (some call sites clone, others don't) is the same class of bug as the report: an aliasing constructor/getter combined with in-place mutators creates a risk that a `byte[]` shared between a "value object" (`DataWord`) and its backing store/cache gets corrupted if any code path skips the clone.
