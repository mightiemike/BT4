### Title
Rate limiter bypass via sender-string format variation while allowlist normalizes address - ([File: core/services/functions/connector_handler.go])

### Summary
`functionsConnectorHandler.HandleGatewayMessage` normalizes `body.Sender` into an `ethCommon.Address` for the allowlist check but passes the raw, unnormalized `body.Sender` string to the rate limiter. An attacker whose address is allowlisted can vary the hex-string formatting (case, `0x` prefix, leading zeros) of the same underlying address across requests to generate distinct rate-limiter keys, defeating the intended per-sender throttling.

### Finding Description
In `core/services/functions/connector_handler.go`, `HandleGatewayMessage` computes: [1](#0-0) 

`fromAddr := ethCommon.HexToAddress(body.Sender)` canonicalizes the sender to a fixed-length 20-byte address regardless of input casing or leading-zero/prefix formatting, and this normalized value is used for the allowlist check (`h.allowlist.Allow(fromAddr)`). However, `h.rateLimiter.Allow(body.Sender)` uses the raw, attacker-supplied string as the rate-limit key. `body.Sender` comes directly from the JSON-RPC request body decoded via `hc.ValidatedMessageFromReq` (`core/services/gateway/handlers/common/message_util.go`), which only validates JSON-RPC envelope fields and calls `msg.Validate()` — it does not canonicalize or checksum the `Sender` string itself. Because Ethereum hex addresses are case-insensitive and accept variable leading-zero/prefix formatting, an attacker on the allowlist can submit functionally identical requests (same recovered/normalized address) using different string representations of `body.Sender` (e.g., `0xABCDEF...`, `0xabcdef...`, mixed-case EIP-55 variants, or same value with/without the `0x` prefix if accepted by the JSON field), each treated as a distinct key by `h.rateLimiter.Allow`. The allowlist check passes identically for all variants since it operates on the normalized `fromAddr`, but the rate limiter's internal counter map keyed by the raw string never accumulates hits against the same logical identity, so throttling never triggers for the attacker's traffic.

### Impact Explanation
This allows an allowlisted-but-otherwise-unprivileged sender to flood `MethodSecretsSet` (S4 storage writes, gated only by an insufficient-balance check, not request volume) and `MethodHeartbeat` (creates entries in `h.heartbeatRequests`/`orderedRequests` and spawns goroutines via `handleOffchainRequest`) far beyond the intended per-sender rate limit. This causes storage abuse/resource exhaustion on the gateway-connected node — matches a low/medium DoS-style bounty impact (resource exhaustion via rate-limit bypass), not a full compromise, since the allowlist and balance checks remain intact as separate gates.

### Likelihood Explanation
Feasible and repeatable for any attacker who is already allowlisted (a legitimate but potentially compromised or rate-limit-evading DON participant/user address) — this precondition is explicitly permitted by the audit scope ("attacker is on the allowlist"). No cryptographic bypass is needed: forging alternate string representations of the same Ethereum address (case variation) is trivial and does not require breaking any signature or allowlist logic, since those checks operate on the correctly normalized address.

### Recommendation
Normalize `body.Sender` before using it as the rate-limiter key, e.g., call `h.rateLimiter.Allow(fromAddr.Hex())` (or `strings.ToLower(fromAddr.Hex())`) instead of `h.rateLimiter.Allow(body.Sender)`, so the rate limiter and allowlist share the same canonical identity.

### Proof of Concept
Unit test in `core/services/functions/connector_handler_test.go`:
1. Configure `functionsConnectorHandler` with a real (non-mocked) `ratelimit.RateLimiter` with a small global/per-sender limit (e.g., 2 requests per window) and an allowlist mock that always returns `true` for a fixed address.
2. Send N+1 (e.g., 3) `HandleGatewayMessage` calls with `MethodHeartbeat` or `MethodSecretsSet`, each using a different string casing/format of `body.Sender` for the same underlying address (e.g., `"0xAAAA...AAAA"`, `"0xaaaa...aaaa"`, `"0xAaAa...aAaA"`).
3. Assert that with the current code, all 3 requests pass the rate limiter (`Allow` returns true each time, verified via absence of "request rate-limited" log or via response success), demonstrating the bypass.
4. After applying the fix (normalizing the rate-limiter key), assert the 3rd request is rejected by the rate limiter as expected.
