### Title
`decodeSessionToken` embeds attacker-controlled raw token in `InvalidJwtError.message`, which is echoed verbatim in HTTP responses via `shopify-app-express`'s `handleSessionError` - ([File: packages/apps/shopify-api/lib/session/decode-session-token.ts])

### Summary
`decodeSessionToken` builds `InvalidJwtError` messages that interpolate the raw, unvalidated bearer token plus the underlying `jose` library's specific failure reason (`signature verification failed`, `JWT expired`, malformed-compact-JWT errors, etc.). In `packages/apps/shopify-app-express`, this message is returned directly in the HTTP response body via `res.send(error.message)`, and elsewhere it is passed to `logger.debug`/`logger.error` calls without sanitization.

### Finding Description
`decodeSessionToken` catches any error thrown by `jose.jwtVerify` and rethrows it as: [1](#0-0) 
The `token` parameter is fully attacker-controlled (it comes straight from the `Authorization: Bearer` header), and `error.message` is whatever specific reason `jose` gives for rejecting the token (bad signature vs. bad `aud`/expiry vs. malformed base64/JSON all produce distinguishable messages).

This function is invoked from `getCurrentSessionId`, which is exposed through `Shopify.session.getCurrentId`: [2](#0-1) 

In `shopify-app-express`, `validateWithAuthCodeFlow` calls `api.session.getCurrentId(...)`, catches any thrown error, and routes it to `handleSessionError`, which for `InvalidJwtError` instances sends the raw `error.message` (including the embedded raw token and jose's granular failure reason) straight back in the HTTP response body: [3](#0-2) 

Separately, `shopify-app-remix`'s `validateSessionToken` logs the same unsanitized message via `logger.debug` before falling back to a generic 401 through `respondToInvalidSessionToken` (which itself does *not* leak the message to the client): [4](#0-3) [5](#0-4) 

No sanitization/redaction of the token or the underlying JWT-library error text occurs anywhere in this chain, so both CRLF/control-character content embedded in a crafted token and library-specific error text (which discloses which validation stage failed: signature vs. claims vs. parsing) reach either the HTTP client (Express) or the application log stream (Remix, and also Express's own `config.logger` calls) verbatim.

### Impact Explanation
Two distinct, scoped impacts:
1. **Information/format oracle**: An attacker can send four classes of malformed tokens (bad signature, bad `aud`, expired, malformed base64) and, by diffing the `jose` error text embedded in `InvalidJwtError.message`, determine exactly why validation failed (signature-stage vs. claims-stage vs. parse-stage). This narrows the search space for a forgery attempt by confirming which stage of validation is reached, though because HS256/HMAC verification is not susceptible to bit-flipping or padding-oracle style attacks, this does not by itself enable computing a valid signature without the secret.
2. **Log/response injection**: Because the raw token (attacker-controlled, arbitrary bytes within JWT base64url charset — but crucially, the message is a JS template literal, not URL/log-encoded) is concatenated directly into a string that is both sent to `res.send()` (Express) and passed to app loggers (`logger.debug`, `config.logger.error`), any downstream string-based log sink or fragile parser that does not itself re-encode could be influenced by adjacent content. Since JWTs are restricted to base64url characters, actual CRLF/ANSI injection via the token substring itself is not directly possible unless the app or an intermediate layer decodes/logs a decoded segment; the primary concrete impact here is the direct raw-token/error-detail leak into the HTTP response body in `shopify-app-express`.

This matches Shopify's "information leak aiding forgery / log injection" bounty class, but is a low-severity information disclosure rather than a direct account-takeover or forgery primitive, since the attacker only ever gains oracle information about *their own supplied token*, not about tokens they don't already control.

### Likelihood Explanation
Any unauthenticated caller of an app built with `shopify-app-express` that exercises the legacy Auth Code / `validateAuthenticatedSession` middleware can trigger this by sending a request with a crafted `Authorization: Bearer <token>` header, with no other preconditions (default configuration, no privileged access needed) beyond the host app using `shopify-app-express`'s standard middleware and not overriding error handling.

### Recommendation
- Do not interpolate the raw `token` value into `InvalidJwtError` messages in `decode-session-token.ts`; log/report only the `error.message` (or a generic classification such as "invalid_signature" / "expired" / "malformed") without the token payload.
- In `shopify-app-express/src/middlewares/validate-authenticated-session.ts`'s `handleSessionError`, avoid `res.send(error.message)` for `InvalidJwtError`; return a generic 401 body (mirroring `respondToInvalidSessionToken` in the Remix/React-Router packages) and log the detailed error server-side only.
- Consider normalizing all JWT validation failures to a single generic error message before they leave the library boundary, so the specific `jose` failure reason is not distinguishable externally.

### Proof of Concept
```ts
// packages/apps/shopify-app-express/src/middlewares/__tests__/validate-authenticated-session.leak.test.ts
import request from 'supertest';
// ...harness setup for validateAuthenticatedSession middleware...

test('leaks raw token and jose error detail on invalid signature', async () => {
  const res = await request(app)
    .get('/protected')
    .set('Authorization', 'Bearer eyJhbGciOiJIUzI1NiJ9.eyJhdWQiOiJhcGlLZXkifQ.badsignature');
  expect(res.status).toBe(401);
  // Vulnerable: response body contains the raw token and jose's specific reason
  expect(res.text).toContain('badsignature');
  expect(res.text).toMatch(/signature verification failed/);
});

test('distinguishes failure classes via error text', async () => {
  const expiredRes = await request(app).get('/protected')
    .set('Authorization', `Bearer ${expiredToken}`);
  const malformedRes = await request(app).get('/protected')
    .set('Authorization', 'Bearer not-a-jwt');
  // Fails desired invariant: messages are NOT indistinguishable
  expect(expiredRes.text).not.toEqual(malformedRes.text);
});
```
Expected (secure) behavior: both responses should return an identical generic 401 body with no token content or jose-specific error text, matching what `respondToInvalidSessionToken` already does in the Remix/React-Router packages.

export function respondToInvalidSessionToken({
  params,
  request,
  retryRequest = false,
}: RespondToInvalidSessionTokenParams) {
  const {api, logger, config} = params;

  const isDocumentRequest = !request.headers.get('authorization');
  if (isDocumentRequest) {
    return redirectToBouncePage({api, logger, config}, new URL(request.url));
  }

  throw new Response(undefined, {
    status: 401,
    statusText: 'Unauthorized',
    headers: retryRequest ? RETRY_INVALID_SESSION_HEADER : {},
  });
