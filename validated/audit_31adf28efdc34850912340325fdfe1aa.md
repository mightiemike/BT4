Based on my research, I found a concrete, self-documented integrity gap in the replay/proof-verification path, not just an analog inference.

### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, allowing corrupted state roots to pass as verified during chunk replay - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the function used to validate a locally re-executed/replayed `TransactionOutput` against an authenticated `TransactionInfo` (the object anchored in the transaction accumulator and covered by validator signatures/consistency proofs). While it validates status, gas used, write-set hash, and event root hash, it explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually commit to the resulting Merkle state roots. This is acknowledged directly in the code's own TODO comment.

### Finding Description [1](#0-0) 

The function compares four things between a computed `TransactionOutput` and the target `TransactionInfo`: execution status, gas used, the write-set hash (`state_change_hash`), and the event root hash [2](#0-1) . It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, and the code says so explicitly: [3](#0-2) 

Critically, `write_set_hash` is only the hash of the raw per-transaction write diffs — it is not the resulting Jellyfish Merkle Tree state root, hot-state root, or native-position-tree root. Those roots are computed separately during state-checkpoint/ledger-update processing [4](#0-3)  and are only bound into `TransactionInfoV1` when the relevant feature flags (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) are enabled, precisely so they become "consensus-verified" [5](#0-4) .

`ensure_match_transaction_info` is called from the chunk executor path used during state sync/replay [6](#0-5) , as well as from `aptos-debugger` and the Aptos CLI (`aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`). I was unable to fully view the exact call-site logic inside `chunk_executor/mod.rs` in this session (the file read returned no content for the requested range), so I cannot confirm with certainty whether the chunk-executor caller performs an independent state-root check elsewhere in its pipeline that would compensate for this gap.

### Impact Explanation
If a node's locally-computed state root (main JMT state root, hot-state root, or the newer native-position Merkle root) diverges from the authenticated value carried in `TransactionInfoV1` — whether due to a local execution/serialization bug, a stale replay path, or storage corruption — this validation function will still report success as long as the write-set bytes, events, gas, and status match. This defeats the entire purpose of the state-checkpoint-hash fields being "committed to the ledger accumulator" for consensus verification, and it means replay-verify tooling (e.g., `replay_on_archive`) can certify a corrupted/divergent local ledger state as consistent with the authenticated chain history. This is exactly the class of proof-binding violation called out in the task's scope ("Authenticated API or state-view output bound to the wrong version, object, or proof context" and "Committed state that differs from the correct VM result").

### Likelihood Explanation
This is not a hypothetical or speculative issue — the code's own comment (lines 2197-2202) documents that this gap exists and explicitly warns that enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` without first fixing this check would let replay-verify tooling silently miss position-state divergence. This is a real gap in the currently shipped verification logic, and it applies immediately once any workflow using `ensure_match_transaction_info` needs to actually validate checkpoint-hash-bearing `TransactionInfoV1` records (i.e., once `TRANSACTION_INFO_V1` plus the trading-native or hot-state-root flags are active).

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the target `TransactionInfo`) against the locally computed roots before those checkpoint-committing feature flags (especially `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) are enabled on mainnet, exactly as the existing TODO comment recommends.

### Proof of Concept
Not applicable as a standalone exploit script — the "proof of concept" here is the code path itself: any caller invoking `TransactionOutput::ensure_match_transaction_info` on a `TransactionInfoV1` populated with a `position_state_checkpoint_hash` (or `hot_state_checkpoint_hash`) that differs from the value implied by the locally computed state will still receive `Ok(())`, since none of the `ensure!` checks in the function inspect those fields [7](#0-6) .

**Caveat on confidence**: I could not directly inspect the exact call site inside `execution/executor/src/chunk_executor/mod.rs` in this session (tool read returned empty), so I cannot fully rule out that an independent, redundant state-root check exists elsewhere in that specific caller's pipeline that would mitigate the impact for chunk-execution specifically. The gap in `ensure_match_transaction_info` itself, however, is confirmed directly from source and its own documentation.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

        (0..to_commit.len())

                        )
                        .build()
                } else {
                    TransactionInfo::builder_v0()

                        .state_change_hash(write_set_hash)
                        .event_root_hash(event_root_hash)
                        .maybe_state_checkpoint_hash(state_checkpoint_hash)
                        .gas_used(txn_output.gas_used())
                        .status(status)
                        .maybe_auxiliary_info_hash(auxiliary_info_hash)
