### Title
Deposit Refund Misdirection in Meta-Transaction Failure: Relayer Loses Attached Deposit to Sender — (`runtime/runtime/src/actions.rs`)

### Summary

When a `DelegateAction` (meta-transaction) inner receipt fails on the receiver's shard, the attached deposit is refunded to the **sender** (`Alice`) rather than the **relayer** who actually paid it. An unprivileged user can deliberately craft a `DelegateAction` with a large attached deposit that is guaranteed to fail on the receiver's shard, causing the relayer to permanently lose the deposit while the user gains it.

### Finding Description

In `apply_delegate_action`, the inner receipt spawned from a `DelegateAction` is constructed with `predecessor_id` set to `sender_id` (Alice, the delegate signer), while `signer_id` is set to the relayer: [1](#0-0) 

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // ← Alice
    receiver_id: delegate_action.receiver_id().clone(),
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // ← Relayer
        ...
        actions: delegate_action.get_actions(),
    }),
});
```

When this inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` is called. The deposit refund is sent to `receipt.balance_refund_receiver()`, which resolves to `receipt.predecessor_id()` — Alice: [2](#0-1) 

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(), // ← resolves to predecessor_id = Alice
        deposit_refund,
    ));
}
```

The `balance_refund_receiver` method returns `predecessor_id` for `ReceiptEnum::Action` receipts (the type used for the inner receipt): [3](#0-2) 

The gas refund correctly goes to the relayer (via `signer_id`), but the deposit — which the relayer paid — goes to Alice.

The code comment at the construction site acknowledges this behavior: [4](#0-3) 

> "If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction."

The architecture documentation also explicitly acknowledges the financial incentive this creates: [5](#0-4) 

> "But what if the transaction fails execution on Bob's shard? At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a **financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard**."

### Impact Explanation

The relayer pays the full deposit when the transaction is converted to a receipt (gas purchase step). If the inner receipt fails, the deposit is refunded to Alice, not the relayer. The relayer suffers a permanent loss equal to the attached deposit. Alice gains the deposit without having paid for it. This is a direct, protocol-enforced balance transfer from relayer to Alice triggered by a deliberate failure.

The broken invariant: **the party who funded the deposit must receive the refund on failure**. The exact corrupted value is `deposit_refund` (the full sum of all `deposit` fields in the inner actions) being credited to Alice's account instead of the relayer's.

### Likelihood Explanation

Any user who can submit a `DelegateAction` to a relayer can exploit this. The attack requires:
1. Alice constructs a `DelegateAction` with a large `deposit` attached to a `FunctionCall` or `Transfer` targeting a receiver that will fail (e.g., a non-existent account, a contract that panics, or a method that does not exist).
2. Alice submits this to a relayer.
3. The relayer, after off-chain validation, submits the meta-transaction.
4. The inner receipt fails on the receiver's shard.
5. The deposit is refunded to Alice.

No privileged access is required. The attack is repeatable and scales linearly with the deposit size the relayer is willing to forward.

### Recommendation

The inner receipt spawned by `apply_delegate_action` should set `predecessor_id` to the relayer (the outer receipt's `predecessor_id` or `signer_id`) rather than `sender_id`, so that deposit refunds on failure flow back to the party who funded them. Alternatively, the `ActionReceiptV2` `refund_to` field (already present in the codebase for redirecting refunds) should be set to the relayer's account ID when constructing the inner receipt, overriding the default `predecessor_id`-based refund routing: [6](#0-5) 

This would ensure that `balance_refund_receiver()` returns the relayer rather than Alice when the inner receipt fails.

### Proof of Concept

1. Relayer `R` operates a meta-transaction service.
2. Alice (`A`) constructs a `DelegateAction` targeting `Bob` with a `FunctionCall` action carrying `deposit = 100 NEAR` to a method that does not exist on Bob's contract.
3. Alice submits the signed `DelegateAction` to `R`.
4. `R` wraps it in a transaction (paying gas + the 100 NEAR deposit from its own balance) and submits it.
5. On Alice's shard, `apply_delegate_action` creates an inner receipt: `predecessor_id = Alice`, `signer_id = R`.
6. On Bob's shard, the function call fails (`MethodNotFound`). `refund_unspent_gas_and_deposits` runs:
   - `deposit_refund = 100 NEAR`
   - `Receipt::new_balance_refund(receipt.balance_refund_receiver(), 100 NEAR)` → refund sent to Alice.
   - Gas refund sent to `R` (signer).
7. Alice's balance increases by 100 NEAR. R's balance decreases by 100 NEAR (net of gas refund).

Alice can repeat this attack indefinitely, draining the relayer's deposit budget.

    pub fn refund_to(&self) -> &Option<AccountId> {
        match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }
