## Analysis: Spot-price manipulation analog found in TRX/TRC10 Exchange (Bancor-style AMM)

The Sherlock report concerns `CurveOracle.getPrice` deriving an LP token's USD value from **spot** balances of the underlying Curve pool — balances that can be skewed within a single transaction/flash loan, and that value is then trusted by downstream settlement logic without a TWAP.

java-tron's native TRC10 "Exchange" module (a Bancor-relay AMM, not a smart contract) exhibits the same root-cause pattern: settlement amounts for liquidity add/remove are computed directly from the pool's **current spot reserve balances**, which are themselves mutated in the same block by ordinary swap transactions, with no time-weighting or invariant check protecting the withdraw/inject math.

### Title
Spot-balance-ratio manipulation in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` enables value extraction from TRC10 Exchange pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeCapsule.transaction()` prices swaps using a Bancor relay-supply formula [1](#0-0) , executed via `ExchangeTransactionActuator`, which any unprivileged account can call against any pool [2](#0-1) . In contrast, `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the paired-token settlement amount from a **simple linear ratio** of the pool's current `firstTokenBalance`/`secondTokenBalance` — i.e., the raw spot reserves — rather than from the Bancor invariant used for swaps: [3](#0-2)  and [4](#0-3) . This is structurally identical to CurveOracle's reliance on manipulable spot balances rather than a manipulation-resistant price source.

### Finding Description
Each `Exchange` pool has exactly one privileged-per-pool address, its `creatorAddress`, checked in `doValidate()` of both Inject and Withdraw [5](#0-4) . Crucially, this "creator" role is **not** a chain-level trusted role — any unprivileged account can call `ExchangeCreateActuator` and become creator of its own pool, then invite/permit arbitrary counterparties to trade against it via the permissionless `ExchangeTransactionActuator`.

Because `ExchangeTransactionActuator` mutates `firstTokenBalance`/`secondTokenBalance` on every trade [6](#0-5) , and `ExchangeWithdrawActuator`/`ExchangeInjectActuator` immediately read those same fields to compute the "other token" amount for a liquidity operation [7](#0-6) , a creator can:
1. Execute (or have an accomplice execute) a large `ExchangeTransactionContract` trade that skews the reserve ratio away from its "fair" pre-trade state.
2. Immediately submit `ExchangeWithdrawContract`/`ExchangeInjectContract` in the same block, extracting/injecting tokens at the now-skewed linear ratio instead of the value the Bancor curve would imply.
3. Reverse the initial trade in a subsequent transaction in the same block to restore the ratio, pocketing the difference.

This mirrors the CurveOracle bug class exactly: a price/ratio read from mutable, single-block reserve state is trusted by settlement logic (`Inject`/`Withdraw`) without any TWAP or invariant-consistency check, even though the same reserves are read as a spot price by a sibling swap function (`transaction()`).

### Impact Explanation
An attacker who creates a pool and lures liquidity/trading volume into it can extract value disproportionate to their actual pool ownership by timing trade + inject/withdraw sequences within a single block, at the expense of counterparties who traded into the skewed pool. This is an accounting/economic-manipulation impact consistent with "underpriced-public-work" / settlement-manipulation classes: the withdraw/inject amount is mispriced relative to the pool's true bonding-curve state.

### Likelihood Explanation
Requires no special privilege beyond creating one's own Exchange pool (permissionless) and controlling transaction ordering within a single block (achievable by any account submitting back-to-back transactions, or trivially by a block-producing witness). No flash loan primitive is needed since java-tron's own multi-step actuator flow inside one block reproduces the same atomicity assumption abused in the original report.

### Recommendation
Compute `anotherTokenQuant` in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` using the same invariant-preserving (Bancor relay-supply) math as `ExchangeCapsule.transaction()`, or add a minimum-holding-period / TWAP-based check on reserve ratios before allowing inject/withdraw, so that spot-balance manipulation via interleaved swaps cannot change the payout ratio for liquidity operations within the same block.

### Proof of Concept
1. Account C calls `ExchangeCreateActuator` to create pool P(A,B) with balances A0:B0 (C is creator).
2. Account U (any unprivileged trader) calls `ExchangeTransactionActuator` selling a large amount of A into P, driving `firstTokenBalance` up and `secondTokenBalance` down per `ExchangeCapsule.transaction()` [8](#0-7) .
3. In the same block, C calls `ExchangeWithdrawActuator` withdrawing token A; `anotherTokenQuant` is computed from the now-skewed `secondTokenBalance/firstTokenBalance` ratio [9](#0-8) , yielding more of token B than the pre-trade ratio would have given.
4. C (or U) reverses U's trade with an opposite `ExchangeTransactionActuator` call, restoring the ratio and leaving C with a net gain of token B extracted from U's trade proceeds, beyond what the Bancor curve alone would allow.

    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
