### Title
Inconsistent Rounding in Hardened Withdraw Precision Check Causes Persistent Denial-of-Service on `ExchangeWithdrawActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
When the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal is enacted, `ExchangeWithdrawActuator.doValidate()` recomputes the expected counter-token amount using 4-decimal `HALF_UP` rounding and compares it against the actual `anotherTokenQuant`, which was computed via plain integer (floor) division. Because the two values use different rounding rules, any withdrawal whose true fractional remainder is ≥ 0.5 will systematically fail with `"Not precise enough"`, even though the withdrawer supplied no invalid input. Since which amounts trigger this failure depends entirely on the live `firstTokenBalance`/`secondTokenBalance` ratio (i.e., the pool's internal "exchange rate"), ordinary trading activity that shifts this ratio can push withdraw operations into a state where the check fails for essentially all viable quantities, freezing the creator's ability to withdraw liquidity until governance disables the hardening proposal.

### Finding Description
`ExchangeWithdrawActuator.execute()` computes the counter-token amount with plain (floor) integer division: [1](#0-0) 

`doValidate()`, however, computes the same value the same way (`divideToIntegralValue`, i.e. floor), but then — only when hardening is enabled — recomputes a *second*, more precise reference value using 4-decimal `HALF_UP` rounding and demands the two agree within a 0.0001 relative tolerance: [2](#0-1) 

Because `anotherTokenQuant` is always the *floor* of `secondTokenBalance * tokenQuant / firstTokenBalance`, while the "expected" reference value rounds to the nearest 4-decimal value, any true quotient whose fractional part is ≥ 0.5 causes the reference to round *up* a full unit relative to the floor result. The resulting `remainder` (≈1.0) then exceeds the tolerance `anotherTokenQuant * 0.0001` for any `anotherTokenQuant` below ~10,000, unconditionally triggering `"Not precise enough"` — regardless of what value the withdrawer chooses. This is not a validation of user-supplied precision; it is an inherent inconsistency between two internally-computed values, driven purely by the pool's current token-balance ratio (i.e., the internal exchange rate), analogous to the `ImbalancedPool` revert in the reported `SelfPeggingAsset.collectFeeOrYield()` bug: a state-dependent invariant check that can be forced into permanent failure by the same "exchange rate" that legitimate operations rely on.

The `allowHarden()` flag is controlled solely by the `ALLOW_HARDEN_EXCHANGE_CALCULATION` governance proposal: [3](#0-2) [4](#0-3) 

so once enabled, no unprivileged actor can restore withdraw functionality for affected balance ratios — matching the report's description of a freeze that "effectively locks... until the owner or an administrator intervenes."

### Impact Explanation
Any account (the exchange's creator) attempting `ExchangeWithdrawContract` transactions can be denied service persistently whenever the pool ratio at withdrawal time makes the true division's fractional part ≥ 0.5 and `anotherTokenQuant` is below the ~10,000-unit threshold where the absolute rounding error exceeds the 0.0001 relative tolerance. Since token balance ratios shift continuously due to normal `ExchangeTransactionContract`/`ExchangeInjectContract` activity by any user, this can render withdrawal effectively unusable for extended periods without requiring any malicious actor — a pure availability/accounting-consistency defect in the on-chain exchange market implementation.

### Likelihood Explanation
This triggers under normal usage once the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal (already defined and gated only by a standard fork/committee proposal, not privileged runtime access) is active and the pool's token ratio combined with a chosen `tokenQuant` naturally produces a fractional quotient ≥ 0.5 for a reasonably small counter-token amount — a common, easily reproducible scenario in ordinary AMM-style trading pools, requiring no attacker privilege.

### Recommendation
Make the precision reference calculation use the same rounding mode (floor / `RoundingMode.DOWN`) as the actual `anotherTokenQuant` computation, or compare using an absolute tolerance derived consistently from the same division method, so the check only rejects genuinely imprecise/manipulated inputs rather than an artifact of mismatched rounding between two internally derived values.

### Proof of Concept
1. Enable `ALLOW_HARDEN_EXCHANGE_CALCULATION` via governance proposal.
2. Create/observe an exchange pool where `firstTokenBalance` and `secondTokenBalance` yield a ratio such that `secondTokenBalance * tokenQuant / firstTokenBalance` has a fractional part ≥ 0.5 for the desired `tokenQuant` (e.g., `firstTokenBalance = 3`, `secondTokenBalance = 2`, `tokenQuant = 1` → true quotient `0.6667`, floor `anotherTokenQuant = 0` fails the `> 0` check first; choose values so `anotherTokenQuant` is small but nonzero, e.g., `firstTokenBalance = 7`, `secondTokenBalance = 10`, `tokenQuant = 5` → true quotient `50/7 = 7.142857` floor `7`; instead pick a ratio producing fractional ≥ .5 with a small quotient, e.g., `firstTokenBalance = 4`, `secondTokenBalance = 3`, `tokenQuant = 5` → quotient `15/4=3.75`, floor `3`, HALF_UP-rounded-to-4-decimals reference `3.7500` truncated to long via `.doubleValue()-anotherTokenQuant` in non-hardened path is fine, but in hardened path `remainder = 3.7500 - 3 = 0.75`, threshold `= 3*0.0001=0.0003` → `0.75 > 0.0003` → `ContractValidateException("Not precise enough")`.
3. Call `ExchangeWithdrawActuator.validate()` with these parameters — the transaction is rejected every time regardless of resubmission, for as long as the pool ratio remains in this regime, demonstrating the persistent, state-driven denial-of-service analogous to the reported `ImbalancedPool` freeze.
