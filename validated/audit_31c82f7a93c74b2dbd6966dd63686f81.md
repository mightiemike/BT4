### Title
Replay-verify tooling silently accepts wrong state-checkpoint / hot-state / position-state roots - (File: `types/src/transaction/mod.rs`)

### Summary
The `db-tool replay-verify` / backup-verify pipeline re-executes archived transactions and compares the freshly-computed `TransactionOutput` against the `TransactionInfo` recorded in the backup, using `TransactionOutput::ensure_match_transaction_info`. This function checks status, gas, write-set hash, and event root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. A state-root divergence (e.g., from a JMT/hot-state/position-state bug, or a maliciously/accidentally corrupted archive) will pass replay-verify undetected, defeating the tool's purpose of catching state-commitment divergence before it reaches consensus/mainnet operators.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  validates only:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

The function contains an explicit acknowledgement of the gap: [2](#0-1) 

This comparator is invoked by `ChunkExecutor::verify_execution`, the routine used by `db-tool replay-verify` (and `replay_on_archive`) to re-execute a chunk of archived transactions and confirm local execution matches the recorded, ledger-info-signed `TransactionInfo`s: [3](#0-2) 

However, `TransactionInfo` (V1) actually carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields that are supposed to bind the committed JMT root, hot-state root, and native-position-state root for that version, as assembled during normal commit in `DoLedgerUpdate::assemble_transaction_infos`: [4](#0-3) 

Because `ensure_match_transaction_info` never re-derives and compares these checkpoint hashes against the locally recomputed state after replay, any divergence in the state tree (main state, hot state, or native position state) that still produces a matching write set and event hashes will not be flagged by replay-verify. This can occur, for example, from a bug in JMT hashing, hot-state checkpoint construction, or the newer native-position-state commit path (`commit_native_position` in `storage/aptosdb/src/db/aptosdb_writer.rs`), all of which are separate write paths from the write-set/event hash and are not otherwise reconciled by this check.

### Impact Explanation
Replay-verify (`storage/db-tool/src/replay_verify.rs`, `storage/backup/backup-cli/src/coordinators/replay_verify.rs`) is a primary mechanism operators and Aptos Labs use to detect nondeterminism/hard-fork divergence between a canonical backup and local re-execution across node software versions. Because the verification path silently ignores checkpoint-hash fields that are the actual binding of the committed state root, a hard-fork-class state divergence (wrong JMT root, wrong hot-state root, or wrong position-state root committed to durable storage) would go undetected by this tool even though the write set and events match. This directly matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong accumulator root ... accepted as valid" impact categories in the gate, since the checkpoint hash is exactly the field an accumulator/`TransactionInfo` uses to commit the state root for that version.

### Likelihood Explanation
This is not a hypothetical stretch: the code contains an explicit `TODO(trading-native)` comment written by the maintainers stating the comparator "ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." This is a real, currently-shipped gap in a verification-oriented tool, not merely event-only or a minor rounding difference — it is a proof/commitment-integrity omission in the exact invariant the gate calls out (root/commitment binding surviving executor-to-storage handoff and cross-checks). The likelihood of being triggered scales with any bug in the newer hot-state / native-position-state code paths, which are called out in the same comment as feature-gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` (or its caller in `ChunkExecutor::verify_execution`) to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` from the locally re-executed state against the corresponding fields on the provided `TransactionInfo`, failing verification on any mismatch, before enabling/relying on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any hot-state/position-state feature in production replay-verify runs.

### Proof of Concept
No exploit PoC is provided; this is a code-inspection finding based on the maintainers' own TODO annotation combined with tracing the call graph (`db-tool replay-verify` → `ReplayVerifyCoordinator` → `ChunkExecutor::verify_execution` → `TransactionOutput::ensure_match_transaction_info`) to confirm the checkpoint-hash fields are never compared. A full demonstration would require constructing a chunk of transactions whose write set and events are unchanged but whose state/hot-state/position-state checkpoint hash differs from the recorded `TransactionInfo`, and showing `verify_execution` returns `Ok`. I was not able to execute this in the current read-only environment; this should be validated by a Devin agent with test-execution access before treating it as fully confirmed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
