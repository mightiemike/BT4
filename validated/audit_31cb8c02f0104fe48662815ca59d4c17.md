### Title
Unthrottled Transaction Submission Endpoint Enables Application-Layer DoS via Repeated Signature Verification and Trie Reads — (File: `chain/jsonrpc/src/lib.rs`, `chain/client/src/rpc_handler.rs`)

### Summary

The nearcore JSON-RPC HTTP server exposes `broadcast_tx_async`, `broadcast_tx_commit`, and `send_tx` endpoints with no per-IP or per-origin rate limiting. Every submission — including those with invalid signatures or non-existent signers — unconditionally triggers an ED25519 signature verification and, when the node tracks the relevant shard, a trie read for the signer account and access key. An unprivileged attacker can pipeline arbitrarily many crafted requests at zero cost, exhausting the `RpcHandlerActor` thread pool and degrading or denying service to legitimate users. No hardfork is required to fix this.

### Finding Description

`RpcConfig` (the sole configuration struct for the JSON-RPC server) contains only a body-size cap and CORS settings — no rate-limiting field exists: [1](#0-0) 

The Axum router is built with exactly two middleware layers — `CorsLayer` and `RequestBodyLimitLayer` (10 MB) — and nothing else: [2](#0-1) 

A grep of the entire `chain/jsonrpc/src/` tree for any rate-limit, throttle, or per-IP token-bucket symbol returns zero matches. The `RpcHandlerConfig` struct likewise carries no rate-limiting state: [3](#0-2) 

For every `ProcessTxRequest` that arrives, `process_tx_internal` unconditionally executes:

1. **`check_transaction_validity_period`** — chain-store reads to verify the referenced block hash.
2. **`validate_tx` → `ValidatedTransaction::new`** — performs a full ED25519 `signature.verify()` call regardless of whether the signer account exists: [4](#0-3) 

3. **`can_verify_and_charge_tx`** — when the node tracks the signer's shard, opens a trie handle and reads the signer account and access key from storage: [5](#0-4) 

All three steps execute before any error is returned to the caller. For `broadcast_tx_async` the HTTP response is returned immediately (fire-and-forget), so the attacker does not even need to wait for the response before sending the next request: [6](#0-5) 

By contrast, rate limiting in nearcore exists only for peer-to-peer `PeerMessage` traffic via `RateLimits` / `TokenBucket` in `chain/network/src/rate_limits/` — it is entirely absent from the HTTP RPC path: [7](#0-6) 

### Impact Explanation

An unprivileged attacker submitting transactions with a syntactically valid but cryptographically invalid signature (or referencing a non-existent `signer_id`) pays zero on-chain cost. Each request forces the node to:
- Execute one ED25519 verify (CPU-bound, ~50–100 µs per call).
- Perform one or two trie reads (I/O-bound, hitting RocksDB or memtrie).

At a sustained rate of thousands of requests per second — trivially achievable from a single machine over HTTP — the `RpcHandlerActor` thread pool saturates, response latency for legitimate transactions rises, and the node may stop accepting new transactions entirely. This is a non-network-level application-layer DoS fixable without a hardfork.

### Likelihood Explanation

The endpoint is publicly reachable on port 3030 by default with `cors_allowed_origins: ["*"]`. No authentication, API key, or connection-level throttle is required. The `broadcast_tx_async` fire-and-forget path makes pipelining trivial. Any actor who can reach the node's RPC port can trigger this.

### Recommendation

Add a per-IP token-bucket rate-limiting middleware layer to the Axum router in `chain/jsonrpc/src/lib.rs`, applied before request deserialization. The existing `chain/network/src/concurrency/rate.rs` `Limit` / `chain/network/src/rate_limits/token_bucket.rs` infrastructure can be reused or adapted. The limit should be enforced even when the submitted transaction is later found to be invalid, mirroring the recommendation in the seed report. [8](#0-7) 

### Proof of Concept

```python
import asyncio, aiohttp, base64, borsh_construct as borsh

# Craft a syntactically valid SignedTransaction with a random (invalid) 64-byte signature.
# The Borsh-encoded payload passes the 10 MB body limit and basic deserialization.
# The node will run ED25519 verify on every request and return InvalidSignature.

ENDPOINT = "http://<node>:3030"
PAYLOAD = {
    "jsonrpc": "2.0", "id": "x", "method": "broadcast_tx_async",
    "params": ["<base64-borsh-encoded SignedTransaction with garbage signature>"]
}

async def flood():
    async with aiohttp.ClientSession() as s:
        await asyncio.gather(*[s.post(ENDPOINT, json=PAYLOAD) for _ in range(10_000)])

asyncio.run(flood())
# Each of the 10,000 requests triggers one ED25519 verify + optional trie read
# with no per-IP throttle, saturating RpcHandlerActor worker threads.
