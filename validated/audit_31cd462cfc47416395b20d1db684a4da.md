### Title
Coinbase reward split among miner and user-burn-supporters permanently loses reward dust due to per-participant integer division - (File: `stackslib/src/chainstate/stacks/db/accounts.rs`)

### Summary
`StacksChainState::calculate_miner_reward()` computes each block-mining participant's (miner + every user-burn-supporter) share of the coinbase as `participant.coinbase * this_burn_total / burn_total`, using truncating integer division. Because this function is invoked independently once per participant (once for the miner, once for each user-support-burn entry), and each call performs its own floor division against the same `burn_total` denominator, the sum of all participants' resulting `coinbase_reward` values can be strictly less than the block's total `coinbase` amount. The truncated remainder is never minted to anyone — it is permanently lost, exactly the "precision loss leads to locked incentives" pattern from the referenced report, applied to Stacks' coinbase distribution instead of an ERC-20 incentive pool.

### Finding Description
`calculate_miner_reward` computes, for each participant (miner or user-burn-supporter): [1](#0-0) 

This is called once for the miner and once per user reward from `find_mature_miner_rewards`, each call being independent and using the same `participant.coinbase` total value but a different `this_burn_total`: [2](#0-1) 

Since `coinbase_reward_i = floor(coinbase * burn_i / burn_total)` is computed independently for every participant `i`, the invariant `Σ coinbase_reward_i == coinbase` does not generally hold — the sum can be strictly less whenever `burn_i` values do not divide `burn_total` cleanly (which is the common case, since burn amounts are chosen freely by burnchain participants sending BTC). The shortfall is never separately accounted for or minted anywhere; `process_matured_miner_rewards` only sums and mints exactly what `calculate_miner_reward` returned per participant: [3](#0-2) 

This mirrors the reported bug class precisely: a percentage/ratio computed via integer division for multiple claimants of a shared pool, where each claimant's floor-rounded share can leave dust that is permanently unclaimed/unminted.

Note: because every full node performs this exact same deterministic computation from already-committed consensus data (the participants' `burnchain_commit_burn` amounts recorded from the burnchain), this does *not* cause any state-root or node-to-node divergence — all nodes compute and agree on the same (slightly reduced) total minted coinbase. The issue is a permanent, protocol-level reward loss, not a chain split.

### Impact Explanation
Any user who submits a user-burn-support transaction (an unprivileged, permissionless burnchain operation available to any burner) with a burn amount that does not evenly divide the aggregate burn total will cause the coinbase reward split to leave dust that is never minted to the miner, to any user-burn-supporter, or to any other account — a small, permanent reduction of the block-reward total actually paid out relative to the schedule. This matches "block-reward ... loss" as an allowed impact category, though the magnitude per block is bounded to at most `(number of participants - 1)` micro-STX units of dust (a rounding artifact, not majority- or admin-triggerable).

### Likelihood Explanation
Extremely likely to occur on essentially every block that has more than one coinbase-reward participant (i.e., any block with at least one user-burn-support transaction alongside the miner), since burn amounts practically never divide evenly. No coordination, privilege, or majority is required — a single unprivileged user burning BTC in support of a block commit can trigger it.

### Recommendation
Compute all participants' proportional coinbase shares within a single pass (as already effectively done via `this_burn_total`/`other_burn_total` bookkeeping) and explicitly account for/allocate the remainder — e.g., award the truncation remainder to the miner (the canonical last-resort recipient, analogous to how transaction fee remainders are commonly handled) instead of silently discarding it, so that `Σ coinbase_reward_i == coinbase` holds exactly for every block.

### Proof of Concept
Given a block with `coinbase = 1000`, a miner with `burnchain_commit_burn = 3`, and a single user-burn-supporter with `burnchain_commit_burn = 1` (`burn_total = 4`):
- Miner's share: `floor(1000 * 3 / 4) = 750`
- User's share: `floor(1000 * 1 / 4) = 250`
- Sum minted: `1000` (this particular ratio happens to divide evenly)

Now use `burn_total = 3` with `burnchain_commit_burn` values `2` (miner) and `1` (user):
- Miner's share: `floor(1000 * 2 / 3) = 666`
- User's share: `floor(1000 * 1 / 3) = 333`
- Sum minted: `999` instead of `1000` — `1` micro-STX of coinbase is permanently lost, never minted to any account, exactly reproducing `calculate_miner_reward`'s independent floor-division logic at [4](#0-3) . Because a burner freely chooses their `burnchain_commit_burn`, they can trivially engineer ratios like this on every block they participate in.

    /// Process matured miner rewards for this block.
    /// Returns the number of liquid uSTX created -- i.e. the coinbase
    pub fn process_matured_miner_rewards(
        clarity_tx: &mut ClarityTx<'_, '_>,
        miner_share: &MinerReward,
        users_share: &[MinerReward],
        parent_share: &MinerReward,
    ) -> Result<u128, Error> {
        let mut coinbase_reward = miner_share.coinbase;
        StacksChainState::process_matured_miner_reward(clarity_tx, miner_share)?;
        for reward in users_share.iter() {
            coinbase_reward += reward.coinbase;
            StacksChainState::process_matured_miner_reward(clarity_tx, reward)?;
        }

        // give the parent its confirmed share of the streamed microblocks
        assert_eq!(parent_share.total(), parent_share.tx_fees_streamed_produced);
        StacksChainState::process_matured_miner_reward(clarity_tx, parent_share)?;
        Ok(coinbase_reward)
    }
