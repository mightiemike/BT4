### Title
Failed/timed-out contract execution logs leak into persisted `TransactionInfo` events when `allowTvmOsaka` is not active - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
This is a direct analog of the Phoenix SDK bug: events/logs are recorded for a transaction execution path even though the transaction ultimately failed. In java-tron, `VMActuator.execute()` clears accumulated `LogInfo` entries from a reverted/failed execution on the *normal* return path unconditionally, but on the *exception* paths (`JVMStackOverFlowException`, `OutOfTimeException`, generic `Throwable`) it only clears them via `clearExceptionResult()`, which is gated behind the `VMConfig.allowTvmOsaka()` feature flag.

### Finding Description
In the normal (non-exception) execution path, when the top-level call reverts or throws, logs are cleared unconditionally: [1](#0-0) 

However, when execution instead exits via a Java exception (stack overflow, CPU/out-of-time, or any other `Throwable`), the same cleanup is delegated to `clearExceptionResult`, and that method is a no-op unless the `allowTvmOsaka` hard fork parameter is enabled: [2](#0-1) 

Note in particular the explicit `OutOfTimeException` flow that is thrown deliberately when block generation timing forces `contractResult.OUT_OF_TIME`: [3](#0-2) 

If `allowTvmOsaka()` is not yet activated on the network (i.e. the fix/committee proposal has not been switched on), any `LogInfo` entries accumulated in `ProgramResult` prior to the exception (e.g., from internal calls executed and merged into the result before the outer exception fired) remain in `result.getLogInfoList()` even though the overall transaction is subsequently marked `FAILED`/`OUT_OF_TIME`.

These un-cleared logs then flow unconditionally into the persisted `TransactionInfo`, regardless of the `code.FAILED` result already set two lines earlier: [4](#0-3) 

From there they propagate to the event-subscription pipeline (`BlockEventGet.parseLogs`, `TransactionLogTriggerCapsule`) and to JSON-RPC/gRPC transaction receipts consumed by wallets and SDKs, exactly mirroring the Phoenix SDK's failure to check `is_err` before processing inner-instruction logs: [5](#0-4) [6](#0-5) 

By contrast, the correct/intended invariant is enforced elsewhere in `ProgramResult.merge()`, which only merges logs from a sub-call if that sub-call neither threw nor reverted: [7](#0-6) 

The exception-path gap in `VMActuator` breaks this same invariant for the top-level (outer) execution result whenever the flag is inactive.

### Impact Explanation
Consumers of transaction events (indexers, wallets, exchanges, monitoring/DoS-detection systems built on the event plugin or JSON-RPC `eth_getTransactionReceipt`/`logs`) can observe log/event data attached to a transaction whose on-chain result is `FAILED`/`OUT_OF_TIME`. This is the same class of impact called out in the Phoenix report: inaccurate log/event processing that can mislead automated systems (e.g., an exchange crediting a deposit event, or an off-chain accounting system reacting to a contract event) for a transaction that never actually succeeded, and can be leveraged to cause downstream denial-of-service/incorrect-state conditions in systems that trust these events.

### Likelihood Explanation
Exploitability depends entirely on network configuration: this only manifests while `allowTvmOsaka` is not enabled. If the flag is already active on the target chain, this specific gap is closed system-wide. Because `clearExceptionResult` was clearly added as a targeted (Osaka-gated) fix for exactly this scenario, it strongly suggests the underlying bug (uncleared logs on exception paths) was a real, previously-unpatched issue that is only now conditionally remediated — meaning any deployment/chain that has not activated `allowTvmOsaka` remains exposed. An attacker (unprivileged) simply needs a contract call structured to accumulate log entries via internal calls and then force the containing execution to hit `JVMStackOverFlowException`, `OutOfTimeException`, or any other uncaught `Throwable` at the top level.

### Recommendation
Remove the `allowTvmOsaka()` gate from `clearExceptionResult` (or otherwise unconditionally clear `deleteAccounts`/`logInfoList`/internal transactions on all exception paths in `VMActuator.execute`), matching the unconditional clearing already performed in the normal revert/exception branch at lines 234-238. Alternatively/additionally, enforce a final check before persisting `TransactionInfo` logs in `TransactionUtil.buildTransactionInfoInstance` that discards `programResult.getLogInfoList()` whenever `builder.getResult()` is not `SUCESS`.

### Proof of Concept
1. On a network where `allowTvmOsaka` is not active, deploy a contract `A` that internally calls contract `B`.
2. `B` emits a `LOG` event and returns normally (so its result is merged into `A`'s `ProgramResult` per `ProgramResult.merge()` at [7](#0-6) ).
3. After the call to `B` returns, `A`'s remaining code path triggers deep recursion (stack overflow) or is deliberately crafted/timed to exceed the CPU time budget for the transaction (`OutOfTimeException`), causing the top-level execution to exit via one of the exception branches in `VMActuator.execute` at [8](#0-7) .
4. Because `clearExceptionResult` no-ops without `allowTvmOsaka`, `B`'s emitted log survives in `result.getLogInfoList()`.
5. `TransactionUtil.buildTransactionInfoInstance` marks the transaction `FAILED` but still appends the surviving log to `TransactionInfo.log`, from which it is served via `eth_getTransactionReceipt`/log filters and event-plugin triggers as if it were a valid, successful event.

  private List<ContractTrigger> parseLogs(Protocol.Transaction tx,
                                          Protocol.TransactionInfo txInfo) {
    String originAddress = StringUtil
        .encode58Check(TransactionCapsule.getOwner(tx.getRawData().getContract(0)));

    List<Protocol.TransactionInfo.Log> logs = txInfo.getLogList();
    List<ContractTrigger> list = new LinkedList<>();
    if (logs.isEmpty()) {
      return list;
    }

    Map<String, String> addrMap = new HashMap<>();
    Map<String, SmartContractOuterClass.SmartContract.ABI> abiMap = new HashMap<>();
    parseLogs(logs, originAddress, addrMap, abiMap);

    int index = 1;
    for (Protocol.TransactionInfo.Log log : logs) {

      byte[] contractAddress = TransactionTrace
          .convertToTronAddress(log.getAddress().toByteArray());
      String strContractAddress =
          ArrayUtils.isEmpty(contractAddress) ? "" : StringUtil.encode58Check(contractAddress);
      SmartContractOuterClass.SmartContract.ABI abi = abiMap.get(strContractAddress);
      ContractTrigger event = new ContractTrigger();
      String creatorAddr = addrMap.get(strContractAddress);
      String txId = Hex.toHexString(txInfo.getId().toByteArray());
      event.setUniqueId(txId + "_" + index);
      event.setTransactionId(txId);
      event.setContractAddress(strContractAddress);
      event.setOriginAddress(originAddress);
      event.setCallerAddress("");
      event.setCreatorAddress(StringUtils.isEmpty(creatorAddr) ? "" : creatorAddr);
      event.setBlockNumber(txInfo.getBlockNumber());
      event.setTimeStamp(txInfo.getBlockTimeStamp());
      event.setLogInfo(buildLogInfo(log));
      event.setAbi(abi);

      list.add(event);
      index++;
    }

    return list;
  }
