### Title
Background delete thread panics on filesystem error, converting resource exhaustion into an availability crash - (File: accounts-db/src/utils.rs)

### Summary
`move_and_async_delete_path` spawns a background thread that calls `panic!()` if `dirs::remove_dir_all(&path_delete)` returns an `Err` [1](#0-0) . This function is invoked during normal shrink/clean/snapshot-recycling operations reachable from ordinary account activity via `runtime/src/snapshot_utils.rs` and `ledger/src/bank_forks_utils.rs`, so any filesystem error surfaced mid-delete (disk-full, I/O error, permission/NFS staleness, or copy-on-write filesystem ENOSPC-on-delete) turns into an unhandled panic in that thread rather than a logged, recoverable failure.

### Finding Description
`move_and_async_delete_path` renames a path to be deleted and spawns a `solDeletePath` thread that runs `dirs::remove_dir_all(&path_delete)`; on any `Err` it calls `panic!("Failed to async delete '{}': {err}", ...)` [2](#0-1) . This is called from `move_and_async_delete_path_contents`, which is used by account-path cleanup/recreation flows, and from snapshot/bank-forks cleanup call sites (`runtime/src/snapshot_utils.rs`, `ledger/src/bank_forks_utils.rs`). An attacker who can cheaply generate large volumes of paid account writes (large data, many accounts, frequent rewrite/resize/close cycles) can drive real disk usage on the accounts/snapshot filesystem toward capacity, increasing the probability that a concurrent `remove_dir_all` in the background thread hits `ENOSPC`/I/O errors — this is a real, filesystem-dependent effect: many filesystems (especially copy-on-write ones such as ZFS/btrfs) require allocating new metadata/journal blocks even to *delete* files, so deletions can fail under `ENOSPC` despite only removing data. On such an error, no graceful handling exists; the thread panics immediately.

Whether this crashes the whole validator process versus only terminating the background thread depends on the process-wide panic behavior (i.e., whether a custom panic hook aborts the process on any thread panic, or whether the build uses `panic = "abort"`). I was unable to locate any global panic hook or `panic = "abort"` profile setting configured for the validator binary in this repository within the time available — the `set_hook` usages found are limited to `metrics/src/metrics.rs` (unrelated to process abort semantics) and `solana-test-validator.rs`. This is an important gap: if no such hook/config exists, a thread panic in `solDeletePath` would, by default, only kill that single background thread and be reported via `thread::spawn`'s `JoinHandle` (which is never joined here since `.spawn(...).expect(...)` discards the handle), meaning the panic could silently terminate the delete thread without crashing the process at all — leaving the `path_delete` directory permanently un-cleaned and still marked "in progress" in `IN_PROGRESS_DELETES`, which is a resource-leak/stall issue rather than a validator crash. I could not conclusively verify which behavior applies to the deployed validator binary.

### Impact Explanation
If a global abort-on-panic hook is active for the validator process, this bug allows an attacker to induce a full validator crash purely through disk-pressure caused by their own paid account writes, which is a legitimate availability-impacting escalation of the referenced resource-exhaustion issue (cheap storage-cost asymmetry → node crash). If no such hook exists, the practical effect is instead a stuck/leaked cleanup thread and permanently orphaned `_to_be_deleted` directory consuming disk space, which is still a disproportionate-resource-cost/availability degradation, though less severe than a full crash. Either way, the root cause — turning a recoverable I/O error into an unhandled `panic!()` instead of logging and retrying/recovering — is a defect in `move_and_async_delete_path` that violates graceful-error-handling expectations for a component reachable from adversary-controlled account write volume.

### Likelihood Explanation
Reaching this code path requires no privileged access: an unprivileged user can already, per the referenced scope, cheaply create/resize/rewrite accounts to grow on-disk storage usage and trigger shrink/clean cycles that call `move_and_async_delete_path`. Actually forcing `remove_dir_all` to fail requires driving the target filesystem close to genuine full-disk conditions or triggering another OS-level I/O error, which is filesystem- and environment-dependent (more reliable on COW filesystems like ZFS/btrfs where deletes can require free space; less reliable on ext4 where deletes are close to space-neutral). This makes the trigger condition plausible but non-deterministic and environment-sensitive, and the ultimate severity (thread death vs. process abort) hinges on unverified process-wide panic-handling configuration.

### Recommendation
Replace the `panic!()` in the spawned thread with error logging (e.g., `error!`) and clean removal from `IN_PROGRESS_DELETES`, optionally with a bounded retry, so that a transient or persistent filesystem error during background deletion cannot escalate into a thread abort or process crash; additionally consider proactively checking available disk space before spawning large batch deletes and surfacing a metric/alert instead of terminating.
