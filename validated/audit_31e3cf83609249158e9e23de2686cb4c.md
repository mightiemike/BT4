### Title
Unbounded growth of per-shop session-id array in `RedisSessionStorage` enables DoS of the OAuth/session-storage path - (File: `packages/apps/session-storage/shopify-app-session-storage-redis/src/redis.ts`)

### Summary
`RedisSessionStorage` tracks every session id belonging to a shop inside a single JSON array stored under the `shop` key. This array is only ever appended to on `storeSession`/`addKeyToShopList`, and entries are removed only when `deleteSession` is explicitly called for that exact id. Because non-embedded apps mint a brand-new random session id (`crypto.randomUUID()`) on every OAuth login rather than reusing a deterministic id, a single unprivileged actor who repeatedly authenticates against the app (a completely normal, permission-less action) can grow this array without bound, since old ids are never garbage-collected or expired proactively.

### Finding Description
`addKeyToShopList` reads the array for `shop`, and if the new `idKey` isn't already present, pushes it and re-serializes/re-stores the whole array: [1](#0-0) 

Every read/mutation of that per-shop array is `O(n)` (`Array.includes`, `Array.indexOf`, plus `JSON.parse`/`JSON.stringify` of the whole payload) and is called on the hot path of `storeSession`/`deleteSession`: [2](#0-1) 

`findSessionsByShop` also iterates the full id array, issuing one Redis `GET` per stored id: [3](#0-2) 

For non-embedded apps, each OAuth login generates a fresh, non-deterministic online session id (`crypto.randomUUID()`), unlike embedded apps which reuse a deterministic `shop_userId` id that naturally de-duplicates via the `includes` check: [4](#0-3) 

There is no code path in this repository that proactively prunes expired session ids from the per-shop array — removal only happens via an explicit `deleteSession(id)` call for that specific id, which the app must invoke itself; there is no automatic cleanup tied to `expires`. As a result, a single merchant/customer repeatedly going through the OAuth flow (e.g., reloading/re-authenticating a non-embedded app) will keep appending new ids to the shared per-shop array forever, mirroring the "unbounded array growth via permission-less repeated actions" bug class from the original report (there, malicious NFT deposits grew an array that could never be pruned because the removal path was blocked; here, ordinary repeated logins grow an array that is never proactively pruned).

### Impact Explanation
As the array for a shop grows, every subsequent `storeSession`, `deleteSession`, and `findSessionsByShop` call for that shop becomes progressively slower (linear scan + full JSON re-serialization of an ever-larger payload), and the underlying Redis value size increases without bound. Because `storeSession`/`deleteSession` sit directly in the OAuth callback and session-lifecycle path, this degrades or eventually can stall session storage operations for that shop, i.e., a DoS of the app's auth/session-storage handling for the affected shop. Other shops' data isn't directly affected, but this is a legitimate resource-exhaustion vector caused entirely by an unprivileged actor.

### Likelihood Explanation
This does not require a malicious contract or exploit — it is triggered by an unprivileged, single actor's completely normal use of the app (repeated login/OAuth flows on a non-embedded app), so likelihood of at least gradual, unintentional growth is high; deliberate abuse by an attacker scripting repeated OAuth flows to accelerate the growth is straightforward and requires no special privileges.

### Recommendation
- Use a Redis Set (`SADD`/`SREM`/`SMEMBERS`) or a Sorted Set keyed by expiry instead of a JSON array under a single key, so membership checks/removals are O(1)/O(log n) and the value doesn't need full re-serialization on every mutation.
- Proactively expire/prune ids whose `expires` timestamp has passed (e.g., lazily during `addKeyToShopList`/`findSessionsByShop`, or via a Redis TTL on a per-id marker).
- Consider capping the number of tracked online sessions per shop, or reusing a deterministic id for non-embedded online sessions where feasible.

### Proof of Concept
1. Deploy a non-embedded app configured with `RedisSessionStorage`.
2. As a single merchant/customer, repeatedly complete the OAuth online-token flow (e.g., script "install/login" against `/auth` -> `/auth/callback`) many times in a loop.
3. Each iteration calls `createSession`, which for non-embedded apps generates a new `crypto.randomUUID()` id, then `storeSession` -> `addKeyToShopList` appends this id to the shop's array in Redis.
4. Observe the `shop` key's JSON array value in Redis growing linearly with each login and never shrinking (no id is ever deleted unless the app explicitly calls `deleteSession` for that specific id).
5. Measure increasing latency of subsequent `storeSession`/`deleteSession`/`findSessionsByShop` calls for that shop as the array grows, demonstrating degraded/DoS'd session-storage performance for that shop's auth path.

  public async loadSession(id: string): Promise<Session | undefined> {
    await this.ready;

    let rawResult: any = await this.client.get(id);

    if (!rawResult) return undefined;
    rawResult = JSON.parse(rawResult);

    return Session.fromPropertyArray(rawResult, true);
  }

  public async deleteSession(id: string): Promise<boolean> {
    await this.ready;
    const session = await this.loadSession(id);
    if (session) {
      await this.removeKeyFromShopList(session.shop, id);
      await this.client.del(id);
    }
    return true;
  }

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    await this.ready;

    const idKeysArrayString = await this.client.get(shop);
    if (!idKeysArrayString) return [];

    const idKeysArray = JSON.parse(idKeysArrayString);
    const results: Session[] = [];
    for (const idKey of idKeysArray) {
      const rawResult = await this.client.get(idKey, false);
      if (!rawResult) continue;

      const session = Session.fromPropertyArray(JSON.parse(rawResult), true);
      results.push(session);
    }

    return results;
  }

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
