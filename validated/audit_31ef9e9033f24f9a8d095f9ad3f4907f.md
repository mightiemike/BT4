### Title
Unhandled `new URL()` Exception in `sanitizeHost` Can Crash/500 Unauthenticated Auth Handlers - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates the `host` query parameter using only a base64-charset regex before decoding it and passing the decoded bytes directly into `new URL()` with no `try/catch`. Since base64 decoding (`atob`) can produce arbitrary binary content, including forbidden host code points, this can cause `new URL()` to throw an uncaught `TypeError`. This mirrors the reported bug class: an unvalidated string-conversion function that throws on malformed input, invoked in a code path reachable by anonymous/unauthenticated requests, with no error handling to gracefully degrade.

### Finding Description
`sanitizeHost` only checks that the `host` value is base64-formatted text via `base64regex.test(host)`: [1](#0-0) 

It then unconditionally decodes it and constructs a `URL` object: [2](#0-1) 

`decodeHost` is a thin wrapper around `atob`, which can decode to any sequence of bytes, including forbidden host code points (NUL, TAB, LF, CR, space, `#`, `%`, `/`, `:`, `<`, `>`, `?`, `@`, `[`, `\`, `]`, `^`, `|`): [3](#0-2) 

Per the WHATWG URL spec, if such a code point appears in the host portion of the string passed to `new URL()`, the constructor throws a `TypeError`. Because line 58 is not wrapped in a `try/catch`, this exception propagates straight out of `sanitizeHost`, uncaught.

`sanitizeHost` is called directly from multiple unauthenticated, request-authentication entry points, with no additional validation or error handling around the call: [4](#0-3) [5](#0-4) 

`validateShopAndHostParams` is invoked from the `authStrategyFactory`'s OAuth/auth-code-flow handling (`ensureInstalledOnShop`), which is executed for any document request lacking a session token header — i.e., fully anonymous traffic hitting the app's authenticated admin route: [6](#0-5) [7](#0-6) 

The Express template's `redirect-to-auth.ts` has the identical pattern, called from the `ensureInstalledOnShop` middleware chain reachable by any anonymous request to `/`, `?embedded=1&host=...`.

### Impact Explanation
An attacker who sends any request to an unauthenticated app entry point (e.g., the app root/auth path) with a crafted `host` query parameter that is valid base64 but decodes to a string with a forbidden URL host code point will trigger an unhandled `TypeError` from `new URL()`. This is a Denial-of-Service against the request-authentication handler: the exception is not caught anywhere along the call path shown, so instead of returning a controlled 4xx response (as the surrounding code intends for invalid `host`/`shop` values), the request throws and the error propagates to the top of the framework's error handling (or, in less defensive runtimes/middleware, could surface as an unhandled exception/rejection). This is directly analogous to the `MustNewDecFromString` panic in the source report: an unvalidated conversion of attacker-supplied string data throws instead of returning a handled error, and it sits on a request path that unauthenticated third parties can reach at will, repeatedly, to degrade or disrupt the authentication flow.

### Likelihood Explanation
Likelihood is moderate. The `base64regex` check only constrains character set, not decoded content, so it is straightforward for an attacker to construct base64 strings that decode to byte sequences containing forbidden host code points (e.g., NUL, `#`, `%`, `/`, `@`, `[`, `]`). No authentication, session, or prior state is required — this is reachable by a single anonymous HTTP GET with a query string, which is the same entry point used to boot the OAuth flow for embedded apps.

### Recommendation
Wrap the `new URL()` construction inside `sanitizeHost` in a `try/catch`, treating a decode/parse failure the same as any other invalid host (return `null` or throw `InvalidHostError` consistently with `throwOnInvalid`), for example:

```ts
export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;
    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      try {
        const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
        // ... existing regex checks using hostname
      } catch (_error) {
        sanitizedHost = null;
      }
    }
    if (!sanitizedHost && throwOnInvalid) {
      throw new InvalidHostError('Received invalid host argument');
    }
    return sanitizedHost;
  };
}
```

### Proof of Concept
1. Choose a byte sequence containing a forbidden host code point, e.g. the string `"a#b"` (contains `#`).
2. Base64-encode it: `Buffer.from('a#b').toString('base64')` → `YSNi` (passes `base64regex`).
3. Send a request to an app's unauthenticated admin entry route with this value, e.g.:
   `GET /?embedded=1&host=YSNi`
4. `sanitizeHost` decodes `YSNi` back to `a#b` and calls `new URL('https://a#b')`. Depending on the exact byte sequence chosen (some forbidden code points like `#` are treated as a fragment separator rather than throwing — an attacker would need a code point that WHATWG URL treats as an outright parse failure, such as embedding a raw space, `\u0000`, or unescaped `%`, e.g. base64 for `"a b"` → `YSBi`, or for a literal `%` → `YSVi`), producing an uncaught `TypeError: Invalid URL` inside `sanitizeHost`.
5. Because the call sites (`validateShopAndHostParams`, `redirectToAuth`, etc.) do not wrap this call in `try/catch`, the exception propagates out of the handler instead of the intended "Invalid host" 4xx response.

Note: exact confirmation of which specific byte value throws under the current JS `URL` implementation would require running the code (dynamic verification), which is outside the scope of this static review; the code-path analysis (unchecked decode → unchecked `URL` construction → no surrounding try/catch on any caller) is confirmed from source.
