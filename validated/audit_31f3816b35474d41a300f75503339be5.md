### Title
`ExecutePayload` charges UEA gas fees for EVM execution attempts that fail signature/authorization verification without ever mutating chain state - ([File: x/uexecutor/keeper/msg_execute_payload.go])

### Summary
`ExecutePayload` (the direct, non-cached message path, distinct from the CacheContext-wrapped `ExecutePayloadV2`) executes the UEA call outside a `CacheContext`, then unconditionally calls `DeductGasFeesFromReceipt` "regardless of success/failure" per the code comment, before checking `execErr`.

### Finding Description [1](#0-0) 

```go
// Step 3: Execute payload through UEA
receipt, execErr := k.CallUEAExecutePayload(sdkCtx, evmFrom, ueaAddr, universalPayload, verificationDataVal)

// Step 4: Deduct gas fees regardless of success/failure.
// If deduction fails, return error so the entire Cosmos tx rolls back (including EVM state).
if feeErr := k.DeductGasFeesFromReceipt(ctx, sdkCtx, ueaAddr, receipt, universalPayload); feeErr != nil {
    return fmt.Errorf("gas fee deduction failed: %w", feeErr)
}

if execErr != nil {
    return execErr
}
```

This directly mirrors the audited bug class: a resource ("Limited uses" in the Andromeda report, a fund balance here) is consumed by a check/attempt path regardless of whether that attempt actually produced a useful/authorized outcome. Here, `CallUEAExecutePayload` is executed directly against `sdkCtx` (not a `CacheContext`), so any EVM-level state changes from a *reverted* UEA call (e.g. gas consumed internally by the UEA contract before it reverts on bad `verificationData`, or any other execErr path that still produces `receipt.GasUsed > 0`) are billed via `DeductGasFeesFromReceipt` to the owner's UEA balance before `execErr` is even inspected.

This is architecturally inconsistent with the sibling function `ExecutePayloadV2` in the same package, which explicitly wraps both the call and the fee deduction in a `sdkCtx.CacheContext()` specifically "to close the free-execution gap" and roll back the EVM state atomically with the fee outcome. `ExecutePayload` (used by `MsgExecutePayload`, the primary gasless entrypoint per `app/txpolicy/gasless.go`) — the one actually reachable by unprivileged users — lacks this protection.

Per the module's own documentation, the `Signer` of `MsgExecutePayload` is intentionally decoupled from the UEA `Owner` (contract-only binding model), meaning **any unprivileged third party can submit a `MsgExecutePayload` for someone else's UEA**. If the underlying `CallUEAExecutePayload`/EVM call can consume gas and still return `execErr != nil` (revert) with a non-zero `receipt.GasUsed`, `DeductGasFeesFromReceipt` will burn real `upc` from the victim UEA's balance for a payload execution attempt that produced zero useful output, exactly analogous to consuming a "Limited use" for a permission check that never actually authorized anything.

### Impact Explanation
If reachable (see uncertainty below), this allows an unprivileged attacker to drain a victim UEA's native `upc` balance by repeatedly submitting `MsgExecutePayload` messages that intentionally revert late in EVM execution (after consuming gas) — a griefing/fund-drain vector requiring no gas cost to the attacker (the message type is on the gasless allowlist) while imposing real, unauthorized fund loss on the victim.

### Likelihood Explanation
Medium-to-low confidence on exploitability: I was not able to fully verify from the available index whether `CallUEAExecutePayload`'s underlying EVM call path can produce `execErr != nil` together with `receipt.GasUsed > 0` for an attacker-controlled failure (vs. only Go-level errors with a nil receipt, which `DeductGasFeesFromReceipt` explicitly no-ops on). The documented invariant ("No state changes survive a failed signature check") applies to the specific signature-check revert case, but `ExecutePayload`'s comment ("Deduct gas fees regardless of success/failure") reads as intentional design for legitimate partial-execution billing, not necessarily a bug — this needs runtime/EVM-semantics verification that isn't visible from indexed sources alone.

### Recommendation
Wrap `CallUEAExecutePayload` and `DeductGasFeesFromReceipt` in `ExecutePayload` (the `MsgExecutePayload` path) in a `sdkCtx.CacheContext()`, matching `ExecutePayloadV2`'s pattern, so that fee deduction and EVM state changes commit or roll back atomically, and confirm whether `execErr != nil` paths can ever produce billable `GasUsed`.

### Proof of Concept
Not constructible from static analysis alone — requires confirming, via `pchaind` local devnet, whether a UEA `executeUniversalTx` revert path (e.g., valid `verificationData` recovery but payload call reverting inside the target contract) yields `receipt.GasUsed > 0` alongside `execErr != nil` from `CallUEAExecutePayload`. If confirmed, PoC is: attacker submits `MsgExecutePayload` with `UniversalAccountId.Owner` = victim, `Signer` = attacker's own funded account, and a payload crafted to revert after consuming gas; repeat to drain victim UEA balance.
