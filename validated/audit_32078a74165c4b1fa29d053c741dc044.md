Confirmed: the vulnerability exists as described.

### Title
Event-V2-to-V1 translation derives `EventKey`/`sequence_number` from read-time "latest" state instead of commit-version state, corrupting the indexer's translated event/proof binding - (File: `storage/indexer/src/event_v2_translator.rs`)

### Summary
`EventV2TranslationEngine::get_state_value_bytes_for_resource` and `get_state_value_bytes_for_object_group_resource` both fetch the relevant resource (e.g. `TokenStore`, `Collections`, `FixedSupply`/`UnlimitedSupply`, `Token`) via `self.main_db_reader.latest_state_checkpoint_view()` [1](#0-0) [2](#0-1) . This is the *current/latest* state, not a snapshot pinned to the version of the transaction whose V2 event is being translated. Every token/coin translator (`TokenWithdrawTranslator`, `MintTokenTranslator`, `TokenMutationTranslator`, `BurnTranslator`, `CreateCollectionTranslator`, `OfferTranslator`, `ClaimTranslator`, etc.) uses this method to read a resource's embedded `EventHandle` (`key()` and `count()`), and derives the translated `ContractEventV1`'s `EventKey` and `sequence_number` from those fields, e.g. [3](#0-2) .

### Finding Description
`EventHandle.count()` (the legacy V1 "next sequence number" field baked into the resource) changes every time a new V1-style event fires on that handle. Because the translator reads whatever `count()` happens to be in the *latest* checkpoint state view at indexing time — not the state as of the version of the transaction that emitted the V2 event being translated — the `default` sequence number fed to `get_next_sequence_number` can be stale or advanced relative to what a deterministic, commit-time computation would have produced [4](#0-3) . If the internal `event_sequence_number_cache`/`EventSequenceNumberSchema` entry for that key hasn't been seeded yet (indexer restart, backfill run, cold cache), the translator falls back on `default` derived from this read-time snapshot, so replaying the same V2 event at two different indexing times (or on two nodes with different sync/backfill timing) can yield two different `ContractEventV1` sequence numbers for the same logical event. This breaks the review's core invariant that "event key/sequence derivation must be a pure function of state at commit version," since it is instead a function of whatever state happens to be current when the batch is (re)processed.

The corrupted `(key, sequence_number)` pair is what gets persisted into `EventByKeySchema`, `EventByVersionSchema`, and `TranslatedV1EventSchema` [5](#0-4) , and it is exactly what `get_events_by_event_key` later returns to callers and asserts consistency against via `ensure!(seq == v0.sequence_number(), ...)` [6](#0-5) . Since this indexer-produced sequence position is not tied to the actual VM/committed-state-derived value at the transaction's own version, an attacker who mutates the relevant resource (e.g., additional token transfers bumping `TokenStore.withdraw_events.count()`) between the time transaction T commits and the time the indexer/backfill actually processes T can cause the indexer to record a different sequence number for T's translated event than would result from a deterministic, same-version computation.

### Impact Explanation
This affects `storage/indexer` (the internal/local indexer used to serve V1-style event queries for legacy V2-emitting Move modules such as `0x3::token`, `0x4::token`, coin events, etc.), not the core consensus-critical accumulator/JMT/transaction-output proof paths, and not the actual on-chain `ContractEventsRoot`. The translated `ContractEventV1` is a derived artifact used only for legacy API compatibility/event lookups by key; it does not affect the state root, event root, or any accumulator proof that consensus or light clients verify. The practical impact is: indexer nodes can diverge from one another (or from a hypothetical "correct" replay) in what sequence number they assign to a translated event, and backfilled/restarted indexers can produce different results than continuously-running ones for the same underlying transaction — a reproducibility/consistency bug in indexer output rather than a corruption of consensus-authenticated ledger state or proof material.

### Likelihood Explanation
Likely to manifest in ordinary operation whenever the indexer cache is cold (node restart, index rebuild, backfill of a version range) and further transactions mutating the same resource's event-handle counter occur before/around indexing — no privileged access is required, just normal transaction activity by any account, which matches the "unprivileged input" scope requirement.

### Recommendation
`get_state_value_bytes_for_resource`/`get_state_value_bytes_for_object_group_resource` should read state as of the *version being processed* (e.g. via `main_db_reader.state_view_at_version(version)` or an equivalent versioned state view) rather than `latest_state_checkpoint_view()`, and `translate_event_v2_to_v1` should be threaded with the transaction's version so the resource lookup and hence the derived `EventHandle`/count is pinned to that version, making translation a pure function of commit-time state.

### Proof of Concept
1. Submit a transaction T at version V that emits a `TokenWithdraw` V2 event for `TokenStore` at address A, where `TokenStore.withdraw_events.count()` at version V is N.
2. Before the indexer processes T (e.g., during backfill after a fresh indexer bootstrap with empty `event_sequence_number_cache`/`EventSequenceNumberSchema` for that key), submit additional transactions that trigger more withdraw events for the same `TokenStore`, advancing `count()` to N+k in the latest state.
3. When the indexer eventually processes T, `TokenWithdrawTranslator::translate_event_v2_to_v1` calls `engine.get_state_value_bytes_for_resource(A, TokenStore)`, which reads the *current* `TokenStore` (count = N+k) rather than the value at version V (count = N) [3](#0-2) .
4. Compare against a control run where the indexer processes transactions in order from genesis with a warm/consistent cache (so `get_next_sequence_number` returns N via the cached path) — the two runs assign different `sequence_number` values to the same event, demonstrating that the translation is not a deterministic function of the transaction's own commit-time state.
