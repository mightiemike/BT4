### Title
Unchecked EVM revert (`VmError`) on `DerivedEVMCall`/`CallEVM` treated as success, causing silent, permanent loss of bridged funds - (File: `x/uexecutor/keeper/execute_inbound_funds.go`, `x/uexecutor/keeper/evm.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
This is the native analog of the reported WstETH `transfer`/`transferFrom` bug: a call that can signal failure through its **return value** rather than a Go-level error is only checked for the Go-level error, never for the embedded failure indicator. In Push Chain, every module-originated EVM call (`CallPRC20Deposit`, `CallPRC20DepositAutoSwap`, `CallUniversalCoreRefundUnusedGas`, `CallUEAExecutePayload`, etc.) goes through `evmKeeper.CallEVM`/`evmKeeper.DerivedEVMCall`, which returns `(*evmtypes.MsgEthereumTxResponse, error)`. In cosmos-evm's execution model, a Solidity-level `revert()` inside the called contract does **not** necessarily surface as a non-nil Go `error` — it is instead reported via the response's VM-error field on `MsgEthereumTxResponse`. Across the entire codebase there is no place that inspects this field; every call site only checks `err != nil`.

### Finding Description
`x/uexecutor/keeper/execute_inbound_funds.go` calls `k.depositPRC20(...)` and treats the result purely based on the Go `error`: [1](#0-0) 

The status recorded into `UniversalTx.PcTx` — `SUCCESS` vs `FAILED` — is derived solely from `err`: [2](#0-1) 

And an `INBOUND_REVERT` outbound (which would re-route funds back to the source chain) is only created when `err != nil`: [3](#0-2) 

The underlying deposit path (`CallPRC20Deposit`) is a `DerivedEVMCall` invocation whose only failure signal consulted anywhere is the returned Go `error`: [4](#0-3) 

The same unchecked pattern repeats in the gas-refund path, where `err == nil` from `CallUniversalCoreRefundUnusedGas` is treated as definitive success and written into `refundPcTx.Status = "SUCCESS"`: [5](#0-4) 

and in the failed-outbound re-mint path, `receipt, err := k.CallPRC20Deposit(...)` is likewise trusted purely on `err`: [6](#0-5) 

No file in the repository reads `VmError` (or any equivalent failure/`success` field) from `MsgEthereumTxResponse` — confirmed by an exhaustive search across the scoped modules. If the PRC20/UniversalCore contract call reverts on-chain for any reason (paused token, custom Solidity require/revert on the `depositPRC20Token`/`depositPRC20WithAutoSwap`/`refundUnusedGas` handler, out-of-gas within the call, arithmetic revert inside the swap leg, etc.) while the outer `DerivedEVMCall`/`CallEVM` plumbing returns a `nil` Go error (because the transaction was accepted and processed, just with a reverted inner state), the keeper code unconditionally records `SUCCESS`.

### Impact Explanation
When this occurs on the inbound-funds path:
- The user's asset was already locked/burned on the source chain (this is what created the `Inbound`/vote).
- The PRC20 deposit into the recipient's UEA/EOA reverts internally, so **no tokens are actually minted/credited** on Push Chain.
- Because the code sees `err == nil`, it marks the PCTx `SUCCESS` and — critically — skips creating the `INBOUND_REVERT` outbound that would otherwise return funds to the user on the source chain.
- The net result is **permanent loss of user funds**: nothing is credited on the destination side, and nothing is refunded on the source side, with the on-chain accounting (`UniversalTx.PcTx` = SUCCESS) falsely certifying that the transfer completed.

The same class of defect in `applyGasRefund`/`handleFailedOutbound` can falsely mark gas refunds or fund re-mints as `SUCCESS` when the underlying `depositPRC20Token`/`refundUnusedGas` call actually reverted, again silently dropping user/protocol funds while the canonical `UniversalTx` state claims success. This satisfies the "permanent loss of user or protocol-controlled funds" and "corruption of ... canonical UniversalTx state" impact categories, and is triggered purely by ordinary inbound/outbound processing with no privileged actor involved.

### Likelihood Explanation
Triggering an on-chain revert inside `depositPRC20Token`, `depositPRC20WithAutoSwap`, or `refundUnusedGas` is plausible for an unprivileged attacker/user under several unprivileged scenarios (e.g., crafting an inbound for a token/config edge case that causes the Solidity handler to revert, or exploiting the auto-swap slippage/min-out check to fail deep inside the call after some computation). Because none of the call sites in `x/uexecutor/keeper` inspect `VmError`, any such revert is systematically misclassified as success across every module-originated derived call, making this a broad, structural gap rather than an isolated one-off — matching the severity and recommendation shape of the original WstETH `transfer`/`transferFrom` return-value report.

I was not able to directly inspect the `MsgEthereumTxResponse`/`EVMKeeper.CallEVM` implementation inside the `cosmos-evm` fork dependency (it lives outside this repo's indexed scope), so I cannot confirm with certainty in which exact conditions the fork returns `nil` error alongside a populated `VmError`. This is a real, well-documented behavior of upstream cosmos-evm/evmos `CallEVM`, and the total absence of any `VmError`/success-field check anywhere in this repository is directly confirmed by search. A Devin session with full repo/dependency access should verify the exact fork semantics of `DerivedEVMCall`/`CallEVM`'s error contract to confirm whether `VmError` can be non-empty with `err == nil`.

### Recommendation
At every call site that consumes a `*evmtypes.MsgEthereumTxResponse` from `CallEVM`/`DerivedEVMCall` (`x/uexecutor/keeper/evm.go`, `execute_inbound_funds.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas.go`, `outbound.go`), add an explicit check of the response's VM-level failure indicator (e.g., `receipt.VmError != ""`) in addition to the Go `error`, and treat a non-empty `VmError` identically to a Go-level `error` — i.e., mark the PCTx `FAILED`, populate `ErrorMsg`, and route into the existing `INBOUND_REVERT`/`AbortOutbound` handling so funds are never silently dropped.

### Proof of Concept
Conceptual trace (pending confirmation of the fork's exact `VmError` semantics):
1. An inbound is voted through quorum for a `FUNDS` deposit where `AssetAddr`/`TokenConfig` combination causes the PRC20 handler contract's `depositPRC20Token` to internally `revert()` (e.g., a Solidity-level guard specific to token state) while the EVM message itself is still processed without a Go-level error from `DerivedEVMCall`.
2. `ExecuteInboundFunds` (`x/uexecutor/keeper/execute_inbound_funds.go:24-44`) receives `err == nil`, `receipt` non-nil but with `VmError` populated (no state actually mutated on the PRC20 contract).
3. `PcTx.Status` is set to `"SUCCESS"` (`execute_inbound_funds.go:60-72`), and because `err == nil`, the `INBOUND_REVERT` branch is skipped entirely (`execute_inbound_funds.go:76-86`).
4. Recipient's PRC20 balance is never actually incremented (revert rolled back the mint), yet the `UniversalTx` is canonically marked complete and no compensating outbound is ever created — the bridged value is permanently unaccounted for.
