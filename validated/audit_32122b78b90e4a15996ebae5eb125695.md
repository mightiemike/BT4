### Title
Gas fee under-collection from divide-before-multiply truncation of `baseFee` in `CalculateGasCost` - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`x/uexecutor/keeper/fees.go`'s `CalculateGasCost` truncates the fractional (sub-`upc`) portion of `baseFee` to a whole integer *before* multiplying by `gasUsed`, instead of multiplying first and truncating only the final result. This mirrors the Canto `update_market` bug class: a legitimate fixed-point value is divided down before being scaled by a large volume factor, discarding real precision instead of only discarding an unavoidable final remainder.

### Finding Description
`CalculateGasCost` receives `baseFee` as a `cosmossdk.io/math.LegacyDec`, whose internal representation is `actual_value * 1e18`: [1](#0-0) 

The code performs `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` to "unwrap" the Dec into a whole-`upc` integer *before* any multiplication by `gasUsed`: [2](#0-1) 

The inline comment asserts this is safe because "the base fee is always a whole number of upc -- no fractional upc exists," i.e. it assumes `GetBaseFee` (implemented by the external `FeeMarketKeeper`, `cosmos/evm/x/feemarket`) never returns a fractional Dec value: [3](#0-2) 

This assumption is the crux of the bug: standard EIP-1559-style base-fee markets update `baseFee` every block via a percentage adjustment (`baseFee * (1 ± Δ/target/8)`), which is Dec arithmetic and essentially never produces a value that is an exact whole multiple of `1e18` internally. If `baseFee` genuinely carries a fractional component (as fee markets normally do), then:

- `baseFeeBig.Div(..., 1e18)` truncates that fractional/sub-`upc` price-per-gas *before* it is multiplied by `gasUsed` in `gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig)`.
- Correct order would be `gasCost = (baseFeeRaw * gasUsed) / 1e18`, i.e. multiply first, then truncate once at the end — exactly the fix pattern recommended in the Canto report.
- Dividing first discards up to `(1e18-1)/1e18` of a whole `upc` *per unit of gas*, and this loss is amplified by `gasUsed` instead of being bounded to under 1 `upc` total.
- In the degenerate but plausible case where the fractional/sub-`upc` gas price is `< 1 upc` per gas unit (common when base fee is low), `effectiveGasPrice` truncates to `0`, making `gasCost.Sign() <= 0`, and `DeductGasFeesFromReceipt` returns `nil` without deducting or burning any fee at all: [4](#0-3) 

This function is invoked from ordinary, unprivileged, user-reachable universal payload/inbound execution paths (`execute_payload.go`, `msg_execute_payload.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas_and_payload.go`), meaning any user submitting a `UniversalPayload` that triggers real EVM execution can benefit from systematically under-billed (or fully zeroed) gas cost accounting.

### Impact Explanation
This corrupts gas fee accounting in a user-reachable execution path: real EVM gas is consumed (paid for by the protocol/module account executing the call), but the amount recovered from the recipient via `DeductAndBurnFees` is silently reduced, and can become exactly zero when the truncated gas price rounds to `0 upc`. This matches the in-scope impact category "corruption of ... gas fee accounting, refund accounting" — ordinary users get free or systematically discounted EVM execution at protocol expense, without any privileged actor involved.

### Likelihood Explanation
Likelihood depends entirely on whether the `cosmos/evm` feemarket module's `GetBaseFee` can actually return a Dec value with a non-trivial fractional part under normal AIMD/EIP-1559 fee adjustments (very likely, since fee-market computations use percentage-based multiplications), and on typical gas-price magnitude relative to 1 `upc`. **I was not able to fully verify the feemarket module's `BaseFee` computation code in this session** — it lives outside the `x/` custom scope (imported from `cosmos/evm`), so I could not confirm from this repo alone how often/how much fractional truncation actually occurs in practice, or the chain's exact base-denom decimal configuration. This is the main open uncertainty: if the deployed feemarket parameters or gas-price floor keep `baseFee` always landing on exact whole-`upc` multiples in practice, the described precision loss would not manifest, similar to how Canto's own team initially argued the effect was negligible before conceding it could reach up to ~1 unit of loss.

### Recommendation
Reorder the arithmetic to multiply before dividing, matching the Canto fix pattern:
```go
// gasCost = (baseFeeRaw * gasUsed) / 1e18, truncating only once at the end
gasCostRaw := new(big.Int).Mul(baseFee.BigInt(), gasUsedBig)
gasCost := new(big.Int).Div(gasCostRaw, big.NewInt(1e18))
```
Remove reliance on the unverified "base fee is always whole" assumption, or explicitly assert/enforce that invariant in the feemarket configuration if it must be relied upon.

### Proof of Concept
Given `baseFee = 1.9999999999999999e0` upc as a `LegacyDec` (i.e., internal raw value `1_999999999999999900`, not a multiple of `1e18`) and `gasUsed = 1_000_000`:
- Current code: `baseFeeBig.Div(_, 1e18) = 1`, `gasCost = 1 * 1_000_000 = 1_000_000` upc.
- Correct order: `gasCost = (1_999999999999999900 * 1_000_000) / 1e18 ≈ 1_999_999` upc.
- Difference: ~999,999 `upc` under-charged in a single call — a loss proportional to `gasUsed`, not bounded to a few wei as in typical rounding.

If `baseFee < 1` upc (raw value `< 1e18`), `effectiveGasPrice` truncates to `0`, and `gasCost.Sign() <= 0` causes `DeductGasFeesFromReceipt` to skip fee collection entirely regardless of `gasUsed`, per [5](#0-4) .
