### Title
`ExchangeProcessor.exchangeToSupply` performs unchecked signed-long arithmetic on attacker-controlled `sellTokenQuant`, allowing overflow-driven corruption of exchange balances - (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Finding Description
`ExchangeProcessor.exchangeToSupply` computes `long newBalance = balance + quant;` with no overflow check [1](#0-0) , unlike `SafeExchangeProcessor.exchangeToSupply`, which uses `StrictMathWrapper.addExact` and throws `ArithmeticException` on overflow [2](#0-1) .

Whether the guarded `SafeExchangeProcessor` or the unguarded `ExchangeProcessor` is used depends entirely on `hardenedCalc`, which comes from `AbstractExchangeActuator.allowHarden()` reading `dynamicStore.allowHardenExchangeCalculation()` [3](#0-2) . When this dynamic parameter is off (its default/unset state unless a committee proposal enables it), `ExchangeCapsule.transaction` selects the plain `new ExchangeProcessor(supply, useStrictMath)` instead of `SafeExchangeProcessor.INSTANCE`, and skips the post-transaction negative-balance check entirely because that check is gated by `hardenedCalc && (...)` [4](#0-3) .

Critically, the same `allowHarden()` flag also governs the overflow-safety of the *validation-layer* guards inside `AbstractExchangeActuator.addExact`/`subtractExact`, which fall back to plain unchecked `x + y` / `x - y` when harden is disabled [5](#0-4) . `ExchangeTransactionActuator.doValidate()` relies on these same helpers to check the exchange balance limit (`tokenBalance = addExact(tokenBalance, tokenQuant); if (tokenBalance > balanceLimit) throw ...`) and the sender's sufficient-balance check (`accountCapsule.getBalance() < addExact(tokenQuant, calcFee())`) [6](#0-5) . With harden disabled, both of these guards are themselves subject to signed-long wraparound: an attacker who picks `tokenQuant` close to `Long.MAX_VALUE` can make `tokenBalance + tokenQuant` and `tokenQuant + fee` wrap to a negative value, which trivially satisfies `<= balanceLimit` and `>= (small real balance)`, bypassing both the exchange-cap and balance-sufficiency checks without owning anywhere near that many tokens/TRX.

Once validation is bypassed, `execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, allowStrictMath, allowHarden())`, which (with harden off) reaches the vulnerable `ExchangeProcessor.exchangeToSupply(balance, quant)`. `balance + quant` overflows/wraps, producing an arbitrary `newBalance` (potentially zero, negative, or near zero), which corrupts the `1.0 + quant/newBalance` ratio used in `Maths.pow`, yielding an unconstrained `issuedSupply`/`out` (NaN, Infinity, or a wildly wrong magnitude after the `(long)` cast). This `out` is then propagated through `exchangeFromSupply` as the counterpart `buyTokenQuant`, and both `firstTokenBalance`/`secondTokenBalance` are updated with this corrupted amount with no negativity check (since `hardenedCalc` is false), permanently desynchronizing `ExchangeCapsule` balances from real user deposits held in `AccountCapsule`.

### Impact Explanation
This breaks the exchange accounting invariant: `ExchangeCapsule.firstTokenBalance`/`secondTokenBalance` no longer reflect actual escrowed user funds. An attacker can potentially credit themselves a large/corrupted counterpart-token amount via `accountCapsule.addAssetAmountV2`/`setBalance(addExact(...))` in `execute()` [7](#0-6) , while driving the exchange pool balances negative or into an inconsistent state, which can freeze/lock other users' funds in that exchange pool (their subsequent trades will compute against a corrupted `balance`/`supply` baseline) and enables value duplication/theft.

### Likelihood Explanation
The bug is reachable by any unprivileged user broadcasting a normal `ExchangeTransactionContract` — no special privilege is required. The only precondition is that `allowHardenExchangeCalculation` is not enabled on the chain (its default/unset state), which is a chain-configuration state, not an attacker action; under that default state, the entire chain of overflow guards (validation-layer `addExact`/`subtractExact` and `ExchangeProcessor.exchangeToSupply`) is unchecked plain arithmetic, making the attack straightforwardly repeatable with a single crafted large `sellTokenQuant`.

### Recommendation
Make overflow-safe arithmetic (the `SafeExchangeProcessor`/`StrictMathWrapper.addExact/subtractExact` path and the negative-balance post-check in `ExchangeCapsule.transaction`) unconditional rather than gated behind `allowHarden()`/`hardenedCalc`, so that `exchangeToSupply`'s `balance + quant` and all validation-layer sum/difference checks in `AbstractExchangeActuator` and `ExchangeTransactionActuator` always reject overflow instead of silently wrapping, regardless of the dynamic parameter's state.

### Proof of Concept
```java
// framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java

@Test
public void testUnguardedOverflowWraparound() {
  ExchangeProcessor processor = new ExchangeProcessor(1_000_000_000_000_000_000L, false);
  long sellBalance = Long.MAX_VALUE - 10L;   // near-overflow pool balance
  long buyBalance = 1_000_000_000L;
  long sellQuant = 100L;                     // balance + quant overflows signed long

  // Unsafe path: no exception, silently produces a corrupted/garbage result
  long result = processor.exchange(sellBalance, buyBalance, sellQuant);

  // Compare against SafeExchangeProcessor which must reject the same overflow
  assertThrows(ArithmeticException.class, () ->
      SafeExchangeProcessor.INSTANCE.exchange(sellBalance, buyBalance, sellQuant));

  // Demonstrates divergence: unsafe path returns a value while safe path throws,
  // proving exchangeToSupply lacks overflow protection when hardenedCalc/allowHarden is false.
  Assert.assertNotNull(result);
}
```
Additional integration test: drive `ExchangeTransactionActuator` with `dynamicStore.allowHardenExchangeCalculation() == false` (default), an `ExchangeCapsule` with small real `firstTokenBalance`, and a crafted `ExchangeTransactionContract.quant` near `Long.MAX_VALUE`; assert that `doValidate()` does **not** throw despite the attacker's real account balance/asset amount being far smaller than `tokenQuant`, confirming the overflow bypass of `addExact`/`subtractExact` guard checks in `ExchangeTransactionActuator`.
