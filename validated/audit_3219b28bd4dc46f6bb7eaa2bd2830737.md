### Title
DoS via unbounded O(cycles × votes) reward iteration in `MortgageService.computeReward`/`getOldReward` billed at fixed fee - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.withdrawReward`/`queryReward` call `computeReward(beginCycle, endCycle, accountCapsule)`, which for cycles before `getNewRewardAlgorithmEffectiveCycle()` falls back to `getOldReward`, iterating every uncollected maintenance cycle and, within each cycle, every voted witness, each requiring two `DelegationStore` lookups that reconstruct Hex string keys. [1](#0-0)  This is reachable from `WithdrawBalanceActuator.execute` (broadcast `WithdrawBalanceContract`) and from TVM's `WITHDRAWREWARD` opcode via `VoteRewardUtil.withdrawReward`, both of which are unprivileged, ordinary-account operations. [2](#0-1) [3](#0-2) 

### Finding Description
`computeReward(beginCycle, endCycle, accountCapsule)` in `MortgageService` splits the cycle range at `newAlgorithmCycle` and for the portion before that cycle calls `getOldReward(beginCycle, oldEndCycle, srAddresses)`. [4](#0-3) 

`getOldReward` has two code paths gated by `dynamicPropertiesStore.allowOldRewardOpt()`:
- If the "old reward opt" is enabled, it delegates to `RewardViCalService.getNewRewardAlgorithmReward`, which computes reward in O(votes) using precomputed VI (value-per-vote) deltas — this is efficient.
- If the flag is *not* enabled, it falls back to the legacy loop: `for (long cycle = begin; cycle < end; cycle++) { reward += computeReward(cycle, votes); }`, i.e. O(cycles × votes), and each `computeReward(cycle, votes)` call performs, per witness voted for, a `delegationStore.getReward(cycle, srAddress)` and `delegationStore.getWitnessVote(cycle, srAddress)` lookup, both of which build a Hex-encoded string key (`cycle + "-" + Hex.toHexString(address) + "-reward"/"-vote"`) on every call. [5](#0-4) [6](#0-5) [7](#0-6) 

This is invoked from `MortgageService.withdrawReward(address)` on every `WithdrawBalanceContract` and every `VoteWitnessContract` (`countVoteAccount` calls `mortgageService.withdrawReward(ownerAddress)` before applying new votes), and from `WithdrawRewardProcessor`/`VoteRewardUtil.withdrawReward` for the TVM `WITHDRAWREWARD` opcode. [8](#0-7) [9](#0-8) [10](#0-9) 

The billed cost for the underlying operations is fixed: `WithdrawBalanceActuator` charges a static `calcFee()` base fee, and the TVM `WITHDRAWREWARD` opcode is billed a flat `EnergyCost.WITHDRAW_REWARD` energy amount regardless of how many cycles/votes are actually processed. There is no per-cycle or per-vote metering in either path.

The severity of this issue, however, depends entirely on whether `allowOldRewardOpt` is active on the target chain. This flag is a committee-controlled dynamic property (settable through a `ProposalCreateActuator`/governance proposal, per `ProposalUtil.java` and `ProposalService.java`), not a compile-time constant. I was unable to fully determine from the available index whether `allowOldRewardOpt` is enabled by default on current TRON mainnet, or whether it was activated years ago and thus this legacy O(cycles×votes) path is now dead code in practice (in which case the DoS surface described here would not be exploitable on production chains that have already flipped the flag). I was also unable to confirm from the index whether there is a hard cap on the number of witnesses an account can vote for (e.g., a `MAX_VOTE_NUMBER` constant referenced in `VoteWitnessProcessor`/`VoteWitnessActuator`), which bounds the "votes" factor in the O(cycles×votes) product.

### Impact Explanation
If `allowOldRewardOpt` is disabled (or an account has unwithdrawn history predating the optimization's activation on a network where it was enabled later), an attacker who votes for the maximum number of witnesses, then withholds withdrawal for a long span of maintenance cycles, can force a single `WithdrawBalanceContract`/`WITHDRAWREWARD` transaction to perform a number of Hex-string key builds and store lookups proportional to `cycles × votes`, while paying only the fixed base fee/flat energy cost. This matches TRON's "DoS via the TRON protocol implementation" impact class: node CPU work for a single transaction is not bounded by the fee/energy charged, and many attacker-funded accounts broadcasting this pattern in the same block could disproportionately slow block processing/re-execution.

### Likelihood Explanation
Exploitability is conditional and not confirmed against current mainnet state:
- Preconditions require an account with old-algorithm, unwithdrawn reward history spanning many cycles before `newRewardAlgorithmEffectiveCycle`, and — critically — for `allowOldRewardOpt` to be off for those cycles (or the account's history to predate whatever activation happened).
- On a long-lived mainnet where the optimization proposal was already approved and applied, existing unwithdrawn balances would generally already have been "settled" by any subsequent withdrawal or by the VI-accumulation optimization during maintenance (`accumulateWitnessVi` in `MaintenanceManager.doMaintenance`), which changes the reward accounting model going forward. Whether legacy unsettled cycles from before optimization remain reachable and reprocessed via the slow path could not be verified from indexed code alone.
- Cost to the attacker is capped by whatever per-witness-vote limit exists (unconfirmed here) and by the number of maintenance cycles they can accumulate, which is bounded by real wall-clock time (cycles occur on a fixed schedule), limiting how fast an attacker can build up a large "cycles" factor.

### Recommendation
- Ensure `allowOldRewardOpt` (or an equivalent always-on optimization) is unconditionally active for all pre-existing/legacy cycles, removing the O(cycles) fallback loop entirely, or bound the maximum number of cycles processed per call and require multiple transactions to fully settle very old debts.
- Meter the cost of `withdrawReward`/`queryReward` proportionally to the actual number of `(cycle, witness)` lookups performed (dynamic energy/bandwidth charge) rather than a flat fee, for both the actuator and TVM opcode paths.
- Cache/avoid repeated Hex-string key construction in `DelegationStore` hot loops, and add a periodic sweep (e.g., during maintenance) that pre-aggregates or forcibly settles very old unclaimed cycles to prevent unbounded backlog accumulation.

### Proof of Concept
A concrete PoC would require confirming, on the target chain, that `allowOldRewardOpt` is disabled (or that a legacy pre-optimization cycle backlog exists) and that no cap prevents an account from accumulating a large `cycles × votes` product. Since I could not verify these preconditions with the available index (I could not confirm `allowOldRewardOpt`'s default/current value nor the exact vote-count cap in `VoteWitnessProcessor`/`VoteWitnessActuator`), a fully reproducible request-level PoC cannot be certified from this analysis alone. The unit-test scaffolding to build such a benchmark already exists in the repo (`framework/src/test/java/org/tron/core/services/ComputeRewardTest.java` and `framework/src/test/java/org/tron/core/services/DelegationServiceTest.java`), which directly exercise `MortgageService.computeReward`/`withdrawReward` against a real `DelegationStore`, and could be extended with `dynamicPropertiesStore.saveAllowOldRewardOpt(0)`, thousands of synthetic cycles via `delegationStore.setWitnessVote`/`addReward`, and many voted witnesses on `accountCapsule`, then timing `mortgageService.withdrawReward(address)` against the fixed fee it would be billed in production.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
