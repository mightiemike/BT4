### Title
OAuth Callback `shop` Parameter Pollution — HMAC-Validated Value Differs From the Value Used for Token Exchange and Session Creation - (File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts)

### Summary
In the OAuth callback handler, the `shop` query parameter is read twice using two different extraction methods that resolve duplicate keys differently. `URLSearchParams.get('shop')` returns the **first** occurrence of a repeated `shop` parameter, while `Object.fromEntries(query.entries())` (used to build the object that is HMAC-verified) resolves to the **last** occurrence. An attacker who controls the callback query string can therefore make the app's HMAC check validate one `shop` value while a different, attacker-chosen `shop` value is actually used for the access-token exchange and for the resulting session — the same class of bug as the MEME404 issue, where one field (`nftId`) was checked for consistency but a related field (`isFungible`) used elsewhere in the logic was not cross-validated against it.

### Finding Description
`callback()` in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts` builds the `URLSearchParams` from the raw request URL and immediately extracts `shop` with `.get()`: [1](#0-0) 

It later builds `authQuery`, the object that is actually HMAC-verified, using `Object.fromEntries(query.entries())`: [2](#0-1) 

Then, after the HMAC check passes, it re-derives `cleanShop` directly from the `URLSearchParams` object again with `.get('shop')`, and this value is used to build the outbound token-exchange request and the session: [3](#0-2) 

- `URLSearchParams.get(key)` always returns the **first** value for a repeated key.
- `Object.fromEntries(iterable)` iterates entries in order and lets **later** entries overwrite earlier ones, so it captures the **last** value for a repeated key.

`validateHmac`/`normalizeQuery` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` only guards against duplicate/array-valued security parameters when the input is a raw `URLSearchParams` instance **and** the signator is `appProxy`; for the `admin` signator (used by the OAuth callback) there is no rejection of duplicate `shop`/`hmac`/`state`/`timestamp` values at all: [4](#0-3) 

Because `authQuery` passed into `validQuery`/`validateHmac` is already a plain object (built via `Object.fromEntries`) by the time it reaches `normalizeQuery`, that function's `instanceof URLSearchParams` branch is skipped entirely, so the "last-value-wins" collapse from `Object.fromEntries` is silently accepted with no duplicate-key check for the admin flow.

The net effect: if the callback query string contains `shop` twice (`shop=<attacker-value>&...&shop=<value-that-matches-the-real-HMAC>`), the recomputed local HMAC (calculated from `authQuery`, which resolves to the second/last `shop`) matches Shopify's real HMAC, so `validQuery` returns `true`. But the `shop` value actually used to build `cleanShop` — and therefore the URL used for the `/admin/oauth/access_token` POST and the `shop` field written into the created `Session` — is the **first** occurrence, i.e., the attacker-controlled one.

### Impact Explanation
This breaks the core invariant of HMAC-based request authentication: "the data that was verified is the data that gets used." Concretely:
- The `shop` value used to construct the outbound token-exchange URL (`https://${cleanShop}/admin/oauth/access_token`) can be attacker-controlled independently of what was actually signed by Shopify.
- The `shop` value written into the resulting `Session` object (via `createSession`) can likewise diverge from the value the HMAC verified, corrupting session/shop bookkeeping in the session storage layer for whichever shop record gets created.
- More generally, this is a parameter-pollution class flaw in the request-authentication handler for OAuth callbacks — exactly the kind of "same-key-different-value inconsistency between validation and usage" flagged in the MEME404 report (`isFungible` differing for the same `nftId`).

Full compromise (stealing another shop's access token) is bounded by the fact that the `/admin/oauth/access_token` endpoint on the attacker-chosen shop domain will independently reject a `code` that wasn't issued for it, so the most immediately exploitable outcome is corruption of the `shop` field associated with a session/token-exchange attempt and violation of the authentication integrity guarantee, rather than a directly demonstrated cross-tenant token theft.

### Likelihood Explanation
Exploitation requires the attacker to control (or get a victim to submit) a callback URL containing a duplicated `shop` parameter while preserving a valid `state` cookie and a genuine Shopify-issued `hmac`/`code`. Because the OAuth callback is a plain GET endpoint whose query string an attacker fully controls when driving their own browser (e.g., during their own app-install flow), and because `state`/`hmac` are unaffected by adding an extra `shop=` parameter (they still validate against the "last" value), this precondition is realistically achievable by a single, otherwise-unprivileged actor performing/manipulating their own OAuth flow.

### Recommendation
Normalize duplicate query parameters consistently and reject (not silently collapse) duplicates of security-critical fields for **both** signators, not just `appProxy`:
- In `normalizeQuery` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts`), apply the `APP_PROXY_SINGLE_VALUE_PARAMS`-style duplicate rejection regardless of signator, and perform this check on the raw `URLSearchParams` **before** any other code (such as `Object.fromEntries`) has a chance to silently collapse duplicates.
- In `callback()` (`packages/apps/shopify-api/lib/auth/oauth/oauth.ts`), derive `shop` (and any other security-relevant field) from the same normalized/validated query object used for HMAC verification, rather than re-reading it independently via `query.get(...)`.

### Proof of Concept
1. Attacker starts a normal OAuth flow for a shop they control (`attacker-shop.myshopify.com`), obtaining the signed `STATE_COOKIE_NAME` cookie and letting Shopify redirect to the callback URL:
   `GET /auth/callback?code=abc123&shop=attacker-shop.myshopify.com&state=<state>&hmac=<valid-hmac-for-this-query>&timestamp=...`
2. Before this request reaches the app (e.g., via a proxy, browser history replay, or a link the attacker constructs and sends to their own session), the attacker inserts a second `shop` parameter **before** the original one, keeping the original value last so the HMAC (computed on the `Object.fromEntries`-collapsed, i.e. last-value, query) still matches:
   `GET /auth/callback?code=abc123&shop=malicious-shop.myshopify.com&state=<state>&hmac=<same-valid-hmac>&timestamp=...&shop=attacker-shop.myshopify.com`
3. `validQuery`/`validateHmac` computes the local HMAC from `Object.fromEntries(query.entries())`, whose `shop` resolves to `attacker-shop.myshopify.com` (last value) — matching the real HMAC, so validation **passes**.
4. `cleanShop = sanitizeShop(config)(query.get('shop')!, true)` resolves to `malicious-shop.myshopify.com` (first value) — the attacker-controlled value — and this is what is used to build the token-exchange request URL and the resulting `Session.shop` field, diverging from the value that was actually authenticated.

I was not able to execute this against a live app instance to confirm run-time behavior (no terminal/execution access in this mode); the analysis above is based on static tracing of `oauth.ts` and `hmac-validator.ts`. Since token-exchange success ultimately depends on Shopify's own `/admin/oauth/access_token` endpoint enforcing that `code` matches the target shop, full impact validation (e.g., confirming whether a partially-successful/failed exchange still leaves an inconsistent `Session` record persisted) would require dynamic testing that is outside the scope of this read-only code review.

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
