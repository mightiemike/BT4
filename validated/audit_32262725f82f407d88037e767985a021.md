**Mathematical analysis of the claimed attack:**

The alt_bn128 twist curve E'(Fq2) has order `h·r` where `h = 2` (cofactor) and `r` is the large prime order of G2. A 2-torsion point `T` satisfies `2·T = 0` and `r·T = T ≠ 0` (since `r` is odd). For the Ate pairing, the final exponentiation raises the Miller loop result to `(p¹² − 1)/r`. Because `r` is odd and `p¹² − 1` is divisible by 2, this exponent is even, so the final exponentiation clears the 2-torsion. Consequently `e(P, T) = 1` in `Gt` for **any** `P ∈ G1` when `T` is a 2-torsion point outside G2.

**Exploitability constraint:** The false-positive (`Ok(true)`) is unconditional only when the attacker controls **all** G2 inputs. In Groth16-style verifiers the verification key's G2 points (β, γ, δ) are fixed, so the attacker controls only `B`. Substituting a 2-torsion `B` makes `e(A, B) = 1`, reducing the multi-pairing product to `e(−α, β)·e(−L, γ)·e(−C, δ)`, which equals 1 only if the verification key itself is degenerate — not a general bypass for Groth16. However, for simpler single-pairing gates (`e(P, Q) = 1` where both P and Q come from the caller), the attacker submits any P alongside a 2-torsion Q and the check trivially passes.

**Comparison with BLS12-381:** The BLS12-381 pairing host function in the same codebase explicitly calls `blst_p1_affine_in_g1` and `blst_p2_affine_in_g2` before proceeding, returning an error code for non-subgroup points. The alt_bn128 path has no equivalent guard. [5](#0-4) 

**Verdict:**

The missing subgroup check is a real code-level defect and a clear specification violation. The pairing result is provably wrong (returns `true`) for any caller who supplies a 2-torsion G2 point. Whether this translates to fund loss or unauthorized authorization depends entirely on how the affected contract uses the boolean result. For contracts that gate actions on a single pairing equality with attacker-supplied G2 inputs, the bypass is direct. For Groth16-style verifiers with fixed verification-key G2 points, the bypass does not generalize.

Because the impact is scoped to contract-level ZK verification logic (not nearcore consensus, trie, or fund accounting directly), and because the most dangerous scenario (full false-positive bypass) requires the attacker to control all G2 inputs — a condition that holds for some but not all deployed contracts — the finding is a **real cryptographic flaw in the nearcore host function** but its severity is bounded by the specific contract's input model.

### Title
Missing G2 Subgroup Membership Check in `decode_g2` Allows False-Positive Pairing Results — (`runtime/near-vm-runner/src/logic/alt_bn128.rs`)

### Summary
`decode_g2` accepts any point on the alt_bn128 twist curve E'(Fq2) without verifying it lies in the prime-order G2 subgroup. A 2-torsion point outside G2 passes the on-curve check, enters `bn::pairing_batch`, and — because the Ate pairing's final exponentiation clears the cofactor — always produces `Gt::one()`, making `pairing_check` return `Ok(true)` regardless of the G1 input.

### Finding Description
`bn::AffineG2::new(x, y)` in `zeropool-bn` verifies only the curve equation `y² = x³ + b/(i+9)` over Fq2. It does not multiply by the cofactor `h = 2` to test subgroup membership (`h·P == 0`). After `decode_g2` succeeds, the point is passed directly to `bn::pairing_batch`. The Ate pairing's final exponentiation exponent `(p¹² − 1)/r` is even (since `r` is odd and `p¹² − 1` is even), so it annihilates any 2-torsion component, yielding `Gt::one()` for any 2-torsion G2 input paired with any G1 point.

### Impact Explanation
Any contract using `alt_bn128_pairing_check` as a ZK proof gate where the caller supplies G2 bytes can receive `true` from the host function for an invalid proof. For single-pairing gates with attacker-controlled G2, the bypass is unconditional. This constitutes a cryptographic flaw in the nearcore runtime host function, violating the documented invariant and potentially enabling unauthorized contract actions gated on ZK proof validity.

### Likelihood Explanation
The attack requires only a standard transaction calling a contract that uses `alt_bn128_pairing_check` with caller-supplied G2 inputs. No privileged access, validator role, or key compromise is needed. Constructing a 2-torsion point on E'(Fq2) is straightforward (take any generator and multiply by `r`).

### Recommendation
After `bn::AffineG2::new(x, y)` succeeds, perform a subgroup membership check by verifying `r · P == 0` (i.e., scalar-multiply the decoded point by the group order and check for the identity). Return `InvalidInput` if the check fails, matching the behavior already implemented for BLS12-381 (`blst_p2_affine_in_g2`).

fn decode_g2(raw: &[u8; 2 * POINT_SIZE]) -> Result<bn::G2, InvalidInput> {
    let (x, y) = stdx::split_array(raw);
    let x = decode_fq2(x)?;
    let y = decode_fq2(y)?;
    if x.is_zero() && y.is_zero() {
        Ok(bn::G2::zero())
    } else {
        bn::AffineG2::new(x, y)
            .map_err(|_err| InvalidInput::new("invalid g2", raw))
            .map(bn::G2::from)
    }
}
