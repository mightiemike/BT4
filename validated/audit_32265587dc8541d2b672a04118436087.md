### Title
`VoteTssKeyProcess` never validates that the caller-supplied `processId` matches the current active TSS process, allowing a stale/superseded key-generation round to finalize as `CurrentTssKey` - (File: `x/utss/keeper/msg_vote_tss_key_process.go`)

### Summary
The C4 report's root cause is a two-step lifecycle where the "old" pending state (`_pendingOwner`) is only cleared on the *first* invocation of the finalizing function, not re-validated against the *second*, so a stale value survives to be replayed later and grants privilege after the entity believed control had been renounced. The structural analog in this repo is Push Chain's TSS key-rotation state machine: `x/utss` maintains a single `CurrentTssProcess` (like a "committed" pointer) plus a `processId` parameter supplied on every vote, but `VoteTssKeyProcess` never checks that the `processId` argument actually matches `CurrentTssProcess.Id` before voting/finalizing.

### Finding Description
`InitiateTssKeyProcess` (`x/utss/keeper/initiate_tss_key_process.go:22-58`) can force-expire an existing `CurrentTssProcess` when a new one is started: it sets `existing.ExpiryHeight = currentHeight - 1`, writes it to `ProcessHistory`, marks the associated `TssEvent` `EXPIRED`, and removes the `PendingTssEvents` index — then overwrites `CurrentTssProcess` with a brand-new process/ID/expiry. [1](#0-0) 

`VoteTssKeyProcess` (`x/utss/keeper/msg_vote_tss_key_process.go:14-63`) accepts an explicit `processId` from the message, but instead of loading/validating the process referenced *by that ID*, it fetches `k.CurrentTssProcess.Get(ctx)` (whatever process is currently active) and only checks `sdkCtx.BlockHeight() >= process.ExpiryHeight` against that fetched (current) process's expiry — never comparing `processId == process.Id`: [2](#0-1) 

It then calls `k.VoteOnTssBallot(tmpCtx, universalValidator, processId, tssPubKey, keyId)` using the caller-supplied (potentially stale) `processId`, and on finalization writes `CurrentTssKey`/`TssKeyHistory` and a `TssKey{ProcessId: processId, Participants: process.Participants, ...}` record using the *current* process's participant set metadata even though the actual quorum accumulated under a different (superseded) `processId`'s ballot: [3](#0-2) 

The only defense against duplicate/incorrect finalization is `GetTssKeyByID(ctx, keyId)` ensuring the target `keyId` doesn't already exist — this does not protect against votes tied to a process that has since been force-expired and replaced. Since `TssKeyProcess` state is looked up only by `CurrentTssProcess` (singleton), not by the `processId` argument, in-flight votes for an old process (delayed messages, slow validators, or a process that raced with `InitiateTssKeyProcess`'s force-expiry) can still be recorded against the ballot and, once quorum accumulates, finalize as if it were the process's outcome — even though `CurrentTssProcess` had already moved on to a new round with a new participant/expiry configuration.

### Impact Explanation
If honest validators cast otherwise-valid votes for a `processId` that has already been superseded (e.g. an admin/governance-driven `REFRESH`/`QUORUM_CHANGE`/`KEYGEN` re-initiation races with in-flight votes, or votes arrive after a new process supersedes the old one but before the mempool/vote messages are dropped), `VoteTssKeyProcess` can still finalize the stale round's key into `CurrentTssKey` — the single source of truth used to sign every outbound transaction chain-wide (`x/utss/README.md`). This corrupts the canonical TSS key record with a key/participant set that does not correspond to the currently intended process, directly impacting "TSS coordination" and "wrong TSS event/migration outcome" invariants called out in scope. Because `CurrentTssKey` gates outbound signing across every connected chain, an incorrect finalization here has systemic fund-safety implications (wrong key controlling assets on external chains).

### Likelihood Explanation
Triggering this requires no signature forgery or malicious validator — only honest validators submitting votes whose `processId` no longer matches `CurrentTssProcess` due to timing with `InitiateTssKeyProcess`'s force-expiry path. `InitiateTssKeyProcess` is admin-gated, but the vulnerable path itself is exercised by ordinary, honest `MsgVoteTssKeyProcess` submissions racing with a legitimate re-initiation — this is a plausible operational race rather than a privileged-actor exploit, and the report explicitly requires including this analog under "honest-validator finalization path" and "TSS coordination". However, I was unable to fully verify `VoteOnTssBallot`'s ballot-keying scheme (whether the ballot ID itself already encodes `processId` uniquely, which could still permit finalization to complete against the *wrong* recorded `CurrentTssKey`/`TssKey.ProcessId` state even if the ballot itself is scoped correctly) since the underlying `x/utss/keeper/voting.go` implementation was not retrieved before the tool budget ran out — this should be validated by a background agent.

### Recommendation
In `VoteTssKeyProcess`, look up the `TssKeyProcess` by the supplied `processId` (via `ProcessHistory`/dedicated lookup) rather than trusting whatever `CurrentTssProcess` currently holds, and explicitly reject the vote if `processId != CurrentTssProcess.Id` or if the looked-up process's own status/expiry indicates it was already superseded/force-expired. This mirrors the C4 fix pattern of clearing/validating pending state on every transition, not just the first.

### Proof of Concept
Not independently executable without a live 3+ validator TSS harness; conceptually:
1. Admin calls `MsgInitiateTssKeyProcess` (process A, id=1).
2. Two of three validators vote via `MsgVoteTssKeyProcess(processId=1, ...)` — quorum not yet reached, votes recorded on ballot for process 1.
3. Admin calls `MsgInitiateTssKeyProcess` again before process 1 naturally expires, force-expiring process 1 (`ExpiryHeight = currentHeight-1` in history) and creating process B (id=2) with a new, longer `ExpiryHeight`.
4. A third (honest, but slow) validator submits `MsgVoteTssKeyProcess(processId=1, ...)` — `VoteTssKeyProcess` fetches `CurrentTssProcess` (process B, id=2) and checks `sdkCtx.BlockHeight() >= process(B).ExpiryHeight`, which passes since B's expiry is far in the future, even though process A(id=1) was already expired.
5. The vote finalizes on the process-1 ballot, and `CurrentTssKey` is overwritten with process 1's stale key/participant data, while `TssKeyProcess.ProcessId` metadata mixes fields from both processes.

Confirming the exact ballot-collision mechanics (`VoteOnTssBallot` in `x/utss/keeper/voting.go`, not retrieved) is required to fully validate exploitability before treating this as confirmed; recommend a Devin session with full repo access to trace `VoteOnTssBallot` and `FinalizeTssKeyProcess`.

func (k Keeper) VoteTssKeyProcess(
	ctx context.Context,
	universalValidator sdk.ValAddress,
	tssPubKey, keyId string,
	processId uint64,
) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	process, err := k.CurrentTssProcess.Get(ctx)
	if err != nil {
		return fmt.Errorf("no active TSS process running")
	}

	if sdkCtx.BlockHeight() >= process.ExpiryHeight {
		return fmt.Errorf("TSS process %d has expired", process.Id)
	}

	// Step 1: Ensure the key doesn't already exist
	_, found, err := k.GetTssKeyByID(ctx, keyId)
	if err != nil {
		return errors.Wrap(err, "failed to check existing TSS key")
	}
	if found {
		return fmt.Errorf("tss key with key_id %s already exists", keyId)
	}

	k.logger.Info("tss vote received",
		"process_id", processId,
		"key_id", keyId,
		"validator", universalValidator.String(),
	)

	// Step 2: Vote on the ballot (using a cache context so we don’t mutate state on failure)
	// The entire vote + finalization is wrapped in a single CacheContext so that
	// if any post-finalization step fails, the vote itself is also rolled back.
	tmpCtx, commit := sdkCtx.CacheContext()
	isFinalized, _, err := k.VoteOnTssBallot(tmpCtx, universalValidator, processId, tssPubKey, keyId)
	if err != nil {
		return errors.Wrap(err, "failed to vote on TSS ballot")
	}
