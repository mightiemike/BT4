## Analysis

The reported bug class is: a liquidity-provision call computes counterpart token amounts from the current pool ratio and passes them to an underlying operation with **no slippage tolerance parameter**, so if the pool ratio changes between when the caller commits to the operation and when it actually executes, the operation either reverts (DoS) or executes with terms the caller never agreed to (value extraction).

java-tron's Bancor-style exchange pools have the exact analog in `ExchangeInjectActuator`.

`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum-amount field to bound the computed counterpart amount, unlike its sibling `ExchangeTransactionContract` which explicitly has an `expected` field and enforces it. [1](#0-0) [2](#0-1) 

In `ExchangeInjectActuator.execute()`, `anotherTokenQuant` is derived purely from the pool's current on-chain balances at execution time (`floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` or the symmetric case), and this value is unconditionally deducted from the caller's balance/asset holdings with no upper-bound check: [3](#0-2) 

Compare this to `ExchangeTransactionActuator`, which does validate the computed counterpart amount against a caller-supplied `expected` bound before proceeding: [4](#0-3) 

Any account can create an exchange pool via `ExchangeCreateContract` and become its "creator" (an ordinary, unprivileged role, not an access-controlled admin), and only the creator may call `ExchangeInject` on that pool: [5](#0-4) 

Because injection has no slippage bound, any anonymous third party can broadcast an `ExchangeTransactionContract` trade against the same pool to shift the ratio between the time the creator signs/broadcasts an `ExchangeInject` transaction and the time it is actually included in a block, causing the creator's injection to consume a materially different (larger) amount of the counterpart asset than they intended when they signed the transaction — a front-running/sandwich pattern directly analogous to the reported "expects zero slippage" root cause (missing slippage-tolerance parameter on a liquidity operation).

### Title
Missing slippage-tolerance bound in `ExchangeInjectContract` allows front-running of liquidity injection - (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectContract`/`ExchangeInjectActuator` computes the counterpart token amount to withdraw from the caller purely from the pool's live ratio at execution time, with no caller-supplied minimum/maximum bound field in the protocol message, unlike `ExchangeTransactionContract` which has an `expected` field enforced in `ExchangeTransactionActuator`.

### Finding Description
`ExchangeInjectContract` only defines `owner_address`, `exchange_id`, `token_id`, `quant`; it has no slippage/expected-amount field. In `execute()`, `anotherTokenQuant` is recomputed from `firstTokenBalance`/`secondTokenBalance` at the moment of on-chain execution and then deducted from the caller's balance with no check that it matches what the caller expected when they signed the transaction. Because pool ratios are mutated by any `ExchangeTransactionContract` trade (an unprivileged, anonymous broadcast transaction), a third party can shift the ratio between when the creator signs an inject transaction and when it lands on-chain, changing the effective price of the injection without the actuator ever detecting or rejecting the discrepancy. This mirrors the reported root cause: a liquidity-provisioning call omits a slippage-tolerance parameter that the analogous trade path (`ExchangeTransactionContract`) already has.

### Impact Explanation
The exchange creator can be forced to inject liquidity at a manipulated ratio, receiving a smaller effective share of pool ownership for a larger amount of the counterpart asset than intended — a value-extraction/accounting-corruption risk realized purely via anonymous, unprivileged `ExchangeTransactionContract` broadcasts against the target pool. This falls in the exchange/market math and resource-accounting category explicitly in scope.

### Likelihood Explanation
Requires the attacker to observe a pending `ExchangeInject` transaction (e.g., in the mempool) and race a trade transaction into an earlier block position — a standard front-running technique available to any network participant, with no special privilege needed.

### Recommendation
Add an `expected`/minimum (and optionally maximum) counterpart-amount field to `ExchangeInjectContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` the same way `ExchangeTransactionActuator` enforces `expected`, so injection reverts if the pool ratio at execution time falls outside the caller's tolerated slippage range.

### Proof of Concept
1. Attacker observes a pending `ExchangeInject` transaction from a pool creator targeting exchange `X` for `tokenQuant` of `firstTokenID`.
2. Attacker broadcasts an `ExchangeTransactionContract` against exchange `X` with a lower gas price wait or same-block priority that shifts `firstTokenBalance`/`secondTokenBalance` before the inject transaction executes.
3. When the inject transaction executes, `anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` is computed against the manipulated ratio and deducted from the creator's balance, per [6](#0-5) , with no bound check comparable to the `expected` check present in `ExchangeTransactionActuator` at [4](#0-3) .
