### Title
Unauthenticated batch-prover RPC methods (`setCommitments`, `submitFakeProof`, `prove`, `pauseProving`) allow any network caller to mutate ledger state and force DA submissions signed by the prover's own key - (File: `crates/common/src/rpc/auth.rs`, `crates/batch-prover/src/rpc.rs`)

### Summary
The `Auth` JSON-RPC middleware only requires an API key for three backup-related methods; every other RPC method exposed by a node — including the batch-prover's state-mutating methods `batchProver_setCommitments`, `batchProver_submitFakeProof`, `batchProver_prove`, `batchProver_pauseProving`, and `batchProver_createCircuitInput` — is reachable by any unauthenticated caller who can reach the node's RPC port. This is the same bug class as the reported `PythPriceFeedUpdate` issue: a message/operation that is supposed to be produced only by a privileged internal actor (there: the Oracle thread; here: the operator/internal tooling) is instead accepted from arbitrary external HTTP/JSON-RPC callers because the transport-level authorization boundary does not cover it.

### Finding Description
`crates/common/src/rpc/server.rs` wires every node's RPC server with the same `Auth` middleware: [1](#0-0) 

`Auth::call` only gates methods present in `PROTECTED_METHODS`: [2](#0-1) [3](#0-2) 

`PROTECTED_METHODS` is `["backup_create", "backup_validate", "backup_info"]` only. Every other registered method, including the batch-prover's admin surface, bypasses the API-key check entirely and is served to any caller who can open a connection to the RPC port.

The batch-prover exposes, with no additional guard in the handler implementations themselves:
- `batchProver_setCommitments`, which unconditionally overwrites ledger DB commitment records supplied by the caller (`merkle_root`, `index`, `l2_end_block_number`) with no signature or provenance check tying them to an actual DA-observed `SequencerCommitment`: [4](#0-3) 
- `batchProver_submitFakeProof`, which builds a proof output from whatever commitments are currently in the ledger DB (including ones just injected via `setCommitments`) and sends it to DA using the batch prover's own `da_service` — i.e., signed with the legitimate prover's DA key: [5](#0-4) [6](#0-5) 
- `batchProver_prove` and `batchProver_pauseProving`, which respectively trigger real proving jobs and halt future proving, both without any caller authentication: [7](#0-6) [8](#0-7) 

None of these method names appear in `PROTECTED_METHODS`, so none of them require the `api_key` configured in `RpcConfig`: [9](#0-8) 

### Impact Explanation
This matches the High-severity bucket "an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`". Concretely:
- Any external, unprivileged caller can call `batchProver_setCommitments` to overwrite the batch prover's local view of sequencer commitments (`ledger_db.put_commitment_by_index` / `put_commitment_index_by_l1` / `put_prover_pending_commitment`) with attacker-chosen data, corrupting the state the prover subsequently uses when constructing proofs.
- The same unauthenticated caller can then invoke `batchProver_prove` / `batchProver_submitFakeProof` to make the prover assemble a `BatchProofCircuitOutput` from the corrupted commitment data and submit it to Bitcoin DA using the prover's own signing key — i.e., an attacker with no privileged role can force the honest, key-holding batch prover to publish a DA transaction whose *content* the attacker fully controls (subject to whatever the corrupted ledger data allows).
- `batchProver_pauseProving` lets any caller halt legitimate proving indefinitely, a denial of the prover's core function that is triggered purely by an unauthenticated RPC call.

The severity of the "false proof reaches the light client circuit" scenario in particular depends on whether the light client's ZK verifier (`Vm::verify`) is configured to accept `InnerReceipt::Fake` receipts in the deployment (e.g., RISC0 dev-mode) — I could not confirm from the indexed code whether production verification paths reject `FakeReceipt`s outright, so that specific downstream consequence is not fully verified and may depend on deployment configuration, which per the rules should not be assumed. The state-mutation-without-authentication part, however, is independently confirmed and sufficient on its own to meet the "unauthenticated JSON-RPC call that mutates node state or bypasses Auth" bar.

### Likelihood Explanation
High. No credentials, keys, or special network position are required — only network reachability to the batch-prover's RPC endpoint, which is the same reachability assumption used for the reported Pyth HTTP-`action` endpoint. The methods are permanently registered and reachable unless an operator manually firewalls the RPC port, which is not enforced by the code itself (the `Auth` layer, the only in-process gate, does not cover these methods).

### Recommendation
Add the state-mutating/administrative batch-prover RPC methods (`setCommitments`, `submitFakeProof`, `prove`, `pauseProving`, `createCircuitInput`, `retryProvingJob`, and any equivalent admin methods on other node types) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, or otherwise require the configured `api_key` (or a dedicated admin authentication mechanism) for every RPC method that mutates ledger/prover state, rather than only for the three `backup_*` methods.

### Proof of Concept
1. Start a batch-prover node with default `RpcConfig` (no `api_key` set, or set but irrelevant since these methods aren't gated).
2. From an unauthenticated client with network access to the RPC port, send:
   ```json
   {"jsonrpc":"2.0","id":1,"method":"batchProver_setCommitments","params":[[{"merkleRoot":"0x...","index":999,"l2EndBlockNumber":"0x...","l1Height":"0x..."}]]}
   ```
   This succeeds and overwrites `ledger_db` commitment state — confirmed by `set_commitments` in `crates/batch-prover/src/rpc.rs:345-381`, which performs the writes unconditionally.
3. Follow with:
   ```json
   {"jsonrpc":"2.0","id":2,"method":"batchProver_submitFakeProof","params":[999,999]}
   ```
   This causes the prover to build a proof output from the attacker-supplied commitment and submit it to DA using the prover's own key (`crates/batch-prover/src/rpc.rs:405-533`), all without any authentication challenge from the `Auth` middleware (`crates/common/src/rpc/auth.rs:31-38`), since `batchProver_submitFakeProof` is not in `PROTECTED_METHODS`.

```rust
    async fn set_commitments(
        &self,
        commitments: Vec<SequencerCommitmentRpcParam>,
    ) -> RpcResult<()> {
        for commitment in commitments {
            let l1_height = commitment.l1_height.to::<u64>();
            let commitment = SequencerCommitment {
                merkle_root: commitment.merkle_root,
                index: commitment.index.to::<u32>(),
                l2_end_block_number: commitment.l2_end_block_number.to::<u64>(),
            };

            info!(
                "Overriding sequencer commitment, index={} merkle_root={} l2_end_height={} l1_height={}",
                commitment.index,
                hex::encode(commitment.merkle_root),
                commitment.l2_end_block_number,
                l1_height,
            );

            self.context
                .ledger_db
                .put_commitment_by_index(&commitment)
                .map_err(internal_rpc_error)?;
            // This might cause some duplicate commitment indices appear in l1 -> index table which is ok
            self.context
                .ledger_db
                .put_commitment_index_by_l1(SlotNumber(l1_height), commitment.index)
                .map_err(internal_rpc_error)?;
            self.context
                .ledger_db
                .put_prover_pending_commitment(commitment.index)
                .map_err(internal_rpc_error)?;
        }

        Ok(())
    }
```

```rust
    async fn submit_fake_proof(
        &self,
        index_start: u32,
        index_end: u32,
    ) -> RpcResult<BatchProofResponse> {
        info!(
            "Submitting fake proof for commitment index range [{},{}]",
            index_start, index_end
        );

        let ledger_db = &self.context.ledger_db;

        if index_start > index_end {
            return Err(internal_rpc_error("Invalid index range"));
        }
        // don't allow first commitment index to be called through this rpc as it requires extra handling
        if index_start <= 1 {
            return Err(internal_rpc_error(
                "submitFakeProof rpc supports only index_start > 1",
            ));
        }

        let previous_commitment = ledger_db
            .get_commitment_by_index(index_start - 1)
            .map_err(internal_rpc_error)?
            .ok_or_else(|| internal_rpc_error("Missing previous commitment index"))?;

        let commitments = ledger_db
            .get_commitment_by_range(index_start..=index_end)
            .map_err(internal_rpc_error)?;
        if commitments.len() as u32 != index_end - index_start + 1 {
            return Err(internal_rpc_error(
                "Missing some commitment indices from the range",
            ));
        }

        let last_commitment = commitments.last().expect("Already ensured");
        let last_l2_block = ledger_db
            .get_l2_block_by_number(&L2BlockNumber(last_commitment.l2_end_block_number))
            .map_err(internal_rpc_error)?
            .ok_or_else(|| internal_rpc_error("Not synced up to latest L2 block yet"))?;
```
