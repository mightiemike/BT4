### Title
Unbounded `PendingInbounds.Walk` in inbound-ballot terminal hook lets an unprivileged depositor inflate finalization cost for every future inbound - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
`afterInboundBallotTerminal` locates the `PendingInboundEntry` owning a terminating ballot by doing a full, unbounded `k.PendingInbounds.Walk(ctx, nil, ...)` over the *entire* `PendingInbounds` collection on every single inbound-ballot terminal transition, rather than a keyed lookup. `PendingInbounds` entries are created for free by `RecordInboundVote` for every distinct inbound event/utx_key, and there is no minimum-amount or rate-limiting check gating how many such entries can exist. An unprivileged external-chain user can flood the gateway with many cheap/dust cross-chain deposits, each producing a new `PendingInboundEntry`, growing the walked set and increasing the per-finalization cost paid by every honest validator node processing any `MsgVoteInbound`, degrading throughput chain-wide. This is the direct structural analog of the Boot Finance vesting bug: an attacker-fillable, unbounded collection is later iterated in full by a legitimate finalization/claim path, turning normal usage into a resource-exhaustion vector for everyone, not just the attacker's own entries.

### Finding Description
`RecordInboundVote` (`x/uexecutor/keeper/inbound.go:27-88`) creates a new `PendingInboundEntry` keyed by `utx_key = sha256(source_chain:tx_hash:log_index)` on the *first* vote for any distinct inbound event, with no minimum-amount enforcement anywhere in the vote/inbound path (confirmed by the absence of any `MinAmount`/dust guard in the codebase). Any external-chain sender can create arbitrarily many distinct, cheap inbound transactions on a source chain; honest, non-privileged Universal Validators will observe and vote on each one exactly as designed, each producing its own `PendingInboundEntry`.

When any one of these ballots later reaches a terminal state (`EXPIRED`, `PASSED`, or `REJECTED`), `x/uvalidator`'s ballot machine invokes `BallotHooks.AfterBallotTerminal` → `afterInboundBallotTerminal` (`x/uexecutor/keeper/ballot_hooks.go:72-143`). Because ballot IDs are "one-way canonical digests" and not reversible to a `utx_key`, this function performs:

```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [1](#0-0) 

This scans **every** entry in `PendingInbounds` — not just the one belonging to the terminating ballot — on every terminal transition. The code comment explicitly (and incorrectly, from a security standpoint) assumes the set stays small: *"the pending set is small and transient, and this hook only fires on terminal transitions"* [2](#0-1) . That assumption is an attacker-controllable invariant, not an enforced one: nothing bounds how many concurrent `PendingInboundEntry` records can exist, and each entry can itself carry multiple `InboundVariant`s (further inflating the inner loop) if validators observe slightly different byte encodings for the same event.

This mirrors the Boot Finance `Vesting.sol` bug precisely: in the original bug, `vest()` let anyone push cheap entries into `timelocks[beneficiary]`, and `_claimableAmount()`/`claim()` later iterated the whole unbounded array, causing gas-limit reverts for the beneficiary. Here, `RecordInboundVote` lets any external-chain sender push cheap entries into `PendingInbounds` (a chain-wide, not per-beneficiary, collection), and `afterInboundBallotTerminal` later iterates the whole collection on **every** ballot finalization, driving up per-finalization cost for the whole validator set as the pending set grows.

`MsgVoteInbound` is documented as a **gasless** message type (`app/txpolicy/gasless.go`, referenced in `x/uexecutor/README.md:199-204` [3](#0-2) ), meaning the validator submitting the vote pays no Cosmos-level transaction fee for triggering this walk — there is no economic cost recovery mechanism proportional to the walk's actual computational cost, unlike a metered EVM call.

### Impact Explanation
This is a denial-of-service vector reachable purely by unprivileged, ordinary user action (submitting many low-value/dust source-chain deposits), not by any malicious validator, peer, or privileged actor — it fits the in-scope "denial of service only when it is not network-level and is reachable without privileged control" category. As `PendingInbounds` grows (bounded only by ballot expiry duration and the volume of dust deposits an attacker is willing/able to submit on a source chain, which can be a low-fee or testnet-like chain), every single inbound-ballot finalization — including ones belonging to completely unrelated, legitimate users — pays an ever-increasing linear (and gasless) walk cost. At sufficient scale this degrades block-processing time across all validators, and in the worst case could push per-block processing time high enough to threaten liveness/timeliness of inbound finalization for all users, effectively the same "unclaimable due to unbounded loop" outcome as the original report, but chain-wide instead of per-beneficiary.

### Likelihood Explanation
Feasibility is high: no minimum deposit amount, no cap on concurrent `PendingInboundEntry` records, and no per-attacker rate limit were found in the reviewed code paths (`RecordInboundVote`, `VoteInbound`, `RecordOutboundVote`/pending outbound path shows the analogous "pending set is small" assumption too, in `PendingOutbounds`). The only natural bound is ballot expiry (`BlockHeightExpiry`), which removes entries once all variants reach a terminal state, but an attacker only needs to keep a steady stream of new distinct inbound events flowing in faster than they expire to keep the set large. Producing many distinct source-chain transactions is inexpensive on many supported source chains.

### Recommendation
- Replace the reverse ballot-ID → `utx_key` lookup with a direct secondary index (e.g., a `Map[ballotID]string` from ballot ID to `utx_key`) maintained alongside `RecordInboundVote`, so `afterInboundBallotTerminal` can do an O(1) `Get` instead of a full `Walk`.
- Alternatively/additionally, bound the number of concurrent `PendingInboundEntry` records (or total variants) per source chain / per block, and/or introduce a minimum bridged-amount threshold to raise the cost of flooding the set with dust entries.
- Revisit the "pending set is small and transient" assumption anywhere else it is relied upon in the codebase (e.g., similar full-`Walk` patterns in `PendingOutbounds` handling) and replace with explicit, enforced bounds rather than documentation comments.

### Proof of Concept
1. An external-chain attacker submits N distinct low-value/dust deposit transactions to the source-chain gateway contract (each with a unique `tx_hash`/`log_index`), causing N distinct `utx_key`s.
2. Honest Universal Validators observe and call `MsgVoteInbound` for each, invoking `RecordInboundVote`, which creates N `PendingInboundEntry` records in the `PendingInbounds` collection (`x/uexecutor/keeper/inbound.go:27-88`).
3. As votes accumulate toward quorum/expiry for any one of these ballots (or an unrelated legitimate user's ballot), `AfterBallotTerminal` fires and `afterInboundBallotTerminal` performs `PendingInbounds.Walk` over all N entries to find the one matching the terminating ballot ID (`x/uexecutor/keeper/ballot_hooks.go:86-94`).
4. Repeating step 1 continuously (faster than ballot expiry removes entries) keeps N growing, making every subsequent inbound-ballot finalization — including those for legitimate, unrelated users — progressively more expensive for every validator processing `MsgVoteInbound`, with no gas-fee cost recovery since the message type is gasless.

*Note: I was unable to fully verify the exact production ballot-expiry block window (`expiryAfterBlocks`) used for `INBOUND_TX` ballots, nor the concrete per-block validator processing budget, which would be needed to quantify the precise N required to cause material degradation; these are configuration/parameter values that a background engineering session with full repo access should confirm before treating severity as more than a scoping estimate.*
