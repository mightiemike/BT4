### Title
Any Fatal SnapshotError Halts the Entire AccountsBackgroundService (Flush/Clean/Shrink/Snapshotting), Requiring Validator Restart - (File: runtime/src/accounts_background_service.rs)

### Summary
`AccountsBackgroundService::new` runs a single background loop that handles all snapshot requests and, on the non-snapshot path, performs cache flush, clean, and shrink of `AccountsDb`. When `handle_snapshot_requests` returns any `Err(SnapshotError)`, the loop unconditionally sets `exit` to `true` and `break`s, permanently terminating the service for the life of the process, with no retry, bypass, or fallback path.

### Finding Description
The relevant code is: [1](#0-0) 

`handle_snapshot_requests` can return `Err(SnapshotError)` for a variety of underlying I/O, serialization, or archival failures during snapshot generation/rebuild (`agave_snapshots::error::SnapshotError`, imported at line 17). On any such error, regardless of transient or permanent nature, the service logs "Stopping AccountsBackgroundService! Fatal error..." and does:
```rust
exit.store(true, Ordering::Relaxed);
break;
```
This is the *sole* thread that performs `flush_accounts_cache`, `clean_accounts`, and `shrink_candidate_slots` for the running validator, as seen in the surrounding non-snapshot branch: [2](#0-1) 

There is no code path that: (a) retries a failed snapshot generation, (b) skips just the failing snapshot request while continuing to flush/clean/shrink, or (c) isolates a snapshot-generation error from ongoing accounts-storage maintenance. This mirrors the reported bug-class exactly: a single failure in one code path (there, the OFT messenger; here, snapshot serialization/archival) is allowed to cascade and disable an entire class of otherwise-independent operations (there, canonical token transfer + root bundle propagation; here, all subsequent cache flush/clean/shrink/snapshot generation), with the only "fix" being manual intervention — i.e., restarting the validator process, since `exit` is a process-wide flag.

Additionally, `exit.store(true, ...)` uses the same `Arc<AtomicBool>` that is checked elsewhere in the validator for full shutdown, meaning this single background thread can trigger a full validator exit sequence in response to what may be a transient I/O hiccup (e.g., temporary disk space pressure or filesystem error) during snapshot archiving, not necessarily anything related to consensus safety.

### Impact Explanation
Once the `AccountsBackgroundService` background thread halts (or triggers a full validator exit), AccountsDb no longer has active cache flushing, cleaning, or shrinking. Since these are periodic, unprivileged-operation-agnostic maintenance passes (any user's transactions cause the write cache to grow and dirty stores to accumulate), the accounts write cache and storage will grow unboundedly until either the validator crashes from resource exhaustion or is manually restarted — a stall/DoS-class impact analogous to the reported issue's "stall situation until resolved" and matching the "disproportionate storage and CPU cost" acceptance criterion.

### Likelihood Explanation
Triggering requires a genuine `SnapshotError` during snapshot request handling — this can occur from disk I/O errors, filesystem/serialization edge cases in `serialize_snapshot`/`archive_snapshot_package`, or other unhandled snapshot-generation faults, none of which require any special privilege since snapshotting runs automatically as part of ordinary root-bank processing driven by ordinary transaction activity. However, the ordinary operating conditions (adequate disk, normal filesystem behavior) make this a low-but-nonzero likelihood; it is primarily an environmental-failure scenario rather than one triggerable purely by transaction content.

### Recommendation
Distinguish between snapshot errors that are truly fatal (e.g., internal invariant violations warranting a hard stop) and those that are transient/environmental (I/O errors, temporary disk pressure). For the latter, log and skip the failed snapshot request while continuing to run flush/clean/shrink on the accounts cache/storage, and retry snapshot generation at the next request rather than unconditionally halting the entire background service and forcing a full validator exit.

### Proof of Concept
Not applicable as a runnable PoC — the vulnerable code path is a `match` arm reachable whenever `agave_snapshots::error::SnapshotError` is returned by `handle_snapshot_requests`; a concrete PoC would require injecting an I/O/serialization fault during snapshot archival (e.g., simulating a disk-full condition on `bank_snapshots_dir`/`full_snapshot_archives_dir`) to force this branch, which is unconfirmed to be reachable purely by an unprivileged transaction sender without environmental fault injection.
