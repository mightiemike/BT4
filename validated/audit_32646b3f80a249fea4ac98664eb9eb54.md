### Title
Post-decision commit failures crash a single node's consensus task instead of being tolerated, causing honest-node divergence - (File: `crates/apollo_consensus_orchestrator/src/sequencer_consensus_context.rs`)

### Summary
After consensus reaches a decision, `SequencerConsensusContext::decision_reached` calls `Batcher::decision_reached`, which performs several networked, component-to-component calls (mempool client, L1 provider client, commitment/committer manager) to persist the already-decided block. Any transient failure in these calls (which are genuine network RPCs in distributed/hybrid deployments) propagates as a hard error all the way out of the top-level `run_consensus` loop, terminating that node's consensus task, while peer nodes whose network calls happened to succeed continue normally. This mirrors the reported CometBFT `FinalizeBlock`/`PostFinalize` bug class: a non-deterministic network dependency injected into a step that is supposed to be uniformly reliable across all honest nodes after a decision/commit point.

### Finding Description
`Batcher::decision_reached` first commits the block locally and to networked components using `?`, i.e. any error aborts the function: [1](#0-0) 

`commit_proposal_and_block` (called above) issues calls to `mempool_client.commit_block` and `l1_provider_client.commit_block` — both of which are `ComponentClient` calls that can be remote gRPC-style calls to separate services in a distributed/hybrid deployment (see the per-service `url`/`port` configuration for `mempool`, `committer`, `l1_events_provider` in the deployment configs). `write_commitment_results_and_add_new_task` similarly drives the commitment manager, which sends tasks to a committer client: [2](#0-1) [3](#0-2) 

At the consensus-context layer, the whole batcher call is awaited with `?` right after the explicit comment stating the block is already committed and the function "must not fail beyond this point": [4](#0-3) 

`ConsensusError::BatcherError` is a `#[from] BatcherClientError`, i.e. any batcher-client communication error (including network/communication failures) is silently converted into a `ConsensusError`: [5](#0-4) 

In `MultiHeightManager::run_height`, the `context.decision_reached(...).await?` call sits in the `RunHeightRes::Decision(decision)` arm of the *success* match, outside the `Err(err) => match err { BatcherError | CommitteeError => fallback-to-sync, ... }` recovery logic that exists for errors produced *before* a decision is reached: [6](#0-5) 

Consequently, once a decision has already been reached (i.e., after the block is effectively final for that node), a `ConsensusError` from `decision_reached` is not caught by the sync-fallback path; it propagates via `?` straight out of `run_height`, and then out of `run_consensus`'s `manager.run_height(...).await?`, terminating the consensus task entirely: [7](#0-6) 

Because the underlying failure source is a network call to peer components (mempool, L1 events provider, committer) whose reachability/latency is independent per node, some honest nodes will hit a transient failure and crash their consensus task at this exact point while others, with a healthy network path, continue seamlessly — exactly the class of non-determinism identified in the CometBFT report, just relocated to the sequencer's own post-decision commit pipeline instead of `FinalizeBlock`/`PostFinalize`.

### Impact Explanation
A node whose internal network call (to mempool, L1 events provider, or committer) transiently fails immediately after a decision is reached will have its entire consensus loop terminate with an unhandled error, even though the block was already (partially) committed locally. This causes honest-node divergence: some validators silently drop out of consensus participation (requiring manual restart/intervention) while others proceed normally, degrading the effective validator set and — if this correlates across enough nodes (e.g., during a shared network blip or committer/mempool restart) — can threaten the liveness of the network's ability to reach further decisions. This falls under "honest-node divergence" / "network unable to confirm new transactions" in the acceptance criteria.

### Likelihood Explanation
No malicious transaction, proposer, or peer is required — any transient network hiccup between the consensus/batcher process and the mempool, L1 events provider, or committer service (all of which are deployed as separate networked components in hybrid/distributed deployments) is sufficient to trigger this on the affected node, on every block. Given that these are ordinary internal service calls (not attacker controlled), the likelihood of occasional divergence in production, multi-service deployments is non-trivial, especially under load or during rolling restarts of internal services.

### Recommendation
Do not let `decision_reached`/`commit_proposal_and_block`/`write_commitment_results_and_add_new_task` failures crash the top-level consensus task once a decision has been reached. Either:
- Retry these networked calls indefinitely/with backoff (as `state_committer.rs`'s `perform_task` already does for the committer path) before returning from `decision_reached`, or
- Treat post-decision commit errors identically to the existing `BatcherError`/`CommitteeError` sync-fallback path in `manager.rs::run_height`, so a node that fails to commit can catch up via sync rather than terminating its consensus task.

### Proof of Concept
Not applicable as a transaction-driven PoC: this is an infrastructure/control-flow issue triggered by transient network failure between internal sequencer components (mempool/L1-provider/committer), reproducible by injecting a `BatcherClientError`/communication failure from any of `mempool_client.commit_block`, `l1_provider_client.commit_block`, or the committer channel during `Batcher::decision_reached` on a single node while other nodes' calls succeed — observable via the existing test `decision_reached_return_success_when_l1_commit_block_fails` pattern (which currently shows the L1-provider failure path is tolerated) but is not exercised for the mempool/committer error paths, where `?` still aborts the whole flow and, per `manager.rs`, is not caught by the sync-fallback logic once a decision has already been reached.         self.successfully_added_commitment_task(height, state_diff_commitment);
        Ok(())

    async fn decision_reached(
        &mut self,
        height: BlockNumber,
        round: Round,
        commitment: ProposalCommitment,
        wait_for_last_commitment: bool,
    ) -> Result<(), ConsensusError> {
        info!("Finished consensus for height: {height}. Agreed on block: {:#066x}", commitment.0);

        self.interrupt_active_proposal().await;
        let (init, transactions, proposal_id, finished_info) = {
            let mut proposals = self.valid_proposals.lock().unwrap();
            let (init, transactions, proposal_id, finished_info) =
                proposals.get_proposal(&height, &round, &commitment).clone();
            proposals.remove_proposals_below_or_at_height(&height);
            (init, transactions, proposal_id, finished_info)
        };

        let decision_reached_response =
            self.deps.batcher.decision_reached(DecisionReachedInput { proposal_id }).await?;

        // CRITICAL: The block is now committed. This function must not fail beyond this point
        // unless the state is fully reverted, otherwise the node will be left in an
        // inconsistent state.

        self.finalize_decision(
            height,
            &init,
            commitment,
            transactions,
            decision_reached_response,
            finished_info.block_header_commitments.clone(),
            finished_info.l2_gas_used,
            wait_for_last_commitment,
        )
        .await;
