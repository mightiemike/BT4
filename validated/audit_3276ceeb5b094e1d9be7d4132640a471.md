### Title
Unbounded in-memory body buffering before signature validation in webhook/flow/fulfillment-service authentication handlers - ([File: packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts])

### Summary
The `authenticate.webhook`, `authenticate.flow`, and `authenticate.fulfillmentService` handlers in `shopify-app-remix` and `shopify-app-react-router` call `await request.text()` to buffer the *entire* HTTP request body into memory as a string before any HMAC/signature validation is performed. This mirrors the Fastify CVE-2018-3711 bug class: no payload size limit is enforced prior to buffering/parsing an anonymous, unauthenticated POST body, allowing an attacker to exhaust process memory or trigger a V8 string-length crash.

### Finding Description
All three public "auth handler" style endpoints follow this pattern: [1](#0-0) 

The webhook handler unconditionally reads the full body via `request.text()` before `api.webhooks.validate()` is ever invoked to check the HMAC. The same unbounded-read-before-validation pattern exists for Flow requests: [2](#0-1) 

and for fulfillment-service requests: [3](#0-2) 

The identical pattern is duplicated in `shopify-app-react-router`: [4](#0-3) 

None of these call sites, nor the underlying `NormalizedRequest`/adapter types, impose a content-length or streaming size cap: [5](#0-4) 

Because `request.text()` (the standard Fetch API `Request.text()`) must materialize the whole body into a single in-memory string before returning, and because these routes are reachable by any unauthenticated caller (webhook/flow/fulfillment-service endpoints are public HTTP POST endpoints that only become "authenticated" after the HMAC check that happens *after* this read), an attacker can send arbitrarily large payloads to force excessive memory allocation, exactly the resource-exhaustion pattern described in the Fastify report (build up payload fully before any validation/parsing gate).

### Impact Explanation
An anonymous attacker (no session, no valid HMAC, no merchant/customer credentials) can send POST requests with very large bodies to any of these publicly-reachable, unauthenticated endpoints (`/webhooks`, Flow action endpoint, fulfillment-service callback endpoint). Because the body is fully buffered before the signature check rejects it, this can be repeated indefinitely and in parallel, potentially exhausting server memory or crashing the Node process — a denial-of-service of the app's authentication/webhook-processing surface, which is explicitly an accepted analog per the validation criteria ("DoS of an auth handler").

### Likelihood Explanation
High likelihood: these routes are intentionally public-facing (webhook receivers, Flow action endpoints, fulfillment-service callbacks must be reachable without prior authentication so Shopify can call them), require no secrets or session state to reach, and the vulnerable code path (`request.text()`) executes unconditionally on every POST before any validation.

### Recommendation
- Enforce a maximum request body size (e.g., checking `Content-Length` header and rejecting/streaming-limiting bodies over a safe threshold, such as 1–5 MB, consistent with Shopify webhook payload sizes) before calling `request.text()`.
- Consider reading the body via a size-capped streaming reader that aborts once a threshold is exceeded, rather than accumulating unbounded data.
- Apply this consistently across `authenticate.webhook`, `authenticate.flow`, and `authenticate.fulfillmentService` in both `shopify-app-remix` and `shopify-app-react-router`.

### Proof of Concept
```bash
# Send an oversized POST body to a public webhook/flow/fulfillment-service endpoint
# with an arbitrary/invalid HMAC header — the entire body is buffered into memory
# via request.text() before the HMAC check rejects it.
node -e '
const http = require("http");
const req = http.request("http://target-app/webhooks", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "X-Shopify-Hmac-Sha256": "invalid",
    "X-Shopify-Topic": "products/create",
    "X-Shopify-Shop-Domain": "test.myshopify.com",
    "X-Shopify-Webhook-Id": "1",
    "X-Shopify-API-Version": "2023-01",
  },
});
const chunk = Buffer.alloc(10 * 1024 * 1024, "a"); // 10MB chunk
for (let i = 0; i < 200; i++) req.write(chunk); // ~2GB total
req.end();
'
```
Repeating this concurrently from multiple connections forces each request handler to fully materialize an oversized string in memory before HMAC validation fails, which can exhaust memory or crash the process.
