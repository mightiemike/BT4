The `apparent_sender` field is derived from parsing the change-output address of a `LeaderBlockCommit` Bitcoin transaction, and when the output is missing or undecodable, the parser silently substitutes one of two fixed placeholder strings rather than rejecting the transaction:### Title
Silent placeholder coercion of `apparent_sender` on undecodable change output collapses distinct miners into one identity - ([File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs])

### Summary
`LeaderBlockCommitOp::parse_from_tx` derives the consensus-tracked `apparent_sender` field from the block-commit's Bitcoin change output. When that output is missing or its address cannot be decoded, the parser does not reject the transaction; instead it silently substitutes one of two fixed sentinel strings, `"<no-change-output>"` or `"<undecodable-output>"`, and treats the block-commit as valid.

### Finding Description
In `parse_pox_waterfall_commits`/the reward-phase and sunset branches of `LeaderBlockCommitOp::parse_from_tx`, the sender identity is computed as: [1](#0-0) 

```
let apparent_sender = BurnchainSigner(
    outputs
        .get(1)
        .map(|out| out.as_ref().map(|out| out.address.clone().to_b58())
            .unwrap_or("<undecodable-output>".to_string()))
        .unwrap_or("<no-change-output>".to_string()),
);
```

The same pattern recurs for the reward-phase branch: [2](#0-1) 

`apparent_sender` is not a decorative field — it is the identity SortDB uses to link a miner's successive block-commits (via `SortitionDB::get_last_block_commit_by_sender`) and it is echoed in every consensus-relevant log/error path in `check_common` (`apparent_sender_repr`): [3](#0-2) [4](#0-3) . It is also the key that miner-side spend-distribution accounting groups burns by: [5](#0-4) .

Because a burn transaction is an arbitrary, attacker-crafted Bitcoin transaction (any minority participant can submit one with any script or omit the second output entirely), any minority miner can craft a `LeaderBlockCommit` OP_RETURN transaction whose second output is absent, or is present but encodes an address type the node's Bitcoin-address decoder does not recognize. In either case, `to_b58()`/the outer `.map()` fails, and the parser does not return `op_error::ParseError`/`InvalidInput` — it substitutes the fixed literal string. Every node in the network applies the exact same fallback deterministically, so this by itself does not cause a fork; the danger is that it breaks the intended equality "one Bitcoin signer == one apparent_sender" that downstream sortition/RBF bookkeping relies on, allowing multiple distinct miners (all of whom omit/mangle their change output) to collide onto the identical sentinel `apparent_sender` value.

### Impact Explanation
This does not directly forge a sortition winner (the burn-weight computation in `distribution.rs` operates on `burn_fee`, not `apparent_sender`), so it does not by itself break the core VRF/burn-weight equality. Its concrete, reproducible effect is on `SortitionDB::get_last_block_commit_by_sender`, which multiple call sites use to chain a miner's block-commits (finding "my previous commit" to compute UTXO/commit lineage): [4](#0-3) . If two unrelated minority miners both produce a commit with an undecodable/absent second output in the same fork, the second miner's lookup by `apparent_sender` will find the first miner's row and treat it as its own prior commit, corrupting its own book-keeping (miscomputed committed-input reference) — a self-inflicted validation inconsistency for that miner, not a network-wide invalid-accept. Given the CVSS scope of the analog report (bounded, non-majority, no direct fund theft), this is best characterized as a High-severity, minority-triggerable state/validation divergence bounded to the affected miner's own commit chain and to any off-chain accounting (spend-distribution reporting in `chain_data.rs`) that keys on `apparent_sender`. It does not produce a network-wide invalid block accept, a non-reproducible state root, or reward double-payment, so it falls short of "Critical."

### Likelihood Explanation
Triggering this requires only submitting a normal Bitcoin transaction with the `LeaderBlockCommit` OP_RETURN payload and either omitting the second (change) output or using a non-standard/undecodable output script for it — something well within reach of any single, unprivileged burnchain participant (no majority, no signer key, no node-operator access needed). The consuming code paths (`get_last_block_commit_by_sender`, `chain_data.rs` spend distribution) are exercised on every commit, so any miner making this mistake (deliberately or accidentally) reaches the vulnerable equality every time.

### Recommendation
Reject (rather than silently coerce) block-commit transactions whose apparent-sender output is missing or undecodable, mirroring the strictness already used for `output_0` (`ok_or_else(... InvalidInput)`), or, if backward compatibility with existing "<no-change-output>"-tagged commits is required, make the sentinel value unique per-transaction (e.g., derived from `txid`) instead of a shared literal, so no two distinct senders can ever collide onto the same `apparent_sender`.

### Proof of Concept
1. Craft a Bitcoin transaction with a valid `LeaderBlockCommit` OP_RETURN in output 0, but supply as output 1 either nothing (single-output tx) or a script type unsupported by `BitcoinAddress` decoding (e.g., a bare multisig or `OP_RETURN` script instead of a P2PKH/P2SH).
2. Submit two such transactions from two different Bitcoin keys/wallets within the same sortition window.
3. Observe that `LeaderBlockCommitOp::parse_from_tx` accepts both, and both end up with `apparent_sender == BurnchainSigner("<no-change-output>")` (or `"<undecodable-output>"`).
4. Query `SortitionDB::get_last_block_commit_by_sender(ic.conn(), &BurnchainSigner("<no-change-output>".into()))` — it now returns whichever of the two miners' commits happens to satisfy the SortDB's "latest" ordering, incorrectly linking the second miner's commit lineage to the first miner's transaction, corrupting the input/UTXO-chaining logic exercised in `stackslib/src/burnchains/tests/mod.rs:441-444`.
