## Title
Stale cross-shard `target_shard` on `GlobalContractDistribution` receipts can panic/halt a node after multiple reshardings - (File: `core/primitives/src/receipt.rs` / `runtime/runtime/src/congestion_control.rs`)

### Summary
The reported ether-fi bug (`GlobalIndexLibrary.calculateRewardsPerTierV0` indexing `tierDeposits` with a `numberOfTiers` that grew without the backing array being resized, causing every `rebase()` call to revert) is the same bug class as a documented issue in nearcore's dynamic-resharding path: a receipt carries a `target_shard`/`receiver_shard_id` computed under an old `ShardLayout`, and after the shard set changes (a "new tier" being added, i.e. a shard split) the remap of that stale shard id can fail when the code assumes the id is still resolvable, causing a panic that halts chunk processing instead of a graceful error.

### Finding Description
`GlobalContractDistribution` receipts are long-lived: they can sit in the delayed-receipt queue across chunk applications (e.g. while a shard is saturated with compute) and reference a `target_shard` computed against the shard layout that existed at receipt-creation time [1](#0-0) . Dynamic resharding can split a shard more than once across epochs (`DynamicReshardingConfig` allows sequential force-splits) [2](#0-1) . This is directly analogous to "adding a new tier": `numberOfTiers` (≈ number of shards) grows, but the parallel data referencing the old index/shard (≈ `tierDeposits`, here the receipt's `target_shard`) is not migrated in lock-step, so a subsequent operation over the new, larger shard set can index/resolve incorrectly.

The regression test explicitly documents the failure mode: "processing the stale `GlobalContractDistribution` receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old `target_shard` after two resharding generations" [3](#0-2) . The delayed-receipt queue's `receipt_filter_fn` and the shard-remap logic (`receiver_shard_id`, `get_shard_index`, ancestor/parent lookups in `ShardLayout`) are exactly the kind of "iterate assuming index/shard is still valid" pattern that produced the ether-fi out-of-bounds revert: a shard/tier count that has increased twice, with a stale reference computed under a much older layout, is the scenario the fix must specifically special-case ("the fix only works with V3 shard layouts... with static resharding the shard layout doesn't maintain a full split history") [4](#0-3) .

The reachable trigger is fully unprivileged: any account can submit a `DeployGlobalContract` action, which produces a `GlobalContractDistribution` receipt with a `target_shard`, and by saturating compute on that shard with ordinary function calls (`burn_gas_raw`-style transactions) an attacker can force the receipt to remain in the delayed queue across two shard-split epochs before it is finally processed [5](#0-4) .

### Impact Explanation
If the remap of the stale `target_shard`/`receiver_shard_id` is not fully robust to a receipt surviving two (or more) resharding generations, applying that delayed receipt would panic mid-chunk-apply. Because chunk application is on the block-processing critical path, a panic here is a transaction/receipt-triggered halt of the node applying that chunk — validators/chunk producers tracking the shard would crash or refuse to progress, which is explicitly one of the accepted high-severity outcomes (a transaction-triggered halt). This mirrors the "adding a new tier prevents further protocol operation (`rebase`)" impact from the source report, except in nearcore the "protocol operation" is chunk/receipt processing rather than a reward rebase.

### Likelihood Explanation
The scenario requires: (1) dynamic resharding enabled with `ShardLayoutConfig::Dynamic`, (2) two reshardings splitting the shard that holds a pending `GlobalContractDistribution` receipt, and (3) the receipt being kept in the delayed queue across both epochs (achievable deterministically by any account saturating chunk compute on that shard with cheap `FunctionCall` transactions). All three are achievable by an unprivileged user/transaction signer without any special permission, matching this project's own dedicated regression test built purely from ordinary transactions (`tx_deploy_test_contract`, `tx_deploy_global_contract`, `tx_call`) [6](#0-5) . Because a fix/regression test already exists in this tree (`test_stale_global_contract_distribution_after_double_resharding`) I could not confirm from static reading whether the underlying `receiver_shard_id`/`receipt_filter_fn` logic in `core/primitives/src/receipt.rs` fully handles an arbitrary N-generation resharding chain or only the exact two-generation case exercised by the test — this is the main open uncertainty, since I was not able to fully read `receiver_shard_id`'s implementation and its ancestor-shard resolution logic before the tool budget ran out.

### Recommendation
Audit `Receipt::receiver_shard_id` (and any other code that resolves a `target_shard`/`receiver_shard` field embedded in a persisted receipt) to ensure it walks the *full* ancestor chain recorded in `ShardLayout::V3`'s split history for arbitrarily many resharding generations, not just one or two hops, and returns a proper `Result`/`Error` instead of panicking (e.g., via `.expect()`/`unwrap()`) when a shard id cannot be resolved. Extend `test_stale_global_contract_distribution_after_double_resharding` (or add a parameterized variant) to cover three or more sequential splits of the same shard to close the gap between the tested two-generation case and the general N-generation case implied by `ShardLayout::V3`'s design.

### Proof of Concept
Use the existing test as the reproduction template — it is an unprivileged-transaction-only scenario:
1. Deploy a contract on `user0` and then deploy a `GlobalContract` from `user0`, producing a `GlobalContractDistribution` receipt whose `target_shard` is `user0`'s current shard [7](#0-6) .
2. Continuously submit `burn_gas_raw` calls to `user0`'s shard every block so the distribution receipt is pushed into (and stays in) the delayed-receipt queue [8](#0-7) .
3. Configure `DynamicReshardingConfig` to force-split `user0`'s shard and then split it again in the following epoch [2](#0-1) , so the shard count/tier increases twice while the delayed receipt is outstanding.
4. Stop saturating and let the delayed queue drain; if the shard-remap logic on the stale receipt is not fully generalized, chunk application panics and the chain halts at that height, which the test detects via `head_height >= drain_end` [9](#0-8) .

    // two local receipts exhaust the chunk's compute budget. We submit 3 per

    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {

                    Balance::ZERO,
