### No vulnerability found for this question.

The concern doesn't hold up given the actual code flow:

1. In `ShieldedTransferActuator.execute()`, the `addExact`/`subtractExact` computation happens strictly *before* the store mutation: `Commons.adjustTotalShieldedPoolValue(addExact(subtractExact(toAmount, fromAmount), fee), dynamicStore)` — if the arithmetic throws `ArithmeticException`, `adjustTotalShieldedPoolValue` (the only place that calls `dynamicPropertiesStore.saveTotalShieldedPoolValue`) is never invoked at all, so no partial write to `totalShieldedPoolValue` can occur from this path. [1](#0-0) 

2. `Commons.adjustTotalShieldedPoolValue` itself only calls `saveTotalShieldedPoolValue` after the fresh `subtractExact`/negative check succeeds — it's a single atomic read-check-write, not split across multiple persisted steps. [2](#0-1) 

3. Any other partial state writes made earlier in `execute()` (nullifier insertion, merkle tree updates, account balance adjustments) are not left dangling either: transactions are processed inside a revoking-store `ISession` (`tmpSession`) that is only `merge()`d/`commit()`ed on success; if `ContractExeException` propagates out of `processTransaction`, the try-with-resources closes the session without merging, reverting all writes for that transaction. [3](#0-2) 

4. `checkProof`'s `proofStore`/`recordProof` cache only remembers whether the zk-SNARK cryptographic proof was previously valid — it has nothing to do with `totalShieldedPoolValue`, and the actual pool-value guard in `execute()` is recomputed fresh from the current `dynamicStore` value every single time via `Commons.adjustTotalShieldedPoolValue`, so a cached proof result cannot be leveraged to bypass the negative-pool check. [4](#0-3) 

5. Extreme `fromAmount`/`toAmount` values near `Long.MAX_VALUE`/`MIN_VALUE` are also independently rejected earlier in `validateTransparent`, which requires non-negative amounts, `fromAmount <= fee` rejection, and that the sender's real balance (`balance < fromAmount`) covers the claimed `fromAmount`, preventing an attacker from supplying unbacked huge values without controlling a correspondingly large real balance. [5](#0-4) 

Existing tests (`ManagerTest.adjustTotalShieldPoolValueTest`, `ShieldedTransferActuatorTest.shieldAddressToPublicNotEnoughFailure`) already exercise the negative-pool rejection path and confirm the value is never decremented when the check fails. [6](#0-5)

  public static void adjustTotalShieldedPoolValue(long valueBalance,
      DynamicPropertiesStore dynamicPropertiesStore) throws BalanceInsufficientException {
    long totalShieldedPoolValue = subtractExact(
        dynamicPropertiesStore.getTotalShieldedPoolValue(), valueBalance,
        dynamicPropertiesStore.disableJavaLangMath());
    if (totalShieldedPoolValue < 0) {
      throw new BalanceInsufficientException(String.format(
          "total shielded pool value can not below 0, actual: %d", totalShieldedPoolValue));
    }
    dynamicPropertiesStore.saveTotalShieldedPoolValue(totalShieldedPoolValue);
  }
