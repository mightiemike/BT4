### Title
Free-bandwidth global pool (`PUBLIC_NET_LIMIT`) can be exhausted by low-cost transactions to DoS other free-tier accounts — (File: `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`)

### Summary
Like the Axelar `TokenManager` per-epoch flow limit, java-tron enforces a shared, periodically-decaying resource cap — the network-wide free bandwidth pool (`PUBLIC_NET_USAGE`/`PUBLIC_NET_LIMIT`) — that any anonymous account consumes when broadcasting ordinary transactions without frozen bandwidth. An attacker can cheaply flood this shared pool at the start of its recovery window, exhausting it for all other unprivileged accounts for the remainder of the window.

### Finding Description
`BandwidthProcessor.consume()` tries, in order, account-owned bandwidth, then the free bandwidth pool, then falls back to paying a TRX fee: [1](#0-0) 

The free-bandwidth check in `useFreeNet()` draws from two decaying counters that recover over a sliding window (analogous to Axelar's 6-hour epoch): the per-account `freeNetUsage`/`freeNetLimit` and — critically — the network-wide shared `publicNetUsage`/`publicNetLimit`: [2](#0-1) 

The shared counter is a single global value (`PUBLIC_NET_USAGE`, `PUBLIC_NET_LIMIT`, `PUBLIC_NET_TIME`) maintained in `DynamicPropertiesStore`: [3](#0-2) 

The recovery/decay logic in `ResourceProcessor.increase()` is exactly the same "windowed capacity that refills over time" pattern used by the Axelar flow limit: usage decays linearly as time passes within the window and resets to zero once the window has fully elapsed: [4](#0-3) 

Because `publicNetUsage` is a single global counter shared by every account that has no frozen bandwidth, any anonymous sender can broadcast a burst of ordinary (near-zero-fee) transactions at the beginning of a window to drive `newPublicNetUsage` up to `publicNetLimit`. Once exhausted, `useFreeNet()` returns `false` for every other account for the rest of the window: [5](#0-4) 

At that point every other free-tier account (i.e., every ordinary account without frozen TRX for bandwidth) is forced down the `useTransactionFee` fallback and must burn TRX for bandwidth or have its transaction rejected with `AccountResourceInsufficientException` if it lacks balance: [6](#0-5) 

This is structurally identical to the Axelar report: a single shared capacity value that resets on a fixed period, consumable by any unprivileged actor at negligible cost, with no per-account or per-IP throttling on how much of the *shared* pool a single account can claim in one window.

### Impact Explanation
An attacker (no special privileges, no large stake required — only enough TRX to pay minimal per-transaction fees or none at all if bandwidth is otherwise free) can repeatedly exhaust `PUBLIC_NET_LIMIT` at the start of every recovery window. This does not corrupt funds or consensus, but it degrades availability of the free-bandwidth tier for the entire network: legitimate low-balance/free-tier accounts are pushed into paying TRX fees or having transactions rejected, mirroring the "temporary availability" Medium-severity classification given to the original Axelar finding.

### Likelihood Explanation
High feasibility and low cost: the attack only requires broadcasting a burst of standard, low-fee transactions from one or more addresses, exactly as anonymous RPC/HTTP broadcast callers are permitted to do. No contract deployment, no elevated permission, and no large capital lockup (unlike the energy/bandwidth-weight mechanisms tied to frozen balance) are required, since `useFreeNet` applies to accounts without frozen bandwidth at all.

### Recommendation
Apply the operator-side mitigations already discussed for the analogous Axelar issue: consider per-account or per-IP sub-limits on the shared free-bandwidth pool (accepting Sybil-resistance tradeoffs), or reduce/eliminate reliance on a single global free-bandwidth counter in favor of quotas scoped more granularly, and ensure operators can tune `PUBLIC_NET_LIMIT`/`FREE_NET_LIMIT` via governance proposals as an operational response, similar to how Axelar recommends operators adjust `flowLimit`.

### Proof of Concept
1. At the start of a fresh recovery window (i.e., right after `publicNetUsage` has decayed to near zero), an attacker broadcasts a burst of ordinary transactions from an account (or several Sybil accounts) with no frozen bandwidth.
2. Each transaction is validated via `BandwidthProcessor.consume()` → `useFreeNet()`, incrementing the shared `publicNetUsage` counter.
3. Once `newPublicNetUsage` reaches `publicNetLimit`, subsequent calls to `useFreeNet()` for *any* other account return `false` (see lines 526-531 above).
4. All other free-tier accounts broadcasting transactions in that window fall through to `useTransactionFee`, forcing them to pay TRX or fail with `AccountResourceInsufficientException` until the window naturally decays the shared counter back down.

  private boolean useFreeNet(AccountCapsule accountCapsule, long bytes, long now) {

    long freeNetLimit = chainBaseManager.getDynamicPropertiesStore().getFreeNetLimit();
    long freeNetUsage = accountCapsule.getFreeNetUsage();
    long latestConsumeFreeTime = accountCapsule.getLatestConsumeFreeTime();
    long newFreeNetUsage = increase(freeNetUsage, 0, latestConsumeFreeTime, now);

    if (bytes > (freeNetLimit - newFreeNetUsage)) {
      logger.debug("Free net usage is running out."
              + " Bytes: {}, freeNetLimit: {}, newFreeNetUsage: {}.",
          bytes, freeNetLimit, newFreeNetUsage);
      return false;
    }

    long publicNetLimit = chainBaseManager.getDynamicPropertiesStore().getPublicNetLimit();
    long publicNetUsage = chainBaseManager.getDynamicPropertiesStore().getPublicNetUsage();
    long publicNetTime = chainBaseManager.getDynamicPropertiesStore().getPublicNetTime();

    long newPublicNetUsage = increase(publicNetUsage, 0, publicNetTime, now);

    if (bytes > (publicNetLimit - newPublicNetUsage)) {
      logger.debug("Free public net usage is running out."
              + " Bytes: {}, publicNetLimit: {}, newPublicNetUsage: {}.",
          bytes, publicNetLimit, newPublicNetUsage);
      return false;
    }

  protected long increase(long lastUsage, long usage, long lastTime, long now, long windowSize) {
    long averageLastUsage;
    long averageUsage;
    if (hardenCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize);
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision), biWindowSize);
    } else {
      averageLastUsage = divideCeil(lastUsage * precision, windowSize);
      averageUsage = divideCeil(usage * precision, windowSize);
    }

    if (lastTime != now) {
      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay,
            this.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }
