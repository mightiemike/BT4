### Title
`ensure_match_transaction_info` silently skips the position/hot-state checkpoint-hash check, letting replay-verify accept a corrupted position-state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticity check used by replay/verification tooling to confirm that a freshly-computed `TransactionOutput` matches the persisted, ledger-info-anchored `TransactionInfo`. The function checks status, gas, write-set hash, and event-root hash, but explicitly returns `Ok(())` without checking the `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields that are also part of `TransactionInfo` (and thus part of what is Merkle-committed and signed by validators). This is a direct analog of the "return value not checked" bug class in the seed report: a success signal (`Ok(())`) is returned even though a state-commitment invariant was never actually validated.

### Finding Description
`TransactionInfo` (builder_v1, see `execution/executor/src/workflow/do_ledger_update.rs:95-121`) includes `maybe_hot_state_checkpoint_hash` and `maybe_position_state_checkpoint_hash` fields, which are populated from `hot_state_checkpoint_hashes` / `position_state_checkpoint_hashes` computed during ledger update, and become part of the hash of `TransactionInfo` that is accumulated and signed as part of the authenticated ledger.

`TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs:2139-2204` is the function that tools use to confirm a re-executed `TransactionOutput` corresponds to the expected, previously-committed `TransactionInfo`. It checks:
- status [1](#0-0) 
- gas used [2](#0-1) 
- write-set hash [3](#0-2) 
- event root hash [4](#0-3) 

But it then returns success while explicitly documenting that it skips the checkpoint hashes: [5](#0-4) 

This function is directly used as the correctness oracle by `storage/db-tool/src/replay_on_archive.rs`, which drives the `replay-verify` / `replay_on_archive` tooling: it re-executes historical transactions and calls `ensure_match_transaction_info` to decide pass/fail for each transaction. [6](#0-5) 

Because the hot-state and position-state checkpoint hashes are not compared, `replay_on_archive`/`replay-verify` can report a transaction (and the surrounding chunk/epoch) as successfully verified even though the locally recomputed position-state (or hot-state) root diverges from the value that is actually part of the authenticated, validator-signed `TransactionInfo`/accumulator leaf. This breaks the "proof-bearing/authenticated response must stay bound to the right root" invariant for that part of ledger state, specifically for the "trading-native" position-state commitment path (`native_position`, see `storage/aptosdb/src/db/aptosdb_native_position.rs`) that is gated behind the (currently disabled per the code comment) `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature.

### Impact Explanation
If/when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled and the native-position (or hot-state) subsystem participates in consensus-committed state roots, this gap means the primary automated replay/verify safety net used to detect divergence between VM execution output and the authenticated ledger will not catch corruption or non-determinism in that specific root. A bug in position-state computation, JMT construction, or hot-state promotion could silently corrupt the durable, authenticated ledger commitment while `replay-verify` continues to report success, masking a hard-fork-class divergence between nodes or between historical archives and current execution. This satisfies the "committed state differs from correct VM result... accepted as valid" and "hard-fork-only divergence during commit/replay not detected" impact classes.

### Likelihood Explanation
Today, likelihood of exploitation is constrained by the fact that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and the native-position checkpoint path appear to be new/experimental (feature-gated) at the time of this scan, and the code comment itself flags this as a known TODO ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"). However, the root cause — an authenticity-checking function returning `Ok(())` while skipping verification of fields that are already part of `TransactionInfo`'s hash — is unprivileged, deterministic, and independently provable from the code as written; the moment the feature is enabled (or if any code path already relies on this hash being meaningful), the verification gap becomes live with no additional preconditions.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`-derived hot-state and position-state checkpoint hashes (once locally recomputed) against `txn_info.hot_state_checkpoint_hash()` / `txn_info.position_state_checkpoint_hash()`, mirroring the pattern already used for `state_change_hash` and `event_root_hash`, before allowing `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any consumer of these fields) to be enabled. Until this is done, `replay-verify`/`replay_on_archive` should not be treated as authoritative for correctness of the trading-native/hot-state checkpoint roots.

### Proof of Concept
Not applicable as an exploit chain against currently-live mainnet functionality (the affected checkpoint fields are behind the disabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature per the code’s own comment). The proof is the code path itself:
1. `do_ledger_update.rs::assemble_transaction_infos` builds a `TransactionInfo` including `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` as committed fields. [7](#0-6) 
2. `replay_on_archive.rs::execute_and_verify` treats `ensure_match_transaction_info() == Ok(())` as full verification success for that transaction. [6](#0-5) 
3. `ensure_match_transaction_info` never compares those two hash fields and always returns `Ok(())` regardless of their value, as documented in its own TODO. [5](#0-4) 

I was not able to fully verify the exact current activation status/rollout state of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on mainnet within this investigation (only found its 3 references in `aptos_features.rs`, `aptosdb_reader.rs`, `aptosdb_writer.rs`, and `types/src/transaction/mod.rs` without reading their full context due to iteration limits) — this should be confirmed before treating the impact as currently live versus latent/future-risk.
