### Title
Gateway process panic (DoS) on class-manager/state-sync inconsistency during transaction validation — ([File: crates/apollo_gateway/src/sync_state_reader.rs])

### Summary
`SyncStateReader::get_contract_class_from_client` panics the whole gateway process when `is_class_declared_at` reports a class as declared but `class_manager_client.get_executable` returns `None` for that same class hash. This is directly analogous to the CVE's "predefined function is getting a NULL value as parameter" bug class: an internally-assumed-non-null/always-present value (the executable class) is unwrapped without a defensive check, and a crafted/malicious transaction can trigger this inconsistency.

### Finding Description [1](#0-0) 

The `SyncStateReader` is used by the gateway's stateful transaction validator to read contract classes during transaction validation. When validating a transaction that references a contract class, the code:

1. Calls `state_sync_client.is_class_declared_at(block_number, class_hash)` to check if the class is declared
2. If declared, calls `class_manager_client.get_executable(class_hash)` to fetch the executable class
3. **Panics** if `get_executable` returns `None` despite the class being declared:

```rust
let contract_class = self
    .runtime
    .block_on(self.class_manager_client.get_executable(class_hash))
    .map_err(|e| StateError::StateReadError(e.to_string()))?
    .unwrap_or_else(|| {
        panic!(
            "Class with hash {class_hash:?} doesn't appear in class manager even though \
             it was declared"
        )
    });
```

This code path is reachable from:
- `get_contract_class_from_client` (lines 77-99)
- `get_compiled_class` (line 171, calls `get_contract_class_from_client`)
- `get_compiled_classes` (line 104, calls `get_contract_class_from_client`)

All three are part of the `BlockifierStateReader` and `FetchCompiledClasses` traits, which are used during transaction validation in the blockifier execution layer.

### Impact Explanation [2](#0-1) 

The `SyncStateReader` is instantiated by `SyncStateReaderFactory` and injected into `StatefulTransactionValidator`, which validates every incoming transaction submitted to the gateway. When a transaction references a contract class, the validator calls `get_compiled_class` to fetch and validate the class during the `run_validate_entry_point` phase.

If state-sync and class-manager become inconsistent (class marked as declared in state-sync but missing from class-manager), any transaction referencing that class will cause the gateway process to panic and crash. This is a **denial of service** that freezes the sequencer's ability to accept new transactions.

The inconsistency can occur through:
- Race conditions during state-sync: a class is marked declared in storage before the class-manager finishes writing it
- Partial failures in class-manager writes (e.g., network timeout, storage error)
- Malicious or corrupted state-sync data

### Likelihood Explanation [3](#0-2) 

The state-sync flow shows that classes are written to state-sync storage and class-manager asynchronously. The class is marked as declared in state-sync before the class-manager write completes. If a transaction arrives during this window, it will trigger the panic.

Additionally, [4](#0-3)  shows similar panic patterns in other state readers, indicating this is a systemic issue where the codebase assumes class-manager consistency without defensive checks.

The code style guide explicitly forbids this pattern: [5](#0-4)  states "Code reachable from HTTP handlers or external input must never use `.unwrap()`, `.expect()`, or unchecked indexing on values derived from that input."

### Recommendation
Replace the `unwrap_or_else(|| panic!(...))` with proper error handling:

```rust
let contract_class = self
    .runtime
    .block_on(self.class_manager_client.get_executable(class_hash))
    .map_err(|e| StateError::StateReadError(e.to_string()))?
    .ok_or_else(|| {
        StateError::StateReadError(
            format!("Class {class_hash:?} declared in state-sync but missing from class-manager")
        )
    })?;
```

This converts the panic into a proper `StateError` that propagates as a transaction validation failure, allowing the gateway to reject the transaction and continue operating.

### Proof of Concept
1. Submit a transaction that calls a contract at address A
2. Ensure contract A's class hash is in state-sync's declared classes
3. Ensure that same class hash is NOT in the class-manager (e.g., via a race condition or corrupted state)
4. The gateway's `SyncStateReader::get_contract_class_from_client` will panic when validating the transaction
5. The gateway process crashes, unable to accept new transactions [6](#0-5)  confirms this is a known panic path with a test that explicitly expects it.

### Never panic on data reachable from requests
- Code reachable from HTTP handlers or external input must never use `.unwrap()`, `.expect()`, or unchecked indexing on values derived from that input
- Reserve panics for compile-time invariants where failure is a programmer bug, not a runtime possibility
- Return `Result` with a descriptive error variant, or use saturating/capping alternatives
