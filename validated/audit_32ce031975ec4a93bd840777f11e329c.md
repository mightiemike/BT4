Based on the investigation, the strongest local analog found is a self-documented gap in `types/src/transaction/mod.rs`.

### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash verification, allowing accepted transaction outputs to diverge from the authenticated ledger state - (File: `types/src/transaction/mod.rs`)

### Summary
Analogous to the external report where a function silently assumed the wrong "index" for a given `id` and thus returned/propagated incorrect committed values without validating the actual type, `TransactionOutput::ensure_match_transaction_info` computes and checks only a subset of the fields carried by `TransactionInfo` (status, gas, write-set hash, event root hash) but explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the locally recomputed state.

### Finding Description
`ensure_match_transaction_info` is the function used to validate that a locally re-executed `TransactionOutput` matches the `TransactionInfo` that is authenticated by the ledger/accumulator proof (i.e., it is a "replay verification" gate). It checks `status`, `gas_used`, `write_set_hash` vs `state_change_hash`, and `event_root_hash`, but the function ends with a `TODO(trading-native)` comment stating explicitly that it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)." [1](#0-0) 

This mirrors the report's bug class: a state-commitment-adjacent function returns "success" (a validated match) while silently using/ignoring the wrong or incomplete data for a subset of its inputs, similar to how `totalSupply` silently applied the wrong index for debt-token IDs. Here, the position/hot-state checkpoint hashes — which are real proof-bearing fields on `TransactionInfoV1` — are produced by `DoStateCheckpoint::run` and `compute_position_checkpoint` and threaded through `TransactionInfo::builder_v1`, gated by `execution_output.compute_trading_native_state_roots` and `hot_state_root_in_txn_info`. [2](#0-1) [3](#0-2) 

The comment states this is used by "replay-verify tooling (e.g. db-tool's `replay_on_archive`)," meaning a replayed/re-executed transaction whose locally-computed position or hot-state root diverges from what is embedded in the authenticated `TransactionInfoV1` will still be reported as a successful match by `ensure_match_transaction_info`, because that function never recomputes or compares those hash fields.

### Impact Explanation
If `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or `HOT_STATE_ROOT_IN_TXN_INFO`) is enabled on mainnet, a divergence in the position-state (or hot-state) Merkle root between the authenticated chain history and a node's locally recomputed state would not be caught by this comparator. This defeats a designed proof-integrity invariant: authenticated proof fields bound to a specific ledger version/root are supposed to be verified against locally recomputed state during replay, but a class of checkpoint roots is excluded from that check. Tooling relying on `ensure_match_transaction_info` (replay-verify) could report success/consistency even though the position state root — part of the committed, hash-chained `TransactionInfoV1` — has silently diverged, undermining confidence in replay-based integrity checks and potentially masking real state divergence (e.g., from a hard-fork-only bug in position-state computation) until much later.

### Likelihood Explanation
This code path is only exercised for the specific fields when the underlying feature flags (`compute_trading_native_state_roots`, `hot_state_root_in_txn_info`) are active, and the TODO comment itself says validation should be added "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying the feature may not be enabled on mainnet yet. I could not verify from the available code index whether this feature flag is currently active on mainnet or still gated off; this materially affects real-world exploitability and I was unable to fully confirm it due to index/tool limitations.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on `TransactionInfoV1`) against the actual locally computed checkpoint roots, mirroring the pattern already used for `write_set_hash` and `event_root_hash`, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Proof of Concept
Not directly demonstrable from static code alone since it depends on runtime feature-flag state and the position-state computation path (`DoStateCheckpoint::compute_position_checkpoint`) diverging from what was persisted in `TransactionInfoV1.position_state_checkpoint_hash`; a full PoC would require an executor/replay integration test toggling `compute_trading_native_state_roots` and injecting a position-state divergence, which is outside what can be confirmed via code search alone.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
