The reported issue is specific to the `VestingEscrow` smart contract's owner-controlled `revokeAll()` vs. recipient-controlled `claim()` race, which requires an application-level vesting/escrow contract with distinct "owner" and "recipient" roles and no time-delay between claim submission and execution. Searching the nearcore codebase for the closest structural analogs (access-key revocation, staking unstake/kickout, vesting/lockup logic) shows no reachable core-protocol path matching this bug class:

- Vesting/lockup logic (`terminate_vesting`) is not part of this nearcore repository's protocol code — it exists only as an external `lockup_contract.wasm` binary used solely for gas-cost benchmarking in the params estimator, not as in-scope production runtime code that an unprivileged signer/RPC caller reaches through validated protocol logic. [1](#0-0) 
- `DeleteKey`/access-key revocation is always initiated by the account itself (`signer_id == receiver_id` for `delete_key`), so there is no cross-account "owner revokes, victim front-runs" dynamic; any unused allowance is simply burned rather than redirected to a party that could be front-run. [2](#0-1) [3](#0-2) 
- Staking/unstaking and validator kickout do not exhibit the "recipient claims value that should go to owner" pattern either: slashing (the only mechanism that would seize a validator's locked stake) is explicitly disabled in this codebase, so unstaking cannot be front-run to divert funds that would otherwise be confiscated. [4](#0-3) [5](#0-4) 

Since the bug class fundamentally requires an owner-vs-recipient value-revocation race in application-level contract logic that is not present as reachable in-scope protocol code in this repository, there is no valid nearcore analog to report.
