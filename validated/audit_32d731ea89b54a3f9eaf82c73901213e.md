### Title
Attacker-controlled zero/near-zero outbound `gasLimit` permanently stalls outbound broadcast and freezes bridged funds - (File: `x/uexecutor/keeper/create_outbound.go`, `universalClient/chains/evm/tx_builder.go`)

### Summary
An unprivileged caller who triggers a `UniversalTxOutboundEvent` (e.g. via a smart contract or the SDK calling `sendUniversalTxOutbound`) fully controls the `gasLimit` field carried in that event. Push Chain's `x/uexecutor` module copies this value verbatim into `OutboundTx.GasLimit` and the `universalClient` TSS pipeline signs and broadcasts an EVM transaction using that exact value with no minimum-gas validation.

### Finding Description
`BuildOutboundsFromReceipt` in [1](#0-0)  sets `outbound.GasLimit = event.GasLimit.String()` directly from the decoded on-chain event with no bound check. This flows into `OutboundCreatedEvent` and eventually to the universalClient's `TxBuilder.GetOutboundSigningRequest` and `BroadcastOutboundSigningRequest`, both of which call `parseGasLimit(data.GasLimit)` and construct the EVM transaction with `gasLimit.Uint64()` unmodified: [2](#0-1)  and [3](#0-2) .

If the gas limit is below the EVM intrinsic-gas floor (e.g., below 21000 for a simple transfer, or below the calldata-dependent floor for a payload call), the signed transaction is invalid and will be rejected by the destination RPC node at broadcast time — it never lands on-chain and never produces a receipt. The broadcaster's failure-handling path treats this the same as a transient network error: `broadcastOutboundEVM`/`broadcastOutboundSVM`-style logic simply logs the error and leaves the event in `SIGNED` state for the next tick, per the TSS broadcaster pattern shown in [4](#0-3)  (the EVM equivalent follows the same retry-without-fallback structure). Because the same invalid, too-low `gasLimit` is reused every retry, the transaction fails deterministically forever.

Since the outbound never gets included on-chain, it never reaches `VerifyBroadcastedTx`'s "found" branch nor the nonce-consumed branch in `resolveOutboundEVM` ( [5](#0-4) ) that would otherwise trigger `voteOutboundFailureAndMarkReverted` and, via `handleFailedOutbound` ( [6](#0-5) ), automatically re-mint/refund the bridged funds on Push Chain. The outbound is permanently stuck `PENDING`, and the bridged tokens are effectively frozen with no automated recovery path.

### Impact Explanation
This is a direct analog of the cited Gnosis AMB report: a user-controllable gas-limit parameter with no minimum-bound enforcement, that when set too low, causes destination-side execution to permanently fail in a way outside the normal success/fail observation loop, leaving claimed/bridged value stuck and requiring manual/governance-style intervention (there's no on-chain "replay with higher gas" path visible in this codebase). This falls under the in-scope "permanent freezing of user or protocol-controlled funds" and "corruption of ... refund accounting" categories, reachable by an ordinary unprivileged user submitting a payload with an attacker-chosen `gasLimit` (e.g. `1`) for a `FUNDS`/`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` outbound.

### Likelihood Explanation
Moderate-to-high: it requires only that the caller of `sendUniversalTxOutbound` (a normal, permissionless entrypoint invoked by any UEA/CEA payload) supply a `gasLimit` value low enough to fall below the EVM intrinsic-gas floor. Whether this is actually reachable depends on validation performed in the `UniversalCore`/`UniversalGatewayPC` Solidity contracts (outside this repo, not verifiable here) — if those contracts enforce a hard floor above the intrinsic-gas requirement for every chain (as `getOutboundTxGasAndFees`'s `baseGasLimitByChainNamespace` fallback logic suggests they might for the `gasLimit=0` case), this may not be exploitable in practice. I could not confirm from this repo's code whether a small nonzero attacker-supplied `gasLimit` is bounded by the Solidity contract, since that contract's source is not part of this repository's index.

### Recommendation
In `x/uexecutor/keeper/create_outbound.go`, validate `event.GasLimit` against a documented minimum (chain-specific intrinsic-gas floor, e.g. via `uregistry` chain config) before persisting it into `OutboundTx`, rejecting or clamping outbounds whose gas limit cannot possibly execute. Additionally, in `universalClient/tss/txbroadcaster` and `universalClient/chains/evm/tx_builder.go`, detect a deterministic "intrinsic gas too low" broadcast error and short-circuit to the failure/revert path instead of retrying indefinitely, so `handleFailedOutbound`'s automatic fund-return logic can trigger.

### Proof of Concept
1. A user calls the UEA/CEA path that emits `UniversalTxOutboundEvent` with `TxType_FUNDS` (or `FUNDS_AND_PAYLOAD`) and sets `gasLimit = 1` in the payload/contract call.
2. `BuildOutboundsFromReceipt` copies this into `OutboundTx.GasLimit = "1"` with no validation (`x/uexecutor/keeper/create_outbound.go:78`).
3. `universalClient`'s TxBuilder signs an EVM tx with `gasLimit.Uint64() = 1` (`universalClient/chains/evm/tx_builder.go:142`).
4. The destination RPC node rejects the tx as invalid (`intrinsic gas too low`) at broadcast time; `BroadcastOutboundSigningRequest` returns an error.
5. The broadcaster logs the failure and leaves the event `SIGNED`, retrying every tick with the same unbroadcastable gas limit forever.
6. The outbound never reaches `OBSERVED`/`REVERTED`; `handleFailedOutbound`'s automatic PRC20 re-mint/refund never fires; bridged funds remain permanently locked in the `OutboundTx` PENDING state.

Note: I was unable to verify within this repository whether the external `UniversalCore.sol`/`UniversalGatewayPC.sol` contracts (not part of this repo's index) enforce a gas-limit floor before emitting the event, which would determine whether this is actually reachable end-to-end. If a Devin session with full repo/contract access is desired to confirm this cross-repo dependency, that would need to be verified against the Solidity contracts repository separately.

// handleFailedOutbound mints back the bridged tokens to the revert recipient,
// then attempts to refund any excess gas (gasFee - gasFeeUsed) just like a
// successful outbound would. Both operations are recorded on the outbound.
func (k Keeper) handleFailedOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	// Only revert bridged funds for funds-related tx types
	if outbound.TxType == types.TxType_FUNDS || outbound.TxType == types.TxType_GAS_AND_PAYLOAD ||
		outbound.TxType == types.TxType_FUNDS_AND_PAYLOAD {

		// Decide revert recipient safely
		recipient := outbound.Sender
		if outbound.RevertInstructions != nil &&
			outbound.RevertInstructions.FundRecipient != "" {
			recipient = outbound.RevertInstructions.FundRecipient
		}

		amount := new(big.Int)
		amount, ok := amount.SetString(outbound.Amount, 10)
		if !ok {
			return fmt.Errorf("invalid amount: %s", outbound.Amount)
		}
		receipt, err := k.CallPRC20Deposit(ctx, common.HexToAddress(outbound.Prc20AssetAddr), common.HexToAddress(recipient), amount)

		pcTx := types.PCTx{
			Sender:      outbound.Sender,
			BlockHeight: uint64(ctx.BlockHeight()),
		}
		// Capture tx hash from receipt even on EVM revert for debugging.
		if receipt != nil {
			pcTx.TxHash = receipt.Hash
			pcTx.GasUsed = receipt.GasUsed
		}
		if err != nil {
			pcTx.Status = "FAILED"
			pcTx.ErrorMsg = err.Error()
			outbound.PcRevertExecution = &pcTx
			// Re-mint failed — mark as ABORTED for manual intervention
			return k.AbortOutbound(ctx, utxId, outbound,
				fmt.Sprintf("failed to re-mint tokens for revert: %s", err.Error()))
		}
		pcTx.TxHash = receipt.Hash
		pcTx.GasUsed = receipt.GasUsed
		pcTx.Status = "SUCCESS"
		outbound.PcRevertExecution = &pcTx
		k.Logger().Info("outbound failed: funds re-minted for revert",
			"utx_id", utxId,
			"outbound_id", outbound.Id,
			"tx_hash", receipt.Hash,
		)
	}

	outbound.OutboundStatus = types.Status_REVERTED
	k.Logger().Info("outbound reverted",
		"utx_id", utxId,
		"outbound_id", outbound.Id,
		"dest_chain", outbound.DestinationChain,
	)

	// Refund excess gas regardless of tx type — gas was consumed on the external
	// chain whether the execution succeeded or failed.
	k.applyGasRefund(ctx, &outbound, obs)

	return k.UpdateOutbound(ctx, utxId, outbound)
}
