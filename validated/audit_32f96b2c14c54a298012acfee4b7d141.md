### Title
PoisonMicroblock only checks recovered-pubkey equality, not header-content difference, letting a reporter forge a "double-sign" via ECDSA signature malleability or benign re-signing of identical content - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`check_microblock_header_signer` and `handle_poison_microblock` verify only that `check_recover_pubkey()` returns the same `Hash160` for both submitted `StacksMicroblockHeader`s; they never verify that the two headers actually diverge in content (e.g. `tx_merkle_root`). Because `check_recover_pubkey` uses `recover_to_pubkey_without_validating_low_s`, an attacker can take any single, honestly-broadcast microblock header and mechanically derive a second, byte-different-but-still-recovering signature over the identical header (via the standard ECDSA malleability transform `s' = n-s`, recovery-parity flipped) without ever possessing the miner's private key, and submit both as a `PoisonMicroblock` report.

### Finding Description
The claimed invariant — "a recorded poison report implies the pubkey-hash's private key actually signed two divergent microblocks" — is broken.

- `check_microblock_header_signer` (`stackslib/src/chainstate/stacks/db/transactions.rs:686-713`) computes `pkh1 = mblock_hdr_1.check_recover_pubkey()` and `pkh2 = mblock_hdr_2.check_recover_pubkey()` and only requires `pkh1 == pkh2`. It never compares `tx_merkle_root`, `sequence`, or any other field between the two headers for actual divergence. [1](#0-0) 

- `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs:722-856`), the consensus-critical entry point invoked from `ClarityTransactionConnection::run_poison_microblock`, calls only `check_microblock_header_signer` before recording the report via `insert_microblock_poison`. It performs no additional structural-inequality check between `mblock_header_1` and `mblock_header_2`. [2](#0-1) [3](#0-2) 

- `check_recover_pubkey` (`stacks-codec/src/transaction.rs:2598-2616`) uses `recover_to_pubkey_without_validating_low_s`, i.e. it recovers a public key from *any* recoverable signature regardless of low-S normalization, which is precisely the property that malleated (high-S) signatures rely on. [4](#0-3) 

- The repo itself contains a signature-malleation helper, `malleablize_signature`, whose comment states it "recovers to the same public key ... without changing its execution," demonstrating that any valid signature can be transformed into a distinct-byte, still-recovering signature with no private-key access. [5](#0-4) 

- The existing test `process_poison_microblock_same_block` already demonstrates the design gap: it calls `make_signed_microblock` twice with the *same key, same content* (`BlockHeaderHash([0x11;32])`, sequence `123`), producing two headers that differ only in signature bytes (`assert!(mblock_1 != mblock_2)`), and the poison-report is accepted and recorded — with no assertion that `tx_merkle_root` differs between the two headers. [6](#0-5) 

- The only place that checks any structural relationship between the two headers is the *mempool admission* filter (`stackslib/src/chainstate/stacks/db/blocks.rs:6844-6867`), and even that only requires `sequence`, `prev_block`, and `version` to match and `pkh1 == pkh2` — it never compares `tx_merkle_root`, so it is trivially satisfied by two headers with identical content and different signature bytes. [7](#0-6) 

**Exploit flow**: An unprivileged attacker observes one legitimately broadcast, valid `StacksMicroblockHeader` (public gossip data) signed by a target miner's microblock key. The attacker computes `malleablize_signature` (or, more simply, waits/asks the miner to resign the identical unsigned header body twice, since ECDSA nonces are randomized and this is already accepted per the existing test) to obtain a second signature blob over the exact same header content that recovers to the same `Hash160`. The attacker builds `TransactionPayload::PoisonMicroblock(header, malleated_header)`, submits it, it passes mempool admission (`blocks.rs:6844-6867`) and on-chain processing (`handle_poison_microblock`), and `insert_microblock_poison` records a slash for a miner who produced only a single microblock and never equivocated.

### Impact Explanation
This causes a reward mis-payment: the poison-report mechanism is designed to divert the "cheating" miner's coinbase reward (or a commission of it) to the reporter as punishment for double-signing. Because the equality check is satisfiable without any genuine fork, an honest miner who never produced two divergent microblocks can be falsely reported and penalized, and the attacker (reporter) collects a reward/commission they did not earn. This is block-reward theft from an honest, non-equivocating miner, bounded to the affected miner's slashed/matured reward — this fits the "High" category (poison/reward mis-payment bounded to a specific miner's reward) more precisely than a chain-split, since it does not directly cause two honest nodes to disagree on the chain tip (both nodes will deterministically accept the same malformed-but-passing PoisonMicroblock transaction and record the same report) — the harm is a wrongful/consensus-agreed reward transfer, not consensus divergence.

### Likelihood Explanation
No majority stake, no privileged role, and no access to the miner's private key are required — only public knowledge of one previously broadcast microblock header, which is routinely available via microblock relay/gossip. The signature malleation transform is a handful of big-integer subtraction operations, and the repo already contains a nearly identical helper (`malleablize_signature`) demonstrating its correctness. The attack is repeatable against every miner whose microblock pubkey hash and one signed header are observable, at essentially zero cost (just the poison-microblock transaction fee).

### Recommendation
Require the two `StacksMicroblockHeader`s in `check_microblock_header_signer`/`handle_poison_microblock` to differ meaningfully (e.g., have different `tx_merkle_root`, or otherwise represent genuinely distinct, non-malleable commitments) in addition to `pkh1 == pkh2`, and/or enforce low-S normalization in `check_recover_pubkey` (use `recover_to_pubkey` instead of `recover_to_pubkey_without_validating_low_s`) so that only one canonical signature is ever considered valid for a given header body, eliminating the malleability-derived "second signature" entirely.

### Proof of Concept
Rust integration test plan (extending `stackslib/src/chainstate/stacks/db/transactions.rs` test module):
1. Build a single `StacksMicroblockHeader` with fixed `sequence`, `prev_block`, `tx_merkle_root`, sign it with `block_privk` to get `mblock_1`.
2. Call `malleablize_signature(&mblock_1.header.signature)` (as already implemented in `stackslib/src/chainstate/nakamoto/tests/node.rs`) to produce `mblock_2` = a clone of `mblock_1.header` with only the `signature` field replaced.
3. Assert `mblock_1.header.tx_merkle_root == mblock_2.tx_merkle_root` (same content) but `mblock_1.header.signature != mblock_2.signature` (different bytes).
4. Assert `mblock_1.header.check_recover_pubkey().unwrap() == mblock_2.check_recover_pubkey().unwrap()` (both recover to the same `Hash160`, proving the "double-sign" equality is satisfied despite no real fork).
5. Register the pubkey hash via `StacksChainState::insert_microblock_pubkey_hash`, build and sign a `TransactionPayload::PoisonMicroblock(mblock_1.header, mblock_2)` from a reporter key, process it via `StacksChainState::process_transaction`, and assert `StacksChainState::get_poison_microblock_report` returns `Some((reporter_addr, sequence))`, proving a slash was recorded for a miner that never produced two divergent microblocks.

                &pkh1, &pkh2
            );

            return Err(Error::InvalidStacksTransaction(msg, false));

    }

    pub fn check_recover_pubkey(&self) -> Result<Hash160, AuthError> {
        let mut bytes = vec![];
        self.serialize(&mut bytes, true)
            .expect("BUG: failed to serialize to a vec");
        let digest = Sha512Trunc256Sum::from_data(&bytes[..]);

            &self.signature,
        )

            AuthError::VerifyingError(
                "Failed to verify signature: failed to recover public key".to_string(),
            )
        })?;

        pubk.set_compressed(true);
        Ok(Hash160::from_node_public_key(&pubk))
    }

/// high-S/low-S complement `s' = n - s`, with the recovery id's parity bit
/// flipped. It recovers to the same public key, so the signature remains valid,
/// but its bytes (and any hash committing to them) change. Used to construct
/// malleablized blocks: flipping the miner signature changes a block's id
/// without changing its execution.
fn malleablize_signature(sig: &MessageSignature) -> MessageSignature {
    // secp256k1 group order `n`, big-endian.
    const SECP256K1_ORDER_BE: [u8; 32] = [
        0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF, 0xFF,
        0xFE, 0xBA, 0xAE, 0xDC, 0xE6, 0xAF, 0x48, 0xA0, 0x3B, 0xBF, 0xD2, 0x5E, 0x8C, 0xD0, 0x36,
        0x41, 0x41,
    ];
    // MessageSignature layout: [recovery_id (1)][r (32)][s (32)].
    let mut bytes = sig.0;
    // s' = n - s, as a 32-byte big-endian subtraction.
    let mut borrow = 0i16;
    for i in (0..32).rev() {
        let diff = SECP256K1_ORDER_BE[i] as i16 - bytes[33 + i] as i16 - borrow;
        let (val, next_borrow) = if diff < 0 { (diff + 256, 1) } else { (diff, 0) };
        bytes[33 + i] = val as u8;
        borrow = next_borrow;
    }
    // Negating s flips the parity of R, so flip the recovery id's low bit.
    bytes[0] ^= 0x01;
    MessageSignature(bytes)
}
