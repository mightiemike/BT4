## Title
Unvalidated minimal token balances in `ExchangeCreateActuator` allow an unprivileged user to create a malfunctioning/degenerate Bancor-curve `Exchange` pool - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
Java-tron's built-in TRC10 `Exchange` feature (a Bancor-formula AMM analogous to Timeswap's pair) lets any account create a new trading pool via `ExchangeCreateContract`. The `ExchangeCreateActuator` only checks that `firstTokenBalance` and `secondTokenBalance` are strictly greater than zero, with no minimum-liquidity/ratio validation, mirroring the root cause of the Timeswap `mint()`/`state.y` finding, where an attacker can seed a pool with a degenerate, extremely small balance.

### Finding Description
In `ExchangeCreateActuator.doValidate()`, the only sanity checks on the initial pool reserves are: [1](#0-0) 

```java
if (Arrays.equals(firstTokenID, secondTokenID)) {
  throw new ContractValidateException("cannot exchange same tokens");
}
if (firstTokenBalance <= 0 || secondTokenBalance <= 0) {
  throw new ContractValidateException("token balance must greater than zero");
}
long balanceLimit = dynamicStore.getExchangeBalanceLimit();
if (firstTokenBalance > balanceLimit || secondTokenBalance > balanceLimit) {
  throw new ContractValidateException("token balance must less than " + balanceLimit);
}
```

Any account can create a new `Exchange` with `firstTokenBalance = 1` and `secondTokenBalance = balanceLimit` (or vice versa), which is exactly the analog of Timeswap allowing `state.y` to be seeded at "1 wei." There is no minimum-reserve or minimum-ratio requirement (comparable to the recommended `2**32/10000` floor in the Timeswap report).

This extreme initial ratio is then fed directly into the Bancor pricing engine in `ExchangeCapsule.transaction()` / `ExchangeProcessor`: [2](#0-1) 

which calls the double-precision power-curve math: [3](#0-2) 

With one reserve at `1` and the other near `balanceLimit`, `quant/newBalance` and `supplyQuant/supply` ratios become pathological, causing `Maths.pow` to return values that round to `0` (via the final `(long) issuedSupply`/`(long) exchangeBalance` truncation) or to values that make subsequent trades round to zero/negative deltas. Once such a degenerate pool is created, all pricing through `ExchangeTransactionActuator` (`token quant`/`expected` checks in lines 217-221) will behave unpredictably or become effectively frozen (any trade returns `0` tokens and fails the `anotherTokenQuant < tokenExpected` check), permanently bricking the pool — the same "can only be abandoned" state described in the report.

There is also no restriction preventing multiple `Exchange` pools from being created for the same token pair (only same-token self-pairing is blocked), so an attacker can front-run a legitimate `ExchangeCreateContract` for a meaningful token pair by broadcasting their own degenerate pool first, since `ExchangeStore`/`ExchangeV2Store` keys are simply incrementing `exchange_id` values with no pair uniqueness enforcement, as seen in `execute()`: [4](#0-3) 

### Impact Explanation
This is an invalid-state/functional-halt issue reachable by any unprivileged account holding minimal TRX/TRC10 balance (only the create fee plus 1 unit of a token is needed). The impact is:
- Permanent malfunction of a specific `Exchange` pool (broken pricing / stuck trades), matching the "Medium" severity classification of the original Timeswap finding.
- Griefing/front-running potential: an attacker can pre-empt a meaningful token pair (e.g., a platform's intended TRX/TokenX market) with a near-worthless, tiny-liquidity pool bearing a low `exchange_id`, forcing users/integrators who reference exchanges by pair or expect the "first" pool for a pair to interact with the broken one.
- No funds are directly stolen from third parties in this specific path (the attacker only spends their own tiny reserve), but it degrades protocol usability/integrity of the on-chain AMM feature and can be used for denial-of-service against expected pair semantics.

### Likelihood Explanation
Likelihood is high: `ExchangeCreateContract` is a standard, unprivileged wallet-level transaction; no special permissions, proposals, or committee actions are required. The fee is fixed and the token balance requirement is only `>0`, so exploitation is trivial and cheap (1 unit of any TRC10/TRX plus the create fee).

### Recommendation
Add a minimum-liquidity/minimum-ratio validation in `ExchangeCreateActuator.doValidate()`, analogous to the report's suggested floor for `state.y`:
- Enforce a minimum absolute value for `firstTokenBalance` and `secondTokenBalance` (e.g., a `MIN_TOKEN_BALANCE` chain parameter), and/or
- Enforce a maximum allowed ratio between `firstTokenBalance` and `secondTokenBalance` (e.g., reject balances differing by more than a configurable order of magnitude) to prevent degenerate seed ratios from being accepted by the Bancor-curve calculations in `ExchangeProcessor`.

### Proof of Concept
1. Attacker account holds ≥ create fee (`calcFee()`) plus 1 unit of `TokenA` and a large amount of `TokenB` (or TRX) up to `dynamicStore.getExchangeBalanceLimit()`.
2. Attacker submits `ExchangeCreateContract` with `first_token_balance = 1`, `second_token_balance = balanceLimit`.
3. `ExchangeCreateActuator.doValidate()` passes because `1 > 0` and `balanceLimit <= balanceLimit`, as shown in lines 201-208 above.
4. `ExchangeCreateActuator.execute()` persists the pool with this skewed ratio via `exchangeCapsuleV2.setBalance(firstTokenBalance, secondTokenBalance)`.
5. Any subsequent `ExchangeTransactionContract` against this pool calls `ExchangeCapsule.transaction()` → `ExchangeProcessor.exchange()`, where the extreme ratio causes `Maths.pow` results to truncate to `0` on the `(long)` cast, so `anotherTokenQuant` returns `0`, which fails the caller's `expected` check in `ExchangeTransactionActuator.doValidate()` (lines 217-221), rendering the pool unusable/malfunctioning going forward.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
