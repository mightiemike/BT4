This confirms the rounding-error pattern analogous to the RubiconMarket `buy()` bug in java-tron's TRC10 exchange order matching (`MarketSellAssetActuator`).

### Title
Floor-division rounding in TRC10 market order matching lets a taker underpay relative to the exact price ratio - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the amount a taker must pay a maker using integer floor division via `MarketUtils.multiplyAndDivide`, while the amount the taker receives is fixed at the maker's full remaining sell quantity. Because the "amount paid" side is rounded down and the "amount received" side is exact, a taker can consistently receive slightly more value than what they pay, exactly mirroring the RubiconMarket `buy()` rounding bug where `spend` is rounded down.

### Finding Description
In the `taker > maker` branch of `matchSingleOrder`, the taker receives the maker's entire remaining sell-token balance exactly: [1](#0-0) 
while the amount debited from the taker (paid to the maker) is computed with `MarketUtils.multiplyAndDivide`, which performs `floorDiv`: [2](#0-1) 
`multiplyAndDivide` truncates towards zero (`floorDiv`), never rounding up: [3](#0-2) 
The truncated `makerBuyTokenQuantityReceive` is what actually gets subtracted from the taker's remaining sell-side balance and credited to the maker: [4](#0-3) 
and both sides are then settled by directly crediting accounts based on these numbers: [5](#0-4) 
This is structurally identical to the RubiconMarket `buy()` bug: the quantity delivered to the "buyer" (taker) is computed exactly/independently, while the quantity the buyer must pay is computed via a rounded-down integer division. Every trade that consumes a maker order fully (`taker > maker` or `taker == maker` branches) is subject to this truncation, and the effect compounds per trade — an attacker can split a large intended trade into many small `MarketSellAsset` transactions against the same or multiple maker orders to repeatedly capture the rounding remainder.

### Impact Explanation
Each individual truncation error is bounded by 1 unit of the maker's buy-token (in the token's smallest denomination), so the per-trade profit is small. However, TRC10 tokens can be issued with very few decimal places (as low as 0 precision) or very small maker sell quantities, and there is no minimum-quantity restriction preventing an attacker from performing many small trades that walk through many maker orders (`MAX_MATCH_NUM` limits per-transaction matches, but not per-block/per-account transaction count). By repeating the attack across many transactions, an attacker can accumulate a measurable, repeatable, risk-free arbitrage profit extracted from maker liquidity, corrupting the intended exchange accounting invariant (taker should pay at least the maker's quoted price).

### Likelihood Explanation
The path is reachable directly from any anonymous account broadcasting a `MarketSellAssetContract` transaction and requires no special privilege — only an existing counter-order in the order book and sufficient token balance. Because the vulnerable computation triggers whenever a taker order fully consumes a maker's remaining quantity (a very common execution path), the conditions for triggering the rounding-favorable branch are easy to construct deliberately (place a small maker order, then send a taker order sized to consume it entirely).

### Recommendation
Round the amount the taker pays (`makerBuyTokenQuantityReceive` in the `taker > maker` and `taker == maker` branches) up (ceiling division) rather than down, or otherwise ensure that the taker never receives more value than the exact ratio it is paying for. This mirrors the RubiconMarket fix of rounding the `spend` calculation up instead of down.

### Proof of Concept
Conceptually (values not derived from a runnable in-repo test, since none is present in the index, but derived directly from the code paths cited above):
1. Attacker creates a maker order selling a small quantity `makerSellQuantity` of Token B for `makerBuyQuantity` of Token A, at a price ratio that does not divide evenly (e.g., `makerSellQuantity = 3`, `makerBuyQuantity = 10`).
2. A taker (the same attacker, from a different account) submits a `MarketSellAssetContract` selling Token A with `sellTokenQuantity` chosen so that `takerBuyTokenQuantityRemain >= makerSellRemainQuantity` (the `taker > maker` branch fires).
3. `takerBuyTokenQuantityReceive` is set to the maker's full `sellTokenQuantityRemain` (3, exact), while `makerBuyTokenQuantityReceive = multiplyAndDivide(3, 10, 3) `-style floor computation truncates fractional remainders that would otherwise require the taker to pay more of Token A.
4. Repeating this construction across many transactions (splitting a large trade into many small maker/taker order pairs) allows the attacker to accumulate more Token B than the exact price ratio entitles them to, at the expense of makers/the exchange's accounting invariant — the same "free tokens via repeated rounding" pattern as the original RubiconMarket exploit.

Note: I was not able to find an existing runnable PoC/test in the indexed codebase demonstrating actual measured profit numbers (gas-cost-adjusted), so the concrete numeric profitability (as in the original RubiconMarket report) would need to be validated with a live/testnet reproduction using a Devin session with full repo and node access.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
