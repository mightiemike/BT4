### Title
Restriction bypass: `ForbidTransferToContract` governance restriction is not enforced on internal TVM transfers (`suicide`/`selfdestruct`, internal `CALL` with value, `CREATE`) - ([File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java])

### Summary
`ForbidTransferToContract` is a governance-controlled restriction meant to prevent TRX from being sent to smart-contract addresses via top-level transactions. It is enforced only in `TransferActuator.validate()` [1](#0-0)  and `TransferAssetActuator.validate()` [2](#0-1) . However, all internal TVM value-transfer paths — `MUtil.transfer`/`MUtil.transferToken` (used by `callToAddress`, `createContractImpl`, `callToPrecompiledAddress`) and `Program.suicide`/`suicide2` — route through `VMUtils.validateForSmartContract`, which never checks `getForbidTransferToContract()`. This mirrors the reported bug class: a restriction implemented on one transfer entry point (`transfer`/`transferFrom` in the vault analog; `TransferContract`/`TransferAssetContract` here) is silently skipped when value moves through an alternate internal transfer mechanism (`_transfer` in the vault; `MUtil.transfer`/`suicide` here).

### Finding Description
`TransferActuator` and `TransferAssetActuator` explicitly check the dynamic parameter `ForbidTransferToContract` before allowing a top-level TRX/TRC10 transfer to an account whose type is `Contract`: [1](#0-0) [3](#0-2) 

But value transfers performed from inside the TVM — via `.transfer()`/`.send()`/low-level `call{value:}` (handled by `Program.callToAddress`) [4](#0-3) , via contract creation with an initial value (`Program.createContractImpl` → `VMActuator`) [5](#0-4) , and via `selfdestruct`/`suicide` [6](#0-5)  — all funnel through `MUtil.transfer`/`MUtil.transferToken`: [7](#0-6) 

which only calls `VMUtils.validateForSmartContract`. That validator checks address validity, self-transfer, account existence, asset existence/balance, and overflow — but contains no `ForbidTransferToContract` (or `AllowTvmCompatibleEvm` contract-version) check at all: [8](#0-7) 

Consequently, a smart contract (or a contract deployed with an initial value transfer, or a `suicide` beneficiary) can freely receive TRX/TRC10 that governance intended to forbid, exactly analogous to the vault bug where `cancelRedeemRequest`/`claimCancelRedeemRequest` used the internal `_transfer` and thereby skipped `_checkTransfer`.

### Impact Explanation
This allows any attacker-controlled or third-party smart contract to receive TRX/TRC10 tokens even while the `ForbidTransferToContract` governance switch is active — completely undermining a network-wide policy decision (typically put in place to prevent old, potentially-vulnerable contract versions such as V1 contracts from receiving/holding funds unexpectedly, or to enforce migration to `TriggerSmartContract`). Because the restriction is bypassable purely by using `CALL`/`transfer`/`selfdestruct` opcodes instead of a top-level `TransferContract`, this is reachable by any anonymous account broadcasting a normal `TriggerSmartContract` transaction that triggers a contract using these opcodes — no privileged role required.

### Likelihood Explanation
High likelihood: any user can deploy or invoke a trivial contract using Solidity `.transfer()`/`.send()`/`call{value:}()` or `selfdestruct()` to move TRX to any target contract address. No special permission, key compromise, or validator collusion is needed — only a normal `TriggerSmartContract` transaction.

### Recommendation
Add the same `ForbidTransferToContract` (and, where relevant, `AllowTvmCompatibleEvm` contract-version) checks that exist in `TransferActuator`/`TransferAssetActuator` into `VMUtils.validateForSmartContract` (or into `MUtil.transfer`/`transferToken` and `Program.suicide`/`suicide2`), so that internal TVM transfers to contract-type accounts are equally restricted when the governance flag is enabled.

### Proof of Concept
1. Governance enables `ForbidTransferToContract` (`getForbidTransferToContract() == 1`).
2. Attacker deploys/uses a contract `Attacker` with a function:
   ```solidity
   function drain(address payable target) public payable {
       target.transfer(msg.value); // or target.call{value: msg.value}("")
   }
   ```
3. Attacker calls `drain(targetContractAddress)` via a normal `TriggerSmartContract` transaction, sending TRX.
4. Execution reaches `Program.callToAddress` → `VMUtils.validateForSmartContract` (no `ForbidTransferToContract` check) → balance moved to `targetContractAddress` successfully, despite the same transfer being rejected if attempted via a top-level `TransferContract` (which would throw `"Cannot transfer TRX to a smartContract."`).
5. Equivalent PoC applies to `selfdestruct(targetContractAddress)` inside a contract with a nonzero balance.

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);

    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }

  public static boolean validateForSmartContract(Repository deposit, byte[] ownerAddress,
      byte[] toAddress, byte[] tokenId, long amount) throws ContractValidateException {
    if (deposit == null) {
      throw new ContractValidateException("No deposit!");
    }

    byte[] tokenIdWithoutLeadingZero = ByteUtil.stripLeadingZeroes(tokenId);

    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid ownerAddress");
    }
    if (!DecodeUtil.addressValid(toAddress)) {
      throw new ContractValidateException("Invalid toAddress");
    }

    if (amount <= 0) {
      throw new ContractValidateException("Amount must greater than 0.");
    }

    if (Arrays.equals(ownerAddress, toAddress)) {
      throw new ContractValidateException("Cannot transfer asset to yourself.");
    }

    AccountCapsule ownerAccount = deposit.getAccount(ownerAddress);
    if (ownerAccount == null) {
      throw new ContractValidateException("No owner account!");
    }

    if (deposit.getAssetIssue(tokenIdWithoutLeadingZero) == null) {
      throw new ContractValidateException("No asset !");
    }
    if (!Commons.getAssetIssueStoreFinal(deposit.getDynamicPropertiesStore(),
        deposit.getAssetIssueStore(), deposit.getAssetIssueV2Store())
        .has(tokenIdWithoutLeadingZero)) {
      throw new ContractValidateException("No asset !");
    }

    Long assetBalance = ownerAccount.getAsset(deposit.getDynamicPropertiesStore(),
            ByteArray.toStr(tokenIdWithoutLeadingZero));
    if (null == assetBalance || assetBalance <= 0) {
      throw new ContractValidateException("assetBalance must greater than 0.");
    }
    if (amount > assetBalance) {
      throw new ContractValidateException("assetBalance is not sufficient.");
    }

    AccountCapsule toAccount = deposit.getAccount(toAddress);
    if (toAccount != null) {
      assetBalance = toAccount.getAsset(deposit.getDynamicPropertiesStore(),
              ByteArray.toStr(tokenIdWithoutLeadingZero));
      if (assetBalance != null) {
        try {
          addExact(assetBalance, amount,
              VMConfig.disableJavaLangMath()); //check if overflow
        } catch (Exception e) {
          logger.debug(e.getMessage(), e);
          throw new ContractValidateException(e.getMessage());
        }
      }
    } else {
      throw new ContractValidateException(
          "Validate InternalTransfer error, no ToAccount. And not allowed to create account in smart contract.");
    }

    return true;
  }
}
