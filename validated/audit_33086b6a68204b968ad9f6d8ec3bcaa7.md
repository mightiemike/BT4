### Title
Unbounded array index in `WalletUtil.checkPermissionOperations` allows out-of-range `ContractType` to crash validation via `ArrayIndexOutOfBoundsException` - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
`WalletUtil.checkPermissionOperations` computes a bit index into a fixed 32-byte `operations` bitmap using `contract.getTypeValue()` (the raw protobuf enum value) without any bounds validation. Because protobuf enum fields accept arbitrary int32 values on the wire (unrecognized enum values are preserved and returned unclamped by `getTypeValue()`), a `Contract.type` field crafted with a value ≥ 256 causes `contractType / 8` to index past the 32-byte array, throwing an unhandled `ArrayIndexOutOfBoundsException` inside `ByteString.byteAt`.

### Finding Description
The vulnerable code is: [1](#0-0) 

`operations` is validated to be exactly 32 bytes (256 bits), but `contractType` — obtained via `contract.getTypeValue()` rather than the mapped `ContractType` enum — is never checked against this range before being used to compute `operations.byteAt(contractType / 8)`. Protobuf's open-enum wire semantics mean `getTypeValue()` returns whatever raw int32 was encoded on the wire for that field, regardless of whether it corresponds to a known `ContractType` value; `getType()` would map an unknown value to `UNRECOGNIZED`, but this code deliberately uses `getTypeValue()` and never checks it. An attacker can therefore hand-craft a `Transaction.Contract` with `type` set to, e.g., `300` via direct protobuf field manipulation (bypassing the Java builder's enum constraints, which only apply to generated-code call paths, not wire-level construction), producing `contractType/8 = 37`, which is out of bounds for the 32-byte `operations` array.

This path is only reached for accounts using multi-signature permissions (i.e., a `permission_id` set on the contract referencing a custom `Permission` with an `operations` bitmap), which any funded account can set up via `AccountPermissionUpdateContract`. Once such a permission exists, subsequent transactions using that permission trigger `checkPermissionOperations` during signature/permission validation.

### Impact Explanation
If this method is invoked before contract-type dispatch/validation (i.e., during permission/signature checking prior to actuator creation), the uncaught `ArrayIndexOutOfBoundsException` would propagate out of `checkPermissionOperations` as a `RuntimeException`, since only `PermissionException` is declared/caught by the method signature and no explicit `try/catch` for `ArrayIndexOutOfBoundsException` is present in this file. This matches a DoS-via-protocol-implementation impact class: a single crafted, funded, signed transaction could disrupt validation of that transaction, and if the exception propagates uncaught through the transaction-processing thread (rather than being converted to a rejected transaction), it could destabilize node/block processing.

### Likelihood Explanation
Exploitability requires: (1) an existing or attacker-created multisig account with a custom `Permission.operations` bitmap (achievable by any funded account via `AccountPermissionUpdateContract`, at normal fee cost), and (2) the ability to place an out-of-range raw int32 into the `Contract.type` wire field, which is legal under protobuf's open-enum wire format but is **not achievable through the standard Java protobuf builder API** (`Transaction.Contract.newBuilder().setType(ContractType)` only accepts declared enum constants). To exploit this, the attacker would need to serialize the `Contract.type` field manually at the wire level (e.g., writing a raw varint tag/value pair) rather than using the generated Java API, which is a nontrivial but feasible attack given TRON's protobuf-based wire format is well-documented and off-the-shelf protobuf libraries in other languages permit setting arbitrary enum wire values.

I could not fully verify from the available index whether `checkPermissionOperations` is invoked before or after any prior switch/dispatch on `contract.getType()` that might reject `UNRECOGNIZED` contract types earlier in the call chain (e.g., inside `TransactionCapsule`'s signature/permission validation flow, or `ActuatorFactory`/`ActuatorCreator` dispatch). If an earlier check already rejects unrecognized `ContractType` values before reaching this method, the practical reachability of this bug would be eliminated. This ordering could not be confirmed with the tools available in this session.

### Recommendation
Add an explicit bounds check in `checkPermissionOperations` before computing the bit index, e.g.:
```java
int contractType = contract.getTypeValue();
if (contractType < 0 || contractType >= operations.size() * 8) {
  throw new PermissionException("contract type " + contractType + " is out of range");
}
```
Additionally, validate `contract.getType() != ContractType.UNRECOGNIZED` (or equivalently bound-check `getTypeValue()`) as early as possible in the transaction ingestion/validation pipeline, before any permission or signature-weight logic is reached, so malformed/unknown contract types are rejected deterministically rather than relying on this single call site.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
