### Title
Silent `long` truncation via `BigInteger.longValue()` fallback in market order matching - ([File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java])

### Summary
The reported bug class (unsafe type-casts that truncate values without reverting, leading to attacker-favorable settlement/accounting results) has a structural analog in java-tron's TRC10 market/exchange order-matching logic. `MarketUtils.multiplyAndDivide` falls back to `BigInteger` arithmetic on `long` overflow, but ends the fallback path with `.longValue()` instead of `.longValueExact()`, silently truncating results that don't fit into a `long` rather than throwing.

### Finding Description
`MarketUtils.multiplyAndDivide` first attempts checked `long` math and, only on `ArithmeticException`, falls back to `BigInteger`: [1](#0-0) 

The final line `aBig.multiply(bBig).divide(cBig).longValue()` uses the unsafe `.longValue()` conversion (which truncates/wraps silently per Java semantics) instead of `.longValueExact()` (which throws `ArithmeticException` if the value doesn't fit). This function is used to compute the exchanged quantities during market order matching: [2](#0-1) [3](#0-2) [4](#0-3) 

`sellTokenQuantity`/`buyTokenQuantity` on orders are user-supplied `long` values (bounded only by TRC10 asset total-supply limits, which themselves can be close to `Long.MAX_VALUE`). Since `a * b` can reach up to roughly 2^126 and division by a small `c` (e.g. `makerBuyQuantity == 1`) may still leave a quotient far larger than `Long.MAX_VALUE`, the `.longValue()` truncation can produce an arbitrary wrapped `long` (potentially small, zero, or negative) instead of reverting the transaction. This computed value directly determines `takerBuyTokenQuantityRemain`/`makerBuyTokenQuantityReceive`, which are subsequently used to adjust order state and to transfer assets between accounts during settlement (analogous to the reported `getNetBalance`/invariant down-casting issue, where an unchecked numeric truncation feeds directly into balance-affecting logic).

I was not able to fully verify, within the available context, whether `MarketSellAssetActuator.validate()` imposes bounds on `sellTokenQuantity`/`buyTokenQuantity` tight enough to make the overflow-then-truncate scenario unreachable (the file is large and the specific bound checks weren't retrieved in the exploration window). This is a material open question for confirming exploitability.

### Impact Explanation
If reachable, this could allow a malicious pair of orders (or a single attacker acting as both maker and taker via colluding accounts, or crafting order quantities) to make the matching engine compute a wrapped/truncated exchange quantity rather than reverting on overflow. Because the result feeds into `setSellTokenQuantityRemain`, `addAssetAmountV2`/balance adjustments, and order state transitions, a wrapped value could result in a mismatch between the assets debited and credited — e.g., consuming an order without ever crediting the correct offsetting amount, or crediting the wrong (potentially favorable) amount to an attacker. This falls squarely in "underpriced-public-work/settlement" and "invalid-state divergence" impact categories, since token accounting for a public, unprivileged, permissionless feature (the TRC10 exchange/market) would be corrupted.

### Likelihood Explanation
Likelihood is **uncertain/moderate at best** without further verification. It requires: (1) the order-quantity validation in `MarketSellAssetActuator.validate()` to permit large enough imbalanced quantities such that `a*b/c` still exceeds `Long.MAX_VALUE` after division, and (2) an economically viable order-book state (asset total supply near `Long.MAX_VALUE`) to exist on chain. These are non-trivial preconditions, and TRC10 asset supplies are typically far below `Long.MAX_VALUE` in practice, which significantly reduces real-world likelihood. Without confirming the validate-path bounds, I cannot assert this is concretely exploitable — this is the weakest link in the analog and should be verified against `MarketSellAssetActuator.validate()`/`MarketOrderCapsule` bound checks before treating it as confirmed.

### Recommendation
Replace `.longValue()` with `.longValueExact()` in `MarketUtils.multiplyAndDivide`'s `BigInteger` fallback path so that any result which does not fit in a `long` causes the transaction to fail explicitly (e.g., via `ContractExeException`) rather than silently wrapping. Additionally, audit `MarketSellAssetActuator.validate()` to confirm/add explicit range checks on `sellTokenQuantity` and `buyTokenQuantity` so that the multiplication cannot realistically approach values where post-division truncation is possible, consistent with the general recommendation in the reference report to use safe (reverting) type-casts as the default rather than silently-truncating ones.

### Proof of Concept
Not constructed — this requires confirming order-quantity validation bounds in `MarketSellAssetActuator.validate()` (not fully retrieved in this investigation) to determine a concrete quantity combination that triggers `BigInteger` truncation in `multiplyAndDivide`. A full PoC would: (1) issue a TRC10 asset with a very large total supply, (2) create a maker sell order with `makerSellQuantity` near `Long.MAX_VALUE` and `makerBuyQuantity = 1`, (3) create a matching taker order with a large `sellTokenQuantityRemain`, and (4) observe whether `multiplyAndDivide` produces a wrapped/truncated result instead of throwing, and trace whether this corrupts the resulting asset transfer amounts.
