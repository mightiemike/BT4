### Title
State variable `assets` decremented after external token transfer instead of before — CEI violation in `redeem()` - (File: mainnet/contracts/vault/v0-vault-usdc.clar)

### Summary
`redeem()` in every Zest v2 vault contract (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) reads the liquidity guard values (`current-assets`, `available-assets`) once at the top of the function, performs the checks against those stale values, executes the external interaction (`send-underlying`), and only afterwards commits the invalidating state update (`var-set assets ...)`. This is the exact Checks-Effects-Interactions ordering flaw described in the referenced report: the accounting variable that should invalidate a repeat pass of the guard is mutated *after* the external call, not before it.

### Finding Description
In `redeem`, the guard values are bound once in the `let`, before any interaction: [1](#0-0) 

and the external transfer happens strictly before the effect that would invalidate those bound values for any nested/re-entrant execution: [2](#0-1) 

`UNDERLYING` is a hardcoded principal for the token contract that `send-underlying` calls into: [3](#0-2) 

The same structure (bind `current-assets`/`available-assets` before the external `send-underlying` call, decrement `assets` only after) is repeated identically across all six vault instances, e.g.: [4](#0-3) [5](#0-4) [6](#0-5) 

The value bound is `current-assets` (and `available-assets`, derived from it) via `(var-get assets)` at the top of `redeem`. The event that should invalidate it is the decrement of `assets` reflecting the just-redeemed liquidity. The later (mis-ordered) use is the fact that this invalidation happens only after `send-underlying`'s external call has already completed, meaning any nested call taking control flow during that external call would still observe the pre-decrement `assets`/`available-assets` values and pass the exact same `>= current-assets inkind` / `>= available-assets inkind` checks.

Under Clarity's evaluation order, `try!` forms execute sequentially and `contract-call?` to `UNDERLYING` is a genuine external call into another contract's code; if that call path (directly, or via a future upgrade of the underlying token contract, mirroring the mStable-factory upgradeability risk flagged in the source report) triggers a callback into this vault before returning, the callback would re-enter `redeem` (or `collateral-remove-redeem` in `market.clar`, which chains `collateral-remove` and `vault-redeem` in two separate steps) with the stale, not-yet-decremented `assets` state, exactly reproducing the `l1BurntAmountOf`/`claimedAmountOf` ordering bug from the report, just mapped onto `current-assets`/`assets`.

The report explicitly notes this exact class of risk is latent, not necessarily exploitable today, contingent on the interacted token gaining transfer callbacks or being upgraded — the same caveat applies here since `UNDERLYING` in `v0-vault-usdc.clar` is a specific external contract address whose upgradeability was not verified from available code.

### Impact Explanation
If the external call in `send-underlying` were to gain (via callback-capable token semantics or a token-contract upgrade) the ability to hand control flow back to the caller before returning, an attacker could re-enter `redeem` and pass the liquidity/balance guards multiple times against the same underlying pool of `assets`, draining vault liquidity beyond what a single redemption should permit — this is a direct theft of user/protocol funds at rest, i.e., Critical impact if the precondition (callback-capable underlying) is ever met.

### Likelihood Explanation
Low under current conditions, mirroring the original report's own conclusion: it requires the hardcoded `UNDERLYING` token contract to trigger a callback to the vault during `ft-transfer?`/transfer execution, which none of the current SIP-010 tokens used by Zest are known to do. However, since `UNDERLYING` addresses are external, potentially-proxied contracts not controlled by this codebase, the ordering bug itself is present in code today and would become live the moment the underlying token's transfer semantics change — matching the exact conditional-likelihood framing accepted in the source report.

### Recommendation
Reorder `redeem()` (and the equivalent pattern in every vault file) so the effect (`var-set assets (- current-assets inkind)`) is committed before the external interaction (`send-underlying`), or add an explicit reentrancy guard (mirroring the existing `in-flashloan` flag pattern already used elsewhere in the vaults) around `redeem`/`deposit`/`system-borrow`/`system-repay` so that any nested call during the external transfer is rejected rather than allowed to re-read stale guard state.

### Proof of Concept
1. Assume (per the same assumption the source report made about the mStable factory) that the token at `UNDERLYING` (`'SP120SBRBQJ00MCWS7TM5R8WJNTTKD5K0HFRC2CNE.usdcx`) is upgraded to a SIP-010 implementation whose transfer function calls back into the recipient (analogous to ERC-777 semantics).
2. Attacker calls `redeem(amount, min-out, recipient=attacker-controlled-contract)` on `v0-vault-usdc.clar`. `current-assets` and `available-assets` are bound from `(var-get assets)`.
3. Guards pass; `ft-burn?` burns the attacker's zUSDC shares; `send-underlying` calls into the (now callback-capable) `UNDERLYING` token to transfer `inkind` USDC to `recipient`.
4. During that external call, the attacker-controlled `recipient` contract re-enters `redeem` with a second batch of zUSDC shares. Because `var-set assets (- current-assets inkind)` from step 3's call has not yet executed, the reentrant call's own `current-assets`/`available-assets` bindings are still the pre-decrement values, so its guards pass even though the pool has already sent out `inkind` from step 3.
5. Both calls complete, each sending `inkind` underlying tokens to the attacker, while `assets` is only decremented twice sequentially — but the liquidity check used to authorize the second `send-underlying` was made against balances that hadn't accounted for the first drain, allowing the attacker to withdraw more underlying than the vault's actual available liquidity permits.

(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    (states (var-get pause-states))
    (u (try! (accrue)))
    (account contract-caller)
    (current-assets (var-get assets))
    (balance (get-balance-internal account))
    (balance-check (asserts! (>= balance amount) ERR-INSUFFICIENT-BALANCE))
    (available-assets (get-available-assets))
    (inkind (convert-to-assets-preview amount)))

  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  (asserts! (>= available-assets inkind) ERR-INSUFFICIENT-LIQUIDITY)
