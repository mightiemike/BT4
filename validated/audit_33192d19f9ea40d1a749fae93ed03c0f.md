### Title
Unbounded recursion in `bytecode_hash_node` during compiled class hash computation can crash the Sierra compiler service on a crafted declared class - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
The CVE describes a crash in BinUtils' `d_discriminator` demangler caused by unbounded recursive descent over attacker-crafted input, with no depth guard, leading to stack-overflow DoS. The closest reachable analog in this codebase is the compiled-class-hash bytecode-segment hashing routine, which recursively walks a `NestedIntList` tree produced from a user-declared Sierra program's compiled CASM with no recursion-depth limit, and this traversal happens in-process, outside the resource-limited compilation subprocess.

### Finding Description
When a class is declared, `SierraCompiler::compile` invokes the sandboxed Sierra→CASM compiler subprocess (bounded by `max_cpu_time`/`max_memory_usage`/`max_bytecode_size`), but then computes the compiled class hash directly in the calling process, unsandboxed: [1](#0-0) 

That hash computation calls into `HashableCompiledClass::hash`, which for `CasmContractClass` recurses over `bytecode_segment_lengths` (a `NestedIntList` tree) via `bytecode_hash_node`, with no depth bound or iterative rewrite: [2](#0-1) 

The `max_bytecode_size` limit enforced during subprocess compilation bounds only the total flattened bytecode length, not the *depth* of the segment tree produced by the compiler for deeply/sequentially nested control flow (e.g., long chains of nested branches or match arms). Because `bytecode_hash_node` recurses once per tree level with no explicit depth check, a Sierra program engineered to produce a segment tree many thousands of levels deep — while still satisfying the bytecode-size cap — can drive the recursion deep enough to overflow the call stack of the (non-sandboxed) sierra-compiler process, analogous to the demangler's unbounded `d_discriminator` recursion crashing on crafted input.

This differs qualitatively from the Cairo-VM/Cairo-Native recursion cases found elsewhere in the repo (e.g. `recursive_syscall`, `test_stack_overflow`), which are metered by Sierra gas / step limits and can only revert the transaction, not crash the host process: [3](#0-2) 
The `bytecode_hash_node` recursion, by contrast, executes as plain native Rust recursion with no gas metering, no depth cap, and outside the CPU/memory-limited subprocess boundary that protects compilation itself.

### Impact Explanation
If the segment-tree depth can be forced high enough (this specific depth threshold was not empirically verified in this analysis — see Likelihood), a single class declaration could crash the sierra-compiler component's process with a native stack overflow. Since class declaration/compilation is on the path required to admit new declare transactions into blocks, a crash or repeated crash-restart loop of this component would degrade or halt the network's ability to process new declare transactions, and depending on deployment topology (dedicated `SierraCompiler` service vs. co-located with class manager), could affect broader block-building availability.

### Likelihood Explanation
Medium. Reaching this requires an attacker-controlled Sierra program whose *compiled* CASM bytecode-segment structure is deep, not merely large — i.e., depth induced by the compiler's segmentation algorithm (per-function/per-branch nesting) rather than by raw bytecode size, which is already bounded by `max_bytecode_size`. I could not fully verify, within available context, how deep a `bytecode_segment_lengths` tree the `cairo-lang-sierra-to-casm` crate can be induced to produce for a bytecode-size-bounded program, nor the exact native stack depth needed to overflow the sierra-compiler process's default thread stack. This uncertainty should be resolved by testing/fuzzing the compiler's segment-length generation for maximal nesting depth under `DEFAULT_MAX_BYTECODE_SIZE`.

### Recommendation
- Convert `bytecode_hash_node` (and its Cairo-side equivalents `hash_entry_points_inner`/`bytecode_hash_internal_node`, which are similarly unbounded recursions) to an iterative, explicit-stack traversal, or add an explicit maximum-depth check that rejects a `NestedIntList` exceeding a safe bound before hashing.
- Enforce a maximum nesting depth on `bytecode_segment_lengths` as part of `validate_class_length`/class validation in `apollo_class_manager`, independent of the flat bytecode-size cap.
- Run the post-compilation hash computation (`executable_class.hash(...)`) under the same resource-limited execution context (subprocess or bounded-stack thread) as the Sierra→CASM compilation step, rather than directly in the compiler service's main thread.

### Proof of Concept
Conceptual (not executed/verified against the real cairo-lang-sierra-to-casm segmentation algorithm):
1. Author a Sierra contract whose control flow is engineered to force the Sierra→CASM compiler to emit a deeply, sequentially nested `NestedIntList` bytecode-segment structure (e.g., long chains of nested conditional/match branches), while keeping total bytecode under `DEFAULT_MAX_BYTECODE_SIZE`.
2. Submit the class via a declare transaction / `ClassManager::add_class`.
3. `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:60-74`) successfully compiles the class in the sandboxed subprocess (within size/CPU/memory limits), then calls `executable_class.hash(&HashVersion::V2)` in the parent process.
4. `hash_inner` → `bytecode_hash` → `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:96-132`) recurses once per segment-tree level; if depth is large enough, the sierra-compiler process's stack is exhausted and the process crashes. [4](#0-3)

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

/// Tests that Native can handle deep recursion calls without causing a stack overflow.
/// The recursive function must be complex enough to prevent the compiler from optimizing it into a
/// loop. This function was manually tested with increased maximum gas to ensure it reaches a stack
/// overflow.

/// Note: Testing the VM is unnecessary here as it simulates the stack where the stack in the heap

fn test_stack_overflow(#[values(true, false)] concurrency_enabled: bool) {
    let block_context = BlockContext::create_for_account_testing();
    let cairo_version = CairoVersion::Cairo1(RunnableCairo1::Native);
    let TestInitData { state, account_address, contract_address, mut nonce_manager } =
        create_test_init_data(&block_context.chain_info, cairo_version);
    let depth = felt!(1000000_u128);
    let entry_point_args = vec![depth];
    let calldata = create_calldata(contract_address, "test_stack_overflow", &entry_point_args);
    let invoke_tx = executable_invoke_tx(invoke_tx_args! {
        sender_address: account_address,
        calldata,
        nonce: nonce_manager.next(account_address),
        resource_bounds: ValidResourceBounds::create_for_testing_no_fee_enforcement(),
    });
    let account_tx = AccountTransaction::new_for_sequencing(invoke_tx);
    // Ensure the transaction is allocated the maximum gas limits.
    assert!(
        account_tx.resource_bounds().get_l2_bounds().max_amount
            >= block_context.versioned_constants.os_constants.execute_max_sierra_gas
                + block_context.versioned_constants.os_constants.validate_max_sierra_gas
    );
    // Run.
    let config = TransactionExecutorConfig::create_for_testing(concurrency_enabled);
    let mut executor = TransactionExecutor::new(state, block_context, config);
    let results = executor.execute_txs(&[account_tx.into()], None);

    let (tx_execution_info, _state_diff) = results[0].as_ref().unwrap();
    assert!(tx_execution_info.is_reverted());
    let err = tx_execution_info.revert_error.clone().unwrap().to_string();

    // Recursion is terminated by resource bounds before stack overflow occurs.
    assert!(err.contains("'Out of gas'"));
}
