## Analog Identified: Front-Run Account Pre-Creation Breaks the Gasless Bootstrap Path

### Title
Attacker-Triggered Account Pre-Creation Bypasses the Zero-Value Bootstrap Verification in `AccountInitDecorator`, Permanently Blocking a Victim's First Gasless Transaction — (File: `app/ante/account_init_decorator.go`)

### Summary
The Phoenix bug class is: an account-creation primitive that behaves differently (and fails/produces wrong results) if the target account already has state (lamports) before the primitive runs, letting an attacker pre-empt legitimate account creation. Push Chain's `AccountInitDecorator` has the same shape: its entire bootstrap logic branches on `AccountKeeper.HasAccount`, and an unprivileged attacker can flip that boolean ahead of the victim's first transaction by simply sending funds to the victim's address, which causes the Cosmos SDK bank module to auto-create the recipient's `BaseAccount` (with a real, non-zero `AccountNumber`). This silently reroutes the victim's transaction away from the special zero-value verification path into the standard signature-verification pipeline, which will reject it.

### Finding Description
`AccountInitDecorator.AnteHandle` exists specifically so a brand-new signer (e.g. a freshly keygen'd Universal Validator hot key, per the documented rationale "lets a freshly-keygen'd Universal Validator hot key vote on its very first tx, without anyone first having to fund it") can submit its first gasless message without ever having appeared on-chain: [1](#0-0) 

The branch taken is entirely determined by `aid.ak.HasAccount(ctx, newAccAddr)`. When the account does **not** yet exist, `verifySignatureForNewAccount` hard-codes `accNum = 0` and `accSequence = 0` for signature verification: [2](#0-1) 

This 0/0 convention is the documented, intended bootstrap contract for this feature (see `app/README.md`): [3](#0-2) 

The problem: `HasAccount` is not attacker-resistant. In the Cosmos SDK, `x/bank`'s `SendCoins` auto-vivifies the recipient's `x/auth` account (assigning it the next sequential, non-zero `AccountNumber`) the first time it receives any balance — this is a completely permissionless, unprivileged action (an ordinary `MsgSend`, even for a dust amount). Once that happens, `HasAccount` flips to `true` for the victim's address, and the decorator falls through to `next(ctx, tx, simulate)` instead of taking the bootstrap branch: [4](#0-3) 

Downstream, the normal Cosmos ante chain (`SetPubKeyDecorator` → `SigVerificationDecorator`) verifies the signature against the account's **real, persisted** `AccountNumber` (whatever value the attacker's pre-funding transfer caused it to be assigned) and not `0`. A victim (e.g. a Universal Validator hot key) that follows the documented bootstrap convention — sign with `account_number=0, sequence=0` because it has never touched the chain and cannot query a nonexistent account — will now fail signature verification with `ErrUnauthorized`, because the account is no longer "new" from the decorator's point of view even though the victim never used it.

The whole point of `AccountInitDecorator` was to remove the need for any prior on-chain interaction/funding before a UV hot key's first vote; an attacker trivially defeats that guarantee for any address whose gasless-eligible role is known in advance (UV hotkeys are registered on-chain via `x/uvalidator`/`authz` grants before their first vote, as seen in the test setup wiring `uniValAddr` grants ahead of any vote): [5](#0-4) 

### Impact Explanation
This is a denial-of-service on account/session bootstrapping reachable by any unprivileged external actor at negligible cost (the price of one `MsgSend` of a minimal amount):
- A newly onboarded Universal Validator hot key (or any first-time gasless sender, e.g. a fresh UEA-related signer relying on the same bootstrap decorator) can be permanently denied its first vote/tx if it strictly follows the documented `account_number=0/sequence=0` bootstrap convention, since the attacker can pre-empt account creation before the victim ever transacts.
- Because `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration` are all gasless message types gated by this exact decorator, targeted griefing of specific UV hotkeys can delay or disrupt ballot finalization and TSS coordination participation for those validators until an operator manually detects and corrects the account number mismatch — directly touching the "honest-validator finalization path" and "TSS coordination" invariants in scope.
- This is not a privileged-actor or malicious-validator scenario: the attacker only needs to know (or guess) a target address and send it any amount of `upc`, both fully permissionless actions.

### Likelihood Explanation
High feasibility, low cost:
- UV hotkey addresses (and other gasless-first-use addresses) become observable on-chain before their first gasless transaction (e.g. via `AddUniversalValidator`/authz grant registration events), giving an attacker a concrete target list.
- The griefing transaction itself is a standard, cheap `MsgSend`.
- The victim's client tooling is exactly designed to rely on the `0/0` bootstrap convention (that is the documented purpose of this decorator), making the failure mode systematic rather than a corner case.

### Recommendation
Do not use `HasAccount` alone to gate the bootstrap branch. Instead, determine "new account" status based on whether the account has ever had a `PubKey` set (or another attacker-uncontrollable signal), and/or verify the signature against both the account's actual persisted `AccountNumber` and the `0` fallback, accepting whichever matches, before deciding definitively to reject. At minimum, the decorator should tolerate an account that exists but has no pubkey and sequence `0` by treating it the same as "new" for signature verification purposes, since such accounts could only have been created by unrelated third-party transfers, not by the signer themselves.

### Proof of Concept
1. Determine (or predict) the `push`-bech32 address that will be used as the hot key for a soon-to-be-registered Universal Validator, or any other address expected to submit its first transaction via a gasless message type.
2. As an unprivileged attacker, submit an ordinary `MsgSend` of the minimal denomination (`1upc`) to that address. This causes `x/bank`'s `SendCoins` to auto-create a `BaseAccount` for it with the next sequential `AccountNumber` (e.g. `47`), sequence `0`.
3. The victim later submits their legitimate first gasless transaction (e.g. `MsgVoteInbound`), signed per the documented convention with `account_number=0, sequence=0`, since from their perspective this is their genuinely first on-chain interaction.
4. In `AccountInitDecorator.AnteHandle`, `aid.ak.HasAccount(ctx, newAccAddr)` returns `true` (due to step 2), so the function calls `next(ctx, tx, simulate)` instead of `verifySignatureForNewAccount`.
5. `SetPubKeyDecorator`/`SigVerificationDecorator` verify the signature against `SignerData{AccountNumber: 47, Sequence: 0}`, which does not match the victim's signature (signed against `AccountNumber: 0`). The transaction is rejected with `ErrUnauthorized`, and the victim cannot activate their account/participate in voting until they detect the mismatch and manually re-sign using the (attacker-influenced) real account number.
