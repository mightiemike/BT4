### Title
Stale liquidity-index cache in `market.clar` not invalidated when a vault's `lindex` is force-updated by `socialize-debt` — (File: `mainnet/contracts/market/v0-4-market.clar`, `mainnet/contracts/vault/v0-vault-ststx.clar`)

### Summary
`market.clar` caches each vault's liquidity index (`lindex`/`index`) per block timestamp in `index-cache` to avoid repeated cross-contract calls to the vaults. The cache is only ever refreshed through `accrue-and-cache`, which calls `vault-accrue`. However, the vault's `lindex` can also be mutated directly by `socialize-debt`, a path that bypasses `accrue-and-cache` entirely and never touches `index-cache`. Because the cache key is `{timestamp: stacks-block-time, aid}` and not tied to the vault's actual state, any cache entry populated earlier in the same block (or same transaction, if `socialize-debt` is invoked mid-flow) becomes stale the moment `socialize-debt` runs, yet subsequent reads within that same timestamp still return the old cached values.

### Finding Description
`accrue-and-cache` in `market.clar` implements the cache: [1](#0-0) 

This cache is read by `resolve-ztoken` when pricing zToken collateral, via an `unwrap!` on `get-cached-indexes` (no fallback to a fresh vault call): [2](#0-1) 

It is also read directly for debt notional value in `calculate-asset-notional-value`: [3](#0-2) 

Separately, `socialize-debt` in the vault contracts writes `lindex`, `principal-scaled`, `total-borrowed`, and `assets` directly via `var-set`, with no call into `accrue-and-cache` and no invalidation of `market.clar`'s `index-cache`: [4](#0-3) 

`market.clar` exposes this vault function through `vault-socialize-debt`, so it is reachable from the market layer that also drives price/notional evaluation: [5](#0-4) 

Because `index-cache` is keyed only by `{timestamp, aid}` (block timestamp, not a fresh state hash), once any operation in the block populates the cache for a given `aid` (e.g. a debt accrual triggered by a borrow, or `accrue-user-collateral`), the cached `{index, lindex}` pair is considered valid for the rest of that same timestamp — even though `socialize-debt` can change the vault's real `lindex` afterward within the same block/transaction sequence. Any subsequent notional-value or zToken price computation that hits the cache (rather than re-querying the vault) will use the pre-`socialize-debt` index, misvaluing collateral or debt.

### Impact Explanation
If a position's collateral or debt notional value is computed from a stale (pre-`socialize-debt`) `lindex`/`index` after the real vault state has moved, the health-factor calculation used for borrow/withdraw checks and liquidation eligibility will use wrong data. This can let a user borrow against overstated zToken collateral value, or let an under-collateralized position appear artificially healthy and evade a liquidation that should occur — a direct path to protocol insolvency or theft of funds, since positions are approved/rejected using incorrect collateral/debt totals.

### Likelihood Explanation
The unsafe interleaving requires only ordinary protocol activity within one block/timestamp: (1) any action that triggers `accrue-and-cache` for an asset (populating `index-cache`), followed by (2) `socialize-debt` being executed for the same asset (an intended, market-callable operation), followed by (3) any borrow/withdraw/health-check flow that reads the now-stale cache before the timestamp changes. No attacker-controlled external interference between two different users is required — the mechanism is purely the cache's timestamp-only invalidation versus the vault's out-of-band state mutation.

### Recommendation
Invalidate (or actively refresh) the corresponding `index-cache` entry whenever `socialize-debt` (or any other vault path that mutates `lindex`/`total-borrowed`/`assets` outside of `vault-accrue`) executes, e.g. by having `vault-socialize-debt` in `market.clar` call `map-delete` on `index-cache` for that `aid` immediately after the vault call, or by routing `socialize-debt`'s index update through the same `accrue-and-cache` path so the cache always reflects the latest vault state.

### Proof of Concept
1. Within block `T`, a user action (e.g. a borrow) on asset `aid` calls `accrue-user-debts` → `accrue-and-cache aid`, which is a cache MISS, computes fresh `{index, lindex}` from `vault-accrue`, and stores it in `index-cache {timestamp: T, aid}`. [6](#0-5) 
2. Still within block `T`, `market.clar`'s `vault-socialize-debt aid amount` is invoked, which calls the vault's `socialize-debt`, directly `var-set`ting a new `lindex` reflecting debt write-off — bypassing `index-cache` entirely. [4](#0-3) 
3. A subsequent operation in the same block `T` (e.g. a health check or another borrow) for a position holding zToken `aid` collateral calls `resolve-ztoken`, which reads `get-cached-indexes aid` — a cache HIT returning the stale `lindex` from step 1, not the updated value from step 2. [2](#0-1) 
4. The stale index is used to compute collateral/debt notional value for health-factor evaluation, producing an incorrect solvency assessment for the affected position.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
