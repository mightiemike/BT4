### Title
Threshold-based accounts-index memory limit is silently rounded down to the nearest power of two, causing premature/excess disk write-through and eviction - ([File: accounts-db/src/accounts_index/bucket_map_holder.rs])

### Summary
`BucketMapHolder::calculate_target_entries_per_bin` computes the per-bin entry threshold used to decide when the in-memory accounts index must write-through to disk and start evicting entries. Instead of scaling the configured budget (`entries_per_bin`) directly, it first collapses it to the nearest *lower* power of two via `entries_per_bin.ilog2()` before applying the 7/8 fill factor. This mirrors the class of bug in the referenced report: a value that is supposed to be scaled by a real magnitude/precision factor is instead computed using a coarse, lossy transformation, silently producing a result that can be roughly half of the intended value.

### Finding Description
In `accounts-db/src/accounts_index/bucket_map_holder.rs`: [1](#0-0) 

```rust
fn calculate_target_entries_per_bin(entries_per_bin: usize) -> usize {
    if entries_per_bin == 0 {
        0
    } else {
        // HashMap capacities grow in powers of 2 and typically trigger a reallocation
        // when ~7/8 full. Derive the target as the highest power-of-two capacity that
        // fits within entries_per_bin, then apply the 7/8 factor to stay below the
        // reallocation threshold.
        let entries_per_bin_log2 = entries_per_bin.ilog2();
        (1usize << entries_per_bin_log2) * 7 / 8
    }
}
```

This function is called from `BucketMapHolder::new` when `IndexLimit::Threshold` is configured (i.e. `--accounts-index-memory-limit-mb`), to derive `target_entries_per_bin`, from which `high_water_mark` and `low_water_mark` are derived by subtracting `DEFAULT_NUM_ENTRIES_OVERHEAD` and `DEFAULT_NUM_ENTRIES_TO_EVICT`: [2](#0-1) 

The intent (per the comment) is to stay just under the point where Rust's `HashMap` would reallocate (≈7/8 full), i.e. the target should be `entries_per_bin * 7 / 8`. Instead, `entries_per_bin` is first floored to the nearest power of two (`1usize << entries_per_bin.ilog2()`), which can discard up to almost half of the value whenever `entries_per_bin` is not itself already a power of two. For example, if the computed `entries_per_bin` (derived from the operator's configured memory limit divided evenly across bins) is `1,999,999`, `ilog2()` returns `20` (`2^20 = 1,048,576`), so the resulting target is `1,048,576 * 7 / 8 = 917,504` — less than half of the value that a correct `entries_per_bin * 7 / 8 ≈ 1,749,999` calculation would produce.

This is analogous to the `_computeTokens` bug: a quantity meant to be scaled by a straightforward, precision-preserving factor (7/8) is instead first passed through a lossy, order-of-magnitude-altering transformation (flooring to a power of two), silently and systematically under-provisioning the configured resource.

### Impact Explanation
The `threshold_entries_per_bin` values gate the in-memory accounts-index write-through/eviction logic used by `InMemAccountsIndex` (the accounts-index in-memory cache), which is part of AccountsDB's index/cache-flush machinery. When an operator configures `IndexLimit::Threshold` with a memory budget that does not correspond exactly to a power-of-two number of entries per bin (the overwhelmingly common case), the actual effective threshold used to trigger write-through and eviction can be roughly 50% (worst case, just under a power-of-two boundary) of what the configuration implies. This causes:
- Premature and substantially more frequent write-through-to-disk and eviction cycles than intended, increasing disk I/O and CPU load on the accounts index hot path.
- Under-utilization of the memory budget the operator explicitly configured, defeating the purpose of the `--accounts-index-memory-limit-mb` tuning knob.

This fits the "disproportionate storage and CPU cost" impact category, since a correctly-functioning validator can incur significantly more index eviction/flush I/O and CPU work than the configured threshold should allow, purely due to this rounding defect — not because of any external attacker action.

### Likelihood Explanation
This triggers deterministically for any operator using `IndexLimit::Threshold` (i.e. anyone who sets an explicit accounts-index memory limit) whenever the derived `entries_per_bin` is not an exact power of two, which is the common case given `entries_per_bin` is derived from `limit_bytes / bytes_per_entry / bins` (three divisions of arbitrary configuration values). No attacker interaction is required; this is a straightforward computation bug reachable on any configuration path that uses the index memory-threshold feature.

### Recommendation
Compute the target directly from `entries_per_bin` without first flooring to a power of two:
```rust
fn calculate_target_entries_per_bin(entries_per_bin: usize) -> usize {
    entries_per_bin * 7 / 8
}
```
This preserves the intent described in the comment (stay below the ~7/8 HashMap reallocation threshold) without discarding up to half of the configured memory budget. If the power-of-two rounding was intentional for some other reason (e.g. to align with actual `HashMap` bucket-count growth), that rationale should be documented and the magnitude of loss (up to ~2x) should be called out explicitly, since it silently changes the effective behavior of the `--accounts-index-memory-limit-mb` flag.

### Proof of Concept
1. Configure the validator/accounts-index with `IndexLimit::Threshold` such that the computed `entries_per_bin` (from `limit_bytes / bytes_per_entry / bins`) is just above a power of two, e.g. `entries_per_bin = 1_999_999`.
2. Compute `calculate_target_entries_per_bin(1_999_999)`:
   - `entries_per_bin.ilog2() = 20`
   - `(1 << 20) * 7 / 8 = 917_504`
3. Compare against the value a correct linear scaling would produce: `1_999_999 * 7 / 8 = 1_749_999`.
4. The actual `target_entries_per_bin` (and therefore `high_water_mark`/`low_water_mark`) used to gate write-through/eviction is `917_504`, roughly 47% of the value implied by the configured memory limit — meaning eviction begins, and disk writes occur, at roughly half the intended memory utilization, causing correspondingly more frequent flush/evict work than the configuration was meant to allow.

Note: I was unable to fully trace every downstream consumer of `high_water_mark`/`low_water_mark` in `in_mem_accounts_index.rs` within the available search budget; the described impact (excess I/O/CPU due to premature eviction) follows directly from the documented purpose of these fields but the precise magnitude of runtime overhead was not empirically measured.
