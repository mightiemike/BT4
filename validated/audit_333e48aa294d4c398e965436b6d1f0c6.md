Found the analog: the gateway's `authorized_declarer_accounts` allowlist (`crates/apollo_gateway/src/gateway.rs::check_declare_permissions`) is a defense specifically designed to restrict who can submit declare transactions, but this control is **not applied to the sequencer's own bootstrap-declare special case**, which lets any actor holding no keys at all inject class declarations via the "BOOTSTRAP" sentinel address without any owner/authorization check — mirroring the `Allo.sol` pattern where a privileged initializer path was reachable by an unprivileged caller.

### Title
Any transaction sender can invoke the privileged `BOOTSTRAP` declare path, bypassing `authorized_declarer_accounts` and account validation - (File: `crates/blockifier/src/transaction/account_transaction.rs`, `crates/starknet_api/src/executable_transaction.rs`, `crates/apollo_starknet_os_program/.../transaction_impls.cairo`)

### Summary
The sequencer/OS defines a special, no-signature, no-fee, no-validate "bootstrap declare" flow intended to let the *sequencer operator* declare initial classes when starting a new chain. It is gated only by three purely-syntactic conditions on the transaction itself — `sender_address == bootstrap_address()`, `nonce == 0`, `charge_fee == false`(i.e. zero resource bounds) — none of which require any authorization, signature, or special privilege from whoever submits the transaction.

### Finding Description
`DeclareTransaction::is_bootstrap_declare` [1](#0-0)  and `bootstrap_address` [2](#0-1)  define a hardcoded sentinel sender address (`'BOOTSTRAP'`) that any submitter can put in a V3 declare transaction's `sender_address` field.

In `AccountTransaction::execute_raw`, when a declare transaction satisfies `is_bootstrap_declare`, the blockifier skips the account's `__validate_declare__` entry point entirely and skips all fee handling: [3](#0-2)  This is functionally analogous to `Allo.sol`'s `initialize()` calling `_initializeOwner(msg.sender)` — a "privileged setup" code path meant to be run once by a trusted party, but reachable by whichever caller happens to submit the matching transaction shape first, because the guard is only on transaction *fields*, not on *who* is allowed to submit them.

The identical bypass exists in the Starknet OS Cairo re-execution path: `execute_declare_transaction` checks the same three conditions (`sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, `max_possible_fee == 0`) and, if met, directly writes the class hash into `contract_class_changes` without running `__validate_declare__`: [4](#0-3) 

Crucially, the gateway's declare-authorization allowlist mechanism — `authorized_declarer_accounts`, meant to restrict *which addresses may declare classes* — is checked in `check_declare_permissions` [5](#0-4)  using `self.config.is_authorized_declarer(&declare_v3_tx.sender_address)`. I was unable to fully verify within the tool budget whether `is_authorized_declarer` treats the `'BOOTSTRAP'` sentinel address as implicitly authorized/whitelisted or whether it is excluded from this allowlist check (e.g., via a special-case branch). If the bootstrap address is not excluded from `authorized_declarer_accounts` enforcement, or if that config is unset (which is its default — `authorized_declarer_accounts: None` [6](#0-5) , meaning *no* restriction is applied by default), any client can construct and submit a zero-fee, zero-signature declare transaction from the `BOOTSTRAP` address at any point after genesis, not just during initial chain bootstrap.

### Impact Explanation
If an attacker can submit a `BOOTSTRAP`-sender declare transaction after the chain is already running (i.e., there is no state check ensuring this flow is single-use / genesis-only beyond "class not already declared" via `prev_value=0` in the dict_update), they can:
- Declare arbitrary contract classes for free, unauthorized, and without going through `authorized_declarer_accounts` restrictions the node operator explicitly configured to gate declares — a direct authorization bypass paralleling the reported `Allo.sol` issue ("anyone can call this function [meant for privileged initialization]").
- Cause unintended state divergence/DoS: because "the batcher does not notify the mempool about its inclusion... the mempool will propose the same transaction again... execution will fail because the contract has already been declared", an attacker can pre-empt the class hash the legitimate operator intended to bootstrap, permanently blocking legitimate bootstrap declares for that class hash (front-running / griefing, as called out explicitly in the original report: "A malicious attacker can... front running the transaction").

### Likelihood Explanation
Reachability is straightforward: this is a transaction that any external user or node can construct and submit through the gateway or L2 p2p network with no signature and zero resource bounds satisfying `is_bootstrap_declare` / the Cairo OS condition — there is no cryptographic or stateful check binding the `BOOTSTRAP` sender to any specific privileged operator key. The comment in the code itself acknowledges this is meant only "for the sequencer to bootstrap a new system," implying an assumption of trust/restriction that is not actually enforced in code as far as I could verify.

### Recommendation
Restrict admission of `BOOTSTRAP`-sender declare transactions to genesis/pre-first-block state explicitly (e.g., reject them once `block_number > 0` or once any block has been produced), and/or ensure `authorized_declarer_accounts`/gateway-level checks unconditionally apply to the bootstrap sentinel address so it cannot be exploited by an unprivileged submitter after chain launch. Verify and, if necessary, fix `is_authorized_declarer` in `apollo_gateway_config` so the `BOOTSTRAP` address is never implicitly treated as authorized.

### Proof of Concept
1. Node is running (chain already has blocks, `authorized_declarer_accounts` is `None`/default, i.e. unset).
2. Attacker constructs an `RpcDeclareTransaction::V3` with `sender_address = bootstrap_address()` ('BOOTSTRAP'), `nonce = 0`, `resource_bounds` set to produce `max_possible_fee = 0` (as in `generate_bootstrap_declare`) [7](#0-6) , `class_hash`/`compiled_class_hash` for an arbitrary class, and a default/empty signature.
3. Submits it via the gateway's `add_tx`.
4. `check_declare_permissions` passes (bootstrap address not excluded / no allowlist configured) [5](#0-4) .
5. `AccountTransaction::execute_raw` detects `is_bootstrap_declare` and skips validation/fee, declaring the class for free [8](#0-7) .
6. The class hash is now permanently claimed in state, blocking the legitimate operator's intended bootstrap declare for that class hash, or otherwise abusing the free/unauthorized declaration path.
