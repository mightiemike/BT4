Confirmed: `AllowTvmCompatibleEvm` version-1 contract check exists only in `TransferActuator`, not in `TransferAssetActuator`. This is the strongest concrete analog found.

### Title
Inconsistent enforcement of "no direct transfer to version-1 smart contract" between `TransferActuator` and `TransferAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
The external report describes a class of bug where two code paths that conceptually perform the same operation (minting an NFT to a recipient) use inconsistent safety semantics — one path validates that the recipient can actually make use of what it receives, the other does not — resulting in assets that can be delivered but never usable/claimable by the recipient. The java-tron analog is the divergence between `TransferActuator#validate` (TRX transfers) and `TransferAssetActuator#validate` (TRC10 asset transfers) regarding transfers directed at "version-1" smart contract accounts once `AllowTvmCompatibleEvm` is active.

### Finding Description
`TransferActuator#validate` contains an explicit guard: once the `AllowTvmCompatibleEvm` proposal is active, TRX cannot be sent via the plain `TransferContract` actuator to a smart-contract account whose `contractVersion() == 1`; the caller is told to use `TriggerSmartContract` instead: [1](#0-0) 

`TransferAssetActuator#validate`, which handles the structurally equivalent operation for TRC10 tokens, only checks `getForbidTransferToContract()` and has no equivalent check against `getAllowTvmCompatibleEvm()`/`contractVersion() == 1`: [2](#0-1) 

Both actuators share the identical "toAccount == null → create account, else check `AccountType.Contract`" pattern used for the TRX-specific guard [3](#0-2) , confirming the omission in `TransferAssetActuator` is a gap rather than an intentional design difference — exactly the "inconsistent use of [safety] methods in two different [but structurally identical] code paths" pattern described in the source report.

### Impact Explanation
The `AllowTvmCompatibleEvm`/version-1 restriction exists specifically because version-1 contracts are not guaranteed to correctly process direct value transfers under the new EVM-compatible semantics; this is why `TransferActuator` forces callers through `TriggerSmartContract` for TRX. Because `TransferAssetActuator` lacks the same guard, a TRC10 asset can still be sent directly to a version-1 contract account, bypassing the protocol's own safety rule for that class of contract. Depending on how such a contract handles/represents incoming TRC10 balances under the new EVM engine, the asset can become effectively unrecoverable/unusable to the contract (funds locked in an account the contract logic never expected to receive token balance through this path) — an invalid-state/stuck-asset outcome analogous to the un-claimable NFT DOS in the source report, and a direct violation of consistency guarantees the protocol otherwise enforces for TRX.

### Likelihood Explanation
The check is reachable by any unprivileged user simply broadcasting a `TransferAssetContract` targeting a known version-1 contract address once `AllowTvmCompatibleEvm` is enabled network-wide (it is a chain-wide proposal, not per-transaction opt-in). No special permissions are required, and both actuators are on the standard unprivileged transaction path.

### Recommendation
Add the same `AllowTvmCompatibleEvm`/`contractVersion() == 1` guard to `TransferAssetActuator#validate` that already exists in `TransferActuator#validate`, so TRC10 transfers to version-1 smart contracts are rejected with a message directing users to `TriggerSmartContract`, matching the TRX transfer behavior.

### Proof of Concept
1. Chain has `AllowTvmCompatibleEvm` proposal active.
2. A version-1 smart contract `C` exists (deployed prior to the EVM-compatibility upgrade).
3. Attempt `TransferContract` sending TRX to `C` → actuator rejects with `"Cannot transfer TRX to a smartContract which version is one..."` per [4](#0-3) .
4. Attempt `TransferAssetContract` sending a TRC10 asset to the same `C` → actuator only checks `ForbidTransferToContract`; if that flag is not set, the transfer succeeds despite the contract having the exact same version-1 incompatibility that blocks TRX transfers, per [2](#0-1) .
