### Title
TVM `FREEZE` opcode bypasses the frozen-balance lock period enforced by the normal `FreezeBalanceContract` path - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The bug class in the external report is: a state-mutating operation ("mint shares") is reachable through two different code paths, and one of the paths intentionally applies a time-lock (`shareUnlockTime` / `_afterPublicDeposit`) while the other path (bridge/cross-chain callback) skips it, letting the attacker obtain the unlocked effect earlier than intended. Java-tron has a structurally identical divergence in the freeze/unfreeze resource-locking logic: `FreezeBalanceContract` (the normal, user-facing transaction) enforces a minimum lock duration, while the TVM `FREEZE`/`UNFREEZE` opcodes reach the very same `FreezeBalanceProcessor`/`UnfreezeBalanceProcessor` state transition through `Program.freeze()`/`Program.unfreeze()` but without enforcing any lock duration.

### Finding Description
`FreezeBalanceActuator.validate()` enforces a minimum/maximum frozen duration, gated by a "for test" flag `CommonParameter.getCheckFrozenTime()`: [1](#0-0) 

However, the TVM-reachable equivalent, `Program.freeze()`, unconditionally sets the frozen duration to `0` unless the very same test-only flag is enabled: [2](#0-1) 

That `frozenDuration` value flows directly into `FreezeBalanceProcessor.execute()`, which computes `expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD`: [3](#0-2) 

Critically, `FreezeBalanceProcessor.validate()` (the validation invoked from the TVM opcode path) never checks `frozenDuration` bounds at all — unlike `FreezeBalanceActuator.validate()`, it has no equivalent of the `minFrozenTime`/`maxFrozenTime` check: [4](#0-3) 

In addition, `FreezeBalanceActuator.validate()` explicitly rejects old-style freezing once Stake v2 is active on chain (`supportUnfreezeDelay()`), but `FreezeBalanceProcessor.validate()` has no such guard, so this legacy freeze/unfreeze mechanism remains callable via TVM even after it is supposed to be fully disabled at the network level: [5](#0-4) 

Because `expireTime` ends up equal to (or before) `now` when `frozenDuration = 0`, an account's frozen balance is immediately eligible to be reclaimed via `Program.unfreeze()`, whose processor releases the balance back to the owner as soon as `expireTime <= now`: [6](#0-5) 

This mirrors exactly the report's bug class: the intended lock (`FROZEN_PERIOD`/`minFrozenTime` for freezing, analogous to `shareLockPeriod`) is enforced on the "normal" entry point (`FreezeBalanceContract`), but a second, unprivileged, reachable entry point (a smart contract invoking the `FREEZE`/`UNFREEZE` opcodes) reaches the identical account-state mutation (adding frozen balance, incrementing `TotalNetWeight`/`TotalEnergyWeight`, delegating resources) while skipping the lock enforcement.

### Impact Explanation
Any unprivileged user can deploy a trivial smart contract (see `FreezeTest.sol` in the test suite, which already exercises the `FREEZE`/`UNFREEZE`/`FREEZEEXPIRETIME` opcodes) to freeze TRX for bandwidth/energy and immediately unfreeze it in the same or a following transaction, obtaining bandwidth/energy weight contribution and any delegation side effects without being subject to the intended multi-day lock. This breaks the accounting/economic assumption that frozen TRX is committed for a minimum period (used to back `TotalNetWeight`/`TotalEnergyWeight` and thus resource pricing for the whole network), enabling free-riding/gaming of the resource market with no cost, and it also allows the legacy freeze/unfreeze mechanism to remain exploitable even after `supportUnfreezeDelay()` (Stake v2) is turned on network-wide, causing divergence from the actuator-enforced disablement.

### Likelihood Explanation
High. The precompiled TVM opcodes (`FREEZE`=0xd5, `UNFREEZE`=0xd6, `FREEZEEXPIRETIME`=0xd7) are documented and directly reachable by any account through ordinary smart-contract deployment/calls, requiring no special privilege. The test file `FreezeV2Test.java`/`FreezeTest.sol` shows these opcodes are actively supported and tested, confirming reachability.

### Recommendation
Make `FreezeBalanceProcessor.validate()` (and `Program.freeze()`) enforce the same `minFrozenTime`/`maxFrozenTime` duration checks that `FreezeBalanceActuator.validate()` applies, regardless of the `checkFrozenTime`/test-only flag, and add the `supportUnfreezeDelay()` guard so the TVM opcode path cannot be used once the old-freeze mechanism is disabled network-wide. The `frozenDuration` used for TVM-triggered freezes should never default to `0` in production configurations.

### Proof of Concept
1. Deploy the `FreezeContract`/`Factory` pair shown in the repo's test fixtures, which expose `freeze(target, amount, resource)` and `unfreeze(target, resource)` wrapping the TVM opcodes: [7](#0-6) 
2. Call `freeze(myAddress, amount, BANDWIDTH)`. Internally this invokes `Program.freeze()`, which sets `frozenDuration=0` (since `getCheckFrozenTime()` is a "for test" flag, disabled in production): [8](#0-7) 
3. `FreezeBalanceProcessor.execute()` computes `expireTime = now + 0 = now`, immediately setting the frozen balance's `expireTime` to the current time: [9](#0-8) 
4. Immediately call `unfreeze(myAddress, BANDWIDTH)`. `UnfreezeBalanceProcessor.execute()` sees `expireTime <= now` and refunds the full frozen balance back to the caller in the same block/transaction sequence: [6](#0-5) 

The user has thus obtained the bandwidth/energy weight increment from freezing without incurring the intended lock period, while `FreezeBalanceActuator` (normal-transaction path) would have enforced `minFrozenTime` days before allowing unfreeze.

  public void validate(FreezeBalanceParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(
            "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
    }

    // validate for delegating resource
    byte[] receiverAddress = param.getReceiverAddress();
    if (!FastByteComparisons.isEqual(ownerAddress, receiverAddress)) {
      param.setDelegating(true);

      // check if receiver account exists. if not, then create a new account
      AccountCapsule receiverCapsule = repo.getAccount(receiverAddress);
      if (receiverCapsule == null) {
        receiverCapsule = repo.createNormalAccount(receiverAddress);
      }

      // forbid delegating resource to contract account
      if (receiverCapsule.getType() == Protocol.AccountType.Contract) {
        throw new ContractValidateException(
            "Do not allow delegate resources to contract addresses");
      }
    }
  }
